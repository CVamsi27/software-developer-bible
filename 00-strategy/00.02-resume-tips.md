# Resume Tips for Senior Full Stack Engineers

A hiring manager scanning a stack of applications spends seconds deciding whether to read further or move on. Compare `"Responsible for backend API performance"` with `"Eliminated N+1 catalog queries and added a bounded read cache; p95 latency dropped from 800 ms to 120 ms."` The first line states a job description; the second shows a concrete engineering mechanism and an outcome you can defend in a technical deep dive.

```text
Target Role Requirement ─► Relevant System You Owned ─► Technical Action ─► Verifiable Outcome
```

## Definition

A **resume** is a concise evidence document linking your real engineering work to a target role's requirements. Its job is twofold: help a screener confirm relevance quickly, and give your interviewers concrete projects worth digging into.

> **Textbook Definition:** A resume is a selective professional record that summarizes a candidate's qualifications, employment, and contributions for evaluation against a role's requirements.

## First Principles

Screeners skim before they read, so your strongest, most relevant proof must sit in plain sight on page one. Every claim on your resume is an invitation to a deep follow-up question: truthful scope and real outcomes build trust, while inflated numbers collapse in the first five minutes of a senior technical screen.

## 1. Turn Job Duties Into Evidence-Backed Bullets

Use a simple formula for every bullet: **what you changed + how you engineered it + observable result**. Notice the difference across three realistic senior full-stack examples (numbers below are illustrative — always substitute your own verified facts):

| Weak (responsibility only) | Strong (mechanism + verifiable scope/outcome) |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| *"Worked on React frontend performance."* | *"Replaced full-list re-renders with virtualized rows and memoized filters on a 10k-row billing table, removing typing lag reported by support teams."* |
| *"Responsible for API performance and caching."* | *"Removed repeated catalog queries with a bounded Redis cache and explicit invalidation; p95 fell from 800 ms to 120 ms."* |
| *"Led architecture for microservices migration."* | *"Split invoice generation into an idempotent background worker with a dead-letter queue, eliminating timeout failures during month-end billing runs."* |

**When you do not have an exact percentage:** never fabricate one. Concrete non-percentage outcomes are just as credible — e.g., *"adopted by four product squads,"* *"removed a 45-minute manual deploy step,"* or *"prevented duplicate charges during webhook retries."* Each strong bullet doubles as a seed for your [STAR stories](00.03-star-method.md).

## 2. Structure Page One for Fast Scanning

Keep the top half of page one high-signal:

1. **Header:** Name, city/location (or work-authorization context if helpful), email, GitHub, and LinkedIn. Skip full street addresses and photos unless the local market expects them.
2. **Optional 2-line summary:** Only include one if it states concrete domain, scale, and specialization (*"Senior Full-Stack Engineer (TypeScript, React, Node.js, PostgreSQL) building multi-tenant B2B SaaS and reliable payment/clinical workflows"*). Skip generic fluff like *"passionate problem solver."*
3. **Experience (reverse chronological):** Add one short line of product context under each company so an unfamiliar reader knows what the system does, then 3–5 impact bullets ordered by relevance to the target role.
4. **Grouped skills:** Group cleanly by **Languages**, **Frontend**, **Backend & Data**, and **Platform/Testing** — list only tools you can explain and debug in an interview.
5. **Education / Projects / Writing:** Include open-source or deep personal projects only when they add technical proof your job history does not already cover.

Use **one or two pages** based on how much relevant senior proof you actually have — never shrink fonts to 8pt to squeeze onto one page, and never pad onto two pages with outdated internship tasks.

## 3. Show Senior Scope Explicitly

Mid-level resumes describe tickets closed; senior resumes show **ownership, trade-offs, and leverage**:

- **System ownership:** Name the service, traffic or tenancy boundary, and risk profile you owned.
- **Technical decisions:** State *why* you chose an architecture (e.g., transactional outbox, row-level security, incremental rollout).
- **Cross-team alignment & mentorship:** Show concrete leverage — *"introduced API contract checks that caught breaking schema changes in CI across three teams"* or *"mentored two mid-level engineers to own on-call releases independently"* beats writing `"mentored juniors."`

## 4. Keep Formatting Clean for Both Humans and ATS Parsers

Applicant Tracking Systems vary widely in how they extract text — there is no universal auto-rejection formula or fixed scan timer, but multi-column graphics, text inside images, and exotic icons routinely scramble extracted text.

| Check | Why it matters |
| ----------------------------------------------------------- | -------------------------------------------------------------- |
| **Standard headings** (`Experience`, `Skills`, `Education`) | Both humans and ATS parsers locate sections reliably |
| **Single-column layout & clean spacing** | Easy to skim on a laptop screen; survives PDF text extraction |
| **Consistent date & title formatting** | Makes tenure and progression obvious at a glance |
| **Role-matched vocabulary (truthful only)** | Surfaces real matching skills without keyword stuffing |
| **Copy-paste test on exported PDF** | Visually neat PDFs can still copy out in garbled reading order |

Export to PDF (unless the employer asks for `.docx`), open it, select all text, paste it into a plain text editor, and verify that every line reads in the right order and every link clicks through.

## 5. Tailor From One Master Document

Keep one comprehensive **master achievement record** in your private workspace with every project, architecture decision, and measured result. For each application, select the 3–5 bullets per role that match the posting's actual engineering problems. Never add a framework from the job description unless you can defend it under probing questions.

Before submitting, run a 30-second peer test: hand the PDF to another engineer for half a minute, take it away, and ask what domain, stack, and biggest impact they remember. If they cannot answer, tighten the top half of page one.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------- | --------------------------------------------------------------------- |
| Listing daily duties (*"Maintained Node APIs"*) | Describe a specific change, mechanism, and outcome |
| Inventing percentages to look impressive | Use verifiable counts, latency, adoption, or eliminated failure modes |
| Dumping every library ever installed | Keep only technologies you can debug live in an interview |
| Stuffing unowned job-description keywords | Show where you genuinely applied the skill (or leave it out) |
| Sending an unchecked PDF export | Run the copy-paste extraction test and click every URL |

## Summary

Build your resume from verifiable engineering evidence, lead each bullet with a concrete mechanism and outcome, and put your strongest senior ownership on page one. Format cleanly so both recruiters and ATS parsers read it in order, tailor emphasis from a single master achievement record without inventing metrics, and make sure you have a deep technical story ready behind every prominent line.

# Execution Context

When a function pauses to invoke another function, how does JavaScript remember where the caller paused, where its return value should go, and which variables are in scope? The engine manages this runtime state through **execution contexts**.

```javascript
const label = 'outside';

function describe(value) {
  const message = `${label}: ${value}`;
  return message;
}

console.log(describe(7)); // outside: 7
```

## Definition

An **execution context** is the specification mechanism for tracking an active or suspended evaluation. For ECMAScript code it includes references to the **environments** used for identifier resolution, the active **realm** (intrinsics and global environment), and the state needed to continue evaluation. Calls nest contexts; returning resumes the caller. A returned closure retains access to bindings, not a completed call on the stack.

> **Textbook Definition:** An execution context is a specification record that tracks the code being evaluated, the environments used by that evaluation and the state needed to continue it. An execution can be active or suspended for later resumption.

## First Principles

A language with function calls, lexical nesting, and async resumption must solve two problems. **Continuation tracking**: when a caller transfers control to a callee, evaluation must preserve enough state to resume at the right place. **Environment isolation**: the callee needs private storage for arguments and locals while keeping deterministic access to outer bindings from the source text. JavaScript packages these into the **call stack** (control flow) and **environment records** (identifier resolution).

## 1. The Anatomy of an Execution Context

In the ECMAScript specification, an execution context is a record of state components:

| Component | Responsibility |
| :----------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| **`code evaluation state`** | Abstract state needed to evaluate, suspend or resume code; no bytecode or register layout is prescribed. |
| **`Function`** | Points to the function object being evaluated (null for global scripts). |
| **`Realm`** | The execution environment providing built-in intrinsics (`Array`, `Object`, `Math`) and the global object. |
| **`ScriptOrModule`** | Identifies the source script or ES module contributing the code. |
| **`LexicalEnvironment` (LE)** | The Environment Record used to resolve bare identifier names at the current instruction. |
| **`VariableEnvironment` (VE)** | The Environment Record that houses declarations introduced by `var` statements. |
| **`PrivateEnvironment`** | The private-name environment used to resolve class `#private` names, rather than the field values stored on instances. |

## 2. Entry Points Share a Realm, Not One Permanent Call

A realm supplies intrinsics, a global object and a global environment. Its lifetime is distinct from the lifetime of an evaluation:

- **Classic script evaluation** enters a context that uses the realm's global environment. That script can finish while its global bindings remain available to later scripts and callbacks; its context need not sit on the stack until the host terminates.
- **Function invocation** establishes the state for that call. Ordinary functions can have their own receiver and arguments; arrows use lexical `this` and do not create an implicit `arguments` binding.
- **Module evaluation** uses a module environment for top-level declarations and imports. Its outer environment still permits global-name lookup; module-local `var` does not become a global-object property.
- **Eval evaluation** has additional direct/indirect and strict/sloppy rules. Direct eval can use the caller's lexical context; sloppy direct eval can introduce eligible `var` bindings there. Indirect eval uses the global environment.

These are useful code-entry cases, not an exhaustive classification of engine frames. The specification also models built-in calls and suspended evaluations. See [ECMAScript execution contexts](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-execution-contexts).

## 3. Declaration Setup Precedes Statement Evaluation

For a given scope, distinguish declaration instantiation from evaluating its statements. This describes observable language semantics, not two mandatory compiler passes:

```text
Scope entry
  → establish applicable bindings
  → initialize var and eligible function declarations
  → leave lexical declarations uninitialized until evaluated
Statement evaluation
  → read/write bindings under those rules
  → enter nested calls and scopes as required
```

The applicable script, module, function or block algorithms establish bindings before that scope's statements run. They initialize `var` and eligible function declarations differently from lexical declarations. Module linking has its own setup rules. Parsing, bytecode generation and JIT compilation are engine strategies; they are not the operation that makes a binding readable during a particular call.

## 4. Stack Frames vs. Block Scope (Why Blocks Don't Push New Contexts)

A common misconception is that every `{ ... }` block pushes a new execution context. It does not:

- **Function invocations** establish a nested evaluation context. Engines may inline calls or otherwise change their physical frame representation.
- **Blocks (`if`, `for`, `{}`)** only swap the running context's `LexicalEnvironment` (LE) pointer to a new Declarative Environment Record, leaving `VariableEnvironment` (VE) on the enclosing function.

```javascript
'use strict';
function traceScope() {
  var fnVar = 1;
  let fnLet = 2;

  {
    // NO new Execution Context is pushed to the call stack!
    // LE points to a new Block Declarative Record { blockLet: 3 }
    // VE still points to the Function Record { fnVar: 1 }
    let blockLet = 3;
    var fnVar = 100; // Evaluated in VE (function boundary)

    console.log(fnVar, fnLet, blockLet); // 100, 2, 3
  }

  // Block Exit: LE is restored to the enclosing body environment
  console.log(fnVar, fnLet); // 100, 2
}
traceScope();
```

On block exit `LE` is restored. The distinction explains lookup and call nesting; it does not establish a particular allocation cost.

## Parameter and body bindings can differ

Parameter expressions such as default initializers can require separate environments for parameter evaluation and body variables. There is no distinct specification record type named Parameter Environment Record. Non-simple syntax alone is not a universal rule that every function has the same extra environment:

```javascript
function chooseReader(value = 'parameter', read = () => value) {
  var value = 'body';
  return [read(), value];
}
console.log(chooseReader()); // ['parameter', 'body']
```

Why does `read()` return `'parameter'`? The default initializer creates `read = () => value` in the environment used to evaluate those defaults, so the function retains access to that parameter binding. The body then creates a separate **body variable environment** for `var value = 'body'`. `read()` still references the parameter slot, leaving the body `value` isolated.

## 5. Engine Realities: Native Call Stack vs. Spec Records

Contexts and Environment Records are specification structures, not required dictionary objects in memory. An engine may use registers, native frames, heap contexts, inlining or reconstructed state while preserving the same result:

- **Local values**: a value may live in a register or frame slot, be eliminated, or require materialized storage. Source syntax alone does not prove its representation.
- **Retained bindings**: escaping closures need continued access to their bindings. Captures, dynamic evaluation and optimization decisions can affect what is materialized; escape is not the only possible reason for a heap context.
- **Suspended work**: generators and async functions retain enough state to resume. Generator resumption and Promise-job scheduling are different triggers; neither requires a suspended call to occupy one native frame while waiting.

## Summary

An execution context carries the continuation state and environment references for a unit of executing code. The call stack coordinates nesting and return addresses, while LexicalEnvironment and VariableEnvironment resolve identifiers. Block scopes change the active binding environment without making a function call, and parameter expressions can create a boundary distinct from body variables. A realm can outlive the evaluation that used it. Engines choose physical storage and compilation strategies; closures retain bindings rather than completed stack frames.

# Execution Context

When a function pauses to invoke another function, how does JavaScript remember where the caller paused, where its return value should go, and which variables are in scope? The engine manages this runtime state through **execution contexts**.

```javascript
const label = 'outside';

function describe(value) {
  const message = `${label}: ${value}`;
  return message;
}

console.log(describe(7)); // outside: 7
```

## Definition

An **execution context** is the specification mechanism that encapsulates all runtime state required to evaluate or resume a unit of JavaScript code. Every context tracks the code under evaluation, pointers to the **lexical environments** used for identifier resolution, the active **realm** (built-in globals and prototypes), and suspension state for generators or async continuations. Calling a function pushes a new context onto the call stack; returning pops it and resumes the caller.

> **Textbook Definition:** An execution context is a specification record that tracks the code being evaluated, the environments used by that evaluation and the state needed to continue it. An execution can be active or suspended for later resumption.

## First Principles

A language with function calls, lexical nesting, and async resumption must solve two problems. **Continuation tracking**: when a caller transfers control to a callee, the machine must preserve the caller's instruction pointer and return address so it resumes seamlessly. **Environment isolation**: the callee needs private storage for arguments and locals while keeping deterministic access to outer bindings from the source text. JavaScript packages these into the **call stack** (control flow) and **environment records** (identifier resolution).

## 1. The Anatomy of an Execution Context

In the ECMAScript specification, an execution context is a record of state components:

| Component | Responsibility |
| :----------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **`code evaluation state`** | Position in the bytecode stream, registers, and resumption state (used by generators and async/await). |
| **`Function`** | Points to the function object being evaluated (null for global scripts). |
| **`Realm`** | The execution environment providing built-in intrinsics (`Array`, `Object`, `Math`) and the global object. |
| **`ScriptOrModule`** | Identifies the source script or ES module contributing the code. |
| **`LexicalEnvironment` (LE)** | The Environment Record used to resolve bare identifier names at the current instruction. |
| **`VariableEnvironment` (VE)** | The Environment Record that houses declarations introduced by `var` statements. |
| **`PrivateEnvironment`** | The environment record tracking class `#private` fields and methods. |

## 2. The Three Types of Execution Contexts

Code always evaluates inside one of three context types:

1. **Global Execution Context (GEC)** — created once when the engine starts evaluating a top-level script. It instantiates the global object (`window` in browsers, `globalThis` universally) and sits at the bottom of the call stack until the program terminates.
2. **Function Execution Context (FEC)** — instantiated on every ordinary function, method, or arrow invocation. It allocates parameter bindings, the `this` binding, and local declarations, then pops off the stack on return (unless a closure retains it).
3. **Eval Execution Context** — created for code strings inside `eval()`. In strict mode it runs in its own private lexical scope; in sloppy mode it can pollute the caller's variable environment.

## 3. Lifecycle: Creation Phase vs. Execution Phase

Every context runs through two passes:

```text
┌────────────────────────────────────────────────────────┐
│ 1. CREATION PHASE (Compile / Allocation Pass)          │
│ - Create Environment Record                            │
│ - Hoist 'var' (initialized to undefined)               │
│ - Hoist 'function' declarations (fully initialized)     │
│ - Register 'let', 'const', 'class' (uninitialized TDZ) │
│ - Determine 'this' binding                             │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. EXECUTION PHASE (Evaluation Pass)                   │
│ - Assign values to variables                           │
│ - Execute expressions and function invocations         │
│ - Push callees / pop upon return                       │
└────────────────────────────────────────────────────────┘
```

The **creation phase** scans the block before running a single statement and registers every declaration. The **execution phase** then evaluates assignments and instructions sequentially.

## 4. Stack Frames vs. Block Scope (Why Blocks Don't Push New Contexts)

A common misconception is that every `{ ... }` block pushes a new execution context. It does not:

- **Function invocations** push a brand-new execution context (and physical stack frame) onto the call stack.
- **Blocks (`if`, `for`, `{}`)** only swap the running context's `LexicalEnvironment` (LE) pointer to a new Declarative Environment Record, leaving `VariableEnvironment` (VE) on the enclosing function.

```javascript
'use strict';
function traceScope() {
  var fnVar = 1;
  let fnLet = 2;

  {
    // NO new Execution Context is pushed to the call stack!
    // LE points to a new Block Declarative Record { blockLet: 3 }
    // VE still points to the Function Record { fnVar: 1 }
    let blockLet = 3;
    var fnVar = 100; // Evaluated in VE (function boundary)

    console.log(fnVar, fnLet, blockLet); // 100, 2, 3
  }

  // Block Exit: LE is restored to the Function Record
  console.log(fnVar, fnLet); // 100, 2
}
traceScope();
```

On block exit `LE` is restored. This avoids the cost of allocating stack frames for plain blocks.

## Parameter and body bindings can differ

With default parameters, destructuring, or rest arguments, ECMAScript creates an intermediate **Parameter Environment Record** between the outer scope and the function body:

```javascript
function chooseReader(value = 'parameter', read = () => value) {
  var value = 'body';
  return [read(), value];
}
console.log(chooseReader()); // ['parameter', 'body']
```

Why does `read()` return `'parameter'`? The default initializer creates `read = () => value` while the **parameter environment** is active, so its `[[OuterEnv]]` links to that parameter scope. The body then creates a separate **body variable environment** for `var value = 'body'`. `read()` still references the parameter slot, leaving the body `value` isolated.

## 5. Engine Realities: Native Call Stack vs. Spec Records

The spec describes contexts and environment records as abstract dictionary objects. Production engines like V8 optimize them aggressively:

- **Hardware stack frames**: for ordinary functions without escaping closures, variables live in CPU registers or native stack offsets.
- **Heap contexts for closures**: only when a nested function escapes and captures outer variables does V8 allocate a heap-based `Context` object.
- **Heap-saved continuations**: suspended generators and async tasks save their context state in heap objects, restored to the native stack when the microtask queue resumes them.

## Summary

An execution context carries the continuation state and environment references for a unit of executing code. The call stack coordinates nesting and return addresses, while LexicalEnvironment and VariableEnvironment resolve identifiers. Block scopes swap environment pointers without pushing new contexts, and parameter initializers can form a scope boundary distinct from the function body. Engines map these abstractions onto CPU registers and native stack frames for throughput.

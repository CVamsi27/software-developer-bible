# Execution Context

## Definition

An **execution context** records what JavaScript needs to run a piece of code or resume it later. It tracks the code, the environments used to find variables, and other execution state. This is a model in the language specification; engines do not have to store it in one physical memory container. Calling a function creates execution state for that call. Entering a block can create a new environment for its variables without calling another function.

## First Principles

1. A function call needs to know which code to run and where its caller should continue afterward.
2. Reading a variable name requires finding the right variable. The name is associated with that variable through a **binding**. The running code keeps references to the environments used to find those bindings.
3. A call can finish while a returned function still needs its variables. A **closure** keeps that access after the call returns.

## Follow One Call

```javascript
const label = 'outside';
function describe(value) {
  const message = `${label}: ${value}`;
  return message;
}
console.log(describe(7)); // outside: 7
```

1. The surrounding script or module establishes its declarations. `describe` is available as a function; the lexical `label` binding becomes initialized when its declaration executes.
2. Calling `describe(7)` starts a function evaluation with a fresh parameter binding `value = 7`.
3. Evaluating the initializer reads `value` from the call's environment and `label` through the function's enclosing lexical environment.
4. The return supplies `message` to the caller; the call's evaluation leaves the active stack.
5. `console.log` receives the returned string. It does not execute inside the completed `describe` call.

```text
active evaluation              name resolution
script/module                  describe call → enclosing script/module
  └─ describe(7)               value: 7         label: 'outside'
       └─ return string        message: 'outside: 7'
```

The call stack answers “what is executing?” The environment chain answers “where does this identifier resolve?” They cooperate, but they are not the same chain.

## Declaration Setup and Execution

“Creation phase, then execution phase” is a teaching shortcut: JavaScript sets up declarations before evaluating statements in the relevant scope. The specification calls that setup **declaration instantiation**. This does not require the engine to allocate every value in one scan, or put the variables from every nested block into one flat record.

| Declaration | Before its declaration executes in the relevant scope |
| ----------------------------- | ------------------------------------------------------------------------------- |
| `var` | Binding initialized to `undefined` |
| Ordinary function declaration | Function available after declaration instantiation, with scope-specific details |
| `let` / `const` / class | Binding uninitialized; access throws in the temporal dead zone |

A `let` inside a nested block belongs to that block's environment. Modules have their own environment and strict semantics. See [Hoisting](10.1.1.04-hoisting.md) for the cases rather than repeating their examples here.

## What `this` Depends On

For an ordinary function, the way you call it supplies `this`, often the object a method should work on. That value is called the **receiver**. An arrow function uses `this` from its surrounding scope instead of getting a new receiver from its call.

```javascript
'use strict';
const user = {
  name: 'Alice',
  greet() { return this.name; },
};
console.log(user.greet()); // Alice
const detached = user.greet;
// detached(); // TypeError: this is undefined
const bound = user.greet.bind(user);
console.log(bound()); // Alice
```

| Invocation | `this` behavior |
| --------------------------------- | ------------------------------------------------------------- |
| `object.method()` | Receiver object |
| Plain strict function call | `undefined` |
| Plain sloppy function call | Global object after ordinary this conversion |
| `call` / `apply` / bound function | Explicit value, subject to the function's mode and conversion |
| Arrow function | Enclosing lexical `this`; call/apply cannot replace it |
| Constructor call | Constructed receiver, subject to constructor return rules |

A browser classic script, an ES module and a CommonJS module differ at top level. Do not assume every global context creates `window` or sets top-level `this` to it. The host supplies the global environment; module top-level `this` is `undefined`.

## Returning Does Not Destroy Captured State

```javascript
function makeReader(value) {
  return () => value;
}
const read = makeReader(42);
console.log(read()); // 42, after makeReader returned
```

The finished call no longer occupies the active call stack. The returned function retains the lexical access it needs. This is the [closure mechanism](10.1.1.06-closures.md), not a dormant call that remains on the stack.

Direct `eval` introduces special evaluation rules; sloppy direct eval can affect the caller's variable environment, while strict eval keeps its declarations isolated. Avoid eval for untrusted code and prefer a data format or explicit dispatch.

## Common Mistakes

| Mistake | Repair |
| ------------------------------------------------------------- | -------------------------------------------------------------- |
| Equating a block with a new function execution context | Separate block environments from call evaluations |
| Treating environment records as a mandated heap layout | Use the language model; engines may optimize physical storage |
| Assuming lexical bindings are global-object properties | Distinguish classic-script global lexical bindings and modules |
| Saying a closure keeps a whole execution context on the stack | It retains lexical access after evaluation returns |
| Losing a method receiver in a callback | Bind deliberately or use a suitable closure |

## Summary

Execution contexts track active or resumable evaluations; environments resolve names. Trace the call, its declaration setup, the identifiers it reads and the return to its caller. Keep invocation-based `this`, lexical scope and retained closure state as distinct mechanisms.

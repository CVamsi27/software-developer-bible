# Execution Context

When a function pauses to call another function, JavaScript must remember what is running and where the caller should continue. It must also know which environment the current code uses to resolve names.

## Definition

An **execution context** is the specification model for the state needed to evaluate or resume JavaScript code. It associates an evaluation with its code and environment references, along with other execution state. A function call creates a new context; entering a block can change the environment used for name lookup without creating a function call. Engines may represent this state in different ways.

> **Textbook Definition:** An execution context is a specification record that tracks the code being evaluated, the environments used by that evaluation and the state needed to continue it. An execution can be active or suspended for later resumption.

## First Principles

1. A caller pauses at a function call and needs a continuation point so it can resume when that call returns.
2. The called code needs its own parameters and local state, plus access to surrounding bindings according to lexical scope.

## Follow one call

```javascript
const label = 'outside';
function describe(value) {
  const message = `${label}: ${value}`;
  return message;
}
console.log(describe(7)); // outside: 7
```

Calling `describe(7)` creates an evaluation with its own `value` binding. The expression reads `value` there, then resolves `label` through the environment surrounding the function. Returning the string finishes that call, and the caller continues with the result.

```text
active evaluation             environment used for names
script or module              its own top-level environment
  └─ describe(7)               value = 7 → outer label = 'outside'
       └─ returns string      'outside: 7'
```

The **call stack** tracks unfinished calls and their continuation points. The **environment chain** resolves identifiers. A function can be called by one function while looking up a name through a different, source-defined environment. Follow [Scope](10.1.1.02-scope.md) and [Lexical Environment](10.1.1.05-lexical-environment.md) for that lookup rule.

## A block changes lookup without making a call

An execution context refers to the environments used by its current evaluation. The specification names two roles: **LexicalEnvironment (LE)** is where identifier lookup starts, and **VariableEnvironment (VE)** identifies the environment used for `var` declarations during setup. In a simple function they can refer to the same record. A nested block can change LE while VE continues to point at the function's `var` boundary.

```javascript
'use strict';
function showBindings() {
  var shared = 'function';
  let local = 'function';
  {
    var shared = 'still function';
    let local = 'block';
    console.log(shared, local); // still function, block
  }
  console.log(shared, local); // still function, function
}
showBindings();
```

On block entry, LE points to a new block environment containing the inner `local`; VE still identifies the function environment containing `shared`. Reads of either name start at LE and follow its outer link. On block exit, lookup resumes from the function environment. LE and VE therefore describe roles in setup and lookup, not two competing ways to read a variable. The [Lexical Environment chapter](10.1.1.05-lexical-environment.md#le-and-ve-name-different-roles) traces the records and initialization states.

Parameter initializers can add a separate parameter environment before the function body begins. A function created by a default parameter can keep reading that parameter even when the body declares a same-named `var`. The [parameter trace](#parameter-and-body-bindings-can-differ) shows this boundary.

### Parameter and body bindings can differ

```javascript
function chooseReader(value = 'parameter', read = () => value) {
  var value = 'body';
  return [read(), value];
}
console.log(chooseReader()); // ['parameter', 'body']
```

The default initializer creates `read` while the parameter environment is active. The body's `var value` has a distinct binding, so the returned function still reads `'parameter'`. Parameter expressions, strictness and direct `eval` affect declaration setup; consult the [specification's FunctionDeclarationInstantiation algorithm](https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-functiondeclarationinstantiation) when analyzing those edge cases.

## Keep the model separate from neighboring rules

Declaration setup determines when bindings exist and become initialized; [Hoisting](10.1.1.04-hoisting.md) follows those states. Invocation determines an ordinary function's `this`, while arrows use lexical `this`; see [This](../02-objects-prototypes-this/10.1.2.01-this.md). A returned function can retain access after its call finishes, which is the [closure mechanism](10.1.1.06-closures.md). These rules interact, but each answers a different question.

An execution-context diagram predicts observable language behavior. It does not specify an engine's physical stack layout, variable storage or garbage-collection timing. Measure those properties in the runtime when they affect a production decision.

## Summary

An execution context tracks one evaluation and the state needed to continue it. The call stack explains which call resumes; environment references explain where names resolve. Blocks can change lookup environments without adding function calls, and parameter initialization can create a distinct boundary from the function body.

# Execution Context

When a function pauses to invoke another function, how does JavaScript remember where the caller paused, where its return value should go, and which variables are in scope? The engine manages this runtime state through **execution contexts**.

```javascript
const label = 'outside';

function describe(value) {
  const message = `${label}: ${value}`;
  return message;
}

console.log(describe(7)); // outside: 7
```

## Definition

An **execution context** is the specification mechanism that encapsulates all runtime state required to evaluate or resume a unit of JavaScript code. Every execution context tracks the currently evaluating script or function, pointers to the lexical environments used for identifier resolution, the active realm (built-in globals and prototypes), and suspension state for generators or async continuations. A function invocation pushes a new execution context onto the call stack; exiting returns control to the caller's context.

> **Textbook Definition:** An execution context is a specification record that tracks the code being evaluated, the environments used by that evaluation and the state needed to continue it. An execution can be active or suspended for later resumption.

## First Principles

Any program that supports function calls, lexical nesting, and asynchronous resumption must satisfy two fundamental computational requirements:
1. **Continuation Tracking**: When control transfers from a caller to a callee, the machine must preserve the caller's exact instruction pointer, stack offset, and return address so execution resumes seamlessly when the callee completes.
2. **Environment Isolation**: The callee needs private storage for its arguments and local variables while maintaining deterministic, static access to outer enclosing bindings defined in the source code.

JavaScript packages these two responsibilities into the **Call Stack** (tracking execution flow) and **Environment Records** (resolving identifiers).

## How It Works

### 1. The Anatomy of an Execution Context

In the ECMAScript specification, an Execution Context is a record containing state components:

| Component | Responsibility |
| :----------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **`code evaluation state`** | Position in the bytecode stream, registers, and resumption state (used by generators and async/await). |
| **`Function`** | Points to the function object being evaluated (null for global scripts). |
| **`Realm`** | The execution environment providing built-in intrinsics (`Array`, `Object`, `Math`) and the global object. |
| **`ScriptOrModule`** | Identifies the source script or ES module contributing the code. |
| **`LexicalEnvironment` (LE)** | The Environment Record used to resolve bare identifier names at the current instruction. |
| **`VariableEnvironment` (VE)** | The Environment Record that houses declarations introduced by `var` statements. |
| **`PrivateEnvironment`** | The environment record tracking class `#private` fields and methods. |

### 2. The Three Types of Execution Contexts

JavaScript code evaluates within one of three context types:

1. **Global Execution Context (GEC)**:
   - Created exactly once when the JavaScript engine starts evaluating a top-level script.
   - Instantiates the global object (`window` in browsers, `global` in Node.js, accessible via `globalThis`).
   - Sits permanently at the bottom of the Call Stack until the application terminates.

2. **Function Execution Context (FEC)**:
   - Instantiated whenever an ordinary function, method, or arrow function is invoked.
   - Allocates parameter bindings, `this` binding, and local declarations.
   - Pushed onto the Call Stack when called, and popped off upon returning (unless retained by a closure).

3. **Eval Execution Context**:
   - Created when evaluating code strings inside `eval()`.
   - In strict mode (`'use strict'`), runs in its own private lexical scope; in sloppy mode, can pollute the caller's variable environment.

### 3. Lifecycle: Creation Phase vs. Execution Phase

Every execution context runs through two distinct phases:

```text
┌────────────────────────────────────────────────────────┐
│ 1. CREATION PHASE (Compile / Allocation Pass)          │
│ - Create Environment Record                            │
│ - Hoist 'var' (initialized to undefined)               │
│ - Hoist 'function' declarations (fully initialized)     │
│ - Register 'let', 'const', 'class' (uninitialized TDZ) │
│ - Determine 'this' binding                             │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. EXECUTION PHASE (Evaluation Pass)                   │
│ - Assign values to variables                           │
│ - Execute expressions and function invocations         │
│ - Push callees / pop upon return                       │
└────────────────────────────────────────────────────────┘
```

During the **Creation Phase**, the engine scans the code block before running a single statement. It registers all identifier declarations into the environment record. During the **Execution Phase**, the engine evaluates assignments, reads values, and executes instructions sequentially.

### 4. Stack Frames vs. Block Scope (Why Blocks Don't Push New Contexts)

A common misconception is assuming every `{ ... }` block pushes a new execution context onto the call stack.

- **Function Invocations**: Push a brand-new Execution Context (and physical stack frame) onto the Call Stack.
- **Blocks (`if`, `for`, `{}` )**: Do **not** create a new execution context. Instead, the currently running execution context simply swaps its `LexicalEnvironment` (LE) pointer to a new Declarative Environment Record while leaving `VariableEnvironment` (VE) pointing to the enclosing function.

```javascript
'use strict';
function traceScope() {
  var fnVar = 1;
  let fnLet = 2;

  {
    // NO new Execution Context is pushed to the call stack!
    // LE points to a new Block Declarative Record { blockLet: 3 }
    // VE still points to the Function Record { fnVar: 1 }
    let blockLet = 3;
    var fnVar = 100; // Evaluated in VE (function boundary)

    console.log(fnVar, fnLet, blockLet); // 100, 2, 3
  }

  // Block Exit: LE is restored to the Function Record
  console.log(fnVar, fnLet); // 100, 2
}
traceScope();
```

When the block terminates, `LE` restores its previous pointer. This avoids the severe performance cost of allocating stack frames for simple blocks.

### Parameter and body bindings can differ

When a function uses default parameters, destructuring, or rest arguments, ECMAScript creates an intermediate **Parameter Environment Record** between the outer scope and the function body.

```javascript
function chooseReader(value = 'parameter', read = () => value) {
  var value = 'body';
  return [read(), value];
}
console.log(chooseReader()); // ['parameter', 'body']
```

Why does `read()` output `'parameter'` instead of `'body'`?
1. The default parameter initializer creates `read = () => value` while the **Parameter Environment** is active. Its `[[OuterEnv]]` links to that parameter scope.
2. When the function body executes, the engine creates a separate **Body Variable Environment** for the body's `var value = 'body'`.
3. `read()` still references the parameter slot in the parameter environment, leaving the body `value` isolated.

### 5. Engine Realities: Native Call Stack vs. Spec Records

The ECMAScript specification describes execution contexts and environment records as abstract dictionary objects. Production engines like V8 optimize them aggressively:

- **Hardware Stack Frame Allocation**: For ordinary functions without escaping closures, variables live in CPU registers (`RAX`, `RBX`) or native stack offsets (`RBP - 8`).
- **Context Objects for Closures**: Only when a nested function escapes and captures outer variables does V8 allocate a heap-based `Context` object.
- **Micro-tasks and Generators**: Suspended generators and async tasks save their execution context state in heap objects that can be restored to the native stack when the microtask queue resumes them.

## Summary

An execution context manages the continuation state and environment references for executing code. The Call Stack coordinates function nesting and return addresses, while LexicalEnvironment and VariableEnvironment resolve identifiers. Block scopes modify environment pointers without pushing new execution contexts, and parameter initializers can establish a distinct scope boundary from the function body. Modern engines map these abstractions directly to CPU registers and native stack frames for optimal throughput.

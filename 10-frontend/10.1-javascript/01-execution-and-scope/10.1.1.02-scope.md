# Scope

Why does a `var` declared inside an `if` block stay visible throughout the whole function, while a `let` in the same spot throws a `ReferenceError` outside the block? The two keywords register their bindings at different declaration boundaries.

```javascript
function demoScope() {
  if (true) {
    var functionScoped = 'accessible outside block';
    let blockScoped = 'isolated inside block';
  }
  console.log(functionScoped); // 'accessible outside block'
  // console.log(blockScoped); // ReferenceError: blockScoped is not defined
}
demoScope();
```

## Definition

**Scope** is the region of source code in which an identifier (variable, function, class) is visible and accessible. JavaScript enforces **lexical scoping** (static scoping): boundaries come from the physical nesting of functions and blocks at parse time, never from runtime call order. A **binding** is the association between an identifier name and its variable record.

> **Textbook Definition:** Scope is the region in which a declaration contributes a binding for identifier resolution. Lexical scope derives that resolution from source nesting rather than the sequence of function calls.

## First Principles

Scopes exist to solve two problems. **Name collision prevention**: programs reuse names like `index` and `result`, so scopes partition memory into namespaces where identical names cannot silently overwrite each other. **Deterministic lookup**: tying resolution to static source structure instead of the dynamic call stack guarantees a function behaves identically no matter who calls it.

## How It Works

### 1. The Four Scope Levels

JavaScript has four tiers of lexical scope:

| Scope Level | Enclosing Boundary | Typical Declarations |
| :----------------- | :--------------------------------------------------------------------- | :-------------------------------------------------------------------------------- |
| **Global Scope** | Entire JavaScript runtime environment. | Top-level classic script declarations, built-in globals (`Object`, `Math`). |
| **Module Scope** | Single ES module file (`<script type="module">`). | Top-level `import`, `export`, `const`, `let`, `var`. Isolated from global object. |
| **Function Scope** | Function body enclosed by `function() { ... }`. | `var` declarations, function parameters, `arguments`. |
| **Block Scope** | Any pair of curly braces `{ ... }` (`if`, `for`, `while`, raw blocks). | `let`, `const`, `class`, explicit functions in strict mode. |

### 2. Lexical Resolution and Shadowing

The engine resolves an identifier by searching from the innermost lexical environment outward along the `[[OuterEnv]]` chain, stopping at the first match:

```javascript
const value = 'module';

function outer() {
  const value = 'function';

  if (true) {
    const value = 'block';
    console.log(value); // 'block' (block binding found first)
  }

  console.log(value);   // 'function' (outer function binding)
}
outer();
console.log(value);     // 'module' (top-level binding)
```

```text
Inside if-block:  [Block Environment: value='block']
                           │
                           ▼ (outer link)
Inside function:  [Function Environment: value='function']
                           │
                           ▼ (outer link)
Global / Module:  [Module Environment: value='module']
```

When an inner scope redeclares an outer name it **shadows** the outer binding: the outer variable is untouched, but inner lookups never reach it.

### 3. Comparing Declaration Boundaries: var vs. let vs. const

The keyword decides which Environment Record receives the binding:

| Declaration | Scope Boundary | Hoisting State | TDZ Active? | Reassignable? |
| :---------- | :------------------------------------- | :------------------------- | :---------- | :-------------------------- |
| **`var`** | Enclosing Function or Global Object ER | Initialized to `undefined` | No | Yes |
| **`let`** | Enclosing Block / Function / Loop | Uninitialized | Yes | Yes |
| **`const`** | Enclosing Block / Function / Loop | Uninitialized | Yes | No (Immutable binding) |
| **`using`** | Enclosing Block | Uninitialized | Yes | No (Disposed on block exit) |

Two distinctions matter in practice. **`const` freezes the binding, not the value**: `const user = { name: 'Alice' }` forbids `user = {}` but allows `user.name = 'Bob'` — use `Object.freeze()` for deep immutability. **Sloppy-mode assignment creates globals**: assigning to an undeclared identifier (`undeclaredVar = 42`) writes a `globalThis` property, while strict mode throws a `ReferenceError` immediately.

### 4. A Fresh Binding for Each Loop Iteration

The classic loop-callback bug comes from `var` sharing one binding across iterations:

```javascript
// Problem: var shares a single binding across all iterations
const varCallbacks = [];
for (var i = 0; i < 3; i++) {
  varCallbacks.push(() => i);
}
console.log(varCallbacks.map(fn => fn())); // [3, 3, 3]

// Solution: let creates a brand-new lexical binding for every iteration
const letCallbacks = [];
for (let j = 0; j < 3; j++) {
  letCallbacks.push(() => j);
}
console.log(letCallbacks.map(fn => fn())); // [0, 1, 2]
```

With `var`, the engine allocates exactly **one** binding in the function's Variable Environment, so all three arrows close over the same slot (holding `3` after the loop). With `let`, the spec mandates a **fresh Declarative Environment Record per iteration**, copying the incremented value forward — each closure captures its own slot.

### 5. Subtle Scope Boundaries: Switch, Catch, and Parameters

Three constructs surprise even experienced engineers:

1. **Switch statements share one scope across cases.** Declaring `let x` in two cases of the same switch is a SyntaxError — wrap each case body in explicit braces to isolate it:
   ```javascript
   switch (type) {
     case 'A': {
       const message = 'Type A'; // Isolated inside explicit braces
       break;
     }
     case 'B': {
       const message = 'Type B'; // Legal because case 'A' used block braces
       break;
     }
   }
   ```
2. **Catch clauses scope the error identifier.** `catch (error)` creates an isolated declarative environment for `error` that shadows any outer binding of the same name:
   ```javascript
   let error = 'outer';
   try {
     throw new Error('boom');
   } catch (error) {
     console.log(error.message); // 'boom' (shadows outer variable)
   }
   console.log(error); // 'outer' (outer binding is unaffected)
   ```

### 6. Scope (Visibility) vs. Lifetime (Garbage Collection)

**Scope** is a compile-time syntactic boundary governing where an identifier can be referenced. **Lifetime** is a runtime memory state governing when a slot becomes eligible for garbage collection. The two are independent:

```javascript
function createCounter() {
  let count = 0; // Out of scope once createCounter() finishes
  return function increment() {
    return ++count; // count is retained in memory by closure!
  };
}
const counter = createCounter();
console.log(counter()); // 1
```

`count` has left its lexical scope, but its lifetime continues as long as the returned `increment` closure stays reachable.

## Summary

Scope controls identifier visibility through static source boundaries across four tiers: global, module, function, and block. Lookup runs inside-out along the lexical environment chain, with inner bindings shadowing outer ones. `var` binds to function or global environments while `let` and `const` respect block boundaries and create per-iteration loop bindings. Scope decides where code can read a binding; heap reachability decides how long the value lives.

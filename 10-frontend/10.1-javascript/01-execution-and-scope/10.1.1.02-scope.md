# Scope

Why does a `var` declared inside an `if` block remain visible throughout the entire function, while a `let` declared in the exact same spot causes a `ReferenceError` when accessed outside the block? The answer lies in how JavaScript defines declaration boundaries.

```javascript
function demoScope() {
  if (true) {
    var functionScoped = 'accessible outside block';
    let blockScoped = 'isolated inside block';
  }
  console.log(functionScoped); // 'accessible outside block'
  // console.log(blockScoped); // ReferenceError: blockScoped is not defined
}
demoScope();
```

## Definition

**Scope** defines the spatial region of source code within which an identifier (variable, function, class) is visible and accessible. JavaScript enforces **lexical scoping** (also called static scoping), meaning scope boundaries are determined strictly at parse time by the physical structure of functions and blocks in the source code, rather than dynamically at runtime by call order. A **binding** is the association between an identifier name and a variable record.

> **Textbook Definition:** Scope is the region in which a declaration contributes a binding for identifier resolution. Lexical scope derives that resolution from source nesting rather than the sequence of function calls.

## First Principles

1. **Name Collision Prevention**: Complex programs require the reuse of common variable names (`index`, `item`, `result`). Scopes partition program memory into isolated namespaces so that declarations inside one function or module cannot silently overwrite identically named variables elsewhere.
2. **Deterministic Lookup**: A language needs unambiguous rules to resolve bare identifiers. By binding identifier resolution strictly to lexical source structure rather than the dynamic call stack, JavaScript ensures that a function behaves identically regardless of which caller invokes it.

## How It Works

### 1. The Four Scope Levels

JavaScript provides four distinct tiers of lexical scope:

| Scope Level | Enclosing Boundary | Typical Declarations |
| :----------------- | :--------------------------------------------------------------------- | :-------------------------------------------------------------------------------- |
| **Global Scope** | Entire JavaScript runtime environment. | Top-level classic script declarations, built-in globals (`Object`, `Math`). |
| **Module Scope** | Single ES module file (`<script type="module">`). | Top-level `import`, `export`, `const`, `let`, `var`. Isolated from global object. |
| **Function Scope** | Function body enclosed by `function() { ... }`. | `var` declarations, function parameters, `arguments`. |
| **Block Scope** | Any pair of curly braces `{ ... }` (`if`, `for`, `while`, raw blocks). | `let`, `const`, `class`, explicit functions in strict mode. |

### 2. Lexical Resolution and Shadowing

When the engine encounters an identifier, it searches from the current innermost lexical environment outward along the `[[OuterEnv]]` chain until it locates the first matching binding:

```javascript
const value = 'module';

function outer() {
  const value = 'function';

  if (true) {
    const value = 'block';
    console.log(value); // 'block' (finds block binding immediately)
  }

  console.log(value);   // 'function' (finds outer function binding)
}
outer();
console.log(value);     // 'module' (finds top-level binding)
```

```text
Inside if-block:  [Block Environment: value='block'] 
                           │
                           ▼ (outer link)
Inside function:  [Function Environment: value='function']
                           │
                           ▼ (outer link)
Global / Module:  [Module Environment: value='module']
```

When an inner scope declares a variable with the same name as an outer variable, it **shadows** the outer binding. The outer variable remains untouched in its own environment; the inner scope simply intercepts identifier lookups before the outer environment can be reached.

### 3. Comparing Declaration Boundaries: var vs. let vs. const

The choice of declaration keyword dictates which Environment Record receives the binding:

| Declaration | Scope Boundary | Hoisting State | TDZ Active? | Reassignable? |
| :---------- | :------------------------------------- | :------------------------- | :---------- | :-------------------------- |
| **`var`** | Enclosing Function or Global Object ER | Initialized to `undefined` | No | Yes |
| **`let`** | Enclosing Block / Function / Loop | Uninitialized | Yes | Yes |
| **`const`** | Enclosing Block / Function / Loop | Uninitialized | Yes | No (Immutable binding) |
| **`using`** | Enclosing Block | Uninitialized | Yes | No (Disposed on block exit) |

Key engineering distinctions:
- **`const` guarantees binding immutability, not value immutability**: `const user = { name: 'Alice' }` prevents `user = {}`, but does not freeze `user.name = 'Bob'`. Use `Object.freeze()` for deep immutability.
- **Accidental Globals**: In sloppy mode, assigning to an undeclared identifier (`undeclaredVar = 42`) creates a property on `globalThis`. Strict mode (`'use strict'`) turns this into a immediate `ReferenceError`.

### A fresh binding for each loop iteration

One of the most frequent JavaScript interview questions and production bugs stems from the interaction between loop iteration and asynchronous callbacks:

```javascript
// Problem: var shares a single binding across all iterations
const varCallbacks = [];
for (var i = 0; i < 3; i++) {
  varCallbacks.push(() => i);
}
console.log(varCallbacks.map(fn => fn())); // [3, 3, 3]

// Solution: let creates a brand-new lexical binding for every iteration
const letCallbacks = [];
for (let j = 0; j < 3; j++) {
  letCallbacks.push(() => j);
}
console.log(letCallbacks.map(fn => fn())); // [0, 1, 2]
```

Under the hood:
- In `for (var i ...)`, the engine allocates exactly **one** binding in the function's Variable Environment. All three arrow functions close over that same mutable memory slot. When the loop ends, `i` has incremented to `3`.
- In `for (let j ...)`, the ECMAScript specification mandates that the engine create a **fresh Declarative Environment Record** for each iteration of the loop body, copying the previous iteration's incremented value into the new binding. Each closure captures its own independent slot.

### 5. Subtle Scope Boundaries: Switch, Catch, and Parameters

Several syntax structures introduce non-obvious scoping rules:

1. **Switch Statements**: All `case` clauses share a single lexical scope. Declaring `let x` in two different cases in the same switch block causes a SyntaxError:
   ```javascript
   switch (type) {
     case 'A': {
       const message = 'Type A'; // Isolated inside explicit braces
       break;
     }
     case 'B': {
       const message = 'Type B'; // Legal because case 'A' used block braces
       break;
     }
   }
   ```
2. **Catch Clauses**: The `catch (error)` block introduces an isolated declarative environment specifically for the error identifier:
   ```javascript
   let error = 'outer';
   try {
     throw new Error('boom');
   } catch (error) {
     console.log(error.message); // 'boom' (shadows outer variable)
   }
   console.log(error); // 'outer' (outer binding is unaffected)
   ```

### 6. Scope (Visibility) vs. Lifetime (Garbage Collection)

A critical distinction for senior engineers is understanding that **scope does not dictate object lifetime**:

- **Scope** is a compile-time syntactic boundary that governs where an identifier can be referenced in code.
- **Lifetime** is a runtime memory state that governs when an object or variable slot is eligible for garbage collection.

```javascript
function createCounter() {
  let count = 0; // Out of scope once createCounter() finishes
  return function increment() {
    return ++count; // count is retained in memory by closure!
  };
}
const counter = createCounter();
console.log(counter()); // 1
```

Even though `count` has exited its lexical scope, its lifetime continues indefinitely as long as the inner `increment` closure remains reachable from an active root.

## Summary

Scope dictates identifier visibility through static source code boundaries. Modern JavaScript features four scope tiers: Global, Module, Function, and Block. Identifier lookup proceeds inside-out along the lexical environment chain, with inner bindings shadowing outer declarations. `var` binds to function or global variable environments, while `let` and `const` adhere strictly to block boundaries and introduce per-iteration bindings in loops. Scope determines where code can read a binding, while heap reachability governs memory lifetime.

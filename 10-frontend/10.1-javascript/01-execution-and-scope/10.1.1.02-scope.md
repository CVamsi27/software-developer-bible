# Scope

A `var` declared inside an `if` block is still readable after the block closes; the same `let` throws `ReferenceError: blockScoped is not defined`. The two keywords do not differ in strength — they differ in **where the binding is registered**: `var` binds at the enclosing function, module or applicable script boundary, `let` and `const` bind at the enclosing block boundary, so begin a scope diagnosis by locating that boundary. Declaration timing is a separate question.

```javascript
function demoScope() {
  if (true) {
    var functionScoped = 'accessible outside block';
    let blockScoped = 'isolated inside block';
  }
  console.log(functionScoped); // 'accessible outside block'
  // console.log(blockScoped); // ReferenceError: blockScoped is not defined
}
demoScope();
```

## Definition

**Scope** is the region of source code in which an identifier (variable, function, class) is visible and accessible. JavaScript enforces **lexical scoping** (static scoping): boundaries come from the physical nesting of functions and blocks at parse time, never from runtime call order. A **binding** is the association between an identifier name and its variable record.

> **Textbook Definition:** Scope is the region in which a declaration contributes a binding for identifier resolution. Lexical scope derives that resolution from source nesting rather than the sequence of function calls.

## First Principles

Scopes keep reused names such as `index` and `result` associated with distinct bindings. **Deterministic lookup**: tying resolution to static source structure instead of the dynamic call stack keeps ordinary enclosing-name resolution independent of the caller's locals. Arguments, receiver selection and external state can still change behavior.

## 1. Four Scope Levels, One Boundary Decision Per Keyword

JavaScript has four tiers of lexical scope, and the keyword you write decides which tier receives the binding:

| Scope Level | Enclosing Boundary | Typical Declarations |
| :----------------- | :----------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| **Global Scope** | Shared global environment of a particular realm. | Top-level classic script declarations, built-in globals (`Object`, `Math`). |
| **Module Scope** | Single ES module file (`<script type="module">`). | Top-level `import`, `export`, `const`, `let`, `var`. Isolated from global object. |
| **Function Scope** | Function invocation, including method and arrow bodies. | `var` declarations and parameters; ordinary functions also supply implicit `arguments`, while arrows use an enclosing one. |
| **Block Scope** | Lexical statement blocks and loop/catch constructs; braces in an object literal do not create a block scope. | `let`, `const`, `class`, explicit functions in strict mode. |

Read the table as the answer to the opening question: a `var` inside an `if` block registers at the **function** boundary, so the binding exists for the whole function body; a `let` in the same spot registers at the **block** boundary, so code after that block cannot resolve it through the same lookup path. A closure created inside may still retain it. A module file adds a boundary that classic scripts lack — see [Lexical Environment](10.1.1.05-lexical-environment.md) for how a module's top-level declarations stay off `globalThis`.

## 2. Lookup Walks Outward, and an Inner Name Shadows the Outer One

The engine resolves an identifier by searching from the innermost lexical environment outward along the `[[OuterEnv]]` chain, stopping at the first match:

```javascript
const value = 'module';

function outer() {
  const value = 'function';

  if (true) {
    const value = 'block';
    console.log(value); // 'block' (block binding found first)
  }

  console.log(value);   // 'function' (outer function binding)
}
outer();
console.log(value);     // 'module' (top-level binding)
```

```text
Inside if-block:  [Block Environment: value='block']
                           │
                           ▼ (outer link)
Inside function:  [Function Environment: value='function']
                           │
                           ▼ (outer link)
Global / Module:  [Module Environment: value='module']
```

When an inner scope redeclares an outer name it **shadows** the outer binding: the outer variable is untouched, but inner lookups never reach it. The observable result is the one in the trace — three bindings, one name, three different values, resolved without any runtime search of the call stack.

## 3. `var` vs `let` vs `const` vs `using`: the Table and the Two Consequences It Hides

The keyword decides which Environment Record receives the binding:

| Declaration | Scope Boundary | Hoisting State | TDZ Active? | Reassignable? |
| :---------- | :---------------------------------------------------------- | :------------------------- | :---------- | :-------------------------- |
| **`var`** | Enclosing function, module or applicable script environment | Initialized to `undefined` | No | Yes |
| **`let`** | Enclosing Block / Function / Loop | Uninitialized | Yes | Yes |
| **`const`** | Enclosing Block / Function / Loop | Uninitialized | Yes | No (Immutable binding) |
| **`using`** | Applicable lexical scope / loop iteration | Uninitialized | Yes | No (Disposal at scope exit) |

Two distinctions matter in practice. **`const` freezes the binding, not the value**: `const user = { name: 'Alice' }` forbids `user = {}` but allows `user.name = 'Bob'` — `Object.freeze()` prevents changes to the object's own properties but is shallow. A nested object can still change; deep immutability needs a deliberate recursive/domain policy or immutable updates. [Object.freeze boundary](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/freeze). **Sloppy-mode assignment creates globals**: assigning to an undeclared identifier (`undeclaredVar = 42`) writes a `globalThis` property, while strict mode throws a `ReferenceError` immediately. Both consequences come from the same table row you would otherwise skim: the uninitialized state is what makes the temporal dead zone real, and the boundary column is what makes an ES module's top-level `var` invisible to `globalThis`.

## 4. A Loop Is Not One Scope: `let` Allocates a Binding per Iteration

The classic loop-callback bug comes from `var` sharing one binding across iterations:

```javascript
// Problem: var shares a single binding across all iterations
const varCallbacks = [];
for (var i = 0; i < 3; i++) {
  varCallbacks.push(() => i);
}
console.log(varCallbacks.map(fn => fn())); // [3, 3, 3]

// Solution: let creates a brand-new lexical binding for every iteration
const letCallbacks = [];
for (let j = 0; j < 3; j++) {
  letCallbacks.push(() => j);
}
console.log(letCallbacks.map(fn => fn())); // [0, 1, 2]
```

With `var`, the engine allocates exactly **one** binding in the function's Variable Environment, so all three arrows close over the same slot (holding `3` after the loop). With `let`, the spec mandates a **fresh Declarative Environment Record per iteration**, copying the incremented value forward — each closure captures its own slot. The bug and the fix are the same mechanism seen twice: the loop keyword chooses whether "the loop" is one scope or a scope per iteration.

## 5. The Boundaries That Surprise Senior Engineers: `switch`, `catch` and Parameters

Switch and catch syntax expose boundaries that are easy to overlook; parameter-expression environments are developed in [Execution Context](10.1.1.01-execution-context.md#parameter-and-body-bindings-can-differ):

1. **Switch statements share one scope across cases.** Declaring `let x` in two cases of the same switch is a SyntaxError — wrap each case body in explicit braces to isolate it:
   ```javascript
   switch (type) {
     case 'A': {
       const message = 'Type A'; // Isolated inside explicit braces
       break;
     }
     case 'B': {
       const message = 'Type B'; // Legal because case 'A' used block braces
       break;
     }
   }
   ```
2. **Catch clauses scope the error identifier.** `catch (error)` creates an isolated declarative environment for `error` that shadows any outer binding of the same name:
   ```javascript
   let error = 'outer';
   try {
     throw new Error('boom');
   } catch (error) {
     console.log(error.message); // 'boom' (shadows outer variable)
   }
   console.log(error); // 'outer' (outer binding is unaffected)
   ```

Both surprises are the boundary rule applied to syntax that does not look like a block: the switch's case labels are not a boundary, a catch parameter is one, and the error you hit tells you which of the two you are in.

## 6. Scope Is Not Lifetime

**Scope** describes the source regions in which a declaration participates in identifier lookup. Those regions do not disappear when a call returns. **Lifetime** concerns the particular runtime bindings and values created by an evaluation and how long reachable code needs them. The two are independent:

```javascript
function createCounter() {
  let count = 0; // One binding for this factory call
  return function increment() {
    return ++count; // count is retained in memory by closure!
  };
}
const counter = createCounter();
console.log(counter()); // 1
```

`count` remains lexically visible in the nested function's source, and that call's binding remains usable through the returned `increment` closure — the same pair of facts that makes [Closures](10.1.1.06-closures.md) work and makes leaked closures a memory problem.

## Summary

Scope controls identifier visibility through static source boundaries across four tiers: global, module, function, and block. Lookup runs inside-out along the lexical environment chain, with inner bindings shadowing outer ones. `var` binds to the enclosing function, module or applicable script environment, while `let` and `const` respect block boundaries and create per-iteration loop bindings. Scope decides where code can read a binding; heap reachability decides how long the value lives.

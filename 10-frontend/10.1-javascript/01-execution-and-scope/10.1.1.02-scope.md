# Scope

`var` inside a block can remain visible after the closing brace, while `let` does not. The declaration boundary explains why those two reads behave differently.

## Definition

**Scope** determines where a name can refer to a particular variable or declaration. JavaScript normally finds names using **lexical scope**: it starts with the environment of the code that reads the name, then checks the environments surrounding it in the source. A name's association with a variable is called a **binding**. Scope controls where a binding is visible; it does not specify when the variable's memory is freed.

> **Textbook Definition:** Scope is the region in which a declaration contributes a binding for identifier resolution. Lexical scope derives that resolution from source nesting rather than the sequence of function calls.


## First Principles

1. Programs reuse names. Separate scopes let two variables have the same name without referring to the same variable.
2. A name needs a predictable lookup rule. JavaScript follows the scopes surrounding the code in the source, rather than searching the caller's local variables.
3. A closure can keep access to a variable after its enclosing call returns. Whether its data stays in memory depends on whether the program can still reach it, not simply on whether execution passed a closing brace.

## Trace a Shadowed Name

```javascript
const value = 'module';
function outer() {
  const value = 'function';
  if (true) {
    const value = 'block';
    console.log(value); // block
  }
  console.log(value); // function
}
outer();
console.log(value); // module
```

At each read, search from the innermost active lexical environment outward. The first matching binding wins. Leaving the block changes the starting environment; it does not overwrite the outer `value`.

```text
inside if:   block value → function value → module value
                            ↑
after if:                   start here
after call:                                   start here
```

These are environment links, not an extra function call for each `let` block. A variable environment used for `var` declarations is also not a separate parallel lookup tree that skips lexical bindings.

## Compare Declaration Boundaries

The **temporal dead zone (TDZ)** is the interval after a lexical binding is established but before its declaration initializes it. Reading that binding fails even if an outer variable has the same name. Scope decides which binding is found; initialization decides whether that binding can be read. The hoisting chapter traces the failure.

| Declaration | Binding boundary | Important consequence |
| -------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `var` | Function or top-level script/module variable environment | An `if` block does not isolate it; module `var` is not a global-object property |
| `let` / `const` / class | Enclosing lexical scope | A block can shadow an outer name and has a TDZ |
| `using` / `await using` | Enclosing lexical scope | Resource is disposed when its scope exits; see the support note in [Hoisting](10.1.1.04-hoisting.md) |
| Other top-level ES-module declarations | Module | Imports and declarations are not global-object properties |

```javascript
function example() {
  if (true) {
    var shared = 1;
    const local = 2;
  }
  console.log(shared); // 1
  // console.log(local); // ReferenceError: no visible binding
}
example();
```

`const` prevents reassignment of its binding; it does not deeply freeze an object. Unqualified assignment to an undeclared name throws in strict code and modules; sloppy code can create a global property.

## Definition Site Beats Call Site

```javascript
const message = 'outside';
function read() { return message; }
function caller() {
  const message = 'caller';
  return read();
}
console.log(caller()); // outside
```

`read` was created outside `caller`; its lookup does not walk through the caller's local `message`. The [Lexical Environment chapter](10.1.1.05-lexical-environment.md) develops the environment links, and [Closures](10.1.1.06-closures.md) follows what happens after an enclosing call returns.

## A Fresh Binding for Each Loop Iteration

```javascript
const shared = [];
for (var i = 0; i < 3; i++) shared.push(() => i);
console.log(shared.map(read => read())); // [3, 3, 3]

const separate = [];
for (let j = 0; j < 3; j++) separate.push(() => j);
console.log(separate.map(read => read())); // [0, 1, 2]
```

The first callbacks share one `i`. The `let` loop establishes per-iteration bindings, so the second callbacks do not all read the last iteration's variable. The same distinction explains delayed timer callbacks; no timer is required to demonstrate it.

## Less Obvious Boundaries

The cases of a `switch` share one surrounding lexical block. Wrap a case in braces when it needs a separate scope for a `let` or `const` declaration. Older code can create a function scope with an **immediately invoked function expression (IIFE)**, a function expression called as soon as it is created. ES modules usually provide the modern boundary between files.

Declare variables near their use with the smallest appropriate scope. Moving every variable to the top of a function generally makes dependencies harder to read. Use explicit parameters where they clarify a function's dependency rather than asserting that a deeper chain is necessarily slow.

## Scope and Lifetime

A returned closure can keep a binding usable after its enclosing call finishes. An engine may also optimize away an unused binding or collect a value once it is unreachable. Neither stack/heap placement nor collection timing follows from lexical scope alone.

Do not claim a large array is destroyed immediately at function return. Check reachability through listeners, timers, module state and returned functions; use the memory chapters for measurement and cleanup.

## Summary

Resolve a name from the code's innermost lexical environment outward, stopping at the first matching binding. Distinguish function, block, global and module boundaries; trace per-iteration bindings separately. Scope determines visibility, while reachability determines whether retained data can be collected.

# Call Stack

## Definition

The **call stack** tracks nested active calls and where each caller resumes. The usual function-call sequence is last-in, first-out: the inner call returns before its caller continues. An engine's physical frames and optimizations are implementation details behind that useful model.

## First Principles

1. A caller pauses at a call and needs a continuation point.
2. Nested calls create nested continuation points, so the most recent one resumes first.
3. Execution resources are finite. Excessively deep recursion can exceed the runtime's supported stack even when the algorithm has a base case.

## Trace Three Calls

```javascript
function first() {
  console.log('first starts');
  second();
  console.log('first ends');
}
function second() {
  console.log('second starts');
  third();
  console.log('second ends');
}
function third() { console.log('third'); }
first();
```

The output is `first starts`, `second starts`, `third`, `second ends`, `first ends`.

```text
call first     call second     call third      return third   return second
               second         third           second         first
first          first          second          first
caller         caller         first           caller         caller
                              caller
```

The stack shows **who called whom**. It does not show lexical identifier lookup: `third` does not automatically read `second`'s local variables. That belongs to the [scope chain](10.1.1.02-scope.md).

## Read an Exception's Path

```javascript
function load() { validate(); }
function validate() { throw new Error('Invalid input'); }
try {
  load();
} catch (error) {
  console.log(error instanceof Error ? error.stack : error);
}
```

The throw propagates outward until a handler catches it. A stack trace usually starts with the innermost failing location; exact formatting and async ancestry depend on the engine. `finally` cleanup executes while control unwinds. A retained error's stack is diagnostic history, not proof those calls are still active.

## Recursion: Count Depth Separately From Work

```javascript
function factorial(n) {
  if (!Number.isInteger(n) || n < 0) throw new RangeError('Nonnegative integer');
  if (n <= 1) return 1;
  return n * factorial(n - 1);
}
console.log(factorial(5)); // 120
```

The multiplication waits for each recursive result, retaining nested work. A base case makes termination possible; it does not guarantee a safe depth for huge inputs. A naive Fibonacci routine can do exponential total work with only linear active depth. Memoization reduces repeated work but may retain the same depth; an iterative implementation can remove that call-depth cost.

Recursion limits vary by engine, call shape and configuration. Deep recursion errors may be reported differently by engines, so do not hardcode a universal safe count or error message. Prefer iteration or an explicit work stack for unbounded input. A hand-maintained depth counter must release its count in `finally`, including on errors.

## What Happens at `await`

```javascript
async function example() {
  console.log('before await');
  await Promise.resolve();
  console.log('after await');
}
example();
console.log('caller continues');
// before await → caller continues → after await
```

The async evaluation suspends and returns control to its caller; the continuation resumes later through promise scheduling. The completed or suspended evaluation is not blocking the active call stack while it waits. Calling an async function still runs its code synchronously until suspension, so an expensive loop before the first `await` can block the main thread.

See [Event Loop](../03-async-concurrency/10.1.3.01-event-loop.md) for the queue checkpoints and genuine yielding needed to let input or rendering progress. Merely adding `async`, or repeatedly awaiting already-fulfilled promises, does not move CPU work to another thread.

## Tail Calls and Physical Memory

A tail call has no work remaining in the caller after it returns. Proper tail-call handling is specified for the relevant strict-mode cases, but implementation support is limited; do not depend on it for portable stack safety. A call followed by multiplication or logging is not in tail position.

The language does not require every object on the heap and every local in a fixed stack slot. Engines can eliminate allocations, inline calls or use different representations. Inspect actual runtime behavior rather than claiming a particular array's source declaration determines its physical location.

## Common Mistakes

| Mistake | Repair |
| ----------------------------------------------- | ------------------------------------------------------ |
| Confusing call ancestry with scope ancestry | Trace invocation and lexical lookup separately |
| Treating a base case as enough for stack safety | Bound depth or use iteration for large input |
| Assuming an async function cannot block | Inspect its synchronous work before and between awaits |
| Claiming workers guarantee a frame rate | Measure main-thread, worker and rendering costs |
| Depending on tail-call optimization everywhere | Use a portable iterative or explicit-stack design |

## Summary

Trace nested calls, their pending work and the point where each caller resumes. Count active depth separately from total algorithmic work, and use exception traces as history. Suspension releases active execution but does not automatically yield to rendering or move work off-thread.

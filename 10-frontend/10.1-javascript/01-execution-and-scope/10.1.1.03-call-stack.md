# Call Stack

When deep recursion halts with `RangeError: Maximum call stack size exceeded`, what structure filled up, why is its memory bounded, and how does the runtime coordinate nested function returns? The **call stack** models active nested calls and where each caller continues. Engines use bounded resources to represent that work; supported depth and the error differ by runtime, function shape and optimization. A logical call is not guaranteed to have one distinct native frame.

```javascript
function first() {
  second();
}
function second() {
  third();
}
function third() {
  console.trace('Call Stack Snapshot');
}
first();
```

## Definition

The **call stack** is the runtime structure that tracks active function invocations, their local execution state, and return addresses on a **Last-In, First-Out (LIFO)** discipline. A nested call suspends its caller's evaluation; returning resumes it. Physical frames are an implementation of that relationship and may be changed by inlining or other optimizations.

> **Textbook Definition:** A call stack is a last-in, first-out record of active function invocations and their continuation points. Completing an invocation returns control to its caller; implementation optimizations may alter the physical frames.

## First Principles

Within one synchronous execution, a nested call runs before its caller continues. When `A` calls `B`, `A` must preserve enough continuation state to resume after `B` completes. Because calls nest symmetrically — the most recently invoked function finishes before its caller can continue — a stack models this lifecycle exactly. Representing nested work consumes finite runtime resources. Both a base case and bounded input depth matter: a terminating recursive algorithm can still exceed the supported depth.

## 1. Step-by-Step Frame Push and Pop Lifecycle

```javascript
function first() {
  console.log('1. first starts');
  second();
  console.log('5. first ends');
}

function second() {
  console.log('2. second starts');
  third();
  console.log('4. second ends');
}

function third() {
  console.log('3. third executes');
}

first();
```

The stack transitions through six states:

```text
Step  Active evaluations, from caller to current callee
1     script → first
2     script → first → second
3     script → first → second → third
4     script → first → second          (third returned)
5     script → first                   (second returned)
6     script                           (first returned)
      script finishes; later jobs can enter their own evaluations
```

This diagram follows one active classic-script evaluation; when it finishes, it is no longer a permanent bottom frame. The stack records **who called whom** (the dynamic call graph). It does not resolve variables: `third` cannot see `second`'s locals unless it was lexically nested inside `second` in the source.

## 2. Anatomy of a Physical Stack Frame

An engine frame may contain return information, saved machine state, arguments and local slots. The following are possible implementation details, not a required layout for every JavaScript call:

- **Return address** — the hardware instruction pointer (e.g., `RIP` on x86-64) targeting the caller instruction after the `call`.
- **Saved frame pointer** — the previous frame's base pointer (`RBP`) for unwinding.
- **Parameters and arguments** — passed-in values (or pointers to register spill slots).
- **Local slots** — values that were not held in registers, eliminated or placed in another representation. Declaring `let` or `const` does not decide that placement.

## 3. Stack Overflow: Causes and Mitigations

Deep recursion can exceed the engine's supported nesting. There is no portable frame count or memory limit to copy into an application contract:

```javascript
function recursiveBomb() {
  recursiveBomb(); // RangeError: Maximum call stack size exceeded
}
```

A common error is confusing total work with stack depth. Naive recursive Fibonacci does O(2ⁿ) work but never exceeds O(n) depth, because left branches unwind before right branches run. A straightforward recursive factorial has O(n) recursive steps and O(n) call depth; large integer arithmetic adds its own cost. Its failure threshold depends on the runtime and function. The fix for unbounded depth is iteration or a **trampoline**, which converts recursion into a loop:

```javascript
// Iterative: O(1) stack space
function factorialIterative(n) {
  let acc = 1n;
  for (let i = 2n; i <= BigInt(n); i++) {
    acc *= i;
  }
  return acc;
}
```

## 4. Exception Unwinding and Stack Traces

A thrown error triggers **stack unwinding**:

```javascript
function alpha() { beta(); }
function beta() { gamma(); }
function gamma() {
  throw new Error('Database connection failed');
}

try {
  alpha();
} catch (error) {
  console.log(error.stack);
}
```

1. The engine looks for a `catch` in `gamma()`; finding none, it runs `gamma`'s `finally` blocks and pops its frame.
2. It repeats for `beta()`, then reaches the `try...catch` enclosing `alpha()` in the caller.
3. Runtime diagnostic stack information can describe where the error was created. `Error.stack` formatting, optimized/omitted frames and reconstructed async ancestry are implementation-dependent; it is not a portable memory-layout dump.

## 5. What Happens to the Stack at `await`

An async function runs synchronously until it suspends. Long synchronous work before or between awaits still blocks that thread:

```javascript
async function fetchUser() {
  console.log('1. Start fetch');
  await fetch('/api/user');
  console.log('3. Finish fetch');
}

fetchUser();
console.log('2. Synchronous caller continues');
```

`fetchUser()` runs synchronously and prints `1`. At `await`, that evaluation suspends and the caller can continue to print `2`. Required continuation state remains available without holding an active native frame for the entire wait. After the awaited promise settles, a Promise reaction job resumes evaluation to print `3`; a fresh microtask is not another invocation of the function. Even an already fulfilled awaited value resumes asynchronously.

## 6. Tail Call Optimization (TCO) Reality Check

ECMAScript specifies **Proper Tail Calls** for eligible strict-mode tail positions, allowing the caller's continuation to be replaced rather than accumulated. Runtime support is uneven; JavaScriptCore supports it, while commonly deployed V8 and SpiderMonkey do not. Verify the target runtime instead of inferring support from the syntax. **Senior rule**: never rely on TCO for stack safety in cross-platform JavaScript; use explicit loops for unbounded depth.

## Summary

The call stack runs code as a LIFO stack of execution contexts and return pointers. Frames track dynamic calls while lexical scope chains resolve names. Deep or infinite recursion exhausts finite stack memory, so convert unbounded depth to iteration. Awaited work can suspend evaluation and resume through Promise jobs; synchronous computation in async functions still blocks the executing thread. Physical frame layout, diagnostic traces and supported recursion depth remain runtime-specific.

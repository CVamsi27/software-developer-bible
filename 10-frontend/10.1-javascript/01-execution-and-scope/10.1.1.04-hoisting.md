# Hoisting

## Definition

Hoisting describes observable declaration behavior before execution reaches a declaration's source position. JavaScript establishes bindings when it enters the relevant scope. Some already hold a usable value; others exist but cannot be read yet. The engine does not rearrange the source text.

## First Principles

A name and its value are separate things. To resolve names consistently, an entered scope must know which names belong to it, including names declared later in its body. That does not require giving every name a value immediately. Declaration kind determines its initial state; running an initializer is a later operation.

## Why does a later declaration change an earlier read?

Imagine a module exporting a service whose startup reads a configuration value. Moving the configuration declaration below the startup call can change a successful read into `undefined` or an exception. Follow the binding's state rather than picturing code being moved.

```text
enter scope → establish binding → run statements in source order
                  │
                  ├─ var: initialized to undefined
                  ├─ function declaration: initialized to function object
                  └─ let/const/class: uninitialized until evaluation reaches it
```

The **temporal dead zone (TDZ)** is the period during which an existing lexical binding remains uninitialized. Reading it throws `ReferenceError`; lookup does not fall through to an outer binding with the same name.

## Trace four declaration kinds in one scope

Run this as JavaScript. TypeScript can reject deliberate before-declaration reads, so a TypeScript fence would obscure the runtime lesson.

```js
'use strict';

function demonstrate() {
  function report(label, read) {
    try {
      console.log(label, read());
    } catch (error) {
      console.log(label, error.name);
    }
  }

  report('var before', () => count);                  // undefined
  report('function before', () => add(2, 3));         // 5
  report('let before', () => total);                  // ReferenceError
  report('typeof let before', () => typeof total);    // ReferenceError
  report('class before', () => new Counter());        // ReferenceError
  report('var expression before', () => multiply(2, 3)); // TypeError

  var count = 10;
  let total = 20;
  const label = 'ready';
  var multiply = (a, b) => a * b;
  function add(a, b) { return a + b; }
  class Counter { constructor() { this.value = count; } }

  report('values after', () => [count, total, label].join(',')); // 10,20,ready
  report('expression after', () => multiply(2, 3));             // 6
  report('class after', () => new Counter().value);              // 10
}

demonstrate();
```

1. Entering `demonstrate` initializes `count` and `multiply` to `undefined`, installs `report` and `add`, and establishes uninitialized lexical bindings.
2. The reporting calls run before the later initializers. Reading `multiply` succeeds, but calling its current value (`undefined`) fails with `TypeError`.
3. Reading `total` or `Counter` fails at the uninitialized binding. Even `typeof total` cannot bypass that state. By contrast, `typeof` of an entirely unresolved identifier returns `'undefined'`.
4. The declarations execute in order. Only now do the arrow function and class values become available through their bindings.

A function expression behind `const` follows `const`'s TDZ rule. Its arrow/function syntax does not turn the variable declaration into a function declaration.

## A function can exist before the data it closes over

Installing a function object does not initialize the values its body will later read. The statement “function bodies do not depend on execution order” is therefore misleading.

```js
'use strict';
function initialize() {
  try {
    console.log(readConfig());
  } catch (error) {
    console.log(error.name); // ReferenceError
  }
  const config = 'production';
  console.log(readConfig()); // production
  function readConfig() { return config; }
}
initialize();
```

The first call can resolve `readConfig`; its body then resolves `config` and reaches the TDZ. The second call runs after initialization. Keep initialization dependencies visible even when helpers are declared below their callers.

## Which scope owns the declaration?

`var` in a normal block belongs to its enclosing function (or applicable script/module scope). Lexical declarations belong to the entered block. A function declaration in strict block code is block-scoped too.

```js
'use strict';
function chooseGreeting(friendly) {
  if (friendly) {
    function greeting() { return 'Hello'; }
    return greeting();
  }
  return 'Goodbye';
}
console.log(chooseGreeting(true)); // Hello
console.log(typeof greeting);     // undefined: no binding in this outer scope
```

Non-strict classic scripts have legacy Annex B behavior for eligible block function declarations, which can also affect an enclosing var-like binding. Avoid relying on that mode-sensitive behavior: use a clearly scoped declaration or assign a function value explicitly.

A loop's `var` callbacks share one binding; a `for (let …)` loop creates per-iteration bindings. The [closure chapter](10.1.1.06-closures.md) owns the complete callback trace. This is a scope/lifetime distinction, not delayed movement of declarations.

## Module linking creates bindings before module evaluation

ES module imports are **live bindings**: they stay connected to the exported variables rather than taking a one-time copy. **Linking** connects these imports and exports before the modules evaluate their code. An imported value can be read only when its exported binding is initialized; the import statement's position does not decide that. When modules import each other in a cycle, one can try to read a variable before the other initializes it. A function declaration may already be available. Do not model every import as a local `let` assigned when execution reaches the import line. See [Modules](../05-functional-patterns/10.1.5.01-modules.md) for module lifecycle and cycle examples.

TypeScript can refer to an interface declared later in a file, but that is static name resolution. Interfaces are erased; they are not runtime hoisted objects. Likewise a React function component follows ordinary function-declaration rules rather than a React-specific hoisting mechanism.

## What declaration order does not tell you

Binding rules specify observable behavior, not physical memory placement or garbage-collection timing. A block-scoped value may remain reachable through a closure after the block exits; an engine may optimize away an unused binding. Do not select `let` over `var` because a diagram claims its memory must be freed sooner.

A function declaration inside a called function can create a function object on each invocation. A function expression at module scope may execute only once. Allocation depends on the enclosing execution and engine optimizations, not a universal declaration-versus-expression speed ranking.

## Summary

Resolve the name in its owning scope, inspect whether its binding is initialized, and only then consider the operation on its value. That sequence explains `undefined`, TDZ `ReferenceError`, and calling-an-undefined-value `TypeError` without rewriting the source in your head.

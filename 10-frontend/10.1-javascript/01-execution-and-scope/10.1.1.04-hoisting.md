# Hoisting

## TL;DR

Hoisting is the engine's creation-phase behavior: before the first statement runs, every declaration in scope receives a binding — `var` set to `undefined`, function declarations installed with their full body, `let`/`const`/`class` left uninitialized behind the Temporal Dead Zone (TDZ). The name suggests code moves; no source line ever does.

## First Principles

Hoisting is not a feature — it is an inference from one fact you already know:

1. **Contexts are created in two phases** (→ 10.1.1.01). Bindings are allocated in the *creation phase*, before any statement executes. So of course declarations are "usable early" — they were never absent; the question is only *what state they're in*.
2. **Declaration and initialization are separable events.** The two keywords answer that question differently: `var` fuses them loosely (created *and* initialized to `undefined` up front), while `let`/`const` keeps initialization strictly at the declaration line — the temporal dead zone is the span where the binding exists but is deliberately unusable, turning silent `undefined` bugs into loud errors.
3. **Function declarations are materialized in phase one.** Their bodies don't depend on execution order, so installing them whole is safe — which is exactly why you can call a function declared later in the file.


## Why It Matters

TDZ errors (`Cannot access 'x' before initialization`) are a common senior-interview gotcha. Knowing the difference between `var` hoisting, function declaration hoisting, and class hoisting is essential for debugging initialization-order bugs in ESM modules and circular dependencies.

## Definition

**Hoisting** is the name for what the engine does in the *creation phase* of the execution context: it instantiates every declaration in the scope — allocating the binding and, where that declaration's kind demands it, a starting value — before any statement executes. `var` bindings begin as `undefined`, function declarations arrive complete with their body (so they can be called before their line of code appears), and `let`/`const`/`class` bindings exist but stay unreadable until their declaration line runs — exactly what the Temporal Dead Zone enforces. Nothing in your source file is rearranged: "moving declarations to the top" is a metaphor for this allocation, not an operation any engine performs.


## How It Works

### Hoisting Mechanism

```text

│ HOISTING MECHANISM                                      │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ AS WRITTEN (your source file — never modified):         │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ console.log(x); // What happens here?               │ │
│ │ var x = 10;                                         │ │
│ │                                                     │ │
│ │ greet(); // What happens here?                      │ │
│ │ function greet() {                                  │ │
│ │ console.log("Hello!");                              │ │
│ │ }                                                   │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ CREATION PHASE (conceptual — your source is untouched): │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ // Binding created in the creation phase            │ │
│ │ var x; // created — initialized to undefined        │ │
│ │                                                     │ │
│ │ // Function declaration instantiated with its body  │ │
│ │ function greet() {                                  │ │
│ │ console.log("Hello!");                              │ │
│ │ }                                                   │ │
│ │                                                     │ │
│ │ console.log(x); // undefined                        │ │
│ │ x = 10; // Assignment happens here                  │ │
│ │                                                     │ │
│ │ greet(); // Works — installed in creation phase     │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
└─────────────────────────────────────────────────────────┘

```

### What Gets Hoisted

```text
┌─────────────────────────────────────────────────────────────┐
│ WHAT GETS HOISTED?                                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ INITIALIZED IN THE CREATION PHASE:                          │
│ ┌─────────────────────────────────────────────────────┐     │
│ │ • var → created, set to undefined                   │     │
│ │ • function declaration → full function object       │     │
│ └─────────────────────────────────────────────────────┘     │
│                                                             │
│ CREATED, BUT UNINITIALIZED (TDZ):                           │
│ ┌─────────────────────────────────────────────────────┐     │
│ │ • let / const → usable only after their line        │     │
│ │ • class declaration → same rule as let              │     │
│ │ • import → live binding filled when the export runs │     │
│ └─────────────────────────────────────────────────────┘     │
│                                                             │
│ NOT DECLARATIONS — the binding follows its keyword:         │
│ ┌─────────────────────────────────────────────────────┐     │
│ │ • function expression + var → undefined until set   │     │
│ │ • function expression + let/const → TDZ until line  │     │
│ │ • arrow function → same rule as function expression │     │
│ └─────────────────────────────────────────────────────┘     │
│                                                             │
│ TDZ = Temporal Dead Zone (cannot access before declaration) │
│                                                             │
└─────────────────────────────────────────────────────────────┘

```

### var vs let/const Hoisting

```text
┌─────────────────────────────────────────────────────────┐
│ var vs let/const HOISTING                               │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ var HOISTING:                                           │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ console.log(x); // undefined                        │ │
│ │ var x = 5;                                          │ │
│ │                                                     │ │
│ │ // What happens internally:                         │ │
│ │ var x; // created in creation phase (undefined)     │ │
│ │ console.log(x); // undefined                        │ │
│ │ x = 5; // Assignment stays in place                 │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ let/const HOISTING:                                     │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ console.log(y); // ReferenceError!                  │ │
│ │ let y = 10;                                         │ │
│ │                                                     │ │
│ │ // What happens internally:                         │ │
│ │ // y is hoisted but NOT initialized                 │ │
│ │ // y is in "Temporal Dead Zone"                     │ │
│ │ console.log(y); // ReferenceError                   │ │
│ │ let y = 10; // Initialization happens here          │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
└─────────────────────────────────────────────────────────┘

```

### Function Hoisting

```text
┌─────────────────────────────────────────────────────────┐
│ FUNCTION HOISTING                                       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ FUNCTION DECLARATION:                                   │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ greet(); // Works! "Hello!"                         │ │
│ │                                                     │ │
│ │ function greet() {                                  │ │
│ │ console.log("Hello!");                              │ │
│ │ }                                                   │ │
│ │                                                     │ │
│ │ // Entire function is hoisted                       │ │
│ │ // Can be used before declaration                   │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ FUNCTION EXPRESSION:                                    │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ greet(); // ReferenceError — const is in the TDZ    │ │
│ │                                                     │ │
│ │ const greet = function() {                          │ │
│ │ console.log("Hello!");                              │ │
│ │ };                                                  │ │
│ │                                                     │ │
│ │ // Only the binding exists — no function value yet  │ │
│ │ // greet is in the TDZ until its line runs          │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ ARROW FUNCTION:                                         │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ greet(); // ReferenceError — const is in the TDZ    │ │
│ │                                                     │ │
│ │ const greet = () => {                               │ │
│ │ console.log("Hello!");                              │ │
│ │ };                                                  │ │
│ │                                                     │ │
│ │ // Same rule — the binding stays in the TDZ         │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
└─────────────────────────────────────────────────────────┘

```

### Temporal Dead Zone (TDZ)

```text
┌─────────────────────────────────────────────────────────┐
│ TEMPORAL DEAD ZONE                                      │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ TIMELINE:                                               │
│ ┌─────────────────────────────────────────────────────┐ │
│ │                                                     │ │
│ │ ─────────────────────────────────────────────────   │ │
│ │ | TDZ | LIVE ZONE |                                 │ │
│ │ ─────────────────────────────────────────────────   │ │
│ │                                                     │ │
│ │ |←─ Scope starts ─→|←─ Declaration ─→|←─ Use ─→|    │ │
│ │ | |                                                 │ │
│ │ | let x = 5; | x = 10;                              │ │
│ │ | |                                                 │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ CODE EXAMPLE:                                           │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ {                                                   │ │
│ │ // TDZ starts here                                  │ │
│ │ console.log(a); // ReferenceError                   │ │
│ │ console.log(b); // ReferenceError                   │ │
│ │                                                     │ │
│ │ let a = 10; // TDZ ends here                        │ │
│ │ const b = 20; // TDZ ends here                      │ │
│ │                                                     │ │
│ │ console.log(a); // 10                               │ │
│ │ console.log(b); // 20                               │ │
│ │ }                                                   │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ WHY TDZ EXISTS:                                         │
│ • Prevents accidental use before initialization         │
│ • Makes code behavior more predictable                  │
│ • Enables better error messages                         │
│ • Supports block scoping properly                       │
│                                                         │
└─────────────────────────────────────────────────────────┘

```

The thrown error is a **ReferenceError**, and the reason is precise: the environment record already lists the name — which is how the engine can print `Cannot access 'y' before initialization` instead of `y is not defined` — but the slot's initialized flag is still false, so every read, including `typeof y`, fails at binding lookup. A failed lookup is ReferenceError territory; a failed *operation on a value* would be TypeError, which is why TDZ never produces one.

## Code Examples

### Basic var Hoisting

```typescript
// var hoisting
console.log(name); // undefined
var name = "Alice";
console.log(name); // "Alice"

// What JS engine sees:
// var name;
// console.log(name); // undefined
// name = "Alice";
// console.log(name); // "Alice"

```

### let/const TDZ

```typescript
// let/const TDZ
try {
  console.log(age); // ReferenceError: Cannot access 'age' before initialization
} catch (e) {
  console.log(e.message);
}

let age = 25;
console.log(age); // 25

// const behaves the same
try {
  console.log(COLOR); // ReferenceError
} catch (e) {
  console.log(e.message);
}

const COLOR = "red";
console.log(COLOR); // "red"

```

### Function Declaration vs Expression

```typescript
// Function declaration - fully hoisted
add(2, 3); // 5

function add(a: number, b: number): number {
  return a + b;
}

// Function expression - only the binding's keyword is instantiated
try {
  multiply(2, 3); // ReferenceError: Cannot access 'multiply' before initialization
} catch (e) {
  console.log(e.message);
}

const multiply = function(a: number, b: number): number {
  return a * b;
};

// Arrow function - same rule (a `var` binding would instead be
// undefined here, giving a TypeError)
try {
  divide(6, 2); // ReferenceError: Cannot access 'divide' before initialization
} catch (e) {
  console.log(e.message);
}

const divide = (a: number, b: number): number => a / b;

```

### Class Hoisting

```typescript
// Classes are NOT fully hoisted: the binding is created, but it stays
// uninitialized (TDZ, like let/const) until the class line runs
try {
  const instance = new MyClass(); // ReferenceError
} catch (e) {
  console.log(e.message);
}

class MyClass {
  constructor() {
    this.value = 42;
  }
}

// A class expression behind const follows the same TDZ rule — before its
// line it throws rather than working
try {
  const early = new MyClassExpression(); // ReferenceError
} catch (e) {
  console.log(e.message);
}

const MyClassExpression = class {
  constructor() {
    this.value = 42;
  }
};

// Declared first, then used — this works
const instance = new MyClassExpression();
console.log(instance.value); // 42

```

### Hoisting in Loops

```typescript
// var in loops - common bug
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100); // 3, 3, 3
}

// let in loops - works as expected
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 100); // 0, 1, 2
}

// Why? var i is hoisted to function/global scope
// All callbacks share the same i variable
// By the time setTimeout runs, i is already 3

```

### Nested Function Hoisting

```typescript
function outer() {
  console.log(inner()); // Works! Function is hoisted

  function inner() {
    return "Hello from inner";
  }

  // But this wouldn't work (const is in the TDZ before its line):
  // console.log(inner2()); // ReferenceError: Cannot access 'inner2' before initialization
  // const inner2 = () => "Hello";
}

outer();

```

### Conditional Function Declaration

```typescript
// In sloppy (non-strict) scripts the branch that RUNS wins: Annex B gives the
// block-level declaration a var-like binding on the enclosing scope and
// assigns it when that block executes — it is NOT "the last declaration wins"
if (true) {
  function sayHello() {
    return "Hello";
  }
} else {
  function sayHello() {
    return "Goodbye";
  }
}

console.log(sayHello()); // "Hello" — the executed branch

// In strict mode / ES modules the declaration is block-scoped instead:
// outside the block, sayHello is not defined at all

// This is why function expressions are safer
let sayGoodbye: () => string;

if (true) {
  sayGoodbye = () => "Hello";
} else {
  sayGoodbye = () => "Goodbye";
}

console.log(sayGoodbye()); // "Hello" (as expected)

```

## Real-World Use Cases

### 1. Utility Functions

```typescript
// Hoisting allows organizing code logically
function calculateArea(width: number, height: number): number {
  return multiply(width, height); // Can use multiply before declaration
}

function calculatePerimeter(width: number, height: number): number {
  return add(add(width, width), add(height, height));
}

// Helper functions defined below (but hoisted)
function multiply(a: number, b: number): number {
  return a * b;
}

function add(a: number, b: number): number {
  return a + b;
}

```

### 2. Module Pattern

> *Nothing here is hoisting's doing — an IIFE gets privacy from its own function scope, so the pattern and its private-state variants live in [Scope — IIFE](10.1.1.02-scope.md#iife-immediately-invoked-function-expression) and [Closures — Data Privacy](10.1.1.06-closures.md#data-privacy-module-pattern).*

### 3. React Component Hoisting

```typescript
// Component declarations are hoisted
function App() {
  return <ChildComponent />;
}

// Child can be used before declaration
function ChildComponent() {
  return <div>Hello</div>;
}

```

### 4. TypeScript Interface Hoisting

```typescript
// Types are erased at compile time — TypeScript resolves them anywhere in
// the file, so a signature may name a type declared further down
function createUser(user: User): User {
  return user;
}

interface User {
  name: string;
  age: number;
}

```

## Common Mistakes

### 1. Using var Before Declaration

```typescript
// Mistake: Expecting undefined
console.log(x); // undefined (not ReferenceError!)
var x = 10;

// This can cause confusing bugs
function example() {
  console.log(x); // undefined
  if (true) {
    var x = 20; // Hoisted to function scope
  }
  console.log(x); // 20
}

```

### 2. Assuming let/const Are Hoisted Like var

> *Same demo, same error, lives in [let/const TDZ](#letconst-tdz) under Code Examples: the binding exists from the creation phase but reads before its line throw ReferenceError instead of yielding `undefined`.*

### 3. Function Expression Hoisting

> *Calling a `const`-declared function before its line throws ReferenceError (TDZ) while a `var`-declared one would be `undefined` and throw TypeError — see [Function Declaration vs Expression](#function-declaration-vs-expression), which also shows the fix: give the function a declaration so its body, not its assignment, is what gets instantiated.*

### 4. Class Hoisting

> *`new MyClass()` before the class line fails with ReferenceError, never TypeError — the class binding is created uninitialized exactly like `let`. Full demo, plus the class-expression variant, in [Class Hoisting](#class-hoisting).*

## Best Practices

### 1. Use const by Default

Declaration-keyword choice is a scoping decision, not a hoisting one — the const/let guidance and the "declare at top" pattern are owned by [Scope](10.1.1.02-scope.md#best-practices). Hoisting's own rules:

### 2. Declare Variables at Top of Scope

Same owner — [Scope — Best Practices](10.1.1.02-scope.md#best-practices) carries the example. The hoisting-specific rule is simpler: a `var` binding exists from the creation phase, so a `var` read before its assignment line yields `undefined`, not an error.

### 3. Use Function Declarations for hoisting

```typescript
// Good: Function declarations are fully hoisted
function processItem(item: any) {
  return transform(item); // Can use transform before declaration
}

function transform(item: any) {
  return { ...item, processed: true };
}

// Function expressions should be used when needed conditionally
const processItemExpr = condition
  ? (item: any) => item.value
  : (item: any) => item.name;

```

### 4. Avoid Conditional Function Declarations

> *Assign a function expression or arrow to a `const` instead — which branch ran is then simply the value of the binding. The declaration form's behavior depends on mode: the executed branch wins in sloppy scripts (Annex B), while strict code and ES modules make the declaration block-scoped — worked through in [Conditional Function Declaration](#conditional-function-declaration).*

## Performance Considerations

### Memory Allocation

```typescript
// var is hoisted to function scope
function example() {
  // var x is allocated for entire function
  // even if only used in one branch
  if (true) {
    var x = 10; // Allocated at function start
  }
  console.log(x); // 10
}

// let/const are block-scoped
function exampleOptimized() {
  if (true) {
    const y = 10; // Allocated only in this block
    console.log(y); // 10
  }
  // y is not accessible here, memory can be freed
}

```

### Function Declaration Optimization

```typescript
// Function declarations are hoisted and created once
function expensiveOperation() {
  // This function object is created during creation phase
  // and reused for all calls
  return Math.random();
}

// A function expression builds its object when the line runs — once here
// (a top-level const); the same line inside a hot function would rebuild it
const expensiveOperationExpr = function() {
  return Math.random();
};

```

## Summary

Hoisting is a fundamental JavaScript concept:

1. **What**: Creation-phase instantiation of every declaration in scope — a memory model, not a rewrite of your source

2. **var**: Hoisted and initialized to `undefined`

3. **let/const**: Hoisted but not initialized (TDZ)

4. **Functions**: Declarations instantiated with their body; expressions are not declarations

5. **Classes**: Binding created but uninitialized (TDZ), like `let`/`const`

6. **TDZ**: Prevents access before initialization

7. **Best practices**: Use const/let, avoid var, declare at top

## Revision Questions

**How It Works**

1. **Q:** Does hoisting move any line of your source file, and if not, what does the word actually describe?
   **A:** Nothing moves — the file is read as written. The name describes allocation during the creation phase: bindings are created and, depending on the declaration kind, given a starting value before the first statement runs.

2. **Q:** Compare the creation-phase state of `var x`, `let x`, and a `function f(){}`.
   **A:** `var x` exists with the value `undefined`, `let x` exists but is flagged uninitialized (the TDZ covers everything before its line), and `function f` arrives already bound to the complete function object. Same phase, three different states.

3. **Q:** What does the Temporal Dead Zone actually record, and which error type does violating it raise?
   **A:** The environment record holds the name but marks its slot uninitialized, so any read — even `typeof x` — fails during binding lookup. Lookup failures throw ReferenceError, which is why a TDZ violation can never surface as TypeError.

**Code Examples**

4. **Q:** What error do you get for `greet()` placed above `const greet = () => "Hello"`, and how does it differ from the `var` version?
   **A:** ReferenceError (`Cannot access 'greet' before initialization`) because the `const` binding is still in its TDZ. With `var greet`, the binding would be `undefined`, and calling it would instead throw `TypeError: greet is not a function`.

5. **Q:** Are classes hoisted like function declarations?
   **A:** No — the class name is instantiated in the creation phase like `let`, then left uninitialized until the class statement executes. Reading or `new`-ing it before that line throws ReferenceError.

**Common Mistakes**

6. **Q:** A function declaration sits inside an `if` branch and a second definition sits in the `else`. Which one wins?
   **A:** In sloppy scripts the branch that actually executes wins — Annex B gives the block-level declaration a var-like binding on the enclosing scope and assigns it when the block runs, so it is not a "last one written" race. In strict mode and ES modules the declaration is block-scoped, and outside the block the name does not exist at all.

**Best Practices**

7. **Q:** When is the right moment to use a function declaration instead of assigning a function expression?
   **A:** Use a declaration when the function should be callable anywhere in its scope regardless of statement order — only a declaration is instantiated with its body during the creation phase. Reach for an expression (assigned to `const`) when the function's very existence depends on a runtime condition.

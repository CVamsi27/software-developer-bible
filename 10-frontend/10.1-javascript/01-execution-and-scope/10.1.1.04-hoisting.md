# Hoisting

Why does a `var` read as `undefined` before its declaration, a function declaration run fine before its definition, but a `let` read throw a `ReferenceError`? Because declaration setup runs in phases with three different end states: a `var` binding is created **and initialized to `undefined`** when its scope is entered, a function declaration is created **and initialized** during instantiation, and `let`/`const` bindings are created **but left uninitialized** until their statement executes — reading one before then is the temporal dead zone.

```javascript
console.log(varVariable);   // undefined
console.log(greet());       // "Hello!"
// console.log(letVariable); // ReferenceError: Cannot access 'letVariable' before initialization

var varVariable = 'I am var';
function greet() { return 'Hello!'; }
let letVariable = 'I am let';
```

## Definition

**Hoisting** is the observable effect of the engine creating identifier bindings through the applicable declaration-instantiation algorithms before that scope's statements are evaluated. Source code is never moved. Each declaration kind (`var`, `function`, `let`, `const`, `class`) is either initialized immediately or left uninitialized in the **Temporal Dead Zone (TDZ)**.

> **Textbook Definition:** Hoisting is the observable effect of creating declaration bindings before evaluating the statements in their scope. Initialization depends on declaration kind: lexical bindings remain unreadable until their declaration is evaluated.

## First Principles

The language must define whether a binding exists and whether it is initialized when a statement reads it. Declaration instantiation and initialization are separate semantic operations, independent of whether an engine interprets or compiles the code: `var` defaults to `undefined`, function declarations install their full bodies, and lexical bindings (`let`, `const`) stay uninitialized until execution reaches their declaration line.

## 1. Declaration Instantiation vs. Statement Evaluation

```text
Declaration instantiation for the applicable scope
  function greet → initialized function object
  var varVariable → initialized undefined
  let letVariable → uninitialized binding
Statement evaluation in the opening example
  read varVariable → undefined
  call greet()     → "Hello!"
  read letVariable → ReferenceError if attempted before initialization
```

The source is never moved. Applicable script, module, function and block algorithms establish bindings before evaluating that scope's statements. Parsing and JIT compilation may happen at different times; they are not a mandatory two-pass explanation of hoisting.

## 2. The Hoisting Matrix

Behavior when referencing a declaration before its definition line:

| Declaration Kind | Scope | Established before evaluation? | Initial Value Before Line | Attempting to Read Throws |
| :--------------- | :------------------------- | :----------------------------- | :------------------------ | :--------------------------- |
| **`function`** | Enclosing Scope | Yes | Complete Function Object | None (Runs successfully) |
| **`var`** | Function / Module / Script | Yes | `undefined` | None (Evaluates `undefined`) |
| **`let`** | Enclosing Block | Yes | *Uninitialized* (TDZ) | `ReferenceError` |
| **`const`** | Enclosing Block | Yes | *Uninitialized* (TDZ) | `ReferenceError` |
| **`class`** | Enclosing Block | Yes | *Uninitialized* (TDZ) | `ReferenceError` |
| **`import`** | Module Scope | Yes | Linked Live Binding | Depends on exporter init |

## 3. The Temporal Dead Zone (TDZ) and `the_hole` Sentinel

The **Temporal Dead Zone** spans from entering a scope until the declaration statement executes:

```javascript
{
  // <--- TDZ for 'data' starts here upon entering the block
  // console.log(data); // Throws ReferenceError: Cannot access 'data' before initialization

  const unused = 42;

  let data = 'Loaded'; // <--- TDZ for 'data' ends here!
  console.log(data);   // 'Loaded'
}
```

The TDZ makes an early read fail instead of inventing a usable value before initialization. Initialization is distinct from reassignment: `const` allows its initial value to be established once, then forbids reassignment. These rules apply without requiring any particular compiler representation.

- **Engine reality**: V8 can represent an uninitialized lexical binding using an internal hole value and emit a checked read. That is one implementation of the required `ReferenceError`, not a rule that every hole value in every engine operation throws.
- **`typeof` is not exempt**: `typeof nonExistent` safely returns `'undefined'` for undeclared names, but `typeof blocked` inside the TDZ throws:
  ```javascript
  console.log(typeof nonExistent); // 'undefined' (undeclared variable)

  // console.log(typeof blocked);  // ReferenceError: Cannot access 'blocked' before initialization
  let blocked = 100;
  ```

## 4. Function Declarations vs. Function Expressions

A classic interview trap — only declarations hoist their bodies:

```javascript
// 1. Function Declaration: Fully hoisted
sayHello(); // "Hello!"
function sayHello() {
  return "Hello!";
}

// 2. var Function Expression: Variable hoisted as undefined
try {
  sayBye(); // TypeError: sayBye is not a function
} catch (e) {
  console.log(e instanceof TypeError); // true
}
var sayBye = function() {
  return "Bye!";
};

// 3. const / let Function Expression: Lexical TDZ
try {
  sayLater(); // ReferenceError: Cannot access 'sayLater' before initialization
} catch (e) {
  console.log(e instanceof ReferenceError); // true
}
const sayLater = () => "Later!";
```

`var sayBye` hoists as `undefined`, so calling it throws `TypeError`. `const sayLater` sits uninitialized in the TDZ, so even reading it throws `ReferenceError`.

## 5. Block-Level Function Hoisting (Strict Mode vs. Annex B)

```javascript
'use strict';
if (true) {
  function blockScopedFunc() { return 'Strict block scope'; }
  console.log(blockScopedFunc()); // 'Strict block scope'
}
console.log(typeof blockScopedFunc); // 'undefined'
```

In **strict mode**, block-level function declarations are block-scoped but initialized when the block is entered, so they can be called before their declaration line inside that block. They do not share `let`'s pre-declaration TDZ behavior. In **sloppy scripts**, eligible Annex B cases add an outer `var`-like binding alongside the block binding. Eligibility and evaluation rules matter; do not generalize it to every function declaration or module. **Senior rule**: always use strict mode or ES modules to avoid Annex B behavior.

## 6. ES Module Import Hoisting and Circular Dependencies

`import` statements link before module code executes:

```javascript
// Imports are hoisted and linked before module code executes
import { apiConfig } from './config.js';
console.log(apiConfig.endpoint);
```

During the **linking phase**, the engine wires imports to exporter memory slots as **live bindings**. In a circular dependency (`A` imports `B`, `B` imports `A`), reading an imported `const`/`let` before the exporter's file has run throws `ReferenceError: Cannot access before initialization` across module boundaries.

## Summary

Hoisting describes declaration setup before the relevant statements evaluate, not a source rewrite or mandatory compiler pass. Function declarations hoist with their bodies, `var` hoists as `undefined`, and `let`/`const`/`class` stay uninitialized in the Temporal Dead Zone, throwing `ReferenceError` on early reads. The same two-phase model explains function-expression traps, strict-mode block functions, and cross-module circular-dependency errors.

# Hoisting

Why does accessing a `var` before its declaration evaluate to `undefined`, calling a function declaration before its definition succeed effortlessly, but reading a `let` or `const` throw a fatal `ReferenceError`? 

```javascript
console.log(varVariable);   // undefined
console.log(greet());       // "Hello!"
// console.log(letVariable); // ReferenceError: Cannot access 'letVariable' before initialization

var varVariable = 'I am var';
function greet() { return 'Hello!'; }
let letVariable = 'I am let';
```

## Definition

**Hoisting** is the observable runtime behavior resulting from the JavaScript engine's two-phase compilation architecture: the engine creates identifier bindings in their respective Environment Records during the compile/parse pass *before* executing any runtime statements. The physical source code is never moved or rearranged. Depending on the declaration type (`var`, `function`, `let`, `const`, `class`), the binding is either initialized immediately or placed into an uninitialized state known as the **Temporal Dead Zone (TDZ)**.

> **Textbook Definition:** Hoisting is the observable effect of creating declaration bindings before evaluating the statements in their scope. Initialization depends on declaration kind: lexical bindings remain unreadable until their declaration is evaluated.

## First Principles

1. **Two-Phase Architecture**: JavaScript engines do not interpret code line-by-line as raw text. They first parse and compile source text into an Abstract Syntax Tree (AST) and bytecode. During this first pass, the engine must register every declared identifier in the scope so it can allocate memory slots and optimize variable access.
2. **Separation of Allocation and Initialization**: Allocating space for an identifier name and assigning it a meaningful runtime value are distinct operations. Variable declarations (`var`) are initialized to a default `undefined`, function declarations are initialized with their complete function bodies, and lexical bindings (`let`, `const`) are left uninitialized until execution reaches their assignment line.

## How It Works

### 1. Compile Pass vs. Runtime Pass

Hoisting is purely an artifact of the engine's compilation lifecycle:

```text
┌────────────────────────────────────────────────────────┐
│ PASS 1: PARSE & ALLOCATION (Compile Phase)             │
│ - Engine scans scope and discovers all declarations    │
│ - Registers bindings in the Environment Record:        │
│   • function greet   ──► Initialized with function obj │
│   • var varVariable  ──► Initialized to undefined      │
│   • let letVariable  ──► Uninitialized (TDZ active)   │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ PASS 2: BYTECODE EXECUTION (Runtime Phase)             │
│ - Runs statements line-by-line                         │
│ - Line 1: greet() works because it is already a func   │
│ - Line 2: varVariable reads 'undefined'                │
│ - Line 3: letVariable throws ReferenceError (in TDZ!)  │
└────────────────────────────────────────────────────────┘
```

The source file is not physically rewritten; the engine simply enters the scope with memory bindings already registered.

### 2. The Hoisting Matrix

How different declarations behave when referenced before their definition:

| Declaration Kind | Scope | Bound in Creation Phase? | Initial Value Before Line | Attempting to Read Throws |
| :--------------- | :---------------- | :----------------------- | :------------------------ | :--------------------------- |
| **`function`** | Enclosing Scope | Yes | Complete Function Object | None (Runs successfully) |
| **`var`** | Function / Global | Yes | `undefined` | None (Evaluates `undefined`) |
| **`let`** | Enclosing Block | Yes | *Uninitialized* (TDZ) | `ReferenceError` |
| **`const`** | Enclosing Block | Yes | *Uninitialized* (TDZ) | `ReferenceError` |
| **`class`** | Enclosing Block | Yes | *Uninitialized* (TDZ) | `ReferenceError` |
| **`import`** | Module Scope | Yes | Linked Live Binding | Depends on exporter init |

### 3. The Temporal Dead Zone (TDZ) and `the_hole` Sentinel

The **Temporal Dead Zone** is the time span between entering a scope and executing the declaration statement for a `let`, `const`, or `class` binding:

```javascript
{
  // <--- TDZ for 'data' starts here upon entering the block
  // console.log(data); // Throws ReferenceError: Cannot access 'data' before initialization

  const unused = 42;

  let data = 'Loaded'; // <--- TDZ for 'data' ends here!
  console.log(data);   // 'Loaded'
}
```

#### Why was TDZ introduced in ES6?
1. **Catching Latent Bugs**: Accessing variables before initialization is almost always an accidental bug. In ES5, reading a variable before its declaration silently returned `undefined`, creating subtle runtime bugs.
2. **Preserving `const` Semantics**: If `const x = 10` hoisted as `undefined`, its value would transition from `undefined` to `10` during evaluation—violating the core guarantee that a `const` binding is immutable throughout its lifetime.

#### Engine Reality: The `the_hole` Sentinel
In production engines like Google V8, uninitialized lexical slots are stamped with an internal sentinel object called `the_hole`. Whenever bytecode attempts an identifier read and encounters `the_hole`, the engine emits a native bailout that throws a JavaScript `ReferenceError`.

#### The `typeof` Exception
In classic JavaScript, `typeof undeclaredIdentifier` is safe and returns `'undefined'`. However, `typeof` inside the TDZ throws an exception:
```javascript
console.log(typeof nonExistent); // 'undefined' (undeclared variable)

// console.log(typeof blocked);  // ReferenceError: Cannot access 'blocked' before initialization
let blocked = 100;
```

### 4. Function Declarations vs. Function Expressions

A frequent interview trap is the difference between function declarations and function expressions:

```javascript
// 1. Function Declaration: Fully hoisted
sayHello(); // "Hello!"
function sayHello() {
  return "Hello!";
}

// 2. var Function Expression: Variable hoisted as undefined
try {
  sayBye(); // TypeError: sayBye is not a function
} catch (e) {
  console.log(e instanceof TypeError); // true
}
var sayBye = function() {
  return "Bye!";
};

// 3. const / let Function Expression: Lexical TDZ
try {
  sayLater(); // ReferenceError: Cannot access 'sayLater' before initialization
} catch (e) {
  console.log(e instanceof ReferenceError); // true
}
const sayLater = () => "Later!";
```

- With `var sayBye`, the variable binding `sayBye` is hoisted and initialized to `undefined`. Invoking `undefined()` triggers a `TypeError`.
- With `const sayLater`, the variable is uninitialized in the TDZ, triggering a `ReferenceError`.

### 5. Block-Level Function Hoisting (Strict Mode vs. Annex B)

What happens when a function is declared inside an `if` block?

```javascript
'use strict';
if (true) {
  function blockScopedFunc() { return 'Strict block scope'; }
  console.log(blockScopedFunc()); // 'Strict block scope'
}
console.log(typeof blockScopedFunc); // 'undefined'
```

- In **Strict Mode (`'use strict'`)**: Function declarations inside blocks behave like `let` declarations: they are block-scoped and invisible outside the block.
- In **Sloppy Mode (Annex B)**: For backwards compatibility with web code written in the 1990s, browsers execute complex legacy rules (Annex B.3.3) that hoist a `var` binding to the outer function while maintaining a block binding. **Senior Best Practice**: Always enforce strict mode or ES modules to avoid Annex B legacy behavior.

### 6. ES Module Import Hoisting and Circular Dependencies

ES module `import` statements are hoisted to the top of the module file:

```javascript
// Imports are hoisted and linked before module code executes
import { apiConfig } from './config.js';
console.log(apiConfig.endpoint);
```

During the **Linking Phase**, the JS engine links all imports to their corresponding export memory slots as **live bindings**.
If module `A` and module `B` form a circular dependency (`A` imports `B`, `B` imports `A`), attempting to read an imported `const` or `let` before the exporter's file has executed will trigger a `ReferenceError: Cannot access before initialization` across module boundaries.

## Summary

Hoisting is the observable consequence of the engine registering declarations during its compile pass before executing runtime statements. Function declarations hoist with their complete executable bodies, while `var` variables hoist initialized to `undefined`. In contrast, `let`, `const`, and `class` declarations are bound in an uninitialized state, enforcing a Temporal Dead Zone that throws `ReferenceError` on premature access. Understanding the distinction between compilation and execution phases demystifies TDZ errors, function expression traps, and module dependency lifecycles.

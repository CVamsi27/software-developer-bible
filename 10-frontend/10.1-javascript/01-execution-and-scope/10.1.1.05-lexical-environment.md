# Lexical Environment

When `read()` returns `label`, should it use the caller's `label`, the one beside its definition, or the global one? JavaScript answers by following the environment chain where the function was defined.

```javascript
const label = 'global';

function makeReader() {
  const label = 'outer';
  return function read() {
    return label;
  };
}

function invoke() {
  const label = 'caller';
  return makeReader()();
}

console.log(invoke()); // 'outer'
```

## Definition

A **lexical environment** describes the names available to code at a particular point. It consists of an **Environment Record**, which models that scope's bindings, and a reference to the surrounding environment. A **binding** connects an identifier such as `label` to a variable. **Identifier resolution** follows the current environment and its outer references until it finds that binding.

> **Textbook Definition:** A lexical environment is a specification structure that pairs an Environment Record with an outer-environment reference, defining the bindings available to identifier resolution at that point in program execution.

## First Principles

Nested code must be able to use names from its surrounding scope. Searching the caller's local variables would make a function's result depend on where it was called. JavaScript instead gives each scope its own bindings and links that scope to the one surrounding it in the source.

## Follow the lookup chain

When `read()` runs, its own function environment has no `label`. The function was created while `makeReader()` was running, so its outer reference reaches that call's `label`, whose value is `'outer'`. The `invoke()` environment containing `'caller'` is not on this chain. Lookup stops at the first matching binding and returns `'outer'`.

```text
read() environment ──outer──► makeReader() environment: label = 'outer'
                                      │
                                      └──outer──► global environment: label = 'global'

invoke() environment: label = 'caller'   (not part of read()'s lookup chain)
```

Scopes use different Environment Record kinds depending on where their names come from:

| Record kind | What it models |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Declarative** | Bindings introduced by declarations, such as block variables and function parameters. |
| **Function** | A function invocation's declarative bindings and function-specific state. An ordinary function has its own `this`; an arrow gets `this` lexically. |
| **Module** | A module's declarations and imports. An import stays linked to the exporting binding, so reads can observe later updates. |
| **Object** | Eligible names resolved through object properties, as in legacy `with` statements. Strict mode forbids `with`. |
| **Global** | The global environment's object-backed names together with its declarative bindings. |

These are alternatives and specializations, not five pieces inside every scope. In particular, Function and Module records specialize declarative bindings, while the Global record combines object-backed and declarative parts.

This model explains why not every global name is a `globalThis` property. In a browser classic script, top-level `var` and function declarations normally use the object-backed side, while `let`, `const` and class declarations use the declarative side. An ES module uses its own Module Environment Record, including for top-level `var`. The [scope chapter](10.1.1.02-scope.md) covers host and declaration boundaries; [modules](../05-functional-patterns/10.1.5.01-modules.md) and [this](../02-objects-prototypes-this/10.1.2.01-this.md) explain those topics in full.

Ordinary property access does not create an Object Environment Record: `settings.theme` first resolves the variable `settings`, then reads its `theme` property. These record types describe language behavior; they are not JavaScript objects that application code can inspect.

## A matching binding may not be ready to read

```javascript
let score = 10;

try {
  {
    console.log(score); // ReferenceError
    let score = 20;
  }
} catch (error) {
  console.log(error instanceof ReferenceError); // true
}

console.log(score); // 10
```

The block's `score` binding exists as soon as the block is entered, so lookup finds it first. Its declaration has not initialized it yet, so reading it throws instead of falling through to the outer `score`. This interval is the **temporal dead zone (TDZ)**. [Hoisting](10.1.1.04-hoisting.md) explains when declarations become usable.

## LE and VE name different roles

An execution context holds two environment references. **LexicalEnvironment (LE)** identifies where identifier lookup starts. **VariableEnvironment (VE)** identifies the environment used for `var` declarations during setup. They can refer to the same record; entering a block can change LE while VE stays at the function's `var` boundary. Reads through either role follow the same lookup chain, so LE and VE describe roles, not separate stores. The [execution-context chapter](10.1.1.01-execution-context.md#a-block-changes-lookup-without-making-a-call) traces a block and a parameter boundary.

The specification's environment diagram predicts which binding a read finds. It does not promise how an engine stores variables or how much memory a particular function retains. Use the [closures chapter](10.1.1.06-closures.md) for retained bindings and memory ownership.

## Summary

Identifier lookup starts in the code's lexical environment and follows outer references until it finds the first binding. An uninitialized inner binding still wins and causes a TDZ error. Record types explain where names come from; LE and VE describe different execution-context roles, not different lookup trees.

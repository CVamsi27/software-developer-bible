# Lexical Environment

When `read()` returns `label`, should it use the caller's `label`, the one beside its definition, or the global one? JavaScript resolves this by following the environment chain established where the function was declared in the source code, completely ignoring where it was called.

```javascript
const label = 'global';

function makeReader() {
  const label = 'outer';
  return function read() {
    return label;
  };
}

function invoke() {
  const label = 'caller';
  return makeReader()();
}

console.log(invoke()); // 'outer'
```

## Definition

A **lexical environment** describes the identifiers available to executing code at a specific point in a program. ECMAScript formalizes this with an **Environment Record**, which stores the current scope's bindings and maintains a reference (`[[OuterEnv]]`) to its parent environment. A **binding** associates an identifier name (like `label`) with a memory value and mutation rules. **Identifier resolution** is the deterministic process of traversing outer environment records until the engine finds the target binding or reaches the global boundary.

> **Textbook Definition:** A lexical environment is the binding context used to resolve identifiers. In current ECMAScript, an execution context's LexicalEnvironment identifies an Environment Record, and each record's `[[OuterEnv]]` links to the enclosing record or null at the outer boundary.

## First Principles

Nested code must resolve identifiers from surrounding scopes reliably without runtime collisions. If identifier lookup followed the dynamic call stack (searching the caller's local variables), a function's return value would mutate depending on where it was invoked. JavaScript eliminates this ambiguity using **lexical scoping**: each scope maintains its own bindings and points to the enclosing scope in the static source text, ensuring identifier resolution is completely deterministic at parse time.

## 1. The Environment Record Family Tree (Specialization, Not Accumulation)

Identifier lookup always begins in the innermost active environment and climbs upward:

```text
read() environment ──outer──► makeReader() environment: label = 'outer'
                                      │
                                      └──outer──► global environment: label = 'global'

invoke() environment: label = 'caller'   (not part of read()'s lookup chain)
```

When `read()` runs, its local function environment has no binding named `label`. Because `read` was instantiated while `makeReader()` was executing, its `[[OuterEnv]]` pointer leads directly to `makeReader()`'s environment, where `label` evaluates to `'outer'`. The `invoke()` execution context is irrelevant to the search. Lookup halts immediately upon finding the first matching binding.

A single scope does not contain all five environment record types. Every scope picks exactly one record type tailored to its operational requirements:

- **Declarative Environment Record**: The foundational, high-performance store for variables (`let`, `const`, `class`, function parameters, and `catch` clauses).
- **Function Environment Record**: A specialized Declarative ER used for function invocations that tracks function-specific runtime state, including `this` binding status, `arguments`, `super`, and `[[NewTarget]]`.
- **Module Environment Record**: A specialized Declarative ER for ES modules featuring live indirect bindings, ensuring imported identifiers stay linked directly to the exporter's mutable memory slot.
- **Object Environment Record**: A legacy wrapper that projects an ordinary JavaScript object (such as `window` or a `with` statement's target object) into an identifier scope.
- **Global Environment Record**: A hybrid composite record that combines an Object ER (for classic `var` declarations, top-level functions, and built-ins) and a Declarative ER (for top-level `let`, `const`, and `class`) under one roof.

## 2. Why let Doesn't Attach to globalThis (and Why Modules Isolate Everything)

Top-level declarations behave differently depending on whether you are executing a classic script or an ES module:

```javascript
// Classic Browser Script:
var a = 1;   // Routes to Global Object ER -> Appears on window.a
let b = 2;   // Routes to Global Declarative ER -> window.b is undefined
```

- **Classic Scripts (`<script>`)**: Top-level `var` and function declarations register in the Global Environment's Object record (bound directly to `globalThis` / `window`), polluting the global object. Top-level `let`, `const`, and `class` declarations register in the Global Environment's Declarative record, making them accessible everywhere in the program without polluting `globalThis`.
- **ES Modules (`<script type="module">`)**: Modules completely bypass the Global Environment Record. Every module runs inside its own isolated **Module Environment Record**, meaning even top-level `var` declarations stay contained within the module file and never attach to `globalThis`.

## 3. Property Access (`settings.theme`) is NOT an Object Environment Record

A common point of confusion is conflating Object Environment Records with standard object property lookups.

When you write `settings.theme`, the engine does **not** create or query an Object Environment Record. Instead, it executes two distinct sequential operations:

1. **Identifier Resolution**: The engine searches the active Lexical Environment chain to find the identifier `settings` and retrieve its object reference in memory.
2. **Property Access**: The engine invokes the internal `[[Get]]` method on that resolved object to access the `theme` property along the prototype chain.

Object Environment Records are strictly reserved for resolving bare, unqualified variable names directly against an object's properties (such as top-level `var` lookups in classic scripts or legacy `with(obj)` blocks).

## 4. Spec Abstractions vs. Real Engine Implementation (V8 Internals)

ECMAScript defines scopes and bindings as chains of Environment Record specification types. Production engines like Google V8 optimize these heavily rather than allocating dictionary objects for every block:

- **Stack Allocation for Non-Escaping Variables**: If a variable declared with `let` or `const` is never captured by an inner closure, V8 optimizes the Environment Record away. The variable lives entirely in a CPU register or on the native stack frame.
- **Heap Contexts for Escaped Bindings**: Only when an inner function escapes and references an outer variable does V8 allocate a heap-allocated `Context` object (a flat array of slots).
- **Internal Specs vs. Runtime Objects**: You cannot inspect `currentScope.DeclarativeRecord` in application code. Variables are compiled to fast slot offsets determined during bytecode generation.

## 5. Temporal Dead Zone: Why Matching Bindings Throw Before Initialization

A binding may exist in the environment record before it is safe to read:

```javascript
let score = 10;

try {
  {
    // The inner block binding exists immediately upon entering the block
    console.log(score); // ReferenceError: Cannot access 'score' before initialization
    let score = 20;
  }
} catch (error) {
  console.log(error instanceof ReferenceError); // true
}

console.log(score); // 10
```

When execution enters a block, all lexical declarations (`let`, `const`) are instantiated in the Declarative ER immediately, but remain **uninitialized**. The interval between entering the block and evaluating the declaration statement is the **temporal dead zone (TDZ)**.

Because the inner `score` binding already exists in the innermost Declarative ER, identifier resolution finds it immediately and halts. Encountering an uninitialized binding causes the engine (via an internal sentinel like V8's `the_hole`) to throw a `ReferenceError` rather than falling back to the outer `score`.

## LE and VE name different roles

An execution context maintains two distinct environment references:

- **LexicalEnvironment (LE)**: Identifies the Environment Record where current identifier resolution starts.
- **VariableEnvironment (VE)**: Identifies the Environment Record that receives `var` declarations during function setup.

```javascript
'use strict';
function showBindings() {
  var shared = 'function';
  let local = 'function';

  {
    // Block Entry:
    // LE points to a new Block Declarative ER { local: 'block' }
    // VE stays pointing to the Function ER { shared: 'function' }
    var shared = 'still function'; // Stored in VE (function scope)
    let local = 'block';           // Stored in LE (block scope)
    console.log(shared, local);    // 'still function', 'block'
  }

  // Block Exit:
  // LE is restored to the Function ER
  console.log(shared, local);      // 'still function', 'function'
}
showBindings();
```

Inside the block, `LE` points to the new block environment containing `local`, while `VE` points to the function environment containing `shared`. Identifier reads always begin at `LE` and climb outer references. On block exit, `LE` is restored to the enclosing function record. `LE` and `VE` represent operational roles during execution, not separate competing variable storage systems.

## Summary

Identifier lookup begins at the execution context's current `LexicalEnvironment` and traverses outer environment records until finding the first matching binding. Environment Records specialize based on context: Declarative for local variables, Function for call state and `this`, Module for live imports, Object for property-backed scopes, and Global for hybrid scripts. Uninitialized lexical bindings trigger Temporal Dead Zone errors rather than falling back to outer scopes, and engines optimize non-escaping records into native stack registers.

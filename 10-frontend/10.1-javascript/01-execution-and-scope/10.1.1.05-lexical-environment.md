# Lexical Environment

## Definition

A **lexical environment** is JavaScript's model for answering “which variable does this name refer to here?” A **binding** associates a name, such as `count`, with a variable and its state. An **Environment Record** describes the bindings available at one level and links to the enclosing environment.

These are specification concepts, not objects your program can inspect or a required engine memory layout. The current specification puts the outer link, `[[OuterEnv]]`, on the Environment Record itself. The familiar diagram “local bindings + outer link” is a useful teaching model. [ECMAScript environment records](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-environment-records).

## First Principles

Two scopes can declare the same name and still hold different variables. Name lookup therefore needs to distinguish the current bindings from enclosing bindings. A nested function can use an enclosing variable after the enclosing call returns, so leaving the call stack cannot automatically erase every binding that function needs.

## Follow one name through a nested function

```javascript
const label = 'global';

function makeReader() {
  const label = 'outer';

  return function read() {
    return label;
  };
}

const reader = makeReader();
console.log(reader()); // 'outer'
```

Follow the read of `label`:

1. `makeReader()` creates a local `label` binding with the value `'outer'`.
2. Creating `read` associates it with that enclosing environment.
3. Calling `reader()` creates the environment for that call.
4. The read of `label` finds no local declaration in `read`, then finds the binding from `makeReader`.
5. Lookup stops there. The global `label` is a different binding.

```text
read call
  local bindings: no label
  outer ──► makeReader call
              local bindings: label = 'outer' ← read stops here
              outer ──► enclosing module/script environment
                          label = 'global'
```

Where `read` is called does not substitute the caller's variables into this chain. The nested function's definition determines its enclosing environment. For the complete behavior, continue to [closures](10.1.1.06-closures.md).

## Inside a lexical environment: what the Environment Record stores

The **Environment Record is the part of the model that keeps track of names**. Its job is broader than a plain name-to-value dictionary: it records whether a binding exists, whether it has been initialized, and whether reassignment is allowed.

For a teaching example containing `let score = 10` and `const limit = 20`, think of the local bindings like this:

| Name | After its declaration executes | Can the binding be reassigned? |
| ------- | ------------------------------ | ------------------------------ |
| `score` | Initialized to `10` | Yes |
| `limit` | Initialized to `20` | No |

`const` restricts reassignment of the binding; it does not freeze an object stored in it. The outer link tells lookup where to continue when this environment has no binding for the requested name.

### Different records represent different kinds of scope

| Record kind | What it represents |
| ----------- | --------------------------------------------------------------------- |
| Declarative | Bindings introduced by declarations; blocks use this kind |
| Function | A specialized declarative record for a function call |
| Module | A specialized declarative record for module declarations and imports |
| Object | Names resolved through a backing object's properties |
| Global | A composite of declarative bindings and global-object-backed bindings |

These are variants of the same lookup model, not five components that every environment contains. A module's top-level variables do not automatically become properties of `globalThis`.

## An inner declaration stops lookup even before initialization

```javascript
let score = 10;

try {
  {
    console.log(score); // ReferenceError
    let score = 20;
  }
} catch (error) {
  console.log(error instanceof ReferenceError); // true
}

console.log(score); // 10
```

The inner block already has a binding named `score`, but that binding is uninitialized when the read occurs. Lookup finds it and fails; it does not continue outward to return `10`. This interval is the **temporal dead zone (TDZ)**. See [MDN: let and TDZ](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/let).

After the block, the outer `score` is unchanged. [Hoisting](10.1.1.04-hoisting.md) explains when different declarations become usable; [scope](10.1.1.02-scope.md) explains their visibility boundaries.

## Each factory call gives its returned function different state

```javascript
function makeCounter() {
  let count = 0;
  return () => ++count;
}

const first = makeCounter();
const second = makeCounter();

console.log(first());  // 1
console.log(first());  // 2
console.log(second()); // 1
```

The two calls create different `count` bindings. Calling `first` changes the one retained by `first`; calling `second` uses the other. Returning a function does not copy the current number into it. The function continues to access its binding. See [MDN: closures](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Closures).

A `for (let i = …)` loop similarly supplies separate iteration bindings for callbacks, whereas a `var` loop commonly leaves them sharing one binding. Study the trace in [closures](10.1.1.06-closures.md), rather than learning a second duplicate implementation here.

## Keep the model separate from engine internals

An execution context tracks the current evaluation, including environment references. An environment describes bindings and enclosing scope. The call stack tracks active calls. They are related concepts with different jobs.

The specification does not require engines to allocate one ordinary object per block or physically traverse a linked list on every read. Optimizations can preserve the same observable behavior with a different representation. Scope depth alone is not a performance measurement.

Captured state can remain usable after a call returns. That does not mean a closure must retain every unused local or that an entire stack frame stays active. Investigate actual retaining paths when diagnosing memory use; do not infer them from the drawing.

## Summary

Use the environment model to locate a binding: check this level, then enclosing levels. The Environment Record describes local binding state and carries the outer link. Finding an uninitialized inner binding stops the search with an error; a returned function can keep accessing an enclosing binding after its call has finished.

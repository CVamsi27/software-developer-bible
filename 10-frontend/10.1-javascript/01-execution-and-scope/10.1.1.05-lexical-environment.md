# Lexical Environment

## Definition

A **lexical environment** describes the variables available to code at a particular place in a program. When code reads a name such as `count`, JavaScript looks in the current **scope** first, then in the surrounding scopes. A scope is the part of a program where a variable can be accessed.

An **identifier** is a name used in source code, such as `count`. Resolving an identifier means finding the binding that this occurrence of the name refers to.

> **Textbook Definition:** A lexical environment associates identifier names with bindings and links to an outer environment. Identifier resolution follows this chain until it finds a binding or exhausts the available environments.


## First Principles

Two functions can both declare `count`. Each function must be able to change its own `count` without changing the other function's variable.

A function can also return another function that uses its variables. The returned function may run later, after the first function has finished. JavaScript therefore needs to keep access to the variables that the returned function still uses.

## Follow one name through a nested function

```javascript
const label = 'global';

function makeReader() {
  const label = 'outer';

  return function read() {
    return label;
  };
}

const reader = makeReader();
console.log(reader()); // 'outer'
```

Follow the read of `label`:

1. Calling `makeReader()` creates its own variable named `label`, with the value `'outer'`.
2. The function `read` is defined inside `makeReader`, so it can use that variable.
3. `makeReader` returns `read`. The variable `reader` now holds that returned function.
4. Calling `reader()` runs `read`. There is no `label` declared inside `read`, so JavaScript checks the surrounding scope: the call to `makeReader` that created it.
5. It finds `label = 'outer'` and stops searching. The top-level `label = 'global'` is a separate variable.

```text
read call
  local variables: no label
  outer ──► makeReader call
              local variables: label = 'outer' ← read stops here
              outer ──► enclosing module/script environment
                          label = 'global'
```

JavaScript follows where the function was **defined**, not where it is called. Calling `reader()` from another function would not make it read that caller's local `label`. A function that keeps access to surrounding variables is a **closure**; [the closures chapter](10.1.1.06-closures.md) explains that behavior further.

## Inside a lexical environment: what the Environment Record stores

JavaScript needs information about the variables in each scope. **Environment Record** is the language specification's name for that information. In the example above, the record for the `makeReader` call describes its own `label` variable.

A **binding** connects a name to a particular variable. That variable can have a current value or be waiting for its declaration to initialize it. After `let score = 10` runs, the name `score` refers to `10`. Reassigning `score` changes the value of that same binding.

The record also tracks whether a variable is ready to read and whether its value can be reassigned. **Initialized** means its initial value has been set; `let score = 10` initializes `score` to `10`.

For `let score = 10` and `const limit = 20`, the record needs this information after the declarations run:

| Name | After its declaration executes | Can the binding be reassigned? |
| ------- | ------------------------------ | ------------------------------ |
| `score` | Initialized to `10` | Yes |
| `limit` | Initialized to `20` | No |

`const` prevents assigning another value to that name. It does not prevent changing the properties of an object held by the variable.

A record also has an **outer link**: a reference to the record for the surrounding scope. If the current record has no variable with the requested name, JavaScript uses that link to continue searching. In the diagram above, the arrows show these links.

### Different records represent different kinds of scope

The lookup problem is the same at every level: does this scope supply the requested name, and if so, how should the read behave? The source of the binding differs. A block supplies its own declarations, a module can refer to another module's exported variable, and the global scope must also expose names backed by object properties.

The specification describes these differences with record types. **Declarative** means the names come from declarations in that scope. Function and Module records specialize that model. **Object** means the names are backed by properties of an associated object. A **Global** record combines declarative and object-backed bindings.

```text
Environment Record — common name-lookup operations and an outer link
├─ Declarative — bindings established by declarations
│  ├─ Function — function-call state, including applicable this state
│  └─ Module — module declarations and connections to imports
├─ Object — bindings backed by an object's properties
└─ Global — combines Declarative and Object responsibilities
```

This is a relationship between specification types, not five parts allocated inside every scope or JavaScript classes you instantiate. The following cases explain what each distinction changes.

## Declarative records give a block its own names

A block can introduce a variable without putting a property on an application object. Its Declarative record identifies that binding and its initialization state. This is the kind of record that explains the inner `score` in the TDZ example below.

```javascript
let mode = 'outside';
{
  let mode = 'inside';
  mode = 'changed';
  console.log(mode); // changed
}
console.log(mode); // outside
```

Entering the block establishes an inner `mode`. Its declaration initializes it to `'inside'`; the assignment updates that binding. The first read finds it before searching outward. After the block exits, lookup starts outside again, where the original `mode` is still `'outside'`. The two names did not identify the same variable.

Catch parameters and loop declarations also need scope boundaries. The exact placement depends on the construct: a `for (let …)` loop additionally establishes per-iteration bindings. The [scope chapter](10.1.1.02-scope.md) owns that loop trace.

## Function records connect names to a particular invocation

Calling a function establishes a fresh environment for that invocation. Parameters and local declarations therefore belong to the call that is executing, rather than one shared store attached to the source-code definition. This explains why two calls to `makeReader` can return functions with different outer bindings.

An ordinary function's call also needs a `this` value: the receiver selected by its invocation. Function records supply the relevant `this` state. Arrows still have their own parameters and local names, but do not establish their own `this` or implicit `arguments`; those are resolved through the enclosing environment.

```javascript
'use strict';
function describe(id) {
  return () => [this.name, arguments[0]];
}
const read = describe.call({ name: 'first' }, 7);
console.log(read.call({ name: 'second' }, 99)); // ['first', 7]
```

The first call supplies `describe` with `this.name = 'first'` and argument `7`. The returned arrow uses that enclosing call's `this` and `arguments`. Its later `.call` cannot replace those captured sources, so neither `'second'` nor `99` appears in the result. `id` is a parameter binding; `arguments` is the implicit argument object in this example, not a synonym for all local variables.

Constructor calls have additional call state, including `new.target`, which identifies the constructor supplied by the construction operation. In a derived constructor, accessing `this` before `super()` initializes it fails. These are reasons a Function record needs more than a block's ordinary named bindings. See [this](../02-objects-prototypes-this/10.1.2.01-this.md) for complete receiver rules.

## Module records connect an import to the exported binding

A module has its own top-level declarations. An import can expose a variable owned by another module, so a Module record must describe that connection rather than simply store a copied value.

Save these as two files and run `main.mjs` as a native ES module:

```javascript
// counter.mjs
export let count = 0;
export function increment() { count += 1; }
```

```javascript
// main.mjs
import { count, increment } from './counter.mjs';
console.log(count); // 0
increment();
console.log(count); // 1
try {
  count = 99;
} catch (error) {
  console.log(error.name); // TypeError in native execution
}
```

The importing code reads the current exported `count` both times. `increment` changes the exporter's binding, so the second read observes `1`. This is a **live binding**. The importer cannot assign a different value through its import; the exporting module controls that variable. A build tool may reject that assignment before execution instead.

This restriction concerns reassignment of the binding. An imported object can still be mutable. Imports also do not bypass initialization: a cyclic dependency can attempt to read an exported lexical variable while it is still uninitialized. [Modules](../05-functional-patterns/10.1.5.01-modules.md) owns linking, cycles and their complete examples.

## Object records resolve names through object properties

An Object record uses an associated object's properties to answer lookup operations. Finding such a binding can involve property checks and reads, rather than a declaration-only store. In the global environment, this explains how a name such as `Math` can correspond to a property of the global object.

Legacy `with (object) { … }` code places an object's eligible properties in the identifier-lookup path. That changes what an unqualified name means without writing `object.name` at the read site. It makes dependencies hard to see and is forbidden in strict code, including ES modules. Prefer explicit property access; this record type explains the language model, not a recommended way to organize new code.

An ordinary expression such as `settings.theme` does not create an Object Environment Record for `settings`. It performs a property access after resolving the variable `settings`. A namespace or options object is not automatically a lexical scope.

## Global records reconcile script declarations with the global object

A **global object** exposes properties such as standard global APIs. `globalThis` provides access to the host's global `this` value; browser hosts can expose it through a proxy. Reading `globalThis.name` is an object-property operation. Reading an unqualified `name` instead uses identifier resolution, which can also find a declarative global binding.

Run this in a fresh browser page as a classic `<script>`, using names not already present on its global object:

```javascript
var scriptCount = 10;
let scriptLimit = 20;
console.log(scriptCount, globalThis.scriptCount); // 10 10
console.log(scriptLimit, Object.hasOwn(globalThis, 'scriptLimit')); // 20 false
```

Both declarations are available by name. The Global record's Object part backs the classic script's `var`; its Declarative part holds `let`. Consequently, `scriptCount` is also an object property, while `scriptLimit` is not. Top-level `const` and class declarations similarly belong to the declarative side. This is why “all global variables are properties of window” is an incomplete model.

Now run a separate fresh page with `<script type="module">`:

```javascript
var moduleCount = 10;
let moduleLimit = 20;
console.log(moduleCount, moduleLimit); // 10 20
console.log(Object.hasOwn(globalThis, 'moduleCount')); // false
console.log(Object.hasOwn(globalThis, 'moduleLimit')); // false
```

Both declarations belong to the Module record, including `var`. They do not become global-object properties. The module can still resolve available global names through its outer environment; isolation of its declarations does not remove access to global APIs.

These examples compare browser classic scripts with native modules. A Node.js CommonJS file has a wrapper-function boundary, and a developer-tools console can have special evaluation behavior. State the environment before predicting what `globalThis` contains.

## LE and VE identify different jobs inside execution state

The execution context keeps two environment references. **LexicalEnvironment (LE)** identifies the starting record for ordinary identifier resolution. **VariableEnvironment (VE)** identifies the record used for `var` declarations in that evaluation.

They can point to the same record. Entering a block can make LE point to a new inner Declarative record while VE stays at the applicable function-level record. That explains how a block can isolate `let` while an ordinary `var` remains available after the block. Reads of either declaration still use the normal lookup chain; there is no separate search reserved for `var` names.

Do not equate LE with “the let/const storage” and VE with “a second var storage.” They describe roles, not two disjoint heaps. Function setup, parameter expressions and strictness affect the records involved. The [execution-context trace](10.1.1.01-execution-context.md#follow-le-and-ve-through-a-block) shows the transitions and a default-parameter case.

## An inner declaration stops lookup even before initialization

```javascript
let score = 10;

try {
  {
    console.log(score); // ReferenceError
    let score = 20;
  }
} catch (error) {
  console.log(error instanceof ReferenceError); // true
}

console.log(score); // 10
```

The inner block has its own `score` variable from the start of the block. However, JavaScript has not yet executed `let score = 20`, so that variable is not ready to read.

The read finds the inner `score` and throws a `ReferenceError`. It does not skip that variable and use the outer value `10`. The time from entering the scope until the declaration initializes the variable is called the **temporal dead zone (TDZ)**. See [MDN: let and TDZ](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/let).

After the block, the outer `score` is unchanged. [Hoisting](10.1.1.04-hoisting.md) explains when different declarations become usable; [scope](10.1.1.02-scope.md) explains their visibility boundaries.

## Each factory call gives its returned function different state

```javascript
function makeCounter() {
  let count = 0;
  return () => ++count;
}

const first = makeCounter();
const second = makeCounter();

console.log(first());  // 1
console.log(first());  // 2
console.log(second()); // 1
```

Each call to `makeCounter()` creates a new `count` variable. The function stored in `first` uses the first call's variable. The function stored in `second` uses the second call's variable.

Calling `first()` twice changes its `count` from `0` to `1`, then to `2`. The other counter still starts at `0`, so its first call returns `1`. The returned function keeps access to its variable; it does not just receive a copy of the number that existed when it was created. See [MDN: closures](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Closures).

For callbacks created inside a `for (let i = …)` loop, each iteration has its own `i`. With `var`, those callbacks usually share one `i`. The [closures chapter](10.1.1.06-closures.md) traces the callback behavior.

## Keep the model separate from engine internals

The **language specification** is the document that defines how JavaScript must behave. It describes Environment Records so that variable lookup has precise rules. Your program cannot get one of these records as an ordinary JavaScript object.

In that document, `[[OuterEnv]]` is the name for a record's link to the surrounding scope. The double brackets mark an internal specification field. You do not write `record.[[OuterEnv]]` in application code. The diagram above uses “outer” for this link to make the search easy to follow. [ECMAScript environment records](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-environment-records).

Keep these three jobs separate:

| Concept | What it tracks |
| ------------------- | -------------------------------------------------------------------------------- |
| Execution context | Information needed to run the current code, including which environment it uses |
| Lexical environment | Which variables the code can use and where to search next |
| Call stack | Which function calls are currently running or waiting for another call to return |

A JavaScript **engine**, such as V8, is the software that runs your code. Engines may store and find variables differently from this diagram, as long as your code behaves according to the language rules. A drawing with more scope levels does not, by itself, prove that the code is slower.

A returned function can still use an outer variable after the creating call finishes. This does not mean that the call is still running or that every local variable must stay in memory. If you suspect a memory leak, inspect the objects kept alive in a memory profile instead of treating the diagram as a picture of actual memory.

## Summary

When code reads a variable, JavaScript checks its current scope, then the surrounding scopes. An Environment Record describes the names at one level and links to the next level. A variable found before its `let` or `const` declaration has run causes an error instead of falling back to an outer variable. A returned function can keep using the outer variables from the call that created it.

Record kinds adapt that model to declarations, function calls, live module imports and object-backed names. Global records reconcile classic-script declarations with the global object; native modules keep their declarations in their own environment. LE identifies the current lookup start, while VE supplies the relevant `var` declaration boundary.

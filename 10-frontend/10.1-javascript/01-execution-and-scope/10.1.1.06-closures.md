# Closures

When an outer function finishes, its context pops off the call stack. Why can a returned inner function still read and mutate that call's variables?

```javascript
function createCounter(start = 0) {
  let count = start;
  return {
    increment() { return ++count; },
    read() { return count; },
  };
}

const counter = createCounter(10);
console.log(counter.increment()); // 11
console.log(counter.read());      // 11
```

## Definition

A **closure** is a function bundled with references to its surrounding lexical environment. An ECMAScript function's `[[Environment]]` records the defining environment used for enclosing-name lookup. When the function escapes — returned, passed as a callback, stored on an object — it keeps read/write access to its **free variables** (identifiers declared in an outer scope but used inside).

> **Textbook Definition:** A closure is a function together with access to its defining lexical environment. References to free variables resolve through that environment, retaining access to bindings rather than frozen copies of their values.

## First Principles

Functions are first-class values: they cross call and async boundaries as return values and arguments. If a function's identifiers lived only in physical stack frames, returning one would dangle the moment its frame popped. The implementation must preserve access to the relevant bindings for as long as reachable code needs them. Heap contexts are one engine technique; a closure is the language-level function/environment relationship, not a promise about promotion timing or object layout.

## 1. Retained Bindings Outlive an Active Call

```text
1. CALL: createCounter() executes on Call Stack
   [ Call Stack: createCounter() Frame ]
   └── Instantiates inner increment() and read()

2. RETAIN: Returned functions keep access to the captured binding
   [ Binding environment: conceptual, not a required object layout ]
   ├── count: 10
   ├── increment.[[Environment]] ──► points to binding environment
   └── read.[[Environment]]      ──► points to binding environment

3. RETURN: createCounter() frame is popped off Call Stack
   └── The count binding remains usable through the returned functions!
```

When `createCounter()` returns, its evaluation is no longer an active call. Both returned functions still resolve the same `count` binding. The engine may represent that state in a heap context or another equivalent form; the observable sharing is the contract.

## 2. Closures Bind to Live References, Not Snapshot Copies

Closures close over the variable **binding itself**, not a frozen copy:

```javascript
let status = 'pending';
const readStatus = () => status;

console.log(readStatus()); // 'pending'

status = 'completed';      // Mutating outer variable
console.log(readStatus()); // 'completed' (observes updated binding!)
```

The closure holds the storage slot of `status`, so outer mutations are immediately visible through it.

## 3. Sibling Closures Share Bindings

Functions defined in the same scope share the **same** lexical environment record — while separate calls get separate records:

```javascript
function makeStore() {
  let value = 0;
  return {
    set(v) { value = v; },
    get()  { return value; }
  };
}

const storeA = makeStore();
const storeB = makeStore();

storeA.set(42);
console.log(storeA.get()); // 42
console.log(storeB.get()); // 0 (storeB has its own independent value binding)
```

`storeA`'s methods share one `value` binding, but the second `makeStore()` call supplies a distinct `value` binding — the two stores stay isolated.

## 4. Real-World Architectural Patterns

Closures underpin state management and functional programming in JavaScript:

1. **Data encapsulation (module pattern)** — `balance` is truly private; only the returned methods can touch it:
   ```javascript
   function createBankAccount(initialBalance) {
     let balance = initialBalance; // Truly private variable
     return {
       deposit(amount) {
         if (amount > 0) balance += amount;
         return balance;
       },
       getBalance() { return balance; }
     };
   }
   ```
2. **Function factories and partial application** — each call captures its own `factor`:
   ```javascript
   const createMultiplier = factor => value => value * factor;
   const double = createMultiplier(2);
   const triple = createMultiplier(3);
   console.log(double(5)); // 10
   console.log(triple(5)); // 15
   ```
3. **Stateful utilities (debounce)** — `timerId` persists across invocations of the returned function:
   ```javascript
   function debounce(fn, delayMs) {
     let timerId = null; // Preserved across invocations
     return function(...args) {
       clearTimeout(timerId);
       timerId = setTimeout(() => fn.apply(this, args), delayMs);
     };
   }
   ```

## 5. Retention Needs a Reachable Owner

A registered listener can keep its callback and the data it actually captures reachable. Releasing the registration ends that retaining path; other owners may still exist:

```javascript
function observeSelection(target, state, onSelection) {
  const listener = () => onSelection(state.selectedId);
  target.addEventListener('change', listener);
  return () => target.removeEventListener('change', listener);
}

const target = new EventTarget();
const state = { selectedId: 'item-1' };
const stop = observeSelection(target, state, id => console.log(id));
target.dispatchEvent(new Event('change')); // item-1
stop();
target.dispatchEvent(new Event('change')); // listener no longer runs
```

The callback captures `state`, so its reachable object graph may matter. Cleanup must remove the same registered listener; dropping an unrelated local reference does not remove it. A returned cleanup function also has an owner and must itself become unreachable when no longer needed.

Some engine versions can retain additional values through shared closure contexts; optimizers can also eliminate unused values. A nearby large array and an unused nested function therefore do not prove a particular leak or byte count. Inspect a heap snapshot's retaining path, then release the long-lived owner or move the necessary small state into a narrower factory. See [Garbage Collection](../04-memory-and-data/10.1.4.07-garbage-collection.md) for reachability and diagnosis.

## 6. The React Stale Closure Dilemma

Re-renders create fresh closures, so a long-lived callback can capture an older render's bindings:

```javascript
// Inside a React component:
// const [count, setCount] = useState(0);

// Problematic: Captures 'count' at the moment the callback was scheduled
// setTimeout(() => {
//   setCount(count + 1); // If count was 0, it sets 1, ignoring subsequent updates
// }, 2000);

// Solution: Functional State Updates bypass stale closures
// setCount(prevCount => prevCount + 1);
```

An updater function (`prevCount => prevCount + 1`) lets React apply that update to the pending state in its queue rather than using the captured `count`. It does not refresh other captured props, cancel an obsolete request or order server writes. Those values and operations need their own identity/lifecycle policy.

## Summary

Closures bind functions to their defining lexical environments, so escaping functions keep access to free variables after the parent frame pops. The implementation preserves access without requiring the completed parent call to remain active; its physical representation can vary. A closure reads its captured bindings; different React renders create different bindings. Retained binding identity powers private state, currying and debounce. Inspect retaining paths and release listeners or other long-lived owners when their captured state is no longer needed.

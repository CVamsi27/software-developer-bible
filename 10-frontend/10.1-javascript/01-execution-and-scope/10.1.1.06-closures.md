# Closures

When an outer function finishes executing, its execution context is popped off the Call Stack. Why can an inner returned function continue to read and mutate variables that belonged to that completed call?

```javascript
function createCounter(start = 0) {
  let count = start;
  return {
    increment() { return ++count; },
    read() { return count; },
  };
}

const counter = createCounter(10);
console.log(counter.increment()); // 11
console.log(counter.read());      // 11
```

## Definition

A **closure** is the combination of a function bundled together with references to its surrounding lexical environment. In ECMAScript, whenever a function is instantiated, it maintains an internal reference (`[[Environment]]`) to the active Environment Record. Even when the function escapes its creating scope—by being returned, passed as a callback, or stored on an object—it retains direct read and write access to its **free variables** (identifiers used inside the function that were declared in an outer scope).

> **Textbook Definition:** A closure is a function together with access to its defining lexical environment. References to free variables resolve through that environment, retaining access to bindings rather than frozen copies of their values.

## First Principles

1. **First-Class Functions**: In JavaScript, functions are values: they can be returned from other functions, assigned to variables, and passed as arguments across asynchronous boundaries.
2. **Lexical Scope Persistence**: If a function's accessible identifiers were tied strictly to physical stack frames, returning a function would cause undefined behavior or dangling pointers as soon as the stack frame popped.
3. **Heap Context Promotion**: To keep free variables accessible after an enclosing function returns, the runtime promotes captured variables from short-lived CPU stack frames to persistent, garbage-collected heap objects.

## How It Works

### 1. Stack vs. Heap Allocation: How Closures Outlive Stack Frames

In low-level languages like C, local variables live on the stack and are destroyed upon function return. JavaScript solves this with escape analysis:

```text
1. CALL: createCounter() executes on Call Stack
   [ Call Stack: createCounter() Frame ]
   └── Instantiates inner increment() and read()

2. ESCAPE: Variables captured by inner functions are allocated on Heap
   [ Heap: V8 Context Object ]
   ├── count: 10
   ├── increment.[[Environment]] ──► points to Context
   └── read.[[Environment]]      ──► points to Context

3. RETURN: createCounter() frame is popped off Call Stack
   └── The Heap Context remains alive because increment and read still reference it!
```

When `createCounter()` returns, its execution context leaves the call stack. However, the internal heap `Context` object holding `count` remains alive in memory because `counter.increment` and `counter.read` hold references to it.

### 2. Closures Bind to Live References, Not Snapshot Copies

A common misconception is assuming closures take a frozen copy of a variable at the time the closure is created. In JavaScript, **closures close over the variable binding itself**:

```javascript
let status = 'pending';
const readStatus = () => status;

console.log(readStatus()); // 'pending'

status = 'completed';      // Mutating outer variable
console.log(readStatus()); // 'completed' (observes updated binding!)
```

The closure maintains a live reference to the storage slot of `status`. When the outer scope mutates the variable, the closure immediately observes the new value.

### 3. Shared Context Slots Across Sibling Closures

When multiple functions are defined within the same enclosing scope, they share the **exact same** lexical environment record:

```javascript
function makeStore() {
  let value = 0;
  return {
    set(v) { value = v; },
    get()  { return value; }
  };
}

const storeA = makeStore();
const storeB = makeStore();

storeA.set(42);
console.log(storeA.get()); // 42
console.log(storeB.get()); // 0 (storeB has its own independent heap Context)
```

- Methods on `storeA` share the same `value` binding.
- Calling `makeStore()` a second time allocates an entirely separate heap Context for `storeB`, keeping their private states completely isolated.

### 4. Real-World Architectural Patterns

Closures are the foundational building block for state management and functional programming in JavaScript:

1. **Data Encapsulation (Module Pattern)**:
   ```javascript
   function createBankAccount(initialBalance) {
     let balance = initialBalance; // Truly private variable
     return {
       deposit(amount) {
         if (amount > 0) balance += amount;
         return balance;
       },
       getBalance() { return balance; }
     };
   }
   ```
2. **Function Factories & Partial Application**:
   ```javascript
   const createMultiplier = factor => value => value * factor;
   const double = createMultiplier(2);
   const triple = createMultiplier(3);
   console.log(double(5)); // 10
   console.log(triple(5)); // 15
   ```
3. **Stateful Utilities (Debounce)**:
   ```javascript
   function debounce(fn, delayMs) {
     let timerId = null; // Preserved across invocations
     return function(...args) {
       clearTimeout(timerId);
       timerId = setTimeout(() => fn.apply(this, args), delayMs);
     };
   }
   ```

### 5. Memory Leaks: Retaining Paths and the V8 Shared Context Pitfall

Because closures keep outer variables reachable from GC roots, they can prevent memory from being reclaimed if lifecycle boundaries are mismanaged.

#### The V8 Shared Scope Pitfall (The Meteor Leak)
In Google V8, all closures declared in the same scope share a single heap `Context` object:

```javascript
let leak = null;

function outer() {
  const hugeBuffer = new Array(10000000).fill('data'); // 80MB buffer
  const smallId = 42;

  function unusedClosure() {
    // Reading hugeBuffer forces it into the shared Heap Context!
    if (hugeBuffer) return;
  }

  // leak escapes and references smallId, but DOES NOT use hugeBuffer
  leak = function retainedClosure() {
    return smallId;
  };
}

outer();
// Problem: 'leak' keeps the entire shared Heap Context alive,
// including hugeBuffer, even though retainedClosure never touches hugeBuffer!
```

**Senior Mitigation**: If a function produces a long-lived closure alongside large temporary buffers, null out the large references or isolate the escaping closure in its own separate function scope.

### 6. The React Stale Closure Dilemma

In React, state updates trigger re-renders that instantiate fresh closures. A "stale closure" occurs when a long-lived callback captures an older render's variable binding:

```javascript
// Inside a React component:
// const [count, setCount] = useState(0);

// Problematic: Captures 'count' at the moment the callback was scheduled
// setTimeout(() => {
//   setCount(count + 1); // If count was 0, it sets 1, ignoring subsequent updates
// }, 2000);

// Solution: Functional State Updates bypass stale closures
// setCount(prevCount => prevCount + 1);
```

Passing an updater function (`prevCount => prevCount + 1`) decouples state mutation from the closed-over scope, ensuring the latest runtime state is always updated.

## Summary

Closures bind functions to their surrounding lexical environments, allowing escaping functions to retain access to free variables after parent execution contexts pop off the call stack. Engines implement closures by allocating captured variables in persistent heap Context objects rather than native stack frames. Closures reference live mutable bindings rather than frozen snapshots, enabling patterns like private state, currying, and debouncing. Managing closure lifecycles—including event listener teardown and shared heap context hygiene—is essential to preventing production memory leaks.

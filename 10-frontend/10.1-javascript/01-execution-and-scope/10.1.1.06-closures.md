# Closures

## Definition

A **closure** is a function that keeps access to variables from the scope where it was defined. A **binding** connects a variable name to that variable and its current state. The enclosing **lexical environment** describes these bindings and how to find names in outer scopes. Returning the function or passing it elsewhere does not change which outer variables it uses. It can still access them after the enclosing function call finishes.

A **free variable** is a name used inside a function but not declared as one of its own parameters or local variables. Its lookup reaches the surrounding environment; “free” does not mean the name is undeclared everywhere.

> **Textbook Definition:** A closure is a function together with access to its defining lexical environment. References to free variables resolve through that environment, retaining access to bindings rather than frozen copies of their values.

## First Principles

1. Functions are values: they can leave the call that created them.
2. Their bodies still reference outer bindings. Lexical access must remain meaningful wherever those functions are invoked.
3. Several functions can share one binding. A closure reads that binding's current value rather than taking an automatic frozen copy.

## Follow shared state after the creating call returns

```javascript
function createCounter(start = 0) {
  let count = start;
  return {
    increment() { return ++count; },
    read() { return count; },
  };
}
const first = createCounter(0);
const second = createCounter(10);
console.log(first.increment()); // 1
console.log(first.read());      // 1
console.log(second.read());     // 10
```

1. The first factory call establishes its own `count` binding.
2. Both returned methods retain access to that binding.
3. The factory returns, so its evaluation leaves the active call stack.
4. `first.increment()` changes the shared binding; `first.read()` observes the change.
5. A second factory call establishes a different binding, so its state remains independent.

```text
first.increment ─┐
                 ├─→ environment A: count = 1
first.read ──────┘
second.read ────────→ environment B: count = 10

active stack: current method call → caller
retained state: environment bindings, not the completed factory frame
```

## A closure reads its binding, not a frozen value

```javascript
let status = 'pending';
const readStatus = () => status;
status = 'complete';
console.log(readStatus()); // complete
```

The closure follows the same binding after reassignment. If you need a snapshot of a primitive value, create a separate binding with that value at the intended time. For an object, another binding can still reference the same mutable object; copying a reference does not create an independent snapshot. This also explains [loop callbacks](10.1.1.02-scope.md#a-fresh-binding-for-each-loop-iteration): shared `var` versus per-iteration `let` is a binding distinction.

An arrow's `this` is lexical, but ordinary methods choose `this` at invocation. Closure access to a variable and selection of `this` are separate rules; see [Execution Context](10.1.1.01-execution-context.md#what-this-depends-on).

## Decide who owns the retained state

Factories can configure functions without classes:

```javascript
function createMultiplier(factor) {
  return value => value * factor;
}
console.log(createMultiplier(3)(5)); // 15
```

The same retained state can hold a debounce timer, an iterator's position or a memoization cache. A closure alone does not make those helpers correct. A debounce helper must decide how cancellation works and preserve the intended `this` value. A memoizer needs keys that correctly distinguish inputs and limits on how much data its cache keeps. `JSON.stringify(args)` cannot uniquely identify every possible JavaScript input. The canonical chapters develop those complete contracts.

For React, each render establishes new local bindings. An old callback may read an old render's state. A functional state update uses the updater's supplied current state; dependencies, refs and effect cleanup each solve a different part of that lifecycle. Use the React chapters for complete examples.

## Give Listeners a Cleanup Owner

```javascript
function installClickListener(target, message) {
  const handler = () => console.log(message);
  target.addEventListener('click', handler);
  return () => target.removeEventListener('click', handler);
}
// const cleanup = installClickListener(button, 'Saved');
// cleanup(); // when the owner's lifetime ends
```

The target retains the callback while registered. Removing it releases that reference, provided no other owner retains it. Timers, subscriptions and caches have similar ownership questions.

A closure does not necessarily keep every variable from its surrounding function in memory. An engine may omit a large variable that the closure never reads. When the callback needs only a small value from a large structure, calculate that value first and let the callback use it. To confirm a leak, inspect the **retaining path** in a memory profile: the chain of references that keeps the object alive. Source syntax alone does not prove its physical memory layout.

## Privacy Has a Boundary

The counter's `count` is not an exposed object property. That is useful encapsulation, but it is not a security sandbox. Returning mutable internal objects can expose the state indirectly. A WeakMap or private class field supplies other encapsulation options; they do not automatically replace the lifecycle responsibilities of listeners and caches.

## Common Mistakes

| Mistake | Repair |
| ----------------------------------------------------------------- | ----------------------------------------------------------------- |
| Expecting a closure to copy every value when created | Trace the binding and later mutations |
| Saying the outer call remains on the stack | Separate retained lexical access from active evaluation |
| Sharing `var` in delayed loop callbacks | Use the intended per-iteration binding |
| Leaving a registered callback past its owner lifetime | Return and invoke cleanup |
| Calling a one-shot handler again after clearing its captured data | Define repeat-call behavior instead of using a non-null assertion |
| Assuming every closure is a leak | Identify an unintended long-lived owner and inspect reachability |

## Summary

Trace which binding each function retains, whether other functions share it, and which owner keeps the function reachable. A completed call can leave usable lexical state without occupying the call stack. Cleanup, cache bounds and render lifecycles determine whether that retained state is useful or accidental.

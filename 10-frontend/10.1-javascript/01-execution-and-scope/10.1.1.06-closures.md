# Closures

When an outer function finishes, its context pops off the call stack. Why can a returned inner function still read and mutate that call's variables?

```javascript
function createCounter(start = 0) {
  let count = start;
  return {
    increment() { return ++count; },
    read() { return count; },
  };
}

const counter = createCounter(10);
console.log(counter.increment()); // 11
console.log(counter.read());      // 11
```

## Definition

A **closure** is a function bundled with references to its surrounding lexical environment. Every instantiated function carries an internal `[[Environment]]` pointer to the active Environment Record. When the function escapes — returned, passed as a callback, stored on an object — it keeps read/write access to its **free variables** (identifiers declared in an outer scope but used inside).

> **Textbook Definition:** A closure is a function together with access to its defining lexical environment. References to free variables resolve through that environment, retaining access to bindings rather than frozen copies of their values.

## First Principles

Functions are first-class values: they cross call and async boundaries as return values and arguments. If a function's identifiers lived only in physical stack frames, returning one would dangle the moment its frame popped. The runtime therefore promotes captured variables from short-lived stack frames to persistent, garbage-collected heap objects — which is exactly what a closure is.

## How It Works

### 1. Stack vs. Heap Allocation: How Closures Outlive Stack Frames

```text
1. CALL: createCounter() executes on Call Stack
   [ Call Stack: createCounter() Frame ]
   └── Instantiates inner increment() and read()

2. ESCAPE: Variables captured by inner functions are allocated on Heap
   [ Heap: V8 Context Object ]
   ├── count: 10
   ├── increment.[[Environment]] ──► points to Context
   └── read.[[Environment]]      ──► points to Context

3. RETURN: createCounter() frame is popped off Call Stack
   └── The Heap Context remains alive because increment and read still reference it!
```

When `createCounter()` returns, its frame leaves the stack — but the heap `Context` holding `count` survives because the two returned functions still reference it.

### 2. Closures Bind to Live References, Not Snapshot Copies

Closures close over the variable **binding itself**, not a frozen copy:

```javascript
let status = 'pending';
const readStatus = () => status;

console.log(readStatus()); // 'pending'

status = 'completed';      // Mutating outer variable
console.log(readStatus()); // 'completed' (observes updated binding!)
```

The closure holds the storage slot of `status`, so outer mutations are immediately visible through it.

### 3. Shared Context Slots Across Sibling Closures

Functions defined in the same scope share the **same** lexical environment record — while separate calls get separate records:

```javascript
function makeStore() {
  let value = 0;
  return {
    set(v) { value = v; },
    get()  { return value; }
  };
}

const storeA = makeStore();
const storeB = makeStore();

storeA.set(42);
console.log(storeA.get()); // 42
console.log(storeB.get()); // 0 (storeB has its own independent heap Context)
```

`storeA`'s methods share one `value` binding, but the second `makeStore()` call allocates an entirely separate heap Context — the two stores stay isolated.

### 4. Real-World Architectural Patterns

Closures underpin state management and functional programming in JavaScript:

1. **Data encapsulation (module pattern)** — `balance` is truly private; only the returned methods can touch it:
   ```javascript
   function createBankAccount(initialBalance) {
     let balance = initialBalance; // Truly private variable
     return {
       deposit(amount) {
         if (amount > 0) balance += amount;
         return balance;
       },
       getBalance() { return balance; }
     };
   }
   ```
2. **Function factories and partial application** — each call captures its own `factor`:
   ```javascript
   const createMultiplier = factor => value => value * factor;
   const double = createMultiplier(2);
   const triple = createMultiplier(3);
   console.log(double(5)); // 10
   console.log(triple(5)); // 15
   ```
3. **Stateful utilities (debounce)** — `timerId` persists across invocations of the returned function:
   ```javascript
   function debounce(fn, delayMs) {
     let timerId = null; // Preserved across invocations
     return function(...args) {
       clearTimeout(timerId);
       timerId = setTimeout(() => fn.apply(this, args), delayMs);
     };
   }
   ```

### 5. Memory Leaks: Retaining Paths and the V8 Shared Context Pitfall

Closures keep outer variables reachable from GC roots, so mismanaged lifecycles leak memory. In V8, all closures declared in one scope share a **single** heap `Context`:

```javascript
let leak = null;

function outer() {
  const hugeBuffer = new Array(10000000).fill('data'); // 80MB buffer
  const smallId = 42;

  function unusedClosure() {
    // Reading hugeBuffer forces it into the shared Heap Context!
    if (hugeBuffer) return;
  }

  // leak escapes and references smallId, but DOES NOT use hugeBuffer
  leak = function retainedClosure() {
    return smallId;
  };
}

outer();
// Problem: 'leak' keeps the entire shared Heap Context alive,
// including hugeBuffer, even though retainedClosure never touches hugeBuffer!
```

**Senior mitigation**: when a scope produces a long-lived closure beside large temporaries, null out the large references or isolate the escaping closure in its own function scope.

### 6. The React Stale Closure Dilemma

Re-renders create fresh closures, so a long-lived callback can capture an older render's bindings:

```javascript
// Inside a React component:
// const [count, setCount] = useState(0);

// Problematic: Captures 'count' at the moment the callback was scheduled
// setTimeout(() => {
//   setCount(count + 1); // If count was 0, it sets 1, ignoring subsequent updates
// }, 2000);

// Solution: Functional State Updates bypass stale closures
// setCount(prevCount => prevCount + 1);
```

An updater function (`prevCount => prevCount + 1`) decouples the mutation from the closed-over scope, so the latest runtime state always wins.

## Summary

Closures bind functions to their defining lexical environments, so escaping functions keep access to free variables after the parent frame pops. Engines implement this by promoting captured variables to persistent heap Context objects. Closures see live mutable bindings — never snapshots — which powers private state, currying, and debounce. Managing closure lifecycles, from listener teardown to shared-context hygiene, is what prevents production memory leaks.

# V8 Execution and Optimization

A JavaScript function runs slowly on its first calls, accelerates once warm, and suddenly stalls when handed an unexpected object shape or value type. That swing happens because V8 records runtime feedback to compile fast machine code for observed patterns, then bails out (**deoptimizes**) whenever a new input violates those assumptions.

```javascript
function calculateTotal(items) {
  let sum = 0;
  for (let i = 0; i < items.length; i++) {
    sum += items[i].price;
  }
  return sum;
}

const uniform = Array.from({ length: 1000 }, (_, i) => ({ id: i, price: 10 }));
let acc = 0;
for (let r = 0; r < 200; r++) acc += calculateTotal(uniform);
console.log('uniform:', acc); // uniform: 2000000

// A different property layout splits shape feedback at `items[i].price`.
console.log('mixed:', calculateTotal([{ id: 1, price: 10 }, { note: 'rush', id: 2, price: 20 }])); // mixed: 30
```

## Definition

**Google V8** is the open-source JavaScript and WebAssembly engine behind Chromium browsers and Node.js. Rather than staying in a pure interpreter, V8 uses a **multi-tier Just-In-Time (JIT) compilation pipeline**: source code becomes compact bytecode first for fast startup, and optimizing tiers compile hot functions using runtime shape and type feedback with deoptimization fallbacks that preserve ECMAScript semantics.

> **Textbook Definition:** A JavaScript engine implements the language's specified observable semantics and may interpret or compile code into native instructions. V8 uses runtime execution feedback to speculatively optimize hot functions and loops, reconstructing interpreter frames if speculative assumptions fail.

## First Principles

JavaScript allows dynamic property additions, heterogeneous arrays, and polymorphic operators, whereas CPU instructions expect fixed field offsets and concrete numeric types. Compiling every script with full optimizations at startup would stall initial page load and waste memory on cold initialization code. V8 resolves that trade-off by executing bytecode immediately, recording type and shape stability at each operation, specializing hot code paths around those observations, and keeping bailout metadata so correctness never breaks. Exact tier thresholds and cache sizes change across V8 releases, so treat numeric limits below as typical V8 behavior and profile your target build before tuning.

## 1. Parsing, Pre-Parsing, and the Multi-Tier JIT Pipeline

V8 defers expensive work on cold functions while promoting hot loops and callees through four execution tiers:

```text
source ─► parse and pre-parse ─► Ignition bytecode interpreter (collects feedback)
                                        │
                 ┌──────────────────────┼──────────────────────┐
                 ▼                      ▼                      ▼
        Sparkplug (baseline)    Maglev (mid-tier SSA)    TurboFan and Turboshaft
        fast native code        fast optimizing JIT      peak inlining and guards
                                        │                      │
                                        └──────────┬───────────┘
                                                   ▼ (guard fails or OSR exit)
                                       reconstruct Ignition frame and resume safely
```

1. **Lazy pre-parsing and bytecode caching:** When loading a script, V8 parses top-level executed code into an **Abstract Syntax Tree (AST)** and skips building full ASTs for uncalled inner functions. A lighter **pre-parser** validates syntax and tracks free variable references so outer scopes keep captured bindings alive, deferring full compilation until a function actually runs. On repeat script loads, V8 can cache compiled **Ignition** bytecode to skip re-parsing unchanged code.
2. **Ignition (bytecode interpreter):** Converts AST nodes into register-based bytecode so execution starts quickly. Every load, store, arithmetic op, and call reads a slot in the function's **feedback vector**, a per-function table storing observed shapes and types.
3. **Sparkplug (baseline compiler):** Translates Ignition bytecode directly into machine code without building an Intermediate Representation (IR), removing interpreter dispatch overhead with negligible compile cost.
4. **Maglev (mid-tier optimizing compiler):** Builds machine code from a **Static Single Assignment (SSA)** IR, where each computed value is assigned exactly once. Because values never change meaning mid-block, type narrowing and redundant check removal stay fast enough to run much earlier than peak optimization.
5. **TurboFan and Turboshaft (top-tier optimizing pipeline):** Consumes stable feedback vectors to inline callees, eliminate non-escaping allocations, and specialize loops. **On-Stack Replacement (OSR)** lets V8 swap a hot `for` or `while` loop from Ignition into Maglev or TurboFan mid-execution instead of waiting for the next function invocation.

## 2. Value Representations: Tagged Pointers, Smi, HeapNumber, and Pointer Compression

Before optimizing math or property reads, V8 distinguishes small integers from heap objects inside every JavaScript value slot. On 64-bit architectures, naive 64-bit pointers waste L1 and L2 cache capacity when most objects live in the same managed heap.

- **Pointer tagging:** Every V8 value slot carries a low **tag bit** telling generated machine code whether the word holds an unboxed integer or a heap pointer.
- **Smi (Small Integer):** V8 stores 31-bit signed integers directly inline inside the tagged word with zero heap allocation or garbage-collector pressure.
- **HeapNumber:** When arithmetic overflows the 31-bit Smi range or produces a non-integer float (`1.5`), V8 allocates a boxed IEEE-754 64-bit floating-point **HeapNumber** object on the heap and stores a pointer to it.
- **Pointer compression:** In standard 64-bit V8 builds, the managed heap sits inside a contiguous 4 GB virtual address reservation. V8 stores 32-bit offsets relative to that base address, shrinking every tagged object slot from 8 bytes to 4 bytes while reconstructing full pointers on dereference.

Because feedback vectors track whether an operation only saw `Smi`, `HeapNumber`, or strings, a function warmed on integers compiles directly into machine integer instructions with a cheap tag check on entry.

## 3. Hidden Classes (Maps): How a Shape Becomes an Offset

Two objects holding identical property names can hit different execution paths in a hot loop if their properties were attached in a different order. Instead of hashing property names at runtime, V8 attaches a shared **Map** (also called a hidden class) describing the object's layout.

### The Map describes the shape; the object holds the values

Creating `{ price: 10 }` gives the instance a pointer to a shared Map descriptor, while the instance itself stores field values in contiguous slots:

| Stored in the Map | Why it changes property access |
| ---------------------------------- | ---------------------------------------------------------------------------- |
| Property names and insertion order | Two objects share a Map only when names and order match |
| Field slot offsets | Converts a name lookup into a single base-plus-offset load |
| Backing-store overflow flags | Tracks whether excess fields live in an external property array |
| Transition pointers to child Maps | Attaching a new key follows a shared edge instead of building a custom shape |
| Prototype and descriptor metadata | Distinguishes data fields from getters, setters, or prototype mutations |

### Adding properties walks a transition tree

```text
Map A (empty)
  ├─ add 'x' ─► Map B { x }
  │               └─ add 'y' ─► Map C { x, y }
  └─ add 'y' ─► Map D { y }
                  └─ add 'x' ─► Map E { y, x }
```

Every object constructed via `{ x: 1, y: 2 }` lands on Map C, whereas constructing `{ y: 2, x: 1 }` lands on Map E. A common production bug is conditionally omitting optional fields (`if (note) item.note = note`) rather than initializing `{ id, note: undefined }`: half the batch lands on one Map and half on another, splitting every downstream access site.

### Out-of-object properties and dictionary mode

When an object grows past its inline slots, V8 moves extra fields into a separate properties array, adding one pointer indirection. Repeated random `delete` calls or chaotic mutations can convert the object into **dictionary mode** (a self-contained hash table), removing fast offset access while preserving correctness. Initializing consistent keys upfront or keeping `delete` off hot objects avoids shape thrash without forbidding `delete` on cold configuration maps.

You can verify whether two instances share one Map using Node's native diagnostics (do not enable `--allow-natives-syntax` in production):

```javascript
// Run with: node --allow-natives-syntax check-maps.js
const a = { id: 1, note: undefined };
const b = { id: 2, note: 'urgent' };
const c = { note: 'urgent', id: 2 };
const d = { id: 3 };

console.log('initialized same shape:', %HaveSameMap(a, b));  // true
console.log('reversed keys:', %HaveSameMap(a, c));           // false
console.log('conditional omitted key:', %HaveSameMap(a, d)); // false
```

## 4. Elements Kinds: How V8 Optimizes Arrays

Objects use Maps for named properties, while arrays track numeric indices (`0`, `1`, `2`) separately through **Elements Kinds** along two dimensions: **value type** (`SMI`, `DOUBLE`, `ELEMENTS`) and **density** (`PACKED` vs. `HOLEY`).

```text
PACKED_SMI_ELEMENTS  ──► PACKED_DOUBLE_ELEMENTS ──► PACKED_ELEMENTS
        │                         │                        │
        ▼ (introduce hole)        ▼                        ▼
HOLEY_SMI_ELEMENTS   ──► HOLEY_DOUBLE_ELEMENTS  ──► HOLEY_ELEMENTS ──► DICTIONARY_ELEMENTS
```

Three array rules directly govern hot-loop speed:

1. **Transitions are strictly one-way:** Pushing a float (`19.99`) onto a `PACKED_SMI_ELEMENTS` array widens every element slot to unboxed doubles (`PACKED_DOUBLE_ELEMENTS`). Pushing a string converts the backing store to tagged pointers (`PACKED_ELEMENTS`). Deleting elements, calling `.pop()`, or truncating `.length` never promotes the array back to a tighter kind.
2. **Pre-allocating `new Array(n)` starts `HOLEY`:** Writing `new Array(1000)` allocates 1,000 empty holes (`HOLEY_SMI_ELEMENTS`) instead of a dense array. Filling via `[].push(...)` or `Array.from(...)` preserves `PACKED` representations until an index is skipped.
3. **Holes trigger prototype-chain lookups:** Reading a dense slot inside bounds loads straight from backing memory. Reading a hole (`undefined` gap) forces V8 to inspect `Array.prototype` and `Object.prototype` in case an indexed accessor or property exists there.

```javascript
// Run with: node --allow-natives-syntax check-elements.js
const prices = [10, 20, 30];
console.log('PACKED_SMI:', !%HasHoleyElements(prices), %HasSmiElements(prices));       // true true

prices.push(19.99);
console.log('PACKED_DOUBLE:', !%HasHoleyElements(prices), %HasDoubleElements(prices)); // true true

prices.push('USD');
console.log('PACKED_ELEMENTS:', !%HasHoleyElements(prices), %HasObjectElements(prices)); // true true

prices[10] = 'EUR';
console.log('HOLEY_ELEMENTS:', %HasHoleyElements(prices), %HasObjectElements(prices)); // true true

prices.pop();
console.log('after pop still HOLEY:', %HasHoleyElements(prices));                      // true

const preallocated = new Array(3);
console.log('new Array(3) HOLEY_SMI:', %HasHoleyElements(preallocated), %HasSmiElements(preallocated)); // true true
```

## 5. Inline Caches (IC): Monomorphic, Polymorphic, and Megamorphic

An **Inline Cache (IC)** sits at each property read (`item.price`), method call, or element access and updates its slot in the function's feedback vector with every Map seen there:

1. **Monomorphic (1 Map):** One inline Map check guards a direct slot offset load. This gives optimizing compilers exact type knowledge to inline and specialize downstream math.
2. **Polymorphic (typically 2–4 Maps):** The site checks a short linear list of observed Maps and offsets, adding one comparison per extra shape.
3. **Megamorphic (beyond the polymorphic limit):** V8 stops specializing per shape and consults a global fixed-size stub cache before falling back to generic dictionary or prototype lookup.

```javascript
function readX(point) {
  return point.x;
}

const sameOrder = { x: 1, y: 2 };        // Map C { x, y }
const reversed = {};
reversed.y = 2;
reversed.x = 1;                          // Map E { y, x }: same keys, different Map

let total = 0;
for (let i = 0; i < 10000; i++) {
  total += readX(sameOrder);             // Monomorphic IC: single Map check
}
total += readX(reversed);                // Polymorphic IC: two Maps recorded at `point.x`
console.log(total);                      // 10001
```

Because ICs belong to the bytecode **call site**, passing mixed shapes to one helper degrades that helper globally for every caller until polymorphism stays bounded.

## 6. Inlining, Escape Analysis, and Closure Context Allocation

Once an IC is monomorphic or narrowly polymorphic, Maglev and TurboFan optimize across function boundaries and manage captured closure memory:

- **Function inlining:** Small hot callees are copied directly into their caller, removing frame setup and exposing exact argument Maps inside the loop body.
- **Escape analysis and scalar replacement:** If an inlined helper constructs `{ dx: a.x - b.x, dy: a.y - b.y }` and only its numeric fields are read before the temporary object vanishes, TurboFan proves the object never escapes the function and keeps `dx` and `dy` in CPU registers with **zero heap allocation**.
- **Closure `Context` allocation:** Non-captured local variables live in stack slots or registers, while variables read or mutated by an inner closure are promoted to a heap-allocated **V8 `Context` object**. Crucially, **all sibling closures created in the same outer scope share one `Context`**, so if `heavyHandler` captures a 50 MB buffer while `tinyCallback` captures only a counter from the same function scope, keeping `tinyCallback` alive can pin the entire shared `Context` until the unused heavy binding is cleared or separated. See [Garbage Collection](../04-memory-and-data/10.1.4.07-garbage-collection.md) for heap-snapshot retaining-path diagnosis.

## 7. Speculative Optimization, OSR, and Deoptimization (Bailouts)

Optimizing compilers emit fast machine code guarded by assumptions from the feedback vector. When an assumption breaks, V8 triggers one of two bailout paths:

- **Eager deoptimization:** An inline guard immediately fails during execution (for instance, a string argument hits an integer-only `+`, or an unexpected Map arrives at a monomorphic property read). V8 reconstructs the interpreter frame from deopt metadata and resumes safely in Ignition.
- **Lazy deoptimization:** Code already on the call stack stays compiled until another operation invalidates a global dependency—such as altering `Object.prototype`, changing a field from Smi to string on a shared Map, or mutating a `const` module cell. V8 marks that compiled code invalid so the next return or OSR loop edge exits cleanly.

Running `node --trace-opt --trace-deopt` exposes both OSR promotion and field-representation bailouts on real code:

```javascript
// Run with: node --trace-opt --trace-deopt trace-deopt.js
function sumPrice(items) {
  let total = 0;
  for (let i = 0; i < items.length; i++) total += items[i].price;
  return total;
}

const batch = Array.from({ length: 1000 }, (_, i) => ({ id: i, price: 10 }));
let acc = 0;
for (let r = 0; r < 500; r++) acc += sumPrice(batch);
acc += sumPrice([{ id: 1, price: '10' }]); // Breaks field representation assumption (`price` Smi -> string)
console.log(acc); // 500000010
```

Observed diagnostic output in Node 26 (V8 Maglev and TurboFan):

```text
[marking <JSFunction sumPrice> for optimization to MAGLEV, reason: hot and stable]
[compiling method <JSFunction sumPrice> (target MAGLEV) OSR]
[compiling method <JSFunction sumPrice> (target TURBOFAN_JS) OSR]
[marking dependent code <Code MAGLEV> (<SharedFunctionInfo sumPrice>) for deoptimization, reason: dependent field representation changed]
[aborted optimizing <JSFunction sumPrice> (target TURBOFAN_JS) OSR because: Bailed out due to dependency change]
```

Reading that trace confirms the full cycle: `sumPrice` tiered up mid-loop via OSR first to Maglev and began compiling for TurboFan, then `{ price: '10' }` altered the shared Map's `price` representation from Smi to string (`dependent field representation changed`), triggering lazy deoptimization and aborting the concurrent TurboFan compilation.

## 8. Measuring Before Optimizing

Never rewrite clean domain code for guessed V8 internals; follow an evidence-first triage order:

1. **Profile end-to-end first:** Capture a `--cpu-prof` trace or DevTools performance timeline under realistic traffic (see [Debugging and Profiling Node.js](../../../20-backend/20.1-node.js/04-security-and-operations/20.1.4.02-debugging-profiling-nodejs.md)). Only optimize V8 shapes if synchronous JavaScript CPU time actually dominates latency.
2. **Confirm IC splits and bailouts:** Run a focused reproducer with `node --trace-opt --trace-deopt` or `--allow-natives-syntax` (`%HaveSameMap`, `%HasHoleyElements`) to verify repeated deoptimizations on hot functions.
3. **Apply low-cost structural hygiene in hot paths:** Initialize optional object keys consistently (`{ id, note: null }`), prefer dense arrays (`[]`, `Array.from`) over sparse `new Array(n)`, and keep prototype mutations (`Object.setPrototypeOf`) and dynamic scope (`eval`, `with`) out of application code.
4. **Re-benchmark under equal warmup:** Compare steady-state throughput and memory after warmup rather than trusting cold microbenchmarks.

## Summary

V8 balances fast startup against peak throughput by pairing lazy pre-parsing and Ignition bytecode interpretation with Sparkplug, Maglev, and TurboFan compilation tiers backed by OSR. Value tagging (inline Smi integers vs. boxed HeapNumbers) and 4-byte pointer compression reduce allocation overhead, while shared Maps (Hidden Classes) and Elements Kinds turn property and array lookups into direct memory offsets as long as shapes stay consistent and dense. Inline caches track observed Maps per call site, enabling inlining and escape analysis, while shared closure `Context` slots require care when sibling closures capture oversized objects. Profile end-to-end workloads first, then use `--trace-opt`, `--trace-deopt`, and native shape predicates to diagnose verified hot-path bailouts.

# V8 Execution and Optimization

A JavaScript function can run slowly on its first call, speed up after repeated calls, then slow down when the values it receives change shape. The JavaScript result must stay the same; the engine changes how it produces that result.

## Definition

V8 is Google's JavaScript and WebAssembly engine, used by Chrome and Node.js. It parses JavaScript and chooses runtime representations and execution strategies that preserve the language's observable behavior.

> **Textbook Definition:** A JavaScript engine implements the language's specified semantics and may interpret or compile code into machine instructions. V8 uses runtime feedback to optimize frequently executed code, while preserving correct behavior when optimization assumptions no longer hold.

## First Principles

JavaScript defines what a program may observe, not whether an engine uses an interpreter, bytecode, hidden classes, or machine-code tiers. A dynamic engine can begin executing before it knows the types and object layouts that later calls will use. It gathers evidence while running, then spends compilation work only where that evidence suggests a benefit.

```text
source
  -> parse and create internal representations
  -> execute while collecting feedback about values and object shapes
  -> compile selected hot code using that feedback
  -> guard assumptions; deoptimize and resume correctly if they fail
```

Ignition interprets **bytecode**, an engine instruction format generated from parsed JavaScript. Sparkplug can compile that bytecode quickly into baseline machine code; Maglev and TurboFan use runtime feedback for further optimization. V8 has also been replacing parts of TurboFan's Sea-of-Nodes representation with Turboshaft. This is an implementation model, not a guaranteed sequence for every function; tiering policy and compiler internals change between releases and workloads.

## Follow one property access

Consider a hot loop that reads `x` and `y` from many points:

```javascript
function sumCoordinates(points) {
  let total = 0;
  for (const point of points) {
    total += point.x + point.y;
  }
  return total;
}

const points = [
  { x: 2, y: 4 },
  { x: 5, y: 7 },
];
```

V8 can observe that the `point.x` access repeatedly sees compatible object layouts. V8 calls the internal layout descriptor a **Map** or hidden class; this is unrelated to JavaScript's `Map` collection. Objects built with the same properties in the same order can share a Map, letting the engine reuse field offsets and access feedback.

An **inline cache (IC)** records what a property or call site has observed. A site that repeatedly sees one shape is monomorphic; a site that sees a small number of shapes is polymorphic. The optimizing compiler can use that feedback to generate a guarded fast path. An unsupported shape may take a slower path or trigger deoptimization. When V8 deoptimizes, it reconstructs execution state and resumes through less specialized code that preserves JavaScript behavior. Correctness remains; performance may pay for the fallback or recompilation.

```javascript
const sameShape = { x: 1, y: 2 };
const anotherSameShape = { x: 3, y: 4 };
const differentConstructionOrder = { y: 6, x: 5 };
```

The final object can have a different V8 Map despite having the same property names. That may make a hot access site see more shapes, but one such object is not automatically a performance problem. Measure the actual call site and workload before changing a data model.

## Make a performance decision from evidence

Tiering has costs as well as gains. Parsing and compilation consume startup time and memory; optimized code consumes code-cache memory; assumptions and guards add work; deoptimization can interrupt a hot path. A short command-line process may finish before optimization helps, while a long-running service may benefit after warm-up. Neither result can be inferred from source syntax alone.

For a production decision:

1. Profile representative traffic, including startup and steady state. Separate JavaScript CPU from I/O, garbage collection, serialization, and host work.
2. Find a measured hot function before changing object creation or call patterns. Keep stable fields initialized consistently when that also makes the domain model clearer.
3. Compare end-to-end latency and memory after the change. A microbenchmark can overstate a tight-loop optimization that does not affect user-visible work.

V8 Maps are one engine's object-shape mechanism. They do not change prototype lookup or the language's property semantics. Garbage collection and object retention are a separate memory question; see [Garbage Collection](../04-memory-and-data/10.1.4.07-garbage-collection.md). The execution-context chapter describes specification state, not V8's physical frames or compiled code.

## Summary

V8 can interpret code, collect feedback, and compile hot paths using observed types and object shapes. Inline caches and hidden classes are V8 implementation details; speculative code guards assumptions and deoptimizes when they fail. Treat the tier names as a changing implementation model, and use profiles from the actual runtime before tuning code.

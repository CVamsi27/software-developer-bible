# V8 Execution and Optimization

A function can run slowly on its first calls, accelerate after dozens of iterations, then suddenly slow down when handed an unexpected data shape. What changes under the hood, and how does the engine make dynamic JavaScript fast?

```javascript
function calculateTotal(items) {
  let sum = 0;
  for (let i = 0; i < items.length; i++) {
    sum += items[i].price; // How does V8 read .price in nanoseconds?
  }
  return sum;
}

const cart = [{ price: 10 }, { price: 20 }, { price: 30 }];
calculateTotal(cart);
```

## Definition

**Google V8** is the open-source JavaScript and WebAssembly engine behind Chromium browsers and Node.js. Instead of pure interpretation, V8 runs a **Just-In-Time (JIT) multi-tier compilation pipeline**: source becomes bytecode and then native machine code, while runtime type feedback lets it speculatively optimize hot paths — with **deoptimization** fallbacks that preserve exact ECMAScript semantics.

> **Textbook Definition:** A JavaScript engine implements the language's specified semantics and may interpret or compile code into machine instructions. V8 uses runtime feedback to optimize frequently executed code, while preserving correct behavior when optimization assumptions no longer hold.

## First Principles

JavaScript has dynamic types, runtime object mutation, and prototype lookups — but CPUs only do fixed-offset operations on concrete types. An optimizing engine bridges that gap by predicting stability and compiling dynamic statements into direct hardware operations. Compiling everything up front would wreck startup time and waste memory on once-run code, so V8 starts with a fast interpreter, profiles hot paths, and compiles only performance-critical sections using observed types.

## How It Works

### 1. The V8 JIT Compilation Pipeline

V8 balances startup latency against steady-state throughput across tiers:

```text
                  ┌────────────────────────┐
                  │ JavaScript Source Code │
                  └───────────┬────────────┘
                              │ Parser
                              ▼
                  ┌────────────────────────┐
                  │  Abstract Syntax Tree  │
                  └───────────┬────────────┘
                              │ Bytecode Generator
                              ▼
                  ┌────────────────────────┐
                  │ Ignition (Interpreter) │ ──► Fast Startup, Memory Efficient
                  └───────────┬────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │ (warm functions)  │ (hot functions)   │ (very hot functions)
          ▼                   ▼                   ▼
┌─────────────────────────────────────────────────────────────────────┐ ┌──────────────────┐ ┌───────────────────────────┐
│ Sparkplug        │ │ Maglev           │ │ TurboFan / Turboshaft     │
│ Baseline JIT     │ │ Mid-Tier JIT     │ │ Optimizing JIT            │
│ Fast native code │ │ SSA optimization │ │ Speculative Machine Code  │
└─────────────────────────────────────────────────────────────────────┘ └──────────────────┘ └─────────────┬─────────────┘
                                                        │ Type assumption fails!
                                                        ▼
                                          ┌───────────────────────────┐
                                          │ Deoptimization (Bailout)  │
                                          │ Revert back to Ignition   │
                                          └───────────────────────────┘
```

1. **Parser and bytecode**: source becomes an AST, and **Ignition** generates compact bytecode — execution starts immediately with no compilation lag.
2. **Sparkplug (baseline compiler)**: translates Ignition bytecode straight into simple non-optimizing machine code, skipping type-feedback analysis for a quick boost.
3. **Maglev (mid-tier compiler)**: builds faster machine code using a Static Single Assignment (SSA) intermediate representation.
4. **TurboFan / Turboshaft (optimizing compiler)**: consumes collected runtime feedback to inline functions, unroll loops, and drop bounds checks in hot functions.

### 2. Hidden Classes (Maps): Transition Trees and Memory Offsets

Objects are conceptually hash maps, but a hash lookup per `point.x` would be catastrophically slow. V8 assigns each object an internal **Map** (historically **Hidden Class**) mapping property names to fixed memory offsets:

```javascript
const obj1 = { x: 1, y: 2 }; // Map #1 (properties x then y)
const obj2 = { x: 3, y: 4 }; // Shares Map #1 (offset 0: x, offset 1: y)

const obj3 = { y: 2, x: 1 }; // Map #2 (different property order creates a different Map!)
```

```text
Map 0 (Empty) ──add 'x'──► Map 1 { x @ offset 0 } ──add 'y'──► Map 2 { x @ offset 0, y @ offset 1 }
```

Adding properties walks a deterministic **transition tree**. Same properties in the same order reuse a Map, turning property reads into fixed-offset loads (`MOV RAX, [RDI + 16]`) instead of hash lookups.

### 3. Inline Caches (IC): Monomorphic, Polymorphic, and Megamorphic

An **Inline Cache (IC)** sits at each property-access site (`obj.price`) and remembers the Maps previously seen there:

1. **Monomorphic (fastest)** — one Map observed. V8 emits a single check (`if object.map === MapA`) plus a direct offset load, ~1 CPU cycle.
2. **Polymorphic (fast)** — 2–4 distinct Maps observed. V8 emits a small linear branch table over the known Maps.
3. **Megamorphic (slow)** — 5+ distinct Maps observed. V8 abandons inline branching for a generic dictionary lookup, with a noticeable slowdown.

```javascript
function getPrice(item) {
  return item.price; // IC site tracks every Map passed to this function
}

// Monomorphic: all objects share the same shape
for (let i = 0; i < 10000; i++) {
  getPrice({ price: 10 }); // Always the same Map! Blazing fast.
}
```

### 4. Speculative Optimization and Deoptimization (Bailouts)

TurboFan compiles from **speculative assumptions** in feedback vectors:

```javascript
function add(a, b) {
  return a + b;
}

// 1. Warm-up Phase: Called millions of times with integers
for (let i = 0; i < 1000000; i++) {
  add(1, 2);
}
```

Having seen only numbers, TurboFan reduces `add` to one native instruction (`ADD RAX, RBX`), skipping every dynamic check (is `a` a string? does `b` have `valueOf`?). But call `add("hello", "world")` and the hardware type-guard fires a bailout: V8 discards the optimized code, reconstructs the interpreter frame from register state, and resumes in **Ignition**. Repeated bailouts cause compiler churn and latency spikes — future calls run interpreted or recompile with polymorphic feedback.

### 5. Senior Engineering Rules: Writing JIT-Friendly Code

Modern JITs optimize idiomatic code well; these rules avoid accidental deoptimization:

- **Initialize properties in constructor order** — same field order means shared Maps across instances.
- **Never reshape objects later** — dynamic `obj.newProp = 1` or `delete obj.prop` mutates Maps and can demote objects to slow dictionary mode.
- **Keep hot call sites monomorphic** — feed homogenous structures into functions on critical loops.
- **Avoid anti-optimization constructs** — `eval()`, `with`, and sloppy `arguments` mutation block aggressive SSA register optimization.

## Summary

V8 runs JavaScript through tiered JIT compilation: Ignition bytecode for fast startup, then Sparkplug, Maglev, and TurboFan for near-native hot-path throughput. Hidden classes (Maps) replace hash lookups with fixed offsets, inline caches specialize each access site by observed shapes, and speculative compilation bails out to the interpreter when assumptions fail. Consistent object shapes and monomorphic call sites let the engine deliver hardware-level speed.

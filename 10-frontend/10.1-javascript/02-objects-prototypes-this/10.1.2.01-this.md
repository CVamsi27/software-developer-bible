# This

Why can `account.describe()` return `Alice`, while an extracted `describe()` throws in strict mode? The function did not change; the invocation stopped supplying `account` as its receiver.

## Definition

`this` is a value available inside many JavaScript functions. It often identifies the object a method is working on; that value is called the **receiver**. For an ordinary function, how you call it supplies `this`. The value does not have to be an object or the object that originally stored the function. An arrow function has no separate `this` of its own; it uses `this` from the surrounding scope.

> **Textbook Definition:** `this` is an execution-time receiver value resolved according to the function and invocation form. Ordinary calls establish a receiver binding; arrow functions obtain it from their surrounding lexical environment.

## First Principles


A shared method needs to know which receiver it is operating on. Storing one function on two objects cannot permanently associate that function with both receivers. JavaScript therefore lets a method-style call supply the receiver. Passing only the function value elsewhere removes that call-site relationship unless the programmer deliberately preserves it.

## Why does an extracted method behave differently?

```js
'use strict';
const account = {
  name: 'Alice',
  describe() { return this.name; }
};
const other = { name: 'Bob', describe: account.describe };

console.log(account.describe()); // Alice
console.log(other.describe());   // Bob: same function, different receiver
const detached = account.describe;
try {
  detached();
} catch (error) {
  console.log(error.name);       // TypeError: this is undefined
}
console.log(detached.call(account)); // Alice
```

```text
account.describe()  → call retains the property reference → this = account
other.describe()    → call retains another reference      → this = other
detached()          → plain function call                 → no receiver
```

A plain call to a strict ordinary function gets `undefined` as `this`. A non-strict ordinary function replaces `null` or `undefined` with the global object from its **realm**, the global environment that function belongs to. It also wraps primitive receivers in objects, called **boxing**. These `this` rules do not change variable lookup: ordinary names still follow lexical scope.

## How can a callback keep the intended receiver?

A callback API chooses how it invokes a function. It may use a plain call, a documented receiver, or an explicit `thisArg`; passing a method does not tell it to remember the original object.

```js
'use strict';
class Counter {
  count = 0;
  increment() { this.count += 1; return this.count; }
  callback = () => this.increment();
}
const counter = new Counter();
const bound = counter.increment.bind(counter);
const wrapped = () => counter.increment();
console.log(bound());            // 1
console.log(wrapped());          // 2
console.log(counter.callback()); // 3
console.log(bound.call({ count: 100 })); // 4: a later call cannot replace binding
```

`bind` creates a function that stores a receiver and optionally leading arguments. The wrapper instead explicitly performs a method call when invoked. The class-field arrow captures the instance's `this` during field initialization. These differ in identity and allocation, but all can preserve the intended receiver.

Keep the resulting callback when an API requires that same identity for removal. Calling `bind` again creates a different function, so it cannot remove the earlier listener.

## What is lexical about an arrow?

An object literal does not create a new `this` scope. An arrow written inside it therefore captures the surrounding `this`, not the literal object. An arrow created inside an ordinary method resolves that method's receiver.

```js
'use strict';
function makeAccount() {
  return {
    name: 'Alice',
    arrow: () => this.name,
    method() {
      const read = () => this.name;
      return read.call({ name: 'Ignored' });
    }
  };
}
const account = makeAccount.call({ name: 'Factory receiver' });
console.log(account.arrow());  // Factory receiver
console.log(account.method()); // Alice
```

At the record level, an arrow still has parameters and local bindings, but its Function Environment Record does not establish its own `this`. Resolving `this` walks outward to a record that supplies it. An ordinary block's Declarative record does not supply a new receiver, so entering `{ ... }` can change where name lookup begins without changing the method's `this`. Default-parameter setup may also separate parameter and body bindings; neither LE nor VE is a universal separate receiver storage bucket. The [Lexical Environment](../01-execution-and-scope/10.1.1.05-lexical-environment.md) chapter owns the record hierarchy and lookup traces.

`call`, `apply` and `bind` cannot replace an arrow's lexical `this`. Arrows cannot be constructors. A nested **ordinary** function does not inherit its caller's receiver merely because its source is inside the caller; a plain call still follows the ordinary call rule.

## How do call, apply and construction fit?

| Invocation | Receiver behavior |
| ----------------------------------------- | ------------------------------------------------------- |
| `object.method()` or `object['method']()` | The object from the property reference |
| `fn.call(value, a, b)` | Supplied `value`; arguments supplied separately |
| `fn.apply(value, arrayLike)` | Supplied `value`; arguments taken from array-like input |
| `fn.bind(value, a)` then invoke | Saved receiver and leading argument |
| `new Constructor(args)` | Newly created instance, with constructor-specific rules |
| Arrow invocation | Enclosing `this`; ordinary receiver rules do not apply |

A bound function whose target is constructible can still be called with `new`; construction ignores its saved `this` value but keeps its bound arguments. An ordinary constructor can return an object to replace the newly created instance. Class constructors require `new`, and derived constructors must initialize `this` through `super()` before using it. These are construction rules, not a universal precedence slogan applying to every function kind.

## The host can provide a receiver even in strict code

Top-level `this` differs by environment: a browser classic script gets the global receiver (even with a strict directive), an ES module gets `undefined`, and Node CommonJS normally gets the module's initial `exports` object.

A normal DOM listener gets the current event target as `this`. Browser timers supply the window/global receiver even to a strict callback; Node timers use their own documented implementation behavior rather than the owning application instance. Neither timer binds a callback to the object from which it was extracted. Prefer an explicit closure when the code needs that instance.

```js
function installButtonCounter(button) {
  let clicks = 0;
  function onClick(event) {
    clicks += 1;
    console.log(this === event.currentTarget); // true
    button.textContent = `Clicked ${clicks} times`;
  }
  button.addEventListener('click', onClick);
  return () => button.removeEventListener('click', onClick);
}
```

Pass an actual button element. The function retains the exact listener for cleanup. An arrow listener could use `event.currentTarget` or the captured `button` explicitly, without relying on a host-supplied `this`. For delegated events, `event.target` may be a nested descendant; it is not interchangeable with the container/current target.

## What changes in classes and TypeScript?

Prototype methods are shared across instances; arrow fields and bound methods usually allocate per instance. That is an allocation distinction, not a promise that all arrow and method calls have identical measured cost. A chainable method returns its receiver (`return this`) so the next call can continue operating on it.

React function components do not have a component-instance `this`. In legacy class components, an event callback must retain the instance through a bound method or class-field arrow; the event system does not infer ownership from where the method was declared. Use functional state updates when the next value depends on the previous one.

TypeScript can declare the receiver requirement without creating a runtime argument:

```ts
function greet(this: { name: string }, greeting: string): string {
  return `${greeting}, ${this.name}`;
}
console.log(greet.call({ name: 'Alice' }, 'Hello')); // Hello, Alice
```

The `this` parameter is erased. Runtime callers still need a correct receiver. For decorators or debounce wrappers that must preserve a call's receiver and arguments, retain them and call the original with `apply`; see the canonical [Debounce](../04-memory-and-data/10.1.4.04-debounce.md) implementation rather than duplicating its scheduling here.

## Summary

Start at the invocation: was a property reference retained, an explicit receiver supplied, a bound function used, or a constructor called? For an arrow, follow the enclosing `this` instead. Callback APIs and host environments add their own invocation contracts; a function's storage location alone does not supply its receiver.

# Proxy & Reflect

## Definition

A `Proxy` is a distinct object that intercepts selected internal operations on a target through handler functions called **traps**. `Reflect` exposes operations such as get, set and construction as callable functions, so a trap can deliberately forward an operation. Interception applies to callers using the proxy; code retaining the raw target can bypass it.

## First Principles

An object may need behavior around an operation rather than inside a named method: validate an assignment, track a read, or log a call. Getters/setters already intercept selected property access; proxies extend interception across the object's internal operations. Forwarding must preserve the original operation's receiver and failure rules, while engine invariants prevent a wrapper from contradicting protected target properties.

## How does an intercepted assignment reach the target?

```text
proxy.age = 31
    → handler.set(target, 'age', 31, proxy)
    → validate the input
    → Reflect.set(target, 'age', 31, proxy)
    → boolean success result
```

The `receiver` matters for inherited accessors: their `this` should ordinarily be the object through which the operation was requested. `target[property]` can supply a different receiver; `Reflect.get/set` lets the trap preserve it.

```js
'use strict';
const target = { name: 'Alice', age: 30 };
const user = new Proxy(target, {
  get(object, key, receiver) {
    console.log('get', String(key));
    return Reflect.get(object, key, receiver);
  },
  set(object, key, value, receiver) {
    if (key === 'age' && (!Number.isInteger(value) || value < 0 || value > 150)) {
      throw new TypeError('age must be an integer from 0 to 150');
    }
    return Reflect.set(object, key, value, receiver);
  }
});
console.log(user.age = 31); // 31: assignment evaluates to its right-hand side
console.log(user.age);     // logs get age, then 31
try { user.age = -1; } catch (error) { console.log(error.name); } // TypeError
console.log(target.age);   // 31: successful forwarding changed the target
```

The set trap's result reports **success**, not the assignment's value. A falsy result makes strict-mode assignment throw. Returning true can still violate an invariant, for example claiming a new value for a non-configurable, non-writable own data property.

This example validates ordinary `age` assignments through this wrapper. It is not complete input validation: initial data, direct target writes, `defineProperty`, deletion and nested values have different paths. Validate external payloads at their boundary with a runtime schema.

## Which operations can be intercepted?

| Operations | Traps | Role inside the object model |
| --------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------- |
| Read/write/delete/test a property | `get`, `set`, `deleteProperty`, `has` | Property access and `in` |
| Inspect keys/descriptors or define a property | `ownKeys`, `getOwnPropertyDescriptor`, `defineProperty` | Reflection and enumeration; Object.keys also filters descriptors |
| Read/change the prototype | `getPrototypeOf`, `setPrototypeOf` | Prototype relationships |
| Inspect/prevent extensibility | `isExtensible`, `preventExtensions` | Whether new own properties are allowed |
| Call a function | `apply` | Target must be callable |
| Construct an instance | `construct` | Target must be constructible; an arrow target is not |

Omitted traps forward to the target's corresponding internal operation. `Reflect.ownKeys` includes symbols and non-enumerable keys, unlike `Object.keys`; forwarding is not a reason to treat the APIs as interchangeable.

## How can tracking reads support reactivity?

A reactive system connects **a specific object's property** to computations that read it. A get trap records that dependency during an effect; a successful set schedules or runs the affected computations. Production systems additionally handle nested structures, collections, batching and lifecycle rules.

This complete synchronous example intentionally supports plain top-level properties and one currently executing effect. It retracks changing dependencies and returns a disposer; it is not a replacement for Vue's full reactive runtime.

```js
function createReactiveRuntime() {
  const dependencies = new WeakMap();
  let active = null;

  function bucket(target, key) {
    let keys = dependencies.get(target);
    if (!keys) { keys = new Map(); dependencies.set(target, keys); }
    let readers = keys.get(key);
    if (!readers) { readers = new Set(); keys.set(key, readers); }
    return readers;
  }
  function reactive(target) {
    return new Proxy(target, {
      get(object, key, receiver) {
        if (active) {
          const readers = bucket(object, key);
          readers.add(active);
          active.groups.add(readers);
        }
        return Reflect.get(object, key, receiver);
      },
      set(object, key, value, receiver) {
        const previous = Reflect.get(object, key, receiver);
        const success = Reflect.set(object, key, value, receiver);
        if (success && !Object.is(previous, Reflect.get(object, key, receiver))) {
          for (const reader of [...bucket(object, key)]) reader.run();
        }
        return success;
      }
    });
  }
  function effect(fn) {
    const reader = {
      groups: new Set(), stopped: false, running: false,
      clear() {
        for (const group of this.groups) group.delete(this);
        this.groups.clear();
      },
      run() {
        if (this.stopped || this.running) return;
        this.clear();
        const previous = active;
        active = this;
        this.running = true;
        try { fn(); }
        finally { active = previous; this.running = false; }
      }
    };
    try { reader.run(); }
    catch (error) { reader.stopped = true; reader.clear(); throw error; }
    return () => { reader.stopped = true; reader.clear(); };
  }
  return { reactive, effect };
}

const runtime = createReactiveRuntime();
const state = runtime.reactive({ count: 0, enabled: true });
const stop = runtime.effect(() => console.log(state.enabled ? state.count : 'off'));
state.count = 1;       // 1 (initial run previously printed 0)
state.enabled = false; // off; count is no longer a dependency
state.count = 2;       // no output
stop();
state.enabled = true; // no output: subscription disposed
```

Effects must be pure readers in this small model: it suppresses self-reentrant execution rather than resolving effect cycles. The example does not intercept deletion/definition, deeply proxy nested objects, or batch asynchronous jobs. Those limitations explain why copying a tiny get/set demo is not equivalent to adopting a framework. [Vue's mechanism](https://vuejs.org/guide/extras/reactivity-in-depth.html).

## What does revocation actually stop?

```js
const target = { message: 'hello' };
const { proxy, revoke } = Proxy.revocable(target, {});
console.log(proxy.message); // hello
revoke();
try { console.log(proxy.message); }
catch (error) { console.log(error.name); } // TypeError
console.log(target.message); // hello: raw target remains usable
```

After revocation, trapped internal operations throw; it does not destroy the target or recursively revoke values previously handed out. Proxy identity remains observable (`proxy !== target`), and identity comparison is not a trapped property read. Revocation is a lifecycle tool, not an unrestricted security sandbox.

## Where do wrappers change the contract?

- **Read-only views:** rejecting set/delete/defineProperty can restrict those operations through the proxy. Nested objects, the raw target, prototype changes and mutable internal slots need separate treatment; `Readonly<T>` is only a static type.
- **Defaults:** a get trap can provide missing values, but `in`, ownKeys and serialization may still report the original shape. Declare the resulting type honestly; do not return extra properties while pretending a generic input type has not changed.
- **Negative array indices:** translating `'-1'` to `length - 1` can change reads. Writes, membership and enumeration remain ordinary unless explicitly handled. Native `array.at(-1)` often avoids that custom contract.
- **Logging:** wrapping a method on every get changes its identity. A wrapper must preserve its intended receiver and treat thrown errors, async rejection, sensitive arguments and logging failure deliberately.
- **Metrics:** a synchronous `finally` around a method measures time until it returns a promise, not until asynchronous work finishes. Awaiting completion changes the wrapper's return shape unless the API is already asynchronous; use a contract-specific wrapper.

Private class fields and built-ins such as Map rely on internal identity/slots. A no-op proxy is not automatically a transparent receiver for all their methods. Binding methods to the target can solve some brand checks but changes receiver/interception behavior; test the actual contract rather than binding every function indiscriminately.

## Summary

Identify which internal operation is intercepted, preserve its receiver and return contract when forwarding, and respect target invariants. A proxy is a separate identity and a partial boundary: raw access, nested values, native slots and lifecycle still need explicit design. Measure its workload without assuming a fixed slowdown multiplier.

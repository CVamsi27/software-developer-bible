# Event Loop

A page can freeze inside a loop that awaits an already-fulfilled promise. The developer believes each iteration yields to the browser — but `await Promise.resolve()` only queues microtasks, which run before timers, input, and rendering ever get a turn.

```javascript
console.log('script');

setTimeout(() => console.log('timer'), 0);
Promise.resolve().then(() => console.log('microtask'));

console.log('end');
// script → end → microtask → timer
```

## Definition

The **event loop** orchestrates synchronous execution, task queues, microtask checkpoints, and rendering inside a JavaScript host. Each agent runs one main thread, so timers, I/O, and events are processed as queued turns — never by preempting running code.

> **Textbook Definition:** An event loop coordinates runnable tasks and microtask checkpoints for a JavaScript host environment. A browser event loop additionally coordinates rendering opportunities across browsing contexts; task selection and rendering schedules follow host-specific dispatch policies rather than a single global first-in, first-out queue.

## First Principles

A JavaScript agent owns one call stack and runs each task to completion with no preemption (**run-to-completion**). External events — timers, socket packets, clicks, IPC messages — therefore arrive as discrete **macrotasks** in host-managed queues. Whenever the stack empties, the engine runs a **microtask checkpoint** that drains every queued microtask (including ones enqueued mid-drain) before yielding. Browser paint happens between macrotasks, only once microtasks are gone and the frame deadline permits.

## How It Works

### 1. One Turn of the Loop

```text
┌────────────────────────────────────────────────────────┐
│ 1. Dequeue Oldest Task from Target Task Queue          │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. Execute Task on Call Stack until Empty              │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 3. PerformMicrotaskCheckpoint() (Drain all microtasks) │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 4. Rendering Opportunity? (Evaluate rAF, Style, Paint) │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 5. Idle Period (Evaluate requestIdleCallback)          │
└────────────────────────────────────────────────────────┘
```

### 2. Queue Layers and Drain Rules

| Execution Layer | Queue Mechanism | Examples | Scheduling Timing | Drain Behavior |
| :-------------- | :----------------------- | :-------------------------------------------------------------------------- | :------------------------------------------------ | :--------------------------------------- |
| **Call Stack** | LIFO Execution Frames | Synchronous code, function calls | Immediate | Runs current frame to completion |
| **Microtasks** | FIFO Dedicated Queue | `Promise` reactions, `queueMicrotask`, `MutationObserver` | Immediately when call stack reaches zero | Drains *completely* until queue is empty |
| **Macrotasks** | Multiple Priority Queues | `setTimeout`, `setInterval`, `setImmediate` (Node), DOM events, Network I/O | Chosen by host scheduler per turn | Executes exactly *one* task per turn |
| **Rendering** | Compositor Pipeline | `requestAnimationFrame`, CSS styles, Layout, Paint | Synchronized with display VSync (e.g. 60Hz/120Hz) | Evaluates rAF callbacks, then paints |

The WHATWG spec mandates *multiple* task queues (user interaction, timer, network, rendering) — not one FIFO. Hosts may prioritize the interaction queue over background timers to keep input responsive.

### 3. Ordering in Practice

```javascript
console.log('1: Synchronous script start');

setTimeout(() => {
  console.log('6: Timer macrotask executed');
}, 0);

Promise.resolve().then(() => {
  console.log('3: Microtask 1 executed');
  queueMicrotask(() => {
    console.log('5: Nested microtask executed');
  });
}).then(() => {
  console.log('4: Microtask 2 executed');
});

queueMicrotask(() => {
  console.log('2: Microtask 3 executed');
});

console.log('Synchronous script end');

// Output Sequence:
// 1: Synchronous script start
// Synchronous script end
// 3: Microtask 1 executed
// 2: Microtask 3 executed
// 4: Microtask 2 executed
// 5: Nested microtask executed
// 6: Timer macrotask executed
```

Sync code runs first, scheduling one timer and three microtasks. When the script task ends, `PerformMicrotaskCheckpoint()` runs Microtask 1 and Microtask 3; Microtask 1 attaches Microtask 2 and nests Microtask 5. Everything drains before the timer macrotask gets its turn.

### 4. Microtask Starvation and the False-Yield Trap

`await` on a fulfilled promise schedules a promise-reaction microtask — not a host yield. This loop freezes the tab for its whole run:

```javascript
// Antipattern: Starves rendering and user interactions
async function processLargeBatch(items) {
  for (let i = 0; i < items.length; i++) {
    computeHeavyItem(items[i]);
    // The developer assumes this yields to the browser:
    await Promise.resolve(); // DANGEROUS: Schedules a microtask!
  }
}
```

Each `await` empties the stack straight into another microtask checkpoint, so no render step or click handler runs until the queue is fully empty. A 500ms loop means a 500ms frozen tab.

### 5. Cooperative Yielding and Same-Turn Coalescing

At 60fps the frame budget is 16.6ms, so heavy work must yield at a **macrotask** boundary — via `scheduler.yield()` or a `setTimeout` fallback:

```javascript
// True event-loop yielding utility
function yieldToHost() {
  // Modern browsers support scheduler.yield()
  if (globalThis.scheduler?.yield) {
    return globalThis.scheduler.yield();
  }
  // Fallback: Post a macrotask via setTimeout
  return new Promise((resolve) => {
    setTimeout(resolve, 0);
  });
}

async function processInChunks(items, processItem, chunkSize = 100) {
  if (!Number.isInteger(chunkSize) || chunkSize <= 0) {
    throw new RangeError('chunkSize must be a positive integer');
  }

  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);

    // Yield at chunk boundary to allow layout, paint, and clicks
    if ((i + 1) % chunkSize === 0 && i + 1 < items.length) {
      await yieldToHost();
    }
  }
}
```

Conversely, microtasks are ideal for **same-turn coalescing** — batching synchronous calls into one flush before rendering:

```javascript
function createCoalescedBatcher(flush) {
  let queued = false;
  let batch = [];

  return function enqueue(item) {
    batch.push(item);
    if (queued) return;
    queued = true;

    queueMicrotask(() => {
      const pendingItems = batch;
      batch = [];
      queued = false;
      flush(pendingItems);
    });
  };
}
```

### 6. Frame Pipeline, rAF, and Timer Clamping

Frames follow a VSync-driven schedule:

```text
Macrotask ──▶ Microtasks ──▶ [ rAF Callbacks ──▶ Recalculate Styles ──▶ Layout ──▶ Paint ] ──▶ Next Macrotask
```

- **`requestAnimationFrame(callback)`** runs just before style recalculation — the only safe place to measure and mutate layout without forced synchronous layouts (layout thrash).
- **`requestIdleCallback(callback)`** runs in leftover time before the next VSync deadline.
- **Timer clamping**: `setTimeout(fn, 0)` is never 0ms. After 5 nested timer calls, the HTML standard forces a 4ms minimum.

### 7. Host Differences: Dispatch Timing and Node's libuv

**Synchronous vs. async dispatch** changes microtask timing. With two click listeners that each queue a microtask, a real user click interleaves (`Listener 1 → Microtask 1 → Listener 2 → Microtask 2`) because the stack empties between dispatched listeners. A synthetic `button.click()` keeps the stack non-empty across both listeners, so both microtasks drain together (`Listener 1 → Listener 2 → Microtask 1 → Microtask 2`).

**Node.js (libuv)** replaces the browser pipeline with phases, each followed by a microtask checkpoint:

```text
Browser Event Loop:
[Task Queue Selection] ──▶ [Run Task] ──▶ [Drain Microtasks] ──▶ [Render Steps (VSync)]

Node.js (libuv) Event Loop:
┌──▶ Timers (setTimeout, setInterval)
│    │  Microtask Checkpoint (process.nextTick, Promise reactions)
├──▶ Pending Callbacks (I/O callbacks deferred to the next loop iteration)
│    │  Microtask Checkpoint
├──▶ Idle, Prepare (Internal libuv phases)
├──▶ Poll (Retrieve new I/O events; block when appropriate)
│    │  Microtask Checkpoint
├──▶ Check (setImmediate callbacks)
│    │  Microtask Checkpoint
└──▶ Close Callbacks (socket.on('close'))
        Microtask Checkpoint
```

- **`process.nextTick`** runs immediately after the current operation, before standard promise microtasks.
- **`setImmediate`** runs in the Check phase, after I/O polling completes.

## Summary

The event loop preserves run-to-completion while coordinating async I/O and paint. Macrotasks run one per turn from prioritized host queues; microtasks drain to exhaustion whenever the stack empties. Chained microtasks starve rendering and input — partition heavy work into chunks that yield at macrotask boundaries, and reserve microtasks for same-turn coalescing.

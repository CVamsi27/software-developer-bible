# Event Loop

## Definition

An **event loop** is how the surrounding runtime schedules work for JavaScript. It chooses work to run and reaches checkpoints where it processes **microtasks**, including queued promise callbacks. Browser event loops also coordinate opportunities to update the screen. Node.js uses its own phases and scheduling rules. The event loop is therefore not the same two queues in every runtime.

> **Textbook Definition:** An event loop is a coordination mechanism that schedules and dispatches tasks, microtasks, user interactions, and rendering passes across an agent execution context (WHATWG HTML Living Standard §8.1.6). In each spin, it executes the oldest eligible task from a task queue, drains the microtask queue to completion at the microtask checkpoint (ECMA-262 Job Queues), and executes document lifecycle rendering steps.

## First Principles


1. A **JavaScript agent** runs a sequence of JavaScript work with its own execution resources. It runs one evaluation at a time. A timer or completed input/output operation must wait for an opportunity to run its callback.
2. Code scheduled through a promise runs after the current synchronous code reaches a **microtask checkpoint**, when the runtime processes queued promise callbacks. It does not interrupt that code at an arbitrary line.
3. To remain responsive, the runtime needs opportunities to handle other work. Each callback must finish within a reasonable budget. Microtasks can keep adding more microtasks and delay later tasks or rendering.

## Trace One Browser Task

Run this in an ordinary browser script:

```javascript
console.log('A');
setTimeout(() => console.log('timer'), 0);
Promise.resolve().then(() => {
  console.log('promise');
  queueMicrotask(() => console.log('nested microtask'));
});
queueMicrotask(() => console.log('microtask'));
console.log('B');
// A → B → promise → microtask → nested microtask → timer
```

1. Synchronous evaluation prints `A`, schedules the timer and queues the promise reaction and microtask, then prints `B`.
2. At the microtask checkpoint, the promise reaction prints `promise` and appends another microtask.
3. The already queued `microtask` runs before the newly appended `nested microtask`.
4. The checkpoint drains before the eligible timer task runs.

```text
current task:       A, schedule work, B
microtask queue:    promise → microtask → nested microtask
later timer task:   timer
render opportunity: chosen by the browser; not a guaranteed step after each task
```

There are multiple task sources, not one globally FIFO “macrotask queue.” Ordering within a source and host selection rules matter. The diagram describes this snippet's dependencies; it does not establish an ordering between arbitrary network, input and timer callbacks.

## A Timer Delay Is an Eligibility Threshold

`setTimeout(callback, 0)` cannot interrupt the current task. Its callback waits for timer eligibility and host scheduling, including any applicable clamping or background throttling. A delay is not an appointment at an exact wall-clock instant.

A promise executor runs synchronously when `new Promise(executor)` is evaluated. A `.then` reaction runs later after settlement; registering `.then` does not synchronously invoke it. `await` on a fulfilled promise also suspends and resumes through promise scheduling. Follow that distinction in the [Promises](10.1.3.02-promises.md) and [Async/Await](10.1.3.03-async-await.md) chapters.

## Microtasks Do Not Yield to Paint

```javascript
async function misleadingYield() {
  for (let i = 0; i < 1000; i++) {
    // CPU work here still runs on this agent.
    await Promise.resolve();
  }
}
```

The loop keeps scheduling more promise callbacks while the browser processes microtasks. If a microtask continually queues another, timers, input and rendering may have to wait. `queueMicrotask` is useful for **same-turn coalescing**, combining several calls made before that microtask runs. It does not give the browser a frame between expensive chunks.

Use a host task boundary for cooperative CPU work:

```javascript
async function yieldToHost() {
  if (globalThis.scheduler?.yield) {
    await globalThis.scheduler.yield();
  } else {
    await new Promise(resolve => setTimeout(resolve, 0));
  }
}
async function processInChunks(items, processItem, chunkSize = 100) {
  if (!Number.isInteger(chunkSize) || chunkSize <= 0) throw new RangeError('chunkSize');
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);
    if ((i + 1) % chunkSize === 0 && i + 1 < items.length) await yieldToHost();
  }
}
```

Each chunk must itself be bounded. A single expensive item still blocks; size or time-budget chunks using measurements. Yielding creates an opportunity for other work, not a guaranteed paint or deadline. Workers can move suitable computation off the main thread, with transfer, coordination and rendering costs still present.

## Same-Turn Coalescing Is a Different Tool

```javascript
function coalesceMicrotask(fn) {
  let pending = false;
  let latest;
  return (...args) => {
    latest = args;
    if (pending) return;
    pending = true;
    queueMicrotask(() => {
      const argsToUse = latest;
      pending = false; // reset before calling user code, including if it throws
      fn(...argsToUse);
    });
  };
}
```

This combines calls made before its queued microtask executes and uses the latest arguments. It does not wait for a typing pause or debounce across later input tasks. Use the canonical [Debounce](../04-memory-and-data/10.1.4.04-debounce.md) contract for that behavior. Exceptions from `queueMicrotask` callbacks are reported as callback errors; a throwing promise reaction instead rejects its returned promise.

## Rendering and Animation

`requestAnimationFrame` schedules a callback in an appropriate rendering update before painting that frame. It is not another ordinary timer and does not guarantee a fixed frame rate. A zero-delay timer and the next rendering opportunity do not have one universal relative order. Hidden documents and browser scheduling can defer callbacks.

Use rAF for bounded visual updates, timers/tasks for scheduled nonvisual work, and CSS/WAAPI where the browser can own suitable animation. Avoid claiming every `await` or every empty stack triggers paint. MutationObserver notifications use microtask delivery; replacing an entire page's `innerHTML` is unnecessary to demonstrate that and can destroy application state.

## Node.js Has a Different Host Loop

Node adds `process.nextTick`, promise microtasks and libuv phases. In common CommonJS callback boundaries, next-tick processing precedes promise microtasks, but ES-module evaluation and callbacks already inside microtask processing require more precise reasoning. Do not infer all ordering from a browser snippet or the slogan “nextTick always wins.” Use the [Node.js event-loop chapter](../../../20-backend/20.1-node.js/01-runtime-and-async/20.1.1.01-event-loop.md) for its explicit contexts.

## Measure the Work That Blocks

Use a performance trace to locate long main-thread tasks, layout/paint costs and queued input. `performance.now()` around a synchronous function measures elapsed time for that call, not total async completion. Counting rAF callbacks estimates callback cadence, not guaranteed displayed frames or GPU throughput.

Calling a job “high priority” in your own queue does not change a fetch request's browser priority or make it finish before unrelated timers. A useful application scheduler limits how much work enters the queue, schedules one callback to drain it, stops after a work budget and yields through a host task boundary. Draining the queue recursively through microtasks can prevent input and rendering from progressing.

## Summary

Trace synchronous work, when each continuation becomes eligible and the checkpoint that processes it. Microtasks drain before later task selection and can starve it. Use bounded task-level yielding for responsiveness, treat rendering as a host opportunity, and apply the scheduling rules of the actual browser or Node context.

# Event Loop

A page can freeze inside a loop that awaits an already-fulfilled promise. The developer believes each iteration yields to the browser — but `await Promise.resolve()` only queues microtasks, which run before timers, input, and rendering ever get a turn.

```javascript
console.log('script');

setTimeout(() => console.log('timer'), 0);
Promise.resolve().then(() => console.log('microtask'));

console.log('end');
// script → end → microtask → timer
```

## Definition

The **event loop** orchestrates synchronous execution, task queues, microtask checkpoints, and rendering inside a JavaScript host. Within one agent, ordinary JavaScript jobs run to completion. The host schedules timers, I/O and events around that work; other agents and eligible compositor work can progress independently.

> **Textbook Definition:** An event loop coordinates runnable tasks and microtask checkpoints for a JavaScript host environment. A browser event loop additionally coordinates rendering opportunities across browsing contexts; task selection and rendering schedules follow host-specific dispatch policies rather than a single global first-in, first-out queue.

## First Principles

A JavaScript agent owns one call stack and runs ordinary JavaScript jobs to completion without another ordinary job preempting them (**run-to-completion**). Hosts arrange timer, network, input and message callbacks as scheduled work. Browser task callbacks are often called **macrotasks**, while promise jobs use the microtask machinery. The host performs a **microtask checkpoint** at specified boundaries, including after a task and after applicable callback cleanup when no JavaScript evaluation remains. It drains newly queued microtasks too. An empty stack alone is not an independent instruction to paint: rendering has its own eligible update steps and can be skipped.

## 1. One Turn of the Loop

```text
Select runnable task from a host-chosen queue
  → Run its JavaScript
  → Perform microtask checkpoint (drain newly queued work too)
  → Run eligible rendering update, if any
  → Use an eligible idle period, if any
```

## 2. Queue Layers and Drain Rules

| Execution Layer | Queue Mechanism | Examples | Scheduling Timing | Drain Behavior |
| :-------------- | :----------------------- | :-------------------------------------------------------------------------- | :------------------------------------------------ | :-------------------------------------------------- |
| **Call Stack** | LIFO Execution Frames | Synchronous code, function calls | Immediate | Runs current frame to completion |
| **Microtasks** | FIFO Dedicated Queue | `Promise` reactions, `queueMicrotask`, `MutationObserver` | At host-defined microtask checkpoints | Drains *completely* until queue is empty |
| **Macrotasks** | Host task queues | `setTimeout`, `setInterval`, `setImmediate` (Node), DOM events, Network I/O | Chosen by host scheduler per turn | Executes exactly *one* task per turn |
| **Rendering** | Rendering update | `requestAnimationFrame`, CSS styles, Layout, Paint | Synchronized with display VSync (e.g. 60Hz/120Hz) | Runs eligible update steps; paint is not guaranteed |

The HTML standard permits one or more task queues and associates each task source with a queue; it does not require one global FIFO or a separate queue for every source. The host selects a runnable queue under its scheduling policy, which can prioritize user interaction. Rendering follows the event loop's update-rendering steps rather than being guaranteed after every task.

## 3. Ordering in Practice

```javascript
console.log('1: Synchronous script start');

setTimeout(() => {
  console.log('6: Timer macrotask executed');
}, 0);

Promise.resolve().then(() => {
  console.log('3: Microtask 1 executed');
  queueMicrotask(() => {
    console.log('5: Nested microtask executed');
  });
}).then(() => {
  console.log('4: Microtask 2 executed');
});

queueMicrotask(() => {
  console.log('2: Microtask 3 executed');
});

console.log('Synchronous script end');

// Output Sequence:
// 1: Synchronous script start
// Synchronous script end
// 3: Microtask 1 executed
// 2: Microtask 3 executed
// 5: Nested microtask executed
// 4: Microtask 2 executed
// 6: Timer macrotask executed
```

Sync code schedules a timer and two initial microtasks: the first promise reaction and the explicit `queueMicrotask`. During the first reaction, the nested microtask is enqueued. Returning then fulfills the intermediate promise, queuing the chained reaction behind that nested microtask. The checkpoint drains all four before the timer runs.

## 4. Microtask Starvation and the False-Yield Trap

`await` on a fulfilled promise schedules a promise-reaction microtask — not a host yield. This loop freezes the tab for its whole run:

```javascript
// Antipattern: Starves rendering and user interactions
async function processLargeBatch(items) {
  for (let i = 0; i < items.length; i++) {
    computeHeavyItem(items[i]);
    // The developer assumes this yields to the browser:
    await Promise.resolve(); // DANGEROUS: Schedules a microtask!
  }
}
```

Each resumption queues the next continuation before the checkpoint can finish. Task-based input callbacks and the browser's main-thread rendering update wait until this chain ends. The duration depends on the work; the point is the missing task boundary, not a guaranteed delay.

## 5. Cooperative Yielding and Same-Turn Coalescing

At 60 Hz a display interval is about 16.7 ms, shared with the browser's other work. Partition long work and return control to the host — via `scheduler.yield()` where supported or a timer fallback. Neither guarantees an immediate paint or a particular frame rate:

```javascript
// True event-loop yielding utility
function yieldToHost() {
  // Feature-detect scheduler.yield() in the target browsers
  if (globalThis.scheduler?.yield) {
    return globalThis.scheduler.yield();
  }
  // Fallback: Post a macrotask via setTimeout
  return new Promise((resolve) => {
    setTimeout(resolve, 0);
  });
}

async function processInChunks(items, processItem, chunkSize = 100) {
  if (!Number.isInteger(chunkSize) || chunkSize <= 0) {
    throw new RangeError('chunkSize must be a positive integer');
  }

  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);

    // Offer the host an opportunity to schedule other work
    if ((i + 1) % chunkSize === 0 && i + 1 < items.length) {
      await yieldToHost();
    }
  }
}
```

Conversely, microtasks are ideal for **same-turn coalescing** — batching synchronous calls into one flush before rendering:

```javascript
function createCoalescedBatcher(flush) {
  let queued = false;
  let batch = [];

  return function enqueue(item) {
    batch.push(item);
    if (queued) return;
    queued = true;

    queueMicrotask(() => {
      const pendingItems = batch;
      batch = [];
      queued = false;
      flush(pendingItems);
    });
  };
}
```

## 6. Frame Pipeline, rAF, and Timer Clamping

A simplified eligible main-thread rendering update looks like this; it is not a promise of a paint after every task:

```text
Macrotask ──▶ Microtasks ──▶ [ rAF Callbacks ──▶ Recalculate Styles ──▶ Layout ──▶ Paint ] ──▶ Next Macrotask
```

- **`requestAnimationFrame(callback)`** coordinates visual work with an eligible rendering update. It does not prevent forced layout: changing a size and then reading `offsetHeight` can force layout even inside the callback. Batch required reads before writes and inspect a performance trace.
- **`requestIdleCallback(callback)`** requests low-priority work during a host-chosen idle period. It can be delayed; respect the supplied time budget and feature-detect support.
- **Timer clamping**: `setTimeout(fn, 0)` schedules a later task, not an immediate call or an exact deadline. HTML applies a 4 ms minimum when the timer nesting level is greater than five; background throttling and a busy host can delay it further.

## 7. Host Differences: Dispatch Timing and Node's libuv

**Synchronous vs. async dispatch** changes microtask timing. With two click listeners that each queue a microtask, a real user click interleaves (`Listener 1 → Microtask 1 → Listener 2 → Microtask 2`) because the stack empties between dispatched listeners. A synthetic `button.click()` keeps the stack non-empty across both listeners, so both microtasks drain together (`Listener 1 → Listener 2 → Microtask 1 → Microtask 2`).

**Node.js (libuv)** uses host phases rather than browser rendering. This is a logical overview, not a timer-order guarantee across all Node releases:

```text
Browser: selected task → microtask checkpoint → eligible rendering work
Node:    host callback → applicable next-tick / promise-job processing
         libuv phases schedule timers, polling, immediate and close callbacks
```

The [Node.js event-loop chapter](../../../20-backend/20.1-node.js/01-runtime-and-async/20.1.1.01-event-loop.md) owns the full phase trace.

Since libuv 1.45.0 (Node.js 20), timers are processed after poll rather than both before and after it; this changes some timer/`setImmediate` interactions. At ordinary callback boundaries, Node processes next-tick work before promise jobs. ES module evaluation and code already running inside a microtask have different ordering: nextTick does not preempt the current microtask checkpoint.

- **`process.nextTick`** uses a Node-specific queue, separate from promise jobs; recursively filling it can starve I/O.
- **`setImmediate`** runs in the Check phase, after I/O polling completes.

## Summary

The event loop preserves run-to-completion while coordinating async I/O and paint. Tasks are selected under host queue policies; microtasks drain to exhaustion at host-defined checkpoints. Chained microtasks starve rendering and input — partition heavy work into chunks that yield at macrotask boundaries, and reserve microtasks for same-turn coalescing.

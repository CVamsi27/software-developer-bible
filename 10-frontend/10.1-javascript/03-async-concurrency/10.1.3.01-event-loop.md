# Event Loop

A web page can freeze entirely while executing a loop that awaits an already-fulfilled promise. Even though the developer believes they are yielding control back to the browser on every iteration, `await Promise.resolve()` merely queues microtasks that execute before timers, user input, or rendering ever get an opportunity to run.

## Definition

The **event loop** is the orchestration mechanism that coordinates synchronous script execution, incoming task queues, microtask checkpoints, and rendering pipelines within a JavaScript host environment. Because JavaScript agents operate on a single main thread of execution, asynchronous I/O, timers, and events are processed through an event loop cycle rather than concurrent thread interruption.

> **Textbook Definition:** An event loop coordinates runnable tasks and microtask checkpoints for a JavaScript host environment. A browser event loop additionally coordinates rendering opportunities across browsing contexts; task selection and rendering schedules follow host-specific dispatch policies rather than a single global first-in, first-out queue.

## First Principles

1. **Single-Threaded Execution Agent:** A JavaScript execution agent owns a single call stack and memory heap. It evaluates one execution context at a time to completion ("run-to-completion" invariant) without preemptive context switching.
2. **Macrotask Ingress:** External events—such as hardware timers, network socket packets, user mouse clicks, and IPC messages—are enqueued into host-managed task queues as discrete macrotasks.
3. **Microtask Checkpoint Gate:** Whenever the call stack clears down to zero, the engine executes a microtask checkpoint, aggressively draining all queued microtasks (including those spawned during the drain) before relinquishing control.
4. **Cooperative Screen Updates:** In browser environments, style recalculation, layout, and visual painting occur between macrotasks, provided the microtask queue has fully drained and the display refresh deadline permits.

```text
┌────────────────────────────────────────────────────────┐
│ 1. Dequeue Oldest Task from Target Task Queue          │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. Execute Task on Call Stack until Empty              │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 3. PerformMicrotaskCheckpoint() (Drain all microtasks) │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 4. Rendering Opportunity? (Evaluate rAF, Style, Paint) │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 5. Idle Period (Evaluate requestIdleCallback)          │
└────────────────────────────────────────────────────────┘
```

## Macrotasks vs. Microtasks vs. Rendering

Host environments manage distinct queues with fundamentally different prioritization rules and lifecycle guarantees:

| Execution Layer | Queue Mechanism | Examples | Scheduling Timing | Drain Behavior |
| :-------------- | :----------------------- | :-------------------------------------------------------------------------- | :------------------------------------------------ | :--------------------------------------- |
| **Call Stack** | LIFO Execution Frames | Synchronous code, function calls | Immediate | Runs current frame to completion |
| **Microtasks** | FIFO Dedicated Queue | `Promise` reactions, `queueMicrotask`, `MutationObserver` | Immediately when call stack reaches zero | Drains *completely* until queue is empty |
| **Macrotasks** | Multiple Priority Queues | `setTimeout`, `setInterval`, `setImmediate` (Node), DOM events, Network I/O | Chosen by host scheduler per turn | Executes exactly *one* task per turn |
| **Rendering** | Compositor Pipeline | `requestAnimationFrame`, CSS styles, Layout, Paint | Synchronized with display VSync (e.g. 60Hz/120Hz) | Evaluates rAF callbacks, then paints |

### The Multiple Task Queue Architecture

The WHATWG specification explicitly dictates that a browser event loop has *multiple* task queues (e.g., user interaction, timer, network, rendering), not a single monolithic queue. A browser host may prioritize the user-interaction queue over background timer tasks to guarantee responsive user input.

```javascript
console.log('1: Synchronous script start');

setTimeout(() => {
  console.log('6: Timer macrotask executed');
}, 0);

Promise.resolve().then(() => {
  console.log('3: Microtask 1 executed');
  queueMicrotask(() => {
    console.log('5: Nested microtask executed');
  });
}).then(() => {
  console.log('4: Microtask 2 executed');
});

queueMicrotask(() => {
  console.log('2: Microtask 3 executed');
});

console.log('Synchronous script end');

// Output Sequence:
// 1: Synchronous script start
// Synchronous script end
// 3: Microtask 1 executed
// 2: Microtask 3 executed
// 4: Microtask 2 executed
// 5: Nested microtask executed
// 6: Timer macrotask executed
```

1. Synchronous code executes, scheduling the timer on the host timer queue and queuing three microtasks.
2. The initial script task completes, emptying the call stack.
3. The engine invokes `PerformMicrotaskCheckpoint()`. Microtask 1 and Microtask 3 run.
4. Microtask 1 attaches Microtask 2 and nests Microtask 5.
5. All microtasks drain completely before the engine allows the next macrotask (the timer) to execute.

## The Microtask Starvation and False Yield Trap

A dangerous architectural pitfall in frontend applications is assuming that `await Promise.resolve()` yields execution to the browser to paint UI or handle user clicks.

```javascript
// Antipattern: Starves rendering and user interactions
async function processLargeBatch(items) {
  for (let i = 0; i < items.length; i++) {
    computeHeavyItem(items[i]);
    // The developer assumes this yields to the browser:
    await Promise.resolve(); // DANGEROUS: Schedules a microtask!
  }
}
```

Because an `await` on a fulfilled promise schedules an immediate promise reaction microtask, the call stack empties and immediately re-enters the microtask checkpoint. The browser cannot perform a rendering step or process pending user clicks until the microtask queue is entirely empty. If this loop runs for 500ms, the entire tab freezes for 500ms.

## Cooperative Scheduling and Yielding

To maintain a responsive UI at 60fps (16.6ms frame budget), long-running computation must be partitioned into chunks that yield back to the host event loop at a macrotask boundary.

```javascript
// True event-loop yielding utility
function yieldToHost() {
  // Modern browsers support scheduler.yield()
  if (globalThis.scheduler?.yield) {
    return globalThis.scheduler.yield();
  }
  // Fallback: Post a macrotask via setTimeout
  return new Promise((resolve) => {
    setTimeout(resolve, 0);
  });
}

async function processInChunks(items, processItem, chunkSize = 100) {
  if (!Number.isInteger(chunkSize) || chunkSize <= 0) {
    throw new RangeError('chunkSize must be a positive integer');
  }

  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);

    // Yield at chunk boundary to allow layout, paint, and clicks
    if ((i + 1) % chunkSize === 0 && i + 1 < items.length) {
      await yieldToHost();
    }
  }
}
```

### Same-Turn Coalescing

Microtasks are the ideal tool when multiple synchronous calls must be coalesced into a single consolidated batch before rendering:

```javascript
function createCoalescedBatcher(flush) {
  let queued = false;
  let batch = [];

  return function enqueue(item) {
    batch.push(item);
    if (queued) return;
    queued = true;

    queueMicrotask(() => {
      const pendingItems = batch;
      batch = [];
      queued = false;
      flush(pendingItems);
    });
  };
}
```

## Frame Pipeline and Animation Scheduling

The browser frame pipeline follows a strict schedule driven by display VSync:

```text
Macrotask ──▶ Microtasks ──▶ [ rAF Callbacks ──▶ Recalculate Styles ──▶ Layout ──▶ Paint ] ──▶ Next Macrotask
```

1. **`requestAnimationFrame(callback)`:** Executes immediately prior to style recalculation and layout. This is the only safe place to calculate and set CSS layout attributes without forcing layout trashing.
2. **`requestIdleCallback(callback)`:** Executes during idle periods when the browser has remaining time before the next VSync deadline.
3. **Timer Clamping:** `setTimeout(fn, 0)` is not zero milliseconds. The HTML standard specifies that after 5 nested timer calls, the minimum delay is forcibly clamped to 4ms.

## Synchronous Event Dispatch vs. Async User Clicks

A classic senior engineering test demonstrates the difference between user-initiated events and synthetic `.click()` invocations:

```javascript
const button = document.querySelector('button');

button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('Microtask 1'));
  console.log('Listener 1');
});

button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('Microtask 2'));
  console.log('Listener 2');
});
```

- **Scenario A: User clicks the button:**
  1. Browser dispatches click event. Listener 1 runs (`Listener 1`).
  2. Listener 1 finishes; call stack is **empty**. Microtask checkpoint drains (`Microtask 1`).
  3. Browser dispatches click to Listener 2. Listener 2 runs (`Listener 2`).
  4. Listener 2 finishes; call stack is **empty**. Microtask checkpoint drains (`Microtask 2`).
  5. Result: `Listener 1` → `Microtask 1` → `Listener 2` → `Microtask 2`.

- **Scenario B: Script calls `button.click()`:**
  1. `button.click()` pushes onto the call stack.
  2. Listener 1 runs synchronously (`Listener 1`).
  3. Listener 1 returns, but the call stack is **not empty** (it contains `button.click()`).
  4. Listener 2 runs immediately (`Listener 2`).
  5. `button.click()` finishes; call stack reaches zero.
  6. Microtask checkpoint drains both microtasks together.
  7. Result: `Listener 1` → `Listener 2` → `Microtask 1` → `Microtask 2`.

## Browser vs. Node.js Event Loop Model

While both run Google V8, their host loop implementations diverge fundamentally:

```text
Browser Event Loop:
[Task Queue Selection] ──▶ [Run Task] ──▶ [Drain Microtasks] ──▶ [Render Steps (VSync)]

Node.js (libuv) Event Loop:
┌──▶ Timers (setTimeout, setInterval)
│    │  Microtask Checkpoint (process.nextTick, Promise reactions)
├──▶ Pending Callbacks (I/O callbacks deferred to the next loop iteration)
│    │  Microtask Checkpoint
├──▶ Idle, Prepare (Internal libuv phases)
├──▶ Poll (Retrieve new I/O events; block when appropriate)
│    │  Microtask Checkpoint
├──▶ Check (setImmediate callbacks)
│    │  Microtask Checkpoint
└──▶ Close Callbacks (socket.on('close'))
        Microtask Checkpoint
```

- **Node.js `process.nextTick`:** Executes immediately after the current phase operation before any standard Promise microtasks.
- **Node.js `setImmediate`:** Runs during the `Check` phase, specifically designed to run after I/O polling completes.

## Summary

The event loop maintains JavaScript's run-to-completion contract while coordinating asynchronous I/O and visual rendering. Macrotasks represent discrete host events executed one per turn, whereas microtasks drain to exhaustion immediately whenever the call stack reaches zero. Chained microtasks starve rendering and user interactions; resilient systems partition heavy workloads into cooperative chunks using explicit host yields.

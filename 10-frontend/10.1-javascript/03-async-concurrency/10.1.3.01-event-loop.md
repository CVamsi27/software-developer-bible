# Event Loop

## TL;DR

The event loop is the runtime mechanism that drains the call stack, then processes microtasks (Promise reactions, `queueMicrotask`), then macrotasks (timers, I/O). Microtasks always run to completion before the next macrotask.

## First Principles

The event loop is forced by three facts colliding:

1. **One stack** (→ 10.1.1.03) — so slow work (I/O, timers) cannot run on it without freezing everything.
2. **The platform must stay responsive** — so slow work must happen *elsewhere* (browser/Node internals) and return results later.
3. **"Later" must be deterministic** — so there is exactly one rule: work re-enters the stack only when the stack is empty. That rule *is* the event loop; its two queues (microtask before macrotask) exist because *promise continuations must never be starved by a flood of timers*, a priority the spec pins.

`setTimeout(fn, 0)` never meaning "now" is axiom 3, not a quirk.


## Why It Matters

Understanding the event loop is required to reason about `setTimeout` ordering, why `await` yields to microtasks, and how to avoid UI jank. Interviewers test this with code-tracing questions like the famous `console.log` order puzzles (e.g., async vs Promise.resolve().then).

Everything downstream — `await`, promise reactions, timers, rendering — is just an entry in one of the two queues, so reading the order of any snippet is a matter of asking which queue each line lands in and when it was enqueued.

## Definition

The **Event Loop** is the mechanism that allows JavaScript to perform non-blocking operations despite being single-threaded. It continuously checks the call stack and callback queues, executing tasks when the stack is empty. The event loop is the heart of JavaScript's asynchronous behavior.

### Microtasks vs Macrotasks

```text
┌─────────────────────────────────────────────────────────┐
│ MICROTASKS vs MACROTASKS                                │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ MICROTASKS (High Priority):                             │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ • Promise.then/catch/finally                        │ │
│ │ • queueMicrotask()                                  │ │
│ │ • MutationObserver callbacks                        │ │
│ │                                                     │ │
│ │ • Execute after current task completes              │ │
│ │ • ALL microtasks run before next macrotask          │ │
│ │ • Can block rendering if too many                   │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ MACROTASKS (Normal Priority):                           │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ • setTimeout/setInterval callbacks                  │ │
│ │ • I/O operations                                    │ │
│ │ • UI rendering                                      │ │
│ │ • requestAnimationFrame                             │ │
│ │ • MessageChannel                                    │ │
│ │ • postMessage                                       │ │
│ │                                                     │ │
│ │ • One macrotask per event loop iteration            │ │
│ │ • Render happens after macrotasks                   │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ EXECUTION ORDER:                                        │
│ ┌─────────────────────────────────────────────────────┐ │
│ │                                                     │ │
│ │ 1. Synchronous code (call stack)                    │ │
│ │ 2. ALL microtasks                                   │ │
│ │ 3. ONE macrotask                                    │ │
│ │ 4. Render (if needed)                               │ │
│ │ 5. Repeat from step 2                               │ │
│ │                                                     │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
└─────────────────────────────────────────────────────────┘

```

Node.js adds one queue in front of both: `process.nextTick` callbacks drain to exhaustion — including ticks queued from inside a tick — before the promise/`queueMicrotask` queue does, so `await` loses to `nextTick` and promise code can still starve timers ([Node's own loop phases](../../../20-backend/20.1-node.js/01-runtime-and-async/20.1.1.01-event-loop.md) map the rest).

## Code Examples

### Basic Event Loop

```typescript
console.log('Start');

setTimeout(() => {
  console.log('Timeout 1');
}, 0);

setTimeout(() => {
  console.log('Timeout 2');
}, 0);

Promise.resolve().then(() => {
  console.log('Promise 1');
});

Promise.resolve().then(() => {
  console.log('Promise 2');
});

console.log('End');

// Output:
// Start
// End
// Promise 1
// Promise 2
// Timeout 1
// Timeout 2

// Why?
// 1. Synchronous code runs first: 'Start', 'End'
// 2. Microtasks (Promises) run: 'Promise 1', 'Promise 2'
// 3. Macrotasks (setTimeout) run: 'Timeout 1', 'Timeout 2'

```

### Complex Ordering

```typescript
console.log('1');

setTimeout(() => {
  console.log('2');
}, 0);

Promise.resolve().then(() => {
  console.log('3');
}).then(() => {
  console.log('4');
});

console.log('5');

// Output: 1, 5, 3, 4, 2

// Why?
// 1. Sync: '1', '5'
// 2. Microtask: '3' (first .then)
// 3. Microtask: '4' (second .then, scheduled after first)
// 4. Macrotask: '2'

```

### Nested Promises

```typescript
Promise.resolve().then(() => {
  console.log('Promise 1');

  setTimeout(() => {
    console.log('Timeout 1');
  }, 0);

  Promise.resolve().then(() => {
    console.log('Promise 2');
  });
});

setTimeout(() => {
  console.log('Timeout 2');
}, 0);

// Output:
// Promise 1
// Promise 2
// Timeout 2
// Timeout 1

// Why?
// 1. First Promise runs: 'Promise 1'
// 2. Inside Promise: schedules Timeout 1 and Promise 2
// 3. Promise 2 is microtask, runs before Timeout 2
// 4. Timeout 2 is macrotask, runs after all microtasks
// 5. Timeout 1 is macrotask, runs in next iteration

```

### queueMicrotask

```typescript
console.log('Start');

queueMicrotask(() => {
  console.log('Microtask 1');
});

Promise.resolve().then(() => {
  console.log('Promise 1');
});

queueMicrotask(() => {
  console.log('Microtask 2');
});

console.log('End');

// Output:
// Start
// End
// Microtask 1
// Promise 1
// Microtask 2

// queueMicrotask runs in microtask queue
// Order within microtasks: insertion order

```

### requestAnimationFrame

```typescript
console.log('Start');

requestAnimationFrame(() => {
  console.log('RAF 1');
});

requestAnimationFrame(() => {
  console.log('RAF 2');
});

setTimeout(() => {
  console.log('Timeout');
}, 0);

Promise.resolve().then(() => {
  console.log('Promise');
});

console.log('End');

// Output:
// Start
// End
// Promise
// then, in an order the spec does not pin down:
//   RAF 1, RAF 2, Timeout   or   Timeout, RAF 1, RAF 2

// What IS pinned: rAF callbacks run before the frame is painted, and both
// run after the microtask queue has drained. A 0ms timer is a task, so it
// competes with the render opportunity rather than with the paint itself —
// which one the browser takes first depends on when the timer expires
// relative to the frame.

```

### Async/Await

> *async/await gets its own deep-dive in [10.1.3.03 — Async/Await](10.1.3.03-async-await.md).*

```typescript
async function example() {
  console.log('Async Start');

  await Promise.resolve();

  console.log('After Await');
}

example();

console.log('End');

// Output:
// Async Start
// End
// After Await

// Why?
// 1. 'Async Start' runs synchronously
// 2. await pauses execution, returns to caller
// 3. 'End' runs synchronously
// 4. Microtask: 'After Await' runs after promise resolves

```

### fetch and Event Loop

```typescript
console.log('Start');

fetch('https://api.example.com/data')
  .then(response => response.json())
  .then(data => {
    console.log('Data received');
  })
  .catch(error => {
    console.log('Error');
  });

console.log('End');

// Output:
// Start
// End
// Data received (or Error)

// Why?
// 1. 'Start' and 'End' run synchronously — fetch() only hands the request
//    to the network stack and returns a pending promise
// 2. When the response lands, that settle happens inside a task, and the
//    .then reaction is queued as a microtask at that moment
// 3. So 'Data received' prints in a later turn of the loop, never in this
//    tick — but once it is queued it still beats every timer behind it

```

## Real-World Use Cases

### 1. UI Responsiveness

```typescript
// Bad: Blocking UI
function processLargeArray(items: any[]) {
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]); // Blocks UI
  }
}

// Good: Yield to event loop
async function processLargeArrayAsync(items: any[]) {
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);

    // Yield every 100 items
    if (i % 100 === 0) {
      await new Promise(resolve => setTimeout(resolve, 0));
    }
  }
}

```

### 2. Debouncing with Microtasks

```typescript
function debounceMicrotask<T extends (...args: any[]) => any>(
  func: T,
  wait: number
): (...args: Parameters<T>) => void {
  let timeout: ReturnType<typeof setTimeout>;

  return function(...args: Parameters<T>) {
    clearTimeout(timeout);
    timeout = setTimeout(() => func(...args), wait);
  };
}

// Or using microtask
function debounceMicro<T extends (...args: any[]) => any>(
  func: T
): (...args: Parameters<T>) => void {
  let pending = false;

  return function(...args: Parameters<T>) {
    if (!pending) {
      pending = true;
      queueMicrotask(() => {
        func(...args);
        pending = false;
      });
    }
  };
}

```

### 3. Animation Timing

```typescript
class Animation {
  private running = false;

  start() {
    this.running = true;
    this.animate();
  }

  animate() {
    if (!this.running) return;

    // Update animation state
    this.update();

    // Schedule next frame
    requestAnimationFrame(() => this.animate());
  }

  update() {
    // Animation logic here
  }

  stop() {
    this.running = false;
  }
}

```

### 4. Data Loading with Priority

```typescript
class DataLoader {
  private cache = new Map<string, any>();
  private pending = new Map<string, Promise<any>>();

  async load(url: string, priority: 'high' | 'low' = 'low') {
    if (this.cache.has(url)) {
      return this.cache.get(url);
    }

    if (this.pending.has(url)) {
      return this.pending.get(url);
    }

    const promise = fetch(url)
      .then(response => response.json())
      .then(data => {
        this.cache.set(url, data);
        this.pending.delete(url);
        return data;
      });

    this.pending.set(url, promise);

    // 'priority' here only decides how this function's own continuation
    // resumes: a high-priority caller waits on a microtask, so it gets its
    // answer before any timer or I/O task; the network itself is unaffected
    if (priority === 'high') {
      await new Promise(resolve => queueMicrotask(resolve));
    }

    return promise;
  }
}

```

function setupEventDelegation(container: HTMLElement) {

## Common Mistakes

### 1. Assuming setTimeout 0 is Immediate

```typescript
console.log('Start');

setTimeout(() => {
  console.log('Timeout');
}, 0);

console.log('End');

// Output: Start, End, Timeout
// setTimeout 0 doesn't mean "run immediately"
// It means "run after current synchronous code and microtasks"

```

### 2. Blocking the Event Loop

```javascript
// Bad: Long-running synchronous code
function heavyComputation() {
  let sum = 0;
  for (let i = 0; i < 1000000000; i++) {
    sum += i;
  }
  return sum;
}

// This blocks the event loop for seconds
// UI becomes unresponsive

// Good: Time-slicing — exit the stack between chunks so the
// event loop can interleave renders and input handling
async function heavyComputationChunked() {
  const TOTAL = 1_000_000_000;
  const CHUNK = 1_000_000;
  let sum = 0;

  for (let i = 0; i < TOTAL; i++) {
    sum += i;
    if (i % CHUNK === 0) {
      await scheduler.yield(); // Yields without setTimeout's ~4ms clamping delay
    }
  }

  return sum;
}

// Where scheduler.yield() is unavailable, fall back to a macrotask break:
//   await new Promise(resolve => setTimeout(resolve, 0));
// For work that should never touch the main thread at all,
// use a Web Worker (see 10.1.6.02-web-workers.md)
```

Why time-slicing works: `await` (or a `setTimeout` callback) means the current function **returns and pops off the call stack** before the next chunk runs. Between chunks the stack is empty, so the event loop is free to dispatch queued clicks and let the browser repaint.

Timer clamping caveat: nested `setTimeout(..., 0)` calls are clamped to ~4ms each by browsers — 1,000 chunks adds ~4 seconds of pure waiting. That is exactly what `scheduler.yield()` avoids: it requeues the continuation as a normal task with no minimum delay. For `requestAnimationFrame`-aligned yielding see the rAF section above.

### 3. Microtask Starvation

```typescript
// Bad: Infinite microtask loop
function microtaskStarvation() {
  queueMicrotask(() => {
    console.log('Microtask');
    microtaskStarvation(); // Keeps adding microtasks
  });
}

// This blocks macrotasks and rendering
// UI freezes

// Good: Use setTimeout for long-running tasks
function goodPattern() {
  queueMicrotask(() => {
    console.log('Microtask');
    if (shouldContinue) {
      setTimeout(goodPattern, 0); // Use macrotask
    }
  });
}

```

### 4. Forgetting await

```typescript
// Bad: Missing await
async function fetchData() {
  const response = fetch('https://api.example.com'); // Missing await!
  const data = response.json(); // Error: response is Promise
  return data;
}

// Good: Proper await
async function fetchDataFixed() {
  const response = await fetch('https://api.example.com');
  const data = await response.json();
  return data;
}

```

## Best Practices

1. **Prefer `async`/`await` over chained `.then`** — one `try`/`catch` replaces the per-stage `.catch`, and the stack reads top to bottom (worked in [10.1.3.03 — Async/Await](10.1.3.03-async-await.md)).
2. **Never own the stack for long** — chunk synchronous work with `await scheduler.yield()` (or a `setTimeout(…, 0)` break), and move workloads that must never touch the thread into a [Web Worker](../06-modern-and-interview/10.1.6.02-web-workers.md).
3. **Match the queue to the urgency** — `queueMicrotask` for a DOM write that has to land before anything renders, a timer task for work that may sit behind input and paint.
4. **Schedule cooperatively instead of recursively** — draining high-priority items and then yielding one low-priority item (the `TaskScheduler` pattern below) stops a burst from monopolizing a single turn of the loop.

## Performance Considerations

### Task Timing

The same numbers show up in DevTools' Performance panel as task bars with an "Long task" marker, which is usually faster than hand-timing — use `performance.now()` only when you need the figure in code (for telemetry, say).

```typescript
// Measure task execution time
function measureTask(name: string, fn: () => void) {
  const start = performance.now();
  fn();
  const end = performance.now();
  console.log(`${name}: ${end - start}ms`);
}

// Use for performance profiling
measureTask('Heavy computation', () => {
  heavyComputation();
});

```

### Frame Rate

```typescript
// Monitor frame rate
let lastTime = performance.now();
let frameCount = 0;

function checkFrameRate() {
  frameCount++;
  const currentTime = performance.now();

  if (currentTime - lastTime >= 1000) {
    console.log(`FPS: ${frameCount}`);
    frameCount = 0;
    lastTime = currentTime;
  }

  requestAnimationFrame(checkFrameRate);
}

requestAnimationFrame(checkFrameRate);

```

### Task Scheduling

```typescript
class TaskScheduler {
  private highPriority: (() => void)[] = [];
  private lowPriority: (() => void)[] = [];

  schedule(task: () => void, priority: 'high' | 'low' = 'low') {
    if (priority === 'high') {
      this.highPriority.push(task);
    } else {
      this.lowPriority.push(task);
    }

    this.process();
  }

  private process() {
    queueMicrotask(() => {
      // Process all high priority first
      while (this.highPriority.length > 0) {
        const task = this.highPriority.shift()!;
        task();
      }

      // Then process one low priority
      if (this.lowPriority.length > 0) {
        const task = this.lowPriority.shift()!;
        task();
      }

      // Continue if there are more tasks
      if (this.highPriority.length > 0 || this.lowPriority.length > 0) {
        this.process();
      }
    });
  }
}

```

## Summary

The event loop is fundamental to JavaScript:

1. **Single-threaded**: Uses event loop for concurrency

2. **Two queues**: Microtasks (high priority) and macrotasks (low priority)

3. **Execution order**: Sync → Microtasks → Macrotask → Render

4. **Non-blocking**: Allows handling multiple operations

5. **Performance**: Don't block the event loop

6. **Debugging**: Use DevTools and performance APIs

7. **Best practices**: Use async/await, Web Workers, proper scheduling

## Revision Questions

**Definition**

1. **Q:** In one sentence, what job does the event loop do?
   **A:** It only ever hands the stack work from an empty stack: drain the stack, drain every microtask, take one task, look for a chance to render — then start again.

**How It Works**

2. **Q:** Why do promise continuations get a separate queue instead of waiting alongside timers?
   **A:** The spec pins that priority — a `.then` must finish before the next task starts — so timers can never starve promises, while promises are free to starve rendering.

3. **Q:** Where does Node's `process.nextTick` sit relative to those queues?
   **A:** In front of the microtask queue, drained to exhaustion first (including ticks queued by ticks), which is why `nextTick` work beats both `await` continuations and timers.

**Code Examples**

4. **Q:** A snippet logs synchronously, then schedules `setTimeout(fn, 0)` and a `.then`; what order do the three print in?
   **A:** The synchronous lines, then the microtask, then the timer — the stack empties, microtasks drain to exhaustion, and only then does the loop take one task off the timer queue.

5. **Q:** Why does code after `await Promise.resolve()` start running after the caller's remaining synchronous code?
   **A:** `await` hands a pending promise back to the caller and parks the rest of the function as a reaction, so the caller finishes on this stack and the continuation arrives in a later microtask drain.

**Common Mistakes**

6. **Q:** Why is `setTimeout(fn, 0)` never equivalent to calling `fn()` on the next line?
   **A:** It enqueues a task, and a task cannot start until the stack is empty *and* every microtask queued in the meantime has already run.

**Performance Considerations**

7. **Q:** What stops running while a synchronous loop occupies the stack for two seconds?
   **A:** Everything scheduled through the loop — microtasks, tasks, and rendering all wait, because none of them may enter a stack that is not empty; input queues up instead of being handled.

**Best Practices**

8. **Q:** A DOM write must be visible in the very next paint; which queue do you use and why?
   **A:** A microtask, because microtasks drain before the render opportunity arrives, whereas a timer task is eligible only after the current task — and could miss the frame.

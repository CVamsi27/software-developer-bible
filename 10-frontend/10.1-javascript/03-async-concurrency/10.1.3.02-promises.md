# Promises

A fetch can succeed while the downstream transform throws. Code needs a handle that represents the pending computation, pipes values through stages, and routes failures to a recovery boundary — without collapsing the stack.

```javascript
// excerpt
fetch('/api/users')
  .then((res) => res.json())
  .then((users) => users.length)
  .catch((err) => console.error('Pipeline failed:', err));
```

## Definition

A **Promise** is an object representing eventual completion or failure. Its settlement cannot be replaced, although a fulfilled object can still mutate. Callers compose that eventual outcome through reactions.

> **Textbook Definition:** A Promise is an object that acts as a placeholder for the eventual result of an asynchronous operation, existing in one of three mutually exclusive states: pending, fulfilled, or rejected. State transitions are irrevocable, and registered reaction callbacks are guaranteed to execute asynchronously during microtask checkpoints.

## First Principles

A promise is a single-transition state machine: `pending` → `fulfilled` *or* `rejected`, exactly once, then immutable. Reactions (`.then()`, `.catch()`, and `.finally()`) never run inline — even on an already-settled promise — but queue as microtasks. Each combinator call returns a *new* promise, so pipelines branch without mutation. And resolving is not fulfilling: resolving with another thenable delegates the outcome, keeping the outer promise pending until the inner one settles.

```text
pending ──fulfill(value)──► fulfilled(value)
    └────reject(reason)──► rejected(reason)

resolve(thenable) locks the outcome path while adoption may remain pending.
Fulfillment and rejection cannot later be replaced.
```

## 1. Internal Slots and the Synchronous Executor

The engine builds each promise with spec internal slots:

| Internal Slot | Description | Initial Value |
| :---------------------------- | :-------------------------------------------------------------------------------------------------------- | :-------------- |
| `[[PromiseState]]` | Lifecycle state: `"pending"`, `"fulfilled"`, or `"rejected"` | `"pending"` |
| `[[PromiseResult]]` | The fulfillment value or rejection reason once settled | `undefined` |
| `[[PromiseFulfillReactions]]` | List of `PromiseReaction` records triggered upon fulfillment | Empty List `[]` |
| `[[PromiseRejectReactions]]` | List of `PromiseReaction` records triggered upon rejection | Empty List `[]` |
| `[[PromiseIsHandled]]` | Tracks whether promise reactions have been registered; downstream promises still need rejection ownership | `false` |

The executor runs **synchronously**; reactions run as microtasks:

```javascript
const promise = new Promise((resolve, reject) => {
  console.log('1: Synchronous executor executes immediately');
  resolve('payload');
});

promise.then((val) => {
  console.log('3: Microtask reaction receives:', val);
});

console.log('2: Synchronous code continues');

// Output:
// 1: Synchronous executor executes immediately
// 2: Synchronous code continues
// 3: Microtask reaction receives: payload
```

Engines check `[[PromiseIsHandled]]` when the current microtask checkpoint completes after a rejection. Deferring `.catch()` into a later `setTimeout` misses that window — triggering a host `unhandledRejection` notification first (which terminates Node under `--unhandled-rejections=throw`) and only firing `rejectionHandled` if the process survives until the later handler attaches. Attach `.catch()` synchronously or on the active chain so `[[PromiseIsHandled]]` flips to `true` before the checkpoint finishes.

## 2. The Resolution Procedure: Resolving vs. Fulfilling

```javascript
// Resolving with another Promise adopts its state:
const inner = new Promise((resolve) => setTimeout(() => resolve('ready'), 50));
const outer = new Promise((resolve) => resolve(inner));

console.log(outer); // Promise { <pending> } -> NOT fulfilled yet!
outer.then((val) => console.log(val)); // Prints "ready" after the timer fires (no exact deadline)
```

The first effective `resolve` or `reject` call locks the outcome path. Resolving a promise with itself **rejects that promise with a `TypeError`**; the `resolve` call does not throw that error to its caller. For an object, the algorithm reads `then`: a throwing getter rejects the promise, a callable `then` is invoked in a later promise job with guarded resolving functions, and a non-callable `then` lets the object fulfill normally. Adopting a pending thenable can therefore leave a resolved promise pending.

```javascript
let resolveSelf;
const self = new Promise((resolve) => { resolveSelf = resolve; });
resolveSelf(self); // Returns normally; self becomes rejected
self.catch((error) => console.log(error instanceof TypeError)); // true
```

## 3. Chaining and the Return Propagation Matrix

Each `.then()` returns a new promise whose fate depends on the callback:

| Handler Execution | Handler Return Value | Child Promise Outcome |
| :---------------------- | :---------------------------------------- | :----------------------------------------------- |
| Returns standard value | `return 42` or `return { ok: true }` | Fulfills with returned value |
| Returns another Promise | `return fetch('/api')` | Adopts state and value of returned Promise |
| Throws an Exception | `throw new Error('boom')` | Rejects with thrown error as reason |
| No return statement | `console.log(x)` (implicitly `undefined`) | Fulfills with `undefined` |
| Omitted handler | (Pass-through) | Adopts parent promise state and result unchanged |

```javascript
Promise.resolve(10)
  .then((num) => {
    console.log('Step 1:', num); // 10
    return num * 2;
  })
  .then((doubled) => {
    console.log('Step 2:', doubled); // 20
    throw new Error('Calculation halted');
  })
  .catch((err) => {
    console.log('Step 3 (Recovered):', err.message); // Calculation halted
    return 100; // Recovery value fulfills subsequent chain
  })
  .then((recovered) => {
    console.log('Step 4:', recovered); // 100
  });
```

**The sibling-handler trap**: in `.then(onFulfilled, onRejected)`, `onRejected` handles only the *preceding* promise — it never catches errors thrown inside its sibling `onFulfilled`:

```javascript
// excerpt
// DANGEROUS: Sibling onRejected misses errors in onFulfilled
apiCall().then(
  (data) => {
    throw new Error('Parsing error');
  },
  (err) => {
    // This handler NEVER catches "Parsing error"!
    console.error('Network failed:', err);
  }
);

// CORRECT: Chained .catch() intercepts errors from both
apiCall()
  .then((data) => {
    throw new Error('Parsing error');
  })
  .catch((err) => {
    // Catches network failures AND parsing errors
    console.error('Caught pipeline error:', err);
  });
```

## 4. `finally` Semantics and the Async-Executor Pitfall

`.finally(callback)` is for cleanup: it receives no arguments, passes the parent outcome through untouched — unless the callback itself throws or returns a rejected promise, which replaces the outcome:

```javascript
Promise.resolve('data')
  .finally(() => {
    console.log('Cleanup resources');
  })
  .then((val) => console.log('Result:', val)); // Prints "data"
```

Never pass an `async` executor to `new Promise()`: an async function reports throws through its own returned promise, even before its first await. The constructor ignores that returned promise, so the outer promise may remain pending while the executor rejection goes unhandled:

```javascript
// excerpt
// ANTIPATTERN: Async Executor
new Promise(async (resolve, reject) => {
  const user = await fetchUser(); // If this throws...
  resolve(user);
});
```

## 5. The Four Promise Combinators

| Combinator | Settlement Strategy | Winning Condition | Rejection Condition | Empty Iterable `[]` |
| :----------------------- | :------------------ | :------------------- | :-------------------------------------- | :---------------------------------------- |
| **`Promise.all`** | All-or-nothing | All inputs fulfill | First rejection short-circuits | Fulfills immediately: `[]` |
| **`Promise.allSettled`** | Comprehensive | All inputs settle | Input rejections become outcome records | Fulfills immediately: `[]` |
| **`Promise.race`** | First responder | First input settles | First input rejects | Remains **pending forever** |
| **`Promise.any`** | First success | First input fulfills | All inputs reject (`AggregateError`) | Rejects immediately with `AggregateError` |

```javascript
async function compareCombinators() {
  const p1 = Promise.resolve('fast');
  const p2 = Promise.reject(new Error('fail'));

  // 1. Promise.allSettled: Inspects ordinary input fulfillment and rejection
  const settled = await Promise.allSettled([p1, p2]);
  console.log(settled);
  // [{ status: 'fulfilled', value: 'fast' }, { status: 'rejected', reason: Error }]

  // 2. Promise.any: Ignores failures if at least one fulfills
  const firstSuccess = await Promise.any([p1, p2]);
  console.log(firstSuccess); // "fast"

  // 3. Promise.all: Fast-fails on first error
  try {
    await Promise.all([p1, p2]);
  } catch (err) {
    console.log('all failed:', err.message); // fail
  }
}

compareCombinators();
```

For a normal iterable of promises, `allSettled` records input rejections. Iterating a broken iterable can instead reject the aggregate; it is not a universal never-reject contract. All combinators return outcomes asynchronously to attached reactions, even when their empty-input promise is already settled.

> [!WARNING]
> Short-circuiting (`Promise.all`, `Promise.race`) does **not** cancel underlying requests — they keep consuming bandwidth and server resources unless aborted via `AbortController`.

Two newer built-in helpers remove common promise boilerplate:

- **`Promise.withResolvers()` (ES2024)** returns `{ promise, resolve, reject }` directly when settlement must be triggered outside the constructor callback (for example, from an event listener or stream controller).
- **`Promise.try(fn, ...args)` (ES2025)** calls `fn` synchronously and wraps both its return value and any synchronous throw into a returned Promise — useful when wrapping a callback that might be synchronous or async without delaying execution by a microtask.

```javascript
// ES2024: Defer settlement outside new Promise(...)
const { promise: readyPromise, resolve: markReady } = Promise.withResolvers();
setTimeout(() => markReady('connected'), 10);

// ES2025: Execute immediately, converting sync throws into Promise rejections
const syncThrowPromise = Promise.try(() => {
  throw new Error('sync failure captured');
});

Promise.allSettled([readyPromise, syncThrowPromise]).then((outcomes) => {
  console.log(outcomes[0].value, outcomes[1].reason.message);
  // 'connected' 'sync failure captured'
});
```

## 6. Production Pattern: In-Flight Promise Memoization

Concurrent callers for the same key cause a cache stampede. Memoizing the *in-flight promise* shares one execution (on ES2025+ runtimes, `Promise.try(() => fetcher(key))` can replace `Promise.resolve().then(() => fetcher(key))` so `fetcher` starts immediately while still converting synchronous throws into rejections):

```javascript
function createInFlightDeduplicator(fetcher) {
  const inFlight = new Map();

  return function load(key) {
    if (inFlight.has(key)) {
      return inFlight.get(key); // Return shared pending promise
    }

    const promise = Promise.resolve()
      .then(() => fetcher(key))
      .finally(() => {
        // Automatically evict from in-flight cache upon settlement
        inFlight.delete(key);
      });

    inFlight.set(key, promise);
    return promise;
  };
}

let calls = 0;
const fetchUserData = createInFlightDeduplicator(async (id) => {
  calls++;
  await new Promise((resolve) => setTimeout(resolve, 10));
  if (calls === 2) throw new Error('transient error');
  return { id, role: 'admin' };
});

(async () => {
  // Concurrent calls share one execution and identical object reference:
  const [userA, userB] = await Promise.all([
    fetchUserData('usr_101'),
    fetchUserData('usr_101'),
  ]);
  console.log(calls, userA === userB); // 1 true

  // Settlement evicts the key so subsequent failures and retries run cleanly:
  await fetchUserData('usr_101').catch((e) => console.log('retried:', calls, e.message));
  const recovered = await fetchUserData('usr_101');
  console.log(calls, recovered.id); // 3 'usr_101'
})();
```

## Summary

Promises replace callback nesting with composable handles on strict microtask timing. Settlement is single and irrevocable; each `.then()` spawns an independent promise governed by the handler's return; `.finally` passes outcomes through for cleanup; the four combinators orchestrate concurrency without canceling I/O. Share in-flight promises to deduplicate stampedes, and never use async executors.

# Promises

An asynchronous fetch operation can succeed while a downstream data transformation throws a runtime error. Applications require a deterministic handle to encapsulate pending computations, propagate values across pipelines, and channel exceptions to designated recovery boundaries without collapsing the call stack.

## Definition

A **Promise** is a stateful abstraction representing the eventual completion or failure of an asynchronous operation. It acts as an immutable proxy for a value that may not be known when the promise is constructed, enabling asynchronous methods to return values like synchronous functions.

> **Textbook Definition:** A Promise is an object that acts as a placeholder for the eventual result of an asynchronous operation, existing in one of three mutually exclusive states: pending, fulfilled, or rejected. State transitions are irrevocable, and registered reaction callbacks are guaranteed to execute asynchronously during microtask checkpoints.

## First Principles

1. **State Machine Invariant:** A promise begins in the `pending` state and may transition exactly once to either `fulfilled` (with a value) or `rejected` (with a reason). Once settled, its state and payload are immutable.
2. **Asynchronous Reaction Guarantee:** Handlers registered via `.then()`, `.catch()`, or `.finally()` never execute synchronously inline, even if the promise is already settled when the handler is attached. They are queued as microtasks.
3. **Chain Identity Separation:** Every invocation of `.then()`, `.catch()`, or `.finally()` constructs and returns a brand-new Promise instance, preserving immutability and enabling branching pipelines.
4. **Resolution Procedure Decoupling:** Resolving a promise is distinct from fulfilling it. Resolving with another thenable delegates the outcome to that object, keeping the outer promise pending until the inner operation settles.

```text
                      ┌───────────────┐
                      │    Pending    │
                      └───────┬───────┘
                              │
             ┌────────────────┴────────────────┐
             │ Resolve(value)                  │ Reject(reason)
             ▼                                 ▼
    ┌───────────────────────────────────────────────────┐               ┌─────────────────┐
    │    Fulfilled    │               │    Rejected     │
    │ (Result: value) │               │ (Result: reason)│
    └───────────────────────────────────────────────────┘               └─────────────────┘
             │                                 │
             └───────────────┬─────────────────┘
                             ▼
                 Irrevocable Settlement
```

## Promise Internal Slots and Engine Mechanics

According to the ECMAScript specification, an engine instantiates a Promise with several internal slots:

| Internal Slot | Description | Initial Value |
| :---------------------------- | :----------------------------------------------------------------- | :-------------- |
| `[[PromiseState]]` | Lifecycle state: `"pending"`, `"fulfilled"`, or `"rejected"` | `"pending"` |
| `[[PromiseResult]]` | The fulfillment value or rejection reason once settled | `undefined` |
| `[[PromiseFulfillReactions]]` | List of `PromiseReaction` records triggered upon fulfillment | Empty List `[]` |
| `[[PromiseRejectReactions]]` | List of `PromiseReaction` records triggered upon rejection | Empty List `[]` |
| `[[PromiseIsHandled]]` | Boolean flag indicating whether a rejection handler was registered | `false` |

```javascript
const promise = new Promise((resolve, reject) => {
  console.log('1: Synchronous executor executes immediately');
  resolve('payload');
});

promise.then((val) => {
  console.log('3: Microtask reaction receives:', val);
});

console.log('2: Synchronous code continues');

// Output:
// 1: Synchronous executor executes immediately
// 2: Synchronous code continues
// 3: Microtask reaction receives: payload
```

The executor function is invoked synchronously by the `Promise` constructor. However, the reactions attached via `.then()` are queued into V8's microtask queue and execute only during the microtask checkpoint after the current stack clears.

## The Promise Resolution Procedure

A critical distinction for senior engineers is that **resolving** a promise does not necessarily mean **fulfilling** it. When `resolve(x)` is called:

```javascript
// Resolving with another Promise adopts its state:
const inner = new Promise((resolve) => setTimeout(() => resolve('ready'), 50));
const outer = new Promise((resolve) => resolve(inner));

console.log(outer); // Promise { <pending> } -> NOT fulfilled yet!
outer.then((val) => console.log(val)); // Prints "ready" after 50ms
```

1. **Self-Resolution Check:** If `promise === x`, the engine throws a `TypeError` to prevent an infinite resolution cycle.
2. **Promise Adoption:** If `x` is already a Promise, the target promise adopts `x`'s `[[PromiseState]]` and `[[PromiseResult]]`.
3. **Thenable Extraction:** If `x` is an object or function with a callable `then` property, the engine invokes `x.then(resolvePromise, rejectPromise)`. It guards against multiple invocations using an internal `alreadyCalled` flag.
4. **Value Settlement:** If `x` is a non-thenable value, the promise immediately transitions to `fulfilled` with `x`.

## Chaining and Return Propagation Matrix

Every `.then()` call returns a new promise whose fate depends entirely on the return value or thrown error of the callback:

| Handler Execution | Handler Return Value | Child Promise Outcome |
| :---------------------- | :---------------------------------------- | :----------------------------------------------- |
| Returns standard value | `return 42` or `return { ok: true }` | Fulfills with returned value |
| Returns another Promise | `return fetch('/api')` | Adopts state and value of returned Promise |
| Throws an Exception | `throw new Error('boom')` | Rejects with thrown error as reason |
| No return statement | `console.log(x)` (implicitly `undefined`) | Fulfills with `undefined` |
| Omitted handler | (Pass-through) | Adopts parent promise state and result unchanged |

```javascript
Promise.resolve(10)
  .then((num) => {
    console.log('Step 1:', num); // 10
    return num * 2;
  })
  .then((doubled) => {
    console.log('Step 2:', doubled); // 20
    throw new Error('Calculation halted');
  })
  .catch((err) => {
    console.log('Step 3 (Recovered):', err.message); // Calculation halted
    return 100; // Recovery value fulfills subsequent chain
  })
  .then((recovered) => {
    console.log('Step 4:', recovered); // 100
  });
```

### The Sibling Handler Trap

In `.then(onFulfilled, onRejected)`, the `onRejected` callback only handles rejections from the *preceding* promise. It cannot catch errors thrown inside its sibling `onFulfilled`:

```javascript
// DANGEROUS: Sibling onRejected misses errors in onFulfilled
apiCall().then(
  (data) => {
    throw new Error('Parsing error');
  },
  (err) => {
    // This handler NEVER catches "Parsing error"!
    console.error('Network failed:', err);
  }
);

// CORRECT: Chained .catch() intercepts errors from both
apiCall()
  .then((data) => {
    throw new Error('Parsing error');
  })
  .catch((err) => {
    // Catches network failures AND parsing errors
    console.error('Caught pipeline error:', err);
  });
```

## Error Handling, Finally, and the Async Executor Pitfall

### The Semantics of `.finally()`

`.finally(callback)` is designed for resource cleanup. It has unique semantics:
- It receives no arguments (it cannot inspect whether the promise fulfilled or rejected).
- It passes through the parent's fulfillment value or rejection reason untouched.
- **Exception:** If the `finally` callback throws an error or returns a rejected promise, that new rejection replaces the original outcome.

```javascript
Promise.resolve('data')
  .finally(() => {
    console.log('Cleanup resources');
  })
  .then((val) => console.log('Result:', val)); // Prints "data"
```

### The Async Executor Anti-Pattern

Never pass an `async` function as the executor to `new Promise()`:

```javascript
// ANTIPATTERN: Async Executor
new Promise(async (resolve, reject) => {
  const user = await fetchUser(); // If this throws...
  resolve(user);
});
```

If an error is thrown inside an `async` executor after an `await`, it results in an unhandled rejection because the `Promise` constructor only catches errors thrown *synchronously* during the initial executor invocation.

## The Four Promise Combinators

JavaScript provides four combinator methods to coordinate concurrent operations:

| Combinator | Settlement Strategy | Winning Condition | Rejection Condition | Empty Iterable `[]` |
| :----------------------- | :------------------ | :------------------- | :----------------------------------- | :---------------------------------------- |
| **`Promise.all`** | All-or-nothing | All inputs fulfill | First rejection short-circuits | Fulfills immediately: `[]` |
| **`Promise.allSettled`** | Comprehensive | All inputs settle | Never rejects | Fulfills immediately: `[]` |
| **`Promise.race`** | First responder | First input settles | First input rejects | Remains **pending forever** |
| **`Promise.any`** | First success | First input fulfills | All inputs reject (`AggregateError`) | Rejects immediately with `AggregateError` |

```javascript
async function compareCombinators() {
  const p1 = Promise.resolve('fast');
  const p2 = Promise.reject(new Error('fail'));

  // 1. Promise.allSettled: Never throws; inspects all outcomes
  const settled = await Promise.allSettled([p1, p2]);
  console.log(settled);
  // [{ status: 'fulfilled', value: 'fast' }, { status: 'rejected', reason: Error }]

  // 2. Promise.any: Ignores failures if at least one fulfills
  const firstSuccess = await Promise.any([p1, p2]);
  console.log(firstSuccess); // "fast"

  // 3. Promise.all: Fast-fails on first error
  try {
    await Promise.all([p1, p2]);
  } catch (err) {
    console.log('all failed:', err.message); // fail
  }
}
```

> [!WARNING]
> Combinator short-circuiting (e.g. `Promise.all` or `Promise.race`) does **not** cancel underlying network requests. The unhandled network operations continue consuming bandwidth and server resources unless explicitly aborted via `AbortController`.

## Production Pattern: In-Flight Promise Memoization

When multiple microservices or UI components simultaneously request the same resource, naive implementations trigger redundant network requests (cache stampede). Memoizing the *in-flight promise* ensures all callers share a single execution:

```javascript
function createInFlightDeduplicator(fetcher) {
  const inFlight = new Map();

  return function load(key) {
    if (inFlight.has(key)) {
      return inFlight.get(key); // Return shared pending promise
    }

    const promise = Promise.resolve()
      .then(() => fetcher(key))
      .finally(() => {
        // Automatically evict from in-flight cache upon settlement
        inFlight.delete(key);
      });

    inFlight.set(key, promise);
    return promise;
  };
}

// Usage:
const fetchUserData = createInFlightDeduplicator(async (id) => {
  const res = await fetch(`/api/users/${id}`);
  return res.json();
});

// Both calls fire concurrently but execute exactly one network fetch:
const [userA, userB] = await Promise.all([
  fetchUserData('usr_101'),
  fetchUserData('usr_101'),
]);
console.log(userA === userB); // true (Identical result object reference)
```

## Summary

Promises replace callback hell with composable, stateful handles governed by strict microtask execution. State transitions from pending to fulfilled or rejected are irrevocable. Every `.then()` creates an independent promise whose outcome depends on the handler's return value. The four combinators (`all`, `allSettled`, `race`, `any`) provide precise orchestration, but do not cancel underlying network I/O upon short-circuiting without explicit signal handling.

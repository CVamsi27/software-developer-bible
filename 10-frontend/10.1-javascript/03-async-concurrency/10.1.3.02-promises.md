# Promises

## Definition

A **promise** is a handle for an outcome that may arrive later: either a value (**fulfillment**) or a failure reason (**rejection**). While neither has arrived, it is **pending**. Fulfilled or rejected promises are **settled**.

Imagine loading an account and then its orders. The caller cannot use account data before it arrives, but it needs a way to say what should happen next. A promise gives that caller a stable handle instead of requiring the result immediately.

## First Principles

An operation and the code using its result can finish at different times. To compose them, the caller needs to retain the eventual outcome, register a continuation and propagate failures. Promise chaining supplies those relationships: each attachment returns a new promise for the next step.

A promise does not itself create a thread, make work cancellable or force an operation to finish. It represents the outcome; the operation's implementation determines how work progresses.

## Follow one value through two steps

```js
const source = new Promise(resolve => {
  console.log('executor');
  resolve(2);
});

const doubled = source.then(value => {
  console.log('first', value);
  return value * 2;
});

const final = doubled.then(value => {
  console.log('second', value);
  return value + 1;
});

console.log('attached');
final.then(value => console.log('result', value));
// executor → attached → first 2 → second 4 → result 5
```

The function passed to `new Promise` is its **executor**. The constructor calls it immediately with `resolve` and `reject` functions: use them to supply an outcome. Here the executor prints `executor` and resolves with `2` before the next statement runs. This constructor is useful when adapting a callback-based API; an API that already returns a promise usually needs no wrapper.

`source` already holds `2`, but its handler does not run inline when attached. Current synchronous code prints `attached` first. The first handler returns `4`, which fulfills `doubled`; the next returns `5`, which fulfills `final`.

```text
source: 2 → first handler → doubled: 4 → second handler → final: 5
```

The promise returned by `then` is different from the promise it was attached to. Follow that returned promise when reasoning about the next result or failure.

## A handler decides the next promise's outcome

| Handler behavior | Outcome of the promise returned by `then` |
| ----------------------- | ----------------------------------------- |
| Returns a value | Fulfills with that value |
| Returns another promise | Adopts that promise's eventual outcome |
| Throws | Rejects with the thrown reason |
| Returns nothing | Fulfills with `undefined` |

Starting another operation inside a handler without returning its promise detaches it from this chain. The next step can run before that operation finishes, and the chain does not own its later rejection. Use [Async/Await](10.1.3.03-async-await.md) when a linear workflow is easier to read.

Handlers run as promise jobs/microtasks, including when attached after fulfillment. The [event-loop chapter](10.1.3.01-event-loop.md) explains their relationship to tasks and rendering.

## Where does an error go?

A throw in a synchronous executor rejects its promise. A throw inside a reaction rejects the **new promise returned by that reaction's attachment**. Returning a recovery value from `catch` fulfills the subsequent chain; rethrowing preserves a rejection path.

```js
async function recover() {
  const result = await Promise.resolve('input')
    .then(() => { throw new Error('invalid'); })
    .catch(error => `fallback: ${error.message}`)
    .finally(() => console.log('cleanup'));
  console.log(result); // fallback: invalid
}
recover().catch(error => console.error(error));
```

`finally` normally passes the earlier outcome through after cleanup completes. If cleanup throws or returns a rejected promise, that failure replaces the earlier outcome. It receives no fulfillment value or rejection reason argument.

`then(onSuccess, onFailure)` handles rejection of the promise it is attached to; `onFailure` does not catch an error thrown by its sibling `onSuccess`. A later `catch` can handle that new chain rejection.

Returning the next promise matters. Starting it inside a handler without returning/awaiting it detaches its completion and rejection from that chain. Avoid `new Promise(async executor)`: the constructor does not adopt the async executor's returned promise, so a later throw can leave the outer promise pending and create an unhandled rejection.

## Which group outcome does the caller need?

These combinators observe inputs already supplied to them; they do not start functions or create a concurrency limit themselves. Calling `fetch(...)` while building the input array starts that work before the combinator is invoked.

| Combinator | Outcome policy | Empty iterable |
| ------------ | ------------------------------------------------------------------------------------------- | ---------------------------- |
| `all` | Fulfill with input-ordered values after all fulfill; reject on the first observed rejection | Fulfilled with `[]` |
| `allSettled` | Wait for every outcome and return input-ordered status records | Fulfilled with `[]` |
| `race` | Adopt the first observed settlement, fulfillment or rejection | Remains pending |
| `any` | Fulfill with the first observed fulfillment; reject with AggregateError if all reject | Rejected with AggregateError |

```js
async function compare() {
  const inputs = [Promise.resolve('account'), Promise.reject(new Error('orders unavailable'))];
  console.log((await Promise.allSettled(inputs)).map(item => item.status).join(','));
  console.log(await Promise.any(inputs)); // account
  try { await Promise.all(inputs); }
  catch (error) { console.log(error.message); } // orders unavailable
  console.log(await Promise.race([Promise.resolve('cache'), Promise.resolve('network')])); // cache
}
compare().catch(error => console.error(error));
```

Failing or winning a group does not cancel its other inputs. A timeout implemented with `race` stops the caller's wait; the underlying request may still complete. Timer cleanup and cooperative cancellation belong to [Abort & Cancellation](10.1.3.05-abort-and-cancellation.md). Retrying a rejected write can duplicate effects unless the operation's identity/protocol makes retries safe.

## Why does resolving not always mean fulfilled?

A promise is pending, fulfilled or rejected; fulfilled/rejected means **settled**. Resolving with a thenable or another promise adopts its outcome, so a resolved promise can remain pending while that outcome is unresolved. It cannot subsequently be switched to a different resolution by calling its resolving function again.

The settled outcome reference is fixed; the referenced object can still mutate. A fulfilled promise is not a deep freeze of its value. Thenable adoption also means returning an object with a callable `then` has special behavior rather than being an ordinary inert return value.

## Can simultaneous callers share one pending result?

This complete helper deduplicates **in-flight** work for the same key. It removes both successful and failed work after settlement, so it does not accidentally cache a rejection forever.

```js
function createInFlightLoader(load) {
  const pending = new Map();
  return function get(key) {
    const existing = pending.get(key);
    if (existing) return existing;
    const job = Promise.resolve().then(() => load(key)).finally(() => {
      if (pending.get(key) === job) pending.delete(key);
    });
    pending.set(key, job);
    return job;
  };
}
async function demonstrateSharing() {
  let calls = 0;
  const get = createInFlightLoader(async id => {
    calls += 1;
    return { id, name: 'Alice' };
  });
  const first = get('account:1');
  const second = get('account:1');
  console.log(first === second); // true
  console.log((await first).name); // Alice
  await get('account:1'); // previous in-flight entry was removed
  console.log(calls); // 2
}
demonstrateSharing().catch(error => console.error(error));
```

Production keys must include the identity that affects the result, such as tenant, principal and query parameters. Sharing a promise also shares its outcome object and underlying request: one caller's cancellation must not accidentally cancel required work for another. Persistent value caches additionally need freshness, eviction and invalidation rules; this helper intentionally implements none of those.

## What must the host and application handle?

Fetch rejects for request failures, not every unsuccessful HTTP status; check `response.ok` before treating a response as success and validate parsed data. A rejection reason may be any value, so code cannot assume it always has `error.message` unless it established that contract.

Handle rejection at the operation's owning boundary or return it to a caller that will. Host-level unhandled-rejection reporting is diagnostic backup, not a substitute for request cleanup or recovery. Node's behavior depends on runtime flags and installed handlers; browsers have an `unhandledrejection` event with platform-specific reporting constraints.

Start independent work concurrently only within resource limits. Concurrent I/O can reduce waiting, but CPU-bound JavaScript does not become parallel because it returns promises. For a long list, use [Bounded Concurrency](10.1.3.06-bounded-concurrency.md); storing all final results can still consume large memory even when active work is bounded.

## Summary

Follow the promise returned by each attachment and the outcome returned or thrown by its handler. Choose group semantics for the caller's failure policy, preserve operation ownership, and distinguish observing an outcome from scheduling or cancelling the work behind it.

# Async/Await

Writing `const user = await fetchUser(); const orders = await fetchOrders();` sequentially serializes independent I/O operations, forcing the user to wait for the sum of both latencies rather than the maximum. Understanding where execution suspends, how the engine desugars coroutines, and how errors propagate through return statements is critical for high-throughput JavaScript applications.

## Definition

`async` and `await` are syntactic abstractions that allow asynchronous, promise-based code to be authored and reasoned about in a synchronous, linear structure. An `async` function implicitly wraps its return value in a Promise, while the `await` expression suspends function evaluation until the awaited promise settles, resuming execution during a microtask checkpoint without blocking the host's main thread.

> **Textbook Definition:** An `async` function is an asynchronous coroutine that produces an implicit Promise resolving to its returned value. An `await` expression suspends the coroutine's evaluation, yielding control to the host caller while attaching resumption handlers to the target promise's microtask queue.

## First Principles

1. **Coroutine State Machine:** An `async` function behaves as an asynchronous coroutine. The engine compiles the function body into a state machine that can pause execution at designated suspension points (`await`) and resume with state intact when external work settles.
2. **Synchronous Execution to First Await:** An `async` function executes synchronously on the call stack from its initial statement up until the evaluation of the first `await` expression. It does not defer its initial invocation to a microtask.
3. **Implicit Promise Wrapping:** The return value of an `async` function is always coerced into a Promise via the Promise Resolution Procedure. Returning a non-promise value `T` produces a Promise fulfilled with `T`.
4. **Cooperative Main-Thread Non-Blocking:** Suspending an `async` function does not block the operating system thread or the JavaScript agent; the thread is immediately returned to the host event loop to process other macrotasks and microtasks.

```text
Caller Invocation
      │
      ▼
┌──────────────────────────────────────────────┐
│ Synchronous Execution (Statements 1..N)      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ Encounter `await targetPromise`              │
├──────────────────────────────────────────────┤
│ 1. Wrap target: Promise.resolve(target)      │
│ 2. Attach resume callback to .then()         │
│ 3. Freeze local stack frame and variables    │
│ 4. Return pending Promise to Caller          │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
Caller Continues Synchronous Work (Thread is Free)
                       │
                       ▼ (targetPromise Settles)
┌──────────────────────────────────────────────┐
│ Microtask Checkpoint: Resume Coroutine Frame │
├──────────────────────────────────────────────┤
│ Restore variables, assign result, continue   │
└──────────────────────────────────────────────┘
```

## Engine Internals: Desugaring to Generators and Promises

Under the hood, engines like V8 implement `async/await` as a generator coroutine driven by a recursive promise runner. Conceptualizing this desugaring demystifies why `await` schedules microtasks:

```javascript
// High-level conceptual desugaring of an async function
function asyncCoroRunner(generatorFactory) {
  return function (...args) {
    const iterator = generatorFactory.apply(this, args);

    return new Promise((resolve, reject) => {
      function step(verb, arg) {
        let iteration;
        try {
          iteration = iterator[verb](arg);
        } catch (syncError) {
          return reject(syncError);
        }

        if (iteration.done) {
          return resolve(iteration.value);
        }

        // Always coerce yielded values through Promise.resolve():
        Promise.resolve(iteration.value).then(
          (resolvedVal) => step('next', resolvedVal),
          (rejectionErr) => step('throw', rejectionErr)
        );
      }

      step('next'); // Kick off synchronous execution
    });
  };
}
```

Because every resumption is scheduled inside a `.then()` reaction, even awaiting a non-promise primitive (such as `await 42`) yields execution back to the caller and schedules resumption for the microtask checkpoint.

## Synchronous Entry vs. Asynchronous Continuation

Tracing call order illustrates precisely when execution yields:

```javascript
async function loadWorkflow() {
  console.log('2: Synchronous inside async function');
  const result = await 42; // Yields here! Suspends frame.
  console.log('4: Resumed inside async function with:', result);
  return result * 2;
}

console.log('1: Script start');
const workflowPromise = loadWorkflow();
console.log('3: Synchronous script continues after suspension');

workflowPromise.then((val) => {
  console.log('5: Caller receives final promise fulfillment:', val);
});

// Output:
// 1: Script start
// 2: Synchronous inside async function
// 3: Synchronous script continues after suspension
// 4: Resumed inside async function with: 42
// 5: Caller receives final promise fulfillment: 84
```

1. Statement 1 runs synchronously.
2. `loadWorkflow()` is invoked. Statements prior to the first `await` run synchronously (`2`).
3. The engine encounters `await 42`, packages `42` into a resolved promise, registers the resumption reaction, and returns a pending Promise to the caller.
4. The caller continues synchronously (`3`).
5. When the call stack clears, the microtask checkpoint runs the resumption reaction (`4`).
6. The function returns `84`, fulfilling the outer promise, which schedules its `.then()` handler (`5`).

## Concurrency Patterns: Sequential Waterfall vs. Parallel Initiation

A prevalent performance bug in asynchronous code is the inadvertent async waterfall:

```javascript
// ANTIPATTERN: Sequential Waterfall (Total duration: T_A + T_B + T_C)
async function fetchDashboardWaterfall(userId) {
  const profile = await fetchProfile(userId);     // Waits 100ms
  const preferences = await fetchPrefs(userId);    // Waits 80ms
  const notifications = await fetchNotifs(userId); // Waits 120ms
  return { profile, preferences, notifications };  // Total: 300ms
}

// OPTIMAL: Concurrent Orchestration (Total duration: max(T_A, T_B, T_C) ≈ 120ms)
async function fetchDashboardConcurrent(userId) {
  // 1. Initiate all promises concurrently (work starts immediately):
  const profilePromise = fetchProfile(userId);
  const preferencesPromise = fetchPrefs(userId);
  const notificationsPromise = fetchNotifs(userId);

  // 2. Await concurrent fulfillment:
  const [profile, preferences, notifications] = await Promise.all([
    profilePromise,
    preferencesPromise,
    notificationsPromise,
  ]);

  return { profile, preferences, notifications };
}
```

| Strategy | When to Apply | Latency Characteristics | Failure Behavior |
| :---------------------------------- | :------------------------------------------------------------ | :---------------------------- | :----------------------------------------------------------------------- |
| **Sequential `await`** | Dependent steps (Step B requires output of Step A) | Sum of latencies ($\sum T_i$) | Halts at first failure; later steps never start |
| **Concurrent `Promise.all`** | Independent operations with strict all-or-nothing requirement | Maximum latency ($\max T_i$) | Fast-fails on first rejection; unhandled requests continue in background |
| **Concurrent `Promise.allSettled`** | Independent operations where partial results are acceptable | Maximum latency ($\max T_i$) | Never throws; aggregates all fulfillments and rejections |

## Error Boundaries and the `return await` Trap

The interaction between `try/catch/finally` blocks and `return await` is one of the most misunderstood areas of JavaScript error handling.

```javascript
async function riskyOperation() {
  throw new Error('Database connection failed');
}

// CASE A: return await inside try/catch -> CATCHES ERROR
async function handleWithAwait() {
  try {
    return await riskyOperation(); // Pauses frame inside try block!
  } catch (err) {
    return 'Recovered: Default Fallback Data';
  }
}

// CASE B: return without await inside try/catch -> MISSES LOCAL CATCH!
async function handleWithoutAwait() {
  try {
    return riskyOperation(); // Returns pending promise and exits try immediately!
  } catch (err) {
    return 'Never Reached!'; // The error rejects outside this function's scope!
  }
}
```

- In **Case A**, `return await` suspends the coroutine while still inside the `try` block. When `riskyOperation` rejects, the exception throws directly into the local `catch` handler, allowing successful recovery.
- In **Case B**, `return riskyOperation()` returns the rejected Promise object immediately. The function exits the `try` block before the promise settles. The rejection bypasses the local `catch` block entirely and rejects the promise returned by `handleWithoutAwait`.

> [!TIP]
> Always use `return await` when wrapping an asynchronous call inside a `try/catch` block if you want the local `catch` or `finally` blocks to intercept rejections. Modern JavaScript engines (V8 v7.3+) provide zero-cost async stack traces and do not incur performance penalties for `return await`.

## Runtime Validation of Awaited Payloads

TypeScript annotations on async functions do not validate incoming data over network boundaries. Senior engineers validate the runtime schema before casting:

```typescript
type UserAccount = {
  id: string;
  email: string;
  role: 'admin' | 'member';
};

function isUserAccount(val: unknown): val is UserAccount {
  return (
    typeof val === 'object' &&
    val !== null &&
    'id' in val &&
    typeof (val as Record<string, unknown>).id === 'string' &&
    'email' in val &&
    typeof (val as Record<string, unknown>).email === 'string' &&
    'role' in val &&
    ['admin', 'member'].includes((val as Record<string, unknown>).role as string)
  );
}

async function fetchUserSafe(userId: string, signal?: AbortSignal): Promise<UserAccount> {
  const response = await fetch(`/api/users/${encodeURIComponent(userId)}`, { signal });

  if (!response.ok) {
    throw new Error(`HTTP error ${response.status}: ${response.statusText}`);
  }

  const payload: unknown = await response.json();

  if (!isUserAccount(payload)) {
    throw new TypeError(`Malformatted payload received for user ${userId}`);
  }

  return payload; // Narrowed safely to UserAccount
}
```

## Asynchronous Iteration (`for await...of`)

Asynchronous iterables implement the `Symbol.asyncIterator` protocol, allowing consumers to process streaming chunks or paginated records sequentially:

```javascript
async function* paginatedFetcher(endpoint) {
  let nextPageUrl = endpoint;

  while (nextPageUrl) {
    const res = await fetch(nextPageUrl);
    const data = await res.json();
    nextPageUrl = data.nextCursor ? `${endpoint}?cursor=${data.nextCursor}` : null;
    yield data.items; // Yields an array of items per page
  }
}

async function consumePages() {
  for await (const pageItems of paginatedFetcher('/api/logs')) {
    console.log(`Processing page batch of ${pageItems.length} records`);
    if (pageItems.length === 0) break; // Clean early termination invokes iterator.return()
  }
}
```

## Distributed Systems Caveat: Async Is Not Atomic

A sequence of consecutive `await` statements does not constitute an ACID transaction:

```javascript
async function checkout(orderId, userId, amount) {
  await debitBalance(userId, amount); // Step 1: Deducts money
  await reserveInventory(orderId);     // Step 2: If this network call crashes...
  await sendReceiptEmail(userId);      // Money is gone, but inventory was not reserved!
}
```

Because other network traffic and event loop ticks interleave between each `await`, distributed architectures must employ compensating transactions (the Saga pattern), database two-phase commit, or transactional outboxes with idempotency keys to handle partial failures gracefully.

## Summary

`async/await` transforms asynchronous workflows into readable coroutines compiled down to generator-like state machines and Promise reactions. The function executes synchronously until the first `await`, returning an implicit promise to the caller while suspending its local frame. Parallelizing independent operations prevents waterfall latency penalties, while `return await` ensures local `try/catch` error boundaries intercept asynchronous rejections reliably.

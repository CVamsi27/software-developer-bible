# Async/Await

A dashboard loads a profile and preferences for the same known user ID. Calling the second only after awaiting the first prevents overlap even though neither needs the other's result. If an operation really needs the returned user ID, the dependency must stay sequential.

```javascript
// Sequential: independent waits accumulate
const profile = await fetchProfile(userId);
const preferences = await fetchPrefs(userId);

// Concurrent: same inputs and work, initiated together
const [profile2, preferences2] = await Promise.all([
  fetchProfile(userId), fetchPrefs(userId),
]);
```

## Definition

**`async`/`await`** lets promise-based code read like linear synchronous code. An `async` function wraps its return value in an implicit Promise; `await` suspends evaluation until the awaited promise settles, resuming at a microtask checkpoint without blocking the host thread.

> **Textbook Definition:** An `async` function is an asynchronous coroutine that produces an implicit Promise resolving to its returned value. An `await` expression suspends the coroutine's evaluation, yielding control to the host caller while arranging promise-job continuations through the host's microtask machinery.

## First Principles

An `async` function is a **coroutine state machine**: it pauses at `await` points and resumes with locals intact when external work settles. It runs **synchronously up to the first `await`** — invocation never defers to a microtask. Its return always coerces through the Promise Resolution Procedure, so a plain value `T` becomes a promise fulfilled with `T`. Suspension releases this evaluation so its caller can continue. It does not guarantee the host runs another task or paints; synchronous work before an await and after resumption still occupies the agent.

```text
Caller Invocation
      │
      ▼
┌──────────────────────────────────────────────┐
│ Synchronous Execution (Statements 1..N)      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ Encounter `await targetPromise`              │
├──────────────────────────────────────────────┤
│ 1. Adopt target through promise operations   │
│ 2. Arrange continuation jobs                 │
│ 3. Preserve suspended evaluation state       │
│ 4. Return pending Promise to Caller          │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
Caller Continues Synchronous Work (Agent is still occupied)
                       │
                       ▼ (targetPromise Settles)
┌──────────────────────────────────────────────┐
│ Microtask Checkpoint: Resume Coroutine Frame │
├──────────────────────────────────────────────┤
│ Restore variables, assign result, continue   │
└──────────────────────────────────────────────┘
```

## 1. A Conceptual Generator Runner

A generator runner makes suspension and rejection propagation visible. This is a teaching analogy, not V8's literal implementation or a complete substitute for native async semantics. Native `await` uses specification promise operations; engines optimize representation independently:

```javascript
// High-level conceptual desugaring of an async function
function asyncCoroRunner(generatorFactory) {
  return function (...args) {
    const iterator = generatorFactory.apply(this, args);

    return new Promise((resolve, reject) => {
      function step(verb, arg) {
        let iteration;
        try {
          iteration = iterator[verb](arg);
        } catch (syncError) {
          return reject(syncError);
        }

        if (iteration.done) {
          return resolve(iteration.value);
        }

        // Always coerce yielded values through Promise.resolve():
        Promise.resolve(iteration.value).then(
          (resolvedVal) => step('next', resolvedVal),
          (rejectionErr) => step('throw', rejectionErr)
        );
      }

      step('next'); // Kick off synchronous execution
    });
  };
}
```

In this model, the runner resumes from a reaction. Native `await` also schedules continuation through promise jobs, so even `await 42` resumes after the caller's current synchronous work. It need not call a user-overridden `.then` on a native promise.

## 2. Synchronous Entry vs. Asynchronous Continuation

```javascript
async function loadWorkflow() {
  console.log('2: Synchronous inside async function');
  const result = await 42; // Yields here! Suspends frame.
  console.log('4: Resumed inside async function with:', result);
  return result * 2;
}

console.log('1: Script start');
const workflowPromise = loadWorkflow();
console.log('3: Synchronous script continues after suspension');

workflowPromise.then((val) => {
  console.log('5: Caller receives final promise fulfillment:', val);
});

// Output:
// 1: Script start
// 2: Synchronous inside async function
// 3: Synchronous script continues after suspension
// 4: Resumed inside async function with: 42
// 5: Caller receives final promise fulfillment: 84
```

The call runs synchronously through `2`, then `await 42` wraps the value, registers resumption, and hands a pending promise back — so the caller prints `3` before the checkpoint resumes at `4` and fulfills with `84` at `5`.

## 3. Concurrency Patterns: Sequential Waterfall vs. Parallel Initiation

The most common async performance bug is the inadvertent waterfall:

```javascript
// ANTIPATTERN: Sequential Waterfall (Total duration: T_A + T_B + T_C)
async function fetchDashboardWaterfall(userId) {
  const profile = await fetchProfile(userId);     // Waits 100ms
  const preferences = await fetchPrefs(userId);    // Waits 80ms
  const notifications = await fetchNotifs(userId); // Waits 120ms
  return { profile, preferences, notifications };  // Total: 300ms
}

// Concurrent initiation: waits can overlap (illustrative durations above)
async function fetchDashboardConcurrent(userId) {
  // 1. Initiate all promises concurrently (work starts immediately):
  const profilePromise = fetchProfile(userId);
  const preferencesPromise = fetchPrefs(userId);
  const notificationsPromise = fetchNotifs(userId);

  // 2. Await concurrent fulfillment:
  const [profile, preferences, notifications] = await Promise.all([
    profilePromise,
    preferencesPromise,
    notificationsPromise,
  ]);

  return { profile, preferences, notifications };
}
```

These latency formulas describe ideal overlapping waits, not guaranteed elapsed time; CPU work, connection limits and downstream contention can change the result.

| Strategy | When to Apply | Latency Characteristics | Failure Behavior |
| :---------------------------------- | :------------------------------------------------------------ | :---------------------------- | :--------------------------------------------------------------------------------- |
| **Sequential `await`** | Dependent steps (Step B requires output of Step A) | Sum of latencies ($\sum T_i$) | Halts at first failure; later steps never start |
| **Concurrent `Promise.all`** | Independent operations with strict all-or-nothing requirement | Maximum latency ($\max T_i$) | Rejects on observed failure; other operations continue unless separately cancelled |
| **Concurrent `Promise.allSettled`** | Independent operations where partial results are acceptable | Maximum latency ($\max T_i$) | Records ordinary input outcomes; invalid iteration can still reject |

## 4. Error Boundaries and the `return await` Trap

```javascript
async function riskyOperation() {
  throw new Error('Database connection failed');
}

// CASE A: return await inside try/catch -> CATCHES ERROR
async function handleWithAwait() {
  try {
    return await riskyOperation(); // Pauses frame inside try block!
  } catch (err) {
    return 'Recovered: Default Fallback Data';
  }
}

// CASE B: return without await inside try/catch -> MISSES LOCAL CATCH!
async function handleWithoutAwait() {
  try {
    return riskyOperation(); // Adopts its promise and exits this try!
  } catch (err) {
    return 'Never Reached!'; // The error rejects outside this function's scope!
  }
}
```

**Case A** suspends inside the `try`, so the rejection throws into the local `catch`. **Case B** adopts the returned promise without awaiting inside the `try`, so its rejection bypasses the local handler. This holds even if that returned promise is already rejected; a direct synchronous throw from a non-async callee would be a different case. **Rule**: use `return await` inside `try/catch` when local handlers must see rejections. Modern engines optimize native await, so removing it solely because of old extra-microtask folklore is not a sound rule. Stack traces and performance depend on runtime and workload; choose the needed error boundary and measure material costs.

## 5. Runtime Validation of Awaited Payloads

TypeScript types vanish at the network boundary — validate schemas before casting:

```typescript
type UserAccount = {
  id: string;
  email: string;
  role: 'admin' | 'member';
};

function isUserAccount(val: unknown): val is UserAccount {
  return (
    typeof val === 'object' &&
    val !== null &&
    'id' in val &&
    typeof (val as Record<string, unknown>).id === 'string' &&
    'email' in val &&
    typeof (val as Record<string, unknown>).email === 'string' &&
    'role' in val &&
    ['admin', 'member'].includes((val as Record<string, unknown>).role as string)
  );
}

async function fetchUserSafe(userId: string, signal?: AbortSignal): Promise<UserAccount> {
  const response = await fetch(`/api/users/${encodeURIComponent(userId)}`, { signal });

  if (!response.ok) {
    throw new Error(`HTTP error ${response.status}: ${response.statusText}`);
  }

  const payload: unknown = await response.json();

  if (!isUserAccount(payload)) {
    throw new TypeError(`Malformatted payload received for user ${userId}`);
  }

  return payload; // Narrowed safely to UserAccount
}
```

## 6. Asynchronous Iteration (`for await...of`)

Async iterables (`Symbol.asyncIterator`) stream pages or chunks sequentially:

```javascript
async function* paginatedFetcher(endpoint) {
  let nextPageUrl = endpoint;

  while (nextPageUrl) {
    const res = await fetch(nextPageUrl);
    const data = await res.json();
    nextPageUrl = data.nextCursor ? `${endpoint}?cursor=${data.nextCursor}` : null;
    yield data.items; // Yields an array of items per page
  }
}

async function consumePages() {
  for await (const pageItems of paginatedFetcher('/api/logs')) {
    console.log(`Processing page batch of ${pageItems.length} records`);
    if (pageItems.length === 0) break; // Clean early termination invokes iterator.return()
  }
}
```

## 7. Distributed Systems Caveat: Async Is Not Atomic

Consecutive `await`s are not a transaction — other traffic interleaves between them:

```javascript
async function checkout(orderId, userId, amount) {
  await debitBalance(userId, amount); // Step 1: Deducts money
  await reserveInventory(orderId);     // Step 2: If this network call crashes...
  await sendReceiptEmail(userId);      // Money is gone, but inventory was not reserved!
}
```

Partial failure leaves money debited with no reservation. Choose a transaction within one supported authority, or coordinate durable state, idempotent effects and compensation across boundaries. An outbox couples local state with an event intent; it cannot by itself undo an already completed external debit. See the [transaction patterns](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.06-idempotency-retry-deep-dive.md) for the canonical mechanisms.

## Summary

`async`/`await` preserves suspended evaluation state and resumes through promise jobs; a generator runner is a useful analogy rather than a portable engine implementation. Functions run synchronously to the first `await`, then suspend without blocking the thread. Parallelize independent calls to avoid waterfall latency, use `return await` so local `try/catch` sees rejections, validate network payloads at runtime, and never mistake consecutive awaits for an atomic transaction.

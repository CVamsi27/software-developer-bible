# Async/Await

## Definition

An `async` function returns a promise representing its eventual outcome. `await` suspends that function's evaluation and later resumes it with a fulfilled value or throws the rejection into it. It does not block the calling thread, cancel the operation, or automatically move computation elsewhere.

## First Principles

A workflow often needs one result before it can perform the next step. Representing those dependencies with promises is sufficient, but linear `try`, `catch`, loops and local variables can make the workflow easier to follow. Async functions provide that control flow while retaining promise outcomes for their callers. Suspension is a boundary: other work may run before the function resumes, so shared state may have changed.

## Where does execution pause?

```js
async function load() {
  console.log('load starts');
  const value = await 7;
  console.log('load resumes', value);
  return value * 2;
}
console.log('caller starts');
const result = load();
console.log('caller continues');
result.then(value => console.log('result', value));
// caller starts → load starts → caller continues → load resumes 7 → result 14
```

```text
caller invokes load
  → load runs synchronously to await
  → caller gets a promise and continues
  → await continuation runs later as a promise job
  → load returns 14; its promise fulfills
  → caller's reaction receives 14
```

Even awaiting a non-promise value suspends continuation; it is not a guaranteed opportunity for a browser paint or another task. A long chain of microtasks can still starve rendering. CPU-heavy code before or after an await still runs on the executing thread.

## Does sequential syntax imply sequential work?

The start time is determined by **calling the operation**, not by the later await. `await fetchA(); await fetchB();` starts B after A completes; saving both promises before awaiting means both have already started. Attach group observation promptly so an early rejection is owned.

```js
async function demonstrate() {
  const events = [];
  function start(name) {
    events.push(`start ${name}`);
    return Promise.resolve(name);
  }

  const a = await start('A');
  const b = await start('B');
  console.log(events.join(',')); // start A,start B

  events.length = 0;
  const group = Promise.all([start('C'), start('D')]);
  events.push('both started');
  const [c, d] = await group;
  console.log(events.join(',')); // start C,start D,both started
  console.log([a, b, c, d].join(',')); // A,B,C,D
}
demonstrate().catch(error => console.error(error));
```

The example exposes call order, not a timing benchmark: its operations settle immediately. For independently progressing I/O, concurrency can overlap waiting. For dependent work, ordered writes or constrained resources, serial execution may be correct. Use [Bounded Concurrency](10.1.3.06-bounded-concurrency.md) for large workloads instead of an unbounded `items.map` plus `Promise.all`.

## Which failures reach a local catch?

Await a promise **inside** the try when its later rejection must reach that catch. Merely returning the promise exits the try before the eventual rejection occurs.

```js
async function rejection() { throw new Error('failed'); }
async function observed() {
  try { return await rejection(); }
  catch (error) { return `recovered ${error.message}`; }
}
async function returned() {
  try { return rejection(); }
  catch { return 'not reached'; }
}
async function demonstrateErrors() {
  console.log(await observed()); // recovered failed
  try { await returned(); }
  catch (error) { console.log(error.message); } // failed
}
demonstrateErrors().catch(error => console.error(error));
```

A synchronous throw inside the try is caught as usual. A detached promise needs its own owner/handler. Avoid swallowing an error into `undefined` unless that is the declared result contract. `finally` runs on exits, but a failing cleanup can replace the earlier error/result; asynchronous cleanup must itself be awaited when completion matters.

Returning an existing promise from an async function adopts its outcome but normally produces a different promise identity. This matters for deduplication APIs whose callers intentionally compare handles. Using `.then` alongside await can be reasonable for a deliberate transformation; a blanket ban on mixing syntax is not a correctness rule.

## Awaiting HTTP success still requires validation

This complete helper is intended for a browser application with `/api/users/:id`. The endpoint owns authorization; the client checks status and runtime response shape before exposing a typed result.

```ts
type User = { id: string; name: string };

async function loadUser(id: string, signal?: AbortSignal): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`, { signal });
  if (!response.ok) throw new Error(`User request failed: ${response.status}`);
  const data: unknown = await response.json();
  if (typeof data !== 'object' || data === null ||
      !('id' in data) || typeof data.id !== 'string' ||
      !('name' in data) || typeof data.name !== 'string') {
    throw new TypeError('Invalid user response');
  }
  if (data.id !== id) throw new TypeError('Unexpected user identity');
  return { id: data.id, name: data.name };
}
```

An annotation on `response.json()` alone does not validate the payload. A schema library such as Zod can own richer validation. Passing an AbortSignal enables supported cooperative cancellation; wrapping a promise to suppress its resolution leaves awaiters hanging and does not stop underlying work.

In React, a component effect also needs cleanup and a policy for obsolete results when the requested identity changes. The [effect chapter](../../10.3-react/02-core-hooks/10.3.2.02-useeffect.md) owns that lifecycle; a bare `await` does not prevent stale UI updates.

## How does await control an iterator's lifecycle?

`for await...of` consumes asynchronous iterables (and can adapt synchronous ones). Breaking normally calls the iterator's return/cleanup path and awaits it. The iterator must still implement resource cleanup; abandoning an unrelated promise is a different operation.

```js
async function* values() {
  try {
    for (let i = 0; i < 3; i += 1) yield i;
  } finally {
    console.log('iterator closed');
  }
}
async function consume() {
  for await (const value of values()) {
    console.log(value);
    if (value === 1) break;
  }
}
consume().catch(error => console.error(error));
// 0 → 1 → iterator closed
```

See [Generators](../05-functional-patterns/10.1.5.03-generators.md) for the protocol and [Abort & Cancellation](10.1.3.05-abort-and-cancellation.md) for signal-driven resource ownership.

## What does await not make atomic?

Creating an order, decrementing inventory and sending email in successive awaits does not make one transaction. A failure can leave earlier steps committed. Database transactions protect their supported database operations; an outbox can persist notification intent with the business change, and a worker delivers it with retry/idempotency. See [Transactional Outbox](../../../30-architecture/30.2-system-design/01-theory/30.2.1.18-outbox-and-cdc.md) for the actual mechanism.

Likewise, `await next()` only surrounds downstream work if the middleware contract returns a promise for it. Express's `next()` is not that promise contract; async onion middleware and Express middleware must not be conflated. Authentication requires verifying the credential and authorization policy, not just checking whether a header exists.

Top-level await belongs to modules and affects their evaluation/dependants; it is not allowed in an ordinary classic script. Async stack traces can connect continuations for debugging, but their detail varies by runtime and tooling. Preserve operation/request identities in logs rather than assuming every detached path will retain a complete logical stack.

## Summary

Find when each operation starts, which promise owns its outcome, and where an await resumes the workflow. Await provides sequencing and local rejection handling; resource limits, stale results, cancellation, transaction boundaries and external effects still need explicit mechanisms.

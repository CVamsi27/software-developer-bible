# Error Handling

A `fetch` that receives HTTP 500 still *fulfills*: an HTTP response arrived. It might even contain valid JSON, so parsing alone cannot detect the status failure. Robust code checks status, validates the payload and preserves the original cause when translating a failure.

```javascript
try {
  const res = await fetch('/api/orders');
  if (!res.ok) throw new NetworkHttpError(res.status, res.statusText);
  return await res.json();
} catch (err) {
  throw new DomainError('Order load failed', { cause: err });
}
```

## Definition

**Error handling** is the practice of detecting, isolating, translating, and recovering from exceptional states and predictable domain failures. JavaScript unwinds sync stacks via `throw`/`try`/`catch`/`finally`, signals async failure via promise rejections, and monitors process-level crashes through host hooks.

> **Textbook Definition:** Error handling defines the structured mechanisms by which a runtime responds to abnormal program termination. JavaScript coordinates synchronous unwinding across execution contexts with asynchronous microtask rejection propagation, preserving diagnostic context through chained causes and enforcing cleanup through guaranteed control-flow exit handlers.

## First Principles

Sync exceptions unwind the current stack immediately; async work spans event-loop turns and must travel through rejection reactions instead. Expected domain states (bad input) are ordinary data — best modeled as Result types — while unexpected invariant failures need an explicit safe boundary. Some failures, including a killed process or certain out-of-memory conditions, never reach a JavaScript catch. Wrapping errors must preserve the root cause, which ES2022's `Error.cause` provides. And `finally` runs on ordinary control-flow exits through its block, rather than guaranteeing cleanup after process termination or an evaluation that never exits — but a `return`/`throw` inside `finally` irrevocably overrides prior outcomes.

```text
┌────────────────────────────┐
│ Incoming Operation Failure │
└────────────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
     [Expected Domain Error]     [Catastrophic Fault]
     (e.g., Invalid form input)   (e.g., Failed invariant)
              │                           │
              ▼                           ▼
     Return Discriminated         Throw Error / Reject
     Result<T, E> Object          Unwind to Safe Boundary
              │                           │
              ▼                           ▼
     Linear Business Handling     Log Context + Fallback UI
```

## 1. Built-In Error Hierarchy and Custom Error Architecture

| Error Type | Primary Trigger | Common Engineering Example |
| :------------------- | :------------------------------------ | :----------------------------------------------------------- |
| **`Error`** | Generic base exception | Custom application-level domain errors |
| **`TypeError`** | Value is not of expected type | Calling non-function, reading property of `null`/`undefined` |
| **`RangeError`** | Numeric value outside allowable range | Array length out of bounds, recursive stack overflow |
| **`SyntaxError`** | Engine parsing invalid code | `JSON.parse('{ invalid json }')` |
| **`ReferenceError`** | Dereferencing undeclared identifier | Accessing variable in Temporal Dead Zone (TDZ) |
| **`AggregateError`** | Multiple errors bundled together | `Promise.any` when all input promises reject |

Custom errors can carry machine-readable codes, candidate transient flags and trimmed stacks (`Error.captureStackTrace` on V8/Node removes framework frames from user logs):

```typescript
export class DomainError extends Error {
  public readonly code: string;
  public readonly isTransient: boolean;

  constructor(
    message: string,
    options?: { code?: string; isTransient?: boolean; cause?: unknown }
  ) {
    super(message, { cause: options?.cause });
    this.name = this.constructor.name;
    this.code = options?.code ?? 'INTERNAL_ERROR';
    this.isTransient = options?.isTransient ?? false; // Hint, not permission to repeat a write

    // V8-specific stack trace sanitization: removes constructor frame
    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, this.constructor);
    }
  }
}

export class NetworkHttpError extends DomainError {
  constructor(public readonly status: number, statusText: string, cause?: unknown) {
    super(`HTTP ${status}: ${statusText}`, {
      code: `HTTP_${status}`,
      isTransient: status >= 500 || status === 429, // Broad hint; endpoint policy decides
      cause,
    });
  }
}
```

## 2. Throwing Exceptions vs. Result Type Unions

Throwing for expected domain failures hides control flow from the type system. Discriminated-union Results make errors inspectable data:

```typescript
export type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

// Syntax validation only: the parsed shape is still unknown.
export function parseJsonSafe(jsonString: string): Result<unknown, SyntaxError> {
  try {
    const parsed: unknown = JSON.parse(jsonString);
    return { ok: true, value: parsed };
  } catch (err) {
    if (err instanceof SyntaxError) return { ok: false, error: err };
    throw err;
  }
}

export type ThemeConfig = { theme: 'dark' | 'light' };
export function decodeThemeConfig(value: unknown): ThemeConfig {
  if (typeof value !== 'object' || value === null || !('theme' in value) ||
      (value.theme !== 'dark' && value.theme !== 'light')) {
    throw new TypeError('Expected a dark or light theme');
  }
  return { theme: value.theme };
}

const outcome = parseJsonSafe('{"theme": "dark"}');
if (outcome.ok) {
  const config = decodeThemeConfig(outcome.value); // Separate shape validation
  console.log('Parsed theme:', config.theme);
} else {
  console.error('Invalid JSON syntax:', outcome.error.message);
}
```

A Result makes the success/failure branches available for narrowing; TypeScript does not force every caller to inspect both. Parsing checks JSON syntax, while a decoder or schema validator checks the domain shape. The decoder may itself reject a syntactically valid payload.

## 3. The Traps of `finally` Control Flow

`finally` runs when ordinary control flow exits its associated `try`/`catch`; it cannot promise cleanup after a killed process or a loop that never exits. Control-flow statements inside it can mask whatever came before:

```javascript
// DANGEROUS: return inside finally swallows thrown errors!
function dangerousSwallow() {
  try {
    throw new Error('Critical database corruption!');
  } finally {
    return 'Everything is fine'; // SILENTLY SUPPRESSES ERROR!
  }
}

console.log(dangerousSwallow()); // "Everything is fine" (Error vanished!)
```

> [!WARNING]
> Never execute `return`, `throw`, `break`, or `continue` inside a `finally` block unless the explicit architectural intention is to override and discard all prior exceptions and return values.

## 4. Context Preservation with `Error.cause`

Translate low-level errors into domain errors without severing diagnostics (ES2022):

```typescript
async function processOrderPayment(orderId: string, amount: number): Promise<void> {
  try {
    await paymentGateway.charge(orderId, amount);
  } catch (originalError) {
    // Preserve root cause for telemetry and debugging:
    throw new DomainError(`Payment processing failed for order ${orderId}`, {
      code: 'PAYMENT_FAILED',
      cause: originalError,
    });
  }
}
```

Log aggregators then render the full chain: `DomainError: Payment processing failed` → `Caused by: NetworkHttpError: HTTP 504 Gateway Timeout` → `Caused by: SocketError: Connection reset by peer`.

## 5. Separate Read Failures from Retry Policy

`fetch()` usually rejects for transport, request-setup or cancellation failures; HTTP 4xx/5xx responses fulfill and need status inspection. A malformed JSON response is a parsing failure, and a schema mismatch is a validation failure. Neither is automatically transient. Cancellation must preserve the caller's reason rather than start another attempt.

This helper performs **one read-only GET**, checks HTTP status and passes an unknown payload to the caller's decoder. It deliberately makes no retry decision:

```typescript
export async function fetchJsonRead<T>(
  url: string,
  decode: (payload: unknown) => T,
  signal?: AbortSignal
): Promise<T> {
  signal?.throwIfAborted();
  const response = await fetch(url, { method: 'GET', signal });
  if (!response.ok) {
    if (response.body) {
      // Release an unread error body; keep the HTTP failure as the outcome.
      await response.body.cancel().catch(() => {});
    }
    signal?.throwIfAborted();
    throw new NetworkHttpError(response.status, response.statusText);
  }
  const payload: unknown = await response.json();
  signal?.throwIfAborted();
  return decode(payload);
}
```

Use it only with an endpoint whose GET contract is read-only. The decoder owns runtime schema validation; this helper does not impose a response byte limit. See [Retry Patterns](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.02-retry-patterns.md) for the single canonical bounded read retry implementation: classified outcomes, an overall deadline, attempt budget, server hints and jitter. Writes additionally require a stable operation identity and reconciliation of uncertain outcomes; see [Idempotency & Retry](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.06-idempotency-retry-deep-dive.md).

## 6. Global Unhandled Failure Handlers: Node.js vs Browser

Escaped failures land on host-level hooks:

```text
Browser Environment:
  ├── window.onerror               (Synchronous script exceptions)
  └── window.onunhandledrejection  (Uncaught Promise rejections)

Node.js Environment:
  ├── process.on('uncaughtException')       (Fatal synchronous crashes)
  ├── process.on('uncaughtExceptionMonitor')(Audit crash without stopping exit)
  └── process.on('unhandledRejection')      (Uncaught Promise rejections)
```

An uncaught exception is a crash boundary, not a recovery loop. For Node, a monitor can record it without suppressing the default crash. Configure rejection policy deliberately (for example, `--unhandled-rejections=strict` when the process should crash on an unhandled rejection):

```javascript
// Node.js process safety configuration
process.on('uncaughtExceptionMonitor', (err, origin) => {
  // Use a sink that completes synchronously; crash-time async flush may be lost.
  crashLogger.writeSync({ err, origin });
});

// No uncaughtException/unhandledRejection listener suppresses default policy.
// Arrange process restart and service recovery through the supervisor.
```

## Summary

Model expected failures as Result unions and exceptional faults as thrown errors with `Error.cause` chains. Never steer control flow from inside `finally`. Classify HTTP statuses explicitly — `fetch` fulfills on 4xx/5xx — and distinguish syntax, schema, cancellation and transport outcomes. A read helper supplies one validated result; the canonical retry policy owns repeated attempts. Reserve global handlers for telemetry and deliberate crash policy.

# Error Handling

An HTTP request that returns a `500 Internal Server Error` fulfills its promise because network communication succeeded, yet passing this payload to a parser triggers a runtime exception. Robust systems establish explicit failure boundaries, categorize errors into transient versus permanent faults, and preserve root-cause diagnostic chains.

## Definition

**Error handling** is the architectural practice of detecting, isolating, translating, and recovering from exceptional runtime states and predictable domain failures. JavaScript provides synchronous stack unwinding via `throw` and `try/catch/finally`, asynchronous rejection signaling via Promises, and process-level crash monitors.

> **Textbook Definition:** Error handling defines the structured mechanisms by which a runtime responds to abnormal program termination. JavaScript coordinates synchronous unwinding across execution contexts with asynchronous microtask rejection propagation, preserving diagnostic context through chained causes and enforcing cleanup through guaranteed control-flow exit handlers.

## First Principles

1. **Failure Channel Separation:** Synchronous exceptions unwind the current execution stack immediately. Asynchronous operations execute across distinct event loop turns and must channel failures through promise rejection reactions rather than enclosing call stacks.
2. **Predictable Domain States vs. Exceptional Failures:** Expected validation errors (e.g. malformed inputs) are regular domain data best represented as explicit Result types. Unrecoverable defects (e.g. missing memory, syntax bugs) should throw to halt invalid execution paths.
3. **Causal Chain Preservation:** Wrapping low-level errors into domain-specific exceptions must never erase original root-cause telemetry. The ES2022 `Error.cause` property provides an unbroken diagnostic lineage.
4. **Clean Exit Invariant:** `finally` blocks guarantee cleanup execution upon any exit path (normal return, thrown exception, or early break), but return or throw statements inside `finally` irrevocably override prior return values and unhandled exceptions.

```text
┌────────────────────────────────────────────────────────┐
│ Incoming Operation Failure                             │
└──────────────────────────┬─────────────────────────────┘
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
    [Expected Domain Error]     [Catastrophic Fault]
    (e.g., Invalid form input)   (e.g., Corrupt heap, OOM)
             │                           │
             ▼                           ▼
    Return Discriminated         Throw Error / Reject
    Result<T, E> Object          Unwind to Safe Boundary
             │                           │
             ▼                           ▼
    Linear Business Handling     Log Context + Fallback UI
```

## Built-In Error Hierarchy and Custom Error Architecture

JavaScript defines a base `Error` class and specialized native subclasses:

| Error Type | Primary Trigger | Common Engineering Example |
| :------------------- | :------------------------------------ | :----------------------------------------------------------- |
| **`Error`** | Generic base exception | Custom application-level domain errors |
| **`TypeError`** | Value is not of expected type | Calling non-function, reading property of `null`/`undefined` |
| **`RangeError`** | Numeric value outside allowable range | Array length out of bounds, recursive stack overflow |
| **`SyntaxError`** | Engine parsing invalid code | `JSON.parse('{ invalid json }')` |
| **`ReferenceError`** | Dereferencing undeclared identifier | Accessing variable in Temporal Dead Zone (TDZ) |
| **`AggregateError`** | Multiple errors bundled together | `Promise.any` when all input promises reject |

### Production Custom Error Class with Stack Trimming

When authoring custom errors, use `Error.captureStackTrace` (supported in V8 and Node.js) to trim internal framework frames from user logs:

```typescript
export class DomainError extends Error {
  public readonly code: string;
  public readonly isTransient: boolean;

  constructor(
    message: string,
    options?: { code?: string; isTransient?: boolean; cause?: unknown }
  ) {
    super(message, { cause: options?.cause });
    this.name = this.constructor.name;
    this.code = options?.code ?? 'INTERNAL_ERROR';
    this.isTransient = options?.isTransient ?? false;

    // V8-specific stack trace sanitization: removes constructor frame
    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, this.constructor);
    }
  }
}

export class NetworkHttpError extends DomainError {
  constructor(public readonly status: number, statusText: string, cause?: unknown) {
    super(`HTTP ${status}: ${statusText}`, {
      code: `HTTP_${status}`,
      isTransient: status >= 500 || status === 429,
      cause,
    });
  }
}
```

## Throwing Exceptions vs. Result Type Unions

Throwing exceptions for expected domain failures introduces hidden control-flow jumps that defeat type safety. Using discriminated union Result types converts errors into inspectable data:

```typescript
export type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

export function parseJsonSafe<T>(jsonString: string): Result<T, SyntaxError> {
  try {
    const parsed = JSON.parse(jsonString) as T;
    return { ok: true, value: parsed };
  } catch (err) {
    if (err instanceof SyntaxError) {
      return { ok: false, error: err };
    }
    throw err; // Re-throw truly unexpected internal engine faults
  }
}

// Caller usage: Forced compile-time handling of both branches
const outcome = parseJsonSafe<{ theme: string }>('{"theme": "dark"}');
if (outcome.ok) {
  console.log('Parsed theme:', outcome.value.theme);
} else {
  console.error('Configuration corrupted:', outcome.error.message);
}
```

## The Traps of `finally` Control Flow

A `finally` block executes regardless of whether the `try` block completed normally or threw an exception. However, altering control flow inside `finally` masks errors:

```javascript
// DANGEROUS: return inside finally swallows thrown errors!
function dangerousSwallow() {
  try {
    throw new Error('Critical database corruption!');
  } finally {
    return 'Everything is fine'; // SILENTLY SUPPRESSES ERROR!
  }
}

console.log(dangerousSwallow()); // "Everything is fine" (Error vanished!)
```

> [!WARNING]
> Never execute `return`, `throw`, `break`, or `continue` inside a `finally` block unless the explicit architectural intention is to override and discard all prior exceptions and return values.

## Context Preservation with `Error.cause`

When translating low-level transport errors into high-level business errors, retain the original error in the `cause` option (ES2022 standard):

```typescript
async function processOrderPayment(orderId: string, amount: number): Promise<void> {
  try {
    await paymentGateway.charge(orderId, amount);
  } catch (originalError) {
    // Preserve root cause for telemetry and debugging:
    throw new DomainError(`Payment processing failed for order ${orderId}`, {
      code: 'PAYMENT_FAILED',
      cause: originalError,
    });
  }
}
```

In modern logging aggregators, inspecting `error.cause` uncovers the full nested chain:
`DomainError: Payment processing failed` → `Caused by: NetworkHttpError: HTTP 504 Gateway Timeout` → `Caused by: SocketError: Connection reset by peer`.

## Network Failure Classification and Retries

Calling `fetch()` only rejects on catastrophic network failures (DNS failure, network loss, CORS rejection, or request abort). It fulfills successfully for HTTP 4xx and 5xx status codes:

```typescript
async function fetchWithRetry<T>(
  url: string,
  options: RequestInit & { maxRetries?: number; baseDelayMs?: number } = {}
): Promise<T> {
  const { maxRetries = 3, baseDelayMs = 200, ...fetchOpts } = options;

  let attempt = 0;
  while (true) {
    try {
      const response = await fetch(url, fetchOpts);

      if (!response.ok) {
        throw new NetworkHttpError(response.status, response.statusText);
      }

      return (await response.json()) as T;
    } catch (err) {
      attempt++;
      const isTransient = err instanceof NetworkHttpError ? err.isTransient : true;

      if (attempt > maxRetries || !isTransient) {
        throw new DomainError(`Operation exhausted retries (${attempt}/${maxRetries})`, {
          cause: err,
        });
      }

      // Exponential backoff with full jitter to prevent thundering herds
      const delay = Math.random() * (baseDelayMs * 2 ** (attempt - 1));
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
}
```

## Global Unhandled Failure Handlers: Node.js vs Browser

When an exception or rejection escapes local boundaries, runtime host environments provide top-level hooks:

```text
Browser Environment:
  ├── window.onerror               (Synchronous script exceptions)
  └── window.onunhandledrejection  (Uncaught Promise rejections)

Node.js Environment:
  ├── process.on('uncaughtException')       (Fatal synchronous crashes)
  ├── process.on('uncaughtExceptionMonitor')(Audit crash without stopping exit)
  └── process.on('unhandledRejection')      (Uncaught Promise rejections)
```

In Node.js, `uncaughtException` signals that the application process is in an undefined, corrupted state. The documented best practice is to perform emergency synchronous logging and resource drainage, then terminate immediately via `process.exit(1)`:

```javascript
// Node.js process safety configuration
process.on('uncaughtExceptionMonitor', (err, origin) => {
  logger.fatal({ err, origin }, 'Uncaught exception detected by process monitor');
});

process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'Process entering emergency shutdown');
  // Flush logs synchronously and exit:
  process.exit(1);
});

process.on('unhandledRejection', (reason, promise) => {
  logger.error({ reason, promise }, 'Unhandled Promise Rejection detected');
});
```

## Summary

Resilient error handling distinguishes expected domain states from exceptional runtime faults. Expected outcomes are modeled as explicit Result union types, while exceptional conditions trigger exceptions that preserve root-cause chains via `Error.cause`. `finally` provides cleanup guarantees, but must avoid altering control flow. Network clients must classify HTTP status codes explicitly and employ exponential backoff with jitter, reserving global process handlers strictly for telemetry and emergency shutdown.

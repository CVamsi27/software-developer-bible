# Error Handling

## Definition

**Error handling** means detecting a failed operation and deciding how the program should respond. JavaScript can throw an `Error` object; a `try/catch/finally` block can catch it and run cleanup. A synchronous error travels through the active function calls, while a promise reports asynchronous failure through rejection. JavaScript also permits other thrown values, so code should not assume every caught value is an `Error`. A useful handler recovers, translates the failure for its caller or stops the affected work.

> **Textbook Definition:** Error handling governs how abnormal completion propagates, is recovered from or is translated into a caller-facing failure. JavaScript distinguishes synchronous throws from promise rejection and provides cleanup through `finally`.


## First Principles

A failed operation needs code responsible for recovering, reporting a different result or stopping the affected work. A synchronous `throw` travels through the active function calls until it finds a matching handler. A callback that runs later no longer has the original call stack, so it needs its own error path. A promise carries failure as a rejection. Using `await` inside `try` lets that async function's `catch` handle the rejection.

Unhandled-rejection reporting is a host policy, not a garbage-collection rule. Returning a rejected promise can be correct when its caller owns the outcome; adding a catch that only logs and returns undefined can incorrectly turn failure into success.

## Follow one failure to its owner

```text
operation fails → throw/reject
    → local code adds useful context or lets it propagate
    → request/job/UI boundary chooses recovery or a safe response
    → monitoring records the failure with operation identity
```

Invalid input may need a field error. An unavailable dependency may justify a limited retry. A broken **invariant**, a condition the program relies on being true, may require ending the request or process. Choose that response before choosing where to catch the failure. An error hierarchy is useful when its categories lead to those different decisions.

## Why It Matters

Choose error categories from the decisions they require: field correction, authentication, limited retry or stopping unsafe work. Distinguish an expected operational failure from a broken program invariant, and use global handlers for last-resort reporting rather than local recovery. Record useful context such as operation/request IDs; redact sensitive data and avoid logging personal identifiers by default.

Translate failures into useful user-facing outcomes while retaining diagnostic context for the owning boundary. Use a custom class, stable error code or discriminated Result when it supports a different decision; one generic error can be sufficient for a genuinely uniform response.

## How It Works

### Error Propagation

```text
CALL STACK ERROR PROPAGATION:

function a() {
  throw new Error('Failed in a');
}

function b() { a(); }
function c() { b(); }

try {
  c();
} catch (err) {
  // Error propagates: a → b → c → catch
  console.log(err.message); // "Failed in a"
  console.log(err.stack); // Full stack trace
}

┌──────────────────────────────────┐
│ Call Stack when error is thrown: │
│                                  │
│ a() ← error thrown here          │
│ b() ← stack unwinds through here │
│ c() ← stack unwinds through here │
│ try/catch ← caught here          │
└──────────────────────────────────┘
```

### The Error Object

```typescript
// Built-in error types
new Error('message'); // Generic error
new SyntaxError('message'); // Syntax parsing error
new TypeError('message'); // Wrong type encountered
new ReferenceError('message'); // Invalid reference
new RangeError('message'); // Value out of range
new URIError('message'); // URI handling error
new EvalError('message'); // Legacy category; modern eval failures use ordinary error types

// Error object properties
const err = new Error('Something went wrong');
console.log(err.message); // "Something went wrong"
console.log(err.name); // "Error"
console.log(err.stack); // Stack trace (non-standard but widely supported)
console.log(err.cause); // undefined here — only set when you pass { cause }
```

## Code Examples

### Basic try/catch/finally

```typescript
function parseJSON(jsonString: string): unknown {
  try {
    const result = JSON.parse(jsonString);
    return result;
  } catch (error) {
    // Handle the error
    console.error('Failed to parse JSON:', error);
    return null;
  } finally {
    // Runs on normal control-flow exits, including a rethrow
    console.log('Parse attempt completed');
  }
}

console.log(parseJSON('{"name": "Alice"}')); // { name: 'Alice' }
console.log(parseJSON('invalid json')); // null (no crash)
```

The parser above deliberately maps every JSON syntax failure to `null`. Valid JSON `null` has the same result, so callers cannot distinguish those outcomes. Use a tagged Result or let the exception propagate when that distinction matters. `finally` runs on normal control-flow exits; process termination is outside that guarantee.

### Custom Error Classes

```typescript
class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly statusCode: number = 500,
    options?: ErrorOptions
  ) {
    super(message, options);
    this.name = 'AppError';
  }
}

class ValidationError extends AppError {
  constructor(
    message: string,
    public readonly field: string
  ) {
    super(message, 'VALIDATION_ERROR', 400);
    this.name = 'ValidationError';
  }
}

class NotFoundError extends AppError {
  constructor(resource: string, id: string) {
    super(`${resource} with id '${id}' not found`, 'NOT_FOUND', 404);
    this.name = 'NotFoundError';
  }
}

// Usage
function findUser(id: string): never {
  throw new NotFoundError('User', id);
}

try {
  findUser('invalid-id');
} catch (error) {
  if (error instanceof NotFoundError) {
    console.log(`404: ${error.message}`); // 404: User with id 'invalid-id' not found
  } else if (error instanceof ValidationError) {
    console.log(`400: ${error.message}`);
  } else if (error instanceof AppError) {
    console.log(`${error.statusCode}: ${error.message}`);
  }
}
```

### Error Handling with Type Narrowing

```typescript
function handleError(error: unknown): string {
  // Unknown type forces proper narrowing
  if (error instanceof Error) {
    return `Error: ${error.message}`;
  }

  if (typeof error === 'string') {
    return `String error: ${error}`;
  }

  if (typeof error === 'object' && error !== null &&
      'message' in error && typeof error.message === 'string') {
    return `Object error: ${error.message}`;
  }

  return `Unknown error: ${String(error)}`;
}

// Usage
try {
  throw { code: 500, message: 'Server fault' };
} catch (error) {
  console.log(handleError(error)); // "Object error: Server fault"
}
```

### Async Error Handling

Assume `User` is the application's response type and that `/api/users/:id` returns JSON. Checking HTTP status establishes transport success; validating the JSON against `User` is a separate boundary, as shown in [Async/Await](10.1.3.03-async-await.md). An HTTP 404 fulfills `fetch` with a response; request failure or abort rejects it. A JSON parse failure rejects body reading instead.

```typescript
// async/await with try/catch
async function fetchUserData(userId: string): Promise<User> {
  try {
    const response = await fetch(`/api/users/${encodeURIComponent(userId)}`);

    if (!response.ok) {
      throw new AppError(
        `HTTP ${response.status}: ${response.statusText}`,
        'HTTP_ERROR',
        response.status
      );
    }

    return await response.json();
  } catch (error) {
    // Handle network errors and HTTP errors
    if (error instanceof TypeError) {
      // Classify this conservatively: TypeError can also have other causes.
      throw new AppError('Request failed', 'REQUEST_ERROR', 503, { cause: error });
    }
    throw error; // Re-throw HTTP errors
  }
}

```

Do not infer a network cause merely from `instanceof TypeError`: request setup and application code can throw that type too. Keep the original error as `cause`. For deadlines, the canonical [cancellation chapter](10.1.3.05-abort-and-cancellation.md) passes a signal to fetch and explains timer cleanup. `Promise.race` alone can reject the wait while the request and timeout remain active.

### Error Boundary Pattern (try/catch at Boundaries)

```typescript
// This boundary chooses Result outcomes and validates data before success.
class ApiService {
  async get<T>(path: string, decode: (data: unknown) => T): Promise<Result<T>> {
    try {
      const response = await fetch(path);
      if (!response.ok) {
        throw new AppError('API request failed', 'HTTP_ERROR', response.status);
      }
      const data: unknown = await response.json();
      return { success: true, data: decode(data) };
    } catch (error) {
      return {
        success: false,
        error: error instanceof AppError
          ? error
          : new AppError('Unexpected API error', 'UNKNOWN', 500, { cause: error }),
      };
    }
  }
}

// Result type pattern (Rust-inspired)
type Result<T> =
  | { success: true; data: T }
  | { success: false; error: AppError };

// Usage — no try/catch needed at call site!
const apiService = new ApiService();
// decodeUsers is an application runtime validator; it throws on invalid data.
const result = await apiService.get<User[]>('/api/users', decodeUsers);

if (result.success) {
  console.log(result.data.length, 'users found');
} else {
  console.error('Failed:', result.error.message);
}
```

This TypeScript module requires the application's `User` type and `decodeUsers` validator. Trace the three outcomes: valid 200 JSON reaches `success: true`; a 404 becomes an HTTP error; malformed JSON or a rejected schema becomes an error retaining its cause. Narrowing `result.success` permits access to exactly one branch. Returning a `Result` is an explicit API choice, not a reason to suppress failures in every function.

### Global Error Handlers

```typescript
// Browser: Unhandled promise rejections
window.addEventListener('unhandledrejection', (event) => {
  console.error('Unhandled promise rejection:', event.reason);
  event.preventDefault(); // Prevent default console warning
});

// Browser: Uncaught exceptions
window.onerror = (message, source, lineno, colno, error) => {
  console.error('Global error:', { message, source, lineno, error });
  // Send to error tracking service (Sentry, etc.)
  return true; // Prevent default browser handling
};

// Node.js: Unhandled rejections
// With Node's default --unhandled-rejections=throw policy, a listener
// changes escalation. Other flags (including strict) behave differently.
process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled Rejection at:', promise, 'reason:', reason);
});

// Node.js: Uncaught exceptions
process.on('uncaughtException', (error) => {
  console.error('Uncaught Exception:', error);
  // Perform cleanup
  // Then exit — the process is in an unknown state
  process.exit(1);
});
```

## Real-World Use Cases

### 1. Form Validation

```typescript
class FormValidationError extends AppError {
  constructor(
    message: string,
    public readonly errors: Record<string, string[]>
  ) {
    super(message, 'FORM_VALIDATION', 422);
  }
}

function validateForm(data: Record<string, unknown>): void {
  const errors: Record<string, string[]> = {};

  if (!data.email || typeof data.email !== 'string') {
    errors.email = ['Email is required'];
  } else if (!data.email.includes('@')) {
    errors.email = ['Invalid email format'];
  }

  if (typeof data.password !== 'string' || data.password.length < 8) {
    errors.password = ['Password must be at least 8 characters'];
  }

  if (Object.keys(errors).length > 0) {
    throw new FormValidationError('Validation failed', errors);
  }
}
```

This demonstrates collecting field errors, not a complete email validator or production password policy. Server-side validation and the application's actual authentication requirements remain authoritative.

### 2. Retry with Exponential Backoff

The callback below must represent retry-safe work, such as a read or a write carrying a stable idempotency key. `maxAttempts` includes the first call: three permits two retries. Validate the budget and classify which errors are transient rather than retrying every failure.

```typescript
async function withRetry<T>(
  fn: () => Promise<T>,
  options: { maxAttempts?: number; baseDelay?: number } = {}
): Promise<T> {
  const { maxAttempts = 3, baseDelay = 1000 } = options;
  if (!Number.isInteger(maxAttempts) || maxAttempts < 1 ||
      !Number.isFinite(baseDelay) || baseDelay < 0) {
    throw new RangeError('Invalid retry budget');
  }

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (attempt === maxAttempts) throw error;

      // Don't retry non-retryable errors
      if (!(error instanceof AppError) ||
          ![429, 502, 503, 504].includes(error.statusCode)) {
        throw error;
      }

      // Exponential backoff with jitter
      const delay = baseDelay * Math.pow(2, attempt - 1) + Math.random() * 1000;
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }

  throw new Error('Unreachable');
}
```

If the first two calls reject with 503 and the third succeeds, the helper sleeps after attempts one and two, then returns the third result. A validation failure stops on the first call. This simplified policy omits cancellation, `Retry-After`, a maximum delay and an overall deadline; production retries need those limits. A timeout can hide a committed write, so retrying without operation identity can duplicate effects.

## Common Mistakes

### 1. Catching and Swallowing

```typescript
// BAD: Silent catch — hides bugs
try {
  await processData();
} catch (error) {
  // Does nothing — bugs are hidden!
}

// Propagate when this layer cannot recover; its owner decides reporting
try {
  await processData();
} catch (error) {
  console.error('processData failed:', error);
  throw error; // Or handle appropriately
}
```

### 2. Using `throw` with Non-Errors

```typescript
// BAD: Throwing non-Error objects
throw 'Something went wrong';
throw 404;
throw { message: 'Custom error' };

// GOOD: Always throw Error instances
throw new Error('Something went wrong');
throw new AppError('Not found', 'NOT_FOUND', 404);
```

### 3. Not Distinguishing Error Types

```typescript
// BAD: Generic catch for all errors
try {
  await apiCall();
} catch (error) {
  showError('Something went wrong'); // Same message for all errors
}

// GOOD: Handle different errors differently
try {
  await apiCall();
} catch (error) {
  if (error instanceof FormValidationError) {
    showFieldErrors(error.errors);
  } else if (error instanceof NotFoundError) {
    showNotFound();
  } else {
    showGenericError();
  }
}
```

## Best Practices

1. **Prefer Error instances for exceptional failures** — they support standard diagnostic fields; thrown values received from other code can still have another shape.

2. **Add categories when decisions differ** — use classes, stable codes or Result variants without creating a hierarchy for every message.

3. **Catch where you own a decision** — local recovery/cleanup may be appropriate; translate outward-facing errors at the request, job or UI boundary.

4. **Keep failure observable to its owner** — recover explicitly or propagate. Logging at every layer creates duplicates; an intentional ignored cancellation needs a stated policy.

5. **Use the `cause` property** (ES2022) to chain related errors.

6. **Narrow caught values** — TypeScript uses `unknown` with `useUnknownInCatchVariables`, enabled by `strict`; the runtime can throw any value regardless of that option.

7. **Async error handling** — await inside a local try when that function can handle the rejection, or return the rejected outcome to an owning boundary.

8. **Global handlers** — set up `unhandledrejection` and `onerror` for safety net.

9. **Result types** — consider using discriminated unions for expected failures.

10. **Don't over-catch** — allow errors to propagate to appropriate handlers.

11. **Sanitize before you show** — never render `err.stack` or a raw internal message to a user; they leak file paths, queries, and identifiers. Map to a safe message at the boundary, log the full error server-side with the request ID.

## Performance Considerations

- **Measure the relevant path.** Error allocation, stack capture/formatting and propagation costs depend on the engine and workload; there is no universal overhead ratio.
- **Choose semantics before micro-optimizing.** Expected repeated outcomes may fit a Result or ordinary branch; reserve exceptions for the failure contract you intend.
- **Keep diagnostic stack behavior qualified.** `stack` is widely implemented, but its capture/formatting timing and detail are host-dependent. Nested handlers should each own a distinct decision.
- **Scope, not speed, decides `.catch` vs `try/catch`** — chain rejection can be observed by a rejection handler; local try/catch observes an awaited rejection or an ordinary synchronous throw

## Summary

1. **Mechanism**: a synchronous `throw` reaches its enclosing handler; a rejected promise propagates through dependent outcomes until handled, or is observed by an awaited local catch
2. **Custom errors**: `extends Error` + a `code` gives you typed branches (`instanceof`) instead of string matching
3. **Boundaries**: catch where you can recover, clean up or translate; an outer API/job/UI boundary owns the final outcome
4. **Ownership**: recover deliberately or propagate the failure; one reporting owner avoids duplicated logs
5. **Safety net**: host-level handlers observe otherwise unhandled failure; they do not make interrupted work safe to resume
6. **Cost**: measure the real engine and workload; stack diagnostics and exceptional paths have implementation-dependent costs

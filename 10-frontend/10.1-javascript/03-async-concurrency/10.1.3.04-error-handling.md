# Error Handling

## Definition

A request can fail in several ways: code may throw immediately, a promise may reject later, or an operation may complete with an error response. Error handling decides who recognizes that failure, what context to preserve, and whether to recover, return a safe result, or stop the affected work.

> **Textbook Definition:** Error handling governs the propagation, recovery, translation, and reporting of abnormal completion. JavaScript uses synchronous exceptions and promise rejections, while `finally` provides control-flow cleanup.

## First Principles

A handler is useful only where it can make a decision. If a layer cannot recover, clean up, or add context the caller needs, let the failure propagate. A callback that runs later needs its own failure channel because the original `try` block has already returned. Awaiting a promise inside `try` brings its rejection into that block.

## Return expected failures; throw failures the caller cannot treat as data

A malformed configuration is often an expected input outcome. A discriminated result makes that outcome visible without using `null` for both valid data and failure:

```typescript
type ParseResult =
  | { ok: true; value: unknown }
  | { ok: false; reason: SyntaxError };

function parseJson(source: string): ParseResult {
  try {
    return { ok: true, value: JSON.parse(source) as unknown };
  } catch (cause) {
    if (cause instanceof SyntaxError) return { ok: false, reason: cause };
    throw cause;
  }
}
```

The parsed value remains `unknown` until a runtime validator checks its shape. `finally` runs while JavaScript follows ordinary control flow, including on a throw or return; a `return` or new throw inside `finally` replaces the earlier outcome. It cannot clean up after process termination.

## Preserve useful context across an asynchronous boundary

An HTTP error response is still a fulfilled `fetch` promise. Network failure, abort, body-reading failure, and invalid application data follow different paths, so check each at its own boundary:

```typescript
class HttpError extends Error {
  constructor(readonly status: number) {
    super(`Request failed with HTTP ${status}`);
    this.name = 'HttpError';
  }
}

async function loadUser(id: string, signal: AbortSignal): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`, { signal });
  if (!response.ok) throw new HttpError(response.status);

  const payload: unknown = await response.json();
  return decodeUser(payload); // application-owned runtime validation
}
```

`User` and `decodeUser` belong to the application. A JSON parse error rejects `response.json()`; a validator should reject data that is syntactically valid but structurally wrong. The caller can catch around `await loadUser(...)` if it owns the user-facing decision. Do not turn every `TypeError` into “network error”: request setup and application code can throw that type too.

For a deadline, pass an `AbortSignal` to the operation and clear any owned timer. `Promise.race` can stop the caller waiting while the request and timer continue; the [cancellation chapter](10.1.3.05-abort-and-cancellation.md) traces that lifecycle.

When a layer adds context, retain the original failure in the ES2022 `cause` property rather than flattening it into a message:

```typescript
try {
  await publishInvoice(invoice);
} catch (cause) {
  throw new Error('Publishing invoice failed', { cause });
}
```

Wrap only when the new context helps the next owner. Preserve stable error codes or status fields if callers use them to choose a response. A caught value is `unknown` in strict TypeScript and may be any JavaScript value; narrow it before reading `message`, and never show a raw stack or internal message to a user.

## Retry only work that can safely run again

A timeout does not prove that a remote write failed; the server may have committed before the response was lost. Retry reads or writes with a stable idempotency key, not an arbitrary callback. Bound attempts, delay and total deadline; use jitter to avoid synchronized retries, honor `Retry-After` where the protocol requires it, and pass cancellation through the wait and request. Retry only classified transient failures. A retry loop without those conditions can multiply load or duplicate effects.

## Use host-level handlers as a last resort

A local request, task or UI boundary should own ordinary recovery. Browser `error` and `unhandledrejection` events can provide telemetry for failures that escaped those boundaries, but suppress default reporting only when the replacement reporter owns the record.

In Node, an `unhandledRejection` listener changes the default escalation behavior. An `uncaughtException` handler also overrides the normal exit path; Node documents it for synchronous cleanup before shutdown, not for continuing normal work. If monitoring must observe a crash without changing that behavior, use `uncaughtExceptionMonitor` and let the process fail for its supervisor to restart. See [Node's process-event guidance](https://nodejs.org/api/process.html).

## Summary

Catch where a decision changes. Keep expected outcomes explicit, let unowned failures propagate, and preserve the cause when adding context. Retries need replay safety and a finite budget; global handlers report failures but do not make interrupted work safe to resume.

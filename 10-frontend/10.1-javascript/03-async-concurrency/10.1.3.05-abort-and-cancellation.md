# Aborting & Cancellation

When a user types "react" into an autocomplete input, preceding requests for "r", "re", and "rea" remain active on the network. Without cancellation, responses can arrive out of order, overwriting newer results with stale data while consuming socket bandwidth. JavaScript provides a standardized, cooperative cancellation protocol via `AbortController` and `AbortSignal`.

## Definition

`AbortController` and `AbortSignal` constitute a standardized DOM and runtime API for signaling and observing the cooperative cancellation of asynchronous operations. An `AbortController` owns the cancellation lifecycle, while its associated `AbortSignal` communicates aborted state, custom reasons, and event dispatches to downstream consumers.

> **Textbook Definition:** Cancellation in JavaScript is a cooperative signaling protocol implemented via `AbortController` and `AbortSignal`. The controller transitions its signal into an aborted state and broadcasts an abort event; participating asynchronous tasks observe this signal to terminate execution, release system handles, and reject pending promises.

## First Principles

1. **Cooperative Execution Model:** JavaScript engines do not forcibly terminate running asynchronous operations from the outside. Cancellation requires target APIs or custom functions to actively inspect the signal or subscribe to its `abort` event.
2. **One-Way Irrevocable Lifecycle:** An `AbortSignal` transitions from non-aborted to aborted exactly once. It can never be reset or un-aborted; a subsequent logical operation requires a new `AbortController`.
3. **Payload and Reason Decoupling:** Aborting accepts an optional `reason` payload (defaulting to an `AbortError` `DOMException`). APIs inspect `signal.reason` rather than string-matching error messages.
4. **Listener Hygiene:** Event listeners attached to long-lived `AbortSignal` instances must be unregistered upon normal operation settlement, preventing memory leaks in persistent objects.

```text
Caller / Coordinator                   Asynchronous Worker (fetch / timer)
┌────────────────────────────────────────────────────────────────────────┐               ┌─────────────────────────────────┐
│ new AbortController()│ ── signal ──▶ │ Check signal.aborted            │
└──────────┬─────────────────────────────────────────────────────────────┘               │ Attach signal onAbort listener  │

     User Cancels                                       │

┌────────────────────────────────────────────────────────────────────────┐                   │ Listeners Fired:            │
│ controller.abort()   │ ── event ───────▶ │ 1. Clear Timeout / Drop TCP │

                                           └─────────────────────────────┘
```

## The Anatomy of `AbortController` and `AbortSignal`

The cancellation protocol decouples control from observation:

| Interface | Member | Responsibility | Behavior |
| :-------------------- | :------------------ | :------------------------------- | :-------------------------------------------- |
| **`AbortController`** | `.signal` | Read-only `AbortSignal` instance | Passed to workers to observe cancellation |
| **`AbortController`** | `.abort(reason?)` | Triggers cancellation | Flips `signal.aborted` to `true`, fires event |
| **`AbortSignal`** | `.aborted` | Boolean state flag | Synchronously inspectable |
| **`AbortSignal`** | `.reason` | Rejection payload | Contains provided reason or `AbortError` |
| **`AbortSignal`** | `.throwIfAborted()` | Guard method | Throws `signal.reason` immediately if aborted |

### Composition: `AbortSignal.timeout` and `AbortSignal.any`

Modern runtimes provide static factory utilities that compose multiple cancellation policies cleanly:

```javascript
// 1. Timeout Signal: Aborts automatically after specified delay
const timeoutSignal = AbortSignal.timeout(5000); // Reason: TimeoutError DOMException

// 2. Composed Signal: Aborts if EITHER user aborts OR timeout triggers
function fetchWithTimeout(url, userSignal) {
  const timeout = AbortSignal.timeout(3000);
  const combinedSignal = userSignal
    ? AbortSignal.any([userSignal, timeout])
    : timeout;

  return fetch(url, { signal: combinedSignal });
}
```

`AbortSignal.any()` creates a dependent signal that mirrors the first input signal to abort, propagating its exact `reason`.

## The Listener Memory Leak Trap

A frequent source of memory leaks in production microservices and Single Page Applications is improper listener registration on shared or long-lived `AbortSignal` instances:

```javascript
// LEAK: Passing { once: true } does NOT prevent leaks on success!
function delayWithLeak(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);

    const timer = setTimeout(resolve, ms);

    // If timer resolves normally, this listener is NEVER removed!
    signal?.addEventListener('abort', () => {
      clearTimeout(timer);
      reject(signal.reason);
    }, { once: true });
  });
}
```

If `signal` is passed to hundreds of requests across an application's lifecycle, every successful request leaves an abandoned closure attached to the signal's event registry.

### The Leak-Free Disposable Pattern

Resilient utilities ensure the listener is cleaned up on **both** completion and cancellation:

```javascript
export function delay(ms, signal) {
  if (!Number.isFinite(ms) || ms < 0) {
    return Promise.reject(new RangeError('Delay must be a non-negative number'));
  }

  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      return reject(signal.reason);
    }

    let timer;

    function cleanup() {
      signal?.removeEventListener('abort', onAbort);
    }

    function onAbort() {
      clearTimeout(timer);
      cleanup();
      reject(signal.reason);
    }

    timer = setTimeout(() => {
      cleanup();
      resolve();
    }, ms);

    signal?.addEventListener('abort', onAbort);
  });
}
```

## Search Race Conditions: Dual Defense Pattern

In real-world UI development, network requests cannot be guaranteed to abort instantly. Furthermore, cached responses may return synchronously, or an intermediate proxy might delay the abort signal.

To prevent race conditions where an older query overwrites a newer query, applications combine **cancellation** with **generation sequence tokens**:

```typescript
export interface SearchManager<T> {
  search: (query: string) => Promise<void>;
  cancel: () => void;
  dispose: () => void;
}

export function createSearchManager<T>(
  fetcher: (query: string, signal: AbortSignal) => Promise<T>,
  onSuccess: (data: T) => void,
  onError: (err: unknown) => void
): SearchManager<T> {
  let activeController: AbortController | null = null;
  let currentGeneration = 0;
  let isDisposed = false;

  return {
    async search(query: string): Promise<void> {
      if (isDisposed) throw new Error('SearchManager has been disposed');

      // 1. Invalidate previous request by bumping generation token:
      const thisGeneration = ++currentGeneration;

      // 2. Abort in-flight network request:
      activeController?.abort(new DOMException('New query submitted', 'AbortError'));
      const controller = new AbortController();
      activeController = controller;

      try {
        const result = await fetcher(query, controller.signal);

        // 3. Dual check: Verify generation token AND signal state
        if (thisGeneration === currentGeneration && !controller.signal.aborted) {
          onSuccess(result);
        }
      } catch (err) {
        if (thisGeneration === currentGeneration && !controller.signal.aborted) {
          onError(err);
        }
      } finally {
        if (thisGeneration === currentGeneration) {
          activeController = null;
        }
      }
    },

    cancel(): void {
      currentGeneration++;
      activeController?.abort(new DOMException('Search cancelled', 'AbortError'));
      activeController = null;
    },

    dispose(): void {
      isDisposed = true;
      this.cancel();
    },
  };
}
```

## What AbortSignal Cannot Stop

Understanding the limits of `AbortSignal` prevents architectural defects:

1. **Tight Synchronous Loops:** A CPU-bound loop running on the main thread blocks the event loop. The `abort` event cannot be delivered until the synchronous block yields. CPU tasks must cooperatively inspect a flag and yield via `scheduler.yield()` or run in a Worker.
2. **Server-Side Side Effects:** Calling `controller.abort()` terminates the client's HTTP socket. However, if the server has already parsed the request and initiated database mutations, the server work proceeds unless the backend runtime explicitly checks client disconnects.
3. **Non-Reversible Actions:** Aborting an operation does not roll back mutations that already executed. Idempotency keys, compensating transactions, or distributed sagas must handle partial failure rollback.

## Summary

`AbortController` provides standardized, cooperative lifecycle management for asynchronous operations. Signals transition to aborted state exactly once, carrying typed reasons and broadcasting abort events. High-performance implementations remove abort listeners upon successful completion to prevent memory leaks, and pair network cancellation with generation tokens to eliminate UI race conditions.

# Aborting & Cancellation

## Definition

An `AbortController` owns a one-way cancellation signal. Its `signal` exposes whether cancellation was requested, the reason, and an abort event. `controller.abort(reason?)` records the request; an operation stops only if its API or implementation observes that signal.

> **Textbook Definition:** Cancellation is a cooperative protocol in which a controller changes a signal to an aborted state and participating operations observe it. Aborting a signal does not itself reverse completed side effects or force arbitrary code to stop.

## First Principles

A caller may stop needing a result before work finishes. Ignoring the result prevents a UI update but can leave requests, timers or computation active. A separate signal lets the caller communicate lifetime without taking over the callee's implementation. Because the operation may already have performed effects, requesting cancellation is not equivalent to rolling back those effects.

## What happens when the owner aborts?

```text
caller owns controller → operation receives signal
caller aborts          → signal becomes aborted and records reason
                       → listeners/cooperative checks observe the request
                       → operation cleans up supported resources
                       → pending result follows that API's cancellation contract
```

One signal can govern several related operations. An aborted signal stays aborted; start a fresh logical operation with an appropriate fresh controller rather than trying to reset it.

Fetch can stop a supported request/body read when signalled. DOM event registration can use a signal to remove listeners. Other APIs have their own contracts: do not assume every stream, media API or timer accepts the same option. For example, obtaining media and stopping already obtained media tracks are distinct lifecycles.

## Preserve the reason instead of guessing from a name

`abort()` without a reason uses a default AbortError DOMException. A supplied reason can be another JavaScript value; `throwIfAborted()` throws that actual reason. `AbortSignal.timeout` uses a TimeoutError reason. Name-only checks can therefore miss application-defined cancellation. Choose behavior from the owned signal, its reason and the operation's documented rejection contract, rather than asserting that all cancellation looks identical. [AbortSignal reference](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal).

A user navigating away may need no error message. A current request reaching its timeout may need a retry action. “Cancelled” is not universally silent or universally retryable.

## Make a timer both abortable and cleanly disposable

This complete helper settles on normal completion or cancellation. It handles an already-aborted signal and removes its own listener after success; `{ once: true }` alone would only remove it **if an abort event fires**.

```js
function delay(ms, signal) {
  if (!Number.isFinite(ms) || ms < 0) return Promise.reject(new RangeError('Invalid delay'));
  return new Promise((resolve, reject) => {
    if (signal?.aborted) { reject(signal.reason); return; }
    const timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, ms);
    function onAbort() {
      clearTimeout(timer);
      signal.removeEventListener('abort', onAbort);
      reject(signal.reason);
    }
    signal?.addEventListener('abort', onAbort, { once: true });
  });
}
async function demonstrate() {
  const controller = new AbortController();
  const reason = new Error('No longer needed');
  const outcome = delay(1000, controller.signal).catch(error => error);
  controller.abort(reason);
  console.log((await outcome) === reason); // true
  await delay(0);
  console.log('normal completion');
}
demonstrate().catch(error => console.error(error));
```

The owner can cancel the timer because this helper implements cleanup. A race with an unrelated rejection would only stop waiting unless it also cleared the timer. The helper does not reset the signal or convert its reason into a fabricated AbortError.

## Why does search need both cancellation and a latest-result rule?

A request may finish just before cancellation, or a custom loader may ignore its signal. A **generation**, a number or token identifying the latest request, lets the application check whether a result still belongs to the current search. Cancellation can stop supported work. The generation check separately prevents an older result from replacing a newer one.

```ts
function createLatestLoader<T>(
  load: (query: string, signal: AbortSignal) => Promise<T>,
  publish: (result: T) => void,
  report: (error: unknown) => void
) {
  let generation = 0;
  let active: AbortController | null = null;
  let disposed = false;

  return {
    async run(query: string): Promise<void> {
      if (disposed) throw new Error('Loader is disposed');
      const mine = ++generation;
      active?.abort();
      const controller = new AbortController();
      active = controller;
      try {
        const result = await load(query, controller.signal);
        if (mine === generation && !controller.signal.aborted) publish(result);
      } catch (error) {
        if (mine === generation && !controller.signal.aborted) report(error);
      } finally {
        if (mine === generation) active = null;
      }
    },
    dispose(): void {
      disposed = true;
      generation += 1;
      active?.abort();
      active = null;
    }
  };
}
```

The callbacks and query loader are supplied by the application. `load` should encode the query, check HTTP status and validate returned data; [Async/Await](10.1.3.03-async-await.md) owns that response-validation example. `publish` and `report` should not throw in this helper's contract. Disposing invalidates publication even if the loader completes later. A React effect needs to call the appropriate cleanup when its lifetime ends; [useEffect](../../10.3-react/02-core-hooks/10.3.2.02-useeffect.md) owns the component integration.

## How do cancellation sources compose?

`AbortSignal.any` returns a signal that adopts the first input's cancellation reason. It combines lifetime policies; it does not create a new retry or rollback policy. Static helpers require support in the selected runtime/browser matrix.

```js
function requestWithDeadline(url, ownerSignal) {
  const timeout = AbortSignal.timeout(5000);
  const signal = ownerSignal ? AbortSignal.any([ownerSignal, timeout]) : timeout;
  return fetch(url, { signal });
}
```

This helper returns the fetch response promise, not validated JSON. The timeout can also affect body consumption while the caller reads it. Browser timeout accounting uses active time and may pause while a document is in the back-forward cache; it is not a hard end-to-end wall-clock server deadline. [Timeout semantics](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static).

For listeners your application adds directly to a long-lived signal, remove them when the operation finishes, even if it never aborts. Signals passed through API options and listeners added manually have different cleanup ownership.

## Which work cannot be stopped by merely setting a flag?

A tight synchronous loop cannot observe a new event dispatched on the same blocked agent until it yields. Checkpoints help only if the cancellation state can change between them; for cooperative CPU work, split bounded chunks and yield appropriately, or use a worker with a designed termination/message protocol. Awaiting only an already-fulfilled promise does not guarantee a browser task/paint opportunity.

A client abort does not prove that the server stopped a payment or database write. After a timeout with an uncertain outcome, use the same operation ID to check whether the server already completed it before retrying. Server-side deadlines limit server work. Idempotency prevents a repeated request from repeating its effect. Both complement cancellation; neither is guaranteed by calling `abort`.

Graceful shutdown similarly needs an explicit order: stop accepting work, let required transactions finish or cancel safe work, drain/close resources, and enforce a bounded shutdown deadline. Calling `abort` on a shared controller alone does not prove all jobs honor it or that a process will exit promptly.

## Summary

The owner communicates lifetime through a signal; each operation implements its own cancellation and cleanup contract. Preserve reasons, remove application listeners after completion, and keep a separate rule for obsolete results. Cancellation limits further work but does not establish rollback or successful server-side termination.

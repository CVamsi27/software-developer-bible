# Aborting & Cancellation

## TL;DR

`AbortController` + `AbortSignal` are the standard cancellation mechanism for async JavaScript: `fetch`, event listeners, Node timers, and streams all accept a `signal`, and calling `controller.abort()` cancels everything listening to it. `AbortSignal.timeout(ms)` gives one-line timeouts, `AbortSignal.any([...])` composes multiple cancel sources, and `signal.throwIfAborted()` makes long loops cooperative. An abort rejects with an `AbortError` — catch it by `error.name`, not as a generic failure.

## First Principles

Cancellation must exist because of one economic fact, and takes its shape from one cooperative fact:

1. **Resources keep billing after you stop caring.** A fetch that nobody awaits still holds sockets, memory, and battery. "Just ignore the result" is not cancellation — the work must be *told to stop*, so stop-signals need a first-class channel: the `AbortController`/`AbortSignal` pair (one broadcaster, many listeners).
2. **Cancellation is cooperative, never pre-emptive.** The platform cannot tear down a running function mid-frame (one stack, → 10.1.3.01); it can only flip a flag and fire an event. Every cancellable API therefore *checks the signal* — which is why your own long loops must also check it to be abortable.
3. **Cancellation is a rejection with a specific identity.** An aborted fetch rejects with `DOMException`/`AbortError` — not because the authors liked exceptions, but because the result *must* travel the promise channel (→ 10.1.3.04), and consumers must distinguish "failed" from "gave up."

Timeouts are just automated cancellation: a signal wired to a timer.

## Why It Matters

Senior engineers treat cancellation as a first-class part of async design, not an afterthought:

- **Stale-request race conditions** — the classic React bug: type "a", "ab" quickly; the slow "a" response arrives last and overwrites "ab". Aborting the previous request on every keystroke is the fix.
- **Resource leaks** — an unmounted component's fetch keeps running, keeping sockets, buffers, and memory alive until it completes.
- **Timeouts** — no server, client, or middleware guarantees a response time. Client-side cancellation is the only enforcement you own.
- **Graceful shutdown** — Node services abort in-flight work on `SIGTERM` instead of waiting for sockets to drain on their own.

Mid-level engineers add `await fetch(...)`. Senior engineers add `await fetch(..., { signal })` and design what happens when it fires.

**Concretely:**

1. **Cancel stale requests** — superseded results must not clobber fresh ones
2. **Enforce timeouts** — `AbortSignal.timeout()` without `Promise.race` boilerplate
3. **Clean up listeners** — `addEventListener(type, fn, { signal })` removes the need to keep handler references for `removeEventListener`
4. **Cooperative cancellation** — stop long loops/workers when the result is no longer wanted
5. **Graceful shutdown** — abort in-flight work when a process receives a termination signal
6. **Composable cancel sources** — user-cancel OR timeout OR parent-teardown via `AbortSignal.any`

## Definition

**`AbortController`** is a controller object with two members: `signal` (an `AbortSignal` you hand to cancellable operations) and `abort(reason?)` (fires the signal). **`AbortSignal`** is the observable half: it carries `aborted` (boolean), `reason` (why it was aborted), an `abort` event, and static helpers:

- `AbortSignal.timeout(ms)` — a signal that aborts itself after `ms` milliseconds
- `AbortSignal.any([s1, s2, ...])` — a signal that aborts when **any** input signal aborts
- `signal.throwIfAborted()` — throws `signal.reason` if aborted (for cooperative checks)

Cancellation is **cooperative**: aborting a signal doesn't kill code; an operation cancels only if it was written to observe the signal. All Web APIs that accept signals (`fetch`, `addEventListener`, streams, `navigator.mediaDevices`) respect it natively; your own long-running code must check `signal.aborted` / `throwIfAborted()` at safe points.


## How It Works

```text
┌────────────────────────────────────────────────────┐
│ controller.abort(reason)                           │
│   → Signal: aborted = true, reason stored          │
│   → 'abort' event fires on the signal              │
│   → every listening operation cancels:             │
│       fetch rejects with DOMException "AbortError" │
└────────────────────────────────────────────────────┘
```

1. Create a controller; hand `controller.signal` to one or more operations
2. Something decides to cancel (unmount, timeout, user, parent teardown) and calls `controller.abort()`
3. The signal flips `aborted`, stores `reason`, and fires the `abort` event
4. Every operation watching the signal cancels — `fetch` rejects with a `DOMException` named `"AbortError"`
5. Your code catches it and responds (silently ignore, show "cancelled", or rethrow)

A signal can be shared by many operations (abort them all at once), but a controller is **one-shot**: once aborted it stays aborted.

## Code Examples

### Basic Fetch Cancellation (with React cleanup)

```typescript
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${query}`, { signal: controller.signal })
    .then(res => res.json())
    .then(setResults)
    .catch(err => {
      if (err.name === 'AbortError') return; // expected on unmount/new keystroke
      setError(err.message);
    });

  return () => controller.abort(); // cleanup cancels in-flight request
}, [query]);
```

This single `signal` fixes both the race condition (old request aborted before it can resolve) and the leak (nothing outlives the component).

### Catching AbortError Correctly

```typescript
async function loadDashboard(signal: AbortSignal) {
  try {
    const res = await fetch('/api/dashboard', { signal });
    return await res.json();
  } catch (err) {
    if (err instanceof DOMException && err.name === 'AbortError') {
      return null; // cancelled — not a failure; don't show an error toast
    }
    throw err; // genuine network/server failure — propagate
  }
}
```

### Timeouts: `AbortSignal.timeout()`

```typescript
// Modern: one line. Aborts (and therefore rejects) after 5s.
const res = await fetch('/api/slow', { signal: AbortSignal.timeout(5_000) });

// Composed: caller's cancel signal OR a 5s timeout, whichever fires first
const res2 = await fetch('/api/slow', {
  signal: AbortSignal.any([callerSignal, AbortSignal.timeout(5_000)]),
});
```

`AbortSignal.timeout` never leaks a timer into your logic: the signal is self-managed, and you never call `.abort()` on it yourself.

### Event Listener Cleanup Without Handler References

```typescript
// Old style: keep a reference so you can removeEventListener later
window.addEventListener('resize', onResize);
window.removeEventListener('resize', onResize);

// Modern: one signal tears down everything registered with it
const teardown = new AbortController();
window.addEventListener('resize', onResize, { signal: teardown.signal });
window.addEventListener('focus', onFocus, { signal: teardown.signal });
document.addEventListener('visibilitychange', onVisibility, { signal: teardown.signal });
// ...one call removes them all:
teardown.abort();
```

In React, abort the controller in the `useEffect` cleanup — all listeners registered with its signal vanish with the component.

### Cooperative Cancellation in Long-Running Loops

```typescript
async function processBatch(items: string[], signal: AbortSignal): Promise<Summary> {
  const summary: Summary = { done: 0, skipped: 0 };

  for (const item of items) {
    signal.throwIfAborted(); // throws signal.reason (AbortError) if cancelled

    await processOne(item, { signal }); // I/O also honors the signal
    summary.done++;
  }

  return summary;
}

// Caller
const controller = new AbortController();
processBatch(allItems, controller.signal).catch(err => {
  if (err.name !== 'AbortError') report(err);
});

// Later — stop the batch when the user navigates away:
controller.abort();
```

### Graceful Shutdown in Node

```typescript
const controller = new AbortController();

process.on('SIGTERM', () => {
  // Stop accepting new work and cancel in-flight operations
  server.close();
  controller.abort(new Error('Shutting down'));
});

await runJob({ signal: controller.signal }); // exits promptly on SIGTERM
```

## Real-World Use Cases

### 1. Search-As-You-Type (Race Condition Fix)

```typescript
let active: AbortController | null = null;

async function onSearchInput(q: string) {
  active?.abort();            // cancel the previous query
  active = new AbortController();

  try {
    const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
      signal: active.signal,
    });
    renderResults(await res.json()); // only the newest query gets here
  } catch (err) {
    if (err.name !== 'AbortError') showError(err); // cancelled = ignore
  }
}
```

### 2. Data-Layer Fetch Wrapper (Timeout at the Edges)

```typescript
async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(path, {
    ...init,
    signal: init.signal
      ? AbortSignal.any([init.signal, AbortSignal.timeout(10_000)])
      : AbortSignal.timeout(10_000),
  });
  if (!res.ok) throw new ApiError(res.status, path);
  return res.json() as Promise<T>;
}
```

Every call gets a ceiling by default; callers can layer their own cancel signals on top with `AbortSignal.any`.

## Common Mistakes

### 1. Swallowing AbortError as a Generic Failure

```typescript
// BAD: cancelled requests show error toasts / retry loops
fetch(url, { signal })
  .catch(err => showError(err.message)); // fires on every unmount!

// GOOD: branch on the error name
fetch(url, { signal })
  .catch(err => {
    if (err.name === 'AbortError') return;
    showError(err.message);
  });
```

### 2. Creating the Controller in the Wrong Scope

```typescript
// BAD: nothing can reach the controller to abort it
async function load() {
  const controller = new AbortController(); // born and buried inside load()
  const res = await fetch(url, { signal: controller.signal });
}

// GOOD: the caller owns the lifetime
function load(signal: AbortSignal) {
  return fetch(url, { signal });
}
// caller: const c = new AbortController(); load(c.signal); ... c.abort();
```

### 3. Treating an Aborted Signal as Resettable

```typescript
// BAD: controllers are one-shot
controller.abort();
controller.signal.aborted; // true forever — no "unabort"

// GOOD: create a fresh controller per operation/attempt
```

### 4. Registering Abort Listeners That Leak

```typescript
// BAD: handler outlives its usefulness, and runs after your teardown logic died
signal.addEventListener('abort', cleanup);

// GOOD: signal-based cleanup, remove when done, or rely on the owning controller
signal.addEventListener('abort', cleanup, { once: true });
// ...and abort the owning controller in your component/job teardown
```

## Best Practices

1. **Thread `signal` through every async layer** — wrappers, loaders, and helpers should accept and forward it, not hide it
2. **Put timeouts at the edges** — a fetch wrapper with `AbortSignal.timeout` beats scattering `Promise.race` through the codebase
3. **Compose with `AbortSignal.any`** — user-cancel, parent-teardown, and timeout are independent concerns that merge into one signal
4. **Check `throwIfAborted()` at checkpoints** in cooperative loops — cheap, and makes long CPU batches cancellable
5. **Always distinguish `AbortError`** from real failures before logging, toasting, or retrying
6. **One controller per logical operation** — fresh controller per request attempt; share one signal across sibling operations that should die together

## Performance Considerations

- **Overhead is negligible** — a signal costs one object and one event; a leaked request costs a socket, buffers, and GC pressure
- **Abort is client-side** — the server may still finish processing; cancellation stops *your* wait, not their work. Pair with server-side timeouts/idempotency
- **AbortSignal.timeout timers** are scheduled lazily and cleaned up by the platform — no manual `clearTimeout` bookkeeping
- **Avoid per-item controllers** in hot loops — one controller per batch, checked via `throwIfAborted()`

## Summary

`AbortController`/`AbortSignal` are the standard, composable cancellation primitives of modern JavaScript: fetch, listeners, timers, streams, and your own loops all cancel through the same mechanism. Pass `signal` down through async layers, set timeouts with `AbortSignal.timeout()`, merge sources with `AbortSignal.any()`, check `throwIfAborted()` in cooperative work, and always handle `AbortError` as "cancelled — not failed". Cancellation is what turns async code from fire-and-forget into a controlled resource.

## Cheat Sheet

```text
ABORT & CANCELLATION CHEAT SHEET
═══════════════════════════════════════

BASICS:
const c = new AbortController();
fetch(url, { signal: c.signal });
c.abort();                    // cancel
c.signal.aborted;             // true after abort
c.signal.reason;              // why (DOMException by default)

ONE-LINE TIMEOUT:
fetch(url, { signal: AbortSignal.timeout(5000) });

COMPOSITION:
AbortSignal.any([userSig, timeoutSig])  // first abort wins

LISTENER CLEANUP:
addEventListener('resize', fn, { signal })
// one abort removes every listener registered with it

COOPERATIVE LOOPS:
for (...) { signal.throwIfAborted(); ... }

CATCHING:
catch (err) {
  if (err.name === 'AbortError') return; // cancelled ≠ failed
  throw err;
}

GOTCHAS:
• Controller is one-shot — fresh one per attempt
• Abort is cooperative — ops must accept signal
• Abort is client-side — server keeps working
```

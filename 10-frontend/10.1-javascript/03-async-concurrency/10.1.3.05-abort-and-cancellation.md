# Aborting & Cancellation

Typing "react" into autocomplete leaves requests for "r", "re", and "rea" still in flight. Without a current-request guard, stale responses can arrive last and overwrite fresh results — while burning socket bandwidth. JavaScript answers with a cooperative protocol: `AbortController` plus `AbortSignal`.

```javascript
const controller = new AbortController();

fetch('/api/search?q=rea', { signal: controller.signal })
  .catch((err) => console.log(err.name)); // 'AbortError' after abort()

controller.abort(new DOMException('New query submitted', 'AbortError'));
```

## Definition

**`AbortController`/`AbortSignal`** is the standard API for cooperative cancellation of async work. The **controller** owns the lifecycle; its **signal** broadcasts aborted state, reasons, and events to downstream consumers.

> **Textbook Definition:** Cancellation in JavaScript is a cooperative signaling protocol implemented via `AbortController` and `AbortSignal`. The controller transitions its signal into an aborted state and broadcasts an abort event; participating asynchronous tasks observe this signal to terminate execution, release system handles, and reject pending promises.

## First Principles

An AbortSignal does not forcibly kill work — participating targets inspect the signal or subscribe to its `abort` event (**cooperative** model). A signal flips from live to aborted exactly **once** and never resets; the next operation needs a new controller. Aborts carry a `reason` value (default: `AbortError` `DOMException`), so consumers read `signal.reason` instead of string-matching messages. And listeners on long-lived signals must be removed on settlement so they do not retain completed operations.

```text
Owner creates controller → passes signal to supported work
Owner calls abort(reason)
  → signal becomes aborted
  → abort listeners run synchronously and perform supported cleanup
  → pending promise observers run later with the cancellation outcome

Remote effects and non-cooperating work may continue.
```

## 1. The Anatomy of `AbortController` and `AbortSignal`

Control and observation are decoupled:

| Interface | Member | Responsibility | Behavior |
| :-------------------- | :------------------ | :------------------------------- | :-------------------------------------------- |
| **`AbortController`** | `.signal` | Read-only `AbortSignal` instance | Passed to workers to observe cancellation |
| **`AbortController`** | `.abort(reason?)` | Triggers cancellation | Flips `signal.aborted` to `true`, fires event |
| **`AbortSignal`** | `.aborted` | Boolean state flag | Synchronously inspectable |
| **`AbortSignal`** | `.reason` | Rejection payload | Contains provided reason or `AbortError` |
| **`AbortSignal`** | `.throwIfAborted()` | Guard method | Throws `signal.reason` immediately if aborted |

Static factories compose policies — timeouts plus user intent:

```javascript
// 1. Timeout Signal: Aborts automatically after specified delay
const timeoutSignal = AbortSignal.timeout(5000); // Reason: TimeoutError DOMException

// 2. Composed Signal: Aborts if EITHER user aborts OR timeout triggers
function fetchWithTimeout(url, userSignal) {
  const timeout = AbortSignal.timeout(3000);
  const combinedSignal = userSignal
    ? AbortSignal.any([userSignal, timeout])
    : timeout;

  return fetch(url, { signal: combinedSignal });
}
```

`AbortSignal.any()` mirrors whichever input aborts first, propagating its exact `reason`.

## 2. The Listener Memory Leak Trap

`{ once: true }` does **not** prevent leaks on the success path — a resolved timer leaves its abort listener attached forever:

```javascript
// LEAK: Passing { once: true } does NOT prevent leaks on success!
function delayWithLeak(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);

    const timer = setTimeout(resolve, ms);

    // If timer resolves normally, this listener is NEVER removed!
    signal?.addEventListener('abort', () => {
      clearTimeout(timer);
      reject(signal.reason);
    }, { once: true });
  });
}
```

Across hundreds of requests sharing one signal, every success strands a closure in the signal's registry. The leak-free pattern cleans up on **both** paths:

```javascript
export function delay(ms, signal) {
  if (!Number.isFinite(ms) || ms < 0) {
    return Promise.reject(new RangeError('Delay must be a non-negative number'));
  }

  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      return reject(signal.reason);
    }

    let timer;

    function cleanup() {
      signal?.removeEventListener('abort', onAbort);
    }

    function onAbort() {
      clearTimeout(timer);
      cleanup();
      reject(signal.reason);
    }

    timer = setTimeout(() => {
      cleanup();
      resolve();
    }, ms);

    signal?.addEventListener('abort', onAbort);
  });
}
```

## 3. Search Race Conditions: Dual Defense Pattern

Calling `controller.abort()` synchronously changes signal state and dispatches its abort event. Promise reactions still run asynchronously. Cancellation cannot retract a result already delivered, and custom async work may ignore the signal; remote work can also finish independently. Pair **cancellation** with **generation tokens** so only the current operation may commit UI results:

```typescript
export interface SearchManager<T> {
  search: (query: string) => Promise<void>;
  cancel: () => void;
  dispose: () => void;
}

export function createSearchManager<T>(
  fetcher: (query: string, signal: AbortSignal) => Promise<T>,
  onSuccess: (data: T) => void,
  onError: (err: unknown) => void
): SearchManager<T> {
  let activeController: AbortController | null = null;
  let currentGeneration = 0;
  let isDisposed = false;

  return {
    async search(query: string): Promise<void> {
      if (isDisposed) throw new Error('SearchManager has been disposed');

      // 1. Invalidate previous request by bumping generation token:
      const thisGeneration = ++currentGeneration;

      // 2. Abort in-flight network request:
      activeController?.abort(new DOMException('New query submitted', 'AbortError'));
      const controller = new AbortController();
      activeController = controller;

      try {
        const result = await fetcher(query, controller.signal);

        // 3. Dual check: Verify generation token AND signal state
        if (thisGeneration === currentGeneration && !controller.signal.aborted) {
          onSuccess(result);
        }
      } catch (err) {
        if (thisGeneration === currentGeneration && !controller.signal.aborted) {
          onError(err);
        }
      } finally {
        if (thisGeneration === currentGeneration) {
          activeController = null;
        }
      }
    },

    cancel(): void {
      currentGeneration++;
      activeController?.abort(new DOMException('Search cancelled', 'AbortError'));
      activeController = null;
    },

    dispose(): void {
      isDisposed = true;
      this.cancel();
    },
  };
}
```

## 4. What AbortSignal Cannot Stop

Three hard limits shape architecture:

1. **Tight synchronous loops** — another task cannot call `abort()` on that same agent while it is blocked. Once `abort()` is called, event dispatch is synchronous; it is the other task's chance to call it that is delayed. Check the signal at safe points and yield to host tasks, or move CPU work to a Worker.
2. **Server-side side effects** — an abort-aware client stops its own waiting/work according to the API. It does not guarantee a dedicated socket closes or a remote mutation stops. Even disconnect-aware servers need an explicit cancellation and commit policy.
3. **Non-reversible actions** — abort rolls back nothing already executed. Partial failures need idempotency keys, compensating transactions, or sagas.

## Summary

`AbortController` owns cooperative cancellation; its signal flips to aborted exactly once, carrying an arbitrary reason value and synchronously firing an event when abort is invoked. Deregister abort listeners on success as well as cancellation to avoid leaks, combine network aborts with generation tokens so stale results can't win races, and remember that a signal requests cooperation; it does not undo a server commit or preempt running JavaScript.

# Bounded Concurrency & Promise Pools

## TL;DR

`Promise.all(tasks)` starts **every** task at once — 10,000 fetches means 10,000 open sockets. **Bounded concurrency** runs at most N tasks simultaneously, starting the next as each finishes. The two-structure implementation: a **worker pool** (N async workers pulling from a shared index) or a **recursion chain** (`p.then(chain)` per slot). Know `Promise.all`-style fail-fast vs `allSettled`-style collect-all, and why results must be indexed — completion order is not submission order.

## First Principles

Bounded concurrency is forced by the gap between *parallelism you want* and *parallelism the target tolerates*:

1. **`Promise.all` conflates "all results" with "all at once"** (→ 10.1.3.02). Independent tasks *should* overlap — but the callee (API rate limit, connection pool, browser socket cap) bounds how many can usefully be in flight. Once the bound is the constraint, the scheduler must hold the rest back.
2. **Queuing is the only honest way to wait.** Held-back tasks must not start (their side effects fire at start), so a list of un-started thunks is the core data structure — the pool consumes thunks, not promises. This is why `mapWithConcurrency` takes `() => fetch(...)` factories, not created promises.
3. **Slots must refill — so the primitive is a chain, not a counter.** A finished slot must start the next task *without busy-waiting*. Attaching `.then(next)` to each worker's promise makes completion itself the scheduling event; that's also why the whole pool settles exactly when all N worker chains settle (one `all`).

## Definition

**Bounded concurrency** is a scheduling discipline that keeps exactly `limit` (or fewer) asynchronous operations in flight, queuing the remainder and starting one queued operation each time an in-flight one settles. A **promise pool** is the implementation: N persistent "workers", each looping `take next task → await it → repeat` until the task list is exhausted; the pool's overall promise settles when every worker's chain settles.

## Why It Matters

Every non-trivial backend and batch job hits this: uploading 5,000 images, crawling 50,000 pages, calling a rate-limited API for 20,000 IDs, fan-out enrichment in an ETL step. Unbounded `Promise.all` produces memory pressure (10k open request objects), socket exhaustion (`EMFILE`), 429 storms, and upstream outages. The failure is *always* the same shape — which is why `mapWithConcurrency(items, limit, fn)` is a top-3 take-home/whiteboard question: it tests whether you can combine promise semantics (→ 10.1.3.02) with queueing in ~20 lines.

**Concretely:**

- **Rate-limited third-party APIs** — stay under X req/s without serializing
- **Bulk uploads/downloads** — saturate bandwidth without exhausting sockets
- **Fan-out enrichment** (N+1 by design) — bounded parallelism with indexed results
- **Worker pools in Node** — same shape as `worker_threads` dispatch (→ 20.1.3.02)

## How It Works

The mental model: **N workers, one shared queue, results stored by index**.

```text
┌────────────────────────────────────────────────────────────────┐
│  tasks:  [T0, T1, T2, T3, T4, T5, T6, T7]    limit = 3         │
│                                                                │
│  worker A: T0 ──▶ T3 ──▶ T6                                    │
│  worker B: T1 ──▶ T4 ──▶ T7        each worker takes the next  │
│  worker C: T2 ──▶ T5            index when its current task    │
│                                    settles — completion IS the │
│  results[0..7] written by index  scheduling event              │
└────────────────────────────────────────────────────────────────┘
```

Three invariants to preserve:

1. **At most `limit` tasks in flight, always.** A worker awaits its current task before taking another.
2. **Every task runs exactly once.** The shared cursor increments atomically — JS is single-threaded (→ 10.1.1.03), so `tasks[i++]` between awaits cannot race.
3. **Results land by submission index.** Workers finish out of order; `results[i] = value` keeps output aligned with input.

## Code Examples

### The canonical implementation — worker pool

```typescript
async function mapWithConcurrency<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn, index: number) => Promise<TOut>,
): Promise<TOut[]> {
  const results = new Array<TOut>(items.length);
  let next = 0; // shared cursor — safe: JS is single-threaded between awaits

  async function worker(): Promise<void> {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i); // in-flight until it settles
    }
  }

  // min(limit, items.length) real workers; each chain drains the queue
  const workers = Array.from(
    { length: Math.min(limit, items.length) },
    () => worker(),
  );
  await Promise.all(workers); // settles when every chain is exhausted
  return results;
}
```

Key subtleties (the parts interviewers probe):

- **`fn` receives the *item*, not a promise** — tasks are started inside the worker, so queued items have zero side effects before their turn.
- **`Promise.all(workers)` never rejects** — `worker` can't throw (a rejecting `fn` propagates into `results[i] = await` and kills that *chain*). This is the fail-fast bug; fix below.
- **Zero items** → `Array.from({length: 0})` → `all([])` resolves immediately. `limit: 0` is a caller bug — throw instead of hanging.

### Fail-fast vs collect-all — the error policy is a choice

```typescript
// FAIL-FAST: reject as soon as any task rejects (Promise.all semantics)
async function mapWithConcurrencyFast<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn) => Promise<TOut>,
): Promise<TOut[]> {
  const results = new Array<TOut>(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i]); // throws → chain rejects → all() rejects
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

// COLLECT-ALL: run everything, mirror Promise.allSettled's shape
type Settled<T> = { status: 'fulfilled'; value: T } | { status: 'rejected'; reason: unknown };

async function mapWithConcurrencySettled<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn) => Promise<TOut>,
): Promise<Settled<TOut>[]> {
  const results = new Array<Settled<TOut>>(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length) {
      const i = next++;
      try {
        results[i] = { status: 'fulfilled', value: await fn(items[i]) };
      } catch (reason) {
        results[i] = { status: 'rejected', reason }; // one failure ≠ dead chain
      }
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

The subtle fail-fast trap: when a worker chain rejects, `Promise.all` rejects — **but the other workers keep consuming the queue**. Their results are discarded and their in-flight requests are *not* cancelled. Production pools pair fail-fast with an abort signal (below) or just use the settled variant.

### Cancellation — wiring AbortSignal (→ 10.1.3.05)

```typescript
async function mapWithConcurrencyAbort<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  signal: AbortSignal,
  fn: (item: TIn, signal: AbortSignal) => Promise<TOut>,
): Promise<PromiseSettledResult<TOut>[]> {
  const results = new Array<PromiseSettledResult<TOut>>(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length && !signal.aborted) {
      const i = next++;
      try {
        results[i] = { status: 'fulfilled', value: await fn(items[i], signal) };
      } catch (reason) {
        if (signal.aborted) results[i] = { status: 'rejected', reason };
        else results[i] = { status: 'rejected', reason };
      }
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

// caller: abort everything after 5 seconds
const controller = new AbortController();
setTimeout(() => controller.abort(), 5_000);
await mapWithConcurrencyAbort(urls, 8, controller.signal,
  (url, signal) => fetch(url, { signal }));
```

Each task gets the signal so it can cancel its own I/O; the workers additionally stop *pulling* new tasks once aborted. Both layers matter — a task that ignores its signal still can't be stopped, but the pool won't start *new* work (→ 10.1.3.05's cooperative-cancellation axiom).

### The recursion-chain variant (and why the pool is better)

```typescript
// One chain per slot: each completion starts the next task.
// Same invariants, but per-task .then allocations and harder to read.
function mapWithConcurrencyChain<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn) => Promise<TOut>,
): Promise<TOut[]> {
  const results = new Array<TOut>(items.length);
  let next = 0;

  function chain(): Promise<void> {
    if (next >= items.length) return Promise.resolve();
    const i = next++;
    return fn(items[i]).then((value) => {
      results[i] = value;
      return chain(); // completion schedules the next take
    });
  }

  return Promise.all(Array.from({ length: Math.min(limit, items.length) }, chain))
    .then(() => results);
}
```

Interview answer: both are correct; prefer the pool because the `while` loop reads like the invariant it enforces, and error policy composes cleanly per-worker.

## Real-World Use Cases

- **Docita's `map-with-concurrency.ts`** — bounded async worker pool over `Promise.all` for third-party API fan-out (the exact pattern this chapter implements).
- **Upload pipelines**: `mapWithConcurrency(files, 4, upload)` — 4 parallel uploads, UI stays responsive, server not hammered.
- **Rate-limited integrations**: wrap `limit` to match the provider's documented concurrency cap (Stripe: 25; most REST APIs: 5–10).
- **Crawlers/ETL**: page fetches bounded to be polite; settled variant to keep partial results when some URLs 404.
- **In production, reach for `p-limit`/`p-map`** — same semantics, battle-tested (progress callbacks, `stopOnError`, AbortSignal integration). Hand-rolling is for interviews and zero-dependency libs.

## Common Mistakes

1. **`Promise.all(items.map(fn))` and calling it concurrency control** — it's the *absence* of it: every task starts immediately. The classic take-home auto-fail.
2. **Passing created promises instead of thunks** — `mapWithConcurrency(items, 4, urls.map(u => fetch(u)))` has already started every fetch; the pool throttles nothing. The contract is a *function* that starts work when called.
3. **Results pushed, not indexed** — `results.push(await fn(item))` scrambles output when tasks finish out of order. Always `results[i] = ...`.
4. **`limit` larger than `items.length` without clamping** — harmless with `Math.min`, wasteful (or confusing) without; `limit: 0` must throw, not hang forever.
5. **Mixing fail-fast with un-aborted workers** — after `all` rejects, surviving chains keep firing requests into the void. Use the settled variant, or wire AbortSignal, or both.
6. **Re-implementing `Promise.all` inside the worker loop** — e.g. `results[i] = await Promise.all(subtasks)` is fine per-task, but starting *all* subtasks of *all* items up front is just unbounded again, one level down.

## Best Practices

- **Default limits**: 4–8 for I/O fan-out to a single host; match documented API caps when they exist. More concurrency is not more speed once the target is saturated (→ 20.3.4.01's rate limiting).
- **Index everything**: results by submission index; progress by completed count; never by completion order.
- **Make the error policy explicit in the API**: `mapWithConcurrency` (fail-fast) and `mapWithConcurrencySettled` (collect-all) as separate functions beat one function with a flag callers forget.
- **Thread AbortSignal through**: pools without cancellation leak work when their caller times out.
- **Measure, then tune**: concurrency above the target's saturation point increases latency (queuing) and error rates (429s) together.

## Performance Considerations

- **Pool overhead is O(tasks)** — one promise per task plus `limit` chains; negligible vs the I/O being scheduled.
- **The cursor makes workers cheap**: a "worker" is one async function; there is no thread, no lock — single-threaded JS (→ 10.1.1.03) guarantees `next++` is atomic between awaits.
- **Backpressure for free**: a generator source (→ 10.1.5.03) instead of a fixed array lets the pool *pull* work, so producers never outrun consumers.

## Summary

1. **`Promise.all` = unbounded; a pool = bounded** — the worker-pool pattern (N loops over a shared cursor) is the canonical ~20-line implementation
2. **Results are indexed, not pushed** — completion order never matches submission order
3. **Error policy is a design choice** — fail-fast (kills one chain, `all` rejects) vs settled (collect everything); fail-fast without cancellation leaves ghost requests running
4. **Thunks, not promises** — the pool must own task *start*, or nothing is actually bounded

## Cheat Sheet

```text
PATTERN      N workers · shared cursor · results[i] = await fn(items[i])
SPAWN        Array.from({ length: Math.min(limit, items.length) }, worker)
AWAIT        Promise.all(workers)  → settles when queue drains
FAIL-FAST    let fn throw → chain rejects → all rejects (workers keep draining!)
COLLECT-ALL  try/catch inside worker → { status, value|reason } per index
CANCEL       pass AbortSignal to fn + stop pulling when signal.aborted
PICK LIMIT   4–8 per host; provider cap if documented
LIBRARY      p-limit / p-map (prod) · hand-rolled (interviews)
```

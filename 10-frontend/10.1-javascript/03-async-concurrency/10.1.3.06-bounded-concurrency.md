# Bounded Concurrency & Promise Pools

## Definition

A batch of thousands of requests can finish sooner when some work overlaps, but starting every request at once can exhaust sockets or overwhelm the service. **Bounded concurrency** starts no more than a chosen number of asynchronous operations at a time. A **promise pool** opens a slot for the next item when an active operation settles. Its workers are async loops, not threads.

> **Textbook Definition:** Bounded concurrency schedules asynchronous operations under a maximum active-work limit. The scheduler controls when work starts; ordering, failure propagation, cancellation, and result buffering are separate policies.

## First Principles

The pool needs items plus a mapper it calls when a slot is free. A promise created before the pool receives it has already started, so the pool cannot throttle that work. Each worker awaits one operation before claiming the next item; several workers overlap I/O while JavaScript still runs callbacks on its event loop.

The limit controls active operations, not request starts per second. A fast mapper may reuse its slots many times in one second; a separate rate limiter is needed for a rate budget. For synchronous CPU work, async concurrency does not create parallel CPU execution—use an appropriate worker or process boundary.

## Start work only when a slot opens

With a limit of three, each completed worker takes the next index. Results are written back at that index so callers receive submission order even when tasks finish in a different order.

```text
tasks:   [T0, T1, T2, T3, T4, T5, T6]      limit = 3
worker A: T0 ───────→ T3 ───────→ T6
worker B: T1 ──→ T4
worker C: T2 ─────→ T5
results: [R0, R1, R2, R3, R4, R5, R6]      indexed by input
```

```typescript
async function mapWithConcurrency<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn, index: number) => Promise<TOut>,
): Promise<TOut[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('limit must be a positive integer');
  }

  const results = new Array<TOut>(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length) {
      const index = next++;
      results[index] = await fn(items[index], index);
    }
  }

  await Promise.all(
    Array.from({ length: Math.min(limit, items.length) }, () => worker()),
  );
  return results;
}
```

The shared cursor needs no lock because each worker claims its index synchronously before awaiting; no other JavaScript callback can interleave in that interval on the same agent. This does not apply to shared memory used by multiple worker threads. An empty input creates no workers and returns an empty array. The `items` and `results` arrays still use O(n) memory, so this implementation suits finite batches.

## Decide what one failure means

`Promise.all(workers)` is fail-fast for the caller: the pool promise rejects when a worker rejects. That worker stops, but the other workers continue their loops and may start more items. The aggregate rejection does not cancel active operations or stop the queue.

If every item should have an outcome, catch inside each worker and store it by index. The following replaces the worker body above; it preserves the same start limit:

```typescript
type Outcome<T> =
  | { status: 'fulfilled'; value: T }
  | { status: 'rejected'; reason: unknown };

try {
  results[index] = { status: 'fulfilled', value: await fn(items[index], index) };
} catch (reason) {
  results[index] = { status: 'rejected', reason };
}
```

Collect-all keeps claiming items after a failure. Use fail-fast when the batch should stop being useful after one error; use per-item outcomes when independent successes remain valuable. If fail-fast must also stop new starts, add an internal stop flag or controller at the first failure and still pass cancellation to active mappers. Cancellation is cooperative: a mapper that ignores its signal can keep running.

## Stop claiming work when the owner cancels

The caller can abort active, abort-aware operations and prevent workers from claiming queued items. A queued item that never started is **skipped**, not rejected; keeping that distinction makes the result useful for retries and reporting.

```typescript
type PoolOutcome<T> =
  | { status: 'fulfilled'; value: T }
  | { status: 'rejected'; reason: unknown }
  | { status: 'skipped'; reason: unknown };

async function mapWithConcurrencyAbort<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  signal: AbortSignal,
  fn: (item: TIn, index: number, signal: AbortSignal) => Promise<TOut>,
): Promise<PoolOutcome<TOut>[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('limit must be a positive integer');
  }

  const results = new Array<PoolOutcome<TOut>>(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length && !signal.aborted) {
      const index = next++;
      try {
        results[index] = {
          status: 'fulfilled',
          value: await fn(items[index], index, signal),
        };
      } catch (reason) {
        results[index] = { status: 'rejected', reason };
      }
    }
  }

  await Promise.all(
    Array.from({ length: Math.min(limit, items.length) }, () => worker()),
  );
  while (next < items.length) {
    results[next++] = { status: 'skipped', reason: signal.reason };
  }
  return results;
}
```

An operation already claimed when abort fires may still finish or reject; the pool records its actual outcome. Items not yet claimed receive `skipped`. If a mapper returns `fetch(...)`, the slot is released when response headers arrive, not when the body finishes. Consume or cancel each body inside the mapper when a complete transfer is the bounded unit, check `response.ok` because HTTP error statuses still fulfill `fetch`, and bound body size separately.

A deadline timer belongs to the caller and needs cleanup:

```typescript
async function runBatch(urls: readonly string[]) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), 5_000);
  try {
    return await mapWithConcurrencyAbort(urls, 8, controller.signal,
      async (url, _index, signal) => {
        const response = await fetch(url, { signal });
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        return await response.json();
      });
  } finally {
    clearTimeout(timer);
  }
}
```

This example bounds requests through response-body parsing, but `response.json()` buffers the full body. For large payloads, consume a stream with its own byte and queue limits. A timed-out write may still have committed remotely; use idempotency or reconciliation when the outcome is uncertain.

## Choose a pool that matches the input and output

For ordinary finite arrays, a small worker pool may be enough. The current [`p-map` API](https://github.com/sindresorhus/p-map) provides `pMap` for ordered fail-fast results, `pMapSettled` for one outcome per item, and `pMapIterable` for async output with concurrency and backpressure controls. Its `stopOnError: false` option waits for mapper work and then rejects with `AggregateError`; that is different from returning per-item outcomes. Check the installed version's cancellation and input-iterator contract before relying on it.

A promise pool over an array retains all inputs and outputs. For a large or open-ended source, use a pull-based async iterable and bound both active mappers and completed results waiting for a slow consumer. Preserving input order can create a buffer behind one slow early item; emitting in completion order avoids that buffer only when order is not part of the contract.

## Summary

Give the pool ownership of task start, state whether one failure rejects the batch or becomes an item result, and thread cancellation through work that supports it. Bound rate and response memory separately from active task count; for streaming workloads, bound the producer and result buffer too.

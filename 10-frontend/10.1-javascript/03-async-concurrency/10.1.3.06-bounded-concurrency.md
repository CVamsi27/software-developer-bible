# Bounded Concurrency & Promise Pools

## Definition

**Bounded concurrency** keeps at most `limit` asynchronous operations running at once. The remaining operations wait, and another starts when one finishes. A **promise pool** implements this with N asynchronous loops, often called workers. Each loop takes the next task, waits for it, then repeats until no tasks remain. These workers are not separate threads. When all workers succeed, the pool resolves after they finish. Its behavior on failure needs a separate policy.

> **Textbook Definition:** Bounded concurrency schedules queued operations subject to an upper limit on active work. Completion releases capacity for another operation; ordering, failure propagation and cancellation are separate scheduling policies.

## First Principles

Bounded concurrency is forced by the gap between *parallelism you want* and *parallelism the target tolerates*:

1. **Combining results does not control when operations start** (→ 10.1.3.02). Independent tasks can overlap, but API limits, available connections and browser socket limits bound how many can make progress at once. The scheduler keeps the rest waiting.
2. **Waiting tasks must not have started yet.** Starting them may already perform side effects. Give the pool items and a function it calls when a slot is free, or functions that start their work only when called. Such a function is sometimes called a **thunk**. A promise for work you already started cannot postpone that start.
3. **Finishing one task should start the next.** Each worker waits for its current task, then takes another without repeatedly polling for completion. A successful pool resolves after all workers finish. A fail-fast aggregate can reject while the other workers are still running.

## Why It Matters

Large batch operations make resource limits visible: uploading 5,000 images, crawling 50,000 pages or reading a rate-limited API for 20,000 IDs. Starting all requests at once can retain many request objects, exhaust sockets or file descriptors (`EMFILE`), trigger many rate-limit responses (`429`) and overload the upstream service. A pool makes the active-work budget explicit and combines promise outcomes (→ 10.1.3.02) with controlled starts. The right capacity still depends on the transport and service.

**Concretely:**

- **Third-party APIs** — cap active requests; add a separate rate limiter for requests-per-second budgets
- **Bulk uploads/downloads** — saturate bandwidth without exhausting sockets
- **Fan-out enrichment** (N+1 by design) — bounded parallelism with indexed results
- **Worker pools in Node** — same shape as `worker_threads` dispatch (→ 20.1.3.02)

## How It Works

The model is **N workers, one shared queue, results stored by index**. The diagram shows one possible completion pattern; the next task goes to whichever worker finishes, rather than a fixed round-robin assignment.

```text
┌────────────────────────────────────────────────────────────────┐
│  tasks:  [T0, T1, T2, T3, T4, T5, T6, T7]    limit = 3         │
│                                                                │
│  worker A: T0 ──▶ T3 ──▶ T6                                    │
│  worker B: T1 ──▶ T4 ──▶ T7        each worker takes the next  │
│  worker C: T2 ──▶ T5            index when its current task    │
│                                    settles — completion IS the │
│  results[0..7] written by index  scheduling event              │
└────────────────────────────────────────────────────────────────┘
```

Three invariants to preserve:

1. **At most `limit` tasks in flight, always.** A worker awaits its current task before taking another.
2. **Every claimed task runs once; collect-all claims every task.** The synchronous cursor update is uninterrupted within this one JavaScript agent (→ 10.1.1.03), so `tasks[i++]` between awaits cannot race.
3. **Results land by submission index.** Workers finish out of order; `results[i] = value` keeps output aligned with input.

## Code Examples

### The canonical implementation — worker pool

```typescript
async function mapWithConcurrency<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn, index: number) => Promise<TOut>,
): Promise<TOut[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('limit must be a positive finite integer');
  }
  const results = new Array<TOut>(items.length);
  let next = 0; // shared cursor — safe: JS is single-threaded between awaits

  async function worker(): Promise<void> {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i); // in-flight until it settles
    }
  }

  // min(limit, items.length) real workers; each chain drains the queue
  const workers = Array.from(
    { length: Math.min(limit, items.length) },
    () => worker(),
  );
  await Promise.all(workers); // all finish on success; first worker failure rejects
  return results;
}
```

Important scheduling boundaries:

- **`fn` receives the *item*, not a promise** — tasks are started inside the worker, so queued items have zero side effects before their turn.
- **`Promise.all(workers)` rejects on a worker failure** — a synchronous mapper throw or rejected promise stops that chain. Other worker chains keep running; rejection is not cancellation.
- **Zero items** → `Array.from({length: 0})` → `all([])` resolves immediately. Non-positive, fractional, or non-finite limits are rejected before workers are created. Without validation, zero workers resolve with an unfilled result array.

### Fail-fast vs collect-all — the error policy is a choice

The canonical implementation above already rejects as soon as one worker fails. To keep every outcome, catch inside each worker instead:

```typescript
// COLLECT-ALL: run everything, mirror Promise.allSettled's shape
type Settled<T> = { status: 'fulfilled'; value: T } | { status: 'rejected'; reason: unknown };

async function mapWithConcurrencySettled<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn) => Promise<TOut>,
): Promise<Settled<TOut>[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('limit must be a positive finite integer');
  }
  const results = new Array<Settled<TOut>>(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length) {
      const i = next++;
      try {
        results[i] = { status: 'fulfilled', value: await fn(items[i]) };
      } catch (reason) {
        results[i] = { status: 'rejected', reason }; // one failure ≠ dead chain
      }
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

The fail-fast boundary: when a worker chain rejects, `Promise.all` rejects — **but the other workers keep consuming the queue**. The aggregate no longer returns their results, but their side effects and in-flight requests continue. Production pools pair fail-fast with an abort signal (below) or just use the settled variant.

### Cancellation — wiring AbortSignal (→ 10.1.3.05)

```typescript
async function mapWithConcurrencyAbort<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  signal: AbortSignal,
  fn: (item: TIn, signal: AbortSignal) => Promise<TOut>,
): Promise<PromiseSettledResult<TOut>[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('limit must be a positive finite integer');
  }
  const results = new Array<PromiseSettledResult<TOut>>(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length && !signal.aborted) {
      const i = next++;
      try {
        results[i] = { status: 'fulfilled', value: await fn(items[i], signal) };
      } catch (reason) {
        results[i] = { status: 'rejected', reason };
      }
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  // Represent tasks never started after abort; return no sparse holes.
  while (next < items.length) {
    results[next++] = { status: 'rejected', reason: signal.reason };
  }
  return results;
}

// caller: request cooperative cancellation after 5 seconds
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 5_000);
try {
  await mapWithConcurrencyAbort(urls, 8, controller.signal,
    (url, signal) => fetch(url, { signal }));
} finally {
  clearTimeout(timer);
}
```

The `fetch` mapper above resolves when response headers arrive, not after the whole response body is consumed. To bound complete transfers, the mapper must consume or cancel the body before resolving, and impose a separate body-size/stream-buffer budget. Merely returning a `Response` bounds that request-start/header phase.

Each task gets the signal so it can cancel its own I/O; the workers additionally stop *pulling* new tasks once aborted. Both layers matter — a task that ignores its signal still can't be stopped, but the pool won't start *new* work (→ 10.1.3.05's cooperative-cancellation axiom).

### The recursion-chain variant (and why the pool is better)

```typescript
// One chain per slot: each completion starts the next task.
// Same invariants, but per-task .then allocations and harder to read.
function mapWithConcurrencyChain<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  fn: (item: TIn) => Promise<TOut>,
): Promise<TOut[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('limit must be a positive finite integer');
  }
  const results = new Array<TOut>(items.length);
  let next = 0;

  function chain(): Promise<void> {
    if (next >= items.length) return Promise.resolve();
    const i = next++;
    return Promise.resolve().then(() => fn(items[i])).then((value) => {
      results[i] = value;
      return chain(); // completion schedules the next take
    });
  }

  return Promise.all(Array.from({ length: Math.min(limit, items.length) }, chain))
    .then(() => results);
}
```

Interview answer: both are correct; prefer the pool because the `while` loop reads like the invariant it enforces, and error policy composes cleanly per-worker.

## Real-World Use Cases

- **API fan-out** — use a bounded async worker pool when one application operation calls multiple third-party services.
- **Upload pipelines**: `mapWithConcurrency(files, 4, upload)` — 4 parallel uploads, active uploads remain bounded; responsiveness and upstream load still require measurement.
- **Rate-limited integrations**: match the endpoint's documented concurrency budget; a separate token bucket or paced queue enforces a request-rate cap. Fixed provider-wide numbers can hide endpoint and account differences.
- **Crawlers/ETL**: page fetches bounded to be polite; settled variant to keep partial results when some URLs 404.
- **Library pools**: `p-map` exposes concurrency, `stopOnError`, and AbortSignal support; `stopOnError: false` rejects with an `AggregateError` after processing, unlike this chapter's per-item settled array. Check the specific library API rather than assuming interchangeable policies.

## Common Mistakes

1. **`Promise.all(items.map(fn))` and calling it concurrency control** — it's the *absence* of it: every task starts immediately. A result combinator alone does not enforce an active-work budget.
2. **Passing created promises instead of thunks** — `mapWithConcurrency(items, 4, urls.map(u => fetch(u)))` has already started every fetch; the pool throttles nothing. The contract is a *function* that starts work when called.
3. **Results pushed, not indexed** — `results.push(await fn(item))` scrambles output when tasks finish out of order. Use indexed assignment when the API promises input order; completion-order output is a different valid contract.
4. **`limit` larger than `items.length` without clamping** — harmless with `Math.min`, wasteful (or confusing) without; zero/negative/fractional/non-finite limits must throw rather than silently return holes.
5. **Mixing fail-fast with un-aborted workers** — after `all` rejects, surviving chains keep firing requests into the void. Use the settled variant, or wire AbortSignal, or both.
6. **Re-implementing `Promise.all` inside the worker loop** — e.g. `results[i] = await Promise.all(subtasks)` is fine per-task, but starting *all* subtasks of *all* items up front is just unbounded again, one level down.

## Best Practices

- **Choose limits from measurements**: start conservatively and match documented endpoint caps when they exist. More concurrency is not more speed once the target is saturated (→ 20.3.4.01's rate limiting).
- **Index everything**: results by submission index; progress by completed count; never by completion order.
- **Make the error policy explicit in the API**: `mapWithConcurrency` (fail-fast) and `mapWithConcurrencySettled` (collect-all) as should be distinguishable at the call site; separate functions or explicit options can both communicate the contract.
- **Thread AbortSignal through**: work may continue after a caller times out; cancellation must be supported by each mapper and complemented by queue-stop policy.
- **Measure, then tune**: concurrency above the target's saturation point increases latency (queuing) and error rates (429s) together.

## Performance Considerations

- **Pool overhead is O(tasks)** — promise/task overhead plus at most `limit` worker chains; scheduling cost depends on mapper duration and runtime; measure short-task workloads.
- **The cursor makes workers cheap**: a "worker" is one async function; there is no thread, no lock — one agent executes these ordinary synchronous cursor updates without interleaving; this is not an atomic shared-memory operation across worker threads.
- **Streaming needs a separate contract**: these examples retain O(items) inputs/results. A pull-based iterable (→ 10.1.5.03) can limit production, but preserving ordered results also needs a bound on completed values waiting for a slow consumer.

## Summary

1. **Eager mapping starts all tasks; a pool bounds starts** — the worker-pool pattern (N loops over a shared cursor) is a straightforward implementation with explicit scheduling invariants
2. **Results are indexed, not pushed** — completion order may differ from submission order
3. **Error policy is a design choice** — fail-fast (kills one chain, `all` rejects) vs settled (collect everything); fail-fast without cancellation leaves ghost requests running
4. **Thunks, not promises** — the pool must own task *start*, or nothing is actually bounded

# Bounded Concurrency & Promise Pools

`await Promise.all(urls.map(url => fetch(url)))` over ten thousand URLs initiates all requests without an application concurrency budget. The transport may queue or multiplex connections, yet the burst can still overload downstream quotas, memory and response-body buffers. A promise pool controls when work starts.

```javascript
// Starts every request immediately; transport socket count is host-dependent
async function processAllUrls(urls) {
  return Promise.all(urls.map(async (url) => {
    const res = await fetch(url);
    return res.json();
  }));
}
```

## Definition

**Bounded concurrency** caps concurrently active async operations at a fixed maximum. A **promise pool** runs $K$ worker coroutines that pull tasks from a shared backlog — steady throughput without overloading sockets, downstream services, or memory.

> **Textbook Definition:** Bounded concurrency constrains asynchronous operation scheduling such that at most $K$ tasks remain active simultaneously. A promise pool multiplexes task execution across $K$ asynchronous worker coroutines, separating start times, task ingestion rates, failure boundaries, and result buffering policies.

## First Principles

A promise represents work; it does not schedule it by itself. A constructor executor runs synchronously, and calling `fetch` starts the request. Handing already-started promises to a pool cannot throttle those starts, so the pool must control task-*factory* invocation. JavaScript's single-threaded run-to-completion makes a shared backlog cursor (`cursor++`) atomic with no mutexes. Note the two orthogonal limits: **concurrency** caps *in-flight* mapper work (5 active operations), while **rate limiting** caps *initiations per interval* (50 requests/second). And since tasks finish out of order, pre-allocating results by input index decouples execution order from output order.

```text
Tasks Queue: [ T0, T1, T2, T3, T4, T5, T6 ] (Concurrency Limit = 3)

Worker 1: ───[  Task 0  ]───▶───[  Task 3  ]───▶───[  Task 6  ]───▶ (Done)
Worker 2: ───[ Task 1 ]───▶───────[    Task 4    ]───▶ (Done)
Worker 3: ───[   Task 2   ]───▶───[  Task 5  ]───▶ (Done)

Output Buffer: [ R0, R1, R2, R3, R4, R5, R6 ] (Restored to input order)
```

## 1. The Unbounded Concurrency Trap

An unbounded initiation burst can exceed connection/file-descriptor limits, resolver capacity, downstream request quotas or database-pool capacity. Exact sockets and error codes depend on transport pooling, HTTP multiplexing, host and failure stage; no fixed URL count guarantees an `EMFILE` or `ENOTFOUND` error.

## 2. Core Implementation: The Lockless Worker Pool

$K$ worker coroutines share one cursor; `cursor++` executes synchronously before any `await`, so no two workers claim the same index:

```typescript
export async function mapWithConcurrency<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  taskFn: (item: TIn, index: number) => Promise<TOut>
): Promise<TOut[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('Concurrency limit must be a positive integer >= 1');
  }

  if (items.length === 0) return [];

  const results = new Array<TOut>(items.length);
  let cursor = 0;

  // Each worker coroutine pulls tasks sequentially until backlog is exhausted
  async function worker(): Promise<void> {
    while (cursor < items.length) {
      // Synchronous index acquisition: guaranteed atomic on single-threaded agent
      const index = cursor++;
      results[index] = await taskFn(items[index], index);
    }
  }

  // Spawn exactly K workers (or fewer if items count is smaller than limit)
  const workerCount = Math.min(limit, items.length);
  const workers = Array.from({ length: workerCount }, () => worker());

  await Promise.all(workers);
  return results;
}
```

## 3. Failure Strategies: Fail-Fast vs. Comprehensive Settlement

| Policy | Behavior on Failure | Unstarted Items | Best Used For |
| :-------------- | :---------------------------------------------------------------------------- | :------------------------------------------ | :---------------------------------------------- |
| **Fail-Fast** | Rejects aggregate on an observed mapper rejection; other workers keep running | Other workers can still claim backlog items | Caller needs an early failure signal |
| **All-Settled** | Catches errors per item; records status records; completes full backlog | All items processed regardless of failures | Scraping, batch syncs, bulk notifications |

Fail-fast observation is not cancellation, atomicity or rollback. In this canonical helper only the failed worker exits; stopping other starts requires an explicit shared policy. For collect-all pipelines, a third outcome — **skipped** — separates never-started items from claimed work under an `AbortSignal`:

```typescript
export type TaskOutcome<T> =
  | { status: 'fulfilled'; value: T }
  | { status: 'rejected'; reason: unknown }
  | { status: 'skipped'; reason: unknown };

export async function mapWithConcurrencySettled<TIn, TOut>(
  items: readonly TIn[],
  limit: number,
  signal: AbortSignal,
  taskFn: (item: TIn, index: number, signal: AbortSignal) => Promise<TOut>
): Promise<TaskOutcome<TOut>[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('Limit must be a positive integer');
  }

  const results = new Array<TaskOutcome<TOut>>(items.length);
  let cursor = 0;

  async function worker(): Promise<void> {
    while (cursor < items.length && !signal.aborted) {
      const index = cursor++;
      try {
        const value = await taskFn(items[index], index, signal);
        results[index] = { status: 'fulfilled', value };
      } catch (reason) {
        results[index] = { status: 'rejected', reason };
      }
    }
  }

  const workerCount = Math.min(limit, items.length);
  await Promise.all(Array.from({ length: workerCount }, () => worker()));

  // Mark all unstarted tasks as skipped:
  while (cursor < items.length) {
    results[cursor++] = { status: 'skipped', reason: signal.reason };
  }

  return results;
}
```

## 4. Memory Management, Streaming Backpressure, and `p-map`

`mapWithConcurrency` holds all inputs and outputs — $O(N)$ memory. Millions of rows need streaming backpressure instead:

```text
High-Memory Pool (In-Memory Array):
[ 10,000 Items Array ] ──▶ [ Pool Buffer: 10,000 Results Array ] ──▶ O(N) RAM

Low-Memory Streaming Pool (Async Iterator):
[ Readable Stream ] ──▶ [ K In-Flight Workers ] ──▶ [ Writable Destination Sink ]
(K active tasks plus bounded producer, completion and destination buffers)
```

Use an `AsyncIterable` source and honor destination backpressure so the producer cannot outrun the consumer. Ordered output may retain later results behind one slow early item; bound that completion buffer too. A task returning fetch headers can release its slot while its body remains active, so consume or cancel the body before completion when that transfer is the bounded unit. `p-map` supplies a maintained array-result API, while its `pMapIterable` API exposes a separate backpressure budget:

```javascript
import pMap from 'p-map';

const results = await pMap(
  urls,
  async (url) => {
    const res = await fetch(url);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
  },
  {
    concurrency: 8,       // Maximum active tasks
    stopOnError: false,   // If false, collects AggregateError at the end
  }
);
```

> [!NOTE]
> `p-map` with `stopOnError: false` waits for all tasks to settle, but rejects with an `AggregateError` containing all accumulated errors rather than returning a status record array. For item-by-item status arrays, wrap the mapper in a `try/catch` returning a custom outcome object.

## Summary

Unbounded initiation can overload transport, memory or downstream capacity. Bounded pools run a fixed set of worker loops against an atomic cursor, restoring input order through pre-allocated slots. Choose fail-fast observation for an early failure signal and settled outcomes for per-item reporting; wire `AbortSignal` to halt ingestion with explicit skipped tracking; stream when $O(N)$ memory is untenable.

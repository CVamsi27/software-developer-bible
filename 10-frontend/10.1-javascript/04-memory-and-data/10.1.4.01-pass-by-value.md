# Pass by Value vs Pass by Reference

When a function executes `record.count = 2` followed by `record = { count: 3 }`, the property mutation alters the caller's object, but the subsequent reassignment has zero effect outside the function. This discrepancy often confuses developers who assume JavaScript passes objects by reference. In reality, JavaScript evaluates all arguments strictly by value.

## Definition

JavaScript employs an evaluation strategy known strictly as **pass-by-value** (specifically specialized as **call-by-sharing** for composite types). In this model, function arguments are evaluated and their values are copied into independent parameter bindings within the callee's execution context. For primitive types, the raw value is copied; for objects, the pointer reference to the heap object is copied by value.

> **Textbook Definition:** JavaScript strictly evaluates all function arguments using pass-by-value semantics. When passing an object, the value copied into the callee's parameter binding is the reference pointer addressing the heap object; parameter reassignment re-binds the local pointer without altering the caller's variable, whereas property dereferencing mutates the shared heap allocation.

## First Principles

1. **Independent Execution Binding:** Every function invocation establishes a new Declarative Environment Record. Parameter identifiers are distinct, local variable slots allocated in the callee's execution context.
2. **Value Copy Semantics:** Argument expressions are evaluated to completion before the function runs. The resultant bit pattern or reference address is written into the callee's parameter slot.
3. **Shared Heap Indirection (Call-by-Sharing):** Objects exist exclusively on the heap. When an object is passed, the caller's binding and the callee's parameter binding hold identical memory address pointers.
4. **Reassignment vs. Dereferencing:** Variable assignment (`=`) modifies the address stored within the target binding slot. Property access (`.`) dereferences the address pointer to mutate the heap-allocated memory structure.

```text
At Function Invocation:
Caller Scope: [ original ] ───▶ (0x7FFF) ───▶ Heap Object: { count: 1 }
                                  ▲
Callee Scope: [ record   ] ───────┘ (Pointer copied by value)

After `record.count = 2` (Dereference & Mutate):
Caller Scope: [ original ] ───▶ (0x7FFF) ───▶ Heap Object: { count: 2 }
                                  ▲
Callee Scope: [ record   ] ───────┘

After `record = { count: 3 }` (Local Reassignment):
Caller Scope: [ original ] ───▶ (0x7FFF) ───▶ Heap Object: { count: 2 }
Callee Scope: [ record   ] ───▶ (0x9AAA) ───▶ Heap Object: { count: 3 }
```

## The Core Senior Distinction: Reassignment vs. Mutation

Tracing execution demonstrates the interaction between pointer values and local bindings:

```javascript
const original = { count: 1 };

function update(record) {
  // 1. Property mutation dereferences the shared 0x7FFF heap address:
  record.count = 2;

  // 2. Local reassignment overwrites the callee's local pointer with 0x9AAA:
  record = { count: 3 };

  return record;
}

const replacement = update(original);

console.log(original.count);            // 2 (Shared object was mutated)
console.log(replacement.count);         // 3 (New heap allocation returned)
console.log(original === replacement);  // false (Different memory addresses)
```

1. When `update(original)` is invoked, the memory address of `{ count: 1 }` (e.g. `0x7FFF`) is copied into parameter `record`.
2. `record.count = 2` dereferences `0x7FFF` and writes `2` into its property slot. Because `original` points to `0x7FFF`, the caller observes this mutation.
3. `record = { count: 3 }` instantiates a brand-new object at `0x9AAA` and stores that new address in `record`. The caller's `original` binding remains entirely unaffected, still pointing to `0x7FFF`.

## Memory Internals: Stack Frames vs. V8 Garbage Collected Heap

Engines like Google V8 optimize primitive and reference storage differently:

| Value Type | Engine Representation | Storage Location | Copy Mechanism |
| :------------------------------ | :------------------------------ | :------------------------ | :------------------------------------------------------------------- |
| **Small Integer (Smi)** | 31-bit or 32-bit tagged integer | Call Stack / CPU Register | Raw value copied inline; zero heap allocation |
| **Primitives (String, BigInt)** | Immutable heap structure | V8 Heap | Immutable pointer copied; deduplicated via internalized string table |
| **Objects & Arrays** | Mutable `JSObject` structure | V8 Garbage Collected Heap | 32-bit compressed pointer copied into parameter slot |

True pass-by-reference (available in languages like C++ via `&` or C# via `ref`) passes the memory address of the variable *binding itself*. In true pass-by-reference, reassigning `record = { count: 3 }` would overwrite the caller's `original` variable. Because JavaScript does not expose variable addresses, true pass-by-reference is impossible in ECMAScript.

## Destructuring and Spread: What Actually Copies?

Destructuring and the spread operator (`...`) create new shallow bindings rather than cloning deep structures:

```javascript
const state = {
  user: { name: 'Alice' },
  roles: ['admin', 'editor'],
};

// Spread shallow-copies the outer object:
const stateClone = { ...state };

// The outer containers have distinct identities:
console.log(state === stateClone); // false

// BUT nested objects share identical reference addresses:
console.log(state.user === stateClone.user);   // true
console.log(state.roles === stateClone.roles); // true

// Mutating a nested reference affects BOTH copies:
stateClone.user.name = 'Bob';
console.log(state.user.name); // "Bob" (Inadvertent mutation!)
```

Destructuring assignment works identically:
```javascript
const { user } = state;
user.name = 'Charlie'; // Mutates state.user.name on the shared heap!
```

## Contract Design: Pure Functions vs. In-Place Mutation

High-reliability engineering requires clear API contracts distinguishing between mutating in-place methods and pure transformation methods:

```typescript
// MUTATING IN-PLACE (Impure Contract)
function appendInPlace<T>(list: T[], item: T): T[] {
  list.push(item);
  return list;
}

// PURE TRANSFORMATION (Defensive Copy Contract)
function appendImmutable<T>(list: readonly T[], item: T): T[] {
  return [...list, item];
}
```

### Modern ECMAScript (ES2023) Non-Mutating Array Methods

ECMAScript 2023 introduced non-mutating counterparts for historic in-place array methods:

| In-Place Mutating Method | Non-Mutating Pure Counterpart | Returned Output |
| :------------------------- | :---------------------------- | :--------------------------- |
| `arr.sort(compareFn)` | `arr.toSorted(compareFn)` | New sorted array instance |
| `arr.reverse()` | `arr.toReversed()` | New reversed array instance |
| `arr.splice(start, count)` | `arr.toSpliced(start, count)` | New spliced array instance |
| `arr[i] = value` | `arr.with(i, value)` | New array with updated index |

```javascript
const numbers = [3, 1, 2];

// Historic method mutates original array:
// numbers.sort(); // Mutates numbers to [1, 2, 3]

// Modern ES2023 pure method:
const sorted = numbers.toSorted();
console.log(numbers); // [3, 1, 2] (Preserved untouched)
console.log(sorted);  // [1, 2, 3] (New array instance)
```

## Summary

JavaScript passes all arguments strictly by value. For primitive types, the actual value bit pattern is copied; for objects, the heap memory address pointer is copied by value (call-by-sharing). Property mutation dereferences the shared pointer, altering heap state visible across all aliases. Reassigning a parameter variable merely updates the local context slot, leaving the caller's binding and heap references untouched.

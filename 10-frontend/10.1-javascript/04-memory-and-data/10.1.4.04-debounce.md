# Debounce

## Definition

**Debouncing** delays a callback until a chosen quiet period has passed since the latest call. A trailing callback uses the latest arguments in the burst. An optional leading callback runs at the burst's start.

> **Textbook Definition:** Debouncing is a time-based coalescing technique that groups calls separated by less than a configured quiet-time threshold and invokes work according to a leading, trailing, or combined policy.

## First Principles

Search input is a useful example. If each keystroke starts a request, most requests become obsolete before they finish. If the interface only needs the settled query, reset a timer on each change and start work after the user pauses. This trades fewer operations for added latency. If continuous input must still produce periodic updates, use a throttle instead.

## One timer owns one burst

The wrapper retains a timer, the latest arguments, and the call receiver. Calls reset the deadline and replace those saved values. When the timer expires, trailing mode invokes once. A long stream of calls can keep moving the deadline forever; a `maxWait` policy is needed when work must run during continuous input.

```typescript
type Debounced<F extends (...args: any[]) => any> =
  ((this: ThisParameterType<F>, ...args: Parameters<F>) => void) & {
    cancel(): void;
    flush(): void;
  };

function debounce<T extends (...args: any[]) => any>(
  fn: T,
  wait: number,
  { leading = false, trailing = true } = {}
): Debounced<T> {
  if (!Number.isFinite(wait) || wait < 0) throw new RangeError('Invalid wait');

  let timer: ReturnType<typeof setTimeout> | undefined;
  let args: Parameters<T> | undefined;
  let receiver: ThisParameterType<T> | undefined;

  function invoke() {
    if (args === undefined) return;
    const savedArgs = args;
    const savedReceiver = receiver as ThisParameterType<T>;
    args = undefined;
    receiver = undefined;
    fn.apply(savedReceiver, savedArgs);
  }

  const wrapped = function(this: ThisParameterType<T>, ...nextArgs: Parameters<T>) {
    const startsBurst = timer === undefined;
    args = nextArgs;
    receiver = this;
    if (timer !== undefined) clearTimeout(timer);
    timer = setTimeout(() => {
      timer = undefined;
      if (trailing) invoke();
      else { args = undefined; receiver = undefined; }
    }, wait);
    if (startsBurst && leading) invoke();
  } as Debounced<T>;

  wrapped.cancel = () => {
    if (timer !== undefined) clearTimeout(timer);
    timer = undefined;
    args = undefined;
    receiver = undefined;
  };
  wrapped.flush = () => {
    if (timer === undefined) return;
    clearTimeout(timer);
    timer = undefined;
    if (trailing) invoke();
    else { args = undefined; receiver = undefined; }
  };
  return wrapped;
}
```

With a 300 ms delay and calls at 0, 100, and 200 ms, trailing-only mode runs once at about 500 ms with the third call's arguments. Leading mode also runs immediately at 0 ms. When both edges are enabled, one call in a burst runs only once; a later call during that burst creates the trailing invocation. `flush()` deliberately runs pending trailing work early. `cancel()` drops it. Timer delays are minimum eligibility times, not exact scheduling guarantees.

## Keep the async result attached to the current input

Debounce controls when work starts. It neither cancels a request already in flight nor determines which response may update the UI. On every input change, invalidate or abort the previous request immediately, then pass the new value to the debounced wrapper. When responses arrive, publish only the result belonging to the current input generation. A request failure is not a validation failure, and the server must validate submitted data independently.

The same separation matters for submission buttons. Debouncing can coalesce rapid clicks, but it cannot guarantee one request at a time or prevent a duplicate write after the wait expires. Use an in-flight guard for client behavior and an idempotency key or equivalent server policy for durable writes.

## Own the wrapper's lifetime

The timer belongs to the wrapper, not to the callback invocation. Recreating the wrapper on each React render creates new timing state and can strand pending work. Keep one wrapper for the intended lifetime and cancel it when that owner ends. A React hook should create the wrapper in a memo/effect boundary, update any “latest callback” reference after commit, and cancel during cleanup. Do not schedule timers during render.

For viewport and scroll events, create the wrapper in an effect and remove the event listener and cancel pending work during cleanup. Server-rendered components must not read `window` during initial render; measure it after mounting. Debounce makes a resize display wait for quiet, while animation work usually needs one update per rendering opportunity and is better coalesced with `requestAnimationFrame`.

One wrapper retains its latest arguments and receiver until invocation or cancellation, so pending work can keep large objects alive. A promise-returning debounce needs a separate contract for callers whose calls are superseded; returning the last callback's promise to every call or leaving earlier promises unresolved is not a neutral implementation detail.

## Summary

Debounce waits for quiet and coalesces a burst into leading and/or trailing work. State which edge runs, whether continuous input can postpone work, and how the wrapper is canceled. For async operations, add cancellation and latest-result ownership; debounce alone provides neither.

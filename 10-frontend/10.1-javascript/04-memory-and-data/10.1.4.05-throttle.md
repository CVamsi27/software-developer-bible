# Throttle

## Definition

**Throttling** limits how often a callback may start while calls continue arriving. A leading call can run immediately; an optional trailing call can run once with the latest suppressed arguments. Intermediate calls are discarded.

> **Textbook Definition:** Throttling is a rate-control technique that admits callback executions according to a time interval or window, optionally preserving one leading or trailing invocation from calls received during that interval.

## First Principles

Debounce waits until events stop. That works for a settled search query but can starve a scroll indicator while scrolling continues. Throttle gives periodic feedback instead: run at most once per interval and decide whether a final pending value should run at the boundary. Choose by what the user must observe, not by which function is cheaper.

## Track the last run, not just the first event

This implementation measures time from the **last actual callback start**. It keeps one timer and the latest suppressed call. If calls arrive at 0, 30, and 90 ms with a 100 ms interval, leading execution runs at 0 and the trailing call runs around 100 ms. A new call at 101 ms waits until around 200 ms; the trailing run started a fresh interval.

```typescript
type Throttled<F extends (...args: any[]) => any> =
  ((this: ThisParameterType<F>, ...args: Parameters<F>) => void) & {
    cancel(): void;
    flush(): void;
  };

function throttle<T extends (...args: any[]) => any>(
  fn: T,
  interval: number,
  { leading = true, trailing = true } = {}
): Throttled<T> {
  if (!Number.isFinite(interval) || interval < 0) throw new RangeError('Invalid interval');

  let lastRun: number | undefined;
  let timer: ReturnType<typeof setTimeout> | undefined;
  let args: Parameters<T> | undefined;
  let receiver: ThisParameterType<T> | undefined;

  function invoke(now: number) {
    if (args === undefined) return;
    const savedArgs = args;
    const savedReceiver = receiver as ThisParameterType<T>;
    args = undefined;
    receiver = undefined;
    lastRun = now;
    fn.apply(savedReceiver, savedArgs);
  }

  const wrapped = function(this: ThisParameterType<T>, ...nextArgs: Parameters<T>) {
    if (!leading && !trailing) return;
    const now = performance.now();
    args = nextArgs;
    receiver = this;

    if (lastRun === undefined) {
      if (leading) {
        invoke(now);
        return;
      }
      lastRun = now;
    }

    const remaining = interval - (now - lastRun);
    if (remaining <= 0) {
      if (timer !== undefined) clearTimeout(timer);
      timer = undefined;
      invoke(now);
    } else if (trailing && timer === undefined) {
      timer = setTimeout(() => {
        timer = undefined;
        invoke(performance.now());
      }, remaining);
    } else if (!trailing) {
      args = undefined;
      receiver = undefined;
    }
  } as Throttled<T>;

  wrapped.cancel = () => {
    if (timer !== undefined) clearTimeout(timer);
    timer = undefined;
    lastRun = undefined;
    args = undefined;
    receiver = undefined;
  };
  wrapped.flush = () => {
    if (timer === undefined) return;
    clearTimeout(timer);
    timer = undefined;
    invoke(performance.now()); // Explicitly runs early and resets the interval.
  };
  return wrapped;
}
```

This version uses `performance.now()` so elapsed time is measured with a monotonic clock. It returns `void`; an async callback must handle its own rejection. `flush()` deliberately overrides the interval, and `cancel()` drops pending work and resets the wrapper. Neither stops work that already started.

With `leading: false`, the first call waits one full interval. With `trailing: false`, suppressed calls are discarded, including the final position. With both options disabled, nothing runs. Timer callbacks can be delayed by event-loop work or browser throttling, so intervals define eligibility, not exact execution times.

## Match the scheduling policy to the work

- **Scroll/resize state:** A trailing throttle can keep a displayed value reasonably current. If the work is visual, `requestAnimationFrame` can coalesce events to a rendering opportunity; it does not promise a fixed frame rate.
- **Search input:** Usually debounce because the desired trigger is a pause. Throttle is appropriate only when periodic suggestions during continuous typing are part of the product contract.
- **One request in flight:** A throttle only spaces starts. Use an in-flight guard if requests must not overlap.
- **One durable write:** Client throttling cannot guarantee deduplication across retries, tabs, or devices. Enforce idempotency or rate limits at the server boundary.
- **Audit, billing, or event counts:** Do not discard intermediate calls. Queue, aggregate under an explicit rule, or persist every required event.

The wrapper owns its timer and latest pending arguments. Create it once for the event source's lifetime, remove the listener and call `cancel()` during cleanup, and avoid retaining large event objects longer than necessary. Server-rendered code must wait until mount/effect before reading `window`.

## Summary

Throttle admits work periodically during a continuing event stream. Define leading and trailing behavior, the spacing reference point, and whether dropping intermediate values is acceptable. Use a guard for concurrency and server-side idempotency for durable writes; a timer cannot supply either guarantee.

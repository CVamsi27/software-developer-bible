# Throttle

## Definition

**Throttling** is a technique that limits how often a function can execute. It ensures a function is called at most once in a specified time period, regardless of how many times it's triggered.

> **Textbook Definition:** Throttling bounds callback frequency by admitting invocations according to a time-window policy. Leading and trailing behavior determines whether intermediate calls are discarded or represented by a later invocation.


## First Principles

Throttle answers the case debounce cannot:

1. **Continuous events may not leave a quiet period.** Scroll or mouse-move events can keep resetting a debounce timer. When feedback must continue, limit how often work runs rather than waiting for the burst to end. The throttle's interval and leading/trailing policy decide which calls run.
2. **Throttling may discard intermediate values.** This can suit a progress indicator or current scroll position. It does not suit work that must record every keystroke (→ 10.1.4.04).
3. **A timestamp or timer controls the next allowed execution.** A trailing invocation can remember the latest arguments and run them when the current window ends, so the final event is not lost. Choose that policy deliberately rather than assuming every throttle preserves it.

Choose by the feedback contract: wait for quiet with debounce, or keep producing periodic feedback with throttle. A trailing call can preserve the final value in either policy; continuous input can postpone a debounce indefinitely unless it has a maximum wait.


## Why It Matters

Debounce and throttle can each offer leading and trailing options; the distinction is quiet-period reset versus periodic execution policy. For scroll/resize tied to rendering, use rAF throttling; for input-driven search, use debounce. Throttle is what you reach for when you need consistent execution rate, not just delay.

## Code Examples

### Preserve the spacing after a trailing call

This wrapper uses a monotonic clock (`performance.now`) to measure elapsed time. It owns the last execution time, one pending timer and the latest suppressed arguments. Leading execution admits the first call immediately; trailing execution keeps the final suppressed value. The wrapper returns `void`, so an async callback owns its rejection and callers do not receive individual results.

```typescript
function throttle<T extends (...args: any[]) => any>(
  func: T,
  limit: number,
  { leading = true, trailing = true } = {}
): ((...args: Parameters<T>) => void) & { cancel: () => void; flush: () => void } {
  if (!Number.isFinite(limit) || limit < 0) throw new RangeError('Invalid limit');
  let timer: ReturnType<typeof setTimeout> | null = null;
  let lastRun: number | null = null;
  let args: Parameters<T> | null = null;
  let receiver: any;

  function invoke(now: number) {
    if (args === null) return;
    const savedArgs = args;
    const savedReceiver = receiver;
    args = null;
    receiver = undefined;
    lastRun = now; // Includes trailing calls; do this before invoking user code.
    func.apply(savedReceiver, savedArgs);
  }
  function schedule(delay: number) {
    timer = setTimeout(() => {
      timer = null;
      invoke(performance.now());
    }, delay);
  }

  const wrapped = function(this: any, ...nextArgs: Parameters<T>) {
    if (!leading && !trailing) return;
    const now = performance.now();
    args = nextArgs;
    receiver = this;
    if (lastRun === null) {
      lastRun = now;
      if (leading) { invoke(now); return; }
    }
    const remaining = limit - (now - lastRun);
    if (remaining <= 0) {
      if (timer !== null) clearTimeout(timer);
      timer = null;
      if (leading) invoke(now);
      else { lastRun = now; schedule(limit); }
    } else if (trailing && timer === null) {
      schedule(remaining);
    }
    if (!trailing) { args = null; receiver = undefined; }
  };
  wrapped.cancel = () => {
    if (timer !== null) clearTimeout(timer);
    timer = null;
    lastRun = null;
    args = null;
    receiver = undefined;
  };
  wrapped.flush = () => {
    if (timer === null) return;
    clearTimeout(timer);
    timer = null;
    invoke(performance.now());
  };
  return wrapped;
}
```

With a 100ms limit, calls at 0, 30 and 90ms produce the first value at 0 and the latest pending value at about 100ms. A call at 101ms must wait until about 200ms: the trailing execution at 100ms started the next spacing interval. A flag that simply resets at 100ms would incorrectly admit another execution immediately at 101ms. Delayed timers may run later than their requested time; ordinary execution is bounded by the actual last run.

With `leading: false`, a lone call waits one interval. With `trailing: false`, calls inside the interval are discarded, including the final position. Both disabled means no work. `cancel` drops pending work and resets the window. `flush` deliberately runs a pending value early, overriding normal spacing; neither method stops already-running async work. This is a local callback policy, not a server rate limiter or a concurrency limit.

### React Hook

```typescript
import { useEffect, useMemo, useRef } from 'react';

function useThrottle<T extends (...args: any[]) => any>(func: T, limit: number) {
  const latest = useRef(func);
  useEffect(() => { latest.current = func; }, [func]);
  const wrapped = useMemo(
    () => throttle((...args: Parameters<T>) => latest.current(...args), limit),
    [limit]
  );
  useEffect(() => () => wrapped.cancel(), [wrapped]);
  return wrapped;
}

function ScrollComponent() {
  const onScroll = useThrottle(() => console.log(window.scrollY), 100);
  useEffect(() => {
    window.addEventListener('scroll', onScroll);
    return () => window.removeEventListener('scroll', onScroll);
  }, [onScroll]);
  return <div>Scroll content</div>;
}
```

The hook keeps timing state across renders while `limit` stays the same, uses the latest committed callback, and cancels pending work when replaced or unmounted. Suppressed calls replace the pending arguments, so the trailing call receives the newest event rather than the first discarded one. Application examples below assume React imports and the wrapper above.

## Real-World Use Cases

### 1. Scroll Event Handler

```typescript
function useScrollProgress() {
  const [progress, setProgress] = useState(0);

  useEffect(() => {
    const handleScroll = throttle(() => {
      const scrollTop = window.scrollY;
      const docHeight = document.documentElement.scrollHeight - window.innerHeight;
      const scrollPercent = docHeight > 0 ? (scrollTop / docHeight) * 100 : 0;
      setProgress(scrollPercent);
    }, 100);

    window.addEventListener('scroll', handleScroll);
    return () => {
      handleScroll.cancel();
      window.removeEventListener('scroll', handleScroll);
    };
  }, []);

  return progress;
}

```

### 2. Mouse Move Handler

```typescript
function useMousePosition() {
  const [position, setPosition] = useState({ x: 0, y: 0 });

  useEffect(() => {
    const handleMouseMove = throttle((e: MouseEvent) => {
      setPosition({ x: e.clientX, y: e.clientY });
    }, 50);

    window.addEventListener('mousemove', handleMouseMove);
    return () => {
      handleMouseMove.cancel();
      window.removeEventListener('mousemove', handleMouseMove);
    };
  }, []);

  return position;
}

```

### 3. Button Click Handler

A time window cannot enforce “one request in flight”: a request may last longer than the interval. For that contract, guard completion directly. The ref closes the gap before React renders the disabled state; the server still needs its own duplicate-write policy.

```typescript
function LikeButton() {
  const busy = useRef(false);
  const [likes, setLikes] = useState(0);
  const [isProcessing, setIsProcessing] = useState(false);
  const [error, setError] = useState('');

  async function handleLike() {
    if (busy.current) return;
    busy.current = true;
    setIsProcessing(true);
    setError('');
    try {
      await api.likePost(); // Application API; assume rejection for a failed write.
      setLikes(prev => prev + 1);
    } catch {
      setError('Could not record like');
    } finally {
      busy.current = false;
      setIsProcessing(false);
    }
  }
  return <>
    <button onClick={handleLike} disabled={isProcessing}>Like ({likes})</button>
    {error && <p role="alert">{error}</p>}
  </>;
}
```

### 4. Window Resize Handler

This viewport initializer is browser-only. A server-rendered component must start with a server-safe value and measure `window` after mounting. The final size arrives on the trailing call; a timer does not guarantee the UI paints at that same instant.

```typescript
function useWindowSize() {
  const [size, setSize] = useState({
    width: window.innerWidth,
    height: window.innerHeight
  });

  useEffect(() => {
    const handleResize = throttle(() => {
      setSize({
        width: window.innerWidth,
        height: window.innerHeight
      });
    }, 250);

    window.addEventListener('resize', handleResize);
    return () => {
      handleResize.cancel();
      window.removeEventListener('resize', handleResize);
    };
  }, []);

  return size;
}

```

### 5. Rate-Limiting a Fire-and-Forget Call

```typescript
// Throttle DISCARDS the excess — correct for telemetry, wrong for anything
// that must return a response (the dropped call would mean a dropped
// request/response cycle). Rate-limit beacons, not queries.
class Analytics {
  private sendBeacon = throttle((event: string) => {
    navigator.sendBeacon('/collect', event);
  }, 1000);

  track(event: string): void {
    this.sendBeacon(event); // at most one beacon per second
  }
}

// For a request/response API you need a QUEUE (or the server's own rate
// limit) — dropping the call would silently lose the user's action.
```

## Common Mistakes

### 1. Not Cleaning Up

```typescript
// Bad: No cleanup
useEffect(() => {
  const handleScroll = throttle(updatePosition, 100);
  window.addEventListener('scroll', handleScroll);
  // Missing cleanup!
}, []);

// Good: Proper cleanup
useEffect(() => {
  const handleScroll = throttle(updatePosition, 100);
  window.addEventListener('scroll', handleScroll);
  return () => {
    handleScroll.cancel();
    window.removeEventListener('scroll', handleScroll);
  };
}, []);

```

### 2. Wrong Limit Time

```typescript
// Too short: Still too frequent
const scroll = throttle(updatePosition, 10);

// Too long: Feels unresponsive
const scroll = throttle(updatePosition, 1000);

// Good: Balance based on use case
const scroll = throttle(updatePosition, 100);

```

### 3. Using Throttle for Debounce Cases

```typescript
// Bad: Throttle for search input
const search = throttle(fetchResults, 300);
// Still makes too many API calls

// Good: Use debounce for search
const search = debounce(fetchResults, 300);

```

### 4. Not Handling Trailing Call

```typescript
// Bad: Only leading edge
const fn = throttle(originalFn, 100, { trailing: false });
// Misses last call

// Good: Handle trailing
const fn = throttle(originalFn, 100, { trailing: true });

```

## Best Practices

### 1. Choose Appropriate Limit

```typescript
// Visual updates: consider requestAnimationFrame; a fixed interval does not guarantee a frame rate
const scroll = throttle(update, 16);

// Mouse move: 50ms
const mouse = throttle(update, 50);

// Button click: 1000ms
const click = throttle(handleClick, 1000);

// Resize: 250ms
const resize = throttle(update, 250);

```

### 2. Clean Up Throttled Functions

```typescript
useEffect(() => {
  const throttledFn = throttle(fn, limit);

  return () => {
    throttledFn.cancel();
  };
}, [fn, limit]);

```

### 3. Use Cancel Method

```typescript
// Cancel on unmount or when no longer needed
const throttledFn = throttle(fn, limit);

// Cleanup
throttledFn.cancel();

```

### 4. Consider Leading vs Trailing

```typescript
// Leading: Execute immediately, then throttle
const immediate = throttle(update, 100, { leading: true, trailing: false });

// Trailing: Execute at end of interval
const deferred = throttle(update, 100, { leading: false, trailing: true });

// Both: Execute at start and end
const both = throttle(update, 100, { leading: true, trailing: true });

```

## Performance Considerations

### Timer Overhead

```typescript
// Timer-based throttle variants use timers; timestamp-only variants may not
// Minimize by using requestAnimationFrame for animations

// Bad: Throttle for animations
const handleScroll = throttle(updateAnimation, 16);

// Good: Use requestAnimationFrame
let frame: number | null = null;
const handleScroll = () => {
  if (frame !== null) return;
  frame = requestAnimationFrame(() => {
    frame = null;
    updateAnimation();
  });
};
// Teardown removes the listener and cancels a pending frame.

```

### Memory Usage

```typescript
// Weak: a brand-new throttled function on every render.
// The abandoned ones are garbage, not a leak — the real costs are an
// unstable identity (re-fires effect deps, breaks memoized children) and a
// timer left over from a render whose state has already been superseded.
const Component = () => {
  const throttledFn = throttle(fn, 100);
  return <button onClick={throttledFn}>Click</button>;
};

// Better: keep ONE throttled function per stable `fn`.
// useCallback evaluates its argument every render, but hands back the first
// result while the deps stay unchanged, so identity remains constant.
const Component = () => {
  const throttledFn = useCallback(throttle(fn, 100), [fn]);
  return <button onClick={throttledFn}>Click</button>;
};

// Identity is only part of ownership: cancel replaced wrappers in an effect cleanup.
// useEffect(() => () => throttledFn.cancel(), [throttledFn]);
const Component = () => {
  const throttledFn = useMemo(() => throttle(fn, 100), [fn]);
  return <button onClick={throttledFn}>Click</button>;
};
```

## Summary

Throttling is essential for performance:

1. **Definition**: Limits function execution frequency

2. **Use cases**: Scroll, mouse move, button clicks

3. **Implementation**: Last execution time plus one pending trailing timer

4. **Options**: Leading, trailing, cancel, flush

5. **Performance**: Prevents excessive function calls

6. **Cleanup**: Always clean up timers

7. **Testing**: Use fake timers

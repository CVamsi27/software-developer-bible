# Memory Leaks

A Single Page Application navigates between dashboard routes for an hour until the browser tab consumes two gigabytes of RAM and crashes. The garbage collector never collected the unmounted views because global event listeners, forgotten timers, and detached DOM trees maintained unbroken retaining paths back to the application roots.

## Definition

A **memory leak** in a garbage-collected language occurs when memory that is no longer required by application logic remains allocated on the heap because unintended strong references maintain reachability from a Garbage Collection (GC) root. Because tracing garbage collectors cannot infer developer intent, reachable objects cannot be reclaimed.

> **Textbook Definition:** A memory leak in a managed runtime is the unintentional retention of heap-allocated memory caused by active reference chains originating from GC roots to obsolete data structures. Garbage collection algorithms reclaim exclusively unreachable memory; retaining paths created by closures, detached DOM subtrees, unmanaged intervals, and unbounded caches prevent reclamation.

## First Principles

1. **Reachability Governs Collection:** The engine's garbage collector does not determine whether an object is *useful*; it determines strictly whether an object is *reachable* via a chain of references originating from GC roots (global object, call stack frames, DOM document).

2. **Retaining Paths and Retained Size:** An object's *shallow size* is the memory consumed by its own direct properties and header. Its *retained size* is the total memory freed if that object and all descendants reachable exclusively through it were reclaimed.

3. **Detached Subtree Cascades:** In DOM tree architectures, child nodes retain parent nodes via internal `.parentNode` pointers. Holding a reference to a single detached table cell prevents the garbage collector from reclaiming the entire detached parent table and view hierarchy.

4. **Shared Closure Context Allocation:** V8 allocates a single shared `Context` object for all closures declared within the same parent lexical scope. A long-lived closure retains all variables enclosed in that shared context, even variables it never reads.

```text
GC Roots (window / global / Active Call Stack)
      │
      ▼ (Strong Pointer)
[ Global Window Object ]
      │
      ├── .addEventListener('resize', handler)
      │                                  │
      │                                  ▼
      │                     [ Closure Context Scope ]
      │                                  │
      │                                  ▼
      │                     [ Detached Component View ] ──▶ Retains 50MB Heap
      │
      └── (Active View Transition Disposed)
```

## The Five Classical Memory Leaks in JavaScript

### 1. Forgotten Timers and Intervals

`setInterval` and `setTimeout` hold references to their callback closures in the host's internal timer queue until explicitly cleared:

```javascript
// LEAK: Timer runs indefinitely, retaining component and data
function startMetricsCollector(componentInstance) {
  const heavyDataBuffer = new Uint8Array(10_000_000); // 10MB

  setInterval(() => {
    // The closure retains heavyDataBuffer AND componentInstance
    console.log('Heartbeat:', componentInstance.id);
  }, 1000);
}
```

Even if `componentInstance` is unmounted and discarded from the DOM, the host timer registry continues executing the callback, preventing both the closure and `heavyDataBuffer` from being collected.

- **Remedy:** Always store timer IDs and call `clearInterval(timerId)` during lifecycle teardown.

### 2. Unregistered Global Event Listeners and Observers

Registering event listeners on global objects (`window`, `document`, `navigator`) establishes strong references from the global GC root:

```javascript
export function attachPreviewModal() {
  const container = document.createElement('div');
  const onWindowResize = () => {
    container.style.width = `${window.innerWidth}px`;
  };

  window.addEventListener('resize', onWindowResize);
  document.body.appendChild(container);

  // TEARDOWN CONTRACT: Must remove listener when element is destroyed
  return function teardown() {
    window.removeEventListener('resize', onWindowResize);
    container.remove();
  };
}
```

Calling `container.remove()` without `window.removeEventListener()` leaves `window` pointing to `onWindowResize`, which closes over `container`, keeping the entire container allocated in memory.

### 3. Detached DOM Trees (The Leaf Node Trap)

Removing a DOM node from the document disconnects it from the render tree, but keeping a reference to *any* element inside that subtree keeps the *entire* subtree in memory:

```javascript
let detachedCellReference;

function leakTable() {
  const table = document.createElement('table');
  for (let i = 0; i < 1000; i++) {
    const row = table.insertRow();
    const cell = row.insertCell();
    cell.textContent = `Cell data ${i}`;
  }
  document.body.appendChild(table);

  // Retain a reference to just ONE inner cell:
  detachedCellReference = table.rows[500].cells[0];

  // Remove table from DOM:
  table.remove();
}
```

Even though `table` was removed, `detachedCellReference` holds an internal pointer to `table.rows[500]`, which holds a pointer up to `table`. The entire 1,000-row table remains retained in memory as a **Detached DOM Tree**.

- **Remedy:** Set DOM element variables to `null` when elements are removed: `detachedCellReference = null`.

### 4. Shared Lexical Scope Closure Leak (The V8 Context Trap)

When multiple functions are declared in the same scope, V8 merges their captured variables into a shared heap-allocated `Context` record:

```javascript
let globalLeaker;

function outerScope() {
  const hugeBuffer = new Array(1_000_000).fill('*'); // ~8MB

  // Closure A: Captures hugeBuffer
  function unusedClosure() {
    if (hugeBuffer) return hugeBuffer;
  }

  // Closure B: Does NOT read hugeBuffer, but shares the same Lexical Context!
  return function exportedClosure() {
    console.log('I only print a string');
  };
}

// Every invocation links a new exportedClosure to a context holding hugeBuffer:
setInterval(() => {
  globalLeaker = outerScope(); // Keeps hugeBuffer alive in heap!
}, 100);
```

Because `unusedClosure` touches `hugeBuffer`, V8 places `hugeBuffer` in the parent `Context`. `exportedClosure` is assigned to `globalLeaker`, keeping the entire `Context` (and `hugeBuffer`) alive forever.

### 5. Unbounded Caches and Persistent Maps

Using a standard `Map` as an in-memory cache without eviction guarantees a memory leak:

```typescript
// LEAK: Unbounded Map grows indefinitely
const queryCache = new Map<string, unknown>();

export async function fetchWithCache(query: string) {
  if (queryCache.has(query)) return queryCache.get(query);
  const data = await executeQuery(query);
  queryCache.set(query, data); // Never evicts entries!
  return data;
}
```

- **Remedy:** Replace unbounded `Map` instances with an `LruCache` with a strict `maxSize` cap, or use `WeakMap` if keys are objects whose lifecycle is tied to caller ownership.

## Profiling and Diagnosing Leaks in Chrome DevTools

1. **Take Baseline Snapshot:** Open Chrome DevTools → Memory Panel → Select **Heap snapshot** → Take Snapshot 1.

2. **Execute Action Iterations:** Perform the suspect user action (e.g. open and close a modal) 10 consecutive times.

3. **Force Garbage Collection:** Click the trash can icon (**Collect Garbage**) in DevTools to eliminate transient garbage.

4. **Take Comparison Snapshot:** Take Snapshot 2 → Switch dropdown view from **"Summary"** to **"Comparison"** (Snapshot 2 vs Snapshot 1).

5. **Inspect Delta and Detached Elements:**
   - Filter by **Detached** to locate detached HTML elements (highlighted in yellow or red).
   - Expand the suspect class/object to inspect the **Retainers** tree at the bottom.
   - The Retainers pane displays the exact path of pointers holding the object alive up to the `window` GC root.

## Node.js Memory Diagnostics

In Node.js backend processes, inspect memory allocation via `process.memoryUsage()`:

| Metric | Meaning | Normal Production Profile |
| :------------------------ | :------------------------------------------------------- | :--------------------------------------- |
| **`rss`** (Resident Set Size) | Total process RAM allocated in physical memory | Stable baseline under sustained load |
| **`heapTotal`** | Total memory allocated by V8 for heap structures | Scales with heap demands |
| **`heapUsed`** | Actual memory occupied by live JavaScript objects | Periodic saw-tooth pattern (drops on GC) |
| **`external`** | Memory allocated by C++ bindings (e.g. `Buffer`, crypto) | Monitored when streaming heavy I/O |

A steady, monotonic climb in `heapUsed` that does not reset following major garbage collection cycles is conclusive evidence of a memory leak.

## Summary

Memory leaks in JavaScript occur not when memory is unreferenced, but when obsolete memory remains reachable from GC roots. Classical leaks stem from:

- **Forgotten intervals** — `setInterval`/`setTimeout` without `clearInterval`/`clearTimeout`
- **Global event listeners** — Registered without corresponding removal
- **Detached DOM trees** — References to removed elements retained entire subtrees
- **Shared closure contexts** — V8 Context records keeping entire scopes alive
- **Unbounded caches** — Maps/growing data structures without eviction

Diagnosing leaks requires inspecting retained sizes and retaining paths in DevTools heap snapshots, while architectural resilience requires pairing every resource allocation with explicit teardown contracts.

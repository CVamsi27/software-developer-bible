# Memory Leaks

## Definition

A **Memory Leak** occurs when a program allocates memory but fails to release it when no longer needed. In JavaScript, this happens when objects are no longer used but still have references, preventing garbage collection.

> **Textbook Definition:** A memory leak is retained memory whose lifetime exceeds the application need it serves. In a tracing garbage-collected runtime, unintended reachable paths can keep obsolete objects alive despite correct automatic collection.


## First Principles

Every leak reduces to one definition, which is why the fixes generalize:

1. **A reachable object can still be unwanted.** The garbage collector frees unreachable objects (→ 10.1.4.07); it cannot infer whether you still want a reachable one. A long-lived timer, listener, cache or closure can keep data alive after the application has finished using it.
2. **Cleanup removes the references that keep unwanted data alive.** Clearing timers, removing listeners, clearing arrays and using weak collections for suitable metadata all address retention. Capacity limits and expiry keep containers from growing without bound. **Backpressure**, making producers slow down when consumers cannot keep up, can also prevent retained work from accumulating.
3. **Every resource needs a cleanup owner.** The code that creates a listener, timer or subscription must arrange to release it, either directly or through an explicit owner. A component effect can tie that cleanup to the component's lifetime.


## Why It Matters

Senior engineers audit for leaks in: SPA route changes (listeners on document/window), Node servers (growing Map keyed by request ID without eviction), and React effects (subscriptions in useEffect without cleanup). The pattern is always: every acquisition has a paired release.

## How It Works

### Follow the retaining path

A **retaining path** is a chain of references from a runtime root to an object. A detached node is merely outside the document tree; a reachable callback can still keep it alive. These two paths differ:

```text
window -> resize listener -> callback -> detached button   (still reachable)
detached button -> its click listener -> button            (cycle without a root)
```

Removing a button breaks the document's path to it, but does not remove a listener registered on `window`. That first path needs explicit teardown. The second cycle can be collected when no other path reaches it. A closure and a listener are not leaks by themselves; the defect is a lifetime longer than the application needs. Timers and caches create the same kind of long-lived path.

### Diagnose growth across repeated lifetimes

Use a repeatable action, such as opening and closing the same route ten times. Let pending work finish, compare heap snapshots at equivalent idle points, then inspect retained objects and their paths to roots. A growing post-collection baseline is a clue; temporary allocation spikes, deliberate caches and browser/native memory need separate interpretation. Removing the suspected path and repeating the action tests the proposed cause.

Chrome's Memory panel can show snapshots, detached nodes and allocation profiles. `performance.memory` is a deprecated, nonstandard Chromium-specific estimate of the JavaScript heap, not portable total-page memory. Feature-detect it if used for a local experiment; do not treat one high reading or a fixed percentage as proof of a leak.

## Code Examples

### Global Variable Leak

```typescript
// Browser classic script in sloppy JavaScript only; strict mode/modules throw.
// This intentionally invalid TypeScript assignment illustrates an implicit global.
function leak() {
  leakedArray = []; // Implicit global!
  for (let i = 0; i < 1000000; i++) {
    leakedArray.push(i);
  }
}

// Good: Use const/let
function noLeak() {
  const localArray = [];
  for (let i = 0; i < 1000000; i++) {
    localArray.push(i);
  }
}

```

### Forgotten Timer

```typescript
// Bad: Timer not cleared — the interval fires forever, and the closure over
// `data` means 1M elements stay resident for the life of the process.
function startTimer() {
  const data = new Array(1000000).fill(0);

  setInterval(() => {
    console.log(data.length); // data kept alive
  }, 1000);
}

// Good: the code that starts the timer also owns its teardown, and hands the
// handle back so the owner can clear it (route change, job done, unmount).
function startTimerFixed() {
  const data = new Array(1000000).fill(0);

  const intervalId = setInterval(() => {
    console.log(data.length);
  }, 1000);

  return () => clearInterval(intervalId);
}

```

### Detached DOM

```typescript
function mountPreview() {
  const button = document.createElement('button');
  const onResize = () => { button.textContent = String(window.innerWidth); };
  document.body.appendChild(button);
  window.addEventListener('resize', onResize);

  return () => {
    window.removeEventListener('resize', onResize);
    button.remove();
  };
}

const dispose = mountPreview();
// Owner calls dispose on route exit, then drops its reference to this disposer.
dispose();
```

If route exit only calls `button.remove()`, `window` still owns `onResize`, which can still access the button. The disposer removes that path and detaches the node. If the owner itself stores the disposer forever, that closure can retain the button too; cleanup ownership includes retiring the cleanup handle. A listener registered only on an otherwise unreachable button does not keep the button alive from a root.

### Closure Memory Leak

```typescript
// Bad: the handler READS the array, so the scope holding it stays alive for
// as long as anything references the handler — every listener, timeout or
// subscription that pins the handler pins all 1M elements with it.
function createHandler() {
  const hugeData = new Array(1000000).fill(0);

  return function handler() {
    return hugeData.length; // referenced → retained
  };
}

// Good: hoist the one value you need out of the scope. Do not rely on a particular engine's closure-slot optimization. Separate the large-data lifetime from the listener's lifetime and inspect retaining paths when it matters.
function handlerForLength(length: number) {
  return () => console.log(length);
}
function createHandlerFixed() {
  const hugeData = new Array(1000000).fill(0);
  return handlerForLength(hugeData.length);
}

```

### Event Listener Leak

These are alternative class lifecycle sketches; assume `handleResize` is a stable instance method. Creating a fresh bound function in cleanup would fail to remove the original listener.

```typescript
// Bad: Not removing listener
class Component {
  componentDidMount() {
    window.addEventListener('resize', this.handleResize);
  }

  // componentWillUnmount() missing!
}

// Good: Proper cleanup
class Component {
  componentDidMount() {
    window.addEventListener('resize', this.handleResize);
  }

  componentWillUnmount() {
    window.removeEventListener('resize', this.handleResize);
  }
}

```

### React useEffect Leak

```typescript
// Bad: Missing cleanup
useEffect(() => {
  const subscription = api.subscribe(data => {
    setData(data);
  });
  // Missing cleanup!
}, []);

// Good: Proper cleanup
useEffect(() => {
  const subscription = api.subscribe(data => {
    setData(data);
  });

  return () => {
    subscription.unsubscribe();
  };
}, []);

```

### Array Growth

```typescript
// Bad: Array keeps growing
const cache: any[] = [];

function addToCache(item: any) {
  cache.push(item); // Never cleaned!
}

// Good: Limit cache size
const cache: any[] = [];
const MAX_CACHE_SIZE = 1000;

function addToCacheFixed(item: any) {
  cache.push(item);
  if (cache.length > MAX_CACHE_SIZE) {
    cache.shift(); // Remove oldest
  }
}

```

### WeakMap metadata follows key lifetime

```typescript
// Good: Use WeakMap for object references
const cache = new WeakMap();

function processObject(obj: object) {
  if (cache.has(obj)) {
    return cache.get(obj);
  }

  const result = expensiveComputation(obj);
  cache.set(obj, result);
  return result;
  // When obj is garbage collected, cache entry is removed
}

```

## Real-World Use Cases

### 1. Component Cleanup (React)

Assume React imports and an endpoint returning application data. The effect owns the controller and handles its task's rejection. Aborting on cleanup prevents this request from outliving the effect; it cannot roll back a server write. A real endpoint also needs schema validation before treating JSON as application data.

```typescript
function DataComponent() {
  const [data, setData] = useState<unknown>(null);
  const [error, setError] = useState('');

  useEffect(() => {
    const controller = new AbortController();

    async function fetchData() {
      try {
        const response = await fetch('/api/data', {
          signal: controller.signal
        });
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const result: unknown = await response.json();
        if (!controller.signal.aborted) setData(result);
      } catch (error) {
        if (!controller.signal.aborted) setError('Could not load data');
      }
    }

    fetchData();

    return () => {
      controller.abort();
    };
  }, []);

  return <div>{error || JSON.stringify(data)}</div>;
}

```

### 2. Event Delegation

Delegation reduces listener count by putting one listener on a container. It still needs an owner and cleanup; child removal alone does not retire the container listener. `closest` lets a click on an item's nested label resolve to the item, and containment excludes matches outside the intended subtree.

```typescript
function setupItems(container: HTMLElement) {
  const onClick = (event: MouseEvent) => {
    if (!(event.target instanceof Element)) return;
    const item = event.target.closest('.item');
    if (item && container.contains(item)) handleClick(event); // Application action
  };
  container.addEventListener('click', onClick);
  return () => container.removeEventListener('click', onClick);
}
```

### 3. Object pooling retains spare capacity

A pool keeps released objects so another operation can reuse them. That intentionally extends their lifetime: an unbounded pool can retain the peak load forever. Cap the number of idle objects, clear references to prior payloads before returning objects, and prevent borrowers from releasing the same object twice. Use the [GC chapter's pooling trade-offs](10.1.4.07-garbage-collection.md#object-pooling) before choosing pooling over normal allocation.

### 4. Cache with Expiration

**Time to live (TTL)** is the validity duration after insertion. `get` deletes an expired entry only when that key is read. Unread expired entries remain in this strong `Map` until `cleanup` runs; the owner must schedule and stop that cleanup, and add a capacity bound for high insertion rates. Expiry controls usefulness; collection requires deleting the retained reference.

```typescript
class Cache<K, V> {
  private cache = new Map<K, { value: V; timestamp: number }>();
  private ttl: number;

  constructor(ttl: number = 60000) {
    this.ttl = ttl;
  }

  set(key: K, value: V) {
    this.cache.set(key, { value, timestamp: Date.now() });
  }

  get(key: K): V | undefined {
    const entry = this.cache.get(key);
    if (!entry) return undefined;

    if (Date.now() - entry.timestamp > this.ttl) {
      this.cache.delete(key);
      return undefined;
    }

    return entry.value;
  }

  cleanup() {
    const now = Date.now();
    for (const [key, entry] of this.cache) {
      if (now - entry.timestamp > this.ttl) {
        this.cache.delete(key);
      }
    }
  }
}

```

## Common Mistakes

### 1. Not Cleaning Up useEffect

```typescript
// Bad
useEffect(() => {
  const handler = () => console.log('resize');
  window.addEventListener('resize', handler);
}, []);

// Good
useEffect(() => {
  const handler = () => console.log('resize');
  window.addEventListener('resize', handler);
  return () => window.removeEventListener('resize', handler);
}, []);

```

### 2. Retaining more state than the UI needs

```typescript
// Full data is appropriate if the UI needs it; size alone does not imply a leak.
const [data, setData] = useState(largeObject);

// If only the summary is needed, avoid retaining the entire source graph.
const [summary, setSummary] = useState(extractSummary(largeObject));

```

### 3. Choosing strong or weak ownership

```typescript
// Use Map when entries need explicit enumeration, capacity or reliable lifetime.
const cache = new Map();
cache.set(obj, result);

// Use WeakMap for metadata that should live only while an object key is reachable.
const cache = new WeakMap();
cache.set(obj, result);

```

### 4. Global State Growth

```typescript
// Bad: Global state keeps growing
const globalState = {
  items: [] // Never cleaned!
};

// Good: Implement cleanup
const globalState = {
  items: [],
  cleanup() {
    this.items = [];
  }
};

```

## Best Practices

### 1. Always Clean Up

```typescript
// React
useEffect(() => {
  const subscription = subscribe();
  return () => subscription.unsubscribe();
}, []);

// Vanilla JS
const handler = () => {};
element.addEventListener('click', handler);
// Later
element.removeEventListener('click', handler);

```

### 2. Use WeakMap/WeakRef

```typescript
// For object caches
const cache = new WeakMap();

// For event listeners on objects
const listeners = new WeakMap<object, Function>();

```

### 3. Limit Cache Size

```typescript
class LimitedCache<T> {
  private cache = new Map<string, T>();
  private maxSize: number;

  constructor(maxSize: number = 1000) {
    if (!Number.isInteger(maxSize) || maxSize < 1) throw new RangeError('Invalid capacity');
    this.maxSize = maxSize;
  }

  set(key: string, value: T) {
    if (!this.cache.has(key) && this.cache.size >= this.maxSize) {
      const firstKey = this.cache.keys().next().value;
      this.cache.delete(firstKey!);
    }
    this.cache.set(key, value);
  }
}

```

### 4. Pool only when profiling justifies retained objects

Profile allocation rate and pauses before introducing a pool. Cap idle capacity and reset returned objects; the pool itself becomes an intentional retaining root. Pools that improve a short benchmark may increase the long-lived heap of a real session.

## Performance Considerations

### Memory Monitoring

```typescript
function monitorMemory() {
  const memory = (performance as any).memory; // Nonstandard; local Chromium experiment
  if (memory) {
    const used = memory.usedJSHeapSize / 1024 / 1024;
    const total = memory.jsHeapSizeLimit / 1024 / 1024;
    console.log(`Memory: ${used.toFixed(2)}MB / ${total.toFixed(2)}MB`);
  }
}

const monitoring = setInterval(monitorMemory, 5000);
// Owner stops monitoring when the experiment ends: clearInterval(monitoring);

```

### Garbage Collection Impact

Allocation rate and retained size are different measurements. Fewer allocations may reduce collection work but in-place mutation can break state snapshots or other owners. Both examples still allocate a result array. Choose the ownership contract first, then measure the hot path; immutable copying is not automatically a leak.

```typescript
// Frequent GC causes jank
// Reduce allocations in hot paths

// Bad: Creates new objects
function processItems(items: any[]) {
  return items.map(item => ({ ...item, processed: true }));
}

// In-place variant: safe only when callers give exclusive mutation ownership.
function processItems(items: any[]) {
  return items.map(item => {
    item.processed = true;
    return item;
  });
}

```

## Summary

Memory leaks are critical to prevent:

1. **Causes**: Detached DOM, forgotten timers, closures, global variables

2. **Detection**: Repeated-lifetime heap snapshots and retaining paths

3. **Prevention**: Paired cleanup, suitable weak metadata, bounded caches/pools

4. **React**: Always clean up useEffect

5. **Performance**: Monitor memory, reduce allocations

6. **Best practices**: Document cleanup, test for leaks

7. **Tools**: Chrome DevTools, memory profilers

# Memory Leaks

## Definition

A **memory leak** is memory that remains retained after the application no longer needs it. JavaScript's garbage collector reclaims unreachable objects, but it cannot infer that a reachable cache entry, callback, node, or queued task has become obsolete.

> **Textbook Definition:** A memory leak is retained storage whose lifetime exceeds the useful lifetime of the data it contains. In a tracing garbage-collected runtime, unintended strong-reference paths can keep obsolete objects reachable and prevent reclamation.

## First Principles

The key question is not “how much did the program allocate?” It is “what still owns this data, and should that owner still exist?” Allocation creates objects; retaining references determines whether they remain live. A timer, listener, module-level cache, subscription, or growing queue can be the long-lived owner.

## Find the retaining path

A **retaining path** is a chain of references from a runtime root to an object. A detached DOM node can remain alive if a global listener closes over it:

```text
window → resize listener → callback → detached button
```

A cycle with no path from a root is different:

```text
detached button → click listener → button
```

The second cycle can be collected. The first needs its owner to remove the listener. Closures and listeners are not leaks by themselves; their lifetimes become a problem when they preserve data longer than the work that needs it.

Give each resource one cleanup owner. The code that registers the listener also removes it; the code that starts the timer also clears it; a subscription owner also unsubscribes. Stop producers as well as deleting accumulated work, or the same data will immediately return. For asynchronous work, abort where possible and invalidate stale completions before they can publish results.

```js
function mountPreview() {
  const button = document.createElement('button');
  const onResize = () => { button.textContent = String(window.innerWidth); };
  document.body.append(button);
  window.addEventListener('resize', onResize);

  return () => {
    window.removeEventListener('resize', onResize);
    button.remove();
  };
}
```

The returned disposer must itself be retired by the route or component owner. Removing the button alone leaves the `window → callback → button` path intact.

## Distinguish leaks from expected memory

Reproduce the same lifecycle repeatedly—for example, open and close one route ten times. Let expected work finish, compare heap snapshots at equivalent idle points, and inspect objects that remain along with their paths to roots. A growing post-workload baseline is evidence to investigate, not proof on its own: delayed collection, warmed caches, and native or graphics memory can also raise process memory.

In browser DevTools, heap snapshots expose retained objects and detached nodes; allocation profiles help locate creation sites. `performance.memory` is a deprecated, nonstandard Chromium estimate of JavaScript heap, not total page or process memory. In Node.js, inspect heap snapshots and process metrics separately: `heapUsed`, external memory, and resident set size describe different parts of memory use. Compare equivalent workload phases rather than reacting to a single high reading.

Closures deserve the same evidence-based treatment. If a retained callback reads a large value, the callback can preserve access to it. Source syntax alone does not prove which slots an engine physically retains; inspect the retaining path. Move the callback to a smaller scope when only a derived scalar is needed, rather than relying on engine optimization.

## Bound what is intentionally retained

A strong `Map` is appropriate when entries must be enumerated or evicted, but a long-lived, unbounded map grows for as long as distinct keys arrive. Capacity limits entry count; it does not bound bytes if values vary widely. Expiry is a usefulness policy, not garbage collection: deleting an expired entry removes the strong reference. A TTL cache that only checks on reads can still retain expired, unread entries indefinitely.

Weak collections solve a narrower problem. A `WeakMap` does not keep an eligible key alive solely because it is a key, which suits per-object metadata (→ [Map and WeakMap](10.1.4.02-map-set-weakmap-weakset.md)). If the key remains reachable, its associated value remains reachable too. Weak collections cannot enumerate entries or provide deterministic expiry, and they do not unregister listeners or close sockets.

Object pools deliberately retain idle objects for reuse. Cap idle capacity, reset payload references, prevent duplicate release, and profile first; pooling can trade allocation work for a large retained heap. If producers outrun consumers, apply backpressure or bounded queues instead of merely collecting more often.

## Summary

A leak is unwanted lifetime, not a large allocation or a detached node by itself. Repeat a controlled workload, inspect what remains and follow its retaining path to the owner. Remove or bound the unwanted ownership, stop producers, and clean up external resources explicitly. Measure JavaScript heap separately from buffers, native memory, and process RSS.

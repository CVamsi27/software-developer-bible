# Memory Leaks

An SPA keeps growing after repeated dashboard route changes. The collector cannot free the old views — global listeners, forgotten timers, and detached DOM trees kept unbroken retaining paths to the roots.

```javascript
// Without calling the disposer, this interval retains the instance and buffer.
function startMetricsCollector(componentInstance) {
  const heavyDataBuffer = new Uint8Array(10_000_000); // 10MB

  const intervalId = setInterval(() => {
    console.log('Heartbeat:', componentInstance.id, heavyDataBuffer.byteLength);
  }, 1000);
  return () => clearInterval(intervalId);
}
```

## Definition

A **memory leak** in a garbage-collected language is heap memory the app no longer needs but the collector cannot reclaim — because unintended strong references keep it **reachable** from a GC root. Tracing collectors cannot read intent; reachable means retained.

> **Textbook Definition:** A memory leak in a managed runtime is the unintentional retention of heap-allocated memory caused by active reference chains originating from GC roots to obsolete data structures. Garbage collection algorithms reclaim exclusively unreachable memory; retaining paths created by closures, detached DOM subtrees, unmanaged intervals, and unbounded caches prevent reclamation.

## First Principles

The collector asks only whether an object is **reachable** from roots (global object, active stack frames, `document`) — never whether it is *useful*. What matters diagnostically is **retained size**: the memory freed if an object plus everything reachable exclusively through it were collected — at least its shallow size under the profiler's accounting, and possibly much larger. A retained DOM leaf can keep its still-linked detached subtree reachable. Closure representation is engine-specific: some optimized or materialized contexts retain additional bindings, while others eliminate unused state. The retaining path in the actual snapshot decides what is held.

```text
GC Roots (window / global / Active Call Stack)
      │
      ▼ (Strong Pointer)
[ Global Window Object ]
      │
      ├── .addEventListener('resize', handler)
      │                                  │
      │                                  ▼
      │                     [ Closure Context Scope ]
      │                                  │
      │                                  ▼
      │                     [ Detached Component View ] ──▶ Retains obsolete view data
      │
      └── (Active View Transition Disposed)
```

## 1. The Five Classical Memory Leaks in JavaScript

**1. Forgotten timers and intervals.** The host retains pending timer callbacks until they fire or are cleared; an interval keeps scheduling until its owner clears it. Unmounting the component changes nothing — the heartbeat above runs forever, retaining both the closure and the 10MB buffer. **Remedy**: store timer IDs and `clearInterval` in teardown.

**2. Unregistered global event listeners.** Listeners on `window`/`document` root the handler — and everything it closes over:

```javascript
export function attachPreviewModal() {
  const container = document.createElement('div');
  const onWindowResize = () => {
    container.style.width = `${window.innerWidth}px`;
  };

  window.addEventListener('resize', onWindowResize);
  document.body.appendChild(container);

  // TEARDOWN CONTRACT: Must remove listener when element is destroyed
  return function teardown() {
    window.removeEventListener('resize', onWindowResize);
    container.remove();
  };
}
```

`container.remove()` alone leaves `window → onWindowResize → container` intact — the "removed" element stays allocated.

**3. Detached DOM trees (the leaf-node trap).** Keeping *any* node of a removed subtree pins the *whole* subtree, since children link back to parents:

```javascript
let detachedCellReference;

function leakTable() {
  const table = document.createElement('table');
  for (let i = 0; i < 1000; i++) {
    const row = table.insertRow();
    const cell = row.insertCell();
    cell.textContent = `Cell data ${i}`;
  }
  document.body.appendChild(table);

  // Retain a reference to just ONE inner cell:
  detachedCellReference = table.rows[500].cells[0];

  // Remove table from DOM:
  table.remove();
}
```

One cell reference retains all 1,000 rows as a **detached DOM tree**. **Remedy**: null out element variables on removal.

**4. Closures retained by a longer-lived owner.** A closure retaining obsolete data stays live as long as its owner does. Shared context storage can add implementation-specific retention, but unused sibling source code alone does not prove a leak or a byte count:

```javascript
function holdSnapshots(target) {
  const snapshots = [];
  const onSnapshot = (event) => snapshots.push(event.detail);
  target.addEventListener('snapshot', onSnapshot);
  return () => {
    target.removeEventListener('snapshot', onSnapshot);
    snapshots.length = 0;
  };
}
```

While the target stays reachable, its registration retains the callback and the growing snapshot array. Calling the disposer removes that path and clears retained snapshots; another reference can still keep data alive. Use a bounded history if old snapshots are intentionally retained. The [closure chapter](../01-execution-and-scope/10.1.1.06-closures.md) owns the simpler callback identity/cleanup trace; this case adds unbounded history retention.

**5. Unbounded caches and persistent Maps.** A `Map` cache without eviction can grow with every distinct key:

```typescript
// LEAK: Unbounded Map grows indefinitely
const queryCache = new Map<string, unknown>();

export async function fetchWithCache(query: string) {
  if (queryCache.has(query)) return queryCache.get(query);
  const data = await executeQuery(query);
  queryCache.set(query, data); // Never evicts entries!
  return data;
}
```

**Remedy**: cap with an `LruCache(maxSize)`, or use `WeakMap` when keys are objects tied to caller lifetimes.

## 2. Profiling and Diagnosing Leaks in Chrome DevTools

1. **Baseline snapshot** — Memory panel → Heap snapshot → Snapshot 1.
2. **Repeat the suspect action** — open/close the modal 10 times.
3. **Force GC** — trash-can icon (Collect Garbage) to clear transients.
4. **Compare** — Snapshot 2 → switch view to **Comparison** (2 vs 1).
5. **Inspect delta** — filter **Detached** for yellow/red detached elements; expand the suspect to read its **Retainers** tree, which traces the live pointer path back to the `window` root.

## 3. Node.js Memory Diagnostics

`process.memoryUsage()` exposes the process profile:

| Metric | Meaning | Normal Production Profile |
| :---------------------------- | :------------------------------------------------------- | :--------------------------------------- |
| **`rss`** (Resident Set Size) | Total process RAM allocated in physical memory | Stable baseline under sustained load |
| **`heapTotal`** | Total memory allocated by V8 for heap structures | Scales with heap demands |
| **`heapUsed`** | Used V8 heap, including objects not yet collected | Periodic saw-tooth pattern (drops on GC) |
| **`external`** | Memory allocated by C++ bindings (e.g. `Buffer`, crypto) | Monitored when streaming heavy I/O |

A rising post-collection live-set trend is evidence to investigate, not conclusive proof of unwanted retention: wanted caches, workload growth and delayed collection can also increase it. Compare equivalent workload/lifecycle points and inspect retainers. RSS includes native/external memory and allocator behavior; a stable V8 heap does not rule out growth elsewhere.

## Summary

Leaks are reachable-but-obsolete memory: forgotten intervals, unremoved global listeners, detached DOM leaves pinning whole trees, long-lived closure owners, and unbounded caches. Diagnose with DevTools comparison snapshots (detached filter + retainers tree) and `heapUsed` trends in Node. Architecturally, pair every allocation — timer, listener, cache entry — with an explicit owner and teardown/retention policy; collection timing remains nondeterministic.

# Memory Leaks

An SPA navigates dashboard routes for an hour until the tab eats 2GB and crashes. The collector never freed the old views — global listeners, forgotten timers, and detached DOM trees kept unbroken retaining paths to the roots.

```javascript
// LEAK: interval outlives the component, pinning 10MB + the instance
function startMetricsCollector(componentInstance) {
  const heavyDataBuffer = new Uint8Array(10_000_000); // 10MB

  setInterval(() => {
    console.log('Heartbeat:', componentInstance.id);
  }, 1000);
}
```

## Definition

A **memory leak** in a garbage-collected language is heap memory the app no longer needs but the collector cannot reclaim — because unintended strong references keep it **reachable** from a GC root. Tracing collectors cannot read intent; reachable means retained.

> **Textbook Definition:** A memory leak in a managed runtime is the unintentional retention of heap-allocated memory caused by active reference chains originating from GC roots to obsolete data structures. Garbage collection algorithms reclaim exclusively unreachable memory; retaining paths created by closures, detached DOM subtrees, unmanaged intervals, and unbounded caches prevent reclamation.

## First Principles

The collector asks only whether an object is **reachable** from roots (global object, active stack frames, `document`) — never whether it is *useful*. What matters diagnostically is **retained size**: the memory freed if an object plus everything reachable exclusively through it were collected — always larger than its shallow size. Two structural facts follow: DOM children point back at parents, so one detached leaf pins its whole tree; and V8 merges same-scope closures into one shared `Context`, so one long-lived closure retains every variable its siblings captured.

```text
GC Roots (window / global / Active Call Stack)
      │
      ▼ (Strong Pointer)
[ Global Window Object ]
      │
      ├── .addEventListener('resize', handler)
      │                                  │
      │                                  ▼
      │                     [ Closure Context Scope ]
      │                                  │
      │                                  ▼
      │                     [ Detached Component View ] ──▶ Retains 50MB Heap
      │
      └── (Active View Transition Disposed)
```

## 1. The Five Classical Memory Leaks in JavaScript

**1. Forgotten timers and intervals.** `setInterval`/`setTimeout` pin their callback closures in the host timer queue until cleared. Unmounting the component changes nothing — the heartbeat above runs forever, retaining both the closure and the 10MB buffer. **Remedy**: store timer IDs and `clearInterval` in teardown.

**2. Unregistered global event listeners.** Listeners on `window`/`document` root the handler — and everything it closes over:

```javascript
export function attachPreviewModal() {
  const container = document.createElement('div');
  const onWindowResize = () => {
    container.style.width = `${window.innerWidth}px`;
  };

  window.addEventListener('resize', onWindowResize);
  document.body.appendChild(container);

  // TEARDOWN CONTRACT: Must remove listener when element is destroyed
  return function teardown() {
    window.removeEventListener('resize', onWindowResize);
    container.remove();
  };
}
```

`container.remove()` alone leaves `window → onWindowResize → container` intact — the "removed" element stays allocated.

**3. Detached DOM trees (the leaf-node trap).** Keeping *any* node of a removed subtree pins the *whole* subtree, since children link back to parents:

```javascript
let detachedCellReference;

function leakTable() {
  const table = document.createElement('table');
  for (let i = 0; i < 1000; i++) {
    const row = table.insertRow();
    const cell = row.insertCell();
    cell.textContent = `Cell data ${i}`;
  }
  document.body.appendChild(table);

  // Retain a reference to just ONE inner cell:
  detachedCellReference = table.rows[500].cells[0];

  // Remove table from DOM:
  table.remove();
}
```

One cell reference retains all 1,000 rows as a **detached DOM tree**. **Remedy**: null out element variables on removal.

**4. Shared lexical-scope closure leak (the V8 Context trap).** Sibling closures share one heap `Context` — a closure that reads nothing still retains what its siblings captured:

```javascript
let globalLeaker;

function outerScope() {
  const hugeBuffer = new Array(1_000_000).fill('*'); // ~8MB

  // Closure A: Captures hugeBuffer
  function unusedClosure() {
    if (hugeBuffer) return hugeBuffer;
  }

  // Closure B: Does NOT read hugeBuffer, but shares the same Lexical Context!
  return function exportedClosure() {
    console.log('I only print a string');
  };
}

// Every invocation links a new exportedClosure to a context holding hugeBuffer:
setInterval(() => {
  globalLeaker = outerScope(); // Keeps hugeBuffer alive in heap!
}, 100);
```

**5. Unbounded caches and persistent Maps.** A `Map` cache without eviction grows forever:

```typescript
// LEAK: Unbounded Map grows indefinitely
const queryCache = new Map<string, unknown>();

export async function fetchWithCache(query: string) {
  if (queryCache.has(query)) return queryCache.get(query);
  const data = await executeQuery(query);
  queryCache.set(query, data); // Never evicts entries!
  return data;
}
```

**Remedy**: cap with an `LruCache(maxSize)`, or use `WeakMap` when keys are objects tied to caller lifetimes.

## 2. Profiling and Diagnosing Leaks in Chrome DevTools

1. **Baseline snapshot** — Memory panel → Heap snapshot → Snapshot 1.
2. **Repeat the suspect action** — open/close the modal 10 times.
3. **Force GC** — trash-can icon (Collect Garbage) to clear transients.
4. **Compare** — Snapshot 2 → switch view to **Comparison** (2 vs 1).
5. **Inspect delta** — filter **Detached** for yellow/red detached elements; expand the suspect to read its **Retainers** tree, which traces the live pointer path back to the `window` root.

## 3. Node.js Memory Diagnostics

`process.memoryUsage()` exposes the process profile:

| Metric | Meaning | Normal Production Profile |
| :---------------------------- | :------------------------------------------------------- | :--------------------------------------- |
| **`rss`** (Resident Set Size) | Total process RAM allocated in physical memory | Stable baseline under sustained load |
| **`heapTotal`** | Total memory allocated by V8 for heap structures | Scales with heap demands |
| **`heapUsed`** | Actual memory occupied by live JavaScript objects | Periodic saw-tooth pattern (drops on GC) |
| **`external`** | Memory allocated by C++ bindings (e.g. `Buffer`, crypto) | Monitored when streaming heavy I/O |

A `heapUsed` curve that climbs monotonically and never resets after major GC cycles is conclusive evidence of a leak.

## Summary

Leaks are reachable-but-obsolete memory: forgotten intervals, unremoved global listeners, detached DOM leaves pinning whole trees, shared V8 closure contexts, and unbounded caches. Diagnose with DevTools comparison snapshots (detached filter + retainers tree) and `heapUsed` trends in Node. Architecturally, pair every allocation — timer, listener, cache entry — with an explicit teardown contract.

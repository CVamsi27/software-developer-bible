# Garbage Collection

Two objects can reference each other in a cycle long after the app drops every handle to them — yet modern engines reclaim the whole island without a second thought. Reachability, not reference counting, decides what lives.

```javascript
let a = { name: 'A' };
let b = { name: 'B' };
a.peer = b;
b.peer = a; // Reference cycle

a = null;
b = null; // Entire island is unreachable → eligible for collection despite the cycle (no promised deadline)
```

## Definition

**Garbage Collection (GC)** is the engine subsystem that finds and reclaims heap memory the program can no longer reach. Many modern runtimes use tracing and generational strategies, collecting young and old regions under workload-dependent policies; this chapter uses V8 as a concrete implementation, not a language requirement.

> **Textbook Definition:** Garbage collection is an automated memory reclamation process that identifies unreachable heap allocations using root-tracing graph traversal. Generational tracing collectors partition objects by lifetime and may combine copying, marking, sweeping and optional compaction with incremental, parallel or concurrent work. ECMAScript does not prescribe one heap layout or collection schedule.

## First Principles

An allocation is live **iff** a pointer chain from a GC root (global scope, active stack frames, DOM handles) reaches it — which is exactly why cycles don't fool the collector. The **weak generational hypothesis** observes that most objects die young (temp buffers, loop variables, promise reactions) while few live long — so partitioning the heap into a frequently-swept young generation and a rarely-swept old one avoids rescanning gigabytes per collection. One useful tracing model is **tri-color marking**: White (unvisited, reclamation candidates), Grey (seen, children unexplored), Black (fully explored, live).

```text
GC Roots (Stack Frames, Global Scope, DOM Document)
      │
      ▼
   [ Node A (Black) ] ──────▶ [ Node B (Grey) ] ──▶ [ Node C (White) ]
      │
      ▼
   [ Node D (Black) ]

   [ Cycle X (White) ] ◀────▶ [ Cycle Y (White) ] (Unreachable -> eligible for collection)
```

## 1. V8 Heap Architecture and Memory Spaces

| Region or role | Illustrative implementation concern |
| --------------------------------------- | ----------------------------------------------------------------------------------- |
| Young generation | Frequent collection of many short-lived allocations; size and collector policy vary |
| Old generation | Longer-lived objects, major tracing/sweeping and selected compaction |
| Large-object regions | Dedicated allocation/collection rules; thresholds and mobility vary |
| Executable/code regions | Generated code and runtime-specific protection/allocation rules |
| Read-only and other specialized regions | Build/version-dependent runtime data and metadata |

Historic V8 names such as separate old-pointer/data or map spaces are not a portable current layout. In Node, inspect `v8.getHeapSpaceStatistics()` for the running version; its space names/availability/order may change. Neither large-object space nor the total heap is unbounded: process, host and engine limits still apply.

## 2. Minor GC: Cheney's Copying Scavenger

In the Scavenger copying strategy, the young region uses two semi-spaces, **From** and **To**. When From fills, the collector pauses, traces live objects (via roots plus Old→Young pointers), copies them contiguously into To (which compacts for free), may promote survivors according to age, space and allocation policy, then swaps the spaces and discards the old From wholesale:

```text
Before Scavenge:
From-Space: [ Obj A (Live) ][ Dead X ][ Obj B (Survived 1x) ][ Dead Y ]
To-Space:   [ Empty                                                   ]

After Scavenge:
From-Space: [ Empty                                                   ]
To-Space:   [ Obj A (Live 1x) ] ── (Obj B promoted directly to Old Space)
```

**Remembered sets and write barriers** track relevant Old→Young edges, allowing a young collection to find them without scanning all old objects. A barrier checks relevant stores; fast paths can skip work that needs no bookkeeping. The exact slot/card/page representation belongs to the engine version, not the JavaScript contract.

V8 also has a Minor Mark-Sweep strategy under applicable configurations. It does not copy all survivors in the same way; promotion and collection choices must be tied to the actual runtime/flags.

## 3. Major GC: Mark-Sweep-Compact

When Old Space crosses its threshold: **marking** runs tri-color traversal (white = dead at end, grey = worklisted, black = live); **sweeping** returns non-black chunks to free lists; optional **compaction** relocates selected live objects and rewrites pointers to reduce fragmentation. A major collection can cover the whole heap rather than only old objects.

## 4. V8 Orinoco: Reducing Stop-The-World Work

Project **Orinoco** split collection across threads and time to reduce pauses. Live-set size, allocation rate, flags and hardware still affect latency; these traces illustrate scheduling rather than measured or guaranteed milliseconds:

```text
Historic STW Garbage Collection:
Main Thread: [ JavaScript Code ] ──▶ [ STOP-THE-WORLD COLLECTION ] ──▶ [ Code ]

Modern Orinoco Pipeline:
Main Thread:        [ Code ] ─(slice)─▶ [ Code ] ─(slice)─▶ [ Remaining STW Work ]
Worker Threads:     ──[ Concurrent Marking ]──────────▶ [ Concurrent Sweeping ]
```

- **Parallel work**: unavoidable stop-the-world pauses fan marking/evacuation out to helper threads.
- **Incremental marking**: the main thread interleaves marking slices between JS tasks instead of one giant pause.
- **Concurrent marking and sweeping**: helpers trace and sweep *while* JS runs; write barriers keep the tri-color invariant consistent under mutation.

## 5. WeakRef and FinalizationRegistry

Standard hooks for observing (never controlling) collection:

```javascript
// WeakRef holds an object without preventing its collection
let target = { payload: 'Sensitive Cache Data' };
const weakTarget = new WeakRef(target);

// Dereferencing retrieves the value if still alive:
console.log(weakTarget.deref()?.payload); // "Sensitive Cache Data"

// Register optional notification; it may never be delivered:
const registry = new FinalizationRegistry((heldValue) => {
  console.log('Target object was reclaimed by GC:', heldValue);
});
registry.register(target, 'target-identifier');

// Drop the only strong reference:
target = null;
// No particular GC kind or deadline guarantees a callback.
// The held value must not strongly refer to target, directly or indirectly.
```

> **[Caution]** Finalization timing is fully non-deterministic — the collector may defer indefinitely or exit without ever firing. **Never use `FinalizationRegistry` for critical cleanup** (closing connections, committing transactions); use explicit `try...finally` or supported `using` disposables instead; verify syntax/runtime support.

## Summary

Generational tracing collectors split the heap by longevity: a copying Minor GC can evacuate young survivors (write barriers tracking Old→Young edges), Major GC reclaims old space with tri-color mark-sweep-compact. Orinoco parallelizes and interleaves work to reduce pauses, without a universal latency guarantee. `WeakRef`/`FinalizationRegistry` observe collection non-deterministically — never depend on them for correctness.

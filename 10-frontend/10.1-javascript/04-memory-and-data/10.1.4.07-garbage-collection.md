# Garbage Collection

## Definition

**Garbage collection (GC)** automatically reclaims memory that a JavaScript program can no longer reach. Engines use collection algorithms to determine which objects remain accessible and which memory can be freed. You do not explicitly free ordinary JavaScript objects, but you still need to remove references to data your application no longer needs.

> **Textbook Definition:** Garbage collection automatically reclaims storage that the runtime determines is no longer reachable from its roots. Reachability is a memory-management criterion and does not establish whether an application still needs the data.


## First Principles

GC is deduced from the impossible alternative:

1. **Objects can outlive the function that created them.** Manual memory management must handle lifetimes across functions and modules. Missing a release can leak memory; releasing twice or too early can make access invalid. JavaScript delegates ordinary object reclamation to the runtime, which needs a rule it can check.
2. **Tracing collectors check reachability.** Start from **roots**, such as active execution state, global references and host handles. Follow references and mark the reachable objects. Unreachable objects can be reclaimed. This graph traversal is something the engine can compute; it does not need to infer the programmer's future intent. Generations and incremental marking make that work cheaper or less disruptive.
3. **Reachable but unused objects remain retained** (→ 10.1.4.06). This favors safety: retaining unwanted data is preferable to freeing an object the program can still use.
4. **Collection work affects application time.** Some work pauses the application, while other work can be split into steps, run alongside it or use several threads (→ 10.1.3.01). **Generational collection** uses the observation that many objects become unreachable soon after allocation, so it checks new objects frequently.


## Why It Matters

Senior engineers reason about allocation rate (allocations per second triggers minor GC), short-lived vs long-lived objects (young vs old gen), and use `WeakRef`/`FinalizationRegistry` for caches that shouldn't pin objects. A healthy long-running service should not require periodic restarts merely because it uses GC. Track retained heap, allocation rate and pause behavior to distinguish leaks, intentional caches and load.

## How It Works

### Trace outward from roots

This simplified collector model starts with references the runtime must preserve, such as active execution state, globals and host registrations. It follows each reference, marks every reachable object, then reclaims unmarked storage. Actual engines can move objects, divide work or use different collectors for different regions.

```text
root -> A -> B                 A and B are reachable
        C <-> D               C and D form a cycle with no root path
```

The arrow means “can access through a reference”. Marking reaches A and then B, but never enters the C/D cycle, so both C and D are eligible for reclamation. Removing the root-to-A reference makes A/B eligible too, unless another root has a path to them. Eligibility does not guarantee collection at the next statement.

### Reference Counting

For comparison, a reference counter tracks how many references target each object and releases it when the count reaches zero. C/D retain nonzero counts through their mutual references even after roots disappear. A tracing collector asks whether *roots* can reach the cycle, so it can reclaim that cycle. These counts illustrate an alternative model, not observable counters in JavaScript.

### Generational GC

A **generation** groups objects by age. Checking the young region frequently is useful because many temporary objects become unreachable quickly. Survivors may move to an old region; promotion thresholds and placement are engine policies. A young-only collection must still notice references *from old objects into young ones*. Engines track those writes, often through a **write barrier**, bookkeeping triggered when references are stored, rather than rescanning the entire old heap every time.

**Incremental** marking divides work into smaller pauses. **Concurrent** work runs alongside application execution, while **parallel** work uses multiple collector threads for a phase. These describe scheduling choices and can coexist. The V8 terms below illustrate implementations described in the cited V8 material; ECMAScript does not mandate generation sizes, thresholds or one particular young-generation collector.

```text
┌─────────────────────────────────────────────────────────┐
│ GENERATIONAL GC                                         │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ GENERATIONS:                                            │
│ ┌─────────────────────────────────────────────────────┐ │
│ │                                                     │ │
│ │ Young Generation (Nursery)                          │ │

│ │ • Small size                                        │ │
│ │ • Collected frequently                              │ │
│ │                                                     │ │
│ │ Old Generation (Tenured)                            │ │
│ │ • Objects surviving multiple collections            │ │
│ │ • Larger size                                       │ │
│ │ • Collected less frequently                         │ │
│ │                                                     │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ PROMOTION:                                              │
│ ┌─────────────────────────────────────────────────────┐ │
│ │                                                     │ │
```

## Code Examples

### Basic Garbage Collection

```typescript
// Objects are created and garbage collected
function example() {
  let obj: { data: string } | null = { data: 'hello' }; // Created
  console.log(obj.data);
  obj = null; // No longer reachable from this scope
}

example();
// The object is now eligible for reclamation; a future applicable collection may reclaim it.
// There is no deterministic moment: a GC may not run for a long time.

// Circular references are handled
function createCircular() {
  let a: any = { name: 'a' };
  let b: any = { name: 'b' };
  a.ref = b;
  b.ref = a;

  a = null;
  b = null;
  // The pair still references each other, but nothing reaches either one
  // from the roots — mark-and-sweep reclaims them together.
}

```

### Closures and GC

```typescript
// Closure prevents GC of captured variables
function createClosure() {
  const largeData = new Array(1000000).fill(0);

  return function() {
    // largeData kept alive by closure
    return largeData.length;
  };
}

const closure = createClosure();
// largeData cannot be garbage collected

// To allow GC, release reference
function createClosureFixed() {
  let largeData: number[] | null = new Array(1000000).fill(0);

  return function() {
    const length = largeData?.length ?? 0;
    largeData = null; // Allow GC
    return length;
  };
}

```

### WeakMap and GC

```typescript
// WeakMap allows GC of keys
const cache = new WeakMap<object, any>();

function processObject(obj: object) {
  if (cache.has(obj)) {
    return cache.get(obj);
  }

  const result = expensiveComputation(obj);
  cache.set(obj, result);
  return result;
}

let obj: { data: string } | null = { data: 'test' };
processObject(obj);

// When obj is garbage collected, cache entry is also removed
obj = null;

```

### Object Pooling

A pool is an application-owned list of idle objects, not a collector feature. Reusing a released particle can reduce hot-path allocations, but each idle particle remains strongly reachable. Bound idle capacity and reset payload references. This minimal example assumes one borrower per object and exactly one release after use; duplicate releases would let two borrowers acquire the same mutable object.

```typescript
// Reuse objects to reduce GC pressure
class ObjectPool<T> {
  private pool: T[] = [];
  private factory: () => T;

  constructor(factory: () => T, private maxIdle = 1000) {
    if (!Number.isInteger(maxIdle) || maxIdle < 0) throw new RangeError('Invalid capacity');
    this.factory = factory;
  }

  acquire(): T {
    return this.pool.length > 0
      ? this.pool.pop()!
      : this.factory();
  }

  release(obj: T) {
    if (this.pool.length < this.maxIdle) this.pool.push(obj);
  }
}

// Usage
const pool = new ObjectPool(() => ({ x: 0, y: 0 }));
const obj = pool.acquire();
// Use obj
pool.release(obj); // Return to pool instead of GC

```

### Typed Arrays

```typescript
// A typed array is a numeric view over a buffer, without sparse holes.
// This example uses a fixed-size ArrayBuffer. Resizable buffers can instead
// support length-tracking views; shrinking can make fixed views out of bounds.
const buffer = new ArrayBuffer(1024 * 4);
const view = new Float32Array(buffer);
view[0] = 3.14;
console.log(view.length); // 1024

// The backing bytes have a compact representation; do not assume normal
// numeric arrays box every element or that collectors move buffer bytes.
// Transfer can move ownership of supported buffers and detach the sender.
// A tiny retained subarray still retains its entire backing buffer.
```

## Real-World Use Cases

### 1. React Component Optimization

Assume React imports, `Item` and `List` from the application. `useMemo` avoids recomputation on renders where `items` identity is unchanged. It does not make a mutated array safe or guarantee indefinite retention of the memoized result. Keep render ownership/immutability correct and measure whether this transformation costs enough to cache.

```typescript
// Bad: Creating new objects on each render
function Component({ items }: { items: Item[] }) {
  const processed = items.map(item => ({
    ...item,
    processed: true
  }));

  return <List items={processed} />;
}

// Good: Memoize expensive computations
function Component({ items }: { items: Item[] }) {
  const processed = useMemo(
    () => items.map(item => ({ ...item, processed: true })),
    [items]
  );

  return <List items={processed} />;
}

```

### 2. Metadata lifetime versus subscription lifetime

A `WeakMap<object, Callback[]>` can associate metadata with an object without keeping the key alive by itself. It does not unregister callbacks stored by an actual DOM target, socket or event bus. That host's registration is a separate strong retaining path and needs an explicit unsubscribe operation; see [Memory leaks](10.1.4.06-memory-leaks.md#detached-dom) for the complete lifecycle trace.

### 3. Cache Implementation

The weak key controls retention; the timestamp controls whether a still-reachable key's cached value is valid. Expiry is checked on reads, so a reachable but unread key can retain an expired value. Weak storage offers neither enumeration nor predictable eviction timing. Use a bounded strong cache when those controls are required.

```typescript
class GCFriendlyCache<K extends object, V> {
  private cache = new WeakMap<K, { value: V; timestamp: number }>();
  private ttl: number;

  constructor(ttl: number = 60000) {
    this.ttl = ttl;
  }

  set(key: K, value: V) {
    this.cache.set(key, { value, timestamp: Date.now() });
  }

  get(key: K): V | undefined {
    const entry = this.cache.get(key);
    if (!entry) return undefined;

    if (Date.now() - entry.timestamp > this.ttl) {
      this.cache.delete(key);
      return undefined;
    }

    return entry.value;
  }
}

```

### 4. Memory Monitoring

`performance.memory` is a deprecated, nonstandard estimate of JavaScript heap usage. It omits parts of browser/process memory and is not a portable alarm. A high percentage suggests investigation rather than establishing a leak; compare repeated workloads and retaining paths, as taught in the leak chapter.

```typescript
function monitorMemory() {
  const memory = (performance as any).memory; // Nonstandard Chromium diagnostic
  if (memory) {
    const used = memory.usedJSHeapSize;
    const total = memory.jsHeapSizeLimit;
    const percentage = (used / total) * 100;

    console.log(`Memory: ${percentage.toFixed(2)}%`);

    if (percentage > 80) {
      console.warn('High memory usage!');
    }
  }
}

const monitoring = setInterval(monitorMemory, 5000);
// Dispose when done: clearInterval(monitoring);

```

## Common Mistakes

### 1. Holding Unnecessary References

```typescript
// NOT a leak: inside a short function there is nothing to release — `data`
// becomes unreachable the moment process() returns, and the collector
// reclaims it on the next pass. Forcing `data = null` here buys nothing.
function process() {
  const data = fetchData();
  consume(data);
}

// The real version of the mistake: a binding in a LONG-LIVED scope — module
// top level, a cache closure, an object property — that outlives its use and
// therefore outlives its usefulness. Dropping the binding is the fix.
const store = { data: fetchData() };
consume(store.data);

// done with the payload; the big object is now unreachable
store.data = null;

```

### 2. Global Caches Without Limits

```typescript
// Bad: Unbounded cache
const cache = new Map();
function getCached(key: string) {
  if (!cache.has(key)) {
    cache.set(key, expensiveOperation(key));
  }
  return cache.get(key);
}

// Good: Bounded cache
const cache = new Map();
const MAX_SIZE = 1000;
function getCached(key: string) {
  if (!cache.has(key) && cache.size >= MAX_SIZE) {
    const firstKey = cache.keys().next().value;
    cache.delete(firstKey!);
  }
  if (!cache.has(key)) {
    cache.set(key, expensiveOperation(key));
  }
  return cache.get(key);
}

```

### 3. Not Using WeakMap for Object References

```typescript
// Strong ownership: use this when the cache should keep entries until eviction.
const objectCache = new Map();
function process(obj: object) {
  objectCache.set(obj, result);
}

// Weak metadata: only suitable if disappearance with the key is acceptable.
const objectCache = new WeakMap();
function process(obj: object) {
  objectCache.set(obj, result);
}

```

### 4. Forgetting to Clear Timers

```typescript
// Bad: Timer keeps running
function start() {
  setInterval(() => {
    updateUI();
  }, 1000);
}

// Good: Clear timer
function start() {
  const id = setInterval(() => {
    updateUI();
  }, 1000);

  return () => clearInterval(id);
}

```

## Best Practices

### 1. Minimize Object Creation

Reducing allocation is an optimization, not permission to mutate shared data. The in-place version changes the caller's objects and can invalidate React state snapshots or cached calculations. Preserve the ownership contract first; then profile allocation and pause behavior to decide whether optimization is useful.

```typescript
// Bad: Creates new objects
function process(items: Item[]) {
  return items.map(item => ({
    ...item,
    processed: true
  }));
}

// In-place variant: requires exclusive mutation ownership; still allocates an array.
function process(items: Item[]) {
  return items.map(item => {
    item.processed = true;
    return item;
  });
}

```

### 2. Use Object Pooling

```typescript
// For frequently created/destroyed objects
const pool = new ObjectPool(() => ({
  x: 0, y: 0, vx: 0, vy: 0
}));

function createParticle() {
  return pool.acquire();
}

function destroyParticle(particle: Particle) {
  pool.release(particle);
}

```

### 3. Implement Bounded Caches

```typescript
class BoundedCache<K, V> {
  private cache = new Map<K, V>();
  private maxSize: number;

  constructor(maxSize: number) {
    if (!Number.isInteger(maxSize) || maxSize < 1) throw new RangeError('Invalid capacity');
    this.maxSize = maxSize;
  }

  set(key: K, value: V) {
    if (!this.cache.has(key) && this.cache.size >= this.maxSize) {
      const firstKey = this.cache.keys().next().value;
      this.cache.delete(firstKey!);
    }
    this.cache.set(key, value);
  }
}

```

### 4. WeakRef permits disappearance; it does not schedule eviction

A weak reference offers optional access without keeping its target alive. Read `deref()` once and handle `undefined`, for example by reloading the data. The returned strong reference protects use while held. Neither a weak reference nor a finalizer can be the only owner of data/resources the application must reliably retain or close.

```typescript
// Allow GC while maintaining access
class DataStore {
  private data: WeakRef<LargeObject>;

  constructor(initial: LargeObject) {
    this.data = new WeakRef(initial);
  }

  getData(): LargeObject | undefined {
    return this.data.deref();
  }

  setData(data: LargeObject) {
    this.data = new WeakRef(data);
  }
}

```

## Performance Considerations

### GC Pauses

```typescript
// GC can cause pauses
// Mitigate by:
// 1. Reducing allocations in hot paths
// 2. Using object pooling
// 3. Processing data in chunks

// Bad: Large allocation
function process() {
  const hugeArray = new Array(10000000);
  // ... process
}

// Smaller peak temporary data, provided completed chunks are not retained.
// This synchronous loop still does not yield to the event loop.
function process() {
  for (let i = 0; i < 10000000; i += 1000) {
    const chunk = new Array(1000);
    // ... process chunk
  }
}

```

### Memory Pressure

```typescript
// Monitor and respond to memory pressure
if ('memory' in performance) {
  const memory = (performance as any).memory;

  if (memory.usedJSHeapSize > memory.jsHeapSizeLimit * 0.8) {
    // Reduce cache size, clear unnecessary data
    cache.clear();
  }
}

```

Use `WeakRef` only when disappearance is acceptable and recomputation is safe. `FinalizationRegistry` callbacks are nondeterministic and may never run before process exit; close sockets, unsubscribe listeners and release resources explicitly. Pooling retains objects and can increase old-generation pressure, so compare it against normal allocation on the measured workload.

## Summary

Garbage collection is essential for JavaScript:

1. **Algorithm**: Mark-and-sweep (handles circular refs)

2. **Generational**: Young/old generation optimization

3. **Performance**: GC pauses can impact performance

4. **Best practices**: Preserve ownership; measure before pooling or reducing allocation

5. **WeakMap/WeakRef**: Allow GC of referenced objects

6. **Monitoring**: Track memory usage

7. **Common issues**: Closures, global caches, timers

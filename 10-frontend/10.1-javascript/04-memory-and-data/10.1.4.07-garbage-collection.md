# Garbage Collection

Two objects can reference each other in a cycle long after the app drops every handle to them — yet modern engines reclaim the whole island without a second thought. Reachability, not reference counting, decides what lives.

```javascript
let a = { name: 'A' };
let b = { name: 'B' };
a.peer = b;
b.peer = a; // Reference cycle

a = null;
b = null; // Entire island is unreachable → reclaimed despite the cycle
```

## Definition

**Garbage Collection (GC)** is the engine subsystem that finds and reclaims heap memory the program can no longer reach. Modern runtimes trace from roots through **generational** heaps — collecting short-lived objects often and cheaply, long-lived ones rarely and thoroughly.

> **Textbook Definition:** Garbage collection is an automated memory reclamation process that identifies unreachable heap allocations using root-tracing graph traversal. Modern engines implement generational collectors that segregate objects into young and old spaces, combining Cheney copying scavengers, incremental and concurrent tri-color marking, and pointer-compacting sweeps to minimize main-thread execution pauses.

## First Principles

An allocation is live **iff** a pointer chain from a GC root (global scope, active stack frames, DOM handles) reaches it — which is exactly why cycles don't fool the collector. The **weak generational hypothesis** observes that most objects die young (temp buffers, loop variables, promise reactions) while few live long — so partitioning the heap into a frequently-swept young generation and a rarely-swept old one avoids rescanning gigabytes per collection. The tracer itself runs **tri-color marking**: White (unvisited, reclamation candidates), Grey (seen, children unexplored), Black (fully explored, live).

```text
GC Roots (Stack Frames, Global Scope, DOM Document)
      │
      ▼
   [ Node A (Black) ] ──────▶ [ Node B (Grey) ] ──▶ [ Node C (White) ]
      │
      ▼
   [ Node D (Black) ]

   [ Cycle X (White) ] ◀────▶ [ Cycle Y (White) ] (Unreachable -> RECLAIMED!)
```

## How It Works

### 1. V8 Heap Architecture and Memory Spaces

| Memory Space | Allocation Size | Collection Subsystem | Description & Optimization |
| :------------------------ | :-------------- | :-------------------- | :----------------------------------------------------------------- |
| **New Space (Young Gen)** | 1MB – 64MB | Minor GC (Scavenger) | Fast bump-pointer allocation; divided into From and To semi-spaces |
| **Old Pointer Space** | Dynamic (GBs) | Major GC (Mark-Sweep) | Contains surviving objects that hold pointers to other objects |
| **Old Data Space** | Dynamic (GBs) | Major GC (Mark-Sweep) | Contains raw byte data (strings, boxed numbers, raw buffers) |
| **Large Object Space** | Unbounded | Custom sweep | Objects exceeding page size (~512KB); never moved or compacted |
| **Code Space** | V8-managed | JIT compiler | JIT-compiled machine code instructions generated by TurboFan |
| **Map Space** | V8-managed | Map GC | Hidden Classes (Maps) and shape transition trees |

### 2. Minor GC: Cheney's Copying Scavenger

The young generation splits into two semi-spaces, **From** and **To**. When From fills, the collector pauses, traces live objects (via roots plus Old→Young pointers), copies them contiguously into To (which compacts for free), promotes twice-survivors straight to Old Space, then swaps the spaces and discards the old From wholesale:

```text
Before Scavenge:
From-Space: [ Obj A (Live) ][ Dead X ][ Obj B (Survived 1x) ][ Dead Y ]
To-Space:   [ Empty                                                   ]

After Scavenge:
From-Space: [ Empty                                                   ]
To-Space:   [ Obj A (Live 1x) ] ── (Obj B promoted directly to Old Space)
```

**Remembered set and write barriers**: finding Old→Young pointers without scanning gigabytes of Old Space relies on a **write barrier** — every reference store (`oldObject.field = newObject`) is intercepted, and Old→Young edges are logged in a card-table **remembered set** that Minor GC scans instead.

### 3. Major GC: Mark-Sweep-Compact

When Old Space crosses its threshold: **marking** runs tri-color traversal (white = dead at end, grey = worklisted, black = live); **sweeping** returns non-black chunks to free lists; **compacting** relocates live objects into contiguous pages and rewrites pointers, eliminating fragmentation.

### 4. V8 Orinoco: Eliminating Stop-The-World Latency

Historic major cycles froze JS for 100–500ms. Project **Orinoco** split collection across threads and time:

```text
Historic STW Garbage Collection:
Main Thread: [ JavaScript Code ] ──▶ [ STOP-THE-WORLD PAUSE (200ms) ] ──▶ [ Code ]

Modern Orinoco Pipeline:
Main Thread:        [ Code ] ─(1ms)─▶ [ Code ] ─(1ms)─▶ [ Short STW Compacting ]
Worker Threads:     ──[ Concurrent Marking ]──────────▶ [ Concurrent Sweeping ]
```

- **Parallel work**: unavoidable stop-the-world pauses fan marking/evacuation out to helper threads.
- **Incremental marking**: the main thread interleaves ~1ms marking slices between JS tasks instead of one giant pause.
- **Concurrent marking and sweeping**: helpers trace and sweep *while* JS runs; write barriers keep the tri-color invariant consistent under mutation.

### 5. WeakRef and FinalizationRegistry

Standard hooks for observing (never controlling) collection:

```javascript
// WeakRef holds an object without preventing its collection
let target = { payload: 'Sensitive Cache Data' };
const weakTarget = new WeakRef(target);

// Dereferencing retrieves the value if still alive:
console.log(weakTarget.deref()?.payload); // "Sensitive Cache Data"

// Register cleanup callback invoked after garbage collection:
const registry = new FinalizationRegistry((heldValue) => {
  console.log('Target object was reclaimed by GC:', heldValue);
});
registry.register(target, 'target-identifier');

// Drop the only strong reference:
target = null;
// Once the engine performs a Major GC, the registry callback will fire.
```

> **[Caution]** Finalization timing is fully non-deterministic — the collector may defer indefinitely or exit without ever firing. **Never use `FinalizationRegistry` for critical cleanup** (closing connections, committing transactions); use explicit `try...finally` or `using` disposables instead.

## Summary

Generational tracing collectors split the heap by longevity: Minor GC evacuates the young generation with Cheney copying (write barriers tracking Old→Young edges), Major GC reclaims old space with tri-color mark-sweep-compact. Orinoco parallelizes and interleaves that work to erase long pauses. `WeakRef`/`FinalizationRegistry` observe collection non-deterministically — never depend on them for correctness.

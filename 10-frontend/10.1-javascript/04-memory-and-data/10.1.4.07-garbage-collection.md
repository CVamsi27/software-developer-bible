# Garbage Collection

Two JavaScript objects can hold circular references to each other after the rest of the application has discarded all references to them. In modern engines, this entire circular cycle is reclaimed smoothly because garbage collectors evaluate reachability from roots rather than counting references. Understanding engine garbage collection architectures is essential for building high-throughput systems that avoid main-thread stop-the-world jank.

## Definition

**Garbage Collection (GC)** is the automated memory management subsystem within a JavaScript engine responsible for detecting and reclaiming heap-allocated memory that can no longer be reached by the running program. Modern runtimes employ tracing generational garbage collectors that partition memory into distinct lifecycle spaces and optimize collection frequency based on object longevity.

> **Textbook Definition:** Garbage collection is an automated memory reclamation process that identifies unreachable heap allocations using root-tracing graph traversal. Modern engines implement generational collectors that segregate objects into young and old spaces, combining Cheney copying scavengers, incremental and concurrent tri-color marking, and pointer-compacting sweeps to minimize main-thread execution pauses.

## First Principles

1. **Root-Referenced Reachability:** An allocation is live if and only if it can be reached through a directed chain of pointers originating from a Garbage Collection Root (global scope, current call stack frames, or host-managed DOM handles).

2. **The Weak Generational Hypothesis:** The overwhelming majority of allocated objects die shortly after instantiation (temporary calculation buffers, loop variables, promise reactions). Long-lived objects represent a small, stable minority.

3. **Partitioned Heap Generations:** To avoid scanning the entire multi-gigabyte heap on every collection, the heap is partitioned into a Young Generation (collected frequently with lightweight copying algorithms) and an Old Generation (collected infrequently with comprehensive mark-sweep-compact).

4. **Tri-Color Marking State Invariant:** Tracing collectors categorize objects into White (unvisited / candidate for reclamation), Grey (visited, but children unexplored), and Black (visited along with all reachable children).

```text
GC Roots (Stack Frames, Global Scope, DOM Document)
      │
      ▼
   [ Node A (Black) ] ──────▶ [ Node B (Grey) ] ──▶ [ Node C (White) ]
      │
      ▼
   [ Node D (Black) ]

   [ Cycle X (White) ] ◀────▶ [ Cycle Y (White) ] (Unreachable -> RECLAIMED!)
```

## V8 Heap Architecture and Memory Spaces

Google V8 divides its managed heap into specialized memory spaces:

| Memory Space | Allocation Size | Collection Subsystem | Description & Optimization |
| :------------------------ | :-------------- | :-------------------- | :----------------------------------------------------------------- |
| **New Space (Young Gen)** | 1MB – 64MB | Minor GC (Scavenger) | Fast bump-pointer allocation; divided into From and To semi-spaces |
| **Old Pointer Space** | Dynamic (GBs) | Major GC (Mark-Sweep) | Contains surviving objects that hold pointers to other objects |
| **Old Data Space** | Dynamic (GBs) | Major GC (Mark-Sweep) | Contains raw byte data (strings, boxed numbers, raw buffers) |
| **Large Object Space** | Unbounded | Custom sweep | Objects exceeding page size (~512KB); never moved or compacted |
| **Code Space** | V8-managed | JIT compiler | JIT-compiled machine code instructions generated by TurboFan |
| **Map Space** | V8-managed | Map GC | Hidden Classes (Maps) and shape transition trees |

## Minor GC: Cheney's Copying Scavenger

The Young Generation is divided into two equally sized semi-spaces: **From-Space** and **To-Space**. When From-Space fills:

1. **Pause and Trace:** A Minor GC pause is triggered. The engine traces live objects in From-Space reachable from roots and Old Space pointers.

2. **Copy to To-Space:** Live objects are copied contiguously into To-Space (Cheney's algorithm). Copying naturally compacts memory, eliminating fragmentation.

3. **Tenuring (Promotion):** If an object has already survived a previous Scavenge cycle, it is **promoted** directly to Old Space rather than To-Space.

4. **Space Swap:** The roles of From-Space and To-Space are swapped. All residual allocations left in the previous From-Space are discarded en masse.

```text
Before Scavenge:
From-Space: [ Obj A (Live) ][ Dead X ][ Obj B (Survived 1x) ][ Dead Y ]
To-Space:   [ Empty                                                   ]

After Scavenge:
From-Space: [ Empty                                                   ]
To-Space:   [ Obj A (Live 1x) ] ── (Obj B promoted directly to Old Space)
```

### The Remembered Set and Write Barriers

When Scavenging the Young Generation, how does V8 identify whether an Old Generation object points to a Young Generation object without scanning the entire multi-gigabyte Old Space?

V8 implements a **Write Barrier**: whenever JavaScript code writes an object reference (`oldObject.field = newObject`), the engine intercepts the assignment. If the source is in Old Space and the target is in Young Space, the pointer address is logged in a specialized tracking structure called the **Remembered Set** (card table). Minor GC scans only the Remembered Set rather than all of Old Space.

## Major GC: Mark-Sweep-Compact

When Old Space reaches dynamic memory thresholds, V8 initiates a Major Garbage Collection cycle:

1. **Marking (Tri-Color Traversal):** The collector identifies live objects using tri-color marking:
   - **White:** Initial state; unvisited. At the end of marking, white objects are dead.
   - **Grey:** Discovered by the collector; enqueued on the marking worklist.
   - **Black:** Fully explored; guaranteed to be live.

2. **Sweeping:** The engine traverses non-black memory chunks, adding unreferenced byte ranges to memory **Free Lists** for future allocations.

3. **Compacting (Evacuation):** Sweeping leaves memory fragmented with scattered holes. Compacting relocates live black objects into contiguous free pages, rewriting all internal pointers to update addresses.

## V8 Orinoco: Eliminating Stop-The-World Latency

Historically, a Major GC cycle stopped JavaScript execution for 100ms–500ms, completely freezing animations and input handling. Project **Orinoco** restructured V8's GC into a modern concurrent and incremental pipeline:

```text
Historic STW Garbage Collection:
Main Thread: [ JavaScript Code ] ──▶ [ STOP-THE-WORLD PAUSE (200ms) ] ──▶ [ Code ]

Modern Orinoco Pipeline:
Main Thread:        [ Code ] ─(1ms)─▶ [ Code ] ─(1ms)─▶ [ Short STW Compacting ]
Worker Threads:     ──[ Concurrent Marking ]──────────▶ [ Concurrent Sweeping ]
```

- **Parallel Work:** During unavoidable Stop-The-World pauses, the main thread distributes marking and evacuation work across multiple background helper threads.
- **Incremental Marking:** Instead of marking the entire heap in one giant pause, the main thread interleaves small 1ms marking slices between JavaScript tasks.
- **Concurrent Marking & Sweeping:** Helper threads execute tri-color marking and sweeping in the background *while the main thread is simultaneously running JavaScript*. Write barriers intercept runtime mutations to maintain marking consistency.

## WeakRef and FinalizationRegistry

ECMAScript standardizes `WeakRef` and `FinalizationRegistry` for observing garbage collection lifecycles:

```javascript
// WeakRef holds an object without preventing its collection
let target = { payload: 'Sensitive Cache Data' };
const weakTarget = new WeakRef(target);

// Dereferencing retrieves the value if still alive:
console.log(weakTarget.deref()?.payload); // "Sensitive Cache Data"

// Register cleanup callback invoked after garbage collection:
const registry = new FinalizationRegistry((heldValue) => {
  console.log('Target object was reclaimed by GC:', heldValue);
});
registry.register(target, 'target-identifier');

// Drop the only strong reference:
target = null;
// Once the engine performs a Major GC, the registry callback will fire.
```

> **[Caution]** The ECMAScript specification explicitly warns that `FinalizationRegistry` callbacks and `WeakRef` dereferencing timing are completely non-deterministic. A garbage collector may defer collection indefinitely or terminate without invoking cleanup. **Never rely on FinalizationRegistry for critical resource cleanup** (such as closing database connections or committing transactions). Use explicit `try...finally` or `using` disposable statements instead.

## Summary

JavaScript memory is managed by generational tracing garbage collectors. Minor GC rapidly evacuates young allocations using Cheney's copying algorithm, aided by write barriers and remembered sets. Major GC reclaims long-lived heap memory using tri-color mark-sweep-compact. Modern engines eliminate user-facing pauses through V8 Orinoco's concurrent and incremental worker pipelines, while `WeakRef` and `FinalizationRegistry` provide non-deterministic hooks for cache management.

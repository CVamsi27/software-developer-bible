# Garbage Collection

## Definition

**Garbage collection (GC)** is the runtime process that reclaims storage the program can no longer reach. JavaScript developers do not free ordinary objects manually, but must still release references and external resources when their owners are done.

> **Textbook Definition:** Garbage collection automatically reclaims storage for values that the runtime determines are no longer reachable from its roots. Reachability is a memory-management criterion; it does not tell the runtime whether reachable data is still useful to the application.

## First Principles

The runtime needs a rule it can compute without guessing what the program will do next. If an object can still be reached, keeping it is safe; reclaiming it might break a later read. If there is no path to it from any live root, the program cannot observe it through ordinary references and its storage can be reused.

## Trace from roots

Roots include active execution state, global references, and host-managed handles. A tracing collector follows references from those roots and marks reachable objects; unmarked objects may be reclaimed. The runtime is free to choose when collection happens and which collector algorithm to use.

```text
root → A → B        A and B are reachable
       C ↔ D        C and D form a cycle with no path from a root
```

The C/D cycle is eligible for reclamation even though its members reference one another. A reference-counting-only scheme could miss it because each count stays nonzero; tracing asks whether any root reaches the cycle. This explains the observable principle without claiming that every JavaScript engine uses one mark-and-sweep design.

## Make collection work manageable

Many objects become unreachable soon after allocation, so engines often collect newer objects more frequently than older ones. A **scavenge** commonly means a young-generation collection; in copying collectors, survivors move between young spaces or are promoted into older storage. Promotion thresholds and memory regions are engine policies, and not every young collection copies every survivor. A young-only collection still needs to find references from older objects into young ones; engines track relevant writes with mechanisms such as write barriers and remembered sets.

Collectors also divide work to control pauses. **Incremental** collection breaks work into smaller steps. **Concurrent** work runs alongside application execution. **Parallel** work uses multiple collector threads for a phase. These techniques can be combined; none eliminates coordination or guarantees a pause-free application. V8's Orinoco project is one implementation example, not an ECMAScript requirement.

Allocation rate and retained size measure different pressures. A high allocation rate can create more collection work even when the live set is stable. A growing live set can pressure memory even when allocations are modest. Profile the target runtime and workload before pooling objects or changing mutation behavior. Pools deliberately keep released objects strongly reachable and can preserve peak capacity long after a workload subsides (→ [Memory Leaks](10.1.4.06-memory-leaks.md)).

## Weak references do not own required cleanup

`WeakMap` and `WeakSet` allow membership that does not keep an eligible key or member alive solely through the collection. A reachable WeakMap can still keep its value reachable while the key is live. See [Map and WeakMap](10.1.4.02-map-set-weakmap-weakset.md) for that ownership boundary.

`WeakRef.deref()` may return `undefined`. If it returns the target, the target is kept alive through the current JavaScript job. A `FinalizationRegistry` callback may run after collection, but is not guaranteed to run promptly—or at all. A held value that strongly references the target can prevent the target from becoming collectible. Use weak references only when the application can tolerate a cache miss; close sockets, files, subscriptions, and other resources deterministically.

## Buffers and process memory

Typed arrays are views over backing buffers. Keeping a small view alive can keep its entire backing buffer alive. The bytes may be accounted outside the ordinary JavaScript heap, so a stable `heapUsed` does not prove total process memory is stable. In Node.js, compare `heapUsed`, `external`, `arrayBuffers`, and RSS; `arrayBuffers` is included in `external`, and RSS covers the wider process. On worker threads, RSS is process-wide while other fields describe the current thread.

## Summary

Tracing collection reclaims unreachable storage and handles cycles, but cannot identify unwanted objects that remain reachable or close external resources. Generations and concurrent/incremental work are engine strategies with measurable trade-offs. Separate allocation rate, retained heap, buffer/native memory, and pause behavior; use weak observation only when disappearance is safe.

# Hash Tables and Hash Maps

When an application searches a database index or accesses a key in a `Map`, developers expect immediate $O(1)$ lookups. However, behind this constant-time guarantee lies an intricate machinery of integer hashing, modular range reduction, collision resolution chains, and dynamic array resizing.

## Definition

A **hash table** is an associative data structure that stores key-value pairs in an underlying contiguous array. It computes an integer hash code from the key using a hash function, maps that code to an array slot index via range reduction, and resolves collisions using deterministic search sequences or chained buckets to provide expected average $O(1)$ time complexity for lookups, insertions, and deletions.

> **Textbook Definition:** A hash table is a keyed data structure that implements an associative array abstract data type using a hash function to map keys into an array of buckets or slots. Collisions resulting from non-injective hash mappings are resolved through separate chaining or open addressing, with expected sublinear performance governed by load factors and amortized geometric resizing.

## First Principles

1. **Non-Injective Mapping Inevitability (Pigeonhole Principle):** The universe of potential keys (e.g. all 64-bit strings) vastly exceeds any table's finite bucket capacity $M$. Collisions—where two distinct keys $k_1 \neq k_2$ produce identical slot indices—are mathematically guaranteed to occur.
2. **Two-Stage Address Computation:** Address resolution consists of two operations: first, a cryptographic or non-cryptographic hash function computes an integer digest $H(k)$; second, range reduction maps this integer into array bounds (typically $H(k) \pmod M$ or $H(k) \ \& \ (M - 1)$ for power-of-two capacities).
3. **Equality Verification Invariant:** A hash code match is a necessary but insufficient proof of key identity. The hash table must always execute a secondary equality check (such as `SameValueZero` in JavaScript) on stored keys to confirm an exact match.
4. **Load Factor Governs Degradation:** As the load factor $\alpha = N / M$ (items divided by capacity) rises, collision frequency increases geometrically, degrading lookups toward $O(N)$ linear scans unless the table resizes and rehashes.

```text
Key Input: "alice"
      │
      ▼ (Hash Function H(k))
Hash Code: 0x8F3A21BC
      │
      ▼ (Range Reduction: Hash & (Capacity - 1))
Bucket Index: 3
      │
      ▼ (Inspect Slot 3)
┌────────────────────────────────────────────────────────┐
│ Slot 3: Stored Key "bob" (Collision!)                  │
├────────────────────────────────────────────────────────┤
│ Follow Collision Resolution:                           │
│ 1. Separate Chaining: Follow next pointer in bucket    │
│ 2. Open Addressing: Probe slot 4, 5, 6...              │
│ 3. V8 OrderedHashTable: Follow NextChain index in Data │
└────────────────────────────────────────────────────────┘
```

## Collision Resolution: Separate Chaining vs. Open Addressing

| Dimension | Separate Chaining | Open Addressing (Linear / Quadratic) | V8 `OrderedHashTable` |
| :--------------------------- | :----------------------------------------- | :-------------------------------------- | :------------------------------------------- |
| **Storage Structure** | Array of linked lists or balanced trees | Flat array of direct key-value slots | Contiguous flat array (Buckets + Data table) |
| **Collision Handling** | Appends entries into bucket's linked chain | Probes adjacent slots ($i+1, i+2\dots$) | Follows internal collision chain indices |
| **Max Load Factor $\alpha$** | Can exceed $1.0$ (e.g. $\alpha = 2.0$) | Must remain strictly $< 0.75$ | Strictly managed around load limit $0.5$ |
| **Cache Locality** | Poor (pointer-chasing across heap nodes) | High (sequential array memory access) | High (contiguous backing buffer) |
| **Deletion Mechanism** | Standard linked-node unlinking | Requires **Tombstone** sentinels | Marks entry as deleted; compacted on rehash |

### The Tombstone Problem in Open Addressing

In open addressing (linear probing), deleting an item cannot simply set its slot to `undefined`. If keys `A` and `B` collide at slot 2, `B` probes and settles in slot 3. If `A` is cleared to empty, a subsequent search for `B` starts at slot 2, encounters an empty slot, and falsely terminates with a "not found" result.

The table must write a **Tombstone** sentinel in slot 2. Searches treat tombstones as occupied and continue probing; insertions treat tombstones as free slots and overwrite them.

## V8 Engine Internals: How `Map` and `Set` Work

The ECMAScript specification imposes a challenging requirement on `Map` and `Set`: they must deliver **average sublinear lookup performance** while simultaneously guaranteeing that iteration runs strictly in **insertion order**.

V8 solves this using an internal C++ data structure named **`OrderedHashTable`** (defined in `v8/src/objects/ordered-hash-table.h`):

```text
V8 OrderedHashTable Flat Memory Layout:
┌───────────────────────────────────────────────────────────────────────┐
│ Header (Capacity, Number of Elements, Number of Deleted Elements)     │
├───────────────────────────────────────────────────────────────────────┤
│ Hash Buckets: [ Slot 0 ][ Slot 1 ][ Slot 2 ][ Slot 3 ]                │
│ (Each slot stores an index pointing to the first entry in Data Table) │
├───────────────────────────────────────────────────────────────────────┤
│ Data Table (Grows Sequentially in Insertion Order):                   │
│ Entry 0: [ Key: "a" ][ Value: 10 ][ Next: -1 ]                        │
│ Entry 1: [ Key: "b" ][ Value: 20 ][ Next: -1 ]                        │
│ Entry 2: [ Key: "c" ][ Value: 30 ][ Next:  0 ] (Collision chain)      │
└───────────────────────────────────────────────────────────────────────┘
```

1. **Insertion Order Preservation:** New keys are appended sequentially to the next free slot in the Data Table. Iteration simply walks the Data Table from index `0` to `N - 1`, effortlessly guaranteeing insertion order without auxiliary linked lists.
2. **Fast Hash Lookup:** The Hash Buckets array contains integer offsets pointing into the Data Table. When looking up a key, V8 hashes the key, finds the bucket, and follows the `Next` collision indices inside the Data Table.
3. **Soft Deletion & Compaction:** When `.delete(key)` is invoked, V8 marks the Data Table entry with a sentinel "Hole" value and increments `NumberOfDeletedElements`. When deletions exceed a threshold or capacity is exhausted, the table is compacted and rehashed into a new contiguous allocation.

## Amortized Complexity vs. Latency Spikes

While hash table insertions are mathematically **amortized $O(1)$**, individual operations exhibit variable latency profiles:

```text
Insert Operations Timeline:
[ O(1) ][ O(1) ][ O(1) ][ O(1) ] ──▶ [ RESIZE: O(N) Latency Spike! ] ──▶ [ O(1) ]
```

When the number of entries exceeds `Capacity * MaxLoadFactor`:
1. The table allocates a new backing buffer with double the capacity ($2 \times M$).
2. Every existing key must undergo range reduction against the new capacity and be reinserted into the new bucket array.
3. For a table holding 1,000,000 entries, this single resize operation incurs an $O(N)$ execution pause, which can drop frames in latency-sensitive audio or rendering loops.

## Summary

Hash tables provide expected constant-time associative lookups by pairing hash functions with modular range reduction and collision resolution strategies. Separate chaining stores collisions in external linked lists, while open addressing probes contiguous slots using tombstone sentinels. V8 implement `Map` and `Set` via `OrderedHashTable`, combining a bucket index array with an insertion-ordered flat data table to deliver both $O(1)$ lookups and deterministic iteration order.

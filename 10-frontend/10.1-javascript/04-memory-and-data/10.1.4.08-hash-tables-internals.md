# Hash Tables and Hash Maps

Hash tables can provide expected $O(1)$ access under suitable hashing/load assumptions. JavaScript Map instead promises average sublinear access, without mandating one hashing strategy or constant worst-case latency. Knowing the machinery explains the failure modes: collision pile-ups, tombstone drag, and resize pauses.

```javascript
const index = new Map();
index.set('alice', { id: 1 });
console.log(index.get('alice')); // { id: 1 } — hash, reduce, fetch
console.log(index.get('nobody')); // undefined — miss after probing
```

## Definition

A **hash table** stores key-value pairs in a contiguous array: a **hash function** computes an integer code from the key, **range reduction** maps it to a slot index, and a **collision strategy** resolves sharing — delivering expected average $O(1)$ lookup, insertion, and deletion.

> **Textbook Definition:** A hash table is a keyed data structure that implements an associative array abstract data type using a hash function to map keys into an array of buckets or slots. Collisions resulting from non-injective hash mappings are resolved through separate chaining or open addressing, with expected sublinear performance governed by load factors and amortized geometric resizing.

## First Principles

The key universe (every string, number, object) dwarfs any finite bucket array — so by the **Pigeonhole Principle**, distinct keys *must* share slots. A finite range cannot uniquely identify every possible key; collisions must be managed rather than assumed absent. This does not mean every small actual key set necessarily contains a collision. Separately, equality is not hashing: a code match only nominates a candidate, and a second equality check (`SameValueZero` in JS) confirms identity.

## 1. Why Collisions Are Inevitable

Two distinct keys can hash to the same slot; if more distinct keys than slots are stored, a collision follows from the pigeonhole principle. With $M = 8$ buckets, a lookup walks the full pipeline:

```text
Key Input: "alice"
      │
      ▼ (Hash Function H(k))
Hash Code: 0x8F3A21BB
      │
      ▼ (Range Reduction: Hash & (Capacity - 1))
Bucket Index: 3
      │
      ▼ (Inspect Slot 3)
┌────────────────────────────────────────────────────────┐
│ Slot 3: Stored Key "bob" (Collision!)                  │
├────────────────────────────────────────────────────────┤
│ Follow Collision Resolution:                           │
│ 1. Separate Chaining: Follow next pointer in bucket    │
│ 2. Open Addressing: Probe slot 4, 5, 6...              │
│ 3. V8 OrderedHashTable: Follow NextChain index in Data │
└────────────────────────────────────────────────────────┘
```

## 2. Two-Stage Address Computation

A common hash-table pipeline is hash then range-reduce; implementations can combine these operations:

```text
H(k) → integer digest
      ↓
H(k) mod M  OR  H(k) & (M - 1)  →  bucket index
```

A bitmask `H & (M - 1)` is one reduction for a power-of-two capacity; modulo is another common choice. Multiplication/high-bit schemes and other implementation choices also exist; the distribution must suit the chosen reduction.

## 3. Collision Resolution Strategies

| Dimension | Separate Chaining | Open Addressing (Linear / Quadratic) | V8 `OrderedHashTable` |
| :--------------------------- | :----------------------------------------- | :---------------------------------------------------------------- | :-------------------------------------------------- |
| **Storage Structure** | Array of linked lists or balanced trees | Flat array of direct key-value slots | Contiguous flat array (Buckets + Data table) |
| **Collision Handling** | Appends entries into bucket's linked chain | Probes adjacent slots ($i+1, i+2\dots$) | Follows internal collision chain indices |
| **Max Load Factor $\alpha$** | Can exceed $1.0$ (e.g. $\alpha = 2.0$) | Needs a controlled probe/load policy; no universal 0.75 threshold | Version-specific entry/bucket capacity relationship |
| **Cache Locality** | Poor (pointer-chasing across heap nodes) | High (sequential array memory access) | High (contiguous backing buffer) |
| **Deletion Mechanism** | Standard linked-node unlinking | Often uses tombstones; backward-shift deletion is another policy | Marks entry as deleted; compacted on rehash |

**The tombstone problem**: in linear probing, blanking a deleted slot breaks chains — if `A` and `B` collided at slot 2 with `B` settling in slot 3, clearing `A` makes a search for `B` stop early at the "empty" slot 2. The fix is a **tombstone** sentinel: searches treat it as occupied and keep probing; insertions remember it as a reusable position but continue checking for an existing equal key farther along the probe path before inserting. Otherwise an update can incorrectly create a duplicate key.

## 4. V8 Engine Internals: How `Map` and `Set` Work

The spec demands average sublinear lookup *and* strict insertion-order iteration. The cited V8 **`OrderedHashTable`** source (`v8/src/objects/ordered-hash-table.h`) separates the concerns into bucket and ordered-entry regions in a backing store. This is an implementation example; inspect the source revision matching the deployed engine before assuming its exact layout:

```text
V8 OrderedHashTable Flat Memory Layout:
┌───────────────────────────────────────────────────────────────────────┐
│ Header (Capacity, Number of Elements, Number of Deleted Elements)     │
├───────────────────────────────────────────────────────────────────────┤
│ Hash Buckets: [ Slot 0 ][ Slot 1 ][ Slot 2 ][ Slot 3 ]                │
│ (Each slot stores an index pointing to the first entry in Data Table) │
├───────────────────────────────────────────────────────────────────────┤
│ Data Table (Grows Sequentially in Insertion Order):                   │
│ Entry 0: [ Key: "a" ][ Value: 10 ][ Next: -1 ]                        │
│ Entry 1: [ Key: "b" ][ Value: 20 ][ Next: -1 ]                        │
│ Entry 2: [ Key: "c" ][ Value: 30 ][ Next:  0 ] (Collision chain)      │
└───────────────────────────────────────────────────────────────────────┘
```

- **Insertion order**: new keys append sequentially to the Data Table, so iteration walks index `0 → N-1` with no auxiliary list.
- **Fast lookup**: buckets hold offsets into the Data Table; lookups hash, jump to the bucket, and follow `Next` collision indices.
- **Soft deletion**: `.delete()` stamps a Hole sentinel and bumps `NumberOfDeletedElements`; past a threshold (or at capacity) the table compacts and rehashes.

The inspected source defines entry capacity as `NumberOfBuckets() * kLoadFactor` with `kLoadFactor = 2`; that is not a universal 0.5 entries-per-bucket limit. Deleted entries and small-table variants add policies. The JavaScript contract specifies neither this constant nor these regions.

## 5. Amortized Complexity vs. Latency Spikes

With a suitable hash/load policy and geometric growth, insertions can be amortized $O(1)$; hashing a long key and individual growth operations still add cost:

```text
Insert Operations Timeline:
[ O(1) ][ O(1) ][ O(1) ][ O(1) ] ──▶ [ RESIZE: O(N) Latency Spike! ] ──▶ [ O(1) ]
```

A geometric-growth implementation may allocate a larger table and rehash entries, adding O(N) work to a particular insertion. Other implementations can spread migration or use different policies. Measure the running engine and workload rather than predicting a fixed pause from entry count. JavaScript Map exposes no portable reserve-capacity API; bound table size/churn or prepare data outside a latency-sensitive path.

## Summary

Hash tables pair hash-then-reduce addressing with chaining or probing (tombstones preserving probe chains on delete). V8's `OrderedHashTable` separates bucket indexes from an insertion-ordered data table, illustrating expected efficient access plus insertion-ordered iteration under its chosen policy. Amortized $O(1)$ still hides $O(N)$ resize pauses — avoid unbounded growth on latency-critical paths; there is no portable Map reserve operation.

# Hash Tables & HashMaps — Internals, Collision Resolution & V8


---

## Definition

A hash table is an array plus a hash function that maps arbitrary keys to slot indexes, buying average O(1) lookup, insert, and delete at the price of one unavoidable problem: two keys can claim the same slot. Every row below is either part of that mechanism or a strategy for the collision problem — which is why interviewers treat this table as the chapter's map.

## First Principles

Hash tables are forced by a two-sided constraint:

1. **Arrays give O(1) only by address; keys aren't addresses.** To get O(1) lookup *by key*, something must turn a key into an index: the hash function. Everything about hash tables — buckets, collisions, resizing — is managing the imperfection of that transformation.
2. **Collisions are inevitable** (pigeonhole: more possible keys than slots), so a collision strategy — chaining or open addressing — is not optional design but required machinery, and it's where the real complexity lives.
3. **Amortized O(1) requires controlled load.** Fixed capacity + growing data ⇒ degrading chains; therefore the table resizes (rehashing everything) when load factor crosses a threshold. That rehash is why a single insert is occasionally O(n) while *amortized* cost stays O(1) — the core interview nuance.
4. **JS objects/Maps are this machinery with different key rules** (string-coerced vs identity-preserving, → 10.1.4.02). V8 additionally hides shaped hidden classes behind plain objects — which is why deleting properties and mixed shapes degrade performance.


## Why It Matters

Hash tables are the **most important data structure in practice**. Hash tables underpin many Map/Set and dictionary implementations. Ordinary JavaScript objects can also use shaped property storage, and Redis hashes may use compact encodings for small records; an API name does not mandate one internal representation. Understanding internals matters for:

1. **Performance**: A well-tuned hash table is O(1) for lookup/insert/delete. A poorly tuned one degrades to O(n) when load factor is too high or the hash function is bad.
2. **Interviews**: "Design a HashMap" (LC #706), "LRU Cache" (LC #146), "Group Anagrams" (LC #49), "Two Sum" (LC #1) — all require knowing how hash tables work.
3. **Debugging**: Memory leaks, unexpected collisions, and performance cliffs all trace back to hash table internals.
4. **Distributed systems**: Consistent hashing, partitioning, and caching all build on hash table concepts.

## How Hash Tables Work

### The Core Idea

```text
hash("alice") → 3     Store (alice, 42) at index 3
hash("bob")   → 7     Store (bob, 17) at index 7
hash("carol") → 3     Collision! "carol" and "alice" both map to index 3
```

```text
Array (m=8 slots):

Index:  0    1    2    3         4    5    6    7
      [ null, null, null, (alice,42), null, null, null, (bob,17) ]
                                         ↑
                              hash("alice") = 3
                              hash("carol") = 3  ← COLLISION
```

### The Hash Function

A good hash function distributes keys **uniformly** across the array. Common strategies (runtime choices and versions differ):

| Method | Formula | Notes |
| ------------------ | ------------------------------------ | ------------------------------------------------------------------------------------------- |
| **Division** | `h(k) = k % m` | Simple; choose `m` prime to minimize clustering |
| **Multiplication** | `h(k) = ⌊m × (k × A mod 1)⌋` | `A ≈ 0.618` (golden ratio); works for any `m` |
| **FNV-1a** | Bit-mixing: `h = (h ^ byte) × prime` | Fast, good distribution; used in many runtime hash maps |
| **MurmurHash3** | 128-bit mixing function | Non-cryptographic mixing family; verify the selected variant in a particular implementation |
| **SipHash** | Cryptographically keyed hash | Resistant to hash-flooding DoS; used by Python, Ruby |

```typescript
// FNV-1a (32-bit) — simple, fast, good enough for most hash tables
function fnv1a(key: string): number {
  let h = 0x811c9dc5; // FNV offset basis
  for (let i = 0; i < key.length; i++) {
    h ^= key.charCodeAt(i);
    h = Math.imul(h, 0x01000193); // FNV prime
  }
  return h >>> 0; // unsigned 32-bit
}

// Map to array index
function indexFor(key: string, capacity: number): number {
  return fnv1a(key) % capacity;
}
```

**Why not MD5/SHA-256?** They provide cryptographic properties such as collision and preimage resistance; general cryptographic hashes are not deliberately slow password hashes. Hash tables need *fast* and *uniform*: FNV-1a is one pass of xor+multiply over the bytes, SHA-256 is 64 rounds of compression plus message scheduling. Enough distribution for bucketing, at a fraction of the cost.

## How the parts fit together

A key is hashed, its hash selects a bucket/slot, and equality distinguishes the entries that land there. A load policy grows the storage before collision work becomes excessive. The following vocabulary names those roles; the collision strategies below show their different storage choices.

| Term | Meaning | Interview one-liner |
| ---------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Hash function** | `f(key) → index` mapping an arbitrary key to a bounded array slot | "The function that turns your key into an array position" |
| **Collision** | Two distinct keys `k₁ ≠ k₂` where `h(k₁) = h(k₂)` | "Inevitable by pigeonhole — the real question is how you handle it" |
| **Load factor** `α` | `n / m` — entries ÷ slots. Controls when to resize | "α > 0.75 → rehash in Java; α > 0.5 → common default" |
| **Separate chaining** | Each bucket holds a linked list (or balanced tree) of colliding entries | "A mini-container at each slot" |
| **Open addressing** | All entries live in the array itself; collisions probe for the next open slot | "No overflow — everything stays in one flat array" |
| **Linear probing** | On collision, check slot+1, slot+2, … until empty | "Simple but suffers clustering" |
| **Quadratic probing** | Check slot+1², slot+2², slot+3², … | "Breaks primary clustering" |
| **Double hashing** | Use `h₁(key)` for the first slot, `h₂(key)` as the step size | "Best probe distribution; most expensive" |
| **Robin Hood hashing** | Open addressing where a new entry "steals" from a less-located entry | "Steals from the rich (short probe) to give to the poor (long probe)" |
| **Rehashing** | Allocate a larger array, re-insert all entries | "O(n) amortized over n inserts → O(1) per insert" |
| **Amortized O(1)** | Most inserts are O(1); occasional rehash is O(n) but spreads cost | "Pays for itself over a sequence of operations" |

## Collision Resolution

### Strategy 1: Separate Chaining

Each bucket holds a linked list (or tree) of all entries that hash to that index.

```text
After inserting: alice(3), bob(7), carol(3), dave(3)

Index 0: [ ]
Index 1: [ ]
Index 2: [ ]
Index 3: [(alice,42)] → [(carol,99)] → [(dave,5)]   ← chain of 3
Index 4: [ ]
Index 5: [ ]
Index 6: [ ]
Index 7: [(bob,17)]
```

```typescript
class ChainingHashMap<K, V> {
  private buckets: Array<Array<[K, V]>>;
  private size = 0;
  private capacity: number;
  private loadFactor: number;

  constructor(capacity = 16, loadFactor = 0.75) {
    this.capacity = capacity;
    this.loadFactor = loadFactor;
    this.buckets = Array.from({ length: capacity }, () => []);
  }

  private hash(key: K): number {
    const str = String(key);
    let h = 0x811c9dc5;
    for (let i = 0; i < str.length; i++) {
      h ^= str.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    return (h >>> 0) % this.capacity;
  }

  set(key: K, value: V): void {
    if (this.size / this.capacity > this.loadFactor) {
      this.resize(this.capacity * 2);
    }
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    const existing = bucket.find(([k]) => k === key);
    if (existing) {
      existing[1] = value; // update
    } else {
      bucket.push([key, value]);
      this.size++;
    }
  }

  get(key: K): V | undefined {
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    const pair = bucket.find(([k]) => k === key);
    return pair?.[1];
  }

  delete(key: K): boolean {
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    const len = bucket.length;
    this.buckets[idx] = bucket.filter(([k]) => k !== key);
    if (bucket.length !== this.buckets[idx].length) {
      this.size--;
      return true;
    }
    return false;
  }

  private resize(newCapacity: number): void {
    const old = this.buckets;
    this.capacity = newCapacity;
    this.buckets = Array.from({ length: newCapacity }, () => []);
    this.size = 0;
    for (const bucket of old) {
      for (const [k, v] of bucket) {
        this.set(k, v);
      }
    }
  }
}
```

**Performance with chaining:**

| Operation | Average | Worst case (all collide) |
| ----------- | --------- | -------------------------- |
| Insert | O(1) | O(n) |
| Lookup | O(1) | O(n) |
| Delete | O(1) | O(n) |

**When chains grow long, Java 8+ converts them to balanced trees** (red-black tree) subject to bin size and table-capacity conditions. Tree bins can improve collisions, but arbitrary incomparable keys still require careful worst-case analysis; this is not a universal bound for every key type. This is the "treeification" optimization.

### Strategy 2: Open Addressing

All entries live in the array itself. On collision, probe for the next open slot.

```text
Linear probing — hash("carol") = 3, slot 3 occupied:

  Probe: slot 3 (taken) → slot 4 (empty!) → insert carol at 4

Index:  0    1    2    3         4         5    6    7
      [ null, null, null, (alice,42), (carol,99), null, null, (bob,17) ]
```

```typescript
class OpenAddressingHashMap<K, V> {
  private keys: (K | null)[];
  private values: (V | null)[];
  private size = 0;
  private capacity: number;
  private DELETED = Symbol('DELETED');

  constructor(capacity = 16) {
    this.capacity = capacity;
    this.keys = new Array(capacity).fill(null);
    this.values = new Array(capacity).fill(null);
  }

  private hash(key: K): number {
    const str = String(key);
    let h = 0x811c9dc5;
    for (let i = 0; i < str.length; i++) {
      h ^= str.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    return (h >>> 0) % this.capacity;
  }

  set(key: K, value: V): void {
    if (this.size >= this.capacity * 0.7) this.resize(this.capacity * 2);
    let idx = this.hash(key);
    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null || this.keys[idx] === this.DELETED) {
        this.keys[idx] = key;
        this.values[idx] = value;
        this.size++;
        return;
      }
      if (this.keys[idx] === key) {
        this.values[idx] = value; // update
        return;
      }
      idx = (idx + 1) % this.capacity; // linear probe
    }
  }

  get(key: K): V | undefined {
    let idx = this.hash(key);
    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) return undefined;
      if (this.keys[idx] === key) return this.values[idx] as V;
      idx = (idx + 1) % this.capacity;
    }
    return undefined;
  }

  delete(key: K): boolean {
    let idx = this.hash(key);
    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) return false;
      if (this.keys[idx] === key) {
        this.keys[idx] = this.DELETED as any; // tombstone
        this.values[idx] = null;
        this.size--;
        return true;
      }
      idx = (idx + 1) % this.capacity;
    }
    return false;
  }

  private resize(newCapacity: number): void {
    const oldKeys = this.keys;
    const oldValues = this.values;
    this.capacity = newCapacity;
    this.keys = new Array(newCapacity).fill(null);
    this.values = new Array(newCapacity).fill(null);
    this.size = 0;
    for (let i = 0; i < oldKeys.length; i++) {
      if (oldKeys[i] !== null && oldKeys[i] !== (this.DELETED as any)) {
        this.set(oldKeys[i] as K, oldValues[i] as V);
      }
    }
  }
}
```

### Probing Variants Compared

| Probe | Sequence | Pros | Cons |
| -------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Linear** | `h+1, h+2, h+3, ...` | Simple, cache-friendly | **Primary clustering** — long runs of occupied slots grow self-reinforcing |
| **Quadratic** | `h+1², h+2², h+3², ...` | Breaks primary clustering | **Secondary clustering** — same hash → same probe sequence |
| **Double** | `h₁+k·h₂(key)` | Breaks both clusterings | Two hash computations; `h₂` must be nonzero and coprime to the table capacity to visit every slot |
| **Robin Hood** | Linear probe, but swap if current entry has shorter probe distance | Compresses *variance* — probe distances become less uneven; occupied clusters can remain | More complex; still suffers clustering at high load |

```text
CLUSTERING VISUALIZED (linear probing, 50% load):

Linear probing — clustered:
[ ████░░░░████████░░░░░░░░████░░░░ ]
  ↑ long occupied run → new keys pile up here

Double hashing — uniform:
[ █░░░██░░█░░░███░░░░██░░█░░░██░░ ]
  ↑ keys scattered evenly
```

## Load Factor & Rehashing

The **load factor** `α = n/m` (entries ÷ slots) determines performance:

```text
SEPARATE CHAINING — successful-lookup probes ≈ 1 + α/2
(measured, m = 32768 buckets, uniform hash):

  α = 0.50 → 1.25 probes    α = 0.75 → 1.38 probes (Java default)
  α = 0.90 → 1.45 probes    α = 1.50 → 1.75 probes (α may exceed 1 —
                              chains simply get longer)

As long as resizing keeps α bounded this cost is constant → O(1). A table
that never resizes grows α with n, chains grow with it, and lookup degrades
to O(n).

OPEN ADDRESSING — measured successful-lookup probes (linear probing):

  α = 0.50 → 1.5 probes     α = 0.70 → 2.2 probes
  α = 0.90 → 5.4 probes     α = 0.95 → 10.2 probes
  α = 1.00 → insertion cannot terminate: there is no empty slot left.

That asymmetry is why chaining tolerates α near 1 while open-addressed
tables must resize early and hold α well under 1.
```

**Rehashing** = allocate a larger array (typically 2×), re-insert all entries:

```text
Before rehash (capacity=4, α=1.0):
Index: 0    1    2    3
      [ A    B    C    D ]

After rehash (capacity=8, α=0.5):
Index: 0    1    2    3    4    5    6    7
      [ A    _    C    _    B    _    _    D ]
         ↑                                  ↑
    rehashed to new positions based on h(key) % 8
```

**Amortized O(1) proof (aggregate method):**
- Inserting `n` keys into an initially empty table requires at most `1 + 2 + 4 + ... + n ≈ 2n` operations total (sum of all rehash costs).
- Average per insert: `2n / n = 2` = O(1) amortized.
- Geometric growth gives the amortized resize bound; exact doubling is not mandatory. Shrink at a substantially lower threshold than growth to avoid resize thrashing. Expected constant-time hashing/collision costs are a separate assumption from amortizing resizes.

## V8 Internals — How JavaScript Implements Hash Tables

### V8's `Map` (JS Map, not V8 Map — confusing naming!)

V8 uses an **ordered hash table** to preserve insertion order for JS `Map` and `Set`. The internal structure:

```text
V8 OrderedHashTable (used for Map/Set):

┌─────────────────────────────────────────────────┐
│ Data table:  one row per entry, in insertion    │
│              order — [ hash | key | value ]     │
│ Hash index:  separate chaining — bucket =       │
│              hash & (buckets − 1); colliding    │
│              slots chained by table offsets     │
│ Capacity:    entries = buckets × 2 (2 per       │
│              bucket); doubles when full and     │
│              compacts deletions first; shrinks  │
│              when fewer than ¼ full             │
│ Hash:        strings → seeded content hash      │
│              (Jenkins one-at-a-time); objects   │
│              → a random identity hash stored    │
│              on the object                      │
│ Tombstones:  deletions unlink the slot; the row │
│              is reclaimed at the next rehash    │
└─────────────────────────────────────────────────┘
```

### V8's Object (plain `{}`)

Plain JS objects use a different internal representation — a **property dictionary** that changes representation based on usage:

```text
V8 Object representations (hidden classes / maps):

Phase 1: Fast mode (in-object properties)
┌───────────────────────────┐
│ Hidden Class (Map)        │  ← shared schema
│ Properties: [a, b, c]     │  ← fixed offsets, fast access
│ In-object slots (fixed)   │
└───────────────────────────┘

Phase 2: Overflow to backing store
┌───────────────────────────┐
│ Hidden Class (Map)        │
│ In-object slots: [a, b]   │
│ Backing Store (Array):    │  ← hash table for overflow
│   [c → value, d → value]  │
└───────────────────────────┘

Phase 3: Dictionary mode (too many deletes/reconfigs)
┌───────────────────────────┐
│ Name Dictionary           │  ← full hash table
│ Keys: [string → index]    │
│ Values: sparse array      │
└───────────────────────────┘
```

**Why this matters:** If you add/delete properties randomly, V8 falls back to dictionary mode (hash table), which is slower than the fast in-object representation. This is why creating objects with a consistent shape ("hidden class transitions") is a V8 optimization best practice.

### Implementation choices are examples, not language contracts

| Feature | V8 Map/Set | Java HashMap | Python dict |
| ------------------ | ------------------------------------------------------------- | -------------------------- | --------------------------------------- |
| Implementation | Ordered hash table | Array + chaining | Combined table (keys + hashes + values) |
| Hash function | Seeded content hash (strings); stored identity hash (objects) | `key.hashCode()` + spread | SipHash-1-3 (random seed) |
| Collision strategy | Separate chaining (bucket offsets) | Chaining (treeify at 8) | Open addressing (perturbation) |
| Load factor | 2 entries per bucket | 75% | 66% (⅔ full) |
| Resize factor | ×2 when full | ×2 | ≈×2 (new size = 3 × entries) |
| Insertion order | ✅ Preserved | ❌ Not preserved | ✅ Preserved (Python 3.7+) |
| Tombstones | Yes (rehashed) | No (removed from chain) | Yes (index marked dummy; rehashed) |
| Worst-case lookup | O(n) (all hash to same bucket) | O(log n) (treeified chain) | O(n) |

## Code Examples

### Design a HashMap (LC #706) — Interview Classic

```typescript
class MyHashMap {
  private buckets: Array<Array<[number, number]>>;
  private capacity = 1000;

  constructor() {
    this.buckets = Array.from({ length: this.capacity }, () => []);
  }

  private hash(key: number): number {
    return key % this.capacity;
  }

  put(key: number, value: number): void {
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    const pair = bucket.find(([k]) => k === key);
    if (pair) {
      pair[1] = value;
    } else {
      bucket.push([key, value]);
    }
  }

  get(key: number): number {
    const idx = this.hash(key);
    const pair = this.buckets[idx].find(([k]) => k === key);
    return pair ? pair[1] : -1;
  }

  remove(key: number): void {
    const idx = this.hash(key);
    this.buckets[idx] = this.buckets[idx].filter(([k]) => k !== key);
  }
}
```

### Two Sum (LC #1) — HashMap Pattern

```typescript
function twoSum(nums: number[], target: number): number[] {
  const seen = new Map<number, number>(); // value → index
  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];
    if (seen.has(complement)) {
      return [seen.get(complement)!, i];
    }
    seen.set(nums[i], i);
  }
  return [];
}
// O(n) time, O(n) space — the hash table makes this possible
```

### Group Anagrams (LC #49) — Hash Map as Bucket

```typescript
function groupAnagrams(strs: string[]): string[][] {
  const groups = new Map<string, string[]>();
  for (const s of strs) {
    const key = s.split('').sort().join(''); // canonical form
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key)!.push(s);
  }
  return [...groups.values()];
}
// O(n × k log k) where k = max string length
```

### LRU Cache (LC #146) — Map insertion order

```typescript
class LRUCache {
  private cache = new Map<number, number>();
  constructor(private capacity: number) {}

  get(key: number): number {
    if (!this.cache.has(key)) return -1;
    const value = this.cache.get(key)!;
    this.cache.delete(key);
    this.cache.set(key, value); // move to end (most recent)
    return value;
  }

  put(key: number, value: number): void {
    if (this.cache.has(key)) this.cache.delete(key);
    if (this.cache.size >= this.capacity) {
      const oldest = this.cache.keys().next().value!; // first = least recent
      this.cache.delete(oldest);
    }
    this.cache.set(key, value);
  }
}
// Map iteration order = insertion order → .keys().next() = LRU entry
```

### Implement Robin Hood Hashing

```typescript
class RobinHoodHashMap<K, V> {
  private keys: (K | null)[];
  private values: (V | null)[];
  private hashes: number[];
  private size = 0;
  private capacity: number;

  constructor(capacity = 16) {
    this.capacity = capacity;
    this.keys = new Array(capacity).fill(null);
    this.values = new Array(capacity).fill(null);
    this.hashes = new Array(capacity).fill(0);
  }

  private probeDistance(key: K, idx: number): number {
    const ideal = this.hash(key) % this.capacity;
    return (idx - ideal + this.capacity) % this.capacity;
  }

  set(key: K, value: V): void {
    if (this.size >= this.capacity * 0.7) this.resize(this.capacity * 2);
    let idx = this.hash(key) % this.capacity;
    let dist = 0;
    let insertingKey = key;
    let insertingValue = value;
    let insertingHash = this.hash(key);

    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) {
        this.keys[idx] = insertingKey;
        this.values[idx] = insertingValue;
        this.hashes[idx] = insertingHash;
        this.size++;
        return;
      }
      if (this.keys[idx] === insertingKey) {
        this.values[idx] = insertingValue;
        return;
      }
      // Robin Hood: if existing entry has shorter probe distance, swap
      const existingDist = this.probeDistance(this.keys[idx]!, idx);
      if (dist > existingDist) {
        // Steal this slot
        [insertingKey, this.keys[idx]] = [this.keys[idx]!, insertingKey];
        [insertingValue, this.values[idx]] = [this.values[idx]!, insertingValue];
        [insertingHash, this.hashes[idx]] = [this.hashes[idx], insertingHash];
        dist = existingDist;
      }
      idx = (idx + 1) % this.capacity;
      dist++;
    }
  }

  get(key: K): V | undefined {
    const h = this.hash(key);
    let idx = h % this.capacity;
    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) return undefined;
      if (this.keys[idx] === key && this.hashes[idx] === h) return this.values[idx] as V;
      if (this.probeDistance(this.keys[idx]!, idx) < i) return undefined; // early exit
      idx = (idx + 1) % this.capacity;
    }
    return undefined;
  }

  private hash(key: K): number {
    const str = String(key);
    let h = 0x811c9dc5;
    for (let i = 0; i < str.length; i++) {
      h ^= str.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    return h >>> 0;
  }

  private resize(newCap: number): void {
    const oldK = this.keys, oldV = this.values, oldH = this.hashes;
    this.capacity = newCap;
    this.keys = new Array(newCap).fill(null);
    this.values = new Array(newCap).fill(null);
    this.hashes = new Array(newCap).fill(0);
    this.size = 0;
    for (let i = 0; i < oldK.length; i++) {
      if (oldK[i] !== null) this.set(oldK[i] as K, oldV[i] as V);
    }
  }
}
```

## Real-World Use Cases

| Use case | Hash table role | Key insight |
| ---------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **JS `Object` / `Map`** | Property *names* live in a hash table (name dictionary) | Fast objects resolve `obj.foo` by hidden-class offset; dictionary-mode objects do a real hash lookup |
| **Database indexes** | B-tree is primary, but hash indexes for equality-only lookups | PostgreSQL `hash` access method answers `=` queries |
| **Redis Hashes** | `HSET` / `HGET` — hash table per user/session | "The string-equivalent for structured data" |
| **Python `dict`** | All dict literals, sets, and kwargs use hash tables | `**kwargs` is literally unpacking a hash table |
| **Compiler symbol tables** | Variable/function name → type info | Fast lookup is critical for compile speed |
| **DNS resolution** | Domain name → IP address (with caching) | Hash table in local resolver cache |
| **Memcached / Redis cache** | Key → value with O(1) get/set | Consistent hashing distributes across nodes |
| **Webhook signature verification** | `Map<webhookId, secret>` for HMAC lookup | Efficient key lookup; signature validation still needs cryptographic comparison and replay protection |

## Common Mistakes

| Mistake | Why it fails | Instead |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Using a bad hash function (e.g., `hashCode() % smallNumber`) | Poor distribution → many collisions → O(n) | Use FNV-1a, MurmurHash3, or SipHash; ensure `m` is large and prime-ish |
| Ignoring load factor | α → 1.0 means every probe checks occupied slots; open addressing breaks | Resize at α > 0.75 (chaining) or α > 0.5 (open addressing) |
| Forgetting to rehash on delete (open addressing) | Tombstones accumulate → probe chains grow → lookup degrades | Periodically rehash, or use Robin Hood / backward shift deletion |
| Expecting structurally identical objects to share a `Map` entry | `Map` compares object keys by identity (SameValueZero), so `{id: 1}` and a different `{id: 1}` are two distinct keys | Key by a primitive (`id`), or canonicalize first (`JSON.stringify`, sorted fields) |
| Treating hash table lookup as always O(1) | Worst case is O(n) with adversarial inputs (hash flooding DoS) | Use SipHash with a random seed (Python, Ruby do this by default) |
| Expecting iteration order from plain objects | Post-2015 order is well-defined but not pure insertion order: integer-like keys come first in ascending order, then string keys in insertion order | Use `Map` when insertion order matters |

---

## Best Practices

1. **Choose load by the collision strategy and measurements**: chaining permits loads above one; open addressing needs spare slots. The tutorial thresholds are examples, not universal safe defaults.
2. **Use a fast hash function**: FNV-1a or MurmurHash3 for in-process hash tables. SHA-256 is for security, not speed.
3. **Coordinate capacity with hash mixing and probing**: masking a power-of-two capacity still uses low bits, so ensure those bits are well mixed. A prime capacity alone cannot rescue a poor hash.
4. **Pre-size when possible**: If you know `n` in advance, allocate `m ≈ n / 0.75` to avoid rehashing.
5. **Prefer `Map` over `{}` in JS**: Better performance for dynamic keys, no inherited property-name collision, with average sublinear access required by ECMAScript.
6. **Understand your engine**: V8's `Map`/`Set` uses separate chaining; Java's `HashMap` uses chaining with treeification; Python's dict uses a combined open-addressed index. The choice affects worst-case behavior.
7. **For interviews**: State the hash function, collision strategy, load factor threshold, and resize policy before writing code.

## Performance Considerations

| Factor | Effect on performance |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **Load factor** | Probe cost rises as open-addressed storage fills; insertion, successful and unsuccessful search have different estimates |
| **Hash quality** | Perfect hash → O(1); many collisions → O(n) |
| **Cache locality** | Open addressing is more cache-friendly (flat array) vs chaining (pointer chasing) |
| **Resize cost** | O(n) but amortized O(1) per insert; avoid resizing in latency-critical paths |
| **Entry size** | Large values → store pointers (indirection) not copies |
| **Tombstones** | Open addressing: deleted entries waste space until rehash; chaining: just remove from list |

LOOKUP COST vs LOAD FACTOR (measured, m = 32768, uniform hash):

Separate chaining — successful-lookup probes (≈ 1 + α/2):
  α:      0.1    0.3    0.5    0.7    0.9    0.95
         1.05   1.15   1.25   1.35   1.45   1.48

Open addressing — successful-lookup probes (linear probing):
  α:      0.1    0.3    0.5    0.7    0.9    0.95
         1.06   1.21   1.50   2.16   5.43  10.23

Chaining loses ~0.1 probes per +0.2 of α; linear probing collapses past
~0.9 (probe clusters feed on themselves), which is why open-addressed
tables resize earlier.

## Summary

- A hash table maps keys to values in **amortized O(1)** using a hash function to compute an array index.
- **Collisions are inevitable** — separate chaining (linked lists/trees per bucket) and open addressing (probing for empty slots) are the two resolution families.
- **Load policy** controls collision cost and resizing; choose thresholds for the implementation rather than treating example numbers as universal rules.
- **V8 uses an ordered hash table** for JS `Map`/`Set` — separate chaining, 2 entries per bucket, doubling when full — with insertion order preserved, plus a fast-to-dictionary transition for plain objects.
- **Robin Hood hashing** reduces worst-case variance by swapping entries to equalize probe distances.
- **For interviews**: implement with chaining (simpler), mention load factor + rehashing, state your hash function choice.

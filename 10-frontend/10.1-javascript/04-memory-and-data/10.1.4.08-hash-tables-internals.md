# Hash Tables & HashMaps — Internals, Collision Resolution & V8

A user lookup starts with a key like `alice`, but an array needs a numeric slot. Hashing gives the table a candidate slot; a second key can land there too, so the table must still resolve collisions and compare keys. Follow that one lookup to see where the average O(1) claim comes from and where it stops.

---

## Definition

A **hash table** stores key-value entries in indexed storage. A **hash function** maps a key to a hash code; a range-reduction step maps that code to a slot. Different keys can reach the same slot, so the table also needs a collision strategy and an equality check. With suitable hashing, capacity and collision behavior, lookup, insertion and deletion are expected O(1); resizing can still make an individual insertion O(n).

> **Textbook Definition:** A hash table maps keys to storage positions using a hash function and resolves collisions between keys mapped to the same position. Average operation cost depends on load, hash distribution and collision strategy.

## First Principles

Hash tables solve four linked constraints:

1. **An array can use an index directly; arbitrary keys need a conversion.** A hash function maps the key to a hash code, then range reduction chooses an array index. Buckets and collision handling deal with different keys reaching the same place.
2. **A collision strategy is necessary.** There are more possible keys than array slots, so distinct keys can share an index. Separate chaining stores multiple entries at a slot. Open addressing searches other slots.
3. **Growth must leave enough capacity.** The **load factor** is the number of entries divided by the number of slots. As it grows, collisions become more expensive. Resizing allocates more storage and **rehashes**, reinserts the entries into that storage. One resize can cost O(n). With suitable geometric growth, that occasional cost averages to O(1) across many inserts; this is **amortized** cost. Expected collision cost is a separate assumption.
4. **JavaScript APIs add their own key rules** (→ 10.1.4.02). Objects convert non-symbol property keys to strings; Maps preserve object-key identity. V8 can also store ordinary object properties using **hidden classes**, internal descriptions of an object's property layout. Deletions and changing shapes can affect those optimizations, so measure the actual workload.


## Follow a key from hash to stored entry

### Hash to a candidate slot, then compare keys

```text
hash("alice") → 3     Store (alice, 42) at index 3
hash("bob")   → 7     Store (bob, 17) at index 7
hash("carol") → 3     Collision! "carol" and "alice" both map to index 3
```

```text
Array (m=8 slots):

Index:  0    1    2    3         4    5    6    7
      [ null, null, null, (alice,42), null, null, null, (bob,17) ]
                     ↑
               alice and carol both select slot 3
```

Lookup must compare the requested key with a stored key after hashing: a matching bucket is only a candidate. To find carol in bucket 3, compare alice (not equal) and then carol (equal). Equality and hashing must agree: keys regarded as equal must select the same candidate path, while unequal keys are allowed to collide.

### The Hash Function

A good hash function distributes keys **uniformly** across the array. Common strategies (runtime choices and versions differ):

| Method | Formula | Notes |
| ------------------ | ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **Division** | `h(k) = k % m` | Simple range reduction; some key domains benefit from a prime `m`, but it cannot fix a poor hash |
| **Multiplication** | `h(k) = ⌊m × (k × A mod 1)⌋` | `A ≈ 0.618` (golden ratio); works for any `m` |
| **FNV-1a** | Bit-mixing: `h = (h ^ byte) × prime` | Fast, good distribution; Unkeyed; not a hostile-input defense |
| **MurmurHash3** | 128-bit mixing function | Non-cryptographic mixing family; verify the selected variant in a particular implementation |
| **SipHash** | Keyed hash designed for short inputs | Makes chosen-collision attacks harder; still apply input and work limits |

```typescript
// FNV-style 32-bit mixer over UTF-16 code units, for this string-key tutorial.
// Byte-defined FNV-1a instead hashes an explicitly chosen byte encoding.
function fnv1a(key: string): number {
  let h = 0x811c9dc5; // FNV offset basis
  for (let i = 0; i < key.length; i++) {
    h ^= key.charCodeAt(i);
    h = Math.imul(h, 0x01000193); // FNV prime
  }
  return h >>> 0; // unsigned 32-bit
}

// Map to array index
function indexFor(key: string, capacity: number): number {
  return fnv1a(key) % capacity;
}
```

**Why not SHA-256 for every table?** A cryptographic hash provides security properties beyond distributing buckets, at a workload-dependent cost. MD5 has broken collision resistance and should not be chosen for a security guarantee. General cryptographic hashes are not deliberately slow password hashes. Untrusted keys also require a threat model: deliberately chosen collisions can force many comparisons, a **hash-flooding denial of service**. Keyed hashes make predictable collisions harder; input/work limits still matter. Hash tables need *fast* and *uniform*: the tutorial mixer makes one xor+multiply pass over the string code units, SHA-256 performs compression rounds and message scheduling for each block. Benchmark before making a cost claim; the tutorial mixer illustrates bucketing and makes no security guarantee.

---

The hash function only chooses where to look; it does not prove that the key is there. Collision strategies decide where competing entries live, and the load policy decides when to allocate a larger table. The next sections compare those choices.

## When keys collide, storage strategy matters

### Strategy 1: Separate Chaining

Each bucket holds a small container of entries that hash to that index. The diagram uses links; the teaching implementation uses an array. Run the implementations as separate TypeScript examples. They deliberately accept only string keys with strict equality, not arbitrary JavaScript `Map` keys or adversarial traffic. Hashing costs O(key length); the usual constant-time claim assumes bounded-cost keys.

For the diagram's illustrative hashes, setting carol scans alice, then appends carol. Setting carol again updates its value rather than adding another entry. Deleting alice removes only its pair: the bucket still contains carol. Resizing must recalculate each bucket because `hash % capacity` changes when capacity changes.

```text
After inserting: alice(3), bob(7), carol(3), dave(3)

Index 0: [ ]
Index 1: [ ]
Index 2: [ ]
Index 3: [(alice,42)] → [(carol,99)] → [(dave,5)]   ← chain of 3
Index 4: [ ]
Index 5: [ ]
Index 6: [ ]
Index 7: [(bob,17)]
```

```typescript
class ChainingHashMap<K extends string, V> {
  private buckets: Array<Array<[K, V]>>;
  private size = 0;
  private capacity: number;
  private loadFactor: number;

  constructor(capacity = 16, loadFactor = 0.75) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new RangeError('Invalid capacity');
    if (!Number.isFinite(loadFactor) || loadFactor <= 0) throw new RangeError('Invalid load');
    this.capacity = capacity;
    this.loadFactor = loadFactor;
    this.buckets = Array.from({ length: capacity }, () => []);
  }

  private hash(key: K): number {
    const str = String(key);
    let h = 0x811c9dc5;
    for (let i = 0; i < str.length; i++) {
      h ^= str.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    return (h >>> 0) % this.capacity;
  }

  set(key: K, value: V): void {
    if (this.size / this.capacity > this.loadFactor) {
      this.resize(this.capacity * 2);
    }
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    const existing = bucket.find(([k]) => k === key);
    if (existing) {
      existing[1] = value; // update
    } else {
      bucket.push([key, value]);
      this.size++;
    }
  }

  get(key: K): V | undefined {
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    const pair = bucket.find(([k]) => k === key);
    return pair?.[1];
  }

  delete(key: K): boolean {
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    this.buckets[idx] = bucket.filter(([k]) => k !== key);
    if (bucket.length !== this.buckets[idx].length) {
      this.size--;
      return true;
    }
    return false;
  }

  private resize(newCapacity: number): void {
    const old = this.buckets;
    this.capacity = newCapacity;
    this.buckets = Array.from({ length: newCapacity }, () => []);
    this.size = 0;
    for (const bucket of old) {
      for (const [k, v] of bucket) {
        this.set(k, v);
      }
    }
  }
}
```

**Performance with chaining:**

| Operation | Average | Worst case (all collide) |
| ----------- | --------- | -------------------------- |
| Insert | O(1) | O(n) |
| Lookup | O(1) | O(n) |
| Delete | O(1) | O(n) |

**When chains grow long, Java 8+ converts them to balanced trees** (red-black tree) subject to bin size and table-capacity conditions. Tree bins can improve collisions, but arbitrary incomparable keys still require careful worst-case analysis; this is not a universal bound for every key type. This is the "treeification" optimization.

### Strategy 2: Open Addressing

All entries live in the array itself. Lookup must follow the same probe sequence as insertion. Deletion therefore leaves a **tombstone**, a marker meaning “continue searching”, instead of an empty slot meaning “this key was never inserted beyond here”.

Suppose alice is at 3 and carol at 4. After deleting alice, lookup for carol crosses the tombstone at 3 and finds 4. Updating carol must also cross it; inserting immediately at the tombstone would leave two copies of carol. The implementation remembers the first tombstone but checks for an existing key before reusing it. Tombstones can still make unsuccessful searches expensive; a production table also tracks occupied/deleted load and compacts on churn.

```text
Linear probing — hash("carol") = 3, slot 3 occupied:

  Probe: slot 3 (taken) → slot 4 (empty!) → insert carol at 4

Index:  0    1    2    3         4         5    6    7
      [ null, null, null, (alice,42), (carol,99), null, null, (bob,17) ]
```

```typescript
const DELETED = Symbol('DELETED');
class OpenAddressingHashMap<K extends string, V> {
  private keys: (K | typeof DELETED | null)[];
  private values: (V | null)[];
  private size = 0;
  private capacity: number;

  constructor(capacity = 16) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new RangeError('Invalid capacity');
    this.capacity = capacity;
    this.keys = new Array(capacity).fill(null);
    this.values = new Array(capacity).fill(null);
  }

  private hash(key: K): number {
    const str = String(key);
    let h = 0x811c9dc5;
    for (let i = 0; i < str.length; i++) {
      h ^= str.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    return (h >>> 0) % this.capacity;
  }

  set(key: K, value: V): void {
    if (this.size >= this.capacity * 0.7) this.resize(this.capacity * 2);
    let idx = this.hash(key);
    let firstDeleted = -1;
    for (let i = 0; i < this.capacity; i++) {
      const stored = this.keys[idx];
      if (stored === key) {
        this.values[idx] = value;
        return;
      }
      if (stored === DELETED && firstDeleted === -1) firstDeleted = idx;
      if (stored === null) {
        const destination = firstDeleted === -1 ? idx : firstDeleted;
        this.keys[destination] = key;
        this.values[destination] = value;
        this.size++;
        return;
      }
      idx = (idx + 1) % this.capacity;
    }
    // A table full of tombstones can lack a never-used slot.
    if (firstDeleted !== -1) {
      this.keys[firstDeleted] = key;
      this.values[firstDeleted] = value;
      this.size++;
      return;
    }
    throw new Error('No insertion slot');
  }

  get(key: K): V | undefined {
    let idx = this.hash(key);
    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) return undefined;
      if (this.keys[idx] === key) return this.values[idx] as V;
      idx = (idx + 1) % this.capacity;
    }
    return undefined;
  }

  delete(key: K): boolean {
    let idx = this.hash(key);
    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) return false;
      if (this.keys[idx] === key) {
        this.keys[idx] = DELETED; // tombstone
        this.values[idx] = null;
        this.size--;
        return true;
      }
      idx = (idx + 1) % this.capacity;
    }
    return false;
  }

  private resize(newCapacity: number): void {
    const oldKeys = this.keys;
    const oldValues = this.values;
    this.capacity = newCapacity;
    this.keys = new Array(newCapacity).fill(null);
    this.values = new Array(newCapacity).fill(null);
    this.size = 0;
    for (let i = 0; i < oldKeys.length; i++) {
      if (oldKeys[i] !== null && oldKeys[i] !== DELETED) {
        this.set(oldKeys[i] as K, oldValues[i] as V);
      }
    }
  }
}
```

### Probing changes which empty slot can be found

**Linear probing** follows adjacent slots. Starting at 3 in an eight-slot array, it checks 3, 4, 5 and so on, wrapping at the end. A long occupied run attracts more entries to its end; this is **primary clustering**. **Quadratic probing** changes the distance on each probe: 3, 4, 7, 4, 3 for the simple square formula modulo eight. That trace repeats before reaching every slot, so the capacity/formula/load policy must guarantee enough reachable vacancies; “there is an empty slot somewhere” is insufficient.

**Double hashing** chooses a step from the key. Starting at 3 with step 3 visits 3, 6, 1, 4, 7, 2, 5, 0. A nonzero step coprime to the capacity visits the whole array; different keys can follow different paths. **Secondary clustering** means keys with the same initial hash still follow the same probe sequence, as with the simple quadratic rule.

**Robin Hood hashing** changes who owns an occupied slot. If an incoming entry has traveled one slot and the occupant is still at its ideal slot, swap them, then continue probing with the displaced entry. This redistributes probe distances, rather than eliminating collisions. The complete implementation below traces the swap and its lookup stopping rule.

### Probing Variants Compared

| Probe | Sequence | Pros | Cons |
| -------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Linear** | `h+1, h+2, h+3, ...` | Simple, cache-friendly | **Primary clustering** — long runs of occupied slots grow self-reinforcing |
| **Quadratic** | `h+1², h+2², h+3², ...` | Breaks primary clustering | **Secondary clustering** — same hash → same probe sequence |
| **Double** | `h₁+k·h₂(key)` | Reduces primary and secondary clustering when the second hash varies | Two hash computations; `h₂` must be nonzero and coprime to the table capacity to visit every slot |
| **Robin Hood** | Linear probe, but swap if current entry has shorter probe distance | Compresses *variance* — probe distances become less uneven; occupied clusters can remain | More complex; still suffers clustering at high load |

```text
CLUSTERING VISUALIZED (linear probing, 50% load):

Linear probing — clustered:
[ ████░░░░████████░░░░░░░░████░░░░ ]
  ↑ long occupied run → new keys pile up here

Double hashing — uniform:
[ █░░░██░░█░░░███░░░░██░░█░░░██░░ ]
  ↑ keys scattered evenly
```

## Grow before collision work dominates

The **load factor** `α = n/m` (entries ÷ slots) determines performance:

For chaining, increasing load makes the average bucket longer; load can exceed one because a bucket holds multiple entries. For open addressing, load approaches one as the flat array fills, leaving fewer stopping points for unsuccessful searches and insertions. Clusters and tombstones make that cost worse. A bounded probe loop can report failure in a full table; a naïve “keep searching until empty” loop cannot terminate.

These are workload-dependent costs, not measurements performed by this chapter. Successful search, unsuccessful search and insertion must be measured separately. The 0.7 growth threshold in the teaching implementation is a policy choice, not a universal performance guarantee.

**Rehashing** = allocate a larger array (typically 2×), re-insert all entries:

```text
Before rehash (capacity=4, α=1.0):
Index: 0    1    2    3
      [ A    B    C    D ]

After rehash (capacity=8, α=0.5):
Index: 0    1    2    3    4    5    6    7
      [ A    _    C    _    B    _    _    D ]
         ↑                                  ↑
    rehashed to new positions based on h(key) % 8
```

**Amortized O(1) proof (aggregate method):**
- With doubling, the total entries moved by successive resizes form a geometric sum less than a constant multiple of `n`. Add the `n` ordinary insertions: total resize plus insertion work is O(n), assuming bounded expected hashing/collision work.
- Dividing that total by `n` gives O(1) amortized per insertion; this does not bound one operation’s latency.
- Geometric growth gives the amortized resize bound; exact doubling is not mandatory. Shrink at a substantially lower threshold than growth to avoid resize thrashing. Expected constant-time hashing/collision costs are a separate assumption from amortizing resizes.

## Separate JavaScript key rules from V8's implementation choices

### V8's `Map`: lookup and iteration need different paths

An ordered hash table separates bucket lookup from insertion-order storage. Conceptually, bucket chains point to entry rows, while iteration visits rows in insertion order. A deleted row must be skipped; a resize can rebuild lookup storage while preserving the order of surviving entries. Deleting and reinserting a key gives it a new position at the end.

The current V8 source describes ordered tables for `Map` and `Set`: bucket links find candidate entries, while entry storage preserves iteration order; deleted entries are tracked. That source gives the table two data-entry slots per bucket. These are V8 implementation details, not ECMAScript guarantees, and the internal layout can vary by size and revision. Object keys use identity semantics, so equal-looking objects remain different keys. A 2018 V8 hash-code article is useful historical background, but its storage offsets and benchmark results are not current tuning guidance.

### V8's Object (plain `{}`)

A hidden class (also called a V8 **Map**, distinct from the JavaScript collection) describes a shape shared by compatible objects. For a named property, it can identify a slot directly in the object or in a separate indexed property store. Overflow to that store does **not** by itself mean hash-table lookup. A dictionary representation stores per-object name metadata when dynamic modification makes the shared-shape approach less useful. Indexed elements are a separate store.

The following are possible storage arrangements, not three mandatory phases every object passes through:

```text
V8 Object representations (hidden classes / maps):

Arrangement 1: Fast mode (in-object properties)
┌───────────────────────────┐
│ Hidden Class (Map)        │  ← shared schema
│ Properties: [a, b, c]     │  ← fixed offsets, fast access
│ In-object slots (fixed)   │
└───────────────────────────┘

Arrangement 2: Overflow to backing store
┌───────────────────────────┐
│ Hidden Class (Map)        │
│ In-object slots: [a, b]   │
│ Backing Store (Array):    │  ← indexed fast-property storage
│   [c → value, d → value]  │
└───────────────────────────┘

Arrangement 3: Dictionary mode (dynamic changes can favor dictionary storage)
┌───────────────────────────┐
│ Name Dictionary           │  ← full hash table
│ Keys: [string → index]    │
│ Values: sparse array      │
└───────────────────────────┘
```

Repeated additions and deletions can make dictionary storage more suitable than a shared shape for some objects. Stable shapes may help hot property access, but this is an engine-specific optimization; profile the target workload before reshaping application data around it.

### Other runtimes make different trade-offs

Java `HashMap` starts with bucket chains and can convert crowded bins into balanced trees, subject to table-capacity and bin-size conditions. A tree orders entries so search can discard branches, but arbitrary incomparable keys complicate a universal logarithmic worst-case claim. Python's `dict` uses an open-addressed index plus entry storage; its perturbation rule changes the probe path. Its insertion-order contract does not mean it shares V8's collision strategy.

The primary implementations linked below are useful comparisons. Fixed hashes, growth multipliers, thresholds and physical layouts should be checked for the target runtime version rather than memorized as language guarantees.

## Apply the table to common lookup problems

### Design a HashMap (LC #706) — Interview Classic

Assume the exercise's nonnegative integer keys and values, with `-1` reserved for missing. Key 1 and key 1001 both select bucket 1; lookup compares their full keys to return the correct value. This fixed-capacity exercise map has no resize, so large collision buckets lose the usual expected constant-cost assumption.

```typescript
class MyHashMap {
  private buckets: Array<Array<[number, number]>>;
  private capacity = 1000;

  constructor() {
    this.buckets = Array.from({ length: this.capacity }, () => []);
  }

  private hash(key: number): number {
    return key % this.capacity;
  }

  put(key: number, value: number): void {
    const idx = this.hash(key);
    const bucket = this.buckets[idx];
    const pair = bucket.find(([k]) => k === key);
    if (pair) {
      pair[1] = value;
    } else {
      bucket.push([key, value]);
    }
  }

  get(key: number): number {
    const idx = this.hash(key);
    const pair = this.buckets[idx].find(([k]) => k === key);
    return pair ? pair[1] : -1;
  }

  remove(key: number): void {
    const idx = this.hash(key);
    this.buckets[idx] = this.buckets[idx].filter(([k]) => k !== key);
  }
}
```

### Two Sum (LC #1) — HashMap Pattern

For `[2, 7, 11]` and target 9, index 0 records value 2 after looking for 7. Index 1 looks for 2, finds index 0, and returns `[0, 1]`. Looking *before* insertion prevents reusing the current element as both addends. The input is ordinary finite exercise numbers; missing pairs return an empty array.

```typescript
function twoSum(nums: number[], target: number): number[] {
  const seen = new Map<number, number>(); // value → index
  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];
    if (seen.has(complement)) {
      return [seen.get(complement)!, i];
    }
    seen.set(nums[i], i);
  }
  return [];
}
// O(n) time, O(n) space — the hash table makes this possible
```

### Group Anagrams (LC #49) — Hash Map as Bucket

For lowercase ASCII exercise words, `eat` and `tea` both sort to `aet`, so they append to one bucket. The sorted string is a **canonical form**, a representation shared by equivalent inputs. This code compares UTF-16 code units; human-language equivalence may require normalization and a different character policy. It does not solve arbitrary Unicode anagram rules.

```typescript
function groupAnagrams(strs: string[]): string[][] {
  const groups = new Map<string, string[]>();
  for (const s of strs) {
    const key = s.split('').sort().join(''); // canonical form
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key)!.push(s);
  }
  return [...groups.values()];
}
// O(n × k log k) where k = max string length
```

### LRU uses an order policy above the hash table

A least-recently-used (LRU) cache combines key lookup with recency order. In JavaScript `Map`, delete/reinsert moves a hit to the end; updating an existing value alone does not. For capacity two, putting A/B, reading A and putting C evicts B. The complete capacity-validated implementation and trace belong in [Map and Set](10.1.4.02-map-set-weakmap-weakset.md); hashing alone cannot decide which entry to evict.

### Implement Robin Hood Hashing

Imagine entries with ideal slots 3 and 4 currently occupying 3 and 4. A new entry whose ideal slot is 3 reaches slot 4 with distance 1, displaces its distance-0 occupant, then carries that displaced key/value onward to slot 5. Every swap must carry the key, value and stored hash together.

Lookup can stop when its own distance exceeds the occupant's distance: insertion would have placed the searched key earlier by stealing that slot. This relies on the insertion invariant. The implementation supports updates and growth but intentionally omits deletion; simply setting a deleted slot to null would break later lookups. Deletion requires backward shifting or a compatible tombstone algorithm.

```typescript
class RobinHoodHashMap<K extends string, V> {
  private keys: (K | null)[];
  private values: (V | null)[];
  private hashes: number[];
  private size = 0;
  private capacity: number;

  constructor(capacity = 16) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new RangeError('Invalid capacity');
    this.capacity = capacity;
    this.keys = new Array(capacity).fill(null);
    this.values = new Array(capacity).fill(null);
    this.hashes = new Array(capacity).fill(0);
  }

  private probeDistance(key: K, idx: number): number {
    const ideal = this.hash(key) % this.capacity;
    return (idx - ideal + this.capacity) % this.capacity;
  }

  set(key: K, value: V): void {
    if (this.size >= this.capacity * 0.7) this.resize(this.capacity * 2);
    let idx = this.hash(key) % this.capacity;
    let dist = 0;
    let insertingKey = key;
    let insertingValue = value;
    let insertingHash = this.hash(key);

    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) {
        this.keys[idx] = insertingKey;
        this.values[idx] = insertingValue;
        this.hashes[idx] = insertingHash;
        this.size++;
        return;
      }
      if (this.keys[idx] === insertingKey) {
        this.values[idx] = insertingValue;
        return;
      }
      // Robin Hood: if existing entry has shorter probe distance, swap
      const existingDist = this.probeDistance(this.keys[idx]!, idx);
      if (dist > existingDist) {
        // Steal this slot
        [insertingKey, this.keys[idx]] = [this.keys[idx]!, insertingKey];
        [insertingValue, this.values[idx]] = [this.values[idx]!, insertingValue];
        [insertingHash, this.hashes[idx]] = [this.hashes[idx], insertingHash];
        dist = existingDist;
      }
      idx = (idx + 1) % this.capacity;
      dist++;
    }
  }

  get(key: K): V | undefined {
    const h = this.hash(key);
    let idx = h % this.capacity;
    for (let i = 0; i < this.capacity; i++) {
      if (this.keys[idx] === null) return undefined;
      if (this.keys[idx] === key && this.hashes[idx] === h) return this.values[idx] as V;
      if (this.probeDistance(this.keys[idx]!, idx) < i) return undefined; // early exit
      idx = (idx + 1) % this.capacity;
    }
    return undefined;
  }

  private hash(key: K): number {
    const str = String(key);
    let h = 0x811c9dc5;
    for (let i = 0; i < str.length; i++) {
      h ^= str.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    return h >>> 0;
  }

  private resize(newCap: number): void {
    const oldK = this.keys, oldV = this.values;
    this.capacity = newCap;
    this.keys = new Array(newCap).fill(null);
    this.values = new Array(newCap).fill(null);
    this.hashes = new Array(newCap).fill(0);
    this.size = 0;
    for (let i = 0; i < oldK.length; i++) {
      if (oldK[i] !== null) this.set(oldK[i] as K, oldV[i] as V);
    }
  }
}
```

## Where hash-table choices appear in applications

| Use case | Hash table role | Key insight |
| ---------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **JS `Object` / `Map`** | Property access uses shape metadata and, for some objects, a name dictionary | Fast objects can resolve `obj.foo` through shape metadata; dictionary-mode objects use dictionary lookup |
| **Database indexes** | B-tree is primary, but hash indexes for equality-only lookups | PostgreSQL `hash` access method answers `=` queries |
| **Redis hashes** | Field/value records with an encoding chosen by size/configuration | Small records can use compact encoding; the API name does not require a hash table |
| **CPython `dict` and `set`** | Key/value and membership lookup | Their hash-table layout is a CPython implementation detail; `**kwargs` exposes a keyword mapping, not a promise about its storage representation. |
| **Compiler symbol tables** | Variable/function name → type info | Fast lookup is critical for compile speed |
| **DNS resolver cache** | A possible name/record cache implementation | Actual data structure, TTL and eviction are resolver-specific |
| **Distributed caches** | A local lookup structure plus a separate partitioning policy | A client may use consistent hashing; Redis Cluster uses hash slots |
| **Webhook signature verification** | `Map<webhookId, secret>` for HMAC lookup | Efficient key lookup; signature validation still needs cryptographic comparison and replay protection |

## Choose and measure for the real workload

The average O(1) claim hides key length, collision distribution, memory layout and occasional resize cost. Choose from the key semantics and operation mix, then measure the actual runtime:

| Decision | What changes the choice |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dynamic keys and object identity** | `Map` preserves object-key identity and avoids inherited property-name collisions. A plain object converts non-symbol keys to property keys; separately created `{ id: 1 }` objects are not equal Map keys. |
| **Iteration order** | `Map` preserves insertion order. Ordinary object property order is defined but treats integer-index keys specially: they are enumerated first in ascending order, followed by other strings in insertion order. |
| **Collision strategy** | Chaining can support load factors above one but traverses bucket entries. Open addressing keeps entries in a flat array, which can improve locality, but needs empty slots and must account for tombstones. Thresholds depend on the strategy and workload. |
| **Hash quality and hostile input** | A power-of-two capacity makes low-bit mixing important; a prime capacity cannot rescue a poor hash. Use keyed hashing and input/work limits when users can choose keys. A fast unkeyed tutorial mixer is not a denial-of-service defense. |
| **Latency-sensitive inserts** | Rehashing can move every entry in O(n), even when inserts are amortized O(1) across a sequence. Pre-size where the API supports it; JavaScript `Map` has no public initial-capacity parameter. |
| **Costly keys or large values** | Hashing a long string still costs O(key length). Copying large entries can dominate; storing references trades that copy for indirection. Measure the representation in the target runtime. |

The ECMAScript collection contract requires average access to be sublinear in collection size, not a particular O(1) table algorithm. V8 and other engines can change their internal layout. Record probes and latency separately for successful lookups, misses, inserts, resize events and delete/reinsert churn; test realistic key lengths and distributions, including adversarial cases when relevant.

## Summary

- A hash table maps a key to a hash code, reduces it to a candidate slot, then resolves collisions by key equality. Expected lookup cost and amortized resize cost rely on separate assumptions.
- **Collisions are inevitable** — separate chaining (linked lists/trees per bucket) and open addressing (probing for empty slots) are the two resolution families.
- **Load policy** controls collision cost and resizing; choose thresholds for the implementation rather than treating example numbers as universal rules.
- **V8 implementation details can change.** Its current ordered `Map`/`Set` tables keep lookup buckets and ordered entries; JavaScript guarantees observable collection behavior, not this physical layout. Plain-object shapes and dictionary storage are a separate optimization path.
- **Robin Hood hashing** reduces probe-distance variance by swapping entries to equalize probe distances.
- **For interviews**: implement with chaining (simpler), mention load factor + rehashing, state your hash function choice.

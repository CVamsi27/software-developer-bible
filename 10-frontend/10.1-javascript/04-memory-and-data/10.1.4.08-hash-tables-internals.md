# Hash Tables and Hash Maps

A lookup table receives a key such as `alice`, but its backing array needs a numeric position. Hashing chooses a candidate position; another key may choose the same one. Follow the lookup to see how a table resolves that collision, when it grows, and what the familiar average O(1) claim assumes.

## Definition

A **hash table** stores key–value entries in indexed storage. A **hash function** maps a key to an integer hash code; range reduction maps that code to a bucket or slot. If multiple keys select the same location, the table resolves the collision and compares keys for equality.

> **Textbook Definition:** A hash table is a data structure that maps keys to candidate storage positions by hashing, then uses a collision-resolution strategy and key equality to locate entries. Its expected operation cost depends on key cost, hash distribution, load, and the collision strategy.

## First Principles

1. **A key needs a candidate location.** The table hashes the key, then reduces the result to one of its current buckets or slots.
2. **A candidate is not proof of a match.** Distinct keys can have the same hash or slot. The table must compare the stored key using the collection's equality rule.
3. **Crowding increases work.** The load factor, entries divided by slots, helps describe how much collision work to expect. A growth policy adds storage and rehashes entries before operations become too costly.
4. **The complexity claim has assumptions.** Expected lookup is often described as O(1) when hashing is bounded and collisions stay controlled. A pathological collision set can make lookup O(n); resizing can make one insert O(n) even when inserts are amortized O(1) over time.

## Follow one key through a collision

Assume an eight-slot table and illustrative range reduction `hash(key) % 8`:

```text
hash("alice") % 8 = 3    store (alice, 42) at slot 3
hash("carol") % 8 = 3    collision: both keys select slot 3
```

A lookup for `carol` reaches slot 3, compares `alice` with `carol`, then follows the collision strategy until it finds the matching key. A hash match alone never establishes equality. If two keys compare equal, the table must send them to a compatible lookup path; otherwise it could store duplicates that the equality rule says are the same key.

Hashing a string takes time proportional to its length, so “constant time” treats key cost as bounded. For long strings, the hash computation itself can dominate even when there are few collisions.

## Resolve collisions

Two common strategies arrange entries differently:

| Strategy | Where entries live | What lookup does | Deletion concern |
| --------------------- | -------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------- |
| **Separate chaining** | Each bucket holds its own entries | Search the selected bucket and compare keys | Remove the matching entry from that bucket |
| **Open addressing** | Entries occupy slots in the main array | Follow a probe sequence until a match or a valid stopping point | Preserve the probe path, often with a tombstone |

With chaining, two colliding keys can remain in one bucket. With open addressing, a collision sends the new key to another slot. Linear probing checks adjacent slots; long occupied runs can attract more entries and make later lookups slower. Other probe sequences change clustering behavior but still depend on a valid capacity and termination policy.

A tombstone marks a deleted slot as “continue searching.” Replacing it with a truly empty slot could make lookup stop before it reaches a key inserted later in the same probe sequence. An insertion that reuses a tombstone must first check the rest of the path for an existing copy of the key. Tables that see heavy deletion may need to compact or rehash to remove accumulated tombstones.

Some designs, such as Robin Hood hashing, redistribute probe distances by displacing entries. They change the distribution of lookup work, not the need for equality checks or a deletion invariant. The exact design is an implementation choice; interviews usually need the collision invariant and cost trade-off, not a memorized production implementation.

## Grow without hiding the latency spike

The load factor is `α = entries / slots`. Chaining can have a load factor above one because buckets can hold multiple entries. Open-addressed tables need vacant slots, so their growth policy must preserve room for probing. A threshold is a policy, not a universal constant; the useful value depends on the implementation and workload.

When a table grows, it allocates more slots and reinserts the entries because range reduction now uses a different capacity. That rehash costs O(n). With geometric growth, the total entries moved across successive resizes is a geometric sum, so the resize work is amortized O(1) per insertion. Amortized cost describes a sequence; one resize can still create an O(n) latency spike.

| Operation | Typical assumption | Worst case |
| ------------------------------ | ----------------------------------------------------------------- | ----------------------------- |
| Lookup, insert, delete | Expected O(1) when hashes distribute well and key work is bounded | O(n) under severe collisions |
| Resize | Not paid on every operation | O(n) for that resize |
| Insert across geometric growth | Amortized O(1), given controlled collision work | Individual insert can be O(n) |

Amortizing resize does not fix poor distribution. Measure successful lookups, misses, inserts, and delete/reinsert churn separately; include realistic key lengths and load. If attackers control keys and the implementation is yours, consider a keyed hash and bound input and total work. A fast unkeyed tutorial hash is not a denial-of-service defense.

## Apply the model to JavaScript collections

`Map` and `Set` use SameValueZero for key/member equality: `NaN` matches itself, positive and negative zero are equivalent, and objects match by identity. The ECMAScript requirement is average access time sublinear in collection size. It does not promise a hash table, exact O(1) behavior, a collision strategy, or a particular memory layout.

```js
const first = { id: 1 };
const second = { id: 1 };
const users = new Map([[first, 'Alice']]);

users.get(first);  // 'Alice'
users.get(second); // undefined: same fields, different identity
```

A plain object has a different key contract: property keys are strings or symbols. Other values are converted to property keys, so numeric `1` and string `'1'` address the same property. Objects are generally converted to strings, which is why unrelated objects should not be used as identity keys in a record. Use an object for a fixed set of fields; use `Map` when the application needs arbitrary keys, direct membership, or collection iteration. Ordinary object enumeration also treats integer-index keys specially, so use `Map` when insertion order across arbitrary keys is part of the contract.

V8 may use different internal structures for `Map`, `Set`, and ordinary object properties. Hidden classes (V8 Maps) describe compatible object shapes; that optimization is separate from the JavaScript `Map` collection. These internals change between engine versions and do not alter the language contract. Profile the deployed runtime before changing object shapes or collection choices for speed.

## Recognize the pattern in an interview

For Two Sum, store each number's index as you scan. Before inserting the current number, look up its complement; this prevents using the same array element twice. The map makes the usual solution expected O(n) time and O(n) extra space, subject to the collection's key and complexity contract. The full exercise belongs in the [hash-map coding-pattern drill](../../../70-interview-toolkit/70.2-coding-patterns/INDEX.md).

The senior-level explanation is the assumption behind the cost: hash the key, resolve collisions with equality, resize as occupancy grows, and name the worst-case and latency boundary. In production, prefer the built-in `Map` unless a measured workload and explicit key contract justify another structure.

## Summary

A hash table maps a key to a candidate location, resolves collisions, and checks equality before returning an entry. Load policy and geometric growth control average work but do not remove worst-case collisions or individual resize spikes. JavaScript specifies collection semantics and average sublinear access; the runtime chooses its internal representation. Choose collections by key and ordering requirements, then measure the actual workload.

# Equality & Type Coercion

## Definition

**Type coercion** is a conversion JavaScript performs because an operation requires a different kind of value, sometimes first converting an object to a primitive. Common triggers include: comparison operators (`==`, `<`, `>`), arithmetic operators (`+`, `-`, `*`…), and conditional contexts (`if`, `&&`, ternaries). The two equality operators are: **strict** (`===` — same type and same value, no conversion) and **loose** (`==` — applies type-dependent comparison and conversion rules).

> **Textbook Definition:** Coercion applies language-defined conversions when an operation requires a different value representation. Equality algorithms differ in whether they permit conversion and in their handling of numeric edge cases and object identity.

## First Principles

Equality in JS is layered because each layer answers a different question:

1. **Comparing without conversion still needs a rule.** Objects and symbols compare by identity; other primitives follow rules for their value types. `Object.is` and `===` differ in their treatment of `NaN` and positive/negative zero.
2. **Loose equality performs specified conversions.** `==` can convert operands before comparing. Depending on the operands, this can include `ToPrimitive`, converting an object to a primitive, or `ToNumber`, converting a value to a number. Prefer `===` and explicit conversion when these implicit steps would obscure the intended comparison.
3. **A condition asks a different question.** `if (x)` checks whether `x` is **truthy**, treated as true in a Boolean context. Thus `[]` is truthy while `[] == false` is true: the condition and equality operator apply different rules.
4. **Collection keys need a consistent equality rule.** Map and Set use **SameValueZero**. It keeps object identity, treats `NaN` as equal to itself and treats positive and negative zero as equal. Callers cannot switch these collections to loose equality (→ 10.1.4.02).


## Why It Matters

Senior engineers deliberately choose `===` by default and reach for `==` only when its coercion is the feature (`x == null` catches both `null` and `undefined`). They can explain why `0.1 + 0.2 !== 0.3` (IEEE-754, not coercion), why `[10] == 10` is `true` (ToPrimitive), and why `if ([])` is truthy while `[] == false` is also `true` (different algorithms: boolean truthiness vs. ToNumber). That derivation ability — not memorization of the coercion table — is the senior signal.

## How It Works

### Follow the rules for the operand types

This sketch covers ordinary Number/string/Boolean/object cases. Each conversion feeds the resulting operands back into comparison; it is not a rule to blindly convert both sides to numbers. Two objects compare by identity without calling conversion hooks. BigInt rules and the legacy `document.all` exception are qualified below.

```text
a == b  →
┌────────────────────────────────────────────────────────────┐
│ same type?  ──yes──►  compare values (=== semantics)       │
│     │no                                                    │
│ null == undefined ? ──yes──► true (and ONLY each other)    │
│     │no                                                    │
│ number vs string? ──► ToNumber(string), compare as numbers │
│     │                                                      │
│ boolean involved? ──► ToNumber(boolean), restart           │
│     │                                                      │
│ object vs primitive? ──► ToPrimitive(object), restart      │
└────────────────────────────────────────────────────────────┘
```

### Converting objects, numbers and conditions

`ToPrimitive` is the specification operation that asks an object for a primitive representation. Its **hint** tells the object whether the caller prefers a string or number; `default` leaves the policy to the object. A supplied `Symbol.toPrimitive` must return a primitive or conversion throws. Without that hook, ordinary number/default conversion tries `valueOf` and then `toString`, while the string hint reverses that order. Dates customize the default behavior.

The following deliberately surprising expressions are JavaScript examples run separately in a console; TypeScript may reject mixed-type arithmetic before execution. With `obj == 42`, the hook receives the default hint and returns 42, reducing the comparison to equal Numbers. With a template string it receives the string hint and returns `obj` instead.

```javascript
// ToPrimitive(object, hint): objects become primitives via
//   1. Symbol.toPrimitive(hint)   — highest priority
//   2. valueOf()                  — for "number"/"default" hints
//   String hint reverses the ordinary fallback order: toString(), then valueOf().
const obj = {
  [Symbol.toPrimitive](hint) {
    return hint === 'string' ? 'obj' : 42;
  },
};
`${obj}`;      // "obj"   (string hint)
obj + 1;       // 43      (default/number hint)
obj == 42;     // true    (ToPrimitive → 42 → same type)

// ToNumber: the table interviewers actually test
Number(null);        // 0
Number(undefined);   // NaN
Number(true);        // 1
Number('');          // 0
Number('  42  ');    // 42  (trims whitespace)
Number('42px');      // NaN
Number([]);          // 0    ([] → '' → 0)
Number([7]);         // 7    ([7] → '7' → 7)
Number([1, 2]);      // NaN  ('1,2' is not numeric)

// Truthiness (boolean context) is its OWN rule — NOT ToNumber:
Boolean([]);         // true   (ordinary objects are truthy, even empty; document.all is a legacy exception)
Boolean('');         // false
Boolean(0);          // false
Boolean('false');    // true: a nonempty string, not a parsed Boolean
// So:  if ([])  → runs      but   [] == false → true
// Different algorithms produce that apparent contradiction.
```

### The `+` operator: concatenation or addition?

```javascript
// If EITHER operand is a string after ToPrimitive → concatenate
1 + '2';        // "12"
'5' + 3;        // "53"
[1, 2] + [3];   // "1,23"   (both → strings)
{} + 1;         // 1 or "[object Object]1" depending on context:
                // as a statement, {} is parsed as an empty BLOCK,
                // so it's +1 → 1. Inside parens: ({}) + 1 → "[object Object]1"

// Everything else → numeric
'6' - 1;        // 5     (no string concatenation for -)
true + true;    // 2
null + 1;       // 1     (null → 0)
undefined + 1;  // NaN
```

## Code Examples

### The classics, derived (not memorized)

```javascript
// [] == ![]  →  true. Why?
// 1. ![] → false            (ordinary objects are truthy)
// 2. [] == false            (boolean on one side → ToNumber)
// 3. [] → '' → 0, false → 0
// 4. 0 == 0 → true

// null == undefined → true. Browser document.all is a legacy exceptional case.
null == 0;          // false  (null only loosely equals undefined)
null >= 0;          // true   (RELATIONAL operators: null → 0)
null > 0;           // false  (0 > 0 is false)
// The null == 0 vs null >= 0 split is a favorite senior probe.

// '5' == 5 → true (string → number), but '5' === 5 → false

// NaN never equals anything, including itself
NaN === NaN;        // false
Object.is(NaN, NaN); // true  (Object.is: SameValue, fixes both NaN and -0)
Object.is(0, -0);   // false  (=== says true)

// -0 vs 0: === and == say equal, Object.is distinguishes,
// Math.sign(-0) preserves negative zero; choose equality by the required numeric semantics.
```

### A nullish comparison deliberately accepts two types

```typescript
// Idiomatic: catch both null and undefined in one check
function normalize(value: string | null | undefined): string {
  if (value == null) return ''; // == null is the FEATURE: covers null + undefined
  return value.trim();
}

// Everything else: === with explicit conversion where needed
function coerceInt(input: unknown): number {
  if (typeof input !== 'number' && typeof input !== 'string') return 0;
  if (typeof input === 'string' && input.trim() === '') return 0;
  const n = Number(input);
  return Number.isFinite(n) ? Math.trunc(n) : 0;
}
```

This fallback conversion intentionally maps invalid input to zero; business validation may need to report an error instead. `Number()` is explicit but not validation by itself: blank strings become zero, infinity stays infinite, Symbols throw, and object conversion can execute user code.

## Real-World Use Cases

### 1. Form input arithmetic

```javascript
// HTML input.value is a string; valueAsNumber and typed form models have other contracts.
const qty = form.qty.value;        // "3"
const inStock = 1999;
let total = qty + inStock;           // "31999"  ← string concat, real production bug
total = Number(qty) + inStock;       // 2002     ← explicit conversion
```

### 2. Optional params and defaults

```typescript
// || vs ?? — the coercion decision with real consequences
function badDefault(v: number | undefined) {
  return v || 50;   // 0 becomes 50  ← probably wrong
}

function goodDefault(v: number | undefined) {
  return v ?? 50;   // only undefined/null become 50 ← correct
}
```

### 3. Sorting mixed values

```javascript
// Default sort converts defined values to strings and compares code units.
// It does not call < on each original pair.
[10, 9, '8'].sort();               // [10, '8', 9]  (all → strings, then lexicographic)
[10, 9, 8].sort((a, b) => a - b);  // [8, 9, 10]    (numeric comparator — no coercion surprises)
```

## Common Mistakes

### 1. `||` where `??` is meant

```javascript
// BAD: valid falsy values (0, '', false) get replaced
const bad = userSetting || 3;    // 0 → 3

// GOOD: only nullish falls back
const good = userSetting ?? 3;
```

### 2. Assuming `Number()` and `parseInt()` agree

```javascript
Number('42px');     // NaN
parseInt('42px');   // 42   (leading-numeric parsing)
Number('');         // 0
parseInt('', 10);   // NaN
// Choose by intent: Number for whole-string conversion, parseInt for leading digits.
// Always pass the radix to parseInt.
```

### 3. Truthiness checks on collections

```javascript
// BAD: an empty array/object is truthy
if (results) render(results);        // runs with [] — is that "no results"?

// GOOD: check emptiness explicitly
if (Array.isArray(results) && results.length > 0) render(results);
```

### 4. Mixing `-` with string operands expecting concat

```javascript
// BAD: expecting subtraction to behave like +
'a' - 1;   // NaN (not an error, not 'a1')

// GOOD: validate before arithmetic, or Number() explicitly
```

## Best Practices

1. **Default to `===`/`!==`.** `x == null` and `x != null` deliberately combine nullish checks. Other loose comparisons need an explicit operand contract and a reason to accept their conversion rules.
2. **Prefer `??` over `||` for defaults** — reserve `||` for boolean-coalescing where falsy values are genuinely invalid.
3. **Parse and validate at boundaries** — form input, URL params, `localStorage`, API payloads. Explicit conversion makes the operation visible; it still needs a type/range policy. `Boolean('false')` is true, so parse textual Boolean flags by the allowed spellings.
4. **Use `Object.is` in comparisons where `-0`/`NaN` matter** (polyfill-grade equality, test assertions).
5. **Sort with comparators** — never rely on default lexicographic sort for numbers.
6. **Make library input contracts explicit** — accept the intended types and define conversion/error behavior. Ordinary conditions still use truthiness; the goal is predictable semantics, not eliminating every language conversion.

## Performance Considerations

- Primitive conversion is often small work, but object hooks can execute arbitrary code and large strings require parsing. Correctness comes first; measure conversion costs in the actual hot path.
- `Number(x)` vs `+x` vs `x | 0`: `|0` truncates to 32-bit and is a micro-optimization only — `Math.trunc` communicates intent and handles values beyond 32-bit.
- Stable input types can help engine specialization, but mixed values do not imply a universal deoptimization rule. Profile the target engine and workload before changing an input contract for speed.

BigInt represents integers separately from Number. `1n == '1'` parses the string as an integer and returns true; `1n == '1.5'` returns false. For Number/BigInt equality, the numeric values must be equal and the Number finite; `1n == 1` is true while `1n == 1.5` is false. Arithmetic has a different boundary: `1n + 1` throws because the numeric operands have different types. Equality does not authorize mixing their arithmetic. An object may run conversion code through `Symbol.toPrimitive`; conversions can have side effects or throw. Boolean contexts do not use those object-to-primitive hooks.

## Summary

1. `===` compares as-is; `==` coerces via a small, derivable algorithm (null/undefined pair, ToNumber, ToPrimitive).
2. Three conversion rules: ToPrimitive (hook or hint-ordered ordinary methods), ToNumber, and boolean truthiness — and they disagree (`[]` is truthy but `[] == false`).
3. `+` concatenates if either primitive result is a string; `-` is always numeric.
4. `??` guards only `null`/`undefined`; `||` guards all falsy — the choice is a correctness decision, not style.
5. Nullish loose comparison deliberately accepts two values; prefer explicit parsing and strict comparison when a different conversion policy is required.
6. `Object.is` distinguishes `NaN` and `-0`; `===` does not.

# Equality & Type Coercion

## Definition

**Type coercion** is the automatic conversion of a value from one primitive type to another. JavaScript does it in three places: comparison operators (`==`, `<`, `>`), arithmetic operators (`+`, `-`, `*`…), and conditional contexts (`if`, `&&`, ternaries). The two equality operators are: **strict** (`===` — same type and same value, no conversion) and **loose** (`==` — same value *after* coercion).

## First Principles

Equality in JS is layered because each layer answers a different question:

1. **Identity is the primitive.** "Is it the *same thing*?" (identity for objects and symbols, type-specific value semantics for other primitives) still requires a defined comparison rule — `Object.is`/`===` sit here, differing only in how they treat the two pathological numbers, `NaN` and ±0.
2. **Loose equality applies a conditional conversion policy.** `==` answers "same thing *after* making types agree" — a rule-based conversion chain (ToPrimitive → ToNumber). Its infamy comes not from being wrong but from the chain being long enough that few hold it in their heads; the senior move is knowing the chain exists and refusing to enter it (`===` + explicit conversion).
3. **Truthiness is a third, separate question.** `if (x)` coerces to boolean — which is why `[]` is truthy while `[] == false` is true: different operators, different chains, no contradiction.
4. **Collections need a stable key-equivalence rule.** Map/Set use SameValueZero — you can't configure "loose" keys, because identity-preserving keys is exactly what makes them honest (→ 10.1.4.02).


## Why It Matters

Senior engineers deliberately choose `===` by default and reach for `==` only when its coercion is the feature (`x == null` catches both `null` and `undefined`). They can explain why `0.1 + 0.2 !== 0.3` (IEEE-754, not coercion), why `[10] == 10` is `true` (ToPrimitive), and why `if ([])` is truthy while `[] == false` is also `true` (different algorithms: boolean truthiness vs. ToNumber). That derivation ability — not memorization of the coercion table — is the senior signal.

## How It Works

### The one flowchart behind every `==` question

```text
a == b  →
┌────────────────────────────────────────────────────────────┐
│ same type?  ──yes──►  compare values (=== semantics)       │
│     │no                                                    │
│ null == undefined ? ──yes──► true (and ONLY each other)    │
│     │no                                                    │
│ number vs string? ──► ToNumber(string), compare as numbers │
│     │                                                      │
│ boolean involved? ──► ToNumber(boolean), restart           │
│     │                                                      │
│ object vs primitive? ──► ToPrimitive(object), restart      │
└────────────────────────────────────────────────────────────┘
```

### The two conversion engines

```typescript
// ToPrimitive(object, hint): objects become primitives via
//   1. Symbol.toPrimitive(hint)   — highest priority
//   2. valueOf()                  — for "number"/"default" hints
//   3. toString()                 — for "string" hint (and valueOf fallback)
const obj = {
  [Symbol.toPrimitive](hint: string) {
    return hint === 'string' ? 'obj' : 42;
  },
};
`${obj}`;      // "obj"   (string hint)
obj + 1;       // 43      (default/number hint)
obj == 42;     // true    (ToPrimitive → 42 → same type)

// ToNumber: the table interviewers actually test
Number(null);        // 0
Number(undefined);   // NaN
Number(true);        // 1
Number('');          // 0
Number('  42  ');    // 42  (trims whitespace)
Number('42px');      // NaN
Number([]);          // 0    ([] → '' → 0)
Number([7]);         // 7    ([7] → '7' → 7)
Number([1, 2]);      // NaN  ('1,2' is not numeric)

// Truthiness (boolean context) is its OWN rule — NOT ToNumber:
Boolean([]);         // true   (every object is truthy, even empty)
Boolean('');         // false
Boolean(0);          // false
// So:  if ([])  → runs      but   [] == false → true
// Different algorithms produce that apparent contradiction.
```

### The `+` operator: concatenation or addition?

```typescript
// If EITHER operand is a string after ToPrimitive → concatenate
1 + '2';        // "12"
'5' + 3;        // "53"
[1, 2] + [3];   // "1,23"   (both → strings)
{} + 1;         // 1 or "[object Object]1" depending on context:
                // as a statement, {} is parsed as an empty BLOCK,
                // so it's +1 → 1. Inside parens: ({}) + 1 → "[object Object]1"

// Everything else → numeric
'6' - 1;        // 5     (no string concatenation for -)
true + true;    // 2
null + 1;       // 1     (null → 0)
undefined + 1;  // NaN
```

## Code Examples

### The classics, derived (not memorized)

```typescript
// [] == ![]  →  true. Why?
// 1. ![] → false            (every object is truthy)
// 2. [] == false            (boolean on one side → ToNumber)
// 3. [] → '' → 0, false → 0
// 4. 0 == 0 → true

// null == undefined → true. Browser document.all is a legacy exceptional case.
null == 0;          // false  (null only loosely equals undefined)
null >= 0;          // true   (RELATIONAL operators: null → 0)
null > 0;           // false  (0 > 0 is false)
// The null == 0 vs null >= 0 split is a favorite senior probe.

// '5' == 5 → true (string → number), but '5' === 5 → false

// NaN never equals anything, including itself
NaN === NaN;        // false
Object.is(NaN, NaN); // true  (Object.is: SameValue, fixes both NaN and -0)
Object.is(0, -0);   // false  (=== says true)

// -0 vs 0: === and == say equal, Object.is distinguishes,
// Math.sign(-0) preserves negative zero; choose equality by the required numeric semantics.
```

### A nullish comparison deliberately accepts two types

```typescript
// Idiomatic: catch both null and undefined in one check
function normalize(value: string | null | undefined): string {
  if (value == null) return ''; // == null is the FEATURE: covers null + undefined
  return value.trim();
}

// Everything else: === with explicit conversion where needed
function coerceInt(input: unknown): number {
  const n = Number(input);
  return Number.isNaN(n) ? 0 : Math.trunc(n); // explicit > implicit
}
```

## Real-World Use Cases

### 1. Form input arithmetic

```typescript
// HTML input.value is a string; valueAsNumber and typed form models have other contracts.
const qty = form.qty.value;        // "3"
const price = 1999;
let total = qty + price;           // "31999"  ← string concat, real production bug
total = Number(qty) + price;       // 2002     ← explicit conversion
```

### 2. Optional params and defaults

```typescript
// || vs ?? — the coercion decision with real consequences
function badDefault(v: number | undefined) {
  return v || 50;   // 0 becomes 50  ← probably wrong
}

function goodDefault(v: number | undefined) {
  return v ?? 50;   // only undefined/null become 50 ← correct
}
```

### 3. Sorting mixed values

```typescript
// Relational operators coerce: mixed-type arrays sort by coerced comparison
[10, 9, '8'].sort();               // [10, '8', 9]  (all → strings, then lexicographic)
[10, 9, 8].sort((a, b) => a - b);  // [8, 9, 10]    (numeric comparator — no coercion surprises)
```

## Common Mistakes

### 1. `||` where `??` is meant

```typescript
// BAD: valid falsy values (0, '', false) get replaced
const bad = userSetting || 3;    // 0 → 3

// GOOD: only nullish falls back
const good = userSetting ?? 3;
```

### 2. Assuming `Number()` and `parseInt()` agree

```typescript
Number('42px');     // NaN
parseInt('42px');   // 42   (leading-numeric parsing)
Number('');         // 0
parseInt('', 10);   // NaN
// Choose by intent: Number for whole-string conversion, parseInt for leading digits.
// Always pass the radix to parseInt.
```

### 3. Truthiness checks on collections

```typescript
// BAD: an empty array/object is truthy
if (results) render(results);        // runs with [] — is that "no results"?

// GOOD: check emptiness explicitly
if (Array.isArray(results) && results.length > 0) render(results);
```

### 4. Mixing `-` with string operands expecting concat

```typescript
// BAD: expecting subtraction to behave like +
'a' - 1;   // NaN (not an error, not 'a1')

// GOOD: validate before arithmetic, or Number() explicitly
```

## Best Practices

1. **Default to `===`/`!==`.** Use `==` only for the two idioms where coercion is the feature: `x == null` and `x != null`.
2. **Prefer `??` over `||` for defaults** — reserve `||` for boolean-coalescing where falsy values are genuinely invalid.
3. **Convert explicitly at boundaries** — form input, URL params, `localStorage`, API payloads: `Number()`, `String()`, `Boolean()` make the conversion visible and reviewable.
4. **Use `Object.is` in comparisons where `-0`/`NaN` matter** (polyfill-grade equality, test assertions).
5. **Sort with comparators** — never rely on default lexicographic sort for numbers.
6. **Never rely on implicit coercion in library code** — the derivation rules above are for reading/debugging legacy code and interviews, not a license to write `[] + {}` in production.

## Performance Considerations

- Coercion itself is cheap; the real cost is the *bugs* it hides (a `"31999"` total ships before anyone notices).
- `Number(x)` vs `+x` vs `x | 0`: `|0` truncates to 32-bit and is a micro-optimization only — `Math.trunc` communicates intent and handles values beyond 32-bit.
- Hot paths (parsers, sorters) benefit from keeping types consistent so engines stay on the monomorphic fast path — mixed-type arrays deoptimize comparisons in V8.

Arithmetic with BigInt is another boundary: `1n + 1` throws rather than converting both to Number, while loose equality can compare a BigInt and a suitable numeric/string value. An object may run conversion code through `Symbol.toPrimitive`; conversions can have side effects or throw. Boolean contexts do not use those object-to-primitive hooks.

## Summary

1. `===` compares as-is; `==` coerces via a small, derivable algorithm (null/undefined pair, ToNumber, ToPrimitive).
2. Three conversion engines: ToPrimitive (`Symbol.toPrimitive` → `valueOf` → `toString`), ToNumber, and boolean truthiness — and they disagree (`[]` is truthy but `[] == false`).
3. `+` concatenates if either primitive result is a string; `-` is always numeric.
4. `??` guards only `null`/`undefined`; `||` guards all falsy — the choice is a correctness decision, not style.
5. The one sanctioned `==` idiom is `x == null`. Everything else: explicit conversion.
6. `Object.is` distinguishes `NaN` and `-0`; `===` does not.

# Modules

## TL;DR

ESM (`import`/`export`) is the standard, static-analyzable module system. CommonJS (`require`/`module.exports`) is the legacy Node format. ESM supports tree-shaking, top-level await, and is async to load. CJS is sync, dynamic, and bundles naturally with Node.

## First Principles

Modules are the endpoint of one escalating necessity:

1. **Shared global scope cannot scale** (→ 10.1.1.02): as programs grow, name collisions and invisible coupling make change dangerous. The only cure is a language-level boundary: an execution unit with its own scope and an *explicit* list of what it exports.
2. **Dependency must be static to be analyzable.** `import` statements are fixed at parse time — so bundlers can tree-shake, cycles can be detected, and tools can reason about the graph without running anything. That is *why* ESM beats dynamic patching systems; staticness is the feature.
3. **Privacy falls out of scope, not keywords.** A module's top-level scope is already unreachable from outside (→ 10.1.1.06); `export` simply punches the only holes. The IIFE-module pattern was this same insight before the language supported it.
4. **Caching of the module instance** (one evaluation per import graph) makes module top-level state a singleton by definition — a feature and a hazard in one.


## Why It Matters

Senior engineers know: ESM is stricter (top-level `this` is undefined, exports are live bindings rather than object properties, and reading a binding whose module hasn't evaluated yet throws a ReferenceError instead of yielding `undefined`), and dual-package projects need `package.json` `exports` field, `.mjs`/`.cjs` extensions, and careful handling of `__dirname` (undefined in ESM).

## Definition

**Modules** are reusable pieces of code that encapsulate functionality and can be imported/exported between files. They provide code organization, encapsulation, and dependency management in JavaScript applications.

## Code Examples

### ES Module Basics

```typescript
// math.ts - Export
export const PI = 3.14159;

export function add(a: number, b: number): number {
  return a + b;
}

export function multiply(a: number, b: number): number {
  return a * b;
}

export default class Calculator {
  result = 0;

  add(n: number) {
    this.result += n;
    return this;
  }

  getResult() {
    return this.result;
  }
}

```

```typescript
// app.ts - Import
import Calculator, { PI, add, multiply } from './math';

console.log(PI); // 3.14159
console.log(add(2, 3)); // 5

const calc = new Calculator();
calc.add(5).add(10);
console.log(calc.getResult()); // 15

```

### Named vs Default Exports

```typescript
// utils.ts
export const formatDate = (date: Date) => date.toISOString();
export const parseJSON = (str: string) => JSON.parse(str);

// Default export
export default function greet(name: string) {
  return `Hello, ${name}`;
}

```

```typescript
// app.ts
// Named imports
import { formatDate, parseJSON } from './utils';

// Default import
import greet from './utils';

// Rename imports
import { formatDate as format } from './utils';

// Namespace import
import * as utils from './utils';
console.log(utils.formatDate(new Date()));

```

### Dynamic Imports

```typescript
// Lazy load module
async function loadModule() {
  const module = await import('./heavy-module');
  module.doSomething();
}

// Conditional import
if (condition) {
  const module = await import('./optional-module');
  module.doSomething();
}

// With webpack
const module = await import(
  /* webpackChunkName: "heavy" */
  './heavy-module'
);

```

### Re-exports

```typescript
// index.ts - barrel file
export { User } from './user';
export { Post } from './post';
export { Comment } from './comment';

// Or rename
export { User as UserModel } from './user';

```

### CommonJS (Node.js)

```typescript
// utils.js (CommonJS)
const PI = 3.14159;

function add(a, b) {
  return a + b;
}

module.exports = { PI, add };

// Or
exports.PI = PI;
exports.add = add;

```

```typescript
// app.js (CommonJS)
const { PI, add } = require('./utils');
// Or
const utils = require('./utils');
console.log(utils.PI);

```

## Real-World Use Cases

### 1. React Components

```typescript
// Button.tsx
export interface ButtonProps {
  children: React.ReactNode;
  onClick?: () => void;
  variant?: 'primary' | 'secondary';
}

export function Button({ children, onClick, variant = 'primary' }: ButtonProps) {
  return (
    <button className={`btn btn-${variant}`} onClick={onClick}>
      {children}
    </button>
  );
}

```

```typescript
// App.tsx
import { Button } from './Button';

function App() {
  return (
    <Button onClick={() => console.log('clicked')}>
      Click me
    </Button>
  );
}

```

### 2. Utility Library

```typescript
// utils/index.ts
export { formatDate, parseDate } from './date';
export { debounce, throttle } from './timing';
export { deepClone, isEqual } from './objects';

```

```typescript
// utils/date.ts
export function formatDate(date: Date): string {
  return date.toLocaleDateString();
}

export function parseDate(str: string): Date {
  return new Date(str);
}

```

### 3. API Client

```typescript
// api/client.ts
export class ApiClient {
  constructor(private baseUrl: string) {}

  async get<T>(endpoint: string): Promise<T> {
    const response = await fetch(`${this.baseUrl}${endpoint}`);
    return response.json();
  }
}

export const api = new ApiClient('https://api.example.com');

```

```typescript
// api/users.ts
import { api } from './client';

export interface User {
  id: string;
  name: string;
}

export async function getUsers(): Promise<User[]> {
  return api.get<User[]>('/users');
}

```

### 4. Configuration

```typescript
// config/index.ts — environment-specific config, swapped at import time
const config = {
  development: {
    apiUrl: 'http://localhost:3000',
    debug: true
  },
  production: {
    apiUrl: 'https://api.example.com',
    debug: false
  }
};

const env = process.env.NODE_ENV || 'development';
export default config[env as keyof typeof config];

```

Which env mechanism is available depends on the runtime: `process.env.NODE_ENV`
works in Node.js and is statically replaced by every bundler. In Vite browser
code the idiomatic access is `import.meta.env.MODE` (and `import.meta.env.VITE_*`
for custom variables); Next.js exposes `process.env.NEXT_PUBLIC_*` to the client
bundle and keeps everything else server-only. The module pattern is the same in
all three — the bundler inlines the value at build time, so dead config branches
are tree-shaken away.

## Common Mistakes

### 1. Circular Dependencies

```typescript
// a.ts
import { b } from './b';
export const a = 'a';

// b.ts
import { a } from './a'; // Circular!
export const b = 'b';

// Solution: Restructure code, use dependency injection

```

### 2. Default vs Named Exports

```typescript
// Bad: Inconsistent exports
export default function foo() {}
export function bar() {}

// Good: Consistent pattern
// Either all default or all named
export function foo() {}
export function bar() {}

```

### 3. Side-Effect Imports Are Legitimate — Accidental Ones Aren't

```typescript
// Correct: a polyfill/CSS import exists purely for its side effects —
// there is no binding to import, and the module MUST run.
import './polyfill';
import './styles.css';

// The real footgun: importing a whole namespace for one helper, so the
// bundler pulls in every module the barrel touches.
import * as utils from './utils';   // everything in the barrel
const stamp = utils.formatDate(new Date());

// Better: import the binding you use — unused named exports drop out.
import { formatDate } from './utils';
```

Bundlers only skip a module they can prove is unused: `sideEffects: false`
in the library's `package.json` (plus named exports) is what lets tree
shaking delete the rest. An `import 'x'` line with no bindings is never
shaken away — by design.

### 4. Missing File Extensions

```typescript
// Node ESM: extension (and full path) is REQUIRED — the resolver does no
// directory/index guessing like CJS does:
import { foo } from './utils.js';   // works in Node ESM
import { foo } from './utils';      // ERR_MODULE_NOT_FOUND

// Bundlers (webpack, Vite, esbuild) resolve extensionless specifiers via
// their own `resolve.extensions` config, so './utils' is fine there —
// but the same file cannot be imported by both without a compromise path.
```

## Best Practices

1. **Prefer named exports over a default-exported object.** They can be renamed at the import site (`import { formatDate as format }`), statically checked, and tree-shaken; `export default { add, multiply }` keeps every property alive no matter what you use.
2. **Give each folder one import path with a barrel file** (`utils/index.ts`): `export * from './date'` for a wide barrel, or explicit `export { formatDate } from './date'` when you want the surface enumerated (see Re-exports under Code Examples).
3. **Lazy-load heavy routes and components** with `React.lazy(() => import(...))` + `<Suspense>` — the example lives under Performance Considerations, next to the route-splitting pattern it pairs with.
4. **Keep types out of the runtime graph** — `import type { User } from './types'` is erased at compile time, so a type-only dependency never becomes a real module edge.

## Performance Considerations

### Code Splitting

```typescript
// Route- or component-based splitting: the chunk is fetched on first use,
// not in the initial bundle.
const Home = React.lazy(() => import('./pages/Home'));
const HeavyChart = React.lazy(() => import('./components/HeavyChart'));

// Suspense is the required companion — it holds the UI (and the fallback)
// while the chunk loads; without it the lazy component suspends the render.
function App() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <Home />
      <HeavyChart />
    </Suspense>
  );
}
```

### Tree Shaking

```typescript
// Good: Named exports for tree shaking
export function add(a: number, b: number) { return a + b; }
export function multiply(a: number, b: number) { return a * b; }

// Import only what's needed
import { add } from './math';
// multiply is not included in bundle

// Bad: Default export with everything
export default { add, multiply };
// Both are included even if only add is used

```

## Summary

Modules are essential for modern JavaScript:

1. **CommonJS**: require(), synchronous, Node.js

2. **ES Modules**: import/export, asynchronous, modern standard

3. **Tree shaking**: Remove unused code

4. **Code splitting**: Load code on demand

5. **Best practices**: Named exports, barrel files, avoid circular deps

6. **Performance**: Lazy loading, proper bundling

7. **TypeScript**: Type safety with modules

## Revision Questions

**Definition**

1. **Q:** What three properties separate a module from "a script in a wrapper"?
   **A:** A top-level scope nothing outside can reach, an explicit export list as the only way through that wall, and one cached instance per URL — so importing the same module twice still runs it once.

**First Principles**

2. **Q:** Why does ESM insist that dependencies be static, and what does that buy?
   **A:** `import` specifiers are fixed at parse time, so tools can build the full graph, detect cycles, and drop unused exports without executing anything — analyzability is the feature, not the syntax.

3. **Q:** Why is module top-level state a singleton, and when is that a hazard?
   **A:** The module map caches one instance per URL, so every importer shares the same bindings — ideal for config or a shared client, a trap the moment you wanted a fresh copy per importer.

**How It Works**

4. **Q:** Put the ESM loading pipeline in order.
   **A:** Parse the entry graph → resolve specifiers to URLs → fetch → parse each module → link imports to exports → evaluate in dependency order; evaluation happens once per module no matter how many importers it has.

5. **Q:** What can CommonJS `require()` do that a static `import` cannot, and what is ESM's escape hatch?
   **A:** `require()` builds its argument at runtime, so it can run conditionally or on a computed path; ESM imports are hoisted and resolved before any code runs — for conditional loading you `await import()`, which yields a promise for the module namespace.

**Common Mistakes**

6. **Q:** When a circular dependency bites, do you get `undefined` or an error?
   **A:** It depends on the system: CommonJS hands back a partially-filled `exports` object (`undefined` for anything not assigned yet, plus Node's circular-dependency warning), while reading an uninitialized ESM live binding throws a ReferenceError (TDZ).

7. **Q:** Why can `import { foo } from './utils'` fail in Node ESM yet work in a bundler?
   **A:** Node's ESM resolver requires the full path with an extension and does no directory/index guessing; bundlers apply their own `resolve.extensions` config — so dual-target code needs a deliberate strategy (`exports` map, or always ship explicit paths).

**Performance Considerations**

8. **Q:** What must a module provide before a bundler can tree-shake its exports away?
   **A:** Static, side-effect-free named exports the bundler can prove are unused (ideally with `sideEffects: false` in `package.json`) — a namespace import or a default-exported object keeps every member reachable.

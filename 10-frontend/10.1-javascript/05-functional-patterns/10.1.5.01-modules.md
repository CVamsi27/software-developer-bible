# Modules

A feature imports a client, a helper, and a type. If one import fails or a supposedly shared client has separate state, the problem may be how the host identifies, loads, or evaluates modules — not what the exported function does.

```js
// math.js
export const taxRate = 0.2;
export function total(amount) { return amount * (1 + taxRate); }

// app.js
import { total } from './math.js';
console.log(total(100)); // 120
```

## Definition

A **module** is a separately scoped unit of code with an explicit public surface. Other modules import that surface through a dependency graph. ECMAScript modules (ESM) link imports to exports before evaluation; the host or toolchain resolves and loads the files.

> **Textbook Definition:** A module is an independently scoped program unit that declares imports and exports. In ESM, imports are bindings connected during linking and exports expose bindings to other modules; module identity, loading, and evaluation are governed by the host environment.

## First Principles

A module system solves three related problems. **Scope** keeps internal names private unless exported. **Dependency edges** make relationships between files explicit. **Module identity** determines whether importers share the same evaluation and state. These guarantees depend on the module format and loader; a module boundary organizes access but does not hide source code or protect embedded secrets.

## How It Works

### 1. Resolve, Link, Then Evaluate

A host resolves a specifier such as `./client.js` to a module identity, loads and parses it, links its imports to exports, then evaluates the graph. A missing named export can fail at linking. A cycle can link successfully but still throw if evaluation reads a lexical export before it is initialized. Dependencies may be fetched or evaluated asynchronously; this model describes the relationships, not a fixed series of network requests.

CommonJS cycles have a different observable boundary: `require()` can return an export value before the other module has finished evaluating. The importer may therefore see a partially initialized object. Do not assume an ESM temporal-dead-zone error and a CommonJS partial export behave the same way.

```text
app.js ──imports──> users.js ──imports──> client.js
                                └────────> types.js (type-only in TypeScript)
```

Within one loader, importers normally share the instance for the same resolved module identity. Different URLs, paths, realms, test loaders, or bundled copies can create separate instances. A module-level API client is therefore shared state: it should not hold per-user credentials when concurrent requests may belong to different users. See [Lexical Environment](../01-execution-and-scope/10.1.1.05-lexical-environment.md) for the complete live-binding trace.

### 2. ESM and CommonJS Expose Different Contracts

| Concern | ESM | CommonJS |
| ------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Public surface | Static `export` declarations; imports are bindings | The value assigned to `module.exports`; `require()` returns that value |
| Evaluation | Imports are linked before module-body evaluation | `require()` loads and evaluates synchronously when called |
| Binding behavior | An import observes updates to the exported binding; the importer cannot assign through it | Exported object properties can be mutated; destructuring a primitive copies its current value |
| Main environments | Native in browsers, Node, and modern toolchains | Node format; browsers need tooling or a compatibility runtime |
| Strictness and top-level `this` | Always strict; top-level `this` is `undefined` | Node's wrapper supplies a module context; top-level `this` is `module.exports` |

In CommonJS, `exports` initially aliases `module.exports`; assigning a new object to `exports` alone does not replace the exported value. When ESM imports CommonJS in Node, the default import is the `module.exports` value. Detected named exports are interoperability conveniences and should not be treated as live CommonJS bindings.

Node supports both formats. Package `type` and `.mjs`/`.cjs` extensions provide explicit markers; modern Node versions can also use syntax detection for otherwise ambiguous `.js` files. `exports` conditions and the supported Node versions further determine a package's entry points. Explicit markers avoid ambiguity. Node's CommonJS/ESM interop has version and graph constraints, especially around top-level `await`; test the emitted package on the versions you support. A TypeScript source import must also resolve to a valid emitted runtime path. `moduleResolution: "nodenext"` can map a `.js` specifier to a `.ts` source while preserving the `.js` specifier in output; bundler resolution may accept extensionless paths that native Node does not.

### 3. Make the Public Surface Deliberate

A package's `exports` field can define supported entry points and prevent consumers from depending on internal file paths. A barrel file can provide a convenient surface:

```js
// utils/index.js
export { formatDate } from './date.js';
export { parseMoney } from './money.js';
```

Prefer explicit re-exports when they make the API easy to review. A default export is one binding named `default`, not an object containing all named exports. Wide `export *` barrels can make ownership less obvious and can participate in cycles. A cycle is not automatically a bug, but an initialization-time read of an uninitialized lexical binding throws. Move shared definitions to a lower-level module or delay the dependent work when a cycle obscures initialization order.

TypeScript's `import type` and `export type` describe compile-time dependencies and are erased from emitted JavaScript. They should not be mistaken for runtime module edges. Keep the compiler's module and resolution settings aligned with the environment that executes the output.

### 4. Defer Loading Only When the User Can Benefit

Static imports declare the module graph up front. `import()` loads a module on demand and returns a promise, which can defer route-specific code until a user opens that route:

```js
async function openReport() {
  const { renderReport } = await import('./report.js');
  return renderReport();
}
```

A bundler may emit a separate chunk, shared chunks, or another layout. React's `lazy` can consume a dynamic import, but its pending UI and chunk-error handling belong to React's Suspense and Error Boundary contract. Verify the production output and test a failed chunk request; one dynamic import does not promise one network request.

Static syntax can help a bundler prove that unused exports are removable, but tree shaking is a build-time analysis, not a runtime guarantee. Side-effectful modules must remain. Package `sideEffects` metadata can enable removal of unused files; incorrect metadata can drop required CSS, polyfills, or initialization. Inspect the production bundle and exercise the side effects the application relies on.

## Summary

A module graph defines scope, dependencies, and shared module identity. ESM exposes linked live bindings; CommonJS exposes the value assigned to `module.exports`. Host resolution, package conditions, cycles, and emitted paths determine whether those contracts work in production. Keep the public surface explicit, keep request-specific state with its request owner, and verify bundler behavior from emitted output.

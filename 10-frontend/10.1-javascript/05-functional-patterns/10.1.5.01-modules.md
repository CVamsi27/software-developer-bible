# Modules

## Definition

**Modules** are reusable pieces of code that encapsulate functionality and can be imported/exported between files. They provide code organization, encapsulation, and dependency management in JavaScript applications.

> **Textbook Definition:** A module is a separately scoped unit with explicit exports and imports that form a dependency graph. ECMAScript modules link live bindings before evaluation; loading and resolution remain responsibilities of the host or toolchain.


## First Principles

Modules are the endpoint of one escalating necessity:

1. **Shared names become harder to manage as code grows** (→ 10.1.1.02). A module gives code its own scope and an explicit list of exports, reducing accidental name collisions and hidden dependencies.
2. **Static imports make dependencies easier to inspect.** An `import` statement names its dependency before the code runs. Tools can follow those links as a **dependency graph**, detect cycles and remove provably unused code, called **tree shaking**. Runtime `import()` is a separate mechanism for loading dynamically.
3. **Unexported names remain inside module scope** (→ 10.1.1.06). Other modules can access exported bindings, but cannot directly name private top-level variables. Older IIFE module patterns used a function scope for a similar boundary.
4. **Importers normally share a cached module instance.** The loader evaluates a module once for its resolved identity and shares its state. Different URLs, loaders, realms or bundled copies can create separate instances. Shared state is useful for a common client, but unsuitable when each caller needs independent state.


## Why It Matters

ES modules differ from CommonJS in several important ways. Top-level `this` is `undefined`. Exports are live bindings connected to variables, rather than properties copied from an export object. Reading an exported lexical binding before initialization throws `ReferenceError`; `var` and function declarations have different initial states. A package supporting both systems needs deliberate `package.json` exports and file extensions such as `.mjs` and `.cjs`. CommonJS's `__dirname` is not an ordinary variable available in ESM.

## How It Works

### Two ways to expose a file's public surface

A CommonJS file runs inside Node's module wrapper and assigns properties to `module.exports`; `require` retrieves its exported value. Mutating an exported object remains visible through shared references, but destructuring a primitive property copies its current value. `exports` initially refers to `module.exports`; assigning a new object to `exports` alone does not replace the exported value.

An ECMAScript module (ESM) declares named exports and import bindings before its body evaluates. An import refers to the exporting binding, so later exporter assignments can be observed; importers cannot assign through that import. The [lexical-environment module example](../01-execution-and-scope/10.1.1.05-lexical-environment.md) owns the complete live-binding trace. A default export is one export named `default`, not an automatic object containing all the names.

| Question | CommonJS | ESM |
| ------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| What does the importer receive? | The module's exported value | Bindings exposed through import syntax or a namespace |
| Where does resolution happen? | The host resolves a require argument when called | The host resolves static dependency specifiers while loading/linking |
| What does loading return? | require returns synchronously | import() returns a promise for a namespace |
| Is it native in browsers? | No; needs conversion/tooling | Yes, with module loading rules |

Node supports both systems; choose explicit `.cjs`/`.mjs` or package `type` rather than assuming all `.js` files have one default. Some Node versions support requiring synchronous ESM graphs; graphs with top-level await need asynchronous loading. Static ESM syntax does not mean paths resolve independently of host/toolchain rules, nor that all ESM evaluation must be asynchronous.

### Module Loading

**Resolution** maps a specifier such as `./user.js` to a module identity. The loader obtains/parses that module and follows its imports recursively. **Linking** checks exports and connects import bindings before evaluation. **Evaluation** executes module bodies in dependency order, accounting for cycles and top-level await. A missing export therefore fails before importer body execution; an imported lexical binding read too early in a cycle can still throw during evaluation.

In the graph below, three edges point to the same resolved user module. They share its instance and state within that loader, rather than executing three independent copies. Native browser loading fetches URLs; Node often reads files; a bundler can transform the graph before it reaches either host. The listed steps are a conceptual dependency process, not a promise of serial network requests.

## Code Examples

TypeScript/TSX examples below assume a configured compiler and bundler that resolves extensionless source imports. For native Node ESM after emitting JavaScript, use explicit `.js` relative specifiers and an ESM package/file marker. Browser examples need a module script served over HTTP with valid module responses. Each file-comment pair names separate source files; do not paste all blocks into one file.

### ES Module Basics

```typescript
// math.ts - Export
export const PI = 3.14159;

export function add(a: number, b: number): number {
  return a + b;
}

export function multiply(a: number, b: number): number {
  return a * b;
}

export default class Calculator {
  result = 0;

  add(n: number) {
    this.result += n;
    return this;
  }

  getResult() {
    return this.result;
  }
}

```

```typescript
// app.ts - Import
import Calculator, { PI, add, multiply } from './math';

console.log(PI); // 3.14159
console.log(add(2, 3)); // 5

const calc = new Calculator();
calc.add(5).add(10);
console.log(calc.getResult()); // 15

```

### Named vs Default Exports

```typescript
// utils.ts
export const formatDate = (date: Date) => date.toISOString();
export const parseJSON = (str: string) => JSON.parse(str);

// Default export
export default function greet(name: string) {
  return `Hello, ${name}`;
}

```

```typescript
// app.ts
// Named imports
import { formatDate, parseJSON } from './utils';

// Default import
import greet from './utils';

// Rename imports
import { formatDate as format } from './utils';

// Namespace import
import * as utils from './utils';
console.log(utils.formatDate(new Date()));

```

### Dynamic Imports

```typescript
// Lazy load module
async function loadModule() {
  const module = await import('./heavy-module');
  module.doSomething();
}

// Conditional import
if (condition) {
  const module = await import('./optional-module');
  module.doSomething();
}

// With webpack
const module = await import(
  /* webpackChunkName: "heavy" */
  './heavy-module'
);

```

### Re-exports

```typescript
// index.ts - barrel file
export { User } from './user';
export { Post } from './post';
export { Comment } from './comment';

// Or rename
export { User as UserModel } from './user';

```

### CommonJS (Node.js)

```typescript
// utils.cjs (CommonJS)
const PI = 3.14159;

function add(a, b) {
  return a + b;
}

module.exports = { PI, add };

// Or (instead of replacing module.exports above)
exports.PI = PI;
exports.add = add;

```

```typescript
// app.cjs (CommonJS)
const { PI, add } = require('./utils.cjs');
// Or
const utils = require('./utils.cjs');
console.log(utils.PI);

```

## Real-World Use Cases

### 1. React Components

```typescript
// Button.tsx
export interface ButtonProps {
  children: React.ReactNode;
  onClick?: () => void;
  variant?: 'primary' | 'secondary';
}

export function Button({ children, onClick, variant = 'primary' }: ButtonProps) {
  return (
    <button className={`btn btn-${variant}`} onClick={onClick}>
      {children}
    </button>
  );
}

```

```typescript
// App.tsx
import { Button } from './Button';

function App() {
  return (
    <Button onClick={() => console.log('clicked')}>
      Click me
    </Button>
  );
}

```

### 2. Utility Library

One folder, one import path: callers write `import { formatDate } from '../utils'` and never reach into `utils/date.ts`. The barrel syntax itself is covered under [Re-exports](#re-exports) above — the part unique to a library folder is that the barrel *is* the public surface: a file not re-exported is absent from the intended public surface. A relative deep import may still reach it; enforce package boundaries through exports, tooling and reviews.
### 3. API Client

The module creates one client for its resolved identity; user functions import that client rather than constructing one per call. This is a reuse/lifetime example, not proof that JSON has a declared type. Supply an application `decodeUsers` function/import that validates the unknown response, and let the caller handle rejection. Keep per-user credentials out of a global mutable singleton when concurrent requests require different sessions.

```typescript
// api/client.ts
export class ApiClient {
  constructor(private baseUrl: string) {}

  async get(endpoint: string): Promise<unknown> {
    const response = await fetch(`${this.baseUrl}${endpoint}`);
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json();
  }
}

export const api = new ApiClient('https://api.example.com');

```

```typescript
// api/users.ts
import { api } from './client';

export interface User {
  id: string;
  name: string;
}

export async function getUsers(): Promise<User[]> {
  const payload = await api.get('/users');
  return decodeUsers(payload); // Application schema decoder: validates unknown or throws.
}

```

### 4. Configuration

```typescript
// config/index.ts — environment-specific config, swapped at import time
const config = {
  development: {
    apiUrl: 'http://localhost:3000',
    debug: true
  },
  production: {
    apiUrl: 'https://api.example.com',
    debug: false
  }
};

const env = process.env.NODE_ENV ?? 'development';
if (env !== 'development' && env !== 'production') throw new Error(`Unknown mode: ${env}`);
export default config[env];

```

Which env mechanism is available depends on the runtime: `process.env.NODE_ENV`
is available in Node.js; browser bundler replacement depends on configured defines and framework conventions. In Vite browser
code the idiomatic access is `import.meta.env.MODE` (and `import.meta.env.VITE_*`
for custom variables); Next.js exposes `process.env.NEXT_PUBLIC_*` to the client
bundle and keeps everything else server-only. The module pattern is the same in
all three — some public values are substituted at build time, while server values can remain runtime reads. Dead-branch removal depends on the resulting code and bundler configuration.

## Common Mistakes

### 1. Circular Dependencies

A cycle is a graph condition, not automatically an error. The two modules below do not read each other's values while initializing, so this particular ESM cycle can evaluate successfully. If b instead initializes its export from a's still-uninitialized const, that read throws. Factor shared definitions into a lower-level module or delay the dependent operation; moving import lines alone does not change the graph.

```typescript
// a.ts
import { b } from './b';
export const a = 'a';

// b.ts
import { a } from './a'; // Circular!
export const b = 'b';

// Solution: Restructure code, use dependency injection

```

### 2. Default vs Named Exports

Both forms are checked at linking: a missing named export and a missing default export can each fail before evaluation. A default-exported object's properties are ordinary property accesses, so a typo can produce undefined unless types/validation catch it. A default-exported function/class does not share that object-property issue. Mixing named and default exports is valid; choose a public API that callers can understand rather than treating consistency as a language correctness requirement.

### 3. Side-Effect Imports Are Legitimate — Accidental Ones Aren't

```typescript
// Correct: a polyfill/CSS import exists purely for its side effects —
// there is no binding to import, and the module MUST run.
import './polyfill';
import './styles.css';

// The real footgun: importing a whole namespace for one helper, so the
// unused exports may or may not be eliminated depending on analysis and side effects.
import * as utils from './utils';   // static utils.formatDate may still be analyzable
const stamp = utils.formatDate(new Date());

// A direct named import makes intended usage clear; elimination still needs proof.
import { formatDate } from './utils';
```

Tree shaking removes code only when analysis and build configuration establish that removal preserves behavior. In webpack, package `sideEffects` metadata can permit removal of unused modules; it is not the sole mechanism or a guarantee that every unused function disappears. Incorrect `sideEffects: false` metadata can cause even intended side-effect modules to be dropped. Mark CSS/polyfill modules appropriately and verify the production bundle.

### 4. Missing File Extensions

```typescript
// Node ESM: extension (and full path) is REQUIRED — the resolver does no
// directory/index guessing like CJS does:
import { foo } from './utils.js';   // works in Node ESM
import { foo } from './utils';      // ERR_MODULE_NOT_FOUND

// Bundlers (webpack, Vite, esbuild) resolve extensionless specifiers via
// their own `resolve.extensions` config, so './utils' is fine there —
// but the same file cannot be imported by both without a compromise path.
```

## Best Practices

1. **Prefer named exports over a default-exported object.** They can be renamed at the import site (`import { formatDate as format }`), statically checked, and tree-shaken; a default-exported object can make per-property elimination harder, but the result depends on the bundler and how callers use it.
2. **Define an intentional public surface; use a barrel when helpful** (`utils/index.ts`): `export * from './date'` for a wide barrel, or explicit `export { formatDate } from './date'` when you want the surface enumerated (see Re-exports under Code Examples).
3. **Lazy-load heavy routes and components** with `React.lazy(() => import(...))` + `<Suspense>` — the example lives under Performance Considerations, next to the route-splitting pattern it pairs with.
4. **Keep types out of the runtime graph** — `import type { User } from './types'` is erased at compile time, so a type-only dependency never becomes a real module edge.

## Performance Considerations

### Code Splitting

```typescript
// Route- or component-based splitting: the chunk is fetched on first use,
// not in the initial bundle.
const Home = React.lazy(() => import('./pages/Home'));
const HeavyChart = React.lazy(() => import('./components/HeavyChart'));

// Suspense is the required companion — it holds the UI (and the fallback)
// while the chunk loads; without it the lazy component suspends the render.
function App() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <Home />
      <HeavyChart />
    </Suspense>
  );
}
```

### Tree Shaking

```typescript
// Good: Named exports for tree shaking
export function add(a: number, b: number) { return a + b; }
export function multiply(a: number, b: number) { return a * b; }

// Import only what's needed
import { add } from './math';
// A suitable optimized build may eliminate multiply if its removal preserves behavior.

// Bad: Default export with everything
export default { add, multiply };
// Object-property elimination depends on bundler analysis and namespace usage.

```

Combining files reduces some module fetches; splitting can avoid loading unused routes. Inspect the emitted bundle rather than inferring request count or elimination from the import spelling alone.

## Summary

Modules are essential for modern JavaScript:

1. **CommonJS**: require(), synchronous, Node.js

2. **ES Modules**: statically linked imports and live bindings; loading/evaluation timing depends on the host and top-level await

3. **Tree shaking**: Remove unused code

4. **Code splitting**: Load code on demand

5. **Best practices**: Named exports, barrel files, avoid circular deps

6. **Performance**: Lazy loading, proper bundling

7. **TypeScript**: Type safety with modules

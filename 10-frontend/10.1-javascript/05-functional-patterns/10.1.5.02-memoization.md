# Memoization

## Definition

**Memoization** is an optimization technique that caches the results of expensive function calls and returns the cached result when the same inputs occur again. It trades memory for computation time.


## First Principles

Memoization is a cache applied to a specific guarantee:

1. **Pure functions map inputs to outputs — never anything else.** No side effects, no dependence on the outside. That guarantee is *why* recomputation is waste: the answer for `(3, 4)` is stable, so reuse can help when lookup/keying/retention cost is lower than recomputation.
2. **A cache is a hash-map keyed by input** (→ 10.1.4.08). Nothing more. Which also yields the two failure modes for free: unbounded growth (the leak — fix with LRU/WeakMap (→ 10.1.4.02)) and wrong answers if the "pure" function secretly isn't.
3. **Memoize only when the shape of use justifies it** — repeated subproblems (Fibonacci, recursive tree work, expensive derives over stable inputs). One-shot functions gain nothing and pay memory for it.


## Why It Matters

Senior engineers know when NOT to memoize: trivial functions, components that always re-render, or inputs that change every render. They use `useMemo` to stabilize referential equality (deps in effect arrays, props in memoized children) — not for performance in isolation.

## How It Works

### Memoization Flow

```text
┌─────────────────────────────────────────────────────────┐
│ MEMOIZATION FLOW                                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ WITHOUT MEMOIZATION:                                    │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ fibonacci(5) → calculates                           │ │
│ │ fibonacci(5) → calculates again!                    │ │
│ │ fibonacci(5) → calculates again!                    │ │
│ │                                                     │ │
│ │ Same calculation repeated multiple times            │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ WITH MEMOIZATION:                                       │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ fibonacci(5) → calculates, stores in cache          │ │
│ │ fibonacci(5) → returns cached result                │ │
│ │ fibonacci(5) → returns cached result                │ │
│ │                                                     │ │
│ │ First call: O(n)                                    │ │
│ │ Subsequent: O(1)                                    │ │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ CACHE STRUCTURE:                                        │
│ ┌─────────────────────────────────────────────────────┐ │
│ │                                                     │ │
│ │ Map or Object:                                      │ │
│ │ {                                                   │ │

│ │ }                                                   │ │
│ │                                                     │ │

│                                                         │
└─────────────────────────────────────────────────────────┘

```

## Code Examples

### Basic Memoization

The canonical `memoize()` closure — cache keyed by `JSON.stringify(args)` — is built and annotated in [Closures — Memoization with Closures](../01-execution-and-scope/10.1.1.06-closures.md); that example *is* the demonstration of closure-state. This chapter builds on it: where the naive version costs, and the trades of each strategy.

### Fibonacci with Memoization

```typescript
// Without memoization: O(2^n)
function fibonacci(n: number): number {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
}

// With memoization: O(n)
function fibonacciMemo(n: number, memo: Map<number, number> = new Map()): number {
  if (n <= 1) return n;

  if (memo.has(n)) {
    return memo.get(n)!;
  }

  const result = fibonacciMemo(n - 1, memo) + fibonacciMemo(n - 2, memo);
  memo.set(n, result);
  return result;
}

// Using memoize utility
const fib = memoize((n: number): number => {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
});

```

### Advanced Memoization with LRU Cache

```typescript
class LRUCache<K, V> {
  private cache = new Map<K, V>();
  private maxSize: number;

  constructor(maxSize: number) {
    this.maxSize = maxSize;
  }

  get(key: K): V | undefined {
    const value = this.cache.get(key);
    if (value !== undefined) {
      // Move to end (most recently used)
      this.cache.delete(key);
      this.cache.set(key, value);
    }
    return value;
  }

  set(key: K, value: V) {
    if (this.cache.has(key)) {
      this.cache.delete(key);
    } else if (this.cache.size >= this.maxSize) {
      // Delete oldest (first) entry
      const firstKey = this.cache.keys().next().value;
      this.cache.delete(firstKey);
    }
    this.cache.set(key, value);
  }
}

function memoizeWithLRU<T extends (...args: any[]) => any>(
  fn: T,
  maxSize: number = 100
): (...args: Parameters<T>) => ReturnType<T> {
  const cache = new LRUCache<string, ReturnType<T>>(maxSize);

  return function(...args: Parameters<T>): ReturnType<T> {
    const key = JSON.stringify(args);

    const cached = cache.get(key);
    if (cached !== undefined) {
      return cached;
    }

    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

```

### React useMemo/useCallback

```typescript
import { useMemo, useCallback } from 'react';

function ExpensiveComponent({ items, filter }: Props) {
  // Memoize expensive computation
  const filteredItems = useMemo(() => {
    return items.filter(item => item.category === filter);
  }, [items, filter]);

  // Memoize callback
  const handleClick = useCallback((id: string) => {
    console.log(`Clicked ${id}`);
  }, []);

  return (
    <ul>
      {filteredItems.map(item => (
        <li key={item.id} onClick={() => handleClick(item.id)}>
          {item.name}
        </li>
      ))}
    </ul>
  );
}

```

### Memoization with TTL

```typescript
function memoizeWithTTL<T extends (...args: any[]) => any>(
  fn: T,
  ttl: number = 60000
): (...args: Parameters<T>) => ReturnType<T> {
  const cache = new Map<string, { value: ReturnType<T>; timestamp: number }>();

  return function(...args: Parameters<T>): ReturnType<T> {
    const key = JSON.stringify(args);
    const now = Date.now();

    const cached = cache.get(key);
    if (cached && now - cached.timestamp < ttl) {
      return cached.value;
    }

    const result = fn(...args);
    cache.set(key, { value: result, timestamp: now });
    return result;
  };
}

// Usage
const apiCall = memoizeWithTTL(fetchData, 30000); // Cache for 30 seconds

```

## Real-World Use Cases

### 1. Data Processing

```typescript
const expensiveTransform = memoize((data: any[]) => {
  return data
    .filter(item => item.active)
    .map(item => ({
      ...item,
      score: calculateScore(item)
    }))
    .sort((a, b) => b.score - a.score);
});

```

### 2. API Response Caching

```typescript
const apiCache = memoizeWithTTL(async (url: string) => {
  const response = await fetch(url);
  return response.json();
}, 60000);

// Usage
const users = await apiCache('/api/users');

```

Two mechanics worth naming: the cache stores the *promise*, so concurrent
callers share one in-flight request instead of stampeding the endpoint — and
a rejected promise is stored too, so without an eviction on failure every
caller for the next 60 s gets the same rejection back. An in-flight cache should evict the matching promise on failure without swallowing its rejection or deleting a newer entry. See the complete shared-request implementation in [Promises](../03-async-concurrency/10.1.3.02-promises.md); session/tenant identity and invalidation belong in its key/ownership contract.

### 3. React Component Optimization

```typescript
function ProductList({ products, category }: Props) {
  const filtered = useMemo(
    () => products.filter(p => p.category === category),
    [products, category]
  );

  const total = useMemo(
    () => filtered.reduce((sum, p) => sum + p.price, 0),
    [filtered]
  );

  return (
    <div>
      <p>Total: ${total}</p>
      <ul>
        {filtered.map(p => <li key={p.id}>{p.name}</li>)}
      </ul>
    </div>
  );
}

```

### 4. Recursive Functions

The wrapper itself is defined once, in [Closures — Memoization with Closures](../01-execution-and-scope/10.1.1.06-closures.md); recursion is where it pays off, because each call registers a subproblem the later calls will hit:

```typescript
// Recursive factorial — every level caches its own n
const factorial = memoize((n: number): number => {
  if (n <= 1) return 1;
  return n * factorial(n - 1);
});

// Same shape as the memoized fibonacci above: with the cache warm the
// factorial already has linear recursion; caching helps repeated calls,
// while Fibonacci's overlapping subproblems remove exponential repeated work.
```

## Common Mistakes

### 1. Memoizing Everything

```typescript
// Bad: paying cache lookup + memory for an O(1) addition
const add = memoize((a: number, b: number) => a + b);

// Good: only memoize expensive operations — or the recursive /
// filter-sort work that actually repeats subproblems
const complexCalculation = memoize((data: LargeDataset) => {
  // Expensive computation
});

```

### 2. Ignoring Cache Size

```typescript
// Bad: Unbounded cache
const cache = new Map();
function getData(key: string) {
  if (!cache.has(key)) {
    cache.set(key, fetchData(key));
  }
  return cache.get(key);
}

// Good: Bounded cache
const boundedCache = new LRUCache(1000);

```

### 3. Wrong Cache Key

```typescript
// Per-identity keying: only the SAME object instance hits the cache.
// Not a bug when identity is the contract — but {a: 1} literals passed
// on two calls are two different keys, so the cache never fires.
const cache = new Map<object, Result>();
function process(obj: object): Result {
  const hit = cache.get(obj);
  if (hit !== undefined) return hit;
  const result = compute(obj);
  cache.set(obj, result);
  return result;
}

// Structural keying shares equal-by-value objects — but plain
// JSON.stringify is insertion-order sensitive, so the same data in a
// different key order misses:
JSON.stringify({ a: 1, b: 2 });  // '{"a":1,"b":2}'
JSON.stringify({ b: 2, a: 1 });  // '{"b":2,"a":1}'  ← different key

```

```typescript
// Order-insensitive key: sort object keys recursively (verified: equal
// for {a,b} vs {b,a}, still distinct for {a:{z:1}} vs {a:{y:2}})
function stableStringify(value: unknown): string {
  if (Array.isArray(value)) return '[' + value.map(stableStringify).join(',') + ']';
  if (value && typeof value === 'object') {
    return '{' + Object.keys(value).sort()
      .map(k => JSON.stringify(k) + ':' + stableStringify(value[k])).join(',') + '}';
  }
  return JSON.stringify(value);
}
const createKey = (args: unknown[]): string => args.map(stableStringify).join(' ');

```

### 4. Not Handling Cache Invalidation

```typescript
// Bad: Cache never invalidated
const data = memoize(fetchData);

// Good: Implement TTL or manual invalidation
const freshData = memoizeWithTTL(fetchData, 60000);

```

## Best Practices

1. **Choose what to memoize**: expensive computations, API calls with repeated parameters, complex filtering/sorting, and recursive functions. Skip simple operations, frequently-changing inputs, and anything with side effects — memoization amplifies impurity instead of caching it.
2. **Set cache limits** — a capacity bound and, where freshness matters, a TTL; both are implemented under Common Mistakes and Code Examples, and both exist because an unbounded cache converts a hot path into a slow leak.
3. **Use proper cache keys** — `JSON.stringify(args)` is order-sensitive for objects and misses equal data in a different key order; the recursive stable-key version under [Common Mistakes — Wrong Cache Key](#3-wrong-cache-key) shares equal-by-value entries without collapsing structurally different ones.
4. **Profile before memoizing** — time both paths on real inputs before paying for the cache:

```typescript
// Measure performance impact
console.time('memoized');
memoizedFn(args);
console.timeEnd('memoized');

console.time('original');
originalFn(args);
console.timeEnd('original');

```

## Performance Considerations

### Memory vs Time Trade-off

> Memoizing an O(1) helper (`const add = memoize((a, b) => a + b)`) spends a
> cache lookup and permanent memory to skip arithmetic — the decision rule
> and the bad/good pair live in [Common Mistakes — Memoizing Everything](#1-memoizing-everything).
> The rest of the trade is the first-principles one: the cache never shrinks
> unless you bound it, so a reachable unbounded cache retains its entries
> that only earns its keep when recomputation was expensive.

### Cache Hit Rate

```typescript
// Monitor cache effectiveness
function memoizeWithStats<T extends (...args: any[]) => any>(fn: T) {
  const cache = new Map();
  let hits = 0;
  let misses = 0;

  const memoized = function(...args: Parameters<T>) {
    const key = JSON.stringify(args);
    if (cache.has(key)) {
      hits++;
      return cache.get(key);
    }
    misses++;
    const result = fn(...args);
    cache.set(key, result);
    return result;
  } as T & { getStats(): { hits: number; misses: number; ratio: number } };

  memoized.getStats = () => ({ hits, misses, ratio: hits / (hits + misses) });

  return memoized;
}

```

## Summary

Memoization is a powerful optimization:

1. **Definition**: Cache results of expensive function calls

2. **Implementation**: Map/object with stringified keys

3. **React**: useMemo, useCallback, React.memo

4. **Cache strategies**: LRU, TTL, bounded size

5. **Performance**: Trade memory for computation time

6. **Best practices**: Profile, set limits, handle invalidation

7. **Common issues**: Unbounded caches, stale data

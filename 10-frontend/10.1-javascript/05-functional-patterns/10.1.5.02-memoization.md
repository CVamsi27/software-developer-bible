# Memoization

A search result is expensive to compute but often requested again for the same tenant, query and page. A cache can make the second request cheaper, but only if its key captures every input that changes the answer and its lifetime matches the data's freshness.

## Definition

**Memoization** is an optimization technique that caches the results of expensive function calls and returns the cached result when the same inputs occur again. It trades memory for computation time.

> **Textbook Definition:** Memoization reuses a previously computed result by associating it with an input-derived cache key. Correct reuse requires equivalent inputs and stable dependencies; eviction bounds the memory retained by the cache.


## First Principles

Memoization is a cache applied to a specific guarantee:

1. **Reuse requires the same inputs to produce the same result.** A **pure function** depends only on its inputs and performs no side effects. Its answer for `(3, 4)` stays the same, so a cached result can replace another calculation. Reuse saves work only when finding the entry, constructing its key and keeping it in memory cost less than recomputing.
2. **The cache must identify inputs and control how long results remain.** A map keyed by input is a common implementation (→ 10.1.4.08). An unbounded cache can retain unwanted data for the lifetime of its owner. A **least recently used (LRU)** cache removes older entries when capacity is reached; a `WeakMap` can let eligible keys follow the lifetime of objects used elsewhere (→ 10.1.4.02). If the function secretly depends on changing external state, reusing an old answer can also be wrong.
3. **Repeated work must actually occur.** Repeated Fibonacci subproblems, recursive tree work and expensive calculations over unchanged inputs may benefit. A function called once cannot reuse its result, but still pays to store it.


## A hit skips the function; a miss must compute and retain

A wrapper derives a key from the call's inputs, checks its cache, and returns a stored value on a hit. On a miss it runs the function, stores the result under that key, and returns it. That sounds simple, but key equality, hidden dependencies, failures, expiry and eviction decide whether the shortcut is correct.

## Choose the cache contract before writing the wrapper

Repeated subproblems make the cache worthwhile: the first call pays to fill it, then later branches reuse those results.

The canonical `memoize()` closure — cache keyed by `JSON.stringify(args)` — is built and annotated in [Closures — Memoization with Closures](../01-execution-and-scope/10.1.1.06-closures.md); that example *is* the demonstration of closure-state. This chapter builds on it: where the naive version costs, and the trades of each strategy.

### Fibonacci with Memoization

Assume nonnegative integer n small enough for Number arithmetic and the runtime stack. The first `fibonacciMemo(5)` computes/cache-fills subproblems 2–5; overlapping branches reuse them. The default map is new for each top-level call, so independent calls do not share it unless the caller passes the same map. The wrapper-based alternative keeps one closure cache between calls; `memoize` comes from the linked closure chapter.

```typescript
// Without memoization: O(2^n)
function fibonacci(n: number): number {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
}

// With memoization: O(n)
function fibonacciMemo(n: number, memo: Map<number, number> = new Map()): number {
  if (n <= 1) return n;

  if (memo.has(n)) {
    return memo.get(n)!;
  }

  const result = fibonacciMemo(n - 1, memo) + fibonacciMemo(n - 2, memo);
  memo.set(n, result);
  return result;
}

// Using memoize utility
const fib = memoize((n: number): number => {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
});

```

### Bound retention and choose an equivalence key

Capacity and input equivalence solve different problems. This teaching wrapper uses insertion order to evict least-recently-used entries; the complete LRU collection explanation belongs in [Map and Set](../04-memory-and-data/10.1.4.02-map-set-weakmap-weakset.md). The caller supplies `keyOf` so the wrapper does not silently assume JSON serialization represents every input.

```typescript
function memoizeWithLRU<T extends (...args: any[]) => any>(
  fn: T,
  keyOf: (...args: Parameters<T>) => string,
  maxSize = 100
): (...args: Parameters<T>) => ReturnType<T> {
  if (!Number.isInteger(maxSize) || maxSize < 1) throw new RangeError('Invalid capacity');
  const cache = new Map<string, ReturnType<T>>();
  return (...args: Parameters<T>): ReturnType<T> => {
    const key = keyOf(...args);
    if (cache.has(key)) {
      const value = cache.get(key)!;
      cache.delete(key);
      cache.set(key, value);
      return value;
    }
    const result = fn(...args);
    if (cache.size >= maxSize) cache.delete(cache.keys().next().value!);
    cache.set(key, result);
    return result;
  };
}
```

Membership is checked separately from the value, so cached undefined is still a hit. For capacity two, calls A/B/A/C evict B. An exception before return is not cached; a returned promise is cached immediately, including a later rejection unless a separate failure-eviction policy removes it. This wrapper assumes a plain pure function: it does not forward dynamic this, preserve overloads or clone mutable returned objects.

### React caches are scoped to a render lifetime

useMemo may reuse a derived value while its dependencies are unchanged. useCallback is useful when a memoized child or another identity-sensitive consumer observes the callback reference; in this example, ItemRow is memoized and receives stable item identities.

```typescript
import { memo, useCallback, useMemo } from 'react';

type Item = { id: string; name: string; category: string };
type Props = { items: Item[]; filter: string };

const ItemRow = memo(function ItemRow({
  item,
  onClick,
}: {
  item: Item;
  onClick: (id: string) => void;
}) {
  return <li onClick={() => onClick(item.id)}>{item.name}</li>;
});

function ExpensiveComponent({ items, filter }: Props) {
  const filteredItems = useMemo(
    () => items.filter(item => item.category === filter),
    [items, filter],
  );
  const handleClick = useCallback((id: string) => {
    console.log('Clicked', id);
  }, []);

  return (
    <ul>
      {filteredItems.map(item => (
        <ItemRow key={item.id} item={item} onClick={handleClick} />
      ))}
    </ul>
  );
}
```

In-place mutation of items can leave the derived value stale because the array identity did not change. Recreating every item object defeats the row's shallow prop comparison. Dependency correctness is a behavior contract; memoization is still only an optimization and React may discard its cache.

### Memoization with TTL

A time-to-live (TTL) sets how long an entry may be reused, measured here with a process-local monotonic clock from computation start. This alternate teaching wrapper deliberately uses JSON-compatible argument keys; signed zero, undefined, NaN and other values can collapse or fail under JSON, so restrict/validate the input domain. Expired entries are replaced only on another call for that key. TTL alone does not bound retained key count; add capacity, cleanup or a cache lifetime owner.

```typescript
function memoizeWithTTL<T extends (...args: any[]) => any>(
  fn: T,
  ttl: number = 60000
): (...args: Parameters<T>) => ReturnType<T> {
  if (!Number.isFinite(ttl) || ttl < 0) throw new RangeError('Invalid TTL');
  const cache = new Map<string, { value: ReturnType<T>; timestamp: number }>();

  return function(...args: Parameters<T>): ReturnType<T> {
    const key = JSON.stringify(args);
    const now = performance.now();

    const cached = cache.get(key);
    if (cached && now - cached.timestamp < ttl) {
      return cached.value;
    }

    const result = fn(...args);
    cache.set(key, { value: result, timestamp: now });
    return result;
  };
}

// Usage
const apiCall = memoizeWithTTL(fetchData, 30000); // Cache for 30 seconds

```

## Real-World Use Cases

### Cache an expensive deterministic transform

```typescript
const expensiveTransform = memoize((data: any[]) => {
  return data
    .filter(item => item.active)
    .map(item => ({
      ...item,
      score: calculateScore(item)
    }))
    .sort((a, b) => b.score - a.score);
});

```

### Share an in-flight API request only under a safe key

```typescript
const apiCache = memoizeWithTTL(async (url: string) => {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json(); // Application decoder must validate the payload.
}, 60000);

// Usage
const users = await apiCache('/api/users');

```

Two mechanics worth naming: the cache stores the *promise*, so concurrent
callers share one in-flight request instead of stampeding the endpoint — and
a rejected promise is stored too, so without an eviction on failure every
caller for the next 60 s gets the same rejection back. An in-flight cache should evict the matching promise on failure without swallowing its rejection or deleting a newer entry. See the complete shared-request implementation in [Promises](../03-async-concurrency/10.1.3.02-promises.md); session/tenant identity and invalidation belong in its key/ownership contract.

### React derivations depend on immutable inputs

The React example above reuses a filtered result while `items` and `filter` keep their identities/values. Mutating the same items array in place can leave a cached derivation stale. Omitting a dependency has the same correctness risk. Derived totals can reuse that filtered result, but add a second cache only when profiling justifies it; [useMemo](../../10.3-react/02-core-hooks/10.3.2.03-usememo-usecallback.md) owns React’s dependency and cache-lifetime rules.

## Bound identity, retention and failure behavior

### 1. Memoizing Everything

```typescript
// Bad: paying cache lookup + memory for an O(1) addition
const add = memoize((a: number, b: number) => a + b);

// Compare cache key/lookup/retention cost against a real repeated calculation.
// An empty placeholder body cannot demonstrate a performance benefit.

```

### 2. Ignoring Cache Size

```typescript
// Bad: Unbounded cache
const cache = new Map();
function getData(key: string) {
  if (!cache.has(key)) {
    cache.set(key, fetchData(key));
  }
  return cache.get(key);
}

// Good: Bounded cache
const bounded = memoizeWithLRU(computeForId, (id: string) => id, 1000);

```

### 3. Wrong Cache Key

```typescript
// Per-identity keying: only the SAME object instance hits the cache.
// Not a bug when identity is the contract — but {a: 1} literals passed
// on two calls are two different keys, so the cache never fires.
const cache = new Map<object, Result>();
function process(obj: object): Result {
  const hit = cache.get(obj);
  if (hit !== undefined) return hit;
  const result = compute(obj);
  cache.set(obj, result);
  return result;
}

// Structural keying shares equal-by-value objects — but plain
// JSON.stringify is insertion-order sensitive, so the same data in a
// different key order misses:
JSON.stringify({ a: 1, b: 2 });  // '{"a":1,"b":2}'
JSON.stringify({ b: 2, a: 1 });  // '{"b":2,"a":1}'  ← different key

```

A domain-specific key is often clearer than a purported universal serializer. Suppose results depend on tenant, query and integer page. Encode that complete primitive tuple; reject unsupported page values before serializing. Property order then disappears because callers pass the same ordered tuple.

```typescript
function searchKey(tenant: string, query: string, page: number): string {
  if (!Number.isSafeInteger(page) || page < 1) throw new RangeError('Invalid page');
  return JSON.stringify([tenant, query, page]);
}
// Same tuple -> same key, even if callers obtained fields from differently ordered objects.
// Different tenants -> different keys; omitting tenant could expose another user's result.
```

If the computation also depends on language, authorization or data version, those belong in the key or an explicit invalidation boundary. A JSON key cannot distinguish values it discards/coerces; a canonical serializer needs a defined data model, not merely sorted keys. Object-identity keys also require immutable inputs or invalidation when those objects change.

### 4. Not Handling Cache Invalidation

```typescript
// Bad: Cache never invalidated
const data = memoize(fetchData);

// Good: Implement TTL or manual invalidation
const freshData = memoizeWithTTL(fetchData, 60000);

```

## A TTL is not an eviction policy

An LRU capacity limits how many entries stay reachable; TTL limits how long an entry is eligible for reuse. Expiry alone does not remove cold keys unless the cache performs cleanup, so a TTL cache can still grow without a capacity or lifetime boundary. For asynchronous work, define whether callers share an in-flight promise, whether a rejection is retried or negative-cached, and how an old failure avoids deleting a newer entry.

## Measure saved work and retained state

Compare the original computation with the memoized path on representative production-shaped inputs. Track hit rate alongside latency saved, key-construction cost, entry count and retained bytes. A high hit rate alone is not proof of a win if hits avoid trivial work or retain large results. Remove the cache when workload reuse does not pay for lookup and retention.

## Summary

A cached result is reusable only under a complete input/dependency equivalence rule. Distinguish misses from cached undefined, and decide whether promises—including failures—are retained. Capacity bounds memory; TTL limits reuse age but needs enforcement and ownership. Measure hits, computation saved and retained bytes before adding a cache.

# Memoization

The same search may be requested repeatedly for one tenant, query, and page. Reusing its result can save computation, but only if the cache key includes every input that changes the answer and the result is still fresh when reused.

```js
const cache = new Map();
function searchResults(tenant, query, page) {
  const key = JSON.stringify([tenant, query, page]);
  if (cache.has(key)) return cache.get(key); // Hit: skip the work
  const result = expensiveSearch(tenant, query, page); // Miss: compute once
  cache.set(key, result);
  return result;
}
```

## Definition

**Memoization** stores results under keys derived from function inputs and returns a stored result when an equivalent call occurs again. It trades computation for lookup work and retained memory.

> **Textbook Definition:** Memoization is a result-reuse technique in which a computation is associated with an input-derived key. Correct reuse requires the key to preserve the relevant input equivalence and the cache lifetime to respect changes in dependencies and result freshness.

## First Principles

A cache hit is correct only when the earlier result is interchangeable with this call's result. For a **pure function**, the same inputs always produce the same output, so a complete key is enough. If the function also depends on a clock, database, current user, locale, or mutable object, that dependency must be included or handled through invalidation. Reuse is worthwhile only when lookup, key construction, and retention cost less than recomputing.

## 1. A Hit Skips Work; a Miss Computes It Once

Fibonacci illustrates overlapping subproblems: naive recursion recomputes `fibonacci(n - 2)` across branches. The map stores each completed result, so one top-level call computes each smaller `n` once. This assumes a nonnegative integer small enough for Number precision and available stack; use BigInt or iteration when the numeric range or depth requires it.

```js
function fibonacci(n, cache = new Map()) {
  if (!Number.isSafeInteger(n) || n < 0) throw new RangeError('Expected a nonnegative safe integer');
  if (n < 2) return n;
  if (cache.has(n)) return cache.get(n);

  const result = fibonacci(n - 1, cache) + fibonacci(n - 2, cache);
  cache.set(n, result);
  return result;
}
```

For one call, this visits O(n) distinct inputs and retains O(n) results. Common runtimes give this integer-key example expected O(n) time, but the language does not promise exact O(1) access for every `Map` operation. The default cache is created per top-level call; a long-lived wrapper can share a cache across calls but also retains entries for the wrapper's lifetime. The bounded wrapper below owns the reusable memoization example; the closure chapter explains how its returned function retains cache bindings.

## 2. Choose a Key and a Retention Policy

The cache's equality rule must match the inputs' meaning. A `Map` keyed by an object uses object identity, so two separately created `{ id: 1 }` objects do not share an entry. `JSON.stringify(args)` is not a universal structural key: object property order can change the string, and values such as `undefined`, `NaN`, functions, and symbols can be omitted or rewritten. Prefer a domain key with an explicit data model.

This compact synchronous wrapper takes that key explicitly and caps entry count. It assumes a pure function and immutable or safely shared results; it does not forward a dynamic `this`, preserve overloads, or bound result bytes.

```js
function memoizeLRU(fn, keyOf, maxSize = 100) {
  if (!Number.isSafeInteger(maxSize) || maxSize < 1) throw new RangeError('Invalid capacity');
  const cache = new Map();
  return (...args) => {
    const key = keyOf(...args);
    if (cache.has(key)) {
      const value = cache.get(key);
      cache.delete(key);
      cache.set(key, value);
      return value;
    }
    const value = fn(...args); // A synchronous throw is not cached.
    if (cache.size === maxSize) cache.delete(cache.keys().next().value);
    cache.set(key, value);
    return value;
  };
}

const searchKey = (tenant, query, page) => JSON.stringify([tenant, query, page]);
```

For a search cache, include tenant, query, page, and any locale or data-version input that changes the response. Omitting the tenant can return another user's result; omitting a data version can return stale data. `Map.has()` distinguishes a cached `undefined` from a miss. An LRU bound limits entry count, not total bytes; variable-size values may need a byte budget.

## 3. Async Work Needs a Separate Failure Contract

If a function returns a promise, a cache stores that promise immediately. Concurrent callers can then share one in-flight operation. A rejected promise remains rejected in the cache unless the matching entry is evicted, so define whether failures are retried, briefly negative-cached, or retained. Eviction must not delete a newer promise for the same key. The [Promises chapter](../03-async-concurrency/10.1.3.02-promises.md) owns the complete single-flight implementation.

A time-to-live (TTL) determines how long an entry may be reused; it does not necessarily remove an expired entry from memory. A TTL cache that only checks an entry when it is read can retain cold expired keys indefinitely. Combine expiry with a capacity, periodic cleanup, or a shorter-lived owner. A `WeakMap` can associate metadata with object lifetimes, but it cannot be enumerated or used for deterministic expiry; see [Map and WeakMap](../04-memory-and-data/10.1.4.02-map-set-weakmap-weakset.md).

## 4. React Memoization Has a Render Contract

React's memoization APIs optimize specific render work; they are not a general persistent cache:

| API | Reuses | Reuse boundary |
| ----------------------- | ------------------- | ----------------------------------------------------------------------------------------- |
| `memo(Component)` | A component render | Parent update with equal props; the component's own state and context can still update it |
| `useMemo(fn, deps)` | A calculated value | A render where dependencies compare equal |
| `useCallback(fn, deps)` | A function identity | A render where dependencies compare equal |

Dependencies must include every reactive value read by the callback. Mutating an input in place can make an identity-based cache stale; recreating inputs every render can prevent hits. React may discard a memoized value, so correctness must not depend on the cache. See [useMemo and useCallback](../../10.3-react/02-core-hooks/10.3.2.03-usememo-usecallback.md) for React's exact lifecycle.

## 5. Measure Saved Work and Retained State

Measure representative inputs and track more than hit rate: compare computation time with key-construction and lookup cost, retained entry count/bytes, and invalidation behavior. A high hit rate can still lose when the original work is cheap or cached results are large. Remove the cache if its workload does not justify the retained state.

## Summary

Memoization is correct only when the key captures every dependency that changes the result and the entry remains fresh. Define capacity and expiry separately, decide how promise failures are evicted, and account for mutable cached results. Measure saved work against key and retention cost; React's memo APIs follow render-scoped rules rather than a general cache contract.

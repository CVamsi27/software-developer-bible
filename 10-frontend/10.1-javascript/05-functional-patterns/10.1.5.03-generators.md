# Generators

A report exporter may need to process millions of rows even when the caller stops after the first page. Building a complete array makes the producer finish before the caller can stop. A generator lets the consumer request work one step at a time.

```js
function* countTo(limit) {
  for (let n = 1; n <= limit; n++) yield n;
}

const iterator = countTo(3);
iterator.next(); // { value: 1, done: false }
iterator.next(); // { value: 2, done: false }
iterator.next(); // { value: 3, done: false }
iterator.next(); // { value: undefined, done: true }
```

## Definition

A **generator** is a resumable function, declared with `function*`, that can suspend at `yield` and continue on a later request. Calling it creates an iterator; each `next()` returns an object with a `value` and `done` flag.

> **Textbook Definition:** A generator is a suspended computation that retains its execution state across yield points. Its iterator follows the iterator protocol: `next` advances it, `return` requests completion, and `throw` injects an exception at the suspension point.

## First Principles

A pull-based iterator gives the consumer control over when the producer advances. This can prevent eager computation and unnecessary output storage. It is not full backpressure by itself: a producer can still buffer internally, each yielded value can be large, and an async step can be blocked on I/O. The producer and consumer must agree on a unit of work and how early termination is handled.

## 1. Follow a Generator Through One Request

The body does not run when `countTo(3)` is called. The first `next()` starts it and runs until `yield`; the next call resumes after that expression. After completion, later calls keep returning `done: true` (as the hook example shows).

A generator can also receive values. The value passed to the first `next(value)` is ignored because no `yield` is waiting yet; later values become the result of the suspended `yield` expression. TypeScript names the three data directions as `Generator<Yield, Return, Next>`. A `for...of` loop exposes yielded values but discards the generator's final return value.

```js
function* askName() {
  const name = yield 'What is your name?';
  return `Hello, ${name}`;
}

const prompt = askName();
prompt.next();          // { value: 'What is your name?', done: false }
prompt.next('Sam');     // { value: 'Hello, Sam', done: true }
```

## 2. Pull Async Pages and Stop Before the Next Request

An async generator makes each `next()` return a promise. Here a new page request starts only when the consumer asks for the next page. A page-number API needs a stable ordering to avoid duplicates or skips while records change; a cursor tied to a snapshot can provide a stronger traversal contract. The consumer snippet uses top-level `for await`, so run it as a module; the owning route controls the abort signal.

```js
async function* fetchPages(url, signal, maxPages = 1000) {
  if (!Number.isSafeInteger(maxPages) || maxPages < 1) throw new RangeError('Invalid page limit');
  const target = new URL(url);
  if (!['http:', 'https:'].includes(target.protocol)) throw new TypeError('Expected HTTP(S) URL');

  for (let page = 1; page <= maxPages; page++) {
    target.searchParams.set('page', String(page));
    const response = await fetch(target, { signal });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const rows = await response.json();
    if (!Array.isArray(rows)) throw new TypeError('Expected a page array');
    if (rows.length === 0) return;
    yield rows; // Validate each row before using it as application data.
  }
  throw new RangeError('Pagination exceeded maxPages; results may be incomplete');
}

const controller = new AbortController();
for await (const page of fetchPages('https://api.example.com/data', controller.signal)) {
  console.log(`${page.length} rows`); // Replace with the application's validated page handler.
}
// The route/component that owns this work calls controller.abort() on cleanup.
```

The explicit limit prevents an endless endpoint from running forever; reaching the cap reports possible truncation rather than silently claiming completion. Breaking from the loop stops future page requests. It does not cancel I/O already in progress, so pass an owner-controlled `AbortSignal` when pending work must stop. Iterator closure and network cancellation are separate operations.

## 3. Close Suspended Work When Its Owner Ends

A started generator's `return(value)` resumes it as if completion were requested at the suspended `yield`. A `finally` block can then release a lock or close a resource. `throw(error)` injects an exception at that suspension point; a surrounding `try/catch` may handle it. `yield* inner` delegates iteration and forwards control to the inner iterator. Before the first `next()`, the generator body and its `finally` have not run, so acquire resources inside the body or keep cleanup with the external owner.

A suspended generator retains its execution state and referenced local values while its iterator remains reachable. A `for...of` loop calls an available `return()` when it exits early through `break`, `return`, or a loop-body exception; `for await...of` awaits asynchronous iterator closure. Manual `next()` loops need their own `try/finally` and `return()` call. An error thrown by `next()` is a producer failure, not consumer-driven early closure, so cleanup that must run for both paths belongs in the generator's `finally` block.

Do not make essential cleanup depend on a `finally` block yielding another value: that delays completion until the consumer asks again. If an iterator owns a file, lock, subscription, or request, its caller must retain and close that iterator when the work is abandoned. For Node streams or database cursors, also use the host API's explicit destruction/cancellation contract where required.

## 4. Laziness Changes Production, Not Total Work

A generator can avoid building an output array. If it retains constant state and the consumer processes each value immediately, output storage can stay bounded as the sequence grows. It still performs the work for each requested value; a growing internal map or an accumulating consumer can still use O(n) memory. Measure the entire producer-consumer path.

## Summary

A generator is a pull-driven iterator that pauses at `yield` and resumes on `next`. Async generators can wait for work between steps, but do not cancel pending I/O by themselves. Define the yielded/final/sent value contract and close suspended work when its owner ends; laziness saves memory only when the rest of the pipeline also stays bounded.

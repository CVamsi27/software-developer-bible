# Recursion and Tail Calls

A tree is naturally recursive: each node contains smaller child trees. But if an input controls tree depth, a clear recursive traversal can exceed the runtime's call-stack limit before it finishes. Choose recursion with both the data shape and depth contract in mind.

## Definition

**Recursion** is a computation that solves a problem by calling itself on smaller subproblems. A terminating recursive function needs a **base case** and progress toward that case. A **tail call** is a call made from a tail position, where the caller has no further work after the callee returns.

> **Textbook Definition:** A recursive computation is defined in terms of smaller instances of itself or mutually recursive functions. In a proper tail call, the caller's continuation is not retained; an implementation that provides proper tail-call semantics can execute qualifying calls with constant call-stack space.

## First Principles

A recursive call normally needs its caller's pending state so execution can continue after the child returns. A tail call has no such continuation, so a proper tail-call implementation can reuse or release the caller's execution context. This can reduce stack growth, but recursion still needs a valid base case, work for each step, and memory for any data it deliberately retains.

## Trace the pending work

In the ordinary factorial, multiplication remains after the recursive call, so each caller must wait with its `n` on the stack:

```js
function factorial(n) {
  if (!Number.isSafeInteger(n) || n < 0) throw new RangeError('Expected a nonnegative safe integer');
  if (n === 0) return 1;
  return n * factorial(n - 1); // multiply after the child returns
}
```

An accumulator moves that multiplication before the call. The recursive call is now in tail position:

```js
'use strict';
function factorialTail(n, product = 1) {
  if (!Number.isSafeInteger(n) || n < 0) throw new RangeError('Expected a nonnegative safe integer');
  if (n === 0) return product;
  return factorialTail(n - 1, product * n);
}
```

This form illustrates tail position; it does not make deep recursion safe in every JavaScript runtime. It also inherits Number precision limits and can produce `Infinity` for large factorials. Each function validates the domain so every recursive step approaches its base case.

## What JavaScript guarantees—and what portable code should do

ECMAScript specifies **proper tail calls (PTC)** for qualifying tail positions in strict-mode code. The specification requires the caller's transient execution resources to be released or reused before the callee runs. This is stronger than an optional speed optimization. In engines that implement PTC, stack traces also omit discarded caller frames.

Implementation support differs, so code that runs across JavaScript engines must not rely on tail position alone to prevent stack overflow. Verify the exact supported runtimes if the guarantee matters. For unbounded depth, an explicit loop or work stack is the portable choice; a trampoline can preserve a recursive-looking interface by returning deferred steps to a loop, but adds allocations and is usually less direct than iteration.

## Use a work stack for untrusted depth

A recursive tree walk follows the data shape closely. If the input can be cyclic or contain shared nodes, define whether to visit each identity once; a tree assumption does not hold for an arbitrary graph.

```js
function walkTree(root, visit) {
  const stack = [root];
  const seen = new WeakSet();

  while (stack.length) {
    const node = stack.pop();
    if (seen.has(node)) continue;
    seen.add(node);
    visit(node);
    for (let i = node.children.length - 1; i >= 0; i--) {
      stack.push(node.children[i]);
    }
  }
}
```

Assume every node is an object with a `children` array. The explicit stack moves depth from the JavaScript call stack into application-managed storage, where you can set a limit or report an input error. This example visits each reachable node once in O(V + E) time and retains O(V) identities; its stack strongly retains queued nodes until they are processed.

Recursion remains useful when depth is bounded and the call structure clarifies the proof—for example, binary search over a sorted array uses O(log n) depth. Overlapping subproblems such as naive Fibonacci need memoization or an iterative dynamic program to avoid repeated work; memoization improves time, not maximum recursion depth. See [Memoization](10.1.5.02-memoization.md).

## Summary

Recursion mirrors nested problems, but ordinary calls retain pending caller state and can exhaust the stack. Tail position enables constant-stack execution only where the runtime provides ECMAScript proper-tail-call behavior. Validate progress and input depth; use iteration or an explicit work stack for unbounded input, and memoization only when subproblems repeat.

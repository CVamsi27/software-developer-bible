# Web Workers

> **Dedicated and Shared Workers, OffscreenCanvas, and CPU-intensive task delegation in the browser.**

## TL;DR

- Workers run JS on a **separate thread with its own heap and event loop** — heavy computation stops freezing the UI (→ 10.1.3.01's one-stack rule is the problem they solve).
- They **can't touch the DOM**; all communication is `postMessage` (structured clone) or transferables (ownership handoff) — the message boundary *is* the concurrency model.
- Use for **CPU-bound work only** (parsing, crypto, image processing); I/O belongs to `fetch` + the event loop. Always `terminate()` on teardown.

---

## First Principles

Workers exist because the one-stack rule creates one specific wall:

1. **Heavy computation starves the UI** — the single stack cannot run a 300 ms parse loop and paint frames at once (→ 10.1.1.03, 10.1.3.01). Parallelism is the only fix, so the platform spawns *whole separate stacks*: new heaps, new event loops, own globals.
2. **Separate heaps force message-passing.** No shared objects means workers communicate only by structured-clone (copy) or transferables (ownership handoff). That's not an implementation detail — it's the entire concurrency model, and it's why workers can't share mutations and thus can't share most bugs.
3. **Isolation dictates the boundary of use**: DOM access stays on the main thread (the DOM is single-owner by design), so workers are for pure computation — parsing, crypto, image processing, search. Everything that touches the UI crosses the boundary via messages, and that crossing is the cost to design around.

## Definition

A **Web Worker** is a browser-provided thread that runs a script in a separate global scope — its own heap, its own event loop, no access to the DOM or the creating page's variables. The main thread and the worker exchange data exclusively through asynchronous messages: `postMessage()` serializes (structured clone) or transfers (ownership handoff) values across the boundary.

## Why It Matters

JavaScript runs on a single thread. A long-running computation (image processing, data transformation, encryption) blocks the main thread, freezing the UI.

```
Main Thread:
User Click → Heavy Computation (200ms) → UI Frozen → Frame Drops →

With Web Worker:
User Click → Post to Worker → Worker Computes (200ms) → Post Result → UI Fluid →
```

The 16 ms frame budget (→ 50.3.1.01) is the economics: any task longer than one frame steals paint time and shows up as jank. Workers move the budget-buster to a thread paints don't depend on.

## Types of Workers

| Type | Scope | Communication | Use Case |
| -------------------- | ---------------- | ------------------ | -------------------------------------------- |
| **Dedicated Worker** | One client (tab) | Message passing | Heavy computation, data processing |
| **Shared Worker** | Multiple tabs | Message passing | Cross-tab state, shared connections |
| **Service Worker** | Entire origin | Intercept requests | Offline support, caching, push notifications |

## Dedicated Worker

### Creating a Worker

```typescript
// worker.ts — runs in its own thread
self.onmessage = (event: MessageEvent) => {
  const { numbers } = event.data;

  // Heavy computation — doesn't block main thread
  const result = numbers.reduce((acc, n) => {
    // Simulate heavy work
    let sum = 0;
    for (let i = 0; i < 1000000; i++) {
      sum += Math.sqrt(n * i);
    }
    return acc + sum;
  }, 0);

  self.postMessage({ result });
};

// main.ts — runs on main thread
const worker = new Worker(new URL('./worker.ts', import.meta.url), {
  type: 'module',
});

// Send data to worker
worker.postMessage({ numbers: [1, 2, 3, 4, 5] });

// Receive result from worker
worker.onmessage = (event) => {
  console.log('Result:', event.data.result);
  // Update UI
  document.getElementById('result')!.textContent = event.data.result;
};

// Error handling
worker.onerror = (error) => {
  console.error('Worker error:', error.message);
};

// Terminate when done
worker.terminate();
```

### React Integration

```typescript
// hooks/useWorker.ts
import { useEffect, useRef, useState } from 'react';

export function useWorker<TInput, TOutput>(
  workerFactory: () => Worker,
  input: TInput | null
): { result: TOutput | null; loading: boolean; error: Error | null } {
  const workerRef = useRef<Worker | null>(null);
  const [result, setResult] = useState<TOutput | null>(null);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    if (input === null) return;

    const worker = workerFactory();
    workerRef.current = worker;

    setLoading(true);
    worker.postMessage(input);

    worker.onmessage = (e) => {
      setResult(e.data);
      setLoading(false);
    };

    worker.onerror = (e) => {
      setError(new Error(e.message));
      setLoading(false);
    };

    return () => worker.terminate();
  }, [input]);

  return { result, loading, error };
}

// Usage in component
function DataProcessor({ rawData }: { rawData: number[] }) {
  const { result, loading, error } = useWorker(
    () => new Worker(new URL('./processor.worker.ts', import.meta.url)),
    rawData
  );

  if (loading) return <Spinner />;
  if (error) return <Error message={error.message} />;
  return <div>Processed: {result}</div>;
}
```

### Transferables — Zero-Copy Handoff

Structured clone *copies* data across the boundary; for large ArrayBuffers that copy is the new bottleneck. Transferables move ownership instead — the buffer arrives without being copied, and the sender loses access:

```typescript
// main.ts — parse a 100 MB CSV without copying its bytes
const response = await fetch('/big.csv');
const buffer = await response.arrayBuffer();

worker.postMessage({ buffer }, [buffer]); // transferred, not cloned
// buffer.byteLength is now 0 on the main thread — ownership moved

// worker.ts
self.onmessage = (event) => {
  const text = new TextDecoder().decode(event.data.buffer);
  const parsed = parseCSV(text);
  self.postMessage(parsed);
};
```

Rule of thumb: clone small structured data; transfer big buffers. Returning the buffer to the main thread works the same way in reverse.

## Shared Worker

Shared Workers run across multiple tabs, enabling cross-tab communication.

```typescript
// shared-worker.ts
const connections = new Set<MessagePort>();

self.onconnect = (event: MessageEvent) => {
  const port = event.ports[0];
  connections.add(port);

  port.onmessage = (msg) => {
    // Broadcast to all connected tabs
    connections.forEach((conn) => {
      conn.postMessage(msg.data);
    });
  };

  port.start();
};

// main.ts (in each tab)
const worker = new SharedWorker(new URL('./shared-worker.ts', import.meta.url));
worker.port.start();

// Send to all tabs
worker.port.postMessage({ type: 'user-updated', userId: '123' });

// Receive from other tabs
worker.port.onmessage = (event) => {
  if (event.data.type === 'user-updated') {
    refreshUserProfile(event.data.userId);
  }
};
```

## OffscreenCanvas

OffscreenCanvas allows rendering in a Web Worker — useful for complex visualizations without blocking UI.

```typescript
// worker.ts
const canvas = new OffscreenCanvas(800, 600);
const ctx = canvas.getContext('2d')!;

self.onmessage = (event) => {
  const { frame } = event.data;

  // Render frame offscreen
  ctx.clearRect(0, 0, 800, 600);
  ctx.fillStyle = `hsl(${frame % 360}, 70%, 50%)`;
  ctx.fillRect(100, 100, 200, 200);

  // Transfer bitmap to main thread
  const bitmap = canvas.transferToImageBitmap();
  self.postMessage({ bitmap }, [bitmap]);
};

// main.ts
const canvas = document.getElementById('canvas') as HTMLCanvasElement;
const ctx = canvas.getContext('2d')!;
const worker = new Worker(new URL('./worker.ts', import.meta.url));

let frame = 0;
function animate() {
  worker.postMessage({ frame: frame++ });
  requestAnimationFrame(animate);
}

worker.onmessage = (event) => {
  ctx.drawImage(event.data.bitmap, 0, 0);
};

animate();
```

## When to Use Workers

| Task | Use Worker? | Why |
| ------------------------ | ----------- | ------------------------------------- |
| Image resize/compress | Yes | CPU-intensive, blocks main thread |
| CSV/JSON parsing (large) | Yes | Blocks main thread for seconds |
| Encryption/decryption | Yes | CPU-intensive |
| Complex calculations | Yes | Physics, math, data science |
| Simple DOM manipulation | No | Needs access to DOM (worker can't) |
| API calls | No | Network-bound, not CPU-bound |
| Simple string operations | No | Overhead of worker setup not worth it |

---

## Interview Questions

**Q: "When would you use a Web Worker in a frontend application?"**

> When you have CPU-intensive tasks that would block the main thread and cause UI jank: image processing (resize before upload), large CSV/JSON parsing (100MB+), client-side search with scoring, cryptographic operations, or complex calculations (spreadsheet formulas). The pattern: create a Worker, post data, receive result via onmessage. Workers can't access the DOM, so all UI updates happen on the main thread after receiving the result.

---

## 30-Second Interview Version

> Web Workers run JavaScript on a separate thread, preventing UI freezes during heavy computation. Dedicated workers serve one tab (image processing, data parsing). Shared workers serve multiple tabs (cross-tab state). OffscreenCanvas enables off-thread rendering. Workers can't access the DOM — communicate via postMessage/onmessage. Use for CPU-intensive tasks (not I/O). In React, wrap in a custom hook with cleanup (worker.terminate on unmount).

## Common Mistakes

1. **Moving I/O to workers** — `fetch` is already async and off the UI path (→ 10.1.3.01); a worker adds message overhead for zero gain. Workers are for *CPU*-bound work, not network work.
2. **Spawning a worker per task** — worker startup costs ~1–40 ms plus script evaluation. For many small tasks, keep a pool (or a single worker with a request queue) and amortize the startup.
3. **Sending DOM nodes or functions through `postMessage`** — structured clone rejects them with a `DataCloneError`. Pass plain data; rebuild DOM on the main thread from the result.
4. **Leaking workers** — a worker that outlives its component holds a thread and its heap. Terminate on teardown (the `useWorker` hook above does it in the effect cleanup).
5. **Assuming shared state** — there is none. Messages from the main thread arrive in order, but results interleave with the worker's own messages; design the protocol as request/response with IDs, not as shared variables.

## Best Practices

- **Pool, don't spawn**: one worker (or `navigator.hardwareConcurrency` workers) reused across tasks beats create/terminate cycles.
- **Transfer, don't clone, big buffers**: `postMessage(buf, [buf])` for ArrayBuffers over ~1 MB.
- **Use Comlink for ergonomics**: `Comlink.wrap`/`Comlink.expose` turn the message protocol into async RPC — same semantics, far less plumbing.
- **Module workers by default**: `new Worker(url, { type: 'module' })` — imports work, and it's the format bundlers target.
- **Feature-detect OffscreenCanvas** (`typeof OffscreenCanvas !== 'undefined'`) and fall back to main-thread rendering.

## Summary

1. **Workers move CPU-heavy work off the main thread** — no DOM access, communicate via `postMessage` and structured clone
2. **Transferables move buffers without copying** — `postMessage(buf, [buf])` for large ArrayBuffers
3. **OffscreenCanvas unlocks rendering in workers** — charts and image processing without jank
4. **Comlink turns postMessage into RPC** — `Comlink.wrap`/`expose` hide the message plumbing
5. **Always `terminate()` on teardown** — a leaked worker leaks memory and a core; wrap in a hook with cleanup

## Cheat Sheet

```text
CREATE      new Worker(new URL('./w.ts', import.meta.url), { type: 'module' })
SEND        worker.postMessage(data)            // structured clone
            worker.postMessage(buf, [buf])      // transfer ownership (zero-copy)
RECEIVE     worker.onmessage = (e) => ...       // e.data is the payload
ERRORS      worker.onerror = (e) => e.message
TEARDOWN    worker.terminate()                  // on unmount / route change
KINDS       Dedicated = 1 tab | Shared = many tabs | Service = origin (offline/cache)
CAN'T       DOM access, window, functions in messages
USE FOR     parse, crypto, image/video, search, physics — CPU-bound only
SKIP FOR    fetch, timers, UI updates — event loop already handles these
```

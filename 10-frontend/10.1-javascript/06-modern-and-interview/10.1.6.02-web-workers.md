# Web Workers

A large client-side calculation can freeze input and painting even when the result arrives quickly. Moving the calculation to a worker gives it another JavaScript execution agent; it does not move a closure or DOM node. The page and worker need a message protocol that says who owns each request and result.

## Definition

A web worker runs JavaScript in a separate environment from its creating page. It cannot directly use that page's DOM or local variables. The contexts communicate through messages: structured cloning creates independent supported data, transfer moves ownership of supported resources, and `SharedArrayBuffer` explicitly shares bytes under synchronization rules.

> **Textbook Definition:** A web worker is a browser-managed execution context that runs script outside the page's main JavaScript agent and exchanges data with other contexts through message ports or explicitly shared memory.

## First Principles

1. **Synchronous JavaScript occupies its agent.** While the page runs a long calculation, it cannot process another input handler. A worker can run suitable computation independently, but its startup, data transfer, CPU use, and final DOM updates still cost time.
2. **Messages cross an ownership boundary.** Send plain request data and a request identifier. When a reply arrives, accept it only if that request still owns the visible result.
3. **Cancellation needs cooperation.** A worker cannot receive a cancel message while blocked in one long synchronous loop. Chunk and yield the work, check a cancellation flag between chunks, or `terminate` a dedicated worker when all of its work should stop.

At 60 Hz a refresh interval is about 16.7 ms, but devices and workloads have different budgets. Measure the main-thread task and transfer cost first. Network I/O and APIs already scheduled by the browser do not become faster just because a worker waits for them.

## Pick a worker by its owner

| Kind | Owner and lifetime | Use it for |
| ---------------- | ------------------------------------------------------------------------------- | ------------------------------------------------- |
| Dedicated worker | One creator owns the Worker object and can `terminate` it | Per-page computation or a background pipeline |
| Shared worker | Eligible clients connect through separate `MessagePort`s to one worker instance | A live service such as one shared socket or cache |
| Service worker | The browser starts it for eligible events and may stop it between events | Request interception, offline behavior, and push |

When a page listens to a shared worker port with `addEventListener`, call `port.start()`; assigning `port.onmessage` starts delivery implicitly. A shared worker is not durable storage; persist anything that must survive all clients closing. A service worker is event-driven, not an always-running session thread. Its install, activation, control, and cache lifecycle belongs in the [PWA chapter](../../10.7-html-css/10.7.05-pwa.md).

## Trace one request and its reply

The example uses a Vite module worker. The worker accepts only finite numbers and includes the request ID even in a validation error, so the page can match each reply to its owner.

~~~typescript
// sum.worker.ts
/// <reference lib="webworker" />
export {};
const scope = self as DedicatedWorkerGlobalScope;

scope.onmessage = (event: MessageEvent<unknown>) => {
  const value = event.data;
  if (typeof value !== "object" || value === null ||
      !("id" in value) || !Number.isSafeInteger(value.id) ||
      !("values" in value) || !Array.isArray(value.values)) return;

  const id = value.id as number;
  if (!value.values.every(item => typeof item === "number" && Number.isFinite(item))) {
    scope.postMessage({ id, error: "Expected finite numbers" });
    return;
  }

  const result = (value.values as number[]).reduce((sum, item) => sum + item, 0);
  if (!Number.isFinite(result)) {
    scope.postMessage({ id, error: "Sum overflowed" });
    return;
  }
  scope.postMessage({ id, result });
};
~~~

~~~typescript
// main.ts
const worker = new Worker(new URL("./sum.worker.ts", import.meta.url), { type: "module" });
let currentId = 0;
function publishResult(value: number): void { console.log("sum", value); }
function showError(message: string): void { console.error(message); }

function calculate(values: number[]): void {
  const id = ++currentId;
  worker.postMessage({ id, values });
}

worker.onmessage = (event: MessageEvent<unknown>) => {
  const reply = event.data;
  if (typeof reply !== "object" || reply === null ||
      !("id" in reply) || reply.id !== currentId) return; // stale request
  if ("result" in reply && typeof reply.result === "number" && Number.isFinite(reply.result)) {
    publishResult(reply.result);
  } else if ("error" in reply && typeof reply.error === "string") {
    showError(reply.error);
  }
};
worker.onerror = event => showError(event.message || "Worker failed");
worker.onmessageerror = () => showError("Could not decode worker reply");

function dispose(): void {
  worker.terminate();
}
~~~

The receiving page should also validate the reply shape and result type before using it; that check is shortened here to keep the ownership trace visible. If several requests can be queued, bound the queue and define whether new input replaces, waits for, or cancels older work. A React component should create and clean up its worker in an effect, not during render; use a reusable worker or pool when requests are frequent.

## Choose how data crosses the boundary

Structured cloning handles supported data types and cycles, but it creates a separate object graph in the receiving context; functions and DOM nodes cannot be cloned and cause `DataCloneError`. A transferred `ArrayBuffer` instead detaches the sender's buffer and moves its usable ownership:

~~~javascript
const bytes = new Uint8Array([10, 20, 30]);
worker.postMessage(bytes.buffer, [bytes.buffer]);
console.log(bytes.byteLength); // 0: the sender's view is detached
~~~

List the resource in the message and in the transfer list. Transferring a shared backing buffer affects every sender-side view of it. The specification defines observable ownership, not whether an engine physically copies the bytes. `SharedArrayBuffer` is different: both agents can observe shared bytes, so the design must use Atomics and the browser's required isolation policy.

For a `SharedWorker`, each page gets its own port. The worker must route a reply to its requesting port or deliberately broadcast to tracked ports; it also needs a policy for ports that disappear. For a service worker, keep required work inside the event lifetime and store state that must survive termination.

`OffscreenCanvas` can move drawing work to a worker. A page can transfer control of its visible canvas to the worker, or the worker can draw to an independent `OffscreenCanvas` and transfer `ImageBitmap`s back; sizing, queued frames, lifecycle, and final presentation still need owners. Bound frames in flight and close transferred `ImageBitmap`s after use. See the [canvas chapter](../../10.6-animation/10.6.07-canvas-svg-animation.md) for a complete render loop.

## Decide whether the move pays off

Workers fit substantial parsing, indexing, image processing, or numerical work when measurement shows that moving it reduces the page's main-thread task. An asynchronous fetch alone usually does not need a worker. Start with a reusable worker rather than creating one for every small request; measure startup, transfer, compute, and presentation, and add a pool only when throughput justifies CPU contention. `hardwareConcurrency` is a capacity hint, not an instruction to occupy every logical processor.

## Summary

A worker gives suitable computation a separate execution agent. Design request ownership, validation, stale-result handling, cancellation, and teardown at the message boundary. Cloning, transfer, and shared memory have different identity and ownership rules; none guarantees a frame rate or cancels remote effects.

# Web Workers

> **Dedicated and Shared Workers, OffscreenCanvas, and CPU-intensive task delegation in the browser.**

## Definition

A **Web Worker** runs JavaScript separately from the browser page, with its own global environment. It cannot directly access the page's DOM or local variables. The page and worker exchange messages. Ordinary message data is copied by structured cloning; supported resources can instead be transferred so ownership moves to the receiver. Shared memory is a separate feature you must choose explicitly. Ordinary objects are not automatically shared.

> **Textbook Definition:** A web worker executes script in a separate worker environment and communicates with other contexts through messages. Structured cloning, ownership transfer and explicitly shared memory provide different data-exchange semantics.

## First Principles

1. **A long synchronous calculation occupies its agent.** Main-thread JavaScript cannot process another input callback while that calculation runs. Reduce the calculation, split it into yielding tasks, or move suitable work to another agent.
2. **Moving work also moves ownership.** The worker cannot read a page variable directly. Send a request with an ID and data, then match its result to the request that still owns the UI.
3. **Parallel work still consumes resources.** Startup, serialization, memory and CPU contention can outweigh a small calculation. Worker results still need main-thread DOM work, so moving computation does not guarantee a frame rate.

## Trace a calculation across the boundary

For a slow calculation, measure both the calculation and the transfer. The intended sequence is:

```text
page: input → send {id, values} → return to input handling
worker: receive → validate → calculate → send {id, result}
page: receive → check current owner → publish result
```

At 60 Hz a frame interval is about 16.7 ms, but refresh rates and available work budgets vary. A worker reduces the main-thread calculation on this path; it does not reserve a core or guarantee a paint deadline. Async APIs such as Web Crypto may already use native work scheduling, so assess the actual bottleneck before adding a worker.

## Dedicated, shared and service workers serve different owners

| Kind | Owner and lifetime | Main purpose |
| ---------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Dedicated worker | Created by one client, which owns its termination | Offload computation or own a background pipeline |
| Shared worker | Eligible same-origin clients connect through ports; identity includes script/name and browser partition rules | Share state/connections across compatible contexts |
| Service worker | Browser-managed registration with a scope; starts for events and may stop between them | Intercept eligible requests, offline behavior and push |

A dedicated worker may itself be created by another worker. A service worker is not an always-running thread for an entire origin; [PWA architecture](../../10.7-html-css/10.7.05-pwa.md) owns its lifecycle and cache behavior.

## A complete Vite module-worker request

Save this as `sum.worker.ts`. Its protocol accepts finite numeric arrays and echoes the request ID. Compile worker files with the WebWorker library rather than relying on the page's Window declarations.

```typescript
/// <reference lib="webworker" />
export {};
const workerScope = self as DedicatedWorkerGlobalScope;
workerScope.onmessage = (event: MessageEvent<unknown>) => {
  const data = event.data;
  if (typeof data !== "object" || data === null ||
      !("id" in data) || !Number.isSafeInteger(data.id) ||
      !("values" in data) || !Array.isArray(data.values) ||
      !data.values.every(value => typeof value === "number" && Number.isFinite(value))) {
    workerScope.postMessage({ error: "Invalid sum request" });
    return;
  }
  let total = 0;
  for (const value of data.values) total += value;
  if (!Number.isFinite(total)) {
    workerScope.postMessage({ id: data.id, error: "Sum overflowed" });
    return;
  }
  workerScope.postMessage({ id: data.id, result: total });
};
```

Save this beside it as `main.ts` in a Vite browser entry. A new request supersedes the previous visible result; the worker may still calculate both. Termination belongs to page teardown, not the line immediately after posting work.

```typescript
let currentId = 0;
const worker = new Worker(new URL("./sum.worker.ts", import.meta.url), { type: "module" });
const result = document.createElement("p");
result.setAttribute("role", "status");
document.body.append(result);
worker.onmessage = (event: MessageEvent<unknown>) => {
  const data = event.data;
  if (typeof data !== "object" || data === null ||
      !("id" in data) || data.id !== currentId) return;
  if ("result" in data && typeof data.result === "number") {
    result.textContent = `Sum: ${data.result}`;
  } else if ("error" in data && typeof data.error === "string") {
    result.textContent = data.error;
  }
};
worker.onerror = event => { result.textContent = `Worker failed: ${event.message}`; };
worker.onmessageerror = () => { result.textContent = "Could not decode worker response"; };
function calculate(values: number[]) {
  currentId += 1;
  result.textContent = "Calculating…";
  try { worker.postMessage({ id: currentId, values }); }
  catch (error) { result.textContent = error instanceof Error ? error.message : "Could not send request"; }
}
calculate([1, 2, 3]); // Sum: 6 once the response arrives.
window.addEventListener("pagehide", () => worker.terminate(), { once: true });
```

The tiny array demonstrates the protocol; it is too small to justify a worker for performance. For larger workloads, bound input size and queued requests. Ignoring a stale result protects UI ownership but does not cancel its computation. A cancellation message cannot interrupt a worker that is blocked in one synchronous loop; chunk/yield inside it or terminate a dedicated worker when stopping all its work is acceptable. Coordinate `pageshow` re-creation if a page may resume from the back-forward cache after teardown.

## React owns a worker through an effect

This complete component uses the same worker file. It deliberately creates a dedicated worker for each input lifetime; a stable factory/pooled protocol is more appropriate for frequent tiny requests. Keep the input reference stable when its content has not changed.

```tsx
import { useEffect, useState } from "react";
type Result = { input: readonly number[]; value?: number; error?: string };
export function WorkerSum({ values }: { values: readonly number[] }) {
  const [result, setResult] = useState<Result | null>(null);
  useEffect(() => {
    let active = true;
    let worker: Worker | undefined;
    const fail = (message: string) => {
      if (active) setResult({ input: values, error: message });
      worker?.terminate();
    };
    try {
      worker = new Worker(new URL("./sum.worker.ts", import.meta.url), { type: "module" });
      worker.onmessage = (event: MessageEvent<unknown>) => {
        if (!active) return;
        const data = event.data;
        if (typeof data !== "object" || data === null || !("id" in data) || data.id !== 1) {
          fail("Invalid worker response"); return;
        }
        if ("result" in data && typeof data.result === "number" && Number.isFinite(data.result)) {
          setResult({ input: values, value: data.result });
          worker?.terminate();
        } else if ("error" in data && typeof data.error === "string") fail(data.error);
        else fail("Invalid worker response");
      };
      worker.onerror = event => fail(event.message || "Worker failed");
      worker.onmessageerror = () => fail("Could not decode worker response");
      worker.postMessage({ id: 1, values });
    } catch (error) { fail(error instanceof Error ? error.message : "Could not start worker"); }
    return () => { active = false; worker?.terminate(); };
  }, [values]);
  if (result?.input !== values) return <p role="status">Calculating…</p>;
  if (result.error) return <p role="alert">{result.error}</p>;
  return <p>Sum: {result.value}</p>;
}
```

On an input change, old cleanup disables publication and terminates its worker. The render also checks which input owns the stored result, so an old answer is never presented as the new input's answer while the new effect starts. Development Strict Mode can repeat setup/cleanup; this ownership is symmetric.

## Transfer a buffer when the sender can give it up

```javascript
const worker = new Worker(new URL("./buffer.worker.js", import.meta.url), { type: "module" });
const buffer = new Uint8Array([10, 20, 30]).buffer;
worker.onmessage = event => {
  console.log(event.data); // 60
  worker.terminate();
};
worker.onerror = () => worker.terminate();
worker.postMessage(buffer, [buffer]);
console.log(buffer.byteLength); // 0: sender's buffer is detached.
```

Save the recipient as `buffer.worker.js`:

```javascript
self.onmessage = event => {
  const bytes = new Uint8Array(event.data);
  self.postMessage(bytes.reduce((sum, value) => sum + value, 0));
};
```

Transfer changes ownership and detaches the sender; the specification does not guarantee a physical zero-copy implementation. The resource must appear in the message as well as its transfer list. Transfer the underlying buffer of a typed-array view, not the view itself, and remember that this can detach other views sharing that buffer.

Ordinary cloned objects have distinct identities across agents. `SharedArrayBuffer` instead lets agents observe shared bytes in permitted, typically cross-origin-isolated browser contexts. That needs synchronization through Atomics and a carefully designed memory protocol; it does not share arbitrary objects or DOM nodes.

## A SharedWorker needs port lifecycle ownership

The connecting page uses `new SharedWorker(url, { type: "module" })`, registers a handler on `worker.port` and calls `port.start()` when using event listeners. The worker's `connect` event supplies a `MessagePort` for that client.

A broadcast owner may keep a Set of ports and forward messages to each. It must also process explicit disconnect messages, close/remove disconnected ports and bound clients/queued data. Unexpected tab termination may not deliver that message, so robust ownership may need heartbeat/expiry or another protocol. Merely adding every port forever to a Set is not a complete lifecycle.

For simple cross-tab invalidation without a shared computation owner, use [BroadcastChannel](10.1.6.04-cross-tab-communication.md). Neither worker messaging nor channel delivery authorizes a server write.

## OffscreenCanvas moves canvas work, not all rendering work

Two approaches have different owners:

- Transfer a visible canvas with `transferControlToOffscreen()` before getting a context, then transfer that OffscreenCanvas to the worker. The worker draws into it; size changes, device-pixel ratio and lifecycle remain explicit messages.
- Draw into an independent OffscreenCanvas and transfer ImageBitmaps back. The page displays them and closes each bitmap after use. Permit at most a bounded number of frames in flight; posting a new frame every rAF while the worker falls behind creates a growing queue.

Feature-detect the required API/context, provide a main-thread alternative and stop scheduling work on teardown. Graphics, message transfer and final presentation still have costs. See the complete [Canvas lifecycle example](../../10.6-animation/10.6.07-canvas-svg-animation.md) for frame scheduling, resize and disposal.

## Decide by measured work and ownership

Move substantial parsing, indexing, image processing or numerical work when the transfer/startup cost earns its keep. Network calls alone are already asynchronous; a worker can still own a network-plus-processing pipeline, but moving an unchanged fetch does not inherently improve responsiveness.

Start with one reusable worker where appropriate, then measure any pool. `navigator.hardwareConcurrency` is a coarse reported capacity hint, not permission to saturate every CPU. Comlink can wrap message exchange as asynchronous RPC, but lifetime, transfer, cancellation and errors remain part of the protocol. Worker scripts and libraries must be compatible with worker globals and the deployed bundler/runtime.

## Summary

Workers give suitable computation a separate execution agent. Design the message, ownership, stale-result and teardown contract first; then measure startup, transfer, calculation and presentation. Cloning, transfer and shared memory have different identity rules, and none guarantees a frame rate or a remote rollback.

# DOM Events & Delegation

A table can gain rows after it renders. If every button owns its own listener, each insertion and removal must also manage event wiring. A listener on the stable table body can handle both existing and future rows because a click travels through the DOM event path.

```js
tbody.addEventListener('click', (event) => {
  const button = event.target.closest('button[data-action]');
  if (!button || !tbody.contains(button)) return;
  console.log(button.dataset.action); // works for rows added later, too
});
```

## Definition

A DOM event is dispatched along a path through nodes in a document. Listeners may run during **capture**, at the **target**, and during **bubbling** when that event bubbles. **Event delegation** places a listener on a stable ancestor and identifies the relevant descendant from the event.

> **Textbook Definition:** DOM event dispatch invokes listeners on an event path during capture, target, and eligible bubbling phases. Event delegation handles descendant events through a listener registered on an ancestor.

```text
capture: window → document → table → button
at target: capture listeners, then non-capture listeners
bubble: button → table → document → window  (when the event bubbles)
```

## First Principles

Delegation works because an event travels from a changing child to a stable ancestor — a listener only sees events that reach its node. The target may be nested inside the control (an icon inside a button), so the handler must resolve the intended action and verify it belongs to the delegated root. One listener then serves many descendants, and its owner must remove it when the root or feature goes away.

## How It Works

### 1. Trace One Click from the Child to the Owner

For a click inside an icon within a row button, the event starts at the clicked node and bubbles to the table body. The body uses `closest` to find the button, then checks that the match belongs to its own subtree before acting.

```typescript
function delegateRowActions(tbody: HTMLTableSectionElement): () => void {
  const lifetime = new AbortController();
  tbody.addEventListener("click", event => {
    if (!(event.target instanceof Element)) return;
    const button = event.target.closest<HTMLButtonElement>("button[data-action]");
    if (!button || !tbody.contains(button)) return;

    const row = button.closest<HTMLTableRowElement>("tr[data-id]");
    const action = button.dataset.action;
    const id = row?.dataset.id;
    if (!row || !tbody.contains(row) || !id) return;
    if (action === "edit") editRow(id);
    else if (action === "delete") deleteRow(id);
  }, { signal: lifetime.signal });

  return () => lifetime.abort();
}
```

The containment check prevents an unrelated matching ancestor from being treated as a row action. Dataset values are input: validate them and enforce authorization in the application or server. Delegation reduces per-child setup; it does not make an invalid action safe.

### 2. Read the Event at the Listener That Owns It

The event's path determines order. Ancestor capture listeners run before the target. At the target, capture listeners run before non-capture listeners. Eligible bubbling then visits ancestors on the way out. An event that does not bubble can still be observed during capture.

- **target** identifies the dispatch target as exposed at that point in the path. Shadow DOM can retarget it across a boundary; use composedPath when the component contract needs the visible path.
- **currentTarget** identifies the object whose listener is running. Save what you need inside the handler: it returns to null after dispatch and is not a persistent event reference for later async work.
- `closest(selector)` walks from the target toward its ancestors. It does not cross into a different shadow tree, so component boundaries may need an explicit event or public method.

Common non-bubbling events include focus and blur; listen in capture or use `focusin`/`focusout` when bubbling behavior is needed. React exposes `onFocus` through its own event system, which can bubble through the React tree. Event behavior can differ by event type, so verify the event contract instead of assuming every interaction bubbles.

### 3. Keep Propagation, Default Action, and Passivity Distinct

Propagation controls which listeners observe the event; the browser's default action (link navigation, form submission) is separate.

| Operation | Effect |
| ---------------------------- | --------------------------------------------------------------------------------------------------- |
| `preventDefault()` | Cancels a cancelable default action when the listener is not passive. It does not stop propagation. |
| `stopPropagation()` | Prevents later path steps. Other listeners at the current node can still run. |
| `stopImmediatePropagation()` | Also stops remaining listeners in the current invocation. |

An ancestor capture listener can observe an event before target and bubbling handlers run, but an earlier capture listener may still stop propagation. A passive listener promises not to call `preventDefault`. For cancelable wheel or touch input, this can let the browser proceed without waiting for a cancellation decision. The handler still runs on the main thread and can still delay other work. Set passivity explicitly when cancellation behavior matters.

### 4. Use the Right Event Boundary

Use a `CustomEvent` for synchronous communication among components in one JavaScript agent; its detail is an ordinary shared value, not a structured-cloned message. Use a channel or worker protocol when communication must cross a tab or worker boundary. The [cross-tab chapter](10.1.6.04-cross-tab-communication.md) covers those transports.

React exposes event props such as `onClick` and `onClickCapture` through its own event system. Prefer them for React-owned UI, and attach native listeners only when the browser API requires one; give each native listener an explicit cleanup owner. When native and React handlers interact, reason about propagation at the actual boundary and test the ordering relied on by the feature.

High-frequency scroll and pointer work should also have an explicit scheduling policy. Use the separate [throttle](../04-memory-and-data/10.1.4.05-throttle.md) or [debounce](../04-memory-and-data/10.1.4.04-debounce.md) chapter for those timing contracts.

## Summary

Delegation works when the event reaches a stable ancestor and the handler safely identifies a descendant within that root. Track target, listener ownership, propagation, default behavior, and cleanup as separate contracts. A framework can add its own event layer, so keep native and framework handlers deliberate.

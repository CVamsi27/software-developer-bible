# DOM Events & Delegation

A table can receive new rows after it renders. Attaching a click listener to every button ties event wiring to each row's lifetime; one listener on the table can route actions for both existing and future rows. Understanding the browser's event path explains when that works, when it does not, and what React changes.

## Definition

The Document Object Model (DOM) represents the page as connected nodes. A dispatched DOM event follows its event path, with capture and target processing plus bubbling when that event supports it: **capturing** (from `window` down to the target's parent), **target** (at the element itself), and **bubbling** (back up to `window`). **Event delegation** registers a single listener on an ancestor and inspects `event.target` to decide what was clicked.

> **Textbook Definition:** DOM event dispatch traverses an event path through capture, target and eligible bubbling phases. Delegation handles descendant interactions through an ancestor listener, using the event path or target to identify the relevant element.

```text
capture: window -> document -> outer -> target
at target: capture listeners, then non-capture listeners
bubble (if supported): target -> outer -> document -> window
```

The arrows describe which listener locations dispatch visits. Ancestor capture runs before target handlers. At the target, capture/non-capture listener groups both run with the target phase; then supported bubbling carries the event back through ancestors. Nodes without a matching listener do not log anything, and stopping propagation can shorten the path.

## First Principles

Event delegation is deduced from two facts about the DOM:

1. **Bubbling carries supported events toward ancestors.** A listener on a stable parent can observe events from current children and children added later. Not every event bubbles, and propagation can be stopped.
2. **Each listener needs registration and lifetime management.** A thousand rows with separate listeners can require a thousand registrations and callbacks to track (→ 10.1.4.06). A delegated container listener reduces that per-child wiring while the container remains mounted.
3. **The shared handler must identify the relevant child.** It can use `event.target.closest(...)` to find a matching element and decide which action to run. Check the target's type and container membership. Nested controls and stopped propagation can affect which event the handler sees.

Frameworks can add an event abstraction over native dispatch. The React section below compares its listener placement and propagation behavior with the browser's event path.

## How does a delegated click travel through the DOM?

### The event path sets the order

In a browser page containing `<div id="outer"><button id="inner">Save</button></div>`, attach these listeners and call the button's click method. The expected order is outer capture, inner capture, inner bubble, outer bubble. Default activation, if any, is separate from this listener order.

```typescript
// Capture-phase listener runs BEFORE target/bubble listeners.
document.getElementById("outer")!.addEventListener(
  "click",
  (e) => console.log("outer capture"),
  true // or { capture: true }
);

// Bubble-phase listener (default).
document.getElementById("outer")!.addEventListener(
  "click",
  (e) => console.log("outer bubble")
);
const inner = document.getElementById("inner")!;
inner.addEventListener("click", () => console.log("inner capture"), true);
inner.addEventListener("click", () => console.log("inner bubble"));
inner.click();
```

Not every event bubbles. Non-bubbling events include `focus`/`blur`, `load`/`unload`, `mouseenter`/`mouseleave`, and media events (`play`, `pause`). React papers over some gaps (`onFocus` maps to the bubbling `focusin`), but in native code you must know the difference.

### The clicked node and the listening node differ

A click on a span inside a list button starts at that span, but the list handler runs with currentTarget set to the list. After dispatch, currentTarget resets to null: capture the needed element inside the handler before awaiting. Shadow boundaries can change which target/path is visible; ordinary closest traversal does not cross into a different shadow tree.

| Property | Meaning | Constant during propagation? |
| --------------------- | --------------------------------------------- | ----------------------------------------------- |
| `event.target` | Dispatch target as exposed to this listener | Shadow DOM can retarget it across a boundary |
| `event.currentTarget` | Element whose listener is currently executing | No — equals the node the handler is attached to |

```typescript
list.addEventListener("click", (e: MouseEvent) => {
  // e.currentTarget === list  (always, in this handler)
  // e.target === whatever was actually clicked (span, svg, text node's element...)
});
```

### Stop propagation and cancel default behavior separately

Propagation selects later listeners; default behavior is a separate action such as navigation or form submission. preventDefault only affects a cancelable event and is ignored in a passive listener. stopPropagation leaves other listeners in the current dispatch step eligible; stopImmediatePropagation ends that group too. Returning false from an addEventListener callback has no cancellation effect; legacy handler attributes and library conventions differ.

| Call | Stops propagation? | Cancels browser default? | Other listeners on same element? |
| ---------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------ | -------------------------------------- |
| `stopPropagation()` | Stops later path steps | No | Current invocation listeners still run |
| `stopImmediatePropagation()` | Yes | No | Also cancelled |
| `preventDefault()` | No | Only if cancelable/non-passive | Still run |
| `return false` from an event-handler attribute | No | Cancels default | Still eligible |

```typescript
form.addEventListener("submit", (e) => {
  e.preventDefault(); // keep the page from reloading
  // propagation continues: document-level analytics still fires
});

link.addEventListener("click", (e) => {
  e.preventDefault();       // don't navigate
  e.stopPropagation();      // AND don't tell ancestors about the click
});
```

### Let scrolling proceed when cancellation is unnecessary

A passive listener promises the browser it will never call `preventDefault()`. For cancelable wheel and touch input, the browser may otherwise wait for the handler's cancellation decision before scrolling. A passive listener removes that decision point, but scrolling and presentation still depend on the browser and workload.

```typescript
// When cancelable and non-passive, the browser may await this listener decision.
document.addEventListener("wheel", onWheel);

// Explicit passive intent removes this listener's cancellation decision.
document.addEventListener("wheel", onWheel, { passive: true });
```

Chrome defaults root-target `touchstart`/`touchmove` and `wheel`/legacy `mousewheel` listeners to passive in its documented interventions. Defaults differ by browser and target; specify `{ passive: true }` when cancellation is not needed, and specify `{ passive: false }` deliberately when it is. A passive handler still runs JavaScript and can delay other main-thread work.

### Use CustomEvent for synchronous communication in one page

```typescript
interface CartDetail {
  sku: string;
  quantity: number;
}

const CART_UPDATED = "cart:updated";

function publishCartUpdate(detail: CartDetail): void {
  window.dispatchEvent(
    new CustomEvent<CartDetail>(CART_UPDATED, {
      detail,
      bubbles: false,
      cancelable: false,
    })
  );
}

window.addEventListener(CART_UPDATED, (e) => {
  const { sku, quantity } = (e as CustomEvent<CartDetail>).detail;
  console.log(`Cart changed: ${sku} x${quantity}`);
});
```

`dispatchEvent()` invokes listeners synchronously in the current agent. `detail` is the same object reference in that agent, not a structured-cloned message; consumers can mutate shared data unless the event contract prevents it.

## How can a stable root handle changing children?

### Route actions from a changing list

```typescript
interface RowClickMeta {
  rowId: string;
  action: "edit" | "delete";
}

function delegateRowActions(tbody: HTMLTableSectionElement): () => void {
  const onClick = (e: MouseEvent) => {
    if (!(e.target instanceof Element)) return;
    const button = e.target.closest<HTMLButtonElement>(
      "button[data-action]"
    );
    if (!button || !tbody.contains(button)) return;

    const row = button.closest<HTMLTableRowElement>("tr[data-id]");
    if (!row || !tbody.contains(row) || !row.dataset.id) return;
    const action = button.dataset.action;
    if (action !== 'edit' && action !== 'delete') return;
    const meta: RowClickMeta = { rowId: row.dataset.id, action };

    if (meta.action === "delete") deleteRow(meta.rowId);
    else editRow(meta.rowId);
  };
  tbody.addEventListener('click', onClick);
  return () => tbody.removeEventListener('click', onClick);
}
```

Key details: `closest()` walks up from the real target so clicks on icons/spans inside the button still match; the `contains()` guard rejects a closest match above/outside the root; `dataset` carries the payload so no closures per row are needed.

### Reuse delegation without treating a selector as a type proof

The utility returns the exact listener's unsubscribe function; an `AbortSignal` can provide the same lifetime boundary when a component owns several listeners. Its selector/type parameter is a caller contract: generics do not prove that a matched DOM node has a particular class. Use a suitable selector or an instanceof guard where runtime subtype matters. The application snippets assume real elements and named deleteRow/editRow/handleRow actions; treat dataset values as input rather than as proof of authorization.

```typescript
type Handler<E extends Event, T extends Element> = (
  event: E,
  matched: T
) => void;

function delegate<
  K extends keyof HTMLElementEventMap,
  T extends Element = HTMLElement
>(
  root: Element | Document | DocumentFragment,
  selector: string,
  type: K,
  handler: Handler<HTMLElementEventMap[K], T>
): () => void {
  const listener = (event: HTMLElementEventMap[K]): void => {
    if (!(event.target instanceof Element)) return;
    const matched = event.target.closest<T>(selector);
    if (matched && root.contains(matched)) handler(event, matched);
  };

  root.addEventListener(type, listener as EventListener);
  return () => root.removeEventListener(type, listener as EventListener);
}

// Usage — returns an unsubscribe fn for cleanup in SPAs
const off = delegate<"click", HTMLButtonElement>(
  document.querySelector("#toolbar")!,
  ".tool-button",
  "click",
  (_e, btn) => btn.classList.toggle("active")
);
```

### Coalesce scroll work and clean up both callbacks

```typescript
let frame: number | null = null;
const onScroll = () => {
  if (frame !== null) return;
  frame = requestAnimationFrame(() => {
    frame = null;
    const height = document.documentElement.scrollHeight - innerHeight;
    const progress = height > 0 ? window.scrollY / height : 0;
    document.documentElement.style.setProperty('--scroll-progress', String(progress));
  });
};
window.addEventListener('scroll', onScroll, { passive: true });
function disposeTracking() {
  window.removeEventListener('scroll', onScroll);
  if (frame !== null) cancelAnimationFrame(frame);
  frame = null;
}
```

The first event schedules one rendering callback; further events wait for that callback, which reads the latest position. A page with no scrollable range reports zero rather than dividing by zero. Teardown removes future input and the already-pending frame. Native scroll is not cancelable; passivity does not make the callback cheap.

### Give application events a typed payload

```typescript
class DomEventBus<Events extends Record<string, unknown>> {
  constructor(private scope: EventTarget = new EventTarget()) {}

  emit<K extends keyof Events>(type: K, detail: Events[K]): void {
    this.scope.dispatchEvent(
      new CustomEvent(type as string, { detail })
    );
  }

  on<K extends keyof Events>(
    type: K,
    handler: (detail: Events[K]) => void
  ): () => void {
    const listener = (e: Event): void =>
      handler((e as CustomEvent<Events[K]>).detail);
    this.scope.addEventListener(type as string, listener);
    return () => this.scope.removeEventListener(type as string, listener);
  }
}

type AppEvents = {
  "user:login": { id: string };
  "cart:updated": { items: number };
};

const bus = new DomEventBus<AppEvents>();
const offLogin = bus.on("user:login", ({ id }) => trackLogin(id));
bus.emit("cart:updated", { items: 3 }); // fully typed payload
offLogin();
```

## How does React layer on top of native events?

React attaches its own delegated listeners **once at the root container** (React 17+; previously `document`). Most common bubbling events use that delegation; non-delegated events also exist.

```tsx
function Toolbar() {
  const handleClick = (e: React.MouseEvent<HTMLButtonElement>): void => {
    console.log(e.currentTarget);  // the <button> (synthetic wrapper)
    console.log(e.target);         // exposed target; shadow DOM can retarget it
    console.log(e.nativeEvent);    // the underlying native MouseEvent
    e.stopPropagation();           // stops later React propagation and calls
                                   // native stopPropagation at the root listener
  };
  return <button onClick={handleClick}>Save</button>;
}
```

What seniors know about the mapping:

| Behavior | Native world | React |
| --------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where listeners live | Chosen registration target | Most common delegated types at root; exceptions exist |
| `e.stopPropagation()` | Stops later native path steps | Stops React propagation and invokes native stopPropagation at the framework listener; later native ancestors may not receive the event |
| Non-bubbling events | `focus` does not bubble | `onFocus` works via `focusin` (bubbles); `onScroll` does not bubble in React 17+; use an appropriate capture handler or listen at the scroll owner |
| Event object reuse | Fresh native event | Pooling removed in React 17 — safe to hold `e` in async code |
| Ordering | Capture then bubble | Same phases; `onClickCapture` exists |

Because React delegates at the root, a *native* `stopImmediatePropagation` called below the root will prevent React handlers from firing entirely — a classic source of "my onClick stopped working" bugs.


## Summary

A delegated handler sees only events that reach its root and uses the event path to identify an eligible child. Keep propagation, default cancellation and listener lifetime as separate decisions. Use passive listeners only when cancellation is unnecessary, and account for React's event layer when native and framework handlers meet.

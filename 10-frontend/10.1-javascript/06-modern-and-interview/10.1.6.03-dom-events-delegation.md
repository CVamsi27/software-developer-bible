# DOM Events & Delegation

## Definition

A dispatched DOM event follows its event path, with capture and target processing plus bubbling when that event supports it: **capturing** (from `window` down to the target's parent), **target** (at the element itself), and **bubbling** (back up to `window`). **Event delegation** registers a single listener on an ancestor and inspects `event.target` to decide what was clicked.

```text
EVENT PROPAGATION PHASES
═══════════════════════════════════════════════════════════════

  CAPTURE (top-down)          BUBBLE (bottom-up)
  ─────────────────▶          ◀─────────────────

  ┌─────────────────┐         ┌─────────────────┐
  │ window                      │ ◀───┐   │ window          │
  │  └ document                 │     │   │  └ document     │
  │     └ html/body             │     │   │     └ html/body │
  │        └ ul                 │     │   │        └ ul     │
  │           └ li              │     │   │           └ li  │
  │              └ button ◄─┘   │              └ button
  └─────────────────┘         └─────────────────┘
            ▲ TARGET PHASE ▲
        listener runs here first,
      unless registered with capture:true
```


## First Principles

Event delegation is deduced from two facts about the DOM:

1. **Bubbling carries supported events toward ancestors.** A listener on a stable parent can observe events from current children and children added later. Not every event bubbles, and propagation can be stopped.
2. **Each listener needs registration and lifetime management.** A thousand rows with separate listeners can require a thousand registrations and callbacks to track (→ 10.1.4.06). A delegated container listener reduces that per-child wiring while the container remains mounted.
3. **The shared handler must identify the relevant child.** It can use `event.target.closest(...)` to find a matching element and decide which action to run. Check the target's type and container membership. Nested controls and stopped propagation can affect which event the handler sees.

React delegates many event types at its root; some have different listener placement or propagation rules; knowing the mechanics tells you what it does under the hood.

## Why It Matters

Senior interviews probe events beyond "add a click handler": explain the capture phase, why `focus` does not bubble, what `passive: true` buys you, and how React attaches its listeners at the root. Delegation is also a daily engineering tool — one listener for a 10,000-row list beats 10,000 listeners, and it keeps working when rows are re-rendered.

**Concretely:**

1. **Performance**: One delegated listener replaces thousands of per-child listeners, cutting memory and attach/detach cost in dynamic lists.
2. **Dynamic content**: Children added later are handled automatically — no re-binding after every render.
3. **Control flow**: Knowing the phases lets you intercept events before children see them (capture) or aggregate them after (bubble).
4. **Scroll performance**: Passive wheel/touch listeners let the browser proceed without waiting to learn whether those handlers cancel scrolling. Their JavaScript can still block main-thread work or cause jank.
5. **Decoupled architecture**: `CustomEvent` lets independent modules communicate without direct references.
6. **Framework literacy**: React's synthetic system is a thin layer over these phases; debugging "why didn't my handler fire?" requires the native model.

## How It Works

### The Three Phases

```typescript
// Capture-phase listener runs BEFORE target/bubble listeners.
document.getElementById("outer")!.addEventListener(
  "click",
  (e) => console.log("outer capture"),
  true // or { capture: true }
);

// Bubble-phase listener (default).
document.getElementById("outer")!.addEventListener(
  "click",
  (e) => console.log("outer bubble")
);
```

Not every event bubbles. Non-bubbling events include `focus`/`blur`, `load`/`unload`, `mouseenter`/`mouseleave`, and media events (`play`, `pause`). React papers over some gaps (`onFocus` maps to the bubbling `focusin`), but in native code you must know the difference.

### target vs currentTarget

| Property | Meaning | Constant during propagation? |
| --------------------- | --------------------------------------------- | ----------------------------------------------- |
| `event.target` | Dispatch target as exposed to this listener | Shadow DOM can retarget it across a boundary |
| `event.currentTarget` | Element whose listener is currently executing | No — equals the node the handler is attached to |

```typescript
list.addEventListener("click", (e: MouseEvent) => {
  // e.currentTarget === list  (always, in this handler)
  // e.target === whatever was actually clicked (span, svg, text node's element...)
});
```

### stopPropagation vs preventDefault

| Call | Stops propagation? | Cancels browser default? | Other listeners on same element? |
| --------------------------------- | --------------------------------------------------------------------------------- | ------------------------ | -------------------------------- |
| `stopPropagation()` | Yes | No | Still run |
| `stopImmediatePropagation()` | Yes | No | Also cancelled |
| `preventDefault()` | No | Yes | Still run |
| `return false` (inline attr only) | Legacy jQuery behavior; in vanilla it only calls `preventDefault()` on attributes | — | — |

```typescript
form.addEventListener("submit", (e) => {
  e.preventDefault(); // keep the page from reloading
  // propagation continues: document-level analytics still fires
});

link.addEventListener("click", (e) => {
  e.preventDefault();       // don't navigate
  e.stopPropagation();      // AND don't tell ancestors about the click
});
```

### Passive Listeners

A passive listener promises the browser it will never call `preventDefault()`. Without that promise, the browser must wait for your handler to finish before it can start scrolling; with it, the browser need not wait for that listener's cancellation decision; scrolling and presentation still depend on the browser and workload.

```typescript
// BAD: forces main-thread round-trip on every wheel tick
document.addEventListener("wheel", onWheel);

// GOOD: scroll proceeds while JS runs
document.addEventListener("wheel", onWheel, { passive: true });
```

Chrome already treats `touchstart`, `touchmove`, `wheel`, and legacy `mousewheel` on `window`/`document`/`body` as passive by default — but explicitly marking them documents intent and covers other browsers and elements.

### CustomEvent

```typescript
interface CartDetail {
  sku: string;
  quantity: number;
}

const CART_UPDATED = "cart:updated";

function publishCartUpdate(detail: CartDetail): void {
  window.dispatchEvent(
    new CustomEvent<CartDetail>(CART_UPDATED, {
      detail,
      bubbles: false,
      cancelable: false,
    })
  );
}

window.addEventListener(CART_UPDATED, (e) => {
  const { sku, quantity } = (e as CustomEvent<CartDetail>).detail;
  console.log(`Cart changed: ${sku} x${quantity}`);
});
```

## Code Examples

### Delegation: One Listener for N Children

```typescript
interface RowClickMeta {
  rowId: string;
  action: "edit" | "delete";
}

function delegateRowActions(tbody: HTMLTableSectionElement): void {
  tbody.addEventListener("click", (e: MouseEvent) => {
    const button = (e.target as HTMLElement).closest<HTMLButtonElement>(
      "button[data-action]"
    );
    if (!button || !tbody.contains(button)) return;

    const row = button.closest<HTMLTableRowElement>("tr[data-id]");
    if (!row) return;

    const meta: RowClickMeta = {
      rowId: row.dataset.id!,
      action: button.dataset.action as RowClickMeta["action"],
    };

    if (meta.action === "delete") deleteRow(meta.rowId);
    else editRow(meta.rowId);
  });
}
```

Key details: `closest()` walks up from the real target so clicks on icons/spans inside the button still match; the `contains()` guard rejects events delegated from outside; `dataset` carries the payload so no closures per row are needed.

### Generic Typed Delegator

```typescript
type Handler<E extends Event, T extends Element> = (
  event: E,
  matched: T
) => void;

function delegate<
  K extends keyof HTMLElementEventMap,
  T extends Element = HTMLElement
>(
  root: ParentNode,
  selector: string,
  type: K,
  handler: Handler<HTMLElementEventMap[K], T>
): () => void {
  const listener = (event: HTMLElementEventMap[K]): void => {
    const target = event.target as Element | null;
    const matched = target?.closest<T>(selector);
    if (matched && root.contains(matched)) handler(event, matched);
  };

  root.addEventListener(type, listener as EventListener);
  return () => root.removeEventListener(type, listener as EventListener);
}

// Usage — returns an unsubscribe fn for cleanup in SPAs
const off = delegate<HTMLButtonElement>(
  document.querySelector("#toolbar")!,
  ".tool-button",
  "click",
  (_e, btn) => btn.classList.toggle("active")
);
```

### Passive Scroll Tracking

```typescript
let ticking = false;

window.addEventListener(
  "scroll",
  () => {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => {
      const progress =
        window.scrollY / (document.body.scrollHeight - innerHeight);
      document.documentElement.style.setProperty(
        "--scroll-progress",
        String(progress)
      );
      ticking = false;
    });
  },
  { passive: true }
);
```

### Typed Event Bus over CustomEvent

```typescript
class DomEventBus<Events extends Record<string, unknown>> {
  constructor(private scope: EventTarget = new EventTarget()) {}

  emit<K extends keyof Events>(type: K, detail: Events[K]): void {
    this.scope.dispatchEvent(
      new CustomEvent(type as string, { detail })
    );
  }

  on<K extends keyof Events>(
    type: K,
    handler: (detail: Events[K]) => void
  ): () => void {
    const listener = (e: Event): void =>
      handler((e as CustomEvent<Events[K]>).detail);
    this.scope.addEventListener(type as string, listener);
    return () => this.scope.removeEventListener(type as string, listener);
  }
}

type AppEvents = {
  "user:login": { id: string };
  "cart:updated": { items: number };
};

const bus = new DomEventBus<AppEvents>();
const offLogin = bus.on("user:login", ({ id }) => trackLogin(id));
bus.emit("cart:updated", { items: 3 }); // fully typed payload
offLogin();
```

## Real-World Use Cases

### 1. Analytics Click Tracking (Capture Phase)

An eligible ancestor capture listener can observe the click before descendant handlers stop propagation. A prior listener on the path, shadow retargeting or another context can still limit what it sees:

```typescript
document.addEventListener(
  "click",
  (e) => {
    const el = (e.target as HTMLElement).closest("[data-analytics]");
    if (el) {
      analytics.track(el.dataset.analytics!, {
        path: location.pathname,
      });
    }
  },
  { capture: true } // runs before app handlers anywhere
);
```

### 2. Dropdown Menus That Close on Outside Click

One document-level listener replaces per-menu wiring and survives menus being mounted/unmounted:

```typescript
document.addEventListener("pointerdown", (e) => {
  document.querySelectorAll("[data-menu].open").forEach((menu) => {
    if (!menu.contains(e.target as Node)) menu.classList.remove("open");
  });
});
```

### 3. Infinite Virtual List

Rows mount/unmount constantly; delegation on the container means no per-row native listener rebinding; record data, dispatch routing and framework handlers still use memory.

### 4. React Synthetic Events — How They Relate

React attaches its own delegated listeners **once at the root container** (React 17+; previously `document`). Most common bubbling events use that delegation; non-delegated events also exist.

```tsx
function Toolbar(): JSX.Element {
  const handleClick = (e: React.MouseEvent<HTMLButtonElement>): void => {
    console.log(e.currentTarget);  // the <button> (synthetic wrapper)
    console.log(e.target);         // deepest element clicked
    console.log(e.nativeEvent);    // the underlying native MouseEvent
    e.stopPropagation();           // stops SYNTHETIC propagation;
                                   // native bubbling already happened
  };
  return <button onClick={handleClick}>Save</button>;
}
```

What seniors know about the mapping:

| Behavior | Native world | React |
| --------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where listeners live | Per-element | Once per root container |
| `e.stopPropagation()` | Stops native bubbling | Stops React propagation and invokes native stopPropagation; ancestor native listeners beyond the root may still be prevented |
| Non-bubbling events | `focus` does not bubble | `onFocus` works via `focusin` (bubbles); `onScroll` does not bubble in React 17+; use an appropriate capture handler or listen at the scroll owner |
| Event object reuse | Fresh native event | Pooling removed in React 17 — safe to hold `e` in async code |
| Ordering | Capture then bubble | Same phases; `onClickCapture` exists |

Because React delegates at the root, a *native* `stopImmediatePropagation` called below the root will prevent React handlers from firing entirely — a classic source of "my onClick stopped working" bugs.

## Common Mistakes

### 1. Reading `this` Instead of `currentTarget`

```typescript
// BAD: `this` is undefined with arrow functions, unreliable elsewhere
el.addEventListener("click", () => console.log(this));

// GOOD: currentTarget is always the attached node
el.addEventListener("click", (e) => console.log(e.currentTarget));
```

### 2. Confusing preventDefault With stopPropagation

```typescript
// BAD: meant to cancel navigation, but stopPropagation doesn't — the page
// navigates away anyway and only the ancestor listeners are silenced
link.addEventListener("click", (e) => e.stopPropagation());

// GOOD: name what you want
link.addEventListener("click", (e) => {
  e.preventDefault();      // stay on page
  // propagation untouched: document analytics still records the click
});
```

### 3. Attaching Non-Passive Wheel Handlers

```typescript
// BAD: every scroll frame waits for JS
container.addEventListener("wheel", zoomHandler);

// GOOD: declare passivity unless preventDefault is truly needed
container.addEventListener("wheel", zoomHandler, { passive: true });
```

### 4. Delegating Without `closest` Guarding

```typescript
// BAD: clicking the icon span breaks dataset lookups
list.addEventListener("click", (e) => {
  const id = (e.target as HTMLElement).dataset.id; // undefined!
});

// GOOD: search upward from the real target
list.addEventListener("click", (e) => {
  const row = (e.target as HTMLElement).closest("[data-id]");
  if (row) handleRow(row.dataset.id!);
});
```

### 5. Forgetting to Remove Listeners

```typescript
// BAD: SPA navigation piles up duplicate listeners on document
useEffect(() => {
  document.addEventListener("keydown", onKey);
}, []);

// GOOD: symmetric cleanup
useEffect(() => {
  document.addEventListener("keydown", onKey);
  return () => document.removeEventListener("keydown", onKey);
}, []);
```

### 6. Mixing Native `stopPropagation` Under React Roots

```typescript
// BAD: kills React's root-delegated handlers downstream
widgetEl.addEventListener("click", (e) => e.stopImmediatePropagation());

// GOOD: coordinate at the React level or use capture deliberately
<div onClickCapture={(e) => { /* gate logic */ }} />
```

## Best Practices

1. **Delegate at the nearest stable ancestor** — the container of dynamic children, not always `document`.
2. **Choose capture when observation must precede descendant bubble handlers**; it does not guarantee every event is visible or unaffected by earlier capture listeners.
3. **Mark scroll-family listeners passive** unless you genuinely call `preventDefault`.
4. **Prefer `closest(selector)` over fragile `target.tagName` checks** in delegated handlers.
5. **Return unsubscribe functions** from setup utilities so effects clean up symmetrically.
6. **Type custom events** with generics instead of casting `any` payloads.
7. **Never rely on `event.returnValue`/`return false`** — call the explicit methods.
8. **In React, treat `nativeEvent` as read-only telemetry**, not as the primary API.

## Performance Considerations

| Concern | Cost | Mitigation |
| -------------------------------------------- | ------------------------------------- | ------------------------------------------------------------ |
| 10k listeners on a grid | High memory, slow attach on re-render | One delegated listener |
| Scroll/wheel handler blocking paint | Dropped frames, jank | `passive: true` + `requestAnimationFrame` batching |
| Heavy work in bubble phase on `document` | Every click pays it | Filter early with `closest`, bail fast |
| Frequent `CustomEvent` dispatch on hot paths | Allocation + synchronous fan-out | Batch payloads; prefer signals/store for high-frequency data |

## Summary

- Events flow capture (top-down) → target → bubble (bottom-up); most but not all events bubble.
- `target` can be retargeted across a shadow boundary; `currentTarget` is the node running the listener and should be captured if needed after an asynchronous boundary.
- `preventDefault` cancels browser behavior, `stopPropagation` cancels travel, `stopImmediatePropagation` also silences sibling listeners.
- Delegation gives one listener, dynamic-child support, and lower memory; implement with `closest` + guards.
- Mark cancelable wheel/touch listeners passive when cancellation is unnecessary. Native scroll itself is not cancelable; passive does not make its callback inexpensive.
- React synthesizes events from root-delegated native listeners; knowing the native phases explains nearly every surprising React event bug.

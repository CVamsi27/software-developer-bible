# Cross-Tab Communication

Changing a theme in one tab should update the other open tabs. A notification can do that, but a tab opened later needs saved state. If tabs must avoid overlapping work, they also need coordination. Those are separate guarantees, so choose the guarantee before the API.

```js
const channel = new BroadcastChannel('theme');
channel.onmessage = (event) => applyTheme(event.data); // live peers update
channel.postMessage('dark');
localStorage.setItem('theme', 'dark'); // later tabs read this on startup
```

## Definition

Cross-tab communication exchanges messages or coordinated state between distinct browser contexts, such as tabs, windows, and iframes. Those contexts have separate JavaScript globals. A web origin is the scheme, host, and port. Origin and browser storage-partition rules decide which contexts can use a shared transport or storage area.

> **Textbook Definition:** Cross-context communication is the exchange of messages or coordination over shared browser resources among distinct browsing contexts. Its security and delivery rules depend on origin, storage partition, transport, and lifecycle.

## First Principles

Each tab owns its JavaScript state — a shared origin may unlock a transport or storage area, but never merges globals. A **notification**, a **saved value**, and an **exclusive owner** are three different guarantees; pick each one the feature needs instead of expecting one API to provide all three. And design for hostile delivery: messages can be missed, duplicated, delayed, or sent by stale tabs — so validate schemas and keep an authoritative owner for anything affecting security or remote writes.

```text
Tab A -- transient notification --> Tab B
  |                                  |
  +---- saved state in storage ------+

A message can be missed; a later tab must read saved state.
```

## 1. Decide What the Feature Must Guarantee

| Need | Suitable mechanism | What it does not guarantee |
| ------------------------------------------------------------ | ----------------------------------------- | -------------------------------------------------------------------------------- |
| Notify currently open peers | `BroadcastChannel` | Durable delivery or replay to a tab opened later |
| Persist the latest small value | `localStorage` plus a startup read | Atomic read-modify-write, a message history, or notification in the writing tab |
| Persist structured or larger data | `IndexedDB`, then notify with a record ID | Immediate fan-out or unlimited storage; receivers still validate and read |
| One live owner for several clients | `SharedWorker` with a port per client | Durable state after every client closes |
| A direct window pair, including an allowed cross-origin pair | `window.postMessage` | A queue for a future window; callers must check origin, source, and payload |
| Serialize cooperating same-origin work | `Web Locks` | Protection from code that ignores the lock or from duplicate remote side effects |
| Notify controlled pages from a service worker | Service-worker messaging | An always-running worker or a durable message queue |

Messages usually use structured cloning. It copies supported data into the receiving context; it does not share an ordinary object. `BroadcastChannel` reaches eligible contexts with the same channel name, origin, and storage partition, but the sending channel object does not receive its own post. Another channel object in the same tab may receive it.

## 2. Synchronize a Theme with a Stored Fallback

Use the channel for quick notification and `localStorage` for the latest value a new tab can read. The writing tab applies the change itself because it receives no storage event. Channel and storage can both notify another tab, so applying the same valid theme twice must be harmless.

```typescript
type Theme = "light" | "dark" | "system";
const key = "theme";
let channel: BroadcastChannel | null = null;
try { channel = new BroadcastChannel("theme"); } catch { /* unavailable in this context */ }

function isTheme(value: unknown): value is Theme {
  return value === "light" || value === "dark" || value === "system";
}
function accept(value: unknown): void {
  if (isTheme(value)) applyTheme(value); // application callback
}

if (channel) channel.onmessage = event => accept(event.data);
function onStorage(event: StorageEvent): void {
  if (event.key === key) accept(event.newValue);
}
window.addEventListener("storage", onStorage);
try { accept(localStorage.getItem(key)); } catch { /* storage may be unavailable */ }

function setTheme(theme: Theme): void {
  try { localStorage.setItem(key, theme); } catch { /* channel is transient fallback */ }
  channel?.postMessage(theme);
  applyTheme(theme);
}

function dispose(): void {
  channel?.close();
  window.removeEventListener("storage", onStorage);
}
```

This compact theme example assumes changes do not need a global concurrent-write order. Delayed competing writes can otherwise leave tabs with different last-arriving values. When the stored latest value is authoritative, treat notifications as hints and re-read storage; stronger version/tie-break rules belong in the application protocol. A transient-only channel fallback cannot supply durable ordering.

`localStorage` stores strings, access can fail, and a write of the same value does not emit a storage event. `sessionStorage` events are limited to related documents in the same top-level browsing context, not independent tabs. Neither storage API makes read-then-write atomic.

## 3. Coordinate Work Without Pretending It Is a Transaction

Two tabs can both read an empty `localStorage` key before either writes, so a check-then-set sequence is not a lock. Use `Web Locks` when cooperating browser contexts must serialize a local operation:

```typescript
await navigator.locks.request(
  "report-export",
  { ifAvailable: true },
  async lock => {
    if (!lock) return; // another tab owns it
    await exportReport(); // the lock lasts until this promise settles
  }
);
```

With `ifAvailable`, a busy lock gives the callback null immediately; without it, the request waits in the queue. The callback's returned promise defines how long the lock is held. `Web Locks` are exposed in secure contexts, so feature-detect the API and choose a safe fallback for unsupported targets. This only coordinates callers using the same lock. A payment, upload, or other remote write still needs server-side idempotency because a browser can lose its response after the server commits.

For structured messages, include a schema version because old and new tabs can remain open at the same time. For authentication changes, send an event ID and a public session-generation value, never an access token. Validate the message, ignore duplicates, and revalidate with the server when authorization matters. A persisted latest marker can help a later tab catch up, but it is not a durable event log; startup should read current state from its authoritative owner.

If messages carry a large report, write it to `IndexedDB` and commit the transaction before sending its ID. The receiving tab validates the ID and schema, then reads the data. Handle transaction errors, quota, eviction, and a late receiver explicitly. The notification is a hint to read committed state, not the state itself.

## 4. Select the Owner for Other Browser Boundaries

A `SharedWorker` provides a live hub: each client uses its own `MessagePort`, and the worker routes replies or deliberately broadcasts them. Use it when one in-memory owner, such as a WebSocket connection, is valuable across open tabs; persist data elsewhere if it must survive that worker's lifetime.

For `window.postMessage`, send only to the expected `targetOrigin` and check `event.origin`, `event.source`, and message shape before acting. Direct references can support an explicitly allowed cross-origin pair, but they do not grant access to the other window's ordinary objects.

A service worker can message eligible clients during an event, but the browser may stop it between events. Its registration, update, control, and cache lifecycles belong in the [PWA chapter](../../10.7-html-css/10.7.05-pwa.md).

## Summary

`BroadcastChannel` notifies live peers, storage gives later tabs a value to read, `SharedWorker` gives clients one live owner, and `Web Locks` serialize cooperating local work. Keep payload and authorization contracts explicit, close resources with their owner, and make missed or duplicate notifications safe. Remote correctness belongs to the server.

# Cross-Tab Communication

## Definition

**Cross-tab communication** is the set of browser APIs that let independent browsing contexts (tabs, windows, iframes) of the **same origin** exchange messages or observe each other's persisted state, since they share storage but not the JS heap.

```text
SAME ORIGIN, NO SHARED HEAP
═══════════════════════════════════════════════════════════════

 ┌──────────────┐   BroadcastChannel    ┌──────────────┐
 │ Tab A        │ ────────────────────▶ │ Tab B        │
 │ JS heap: 0x1 │ ◀──────────────────── │ JS heap: 0x2 │
 └──────┬───────│                       └──────┬───────│
        │       ┌──────────────────┐          │
        ▼       │ Shared transports│          ▼
 ┌─────────────────────────────────────────────────────┐ │ - localStorage   │  ┌──────────────┐
 │ IndexedDB    │ │ - BroadcastCh.   │  │ Service      │
 │ (shared disk)│ │ - SharedWorker   │  │ Worker       │
 └─────────────────────────────────────────────────────┘ │ - SW messaging   │  └──────────────┘
                  └──────────────────┘
 Cross-origin tabs see NOTHING of this.
```


## First Principles

Cross-tab communication exists because tabs are strangers by security design:

1. **Isolation is the default.** Independent contexts have their own globals/realms; they do not automatically share application state. Same-origin windows can also hold direct references, and storage access depends on partitioning and policy. Any communication must go through a *channel the browser mediates*: `postMessage`/`MessageChannel` (direct pair), `BroadcastChannel` (same-origin group), storage events (shared localStorage), or the server (shared truth). Four primitives, each a different trade of coupling and reach.
2. **Same-origin is the trust boundary.** `BroadcastChannel` and storage events are free of origin checks only *because* they never cross origins; `postMessage` must because it can. Choosing a channel is choosing who's allowed to hear you.
3. **Nothing here is transactional.** Tabs die without goodbye, messages arrive in different orders per channel, and storage events don't fire in the writing tab — so every protocol built on these primitives needs its own consistency story (leader election via `Web Locks` is the standard one).

## Why It Matters

Cross-tab bugs are user-visible and embarrassing: log out in one tab, keep working in another with a stale token; two tabs overwrite each other's drafts; a checkout runs twice. Interviewers love this topic because it tests events, async storage APIs, race conditions, and graceful degradation in one question.

**Concretely:**

1. **Session integrity**: Propagate session/permission invalidation promptly while retaining server-side authorization; suspended or newly opened tabs may miss transient messages.
2. **Consistent UX**: Theme, feature flags, cart, and unsaved-draft indicators should match across tabs.
3. **Mutual exclusion**: Only one tab may play audio, hold an edit lock, or run a background sync.
4. **Payload sharing**: Downloading a 50 MB report once and sharing it via IndexedDB beats five downloads.
5. **Lifecycle coordination**: Announce "new service worker installed — reload to update" to every tab.

## How It Works

### Transport Comparison

| API | Direction | Payload | Same-origin only? | Support notes |
| ------------------------------------ | ------------------------------------------- | -------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------ |
| `BroadcastChannel` | Many-to-many pub/sub | Structured clone | Yes | All modern browsers; Safari 15.4+ |
| `storage` event | One writer → all other contexts | Strings via `localStorage` | Yes | Fires everywhere; NOT in the writing tab |
| `SharedWorker` | Hub-and-spoke through one worker | Structured clone ports | Yes | Check the target compatibility matrix and storage partition; lifetime is tied to eligible owners |
| `postMessage` (`window.open`/iframe) | Point-to-point between windows holding refs | Structured clone | Configurable via `targetOrigin` | Needs direct window reference |
| Service worker messages | SW ↔ its clients | Structured clone | Yes | Works even when channel objects would be recreated per page load |
| Web Locks (`navigator.locks`) | Coordination, not messaging | n/a (mutex) | Yes | Modern answer to tab mutexes |

### BroadcastChannel

```typescript
const channel = new BroadcastChannel("app-sync");

channel.onmessage = (event: MessageEvent) => {
  console.log("received", event.data);
};

channel.postMessage({ type: "ping", at: Date.now() });

// Release for GC when the page unloads
channel.close();
```

Messages are structured-cloned (objects, Maps, Blobs pass through), delivered to eligible listening channel objects listening on the same channel name and storage partition — except the sending channel object. Another channel object in the same tab may receive it.

### Storage Events

```typescript
// Tab B listens
window.addEventListener("storage", (e: StorageEvent) => {
  // e.key, e.oldValue, e.newValue, e.url, e.storageArea
  if (e.key === "theme") applyTheme(e.newValue);
});

// Tab A writes — fires 'storage' in OTHER tabs, not here
localStorage.setItem("theme", "dark");
```

Two gotchas seniors must know: the event does **not** fire in the tab that wrote, and it does **not** fire if you set the *same value* again (compare old vs new first).

### SharedWorker vs postMessage Trade-offs

| Concern | `BroadcastChannel` | `SharedWorker` |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------ |
| Topology | Peer-to-peer fan-out | Star: hub owns state/connections |
| Shared mutable state | No — each tab keeps its own copy | Yes — single source of truth lives in the worker |
| WebSocket pooling | Each tab opens its own socket | One socket shared by all tabs |
| Lifecycle | Lives per page | Dies when last tab closes; must persist state externally |
| Debugging | DevTools console per tab | Separate worker inspector |
| Mobile support | Broad | Version/partition support varies — feature-detect and test targets |

Rule of thumb: use `BroadcastChannel` for notifications; graduate to a `SharedWorker` (or a service worker) when you need one authoritative socket or one serialized queue.

### localStorage Mutex Pattern

Before Web Locks existed, teams used write-if-absent keys as locks:

```typescript
function acquireLock(name: string, ttlMs = 10_000): boolean {
  const now = Date.now();
  const raw = localStorage.getItem(`lock:${name}`);
  if (raw) {
    const { expires } = JSON.parse(raw) as { expires: number };
    if (expires > now) return false; // someone holds it
  }
  // Race window exists between check and set — acceptable for UX,
  // enforce authoritatively server-side for correctness.
  localStorage.setItem(
    `lock:${name}`,
    JSON.stringify({ owner: crypto.randomUUID(), expires: now + ttlMs })
  );
  return true;
}

function releaseLock(name: string): void {
  localStorage.removeItem(`lock:${name}`);
}
```

The modern replacement is atomic — and note the `{ ifAvailable: true }`, without which the callback is *queued* until the lock is free and always receives a lock:

```typescript
await navigator.locks.request(
  "report-export",
  { ifAvailable: true },
  async (lock) => {
    if (!lock) return; // held elsewhere — this branch never runs without ifAvailable
    await exportReport();
  }
);
```

### Sync Logout Across Tabs

Broadcast the intent and persist a session/version marker if late tabs need catch-up. The setup code must explicitly read that marker; the storage event only reports later changes. Duplicate channel/storage delivery should be idempotent, and a stale logout marker must not log out a newly established session.

```typescript
// auth-bus.ts
type AuthMessage =
  | { type: "logout"; reason?: string }
  | { type: "token-refreshed"; token: string };

const AUTH_CHANNEL = "auth";

export class AuthBus {
  private channel = new BroadcastChannel(AUTH_CHANNEL);

  constructor(private onMessage: (msg: AuthMessage) => void) {
    this.channel.onmessage = (e) => this.onMessage(e.data);

    // Fallback + late-tab catch-up via storage event
    window.addEventListener("storage", (e) => {
      if (e.key === "auth-event" && e.newValue) {
        this.onMessage(JSON.parse(e.newValue) as AuthMessage);
      }
    });
  }

  broadcast(msg: AuthMessage): void {
    this.channel.postMessage(msg);
    localStorage.setItem("auth-event", JSON.stringify({ ...msg, at: Date.now() }));
  }

  destroy(): void {
    this.channel.close();
  }
}

// usage.tsx — inside your auth provider
const bus = new AuthBus((msg) => {
  if (msg.type === "logout") redirectToLogin();
  if (msg.type === "token-refreshed") setToken(msg.token);
});
```

### IndexedDB for Larger Payloads

Signal small over the wire, ship the heavy data through shared disk storage (for the storage APIs themselves — quotas, eviction, and when *not* to use `localStorage` — see [Browser Storage](../../10.7-html-css/10.7.08-browser-storage.md)):

```typescript
async function shareLargeResult(id: string, rows: ReportRow[]): Promise<void> {
  const db = await openDb("reports", 1, (db) =>
    db.createObjectStore("payloads")
  );
  await putValue(db, "payloads", id, rows);     // megabytes land in IDB
  channel.postMessage({ type: "report-ready", id }); // bytes travel between tabs
}

// Receiver tab
channel.onmessage = async (e) => {
  if (e.data.type === "report-ready") {
    const rows = await getValue<ReportRow[]>("reports", "payloads", e.data.id);
    render(rows);
  }
};
```

### Service-Worker Messaging

A service worker can reach every client — including announcing updates:

```typescript
// In the service worker
self.addEventListener("message", (event) => {
  if (event.data?.type === "SKIP_WAITING") self.skipWaiting();
});

self.addEventListener("activate", () => {
  self.clients.matchAll({ type: "window" }).then((clients) => {
    clients.forEach((client) =>
      client.postMessage({ type: "sw-updated" })
    );
  });
});
```

```typescript
// In the app
navigator.serviceWorker.addEventListener("message", (e) => {
  if (e.data.type === "sw-updated") showReloadToast();
});
```

## Code Examples

### Feature: Cross-Tab Theme Sync With Fallback

```typescript
class ThemeSync {
  private bc: BroadcastChannel | null = null;

  constructor(private apply: (theme: string) => void) {
    try {
      this.bc = new BroadcastChannel("theme");
      this.bc.onmessage = (e) => this.apply(e.data.theme);
    } catch {
      // Very old browsers: storage-event fallback only
    }
    window.addEventListener("storage", this.onStorage);
  }

  private onStorage = (e: StorageEvent): void => {
    if (e.key === "theme" && e.newValue) this.apply(e.newValue);
  };

  set(theme: string): void {
    localStorage.setItem("theme", theme); // persists + notifies others
    this.bc?.postMessage({ theme });      // instant, structured
    this.apply(theme);                    // this tab gets no storage event!
  }
}
```

### Feature: Single-Tab Background Poller

```typescript
let hasLeadership = false;

setInterval(async () => {
  await navigator.locks.request(
    "poller",
    { ifAvailable: true },
    async (lock) => {
      if (!lock) return;
      if (!hasLeadership) console.log("this tab is now leader");
      hasLeadership = true;
      await pollInbox(); // only one tab polls at a time;
                         // lock auto-releases to another tab on close
    }
  );
}, 30_000);
```

## Real-World Use Cases

| Scenario | Transport | Notes |
| -------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------ |
| Logout / session expiry everywhere | BroadcastChannel + storage fallback | Also invalidate server-side |
| Draft autosave conflict ("editing in another tab") | Web Locks plus server version checks | A localStorage check-then-set is not mutual exclusion; surface conflicts |
| Live cart badge sync in e-commerce | BroadcastChannel | Cart truth stays server-side |
| One WebSocket for N tabs | SharedWorker | Reconnect logic written once |
| "New version available — refresh" toast | Service worker → clients | Pair with `skipWaiting` flow |
| Sharing a parsed 100 MB CSV across tabs | IndexedDB signal + payload | Parse once, read many |

## Common Mistakes

### 1. Expecting the Storage Event in the Writing Tab

```typescript
// BAD: nothing happens locally
localStorage.setItem("theme", "dark");
applyThemeFromStorageEvent(); // never fires here

// GOOD: apply locally yourself; the event is only for other tabs
localStorage.setItem("theme", "dark");
applyTheme("dark");
```

### 2. Writing the Same Value Again to "Notify"

```typescript
// BAD: no change → no storage event anywhere
localStorage.setItem("last-seen", String(now));

// GOOD: include a nonce/timestamp so the value actually changes
localStorage.setItem("ping", JSON.stringify({ t: performance.now() }));
```

### 3. Leaking Channels and Listeners

```typescript
// BAD: every SPA navigation creates another channel
useEffect(() => {
  const ch = new BroadcastChannel("cart");
  ch.onmessage = handleCart;
}, []);

// GOOD: close what you open
useEffect(() => {
  const ch = new BroadcastChannel("cart");
  ch.onmessage = handleCart;
  return () => ch.close();
}, []);
```

### 4. Trusting Client-Side Locks for Money

```typescript
// BAD: two tabs raced the check-then-set window and double-charged
if (acquireLock("checkout")) chargeCard();

// GOOD: client locks are UX; idempotency keys are correctness
chargeCardWithIdempotencyKey(orderId);
```

### 5. Assuming SharedWorker Exists Everywhere

```typescript
// Unsupported/disabled contexts need a fallback; do not infer availability from a user-agent cutoff.
const worker = new SharedWorker(url);

// GOOD: feature-detect and degrade to BroadcastChannel
const hub = typeof SharedWorker !== "undefined"
  ? new SharedWorkerHub()
  : new BroadcastChannelFallback();
```

### 6. Shipping Secrets Through Same-Origin Channels

Any script on the origin can open your channel name. Tokens belong in httpOnly cookies; channels carry UI-level facts, not credentials.

## Best Practices

1. **Default to `BroadcastChannel`; layer the `storage` event underneath as a fallback**, and always handle the current tab separately.
2. **Keep messages small and typed** (discriminated unions); move bulk data through IndexedDB.
3. **Use Web Locks for mutual exclusion**, not ad-hoc flags, whenever browser targets allow.
4. **Design for tab death**: any tab can vanish mid-flow; make server state, not tab state, the source of truth.
5. **Close channels, clear locks, remove listeners on unmount** — cross-tab leaks multiply by tab count.
6. **Version your message schema** (`{ v: 2, ... }`) because an old tab and a new tab can be open simultaneously after deploy.
7. **Test with three tabs**: sender, receiver, and one opened *after* the fact (catch-up semantics).

## Performance Considerations

- `storage` events serialize everything to strings — JSON cost grows with payload size; prefer structured-clone channels for rich data.
- `BroadcastChannel` delivery is asynchronous to eligible recipients but cheap per message; batch high-frequency streams (cursor positions) with `requestAnimationFrame`.
- IndexedDB writes are async and transactional; reuse one connection instead of opening per message.
- A `SharedWorker` amortizes one WebSocket across tabs — fewer sockets, fewer reconnect storms on flaky networks.
- A cooperative Web Lock is released when its callback completes or its owning context is destroyed; it does not need an application TTL by default. A lease stored in localStorage needs expiry/renewal, but those do not make read-then-write acquisition atomic.

## Summary

- Tabs share origin and storage, never the JS heap; pick a transport per topology: peer fan-out (BroadcastChannel/storage), hub (SharedWorker/SW), or point-to-point (`postMessage`).
- The `storage` event fires only in other tabs and only on real changes.
- Use Web Locks for cooperative exclusion among eligible contexts; localStorage read-then-write cannot enforce exclusive ownership.
- Sync logout = broadcast + persisted marker + server invalidation.
- Large payloads travel as IndexedDB references announced by tiny messages.
- Every transport demands disciplined cleanup and schema versioning.

# Cross-Tab Communication

## Definition

**Cross-tab communication** lets separate browser contexts, such as tabs, windows and iframes, exchange messages or observe saved state. These contexts do not share their ordinary JavaScript objects. Eligible contexts from the **same origin**, the same scheme, host and port, can use shared browser storage and communication APIs, subject to browser partitioning rules.

> **Textbook Definition:** Cross-context communication exchanges messages or coordinated state between distinct browsing contexts. Origin and storage-partition rules constrain participation; message delivery does not by itself provide durable state or exclusive ownership.

```text
Tab A -- small notification --> shared channel --> Tab B
  |                                                 |
  +-- write report --> shared IndexedDB <-- read ----+
```

Each tab owns its local variables and view. The channel copies a message; the database holds a separately stored value. Tab B must read the report after the transaction commits. A notification that arrives while B is closed is lost, so B also needs a startup read when catch-up matters. Same-origin windows with direct references can access eligible objects; shared transports do not make their independent globals one shared state.

## First Principles

Cross-tab communication exists because tabs are strangers by security design:

1. **Separate browser contexts do not automatically share application state.** They have their own globals. Eligible same-origin windows can hold direct references, but storage and communication also depend on browser partitioning rules. Channels include `postMessage` or `MessageChannel` for a direct pair, `BroadcastChannel` for an eligible same-origin group, storage events for saved changes and the server for shared remote state.
2. **The channel decides who can receive the data.** `BroadcastChannel` and storage events are restricted by origin and storage partition. Window `postMessage` can cross origins, so supply and verify the intended origin. Being on the same origin does not itself make every script trustworthy.
3. **Delivery does not make a multi-step operation atomic.** A tab can close unexpectedly, messages on different channels can arrive in different orders, and the writer does not receive its own storage event. Design rules for missed or repeated messages and concurrent writes. Web Locks can coordinate eligible cooperating contexts, but server-side effects still need server-side correctness rules.

## Why It Matters

Cross-tab bugs are user-visible and embarrassing: log out in one tab, keep working in another with a stale token; two tabs overwrite each other's drafts; a checkout runs twice. Interviewers love this topic because it tests events, async storage APIs, race conditions, and graceful degradation in one question.

**Concretely:**

1. **Session integrity**: Propagate session/permission invalidation promptly while retaining server-side authorization; suspended or newly opened tabs may miss transient messages.
2. **Consistent UX**: Theme, feature flags, cart, and unsaved-draft indicators should match across tabs.
3. **Mutual exclusion**: Only one tab may play audio, hold an edit lock, or run a background sync.
4. **Payload sharing**: A committed IndexedDB value can avoid repeated downloads when quota, retention, and lifecycle allow it.
5. **Lifecycle coordination**: Announce "new service worker installed — reload to update" to every tab.

## How It Works

### A message transport differs from stored state and ownership

A transport delivers a copy to recipients. Storage holds a value for later reads. A lock grants one cooperating callback permission to run at a time; it does not deliver data. A **mutex**, or mutual-exclusion lock, prevents two cooperating owners from entering the same named operation simultaneously. Choose among these roles before choosing an API.

### Transport Comparison

| API | Direction | Payload | Participation | Delivery boundary |
| ------------------------------------ | ------------------------------------------- | -------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------ |
| `BroadcastChannel` | Many-to-many pub/sub | Structured clone | Same origin and storage partition | Transient; sending channel object excluded |
| `storage` event | One writer → all other contexts | Strings via `localStorage` | Eligible shared storage area | Writing document excluded; changed value only |
| `SharedWorker` | Hub-and-spoke through one worker | Structured clone ports | Eligible same-origin contexts | Check the target compatibility matrix and storage partition; lifetime is tied to eligible owners |
| `postMessage` (`window.open`/iframe) | Point-to-point between windows holding refs | Structured clone | Configurable via `targetOrigin` | Needs direct window reference |
| Service worker messages | SW ↔ its clients | Structured clone | Eligible service-worker clients | Worker may stop between events |
| Web Locks (`navigator.locks`) | Coordination, not messaging | No payload | Eligible same-origin contexts | Promise returned by callback defines ownership |

### BroadcastChannel

```typescript
const channel = new BroadcastChannel("app-sync");

channel.onmessage = (event: MessageEvent) => {
  console.log("received", event.data);
};

channel.postMessage({ type: "ping", at: Date.now() });

// Keep this channel open while its owning view is active.
function disposeSync(): void { channel.close(); }
```

Messages are structured-cloned (objects, Maps, Blobs pass through), delivered to eligible listening channel objects listening on the same channel name and storage partition — except the sending channel object. Another channel object in the same tab may receive it.

### Storage Events

```typescript
// Tab B listens
window.addEventListener("storage", (e: StorageEvent) => {
  // e.key, e.oldValue, e.newValue, e.url, e.storageArea
  if (e.key === "theme") applyTheme(e.newValue);
});

// Tab A writes — fires 'storage' in OTHER tabs, not here
localStorage.setItem("theme", "dark");
```

Install the listener before another tab writes. `applyTheme` is an application callback that accepts validated theme values; a removal sends `null`. On startup, read the current stored value separately. `localStorage` changes notify eligible other same-origin tabs; `sessionStorage` changes reach eligible frames within the same top-level tab, not independent tabs. Storage access can fail when denied or full.

Two delivery conditions matter: the event does **not** fire in the tab that wrote, and it does **not** fire if you set the *same value* again (compare old vs new first).

### SharedWorker vs postMessage Trade-offs

| Concern | `BroadcastChannel` | `SharedWorker` |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------ |
| Topology | Peer-to-peer fan-out | Star: hub owns state/connections |
| Shared mutable state | No — each tab keeps its own copy | One worker-owned in-memory model; durability needs storage |
| WebSocket pooling | Each tab opens its own socket | One socket shared by all tabs |
| Lifecycle | Lives per page | Owner-dependent lifetime; persist state externally |
| Debugging | DevTools console per tab | Separate worker inspector |
| Mobile support | Broad | Version/partition support varies — feature-detect and test targets |

With a shared worker, A and B each send through their own `MessagePort`. The worker can serialize requests and reply on the originating port, or explicitly fan a result out to both ports. Its cache is in the worker's memory, so tabs need a recovery path if that owner disappears. See [Web Workers](10.1.6.02-web-workers.md) for the port trace. A service worker has an event-driven lifecycle and is not a permanently running socket owner.

For window `postMessage`, A needs a window reference, such as the value returned by `window.open` or an iframe's `contentWindow`. A sends with an exact expected `targetOrigin`; B checks `event.origin`, `event.source` and message shape before using it. This permits an explicitly allowed cross-origin pair without granting either side access to the other's objects. Losing the window reference or opening B later does not create a persistent message queue.

### Why a localStorage check-then-set is not a lock

A storage read followed by a write is not one indivisible operation. Suppose the key is empty: A reads empty, B reads empty, A writes its owner, and B overwrites it. Both callers can report success. An expiry time limits stale data but does not remove this race; removing the key without checking ownership can also erase another caller's lease.

Do not use that pattern as an exclusive lock. If Web Locks is unavailable, choose an operation that tolerates concurrency or enforce ownership at the server. The following browser example assumes a secure context with Web Locks and an application `exportReport()` that returns a promise for the whole operation.

Web Locks serialize callbacks that request the same lock name in eligible contexts. They do not make remote work atomic or protect callers that ignore the lock. With `{ ifAvailable: true }`, a request returns immediately with `null` when another owner holds the lock; without it, the callback waits in the queue:

```typescript
await navigator.locks.request(
  "report-export",
  { ifAvailable: true },
  async (lock) => {
    if (!lock) return; // held elsewhere — this branch never runs without ifAvailable
    await exportReport();
  }
);
```

### Sync Logout Across Tabs

Broadcast the intent and persist a session/version marker if late tabs need catch-up. The setup code must explicitly read that marker; the storage event only reports later changes. Duplicate channel/storage delivery should be idempotent, and a stale logout marker must not log out a newly established session.

```typescript
// Browser-only auth-bus.ts; no access tokens are sent.
type AuthMessage = {
  v: 1; id: string; sessionId: string;
  type: "logout" | "session-changed";
};
function decodeAuth(value: unknown): AuthMessage | null {
  if (typeof value !== "object" || value === null) return null;
  const m = value as Record<string, unknown>;
  return m.v === 1 && typeof m.id === "string" && m.id.length > 0 &&
    typeof m.sessionId === "string" && m.sessionId.length > 0 &&
    (m.type === "logout" || m.type === "session-changed")
    ? m as AuthMessage : null;
}

export class AuthBus {
  private channel: BroadcastChannel | null = null;
  private seen = new Set<string>();
  private onStorage = (e: StorageEvent): void => {
    let isLocalStorageEvent = false;
    try {
      isLocalStorageEvent = e.storageArea === localStorage;
    } catch { /* storage may be denied in this context */ }
    if (isLocalStorageEvent && e.key === "auth-event") this.readMarker(e.newValue);
  };

  constructor(
    private sessionId: string, // public session generation, not a credential
    private onMessage: (msg: AuthMessage) => void,
  ) {
    try {
      this.channel = new BroadcastChannel("auth");
      this.channel.onmessage = (e) => this.accept(e.data);
    } catch { /* storage notification remains available */ }
    window.addEventListener("storage", this.onStorage);
    try { this.readMarker(localStorage.getItem("auth-event")); }
    catch { /* storage may be denied */ }
  }
  private readMarker(raw: string | null): void {
    if (!raw) return;
    try { this.accept(JSON.parse(raw)); } catch { /* malformed marker */ }
  }
  private accept(value: unknown): void {
    const msg = decodeAuth(value);
    if (!msg || msg.sessionId !== this.sessionId || this.seen.has(msg.id)) return;
    this.seen.add(msg.id);
    if (this.seen.size > 100) this.seen.delete(this.seen.values().next().value!);
    this.onMessage(msg);
  }
  broadcast(type: AuthMessage["type"]): void {
    const msg: AuthMessage = {
      v: 1, id: crypto.randomUUID(), sessionId: this.sessionId, type,
    };
    this.channel?.postMessage(msg);
    try { localStorage.setItem("auth-event", JSON.stringify(msg)); }
    catch { /* delivery remains best-effort */ }
    this.accept(msg); // the writer receives no storage event
  }
  destroy(): void {
    window.removeEventListener("storage", this.onStorage);
    this.channel?.close();
  }
}
```

Supply the current public session generation from your authoritative session response, and recreate/destroy the bus when that generation changes. The callback invalidates cached UI and reloads authoritative session state; a channel message must not grant authorization. In a concrete trace, A broadcasts event E for session S, B sees E through both channel and storage but applies it once, and a newly opened tab for S reads E from storage. A later login with generation T ignores the saved S event.

The 100-ID set bounds memory and deduplicates recent deliveries, not all historical deliveries. Keep the callback idempotent. One persisted marker cannot represent an event history, and denied storage, suspension or tab death can prevent delivery. Startup/server revalidation supplies correctness; notifications improve responsiveness. `onMessage` is a synchronous application callback; an async revalidation it starts must handle its own rejection.

### IndexedDB for Larger Payloads

Send a small notification and keep the payload in shared IndexedDB storage (for quotas, eviction and storage choices, see [Browser Storage](../../10.7-html-css/10.7.08-browser-storage.md)):

```typescript
// Integration sketch: these adapters and ReportRow are application-defined.
async function shareLargeResult(id: string, rows: ReportRow[]): Promise<void> {
  const db = await openDb("reports", 1, (db) =>
    db.createObjectStore("payloads")
  ); // application adapter caches and reuses this database connection
  await putValue(db, "payloads", id, rows);     // resolve only when the transaction commits
  channel.postMessage({ type: "report-ready", id }); // only the identifier is sent
}

// Receiver tab
channel.onmessage = async (e) => {
  if (e.data.type === "report-ready") {
    const rows = await getValue<ReportRow[]>("reports", "payloads", e.data.id);
    render(rows);
  }
};
```

The database adapters must reuse a connection, handle upgrades and errors, validate stored rows, and resolve writes on transaction completion rather than an individual request's success. Otherwise B can receive `report-ready` before the data is committed. Validate the notification's version/type/id before reading; catch read failures. A startup read of known report IDs provides late-tab recovery. The sketch omits those application contracts; it is not a runnable database wrapper.

### Service-Worker Messaging

A service worker can message eligible clients. `clients.matchAll` normally returns clients controlled by that worker; `includeUncontrolled` broadens eligible same-origin clients, not arbitrary windows. Extend the event lifetime until notification work finishes:

```typescript
// Separate worker entry, compiled with the WebWorker library.
const sw = self as unknown as ServiceWorkerGlobalScope;
sw.addEventListener("message", (event) => {
  if (event.data?.type === "SKIP_WAITING") event.waitUntil(sw.skipWaiting());
});

sw.addEventListener("activate", (event) => {
  event.waitUntil(sw.clients.matchAll({ type: "window" }).then((clients) => {
    clients.forEach((client) =>
      client.postMessage({ type: "sw-updated" })
    );
  }));
});
```

```typescript
// In the app
navigator.serviceWorker.addEventListener("message", (e) => {
  if (e.data.type === "sw-updated") showReloadToast();
});
```

Service-worker installation, waiting, activation and mixed-version reload decisions have their canonical explanation in [PWA and Service Workers](../../10.7-html-css/10.7.05-pwa.md). Send `SKIP_WAITING` only as part of that explicit update policy, and dispose the app message listener with its view.

### Feature: Cross-Tab Theme Sync With Fallback

```typescript
type Theme = "light" | "dark" | "system";
function isTheme(value: unknown): value is Theme {
  return value === "light" || value === "dark" || value === "system";
}
class ThemeSync {
  private bc: BroadcastChannel | null = null;
  private onStorage = (e: StorageEvent): void => {
    let isLocalStorageEvent = false;
    try {
      isLocalStorageEvent = e.storageArea === localStorage;
    } catch { /* storage may be denied in this context */ }
    if (isLocalStorageEvent && e.key === "theme" && isTheme(e.newValue)) this.apply(e.newValue);
  };
  constructor(private apply: (theme: Theme) => void) {
    try {
      this.bc = new BroadcastChannel("theme");
      this.bc.onmessage = (e) => { if (isTheme(e.data)) this.apply(e.data); };
    } catch { /* use storage events if available */ }
    window.addEventListener("storage", this.onStorage);
    try {
      const saved = localStorage.getItem("theme");
      if (isTheme(saved)) this.apply(saved);
    } catch { /* retain application default */ }
  }
  set(theme: Theme): void {
    try { localStorage.setItem("theme", theme); } catch { /* transient only */ }
    this.bc?.postMessage(theme);
    this.apply(theme);
  }
  destroy(): void {
    window.removeEventListener("storage", this.onStorage);
    this.bc?.close();
  }
}
```

Construct this in a browser view with an `apply` callback that updates the DOM, and destroy it when that view ends. A selects dark: A applies it immediately, B receives either notification, and a later C reads dark from storage. Repeated application must be harmless because channel and storage can both deliver. Concurrent tabs can select different themes; this simple example uses whichever valid update arrives last in each tab and provides no global conflict ordering.

### Feature: Prevent Overlapping Poll Operations

```typescript
// Browser setup: pollInbox resolves after its entire request/update operation.
function startPolling(pollInbox: () => Promise<void>): () => void {
  let pending = false;
  const timer = setInterval(() => {
    if (pending) return;
    pending = true;
    void navigator.locks.request("poller", { ifAvailable: true }, async (lock) => {
      if (lock) await pollInbox();
    }).catch(console.error).finally(() => { pending = false; });
  }, 30_000);
  return () => clearInterval(timer);
}
```

A obtains the lock and starts a request; B's overlapping attempt receives `null` and skips. Once A's promise settles, another tab may acquire it. This is exclusion for one operation, not permanent leadership or one globally scheduled poll every 30 seconds: staggered tabs may all poll sequentially. Background timers may also be delayed. The disposer stops future ticks; cancelling an already running request needs an `AbortSignal` contract in `pollInbox`. A stable leader would need to keep its lock callback pending for the whole leadership lifetime and provide explicit shutdown/recovery.

## Real-World Use Cases

| Scenario | Transport | Notes |
| -------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------ |
| Logout / session expiry everywhere | BroadcastChannel + storage fallback | Validate session generation; also invalidate server-side |
| Draft autosave conflict ("editing in another tab") | Web Locks plus server version checks | A localStorage check-then-set is not mutual exclusion; surface conflicts |
| Live cart badge sync in e-commerce | BroadcastChannel | Cart truth stays server-side |
| One WebSocket for N tabs | SharedWorker | Reconnect logic written once |
| "New version available — refresh" toast | Service worker → clients | Pair with `skipWaiting` flow |
| Sharing a parsed 100 MB CSV across tabs | IndexedDB signal + payload | Parse once, read many |

## Common Mistakes

### 1. Expecting the Storage Event in the Writing Tab

```typescript
// BAD: nothing happens locally
localStorage.setItem("theme", "dark");
applyThemeFromStorageEvent(); // never fires here

// GOOD: apply locally yourself; the event is only for other tabs
localStorage.setItem("theme", "dark");
applyTheme("dark");
```

### 2. Writing the Same Value Again to "Notify"

```typescript
// BAD: no change → no storage event anywhere
localStorage.setItem("last-seen", String(now));

// GOOD: include a nonce/timestamp so the value actually changes
localStorage.setItem("ping", JSON.stringify({ id: crypto.randomUUID() }));
```

### 3. Leaking Channels and Listeners

```typescript
// BAD: every SPA navigation creates another channel
useEffect(() => {
  const ch = new BroadcastChannel("cart");
  ch.onmessage = handleCart;
}, []);

// GOOD: close what you open
useEffect(() => {
  const ch = new BroadcastChannel("cart");
  ch.onmessage = handleCart;
  return () => ch.close();
}, []);
```

### 4. Trusting Client-Side Locks for Money

```typescript
// BAD: two tabs raced the check-then-set window and double-charged
if (acquireLock("checkout")) chargeCard();

// GOOD: client locks are UX; idempotency keys are correctness
chargeCardWithIdempotencyKey(orderId);
```

### 5. Assuming SharedWorker Exists Everywhere

```typescript
// Construction can fail even when the constructor exists (for example, due to policy).
let hub: SharedWorkerHub | BroadcastChannelFallback;
try {
  hub = typeof SharedWorker === "undefined"
    ? new BroadcastChannelFallback()
    : new SharedWorkerHub(url);
} catch {
  hub = new BroadcastChannelFallback();
}
```

### 6. Shipping Secrets Through Same-Origin Channels

An eligible script within the origin/storage partition can open a known channel name. A name is not authentication. Validate data, retain server authorization, and carry UI invalidation facts rather than credentials. Choose credential storage according to the application security model.

## Best Practices

1. **Default to `BroadcastChannel`; layer the `storage` event underneath as a fallback**, and always handle the current tab separately.
2. **Keep messages small and typed** (discriminated unions); move bulk data through IndexedDB.
3. **Use Web Locks for mutual exclusion**, not ad-hoc flags, whenever browser targets allow.
4. **Design for tab death**: any tab can vanish mid-flow; make server state, not tab state, the source of truth.
5. **Close channels, end owned lock callbacks, remove listeners on unmount** — cross-tab leaks multiply by tab count.
6. **Version your message schema** (`{ v: 2, ... }`) because an old tab and a new tab can be open simultaneously after deploy.
7. **Test with three tabs**: sender, receiver, and one opened *after* the fact (catch-up semantics).

## Performance Considerations

- Web Storage stores strings; application JSON encoding and parsing costs grow with payload size, so prefer structured-clone channels for rich transient messages.
- `BroadcastChannel` delivery is asynchronous to eligible recipients and uses structured cloning; payload size and frequency still cost serialization and scheduling, so batch high-frequency streams such as cursor positions.
- IndexedDB writes are async and transactional; reuse one connection instead of opening per message.
- A `SharedWorker` amortizes one WebSocket across tabs — fewer sockets, fewer reconnect storms on flaky networks.
- A cooperative Web Lock is released when its callback completes or its owning context is destroyed; it does not need an application TTL by default. A lease stored in localStorage needs expiry/renewal, but those do not make read-then-write acquisition atomic.

## Summary

- Separate tabs own their globals. Pick group notifications, a worker-owned hub, or a direct window pair according to the recipients and recovery needs.
- The `storage` event fires only in other tabs and only on real changes.
- Use Web Locks for cooperative exclusion among eligible contexts; localStorage read-then-write cannot enforce exclusive ownership.
- Session invalidation needs a validated generation-aware marker, local application, cleanup and server revalidation.
- Large payloads travel as IndexedDB references announced by tiny messages.
- Every transport demands disciplined cleanup and schema versioning.

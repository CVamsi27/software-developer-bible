# Regular Expressions and Text Matching

A support log line is about to be shipped to a third-party tracer, and it carries a customer email and a bearer token. Splitting on spaces does not rescue you: the token field contains a space, quoted values contain more, and every new log format breaks the hand-written parser. The replacement is a *pattern* that describes the shape of the value you want, so the search survives formatting changes the parser cannot anticipate.

The catch is that the same tool can hang a request for seconds, silently skip half a list, or mangle an emoji. This chapter follows one redaction job from a working pattern to the three failures that bite in production.

## Definition

A **regular expression** (regex) is a pattern that describes a set of strings. A regex engine compares that pattern against an input and reports whether a substring matches, where it starts and ends, and what each **capture group** collected. In JavaScript a regex is a `RegExp` object, written as a literal (`/pattern/flags`) or built at runtime (`new RegExp(source, flags)`).

> **Textbook Definition:** A regular expression is a formal description of a language over an alphabet, built from concatenation, alternation and repetition. A matcher decides membership and reports the substring and subexpressions that satisfy the description.

## First Principles

Text matching needs a way to say "a run of word characters", "either of these schemes", "this, repeated" without enumerating strings. Three operators are enough: **concatenation** (this then that), **alternation** (`a|b`), and **repetition** (`*`, `+`, `?`, `{m,n}`). Everything else — classes, anchors, groups — is notation on top of that algebra.

How the engine executes the pattern is a separate decision with visible consequences. JavaScript engines use a **backtracking** matcher: it tries one path, and on failure returns to the last choice point and tries the next. Backtracking is what makes backreferences and lookaround possible, and it is also why an ambiguous pattern can take exponential time. A Thompson NFA simulation would run in linear time but could not express those features. So the same syntax has very different worst cases across engines, and in JavaScript you own that risk.

## 1. Read a Pattern as Parts, Not as a Blob

Regex bugs are usually misread structure. Naming the parts turns a wall of punctuation back into a sentence:

| Part | In `(?<scheme>Bearer)\s+(?<token>[A-Za-z0-9._~+/=-]+)` | Question it answers |
| :-------------- | :-------------------------------------------------------------------------------------- | :------------------------------------------------------- |
| Literal | `Bearer` | Which exact characters must appear? |
| Class | `[A-Za-z0-9._~+/=-]` | Which single characters are allowed here? |
| Quantifier | `+` after the class | How many of them, at least and at most? |
| Group | `(?<scheme>…)`, `(?<token>…)` | Which parts must be captured, and under what name? |
| Anchor | none here; `^` and `$` in the field parser | Where may the match begin and end? |

Two defaults decide most surprises. Quantifiers are **greedy**: they take as much as possible, then give characters back only when the rest of the pattern fails; a trailing `?` makes them lazy instead. And shorthand classes are ASCII-first: `\w` means `[A-Za-z0-9_]` unless the `u` flag plus `\p{…}` says otherwise, so `\w+` does not match `Zoë` in full and never matches `李`.

## 2. Flags Change Where a Match Starts and What a Character Is

Flags are not modifiers on "how strict" the match is; they change the matching model:

| Flag | Effect | Failure it prevents or causes |
| :--- | :------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------- |
| `g` | Search the whole string; `lastIndex` advances and persists between calls | A shared `/g` regex is stateful — the bug in the example below |
| `y` | Match only at `lastIndex`, never search forward | Silently rejects input when `lastIndex` is not where you think |
| `i` | Case-insensitive matching | Fine, but `i` on user data can widen matches unexpectedly |
| `m` | `^`/`$` match at line boundaries | Anchors stop meaning "whole input" |
| `s` | `.` also matches newline | Log patterns that rely on `.` stop crossing lines |
| `u` | Code-point semantics, `\p{…}` properties, stricter escapes | Without it, an astral character is two matches |
| `v` | Unicode sets: `[\p{L}--[a-z]]`, intersection | Set operations unavailable on older runtimes |
| `d` | Records `index` ranges for each group in `indices` | Needed to slice the original string precisely |

The `g` flag is the one that produces wrong answers rather than slow ones. `RegExp.prototype.test` starts at `lastIndex` and does not reset it on success, so a single reused object skips early matches in later strings:

```javascript
const reused = /error/gi;
const messages = ['ERROR disk full', 'error: timeout', 'all good'];
console.log('shared /g test:', messages.map((m) => reused.test(m)));
console.log('fresh regexp:  ', messages.map((m) => /error/i.test(m)));
```

```text
shared /g test: [ true, false, false ]
fresh regexp:   [ true, true, false ]
```

The second message *does* contain `error`, but the shared regex was still parked at index 5 from the first call, so the scan began after the match and returned `false`. Either create the regex inside the loop or reset `re.lastIndex = 0` before each use. The same statefulness explains a stray `for` loop that finds every second occurrence: `String.prototype.matchAll` refuses to run without `g` (it throws `TypeError: String.prototype.matchAll called with a non-global RegExp argument`), while `replace` with `g` ignores a pre-set `lastIndex` and resets it to `0` afterwards.

## 3. The Complete Worked Example: Redact a Log Line

Two passes, one per secret shape. `replace` with a global pattern rewrites every occurrence, and the named-group form `$<scheme>` keeps the readable part of the token while dropping the credential:

```javascript
// Redact customer identifiers in a support log line before it reaches a third-party tracer.
const line =
  '2026-11-12T09:41:02Z INFO user=bob@example.com token=Bearer eyJhbGciOi.abc ip=10.0.0.7';

const EMAIL = /[\w.+-]+@[\w-]+\.[\w.]+/g;
const BEARER = /(?<scheme>Bearer)\s+(?<token>[A-Za-z0-9._~+/=-]+)/g;

const redacted = line
  .replace(EMAIL, '[email]')
  .replace(BEARER, '$<scheme> [token]');

console.log('redacted:', redacted);

const FIELDS =
  /^(?<time>\S+) (?<level>[A-Z]+) user=(?<user>\S+) token=(?<scheme>\w+) (?<token>\S+) ip=(?<ip>\S+)$/;
const parsed = FIELDS.exec(line);

console.log('fields:', parsed.groups.level, parsed.groups.ip);
console.log('email matches:', [...line.matchAll(new RegExp(EMAIL.source, 'g'))].length);

const reused = /error/gi;
const messages = ['ERROR disk full', 'error: timeout', 'all good'];
console.log('shared /g test:', messages.map((m) => reused.test(m)));
console.log('fresh regexp:  ', messages.map((m) => /error/i.test(m)));
```

Run on Node 24.22.2, this prints:

```text
redacted: 2026-11-12T09:41:02Z INFO user=[email] token=Bearer [token] ip=10.0.0.7
fields: INFO 10.0.0.7
email matches: 1
shared /g test: [ true, false, false ]
fresh regexp:   [ true, true, false ]
```

The redaction is order-independent here because the two patterns cannot overlap, and it is idempotent on this line: neither `[email]` nor `Bearer [token]` matches either pattern again. `parsed` is the check that the line still has the shape the tracer expects — and writing it caught a real defect while this example was prepared: the first version parsed `token=(?<token>\S+)` and returned `null` on the very line it was written for, because `Bearer` and the credential are two whitespace-separated tokens. An anchored whole-line pattern fails loudly; an unanchored `\S+` field would have silently truncated the value and looked healthy.

## 4. Where Patterns Break

**Catastrophic backtracking.** Nested quantifiers such as `^(a+)+$` give the matcher exponentially many ways to split the same run of `a`s. On a non-matching input it tries them all. Median of five runs on Node 24.22.2 on one laptop, with `'a'.repeat(n) + 'b'` (absolute times vary by machine; the growth is the point):

| Input length | Result | Median time |
| :----------- | :------- | ----------: |
| 16 | no match | 0.6 ms |
| 20 | no match | 9.8 ms |
| 22 | no match | 33.9 ms |
| 24 | no match | 137.2 ms |

Each two extra characters multiplies the work. Node exposes no regex timeout, so one hostile string in an unvalidated field blocks the event loop for every request on that process. The defenses are structural: avoid nested quantifiers over overlapping alternatives (`(a+)+`, `(\w+\s?)*`), anchor and bound the input (`.slice(0, 200)` before matching), prefer a character class to an alternation of prefixes, and keep user-supplied patterns out of the server. A linter or a review checklist catches the common shapes; benchmarks on adversarial input catch the rest.

**Unicode is code units by default.** `'👍'.match(/./g)` returns two matches because the default model counts UTF-16 code units; with `u` it returns one, and `\p{Script=Greek}` only works when `u` (or `v`) is present. Emoji, combining marks and any non-BMP text therefore behave differently with and without `u`, which is a correctness bug before it is a performance one.

**Feature availability is a runtime fact.** Lookbehind `(?<=…)`, named groups, and the `d` flag work in Node 24.22.2; `RegExp.escape` and the `v` flag are recent enough that a browser matrix or an older embedded runtime may not have them. Confirm on the runtime you actually ship to rather than assuming the newest syntax exists everywhere.

**Some grammars are not regular.** HTML, JSON and CSV with quoting are nested or stateful; a regex that "works" on the sample fails on the first escaped quote or nested tag. Parse those with a parser and use regex only for the leaf values.

## 5. Building a Pattern From Input

Interpolating a user string into `new RegExp()` turns regex metacharacters into syntax: a search for `a.b*c` becomes "a, any character, b repeated" and throws or matches the wrong rows. `RegExp.escape` renders the literal form:

```javascript
const literal = new RegExp(RegExp.escape('a.b*c'));
console.log(literal.source, literal.test('a.b*c'));
```

```text
\x61\.b\*c true
```

Escaping is necessary but not sufficient: it fixes the metacharacters, not the cost. A still-longer escaped pattern with nested quantifiers remains a backtracking hazard, so bound the length of any pattern you build from input.

## Summary

A regular expression describes a set of strings with concatenation, alternation and repetition; a backtracking engine searches for a match and reports captures. Read a pattern by naming its parts, and remember that flags change the matching model — `g` makes `test` stateful, `u` changes what a character is, `y` removes the search step. Redaction and parsing examples work because the patterns are anchored and the fields are bounded; the failure boundary is exponential backtracking on ambiguous patterns, code-unit splitting without `u`, and runtime-dependent features. Escape input before it becomes a pattern, and hand nested grammars to a parser.

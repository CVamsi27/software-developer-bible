# Types vs Interfaces

## Definition

A **type alias** names a TypeScript type expression, including an object shape, union, tuple or function type. An **interface** declares a named object contract, including properties and call/construct signatures, and supports extension and declaration merging. Both are erased; neither validates a runtime value.

## First Principles

1. **Names should let a contract change in one place.** Reusing a shape in several parameters is clearer when it has a name. A name alone does not give the value a distinct runtime identity.
2. **Some contracts describe alternatives, others describe combined members.** An object with a name and email is a shape; success-or-failure is a union. Choose syntax that can express that relationship.
3. **An open contract can be augmented by another declaration.** That is useful for a library extension point, but an accidental duplicate interface also changes the shared contract. An alias cannot merge under the same name.

## Both names describe the same object shape

Save each code block below as an independent TypeScript module and check it with `tsc --noEmit --strict`. This first example shows what structural compatibility means:

```typescript
export {};
type UserRecord = { id: string; name: string };
interface UserContract { id: string; name: string }
function displayName(user: UserContract): string { return user.name; }
const record: UserRecord = { id: "u1", name: "Ada" };
console.log(displayName(record)); // Ada

const richer = { id: "u2", name: "Bob", email: "bob@example.com" };
const accepted: UserRecord = richer; // Existing compatible value has extra fields.
// @ts-expect-error Fresh literal is checked for unexpected properties.
const typo: UserRecord = { id: "u3", name: "Cara", emali: "cara@example.com" };
```

The compiler checks the members needed by `displayName`; it does not require `record` to have been declared with the interface's name. The fresh-literal check helps catch typos but does not make the type an exact runtime schema. Index signatures, unions, assertions and other contexts affect that check. Classes with private/protected members and branded values introduce additional compatibility constraints; “structural” does not mean every same-looking class is interchangeable.

An inline object type such as `(user: { name: string })` is also valid. An interface declaration is named syntax; there is no inline anonymous-interface declaration inside that parameter.

## A union expresses mutually exclusive outcomes

```typescript
export {};
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; error: string };
type Pair<T> = readonly [T, T];
type Identifier = string | number;
interface Formatter { (value: string): string }
const uppercase: Formatter = value => value.toUpperCase();
function describe(result: Result<string>): string {
  return result.ok ? uppercase(result.value) : `Failed: ${result.error}`;
}
console.log(describe({ ok: true, value: "saved" })); // SAVED
```

An interface can describe a callable object, so it is not restricted to class-oriented code. It cannot directly replace an alias for a primitive or union. Mapped and conditional type expressions also need an alias when you want to name their result; their mechanisms belong in [Type Transformations](../03-type-transformations/INDEX.md).

## Extension combines members; conflicting members expose a difference

Interfaces can extend interfaces or suitable object aliases with statically known members. Aliases combine object types using intersections. A class can implement either suitable object contract; it cannot implement a union of alternative shapes.

```typescript
export {};
type HasId = { id: string };
interface Timestamped extends HasId { createdAt: Date }
interface User extends Timestamped { name: string }
type UserAlias = HasId & { createdAt: Date; name: string };
const user: UserAlias = { id: "u1", createdAt: new Date(0), name: "Ada" };
const compatible: User = user;

interface TextValue { value: string }
// @ts-expect-error Interface extension rejects incompatible member types.
interface BadExtension extends TextValue { value: number }
type Impossible = TextValue & { value: number };
// @ts-expect-error string & number becomes never; no ordinary value fits.
const impossible: Impossible = { value: 1 };
```

An intersection is not “take the last property's type”. It requires satisfying both contracts; incompatible property requirements can produce `never`. An interface extension commonly reports the conflict at its declaration, which can make a public contract easier to diagnose.

## Merging is an explicit extension point

```typescript
export {};
interface RequestConfig { timeoutMs: number }
interface RequestConfig { traceId?: string }
const config: RequestConfig = { timeoutMs: 5000, traceId: "request-1" };

type ClosedConfig = { timeoutMs: number };
// A second `type ClosedConfig = ...` in this scope is a duplicate-name error.
type WithTrace = ClosedConfig & { traceId?: string }; // New name is allowed.
console.log(config.timeoutMs); // 5000
```

Merged non-function properties must agree in type and modifiers. A second declaration is not a runtime patch and cannot arbitrarily replace a member. Module/global augmentation must target the appropriate declaration scope; a module-local `interface Window` does not automatically augment the browser's global Window. Use `declare global` from a module when that is the intended boundary, as explained in [Declaration Merging](https://www.typescriptlang.org/docs/handbook/declaration-merging.html).

## Application contracts still need runtime boundaries

For a database record, name the entity shape and derive intentional input views:

```typescript
export {};
interface UserEntity {
  id: string;
  name: string;
  email: string;
  passwordHash: string;
  createdAt: Date;
}
type PublicUser = Pick<UserEntity, "id" | "name">;
type RenameUserInput = Pick<UserEntity, "name">;
type EditableProfile = Pick<UserEntity, "name" | "email">;
type ProfilePatch = Partial<EditableProfile>;
```

Do not turn every database field except an ID into a public write DTO: secret fields and server-controlled data need separate rules. Derived types do not validate JSON, authorize an edit, hash a password or implement ORM behavior. Use runtime validation at the boundary and whitelist writable fields.

For React props, either syntax is appropriate; a discriminated prop union needs an alias. Follow a consistent project convention for plain shapes. For NestJS dependency injection, an interface is a compile-time contract; the runtime injection token must be a class, symbol, string or another supported provider token. It cannot be the erased interface itself.

## Keep complex types diagnosable

Name meaningful contracts, rather than long anonymous expansions or repeated intersection chains. TypeScript's performance guidance favors interfaces for composing object types where appropriate because their relationship checking can be cached and their conflicts are easier to display. Profile checker performance with diagnostics/traces before attributing a slow build to a keyword.

Both syntaxes can represent recursive object relationships. An alias such as `type Node = { next?: Node }` is valid; an unproductive self-alias such as `type Loop = Loop | string` is rejected. Recursive compatibility and large generated unions still need complexity limits regardless of the syntax.

## Summary

Use either syntax to name a plain object shape. Use an alias for alternatives and computed type expressions; use an interface when a compatible object contract needs extension or intentional declaration merging. Check the resulting member relationships, and keep runtime validation and injection tokens separate from erased types.

# Types vs Interfaces

## TL;DR

`type` aliases represent any type (unions, intersections, tuples, mapped); `interface` declares object shapes with declaration merging and `extends` support. For object literals, either works; for unions/intersections/mapped, use `type`; for library extension and OOP, use `interface`.

## First Principles

The type system's one job: prove the compiler's assumptions about runtime values.

1. **Types are erased at runtime** — everything here is compile-time reasoning over a *parallel description* of the code. `type` and `interface` are two syntaxes for the same role; the differences (unions, declaration merging, extends) are tooling-shaping, not semantic cliffs.
2. **Structural typing is the rule**: a value's type is *its shape*, not its declared name — which is why interfaces and object types are interchangeable and why branded types (→ 10.2.4.02) exist to fake nominality when shape isn't enough.
3. **The choice is convention, then capability**: need unions/intersections/conditional composition → `type`; need declaration merging or extendable contracts (→ 10.2.1.02) → `interface`. Everything else is style — pick one per codebase.

## Why It Matters

Senior engineers must know when each shines: declaration merging is interface-only, so library authors use interfaces to allow extension. Unions and mapped types are type-only. The rule of thumb: `interface` for public object APIs (extension-friendly), `type` for everything else.

## Definition

**Type aliases (`type`)** and **interfaces (`interface`)** are TypeScript constructs that describe the shape of objects and other data structures. While they overlap significantly in functionality, they have distinct features and use cases.

- **`type`**: A type alias that can represent any TypeScript type — primitives, unions, intersections, tuples, functions, and more.
- **`interface`**: A named contract for object shapes that supports declaration merging, extension via `extends`, and is specifically designed for object-oriented patterns.

## How It Works

### Syntax Differences

```typescript
// ─── Type Alias ───────────────────────────────────────────────
type StringOrNumber = string | number;
type Point = { x: number; y: number };
type Pair<T> = [T, T];

// ─── Interface ────────────────────────────────────────────────
interface StringOrNumberInterface {} // Cannot represent unions
interface PointInterface {
  x: number;
  y: number;
}

```

### Declaration Merging (Interface Only)

```typescript
interface Window {
  title: string;
}
interface Window {
  close(): void;
}
// Result: Window has both `title` and `close()`

// Type aliases cannot merge — second declaration causes error
type Config = { debug: boolean };
type Config = { verbose: boolean }; // Duplicate identifier

```

### Extends vs Intersection

```typescript
// ─── Interface Extends ────────────────────────────────────────
interface Animal {
  name: string;
}
interface Dog extends Animal {
  breed: string;
}

// ─── Type Intersection ────────────────────────────────────────
type Animal = { name: string };
type Dog = Animal & { breed: string };

// ─── Interface Extending Multiple Interfaces ──────────────────
interface Serializable {
  serialize(): string;
}
interface Loggable {
  log(): void;
}
interface Entity extends Serializable, Loggable {
  id: number;
}

// ─── Type Intersection (equivalent) ──────────────────────────
type Entity = Serializable & Loggable & { id: number };

```

### Nameability

```typescript
// Both syntaxes can be written inline, at a single call site
function greet(person: { name: string }) {}
function process(data: { items: number[] }) {}

// Naming pays off as soon as the shape appears twice: errors and hovers
// print the name instead of expanding the whole structure, and only a
// named declaration can later be extended or merged.
type User = { name: string; age: number };
interface UserInterface { name: string; age: number }

function save(u: User) {}
// save({ name: "Ada" });  // error says `User`, not `{ name: string; age: number }`
```

## Code Examples

### Structural Typing

```typescript
// TypeScript uses structural typing — both types and interfaces
// are compatible based on shape, not explicit declaration

type Point = { x: number; y: number };
interface PointInterface { x: number; y: number }

const p1: Point = { x: 1, y: 2 };
const p2: PointInterface = p1; // Compatible — same structure

// Extra properties are allowed when assigning to a variable
const p3 = { x: 1, y: 2, z: 3 };
const p4: Point = p3; // OK — extra properties allowed

// Extra properties are NOT allowed in object literals
const p5: Point = { x: 1, y: 2, z: 3 }; // Error: excess property

```

### Common Patterns

```typescript
// ─── Pattern 1: API Response Types ───────────────────────────
type ApiResponse<T> = {
  data: T;
  status: number;
  message: string;
};

interface User {
  id: number;
  name: string;
  email: string;
}

type UserResponse = ApiResponse<User>;

// ─── Pattern 2: Discriminated Unions (type only) ────────────
type Shape =

  | { kind: "circle"; radius: number }
  | { kind: "rectangle"; width: number; height: number };

// ─── Pattern 3: React Props (interface preferred) ────────────
interface ButtonProps {
  label: string;
  onClick: () => void;
  variant?: "primary" | "secondary";
}

```

> *Pattern 4 — a class `implements` a generic `Repository<T>` contract — is covered with the full example in [10.2.2.01 — Generics](../02-generics-and-inference/10.2.2.01-generics.md).*

### Extending and Intersecting

```typescript
// ─── Interface Chain ──────────────────────────────────────────
interface BaseEntity {
  id: string;
  createdAt: Date;
  updatedAt: Date;
}

interface TimestampedEntity extends BaseEntity {
  deletedAt?: Date;
}

interface User extends TimestampedEntity {
  name: string;
  email: string;
}

// ─── Type Chain ──────────────────────────────────────────────
type BaseEntity = {
  id: string;
  createdAt: Date;
  updatedAt: Date;
};

type TimestampedEntity = BaseEntity & {
  deletedAt?: Date;
};

type User = TimestampedEntity & {
  name: string;
  email: string;
};

// ─── Mixed Extends and Intersection ──────────────────────────
interface HasId {
  id: string;
}

type Timestamped = {
  createdAt: Date;
  updatedAt: Date;
};

// Interface can extend a type intersection
interface User extends HasId, Timestamped {
  name: string;
}

```

## Real-World Use Cases

### Database Models

```typescript
// Interface for database entity (declaration merging with ORM)
interface BaseModel {
  id: string;
  createdAt: Date;
  updatedAt: Date;
}

interface User extends BaseModel {
  name: string;
  email: string;
  passwordHash: string;
}

// Type for creation (omit auto-generated fields)
type CreateUserDTO = Omit<User, "id" | "createdAt" | "updatedAt">;

// Type for update (all fields optional)
type UpdateUserDTO = Partial<CreateUserDTO>;

```

### Configuration

```typescript
// Pieces that never get extended stay as type aliases
type Environment = "development" | "staging" | "production";

type DatabaseConfig = {
  host: string;
  port: number;
  database: string;
  ssl: boolean;
};

// The config itself is an interface so a later declaration can merge
// new top-level options in — the pattern library configs are built on.
interface AppConfig {
  env: Environment;
  port: number;
  database: DatabaseConfig;
}

interface AppConfig {
  logging: {
    level: "debug" | "info" | "warn" | "error";
    format: "json" | "text";
  };
}
// Result: one AppConfig with env/port/database AND logging.
// (A second `type AppConfig = …` here would be a duplicate-identifier error.)
```

## Common Mistakes

### 1. Using Interface When Type Is Required

```typescript
// Wrong: Interface cannot represent unions
interface Status = "active" | "inactive"; // Syntax error

// Correct
type Status = "active" | "inactive";

```

### 2. Using Type When Interface Would Be Better

```typescript
// Poor: No declaration merging, no extends
type Config = { debug: boolean };
// Later need to extend...

// Better: Interface allows merging and extension
interface Config {
  debug: boolean;
}
interface Config {
  verbose: boolean; // Merges automatically
}

```

### 3. Forgetting Structural Typing

```typescript
// This works because TypeScript uses structural typing
type Duck = { quack(): void };
type Bird = { quack(): void };

const duck: Duck = { quack: () => console.log("quack") };
const bird: Bird = duck; // No error — same structure

```

### 4. Excessive Intersections

```typescript
// Bad: Hard to read and debug
type ComplexType = A & B & C & D & E & F;

// Better: Use interfaces with extends
interface ComplexType extends A, B, C {
  // Group related properties
}

```

## Best Practices

```typescript
// 1. Use interfaces for object shapes and class contracts
interface User {
  name: string;
  email: string;
}

// 2. Use types for unions, intersections, and primitives
type ID = string | number;
type Result<T> = { success: true; data: T } | { success: false; error: string };

// 3. Use interfaces for public APIs (library authors)
// Declaration merging allows consumers to extend your types
interface RequestConfig {
  timeout: number;
}

// 4. Use types for internal implementation details
type InternalState = {
  cache: Map<string, unknown>;
  retryCount: number;
};

// 5. Be consistent within your project
// Pick one style for similar use cases and stick with it

```

## Performance Considerations

- **Compile speed**: the keyword you pick is not a measurable lever — checking cost tracks the size of the resulting object type. The one real cost is a long `&` intersection chain: every member pair has to be compared, while an interface `extends` list resolves to the same members in a shape the checker memoizes and reuses.
- **Errors and hovers**: the difference is readability, not fidelity — a *named* type (either syntax) prints as its name; an anonymous inline shape expands in full wherever it appears.
- **Circular references**: both handle cycles. Interfaces can be forward-referenced freely; a recursive type alias must wrap the cycle in an object, array, or tuple position — `type A = A | string` is rejected as circular, `type A = { next: A }` is fine.

## Summary

| Feature | Type | Interface |
| --------------------------- | :-----: | :------------------------: |
| Object shapes | ✓ | ✓ |
| Primitive / union aliases | ✓ | ✗ |
| Tuples | ✓ | ✗ |
| Intersections | ✓ (`&`) | ✗ (compose with `extends`) |
| Mapped / conditional types | ✓ | ✗ |
| Call & construct signatures | ✓ | ✓ |
| Declaration merging | ✗ | ✓ |
| Class `implements` it | ✓ | ✓ |

## Revision Questions

**Definition**

1. **Q:** What can `type` declare that `interface` cannot, and vice versa?
   **A:** `type` covers unions, intersections, tuples, mapped/conditional types and primitive aliases; `interface` adds declaration merging and the `extends` form libraries use for augmentation. Everything both can express is interchangeable.

2. **Q:** Why do two declarations with the same name collide for `type` but merge for `interface`?
   **A:** A type alias is a one-shot binding to a single type — a second one is a duplicate identifier. An interface is an open contract: each declaration contributes members to the same growing shape.

**How It Works**

3. **Q:** Does `interface Dog extends Animal` do something `type Dog = Animal & { … }` cannot?
   **A:** No for a single object shape — the intersection produces the same members. The differences are elsewhere: `extends` cannot express a union, and only the interface form is mergeable.

4. **Q:** What does structural typing imply about a `type Point` and an identically-shaped `interface PointInterface`?
   **A:** They are interchangeable: a value typed one is assignable to the other, because assignability compares members, never declared names.

**Code Examples**

5. **Q:** Why does `const p: Point = { x: 1, y: 2, z: 3 }` fail while assigning an object literal *variable* with an extra `z` succeeds?
   **A:** Object literals get an excess-property check against the target type; a variable already typed elsewhere is only checked structurally, and extra members never break assignability.

**Common Mistakes**

6. **Q:** What error do you get from `interface Status = "active" | "inactive"`, and what is the fix?
   **A:** It is a syntax error — `interface` only declares a body of members. Write `type Status = "active" | "inactive"` instead.

**Summary**

7. **Q:** When a shape must be extended later by consumers of your library, which keyword should you reach for and why?
   **A:** `interface` — declaration merging lets downstream code add members to the same contract without editing (or forking) your source.

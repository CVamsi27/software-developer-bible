# Types vs Interfaces

A client library needs a request shape that consumers may extend, while a result needs to represent either success or failure. TypeScript has two ways to name contracts, but only one can directly express that alternative.

## Definition

A **type alias** gives a name to any TypeScript type, including object shapes, unions, tuples and functions. An **interface** declares an object contract and can be extended or augmented through **declaration merging**. Both are erased from emitted JavaScript; neither validates runtime values.

> **Textbook Definition:** A type alias names a type expression, whereas an interface declares an extensible object contract. TypeScript compares both through structural assignability; interfaces can merge across declarations, while aliases bind once to a type expression.

## First Principles

1. A type name does not create a new runtime value or identity; it describes which values the checker accepts.
2. A shape lists members that must coexist. A union lists alternatives, so a consumer must first establish which case it has.
3. An interface is intentionally open to extension. That is useful for library extension points and risky when an accidental duplicate declaration changes the shared contract.

## The same object can satisfy either name

```typescript
export {};
type UserRecord = { id: string; name: string };
interface UserContract { id: string; name: string }

function displayName(user: UserContract): string { return user.name; }
const record: UserRecord = { id: "u1", name: "Ada" };
displayName(record); // structural compatibility; the declared names need not match

const richer = { id: "u2", name: "Bob", email: "bob@example.com" };
const accepted: UserRecord = richer; // extra members are allowed on a compatible value
// @ts-expect-error A fresh literal check catches the misspelled property.
const typo: UserRecord = { id: "u3", name: "Cara", emali: "cara@example.com" };
```

The compiler checks that a value supplies the members its target requires. A fresh object literal also receives an excess-property check, which helps catch typos; this is not an exact-object guarantee. A value can have additional properties, and only a runtime schema can validate data arriving from JSON or a network.

## Use an alias for alternatives and computed types

```typescript
export {};
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; error: string };

type Pair<T> = readonly [T, T];
type Identifier = string | number;
interface Formatter { (value: string): string }

const uppercase: Formatter = value => value.toUpperCase();
function describe(result: Result<string>): string {
  return result.ok ? uppercase(result.value) : `Failed: ${result.error}`;
}
```

Interfaces can describe callable or constructable objects, but cannot directly name a primitive or union. Conditional and mapped type expressions also need aliases when their result is named; their transformations are covered in [Type Transformations](../03-type-transformations/INDEX.md).

## Choose how contracts combine

Interfaces extend compatible object contracts. Aliases combine object types with intersections. A class can implement a suitable object contract, but cannot implement a union of alternatives.

```typescript
export {};
type HasId = { id: string };
interface Timestamped extends HasId { createdAt: Date }
interface User extends Timestamped { name: string }
type UserAlias = HasId & { createdAt: Date; name: string };

interface TextValue { value: string }
// @ts-expect-error Extension reports the conflict at the declaration.
interface BadExtension extends TextValue { value: number }
type Impossible = TextValue & { value: number };
// @ts-expect-error A string cannot also be a number.
const impossible: Impossible = { value: 1 };
```

An intersection does not mean “the later property wins.” A value must satisfy both members, so incompatible requirements can make a property `never`. An interface extension generally reports the conflict where the public contract is declared. Prefer the form whose diagnostics make the intended relationship clearest; profile a real type-checking bottleneck before optimizing based on the keyword.

## Make declaration merging deliberate

```typescript
export {};
interface RequestConfig { timeoutMs: number }
interface RequestConfig { traceId?: string }
const config: RequestConfig = { timeoutMs: 5000, traceId: "request-1" };

type ClosedConfig = { timeoutMs: number };
// A second ClosedConfig alias in this scope is a duplicate-name error.
type WithTrace = ClosedConfig & { traceId?: string };
```

Merged non-function members must agree in type and modifiers. Module or global augmentation must target the library declaration in the correct scope; a module-local `interface Window` does not augment the browser global. Use `declare global` from a module only when the application deliberately owns that global extension. See the [declaration merging guide](https://www.typescriptlang.org/docs/handbook/declaration-merging.html).

## Keep the static contract separate from runtime rules

For a database entity, derive narrow output and input views rather than exposing every column as writable:

```typescript
export {};
interface UserEntity {
  id: string;
  name: string;
  email: string;
  passwordHash: string;
  createdAt: Date;
}
type PublicUser = Pick<UserEntity, "id" | "name">;
type RenameUserInput = Pick<UserEntity, "name">;
type ProfilePatch = Partial<Pick<UserEntity, "name" | "email">>;
```

These types do not validate a request, authorize an edit, hash a password or configure an ORM. Validate external input at runtime and whitelist writable fields. For React props, either syntax works for an ordinary shape; a mutually exclusive prop API needs a union. For NestJS injection, an interface is erased, so the provider needs a runtime class, symbol, string or other supported token.

## Summary

Use either syntax for a named object shape. Use an alias for alternatives and computed types; use an interface when consumers need compatible extension or intentional merging. Structural assignability is a compile-time rule, so validate external data and keep runtime ownership, authorization and dependency-injection tokens explicit.

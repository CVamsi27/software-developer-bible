# Type Narrowing

An API response can be valid JSON and still have the wrong shape. If the program casts parsed data to `User`, the compiler accepts the claim without checking the value. Narrowing gives the checker evidence from runtime conditions, so the program can validate the input before using it.

## Definition

**Type narrowing** is the refinement of a value's possible static types along a control-flow path. A **type guard** is a check whose result lets TypeScript remove impossible alternatives from that path. Narrowing changes the checker's model, not the runtime value.

> **Textbook Definition:** TypeScript control-flow analysis refines a variable's apparent type from its declared type by tracking reachable branches, assignments and recognized guards. Assertions bypass that proof; runtime validation must still establish claims about external data.

```text
value: string | number | boolean
  typeof value === "string" -> string branch
  otherwise                  -> number | boolean
    typeof value === "number" -> number branch
    otherwise                  -> boolean branch
```

## First Principles

1. A union lists possibilities; a branch becomes safe only after a check excludes the alternatives that cannot occur there.
2. The checker recognizes runtime evidence such as `typeof`, a discriminant or a predicate signature. An authored predicate is trusted, so its implementation must be correct.
3. `as T` is a claim to the checker, not a conversion or a guard. Use it only when an external invariant has already been established.

## Validate once, then handle a discriminated result

`unknown` accepts any value but cannot be used as a string, object or number until a check narrows it. Assigning `JSON.parse()` to `unknown` prevents its library return type (`any`) from silently flowing through the rest of the program.

```typescript
export {};
interface User { name: string; email: string }
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; error: string };

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null || Array.isArray(value)) return false;
  const candidate = value as Record<string, unknown>;
  return Object.hasOwn(candidate, "name") && typeof candidate.name === "string"
      && Object.hasOwn(candidate, "email") && typeof candidate.email === "string";
}

function parseUser(json: string): Result<User> {
  let value: unknown;
  try { value = JSON.parse(json); }
  catch { return { ok: false, error: "Invalid JSON" }; }
  if (!isUser(value)) return { ok: false, error: "Invalid user shape" };
  return { ok: true, value };
}

function describe(result: Result<User>): string {
  switch (result.ok) {
    case true: return `Welcome, ${result.value.name}`;
    case false: return `Cannot load user: ${result.error}`;
    default: return assertNever(result);
  }
}
function assertNever(value: never): never {
  throw new Error(`Unhandled result: ${JSON.stringify(value)}`);
}

console.log(describe(parseUser('{"name":"Ada","email":"a@example.com"}')));
console.log(describe(parseUser('{"name":42,"email":"a@example.com"}')));
```

The predicate validates only that `name` and `email` are own string properties. It does not enforce email syntax, reject every extra field, authorize the user or prove that the input came from a trusted server. Add those rules only if the domain contract requires them; a generic `JSON.parse(json) as User` checks none of them.

The `ok` field is a **discriminant**, a literal value shared by the union's alternatives. Checking it makes `value` available only in the success branch and `error` only in the failure branch. If a new result case is added, the `assertNever` call fails to type-check until the switch handles it. A `void` handler with an omitted union case can otherwise compile and silently ignore that event.

## Choose a guard that matches the evidence

| Check | What it can establish | Boundary to remember |
| ---------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| `typeof value === "string"` | A primitive string | `typeof null` is `"object"`; a number check also admits `NaN` and infinities. |
| `value instanceof ErrorType` | The value follows that constructor's prototype/`Symbol.hasInstance` rule | Cross-realm instances may fail; it does not validate a serialized object's fields. |
| `"kind" in value` | The property is present somewhere on the object or its prototype chain | Guard null/non-object values first; optional properties can leave multiple union members possible. |
| `value.kind === "saved"` | The matching discriminated-union member | The runtime value still needs validation at an untrusted boundary. |
| `isUser(value)` | Whatever the predicate checks and claims | TypeScript trusts `value is User`; test both accepted and rejected shapes. |

Truthiness is a different contract from presence. `if (label)` rejects an empty but valid label; use `label !== null` when only null means absent. A numeric value can pass a `typeof` check while being `NaN`; require `Number.isFinite` if the domain needs a finite number. Use the check that expresses the actual input rule.

## Let assignments update the flow type

The narrowed type applies along the path where the evidence holds. Assignment changes the flow type to what the new value proves:

```typescript
let label: string | null = " Ada ";
if (label !== null) {
  label = label.trim(); // still a string on this path
  console.log(label.toUpperCase());
}
```

A later assignment may broaden the flow type again if it can produce `null`. When a property is mutated through an alias or callback, the checker may not model every external change; re-check mutable data at the point where its value is consumed.

An explicit predicate such as `(value: unknown): value is string` is trusted. Since TypeScript 5.5, the compiler can infer predicates for some unannotated Boolean functions, such as `const isNumber = (value: unknown) => typeof value === "number"`. Inference requires a return expression and parameter behavior that distinguish both outcomes; an explicit `: boolean` does not expose a predicate.

```typescript
const isNumber = (value: unknown) => typeof value === "number";
const numbers = [1, "skip", 2].filter(isNumber); // number[]

const maybeScores: Array<number | undefined> = [0, 8, undefined];
const scores = maybeScores.filter(score => score !== undefined); // keeps zero
```

Checking `score !== undefined` preserves the valid value `0`; filtering with `!!score` would discard it. Predicate inference follows what the Boolean expression proves, not the programmer's intended domain.

## Summary

Narrowing removes impossible types from the current control-flow path; it does not convert a value or validate an external contract by itself. Start uncertain input as `unknown`, validate it with guards, use discriminated unions to route known cases, and make exhaustiveness visible with `never`. Treat authored predicates and assertions as claims whose runtime evidence belongs to the application.

# Type Narrowing

## Definition

**Type narrowing** lets TypeScript use a more specific type after a check. For example, a value may start as `string | number`; inside a branch that checks `typeof value === 'string'`, TypeScript treats it as a string. The compiler follows branches and assignments, called **control flow analysis**. A check that distinguishes types is called a **type guard**.

> **Textbook Definition:** Narrowing refines a value's possible static type through control-flow analysis and type guards. The refinement follows evidence such as discriminants or checks, while runtime validation remains necessary for untrusted data.

```text
value: string | number | boolean
  typeof value === "string" -> string branch
  otherwise                  -> number | boolean
    typeof value === "number" -> number branch
    otherwise                  -> boolean branch
```

The arrows remove possibilities along a path; they do not convert the value. The else branch gets the alternatives excluded by the earlier check, which is why branch order matters.

## First Principles

Narrowing exists because a union's safety depends on *proving* which member you hold:

1. **The compiler tracks control flow, not just declarations** — an `if (typeof x === 'string')` re-types `x` in the branch: the type is a function of the path, which is what makes unions (→ 10.2.1.01) usable at all.
2. **Runtime checks supply evidence the compiler can track** — `typeof`, `in`, `instanceof`, discriminants (→ 10.2.2.03), predicates and reachability all refine what can occur on a path. An authored `x is T` predicate is trusted by the compiler; its body still needs a correct runtime check.
3. **Assertions (`as`) are the escape hatch that *disables* the proof** — use them only where the human knows something the checker can't; every `as` is an unverified claim.

## Why It Matters

Senior engineers design discriminated unions (`type Shape = { kind: 'circle'; r: number } | { kind: 'square'; s: number }`) to enable exhaustive narrowing with `switch`/`never`. They write type predicates (`function isUser(x: unknown): x is User`) to validate external data (API responses, JSON.parse).

## How It Works

Run each example as an independent TypeScript module with `strict` enabled. Some later snippets explicitly reuse Shape, Action and assertNever from the named example. Diagnostic examples use `@ts-expect-error` for the rejected line rather than being complete successful programs. Type predicates are trusted descriptions of their checks; tests must verify the runtime condition.

### Nullish absence differs from falsy data

A truthiness check excludes empty strings and zero as well as null/undefined. For a nullable label, `label !== null` keeps the valid empty string. `typeof x === "number"` also admits NaN and Infinity, so a finite-number data contract needs `Number.isFinite`. Equality between variables can narrow both to their overlapping possibilities. These are different checks for different input contracts.

### typeof

```typescript
// Narrow primitive types
function processValue(value: string | number | boolean): string {
  if (typeof value === "string") {
    return value.toUpperCase(); // string methods available
  } else if (typeof value === "number") {
    return value.toFixed(2); // number methods available
  } else {
    return value ? "true" : "false"; // boolean
  }
}

```

Calling processValue("save") takes the string branch and returns SAVE; processValue(2) takes the number branch and returns "2.00"; false reaches the remaining Boolean branch. The compiler follows exactly those checks.

### instanceof

```typescript
// Narrow class instances
class HttpError {
  constructor(public status: number, public message: string) {}
}

class NetworkError {
  constructor(public message: string, public code: string) {}
}

function handleError(error: HttpError | NetworkError): string {
  if (error instanceof HttpError) {
    return `HTTP ${error.status}: ${error.message}`;
  } else {
    return `Network ${error.code}: ${error.message}`;
  }
}

```

`instanceof` follows constructor/prototype behavior, not a JSON field shape. A plain parsed object with status/message is not an HttpError instance; constructors from another realm and customized instanceof behavior also matter.

### in Operator

```typescript
// Check for property existence
interface Bird {
  fly(): void;
  layEggs(): void;
}

interface Fish {
  swim(): void;
  layEggs(): void;
}

function move(animal: Bird | Fish): void {
  if ("fly" in animal) {
    animal.fly(); // Bird
  } else {
    animal.swim(); // Fish
  }
}

```

`in` accepts inherited properties too, and an optional property may exist on more than one union member. It proves presence under the declared union; it is not enough to validate an arbitrary value or establish a callable method.

### User-Defined Type Guards

```typescript
// Type guard function
interface Cat {
  meow(): void;
  purr(): void;
}

interface Dog {
  bark(): void;
  fetch(): void;
}

function isCat(animal: Cat | Dog): animal is Cat {
  return "meow" in animal;
}

function interact(animal: Cat | Dog): void {
  if (isCat(animal)) {
    animal.meow(); // Cat
    animal.purr(); // Cat
  } else {
    animal.bark(); // Dog
    animal.fetch(); // Dog
  }
}

```

The isCat predicate assumes an already valid Cat-or-Dog value; checking one distinguishing required property works for that union. It does not validate all Cat fields on unknown JSON. A predicate that always returns true can compile while lying about the runtime data.

TypeScript 5.5 and later can infer a type predicate for some unannotated Boolean functions. The function must have no explicit return annotation, a single return with no implicit return path, and no mutation of the parameter; its Boolean expression must refine that parameter on both true and false outcomes. This is narrower than “the callback returns a Boolean.”

```typescript
const isNumber = (value: unknown) => typeof value === "number";
// In TS 5.5+, the inferred return type is `value is number`.
const numbers = [1, "skip", 2].filter(isNumber); // number[]

const maybeScores: Array<number | undefined> = [0, 8, undefined];
const scores = maybeScores.filter(score => score !== undefined); // number[]; keeps 0
const truthyScores = maybeScores.filter(score => !!score); // (number | undefined)[]; drops 0 at runtime
```

The explicit `score !== undefined` check preserves zero. A function annotated only as returning `boolean` does not expose an inferred predicate, and TypeScript does not infer a number predicate from `!!score`: a false result could mean either `undefined` or the valid value `0`. An explicit `value is T` signature is trusted by the checker; its implementation must uphold both sides of the claim.

### Discriminated Unions

```typescript
// Union with common discriminant
type Shape =

  | { kind: "circle"; radius: number }
  | { kind: "rectangle"; width: number; height: number }
  | { kind: "triangle"; base: number; height: number };

// Exhaustive check
function assertNever(x: never): never {
  throw new Error("Unexpected value: " + x);
}

function areaExhaustive(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
    case "triangle":
      return (shape.base * shape.height) / 2;
    default:
      return assertNever(shape); // Compile error if missing case
  }
}

```

### The never Type

```typescript
// never represents values that never occur
function throwError(message: string): never {
  throw new Error(message);
}

function infiniteLoop(): never {
  while (true) {}
}

// areaExhaustive above uses never after every Shape case is excluded.
```

## Code Examples

### Practical Examples

```typescript
// ─── API Response handling ────────────────────────────────────
type ApiResponse<T> =

  | { status: "success"; data: T }
  | { status: "error"; error: string }
  | { status: "loading" };

function handleResponse<T>(response: ApiResponse<T>): string {
  switch (response.status) {
    case "success":
      return `Data: ${JSON.stringify(response.data)}`;
    case "error":
      return `Error: ${response.error}`;
    case "loading":
      return "Loading...";
  }
}

// ─── Type-safe event handling ─────────────────────────────────
type AppEvent =

  | { type: "click"; x: number; y: number }
  | { type: "keypress"; key: string }
  | { type: "scroll"; top: number };

function handleEvent(event: AppEvent): void {
  switch (event.type) {
    case "click":
      console.log(`Click at (${event.x}, ${event.y})`);
      break;
    case "keypress":
      console.log(`Key pressed: ${event.key}`);
      break;
    case "scroll":
      console.log(`Scrolled to ${event.top}`);
      break;
  }
}

// Parsing supplies unknown data; validation earns the User type.
interface User { name: string; email: string }
function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) return false;
  const object = value as Record<string, unknown>;
  return typeof object.name === "string" && typeof object.email === "string";
}
function parseUser(json: string): User | null {
  let value: unknown;
  try { value = JSON.parse(json); } catch { return null; }
  return isUser(value) ? value : null;
}
console.log(parseUser('{"name":"Ada","email":"a@example.com"}')?.name); // Ada
console.log(parseUser('{"name":42,"email":"a@example.com"}')); // null

```

A valid JSON string proves only syntax. The validator checks both required fields and rejects null/wrong types; it intentionally accepts extra properties and checks no email format or authorization. A generic `JSON.parse(json) as T` cannot perform those checks.

### Advanced Patterns

```typescript
// ─── Type-safe reducer ────────────────────────────────────────
type Action =

  | { type: "INCREMENT"; amount: number }
  | { type: "DECREMENT"; amount: number }
  | { type: "RESET" };

interface State {
  count: number;
}

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "INCREMENT":
      return { count: state.count + action.amount };
    case "DECREMENT":
      return { count: state.count - action.amount };
    case "RESET":
      return { count: 0 };
  }
}

// ─── Type-safe validation ─────────────────────────────────────
interface ValidationSuccess<T> {
  valid: true;
  value: T;
}

interface ValidationFailure {
  valid: false;
  errors: string[];
}

type ValidationResult<T> = ValidationSuccess<T> | ValidationFailure;

function validate(input: unknown): ValidationResult<string> {
  if (typeof input === "string") {
    return { valid: true, value: input };
  }
  return { valid: false, errors: ["Expected string"] };
}

function processInput(input: unknown): void {
  const result = validate(input);
  if (result.valid) {
    console.log(result.value.toUpperCase()); // string
  } else {
    console.error(result.errors); // string[]
  }
}

// ─── Type-safe optional chaining ──────────────────────────────
function getNestedValue(obj: unknown, path: readonly string[]): string | undefined {
  let current: unknown = obj;
  for (const key of path) {
    if (typeof current !== "object" || current === null ||
        !Object.hasOwn(current, key)) return undefined;
    current = (current as Record<string, unknown>)[key];
  }
  return typeof current === "string" ? current : undefined;
}
console.log(getNestedValue({ profile: { name: "Ada" } }, ["profile", "name"])); // Ada

```

The path walker only reads own properties of data objects; it does not coerce primitives or traverse inherited names. Passing string segments as an array avoids ambiguous dots inside a key. Reads can still invoke getters/proxy traps, so use trusted plain data rather than treating it as a sandbox.

## Real-World Use Cases

- **Discriminated API responses** — `if ('error' in res)` / `res.status === 'ok'` narrows before data access; the backbone of every API client (→ 20.3.3.02's error shape).
- **Form field validation** — `typeof value === 'string'` per field drives both runtime checks and the compiled types.
- **Exhaustive switch over state machines** — `default: x satisfies never` turns a missed checkout step into a compile error instead of a dead screen (→ 10.2.4.01).

## Common Mistakes

### 1. Forgetting Exhaustive Checking

```typescript
// Bad: a void handler missing a case compiles — the branch never runs.
// (Value-returning functions at least fail with TS2366 "Function lacks
// ending return statement"; void handlers fail silently.)
function handle(action: Action): void {
  switch (action.type) {
    case "INCREMENT":
      console.log("up");
      break;
    case "RESET":
      console.log("reset");
      break;
    // DECREMENT missing — no error, the event just vanishes
  }
}

// Good: route the now-impossible remainder through assertNever, so
// adding a union member later puts a compile error on this switch.
function handleAll(action: Action): void {
  switch (action.type) {
    case "INCREMENT":
      console.log("up");
      break;
    case "RESET":
      console.log("reset");
      break;
    case "DECREMENT":
      console.log("down");
      break;
    default:
      assertNever(action); // (from How It Works)
  }
}

```

### 2. Forgetting `typeof null === "object"`

```typescript
interface User {
  name: string;
  email: string;
}

// Bad: `typeof null` is "object", so the guard keeps null in the type
function printUser(user: User | null) {
  if (typeof user === "object") {
    // @ts-expect-error typeof null is object, so user can still be null.
    console.log(user.name);
  }
}

// Good: check the value directly
function printUser(user: User | null) {
  if (user !== null) {
    console.log(user.name); // user: User
  }
}

```

### 3. Not Using Type Guards

```typescript
// Bad: an explicitly boolean-returning helper does not expose an authored predicate — the call stays `unknown`,
// so the branch needs an assertion to do anything with it
function isString(value: unknown): boolean {
  return typeof value === "string";
}

function handle(value: unknown) {
  if (isString(value)) {
    (value as string).toUpperCase(); // Unsafe!
  }
}
```

```typescript
// Good: declare the claim in the signature (`value is string`) and the
// branch narrows automatically
function isString(value: unknown): value is string {
  return typeof value === "string";
}

function handle(value: unknown) {
  if (isString(value)) {
    value.toUpperCase(); // value: string
  }
}
```

## Best Practices

1. **Model variants as discriminated unions** — one literal `kind`/`status`/`type` field makes every `switch` branch provable and every missed branch visible.
2. **Make exhaustiveness explicit** — route the impossible `default` through `assertNever` (or `x satisfies never`) so a new union member errors on the switch itself, not somewhere downstream.
3. **Prefer guards to assertions** — `typeof`/`instanceof`/`in`/predicates prove the narrowing; `as` only silences the check. Reach for assertions only at boundaries you have verified by hand.
4. **Write validators as predicates** — `function isUser(x: unknown): x is User` makes the check reusable at every call site instead of re-asserting inline.
5. **Mind where narrowing dies** — it is path-sensitive: assignment changes the flow type to what that assignment proves; captured mutations and unsafe aliases can invalidate assumptions beyond the checker's analysis, so a guard followed by a mutation must re-prove the type before the next use.

## Performance Considerations

- Narrowing itself is erased — guards compile to the plain JS check you wrote (`typeof`, `in`, `instanceof`, `===`), so the only runtime cost is that check.
- Checker work depends on the size and shape of the types flowing through a function; do not attribute a slow build to a guard keyword without profiling the program.
- The never annotation and satisfies operator are erased, but a declared variable/underlying expression can still emit JavaScript. The assertNever helper deliberately emits a runtime throw for unexpected input. Static exhaustiveness does not validate an external payload.

## Summary

Type narrowing refines the checker's flow type along paths that its control-flow analysis understands; it does not convert the runtime value. Discriminated unions give you the shape to switch on, `never` makes missing branches a compile error, and predicates carry claims the checker trusts. Use runtime guards for actual data validation and assertions only where an external invariant has been established.

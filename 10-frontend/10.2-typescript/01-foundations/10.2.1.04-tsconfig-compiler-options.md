# tsconfig & Compiler Options

## Definition

**tsconfig.json** is the configuration file read by TypeScript's compiler, `tsc`, and much of its tooling. It selects the files to check, how strict the checks should be, which JavaScript module syntax to produce and how to find imported modules. The options below cover four groups: **strictness**, **modules and module lookup**, **generated output and builds**, and **compatibility with other modules and tools**.

> **Textbook Definition:** `tsconfig.json` defines a TypeScript compilation project by specifying its input files and compiler behavior. Options govern checking, module interpretation, output and resolution; they do not automatically configure the runtime or bundler.

## First Principles

A project has source files, a checker, a transform tool and a runtime loader. Each sees a different part of the program. Configuration must make their assumptions agree; stronger checking alone cannot repair missing runtime APIs or invalid emitted imports.

1. **`strict` groups checks about values and calls** (such as implicit `any`, nullability and function assignability). Enabling it does not validate external data or prevent a developer from writing explicit `any` or assertions.
2. **Module settings describe assumptions for the transform and loader** (→ 40.5.1) — a checker/bundler/Node mismatch can pass type checking and still fail at runtime.
3. **Options are a project contract**: CI should use the committed config and compiler version (→ 40.3.2.02), so editors and builds agree about which files and checks apply.

## Why It Matters

Compiler options explain why checking, emitted code and runtime behavior can disagree. Senior-level discussions often trace an import failure to module-resolution settings, a project-reference failure to declaration output, or an unchecked null to the selected strictness flags. Build options such as `incremental`, project references and `skipLibCheck` trade configuration and checking work against build time; none makes an application correct by itself.

## Trace a source file through checking and loading

For a Vite application, TypeScript selects files and checks their imports/types; the bundler emits browser code. For a Node-run package, the emitted files must follow Node's loader rules. A successful checker run does not install runtime APIs or rewrite every import alias. Separate the stages before choosing options:

```text
config + source → TypeScript checks → bundler/tsc emit → runtime loader
   ↑                 ↑                     ↑                ↑
 include/extends    strict/lib       target/module       actual imports/APIs
```


### The strict Flag Family

`"strict": true` enables a version-dependent family, whose individual members can still be overridden. The following are common members:

| Flag | What the check changes | Boundary |
| --------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `strictNullChecks` | Keeps `null` and `undefined` distinct from other types. | It does not check whether parsed or network data matches its declared type. |
| `noImplicitAny` | Reports declarations that would otherwise infer `any`. | Explicit `any` remains allowed. |
| `strictFunctionTypes` | Checks function parameter assignability more soundly. | Method parameters retain a compatibility exception; see [Type Variance](../02-generics-and-inference/10.2.2.04-type-variance.md). |
| `strictPropertyInitialization` | Checks that declared class fields are initialized or definitely assigned. | Assertions and control-flow limits can bypass the intended guarantee. |
| `noImplicitThis` | Reports `this` expressions that would be implicitly `any`. | It does not choose the receiver at runtime. |
| `strictBindCallApply` | Checks arguments supplied through `.bind`, `.call` and `.apply`. | The result depends on the available function signature. |
| `alwaysStrict` | Emits strict-mode behavior for scripts where needed. | ECMAScript modules are strict mode already. |
| `useUnknownInCatchVariables` | Types an unannotated catch variable as `unknown`. | Narrow it before using properties or methods. |
| `strictBuiltinIteratorReturn` (TS 5.6+) | Prevents built-in iterator completion values from silently becoming `any`. | Inspect `.done` before using `.value` when completion types differ. |

TypeScript 6.0 and 7.0 enable `strict` by default; older compiler versions did not. Set it explicitly when a project supports multiple compiler versions. Two useful checks sit outside the `strict` family: `noUncheckedIndexedAccess` makes indexed reads account for a possibly missing element, and `exactOptionalPropertyTypes` distinguishes an absent optional property from one explicitly set to `undefined` during assignment. Reading an optional property can still produce `undefined`.

### Choose module resolution to match the loader

| Settings | Models | Import and package behavior | Use when |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `module: "node16"` + `moduleResolution: "node16"` | Node 16 dual ESM/CJS rules | Relative ESM imports use emitted extensions such as `.js`; reads package conditions. | Maintaining code tied to Node 16 semantics. |
| `module: "node18"` + `moduleResolution: "node16"` (TS 5.8+) | Node 18 dual ESM/CJS rules | Adds Node 18's import-attributes behavior to the Node module contract. | Maintaining code deliberately pinned to Node 18. |
| `module: "node20"` + `moduleResolution: "node16"` (TS 5.9+) | Stable Node 20 module rules | Models Node 20's `require(ESM)` support, available in newer Node 20 releases; resolution remains `node16`. | A project deliberately targeting Node 20 semantics. |
| `module: "nodenext"` + `moduleResolution: "nodenext"` | The current Node ESM/CJS rules understood by that TypeScript release. | Can change as Node support changes; relative ESM imports use emitted extensions such as `.js`. | Node packages that follow current Node behavior. |
| `module: "preserve"` or `"esnext"` + `moduleResolution: "bundler"` (TS 5.0+) | Modern bundler resolution | Models package `exports`; generally permits extensionless relative imports. | Applications whose bundler, not Node, loads the modules. |

Use a compatible `module`/`moduleResolution` pair: `preserve` or `esnext` with `bundler`; `node16`, `node18` or `node20` with `node16`; and `nodenext` with `nodenext`. There is no `node20` value for `moduleResolution`. A checker using legacy `node10` while the actual bundler understands a package's `"exports"` map can resolve a different entry point, so type checking and runtime loading disagree.

```jsonc
{
  // App bundled by Vite:
  "module": "preserve",
  "moduleResolution": "bundler"
}
```

```jsonc
{
  // Library published to npm, consumed by Node ESM:
  "module": "nodenext",
  "moduleResolution": "nodenext"
}
```

For a package pinned to Node 20, use `"module": "node20"` with `"moduleResolution": "node16"`; `node20` is a module mode, not a resolution value.

### isolatedModules — What Single-File Transpilers Need

Transpilers such as esbuild, SWC and Babel can transform each TypeScript file without type-checking the whole program. `isolatedModules: true` makes TypeScript report constructs whose behavior depends on whole-program type information; it does not switch TypeScript into a different emitter.

```typescript
// With isolatedModules, each of these needs explicit intent:

// If ./foo exports an interface named Foo, use a type-only re-export.
export { Foo } from "./foo";

// GOOD: type-only re-export is explicit
export type { Foo } from "./foo";

// const enums are not rejected outright — but a file-at-a-time tool
// cannot inline across files, so a cross-file member reference stays a
// runtime import of a real object. Ambient const enums ARE rejected
// (TS2748): one file can't inline a declaration it can't even see.
```

`verbatimModuleSyntax` is the stricter sibling: it requires `import type`/`export type` anywhere an import is type-only (plain `import { Foo }` of a type-only binding errors — isolatedModules only flags *re*-exports) and forbids the emitter from rewriting your module syntax. It preserves runtime import/export syntax while explicitly type-only syntax is erased; it is not a promise that every source byte survives emission.

Run `tsc --noEmit` alongside your bundler so type errors gate CI even though the bundle step ignores them.

### Incremental and Composite Builds

| Option | Effect |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `incremental: true` | Stores `.tsbuildinfo` so later runs can reuse project state and avoid unnecessary checking. |
| `composite: true` | Makes a project referenceable and enables build-mode metadata; referenced projects produce declarations, though editors may use source redirects. |
| `tsBuildInfoFile` | Where the state file lives (put it in build output, not src) |

A monorepo can connect packages through `references` and enable `composite` for each referenced project. `tsc -b` follows those dependencies and rebuilds projects whose inputs have changed. This forms a build dependency graph: a package must be built after the packages it uses.

### skipLibCheck Trade-off

`skipLibCheck: true` skips type-checking of every `.d.ts`. You still get full checking of your own code against those declarations.

- **Benefit**: can reduce work when dependencies contribute many declaration files and may avoid some declaration-to-declaration conflicts.
- **Costs**: a broken or lying declaration file passes silently; errors surface later in your own files, further from the cause.

Use it as a deliberate checking/performance tradeoff. It also skips checking your own declaration files; pinning dependencies does not prove declarations are correct. Consider a declaration-checking CI job when publishing a library or diagnosing conflicts.

## Code Examples

### A browser app checked by tsc and emitted by a bundler

Save this as `tsconfig.json` next to `src`. Install the application's React types and bundler; configure the same `@` alias in that bundler. The two earlier module examples are `compilerOptions` fragments, not complete root configs. TypeScript 6+ defaults `types` to an empty list, so explicitly include the ambient packages this project needs. Because this example checks `vite.config.ts`, install `@types/node` and list both `vite/client` and `node`.

```jsonc
{
  "compilerOptions": {
    // ── Language level ────────────────────────────────────────────
    "target": "ES2022",              // set the checker's language target; configure the bundler too
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "preserve",            // don't rewrite module syntax; bundler owns it
    "moduleResolution": "bundler",   // extensionless imports + exports maps
    "types": ["vite/client", "node"], // ambient Vite client and Node config globals

    // ── Strictness: non-negotiable core ───────────────────────────
    "strict": true,                  // version-dependent family of checks
    "noUncheckedIndexedAccess": true,// arr[i] => T | undefined
    "noImplicitOverride": true,      // overrides must say so
    "noFallthroughCasesInSwitch": true,

    // ── Bundler/transpiler reality ────────────────────────────────
    "isolatedModules": true,         // check single-file transform restrictions
    "verbatimModuleSyntax": true,    // forces `import type` clarity,
                                     // keeps emit honest
    "resolveJsonModule": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,

    // ── Speed pragmatism ──────────────────────────────────────────
    "skipLibCheck": true,
    "incremental": true,
    "tsBuildInfoFile": ".cache/tsc/tsbuildinfo",

    // ── Emit: none — bundler emits, tsc only type-checks ──────────
    "noEmit": true,

    // ── Project shape ─────────────────────────────────────────────
    "jsx": "react-jsx",
    "paths": { "@/*": ["./src/*"] }
  },
  "include": ["src", "vite.config.ts"]
}
```

The include setting selects initial project files; imports can pull other files into the graph, and exclude does not firewall an imported file. lib supplies descriptions such as Promise/DOM; it does not create those APIs. With this noEmit config, a successful tsc -p . checks the files but produces no runnable output.

For a focused trace, put the following in src/main.ts and run `tsc -p .` with the app config above:

```typescript
export {};
const labels: string[] = ["saved"];
// @ts-expect-error noUncheckedIndexedAccess admits a missing index.
console.log(labels[0].toUpperCase());
const first = labels[0];
if (first !== undefined) console.log(first.toUpperCase()); // SAVED
```

The array's declared type permits an empty array, so the indexed read is string-or-undefined even though this initializer has one item. The guard narrows first to string before accessing its method. Remove the diagnostic marker to see the rejected unsafe read; this is checker evidence, not runtime protection. Run the guard version through the bundler to observe SAVED. Turning strict or indexed checking off accepts more code without changing the missing-value runtime behavior.

### Library tsconfig Differences

```jsonc
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": {
    // Libraries emit real files consumed elsewhere:
    "noEmit": false,
    "declaration": true,             // ship .d.ts
    "declarationMap": true,          // editor "go to definition" into source
    "sourceMap": true,
    "outDir": "dist",
    "module": "nodenext",
    "moduleResolution": "nodenext"   // consumers run you under real Node rules
  },
  "include": ["src"]
}
```

In the library project, supply tsconfig.base.json without noEmit or incompatible browser-only settings, and choose its package.json type/extensions and exports to match NodeNext output. Type declarations describe the emitted implementation rather than replacing it.

### Monorepo Project References

```jsonc
// packages/core/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,             // required for being referenced
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}
```

```jsonc
// apps/web/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "composite": true },
  "references": [{ "path": "../../packages/core" }],
  "include": ["src"]
}
```

```bash
# Build only what changed, in dependency order:
tsc -b apps/web
```

For core then web, tsc -b apps/web first builds referenced core declarations, then checks/builds web using that contract. A solution config can have files:[] with references. References express build dependencies; packages still need correct imports/exports and install/workspace resolution. Re-run with the same compiler version; cached build state is an optimization, not the authoritative source.

### Detecting Config Drift in CI

This script uses the TypeScript 6 compiler API and Node.js globals; type-check it with `@types/node`. TypeScript 7.0's CLI does not expose the previous compiler API. For 7.0 toolchains, use the published `@typescript/typescript6` compatibility package only after checking its package documentation, or compare effective compiler options with `tsc --showConfig`.

```typescript
// scripts/check-tsconfig.ts — run with a TS-capable runner such as tsx.
import * as ts from "typescript";
const parsed = ts.getParsedCommandLineOfConfigFile("tsconfig.json", {}, {
  ...ts.sys,
  onUnRecoverableConfigFileDiagnostic(diagnostic) {
    console.error(ts.flattenDiagnosticMessageText(diagnostic.messageText, "\n"));
    process.exitCode = 1;
  },
});
if (!parsed || parsed.errors.length > 0) {
  for (const diagnostic of parsed?.errors ?? []) {
    console.error(ts.flattenDiagnosticMessageText(diagnostic.messageText, "\n"));
  }
  process.exit(1);
}
const required = ["strict", "noUncheckedIndexedAccess", "isolatedModules"] as const;
for (const flag of required) {
  if (parsed.options[flag] !== true) {
    console.error(`tsconfig regression: ${flag} must be enabled`);
    process.exitCode = 1;
  }
}
```

### TypeScript 6.0 and 7.0 change defaults and accepted options

As of October 2026, TypeScript 7.0 is the current native compiler; TypeScript 6.0 is its compatibility release. TypeScript 6.0 defaults `strict` to `true` and ambient `types` to an empty list, deprecates `baseUrl` and `node10` resolution, and TypeScript 7.0 no longer accepts those deprecated options. Remove `baseUrl` and write paths relative to the config file; list required ambient packages instead of relying on every visible `@types` package. TypeScript 7.0's CLI does not expose the previous compiler API; the published `@typescript/typescript6` package is a migration option for API consumers, not a guarantee that existing scripts work unchanged. Pin the compiler version, inspect the effective config with `tsc --showConfig -p .`, and run consumer/build tests with that exact version. See the [TypeScript 6 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html) and the [TypeScript 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/).

## Real-World Use Cases

1. **Vite SPA**: `bundler` resolution, `noEmit`, `strict`, `skipLibCheck` — tsc exists purely to gate CI while esbuild bundles.
2. **npm library**: use loader-compatible output and declarations. NodeNext selects module format by file extension/package context; dual publishing also needs deliberate file extensions, package exports and consumer tests, not just two arbitrary builds.
3. **Nx/Turbo monorepo**: references for packages that need coordinated declaration builds; cache valid outputs/build state and measure incremental savings.
4. **Gradual JS-to-TS migration**: start with `allowJs: true`, `checkJs: false`, `strict: false` in a dedicated config, then ratchet `strictNullChecks` per-directory using path-scoped configs.
5. **Jest + ESM**: tests transpile via swc, so `isolatedModules` catches type-dependent exports before they become silent runtime no-ops.

## Common Mistakes

### 1. Shipping Without strict

```jsonc
// BAD: nulls and anys flow freely; types are decoration
{ "compilerOptions": { "strict": false } }
```

```jsonc
// GOOD: enable strict from commit #1; later migration requires deliberate boundary checks
{ "compilerOptions": { "strict": true } }
```

### 2. Resolution Mismatch With the Runtime

```jsonc
// BAD: bundler app configured like legacy Node — exports maps ignored,
// deep-import errors appear only in some tools
{ "moduleResolution": "node" }
```

```jsonc
// GOOD: mirror whoever actually loads the files
{ "moduleResolution": "bundler" }   // Vite/webpack app
```

### 3. Missing Extensions Under nodenext

```typescript
// BAD: works in bundler mode, fails to resolve under nodenext ESM
import { helper } from "./helper";

// GOOD: Node ESM requires explicit extensions (pointing at emitted .js)
import { helper } from "./helper.js";
```

### 4. Treating skipLibCheck as a Style Choice to Argue About

```typescript
// Misunderstanding: "it skips checking my code" — it does not.
// It skips checking DECLARATION FILES (.d.ts). Your sources are
// fully checked against them either way.
```

### 5. Composite Without declaration

```jsonc
// BAD: composite implies declaration; this fails to build
{ "composite": true, "declaration": false }
```

```jsonc
// GOOD: let composite imply it, add declarationMap for DX
{ "composite": true, "declarationMap": true }
```

### 6. Relying on Whole-Program Type Tricks With a Single-File Transpiler

```typescript
// Ambient const enums are rejected under isolatedModules — one file
// can't inline a declaration it cannot see:
declare const enum AmbientStatus { Active, Disabled }
const s = AmbientStatus.Active; // Error TS2748

// Ordinary const-enum emission depends on the transpiler/options. A file-at-a-time
// tool cannot generally inline a value from another file's declaration — the "zero-cost" enum ships as a real object
// and cross-file members stay runtime imports.
const enum Status { Active, Disabled }

// Plain union of literals: genuinely zero-runtime, transpiler-proof
type StatusValue = "active" | "disabled";
```

## Best Practices

1. **Set `"strict": true` explicitly in new projects** and consider `noUncheckedIndexedAccess`; the latter is separate from `strict` and catches possibly absent indexed values.
2. **Choose `moduleResolution` from your loader**, not habit: `bundler` for apps, `nodenext` for publishable packages.
3. **Keep `isolatedModules` and `verbatimModuleSyntax` on** so your codebase survives any transpiler swap.
4. **Gate CI with `tsc --noEmit` separately from the bundler** — bundlers ignore type errors by design.
5. **Use `skipLibCheck` deliberately**: know it hides third-party declaration bugs; pin versions and investigate conflicting declarations.
6. **Structure monorepos with `references` + `composite`** and cache `.tsbuildinfo` so rebuilds touch only changed packages.
7. **Review checking-flag changes as type-safety changes**: relaxing a flag changes which programs the compiler accepts, so record the reason and migration boundary.

## Performance Considerations

| Lever | Typical effect |
| --------------------------- | --------------------------------------------------------------------------------------------- |
| `skipLibCheck` | Skips checking declarations; measure whether it materially reduces this project's check time. |
| `incremental` | Reuses prior build state to avoid unnecessary work. |
| `composite` + references | Lets build mode follow project dependencies and rebuild affected projects. |
| Deliberate input scope | Avoid checking unrelated generated/vendor files; imports still enter the graph |
| `noUncheckedIndexedAccess` | Slightly more checking work — worth it for the bug class it kills |

`paths` helps the checker resolve aliases; it does not by itself rewrite those specifiers for Node. `target` controls eligible syntax emission and default libraries; `lib` describes available APIs without polyfilling them. Validate build output and run it with the actual loader as well as checking types.

## Summary

- Set `strict` explicitly across compiler versions; add `noUncheckedIndexedAccess` when the project can account for possibly absent indexed values.
- Choose a compatible pair: `bundler` for bundled apps; `module: "node16"`, `"node18"` or `"node20"` with `moduleResolution: "node16"` for a fixed Node contract; or `nodenext` for both settings when following current Node rules.
- `isolatedModules` exists because esbuild/swc/Babel cannot see the whole program; it bans ambiguous type/value exports.
- `incremental` speeds local checks; `composite` enables monorepo reference builds.
- `skipLibCheck` trades declaration-file checking for reduced work; it can hide incorrect dependency and project declarations.
- A senior tsconfig is short, annotated, and treated as an architectural contract.

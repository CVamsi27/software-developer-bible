# tsconfig & Compiler Options

A Vite app can pass TypeScript checks while its bundle still fails at runtime because the checker and bundler may resolve imports differently. A `tsconfig.json` defines what the compiler accepts and how its tools interpret the project; it must agree with the tool that actually emits and loads the program.

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noEmit": true,
    "module": "preserve",
    "moduleResolution": "bundler"
  },
  "include": ["src"]
}
```

## Definition

A **TypeScript project configuration** is written in JSON with comments. It selects source files and sets the compiler options used for parsing, type checking, module resolution and, when enabled, output generation. Build tools and runtimes have separate configuration and behavior.

> **Textbook Definition:** `tsconfig.json` supplies project scope and compiler options to the TypeScript compiler. It controls static checking and optional emission, but does not configure a bundler, install runtime APIs or validate values when the program runs.

## First Principles

**Checking and execution are different stages**: TypeScript can reject source or emit JavaScript, but a bundler or runtime ultimately decides how modules load. **Library declarations describe APIs; they do not provide them** — `lib`, `types`, and package declarations affect what the checker knows, not what exists in the deployed environment. And **compiler versions change defaults and accepted options**, so pin the version, inspect the effective configuration, and test the actual build/runtime pair during upgrades.

## How It Works

### 1. Follow One File Through the Project

The compiler reads the root config and its `extends`, selects root files through `files` or `include`, and follows imports into the program graph. `exclude` filters root discovery; it is not a firewall around imported files. Inspect the effective settings with `tsc --showConfig -p .` before diagnosing a mismatch.

For a bundled browser app, the following choices keep type checking separate from bundler output:

```jsonc
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "preserve",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "noEmit": true,
    "types": ["vite/client"]
  },
  "include": ["src"]
}
```

`target` controls eligible syntax output and influences the default library set; with `noEmit`, the bundler still needs its own target. `lib` supplies declarations such as DOM and Promise APIs, but does not polyfill them. Since TypeScript 6, `types` defaults to an empty list; name required ambient packages explicitly. Add `node` only if Node globals are required in the checked project, such as for `vite.config.ts`.

`strict` enables the strict-checking family, including `strictNullChecks` and `noImplicitAny`. It does not include every useful safety option: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `noImplicitOverride` remain separate. Turn on the checks the data model supports, then fix or document genuine boundary cases rather than silencing them with `any` or assertions.

### 2. Match Module Settings to the Loader

Choose one compatible pair, then test with the loader and package metadata used in production.

| Runtime owner | `module` | `moduleResolution` | Contract to verify |
| ---------------------------- | --------------------------------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bundler such as Vite | `preserve` or `esnext` | `bundler` | Bundler understands package `exports`, aliases and any extensionless relative imports. |
| Fixed Node 16/18/20 behavior | `node16` (TS 4.7), `node18` (TS 5.8) or `node20` (TS 5.9) | `node16` | Package `type`, conditional exports and the deployed Node release agree; Node ESM source imports use emitted extensions such as `.js`. `node20` is a `module` mode, not a resolution value; it models Node 20 behavior including `require(ESM)` support present in newer Node 20 releases, so pin a compatible runtime floor. |
| Current Node behavior | `nodenext` | `nodenext` | These rules can evolve with TypeScript's model of Node; test the exact compiler/runtime combination. |

For an application, `paths` helps TypeScript resolve an alias but does not rewrite the emitted import. Configure the bundler or loader with the same alias. For a published library, make package `"type"`, file extensions, `"exports"` and declaration output agree, then test the packed package from a consumer project.

### 3. Keep Type Checking Separate from Single-File Transforms

esbuild, SWC and Babel can transpile one file at a time, but that step does not replace whole-program type checking. Run `tsc --noEmit` separately in CI when another tool produces the bundle.

`isolatedModules` reports constructs whose meaning a file-at-a-time transform cannot safely infer, such as a type-only re-export written as a value export or access to an ambient `const enum`. `verbatimModuleSyntax` goes further: every type-only import/export must use `import type` or `export type`, and TypeScript does not rewrite the remaining module syntax:

```typescript
import type { User } from "./user.js";
export type { User };
import { createUser } from "./user.js"; // retained as a runtime import
```

Ordinary `const enum` behavior still depends on the emitting tool and its options; do not assume a separate transpiler will inline a cross-file member. Prefer syntax your build tool supports and verify emitted imports when changing the transform pipeline.

### 4. Build Package Dependencies Deliberately

`incremental` stores compiler state so later checks can reuse work. `composite` marks a project for project references and requires declaration output. In a monorepo, `tsc -b` follows the reference graph, builds dependencies first and rebuilds affected projects. Treat `.tsbuildinfo` as a cache; a clean build must remain correct without it.

`skipLibCheck` skips checking inside declaration files, including declarations in your own project. Your source is still checked against those declarations, so an incorrect declaration can mislead application code without producing an error in the declaration itself. Use the speed/conflict trade-off deliberately, especially when publishing a library or investigating dependency types.

### 5. Upgrade Across TypeScript 6 and 7

As of October 2026, TypeScript 7.0 is the current native compiler; TypeScript 6.0 is the transition release that prepared projects for it. TypeScript 6 changed defaults such as `strict: true`, `module: "esnext"`, and an empty ambient `types` list; TypeScript 7 adopts those defaults. Set important options explicitly so a compiler upgrade does not silently change the project contract.

TypeScript 6 deprecated `baseUrl` and `node10` module resolution; TypeScript 7 rejects removed options. Replace `baseUrl`-dependent aliases with paths relative to the config and select a supported module mode. TypeScript 7.0 does not ship the previous compiler API; tools that need that API can use the official `@typescript/typescript6` compatibility package while keeping the TypeScript 7 `tsc` executable separate. Check the current [TypeScript 6 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html) and [TypeScript 7 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), run `tsc --showConfig`, and test type checking, output and runtime loading with pinned versions.

## Summary

Treat `tsconfig` as the checker's contract with the project. Set strictness and ambient libraries deliberately, pair module settings with the actual loader, and run whole-program type checking even when a bundler emits each file separately. A successful check describes the types and options it saw; it cannot prove that runtime modules, APIs or external values satisfy that description.

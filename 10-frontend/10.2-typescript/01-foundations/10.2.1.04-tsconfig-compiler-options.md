# tsconfig & Compiler Options

## TL;DR

`tsconfig.json` controls how strictly TypeScript checks code and how its output resolves modules. Turn on `strict` (the individual flags that matter most are `strictNullChecks` and `noImplicitAny`), pick `moduleResolution: "bundler"` for Vite/webpack apps or `"nodenext"` for published ESM packages, keep `isolatedModules: true` because every modern transpiler requires it, use `incremental`/`composite` for build speed, and accept `skipLibCheck` as the pragmatic default. A senior engineer can read a tsconfig and predict exactly which bugs it lets through.

## Why It Matters

Compiler options are the difference between "TypeScript with types" and "type-checked TypeScript." Interviews ask about them indirectly — "why does my import fail only in production builds?", "what does `isolatedModules` do?", "why is `strictNullChecks` non-negotiable?" They also explain real CI failures: module resolution mismatches, missing `declaration` in composite builds, and `any`s leaking through disabled strictness.

## Definition

**tsconfig.json** is the manifest `tsc` (and most tooling) reads to decide which files to compile, how permissively to type-check them, what module syntax to emit, and how imported modules are located on disk. Options cluster into four families: **strictness**, **modules/resolution**, **emit/build**, and **interop/lint-adjacent** flags.

```text
TSCONFIG OPTION FAMILIES
═══════════════════════════════════════════════════════════════

┌────────────────────┬─────────────────────────────────────────┐
│ STRICTNESS         │ strict, strictNullChecks, noImplicitAny │
│                    │ strictFunctionTypes, noUncheckedIndex…  │
├────────────────────┼─────────────────────────────────────────┤
│ MODULES            │ module, moduleResolution,               │
│                    │ esModuleInterop, allowSyntheticDefault  │
├────────────────────┼─────────────────────────────────────────┤
│ EMIT / BUILD       │ target, outDir, declaration,            │
│                    │ incremental, composite, noEmit          │
├────────────────────┼─────────────────────────────────────────┤
│ SPEED / PRAGMATISM │ isolatedModules, skipLibCheck,          │
│                    │ jsx, lib, paths                         │
└────────────────────┴─────────────────────────────────────────┘
```

## Why Do We Need It?

1. **Correctness dial**: Strictness flags determine whether `null`, implicit `any`, and unsound function typing are caught at compile time or explode at runtime.
2. **Environment match**: Module resolution must mirror your real runtime/bundler, or imports break in ways unit tests miss.
3. **Build performance**: `incremental`, `composite`, and `skipLibCheck` turn multi-minute type checks into seconds.
4. **Tooling compatibility**: esbuild, swc, Babel, Jest, and Metro transpile file-by-file; `isolatedModules` guarantees your types never depend on whole-program knowledge.
5. **Team consistency**: A reviewed tsconfig is an architectural contract — upgrading it is a deliberate event, not an accident.

## How It Works

### The strict Flag Family

`"strict": true` enables all of these:

| Flag | Catches | Matters? |
|------|---------|----------|
| `strictNullChecks` | `null`/`undefined` assigned to non-nullable types | **Critical** — the single biggest runtime-bug killer |
| `noImplicitAny` | Values silently typed `any` | **Critical** — without it, half your code is unchecked |
| `strictFunctionTypes` | Unsound function-parameter assignability (contravariance) | High — see Type Variance chapter |
| `strictPropertyInitialization` | Class fields not definitely assigned | Medium-high |
| `noImplicitThis` | `this` typed as `any` | Medium |
| `strictBindCallApply` | Wrong signatures through `.bind/.call/.apply` | Low-medium |
| `alwaysStrict` | Emits `"use strict"` | Trivial in ESM |
| `useUnknownInCatchVariables` | `catch (e)` gives `unknown` not `any` | Medium |

Two opt-ins sit outside `strict` but deserve senior consideration: `noUncheckedIndexedAccess` (indexing `arr[i]` yields `T | undefined`) and `exactOptionalPropertyTypes` (`undefined` is not assignable to optional props). Both catch real bugs; both create migration noise on old codebases.

### moduleResolution: bundler vs node16 vs nodenext

| Value | Models | Import style | Use when |
|-------|--------|--------------|----------|
| `node10` (classic `node`) | Old CommonJS Node | Extensionless, no `exports` awareness | Legacy only |
| `node16` / `nodenext` | Real Node ESM+CJS dual mode | Relative imports in ESM **need** `.js` extensions; honors `exports` maps | Published npm packages, Node-run code |
| `bundler` (TS 5.0+) | Vite/webpack/esbuild/turbopack | Extensionless OK; honors `exports`; allows mixing | Any app bundled by a build tool |

The classic failure: package authors ship `"exports"` maps, app tsconfigs still use `node10`, and deep imports fail with "cannot find module" even though the bundler handles them fine. Match resolution to the *thing that actually loads your files*.

```jsonc
{
  // App bundled by Vite:
  "module": "preserve",
  "moduleResolution": "bundler"
}
```

```jsonc
{
  // Library published to npm, consumed by Node ESM:
  "module": "nodenext",
  "moduleResolution": "nodenext"
}
```

### isolatedModules — Why Bundlers Demand It

Transpilers like esbuild/swc/Babel process one file at a time; they cannot know whether `export { Foo }` exports a type or a value. `isolatedModules: true` makes TypeScript reject anything ambiguous up front.

```typescript
// With isolatedModules, each of these needs explicit intent:

// BAD: is Foo a type or value? Transpiler can't tell.
export { Foo } from "./foo";

// GOOD: type-only re-export is explicit
export type { Foo } from "./foo";

// const enums cross file boundaries are also rejected — they need
// whole-program inlining that single-file transpilers can't do.
```

Run `tsc --noEmit` alongside your bundler so type errors gate CI even though the bundle step ignores them.

### Incremental and Composite Builds

| Option | Effect |
|--------|--------|
| `incremental: true` | Writes `.tsbuildinfo`; rechecks only changed files' graph |
| `composite: true` | Project-references mode: implies `declaration` + `incremental`; consumers compile against your `.d.ts`, not sources |
| `tsBuildInfoFile` | Where the state file lives (put it in build output, not src) |

Monorepos use `references` + `composite` so `tsc -b` rebuilds only affected packages — the TS equivalent of a build DAG.

### skipLibCheck Trade-off

`skipLibCheck: true` skips type-checking of every `.d.ts`. You still get full checking of your own code against those declarations.

- **Wins**: dramatically faster cold checks; silences conflicts between two dependencies' copies of the same `.d.ts`.
- **Costs**: a broken or lying declaration file passes silently; errors surface later in your own files, further from the cause.

It is effectively the ecosystem default (create-vite, Next.js) — take it, and pin dependency versions so declaration drift stays rare.

## Code Examples

### Recommended Senior App tsconfig (Annotated)

```jsonc
{
  // ── Language level ────────────────────────────────────────────
  "target": "ES2022",              // syntax downleveled by bundler anyway;
                                   // pick what your browsers support natively
  "lib": ["ES2022", "DOM", "DOM.Iterable"],
  "module": "preserve",            // don't rewrite module syntax; bundler owns it
  "moduleResolution": "bundler",   // extensionless imports + exports maps

  // ── Strictness: non-negotiable core ───────────────────────────
  "strict": true,                  // all eight family flags
  "noUncheckedIndexedAccess": true,// arr[i] => T | undefined
  "noImplicitOverride": true,      // overrides must say so
  "noFallthroughCasesInSwitch": true,

  // ── Bundler/transpiler reality ────────────────────────────────
  "isolatedModules": true,         // required by esbuild/swc/jest
  "verbatimModuleSyntax": true,    // forces `import type` clarity,
                                   // keeps emit honest
  "resolveJsonModule": true,
  "esModuleInterop": true,
  "forceConsistentCasingInFileNames": true,

  // ── Speed pragmatism ──────────────────────────────────────────
  "skipLibCheck": true,
  "incremental": true,
  "tsBuildInfoFile": ".cache/tsc/tsbuildinfo",

  // ── Emit: none — bundler emits, tsc only type-checks ──────────
  "noEmit": true,

  // ── Project shape ─────────────────────────────────────────────
  "jsx": "react-jsx",
  "baseUrl": ".",
  "paths": { "@/*": ["src/*"] },
  "include": ["src", "vite.config.ts"]
}
```

### Library tsconfig Differences

```jsonc
{
  "extends": "./tsconfig.base.json",
  // Libraries emit real files consumed elsewhere:
  "noEmit": false,
  "declaration": true,             // ship .d.ts
  "declarationMap": true,          // editor "go to definition" into source
  "sourceMap": true,
  "outDir": "dist",
  "module": "nodenext",
  "moduleResolution": "nodenext"   // consumers run you under real Node rules
}
```

### Monorepo Project References

```jsonc
// packages/core/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,             // required for being referenced
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}
```

```jsonc
// apps/web/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "composite": true },
  "references": [{ "path": "../../packages/core" }],
  "include": ["src"]
}
```

```bash
# Build only what changed, in dependency order:
tsc -b apps/web
```

### Detecting Config Drift in CI

```typescript
// scripts/check-tsconfig.ts — fail CI if strictness regresses
import { readFileSync } from "node:fs";
import { stringify } from "yaml";

const config = JSON.parse(
  readFileSync("tsconfig.json", "utf8").replace(/^\s*\/\/.*$/gm, "")
);

const REQUIRED = ["strict", "noUncheckedIndexedAccess", "isolatedModules"] as const;

for (const flag of REQUIRED) {
  if (!config.compilerOptions?.[flag]) {
    console.error(`tsconfig regression: ${flag} must be enabled`);
    process.exit(1);
  }
}
```

## Real-World Use Cases

1. **Vite SPA**: `bundler` resolution, `noEmit`, `strict`, `skipLibCheck` — tsc exists purely to gate CI while esbuild bundles.
2. **npm library**: `nodenext`, `declaration`, `declarationMap`, dual CJS/ESM via `tsc -b` per format.
3. **Nx/Turbo monorepo**: `composite` everywhere, references between packages, `.tsbuildinfo` cached remotely for minutes-level savings.
4. **Gradual JS-to-TS migration**: start with `allowJs: true`, `checkJs: false`, `strict: false` in a dedicated config, then ratchet `strictNullChecks` per-directory using path-scoped configs.
5. **Jest + ESM**: tests transpile via swc, so `isolatedModules` catches type-dependent exports before they become silent runtime no-ops.

## Common Mistakes

### 1. Shipping Without strict

```jsonc
// BAD: nulls and anys flow freely; types are decoration
{ "compilerOptions": { "strict": false } }

// GOOD: enable strict from commit #1; retrofitting costs 10x
{ "compilerOptions": { "strict": true } }
```

### 2. Resolution Mismatch With the Runtime

```jsonc
// BAD: bundler app configured like legacy Node — exports maps ignored,
// deep-import errors appear only in some tools
{ "moduleResolution": "node" }
```

```jsonc
// GOOD: mirror whoever actually loads the files
{ "moduleResolution": "bundler" }   // Vite/webpack app
```

### 3. Missing Extensions Under nodenext

```typescript
// BAD: works in bundler mode, fails to resolve under nodenext ESM
import { helper } from "./helper";

// GOOD: Node ESM requires explicit extensions (pointing at emitted .js)
import { helper } from "./helper.js";
```

### 4. Treating skipLibCheck as a Style Choice to Argue About

```typescript
// Misunderstanding: "it skips checking my code" — it does not.
// It skips checking DECLARATION FILES (.d.ts). Your sources are
// fully checked against them either way.
```

### 5. Composite Without declaration

```jsonc
// BAD: composite implies declaration; this fails to build
{ "composite": true, "declaration": false }
```

```jsonc
// GOOD: let composite imply it, add declarationMap for DX
{ "composite": true, "declarationMap": true }
```

### 6. Relying on Whole-Program Type Tricks With a Single-File Transpiler

```typescript
// BAD under isolatedModules: const enum inlining breaks per-file transpile
const enum Status { Active, Disabled }

// GOOD: plain union of literals — zero runtime, transpiler-safe
type Status = "active" | "disabled";
```

## Best Practices

1. **Start every project with `"strict": true` plus `noUncheckedIndexedAccess`** — the retrofit cost grows linearly with commits.
2. **Choose `moduleResolution` from your loader**, not habit: `bundler` for apps, `nodenext` for publishable packages.
3. **Keep `isolatedModules` and `verbatimModuleSyntax` on** so your codebase survives any transpiler swap.
4. **Gate CI with `tsc --noEmit` separately from the bundler** — bundlers ignore type errors by design.
5. **Use `skipLibCheck` deliberately**: know it hides third-party declaration bugs; pin versions to compensate.
6. **Structure monorepos with `references` + `composite`** and cache `.tsbuildinfo` for order-of-magnitude check speedups.
7. **Review tsconfig changes like security changes**: a relaxed flag widens the class of accepted programs forever.

## Performance Considerations

| Lever | Typical effect |
|-------|----------------|
| `skipLibCheck` | 30–60% faster cold `tsc` on dependency-heavy apps |
| `incremental` | Warm checks touch only changed graphs |
| `composite` + references | Monorepo rebuilds shrink to changed packages |
| Fewer/wider `include` globs | Faster file discovery than many excludes |
| `noUncheckedIndexedAccess` | Slightly more checking work — worth it for the bug class it kills |

## Summary

- `strict` is table stakes; `strictNullChecks` and `noImplicitAny` carry most of the value, `noUncheckedIndexedAccess` is the best opt-in beyond it.
- Module resolution must match the loader: `bundler` for bundled apps, `nodenext` for Node-published packages; mismatches produce phantom import failures.
- `isolatedModules` exists because esbuild/swc/Babel cannot see the whole program; it bans ambiguous type/value exports.
- `incremental` speeds local checks; `composite` enables monorepo reference builds.
- `skipLibCheck` is the pragmatic default — fast checks, at the price of trusting third-party `.d.ts`.
- A senior tsconfig is short, annotated, and treated as an architectural contract.

## Cheat Sheet

| Flag | One-liner |
|------|-----------|
| `strict` | Enables the whole strictness family — always on |
| `strictNullChecks` | `null`/`undefined` need explicit types — biggest win |
| `noImplicitAny` | No silent `any` — second biggest win |
| `strictFunctionTypes` | Sound (contravariant) function params |
| `noUncheckedIndexedAccess` | Index access returns `T \| undefined` |
| `moduleResolution: bundler` | Apps built by Vite/webpack — extensionless OK |
| `moduleResolution: nodenext` | Packages consumed by Node — extensions required |
| `isolatedModules` | Per-file-transpilable types — required by bundlers |
| `verbatimModuleSyntax` | Force `import type`, emit mirrors source |
| `skipLibCheck` | Don't check node_modules `.d.ts` — speed default |
| `incremental` | Cache check state in `.tsbuildinfo` |
| `composite` | Project-reference mode; implies declaration+incremental |
| `noEmit` | tsc type-checks only; bundler emits |

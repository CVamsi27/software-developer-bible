# Generics

## Definition

**Generics** are type parameters that allow you to write reusable, type-safe code that works with multiple types while preserving type information. They act as placeholders for types that are specified when the code is used.

> **Textbook Definition:** Generics parameterize types and functions over type variables so that relationships between inputs and outputs remain expressible. Constraints limit valid arguments without replacing the specific inferred argument with the constraint itself.

```text
identity("hello") -- infer T = "hello" --> result type "hello"
identity<string>("hello") -- choose T = string --> result type string
first([] as number[]) -- infer T = number --> result number | undefined
```

A **type argument** is the specific type supplied for a parameter at one use. The checker uses it to verify that input/output relationship, called an instantiation. The runtime still calls the same JavaScript function; it does not create a different specialized function for each T. An empty collection needs an absence result even when its element type is known.

## First Principles

Generics are functions over types — the same abstraction move as functions over values:

1. **A type parameter names a type that can differ at each use.** `<T>(x: T): T` connects the input and output through the same type `T`. TypeScript can infer `T` from the argument, or the caller can provide it explicitly. This relationship is checked before runtime.
2. **A constraint states what the implementation may rely on.** With `T extends HasId`, the function can access the properties guaranteed by `HasId`. It cannot assume additional properties simply because some callers happen to pass them. State the smallest shape the algorithm needs.
3. **Inference reduces what callers must write.** Callers usually omit an explicit argument such as `<string>` when TypeScript can determine it. Generic types are removed from emitted JavaScript, so the type parameters themselves add no runtime work.

## Why It Matters

Generics are how you write reusable, type-safe abstractions. Senior engineers use them for: collection types (`Array<T>`, `Map<K, V>`), React component props (`ComponentProps<typeof X>`), and API response wrappers (`ApiResponse<T>`). The interview signal is understanding inference vs. explicit type arguments.

## How It Works

Check each independent snippet as a strict TypeScript module. Intentional diagnostic lines are marked @ts-expect-error. The generic code is erased, but its ordinary operations still run and retain their normal ownership/error behavior.

### Type Parameters

```typescript
// T is a type parameter — a placeholder for a real type
function identity<T>(value: T): T {
  return value;
}

// TypeScript infers T from the argument
const str = identity("hello"); // inferred T is the literal "hello"
const num = identity(42); // inferred T is the literal 42

// Explicit type argument (rarely needed)
const explicit = identity<string>("hello");

```

### Constraints

```typescript
// Constrain T to types that have a .length property
function logLength<T extends { length: number }>(value: T): T {
  console.log(`Length: ${value.length}`);
  return value;
}

logLength("hello"); // string has .length
logLength([1, 2, 3]); // array has .length
logLength({ length: 10 }); // object with .length

// Constrain T to be a key of an object
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: "Alice", age: 30 };
getProperty(user, "name"); // returns string
getProperty(user, "age"); // returns number
// @ts-expect-error The name is outside the user key union.
getProperty(user, "email");

```

### Default Types

```typescript
// Default type parameter
interface ApiResponse<T = unknown> {
  data: T;
  status: number;
  message: string;
}

// Uses default (unknown)
const response1: ApiResponse = {
  data: null,
  status: 200,
  message: "OK"
};

// Specifies concrete type
interface User {
  name: string;
  email: string;
}
const response2: ApiResponse<User> = {
  data: { name: "Alice", email: "alice@example.com" },
  status: 200,
  message: "OK"
};

```

## Code Examples

### Generic Functions

```typescript
// ─── Basic Generic Function ───────────────────────────────────
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

const firstNum = first([1, 2, 3]); // number | undefined
const firstStr = first(["a", "b"]); // string | undefined

// ─── Multiple Type Parameters ─────────────────────────────────
function map<T, U>(arr: T[], fn: (item: T) => U): U[] {
  return arr.map(fn);
}

const doubled = map([1, 2, 3], n => n * 2); // number[]
const lengths = map(["hello", "world"], s => s.length); // number[]

// Independent types preserve an input relationship without inventing members.
function pair<A, B>(a: A, b: B): readonly [A, B] {
  return [a, b];
}
const result = pair({ name: "Alice" }, 30); // readonly [{name:string}, number]
console.log(result[0].name, result[1]); // Alice 30

```

### Generic Interfaces

```typescript
// ─── Generic Interface ────────────────────────────────────────
interface Repository<T> {
  findById(id: string): Promise<T | null>;
  findAll(): Promise<T[]>;
  save(entity: T): Promise<T>;
  delete(id: string): Promise<boolean>;
}

// Repository<User> fixes every T position to this entity type.
interface User { id: string; name: string; email: string }
// An actual repository supplies persistence, validation and transaction behavior.
```

findById may produce User or null; save consumes and produces User. The interface does not implement storage, establish uniqueness, authorize writes or prove an API body is User. Those responsibilities belong to the concrete repository and boundary decoder.

### Generic Classes

```typescript
// ─── Generic Stack ────────────────────────────────────────────
class Stack<T> {
  private items: T[] = [];

  push(item: T): void {
    this.items.push(item);
  }

  pop(): T | undefined {
    return this.items.pop();
  }

  peek(): T | undefined {
    return this.items[this.items.length - 1];
  }

  get size(): number {
    return this.items.length;
  }

  isEmpty(): boolean {
    return this.items.length === 0;
  }
}

const numberStack = new Stack<number>();
numberStack.push(1);
numberStack.push(2);
const top = numberStack.pop(); // number | undefined

const stringStack = new Stack<string>();
stringStack.push("hello");
const topStr = stringStack.pop(); // string | undefined

```

After push1/push2, numberStack.pop returns2 and leaves one item. A later pop on an empty stack returns undefined; a caller must check that result. A Stack of object values retains their identities rather than cloning them. A generic cache additionally needs key equivalence, capacity, undefined-hit handling and expiry policy; use [Memoization](../../10.1-javascript/05-functional-patterns/10.1.5.02-memoization.md) for the canonical behavior.

### Real-World Use Cases

```typescript
// ─── API Response Handling ────────────────────────────────────
interface ApiResponse<T> {
  data: T;
  status: number;
  timestamp: Date;
}

interface PaginatedResponse<T> extends ApiResponse<T[]> {
  total: number;
  page: number;
  limit: number;
}

async function fetchData<T>(
  url: string, decode: (value: unknown) => T,
): Promise<ApiResponse<T>> {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const raw: unknown = await response.json();
  return { data: decode(raw), status: response.status, timestamp: new Date() };
}
function decodeName(raw: unknown): string {
  if (typeof raw !== "object" || raw === null ||
      !("name" in raw) || typeof raw.name !== "string") {
    throw new Error("Expected a name field");
  }
  return raw.name;
}
// With an endpoint returning {name:"Ada"}, data is "Ada", not the raw object.
const nameResponse = await fetchData("/api/users/1", decodeName);
console.log(nameResponse.data.toUpperCase()); // ADA

```

This browser/API example needs the named endpoint and failure handling at its caller. T is inferred as string from decodeName's return, not manufactured by a caller writing fetchData<User>. The decoder earns that result by runtime checks; HTTP failures, invalid JSON and invalid payloads reject. Its timestamp describes local response handling, not a server field. Event names/payloads use the same key-to-value relationship; [Advanced Patterns](../04-advanced-patterns/10.2.4.05-advanced-patterns.md) owns the emitter implementation.

## Common Mistakes

### 1. Overusing Generics

```typescript
// Bad: a generic that promises all T, then does something only
// number|string support — the body can't be written without a cast
function add<T>(a: T, b: T): T {
  // @ts-expect-error T has no universal addition operation.
  return a + b;
}
```

```typescript
// Good: state the real contract — it is one type, not a family
function add(a: number, b: number): number {
  return a + b;
}

// Note: even `T extends number | string` does not help — `a + b` still
// errors (TS2365), because the operator is checked against the
// unresolved T. Reach for generics only when the caller must bind the type.
```

### 2. Not Constraining Type Parameters

```typescript
// Bad: No constraint, runtime errors possible
function getLength<T>(value: T): number {
  // @ts-expect-error No length member is guaranteed.
  return value.length;
}
```

```typescript
// Good: Add constraint
function getLength<T extends { length: number }>(value: T): number {
  return value.length;
}

```

### 3. Using `any` in Generic Code

```typescript
// Bad: Defeats the purpose of generics
function first<T>(arr: T[]): any {
  return arr[0]; // Loses type information
}
```

```typescript
// Good: Preserve type information
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

```

## Best Practices

1. **Name parameters for their role** — `TInput`/`TOutput`, `K` for keys, `V` for values: a glance should say which unknown binds where.
2. **Constrain to the minimum shape** — `T extends { length: number }` or `K extends keyof T` documents exactly what the body needs; a tighter constraint is a smaller promise the caller must keep.
3. **Default the parameter when omission should still work** — `interface ApiResponse<T = unknown>` lets `ApiResponse` compile as a plain unknown-typed response instead of forcing `ApiResponse<unknown>` noise.
4. **One parameter per independent unknown** — `combine<A, B>(a, b): [A, B]` lets callers bind two unrelated types; a single `T` forces both arguments to match.
5. **Let inference drive call sites** — write `map(arr, fn)` rather than `map<string, number>(arr, fn)`; explicit type arguments are the fallback when inference bottoms out, not the default style.

## Performance Considerations

- **Zero runtime cost**: type parameters are erased — `Stack<number>` and `Stack<string>` ship the same JS.
- **Compile-time cost is instantiation count**: each distinct set of type arguments is a new type the checker must resolve; deep conditional generics over big unions are where type checking slows down (→ 10.2.3.02).
- Checker caching can reduce repeated work, but source-context/inference/union interactions still matter. Measure compiler diagnostics rather than equating the number of written generic uses with an exact cost.

## Summary

Generics let the *caller* bind an unknown type, with constraints stating the minimum shape the body needs and defaults keeping call sites short. Inference does the ergonomic work — explicit type arguments are the exception. The failure modes are familiar: unconstrained parameters that can't be used, `any` leaking the type back out, and generics chosen where one concrete type would do.

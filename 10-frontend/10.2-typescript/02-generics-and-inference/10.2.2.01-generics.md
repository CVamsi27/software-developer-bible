# Generics

An API client receives JSON as `unknown`, validates it, and returns a useful type to its caller. A generic can connect the decoder's result to the response type without claiming that an unchecked payload already has that shape.

```typescript
function identity<T>(value: T): T {
  return value;
}

const word = identity('hello'); // string — inferred, same implementation
const count = identity(42);     // number
```

## Definition

**Generics** parameterize a function, interface, class or type with one or more type variables. Each use binds those variables to specific types, allowing the same implementation to preserve relationships across different inputs and outputs.

> **Textbook Definition:** A generic is a type or operation parameterized by type variables. Inference or explicit type arguments bind those variables at a use site, while constraints restrict permitted bindings and defaults supply omitted arguments.

## First Principles

A generic is useful when a caller needs the output to depend on an input. `<T>(value: T): T` promises to return the same kind of value it receives. A constraint adds the minimum capability the implementation needs; it does not replace the specific inferred type with the constraint.

## How It Works

### 1. Bind an Input Type to Its Output

TypeScript usually infers the type argument from the function's inputs. Use separate parameters for independent types so the function can preserve both rather than forcing them to match.

```typescript
function identity<T>(value: T): T {
  return value;
}

const word = identity('hello'); // string
const count = identity(42); // number
const exactWord = identity<'hello'>('hello'); // 'hello'

function map<Input, Output>(
  values: readonly Input[],
  project: (value: Input) => Output,
): Output[] {
  return values.map(project);
}
const doubled = map([1, 2], value => value * 2); // number[]

function pair<A, B>(first: A, second: B): readonly [A, B] {
  return [first, second];
}
const result = pair({ name: 'Alice' }, 30);
// readonly [{ name: string }, number]
```

The type arguments exist only while checking; both calls use the same JavaScript implementation. In the ordinary `identity<T>` signature, TypeScript infers `string` for `'hello'`; an explicit argument can request a narrower contract such as `'hello'`. Since TypeScript 5.0, a `const` type parameter can ask an API to preserve literal-like inference for inline values:

```typescript
function exactIdentity<const T>(value: T): T {
  return value;
}

const exactLiteral = exactIdentity('hello'); // 'hello'
const exactPair = exactIdentity(['left', 'right']); // readonly ['left', 'right']
```

This affects inference for a literal written at the call site; it does not turn an existing mutable variable into a readonly tuple. A type parameter used only in an output cannot be inferred from an argument; a real implementation then needs a factory or decoder to produce that type. A merge typed as `T & U` is safe only when the runtime operation satisfies both shapes: spread overwrites a shared key, so conflicting property types can make that intersection misleading.

### 2. Constrain the Operations the Function Can Rely On

A constraint states what every valid type argument must provide. The body can use that capability while the return type still preserves the caller's more specific type.

```typescript
function logLength<T extends { length: number }>(value: T): T {
  console.log(value.length);
  return value;
}

logLength('hello');
logLength([1, 2, 3]);
logLength({ length: 10, label: 'batch' });

function getProperty<T, K extends keyof T>(object: T, key: K): T[K] {
  return object[key];
}

const user = { name: 'Alice', age: 30 };
const name = getProperty(user, 'name'); // string
const age = getProperty(user, 'age'); // number
// @ts-expect-error 'email' is not a key of this user.
getProperty(user, 'email');
```

`T extends { length: number }` permits reading `length`; it does not permit assuming that every value is a string. `K extends keyof T` ties the accepted key to the object, and `T[K]` returns the value type for that exact key.

### 3. Reuse the Relationship in an Interface or Class

An interface can describe a repository contract for any entity type. A class can use the same parameter to constrain the values stored in its internal state.

```typescript
interface Repository<T> {
  findById(id: string): Promise<T | null>;
  save(entity: T): Promise<T>;
}

interface User { id: string; name: string }
interface UserRepository extends Repository<User> {}
```

The interface does not implement persistence, validation, transactions or authorization; a concrete repository must provide those behaviors.

```typescript
class Stack<T> {
  private items: T[] = [];

  push(item: T): void { this.items.push(item); }
  pop(): T | undefined { return this.items.pop(); }
  get size(): number { return this.items.length; }
}

const numbers = new Stack<number>();
numbers.push(1);
numbers.push(2);
numbers.pop(); // 2; one item remains
numbers.pop(); // 1
numbers.pop(); // undefined: the stack is empty
```

The stack preserves the element type and object identity; it does not clone values. Returning `T | undefined` makes the empty case part of the contract rather than inventing a value.

### 4. Default a Type Argument When Omission Is Safe

A default lets callers omit a type argument without making the payload unchecked. `unknown` requires narrowing before use; `any` would allow operations without evidence.

```typescript
interface ApiResponse<T = unknown> {
  data: T;
  status: number;
}

const untypedResponse: ApiResponse = { data: null, status: 200 };
interface User { id: string; name: string }
const userResponse: ApiResponse<User> = {
  data: { id: '1', name: 'Ada' },
  status: 200,
};
```

### 5. Let Runtime Validation Establish an External Type

The API client below receives JSON as `unknown` and returns `T` only after calling a decoder. TypeScript infers `T` from that decoder; a caller cannot make the payload valid merely by writing a type argument.

```typescript
interface ApiResponse<T> { data: T; status: number }

async function fetchData<T>(
  url: string,
  decode: (value: unknown) => T,
): Promise<ApiResponse<T>> {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const raw: unknown = await response.json();
  return { data: decode(raw), status: response.status };
}

function decodeName(raw: unknown): string {
  if (typeof raw !== 'object' || raw === null ||
      !('name' in raw) || typeof raw.name !== 'string') {
    throw new Error('Expected a name field');
  }
  return raw.name;
}

const nameResponse = await fetchData('/api/users/1', decodeName);
nameResponse.data.toUpperCase(); // T is inferred as string.
```

The decoder's runtime checks earn the string result. HTTP failures and invalid payloads reject the promise; `T` itself adds no validation or specialized JavaScript. A declaration that merely claims `decodeName` returns a string would not be enough — the implementation must keep that promise.

### 6. Add a Type Parameter Only When the Relationship Needs It

If a function only adds numbers, make it accept and return `number`; a generic parameter does not make `+` valid for every type. Likewise, returning `any` from a generic such as `first<T>(items: T[])` erases the relationship it was meant to preserve. Model an empty array honestly as `T | undefined`.

When repeated explicit type arguments appear at call sites, check whether the signature exposes the relationship clearly enough for inference. Name a reusable constraint when callers need to share or implement it, and keep constraints to the smallest capability the body actually uses.

Type parameters erase from emitted JavaScript. Deep conditional or recursive generic types can still increase checker and editor work, so measure the consuming project with compiler diagnostics instead of assuming a fixed cost per generic use.

## Summary

Generics preserve relationships chosen by callers. Inference binds type arguments, constraints limit what an implementation may assume, and defaults make safe omission possible. External data still needs runtime validation, and concrete operations should remain concrete when no type relationship varies.

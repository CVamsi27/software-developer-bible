# Infer

## Definition

**`infer`** is a keyword used in conditional types to extract and name a type within a type position. It allows you to "infer" or "capture" a type from another type for reuse.

> **Textbook Definition:** `infer` introduces a type variable within the matched pattern of a conditional type. A successful match makes the inferred type available to that branch, enabling extraction of nested type structure.

```text
T = Promise<string>
T extends Promise<infer Payload> ? Payload : T
             matches Payload = string
true branch returns string

T = number does not match -> false branch returns number
```

Matching tests a static type structure. The captured name is available in the successful branch; no promise is awaited or inspected at runtime. This example passes a non-promise through; an extractor may instead choose never to discard a non-match.

## First Principles

Conditional types choose a branch when one static type is assignable to a pattern. If the pattern contains a slot the result needs to reuse, `infer` gives that slot a name; recursion repeats the match until a deliberate base case is reached.

1. **Match before extracting.** In `T extends Promise<infer U>`, the inner type is named `U` only when `T` matches the promise pattern. A non-match cannot use `U` and must follow the false branch.
2. **Choose the non-match result deliberately.** Returning `T` preserves an unrelated input; returning `never` removes that member from a distributed union. Returning `unknown` can absorb useful union members.
3. **Give recursive transforms a stopping condition.** Nested structures need a terminal result, such as a non-promise value or `never`, so the checker can finish evaluating the type.

## Why It Matters

Senior engineers use `infer` for: custom `ReturnType`-like helpers, extracting types from complex generics (e.g., the value type of a deeply-nested Map), and building type-level parsers. The interview signal is being able to write a custom utility type using `infer`.

## How It Works

Use strict TypeScript checking and independent module snippets. These helpers describe types only; a type comment is a predicted checker result, not console output. Some later examples explicitly declare their own domain shapes. Intentional diagnostics are marked.

### Basic Inference

```typescript
// Extract return type
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type A = MyReturnType<() => string>; // string
type B = MyReturnType<(x: number) => boolean>; // boolean

// Extract element type from array
type ElementType<T> = T extends readonly (infer E)[] ? E : never;

type C = ElementType<string[]>; // string
type D = ElementType<number[]>; // number

```

### In Function Parameters

```typescript
// Extract the full parameter tuple, then require a first element.
type Params<T> = T extends (...args: infer P) => any ? P : never;
type FirstParam<T> = T extends (...args: infer P) => any
  ? P extends [infer F, ...unknown[]] ? F : never : never;
type A = FirstParam<(name: string, age: number) => void>; // string
type B = Params<(x: string, y: number, z: boolean) => void>;
// [string, number, boolean]
type Empty = FirstParam<() => void>; // never

```

### In Return Types

```typescript
// Extract Promise inner type
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T;

type A = UnwrapPromise<Promise<string>>; // string
type B = UnwrapPromise<Promise<number>>; // number
type C = UnwrapPromise<number>; // number (not a promise)

// Deep unwrap
type DeepUnwrap<T> = T extends Promise<infer U> ? DeepUnwrap<U> : T;

type D = DeepUnwrap<Promise<Promise<Promise<string>>>>; // string

```

### In Tuple Positions

```typescript
// Extract first element of tuple
type Head<T extends readonly unknown[]> = T extends readonly [infer H, ...unknown[]] ? H : never;

type A = Head<[string, number, boolean]>; // string

// Extract tail of tuple
type Tail<T extends readonly unknown[]> = T extends readonly [unknown, ...infer Rest] ? Rest : never;

type B = Tail<[string, number, boolean]>; // [number, boolean]

// Extract last element
type Last<T extends readonly unknown[]> = T extends readonly [...unknown[], infer L] ? L : never;

type C = Last<[string, number, boolean]>; // boolean

```

Head/Last require a statically guaranteed first/last position: an empty tuple or arbitrary string[] does not establish one. These Tail results are newly inferred mutable tuples even when the input tuple is readonly; specify modifier preservation if that is required. Function extraction from overloads normally uses the last signature, not runtime argument-based overload selection. Awaited is the standard helper when the promise/thenable/nullish contract matters; the Promise-only examples above intentionally have a narrower pattern.

### Complex Inference Patterns

```typescript
// Extract property type
type PropertyType<T, K extends keyof T> = T extends { [P in K]: infer V } ? V : never;

interface User {
  name: string;
  age: number;
}

type A = PropertyType<User, "name">; // string
type B = PropertyType<User, "age">; // number

// Extract event handler parameter
type EventPayload<T> = T extends (event: infer E) => void ? E : never;

type ClickHandler = (event: MouseEvent) => void;
type Payload = EventPayload<ClickHandler>; // MouseEvent

// Extract class instance type
type InstanceOf<T> = T extends new (...args: any[]) => infer I ? I : never;

class UserModel {
  constructor(public name: string) {}
}

type UserInstance = InstanceOf<typeof UserModel>; // UserModel

```

This property-pattern helper matches required properties. If `K` names an optional property, the required pattern may not match and the result can be `never`; use indexed access `T[K]` when you need the property's read type, including `undefined`.

## Code Examples

### Practical Examples

```typescript
// ─── Type-safe API response handling ──────────────────────────
type ApiResponse<T> = {
  data: T;
  status: number;
  timestamp: Date;
};

type ExtractApiResponse<T> = T extends ApiResponse<infer D> ? D : never;

interface User { id: string; name: string; email: string }
const userResponse: ApiResponse<User> = {
  data: { id: "1", name: "Alice", email: "a@b.com" },
  status: 200,
  timestamp: new Date()
};

type UserData = ExtractApiResponse<typeof userResponse>; // User

// Extract middleware inputs without a third-party type installation.
type Middleware<T> = T extends (req: infer Req, res: infer Res, next: infer Next) => any
  ? { request: Req; response: Res; next: Next } : never;
type Handler = (req: { path: string }, res: { status: number }, next: () => void) => void;
type HandlerParts = Middleware<Handler>;
// {request:{path:string}; response:{status:number}; next:()=>void}

```

The response extractor matches ApiResponse<User>, captures User at data and returns it as UserData. It does not validate the actual response. Route-string parsing has one canonical implementation in [Template Literal Types](../03-type-transformations/10.2.3.04-template-literal-types.md); the same capture mechanism names path segments there.

### Advanced Patterns

```typescript
// ─── Deep pick using infer ────────────────────────────────────
type DeepPick<T, K extends string> =
  K extends `${infer Head}.${infer Rest}`
    ? Head extends keyof T
      ? { [P in Head]: DeepPick<T[Head], Rest> }
      : never
      : K extends keyof T
        ? { [P in K]: T[P] }
        : never;

interface Config {
  database: {
    host: string;
    port: number;
    credentials: {
      user: string;
      password: string;
    };
  };
  server: {
    port: number;
  };
}

type DbConfig = DeepPick<Config, "database.host">;
// { database: { host: string } }

type Credentials = DeepPick<Config, "database.credentials.user">;
// { database: { credentials: { user: string } } }

// ─── Extract union members matching pattern ───────────────────
type ExtractByType<T, U> = {
  [K in keyof T]: T[K] extends U ? K : never;
}[keyof T];

interface Mixed {
  name: string;
  age: number;
  active: boolean;
  email: string;
}

type StringKeys = ExtractByType<Mixed, string>; // "name" | "email"
type NumberKeys = ExtractByType<Mixed, number>; // "age"

```

For database.credentials.user, DeepPick captures database/rest, then credentials/rest, then user; each level wraps the selected child, producing the nested result shown. This limited helper assumes required object properties and dot-separated string keys without dots in a name; optional objects, arrays, union-valued paths and merging multiple selected paths need deliberate contracts. It transforms a type, not a runtime pick. [Advanced Generics](10.2.2.03-advanced-generics.md) owns runtime pipeline composition checking.

## Real-World Use Cases

- **Awaited/return extraction** — `Awaited<ReturnType<typeof loadConfig>>` types code that consumes config without importing its types (schema-driven apps).
- **Event payload extraction** — `OnParams<Events['appointment:created']>` keeps handler signatures in sync with the emitter's map (→ 10.2.4.05).
- **Element/prop extraction** — `InferProps<typeof Component>` for wrapper libraries (design systems wrapping buttons/inputs).

## Common Mistakes

### 1. Capturing the whole type when you wanted one part

```typescript
// Legal identity-style pattern; it captures no smaller component
type Bad<T> = T extends infer U ? U : never;
// This just returns T, doesn't capture anything specific

// Correct: infer in specific position
type Good<T> = T extends Promise<infer U> ? U : never;
// Captures the Promise's inner type

```

### 2. Placing `infer` Outside the Pattern

```typescript
// Bad: `infer` is only legal in the extends (pattern) clause —
// this line is a compile error: TS1338. The false branch's `unknown`
// is doubly wrong: a non-match would produce `unknown`, which swallows
// every union it lands in.
// @ts-expect-error infer is outside the extends pattern.
type ExtractString<T> = T extends string ? infer S : unknown;
```

```typescript
// Good: capture in the pattern itself, and send non-matches to
// `never` so they contribute nothing downstream
type Inner<T> = T extends Promise<infer U> ? U : never;

type S1 = Inner<Promise<string>>; // string
type S2 = Inner<number>;          // never (not a match)
```

### 3. Overcomplicating Inference

```typescript
// Bad: Too many nested inferences
type Complex<T> =
  T extends Promise<infer U>
    ? U extends Array<infer V>
      ? V extends Promise<infer W>
        ? W
        : V
      : U
    : T;

// This composition handles nested outer promises followed by nested arrays.
// It is a different contract: an inner Promise after an array is not re-unwrapped.
type Unwrap<T> = T extends Promise<infer U> ? Unwrap<U> : T;
type Flatten<T> = T extends Array<infer E> ? Flatten<E> : T;

type Result = Flatten<Unwrap<Promise<string[]>>>; // string

```

## Best Practices

1. **Capture in the pattern, name for the role** — `infer Payload`, `infer Element`, `infer Ret`: a readable name in `extends` position documents what the extract is for without a comment.
2. **Choose whether a non-match is discarded or retained** — `never` makes non-matches vanish from unions; a default (e.g. `T` itself) is a deliberate choice, and `unknown` silently poisons unions.
3. **Recursion needs a base case** — the pattern is capture → transform → recurse with `never`/the pass-through type as the terminal (see `DeepUnwrap`), the type-level twin of a recursive function's base case.
4. **Keep the docs on public extracts** — a complex `Head<T>`/`DeepPick` in a shared library gets a doc comment saying what it returns for non-matching inputs; `never` vs `T` vs `unknown` behaves differently downstream.
5. **Prefer one small capture per type over nested captures** — helpers compose (`Unwrap` then `Flatten`); a triple-nested `infer U ? U extends infer V ? …` is unreadable and harder for the checker to resolve.

## Performance Considerations

- Everything here is compile-time: `infer` produces no runtime code and no runtime cost.
- Each capture resolves to a concrete type the checker then works with — simple captures are often inexpensive; deep chains of *recursive* conditional types are what push instantiation depth (the `TS2589 Type instantiation is excessively deep` limit).
- Inference interacts with distribution: a naked type parameter distributes over unions before matching, so `Inner<string | number>` runs the pattern twice — usually what you want, occasionally a cost when union members number in the thousands.

## Summary

`infer` is a capture pattern for the `extends` clause: it names the slot a matched type fills (`Promise<infer U>` grabs the inner type, `(...args: infer P) => any` grabs the parameter tuple, `new (...args) => infer I` grabs the instance type). Combined with recursion it decomposes arbitrary type structures — the same shape as writing a recursive parser over values. The discipline: capture in the pattern, `never` for non-matches, a base case in every recursion.

# Advanced Generics

## Definition

**Advanced generics** combine type parameters with other TypeScript features to describe more complex relationships. This includes simulating higher-kinded types, which treat a container such as an array as a reusable type pattern; variadic generics, which work with tuples of varying lengths; conditional types, which choose a result type after a check; and constraints that restrict which types callers may supply. The sections below explain how each pattern works.

> **Textbook Definition:** Advanced generic patterns combine constrained parameters, inference and type-level transformations to preserve relationships across an API. Their usefulness depends on accurate contracts, readable diagnostics and manageable compiler cost.

## First Principles

An API can lose a relationship at each intermediate step. A pipeline must prove that one result is valid input for the next; a container mapping must preserve which container was selected. Individual constraints only prove each piece in isolation. Compose the relationships and check the transitions before returning a precise type.

## Why It Matters

Senior engineers use these for: type-safe API client builders (turning URL templates into typed responses), form libraries (inferring field types from schema), and ORM-style entity types. The interview signal is comfort with multi-step type inference and recursive type definitions.

## How It Works

### A key selects a reusable container pattern

A container combines a structure with an element type: Array<number> and Promise<number> contain the same element type in different structures. A higher-kinded type would let a type parameter stand for that reusable container constructor. TypeScript cannot directly apply an arbitrary F as F<A>, so a keyed table selects known concrete patterns instead. A functor here means an operation that maps contained values while retaining the selected structure.

Check independent examples with strict TypeScript settings. These definitions constrain static relationships; assertions and generics do not validate outside data.

```typescript
// TypeScript doesn't have native HKTs, but we can simulate them

// `interface Functor<F> { map: <A, B>(fa: F<A>, …) }` does NOT compile —
// TS2315 "Type 'F' is not generic". The workaround is a keyed table of
// constructors (the fp-ts-style encoding): map over the table's values.
interface URItoKind<A> {
  array: A[];
  promise: Promise<A>;
}

type URIS = keyof URItoKind<unknown>;
type Kind<URI extends URIS, A> = URItoKind<A>[URI];

interface Functor<URI extends URIS> {
  map: <A, B>(fa: Kind<URI, A>, f: (a: A) => B) => Kind<URI, B>;
}

// Array functor
const arrayFunctor: Functor<"array"> = {
  map: (fa, f) => fa.map(f)
};

// Promise functor
const promiseFunctor: Functor<"promise"> = {
  map: (fa, f) => fa.then(f)
};

```

For arrayFunctor.map([1,2], String), the array key selects A[]=number[] then B[]=string[]: the result is ["1","2"]. The promise key selects Promise<A> and maps only after fulfillment, returning Promise<B>. Adding a new table key needs a corresponding implementation; this encoding is a compile-time lookup, not dynamic dispatch or a runtime container constructor.

### Generic Constraints with keyof

```typescript
// ─── Deep Property Access ─────────────────────────────────────
type DeepPropertyAccess<T, Path extends string> =
  Path extends `${infer Head}.${infer Rest}`
    ? Head extends keyof T
      ? DeepPropertyAccess<T[Head], Rest>
      : never
    : Path extends keyof T
      ? T[Path]
      : never;

interface Config {
  database: {
    host: string;
    port: number;
    credentials: {
      user: string;
      password: string;
    };
  };
}

type HostType = DeepPropertyAccess<Config, "database.host">; // string
type UserType = DeepPropertyAccess<Config, "database.credentials.user">; // string

// ─── Type-safe property setter ────────────────────────────────
type SetProperty<
  T,
  Path extends string,
  Value
> = Path extends `${infer Head}.${infer Rest}`
  ? Head extends keyof T
    ? { [K in keyof T]: K extends Head ? SetProperty<T[K], Rest, Value> : T[K] }
    : T
  : Path extends keyof T
    ? { [K in keyof T]: K extends Path ? Value : T[K] }
    : T;

```

DeepPropertyAccess splits database.credentials.user into database, credentials, then user and returns the final string type. SetProperty rebuilds those containing object types with a replacement value type; it does not perform a runtime write. Both are limited to required object properties and literal dot paths; missing keys return never (read) or the unchanged type (replacement). Optional children, arrays and dots inside names require separate handling.

### Conditional Generic Types

```typescript
// ─── Conditional return type ──────────────────────────────────
type ApiResponse<T> = T extends "user"
  ? { name: string; email: string }
  : T extends "post"
    ? { title: string; content: string }
    : never;

type UserPayload = ApiResponse<"user">;
type PostPayload = ApiResponse<"post">;
// This maps a key to a shape; it does not decode a fetched body.

// One public generic relationship, implemented by ordinary runtime checks.
function measure<T>(value: T): T extends string ? number : boolean;
function measure(value: unknown): number | boolean {
  return typeof value === "string" ? value.length : value !== null;
}
const length = measure("Ada"); // number, runtime 3
const present = measure(null); // boolean, runtime false

```

The overload describes the input/output relationship while the implementation has a broad number-or-boolean result. That signature must agree with every runtime branch; the checker does not derive the conditional return from this implementation. Use the [generic decoder-based fetch](10.2.2.01-generics.md) for external responses rather than asserting a conditional shape from an endpoint name.

### Variadic Generics

```typescript
// ─── Variable-length type parameters ──────────────────────────
type Tuple<T extends any[]> = [...T];

type Result = Tuple<[string, number, boolean]>;
// [string, number, boolean]

// One required tuple element becomes one unary call stage.
type Curry<Args extends unknown[], R> =
  Args extends [infer First, ...infer Rest]
    ? Rest extends [] ? (arg: First) => R : (arg: First) => Curry<Rest, R>
    : () => R;
const add: Curry<[number, number, number], number> = a => b => c => a + b + c;
console.log(add(1)(2)(3)); // 6
// Optional/rest/default/grouped application contracts are deliberately excluded.
// General runtime arity handling belongs to the JavaScript curry chapter.

// A nonempty synchronous unary pipeline must validate adjacent stages.
type Unary = (arg: any) => any;
type Compatible<Fns extends readonly Unary[]> =
  Fns extends readonly [infer F extends Unary, infer G extends Unary, ...infer Rest extends Unary[]]
    ? ReturnType<F> extends Parameters<G>[0]
      ? readonly [F, ...Compatible<readonly [G, ...Rest]>]
      : never
    : Fns;
type LastResult<Fns extends readonly Unary[]> =
  Fns extends readonly [...Unary[], infer Last extends Unary] ? ReturnType<Last> : never;
function pipe<Fns extends readonly [Unary, ...Unary[]]>(
  ...fns: Fns & Compatible<Fns>
): (arg: Parameters<Fns[0]>[0]) => LastResult<Fns> {
  const apply = (arg: unknown): unknown =>
    fns.reduce<unknown>((value, fn) => fn(value), arg);
  return apply as (arg: Parameters<Fns[0]>[0]) => LastResult<Fns>;
}
const formatLength = pipe(
  (x: number) => x + 1,
  (x: number) => String(x),
  (x: string) => x.length,
);
console.log(formatLength(9)); // 2: 9 -> 10 -> "10" -> 2
// @ts-expect-error number output cannot be input to a string-only function.
pipe((x: number) => x + 1, (x: string) => x.length);

```

The check walks adjacent pairs, not every later function against the first output. Thus number → string → number is valid, while number → a string-only consumer is rejected. The runtime reduce is the same synchronous unary loop taught in [Currying and Composition](../../10.1-javascript/05-functional-patterns/10.1.5.04-currying-composition.md); the broad internal function constraint and final implementation assertion are confined to that loop after the public transition checks. The assertion connects that erased proof to the implementation; it cannot repair a caller using any. Inputs using any, overloads, optional/rest signatures or promises need stronger contracts and can escape these checks.

### Recursive Generic Types

```typescript
// ─── Deep readonly ────────────────────────────────────────────
type DeepReadonly<T> =
  T extends ((...args: any[]) => any) | Date | RegExp
    ? T
    : T extends readonly unknown[]
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T extends Map<infer K, infer V>
      ? ReadonlyMap<DeepReadonly<K>, DeepReadonly<V>>
      : T extends Set<infer U>
        ? ReadonlySet<DeepReadonly<U>>
        : T extends object
          ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
          : T;

// ─── Deep partial ─────────────────────────────────────────────
type DeepPartial<T> =
  T extends ((...args: any[]) => any) | Date | RegExp
    ? T
    : T extends readonly (infer U)[]
    ? DeepPartial<U>[]
    : T extends Map<infer K, infer V>
      ? Map<K, DeepPartial<V>>
      : T extends Set<infer U>
        ? Set<DeepPartial<U>>
        : T extends object
          ? { [K in keyof T]?: DeepPartial<T[K]> }
          : T;

// ─── Flatten nested arrays ────────────────────────────────────
type DeepFlatten<T> =
  T extends readonly (infer U)[]
    ? DeepFlatten<U>
    : T;

type Nested = number[][][];
type Flat = DeepFlatten<Nested>; // number

```

DeepReadonly removes Map/Set mutation methods through readonly views and preserves tuple positions; other aliases can still mutate the original. Function/Date/RegExp are explicit leaves, not fully frozen objects. This example supports data objects and the listed containers, not every host/native class. DeepPartial keeps array elements as partial values but intentionally widens tuple/readonly-array structure into a mutable array; it does not define a merge-patch protocol. Recursive types can describe cycles, but actual recursive transformation expansion still needs manageable shapes and depth.

### Runtime enumeration cannot prove every static key

```typescript
// A wider runtime object can satisfy a narrower static contract.
const actual = { name: "Ada", extra: 1 };
const view: { name: string } = actual;
console.log(Object.keys(view)); // ["name", "extra"], not just keyof typeof view

function groupBy<T, K>(arr: readonly T[], keyFn: (item: T) => K): Map<K, T[]> {
  const groups = new Map<K, T[]>();
  for (const item of arr) {
    const key = keyFn(item);
    const group = groups.get(key);
    if (group) group.push(item);
    else groups.set(key, [item]);
  }
  return groups;
}
const grouped = groupBy([{ role: "admin" }, { role: "user" }], u => u.role);
console.log(grouped.get("admin")?.length); // 1
console.log(grouped.get("absent")); // undefined

```

Object.keys lists own enumerable string keys; symbols, nonenumerable/inherited names and extra runtime properties differ from keyof. An assertion cannot make that list exhaustive or remove extras. Empty entries/group inputs likewise cannot create a complete Record<K,V>; Map.get honestly admits an absent group and avoids inherited-key collisions such as __proto__. For supported runtimes, [Map.groupBy](../../10.1-javascript/06-modern-and-interview/10.1.6.01-es2024-features.md) supplies the platform grouping operation.

## Code Examples

### Real-World Use Cases

```typescript
// ─── Type-safe Redux-like store ───────────────────────────────
type ActionMap = {
  "user/create": { name: string; email: string };
  "user/delete": { userId: string };
  "post/create": { title: string; content: string };
};

type Action<T extends keyof ActionMap> = {
  type: T;
  payload: ActionMap[T];
};

function createAction<T extends keyof ActionMap>(
  type: T,
  payload: ActionMap[T]
): Action<T> {
  return { type, payload };
}

const createAction_userCreate = createAction("user/create", {
  name: "Alice",
  email: "alice@example.com"
});

// ─── Type-safe query builder ──────────────────────────────────
interface DatabaseSchema {
  users: {
    id: string;
    name: string;
    email: string;
    age: number;
  };
  posts: {
    id: string;
    title: string;
    content: string;
    authorId: string;
  };
}

type Table = keyof DatabaseSchema;
type Column<T extends Table> = keyof DatabaseSchema[T];

function select<T extends Table>(
  table: T,
  columns: Column<T>[]
): void {
  console.log(`SELECT ${columns.join(", ")} FROM ${table}`);
}

select("users", ["id", "name"]); // ok
select("posts", ["id", "title"]); // ok
// @ts-expect-error title is not a user column.
select("users", ["id", "title"]);

```

The action builder preserves the selected action key and payload shape; a broad union-valued key requires a discriminated action union to retain correlation across cases. The query example only prints identifiers: it does not execute SQL, bind values or authorize columns. Validate outside identifiers against a runtime allowlist and use a real parameterized query API. [Advanced Patterns](../04-advanced-patterns/10.2.4.05-advanced-patterns.md) owns the event-emitter implementation.

## Common Mistakes

### 1. Overcomplicating Generic Constraints

```typescript
// Bad: an inline intersection nobody can read or reuse
function process<
  T extends object & { id: string } & { name: string } & { email: string }
>(value: T): T {
  return value;
}
```

```typescript
// Good: one named constraint — same checking power, readable errors,
// and callers can implement it like any other contract
interface User {
  id: string;
  name: string;
  email: string;
}

function processUser<T extends User>(value: T): T {
  return value;
}

```

### 2. Not Using Default Types

```typescript
// Bad: every use site must spell the argument, even when unknown fits
interface Response<T> {
  data: T;
  status: number;
}
```

```typescript
// Good: Provide default type
interface Response<T = unknown> {
  data: T;
  status: number;
}

const response: Response = { data: null, status: 200 }; // OK

```

### 3. Recursive Types With Nowhere to Recurse

```typescript
// Bad: a bare alias can't reference itself — TS2456
// "Type alias 'Bad' circularly references itself"
// @ts-expect-error Unproductive self-alias is rejected.
type Bad<T> = Bad<T> | T;
```

```typescript
// Good: recursion has to pass through an object (or array/tuple)
// position, which the checker resolves lazily — and a union with a
// terminator gives real code a pattern-matchable end
type LinkedList<T> = { value: T; next: LinkedList<T> } | null;

```

## Best Practices

1. **Give a shared constraint a name.** An interface such as `User` or `HasId` is easier to read than a repeated inline intersection. It gives errors a useful name and puts changes in one place. Classes can also use `implements` with an appropriate object shape.
2. **Provide a default when omission is useful.** `Response<T = unknown>` lets a caller write `Response` when no more specific payload type is needed.
3. **Represent a family of containers with a keyed table.** TypeScript cannot treat an arbitrary parameter `F` as a generic type and apply `F<A>`. `URItoKind<A>` lists concrete container types, and `Kind<URI, A>` selects one by key. Libraries can use this pattern to describe operations such as mapping over different containers.
4. **Separate recursive data from recursive type calculations.** A data type can refer to itself through object, array or tuple members. Its values need a way to end, such as `null` or an empty array. A recursive conditional type also needs a stopping case in its calculation; excessive expansion can produce TS2589.
5. **Let argument types guide inference.** A signature such as `select(table, columns)` can derive the table type and permitted columns from its arguments. If callers repeatedly need explicit type arguments, check whether the signature expresses those relationships clearly.

## Performance Considerations

- All of it erases: no emitted JS differs between a `DeepReadonly` and its plain counterpart — the cost is compile time only.
- Recursive conditional types (curry, pipe, deep walkers) consume instantiation depth; going past the checker's limit fails loudly with `TS2589 Type instantiation is excessively deep` rather than hanging.
- The checker can cache instantiations, but context and recursive/union expansion affect work. Use extendedDiagnostics or a trace to measure the actual project.
- Deep recursive mapped types over large objects (`DeepPartial` of a 200-property config) are the common "editor got slow" culprit — keep them to the layers you actually need.

## Summary

Advanced generics are composition, not new machinery: constraints bound what a body may touch, conditional types branch, `infer` captures, mapped/template types transform, and recursion ties them into type-level programs. The three hard-won lessons: TypeScript has no native type constructors (encode containers as a keyed table), recursion needs an object position plus a stopping story, and tuple transforms need explicit terminal cases, and runtime application must honor the same stage/arity contract.

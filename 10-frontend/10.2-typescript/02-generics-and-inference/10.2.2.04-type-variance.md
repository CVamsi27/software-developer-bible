# Type Variance

TypeScript lets a `Dog[]` stand in for an `Animal[]`. That looks harmless until code writes a cat through the wider alias and the original dog array now contains a value without `breed`. Variance explains which substitutions follow from a type's inputs and outputs, and where TypeScript accepts a less safe assignment for compatibility.

## Definition

**Variance** describes how assignability between generic types changes when their type arguments are related. A producer of `Dog` can usually stand in for a producer of `Animal` (covariance). A consumer that accepts any `Animal` can stand in for a consumer of `Dog` (contravariance). A type that both produces and consumes a value may require matching arguments (invariance). Bivariance accepts either direction.

> **Textbook Definition:** Variance is the relationship between subtyping of a type parameter and assignability of the generic type that uses it. Output positions preserve the direction, input positions reverse it, and mixed read/write positions can require invariance.

## First Principles

A substitution is safe only if it preserves the operations available to the caller. A producer promises what it can return; a consumer promises what it can accept. Reading and writing the same mutable value creates both promises, so widening only one side can let callers violate the other.

## Follow how a type produces or consumes `T`

A return position produces `T`, so a dog producer can satisfy a request for an animal producer. A function parameter consumes `T`, so the direction reverses: a handler for any animal can handle a dog. A read/write type combines both directions.

```typescript
interface Animal { name: string }
interface Dog extends Animal { breed: string }

type Producer<T> = () => T;
type Consumer<T> = (value: T) => void;
type Cell<T> = { read: () => T; write: (value: T) => void };

declare const produceDog: Producer<Dog>;
const produceAnimal: Producer<Animal> = produceDog; // Covariant: safe.

declare const consumeAnimal: Consumer<Animal>;
const consumeDog: Consumer<Dog> = consumeAnimal; // Contravariant: safe.

type EventHandler<T> = (event: T) => void;
declare const logAny: (event: unknown) => void;
const resizeHandler: EventHandler<UIEvent> = logAny; // Accepts every UIEvent.

declare const dogCell: Cell<Dog>;
// @ts-expect-error Cell both returns and accepts T.
const animalCell: Cell<Animal> = dogCell;
```

Under `strictFunctionTypes`, function-valued properties check parameters contravariantly. A `PointerEvent` handler slot can use a broader `MouseEvent` handler because every pointer event is a mouse event; the reverse would let the caller pass a non-pointer mouse event to code that expects pointer fields.

```typescript
type MouseHandler = (event: MouseEvent) => void;
type PointerHandler = (event: PointerEvent) => void;
declare const handleMouse: MouseHandler;
declare const handlePointer: PointerHandler;

const pointerSlot: PointerHandler = handleMouse; // Safe: handles the broader input.
// @ts-expect-error Pointer-only code cannot handle every MouseEvent.
const mouseSlot: MouseHandler = handlePointer;
```

## Know where TypeScript keeps compatibility exceptions

With `strictFunctionTypes` disabled, function parameters are compared bivariantly, so both assignments can pass. With strict checking enabled, method and constructor parameters still use the bivariance exception. That keeps existing JavaScript and library patterns compatible, but can admit an unsafe method assignment; prefer function-valued properties when the narrower input guarantee matters.

```typescript
interface Animal { name: string }
interface Dog extends Animal { breed: string }

interface MethodSlot<T> {
  handle(value: T): void;
}
interface PropertySlot<T> {
  handle: (value: T) => void;
}

declare const animalMethod: MethodSlot<Animal>;
declare const dogMethod: MethodSlot<Dog>;
const safeMethod: MethodSlot<Dog> = animalMethod;
const uncheckedMethod: MethodSlot<Animal> = dogMethod; // Allowed by method bivariance.

declare const animalProperty: PropertySlot<Animal>;
declare const dogProperty: PropertySlot<Dog>;
const safeProperty: PropertySlot<Dog> = animalProperty;
// @ts-expect-error A dog-only property handler cannot handle every animal.
const rejectedProperty: PropertySlot<Animal> = dogProperty;
```

The method exception is a compatibility rule, not evidence that the assignment is safe. It also explains why syntax can change assignability even when the method and property appear to describe the same callback.

## Treat mutable covariance as an unsound boundary

TypeScript permits mutable arrays and plain mutable properties to covary. A wider alias can then write a value the narrower view cannot safely contain. No runtime element check repairs the original type claim.

```typescript
interface Animal { name: string }
interface Dog extends Animal { breed: string }

const dogs: Dog[] = [{ name: 'Rex', breed: 'lab' }];
const animals: Animal[] = dogs; // Allowed covariance.
animals.push({ name: 'Whiskers' });
console.log(dogs[1]?.breed); // undefined: the second value is not a Dog.

interface Box<T> { value: T }
const dogBox: Box<Dog> = { value: { name: 'Rex', breed: 'lab' } };
const animalBox: Box<Animal> = dogBox; // Also allowed.
animalBox.value = { name: 'Whiskers' };
console.log(dogBox.value.breed); // undefined.
```

Expose `readonly Dog[]` or a readonly property view to consumers that only need reads; it removes writes through that view. It does not freeze the original value or stop another mutable alias from changing it. When callers must both read and write safely, keep the owner in control or expose separate reader and writer contracts.

## Use `in` and `out` only when the inferred relationship needs help

TypeScript usually infers variance from how a type parameter is used. An annotation can document the intended direction or help a measured recursive comparison, but it cannot force unrelated structural types to become invariant. The annotation must agree with the type's actual input and output positions.

```typescript
interface Source<out T> {
  get(): T;
}
interface Sink<in T> {
  put(value: T): void;
}
interface Channel<in out T> {
  get(): T;
  put(value: T): void;
}
```

`Source<T>` produces values, `Sink<T>` consumes them, and `Channel<T>` does both. Most application code should rely on inference. Add annotations only when a specific comparison or documented API needs them, and profile before claiming a performance benefit.

## Summary

Trace where `T` enters and leaves a type. Producers are covariant, function inputs are contravariant under strict checking, and safe read/write APIs are invariant. TypeScript preserves method bivariance and mutable array/property covariance for compatibility, so readonly views and explicit ownership matter. Variance annotations document or guide same-generic comparisons; they do not change structural behavior.

# Type Variance

## TL;DR

Variance describes how composite types relate when their type arguments relate. Outputs are **covariant** (`Dog[]` is an `Animal[]`), inputs are **contravariant** (`(Animal) => void` is a `(Dog) => void`), sound read/write cells need **invariance**, but TypeScript does not enforce it for a plain mutable property. TypeScript historically compared function parameters *bivariantly*; `strictFunctionTypes` fixes that for function-type positions (method syntax stays bivariant for compatibility). Arrays stay covariant — and therefore unsound — because reads and writes mix. TS 4.7's `in`/`out` annotations let you declare variance explicitly, which can help checking complex recursive interfaces when variance inference is a measured bottleneck.

## First Principles

Variance answers "when is `Dog[]` a valid `Animal[]`?" — and the answer is what makes `push` unsafe:

1. **Covariance for outputs, contravariance for inputs** is the sound rule: producers can widen, consumers must narrow. Arrays are mutable (both roles), so TS's unsound covariant arrays are a *pragmatic* unsoundness with known sharp edges (`push` a Cat into `Dog[]`).
2. **Function parameter bivariance vs strictFunctionTypes** — method syntax stays bivariant for ergonomics; standalone function types are strictly checked: the flag is the soundness dial.
3. **Variance reasoning prevents real bugs**: callbacks (contravariant params!), mutable containers, and the classic `assignability of event handlers` — the mental model predicts what the compiler will accept.

## Why It Matters

Variance questions separate "uses TypeScript" from "understands TypeScript": Why can you push a `Cat` into a `Dog[]` without a compiler error? Why does changing `(e: Event) => void` to `(e: MouseEvent) => void` in your props break assignability only sometimes? Why did React's `onChange` typing need bivariance? Seniors answer these from first principles instead of sprinkling `any`.



## Definition

Given `Dog extends Animal`, variance defines when `Box<A>` is assignable to `Box<B>`: The compiler's answer differs by container: read-only and produce-only positions can safely covary, consumer positions must contravary, and mutable containers cannot vary at all because a write through the wider type would corrupt the narrower invariant — which is why the table below is really a table about where writes can happen.

| Variance | Relationship | Canonical example |
| ----------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **Covariant** | `A ⊂ B` ⇒ `Box<A> ⊂ Box<B>` (same direction) | `readonly T[]`, `Promise<T>`, return types |
| **Contravariant** | `A ⊂ B` ⇒ `Box<B> ⊂ Box<A>` (reversed) | Function parameters |
| **Invariant** | Type arguments must be compatible in both directions | Read plus function-property write APIs under strict checking |
| **Bivariant** | Either direction allowed | Function parameters when strict checking is off; method parameters even when it is on |

```text
ASSIGNABILITY DIRECTIONS
═══════════════════════════════════════════════════════════════

  Dog ──assignable to──▶ Animal          (subtyping)

  COvariant:     Dog[]   ──▶ Animal[]      follows the arrow
  CONTRAvariant: (Animal)=>void ──▶ (Dog)=>void   reversed

  Why contra? A handler promising to accept ANY Animal
  can safely stand in where a Dog-handler is expected.
  The reverse would crash on a Cat.
```


## How It Works

### Function Parameter Bivariance and strictFunctionTypes

```typescript
interface Animal { name: string }
interface Dog extends Animal { breed: string }

declare let animalHandler: (a: Animal) => void;
declare let dogHandler: (d: Dog) => void;

// Sound direction (contravariance): a handler that accepts any Animal
// certainly accepts Dogs.
animalHandler = dogHandler; // ERROR under strictFunctionTypes!
// Wait — read carefully: assigning dogHandler INTO animalHandler means
// the target expects to pass Animals; dogHandler only promised Dogs.
```

```typescript
// The SOUND assignment: replace a dog-specific callback with a
// more general one.
dogHandler = animalHandler; // OK — accepting Animal covers Dog
```

With `strictFunctionTypes: false` (or pre-2.6 behavior), TypeScript compares parameters *bivariantly* — both directions above compile. That was pragmatic (React event handlers kept working) but unsound. With `strict: true`, only the contravariant direction compiles — **except for methods declared with method syntax**, which remain bivariant by design:

```typescript
interface ComparatorBivariant {
  // Method syntax: parameters stay BIVARIANT even under strict
  compare(other: this): number;
}

interface ComparatorStrict {
  // Property/function syntax: full contravariance checking
  compare: (other: this) => number;
}
```

This distinction is why some library interfaces deliberately use method syntax — it keeps user-implemented handlers assignable while `strict` is on.

### Arrays Are Covariant — and Unsound

TypeScript makes mutable arrays covariant because (a) most array usage is read-heavy and (b) enforcing true invariance broke enormous amounts of existing code:

```typescript
const dogs: Dog[] = [{ name: "Rex", breed: "lab" }];

const animals: Animal[] = dogs; // Allowed: covariance

animals.push({ name: "Whiskers" }); // Cat sneaks into dogs!

console.log(dogs[1].breed); // undefined: this is the pushed object, not Rex
```

The write through the wider-typed alias corrupted the narrower array. This is a compile-time soundness hole: no runtime array-element check is emitted to enforce the narrower alias. Practical defense: treat arrays as covariant for reads, and avoid aliasing mutable collections across type widths — use `ReadonlyArray<T>` when you only read, which restores soundness because there is no `push`.

### in / out Variance Annotations (TS 4.7)

```typescript
// Producer only: T appears in output positions
interface Source<out T> {
  get(): T;
}

// Consumer only: T appears in input positions
interface Sink<in T> {
  put(value: T): void;
}

// Read-write: invariant — must annotate both
interface Channel<in out T> {
  get(): T;
  put(value: T): void;
}
```

Variance annotations guide comparisons of instantiations of the same generic type and can avoid repeated structural work. They do not globally rewrite structural assignability against unrelated shapes, and stricter annotations can unnecessarily reject usable APIs; measure before adding them throughout a library.

### Assignability Puzzle Set

```typescript
// Puzzle 1 — Promise covariance
type P1 = Promise<Dog>;
type P2 = Promise<Animal>;
declare const p1: P1;
const p2: P2 = p1; // OK: Promise<T> is covariant (T only in outputs)

// Puzzle 2 — handler swap direction
type OnMouse = (e: MouseEvent) => void;
type OnPointer = (e: PointerEvent) => void;
declare const general: OnMouse;
const specific: OnPointer = general;
// OK: PointerEvent extends MouseEvent, so a MouseEvent handler accepts it

// Puzzle 3 — a plain mutable property is still compared covariantly
interface Box<T> { value: T }
declare const boxDog: Box<Dog>;
const boxAnimal: Box<Animal> = boxDog; // Allowed, despite the mutable field
// boxAnimal.value = { name: "Cat" }; // Corrupts the Dog view

// Puzzle 4 — readonly restores covariance
interface ReadOnlyBox<T> { readonly value: T }
declare const roDog: ReadOnlyBox<Dog>;
const roAnimal: ReadOnlyBox<Animal> = roDog; // OK: outputs only
```

## Code Examples

### Demonstrating All Four Variances

```typescript
interface Animal { name: string }
interface Dog extends Animal { breed: string }

// Covariant wrapper — like ReadonlyArray
type Producer<T> = () => T;
declare const produceDog: Producer<Dog>;
const produceAnimal: Producer<Animal> = produceDog; // OK

// Contravariant wrapper — like event registration
type Consumer<T> = (item: T) => void;
declare const consumeAnimal: Consumer<Animal>;
const consumeDog: Consumer<Dog> = consumeAnimal;    // OK (strict)

// Invariant wrapper: output field plus contravariant function-property input
class Cell<T> {
  constructor(public value: T) {}
  set = (value: T): void => { this.value = value; };
}
declare const cellDog: Cell<Dog>;
// const cellAnimal: Cell<Animal> = cellDog;
// Error: Type 'Cell<Dog>' is not assignable to 'Cell<Animal>'
```

### The Unsound Array Hole, Repaired

```typescript
function unsound(): void {
  const dogs: Dog[] = [];
  const animals: Animal[] = dogs;       // covariant alias
  animals.push({ name: "Cat" });        // runtime corruption
  const d: Dog | undefined = dogs.pop();
  console.log(d?.breed);                // undefined — lied about
}

function sound(): void {
  const dogs: readonly Dog[] = [];
  const animals: readonly Animal[] = dogs; // still covariant...
  // animals.push(...)  // ...but writes are impossible now: sound
}
```

### EventEmitter Listener Typing Under strict

The generic constraint below recognizes callback shapes without demanding that each callback accept unknown. A `(UIEvent) => void` handler cannot satisfy `(unknown) => void` under strict parameter checking; the broad constraint is only the admissibility check, while `Events[K]` preserves the actual listener signature.

```typescript
type ListenerMap = {
  click: (event: MouseEvent) => void;
  keypress: (event: KeyboardEvent) => void;
};

class TypedEmitter<Events extends { [K in keyof Events]: (e: any) => void }> {
  private listeners = new Map<keyof Events, Set<Events[keyof Events]>>();

  on<K extends keyof Events>(type: K, fn: Events[K]): void {
    const listeners = this.listeners.get(type) ?? new Set<Events[keyof Events]>();
    listeners.add(fn);
    this.listeners.set(type, listeners);
  }
}

// Registering a GENERAL handler where a SPECIFIC one is expected:
// works because parameters are checked contravariantly.
declare const logAny: (e: unknown) => void;

const emitter = new TypedEmitter<{
  resize: (e: UIEvent) => void;
}>();

emitter.on("resize", logAny); // OK — accepting unknown ⊇ accepting UIEvent
```

### Declaring Variance for a Codec

```typescript
// Start with an inferred read/write contract; annotation can make it explicit.
interface Codec<T> {
  encode: (value: T) => unknown;   // T in input  → needs 'in'
  decode: (raw: unknown) => T;     // T in output → needs 'out'
}

// encode+decode together force INVARIANCE:
interface StrictCodec<in out T> {
  encode: (value: T) => unknown;
  decode: (raw: unknown) => T;
}
```

## Real-World Use Cases

1. **React props**: A component typed `onSelect: (id: string) => void` happily receives `(value: unknown) => void` handlers — contravariance in daily action.
2. **Redux reducers**: `Reducer<State, Action>` accepts handlers for union `Action`s; a handler for a *broader* action union substitutes fine, a narrower one does not.
3. **Zustand stores**: `set`/`get` partial-update signatures lean on invariance of the state object to prevent cross-store mixing.
4. **API clients**: `Promise<User>` responses flow into `Promise<Entity>` consumers because promise covariance mirrors data-flow direction.
5. **Read-only event streams**: A producer of MouseEvents can satisfy a consumer-facing producer of Events. The reverse direction needs runtime narrowing or a filter, because every Event is not a MouseEvent.

## Common Mistakes

### 1. Silencing Variance Errors With Method Syntax

```typescript
// BAD: switching to method notation just to make the error disappear,
// silently reintroducing unsoundness
interface BadListener {
  onUpdate(e: CustomEvent): void;   // bivariant loophole
}

// GOOD: keep property syntax; widen the parameter honestly
interface GoodListener {
  onUpdate: (e: Event) => void;     // accept the broader type
}
```

### 2. Casting Instead of Widening Parameters

```typescript
// BAD: erases the promise that this callback accepts only MouseEvents
const mouseOnly = (e: MouseEvent): void => { console.log(e.clientX); };
const onAnyEvent = mouseOnly as (e: Event) => void;
// A KeyboardEvent passed to onAnyEvent lacks the coordinate the code expects.

// GOOD: receive the wider input and establish what is present
const onEventSafe = (e: Event): void => {
  if (e instanceof MouseEvent) console.log(e.clientX);
};
```

### 3. Assuming Generics Are Covariant Everywhere

```typescript
// BAD: expected this to compile like Promise<T>
declare const listDog: Cell<Dog>;
const listAnimal: Cell<Animal> = listDog; // Error — invariant

// GOOD: model mutability honestly; split reader/writer interfaces
interface Reader<out T> { read(): T }
interface Writer<in T> { write(v: T): void }
```

### 4. Writing Into Wider Aliases of Mutable Arrays

> The corrupted array and its readonly alternative are demonstrated in **Code Examples — The Unsound Array Hole, Repaired**.

Expose `readonly Dog[]` to readers and retain mutation in the owning module. The view removes array-writing operations; it does not freeze the original array or its element objects.

### 5. Misreading Which Direction Is Legal

```typescript
// Direction mnemonic — memorize with the puzzle:
// (Animal)=>void IS assignable TO (Dog)=>void slot.  ✔
// (Dog)=>void   IS NOT assignable TO (Animal)=>void slot. ✘
// If your mental model says otherwise, re-derive from
// "the handler must handle whatever the caller sends."
```

## Best Practices

1. **Enable `strictFunctionTypes`** (free with `strict`) — bivariance is legacy compatibility, not a feature.
2. **Prefer widening handler parameters over casting** — contravariance is the intended escape hatch.
3. **Use `ReadonlyArray`/`readonly` fields when a consumer should not mutate** — it converts dangerous covariance into sound covariance.
4. **Use `in`/`out` selectively** when documenting a stable contract or addressing measured recursive-type checking cost; do not annotate every parameter by default.
5. **Keep method-syntax bivariance as a deliberate compat tool**, never as an accident of style.
6. **Design producer/consumer splits** (`Reader`/`Writer`) so each side gets the correct variance naturally.

## Performance Considerations

Inferred variance can let the checker compare type arguments instead of repeatedly visiting every member. Explicit annotations sometimes help recursive relationships whose variance is expensive or ambiguous, but improvement is not guaranteed by interface size alone. Profile with compiler diagnostics or traces before optimizing; adopting method bivariance or `any` to reduce errors discards useful checking rather than demonstrating a performance win.

## Summary

- Variance relates generic arguments to container assignability: output-only types can covary, function-property inputs contravary under strict checking, and a sound read/write API is invariant. Plain mutable fields remain a TypeScript soundness gap.
- `strictFunctionTypes` enforces contravariant parameter checking for function-type properties; method syntax remains bivariant for ecosystem compatibility.
- Arrays are covariant for usability, which is unsound for writes; `ReadonlyArray` restores soundness.
- `in`/`out` annotations (TS 4.7+) guide generic-instantiation comparisons; use them intentionally and measure any performance claim.
- Interview puzzles reduce to one question: "does the substitute handle everything the original position will send it?"

## Revision Questions

**Definition**

1. **Q:** Why may a function accepting any Animal replace a Dog callback?
   **A:** Every Dog that the caller can supply is also an Animal. The broader input promise therefore covers the narrower callback slot.

**How It Works**

2. **Q:** Which syntax keeps callback parameters bivariant even with strict function checking?
   **A:** Method declarations keep the compatibility exception. Function-valued properties receive contravariant parameter checking instead.

3. **Q:** Why does the pushed object appear at index one in the array example?
   **A:** The original Rex object occupies index zero and retains its breed. The write through the Animal alias appends a different object lacking that field.

4. **Q:** Does a plain `{ value: T }` field make a TypeScript container invariant?
   **A:** The checker still permits covariant assignment of that shape. A function-property setter plus an output, or a deliberate variance annotation, is needed to express the stricter generic contract.

**Code Examples**

5. **Q:** Which event type is more specific: PointerEvent or MouseEvent?
   **A:** PointerEvent extends MouseEvent with extra information. A general MouseEvent handler can replace a PointerEvent handler, while the opposite substitution may receive missing fields.

6. **Q:** Why must an emitter's callback constraint avoid requiring unknown input for every handler?
   **A:** A specialized handler cannot process arbitrary unknown values. The constraint should recognize a callback shape while preserving each event's actual parameter type for registration.

**Common Mistakes**

7. **Q:** What protection does a readonly array view leave unprovided?
   **A:** It blocks array writes through that view, but other aliases can still mutate the original. Its elements are not automatically frozen either.

**Performance Considerations**

8. **Q:** When can explicit variance annotations improve compilation work?
   **A:** They can help comparisons of the same generic type when recursive variance inference is expensive or ambiguous. Profiling is needed to establish a benefit for the actual project.

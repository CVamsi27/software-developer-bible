# Type Variance

## TL;DR

Variance describes how composite types relate when their type arguments relate. Outputs are **covariant** (`Dog[]` is an `Animal[]`), inputs are **contravariant** (`(Animal) => void` is a `(Dog) => void`), mutable cells are **invariant**. TypeScript historically compared function parameters *bivariantly*; `strictFunctionTypes` fixes that for function-type positions (method syntax stays bivariant for compatibility). Arrays stay covariant — and therefore unsound — because reads and writes mix. TS 4.7's `in`/`out` annotations let you declare variance explicitly, which also speeds up checking on big interfaces.

## Why It Matters

Variance questions separate "uses TypeScript" from "understands TypeScript": Why can you push a `Cat` into a `Dog[]` without a compiler error? Why does changing `(e: Event) => void` to `(e: MouseEvent) => void` in your props break assignability only sometimes? Why did React's `onChange` typing need bivariance? Seniors answer these from first principles instead of sprinkling `any`.

## Definition

Given `Dog extends Animal`, variance defines when `Box<A>` is assignable to `Box<B>`:

| Variance          | Relationship                                 | Canonical example                                                        |
| ----------------- | -------------------------------------------- | ------------------------------------------------------------------------ |
| **Covariant**     | `A ⊂ B` ⇒ `Box<A> ⊂ Box<B>` (same direction) | `readonly T[]`, `Promise<T>`, return types                               |
| **Contravariant** | `A ⊂ B` ⇒ `Box<B> ⊂ Box<A>` (reversed)       | Function parameters                                                      |
| **Invariant**     | Assignable only if `A` and `B` are identical | `{ value: T }` (mutable), `Array<T>` in theory                           |
| **Bivariant**     | Either direction allowed                     | Method parameters under `strictFunctionTypes: false` or method shorthand |

```text
ASSIGNABILITY DIRECTIONS
═══════════════════════════════════════════════════════════════

  Dog ──assignable to──▶ Animal          (subtyping)

  COvariant:     Dog[]   ──▶ Animal[]      follows the arrow
  CONTRAvariant: (Animal)=>void ◀── (Dog)=>void   against it

  Why contra? A handler promising to accept ANY Animal
  can safely stand in where a Dog-handler is expected.
  The reverse would crash on a Cat.
```

## Why Do We Need It?

1. **Predictable APIs**: Knowing variance tells you which generic swaps compile without trial and error.
2. **Sound callbacks**: Event handlers and comparators rely on parameter contravariance; misunderstanding it forces unsafe casts.
3. **Interview signal**: "Explain why arrays being covariant is unsound" is a classic senior discriminator.
4. **Library design**: `in`/`out` annotations make intent explicit and help the checker resolve variance faster on large types.
5. **Debugging strictFunctionTypes**: Migrating a codebase to strict mode produces exactly one class of new errors — and this chapter explains all of them.

## How It Works

### Function Parameter Bivariance and strictFunctionTypes

```typescript
interface Animal { name: string }
interface Dog extends Animal { breed: string }

declare let animalHandler: (a: Animal) => void;
declare let dogHandler: (d: Dog) => void;

// Sound direction (contravariance): a handler that accepts any Animal
// certainly accepts Dogs.
animalHandler = dogHandler; // ERROR under strictFunctionTypes!
// Wait — read carefully: assigning dogHandler INTO animalHandler means
// the target expects to pass Animals; dogHandler only promised Dogs.
```

```typescript
// The SOUND assignment: replace a dog-specific callback with a
// more general one.
dogHandler = animalHandler; // OK — accepting Animal covers Dog
```

With `strictFunctionTypes: false` (or pre-2.6 behavior), TypeScript compares parameters *bivariantly* — both directions above compile. That was pragmatic (React event handlers kept working) but unsound. With `strict: true`, only the contravariant direction compiles — **except for methods declared with method syntax**, which remain bivariant by design:

```typescript
interface ComparatorBivariant {
  // Method syntax: parameters stay BIVARIANT even under strict
  compare(other: this): number;
}

interface ComparatorStrict {
  // Property/function syntax: full contravariance checking
  compare: (other: this) => number;
}
```

This distinction is why some library interfaces deliberately use method syntax — it keeps user-implemented handlers assignable while `strict` is on.

### Arrays Are Covariant — and Unsound

TypeScript makes mutable arrays covariant because (a) most array usage is read-heavy and (b) enforcing true invariance broke enormous amounts of existing code:

```typescript
const dogs: Dog[] = [{ name: "Rex", breed: "lab" }];

const animals: Animal[] = dogs; // Allowed: covariance

animals.push({ name: "Whiskers" }); // Cat sneaks into dogs!

console.log(dogs[0].breed); // undefined at runtime — DOG[] LIED
```

The write through the wider-typed alias corrupted the narrower array. This is the textbook unsoundness hole; every language with covariant mutable arrays (Java, C#, Dart pre-null-safety) has it. Practical defense: treat arrays as covariant for reads, and avoid aliasing mutable collections across type widths — use `ReadonlyArray<T>` when you only read, which restores soundness because there is no `push`.

### in / out Variance Annotations (TS 4.7)

```typescript
// Producer only: T appears in output positions
interface Source<out T> {
  get(): T;
}

// Consumer only: T appears in input positions
interface Sink<in T> {
  put(value: T): void;
}

// Read-write: invariant — must annotate both
interface Channel<in out T> {
  get(): T;
  put(value: T): void;
}
```

Benefits: the compiler no longer has to infer variance structurally (faster checks on huge recursive interfaces like DOM lib types), and you get an error at the interface if your declared variance contradicts actual usage — documentation that cannot rot.

### Assignability Puzzle Set

```typescript
// Puzzle 1 — Promise covariance
type P1 = Promise<Dog>;
type P2 = Promise<Animal>;
declare const p1: P1;
const p2: P2 = p1; // OK: Promise<T> is covariant (T only in outputs)

// Puzzle 2 — handler swap direction
type OnClick = (e: MouseEvent) => void;
type OnAnyPointer = (e: PointerEvent) => void;
declare const general: OnAnyPointer;
const specific: OnClick = general;
// OK: PointerEvent supertype of MouseEvent → contravariant param fits

// Puzzle 3 — mutable property kills covariance
interface Box<T> { value: T }
declare const boxDog: Box<Dog>;
const boxAnimal: Box<Animal> = boxDog; // ERROR: invariant (mutable .value)

// Puzzle 4 — readonly restores covariance
interface ReadOnlyBox<T> { readonly value: T }
declare const roDog: ReadOnlyBox<Dog>;
const roAnimal: ReadOnlyBox<Animal> = roDog; // OK: outputs only
```

## Code Examples

### Demonstrating All Four Variances

```typescript
interface Animal { name: string }
interface Dog extends Animal { breed: string }

// Covariant wrapper — like ReadonlyArray
type Producer<T> = () => T;
declare const produceDog: Producer<Dog>;
const produceAnimal: Producer<Animal> = produceDog; // OK

// Contravariant wrapper — like event registration
type Consumer<T> = (item: T) => void;
declare const consumeAnimal: Consumer<Animal>;
const consumeDog: Consumer<Dog> = consumeAnimal;    // OK (strict)

// Invariant wrapper — mutable cell
class Cell<T> {
  constructor(public value: T) {}
}
declare const cellDog: Cell<Dog>;
// const cellAnimal: Cell<Animal> = cellDog;
// Error: Type 'Cell<Dog>' is not assignable to 'Cell<Animal>'
```

### The Unsound Array Hole, Repaired

```typescript
function unsound(): void {
  const dogs: Dog[] = [];
  const animals: Animal[] = dogs;       // covariant alias
  animals.push({ name: "Cat" });        // runtime corruption
  const d: Dog | undefined = dogs.pop();
  console.log(d?.breed);                // undefined — lied about
}

function sound(): void {
  const dogs: readonly Dog[] = [];
  const animals: readonly Animal[] = dogs; // still covariant...
  // animals.push(...)  // ...but writes are impossible now: sound
}
```

### EventEmitter Listener Typing Under strict

```typescript
type ListenerMap = {
  click: (event: MouseEvent) => void;
  keypress: (event: KeyboardEvent) => void;
};

class TypedEmitter<Events extends Record<string, (e: unknown) => void>> {
  private listeners = new Map<keyof Events, Set<Events[keyof Events]>>();

  on<K extends keyof Events>(type: K, fn: Events[K]): void {
    /* ... */
  }
}

// Registering a GENERAL handler where a SPECIFIC one is expected:
// works because parameters are checked contravariantly.
declare const logAny: (e: unknown) => void;

const emitter = new TypedEmitter<{
  resize: (e: UIEvent) => void;
}>();

emitter.on("resize", logAny); // OK — accepting unknown ⊇ accepting UIEvent
```

### Declaring Variance for a Big Recursive Type

```typescript
// Before: TS infers variance by scanning every member (slow on
// thousands of members, e.g., lib.dom.d.ts internals).
interface JsonValue { /* ... */ }

// After: annotation documents + enforces + speeds up checking.
interface Codec<T> {
  encode: (value: T) => unknown;   // T in input  → needs 'in'
  decode: (raw: unknown) => T;     // T in output → needs 'out'
}

// encode+decode together force INVARIANCE:
interface StrictCodec<in out T> {
  encode: (value: T) => unknown;
  decode: (raw: unknown) => T;
}
```

## Real-World Use Cases

1. **React props**: A component typed `onSelect: (id: string) => void` happily receives `(value: unknown) => void` handlers — contravariance in daily action.
2. **Redux reducers**: `Reducer<State, Action>` accepts handlers for union `Action`s; a handler for a *broader* action union substitutes fine, a narrower one does not.
3. **Zustand stores**: `set`/`get` partial-update signatures lean on invariance of the state object to prevent cross-store mixing.
4. **API clients**: `Promise<User>` responses flow into `Promise<Entity>` consumers because promise covariance mirrors data-flow direction.
5. **DOM event libraries**: RxJS `Observable<Event> → Observable<MouseEvent>` pipelines work only because observables are read-only producers (covariant).

## Common Mistakes

### 1. Silencing Variance Errors With Method Syntax

```typescript
// BAD: switching to method notation just to make the error disappear,
// silently reintroducing unsoundness
interface BadListener {
  onUpdate(e: CustomEvent): void;   // bivariant loophole
}

// GOOD: keep property syntax; widen the parameter honestly
interface GoodListener {
  onUpdate: (e: Event) => void;     // accept the broader type
}
```

### 2. Casting Instead of Widening Parameters

```typescript
// BAD: hides a real mismatch; crashes if payload isn't a MouseEvent
const onClick = ((e: unknown) => {}) as (e: MouseEvent) => void;

// GOOD: declare what you actually handle
const onClickSafe = (e: Event): void => { /* narrow inside */ };
```

### 3. Assuming Generics Are Covariant Everywhere

```typescript
// BAD: expected this to compile like Promise<T>
declare const listDog: Cell<Dog>;
const listAnimal: Cell<Animal> = listDog; // Error — invariant

// GOOD: model mutability honestly; split reader/writer interfaces
interface Reader<out T> { read(): T }
interface Writer<in T> { write(v: T): void }
```

### 4. Writing Into Wider Aliases of Mutable Arrays

```typescript
// BAD: the classic corruption from earlier
const animals: Animal[] = dogs;
animals.push(someCat);

// GOOD: expose readonly views; keep mutation behind the owning module
function renderDogs(dogs: readonly Dog[]): void { /* ... */ }
```

### 5. Misreading Which Direction Is Legal

```typescript
// Direction mnemonic — memorize with the puzzle:
// (Animal)=>void IS assignable TO (Dog)=>void slot.  ✔
// (Dog)=>void   IS NOT assignable TO (Animal)=>void slot. ✘
// If your mental model says otherwise, re-derive from
// "the handler must handle whatever the caller sends."
```

## Best Practices

1. **Enable `strictFunctionTypes`** (free with `strict`) — bivariance is legacy compatibility, not a feature.
2. **Prefer widening handler parameters over casting** — contravariance is the intended escape hatch.
3. **Use `ReadonlyArray`/`readonly` fields when a consumer should not mutate** — it converts dangerous covariance into sound covariance.
4. **Annotate `in`/`out` on public generic interfaces** in libraries: self-documenting, enforced, and faster type-checking.
5. **Keep method-syntax bivariance as a deliberate compat tool**, never as an accident of style.
6. **Design producer/consumer splits** (`Reader`/`Writer`) so each side gets the correct variance naturally.

## Performance Considerations

- Structural variance inference walks every member of large interfaces; explicit `in out` annotations cut that work — measurable on lib-sized types.
- Bivariant method syntax reduces error surface but also reduces checking work; do not adopt it for speed alone.
- `noImplicitAny` interacts here too: untyped callbacks skip variance analysis entirely, hiding both errors and cost.

## Summary

- Variance answers "when is `C<A>` assignable to `C<B>`": covariant with outputs, contravariant with inputs, invariant with mutable cells.
- `strictFunctionTypes` enforces contravariant parameter checking for function-type properties; method syntax remains bivariant for ecosystem compatibility.
- Arrays are covariant for usability, which is unsound for writes; `ReadonlyArray` restores soundness.
- `in`/`out` annotations (TS 4.7+) document, enforce, and accelerate variance resolution.
- Interview puzzles reduce to one question: "does the substitute handle everything the original position will send it?"

## Cheat Sheet
```text
TYPE VARIANCE CHEAT SHEET
═══════════════════════════════════════════════════════════════

DEFINITIONS (Dog <: Animal):
• Covariant      C<Dog> → C<Animal>     (outputs)
• Contravariant  C<Animal> → C<Dog>     (inputs/callbacks)
• Invariant      identical only         (mutable cells)
• Bivariant      either direction       (legacy/methods)

FUNCTIONS:
• Params: contravariant (under strictFunctionTypes)
• Return: covariant always
• strictFunctionTypes OFF or method syntax → params bivariant

ARRAYS:
• Mutable arrays: covariant AND UNSOUND (push through alias)
• readonly T[]: covariant and sound (no writes)

ANNOTATIONS (TS 4.7+):
• interface Source<out T>     producer
• interface Sink<in T>        consumer
• interface Pipe<in out T>    read+write → invariant

PUZZLE RULE:
• A value can fill a slot if it handles everything
  the slot might receive — nothing more required.
```

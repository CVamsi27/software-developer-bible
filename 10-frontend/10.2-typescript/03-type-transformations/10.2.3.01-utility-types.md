# Utility Types

## Definition

**Utility types** are built-in TypeScript types that provide common type transformations. They allow you to manipulate and transform types without writing complex type logic from scratch.

> **Textbook Definition:** Utility types are reusable type-level transformations that derive a new contract from an existing type. They can select properties, change modifiers or extract function structure, without modifying runtime values.

A profile screen shows id/name, allows changes to name/email, and receives a promise from its loader. These are three relationships: select public fields, make selected editable fields optional, and describe the resolved result. Utilities encode those relationships from one source contract; they do not perform the corresponding projection, patch or await.

## First Principles

The built-in utilities are the standard library of type transformation:

1. **Each utility combines a few basic type operations.** Mapped types build properties, conditional types select a result, and indexed access retrieves a property type. Reading the definitions of `Partial`, `Pick`, `Omit` and `ReturnType` shows how these operations work together.
2. **Derive related shapes from one source.** `Pick<Api, "a" | "b">` takes those properties from `Api`. Changes to their types carry through automatically. A separate handwritten copy can fall out of sync. Selecting keys also makes the intended public fields explicit.

## Why It Matters

Senior engineers reach for `Pick`/`Omit` to derive DTOs from larger models, `Partial<>` for update endpoints (PATCH), `Readonly<>` for immutable views, and `ReturnType<typeof fn>` to extract function return types without re-declaring. They are the daily vocabulary of typed code.



## How It Works

Check each independent code block as a strict TypeScript module; later examples name their own shapes or explicitly reuse User. API adapters marked declare are application contracts, not runnable validators. The only intentionally rejected writes are marked @ts-expect-error.

### Partial<T>

```typescript
// Makes all properties optional
interface User {
  id: string;
  name: string;
  email: string;
  age: number;
}

type PartialUser = Partial<User>;
// {
// id?: string;
// name?: string;
// email?: string;
// age?: number;
// }

// A pure update of selected fields; no database or authorization is implied.
type EditableProfile = Pick<User, "name" | "email">;
type ProfilePatch = Partial<EditableProfile>;
function applyProfilePatch(current: User, updates: ProfilePatch): User {
  return {
    ...current,
    name: updates.name === undefined ? current.name : updates.name,
    email: updates.email === undefined ? current.email : updates.email,
  };
}
const current: User = { id: "1", name: "Alice", email: "a@b.com", age: 30 };
console.log(applyProfilePatch(current, { name: "Bob" }).name); // Bob
console.log(current.name); // Alice: original outer object unchanged

```

The update admits no id/age field through this contract and treats undefined as no change, including when exactOptionalPropertyTypes is off. A server must validate unknown input and authorize the edit; this function only applies already-validated data. A real PATCH protocol must separately decide whether null clears a value, arrays replace or merge, and nested objects are shallow or deep.

### Required<T>

```typescript
// Makes all properties required
interface Config {
  host?: string;
  port?: number;
  debug?: boolean;
}

type RequiredConfig = Required<Config>;
// {
// host: string;
// port: number;
// debug: boolean;
// }

function describeServer(config: RequiredConfig): string {
  return `${config.host}:${config.port} debug=${config.debug}`;
}
console.log(describeServer({ host: "localhost", port: 3000, debug: false }));
// localhost:3000 debug=false
// @ts-expect-error Required removed optionality; it did not fill a default port.
describeServer({ host: "localhost", debug: false });

```

### Readonly<T>

```typescript
// Makes all properties readonly
interface Point {
  x: number;
  y: number;
}

type ReadonlyPoint = Readonly<Point>;
// {
// readonly x: number;
// readonly y: number;
// }

const point: ReadonlyPoint = { x: 1, y: 2 };
// @ts-expect-error The readonly view rejects this typed write.
point.x = 3;

// A shallow readonly view: no runtime freeze, nested data can still mutate
const nested: Readonly<{ settings: { enabled: boolean } }> = {
  settings: { enabled: true }
};
nested.settings.enabled = false; // Allowed; only replacing settings is blocked

```

### Pick<T, K>

```typescript
// Extracts a subset of properties
interface User {
  id: string;
  name: string;
  email: string;
  password: string;
  createdAt: Date;
}

type UserPreview = Pick<User, "id" | "name" | "email">;
// {
// id: string;
// name: string;
// email: string;
// }

// Real-world: API response with limited fields
async function getUserPreview(id: string): Promise<UserPreview> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}?fields=id,name,email`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const data: unknown = await response.json();
  return parsePreview(data);
}
declare function parsePreview(data: unknown): UserPreview; // Runtime validator

```

### Omit<T, K>

```typescript
// Removes a subset of properties
interface User {
  id: string;
  name: string;
  email: string;
  password: string;
  createdAt: Date;
}

type CreateUserDTO = Omit<User, "id" | "createdAt">;
// {
// name: string;
// email: string;
// password: string;
// }

// Real-world: Create entity without auto-generated fields
async function createUser(data: CreateUserDTO): Promise<User> {
  const response = await fetch("/api/users", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(data) // The server supplies generated fields
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const result: unknown = await response.json();
  return parseUser(result);
}
declare function parseUser(data: unknown): User; // Runtime validator

```

### Record<K, T>

```typescript
// Creates an object type with keys K and values T
type Fruit = "apple" | "banana" | "orange";
type FruitCount = Record<Fruit, number>;
// {
// apple: number;
// banana: number;
// orange: number;
// }

const inventory: FruitCount = {
  apple: 10,
  banana: 5,
  orange: 8
};

// Real-world: Lookup tables
type UserRoles = Partial<Record<string, "admin" | "user" | "guest">>;
const roles: UserRoles = {
  "user1": "admin",
  "user2": "user",
  "user3": "guest"
};

// With nested objects
type StatusMessages = Record<
  "success" | "error" | "warning",
  { message: string; code: number }
>;

```

A finite Fruit union requires apple, banana and orange on the assigned inventory. A string-key dictionary instead represents open-ended names whose entries can be missing at runtime; Partial explicitly admits absence. Record does not allocate entries, guard prototype names or populate a lookup.

### Exclude<T, U>

```typescript
// Removes types from a union
type Status = "active" | "inactive" | "pending" | "deleted";
type ActiveStatus = Exclude<Status, "deleted" | "pending">;
// "active" | "inactive"

// Real-world: Filter options
type AllSortFields = "name" | "email" | "createdAt" | "password";
type SafeSortFields = Exclude<AllSortFields, "password">;
// "name" | "email" | "createdAt"

function sortBy(field: SafeSortFields): void {
  // Can't sort by password
}

```

### Extract<T, U>

```typescript
// Extracts types from a union
type Status = "active" | "inactive" | "pending" | "deleted";
type ActiveStatus = Extract<Status, "active" | "inactive">;
// "active" | "inactive"

// Real-world: Filter event types
type UIEventName = "click" | "scroll" | "resize" | "load";
type MouseEvents = Extract<UIEventName, "click" | "scroll">;
// "click" | "scroll"

```

### NonNullable<T>

```typescript
// Removes null and undefined from a type
type MaybeString = string | null | undefined;
type DefinitelyString = NonNullable<MaybeString>;
// string

// Real-world: After null checks
function processValue(value: string | null): string {
  if (value === null) {
    throw new Error("Value is null");
  }
  // value is string (NonNullable applied by control flow)
  return value.toUpperCase();
}

```

### Parameters<T>

```typescript
// Extracts function parameter types as a tuple
function makeUser(name: string, age: number, email: string) {
  return { id: "1", name, age, email, createdAt: new Date() };
}

type CreateUserParams = Parameters<typeof makeUser>;
// [string, number, string]

// A plain-function forwarding relationship; no scheduling or receiver binding.
function invoke<F extends (...args: any[]) => any>(
  fn: F, ...args: Parameters<F>
): ReturnType<F> {
  return fn(...args);
}
console.log(invoke(makeUser, "Ada", 30, "a@b.com").name); // Ada

```

Parameters derives the ordered argument tuple; invoke forwards exactly those values under a plain-call contract. An overloaded function uses its last signature for this extraction. Full scheduling, cancellation and receiver preservation belong to the [canonical Debounce](../../10.1-javascript/04-memory-and-data/10.1.4.04-debounce.md) implementation.

### ReturnType<T>

```typescript
// Extracts function return type
interface User { id: string; name: string }
declare function getUser(id: string): Promise<User>; // Declared API contract

type GetUserReturn = ReturnType<typeof getUser>;
// Promise<User>

// Real-world: Type inference from functions
function createInitialState() {
  return {
    items: [] as string[],
    loading: false,
    error: null as string | null
  };
}

type State = ReturnType<typeof createInitialState>;
// { items: string[]; loading: boolean; error: string | null }

```

### InstanceType<T>

```typescript
// Extracts instance type from a class
class User {
  constructor(
    public name: string,
    public email: string
  ) {}
}

type UserInstance = InstanceType<typeof User>;
// User

// Real-world: Dependency injection
function createUserService(UserModel: new (name: string, email: string) => User): UserInstance {
  return new UserModel("default", "default@example.com");
}

```

### Awaited<T>

```typescript
// Models the recursively resolved value of await, including thenables.
// This is a type transformation; it does not await a runtime value.
type A = Awaited<Promise<string>>; // string
type B = Awaited<Promise<Promise<number>>>; // number
type C = Awaited<string | Promise<number>>; // string | number

// Real-world: Async function return types
async function fetchData(): Promise<string> {
  return Promise.resolve("data");
}

type DataType = Awaited<ReturnType<typeof fetchData>>;
// string

```

## Code Examples

### Comprehensive Transformation Example

```typescript
interface User {
  id: string;
  name: string;
  email: string;
  password: string;
  role: "admin" | "user" | "guest";
  createdAt: Date;
}

// Different views of the same entity
type UserPublic = Pick<User, "id" | "name">;
type CreateUserDTO = Omit<User, "id" | "createdAt">;
type UpdateUserDTO = Partial<Pick<User, "name" | "email">>;
type UserPreview = Pick<User, "id" | "name" | "email">;
type UserRoles = Partial<Record<User["id"], User["role"]>>;

// API response types
type ApiResponse<T> = {
  data: T;
  status: number;
  message: string;
};

type UserResponse = ApiResponse<User>;
type UserListResponse = ApiResponse<User[]>;

// Function types
type GetUserById = (id: string) => Promise<User | null>;
type GetUserParams = Parameters<GetUserById>; // [string]
type GetUserReturn = ReturnType<GetUserById>; // Promise<User | null>

```

### React Patterns

```typescript
// Component props
interface ButtonProps {
  label: string;
  onClick: () => void;
  variant?: "primary" | "secondary";
  disabled?: boolean;
}

// Make all props except 'label' optional
type ButtonPropsPartial = Pick<ButtonProps, "label"> & Partial<Omit<ButtonProps, "label">>;

// Extraction depends on this declared hook contract, not an incomplete effect.
interface User { id: string; name: string }
declare function useUser(id: string): {
  user: User | null; loading: boolean; error: string | null;
};
type UseUserReturn = ReturnType<typeof useUser>;
// { user: User | null; loading: boolean; error: string | null }

```

The hook declaration supplies a static API only; the actual request/error/stale-publication/cleanup lifecycle belongs to [useEffect](../../10.3-react/02-core-hooks/10.3.2.02-useeffect.md). For a concrete runtime projection, create {id:user.id,name:user.name} before serialization. Merely assigning a secret-bearing value to UserPublic still leaves its secret properties on that same object.

## Real-World Use Cases

- **Form draft types** — `Partial<Appointment>` for edit-in-progress, `Required<CreateForm>` for submit-time validation, `Pick<Appointment, 'status'>` for status chips.
- **Read-only boundaries** — `Readonly<Config>` blocks typed writes to top-level fields; nested values and other mutable aliases remain writable.
- **DTO projection** — `Omit<User, 'passwordHash'>` describes an API response shape. Runtime code must actually remove the field; the type does not redact it.

## Common Mistakes

### 1. Overusing Partial

```typescript
interface User { id: string; name: string; email: string }
function requireId(id: string): string { return id; }
function unsafeUpdate(user: Partial<User>): void {
  // @ts-expect-error A partial record has no guaranteed id.
  requireId(user.id);
}
type ProfilePatch = Partial<Pick<User, "name" | "email">>;
function updateTarget(id: string, updates: ProfilePatch): { id: string; updates: ProfilePatch } {
  return { id, updates };
}

```

### 2. Chaining Without Naming Intent

Name the public fields explicitly when the update endpoint must not gain new writable fields just because the source model grows:

```typescript
interface User { id: string; name: string; email: string; role: string }
type EditableUserFields = Pick<User, "name" | "email">;
type UserUpdate = Partial<EditableUserFields>;
```

This keeps the derivation while exposing the endpoint's allowlist. `Partial<Omit<Required<User>, "password">>` also permits IDs and timestamps, so it describes a different contract.

### 3. Forgetting Utility Types Exist

This final example reuses User from Comprehensive Transformation Example; the two names describe the same view without a runtime projection.

```typescript
// Bad: Manual type transformation
type UserWithoutPassword = {
  id: string;
  name: string;
  email: string;
  role: "admin" | "user" | "guest";
  createdAt: Date;
};

// Good: Use utility type
type DerivedUserWithoutPassword = Omit<User, "password">;

```

## Best Practices

- Derive named DTOs from a source model, and choose `Pick` when additions must require explicit review.
- Use object utilities for shallow shapes; a recursive utility needs domain-specific leaf rules.
- Use `Parameters` and `ReturnType` when the implementation owns the contract; overload extraction uses the last signature rather than selecting a call-specific overload.
- Use `Awaited<ReturnType<typeof fn>>` to describe an asynchronous result after resolution.
- Keep runtime validation and projection alongside the types: `Required` cannot fill defaults and `Omit` cannot delete a secret.

Optional properties also depend on `exactOptionalPropertyTypes`: with it enabled, an absent property and an explicitly assigned `undefined` are different unless the value type includes `undefined`. Removing `?` does not universally mean removing every explicit `undefined` from a field's domain.

## Performance Considerations

Utility types are erased and add no runtime memory or bundle code. Their compositions can still increase checker and editor work, especially when nested with recursive types or large unions. Measure the project that consumes the type rather than inferring cost from the utility's name.

## Summary

Utility types derive object views, filter union members and extract function or promise types. Their changes exist only in the checker: validation, defaults, redaction and freezing require runtime code.

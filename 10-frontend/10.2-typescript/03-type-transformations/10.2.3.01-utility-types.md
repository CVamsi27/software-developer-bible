# Utility Types

A profile API may expose only `id` and `name`, accept edits to `name` and `email`, and return a promise from its loader. Utility types derive these related contracts from one model, while runtime code still performs the projection, update and asynchronous work.

## Definition

**Utility types** are reusable transformations supplied by TypeScript's standard library. They derive a new type by selecting properties, changing modifiers, filtering union members or extracting a function's structure.

> **Textbook Definition:** A utility type is a named type-level operation that maps an existing type to a related contract. It changes what the checker accepts; it does not transform a runtime value.

## First Principles

Handwritten copies of related shapes drift when a source model changes. A utility keeps the relationship explicit: choose which fields belong in a view, which may be absent in an update, or which result follows from a function signature. That derivation is useful only when its inclusion and runtime behavior match the application contract.

## Derive public and editable object shapes

Start with one source model. `Pick` creates an allowlisted view, `Omit` excludes named keys, and `Partial` makes selected fields optional. These operations are shallow: nested objects keep their original shapes.

```typescript
interface User {
  id: string;
  name: string;
  email: string;
  passwordHash: string;
  createdAt: Date;
}

type UserPublic = Pick<User, 'id' | 'name'>;
type UserWithoutHash = Omit<User, 'passwordHash'>;
type ProfilePatch = Partial<Pick<User, 'name' | 'email'>>;
type UpdateProfileCommand = { userId: string; changes: ProfilePatch };

function toPublic(user: User): UserPublic {
  return { id: user.id, name: user.name };
}

function applyPatch(current: User, patch: ProfilePatch): User {
  return {
    ...current,
    name: patch.name === undefined ? current.name : patch.name,
    email: patch.email === undefined ? current.email : patch.email,
  };
}

const alice: User = {
  id: '1', name: 'Alice', email: 'a@example.com',
  passwordHash: 'stored-hash', createdAt: new Date(),
};
const publicUser = toPublic(alice); // { id: '1', name: 'Alice' }
const updated = applyPatch(alice, { name: 'Bob' });
// updated.name is 'Bob'; alice.name remains 'Alice'
```

`toPublic` creates an object that contains only the selected fields. Merely assigning `alice` to `UserPublic` or `UserWithoutHash` would change its static view, not remove `passwordHash` from the runtime object. `Pick` is also a safer allowlist when new model fields need review; `Omit` admits newly added fields unless they are excluded.

The patch type permits only `name` and `email`, not `id` or `passwordHash`; a command that identifies its target keeps `userId` required beside the optional changes. The spread returns a new outer object, while any nested references would remain shared. The implementation treats an explicitly supplied `undefined` as no change. With `exactOptionalPropertyTypes`, an optional property does not accept explicit `undefined` unless its value type includes it; without that flag, this function still treats `undefined` as no change. The server must validate outside data and authorize the edit. A real patch protocol must define null-clearing, nested-object and array behavior separately.

## Require fields, block typed writes, and describe key sets

`Required` removes optional modifiers; it does not supply defaults. `Readonly` prevents reassignment through that type view, but is shallow and does not freeze the object. `Record` describes a mapping from a key type to a value type.

```typescript
interface ServerConfig {
  host?: string;
  port?: number;
  debug?: boolean;
}

type CompleteConfig = Required<ServerConfig>;
const config: CompleteConfig = { host: 'localhost', port: 3000, debug: false };
// @ts-expect-error Required makes port mandatory; it does not choose a default.
const missingPort: CompleteConfig = { host: 'localhost', debug: false };

const point: Readonly<{ x: number; y: number }> = { x: 1, y: 2 };
// @ts-expect-error Reassignment through this readonly view is rejected.
point.x = 3;

const settings: Readonly<{ options: { enabled: boolean } }> = {
  options: { enabled: true },
};
settings.options.enabled = false; // Nested object is still mutable.
const mutableAlias = { options: { enabled: true } };
const readonlyView: Readonly<typeof mutableAlias> = mutableAlias;
mutableAlias.options.enabled = false; // A mutable alias can still change it.

type Locale = 'en' | 'de' | 'fr';
type Labels = Record<Locale, string>;
const labels: Labels = { en: 'Save', de: 'Speichern', fr: 'Enregistrer' };

type Role = 'admin' | 'member';
type RoleByUserId = Partial<Record<string, Role>>;
const roles: RoleByUserId = { 'user-1': 'admin' };
```

A finite `Record<Locale, string>` requires every listed locale. The open-ended dictionary admits arbitrary IDs and, because it is `Partial`, missing entries. Neither form allocates values, applies defaults, protects mutable aliases or validates an external key. For untrusted arbitrary keys, choose and validate an appropriate runtime data structure.

## Filter union members and nullish types

`Exclude` keeps union members not assignable to a type; `Extract` keeps the assignable members. `NonNullable` removes both `null` and `undefined`. These utilities describe static possibilities, while control-flow checks establish facts about actual values.

```typescript
type Status = 'active' | 'inactive' | 'pending' | 'deleted';
type VisibleStatus = Exclude<Status, 'pending' | 'deleted'>;
// 'active' | 'inactive'
type ActiveStatus = Extract<Status, 'active' | 'inactive'>;
// 'active' | 'inactive'

type MaybeName = string | null | undefined;
type Name = NonNullable<MaybeName>; // string

function requireName(value: MaybeName): string {
  if (value == null) throw new Error('Name is required');
  return value; // Runtime check narrows this value to string.
}
```

`Exclude` and `Extract` compare each union member by assignability; they do not remove a property from an object. The null check is real JavaScript control flow; `NonNullable` by itself does not check a value.

## Reuse function and constructor contracts

Function utilities derive parameter tuples, declared return types, constructor instance types and values resolved by `await`. The overload-sensitive case is worth remembering: `Parameters` and `ReturnType` use the last declared overload rather than selecting one from hypothetical call arguments.

```typescript
interface LoadedUserRecord { id: string; name: string }
declare function loadUser(id: string): Promise<LoadedUserRecord | null>;

type LoadUserArgs = Parameters<typeof loadUser>; // [id: string]
type LoadUserPromise = ReturnType<typeof loadUser>; // Promise<User | null>
type LoadedUser = Awaited<LoadUserPromise>; // User | null
type MixedResult = Awaited<string | Promise<number>>; // string | number

class UserClient {
  constructor(readonly endpoint: string) {}
}
type Client = InstanceType<typeof UserClient>; // UserClient
```

`Awaited` recursively models `await` and promise-like resolution; it does not wait for a runtime operation. `InstanceType` describes what construction returns, while `new UserClient(...)` performs construction. For a runtime async result, use `Awaited<ReturnType<typeof fn>>` only when the function signature is the source of truth.

## Keep the type and runtime contracts aligned

All these utilities are erased from emitted JavaScript. Validation, authorization, defaults, field redaction, freezing, network requests and promise resolution happen at runtime and need real implementations. Prefer a named type such as `ProfilePatch` when it makes an endpoint's writable fields clear, and use recursive utilities only when their rules for arrays, functions, dates and other domain objects are explicit.

## Summary

Utility types derive views, updates, key maps, filtered unions and function contracts. Check the resulting shape against the real API, then implement the runtime operation that validates, projects, mutates or resolves the value.

# Template Literal Types

## Definition

**Template literal types** build string types using backticks and string literal types, such as the exact type `'user'`. They can combine, split and transform these literal types to describe new permitted strings. Introduced in TypeScript 4.1, they help check CSS property names and event names. Combined with `infer`, which captures part of a matched type, and recursive conditional types, they can perform more complex string transformations during type checking. They do not manipulate runtime strings.

> **Textbook Definition:** A template literal type constructs string types by combining literal text with interpolated types. Union interpolations generate combinations, allowing string-shaped contracts to be described and decomposed at compile time.


## First Principles

Template literal types bring string construction to the type world:

1. **Many APIs identify things by strings.** Event handlers, CSS properties and route patterns all use names. Template literal types generate permitted names from known parts, such as `on${Capitalize<E>}` for an event union `E`. The checker can then reject a misspelled name.
2. **Patterns can also extract parts of a string type.** Built-in transformations such as `Uppercase` and `Capitalize` change literal types. A pattern such as `` `${infer Head}/${infer Rest}` `` names the pieces around a slash. Combining these operations can describe a small, deliberate naming grammar. Complex grammars increase checking work and can make errors hard to read.

## Why It Matters

Template literal types are useful when names come from a finite type-level vocabulary: event names, route parameter names and key conventions are common examples. They can constrain spelling, but do not prove that a route exists, a translation is present, or a CSS rule is installed. They also do not make SQL construction safe; query builders still need parameterized values and runtime validation.



## How It Works

### Basic Syntax

A template such as `Hello, ${"Ada" | "Bob"}!` permits exactly Hello, Ada! and Hello, Bob!. Two independent interpolated unions form every combination, called a Cartesian product. This expansion is separate from conditional-type distribution. A broad string interpolation represents a pattern rather than enumerating a finite whitelist.

Check independent snippets in strict TypeScript modules; aliases do not execute. The runtime route/translation examples below use their explicitly named literal grammar and application data. A static name contract does not ensure a corresponding event handler, CSS rule or translated message exists.

### String Transformers

```typescript
// Built-in string manipulation types
type UppercaseEvent = Uppercase<'click'>; // "CLICK"
type LowercaseEvent = Lowercase<'CLICK'>; // "click"
type Capitalized = Capitalize<'user'>; // "User"
type Uncapitalized = Uncapitalize<'User'>; // "user"

// Applied in template literals
type EventHandler<T extends string> = `on${Capitalize<T>}`;
type ClickHandler = EventHandler<'click'>; // "onClick"
type SubmitHandler = EventHandler<'submit'>; // "onSubmit"

// Union distribution
type Events = 'click' | 'focus' | 'blur';
type Handlers = `on${Capitalize<Events>}`;
// "onClick" | "onFocus" | "onBlur"
```

### Union Distribution in Template Literals

```typescript
// Template literals distribute over unions (cartesian product)
type Horizontal = 'left' | 'center' | 'right';
type Vertical = 'top' | 'middle' | 'bottom';

type Position = `${Vertical}-${Horizontal}`;
// "top-left" | "top-center" | "top-right" |
// "middle-left" | "middle-center" | "middle-right" |
// "bottom-left" | "bottom-center" | "bottom-right"

// With string transformers
type CSSClass = `align-${Vertical}-${Horizontal}`;
// "align-top-left" | "align-top-center" | ...
```

### Inference with Template Literals

```typescript
// Extract parts of a string using infer
type ExtractRoute<T extends string> =
  T extends `${infer Method} /${infer Path}`
    ? { method: Method; path: `/${Path}` }
    : never;

type Route1 = ExtractRoute<'GET /users'>;
// { method: "GET"; path: "/users" }

type Route2 = ExtractRoute<'POST /api/v2/products'>;
// { method: "POST"; path: "/api/v2/products" }

// Extract IDs from patterns
type ExtractUserId<T extends string> =
  T extends `/users/${infer Id}`
    ? Id
    : never;

type UserId1 = ExtractUserId<'/users/abc123'>; // "abc123"
type UserId2 = ExtractUserId<'/users/42'>; // "42"

// Multiple inference positions
type ParsePattern<T extends string> =
  T extends `${infer Resource}:${infer Action}`
    ? { resource: Resource; action: Action }
    : never;

type Parsed = ParsePattern<'user:create'>;
// { resource: "user"; action: "create" }
```

## Code Examples

### 1. Type-Safe Event Emitter

```typescript
type EventMap = {
  'user:created': { userId: string; timestamp: number };
  'user:updated': { userId: string; changes: string[] };
  'user:deleted': { userId: string; reason: string };
  'order:placed': { orderId: string; amount: number };
  'order:shipped': { orderId: string; trackingNumber: string };
};

// Derive event names from the map
type EventName = keyof EventMap;
// "user:created" | "user:updated" | "user:deleted" | "order:placed" | "order:shipped"

// Derive handler names
type HandlerName<T extends EventName> =
  T extends `${infer Resource}:${infer Action}`
    ? `on${Capitalize<Resource>}${Capitalize<Action>}`
    : never;

type UserCreatedHandler = HandlerName<'user:created'>;
// "onUserCreated"

type HandlerRegistry = {
  [E in EventName as HandlerName<E>]: (payload: EventMap[E]) => void;
};
// Example member: onUserCreated:(payload:{userId:string;timestamp:number})=>void
// This is a registry type, not a no-op class pretending to emit events.
```

For user:created, the pattern captures user and created, capitalizes both and builds onUserCreated. The mapped registry retains that event's payload. A runtime [event emitter](../04-advanced-patterns/10.2.4.05-advanced-patterns.md) still has to own subscriptions, delivery and cleanup. Distinct source names can collide after capitalization; define a unique naming grammar or reject collisions before generating a real registry.

### 2. Type-Safe CSS Properties

```typescript
// CSS property types
type CSSUnit = 'px' | 'rem' | 'em' | '%' | 'vw' | 'vh' | 'pt';
type CSSValue = `${number}${CSSUnit}`;

type Width = CSSValue; // "10px" | "2rem" | "50%" | ...
type Margin = `${CSSValue} ${CSSValue}`; // "10px 20px"
type Padding = `${CSSValue} ${CSSValue} ${CSSValue} ${CSSValue}`;

// Type-safe CSS-in-JS
interface CSSProperties {
  width?: CSSValue;
  height?: CSSValue;
  margin?: CSSValue | Margin;
  padding?: CSSValue | Padding;
  fontSize?: CSSValue;
  gap?: CSSValue;
  borderRadius?: CSSValue;
}

const styles: CSSProperties = {
  width: '100px', // Valid
  height: '50%', // Valid
  // width: 'abc', // Type error!
  // height: '10', // Missing unit
  margin: '10px 20px', // Valid
  padding: '10px 15px 10px 15px', // Valid
};
```

CSSValue expresses a deliberately limited number-plus-unit subset, not all CSS: auto, zero without units, calc and two/three-value padding are outside this example. It also admits values a specific CSS property might reject, such as negative width. The types neither parse complete CSS nor install a stylesheet.

### 3. Type-Safe Route Builder

The route table stores literal colon placeholders, so only declared patterns are accepted and their parameter names can be extracted. The builder encodes each path-segment value; this grammar omits optional, repeated and wildcard parameters, which need matching runtime/type-level rules.

```typescript
// Route definitions
type RoutePatterns = {
  'users': `/users`;
  'user-detail': '/users/:id';
  'user-posts': '/users/:userId/posts';
  'user-post-detail': '/users/:userId/posts/:postId';
  'products': `/products`;
  'product-detail': '/products/:id';
};

// Route params extractor
type SegmentParam<S extends string> = S extends `:${infer Name}` ? Name : never;
type ParamNames<T extends string> =
  T extends `${infer Head}/${infer Rest}`
    ? SegmentParam<Head> | ParamNames<Rest> : SegmentParam<T>;
type ExtractParams<T extends string> = Record<ParamNames<T>, string>;

type UserParams = ExtractParams<'/users/:id'>;
// { id: string }

type PostParams = ExtractParams<'/users/:userId/posts/:postId'>;
// { userId: string; postId: string }

// Type-safe route builder
function buildPath<T extends RoutePatterns[keyof RoutePatterns]>(
  pattern: T,
  params: ExtractParams<T>
): string {
  return pattern.split("/").map(segment => {
    if (!segment.startsWith(":")) return segment;
    const name = segment.slice(1);
    const value = (params as Record<string, unknown>)[name];
    if (!Object.hasOwn(params, name) || typeof value !== "string") {
      throw new Error(`Missing string parameter: ${name}`);
    }
    return encodeURIComponent(value);
  }).join("/");
}

const path1 = buildPath('/users/:id', { id: '42' });
// Result: "/users/42"
const path2 = buildPath('/users/:userId/posts/:postId', {
  userId: 'abc',
  postId: '123',
});
// Result: "/users/abc/posts/123"
```

For /users/:userId/posts/:postId, static parsing visits users, :userId, posts and :postId and collects userId|postId. Runtime building visits the same segments and substitutes only entire colon segments; a value a/b becomes a%2Fb inside one segment. This avoids replacing :id inside a longer :id2 name. Repeated named segments reuse a value. Unknown/optional/wildcard route grammar is excluded; outside data can still violate types, so missing/nonstring values throw.

### 4. CSS Class Name Builder

```typescript
// Utility classes
type Spacing = '0' | '1' | '2' | '4' | '8' | '16' | '32';
type Direction = 't' | 'b' | 'l' | 'r' | 'x' | 'y' | '';
type Breakpoint = '' | 'sm:' | 'md:' | 'lg:' | 'xl:';

// Generate margin/padding classes
type SpacingClass<Prefix extends string> =
  `${Breakpoint}${Prefix}${Direction}-${Spacing}`;

type MarginClass = SpacingClass<'m'>;
// "m-0" | "m-1" | ... | "mt-0" | "mb-8" | "sm:mx-4" | ...

type PaddingClass = SpacingClass<'p'>;
// "p-0" | "p-1" | ... | "pt-16" | "md:px-2" | ...

// Color classes
type Color = 'red' | 'blue' | 'green' | 'gray' | 'indigo';
type Shade = '50' | '100' | '200' | '300' | '400' | '500' | '600' | '700' | '800' | '900';
type ColorClass = `text-${Color}-${Shade}` | `bg-${Color}-${Shade}` | `border-${Color}-${Shade}`;
// "text-red-500" | "bg-blue-200" | "border-green-600" | ...

// Combined utility type
type TailwindClass = SpacingClass<'m'> | SpacingClass<'p'> | ColorClass;

function cn(...classes: TailwindClass[]): string {
  return classes.join(' ');
}

cn('m-4', 'p-2', 'text-red-500'); // Valid
// cn('invalid-class'); // Type error
```

cn joins validated typed arguments; it does not resolve utility-class conflicts or cause Tailwind to generate those classes. The supported tokens here are a custom finite subset, not the framework's complete current grammar.

### 5. String Transformations

The camel-to-kebab helper is intended for lower-camel ASCII names with ordinary letter transitions. Digits and punctuation also satisfy `T extends Uppercase<T>`, and acronym runs need a more nuanced boundary rule; the type does not convert any runtime keys or detect key collisions.

```typescript
// SnakeCase to CamelCase
type SnakeToCamel<S extends string> =
  S extends `${infer T}_${infer U}`
    ? `${T}${Capitalize<SnakeToCamel<U>>}`
    : S;

type CamelCase1 = SnakeToCamel<'user_name'>;
// "userName"
type CamelCase2 = SnakeToCamel<'first_last_name'>;
// "firstName"
type CamelCase3 = SnakeToCamel<'user_profile_data'>;
// "userProfileData"

// CamelCase to KebabCase
type CamelToKebab<S extends string> =
  S extends `${infer T}${infer U}`
    ? T extends Uppercase<T>
      ? `-${Lowercase<T>}${CamelToKebab<U>}`
      : `${T}${CamelToKebab<U>}`
    : S;

type Kebab1 = CamelToKebab<'backgroundColor'>;
// "background-color"
type Kebab2 = CamelToKebab<'fontSize'>;
// "font-size"
type Kebab3 = CamelToKebab<'borderRadius'>;
// "border-radius"

// SnakeCase to KebabCase
type SnakeToKebab<S extends string> =
  S extends `${infer T}_${infer U}`
    ? `${T}-${SnakeToKebab<U>}`
    : S;

type Kebab4 = SnakeToKebab<'user_profile'>;
// "user-profile"

// Type aliases are not first-class generic functions: apply this
// known converter directly to each key rather than writing Converter<K>.
type CamelKeys<T> = {
  [K in keyof T as K extends string ? SnakeToCamel<K> : K]: T[K];
};

interface ApiResponse {
  user_name: string;
  user_email: string;
  created_at: Date;
}

type FrontendResponse = CamelKeys<ApiResponse>;
// {
// userName: string;
// userEmail: string;
// createdAt: Date;
// }
```

### 6. Deep Path Extraction

```typescript
// Type-safe object path access
type PathImpl<T, K extends keyof T> =
  K extends string
    ? T[K] extends Record<string, any>
      ? `${K}.${PathImpl<T[K], keyof T[K]> & string}`
      : K
    : never;

type Path<T> = PathImpl<T, keyof T> & string;

interface NestedConfig {
  database: {
    host: string;
    port: number;
    credentials: {
      user: string;
      password: string;
    };
  };
  cache: {
    ttl: number;
    redis: {
      host: string;
      port: number;
    };
  };
}

type ConfigPaths = Path<NestedConfig>;
// "database.host" | "database.port" | "database.credentials.user"
// | "database.credentials.password" | "cache.ttl" | "cache.redis.host"
// | "cache.redis.port"

// Lookup of one selected path is canonical in Advanced Generics.
```

Leaf paths are generated by visiting each record field, prefixing parent names, then returning only terminal paths. For database.credentials.user, database and credentials extend the prefix and user terminates it. The selected-path value lookup has its canonical definition in [Advanced Generics](../02-generics-and-inference/10.2.2.03-advanced-generics.md). This path generator assumes required finite plain records; arrays, native classes, optional children and cycles need separate rules/depth limits.

### 7. Type-Safe i18n / Localization

```typescript
type Locale = 'en' | 'es' | 'fr' | 'de';

type TranslationKeys = {
  'welcome': `welcome.${Locale}`;
  'goodbye': `goodbye.${Locale}`;
  'error.not_found': `error.not_found.${Locale}`;
  'error.server': `error.server.${Locale}`;
};

type TranslationKey = TranslationKeys[keyof TranslationKeys];
// "welcome.en" | "welcome.es" | ... | "error.server.de"

// Permitted message keys are static; dictionary availability is a runtime concern.
// Parameterized translations
type ParamTranslation<T extends string> =
  T extends `${infer Key}.${Locale}` ? Key : never;

type WelcomeKey = ParamTranslation<'welcome.en'>;
// "welcome"

const dictionary: Partial<Record<TranslationKey, string>> = {
  'welcome.en': 'Welcome, {{name}}!'
};
function getTranslation(key: TranslationKey): string {
  const value = dictionary[key];
  if (value === undefined) throw new Error(`Missing translation: ${key}`);
  return value;
}

function translate(key: TranslationKey, params: Record<string, string> = {}): string {
  const value = getTranslation(key);
  return value.replace(/\{\{([A-Za-z][A-Za-z0-9_]*)\}\}/g, (_match, name: string) => {
    const replacement = params[name];
    if (!Object.hasOwn(params, name) || typeof replacement !== "string") {
      throw new Error(`Missing translation parameter: ${name}`);
    }
    return replacement; // callback result inserts literal $ characters too
  });
}

const greeting = translate('welcome.en', { name: 'Alice' }); // Welcome, Alice!
```

The partial dictionary has only welcome.en, so another permitted TranslationKey throws until its actual message is supplied. The replacement grammar handles all repeated {{name}} tokens and throws for missing string values; a callback inserts $& literally rather than treating it as replacement syntax. The type does not derive message-specific parameter names. This is plain text substitution, not pluralization, rich HTML or locale fallback; send its result through a text-rendering boundary.

### 8. Join and Split Types

`Join` preserves literal output for finite mutable or readonly tuples and widens an open-ended array to `string`. `Split` uses a deliberate simplified policy: the empty input yields an empty tuple and a trailing delimiter contributes no final empty field, so it differs from JavaScript `String.split`; avoid an empty delimiter for this helper.

```typescript
// Join array of strings
type Join<T extends readonly string[], Separator extends string = ','> =
  number extends T['length'] ? string :
  T extends readonly [infer F, ...infer R]
    ? F extends string
      ? R extends readonly string[]
        ? R['length'] extends 0
          ? F
          : `${F}${Separator}${Join<R, Separator>}`
        : never
      : never
    : '';

type Joined1 = Join<['a', 'b', 'c']>;
// "a,b,c"
type Joined2 = Join<['a', 'b', 'c'], '-'>;
// "a-b-c"
type Joined3 = Join<['hello'], '.'>;
// "hello"
type JoinedReadonly = Join<readonly ['users', '42'], '/'>;
// "users/42"
type JoinedArray = Join<string[], '/'>;
// string: the element sequence is not known at compile time

// Split string into tuple
type Split<S extends string, D extends string = ','> =
  string extends S ? string[] :
  S extends '' ? [] :
  S extends `${infer T}${D}${infer U}`
    ? [T, ...Split<U, D>]
    : [S];

type Split1 = Split<'a,b,c'>;
// ["a", "b", "c"]
type Split2 = Split<'hello world', ' '>;
// ["hello", "world"]
type Split3 = Split<'user:42:active', ':'>;
// ["user", "42", "active"]
```

### 9. Object Key Prefixed Types

```typescript
// Add prefix to all keys
type PrefixedKeys<T, Prefix extends string> = {
  [K in keyof T as `${Prefix}${string & Capitalize<K & string>}`]: T[K];
};

interface User {
  name: string;
  email: string;
  age: number;
}

type PrefixedUser = PrefixedKeys<User, 'user'>;
// {
// userName: string;
// userEmail: string;
// userAge: number;
// }

// Add suffix to all keys
type SuffixedKeys<T, Suffix extends string> = {
  [K in keyof T as `${string & K}${Suffix}`]: T[K];
};

type ApiUser = SuffixedKeys<User, '_api'>;
// {
// name_api: string;
// email_api: string;
// age_api: number;
// }

// Remove prefix from keys
type RemovePrefix<T, Prefix extends string> = {
  [K in keyof T as K extends `${Prefix}${infer Rest}`
    ? Uncapitalize<Rest>
    : K
  ]: T[K];
};

type RawUser = RemovePrefix<PrefixedUser, 'user'>;
// Reverts back to: { name: string; email: string; age: number }
```

### 10. Recursive String Utility Types

These helpers define specific grammars: `Trim` recognizes space, newline and tab, not every JavaScript whitespace character; `Repeat` expects a small nonnegative integer literal. A negative or fractional count cannot reach the tuple-length base case, and `number` itself would stop immediately at zero.

```typescript
// Trim whitespace
type TrimLeft<S extends string> =
  S extends `${' ' | '\n' | '\t'}${infer Rest}`
    ? TrimLeft<Rest>
    : S;

type TrimRight<S extends string> =
  S extends `${infer Rest}${' ' | '\n' | '\t'}`
    ? TrimRight<Rest>
    : S;

type Trim<S extends string> = TrimLeft<TrimRight<S>>;

type Trimmed1 = Trim<' hello '>; // "hello"
type Trimmed2 = Trim<'\n\t world \n'>; // "world"

// Repeat string N times (using array accumulator for type-level length tracking)
type Repeat<S extends string, N extends number, Acc extends never[] = []> =
  Acc['length'] extends N ? '' : `${S}${Repeat<S, N, [...Acc, never]>}`;

type Dashes = Repeat<'-', 5>; // "-----"
type Dots = Repeat<'.', 3>; // "..."

// Replace all occurrences
type ReplaceAll<S extends string, From extends string, To extends string> =
  From extends '' ? S :
  S extends `${infer Head}${From}${infer Tail}`
    ? `${Head}${To}${ReplaceAll<Tail, From, To>}`
    : S;

type Replaced1 = ReplaceAll<'a-b-c-d', '-', '_'>;
// "a_b_c_d"
type Replaced2 = ReplaceAll<'user@example.com', '@', '[at]'>;
// "user[at]example.com"
```

## Real-World Use Cases

### A custom field-selection contract

This is an illustrative flag map, not the API shape of a particular ORM. Reuse Path from §6 under its finite-record contract:

```typescript
type SelectFields<T> = { [K in keyof T as K extends string ? K : never]?: boolean };
type DeepSelect<T> = Partial<Record<Path<T>, boolean>>;
type ConfigSelection = DeepSelect<NestedConfig>;
const selection: ConfigSelection = { "database.host": true };
```

Runtime code still needs to validate selected names, authorize fields and translate this custom shape to its actual database adapter.

### API Client Generator

```typescript
// Type-safe API endpoints
type ApiVersion = 'v1' | 'v2';
type ApiResource = 'users' | 'posts' | 'comments' | 'products';
type ApiAction = 'list' | 'get' | 'create' | 'update' | 'delete';

type ApiEndpoint = `/api/${ApiVersion}/${ApiResource}`;
type ApiResourceEndpoint<T extends ApiResource> = `/api/v1/${T}`;
type ApiActionEndpoint<T extends ApiResource, A extends ApiAction> =
  A extends 'list' ? `/api/v1/${T}` :
  A extends 'get' ? `/api/v1/${T}/:id` :
  A extends 'create' ? `/api/v1/${T}` :
  A extends 'update' ? `/api/v1/${T}/:id` :
  A extends 'delete' ? `/api/v1/${T}/:id` :
  never;
```

## Common Mistakes

### 1. Recursive Type Instantiation Limits

A recursive type needs progress and a defined precision limit. The following extracts a prefix from a small ASCII literal, deliberately stopping after Budget characters rather than claiming to transform an arbitrary string exactly:

```typescript
type TakePrefix<S extends string, Budget extends number = 10, Seen extends unknown[] = []> =
  Seen["length"] extends Budget ? "" :
  S extends `${infer First}${infer Rest}`
    ? `${First}${TakePrefix<Rest, Budget, [...Seen, unknown]>}` : "";
type Prefix = TakePrefix<"hello-world", 5>; // "hello"
```

Budget is a small nonnegative integer literal; broad/negative/fractional counts require another contract. Truncating static information is a deliberate behavior, not an equivalent replacement for a full transformation.



### 2. Type Instantiation Explosion

```typescript
// BAD: Generates ALL combinations → Slow compilation
type Colors = 'red' | 'green' | 'blue';
type Sizes = 'sm' | 'md' | 'lg' | 'xl' | '2xl' | '3xl';
type States = 'hover' | 'active' | 'focus' | 'disabled';

// 3 × 6 × 4 = 72 combinations (manageable)
type AllClasses = `${Colors}-${Sizes}-${States}`;

// BAD: 3 × 6 × 4 × 100 (if more unions combined)
// Use sparingly with large unions

// GOOD: Limit union combinations
type ColorSize = `${Colors}-${Sizes}`; // Only 18 combinations
```

### 3. Confusing Conditional Distribution with Interpolation

```typescript
type WrapString<T> = T extends string ? `~${T}~` : T;
type Result = WrapString<'a' | 'b'>; // "~a~" | "~b~"
type Wrapped = `~${'a' | 'b'}~`; // The same result without a conditional
```

The first helper distributes because its checked side is a naked type parameter. The second interpolates each union member directly. Both are valid; tuple wrapping affects conditional distribution but does not stop template literals from expanding interpolated unions.

## Best Practices

- Use finite event unions when names should be a whitelist; `Capitalize<string>` only constrains spelling shape.
- Keep literal route patterns as the source of parameter names and ensure the runtime matcher follows the same grammar.
- Define base cases for recursive helpers, including empty patterns and unsupported numeric counts.
- Pre-generate large sets of strings when cross products become expensive, and measure with `tsc --extendedDiagnostics`.
- Pair key-remapping types with actual runtime conversion when consuming an API response; aliases alone leave snake_case keys untouched.

For dot paths, the extractor in §6 selects leaf paths of the demonstrated record shape. Arrays, optional records and recursive models need additional cases or a depth bound before using it as a general library utility.

## Performance Considerations

Interpolating unions creates a Cartesian product: three colors, six sizes and four states produce 72 combinations before any further transform. The checker can hit complexity or instantiation limits when that product or recursion grows; there is no supported tsconfig option to raise a universal recursion depth.

Do not infer compile times from union size alone. Compiler version, surrounding types, caching and recursion strategy all affect cost; use `--extendedDiagnostics` on the consuming project and simplify the helper or generate declarations when measured work becomes excessive.

## Summary

Template literals construct permitted string patterns; unions multiply alternatives, and infer extracts parts of a matched literal. Define a small grammar and trace its terminal cases. Runtime route substitution, key conversion and translation delivery must implement that same contract rather than assuming a type alias performs the work.

# The `satisfies` Operator

## TL;DR

The `satisfies` operator (TS 4.9+) validates that an expression matches a type **without replacing the expression's inferred type with that constraint**. It's the answer to the long-standing tension between "I want to be sure this object matches the contract" and "I want autocomplete on the specific keys I wrote." Use it whenever you need both: type safety AND the narrow type you actually wrote — with `as const satisfies` when you also need literal *values*.

## First Principles

`satisfies` resolves a real tension: check without widening.

1. **Annotating (`: Config`) widens literals and discards inference**; `satisfies Config` *validates* while keeping the expression's own inferred type — your keys and literal-union members survive, where `: Config` would replace them wholesale with the constraint.
2. **The use case is config objects consumed by key**: validate against the schema *and* keep `"api-1"` as a real key (not an index signature) so downstream `keyof`/lookup stays precise (→ 10.2.1.02's derivation chain, unbroken).

## Why It Matters

Before `satisfies`, you chose between a type annotation (validates, but replaces your inferred type with the constraint) and a type assertion (adopts whatever type you claim, with only a convertibility check). `satisfies` gives you both: validation AND preservation. Senior engineers use it for: configuration objects, route tables, event handlers, and any place where you want to type-check without erasing the shape downstream code depends on.

**Concretely:**

1. **Type validation without type widening** — Verify the shape matches a contract while keeping specific keys literal
2. **Better autocomplete** — your keys survive, so `config.` completes `host`/`port` and `keyof typeof config` is `'host' | 'port'`; the same object annotated `Record<string, X>` completes nothing
3. **Catch typos early** — A misspelled property becomes a compile error, but valid keys still have their specific types
4. **Replace dangerous `as` casts** — `as` only checks convertibility, `satisfies` checks the actual contract
5. **Improve object literal ergonomics** — Especially for unions, `Record<string, X>`, and config-driven code

## Definition

`satisfies` is a TypeScript operator introduced in 4.9 that checks an expression is assignable to a type, but returns the expression's original (narrower) inferred type rather than the constraint type. It sits between type assertions (`as`) and type annotations (`:`) in terms of safety.

```typescript
const config = {
  port: 3000,
  host: 'localhost',
  debug: true,
} satisfies ServerConfig;
// Verifies the object matches ServerConfig while keeping the keys
//   port/host/debug — an annotation of Record<string, X> would erase them
// Mutable properties still widen: config.port is number, not 3000 —
//   write `as const satisfies ServerConfig` when you need the literal
```


## How It Works

### The Problem `satisfies` Solves

```typescript
type Routes = Record<string, { path: string; auth: boolean }>;

// Annotation: your keys widen away to an index signature
const routesAnn: Routes = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true },
};
// routesAnn.home is { path: string; auth: boolean } — but `routesAnn.` completes
//   no keys, and keyof typeof routesAnn is just `string`

// Assertion: adopts Routes wholesale — the same index-signature type the
// annotation gives you, but only a loose convertibility check ran
const routesAs = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true },
} as Routes;
// So typos still go undetected:
// routesAs.admni = ... — silently allowed, the index signature takes any key

// satisfies: validates AND keeps the keys you wrote
const routes = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true },
} satisfies Routes;
// routes.home.path is `string` — Routes declares `path: string`, and a mutable
//   property widens the same way it would without satisfies
// The win is at the top level: keys home/admin survive (keyof typeof routes is
//   'home' | 'admin'), so `routes.admni` is an error — the annotation accepted it
```

### Comparing the Three Approaches

```typescript
type Color = 'red' | 'green' | 'blue';

const obj1: Record<string, Color> = { primary: 'red' };
// obj1.primary is Color — the annotation's type replaces the literal (this
// variant does validate; that is the one thing it has over the assertion)

const obj2 = { primary: 'red' } as Record<string, Color>;
// obj2.primary is Color — the assertion adopts its target type, so the narrow
// literal is gone, and its only gate is a convertibility check (`{} as Need`
// passes even when Need requires properties)

const obj3 = { primary: 'red' } satisfies Record<string, Color>;
// obj3.primary is typed as 'red' AND validated against the type
```

### Common Use Cases

```typescript
// ─── 1. Config validation ─────────────────────────────────────
type FeatureFlags = Record<string, boolean>;

const flags = {
  newCheckout: true,
  darkMode: false,
  betaSearch: true,
} satisfies FeatureFlags;
// Values stay literal here: flags.newCheckout is `true`, not `boolean`

// ─── 2. Discriminated union narrowing ─────────────────────────
type Event =
  | { type: 'click'; x: number; y: number }
  | { type: 'keypress'; key: string }
  | { type: 'resize'; width: number; height: number };

const handler = { type: 'click', x: 10, y: 20 } satisfies Event;
// handler.type is 'click' rather than the whole union — the value is already
//   in the click branch, and a typo'd `type: 'clik'` fails the check
// Annotated (`const handler: Event`) you get the union back and must narrow
//   before treating handler as one branch

// ─── 3. Tuple validation with literal preservation ────────────
type Routes = ['home' | 'about' | 'contact', string];
const r = ['home', '/'] satisfies Routes;
// r[0] is 'home' (not 'home' | 'about' | 'contact')

// ─── 4. Object with optional vs required keys ─────────────────
type ApiResponse = {
  data?: unknown;
  error?: { code: number; message: string };
};

const res = { data: { id: 1 } } satisfies ApiResponse;
// res.data is typed as { id: number } — not unknown
// But TS checks: if you wrote res.erro, that's a typo and an error
```

## Code Examples

### Real-World: Feature Flag System

```typescript
type FlagConfig = {
  key: string;
  defaultValue: boolean;
  description: string;
};

const flags = [
  { key: 'newCheckout', defaultValue: false, description: 'New checkout flow' },
  { key: 'darkMode', defaultValue: true, description: 'Dark mode UI' },
] as const satisfies FlagConfig[];
// `as const` is what keeps `key` literal: without it `key: string` in
//   FlagConfig widens each key to `string` and FlagKey below collapses
type FlagKey = typeof flags[number]['key']; // 'newCheckout' | 'darkMode'

declare function isEnabled(key: FlagKey): boolean;
isEnabled('newCheckout'); // OK
isEnabled('typo'); // Type error: not a FlagKey
```

### Real-World: Server Route Table

```typescript
type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE' | 'PATCH';
type RouteDefinition = {
  method: HttpMethod;
  path: string;
  handler: string; // handler name for reference
};

const routes = {
  getUser: { method: 'GET', path: '/users/:id', handler: 'getUser' },
  createUser: { method: 'POST', path: '/users', handler: 'createUser' },
  deleteUser: { method: 'DELETE', path: '/users/:id', handler: 'deleteUser' },
} satisfies Record<string, RouteDefinition>;

// routes.getUser.method is typed as 'GET' (literal), not HttpMethod
// TS validates every entry matches RouteDefinition
// A typo like `methods` would be caught at compile time
```

### Real-World: Color Palette with Strict Keys

```typescript
type Palette = Record<string, `#${string}`>;

const palette = {
  primary: '#3b82f6',
  secondary: '#10b981',
  danger: '#ef4444',
} satisfies Palette;

// palette.primary keeps the literal '#3b82f6' instead of widening to `string`
//   (a plain const object would widen), and any value that isn't a `#${string}`
//   color fails the check right here
```

## Real-World Use Cases

> *Feature flag tables, server route tables, and color palettes are already worked through in **Code Examples** above.*

What those examples don't show: **i18n catalogs** — check every locale's entries against one schema so a missing or misspelled key fails the build; **schema-library output** — `satisfies` a Zod/Valibot-style validator's inferred object against the interface it claims to produce; **enum-like const objects** — keep `keyof typeof` precise (an index-signature annotation would erase the keys) so a downstream `switch` can be exhaustive.

## Common Mistakes

| Mistake | Fix |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Using `satisfies` when you want to constrain a parameter | Use type annotation `:` for that — `satisfies` doesn't constrain the inferred type |
| Using `as` instead of `satisfies` to "cast" literals | `as` only asks whether the two types are plausibly convertible — `{} as Need` passes even when `Need` requires properties — while `satisfies` runs the full assignability and excess-property check |
| Putting `satisfies` on a value that needs to be assignable elsewhere | `satisfies` is stricter than `as`; if you need flexibility, use `as` (sparingly) |
| Confusing `satisfies T` with `T =` (constraint on generic) | Different operators: `satisfies` is for expressions, `extends`/default is for generics |
| Expecting `satisfies T` to hand you the wider `T` type | It reports the expression's own type, never the constraint — annotate with `: T` when callers need the wider one |
| Using `satisfies` to assert a value is `any` (defeating safety) | Don't. The whole point of `satisfies` is type-level validation |

## Best Practices

1. **Default to `satisfies` for `const` objects** — the contract check plus your own keys/shape is almost always what you want
2. **Use type annotations for function parameters and exports** — a parameter annotation is what callers get checked against (`satisfies` on a default value constrains nothing else), and for exports the annotation *is* the contract: without it, callers compile against your inferred, implementation-shaped type, so a refactor that merely changes inference changes their build too
3. **Use `satisfies` with `Record<string, X>` to validate AND keep literals** — This is the canonical use case
4. **Combine with `as const` when you want maximally narrow types** — `as const` + `satisfies T` gives you both worlds
5. **Don't replace `as` entirely** — `as` is still useful for genuinely necessary widening (e.g., parsed JSON before validation)
6. **Use `satisfies` to check discriminated unions** — Validates the `type` field is a known value while preserving literal

```typescript
// Best-practice combination
const config = {
  host: 'localhost',
  port: 3000,
} as const satisfies ServerConfig;
// Maximally narrow types, validated against the schema
```

## Performance Considerations

| Aspect | Impact |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Compile time | Negligible — `satisfies` is a single type-check pass |
| Runtime | Zero — pure compile-time operator, no JS emitted |
| Editor performance | Slightly slower for very large `satisfies` expressions on `Record<string, X>`, but rarely a problem |
| IDE autocomplete | Improved — narrower types mean more specific completions |

**Caveat:** `satisfies` is not the same as `as const`. `as const` makes everything `readonly` and turns literals into their most specific type; `satisfies` checks against a constraint and reports the expression's own type instead of the constraint — contextually typed by it, so `boolean`/literal-union members stay narrow while plain `string`/`number` properties widen as usual. They compose: the strictest form, `as const satisfies ServerConfig`, is shown under **Best Practices** above.

## Summary

The `satisfies` operator (TS 4.9+) validates an expression against a type while keeping the expression's own inferred type instead of substituting the constraint. It's the right tool when you need both: type safety AND autocomplete on specific keys. Use it for config objects, route tables, enum-like const maps, and any place you previously had to choose between `:` (erases your keys) and `as` (skips the check). Combine with `as const` for the strictest contracts.

## Revision Questions

**Definition**

1. **Q:** What type does `satisfies T` give the expression — `T`, or something else?
   **A:** The expression's own inferred type; `T` is only consulted to verify assignability, so the value is checked without ever being retyped as the constraint.

2. **Q:** Why is `as` the riskier tool when you just want to validate a config literal?
   **A:** `as` only asks whether the two types are plausibly convertible — `{} as Need` compiles even when `Need` requires properties — and it retypes the value as the target; `satisfies` runs the real assignability check and reports the problem at the literal.

**How It Works**

3. **Q:** Annotating `const routes: Record<string, Route>` vs `satisfies Record<string, Route>` — what disappears in the annotated version?
   **A:** The keys: the annotation replaces them with an index signature, so `keyof typeof routes` becomes `string` and key autocomplete dies, while `satisfies` keeps `home`/`admin` and rejects a typo like `routes.admni`.

4. **Q:** With `ServerConfig.port: number`, what is `config.port` after `satisfies ServerConfig`, and how do you get `3000` instead?
   **A:** It is `number` — mutable properties widen exactly as they would with no operator at all; prefix with `as const` (`as const satisfies ServerConfig`) to pin the literal.

**Code Examples**

5. **Q:** Why does the feature-flag example need `as const` before `satisfies FlagConfig[]`?
   **A:** `FlagConfig.key` is declared `string`, so without `as const` each key widens to `string`, `FlagKey` collapses to `string`, and `isEnabled('typo')` stops being an error — `as const` pins the keys so the union `'newCheckout' | 'darkMode'` is what the compiler sees.

6. **Q:** What does the route-table example catch that writing the same object bare does not?
   **A:** A `method` outside the `HttpMethod` union and unknown extras such as a stray `methods` field both become compile errors on the literal, because `satisfies` runs the full assignability plus excess-property check.

**Common Mistakes**

7. **Q:** Callers need the wide contract type, but `satisfies` keeps handing you the narrow one — what is the fix?
   **A:** Annotate with `: T`; `satisfies` deliberately never widens, it only reports what the expression itself infers.

**Best Practices**

8. **Q:** If `satisfies` exists, when should you still reach for `as`?
   **A:** When you genuinely need a wider type than the expression infers — loosening a narrow literal, or typing parsed JSON before validation — accepting `as`'s looser convertibility check in exchange.

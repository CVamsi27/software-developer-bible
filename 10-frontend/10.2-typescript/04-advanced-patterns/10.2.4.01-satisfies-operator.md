# The `satisfies` Operator

## Definition

`satisfies`, introduced in TypeScript 4.9, checks that an expression can be used as a specified type. It keeps the expression's inferred type rather than replacing it with the entire target type. The target can still guide inference, a process called **contextual typing**. For example, it may preserve a literal type or infer a tuple instead of a general array. `satisfies` neither freezes the value nor validates input at runtime.

> **Textbook Definition:** `satisfies` checks that an expression is assignable to a target type while retaining its resulting inferred type rather than replacing it with that target. Contextual typing can still influence the inference.

```typescript
type ServerConfig = { port: number; host: string; debug?: boolean };

const config = {
  port: 3000,
  host: 'localhost',
  debug: true,
} satisfies ServerConfig;
// Verifies the object matches ServerConfig while keeping the keys
//   port/host/debug — an annotation of Record<string, X> would erase them
// Mutable properties still widen: config.port is number, not 3000 —
//   write `as const satisfies ServerConfig` when you need the literal
```


## First Principles

`satisfies` resolves a real tension: check without widening.

1. **An annotation exposes the declared contract.** With `: Config`, downstream code uses the declared `Config` type, subject to control-flow narrowing. If `Config` has a broad index signature, that view can lose the object's particular keys. `satisfies Config` checks compatibility while retaining the expression's own inferred type. The target can still guide inference; it does not guarantee that every literal stays narrow.
2. **Configuration tables often need both checks and precise keys.** Check each entry against the required shape while retaining a key such as `"api-1"`. Downstream `keyof` and property lookups can then use the actual entries rather than an unrestricted string key.

## Why It Matters

Before `satisfies`, you chose between a type annotation (validates, but replaces your inferred type with the constraint) and a type assertion (adopts whatever type you claim, with only a convertibility check). `satisfies` gives you both: validation AND preservation. Senior engineers use it for: configuration objects, route tables, event handlers, and any place where you want to type-check without erasing the shape downstream code depends on.

## How It Works

### The Problem `satisfies` Solves

```typescript
type Routes = Record<string, { path: string; auth: boolean }>;

// Annotation: your keys widen away to an index signature
const routesAnn: Routes = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true },
};
// routesAnn.home is { path: string; auth: boolean } — but `routesAnn.` completes
//   no keys, and keyof typeof routesAnn is just `string`

// Assertion: adopts Routes wholesale — the same index-signature type the
// annotation gives you, but only a loose convertibility check ran
const routesAs = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true },
} as Routes;
// So typos still go undetected:
// routesAs.admni = ... — silently allowed, the index signature takes any key

// satisfies: validates AND keeps the keys you wrote
const routes = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true },
} satisfies Routes;
// routes.home.path is `string` — Routes declares `path: string`, and a mutable
//   property widens the same way it would without satisfies
// The win is at the top level: keys home/admin survive (keyof typeof routes is
//   'home' | 'admin'), so `routes.admni` is an error — the annotation accepted it
```

An open `Record<string, Entry>` checks each value, but accepts any table key, including a misspelled declaration such as `admni`. The later `routes.admni` access fails only because the inferred object contains `home` and `admin`. If the table must contain exactly those known entries, check the literal against `Record<'home' | 'admin', Entry>` instead. A handler name is only a string here; a router still has to resolve and register it.

### Comparing the Three Approaches

```typescript
type Color = 'red' | 'green' | 'blue';

const obj1: Record<string, Color> = { primary: 'red' };
// obj1.primary is Color — the annotation's type replaces the literal (this
// variant does validate; that is the one thing it has over the assertion)

const obj2 = { primary: 'red' } as Record<string, Color>;
// obj2.primary is Color — the assertion adopts its target type, so the narrow
// literal is gone, and its only gate is a convertibility check (`{} as Need`
// passes even when Need requires properties)

const obj3 = { primary: 'red' } satisfies Record<string, Color>;
// obj3.primary is typed as 'red' AND validated against the type
```

### Common Use Cases

```typescript
// ─── 1. Config validation ─────────────────────────────────────
type FeatureFlags = Record<string, boolean>;

const flags = {
  newCheckout: true,
  darkMode: false,
  betaSearch: true,
} satisfies FeatureFlags;
// Values stay literal here: flags.newCheckout is `true`, not `boolean`

// ─── 2. Discriminated union narrowing ─────────────────────────
type UIEventShape =
  | { type: 'click'; x: number; y: number }
  | { type: 'keypress'; key: string }
  | { type: 'resize'; width: number; height: number };

const handler = { type: 'click', x: 10, y: 20 } satisfies UIEventShape;
// handler.type is 'click' rather than the whole union — the value is already
//   in the click branch, and a typo'd `type: 'clik'` fails the check
// A variable annotated `const handler: Event` also narrows to the click
//   branch at this initialization site; satisfies keeps that expression shape
//   as the declared type rather than declaring the full union

// ─── 3. Tuple validation with literal preservation ────────────
type Routes = ['home' | 'about' | 'contact', string];
const r = ['home', '/'] satisfies Routes;
// r[0] is 'home' (not 'home' | 'about' | 'contact')

// ─── 4. Object with optional vs required keys ─────────────────
type ApiResponse = {
  data?: unknown;
  error?: { code: number; message: string };
};

const res = { data: { id: 1 } } satisfies ApiResponse;
// res.data is typed as { id: number } — not unknown
// But TS checks: if you wrote res.erro, that's a typo and an error
```

## Code Examples

### Real-World: Feature Flag System

```typescript
type FlagConfig = {
  key: string;
  defaultValue: boolean;
  description: string;
};

const flags = [
  { key: 'newCheckout', defaultValue: false, description: 'New checkout flow' },
  { key: 'darkMode', defaultValue: true, description: 'Dark mode UI' },
] as const satisfies readonly FlagConfig[];
// `as const` is what keeps `key` literal: without it `key: string` in
//   FlagConfig widens each key to `string` and FlagKey below collapses
type FlagKey = typeof flags[number]['key']; // 'newCheckout' | 'darkMode'

declare function isEnabled(key: FlagKey): boolean;
isEnabled('newCheckout'); // OK
// @ts-expect-error — not a FlagKey
isEnabled('typo');
```

The `declare` signature describes an existing feature-flag service; it is a compiler example, not its implementation. The first call compiles because its key is in the two-entry table; the second fails before any runtime call. Changing a description does not change `FlagKey`, but adding a third literal key expands it.

### Real-World: Server Route Table

```typescript
type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE' | 'PATCH';
type RouteDefinition = {
  method: HttpMethod;
  path: string;
  handler: string; // handler name for reference
};

const routes = {
  getUser: { method: 'GET', path: '/users/:id', handler: 'getUser' },
  createUser: { method: 'POST', path: '/users', handler: 'createUser' },
  deleteUser: { method: 'DELETE', path: '/users/:id', handler: 'deleteUser' },
} satisfies Record<string, RouteDefinition>;

// routes.getUser.method is typed as 'GET' (literal), not HttpMethod
// TS validates every entry matches RouteDefinition
// A typo like `methods` would be caught at compile time
```

### Real-World: Color Palette with a Prefix Constraint

```typescript
type Palette = Record<string, `#${string}`>;

const palette = {
  primary: '#3b82f6',
  secondary: '#10b981',
  danger: '#ef4444',
} satisfies Palette;

// palette.primary keeps the literal '#3b82f6' instead of widening to `string`
//   (a plain const object would widen), and any value that isn't a `#${string}`
//   color fails the check right here
```

`#${string}` means only a leading `#`; `'#not-a-color'` also satisfies it. It is not a hexadecimal or CSS color parser. Use a finite key union for required palette slots and runtime validation when accepting colors from outside the program.

## Real-World Use Cases

> *Feature flag tables, server route tables, and color palettes are already worked through in **Code Examples** above.*

What those examples don't show: **i18n catalogs** — check literal locale entries against a finite set of message keys so a missing or misspelled key fails the build; **schema-library output** — `satisfies` a Zod/Valibot-style validator's inferred object against the interface it claims to produce; **enum-like const objects** — keep `keyof typeof` precise (an index-signature annotation would erase the keys) so a downstream `switch` can be exhaustive.

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Using `satisfies` when you want to constrain a parameter | Use type annotation `:` for that — `satisfies` doesn't constrain the inferred type |
| Using `as` instead of `satisfies` to "cast" literals | `as` only asks whether the two types are plausibly convertible — `{} as Need` passes even when `Need` requires properties — while `satisfies` runs the full assignability and excess-property check |
| Expecting a checked literal to accept future values from the entire contract | Annotate the variable with the wider contract if later assignments need it; a boolean context can retain `true` and reject a later `false` |
| Confusing `satisfies T` with `T =` (constraint on generic) | Different operators: `satisfies` is for expressions, `extends`/default is for generics |
| Expecting `satisfies T` to hand you the wider `T` type | It reports the expression's own type, never the constraint — annotate with `: T` when callers need the wider one |
| Using `satisfies` to assert a value is `any` (defeating safety) | Don't. The whole point of `satisfies` is type-level validation |

## Best Practices

1. **Use `satisfies` when consumers need the particular inferred shape** — use a wider annotation when the value must accept future members or values from that contract
2. **Use type annotations for function parameters and exports** — a parameter annotation is what callers get checked against (`satisfies` on a default value constrains nothing else), and for exports the annotation *is* the contract: without it, callers compile against your inferred, implementation-shaped type, so a refactor that merely changes inference changes their build too
3. **Choose open or finite table keys deliberately** — open records check entry shapes; finite records also check known literal keys
4. **Combine with `as const` when you want maximally narrow types** — `as const` + `satisfies T` gives you both worlds
5. **Keep assertions at justified boundaries** — parse external JSON as `unknown` and validate it; an assertion can connect a proven runtime invariant to a type, but cannot establish that invariant
6. **Use `satisfies` to check discriminated unions** — Validates the `type` field is a known value while preserving literal

```typescript
// Reuse ServerConfig from Definition, or include its declaration in this file.
const config = {
  host: 'localhost',
  port: 3000,
} as const satisfies ServerConfig;
// Maximally narrow types, validated against the schema
```

## Performance Considerations

| Aspect | Impact |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Compile time | Depends on the target and expression — large mapped types or unions can add checking work |
| Runtime | The operator is erased; the object expression still executes and is emitted |
| Editor performance | Measure representative large expressions if checking becomes slow |
| IDE autocomplete | Improved — narrower types mean more specific completions |

**Caveat:** `satisfies` is not the same as `as const`. `as const` gives literal expressions narrow values and readonly object properties/tuple elements; it does not freeze runtime objects or recursively change separately referenced values; `satisfies` checks against a constraint and reports the expression's own type instead of the constraint — contextually typed by it, so `boolean`/literal-union members stay narrow while plain `string`/`number` properties widen as usual. They compose: the strictest form, `as const satisfies ServerConfig`, is shown under **Best Practices** above.

## Summary

`satisfies` checks compatibility while retaining the contextually inferred expression type. Use it when later code needs the entries you actually wrote; use a wider annotation when later assignments or a stable public API need the target contract. `as const` preserves literals and readonly views separately. Neither operation freezes objects or validates runtime input.

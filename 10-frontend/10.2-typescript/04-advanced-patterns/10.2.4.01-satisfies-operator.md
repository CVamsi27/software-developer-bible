# The `satisfies` Operator

A route table needs two things at once: each entry must match the router’s contract, and later code should know which routes were actually declared. A broad annotation checks the contract but can hide those exact keys. TypeScript’s `satisfies` operator is designed for this case.

## Definition

`satisfies` checks that an expression is assignable to a target type while leaving the expression with its contextually inferred type. The target can guide inference, so the operator does not preserve every literal automatically.

> **Textbook Definition:** The `satisfies` operator performs an assignability check against a target type without replacing the resulting type of the expression with that target type. Contextual typing by the target may still affect inference.

## First Principles

A type annotation describes the variable through the declared type. An assertion tells the checker to treat the value as a type you claim. `satisfies` instead checks the expression against a contract and keeps the expression’s useful shape.

```typescript
type RouteName = 'listUsers' | 'createUser';
type Route = { method: 'GET' | 'POST'; path: string };

const routes = {
  listUsers: { method: 'GET', path: '/users' },
  createUser: { method: 'POST', path: '/users' },
} satisfies Record<RouteName, Route>;

routes.listUsers.method; // 'GET'
routes.listUsers.path;   // string
type DeclaredRoute = keyof typeof routes; // 'listUsers' | 'createUser'

// @ts-expect-error — the table has no such key
routes.listUsr;

// @ts-expect-error — a required route is missing
const incomplete = { listUsers: { method: 'GET', path: '/users' } } satisfies Record<RouteName, Route>;
```

The finite key union checks required names and rejects extra names in this object literal. If keys are intentionally open-ended, use `Record<string, Route>`: it checks each value but accepts any key written in the table. A typo in a later property access still fails because inference retains the keys that exist.

An annotation such as `const routes: Record<RouteName, Route> = ...` is useful when the variable must expose the wider contract or accept later updates covered by that contract. `satisfies` is useful when later code should keep the entries and narrower values that the object actually declares.

## Contextual typing still applies

The target type can provide types for callbacks and literal unions. At the same time, ordinary mutable properties can widen: a property declared as `string` or `number` in the target generally remains a string or number, even if its initializer is one literal.

```typescript
type Handlers = {
  created: (id: string) => void;
  deleted: (id: string) => void;
};

const handlers = {
  created(id) { console.log(id.toUpperCase()); }, // id is contextually string
  deleted(id) { console.log(id); },
} satisfies Handlers;

type HandlerName = keyof typeof handlers; // 'created' | 'deleted'
```

Use `as const satisfies Contract` when literal values and readonly properties are part of the desired type. `as const` changes the static view; neither it nor `satisfies` freezes the object at runtime.

## The runtime boundary

`satisfies` is erased during compilation. It does not inspect JSON, validate environment variables, register routes, or prevent a caller from mutating the object. Parse external input as `unknown`, validate it at runtime, then use the validated value. A route table still needs a router that resolves and invokes its handlers.

## Summary

Use `satisfies` to check a value against a contract while keeping its useful inferred shape. Choose finite keys when the set is fixed and an open record when it is not. Use an annotation when callers need the wider declared type, and runtime validation when the value comes from outside the program.

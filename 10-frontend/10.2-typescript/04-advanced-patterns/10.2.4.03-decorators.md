# Decorators

A controller's `@Get` annotation does not receive a request by itself. The decorator records or changes a declaration; a router later reads that information and dispatches the request. A logging decorator behaves differently because its wrapper runs on each call. Follow the phase to understand what an annotation actually does.

```typescript
function logged<This, Args extends unknown[], Result>(
  original: (this: This, ...args: Args) => Result,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>
) {
  return function (this: This, ...args: Args): Result {
    console.log('Calling ' + String(context.name)); // runs per call
    return original.apply(this, args);
  };
}
```

## Definition

A decorator is a function applied to a class or supported class member while the class is being defined. It can replace behavior, arrange instance initialization or record metadata for a separate consumer.

> **Textbook Definition:** A decorator is a metaprogramming function invoked during class definition with a target and context specific to a class or member. TypeScript's newer TC39-proposal-based convention and its legacy experimental convention have distinct signatures and capabilities.

## First Principles

Most decorator behavior happens in one of three phases:

| Phase | Typical work |
| --------------------------------- | --------------------------------------------------- |
| Class definition | Wrap a method, replace a class or register metadata |
| Instance initialization | Create instance-specific state or bind a method |
| Method call or framework dispatch | Run a wrapper or let a consumer read prior metadata |

A decorator's location does not reveal which phase performs its behavior. Trace the decorator, any initializer or metadata it creates, and the code that later consumes it.

## 1. Choose the Compiler Convention First

TypeScript supports two incompatible calling conventions. The newer TC39-proposal-based convention is available when `experimentalDecorators` is off; TypeScript 5.0 added this support. Existing frameworks may require the legacy convention.

| Capability | Newer proposal-based decorators | Legacy decorators |
| -------------------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------- |
| Class, method, getter/setter, field, auto-accessor | Supported with element-specific context | Supported with target/key and, for methods/accessors, a descriptor |
| Instance initialization | `context.addInitializer` | Framework- or decorator-specific |
| Parameter decorators | Not supported | Supported |
| Compiler-emitted design-type metadata | Not supported by `emitDecoratorMetadata` | Optional with `emitDecoratorMetadata` and a runtime metadata library |

Do not mix examples from the two conventions. The newer convention can use metadata objects through `context.metadata` in TypeScript 5.2 and later; the runtime must support `Symbol.metadata` or provide the compatibility setup required by the target. This does not automatically emit TypeScript design types. Legacy `emitDecoratorMetadata` with `reflect-metadata` exposes only limited runtime type information; interfaces and generic arguments are erased.

## 2. A Wrapper Changes Calls

This newer-convention method decorator preserves the original receiver, argument tuple and return type:

```typescript
function logged<This, Args extends unknown[], Result>(
  original: (this: This, ...args: Args) => Result,
  context: ClassMethodDecoratorContext<
    This,
    (this: This, ...args: Args) => Result
  >
) {
  return function (this: This, ...args: Args): Result {
    console.log('Calling ' + String(context.name));
    return original.apply(this, args);
  };
}

class Greeter {
  greeting = 'Hello';

  @logged
  greet(name: string) {
    return this.greeting + ', ' + name;
  }
}

const greeter = new Greeter();
console.log(greeter.greet('Ada')); // Calling greet, then Hello, Ada
```

The wrapper is installed during class definition and runs for each call. It forwards `this` and the arguments, then returns the original result. If the method returns a promise, this synchronous wrapper returns that promise without awaiting it. A wrapper also does not bind a detached method. A newer-convention decorator can use `context.addInitializer` to install a bound method on each instance; that creates one function per instance. Read the final decorated member before binding so the callback retains the full wrapper chain.

Legacy decorators receive different arguments. A legacy method decorator can mutate the supplied descriptor; returning a descriptor is needed only when supplying a replacement. Keep compiler flags and framework expectations aligned before borrowing a legacy decorator.

## Fields and accessors have different write behavior

A field decorator can change initialization but does not intercept every later assignment. An auto-accessor has get/set operations, so its decorator can validate both initialization and subsequent writes.

```typescript
function nonnegative<This>(
  target: ClassAccessorDecoratorTarget<This, number>,
  _context: ClassAccessorDecoratorContext<This, number>
): ClassAccessorDecoratorResult<This, number> {
  function check(value: number): number {
    if (!Number.isFinite(value) || value < 0) {
      throw new RangeError('Expected a finite nonnegative value');
    }
    return value;
  }

  return {
    init: check,
    set(value) {
      target.set.call(this, check(value));
    }
  };
}

class Profile {
  @nonnegative accessor visits = 0;
}

const profile = new Profile();
profile.visits = 2; // accepted
// Assigning -1 throws before the stored value changes.
```

Use an accessor when every write must pass through a check. A decorator still cannot protect values mutated through another reference or validate serialized data.

## 4. Metadata Needs a Consumer

A metadata decorator can record a route, required field or dependency token, but recording is not execution. A router must resolve a controller and invoke its method; a validator must read required fields and inspect actual values; a dependency container must map tokens to registered providers and build constructor arguments. Define inheritance, duplicate registrations and cleanup where they affect the framework.

The newer decorators cannot decorate parameters. Legacy parameter decorators can record an argument index, but a framework must read it and construct the call. Neither metadata mode validates request data automatically.

## 5. Engineering Decisions

Decorator factory expressions evaluate from top to bottom; the resulting decorators apply from the bottom up, so the outer wrapper runs first. A binding initializer that captures an earlier method can bypass an outer wrapper: read the final decorated method before binding.

Use the convention required by the framework, or the newer decorators for standalone code when the target supports them. Prefer a plain function when declaration-site registration offers no benefit. For wrappers, preserve receiver, arguments, result and thrown errors. For metadata, document the consumer and lifecycle. Put retry, caching and dependency-lifetime policies in explicit runtime components where callers can inspect them. A retry count of three means one initial attempt plus three retries, and retrying a write requires an idempotency policy; stateful caches need receiver-specific storage when results depend on instance state.

A decorator adds definition-time work, per-instance initialization or per-call wrapper overhead depending on its design. Measure the relevant phase; don't assume the syntax itself is free.

## Summary

Decorators wrap behavior, arrange initialization or register metadata. Explain which phase acts and who consumes the result. The newer and legacy conventions have different APIs; parameter decorators and compiler-emitted design metadata belong to the legacy mode. A decorator does not replace runtime validation or framework execution.

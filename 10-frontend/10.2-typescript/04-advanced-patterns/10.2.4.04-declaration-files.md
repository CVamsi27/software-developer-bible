# Declaration Files (.d.ts)

## Definition

**Declaration files** (`.d.ts`) are TypeScript files that describe the shape of JavaScript code — types, interfaces, functions, classes, and modules — without containing any implementation. They provide type information for plain JavaScript libraries, ambient modules, global variables, and custom type definitions. Declaration files enable TypeScript to understand and type-check JavaScript code, including third-party libraries that don't ship their own TypeScript types.

> **Textbook Definition:** A declaration file supplies TypeScript descriptions of values, modules and APIs without emitting their implementation. Its declarations must agree with the actual runtime exports and the project's module-resolution rules.


## First Principles

`.d.ts` files are type-world-only exports — the contract surface of JS packages:

1. **Consumers need a description of the code they import.** A package can ship `.d.ts` files and point to them through its `types` field. DefinitelyTyped supplies declarations for JavaScript packages that do not ship their own. These declarations are a published contract and should stay aligned with the package version.
2. **Existing declarations can be extended.** Interface merging combines compatible declarations with the same name. Module augmentation uses that mechanism to add information to an existing library, such as a custom request field. Global declarations affect a wider scope, so unrelated additions can cause naming conflicts.

## Why It Matters

Senior engineers write declaration files for: untyped JS dependencies (creating a `types/foo.d.ts`), extending third-party types (module augmentation for Express `Request`), and publishing typed libraries (`tsc --declaration`). They are also expected to read and understand DefinitelyTyped contribution patterns.

**Concretely:**

1. **Type existing JS libraries** — Add types to libraries that don't ship `.d.ts` files
2. **Publish TypeScript libraries** — Ship compiled JS + declarations for consumers
3. **Ambient declarations** — Describe global variables, APIs, and DOM extensions
4. **Module augmentation** — Extend third-party types with additional properties
5. **Type library boundaries** — Define public API contracts for packages

## How It Works

### Runtime exports and type descriptions follow separate paths

```text
consumer import './greet.js'
  checker → greet.d.ts → accept greet('Ada'), reject greet(123)
  runtime → greet.js   → execute function → "Hello, Ada!"
```

The checker resolves declarations while Node or a bundler resolves JavaScript. A declaration can describe an existing function value, but cannot create it or guarantee its behavior. If the JavaScript returns a number while the declaration promises a string, checking the consumer alone will not discover the mismatch.

Put these three files together in a package with `"type": "module"`; check the consumer with `strict: true`, `module: "NodeNext"` and `moduleResolution: "NodeNext"`. Emit or transpile the consumer before running it with Node:

```javascript
// greet.js — actual runtime implementation
export function greet(name) { return `Hello, ${name}!`; }
```

```typescript
// greet.d.ts — description found alongside greet.js
export declare function greet(name: string): string;
export interface User { id: number; name: string }
```

```typescript
// consumer.ts
import { greet } from './greet.js';
console.log(greet('Ada')); // Hello, Ada!
// @ts-expect-error — compiler-only negative test; do not run this call
if (false) greet(123);
```

The interface has no runtime export. The function signature describes a runtime export without providing its body. Changing the parameter to `number` changes the accepted calls, while changing only the JavaScript requires a separate runtime check to notice whether the contract still holds.

### File scope decides whether declarations add or extend names

A declaration file's **module format** and its declaration **scope** are related but distinct. Under `NodeNext` or `Node16`, `.d.mts` denotes an ES module format, `.d.cts` denotes CommonJS format, and `.d.ts` follows its nearest package's `"type"` for module-format resolution. For ambient declarations, a top-level import or export (including `export {}`) makes the file an external module; without one, a declaration file can contribute script-scope names and declare a runtime-provided module. In an external-module declaration file, use `declare global` to add globals and `declare module 'existing-lib'` to augment an already resolved dependency. Compiler settings such as `moduleDetection` can affect module detection, so verify the effective project configuration when changing these files.

These scope rules come before the purpose labels. A generated library declaration, an asset declaration and a manual declaration all describe contracts; global declarations and module augmentations differ in where those contracts are visible. Keep application imports in a separate file from a script-level ambient module declaration, or its meaning changes.

## Code Examples

### 1. Basic Module Declaration

`some-lib` below is an illustrative package contract, not a declaration for an installed library. Keep `types/some-lib.d.ts` free of top-level imports and exports, include it in the NodeNext compilation, and install JavaScript exporting this API before executing a consumer. Declarations cannot supply that package.

```typescript
// types/some-lib.d.ts — script-scope ambient module declaration
declare module 'some-lib' {
  // Exported functions
  export function parse(input: string): ParsedResult;
  export function format(data: FormatData): string;

  // Exported interfaces
  export interface ParsedResult {
    success: boolean;
    data: Record<string, unknown>;
    errors?: string[];
  }

  export interface FormatData {
    template: string;
    variables: Record<string, unknown>;
  }

  // Exported classes
  export class Parser {
    constructor(options?: ParserOptions);
    parse(input: string): ParsedResult;
    reset(): void;
  }

  export interface ParserOptions {
    strict?: boolean;
    encoding?: 'utf-8' | 'ascii';
  }

  // Default export
  export default function someLib(): void;

  // For relative re-exports, use a top-level external-module .d.ts instead.
}
```

### 2. Global Type Declarations

```typescript
// types/global.d.ts — script-scope globals
// Declarations that apply globally without import

// Global variables
declare var __APP_VERSION__: string;
declare var __DEV_MODE__: boolean;

// Global functions
declare function logEvent(eventName: string, properties?: Record<string, unknown>): void;

// Global interfaces
interface Window {
  gtag?: (command: string, target: string, params?: Record<string, unknown>) => void;
  dataLayer?: Record<string, unknown>[];
  __INITIAL_STATE__?: Record<string, unknown>;
}

// Do not redeclare built-in DOM methods already supplied by lib.dom.d.ts.

// Ambient namespaces
declare namespace MyApp {
  function init(config: AppConfig): void;
  interface AppConfig {
    apiUrl: string;
    debug?: boolean;
  }
}

// Augment existing interfaces
interface Array<T> {
  // Custom method added via polyfill
  groupByApp<K extends string>(keyFn: (item: T) => K): Partial<Record<K, T[]>>;
}
```

The build must actually substitute `__APP_VERSION__`/`__DEV_MODE__`, and a script must install `logEvent`/`MyApp`; declarations alone would allow calls that fail at runtime. `gtag` and `dataLayer` are optional because loading an analytics script may fail or occur later. Guard `window.gtag` before calling it. `groupByApp` is an application extension requiring a runtime implementation; absent groups are missing keys. It is unrelated to standard `Object.groupBy`/`Map.groupBy`.

To add a global from a declaration file that already has imports, wrap it explicitly:

```typescript
// module-globals.d.ts
export {};
declare global {
  interface Window { appBuild?: string }
}
```

### 3. Module Augmentation

```typescript
// types/express-augmentation.d.ts
import 'express-serve-static-core';

// Extend the core interfaces used by Express handler signatures
declare module 'express-serve-static-core' {
  interface Request {
    user?: {
      id: string;
      email: string;
      role: 'admin' | 'user';
    };
    tenant?: {
      id: string;
      name: string;
    };
    requestId?: string;
  }

  interface Response {
    sendSuccess(data: unknown, statusCode?: number): void;
    sendError(message: string, statusCode?: number): void;
  }
}
```

The Express types must already be installed. Middleware must still populate `request.user` and install `sendSuccess`/`sendError` methods: merging an interface neither runs middleware nor adds a response method. Optional request fields force consumers to handle routes where that middleware did not run.

### 4. Asset Module Declarations

These declarations must match the loader actually configured in the bundler. A plain CSS import may be a side effect, while `*.module.css` can export a class-name map; `resolveJsonModule` provides inferred JSON types instead of an untyped catch-all. Environment declarations describe expectations and do not ensure variables exist at startup.

```typescript
// types/assets.d.ts — script-scope asset and environment declarations
// Declare types for non-code imports

// Images
declare module '*.svg' {
  const content: string; // URL string
  export default content;
}

declare module '*.png' {
  const content: string;
  export default content;
}

declare module '*.jpg' {
  const content: string;
  export default content;
}

declare module '*.gif' {
  const content: string;
  export default content;
}

declare module '*.webp' {
  const content: string;
  export default content;
}

// Styles
declare module '*.module.css' {
  const content: Record<string, string>;
  export default content;
}

declare module '*.module.scss' {
  const content: Record<string, string>;
  export default content;
}

declare module '*.module.less' {
  const content: Record<string, string>;
  export default content;
}

// Workers
declare module '*?worker' {
  class BundlerWorker extends Worker {
    constructor();
  }
  export default BundlerWorker;
}

// Markdown
declare module '*.md' {
  const content: string;
  export default content;
}

// Environment variables
declare namespace NodeJS {
  interface ProcessEnv {
    NODE_ENV?: 'development' | 'production' | 'test';
    API_URL?: string;
    AUTH_SECRET?: string;
    DATABASE_URL?: string;
    REDIS_URL?: string;
  }
}
```

The `?worker` suffix is a bundler convention, not native Node or browser module syntax. Each image, CSS or Markdown declaration must match its configured loader; an SVG component loader needs a component type rather than the URL declaration shown. Keep environment fields optional until startup validation constructs a required configuration object. Importing `API_URL` as a declared string cannot establish that the operating system supplied it.

### 5. Class-Type Declarations

This is an illustrative database contract. It describes overloads and members a runtime library would have to implement; it does not connect to a database or decode rows.

```typescript
// types/database.d.ts — script-scope ambient module declaration
declare module 'my-database' {
  // Declare a class with overloaded constructor
  export class Database {
    constructor(config: DatabaseConfig);
    constructor(url: string, options?: ConnectionOptions);

    // Methods with overloads
    query(sql: string): Promise<QueryResult>;
    query(sql: string, params: readonly unknown[]): Promise<QueryResult>;

    // Properties
    readonly connected: boolean;
    readonly config: DatabaseConfig;

    // Static members
    static create(config: DatabaseConfig): Database;
    static fromURL(url: string): Database;

  }

  export interface DatabaseConfig {
    host: string;
    port: number;
    username: string;
    password: string;
    database: string;
    pool?: {
      min?: number;
      max?: number;
    };
  }

  export interface QueryResult {
    rows: unknown[];
    count: number;
    duration: number;
  }

  export interface ConnectionOptions {
    timeout?: number;
    ssl?: boolean;
    poolSize?: number;
  }
}
```

### 6. Generic Type Declarations

```typescript
// types/event-emitter.d.ts — script-scope ambient module declaration
declare module 'typed-emitter' {
  // Generic type-safe event emitter
  export class TypedEmitter<Events extends object> {
    // Method overloads for different event types
    on<K extends keyof Events>(
      event: K,
      listener: (payload: Events[K]) => void
    ): this;

    once<K extends keyof Events>(
      event: K,
      listener: (payload: Events[K]) => void
    ): this;

    emit<K extends keyof Events>(event: K, payload: Events[K]): boolean;

    off<K extends keyof Events>(
      event: K,
      listener: (payload: Events[K]) => void
    ): this;

    // Remove all listeners for an event
    removeAllListeners<K extends keyof Events>(event?: K): this;
  }

  // Utility type to extract event names
  export type EventNames<Events> = keyof Events;
}

```

This fictitious package's methods return `this` for chaining; they describe that package's contract, rather than the unsubscribe API in [Advanced Patterns](10.2.4.05-advanced-patterns.md). The implementation must provide listener identity, one-shot dispatch and removal behavior. Put the consumer in a **separate** file: a top-level import in the declaration file would change the ambient module into an augmentation.

```typescript
// app.ts
import { TypedEmitter } from 'typed-emitter';

interface AppEvents {
  'user:login': { userId: string; timestamp: number };
  'user:logout': { userId: string };
  'error': { message: string; code: number };
}

const emitter = new TypedEmitter<AppEvents>();
emitter.on('user:login', ({ userId, timestamp }) => {
  // Fully typed payload
});
```

### 7. Namespaced Global Library

The following `MiniQuery` example illustrates a script-loaded namespace shape. It is not a replacement for maintained jQuery declarations, which also describe callable selectors and many additional APIs. A runtime script must install `MiniQuery` before use.

```typescript
// types/mini-query.d.ts — illustrative script-loaded API
declare namespace MiniQuery {
  // Utility functions
  function ajax(settings: AjaxSettings): MiniQueryXHR;
  function get(url: string, data?: unknown): MiniQueryXHR;
  function post(url: string, data?: unknown): MiniQueryXHR;

  // Static properties
  const support: SupportMap;
  const mobile: boolean;

  // Interfaces
  interface AjaxSettings {
    url: string;
    method?: string;
    data?: unknown;
    headers?: Record<string, string>;
    success?: (data: unknown) => void;
    error?: (xhr: MiniQueryXHR, status: string) => void;
    timeout?: number;
  }

  interface MiniQueryXHR {
    responseJSON: unknown;
    status: number;
    readyState: number;
    abort(): void;
  }

  interface SupportMap {
    cors: boolean;
    opacity: boolean;
  }
}

// Make available globally
declare var miniQueryAlias: typeof MiniQuery;
```

### 8. Conditional Type Declarations

A declaration can expose conditional and generic relationships only when its implementation maintains them. Here the illustrative `wrap` preserves an existing native promise and otherwise returns a promise of the input. The timer overloads describe delayed calls returning no immediate result; timing, cancellation and errors are still runtime policies. They are not a substitute for the canonical [Debounce](../../10.1-javascript/04-memory-and-data/10.1.4.04-debounce.md) implementation.

```typescript
// types/async-utils.d.ts — script-scope ambient module declaration
declare module 'async-utils' {
  // Conditional return type based on input
  export function wrap<T>(
    input: T
  ): T extends Promise<any> ? T : Promise<T>;

  // This illustrative trailing-only timer API discards the wrapped result.
  export function debounce<F extends (...args: any[]) => any>(
    fn: F,
    wait: number
  ): (...args: Parameters<F>) => void;

  // Promise utility
  export type MaybePromise<T> = T | Promise<T>;

  // Deep transforms need leaf/array rules: use the canonical mapped-type chapter.
}
```

### 9. Publishing Generated Declarations

For one ESM package, use `src/index.ts` exporting `greet`, the configuration below, and the matching `package.json`. Run `tsc -p tsconfig.json`; it produces `dist/index.js` plus `types/index.d.ts` and its map. The source implementation from the earlier trace becomes `export function greet(name: string): string { ... }`.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "rootDir": "src",
    "outDir": "dist",
    "declaration": true,
    "declarationMap": true,
    "declarationDir": "types"
  },
  "include": ["src/**/*.ts"]
}
```

```json
{
  "name": "my-library",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.js",
  "types": "./types/index.d.ts",
  "exports": {
    ".": {
      "types": "./types/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "files": ["dist/", "types/"]
}
```

The `types` condition comes before the runtime condition. Both paths must be present in the packed package. Declaration maps help editor navigation but require the referenced sources to be available if consumers should open them. `emitDeclarationOnly` emits no runnable JS; use it only when another build step supplies the implementation.

This package supports ESM imports. A dual ESM/CommonJS package needs matching runtime branches and declarations identifying the appropriate module format, often `.d.mts` and `.d.cts`; one declaration path is not automatically correct for both. Check a consumer through the packaged entry point and execute the published JavaScript as well as running declaration checks. No publishing command is required for this local verification.

### 10. Triple-Slash Directives

The lines below illustrate alternatives. Use only references needed by that project, with the referenced file/package installed; copying all five into a library adds unrelated Node, Vite and test globals to consumers.

```typescript
/// <reference path="./other-types.d.ts" />
/// <reference types="node" />
/// <reference lib="es2020" />
/// <reference types="vite/client" />
/// <reference types="vitest/globals" />

// These directives tell TypeScript about dependencies:

// path: Reference another .d.ts file
// types: Reference @types/node package
// lib: Reference built-in lib (es2020, dom, etc.)

// vite/client adds bundler globals; vitest/globals adds describe/it/expect.
// Put directives before statements or declarations so they are recognized.
```

## Real-World Use Cases

| Scenario | Declaration Type | Example |
| ---------------------------- | --------------------------- | ---------------------------------------------------- |
| **Publish a library** | Generated `.d.ts` | React, Lodash, Express |
| **Type a JS library** | Manual `.d.ts` in `@types/` | `@types/react`, `@types/lodash` |
| **Custom window properties** | Global augmentation | `window.gtag`, `window.dataLayer` |
| **Add Express Request user** | Module augmentation | `declare module 'express-serve-static-core' { ... }` |
| **Import SVGs/CSS** | Asset declarations | `declare module '*.svg'` |
| **Environment types** | ProcessEnv augmentation | `process.env.API_URL` |
| **Vite/Webpack features** | Ambient declarations | `import.meta.env`, `require.context` |

## Common Mistakes

### 1. Ambient declarations describe a body elsewhere

At the top level, use `declare function parse(input: string): unknown;` rather than writing a bodyless implementation signature. A named ambient module uses `declare module 'some-lib' { ... }`. Its members are already ambient: `export function foo(): void;` is valid, while repeating `export declare function` inside that block is rejected.

### 2. A new import can silently change scope

Do not combine a script-level `declare module 'new-lib'` with consumer imports in one file. Keep the declaration and consumer separate, or write an external-module `.d.ts` for the package's own entry point. For global additions inside a module, use `declare global` as shown earlier.

### 3. Assuming Input Declarations Are Copied to Output

`tsc` reads source `.d.ts` files for checking but does not emit a copy of them. `declaration: true` generates declarations from implementations; packaging must separately include any hand-authored files required by the published entry point. A `types/` directory is an organization choice, not a compiler requirement.

A script-scope declaration file can contribute ambient modules and globals. Keep module format separate from scope: under NodeNext/Node16, `.d.mts`, `.d.cts` and package `"type"` determine ESM/CJS format, while imports, exports and the effective `moduleDetection` setting determine whether declarations are script-scoped or module-scoped. In a module-scoped file, use `declare global { ... }` for globals and `declare module 'existing-lib'` only to augment an existing dependency.

### 4. More precise does not mean more truthful

Replacing `process(data: any): any` with `process<T>(data: T): T` promises identity-shaped output. If the real function serializes its input, the correct contract is `process(data: unknown): string`. The runtime API determines the declaration; a generic should express an actual input/output relationship rather than hide uncertainty. Unknown JSON, database rows and callback payloads need decoding where their shape is not guaranteed.

## Best Practices

1. **Use bundled declarations when available**, otherwise check maintained `@types/` packages before writing your own
2. **Generate declarations automatically** — Use `declaration: true` in tsconfig
3. **Ship declarations with packages** — Set `"types"` in package.json
4. **Include manual declarations in the compilation and package** — Directory placement alone does neither
5. **Use triple-slash references sparingly** — Prefer ordinary imports or the appropriate `types`/`lib` configuration; `paths` maps resolution and does not load globals
6. **Use `declare` to introduce ambient declarations where needed** — Members already inside a `declare module` block are ambient; do not repeat `declare` on them
7. **Choose aliases or interfaces for the intended contract** — interfaces allow deliberate merging; unions and conditional types require aliases
8. **Document public API** — JSDoc comments carry through to IDE intellisense
9. **Test declarations and runtime exports together** — check a consumer, inspect the packed entry paths and execute matching JavaScript

## Summary

- `.d.ts` files describe JavaScript types without implementation — enabling type checking for plain JS libraries
- Use `declare module 'name'` for module declarations, `declare var/func` for globals
- Module augmentation with `declare module 'existing-lib' { interface X { ... } }` extends existing types
- Generate declarations automatically with `declaration: true` in tsconfig for publishing
- Include manual declarations in checking and published packages; generated output does not copy them automatically

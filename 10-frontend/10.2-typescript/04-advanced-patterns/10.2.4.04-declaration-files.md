# Declaration Files (.d.ts)

A TypeScript consumer can compile against a function that does not exist at runtime, or that returns a different value than promised. Declarations expose a static contract; they do not implement or verify it. Follow both paths when typing a JavaScript package.

```typescript
// greet.d.ts — contract for a JavaScript implementation
export declare function greet(name: string): string;

// consumer.ts
import { greet } from './greet.js';
console.log(greet('Ada')); // Hello, Ada!
// greet(42); // rejected by the declaration — but only the runtime proves the result
```

## Definition

A declaration file describes existing JavaScript values, modules or APIs without providing their implementation. TypeScript uses it during checking, while the runtime loads the corresponding JavaScript.

> **Textbook Definition:** A `.d.ts` file contributes ambient module, global or package API contracts to a TypeScript program without emitting runtime implementations. Its declarations must match runtime exports and module-resolution rules.

## First Principles

```text
TypeScript checker → declaration file → accepted calls and inferred types
JavaScript runtime → implementation     → actual values and side effects
```

A passing consumer proves only that its calls match the declaration. A false signature can make incorrect code compile, so generate declarations from the implementation when possible and compare manual declarations with real behavior.

## Describe existing JavaScript

For a JavaScript module exporting `greet`, a neighboring declaration describes the function and its type-only interface:

```javascript
// greet.js — runtime implementation
export function greet(name) {
  return 'Hello, ' + name + '!';
}
```

```typescript
// greet.d.ts — contract for that implementation
export declare function greet(name: string): string;
export interface User {
  id: number;
  name: string;
}
```

```typescript
// consumer.ts
import { greet } from './greet.js';

console.log(greet('Ada')); // Hello, Ada!

// @ts-expect-error — the declaration rejects this call
greet(42);
```

The interface is erased because it has no runtime value. The function signature supplies no body. Execute the JavaScript too; type checking cannot prove the result is really a string.

## Scope determines whether a declaration adds or extends names

File scope and module format answer different questions.

- A `.d.ts` file with no top-level import or export can declare an ambient module supplied by JavaScript: `declare module 'legacy-parser' { ... }`.
- A file with a top-level import or export is an external module. A `declare module 'existing-package'` block there augments a module that TypeScript already resolves; it does not create a declaration for a new package.
- In an external module, `declare global { ... }` adds global types. Use this for runtime-provided global values such as `window.analytics`.
- Under Node16/NodeNext resolution, `.d.mts` describes ESM format, `.d.cts` describes CommonJS format, and `.d.ts` follows the nearest package's `type` field for format resolution. Check the compiler and package configuration before changing a declaration extension.

A top-level import changes a script declaration file into a module. Keep an ambient declaration for a new dependency separate from application code that imports it.

## 1. Augment a Dependency or Describe a Bundler Asset

Module augmentation extends an existing package surface. Put it in a module-scoped declaration file and target the module that actually declares the interface:

```typescript
import 'express-serve-static-core';

declare module 'express-serve-static-core' {
  interface Request {
    user?: { id: string; roles: readonly string[] };
  }
}
```

This changes only TypeScript's view. Middleware still has to authenticate the request and assign `request.user` before later handlers read it.

An asset declaration must match the bundler's runtime export:

```typescript
// Use only if this bundler returns an asset URL for SVG imports.
declare module '*.svg' {
  const url: string;
  export default url;
}
```

A loader that returns a React component needs a different declaration. Neither declaration configures the loader or makes an absent file loadable. Environment declarations likewise describe values that deployment must actually provide. To add a browser global from a module-scoped .d.ts, use `declare global` around an interface such as `Window`; that does not create the global value.

## 2. Publish Declarations with the Implementation

Generate declarations from TypeScript source with `declaration: true` and publish them at the paths named by package entry points. For an ESM package, an export can pair its contract with its implementation:

```json
{
  "type": "module",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  }
}
```

Both paths must be present in the packed artifact. A dual ESM/CommonJS package needs matching runtime and declaration branches; Node-aware projects often use `.d.mts` and `.d.cts`. Manual source declarations are compiler inputs, and declaration emit does not automatically package every hand-authored file.

Test an installed or packed consumer through the public entry point, then execute the JavaScript. This catches wrong export paths, omitted declarations and contracts that do not match the implementation. Directory placement or a `paths` alias alone does not put declarations in the package.

## 3. Keep Directives and Precision Deliberate

Triple-slash directives such as `/// <reference types="node" />` tell the compiler to include a declaration dependency. Put them at the beginning of the file and use them only when the project needs that dependency; ordinary imports or tsconfig `types`/`lib` settings are usually easier to maintain.

A declaration should express a real relationship. `process<T>(input: T): T` promises that the function returns the input type; it is false if the implementation serializes the value to text. Prefer `unknown` over `any` at unvalidated boundaries, then describe the checked result.

## Summary

Declaration files teach the checker how existing JavaScript can be used. Keep declaration scope, module format and package paths aligned with the runtime; treat a declaration as a promise that must be checked against actual exports and behavior.

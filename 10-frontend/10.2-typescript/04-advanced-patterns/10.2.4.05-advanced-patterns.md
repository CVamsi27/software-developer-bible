# TypeScript Advanced Patterns — Decorators, Middleware, Advanced Generics

## Definition

**Advanced TypeScript patterns** combine the features taught in the preceding chapters. Decorators attach behavior or metadata to classes and supported members; legacy decorators also support parameters. Conditional types (`T extends U ? X : Y`) choose a type after a check. Mapped types (`[P in keyof T]`) build properties from existing keys. Template literal types work with string types. Branded types add type-only markers that distinguish otherwise identical values. This chapter shows how to combine those features.

> **Textbook Definition:** Advanced TypeScript patterns compose type parameters, conditional branches, mapped properties and string-type transformations into derived API contracts. Brands distinguish otherwise compatible representations, while decorators add runtime behavior or metadata; static contracts still require runtime validation at external boundaries.

## First Principles

The advanced patterns are compositions of the primitives — none are new machinery:

1. **Combine features to express one API relationship.** A builder returning `this` can keep the caller's specific class type. A switch can use `never` to reject unhandled union members. Declaration merging extends an existing interface, and recursive conditional types transform nested shapes. These patterns follow from the generics and type transformations taught earlier.
2. **Choose complexity for a concrete benefit.** A complicated type should reject a meaningful invalid call or improve inference for valid calls. Readers also have to understand its errors and maintain it, so use the simplest relationship that protects the API.

## Why It Matters

Real codebases don't use these patterns one at a time — `TypedEventEmitter` needs mapped+conditional+generics together, NestJS needs decorators+reflection together, API layers need branded IDs + discriminated unions together. The interview signal is *composition*: can you glue three primitives into one ergonomic, type-safe API — and do you know when not to?

## Class Decorators

> See [Decorators — How It Works](10.2.4.03-decorators.md#how-it-works) for both calling conventions and the metadata registration/consumer split. Framework route decorators compose that registration with a router which dispatches to the saved method.

## Parameter Decorators

Legacy parameter decorators record an argument index; the framework reads the metadata at request time to provide a current user or body. Parameter decorators are unavailable in the standard ECMAScript decorator API, and metadata alone does not populate the argument. The generic composition lesson is to pair the metadata contract with a typed consumer, rather than assuming an annotation performs injection.

## Advanced Generics

### Couple an event name to its payload, then define dispatch

A producer publishes a named event; listeners subscribe to that same name. The map below is the shared static contract. Indexing it with `'appointment:created'` selects exactly the payload for that event. A generic listener method carries that relationship into its callback; dispatch also needs to keep the name and payload paired when the caller has a union of event names.

```typescript
type EventMap = {
  'appointment:created': { appointmentId: string; clinicId: string };
  'appointment:cancelled': { appointmentId: string; reason: string };
  'user:login': { userId: string; timestamp: Date };
};
// A union of complete [name, payload] pairs, not independently unioned arguments.
type EventArgs<Events extends object> = {
  [K in keyof Events]: [event: K, payload: Events[K]]
}[keyof Events];

class TypedEventEmitter<Events extends object> {
  private listeners = new Map<keyof Events, Set<(payload: unknown) => void>>();

  on<K extends keyof Events>(event: K, listener: (data: Events[K]) => void): () => void {
    // Erase the payload type only inside storage. Registration fixes this key's
    // payload, and emit admits only pairs from the same Events contract.
    const entry = (payload: unknown) => listener(payload as Events[K]);
    let group = this.listeners.get(event);
    if (!group) { group = new Set(); this.listeners.set(event, group); }
    group.add(entry);
    return () => {
      group.delete(entry);
      if (group.size === 0 && this.listeners.get(event) === group) {
        this.listeners.delete(event);
      }
    };
  }

  emit(...[event, payload]: EventArgs<Events>): void {
    const group = this.listeners.get(event);
    if (!group) return;
    // Snapshot: subscription changes take effect on the next emit.
    for (const listener of [...group]) listener(payload);
  }
}

const emitter = new TypedEventEmitter<EventMap>();
const unsubscribe = emitter.on('appointment:created', data => {
  console.log(data.appointmentId); // Known created payload, no cast in the caller.
});
emitter.emit('appointment:created', { appointmentId: 'a1', clinicId: 'c1' }); // a1
stop();
emitter.emit('appointment:created', { appointmentId: 'a2', clinicId: 'c1' }); // No log.
// @ts-expect-error — this is the cancelled payload, not the created payload
if (false) emitter.emit('appointment:created', { appointmentId: 'a3', reason: 'conflict' });
```

Trace `on`: it derives the callback type from the event key, stores a wrapper under that key, and returns a disposer for that particular registration. Trace `emit`: the paired tuple contract checks the arguments, the runtime map selects the group, and its copied listener list receives the payload. `stop` removes its entry and an empty group; repeated cleanup is harmless. Two registrations of the same original function are separate entries with separate disposers.

The tuple union prevents an uncorrelated union event from accepting an arbitrary union payload. Runtime code still has only keys and values: untrusted messages or `any` can bypass the static contract, so validate them before dispatch. Storage's one assertion is justified by the registration/dispatch invariant, rather than validating bytes by casting.

This bus is synchronous. Listeners run in registration order; a thrown error propagates and stops the remaining calls. A returned promise is not awaited, so use synchronous listeners or define a separate async dispatch and error policy. Removing a listener during dispatch affects the next emit; the current snapshot still contains it. Recursive emits take their own snapshot immediately and can recurse without bound. Owners must keep and call disposers to release captured state.

## Conditional Types

Use a conditional type when the input actually determines a result. `Awaited<ReturnType<typeof getUser>>` derives an async result from an existing function; it does not manufacture a typed result from response JSON. An API selecting `'user'` versus `'appointment'` needs corresponding runtime branches and validators, rather than a declaration which merely promises them. [Infer](../02-generics-and-inference/10.2.2.02-infer.md) owns capture rules and [Conditional Types](../03-type-transformations/10.2.3.02-conditional-types.md) owns distribution and whole-union checks.

For this emitter, the important composition is a mapped type followed by indexed access: `EventArgs` builds one pair per key, then `[keyof Events]` selects their union. A broad `[keyof Events, Events[keyof Events]]` would lose that correlation.

## Mapped Types

[Mapped Types](../03-type-transformations/10.2.3.03-mapped-types.md) owns deep transforms and key selection. A transform must specify its domain: plain records, arrays/tuples and leaves such as Date or functions need different rules. A test on `T[P] extends object` can stop at an optional object's `undefined` union. A `PickByType<Appointment, string>` which requires the entire field type to extend string omits `notes?: string`; an alternate rule which removes undefined deliberately includes it. Choose the rule before combining it with an API update type.

Changing only a type does not produce a patch handler. The runtime update path must select allowed keys, preserve fields when omitted and decide what an explicit undefined means; [Utility Types](../03-type-transformations/10.2.3.01-utility-types.md) traces that operation.

## Template Literal Types

[Template Literal Types](../03-type-transformations/10.2.3.04-template-literal-types.md) owns the whole-segment route grammar and encoded route builder. For `/appointments/:clinicId/patients/:patientId`, the static extractor derives two required names, while the builder reads and encodes each actual value. An optional segment or catch-all path needs both a new type rule and a matching runtime parser.

For event names, a template union such as `${'appointment' | 'patient'}.${'created' | 'updated'}` creates six strings, but does not register listeners or assign payloads. Use an event map and real dispatcher when events carry data; an empty `onEvent` function would only demonstrate parameter checking.

## Branded Types

> Use the constructors and same-currency inference checks in [Branded Types — Code Examples](10.2.4.02-branded-types.md#code-examples).

Composition matters at the API boundary: accept branded IDs, validate external values before creating them, and carry the brand through response types. A plain assertion can forge a brand, so the type proves that callers followed the construction convention, rather than proving runtime data independently.

## Utility Type Combinations

A stored discriminant lets the runtime select a response branch, while a generic carries the successful payload shape. This independent file uses a local fixture so every value and output is defined:

```typescript
type SuccessResponse<T> = { success: true; data: T; timestamp: Date };
type ErrorResponse = {
  success: false;
  error: { type: string; title: string; status: number; detail: string };
};
type ApiResponse<T> = SuccessResponse<T> | ErrorResponse;
function isSuccessResponse<T>(response: ApiResponse<T>): response is SuccessResponse<T> {
  return response.success === true;
}
type User = { id: string; name: string };
const response: ApiResponse<User> = {
  success: true, data: { id: 'u1', name: 'Ada' }, timestamp: new Date(0)
};
if (isSuccessResponse(response)) console.log(response.data.name); // Ada
```

The guard checks the stored boolean and narrows an already valid union. It is not a decoder for unknown JSON. A server must produce the response shape, and a network decoder must check each field before constructing `ApiResponse<User>`. Changing the response fixture to the failure branch makes `data` inaccessible and requires inspecting `error.detail`; changing `User` changes the successful payload contract. JSON encodes Date as text, so a wire type should use a validated timestamp string or a decoder which constructs Date rather than assuming the parsed object contains it.

## Real-World Use Cases

- **NestJS controllers/services** — decorators register information; the framework container resolves providers, lifetimes and tokens, while a router reads route metadata and supplies request arguments.
- **Typed event buses** — the `TypedEventEmitter` pattern above can connect domain producers and consumers; the `EventMap` is the single source of truth for producers and consumers.
- **API layer typing** — branded IDs + `SuccessResponse<T> | ErrorResponse` discriminated union + type guard: one possible decoded client response shape (→ 20.3.3.02).
- **Form/route parsing** — a route extractor derives names and a runtime parser or builder must honor the same grammar; the same trick types feature flags and query strings.

## Common Mistakes

1. **Type-level heroics over runtime validation** — a `DeepPartial` proves nothing about bytes arriving over the wire; decode at the boundary with runtime validation (for example, [Zod](../../10.5-form-handling/10.5.02-zod.md)), then use the parsed value and its inferred type internally.
2. **Brands without constructors** — `id as UserId` everywhere means the brand proves nothing; create branded values only through functions that own the invariant.
3. **Decorators without `experimentalDecorators`/`emitDecoratorMetadata` alignment** — the tsconfig and the framework must agree (legacy vs ES decorators, → 10.2.4.03); a mismatch can cause signature errors or incorrect runtime calls.
4. **Conditional-type explosion** — nested conditionals over unions grow combinatorially; distribute only when needed (`[T] extends [U]` to disable distribution) or the error messages become unreadable.
5. **Open-ended event keys** — annotate a concrete event map instead of passing `any` as the map type. `Record<string, unknown>` can reject interfaces lacking a string index signature; a self-keyed constraint or an `object` constraint avoids requiring one.

## Best Practices

- **Keep only complexity which protects a concrete call** — test accepted inputs, rejected inputs and the matching runtime operation.
- **Name the type, export the factory** — `createUserId` owns the invariant; callers never see the raw `as`.
- **Test types, not just code** — `expectTypeOf`/`tsd` assertions keep the composed types honest across refactors.
- **Identify the decorator phase** — metadata registration needs a consumer; wrappers intentionally add invocation behavior.

## Summary

1. **Decorators register or wrap declarations** — a framework supplies DI and routing consumers
2. **Parameter decorators feed metadata** — the mechanism behind constructor injection
3. **Composed types preserve relationships** — the event pair union connects one name with its own payload
4. **Branded types separate domain values for checked callers** — `type UserId = string & { __brand: 'UserId' }`
5. **Know when to stop** — unreadable type-level code fails review; runtime validation at boundaries beats heroics in the type system

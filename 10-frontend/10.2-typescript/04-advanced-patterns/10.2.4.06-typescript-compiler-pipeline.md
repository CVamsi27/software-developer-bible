# TypeScript Compiler Pipeline

An editor may underline a file that `tsc` never checks, or the build may emit JavaScript while reporting a type error. To diagnose either result, follow the whole program from its configured roots through resolution, checking, and output.

## Definition

The TypeScript compiler is a build-time program analyzer that resolves source files, checks declarations and expressions against types, and optionally emits JavaScript, declaration files, and source maps.

> **Textbook Definition:** A compiler pipeline transforms source programs through representations and analyses into diagnostics and, when configured, executable or descriptive output. TypeScript parses and resolves source files into a program, binds declarations, checks types, and emits configured artifacts.

## First Principles

`tsc` does not type-check an isolated filename by guessing what the rest of the application means. It builds a **program**: the root files, their resolved dependencies, and the compiler options that govern the analysis and output.

```text
tsconfig + root files
        │
        ├─ read and parse source files; discover imports and references
        ├─ resolve dependencies, then read and parse those files too
        ▼
Program: source graph + options
        │
        ├─ bind declarations → symbols and scopes
        ├─ check relationships → types and diagnostics
        └─ transform and emit → JavaScript, declarations, source maps (as configured)
```

Parsing and dependency resolution work together as the graph grows; parsing is not a separate step that starts only after every import has resolved. A syntax tree records what was written. A **symbol** connects a declaration to the names that refer to it. The checker uses symbols and types to test whether operations are valid across the program. The emitter transforms supported syntax and writes requested artifacts. A diagnostic in one stage does not automatically suppress output.

This diagram shows logical dependencies, not a promise that every file is processed serially on one thread. **Current release boundary (14 October 2026):** TypeScript 7.0 is the stable native Go implementation of the compiler; TypeScript 7.1 is in beta. The native implementation preserves the language's checking intent while changing compiler internals.

## Follow one import to its output

Suppose `app.ts` imports `parse` from `./parse.js`. TypeScript first determines the compilation roots and options from the selected project. Reading and parsing `app.ts` exposes that import. The module resolver interprets its specifier according to `moduleResolution`, file extensions, package exports, and the intended host model, then the compiler reads the resolved dependency. In Node-oriented modes it can resolve a `.js` specifier to the corresponding TypeScript source for checking; the emitted import must still match the runtime's package and file layout.

The binder records declarations and scopes in the source trees. The checker follows the import to determine the exported function's type and reports a diagnostic if the caller violates it. The emitter may then write JavaScript and declarations according to `target`, `module`, and declaration options.

Three consequences matter in production:

1. **Type checking is not runtime validation.** Interfaces, aliases, generic parameters, and most annotations are erased. Parse and validate JSON, HTTP input, database rows, and other external values at runtime.
2. **A green type check does not prove a module will load.** The runtime or bundler resolves and loads the emitted path. Keep TypeScript's resolver settings aligned with that host, then test the built artifact using the same package layout used in production.
3. **Diagnostics and output have separate controls.** `noEmit` suppresses output; `noEmitOnError` prevents output when errors exist. Without that policy, a compiler can report errors and still write JavaScript. A build pipeline must decide whether diagnostics fail the release.

## Build once, update a program, and serve an editor

Large repositories add two workflows around the core pipeline. **Project references** split a repository into dependent projects; `tsc --build` orders those dependencies and can reuse incremental state such as `.tsbuildinfo`. That state accelerates a later build; it is not a substitute for clean CI builds or published package outputs. Configure project boundaries around actual build and API boundaries, not just folder names.

The **language service** supports editor requests such as diagnostics, navigation, and completions against changing files. It can answer targeted questions without performing a fresh command-line build after every keystroke. Therefore an editor's current diagnostics and a clean production build are related evidence, not interchangeable gates.

When a build surprises you, inspect the inputs before changing types:

```bash
npx tsc -p tsconfig.json --explainFiles
npx tsc -p tsconfig.json --traceResolution
npx tsc --build tsconfig.json --verbose
```

The first command explains why files belong to the program, the second traces import resolution, and the third reports project-reference build order. If a package works in the editor but not at runtime, compare the selected config, resolved source, emitted path, and actual runtime exports.

The compiler's phase model is useful for diagnosis, but compiler internals and programmatic APIs can evolve between TypeScript releases. Depend on documented CLI options and the Compiler API version used by your tooling; do not treat internal node or checker representations as a stable plugin contract.

In the TypeScript 6-and-earlier Compiler API, a `Program` represents the source graph and options; a `CompilerHost` supplies file access, source files, resolution hooks, and output writes. Tools can provide a host for virtual files or a controlled filesystem. TypeScript 7.0 does not ship that JavaScript API; a tool that embeds it needs the compatible TypeScript 6 package or an integration built for the new API. Pin that tooling separately from the command-line compiler.

## Summary

TypeScript reads, parses, and resolves files to build a program, then binds declarations, checks types, and optionally emits output. Diagnostics, output, runtime loading, editor services, and versioned compiler APIs are distinct boundaries. Verify the exact project and artifact used in deployment, and validate external data after types have been erased.

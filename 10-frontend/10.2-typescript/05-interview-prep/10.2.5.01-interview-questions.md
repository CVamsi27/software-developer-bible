# TypeScript Interview Questions

## Definition

Use this bank after the learning chapters and their revision companions. For each answer, predict what the checker accepts, trace the corresponding runtime operation, and change one condition to find the contract's limit. The grouped questions preserve distinct interview drills; the linked chapters own complete mechanisms and implementations.

## First Principles

A type describes a relationship the checker can enforce; the runtime implementation must maintain it. When solving a drill, identify which argument determines another type, where control flow narrows it, and whether external input has actually been validated. A passing assertion or declaration is not evidence that the JavaScript fulfills its promise.

## Practice Flow

Start with shapes and narrowing, then derive generic results and transforms. In the senior design questions, describe ownership, cleanup and failures as well as accepted calls. Independent code blocks use TypeScript 5.4+ with `strict: true` unless they explicitly reuse another answer. React examples are `.tsx` files with installed React types; network and framework sketches identify missing integrations.

## Beginner Questions (10)

### 1. What is TypeScript?

**Answer**: TypeScript adds a static type system and syntax to JavaScript. The compiler erases type-only syntax and may transform JavaScript features for the configured target; types do not add runtime validation.

```javascript
// JavaScript
function add(a, b) { return a + b; }
```

```typescript
// TypeScript
function add(a: number, b: number): number {
  return a + b;
}

```

### 2. What are the benefits of using TypeScript?

**Answer**:

- **Type safety**: Catch errors at compile time
- **Better IDE support**: Autocomplete, refactoring, navigation
- **Self-documenting code**: Types serve as documentation
- **Easier refactoring**: TypeScript catches breaking changes
- **Shared contracts**: producers and consumers can derive their types from the same definition

These benefits depend on checked code paths: `any`, unchecked casts and external data can bypass them. TypeScript does not replace tests of runtime behavior.

### 3. What is the difference between `any` and `unknown`?

**Answer**:

- `any`: Disables type checking, allows any operation
- `unknown`: Type-safe alternative to `any`, requires type checking before use

```typescript
// any - unsafe
let unsafeValue: any = "hello";
unsafeValue.toUpperCase(); // OK
// unsafeValue.foo.bar.baz; // Type-checks, but throws if executed

// unknown - safe
let value: unknown = "hello";
// @ts-expect-error — inspect or narrow unknown before reading string methods
value.toUpperCase();
if (typeof value === "string") {
  value.toUpperCase(); // OK after type check
}

```

### 4. What are type aliases and interfaces?

**Answer**:

- **Type alias (`type`)**: Creates a name for any type (primitives, unions, intersections)
- **Interface**: Defines the shape of objects, supports declaration merging

```typescript
// Type alias
type ID = string | number;
type User = { name: string; age: number };

// Interface
interface UserInterface {
  name: string;
  age: number;
}

```

### 5. What is structural typing?

**Answer**: TypeScript uses structural typing, meaning types are compatible based on their structure, not their explicit declarations.

```typescript
interface Point {
  x: number;
  y: number;
}

interface Coordinate {
  x: number;
  y: number;
}

const point: Point = { x: 1, y: 2 };
const coord: Coordinate = point; // OK - same structure

```

### 6. What are generics?

**Answer**: Generics allow you to write reusable, type-safe code that works with multiple types while preserving type information.

```typescript
function identity<T>(value: T): T {
  return value;
}

const str = identity("hello"); // T is the literal "hello"
const num = identity(42); // T is the literal 42

```

### 7. What are utility types?

**Answer**: Utility types derive a new type from an existing one. `Partial<User>` makes the source properties optional, so their types remain aligned with `User`. `Readonly` blocks typed writes to the properties it transforms; it does not prevent mutation through other references or nested values. `Pick` exposes selected fields, while `Omit` exposes everything except the excluded fields and therefore also admits newly added fields. None of them changes a runtime object.

```typescript
interface User {
  id: string;
  name: string;
  email: string;
}

type PartialUser = Partial<User>; // All properties optional
type ReadonlyUser = Readonly<User>; // All properties readonly
type UserName = Pick<User, "name">; // { name: string }

```

**Trade-off**: derived types stay aligned with their source, but long chains can hide the resulting shape and make diagnostics harder to read. Extract a named intermediate when it makes the contract easier to follow.

### 8. What is type narrowing?

**Answer**: The process of refining a broader type into a more specific type through control flow analysis.

```typescript
function process(value: string | number) {
  if (typeof value === "string") {
    return value.toUpperCase(); // string
  } else {
    return value.toFixed(2); // number
  }
}

```

### 9. What are discriminated unions?

**Answer**: A union of types with a common discriminant property, enabling type-safe pattern matching.

```typescript
type Shape =

  | { kind: "circle"; radius: number }
  | { kind: "rectangle"; width: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
  }
}

```

### 10. What is the `never` type?

**Answer**: A type that represents values that never occur. Used for functions that never return or exhaustive checking.

```typescript
function throwError(message: string): never {
  throw new Error(message);
}

// Exhaustive checking
type Shape = { kind: "circle"; radius: number } | { kind: "rectangle"; width: number; height: number };
function process(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
    default:
      const _exhaustive: never = shape;
      throw new Error(`Unhandled shape: ${String(_exhaustive)}`);
  }
}

```

## Intermediate Questions (10)

### 11. How do you type a function that returns a Promise?

**Answer**: An `async` function returns `Promise<T>`. An explicit `Promise<User>` annotation remains the public type even when the body returns `any`; the risk is unchecked data masquerading as `User`, not the annotation silently widening to `Promise<any>`. Decode at the boundary with a schema parser or hand-written decoder so the annotation is a checked claim. `ReturnType<typeof fetchUser>` derives a type from an implementation you own, but can make the public contract less visible.

```typescript
// Explicit return type
interface User { id: string; name: string }
async function fetchUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const data: unknown = await response.json();
  return parseUser(data);
}
// parseUser must validate the data and return User; an annotation alone cannot.
function parseUser(data: unknown): User {
  if (typeof data !== 'object' || data === null || Array.isArray(data)) throw new Error('Invalid user');
  const record = data as Record<string, unknown>;
  if (!Object.hasOwn(record, 'id') || typeof record.id !== 'string' ||
      !Object.hasOwn(record, 'name') || typeof record.name !== 'string') throw new Error('Invalid user');
  return { id: record.id, name: record.name };
}

// Using ReturnType
type UserReturn = ReturnType<typeof fetchUser>; // Promise<User>

```

**Trade-off**: an explicit `Promise<User>` documents the contract and fails loudly when the body changes; deriving it with `ReturnType` can never drift, but hides the shape from readers of the signature — team convention should pick which side loses.

### 12. What is the difference between `extends` and `&`?

**Answer**:

- `extends`: Interface inheritance; redeclared members must remain compatible with the base
- `&`: Requires both shapes; an incompatible property can become `never`, and some conflicting discriminants reduce the whole intersection to `never`

```typescript
// extends
interface Animal {
  name: string;
}
interface Dog extends Animal {
  breed: string;
}

// &
type AnimalShape = { name: string };
type DogShape = AnimalShape & { breed: string };

```

### 13. How do you type event handlers?

**Answer**: In React, `React.MouseEvent<HTMLButtonElement>` connects the handler to a button, so `currentTarget` has the button type. `target` identifies the element where the event originated, which may be a child of that button. In plain DOM code, `event.target` is `EventTarget | null`; attaching a handler to an input does not by itself prove that every event target is that input. Check the actual target before treating it as an `HTMLInputElement`, or use a known input reference. An assertion records an assumption rather than checking it.

```typescript
import type * as React from 'react';
// React event handlers
function handleClick(event: React.MouseEvent<HTMLButtonElement>) {
  console.log(event.clientX, event.clientY);
}

// DOM event handlers
function handleInput(event: Event) {
  if (event.target instanceof HTMLInputElement) console.log(event.target.value);
}

```

**Trade-off**: precise generics per handler are verbose but keep every property checked; a broad DOM `Event` requires a runtime check or an already known element reference. React's generic applies to currentTarget, while target may still be a child element.

### 14. What are mapped types?

**Answer**: Types that transform existing types by iterating over their keys.

```typescript
type Optional<T> = {
  [K in keyof T]?: T[K];
};

type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

```

### 15. What are conditional types?

**Answer**: Conditional types are the type system's `if` — they let one type *compute* another, which is what turns type definitions from declarations into programs. The detail that separates seniors from users is distribution: a conditional over a naked type parameter distributes over unions, so `IsString<string | number>` evaluates each member separately (`true | false`) rather than testing the union as a whole. Wrapping the parameter in a tuple (`[T] extends [string]`) opts out when whole-union semantics are what you want. Almost every advanced utility type — `Awaited`, `Parameters`, `Extract` — is a conditional type with a structural test inside.

```typescript
type IsString<T> = T extends string ? true : false;

type A = IsString<string>; // true
type B = IsString<number>; // false

```

**Trade-off**: conditional types express relationships that would otherwise need repeated overloads, but deeply nested conditions can make diagnostics difficult to interpret. Prefer a named helper or simpler mapped type when it preserves the same contract more clearly.

### 16. How do you type a generic React component?

**Answer**: `Props<T>` connects an `items: T[]` property with a `renderItem` callback accepting `T`. Passing `User[]` therefore gives the callback a `User` parameter without an assertion. Using `any[]` loses that information; declaring the callback separately loses the relationship between the two props. A render callback makes the connection explicit. It can be a named prop or a function-valued `children` prop; ordinary already-created child elements do not establish that per-item relationship.

```typescript
import * as React from 'react';
interface Props<T> {
  items: readonly T[];
  itemKey: (item: T) => React.Key;
  renderItem: (item: T) => React.ReactNode;
}

function List<T>({ items, itemKey, renderItem }: Props<T>) {
  return <div>{items.map(item => <React.Fragment key={itemKey(item)}>{renderItem(item)}</React.Fragment>)}</div>;
}

// Usage
<List
  items={["a", "b", "c"]}
  itemKey={item => item}
  renderItem={(item) => <span>{item}</span>}
/>

```

### 17. What is the `infer` keyword?

**Answer**: Used in conditional types to extract and name a type.

```typescript
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type Fn = () => string;
type Result = MyReturnType<Fn>; // string

```

### 18. How do you type a REST API response?

**Answer**: A TypeScript response interface is a compile-time contract; it does not verify bytes from a remote service. In the DOM library, `response.json()` returns `Promise<any>`, so assign the result to `unknown` and decode it before use. A hand-written interface can drift from the server; generated types follow the OpenAPI document, which can itself drift from deployed behavior. Contract tests and runtime validation cover different parts of that gap. Model a shared envelope generically only when the API actually returns that shape.

```typescript
interface User { id: string; name: string }

function parseUser(value: unknown): User {
  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    throw new Error("Invalid user response");
  }
  const record = value as Record<string, unknown>;
  if (!Object.hasOwn(record, "id") || typeof record.id !== "string" ||
      !Object.hasOwn(record, "name") || typeof record.name !== "string") {
    throw new Error("Invalid user response");
  }
  return { id: record.id, name: record.name };
}

async function getUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const input: unknown = await response.json();
  return parseUser(input);
}

// If this API returns an envelope, model that actual contract:
interface ApiResponse<T> { data: T; status: number; message: string }
type UserResponse = ApiResponse<User>;

```

### 19. What are type guards?

**Answer**: A type guard narrows a value in a control-flow branch. A function predicate such as `value is string` asks TypeScript to trust the implementation; the compiler does not prove that the check is sound, so a decoder must verify every promised condition.

```typescript
function isString(value: unknown): value is string {
  return typeof value === "string";
}

function process(value: unknown) {
  if (isString(value)) {
    value.toUpperCase(); // OK after type guard
  }
}

```

### 20. How do you type a reducer?

**Answer**: A reducer has the contract `(state: S, action: A) => S`. A discriminated-union action lets the `type` check narrow the matching payload. Add a `never` check in the default branch to make an unhandled action variant a compile-time error; the union alone does not require exhaustive handling.

```typescript
type Action =

  | { type: "INCREMENT"; amount: number }
  | { type: "DECREMENT"; amount: number }
  | { type: "RESET" };

interface State {
  count: number;
}

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "INCREMENT":
      return { count: state.count + action.amount };
    case "DECREMENT":
      return { count: state.count - action.amount };
    case "RESET":
      return { count: 0 };
    default: {
      const unhandled: never = action;
      throw new Error(`Unhandled action: ${String(unhandled)}`);
    }
  }
}

```

## Senior Questions (10)

### 21. How do you implement a type-safe event emitter?

**Answer**: One event-map key selects its payload and the listener parameter through indexed access. A union of complete `[event, payload]` tuples preserves that pairing even when event names form a union; two independent union arguments can lose it. [The canonical emitter](../04-advanced-patterns/10.2.4.05-advanced-patterns.md#couple-an-event-name-to-its-payload-then-define-dispatch) demonstrates storage, snapshot dispatch and per-registration disposal.

Trace subscription, emitting one valid created payload, unsubscribing and emitting again. Then remove a listener during dispatch: the current snapshot still calls it, but the next emission does not. State the failure policy too: synchronous exceptions stop dispatch, and returned promises are not awaited. Payload typing does not validate received bytes or force owners to dispose subscriptions.

### 22. Design a type-safe state management solution

**Answer**: A mapped union preserves the relation between each action tag and its payload. `Action<keyof ActionMap>` written as a single object with two union-valued properties loses that relation, so checking `type` cannot narrow `payload` correctly.

```typescript
type ActionMap = {
  "user/create": { id: string; name: string; email: string };
  "user/delete": { userId: string };
};
type Action<K extends keyof ActionMap = keyof ActionMap> = {
  [P in K]: { type: P; payload: ActionMap[P] }
}[K];

interface UserState { users: { id: string; name: string; email: string }[] }
function reducer(state: UserState, action: Action): UserState {
  switch (action.type) {
    case "user/create":
      return { users: [...state.users, action.payload] };
    case "user/delete":
      return { users: state.users.filter(user => user.id !== action.payload.userId) };
    default: {
      const unhandled: never = action;
      throw new Error(`Unhandled action: ${String(unhandled)}`);
    }
  }
}
```


### 23. How do you create a type-safe router?

**Answer**: Keep a literal path as the input to a parameter extractor, then implement the same grammar in the runtime router. [The whole-segment route example](../03-type-transformations/10.2.3.04-template-literal-types.md) derives names for segments such as `:userId` and encodes their supplied values. Merely returning `{ path, handler }` does not match a URL or populate those parameters.

For `/users/:id`, predict the handler's parameter type. Rename it to `:userId`: code reading `params.id` must fail. Adding optional or catch-all segments requires matching type and runtime rules; test missing values, encoding and segment collisions rather than assuming a regex implements every router grammar.

### 24. Implement a type-safe curry function

**Answer**: Each unary stage consumes the head of a required parameter tuple; recursive conditional types derive the remaining stages. Use the [explicit three-argument curry](../02-generics-and-inference/10.2.2.03-advanced-generics.md) to trace `add(1)(2)(3)` to 6 and a wrong second argument to a type error. The implementation and derived type must agree on arity.

`fn.length` is insufficient for a general API: it stops before the first default parameter and ignores rest parameters. Optional/rest tuples also need a different stopping contract. Either constrain the supported function shape and take explicit arity, or provide tested overloads for the intended variants. A cast to a recursive type cannot resolve that runtime ambiguity.

### 25. How do you type a deep object path?

**Answer**:
The example resolves a supplied dotted path by separating its first segment from the rest and looking up each segment. An invalid segment produces `never`. As written, it handles required object paths; optional intermediate properties or union branches may resolve to `never` and need an explicit nullish/union policy. It does not enumerate every valid path or constrain a runtime getter. A getter must implement the same lookups and handle missing values. Helpers that enumerate many nested paths can create large unions and increase checking work.


```typescript
type DeepPropertyAccess<T, Path extends string> =
  Path extends `${infer Head}.${infer Rest}`
    ? Head extends keyof T
      ? DeepPropertyAccess<T[Head], Rest>
      : never
    : Path extends keyof T
      ? T[Path]
      : never;

interface Config {
  database: {
    host: string;
    port: number;
  };
}

type HostType = DeepPropertyAccess<Config, "database.host">; // string

```

### 26. Design a type-safe form validation system

**Answer**:
Two types carry the design: the schema (field names mapped to validators) and the derived errors type, where each field maps to the errors *its* validator can produce. The example derives rules and error keys from the data type; rules are optional, so missing validators are permitted. A required rule map is needed if every field must be validated. The runtime side just executes the schema; the type side guarantees the results shape. This field-rule map validates already typed data. A schema parser accepting unknown input and deriving its output type is a different, stronger boundary.


```typescript
type ValidationRule<T> = {
  [K in keyof T]?: {
    required?: boolean;
    minLength?: number;
    maxLength?: number;
    pattern?: RegExp;
    custom?: (value: T[K]) => string | null;
  };
};

type ValidationErrors<T> = {
  [K in keyof T]?: string[];
};

function validate<T extends object>(
  data: T,
  rules: ValidationRule<T>
): ValidationErrors<T> {
  const errors: ValidationErrors<T> = Object.create(null);

  for (const key of Object.keys(rules) as (Extract<keyof T, string>)[]) {
    const value = data[key];
    const rule = rules[key];
    const fieldErrors: string[] = [];

    if (rule?.required && (!Object.hasOwn(data, key) || value === undefined || value === null)) {
      fieldErrors.push(`${key} is required`);
    }

    if (typeof value === "string") {
      if (rule?.minLength !== undefined && value.length < rule.minLength) fieldErrors.push(`${key} is too short`);
      if (rule?.maxLength !== undefined && value.length > rule.maxLength) fieldErrors.push(`${key} is too long`);
      if (rule?.pattern) {
        rule.pattern.lastIndex = 0; // Stateful global/sticky patterns must start consistently
        if (!rule.pattern.test(value)) fieldErrors.push(`${key} has an invalid format`);
      }
    }

    if (rule?.custom) {
      const error = rule.custom(value);
      if (error) fieldErrors.push(error);
    }

    if (fieldErrors.length > 0) {
      errors[key] = fieldErrors;
    }
  }

  return errors;
}

```

The loop visits own string rule keys, not inherited or symbol keys. It assumes a closed rule map for the data contract; the key assertion does not validate arbitrary external rules or prove that runtime data matches `T`. Required here rejects an absent own field or null/undefined, not the empty string; length rules apply only to strings, and min/max rules supplied for another type are ignored. The null-prototype error map handles a field named `__proto__` as data. Reusing a global regex resets its cursor before each check.

### 27. How do you create a type-safe middleware chain?

**Answer**: This synchronous chain shares one context type across handlers. Calling `next` transfers control to the remaining handlers, which return before the earlier handler resumes; context enrichment would require a separate staged type design.

```typescript
type Middleware<T> = (req: T, next: () => void) => void;
function createMiddlewareChain<T>(middlewares: Middleware<T>[]): (req: T) => void {
  return req => {
    let lastIndex = -1;
    const dispatch = (index: number): void => {
      if (index <= lastIndex) throw new Error("next called more than once");
      lastIndex = index;
      const middleware = middlewares[index];
      if (middleware) middleware(req, () => dispatch(index + 1));
    };
    dispatch(0);
  };
}
```

### 29. How do you type a plugin system?

**Answer**:
The host supplies the application type to `AppPlugin<T>`, so each installer receives that API. This example checks installer signatures; a typed hook map is an additional design if plugins subscribe to named host events.


```typescript
interface AppPlugin<T> {
  name: string;
  install: (app: T) => void;
}

class App {
  private plugins: AppPlugin<App>[] = [];

  use(plugin: AppPlugin<App>): void {
    this.plugins.push(plugin);
    plugin.install(this);
  }
}

const loggerPlugin: AppPlugin<App> = {
  name: "logger",
  install: (_app) => {
    console.log("Logger installed");
  }
};

```

Each plugin installer receives the same host. The simple `App` retains plugins indefinitely and permits duplicates; an installer failure occurs after its entry was pushed. Question38 deliberately defines a different commit point and duplicate policy.

### 30. Design a type-safe configuration system

**Answer**:
Configuration is where runtime reality (env vars, files) meets compile-time promises, so the design has a seam: a *validated* load step whose output is a precise `AppConfig`, after which everything downstream is typed and total. The example only receives already typed defaults and returns them; a loader must separately parse environment strings and fail at boot for invalid or missing required values. The type is the contract between ops and code — the loaders are how it is enforced.


```typescript
type ConfigSchema = {
  database: {
    host: string;
    port: number;
    credentials: {
      user: string;
      password: string;
    };
  };
  server: {
    port: number;
    ssl: boolean;
  };
};

function createConfig(defaults: ConfigSchema): ConfigSchema {
  return defaults;
}

const config = createConfig({
  database: {
    host: "localhost",
    port: 5432,
    credentials: {
      user: "admin",
      password: "example-placeholder"
    }
  },
  server: {
    port: 3000,
    ssl: false
  }
});

```

## FAANG-style Questions (10)

### 31. Design a type-safe API client

**Answer**: Derive the request body and response from the same endpoint map. A runtime parser converts the untrusted JSON into the declared result; without it, a generic return annotation is only a claim. This minimal client covers literal paths, not path substitution or query parameters.

```typescript
interface UserDTO { id: string; name: string }
interface ApiEndpoints {
  "/users": {
    GET: { response: UserDTO[] };
    POST: { body: { name: string }; response: UserDTO };
  };
}
type Endpoint<P extends keyof ApiEndpoints, M extends keyof ApiEndpoints[P]> = ApiEndpoints[P][M];
type ResponseOf<E> = E extends { response: infer R } ? R : never;
type Options<E> = E extends { body: infer B } ? { body: B } : { body?: never };

class ApiClient {
  async request<P extends keyof ApiEndpoints, M extends keyof ApiEndpoints[P]>(
    path: P,
    method: M,
    options: Options<Endpoint<P, M>>,
    parse: (input: unknown) => ResponseOf<Endpoint<P, M>>
  ): Promise<ResponseOf<Endpoint<P, M>>> {
    const init: RequestInit = {
      method: String(method)
    };
    if (options.body !== undefined) {
      init.headers = { "Content-Type": "application/json" };
      init.body = JSON.stringify(options.body);
    }
    const response = await fetch(path, init);
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const data: unknown = await response.json();
    return parse(data);
  }
}
```


This minimal signature assumes literal endpoint selections. A union-valued method can widen the conditional options type and lose the request-body correlation; accepting dynamic selections requires a union of complete path/method/options specifications, as the event-pair drill demonstrates. The provided decoder is also a trusted boundary: it must check the response rather than casting it.

### 32. Implement a type-safe state machine

**Answer**: Return a new machine whose state parameter is the table's next state. Returning the previous state with an assertion would make the compile-time transition a lie; mutating the same instance would also leave old references with stale state types.

```typescript
const transitions = {
  idle: { FETCH: "loading" },
  loading: { SUCCESS: "success", ERROR: "error" },
  success: { RESET: "idle" },
  error: { RETRY: "loading", RESET: "idle" }
} as const;
type State = keyof typeof transitions;
type EventFor<S extends State> = keyof typeof transitions[S];
type NextState<S extends State, E extends EventFor<S>> = typeof transitions[S][E] & State;

class StateMachine<S extends State> {
  constructor(readonly state: S) {}
  transition<E extends EventFor<S>>(event: E): StateMachine<NextState<S, E>> {
    const table = transitions[this.state];
    if (!Object.hasOwn(table, event)) throw new Error('Invalid transition');
    const next = table[event] as NextState<S, E>;
    return new StateMachine(next);
  }
}
const machine = new StateMachine("idle");
const next = machine.transition("FETCH"); // StateMachine<"loading">
console.log(next.state); // "loading"
// next.transition("FETCH"); // Type error: only SUCCESS or ERROR is legal
```


### 33. Design a type-safe ORM

**Answer**:
The schema is the source of truth: table definitions carry column types, and everything else — entity types, insert payloads (required vs generated columns), query results, join shapes — is derived. `select` narrowing the result to chosen columns is the same mapped-type trick as the query builder, applied to relations. The hard part is not the happy path; it is keeping migrations and types generated from the same schema so drift cannot start. The interface below describes boundary signatures without inventing an implementation. The adapter must assign generated fields and decode persisted rows; a hand-written model can still drift from a migration.


```typescript
interface Model {
  id: string;
  createdAt: Date;
  updatedAt: Date;
}

interface User extends Model {
  name: string;
  email: string;
}

// Boundary signatures only: a real adapter implements persistence and decoding.
interface Repository<T extends Model> {
  findById(id: string): Promise<T | null>;
  findMany(where: Partial<T>): Promise<T[]>;
  create(data: Omit<T, 'id' | 'createdAt' | 'updatedAt'>): Promise<T>;
}
```

### 34. Implement a type-safe middleware system

**Answer**:
This variant adds asynchronous onion-style control flow and ordered registration to Q27. It keeps one fixed context type and returns the router from `use`; it does not prove authentication ordering or provide deregistration.


```typescript
type Context = {
  req: Request;
  res: Response;
  state: Record<string, unknown>;
};

type Middleware = (ctx: Context, next: () => Promise<void>) => Promise<void>;

function createRouter() {
  const middlewares: Middleware[] = [];

  return {
    use(middleware: Middleware) {
      middlewares.push(middleware);
      return this;
    },

    async handle(ctx: Context) {
      const chain = middlewares.slice(); // One invocation sees a stable registration list.
      let lastIndex = -1;
      async function dispatch(index: number): Promise<void> {
        if (index <= lastIndex) throw new Error("next called more than once");
        lastIndex = index;
        const middleware = chain[index];
        if (middleware) await middleware(ctx, () => dispatch(index + 1));
      }
      await dispatch(0);
    }
  };
}

```

For two middleware wrappers, trace outer-before, inner-before, inner-after, outer-after. Each wrapper must await or return `next()` to preserve that ordering; fire-and-forget continuation can outlive the request. A second next call rejects. Middleware registered during a request appears only in the next handle snapshot; exceptions propagate to the caller. Request and Response here are DOM Fetch types, not Express objects.

### 35. Design a type-safe validation library

**Answer**:
This example improves the field-validator signature from Q26: each callback receives its own field type. It collects messages for already typed data and returns a validity flag; parsing `unknown` into a new output type, defaults and coercion require a separate schema parser. The implementation still assumes both arguments match `T` at runtime; its key assertion does not validate extra rule names or parse untrusted input.


```typescript
type Validator<T> = {
  [K in keyof T]?: (value: T[K]) => string | null;
};

type ValidationErrors<T> = {
  [K in keyof T]?: string[];
};

function validate<T extends object>(
  data: T,
  validators: Validator<T>
): { valid: boolean; errors: ValidationErrors<T> } {
  const errors: ValidationErrors<T> = Object.create(null);
  let valid = true;

  for (const key of Object.keys(validators) as (Extract<keyof T, string>)[]) {
    const validator = validators[key];
    if (validator) {
      const error = validator(data[key]);
      if (error) {
        errors[key] = [error];
        valid = false;
      }
    }
  }

  return { valid, errors };
}

```

### 36. Implement a type-safe event system

**Answer**: Extend the emitter from [Question 21](#21-how-do-you-implement-a-type-safe-event-emitter) with a `once` method. Remove the subscription before invoking user code, so a listener that emits recursively cannot run itself a second time.

```typescript
// Add this method inside the canonical TypedEventEmitter<Events> linked in Q21:
once<K extends keyof Events>(event: K, listener: (payload: Events[K]) => void): () => void {
  const unsubscribe = this.on(event, payload => {
    unsubscribe();
    listener(payload);
  });
  return unsubscribe;
}
```

Owners must still call the returned cleanup function when disposed before the event occurs; subscription types alone cannot enforce lifecycle cleanup.


### 37. Design a type-safe dependency injection container

**Answer**: Use a token object whose identity is the lookup key and whose phantom parameter carries the result type. Registration binds that token to a matching instance; resolution cannot choose an unrelated result type through a free generic argument.

```typescript
class Token<T> {
  declare private readonly invariant: (value: T) => T;
  constructor(readonly name: string) {}
}
class Container {
  private services = new Map<object, unknown>();
  register<T>(token: Token<T>, service: NoInfer<T>): void {
    if (this.services.has(token)) throw new Error('Duplicate token');
    this.services.set(token, service);
  }
  resolve<T>(token: Token<T>): T {
    if (!this.services.has(token)) throw new Error(`Missing service: ${token.name}`);
    return this.services.get(token) as T;
  }
}
class DatabaseService {
  query(_sql: string): unknown[] { return []; }
}
const database = new Token<DatabaseService>("database");
const container = new Container();
container.register(database, new DatabaseService());
const db = container.resolve(database); // DatabaseService
// NoInfer requires TS 5.4+; this sample registers instances, not constructor graphs.
```


The private function member makes Token invariant under strict function checking, so widening `Token<Dog>` to `Token<Animal>` cannot allow an incompatible Animal to be registered under a Dog token. It is erased and performs no runtime validation. Lookup uses token object identity, not its display name. This sample registers explicit instances; it does not build constructor graphs or infer service scopes.

### 38. Implement a type-safe plugin system

**Answer**: The `AppPlugin<T>` contract and installation flow are already shown in [Question 29](#29-how-do-you-type-a-plugin-system). Add version metadata and lookup when consumers need to inspect installed plugins; a production host should also define duplicate-name policy and teardown.

```typescript
// Reuse the AppPlugin contract from Q29.
interface AppPlugin<T> { name: string; install: (app: T) => void }
interface VersionedPlugin<T> extends AppPlugin<T> { version: string }
class PluginRegistry<T> {
  private plugins = new Map<string, VersionedPlugin<T>>();
  constructor(private app: T) {}
  register(plugin: VersionedPlugin<T>): void {
    if (this.plugins.has(plugin.name)) throw new Error("Duplicate plugin");
    plugin.install(this.app);
    this.plugins.set(plugin.name, plugin);
  }
  getPlugin(name: string): VersionedPlugin<T> | undefined {
    return this.plugins.get(name);
  }
}
```

If `install` throws, the registry does not record the plugin, but side effects already performed by the installer remain. Rollback or cleanup is a host/plugin contract.


### 39. Design a type-safe configuration system

**Answer**:
This manager supports top-level replacement. Overrides are `Partial<T>`, so a supplied nested object must be complete; spreading `DeepPartial<T>` into the root would overwrite required sibling fields and break the contract. True layered deep merging needs explicit rules for arrays, missing values and non-record objects.


```typescript
type ConfigSchema = {
  database: {
    host: string;
    port: number;
  };
  server: {
    port: number;
  };
};

class ConfigManager<T extends object> {
  private config: T;

  constructor(defaults: T) {
    this.config = { ...defaults };
  }

  get<K extends keyof T>(key: K): T[K] {
    return this.config[key];
  }

  set<K extends keyof T>(key: K, value: T[K]): void {
    this.config[key] = value;
  }

  merge(overrides: Partial<T>): void {
    const next = { ...this.config };
    for (const key of Reflect.ownKeys(this.config) as (keyof T)[]) {
      if (!Object.hasOwn(overrides, key)) continue;
      const value = overrides[key];
      if (value !== undefined) next[key] = value;
    }
    this.config = next;
  }
}

```

This manager assumes an own-property plain configuration record whose runtime keys match `T`. Merge ignores explicit undefined instead of erasing a required field, iterates the defaults' own keys, and replaces a supplied nested object wholesale. TypeScript's structural object types do not enforce exact keys, so validate external defaults and overrides before this typed API. The root copy does not clone nested objects; a value returned by get may still be mutable through an alias.

### 40. Implement a type-safe query builder

**Answer**:
The example checks table and column names, then renders a SQL statement with separately bound values. It mutates one builder and returns `this`, so it does not track selected result shapes or persistent query states; those require additional generic parameters and immutable builder instances.


```typescript
interface DatabaseSchema {
  users: { id: string; name: string; email: string; active: boolean };
  posts: { id: string; title: string; authorId: string };
}

type Table = keyof DatabaseSchema;
type Column<T extends Table> = keyof DatabaseSchema[T];

const columnsByTable: { [T in Table]: readonly Column<T>[] } = {
  users: ['id', 'name', 'email', 'active'], posts: ['id', 'title', 'authorId']
};
class QueryBuilder<T extends Table> {
  private selectedColumns: Column<T>[] = [];
  private whereCondition: string = "";
  private parameters: unknown[] = [];

  constructor(private table: T) {
    if (!Object.hasOwn(columnsByTable, table)) throw new Error('Unknown table');
  }
  private checkColumn(column: PropertyKey): void {
    const allowed: readonly PropertyKey[] = columnsByTable[this.table];
    if (!allowed.includes(column)) throw new Error('Unknown column');
  }

  select(...columns: Column<T>[]): this {
    columns.forEach(column => this.checkColumn(column));
    this.selectedColumns = columns;
    return this;
  }

  where<K extends Column<T>>(column: K, value: DatabaseSchema[T][NoInfer<K>]): this {
    this.checkColumn(column);
    this.whereCondition = `${String(column)} = $1`;
    this.parameters = [value];
    return this;
  }

  build(): { sql: string; parameters: unknown[] } {
    const columns = this.selectedColumns.length ? this.selectedColumns.join(", ") : "*";
    let query = `SELECT ${columns} FROM ${this.table}`;
    if (this.whereCondition) {
      query += ` WHERE ${this.whereCondition}`;
    }
    return { sql: query, parameters: [...this.parameters] };
  }
}

const query = new QueryBuilder("users")
  .select("id", "name")
  .where("id", "1")
  .build();
new QueryBuilder("users").where("active", true);
// @ts-expect-error active is boolean, not a string
new QueryBuilder("users").where("active", "true");

```

For the fixture, build returns `SELECT id, name FROM users WHERE id = $1` with `['1']`. Values stay in the binding array, while table/column names pass runtime allowlists because SQL identifiers cannot use value placeholders. A later where replaces the earlier condition, and selected columns do not derive typed result rows. The allowlists and schema types must remain aligned with the real database adapter.

### 41. How does TypeScript handle module resolution?

**Answer**: Choose module settings for the tool that will run the output. Node modes model Node's ESM/CommonJS rules and package exports: use a fixed mode such as `node16`, `node18` or `node20` when you need that version's contract, or `nodenext` when you want the latest Node behavior. The standard pairing uses `moduleResolution: "node16"` with fixed Node modes and `"nodenext"` with `"nodenext"`; keep the resolver aligned with the runtime version because it selects package conditions and valid import paths. For a bundler, use a bundler-compatible `module` setting with `moduleResolution: "bundler"`; that mode permits extensionless relative imports that Node ESM rejects. `paths` changes TypeScript's lookup only, not emitted import strings, so the runtime or bundler must implement the same alias. Use `tsc --traceResolution` to inspect the chosen files and package conditions. [Module resolution reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html).

### 43. How do you handle circular dependencies?

**Answer**: Separate runtime imports from type-only dependencies with `import type`, move shared contracts to a module with no runtime edges, and reorganize initialization when values depend on each other. Choosing interface versus type alias does not itself break a runtime cycle. Barrel re-exports can add cycles, so inspect the actual import graph before introducing one.

### 47. How do you type a WebSocket connection?

**Answer**: Use separate outgoing and incoming contracts and require a parser for received data. The parser validates `unknown` before the callback sees a typed message; a generic cast on `JSON.parse` would accept arbitrary bytes as any chosen message type.

```typescript
type OutgoingMessage = { type: "subscribe"; topic: string };
type IncomingMessage =
  | { type: "event"; topic: string; data: unknown }
  | { type: "error"; message: string };

class TypedWebSocket {
  constructor(private ws: WebSocket, private parse: (data: unknown) => IncomingMessage) {}
  send(message: OutgoingMessage): void {
    if (this.ws.readyState !== WebSocket.OPEN) throw new Error('Socket not open');
    this.ws.send(JSON.stringify(message));
  }
  on(callback: (message: IncomingMessage) => void, onError: (error: unknown) => void): () => void {
    const listener = (event: MessageEvent) => {
      let message: IncomingMessage;
      try {
        if (typeof event.data !== 'string') throw new Error('Expected text message');
        const data: unknown = JSON.parse(event.data);
        message = this.parse(data);
      } catch (error) { onError(error); return; }
      callback(message);
    };
    this.ws.addEventListener("message", listener);
    return () => this.ws.removeEventListener("message", listener);
  }
}
// The parser must check each discriminant and field; handle malformed input
// according to the connection's protocol rather than trusting the annotation.
```


### 48. What are type assertions?

**Answer**: A way to tell TypeScript about a more specific type.

```typescript
const element = document.getElementById("app") as HTMLDivElement;
const input: unknown = "Ada";
const value = input as string; // Claims string; does not run a typeof check.

```

A DOM assertion does not check null or the tag name. An actual `element instanceof HTMLDivElement` branch validates those conditions; an assertion only changes the checker's view. Assertions can therefore invalidate the evidence promised by brands, guards or library declarations.

### 49. How do you handle async/await with TypeScript?

**Answer**:
The language rules first: `async` functions return `Promise<T>`, `await` recursively unwraps promise-like values (the static type `Promise<Promise<T>>` is distinct, while its awaited result is `T`), and rejected paths are untyped by default — `catch` variables use `unknown` with `useUnknownInCatchVariables`, enabled by `strict` since TS 4.4. The senior patterns follow from that last point: either type errors explicitly via discriminated result objects (`{ ok: true, value } | { ok: false, error }`), or validate in the catch. `Promise.all` rejects on the first rejection; `allSettled` reports every outcome using fulfilled/rejected result variants. Neither API gives rejection reasons a custom checked error type by itself.


```typescript
async function fetchData<T>(url: string, parse: (data: unknown) => T): Promise<T> {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`HTTP error! status: ${response.status}`);
  }
  const data: unknown = await response.json();
  return parse(data);
}
```

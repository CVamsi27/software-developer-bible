## Beginner Questions (10)

### 1. What is TypeScript?

**Answer**: TypeScript is a statically-typed superset of JavaScript that compiles to plain JavaScript. It adds optional type annotations, interfaces, enums, and other features that help catch errors at compile time rather than runtime.

```typescript
// JavaScript
function add(a, b) {
  return a + b;
}

// TypeScript
function add(a: number, b: number): number {
  return a + b;
}

```

### 2. What are the benefits of using TypeScript?

**Answer**:

- **Type safety**: Catch errors at compile time
- **Better IDE support**: Autocomplete, refactoring, navigation
- **Self-documenting code**: Types serve as documentation
- **Easier refactoring**: TypeScript catches breaking changes
- **Scalability**: Essential for large codebases and teams

### 3. What is the difference between `any` and `unknown`?

**Answer**:

- `any`: Disables type checking, allows any operation
- `unknown`: Type-safe alternative to `any`, requires type checking before use

```typescript
// any - unsafe
let value: any = "hello";
value.toUpperCase(); // OK
value.foo.bar.baz; // OK (but runtime error)

// unknown - safe
let value: unknown = "hello";
value.toUpperCase(); // Error: Object is of type 'unknown'
if (typeof value === "string") {
  value.toUpperCase(); // OK after type check
}

```

### 4. What are type aliases and interfaces?

**Answer**:

- **Type alias (`type`)**: Creates a name for any type (primitives, unions, intersections)
- **Interface**: Defines the shape of objects, supports declaration merging

```typescript
// Type alias
type ID = string | number;
type User = { name: string; age: number };

// Interface
interface UserInterface {
  name: string;
  age: number;
}

```

### 5. What is structural typing?

**Answer**: TypeScript uses structural typing, meaning types are compatible based on their structure, not their explicit declarations.

```typescript
interface Point {
  x: number;
  y: number;
}

interface Coordinate {
  x: number;
  y: number;
}

const point: Point = { x: 1, y: 2 };
const coord: Coordinate = point; // OK - same structure

```

### 6. What are generics?

**Answer**: Generics allow you to write reusable, type-safe code that works with multiple types while preserving type information.

```typescript
function identity<T>(value: T): T {
  return value;
}

const str = identity("hello"); // T is string
const num = identity(42); // T is number

```

### 7. What are utility types?

**Answer**: Utility types are the standard library's type *transformers* — they exist so a type has one source of truth and every variant is derived from it. Hand-write `interface PartialUser` and you have promised to keep it in sync with `User` forever; `Partial<User>` cannot drift because it is a computation over the original. The senior-level point is that utility types encode intent: `Readonly` states "this function must not mutate", `Pick` states "this API surface is exactly these fields", and `Omit` states "everything except" — which survives adding new fields, while a hand-written pick-list silently rots.

```typescript
interface User {
  id: string;
  name: string;
  email: string;
}

type PartialUser = Partial<User>; // All properties optional
type ReadonlyUser = Readonly<User>; // All properties readonly
type UserName = Pick<User, "name">; // { name: string }

```

**Trade-off**: derived types improve at the speed of the source type, but deeply chained utilities produce error messages that quote the derivation, not the shape — at three-plus levels, extracting a named intermediate type usually buys back the readability.

### 8. What is type narrowing?

**Answer**: The process of refining a broader type into a more specific type through control flow analysis.

```typescript
function process(value: string | number) {
  if (typeof value === "string") {
    return value.toUpperCase(); // string
  } else {
    return value.toFixed(2); // number
  }
}

```

### 9. What are discriminated unions?

**Answer**: A union of types with a common discriminant property, enabling type-safe pattern matching.

```typescript
type Shape =

  | { kind: "circle"; radius: number }
  | { kind: "rectangle"; width: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
  }
}

```

### 10. What is the `never` type?

**Answer**: A type that represents values that never occur. Used for functions that never return or exhaustive checking.

```typescript
function throwError(message: string): never {
  throw new Error(message);
}

// Exhaustive checking
function process(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
    default:
      const _exhaustive: never = shape;
      return _exhaustive;
  }
}

```

## Intermediate Questions (10)

### 11. How do you type a function that returns a Promise?

**Answer**: The return type of an `async` function is always `Promise<T>` — what the annotation buys you is deciding *what* `T` is. The trap is `response.json()`: it returns `any`, so the code above type-checks while silently widening the promise to `Promise<any>`, and every consumer downstream loses checking. The honest pattern is validating at the boundary (a schema parser or a hand-written assertion) so the annotation is a *checked* claim, not a decoration. `ReturnType<typeof fetchUser>` is the mirror trick for when you own the implementation but not the type — derive the type from the function rather than maintaining both.

```typescript
// Explicit return type
async function fetchUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${id}`);
  return response.json();
}

// Using ReturnType
type UserReturn = ReturnType<typeof fetchUser>; // Promise<User>

```

**Trade-off**: an explicit `Promise<User>` documents the contract and fails loudly when the body changes; deriving it with `ReturnType` can never drift, but hides the shape from readers of the signature — team convention should pick which side loses.

### 12. What is the difference between `extends` and `&`?

**Answer**:

- `extends`: Interface inheritance, can override properties
- `&`: Intersection type, creates a type with all properties

```typescript
// extends
interface Animal {
  name: string;
}
interface Dog extends Animal {
  breed: string;
}

// &
type Animal = { name: string };
type Dog = Animal & { breed: string };

```

### 13. How do you type event handlers?

**Answer**: Two different disciplines hide under "typing an event handler". In React, the event type is parameterized by the element — `React.MouseEvent<HTMLButtonElement>` — because the generic is what makes `currentTarget` typed correctly; `currentTarget` is the element the listener is attached to (always typed), while `target` is what was *actually clicked* (typed only by delegation assumptions). In plain DOM code, `event.target` is typed as `EventTarget | null` for exactly that reason, and the `as HTMLInputElement` cast is you taking over the compiler's job — safe only if the handler genuinely only ever attaches to inputs. The senior tell is knowing casts here are *contracts*, not conveniences.

```typescript
// React event handlers
function handleClick(event: React.MouseEvent<HTMLButtonElement>) {
  console.log(event.clientX, event.clientY);
}

// DOM event handlers
function handleInput(event: Event) {
  const target = event.target as HTMLInputElement;
  console.log(target.value);
}

```

**Trade-off**: precise generics per handler are verbose but keep every property checked; a broad `Event` + one cast is shorter and centralizes the assumption — acceptable at the attachment site, a smell when the cast travels.

### 14. What are mapped types?

**Answer**: Types that transform existing types by iterating over their keys.

```typescript
type Optional<T> = {
  [K in keyof T]?: T[K];
};

type Readonly<T> = {
  readonly [K in keyof T]: T[K];
};

```

### 15. What are conditional types?

**Answer**: Conditional types are the type system's `if` — they let one type *compute* another, which is what turns type definitions from declarations into programs. The detail that separates seniors from users is distribution: a conditional over a naked type parameter distributes over unions, so `IsString<string | number>` evaluates each member separately (`true | false`) rather than testing the union as a whole. Wrapping the parameter in a tuple (`[T] extends [string]`) opts out when whole-union semantics are what you want. Almost every advanced utility type — `Awaited`, `Parameters`, `Extract` — is a conditional type with a structural test inside.

```typescript
type IsString<T> = T extends string ? true : false;

type A = IsString<string>; // true
type B = IsString<number>; // false

```

**Trade-off**: conditional types let a small amount of type code cover enormous API surface, but nested conditionals compile into error messages humans cannot read — past two levels, prefer overloads or a mapped type if the shape allows it.

### 16. How do you type a generic React component?

**Answer**: The rule the generics serve: the component should be maximally abstract over *what* it renders while staying concrete about *how it renders it*. `Props<T>` ties the `items` array to the `renderItem` callback through one parameter — pass `User[]` and the callback's parameter is `User`, with no assertions anywhere. The failure mode this prevents is real: type the items as `any[]` and the render prop signature decays with them; type the render prop alone and you lose the coupling that makes the component reusable. The render-prop-over-children choice is also type-driven — children cannot carry the per-item type connection.

```typescript
interface Props<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}

function List<T>({ items, renderItem }: Props<T>) {
  return <div>{items.map(renderItem)}</div>;
}

// Usage
<List
  items={["a", "b", "c"]}
  renderItem={(item) => <span>{item}</span>}
/>

```

### 17. What is the `infer` keyword?

**Answer**: Used in conditional types to extract and name a type.

```typescript
type ReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type Fn = () => string;
type Result = ReturnType<Fn>; // string

```

### 18. How do you type a REST API response?

**Answer**: The API response type is a *contract with a remote system you do not control* — so the honest senior answer starts there: any annotation on a fetch result is an assertion, not a guarantee. `response.json()` returns `Promise<any>` by design, so the type comes from somewhere: a hand-written interface (drifts silently when the backend changes), a generated type from the OpenAPI spec (drifts only when the spec lies), or runtime validation that makes the type *earned* rather than assumed. What separates seniors is naming which one is in play — and knowing that `envelope` shapes (`{ data, error, status }`) deserve their own generic so every endpoint's client derives its response type instead of hand-copying fields.

**Answer**:

```typescript
interface ApiResponse<T> {
  data: T;
  status: number;
  message: string;
}

interface PaginatedResponse<T> extends ApiResponse<T[]> {
  total: number;
  page: number;
  limit: number;
}

type UserResponse = ApiResponse<User>;
type UserListResponse = PaginatedResponse<User>;

```

### 19. What are type guards?

**Answer**: Functions that return a type predicate, narrowing the type.

```typescript
function isString(value: unknown): value is string {
  return typeof value === "string";
}

function process(value: unknown) {
  if (isString(value)) {
    value.toUpperCase(); // OK after type guard
  }
}

```

### 20. How do you type a reducer?

**Answer**: A reducer's type IS its design document — `(state: S, action: A) => S` says the only way state changes is via a closed set of actions, and TypeScript enforces that closure. Discriminated-union actions (the `type` field as discriminant) make the switch exhaustive: add an action variant and every reducer that hasn't handled it fails to compile — the type system turning a missed case into a build error instead of a production bug. The pair with `never`-checking in the default branch is the senior finishing move: it proves the *next* maintainer's new action will be caught too, not just today's.

**Answer**:

```typescript
type Action =

  | { type: "INCREMENT"; amount: number }
  | { type: "DECREMENT"; amount: number }
  | { type: "RESET" };

interface State {
  count: number;
}

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "INCREMENT":
      return { count: state.count + action.amount };
    case "DECREMENT":
      return { count: state.count - action.amount };
    case "RESET":
      return { count: 0 };
  }
}

```

## Senior Questions (10)

### 21. How do you implement a type-safe event emitter?

**Answer**: The whole game is binding the event name to its payload type, so `emit("user:created", ...)` *cannot* be called with the wrong shape. `Events extends Record<string, any>` with a mapped lookup (`Events[K]`) does exactly that: the generic `K` is constrained to known event names, and the payload type is derived from the same key. The two senior details: `on` returning an unsubscribe function turns subscription into a disposable resource (no manual `off` bookkeeping), and the `Set<Function>` with the keyed cast inside is the one place the type system is told to trust you — the cast is confined to the implementation, so callers never see it.

**Answer**:

```typescript
type EventMap = {
  "user:created": { userId: string };
  "user:deleted": { userId: string };
};

class TypedEventEmitter<Events extends Record<string, any>> {
  private listeners = new Map<string, Set<Function>>();

  on<K extends keyof Events>(
    event: K,
    listener: (payload: Events[K]) => void
  ): () => void {
    if (!this.listeners.has(event as string)) {
      this.listeners.set(event as string, new Set());
    }
    this.listeners.get(event as string)!.add(listener);

    return () => {
      this.listeners.get(event as string)?.delete(listener);
    };
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    this.listeners.get(event as string)?.forEach((fn) =>
      (fn as (payload: Events[K]) => void)(payload)
    );
  }
}

```

### 22. Design a type-safe state management solution

**Answer**:
The design rests on one map: `ActionMap` binds every action name to its payload type, and everything else is derived — `Action<T>` looks the payload up by key, so `dispatch("user/create", ...)` is checked against the map at the call site. State transitions then live in a reducer whose switch is exhaustive over the map's keys. The discipline this buys is real: adding an action means adding it to the map first, and the compiler walks you through every place that must handle it.


```typescript
type ActionMap = {
  "user/create": { name: string; email: string };
  "user/delete": { userId: string };
};

type Action<T extends keyof ActionMap> = {
  type: T;
  payload: ActionMap[T];
};

function createAction<T extends keyof ActionMap>(
  type: T,
  payload: ActionMap[T]
): Action<T> {
  return { type, payload };
}

function reducer<S, A extends Action<keyof ActionMap>>(
  state: S,
  action: A
): S {
  switch (action.type) {
    case "user/create":
      // TypeScript knows action.payload has name and email
      return state;
    default:
      return state;
  }
}

```

### 23. How do you create a type-safe router?

**Answer**:
The trick is treating the path pattern as a literal type: `"/users/:id"` is not just a string, it is type-level information from which the params type (`{ id: string }`) is derived. A `route()` helper binds pattern to handler, and the handler's props include the parsed params — so a rename of `:id` to `:userId` breaks the handler at compile time instead of at runtime for a user with an unusual link. The cost is that your parsing (regex or the new pattern-matching API) must agree with the literal type; one source of truth for the pattern keeps them honest.


```typescript
type RouteParams<T extends string> =
  T extends `${string}:${infer Param}/${infer Rest}`
    ? { [K in Param | keyof RouteParams<Rest>]: string }
    : T extends `${string}:${infer Param}`
      ? { [K in Param]: string }
      : {};

function createRoute<T extends string>(route: T): { path: T; params: RouteParams<T> } {
  return { path: route } as any;
}

const userRoute = createRoute("/users/:id");
// { path: "/users/:id"; params: { id: string } }

```

### 24. Implement a type-safe curry function

**Answer**:
Currying is where TypeScript's tuple manipulation earns its keep: the type tracks which arguments remain as a tuple (`Args extends unknown[]`), and each returned function consumes the head while the rest type shrinks — until the remaining tuple is empty and the return type appears. Fixed-arity overloads or recursive conditional types both work; the recursive version handles any arity but its error messages are the price. The payoff is at call sites: `curried(a)(b)(c)` is checked at every step, which plain `Function`-typed curry never gives you.


```typescript
type Curry<Args extends any[], Return> =
  Args extends [infer First, ...infer Rest]
    ? Rest extends []
      ? (arg: First) => Return
      : (arg: First) => Curry<Rest, Return>
    : Return;

function curry<Args extends any[], Return>(
  fn: (...args: Args) => Return
): Curry<Args, Return> {
  const arity = fn.length;

  if (arity === 1) {
    return fn as any;
  }

  return (arg: any) =>
    curry((...args: any[]) => fn(arg, ...args)) as any;
}

const add = curry((a: number, b: number, c: number) => a + b + c);
add(1)(2)(3); // 6

```

### 25. How do you type a deep object path?

**Answer**:
The type is a recursion over the object: for each key, emit the dotted path, and if the value is itself an object, recurse and emit `key.child` too. The result is a union of every legal path string, which a `get(obj, path)` function then uses to resolve the *return* type by walking the same recursion backwards. This is the machinery behind lodash's `_.get` typed properly and behind tRPC's client. It is powerful but not free — deep objects make the union explode, and compile time notices.


```typescript
type DeepPropertyAccess<T, Path extends string> =
  Path extends `${infer Head}.${infer Rest}`
    ? Head extends keyof T
      ? DeepPropertyAccess<T[Head], Rest>
      : never
    : Path extends keyof T
      ? T[Path]
      : never;

interface Config {
  database: {
    host: string;
    port: number;
  };
}

type HostType = DeepPropertyAccess<Config, "database.host">; // string

```

### 26. Design a type-safe form validation system

**Answer**:
Two types carry the design: the schema (field names mapped to validators) and the derived errors type, where each field maps to the errors *its* validator can produce. Because the errors type is computed from the schema, a field added without a validator, or a validator without a message type, is a compile error. The runtime side just executes the schema; the type side guarantees the results shape. This is exactly what libraries like Zod formalized — schema as source of truth, types as derived artifacts.


```typescript
type ValidationRule<T> = {
  [K in keyof T]?: {
    required?: boolean;
    minLength?: number;
    maxLength?: number;
    pattern?: RegExp;
    custom?: (value: T[K]) => string | null;
  };
};

type ValidationErrors<T> = {
  [K in keyof T]?: string[];
};

function validate<T extends Record<string, any>>(
  data: T,
  rules: ValidationRule<T>
): ValidationErrors<T> {
  const errors = {} as ValidationErrors<T>;

  for (const key in rules) {
    const value = data[key];
    const rule = rules[key];
    const fieldErrors: string[] = [];

    if (rule?.required && (value === undefined || value === null)) {
      fieldErrors.push(`${key} is required`);
    }

    if (rule?.custom) {
      const error = rule.custom(value);
      if (error) fieldErrors.push(error);
    }

    if (fieldErrors.length > 0) {
      errors[key] = fieldErrors;
    }
  }

  return errors;
}

```

### 27. How do you create a type-safe middleware chain?

**Answer**:
The chain is a series of functions sharing one context type, and the type-safety question is what each middleware may *add* to it. Typing the context as a single mutable object forces casts inside every handler; typing middleware as `<C>(ctx: C, next: Next<C & Added>) => ...` lets the compiler accumulate additions along the chain, so a later handler reading `ctx.user` is guaranteed it exists. Express never gave you this because its types describe the wire, not the pipeline — the chain type describes both.


```typescript
type Middleware<T> = (req: T, next: () => void) => void;

function createMiddlewareChain<T>(
  middlewares: Middleware<T>[]
): (req: T) => void {
  return (req: T) => {
    let index = 0;

    function next(): void {
      if (index < middlewares.length) {
        const middleware = middlewares[index++];
        middleware(req, next);
      }
    }

    next();
  };
}

```

### 28. Implement a type-safe query builder

**Answer**:
The builder's methods each return a *new* type that records what has been accumulated — `.where()` adds to a filter union, `.select()` narrows the row shape — and the terminal `.execute()` derives its result type from the chain. The alternative, mutating `this`, loses the narrowing. The cost is type verbosity per method, but the payoff is that an impossible query (selecting a column after mapping) is unrepresentable rather than a runtime error.


```typescript
interface DatabaseSchema {
  users: { id: string; name: string; email: string };
  posts: { id: string; title: string; authorId: string };
}

type Table = keyof DatabaseSchema;
type Column<T extends Table> = keyof DatabaseSchema[T];

class QueryBuilder<T extends Table> {
  private selectedColumns: Column<T>[] = [];

  select(...columns: Column<T>[]): this {
    this.selectedColumns = columns;
    return this;
  }

  where(condition: string): this {
    return this;
  }

  build(): string {
    return `SELECT ${this.selectedColumns.join(", ")} FROM ${this.table}`;
  }

  constructor(private table: T) {}
}

const query = new QueryBuilder("users")
  .select("id", "name")
  .where("id = '1'");

```

### 29. How do you type a plugin system?

**Answer**:
Plugins are the classic tension: open for extension, closed against breakage. The type answer is an interface the host *consumes* (`Plugin<THooks>`), where the hook map is supplied by the host — a plugin registering `onRender` is checked against the hooks the host actually emits. Keyset checking (`Plugin<Partial<Hooks>>`) lets plugins implement only what they need; the host's side stays total. The failure this prevents is the silent no-op: a plugin hooked to a misspelled event name that never fires and never errors.


```typescript
interface Plugin<T> {
  name: string;
  install: (app: T) => void;
}

class App {
  private plugins: Plugin<App>[] = [];

  use(plugin: Plugin<App>): void {
    this.plugins.push(plugin);
    plugin.install(this);
  }
}

const loggerPlugin: Plugin<App> = {
  name: "logger",
  install: (app) => {
    console.log("Logger installed");
  }
};

```

### 30. Design a type-safe configuration system

**Answer**:
Configuration is where runtime reality (env vars, files) meets compile-time promises, so the design has a seam: a *validated* load step whose output is a precise `AppConfig`, after which everything downstream is typed and total. Parse, don't guess: each field gets a parser with a default, and missing/invalid config fails at boot, not at 3 a.m. in a code path that assumed the optional was present. The type is the contract between ops and code — the loaders are how it is enforced.


```typescript
type ConfigSchema = {
  database: {
    host: string;
    port: number;
    credentials: {
      user: string;
      password: string;
    };
  };
  server: {
    port: number;
    ssl: boolean;
  };
};

type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};

function createConfig(defaults: ConfigSchema): DeepPartial<ConfigSchema> {
  return defaults;
}

const config = createConfig({
  database: {
    host: "localhost",
    port: 5432,
    credentials: {
      user: "admin",
      password: "secret"
    }
  },
  server: {
    port: 3000,
    ssl: false
  }
});

```

## FAANG-style Questions (10)

### 31. Design a type-safe API client

**Answer**:
One endpoint map drives everything: method, path params, query, request body, and response are all keyed off it, so `client.getUser({ id })` has its arguments and return type derived from the same table the routes are generated from. When the map is generated from OpenAPI, backend and frontend share one artifact and drift becomes a compile error. Hand-rolling the map is the same idea with more trust placed in the author — the type structure is identical.


```typescript
interface ApiEndpoints {
  "/users": {
    GET: { response: User[] };
    POST: { body: CreateUserDTO; response: User };
  };
  "/users/:id": {
    GET: { response: User };
    PUT: { body: UpdateUserDTO; response: User };
    DELETE: { response: void };
  };
}

type Method = "GET" | "POST" | "PUT" | "DELETE";

class ApiClient {
  async request<
    Path extends keyof ApiEndpoints,
    M extends keyof ApiEndpoints[Path]
  >(
    path: Path,
    method: M,
    options?: { body?: any }
  ): Promise<any> {
    const response = await fetch(path, {
      method: method as string,
      body: options?.body ? JSON.stringify(options.body) : undefined,
      headers: { "Content-Type": "application/json" }
    });
    return response.json();
  }
}

const api = new ApiClient();
const users = await api.request("/users", "GET");

```

### 32. Implement a type-safe state machine

**Answer**:
The states are a union, the transitions are a map from `state + event` to the next state, and the type system's contribution is that `send` accepts only legal (state, event) pairs — an impossible transition simply does not compile. This is XState's core insight expressed in plain generics. The explicit transition table is more code than a `switch`, but it converts 'what happens if this event arrives while we are in that state?' from a design-review question into a lookup.


```typescript
type StateMap = {
  idle: { events: { FETCH: "loading" } };
  loading: { events: { SUCCESS: "success"; ERROR: "error" } };
  success: { events: { RESET: "idle" } };
  error: { events: { RETRY: "loading"; RESET: "idle" } };
};

type State = keyof StateMap;
type Event<S extends State> = keyof StateMap[S]["events"];

class StateMachine<S extends State> {
  constructor(private state: S) {}

  transition<E extends Event<S>>(event: E): StateMap[S]["events"][E] {
    return this.state as any;
  }
}

const machine = new StateMachine<"idle">("idle");
const next = machine.transition("FETCH"); // "loading"

```

### 33. Design a type-safe ORM

**Answer**:
The schema is the source of truth: table definitions carry column types, and everything else — entity types, insert payloads (required vs generated columns), query results, join shapes — is derived. `select` narrowing the result to chosen columns is the same mapped-type trick as the query builder, applied to relations. The hard part is not the happy path; it is keeping migrations and types generated from the same schema so drift cannot start. Every serious ORM (Prisma, Drizzle) is this design plus codegen.


```typescript
interface Model {
  id: string;
  createdAt: Date;
  updatedAt: Date;
}

interface User extends Model {
  name: string;
  email: string;
}

class Repository<T extends Model> {
  async findById(id: string): Promise<T | null> {
    return null;
  }

  async findMany(where: Partial<T>): Promise<T[]> {
    return [];
  }

  async create(data: Omit<T, "id" | "createdAt" | "updatedAt">): Promise<T> {
    return data as T;
  }
}

const userRepo = new Repository<User>();
const user = await userRepo.findById("1");

```

### 34. Implement a type-safe middleware system

**Answer**:
Where the composed chain (Q27) accumulates context, a middleware *system* also needs ordered registration and typed removal. `use()` accepts the context-so-far type and returns a deregistration function; ordering rules that matter (auth before handlers) are enforced by parameterizing `use` on what the context must already contain — a handler requiring `ctx.user` simply cannot be registered before the middleware that adds it. Ordering bugs become compile errors.


```typescript
type Context = {
  req: Request;
  res: Response;
  state: Record<string, any>;
};

type Middleware = (ctx: Context, next: () => Promise<void>) => Promise<void>;

function createRouter() {
  const middlewares: Middleware[] = [];

  return {
    use(middleware: Middleware) {
      middlewares.push(middleware);
      return this;
    },

    async handle(ctx: Context) {
      let index = 0;

      async function next(): Promise<void> {
        if (index < middlewares.length) {
          const middleware = middlewares[index++];
          await middleware(ctx, next);
        }
      }

      await next();
    }
  };
}

```

### 35. Design a type-safe validation library

**Answer**:
The schema object is dual-purpose: at runtime it validates, at compile time `typeof schema` (via `z.infer`-style machinery) yields the parsed type. The design rule is that the *parsed* type is what the rest of the app sees — the input type (with optional/coerced fields) and output type (with defaults applied) are deliberately different, and the library makes that difference expressible. Brands on parsed values (e.g. `Email` vs `string`) stop unvalidated strings from flowing into validated code paths.


```typescript
type Validator<T> = {
  [K in keyof T]?: (value: any) => string | null;
};

type ValidationErrors<T> = {
  [K in keyof T]?: string[];
};

function validate<T extends Record<string, any>>(
  data: T,
  validators: Validator<T>
): { valid: boolean; errors: ValidationErrors<T> } {
  const errors: ValidationErrors<T> = {};
  let valid = true;

  for (const key in validators) {
    const validator = validators[key];
    if (validator) {
      const error = validator(data[key]);
      if (error) {
        errors[key] = [error];
        valid = false;
      }
    }
  }

  return { valid, errors };
}

```

### 36. Implement a type-safe event system

**Answer**:
Where the emitter (Q21) binds names to payloads, a full event system also binds *handlers* to unsubscribe contracts and supports derived subscriptions. The type core is the same handler map, but the design adds cleanup: every `on` returns a typed unsubscribe, and `once` is expressible because the wrapper preserves the payload type. The discipline to enforce is that no module holds a reference that outlives its owner's teardown — the unsubscribe-returning API makes the correct pattern the easy one.


```typescript
type EventMap = {
  "user:created": { userId: string };
  "order:placed": { orderId: string; amount: number };
};

class TypedEventEmitter<Events extends Record<string, any>> {
  private listeners = new Map<string, Set<Function>>();

  on<K extends keyof Events>(
    event: K,
    listener: (payload: Events[K]) => void
  ): () => void {
    if (!this.listeners.has(event as string)) {
      this.listeners.set(event as string, new Set());
    }
    this.listeners.get(event as string)!.add(listener);

    return () => {
      this.listeners.get(event as string)?.delete(listener);
    };
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    this.listeners.get(event as string)?.forEach((fn) =>
      (fn as (payload: Events[K]) => void)(payload)
    );
  }
}

```

### 37. Design a type-safe dependency injection container

**Answer**:
String-keyed containers are `any` factories; the fix is injection *tokens* that carry their type — `const UserService = new Token<UserService>()` — so `resolve(UserService)` returns what the token says. The container is a map from token identity to instance; generics make the token the type witness. The cost over string keys is a token definition per service; the payoff is that a rename or a changed constructor signature surfaces at every resolve site, not in production wiring.


```typescript
type Constructor<T = {}> = new (...args: any[]) => T;

class Container {
  private services = new Map<string, any>();

  register<T>(name: string, constructor: Constructor<T>): void {
    this.services.set(name, new constructor());
  }

  resolve<T>(name: string): T {
    return this.services.get(name) as T;
  }
}

class DatabaseService {
  query(sql: string): any[] {
    return [];
  }
}

const container = new Container();
container.register("database", DatabaseService);
const db = container.resolve<DatabaseService>("database");

```

### 38. Implement a type-safe plugin system

**Answer**:
The implementation detail missing from the type design (Q29) is registration lifecycle: `register(plugin)` validates hook shapes against the host's hook map, stores them keyed by name, and `emit` walks them with the payload type resolved from the same map. The casts live in exactly two places — the registry's internal storage — and nowhere in plugin code. The result is that plugin authors get checking against the host's real API while the host gets runtime flexibility.


```typescript
interface Plugin<T> {
  name: string;
  version: string;
  install: (app: T) => void;
}

class App {
  private plugins: Plugin<App>[] = [];

  use(plugin: Plugin<App>): void {
    this.plugins.push(plugin);
    plugin.install(this);
  }

  getPlugin(name: string): Plugin<App> | undefined {
    return this.plugins.find((p) => p.name === name);
  }
}

const loggerPlugin: Plugin<App> = {
  name: "logger",
  version: "1.0.0",
  install: (app) => {
    console.log("Logger plugin installed");
  }
};

```

### 39. Design a type-safe configuration system

**Answer**:
Layering is the design problem the single-file config (Q30) does not have: defaults < file < env < flags, each layer partial, merged into the total config. The types make the layers' roles explicit — each source is `DeepPartial<AppConfig>`, and only the merged result is `AppConfig`. The deep-merge function is the one place that must be correct (a wrong merge is a type lie), which argues for generating it or testing it exhaustively rather than hand-rolling per project.


```typescript
type ConfigSchema = {
  database: {
    host: string;
    port: number;
  };
  server: {
    port: number;
  };
};

type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};

class ConfigManager<T extends Record<string, any>> {
  private config: T;

  constructor(defaults: T) {
    this.config = defaults;
  }

  get<K extends keyof T>(key: K): T[K] {
    return this.config[key];
  }

  set<K extends keyof T>(key: K, value: T[K]): void {
    this.config[key] = value;
  }

  merge(overrides: DeepPartial<T>): void {
    this.config = { ...this.config, ...overrides } as T;
  }
}

```

### 40. Implement a type-safe query builder

**Answer**:
The implementation shape: each builder method returns a new class instance whose type parameters record the accumulated state — table, selected columns, filters, order. TypeScript's immutable-style generics make the chain itself the type: `select("name").where(...)` produces a type that `.execute()` maps to `Promise<{ name: string }[]>`. The reason to return new instances rather than mutate `this` is exactly that the *old* builder stays typed for reuse — and the reason ORM-style builders feel magical is that they are this pattern with codegen on top.


```typescript
interface DatabaseSchema {
  users: { id: string; name: string; email: string };
  posts: { id: string; title: string; authorId: string };
}

type Table = keyof DatabaseSchema;
type Column<T extends Table> = keyof DatabaseSchema[T];

class QueryBuilder<T extends Table> {
  private selectedColumns: Column<T>[] = [];
  private whereCondition: string = "";

  constructor(private table: T) {}

  select(...columns: Column<T>[]): this {
    this.selectedColumns = columns;
    return this;
  }

  where(condition: string): this {
    this.whereCondition = condition;
    return this;
  }

  build(): string {
    const columns = this.selectedColumns.join(", ");
    let query = `SELECT ${columns} FROM ${this.table}`;
    if (this.whereCondition) {
      query += ` WHERE ${this.whereCondition}`;
    }
    return query;
  }
}

const query = new QueryBuilder("users")
  .select("id", "name")
  .where("id = '1'")
  .build();

```

### 47. How do you type a WebSocket connection?

**Answer**:
The wire protocol is a closed set of message shapes, so type it like one: a union (or map) of message types with a discriminant, separate maps for client-to-server and server-to-client. `send` then accepts only known message types, and `onMessage` narrows via the discriminant before handling. Without this, a socket handler is a `JSON.parse` away from `any` at the boundary — the one place in the app where the data is *least* trustworthy and the types are usually *absent*. Closing that gap is the senior move.


```typescript
interface WebSocketMessage {
  type: string;
  payload: any;
}

class TypedWebSocket {
  constructor(private ws: WebSocket) {}

  send<T extends WebSocketMessage>(message: T): void {
    this.ws.send(JSON.stringify(message));
  }

  on<T extends WebSocketMessage>(
    callback: (message: T) => void
  ): void {
    this.ws.onmessage = (event) => {
      callback(JSON.parse(event.data));
    };
  }
}

```

### 49. How do you handle async/await with TypeScript?

**Answer**:
The language rules first: `async` functions always return `Promise<T>` (the annotation unwraps), `await` flattens nested promises (`Promise<Promise<T>>` is just `Promise<T>`), and rejected paths are untyped by default — `catch` gives you `unknown` since 4.4, deliberately. The senior patterns follow from that last point: either type errors explicitly via discriminated result objects (`{ ok: true, value } | { ok: false, error }`), or validate in the catch. `Promise.all` loses per-promise errors (all-or-nothing); `allSettled` keeps them, and its discriminated result type is why.


```typescript
async function fetchData<T>(url: string): Promise<T> {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`HTTP error! status: ${response.status}`);
  }
  return response.json() as Promise<T>;
}

// Usage
const user = await fetchData<User>("/api/users/1");

```

# Virtual DOM

Type `"rea"` into a controlled React `<input>`. Your component function runs again on every single keystroke and returns brand-new JSX — yet the browser does **not** destroy the `<input>`, lose focus, or reset your cursor. That happens because JSX creates lightweight UI *descriptions*, and React compares each new description against its retained tree so it only patches the real DOM nodes that actually changed.

```jsx
function SearchBox({ query, onChange }) {
  return <input value={query} onChange={onChange} />;
}
// Keystroke 1 ("r") -> new element object { type: 'input', props: { value: 'r', ... } }
// Keystroke 2 ("re") -> new element object { type: 'input', props: { value: 're', ... } }
// React keeps the SAME browser <input> node and only updates input.value = 're'.
```

## Definition

The **Virtual DOM (VDOM)** is an informal name for the in-memory UI descriptions React builds when calculating an update. Each render produces **React elements** — plain JavaScript objects describing the element type, props, `key`, and children you want on screen. React compares those descriptions against its retained internal tree (**Fibers**), computes the required changes, and applies only those updates to the real browser DOM during the commit phase.

> **Textbook Definition:** A virtual DOM is an in-memory representation of a desired user interface that a renderer reconciles against its retained tree before applying changes to the host environment. In React, the term is conceptual shorthand rather than a public API or a persistent clone of the browser DOM.

## First Principles

In imperative UI code (like raw `document.createElement` and `element.classList`), your code must manually update every affected DOM node for every state transition. If a screen has $N$ possible UI states, keeping every transition consistent requires tracking up to $N^2$ edge cases — forgetting one leaves stale text, orphan listeners, or broken focus.

React removes manual transition wiring by letting you describe the whole target UI as a pure function of state (`UI = f(state)`). Because rebuilding the entire browser DOM on every state change would destroy input focus, scroll position, and performance, React introduces a cheap intermediate step: build plain JavaScript descriptions first, diff them against what is already mounted, and mutate only the changed host nodes.

## 1. What JSX Actually Creates: Plain JavaScript Objects

JSX is syntax sugar, not HTML. Your bundler compiles `<input value={query} onChange={onChange} />` into a function call (`jsx()` in the modern JSX transform, or `React.createElement()` in older code) that returns a plain, frozen JavaScript object:

```javascript
// excerpt — simplified shape of a React element produced by jsx()
const element = {
  $$typeof: Symbol.for('react.transitional.element'), // internal tag preventing raw JSON XSS
  type: 'input',                                      // string for host tag, function/class for components
  key: null,                                          // optional identity hint among siblings
  props: {
    value: 're',
    onChange: () => {},
  },
};
```

Creating this object allocates almost no memory and touches **zero** browser DOM APIs. A real `HTMLInputElement` carries hundreds of properties, layout state, event targets, and C++ browser bindings; a React element is just a tiny blueprint that is discarded as soon as React finishes comparing it. That `$$typeof` field also closes a subtle XSS vector: `JSON.parse` can produce plain `{ type, props }` objects from untrusted server data, but JSON cannot represent a JavaScript `Symbol`, so React rejects any object lacking `Symbol.for('react.transitional.element')` (or `Symbol.for('react.element')` in React 18 and earlier).

## 2. Three Separate Layers: Element, Fiber, and DOM Node

Many bugs and interview misconceptions come from collapsing React's internals into "the Virtual DOM." React actually operates across three distinct layers:

```text
Render runs component()
       │
       ▼
1. React Element  ──► Throwaway JS object describing desired UI ({ type, key, props })
       │
       ▼  reconciled against
2. Fiber Node     ──► Persistent internal record holding identity, hook state & pending work
       │
       ▼  commits minimal mutations to
3. Host DOM Node  ──► Real browser object (<input>, <div>) owned by the document
```

| Layer | Lifetime | What it holds |
| ----------------- | ---------------------------------------------- | ------------------------------------------------------------------------ |
| **React element** | Created fresh on every render; short-lived | `type`, `key`, `props`, `children` (desired UI) |
| **Fiber** | Persists across renders while identity matches | Component instance, hooks state, parent and child pointers, effect flags |
| **DOM node** | Owned by the browser until unmounted | Live element, focus, cursor selection, scroll offset, layout geometry |

Notice two immediate consequences:
- **Neither an element nor a Fiber is a DOM node.** React Native, React Three Fiber, and terminal renderers reuse the exact same element-and-Fiber model while committing to native mobile views or WebGL objects instead of a browser DOM.
- **A component can re-render with zero DOM changes.** Your component function runs and returns new React elements, React compares them to the current Fiber tree, sees identical output, and performs **zero** DOM writes.

See [Fiber](10.3.1.02-fiber.md) for how React schedules and interrupts work across Fiber trees.

## 3. Step-by-Step Trace: When React Reuses vs. Replaces a Node

During reconciliation, React walks the previous Fiber tree and the new React elements together. Two rules decide whether an existing DOM node (and component state) survives:

### Case A — Same `type` at the same position: Reuse and patch

```jsx
// excerpt — Render 1 vs. Render 2 comparison
const render1 = (
  <div className="banner">
    <input value="r" onChange={onChange} />
  </div>
);

const render2 = (
  <div className="banner active">
    <input value="re" onChange={onChange} />
  </div>
);
```

1. The outer `div` keeps its tag across renders, so React patches `className` in place instead of replacing the container.
2. Inside it, the `<input>` stays mounted while only its `value` property changes — preserving browser focus and caret position.

### Case B — Different `type` at the same position: Unmount and remount

```jsx
// excerpt — Render 1 vs. Render 2 comparison
const render1 = <div><Counter /></div>;
const render2 = <section><Counter /></section>;
```

Because `div` changed to `section`, React tears down the entire old subtree — running cleanup effects, destroying the old `<Counter />` state, and removing its DOM nodes — then mounts a brand-new `<section>` and a fresh `<Counter />` starting at its initial state.

### Case C — Reordered siblings: `key` preserves identity

When rendering lists, position alone is not enough. If you insert a new item at index `0` and use the array index as `key`, React matches old index `0` to new index `0` — attaching the first item's local state (such as a typed draft or checkbox) to the wrong record.

Assigning a stable record ID (`key={item.id}`) tells React which sibling Fiber matches which record across renders. **Boundary:** `key` preserves identity and state among siblings under the same parent; it does **not** by itself skip re-rendering that child component.

## 4. Why React Uses a Heuristic Diff Instead of an Optimal One

Finding the mathematically smallest edit sequence between two arbitrary trees takes $O(n^3)$ time — for 1,000 elements, that is roughly a billion comparisons per update, which would freeze the browser.

React trades theoretical optimality for predictable linear-time $O(n)$ matching using two heuristics:
1. Two elements with different `type` values produce different subtrees (do not search deep inside for movable matches).
2. Sibling elements in a list can be matched across renders via a stable `key`.

Because this is a heuristic, React does **not** guarantee the absolute minimum number of DOM operations in every edge case (for example, moving a component from one parent container to another unmounts and remounts it rather than relocating the DOM node). See [Reconciliation](10.3.1.03-reconciliation.md) for the full matching rules.

## 5. The Performance Myth: Virtual DOM Is Not "Faster Than the DOM"

A common interview trap is claiming *"React is fast because the Virtual DOM is faster than the real DOM."* That statement is false: React **still uses the real DOM**, and it adds JavaScript overhead on top of every update. Carefully written imperative DOM code that directly mutates one text node will almost always beat a full React render pass in raw microbenchmarks.

What React actually buys you is **predictable, maintainable updates that are fast enough by default** without manually tracking every DOM mutation. When an interaction is slow, measure three separate cost buckets rather than guessing:

1. **Render & reconciliation cost (JavaScript):** When one metric changes in a parent `<Dashboard />`, React re-executes `<Dashboard />` and its ordinary child component functions by default — even if you pass stable callback props (`useCallback`). Stable references only help when an identity-checking boundary such as `React.memo` (or automatic memoization via the React Compiler) sits in front of the child, or when passing an already-created subtree through `{children}` lets React keep the exact same element object reference and bail out of re-rendering that subtree.
2. **Commit cost (DOM mutations):** Applying the minimal set of host insertions, deletions, and attribute patches.
3. **Browser rendering cost:** Style recalculation, layout (reflow), paint, and compositing triggered by those DOM changes.

To compare direct DOM code against React honestly, profile the same interaction on comparable hardware and separate JavaScript render time, commit time, and browser layout and paint time — never quote universal millisecond rules.

## Summary

React's "Virtual DOM" refers to lightweight, throwaway React element objects that describe desired UI output, reconciled against persistent internal Fiber nodes before minimal mutations are committed to the real browser DOM. Matching by `type`, position, and stable sibling `key` lets React reuse existing DOM nodes and component state in linear time without solving an $O(n^3)$ optimal tree-edit problem. A component can re-render without touching the DOM when output is unchanged, and the Virtual DOM is not inherently faster than direct DOM manipulation — its real value is declarative UI consistency, while performance tuning requires measuring JS render work, commit work, and browser layout and paint separately.

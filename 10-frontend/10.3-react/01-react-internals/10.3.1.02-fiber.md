# React Fiber

Before React 16, React relied on what is now called the **Stack Reconciler**. When a state update occurred, React recursively traversed the virtual component tree using standard JavaScript function calls. Once that recursive execution began, it was impossible to interrupt: the native call stack ran synchronously until every single component in the tree was evaluated.

If an application had a large or deeply nested component tree, this synchronous reconciliation took 50ms, 100ms, or longer. During that entire window, the browser main thread was completely blocked: keystrokes lagged, touch gestures dropped, 60fps animations stuttered, and the interface froze.

To eliminate this fundamental bottleneck, the React core team spent years completely re-engineering React's internal reconciliation engine from the ground up.

The result was **React Fiber**.

Fiber reimagined the execution stack as an in-memory, heap-allocated linked list of 'virtual stack frames'. Instead of letting the browser's synchronous call stack control rendering, React became its own cooperative multitasking scheduler: it can compute a unit of component work, pause execution when the frame budget expires, yield the main thread back to the browser to handle high-priority user input or animations, and then resume, restart, or abandon background work.

Mastering Fiber means understanding the anatomical structure of a Fiber node (`child`, `sibling`, `return`), how the **Double Buffering** pattern guarantees visual consistency, and how the cooperative Render phase cleanly separates from the synchronous, un-interruptible Commit phase.

## Definition

**React Fiber** is React's internal architecture for tracking and updating its component tree. Introduced in React 16, it replaced the earlier stack-based **reconciler**, the mechanism that matches new elements to the existing tree. Fiber divides eligible rendering work into units, so React can pause between units, continue later and prioritize urgent updates. This is **incremental rendering**. You do not call Fiber directly; it supports React's rendering and scheduling features.

Fiber represents each component as a **fiber node** (a JavaScript object) containing the component's state, props, effects, and scheduling information. The collection forms a **fiber tree**, distinct from the element objects returned by JSX. Elements describe requested UI; fibers retain component identity, Hook state and pending work between renders.

> **Textbook Definition:** Fiber is React's internal representation of component work and retained state. Linked work records let the renderer schedule and revisit units of rendering before committing a completed result; interruption occurs at React's work boundaries.

## First Principles

1. **A long JavaScript call stack blocks the main thread until it returns.** To yield between components, React must store traversal progress outside that stack. Fiber records links and pending work so the renderer can stop between work units and later resume or restart; one indivisible component calculation can still block.
2. **The displayed tree must stay coherent while another tree is prepared.** Current and work-in-progress records separate committed identity/state from a candidate result. Render-phase changes therefore cannot perform external side effects that would survive even if the candidate were abandoned.
3. **Urgent work may arrive before preparation finishes.** Scheduling metadata lets React choose which updates to process next and interrupt eligible rendering. Commit applies the chosen result synchronously; priorities redistribute preparation time rather than making DOM mutation or arbitrary JavaScript interruptible.

## Why It Matters

Fiber supplies internal machinery for scheduling eligible render work between units. Public APIs such as Transitions can mark non-urgent updates, but a component function and the commit still run synchronously. Suspense coordinates fallbacks for work that actually suspends—such as lazy code or a framework-supported data source; fetching inside an Effect does not activate a boundary by itself.

## The Problem It Solves

### The Problem with the Stack Reconciler

The previous reconciler (React 15 and earlier) was synchronous and non-interruptible:

1. **Main thread blocking**: Once React started rendering, it couldn't be interrupted. Long component trees would block the main thread.

2. **No yield-based scheduling**: The active reconciliation pass could not pause so React could service newer urgent work. Updates could be batched, but batching did not make a running tree walk interruptible.

3. **Janky animations**: Long renders caused frame drops, making animations janky.

4. **No pause/resume**: React couldn't pause rendering to handle urgent events.

```text
Synchronous preparation: work → work → work → commit → browser handles input
Eligible concurrent preparation: work → yield → input → resume/restart → commit
```

A yield returns control to the host so browser work can run. The number of components per slice and the elapsed time are workload-dependent. Fiber is necessary bookkeeping for this scheduling, but does not make every update concurrent.

## How It Works

### Fiber Node Structure

Each fiber node contains:

```typescript
interface FiberNode {
  // Instance properties
  tag: WorkTag; // Component type (FunctionComponent, ClassComponent, HostComponent, etc.)
  key: string | null; // React key
  type: any; // Component function/class or string (div, span, etc.)
  stateNode: any; // Reference to DOM node or class instance

  // Tree structure (linked list)
  return: FiberNode | null; // Parent fiber
  child: FiberNode | null; // First child fiber
  sibling: FiberNode | null; // Next sibling fiber
  index: number; // Child index

  // Pending work
  pendingProps: any; // Props being received
  memoizedProps: any; // Props from last render
  memoizedState: any; // State from last render
  updateQueue: UpdateQueue<any> | null; // Pending state updates

  // Effects
  flags: Flags; // Side effect tags (Placement, Update, Deletion, etc.)
  subtreeFlags: Flags; // Combined flags from subtree
  deletions: FiberNode[] | null; // Fibers to delete

  // Scheduling
  lanes: Lanes; // Priority lanes (pending work)
  childLanes: Lanes; // Child's pending work
  alternate: FiberNode | null; // Reference to the other tree (current vs work-in-progress)

  // This is a partial internal model, not a public API.
  // Function-component effect records are maintained through Hook state
  // and the component update queue, not separate fields for each effect type.
}

```

### Follow child, sibling and parent links

A fiber tree is encoded through linked records. It is still a tree: `child` points to the first child, `sibling` to the next child of the same parent, and `return` back to that parent.

```text
Logical tree                  Selected links
App                           App.child = Header
├─ Header                     Header.return = App
│  ├─ Logo                    Header.child = Logo
│  └─ Nav                     Logo.sibling = Nav; Nav.return = Header
└─ Main                       Header.sibling = Main; Main.return = App
```

Begin work visits App, Header, Logo, Nav, then Main in this simplified depth-first trace. Logo has no child, so it completes and its sibling Nav is selected. Nav has no sibling, so completion returns to Header; Header's sibling Main is the next work item. After Main completes, completion returns to App. Completion bubbles prepared results upward; it is not a second independent render of those components.

A real component may produce several work records, and an application component's parent is a root work record. The simplified App root above shows traversal only.

### Work Loop

The Fiber work loop processes fibers in a depth-first traversal. The sketch uses `requestIdleCallback` only to illustrate yielding; React uses its own scheduler and does not require that browser API. It can yield between units of work, but cannot interrupt a running component function or arbitrary synchronous loop:

```typescript
// Work Loop Algorithm (teaching pseudocode, not React source):

function workLoop(deadline) {
  // Continue working while there's time remaining in the frame
  while (nextUnitOfWork && deadline.timeRemaining() > 1) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }

  if (nextUnitOfWork) {
    // Not done yet, yield to browser and continue next frame
    requestIdleCallback(workLoop);
  } else {
    // All work done, commit to DOM
    commitRoot();
  }
}

function performUnitOfWork(fiber) {
  // 1. Begin phase: Process current fiber
  beginWork(fiber);

  // 2. If fiber has child, return child
  if (fiber.child) {
    return fiber.child;
  }

  // 3. Complete phase: Go up the tree
  let current = fiber;
  while (current) {
    completeWork(current);

    if (current.sibling) {
      return current.sibling;
    }
    current = current.return;
  }

  return null;
}

```

### Two-Phase Rendering

Both begin-work and complete-work belong to the render phase. Complete-work may prepare detached DOM nodes and mutation flags, but the currently displayed tree is changed during commit. The current/work-in-progress pair (linked by `alternate`) lets React abandon an unfinished render while the last committed UI remains usable. Scheduling is cooperative, so the example frame durations above are illustrative, not a guaranteed budget.

```text
Render: begin work → visit children → complete work and collect host-change flags
Commit: before-mutation reads → host mutations → layout work
Passive effects: scheduled for a separate flush after the accepted commit
```

These arrows show responsibilities, not a promise about how many times render runs or when the browser paints relative to passive effects.

### Priority Lanes

Lanes are internal bitmasks used to track pending work and select which updates a render processes. They are not an application-level enum, and their names and bit positions can change between React versions.

Discrete interactions and explicit synchronous flushes require urgent work; continuous interactions, ordinary updates, transitions and idle work have different scheduling needs. `startTransition` marks its state updates as non-blocking; the priority of a plain setter depends on the event/scheduling context rather than always being the default lane. Several lanes may be processed together, so there is no fixed “one lane per frame” sequence.

## Code Examples

### Understanding Fiber Internals

React DevTools presents the component tree. A fiber also has an internal work tag distinguishing functions, classes, host nodes, Suspense boundaries and other kinds of work. Numeric tag values are private implementation details; use the tools' component names instead of relying on a copied enum.

### Demonstrating Concurrent Rendering

```typescript
import React, { memo, useState, useTransition } from 'react';

type Item = { id: string; name: string };
const Results = memo(function Results({ items, query }: { items: Item[]; query: string }) {
  const filtered = items.filter(item => item.name.includes(query));
  return <ul>{filtered.map(item => <li key={item.id}>{item.name}</li>)}</ul>;
});

const SearchApp = ({ items }: { items: Item[] }) => {
  const [query, setQuery] = useState('');
  const [resultsQuery, setResultsQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  const handleSearch = (e: React.ChangeEvent<HTMLInputElement>) => {
    const value = e.target.value;
    setQuery(value); // Controlled input remains urgent.
    startTransition(() => setResultsQuery(value));
  };

  return (
    <div>
      <input value={query} onChange={handleSearch} />
      {isPending && <span>Updating results...</span>}
      <Results items={items} query={resultsQuery} />
    </div>
  );
};
```

For example, type `a`, then `ab` before the first results render commits. The controlled input can show `ab` while the previously committed results remain visible. React can abandon the obsolete `a` attempt and prepare `ab`; `isPending` describes the outstanding transition, not a network request counter.

The transition callback executes immediately. Only the state update changes scheduling; putting `filterData(value)` inside that callback would still block the event handler. Moving the calculation into the results render lets React schedule that render separately, but one long filter remains synchronous; use a worker or smaller work units for truly expensive computation.

### Demonstrating Time Slicing

```typescript
import React, { useState, useEffect, useTransition } from 'react';

const LargeList = () => {
  const [items, setItems] = useState<Item[]>([]);
  const [isPending, startTransition] = useTransition();

  useEffect(() => {
    // Fetch large dataset
    fetchLargeDataset().then(data => {
      startTransition(() => {
        // This update can be interrupted
        // Eligible render work can yield; the component calculation itself cannot be preempted.
        setItems(data);
      });
    });
  }, []);

  return (
    <div>
      {isPending && <div>Updating list...</div>}
      <VirtualList items={items} />
    </div>
  );
};

```

### useTransition vs useDeferredValue

```typescript
import React, { useState, useTransition, useDeferredValue } from 'react';

// useTransition: Mark state updates as non-urgent
const TransitionExample = () => {
  const [isPending, startTransition] = useTransition();
  const [count, setCount] = useState(0);

  const handleClick = () => {
    startTransition(() => {
      // This update is low priority
      // React can defer it if there's urgent work
      setCount(c => c + 1);
    });
  };

  return <button onClick={handleClick}>{count} {isPending && '...'}</button>;
};

// useDeferredValue: Defer a derived value
const DeferredValueExample = () => {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <div>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <div style={{ opacity: isStale ? 0.5 : 1 }}>
        <Results query={deferredQuery} />
      </div>
    </div>
  );
};

```

### Concurrent Features in Action

```typescript
import React, { useState, useTransition, Suspense } from 'react';

// `loadSuspenseResource` is supplied by a framework or cached data layer.
// It returns a stable resource whose read operation suspends while loading.
const ConcurrentApp = () => {
  const [resource, setResource] = useState(initialResource);
  const [isPending, startTransition] = useTransition();

  const handleTabChange = (tab: string) => {
    const nextResource = loadSuspenseResource(tab);
    startTransition(() => {
      // This state update is non-urgent
      // React keeps old UI visible while preparing new one
      setResource(nextResource);
    });
  };

  return (
    <div>
      <TabBar onChange={handleTabChange} />
      {/* isPending shows loading state for the transition */}
      {isPending && <Spinner />}
      <Suspense fallback={<Loading />}>
        <ResourcePanel resource={resource} />
      </Suspense>
    </div>
  );
};

```

The `Suspense` boundary only shows its fallback if `ResourcePanel` reads from a source that suspends during render. A raw `fetch()` started in an event handler or Effect does not gain Suspense behavior merely because the result is stored inside a Transition.

## Real-World Use Cases

### 1. Search with Large Dataset

> [Demonstrating Concurrent Rendering](#demonstrating-concurrent-rendering) contains the urgent-input / deferred-results example. For a dataset whose filter alone blocks input, move that calculation into a worker; transition scheduling cannot preempt a JavaScript function midway through execution.

### 2. Tab Switching with Heavy Content

```typescript
const TabContainer = () => {
  const [activeTab, setActiveTab] = useState('overview');
  const [isPending, startTransition] = useTransition();

  const handleTabSwitch = (tab: string) => {
    startTransition(() => {
      setActiveTab(tab); // Non-urgent: React can defer
    });
  };

  return (
    <div>
      <TabBar
        tabs={['overview', 'details', 'reviews']}
        active={activeTab}
        onChange={handleTabSwitch}
      />
      {isPending && <TabSpinner />}
      <TabContent tab={activeTab} />
    </div>
  );
};

```

### 3. Live Feed with Non-Urgent Updates

```typescript
const AnimatedList = () => {
  const [items, setItems] = useState<Item[]>([]);
  const [isPending, startTransition] = useTransition();

  useEffect(() => {
    // Keep input handling separate from the larger list update.
    // The transition does not schedule animation frames.
    const unsubscribe = subscribeToData(newItems => {
      startTransition(() => {
        setItems(newItems);
      });
    });
    return unsubscribe;
  }, []);

  return (
    <div>
      {items.map(item => (
        <AnimatedItem key={item.id} item={item} isPending={isPending} />
      ))}
    </div>
  );
};

```

### 4. Server-Side Rendering with Streaming

Streaming uses React's separate server renderer, not the client Fiber work loop. Suspense-ready sources can stream later chunks; fetching data in a client effect alone does not suspend rendering or activate streaming. The shared App below must produce matching server and client markup.

```typescript
// Shared App tree for streaming server rendering (simplified).
const App = () => (
  <html>
    <body>
      <Suspense fallback={<Loading />}>
        <Header /> {/* Renders immediately */}
      </Suspense>
      <Suspense fallback={<Loading />}>
        <SlowComponent /> {/* Streams when ready */}
      </Suspense>
    </body>
  </html>
);

// Client hydration (simplified)
import { hydrateRoot } from 'react-dom/client';
// App renders <html>, so hydrate the document, matching the server output.
const root = hydrateRoot(document, <App />);
// Suspense supports selective hydration; there is no onHydrated root option.

```

## Common Mistakes

### 1. Confusing Fiber with Feature

```typescript
// WRONG: "I'll use Fiber to make my app faster"
// Fiber is internal architecture, not a feature you use directly

// CORRECT: Use concurrent features that Fiber enables
const App = () => {
  const [isPending, startTransition] = useTransition();
  // ...
};

```

### 2. Assuming All Updates Are Low Priority

```typescript
// WRONG: Wrapping everything in startTransition
const handleClick = () => {
  startTransition(() => {
    setIsOpen(true); // This should be HIGH priority (user interaction)
  });
};

// CORRECT: Only use startTransition for non-urgent updates
const handleSearch = (value: string) => {
  setSearchQuery(value); // Urgent: update input immediately

  startTransition(() => {
    setResultsQuery(value); // Non-urgent: results read this in their render
  });
};

```

### 3. Misunderstanding `useDeferredValue`

Deferring a value does not delay the calculation that already produced it. The hook can be useful for deferring a derived prop's consumer, but put a costly computation behind the deferred input in that consumer if avoiding urgent computation is the goal.

```typescript
// Does not defer computeExpensiveValue; it only defers consuming its result
const expensiveValue = useMemo(() => computeExpensiveValue(input), [input]);
const deferredValue = useDeferredValue(expensiveValue); // Does not defer the computation above

// CORRECT: Use useDeferredValue for derived values that can lag
const query = useDeferredValue(searchInput); // OK: search results can lag

```

### 4. Not Understanding Lane Priorities

```typescript
// WRONG: Assuming all state updates have the same priority
const handleEverything = () => {
  setState1(a + 1); // Priority depends on context
  setState2(b + 1); // Might be different priority
};

// CORRECT: Understand priority ordering
const handleMixed = () => {
  // Flush synchronously only when an integration requires the DOM before return.
  flushSync(() => {
    setUrgentState(true);
  });

  // Priority follows the calling event context; it is not always Default Lane
  setNormalState(value);

  // Mark this update as non-urgent; internal lane assignment is not an app contract.
  startTransition(() => {
    setDeferredState(newValue);
  });
};

```

## Best Practices

1. **Use `useTransition` for non-urgent state updates**: Search filtering, tab switching, list updates.

2. **Use `useDeferredValue` for derived values**: When a value can lag behind its source.

3. **Keep urgent updates outside `startTransition`**: Input values, click handlers should be immediate.

4. **Profile before using concurrent features**: Not all apps need them.

5. **Memoize only measured boundaries**: `memo` can skip a parent-driven render when props compare equal, but is not required for Transitions and cannot preempt a long component calculation.

6. **Use Suspense for work that actually suspends**: A boundary coordinates fallback/reveal behavior for lazy code or a supported data source; it does not detect fetching done in an Effect.

7. **Think in update urgency, not lane values**: Use public APIs such as `useTransition` and `useDeferredValue` to express intent. Lane assignments are internal and can change between React versions.

## Performance Considerations

### Fiber Overhead

Fiber adds memory overhead compared to the stack reconciler:

- Fiber objects and the current/work-in-progress representation retain additional data; their size depends on the build and engine
- Linked list structure requires more memory
- Scheduling logic adds CPU overhead

### When Concurrent Features Help

| Scenario | Work that may block responsiveness | How concurrent rendering can help |
| -------------------------------- | ---------------------------------------- | ----------------------------------------------------------------- |
| Search with 10K items | Results render delays input | Keep input urgent and prepare results separately |
| Tab switching with heavy content | Preparing the new tab delays interaction | Keep the old tab visible while preparing the next |
| Animation plus data load | Rendering competes with browser work | Yield eligible rendering between work units |
| Large list rendering | Many rows take time to prepare | Schedule eligible rendering; virtualization can reduce total work |

These are possible benefits, not guarantees. One long synchronous calculation, a large DOM commit or expensive browser layout can still block interaction.

### When Concurrent Features Hurt

- **Small apps**: Overhead not worth it
- **Simple state updates**: `startTransition` adds unnecessary complexity
- **Synchronous requirements**: Some updates must be immediate

## Summary

React Fiber is React's internal work representation for reconciliation and scheduling. Fiber nodes form a tree encoded with `child`, `sibling` and `return` links; they retain identity, state and pending work. This lets React schedule eligible render work between units, but cannot interrupt a component function, one long calculation or the synchronous commit.

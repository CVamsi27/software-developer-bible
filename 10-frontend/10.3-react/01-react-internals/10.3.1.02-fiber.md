# React Fiber

A large results view can take long enough to compete with typing. React needs to keep the committed screen coherent while it prepares another result, and it needs a way to choose which eligible work to continue first. Fiber is the internal architecture that supports that work.

```tsx
// excerpt
const [input, setInput] = useState('');
setInput(next); // Urgent: committed screen stays responsive to typing.
startTransition(() => setQuery(next)); // Non-urgent: results may render later.
```

## Definition

React Fiber is React's internal representation of component work and retained state. A fiber records the information React needs to reconcile an element with the existing tree, including component identity, state, and pending updates.

Because each component renders as its own fiber record, the renderer can prepare a work-in-progress tree in memory and publish a completed result during commit.

> **Textbook Definition:** Fiber is React's reconciler architecture, representing component work as resumable units associated with a retained tree. It supports cooperative scheduling between units of work; it does not make arbitrary JavaScript execution preemptible.

## First Principles

A normal JavaScript function runs until it returns — the browser cannot interrupt a long calculation inside it to process a keystroke. If a renderer wants to pause between component work units, it must keep traversal progress on the heap instead of relying only on the JavaScript call stack.

React maintains twin trees (`current` and `workInProgress`) so it can prepare a candidate screen without exposing a partial UI. If urgent work arrives or a `<Suspense>` boundary needs data, eligible background preparation can pause, unwind, restart, or be discarded — and commit then publishes the chosen tree synchronously.

## 1. Two Trees: `current` and `workInProgress`

The `current` tree matches what the user sees on screen, while the `workInProgress` tree holds the candidate update being reconciled. Only when the candidate is complete does commit swap `workInProgress` in as the new `current` tree.

```text
  current (committed DOM)                 workInProgress (candidate render)
  ┌─────────────────────────────────────────────────────────────────┐   alternate     ┌─────────────────────────┐
  │ AppFiber            │ <=============> │ AppFiber (wip)          │
  └──┬──────────────────────────────────────────────────────────────┘                 └──┬──────────────────────┘
     │ child                                 │ child
     v                                       v
  ┌───────────────────────────────────────────────────────┐  sibling  ┌──────────┐  ┌──────────────┐  sibling
  │ SearchInput  │ ────────> │ Results  │  │ SearchInput  │ ────────> ...
  └───────────────────────────────────────────────────────┘           └──────────┘  └──────────────┘
        ▲ return                                  ▲ return
```

React traverses fibers using linked `child`, `sibling`, and `return` (parent) pointers — descending via `child` to **begin work** (render and reconcile child elements), then ascending via `return` when a leaf finishes to **complete work** (create detached host nodes and bubble subtree flags upward) before stepping to the next `sibling`. Linking `alternate` pairs lets React double-buffer and reuse existing fiber objects across commits instead of allocating a fresh tree from scratch. When `workInProgress` suspends on an unresolved async resource, React can show the nearest `<Suspense>` fallback without corrupting `current`. Those internal fields and lane bitmasks are version-sensitive implementation details, never application contracts.

## 2. Priority Lanes and What Stays Synchronous

React groups updates into conceptual priority lanes — such as synchronous user input vs. interruptible transitions — so urgent feedback jumps ahead of expensive background re-renders. Still, the cooperative scheduling boundary is strict:

- React may yield **between** its own fiber work units during concurrent rendering.
- React **cannot** interrupt a component function or a synchronous loop halfway through execution.
- The **commit** phase runs synchronously across three sub-phases — **before mutation** (`getSnapshotBeforeUpdate`), **mutation** (DOM insertions, updates, deletions, and old ref detach), and **layout** (new ref attach and `useLayoutEffect`) — before passive `useEffect` callbacks flush asynchronously after paint.

## 3. What Application Code Controls

Application code never creates fibers or sets bitmasks directly; it signals urgency through React APIs such as `startTransition` and `<Suspense>`:

```tsx
import { memo, startTransition, useState } from 'react';

const Results = memo(function Results({ items, query }: { items: string[]; query: string }) {
  const visible = items.filter((item) => item.toLowerCase().includes(query.toLowerCase()));
  return <ul>{visible.slice(0, 50).map((item) => <li key={item}>{item}</li>)}</ul>;
});

export function SearchableList({ items }: { items: string[] }) {
  const [input, setInput] = useState('');
  const [query, setQuery] = useState('');

  function handleChange(next: string) {
    setInput(next); // Urgent lane: keeps the controlled input responsive.
    startTransition(() => setQuery(next)); // Transition lane: Results can yield between fibers.
  }

  return (
    <>
      <input value={input} onChange={(e) => handleChange(e.target.value)} />
      <Results items={items} query={query} />
    </>
  );
}
```

Watch the common `startTransition` trap: calling `items.filter(...)` synchronously inside a single huge `Results` component (or inside the `startTransition` callback itself, which React runs immediately) still blocks the main thread for the duration of that JS call. Pair transitions with `React.memo` on heavy subtrees so typing only re-renders the input, and split work, query an indexed endpoint, or move CPU-heavy filtering to a Web Worker. React 19 also extended `startTransition` to `async` functions (Actions), keeping `isPending` active across `await` boundaries as covered in [Modern Hooks (React 18/19)](../04-modern-react/10.3.4.01-modern-hooks-react18-19.md).

Lane names, bitmasks, and fiber fields change across React releases and are never stable APIs. Express intent with public scheduling primitives and verify interactions in the React Profiler.

## Summary

Fiber lets React retain reconciliation progress across twin `current` and `workInProgress` trees, coordinate priority lanes and `<Suspense>`, and swap finished work in during a synchronous commit. It yields only between fiber work units — never inside arbitrary JavaScript or DOM commits — so use transitions for priority, `React.memo` for subtree isolation, and profiling or workers for raw CPU cost.

# React Fiber

A large results view can take long enough to compete with typing. React needs to keep the committed screen coherent while it prepares another result, and it needs a way to choose which eligible work to continue first. Fiber is the internal architecture that supports that work.

## Definition

React Fiber is React’s internal representation of component work and retained state. A fiber records information React needs to reconcile an element with the existing tree, including component identity, state and pending updates. The renderer can prepare a work-in-progress tree and publish a completed result during commit.

> **Textbook Definition:** Fiber is React’s reconciler architecture, representing component work as resumable units associated with a retained tree. It supports cooperative scheduling between units of work; it does not make arbitrary JavaScript execution preemptible.

## First Principles

A normal JavaScript function runs until it returns. The browser cannot interrupt a long calculation inside that function to process a keystroke. If a renderer wants to pause between component work units, it must retain traversal progress outside the current call stack.

React’s current and work-in-progress trees let it prepare a candidate without exposing a partial result. If newer urgent work arrives, eligible preparation can be paused, restarted or discarded. Commit then applies the chosen result synchronously.
The current implementation represents traversal with child, sibling and parent links: descend into child work, follow a sibling, then return up the tree to find the next unit. This explains the work loop, but those fields are internal and can change.

The practical boundary is precise:

- React may yield between its own units of render work.
- React cannot interrupt a component function or a long loop halfway through.
- Commit work is synchronous; a transition does not move DOM mutation to a worker.

## What application code controls

Application code does not create fibers or assign their internal priorities. It expresses intent through supported APIs. For example, keep the input’s displayed value urgent and mark the state that drives an expensive result view as non-urgent:

~~~tsx
setInput(next); // The controlled input must update promptly.
startTransition(() => setQuery(next)); // The results may lag behind briefly.
~~~

A transition changes how React schedules the resulting render; it does not make filtering itself faster or move it off the main thread. If one calculation blocks for too long, reduce its work, split it into smaller units, or move appropriate computation to a Web Worker. For large result subtrees, a memoized boundary can prevent the urgent input render from repeating the expensive work with an unchanged query.

Lane names, bitmasks and fiber fields are implementation details. They can change between React releases and are not application contracts. Use public scheduling APIs and profile the actual interaction.

## Summary

Fiber lets React retain reconciliation progress, prepare a candidate tree and schedule eligible work before a synchronous commit. It can yield between work units, not inside arbitrary JavaScript or during commit. Use transitions to express priority; use profiling, algorithmic improvements or workers to address expensive computation.

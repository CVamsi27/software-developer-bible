# Reconciliation

In theoretical computer science, finding the absolute minimum number of operations to transform one arbitrary tree into another requires $O(n^3)$ algorithmic complexity. If an application tree contained just 1,000 components, calculating the diff between two renders using general tree algorithms would require roughly one billion comparison operations—completely destroying interactive browser performance.

How does React compute updates across complex component trees in mere milliseconds?

The answer is **Reconciliation**, powered by React's **Heuristic $O(n)$ Diffing Algorithm**.

Instead of attempting a computationally intractable global search, React relies on two pragmatic observations grounded in real-world frontend behavior:
1. **Different element types produce different trees:** If a `<div>` is replaced by an `<article>`, React does not waste time diffing their children—it tears down the entire old subtree and mounts a fresh one.
2. **Sibling identity can be stabilized with keys:** When children are reordered, inserted, or removed, a unique and stable `key` prop allows React to preserve component identity and state rather than mutating elements in place.

Mastering reconciliation means understanding how React tracks component identity: why changing a component type resets internal state, how the key prop prevents UI corruption during list sorting, and how to control state preservation intentionally.

## Definition

**Reconciliation** is how React matches newly rendered elements to the existing tree, deciding which identities continue and which are replaced. That matching determines whether local state survives and what changes React commits to the DOM.

> **Textbook Definition:** Reconciliation determines which prior component instances and host nodes can represent a newly rendered tree. Element type, position and keys establish identity, which governs state preservation and the host changes prepared for commit.

Imagine an editable patient list. You type a note in Ben's row, then sort the list. The note should stay with Ben. Rendering the right names is insufficient if React associates the old row's state with a different patient.

## First Principles

A component's state must belong to something stable between renders. Display text and array position can change; React therefore needs an identity rule. Matching component type and position, with keys distinguishing siblings, lets it continue an existing instance.

Finding a globally optimal tree-edit sequence would be expensive. React uses type/key heuristics instead. Those heuristics explain state preservation; they do not guarantee the smallest possible DOM edit sequence or a fixed render time.

## Trace a row through a reorder

```tsx
import { useState } from 'react';

type Patient = { id: string; name: string };

function PatientRow({ patient }: { patient: Patient }) {
  const [note, setNote] = useState('');
  return (
    <li>
      <label>
        Note for {patient.name}
        <input value={note} onChange={event => setNote(event.target.value)} />
      </label>
    </li>
  );
}

export function PatientList({ patients }: { patients: Patient[] }) {
  return <ul>{patients.map(patient => (
    <PatientRow key={patient.id} patient={patient} />
  ))}</ul>;
}
```

| Before sort | After sort | Matching result |
| ----------- | ----------- | ----------------------------------------------- |
| Ada, key p1 | Ben, key p2 | Ben's existing row moves; its note survives |
| Ben, key p2 | Ada, key p1 | Ada's existing row moves; its own note survives |

With `key={index}`, key 0 remains at position 0 while its patient prop changes from Ada to Ben. The state still belongs to the positional identity, so a note can appear under the wrong name. React followed the supplied identity; it did not infer that patient name was the intended key.

A newly inserted stable key mounts a new row. A removed key unmounts its row. Reordering a retained key under the same parent preserves that identity, although its component function may still run and its DOM node may move.

## Decide when state should survive

| Change | Identity consequence |
| ----------------------------------------------------------- | ------------------------------------------------------ |
| Same component type at the same unkeyed position, new props | Local state ordinarily survives |
| Same type and stable key among the same parent's children | Identity survives reorder |
| Different key at the same position | Old identity is removed; new state initializes |
| Different component type at the same position | Old subtree is replaced |
| Move to a different parent | A matching key does not transfer state between parents |
| Filter a row out, then add it back later | It remounts; keys are not an offscreen state store |

To preserve edits through filtering/unmounting, store drafts above the row or in an appropriate keyed store. To reset a draft when selecting another patient, changing the key can be intentional:

```tsx
<PatientEditor key={selectedPatient.id} patient={selectedPatient} />
```

Here type and position stay the same while the key changes. Without the key change, a new patient prop alone does not reset local `useState` initialization. [State identity and intentional resets](https://react.dev/learn/preserving-and-resetting-state)

### Keep keys stable and scoped

Keys must be unique among siblings, not throughout the application. React consumes `key`; pass `patientId` separately if the component needs it. Generate an ID when a new record is created, not during every render. Random keys continually remount rows, losing input state and restarting effects.

Index keys can be acceptable when positional identity is intentional and insertion, removal or reorder cannot associate state with another record. For editable, sortable or filtered domain lists, use a persistent domain ID.

For multiple sibling elements per record, use an explicit keyed Fragment:

```tsx
import { Fragment } from 'react';

function Definitions({ terms }: {
  terms: { id: string; term: string; meaning: string }[];
}) {
  return <dl>{terms.map(item => (
    <Fragment key={item.id}>
      <dt>{item.term}</dt>
      <dd>{item.meaning}</dd>
    </Fragment>
  ))}</dl>;
}
```

The shorthand `<>...</>` cannot carry a key.

## Separate rendering from committing changes

```text
Update scheduled → render and match identities → commit accepted DOM changes
```

During render, React evaluates components to describe the next UI and prepares work. A render may be restarted or abandoned; keep it pure. The commit applies accepted host changes. A component can render and produce unchanged DOM output, so “rendered again” does not mean “DOM rebuilt.”

For the same host element type, React can update changed attributes or text while retaining the node. Replacing a host type or component identity can replace its subtree. Effects have their own setup/cleanup timing; do not reduce all lifecycle behavior to the tree-matching diagram. Fiber and concurrent scheduling are covered in their dedicated chapters.

## Identity does not replace performance measurement

Stable keys preserve the intended instance. `memo` addresses some avoidable component evaluations when props compare equal; it does not preserve state across an identity change. A memoized component can update from its own state or consumed context.

Define component types and memo wrappers outside their parent's render function. Creating a new component function or `memo(Child)` wrapper on each render creates a new type, which can reset the child. Inline object props are a separate issue: they can defeat shallow prop comparisons, but do not automatically remount a same-type child.

React's commonly described linear heuristic matching is not a claim that the entire UI update is O(n). Expensive component calculations, sorting, repeated render attempts, layout and output size all contribute. Use the Profiler before optimizing; virtualize very large lists and colocate state when measurements support it.

## Common mistakes

- Testing only displayed labels after reorder, without checking row-local input state.
- Using a random key to “force a render” when a deliberate state update is required.
- Expecting a key to preserve state after unmount or across different parents.
- Treating a same key as sufficient when the component type changed.
- Claiming unchanged props prevent every child render; ordinary children and memoized children have different update boundaries.

## Summary

Reconciliation matches identities by type and tree position, with keys distinguishing siblings. Stable domain keys keep row-local state attached to the right record; changing identity resets it. Rendering, DOM commits and memoization are separate mechanisms with separate performance costs.

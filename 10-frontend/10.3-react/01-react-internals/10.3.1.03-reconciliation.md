# Reconciliation

## TL;DR

Reconciliation is React's diff algorithm: comparing old vs. new fiber trees to decide which DOM mutations to commit. It uses two heuristics — element types determine tree branches, and stable keys identify children across renders.

## First Principles

1. **State belongs to an identity, not to the text a component displays.** React must decide whether a new element continues an existing instance. Matching type and position, with keys distinguishing siblings, preserves that instance; changing identity discards its state and mounts a replacement.
2. **An unrestricted optimal tree edit is too costly for routine UI updates.** React uses type and key heuristics to avoid searching every possible correspondence. Those heuristics make ordinary comparisons efficient but do not promise the globally smallest set of DOM edits.
3. **Evaluating a component is distinct from changing the DOM.** A render can produce the same host output, resulting in no DOM mutation. Memo boundaries may skip some component evaluations, while keys preserve identity; neither mechanism substitutes for the other.

## Why It Matters

Reconciliation is the heart of why React's render is fast. The interview signal is understanding both heuristics and their failure modes: switching element types (e.g., `<div>` to `<span>`) causes a full subtree rebuild, and unstable keys cause unnecessary remounts and lost state.

## Definition

Reconciliation is the process by which React determines which parts of the Virtual DOM need to be created, updated, or destroyed when state or props change. It's the algorithm that compares the new Virtual DOM tree with the previous one and computes the changes required by its heuristics to update the real DOM. Reconciliation is also commonly called "diffing."

Reconciliation is central to React's performance model. Without it, every state change would require re-rendering the entire application from scratch, which would be prohibitively slow.

## The Problem It Solves

### The Problem

When a component's state changes, React needs to figure out:

1. Which components need to re-render

2. What changed between the old and new UI

3. How to update the real DOM efficiently

### Naive Approach (O(n³))

General tree-edit-distance algorithms can have cubic cost because they consider many possible mappings and edit sequences. React uses identity heuristics instead of searching for a globally optimal sequence. Big-O describes how work scales, not an exact operation count for a particular tree.

### React's Approach (O(n))

React makes two key assumptions that reduce complexity to O(n):

1. **Different node types produce different trees**: If a `<div>` changes to a `<span>`, React destroys the old subtree and creates a new one.

2. **Keys identify stable elements**: The `key` prop tells React which elements have moved, been added, or removed.

The O(n) description refers to heuristic tree matching, not the cost of arbitrary component computations, sorting, DOM layout or repeated render attempts.

## How It Works

### Reconciliation Algorithm in Detail

```typescript
// Teaching pseudocode for keyed element children, not a complete reconciler.
function reconcileChildren(parent, nextElements) {
  const oldByKey = mapOldChildren(parent.child);
  let first = null;
  let previous = null;
  let lastPlacedIndex = 0;

  nextElements.forEach((element, index) => {
    const key = element.key ?? index;
    const old = oldByKey.get(key);
    let next;
    if (old && old.type === element.type) {
      next = cloneForWorkInProgress(old, element.props);
      // A reused node may still need a move, even though identity survives.
      if (old.index < lastPlacedIndex) markPlacement(next);
      else lastPlacedIndex = old.index;
    } else {
      if (old) markDeletion(parent, old);
      next = createFiberFromElement(element);
      markPlacement(next);
    }
    oldByKey.delete(key);
    next.index = index;
    next.sibling = null;
    if (previous) previous.sibling = next;
    else first = next;
    previous = next;
  });

  for (const old of oldByKey.values()) markDeletion(parent, old);
  return first;
}
```

Real reconciliation also handles text, fragments, empty children and optimized matching paths. Cloning preserves the current tree until commit; marking deletions and placements prevents a same-key type replacement from leaking the old node or a reorder from silently remaining in the old DOM order.

### Key Prop: The Secret Sauce

A key is scoped to siblings under one parent, and React does not pass it as an ordinary prop. Reusing the same key under a different parent does not carry component state across that move; type and position in the tree still participate in identity.

The `key` prop is the most critical part of reconciliation for list rendering:

```text
Key Prop Behavior:
═══════════════════════════════════════════════════════════════

Without Keys (index-based):
Old: [A, B, C] (indices: 0, 1, 2)
New: [D, A, B, C] (indices: 0, 1, 2, 3)

React compares by index:
Index 0: A → D (update text)
Index 1: B → A (update text)
Index 2: C → B (update text)
Index 3: new → C (create)

Result: positional identities now belong to different records.

With Keys (stable IDs):
Old: [A(id:1), B(id:2), C(id:3)]
New: [D(id:4), A(id:1), B(id:2), C(id:3)]

React compares by key:
Key 1: A → A (no change)
Key 2: B → B (no change)
Key 3: C → C (no change)
Key 4: new → D (create)

Result: D mounts; A/B/C keep identity (may still render).

```

## Code Examples

### Basic Reconciliation

```typescript
import React, { useState, Fragment } from 'react';

// React reconciles these changes:
const App = () => {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
  // When count changes:
  // 1. React creates new VDOM with updated h1 text
  // 2. Reconciles: div type same , h1 type same , text changed
  // 3. Updates only the text node in the real DOM
};

```

### List Reconciliation with Keys

```typescript
// BAD: Using array index as key
const BadList = ({ items }: { items: string[] }) => (
  <ul>
    {items.map((item, index) => (
      <li key={index}>{item}</li>
      // If items reorder, React incorrectly matches old and new items
      // This causes unnecessary re-renders and potential bugs
    ))}
  </ul>
);

// GOOD: Using stable unique IDs
const GoodList = ({ items }: { items: { id: number; text: string }[] }) => (
  <ul>
    {items.map(item => (
      <li key={item.id}>{item.text}</li>
      // React correctly tracks items by ID
      // Reordering preserves identity; component functions may still run
    ))}
  </ul>
);

```

### Conditional Rendering

```typescript
const ConditionalComponent = ({ showDetails }: { showDetails: boolean }) => (

        3. Mount new component

```

### Key Changing Behavior

```typescript
const KeyExample = () => {
  const [activeTab, setActiveTab] = useState('tab1');

  return (
    <div>
      <TabBar
        tabs={['tab1', 'tab2', 'tab3']}
        active={activeTab}
        onChange={setActiveTab}
      />
      {/* Different key forces full unmount/mount */}
      {activeTab === 'tab1' && <Tab1Content key="tab1" />}
      {activeTab === 'tab2' && <Tab2Content key="tab2" />}
      {activeTab === 'tab3' && <Tab3Content key="tab3" />}
      {/* Each tab has a different key, so switching tabs
          completely unmounts the old and mounts the new */}
    </div>
  );
};

// Alternative: Same key, conditional rendering
const SameKeyExample = () => {
  const [activeTab, setActiveTab] = useState('tab1');

  return (
    <div>
      <TabBar tabs={['tab1', 'tab2', 'tab3']} active={activeTab} onChange={setActiveTab} />
      {/* Same key means React keeps the component instance */}
      <TabContent key="tab-content" tab={activeTab} />
    </div>
  );
};

```

### Reconciliation with State

```typescript
const StateReconciliation = () => {
  const [items, setItems] = useState([
    { id: '1', text: 'First' },
    { id: '2', text: 'Second' },
  ]);

  // Adding an item at the beginning
  const addItem = () => {
    setItems(previous => [
      { id: crypto.randomUUID(), text: 'New First' },
      ...previous,
    ]);
    // React reconciles:
    // 1. fresh key: new → create New First
    // 2. key 1: First → First (no change)
    // 3. key 2: Second → Second (no change)
    // Only the new item is created and inserted
  };

  return (
    <ul>
      {items.map(item => (
        <li key={item.id}>{item.text}</li>
      ))}
      <button onClick={addItem}>Add First</button>
    </ul>
  );
};

```

const DataTable = ({ data, sortKey, filterText }: DataTableProps) => {
  const filteredData = data
    .filter(row => row.name.includes(filterText))
    .sort((a, b) => a[sortKey] > b[sortKey] ? 1 : -1);

## Common Mistakes

### 1. Using Array Index as Key

```typescript
// BAD: Array index as key
const BadTodoList = ({ todos }: { todos: Todo[] }) => (
  <ul>
    {todos.map((todo, index) => (
      <TodoItem key={index} todo={todo} />
    ))}
  </ul>
);

// Problem: If todos reorder, React matches wrong items
// Example:
// Old: [A(0), B(1), C(2)] (indices as keys)
// New: [C(0), A(1), B(2)] (reordered)
// React thinks: key 0 changed from A to C (update!)
// key 1 changed from B to A (update!)
// key 2 changed from C to B (update!)
// State at each position follows the wrong record!

```

### 2. Changing Key to Force Re-render

```typescript
// BAD: Using random keys to force re-render
const BadComponent = () => {
  const [, forceRender] = useState(0);

  return (
    <ExpensiveChild key={Math.random()} />
    // This completely destroys and recreates the child
    // Losing all state and effects
  );
};

// GOOD: Use key to intentionally reset state
const GoodComponent = ({ userId }: { userId: string }) => (
  <UserProfile key={userId} userId={userId} />
  // When userId changes, the profile resets
  // This is the correct use case for key-based reset
);

```

### 3. Not Providing Keys for Dynamic Lists

An omitted key uses positional matching and emits a warning. The corrected list already appears in [List Reconciliation with Keys](#list-reconciliation-with-keys); use a domain ID that is stable between renders and unique among siblings.

### 4. Misunderstanding Re-render Scope

A parent update normally runs its ordinary child components again, even with unchanged props. Keys preserve instances; memo boundaries address avoidable component execution.

```typescript
// Define the wrapper once, outside the parent, to preserve component type.
const MemoizedChild = React.memo(Child);
const Parent = () => {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
      <MemoizedChild />
    </div>
  );
};
```

`<React.memo(Child) />` is invalid JSX, and creating `React.memo(Child)` inside each render changes the component type. A memoized child can still update from its own state or consumed context.

## Best Practices

1. **Always use stable, unique keys**: Never use array indices for reorderable lists.

2. **Use domain IDs as keys**: Database IDs, UUIDs, or other stable identifiers.

3. **Don't change key to force re-render**: Use state or context instead.

4. **Understand key-based reset**: Changing a key intentionally resets component state.

5. **Memoize expensive children**: Use `React.memo` to prevent unnecessary re-renders.

6. **Avoid inline objects/arrays in JSX**: They create new references each render.

7. **Profile before optimizing**: Use React DevTools Profiler to identify actual bottlenecks.

## Performance Considerations

### Reconciliation Cost Factors

| Factor | Impact | Mitigation |
| ---------------------- | ------------------------------------ | ----------------------------- |
| Tree depth | Deeper trees take longer to traverse | Flatten component hierarchy |
| Node count | More nodes = more diffing | Virtualize long lists |
| Key stability | Stable keys = efficient updates | Use domain IDs |
| Component type changes | Forces subtree recreation | Avoid dynamic component types |
| State colocation | Less state = less re-rendering | Move state closer to usage |

### When Reconciliation Is Fast

- Most nodes haven't changed (early bail-out)
- Keys are stable and unique
- Component types remain the same
- Shallow prop comparisons succeed (`React.memo`)

### When Reconciliation Is Slow

- Frequent full-tree re-renders
- Unstable keys causing unnecessary unmounting
- Deep component hierarchies
- Many different component types changing

## Summary

Reconciliation is React's core algorithm that determines how to efficiently update the UI. By comparing Virtual DOM trees with O(n) complexity using heuristics (type comparison and keys), React minimizes expensive DOM operations. Understanding reconciliation is crucial for writing performant React applications.

## Revision Questions

**Definition**

1. **Q:** How does reconciliation avoid solving a general optimal tree-edit problem?
   **A:** React uses element type and sibling identity to restrict matching. This makes updates practical while foregoing a guarantee of the optimal edit sequence.

**How It Works**

2. **Q:** What identifies a keyed component strongly enough to preserve its state?
   **A:** Its type and key must match within the same parent position. A key is scoped to siblings, so it does not carry state across different parents.

3. **Q:** Why must a replacement with an existing key still mark the old node for deletion?
   **A:** Matching keys alone do not permit reuse when types differ. The new fiber must mount and the incompatible old fiber must be removed at commit.

**Code Examples**

4. **Q:** What does changing a tab panel key deliberately accomplish?
   **A:** It removes the old panel instance and creates a new one, resetting its local state. Shared state kept above the panel can survive.

**Common Mistakes**

5. **Q:** What happens to item state when a reordered list uses indices as keys?
   **A:** State remains attached to the position whose key matches, potentially becoming associated with another record. The issue is incorrect identity, not merely extra rendering.

6. **Q:** Why must a memo wrapper be declared outside its parent render?
   **A:** Recreating the wrapper produces a different component type and can reset the child. A single stable wrapper lets prop comparisons determine whether parent-driven execution is skippable.

**Performance Considerations**

7. **Q:** What costs are outside the heuristic linear-diff description?
   **A:** Component calculations, sorting, repeated render attempts and browser layout or paint can dominate total time. Linear matching alone does not bound the entire interaction.

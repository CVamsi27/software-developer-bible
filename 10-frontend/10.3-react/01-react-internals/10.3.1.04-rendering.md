# Rendering

A render log can show a component running while the visible page barely changes. To understand the cost, follow the update through calculation, commit and browser paint; those are different pieces of work.

```jsx
// excerpt
function Row({ patient }) {
  console.log('render', patient.id); // runs on every parent render…
  return <tr><td>{patient.name}</td></tr>;
}
// …even when the committed <tr> is byte-identical to before.
```

## Definition

Rendering is React calling components to calculate the next UI from their current props, state and context. React reconciles that output with the retained tree. Commit applies accepted changes to the host environment, such as the browser DOM. A render can finish without changing a DOM node.

> **Textbook Definition:** The render phase computes a prospective interface and reconciles it with retained identity. The commit phase publishes the accepted result to the host environment. Render work may be repeated or discarded, so component rendering must remain pure.

## First Principles

A state update requests another UI calculation; it does not directly mutate the DOM. React calls the updating component, compares its output with the retained tree, and commits the accepted changes before the browser calculates styles, layout, and paint.

Updating a child's own state does not force its ancestors to render again, whereas a parent render normally descends into its ordinary children. Meanwhile, a custom Hook executes inside the component that called it, so returning a fresh object from a custom Hook is a result of rendering rather than a trigger for another render. Because any render work may repeat or be discarded before commit, rendering must remain pure.

```text
Trigger ──▶ Render (pure) ──▶ Commit (DOM mutations + layout Effects) ──▶ Browser Paint ──▶ Passive Effects
```

## 1. One Update, Three Costs (and Automatic Batching)

1. **Render:** React evaluates components and prepares the next tree. Multiple state updates triggered in event handlers, promises, or timers are **automatically batched** in React 18+ into one render and commit pass:
   ```tsx
   // excerpt
   async function handleSave() {
     await saveRecord();
     setSaving(false);
     setSavedAt(Date.now()); // React batches both updates after `await` into one render
   }
   ```
2. **Commit:** React applies the accepted host changes and runs `useLayoutEffect` synchronously before browser paint.
3. **Browser work:** The browser recalculates styles, lays out elements, and paints/composites changes.

React's render phase can yield between work units, though it cannot interrupt a component function halfway through. Passive Effects (`useEffect`) usually flush asynchronously after paint; use `useLayoutEffect` only when work must run after DOM mutation and before paint.

## 2. Purity, Derived Values, and Hydration

Render must be a pure calculation: given the same inputs, it returns the same element tree without side effects, because concurrent restarts can discard uncommitted work. Compute values directly during render instead of storing duplicate state — for example, derive form validation errors inline rather than syncing them through a second state setter and another render.

`React.memo` lets React skip a parent-driven render when props compare equal, though the child's own state or consumed context still triggers updates. Client components also still execute during server-side rendering (SSR) hydration on initial load so React can match server HTML and attach interactive event listeners.

In development, `StrictMode` intentionally double-invokes component bodies, initializers, and Effects to expose impurity. Therefore, a render log count is not the count of visible commits — measure committed work and browser activity with the React Profiler and browser DevTools.

## 3. Flush Only for an Immediate DOM Dependency

If a third-party integration must read the updated DOM synchronously in the same callback, `flushSync` from `react-dom` forces pending updates to commit immediately:

```tsx
// excerpt
import { flushSync } from 'react-dom';

function handleAddItem(nextItem: Item) {
  flushSync(() => setItems((prev) => [...prev, nextItem]));
  // Safe to measure newly committed DOM height on the next line
  listRef.current?.lastElementChild?.scrollIntoView();
}
```

Because `flushSync` can flush more work than the wrapped update and unexpectedly reveal a `<Suspense>` fallback, treat it strictly as an integration escape hatch rather than a general batching or performance tool.

## Summary

Rendering calculates a candidate UI (automatically batched across events, promises, and timers in React 18+); commit applies accepted host changes; the browser handles layout and paint. Updating child state leaves ancestors untouched, derived values belong inline in render, and client components still run during hydration. Keep renders pure, ignore raw development render counts under `StrictMode`, reserve `flushSync` for synchronous DOM reads, and profile before optimizing.

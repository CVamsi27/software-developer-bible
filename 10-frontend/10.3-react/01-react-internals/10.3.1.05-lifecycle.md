# Lifecycle

When a user switches chat rooms, the heading can show the new room while the network connection still points to the old one. The component remains mounted, but the external resource must stop synchronizing with the old props and start with the new ones.

```tsx
// excerpt
// If setup connects without disconnecting on dependency change,
// switching from "general" to "random" leaves the old room socket open.
useEffect(() => subscribeToRoom(roomId), [roomId]);
```

## Definition

A component's lifecycle describes when its identity is added to the tree, updated, and removed. Class components expose methods for these boundaries, whereas function components use Effects (`useEffect` and `useLayoutEffect`) to synchronize with external systems after a commit and stop that synchronization when inputs change or the component unmounts.

> **Textbook Definition:** A component lifecycle is the sequence of mounting, updating, and unmounting for a retained component identity. An Effect has a separate start-and-stop synchronization lifecycle tied to committed props and state; it is not a callback for each component lifecycle method.

## First Principles

An Effect should describe one synchronization process: how to start it and how to stop it. React runs the previous cleanup before starting a replacement setup when dependencies change, and runs the final cleanup on unmount:

```text
Mount (roomId="general") ──▶ setup("general")
Update (roomId="random") ──▶ cleanup("general") ──▶ setup("random")
Unmount                  ──▶ cleanup("random")
```

## 1. One Effect, One Start/Stop Cycle

```tsx
import { useEffect } from 'react';

function ChatRoom({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = connect(roomId);
    return () => connection.disconnect();
  }, [roomId]);

  return <h1>Room: {roomId}</h1>;
}
```

When `roomId` changes, the cleanup closes the connection created for the old value, then the new setup connects to the new room. Writing one dependency-based Effect (`[userId]`) also avoids issuing duplicate requests on initial mount, which separate mount and update Effects would trigger.

Fetching adds an async boundary: aborting a request limits wasted work, though a response can already finish before abort arrives. Guard publication and associate displayed data with the requested identity when stale results would mislead the user — or use a route loader or server-state library for caching and deduplication:

```tsx
// excerpt — cancel in-flight work and guard late resolution with an ignore flag
import { useEffect, useState } from 'react';

function UserProfile({ userId }: { userId: string }) {
  const [profile, setProfile] = useState<{ name: string } | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    let ignore = false;

    fetch(`/api/users/${encodeURIComponent(userId)}`, { signal: controller.signal })
      .then((res) => (res.ok ? res.json() : Promise.reject(new Error(`HTTP ${res.status}`))))
      .then((data) => {
        if (!ignore) setProfile(data);
      })
      .catch((err) => {
        if (!ignore && err.name !== 'AbortError') setProfile(null);
      });

    return () => {
      ignore = true;
      controller.abort();
    };
  }, [userId]);

  return <p>{profile ? profile.name : 'Loading...'}</p>;
}
```

## 2. Timing and Class Component Mapping

| Hook / Method | When It Runs | Primary Role |
| :----------------------------- | :--------------------------------------------- | :----------------------------------------------------------------- |
| **`useLayoutEffect`** | After DOM mutation, before browser paint | Read new DOM layout and adjust visually before paint |
| **`useEffect`** | After commit (usually after paint) | Network sync, subscriptions, timers, external stores |
| **`getSnapshotBeforeUpdate`** | Before DOM mutations commit | Capture old DOM state (e.g., scroll position); no Hook exact match |
| **`componentDidMount`** | Initial mount only | Setup once on mount (`useEffect` also runs after dep updates) |
| **`componentDidUpdate`** | Subsequent updates only (skips initial mount) | Update sync (differs from `useEffect`, which runs on mount too) |
| **`componentWillUnmount`** | Component removal only | Final teardown (an Effect cleanup also runs between dep changes) |

Notice two traps in that table: a dependency-based `useEffect` is not identical to `componentDidUpdate` because it runs on initial mount as well, and `useLayoutEffect` cannot directly replace `getSnapshotBeforeUpdate` because it reads the committed *new* DOM rather than the old DOM.

React also fires Effects bottom-up during commit: child `useLayoutEffect` and `useEffect` setups run before their parent's setups, guaranteeing child DOM nodes and refs exist when a parent Effect reads them. In React 19+, a `ref` callback can return a cleanup function directly (replacing the legacy `ref(null)` convention) so observers like `ResizeObserver` tear down automatically on detach without an extra `useEffect`.

In development, `StrictMode` runs an extra setup → cleanup → setup cycle on mount to verify that your teardown cleanly reverses setup. Users should never notice a difference between that check and a single production setup.

## 3. Keep Non-Synchronization Logic Out of Effects

Not every piece of logic belongs in an Effect. Derive values during render; run interaction-specific work in the event handler; use an Effect only when the committed component must stay synchronized with an external system.

## Summary

Component lifetime and Effect synchronization are related but distinct. Each Effect owns a complete start-and-stop cycle that runs cleanup before re-syncing on dependency changes and at unmount — making one `[id]` Effect superior to split mount and update Effects. Class lifecycle methods map only loosely to Hooks (`getSnapshotBeforeUpdate` has no pre-mutation Hook equivalent), so pick layout timing solely for pre-paint DOM reads and protect async results from stale publication.

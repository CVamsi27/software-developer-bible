# Lifecycle

When a user switches chat rooms, the heading can show the new room while the network connection still points to the old one. The component remains mounted, but the external resource must stop synchronizing with the old props and start with the new ones.

```tsx
function ChatRoom({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = connect(roomId);
    return () => connection.disconnect(); // stop the OLD room before starting the new one
  }, [roomId]);

  return <h1>Room: {roomId}</h1>;
}
```

## Definition

A component’s lifecycle describes when its identity is added to the tree, updated and removed. Class components expose methods for these boundaries. Function components use Effects to synchronize with external systems after a commit and to stop that synchronization when its inputs change or the component is removed.

> **Textbook Definition:** A component lifecycle is the sequence of mounting, updating and unmounting for a retained component identity. An Effect has a separate start-and-stop synchronization lifecycle tied to committed props and state; it is not a callback for each component lifecycle method.

## First Principles

An Effect should describe one synchronization process: how to start it and how to stop it. React runs cleanup for the previous setup before starting a replacement setup whose dependencies changed. Unmount runs the last cleanup.

## 1. One Effect, One Start/Stop Cycle

```tsx
import { useEffect } from 'react';

function ChatRoom({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = connect(roomId);
    return () => connection.disconnect();
  }, [roomId]);

  return <h1>Room: {roomId}</h1>;
}
```

When roomId changes, the cleanup closes the connection created for the old value, then the new setup connects to the new room. Each setup owns the exact resource its cleanup releases. This is why cleanup should reverse setup, rather than merely set a “mounted” flag.

Fetching has an additional boundary: aborting a request can reduce wasted work, but the response may already have completed or the transport may not support cancellation. Guard publication and associate displayed data with the requested identity when stale results would be misleading. Prefer a framework or data library when it provides request caching and coordination.

## 2. Timing and Class Components

- **useLayoutEffect** runs after React mutates the DOM and before the browser paints. Reserve it for work such as a measurement that must affect the same paint.
- **useEffect** runs after commit; React may let the browser paint first, but interaction-related Effects can run before paint. Do not rely on one universal paint order.
- **getSnapshotBeforeUpdate** reads the old DOM before mutation. A layout Effect sees the updated DOM, so it is not a drop-in replacement.
- **componentDidMount**, **componentDidUpdate** and **componentWillUnmount** describe class boundaries. A dependency-based Effect starts on the initial commit and re-synchronizes when dependencies change; the mapping is not one-to-one.

Strict Mode can run an extra setup → cleanup → setup cycle in development to test whether cleanup mirrors setup. The user should not be able to distinguish that check from one correct setup in production.

## 3. Keep Non-Synchronization Logic Out of Effects

Not every piece of logic belongs in an Effect. Derive values during render; run interaction-specific work in the event handler; use an Effect when the rendered component must stay synchronized with an external system.

## Summary

Component lifetime and Effect synchronization are related but distinct. An Effect owns a start/stop cycle for one external resource, with cleanup before resynchronization and on removal. Choose layout timing only when pre-paint work is required, and protect asynchronous results from stale publication.

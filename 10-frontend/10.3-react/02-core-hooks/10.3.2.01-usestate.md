# useState

## Definition

`useState` gives a React component a value that React remembers between renders and a setter that queues its next value. A render sees a **snapshot** of that state; calling the setter does not rewrite variables in the currently executing handler.

Consider a counter. A local variable inside the component would be recreated when the function runs again, and changing it would not ask React to update the UI. State supplies both remembered data and an update request.

> **Textbook Definition:** The `useState` hook is a primitive React dispatcher function that binds local component state to the internal Fiber node's `memoizedState` linked-list cell. It returns a tuple containing the current render's immutable state snapshot and an updater function that enqueues state transitions onto the fiber's update queue, scheduling a concurrent or batched re-render pass.

## First Principles


A component function computes output from inputs, but user actions happen between those computations. Persistent UI data must therefore live beyond one function call and be associated with the component's identity.

Several updates may arrive before another render. React needs an ordered queue to combine them. Keeping unnecessary derived values in separate queues creates extra ways for those values to disagree.

## Follow a click into the next render

```tsx
import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);
  function increment() {
    setCount(count + 1);
    console.log(count); // The snapshot from this render, not the queued value.
  }
  return <button onClick={increment}>Count: {count}</button>;
}
```

The first render receives `0`. Its handler queues `1`, but still logs `0`. React processes the update, renders with `1`, and commits the displayed result. The new handler belongs to that new render and sees `1`.

```text
render reads 0 → handler queues 1 → next render reads 1 → UI commits
```

With modern React roots, automatic batching also applies to updates in promises, timers and native event callbacks; batching is not limited to React event handlers. Separate intentional user events still have their own boundaries. For rare DOM integrations that need an immediate flush, see [flushSync](../01-react-internals/10.3.1.04-rendering.md#flushsync-for-immediate-dom-updates), rather than treating it as a routine optimization.

A setter is not a promise to await, and “asynchronous” alone is an incomplete explanation: the important boundary is the render snapshot. React may skip an update whose value is equal under `Object.is`.

## Functional Updates

A replacement stores the supplied value. An **updater function** receives the pending state after earlier queued updates. Use it when the next value must compose with those updates.

```typescript
const Counter = () => {
  const [count, setCount] = useState(0);
  const incrementWithSnapshot = () => {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    // Replacements use one snapshot: next count is count + 1.
  };
  const incrementThree = () => {
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);
    // Updaters compose in order: next count is count + 3.
  };
  return (
    <div>
      <p>{count}</p>
      <button onClick={incrementWithSnapshot}>Three replacements</button>
      <button onClick={incrementThree}>Three increments</button>
    </div>
  );
};
```

The three replacement calls compute from one snapshot; the three updater calls compose. A closure that retained an old render still retains it after a setter runs. Updater functions solve the pending-state calculation; they do not magically refresh every other captured value.

## Objects are replaced, not merged

Unlike class `setState`, a Hook setter replaces the entire value. Preserve unchanged fields explicitly and copy every changed nested level. A shallow spread still shares untouched nested objects.

```tsx
setUser(previous => ({ ...previous, name: 'John' }));
```

Mutating an existing array/object and passing the same reference can cause an equality bailout and corrupt earlier snapshots. Prefer immutable `map`, `filter` and spread updates, as shown in [Complex State Updates](#complex-state-updates).

## Initialization belongs to a component identity

Pass a function for expensive initial computation: `useState(() => createInitialValue())`. Passing `createInitialValue()` instead computes it whenever the component function runs, even though later renders ignore that initial-state argument.

Initializers and updaters must be pure. Development Strict Mode can call them twice to detect impurities, discarding one result. Generate identifiers in an event handler before queuing a pure update.

Prop changes do not rerun initialization. Preserve or reset local state deliberately; a changed component key starts a new state identity. To store a function as the value, wrap it in an initializer/updater rather than letting React treat it as one.

## Choose the smallest state that describes the UI

| Decision | Useful rule |
| ------------------------------------- | ------------------------------------------------------- |
| Collection and its count | Store the collection; derive its count during render |
| Unrelated values | Separate state variables are often clearer |
| Values that change as one transition | One object or a reducer can express the relationship |
| Complex transition rules | Consider `useReducer` to centralize and test them |
| Data shared by several components | Place ownership at their nearest useful common boundary |
| Mutable value that need not render UI | Consider a ref; changing it does not request a render |

A reducer does not automatically make updates faster, and `useState` can update several related fields coherently in one object. Choose based on transitions and ownership rather than the number of fields alone.

## Practical state shapes

The following application snippets assume hooks, named components and domain types are available. Focus on the transition being taught. Production forms additionally need labels, validation and explicit pending/error behavior; see the form-handling chapters.

### Lazy Initialization

```typescript
const ExpensiveComponent = () => {
  // Passing an initializer avoids parsing on each update render.
  const [state] = useState(() => JSON.parse(largeJSON));
  // Browser-only example: server-rendered apps need matching initial state.
  const [theme] = useState(() => localStorage.getItem('theme') || 'light');
  return <div className={theme}>{state.title}</div>;
};
```

The initializer supplies state on mount, not on subsequent renders; development Strict Mode can invoke it twice to check purity. Prop changes do not rerun initialization. To reset an entire component's local state for a different record, change its key as explained in [Reconciliation](../01-react-internals/10.3.1.03-reconciliation.md#decide-when-state-should-survive).

### Complex State Updates

```typescript
const TodoApp = () => {
  const [todos, setTodos] = useState<Todo[]>([]);

  const addTodo = (text: string) => {
    const id = crypto.randomUUID();
    setTodos(prev => [...prev, { id, text, completed: false }]);
  };

  const toggleTodo = (id: string) => {
    setTodos(prev =>
      prev.map(todo =>
        todo.id === id ? { ...todo, completed: !todo.completed } : todo
      )
    );
  };

  const deleteTodo = (id: string) => {
    setTodos(prev => prev.filter(todo => todo.id !== id));
  };

  return (
    <div>
      <TodoInput onAdd={addTodo} />
      <TodoList todos={todos} onToggle={toggleTodo} onDelete={deleteTodo} />
    </div>
  );
};

```


### Form State Management

```typescript
const ContactForm = () => {
  const [formData, setFormData] = useState({
    name: '',
    email: '',
    message: '',
  });
  const [errors, setErrors] = useState<Record<string, string>>({});
  const [isSubmitting, setIsSubmitting] = useState(false);

  const validate = (): boolean => {
    const newErrors: Record<string, string> = {};
    if (!formData.name) newErrors.name = 'Name is required';
    if (!formData.email) newErrors.email = 'Email is required';
    if (!formData.message) newErrors.message = 'Message is required';
    setErrors(newErrors);
    return Object.keys(newErrors).length === 0;
  };

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    if (!validate()) return;

    setIsSubmitting(true);
    try {
      await submitForm(formData);
      setFormData({ name: '', email: '', message: '' });
    } finally {
      setIsSubmitting(false);
    }
  };

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={formData.name}
        onChange={e => setFormData(prev => ({ ...prev, name: e.target.value }))}
      />
      {errors.name && <span>{errors.name}</span>}
      {/* ... other fields */}
      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? 'Submitting...' : 'Submit'}
      </button>
    </form>
  );
};

```

### Toggle State

```typescript
const Modal = () => {
  const [isOpen, setIsOpen] = useState(false);

  const openModal = () => setIsOpen(true);
  const closeModal = () => setIsOpen(false);
  const toggleModal = () => setIsOpen(prev => !prev);

  return (
    <>
      <button onClick={toggleModal}>Toggle Modal</button>
      {isOpen && (
        <div className="modal">
          <h2>Modal Title</h2>
          <p>Modal content</p>
          <button onClick={closeModal}>Close</button>
        </div>
      )}
    </>
  );
};

```

### Array State

```typescript
const TagInput = () => {
  const [tags, setTags] = useState<string[]>([]);
  const [inputValue, setInputValue] = useState('');

  const addTag = () => {
    if (inputValue && !tags.includes(inputValue)) {
      setTags(prev => [...prev, inputValue]);
      setInputValue('');
    }
  };

  const removeTag = (tagToRemove: string) => {
    setTags(prev => prev.filter(tag => tag !== tagToRemove));
  };

  return (
    <div>
      <div className="tags">
        {tags.map(tag => (
          <span key={tag} className="tag">
            {tag}
            <button onClick={() => removeTag(tag)}>×</button>
          </span>
        ))}
      </div>
      <input
        value={inputValue}
        onChange={e => setInputValue(e.target.value)}
        onKeyDown={e => { if (e.key === 'Enter') { e.preventDefault(); addTag(); } }}
      />
      <button onClick={addTag}>Add</button>
    </div>
  );
};

```

### Dependent State

```typescript
const MultiStepForm = () => {
  const [step, setStep] = useState(1);
  const [formData, setFormData] = useState({
    personal: { name: '', email: '' },
    address: { street: '', city: '', zip: '' },
    payment: { card: '', expiry: '' },
  });

  const nextStep = () => setStep(prev => Math.min(prev + 1, 3));
  const prevStep = () => setStep(prev => Math.max(prev - 1, 1));

  const updatePersonal = (data: Partial<typeof formData.personal>) => {
    setFormData(prev => ({
      ...prev,
      personal: { ...prev.personal, ...data },
    }));
  };

  return (
    <div>
      <StepIndicator currentStep={step} totalSteps={3} />
      {step === 1 && (
        <PersonalInfo
          data={formData.personal}
          onChange={updatePersonal}
          onNext={nextStep}
        />
      )}
      {step === 2 && (
        <Address
          data={formData.address}
          onChange={data => setFormData(prev => ({ ...prev, address: data }))}
          onNext={nextStep}
          onBack={prevStep}
        />
      )}
      {step === 3 && (
        <Payment
          data={formData.payment}
          onChange={data => setFormData(prev => ({ ...prev, payment: data }))}
          onBack={prevStep}
          onSubmit={() => submitForm(formData)}
        />
      )}
    </div>
  );
};

```

## Common failure patterns

| Symptom | Mechanism to inspect |
| ----------------------------------------- | ---------------------------------------------------------------- |
| Setter followed by an old logged value | Current handler still sees its render snapshot |
| Repeated increments produce one increment | Replacement values computed from the same snapshot |
| Object update removes another field | Setter replaced the object rather than merging it |
| UI does not reflect a mutation | Same reference, equality bailout and violated snapshot ownership |
| Endless rendering | Unconditional setter during render |
| Initial state ignores a changed prop | Initializer is not rerun for an existing identity |

Do not unconditionally set state while rendering. React supports rare terminating conditional updates to the currently rendering component, but those restart rendering and need careful reasoning. Deriving a value is usually simpler than storing and synchronizing it. Updates to another component during render are an error-prone pattern.

## How React associates state with the right component

Hook call order identifies state records within a component's Fiber; component position/type/key determine its identity. Call hooks at the top level in a stable order. A setter's identity remains stable for that mounted state record. The internal linked-list representation explains current implementation behavior, but application correctness should rely on the public identity and Hook rules rather than a guessed memory layout.

## Summary

Identify the component that owns the data, then follow its render snapshot and update queue. Use replacements for complete next values, updaters for pending-state transitions, and immutable copies for changed objects. Keep initializers pure and derived values out of stored state.

# useEffect

## Definition

`useEffect` keeps a committed React component synchronized with something outside React, such as a browser event listener, timer or network connection. Its **setup** starts that synchronization; its optional **cleanup** stops or invalidates the previous setup.

For example, a resize listener should exist while a size display is on screen. Creating the listener during rendering would be unsafe: React can render more than once or discard a render. An effect attaches it after commit and removes it when the component leaves.

> **Textbook Definition:** `useEffect` declares synchronization with an external system after a component commits. React runs cleanup before a changed dependency triggers new setup and on unmount; execution after browser paint is not a universal guarantee.

## First Principles


Rendering calculates the UI. External resources have a separate lifetime: a listener can keep firing even after that UI disappears. React therefore needs a way to connect a committed result to the external system and later disconnect it.

A setup also captures the props and state of its render. If the connection depends on a changed value, the previous setup no longer describes the required connection. Dependencies identify when that synchronization must be replaced.

## Follow one listener from setup to cleanup

This complete browser component displays the latest viewport width after its effect runs. The initial placeholder also keeps server and first-client markup consistent.

```tsx
import { useEffect, useState } from 'react';

export function ViewportWidth() {
  const [width, setWidth] = useState<number | null>(null);

  useEffect(() => {
    function updateWidth() {
      setWidth(window.innerWidth);
    }
    updateWidth();
    window.addEventListener('resize', updateWidth);
    return () => window.removeEventListener('resize', updateWidth);
  }, []);

  return <p>Width: {width === null ? 'Reading…' : `${width}px`}</p>;
}
```

1. React renders the placeholder and commits it.
2. Setup reads the browser width and attaches one listener.
3. A resize calls `updateWidth`; the resulting state update renders the new width.
4. The empty dependency list means that width update does not replace this listener.
5. Cleanup removes the same callback when this setup is retired.

The state setter has a stable identity, and the callback is created inside setup. This effect does not read a changing prop or state value, so `[]` accurately describes its reactive inputs.

## Dependencies decide which setup becomes obsolete

A **reactive value** is a prop, state value or component-local value that can differ between renders. Include the reactive values setup reads; do not choose the list merely to force a preferred frequency. React compares each entry using `Object.is`.

| Dependency argument | When synchronization is replaced |
| ------------------- | --------------------------------------------------------------------------- |
| Omitted | After each committed render |
| `[]` | No reactive-input replacement; mounting and real remounting still run setup |
| `[roomId]` | On mount, then after a commit where `roomId` differs |

```text
mount                 → setup for room A
commit with room B    → cleanup for A → setup for B
commit with same room → keep current setup
unmount               → cleanup for B
```

Cleanup captures the old render's values. It does not receive the new room and should release the resource created by its own setup.

A freshly created object or function has a new identity. If it is a dependency, an otherwise unchanged render can replace setup. Often the clearest fix is to create that helper inside the effect or depend on the primitive inputs it actually needs. Removing a required dependency hides the problem and can leave stale behavior.

## Development replay tests whether cleanup matches setup

Strict Mode can run an extra development setup → cleanup → setup cycle. The result should behave like a single active setup. A second subscription or timer usually means cleanup did not undo setup correctly.

An empty dependency list does not mean “once forever.” A real remount starts another lifecycle. A ref used only to suppress a second setup can conceal broken cleanup rather than repair it.

## Commit is guaranteed; after-paint timing is not

Effects run after commit, not for discarded renders, and do not run during server rendering. For work unrelated to an interaction, React generally lets the browser paint first. Interaction-related effects and other scheduling paths can run before paint.

Use `useLayoutEffect` for necessary layout measurement or visual correction that must finish before paint. Its synchronous work can delay painting, so keep it small. A passive effect callback also runs JavaScript synchronously when invoked; expensive work can still block the main thread.

## Decide whether you need an effect at all

| Task | Natural home | Reason |
| ----------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| Filter a list from current props/state | Render calculation | No external system needs synchronization |
| Submit after a user clicks Save | Event handler | The action has a specific user trigger |
| Keep a subscription aligned with `roomId` | Effect | Connection lifetime follows committed inputs |
| Measure layout before displaying a tooltip | Layout effect when required | A visible correction may need to precede paint |
| Load server data with caching and routing needs | Framework loader or server-state library where available | Avoid rebuilding caching, deduplication and navigation behavior |

Effects are not a direct translation of class lifecycle methods. Think of each as a synchronization process, and split unrelated processes when they have different inputs or lifetimes.

## Async work needs both ownership and stale-result protection

The effect callback must return nothing or a cleanup function, not a promise. Define an async function inside setup and invoke it there.

A request for an old identity can finish after a newer request. Cancellation can stop supported work; a separate active/identity guard prevents obsolete work from publishing data, errors or loading state. Guard `finally` too: an old request must not clear a newer request's loading indicator.

A cancelled request is not automatically a memory leak. The questions are whether unwanted work continues and whether an obsolete result can still affect the UI. The complete lifecycle example is [Fetch with Abort Controller](#fetch-with-abort-controller).

## Apply the same lifecycle to different external systems

Choose the case you need after understanding the listener trace. These snippets assume React hooks are imported and any named application components/types exist. Their APIs illustrate lifecycle mechanics; they are not a complete production library.

### Timer with Cleanup

The interval lifetime depends on `delay`; the callback ref lets later ticks use the callback from the most recent passive-effect flush without restarting the timer for every callback identity. A tick between commit and that flush can still see the previous callback. If that gap matters, update the ref in a layout effect or use the applicable modern effect-event pattern; do not write it during render.

```typescript
const useInterval = (callback: () => void, delay: number | null) => {
  const savedCallback = useRef(callback);

  // Remember the latest callback
  useEffect(() => {
    savedCallback.current = callback;
  }, [callback]);

  // Set up the interval
  useEffect(() => {
    if (delay === null) return;

    const id = setInterval(() => savedCallback.current(), delay);
    return () => clearInterval(id);
  }, [delay]);
};

// Usage
const Clock = () => {
  const [time, setTime] = useState(new Date());

  useInterval(() => {
    setTime(new Date());
  }, 1000);

  return <div>{time.toLocaleTimeString()}</div>;
};

```

### Document Title Sync

This illustrates restoring a previous value. If several components own the document title, coordinate that ownership instead of letting independent cleanups overwrite one another.

```typescript
const useDocumentTitle = (title: string) => {
  useEffect(() => {
    const prevTitle = document.title;
    document.title = title;

    return () => {
      document.title = prevTitle;
    };
  }, [title]);
};

const Dashboard = () => {
  useDocumentTitle('Dashboard - MyApp');
  return <div>Dashboard</div>;
};

```

### Intersection Observer

Observer options affect setup identity, so passing a fresh options object can disconnect and recreate the observer after each render. A stable ref object does not notify this hook if its DOM target changes; this example assumes the target is stable. Use stable options and explicit target state or a callback-ref design for replaceable nodes.

```typescript
const useIntersectionObserver = (
  ref: React.RefObject<HTMLElement | null>,
  options?: IntersectionObserverInit
) => {
  const [isVisible, setIsVisible] = useState(false);

  useEffect(() => {
    const element = ref.current;
    if (!element) return;

    const observer = new IntersectionObserver(([entry]) => {
      setIsVisible(entry.isIntersecting);
    }, options);

    observer.observe(element);

    return () => observer.disconnect();
  }, [ref, options]);

  return isVisible;
};

// Usage
const LazyImage = ({ src, alt }: { src: string; alt: string }) => {
  const ref = useRef<HTMLDivElement>(null);
  const observerOptions = useMemo(() => ({ threshold: 0.1 }), []);
  const isVisible = useIntersectionObserver(ref, observerOptions);

  return (
    <div ref={ref}>
      {isVisible ? <img src={src} alt={alt} /> : <div className="placeholder" />}
    </div>
  );
};

```

### Fetch with Abort Controller

This focuses on cleanup and result ownership. The generic `T` is only a TypeScript annotation: validate untrusted JSON before treating it as application data. Also define whether an identity change clears or intentionally retains previous data while the new request is pending.

```typescript
const useFetch = <T,>(url: string) => {
  const [data, setData] = useState<T | null>(null);
  const [error, setError] = useState<Error | null>(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    const controller = new AbortController();
    let active = true;

    const fetchData = async () => {
      setLoading(true);
      setError(null);

      try {
        const response = await fetch(url, {
          signal: controller.signal,
        });

        if (!response.ok) {
          throw new Error(`HTTP error! status: ${response.status}`);
        }

        const result = await response.json();
        if (active) setData(result);
      } catch (err) {
        if (active) setError(err instanceof Error ? err : new Error(String(err)));
      } finally {
        if (active) setLoading(false);
      }
    };

    fetchData();

    return () => { active = false; controller.abort(); };
  }, [url]);

  return { data, error, loading };
};

// Usage
const UserList = () => {
  const { data: users, error, loading } = useFetch<User[]>('/api/users');

  if (loading) return <Spinner />;
  if (error) return <div>Error: {error.message}</div>;
  return <ul>{users?.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
};

```

Aborting cancels supported fetch work; the active flag separately prevents a superseded request from publishing data, errors or its `finally` loading update. Without that guard, cleanup of an old URL can clear the loading state for a newer request.

### Real-Time Search with Debouncing

```typescript
const useDebounce = <T,>(value: T, delay: number): T => {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const handler = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);

    return () => clearTimeout(handler);
  }, [value, delay]);

  return debouncedValue;
};

const SearchInput = () => {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<SearchResult[]>([]);
  const [error, setError] = useState<string | null>(null);
  const debouncedQuery = useDebounce(query, 300);

  useEffect(() => {
    let active = true;
    setError(null);
    if (!debouncedQuery) setResults([]);
    else searchAPI(debouncedQuery)
      .then(data => { if (active) setResults(data); })
      .catch(err => { if (active) setError(err instanceof Error ? err.message : String(err)); });
    return () => { active = false; };
  }, [debouncedQuery]);

  return <><input value={query} onChange={e => setQuery(e.target.value)} />
    {error && <p>{error}</p>}<ResultList results={results} /></>;
};

```

Because the request starts in an Effect, the previous result can remain visible briefly after the debounced query changes. If that would mislabel results, store the query alongside each result and render it only when the identities match, or show an explicit pending state.

### WebSocket Connection

This shows connection replacement, not reconnection/backoff or a validated message protocol. Validate incoming messages and define bounded history and cross-connection message retention before using it in a product.

```typescript
const useWebSocket = (url: string) => {
  const [messages, setMessages] = useState<Message[]>([]);
  const [isConnected, setIsConnected] = useState(false);
  const socketRef = useRef<WebSocket | null>(null);

  useEffect(() => {
    const ws = new WebSocket(url);
    socketRef.current = ws;
    setIsConnected(false);
    ws.onopen = () => setIsConnected(true);
    ws.onclose = () => setIsConnected(false);
    ws.onmessage = event => {
      const message = JSON.parse(event.data);
      setMessages(previous => [...previous, message]);
    };
    return () => {
      // Ignore callbacks from the superseded connection.
      ws.onopen = ws.onclose = ws.onmessage = null;
      if (socketRef.current === ws) socketRef.current = null;
      ws.close();
    };
  }, [url]);

  const sendMessage = (message: unknown) => {
    const ws = socketRef.current;
    if (!ws || ws.readyState !== WebSocket.OPEN) return false;
    ws.send(JSON.stringify(message));
    return true;
  };
  return { messages, isConnected, sendMessage };
};
```

### localStorage Sync

This example assumes `key` stays stable for the component's lifetime. Changing it does not rerun the state initializer, and the write Effect can copy the old value to the new key; remount by key or implement an explicit read-before-write transition. It does not listen for other tabs' storage changes. During server rendering, `window` is unavailable, so this initializer falls back to `initialValue`; if the browser reads a different stored value during hydration, the first client render can mismatch the server. An SSR-safe design uses the same initial value on both sides, reads storage after hydration, and waits for that read before writing.

`JSON.parse` returns untrusted data at runtime; the generic `T` does not validate it. Validate the stored value before returning it as application state.

```typescript
const useLocalStorage = <T,>(key: string, initialValue: T) => {
  const [storedValue, setStoredValue] = useState<T>(() => {
    try {
      const item = window.localStorage.getItem(key);
      return item ? JSON.parse(item) : initialValue;
    } catch (error) {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(storedValue));
    } catch (error) {
      console.error(error);
    }
  }, [key, storedValue]);

  return [storedValue, setStoredValue] as const;
};

// Usage
const ThemeToggle = () => {
  const [theme, setTheme] = useLocalStorage('theme', 'light');

  return (
    <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
      Current: {theme}
    </button>
  );
};

```

### Geolocation

```typescript
const useGeolocation = () => {
  const [location, setLocation] = useState<GeolocationPosition | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (!navigator.geolocation) {
      setError('Geolocation not supported');
      return;
    }

    let active = true;
    navigator.geolocation.getCurrentPosition(
      position => { if (active) setLocation(position); },
      err => { if (active) setError(err.message); }
    );
    return () => { active = false; }; // One-shot requests have no cancellation handle.
  }, []);

  return { location, error };
};

```

## Diagnose the failure before adding another effect

| Symptom | Check first |
| ---------------------------------- | --------------------------------------------------------------- |
| Old prop/state is still used | Missing reactive dependency or a deliberately retained callback |
| Setup runs after every update | Unstable object/function dependency, or no dependency argument |
| Endless updates | Setup changes state that changes one of its own dependencies |
| Duplicate listeners/timers | Missing or mismatched cleanup |
| Old request overwrites new results | Missing stale-result guard; cancellation may be insufficient |
| Derived state lags by one render | Calculation unnecessarily moved into an effect |
| Visual correction flickers | Whether layout work must happen before paint |

## Summary

Model one setup and its matching cleanup. Dependencies describe the committed inputs that make that setup valid; when they change, retire the old setup before starting its replacement. Keep render calculations and user-triggered actions in their natural locations, and give async work an explicit stale-result policy.

# React Context API

A deeply nested account menu needs the signed-in user's display name. Passing it through every layout component adds props to components that do not use the value. Context lets the menu read a value supplied by an ancestor, while keeping the provider's scope visible in the component tree.

```tsx
const ThemeContext = createContext<'light' | 'dark'>('light');

function ThemeLabel() {
  return <span>Current theme: {useContext(ThemeContext)}</span>;
}
// Somewhere above: <ThemeContext value="dark"><Page /></ThemeContext>
```

## Definition

**Practical definition:** React Context makes a value available to components below a provider without passing it through every intermediate component as a prop. The provider defines its scope, and readers receive updates when its value changes.

> **Textbook Definition:** Context is a tree-scoped value propagation mechanism. A context read resolves to the value of the nearest matching provider above the reading component, or to the context's default value when no provider exists.

The context object identifies the channel; it does not hold mutable application state. State usually lives in a component or reducer, and that owner passes its current value to the provider.

The default passed to `createContext` applies only when no matching provider exists above the reader. A matching provider with `value={undefined}` supplies `undefined`; it does not fall back to the context default.

## First Principles

Context follows from three constraints in a component tree. **A value has a scope**: a provider serves its descendants, and a nested provider for the same context starts a new scope. **The reader selects the nearest scope**: `useContext(Context)` reads the closest matching provider above — a provider returned by the same component sits below its own read and cannot supply it. **A changed value updates its readers**: React compares old and new values with `Object.is`; `memo` never blocks a context update, and context offers no per-field selectors.

```text
ThemeContext("dark")
└── Page
    ├── Header             reads "dark"
    └── Preview
        └── ThemeContext("light")
            └── PreviewCard reads "light"
```

## 1. Give the Subtree a Value

Create the context once, then keep the state that changes in its provider. An `undefined` default makes a missing provider visible instead of silently supplying a plausible but incorrect value:

```tsx
import { createContext, useContext, useState, type ReactNode } from 'react';

type Theme = 'light' | 'dark';
const ThemeContext = createContext<Theme | undefined>(undefined);

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');
  const toggleTheme = () => {
    setTheme((current) => current === 'light' ? 'dark' : 'light');
  };

  return (
    // React 19+: <ThemeContext value={theme}>.
    // React 18: use <ThemeContext.Provider value={theme}>.
    <ThemeContext value={theme}>
      <button type="button" onClick={toggleTheme}>Toggle theme</button>
      {children}
    </ThemeContext>
  );
}

export function useTheme(): Theme {
  const theme = useContext(ThemeContext);
  if (theme === undefined) {
    throw new Error('useTheme must be used inside ThemeProvider');
  }
  return theme;
}

export function ThemeLabel() {
  return <span>Current theme: {useTheme()}</span>;
}
```

The provider owns the state; `ThemeLabel` only reads it. If a default such as `'light'` is a meaningful fallback for every consumer, use that default instead of the fail-fast hook.

In React 19, the context object itself can be rendered as the provider; React 18 uses its `.Provider` property.

Starting in React 19.3, a Server Component can import a context created in a Client Component module and render that context directly around descendants. Server Components still cannot create a context or read one with useContext; Client Components below the provider consume its value. Before React 19.3, a Server Component used a provider wrapper exported from the client module for this boundary. See the [React 19.3 release notes](https://react.dev/blog/2026/09/09/react-19-3).

A Server Component can fetch the request-specific value and render the imported context around Client Component descendants:

```tsx
// user-context.tsx
"use client";
import { createContext } from "react";
export const UserContext = createContext<User | null>(null);

// layout.tsx — Server Component
import { UserContext } from "./user-context";
import type { ReactNode } from "react";

// User and getCurrentUser are application-specific.
export default async function Layout({ children }: { children: ReactNode }) {
  const user = await getCurrentUser();
  return <UserContext value={user}>{children}</UserContext>;
}
```

The context object is still created in a Client Component module. Server Components can provide it in 19.3, but only Client Components below it can consume the context. The value crossing into the client must be serializable and safe to expose; a provider does not make server-only secrets suitable for client code.

## 2. Keep Updates Within the Value's Actual Scope

Passing an object literal as `value` creates a new reference whenever the provider renders, even if its fields did not change. The new reference can update every reader in the subtree. When profiling shows those unrelated updates matter, stabilize the object and any functions it contains:

```tsx
import { createContext, useCallback, useMemo, useState, type ReactNode } from 'react';

interface User { id: string; name: string }
interface AuthValue { user: User | null; logout: () => void }

const AuthContext = createContext<AuthValue | undefined>(undefined);

function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const logout = useCallback(() => setUser(null), []);
  const value = useMemo(() => ({ user, logout }), [user, logout]);

  return <AuthContext value={value}>{children}</AuthContext>;
}
```

Memoization only avoids updates when the provider renders for another reason and the dependencies are unchanged. When `user` changes, readers of `AuthContext` still need the new value. Keep this optimization tied to an observed render cost; it does not make context a field-by-field subscription.

If some components need changing state while others need only stable commands, separate those channels. A reducer's `dispatch` function has stable identity, so dispatch-only readers do not update because the state context changed:

```tsx
import { createContext, useReducer, type Dispatch, type ReactNode } from 'react';

type Action = { type: 'increment' };
function countReducer(count: number, action: Action): number {
  switch (action.type) {
    case 'increment': return count + 1;
  }
}

const CountState = createContext<number | undefined>(undefined);
const CountDispatch = createContext<Dispatch<Action> | undefined>(undefined);

function CountProvider({ children }: { children: ReactNode }) {
  const [count, dispatch] = useReducer(countReducer, 0);
  return (
    <CountState value={count}>
      <CountDispatch value={dispatch}>{children}</CountDispatch>
    </CountState>
  );
}
```

The separate dispatch context only avoids a context-driven update for dispatch readers. An ancestor can still render them for other reasons. Split contexts when their consumers have different update needs, and measure before adding more provider structure.

## 3. Choose Context for Scoped Dependencies

Context fits values such as a theme, locale, feature configuration, or a low-churn client session used across a subtree. It is less suitable for rapidly changing values when many consumers need only selected fields; a store with selector-based subscriptions may reduce unrelated work. Component composition can also remove the need for a shared channel: let a layout receive the menu as `children` when it only needs to place it.

Context is not an authorization boundary. A client session can control what the interface displays, but each protected server operation must still authenticate the request and authorize access to the requested resource.

## Summary

Context makes an ancestor-owned value available to descendant readers, with nested providers defining scope. Use it for dependencies shared across a subtree, keep the provider close to those readers, and choose the update boundary deliberately. For frequently changing state, evaluate selector-based stores; for protected data, enforce authorization on the server.

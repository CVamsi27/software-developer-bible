# React Context API

A button needs the active theme, but the theme is owned near the top of the application. Passing `theme` through every layout and panel works, but most of those components do not use it. Context lets the owner provide a value to a subtree and lets only the components that need it read that value.

## Definition

**React Context** is a way to make a value available to components below a provider without passing it through every intermediate component as a prop. The provider establishes the value for a part of the React tree; a consumer reads the closest matching provider above itself with `useContext`.

> **Textbook Definition:** Context is a tree-scoped dependency propagation mechanism: a provider supplies a value to descendant components, and a context read resolves to the nearest matching provider in the component ancestry, or to the context's static default when none exists.

The context object identifies the kind of value being provided; it does not store changing application state by itself. State usually lives in a component above the provider and is passed down as the provider's `value`.

## First Principles

A prop is an explicit dependency between a parent and child. When an intermediate component receives a prop only to pass it farther down, the data path grows even though that component does not depend on the data. If the value belongs to a subtree, context removes those pass-through props while keeping the dependency tied to that subtree.

That convenience has a cost: the dependency is less visible in a component's props, and every component that reads the context subscribes to its value. Use context for values that many distant descendants need; use props or `children` composition when the data belongs to a small, visible part of the tree.

## Let the value follow the tree

Create the context once, outside components. This example keeps theme state in `ThemeProvider` and makes the current value available to any descendant button:

```jsx
import { createContext, useContext, useState } from 'react';

const ThemeContext = createContext('light');

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');

  return (
    <ThemeContext value={theme}>
      {children}
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
        Switch theme
      </button>
    </ThemeContext>
  );
}

function SaveButton() {
  const theme = useContext(ThemeContext);
  return <button className={`button-${theme}`}>Save</button>;
}
```

`SaveButton` can be nested under any number of components; each intermediate component can render its `children` without accepting a `theme` prop. When `setTheme` changes state, the provider receives a different value and React updates components that read this context.

This provider syntax, `<ThemeContext value={theme}>`, is supported in React 19 and later. In React 18 and earlier, write `<ThemeContext.Provider value={theme}>`. The lookup and update behavior is otherwise the same.

## A consumer reads the nearest provider above it

React searches upward from the component calling `useContext` and returns the value from the closest provider for that context. A nested provider can override a value for one subtree:

```jsx
<ThemeContext value="dark">
  <AppShell />
  <ThemeContext value="light">
    <Footer />
  </ThemeContext>
</ThemeContext>
```

`AppShell` and its descendants read `"dark"`; `Footer` and its descendants read `"light"`. A provider returned by the same component does not affect that component's own `useContext` call—the provider must be above the reader in the rendered tree.

`createContext(defaultValue)` supplies a static fallback only when no matching provider exists above the reader. A provider with `value={undefined}` supplies `undefined`; it does not fall back to the default. Choose a useful default when the component has a valid standalone behavior, such as a light theme. For a required dependency, use an undefined default and fail clearly when the provider is missing.

## Keep updates proportional to what changed

React compares a provider's previous and next `value` with `Object.is`. Components that read that context update when the value changes. A new object or function created during every provider render has a new identity, even when its fields are unchanged:

```jsx
const AuthContext = createContext(null);

function AuthProvider({ user, signOut, children }) {
  return (
    <AuthContext value={{ user, signOut }}>
      {children}
    </AuthContext>
  );
}
```

That can update every `AuthContext` consumer after an unrelated parent render. If profiling shows this work matters, stabilize the function with `useCallback` and the value object with `useMemo`:

```tsx
import { createContext, useCallback, useMemo, useState, type ReactNode } from 'react';

type User = { id: string; role: 'member' | 'admin' };
type AuthValue = { user: User | null; signOut: () => void };
const AuthContext = createContext<AuthValue | undefined>(undefined);

function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const signOut = useCallback(() => setUser(null), []);
  const value = useMemo(() => ({ user, signOut }), [user, signOut]);
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}
```

This avoids updates when the underlying inputs are unchanged; it does not stop consumers from updating when the context value really changes. Wrapping a consumer in `memo` does not block a context update it reads.

Split values with different update rates or consumers into separate contexts when measurement shows a benefit. For example, rarely changing locale can have its own context instead of sharing one object with a rapidly changing pointer position. Do not add memoization or split contexts preemptively; the extra providers and dependencies also cost clarity.

Context is not a selector store. A consumer subscribed to one context receives its value as a whole. For high-frequency, large state where components need fine-grained subscriptions, compare an external store or a state library designed for selectors.

## Make required dependencies fail at the boundary

In TypeScript, an `undefined` default can turn a missing provider into a clear error rather than silently supplying an incomplete value:

```tsx
import { createContext, useContext } from 'react';

type Session = { userId: string; role: 'member' | 'admin' };
const SessionContext = createContext<Session | undefined>(undefined);

export function useSession(): Session {
  const session = useContext(SessionContext);
  if (session === undefined) {
    throw new Error('useSession must be used inside SessionProvider');
  }
  return session;
}
```

The provider should still be placed at the narrowest ancestor that owns the session and its lifetime. A context value can control which UI is shown, but it is not an authorization boundary: the server must independently check permissions for protected operations.

## Choose context when the dependency belongs to a subtree

| Need | Good starting point | Why |
| -------------------------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------- |
| A few nearby children need a value | Props or `children` composition | The dependency stays visible at the call site. |
| Many distant descendants need theme, locale or a stable session view | Context | The owning subtree supplies one value without pass-through props. |
| Shared state has transitions and invariants | `useReducer` with context, or a state library | The reducer centralizes transitions; context distributes the state and dispatch. |
| Many components read small slices of rapidly changing state | An external store or selector-based library | Consumers can subscribe to the pieces they use. |
| A form field or temporary interaction has one owner | Local component state | Context would widen the lifetime and dependency unnecessarily. |

A context provider can be composed with other providers in an application root, but keep that composition readable. Give each context one coherent responsibility instead of building a single `AppContext` that changes for unrelated reasons. Authentication, localization and cart state have different update and security boundaries; their full designs belong in the relevant state-management and security chapters.

## Test the behavior through a provider

Render consumers under the real provider and verify observable behavior: a theme switch changes the button's class, or a required session hook reports a missing provider. Tests should also cover the value a consumer sees when providers are nested. Avoid asserting React's internal propagation implementation; the contract is the value available to the component and the resulting UI.

## Summary

Context carries a provider's value to descendants without pass-through props. A reader gets the nearest provider above it, or the static default if none exists. Keep state at the component that owns its lifetime, watch provider value identity, and choose another state mechanism when consumers need fine-grained subscriptions. Context changes UI dependencies; it never replaces server authorization.

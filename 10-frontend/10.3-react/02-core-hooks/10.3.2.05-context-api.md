# Context API

## Definition

**React Context** lets a component provide a value to descendants without passing it as a prop at every intermediate level. For example, a provider can supply a theme, authentication status or language preference. A component that reads that context uses the nearest matching provider above it in the React tree. It need not be a direct child of that provider.

Context consists of three parts:

1. **Context Object**: Created with `React.createContext(defaultValue)`

2. **Provider**: Wraps the component tree to provide the value

3. **Consumer**: Reads the value from the nearest Provider

> **Textbook Definition:** Context supplies a value from the nearest matching provider to descendant consumers. A provider value change, compared with `Object.is`, updates subscribing consumers independently of an ancestor's prop-memoization decision.

## First Principles


1. **A distant descendant may need a value its intermediate parents do not use.** Passing the value through every layer couples those parents to transport. Context lets the descendant resolve a value from the nearest matching provider in the rendered tree.
2. **Transport does not define how a value changes.** State, a reducer or an external store still owns writes. Context publishes the owner's current value; the provider's position determines which descendants see it, and an absent provider uses the static default.
3. **Readers must observe a changed published value.** React compares provider values with `Object.is` and updates consumers when it changes, including consumers behind memo boundaries. Splitting independent values or stabilizing genuinely unchanged objects can reduce broad updates; update frequency alone does not forbid context.

## Why It Matters

Context works well for shared values such as theme, authentication status and locale. A changed provider value notifies its consumers, so a broad provider with many expensive readers can make frequent updates costly. Keep the provider close to its readers, split independent values and measure the result. When readers need independently selected pieces of rapidly changing data, a store with selector-based subscriptions may fit better. Context has no fixed update-frequency limit.

## The Problem It Solves

### The Problem: Prop Drilling

Without Context, data must be passed through props from parent to child, even if intermediate components don't need it:

```text
Prop Drilling Problem:
═══════════════════════════════════════════════════════════════

App (has theme state)
├── Layout (receives theme, passes it down)
│ ├── Sidebar (receives theme, passes it down)
│ │ └── ThemeToggle (NEEDS theme) ← Target
│ └── Main (receives theme, passes it down)
│ └── Content (receives theme, passes it down)
│ └── Article (NEEDS theme) ← Target

Problem: Layout, Sidebar, Main, Content all receive theme
props even though they don't use them!

```

### The Solution: Context

```text
Theme provider (value = dark)
├─ Layout → Sidebar → ThemeToggle (reads dark)
└─ Main → Content → Article (reads dark)
```

Each arrow shows a React child relationship. Intermediate components need no theme transport prop. A reader looks upward from its position, so a provider returned by that same reader is below it and cannot supply that reader's call to `useContext`. Put the owner above the reading component.

## How It Works

### Context Creation and Usage

The default is a static fallback used only when no matching provider exists above the consumer. A provider with `value={undefined}` does not fall back to the default. React 19 also supports `<ThemeContext value={theme}>`; `<ThemeContext.Provider>` remains the React 18-compatible form shown here.

```text
Context API Flow:
═══════════════════════════════════════════════════════════════

1. Create Context:
┌─────────────────────────────────────────────────────────────┐
│ const ThemeContext = React.createContext('light');          │
│ // Default value: 'light'                                   │
└─────────────────────────────────────────────────────────────┘

2. Provide Context:
┌─────────────────────────────────────────────────────────────┐
│ const App = () => {                                         │
│   const [theme, setTheme] = useState('light');              │
│                                                             │
│   return (                                                  │
│   <ThemeContext.Provider value={theme}>                     │
│   <Layout />                                                │
│   </ThemeContext.Provider>                                  │
│   );                                                        │
│ };                                                          │
└─────────────────────────────────────────────────────────────┘

3. Consume Context:
┌─────────────────────────────────────────────────────────────┐
│ const ThemeToggle = () => {                                 │
│   const theme = useContext(ThemeContext);                   │
│                                                             │
│   return <span>Current: {theme}</span>;                     │
│   // State setter is not supplied by a string-only context. │
│ };                                                          │
└─────────────────────────────────────────────────────────────┘

```

### Context Propagation

Only consumers under the provider whose value changed are notified, and a nearer provider shields its consumers from an outer value. `React.memo` cannot block a consumed-context update. Memoizing a provider object avoids changes caused solely by object allocation; it does not prevent ordinary parent-driven child renders or skip updates when a field actually changes.

Trace an outer provider changing from light to dark. A consuming Article below it observes dark even behind `memo`. A second Article below an inner light provider still observes light: its nearest source did not change. Layout can still execute because its parent rendered, even if Layout does not subscribe. Context notification and ordinary parent-driven rendering are separate paths.

### Consumer Component

```text
Consumer Component:
═══════════════════════════════════════════════════════════════

useContext Hook (Recommended):
┌─────────────────────────────────────────────────────────────┐
│ const ThemeToggle = () => {                                 │
│   const theme = useContext(ThemeContext);                   │
│   return <button>Current: {theme}</button>;                 │
│ };                                                          │
└─────────────────────────────────────────────────────────────┘

Consumer Component (Alternative):
┌─────────────────────────────────────────────────────────────┐
│ const ThemeToggle = () => {                                 │
│   return (                                                  │
│   <ThemeContext.Consumer>                                   │
│   {theme => <button>Current: {theme}</button>}              │
│   </ThemeContext.Consumer>                                  │
│   );                                                        │
│ };                                                          │
└─────────────────────────────────────────────────────────────┘

```

## Code Examples

### Basic Context

```typescript
import React, { createContext, useContext, useState } from 'react';
type ThemeValue = { theme: 'light' | 'dark'; toggleTheme: () => void };
const ThemeContext = createContext<ThemeValue | null>(null);

const ThemeProvider = ({ children }: { children: React.ReactNode }) => {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  const toggleTheme = () => setTheme(previous => previous === 'light' ? 'dark' : 'light');
  return <ThemeContext.Provider value={{ theme, toggleTheme }}>{children}</ThemeContext.Provider>;
};

const useTheme = () => {
  const value = useContext(ThemeContext);
  if (value === null) throw new Error('useTheme requires ThemeProvider');
  return value;
};

const ThemeToggle = () => {
  const { theme, toggleTheme } = useTheme();
  return <button onClick={toggleTheme}>Current: {theme}</button>;
};
const App = () => <ThemeProvider><ThemeToggle /></ThemeProvider>;
```

The null fallback makes a missing-provider guard meaningful. A context initialized to `'light'` would return that string outside a provider, so checking it for `undefined` would never detect a missing wrapper. The next optimization example stabilizes this object and callback when profiling shows identity-only updates matter.

### Context with Multiple Values

```typescript
interface AppContextType {
  theme: 'light' | 'dark';
  user: User | null;
  setTheme: (theme: 'light' | 'dark') => void;
  setUser: (user: User | null) => void;
}

const AppContext = createContext<AppContextType | null>(null);

const AppProvider = ({ children }: { children: React.ReactNode }) => {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  const [user, setUser] = useState<User | null>(null);

  const value = useMemo(() => ({
    theme,
    user,
    setTheme,
    setUser,
  }), [theme, user]);

  return (
    <AppContext.Provider value={value}>
      {children}
    </AppContext.Provider>
  );
};

const useApp = () => {
  const context = useContext(AppContext);
  if (!context) {
    throw new Error('useApp must be used within AppProvider');
  }
  return context;
};

```

### Context with Performance Optimization

```typescript
const ThemeContext = createContext<{
  theme: 'light' | 'dark';
  toggleTheme: () => void;
} | null>(null);

const ThemeProvider = ({ children }: { children: React.ReactNode }) => {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');

  const toggleTheme = useCallback(() => {
    setTheme(prev => (prev === 'light' ? 'dark' : 'light'));
  }, []);

  // Memoize context value to prevent unnecessary re-renders
  const value = useMemo(() => ({
    theme,
    toggleTheme,
  }), [theme, toggleTheme]);

  return (
    <ThemeContext.Provider value={value}>
      {children}
    </ThemeContext.Provider>
  );
};

```

### Context with TypeScript

```typescript
// Define context type
interface AuthContextType {
  user: User | null;
  login: (credentials: Credentials) => Promise<void>;
  logout: () => void;
  isAuthenticated: boolean;
}

// Create context with proper typing
const AuthContext = createContext<AuthContextType | null>(null);

// Provider component
const AuthProvider = ({ children }: { children: React.ReactNode }) => {
  const [user, setUser] = useState<User | null>(null);

  const login = useCallback(async (credentials: Credentials) => {
    const response = await api.login(credentials);
    setUser(response.user);
  }, []);

  const logout = useCallback(() => {
    setUser(null);
  }, []);

  const value = useMemo(() => ({
    user,
    login,
    logout,
    isAuthenticated: !!user,
  }), [user, login, logout]);

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  );
};

// Custom hook with proper error handling
const useAuth = (): AuthContextType => {
  const context = useContext(AuthContext);
  if (!context) {
    throw new Error('useAuth must be used within AuthProvider');
  }
  return context;
};

```

### Nested Context

```typescript
const ThemeContext = createContext('light');
const UserContext = createContext<User | null>(null);

const App = () => {
  const [theme, setTheme] = useState('light');
  const [user, setUser] = useState<User | null>(null);

  return (
    <ThemeContext.Provider value={theme}>
      <UserContext.Provider value={user}>
        <Layout />
      </UserContext.Provider>
    </ThemeContext.Provider>
  );
};

// Components can consume either context
const Header = () => {
  const theme = useContext(ThemeContext);
  const user = useContext(UserContext);

  return (
    <header className={theme}>
      {user ? `Welcome, ${user.name}` : 'Welcome, Guest'}
    </header>
  );
};

```

## Real-World Use Cases

### 1. Authentication Context

`parseUser` below is an application runtime decoder for the untrusted JSON response. A TypeScript annotation alone does not validate network data. The initial session lookup treats only HTTP 401 as anonymous; transport and server failures remain visible errors.

```typescript
interface AuthState {
  user: User | null;
  isLoading: boolean;
  error: Error | null;
}

interface AuthContextType extends AuthState {
  login: (email: string, password: string) => Promise<void>;
  logout: () => Promise<void>;
}

const AuthContext = createContext<AuthContextType | null>(null);

export const AuthProvider = ({ children }: { children: React.ReactNode }) => {
  // NOTE: the session token lives in an httpOnly cookie set by the server —
  // the client never touches it (localStorage is readable by any XSS payload).
  // The API layer sends credentials automatically; /api/me answers with the
  // session user or 401.
  const [state, setState] = useState<AuthState>({
    user: null,
    isLoading: true,
    error: null,
  });

  const sessionVersion = useRef(0);
  useEffect(() => {
    const controller = new AbortController();
    let active = true;
    const version = sessionVersion.current;
    const canPublish = () => active && version === sessionVersion.current;
    const loadSession = async () => {
      try {
        const res = await fetch('/api/me', { credentials: 'include', signal: controller.signal });
        if (res.status === 401) {
          if (canPublish()) setState({ user: null, isLoading: false, error: null });
          return;
        }
        if (!res.ok) throw new Error(`Session lookup failed: HTTP ${res.status}`);
        const user = parseUser(await res.json());
        if (canPublish()) setState({ user, isLoading: false, error: null });
      } catch (error) {
        if (canPublish()) {
          setState({
            user: null,
            isLoading: false,
            error: error instanceof Error ? error : new Error(String(error)),
          });
        }
      }
    };
    loadSession();
    return () => { active = false; controller.abort(); };
  }, []);

  const login = useCallback(async (email: string, password: string) => {
    const version = ++sessionVersion.current;
    // Server sets the httpOnly session cookie; the response carries the user
    try {
      const res = await fetch('/api/login', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        credentials: 'include',
        body: JSON.stringify({ email, password }),
      });
      if (!res.ok) throw new Error('Invalid credentials');
      const user = parseUser(await res.json());
      if (version === sessionVersion.current) setState({ user, isLoading: false, error: null });
    } finally {
      if (version === sessionVersion.current) setState(previous => ({ ...previous, isLoading: false }));
    }
  }, []);

  const logout = useCallback(async () => {
    const version = ++sessionVersion.current;
    try {
      const response = await fetch('/api/logout', { method: 'POST', credentials: 'include' });
      if (!response.ok) throw new Error('Logout failed');
      if (version === sessionVersion.current) setState({ user: null, isLoading: false, error: null });
    } finally {
      if (version === sessionVersion.current) setState(previous => ({ ...previous, isLoading: false }));
    }
  }, []);

  const value = useMemo(() => ({
    ...state,
    login,
    logout,
  }), [state, login, logout]);

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  );
};

export const useAuth = () => {
  const context = useContext(AuthContext);
  if (!context) {
    throw new Error('useAuth must be used within AuthProvider');
  }
  return context;
};

```

If login begins before the initial `/api/me` request finishes, incrementing the version invalidates that lookup. The newest action must therefore settle the initial loading state on failure too; otherwise the rejected lookup cannot clear it. Login and logout failures propagate to their caller, and the `finally` blocks preserve the current user while clearing that initial loading flag.

The session version prevents the initial session lookup or an older auth action from replacing the state of a newer action. It orders client result publication only; the API must still enforce authorization and handle conflicting concurrent session mutations.

### 2. Theme Context

```typescript
type Theme = 'light' | 'dark' | 'system';

interface ThemeContextType {
  theme: Theme;
  resolvedTheme: 'light' | 'dark';
  setTheme: (theme: Theme) => void;
}

const ThemeContext = createContext<ThemeContextType | null>(null);

export const ThemeProvider = ({ children }: { children: React.ReactNode }) => {
  // This initializer reads browser storage and can differ from server output.
  const [theme, setTheme] = useState<Theme>(() => {
    try {
      const stored = localStorage.getItem('theme');
      return stored === 'light' || stored === 'dark' || stored === 'system' ? stored : 'system';
    } catch { return 'system'; } // Storage may be unavailable.
  });

  const [resolvedTheme, setResolvedTheme] = useState<'light' | 'dark'>('light');

  useEffect(() => {
    const mediaQuery = window.matchMedia('(prefers-color-scheme: dark)');

    const getResolvedTheme = (): 'light' | 'dark' => {
      if (theme === 'system') {
        return mediaQuery.matches ? 'dark' : 'light';
      }
      return theme;
    };

    setResolvedTheme(getResolvedTheme());
    try { localStorage.setItem('theme', theme); } catch { /* Keep the in-memory choice. */ }

    const handleChange = () => {
      if (theme === 'system') {
        setResolvedTheme(mediaQuery.matches ? 'dark' : 'light');
      }
    };

    mediaQuery.addEventListener('change', handleChange);
    return () => mediaQuery.removeEventListener('change', handleChange);
  }, [theme]);

  const value = useMemo(() => ({
    theme,
    resolvedTheme,
    setTheme,
  }), [theme, resolvedTheme]);

  return (
    <ThemeContext.Provider value={value}>
      {children}
    </ThemeContext.Provider>
  );
};

export const useTheme = () => {
  const context = useContext(ThemeContext);
  if (!context) {
    throw new Error('useTheme must be used within ThemeProvider');
  }
  return context;
};

```

This local-storage initializer is not hydration-safe when the server cannot read the same preference. For SSR, provide the same initial theme from server-readable state; otherwise read storage after mount and accept a possible flash. A pre-hydration theme bootstrap can avoid that flash when the product requires it.

### 3. Internationalization Context

The following template import assumes a bundler configured to include those locale files. Restrict supported locales to a known list and handle a missing file; a runtime path alone does not guarantee that every translation asset ships. For a newly selected locale, distinguish its loading/error state from its loaded translations so the UI does not label the previous text as the new language.

```typescript
interface I18nContextType {
  locale: string;
  t: (key: string, params?: Record<string, any>) => string;
  setLocale: (locale: string) => void;
}

const I18nContext = createContext<I18nContextType | null>(null);

// Browser-only default; SSR should provide the same locale to server and client.
export const I18nProvider = ({ children }: { children: React.ReactNode }) => {
  const [locale, setLocale] = useState(() => {
    return navigator.language.split('-')[0] || 'en';
  });

  const [translations, setTranslations] = useState<Record<string, string>>({});

  useEffect(() => {
    let active = true;
    setTranslations({});
    import(`../locales/${locale}.json`)
      .then(module => { if (active) setTranslations(module.default); })
      .catch(error => { if (active) console.error('Translation load failed:', error); });
    return () => { active = false; };
  }, [locale]);

  const t = useCallback((key: string, params?: Record<string, any>) => {
    let translation = translations[key] || key;
    if (params) {
      Object.entries(params).forEach(([param, value]) => {
        translation = translation.split(`{{${param}}}`).join(String(value));
      });
    }
    return translation;
  }, [translations]);

  const value = useMemo(() => ({
    locale,
    t,
    setLocale,
  }), [locale, t]);

  return (
    <I18nContext.Provider value={value}>
      {children}
    </I18nContext.Provider>
  );
};

export const useI18n = () => {
  const context = useContext(I18nContext);
  if (!context) {
    throw new Error('useI18n must be used within I18nProvider');
  }
  return context;
};

```

### 4. Shopping Cart Context

This client display model assumes every item uses the same currency and stores price in integer minor units, such as cents. It requires nonnegative integer quantities and treats zero as removal. The server must recompute authoritative prices, currency, stock and checkout eligibility; client context is not a payment or authorization boundary. This sketch does not guard quantity increments or aggregate arithmetic against overflow; production code must enforce safe bounds or use decimal/big-integer arithmetic at the domain boundary.

```typescript
interface CartItem {
  id: string;
  name: string;
  priceMinorUnits: number;
  quantity: number;
}

interface CartContextType {
  items: CartItem[];
  addItem: (item: Omit<CartItem, 'quantity'>) => void;
  removeItem: (id: string) => void;
  updateQuantity: (id: string, quantity: number) => void;
  totalMinorUnits: number;
  itemCount: number;
}

const CartContext = createContext<CartContextType | null>(null);

export const CartProvider = ({ children }: { children: React.ReactNode }) => {
  const [items, setItems] = useState<CartItem[]>([]);

  const addItem = useCallback((item: Omit<CartItem, 'quantity'>) => {
    if (!Number.isSafeInteger(item.priceMinorUnits) || item.priceMinorUnits < 0) {
      throw new RangeError('priceMinorUnits must be a nonnegative safe integer');
    }
    setItems(prev => {
      const existing = prev.find(i => i.id === item.id);
      if (existing) {
        return prev.map(i =>
          i.id === item.id ? { ...i, quantity: i.quantity + 1 } : i
        );
      }
      return [...prev, { ...item, quantity: 1 }];
    });
  }, []);

  const removeItem = useCallback((id: string) => {
    setItems(prev => prev.filter(item => item.id !== id));
  }, []);

  const updateQuantity = useCallback((id: string, quantity: number) => {
    if (!Number.isSafeInteger(quantity) || quantity < 0) {
      throw new RangeError('quantity must be a nonnegative safe integer');
    }
    setItems(prev =>
      quantity === 0
        ? prev.filter(item => item.id !== id)
        : prev.map(item => item.id === id ? { ...item, quantity } : item)
    );
  }, []);

  const totalMinorUnits = useMemo(
    () => items.reduce((sum, item) => sum + item.priceMinorUnits * item.quantity, 0),
    [items]
  );

  const itemCount = useMemo(
    () => items.reduce((sum, item) => sum + item.quantity, 0),
    [items]
  );

  const value = useMemo(() => ({
    items,
    addItem,
    removeItem,
    updateQuantity,
    totalMinorUnits,
    itemCount,
  }), [items, addItem, removeItem, updateQuantity, totalMinorUnits, itemCount]);

  return (
    <CartContext.Provider value={value}>
      {children}
    </CartContext.Provider>
  );
};

export const useCart = () => {
  const context = useContext(CartContext);
  if (!context) {
    throw new Error('useCart must be used within CartProvider');
  }
  return context;
};

```

## Common Mistakes

### 1. Not Memoizing Context Value

```typescript
// BAD: New object on every render
const App = () => {
  const [theme, setTheme] = useState('light');

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {/* Every render creates a new value object */}
      {/* All consumers re-render even if theme didn't change */}
      <Child />
    </ThemeContext.Provider>
  );
};

// GOOD: Memoize context value
const App = () => {
  const [theme, setTheme] = useState('light');

  const value = useMemo(() => ({
    theme,
    setTheme,
  }), [theme]);

  return (
    <ThemeContext.Provider value={value}>
      {/* Prevents an identity-only context update; parent-driven renders can still occur. */}
      <Child />
    </ThemeContext.Provider>
  );
};

```

### 2. Creating Context Inside Component

```typescript
// BAD: Creating context inside component
const Parent = () => {
  const ThemeContext = createContext('light'); // New context every render!

  return (
    <ThemeContext.Provider value="light">
      <Child />
    </ThemeContext.Provider>
  );
};

// GOOD: Create context outside component
const ThemeContext = createContext('light');

const Parent = () => {
  return (
    <ThemeContext.Provider value="light">
      <Child />
    </ThemeContext.Provider>
  );
};

```

### 3. Not Providing Error Handling

> [Basic Context](#basic-context) uses a null default and throws when no provider is present. Defaults are application design choices: a meaningful fallback supports optional providers; a sentinel such as null supports a required-provider contract.

### 4. Overusing Context

```typescript
// BAD: Using context for local state
const Component = () => {
  const [count, setCount] = useState(0);

  return (
    <CountContext.Provider value={{ count, setCount }}>
      {/* Unnecessary context for local state */}
      <button onClick={() => setCount(c => c + 1)}>+1</button>
    </CountContext.Provider>
  );
};

// GOOD: Use context only for shared state
const Component = () => {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>+1</button>
  );
};

```

## Best Practices

1. **Stabilize unchanged values when useful**: Memoize a provider object when measured identity-only propagation is costly.

2. **Create context outside components**: Don't create context inside render functions.

3. **Provide error handling**: Choose a sentinel default and guard it in a required-provider hook.

4. **Split contexts**: Don't put everything in one context. Split by concern.

5. **Use custom hooks**: Encapsulate context consumption in custom hooks.

6. **Default values wisely**: Provide meaningful default values or null.

7. **Don't overuse context**: Use local state for component-specific data.

## Performance Considerations

### Context Performance

| Aspect | Impact | Mitigation |
| ---------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Value changes | Consumers under that provider that read the context receive the new value when `Object.is` differs | Stabilize unchanged values; split independent contexts |
| Large contexts | Many consumers affected | Split by concern |
| Frequent updates | Consumers still process each published value | Use a selector-based store when subscribers need independent updates; a Transition can lower urgency but does not remove consumer work |
| Provider scope | Broad scope reaches more consumers | Keep each provider near the subtree needing it |

### When to Use Context

| Need | Fit |
| --------------------------------------- | ------------------------------------------------------------------- |
| Theme, locale, auth identity | Share a scoped value with many readers |
| Shopping cart | Context plus local state/reducer can work; measure consumer costs |
| Complex transitions | A reducer can own state logic while context transports it |
| Many independently updating subscribers | Consider selector-based subscriptions if broad rerenders are costly |

Context has no fixed update-frequency limit. Use the smallest provider scope that serves the readers, and split independent values when an update to one should not rerender readers of another.

## Summary

Context is React's tree-scoped mechanism for sharing a value without passing it through every intermediate prop. It transports values; state or an external store owns their updates. Keep providers near their readers, split independent values when useful, and profile broad consumer work before optimizing.

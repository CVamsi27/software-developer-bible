# React Context API

In small React applications, passing data from parent to child via props is straightforward and explicit. But as component hierarchies deepen, applications inevitably run into **prop drilling**: passing a `theme` or `userSession` prop through dozens of intermediate layout, container, and wrapper components that have no interest in the data, simply to deliver it to a deeply nested `<Avatar />` or `<ThemeToggle />`.

Prop drilling clutters component interfaces, tightly couples intermediate UI containers to unrelated data contracts, and turns simple refactoring into a chore.

The **React Context API** provides an architectural escape hatch. By creating a scoped dependency-injection channel down the component tree, Context enables an ancestor Provider to broadcast data directly to any descendant in its subtree without manual prop forwarding.

However, Context is not a universal replacement for state management. Misunderstanding its re-render mechanics—specifically, treating Context as a high-frequency global store—triggers widespread re-render cascades that can degrade application responsiveness.

Mastering Context means knowing how the Fiber tree resolves providers, how to prevent unwanted re-renders via value memoization and context splitting, and when to graduate from Context to dedicated external stores.

## Definition

**React Context** is React's built-in mechanism for passing data through the component tree without manually threading props at every level. A Provider supplies a value to a subtree, and any descendant component consumes that value using the `useContext` hook or React 19's `use()` API.

> **Textbook Definition:** Context is a tree-scoped dependency propagation mechanism: a provider supplies a value to descendant components, and a context read resolves to the nearest matching provider in the component ancestry, or to the context's static default when none exists.

Context itself does not store or manage mutable state. It is a communication conduit: mutable state lives in a standard React hook (such as `useState` or `useReducer`) inside the provider component and is fed into the Context's `value` prop.

## First Principles

The operational behavior of React Context rests upon three core principles:

1. **Decoupled Data Propagation:** Prop drilling forces every intermediary node in the React tree to declare props it does not use. Context allows leaf components to declare dependencies directly on an ancestor's data channel, keeping intermediate presentation components purely focused on layout.
2. **Nearest-Ancestor Resolution:** When a component calls `useContext(MyContext)`, React walks upward through the Fiber tree along parent pointers until it encounters the first matching Provider for that context. If no matching provider is mounted, it falls back to the default value declared during `createContext(defaultValue)`.
3. **All-or-Nothing Subscription Semantics:** Context is **not** a selector-based store. When a provider's `value` changes (evaluated by reference via `Object.is`), **every single component that calls `useContext` for that context re-renders**. Wrapping a consumer component in `React.memo` will **not** prevent it from re-rendering when the context value it reads updates.

```text
Component Tree Hierarchy:
[ThemeProvider (theme: 'dark')]
       │
       ├──► [AppShell]                (Does NOT consume theme; skips re-render)
       │       │
       │       └──► [DashboardLayout] (Does NOT consume theme; skips re-render)
       │               │
       │               └──► [ThemeToggle] (Calls useContext: RE-RENDERS on theme change)
       │
       └──► [Nested ThemeProvider (theme: 'light')]
               │
               └──► [IsolatedPanel]   (Reads 'light' from nearest ancestor Provider)
```

## A consumer reads the nearest provider above it

To use Context, create the context instance once outside your component functions. The Provider wraps the target subtree, and descendant components read the value:

```tsx
import { createContext, useContext, useState, type ReactNode } from 'react';

// 1. Declare Context with a sensible fallback or undefined
type Theme = 'light' | 'dark';
const ThemeContext = createContext<Theme>('light');

// 2. Encapsulate state inside a dedicated Provider component
export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');

  const toggleTheme = () => {
    setTheme((prev) => (prev === 'light' ? 'dark' : 'light'));
  };

  return (
    // React 19+ supports <ThemeContext value={...}> directly
    // React 18 and earlier requires <ThemeContext.Provider value={...}>
    <ThemeContext value={theme}>
      <button type="button" onClick={toggleTheme}>
        Toggle Theme (Current: {theme})
      </button>
      {children}
    </ThemeContext>
  );
}

// 3. Consume in deeply nested children
export function SaveButton() {
  const theme = useContext(ThemeContext);
  return <button className={`btn-${theme}`}>Save Changes</button>;
}
```

In React 19, writing `<ThemeContext value={theme}>` replaces the legacy `<ThemeContext.Provider value={theme}>` syntax, simplifying JSX composition.

## Keep updates proportional to what changed

Because React evaluates context updates via `Object.is(prevValue, nextValue)`, creating object literals directly inside JSX causes performance issues:

```tsx
// ⚠️ ANTI-PATTERN: Fresh object reference created on EVERY render
function BadAuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  // Even if user hasn't changed, this object has a new memory address every render!
  return (
    <AuthContext value={{ user, logout: () => setUser(null) }}>
      {children}
    </AuthContext>
  );
}
```

Whenever `BadAuthProvider` re-renders (due to a parent re-render or unrelated state update), the object passed to `value` receives a brand new reference. Consequently, **every component in the application that reads `AuthContext` is forced to re-render**.

### Solution: Stabilize Value References with `useMemo` and `useCallback`

```tsx
import { createContext, useContext, useMemo, useCallback, useState, type ReactNode } from 'react';

interface User {
  id: string;
  name: string;
}

interface AuthContextValue {
  user: User | null;
  logout: () => void;
}

const AuthContext = createContext<AuthContextValue | undefined>(undefined);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const logout = useCallback(() => {
    setUser(null);
  }, []);

  // Stabilize the object identity: only changes when `user` changes
  const contextValue = useMemo(() => ({
    user,
    logout,
  }), [user, logout]);

  return (
    <AuthContext value={contextValue}>
      {children}
    </AuthContext>
  );
}
```

Now, unrelated re-renders of `AuthProvider` preserve the existing `contextValue` reference, sparing child consumers from unnecessary re-renders.

## Advanced Pattern: Splitting State and Dispatch Contexts

Even with `useMemo`, an architectural bottleneck remains: if a context object contains both state (`user`) and mutation handlers (`logout`, `updateProfile`), any update to `user` will force components that only care about the mutation handlers to re-render.

For example, a `<LogoutButton />` that only needs the `logout` function will re-render every time the user's profile updates.

The professional solution is **Context Splitting**:

```tsx
import { createContext, useContext, useReducer, type ReactNode, type Dispatch } from 'react';

type State = { count: number };
type Action = { type: 'increment' } | { type: 'decrement' };

// 1. Separate State Context from Dispatch Context
const CounterStateContext = createContext<State | undefined>(undefined);
const CounterDispatchContext = createContext<Dispatch<Action> | undefined>(undefined);

function counterReducer(state: State, action: Action): State {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
  }
}

export function CounterProvider({ children }: { children: ReactNode }) {
  const [state, dispatch] = useReducer(counterReducer, { count: 0 });

  return (
    <CounterStateContext value={state}>
      {/* React guarantees `dispatch` reference is stable for the lifetime of the component */}
      <CounterDispatchContext value={dispatch}>
        {children}
      </CounterDispatchContext>
    </CounterStateContext>
  );
}

// Custom hooks for ergonomic access
export function useCounterState() {
  const context = useContext(CounterStateContext);
  if (!context) throw new Error('useCounterState must be used within CounterProvider');
  return context;
}

export function useCounterDispatch() {
  const context = useContext(CounterDispatchContext);
  if (!context) throw new Error('useCounterDispatch must be used within CounterProvider');
  return context;
}
```

### The Architectural Benefit:
- Components displaying data call `useCounterState()` and re-render when `count` updates.
- Buttons triggering actions call `useCounterDispatch()`. Because `dispatch` is guaranteed by React to have a stable identity across all renders, action buttons **never re-render when state changes**.

## Fail-Fast TypeScript Custom Hooks

Supplying a dummy default value to `createContext` (such as `null as any` or empty strings) masks bugs when developers accidentally render a consumer outside its Provider.

Instead, initialize with `undefined` and throw an explicit error inside a typed custom hook:

```tsx
export function useSession(): Session {
  const session = useContext(SessionContext);
  if (session === undefined) {
    throw new Error('useSession must be used within an enclosing SessionProvider');
  }
  return session; // TypeScript narrows type from `Session | undefined` to pure `Session`
}
```

This ensures TypeScript consumers never have to write defensive `if (!session)` checks, and runtime boundary errors are caught immediately during development.

## When NOT to Use Context: The Composition Alternative

Before reaching for Context to solve prop drilling, consider whether **Component Inversion (`children`)** can eliminate the problem entirely:

```tsx
// ⚠️ Complex prop drilling through PageHeader
<PageHeader user={user} onLogout={handleLogout} />

// ✅ Clean composition: PageHeader doesn't need to know about user or logout!
<PageHeader>
  <UserMenu user={user} onLogout={handleLogout} />
</PageHeader>
```

When an intermediate container simply accepts and renders `{children}`, it does not need to know what props its descendants require, eliminating the need for Context without introducing out-of-band dependencies.

## Summary

React Context solves prop drilling by establishing tree-scoped dependency propagation down the Fiber hierarchy. Because Context triggers re-renders across all consumers whenever its value reference changes, production applications must stabilize context values with `useMemo`, separate volatile state from stable dispatch functions via Context Splitting, and avoid using Context for high-frequency streaming updates where dedicated selector stores are required.

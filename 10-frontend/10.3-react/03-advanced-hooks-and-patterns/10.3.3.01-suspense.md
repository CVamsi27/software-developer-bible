# Suspense

## Definition

**React Suspense** lets a region of the UI show a loading fallback while supported work, such as lazy-loaded code or a Suspense-enabled data source, is not ready. The child signals that it cannot finish rendering yet. React handles that signal at a `<Suspense>` boundary and retries the region when the resource becomes ready. Internally the signal can involve a thrown promise. Suspense does not automatically track every request started in an effect.

> **Textbook Definition:** Suspense defines a boundary that can display a fallback while descendant rendering waits for a supported resource. It coordinates rendering availability, not arbitrary asynchronous work started in an effect or event handler.

Suspense coordinates several kinds of work at a rendering boundary:

1. **Code Splitting**: Lazy loading components with `React.lazy`

2. **Data Fetching**: Integration with Suspense-enabled frameworks and data sources; React does not cache arbitrary `fetch` calls for you.

3. **Streaming server rendering**: Send the shell and reveal completed Suspense regions as their HTML arrives.

4. **Selective Hydration**: Hydrate a ready, urgent region without waiting for every suspended region.

5. **Server-to-client promise handoff**: A Server Component can pass a Promise for a Client Component to read with `use`.

## First Principles

1. **Rendering needs a value now; a pending resource cannot provide it.** A Suspense-aware resource read tells React that this render cannot complete yet. React retains a retry path instead of requiring the component to commit incomplete data and repair it in an effect.
2. **A displayed tree still needs a coherent replacement.** The nearest Suspense boundary defines the region that can show a fallback together. Nested boundaries create independent reveal regions; a transition can retain already revealed content while preparing its replacement.
3. **An unfinished render has not acquired a committed lifetime.** State from an initial render that suspends before mounting is not preserved. React retries that tree when ready, so promises and expensive resource creation need stable ownership outside the abandoned render. Effects cannot make ordinary effect-driven fetching activate Suspense.

## Why It Matters

Senior engineers use Suspense to split code with `React.lazy`, set deliberate loading boundaries, and integrate with a framework or data source that supports Suspense. React 19's `use(promise)` reads a Promise and suspends while it is pending; it does not start or cache the request. The same Promise instance must remain stable across retries and re-renders.

## The Problem It Solves

### The Problem

Suppose a profile needs code and a user record before it can render. An effect-driven implementation must store loading, data and failure state after an initial commit, guard stale responses and coordinate each region manually. That approach remains valid; see [useEffect's complete request lifecycle](../02-core-hooks/10.3.2.02-useeffect.md#fetch-with-abort-controller). Suspense supplies a different boundary when the code or data source supports reads during rendering.

### The Solution

Suspense-aware code reads a stable resource during render rather than starting an uncached request every time.

> The complete promise-prop example is in [Suspense for Data Fetching](#suspense-for-data-fetching-with-use-react-19). Loading belongs to Suspense; rejected resource reads belong to an error boundary.

## How It Works

### Suspense Mechanism

An initial suspended render can be retried from scratch without preserving uncommitted state. If already revealed content suspends during a transition or deferred update, React can keep it visible rather than immediately replace it with a fallback. When visible content is hidden, layout effects are cleaned up and rerun when it is revealed.

```text
Read stable resource → pending → nearest loading boundary displays its fallback
                     → ready   → retry can produce and commit the real content
                     → rejected → error boundary handles the failed read
```

The arrows are alternative outcomes of the resource read. A component does not manually catch the suspension signal. An already revealed transition may retain old content, so pending does not universally mean immediate replacement by a spinner.

### Code Splitting with React.lazy

A module declared as `lazy(() => import('./Dashboard'))` is loaded when React first needs that component. The promise must resolve to an object with a valid `default` component export. A bundler usually emits deferred chunks; their exact boundaries, shared dependencies, preloading and byte counts come from the built application, not from the `lazy` call alone.

### Suspense Boundaries

```text
App
├─ Header                          already available
├─ Suspense(MainSpinner) → Main    one reveal region
└─ Suspense(SidebarSpinner) → Side  another reveal region
```

If Main waits while Side is ready, Side can appear without waiting for Main. A Suspense fallback is UI outside its own suspended child region; if it suspends too, the next outer boundary handles that work. Place boundaries around useful reveal groups rather than every component.

### Error Handling with Error Boundaries

```text
Error Handling:
═══════════════════════════════════════════════════════════════

Suspense + Error Boundary:
┌────────────────────────────────────────┐
│ <ErrorBoundary fallback={<ErrorUI />}> │
│ <Suspense fallback={<Spinner />}>      │
│ <AsyncComponent />                     │
│ </Suspense>                            │
│ </ErrorBoundary>                       │
│                                        │
│ Loading: Shows Spinner                 │
│ Success: Shows AsyncComponent          │
│ Error: Shows ErrorUI                   │
└────────────────────────────────────────┘

```

## Code Examples

### Basic React.lazy

```typescript
import React, { Suspense, lazy, useState } from 'react';

// Lazy load components
const Dashboard = lazy(() => import('./Dashboard'));
const Settings = lazy(() => import('./Settings'));
const AdminPanel = lazy(() => import('./AdminPanel'));

const App = () => {
  const [currentPage, setCurrentPage] = useState('home');

  return (
    <div>
      <nav>
        <button onClick={() => setCurrentPage('home')}>Home</button>
        <button onClick={() => setCurrentPage('dashboard')}>Dashboard</button>
        <button onClick={() => setCurrentPage('settings')}>Settings</button>
        <button onClick={() => setCurrentPage('admin')}>Admin</button>
      </nav>

      <Suspense fallback={<div>Loading...</div>}>
        {currentPage === 'home' && <HomePage />}
        {currentPage === 'dashboard' && <Dashboard />}
        {currentPage === 'settings' && <Settings />}
        {currentPage === 'admin' && <AdminPanel />}
      </Suspense>
    </div>
  );
};

```

### Nested Suspense Boundaries

```typescript
const App = () => (
  <div className="app">
    <Header /> {/* No Suspense - loads instantly */}

    <main>
      <Suspense fallback={<MainSpinner />}>
        <Content /> {/* Loads data */}
      </Suspense>
    </main>

    <aside>
      <Suspense fallback={<SidebarSpinner />}>
        <Sidebar /> {/* Loads data independently */}
      </Suspense>
    </aside>
  </div>
);

```

### Suspense with React.lazy and Error Boundary

The pairing is shown in [Error Handling with Error Boundaries](#error-handling-with-error-boundaries). Use the implementation from [Error Boundary — Basic Error Boundary](10.3.3.02-error-boundary.md#basic-error-boundary) around Suspense; a lazy module rejection becomes an error for that boundary instead of a loading state.

### Suspense for Data Fetching (with `use`, React 19+)

```typescript
import { use, Suspense } from 'react';
const UserProfile = ({ userPromise }: { userPromise: Promise<User> }) => {
  const user = use(userPromise);
  return <div><h1>{user.name}</h1><p>{user.email}</p></div>;
};

// A loader/event/framework creates this promise before rendering the client tree.
const App = ({ userPromise }: { userPromise: Promise<User> }) => (
  <Suspense fallback={<div>Loading user...</div>}>
    <UserProfile userPromise={userPromise} />
  </Suspense>
);
```

Trace the supplied promise: on its pending read the nearest boundary can show “Loading user”; resolution lets React retry and display the user; rejection during client rendering reaches the error path. The loader must validate untrusted network data before treating it as `User`. A parent render with the same promise does not create a second request.

The promise must survive retries and ordinary re-renders; a cache or framework loader can own its lifetime. Creating `fetchUser(userId)` inline in a client render is uncached and can cause warnings, repeated requests and unstable loading. Fetching in an effect does not activate Suspense. A rejected promise read is handled by an error boundary, not the loading fallback.

Server rendering has a separate path: with streaming APIs, a server error inside a Suspense boundary can leave its fallback in the HTML while React retries the content on the client. A client Error Boundary does not catch the server-rendering failure.

### Multiple Lazy Components

> Same pattern as **Real-World → Route-Based Code Splitting** below: one `<Suspense>` around a route switch, with `lazy(() => import(...))` declared per page — see that section for the full `BrowserRouter` version.

## Real-World Use Cases

### 1. Route-Based Code Splitting

```typescript
import { lazy, Suspense } from 'react';
import { BrowserRouter, Routes, Route } from 'react-router-dom';

const Home = lazy(() => import('./pages/Home'));
const Dashboard = lazy(() => import('./pages/Dashboard'));
const Settings = lazy(() => import('./pages/Settings'));
const Profile = lazy(() => import('./pages/Profile'));

const Loading = () => (
  <div className="page-loader">
    <Spinner />
    <p>Loading page...</p>
  </div>
);

const App = () => (
  <BrowserRouter>
    <Suspense fallback={<Loading />}>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/dashboard" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
        <Route path="/profile" element={<Profile />} />
      </Routes>
    </Suspense>
  </BrowserRouter>
);

```

### 2. Heavy Component Lazy Loading

```typescript
const RichTextEditor = lazy(() => import('./RichTextEditor'));
const Chart = lazy(() => import('./Chart'));

const DocumentEditor = () => {
```

### 4. Modal with Lazy Content

```typescript
const HeavyModalContent = lazy(() => import('./HeavyModalContent'));

const Modal = ({ isOpen, onClose }: { isOpen: boolean; onClose: () => void }) => {
  if (!isOpen) return null;

  return (
    <div className="modal-overlay">
      <div className="modal">
        <button className="close-btn" onClick={onClose}>×</button>
        <Suspense fallback={<ModalSpinner />}>
          <HeavyModalContent />
        </Suspense>
      </div>
    </div>

```

## Common Mistakes

### 1. No Suspense Boundary

```typescript
// Declare lazy component types outside the component to preserve identity.
const Dashboard = lazy(() => import('./Dashboard'));
const App = () => <Suspense fallback={<Spinner />}><Dashboard /></Suspense>;
```

Without a boundary, the region has no local fallback for pending work. Add one where the user needs an intentional loading state. Declaring `lazy(...)` during each render is a separate error: the new component type can reset state and restart work.

### 2. Too Broad Suspense Boundaries

```typescript
// BAD: One Suspense for entire app
const App = () => (
  <Suspense fallback={<FullPageSpinner />}>
    <Header />
    <Content />
    <Sidebar />
  </Suspense>
);
// Content loading blocks Header and Sidebar

// GOOD: Specific Suspense boundaries
const App = () => (
  <>
    <Header />
    <Suspense fallback={<ContentSpinner />}>
      <Content />
    </Suspense>
    <Suspense fallback={<SidebarSpinner />}>
      <Sidebar />
    </Suspense>
  </>
);

```

### 3. Not Handling Errors

```typescript
// BAD: No error handling
const App = () => (
  <Suspense fallback={<Spinner />}>
    <LazyComponent />
  </Suspense>
);
// If LazyComponent fails to load, error is not caught

// GOOD: Error boundary
const App = () => (
  <ErrorBoundary fallback={<ErrorMessage />}>
    <Suspense fallback={<Spinner />}>
      <LazyComponent />
    </Suspense>
  </ErrorBoundary>
);

```

### 4. Lazy Loading Too Much

```typescript
// BAD: Lazy loading small components
const Button = lazy(() => import('./Button')); // 1KB - unnecessary!
const Icon = lazy(() => import('./Icon')); // 0.5KB - unnecessary!

// GOOD: Lazy load large components
const RichTextEditor = lazy(() => import('./RichTextEditor')); // 100KB - worth it!
const Chart = lazy(() => import('./Chart')); // 50KB - worth it!

```

## Best Practices

1. **Define loading boundaries deliberately**: Put lazy consumers under Suspense so pending work has intentional fallback UI.

2. **Use specific Suspense boundaries**: Don't wrap entire app in one Suspense.

3. **Combine with Error Boundaries**: Handle both loading and error states.

4. **Lazy load large components**: Don't lazy load small, frequently used components.

5. **Use route-based code splitting**: Lazy load entire pages/routes.

6. **Provide meaningful fallbacks**: Show loading indicators, not blank screens.

7. **Preload when possible**: Start loading before user navigates.

8. **Test loading states**: Drive components into the suspended state (a never-resolving promise or a delayed chunk) and assert the fallback renders, so regressions in boundary placement show up in CI instead of in production.

## Performance Considerations

### Code Splitting Impact

Code splitting reduces the initial payload when deferred code is actually omitted from it. First visits to split regions may wait for additional requests; module size, cache state, bundler output and network conditions determine the cost. Preloading can move the request earlier, but there are no universal bundle-size or latency figures. Measure the built application on its target connection.

### When to Lazy Load

| Component | Lazy Load? | Reason |
| ------------------- | ---------- | ---------------------------- |
| Routes | Yes | User may not visit all pages |
| Heavy components | Yes | Large bundle size |
| Modals | Yes | Not always visible |
| Small utilities | No | Overhead not worth it |
| Critical components | No | Need immediately |

## Summary

React Suspense coordinates availability for supported render-time resources. Its boundary defines the reveal region and loading UI; pending work in an ordinary effect does not activate it. Combined with `React.lazy`, it enables code splitting for better performance. Suspense is the foundation for modern React features like data fetching and server components.

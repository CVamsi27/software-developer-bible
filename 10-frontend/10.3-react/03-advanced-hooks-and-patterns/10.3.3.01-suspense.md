# Suspense

## Definition

In standard client-side React, asynchronous dependencies force components into an awkward defensive posture. If a component needs lazy-loaded code or asynchronous data, it must first mount an incomplete DOM shell, trigger a `useEffect`, store intermediate states (`isLoading`, `data`, `error`), and litter its JSX with null checks and spinners. When multiple nested components follow this pattern, the screen suffers from the **waterfall of spinners**: parent spinners give way to child spinners, triggering repeated layout reflows and visual jitter.

**React Suspense** coordinates asynchronous dependencies by turning rendering availability into a first-class boundary in the component tree. Descendant components attempt to read their resources synchronously during render. If a resource (a code chunk, a streaming promise, or a framework cache) is not yet ready, the component *suspends*—pausing its render execution. React intercepts this interruption at the nearest ancestor `<Suspense>` boundary, defers committing incomplete DOM nodes to the screen, and displays an orchestrated fallback shell. Once the resource settles, React retries rendering the suspended subtree and commits the completed UI in a single atomic DOM update.

> **Textbook Definition:** Suspense is a React boundary component that displays an orchestrated fallback UI while descendant components await asynchronous resources (such as dynamic imports via `React.lazy`, Server Component streaming chunks, or promises read via `use()`), preventing partial DOM commits and eliminating component-level loading state boilerplate.

Suspense coordinates five primary asynchronous capabilities across modern React architectures:

1. **Code Splitting (`React.lazy`)**: Deferring component bundle downloads until the component is actually rendered.
2. **Concurrent Data Fetching (`use(promise)`)**: Reading promises directly during render without `useEffect` or state boilerplate.
3. **Streaming Server-Side Rendering (SSR)**: Emitting HTML shells immediately over HTTP streams while slow dynamic content streams into the document concurrently.
4. **Selective Hydration**: Hydrating interactive UI chunks as they arrive over the wire, and reprioritizing hydration on the fly if the user interacts with a pending component.
5. **Non-Blocking Transitions (`useTransition`)**: Keeping existing, interactive UI on screen while background work prepares the next screen, eliminating fallback flashes altogether.

```text
Without Suspense (Imperative Fetch-on-Render):
Mount Shell ──▶ Commit Spinner ──▶ Effect Fires ──▶ State Update ──▶ Re-render with Data
(Layout jitter, multiple intermediate renders, and manual cleanup boilerplate)

With Suspense (Declarative Render-as-You-Fetch):
Render Attempt ──▶ Resource Pending (Suspends) ──▶ Nearest <Suspense> Displays Fallback
                                                        │
                      Resource Settles ◀────────────────┘
                               │
                               ▼
            Single Atomic Re-render & DOM Commit
```

## First Principles

1. **Render functions are synchronous expressions of state.** A component cannot `await` a promise inside its render body because React reconciliation is synchronous per fiber node. When a value is missing, the component cannot complete execution. Suspense pauses render execution by unwinding the call stack to the nearest boundary that declared how to handle unfinished work.
2. **A UI region must transition atomically.** Showing a dashboard with a loaded header, half-loaded metric card, and empty chart creates cognitive friction and layout reflow. Suspense treats a region as a single atomic unit of visual readiness: either the entire region is ready to commit, or the fallback displays.
3. **Uncommitted renders carry zero state commitment.** When an initial render suspends before mounting, React throws away intermediate work without running layout effects or locking Fiber state. Therefore, resource creation must live outside the abandoned render (in a cache, loader, or server promise), or the retry will trigger an infinite fetch loop.

## The Under-the-Hood Mechanism: How Suspense Traps Asynchronous Work

Understanding Suspense requires demystifying how a synchronous JavaScript render function signals to React that it cannot finish. 

```text
Component Fiber                    Suspense Boundary Fiber
      │                                       │
      │── 1. use(promise) / read() ──────────▶│
      │      (Promise is Pending)             │
      │                                       │
      │── 2. Throws Promise (or Signal) ─────▶│
      │                                       │── 3. Catches thrown Promise
      │                                       │── 4. Attaches .then(retrySchedule)
      │                                       │── 5. Reconciles & Commits Fallback
      │                                       │
      │                                [Network Resolves]
      │                                       │
      │◀── 6. Triggers Fiber Retry ───────────│
      │                                       │
      │── 7. use(promise) returns Value ─────▶│
      │── 8. Reconciles & Commits Subtree ───▶│
```

1. **The Interruption Signal:** When a child component reads an unfinished resource (via `use(promise)` or a custom Suspense cache), the reader checks if the promise has resolved. If still pending, it *throws* the Promise instance itself.
2. **The Fiber Interception:** React's reconciler wraps component execution in internal catch blocks. When it catches a thrown Promise, it inspects the Fiber tree upwards until it finds a `SuspenseComponent` Fiber tag.
3. **Subscription & Fallback Swap:** React attaches `.then(retry)` listeners to the thrown Promise. Instead of committing the broken child subtree, React reconciles and commits the `fallback` prop into the DOM.
4. **Wakeup & Retry:** When the Promise resolves, the `.then()` handler dispatches a low-priority re-render targeting the suspended Fiber. React re-executes the component. This time, `use(promise)` returns the resolved value synchronously, and React commits the completed UI.
5. **Rejection to Error Boundary:** If the promise rejects, the suspension converts into a render error. Suspense does not catch errors; the nearest `<ErrorBoundary>` intercepts the rejection.

## Code Splitting with React.lazy

The original and most common client-side application of Suspense is on-demand bundle loading. By wrapping a dynamic `import()` statement with `lazy()`, bundlers (Webpack, Vite, Turbopack) automatically extract the imported component and its dependencies into an isolated chunk file.

```tsx
import React, { Suspense, lazy, useState } from 'react';

// Chunks are declared at MODULE SCOPE so their identity remains stable
const DashboardView = lazy(() => import('./views/DashboardView'));
const AnalyticsView = lazy(() => import('./views/AnalyticsView'));
const SettingsView = lazy(() => import('./views/SettingsView'));

type Tab = 'dashboard' | 'analytics' | 'settings';

export function ApplicationShell() {
  const [activeTab, setActiveTab] = useState<Tab>('dashboard');

  return (
    <div className="shell-container">
      <nav className="shell-nav" aria-label="Main Navigation">
        <button onClick={() => setActiveTab('dashboard')}>Dashboard</button>
        <button onClick={() => setActiveTab('analytics')}>Analytics</button>
        <button onClick={() => setActiveTab('settings')}>Settings</button>
      </nav>

      <main className="shell-content">
        <Suspense fallback={<div className="skeleton-loader" role="status">Loading module...</div>}>
          {activeTab === 'dashboard' && <DashboardView />}
          {activeTab === 'analytics' && <AnalyticsView />}
          {activeTab === 'settings' && <SettingsView />}
        </Suspense>
      </main>
    </div>
  );
}
```

### Module Scope vs. Render Scope

> [!WARNING]
> Never call `lazy(() => import(...))` inside the body of a component function. Every parent re-render will create a new component definition reference. React will treat it as a completely distinct component type, unmounting the existing DOM, discarding all component state, and re-triggering the dynamic download on every single render.

### Intentional Preloading

To avoid waiting for the user to click a tab before initiating the network request, preload the dynamic chunk during high-intent interactions, such as hovering over navigation buttons:

```tsx
// Expose the raw module promise factory
const analyticsPromiseFactory = () => import('./views/AnalyticsView');
const AnalyticsView = lazy(analyticsPromiseFactory);

function NavButton({ onSelect }: { onSelect: () => void }) {
  return (
    <button
      onClick={onSelect}
      onMouseEnter={() => {
        // Warm the browser cache before the click arrives
        void analyticsPromiseFactory();
      }}
    >
      Analytics
    </button>
  );
}
```

## Suspense for Data Fetching with React 19's `use()`

In React 19, `use(promise)` elevates Suspense from code splitting to direct data reading. Unlike React hooks (`useState`, `useEffect`), `use` can be called conditionally within `if` blocks and loops, but it carries a strict operational contract: **the promise must be cached or owned outside the rendering component**.

```tsx
import { Suspense, use } from 'react';

type UserProfile = {
  id: string;
  name: string;
  role: string;
};

// 1. Child reads the promise synchronously during render
function UserBadge({ profilePromise }: { profilePromise: Promise<UserProfile> }) {
  const profile = use(profilePromise);

  return (
    <div className="user-badge">
      <h3>{profile.name}</h3>
      <span className="badge">{profile.role}</span>
    </div>
  );
}

// 2. Parent or framework loader manages promise instantiation and caching
export function UserProfileCard({ profilePromise }: { profilePromise: Promise<UserProfile> }) {
  return (
    <section className="profile-card">
      <h2>Account Overview</h2>
      <Suspense fallback={<div className="badge-skeleton" aria-busy="true">Loading user data...</div>}>
        <UserBadge profilePromise={profilePromise} />
      </Suspense>
    </section>
  );
}
```

### The Uncached Promise Trap

If you instantiate the Promise directly inside the component body, the application enters an infinite loop:

```tsx
// CATASTROPHIC: Creates a new Promise reference on EVERY render attempt
function BrokenComponent() {
  // 1. Component renders -> initiates new fetch -> suspends
  // 2. Promise resolves -> React retries render
  // 3. New fetch initiated -> creates new pending promise -> suspends again!
  const data = use(fetch('/api/user').then(res => res.json()));
  return <div>{data.name}</div>;
}
```

The Promise passed to `use()` must originate from:
- A React Server Component streaming payload.
- A stable routing loader (React Router loaders, Next.js data passes).
- A memoized client cache (such as TanStack Query or a custom module map).

## Eliminating Fallback Flashes with Concurrent Transitions

A major critique of naive Suspense boundaries is the "flashing spinner" during user-driven navigation. When a user clicks from Tab A to Tab B, immediately replacing Tab A with a loading spinner feels sluggish and jarring.

Using `startTransition` or `useTransition`, React defers the display of the Suspense fallback. It keeps the current, interactive screen visible while rendering the pending screen in the background:

```tsx
import { Suspense, lazy, useState, useTransition } from 'react';

const RecentOrders = lazy(() => import('./RecentOrders'));
const SalesAnalytics = lazy(() => import('./SalesAnalytics'));

export function TabbedDashboard() {
  const [tab, setTab] = useState<'orders' | 'analytics'>('orders');
  const [isPending, startTransition] = useTransition();

  const handleTabChange = (nextTab: 'orders' | 'analytics') => {
    startTransition(() => {
      // Instructs React: "Do not hide the current tab with a fallback spinner.
      // Keep Tab A visible with isPending = true until Tab B is ready."
      setTab(nextTab);
    });
  };

  return (
    <div>
      <div className="tab-buttons">
        <button onClick={() => handleTabChange('orders')}>Orders</button>
        <button onClick={() => handleTabChange('analytics')}>Analytics</button>
        {isPending && <span className="inline-spinner" role="status">Updating...</span>}
      </div>

      <div style={{ opacity: isPending ? 0.7 : 1.0, transition: 'opacity 0.2s' }}>
        <Suspense fallback={<div className="full-spinner">Initial Load...</div>}>
          {tab === 'orders' ? <RecentOrders /> : <SalesAnalytics />}
        </Suspense>
      </div>
    </div>
  );
}
```

With `useTransition`:
1. On the **first visit**, `<Suspense>` shows the `full-spinner` fallback because there is no previous content to retain.
2. On **subsequent tab switches**, the fallback is suppressed. The current tab stays visible at 70% opacity while the next tab downloads and renders in memory, yielding a seamless page swap without layout collapse.

## Streaming SSR and Selective Hydration

In modern server-rendered architectures (Next.js App Router, Remix, standard `renderToPipeableStream`), Suspense coordinates the physical streaming of HTML and selective JavaScript execution in the browser.

```text
Server-Side Streaming Response:
HTTP 200 OK ──▶ Send Shell (Navbar, Layout, Fallback HTML) ──▶ Streamed to Browser (Instant TTFB)
                     │
                     ▼
          Background Server DB Query Completes
                     │
                     ▼
Stream HTML Chunk + <script>$RC("B:0","S:0")</script> ──▶ Replaces Fallback in DOM Before JS Hydration
```

### How Streaming SSR Works
1. **Instant TTFB:** The server renders the root layout and wraps slow dynamic components in `<Suspense>`. It immediately flushes the static shell and fallback markup over the HTTP connection. The browser renders the shell and skeletons in milliseconds.
2. **Out-of-Order Chunk Streaming:** As slow database queries resolve on the server, React renders the suspended component into HTML on the server. It flushes this markup down the open HTTP stream, followed by an inline `<script>` tag that immediately swaps the placeholder DOM node with the real HTML in the browser.
3. **Selective Hydration:** The browser does not need to wait for all JavaScript bundles or streaming chunks to download before making the page interactive. React begins hydrating the static header and navigation immediately. If the user clicks on a partially streamed comments section while another section is hydrating, React pauses lower-priority work and selectively hydrates the comments section first.

## Designing Boundary Hierarchies

A critical architectural decision is deciding where to place `<Suspense>` boundaries. Wrapping every component in its own boundary leads to fragmented visual noise, while wrapping the entire application in a single boundary forces full-page spinner locks.

```text
Hierarchical Boundary Composition:

┌────────────────────────────────────────────────────────┐
│ <RootErrorBoundary>                                    │
│   <NavigationShell /> (Immediate, unblocked)           │
│                                                        │
│   ┌──────────────────────────────────────────────────┐ │
│   │ <Suspense fallback={<DashboardSkeleton />}>      │ │  <- Outer Feature Boundary
│   │   <MetricsOverview />                            │ │
│   │                                                  │ │
│   │   <div className="grid">                         │ │
│   │     ┌──────────────────────────────────────────┐ │ │
│   │     │ <Suspense fallback={<ChartSkeleton />}>  │ │ │  <- Independent Granular Boundary
│   │     │   <RevenueChart />                       │ │ │
│   │     └──────────────────────────────────────────┘ │ │
│   │     ┌──────────────────────────────────────────┐ │ │
│   │     │ <Suspense fallback={<FeedSkeleton />}>   │ │ │  <- Independent Granular Boundary
│   │     │   <LiveActivityFeed />                   │ │ │
│   │     └──────────────────────────────────────────┘ │ │
│   │   </div>                                         │ │
│   │ </Suspense>                                      │ │
│   └──────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

### The Boundary Pairing Rule

Suspense only manages **loading availability**. It does not catch runtime errors or rejected promises. If an asynchronous chunk fails to download (e.g. offline client or chunk hash mismatch after a new deployment), the thrown rejection bubbles up past the Suspense boundary.

Always pair Suspense with an `ErrorBoundary` directly above it:

```tsx
import { Suspense, lazy } from 'react';
import { ErrorBoundary } from './ErrorBoundary';

const HeavyWidget = lazy(() => import('./HeavyWidget'));

export function SafeWidgetContainer() {
  return (
    <ErrorBoundary
      fallback={({ retry }) => (
        <div role="alert" className="error-card">
          <p>Failed to load widget component.</p>
          <button onClick={retry}>Retry Loading</button>
        </div>
      )}
    >
      <Suspense fallback={<div className="widget-skeleton" aria-busy="true">Loading widget...</div>}>
        <HeavyWidget />
      </Suspense>
    </ErrorBoundary>
  );
}
```

## Anti-Patterns and Common Traps

| Anti-Pattern | Root Cause | Observable Symptom | Corrective Architecture |
| :-------------------------------- | :------------------------------------------------------------ | :----------------------------------------------------- | :--------------------------------------------------------------------- |
| **In-Render `lazy()` Definition** | Declaring `const Child = lazy(...)` inside component body | Component state wiped out on every keystroke/render | Hoist `lazy()` to top-level module scope |
| **Uncached `use(fetch())`** | Constructing a new promise reference during render execution | Infinite re-render loop crashing the browser tab | Create the promise in server components, loaders, or an external cache |
| **Monolithic Page Boundary** | Wrapping the whole page in a single `<Suspense>` | Entire screen blanks out when a tiny widget re-fetches | Split boundaries into independent visual regions |
| **Fragmented Spinner Chaos** | Wrapping every individual list item or button in `<Suspense>` | Screen flashes dozens of uncoordinated micro-spinners | Group cohesive regions into single intentional reveal boundaries |
| **Missing Error Boundary** | Expecting `<Suspense>` to display errors on network failure | White screen of death when dynamic chunk 404s | Always wrap `<Suspense>` in an `<ErrorBoundary>` |

## Summary

- **Declarative Readiness**: Suspense replaces imperative `useEffect` loading state tracking with an architectural boundary that catches pending resources and renders coordinated fallbacks.
- **The Fiber Suspension Mechanism**: When a component reads pending code or a promise, it throws the promise; React catches it at the nearest Suspense Fiber, attaches completion listeners, and renders the fallback until resolution.
- **Transition Coordination**: Wrapping state updates in `useTransition` allows React to suppress loading fallbacks for user navigations, keeping the current UI interactive while the next screen prepares.
- **Streaming & Hydration**: In modern SSR architectures, Suspense enables out-of-order HTML chunk streaming and selective, user-interaction-driven client hydration.
- **Error Boundary Pairing**: Suspense handles only pending states; pair it with ancestor Error Boundaries to handle network rejections and chunk failures cleanly.

# Suspense

A dashboard can show the account summary immediately while its large chart is still loading. Put both behind one boundary and the summary waits too; put a spinner around every small widget and the screen becomes noisy. A Suspense boundary defines which region should appear together and what users see while that region is not ready.

```tsx
// excerpt
<Suspense fallback={<p role="status">Loading metrics…</p>}>
  <RevenueMetrics />
</Suspense>
```

## Definition

**Suspense** is a React boundary that displays fallback UI when a supported child cannot finish rendering because required code or data is pending. When that resource becomes available, React retries the suspended work and reveals the content.

> **Textbook Definition:** A Suspense boundary is a component-tree boundary that coordinates the reveal of descendants whose render depends on supported asynchronous resources. The nearest boundary supplies fallback UI while the suspended region is pending; nested boundaries can reveal independent regions separately.

## First Principles

Rendering calculates the next UI, and supported React integrations can signal mid-render that a resource is still pending — React then asks the nearest `<Suspense>` boundary what stays visible. That signal belongs only to supported sources; an ordinary fetch in an Effect never activates Suspense.

Because a boundary is a user-facing loading decision, one boundary reveals together while nested boundaries reveal progressively. Retries also restart the suspended subtree, so resource creation must live in a loader, Server Component, or surviving cache.

## 1. Let One Boundary Match One Loading Decision

For code splitting, declare each lazy component outside the rendering component so it keeps a stable component identity. Put the boundary around the region whose loading state belongs together:

```tsx
import { lazy, Suspense } from 'react';

const RevenueChart = lazy(() => import('./RevenueChart.tsx'));

export function AnalyticsPanel() {
  return (
    <section aria-labelledby="analytics-title">
      <h2 id="analytics-title">Analytics</h2>
      <Suspense fallback={<p role="status">Loading chart…</p>}>
        <RevenueChart />
      </Suspense>
    </section>
  );
}
```

`lazy` asks the bundler to load the module when React first renders that component. Split routes, editors, or charts when the smaller initial bundle justifies the extra network chunk and first-use wait.

If you declare the `lazy` wrapper inside `AnalyticsPanel`, each parent render creates a new component type and can reset the child's state. Because the module loader already caches imports, declaring `lazy` at module scope preserves React's component identity.

Place boundaries at the loading sequence the interface should communicate, not mechanically around every component. One boundary coordinates its descendants together; nested boundaries allow progressive reveal.

If a user switches a tab or route and already-visible content suspends again, React may replace it with the fallback. Wrapping the navigation state update in a transition keeps the existing content visible while the next tree prepares.

```tsx
import { Suspense, useState, useTransition } from 'react';

export function ReportTabs() {
  const [tab, setTab] = useState<'summary' | 'details'>('summary');
  const [isPending, startTransition] = useTransition();

  function select(next: 'summary' | 'details') {
    startTransition(() => setTab(next));
  }

  return (
    <>
      <button onClick={() => select('summary')}>Summary</button>
      <button onClick={() => select('details')}>Details</button>
      {isPending && <span role="status">Updating…</span>}
      <Suspense fallback={<p role="status">Loading report…</p>}>
        {tab === 'summary' ? <Summary /> : <Details />}
      </Suspense>
    </>
  );
}
```

A Transition changes the priority of the state update; it does not make the network or render work faster. React can keep already revealed content during that update, while a newly mounted nested boundary can still show its own fallback. Keep controlled input state urgent; use a separate deferred value when an expensive result should lag behind typing.

## 2. Read Data Through a Suspense-Enabled Source

React 19's `use(promise)` reads a Promise during render. The Promise must come from an owner that reuses the same instance across retries, such as a route loader, Server Component, or Suspense-enabled cache:

```tsx
import { Suspense, use } from 'react';

type Profile = { name: string; role: string };

function ProfileCard({ profile }: { profile: Promise<Profile> }) {
  const value = use(profile);
  return <p>{value.name} — {value.role}</p>;
}

export function ProfileRegion({ profile }: { profile: Promise<Profile> }) {
  return (
    <Suspense fallback={<p role="status">Loading profile…</p>}>
      <ProfileCard profile={profile} />
    </Suspense>
  );
}
```

Do not create a new `Promise` with `fetch()` inside the rendering component and pass it straight to `use`: a retry can create another pending `Promise` and suspend again. A cache or framework must own request reuse, invalidation, and error policy.

Unlike ordinary Hooks, `use` can be called conditionally, but you cannot catch a pending read with `try/catch`; its nearest `<Suspense>` boundary owns the pending state. An Effect-based fetch remains valid when the component itself owns loading and error state.

Kicking off independent reads before rendering (**render-as-you-fetch**) prevents serial fetch-on-render waterfalls, where a nested child only starts requesting data after its parent finishes rendering:

```tsx
// excerpt
// Render-as-you-fetch: start independent reads before rendering children
// (owned by a route loader, Server Component, or Suspense-enabled cache).
function DashboardPage({
  summary,
  chart,
}: {
  summary: Promise<Summary>;
  chart: Promise<ChartData>;
}) {
  return (
    <>
      <Suspense fallback={<p role="status">Loading summary…</p>}>
        <SummaryCard summary={summary} />
      </Suspense>
      <Suspense fallback={<p role="status">Loading chart…</p>}>
        <RevenueChart chart={chart} />
      </Suspense>
    </>
  );
}
```

In React 19, when a child inside a `<Suspense>` boundary suspends, React still pre-warms sibling trees in the background instead of stalling sibling fetches until the first child resolves, while separate boundaries let each region reveal as soon as its own resource settles.

## 3. Keep Pending and Failed States Separate

Suspense handles pending supported work. It does not catch a rejected `lazy` import, a rejected `Promise` read with `use`, or an ordinary render exception — those failures propagate to an error boundary.

Pair the loading boundary with a recoverable error boundary wherever a failed chunk or resource should not take down the surrounding screen. Keep in mind that resetting the boundary alone does not clear a rejected cache entry or failed `Promise`.

On the server, React's streaming renderers can send an HTML shell containing `<Suspense>` fallbacks and stream completed boundary content as it resolves. Frameworks use these boundaries to coordinate server output and selective hydration; adding `<Suspense>` to a client-only app does not enable streaming SSR by itself.

## Summary

Suspense coordinates pending work from supported React sources. The nearest boundary controls the loading region, nested boundaries control progressive reveal, and Transitions can preserve already revealed content during a non-urgent update. Keep Promise ownership in a stable loader or cache, and use an Error Boundary for rejected work.

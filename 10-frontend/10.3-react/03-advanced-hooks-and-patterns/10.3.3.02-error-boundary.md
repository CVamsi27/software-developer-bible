# Error Boundary

## Definition

An **Error Boundary** is a React component that handles supported errors from components below it in the React tree. It can report the failure and show a fallback UI for that region. This resembles a `try/catch` around rendering, but it does not catch every JavaScript error: event-handler errors and ordinary asynchronous callbacks need their own handling.

> **Textbook Definition:** An error boundary replaces a failed descendant render with fallback UI and can report the failure. Its protection covers React-managed descendant lifecycle work, with separate handling required for ordinary event-handler and asynchronous failures.

Error Boundaries must be **class components** with either `componentDidCatch` or `getDerivedStateFromError` methods. They catch errors during:

1. Rendering

2. Lifecycle methods

3. Constructors of child components

They do **not** catch errors in:

1. Event handlers

2. Detached asynchronous code such as timers and ordinary unobserved Promise callbacks

3. Server-side rendering

4. Errors in the error boundary itself

React 19 routes errors from a `useTransition` Action to an error boundary. A rejected promise read by `use(promise)` also becomes a render error for the boundary; these differ from an unrelated timer or Promise callback throwing outside React's work.

## First Principles

JSX describes a child; React calls that child later. A parent's `try/catch` around `<Chart />` therefore cannot catch a failure from React's later render of `Chart`. Recovery needs a boundary that React recognizes in the component tree.

A failed region cannot be committed as though rendering succeeded. React looks for an ancestor boundary and renders its fallback instead. Recovery also needs valid inputs: resetting the boundary retries the region, but does not repair a bad resource or cached rejected promise.

## Trace a failed widget

Suppose a dashboard contains a header, a sales chart and a recent-orders list. Put a boundary around the chart when that region has a useful independent fallback:

```text
Dashboard
├── Header                         remains available
├── ErrorBoundary
│   └── SalesChart throws          replaced by ChartFallback
└── RecentOrders                   remains available
```

1. The chart throws while React renders it.
2. `getDerivedStateFromError` returns fallback state during rendering. It must stay pure.
3. React commits the fallback; `componentDidCatch` can report the error and component stack.
4. A retry clears the boundary state and remounts the failed children. Their previous local state is lost.

The boundary follows **React ownership**, including children rendered through portals. Its own fallback is outside its protection: if that fallback throws, an ancestor boundary must recover. Without a suitable boundary, an unhandled client render error can remove the root's UI.

## Basic Error Boundary

One implementation owns recovery and reporting; each use supplies the region's fallback. The thrown value is `unknown`, because JavaScript can throw a string, object or even `null`.

```tsx
import { Component, type ErrorInfo, type ReactNode } from 'react';

type Props = {
  children: ReactNode;
  fallback: (retry: () => void) => ReactNode;
  report: (error: unknown, componentStack: string | null | undefined) => void;
};
type State = { failed: boolean };

export class ErrorBoundary extends Component<Props, State> {
  state: State = { failed: false };

  static getDerivedStateFromError(): State {
    return { failed: true };
  }

  componentDidCatch(error: unknown, info: ErrorInfo): void {
    this.props.report(error, info.componentStack);
  }

  retry = (): void => {
    this.setState({ failed: false });
  };

  render(): ReactNode {
    return this.state.failed
      ? this.props.fallback(this.retry)
      : this.props.children;
  }
}
```

The application supplies `report`; it should enqueue sanitized telemetry without throwing. A reporting failure is the boundary's own failure. Include enough route/component context to diagnose the incident, but keep credentials, personal data and raw backend error messages out of the fallback and uncontrolled logs.

```tsx
<ErrorBoundary
  report={reportClientError}
  fallback={retry => (
    <section aria-label="Sales chart unavailable">
      <p>The chart could not be displayed.</p>
      <button onClick={retry}>Try chart again</button>
    </section>
  )}
>
  <SalesChart />
</ErrorBoundary>
```

`reportClientError` and `SalesChart` are application components/helpers in this composition example. A raw class boundary is the React primitive; a maintained boundary library can expose a function-friendly API around that primitive. React has no built-in error-boundary Hook.

## Retry the failed resource as well as the region

A child with bad local state can recover by remounting. A rejected promise held in a cache outside the subtree survives that remount: create or invalidate the resource through its owner before retrying. If inputs keep failing, offer another action such as returning to a working route instead of creating an automatic retry loop.

A route change can deliberately reset identity with `key={routeId}`. That also resets the region's local state; use it when losing that state is intended. Preserve draft data through its existing owner rather than expecting the failed subtree to retain it. After recovery, move keyboard focus to a stable heading or meaningful control because the retry button may have unmounted.

## Keep expected failures in their own path

| Failure | Handling path |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Descendant render or React-managed lifecycle failure | Error boundary |
| Pending promise read by `use` | Suspense loading fallback |
| Rejected promise read by `use` | Error boundary |
| Ordinary `onClick` or `onSubmit` rejection | Local awaited `try/catch` and recoverable UI state |
| Image request fails | The image's `onError` event and replacement display state |
| React 19 transition Action throws | An enclosing error boundary can handle it |
| Server rendering fails | The server/framework's error contract; client class boundaries do not provide server recovery |

For a form validation error, show the field error and retain the form. Replacing the entire form with a boundary fallback discards useful interaction state. Framework route boundaries such as Next.js `error.tsx` provide their own placement and reset rules; use that framework contract rather than assuming a custom client boundary protects server work.

## Choose a boundary by recovery scope

| Placement | Decision |
| ------------------ | ----------------------------------------------------------------------- |
| Independent widget | Keep neighboring work available; provide a widget-specific fallback |
| Route content | Recover a page region while retaining navigation |
| Application root | Provide a last-resort screen when narrower recovery is unavailable |
| Every component | Usually fragments the interface without adding a useful recovery action |

Choose the region that a user can recover independently. A boundary reports rendering failures; it does not establish API success, authorization, cancellation or transaction safety.

## Best Practices

Check a throwing child, a throwing fallback, a non-Error thrown value and both transient and persistent failures. Verify that neighboring regions remain usable and a retry remounts only the intended region. Test rejected resources separately from ordinary event handlers; those errors take different paths. In the telemetry integration, test failure and repeated reports so reporting does not become another crash loop.

## Summary

An error boundary gives a failed React region a fallback and a reporting point. Its usefulness depends on placement, safe reporting, resource recovery and a deliberate reset of child state. Keep expected validation and ordinary asynchronous failures in their local handling paths.

# Error Boundary

## Definition

In a complex single-page application, a single unhandled JavaScript exception inside a deeply nested component—such as an unexpected `TypeError: Cannot read properties of undefined` while reading an API payload—is lethal to the user interface. In standard React reconciliation, an uncaught error during rendering unmounts the entire component tree from the DOM, leaving the user staring at a completely blank white screen.

An **Error Boundary** is a specialized React component that traps JavaScript runtime errors anywhere in its descendant component tree, logs the incident to telemetry, and renders a localized fallback UI instead of unmounting the application. It acts as a declarative fault-isolation zone, ensuring that a crash in a secondary widget (such as a comments feed or analytics chart) does not destabilize the primary workspace (such as an active text editor or checkout form).

> **Textbook Definition:** An Error Boundary is a React class component that implements `static getDerivedStateFromError()` and/or `componentDidCatch()` to intercept rendering exceptions, lifecycle errors, and descendant constructor failures, enabling graceful UI degradation and isolated recovery without crashing the root application.

```text
Without Error Boundary:
Uncaught Render Error in <Widget /> ──▶ Bubbles to Root ──▶ Entire App Unmounts (White Screen)

With Error Boundary:
Uncaught Render Error in <Widget /> ──▶ Intercepted by <ErrorBoundary>
                                             │
      ┌──────────────────────────────────────┴──────────────────────────────────────┐
      ▼                                                                             ▼
Commit Local <Fallback /> UI                                           Keep Sibling Subtrees Active
(User can retry or continue working)                                   (Navbar, Editor, Shell intact)
```

Error Boundaries catch errors thrown during:
1. **The Render Phase**: Uncaught exceptions thrown during component execution or JSX evaluation.
2. **Lifecycle Methods & Effect Setups**: Errors thrown inside `componentDidMount`, `componentDidUpdate`, and React 18/19 effect lifecycles.
3. **Descendant Constructors**: Initialization failures in class components.
4. **Suspense Rejections**: Rejected promises unwrapped via React 19's `use(promise)`.
5. **Concurrent Transitions**: In React 19, errors thrown inside `useTransition` Actions.

They do **not** catch errors in:
- **Native Event Handlers** (`onClick`, `onSubmit`): These execute outside the reconciliation cycle; standard JavaScript `try...catch` blocks handle them.
- **Detached Asynchronous Code**: Timers (`setTimeout`), microtasks, and raw unobserved promises outside React transitions.
- **Server-Side Rendering (SSR)**: Node.js or Edge stream failures require server framework error contracts.
- **The Error Boundary Itself**: If the boundary's own `render()` or `fallback` throws, the error bubbles up to the next ancestor boundary.

## First Principles

1. **JSX elements are descriptors, not immediate execution.** Writing `<SalesChart />` does not execute the chart's function body; it merely instantiates an immutable virtual DOM object (`React.createElement`). Therefore, wrapping JSX in an imperative JavaScript `try...catch` block cannot catch runtime errors:
   ```tsx
   // DOES NOT WORK: try block exits before React reconciles the child
   try {
     return <SalesChart />;
   } catch (err) {
     return <Fallback />;
   }
   ```
   The actual render execution happens later, inside React's internal Fiber reconciler. Error handling must therefore exist as a structural node within the Fiber tree itself.
2. **Fault isolation preserves critical user state.** A failure in a non-critical feature must not destroy unsaved work in a sibling feature. Positioning boundaries around independent UI domains isolates failure blast radiuses.
3. **Recovery requires resetting state and inputs.** Simply clearing an error boundary's state causes React to re-render the exact same child tree with the exact same inputs, resulting in an immediate repeat crash. Safe recovery requires invalidating corrupted local state, resetting caches, or altering boundary identity keys.

## Basic Error Boundary

React requires Error Boundaries to be implemented as **class components** because hooks execute during the render phase and cannot intercept uncaught render phase failures from their own children.

A production-grade Error Boundary implements two distinct lifecycles:
- `static getDerivedStateFromError(error)`: A pure static method that updates boundary state during the render phase, causing the immediate next render to display the fallback UI.
- `componentDidCatch(error, errorInfo)`: A commit-phase lifecycle method that receives the raw error and the component stack trace, used to dispatch telemetry to monitoring services (e.g. Sentry, Datadog).

```tsx
import { Component, type ErrorInfo, type ReactNode } from 'react';

type ErrorBoundaryProps = {
  children: ReactNode;
  fallback: (error: Error, reset: () => void) => ReactNode;
  onCatch?: (error: Error, info: ErrorInfo) => void;
  resetKeys?: readonly unknown[];
};

type ErrorBoundaryState = {
  error: Error | null;
};

export class ErrorBoundary extends Component<ErrorBoundaryProps, ErrorBoundaryState> {
  state: ErrorBoundaryState = { error: null };

  // 1. Pure render-phase hook: return fallback state immediately
  static getDerivedStateFromError(error: unknown): ErrorBoundaryState {
    const normalizedError = error instanceof Error ? error : new Error(String(error));
    return { error: normalizedError };
  }

  // 2. Commit-phase hook: dispatch telemetry and diagnostic logging
  componentDidCatch(error: unknown, info: ErrorInfo): void {
    const normalizedError = error instanceof Error ? error : new Error(String(error));
    this.props.onCatch?.(normalizedError, info);
  }

  // 3. Reset boundary state on prop/key change
  componentDidUpdate(prevProps: ErrorBoundaryProps): void {
    if (this.state.error === null) return;

    // If external reset keys changed, clear the error and attempt remounting
    if (this.props.resetKeys && !this.areKeysEqual(prevProps.resetKeys, this.props.resetKeys)) {
      this.resetBoundary();
    }
  }

  private areKeysEqual(prev?: readonly unknown[], next?: readonly unknown[]): boolean {
    if (!prev || !next || prev.length !== next.length) return false;
    return prev.every((key, index) => Object.is(key, next[index]));
  }

  resetBoundary = (): void => {
    this.setState({ error: null });
  };

  render(): ReactNode {
    if (this.state.error) {
      return this.props.fallback(this.state.error, this.resetBoundary);
    }
    return this.props.children;
  }
}
```

## Trace a Failed Widget

Consider a SaaS analytics dashboard composed of a navigation header, an interactive sales chart, and a live user list:

```text
Dashboard Tree:
┌────────────────────────────────────────────────────────┐
│ <DashboardShell>                                       │
│   <GlobalNavigation /> (Stays fully interactive)       │
│                                                        │
│   ┌──────────────────────────────────────────────────┐ │
│   │ <ErrorBoundary resetKeys={[dateRange]}>          │ │
│   │   <SalesChart dateRange={dateRange} />           │ │
│   │   (Throws: Cannot read property 'map' of null)   │ │
│   └──────────────────────────────────────────────────┘ │
│     ▼                                                  │
│   Renders <ChartFallback onRetry={reset} />            │
│                                                        │
│   <UserActivityList /> (Stays fully functional)        │
└────────────────────────────────────────────────────────┘
```

1. **The Crash:** During render, `SalesChart` attempts to map over `data.points`, which is unexpectedly `null`. JavaScript throws a `TypeError`.
2. **Fiber Unwinding:** React's work loop catches the error. It halts rendering for `SalesChart`, marks the fiber as failed, and walks up the `return` pointer chain until it hits the `ErrorBoundary` fiber.
3. **Fallback Swap:** React invokes `ErrorBoundary.getDerivedStateFromError()`, sets `{ error }`, and renders `ChartFallback`.
4. **Commit & Reporting:** React commits `ChartFallback` to the browser DOM. Then, it runs `componentDidCatch()`, transmitting the error and component stack trace to the telemetry pipeline.
5. **User Experience:** The user notices a clean alert card over the chart with a "Retry" button. The top navigation bar, date picker, and neighboring `UserActivityList` remain completely interactive.

## Reset Strategies: Avoiding the Infinite Crash Loop

The most common failure mode in error handling is the **infinite crash loop**: the user clicks "Retry", the boundary clears its error state, but the child immediately re-renders with the exact same corrupted data and crashes again.

To build resilient recovery, combine three reset vectors:

### 1. Declarative Reset via Reset Keys
Pass the primary inputs or parameters (such as `recordId`, `query`, or `dateRange`) to the boundary via `resetKeys`. When the user changes their filter or selects a different item, the boundary automatically resets:

```tsx
<ErrorBoundary
  resetKeys={[selectedUserId]}
  fallback={(error, reset) => (
    <div className="alert alert-danger" role="alert">
      <p>Failed to render profile for user {selectedUserId}.</p>
      <button onClick={reset}>Try Again</button>
    </div>
  )}
>
  <UserProfile userId={selectedUserId} />
</ErrorBoundary>
```

### 2. Cache Invalidation on Reset
If the error was triggered by a stale or malformed cache record (e.g. TanStack Query or Apollo), the reset callback must invalidate the query before clearing boundary state:

```tsx
function QueryAwareBoundary({ queryKey, children }: { queryKey: readonly unknown[]; children: ReactNode }) {
  const queryClient = useQueryClient();

  return (
    <ErrorBoundary
      resetKeys={queryKey}
      fallback={(error, reset) => (
        <div>
          <p>Data fetch encountered an error.</p>
          <button
            onClick={() => {
              // Invalidate cache BEFORE resetting boundary to avoid instant crash
              void queryClient.invalidateQueries({ queryKey });
              reset();
            }}
          >
            Refetch and Retry
          </button>
        </div>
      )}
    >
      {children}
    </ErrorBoundary>
  );
}
```

### 3. Identity Remounting via React `key`
If a subtree contains corrupt local component state (e.g. invalid form drafts), forcing a total remount via a changing `key` guarantees a clean slate:

```tsx
const [recoveryKey, setRecoveryKey] = useState(0);

<ErrorBoundary
  key={recoveryKey}
  fallback={() => (
    <button onClick={() => setRecoveryKey(k => k + 1)}>
      Reset Workspace Completely
    </button>
  )}
>
  <ComplexEditor />
</ErrorBoundary>
```

## Imperative Error Bridging: Catching Event and Async Errors

Because Error Boundaries only catch errors thrown during rendering and React lifecycles, unhandled promise rejections inside `onClick` or custom fetch calls bypass the boundary entirely.

To route asynchronous and event-handler errors into an Error Boundary, bridge the error into the render phase by scheduling a state update that throws:

```tsx
import { useCallback, useState } from 'react';

// Custom hook to bridge imperative errors into the nearest Error Boundary
export function useAsyncError() {
  const [, setError] = useState();

  return useCallback((error: unknown) => {
    setError(() => {
      // Throwing inside a state updater executes during React's render phase!
      throw error instanceof Error ? error : new Error(String(error));
    });
  }, []);
}

// Usage in an event handler
function PaymentButton({ invoiceId }: { invoiceId: string }) {
  const throwAsyncError = useAsyncError();

  const handlePayment = async () => {
    try {
      await processStripePayment(invoiceId);
    } catch (err) {
      // Bridges the network/stripe error directly into the nearest ErrorBoundary
      throwAsyncError(err);
    }
  };

  return <button onClick={handlePayment}>Pay Now</button>;
}
```

## Designing Boundary Hierarchies

Choose error boundary placement by **user recovery scope**:

| Placement Layer | Scope & Responsibility | Typical Fallback UI |
| :----------------------- | :------------------------------------------------ | :---------------------------------------------------------------------------------------- |
| **Application Root** | Catch-all safety net preventing blank screens | Full-page "Something went wrong" screen with hard page reload button |
| **Route / Layout Shell** | Route segment boundary (e.g. Next.js `error.tsx`) | Page-level alert preserving global navigation, sidebar, and breadcrumbs |
| **Feature / Widget** | Isolating secondary, failure-prone components | Granular card fallback with localized retry button; sibling widgets unaffected |
| **Micro-Component** | Over-fragmentation: wrapping every button or icon | **Anti-pattern**: fragments layout and clutters the UI with tiny disconnected error boxes |

```text
Production Boundary Topology:

┌────────────────────────────────────────────────────────┐
│ <RootErrorBoundary>                                    │
│   (Traps fatal shell crashes; logs high-severity P1)   │
│                                                        │
│   <GlobalNavbar />                                     │
│                                                        │
│   ┌──────────────────────────────────────────────────┐ │
│   │ <RouteErrorBoundary>                             │ │
│   │   (Preserves navigation; isolates page crashes)  │ │
│   │                                                  │ │
│   │   ┌────────────────────┐  ┌────────────────────┐ │ │
│   │   │ <WidgetBoundary>   │  │ <WidgetBoundary>   │ │ │
│   │   │   <FeedPanel />    │  │   <MetricsPanel /> │ │ │
│   │   └────────────────────┘  └────────────────────┘ │ │
│   └──────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

## Error Handling Pathways Comparison

| Failure Type | Propagation Mechanism | Appropriate Handling Strategy |
| :----------------------------- | :------------------------------------------------ | :------------------------------------------------------------ |
| **JSX Render Exception** | Uncaught throw during component execution | Nearest `<ErrorBoundary>` |
| **Component Lifecycle Crash** | Error in `componentDidMount` or `useEffect` setup | Nearest `<ErrorBoundary>` |
| **Pending Promise (`use()`)** | Thrown Promise instance during render | `<Suspense>` fallback |
| **Rejected Promise (`use()`)** | Thrown Promise rejection during render | Nearest `<ErrorBoundary>` |
| **Form / Button Event Crash** | Uncaught throw inside `onClick` / `onSubmit` | Local `try...catch` and component error banner |
| **Field Validation Failure** | Expected invalid user input | Form state validation messages (`react-hook-form`, Zod) |
| **Server Streaming Failure** | HTTP stream chunk failure in SSR | Server framework fallback contract (e.g. Next.js `error.tsx`) |

## Anti-Patterns and Common Traps

| Anti-Pattern | Root Cause | Observable Symptom | Corrective Action |
| :------------------------------------ | :----------------------------------------------------------------- | :-------------------------------------------------------- | :----------------------------------------------------------- |
| **Using `try/catch` in Render** | Attempting to catch `<Child />` errors directly | Catch block never triggers; component still crashes | Wrap child in `<ErrorBoundary>` |
| **Stateless Retry Button** | Calling `setState({ error: null })` without changing data | Instant re-crash on retry click | Invalidate cache or pass `resetKeys` |
| **Swallowing Expected Validation** | Replacing entire forms with an error boundary on bad input | User loses all typed input and draft state | Use localized form field validation state |
| **Side Effects in `getDerivedState`** | Dispatching API calls or Sentry logs in `getDerivedStateFromError` | Breaks render purity; causes double-logging in StrictMode | Dispatch telemetry exclusively in `componentDidCatch` |
| **Unprotected Fallback** | Fallback component throws an error itself | Crashes through to parent boundary or blanks root | Keep fallback components ultra-simple, static, and defensive |

## Summary

- **Declarative Fault Isolation**: Error Boundaries trap render-time and lifecycle exceptions, preventing an isolated component failure from crashing the entire application.
- **Class Component Requirement**: React enforces class implementations (`getDerivedStateFromError` for pure render updates and `componentDidCatch` for telemetry) because hooks cannot trap descendant render crashes.
- **Reset Mechanics**: Safe recovery requires resetting corrupted input state or invalidating data caches; pairing boundaries with `resetKeys` automates recovery when parameters change.
- **Imperative Bridging**: Native event handlers and timers do not trigger error boundaries; bridge them into boundaries when desired using state updater throws.
- **Architectural Hierarchy**: Structure boundaries hierarchically—root catch-all, route-level shells, and granular widget wrappers—to balance failure isolation with user experience.

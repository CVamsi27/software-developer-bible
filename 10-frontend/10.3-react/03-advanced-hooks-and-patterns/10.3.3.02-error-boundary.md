# Error Boundary

If a chart throws while rendering malformed data, the dashboard should keep its navigation and unrelated panels usable. Without a boundary, React removes the failed UI from the screen; an ancestor boundary can replace only the affected region with a fallback.

```tsx
<ErrorBoundary fallback={(error, retry) => (
  <section role="alert">
    <p>Chart could not be loaded.</p>
    <button type="button" onClick={retry}>Try again</button>
  </section>
)}>
  <RevenueChart />
</ErrorBoundary>
```

## Definition

An **Error Boundary** is a component-tree boundary that catches render failures in its descendants and displays fallback UI. It can also report the failure, but it is not a general-purpose handler for expected request errors, form validation or arbitrary asynchronous work.

> **Textbook Definition:** An Error Boundary is a React component that uses `static getDerivedStateFromError()` to switch to fallback state and may use `componentDidCatch()` to report an error thrown while rendering a descendant. It limits the failed subtree and enables an explicit recovery path.

## First Principles

The boundary works because it is part of the rendered component tree: React can route a descendant's render failure to the closest ancestor that knows how to replace that region. Its placement defines the recovery scope, so keep unrelated stateful work outside a boundary when its fallback would otherwise remove it. Resetting the boundary only retries the child tree — it does not repair bad input, replace a rejected cached resource, or guarantee the next render succeeds.

## How It Works

### 1. How the Failure Travels

React evaluates a child while rendering the tree, not when the parent creates a JSX element. A `try/catch` around `return <Chart />` therefore cannot catch an error thrown later while React renders `Chart`; the boundary must be an ancestor in the component tree.

```text
Without Error Boundary:
Uncaught Render Error in <Widget /> ──▶ Bubbles to Root ──▶ Entire App Unmounts (White Screen)

With Error Boundary:
Uncaught Render Error in <Widget /> ──▶ Intercepted by <ErrorBoundary>
                                             │
      ┌──────────────────────────────────────┴──────────────────────────────────────┐
      ▼                                                                             ▼
Commit Local <Fallback /> UI                                           Keep Sibling Subtrees Active
(User can retry or continue working)                                   (Navbar, Editor, Shell intact)
```

The nearest boundary handles a descendant render error. If no ancestor boundary catches it, React removes the rendered UI. A rejected promise read with React's `use()` reaches an Error Boundary, while a still-pending promise belongs to `<Suspense>`. React 19 also routes errors from a `useTransition` Action to the nearest boundary.

A client-side Error Boundary does not handle ordinary event-handler errors, detached async callbacks, server-rendering failures or errors thrown by its own fallback. Catch expected failures where they occur and render their state locally; framework server errors need the framework's error contract.

### 2. Implement the Boundary

React does not provide a Hook equivalent for defining an Error Boundary; the built-in mechanism uses class lifecycle methods. A reusable library can wrap the class API if an application wants a function-oriented interface.

`getDerivedStateFromError` selects fallback state and must stay pure. `componentDidCatch` receives the error and React component stack after the failure; use it for sanitized telemetry, not rendering decisions.

```tsx
import { Component, type ErrorInfo, type ReactNode } from 'react';

type ErrorBoundaryProps = {
  children: ReactNode;
  fallback: (error: unknown, reset: () => void) => ReactNode;
  onCatch?: (error: unknown, info: ErrorInfo) => void;
  onReset?: () => void;
};

type ErrorBoundaryState = {
  hasError: boolean;
  error: unknown;
};

export class ErrorBoundary extends Component<ErrorBoundaryProps, ErrorBoundaryState> {
  state: ErrorBoundaryState = { hasError: false, error: undefined };

  static getDerivedStateFromError(error: unknown): ErrorBoundaryState {
    return { hasError: true, error };
  }

  componentDidCatch(error: unknown, info: ErrorInfo): void {
    this.props.onCatch?.(error, info);
  }

  resetBoundary = (): void => {
    this.props.onReset?.();
    this.setState({ hasError: false, error: undefined });
  };

  render(): ReactNode {
    if (this.state.hasError) {
      return this.props.fallback(this.state.error, this.resetBoundary);
    }
    return this.props.children;
  }
}
```

### 3. Recovery Depends on the Failed Resource

A retry button must change something that can make the next render succeed. If the user selects another record, key the boundary by that identity so the old failure state is discarded. This remounts the child and discards its local state, so do not use it around unsaved work unless that loss is deliberate.

For expected request or validation failures, keep the error in the query or form state and render a local message. If a TanStack Query Suspense read is routed to a boundary, pair the boundary's reset callback with `QueryErrorResetBoundary`; resetting only the React boundary leaves the query's error state unchanged. Here, `Posts` is a component that reads with `useSuspenseQuery`:

```tsx
import { Suspense } from 'react';
import { QueryErrorResetBoundary } from '@tanstack/react-query';
// ErrorBoundary is the class component defined above.

<QueryErrorResetBoundary>
  {({ reset }) => (
    <ErrorBoundary
      onReset={reset}
      fallback={(_error, retry) => (
        <section role="alert">
          <p>Posts could not be loaded.</p>
          <button type="button" onClick={retry}>Try again</button>
        </section>
      )}
    >
      <Suspense fallback={<p role="status">Loading posts…</p>}>
        <Posts />
      </Suspense>
    </ErrorBoundary>
  )}
</QueryErrorResetBoundary>
```

The reset signal lets the query retry when the child renders again. In Suspense mode, TanStack Query can keep cached data visible after a failed background refetch; a boundary is for the failed initial read or an explicitly thrown error. For an ordinary event or async callback, catch the failure there and put an expected message in local state. In React 19, a thrown or rejected `useTransition` Action is an exception and reaches the nearest boundary.

### 4. Choose the Recovery Scope

Place a boundary around the smallest region that can fail independently and still leave the rest of the interface useful. A dashboard can keep its shell and place separate boundaries around a chart and a feed; wrapping every button creates noisy fallbacks without adding a useful recovery option. Keep expected field and request errors in their form or query state.

Framework boundaries follow the framework's tree. In the current Next.js App Router, segment `error.tsx` handles descendant errors, while `global-error.tsx` replaces the root layout and must render its own `<html>` and `<body>`. A segment boundary does not catch errors from its own layout. Next.js also provides a framework-specific `catchError` helper for component-level boundaries; React's built-in boundary remains class-based. Keep fallback copy safe, retry only when the underlying input or resource can change, and send redacted diagnostics to telemetry.

Test a boundary by forcing a descendant render failure and checking that the fallback appears while neighboring UI remains usable. Also test the recovery action with changed inputs or a reset query, and verify that an error in the fallback reaches an ancestor boundary.

## Summary

An Error Boundary replaces a failing descendant subtree with fallback UI; it does not handle ordinary request, event or server errors. Place it around a recoverable region, report sanitized diagnostics in `componentDidCatch`, and reset the boundary together with the failed input or resource so the retry can succeed.

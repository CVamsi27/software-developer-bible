# Custom Hooks

## Definition

**Custom Hooks** are JavaScript functions that reuse logic built from React Hooks. Their names start with `use`, and they can return a value, array or object that a component uses. For example, several components can reuse the same subscription logic without repeating it. Each call still has its own Hook state unless the Hook deliberately reads a shared store. Custom Hooks let you combine this logic without adding higher-order components or render-prop wrappers.

> **Textbook Definition:** A custom Hook is a function that composes Hooks into a reusable stateful behavior. Each invocation receives its own Hook state unless the implementation explicitly connects to a shared external store.

Names beginning with `use` followed by an uppercase letter or digit let Hook tooling recognize custom hooks and check their callers. Naming alone does not grant access to React state: runtime Hook calls require React's active dispatcher and consistent call order. Removing the prefix does not bypass those runtime constraints.

## First Principles

1. **Render calls are temporary; state must survive between calls.** React owns each component's Hook records. A custom hook calls built-in Hooks while that component renders, so it can package state and synchronization without adding a wrapper component.
2. **Reusing logic does not imply sharing storage.** Two callers execute the same function but receive separate Hook records. Shared sessions or caches need a common provider or external store; extracting a function alone does not connect those callers.
3. **Effects have lifetimes; ordinary calls do not provide automatic cleanup.** JavaScript functions can maintain state in closures or modules. To connect reusable logic to React's commit and cleanup lifecycle, call Hooks in a custom hook and keep their order stable. `renderHook` provides a focused test harness, while component tests remain useful for checking the user-visible integration; neither requires a full application tree.

## Why It Matters

Extract a custom Hook when repeated stateful behavior has a focused interface. Hooks can compose—for example, a search hook can debounce its query before starting a request—and encapsulate behavior such as authentication or pagination so components can focus on presenting it.

## How It Works

### Custom Hook Convention

```text
Component A → useCounter() → count A
Component B → useCounter() → count B
```

Each Hook call owns its Hook slots inside the calling component. A custom Hook composes built-in Hooks; it does not add a component to the render tree or connect separate callers to shared state. Hook linting can check statically recognizable calls: call Hooks at the top level of components or custom Hooks, never conditionally or in loops, and name custom Hooks with the `use` prefix.

### Data Flow

A component calls `useFetch(url)` during render and reads its current result. After commit, the hook's effect starts a request. A completed request updates the caller's state, which schedules another render. When the URL changes or the component unmounts, cleanup aborts the old request and prevents its eventual completion from replacing the newer result. The complete example below includes these lifetime boundaries.

## Code Examples

### 1. useCounter

The counter uses ordered finite bounds; omitted bounds default to JavaScript’s largest finite magnitudes. Clamp after arithmetic so an overflowing increment/decrement saturates at a finite bound rather than storing infinity.

```typescript
import { useState, useCallback } from 'react';

interface UseCounterProps {
  initialValue?: number;
  min?: number;
  max?: number;
  step?: number;
}

interface UseCounterReturn {
  count: number;
  increment: () => void;
  decrement: () => void;
  reset: () => void;
  setCount: (value: number) => void;
}

function useCounter({
  initialValue = 0,
  min = -Number.MAX_VALUE,
  max = Number.MAX_VALUE,
  step = 1,
}: UseCounterProps = {}): UseCounterReturn {
  if (!Number.isFinite(min) || !Number.isFinite(max) || min > max ||
      !Number.isFinite(initialValue) || !Number.isFinite(step) || step <= 0) {
    throw new RangeError('Counter requires ordered finite bounds, a finite initial value and a positive finite step');
  }
  const clamp = (value: number) => Math.max(min, Math.min(max, value));
  const [count, updateCount] = useState(() => clamp(initialValue));
  const setCount = useCallback((value: number) => {
    if (!Number.isFinite(value)) throw new RangeError('Count must be finite');
    updateCount(Math.max(min, Math.min(max, value)));
  }, [min, max]);

  const increment = useCallback(() => {
    updateCount(prev => Math.max(min, Math.min(prev + step, max)));
  }, [step, min, max]);

  const decrement = useCallback(() => {
    updateCount(prev => Math.max(min, Math.min(prev - step, max)));
  }, [step, min, max]);

  const reset = useCallback(() => {
    setCount(initialValue);
  }, [initialValue, setCount]);

  return { count, increment, decrement, reset, setCount };
}

// Usage
const CounterComponent = () => {
  const { count, increment, decrement, reset } = useCounter({
    initialValue: 10,
    min: 0,
    max: 100,
  });

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={decrement}>-</button>
      <button onClick={increment}>+</button>
      <button onClick={reset}>Reset</button>
    </div>
  );
};
```

Trace two callers initialized to 10: incrementing caller A changes only its Hook record, leaving B at 10. Repeated increments clamp A at `max`; direct `setCount` and reset use the same bounds. Changing configuration does not reinitialize existing state: the next transition uses the new bounds, or the caller can explicitly reset/remount if immediate reset is the intended policy.

### 2. useLocalStorage

This browser-storage hook renders `initialValue` on both the server and the first client render, then reads storage in an Effect. That keeps the hydration snapshot deterministic; the UI can use `ready` to avoid presenting the fallback as saved data. Keep `key`, `initialValue` and `decode` stable for one mounted instance, or remount with a new React key when switching storage slots. The hook does not subscribe to writes from other tabs or other instances.

`JSON.parse` returns untrusted data. The required `decode` function validates or migrates it before it enters typed state; `as T` would provide no runtime check. Values must survive a JSON round trip, and top-level `undefined`, functions and other non-JSON values are outside the contract. Storage access and decoding failures are returned in `error` instead of silently treated as valid saved data.

```typescript
import { useState, useCallback, useEffect } from 'react';

interface LocalStorageState<T> {
  value: T;
  ready: boolean;
  error: Error | null;
  pending: 'write' | 'remove' | null;
}

function useLocalStorage<T>(
  key: string,
  initialValue: T,
  decode: (stored: unknown) => T,
) {
  const [state, setState] = useState<LocalStorageState<T>>({
    value: initialValue,
    ready: false,
    error: null,
    pending: null,
  });

  // Read after hydration so server and initial client output use the same value.
  useEffect(() => {
    let active = true;
    try {
      const item = window.localStorage.getItem(key);
      const value = item === null ? initialValue : decode(JSON.parse(item));
      if (active) setState({ value, ready: true, error: null, pending: null });
    } catch (cause) {
      if (active) setState({
        value: initialValue,
        ready: true,
        error: cause instanceof Error ? cause : new Error(String(cause)),
        pending: null,
      });
    }
    return () => { active = false; };
  }, [key, initialValue, decode]);

  // Keep browser writes out of state updater functions, which React may replay.
  useEffect(() => {
    if (!state.ready || state.pending === null) return;
    try {
      if (state.pending === 'remove') {
        window.localStorage.removeItem(key);
      } else {
        const serialized = JSON.stringify(state.value);
        if (serialized === undefined) throw new TypeError('Value is not JSON-serializable');
        window.localStorage.setItem(key, serialized);
      }
      setState(current => ({ ...current, error: null, pending: null }));
    } catch (cause) {
      setState(current => ({
        ...current,
        error: cause instanceof Error ? cause : new Error(String(cause)),
        pending: null,
      }));
    }
  }, [key, state]);

  const setValue = useCallback((next: T | ((previous: T) => T)) => {
    setState(previous => ({
      ...previous,
      value: typeof next === 'function' ? (next as (value: T) => T)(previous.value) : next,
      error: null,
      pending: 'write',
    }));
  }, []);
  const remove = useCallback(() => {
    setState(previous => ({
      ...previous,
      value: initialValue,
      error: null,
      pending: 'remove',
    }));
  }, [initialValue]);

  return { value: state.value, ready: state.ready, error: state.error, setValue, remove };
}

const decodeTheme = (stored: unknown): 'light' | 'dark' => {
  if (stored === 'light' || stored === 'dark') return stored;
  throw new TypeError('Stored theme must be light or dark');
};

function ThemeToggle() {
  const { value: theme, setValue: setTheme, remove, ready, error } =
    useLocalStorage('theme', 'light', decodeTheme);
  if (!ready) return <p>Loading saved theme…</p>;
  if (error) return <div>
    <p role="alert">Could not load saved theme: {error.message}</p>
    <button onClick={remove}>Remove saved value and use the default</button>
  </div>;
  return (
    <button onClick={() => setTheme(prev => prev === 'light' ? 'dark' : 'light')}>
      Current: {theme}
    </button>
  );
}
```

### 3. useDebounce

The [debounced search example](../02-core-hooks/10.3.2.02-useeffect.md#real-time-search-with-debouncing) contains the timer hook and request cleanup. A debounce delays accepting a value until input settles; it does not cancel a request that already started. ### 4. useFetch

Keep a nonempty `options` object and the `decode` function stable with `useMemo` or define them outside the component when constant. Changes in request options are meaningful dependencies; hiding them in a render-written ref would keep an obsolete request alive. State carries the request identity so a URL/options/decoder change stops exposing the prior result during the render before the new Effect runs. The decoder validates untrusted JSON before it enters typed state. This hook owns cancellation through its internal signal.

```typescript
import { useState, useEffect, useCallback } from 'react';

interface UseFetchResult<T> {
  data: T | null;
  loading: boolean;
  error: Error | null;
  refetch: () => void;
}

interface FetchState<T> extends Omit<UseFetchResult<T>, 'refetch'> {
  url: string;
  options: Omit<RequestInit, 'signal'> | undefined;
  decode: (payload: unknown) => T;
  revision: number;
}

function useFetch<T = unknown>(
  url: string,
  decode: (payload: unknown) => T,
  options?: Omit<RequestInit, 'signal'>
): UseFetchResult<T> {
  const [revision, setRevision] = useState(0);
  const [state, setState] = useState<FetchState<T>>({
    url, options, decode, revision: 0, data: null, loading: true, error: null,
  });
  const refetch = useCallback(() => setRevision(prev => prev + 1), []);

  useEffect(() => {
    const controller = new AbortController();
    let active = true;
    const identity = { url, options, decode, revision };
    setState({ ...identity, data: null, loading: true, error: null });
    async function load() {
      try {
        const response = await fetch(url, { ...options, signal: controller.signal });
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const result = decode(await response.json());
        if (active) setState({ ...identity, data: result, loading: false, error: null });
      } catch (error) {
        if (active) setState({
          ...identity,
          data: null,
          loading: false,
          error: error instanceof Error ? error : new Error(String(error)),
        });
      }
    }
    void load();
    return () => { active = false; controller.abort(); };
  }, [url, options, revision, decode]);

  const isCurrent = state.url === url && state.options === options &&
    state.decode === decode && state.revision === revision;
  return isCurrent
    ? { data: state.data, loading: state.loading, error: state.error, refetch }
    : { data: null, loading: true, error: null, refetch };
}
```

### 5. useIntersectionObserver

This object-ref version assumes the target exists when the Effect runs and remains the same node. An unchanged ref object does not notify the Effect when a node is attached, detached or replaced; use the [callback-ref lifecycle](../02-core-hooks/10.3.2.04-useref.md#callback-refs-own-node-specific-cleanup) for replaceable targets.

```typescript
import { useState, useEffect, useRef, type RefObject } from 'react';

interface UseIntersectionObserverOptions {
  threshold?: number;
  root?: Element | null;
  rootMargin?: string;
  enabled?: boolean;
}

function useIntersectionObserver<T extends HTMLElement = HTMLDivElement>(
  options: UseIntersectionObserverOptions = {}
): { ref: RefObject<T | null>; isIntersecting: boolean; entry: IntersectionObserverEntry | null } {
  const ref = useRef<T | null>(null);
  const [isIntersecting, setIsIntersecting] = useState(false);
  const [entry, setEntry] = useState<IntersectionObserverEntry | null>(null);

  const { threshold = 0, root = null, rootMargin = '0px', enabled = true } = options;

  useEffect(() => {
    if (!enabled || !ref.current) return;

    const observer = new IntersectionObserver(
      entries => {
        const observedEntry = entries[0];
        if (!observedEntry) return;
        setIsIntersecting(observedEntry.isIntersecting);
        setEntry(observedEntry);
      },
      { threshold, root, rootMargin }
    );

    observer.observe(ref.current);

    return () => observer.disconnect();
  }, [threshold, root, rootMargin, enabled]);

  return { ref, isIntersecting, entry };
}

// Usage — Infinite scroll + lazy loading
const LazyImage = ({ src, alt }: { src: string; alt: string }) => {
  const { ref, isIntersecting } = useIntersectionObserver({
    threshold: 0.1,
    rootMargin: '100px',
  });

  return (
    <div ref={ref} style={{ minHeight: 200 }}>
      {isIntersecting ? (
        <img src={src} alt={alt} loading="lazy" />
      ) : (
        <div className="skeleton">Loading...</div>
      )}
    </div>
  );
};
```

### 6. useEventListener

The retained handler is refreshed in a passive Effect, so an event between commit and that flush can see its preceding callback. A fresh `options` object also reinstalls the listener because its identity is an Effect dependency. The target ref must remain attached to the same node; ref assignment alone does not reinstall the listener. Choose stable options and an explicit callback-ref or target-state design when the node can change.

```typescript
import { useEffect, useRef, useState, type RefObject } from 'react';

function useEventListener<K extends keyof WindowEventMap>(
  eventName: K,
  handler: (event: WindowEventMap[K]) => void,
  element?: Window | HTMLElement | RefObject<HTMLElement | null>,
  options?: boolean | AddEventListenerOptions
): void;

function useEventListener<
  K extends keyof HTMLElementEventMap,
  T extends HTMLElement = HTMLDivElement
>(
  eventName: K,
  handler: (event: HTMLElementEventMap[K]) => void,
  element: RefObject<T | null>,
  options?: boolean | AddEventListenerOptions
): void;

function useEventListener(
  eventName: string,
  handler: EventListener,
  element?: Window | HTMLElement | RefObject<HTMLElement | null>,
  options?: boolean | AddEventListenerOptions
): void {
  const savedHandler = useRef(handler);

  useEffect(() => {
    savedHandler.current = handler;
  }, [handler]);

  useEffect(() => {
    const targetElement: Window | HTMLElement | null =
      element && 'current' in element
        ? element.current
        : (element as HTMLElement) ?? window;

    if (!targetElement?.addEventListener) return;

    const eventListener = (event: Event) => savedHandler.current(event);
    targetElement.addEventListener(eventName, eventListener, options);

    return () => {
      targetElement.removeEventListener(eventName, eventListener, options);
    };
  }, [eventName, element, options]);
}

// Usage
const DocumentClick = () => {
  const [clickCount, setClickCount] = useState(0);

  useEventListener('click', () => {
    setClickCount(prev => prev + 1);
  });

  return <p>Document clicked {clickCount} times</p>;
};
```

### When a dedicated form Hook is not worth maintaining

For a small form, local state may be enough. A reusable form Hook must define field types, validation timing, dirty/reset semantics and concurrent submission behavior. The dedicated [form-handling chapters](../../10.5-form-handling/INDEX.md) compare React Hook Form, Formik, TanStack Form, server actions and draft recovery; duplicating a partial form framework here would blur those contracts.

### 7. useAsync

This hook executes on demand. The caller can start it in an effect using a stable callback, as below. A request sequence protects state publication against out-of-order completion, reset, dependency changes, and Strict Mode's development cleanup/replay. A changed function invalidates the old operation; start a replacement or call reset to settle its display state. The returned promise can still yield an obsolete operation's result, so callers performing another side effect need their own identity policy. On failure this implementation stores `error` and resolves `execute` to `undefined`; callers that need promise-style error propagation should rethrow or return an explicit result type. It suppresses obsolete state updates; cancel the underlying operation separately when its API supports cancellation.

```typescript
import { useState, useCallback, useRef, useEffect } from 'react';

type AsyncState<T> = { data: T | null; loading: boolean; error: Error | null };

function useAsync<T, Args extends unknown[]>(asyncFunction: (...args: Args) => Promise<T>) {
  const [state, setState] = useState<AsyncState<T>>({ data: null, loading: false, error: null });
  const requestVersion = useRef(0);
  useEffect(() => () => { requestVersion.current++; }, [asyncFunction]);

  const execute = useCallback(async (...args: Args): Promise<T | undefined> => {
    const version = ++requestVersion.current;
    setState(prev => ({ ...prev, loading: true, error: null }));
    try {
      const result = await asyncFunction(...args);
      if (version === requestVersion.current) {
        setState({ data: result, loading: false, error: null });
      }
      return result;
    } catch (error) {
      if (version === requestVersion.current) {
        setState({ data: null, loading: false,
          error: error instanceof Error ? error : new Error(String(error)) });
      }
      return undefined;
    }
  }, [asyncFunction]);

  const reset = useCallback(() => {
    requestVersion.current++;
    setState({ data: null, loading: false, error: null });
  }, []);
  return { ...state, execute, reset };
}

function UserProfile({ userId }: { userId: string }) {
  const loadUser = useCallback(() => fetchUser(userId), [userId]);
  const { data: user, loading, error, execute } = useAsync(loadUser);
  useEffect(() => { void execute(); }, [execute]);
  if (loading) return <Spinner />;
  if (error) return <ErrorMessage message={error.message} />;
  return <div>{user?.name}</div>;
}
```

## Real-World Use Cases

### 1. useAuth — Authentication Hook

The [authentication context example](../02-core-hooks/10.3.2.05-context-api.md#1-authentication-context) owns a shared session in one provider, exposes `useAuth`, and protects initial loading from superseding a later login/logout. Calling a stateful `useAuth` implementation independently in each component would create separate sessions. Extract the consuming hook for reuse, while keeping shared storage in the provider.

### 2. useWebSocket — Real-Time Connection

The effect owns one connection session and its reconnect timer. Cleanup marks that session stopped before closing the socket, so its close event cannot resurrect it. `onMessage` changes update a callback ref after commit without reopening the connection; a message before that passive Effect flushes can still see the previous callback. The example parses JSON but does not validate the message schema. `send` returning `true` means the browser accepted the call for an open socket, not that the peer received or processed it.

```typescript
import { useState, useEffect, useRef, useCallback } from 'react';

interface UseWebSocketOptions {
  url: string;
  onMessage?: (data: unknown) => void;
  reconnect?: boolean;
  reconnectInterval?: number;
  maxReconnects?: number;
}

function useWebSocket({ url, onMessage, reconnect = true,
  reconnectInterval = 3000, maxReconnects = 5 }: UseWebSocketOptions) {
  const [isConnected, setIsConnected] = useState(false);
  const wsRef = useRef<WebSocket | null>(null);
  const messageRef = useRef(onMessage);
  const stopRef = useRef<(() => void) | null>(null);
  useEffect(() => { messageRef.current = onMessage; }, [onMessage]);

  useEffect(() => {
    let stopped = false;
    let attempts = 0;
    let socket: WebSocket | null = null;
    let timer: ReturnType<typeof setTimeout> | null = null;
    function connect() {
      if (stopped) return;
      const ws = new WebSocket(url);
      socket = ws;
      wsRef.current = ws;
      ws.onopen = () => { if (!stopped) { attempts = 0; setIsConnected(true); } };
      ws.onmessage = event => {
        if (stopped) return;
        let data: unknown;
        try { data = JSON.parse(event.data); }
        catch (error) { console.error('Invalid socket JSON', error); return; }
        messageRef.current?.(data);
      };
      ws.onclose = () => {
        if (stopped) return;
        if (wsRef.current === ws) wsRef.current = null;
        setIsConnected(false);
        if (reconnect && attempts < maxReconnects) {
          attempts++;
          timer = setTimeout(connect, reconnectInterval);
        }
      };
      ws.onerror = () => ws.close();
    }
    function stop() {
      stopped = true;
      if (timer !== null) clearTimeout(timer);
      if (socket) {
        socket.onopen = socket.onmessage = socket.onclose = socket.onerror = null;
        if (wsRef.current === socket) wsRef.current = null;
        socket.close();
      }
    }
    stopRef.current = stop;
    setIsConnected(false);
    connect();
    return () => { stop(); stopRef.current = null; };
  }, [url, reconnect, reconnectInterval, maxReconnects]);

  const send = useCallback((data: unknown): boolean => {
    const ws = wsRef.current;
    if (!ws || ws.readyState !== WebSocket.OPEN) return false;
    ws.send(JSON.stringify(data));
    return true;
  }, []);
  const disconnect = useCallback(() => {
    stopRef.current?.();
    setIsConnected(false);
  }, []);
  return { isConnected, send, disconnect };
}
```

## Common Mistakes

### 1. Breaking the Rules of Hooks

```typescript
// BAD: Hook inside condition
function useBadHook(condition: boolean) {
  if (condition) {
    useState(0); // Conditional hook call
  }
}

// BAD: Hook inside loop
function useBadHook(items: unknown[]) {
  items.forEach(() => {
    useEffect(() => {}); // Hook inside loop
  });
}

// GOOD: Always at top level
function useGoodHook(condition: boolean) {
  const [value] = useState(0);

  useEffect(() => {
    if (condition) {
      // Logic inside effect is fine
    }
  }, [condition]);
}
```

### 2. Not Memoizing Return Values

A fresh return object does not itself schedule a render. It matters when the object is an effect dependency, a context value, or a prop passed across a memoized boundary. Memoize that object when preserving identity helps a measured consumer; callers destructuring primitive fields do not automatically need it. See [useMemo / useCallback](../02-core-hooks/10.3.2.03-usememo-usecallback.md) for the complete dependency and caching examples.

### 3. Creating Stale Closures

An interval effect with `[delay]` that closes over `callback` keeps the callback from its installation render. Either make callback changes restart the timer, or [store the committed callback separately from the timer lifetime](../02-core-hooks/10.3.2.02-useeffect.md#timer-with-cleanup). The latter changes which behavior the next tick sees while preserving the timer cadence.

### 4. Over-Abstracting

```typescript
// BAD: One-line custom hook adds no value
function useDouble(value: number) {
  return value * 2; // Just use `value * 2` inline!
}

// GOOD: Custom hook encapsulates lifecycle-bound logic
function useDocumentTitle(title: string) {
  useEffect(() => {
    document.title = title;
  }, [title]);
}

// Instead of a helper that would be called from a component but could not
// subscribe that component to title changes:
//   useEffect(() => { document.title = title; }, [title]);
```

Use one clear owner for `document.title`; multiple instances of this hook can overwrite one another as their Effects run.

## Best Practices

1. **Start with `use`** — Make custom hooks recognizable to Hook linting and readers

2. **Choose the return shape for the contract** — Use a tuple for a small fixed sequence of values and an object for named results or optional capabilities

3. **Preserve identity when needed** — Memoize values used by identity-sensitive consumers

4. **Accept arguments sparingly** — Use an options object for multiple parameters and document which inputs restart work

5. **Release lasting resources** — Return matching cleanup when setup acquires subscriptions, timers or cancellable work

6. **Handle errors gracefully** — Return error state from async hooks

7. **Separate lifetimes carefully** — A committed callback ref can keep subscriptions stable; reactive request inputs still belong in dependencies

8. **Test in isolation** — Use `renderHook` from `@testing-library/react`

9. **Keep hooks focused** — Each hook should do one thing well

10. **Compose hooks** — Build complex hooks from simpler ones

## Performance Considerations

Custom hooks add function calls and the work performed by their built-in hooks. A fresh return identity can invalidate a memoized prop or effect dependency, but it does not independently schedule an update. First measure expensive computations, subscription churn, and state updates; add identity caching only where a consumer benefits.

| Aspect | Impact | Mitigation |
| -------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Over-memoization | Wasted render cycles | Memoize for measured identity-sensitive consumers |
| Stale closures | Buggy behavior | Keep reactive inputs in dependencies; use a committed callback ref only when subscription lifetime should remain stable |
| State isolation | Clean per-instance state | Use a provider/store when shared state is required |
| Large return objects | Memory overhead | Return only what's needed |
| Frequent re-creation | Can invalidate identity-sensitive consumers | Use `useCallback` only when a consumer benefits from a stable function identity |

```typescript
import { renderHook, act } from '@testing-library/react';

// Test useCounter
test('should increment counter', () => {

// Test useDebounce
test('should debounce value changes', async () => {
  jest.useFakeTimers();

  const { result, rerender, unmount } = renderHook(
    ({ value }) => useDebounce(value, 500),
    { initialProps: { value: 'hello' } }
  );

  expect(result.current).toBe('hello');

  rerender({ value: 'world' });
  expect(result.current).toBe('hello'); // Not updated yet

  act(() => { jest.advanceTimersByTime(500); });
  expect(result.current).toBe('world'); // Updated after delay
  unmount();
  jest.useRealTimers();
});

// Test useLocalStorage
test('should persist value to localStorage', () => {
  const key = 'test-key';
  localStorage.removeItem(key);
  const decodeString = (stored: unknown): string => {
    if (typeof stored !== 'string') throw new TypeError('Expected a string');
    return stored;
  };
  const { result } = renderHook(() => useLocalStorage(key, 'default', decodeString));
  expect(result.current.ready).toBe(true);

  act(() => {
    result.current.setValue('updated');
  });

  expect(localStorage.getItem(key)).toBe('"updated"');
  act(() => { result.current.remove(); });
  expect(localStorage.getItem(key)).toBeNull();
});
```

## Summary

Custom Hooks are the primary mechanism for reusing stateful logic in React. They follow the Hook rules (top-level only, React-only, `use` prefix) and can encapsulate any combination of built-in hooks. Well-designed custom hooks improve code organization, testability, and reusability across components.

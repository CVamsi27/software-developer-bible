# Custom Hooks

Imagine a product page and a compact header that both need the signed-in user's name. The components should share the same session, but they should not each implement loading, errors and refresh behavior. A custom Hook lets both components call the same behavior; a provider or store decides whether the data itself is shared.

## Definition

A **custom Hook** is a JavaScript function that composes React Hooks into reusable behavior. Its name starts with `use`, and a component calls it during render like any other Hook.

> **Textbook Definition:** A custom Hook is a function that composes built-in or other custom Hooks to reuse stateful behavior while associating each invocation with the Hook state of its calling component.

The name helps React's lint rules recognize Hook calls. Unlike a higher-order component or render prop, a Hook returns values to the caller without adding a node to the render tree. It does not create a cache or shared state by itself.

## First Principles

React preserves state by the order of Hook calls made by a component. A custom Hook adds no separate render node: its calls occupy slots in the calling component. This is why two components can reuse one Hook implementation and still get independent state.

Sharing behavior and sharing data are separate decisions. When a Hook reads a provider or external store, that owner supplies shared data; otherwise each caller owns its own state. Likewise, a Hook can coordinate an effect with a component's lifetime, but an ordinary function call has no automatic setup or cleanup phase.

## One implementation, one state per caller

This counter puts the update rule in one place. Each component call gets an independent `count`, while the bounds and step define the behavior of that instance.

```tsx
import { useState } from 'react';

function useCounter(initialValue = 0) {
  const [count, setCount] = useState(initialValue);
  return {
    count,
    increment: () => setCount(value => value + 1),
    reset: () => setCount(initialValue),
  };
}

function CartQuantity() {
  const quantity = useCounter(1);
  return <button onClick={quantity.increment}>Items: {quantity.count}</button>;
}

function RetryCount() {
  const retries = useCounter();
  return <button onClick={retries.increment}>Retries: {retries.count}</button>;
}
```

Clicking one button updates only its component's Hook state. The implementation is shared; the state is not. `initialValue` is used only when that component first mounts; changing the argument later does not reset its state. If both components must observe one session or cart, move that state to a common owner such as Context or a store and let a custom Hook provide a convenient interface to it.

Hooks must be called at the top level of a function component or another custom Hook. A conditional or loop changes call order and can attach later state to the wrong slot. Put the condition inside the Hook's effect or calculation, not around the Hook call. The [Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks) explain the static checks and runtime constraint.

## Effects give reusable behavior a lifetime

A request Hook has more to coordinate than its return shape. When an identifier changes, the old request should stop publishing results; when the component unmounts, the request should be aborted where possible. The effect owns that external work, and its dependencies state which input changes require a new request.

Read [the `useEffect` chapter](../02-core-hooks/10.3.2.02-useeffect.md) for the complete request and cleanup trace. A URL or request option is a reactive input: when it changes, clean up the old request and start the new one. Hiding such an input in a ref can leave obsolete work running. Its debounced search example also shows why a timer and a network request are separate lifetimes: clearing the timer prevents a request from starting, while aborting or ignoring a result handles work already in flight.

When a custom Hook wraps a browser subscription, keep the subscription inputs reactive and remove the exact listener during cleanup. If the subscription should stay installed while only its callback changes, a committed callback ref can separate those lifetimes; that ref updates after commit, so an event in the gap can still call the preceding callback. If several components need a consistent snapshot from one external store, use `useSyncExternalStore` rather than implementing subscription state independently; its [contract and snapshot requirements](10.3.3.04-usesyncexternalstore.md) cover missed updates and concurrent rendering.

## Choose the owner before extracting the Hook

| Behavior | Where the state or resource belongs | Boundary to explain |
| -------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Counter, disclosure, local draft | The component calling the Hook | Each call has independent state; remounting resets it. |
| Signed-in user or shared cart | A provider or store, exposed through a custom Hook | Calling a Hook in two components does not create shared state. See [Context](../02-core-hooks/10.3.2.05-context-api.md). |
| Debounced input | The component's effect and timer | Timer cleanup does not cancel a request that already started. |
| Fetching and caching server data | A query/cache owner or a focused request Hook | Validate response data at runtime; define cancellation, stale results and cache policy. |
| Browser storage | A Hook for one component, or an external store when readers must stay in sync | Parse stored JSON as `unknown` and validate it. With server rendering, read after hydration or provide the same initial snapshot on server and client; cross-tab updates need a subscription. See [cross-tab communication](../../10.1-javascript/06-modern-and-interview/10.1.6.04-cross-tab-communication.md). |
| WebSocket or event subscription | The Hook's effect, or a shared connection manager | Close and reconnect policy, message validation and ownership need explicit contracts. See [WebSockets](../../../60-realtime/60.1-websockets/INDEX.md). |
| Form validation and submission | A form-specific state owner | Dirty state, reset, validation timing and concurrent submission are part of the API. See [form handling](../../10.5-form-handling/INDEX.md). |

Do not extract a Hook merely to shorten a component. A useful Hook hides a repeatable behavior behind a name and a small contract. A calculation such as `value * 2` is an ordinary helper; it does not need React state or lifecycle and should stay an ordinary function.

A Hook may return a fresh object or function on every render. That alone does not schedule another render, but the identity can matter when the result becomes an Effect dependency, context value, or prop to a memoized child. Stabilize it only when that consumer benefits; see [memoization](../02-core-hooks/10.3.2.03-usememo-usecallback.md) for the dependency contract.

## Test the contract callers rely on

Test observable behavior: independent state, setup and cleanup, error handling, and the changed input that should restart work. `renderHook` is useful for a focused Hook test; a component test is still needed when integration with the rendered interface matters.

```tsx
import { act, renderHook } from '@testing-library/react';

test('each caller owns an independent counter', () => {
  const first = renderHook(() => useCounter(0));
  const second = renderHook(() => useCounter(4));

  act(() => first.result.current.increment());

  expect(first.result.current.count).toBe(1);
  expect(second.result.current.count).toBe(4);
});
```

For an effect-backed Hook, also assert that unmount removes the listener or aborts the request, and that changing an input does not let an older result overwrite the current one. Use the test runner's async utilities and fake timers only where the behavior depends on time.

## Summary

A custom Hook packages behavior, while the calling component, provider, or external store owns the state. Hook call order must remain stable. Effects connect reusable behavior to external lifetimes, so dependencies, cleanup, cancellation and stale-result policy belong in the contract. Extract a Hook when its name makes repeated behavior clearer; keep simple calculations as ordinary functions.

# Custom Hooks

Before React introduced Hooks in version 16.8, sharing stateful logic across components was one of the most painful problems in frontend engineering. Teams were forced to choose between flawed architectural patterns: **Mixins** (which caused implicit dependencies and name collisions), **Higher-Order Components** (HOCs, which created deeply nested "wrapper hell" in devtools and obscured component props), and **Render Props** (which led to severe "pyramid of doom" JSX nesting).

**Custom Hooks** solved this entire dilemma in a single, elegant stroke.

A custom Hook is a standard JavaScript function whose name starts with `use` that composes React's built-in primitives (`useState`, `useEffect`, `useRef`, `useCallback`) into modular, reusable units. Instead of wrapping or altering your component tree, custom Hooks let components invoke encapsulated stateful lifecycles directly from within their render execution.

However, custom Hooks are frequently misunderstood:
- Invoking a custom Hook in multiple components does **not** share state between them—it shares **stateful behavior**, granting each calling component its own isolated state slot.
- Custom Hooks must strictly adhere to the **Rules of Hooks** because React tracks execution order through an internal linked list on each component's Fiber node.

Mastering custom Hooks means knowing how to extract complex lifecycles cleanly, how to avoid the notorious stale closure trap, and how to stabilize return values so downstream consumers never re-render unnecessarily.

## Definition

A **custom Hook** is a JavaScript function that starts with the prefix `use` and calls other React Hooks. It extracts component logic into reusable functions that can be tested independently and shared across the application.

> **Textbook Definition:** A custom Hook is a function that composes built-in or other custom Hooks to reuse stateful behavior while associating each invocation with the Hook state of its calling component.

The `use` naming prefix is not cosmetic: it is a compiler and linter contract. It instructs React's ESLint plugin (`eslint-plugin-react-hooks`) to enforce the Rules of Hooks—ensuring hooks are called only at the top level of function components and never inside loops, conditions, or nested functions.

## First Principles

The architecture of custom Hooks is governed by three fundamental mechanics:

1. **Behavior Reuse vs. State Sharing:** A custom Hook reuses the *logic* of state management, not the *instance* of state. When two components call `useDebounce()`, each component allocates independent state memory on its own Fiber. If two components need to read the *same* shared data, that state must live in a parent component, a React Context Provider, or an external store.
2. **The Fiber Linked List Under the Hood:** React does not store hook state inside the function itself. Instead, React maintains a singly linked list of hook records on the component's Fiber node (`fiber.memoizedState -> hook1 -> hook2 -> hook3`). When a component executes a custom Hook, React inlines those hook calls directly into the caller's linked list in the exact order they execute.
3. **Reactive Dependency Integrity:** Custom Hooks must maintain full transparency with respect to reactive inputs. If an effect inside a custom Hook depends on an argument passed to that Hook, that argument **must** be listed in the effect's dependency array. Attempting to bypass dependencies using mutable refs creates stale closure bugs where the Hook acts on outdated props.

```text
Component Fiber Node:
┌────────────────────────────────────────────────────────┐
│ Fiber.memoizedState                                    │
│ ├─ Hook 1: useState(localInput)                        │
│ ├─ Hook 2: [Inlined from useDebounce] useState(val)    │ ──► Allocated directly
│ ├─ Hook 3: [Inlined from useDebounce] useEffect(...)   │     inside the calling
│ └─ Hook 4: [Inlined from useEventListener] useEffect   │     component's Fiber!
└────────────────────────────────────────────────────────┘
```

## Production Custom Hook Patterns

### 1. Resilient Debounce Hook (`useDebounce`)

A classic senior interview and production requirement is debouncing rapidly changing user input (e.g., search queries) to prevent hammering backend APIs:

```typescript
import { useState, useEffect } from 'react';

export function useDebounce<T>(value: T, delayMs: number = 300): T {
  const [debouncedValue, setDebouncedValue] = useState<T>(value);

  useEffect(() => {
    // Schedule state update after the specified delay
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delayMs);

    // Cleanup: cancel the pending timer whenever value or delay changes, or on unmount
    return () => {
      clearTimeout(timer);
    };
  }, [value, delayMs]);

  return debouncedValue;
}
```

#### Usage in Component:
```tsx
function SearchComponent() {
  const [searchTerm, setSearchTerm] = useState('');
  const debouncedSearch = useDebounce(searchTerm, 400);

  useEffect(() => {
    if (debouncedSearch) {
      void fetchSearchResults(debouncedSearch);
    }
  }, [debouncedSearch]);

  return (
    <input
      type="search"
      value={searchTerm}
      onChange={(e) => setSearchTerm(e.target.value)}
      placeholder="Search catalog…"
    />
  );
}
```

Every time `searchTerm` changes, the previous timer is cancelled. Only after the user stops typing for 400 milliseconds does `debouncedValue` update, triggering the search fetch effect cleanly.

### 2. Browser Event Listener Hook (`useEventListener`)

Handling window or DOM events manually inside components leads to forgotten cleanup and memory leaks. A dedicated custom Hook encapsulates lifecycle safety:

```typescript
import { useEffect, useRef } from 'react';

export function useEventListener<K extends keyof WindowEventMap>(
  eventName: K,
  handler: (event: WindowEventMap[K]) => void,
  element: Window | HTMLElement | null = typeof window !== 'undefined' ? window : null
) {
  // Store latest handler in a ref to prevent re-attaching listener on every handler change
  const savedHandler = useRef(handler);

  useEffect(() => {
    savedHandler.current = handler;
  }, [handler]);

  useEffect(() => {
    if (!element) return;

    const eventListener = (event: Event) => {
      savedHandler.current(event as WindowEventMap[K]);
    };

    element.addEventListener(eventName, eventListener);

    return () => {
      element.removeEventListener(eventName, eventListener);
    };
  }, [eventName, element]);
}
```

Notice the architecture: by keeping the latest `handler` inside `savedHandler.current`, the outer `useEffect` does not need `handler` in its dependency array. The listener is attached once and never torn down unnecessarily, while always invoking the freshest handler closure.

### 3. The Event Callback Pattern: Breaking Dependency Cycles

A frequent pain point in React development occurs when an effect needs to read the latest prop or state, but you do *not* want that effect to re-run whenever that prop or state changes.

In React 19+, this is handled by `useEffectEvent`. For React 18, we can construct the equivalent **`useEventCallback`** pattern:

```typescript
import { useCallback, useInsertionEffect, useRef } from 'react';

/**
 * Returns a memoized callback that always accesses the latest closure variables
 * without changing its own reference identity across renders.
 */
export function useEventCallback<Args extends unknown[], R>(fn: (...args: Args) => R) {
  const ref = useRef(fn);

  // useInsertionEffect or useLayoutEffect guarantees ref is updated before paint
  useInsertionEffect(() => {
    ref.current = fn;
  }, [fn]);

  return useCallback((...args: Args) => {
    return ref.current(...args);
  }, []);
}
```

This pattern allows an effect to call `onSuccess(data)` without adding `onSuccess` to the effect's dependencies, completely eliminating unnecessary re-executions.

## Memory and Performance: Stabilizing Hook Return Values

If your custom Hook returns objects or callbacks, remember that returning fresh object literals on every render creates new references:

```typescript
// ⚠️ Potential Performance Bug:
function useUserActions() {
  const [user, setUser] = useState<User | null>(null);

  // Brand new object reference on EVERY render!
  return {
    user,
    resetUser: () => setUser(null), // Brand new function reference on EVERY render!
  };
}
```

If a consuming component passes `resetUser` to a `React.memo` child or lists it in an effect's dependency array, that consumer will re-render or re-run its effect on every tick.

### The Fix:
```typescript
export function useUserActions() {
  const [user, setUser] = useState<User | null>(null);

  const resetUser = useCallback(() => {
    setUser(null);
  }, []);

  return useMemo(() => ({
    user,
    resetUser,
  }), [user, resetUser]);
}
```

## Testing Custom Hooks with `@testing-library/react`

Because custom Hooks cannot be rendered outside a React component, test them using the `renderHook` and `act` utilities:

```typescript
import { renderHook, act } from '@testing-library/react';
import { useDebounce } from './use-debounce';

jest.useFakeTimers();

describe('useDebounce', () => {
  it('should return initial value immediately and update only after delay', () => {
    const { result, rerender } = renderHook(
      ({ value, delay }) => useDebounce(value, delay),
      { initialProps: { value: 'first', delay: 500 } }
    );

    expect(result.current).toBe('first');

    // Trigger update
    rerender({ value: 'second', delay: 500 });
    expect(result.current).toBe('first'); // Still first before delay expires

    // Advance clock
    act(() => {
      jest.advanceTimersByTime(500);
    });

    expect(result.current).toBe('second');
  });
});
```

## Critical Engineering Pitfalls

- **The "God Hook" Anti-Pattern:** Bundling twenty unrelated pieces of component logic into a single massive `useDashboard` hook. Break custom Hooks down by single responsibility (e.g., `useDashboardFilters`, `useMetricsQuery`, `useExportReport`).
- **The Stale Closure Trap:** Capturing state inside an asynchronous callback (like `setTimeout` or `fetch`) without reading from the latest ref or functional state updater (`setCount(prev => prev + 1)`).
- **Thinking Hooks Share State:** Re-iterating for teams: calling `useAuth()` in two separate components executes the Hook twice independently. If you want shared state, wrap the Hook around a React Context or a centralized store.

## Summary

Custom Hooks enable the extraction and reuse of complex stateful lifecycles without polluting the component hierarchy with Higher-Order Components or Render Props. By respecting the Rules of Hooks, keeping reactive dependencies explicit, stabilizing return objects with `useMemo`, and separating logic reuse from state sharing, developers build maintainable and performant frontend architectures.

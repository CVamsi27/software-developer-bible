# useSyncExternalStore

A component reads the current account from a store while another part of the app updates it. If React pauses a render between those reads, one commit could show two different account versions. `useSyncExternalStore` gives React a way to subscribe to an external source and verify the snapshot it is about to commit.

## Definition

`useSyncExternalStore` connects a component to a synchronous snapshot owned outside React. The store provides a subscription, a getter for the current snapshot, and optionally a getter for the initial server-rendered snapshot.

> **Textbook Definition:** `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?)` is a React Hook for observing external stores. React uses the subscription to learn when to re-read the snapshot and checks the snapshot with `Object.is` so a commit does not mix versions of external state.

## First Principles

React owns values updated through `useState` and `useReducer`. A library store or browser API can change independently, so React needs both a notification and a consistent read. The subscription says when to check again; the snapshot says what is true now.

During non-blocking render work, an external store may change after one component has read it but before another component reads it. Before committing, React checks again. If the snapshot changed, React restarts that work as blocking so the committed tree uses one version. This consistency is the main reason to use the Hook; it is not just a convenient way to add a listener.

## Keep the snapshot stable

A store binding needs three parts:

| Argument | Responsibility |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `subscribe(listener)` | Register the listener and return an unsubscribe function. Keep this function stable so each render does not replace the subscription. |
| `getSnapshot()` | Return the current value with no side effects. If the store has not changed, return an `Object.is`-equal value. |
| `getServerSnapshot()` | For SSR, return the initial value used on the server and during hydration. The client must hydrate from the same serialized data. |

For primitive state, the primitive itself is a stable snapshot. For mutable stores with object data, publish an immutable cached snapshot and replace it only when the observed data changes. Allocating `{ ...state }` inside every `getSnapshot` call makes every read look like a change and can trigger an infinite render loop.

```tsx
import { useSyncExternalStore } from 'react';

type Listener = () => void;

function createCounterStore(initialCount: number) {
  let count = initialCount;
  const listeners = new Set<Listener>();

  const subscribe = (listener: Listener) => {
    listeners.add(listener);
    return () => listeners.delete(listener);
  };
  const getSnapshot = () => count;
  const getServerSnapshot = () => initialCount;

  return {
    subscribe,
    getSnapshot,
    getServerSnapshot,
    increment() {
      count += 1;
      listeners.forEach((listener) => listener());
    },
  };
}

// Client-only demo store; create request-scoped instances for server-rendered state.
const counter = createCounterStore(0);

export function Counter() {
  const count = useSyncExternalStore(
    counter.subscribe,
    counter.getSnapshot,
    counter.getServerSnapshot,
  );
  return <button onClick={counter.increment}>Count: {count}</button>;
}
```

`increment` changes the snapshot before notifying listeners, so each listener reads the new count. An identical primitive value compares equal and does not require a render. For server-rendered user data, create the store per request and seed the client from the same serialized initial value; do not share one mutable user store across server requests.

## Select only what a component needs

The base Hook reads a whole snapshot and has no selector argument. A selector-aware binding can derive the value a component needs and use an equality function to reuse an unchanged result. This is why applications normally use their store's React binding instead of connecting every component manually: Zustand selectors and React Redux's `useSelector` build on this external-store contract and provide library-specific selection behavior.

Keep selectors focused and snapshots immutable. If a selector creates a new object on every read, equality never succeeds unless the binding caches or compares the selected fields. Prefer an existing immutable record or a small selected value; add custom equality only when it avoids measured work. A selector narrows store-driven updates, but the component can still render because its parent, local state or context changed.

For browser-owned values such as online status or viewport size, the store adapter listens to the browser event and returns a cached snapshot. During SSR, its server getter should use an explicit neutral value; the browser value is read after hydration. For asynchronous sources such as a WebSocket, the connection owner updates a synchronous cache and notifies it. This Hook does not fetch, persist, reconnect or authorize data.

## Know when the boundary is useful

Use this Hook when a component must read a changing value whose owner is outside React, especially when concurrent rendering could otherwise expose inconsistent snapshots. Prefer React state for values the component owns and a normal Effect when synchronizing one resource into React state is clearer.

External-store updates are synchronous from React's perspective. They can force a transition render to restart as blocking, so do not route every rapidly changing value through one broad store if the UI needs non-blocking transitions. Do not suspend based on a snapshot from this API; a store update can replace already visible Suspense content. Let a framework or query cache own asynchronous loading and suspension.

Test the store contract at the seam: repeated reads without a change keep the same snapshot, writes update it before notification, unsubscribe stops later notifications, and the server and hydration getters use the same initial data.

## Summary

`useSyncExternalStore` connects React to a synchronous value owned elsewhere. Stable subscriptions and cached snapshots let React verify consistency before commit; SSR adds a matching initial snapshot for hydration. Use the store's selector binding when available, and keep async request, persistence and authorization policies with their owners.

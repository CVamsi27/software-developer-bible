# useSyncExternalStore

## Definition

An online indicator reads `navigator.onLine`, but React does not own that browser value. A component that reads it during render can miss later changes; copying it into state with an Effect can also leave a gap between the initial read and subscription.

`useSyncExternalStore` is React's API for reading a synchronous snapshot from a store outside React and subscribing to its changes. It lets React recheck that snapshot before committing work, so one screen does not commit different versions of the same external value.

> **Textbook Definition:** `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?)` connects a component to an external store. The subscription notifies React about changes, the snapshot getter returns the current immutable value, and the optional server getter supplies the matching initial value for server rendering and hydration.

## First Principles

An external source can change without a React state update. React therefore needs two things: a subscription that signals change and a getter that reads the current value. Repeated reads of unchanged data must compare equal with `Object.is`; otherwise React treats every consistency check as another update. Server-rendered components also need matching initial data on the server and during client hydration.

## When the source lives outside React

For React-owned state, use `useState`, `useReducer` or Context. Use this protocol when React needs a current value owned by a library or browser API; it is usually simpler to keep a one-off effect result in React state.

An async database or WebSocket connection is not itself a synchronous snapshot. Its owner receives results, updates a cached snapshot and emits a notification; React reads that cache. This Hook does not implement reconnection, persistence or authorization.

## How It Works

### The Tearing Problem, Concretely

If an external store changes while React prepares a non-blocking transition, React checks the snapshot again before applying DOM changes. When it differs, React restarts that work as a blocking update so the committed tree reads one version. Wrapping the external write in `startTransition` does not turn it into a React-owned transition update.

```text
Without a consistency check:

Time ─────────────────────────────────────────────────▶
Store updates count: 1 ──────────▶ 2

Component A renders, reads count = 1
        ⏸ render interrupted (higher-priority input)
Store now says count = 2
Component B resumes, reads count = 2

Committed frame shows A=1, B=2  ← TEARING: one frame,
                                    two truths
```

With `useSyncExternalStore`, React rechecks the snapshot before commit. If it changed while rendering, React restarts the work rather than committing mixed values.

### The getter supplies evidence; the subscription signals changes

| Argument | Signature | Contract |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `subscribe` | `(onStoreChange: () => void) => () => void` | Register listener; return unsubscribe. Keep function identity stable to avoid resubscription. |
| `getSnapshot` | `() => Snapshot` | Pure, fast read. Repeated calls return the same value while the store is unchanged. |
| `getServerSnapshot` | `() => Snapshot` | Initial value for SSR and hydration; server and initial client render must use the same data. |

### Unchanged data must produce an unchanged snapshot

React compares snapshots with `Object.is`. A primitive getter can return the primitive directly. If the source is mutable and the snapshot is an object or array, cache an immutable snapshot in the store: the getter only returns it, while the source-change handler replaces it when observed data changes and then notifies listeners. Allocating a new object inside every `getSnapshot` call makes every check look like another update and triggers React's “result of `getSnapshot` should be cached” error.

## Code Examples

### 1. Window Size Hook (Platform API)

```typescript
import { useSyncExternalStore } from 'react';
type Viewport = { readonly width: number; readonly height: number };
const FALLBACK_VIEWPORT: Viewport = { width: 0, height: 0 };
function readBrowserViewport(): Viewport {
  return typeof window === 'undefined'
    ? FALLBACK_VIEWPORT
    : { width: window.innerWidth, height: window.innerHeight };
}
let viewportCache = readBrowserViewport();
const viewportListeners = new Set<() => void>();

function getViewport(): Viewport { return viewportCache; }
function refreshViewport() {
  const next = readBrowserViewport();
  if (next.width === viewportCache.width && next.height === viewportCache.height) return;
  viewportCache = next;
  viewportListeners.forEach(listener => listener());
}
function subscribeViewport(onChange: () => void): () => void {
  viewportListeners.add(onChange);
  if (viewportListeners.size === 1) {
    window.addEventListener('resize', refreshViewport);
    refreshViewport(); // Reconcile a resize that happened before subscription.
  }
  return () => {
    viewportListeners.delete(onChange);
    if (viewportListeners.size === 0) window.removeEventListener('resize', refreshViewport);
  };
}
export function useViewport(): Viewport {
  return useSyncExternalStore(subscribeViewport, getViewport, () => FALLBACK_VIEWPORT);
}
```

All readers of this browser module share one listener set, so a resize updates every subscriber instead of only the handler that first changed a shared cache. The first subscription rereads the browser size and reconciles changes that happened while nobody was listening. The getter itself remains a pure cached read. During hydration, React first reads the neutral server snapshot, then reconciles with the current browser dimensions.

### 2. Minimal External Store From Scratch

This small store publishes its initial snapshot for hydration. Treat `initial` and every later object value as immutable. For request-specific server data, create the store per request and initialize the client from the same serialized data; never share one mutable request store at module scope.

```tsx
import { useSyncExternalStore, type ReactElement } from "react";

type Listener = () => void;

export function createStore<T>(initial: T) {
  let state = initial;                    // current immutable snapshot
  const initialSnapshot = initial;        // server + hydration snapshot
  const listeners = new Set<Listener>();

  return {
    getState: (): T => state,
    getInitialState: (): T => initialSnapshot,

    setState(next: T): void {
      if (Object.is(next, state)) return; // bail out on identical value
      state = next;                       // swap reference FIRST...
      listeners.forEach((l) => l());      // ...then notify
    },

    subscribe(listener: Listener): () => void {
      listeners.add(listener);
      return () => { listeners.delete(listener); };
    },
  };
}

// Component binding
const counter = createStore(0);

function Counter(): ReactElement {
  const count = useSyncExternalStore(
    counter.subscribe,
    counter.getState,
    counter.getInitialState
  );
  return (
    <button onClick={() => counter.setState(count + 1)}>
      Count: {count}
    </button>
  );
}
```

Trace `setState(1)`: the store replaces 0 with 1 before notifying; every listener reads 1. Calling `setState(1)` again returns before notification. For an object snapshot, mutate neither the published object nor its nested data in place: produce a new immutable snapshot when observed contents change.

### 3. Selectors Without Unstable Results

`useSyncExternalStore` compares the snapshot it receives; it does not accept a selector or equality function. A selector that allocates an object on every read therefore looks changed even when its fields did not change. A selector-aware adapter can cache the selected result and compare it with the previous one. Keep the selection focused: deriving a full user map to display one user needlessly scans the store on every check.

```tsx
import { useCallback } from 'react';
import { useSyncExternalStoreWithSelector } from 'use-sync-external-store/with-selector';

type User = { id: string; name: string };
type UserView = Pick<User, 'id' | 'name'>;
type AppState = { users: Record<string, User | undefined> };
type Store = {
  subscribe: (listener: () => void) => () => void;
  getState: () => AppState;
  getInitialState: () => AppState;
};
declare const store: Store; // Must publish immutable, cached snapshots.

const sameUserView = (a: UserView | null, b: UserView | null): boolean =>
  a === b || (a !== null && b !== null && a.id === b.id && a.name === b.name);

function useUserView(id: string): UserView | null {
  const selectUser = useCallback((state: AppState): UserView | null => {
    const user = state.users[id];
    return user ? { id: user.id, name: user.name } : null;
  }, [id]);

  return useSyncExternalStoreWithSelector(
    store.subscribe,
    store.getState,
    store.getInitialState, // Serialize the same initial state for hydration.
    selectUser,
    sameUserView,
  );
}
```

The selector reads one record, and the equality function lets a newly allocated view reuse the previous result when its displayed fields are unchanged. If the store already exposes immutable user records, returning `state.users[id] ?? null` is simpler and preserves the reference without a custom comparator. The compatibility package provides the selector adapter; use the selector/equality API supported by the store binding already in the application.

### 4. How Zustand Integrates

```tsx
import { create } from "zustand";
import type { ReactElement } from "react";

interface CartState {
  items: string[];
  add: (sku: string) => void;
}

const useCart = create<CartState>((set) => ({
  items: [],
  add: (sku) =>
    set((state) => ({ items: [...state.items, sku] })),
}));

function CartCount(): ReactElement {
  // Current default Zustand bindings use React.useSyncExternalStore.
  // Selecting this number yields a stable snapshot while the count is unchanged.
  const count = useCart((s) => s.items.length);
  return <span>{count}</span>;
}
```

Select **stable slices** (`s.items.length`, not inline-built objects). Use `useShallow` or an equality-enabled binding for an allocated derived structure. Selecting a slice narrows store notifications; it does not prohibit parent-driven rendering.

### 5. Redux Integration

React-Redux's `useSelector` is the application-facing subscription API; use it instead of wiring `useSyncExternalStore` to Redux yourself. Its default result comparison is strict reference equality, so selectors should return a stable primitive/reference or use the documented equality option for a derived object. The library owns the store subscription and coordinates updates with React. Server rendering still requires application state to be initialized consistently for the request and hydration.

## Boundaries and Failure Modes

| Source | Correct shape | Important boundary |
| ----------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `navigator.onLine` or `matchMedia` | Synchronous getter plus browser event subscription | Treat connectivity as a hint; during SSR use an explicit unknown/neutral snapshot rather than claiming the browser is online. |
| WebSocket, IndexedDB, async storage | Async owner writes results into a synchronous cached snapshot, then notifies | This Hook does not fetch, persist, reconnect, authorize, or cancel the underlying work. |
| Auth/session state | Immutable session snapshot plus refresh/logout notifications | Scope user-specific stores per request on the server; never share one mutable user's state across requests. |
| Large store | Focused selector plus the binding's equality strategy | The base Hook has no selector; broad snapshots make unrelated changes look relevant. Measure before splitting stores. |

Keep `subscribe` stable and return cleanup. Subscribe to the source before relying on a cached value, then let the source handler replace the snapshot before notifying. Do not mutate a published object in place, perform side effects in `getSnapshot`, or suspend from a value that can change through this API: external-store updates are blocking and can replace already-revealed Suspense content.

For a server-rendered reader, `getServerSnapshot` must return the same initial data on the server and during hydration. A neutral browser-only value is often appropriate; request-specific data must be serialized into the client and stores must be created per request. Omitting this getter is valid only for a deliberately client-only render.

Test the integration at its boundaries: unchanged snapshot reads retain identity; a write changes the snapshot before listeners run; a change around subscription is not lost; unmount removes the listener; server and hydration snapshots match; and rapid writes do not commit a mixed view. Use profiling to decide whether selector equality or narrower store ownership is worth its added complexity.

## Summary

`useSyncExternalStore` connects React to a synchronous, immutable snapshot owned elsewhere. The store supplies a stable `subscribe` function and a pure, cached `getSnapshot`; SSR adds a serialized `getServerSnapshot`. Use a selector-aware library binding when a component needs only part of a store, and leave transport, persistence, authorization, and async request policy with their actual owners.

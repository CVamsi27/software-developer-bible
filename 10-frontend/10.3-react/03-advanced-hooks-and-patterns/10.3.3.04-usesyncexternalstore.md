# useSyncExternalStore

## TL;DR

`useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)` is React's official bridge to state that lives *outside* React — Zustand stores, Redux, browser APIs, sockets. It exists because concurrent rendering can **tear**: two components reading an external store mid-render could see different values in one committed frame. The contract is strict: `getSnapshot` must return a cached value with stable reference identity, and returning fresh objects on every call causes infinite re-render loops.

## First Principles

1. **React cannot schedule a write it does not own.** A browser API or external store may change while React is preparing a tree. Merely reading that mutable source during render can give two components different versions of the same data.
2. **A subscription can miss the interval before it is attached.** An effect-only bridge must account for changes between its render-time read and listener setup. React needs both a current snapshot getter and a subscription so it can recheck consistency around attachment and commit.
3. **Consistency checks need stable evidence.** React compares snapshots with `Object.is`. If the getter allocates a new object for unchanged data, a consistency check itself appears to discover another change; caching unchanged snapshots makes the protocol converge. A matching server snapshot provides the same initial evidence for SSR and hydration.

## Why It Matters

Zustand and react-redux 8+ use this integration contract; other libraries, including Jotai, have their own subscription mechanisms. Interviews probe it precisely because it is where React's concurrency model touches the real world: "What is tearing?", "Why does my store hook loop forever?", "What does the third argument do?" Knowing the contract also means you can bind any external source — `matchMedia`, WebSockets, IndexedDB — safely without hand-rolled `useEffect` syncing.

**Concretely:**

1. **Tearing prevention**: In concurrent React, rendering is interruptible; without this hook's snapshot discipline, different components could commit values from different store versions in one frame.
2. **Correct subscription semantics**: A naive effect bridge can miss a change between its render-time read and subscription setup. React also rechecks this Hook's snapshot around subscription and before committing concurrent work, so correctness does not depend on subscriptions attaching before paint.
3. **SSR correctness**: `getServerSnapshot` gives hydration a stable starting value instead of mismatched client data.
4. **A standard for libraries**: One primitive replaces each library's private `useStore` hacks, all sharing the same guarantees.
5. **Direct bindings to platform APIs**: Window size, online status, media queries — anything with events and a readable current value.

## Definition

**useSyncExternalStore** subscribes a component to an external data source. React attaches `subscribe(callback)` on mount and can resubscribe when the subscribe function changes or during development checks, polls `getSnapshot()` during render, and whenever the subscription fires or a render begins, it compares snapshots by reference (`Object.is`) to decide whether the tree is up to date. During server render and hydration it reads `getServerSnapshot`.

```text
HOW REACT KEEPS THE TREE CONSISTENT
═══════════════════════════════════════════════════════════════

 External store            React
┌───────────────┐   subscribe(cb)   ┌──────────────────┐
│  value: T                                   │ ◀──────────────── │ Component mount  │
│               │                   └────────┬─────────┘
│  set(v) ──────┼── cb() ─▶ check snapshot   │
│               │            │                │
│  getSnapshot()                              │ ◀──────────┤ Object.is(old,new)? ──▶ re-render if changed
└─────────────────────────────────────────────┘            │
                             ▼ during CONCURRENT render:
                 every component reading getSnapshot()
                 sees THE SAME snapshot → no tearing
```


## How It Works

### The Tearing Problem, Concretely

When the external snapshot changes during a non-blocking transition, React can restart that work as a blocking update to keep the committed tree consistent. Wrapping an external store mutation in `startTransition` does not make that mutation a non-blocking React state update.

Before React 18, rendering was synchronous: read store, render whole tree, done. Concurrent rendering splits work across frames:

```text
WITHOUT GUARANTEES (naive useState/useEffect bridging):

Time ─────────────────────────────────────────────────▶
Store updates count: 1 ──────────▶ 2

Component A renders, reads count = 1
        ⏸ render interrupted (higher-priority input)
Store now says count = 2
Component B resumes, reads count = 2

Committed frame shows A=1, B=2  ← TEARING: one frame,
                                    two truths
```

With `useSyncExternalStore`, React checks `getSnapshot()` at strategic points (before committing, during interruption recovery). If the snapshot changed mid-render, it restarts the render rather than committing mixed values.

### The Three Arguments

| Argument | Signature | Contract |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `subscribe` | `(onStoreChange: () => void) => () => void` | Register listener; return unsubscribe. Keep function identity stable to avoid resubscription. |
| `getSnapshot` | `() => Snapshot` | Pure, fast, **returns cached value**; same value ⇒ same reference. |
| `getServerSnapshot` | `() => Snapshot` | Value used during SSR + hydration; must represent the same initial data on server and client hydration. |

### Referential Equality Requirements

React compares snapshots with `Object.is`. If `getSnapshot` builds a new object each call, React sees "changed" every time:

```typescript
// BROKEN: new array literal per call → infinite loop
getSnapshot: () => [window.innerWidth, window.innerHeight];

// FIXED: cache until the underlying source changes
let size = { w: window.innerWidth, h: window.innerHeight };
const getSize = () => size;
window.addEventListener("resize", () => {
  const next = { w: innerWidth, h: innerHeight };
  if (next.w !== size.w || next.h !== size.h) {
    size = next;              // new reference ONLY when data changed
    listeners.forEach((l) => l());
  }
});
```

The React error message for violations is explicit: *"The result of getSnapshot should be cached to avoid an infinite loop."*

## Code Examples

### 1. Window Size Hook (Platform API)

```typescript
import { useSyncExternalStore } from 'react';
type Viewport = { readonly width: number; readonly height: number };
const FALLBACK_VIEWPORT: Viewport = { width: 0, height: 0 };
let viewportCache = FALLBACK_VIEWPORT;
const viewportListeners = new Set<() => void>();

function getViewport(): Viewport {
  if (typeof window === 'undefined') return FALLBACK_VIEWPORT;
  const { innerWidth: width, innerHeight: height } = window;
  if (width !== viewportCache.width || height !== viewportCache.height) {
    viewportCache = { width, height };
  }
  return viewportCache;
}
function handleViewportResize() {
  getViewport(); // Refresh once, then notify every subscriber.
  viewportListeners.forEach(listener => listener());
}
function subscribeViewport(onChange: () => void): () => void {
  viewportListeners.add(onChange);
  if (viewportListeners.size === 1) window.addEventListener('resize', handleViewportResize);
  return () => {
    viewportListeners.delete(onChange);
    if (viewportListeners.size === 0) window.removeEventListener('resize', handleViewportResize);
  };
}
export function useViewport(): Viewport {
  return useSyncExternalStore(subscribeViewport, getViewport, () => FALLBACK_VIEWPORT);
}
```

All readers share one listener set, so a resize updates every subscriber instead of only the handler that first changed a shared cache. The getter also detects a size change while no components were subscribed; cache refresh is deterministic and avoids external side effects. Hydration first reads the neutral server snapshot, then reconciles with the current browser dimensions.

### 2. Minimal External Store From Scratch

```typescript
type Listener = () => void;

export function createStore<T>(initial: T) {
  let state = initial;                    // single cached snapshot
  const listeners = new Set<Listener>();

  return {
    getState: (): T => state,

    setState(next: T): void {
      if (Object.is(next, state)) return; // bail out on identical value
      state = next;                       // swap reference FIRST...
      listeners.forEach((l) => l());      // ...then notify
    },

    subscribe(listener: Listener): () => void {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}

// Component binding
const counter = createStore(0);

function Counter(): React.JSX.Element {
  const count = useSyncExternalStore(
    counter.subscribe,
    counter.getState
  );
  return (
    <button onClick={() => counter.setState(count + 1)}>
      Count: {count}
    </button>
  );
}
```

### 3. Selectors Without Loops (the Hard Part)

Selectors transform the snapshot; transforms create fresh objects — the classic trap:

```typescript
// BAD: selector creates a new object per call → infinite loop
function useUserBad(id: string): { id: string } | null {
  return useSyncExternalStore(
    store.subscribe,
    () => {
      const user = store.getState().users[id];
      return user ? { id: user.id } : null; // NEW object every poll!
    }
  );
}
```

```tsx
import { useCallback } from "react";
import { useSyncExternalStoreWithSelector } from "use-sync-external-store/with-selector";
import { shallow as shallowEqual } from "zustand/shallow";

// GOOD: memoized selector layer over the raw snapshot
function useUsersById(): Record<string, User> {
  const selector = useCallback(
    (state: AppState) =>
      Object.fromEntries(
        Object.entries(state.users).map(([id, u]) => [id, u])
      ),
    []
  );

  return useSyncExternalStoreWithSelector(
    store.subscribe,
    store.getState,
    store.getInitialState,   // Serialize this same initial state for client hydration
    selector,
    shallowEqual             // custom equality stops false positives
  );
}
```

The selector shim memoizes derived results and can compare them with custom equality. Zustand's `traditional` bindings use it; current default bindings use React's `useSyncExternalStore` directly, so the supported equality strategy depends on the binding/version.

### 4. How Zustand Integrates

```tsx
import { create } from "zustand";

interface CartState {
  items: string[];
  add: (sku: string) => void;
}

const useCart = create<CartState>((set) => ({
  items: [],
  add: (sku) =>
    set((state) => ({ items: [...state.items, sku] })),
}));

function CartCount(): React.JSX.Element {
  // Current default Zustand bindings use React.useSyncExternalStore.
  // Selecting this number yields a stable snapshot while the count is unchanged.
  const count = useCart((s) => s.items.length);
  return <span>{count}</span>;
}
```

Your job as a Zustand consumer is just rule #1 of the contract: select **stable slices** (`s.items.length`, not inline-built objects) use `useShallow` or an equality-enabled binding for an allocated derived structure.

### 5. Redux Integration (react-redux 8+)

react-redux 8+ uses `useSyncExternalStoreWithSelector` for `useSelector` while retaining its subscription coordination. React checks snapshot consistency around subscription and concurrent commit; this is not a guarantee that subscription setup runs before paint. SSR integrations must supply matching initial server and hydration data, such as Provider's server-state snapshot.

## Real-World Use Cases

Every row below has the same shape — an event that signals change plus a cheap getter for the current value — which is exactly the hook's `(subscribe, getSnapshot)` contract.

| Scenario | Store source | Notes |
| ------------------------ | -------------------------------------------- | -------------------------------------- |
| Online/offline indicator | `navigator.onLine` + `online/offline` events | Tiny, perfect uSES fit |
| Media query hooks | `matchMedia(q).matches` + `change` event | Cache the boolean |
| WebSocket feed | Socket message handler swaps snapshot ref | Reconnect logic in subscribe wrapper |
| Auth session | Session store updated by token refresh timer | Sync logout across UI instantly |
| IndexedDB-backed prefs | Async load writes into sync cache store | uSES reads the cache, not IDB directly |

```typescript
// Real-world: online status in five lines
function useOnline(): boolean {
  return useSyncExternalStore(
    (cb) => {
      addEventListener("online", cb);
      addEventListener("offline", cb);
      return () => {
        removeEventListener("online", cb);
        removeEventListener("offline", cb);
      };
    },
    () => navigator.onLine,
    () => true
  );
}
```

## Common Mistakes

### 1. Unstable Snapshots Causing Infinite Loops

```typescript
// BAD: new object identity on every call
const getSnapshot = (): FilterState => ({
  q: searchParams.get("q") ?? "",
  page: Number(searchParams.get("page") ?? 1),
});
useSyncExternalStore(subscribe, getSnapshot);

// GOOD: cache keyed by the underlying serialized source
let cacheKey: string | undefined;
let cacheValue: FilterState | undefined;
const getSnapshotStable = (): FilterState => {
  const key = searchParams.toString();
  if (cacheValue === undefined || key !== cacheKey) {
    cacheKey = key;
    cacheValue = parseFilters(searchParams); // built ONCE per change
  }
  return cacheValue;
};
```

### 2. Side Effects Inside getSnapshot

```typescript
// BAD: render-phase mutation; breaks purity and double-render safety
() => {
  analytics.track("read-count"); // runs during render!
  return store.count;
};

// GOOD: getSnapshot reads; effects report
() => store.count;
```

### 3. Forgetting to Unsubscribe

```typescript
// BAD: leaks a listener per unmount/mount cycle
subscribe: (cb) => {
  emitter.on("change", cb); // no cleanup returned!
};

// GOOD: symmetric teardown
subscribe: (cb) => {
  emitter.on("change", cb);
  return () => emitter.off("change", cb);
};
```

### 4. Mutating State in Place

```typescript
// BAD: same reference forever → React never learns about changes
store.items.push(newItem);
notify();

// GOOD: replace the reference, then notify
store.items = [...store.items, newItem];
notify();
```

### 5. Divergent Server Snapshot

```typescript
// BAD: hydration mismatch — server says [], client reads localStorage
() => JSON.parse(localStorage.getItem("todos") ?? "[]");

// GOOD: identical neutral snapshot until after hydration
const EMPTY_TODOS: readonly Todo[] = [];
() => EMPTY_TODOS; // getServerSnapshot returns a stable fallback
```

### 6. Using useState + useEffect to Bridge a Store

```typescript
// BAD: misses updates fired between render and effect; tears under
// transitions; double-renders on every change
useEffect(() => {
  store.subscribe((v) => setValue(v));
}, []);

// GOOD: one line, correct timing, no tearing
useSyncExternalStore(store.subscribe, store.getState);
```

## Best Practices

1. **Cache snapshots at the source**: swap references only when data actually changes (`Object.is` bail-outs).
2. **Keep selectors primitive-stable**: prefer selecting scalars, strings, existing references; pass `equalityFn` for derived structures.
3. **Always implement all three arguments for SSR apps**, even trivial ones.
4. **Keep subscription identity stable and derive carefully**: derived snapshots are valid when pure and stable between source changes; use memoized selectors for expensive or allocated transformations.
5. **Never mutate external state in place** — the entire mechanism keys off reference changes.
6. **Reach for uSES before writing another `useEffect` sync** for any event-emitting API with a current-value getter.
7. **Test tearing scenarios** with `React.startTransition` and rapid store writes — the bugs only appear under concurrent load.
8. **Read in render, mutate in events**: `getSnapshot` is a pure read; every store write happens from an event handler or action, never during render.

## Performance Considerations

| Concern | Impact | Mitigation |
| --------------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| Unstable snapshot objects | Infinite re-render / console error | Cache at source; key-based memoization |
| Broad subscriptions (whole store) | Every subscriber re-renders on any change | Selector + equality, slice-level stores |
| Expensive `getSnapshot` | Runs on every render + check | Precompute at write time, O(1) reads |
| Many micro-stores vs one store | Trade-off | Fewer, well-sliced stores beat hundreds of tiny ones |
| Notification storms | Listener loops dominate profile | Batch notifications (`queueMicrotask`/rAF) at store level |

## Summary

- `useSyncExternalStore` is React's concurrency-safe bridge to external mutable state; its purpose is eliminating tearing during interruptible renders.
- Contract: `subscribe` returns cleanup, `getSnapshot` is pure and returns a **cached reference**, `getServerSnapshot` powers SSR/hydration.
- Reference identity is everything — new objects from `getSnapshot` mean infinite loops; mutations-in-place mean missed updates.
- Zustand and modern react-redux are thin selector layers over this hook; understanding it demystifies both.
- Any platform API shaped like "event + current value" (media queries, online status, viewport, sockets) deserves a uSES binding instead of effect-syncing.

## Revision Questions

**First Principles**

1. **Q:** What is "tearing", and why does interruptible rendering make it possible?
   **A:** One committed frame showing *different values of the same external state* in different components. React can pause a render mid-tree for higher-priority input; if the store changes during that pause, components rendered before it keep the old value while resumed components read the new one — two truths in a single frame.

2. **Q:** Why not just bridge a store with `useState` + `useEffect`?
   **A:** A naive bridge can miss a change between reading the source and attaching its listener, and can commit inconsistent values during concurrent rendering. React rechecks external snapshots around subscription and concurrent commit; attachment before paint is not the guarantee.

**How It Works**

3. **Q:** What is the `getSnapshot` contract, and what happens when it's broken?
   **A:** It must be pure and return a *cached* reference — same data ⇒ same object. A fresh object per call makes React's `Object.is` check report "changed" on every render, which triggers another render, which produces another fresh object: an infinite loop, plus the warning *"The result of getSnapshot should be cached to avoid an infinite loop."*

4. **Q:** What is `getServerSnapshot` for, and when does React stop using it?
   **A:** It's what the server render *and* the hydration render read so the markup matches; after hydration, with the subscription attached, React reads `getSnapshot`. Returning a client-only value (e.g. from `localStorage`) as the server snapshot causes a hydration mismatch.

**Code Examples**

5. **Q:** In the viewport hook, where does referential stability come from?
   **A:** The getter retains its cached object while dimensions match. The shared resize handler refreshes it and notifies every subscriber; React suppresses a resulting render when the selected snapshot is unchanged.

6. **Q:** Why does the hand-rolled store assign `state = next` *before* notifying listeners?
   **A:** Listeners synchronously re-read the snapshot when notified; notifying first would make them read the stale value and conclude nothing changed. The `Object.is` bail-out before the swap also keeps identical updates from waking subscribers at all.

**Common Mistakes**

7. **Q:** Why does an inline selector like `() => ({ id: user.id })` loop forever, and what's the fix?
   **A:** It builds a new object on every poll, so `Object.is` never sees equality. Fix it by caching at the source (rebuild only when the underlying data changes) or by using `useSyncExternalStoreWithSelector` with an equality function such as `shallowEqual` — the selector shim used by Zustand's traditional equality-enabled bindings.

**Best Practices**

8. **Q:** When should you reach for this hook instead of an effect?
   **A:** Whenever the source looks like "events + a current-value getter" — `matchMedia`, online status, sockets, `store.getState()`. React checks snapshot consistency around subscription and concurrent commit and supports a matching server snapshot. External-store mutations may force a transition to restart as blocking work; pre-paint subscription setup is not the contract.

# React Performance Optimization

## Definition

React performance optimization is the practice of improving the speed, responsiveness, and efficiency of React applications. It involves reducing unnecessary re-renders, minimizing bundle size, optimizing rendering cycles, and improving user experience metrics like First Contentful Paint (FCP) and Interaction to Next Paint (INP). It is as much about *removing* work (fewer components in the tree, fewer rows in the DOM, fewer bytes shipped) as about caching the work that remains — every memo and boundary adds bookkeeping of its own.

> **Textbook Definition:** React performance engineering measures and reduces the cost of delivering useful interface updates. Rendering work, host layout, network latency and bundle execution are distinct costs, so an optimization must address the measured bottleneck.


## First Principles

1. **The main thread has finite time between input and visible feedback.** Component calculations, DOM writes, layout and paint compete for that time. Making one stage faster cannot fix a bottleneck in another, so measure React render work separately from browser work.
2. **Skipping work requires proof that its output is unchanged.** Memoization compares inputs and retains previous results. Unstable identities can defeat that proof, while an incomplete dependency list can falsely reuse obsolete output; both correctness and comparison cost matter.
3. **Scheduling redistributes work; it does not remove its cost.** A transition can yield between React work units and abandon obsolete renders, but it cannot preempt an arbitrary synchronous calculation. Virtualization reduces mounted work, code splitting delays downloaded work, and a worker moves suitable calculations off the main thread.

## Find which stage delays visible feedback

Suppose typing into a product search feels slow. Trace the interaction before choosing an optimization:

```text
input event → set query → calculate matches → React render
           → DOM update → browser layout/paint → visible result
```

React DevTools Profiler identifies component render work. The browser Performance panel shows event handlers, long tasks, DOM work, layout and paint. Measure loading separately: downloading a chart library can delay the initial page even when later renders are fast. A normal production React build does not enable production profiling; use a profiling-enabled build when collecting those measurements.

| Finding | Change to try | What it cannot solve |
| ------------------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------- |
| A local keystroke renders an unrelated large subtree | Move state closer to its readers; introduce a measured memo boundary | Expensive work in the input handler |
| Repeated calculation has unchanged inputs | Cache it with `useMemo` | The first calculation or different inputs |
| Thousands of mounted rows overwhelm rendering/DOM work | Virtualize the collection | Fetching and filtering the full dataset |
| Urgent input waits for non-urgent React rendering | Defer the result value or use a transition | Preempting one synchronous computation |
| Initial route transfers unused code | Split routes/heavy optional features | Layout or render cost of code already loaded |

## Code Examples

### Keep typing urgent and let the result view lag

This complete component accepts a product array. The input owns the immediate query; the result list receives a deferred query. `memo` lets the list skip the urgent render when its props are unchanged, and `useMemo` reuses its filtering result for unchanged inputs.

```tsx
import { memo, useDeferredValue, useMemo, useState } from "react";

type Product = { id: string; name: string };
const ProductResults = memo(function ProductResults({
  products, query,
}: { products: readonly Product[]; query: string }) {
  const matches = useMemo(() => {
    const normalized = query.trim().toLocaleLowerCase();
    return products.filter(product =>
      product.name.toLocaleLowerCase().includes(normalized));
  }, [products, query]);
  return <ul>{matches.map(product =>
    <li key={product.id}>{product.name}</li>)}</ul>;
});

export function ProductSearch({ products }: { products: readonly Product[] }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;
  return <section>
    <label htmlFor="product-search">Find a product</label>
    <input id="product-search" type="search" value={query}
      onChange={event => setQuery(event.target.value)} />
    <p role="status">{isStale ? "Updating results…" : "Results up to date"}</p>
    <div aria-busy={isStale} style={{ opacity: isStale ? 0.6 : 1 }}>
      <ProductResults products={products} query={deferredQuery} />
    </div>
  </section>;
}
```

Type `ca` after `c`: the urgent render updates the input while the memoized list still has the old deferred value. React prepares the newer list in the background and can abandon obsolete React work when more input arrives. The filter itself is one synchronous JavaScript call and cannot be interrupted mid-loop. For a costly filter, narrow the dataset, query the server or move suitable computation into a worker; deferral does not reduce that CPU cost. It also does not debounce network requests.

`memo` compares each prop with `Object.is`. A fresh `products` array every parent render defeats that comparison; an actual data change should defeat it. State or consumed Context changes can still render a memoized component. Cache a callback with `useCallback` when its identity matters to a consumer; native event handlers do not need universal callback caching.

### Mount fewer rows when DOM size is the bottleneck

The following complete component uses `@tanstack/react-virtual`. It renders a scroll window plus an overscan buffer while preserving the full collection's scroll height. Filtering/data access remain separate concerns.

```tsx
import { useRef } from "react";
import { useVirtualizer } from "@tanstack/react-virtual";

type Item = { id: string; label: string };
export function VirtualList({ items }: { items: readonly Item[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    getItemKey: index => items[index].id,
    estimateSize: () => 50,
    overscan: 10,
  });
  return <div ref={parentRef} role="region" aria-label="Items" tabIndex={0}
    style={{ height: 600, overflow: "auto" }}>
    <ul style={{ height: virtualizer.getTotalSize(), position: "relative",
      margin: 0, padding: 0, listStyle: "none" }}>
      {virtualizer.getVirtualItems().map(row =>
        <li key={row.key} aria-posinset={row.index + 1}
          aria-setsize={items.length} style={{ position: "absolute", top: 0,
            left: 0, width: "100%", height: row.size,
            transform: `translateY(${row.start}px)` }}>
          {items[row.index].label}
        </li>)}
    </ul>
  </div>;
}
```

This example uses fixed-height text rows. Variable-height rows need measurement; interactive rows need a focus policy because scrolling can unmount the focused item. Browser find-in-page and assistive-technology access to unmounted content also need product decisions, such as a non-virtualized or paginated alternative. Stable domain keys preserve row identity; they do not by themselves determine virtualization's speed.

### Code Splitting

> Worked example in [Suspense](10.3.3.01-suspense.md) → *Code Examples → Basic React.lazy*: `lazy(() => import(...))` per route behind one `<Suspense fallback>`, reducing initial transferred code; measure its effect on load and interaction latency. Here it only matters that the lever is load-time, not render-time — memoization does not reduce the code downloaded for the initial route.

### A transition marks a state update as non-urgent

`useDeferredValue` is useful when the component receives a value whose update it does not control. `useTransition` is useful when it controls the setter, such as selecting an expensive tab. A transition exposes pending state and allows React to schedule that rendering behind urgent input. Use the complete Action and tab examples in [Modern Hooks](../04-modern-react/10.3.4.01-modern-hooks-react18-19.md); transitions do not control text inputs or act as CSS animations.

## Real-World Use Cases

- **Dashboards with many live widgets** — measure each stage; virtualize an offscreen collection or memoize unchanged widget inputs only when that work dominates.
- **Feeds/tables with thousands of rows** — `react-virtuoso` renders only visible rows; preserve stable record identity and test scrolling, focus and accessibility.
- **Search-as-you-type over large datasets** — `useDeferredValue`/`useTransition` keep typing responsive while the heavy list re-renders (→ 10.3.4.01).
- **Bundle bloat after feature creep** — `React.lazy` route-level splitting; the win shows up in FCP/INP (→ 50.3.1.01), not in component benchmarks.

## Common Mistakes

| Mistake | Root Cause | Fix |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| Wrapping every callback in `useCallback` | Adds dependency checks and caching; may provide no benefit to a native event handler | Cache identity when a measured consumer or dependency benefits |
| Passing inline objects or array literals to memoized children | `{ ...style }` or `[a, b]` creates a new heap reference every render, breaking equality | Hoist static values outside the component or wrap dynamic objects in `useMemo` |
| Using array index as JSX `key` in dynamic lists | Reconciliation fails to map identity when items reorder or delete, retaining state under the wrong record | Always use stable, unique domain IDs (`item.id`) |
| Monolithic Context providers triggering cascading renders | Any value update in a Context forces all consumers to re-render, even if slice is unused | Split contexts into independent providers or migrate to `useSyncExternalStore` |
| Returning fresh object literals from custom hooks | Consumers depending on that object see a changed dependency each render; a loop occurs if the effect also causes another such render | Return stable values when the consumer needs identity stability; otherwise depend on the relevant fields |
| Assuming `useMemo` caches across component instances | `useMemo` cache is instance-scoped; 1,000 instances compute the value 1,000 times | Use module-level LRU cache or server-state cache (TanStack Query) for cross-instance sharing |
| Sprinkling `useMemo` over trivial derivations "for performance" | Memo bookkeeping runs on every render, and the first render always pays it — `useMemo` never speeds up initial mount | Memoize only measured hot paths (large filters/sorts); leave `a + b` inline |

## Best Practices

1. **Profile before optimizing** — use React DevTools Profiler ("Highlight updates" + flamegraph) to identify actual render bottlenecks before adding memoization
2. **Colocate state** — keep state as close as possible to the components that read and write it; parent state triggers child re-renders
3. **Stabilize values where identity matters** — memo boundaries, effect dependencies and provider values are common consumers
4. **Virtualize collections when measured rendering or DOM size is excessive** — list complexity and target devices matter more than a universal row threshold
5. **Route-level code splitting** — load non-critical routes and heavy dependencies (charts, rich-text editors) via `React.lazy()` and `Suspense`
6. **Embrace Concurrent Transitions** — use `useTransition` for non-urgent route or tab changes to preserve main-thread input responsiveness
7. **React Compiler Readiness** — write idiomatic React following the Rules of Hooks and pure functions so the React Compiler can automate memoization cleanly

## Performance Considerations

| Metric | Target | Tool | Primary Lever |
| ------------------------- | ------- | -------------------------------------- | --------------------------------------- |
| First Contentful Paint | ≤ 1.8s | Lab and field data | Route code-splitting, critical CSS |
| Largest Contentful Paint | ≤ 2.5s | Lab and field data | Image optimization, SSR / Edge delivery |
| Interaction to Next Paint | ≤ 200ms | Field data / browser Performance tools | Reduce long tasks and interaction work |
| Cumulative Layout Shift | ≤ 0.1 | Lab and field data | Explicit image/element dimensions |

Assess field experience at the 75th percentile, separately for mobile and desktop. A short Lighthouse load run does not measure the full session's interactions or later layout shifts; laboratory traces explain causes, while field data establishes user impact. FCP is a useful loading diagnostic; LCP, INP and CLS are the Core Web Vitals.

## Summary

React performance optimization is the measured reduction of unnecessary re-renders, bundle size, and commit overhead. Key strategies include targeted memoization (`React.memo`, `useMemo`, `useCallback`), virtualization for collection rendering, route code-splitting, and concurrent features (`useTransition`, `useDeferredValue`). Always profile in production mode before introducing memoization layers.

# React Performance Optimization

Typing into a product search feels slow. Memoizing every callback may change nothing if the browser is spending its time laying out thousands of rows—or if one synchronous filter blocks the main thread. First find which part of the interaction delays visible feedback.

## Definition

**React performance optimization** reduces the measured cost of rendering useful UI updates by removing unnecessary work or scheduling it around urgent input. The method begins with a concrete latency symptom and targets its measured cause.

> **Textbook Definition:** React performance engineering measures latency across component rendering, DOM commit, browser layout and paint, JavaScript execution, and code loading. An optimization is effective only when it reduces the stage responsible for the observed delay without changing required behavior.

## First Principles

Follow one interaction from its input event through calculation, React rendering, DOM updates and browser paint. The React Profiler shows component work; the browser Performance panel shows long tasks, layout and paint. Field metrics show whether a lab improvement helps real users. These tools answer different questions, so measure the stage that users experience as slow.

Use Core Web Vitals as outcome measures: at the 75th percentile, good results are LCP at or below 2.5 seconds, INP at or below 200 milliseconds, and CLS at or below 0.1. Measure mobile and desktop separately. A lab trace helps explain a cause; field data shows its impact across devices and sessions.

## Match the fix to the delay

| What the trace shows | Try | The boundary |
| ------------------------------------------------------ | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Unrelated components render after a local state change | Move state closer to its readers; add a measured `memo` boundary | A memoized component still renders for its own state or consumed Context. |
| A pure calculation repeats with unchanged inputs | Profile it, then consider `useMemo` | It cannot skip the first calculation or preempt a synchronous calculation. |
| Typing waits for an expensive result view | Keep input state urgent and pass a deferred value to the result subtree | `useDeferredValue` defers rendering; it does not debounce requests or make the calculation faster. |
| Thousands of DOM rows dominate work | Virtualize or paginate the visible collection | Unmounted rows affect keyboard focus, screen-reader navigation and browser find-in-page. |
| Initial load includes rarely used feature code | Split a route or large optional feature | The first visit may wait for an extra chunk and its fallback. |

A small search can use a memoized result subtree while React renders the new query in the background:

```tsx
import { memo, useDeferredValue, useMemo, useState } from 'react';

type Product = { id: string; name: string };

const Results = memo(function Results({
  products,
  query,
}: {
  products: readonly Product[];
  query: string;
}) {
  const visible = useMemo(() => {
    const normalized = query.trim().toLowerCase();
    return products.filter((product) =>
      product.name.toLowerCase().includes(normalized),
    );
  }, [products, query]);

  return <ul>{visible.map((item) => <li key={item.id}>{item.name}</li>)}</ul>;
});

export function ProductSearch({ products }: { products: readonly Product[] }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);

  return (
    <section>
      <label htmlFor="product-search">Find a product</label>
      <input
        id="product-search"
        value={query}
        onChange={(event) => setQuery(event.target.value)}
      />
      {query !== deferredQuery && <p role="status">Updating results…</p>}
      <Results products={products} query={deferredQuery} />
    </section>
  );
}
```

The input updates urgently while the result subtree can lag. By default, `memo` compares each prop with `Object.is`; it lets this subtree skip the urgent render because its deferred query and product reference have not changed. A newly allocated `products` array defeats that skip, while local state or consumed Context can still render the component. React can interrupt background rendering when another keystroke arrives, but it cannot stop the filter once that JavaScript call has started. For a large dataset, reduce the work, query an indexed server endpoint, or move suitable computation to a worker. Debounce separately when the goal is fewer network requests.

Manual memoization is a performance cache, not a correctness tool. It earns its complexity when profiling shows repeated work or an unstable identity prevents a measured consumer from skipping work. React Compiler can automatically memoize eligible components and values when enabled; still measure the interaction and keep behavior correct without a cache.

Virtualization reduces mounted rows rather than making each row render faster. Use stable record keys, and test scrolling, focus restoration and screen-reader behavior when offscreen rows unmount. Code splitting reduces initial transfer but moves some loading cost to the first visit; pair it with an intentional Suspense fallback.

When collecting React Profiler timings, use a profiling-enabled build; the ordinary production build may omit profiling instrumentation. Compare the same interaction, data volume and device conditions before and after the change.

## Summary

Measure the user-visible interaction, identify whether rendering, synchronous JavaScript, DOM work or code loading dominates, then choose the matching lever. Keep input urgent, make large work smaller, and add memoization only when it skips measured work. Verify the result with production-like traces and field metrics.

# React Performance Optimization

## TL;DR

React performance optimization involves: profiling with React DevTools and browser tools (identify rendering and browser costs), memoization (`React.memo`, `useMemo`, `useCallback`), virtualization for long lists (`react-window`, `react-virtuoso`), code splitting (`React.lazy`, `Suspense`), and avoiding reconciliation thrash with stable keys.

## First Principles

1. **The main thread has finite time between input and visible feedback.** Component calculations, DOM writes, layout and paint compete for that time. Making one stage faster cannot fix a bottleneck in another, so measure React render work separately from browser work.
2. **Skipping work requires proof that its output is unchanged.** Memoization compares inputs and retains previous results. Unstable identities can defeat that proof, while an incomplete dependency list can falsely reuse obsolete output; both correctness and comparison cost matter.
3. **Scheduling redistributes work; it does not remove its cost.** A transition can yield between React work units and abandon obsolete renders, but it cannot preempt an arbitrary synchronous calculation. Virtualization reduces mounted work, code splitting delays downloaded work, and a worker moves suitable calculations off the main thread.

## Why It Matters

Senior engineers measure before optimizing: `Profiler` API in a profiling-enabled production build, `why-did-you-render` in dev. They know that `React.memo` is wasted work if the component re-renders for other reasons, and that `useMemo` doesn't memoize across component instances. The biggest perf wins usually come from reducing work, not memoizing existing work.

**Concretely:**

React applications can become slow due to unnecessary re-renders, large bundle sizes, expensive computations, poor state management, and missing memoization.

## Definition

React performance optimization is the practice of improving the speed, responsiveness, and efficiency of React applications. It involves reducing unnecessary re-renders, minimizing bundle size, optimizing rendering cycles, and improving user experience metrics like First Contentful Paint (FCP) and Interaction to Next Paint (INP). It is as much about *removing* work (fewer components in the tree, fewer rows in the DOM, fewer bytes shipped) as about caching the work that remains — every memo and boundary adds bookkeeping of its own.


## How It Works

### Performance Optimization Hierarchy

React Profiler measures render work; use the browser Performance panel to assess DOM work, layout and paint. Production profiling is disabled in standard builds unless a profiling build is selected. Optimizations can improve responsiveness without reducing total CPU work, especially when transitions restart obsolete renders.

```text
Level 1: Component Optimization
├── React.memo: Prevent unnecessary re-renders
├── useMemo: Memoize expensive computations
├── useCallback: Memoize function references
└── State colocation: Keep state close to usage

Level 2: Bundle Optimization
├── Code splitting: Lazy load components
├── Tree shaking: Remove unused code
├── Dynamic imports: Load on demand
└── Compression: gzip, brotli

Level 3: Rendering Optimization
├── Virtualization: Render only visible items
├── Concurrent features: Prioritize updates
├── useTransition: Defer non-urgent updates
└── useDeferredValue: Lag behind source value

```

## Code Examples

### React.memo

```typescript
import React, { memo, useState, useCallback } from 'react';

const MemoizedChild = memo(({ data, onClick }: { data: Data; onClick: () => void }) => {
  console.log('MemoizedChild rendered');
  return <div onClick={onClick}><p>{data.text}</p></div>;
});

const Parent = () => {
  const [count, setCount] = useState(0);
  const [data] = useState({ text: 'Hello' });
  const handleClick = useCallback(() => console.log('clicked'), []);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
      <MemoizedChild data={data} onClick={handleClick} />
    </div>
  );
};

```

`React.memo` compares props shallowly — one `Object.is` per prop, no deep equality. The `useState`-held `data` and `useCallback`-held `onClick` are what make the comparison pay off: leave either one unstable and the memo comparison fails on that prop.

### useMemo for Expensive Computations

```typescript
const DataVisualization = ({ rawData, now }: { rawData: RawDataPoint[]; now: number }) => {
  const [timeRange, setTimeRange] = useState('all');

  const processedData = useMemo(() => {
    const filtered = rawData.filter(d =>
      timeRange === 'all' || d.timestamp >= now - timeRangeToMs(timeRange)
    );
    return filtered.sort((a, b) => a.value - b.value);
  }, [rawData, timeRange, now]);

  return (
    <div>
      <TimeRangeSelector value={timeRange} onChange={setTimeRange} />
      <Chart data={processedData} />
    </div>
  );
};

```

### Virtualization

```typescript
import { useVirtualizer } from '@tanstack/react-virtual';

const VirtualList = ({ items }: { items: Item[] }) => {
  const parentRef = useRef<HTMLDivElement>(null);

  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 50,
    overscan: 10,
  });

  return (
    <div ref={parentRef} style={{ height: '600px', overflow: 'auto' }}>
      <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
        {virtualizer.getVirtualItems().map(virtualRow => (
          <div key={virtualRow.key} style={ {
            position: 'absolute', top: 0, left: 0, width: '100%',
            height: virtualRow.size, transform: `translateY(${virtualRow.start}px)`,
          }}>
            <ListItem item={items[virtualRow.index]} />
          </div>
        ))}
      </div>
    </div>
  );
};

```

### Concurrent Features (useTransition & useDeferredValue)

```typescript
import { memo, useState, useTransition, useDeferredValue } from 'react';

// 1. useTransition for deferring heavy UI transitions
export const TabSwitcher = () => {
  const [tab, setTab] = useState<'overview' | 'analytics'>('overview');
  const [isPending, startTransition] = useTransition();

  const handleSelectTab = (nextTab: 'overview' | 'analytics') => {
    // Non-urgent transition: input/clicks remain interactive while Analytics renders
    startTransition(() => {
      setTab(nextTab);
    });
  };

  return (
    <div>
      <div className="tab-buttons">
        <button onClick={() => handleSelectTab('overview')}>Overview</button>
        <button onClick={() => handleSelectTab('analytics')}>Analytics</button>
      </div>
      {isPending && <span className="loading-badge">Transitioning views...</span>}
      {tab === 'overview' ? <OverviewView /> : <AnalyticsView />}
    </div>
  );
};

const DeferredResults = memo(({ data, query }: { data: string[]; query: string }) => {
  const items = data.filter(item => item.toLowerCase().includes(query.toLowerCase()));
  return <FilteredItemList items={items} />;
});

// 2. useDeferredValue for responsive search-as-you-type
export const SearchBox = ({ data }: { data: string[] }) => {
  const [query, setQuery] = useState('');
  // Deferred results can lag; cooperative scheduling does not guarantee 60fps
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;


  return (
    <div>
      <input
        type="search"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Type to filter immediately..."
      />
      <div style={{ opacity: isStale ? 0.6 : 1, transition: 'opacity 0.2s' }}>
        <DeferredResults data={data} query={deferredQuery} />
      </div>
    </div>
  );
};
```

## Real-World Use Cases

- **Dashboards with 50+ live widgets** — virtualize the grid + memoize each widget; measure first or you'll memoize the wrong 50.
- **Feeds/tables with thousands of rows** — `react-virtuoso` renders only visible rows; pair with stable keys (→ 10.3.1.03's reconciliation) or virtualization gains vanish.
- **Search-as-you-type over large datasets** — `useDeferredValue`/`useTransition` keep typing responsive while the heavy list re-renders (→ 10.3.4.01).
- **Bundle bloat after feature creep** — `React.lazy` route-level splitting; the win shows up in FCP/INP (→ 50.3.1.01), not in component benchmarks.

## Common Mistakes

| Mistake | Root Cause | Fix |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Wrapping every callback in `useCallback` | Adds dependency checks and caching; may provide no benefit to a native event handler | Cache identity when a measured consumer or dependency benefits |
| Passing inline objects or array literals to memoized children | `{ ...style }` or `[a, b]` creates a new heap reference every render, breaking equality | Hoist static values outside the component or wrap dynamic objects in `useMemo` |
| Using array index as JSX `key` in dynamic lists | Reconciliation fails to map identity when items reorder or delete, retaining state under the wrong record | Always use stable, unique domain IDs (`item.id`) |
| Monolithic Context providers triggering cascading renders | Any value update in a Context forces all consumers to re-render, even if slice is unused | Split contexts into independent providers or migrate to `useSyncExternalStore` |
| Returning fresh object literals from custom hooks | Hook callers receive new references every render, triggering downstream `useEffect` loops | Memoize the returned object using `useMemo` inside custom hooks |
| Assuming `useMemo` caches across component instances | `useMemo` cache is instance-scoped; 1,000 instances compute the value 1,000 times | Use module-level LRU cache or server-state cache (TanStack Query) for cross-instance sharing |
| Sprinkling `useMemo` over trivial derivations "for performance" | Memo bookkeeping runs on every render, and the first render always pays it — `useMemo` never speeds up initial mount | Memoize only measured hot paths (large filters/sorts); leave `a + b` inline |

## Best Practices

1. **Profile before optimizing** — use React DevTools Profiler ("Highlight updates" + flamegraph) to identify actual render bottlenecks before adding memoization
2. **Colocate state** — keep state as close as possible to the components that read and write it; parent state triggers child re-renders
3. **Stabilize values where identity matters** — memo boundaries, effect dependencies and provider values are common consumers
4. **Virtualize collections when measured rendering or DOM size is excessive** — list complexity and target devices matter more than a universal row threshold
5. **Route-level code splitting** — load non-critical routes and heavy dependencies (charts, rich-text editors) via `React.lazy()` and `Suspense`
6. **Embrace Concurrent Transitions** — use `useTransition` for non-urgent route or tab changes to preserve main-thread input responsiveness
7. **React Compiler Readiness** — write idiomatic React following the Rules of Hooks and pure functions so the React Compiler can automate memoization cleanly

## Performance Considerations

| Metric | Target | Tool | Primary Lever |
| ------------------------- | ------- | -------------------------------------- | --------------------------------------- |
| First Contentful Paint | < 1.8s | Lighthouse | Route code-splitting, critical CSS |
| Largest Contentful Paint | < 2.5s | Lighthouse | Image optimization, SSR / Edge delivery |
| Interaction to Next Paint | ≤ 200ms | Field data / browser Performance tools | Reduce long tasks and interaction work |
| Cumulative Layout Shift | < 0.1 | Lighthouse | Explicit image/element dimensions |

## Summary

React performance optimization is the measured reduction of unnecessary re-renders, bundle size, and commit overhead. Key strategies include targeted memoization (`React.memo`, `useMemo`, `useCallback`), virtualization for collection rendering, route code-splitting, and concurrent features (`useTransition`, `useDeferredValue`). Always profile in production mode before introducing memoization layers.

## Revision Questions

**First Principles**

1. **Q:** What two distinct diseases does a flamegraph let you tell apart, and why does it matter?
   **A:** *Too-wide* renders — many components re-rendering (cure: memoization, state colocation) vs. *too-expensive* commits — heavy DOM churn (cure: virtualization, fewer nodes). Treating DOM churn with `React.memo` does nothing, because the components doing the rendering were never the bottleneck.

2. **Q:** Why is "reduce the work, don't memoize it" the right first instinct?
   **A:** Memoization only caches work you still perform, and it adds comparison and bookkeeping overhead to every render. Deleting the work — fewer rows in the DOM via virtualization, fewer bytes via code splitting, fewer components re-rendering via colocation — removes cost outright instead of relocating it.

**Code Examples**

3. **Q:** In the `React.memo` example, why do `data` and `onClick` need `useState`/`useCallback` for the memo to bite?
   **A:** `memo` compares props shallowly with `Object.is`; an inline object or a re-created function is a fresh reference on every parent render, so the comparison always fails. Stabilizing both props is what lets the comparison succeed and skip the child's render.

4. **Q:** What is the dimmed list in `SearchBox` communicating to the user?
   **A:** `useDeferredValue(query)` lags behind the input while the heavy filter re-renders, so `query !== deferredQuery` means the visible list still matches an older query. Dropping its opacity tells the user "these results are behind your typing" instead of letting stale results look final or the UI look frozen.

**Common Mistakes**

5. **Q:** Why can deleting an index-keyed row transfer state to the wrong record?
   **A:** React reuses positions whose index keys match, potentially assigning an old row's state to a different record after deletion. Stable domain keys preserve the intended row identities.

6. **Q:** Why doesn't `useMemo` let 1,000 chart instances compute a value once?
   **A:** The cache lives in each instance's hook slots, so 1,000 instances mean 1,000 independent caches. Cross-instance sharing requires something outside the component — a module-level LRU or an external cache like TanStack Query.

**Best Practices**

7. **Q:** When does wrapping a tiny handler in `useCallback` actually hurt?
   **A:** When no identity-sensitive consumer uses its stable reference, the cache adds bookkeeping without skipping useful work. Effects, providers and custom Hook APIs can also supply legitimate consumers besides memoized children.

8. **Q:** What is the correct order of operations before adding a memo layer?
   **A:** Record a DevTools Profiler flamegraph of the real interaction, confirm whether render width or DOM work dominates, then apply the matching lever — memo for wide renders, virtualization for big trees, splitting for load. Unmeasured memoization only moves the bottleneck.

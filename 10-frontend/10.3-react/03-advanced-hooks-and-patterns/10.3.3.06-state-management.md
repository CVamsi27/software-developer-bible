# State Management

## TL;DR

State management is choosing where state lives: local (`useState`/`useReducer`), context (low-frequency shared), external store (Zustand, Jotai, Redux Toolkit, Recoil), or server state (React Query, SWR, RSC). The right choice depends on update frequency, scope, and persistence needs.

## First Principles

1. **A value needs one authoritative owner before it needs a transport.** Duplicated writable copies can disagree. Put independent UI state near its consumer, lift genuinely shared state to a common owner, and expose that owner's updates through a provider or store.
2. **Remote data remains authoritative outside the application.** A local copy can become stale without a local user action. Server-state tools therefore track requests, freshness, invalidation and retries; UI state such as an open menu does not need the same cache lifecycle.
3. **A reader must know which changes affect its output.** Context compares the provided value, while a selector-based binding compares a selected snapshot. Immutable updates and stable selected values make those comparisons meaningful; parent renders and a component's own state can still cause rendering independently of its store selection.

## Why It Matters

Senior engineers distinguish client state (UI, forms) from server state (data fetched from APIs). They use React Query/SWR for server state (caching, refetching, mutations) and a small client store (Zustand/Jotai) for cross-component client state. They avoid Context for high-frequency updates and avoid Redux for simple apps.

## Definition

State management in React refers to how application state (data that changes over time) is stored, updated, and shared across components. It ranges from local component state (`useState`) to global state management solutions (Redux, Zustand, Jotai) and server state management (React Query/TanStack Query).

## The Problem It Solves

### The Problem

As applications grow, state becomes complex:

1. **Shared state**: Multiple components need the same data

2. **Derived state**: Data computed from other state

3. **Async state**: Data from APIs with loading/error states

4. **Persistent state**: Data that persists across page reloads

5. **Server state**: Data synchronized with a backend

### State Categories

```text
State Categories:
═══════════════════════════════════════════════════════════════

1. Local State (useState)
   ├── Component-specific data
   ├── Form inputs
   ├── UI state (open/closed, active tab)
   └── Temporary data

2. Lifted State (useState + props)
   ├── Shared between siblings
   ├── Parent-child communication
   └── Common ancestors

3. Global State (Context, Redux, Zustand)
   ├── App-wide data (theme, auth, language)
   ├── Deeply nested components
   └── Cross-cutting concerns

4. Server State (React Query, SWR)
   ├── API data
   ├── Caching
   ├── Background refetching
   └── Optimistic updates

5. URL State
   ├── Current route
   ├── Query parameters
   └── Filters, pagination

```

## How It Works

### Local State vs Global State

```text
Local State vs Global State:
═══════════════════════════════════════════════════════════════

Local State (useState):
┌─────────────────────────────────────────────────────────────┐
│ Component A                                                 │
│ ├── [count, setCount] = useState(0)                         │
│ └── count is ONLY available in Component A                  │
│                                                             │
│ Component B                                                 │
│ └── Cannot access count!                                    │
└─────────────────────────────────────────────────────────────┘

Global State (Context/Redux):
┌─────────────────────────────────────────────────────────────┐
│ Store/Context                                               │
│ └── [user, setUser] = { user: {...}, setUser: ... }         │
│                                                             │
│ Component A                                                 │
│ └── const user = useContext(AuthContext) // Can access!     │
│                                                             │
│ Component B                                                 │
│ └── const user = useContext(AuthContext) // Can access!     │
└─────────────────────────────────────────────────────────────┘

```

### Context vs Redux vs Zustand

```text
Comparison:
═══════════════════════════════════════════════════════════════

Context API:
├── Built into React
├── Simple to use
├── Good for: themes, auth, language
├── Limitations: performance, devtools
└── No middleware, no time-travel

Redux:
├── Third-party library
├── Complex but powerful
├── Good for: complex state logic
├── Features: middleware, devtools, time-travel
└── Steep learning curve

Zustand:
├── Third-party library (lightweight)
├── Simple API
├── Good for: medium complexity
├── Features: middleware, devtools
└── Minimal boilerplate

Jotai:
├── Third-party library (atomic)
├── Bottom-up approach
├── Good for: granular state
├── Features: async, devtools
└── Minimal boilerplate

```

### Server State vs Client State

```text
Server State vs Client State:
═══════════════════════════════════════════════════════════════

Client State (useState, Redux):
┌─────────────────────────────────────────────────────────────┐
│ Data owned by the client                                    │
│ ├── Form inputs                                             │
│ ├── UI state (modals, tabs)                                 │
│ ├── User preferences                                        │

┌─────────────────────────────────────────────────────────────┐
│ Data owned by the server                                    │

│ ├── Orders from backend                                     │

│                                                             │

│ Persistence: Server database                                │

└─────────────────────────────────────────────────────────────┘

```

## Code Examples

### Local State with useState

```typescript
const Counter = () => {
  const [count, setCount] = useState(0);
  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
    </div>
  );
};

```

### Lifted State

```typescript
const Parent = () => {
  const [count, setCount] = useState(0);
  return (
    <div>
      <p>Count: {count}</p>
      <Child count={count} onIncrement={() => setCount(c => c + 1)} />
    </div>
  );
};

const Child = ({ count, onIncrement }: { count: number; onIncrement: () => void }) => (
  <button onClick={onIncrement}>Count: {count}</button>
);

```

### Context API

> [Context API — Basic Context](../02-core-hooks/10.3.2.05-context-api.md#basic-context) owns the typed provider, consumer and missing-provider contract. Context transports state to descendants; it does not determine the state-transition logic.

### Zustand

```typescript
import { create } from 'zustand';

interface TodoStore {
  todos: Todo[];
  addTodo: (text: string) => void;
  toggleTodo: (id: string) => void;
  deleteTodo: (id: string) => void;
}

const useTodoStore = create<TodoStore>((set) => ({
  todos: [],
  addTodo: (text) => set((state) => ({
    todos: [...state.todos, { id: crypto.randomUUID(), text, completed: false }],
  })),
  toggleTodo: (id) => set((state) => ({
    todos: state.todos.map((t) => t.id === id ? { ...t, completed: !t.completed } : t),
  })),
  deleteTodo: (id) => set((state) => ({
    todos: state.todos.filter((t) => t.id !== id),
  })),
}));

// Usage
const TodoList = () => {
  const todos = useTodoStore((state) => state.todos);
  const addTodo = useTodoStore((state) => state.addTodo);
  return <div>{/* ... */}</div>;
};

```

### Redux Toolkit

Immer permits draft mutation inside a reducer while producing an immutable result. ID creation belongs in action preparation, outside the reducer, so replaying an action remains deterministic.

```typescript
import { createSlice, configureStore, type PayloadAction } from '@reduxjs/toolkit';

const todosSlice = createSlice({
  name: 'todos',
  initialState: [] as Todo[],
  reducers: {
    addTodo: {
      reducer: (state, action: PayloadAction<Todo>) => { state.push(action.payload); },
      prepare: (text: string) => ({ payload: { id: crypto.randomUUID(), text, completed: false } }),
    },
    toggleTodo: (state, action) => {
      const todo = state.find((t) => t.id === action.payload);
      if (todo) todo.completed = !todo.completed;
    },
  },
});

const store = configureStore({ reducer: { todos: todosSlice.reducer } });

```

### React Query (TanStack Query)

```typescript
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

const useUsers = () => useQuery({
  queryKey: ['users'],
  queryFn: async ({ signal }) => {
    const response = await fetch('/api/users', { signal });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json();
  },
});

const useCreateUser = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (newUser: CreateUserDTO) => {
      const response = await fetch('/api/users', {
        method: 'POST', headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(newUser),
      });
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return response.json();
    },
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['users'] }),
  });
};

```

### Optimistic Updates

The following rollback example assumes mutations affecting the same cached list are serialized. Overlapping mutations need a more careful reconciliation strategy, because restoring one old snapshot can erase another optimistic patch. A fetch Promise rejects on network failure, but HTTP error statuses must be converted into thrown errors explicitly for `onError` to run.

```typescript
const useToggleTodo = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (id: string) => {
      const response = await fetch(`/api/todos/${id}/toggle`, { method: 'PATCH' });
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return response;
    },
    onMutate: async (id) => {
      await queryClient.cancelQueries({ queryKey: ['todos'] });
      const previous = queryClient.getQueryData<Todo[]>(['todos']);
      queryClient.setQueryData<Todo[]>(['todos'], old =>
        old?.map((t) => t.id === id ? { ...t, completed: !t.completed } : t)
      );
      return { previous };
    },
    onError: (err, id, context) => {
      if (context?.previous !== undefined) queryClient.setQueryData(['todos'], context.previous);
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: ['todos'] }),
  });
};

```

## Real-World Use Cases

- **Auth/session + theme + feature flags** — server state or context (rarely changes; wide reads); the canonical Context use case (→ 10.3.2.05).
- **Multi-step forms with cross-field validation** — local state per step + one form library store; lifting everything global makes every keystroke a store event.
- **Real-time collaborative views** — external store via `useSyncExternalStore` (→ 10.3.3.04) so websocket snapshots don't fight React's renderer.
- **Server-data-heavy apps** — React Query/SWR own the server cache; Redux/Zustand own only true client state. The "is Redux dead" answer: server-state tools ate its main job.

## Common Mistakes

1. **Putting everything in global state**: Broad subscriptions can rerender on unrelated writes, so a modal's `open` flag kept globally redraws the whole tree that reads it. Keep state at the lowest common ancestor that needs it — lift only when a sibling actually appears.

2. **Not normalizing state**: Nested copies force you to rebuild every ancestor path to update one entity, and the same entity stored in two places goes stale in one of them. A flat `{ byId, allIds }` shape makes an update a single-key replace with one source of truth.

3. **Using Context for complex state**: Context has no selectors — changing the provider's value re-renders *every* consumer regardless of which slice it reads — and it ships no middleware, devtools, or time-travel. Use narrower providers or selector-based subscriptions when those broad notifications are a measured cost. Context can transport a reducer with complex logic; complexity alone does not require another library.

4. **Not handling loading/error states**: An async value read during render before it settles either crashes on `undefined` or flashes stale data. Every fetch surface needs pending/error branches (or Suspense + an error boundary) so failure is a state the UI displays, not an unhandled exception.

5. **Over-fetching**: Refetching on every mount, focus, or keystroke multiplies latency and backend load. A query cache with a staleness window and invalidation (React Query) serves cached data immediately and revalidates in the background.

## Best Practices

1. **Start with local state**: Use useState for component-specific data

2. **Lift state when needed**: Move state to common ancestor for siblings

3. **Use Context for global data**: Theme, auth, language

4. **Use Redux/Zustand for complex state**: Multiple updates, middleware

5. **Use React Query for server state**: Caching, background refetching

6. **Normalize state**: Flat structures for efficient updates

7. **Colocate state**: Keep state near where it's used

## Summary

State management ranges from local useState to global Redux/Zustand and server state React Query. Choose based on complexity: local state for component data, Context for global data, Redux/Zustand for complex logic, React Query for server data.

## Revision Questions

**First Principles**

1. **Q:** Why does remote data need more than a global client-state container?
   **A:** The remote owner can change data without a local event, so cached copies need freshness, requests, invalidation and retry policies. A plain client store can hold that data but does not provide those policies automatically. TanStack Query manages the request/cache lifecycle; application-specific optimistic rollback still needs an explicit policy.

2. **Q:** What is the selector model, and why is it "the performance contract"?
   **A:** A binding reads a selected slice and compares it with the previous selected value. An unchanged slice can suppress a store-triggered render; the component can still render from its parent, local state or context. Immutable normalized data and focused selectors help unchanged slices retain identity.

**How It Works**

3. **Q:** When can one broad context value cause costly updates?
   **A:** Context has no selectors — any change to the provider's value re-renders every consumer, even one that reads a different field — and it offers no middleware, devtools, or time-travel. Split independent context values or use selector-based subscriptions when broad consumer updates are costly. A reducer plus context can still handle complex state; frequency alone is not a prohibition.

4. **Q:** What actually distinguishes server state from client state?
   **A:** Ownership and timing. Server state arrives asynchronously with loading/error and can be invalidated externally, so it needs cache/revalidate/retry semantics; client state is owned by the application; React schedules its local updates, and persistence is optional.

**Code Examples**

5. **Q:** Why do all three steps in the optimistic-toggle mutation — cancel, snapshot, rollback — exist?
   **A:** `cancelQueries` stops an in-flight refetch from overwriting the patch; the `previous` snapshot returned from `onMutate` lets `onError` restore the exact prior list when the PATCH fails; `onSettled` revalidates either way so the cache converges on server truth.

6. **Q:** Why does the Zustand example subscribe to `state.todos` and `state.addTodo` separately?
   **A:** Each `useTodoStore(selector)` call compares its selected value to decide whether that store update requires a render. Selecting the whole store — or returning an inline-built object — would wake the component on every write, defeating the selector contract from First Principles.

**Common Mistakes**

7. **Q:** Why does normalization matter more as the app grows?
   **A:** Nested copies mean one entity update rebuilds every ancestor path, and duplicates drift out of sync; a flat `byId`/`allIds` map updates a single key, keeps one source of truth, and makes lookups O(1).

**Best Practices**

8. **Q:** State appears and the team asks "where does it go?" — give the decision rule.
   **A:** Component-only → `useState`/`useReducer`; shared by siblings → lift to the common ancestor; low-frequency app-wide reads → Context; complex high-frequency client logic → Zustand/Redux; anything fetched from an API → React Query; anything shareable via link → the URL.

# State Management

When a user edits a server-backed profile, the name in the input is a draft; the server still owns the saved record. If both values are stored in one place, a background refresh can overwrite the draft or an optimistic update can make an unconfirmed change look permanent. Start by naming the owner of each value.

```tsx
const [draft, setDraft] = useState(user.name); // local: the user's unconfirmed edit
const { data: saved } = useQuery({ queryKey: ['user', id], queryFn: fetchUser }); // server: the confirmed record
// Refreshing `saved` never clobbers `draft`; saving writes `draft` through a mutation.
```

## Definition

**State management** defines where application values live, who may change them, how readers learn about updates and how long each value remains valid. It avoids conflicting copies by assigning each value an explicit source of truth.

> **Textbook Definition:** State management specifies the ownership, lifetime and transition rules for application data. Local interface state, shared client state, URL state and cached remote state have different sources of truth and require different synchronization and recovery policies.

## First Principles

For each value, identify its source of truth, readers, lifetime and valid transitions. Then choose the smallest mechanism that coordinates those readers. A library cannot fix unclear ownership: duplicating one server record in two independently writable caches creates competing truths even if both libraries work correctly.

## How It Works

### 1. Choose by Ownership

| Value | Usual owner | Useful boundary |
| ------------------------------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Draft, open panel or temporary selection | Component `useState` or `useReducer` | It ends when the component identity is removed unless deliberately lifted or persisted. |
| Value shared by nearby components | Nearest common parent | Props and callbacks make the shared transition explicit. |
| Low-churn value needed across a subtree | Context plus state/reducer in its owner | Context transports the value; it does not own transitions or select individual fields. |
| Independently changing client state with distant readers | Selector-based store such as Zustand or Redux | Select only what a component reads; parent, local-state and Context updates still apply. |
| Remote records with loading, freshness and invalidation needs | One server-state cache such as TanStack Query, RTK Query or SWR | The server remains authoritative; a query key partitions cached responses but does not authorize a request. |
| Shareable filter, sort or page selection | Validated URL state | URLs can be edited, bookmarked and restored through Back/Forward. |

Persisted browser storage adds a lifetime across reloads, but it is not automatically authoritative. Parse and migrate stored values on read, and decide how local edits reconcile with server changes. For large client-owned relational collections, keep one record per ID plus a separate ordered ID list; do not copy a query cache into a second global store merely to normalize remote data.

### 2. Trace One Server-Backed Edit

Keep the editor draft local while the query cache holds the last confirmed server record. Send a validated mutation with the record version, then put the accepted response into the cache. The version check lets the server reject an edit based on an outdated record.

```tsx
import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';

type User = { id: string; name: string; version: number };
type Rename = { id: string; name: string; expectedVersion: number };

declare function readUsers(tenantId: string, signal: AbortSignal): Promise<User[]>;
// The API validates input and authorization, then enforces expectedVersion atomically.
declare function renameUser(tenantId: string, edit: Rename): Promise<User>;

export function useTenantUsers(tenantId: string) {
  const client = useQueryClient();
  const queryKey = ['users', tenantId] as const;
  const users = useQuery({
    queryKey,
    queryFn: ({ signal }) => readUsers(tenantId, signal),
  });
  const rename = useMutation({
    mutationFn: (edit: Rename) => renameUser(tenantId, edit),
    onSuccess: async (saved) => {
      client.setQueryData<User[]>(queryKey, (current) =>
        current?.map((user) => user.id === saved.id ? saved : user),
      );
      await client.invalidateQueries({ queryKey });
    },
  });

  return { users, rename };
}
```

The query key includes the tenant because it changes the response; include other response-shaping filters too. Never put credentials in a key. The server must authorize every request regardless of the key. The query's abort signal can cancel supported obsolete reads; response validation and server-side tenant checks belong at the API boundary.

The input's `draft` stays in component state. While a save is pending, show the proposed value as a temporary UI overlay — for example, from the mutation variables — while the cache continues to represent confirmed data. On success, replace the matching cached record with the accepted version. On a version conflict, refresh and let the user compare or rebase the draft rather than silently overwriting newer data.

In TanStack Query v5, `staleTime` describes how long data is considered fresh; `gcTime` controls how long inactive data remains cached. Invalidating marks matching data stale and normally refetches active queries. These policies govern the client copy, not the server's truth. Mutation retries need an explicit safety contract: a timeout can leave the client unsure whether the server committed the operation.

An optimistic cache patch can improve perceived speed, but snapshot-and-rollback is unsafe when concurrent mutations overlap: an older failure can restore a snapshot over a newer update. Prefer a local pending overlay when that is enough. If shared optimistic state is required, track operations or versions and test out-of-order success and failure; serialize mutations only when the product semantics allow it.

### 3. Keep Transitions and Tools Explicit

Use a reducer when several fields must change together under named transitions; complexity alone does not require Redux. Use Context for a scoped dependency or low-churn state. Choose a selector-based store when distant client readers need independent subscriptions or explicit action tooling. Use a query cache for remote request lifecycles, and keep a single cache owner for each remote collection. Choose a URL when the state should be shareable and history-aware.

When a record is normalized, store one client-owned entity by ID and keep order separately. When it is remote data, let the query cache own its freshness and invalidation rather than mirroring it into Redux or Zustand. These tools can coexist when they own different values.

## Summary

Choose state by source of truth, readers and lifetime. Keep drafts local, lift shared values to their nearest owner, use Context or a selector-based store for different client sharing needs, and give remote data one cache owner with explicit freshness and conflict rules. Validate URL and API input at their boundaries; client state never replaces server authorization.

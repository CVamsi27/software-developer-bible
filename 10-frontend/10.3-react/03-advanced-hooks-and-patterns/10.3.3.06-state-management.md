# State Management

## Definition

State management in React refers to how application state (data that changes over time) is stored, updated, and shared across components. It ranges from local component state (`useState`) to global state management solutions (Redux, Zustand, Jotai) and server state management (React Query/TanStack Query).

> **Textbook Definition:** State management defines the ownership, lifetime and transition rules for application data. Local UI state, shared client state and remotely authoritative state require different synchronization, invalidation and recovery policies.

## First Principles

1. **A value needs one authoritative owner before it needs a transport.** Duplicated writable copies can disagree. Put independent UI state near its consumer, lift genuinely shared state to a common owner, and expose that owner's updates through a provider or store.
2. **Remote data remains authoritative outside the application.** A local copy can become stale without a local user action. Server-state tools therefore track requests, freshness, invalidation and retries; UI state such as an open menu does not need the same cache lifecycle.
3. **A reader must know which changes affect its output.** Context compares the provided value, while a selector-based binding compares a selected snapshot. Immutable updates and stable selected values make those comparisons meaningful; parent renders and a component's own state can still cause rendering independently of its store selection.

## Trace one editable server record

A user's name is persisted by the server. The text currently typed into its editor is a local draft. A filter in the URL is shareable navigation state. A query cache holds a remote copy with a freshness policy. Treating all four as one mutable global object creates competing owners.

```text
server record → query cache → rendered view
                                ↓ edit opens
                            local draft
                                ↓ validated mutation
server accepts/rejects ← request with record version
        ↓ accepted
confirmed response → cache update → targeted revalidation
```

## Which mechanism supplies the missing responsibility?

| Owner/need | Mechanism | Boundary |
| -------------------------------------------------- | ------------------------------- | ------------------------------------------------------ |
| One component's draft or open state | `useState` / `useReducer` | Independent hook calls do not share state |
| Several siblings share one value | Lift to a common owner | Props/callbacks carry that owner's state |
| Descendants need a provider's value | Context | Transport; transition logic still belongs to its owner |
| Many readers need selected external state | Zustand, Redux or atomic stores | Subscription and transition policies vary by library |
| Remote records need request/freshness coordination | TanStack Query | The server remains authoritative |
| Filters must survive sharing/back navigation | Router URL state | Parse and validate parameters |

Context can carry complex reducer state; complexity alone does not require another library. Redux is useful when explicit actions, middleware, tooling and replay matter. Zustand supplies a compact external-store API. Jotai organizes state around atoms. Compare the needed update/subscription contract before choosing among them.

## Code Examples

### Local State with useState

```tsx
import { useState } from 'react';

const Counter = () => {
  const [count, setCount] = useState(0);
  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
    </div>
  );
};

```

### Lifted State

```tsx
import { useState } from 'react';

const Parent = () => {
  const [count, setCount] = useState(0);
  return (
    <div>
      <p>Count: {count}</p>
      <Child count={count} onIncrement={() => setCount(c => c + 1)} />
    </div>
  );
};

const Child = ({ count, onIncrement }: { count: number; onIncrement: () => void }) => (
  <button onClick={onIncrement}>Count: {count}</button>
);

```

### Context API

> [Context API — Basic Context](../02-core-hooks/10.3.2.05-context-api.md#basic-context) owns the typed provider, consumer and missing-provider contract. Context transports state to descendants; it does not determine the state-transition logic.

### Zustand

```typescript
import { create } from 'zustand';

type Todo = { id: string; text: string; completed: boolean };

interface TodoStore {
  todos: Todo[];
  addTodo: (text: string) => void;
  toggleTodo: (id: string) => void;
  deleteTodo: (id: string) => void;
}

const useTodoStore = create<TodoStore>((set) => ({
  todos: [],
  addTodo: (text) => set((state) => ({
    todos: [...state.todos, { id: crypto.randomUUID(), text, completed: false }],
  })),
  toggleTodo: (id) => set((state) => ({
    todos: state.todos.map((t) => t.id === id ? { ...t, completed: !t.completed } : t),
  })),
  deleteTodo: (id) => set((state) => ({
    todos: state.todos.filter((t) => t.id !== id),
  })),
}));

// Usage
const useTodoCount = () => useTodoStore(state => state.todos.length);

```

### Redux Toolkit

Immer permits draft mutation inside a reducer while producing an immutable result. ID creation belongs in action preparation, outside the reducer, so replaying an action remains deterministic.

```typescript
import { createSlice, configureStore, type PayloadAction } from '@reduxjs/toolkit';

type Todo = { id: string; text: string; completed: boolean };

const todosSlice = createSlice({
  name: 'todos',
  initialState: [] as Todo[],
  reducers: {
    addTodo: {
      reducer: (state, action: PayloadAction<Todo>) => { state.push(action.payload); },
      prepare: (text: string) => ({ payload: { id: crypto.randomUUID(), text, completed: false } }),
    },
    toggleTodo: (state, action) => {
      const todo = state.find((t) => t.id === action.payload);
      if (todo) todo.completed = !todo.completed;
    },
  },
});

const store = configureStore({ reducer: { todos: todosSlice.reducer } });

```

### How TanStack Query coordinates the remote copy

The following complete React component module targets **TanStack Query v5 and Zod v4** in a browser SPA. The authenticated API contract is `GET /api/tenants/:tenant/users` returning User[], and `PATCH .../users/:id` returning the accepted User. The backend must verify tenant access, validate the desired name, and atomically enforce `If-Match` against the record version (409/412 on conflict). Query keys do not provide server authorization.

```tsx
import { useRef, useState, type FormEvent } from 'react';
import { QueryClient, QueryClientProvider, useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import { z } from 'zod';

const UserSchema = z.object({
  id: z.string().min(1), name: z.string().min(1), version: z.number().int().nonnegative()
});
type User = z.infer<typeof UserSchema>;
type Edit = { id: string; name: string; version: number };
class ApiError extends Error {
  constructor(readonly status: number, message: string) { super(message); }
}
const NameSchema = z.string().trim().min(1).max(100);
const usersKey = (tenant: string, principal: string) => ['users', tenant, principal] as const;
const usersPath = (tenant: string) => `/api/tenants/${encodeURIComponent(tenant)}/users`;

async function readUsers(tenant: string, signal: AbortSignal): Promise<User[]> {
  const response = await fetch(usersPath(tenant), { signal });
  if (!response.ok) throw new Error(`Read failed: ${response.status}`);
  return z.array(UserSchema).parse(await response.json());
}
async function renameUser(tenant: string, edit: Edit): Promise<User> {
  const response = await fetch(`${usersPath(tenant)}/${encodeURIComponent(edit.id)}`, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json', 'If-Match': `"${edit.version}"` },
    body: JSON.stringify({ name: edit.name })
  });
  if (!response.ok) throw new ApiError(response.status, `Save failed: ${response.status}`);
  const saved = UserSchema.parse(await response.json());
  if (saved.id !== edit.id) throw new TypeError('Unexpected saved identity');
  return saved;
}

function Users({ tenant, principal }: { tenant: string; principal: string }) {
  const client = useQueryClient();
  const key = usersKey(tenant, principal);
  const [editing, setEditing] = useState<User | null>(null);
  const [draft, setDraft] = useState('');
  const [inputError, setInputError] = useState('');
  const submitting = useRef(false);
  const query = useQuery({
    queryKey: key,
    queryFn: ({ signal }) => readUsers(tenant, signal),
    staleTime: 30_000,
    retry: false
  });
  const save = useMutation({
    mutationFn: (edit: Edit) => renameUser(tenant, edit),
    retry: false,
    onSuccess: async saved => {
      await client.cancelQueries({ queryKey: key, exact: true });
      client.setQueryData<User[]>(key, previous =>
        previous?.map(user => user.id === saved.id ? saved : user)
      );
      setEditing(null);
      await client.invalidateQueries({ queryKey: key, exact: true });
    },
    onError: async error => {
      if (error instanceof ApiError && (error.status === 409 || error.status === 412)) {
        await client.invalidateQueries({ queryKey: key, exact: true });
      }
    }
  });
  const latestEditing = editing && query.data?.find(user => user.id === editing.id);
  const versionConflict = save.error instanceof ApiError &&
    (save.error.status === 409 || save.error.status === 412);

  async function submit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (!editing || submitting.current) return;
    const parsed = NameSchema.safeParse(draft);
    if (!parsed.success) { setInputError('Enter a name from 1 to 100 characters.'); return; }
    setInputError('');
    submitting.current = true;
    try { await save.mutateAsync({ id: editing.id, name: parsed.data, version: editing.version }); }
    catch { /* save.error supplies the visible failure; keep the draft */ }
    finally { submitting.current = false; }
  }

  if (query.isPending) return <p role="status">Loading users…</p>;
  if (!query.data) return <section>
    {query.isError && <p role="alert">Users could not be loaded.</p>}
    <button type="button" onClick={() => void query.refetch()}>Retry loading users</button>
  </section>;
  return (
    <section>
      {query.isFetching && <p role="status">Refreshing users…</p>}
      {query.isError && <div>
        <p role="alert">Refresh failed; showing the previously loaded list.</p>
        <button type="button" onClick={() => void query.refetch()}>Retry refresh</button>
      </div>}
      <ul>{query.data.map(user => <li key={user.id}>
        {save.isPending && save.variables.id === user.id ? `${save.variables.name} (saving…)` : user.name}
        <button type="button" disabled={save.isPending} onClick={() => {
          save.reset(); setEditing(user); setDraft(user.name); setInputError('');
        }}>Edit {user.name}</button>
      </li>)}</ul>
      {editing && <form onSubmit={submit}>
        <label htmlFor="user-name">Name</label>
        <input id="user-name" value={draft} disabled={save.isPending} onChange={event => setDraft(event.target.value)} />
        <button disabled={save.isPending}>Save</button>
        {inputError && <p role="alert">{inputError}</p>}
        {save.isError && <p role="alert">Save failed. Review the current server record before retrying.</p>}
        {versionConflict && latestEditing && latestEditing.version !== editing.version && <div>
          <p role="status">The server now has “{latestEditing.name}” at version {latestEditing.version}. Your draft remains in the form.</p>
          <button type="button" onClick={() => { setEditing(latestEditing); save.reset(); }}>
            Keep my draft and retry against the latest version
          </button>
        </div>}
        {versionConflict && !latestEditing && <p role="status">This record no longer exists. Copy the draft before closing the editor.</p>}
        <button type="button" disabled={save.isPending} onClick={() => { setEditing(null); save.reset(); }}>Cancel</button>
      </form>}
    </section>
  );
}

export function UsersApp({ tenant, principal }: { tenant: string; principal: string }) {
  const [client] = useState(() => new QueryClient());
  return <QueryClientProvider client={client}>
    <Users key={JSON.stringify([tenant, principal])} tenant={tenant} principal={principal} />
  </QueryClientProvider>;
}
```

1. The key scopes cached data to the tenant and principal; the query supplies a signal to fetch and validates the response.
2. Opening the editor copies an identified version into a local draft. Editing does not mutate the cached record.
3. During the request, the row shows the proposed name from mutation variables. This is a temporary **UI overlay**, not an optimistic cache write.
4. On success, the accepted version enters the cache and matching active queries revalidate. A 409/412 conflict refreshes the list and exposes the current server name/version; the user can explicitly keep the draft and retry against that version. Other failures retain the draft without changing the cache.

The component assumes one editor entry point for this list. A ref closes the same-component double-submit gap before React paints its pending state; it does not serialize another tab, another component or server writers. The server's version check resolves those conflicts. The API returns a desired name update, rather than a non-idempotent 'toggle' operation.

A keyed remount discards a draft when tenant/principal changes. Scope caches carefully on login/logout, and cancel/clear sensitive queries before switching session when needed. In server rendering, do not share a single mutable QueryClient across unrelated requests. The server and client cache each have their own identity and hydration responsibilities.

### Freshness, retention and cancellation are different policies

`staleTime` describes how long cached data is considered fresh; it is not a deletion deadline. `gcTime` governs retention after a query becomes inactive. Invalidating a key marks eligible queries stale and normally refetches active matches; it does not synchronously make every inactive consumer current. Forwarding the supplied signal lets supported query cancellation reach fetch. [Cancellation contract](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation).

Reads and mutations also need explicit retry policies. The example disables automatic retries to make every attempt visible; a production read may retry selected transient failures with a budget. Retrying a mutation after an uncertain response requires its server-side operation/version/idempotency contract, not just a client callback.

### When does optimistic cache rollback become unsafe?

A common cache strategy is cancel a matching read, snapshot its previous value, apply a patch, then restore the snapshot on rejection and invalidate after settlement. This works only with an adequate ownership/concurrency policy. If mutation A restores its old snapshot after mutation B's patch, it can erase B's visible update.

An independent UI overlay as above avoids changing confirmed cache state. Shared optimistic caches can instead retain patches by operation ID, reconcile against authoritative versions, or deliberately serialize all relevant mutation ownership. A network serialization scope alone does not prove every optimistic onMutate/cache patch is serialized. The library describes [UI and cache approaches](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates); the application's conflict policy remains necessary.

## Real-World Use Cases

- **Auth/session + theme + feature flags** — server state or context (rarely changes; wide reads); the canonical Context use case (→ 10.3.2.05).
- **Multi-step forms with cross-field validation** — local state per step + one form library store; lifting everything global makes every keystroke a store event.
- **Real-time collaborative views** — external store via `useSyncExternalStore` (→ 10.3.3.04) so websocket snapshots don't fight React's renderer.
- **Server-data-heavy apps** — React Query/SWR own the server cache; Redux/Zustand own only true client state. Redux can still coordinate client actions and middleware; server caches solve a different lifecycle.

## Common Mistakes

1. **Putting everything in global state**: Broad subscriptions can rerender on unrelated writes, so a modal's `open` flag kept globally redraws the whole tree that reads it. Keep state at the lowest common ancestor that needs it — lift only when a sibling actually appears.

2. **Not normalizing state**: Nested copies force you to rebuild every ancestor path to update one entity, and the same entity stored in two places goes stale in one of them. A flat `{ byId, allIds }` shape makes an update a single-key replace with one source of truth.

3. **Using Context for complex state**: Context has no selectors — changing the provider's value re-renders *every* consumer regardless of which slice it reads — and it ships no middleware, devtools, or time-travel. Use narrower providers or selector-based subscriptions when those broad notifications are a measured cost. Context can transport a reducer with complex logic; complexity alone does not require another library.

4. **Not handling loading/error states**: An async value read during render before it settles either crashes on `undefined` or flashes stale data. Every fetch surface needs pending/error branches (or Suspense + an error boundary) so failure is a state the UI displays, not an unhandled exception.

5. **Over-fetching**: Refetching on every mount, focus, or keystroke multiplies latency and backend load. A query cache with a staleness window and invalidation (React Query) serves cached data immediately and revalidates in the background.

## Best Practices

1. **Start with local state**: Use useState for component-specific data

2. **Lift state when needed**: Move state to common ancestor for siblings

3. **Use Context for global data**: Theme, auth, language

4. **Choose external stores by their needed contract**: Selected subscriptions, action tooling and middleware can justify a store; complex transitions alone can use a local reducer

5. **Use React Query for server state**: Caching, background refetching

6. **Normalize state**: Flat structures for efficient updates

7. **Colocate state**: Keep state near where it's used

## Summary

State management ranges from local useState to global Redux/Zustand and server state React Query. Choose by ownership, subscription and lifecycle: local drafts stay local, Context transports provider values, external stores coordinate selected client state, and a server-state cache manages remote copies. None of these replaces runtime validation or server authorization.

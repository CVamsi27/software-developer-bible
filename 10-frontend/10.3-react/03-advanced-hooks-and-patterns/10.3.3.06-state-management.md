# State Management

When a user edits a server-backed profile, the typed name is not yet the saved name. A list may show the last confirmed server value while the editor keeps a local draft. The design starts by deciding which copy owns each transition.

## Definition

**State management** defines where application values live, who can change them, how readers are notified and how long the values remain valid. A local draft, a shared client preference, a remote record and a URL filter may all be strings, but they have different owners and recovery rules.

> **Textbook Definition:** State management defines the ownership, lifetime and transition rules for application data. Local UI state, shared client state and remotely authoritative state require different synchronization, invalidation and recovery policies.

## First Principles

Each value needs one authoritative owner, a defined lifetime and a clear update path to its readers. Context describes how a value flows through a subtree; `useSyncExternalStore` describes how React subscribes to a separate source. A remote cache still needs freshness and conflict rules because the server can change outside the component.

## Trace one editable server record

One name can appear in four places, each with a different owner:

```text
server record → query cache → rendered view
                                ↓ edit opens
                            local draft
                                ↓ validated mutation
server accepts/rejects ← request with record version
        ↓ accepted
confirmed response → cache update → targeted revalidation
```

## Choose an owner before choosing a library

| Need | Starting point | Boundary to keep clear |
| -------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------ |
| One component owns a draft or open state | `useState` / `useReducer` | Separate Hook calls do not share state; unmounting ends local lifetime |
| Siblings need the same value | Lift state to their common owner | Props and callbacks carry that owner's updates |
| Descendants need a scoped value | Context plus state/reducer in its owner | Context transports a value; it does not own transitions or select fields |
| Distant readers need selected client state | Zustand, Redux or an atom store | Subscription and action/tooling contracts differ by library |
| React reads a mutable external source | `useSyncExternalStore` or a library adapter | The source needs a stable snapshot and a subscription cleanup contract |
| Remote records need request/freshness coordination | TanStack Query, RTK Query or SWR | The remote service remains authoritative |
| Filters should be shareable or follow Back/Forward | Router URL state | Parse and validate search parameters |

Context can carry reducer state; complex transitions alone do not require an external store. Redux Toolkit fits explicit actions and middleware; Zustand offers selector-based stores; Jotai composes state from atoms. If a Redux app also needs a remote-data cache, RTK Query can own that lifecycle. Avoid keeping the same server collection as independently writable data in both RTK Query and another cache.

## Code Examples

### Zustand: Select the Values a Component Reads

Each component selects the values it reads. Zustand compares a selector's result with `Object.is` by default, so selecting a primitive field suppresses store-triggered updates when unrelated fields change. Parent or local-state updates can still render the component. In Zustand v5, a selector that creates a new object on every evaluation can trigger a maximum-update-depth loop. Use separate selectors or wrap an aggregate selector with `useShallow`; shallow comparison checks only the returned value's top-level fields.

```typescript
import { create } from 'zustand';
import { useShallow } from 'zustand/react/shallow';

interface WorkspaceState {
  sidebarOpen: boolean;
  activePanel: 'editor' | 'preview' | 'terminal';
  zoomLevel: number;
  toggleSidebar: () => void;
  setActivePanel: (panel: 'editor' | 'preview' | 'terminal') => void;
  setZoomLevel: (zoom: number) => void;
}

export const useWorkspaceStore = create<WorkspaceState>((set) => ({
  sidebarOpen: true,
  activePanel: 'editor',
  zoomLevel: 100,
  toggleSidebar: () => set((state) => ({ sidebarOpen: !state.sidebarOpen })),
  setActivePanel: (activePanel) => set({ activePanel }),
  setZoomLevel: (zoomLevel) => set({ zoomLevel }),
}));

// Store-triggered renders follow this selected boolean; parent renders still apply.
export function SidebarToggle() {
  const sidebarOpen = useWorkspaceStore((state) => state.sidebarOpen);
  const toggleSidebar = useWorkspaceStore((state) => state.toggleSidebar);

  return (
    <button onClick={toggleSidebar} aria-expanded={sidebarOpen}>
      {sidebarOpen ? 'Collapse' : 'Expand'}
    </button>
  );
}

// useShallow reuses the previous result while these top-level values are equal.
export function StatusBar() {
  const { activePanel, zoomLevel } = useWorkspaceStore(
    useShallow((state) => ({
      activePanel: state.activePanel,
      zoomLevel: state.zoomLevel,
    }))
  );

  return (
    <footer>
      <span>Panel: {activePanel}</span>
      <span>Zoom: {zoomLevel}%</span>
    </footer>
  );
}
```

### Context API as Transport vs. External Store

Context identifies a value to provide through a subtree; the provider or another owner supplies and updates that value. When the provider's value changes by `Object.is`, components that read that context receive the new value and re-render. `memo` does not block a context update. Split contexts when independent values change separately, or use selector-based subscriptions if profiling shows broad context updates are costly.

> [Context API — giving a subtree a value](../02-core-hooks/10.3.2.05-context-api.md#give-the-subtree-a-value) details provider lookup and value ownership. Use Context for scoped values such as theme or the client session shell; use a selector-based store when consumers need different slices of frequently changing client state.

### URL State for Shareable Navigation

Put navigation choices in the URL when users should be able to bookmark or share them, refresh without losing them, or revisit them with Back and Forward. Parse values at the boundary: URLs can be edited or stale, so do not assume a parameter is valid just because the UI wrote it before.

```tsx
import { useSearchParams } from 'react-router-dom';

export function ProductFilter() {
  const [searchParams, setSearchParams] = useSearchParams();

  const categories = ['all', 'electronics', 'books'] as const;
  type Category = typeof categories[number];
  const isCategory = (value: string | null): value is Category =>
    value !== null && (categories as readonly string[]).includes(value);
  const requestedCategory = searchParams.get('category');
  const currentCategory = isCategory(requestedCategory)
    ? requestedCategory
    : 'all';

  const updateCategory = (category: Category) => {
    setSearchParams((prev) => {
      const next = new URLSearchParams(prev);
      if (category === 'all') {
        next.delete('category');
      } else {
        next.set('category', category);
      }
      next.set('page', '1'); // Reset pagination on filter change
      return next;
    });
  };

  return (
    <div>
      <label htmlFor="product-category">Category</label>
      <select id="product-category" value={currentCategory} onChange={(event) => {
        const value = event.currentTarget.value;
        updateCategory(isCategory(value) ? value : 'all');
      }}>
        <option value="all">All Categories</option>
        <option value="electronics">Electronics</option>
        <option value="books">Books</option>
      </select>
    </div>
  );
}
```

### Redux Toolkit

Immer permits draft mutation inside a reducer while producing an immutable result. ID creation belongs in action preparation, outside the reducer, so replaying an action remains deterministic.

```typescript
import { createSlice, configureStore, type PayloadAction } from '@reduxjs/toolkit';

type Todo = { id: string; text: string; completed: boolean };

export const todosSlice = createSlice({
  name: 'todos',
  initialState: [] as Todo[],
  reducers: {
    addTodo: {
      reducer: (state, action: PayloadAction<Todo>) => { state.push(action.payload); },
      prepare: (text: string) => ({ payload: { id: crypto.randomUUID(), text, completed: false } }),
    },
    toggleTodo: (state, action: PayloadAction<string>) => {
      const todo = state.find((t) => t.id === action.payload);
      if (todo) todo.completed = !todo.completed;
    },
  },
});

export const store = configureStore({ reducer: { todos: todosSlice.reducer } });
```

An array is sufficient for this small list. When a client-owned collection has many relationships or components update individual records, normalize it as an ID-keyed table plus an ordered ID list. Redux Toolkit's `createEntityAdapter` supplies that shape and common reducers/selectors. Do not normalize a remote cache just to mirror server data into a second owner.

### How TanStack Query coordinates the remote copy

The following React module targets **TanStack Query v5 and Zod v4** in a browser SPA. Assume a same-origin, cookie-authenticated API with CSRF protection: `GET /api/tenants/:tenant/users` returns User[], and `PATCH /api/tenants/:tenant/users/:id` returns the accepted User. The backend must verify tenant access, validate the desired name, and atomically enforce `If-Match` against the record version (409/412 on conflict). The cache key uses a non-sensitive account ID to partition client data; query keys do not provide server authorization.

```tsx
import { useRef, useState, type FormEvent } from 'react';
import { QueryClient, QueryClientProvider, useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import { z } from 'zod';

const UserSchema = z.object({
  id: z.string().min(1), name: z.string().min(1), version: z.number().int().nonnegative()
});
type User = z.infer<typeof UserSchema>;
type Edit = { id: string; name: string; version: number };
class ApiError extends Error {
  constructor(readonly status: number, message: string) { super(message); }
}
const NameSchema = z.string().trim().min(1).max(100);
const usersKey = (tenant: string, accountId: string) => ['users', tenant, accountId] as const;
const usersPath = (tenant: string) => `/api/tenants/${encodeURIComponent(tenant)}/users`;

async function readUsers(tenant: string, signal: AbortSignal): Promise<User[]> {
  const response = await fetch(usersPath(tenant), { signal });
  if (!response.ok) throw new Error(`Read failed: ${response.status}`);
  return z.array(UserSchema).parse(await response.json());
}
async function renameUser(tenant: string, edit: Edit): Promise<User> {
  const response = await fetch(`${usersPath(tenant)}/${encodeURIComponent(edit.id)}`, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json', 'If-Match': `"${edit.version}"` },
    body: JSON.stringify({ name: edit.name })
  });
  if (!response.ok) throw new ApiError(response.status, `Save failed: ${response.status}`);
  const saved = UserSchema.parse(await response.json());
  if (saved.id !== edit.id) throw new TypeError('Unexpected saved identity');
  return saved;
}

function Users({ tenant, accountId }: { tenant: string; accountId: string }) {
  const client = useQueryClient();
  const key = usersKey(tenant, accountId);
  const [editing, setEditing] = useState<User | null>(null);
  const [draft, setDraft] = useState('');
  const [inputError, setInputError] = useState('');
  const submitting = useRef(false);
  const query = useQuery({
    queryKey: key,
    queryFn: ({ signal }) => readUsers(tenant, signal),
    staleTime: 30_000,
    retry: false
  });
  const save = useMutation({
    mutationFn: (edit: Edit) => renameUser(tenant, edit),
    retry: false,
    onSuccess: async saved => {
      await client.cancelQueries({ queryKey: key, exact: true });
      client.setQueryData<User[]>(key, previous =>
        previous?.map(user => user.id === saved.id ? saved : user)
      );
      setEditing(null);
      await client.invalidateQueries({ queryKey: key, exact: true });
    },
    onError: async error => {
      if (error instanceof ApiError && (error.status === 409 || error.status === 412)) {
        await client.invalidateQueries({ queryKey: key, exact: true });
      }
    }
  });
  const latestEditing = editing && query.data?.find(user => user.id === editing.id);
  const versionConflict = save.error instanceof ApiError &&
    (save.error.status === 409 || save.error.status === 412);

  async function submit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (!editing || submitting.current) return;
    const parsed = NameSchema.safeParse(draft);
    if (!parsed.success) { setInputError('Enter a name from 1 to 100 characters.'); return; }
    setInputError('');
    submitting.current = true;
    try { await save.mutateAsync({ id: editing.id, name: parsed.data, version: editing.version }); }
    catch { /* save.error supplies the visible failure; keep the draft */ }
    finally { submitting.current = false; }
  }

  if (query.isPending) return <p role="status">Loading users…</p>;
  if (!query.data) return <section>
    {query.isError && <p role="alert">Users could not be loaded.</p>}
    <button type="button" onClick={() => void query.refetch()}>Retry loading users</button>
  </section>;
  return (
    <section>
      {query.isFetching && <p role="status">Refreshing users…</p>}
      {query.isError && <div>
        <p role="alert">Refresh failed; showing the previously loaded list.</p>
        <button type="button" onClick={() => void query.refetch()}>Retry refresh</button>
      </div>}
      <ul>{query.data.map(user => <li key={user.id}>
        {save.isPending && save.variables?.id === user.id ? `${save.variables.name} (saving…)` : user.name}
        <button type="button" disabled={save.isPending} onClick={() => {
          save.reset(); setEditing(user); setDraft(user.name); setInputError('');
        }}>Edit {user.name}</button>
      </li>)}</ul>
      {editing && <form onSubmit={submit}>
        <label htmlFor="user-name">Name</label>
        <input id="user-name" name="name" autoComplete="name" maxLength={100}
          aria-invalid={inputError ? true : undefined}
          aria-describedby={inputError ? 'user-name-error' : undefined}
          value={draft} disabled={save.isPending}
          onChange={event => { setDraft(event.target.value); setInputError(''); }} />
        <button type="submit" disabled={save.isPending}>Save</button>
        {inputError && <p id="user-name-error" role="alert">{inputError}</p>}
        {save.isError && <p role="alert">Save failed. Your draft is still here; review the server record or retry.</p>}
        {versionConflict && latestEditing && latestEditing.version !== editing.version && <div>
          <p role="status">The server now has “{latestEditing.name}” at version {latestEditing.version}. Your draft remains in the form.</p>
          <button type="button" onClick={() => { setEditing(latestEditing); save.reset(); }}>
            Keep my draft and retry against the latest version
          </button>
        </div>}
        {versionConflict && !latestEditing && <p role="status">This record no longer exists. Copy the draft before closing the editor.</p>}
        <button type="button" disabled={save.isPending} onClick={() => { setEditing(null); save.reset(); }}>Cancel</button>
      </form>}
    </section>
  );
}

export function UsersApp({ tenant, accountId }: { tenant: string; accountId: string }) {
  const [client] = useState(() => new QueryClient());
  return <QueryClientProvider client={client}>
    <Users key={JSON.stringify([tenant, accountId])} tenant={tenant} accountId={accountId} />
  </QueryClientProvider>;
}
```

1. The key scopes cached data to the tenant and account; add every filter or input that changes the response. The query supplies a signal to fetch and validates the response. Never put credentials or sensitive personal data in a query key.
2. Opening the editor copies an identified version into a local draft. Editing does not mutate the cached record.
3. During the request, the row shows the proposed name from mutation variables. This is a temporary **UI overlay**, not an optimistic cache write.
4. On success, the accepted version enters the cache and matching active queries revalidate. A 409/412 conflict refreshes the list and exposes the current server name/version; the user can explicitly keep the draft and retry against that version. Other failures retain the draft without changing the cache.

The component assumes one editor entry point for this list. A ref closes the same-component double-submit gap before React paints its pending state; it does not serialize another tab, another component or server writers. The server's version check resolves those conflicts. The API returns a desired name update, rather than a non-idempotent 'toggle' operation.

A keyed remount discards a draft when tenant/account changes. Clear sensitive cached data on logout or account switch, especially when cache persistence is enabled. In server rendering, create a separate mutable QueryClient per request; the server and browser caches have separate identities and hydration responsibilities.

### Freshness, retention and cancellation are different policies

`staleTime` describes how long cached data is considered fresh; it is not a deletion deadline. `gcTime` governs retention after a query becomes inactive. Invalidating a key marks eligible queries stale and normally refetches active matches; it does not synchronously make every inactive consumer current. Forwarding the supplied signal lets supported query cancellation reach fetch. [Cancellation contract](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation).

Reads and mutations also need explicit retry policies. The example disables automatic retries to make every attempt visible; a production read may retry selected transient failures with a budget. Retrying a mutation after an uncertain response requires its server-side operation/version/idempotency contract, not just a client callback.

### When does optimistic cache rollback become unsafe?

A common cache strategy is cancel a matching read, snapshot its previous value, apply a patch, then restore the snapshot on rejection and invalidate after settlement. This works only with an adequate ownership/concurrency policy. If mutation A restores its old snapshot after mutation B's patch, it can erase B's visible update.

An independent UI overlay as above avoids changing confirmed cache state. Shared optimistic caches can instead retain patches by operation ID, reconcile against authoritative versions, or deliberately serialize all relevant mutation ownership. TanStack Query can queue mutations with the same `scope.id`, but that does not coordinate other tabs, clients or server writers, and it does not choose a safe rollback policy for the application. The library describes [UI and cache approaches](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates); the application's conflict policy remains necessary.

## Summary

Choose state by its owner and lifetime. Keep drafts local, lift values only to components that share them, use Context for scoped provider values, and use an external store when selected client subscriptions or action tooling solve a real need. Give remote data one cache owner with explicit freshness and conflict policies; put navigation choices in validated URL parameters when they should survive sharing and browser history. None of these replaces runtime validation or server authorization.

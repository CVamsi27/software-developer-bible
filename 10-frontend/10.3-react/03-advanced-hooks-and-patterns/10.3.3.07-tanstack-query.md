# TanStack Query: Server State Ownership

A profile editor contains an unsaved name when a background request returns an older server record. Replacing the input with that response loses the user's work. Keep the draft local and the fetched record in a server-state cache; only a confirmed write changes what the server has accepted.

## Definition

**TanStack Query** fetches, caches and coordinates asynchronous server state. A query key identifies one query result, and observers subscribe to that result's fetching, error and freshness state. A mutation represents a write; its callbacks let the application reconcile successful or failed writes with cached reads.

> **Textbook Definition:** A server-state cache stores local copies of externally owned data and coordinates fetching, freshness and invalidation. TanStack Query indexes query results by keys; it does not automatically normalize shared entities across different query results.

## First Principles

The browser cannot know every change another client makes on the server. A cached response is therefore an observation, not permanent truth. Its owner needs an identity, an age policy and events that trigger another observation. A local form draft has a different owner: its changes should survive a background read until the user submits, cancels or resolves a conflict.

The cache removes repeated request bookkeeping. It cannot decide authorization, conflicting edits or whether a timed-out write committed. Those decisions belong to the API contract and the interface that uses it.

## 1. Keys separate resources and identities

Components using the same key in one QueryClient share the query and its in-flight fetch. A list key and a detail key hold separate results, even if both contain the same user. Updating one does not automatically update the other.

Include every input that changes the fetched result: tenant, resource ID, filters and page cursor. Keep the query function consistent with that key. A key such as `['user', id]` is unsafe to reuse across tenant changes when IDs or response visibility differ. Keys organize browser state; the server must still authorize each request. Clear or replace identity-scoped caches on sign-out/account changes.

## 2. Freshness permits refetching; it is not a polling timer

`staleTime` controls how long cached data is considered fresh. Expiry makes it stale; expiry alone does not start a request. With the default policies, stale queries can refetch when an observer mounts, the window regains focus or the network reconnects. A separate `refetchInterval` enables polling.

`gcTime` governs inactive queries after their observers are gone. It is independent of freshness. A stale result can still be present and displayed during a background fetch. Distinguish an initial pending view from an existing-data refresh so a routine refetch does not blank a usable page.

Query retries and mutation retries are configurable separately. Client queries retry failures by default; server query retries default to zero, and mutations default to no retry. Decide which failures are retryable: an authorization rejection differs from a transient connection failure. A write needs an idempotency/reconciliation contract before automatic retry is safe.

## 3. Save a draft, then reconcile the confirmed record

This hook keeps the server copy in the cache. Its caller owns a separate name draft and displays mutation errors. It assumes a mounted QueryClientProvider and an API that returns the saved record or a non-success HTTP status:

```tsx
import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';

type User = { id: string; name: string };

export function useProfile(tenantId: string, userId: string) {
  const client = useQueryClient();
  const key = ['tenant', tenantId, 'user', userId] as const;
  const url = `/api/tenants/${encodeURIComponent(tenantId)}/users/${encodeURIComponent(userId)}`;
  const query = useQuery({
    queryKey: key,
    queryFn: async ({ signal }): Promise<User> => {
      const response = await fetch(url, { signal });
      if (!response.ok) throw new Error(`Read failed: ${response.status}`);
      return response.json(); // Validate an unknown response at the API boundary.
    },
    staleTime: 60_000,
  });
  const save = useMutation({
    mutationFn: async (name: string): Promise<User> => {
      const response = await fetch(url, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ name }),
      });
      if (!response.ok) throw new Error(`Save failed: ${response.status}`);
      return response.json();
    },
    retry: false,
    // Prevent an older in-flight read from replacing the confirmed response.
    onMutate: () => client.cancelQueries({ queryKey: key, exact: true }),
    onSuccess: (saved) => { client.setQueryData(key, saved); },
    onSettled: () => client.invalidateQueries({ queryKey: key, exact: true }),
  });
  return { query, save };
}
```

The GET consumes the cancellation signal. Canceling that read does not undo a write on the server. `fetch` also resolves on HTTP error statuses, so the explicit status checks matter. The typed JSON return is an example boundary, not runtime validation; a production client should parse unknown data with its shared response schema.

The caller disables its submit action while pending and preserves the draft if the write fails. Returning the invalidation Promise keeps mutation completion waiting for active matching reads to reconcile. Inactive queries are marked invalid without being fetched by default. Invalidation itself can fail to refresh; decide whether the interface may show the confirmed response with a refresh warning.

For two writers, add a server revision/ETag conflict contract where required. A local disabled button cannot prevent another component, tab or user from writing. Do not let a slower earlier response overwrite a newer confirmed version: serialize edits or reconcile by the server's version semantics.

## 4. Optimism adds a rollback ownership problem

When immediate feedback is worth the complexity, `onMutate` can cancel an interfering read, snapshot the previous cache value and apply an optimistic change. `onError` can use that snapshot; `onSettled` can reconcile after success or failure. These callbacks do nothing until the application implements them; there is no automatic rollback.

A whole-snapshot rollback is safe only within a defined write-ownership boundary. If edit A fails after edit B's optimistic update, restoring A's snapshot can erase B. Options include one outstanding edit per entity, pending variables rendered beside confirmed data, or a versioned patch/rebase strategy. Server idempotency and conflict detection remain necessary independently of the UI technique.

## 5. Server rendering needs request-scoped state and safe transport

Use a request-scoped QueryClient on the server so one visitor's data cannot leak to another. Prefetch authorized data, call `dehydrate`, and restore it using `HydrationBoundary` in React or the core `hydrate` API. Use matching key identities; choose a client freshness policy that avoids an unnecessary immediate refetch when appropriate.

`dehydrate` produces a state object; it does not automatically turn arbitrary data into an HTML-safe string. Use the framework's supported serialization/escaping boundary. Raw JSON interpolated into a script can expose an injection boundary, and unsupported values need an explicit encoding policy. A stale-time difference can cause refetching; it does not by itself prove a React markup hydration mismatch.

## 6. Test the behavior at each boundary

Use an isolated QueryClient per test, deterministic fake responses and explicit retry settings. Check shared-key request counts, separate tenant keys, stale expiry without polling, and active versus inactive invalidation. For mutation tests, control promise completion order and reject one of two writes; assert the final visible record and retained draft.

A cache test does not prove API authorization or database concurrency. Test those through their own real boundaries. For the rendered editor, check pending/error feedback, keyboard operation, preserved unsaved input and the conflict path. Disable or clear long-lived cache timers in tests so the process can finish.

## Summary

Query keys identify cached results, while the server owns persisted records and the form owns its draft. Staleness permits event-driven refetching; garbage collection and polling are separate policies. Writes need explicit reconciliation, concurrent optimism needs an ownership rule, and server rendering needs request isolation and safe serialization.

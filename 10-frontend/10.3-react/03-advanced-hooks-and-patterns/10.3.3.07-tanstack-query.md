# TanStack Query: Server State Ownership

When a user edits a draft profile and the page refreshes, which name wins — the draft in the input or the record on the server? Server state (records fetched from an API) and client state (local drafts) follow different rules, and mixing them without an owner is how optimistic updates silently clobber confirmed data. TanStack Query owns server state: one normalized cache, background refresh, and an explicit mutation lifecycle.

```tsx
const { data: user, isPending, error } = useQuery({
  queryKey: ['user', profileId],
  queryFn: () => fetchUser(profileId),
  staleTime: 5 * 60 * 1000,
});
```

## Definition

**TanStack Query** (formerly React Query) is a server-state management library: it fetches, caches, synchronizes and updates server records without treating them like local UI state. A **query** declares a key and an async fetcher; the library deduplicates identical keys across components, serves cached data immediately, and refetches in the background when the data goes stale. A **mutation** declares how a write changes server state, with explicit success, error and rollback callbacks.

> **Textbook Definition:** TanStack Query maintains a normalized key→value cache of asynchronous server records, serves stale-while-revalidate reads, deduplicates concurrent fetches for the same key, and drives mutations through declared success/error callbacks with cache invalidation as a side effect.

## First Principles

Server state is not owned by the frontend: it can change without the app knowing, it must be fetched asynchronously, and a successful UI draft is not confirmed until the server accepts it. Client state (form drafts, toggles) is owned locally. TanStack Query forces an ownership decision at every read: is this value a cached server record or a local draft? Mixing them makes background refreshes overwrite unconfirmed edits.

## 1. Query keys own the cache (one record per key)

Every read starts with a cache key and ends with a decision about who owns the value:

Every query registers under a serializable key such as `['user', profileId]`. Components requesting the same key share one cached record and one in-flight fetch — concurrent requests dedupe into a single network call. The key is the cache identity: change the key shape and you get a separate, independently cached record.

```tsx
// Same key → shared cache, one fetch
useQuery({ queryKey: ['user', id], queryFn: () => fetchUser(id) });
// Different key → separate record
useQuery({ queryKey: ['user', id, 'detail'], queryFn: () => fetchUserDetail(id) });
```

## 2. Stale-while-revalidate: serve cache, refresh in background

On mount, TanStack Query returns cached data immediately if present, then marks it stale after `staleTime` and refetches in the background. `gcTime` (formerly `cacheTime`) decides how long an unused record stays in memory before garbage collection. A component that unmounts before refresh completes does not lose the record; it stays for `gcTime`.

## 3. Request collapsing and retries

Multiple components mounting at once with the same key trigger one fetch, not N. Failed queries retry with exponential backoff up to `retry` attempts (default 3), then surface `error` to the consuming component. Retries apply to reads only; writes go through mutations with their own retry contract.

## 4. Mutations write through to the server

A mutation declares a `mutationFn` plus lifecycle callbacks: `onMutate` (capture the previous value for rollback), `onSuccess` (update the cache and invalidate related queries), `onError` (roll back), and `onSettle` (always refetch related keys). Optimistic updates apply `onMutate` immediately to the UI while the request is in flight; if the server rejects, `onError` restores the snapshot.

```tsx
const mutation = useMutation({
  mutationFn: updateUser,
  onMutate: (newUser) => { /* snapshot previous, set optimistic UI */ },
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['user'] }),
  onError: (err, newUser, context) => { /* restore context.previousUser */ },
});
```

## 5. SSR and hydration: dehydrate/rehydrate

On the server, `dehydrate()` serializes the query cache into HTML-safe state; on the client, `rehydrate()` restores it so the first render matches the server output without a waterfall. Mismatched cache keys or missing `staleTime` between server and client cause hydration warnings or duplicate fetches.

## 6. Testing server state without the server

Unit tests drive queries and mutations against a fake fetcher (or a network-mocking layer such as MSW). Assert that identical keys dedupe, that `onError` restores the rolled-back value, and that `invalidateQueries` triggers a refetch — without waiting on real network timing.

## Summary

TanStack Query owns server state through one normalized key→value cache: reads are stale-while-revalidate with background refetch, concurrent keys dedupe into one fetch, retries back off exponentially, and mutations write through with explicit rollback and invalidation. Client drafts stay local; the server record is authoritative only after a mutation succeeds and the related queries are invalidated.

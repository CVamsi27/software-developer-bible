# TanStack Query: Server State Ownership

A profile editor contains an unsaved name when a background request returns an older server record. Replacing the input with that response loses the user's work. Keep the draft local and the fetched record in a server-state cache; only a confirmed write changes what the server has accepted.

## Definition

**TanStack Query** fetches, caches and coordinates asynchronous server state. A query key identifies one query result, and observers subscribe to that result's fetching, error and freshness state. A mutation represents a write; its callbacks let the application reconcile successful or failed writes with cached reads.

> **Textbook Definition:** A server-state cache stores local copies of externally owned data and coordinates fetching, freshness and invalidation. TanStack Query indexes query results by keys; it does not automatically normalize shared entities across different query results.

## First Principles

The browser cannot know every change another client makes on the server. A cached response is therefore an observation, not permanent truth. Its owner needs an identity, an age policy and events that trigger another observation. A local form draft has a different owner: its changes should survive a background read until the user submits, cancels or resolves a conflict.

The cache removes repeated request bookkeeping. It cannot decide authorization, conflicting edits or whether a timed-out write committed. Those decisions belong to the API contract and the interface that uses it.

## 1. Keys separate resources and identities

Components using the same key in one `QueryClient` share the query and its in-flight fetch. A list key and a detail key hold separate results even when both contain the same user, so updating one does not automatically update the other.

Include every input that changes the fetched result — tenant, resource ID, filters, and page cursor — and keep the query function consistent with that key. A key such as `['user', id]` is unsafe to reuse across tenant switches when IDs or visibility differ.

Keys organize browser cache state; the server must still authorize every request. Clear or replace identity-scoped caches on sign-out or account switches.

## 2. Freshness permits refetching; it is not a polling timer

`staleTime` controls how long cached data is considered fresh. Expiry makes it stale; expiry alone does not start a request. With the default policies, stale queries can refetch when an observer mounts, the window regains focus or the network reconnects. A separate `refetchInterval` enables polling.

`gcTime` governs inactive queries after their observers are gone. It is independent of freshness. A stale result can still be present and displayed during a background fetch. Distinguish an initial pending view from an existing-data refresh so a routine refetch does not blank a usable page.

Query retries and mutation retries are configurable separately. Client queries retry failures by default; server query retries default to zero, and mutations default to no retry.

Decide which failures are retryable, because an authorization rejection differs from a transient network drop. Any write needs an idempotency and reconciliation contract before automatic retries are safe.

## 3. Save a draft, then reconcile the confirmed record

This hook keeps the server copy in the cache while its caller owns a separate name draft and displays mutation errors. It assumes a mounted `QueryClientProvider` and an API that returns the saved record or a non-success HTTP status:

```tsx
import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';

type User = { id: string; name: string };

export function useProfile(tenantId: string, userId: string) {
  const client = useQueryClient();
  const key = ['tenant', tenantId, 'user', userId] as const;
  const url = `/api/tenants/${encodeURIComponent(tenantId)}/users/${encodeURIComponent(userId)}`;
  const query = useQuery({
    queryKey: key,
    queryFn: async ({ signal }): Promise<User> => {
      const response = await fetch(url, { signal });
      if (!response.ok) throw new Error(`Read failed: ${response.status}`);
      return response.json(); // Validate an unknown response at the API boundary.
    },
    staleTime: 60_000,
  });
  const save = useMutation({
    mutationFn: async (name: string): Promise<User> => {
      const response = await fetch(url, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ name }),
      });
      if (!response.ok) throw new Error(`Save failed: ${response.status}`);
      return response.json();
    },
    retry: false,
    // Prevent an older in-flight read from replacing the confirmed response.
    onMutate: () => client.cancelQueries({ queryKey: key, exact: true }),
    onSuccess: (saved) => { client.setQueryData(key, saved); },
    onSettled: () => client.invalidateQueries({ queryKey: key, exact: true }),
  });
  return { query, save };
}
```

The `GET` consumes the cancellation signal, though canceling a read never undoes a write on the server. Because `fetch` also resolves on HTTP error statuses, explicit `response.ok` checks matter. The typed JSON return is a TypeScript boundary only, not runtime validation; parse untrusted payloads with a shared schema at the API boundary.

The caller disables submit while pending and keeps the draft intact if the write fails. Returning the invalidation `Promise` keeps mutation completion waiting until active matching reads reconcile, whereas inactive queries are only marked invalid. Decide upfront whether a failed refetch shows the confirmed mutation response with a warning.

For concurrent writers, enforce a server revision or `ETag` conflict contract. A local disabled button cannot block another component, tab, or user from writing, so serialize edits or reconcile via server versions so slower responses never overwrite newer ones.

## 4. Optimism adds a rollback ownership problem

When immediate feedback is worth the complexity, `onMutate` can cancel an interfering read, snapshot the previous cache value and apply an optimistic change. `onError` can use that snapshot; `onSettled` can reconcile after success or failure. These callbacks do nothing until the application implements them; there is no automatic rollback.

A whole-snapshot rollback is safe only within a defined write-ownership boundary. If edit A fails after edit B's optimistic update, restoring A's snapshot can erase B.

Options include limiting to one outstanding edit per entity, rendering pending variables beside confirmed data, or applying versioned patches/rebases. Server idempotency and conflict detection remain essential regardless of the UI pattern.

## 5. Server rendering needs request-scoped state and safe transport

Use a request-scoped `QueryClient` on the server so one visitor's data cannot leak to another. Prefetch authorized data, call `dehydrate`, and restore it with `HydrationBoundary` in React (or core `hydrate`) using matching key identities and a client `staleTime` that avoids unnecessary immediate refetches.

`dehydrate` produces a state object, not an automatic HTML-safe string. Use the framework's supported escaping and transport boundary — raw JSON interpolated into an inline `<script>` risks injection, and non-JSON values require an explicit encoding policy. A `staleTime` difference triggers refetches, not a React markup hydration mismatch by itself.

## 6. Test the behavior at each boundary

Use an isolated `QueryClient` per test, deterministic fake responses, and explicit retry settings. Verify shared-key request counts, separate tenant keys, stale expiry without polling, and active vs. inactive invalidation. For mutations, control completion order and reject one of two writes to assert the final confirmed record and preserved draft.

A cache test does not prove API authorization or database concurrency; test those through their own real boundaries. For the rendered editor, verify pending and error feedback, keyboard flow, preserved unsaved input, and conflicts — and clear or disable long-lived cache timers so the test runner exits cleanly.

## Summary

Query keys identify cached results, while the server owns persisted records and the form owns its draft. Staleness permits event-driven refetching; garbage collection and polling are separate policies. Writes need explicit reconciliation, concurrent optimism needs an ownership rule, and server rendering needs request isolation and safe serialization.

# Modern React Hooks: useTransition, useDeferredValue, use, useOptimistic, and React 19 APIs

## Definition

React 18 introduced transition and deferred-value Hooks for scheduling eligible rendering. React 19 added Actions, optimistic overlays and resource reading APIs. Each addresses a different gap between user intent, pending work and confirmed UI; they are not a general speed switch.


## First Principles

1. **Input feedback and its derived results have different deadlines.** The controlled input must reflect the latest typed value promptly; expensive results can lag. Transitions mark the state driving those results, while a deferred value lets a consumer prepare a later version without controlling the producer.
2. **A pending resource cannot supply a finished render value.** `use` reads a stable resource and lets React retry a suspended region when it is ready. A new promise created by each abandoned render does not provide stable ownership, so loaders, caches or server parents must own it.
3. **A proposed mutation and a confirmed value are different states.** An optimistic overlay displays the proposal only while its Action is pending. When the Action completes, the latest confirmed base becomes authoritative; persistence must update that base, and failure needs an appropriate error path. React 19 Actions coordinate this lifetime but do not order arbitrary overlapping requests.

## Follow one interaction through its pending states

A user types a search, opens a result and saves a change. The input must update immediately, the results may lag, a pending resource needs a fallback, and a save needs visible feedback until the server confirms it. Choose the primitive for that specific interval:

| Interval | Primitive | Owner's remaining responsibility |
| --------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------- |
| Urgent input versus expensive result rendering | Transition or deferred value | Reduce indivisible CPU work and keep the input urgent |
| A stable promise has not fulfilled | `use` with Suspense | Own/cache the resource and provide error recovery |
| A proposed write is awaiting confirmation | `useOptimistic` inside an Action | Persist, update the confirmed base and order conflicting writes |
| A form Action is pending or returns expected errors | `useActionState` / `useFormStatus` | Validate, authorize and present success/error outcomes |

## How It Works

### useTransition — Mark Updates as Non-Urgent

```typescript
import { useTransition, useState, useRef, type ChangeEvent } from 'react';

function SearchPage() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<Result[]>([]);
  const [isPending, startTransition] = useTransition();
  const requestVersion = useRef(0);

  const handleChange = (e: ChangeEvent<HTMLInputElement>) => {
    const value = e.target.value;
    // Urgent: keep the input responsive
    setQuery(value);
    // Async work inside the transition keeps isPending true while it runs.
    // React's current limitation: a set() scheduled AFTER an await is not
    // marked as part of the transition, so wrap it in its own startTransition.
    const version = ++requestVersion.current;
    startTransition(async () => {
      const data = await fetchResults(value);
      if (version === requestVersion.current) startTransition(() => setResults(data));
    });
  };

  return (
    <>
      <input value={query} onChange={handleChange} />
      {isPending && <Spinner />}
      <ResultList results={results} />
    </>
  );
}
```

`useTransition` returns `[isPending, startTransition]`. The version guard above suppresses out-of-order responses; transition scheduling does not order arbitrary requests. The async Action form requires React 19. React can interrupt eligible transition rendering for urgent updates. In React 19 an async Action keeps the transition pending while awaited work runs, but setters after an await currently need another `startTransition` to mark that update. The callback's synchronous code still runs immediately.

### Let a results consumer lag behind its input

```typescript
import { useDeferredValue, useState, useMemo } from 'react';

function FilteredList({ items }: { items: Item[] }) {
  const [filter, setFilter] = useState('');
  // deferredFilter lags behind filter on slow renders
  const deferredFilter = useDeferredValue(filter);
  const isStale = filter !== deferredFilter;

  const filtered = useMemo(
    () => items.filter(i => i.name.includes(deferredFilter)),
    [items, deferredFilter]
  );

  return (
    <>
      <input value={filter} onChange={e => setFilter(e.target.value)} />
      <div style={{ opacity: isStale ? 0.6 : 1 }}>
        {filtered.map(item => <Item key={item.id} {...item} />)}
      </div>
    </>
  );
}
```

A memoized results component can also skip its urgent render when passed the deferred filter. Memoizing only the calculation above leaves the list mapping in the input component; large lists should move behind their own boundary.

**`useTransition` vs `useDeferredValue`:**
- `useTransition` marks controlled updates and tracks pending Actions. Use when you own the update.
- `useDeferredValue` wraps a value. Use when a value comes from props or a parent.

### Show a proposal while its Action is pending

```typescript
import { useOptimistic, useState, startTransition } from 'react';
type Comment = { id: string; text: string; pending?: boolean };
type Props = { serverComments: Comment[]; addComment: (text: string) => Promise<void> };

function CommentList({ serverComments, addComment }: Props) {
  const [error, setError] = useState<string | null>(null);
  const [optimisticComments, addOptimistic] = useOptimistic(
    serverComments,
    (state, comment: Comment) => [...state, { ...comment, pending: true }]
  );
  const handleAdd = (text: string) => {
    const comment = { text, id: crypto.randomUUID() };
    setError(null);
    startTransition(async () => {
      addOptimistic(comment);
      try {
        await addComment(text); // Parent must publish confirmed serverComments before completion.
      } catch (error) {
        setError(error instanceof Error ? error.message : String(error));
      }
    });
  };
  return (
    <>
      <button onClick={() => handleAdd('New comment')}>Add comment</button>
      {error && <p role="alert">{error}</p>}
      <ul>{optimisticComments.map(c => <li key={c.id}>{c.text} {c.pending && '(sending...)'}</li>)}</ul>
    </>
  );
}
```

The optimistic setter must run inside an Action such as this transition or a form action. Its temporary overlay reverts to the latest base when that Action finishes, whether it succeeds or fails. Success therefore needs the confirmed base to be updated; the Hook does not persist a successful mutation or decide that it failed.

### Read an owned promise through a Suspense boundary

```typescript
import { use, Suspense } from 'react';

function UserProfile({ userPromise }: { userPromise: Promise<User> }) {
  // 'use' suspends the component until the promise resolves
  const user = use(userPromise);
  return <h1>{user.name}</h1>;
}

// Create the promise in a loader/event before rendering this client tree.
function App({ userPromise }: { userPromise: Promise<User> }) {
  return (
    <Suspense fallback={<Spinner />}>
      <UserProfile userPromise={userPromise} />
    </Suspense>
  );
}
```

`use` differs from `await`:
- `use` reads resources while a component or Hook renders and may be called conditionally; it is not an await replacement inside ordinary async functions
- Suspends the component until the promise resolves
- Works with `<Suspense>` boundary for fallback UI
- Supports Suspense-aware resources; it does not turn an uncached fetch in render into a safe data source

### `<form>` Actions (React 19)

```typescript
// Before: manual submit + state + error handling
function OldForm() {
  const [name, setName] = useState('');
  const [error, setError] = useState('');
  const [isSubmitting, setIsSubmitting] = useState(false);
  return (
    <form onSubmit={async e => {
      e.preventDefault();
      setIsSubmitting(true);
      try { await api.updateName(name); } catch (err) { setError(err.message); }
      finally { setIsSubmitting(false); }
    }}>
      {/* ... */}
    </form>
  );
}

// After: declarative form action
function NewForm({ updateName }: { updateName: (formData: FormData) => Promise<void> }) {
  return (
    <form action={updateName}>
      <input name="name" />
      <SubmitButton />
    </form>
  );
}

import { useFormStatus } from 'react-dom';

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Saving...' : 'Save'}</button>;
}
```

When the action needs to *return* a value (validation errors, the saved entity), React 19's `useActionState` wraps it:

```typescript
import { useActionState } from 'react';

function ChangeName() {
  const [error, formAction, isPending] = useActionState(
    async (prev: string | null, formData: FormData) => {
      try {
        await updateName(String(formData.get('name')));
        return null;
      } catch (err) {
        return (err as Error).message; // returned value becomes `error`
      }
    },
    null
  );
  return (
    <form action={formAction}>
      <input name="name" />
      <button disabled={isPending}>{isPending ? 'Saving...' : 'Save'}</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
```

`useActionState` returns `[state, wrappedAction, isPending]`. It was named `useFormState` in the canary releases; that name is deprecated — import `useActionState` from `react` in new code.

### Refs as Props (React 19)

```typescript
// Before: forwardRef wrapper
const OldInput = forwardRef<HTMLInputElement, Props>((props, ref) => (
  <input ref={ref} {...props} />
));

// After: ref is a regular prop
function NewInput({ ref, ...props }: Props & { ref?: Ref<HTMLInputElement> }) {
  return <input ref={ref} {...props} />;
}
```

No more `forwardRef` wrapper — `ref` is just a prop (React 19 plans to deprecate `forwardRef` over time). `useImperativeHandle` still exists: ref-as-prop only removes the *forwarding* boilerplate, while imperative handles remain the way to expose a custom API (focus, scroll) through a child's ref.

### Real-World: Like Button with Optimistic Update

```typescript
function LikeButton({ likes, isLiked, saveLike }: {
  likes: number;
  isLiked: boolean;
  saveLike: (nextLiked: boolean) => Promise<void>;
}) {
  const [error, setError] = useState<string | null>(null);
  const [pending, startTransition] = useTransition();
  const [optimistic, setOptimistic] = useOptimistic(
    { likes, isLiked },
    (current, nextLiked: boolean) => ({
      likes: current.likes + (nextLiked === current.isLiked ? 0 : nextLiked ? 1 : -1),
      isLiked: nextLiked,
    })
  );
  const handleClick = () => {
    const nextLiked = !optimistic.isLiked;
    setError(null);
    startTransition(async () => {
      setOptimistic(nextLiked);
      try { await saveLike(nextLiked); } // Parent publishes both confirmed base props.
      catch (error) { setError(error instanceof Error ? error.message : String(error)); }
    });
  };
  return <><button disabled={pending} aria-pressed={optimistic.isLiked} onClick={handleClick}>
    {optimistic.likes} ♥
  </button>{error && <p role="alert">{error}</p>}</>;
}
```

Count and selection share the optimistic overlay, so both revert together to the confirmed base on failure. Disabling overlapping clicks prevents this simple example from issuing conflicting requests; successful persistence remains the parent's responsibility.

### Real-World: Async Data Without useEffect

> Same before/after as **How It Works → `use(promise)`** above: the `useEffect` + `useState` + loading-flag Profile reads a stable `userPromise` with `use(userPromise)` inside a `<Suspense>` boundary — the loading state moves out of the component and into the boundary.

## Real-World Use Cases

1. **Search-as-you-type** — `useTransition` separates urgent input from the state driving expensive result rendering
2. **Long lists with filters** — `useDeferredValue` defers heavy re-renders when filters change
3. **Mutations with rollback** — `useOptimistic` for likes, comments, todos, cart updates
4. **Data fetching** — `use(promise)` + `<Suspense>` for clean async data without `useEffect` boilerplate
5. **Form submissions** — React 19's `<form action>` for progressive-enhancement-friendly forms
6. **Server Components + Client Islands** — `use` lets client components suspend on promises passed from server components

## Common Mistakes

| Mistake | Fix |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Wrapping the input value setter in `useTransition` | Only wrap slow updates; keep input updates urgent |
| Using `useTransition` for every state update | It's for non-urgent work. Synchronous trivial updates don't need it |
| Using `useDeferredValue` for a value that's already fast | Only use it for values that cause slow renders (large lists, complex derived data) |
| `useOptimistic` for non-undoable operations | Optimistic updates roll back on failure — if the user expects confirmation, don't use it |
| Using `use` in a Server Component | Server Components can use it too; prefer async/await there when appropriate |
| Putting `use(promise)` outside a `<Suspense>` boundary | Without a boundary, the root can wait without an explicit loading fallback |
| Forgetting that `use` re-suspends on every render with a new promise | The promise should be stable (cached, deduped) — use a framework/library cache or pass a promise created outside render |

## Best Practices

1. **Keep direct input updates urgent**; use transitions for the non-urgent result/tab state that the interaction also changes
2. **Use `useDeferredValue` for values that come from props or external state** — derived data, search filters
3. **Always wrap `use(promise)` consumers in `<Suspense>`** — the boundary defines the fallback UI
4. **Choose optimism by user expectations and recoverability**. Prefer explicit desired-state writes over ambiguous toggles, and retain confirmation for high-consequence actions
5. **Cache the promises you pass to `use`** — without caching, every render creates a new promise and triggers a new fetch
6. **For React 19: use `ref` as a prop** — `forwardRef` is no longer needed
7. **For React 19: prefer `<form action>` over `onSubmit` + state** — use useFormStatus/useActionState for pending and expected errors; progressive enhancement for Server Functions requires server/framework support
8. **Don't reach for these hooks for trivial updates** — `useState` is still the default. Concurrent hooks solve specific UX problems.

## Performance Considerations

| Pattern | Use Case | Tradeoff |
| ------------------------- | ---------------------------------- | --------------------------------------------------------------------------------- |
| `useTransition` | Slow state updates from user input | Adds slight overhead; interrupts can cause minor re-work |
| `useDeferredValue` | Slow derived values from input | May prepare both urgent and deferred renders; interruption can restart work |
| `useOptimistic` | Mutations with fast feedback | Requires rollback handling; can confuse if server fails |
| `use(promise)` + Suspense | Async data fetching | Suspends the tree; needs a boundary; caching is your responsibility |
| `<form action>` | Form submissions | Server Actions require framework support (Next.js, Remix) or a custom integration |

Measure interaction latency on representative devices before choosing an optimization. Reduce long indivisible calculations first; schedule eligible result rendering separately when input feedback has a tighter deadline. An optimistic overlay addresses mutation feedback, not render or network throughput.

## Summary

React 18's concurrent hooks (`useTransition`, `useDeferredValue`) and React 19's new APIs (`use`, `useOptimistic`, ref-as-prop, `<form action>`) are the modern primitives for senior-level React work. Use them to keep input responsive, integrate async data without `useEffect`, and ship instant feedback on mutations. Default to plain `useState` — these are for specific UX problems, not everyday state.

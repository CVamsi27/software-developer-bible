# Modern React: Scheduling, Actions, and DOM APIs

A search box can feel broken even when every request succeeds: typing stalls while a large list renders, old results arrive after new ones, and a saved change appears to vanish. React’s modern APIs address different parts of that interaction. They schedule render work, represent pending writes, and let components read resources or coordinate with the DOM.

```tsx
const [tab, setTab] = useState("overview");
const [isPending, startTransition] = useTransition();

function selectTab(next: string) {
  startTransition(() => setTab(next)); // non-urgent: input stays responsive
}
```

## Definition

**Practical definition:** Modern React APIs let an application distinguish urgent feedback from interruptible rendering and coordinate asynchronous UI work with React’s render and commit lifecycle. They do not make slow JavaScript faster, order network requests, or replace server validation and persistence.

> **Textbook Definition:** React scheduling and Action APIs coordinate when updates are rendered and how asynchronous results participate in UI state. Deferred work may be interrupted and retried; optimistic state is a temporary overlay on confirmed state; external resources and mutations remain owned by the application or its framework.

## First Principles

An interaction may have several deadlines. The input must echo a keystroke promptly; a large result list can update later. A save can show a proposed value while the server is working, but the server’s response remains authoritative. A component reading an unfinished resource needs a loading boundary and a separate failure path.

Choose the API for the part of the interaction it controls. A Transition affects render priority. An Action coordinates pending asynchronous work. Suspense handles a render that cannot yet produce its result. None of these APIs cancels a server-side write or supplies application authorization.

## 1. Keep Input Feedback Urgent

Use **useTransition** when the component owns the state update that drives expensive UI. The input’s own value stays urgent:

```tsx
import { useState, useTransition } from "react";

function TabPicker() {
  const [tab, setTab] = useState("overview");
  const [isPending, startTransition] = useTransition();

  function selectTab(nextTab: string) {
    startTransition(() => setTab(nextTab));
  }

  return (
    <>
      <button onClick={() => selectTab("reports")}>Reports</button>
      {isPending && <span role="status">Updating view…</span>}
      <TabPanel tab={tab} />
    </>
  );
}
```

If the slow value comes from a prop or another owner, **useDeferredValue** lets the result consumer lag behind it. Keep that consumer behind a memoized component so an urgent parent render does not repeat the expensive list work:

```tsx
import { memo, useDeferredValue, useState } from "react";

// Project is an application type; projects keeps a stable identity between keystrokes.
const ProjectResults = memo(function ProjectResults({
  projects,
  query,
}: {
  projects: Project[];
  query: string;
}) {
  const normalized = query.trim().toLowerCase();
  const visible = projects.filter((project) =>
    project.name.toLowerCase().includes(normalized),
  );

  return <ul>{visible.map((project) => <li key={project.id}>{project.name}</li>)}</ul>;
});

function ProjectSearch({ projects }: { projects: Project[] }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <>
      <label>
        Filter projects
        <input value={query} onChange={(event) => setQuery(event.target.value)} />
      </label>
      <div aria-busy={isStale}>
        {isStale && <p role="status">Updating results…</p>}
        <ProjectResults projects={projects} query={deferredQuery} />
      </div>
    </>
  );
}
```

A Transition marks a state update as non-urgent and reports while that Transition is pending. A deferred value gives a consumer a lagging value without changing the producer. Neither API debounces network requests, moves JavaScript to another thread, nor preempts one long synchronous calculation. For request-driven search, also cancel or ignore obsolete requests and keep each displayed result tied to its query.

In an async Transition, React tracks the Action while it is pending. State updates scheduled after an await currently need another startTransition if they should remain non-urgent. Transition scheduling also does not determine which of two server responses is newer; use request identity, cancellation or a server version when ordering matters.

## 2. Keep Pending Writes Separate from Confirmed Data

A React 19 form can pass a function to its action prop. React runs it as an Action and exposes pending state. Use **useActionState** when the Action returns expected validation or conflict messages:

```tsx
import { useActionState } from "react";

type SaveState = { error: string } | null;

async function saveDisplayName(
  _previous: SaveState,
  formData: FormData,
): Promise<SaveState> {
  const value = formData.get("displayName");
  if (typeof value !== "string" || !value.trim()) {
    return { error: "Enter a display name." };
  }

  const result = await api.updateDisplayName(value.trim());
  return result.ok ? null : { error: result.message };
}

function SaveDisplayName() {
  const [state, action, isPending] = useActionState(saveDisplayName, null);

  return (
    <form action={action}>
      <label>
        Display name
        <input name="displayName" required />
      </label>
      <button disabled={isPending}>{isPending ? "Saving…" : "Save"}</button>
      {state?.error && <p role="alert">{state.error}</p>}
    </form>
  );
}
```

Here api.updateDisplayName is application code that calls the authorized server endpoint. Return expected validation or conflict outcomes as state; let unexpected failures reach the nearest error boundary or the application’s error-reporting path.

**useFormStatus** is useful when a design-system submit button needs its parent form’s pending state without receiving a prop. Call it in a component rendered inside that form; calling it in the component that returns the form reads the outer form, if any.

```tsx
import { useFormStatus } from "react-dom";

function SaveButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "Saving…" : "Save"}</button>;
}
```

Import this Hook from react-dom. Keep the button component inside the form whose status it reads.

**useOptimistic** is for a visible proposal while an Action is pending. Its base value remains the confirmed value. Update that base when persistence succeeds; on failure React drops the temporary overlay, so the interface should also explain the failure. If multiple updates can overlap, use a reducer that recomputes against the latest base and define server-side conflict or idempotency behavior. Optimistic UI is feedback, not persistence or concurrency control.

```tsx
import { startTransition, useOptimistic, useState } from "react";

// Inside a component; api.setLiked is application code.
const [liked, setLiked] = useState(initialLiked);
const [shownLiked, setOptimisticLiked] = useOptimistic(liked);

function handleLike() {
  startTransition(async () => {
    setOptimisticLiked(true);
    const confirmed = await api.setLiked(true);
    startTransition(() => setLiked(confirmed));
  });
}
```

This example is an explicit set-to-true operation, so retries do not invert the state. A production handler should map expected API failures to visible error state.

A function-valued form Action is not automatically a no-JavaScript server endpoint. Progressive enhancement requires a Server Function and a framework or server integration that can execute it. React does not validate authorization merely because a form uses Actions.

## 3. Read a Stable Resource During Render

**use(promise)** reads a promise during rendering. A pending promise suspends to the nearest Suspense boundary; a rejected promise reaches the nearest Error Boundary. The promise needs a stable owner, such as a framework loader or cache, rather than being recreated on each render:

```tsx
import { Suspense, use } from "react";

function Comments({ commentsPromise }: { commentsPromise: Promise<Comment[]> }) {
  const comments = use(commentsPromise);
  return <CommentList comments={comments} />;
}

function Article({ commentsPromise }: { commentsPromise: Promise<Comment[]> }) {
  return (
    <Suspense fallback={<p role="status">Loading comments…</p>}>
      <Comments commentsPromise={commentsPromise} />
    </Suspense>
  );
}
```

Unlike most Hooks, use may be called conditionally. It can read a promise in a Client or Server Component; in a Server Component it cannot read Context. A Server Component may pass a promise to a Client Component through a framework that supports that handoff, and the resolved value must be serializable. Prefer async/await for ordinary server data loading.

React 19.3 adds **use(browser())** for a component that has no meaningful server-rendered output: it suspends that component during server rendering and continues in the browser under a Suspense boundary. Use it for genuinely browser-only work, not as a substitute for making ordinary server and client output agree.

## 4. Keep Effects Reactive and DOM Identity Clear

**useEffectEvent** (React 19.2) lets an Effect callback read the latest committed values without restarting an external connection. Use it only for non-reactive logic that belongs to an Effect; it must not hide a value that should cause the Effect to reconnect, and it is not a general callback to pass to children.

```tsx
import { useEffect, useEffectEvent } from "react";

// Inside a component; roomId and theme come from its props.
const onConnected = useEffectEvent(() => showNotification(theme));

useEffect(() => {
  const connection = connect(roomId);
  connection.on("connected", onConnected);
  return () => connection.disconnect();
}, [roomId]);
```

**useId** creates IDs for accessibility relationships such as label/input and aria-describedby. It is not a list key or database identifier. When several React roots share a page, configure distinct identifierPrefix values and match each server prefix with its hydration root.

React 19 function components can receive ref as a prop, so new components usually do not need a forwardRef wrapper. useImperativeHandle remains useful when a component should expose a deliberate imperative API instead of its DOM node.

React 19.3 stabilizes Fragment refs. A ref on Fragment exposes a limited FragmentInstance for coordinating its DOM children — such as focus, observation or scrolling — without inserting a wrapper element. Reach for it when the wrapper would change layout or semantics. ViewTransition can animate tree changes associated with React Transitions and Suspense; urgent updates remain immediate, and animation still needs to respect reduced-motion preferences.

```tsx
import { startTransition, useState, ViewTransition } from "react";

function ProjectPanel() {
  const [expanded, setExpanded] = useState(false);

  return (
    <>
      <button onClick={() => startTransition(() => setExpanded((value) => !value))}>
        Toggle details
      </button>
      <ViewTransition>
        {expanded && <ProjectDetails />}
      </ViewTransition>
    </>
  );
}
```

React coordinates the browser View Transition for eligible updates; this component does not turn every urgent state update into an animation.

React 19.2 also adds Activity for keeping a hidden subtree’s state while its Effects are disconnected and updates are deferred. It fits interfaces that should preserve an inactive screen, not a generic loading placeholder:

```tsx
import { Activity } from "react";

<Activity mode={isOpen ? "visible" : "hidden"}>
  <ReportEditor />
</Activity>
```

React 19.3 adds Trusted Types support in React DOM: trusted values can reach DOM sinks without React first stringifying them, while the application still supplies its CSP and sanitization policy. These version boundaries matter when diagnosing behavior; consult the release notes before adopting an API in a mixed-version application.

## Summary

Keep the input urgent and defer only expensive rendering. Use Actions for pending writes, optimistic state for a temporary proposal, and use for a stable resource with Suspense and error boundaries. Treat server data as authoritative, and use newer DOM APIs only when their specific boundary solves a real problem.

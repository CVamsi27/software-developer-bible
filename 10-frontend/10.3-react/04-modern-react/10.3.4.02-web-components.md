# Web Components

> **Custom Elements, Shadow DOM, and HTML Templates — native browser component system.**

## Definition

**Web Components** are a set of native browser features — Custom Elements, Shadow DOM, and HTML templates/slots — that together let you define reusable, encapsulated HTML elements with their own behavior and styling, usable in any framework or none.

## First Principles

A widget embedded into another team's page must coexist with its DOM and CSS without requiring the host's framework:

1. **HTML needs a named entry point for behavior.** Custom-element registration associates a tag with an element class and lifecycle callbacks.
2. **Global selectors otherwise couple host and widget styles.** A shadow tree creates a selector boundary while allowing deliberate theming through inheritance and exposed parts.
3. **A boundary still needs a data contract.** Attributes carry strings, properties carry JavaScript values, and events report changes to the host. None of these APIs chooses an application-state architecture for you.

## Why It Matters

A registered custom element can be consumed by React, Vue, Angular or plain HTML, with framework-specific property/event and server-rendering integration. The encapsulation is enforced by the platform, not by tooling: shadow DOM scoping is a browser boundary (→ 10.7.06's global-cascade problem, solved natively), so ordinary selectors do not cross the shadow boundary. Inherited styles, CSS custom properties, slotted content, and exposed `::part()` hooks still provide intentional connections (→ 10.7.07). That makes them the natural boundary technology where one codebase's UI must run inside another's page.

```
host HTML → registered tag → element lifecycle/rendering
                  ↘ attributes/properties in; events out
                  ↘ optional shadow tree and cloned templates
```

| Feature | What It Does | Browser Support |
| ------------------- | --------------------------- | ------------------- |
| **Custom Elements** | Define new HTML tags | All modern browsers |
| **Shadow DOM** | Encapsulated DOM and styles | All modern browsers |
| **HTML Templates** | Reusable markup fragments | All modern browsers |

## Registration connects a tag to element behavior

```typescript
// Define a custom element
class PatientCard extends HTMLElement {
  constructor() {
    super();
    // Attach shadow DOM for encapsulation
    this.attachShadow({ mode: 'open' });
  }

  connectedCallback() {
    this.render();
  }

  private render() {
    const name = this.getAttribute('name') || 'Unknown';
    const email = this.getAttribute('email') || '';

    this.shadowRoot!.innerHTML = `
      <style>
        .card {
          border: 1px solid #e0e0e0;
          border-radius: 8px;
          padding: 16px;
          font-family: system-ui;
        }
        .name { font-weight: 600; font-size: 1.1rem; }
        .email { color: #666; }
      </style>
      <div class="card">
        <div class="name"></div>
        <div class="email"></div>
        <slot></slot>
      </div>
    `;
    // Attribute values are text, never executable HTML.
    this.shadowRoot!.querySelector('.name')!.textContent = name;
    this.shadowRoot!.querySelector('.email')!.textContent = email;
  }

  // React to attribute changes
  static get observedAttributes() {
    return ['name', 'email'];
  }

  attributeChangedCallback(name: string, oldVal: string | null, newVal: string | null) {
    if (oldVal !== newVal) {
      this.render(); // React to data without simulating a connection
    }
  }
}

// Register the custom element
customElements.define('patient-card', PatientCard);
```

```html
<!-- Use in HTML -->
<patient-card name="Maria Schmidt" email="maria@example.com">
  <p>Appointment: 2026-08-25</p>
</patient-card>
```

## A shadow tree scopes selectors without isolating code

Shadow DOM scopes selector matching. Inherited properties can reach descendants, `::part()` styles explicitly exposed internals, and slotted nodes remain in light DOM. Encapsulation is not a security sandbox: code can access an open root through `shadowRoot`.

```typescript
class StyledButton extends HTMLElement {
  constructor() {
    super();
    this.attachShadow({ mode: 'open' });
  }

  connectedCallback() {
    this.shadowRoot!.innerHTML = `
      <style>
        /* This style ONLY affects this component */
        button {
          background: var(--btn-bg, #3b82f6);
          color: white;
          border: none;
          padding: 8px 16px;
          border-radius: 4px;
          cursor: pointer;
        }
        button:hover {
          background: var(--btn-hover, #2563eb);
        }
      </style>
      <button><slot></slot></button>
    `;
  }
}

customElements.define('styled-button', StyledButton);
```

### A shadow tree scopes selectors without isolating code Encapsulation

```css
/* External styles DON'T affect shadow DOM */
styled-button button {
  background: red; /* This won't work! */
}

/* Use inherited CSS custom properties as explicit theme inputs */
styled-button {
  --btn-bg: #10b981; /* This works! */
}
```

## A template keeps markup inert until it is cloned

```html
<table><tbody id="patients"></tbody></table>
<template id="patient-row">
  <tr>
    <td class="name"></td>
    <td class="email"></td>
    <td class="status"></td>
  </tr>
</template>

<script>
  const template = document.getElementById('patient-row');
  const clone = template.content.cloneNode(true);

  clone.querySelector('.name').textContent = 'Maria Schmidt';
  clone.querySelector('.email').textContent = 'maria@example.com';
  clone.querySelector('.status').textContent = 'Active';

  document.querySelector('#patients').appendChild(clone);
</script>
```

## Web Components vs React

| Feature | Web Components | React |
| -------------------- | --------------------------------------------------------------------------- | ----------------------------------------------- |
| **Encapsulation** | Shadow DOM (native) | Scoped CSS (tools) |
| **Re-rendering** | Manual (attributeChangedCallback) | Automatic (state change) |
| **Framework** | Framework-agnostic | React-specific |
| **Bundle size** | No required framework; element code still loads | Includes the React runtime and application code |
| **Server rendering** | Server-generated markup / declarative shadow DOM; lifecycle runs in browser | SSR/SSG plus hydration when interactive |
| **Ecosystem** | Limited | Vast |

## Code Examples

### Using a custom element from React (React 19 interop)

React 19's client renderer assigns a prop as a **property when that name exists on the element instance**; otherwise it generally writes an attribute. Register the element before React renders it and initialize fields such as `config` in its constructor. On the server, primitive props are emitted as attributes while non-primitive props are omitted from markup.

```tsx
// booking-widget's constructor declares this.config = undefined.
function BookingWidget({ clinicId, onBooked }: { clinicId: string; onBooked: (id: string) => void }) {
  return (
    <booking-widget
      clinic-id={clinicId}
      config={{ theme: 'dark' }}
      onbooked={(event: CustomEvent<string>) => onBooked(event.detail)}
    />
  );
}
```

The custom tag also needs a project JSX type declaration describing `config` and `onbooked`; React's runtime support does not automatically teach TypeScript a new tag. In React ≤18 a ref effect is a compatibility adapter for property assignment and custom listeners; React 19 no longer requires that adapter for this example.

When an internal button announces a booking, use `new CustomEvent('booked', { detail: id, bubbles: true, composed: true })` so the event can travel from the shadow tree to host ancestors. Slots project host children into the component's layout; they do not move those nodes out of light DOM.

| **React-only application** | Use React components |
| **Development with HMR** | Check the toolchain; custom-element registration needs care |
| **Healthcare app with third-party booking embeds** | React for app; consider Web Components for independent widgets |

## Common Mistakes

1. **Expecting React re-renders to update the element** — only attributes/properties you pass change it; `attributeChangedCallback` re-renders only observed attributes. Passing an object prop that the element doesn't read silently does nothing.
2. **Styling across the boundary with regular selectors** — shadow DOM blocks them. Use inherited CSS custom properties, documented `::part()` hooks or the component's public styling API. Constructable stylesheets organize styles within a root; they do not make external selectors cross it.
3. **Forgetting `observedAttributes`** — without it, `attributeChangedCallback` never fires and props look "broken" in every framework.
4. **Expecting built-in reactive state** — the browser does not provide React-style state updates. An element can still maintain state in fields or use a component library that supplies reactivity.
5. **Changing custom-event casing in JSX** — `onbooked` listens for `booked`, while `onBooked` listens for `Booked`. Preserve the dispatched name in React 19; use a ref listener when supporting older React.

## Best Practices

- **Consider custom elements when one widget must serve multiple host frameworks**; weigh integration, accessibility, server rendering and maintenance before choosing the boundary.
- **Emit CustomEvents with `detail`** for a clean host-facing API; document them like props.
- **Load element modules with `<script type="module">`** and guard duplicate registration when needed. A `customElements.get` guard does not replace an already-registered class during HMR; the development toolchain must handle that lifecycle.
- **Pass data down as properties, receive events up via CustomEvent** — one-way flow, same mental model as React.

## Summary

1. **Web Components = custom elements + shadow DOM + slots** — framework-agnostic encapsulation at the platform level
2. **React 19 interop improved** — custom elements accept props/children more naturally; attribute vs property handling is still the trap
3. **Shadow DOM boundaries affect styling and events** — composed/retargeted events, `:host` styling, constructable stylesheets
4. **Right tool for embeddable widgets and design systems** — one widget consumed by React/Vue/plain-HTML hosts
5. **Choose by integration requirements** — an embeddable booking widget may benefit from a custom-element boundary; a React-only application may not need it

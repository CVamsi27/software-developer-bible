# React Router

## TL;DR

React Router v6/v7 centers on **data routers**: `createBrowserRouter` defines a nested route tree where layouts render children through `<Outlet>`, `loader`s fetch data before a route renders, `action`s handle mutations from `<Form>` submissions, and errors land in per-route `errorElement`s. Hooks (`useParams`, `useNavigate`, `useLocation`) cover navigation state; relative routing resolves against the route hierarchy by default, not URL segments. The examples below target **v7 Data Mode** in a browser SPA. React Router also supports server rendering and prerendering through Framework Mode; choose the deployment mode before comparing frameworks.

## First Principles

Client routing is *URL as state owner*:

1. **The URL is shareable, back-button-compatible state** — routing's job: sync location ↔ UI; nested routes own layout segments (outlets), loaders own data needs (→ 10.4.3.01's server-side analog).
2. **Data routers changed the model**: navigation = loader run + transition, not "render then fetch in effects" — the fetch-on-render waterfall (→ 50.3.1.01's LCP tax) is what the loader model exists to kill.

## Why It Matters

React Router's data APIs change where a route coordinates fetching: data loading moves out of effects into loaders that run *before* render, with automatic revalidation after actions — essentially Remix ideas folded into RR. Interviews increasingly test loader/action semantics, protected-route design, and "why is my relative link wrong?" — all covered here.

**Concretely:**

1. **Declarative nesting**: Layouts, guards, and error UI attach at any tree depth once, instead of per-page wiring.
2. **Data before render**: Loaders eliminate the classic `useEffect` fetch waterfall; navigation can show pending states via `useNavigation`.
3. **Mutations with revalidation**: Actions process form posts and automatically re-run active loaders — no manual refetch code.
4. **Scoped failure handling**: Route error elements handle loader, action, and render failures. Forms work before hydration only with server handling, as in an appropriately configured Framework Mode app.
5. **Deployment choices**: The same library offers Declarative, Data, and Framework modes with different loading and rendering contracts.

## Definition

**React Router (v6/v7)** couples URL matching to a component tree and, in its **data router** form, to data loading and mutation lifecycles. A route object declares `path`, `element`, `children`, plus optional `loader`, `action`, and `errorElement`. The router renders the matched branch, waiting for required loader results, nesting each child inside its parent's `<Outlet />`.

```text
ROUTE TREE → COMPONENT NESTING
═══════════════════════════════════════════════════════════════

createBrowserRouter([
 { path: "/",    element: <Root/>,        errorElement: <RootError/>,
   children: [
   { index: true, element: <Home/> },
   { path: "dashboard", element: <DashLayout/>, loader: dashLoader,
     children: [
     { path: "team/:id", element: <Team/>, loader: teamLoader },
     { path: "settings",  element: <Settings/> },
   ]},
 ]})

URL /dashboard/team/42 renders:

┌─ Root ─────────────────────────────┐
│  <Outlet/> →                       │
│  ┌─ DashLayout ──────────────────┐ │
│  │  <Outlet/> →                  │ │
│  │  ┌─ Team (params.id = 42) ──┐ │ │
│  │  │                          │ │ │
│  │  └──────────────────────────┘ │ │
│  └───────────────────────────────┘ │
└────────────────────────────────────┘

Matched loaders run in parallel; there is no deepest-first guarantee.
```


## How It Works

### Data Router Setup

```tsx
import {
  createBrowserRouter,
} from "react-router";
import { RouterProvider } from "react-router/dom";

const router = createBrowserRouter([
  {
    path: "/",
    element: <Root />,
    errorElement: <RootErrorBoundary />, // catches render AND loader/action errors
    children: [
      { index: true, element: <Home /> },
      {
        path: "dashboard",
        element: <DashboardLayout />,
        loader: dashboardLoader,
        children: [{ path: "team/:teamId", element: <Team />, loader: teamLoader }],
      },
      { path: "login", element: <Login />, action: loginAction },
    ],
  },
]);

export default function App(): React.JSX.Element {
  return <RouterProvider router={router} />;
}
```

V7 browser apps import routing APIs from `"react-router"` and the DOM-aware provider from `"react-router/dom"` (which supplies `flushSync`). V6 uses `"react-router-dom"`; some APIs changed between these majors, including deferred data.

### Loaders and useLoaderData

```typescript
async function teamLoader({ params }: { params: Record<string, string | undefined> }) {
  const [team, members] = await Promise.all([
    fetchTeam(params.teamId!),          // parallel, before render
    fetchMembers(params.teamId!),
  ]);
  if (!team) {
    throw new Response("Not Found", { status: 404 }); // → nearest errorElement
  }
  return { team, members };
}

function Team(): React.JSX.Element {
  const { team, members } = useLoaderData<typeof teamLoader>(); // typed!
  return <Roster team={team} members={members} />;
}
```

Pending states come from `useNavigation().state === "loading"`, enabling global spinners or skeleton routes without per-component bookkeeping.

### Actions and Form Mutations

```tsx
import { Form, redirect, useActionData } from "react-router";

async function loginAction({ request }: { request: Request }) {
  const formData = await request.formData();
  const email = String(formData.get("email"));
  try {
    await api.login(email, String(formData.get("password")));
    return redirect("/dashboard");
  } catch {
    return { error: "Invalid credentials" }; // revalidates + returns data
  }
}

function Login(): React.JSX.Element {
  const result = useActionData<typeof loginAction>();
  return (
    <Form method="post">           {/* POSTs to the route's action */}
      <input name="email" type="email" required />
      <input name="password" type="password" />
      <button type="submit">Sign in</button>
      {result?.error && <p role="alert">{result.error}</p>}
    </Form>
  );
}
```

Successful mutation actions trigger loader revalidation by default. `shouldRevalidate` can override it; in v7, actions returning or throwing 4xx/5xx responses skip revalidation by default. Returning `{ error }` as ordinary data does not itself set an error status.

### Promise Data + Await (Progressive Loading)

V7 loaders return raw promises for non-critical data; v6 used `defer` from `react-router-dom`. A promise placed in a returned object is **not automatically awaited** just because its key is named `critical`:

```tsx
import { Await, useAsyncValue, useLoaderData } from "react-router";
import { Suspense } from "react";

export async function loader() {
  const suggestions = getSuggestionsSlow();
  // Handle an early rejection; Await still receives the original promise.
  void suggestions.catch(() => {});
  const critical = await getDashboardStats();
  return { critical, suggestions }; // only suggestions is still a promise
}

function Suggestions(): React.JSX.Element {
  const data = useAsyncValue() as Suggestion[];
  return <List items={data} />;
}

function Dashboard(): React.JSX.Element {
  const { critical, suggestions } = useLoaderData<typeof loader>();
  return (
    <>
      <Stats data={critical} />
      <Suspense fallback={<Skeleton rows={3} />}>
        <Await resolve={suggestions} errorElement={<RetryPrompt />}>
          <Suggestions />
        </Await>
      </Suspense>
    </>
  );
}
```

The router waits for the loader's critical work before committing this navigation. The slow panel then fills in as its promise settles. The early rejection handler prevents an unhandled rejection while critical data loads; `<Await>` still receives the rejected original promise and renders its error UI. Promise-returning loaders provide progressive client loading here, rather than server HTML streaming.

### Protected Routes

A loader can redirect before protected route content mounts. Because parent and child loaders run in parallel, a layout redirect does not stop a child from starting; protect each data operation and authorize requests at the server:

```typescript
import { Outlet, redirect, useRouteLoaderData } from "react-router";
import type { LoaderFunctionArgs } from "react-router";

export async function requireUser({ request }: LoaderFunctionArgs): Promise<User> {
  const user = await getSessionUser(request);
  if (!user) {
    const to = new URL("/login", request.url);
    to.searchParams.set("from", new URL(request.url).pathname);
    throw redirect(to.toString());
  }
  return user;
}

// This guards the layout UI; children must protect their own data.
const appRoute = {
  id: "app",
  path: "app",
  loader: async (args: LoaderFunctionArgs) => {
    const user = await requireUser(args);
    return { user };
  },
  element: <AppShell />,
};

function AppShell(): React.JSX.Element {
  const { user } = useRouteLoaderData("app") as { user: User };
  return <><header>Signed in as {user.email}</header><Outlet /></>;
}
```

A `<ProtectedRoute><Comp/></ProtectedRoute>` wrapper component using `<Navigate>` still appears in older codebases; prefer loaders because they prevent the flash of protected content entirely.

### Core Hooks

| Hook | Use |
| ------------------------ | ---------------------------------------------------------------- |
| `useParams()` | Read dynamic path segments |
| `useNavigate()` | Navigate programmatically; Data/Framework Mode returns a promise |
| `useLocation()` | Read pathname, search, hash, navigation state and entry key |
| `useSearchParams()` | Read/write query parameters through navigation |
| `useNavigation()` | Observe `idle`, `loading`, or `submitting` |
| `useRouteLoaderData(id)` | Read the matched route loader identified by its explicit ID |

### Relative Routing Rules

```tsx
const childLink = <Link to="details" />;              // relative to ROUTE hierarchy (default)
const parentLink = <Link to=".." />;                   // up one route level (not necessarily ../)
const parentPathLink = <Link to=".." relative="path" />;   // up one URL segment instead
const absoluteLink = <Link to="/absolute" />;            // leading slash = from root
```

v6 changed the default: `to` values resolve against the **route hierarchy**, so moving route definitions around keeps links working. Use `relative="path"` only when you specifically want old-style URL-segment behavior.

## Code Examples

### Full Feature: Nested Dashboard With Guard, Loader, Action

```tsx
// router.tsx
import { createBrowserRouter, Outlet, Link, NavLink, isRouteErrorResponse, useRouteError, useNavigation } from "react-router";

export const router = createBrowserRouter([
  {
    id: "root",
    path: "/",
    element: <Root />,
    errorElement: <RootError />,
    children: [
      { path: "login", action: loginAction, element: <Login /> },
      {
        path: "projects",
        lazy: () => import("./routes/projects"), // code-split route modules
      },
    ],
  },
]);

function Root(): React.JSX.Element {
  const navigation = useNavigation();
  return (
    <div className={navigation.state !== "idle" ? "busy" : ""}>
      <nav>
        <NavLink to="/projects" className={({ isActive }) => isActive ? "active" : ""}>
          Projects
        </NavLink>
      </nav>
      <main>
        <Outlet />
      </main>
    </div>
  );
}

function RootError(): React.JSX.Element {
  const error = useRouteError();
  const message = isRouteErrorResponse(error)
    ? `${error.status} ${error.statusText}`
    : "Unexpected error";
  return <h1>{message}</h1>;
}
```

```tsx
// routes/projects.tsx — named route-object exports for Data Mode
import { useLoaderData, useFetcher } from "react-router";
import type { LoaderFunctionArgs, ActionFunctionArgs } from "react-router";
import { requireUser } from "../auth";

export async function loader(args: LoaderFunctionArgs) {
  await requireUser(args);
  return { projects: await listProjects() };
}

export async function action(args: ActionFunctionArgs) {
  await requireUser(args);
  const { request } = args;
  const fd = await request.formData();
  await renameProject(String(fd.get("id")), String(fd.get("name")));
  return { ok: true }; // triggers loader revalidation automatically
}

export function Component(): React.JSX.Element {
  const { projects } = useLoaderData<typeof loader>();

  return (
    <>
      <ul>
        {projects.map((p) => (
          <li key={p.id}>
            {p.name}
            <RenameButton project={p} />
          </li>
        ))}
      </ul>
    </>
  );
}

function RenameButton({ project }: { project: Project }): React.JSX.Element {
  const fetcher = useFetcher();
  return (
    <fetcher.Form method="post" action="/projects">
      {/* useFetcher = mutations WITHOUT navigation (inline actions) */}
      <input type="hidden" name="id" value={project.id} />
      <button name="name" value={`${project.name}-v2`}>Rename</button>
      {fetcher.state !== "idle" ? "Saving..." : null}
    </fetcher.Form>
  );
}
```

## Real-World Use Cases

### When Plain React Shops Choose RR Over Next.js

| Factor | React Router (SPA) | Next.js |
| -------------------- | ---------------------------------------------- | ----------------------------------------------------- |
| Existing backend API | Ideal — loaders call your API | Also fine, but RSC pushes server-side data access |
| SEO requirements | Limited (CSR unless you add prerendering) | First-class SSR/SSG/ISR |
| Hosting model | Static files + CDN, with API hosted separately | Server deployment or static export, within its limits |
| Team owns infra | Simple nginx/S3 deploys | Framework-managed runtime |
| App type | Dashboards, internal tools, embedded apps | Marketing sites, e-commerce, content |
| Bundle of concepts | Just routing + data loading | Routing + caching + server components + more |

Decision heuristic: authenticated product surface behind login → RR SPA is often simpler end-to-end; public pages whose traffic arrives from search → framework rendering wins.

### Other Patterns

- **Modal routes / detail panes**: render a child route inside a dialog while keeping background state (`useLocation().state.backgroundLocation` pattern).
- **Feature-flagged route trees**: build route arrays conditionally per entitlement.
- **Migration lever**: `lazy: () => import("./route")` gives code splitting per route module without a meta-framework.

## Common Mistakes

### 1. Using `component` Instead of `element` (or vice versa across versions)

```tsx
// BAD (v5 style, breaks in v6+):
const legacyRoute = <Route path="/" component={Home} />;

// GOOD:
const currentRoute = <Route path="/" element={<Home />} />;
```

### 2. Absolute Child Paths Breaking Nesting

```tsx
// BAD: an absolute child must include the combined parent path
const invalidRoute = { path: "settings", children: [{ path: "/profile" /* invalid path */ }] };

// GOOD: relative child paths nest under the parent
const nestedRoute = { path: "settings", children: [{ path: "profile" }] };
```

### 3. Loaders Without Error Elements

```typescript
// BAD: thrown 404 bubbles to root boundary, nuking whole page UX
if (!team) throw new Error("nope");

// GOOD: typed responses + scoped boundaries
if (!team) throw new Response("Not found", { status: 404 });
// ...and define errorElement at the segment that should recover
```

### 4. Fetching in useEffect Instead of Loaders

```tsx
// BAD: waterfall + spinner-in-place + no pending navigation state
useEffect(() => { fetchTeam(id).then(setTeam); }, [id]);

// GOOD: loader runs before render; useNavigation shows progress
```

### 5. Misreading Relative Links After Refactors

```tsx
// BAD assumption: ".." always means one URL segment
const implicitParent = <Link to=".." />;

// GOOD: be explicit about intent
const routeRelative = <Link to="../sibling" />;                 // route-relative
const pathRelative = <Link to="../sibling" relative="path" />; // URL-segment-relative
```

### 6. Guarding Only in Components

```tsx
// A render guard hides this subtree but cannot authorize server data
if (!user) return <Navigate to="/login" replace />;

// GOOD: loader throws redirect BEFORE the route renders
loader: (args) => requireUser(args); // may throw redirect(...)
```

## Best Practices

1. **Model auth and shared chrome as layout routes**, never per-page duplication.
2. **Throw `Response` objects with status codes** from loaders/actions; scope `errorElement` to the smallest recoverable segment.
3. **Use `useNavigation` for global pending UI** and `useFetcher` for inline mutations that should not navigate.
4. **Keep loaders thin**: orchestrate calls, delegate business rules to your API layer; loaders run on navigation hot paths.
5. **Prefer loader-based redirects over render-time `<Navigate>` guards.**
6. **Type loader data with `typeof myLoader`** on `useLoaderData` for end-to-end inference.
7. **Adopt `lazy` route modules** early — retrofitting code-splitting later touches every route definition.

## Performance Considerations

- Loaders declared as siblings execute **in parallel**; nested loaders wait for nothing except their own dependencies — but deep awaits serialize, so split critical vs slow data with an unresolved promise and `<Await>` in v7.
- `lazy` route modules shrink initial bundles; return slow data as promises to progressively reveal panels.
- Revalidation reruns all active loaders after actions; narrow it with `shouldRevalidate` when forms target unrelated slices.
- `useLocation().key` changes on every navigation — avoid putting it in dependency arrays unintentionally.

## Summary

- v6/v7 data routers bind a nested route tree to loaders, actions, and per-segment error boundaries via `createBrowserRouter` + `RouterProvider`.
- `<Outlet>` composes layouts; `index` routes fill parents; params flow through `useParams` and loader args.
- Required loader data is ready before the route commits; v7 uses promise fields with `<Await>` for slower data, and successful actions normally trigger revalidation.
- Loader guards control route UI; every protected loader/action and backend operation still needs its own access check.
- Relative links resolve against the route hierarchy by default — know `relative="path"` exists.
- Compare React Router Data Mode SPAs with Framework Mode or Next.js when server rendering is required.

## Revision Questions

**Definition**

1. **Q:** How does Data Mode differ from a declarative router or Framework Mode?
   **A:** Data Mode adds loaders, actions, and navigation state to a route tree. Declarative Mode supplies matching/navigation, while Framework Mode adds build and server-rendering conventions; this chapter's examples use v7 Data Mode.

**How It Works**

2. **Q:** Can a parent layout loader prevent a child loader from starting its request?
   **A:** No; matched loaders normally execute concurrently. Each protected data operation must check access itself, and the server API must authorize every request.

3. **Q:** What changed about deferred loader data between v6 and v7?
   **A:** V6 used `defer`; v7 returns an object containing an unresolved promise. Await critical data explicitly, then use `<Await>` beneath Suspense for the slower value.

4. **Q:** Why must a lazy Data Mode module export `Component` and `loader`?
   **A:** `route.lazy` supplies route-object fields from named exports. A default component with `clientLoader` belongs to different Framework Mode conventions and will not populate those fields here.

5. **Q:** What does `useFetcher` add when submitting an inline rename?
   **A:** It runs a route action and exposes its pending/data state while keeping the current location. A navigation form instead participates in a route navigation.

**Common Mistakes**

6. **Q:** Does an absolute child path escape its parent layout?
   **A:** No; it must include the parent's combined path to be valid and still belongs to that route branch. Relative child paths avoid that duplication.

7. **Q:** Is a browser-only `<Form>` sufficient to support disabled JavaScript?
   **A:** Only if the server independently handles its native submission target. Progressive enhancement in Framework Mode relies on server actions and rendered HTML; a client-only router cannot run without JavaScript.

**Performance Considerations**

8. **Q:** Why might `shouldRevalidate` improve performance but introduce stale data?
   **A:** It can skip a loader after a mutation, reducing requests. Skip only when the retained data is unaffected, and account for the error-response defaults of the installed router version.

# React Router v8 Data Mode

## Definition

**React Router** maps the current location to a nested route branch. In **Data Mode**, route objects also declare data reads (`loader`), mutations (`action`), pending navigation state, and route-level error UI. The router matches a URL, starts the matched loaders, then renders the branch with each child inserted at its parent's `<Outlet />`. These APIs organize client navigation and data work; they do not authorize access to the underlying resource.

> **Textbook Definition:** A client-side router resolves a location against a route configuration and coordinates the resulting UI branch and navigation lifecycle. React Router Data Mode extends that configuration with loaders, actions, pending state, error boundaries and data revalidation.

**Version boundary:** The examples use React Router v8 Data Mode. The current documentation identifies v8.4.0 as its latest release and requires Node 22.22+ and React/React DOM 19.2.7+; Framework Mode also requires Vite 7+. V8 removes the `react-router-dom` package: import `RouterProvider` from `react-router/dom` and the other APIs from `react-router`. See the [v7-to-v8 upgrade guide](https://reactrouter.com/upgrading/v7) before upgrading an existing app.

```text
ROUTE TREE → COMPONENT NESTING

createBrowserRouter([
 { path: "/",    element: <Root/>,        errorElement: <RootError/>,
   children: [
   { index: true, element: <Home/> },
   { path: "dashboard", element: <DashLayout/>, loader: dashLoader,
     children: [
     { path: "team/:id", element: <Team/>, loader: teamLoader },
     { path: "settings",  element: <Settings/> },
   ]},
 ]})

URL /dashboard/team/42 renders:

┌─ Root ─────────────────────────────┐
│  <Outlet/> →                       │
│  ┌─ DashLayout ──────────────────┐ │
│  │  <Outlet/> →                  │ │
│  │  ┌─ Team (params.id = 42) ──┐ │ │
│  │  │                          │ │ │
│  │  └──────────────────────────┘ │ │
│  └───────────────────────────────┘ │
└────────────────────────────────────┘

Matched loaders run in parallel; there is no deepest-first guarantee.
```


## First Principles

A copied URL should select the same route, and Back should restore a previous location. Route matching therefore needs a location owner rather than independent per-page visibility flags. A nested route also needs a place inside the retained layout; Outlet provides that child insertion point.

The selected page may need data before it can render. Declaring that requirement on the route lets the router start matched loads without waiting for each child to mount. It still cannot make sequential API dependencies parallel or decide server authorization.

## Why It Matters

A route tree can own the read, write and failure behavior for a URL, so navigation does not need each screen to invent its own fetching lifecycle. The router can start independent matched loaders together and expose pending navigation state. Calls that depend on one another still run sequentially, and authorization remains a server/API responsibility.

React Router has three modes. **Declarative Mode** handles matching and navigation; **Data Mode** adds route loaders, actions and pending state while leaving bundling and server integration to the application; **Framework Mode** adds route-module conventions, code splitting, type-safe route data and rendering strategies. Choose the mode by how much infrastructure and lifecycle work the application wants the router to own.

## How It Works

### Data Router Setup

```tsx
import {
  createBrowserRouter,
} from "react-router";
import { RouterProvider } from "react-router/dom";

const router = createBrowserRouter([
  {
    path: "/",
    element: <Root />,
    errorElement: <RootErrorBoundary />, // catches render AND loader/action errors
    children: [
      { index: true, element: <Home /> },
      {
        path: "dashboard",
        element: <DashboardLayout />,
        loader: dashboardLoader,
        children: [{ path: "team/:teamId", element: <Team />, loader: teamLoader }],
      },
      { path: "login", element: <Login />, action: loginAction },
    ],
  },
]);

export default function App(): React.JSX.Element {
  return <RouterProvider router={router} />;
}
```

In v8, import DOM-independent and route APIs from `"react-router"`, and use `"react-router/dom"` for the DOM-aware provider; that entry supplies React DOM's `flushSync`. V7 apps could still import re-exports from `"react-router-dom"`, but that package was removed in v8. Deferred loader data also changed: v6 used `defer`, while v7 and v8 return unresolved promises directly.

### Loaders and useLoaderData

```typescript
import type { LoaderFunctionArgs } from "react-router";

async function teamLoader({ params, request }: LoaderFunctionArgs) {
  const teamId = params.teamId;
  if (!teamId) throw new Response("Not Found", { status: 404 });
  const [team, members] = await Promise.all([
    fetchTeam(teamId, { signal: request.signal }),
    fetchMembers(teamId, { signal: request.signal }),
  ]);
  if (!team) {
    throw new Response("Not Found", { status: 404 }); // → nearest errorElement
  }
  return { team, members };
}

function Team(): React.JSX.Element {
  const { team, members } = useLoaderData<typeof teamLoader>(); // typed!
  return <Roster team={team} members={members} />;
}
```

For `/dashboard/team/42`, matching selects Root → DashboardLayout → Team. The matched dashboard and team loaders normally start concurrently. Each awaits its required data; successful results become loader data for that branch, which renders Team in the layout's Outlet. A Team failure goes to the nearest route error element instead of producing a partial success screen. `Promise.all` also makes the two team reads concurrent; it cannot parallelize one read that requires the other's result.

Pending states come from `useNavigation().state === "loading"`, enabling global spinners or skeleton routes without per-component bookkeeping. Pass `request.signal` to supported loader fetches so a superseded navigation can cancel client work. The router suppresses obsolete results, but cancelling a request does not undo a server mutation; version/idempotency rules still belong to the API. [Race and cancellation boundaries](https://reactrouter.com/explanation/race-conditions)

### Actions and Form Mutations

```tsx
import { Form, redirect, useActionData } from "react-router";
import type { ActionFunctionArgs } from "react-router";

async function loginAction({ request }: ActionFunctionArgs) {
  const formData = await request.formData();
  const email = formData.get("email");
  const password = formData.get("password");
  if (typeof email !== "string" || typeof password !== "string") {
    return { error: "Enter an email and password." };
  }
  const result = await api.login(email, password);
  if (!result.ok) return { error: "Invalid email or password." };
  return redirect("/dashboard");
}

function Login(): React.JSX.Element {
  const result = useActionData<typeof loginAction>();
  return (
    <Form method="post">           {/* POSTs to the route's action */}
      <input name="email" type="email" required />
      <input name="password" type="password" />
      <button type="submit">Sign in</button>
      {result?.error && <p role="alert">{result.error}</p>}
    </Form>
  );
}
```

Successful mutation actions trigger active loader revalidation by default. In v8 Data Mode, an action returning or throwing a 4xx/5xx response skips that default revalidation; returning `{ error }` with a successful status does not. `shouldRevalidate` can refine the default, but preserve `defaultShouldRevalidate` unless the route data is known to be unaffected.

In client-side Data Mode, `<Form>` intercepts the submission after the router is running. A no-JavaScript submission needs a server endpoint at the form URL or Framework Mode's server handling; the browser cannot execute a client-only route action by itself.

### Promise Data + Await (Progressive Loading)

V7 and v8 Data Mode loaders can return a promise for non-critical data; v6 used `defer`. A promise placed in a returned object is **not automatically awaited** just because its key is named `critical`:

```tsx
import { Await, useLoaderData } from "react-router";
import { Suspense } from "react";

export async function loader() {
  const suggestions: Promise<Suggestion[]> = getSuggestionsSlow();
  // Handle an early rejection; Await still receives the original promise.
  void suggestions.catch(() => {});
  const critical = await getDashboardStats();
  return { critical, suggestions }; // only suggestions is still a promise
}

function Dashboard(): React.JSX.Element {
  const { critical, suggestions } = useLoaderData<typeof loader>();
  return (
    <>
      <Stats data={critical} />
      <Suspense fallback={<Skeleton rows={3} />}>
        <Await resolve={suggestions} errorElement={<RetryPrompt />}>
          {(items) => <List items={items} />}
        </Await>
      </Suspense>
    </>
  );
}
```

The router waits for the loader's critical work before committing this navigation. The slow panel then fills in as its promise settles. The early rejection handler prevents an unhandled rejection while critical data loads; `<Await>` still receives the rejected original promise and renders its error UI. This is client-side Data Mode loading: returning a promise does not configure document-level HTML streaming. Framework Mode or a custom server integration must coordinate streamed loader data with React's server renderer.

### Protected Routes

A loader can redirect before protected route content mounts. Because parent and child loaders run in parallel, a layout redirect does not stop a child from starting; protect each data operation and authorize requests at the server:

```typescript
import { Outlet, redirect, useLoaderData } from "react-router";
import type { LoaderFunctionArgs } from "react-router";

async function appLoader({ request }: LoaderFunctionArgs) {
  // In Data Mode, this helper calls an API that verifies the session server-side.
  const user = await getCurrentUser({ signal: request.signal });
  if (!user) {
    const to = new URL("/login", request.url);
    to.searchParams.set("from", new URL(request.url).pathname);
    throw redirect(to.toString());
  }
  return { user };
}

// This guards the layout UI; children must protect their own data.
const appRoute = {
  id: "app",
  path: "app",
  loader: appLoader,
  element: <AppShell />,
};

function AppShell(): React.JSX.Element {
  const { user } = useLoaderData<typeof appLoader>();
  return <><header>Signed in as {user.email}</header><Outlet /></>;
}
```

A `<ProtectedRoute><Comp/></ProtectedRoute>` wrapper using `<Navigate>` still appears in older codebases. A loader can redirect before the route renders, but a client-side redirect is only navigation behavior: the API must authorize every protected read and write. In Framework Mode, keep session access in server-only code; do not import secrets or trust a client loader as a security boundary.

### Core Hooks

| Hook | Use |
| ------------------------ | ---------------------------------------------------------------- |
| `useParams()` | Read dynamic path segments |
| `useNavigate()` | Navigate programmatically; Data/Framework Mode returns a promise |
| `useLocation()` | Read pathname, search, hash, navigation state and entry key |
| `useSearchParams()` | Read/write query parameters through navigation |
| `useNavigation()` | Observe `idle`, `loading`, or `submitting` |
| `useRouteLoaderData(id)` | Read the matched route loader identified by its explicit ID |

### Relative Routing Rules

```tsx
const childLink = <Link to="details" />;                 // relative to ROUTE hierarchy (default)
const parentLink = <Link to=".." />;                      // up one path-contributing route
const parentPathLink = <Link to=".." relative="path" />; // up one URL segment instead
const absoluteLink = <Link to="/absolute" />;             // leading slash = from root
```

Since v6, relative `to` values resolve against the **route hierarchy** by default, so moving route definitions can preserve links. `..` removes one path-contributing route, which may contain several URL segments. Use `relative="path"` only when the intended operation is one URL-segment step.

## Code Examples

### Compose a guarded projects route, loader and action

The following modules show composition; `api`, `Project`, `listProjects`, `renameProject`, Login and its action are application-specific implementations. Validate submitted fields and authorize the particular project at the API, and pass cancellation signals for reads.

```tsx
// router.tsx
import { createBrowserRouter, Outlet, Link, NavLink, isRouteErrorResponse, useRouteError, useNavigation } from "react-router";

export const router = createBrowserRouter([
  {
    id: "root",
    path: "/",
    element: <Root />,
    errorElement: <RootError />,
    children: [
      { path: "login", action: loginAction, element: <Login /> },
      {
        path: "projects",
        lazy: () => import("./routes/projects"), // code-split route modules
      },
    ],
  },
]);

function Root(): React.JSX.Element {
  const navigation = useNavigation();
  return (
    <div className={navigation.state !== "idle" ? "busy" : ""}>
      <nav>
        <NavLink to="/projects" className={({ isActive }) => isActive ? "active" : ""}>
          Projects
        </NavLink>
      </nav>
      <main>
        <Outlet />
      </main>
    </div>
  );
}

function RootError(): React.JSX.Element {
  const error = useRouteError();
  const message = isRouteErrorResponse(error)
    ? `${error.status} ${error.statusText}`
    : "Unexpected error";
  return <h1>{message}</h1>;
}
```

```tsx
// routes/projects.tsx — named route-object exports for Data Mode
import { useLoaderData, useFetcher } from "react-router";
import type { LoaderFunctionArgs, ActionFunctionArgs } from "react-router";
import { requireUser } from "../auth";

export async function loader(args: LoaderFunctionArgs) {
  await requireUser(args);
  return { projects: await listProjects() };
}

export async function action(args: ActionFunctionArgs) {
  await requireUser(args);
  const { request } = args;
  const fd = await request.formData();
  await renameProject(String(fd.get("id")), String(fd.get("name")));
  return { ok: true }; // triggers loader revalidation automatically
}

export function Component(): React.JSX.Element {
  const { projects } = useLoaderData<typeof loader>();

  return (
    <>
      <ul>
        {projects.map((p) => (
          <li key={p.id}>
            {p.name}
            <RenameButton project={p} />
          </li>
        ))}
      </ul>
    </>
  );
}

function RenameButton({ project }: { project: Project }): React.JSX.Element {
  const fetcher = useFetcher();
  return (
    <fetcher.Form method="post" action="/projects">
      {/* useFetcher = mutations WITHOUT navigation (inline actions) */}
      <input type="hidden" name="id" value={project.id} />
      <button name="name" value={`${project.name}-v2`}>Rename</button>
      {fetcher.state !== "idle" ? "Saving..." : null}
    </fetcher.Form>
  );
}
```

## Real-World Use Cases

### Choose by rendering and control requirements

| Requirement | React Router Data Mode | React Router Framework Mode |
| -------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| Route model | Explicit route objects configured by the app | Route modules and framework conventions |
| Data lifecycle | Loaders/actions; app owns bundling and server integration | Loaders/actions plus generated route types and automatic code splitting |
| Rendering | Client rendering unless the app adds server integration | SPA, SSR or static rendering strategies |
| Control | More control over server, build and deployment | More router-managed infrastructure |

Compare those requirements with Next.js or another framework in the context of the actual deployment, server capabilities, SEO needs and team ownership. A dashboard does not inherently require an SPA, and public content does not automatically require a particular framework.

### Other Patterns

- **Modal routes / detail panes**: render a child route inside a dialog while keeping background state (`useLocation().state.backgroundLocation` pattern).
- **Feature-flagged route trees**: build route arrays conditionally per entitlement.
- **Migration lever**: `lazy: () => import("./route")` gives code splitting per route module without a meta-framework.

## Common Mistakes

### 1. Confusing v5 JSX props with current route-object fields

```tsx
// BAD: `component` was the v5 JSX prop and is not the current <Route> prop.
const legacyRoute = <Route path="/" component={Home} />;

// GOOD in JSX route declarations:
const currentRoute = <Route path="/" element={<Home />} />;

// GOOD in a v8 Data Mode route object:
const dataRoute = { path: "/", Component: Home };
```

`element` is also valid on route objects. The distinction is API shape: JSX `<Route>` takes an `element` value; a route object can use `Component` (or `element`).

### 2. Absolute Child Paths Breaking Nesting

```tsx
// BAD: an absolute child must include the combined parent path
const invalidRoute = { path: "settings", children: [{ path: "/profile" /* invalid path */ }] };

// GOOD: relative child paths nest under the parent
const nestedRoute = { path: "settings", children: [{ path: "profile" }] };
```

### 3. Loaders Without Error Elements

```typescript
// BAD: without a closer boundary, the 404 reaches the root route boundary
if (!team) throw new Error("nope");

// GOOD: a status-bearing response + a scoped route boundary
if (!team) throw new Response("Not found", { status: 404 });
// ...and define errorElement at the segment that should recover
```

### 4. Fetching in useEffect Instead of Loaders

```tsx
// BAD for navigation-critical data: the route renders before this Effect finishes
useEffect(() => { fetchTeam(id).then(setTeam); }, [id]);

// Loader: coordinate the read with route matching and expose navigation state
```

### 5. Misreading Relative Links After Refactors

```tsx
// BAD assumption: ".." always means one URL segment
const implicitParent = <Link to=".." />;

// GOOD: be explicit about intent
const routeRelative = <Link to="../sibling" />;                 // route-relative
const pathRelative = <Link to="../sibling" relative="path" />; // URL-segment-relative
```

### 6. Guarding Only in Components

```tsx
// A render guard hides this subtree but cannot authorize server data
if (!user) return <Navigate to="/login" replace />;

// GOOD: loader throws redirect BEFORE the route renders
loader: (args) => requireUser(args); // may throw redirect(...)
```

## Best Practices

1. **Model auth and shared chrome as layout routes**, never per-page duplication.
2. **Throw `Response` objects with status codes** from loaders/actions; scope `errorElement` to the smallest recoverable segment.
3. **Use `useNavigation` for global pending UI** and `useFetcher` for inline mutations that should not navigate.
4. **Keep loaders thin**: orchestrate calls, delegate business rules to your API layer; loaders run on navigation hot paths.
5. **Prefer loader-based redirects over render-time `<Navigate>` guards**, while keeping authorization at the server/API boundary.
6. **Type loader data with `typeof myLoader`** on `useLoaderData` in Data Mode; Framework Mode provides generated route-module types.
7. **Split routes where bundle measurements justify it**; route-level laziness is a code-loading decision, not a requirement for every route.

## Performance Considerations

- Matched loaders run concurrently, including parent and child loaders; only dependencies inside a loader serialize. Use `<Await>` for non-critical promises when progressive content is useful.
- Lazy route modules can reduce initial JavaScript at the cost of another module load; verify the route is a meaningful part of the bundle before splitting.
- Successful actions revalidate active loader data by default. In Data Mode, 4xx/5xx action responses skip default revalidation; customize `shouldRevalidate` only when a route's data is unaffected, and retain `defaultShouldRevalidate` for cases you do not handle.
- `useLocation().key` identifies a history entry; Back can restore an earlier key, while a new entry normally has a new key — depend on it only when entry identity is the intended input.

## Summary

- v8 Data Mode binds a nested route tree to loaders, actions, pending navigation and route-level error UI via `createBrowserRouter` + `RouterProvider`.
- `<Outlet>` composes layouts; `index` routes fill parents; params flow through `useParams` and loader args.
- Required loader data is ready before the route commits. Return a promise for non-critical data and render it through `<Await>` inside `<Suspense>`; this alone does not configure server HTML streaming.
- Successful actions revalidate active data by default; failed 4xx/5xx responses do not in v8 Data Mode. A successful-status `{ error }` result still counts as success.
- A loader redirect can control route navigation, but every protected API operation must authorize on the server.
- Relative links resolve against route hierarchy by default; use `relative="path"` when one URL segment is the intended unit.
- Choose Declarative, Data or Framework Mode by the routing, data, rendering and infrastructure contracts the application needs.

# Portals

A menu belongs to a card, but the card clips anything that extends beyond its edge. Moving the menu into a second React root avoids the clipping, but also separates it from the state and context that own it. A portal changes the DOM destination while keeping the component in its original React tree.

```tsx
import { createPortal } from "react-dom";

function CardMenu() {
  return createPortal(
    <ul role="menu"><li role="menuitem">Rename</li></ul>,
    document.body, // DOM destination…
  );
  // …but state, context, and synthetic events still belong to the card.
}
```

## Definition

**Practical definition:** A portal renders React children into a DOM node outside their parent’s DOM subtree while retaining the same React owner, state and context. It changes placement without creating a new React root.

> **Textbook Definition:** A portal is a React rendering mechanism that places a subtree into a different host container without creating a separate React root. React ancestry continues to govern context and synthetic event propagation; DOM ancestry governs layout and native event paths.

## First Principles

The menu needs the card’s state and context, but it cannot stay in a DOM region that clips it. A separate React root would solve placement by breaking that ownership. A portal keeps the logical owner and changes only where React inserts the host nodes, so two ancestry paths must be considered.

## 1. Keep Ownership; Change Placement

React maintains a logical component tree and commits its host nodes into a DOM tree. A portal splits those relationships at one point:

```text
React tree                       DOM tree
App                              body
└── ProjectCard                  ├── #root
    └── Menu                     │   └── ProjectCard DOM
                                 └── #overlay-root
                                     └── Menu DOM
```

The card still owns the menu’s state and context. CSS layout, native event propagation and focus order follow the menu’s actual DOM position. This is why a portal can escape an ancestor’s `overflow: hidden` or stacking context without becoming an independent application.

## 2. Choose a Stable Destination

Use a portal when the current DOM ancestry causes a real clipping or stacking problem. Keep the destination outside that ancestor and stable for the lifetime of the overlay. A changed container makes React recreate the portal subtree, which can reset child state and focus.

For a client-rendered overlay, an effect can obtain the destination after the first commit:

```tsx
import { useEffect, useState, type ReactNode } from "react";
import { createPortal } from "react-dom";

function OverlayPortal({ children }: { children: ReactNode }) {
  const [destination, setDestination] = useState<HTMLElement | null>(null);

  useEffect(() => {
    setDestination(document.body);
  }, []);

  return destination ? createPortal(children, destination) : null;
}
```

The server and the client’s first render both return `null`; the overlay appears after hydration. This is appropriate for browser-only overlays, but it does not server-render their contents. Do not read `document` or append nodes during render. If an application creates its own destination, create it in an effect and remove that same node in the effect cleanup. A destination supplied by the host belongs to the host and must not be removed by the portal component.

A portal does not automatically reach the browser’s top layer. If a native dialog meets the interaction and styling requirements, `<dialog>.showModal()` already enters that layer and may remove the need for a custom portal. Otherwise, select the destination and its stacking rules deliberately.

## 3. Follow Both Event Paths

A click in a portaled menu bubbles through its React ancestors, even when those ancestors are absent from the DOM event path. A native listener on the original card does not receive that click. A document listener can receive it through the real DOM path.

If a button handler logs `"menu"` and its logical React parent logs `"card"`, clicking once logs the menu entry followed by the card entry. A native listener attached to the card’s DOM node sees neither event because the portaled button is not its DOM descendant.

This distinction affects dismissal logic. An outside-click handler must treat both the trigger and the portaled surface as inside; checking only the trigger’s DOM subtree can close the menu before its item handler runs. Use refs to those two nodes rather than assuming the original parent contains both.

## 4. Placement Does Not Provide Interaction Behavior

A portal can position a modal, tooltip, menu or notification outside a clipped region. It does not implement the component’s interaction contract. A modal still needs an accessible name, a focus entry point, focus containment and restoration, background interaction control, and a clear dismissal policy. A tooltip needs a relationship from its trigger and must remain available to pointer and keyboard users. A menu or listbox needs the keyboard and selection behavior of that specific widget.

Passive notifications should use an appropriate live region and should not move focus. For complicated overlays, prefer a tested accessible primitive over a hand-built portal wrapper.

A document-level query can still find a portaled node; a query scoped to the old parent cannot. Likewise, a destination rendered by a sibling React component in the same initial tree does not exist until that tree commits. Supply a stable host node or wait until after commit before rendering the portal.

## Summary

Use a portal when DOM placement is the problem. React context and synthetic events follow the original component tree, while CSS and native events follow the destination tree. Keep the destination stable, handle server rendering deliberately, and implement focus, keyboard and dismissal behavior separately.

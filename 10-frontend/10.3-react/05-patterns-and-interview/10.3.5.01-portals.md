# Portals

## Definition

**Portals** are a first-class React mechanism for rendering a component's children into a chosen DOM container, often outside the parent's DOM subtree. While the portal content renders elsewhere in the DOM, it remains within the React component tree — meaning context, props, and event bubbling behave as if the portal were still a child of the parent component. Portals are created using `ReactDOM.createPortal(child, container)`.

> **Textbook Definition:** A portal renders children into a separate host container while preserving their position in the React tree. Context and React event propagation follow that logical tree, while layout and native DOM relationships follow the host tree.


## First Principles

An overlay may belong to a card's state while needing a DOM parent outside that card's clipping boundary. Moving the whole component into a separate React root would also change its context and event ownership. A portal therefore changes host placement while retaining logical ownership.

Those two ancestries create two separate responsibilities. React supplies the state/context path; the DOM supplies positioning, native event paths and focus order. Placement cannot supply a modal's keyboard or background-interaction policy.

## When the logical parent is the wrong DOM parent

A menu inside an `overflow: hidden` card may be clipped even when its z-index is large. Rendering that menu into a suitable outer container changes its DOM ancestry while its React parent still supplies context and receives bubbling React events. Check the destination's stacking and layout rules; a portal does not automatically enter the browser top layer.

Common placement problems:

1. **Z-index stacking contexts** — Choose an unclipped overlay destination, then manage stacking; placement alone does not outrank every element or the browser top layer
2. **Overflow clipping** — Escape parent containers with `overflow: hidden` or `clip-path`
3. **CSS transform interference** — Avoid fixed positioning breaking inside transformed parents
4. **Separate scroll containers** — Render notifications/banners outside main scrollable areas
5. **Third-party widget isolation** — Embed widgets in specific DOM nodes without component coupling

## How It Works

### Context follows React; clipping follows DOM ancestry

```text
React tree                  DOM tree
App                         body
└── Main                    ├── #root
    └── Modal               │   └── Main's DOM
                            └── #modal-root
                                └── Modal's DOM
```

`Main` remains the modal's logical React parent. The chosen DOM container must already exist when `createPortal` runs. If that container changes on an update, React recreates the portal content rather than transporting the same retained subtree between containers.

### Moving the container does not move React event ancestry

```text
Event Bubbling:
═══════════════════════════════════════════════════════════════

Even though the Portal renders in a different DOM node,
React handlers propagate through the React component tree.
Native DOM listeners still follow the actual DOM event path.

┌────────────────────────────────────────────────────┐
│ Click inside Modal:                                │
│                                                    │
│ 1. Click event fires on <button> inside portal DOM │
│ 2. Event bubbles DOM-wise (within #modal-root div) │
│ 3. React intercepts and translates to React tree:  │
│ Modal → ModalPortal → Main → App                   │
│ 4. onClick on <div id="app"> catches it            │
│                                                    │
│ If <div id="app"> has onClick, it WILL fire        │
│ even though modal is NOT nested in the DOM there   │
└────────────────────────────────────────────────────┘

```

## Code Examples

### 1. Basic Portal

This first adapter is browser-only and assumes the chosen target already exists. Use the client-only or owned-container adapter below for server rendering.

```typescript
import { createPortal } from 'react-dom';

interface PortalProps {
  children: React.ReactNode;
  container?: Element | DocumentFragment;
}

const Portal = ({ children, container }: PortalProps) => {
  const mountNode = container ?? document.body;
  return createPortal(children, mountNode);
};

// Usage
const App = () => {
  return (
    <div>
      <h1>My App</h1>
      <Portal>
        <div className="toast">This renders in document.body</div>
      </Portal>
    </div>
  );
};
```

### 2. Modal Component

```typescript
import { createPortal } from 'react-dom';
import { useEffect, useRef, useState } from 'react';

interface ModalProps {
  isOpen: boolean;
  onClose: () => void;
  children: React.ReactNode;
  title?: string;
}

const Modal = ({ isOpen, onClose, children, title }: ModalProps) => {
  const overlayRef = useRef<HTMLDivElement>(null);

  // Placement/scroll demonstration: production dialogs also need focus management.
  // Close on Escape key
  useEffect(() => {
    const handleEsc = (e: KeyboardEvent) => {
      if (e.key === 'Escape') onClose();
    };

    if (!isOpen) return;
    const previousOverflow = document.body.style.overflow;
    document.addEventListener('keydown', handleEsc);
    document.body.style.overflow = 'hidden';

    return () => {
      document.removeEventListener('keydown', handleEsc);
      document.body.style.overflow = previousOverflow;
    };
  }, [isOpen, onClose]);

  if (!isOpen) return null;

  return createPortal(
    <div
      ref={overlayRef}
      className="modal-overlay"
      onClick={(e) => {
        if (e.target === overlayRef.current) onClose();
      }}
      role="dialog"
      aria-modal="true"
      aria-label={title}
    >
      <div className="modal-content">
        <div className="modal-header">
          {title && <h2>{title}</h2>}
          <button type="button" onClick={onClose} aria-label="Close">
            &times;
          </button>
        </div>
        <div className="modal-body">{children}</div>
      </div>
    </div>,
    document.getElementById('modal-root') ?? document.body
  );
};

// Usage
const App = () => {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setIsOpen(true)}>Open Modal</button>
      <Modal
        isOpen={isOpen}
        onClose={() => setIsOpen(false)}
        title="Confirm Action"
      >
        <p>Are you sure you want to proceed?</p>
        <button onClick={() => setIsOpen(false)}>Confirm</button>
      </Modal>
    </div>
  );
};
```

This modal is a placement example, not a complete accessible dialog. Supply initial focus, focus trapping/restoration, a non-empty accessible name, and background inertness using the [focus-management chapter](../../../50-quality/50.2-accessibility/50.2.03-keyboard-navigation.md). Multiple simultaneous dialogs also need shared scroll-lock ownership.

### 3. Tooltip with Portal

This is a position-calculation sketch. An accessible tooltip also needs a stable ID referenced by the actual trigger's `aria-describedby`, Escape dismissal and a hover/focus persistence policy; a wrapper receiving focus events alone does not supply that relationship. Use the accessibility chapter or an established overlay primitive for those behaviors. Measure before paint when an initial jump is visible, and handle viewport collisions when the proposed position falls offscreen.

```typescript
import { createPortal } from 'react-dom';
import { useState, useRef, useEffect, useCallback } from 'react';

interface TooltipProps {
  text: string;
  children: React.ReactNode;
  position?: 'top' | 'bottom' | 'left' | 'right';
}

const Tooltip = ({ text, children, position = 'top' }: TooltipProps) => {
  const [isVisible, setIsVisible] = useState(false);
  const [tooltipPos, setTooltipPos] = useState({ top: 0, left: 0 });
  const triggerRef = useRef<HTMLDivElement>(null);

  const calculatePosition = useCallback(() => {
    const trigger = triggerRef.current;
    if (!trigger) return;

    const rect = trigger.getBoundingClientRect();
    const offset = 8; // Gap between trigger and tooltip

    const positions = {
      top: { top: rect.top - offset, left: rect.left + rect.width / 2 },
      bottom: { top: rect.bottom + offset, left: rect.left + rect.width / 2 },
      left: { top: rect.top + rect.height / 2, left: rect.left - offset },
      right: { top: rect.top + rect.height / 2, left: rect.right + offset },
    };

    setTooltipPos(positions[position]);
  }, [position]);

  useEffect(() => {
    if (isVisible) calculatePosition();
  }, [isVisible, calculatePosition]);

  useEffect(() => {
    const handleResize = () => { if (isVisible) calculatePosition(); };
    window.addEventListener('resize', handleResize);
    window.addEventListener('scroll', handleResize, true);
    return () => {
      window.removeEventListener('resize', handleResize);
      window.removeEventListener('scroll', handleResize, true);
    };
  }, [isVisible, calculatePosition]);

  return (
    <>
      <div
        ref={triggerRef}
        onMouseEnter={() => setIsVisible(true)}
        onMouseLeave={() => setIsVisible(false)}
        onFocus={() => setIsVisible(true)}
        onBlur={() => setIsVisible(false)}
        style={{ display: 'inline-block' }}
      >
        {children}
      </div>

      {isVisible && createPortal(
        <div
          role="tooltip"
          style={{
            position: 'fixed',
            top: tooltipPos.top,
            left: tooltipPos.left,
            transform: {
              top: 'translate(-50%, -100%)',
              bottom: 'translate(-50%, 0)',
              left: 'translate(-100%, -50%)',
              right: 'translate(0, -50%)',
            }[position],
            zIndex: 9999,
            backgroundColor: '#333',
            color: '#fff',
            padding: '4px 8px',
            borderRadius: 4,
            fontSize: 12,
            pointerEvents: 'none',
            whiteSpace: 'nowrap',
          }}
        >
          {text}
        </div>,
        document.body
      )}
    </>
  );
};

// Usage
const App = () => (
  <div style={{ overflow: 'hidden' }}>
    {/* Tooltip escapes overflow:hidden via portal */}
    <Tooltip text="This tooltip can overflow its parent">
      <button>Hover me</button>
    </Tooltip>
  </div>
);
```

### 4. Dropdown Menu (Escape Clipping)

This demonstrates placement and outside-click ownership, not a full menu/listbox keyboard contract. The actual trigger needs a button, accessible expanded/control relationships and keyboard opening; the contents need the semantics and focus rules of the chosen widget type.

```typescript
import { createPortal } from 'react-dom';
import { useState, useRef, useEffect, useCallback } from 'react';

interface DropdownMenuProps {
  trigger: React.ReactNode;
  children: React.ReactNode;
}

const DropdownMenu = ({ trigger, children }: DropdownMenuProps) => {
  const [isOpen, setIsOpen] = useState(false);
  const [menuPos, setMenuPos] = useState({ top: 0, left: 0, width: 0 });
  const triggerRef = useRef<HTMLDivElement>(null);
  const menuRef = useRef<HTMLDivElement>(null);

  const updatePosition = useCallback(() => {
    const trigger = triggerRef.current;
    if (!trigger) return;

    const rect = trigger.getBoundingClientRect();
    setMenuPos({
      top: rect.bottom,
      left: rect.left,
      width: rect.width,
    });
  }, []);

  // Close on outside click
  useEffect(() => {
    if (!isOpen) return;

    const handleClick = (e: MouseEvent) => {
      const target = e.target as Node;
      if (triggerRef.current?.contains(target) || menuRef.current?.contains(target)) return;
      setIsOpen(false);
    };

    document.addEventListener('mousedown', handleClick);
    return () => document.removeEventListener('mousedown', handleClick);
  }, [isOpen]);

  // Recalculate position on scroll/resize
  useEffect(() => {
    if (!isOpen) return;
    window.addEventListener('scroll', updatePosition, true);
    window.addEventListener('resize', updatePosition);
    return () => {
      window.removeEventListener('scroll', updatePosition, true);
      window.removeEventListener('resize', updatePosition);
    };
  }, [isOpen, updatePosition]);

  return (
    <>
      <div ref={triggerRef} onClick={() => { updatePosition(); setIsOpen(prev => !prev); }}>
        {trigger}
      </div>

      {isOpen && createPortal(
        <div
          ref={menuRef}
          style={{
            position: 'fixed',
            top: menuPos.top,
            left: menuPos.left,
            width: menuPos.width,
            zIndex: 1000,
            backgroundColor: '#fff',
            border: '1px solid #ddd',
            borderRadius: 4,
            boxShadow: '0 4px 12px rgba(0,0,0,0.15)',
          }}
        >
          {children}
        </div>,
        document.body
      )}
    </>
  );
};
```

### 5. Notification Toast System

Use the basic portal to place an app-level notification region beside the document root. A toast provider owns the list and exposes an `addToast` action through context; each expiration removes the matching ID. Track timer handles and clear them when the provider unmounts. A module-global callback instead couples every mounted application to one mutable singleton and can silently target the wrong root.

Use an appropriate live region for announcements and avoid stealing focus for passive notifications. Placement, dismissal timing, and announcement behavior are separate responsibilities.

### 6. Portal with Context Propagation

```typescript
import { createPortal } from 'react-dom';
import { createContext, useContext, useState } from 'react';

// Theme context — will propagate THROUGH portal
const ThemeContext = createContext('light');

const ThemeProvider = ({ children }: { children: React.ReactNode }) => {
  const [theme] = useState('dark');
  return (
    <ThemeContext.Provider value={theme}>
      {children}
    </ThemeContext.Provider>
  );
};

const PortalContent = () => {
  // Context works inside portal because React tree position matters
  const theme = useContext(ThemeContext);
  return <div className={theme}>Portal content (theme: {theme})</div>;
};

const App = () => {
  const portalContainer = document.getElementById('portal-root')!;

  return (
    <ThemeProvider>
      <div className="app">
        <p>App content</p>
        {/* PortalContent gets ThemeContext from ThemeProvider */}
        {createPortal(<PortalContent />, portalContainer)}
      </div>
    </ThemeProvider>
  );
};
```

### 7. Portal with Event Bubbling

```typescript
import { createPortal } from 'react-dom';
import { useState } from 'react';

const App = () => {
  const [clicks, setClicks] = useState<string[]>([]);

  const handleDivClick = (source: string) => {
    setClicks(prev => [...prev, `div clicked: ${source}`]);
  };

  const handlePortalClick = () => {
    setClicks(prev => [...prev, 'portal clicked']);
  };

  return (
    // Even though portal renders in document.body,
    // clicks bubble up through THIS div in the React tree
    <div onClick={() => handleDivClick('outer div')}>
      <h1>Event Bubbling Demo</h1>

      {createPortal(
        <button onClick={handlePortalClick}>
          Click me (portal)
        </button>,
        document.body
      )}

      <div>
        {clicks.map((msg, i) => (
          <p key={i}>{msg}</p>
        ))}
      </div>
    </div>
  );
};
```

Click the portaled button once: its own handler queues “portal clicked”, then the logical ancestor handler queues “div clicked: outer div”. Functional updates compose those log entries. A native listener on that outer div does not receive this click because the button is outside its DOM subtree; a document-level native listener can receive it along the real path. Stopping propagation intentionally changes which handlers run.

### 8. Multi-Root Portals

For independent destinations, place stable targets in the host HTML **before mounting React**:

```html
<div id="root"></div>
<div id="modal-root"></div>
<div id="tooltip-root"></div>
<div id="notification-root"></div>
```

Use the basic `Portal` with an explicit `container` for each destination. A `<PortalRoots />` sibling in the same first render has not committed yet, so `document.getElementById` would return `null` at that point. If React must create the target, obtain it after commit through a ref/effect before rendering the portal.

### 9. SSR-Safe Portal

```typescript
import { createPortal } from 'react-dom';
import { useEffect, useState } from 'react';

const ClientOnlyPortal = ({
  children,
  selector,
}: {
  children: React.ReactNode;
  selector: string;
}) => {
  const [mounted, setMounted] = useState(false);

  useEffect(() => {
    setMounted(true);
  }, []);

  if (!mounted) return null; // Don't render on server

  const container = document.querySelector(selector);
  if (!container) return null;

  return createPortal(children, container);
};

// Usage — safe for SSR/SSG
const Modal = () => (
  <ClientOnlyPortal selector="#modal-root">
    <div className="modal">Content</div>
  </ClientOnlyPortal>
);
```

### 10. A Portal That Owns Its Container

Reading `document` or appending nodes in `useMemo` performs DOM work during render and fails server rendering. Create an owned container in an effect instead:

```tsx
import { createPortal } from 'react-dom';
import { useEffect, useState } from 'react';

function OwnedPortal({ children }: { children: React.ReactNode }) {
  const [container, setContainer] = useState<HTMLDivElement | null>(null);

  useEffect(() => {
    const element = document.createElement('div');
    document.body.appendChild(element);
    setContainer(element);
    return () => { element.remove(); };
  }, []);

  return container ? createPortal(children, container) : null;
}
```

The server and initial client render both return `null`, then the effect adds the destination. Each instance removes only its own node; an existing application-owned target should be used without removing it during cleanup.

## Real-World Use Cases

| Use Case | Portal Reason | DOM Target |
| ----------------------- | ------------------------------------------------- | ---------------------------------- |
| **Modal/Dialog** | Z-index stacking, overflow escape | `#modal-root` |
| **Tooltip** | Overflow hidden, CSS transform | `#tooltip-root` or `document.body` |
| **Dropdown Menu** | Overflow hidden, scroll containers | `document.body` |
| **Toast/Notification** | Fixed position, stacking | `#notification-root` |
| **Context Menu** | Position at cursor in a suitable stacking context | `document.body` |
| **DatePicker/Select** | Escape card/grid clipping | `#overlay-root` |
| **Side Panel / Drawer** | Separate scroll, z-index | `#drawer-root` |
| **Loading Bar (top)** | Outside app layout structure | `document.body` |

## Common Mistakes

### 1. Creating Containers During Render

Appending a node while rendering leaks it if that render is abandoned; changing only a ref inside an effect also does not trigger a render to reveal the portal. Use the state-backed owned-container example above, and remove only nodes that instance created.

### 2. Assuming DOM Position = Z-Index Order

```typescript
// BAD: Relying on DOM position for z-index
// Portal renders in document.body, not where you expect

// GOOD: Manage z-index explicitly
const Modal = () => (
  createPortal(
    <div style={{ position: 'fixed', zIndex: 1000 }}> {/* Target stacking still matters. */}
      Modal content
    </div>,
    document.body
  )
);
```

### 3. Breaking Event Bubbling Unexpectedly

A portal button still reaches React ancestor handlers. Stop propagation only at the boundary that should consume that interaction; moving the DOM target does not isolate it. See example 7 for the complete bubbling demonstration.

### 4. Querying Only the Original Parent

`document.querySelector('.portal-btn')` can find portaled content normally. A query scoped to the original parent's DOM cannot find a descendant rendered elsewhere. Refs and callbacks are useful for targeting a particular instance without relying on a document-wide selector.

## Best Practices

1. **Choose a stable target** — Declare it in host HTML, obtain it after commit, or create an owned container in an effect
2. **Manage z-index explicitly** — Don't rely on DOM position for stacking
3. **Clean up portals on unmount** — Remove dynamically created containers
4. **Provide accessible attributes** — `role="dialog"`, `aria-modal`, focus trapping
5. **Measure layout/paint before adding containment** — Paint containment can clip overlays; it is not a default portal optimization
6. **Close on Escape key** — Add keyboard handling for modals/dialogs
7. **Prevent body scroll** — Set `overflow: hidden` when modal is open
8. **SSR safety** — Return matching initial server/client markup; obtain DOM targets in an effect before rendering client-only overlays
9. **Choose roots by ownership and stacking needs** — one shared overlay root or separate roots can both work
10. **Test event bubbling** — Understand React tree vs DOM tree behavior

## Performance Considerations

| Aspect | Impact | Mitigation |
| -------------------- | ----------------------------------- | ---------------------------------------------------------------------- |
| **Portal creation** | Minimal overhead | Pre-create containers once |
| **Event delegation** | Normal bubbling | No special perf concern |
| **Re-renders** | Portals re-render with parent | `React.memo` for heavy portal content |
| **CSS containment** | Can change clipping and positioning | Measure and verify overlay behavior before enabling |
| **Reflows** | Same document layout system | Avoid repeated layout reads/writes; placement alone gives no isolation |

## Summary

Portals allow rendering components outside the parent DOM tree while preserving React context and event bubbling. They are essential for modals, tooltips, dropdowns, and notifications that need to escape CSS clipping, overflow, or z-index constraints. Always manage z-index explicitly, clean up dynamically created containers, and provide proper accessibility attributes.

# Compound Components

A tab widget needs several pieces to agree on one selected value, even when a product team arranges those pieces around its own layout. Passing the value through every wrapper couples layout to behavior. A compound API lets related components share one owner while the caller chooses their composition.

## Definition

**Practical definition:** Compound components expose one interface through cooperating React components. Their shared owner coordinates state and behavior while callers arrange the parts around their layout, without forwarding each coordinating prop through every wrapper.

> **Textbook Definition:** A compound-component pattern decomposes a composite interface into cooperating components. A parent owns shared state and behavior; descendants consume an explicit context contract, allowing flexible composition without passing every coordination prop through intermediate components.

## First Principles

Each tab trigger and panel must agree on one selected value. Independent state can let them disagree; passing that value through every layout wrapper couples structure to behavior. One owner with a context gives each part the same selection without requiring wrappers to forward it.

That flexibility creates a composition contract: the parts still need stable identities, valid relationships and defined behavior when one is missing or removed. Context shares state; it does not validate the tree or implement keyboard behavior.

## Show the shared contract

The parent owns the selected value and change action. Its children read that contract through context, so ordinary wrapper components do not interrupt it:

```text
Tabs (owns selected value and change action)
└── Context
    ├── Tabs.List
    │   └── Layout wrapper
    │       └── Tabs.Trigger (reads and changes selection)
    └── Tabs.Panel (renders content for the selected value)
```

A small controlled API shows the relationship:

```tsx
import { createContext, useContext, useId, useMemo, type ReactNode } from "react";

type TabsState = {
  value: string;
  onValueChange(value: string): void;
  id: string;
};

const TabsContext = createContext<TabsState | null>(null);

function useTabs() {
  const state = useContext(TabsContext);
  if (!state) throw new Error("Tabs parts need their matching Tabs parent");
  return state;
}

function TabsRoot({
  value,
  onValueChange,
  children,
}: Omit<TabsState, "id"> & { children: ReactNode }) {
  const id = useId();
  const state = useMemo(() => ({ value, onValueChange, id }), [value, onValueChange, id]);
  return (
    <TabsContext.Provider value={state}>
      {children}
    </TabsContext.Provider>
  );
}

function TabsList({ label, children }: { label: string; children: ReactNode }) {
  return <div role="tablist" aria-label={label}>{children}</div>;
}

function TabsTrigger({ value, children }: { value: string; children: ReactNode }) {
  const tabs = useTabs();
  const selected = tabs.value === value;
  const suffix = encodeURIComponent(value);

  return (
    <button
      type="button"
      role="tab"
      id={`${tabs.id}-tab-${suffix}`}
      aria-selected={selected}
      aria-controls={`${tabs.id}-panel-${suffix}`}
      onClick={() => tabs.onValueChange(value)}
    >
      {children}
    </button>
  );
}

function TabsPanel({ value, children }: { value: string; children: ReactNode }) {
  const tabs = useTabs();
  const suffix = encodeURIComponent(value);
  return (
    <div
      role="tabpanel"
      id={`${tabs.id}-panel-${suffix}`}
      aria-labelledby={`${tabs.id}-tab-${suffix}`}
      hidden={tabs.value !== value}
    >
      {children}
    </div>
  );
}

const Tabs = Object.assign(TabsRoot, { List: TabsList, Trigger: TabsTrigger, Panel: TabsPanel });

function ProfileTabs({ value, onValueChange }: {
  value: string;
  onValueChange(value: string): void;
}) {
  return (
    <Tabs value={value} onValueChange={onValueChange}>
      <Tabs.List label="Project settings">
        <Tabs.Trigger value="profile">Profile</Tabs.Trigger>
        <Tabs.Trigger value="settings">Settings</Tabs.Trigger>
      </Tabs.List>
      <Tabs.Panel value="profile"><ProfileForm /></Tabs.Panel>
      <Tabs.Panel value="settings"><SettingsForm /></Tabs.Panel>
    </Tabs>
  );
}
```

The compound namespace is a convenience for callers; context provides the sharing. This abbreviated example links triggers and panels but omits roving focus and arrow-key behavior. Use a tested primitive or implement that complete keyboard contract before shipping tabs.

Selection should use stable values such as `"profile"`, not child positions. If tabs can be reordered or removed, define what happens when the selected value disappears. If a panel returns `null` while inactive, its child state is destroyed; keep it mounted when a form draft must survive, and decide whether its effects should remain active while hidden.

## Make the composition contract explicit

Context allows wrappers between a parent and its parts, but it does not validate every possible tree. Decide which parts are required, whether duplicates are allowed, and how missing or removed items behave. Throw a clear error when a child is rendered outside its matching parent.

`React.Children` and `cloneElement` operate on elements passed directly as `children`; they do not inspect what a child component later renders or traverse through fragments. Cloning returns a new element, but injected props and refs can make wrappers fragile. Use cloning only when direct-child structure is intentionally part of the public API.

Dynamic choices may register their labels with the owner so the trigger can display the selected label. Replace a `Map` immutably when an option registers or unregisters; an Effect cleanup should unregister the option when it unmounts. Mutating the map in place keeps the same identity and may leave the displayed label stale. Effect registration also means an initially selected dynamic option may not be registered on the first render. Derive its label from the data owner when that delay is not acceptable.

A generic type on a parent JSX element does not flow into separately written child elements. When a component family must share an item type, create its context and children from a factory such as `createList<T>()`. Calling `createList<User>()` binds the context and child API to `User` once, instead of erasing the type to `any`. A `children: ReactNode` prop accepts arbitrary renderable content; it does not prove that callers supplied the right parts or nesting.

For a selectable object list, store a stable item key and derive the current item from the latest collection. Storing the object itself can leave selection pointing at an obsolete instance after the parent replaces its data or removes that item.

## Keep accessibility and state ownership in the contract

The pattern does not supply keyboard interaction or accessible relationships. Tabs need a complete tab/tabpanel contract; disclosure interfaces should prefer native `<details>` when it fits; and a custom select must define focus, selection and keyboard behavior rather than merely resembling a native control.

A form-field family can use one generated ID to join its label, input and error. The input should point to the error with `aria-describedby`, and report invalid state only while an error exists:

```tsx
const id = useId();
<label htmlFor={id}>Email</label>
<input id={id} aria-invalid={Boolean(error)} aria-describedby={error ? `${id}-error` : undefined} />
{error && <p id={`${id}-error`}>{error}</p>}
```

Each field instance needs a distinct ID. A native label and input remain the simplest choice when no reusable compound contract is needed.

Keep controlled and uncontrolled APIs distinct. A controlled selector requires both `value` and `onChange`; do not imply an uncontrolled mode unless the parent implements and documents its default state and change behavior.

## Context updates have a cost

Every consumer of a changed context value can render again. Memoizing the provider object prevents notifications caused only by rebuilding an equivalent value; it does not stop parent renders or shield a component that consumes the changed context. Split independent update domains when profiling shows broad notifications are costly. Use an external store only when its subscription and update model solves a measured need.

## Summary

Compound components trade explicit props for a shared state contract and flexible composition. Use them when callers need to arrange related parts; keep selection identity and mount behavior deliberate, and treat accessibility as part of the public API.

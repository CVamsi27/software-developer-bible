# React Interview Questions

## TL;DR

40+ React interview questions for senior candidates. Use as a self-test. Focus on Fiber architecture, the render/commit split, and why hooks behave the way they do — that's where the bar is for 5+ YoE candidates.

## First Principles

This set probes React's scheduling model (→ 10.3.1) and hook contracts (→ 10.3.2):

1. **The senior tells are Fiber-level**: why StrictMode double-renders, what keys protect, when memo pays, why external stores need useSyncExternalStore (→ 10.3.3.04) — reasoning from the render/commit split, not hook trivia.
2. **State-design questions** (→ 10.3.3.06) separate seniors: server-state vs client-state, owners, and selectors.

## Definition

A senior React interview evaluates a candidate's mental model of React's internal mechanisms, their ability to navigate architectural trade-offs, and their approach to state, performance, and concurrent features.

## Why

Senior React interviews test mental models: reconciliation, hooks dependencies, render vs. commit, why keys matter, when to use external state. Surface knowledge of JSX/syntax doesn't pass — you need to reason about React's behavior at runtime.

## How

When answering these questions, always anchor your response to the underlying mechanism. Use the "Why, How, and Trade-offs" framework to demonstrate depth.

## Real-world

### Section 1: React Internals (Fiber, reconciliation, rendering)

#### Q1: What exactly is React Fiber and why was it introduced?

**Senior answer**: Fiber is React's reimplementation of its core reconciliation algorithm, introduced in React 16. It represents a unit of work as a linked list node, allowing React to pause, abort, or prioritize rendering work. This cooperative scheduling model replaced the old synchronous stack reconciler, enabling concurrent features like `useTransition` where UI updates don't block the main thread.

**Key tradeoff**: Fiber allows responsive UIs at the cost of increased internal memory overhead (maintaining the alternate fiber tree) and breaking the guarantee that a render will complete synchronously once started.

**Follow-up they'll ask**: How does Fiber enable concurrent mode?

**Junior vs senior tell**: A junior says "Fiber makes React faster." A senior explains that Fiber doesn't make it strictly faster, but makes it *interruptible*, keeping the browser responsive by yielding to the main thread during heavy renders.

#### Q2: Can you explain the difference between the render phase and the commit phase?

**Senior answer**: The render phase is when React calls your components to figure out what changed, which is pure, asynchronous, and interruptible in concurrent mode. The commit phase is when React synchronously applies those calculated changes to the actual DOM and fires layout/effect hooks.

**Key tradeoff**: Splitting work allows React to throw away render work if a higher-priority update comes in, but requires components to be absolutely pure during render.

**Follow-up they'll ask**: Why shouldn't you trigger side effects in the render phase?

**Junior vs senior tell**: A junior confuses rendering with painting to the screen. A senior explicitly distinguishes between React calling the function (render) and mutating the DOM (commit).

#### Q3: How does React's reconciliation algorithm actually work under the hood?

**Senior answer**: Reconciliation uses a heuristic O(N) diffing algorithm based on two assumptions: elements of different types produce different trees, and lists use stable `key` props. When comparing the current Fiber tree with the WIP tree, React flags fibers with effect tags (like placement or deletion) to be processed during the commit phase.

**Key tradeoff**: It provides incredible performance for 99% of UI updates, but forces developers to understand rules around stable keys and avoiding wrapper components that change types across renders.

**Follow-up they'll ask**: What happens if you return a different element type (e.g., changing a `div` to a `span`)?

**Junior vs senior tell**: A junior says "it compares the virtual DOM". A senior explains the O(N) heuristics, effect tags, and the tree traversal mechanism.

#### Q4: What exactly does the `key` prop protect during reconciliation?

**Senior answer**: The `key` prop protects component *identity* and state across renders. During the reconciliation of sibling elements, React uses the key to match elements in the original tree with elements in the subsequent tree, preventing state from bleeding between reordered components and avoiding unnecessary DOM destruction/re-creation.

**Key tradeoff**: Proper keys guarantee state correctness but require developers to provide stable identifiers.

**Follow-up they'll ask**: Why is using an array index as a key a bad idea?

**Junior vs senior tell**: A junior says "keys help React identify items." A senior explicitly mentions that keys preserve the underlying component instance and its internal state.

#### Q5: Why does React 18 StrictMode double-invoke effects and reducers?

**Senior answer**: StrictMode intentionally double-invokes render phases and effects in development to expose side-effects and impure functions. In React 18, it mounts, unmounts, and remounts components to simulate the new concurrent behavior where React might preserve state but detach the UI (like for Offscreen API or fast refresh), ensuring your cleanup functions are resilient.

**Key tradeoff**: It creates development friction and confusing console logs, but mathematically enforces the purity contract required for concurrent features.

**Follow-up they'll ask**: How do you fix an issue where StrictMode double-invocation breaks your app?

**Junior vs senior tell**: A junior gets frustrated and turns off StrictMode. A senior uses it to find memory leaks and missing cleanup functions in `useEffect`.

#### Q6: How does React handle work loop priority and interruption?

**Senior answer**: React's scheduler assigns lanes (priorities) to updates. User interactions like typing get sync/high-priority lanes, while transitions get lower-priority lanes. During the render phase, React checks `shouldYieldToHost()` periodically; if the time slice is up or a high-priority update arrives, it yields to the browser, potentially throwing away the WIP tree.

**Key tradeoff**: Excellent perceived performance, but makes tracing execution paths highly complex.

**Follow-up they'll ask**: How do you explicitly mark an update as low priority?

**Junior vs senior tell**: A junior doesn't know about lanes. A senior can explain how `startTransition` maps to lower-priority lanes in the scheduler.

### Section 2: Hooks Deep Dive

#### Q7: Why do hooks have rules? What happens under the hood if you break them?

**Senior answer**: Hooks rely on a stable call order because React stores hook states in a linked list attached to the component's Fiber node. If a hook is called conditionally or inside a loop, the order shifts during a re-render, causing React to read the wrong state for subsequent hooks and corrupting the entire component state.

**Key tradeoff**: The design keeps the hook API clean (no need to pass identifiers) at the cost of strict static analysis requirements (eslint-plugin-react-hooks).

**Follow-up they'll ask**: How would you implement a hook internally if you couldn't use a linked list?

**Junior vs senior tell**: A junior recites the rules. A senior explains the underlying linked list architecture attached to the Fiber node.

#### Q8: Is the dependency array in `useEffect` for optimization or correctness?

**Senior answer**: The dependency array is strictly a correctness contract, not a performance optimization. It tells React which reactive values from the render scope the effect closes over. Omitting dependencies leads to stale closures because the effect will execute using values from a previous render pass.

**Key tradeoff**: Explicit dependency arrays prevent magical implicit reactivity, but require extreme developer discipline.

**Follow-up they'll ask**: What happens if you omit a function from the dependency array?

**Junior vs senior tell**: A junior uses the dependency array to "control when the effect runs". A senior uses it to guarantee the effect always sees the latest closures.

#### Q9: What is the exact difference between `useEffect` and `useLayoutEffect`?

**Senior answer**: `useLayoutEffect` fires synchronously in the commit phase right after React has mutated the DOM but *before* the browser has painted, blocking the main thread. `useEffect` fires asynchronously *after* the browser has painted, allowing the UI to remain responsive.

**Key tradeoff**: `useLayoutEffect` prevents visual flickering for DOM measurements, but blocks the browser's rendering pipeline.

**Follow-up they'll ask**: When should you absolutely use `useLayoutEffect`?

**Junior vs senior tell**: A junior says they are the same but `useLayoutEffect` is faster. A senior understands the exact timing relative to the browser paint cycle.

#### Q10: What are the common cleanup patterns for `useEffect`?

**Senior answer**: Cleanup functions are critical for avoiding memory leaks and race conditions. Common patterns include aborting `fetch` requests using `AbortController`, clearing `setTimeout`/`setInterval`, removing DOM event listeners, and unsubscribing from WebSockets or observables.

**Key tradeoff**: Cleanups require more boilerplate but ensure the component doesn't mutate state after unmounting.

**Follow-up they'll ask**: How do cleanups prevent state updates on unmounted components?

**Junior vs senior tell**: A junior only cleans up event listeners. A senior explicitly uses cleanups to cancel pending promises and network requests to prevent race conditions.

#### Q11: When is `useRef` the right choice over `useState`?

**Senior answer**: `useRef` is for mutable values that should *not* trigger a re-render when they change, effectively acting as instance variables for functional components. It's the correct choice for storing DOM node references, timer IDs, or keeping track of the previous state without causing infinite render loops.

**Key tradeoff**: `useRef` updates are synchronous and immediately available, but they bypass React's reactive rendering cycle.

**Follow-up they'll ask**: Why shouldn't you read or write `useRef.current` during the render phase?

**Junior vs senior tell**: A junior thinks refs are only for DOM elements. A senior knows it's a generic mutable box and understands why mutating it during render breaks concurrent mode purity.

#### Q12: How does `useSyncExternalStore` prevent tearing?

**Senior answer**: Tearing occurs in concurrent rendering when a component reads from an external store, yields to the browser, the store mutates, and it resumes rendering with a mismatched state. `useSyncExternalStore` forces synchronous updates when reading from outside React's state tree, guaranteeing UI consistency.

**Key tradeoff**: It provides absolute consistency for external state but forces React to de-opt to synchronous rendering, losing concurrent benefits for those specific updates.

**Follow-up they'll ask**: Why doesn't Redux just use `useState` or `useEffect` anymore?

**Junior vs senior tell**: A junior has never heard of it. A senior understands the tearing problem in React 18 and why state management libraries migrated to this hook.

#### Q13: Why is mutating state directly in React a problem at the Fiber level?

**Senior answer**: React's reconciliation relies on strict object identity (Object.is) to determine if state has changed and if a re-render should be queued. If you mutate an object, the reference remains the same, so the Fiber node bails out of rendering. Furthermore, in concurrent mode, mutating state destroys the ability to throw away the WIP tree and revert to the current tree.

**Key tradeoff**: Immutability costs memory allocation overhead but provides O(1) change detection and enables safe concurrent rendering.

**Follow-up they'll ask**: How do libraries like Immer solve the boilerplate of immutability?

**Junior vs senior tell**: A junior says "React won't re-render". A senior explains the object identity check and the implications for the WIP Fiber tree.

### Section 3: Performance & Optimization

#### Q14: What actually causes a component to re-render in React?

**Senior answer**: A component re-renders for exactly three reasons: its state changes, its parent re-renders, or a Context it subscribes to changes. Notably, a component will re-render when its parent does, *even if its props haven't changed*, unless explicitly wrapped in `React.memo`.

**Key tradeoff**: This cascading render model is simple to reason about but can cause massive performance bottlenecks if state is hoisted too high in the tree.

**Follow-up they'll ask**: Does changing a prop cause a re-render if the parent hasn't re-rendered?

**Junior vs senior tell**: A junior says "when props or state change". A senior knows that parent renders unconditionally trigger child renders, regardless of props.

#### Q15: When is using `useMemo` or `useCallback` considered a premature optimization?

**Senior answer**: Memoization has a cost: React must allocate memory for the dependency array and run `Object.is` checks on every render. If the computation is trivial (like mapping a small array), or if the child component isn't wrapped in `React.memo`, using `useMemo` is slower than just recalculating.

**Key tradeoff**: You trade CPU time (recalculating) for memory and overhead (storing and comparing dependencies).

**Follow-up they'll ask**: What is the most common mistake when using `useCallback`?

**Junior vs senior tell**: A junior memoizes every function. A senior profiles first and only memoizes referential types passed to `React.memo` components or expensive calculations.

#### Q16: How does context affect performance and how do you optimize it?

**Senior answer**: When a Context value changes, React forces a re-render of *every* component subscribed to that Context, bypassing `React.memo`. To optimize, you should split contexts by domain and frequency of change, or pass a memoized value to the provider.

**Key tradeoff**: Context provides global access without prop drilling, but couples components to the global re-render cycle.

**Follow-up they'll ask**: How do you prevent context from causing unnecessary renders?

**Junior vs senior tell**: A junior puts all global state in one massive Context. A senior splits state and dispatch into separate contexts to prevent consumer re-renders.

#### Q17: What is the impact of inline objects in JSX and when does it actually matter?

**Senior answer**: Inline objects `{ style: { margin: 0 } }` create a new object reference on every render. This only matters if passed as a prop to a component wrapped in `React.memo`, or if used as a dependency in a hook like `useEffect`, which would trigger unnecessary executions. For standard DOM elements, it has negligible impact.

**Key tradeoff**: Inline objects are ergonomic, but break referential equality checks down the tree.

**Follow-up they'll ask**: How do you pass a stable empty array or object as a default prop?

**Junior vs senior tell**: A junior avoids all inline objects. A senior understands it only matters at API boundaries where referential equality is checked.

#### Q18: How do you use the React Profiler to diagnose performance issues?

**Senior answer**: I use the DevTools Profiler to record interactions and analyze the flame graph. I look for the "Why did this render?" tooltip to identify unnecessary renders caused by context or reference changes, and examine the commit times to distinguish between heavy render logic vs heavy DOM mutations.

**Key tradeoff**: Profiling requires running in development mode, which doesn't perfectly reflect production speeds.

**Follow-up they'll ask**: What does a large yellow bar in the flame graph indicate?

**Junior vs senior tell**: A junior guesses performance issues. A senior uses the Profiler to scientifically identify the bottleneck before adding memoization.

#### Q19: What is the difference between shallow rendering and full rendering?

**Senior answer**: Full rendering evaluates the entire component tree and mounts it to a DOM (or jsdom), while shallow rendering only evaluates a single component level, mocking its children. Shallow rendering is fast and isolated for unit tests but fails to test context, child interactions, and integration behaviors.

**Key tradeoff**: Shallow rendering provides true unit isolation but misses real-world integration bugs.

**Follow-up they'll ask**: Why has the community moved away from Enzyme's shallow rendering toward React Testing Library?

**Junior vs senior tell**: A junior only knows RTL. A senior can explain why testing implementation details (shallow) was abandoned for behavioral testing.

### Section 4: State & Data

#### Q20: How do you decide between local component state, context, and a global store?

**Senior answer**: State should live as close to where it's used as possible. Use local state for UI concerns (modals, inputs). Use Context for low-frequency global settings (theme, auth). Use a global store (Redux, Zustand) for complex, high-frequency client state, and a data fetching library (React Query) for server state.

**Key tradeoff**: Hoisting state increases accessibility but widens the blast radius for re-renders and increases architectural complexity.

**Follow-up they'll ask**: What happens if you use Context for high-frequency updates like mouse coordinates?

**Junior vs senior tell**: A junior puts everything in Redux. A senior colocates state and strictly separates server cache from client state.

#### Q21: What is the conceptual difference between client state and server state?

**Senior answer**: Client state is ephemeral, synchronous, and owned by the UI (e.g., is a dropdown open). Server state is persistent, asynchronous, owned by a remote server, and inherently stale the moment it reaches the client. Treating server state like client state leads to over-fetching and complex synchronization bugs.

**Key tradeoff**: Separating them requires multiple tools (e.g., Zustand + React Query) but drastically simplifies code by delegating cache invalidation.

**Follow-up they'll ask**: How does React Query handle cache invalidation?

**Junior vs senior tell**: A junior manually fetches data in `useEffect` and dumps it into Redux. A senior uses a dedicated caching layer for server state.

#### Q22: Why shouldn't you sync props to state?

**Senior answer**: Copying props to state creates a "split source of truth". If the parent updates the prop, the child's state won't automatically update unless you add a `useEffect` to watch the prop, which causes a second cascading render. You should derive the value during render instead.

**Key tradeoff**: Deriving state on render costs CPU cycles but guarantees absolute consistency without lifecycle bugs.

**Follow-up they'll ask**: When is it actually okay to sync a prop to state?

**Junior vs senior tell**: A junior syncs props in `useEffect`. A senior knows the "initial state" pattern where a prop is only used to seed an uncontrolled component.

#### Q23: How do you handle complex derived state?

**Senior answer**: Complex derived state should be computed during the render phase using standard JavaScript variables, not `useState` or `useEffect`. If the calculation is genuinely expensive (e.g., sorting thousands of items), wrap the derivation in `useMemo` with the raw state as dependencies.

**Key tradeoff**: Computing on the fly is safer but requires careful performance monitoring for heavy operations.

**Follow-up they'll ask**: How do you avoid recalculating derived state when irrelevant state changes?

**Junior vs senior tell**: A junior uses `useEffect` to update a secondary state variable. A senior computes it synchronously during render.

#### Q24: What are the trade-offs of using Redux vs Context + useReducer in a modern app?

**Senior answer**: `Context + useReducer` is built-in but suffers from the re-render problem (all consumers re-render on any dispatch) and lacks middleware. Redux provides selective subscriptions, Redux DevTools, and robust middleware (thunks/sagas), but adds significant boilerplate and bundle size.

**Key tradeoff**: Context is simpler to set up, but Redux scales infinitely better for complex data flows.

**Follow-up they'll ask**: Why has Zustand become popular over Redux recently?

**Junior vs senior tell**: A junior thinks Context replaces Redux. A senior understands the subscription model difference and how Redux prevents unnecessary renders.

#### Q25: How do you prevent race conditions when fetching data in `useEffect`?

**Senior answer**: When fetching data, the component might unmount, or a subsequent fetch might resolve before an earlier one. You must use an `AbortController` in the cleanup function to cancel the network request, or use a boolean flag (`ignore = true`) to ensure stale responses don't update state.

**Key tradeoff**: Writing defensive cleanups is verbose but completely eliminates elusive race condition bugs.

**Follow-up they'll ask**: How do modern data fetching libraries solve this?

**Junior vs senior tell**: A junior ignores the possibility of network latency variations. A senior always returns a cleanup function that aborts the request.

### Section 5: Patterns & Architecture

#### Q26: When would you use a Compound Component pattern over passing multiple props?

**Senior answer**: Use Compound Components (like `<Select>`, `<Select.Option>`) when multiple components need to share implicit state and you want to give the consumer control over the markup structure. Passing a massive configuration object as a prop (`options={...}`) creates rigid APIs; Compound Components use Context internally to communicate, offering extreme flexibility.

**Key tradeoff**: Compound components provide exceptional API ergonomics but increase internal implementation complexity.

**Follow-up they'll ask**: How do you pass state between the parent and child in this pattern?

**Junior vs senior tell**: A junior passes a 50-line JSON object as a prop. A senior builds composable component APIs using Context.

#### Q27: In what scenarios are Higher-Order Components (HOCs) still preferred over Hooks?

**Senior answer**: Hooks have largely replaced HOCs for logic reuse, but HOCs are still required when you need to intercept rendering entirely (e.g., wrapping a component in an Error Boundary, implementing `React.memo`, or conditionally returning null before the component even mounts based on auth status).

**Key tradeoff**: HOCs can cause prop collisions and wrapper hell, but provide powerful render-blocking capabilities that hooks cannot.

**Follow-up they'll ask**: Why can't a hook conditionally prevent a component from rendering?

**Junior vs senior tell**: A junior thinks HOCs are deprecated. A senior knows hooks can only inject data and effects, while HOCs can hijack the render lifecycle.

#### Q28: When should you use the Render Props pattern today?

**Senior answer**: The Render Props pattern (`<DataProvider render={(data) => <UI data={data} />} />`) is largely obsolete for state sharing due to hooks. However, it remains highly relevant for layout injection, such as virtualization libraries that need to know exactly how to render a dynamic row item while controlling the container math.

**Key tradeoff**: Render props cause deep nesting (callback hell in JSX) but allow complete inversion of control for UI rendering.

**Follow-up they'll ask**: How do you convert a render prop component into a custom hook?

**Junior vs senior tell**: A junior writes new render props for state sharing. A senior only uses them for UI inversion of control.

#### Q29: How do you handle cross-cutting concerns like analytics in a React app?

**Senior answer**: Analytics should be decoupled from core business logic. I use a custom hook (e.g., `useAnalytics`) that provides a tracking function, or implement an event bus pattern. For page views, I tie into the router events. For specific interactions, I avoid clogging `onClick` handlers by using declarative tracking wrappers or data-attributes caught by a global delegated listener.

**Key tradeoff**: Global listeners are clean but brittle; explicit hooks are verbose but highly typed and reliable.

**Follow-up they'll ask**: How do you test analytics without spamming the real tracking endpoint?

**Junior vs senior tell**: A junior dumps `mixpanel.track()` into every component. A senior centralizes telemetry via hooks or context to ensure consistency.

#### Q30: What is the Custom Hook pattern and how do you structure them?

**Senior answer**: Custom hooks encapsulate stateful logic into reusable functions. A robust custom hook returns a tuple (for single values) or an object (for multiple values), accepts an options object for configuration, and strictly isolates side effects. They should be pure data transformations and not return JSX.

**Key tradeoff**: Custom hooks make code highly reusable but abstract away the visual timeline of when effects run.

**Follow-up they'll ask**: How do you test a custom hook that uses context and side effects?

**Junior vs senior tell**: A junior puts everything into a single component. A senior extracts all non-UI logic into headless custom hooks.

#### Q31: How do Error Boundaries work and what are their limitations?

**Senior answer**: Error Boundaries are class components implementing `componentDidCatch` or `static getDerivedStateFromError` to catch synchronous rendering errors in their subtree. They *cannot* catch async errors (promises, setTimeout), event handler errors, or errors in the boundary itself.

**Key tradeoff**: They prevent the entire app from crashing on a single component failure, but require class components and defensive async error handling.

**Follow-up they'll ask**: How do you catch an error inside a `fetch` callback using an Error Boundary?

**Junior vs senior tell**: A junior thinks Error Boundaries catch all bugs. A senior knows they must manually set a state variable to trigger a render error for async failures.

### Section 6: React 18/19 Modern Features

#### Q32: What does `startTransition` actually do to the scheduler?

**Senior answer**: `startTransition` flags all state updates within its callback as "transitions" (low priority). If a higher-priority update (like a keystroke) occurs, React will interrupt the transition's render phase. It allows you to keep the current UI interactive while computing a heavy background update, without needing to show a loading spinner.

**Key tradeoff**: It provides a fluid UX at the cost of CPU cycles, as interrupted render work is discarded and recalculated.

**Follow-up they'll ask**: What is the difference between `startTransition` and `setTimeout`?

**Junior vs senior tell**: A junior thinks it's just a debounce. A senior explains priority lanes and render phase interruption.

#### Q33: When should you use `useDeferredValue` instead of debouncing?

**Senior answer**: Debouncing waits a fixed amount of time before updating, which means fast devices are artificially slowed down. `useDeferredValue` integrates deeply with React's scheduler; it renders the initial state immediately, then attempts the deferred update in the background. It finishes as fast as the device allows and can be interrupted.

**Key tradeoff**: It leverages device capabilities perfectly but can cause visual tearing if you don't dim the stale UI.

**Follow-up they'll ask**: How do you visually indicate to the user that a deferred value is currently updating?

**Junior vs senior tell**: A junior only uses `lodash.debounce`. A senior leverages React's concurrent scheduler for fluid text inputs.

#### Q34: How does React 19's `use()` hook change async error propagation?

**Senior answer**: `use()` allows reading Promises directly during the render phase. Instead of manually handling `.catch()` and setting error state, if a Promise passed to `use()` rejects, React suspends the component and automatically throws the error up to the nearest Error Boundary, unifying async and sync error handling.

**Key tradeoff**: It dramatically simplifies data fetching code but heavily relies on Suspense and Error Boundaries being correctly placed in the tree.

**Follow-up they'll ask**: Can you call `use()` conditionally inside an `if` statement?

**Junior vs senior tell**: A junior has never heard of it. A senior knows `use()` is the only hook that can be called conditionally.

#### Q35: What is the real use case for `useOptimistic`?

**Senior answer**: `useOptimistic` (React 19) provides a standardized way to build optimistic UIs. It takes the true server state and an update function, allowing you to temporarily mutate the UI while an async action (like a form submission) is pending. If the action fails, React automatically rolls back to the true state.

**Key tradeoff**: It provides instant perceived latency but requires careful error handling to prevent users from thinking an action succeeded when it failed.

**Follow-up they'll ask**: How did we do this before React 19, and why is this better?

**Junior vs senior tell**: A junior manually toggles state and tries to revert it on catch. A senior understands how this integrates with server actions and form state.

#### Q36: How does `useActionState` simplify form submissions?

**Senior answer**: `useActionState` (formerly useFormState) connects a form action to component state. It tracks the pending status, the payload, and the response from a Server Action or async function automatically. It eliminates the need to manually manage `isLoading`, `error`, and `data` states via `useState`.

**Key tradeoff**: It reduces boilerplate immensely but couples your form tightly to React's specific action paradigms.

**Follow-up they'll ask**: How does this work progressively if JavaScript is disabled?

**Junior vs senior tell**: A junior manually prevents default and orchestrates multiple state variables. A senior uses native actions for streamlined data mutation.

#### Q37: What is the difference between Server Components (RSC) and SSR?

**Senior answer**: SSR renders a component tree to HTML on the server, but sends the entire JS bundle to the client to be hydrated. React Server Components (RSC) run *only* on the server, never ship their JS code to the client, and serialize directly into a proprietary stream format that merges with the client tree without hydration overhead.

**Key tradeoff**: RSC drastically reduces bundle size and allows direct database access, but adds massive architectural complexity regarding where state can live (the network boundary).

**Follow-up they'll ask**: Can a Server Component use `useState`?

**Junior vs senior tell**: A junior thinks RSC and SSR are the same thing. A senior understands the serialization boundary and hydration differences.

### Section 7: Senior System Design Questions

#### Q38: How would you architect a complex real-time dashboard in React?

**Senior answer**: I would separate the architecture into layers. For the real-time data, I'd use WebSockets paired with a fast store like Zustand or a custom pub-sub context, bypassing React's render cycle for heavy data streams. I'd extensively use `React.memo` and virtualization to ensure only specific widgets re-render, and use concurrent features to prevent high-frequency socket updates from freezing the main thread.

**Key tradeoff**: Bypassing React for data ingestion is complex but necessary for 60fps performance on heavy dashboards.

**Follow-up they'll ask**: How do you handle a scenario where a socket pushes 1,000 updates per second?

**Junior vs senior tell**: A junior puts the socket data in Context. A senior buffers/throttles the socket data outside of React and flushes updates efficiently.

#### Q39: Design an infinite scrolling list that handles millions of items.

**Senior answer**: I'd implement virtual scrolling. Instead of rendering DOM nodes, the component calculates the user's scroll position, slices the dataset to find the visible range, and only renders those items plus a small overscan buffer. I'd use absolute positioning within a container whose height matches the total dataset size to preserve scrollbars.

**Key tradeoff**: Incredible DOM performance at the cost of complex scroll math, accessibility challenges, and dynamic height difficulties.

**Follow-up they'll ask**: How do you handle items with dynamic, unknown heights?

**Junior vs senior tell**: A junior uses standard pagination. A senior understands the exact math behind virtualization and DOM node recycling.

#### Q40: How would you structure a monorepo containing multiple React applications sharing components?

**Senior answer**: I'd use Turborepo or Nx. The structure would include `apps/` for the specific Next/Vite applications and `packages/` for shared UI libraries, utilities, and ESLint/TS configs. I'd ensure the shared UI package exports compiled code or is natively transpiled by the consumers to avoid dependency hell, using a design system architecture.

**Key tradeoff**: Monorepos solve code sharing but introduce complex CI/CD caching and dependency management overhead.

**Follow-up they'll ask**: How do you prevent one app from breaking when you update a shared component?

**Junior vs senior tell**: A junior copy-pastes code. A senior implements a proper package workspace with strict semantic versioning and CI checks.

#### Q41: Describe your strategy for migrating a legacy SPA to a Next.js App Router application.

**Senior answer**: It must be incremental. I would set up the Next.js app in a monorepo, configure reverse proxies (Nginx or Next.js rewrites) to route specific paths to the new app while falling back to the legacy SPA. I'd migrate route by route, starting with leaf nodes or high-SEO pages, porting shared state to URLs or cookies to survive the bridge between the two apps.

**Key tradeoff**: Running two apps side-by-side is operationally complex but eliminates the catastrophic risk of a "big bang" rewrite.

**Follow-up they'll ask**: How do you share authentication state between the old SPA and the new Next.js app?

**Junior vs senior tell**: A junior rewrites it all from scratch. A senior uses the strangler fig pattern and focuses on risk mitigation.

#### Q42: How do you handle authentication and protected routes effectively?

**Senior answer**: I implement a layered approach. A robust auth context provides the user state. Protected routes are wrapped in a layout component that checks auth and redirects to login if unauthenticated. Crucially, I secure the backend via HTTP-only cookies (not localStorage) to prevent XSS, and use an axios/fetch interceptor to seamlessly handle JWT refresh token rotation on 401 responses.

**Key tradeoff**: Refresh token rotation is highly secure but adds significant complexity to the networking layer.

**Follow-up they'll ask**: Why is storing a JWT in localStorage a security risk?

**Junior vs senior tell**: A junior checks auth inside every single page component. A senior centralizes auth via layouts, interceptors, and secure cookies.

#### Q43: What is your approach to testing a complex React application?

**Senior answer**: I follow the Testing Trophy. I write static tests (TypeScript/ESLint), use Vitest/React Testing Library for integration tests focusing on user workflows and accessibility roles (not implementation details), and Cypress/Playwright for critical end-to-end paths (like checkout). I mock network requests via MSW (Mock Service Worker) so components act naturally.

**Key tradeoff**: Comprehensive testing slows down initial development but pays massive dividends in maintenance and deployment confidence.

**Follow-up they'll ask**: Why is it better to query elements by their ARIA role rather than test IDs?

**Junior vs senior tell**: A junior writes 100% unit tests checking component props. A senior tests behavioral flows and uses MSW for robust network mocking.

## Mistakes

- **Mistake 1**: Answering with basic definition. (e.g. "useMemo caches a value.")
- **Mistake 2**: Failing to mention tradeoffs. Every pattern in React has a cost.
- **Mistake 3**: Not anchoring the answer in React internals (Fiber, concurrent mode, object identity).

## Best practices

- Frame answers around **Correctness first, Performance second**.
- Mention the evolution (e.g. "Before React 18 we did X, but now with Concurrent Mode we do Y").
- Tie theoretical concepts to real bugs you've fixed.

## Summary

To pass a senior React interview, you must demonstrate that you view React not as a magic black box, but as a predictable runtime with specific rules. Understanding the render/commit split, Fiber scheduling, and concurrent features is non-negotiable for a modern senior engineer.

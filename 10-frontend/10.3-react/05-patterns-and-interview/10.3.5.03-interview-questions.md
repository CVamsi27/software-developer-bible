# React Interview Questions

## Definition

A senior React interview tests whether you can use React's contracts to explain correctness, choose state and rendering boundaries, and reason through product constraints. Internal details matter when they explain an observable behavior or change an engineering decision.

## First Principles

React may render a component more than once before committing a result, so render logic must be pure and repeatable. State needs a clear owner; asynchronous results need an identity; external systems need explicit synchronization and cleanup. These constraints explain why keys preserve sibling identity, Effects model synchronization, and transitions change rendering priority without moving CPU work off the main thread.

An interview answer should distinguish public guarantees from implementation details, then follow one concrete update from input through render to commit. The code path alone is not enough: name the user-visible failure, the state or resource that owns it, and how you would verify the fix.

## How to answer

For each prompt, state the contract, trace one concrete case, then give a trade-off or failure boundary. Prefer a measured diagnosis over a rule such as “always memoize.” Avoid presenting private scheduler details as a public guarantee.

### Section 1: React Internals (Fiber, reconciliation, rendering)

#### Q1: What is Fiber, and what problem does it solve?

**Answer**: Fiber is React's internal representation of work for a component tree. It lets React keep render work across units so the renderer can pause, restart, or abandon work between units; it does not move JavaScript to another thread or interrupt a component function midway.

**Boundary**: Fiber fields and scheduling details are implementation, not application APIs. Explain the observable contract first: render work may be retried, so render logic must be pure.

**Follow-up**: What must be true of a component if React may call it again before committing?


#### Q2: Can you explain the difference between the render phase and the commit phase?

**Answer**: Render calculates the next tree and may pause, restart, or be discarded. Commit applies the selected changes to the host environment and runs layout effects after DOM mutation; passive effects are scheduled separately, and their timing is not an unconditional after-paint guarantee.

**Boundary**: A render can run without a corresponding DOM change. Side effects belong in event handlers or effects, not component render code.

**Follow-up they'll ask**: Why shouldn't you trigger side effects in the render phase?


#### Q3: How does React's reconciliation algorithm actually work under the hood?

**Answer**: React compares sibling elements using type and keys; when keys are absent, position helps determine identity. It uses a practical linear-time heuristic rather than solving a globally minimal tree-edit problem. A type or key change can replace a subtree and reset its state.

**Boundary**: Stable keys describe identity among siblings, not a promise that an instance survives removal or a change of parent/type.

**Follow-up they'll ask**: What happens if you return a different element type (e.g., changing a `div` to a `span`)?


#### Q4: What exactly does the `key` prop protect during reconciliation?

**Answer**: A key lets React match a sibling with the same identity across renders. With stable keys, reordering a list can preserve each item's component state with its record; index keys can attach that state to a different record after insertion or sorting.

**Boundary**: Keys are local to one sibling set. A removed item loses its mounted state, and a matching key under another parent does not preserve identity.

**Follow-up they'll ask**: Why is using an array index as a key a bad idea?


#### Q5: Which extra checks does Strict Mode run in development?

**Answer**: Strict Mode adds development-only checks. React calls component bodies and selected pure functions again, and replays Effects and callback refs with setup/cleanup to expose missing cleanup. The initial Effect replay happens when Strict Mode wraps the root; a nested boundary does not replay initial child Effects without the parent.

**Boundary**: Do not build behavior around an exact invocation count. Fix impure render logic and cleanup symmetry; production does not run these extra checks.

**Follow-up they'll ask**: How do you fix an issue where StrictMode double-invocation breaks your app?


#### Q6: What can an application control about render priority?

**Answer**: Applications can mark non-urgent state updates as transitions with `startTransition` or let a subtree lag with `useDeferredValue`. React can interrupt render work for urgent work, but these APIs do not move CPU work in the callback to another thread or assign a documented lane number.

**Boundary**: Priority internals such as lane values and scheduler functions are private. Do not promise a particular update-to-lane mapping.

**Follow-up**: Why does a long synchronous loop inside `startTransition` still block the browser?


### Section 2: Hooks Deep Dive

#### Q7: Why do hooks have rules? What happens under the hood if you break them?

**Answer**: Stateful Hooks rely on the same call order on every render so React can associate each call with its stored state. The `use` API is a special case: it may read a resource inside a condition or loop, but it still belongs in a component or custom Hook and cannot be wrapped in `try`/`catch`.

**Boundary**: `use(context)` is not supported in Server Components; `use(promise)` has a different resource contract. Do not generalize the exception to other Hooks.

**Follow-up they'll ask**: How would you implement a hook internally if you couldn't use a linked list?


#### Q8: Is the dependency array in `useEffect` for optimization or correctness?

**Answer**: Dependencies identify the reactive values an Effect reads from its render. Omitting one can leave the Effect using a stale value. The array is part of synchronization correctness, not a switch for choosing arbitrary run counts.

**Boundary**: If a dependency causes unwanted resynchronization, change the code structure or move non-reactive work out of the Effect; do not suppress the dependency check to force a schedule.

**Follow-up they'll ask**: What happens if you omit a function from the dependency array?


#### Q9: What is the exact difference between `useEffect` and `useLayoutEffect`?

**Answer**: useLayoutEffect runs after DOM mutation but before repaint, allowing a measurement-driven update to finish before the user sees the frame. useEffect usually allows painting first for non-interaction updates, but interaction-related effects and updates from layout effects can run earlier. Choose layout effects only when blocking paint is required.

**Boundary**: Use `useLayoutEffect` only when a measurement-driven update must finish before paint; it blocks painting and has no useful server layout to inspect.

**Follow-up they'll ask**: When should you absolutely use `useLayoutEffect`?


#### Q10: What are the common cleanup patterns for `useEffect`?

**Answer**: Cleanup releases resources established by an Effect: unsubscribe, remove a listener, clear a timer, or request cancellation through an AbortSignal where supported. Mark the Effect instance obsolete so a late result cannot update the UI.

**Boundary**: Aborting is best-effort: it cannot cancel an arbitrary Promise or roll back work already received by a server. React 18 removed the unmounted-state warning; prevent stale writes and release the actual resource instead of suppressing warnings.

**Follow-up they'll ask**: How do cleanups prevent state updates on unmounted components?


#### Q11: When is `useRef` the right choice over `useState`?

**Answer**: A ref holds a value across renders without making changes to that value schedule a render. Use it for a DOM node, timer handle, or imperative integration when the value is not itself rendered output. Use state when the UI must reflect the change.

**Boundary**: Mutating or reading refs during render usually breaks purity assumptions; read or update them in event handlers, effects, or ref callbacks.

**Follow-up they'll ask**: Why shouldn't you read or write `useRef.current` during the render phase?


#### Q12: How does `useSyncExternalStore` prevent tearing?

**Answer**: `useSyncExternalStore` subscribes React to an external store and reads a snapshot. `getSnapshot` must return a cached value while the store is unchanged. Before committing a transition, React can re-read it; if it changed, React restarts that work as blocking so the screen does not commit mixed store versions.

**Boundary**: This protects consistency of the rendered snapshot. It does not order network writes, make mutable snapshots safe, or enforce authorization.

**Follow-up they'll ask**: Why doesn't Redux just use `useState` or `useEffect` anymore?


#### Q13: Why should state updates replace changed objects instead of mutating them?

**Answer**: React can skip a state update when the next value is `Object.is`-equal to the current one. Mutating an object and passing back the same reference can therefore hide a change; shared mutation can also make an in-progress render observe data that changed underneath it. Replace each changed level and preserve unchanged references.

**Boundary**: Structural sharing makes identity comparisons useful, but copying costs depend on the data structure and the paths copied. Immutability is not a blanket O(1) operation.

**Follow-up they'll ask**: How do libraries like Immer solve the boilerplate of immutability?


### Section 3: Performance & Optimization

#### Q14: What actually causes a component to re-render in React?

**Answer**: Common triggers are an update to local state, a changed context subscription, a parent rendering its child, or an external-store subscription notifying React. Memoization and reusing the same element can let React skip child work; Suspense retries and development checks also make a rigid exactly-three-reasons list misleading. A render need not produce a DOM mutation.

**Boundary**: A render is not the same as a DOM mutation. If a measured interaction is slow, identify whether the cost is React render, commit, layout, paint, or network work before changing state ownership.

**Follow-up they'll ask**: Does changing a prop cause a re-render if the parent hasn't re-rendered?


#### Q15: When is using `useMemo` or `useCallback` considered a premature optimization?

**Answer**: Memoization adds dependency comparisons and can retain values, so measure whether avoiding a calculation or stabilizing an identity pays for it. `useMemo` can save expensive work even without a memoized child; `useCallback` can stabilize dependencies as well as props. Neither is a correctness guarantee. If React Compiler is enabled, it can automate many memoizations, but verify the built app and profile the interaction.

**Boundary**: `useMemo` is a performance optimization, not semantic storage; React may discard the cache. `useCallback` stabilizes a function identity, which helps only where identity is observed.

**Follow-up they'll ask**: What is the most common mistake when using `useCallback`?


#### Q16: How does context affect performance and how do you optimize it?

**Answer**: Consumers of a Context update when its provider value changes by `Object.is`, even if they are wrapped in `memo`. Components that do not read that Context are not notified by the context change itself.

**Trade-off**: Split contexts by independent state or update frequency. Memoizing the provider object avoids notifications caused by rebuilding an otherwise equal value; it does not prevent updates when shared state changes or optimize selectors within a consumer.

**Follow-up they'll ask**: How do you prevent context from causing unnecessary renders?

#### Q17: What is the impact of inline objects in JSX and when does it actually matter?

**Answer**: Inline objects such as `{ margin: 0 }` have a new identity each render. That matters where identity is observed, such as a prop compared by `memo` or an Effect dependency; a normal DOM style prop usually does not need memoization by itself.

**Trade-off**: A fresh object defeats shallow identity checks at a memoized boundary; outside identity-sensitive boundaries, the extra object is usually irrelevant.

**Follow-up they'll ask**: Which consumer actually observes this identity, and what work does stabilizing it avoid?


#### Q18: How do you use the React Profiler to diagnose performance issues?

**Answer**: Record representative interactions in React DevTools and inspect which components rendered, their durations, and update causes when that recording option is enabled. Development timings contain additional overhead, so confirm meaningful performance conclusions with a production profiling build. Component render duration and browser layout/paint are different measurements; use browser performance tooling for the latter.

**Trade-off**: A recording describes the workload and environment you captured. Confirm high-impact changes against representative production behavior.

**Follow-up they'll ask**: How do you separate React render cost from browser layout and paint cost?


#### Q19: Why do many component tests render through the DOM instead of using shallow rendering?

**Answer**: Shallow rendering stops at one component boundary, so it cannot verify how users experience the composed tree, context, DOM semantics, or interactions. DOM-based component tests can exercise those contracts without requiring a full browser.

**Trade-off**: Keep pure transformation logic in fast unit tests; use DOM-based tests for component behavior and end-to-end tests for critical browser journeys. Avoid testing private component structure when user-visible behavior is the contract.

**Follow-up they'll ask**: Which user-visible behavior can a DOM-based test verify that a shallow test cannot?


### Section 4: State & Data

#### Q20: How do you decide between local component state, context, and a global store?

**Answer**: Start with ownership and consumers. Keep state local when one area owns it; use Context to pass a scoped value through the tree; choose an external store when its selector, subscription, middleware, or tooling contract is useful. Use a server-state cache when freshness, deduplication, retry, and invalidation policies matter.

**Boundary**: A server cache is still a local copy of remote data. Define its freshness and invalidation policy instead of treating it as authoritative client state.

**Follow-up they'll ask**: What happens if you use Context for high-frequency updates like mouse coordinates?


#### Q21: What is the conceptual difference between client state and server state?

**Answer**: Client state is owned by the UI, such as a draft or open panel; it can also be persisted locally. Server state is owned remotely and may change independently after being fetched, so a cached copy has a freshness window: it can already be stale when it arrives or become stale later. A query cache can manage freshness, retries and invalidation without requiring separate state libraries.

**Boundary**: “Server state” describes ownership and freshness, not where React renders. A response can be stale when it arrives or become stale while cached.

**Follow-up they'll ask**: How do you prevent a stale response from overwriting a newer result?


#### Q22: Why shouldn't you sync props to state?

**Answer**: Copying a prop into state creates two owners. The copy will not track later prop changes unless another synchronization rule is added, often producing a stale render and a second update. Derive the value during render when it is fully determined by current props and state.

**Boundary**: Local state is valid when the component intentionally captures an initial value or edits a draft. For a full reset on identity change, a keyed child is often clearer than an Effect that mirrors the prop.

**Follow-up they'll ask**: When is it actually okay to sync a prop to state?


#### Q23: How do you handle complex derived state?

**Answer**: Compute derived values during render so they cannot drift from their source. Add `useMemo` only after profiling shows the calculation is costly or stable identity prevents measured downstream work.

**Boundary**: If the value must persist independently or be changed by the user, it is state rather than a derivation.

**Follow-up they'll ask**: How do you avoid recalculating derived state when irrelevant state changes?


#### Q24: What are the trade-offs of using Redux vs Context + useReducer in a modern app?

**Answer**: Context plus `useReducer` is enough when one scoped state owner and its update model fit the application. Redux Toolkit with React-Redux adds selector-based subscriptions, middleware, and a mature action/debugging model. Compare the actual update and operational needs rather than assuming Context replaces every store or every app needs Redux.

**Boundary**: Context notifies consumers of a changed provider value; dispatch-only contexts can keep that value stable, but state readers still update when state changes.

**Follow-up they'll ask**: How would you compare Redux Toolkit with another external store for this application?

#### Q25: How do you prevent race conditions when fetching data in `useEffect`?

**Answer**: If a query changes from A to B, B may resolve first and then be overwritten by A. Cleanup should abort supported work and mark that Effect instance obsolete; guard success, failure, and finally paths. Define whether prior data stays visible while B loads.

**Boundary**: Aborting is best-effort and cannot roll back a request the server already processed. Shared caches and mutations need their own identity and ordering contracts.

**Follow-up they'll ask**: How do modern data fetching libraries solve this?


### Section 5: Patterns & Architecture

#### Q26: When would you use a Compound Component pattern over passing multiple props?

**Answer**: Use compound components when several parts need shared state and callers should control how those parts are arranged. A data-driven prop such as `options` can be simpler when callers do not need structural control; the choice is an API trade-off, not a universal hierarchy.

**Boundary**: Context makes state available to descendants; it does not validate required parts, their order, or accessibility relationships.

**Follow-up they'll ask**: How do you pass state between the parent and child in this pattern?


#### Q27: In what scenarios are Higher-Order Components (HOCs) still preferred over Hooks?

**Answer**: Hooks reuse stateful logic inside a component. A wrapper or higher-order component composes around a component and can alter its public props or placement; it remains useful for compatibility with an existing wrapper API or a cross-cutting boundary.

**Boundary**: HOCs add a component boundary and can obscure props, refs, and display names. A custom Hook cannot decide whether its caller renders children, but a normal wrapper can; an HOC is only one way to build that wrapper.

**Follow-up they'll ask**: Why can't a hook conditionally prevent a component from rendering?


#### Q28: When should you use the Render Props pattern today?

**Answer**: A render prop lets the caller supply rendering logic to a component that owns some state or behavior. A Hook is usually simpler when the caller can own the markup; a render prop still fits when the component intentionally exposes values to a caller-defined view.

**Boundary**: Do not use render props solely to share ordinary state that a Hook can expose more directly. Consider nesting and callback identity as part of the API.

**Follow-up they'll ask**: How do you convert a render prop component into a custom hook?


#### Q29: How do you handle cross-cutting concerns like analytics in a React app?

**Answer**: Put analytics behind a typed interface with a clear owner. Route changes can emit page-view events at the routing boundary; business events should be emitted where the business action is confirmed, with consent, privacy filtering, and retry/batching policy handled centrally.

**Boundary**: A click is not proof that an operation succeeded. Keep analytics transport failures from changing business behavior, and avoid logging sensitive payloads.

**Follow-up they'll ask**: How do you test analytics without spamming the real tracking endpoint?


#### Q30: What is the Custom Hook pattern and how do you structure them?

**Answer**: A custom Hook packages logic that follows the Hook rules. Each call owns its own state unless it subscribes to a shared store or service; sharing the same function does not share its state. Return the data and actions that make the caller's contract clear.

**Boundary**: Extract a Hook when it gives a coherent reusable contract, not merely to shorten a component. Keep ownership and Effect timing understandable to its caller.

**Follow-up they'll ask**: How do you test a custom hook that uses context and side effects?


#### Q31: How do Error Boundaries work and what are their limitations?

**Answer**: A class Error Boundary handles descendant errors reported during React rendering and selected lifecycle work, then renders fallback UI. Event-handler exceptions and errors from arbitrary timers or Promise callbacks need local handling. React can report rejected resources read with `use` and errors thrown in a `useTransition` Action to a boundary.

**Boundary**: Boundaries do not catch errors thrown by the boundary itself or server rendering. Put them around a meaningful recovery boundary and log/report the original error separately from the fallback.

**Follow-up they'll ask**: How do you catch an error inside a `fetch` callback using an Error Boundary?

### Section 6: React 18/19 Modern Features

#### Q32: What can startTransition do, and what can it not do?

**Answer**: startTransition runs its callback immediately and marks eligible state updates inside it as non-urgent. React may interrupt the resulting render for urgent work, but synchronous CPU work in the callback still blocks JavaScript. After an await, state updates currently need another transition wrapper to receive transition semantics.

**Boundary**: A transition is neither a debounce nor a network-ordering guarantee. Controlled input state must update synchronously.

**Follow-up they'll ask**: What is the difference between `startTransition` and `setTimeout`?


#### Q33: When should you use `useDeferredValue` instead of debouncing?

**Answer**: useDeferredValue lets an urgent render use the new value while a slower subtree can continue showing the previous value until React commits the updated subtree. It has no fixed wait interval and does not prevent a request from being sent.

**Boundary**: Deferral is for rendering work, not request rate limiting. If users see older results, make that state clear and ensure the result identity still matches the current query.

**Follow-up they'll ask**: How do you visually indicate to the user that a deferred value is currently updating?


#### Q34: How does React's use API read promises and context?

**Answer**: use(promise) reads a cached Promise during render: a pending Promise suspends to the nearest Suspense boundary, and a rejection is reported to an Error Boundary. A fresh uncached Promise on each render does not satisfy this resource contract. use(context) reads a context value and has a separate Server Component restriction.

**Boundary**: use may be called in a condition or loop within a component or Hook, but not inside try/catch. It is a special API, not a general exception to the Rules of Hooks.

**Follow-up they'll ask**: Can you call `use()` conditionally inside an `if` statement?


#### Q35: What is the real use case for `useOptimistic`?

**Answer**: useOptimistic overlays temporary UI state while an Action is pending. An optional reducer recalculates that overlay against the latest base value; when the Action finishes, the UI returns to the current base, which should be updated with the confirmed result on success.

**Boundary**: The optimistic layer is not persisted server data and does not serialize concurrent mutations. Surface failure and define how conflicting updates are reconciled.

**Follow-up they'll ask**: How did we do this before React 19, and why is this better?


#### Q36: How does `useActionState` simplify form submissions?

**Answer**: useActionState connects an Action to state and returns the current state, a dispatch function, and a pending flag. For a form Action, React passes the previous state and submitted FormData to the Action; its return value becomes the next state.

**Boundary**: It can use an ordinary async function. Pre-hydration progressive enhancement requires a Server Function in a React Server Components setup and is usually wired by the framework; a client-only form does not gain it automatically.

**Follow-up they'll ask**: How does this work progressively if JavaScript is disabled?


#### Q37: What is the difference between Server Components (RSC) and SSR?

**Answer**: Server-side rendering produces HTML for the initial response; hydration attaches client behavior to Client Components. React Server Components define a server/client module and data boundary: server component implementations stay on the server, and their rendered result is transported to the client. Frameworks can combine RSC with HTML streaming and hydration.

**Boundary**: RSC does not guarantee a smaller bundle or provide a database API. Server-only code can access server resources through the framework; Client Components still need browser JavaScript, and the boundary adds serialization and deployment constraints.

**Follow-up they'll ask**: Can a Server Component use `useState`?


### Section 7: Senior System Design Questions

#### Q38: How would you architect a complex real-time dashboard in React?

**Answer**: Validate incoming messages, track sequence gaps, and reduce them into a bounded snapshot outside the component tree. Publish at a cadence the product can tolerate through focused subscriptions, then profile render, commit, layout, and paint before choosing memoization or virtualization. External-store updates remain blocking; transitions cannot make arbitrary store mutations non-blocking.

**Trade-off**: Buffering can reduce notifications but delays visibility. Coalesce only updates whose meaning allows it; append-only events and transactional state cannot be dropped indiscriminately.

**Follow-up they'll ask**: How do you handle a scenario where a socket pushes 1,000 updates per second?


#### Q39: Design an infinite scrolling list that handles millions of items.

**Answer**: Separate data pagination from DOM virtualization. Fetch pages, render only the visible window plus overscan, use stable record IDs, and bound retained data. Dynamic heights require measurement and offset correction; a single enormous spacer can exceed browser layout limits.

**Trade-off**: Virtualization complicates focus, screen-reader navigation, browser find, and scroll restoration. Compare it with pagination and windowed scrolling against the product's access and navigation needs.

**Follow-up they'll ask**: How do you handle items with dynamic, unknown heights?


#### Q40: How would you structure a monorepo containing multiple React applications sharing components?

**Answer**: Start with package-manager workspaces and explicit package boundaries. Define exports, dependency direction, shared React/type versions, and whether consumers run source or built output. Build and test affected packages in dependency order; choose a task runner only if graph execution or caching solves a measured need.

**Trade-off**: A monorepo simplifies coordinated changes but increases build-graph, dependency, and release-policy work. Deploy each app independently when its runtime and release cadence differ.

**Follow-up they'll ask**: How do you prevent one app from breaking when you update a shared component?


#### Q41: Describe your strategy for migrating a legacy SPA to a Next.js App Router application.

**Answer**: Define the migration boundary from traffic and session ownership. Inventory routes, deep links, assets, authentication/CSRF, API contracts, and rollback needs; route a small path set to the new app behind a traffic boundary, observe errors and latency, then expand in reversible waves.

**Boundary**: Do not assume cookies, rewrites, asset paths, or SPA fallback behave identically across both deployments. Verify the chosen Next.js and proxy configuration in the target runtime before moving routes.

**Follow-up they'll ask**: How do you share authentication state between the old SPA and the new Next.js app?


#### Q42: How do you handle authentication and protected routes effectively?

**Answer**: Treat client route guards as user experience, not authorization. The server must authenticate and authorize every protected operation and resource. HttpOnly cookies reduce JavaScript access to session tokens but do not prevent XSS or remove CSRF controls; refresh-token rotation needs expiry, replay handling, and coordination for concurrent refreshes.

**Boundary**: Do not blindly retry every 401: distinguish expired credentials from authorization failure, avoid retry loops, and define behavior for requests made while refreshing.

**Follow-up they'll ask**: Why is storing a JWT in localStorage a security risk?


#### Q43: What is your approach to testing a complex React application?

**Answer**: Choose test layers by failure cost: unit-test pure transformations, render components through the DOM to verify user-visible behavior, contract-test service boundaries, and run browser tests for critical journeys. Mock at the network boundary when useful, and separately test server authorization and validation. Type checking and linting are static checks, not behavioral tests.

**Trade-off**: Broad end-to-end suites are slower and more environment-sensitive, so keep them focused on high-risk flows. Include keyboard, focus, loading, empty, and error states where they are part of the contract.

**Follow-up they'll ask**: Why is it better to query elements by their ARIA role rather than test IDs?


## Answer checklist

- Name the public contract before an implementation detail.
- Trace a concrete update or failure through the component tree.
- State the product or consistency trade-off.
- Say what you would measure or test before choosing an optimization.

## Summary

Strong React answers start with ownership, identity and the public contract. Trace the update or failure through render and commit, then choose a boundary that fits the product's consistency, performance and accessibility needs. Treat memoization and scheduler internals as conditional tools; verify behavior with focused tests and representative measurements.

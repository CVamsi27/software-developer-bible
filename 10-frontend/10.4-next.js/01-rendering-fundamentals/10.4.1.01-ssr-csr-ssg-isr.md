# SSR, CSR, SSG, and ISR in Next.js

A product page has shared descriptions, stock that changes, and an Add to Cart control. One page can serve all three without giving the entire route one rendering mode. Decide when each part is produced, whether its result may be shared, and which behavior needs browser JavaScript.

## Definition

Rendering strategy describes when HTML or UI is produced and how generated output is reused. Static Site Generation (SSG) prepares shareable output before a request. Server-Side Rendering (SSR) prepares output while handling a request. Client-Side Rendering (CSR) produces data-driven UI in the browser after JavaScript runs. Incremental Static Regeneration (ISR) reuses generated output and refreshes it under a time or invalidation policy.

> **Textbook Definition:** A rendering strategy assigns computation to build time, request time, or the browser, then defines whether and how its output can be reused. These choices are independent of a component's server or client module boundary.

## First Principles

A server can create HTML before or during a request, and a browser can add behavior after receiving it. Reusing a result across visitors saves work only when those visitors are allowed to see the same result. Its age is a separate contract: every cache needs an acceptable lifetime and a way to refresh.

This gives three decisions:

1. **Where does the code need to run?** Server code can access protected services. Browser code is needed for local interaction and browser APIs.
2. **When can the first useful output be produced?** Build-time output avoids request work; request-time output can use the current request; browser fetching waits for JavaScript and a later network response.
3. **How may the result be reused?** Choose whether it is private or shared, how old it may be, and which event or policy invalidates it.

## Trace one product route

In the App Router, the page can combine these decisions instead of choosing one label for every component.

| Part of the page | Rendering and reuse decision | Engineering reason |
| ------------------------------------ | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Product description and photos | Build-time or cached server output | All visitors may share it for the chosen freshness window |
| Inventory and account-specific price | Request-specific server read, streamed behind a Suspense boundary if slow | The response may depend on current stock, identity, or request data |
| Add to Cart | Client Component hydrated in the browser | The button needs event handling, but its surrounding page can still arrive as HTML |

A cached product price can be old by the time someone checks out. The checkout operation must re-read and authorize the current price and stock; rendered output is not a transaction guarantee.

With Cache Components enabled in Next.js 16, the route can prerender a static shell, cache shareable work with the use cache directive, and defer request-dependent work behind Suspense. Cache Components are opt-in through the cacheComponents setting. Without them, the App Router uses its existing route and data cache rules; inspect the actual fetch options and route inputs instead of assuming that a route or server component is either always static or always fresh.

## Keep the labels distinct

The labels describe timing and reuse, not the entire React component tree:

- **SSG** means shared output is produced during a build or prerender step.
- **SSR** means output is produced for a request. It can still use cached data or a CDN response.
- **ISR** means generated output is reused and made eligible for refresh. A time interval is an eligibility threshold: a later request can trigger regeneration, and a failed refresh leaves the last successful output available.
- **CSR** means browser code fetches or derives data and renders the resulting UI after JavaScript runs. It is not a synonym for Client Components.

A Client Component marks a boundary in the client module graph, but Next.js can still prerender its initial HTML on the server and hydrate it in the browser. Hydration attaches event behavior to matching HTML; it does not mean the page's data was fetched in the browser. The [Server Components](10.4.1.03-server-components.md) and [Client Components](10.4.1.04-client-components.md) chapters trace that boundary in detail.

Existing Pages Router applications express these choices with getStaticProps/getStaticPaths for build-time output, getServerSideProps for request-time output, and revalidate for ISR. The App Router uses route and data caching; with Cache Components enabled, it can combine prerendered, cached, and request-time sections in one route. The [ISR chapter](../03-data-and-caching/10.4.3.05-incremental-static-regeneration.md) owns its regeneration and invalidation sequence.

## Protect the data contract

Build-time output and shared caches can be delivered to many visitors. Never put visitor-specific data in them. Server-side execution alone does not make a response private: set the deployment's response-cache policy and make sure every cache key includes the dimensions that determine whether content can be shared.

Request-time rendering also does not guarantee fresh data. A CDN, framework cache, database replica, or upstream service can return older values. Set a freshness budget for each layer, and make a mutation invalidate only the affected path or tag. The [Data and Caching chapter](../03-data-and-caching/10.4.3.03-caching.md) covers those controls.

## Verify the behavior you deploy

Inspect the production build output to see what Next prerenders. Then test cold and warm requests, two different user identities, stale data, failed refreshes, and on-demand invalidation through the actual hosting cache. Measure generated HTML, the RSC payload, and client JavaScript separately; a rendering label alone does not predict bundle size or latency. Development behavior is not proof of production cache behavior.

## Summary

Choose rendering along three independent axes: where code runs, when useful output is produced, and whether that output can be shared or reused. Keep private data request-scoped, put interaction behind a narrow client boundary, and define a freshness and invalidation policy for every shared result.

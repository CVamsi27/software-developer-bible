# SSR, CSR, SSG, and ISR in Next.js

An online catalog combines product text that changes occasionally, inventory that may change each minute, and a cart control that responds to clicks. Rendering each value at the same time and sharing it under the same cache policy creates either stale data, unnecessary server work or privacy bugs. Choose when each part is produced, where its code runs, and who may reuse its output.

```tsx
// One route, three strategies composed:
<article>
  <ProductCopy />        {/* static: public, stable */}
  <Suspense fallback={<PriceSkeleton />}>
    <PersonalPrice />    {/* request-time: authorized per user */}
  </Suspense>
  <CartButton />         {/* client: interaction */}
</article>
```

## Definition

A **rendering strategy** determines where and when application code produces the UI — **static rendering (SSG)** before a request, **request-time server rendering (SSR)** per request, or **client-side rendering (CSR)** in the browser after load — while **ISR** revalidates cached static output over time or on demand. Cache policy stays a separate decision: whether output or data may be reused, and when it must refresh.

> **Textbook Definition:** A rendering strategy chooses where and when UI computation occurs. A separate cache policy defines whether its output or input data can be reused and when it becomes stale; the server/client module boundary determines where component code is allowed to run.

## First Principles

Keep three questions separate. **When must the data be read?** Public copy tolerates a stale window; an account balance needs the current request. **Who can share the result?** A cached response is safe only when every reader may see the same representation — request-time rendering alone never makes a downstream cache private. **Where does interaction belong?** Database access and credentials stay server-side; event handlers and browser APIs live in Client Components.

```text
[Before request] ─► Static output: generate and reuse an allowed representation
[At request]     ─► Server rendering: use request-specific inputs where required
[On revalidation] ─► ISR/cache policy: refresh eligible cached output by policy
[In browser]     ─► CSR: run interaction or data work that belongs on the client
```

## 1. Static Site Generation (SSG)

Static rendering produces HTML and React Server Component (RSC) output before the request. In the App Router, `generateStaticParams` selects dynamic path values to generate; it does not by itself define how the page's data is cached:

```typescript
// app/products/[id]/page.tsx
import { notFound } from 'next/navigation'
import { getProduct, getTopProductIds } from '@/lib/catalog'

// Pre-render the top 500 catalog items at build time
export async function generateStaticParams() {
  const ids = await getTopProductIds()
  return ids.map((id) => ({ id }))
}

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const product = await getProduct(id)
  if (!product) notFound()

  return (
    <article>
      <h1>{product.title}</h1>
      <p>{product.description}</p>
    </article>
  )
}
```

The exact result depends on the App Router cache model in use. Check the production build output to confirm which paths and components were actually prerendered.

## 2. Server-Side Rendering (SSR)

When output depends on request data such as an authenticated session, render that part at request time and authorize before reading private data. With the previous App Router cache model, request APIs such as `cookies()` and `headers()` make the route dynamic. With Cache Components enabled, request-dependent content can instead sit behind a `<Suspense>` boundary while a safe static shell is prerendered:

```typescript
// app/account/orders/page.tsx
import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'
import { getOrdersForUser } from '@/lib/orders'

export default async function OrdersPage() {
  const cookieStore = await cookies()
  const sessionToken = cookieStore.get('session_id')?.value
  if (!sessionToken) redirect('/login')

  // Executed dynamically on each incoming HTTP request
  const orders = await getOrdersForUser(sessionToken)

  return (
    <section>
      <h2>Your Orders</h2>
      <ul>
        {orders.map((order) => (
          <li key={order.id}>{order.id}: {order.total}</li>
        ))}
      </ul>
    </section>
  )
}
```

Request-time rendering gives the code access to current request inputs, but adds server work and does not guarantee that the database or an upstream service returns fresh data.

## 3. Incremental Static Regeneration (ISR)

In the previous App Router cache model, a time-based revalidation interval or on-demand invalidation can refresh a cached route without rebuilding the entire application. This example uses that model; route-segment `revalidate` is not supported when Cache Components are enabled:

```typescript
// app/catalog/page.tsx
import { getCatalogOverview } from '@/lib/catalog'

// Previous App Router cache model; not used with cacheComponents: true
export const revalidate = 60

export default async function CatalogPage() {
  const catalog = await getCatalogOverview()

  return (
    <main>
      <h1>Catalog Overview</h1>
      <p>Items in store: {catalog.totalCount}</p>
    </main>
  )
}
```

After the interval, a later request can trigger regeneration. A successful regeneration replaces the cached result; if it fails, Next.js can continue serving the last successful output and retry on a later request. The exact revalidation and stale-serving behavior depends on the API and cache profile.

Use `revalidatePath('/catalog')` to invalidate path-based output. In Next.js 16, `revalidateTag('catalog', 'max')` uses stale-while-revalidate behavior; do not copy the deprecated one-argument form into new code. For the broader API and failure cases, see [Incremental Static Regeneration](../03-data-and-caching/10.4.3.05-incremental-static-regeneration.md).

## 4. Client-Side Rendering (CSR)

CSR is useful when UI or data should be produced in the browser, but it delays that content until client code runs and can increase network and main-thread work. Use a narrow Client Component for interaction; do not move an entire route to CSR just because it contains a button:

```typescript
// app/products/live-stock.tsx
'use client'

import { useState, useEffect } from 'react'

export function LiveStockTicker({ productId }: { productId: string }) {
  const [stock, setStock] = useState<number | null>(null)

  useEffect(() => {
    let active = true
    const controller = new AbortController()

    async function fetchStock() {
      try {
        const res = await fetch(`/api/stock/${productId}`, { signal: controller.signal })
        const data = await res.json()
        if (active) setStock(data.count)
      } catch {
        // Fallback or error handled locally
      }
    }

    void fetchStock()
    return () => {
      active = false
      controller.abort()
    }
  }, [productId])

  if (stock === null) return <span>Checking real-time stock…</span>
  return <span>Available in stock: {stock} units</span>
}
```

`'use client'` defines a client module boundary, not a client-only rendering switch. On an initial load, Next.js normally prerenders the component's initial HTML; the browser hydrates it, then runs effects. The example's stock request starts only after that browser commit.

## 5. Hybrid Architecture and Pre-Ship Checks

These labels describe different axes, so one route can combine them — prerendered public copy, request-time personalized price, hydrated cart control. With Next.js 16 Cache Components enabled, a static shell can contain cached components while request-dependent components stream behind Suspense:

| Route Component | Strategy | Runtime Behavior |
| :---------------------------- | :-------------------------- | :------------------------------------------------------------------------------ |
| **Public description** | Static or explicitly cached | Share only if all cache readers may see the same content. |
| **Personal price** | Request-time server work | Read and authorize using the current request; prevent shared-cache leakage. |
| **Stock indicator** | Explicit freshness policy | Choose its acceptable stale window and source-of-truth behavior. |
| **Cart control** | Client interaction | Hydrate the control; validate price and stock again on the server when writing. |

Next.js 16 supports the previous App Router cache model and Cache Components. New apps created with the recommended `create-next-app` defaults enable Cache Components; existing apps may still use the previous model. Check `next.config` before applying an example: with Cache Components, mark reusable work with `'use cache'`, set its lifetime with `cacheLife`, and keep request-specific data outside that cached scope.

Before shipping, verify three failure modes. **Sharing personalized output**: a cache key or boundary that omits identity/tenant scope can expose data — keep private reads request-bound and authorize at the data-access boundary. **Treating SSR as freshness**: request-time rendering does not bypass stale replicas or upstream HTTP caches. **Hydration mismatch**: rendering client-only values (`window.innerWidth`, `localStorage`, `new Date()`) during render produces server/client markup skew — synchronize client state inside `useEffect` instead.

## Summary

Choose rendering time, cache scope and client interaction separately. Static output is reusable only for data every reader may share; request-time rendering handles request-dependent work but cannot promise source freshness; ISR describes a revalidation policy; CSR belongs where browser execution is needed. In Next.js 16, identify whether the app uses Cache Components or the previous model before relying on defaults.

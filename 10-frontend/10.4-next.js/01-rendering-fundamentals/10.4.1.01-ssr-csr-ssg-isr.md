# SSR, CSR, SSG, and ISR in Next.js

Every web application faces an unavoidable tension: how to deliver pages with the instant speed of a static file, the live accuracy of a database query, and the rich interactivity of a native app—without burning server budgets or shipping bloated JavaScript bundles.

Pick pure Client-Side Rendering (CSR), and users stare at a blank white screen while the browser downloads, parses, and executes megabytes of JavaScript, leaving search engine crawlers with an empty shell. Pick pure Server-Side Rendering (SSR), and every incoming request forces the origin server to compute markup from scratch, driving up Time to First Byte (TTFB) and straining databases under traffic surges. Pick pure Static Site Generation (SSG), and build times multiply across thousands of catalog pages while inventory counts become dangerously stale.

Next.js replaces these rigid, all-or-nothing choices with a unified rendering continuum. Instead of forcing an entire application into one archetype, modern Next.js enables developers to blend build-time static generation, on-demand server rendering, background cache revalidation, and browser hydration on the exact same route.

## Definition

A **rendering strategy** determines where and when application code transforms into HTML and interactive UI, as well as how that output is cached and reused across requests.

- **Static Site Generation (SSG):** Pre-renders HTML and React Server Component (RSC) payloads during application build time or prerender phases for maximum cacheability.
- **Server-Side Rendering (SSR):** Renders HTML and RSC payloads dynamically on the server for each incoming HTTP request, enabling real-time personalization.
- **Client-Side Rendering (CSR):** Renders interactive views directly in the browser using client JavaScript after an initial HTML shell arrives.
- **Incremental Static Regeneration (ISR):** Serves cached pre-rendered pages while regenerating updated versions asynchronously in the background based on time intervals or on-demand cache tags.

> **Textbook Definition:** A rendering strategy assigns computation to build time, request time, or the browser, then defines whether and how its output can be reused. These choices are independent of a component's server or client module boundary.

## First Principles

At the architectural level, rendering decisions flow from three fundamental questions:

1. **When is the input data known?** If product titles and marketing copy change only during content deployments, computing them at request time wastes CPU cycles. Conversely, if an account balance depends on an active session cookie, it cannot exist before the request arrives.
2. **Who is allowed to see the output?** Public content can be cached globally at the edge CDN and shared among millions of visitors. Private or tenant-scoped data must remain strictly isolated to the requesting user session.
3. **Where must execution occur?** Reading directly from internal microservices and databases belongs in a trusted server environment to protect secrets. Listening for pointer gestures, managing local component focus, and reading browser APIs require the browser runtime.

```text
[Build Time]  ────► SSG: Compute once, store at CDN edge, serve instantly to all
[Request Time]────► SSR: Read HTTP headers/cookies, fetch live DB, stream HTML
[Background]  ────► ISR: Serve stale cache instantly, recompute in background on trigger
[Browser]     ────► CSR: Download JS bundle, mount DOM, run client effects & handlers
```

## The Four Strategies in Practice

To see how these concepts map to concrete engineering decisions, consider a retail product page: its title and specifications are public and stable, its inventory and personalized pricing fluctuate by user, and its cart button requires client-side event handling.

### 1. Static Site Generation (SSG)

SSG produces static HTML and RSC payloads during `next build`. The hosting edge network can serve these files directly from storage with sub-millisecond latency. In the App Router, dynamic route segments pre-render paths using `generateStaticParams`:

```typescript
// app/products/[id]/page.tsx
import { notFound } from 'next/navigation'
import { getProduct, getTopProductIds } from '@/lib/catalog'

// Pre-render the top 500 catalog items at build time
export async function generateStaticParams() {
  const ids = await getTopProductIds()
  return ids.map((id) => ({ id }))
}

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const product = await getProduct(id)
  if (!product) notFound()

  return (
    <article>
      <h1>{product.title}</h1>
      <p>{product.description}</p>
    </article>
  )
}
```

Routes without dynamic request inputs (such as cookies or un-cached data calls) default to static pre-rendering automatically.

### 2. Server-Side Rendering (SSR)

When a page requires runtime request information—such as geolocation headers, authentication cookies, or real-time inventory counts—Next.js renders the segment on demand. Invoking dynamic APIs like `cookies()` or `headers()` from `next/headers` immediately opts that subtree into dynamic request-time execution:

```typescript
// app/account/orders/page.tsx
import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'
import { getOrdersForUser } from '@/lib/orders'

export default async function OrdersPage() {
  const cookieStore = await cookies()
  const sessionToken = cookieStore.get('session_id')?.value
  if (!sessionToken) redirect('/login')

  // Executed dynamically on each incoming HTTP request
  const orders = await getOrdersForUser(sessionToken)

  return (
    <section>
      <h2>Your Orders</h2>
      <ul>
        {orders.map((order) => (
          <li key={order.id}>{order.id}: {order.total}</li>
        ))}
      </ul>
    </section>
  )
}
```

Dynamic rendering ensures freshness, but shifts latency and computation back to the origin server.

### 3. Incremental Static Regeneration (ISR)

ISR provides the speed of static delivery without requiring full application rebuilds when content changes. By declaring a revalidation window or associating data fetches with cache tags, Next.js implements the stale-while-revalidate pattern:

```typescript
// app/catalog/page.tsx
import { getCatalogOverview } from '@/lib/catalog'

// Revalidate this page in the background at most once every 60 seconds
export const revalidate = 60

export default async function CatalogPage() {
  const catalog = await getCatalogOverview()

  return (
    <main>
      <h1>Catalog Overview</h1>
      <p>Items in store: {catalog.totalCount}</p>
    </main>
  )
}
```

When a request arrives after the 60-second window:
1. The CDN immediately serves the existing (stale) cached page to the visitor without blocking.
2. In the background, Next.js initiates regeneration of the route.
3. Once successfully re-rendered, the cache updates with the new output for all future requests.
4. If background regeneration throws an error, the previous cache remains active, preventing user-facing outages.

On-demand invalidation via `revalidatePath('/catalog')` or `revalidateTag('catalog')` inside Server Actions allows immediate cache purging upon CMS webhook events or user edits.

### 4. Client-Side Rendering (CSR)

CSR delegates rendering logic and data fetching to the browser after the initial page structure loads. While traditional SPAs rendered entire applications this way, the Next.js App Router confines CSR to interactive leaf components using the `'use client'` boundary:

```typescript
// app/products/live-stock.tsx
'use client'

import { useState, useEffect } from 'react'

export function LiveStockTicker({ productId }: { productId: string }) {
  const [stock, setStock] = useState<number | null>(null)

  useEffect(() => {
    let active = true
    const controller = new AbortController()

    async function fetchStock() {
      try {
        const res = await fetch(`/api/stock/${productId}`, { signal: controller.signal })
        const data = await res.json()
        if (active) setStock(data.count)
      } catch {
        // Fallback or error handled locally
      }
    }

    void fetchStock()
    return () => {
      active = false
      controller.abort()
    }
  }, [productId])

  if (stock === null) return <span>Checking real-time stock…</span>
  return <span>Available in stock: {stock} units</span>
}
```

Notice the critical distinction: `'use client'` does **not** mean the component runs exclusively in the browser. Next.js still pre-renders its initial markup into server HTML during SSR/SSG; the browser then hydrates that markup and executes `useEffect` hooks.

## Modern Hybrid Architecture: Beyond Whole-Page Labels

Historically, developers had to choose between SSG, SSR, or CSR for an entire route. In modern Next.js, a single route can seamlessly compose all four paradigms:

| Route Component | Strategy | Runtime Behavior |
| :---------------------------- | :------- | :---------------------------------------------------------------- |
| **Page Header & Nav** | SSG | Pre-rendered once at build time; delivered globally from CDN. |
| **Product Description** | ISR | Stored in edge cache; revalidated every hour or upon CMS webhook. |
| **Price & Stock Stream** | SSR | Dynamic server query streamed inside a `<Suspense>` boundary. |
| **Add to Cart & Review Form** | CSR | Interactive Client Component hydrated in the browser. |

With Cache Components enabled in Next.js 16 (`cacheComponents: true`), developers declare caching intent directly on functions and subtrees with the `'use cache'` directive, replacing route-level configuration flags with fine-grained compiler-driven memoization.

## Critical Engineering Gotchas

- **Cache Poisoning via User State:** Pre-rendering a page or caching a fetch response that incorporates private session IDs, user roles, or personal data exposes that private data to subsequent visitors. Keep all authenticated reads dynamic or strictly client-side.
- **The "SSR Is Always Fresh" Illusion:** Triggering server-side rendering for every request does not guarantee fresh data if your database queries hit read-replicas with replication lag, or if your upstream microservice sits behind an uncoordinated HTTP cache.
- **The Hydration Mismatch Trap:** Attempting to render client-specific values (such as `window.innerWidth`, `localStorage`, or local time via `new Date()`) directly during component render produces different markup on the server than in the browser, triggering React hydration errors. Synchronize client-specific state inside `useEffect` or use an explicit initialization script.

## Summary

Modern web rendering is not a binary choice between static files and dynamic servers. SSG maximizes CDN caching for stable content, SSR enables authenticated server reads on demand, ISR provides low-latency delivery with background freshness, and CSR delivers interactive browser controls. By composing these strategies within a single route tree, Next.js delivers sub-millisecond initial page loads alongside real-time user experiences.

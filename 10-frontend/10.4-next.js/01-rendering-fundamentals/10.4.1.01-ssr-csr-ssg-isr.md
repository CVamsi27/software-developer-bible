# SSR, CSR, SSG, and ISR in Next.js

## Definition

Next.js supports several strategies for deciding where and when a page becomes HTML. **Static site generation (SSG)** creates HTML at build time: each request is inexpensive, but the result can become stale. **Server-side rendering (SSR)** creates HTML for a request: it can read fresh data, but uses server work for that request. **Client-side rendering (CSR)** creates the data-driven UI in the browser after its JavaScript loads. **Incremental Static Regeneration (ISR)** reuses static output and refreshes it under a revalidation policy. Choose based on when the page's data is known and how long users may see an older result.

> **Textbook Definition:** Rendering strategies determine where and when HTML or interactive UI is produced. CSR uses the browser, SSR uses request-time server work, SSG produces build-time output, and ISR refreshes stored output through supported runtime regeneration.

| Strategy | Full Name | Renders On | When |
| -------- | ------------------------------- | -------------------- | ---------------------------------------------------------------- |
| **CSR** | Client-Side Rendering | Browser | The browser fetches or derives data after JavaScript loads |
| **SSR** | Server-Side Rendering | Server | HTML is rendered for a request; data may still come from a cache |
| **SSG** | Static Site Generation | Build | HTML is generated from build-time inputs |
| **ISR** | Incremental Static Regeneration | Server/runtime cache | A stored result is reused and can be revalidated under a policy |

These describe when HTML or data is produced, not whether a component belongs to the server or client module graph. App Router pages can combine server-rendered output with interactive Client Components under any of these data-freshness strategies.


## First Principles

A product description can be shared with everyone; an account balance depends on the visitor. This difference comes before the choice of rendering API.

1. **Build-time code has no visitor request.** If all inputs are known then, produce reusable HTML. New content needs another build or runtime regeneration.
2. **Request-specific inputs need a request owner.** Read a session on the server for personalized HTML, or fetch authorized data in the browser. Never put one visitor's data into shared static output.
3. **Browser interaction needs browser code.** Sending HTML makes content visible before its interactive code is ready; hydration connects React behavior to that HTML. An interactive widget can exist inside a statically generated page.
4. **Reusing output accepts an age policy.** Decide which older values are acceptable and for how long. Rendering per request does not make an upstream cached response current, and regeneration does not happen merely because a clock expires.

## Why It Matters

Choose along four axes: who may share the result, which request inputs it needs, how stale the result may be, and what must be interactive. Check each cache layer—Next's data and route caches, the CDN or host, and the upstream service. Request-time rendering can still return stale cached data; a static result is safe only when it contains no visitor-specific information. ISR fits shared content when serving the last successful result during refresh is acceptable. Browser fetching fits data driven by browser-only inputs or ongoing interaction, with loading, failure, and authorization behavior owned by the client and API.

## How It Works

**Version scope:** App Router examples target Next.js 16.4 and use asynchronous request APIs such as Promise-based `params`; Next.js 15 introduced the async API with temporary synchronous compatibility during migration. The `fetch` and segment-config examples assume Cache Components is disabled: since Next.js 15, `fetch` is not persistently cached by default, although a route with no request-time inputs can still be prerendered. `cache: 'no-store'` makes a fetch request-bound; `cache: 'force-cache'` or a positive `next.revalidate` value enables reuse.

Next.js 16 introduced opt-in Cache Components, available in the current 16.4 release. Enable it with `cacheComponents: true` to compose a prerendered shell with dynamic content behind `<Suspense>` and explicitly cached functions or components marked with `'use cache'`. In this mode, decide which subtree is cached or request-specific; the route-wide SSG/SSR/ISR labels are not enough to describe the whole page. The examples below use the disabled model unless stated otherwise. See the current [Cache Components guide](https://nextjs.org/docs/app/getting-started/caching).

For time-based ISR, the revalidation interval is an eligibility threshold, not a timer: a later request triggers refresh, and the last successful output remains available while it runs. A route with no generated result has a cache miss and needs an initial render; whether the user waits for the complete result or sees a fallback/shell depends on that route's fallback and streaming configuration.

### Rendering Pipeline Comparison

```text
CSR: request → initial HTML → JavaScript → browser data request → populated UI
SSR: request → server data/render → HTML → hydrate interactive components
SSG: build → data/render → stored HTML; request → stored HTML → hydrate
ISR: stored HTML → eligible request → background refresh → replace on success
```

For a shared product page with a 60-second interval, a request at second 59 can reuse the current output. A request after expiry can receive that older output while regeneration runs. After success, later requests receive the replacement; if regeneration fails, the last successful version remains available. The [ISR chapter](../03-data-and-caching/10.4.3.05-incremental-static-regeneration.md) owns the detailed cache and invalidation trace. These are lifecycle differences, not promises about network speed or search rankings.

## Code Examples

These snippets compare rendering and caching boundaries, not complete API adapters. A TypeScript interface does not validate `res.json()`; decode external responses at the data boundary and authorize private reads on the server.

### CSR — Client-Side Rendering (Pages Router)

```typescript
// pages/dashboard.tsx
import { useEffect, useState } from 'react'

interface User {
  id: number
  name: string
  email: string
}

export default function Dashboard() {
  const [users, setUsers] = useState<User[]>([])
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState<string | null>(null)

  useEffect(() => {
    let active = true
    const controller = new AbortController()
    async function load() {
      try {
        const res = await fetch('/api/users', { signal: controller.signal })
        if (!res.ok) throw new Error('Could not load users')
        const data: User[] = await res.json()
        if (active) setUsers(data)
      } catch {
        if (active) setError('Could not load users. Please try again.')
      } finally {
        if (active) setLoading(false)
      }
    }
    void load()
    return () => { active = false; controller.abort() }
  }, [])

  if (loading) return <div>Loading...</div>
  if (error) return <p role="alert">{error}</p>

  return (
    <div>
      <h1>Dashboard</h1>
      {users.map(user => (
        <div key={user.id}>{user.name} — {user.email}</div>
      ))}
    </div>
  )
}

```

### CSR — Client-Side Rendering (App Router)

> The [Pages Router example](#csr--client-side-rendering-pages-router) uses the same effect and state logic. In `app/dashboard/page.tsx`, add `'use client'` before its imports; Next still prerenders the initial loading UI, then the browser fetches the users after hydration.

The CSR example assumes the API returns the declared `User[]` shape; TypeScript does not validate JSON. A production boundary should validate external data, and the API must authorize access. Aborting saves work where supported; the `active` flag separately prevents an obsolete completion from updating the UI.

### SSR — Server-Side Rendering (Pages Router)

```typescript
// pages/profile.tsx
import type { GetServerSideProps } from 'next'

interface ProfileProps {
  user: {
    id: number
    name: string
    email: string
    avatar: string
  }
}

export const getServerSideProps: GetServerSideProps<ProfileProps> = async (context) => {
  const { req } = context

  // Access cookies for authentication
  const token = req.cookies.token

  if (!token) {
    return { redirect: { destination: '/login', permanent: false } }
  }

  const res = await fetch('https://api.example.com/profile', {
    headers: { Authorization: `Bearer ${token}` }
  })

  if (res.status === 401) {
    return { redirect: { destination: '/login', permanent: false } }
  }
  if (!res.ok) throw new Error('Failed to fetch profile')
  const user = await res.json()

  return {
    props: { user }
  }
}

export default function Profile({ user }: ProfileProps) {
  return (
    <div>
      <h1>{user.name}</h1>
      <p>{user.email}</p>
      <img src={user.avatar} alt={user.name} />
    </div>
  )
}

```

### SSR — Server-Side Rendering (App Router)

```typescript
// app/profile/page.tsx
import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'

async function getUser() {
  const cookieStore = await cookies()
  const token = cookieStore.get('token')?.value

  if (!token) {
    redirect('/login')
  }

  const res = await fetch('https://api.example.com/profile', {
    headers: { Authorization: `Bearer ${token}` },
    cache: 'no-store' // Bypass Next's persistent data cache for this request
  })

  if (res.status === 401) redirect('/login')
  if (!res.ok) throw new Error('Failed to fetch user')

  return res.json()
}

export default async function ProfilePage() {
  const user = await getUser()

  return (
    <div>
      <h1>{user.name}</h1>
      <p>{user.email}</p>
    </div>
  )
}

```

A cookie proves only that a value was supplied. The profile service must validate it; a rejected session redirects, while an upstream failure remains an error. Rendering private HTML also requires private response/cache policy at the deployment boundary.

### SSG — Static Site Generation (Pages Router)

```typescript
// pages/blog/[slug].tsx
import type { GetStaticProps, GetStaticPaths } from 'next'

interface Post {
  slug: string
  title: string
  content: string
  publishedAt: string
}

interface PostProps {
  post: Post
}

export const getStaticPaths: GetStaticPaths = async () => {
  const res = await fetch('https://api.example.com/posts')
  if (!res.ok) throw new Error('Failed to fetch post paths')
  const posts: Post[] = await res.json()

  const paths = posts.map(post => ({
    params: { slug: post.slug }
  }))

  return {
    paths,
    fallback: false // 404 for unknown slugs
  }
}

export const getStaticProps: GetStaticProps<PostProps> = async ({ params }) => {
  const slug = params?.slug
  if (typeof slug !== 'string') return { notFound: true }

  const res = await fetch(`https://api.example.com/posts/${encodeURIComponent(slug)}`)
  if (res.status === 404) return { notFound: true }
  if (!res.ok) throw new Error('Failed to fetch post')
  const post = await res.json()

  return {
    props: { post }
  }
}

export default function BlogPost({ post }: PostProps) {
  return (
    <article>
      <h1>{post.title}</h1>
      <time>{post.publishedAt}</time>
      <div>{post.content}</div>
    </article>
  )
}

```

### SSG — Static Site Generation (App Router)

```typescript
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation'

interface Post {
  slug: string
  title: string
  content: string
}

async function getPost(slug: string): Promise<Post | null> {
  const res = await fetch(`https://api.example.com/posts/${encodeURIComponent(slug)}`, {
    next: { revalidate: false } // Static, no revalidation
  })

  if (res.status === 404) return null
  if (!res.ok) throw new Error('Failed to fetch post')
  return res.json()
}

// Generate static params at build time
export async function generateStaticParams() {
  const res = await fetch('https://api.example.com/posts')
  if (!res.ok) throw new Error('Failed to fetch post paths')
  const posts: Post[] = await res.json()

  return posts.map(post => ({
    slug: post.slug
  }))
}

export default async function BlogPost({
  params
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const post = await getPost(slug)

  if (!post) notFound()

  return (
    <article>
      <h1>{post.title}</h1>
      <div>{post.content}</div>
    </article>
  )
}

```

### ISR — Incremental Static Regeneration (Pages Router)

```typescript
// pages/products/[id].tsx
import type { GetStaticProps, GetStaticPaths } from 'next'

interface Product {
  id: string
  name: string
  price: number
  description: string
}

export const getStaticPaths: GetStaticPaths = async () => {
  const res = await fetch('https://api.example.com/products')
  if (!res.ok) throw new Error('Failed to fetch product paths')
  const products: Product[] = await res.json()

  return {
    paths: products.slice(0, 10).map(p => ({
      params: { id: p.id }
    })),
    fallback: 'blocking' // Generate on-demand for non-pre-rendered
  }
}

export const getStaticProps: GetStaticProps = async ({ params }) => {
  const id = params?.id
  if (typeof id !== 'string') return { notFound: true }

  const res = await fetch(`https://api.example.com/products/${encodeURIComponent(id)}`)
  if (res.status === 404) return { notFound: true }
  if (!res.ok) throw new Error('Failed to fetch product')
  const product = await res.json()

  return {
    props: { product },
    revalidate: 60 // Eligible for regeneration after 60 seconds
  }
}

export default function Product({ product }: { product: Product }) {
  return (
    <div>
      <h1>{product.name}</h1>
      <p>${product.price}</p>
      <p>{product.description}</p>
    </div>
  )
}

```

### ISR — Incremental Static Regeneration (App Router)

```typescript
// app/products/[id]/page.tsx
// Empty list enables static generation on demand (Cache Components disabled).
export async function generateStaticParams() { return [] }

interface Product {
  id: string
  name: string
  price: number
  description: string
}

async function getProduct(id: string): Promise<Product> {
  const res = await fetch(`https://api.example.com/products/${encodeURIComponent(id)}`, {
    next: {
      revalidate: 60, // Next visit after 60 seconds triggers background refresh
      tags: ['products'] // Tag-based revalidation
    }
  })

  if (!res.ok) throw new Error('Product not found')
  return res.json()
}

export default async function ProductPage({
  params
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const product = await getProduct(id)

  return (
    <div>
      <h1>{product.name}</h1>
      <p>${product.price}</p>
      <p>{product.description}</p>
    </div>
  )
}

```

### Fallback Rendering Strategies

```typescript
// Pages Router fallback options
export const getStaticPaths: GetStaticPaths = async () => {
  return {
    paths: [
      { params: { id: '1' } }, // Pre-rendered at build
      { params: { id: '2' } },
    ],
    fallback: 'blocking'
    // false: 404 for non-pre-rendered
    // true: direct visits may show fallback; client navigation/crawlers block
    // 'blocking': wait for server render, no fallback UI
  }
}

```

```typescript

export const dynamicParams = true // Allow on-demand generation

}

```

### Observe the cache rather than labeling it

Adding an `x-render-mode: isr` header in middleware only labels matched requests; it cannot prove that a page regenerated or that a cache served it. Inspect production build output, cache diagnostics and timestamps from controlled requests. Development behavior is not evidence of production cache reuse. See the [ISR chapter](../03-data-and-caching/10.4.3.05-incremental-static-regeneration.md) for the verification sequence.

## Real-World Use Cases

| Page Type | Strategy | Reason |
| ----------------------- | ----------------------- | ---------------------------------------------------------------------------------- |
| Marketing landing page | SSG | Content rarely changes |
| Blog posts | ISR | Static performance, occasional updates |
| User dashboard | SSR plus client updates | Personalized initial HTML; choose a live-update mechanism separately |
| E-commerce product page | ISR | Shared description can be stale; checkout rechecks price and availability |
| Admin panel | SSR and/or CSR | Initial content and interaction have separate needs; APIs still authorize requests |
| Documentation | SSG | Built from markdown, rarely changes |
| News article | ISR | Published once, updated rarely |
| Search results | SSR | Dynamic based on query parameters |

## Common Mistakes

### 1. Using SSR When SSG Would Suffice

```typescript
// BAD: Fetching static data on every request
export const getServerSideProps: GetServerSideProps = async () => {
  const data = await fetchStaticContent()
  return { props: { data } }
}

// GOOD: Pre-render at build time; this output stays unchanged until a new build
export const getStaticProps: GetStaticProps = async () => {
  const data = await fetchStaticContent()
  return { props: { data } }
}

```

### 2. Exposing Sensitive Data in SSG

`getStaticProps` runs on the server, so using an unprefixed secret there does not automatically add it to the client bundle. Secrets in query strings can leak into logs; put credentials in headers, and return only public fields because every returned prop is serialized into the generated page. Never generate shared HTML from a visitor's private data.

When content needs periodic refresh without a deployment, opt into ISR with a revalidation policy; that changes the example from build-only SSG to request-triggered regeneration.

### 3. Forgetting revalidate in ISR

```typescript
// BAD: Page will never update after build
export const getStaticProps: GetStaticProps = async () => {
  return { props: { data: await fetchData() } } // Missing revalidate
}

// GOOD: Set appropriate revalidation
export const getStaticProps: GetStaticProps = async () => {
  return {
    props: { data: await fetchData() },
    revalidate: 300 // Eligible for refresh after 5 minutes
  }
}

```

### 4. Mixing CSR and SSR Incorrectly

```typescript
// BAD: Using window in SSR
export const getServerSideProps: GetServerSideProps = async () => {
  const width = window.innerWidth // Error! window is undefined on server
  return { props: { width } }
}

// GOOD: Use useEffect for browser APIs
export default function Page({ initialData }) {
  const [width, setWidth] = useState(0)

  useEffect(() => {
    setWidth(window.innerWidth)
  }, [])

  return <div>Width: {width}</div>
}

```

### 5. Not Handling Loading States

When an App Router page awaits slow data, `loading.tsx` supplies a route fallback; a smaller `<Suspense>` boundary can leave the rest of the page visible. Put the await inside the component wrapped by the boundary—awaiting it in the parent blocks that parent before its fallback can render.

## Best Practices

1. **Set a freshness budget.** Identify the maximum acceptable age and the event that invalidates the result.
2. **Keep private data request-scoped.** Authorize on the server and prevent shared caches from storing personalized output.
3. **Use ISR only when stale output is safe.** Define what users see on a cache miss and when regeneration fails.
4. **Model caches independently.** A Next.js revalidation policy does not invalidate an unrelated CDN or upstream cache.
5. **Use browser fetching for browser-owned inputs.** Keep loading, cancellation, stale-response, and error behavior explicit.
6. **Place Suspense around the work that may wait.** The parent must return the boundary before a descendant can suspend beneath it.
7. **Measure production behavior.** Compare cold and warm requests, build duration, generated paths, and cache diagnostics; `next dev` does not prove production cache behavior.
8. **Use on-demand revalidation when source events need faster visibility than the time policy allows.** Authenticate the webhook and invalidate only the relevant path or tag.
9. **For mixed pages, evaluate Cache Components.** Cache shareable work explicitly and stream request-specific work behind a boundary.

## Performance Considerations

| Strategy | TTFB | FCP | LCP | SEO | Server Load |
| -------- | --------------------- | ----------------- | -------------------- | ---------------------------- | -------------------------------- |
| CSR | Shell delivery | JS/data-dependent | JS/data-dependent | Depends on crawler execution | API work remains |
| SSR | Render/data-dependent | Content in HTML | Asset/data-dependent | HTML available | Request rendering plus data work |
| SSG | Low (cached) | Usually fast | Asset-dependent | HTML available | Low origin load |
| ISR | Low on cache hits* | Usually fast | Asset-dependent | HTML available | Regeneration load |

*Warm ISR cache hits avoid a fresh render. A missing entry or blocking fallback may require request-time work; stale entries regenerate according to the configured policy.

### Bundle Size Impact

Rendering strategy and JavaScript footprint are separate choices. Pages Router pages hydrate their React code; App Router Server Components send an RSC payload without their implementation code, while Client Component islands still need JavaScript under SSR, SSG, or ISR.

## Summary

| Decision boundary | CSR | SSR | SSG | ISR |
| --------------------- | ------------------------------------------ | -------------------------------------------- | -------------------------- | ------------------------------------------ |
| Work happens | In the browser after JavaScript loads | Per request for HTML | At build time | At build time and on eligible revalidation |
| Freshness owner | API/cache policy | Data-cache policy | Next build | Revalidation policy |
| Main failure to guard | Loading, stale response, API authorization | Request failure and private response caching | Stale output until rebuild | Cache miss, stale response, failed refresh |
| Server work | API work remains | Rendering and data work per request | Build and API work | Build, cache and regeneration work |
| Initial HTML | May be only a shell | Available, possibly streamed | Available | Available when generated |

# App Router in Next.js

Traditional web routing treats navigation as a sequence of full-page replacements. When a user clicks from `/dashboard/analytics` to `/dashboard/settings`, naive routers tear down the entire DOM tree, discard active client state in sidebars, flash blank loading spinners, and re-fetch shared navigation data from scratch.

The Next.js **App Router** fundamentally reimagines routing as a nested component hierarchy. Built on top of React Server Components, it maps folder structures directly to nested layout trees. Shared layout shells remain mounted across transitions, sidebars preserve scroll position and local state, slow data panels stream in progressively without holding up fast UI, and error boundaries isolate crashes to specific panels without tearing down the entire screen.

Understanding the App Router means mastering how file-system conventions, asynchronous data fetching, and boundary encapsulation coalesce into a resilient, high-performance web architecture.

## Definition

The **App Router** is Next.js's file-system router built within the `app/` directory. Each directory represents a URL route segment, containing standardized file conventions (`page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, and `route.ts`) that define visual composition, streaming fallbacks, error handling, and API endpoints.

> **Textbook Definition:** The App Router maps filesystem segments to nested route and component trees. Segment conventions define composition and navigation boundaries, while React Server Component rules determine which modules execute on the server or in the browser.

## First Principles

The architecture of the App Router derives from three foundational requirements:

1. **Hierarchy dictates composition:** A URL like `/org/acme/projects/42` is inherently hierarchical. The organizational shell (`org`), the tenant workspace (`acme`), and the project details (`42`) represent nested containers. Mirroring this structure in the file system ensures that parent layouts wrap child views automatically.
2. **Partial rendering minimizes network and CPU cost:** During client-side navigation between sibling routes, only the leaf segment changes. The App Router fetches and re-renders only the changed segment, leaving parent layouts untouched in both memory and the DOM.
3. **Colocated boundaries contain blast radiuses:** An application should never fail completely because one non-critical widget crashed or stalled. Colocating `loading.tsx` and `error.tsx` alongside `page.tsx` scopes asynchronous latency and runtime exceptions strictly to that segment.

```text
app/
├── layout.tsx                 # [Root Layout] Wraps all pages; defines <html> & <body>
├── loading.tsx                # Global loading fallback for initial page boot
├── (marketing)/               # [Route Group] Visual grouping; omitted from URL path
│   └── page.tsx               # Renders at "/"
└── dashboard/                 # URL: "/dashboard"
    ├── layout.tsx             # [Sub-Layout] Dashboard sidebar & persistent shell
    ├── loading.tsx            # Suspense boundary for dashboard transitions
    ├── error.tsx              # Error boundary isolating dashboard crashes
    ├── page.tsx               # Renders at "/dashboard"
    └── settings/
        └── page.tsx           # Renders at "/dashboard/settings" (shares dashboard layout)
```

## The Routing Conventions

### 1. Root Layouts and Nested Layouts

Every Next.js application requires a root `app/layout.tsx`. It defines the root `<html>` and `<body>` tags and wraps all routes in the application.

```typescript
// app/layout.tsx — Root Layout (Required)
export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <html lang="en">
      <body>
        <header className="global-nav">Platform Header</header>
        {children}
      </body>
    </html>
  )
}
```

Nested layouts wrap their sub-tree and persist across child navigation:

```typescript
// app/dashboard/layout.tsx — Persistent Sub-Layout
export default function DashboardLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <div className="dashboard-grid">
      <aside className="sidebar">
        {/* State inside this sidebar survives navigation between child pages */}
        <nav>Dashboard Links</nav>
      </aside>
      <main className="content">{children}</main>
    </div>
  )
}
```

When a user navigates between `/dashboard/analytics` and `/dashboard/settings`, `DashboardLayout` remains mounted. Its DOM nodes are reused, client state is preserved, and unnecessary re-renders are completely avoided.

### 2. Layouts vs. Templates

While layouts preserve state across transitions, certain workflows require a complete remount—such as re-triggering entrance animations, resetting form drafts, or firing page-view analytics hooks. For these scenarios, Next.js provides `template.tsx`:

```typescript
// app/wizard/template.tsx — Remounts on every segment transition
export default function WizardTemplate({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <div className="step-animation-container">
      {/* Creates a fresh instance on every step change */}
      {children}
    </div>
  )
}
```

Next.js mounts a new instance of `template.tsx` on each navigation, resetting child component state and re-running client effects.

### 3. Dynamic Segments and Asynchronous Parameters

Dynamic segments capture URL variables using bracket notation:
- `[id]`: Matches a single dynamic segment (e.g., `/products/123`).
- `[...slug]`: Catch-all segment matching all subsequent paths (e.g., `/docs/setup/install`).
- `[[...slug]]`: Optional catch-all matching the root path and all sub-paths.

In modern Next.js (App Router), `params` and `searchParams` are delivered as **Promises**. This allows the framework to begin streaming the layout shell immediately while the route parameters resolve asynchronously:

```typescript
// app/products/[id]/page.tsx
import { notFound } from 'next/navigation'
import { getProduct } from '@/lib/products'

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const product = await getProduct(id)

  if (!product) {
    // Triggers nearest not-found.tsx boundary immediately
    notFound()
  }

  return (
    <article>
      <h1>{product.title}</h1>
      <p>{product.description}</p>
    </article>
  )
}
```

### 4. Route Groups and Multiple Root Layouts

Wrapping a folder name in parentheses, such as `app/(marketing)` or `app/(auth)`, creates a **Route Group**. Route groups organize file trees logically without affecting the public URL:
- `app/(marketing)/about/page.tsx` resolves cleanly to `/about`.
- `app/(auth)/login/page.tsx` resolves cleanly to `/login`.

Route groups allow applications to define completely distinct root layouts for different sections—for instance, a public marketing layout with a marketing header, and an authenticated app layout with an enterprise sidebar. Navigating between two separate root layouts triggers a full browser page load.

## Scoping Latency and Failures

The App Router provides declarative, file-based wrappers for asynchronous suspense and runtime error recovery:

```text
<Layout>
  <ErrorBoundary fallback={<Error />}>
    <Suspense fallback={<Loading />}>
      <Page />
    </Suspense>
  </ErrorBoundary>
</Layout>
```

- **`loading.tsx`:** Automatically wraps the sibling `page.tsx` in a React `<Suspense>` boundary. The fallback renders immediately while the asynchronous server page executes its queries.
- **`error.tsx`:** A React Client Component (marked with `'use client'`) that wraps the segment's page in an Error Boundary. If the page throws an unhandled exception during rendering, `error.tsx` renders a recovery UI without crashing the parent layout:

```typescript
// app/dashboard/error.tsx
'use client'

export default function DashboardError({
  error,
  reset,
}: {
  error: Error & { digest?: string }
  reset: () => void
}) {
  return (
    <div role="alert" className="error-card">
      <h2>Failed to load dashboard data</h2>
      <button onClick={() => reset()}>Try again</button>
    </div>
  )
}
```

To catch errors thrown within the root layout itself, Next.js requires a `global-error.tsx` file at the root of `app/`, which must define its own `<html>` and `<body>` tags.

## Advanced Routing Patterns: Parallel and Intercepting Routes

### Parallel Routes (`@slot`)

Parallel routes allow simultaneously or conditionally rendering multiple pages within the same layout. Named slots (such as `@feed` and `@analytics`) pass as direct props to the parent layout:

```typescript
// app/dashboard/layout.tsx
export default function DashboardLayout({
  children,
  analytics,
  team,
}: {
  children: React.ReactNode
  analytics: React.ReactNode
  team: React.ReactNode
}) {
  return (
    <section>
      <div>{children}</div>
      <div className="grid-split">
        {analytics}
        {team}
      </div>
    </section>
  )
}
```

When client-navigating, each slot maintains its independent URL state. On full browser refreshes, Next.js renders `default.tsx` for any slot that does not match the active URL segment.

### Intercepting Routes (`(.)`, `(..)`)

Intercepting routes allow loading a route from another part of the application within the current layout, displaying an overlay modal while updating the browser URL. When shared or hard-refreshed, the exact same URL renders the standalone canonical page.

```text
app/
├── feed/
│   ├── page.tsx                  # Photos feed
│   └── @modal/
│       ├── default.tsx           # Renders null when no modal is active
│       └── (.)photos/[id]/       # Intercepts "/photos/[id]" during client navigation
│           └── page.tsx          # Modal view
└── photos/
    └── [id]/
        └── page.tsx              # Standalone canonical photo page on full refresh
```

This pattern powers photo preview modals, checkout drawers, and authentication dialogs without sacrificing bookmarkable, shareable URLs.

## Critical Engineering Pitfalls

- **Layouts Are Never Authorization Gates:** Because layouts do not re-render when users navigate between child pages, an authentication or permission check placed solely inside a layout will not execute when a user moves to a sibling route. Always enforce access control at the data-access layer or within individual page components.
- **`error.tsx` Cannot Catch Its Own Layout:** An `error.tsx` boundary catches exceptions thrown by child components and sibling pages, but cannot catch errors thrown inside its sibling `layout.tsx`. To catch layout errors, place the error boundary in the parent folder.
- **Route Segment Config Deprecation:** In Next.js 16, legacy route-level config variables (such as `export const dynamic = 'force-dynamic'` or `revalidate = 60`) are superseded when Cache Components are enabled. Transition to fine-grained `'use cache'` directives and dynamic Suspense boundaries for robust performance.

## Summary

The App Router unifies routing, layout composition, streaming, and error boundaries into a coherent tree structure. By keeping shared layouts mounted, scoping loading and error states to individual segments, and offering powerful primitives like parallel and intercepting routes, Next.js delivers native-app responsiveness while preserving standard web URLs and edge cacheability.

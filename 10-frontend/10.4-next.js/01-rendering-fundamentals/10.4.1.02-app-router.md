# App Router in Next.js

A dashboard has a sidebar, a page that changes as people navigate, and slow panels that should not hold up the whole screen. The App Router gives each part an owner in the route tree, so shared UI, loading and failures have a clear scope.

## Definition

The **App Router** is Next.js's file-system router. Files under `app/` describe URL segments, pages, layouts, request handlers and the boundaries around them. Layouts and pages are Server Components by default; a client module boundary adds browser behavior where needed.

> **Textbook Definition:** The App Router maps filesystem segments to nested route and component trees. Segment conventions define composition and navigation boundaries, while React Server Component rules determine which modules execute on the server or in the browser.

## First Principles

A URL alone does not explain which parts of a screen should persist or what a visitor should see while new work is pending. The route tree needs three kinds of ownership:

1. **A route owner:** a page makes a segment renderable; folders above it describe the path.
2. **A shared owner:** a layout holds UI common to descendant pages, such as a dashboard sidebar.
3. **A boundary owner:** loading, error and not-found files decide which portion can be replaced when work waits or fails.

## Read the route tree

```text
app/
├── layout.tsx                    # required root document
├── (shop)/                       # group files without adding a URL part
│   └── products/
│       └── [id]/page.tsx         # /products/:id
├── dashboard/
│   ├── layout.tsx                # shared dashboard shell
│   ├── loading.tsx               # pending UI for this segment's subtree
│   ├── error.tsx                 # recovery UI for descendant render errors
│   ├── page.tsx                  # /dashboard
│   └── settings/page.tsx         # /dashboard/settings
└── api/orders/route.ts           # HTTP endpoint, not a page
```

The root `app/layout.tsx` is required and must render the document's `<html>` and `<body>`. If an application uses multiple root layouts inside route groups, each one supplies those tags; without a top-level root layout, define `/` inside one of the groups.

Folders add path segments unless their names use a routing convention. A `(group)` folder is organizational and adds no URL part. `[id]` captures one segment; `[...slug]` captures one or more; `[[...slug]]` also matches the route without a value. `page.tsx` exposes UI at a path. `route.ts` owns HTTP methods there, so a page and route handler cannot claim the same segment.

Dynamic route inputs are asynchronous in current App Router APIs. `generateStaticParams` can choose paths to prerender; it does not replace the page's data lookup or define what an unknown ID means.

```typescript
// app/products/[id]/page.tsx
import { notFound } from 'next/navigation'
import { getProduct } from '@/lib/products'

export async function generateStaticParams() {
  const popularProducts = await getPopularProducts()
  return popularProducts.map(({ id }) => ({ id }))
}

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const product = await getProduct(id)
  if (!product) notFound()

  return <main><h1>{product.name}</h1></main>
}
```

The helper functions are application code. A build-time list is only a rendering choice: the data helper still handles deletion, access rules and missing records. See [dynamic segments](https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes) and [generateStaticParams](https://nextjs.org/docs/app/api-reference/functions/generate-static-params) for version-specific behavior, including Cache Components.

## Let shared UI live as long as its route

A layout wraps its child segment and is reused during client navigation. If someone moves from `/dashboard` to `/dashboard/settings`, the dashboard shell can remain mounted while the page changes. Its in-memory state may survive that navigation, but not a full reload; use durable storage for state that must survive reloads. A layout is also not an authorization boundary: every protected read and mutation must enforce access where the data is used.

A `template.tsx` looks like a layout but creates a remount boundary when its segment key changes. Descendant client state resets and effects run again. Use it when that reset is part of the interaction. A change to search parameters alone does not create that segment change.

Route groups help organize sections with different layouts, such as `(marketing)` and `(account)`. Groups can define separate root layouts, but two files that resolve to the same public path conflict even if their group names differ.

When separate route groups each define a root layout, neither should rely on a shared `app/layout.tsx`; each root layout supplies its own `<html>` and `<body>`. Navigating between those roots performs a full page load, so keep groups separate only when that behavior is acceptable.

## Scope waiting and failure

`loading.tsx` supplies a Suspense fallback for its route subtree, allowing ready surrounding UI to remain visible while a slower part resolves. Put slow work beneath the boundary that should reveal first; if an ancestor awaits it before returning JSX, that boundary cannot show yet. Fine-grained Suspense behavior belongs to [Streaming](../03-data-and-caching/10.4.3.04-streaming.md).

`error.tsx` is a client error boundary for errors in descendant rendering. Because it sits beneath its segment's layout, it cannot catch that layout's own error. A parent boundary handles it; `global-error.tsx` handles failures in the root layout and must provide the document shell. Use `not-found.tsx` or `notFound()` for an absent resource, and an error boundary for an unexpected failure. Keep public error UI generic and send diagnostics through the server-side reporting path.

## Use parallel routes only when the screen has parallel state

An `@slot` folder supplies a named child to its parent layout without adding a URL segment. A dashboard can render its main page and an independently routed analytics panel together. A slot can retain its active page during client navigation. On a hard navigation, Next.js cannot recover an unmatched slot's previous client state, so Next.js 16 requires a `default.tsx` for every parallel slot; the implicit `children` slot may need one too. Return `notFound()` when an unmatched path must remain a 404, or `null` for an intentionally empty panel.

```text
app/feed/
├── layout.tsx
├── page.tsx
├── photos/[id]/page.tsx              # canonical direct page
└── @modal/
    ├── default.tsx
    └── (.)photos/[id]/page.tsx       # intercepted modal on soft navigation
```

The parent layout must render both branches:

```typescript
export default function FeedLayout({
  children,
  modal,
}: {
  children: React.ReactNode
  modal: React.ReactNode
}) {
  return <>{children}{modal}</>
}
```

The gallery can link to `/feed/photos/42`. A client navigation can show the intercepted page over the feed; opening or refreshing that URL shows the canonical page. Interception markers count route segments, not filesystem folders, so `@modal` does not count. The modal still needs accessible focus, labeling, dismissal and history behavior.

All parallel branches at a segment render on the server, even if the layout chooses not to display one. Hiding an admin slot in the layout does not protect its data. Authorize inside each branch before reading protected records. Parallel slots at the same segment also share rendering constraints; do not mix prerendered and request-dynamic work there. See [Parallel Routes](https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes) and [Intercepting Routes](https://nextjs.org/docs/app/api-reference/file-conventions/intercepting-routes).

## Keep request handlers and cache policy at their own boundary

A `route.ts` exposes HTTP methods such as `GET` or `POST`; it is not needed when a Server Component can call the data layer directly. A handler must authenticate, authorize, validate input and map failures before changing data. The [Route Handlers chapter](../02-routing-and-middleware/10.4.2.02-route-handlers.md) owns that API contract.

Rendering and caching are separate decisions. Route Segment Config exports such as `dynamic`, `revalidate` and `runtime` apply only in the configuration model that supports them; they are disabled when Cache Components are enabled. Prefer explicit per-data or per-component cache policy, and verify the chosen model against the deployed Next.js version. The [rendering strategy](10.4.1.01-ssr-csr-ssg-isr.md) and [data caching](../03-data-and-caching/10.4.3.03-caching.md) chapters explain freshness and reuse.

When the application still uses Route Segment Config, treat its execution settings as deployment inputs rather than portable performance promises:

| Setting | What it controls | Boundary to check |
| ----------------- | ------------------------------------------------------- | --------------------------------------------------------------------- |
| `runtime` | Node.js (the default) or Edge execution | Edge has runtime limits and is unsupported with Cache Components |
| `maxDuration` | Maximum duration a deployment may assign to server work | The hosting platform determines whether and how it enforces the value |
| `preferredRegion` | Regions in which a route should run | Supported regions and behavior depend on the host |

The legacy `dynamic`, `revalidate` and `fetchCache` options also have route-wide interactions. Use them only when that model is active, and validate the built route rather than assuming the export alone proves caching behavior.

## Verify the route users will navigate

Test a direct URL and a client-side transition separately. Then refresh an intercepted route, exercise an unknown dynamic ID, trigger a descendant error, and verify that a slow child reveals the intended fallback. Inspect production output and authorization behavior; development navigation alone does not prove cache or deployment behavior.

## Summary

The route tree assigns ownership: pages select content, layouts retain shared shells, templates reset descendants, and nearby boundaries scope waiting and failure. Use parallel or intercepted routes only when the interaction needs independent URL-backed state, and keep authorization and cache policy at the data boundary.

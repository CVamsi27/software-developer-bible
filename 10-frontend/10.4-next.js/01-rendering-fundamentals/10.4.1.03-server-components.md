# Server Components in Next.js

## TL;DR

React Server Components (RSC) render on the server, ship only the resulting HTML + a serialized component tree (RSC payload), and never include the component code in the JS bundle. They can `await` data directly, access backend resources, and reduce client JS. HTML is additionally prerendered for an initial full load; client navigations use the RSC payload.

## First Principles

RSC runs components on the server and ships *output*, not component code:

1. **The serialization contract defines everything**: RSC output is a serialized tree (the RSC payload); server components can be async, touch DBs/secrets directly, and cost zero bundle bytes — client components (with `'use client'`) are the interactive leaves hydrated with code.
2. **The boundary is a one-way door**: client components can't import server components (only receive them as children props) — server→client props must be serializable — the architecture is planning *where the boundary sits* (data fetches stay server-side, interactivity islands stay client-side).
3. **It's not SSR**: SSR renders HTML for first paint; RSC eliminates the *JS* for server-only components permanently — complementary, often confused.

## Why It Matters

Senior engineers use RSC to: fetch data close to the source (no API roundtrip), keep large deps (date libs, markdown parsers) off the client, and reduce bundle size. They know the rules: no `useState`/`useEffect`/event handlers, no browser APIs, no client-only libraries. Client Components can wrap server-rendered children; the boundary follows module imports rather than visual nesting.

## Definition

**Server Components** execute on the server and serialize their rendered tree as an RSC payload; Next.js also produces HTML for the initial page load. They cannot use React hooks like `useState`, `useEffect`, or browser APIs. In Next.js App Router, all components are Server Components by default.


## How It Works

The module graph determines the boundary: importing an ordinary component from a `'use client'` file includes it in that client graph. To preserve server execution, a Server Component must render the child and pass its output into the client wrapper. React serialization supports built-ins such as `Date`, `Map`, and `Set`; arbitrary class instances and ordinary callbacks cannot cross, but Server Function references can.

The session example assumes a database `expiresAt` field; it rejects expired sessions before exposing user data. Server execution alone does not authorize a caller—check identity and resource access near every protected read.

## Code Examples

### Basic Server Component

```typescript
// app/page.tsx — Server Component by default
import { db } from '@/lib/database'

export default async function HomePage() {
  // Direct database access — no API layer needed!
  const posts = await db.post.findMany({
    orderBy: { createdAt: 'desc' },
    take: 10,
  })

  return (
    <div>
      <h1>Latest Posts</h1>
      {posts.map(post => (
        <article key={post.id}>
          <h2>{post.title}</h2>
          <p>{post.excerpt}</p>
          <time>{post.createdAt.toLocaleDateString()}</time>
        </article>
      ))}
    </div>
  )
}

```

### Server Component with External API

```typescript
// app/github/page.tsx
import { Suspense } from 'react'

async function GitHubRepos() {
  const res = await fetch('https://api.github.com/users/facebook/repos', {
    next: { revalidate: 3600 } // Cache for 1 hour
  })
  const repos = await res.json()

  return (
    <ul>
      {repos.map((repo: any) => (
        <li key={repo.id}>
          <a href={repo.html_url}>{repo.name}</a>
          <span>{repo.stargazers_count} </span>
        </li>
      ))}
    </ul>
  )
}

export default function GitHubPage() {
  return (
    <div>
      <h1>Facebook Repos</h1>
      <Suspense fallback={<div>Loading repos...</div>}>
        <GitHubRepos />
      </Suspense>
    </div>
  )
}

```

### Error Handling in Server Components

```typescript
// app/dashboard/page.tsx
import { notFound } from 'next/navigation'

async function getUser(id: string) {
  const res = await fetch(`https://api.example.com/users/${id}`)

  if (res.status === 404) {
    notFound() // Triggers nearest not-found.tsx
  }

  if (!res.ok) {
    throw new Error('Failed to fetch user') // Triggers error.tsx
  }

  return res.json()
}

export default async function DashboardPage() {
  const user = await getUser('123')

  return (
    <div>
      <h1>Welcome, {user.name}</h1>
    </div>
  )
}

```

### Server Component with Context

```typescript
// lib/user-context.tsx
import { cookies } from 'next/headers'
import { db } from '@/lib/database'

export async function getCurrentUser() {
  const cookieStore = await cookies()
  const sessionId = cookieStore.get('session')?.value

  if (!sessionId) return null

  const session = await db.session.findUnique({
    where: { id: sessionId },
    include: { user: true },
  })

  if (!session || session.expiresAt <= new Date()) return null
  return session.user
}

```

```typescript
// app/dashboard/page.tsx
import { getCurrentUser } from '@/lib/user-context'

export default async function DashboardPage() {
  const user = await getCurrentUser()

  if (!user) {
    return <div>Please log in</div>
  }

  return (
    <div>
      <h1>Dashboard for {user.name}</h1>
    </div>
  )
}

```

### Server Component Composition Pattern

> The [nested product components](#nested-server-components) show the composition rule: the server owns data access and inserts client controls. When a Client Component wraps server UI, pass that UI as `children` from a Server Component rather than importing the server module into the client graph.

| Use Case | Server Component Benefit |
| ------------------------ | ---------------------------------------- |
| Blog/Content pages | Direct CMS access, no API layer |
| E-commerce product pages | Database queries, SEO optimization |
| Dashboard overview | Aggregate data without client fetching |

## Common Mistakes

### 1. Using useState/useEffect in Server Components

```typescript
// BAD: Hooks don't work in Server Components
export default async function Page() {
  const [count, setCount] = useState(0) // Error!
  useEffect(() => { /* ... */ }, []) // Error!

  return <div>{count}</div>
}

// GOOD: Use Client Component for interactivity
'use client'
import { useState } from 'react'

export function Counter() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>
}

// Keep page as Server Component
import { Counter } from './counter'

export default function Page() {
  return (
    <div>
      <h1>Counting</h1>
      <Counter />
    </div>
  )
}

```

### 2. Passing Functions as Props

```typescript
// BAD: Can't pass functions from Server to Client Components
async function Page() {
  const handleClick = () => console.log('clicked') // Can't pass this!

  return <ClientButton onClick={handleClick} />
}

// GOOD: Define the handler in the Client Component
'use client'
export function ClientButton() {
  const handleClick = () => console.log('clicked')
  return <button onClick={handleClick}>Click me</button>
}

```

### 3. Accessing Browser APIs

```typescript
// BAD: Browser APIs don't exist on the server
export default async function Page() {
  const width = window.innerWidth // Error!
  const localStorage = window.localStorage // Error!

  return <div>Width: {width}</div>
}

// GOOD: Use useEffect for browser APIs
'use client'
import { useState, useEffect } from 'react'

export function BrowserInfo() {
  const [width, setWidth] = useState(0)

  useEffect(() => {
    setWidth(window.innerWidth)
  }, [])

  return <div>Width: {width}</div>
}

```

### 4. Not Handling Loading States

```typescript
// BAD: Slow data fetch blocks entire page
export default async function Page() {
  const data = await fetchSlowData() // 3 second delay
  return <div>{data.items.map(...)}</div> // User waits 3 seconds
}

// GOOD: Use Suspense for streaming
export default function Page() {
  return (
    <div>
      <h1>Fast content renders immediately</h1>
      <Suspense fallback={<Loading />}>
        <SlowDataComponent />
      </Suspense>
    </div>
  )
}

```

### 5. Exposing Sensitive Data

```typescript
// BAD: Leaking secrets to client
export default async function Page() {
  const apiKey = process.env.API_KEY
  return <div>{apiKey}</div> // Exposed!
}

// GOOD: Only pass safe data
export default async function Page() {
  const apiKey = process.env.API_KEY
  const data = await fetchWithKey(apiKey) // Key stays on server
  return <div>{data.publicField}</div> // Only public data
}

```

## Best Practices

1. **Default to Server Components** — Only use `'use client'` when interactivity is needed

2. **Compose with Suspense** — Stream slow data fetches without blocking the page

3. **Keep data fetching close to usage** — Each component fetches its own data

4. **Use Server Components for data access** — Avoid unnecessary API layers

5. **Isolate Client Components** — Keep them small and specific

6. **Use error boundaries** — Handle failures gracefully per route

7. **Cache data appropriately** — Use `next.revalidate` or `cache: 'force-cache'`

8. **Avoid over-fetching** — Fetch only what each component needs

9. **Use `notFound()` for missing data** — Trigger 404 pages properly
10. **Test both component types** — Server and Client Components behave differently

## Performance Considerations

### Bundle Size Comparison

A Server Component's implementation and server-only dependencies contribute no client bundle bytes, but its rendered output still contributes HTML/RSC payload bytes. Client Component dependencies are shared and split by the bundler, so there is no fixed per-component React-runtime charge; measure the built route bundle rather than adding illustrative component sizes.

### Rendering Performance

For a full page load, the server first builds the RSC payload and prerenders HTML for both component types. The browser displays that HTML, reconciles the payload, and hydrates Client Components; effects run afterward. Server data reads can still incur network latency or waterfalls, and client fetching is optional rather than an inherent lifecycle step.

## Summary

| Aspect | Server Component | Client Component |
| ------------- | --------------------------------------------------- | ------------------------------------ |
| Renders | Server | Server prerender + browser hydration |
| JS Bundle | 0 bytes | Full component |
| Hooks | No state/effect hooks; server-compatible hooks only | Client hooks |
| Browser APIs | No | Yes |
| Data Access | Direct | Via API |
| Interactivity | No | Yes |
| Streaming | Yes | Via Suspense |
| Default | Yes | No |

## Revision Questions

**Definition**

1. **Q:** What does RSC add beyond an ordinary server-rendered HTML response?
   **A:** It serializes the server-rendered component tree for reconciliation without shipping those components' implementations. Initial HTML prerendering complements that payload.


**How It Works**

2. **Q:** Why does a visual child of a Client Component not necessarily become client code?
   **A:** The import graph defines the boundary. A Server Component can supply an already-rendered child through props without the client wrapper importing its module.


**Code Examples**

3. **Q:** What check is missing if a session lookup merely finds a database row?
   **A:** Expiry and current authorization still need validation. Finding an ID does not establish that the session remains usable or can access the resource.


**Common Mistakes**

4. **Q:** Which callback can cross from server code to client UI?
   **A:** A Server Function reference can cross through React's protocol. An ordinary closure created while rendering cannot be passed as a client event handler.

5. **Q:** How can server-only code still leak a secret?
   **A:** Its rendered output and returned client props are delivered to the browser. Server execution protects the implementation, not every value it emits.


**Performance Considerations**

6. **Q:** Why is zero client component-code bytes different from zero delivery cost?
   **A:** HTML and the RSC payload still carry rendered output, and the app needs client routing/runtime support. Large serialized results can remain expensive even without server component code.

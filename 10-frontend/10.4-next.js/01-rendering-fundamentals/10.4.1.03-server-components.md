# Server Components in Next.js

An account page may need private database data, but its headings and layout do not need browser state. A Server Component can read data through server-only code; for private data, authorize the request before returning the result. The browser receives rendered output, not the component implementation or database library.

```tsx
// app/products/[id]/page.tsx — a Server Component by default
import { db } from '@/lib/database';

export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await db.product.findUnique({ where: { id } }); // DB client never ships
  return <article><h1>{product.name}</h1></article>;
}
```

## Definition

A **Server Component** is a React component executed exclusively in the server environment (Node.js or Edge runtime). In the Next.js App Router, all components inside the `app/` directory are Server Components by default unless explicitly declared otherwise with `'use client'`.

Server Components can be asynchronous (`async/await`), read directly from databases, file systems, and internal microservices, but cannot use browser-only APIs (`window`, `localStorage`), user event listeners (`onClick`), or client state hooks (`useState`, `useEffect`).

> **Textbook Definition:** A Server Component is evaluated by the server renderer and contributes its rendered result to the React Server Component (RSC) payload. Its implementation stays out of the client module bundle; any Client Component it references remains a separate browser entry point.

## First Principles

Server Components separate *where* implementation runs from *when* output is generated or cached. **Secrets stay behind trusted perimeters**: connection strings and API tokens must never enter a client bundle. **Server execution is not caching**: a component may re-run per request, so cache only results whose freshness and sharing scope are safe. **The browser needs output plus interactive boundaries**: server results arrive as payload without their implementation, while Client Components still need code and serialized props.

```text
Server Environment (Trusted)                  Browser Runtime (Untrusted)
┌─────────────────────────────────────────────────────────────────────────────┐           ┌───────────────────────────────┐
│ Server Component (async)        │           │ HTML Document (Fast Paint)    │
│ ├─ Direct DB Queries            │           │                               │
│ ├─ File System / Private APIs   │ ────────► │ Serialized rendered output    │
│ └─ Implementation stays server │    RSC    │                               │
│                                 │  Payload  │ Client Component Leaf Nodes   │
│ Client Component Boundary       │ ────────► │ (Hydrates event listeners,    │
│ (References chunk + props)      │           │  local useState, useEffect)   │
└─────────────────────────────────────────────────────────────────────────────┘           └───────────────────────────────┘
```

## How It Works

### 1. How Server Components Execute: The RSC Payload

For an initial route load, Next.js uses the React Server Component (RSC) payload together with Client Components to prerender HTML. The payload is a compact serialized representation of the rendered Server Component tree, not the server component source code. It contains rendered Server Component output, placeholders and JavaScript references for Client Components, and props that cross between the two.

On the first load, the browser can display HTML before interactive code hydrates. React uses the RSC payload to reconcile the component trees, then JavaScript hydrates Client Components. On later client navigation, Next.js can prefetch and send RSC output to update the route without a full document load; Client Components render on the client for that navigation.

### 2. Read Data on the Server

Because Server Components run in Node.js, they fetch data directly from databases without intermediate HTTP handlers:

```typescript
// app/products/[id]/page.tsx — Server Component by default
import 'server-only'
import { notFound } from 'next/navigation'
import { db } from '@/lib/database'
import { AddToCartButton } from './add-to-cart-button'

interface Props {
  params: Promise<{ id: string }>
}

export default async function ProductPage({ params }: Props) {
  const { id } = await params

  // Read directly on the server; the browser does not import the database client.
  const product = await db.product.findUnique({
    where: { id },
    select: {
      id: true,
      name: true,
      description: true,
      price: true,
    },
  })

  if (!product) notFound()

  return (
    <article className="product-layout">
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <span className="price">${(product.price / 100).toFixed(2)}</span>

      {/* Passing serialized primitive props across the client boundary */}
      <AddToCartButton productId={product.id} price={product.price} />
    </article>
  )
}
```

The `import 'server-only'` guard prevents **environment poisoning**: accidentally importing this database module into a Client Component halts the build instead of silently leaking server code into the public bundle.

**Composition pattern**: when an interactive Client Component (modal, drawer, collapsible panel) needs server-rendered content, never let it import the server module directly — that import joins the client graph. Instead, let a Server Component create the child and pass the element through `children`:

```typescript
// app/components/collapsible-panel.tsx
'use client'

import { useState } from 'react'

export function CollapsiblePanel({
  title,
  children,
}: {
  title: string
  children: React.ReactNode
}) {
  const [isOpen, setIsOpen] = useState(false)

  return (
    <section className="panel">
      <button onClick={() => setIsOpen((prev) => !prev)}>
        {title} {isOpen ? '▲' : '▼'}
      </button>
      {isOpen && <div className="panel-body">{children}</div>}
    </section>
  )
}
```

```typescript
// app/dashboard/page.tsx — Server Component
import { CollapsiblePanel } from '@/components/collapsible-panel'
import { HeavyServerFeed } from '@/components/heavy-server-feed'

export default function DashboardPage() {
  return (
    <main>
      <h1>Activity Monitor</h1>
      {/* HeavyServerFeed renders on the server; CollapsiblePanel manages client toggle */}
      <CollapsiblePanel title="Recent Transactions">
        <HeavyServerFeed />
      </CollapsiblePanel>
    </main>
  )
}
```

`HeavyServerFeed` executes on the server because the Server Component page imports it. The client wrapper receives the rendered child slot without importing the feed's module. The child output still reaches the browser, so exclude secrets and data the user must not see.

### 3. Data Serialization Constraints

Props crossing to a Client Component must use React's supported serialization types — a React protocol, not just `JSON.stringify` rules:

| Value | Supported? | Boundary to remember |
| :-- | :-- | :-- |
| Primitives, arrays, plain objects, `Date`, `Map`, `Set`, typed arrays, `ArrayBuffer`, `BigInt`, `undefined`, and globally registered symbols | Yes | Nested values must also be supported. Convert ORM instances to plain data. |
| Promises and JSX elements | Yes | A Client Component can unwrap a supported Promise with React `use()`. |
| Server Function references | Yes | These are special references, not ordinary callbacks. |
| Ordinary functions, class instances, objects with a null prototype, and unregistered symbols | No | Convert values or move the interaction into client code. |

If an interaction needs server-side work, use a Server Function or a route/API request with server-side authorization. Never pass an ordinary closure as a prop from a Server Component.

### 4. Progressive Streaming with Suspense

`<Suspense>` can reveal a ready part of the page while a slower child is pending. Put the awaited work inside the child below the boundary; if the parent awaits it before returning JSX, the boundary cannot show its fallback yet:

```typescript
// app/analytics/page.tsx
import { Suspense } from 'react'
import { FastSummary } from './fast-summary'
import { SlowTimeSeriesChart } from './slow-chart'

export default function AnalyticsPage() {
  return (
    <main>
      <h1>Platform Analytics</h1>
      <FastSummary />

      {/* SlowTimeSeriesChart performs its awaited work below this boundary. */}
      <Suspense fallback={<div className="skeleton-loader">Loading time series…</div>}>
        <SlowTimeSeriesChart />
      </Suspense>
    </main>
  )
}
```

### 5. Work and Security Boundaries

- **Creating server-side waterfalls:** Sequentially awaiting independent reads adds their latencies. Use `Promise.all` when results are jointly required, or separate components behind Suspense when they can appear independently.
- **Server Execution Is Not Automatic Authorization:** Running code on the server does not mean data access is inherently secure. Always verify user identity, role-based access control (RBAC), and tenant ownership within your data-access functions.
- **Leaking Secrets in Rendered JSX:** While database connection strings stay hidden, any data returned in JSX props or text content is delivered in the public HTML and RSC payload. Never include password hashes, private user emails, or internal IDs in rendered elements.

## Summary

Server Components let server-only code read data and produce UI without shipping their implementation to the browser. Their output and Client Component props still cross the network, so authorization, data minimization, cache scope and payload size remain important. Use a Client Component only where browser state or events are needed, and treat its props as a serialization boundary.

# Server Components in Next.js

## Definition

**Server Components** run on the server. React encodes their rendered tree into data called the **RSC payload**, which the client runtime can use to assemble the UI. Next.js also produces HTML for the initial page load. Server Components cannot use client Hooks such as `useState` and `useEffect`, or browser APIs. Components in the Next.js App Router start as Server Components unless a client boundary puts them in the client module tree.

> **Textbook Definition:** A Server Component is evaluated in the server component environment and communicates its rendered result through a serialized component payload. Its implementation is excluded from the client component bundle, while referenced Client Components remain interactive in the browser.


## First Principles

A product card needs database results, while its cart button needs a click handler. Those responsibilities do not have to execute in the same environment.

1. **The browser cannot safely own a database credential.** Read protected data in a trusted environment, check access, and expose only the fields needed by the UI.
2. **A remote result must cross a transport boundary.** React encodes the rendered tree and supported prop values. Arbitrary objects and ordinary closures cannot be reconstructed with their server environment in the browser.
3. **Interaction requires browser code.** A cart control needs client code and state; a server-rendered description does not need its implementation shipped just to display its result. This separation is independent of when Next prerenders the route.

## Why It Matters

Server Components are useful when trusted server code can read data close to its source or keep server-only dependencies out of the browser bundle. They do not remove the need for authorization, runtime data validation, or a deliberate cache policy. Put state and event handlers in a Client Component; when client UI should visually contain server-rendered output, pass that output through a prop such as `children` from a Server Component instead of importing the server module into the client graph.

## How It Works

The module graph determines the boundary: importing an ordinary component from a `'use client'` file includes it in that client graph. To preserve server execution, a Server Component must render the child and pass its output into the client wrapper. React serialization supports built-ins such as `Date`, `Map`, and `Set`; arbitrary class instances and ordinary callbacks cannot cross, but Server Function references can.

The session example assumes a database `expiresAt` field; it rejects expired sessions before exposing user data. Server execution alone does not authorize a caller—check identity and resource access near every protected read.

### Follow the result across the boundary

```text
Server page → query products → render ProductCard → encode output
                                      │
                                      └→ AddToCartButton(productId)
Browser → display initial HTML → read RSC payload → hydrate cart button
```

For product `p42`, the database connection and `ProductCard` implementation stay on the server. Its title and `productId="p42"` are transmitted, so those values must be safe to disclose. Clicking the button updates client state; it does not rerun the card's server function by itself. A navigation, refresh or mutation/revalidation path can request new server output. On later client navigation, Next can fetch an RSC payload without downloading a new HTML document.

## Code Examples

Each labeled file is separate. Database and UI imports are application adapters, not framework-provided modules. These examples use Next.js 16.4 with Cache Components disabled; `fetch` is not persistently cached by default in that model. Server execution does not itself choose a cache lifetime, and Cache Components uses its own explicit `'use cache'` and `cacheLife` policy.

### Basic Server Component

```typescript
// app/page.tsx — Server Component by default
import { db } from '@/lib/database'

export default async function HomePage() {
  // Direct database access — no API layer needed!
  const posts = await db.post.findMany({
    orderBy: { createdAt: 'desc' },
    take: 10,
  })

  return (
    <div>
      <h1>Latest Posts</h1>
      {posts.map(post => (
        <article key={post.id}>
          <h2>{post.title}</h2>
          <p>{post.excerpt}</p>
          <time>{post.createdAt.toLocaleDateString()}</time>
        </article>
      ))}
    </div>
  )
}

```

### Server Component with Data Fetching

```typescript
// app/dashboard/page.tsx
import { Suspense } from 'react'
import { AnalyticsChart } from './analytics-chart'
import { RecentActivity } from './recent-activity'
import { StatsSkeleton, ChartSkeleton, ActivitySkeleton } from './skeletons'
import { StatsOverview } from './stats-overview'

export default async function DashboardPage() {
  return (
    <div className="grid grid-cols-12 gap-6">
      <div className="col-span-12">
        <h1>Dashboard</h1>
      </div>

      {/* Each section streams independently */}
      <div className="col-span-4">
        <Suspense fallback={<StatsSkeleton />}>
          <StatsOverview />
        </Suspense>
      </div>

      <div className="col-span-8">
        <Suspense fallback={<ChartSkeleton />}>
          <AnalyticsChart />
        </Suspense>
      </div>

      <div className="col-span-12">
        <Suspense fallback={<ActivitySkeleton />}>
          <RecentActivity />
        </Suspense>
      </div>
    </div>
  )
}

```

Each section component awaits its own data inside the boundary; the skeletons and imported components are application modules. If the parent awaits all three reads before returning, these inner fallbacks cannot reveal that parent sooner.

### Nested Server Components

```typescript
// app/products/page.tsx — Parent Server Component
import { ProductCard } from './product-card'
import { db } from '@/lib/database'

export default async function ProductsPage() {
  const products = await db.product.findMany({ take: 20 })

  return (
    <div className="grid grid-cols-3 gap-4">
      {products.map(product => (
        <ProductCard key={product.id} product={product} />
      ))}
    </div>
  )
}

```

```typescript
// app/products/product-card.tsx — Child Server Component
import { AddToCartButton } from './add-to-cart-button'
import { db } from '@/lib/database'

interface ProductCardProps {
  product: {
    id: string
    name: string
    price: number
    image: string
  }
}

// Server Component — can access database directly
export async function ProductCard({ product }: ProductCardProps) {
  // Could fetch additional data here
  const reviews = await db.review.findMany({
    where: { productId: product.id },
    take: 3,
  })

  return (
    <div className="border rounded-lg overflow-hidden">
      <img src={product.image} alt={product.name} />
      <div className="p-4">
        <h3>{product.name}</h3>
        <p>${product.price}</p>
        <div className="stars">
          {/* Render reviews */}
        </div>
        {/* Client Component for interactivity */}
        <AddToCartButton productId={product.id} />
      </div>
    </div>
  )
}

```

This sketch assumes `price` is a transport-safe number and the imported cart control exists in a separate client module. A database decimal/class value needs conversion before crossing a client boundary. Per-card review queries can create an N+1 pattern: fetch only the displayed fields and batch or include reviews when query count or latency warrants it.

### Server Component with External API

```typescript
// app/github/page.tsx
import { Suspense } from 'react'

interface GitHubRepo {
  id: number
  name: string
  html_url: string
  stargazers_count: number
}

function isGitHubRepo(value: unknown): value is GitHubRepo {
  return typeof value === 'object' && value !== null &&
    'id' in value && typeof value.id === 'number' &&
    'name' in value && typeof value.name === 'string' &&
    'html_url' in value && typeof value.html_url === 'string' &&
    'stargazers_count' in value && typeof value.stargazers_count === 'number'
}

async function GitHubRepos() {
  const res = await fetch('https://api.github.com/users/facebook/repos', {
    next: { revalidate: 3600 } // Cache for 1 hour
  })
  if (!res.ok) throw new Error('Failed to fetch repositories')
  const payload: unknown = await res.json()
  if (!Array.isArray(payload) || !payload.every(isGitHubRepo)) {
    throw new Error('Unexpected repository response')
  }
  const repos = payload

  return (
    <ul>
      {repos.map(repo => (
        <li key={repo.id}>
          <a href={repo.html_url}>{repo.name}</a>
          <span>{repo.stargazers_count} </span>
        </li>
      ))}
    </ul>
  )
}

export default function GitHubPage() {
  return (
    <div>
      <h1>Facebook Repos</h1>
      <Suspense fallback={<div>Loading repos...</div>}>
        <GitHubRepos />
      </Suspense>
    </div>
  )
}

```

### Error Handling in Server Components

```typescript
// app/dashboard/page.tsx
import { notFound } from 'next/navigation'

async function getUser(id: string) {
  const res = await fetch(`https://api.example.com/users/${encodeURIComponent(id)}`)

  if (res.status === 404) {
    notFound() // Triggers nearest not-found.tsx
  }

  if (!res.ok) {
    throw new Error('Failed to fetch user') // Triggers error.tsx
  }

  const payload: unknown = await res.json()
  if (typeof payload !== 'object' || payload === null ||
      !('name' in payload) || typeof payload.name !== 'string') {
    throw new Error('Unexpected user response')
  }
  return { name: payload.name }
}

export default async function DashboardPage() {
  const user = await getUser('123')

  return (
    <div>
      <h1>Welcome, {user.name}</h1>
    </div>
  )
}

```

### Request-Scoped Session Lookup

```typescript
// lib/current-user.ts
import 'server-only'
import { cookies } from 'next/headers'
import { db } from '@/lib/database'

export async function getCurrentUser() {
  const cookieStore = await cookies()
  const sessionId = cookieStore.get('session')?.value

  if (!sessionId) return null

  const session = await db.session.findUnique({
    where: { id: sessionId },
    select: {
      expiresAt: true,
      user: { select: { id: true, name: true } },
    },
  })

  if (!session || session.expiresAt <= new Date()) return null
  return { id: session.user.id, name: session.user.name }
}

```

```typescript
// app/dashboard/page.tsx
import { getCurrentUser } from '@/lib/current-user'

export default async function DashboardPage() {
  const user = await getCurrentUser()

  if (!user) {
    return <div>Please log in</div>
  }

  return (
    <div>
      <h1>Dashboard for {user.name}</h1>
    </div>
  )
}

```

### Server Component Composition Pattern

> The [nested product components](#nested-server-components) show the composition rule: the server owns data access and inserts client controls. When a Client Component wraps server UI, pass that UI as `children` from a Server Component rather than importing the server module into the client graph.

## Real-World Use Cases

| Use Case | Server Component Benefit |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| Blog/Content pages | Direct CMS access, no API layer |
| E-commerce product pages | Database queries, SEO optimization |
| Dashboard overview | Aggregate data without client fetching |
| Documentation | Static generation with dynamic data |
| User profiles | Secure data access with session handling |
| Search results | Server-side filtering and pagination |
| Admin panels | Keep database access server-side; mutations still require an authorized callable boundary |
| Landing pages | Fast rendering, minimal JS |

## Common Mistakes

### 1. Using Client State or Effects in Server Components

```typescript
// app/page.tsx — BAD: Client state/effect hooks do not work in Server Components
export default async function Page() {
  const [count, setCount] = useState(0) // Error!
  useEffect(() => { /* ... */ }, []) // Error!

  return <div>{count}</div>
}
```

```tsx
// app/counter.tsx — Client Component
// GOOD: Use Client Component for interactivity
'use client'
import { useState } from 'react'

export function Counter() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>
}
```

```tsx
// app/page.tsx — Keep the route as a Server Component
import { Counter } from './counter'

export default function Page() {
  return (
    <div>
      <h1>Counting</h1>
      <Counter />
    </div>
  )
}
```

### 2. Passing Ordinary Callbacks Across the Boundary

```typescript
// BAD: Ordinary callbacks cannot cross; Server Function references are distinct
async function Page() {
  const handleClick = () => console.log('clicked') // Can't pass this!

  return <ClientButton onClick={handleClick} />
}

// GOOD: Define the handler in the Client Component
'use client'
export function ClientButton() {
  const handleClick = () => console.log('clicked')
  return <button onClick={handleClick}>Click me</button>
}

```

### 3. Accessing Browser APIs

```typescript
// BAD: Browser APIs don't exist on the server
export default async function Page() {
  const width = window.innerWidth // Error!
  const localStorage = window.localStorage // Error!

  return <div>Width: {width}</div>
}

// GOOD: Use useEffect for browser APIs
'use client'
import { useState, useEffect } from 'react'

export function BrowserInfo() {
  const [width, setWidth] = useState(0)

  useEffect(() => {
    setWidth(window.innerWidth)
  }, [])

  return <div>Width: {width}</div>
}

```

### 4. Not Handling Loading States

```typescript
// BAD: Slow data fetch blocks entire page
export default async function Page() {
  const data = await fetchSlowData() // 3 second delay
  return <div>{data.items.map(...)}</div> // User waits 3 seconds
}

// GOOD: Use Suspense for streaming
export default function Page() {
  return (
    <div>
      <h1>Fast content renders immediately</h1>
      <Suspense fallback={<Loading />}>
        <SlowDataComponent />
      </Suspense>
    </div>
  )
}

```

### 5. Exposing Sensitive Data

```typescript
// BAD: Leaking secrets to client
export default async function Page() {
  const apiKey = process.env.API_KEY
  return <div>{apiKey}</div> // Exposed!
}

// GOOD: Only pass safe data
export default async function Page() {
  const apiKey = process.env.API_KEY
  const data = await fetchWithKey(apiKey) // Key stays on server
  return <div>{data.publicField}</div> // Only public data
}

```

## Best Practices

1. **Keep data access and authorization together.** A server-side database read still needs a user and resource authorization check.
2. **Guard server-only modules.** Keep credentials and database clients out of the client import graph; `import 'server-only'` can make an accidental client import fail clearly.
3. **Return only the fields the UI needs.** Server execution does not make values embedded in HTML or the RSC payload private.
4. **Choose an explicit cache policy.** With Cache Components disabled, use the supported fetch/cache configuration; with it enabled, use `'use cache'` and a deliberate `cacheLife` or stream request-bound work under Suspense.
5. **Parallelize independent reads and batch repeated ones.** Component-local fetching can improve ownership but does not prevent waterfalls or N+1 queries.
6. **Keep the client boundary small.** Pass a server-rendered child through the Client Component when the wrapper needs browser state but the child does not.
7. **Handle absence and failure distinctly.** Use `notFound()` for a genuinely missing route resource and route error boundaries for unexpected rendering failures.
8. **Measure both sides of the boundary.** Inspect built client chunks, RSC/HTML payload size, server latency, and cache behavior.

## Performance Considerations

### Bundle Size Comparison

A Server Component's implementation and server-only dependencies contribute no client bundle bytes, but its rendered output still contributes HTML/RSC payload bytes. Client Component dependencies are shared and split by the bundler, so there is no fixed per-component React-runtime charge; measure the built route bundle rather than adding illustrative component sizes.

### Rendering Performance

For a full page load, the server first builds the RSC payload and prerenders HTML for both component types. The browser displays that HTML, reconciles the payload, and hydrates Client Components; effects run afterward. Server data reads can still incur network latency or waterfalls, and client fetching is optional rather than an inherent lifecycle step.

## Summary

| Aspect | Server Component | Client Component |
| ------------- | --------------------------------------------------- | ------------------------------------------------------------------------------ |
| Renders | Server | Server prerender + browser hydration |
| Client bundle | Implementation code is not included | Client module graph and its required dependencies; shared chunks can be reused |
| Hooks | No state/effect hooks; server-compatible hooks only | Client hooks |
| Browser APIs | No | In browser lifecycle code, not server prerender |
| Data access | Server-side data source or service | Browser-accessible API or Server Function |
| Interactivity | No | Yes |
| Streaming | Yes | Via Suspense |
| Default | Yes | No |

# Server Components in Next.js

A product page needs database data, while its Add to Cart button needs a click handler. Running both responsibilities in the browser would expose the data-access implementation and ship code that static text does not need. Server Components let the page read and render on the server, then place a small interactive client control where the user needs it.

## Definition

A **Server Component** is a React component evaluated in the server environment. In the Next.js App Router, pages and layouts are Server Components by default. They can use server-only modules and await data, but they cannot use browser APIs, event handlers, or client state and effect Hooks.

> **Textbook Definition:** A Server Component is evaluated by the server renderer and contributes its rendered result to the React Server Component (RSC) payload. Its implementation stays out of the client module bundle; any Client Component it references remains a separate browser entry point.

## First Principles

Three constraints shape the boundary:

1. **Trusted access belongs in a trusted environment.** A database credential or private API token must not enter a browser bundle.
2. **A browser needs a transportable result.** It can receive rendered output and supported values, but it cannot reconstruct a database connection or an ordinary server closure.
3. **Interaction needs browser code.** A click handler and local state belong in a Client Component; surrounding content can remain server-rendered.

## Follow one product result to the browser

```text
Server page → authorize and read product → render description ─┐
                                                               ├→ HTML + RSC payload
                                                               └→ AddToCartButton reference + safe props
Browser → display HTML → reconcile RSC tree → hydrate button → handle click
```

The RSC payload is not a dump of the database response. It carries the rendered Server Component result, references to Client Components and their code, and the props needed at that boundary. A value included in HTML or props is visible to the visitor, even though the component implementation and server credential remain private.

On a full page load, Next.js produces HTML for the initial screen and an RSC payload; the browser can show the HTML before client controls become interactive. On later navigation, Next.js can send an RSC payload without a new HTML document. The route's rendering and cache policy still determines when the server does its work; being a Server Component does not mean “run once” or “always fresh.”

## Keep server reads beside their authorization

```typescript
// app/products/[id]/page.tsx — Server Component
import 'server-only'
import { notFound } from 'next/navigation'
import { AddToCartButton } from './add-to-cart-button'
import { getPublicProduct } from '@/lib/products'

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const product = await getPublicProduct(id)
  if (!product) notFound()

  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <p>{product.displayPrice}</p>
      <AddToCartButton productId={product.id} />
    </main>
  )
}
```

`getPublicProduct` and the database module are application code. For private data, derive the viewer from a verified server session and check access to the specific resource in the same data-access path. `import 'server-only'` makes an accidental import into a client module fail during the build. Return only display fields; the checkout operation must re-read current price and stock and authorize the mutation.

A database row matching a session ID is not enough to accept that session: check its expiry and whether the viewer may access this particular resource. The same check belongs on every server entry point that reads or changes protected data.

The component's source stays on the server, but its title, description, price and product ID are delivered in the response. Never put a secret in rendered text or client props. TypeScript types do not validate data returned by an external service at runtime; parse untrusted JSON before rendering it.

## Pass rendered server UI through client wrappers

The `'use client'` directive divides module graphs. If a Client Component imports a module, that dependency joins the client graph. A Server Component can instead render server UI and pass the result through a Client Component's `children` or another prop. The wrapper then controls browser behavior without importing the server implementation.

An ordinary function created during server rendering cannot become a browser event handler. React supports values such as `Date`, `Map` and `Set`; arbitrary class instances such as Moment objects and ordinary closures cannot cross as props. Server Function references are a distinct mechanism for invoking server work, and their implementation must still authenticate, authorize and validate each call. Convert database-specific values into a small, deliberate UI shape before passing them to a Client Component.

## Let fast content arrive before slow content

Place request or data work inside the subtree whose fallback should remain visible. If the page awaits the slow result before it returns the Suspense boundary, the boundary cannot reveal its fallback early.

```typescript
import { Suspense } from 'react'

export default function DashboardPage() {
  return (
    <main>
      <h1>Dashboard</h1>
      <Suspense fallback={<p>Loading recent activity…</p>}>
        <RecentActivity />
      </Suspense>
    </main>
  )
}

async function RecentActivity() {
  const events = await getRecentActivity()
  return <ActivityList events={events} />
}
```

The helper components and data access are application code. Independent sections can use separate boundaries so one slow chart does not delay a ready summary. A thrown `notFound()` selects the route's not-found UI; an unexpected render failure reaches the nearest error boundary. The [Streaming chapter](../03-data-and-caching/10.4.3.04-streaming.md) covers nested boundaries, timing and deployment buffering.

## Treat cache policy as a separate contract

Server execution does not itself make data private, fresh or reusable. A shared cache must never include a viewer-specific result unless the key and policy isolate that viewer. With Cache Components enabled, mark reusable work with `'use cache'` and an intentional `cacheLife`, or place request-dependent work beneath Suspense. In other rendering models, inspect the framework's fetch options, route behavior and hosting cache for the deployed version. After a mutation, invalidate the relevant path or tag; do not rely on a page reload to repair stale shared data.

Metadata can share a data helper with `generateMetadata`; see [Metadata](../02-routing-and-middleware/10.4.2.03-metadata.md#dynamic-metadata-with-generatemetadata) for inheritance and fetch memoization. For request-scoped identity, see [Authentication](../04-production/10.4.4.01-authentication.md).

## Make the boundary an engineering decision

Server Components fit database-backed pages, content pages and dashboards when data can be read near its source. They do not prevent N+1 queries, waterfalls, large RSC payloads or expensive rendering. Batch repeated reads, parallelize independent work where appropriate, limit the fields returned, and measure server latency and payload size in a production build.

## Summary

Use Server Components to keep data access and noninteractive rendering on the server. React sends rendered output and the values needed by client controls; anything sent is public. Keep authorization beside protected reads, put only interaction in the client graph, and define cache and streaming behavior separately.

# Client Components in Next.js

An add-to-cart control needs browser events and local quantity state; the product description does not. In the App Router, `'use client'` marks the module boundary that brings a file and its imports into the client graph. It does not mean “render only in the browser”: Client Components are normally prerendered into HTML on an initial load, then hydrated.

```tsx
// app/products/quantity-selector.tsx — a narrow interactive leaf
'use client';

export function QuantitySelector({ maxStock }: { maxStock: number }) {
  const [quantity, setQuantity] = useState(1);
  return (
    <div>
      <button onClick={() => setQuantity((q) => Math.max(1, q - 1))}>−</button>
      <span aria-live="polite">{quantity}</span>
      <button onClick={() => setQuantity((q) => Math.min(maxStock, q + 1))}>+</button>
    </div>
  );
}
```

## Definition

A **Client Component** belongs to the client module graph and is delivered to the browser, enabling browser APIs, event handlers, and client hooks such as `useState` and `useEffect`. On an initial load, Next.js can also prerender its output on the server; later client navigation renders it in the browser.

Marking a file with the `'use client'` directive establishes a boundary: that file, and any module it imports, becomes part of the client bundle. On an initial page load, Next.js normally prerenders the initial markup into HTML; the browser then downloads the client JavaScript and hydrates the markup to attach event handlers.

> **Textbook Definition:** A Client Component is a React component reachable from a client module boundary. Its code is delivered to the browser to support interaction and browser capabilities; during initial navigation, Next.js may also prerender its initial output on the server.

## First Principles

The decision follows from three constraints. **Interaction needs the browser engine**: keystrokes, pointers, gestures, and hardware (geolocation, canvas, audio) require live browser execution. **Some feedback belongs near the user**: a menu toggle or quantity selector can update locally without a server roundtrip — durable business changes still go to the server. **Client JavaScript compounds in cost**: every shipped kilobyte consumes mobile data, battery, memory, and main-thread time for parsing, compiling, and hydrating.

```text
Server-Side Pre-render:
[Server Component: ProductPage] ───► Emits static HTML (<main>, <h1>, <p>)
     │
     └──► [Client Boundary: 'use client'] ───► Emits initial HTML (<button>Add to Cart</button>)
                                               + Registers bundle entry point in RSC payload

Browser Runtime:
1. Fast Paint: Browser renders HTML shell immediately (content visible before JS loads)
2. Script Download: Browser fetches targeted client bundle for interactive leaves
3. Hydration: React attaches onClick handlers, mounts useState/useEffect, UI becomes active
```

## 1. Choose the Client Boundary

Keep server-only content outside the client module graph, and place the client boundary around the smallest useful interactive unit. “At the leaves” is a useful default, not a requirement: shared providers and compound controls can make a higher boundary clearer.

For a product page, the description can remain server-rendered while a quantity selector owns its local state. The cart write must still validate current stock and price on the server.

```typescript
// app/products/quantity-selector.tsx — Targeted Client Boundary
'use client'

import { useState } from 'react'

export function QuantitySelector({
  maxStock,
}: {
  maxStock: number
}) {
  const [quantity, setQuantity] = useState(1)

  if (maxStock < 1) return <p>Out of stock</p>

  function updateQuantity(nextValue: number) {
    const clamped = Math.max(1, Math.min(maxStock, nextValue))
    setQuantity(clamped)
  }

  return (
    <div className="quantity-controls" role="group" aria-label="Product quantity">
      <button
        type="button"
        disabled={quantity <= 1}
        onClick={() => updateQuantity(quantity - 1)}
        aria-label="Decrease quantity"
      >
        −
      </button>
      <span aria-live="polite" className="quantity-display">
        {quantity}
      </span>
      <button
        type="button"
        disabled={quantity >= maxStock}
        onClick={() => updateQuantity(quantity + 1)}
        aria-label="Increase quantity"
      >
        +
      </button>
    </div>
  )
}
```

Now, the parent page remains a clean, async Server Component:

```typescript
// app/products/[id]/page.tsx — Server Component
import { db } from '@/lib/database'
import { QuantitySelector } from './quantity-selector'

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const product = await db.product.findUniqueOrThrow({ where: { id } })

  return (
    <main className="product-page">
      <h1>{product.title}</h1>
      <p>{product.description}</p>
      {/* Heavy server layout wraps lightweight interactive leaf */}
      <QuantitySelector maxStock={product.stock} />
    </main>
  )
}
```

The selector's imports join the client bundle; the page's database import does not, because the page is a Server Component and does not import that database module into the client graph. The server must recheck stock when the user adds the item: the displayed value may be stale.

## 2. The Context Provider Pattern

Client-side tools like theme managers, modal controllers, or cache layers (React Query) require React Context — a client-only API. Wrapping the root layout in a Provider does *not* force the whole app into the client graph: isolate the provider in a Client Component that accepts `children`, and server layouts pass pre-rendered Server Components straight through it.

```typescript
// app/providers/theme-provider.tsx — Client Component Wrapper
'use client'

import { createContext, useContext, useState } from 'react'

type Theme = 'light' | 'dark'
const ThemeContext = createContext<{ theme: Theme; toggle: () => void }>({
  theme: 'light',
  toggle: () => {},
})

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light')
  const toggle = () => setTheme((t) => (t === 'light' ? 'dark' : 'light'))

  return (
    <ThemeContext.Provider value={{ theme, toggle }}>
      <div data-theme={theme}>{children}</div>
    </ThemeContext.Provider>
  )
}

export const useTheme = () => useContext(ThemeContext)
```

Now, compose this provider in the root `app/layout.tsx`:

```typescript
// app/layout.tsx — Server Component
import { ThemeProvider } from './providers/theme-provider'

export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <html lang="en">
      <body>
        {/* ThemeProvider manages client state; children remain Server Components */}
        <ThemeProvider>{children}</ThemeProvider>
      </body>
    </html>
  )
}
```

`RootLayout` and its pages remain Server Components because they are not imported by the provider. The provider manages its own client state and can render the server-created `children` slot. Server Components cannot read client context; put consumers that need the context inside the client graph.

## 3. Keep Initial Renders Consistent

On an initial load, React compares the HTML prerender with the Client Component's first browser render. If they produce different markup, hydration can fail or the page can visibly change.

Common causes:

1. **Reading browser-only state during render:** Accessing `window.innerWidth`, `localStorage`, or `navigator.userAgent` is unavailable on the server and may produce a different initial browser result.
2. **Locale or time-zone differences:** Formatting the same timestamp with environment defaults can produce different server and browser text.
3. **Invalid HTML nesting:** A `<p>` inside another `<p>`, or a `<div>` inside a `<p>`, can be rearranged by the browser parser so the resulting DOM no longer matches React's expected tree.

Safe solution — the deferred mounting pattern: synchronize client-only state inside `useEffect` so both renders share identical placeholder markup:

```typescript
// app/components/client-only-timestamp.tsx
'use client'

import { useState, useEffect } from 'react'

export function ClientOnlyTimestamp({ date }: { date: Date }) {
  const [formatted, setFormatted] = useState<string | null>(null)

  useEffect(() => {
    // Runs exclusively on the client after hydration commits
    setFormatted(new Intl.DateTimeFormat(undefined, { timeStyle: 'short' }).format(date))
  }, [date])

  // Initial server and client render produce identical placeholder markup
  if (!formatted) {
    return <time className="timestamp-skeleton">…</time>
  }

  return <time>{formatted}</time>
}
```

Both the prerender and first browser render show the same placeholder. The effect then updates it to the visitor's locale; use this pattern only when the brief placeholder and resulting layout change are acceptable.

## 4. Opting Out of Server Pre-Rendering: `next/dynamic`

When a component relies heavily on browser DOM primitives that crash server environments (such as charting libraries, canvas renderers, or complex audio visualizers), use dynamic imports with `ssr: false`:

```typescript
// app/dashboard/analytics-view.tsx
'use client'

import dynamic from 'next/dynamic'

// Disables server pre-rendering entirely for this specific module
const InteractiveHeatmap = dynamic(
  () => import('@/components/heavy-heatmap').then((mod) => mod.HeavyHeatmap),
  {
    ssr: false,
    loading: () => <div className="chart-skeleton">Loading interactive map…</div>,
  }
)

export function AnalyticsView() {
  return (
    <section>
      <h2>Traffic Heatmap</h2>
      <InteractiveHeatmap />
    </section>
  )
}
```

Next.js skips server prerendering for `InteractiveHeatmap` and uses the fallback until its browser code loads. Keep `ssr: false` inside a Client Component; the option cannot be declared directly from a Server Component.

## 5. Boundary Checks

- **A server module enters the client graph:** Imports below `'use client'` are client dependencies. Split shared helpers by environment and mark server-only modules with `server-only` so an accidental client import fails clearly.
- **Over-Using Client State for URL Data:** Storing pagination, active search queries, or tab filters in local `useState` destroys link shareability and browser back-button navigation. Store navigation state in the URL search parameters (`useSearchParams` or standard `<a>` links) so the page remains bookmarkable.
- **Passing ordinary callbacks across the boundary:** A callback closure from a Server Component is not serializable. Keep event callbacks inside client code or pass a supported Server Function reference for server work.

## Summary

Client Components own browser events, local state and browser APIs. Their code and transitive imports are sent to the browser; their initial output is normally prerendered, then hydrated. Keep boundaries narrow where that reduces client dependencies, preserve server-created children through composition, and keep server writes authoritative for data that can change.

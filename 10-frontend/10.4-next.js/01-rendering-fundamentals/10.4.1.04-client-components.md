# Client Components in Next.js

A product page can show its description before JavaScript loads, but changing a quantity after a click needs browser state. A Client Component supplies that behavior. The useful boundary is usually the control that changes, not every component surrounding it.

## Definition

A **Client Component** belongs to the browser-side module graph and can use React state, effects, event handlers and browser APIs. The `'use client'` directive marks a module entry point; its imports become client dependencies. In the App Router, Next.js can still render the initial UI to HTML on the server before the browser hydrates it.

> **Textbook Definition:** A Client Component is a React component reachable from a client module boundary. Its code is delivered to the browser to support interaction and browser capabilities; during initial navigation, Next.js may also prerender its initial output on the server.

## First Principles

A browser control needs code that can observe input and update visible state. That creates three costs to manage:

1. **Code must reach the browser.** Every imported dependency below a client entry can add to the client graph.
2. **The first output must agree.** The server and browser must begin from compatible input or hydration can find different markup.
3. **The browser does not own trusted decisions.** A client can suggest a quantity or submit a request, but the server must validate and authorize the result.

## Trace one interactive control

```text
Server render: initial quantity 1 → HTML shows 1
Browser: hydrate with initial quantity 1 → buttons become interactive
Click “increase”: client state changes to 2 → React updates this control
Checkout: server rechecks current identity, price and stock
```

Hydration attaches behavior to matching initial HTML; it does not create the page from nothing. Effects run after the browser commits the initial tree. A local state update also does not rerun its enclosing Server Component.

```typescript
// app/products/quantity-control.tsx
'use client'

import { useState } from 'react'

export function QuantityControl({ initial = 1 }: { initial?: number }) {
  const [quantity, setQuantity] = useState(initial)

  return (
    <div role="group" aria-label="Quantity">
      <button
        type="button"
        aria-label="Decrease quantity"
        disabled={quantity <= 1}
        onClick={() => setQuantity(value => Math.max(1, value - 1))}
      >
        −
      </button>
      <output aria-live="polite">{quantity}</output>
      <button
        type="button"
        aria-label="Increase quantity"
        onClick={() => setQuantity(value => value + 1)}
      >
        +
      </button>
    </div>
  )
}
```

The server page can import this control and pass its initial value. The control only manages a local estimate; the checkout service still checks quantity limits, price and availability. Use semantic controls and provide accessible names rather than treating the client boundary as an accessibility feature.

## Place the boundary where browser behavior starts

Keep a page, layout and data reads as Server Components where possible. Put `'use client'` in the file that a Server Component imports as an interactive entry. Files imported beneath that entry do not each need the directive. A large client wrapper can pull otherwise unrelated libraries into the browser graph even when some of its rendered children are static.

A Client Component may receive a Server Component's rendered output through `children` or another prop. The server parent creates that output before passing it to the client wrapper; the wrapper does not import the server component's module. Props crossing this boundary must use values supported by React's transport: `Date` is supported, while an arbitrary class instance such as Moment is not. Convert ORM objects to a small UI shape; ordinary closures cannot be passed as event handlers. A Server Function reference is a separate callable mechanism, and it must validate and authorize every request. See [Server Components](10.4.1.03-server-components.md) for the transport contract.

Providers follow the same rule. Define context in a Client Component and render the provider around only the subtree that consumes it. A server layout can pass its `children` through that provider without turning the layout's module into client code. See [Context API](../../10.3-react/02-core-hooks/10.3.2.05-context-api.md) for ownership and subscriptions.

## Keep the initial render deterministic

The server cannot read `window`, `localStorage`, viewport size or the visitor's current clock. A Client Component may still render on the server initially, so reading those values during render can produce HTML that disagrees with the browser's first render. Start with the same value in both places, then read browser-only state in an effect or event handler.

A common pattern initializes `mounted` to `false` and switches it to `true` in an effect. Both initial renders then produce the same markup; browser-only content appears after hydration.

An effect-based theme toggle is safe from a hydration mismatch but may briefly show the default theme. If the first paint must reflect the saved preference, choose that theme before rendering—for example, from a cookie or a small, carefully placed initialization script—and style from shared CSS tokens. See [Theming and Dark Mode](../../10.7-html-css/10.7.07-theming-design-tokens.md).

For a library that must access the DOM during module initialization, load it dynamically from a Client Component and consider `ssr: false`. That opts the widget out of server prerendering, so provide a useful loading or fallback state. Use this only when the dependency requires a browser environment or a measured bundle split justifies it.

## Choose client state only when it owns the result

Local state is right for a quantity control, open dialog, unsent form draft or transient selection. If a filter changes server-owned search results, keep its value in the URL and navigate so the server can read the new parameters, or fetch through a client data layer. A local dropdown beside a server-rendered grid does not filter the grid by itself.

Native forms can submit without a Client Component. Add client code when the interaction needs immediate validation, optimistic feedback, a rich editor or other browser behavior. The server endpoint or Server Function still validates the input and enforces authorization; hidden fields and disabled buttons are not security controls. See [Server Actions](../03-data-and-caching/10.4.3.02-server-actions.md) for the server mutation boundary.

Use client fetching for browser-owned inputs, polling or live updates. Cancel obsolete work or ignore stale responses when inputs change quickly. For a WebSocket or event stream, validate each received message, bound retained data, authenticate the connection on the server, and close the specific connection created by the effect during cleanup. Reconnect and delivery behavior need an explicit policy; a component does not supply them automatically.

## Account for code, hydration and failure

Hydration cost depends on the JavaScript downloaded and the work performed on the target device; there is no fixed per-component runtime penalty. Shared dependencies may already be in a common chunk. Measure the production route's client chunks, hydration CPU and interaction latency before adding memoization or dynamic imports.

An Error Boundary can handle render failures below it. It does not catch a rejected event-handler request or every asynchronous callback; represent expected failures in local UI state and report unexpected errors through the application's error path. For third-party date pickers, maps, editors or animation libraries, wrap only the required widget and verify keyboard behavior, focus, reduced motion and mobile cost.

## Summary

Use Client Components for state, events, effects and browser APIs, then keep their import graph close to the interaction. Make the initial render deterministic, send only deliberate values across the server boundary, and treat every client result as untrusted until the server validates it.

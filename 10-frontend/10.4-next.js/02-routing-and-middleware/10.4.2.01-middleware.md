# Proxy (formerly Middleware) in Next.js

An incoming request may need a redirect, tenant-aware rewrite, or experiment assignment before Next.js selects a page. **Proxy** handles these early routing decisions. It runs before file-system routes, so its matchers and runtime costs affect every request they cover.

```typescript
// proxy.ts — transparent experiment rewrite, URL unchanged
export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname === '/') {
    const cookie = request.cookies.get('ab_variant')?.value;
    const variant = cookie === 'a' || cookie === 'b' ? cookie : (Math.random() < 0.5 ? 'a' : 'b');
    const destination = request.nextUrl.clone();
    destination.pathname = `/landing-${variant}`;
    return NextResponse.rewrite(destination);
  }
  return NextResponse.next();
}
```

## Definition

In Next.js 16, **Proxy** is a request-interception layer declared in `proxy.ts` (or `middleware.ts` in Next.js 15) that executes before an incoming HTTP request reaches any page, layout, or route handler.

Proxy can continue, rewrite, redirect, change request or response headers, set cookies, or return a response directly. In Next.js 16 its runtime defaults to Node.js; deployment placement is platform-specific.

> **Textbook Definition:** Proxy is a pre-route request boundary that can continue, redirect, rewrite, or answer a request before its destination runs. It can make an early routing decision, but it does not replace authorization at the protected data read or mutation.

## First Principles

Use Proxy only for decisions knowable before the route runs. **Match narrowly**: it executes before route resolution, so unscoped matchers tax assets and APIs that need no early routing. **Decide independently of rendering**: Proxy sees URL, headers, and cookies — never the page's output or downstream data results. **Authorize at the destination**: a Proxy redirect improves navigation, but every protected page, Server Function, and Route Handler must still verify identity and permissions.

```text
Incoming HTTP Request
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ next.config.js headers and redirects                   │
└───────────────────────┬────────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────────┐
│ proxy.ts (Next.js 16) / middleware.ts (Next.js 15)      │
│ ├─ Matcher filters URL patterns                         │
│ ├─ Reads cookies, headers, pathname                     │
│ ├─ Options: Rewrite, Redirect, Add Headers, Return 429  │
└───────────────────────┬─────────────────────────────────┘
                        ▼
┌────────────────────────────────────────────────────────┐
│ File-System Routing (Page, Layout, Route Handler)      │
│ └─ Data fetching, Server Component rendering, auth     │
└────────────────────────────────────────────────────────┘
```

## 1. Match Only the Requests That Need an Early Decision

The statically analyzable `config.matcher` controls where Proxy runs. Without a matcher, it runs on every request, including `public/` assets, `/_next/static` and `/_next/image`. Keep matcher values as literals that Next.js can analyze at build time. Exclude routes that do not need early logic, but keep security checks in the destination handler even when a path bypasses Proxy.

Execution order matters: `next.config` headers and redirects run first, Proxy runs next, then `beforeFiles` rewrites and filesystem routes are considered. A matcher exclusion also excludes Server Function POSTs sent to that page route.

```typescript
// proxy.ts (Next.js 16)
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  // Logic executes only for routes matched by config below
  return NextResponse.next()
}

export const config = {
  matcher: [
    /*
     * Match all request paths except:
     * 1. /api/webhooks/* (the Route Handler still verifies the webhook)
     * 2. /_next/static (Static client chunks)
     * 3. /_next/image (Optimized images)
     * 4. Static files (favicon.ico, sitemap.xml, robots.txt)
     */
    '/((?!api/webhooks|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)',
  ],
}
```

For Next.js 15, name the file `middleware.ts` and export a function named `middleware` (or a default function); do not copy the named `proxy` export unchanged. Matcher boundaries matter: use segment-aware patterns such as `/dashboard/:path*` so `/dashboard-preview` is not captured accidentally. Server Functions issue `POST` requests to their page route, so they follow that route's matcher. Authenticate and authorize the function itself.

## 2. A/B Testing via Transparent Rewrites

A **redirect** changes the browser URL and costs a second round-trip. A **rewrite** changes the destination internally while the address bar stays put — the classic experiment assignment:

```typescript
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

const COOKIE_NAME = 'ab_experiment_variant'

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  // Target marketing landing page only
  if (pathname === '/') {
    const existingVariant = request.cookies.get(COOKIE_NAME)?.value
    const hasValidVariant = existingVariant === 'a' || existingVariant === 'b'
    const variant = hasValidVariant
      ? existingVariant
      : Math.random() < 0.5 ? 'a' : 'b'

    // Keep the original query and other URL context when changing the path.
    const destination = request.nextUrl.clone()
    destination.pathname = `/landing-${variant}`
    const response = NextResponse.rewrite(destination)

    // Persist variant in cookie for future visits
    if (!hasValidVariant) {
      response.cookies.set(COOKIE_NAME, variant, {
        httpOnly: true,
        secure: process.env.NODE_ENV === 'production',
        sameSite: 'lax',
        path: '/',
        maxAge: 60 * 60 * 24 * 30, // 30 days
      })
    }

    return response
  }

  return NextResponse.next()
}
```

Attaching the cookie to the returned rewrite response persists the assignment in the same exchange. Two first-time requests can still race and choose different variants, so use a stable assignment service if consistency across concurrent requests matters. If the rendered variant is publicly cached, partition the cache by variant or bypass shared caching; a cookie does not automatically create a safe CDN cache key.

## 3. Header Forwarding and Security Injection

Proxy can inject security headers across matched routes and forward verified request attributes downstream:

```typescript
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  // Clone incoming request headers to pass data to downstream Server Components
  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-request-id', crypto.randomUUID())

  // Pass modified headers to downstream route handlers and pages
  const response = NextResponse.next({
    request: {
      headers: requestHeaders,
    },
  })

  // Set browser-facing security headers on the HTTP response
  response.headers.set('X-Frame-Options', 'DENY')
  response.headers.set('X-Content-Type-Options', 'nosniff')
  response.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin')

  return response
}
```

Notice the critical distinction: `request.headers` passed inside `NextResponse.next({ request: { headers } })` travel downstream to your page components and route handlers. In contrast, `response.headers.set()` headers travel to the client's browser.

## 4. Rate-Limit at a Shared Boundary

Proxy can reject obvious bursts before route work, but a process-local `Map` is not a production quota: instances do not share counts, updates are not atomic across concurrent requests, and stale keys need cleanup. Prefer a gateway or shared atomic limiter with a defined key, window, expiry and `429`/`Retry-After` response. Trust an IP header only when the ingress overwrites client-supplied values; IP alone is not an account-level quota.

## 5. Keep the Boundary Small and Trustworthy

- **Do not turn Proxy into an application service:** Database reads and slow external calls add latency before routing. Prefer static redirects and headers in `next.config` when possible; use Proxy only when a decision depends on the incoming request.
- **A cookie is only an input:** Presence does not prove a valid session, current identity or permission. Verify those at each protected data read or mutation.
- **Leave webhook bodies to their handler:** A request body is a one-use stream. Read the raw body and verify its signature in the Route Handler that owns the webhook contract.
- **Check the versioned runtime:** Next.js 15 Middleware defaults to Edge; Node.js became stable in 15.5. Next.js 16 renamed it to Proxy, which defaults to Node.js and rejects a `runtime` export.

## Summary

Proxy is a pre-route request hook: use a precise matcher for redirects, rewrites or request-derived routing, then let the selected Route Handler or page validate inputs and authorize data access. In Next.js 16 the runtime defaults to Node.js; keep the hook small and do not rely on it as a security boundary.

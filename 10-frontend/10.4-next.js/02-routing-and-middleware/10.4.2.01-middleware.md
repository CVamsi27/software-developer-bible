# Proxy (formerly Middleware) in Next.js

Before any page renders, layout executes, or database query runs, incoming HTTP requests arrive at the front door of your Next.js application. At this boundary, teams often need to make instant routing choices: Redirect unauthenticated requests to `/login` before wasting server cycles. Rewrite multi-tenant subdomains (`tenant.app.com`) to internal workspace paths (`/workspaces/tenant`). Assign an A/B testing experiment variant before the first byte of HTML renders. Or inject security headers across every route.

In Next.js, **Proxy** (historically named Middleware) serves as the programmable traffic gateway stationed directly in front of the routing engine. Executing before file-system route resolution, Proxy intercepts requests in flight to redirect, rewrite, modify headers, or return early responses.

Used strategically, it eliminates unnecessary page execution and ensures consistent request hygiene. Misunderstood, however, it becomes an application-wide bottleneck that introduces latency onto every incoming request and creates false senses of security.

## Definition

In Next.js 16, **Proxy** is a request-interception layer declared in `proxy.ts` (or `middleware.ts` in Next.js 15) that executes before an incoming HTTP request reaches any page, layout, or route handler.

Proxy can rewrite URLs internally, issue HTTP redirects, read and write request/response headers, set cookies, or return responses directly.

> **Textbook Definition:** Proxy is a pre-route request boundary that can continue, redirect, rewrite, or answer a request before its destination runs. It can make an early routing decision, but it does not replace authorization at the protected data read or mutation.

## First Principles

The operational constraints of Proxy stem from its location in the request lifecycle:

1. **Every matched request blocks on Proxy execution:** Because Proxy executes before the route tree resolves, any synchronous stall, un-cached external API fetch, or database connection made inside Proxy adds direct latency to Time to First Byte (TTFB). Keep its logic lightweight, CPU-bounded, and fast.
2. **Proxy executes before rendering begins:** Proxy receives the incoming HTTP request, but it cannot inspect the rendered HTML, streaming components, or downstream database models that execute later in the page lifecycle. It manages traffic direction, not response content transformation.
3. **Optimistic routing is not access authorization:** Redirecting unauthenticated requests at the Proxy boundary improves user experience by eliminating flash-of-unauthenticated-content, but it does not protect your data. If an attacker bypasses Proxy or hits an internal API endpoint directly, the data access layer must still authenticate the session and authorize the specific resource.

## Configuration and Matcher Precision

Proxy execution is governed by `config.matcher`. By default, Proxy runs on every route in the project. Failing to filter static assets forces Proxy to intercept images, stylesheets, and favicon requests, unnecessarily multiplying execution overhead.

```typescript
// proxy.ts (Next.js 16) or middleware.ts (Next.js 15)
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  // Logic executes only for routes matched by config below
  return NextResponse.next()
}

export const config = {
  matcher: [
    /*
     * Match all request paths except:
     * 1. /api/webhooks/* (Allow raw webhooks without proxy interference)
     * 2. /_next/static (Static client chunks)
     * 3. /_next/image (Optimized images)
     * 4. Static files (favicon.ico, sitemap.xml, robots.txt)
     */
    '/((?!api/webhooks|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)',
  ],
}
```

### Matcher Boundaries:
- Use segment-aware matching (`/dashboard/:path*`) rather than simple string prefixes so `/dashboard-preview` is not inadvertently captured by a `/dashboard` rule.
- Remember that Next.js Server Functions (Server Actions) issue `POST` requests to the current page route. If your matcher filters out specific routes, Server Actions executed from those routes also bypass Proxy.

## Essential Architectural Patterns

### 1. A/B Testing via Transparent Rewrites

A classic use of Proxy is assigning experiment variants without changing the URL displayed in the browser bar. A **redirect** causes the browser URL to change and triggers a second round-trip. A **rewrite** changes the destination route internally while keeping the browser address bar unchanged:

```typescript
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

const COOKIE_NAME = 'ab_experiment_variant'

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  // Target marketing landing page only
  if (pathname === '/') {
    const existingVariant = request.cookies.get(COOKIE_NAME)?.value
    const variant = existingVariant === 'a' || existingVariant === 'b'
      ? existingVariant
      : Math.random() < 0.5 ? 'a' : 'b'

    // Rewrite internally to the assigned variant folder
    const response = NextResponse.rewrite(new URL(`/landing-${variant}`, request.url))

    // Persist variant in cookie for future visits
    if (!existingVariant) {
      response.cookies.set(COOKIE_NAME, variant, {
        httpOnly: true,
        secure: process.env.NODE_ENV === 'production',
        sameSite: 'lax',
        path: '/',
        maxAge: 60 * 60 * 24 * 30, // 30 days
      })
    }

    return response
  }

  return NextResponse.next()
}
```

Attaching the cookie directly to the rewrite response ensures the browser receives the assignment in the same HTTP exchange.

### 2. Header Forwarding and Security Injection

Proxy can inject security headers across all matched routes, as well as forward verified request attributes downstream to Server Components:

```typescript
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  // Clone incoming request headers to pass data to downstream Server Components
  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-request-id', crypto.randomUUID())

  // Pass modified headers to downstream route handlers and pages
  const response = NextResponse.next({
    request: {
      headers: requestHeaders,
    },
  })

  // Set browser-facing security headers on the HTTP response
  response.headers.set('X-Frame-Options', 'DENY')
  response.headers.set('X-Content-Type-Options', 'nosniff')
  response.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin')

  return response
}
```

Notice the critical distinction: `request.headers` passed inside `NextResponse.next({ request: { headers } })` travel downstream to your page components and route handlers. In contrast, `response.headers.set()` headers travel to the client's browser.

### 3. Route-Level Rate Limiting Boundary

While enterprise production systems enforce rate limiting at edge API gateways (Cloudflare, AWS WAF), Proxy can implement emergency fixed-window throttling for sensitive endpoints:

```typescript
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

const requestCounts = new Map<string, { count: number; resetAt: number }>()
const WINDOW_MS = 60 * 1000 // 1 minute
const MAX_REQUESTS = 60

export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname.startsWith('/api/sensitive/')) {
    // Derive client IP from trusted ingress header
    const ip = request.headers.get('x-forwarded-for')?.split(',')[0].trim() || 'anonymous'
    const now = Date.now()
    const tracker = requestCounts.get(ip)

    if (!tracker || now > tracker.resetAt) {
      requestCounts.set(ip, { count: 1, resetAt: now + WINDOW_MS })
      return NextResponse.next()
    }

    if (tracker.count >= MAX_REQUESTS) {
      const retryAfter = Math.ceil((tracker.resetAt - now) / 1000)
      return NextResponse.json(
        { error: 'Rate limit exceeded. Try again later.' },
        {
          status: 429,
          headers: {
            'Retry-After': String(retryAfter),
          },
        }
      )
    }

    tracker.count += 1
    return NextResponse.next()
  }

  return NextResponse.next()
}
```

In multi-instance production environments, in-memory Maps are local to each server process; production limiters should leverage low-latency atomic data stores like Redis.

## Critical Engineering Pitfalls

- **The Database-in-Proxy Trap:** Attempting to query heavy SQL databases or initialize heavy ORMs inside Proxy degrades performance for every matched route. Use Proxy strictly for cookie decoding, lightweight cryptographic token inspection (verifying JWT signatures), and URL re-routing.
- **Proxy Is Not Authorization:** Checking for the presence of an `auth-token` cookie in Proxy prevents accidental navigation, but a malicious client can forge dummy cookies. Always verify the signature, expiration, and user permissions at the database access layer in your Server Components and Route Handlers.
- **Consuming Request Bodies:** Request bodies in the Web Fetch standard are single-use streams. Attempting to parse `request.json()` or `request.formData()` inside Proxy consumes the stream, leaving downstream route handlers unable to read the request body. Avoid inspecting or modifying request bodies in Proxy.
- **Runtime Differences (Next.js 15 vs 16):** Next.js 15 Middleware defaults to the Edge runtime and permits Node.js via `config.runtime = 'nodejs'`. Next.js 16 Proxy runs natively in Node.js and rejects the `runtime` configuration export.

## Summary

Proxy provides a programmable gateway at the edge of your Next.js application, intercepting HTTP requests before route rendering occurs. By keeping logic bounded, filtering static routes with precise matchers, employing transparent URL rewrites, and keeping deep data validation at the page layer, you establish robust routing control without penalizing application performance.

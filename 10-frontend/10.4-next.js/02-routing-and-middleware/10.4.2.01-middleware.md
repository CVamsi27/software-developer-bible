# Proxy (formerly Middleware) in Next.js

## Definition

In Next.js 16, **Proxy** is a request-interception function that runs before a request reaches its page or handler. It can redirect, rewrite, modify request or response headers, set cookies, or return a response. Next.js 15 uses the `middleware.ts` convention; Next.js 16 renames it to `proxy.ts` and deprecates the old convention.

> **Textbook Definition:** Proxy is a pre-route request boundary that can continue, redirect, rewrite, or answer a request before its destination runs. It can make an early routing decision, but it does not replace authorization at the protected data read or mutation.


## First Principles

Proxy exists for decisions that must happen before the destination runs:

1. **A matched request waits for the decision:** Proxy adds work before the route. Keep it bounded; slow data access belongs in the route or service that owns it.
2. **It cannot inspect rendered page output:** return a redirect, rewrite, response or continue signal. Work that depends on the completed response belongs after rendering or at the hosting layer.

## Keep request-dependent decisions at the routing boundary

Use Proxy for a cheap routing choice that depends on the incoming request: a locale redirect, an experiment rewrite, or a request-specific redirect. Put fixed path maps in `next.config` and authorization beside the protected data operation. A cookie check may improve navigation, but it cannot authorize a later page action or data read. Next.js 15 Middleware defaults to Edge and can opt into Node.js from 15.5; Next.js 16 Proxy defaults to Node.js and rejects a `runtime` setting. A runtime label alone does not guarantee low latency.

## Trace matching, decisions, and destination

**Version scope:** Code examples use the current Next.js 16 `proxy.ts` / `export function proxy` convention. Next.js 15 uses `middleware.ts` / `export function middleware`, defaults to Edge, and supports Node.js with `config.runtime: 'nodejs'` from 15.5. In Next.js 16 the old convention is deprecated; Proxy defaults to Node.js and has no `runtime` option. Runtime support and actual geographic placement are separate choices.

Match static literal paths in `config.matcher`; Next.js analyzes them at build time. Match path segments (`pathname === route || pathname.startsWith(route + '/')`) rather than raw prefixes so `/admin-tools` does not accidentally match `/admin`. A broad matcher can also intercept metadata files such as `robots.txt`, `sitemap.xml`, and Open Graph images, so exclude them when they do not need Proxy logic. Test prefetch and data requests as well as direct page visits.

Proxy runs after `next.config` headers and redirects and before filesystem routes and later rewrite phases. A Server Function call is a POST to the route where it is used, not a separate route. A matcher that skips that path also skips Proxy for the function call, so the function itself must authenticate and authorize every operation. Forwarded client-IP, country, and identity headers are trustworthy only when a trusted ingress overwrites caller-supplied values. `NextRequest.geo` is not available in current Next.js; use the host's documented location source. User-agent strings can suggest bot behavior but are spoofable; cookies and forwarded headers are untrusted until validated.

The decision is deliberately early: Proxy cannot inspect the page HTML that will be produced. It can add a response cookie or header, or pass a request header to the destination; response headers go to the browser, while forwarded request headers go to the handler. Set cookies on the response that is actually returned. Avoid carrying secrets in either kind of header. The in-memory rate-limit example below is only a single-process sketch: production enforcement needs a shared atomic store, expiry, a trusted client identity, and a clear failure policy.

### Trace routing before the destination runs

```text
Request / → matcher → assign variant b → rewrite to /variant-b
Browser address stays /; returned rewrite response also sets variant cookie
Next request / → saved b → same destination (unless the experiment changes)
```

A **redirect** tells the browser to request another URL; its address changes. A **rewrite** selects a different internal destination while preserving the visible URL. `NextResponse.next()` continues the current route. Response headers go to the browser; forwarded request headers go to the destination handler. An early gate cannot inspect HTML that has not rendered yet.

These decisions add work before the matched destination. Geographic placement and cold-start latency depend on the host and runtime; Edge is not a universal speed guarantee. API handlers own bodies and response semantics, while Server Components own UI output.

## Apply the boundary to common routing work

### Authentication Redirects

> The full cookie-presence redirect example lives in [Authentication](../04-production/10.4.4.01-authentication.md#1-proxy-for-early-redirects). It is an optimistic UX gate: validate session signature/expiry and resource permissions at the data-access layer. A forged or expired cookie must not grant access or create a login/dashboard redirect loop.

### Role-Based Access Control

> JWT validation and route-role checks live in [Authentication](../04-production/10.4.4.01-authentication.md#6-role-based-access-control). If you pass verified identity downstream, clone `request.headers`, overwrite the identity fields, and pass them through `NextResponse.next({ request: { headers } })`; setting `response.headers` only sends them to the browser. Routes must still enforce authorization themselves.

### A/B Testing Proxy

```typescript
// proxy.ts — Next.js 16 (Next.js 15 used middleware.ts / middleware)
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  const saved = request.cookies.get('ab-variant')?.value
  const variant = saved === 'a' || saved === 'b' ? saved : Math.random() > 0.5 ? 'a' : 'b'
  const response = request.nextUrl.pathname === '/'
    ? NextResponse.rewrite(new URL(`/variant-${variant}`, request.url))
    : NextResponse.next()

  response.cookies.set('ab-variant', variant, {
    httpOnly: true, secure: true, sameSite: 'lax', path: '/',
    maxAge: 60 * 60 * 24 * 30,
  })
  return response
}

export const config = { matcher: '/' }
```

The cookie must be attached to the actual rewrite response. Setting it on one response and returning a newly created response discards the cookie; accepting only `a` or `b` keeps the destination within the experiment's expected set.

### URL Rewriting

```typescript
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  // Rewrite /blog/:slug to /posts/:slug
  if (pathname.startsWith('/blog/')) {
    const slug = pathname.replace('/blog/', '')
    const rewriteUrl = request.nextUrl.clone()
    rewriteUrl.pathname = `/posts/${slug}`
    return NextResponse.rewrite(rewriteUrl)
  }

  // Rewrite API versioning
  if (pathname.startsWith('/api/v1/')) {
    const newPath = pathname.replace('/api/v1/', '/api/')
    const rewriteUrl = request.nextUrl.clone()
    rewriteUrl.pathname = newPath
    return NextResponse.rewrite(rewriteUrl)
  }

  return NextResponse.next()
}

```

Cloning the URL preserves query parameters such as pagination; constructing a path-only URL would discard them. Define whether the destination expects an encoded segment or a nested path before rewriting arbitrary user input.

### Rate Limiting Boundary

The in-memory sketch below illustrates fixed-window decisions only. It is not a production limiter: process restarts and replicas reset or split counters, and high-cardinality keys need eviction. Next recommends using Proxy sparingly; enforce limits at a gateway or an atomic shared store, with a host-verified client identity and an explicit failure policy. `trustedClientIp` is an application adapter, not a Next.js API.

```typescript
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

const rateLimit = new Map<string, { count: number; timestamp: number }>()

const WINDOW_MS = 60 * 1000 // 1 minute
const MAX_REQUESTS = 100

export function proxy(request: NextRequest) {
  const ip = trustedClientIp(request) // Host-specific adapter; overwrites untrusted input
  const now = Date.now()

  const record = rateLimit.get(ip)

  if (!record || now - record.timestamp >= WINDOW_MS) {
    rateLimit.set(ip, { count: 1, timestamp: now })
    return NextResponse.next()
  }

  if (record.count >= MAX_REQUESTS) {
    return NextResponse.json(
      { error: 'Too many requests' },
      { status: 429, headers: { 'Retry-After': String(Math.ceil((WINDOW_MS - (now - record.timestamp)) / 1000)) } }
    )
  }

  record.count++
  return NextResponse.next()
}

```

Requests 1–100 within one window pass; request 101 returns 429 without incrementing the count. At the window boundary, the first request starts a new record. This fixed-window scheme can permit nearly twice the limit across adjacent windows; a shared implementation must preserve atomic increments and expiry. `trustedClientIp` must define the host trust boundary—using an arbitrary forwarded-header string lets callers evade limits, while one `unknown` key unfairly groups users.

### Composing Proxy Helpers

Compose one entry point from small helpers. A helper can return `null` to continue or a complete response to stop, avoiding brittle tests such as `status !== 200` for `NextResponse.next()`. Preserve accumulated headers/cookies on the final response; the [rate-limit example](#rate-limiting-boundary) shows only the fixed-window decision, not a production storage design.

```typescript
// proxy.ts — helpers return a response or null to continue
export async function proxy(request: NextRequest) {
  const blocked = await enforceRateLimit(request)
  if (blocked) return blocked
  const authFailure = await enforceSessionForProtectedPath(request)
  if (authFailure) return authFailure
  return NextResponse.next()
}
```

## Design Decisions and Failure Boundaries

- **Choose the narrowest owner.** Fixed redirects and headers belong in `next.config`; request-dependent routing belongs in Proxy; body parsing, upload validation, and resource authorization belong in the destination handler or data layer.
- **Treat matching as part of the security design.** `/dashboard` does not match `/dashboard/settings`; `:path*` includes nested paths. Avoid redirecting a login route back through the same gate, and test direct visits, prefetches, API/data requests, metadata files, and Server Functions.
- **Use the right runtime and trust boundary.** Next.js 15 Edge Middleware cannot use Node-only APIs; Next.js 16 Proxy uses Node.js and does not accept a `runtime` option. Provider-specific forwarding headers are safe only if ingress overwrites client values.
- **Keep work bounded and observable.** A slow identity or shared-store lookup delays every matched request. Measure p95 latency and define what happens if that dependency is unavailable. Module globals are neither durable nor shared across instances.
- **Do not transform request bodies here.** The body is a one-use stream; consuming it can leave the handler with nothing to read, and buffering a large upload adds latency and memory pressure.

## Summary

Proxy makes an early routing decision: continue, redirect, rewrite, or return a response. Keep matchers narrow, account for Server Function and metadata requests, and keep slow work out of the pre-route path. Treat Proxy checks as navigation aids; the protected handler or data operation remains the authorization boundary.

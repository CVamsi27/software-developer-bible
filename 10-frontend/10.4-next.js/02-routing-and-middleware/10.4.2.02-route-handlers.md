# Route Handlers in Next.js

## Definition

**Route Handlers** are the App Router equivalent of API Routes in the Pages Router. They allow you to create API endpoints within the `app/` directory, handling HTTP requests with full access to Web APIs like Request and Response objects.

> **Textbook Definition:** A Route Handler implements an HTTP method at a filesystem route using request and response APIs. It owns status, headers and body semantics and must enforce validation, authorization and caching policy for its endpoint.


## First Principles

Route handlers are *your* HTTP server surface inside the framework:

1. **The handler is a Web-standard Request→Response function** — Next adds routing, caching semantics, and colocated files, but HTTP semantics are yours to get right (methods, status codes, → 20.3.1.02).
2. **A GET response is not automatically safe to share** — Next.js 15+ leaves GET Route Handlers uncached by default; opt in only for public output independent of request cookies, headers, or query data (→ 10.4.3.03).

## Why It Matters

Senior engineers use Route Handlers for: webhooks, REST API endpoints, third-party integrations, OAuth callbacks. They know Route Handlers are full HTTP endpoints (vs. Server Actions which are mutations), and they configure the runtime (`export const runtime = 'edge' | 'nodejs'`) based on latency/feature needs.

## How It Works

**Version scope:** Examples use Next.js 15+ async route params and the caching model with Cache Components disabled. GET responses require explicit cache opt-in; HTTP `Cache-Control` affects browser/CDN caching separately from Next's Data/Full Route caches. Pages Router API routes remain supported and can stream responses—they are not deprecated merely because the App Router exists.

A `route.ts` can sit in any app segment, but cannot share a segment with `page.tsx`. A request body is a one-use stream: verify webhook signatures against its raw text before parsing. Untrusted query pagination must be finite positive integers with a bounded limit before using ORM offsets.

### Trace an HTTP request through its owner

```text
GET /api/users/42 → app/api/users/[id]/route.ts → GET export
                 → await params → authorize read → load user → JSON + status
```

The segment supplies `id="42"`; it does not prove that the visitor may read user 42. A missing user can return 404, denied access uses the application's disclosure policy, and an upstream failure is a different outcome. Exporting `GET` does not make a response cacheable or make a POST valid.

App Router handlers use Web request/response APIs. Pages Router API routes use `req`/`res`; both remain supported, and both depend on their chosen host's runtime, duration and streaming capabilities.

## Code Examples

### Basic Route Handler

The following stub illustrates method dispatch and response shape; it does not persist users or validate a signup. The [validated creation example](#route-handler-with-error-handling) is the canonical write boundary.

```typescript
// app/api/users/route.ts
import { NextRequest, NextResponse } from 'next/server'

export async function GET(request: NextRequest) {
  const users = [
    { id: 1, name: 'John' },
    { id: 2, name: 'Jane' },
  ]

  return NextResponse.json(users)
}

export async function POST(request: NextRequest) {
  const body = await request.json()

  const newUser = {
    id: Date.now(),
    name: body.name,
    email: body.email,
  }

  return NextResponse.json(newUser, { status: 201 })
}

```

### Dynamic Route Handler

```typescript
// app/api/users/[id]/route.ts
import { NextRequest, NextResponse } from 'next/server'

export async function GET(
  request: NextRequest,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params

  await requireUserReadAccess(request, id) // Application adapter; map denial to HTTP policy
  const user = await db.user.findUnique({
    where: { id },
    select: { id: true, name: true }, // Only fields safe for this caller
  })

  if (!user) {
    return NextResponse.json(
      { error: 'User not found' },
      { status: 404 }
    )
  }

  return NextResponse.json(user)
}

```

For a protected update, parse a narrow schema into an allowlist of editable fields, authorize the session against this user, and handle missing/concurrent records explicitly. Never pass the whole request JSON to `db.user.update`: a visitor could supply fields such as roles or tenant IDs. Deletes need the same resource authorization; define whether repeated deletion is a successful no-op or a 404. The database module and access checks are application adapters.

### Route Handler with Query Params

```typescript
// app/api/search/route.ts
import { NextRequest, NextResponse } from 'next/server'

export async function GET(request: NextRequest) {
  const searchParams = request.nextUrl.searchParams
  const query = searchParams.get('q')?.trim()
  const page = Number(searchParams.get('page') ?? '1')
  const limit = Number(searchParams.get('limit') ?? '10')
  if (!Number.isSafeInteger(page) || page < 1 || !Number.isSafeInteger(limit) || limit < 1 || limit > 100 ||
      !Number.isSafeInteger((page - 1) * limit)) {
    return NextResponse.json({ error: 'Invalid pagination' }, { status: 400 })
  }

  if (!query || query.length > 200) {
    return NextResponse.json(
      { error: 'Query must contain 1–200 characters' },
      { status: 400 }
    )
  }

  const results = await db.post.findMany({
    where: {
      title: { contains: query },
    },
    skip: (page - 1) * limit,
    take: limit,
  })

  return NextResponse.json({
    results,
    page,
    limit,
    total: await db.post.count({
      where: { title: { contains: query } },
    }),
  })
}

```

This search sketch assumes public posts. Add tenant/publication filters where required. A bounded page size does not bound a very large offset or the count query cost; enforce a product-specific maximum page or use cursor pagination for deep result sets. The count and rows are separate reads and may reflect different concurrent snapshots.

### Route Handler with Headers

```typescript
// app/api/data/route.ts
import { NextRequest, NextResponse } from 'next/server'

export async function GET(request: NextRequest) {
  const apiKey = request.headers.get('x-api-key')

  if (!process.env.API_KEY || apiKey !== process.env.API_KEY) {
    return NextResponse.json(
      { error: 'Invalid API key' },
      { status: 401 }
    )
  }

  const data = await fetchData()

  return NextResponse.json(data, {
    headers: {
      'Cache-Control': 'private, no-store',
      'X-Custom-Header': 'value',
    },
  })
}

```

### Route Handler with Cookies

```typescript
// app/api/session/route.ts
import { NextRequest, NextResponse } from 'next/server'

export async function POST(request: NextRequest) {
  const { username, password } = await request.json()

  const user = await authenticate(username, password)

  if (!user) {
    return NextResponse.json(
      { error: 'Invalid credentials' },
      { status: 401 }
    )
  }

  const response = NextResponse.json({ success: true })

  response.cookies.set('session', user.sessionId, {
    httpOnly: true,
    secure: true,
    sameSite: 'lax',
    path: '/',
    maxAge: 60 * 60 * 24 * 7, // Align with server session expiry
  })

  return response
}

export async function DELETE(request: NextRequest) {
  const response = NextResponse.json({ success: true })
  response.cookies.delete('session')
  return response
}

```

The authentication adapter must validate credentials, create/rotate a session and set its expiry. Logout should revoke that server session as well as clear the cookie using its matching scope. These abbreviated handlers also need input validation, abuse limits and a CSRF policy for cookie-authenticated mutations.

### Route Handler with Streaming

```typescript
// app/api/stream/route.ts
import { NextRequest } from 'next/server'

export async function GET(request: NextRequest) {
  const encoder = new TextEncoder()

  let count = 0
  let timer: ReturnType<typeof setInterval> | undefined
  const stop = () => { if (timer !== undefined) clearInterval(timer) }
  const stream = new ReadableStream<Uint8Array>({
    start(controller) {
      timer = setInterval(() => {
        controller.enqueue(encoder.encode(`data: ${JSON.stringify({ count })}\n\n`))
        count += 1
        if (count === 10) { stop(); controller.close() }
      }, 1000)
    },
    cancel() { stop() }, // A disconnected consumer must not keep the producer running.
  })

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
    },
  })
}

```

These frames use the Server-Sent Events protocol, but the sketch has no durable IDs/replay, heartbeat or upstream error mapping. Cancellation stops the local producer; buffering and connection duration depend on the proxy/host. A cookie-authenticated stream still needs access checks before returning its body.

### Route Handler with Webhooks

```typescript
// app/api/webhooks/stripe/route.ts
import { NextRequest, NextResponse } from 'next/server'
import Stripe from 'stripe'

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!)

export async function POST(request: NextRequest) {
  const body = await request.text()
  const sig = request.headers.get('stripe-signature')!

  let event: Stripe.Event

  try {
    event = stripe.webhooks.constructEvent(
      body,
      sig,
      process.env.STRIPE_WEBHOOK_SECRET!
    )
  } catch (err) {
    return NextResponse.json(
      { error: 'Webhook signature verification failed' },
      { status: 400 }
    )
  }

  switch (event.type) {
    case 'payment_intent.succeeded':
      const paymentIntent = event.data.object as Stripe.PaymentIntent
      await handlePaymentSuccess(paymentIntent)
      break
    case 'payment_intent.payment_failed':
      const failedPayment = event.data.object as Stripe.PaymentIntent
      await handlePaymentFailure(failedPayment)
      break
  }

  return NextResponse.json({ received: true })
}

```

Successful signature verification does not make event delivery unique or ordered. `handlePaymentSuccess` and `handlePaymentFailure` must durably deduplicate event IDs and apply state transitions transactionally. Return success after durable acceptance; retryable processing failures must not be acknowledged as completed.

### Route Handler with File Upload

```typescript
// app/api/upload/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { put } from '@vercel/blob'

export async function POST(request: NextRequest) {
  await requireUploadPermission(request) // Authenticate/authorize before buffering
  const formData = await request.formData()
  const file = formData.get('file')

  if (!(file instanceof File)) {
    return NextResponse.json(
      { error: 'No file provided' },
      { status: 400 }
    )
  }

  if (file.size > 5 * 1024 * 1024 || !['image/png', 'image/jpeg'].includes(file.type)) {
    return NextResponse.json({ error: 'Unsupported image or size' }, { status: 400 })
  }
  // Extension/MIME are hints; inspect/re-encode bytes before publishing in production.
  const blob = await put(`uploads/${crypto.randomUUID()}`, file, {
    access: 'public',
  })

  return NextResponse.json({
    url: blob.url,
    pathname: blob.pathname,
  })
}

```

This upload publishes a public URL, so it is unsuitable for private documents. `requireUploadPermission` is an application adapter; size checks after `formData()` do not stop an oversized body from being buffered. Enforce request limits at the host and use direct-to-storage upload flows for large files. Inspect bytes, avoid caller-controlled object paths and apply quota/cleanup policy.

### Route Handler with Revalidation

The canonical model and authenticated, allowlisted invalidation policy live in [Data and Caching](../03-data-and-caching/10.4.3.03-caching.md). In Next.js 16, `revalidateTag(tag, 'max')` marks tagged data for stale-while-revalidate behavior; a one-argument call is deprecated. Invalidating a cache is separate from regenerating it and does not instantly update every visitor's screen.

### Route Handler with Error Handling

```typescript
// app/api/users/route.ts
import { z } from 'zod'
import { db } from '@/lib/database'

const userSchema = z.object({ name: z.string().min(2), email: z.string().email() })

export async function POST(request: Request) {
  let body: unknown
  try { body = await request.json() }
  catch { return Response.json({ error: 'Malformed JSON' }, { status: 400 }) }

  const result = userSchema.safeParse(body)
  if (!result.success) {
    return Response.json({ error: 'Validation failed', details: result.error.issues }, { status: 400 })
  }
  try {
    const user = await db.user.create({ data: result.data })
    return Response.json(user, { status: 201 })
  } catch (error) {
    console.error('Failed to create user:', error)
    return Response.json({ error: 'Internal server error' }, { status: 500 })
  }
}
```

Whitelist parsed fields instead of sending arbitrary JSON directly to an ORM. This is a public signup-shaped example; protected administrative mutations must also validate session and role before writing.

### Route Handler with Middleware Integration

```typescript
// middleware.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function middleware(request: NextRequest) {
  // Add API key validation for all /api routes
  if (request.nextUrl.pathname.startsWith('/api/')) {
    const apiKey = request.headers.get('x-api-key')

    if (!apiKey || apiKey !== process.env.API_KEY) {
      return NextResponse.json(
        { error: 'Invalid API key' },
        { status: 401 }
      )
    }
  }

  return NextResponse.next()
}

```

## Common Mistakes

### 1. Using Node.js APIs in Edge Runtime

```typescript
// BAD: Node.js APIs not available in Edge
export const runtime = 'edge'

export async function GET() {
  const fs = require('fs') // Error!
  const data = fs.readFileSync('file.txt')
  return Response.json({ data })
}

// GOOD: Use Web APIs
export async function GET() {
  const response = await fetch('https://api.example.com/data')
  const data = await response.json()
  return Response.json(data)
}

```

### 2. Not Handling All HTTP Methods

Export only the methods your endpoint supports. Next.js returns `405 Method Not Allowed` for an unsupported method and supplies `OPTIONS` automatically when you do not define it. Adding unrestricted POST/PUT/DELETE handlers to a read-only route unnecessarily expands its write surface.

### 3. Not Validating Request Body

> The [error-handling example](#route-handler-with-error-handling) parses a schema and maps invalid input to 400. A raw `schema.parse()` exception is not automatically an HTTP 400; either catch the validation error or use `safeParse`. Authorization and input validation solve different problems.

### 4. Not Returning Proper Status Codes

```typescript
// BAD: Always returning 200
export async function POST(request: Request) {
  try {
    const user = await createUser(request)
    return Response.json(user) // 200 for creation?
  } catch (error) {
    return Response.json({ error: 'Failed' }) // 200 for error?
  }
}

// GOOD: Proper status codes
export async function POST(request: Request) {
  try {
    const user = await createUser(request)
    return Response.json(user, { status: 201 }) // 201 Created
  } catch (error) {
    return Response.json(
      { error: 'Failed' },
      { status: 500 } // 500 Internal Server Error
    )
  }
}

```

### 5. Not Handling CORS

For a public, non-credentialed cross-origin endpoint, return the same CORS headers on the response and its preflight. Cookie-bearing APIs need an explicit allowed origin and `Access-Control-Allow-Credentials`, rather than `*`; CORS does not authenticate callers.

```typescript
const corsHeaders = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Methods': 'GET, OPTIONS',
  'Access-Control-Allow-Headers': 'Content-Type, Authorization',
}
export async function OPTIONS() {
  return new Response(null, { status: 204, headers: corsHeaders })
}
export async function GET() {
  return Response.json({ data: [] }, { headers: corsHeaders })
}
```

## Best Practices

1. **Use proper HTTP methods** — GET for reading, POST for creating, etc.

2. **Return appropriate status codes** — 200, 201, 400, 401, 404, 500

3. **Validate all inputs** — Use Zod or similar for request validation

4. **Handle errors gracefully** — Try/catch with proper error responses

5. **Choose the runtime by dependencies and placement** — Compare measured latency and data-source distance

6. **Implement rate limiting** — Prevent abuse

7. **Add CORS headers** — For cross-origin requests

8. **Use streaming** — For long-running operations

9. **Cache responses** — Use Cache-Control headers
10. **Document your API** — Clear endpoint documentation

## Performance Considerations

Measure end-to-end latency, database query count, connection limits and errors on the target host. A small handler near users can still be slow if its database is far away. Streaming reduces how long clients wait for ready chunks, while persistent cache reuse can avoid work only when the response's privacy and freshness policy permits it. An extra CDN cache around a cached route can extend visible staleness; test invalidation at each layer rather than assuming one TTL controls everything.

# Data Fetching Patterns in Next.js (App Router)

A product page needs a description, a visitor-specific saved state, and reviews that may be slow. The design question is which reads depend on one another, which may be shared, and which should not delay useful content.

```tsx
// Independent reads start together; dependent ones wait.
const productPromise = getProduct(id);
const promotionPromise = getPromotion();
const [product, promotion] = await Promise.all([productPromise, promotionPromise]);

return (
  <main>
    <h1>{product.name}</h1>
    <Suspense fallback={<ReviewsSkeleton />}>
      <Reviews productId={product.id} /> {/* needs the ID: genuinely sequential */}
    </Suspense>
  </main>
);
```

## Definition

Data-fetching design decides where a read runs, which other values it depends on, and whether its result may be reused. In the App Router, Server Components can read data before sending the page, while Client Components can own reads driven by browser state.

> **Textbook Definition:** A data-fetching strategy assigns reads to server or client execution and defines their dependency order, reuse scope, and freshness. Parallel scheduling reduces latency for independent reads; cache identity and invalidation determine whether reuse remains correct.

## First Principles

A product page mixes owners: the public description belongs in the first server response, saved state depends on the visitor, and slow reviews must not hold up the title and price. Three questions decide the design. **What inputs must exist first?** Reviews keyed by product ID wait for that ID; an unrelated catalog read can start alongside the product read. **Who owns the changing input?** Route-known data reads on the server; search text, focus, polling, and live updates belong to browser code. **Who may reuse the result, and for how long?** Request-local deduplication is not cross-visitor caching — a persistent cache needs a correct identity plus a freshness policy, and neither replaces authorization.

## 1. Start Independent Work Together

The Server Component is usually the simplest owner of data needed for the initial page. It can query an ORM directly; credentials and query code stay on the server. The database query still needs authentication and resource authorization whenever its result is private.

If the page needs the product and a public promotion, start both reads before awaiting either. A later request for reviews can wait for the product ID because that dependency is real:

```typescript
export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;

  const productPromise = getProduct(id);
  const promotionPromise = getPromotion();
  const [product, promotion] = await Promise.all([
    productPromise,
    promotionPromise,
  ]);

  return (
    <main>
      <h1>{product.name}</h1>
      <p>{promotion.label}</p>
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews productId={product.id} />
      </Suspense>
    </main>
  );
}
```

`Promise.all` shortens the wait only when operations are independent. It does not make a reviews query parallel with the product lookup if the query needs the product ID. The Suspense boundary lets the surrounding page reveal while reviews are still pending; it does not schedule the query. See [Streaming](10.4.3.04-streaming.md) for boundary placement and delivery behavior.

## 2. Choose an Explicit Reuse Policy

In Next.js 15 and Next.js 16 without Cache Components, identical `fetch` requests in a React server render are memoized for that render. This is request-local deduplication. Persistent Data Cache reuse is a separate choice: use `force-cache` or a positive `revalidate` when the response is safe to share and has a defined freshness window. A tag labels cached data for later invalidation; it does not turn caching on by itself. Route Handlers do not participate in React-tree fetch memoization.

```typescript
async function getProduct(id: string) {
  const response = await fetch(
    `https://catalog.example.com/products/${encodeURIComponent(id)}`,
    { next: { revalidate: 300, tags: [`product:${id}`] } },
  );
  if (!response.ok) throw new Error('Product service unavailable');
  return parseProduct(await response.json());
}
```

`parseProduct` represents an application runtime decoder. A TypeScript assertion on `response.json()` only changes the compiler's view; it does not check the service response. For a database or another non-`fetch` source, read directly in the Server Component. Add `unstable_cache` only when the traditional model needs deliberate cross-request reuse. With Next.js 16 Cache Components enabled, put reusable functions or components behind `use cache` and define their lifetime. The [Caching chapter](10.4.3.03-caching.md) compares both models and their invalidation boundaries.

Never place a user-specific result in a shared cache unless the key and authorization model isolate that user or tenant. Tags group entries for invalidation; they do not partition users or grant access. For private reads, authorize on the server and leave them uncached unless a verified identity-aware cache design is required.

## 3. Pass Server Work Across the Client Boundary Only When Useful

If a Client Component needs a server-started read — for example, to render it beneath a client-controlled Suspense boundary — the server can pass the promise without awaiting it. React's `use()` reads that promise in the Client Component:

```tsx
// Server Component
import { Suspense } from 'react';
import { InteractiveProducts } from '@/app/ui/interactive-products';

export default function Page() {
  const products = getProducts();
  return (
    <Suspense fallback={<p>Loading products…</p>}>
      <InteractiveProducts products={products} />
    </Suspense>
  );
}
```

The promise crosses to a separate Client Component module:

```tsx
// app/ui/interactive-products.tsx
'use client';
import { use } from 'react';

export function InteractiveProducts({
  products,
}: {
  products: Promise<{ id: string; name: string }[]>;
}) {
  const initialProducts = use(products);
  return <ProductPicker products={initialProducts} />;
}
```

The promise's resolved value must be serializable across the Server/Client boundary. If the browser needs to refetch as inputs change, manage that lifecycle in a client data library instead of starting a new server action for every read.

## 4. Let the Browser Own Live and Input-Driven Reads

Search-as-you-type, polling, infinite scrolling, and optimistic editing often need a browser query cache. React Query and SWR provide loading/error state, deduplication, and freshness rules for those client-owned reads. Pass an `AbortSignal` through to `fetch` so an obsolete query can be cancelled:

```tsx
'use client';

import { useQuery } from '@tanstack/react-query';

function SearchResults({ query }: { query: string }) {
  const result = useQuery({
    queryKey: ['search', query],
    enabled: query.trim().length >= 3,
    queryFn: async ({ signal }) => {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(query)}`,
        { signal },
      );
      if (!response.ok) throw new Error('Search failed');
      return parseSearchResults(await response.json());
    },
  });

  if (query.trim().length < 3) return <p>Enter at least three characters.</p>;
  if (result.isPending) return <p>Searching…</p>;
  if (result.isError) return <p role="alert">Search is unavailable.</p>;
  return <Results items={result.data} />;
}
```

The query key includes every value that changes the result. `useDeferredValue` can keep rendering responsive while a new query is prepared, but it is not a time-based debounce and does not promise fewer requests. Debounce when you need to cap request frequency; cancellation prevents stale work from winning. A same-origin Route Handler can keep upstream credentials on the server, but it must still validate input and authorize access.

## 5. Keep Reads and Writes on the Right Path

Do not use a Server Action as a general read API. Read during Server Component rendering when the route needs the data; use a client query library when browser state owns it. A Server Action is the mutation path: validate runtime input, authenticate, authorize the specific resource, commit the write, then refresh the affected cache or path. A Route Handler is the better fit for a stable HTTP API, webhook, or custom response contract. The [Server Actions chapter](10.4.3.02-server-actions.md) follows that write through its trust and consistency boundaries.

Applied end to end:

- Fetch the public description on the server with a freshness window matching how fast catalog edits must appear.
- At checkout, re-read authoritative price and stock because a page cache is not inventory authority.
- Read saved state under the authenticated identity and never share it in a public cache.
- Stream slow reviews behind an independent fallback.
- Let the browser own the live search query with cancellation.

When a mutation changes a cached value, invalidate the smallest affected path or tag after the authoritative write succeeds — never before it, and never assume a tag alone refreshes open browser tabs.

## Summary

Choose the read location from its inputs and who owns their changes. Start independent server reads together, preserve true dependencies, and stream slow regions when the shell is useful on its own. Define cache identity and freshness separately from authorization. Keep live browser queries in a client data layer and mutations in a validated, authorized write path.

# Data Fetching Patterns in Next.js (App Router)

## Definition

Data fetching in the App Router is the choice of where a read runs, when it starts, and how its result is reused or refreshed. Server Components can read data before sending UI; Client Components own browser-driven reads; mutations use a separate write path.

> **Textbook Definition:** Data-fetching design assigns reads to server or client execution and specifies their dependencies, reuse and freshness. Parallel scheduling shortens independent waits; cache identity and invalidation determine whether reused results remain correct.


## First Principles

An account read needs a session; a catalog read may be independent of it. Start by drawing that dependency graph rather than choosing a Hook.

1. **A read cannot start before its inputs exist.** `getPosts(user.id)` waits for the user. Independent user and catalog reads can start together; placing them in server code does not automatically remove every waterfall.
2. **A result needs an owner for waiting and failure.** Initial server-known content can be read before hydration. Browser input and live updates need client subscriptions or requests; their loading, cancellation and stale-result policy belong to that owner.
3. **Repeated reads require an identity and age policy.** Request-local deduplication avoids duplicate work now; persistent reuse accepts older results later. Neither chooses which visitor may access the data.

## Why It Matters

The execution choice affects latency, data exposure, cache scope, and the number of requests a user waits for. Keep server-only credentials and authorization checks on the server, and let the browser own reads that respond to browser input or need ongoing refresh.

## How It Works

**Version scope:** These fetch and `unstable_cache` examples use the traditional model in Next.js 15 and Next.js 16 with Cache Components disabled. Identical `fetch` calls in the React server tree are request-memoized. A fetch is not automatically put in the persistent Data Cache, though a route may still bake build-time results into static route output. A positive `revalidate` or `force-cache` explicitly opts into persistent data reuse; a tag labels cached data for invalidation. `unstable_cache` persists supported non-fetch results across requests, while React `cache` deduplicates within a render. Next.js 16 Cache Components uses `use cache` instead; see [Caching](10.4.3.03-caching.md#choose-the-model-before-following-the-example).

The client examples assume React Query's `QueryClientProvider` and an SWR fetcher are supplied. `useDeferredValue` changes render priority; it is not a debounce or a guaranteed reduction in network requests. Abort stale requests or debounce when you need to bound traffic.

`parseProduct`, `parseProducts` and `parseSearchResults` below stand for application runtime decoders. A TypeScript annotation on `response.json()` does not validate an upstream response.

### Pattern 1: Server Component `fetch` (Default)

```typescript
// app/products/page.tsx — Server Component
export default async function ProductsPage() {
  // Identical calls in the React server tree are deduplicated for this render.
  // Positive revalidate opts into persistent reuse in the traditional model.
  const res = await fetch('https://api.example.com/products', {
    next: { revalidate: 3600 }, // Revalidate stale data on a later request.
  });
  if (!res.ok) throw new Error('Product read failed');
  const products = parseProducts(await res.json());
  return <ProductList products={products} />;
}
```

**Key behaviors:**
- Identical GET fetches in the React server tree are deduplicated per render pass; Route Handlers are outside that tree
- The Data Cache persists the response across requests, keyed by URL + options
- `next: { revalidate: N }` enables time-based data revalidation; it is not a timer
- `cache: 'no-store'` opts out of Next's persistent Data Cache; upstream freshness is separate
- `next: { tags: ['products'] }` labels cached entries; add `cache: 'force-cache'` or positive `revalidate` to opt in

### Pattern 2: Database / ORM in Server Components

```typescript
// app/dashboard/page.tsx
import { db } from '@/lib/db';
import { unstable_cache } from 'next/cache';

const getStats = unstable_cache(
  async () => {
    return { products: await db.product.count({ where: { published: true } }) };
  },
  ['dashboard-stats'],
  { revalidate: 60, tags: ['stats'] }
);

export default async function DashboardPage() {
  const stats = await getStats();
  return <StatsCards stats={stats} />;
}
```

For non-`fetch` data sources, `unstable_cache` can provide persistent reuse under this model. This example is a public published-product count; private account or tenant aggregates require authorized, correctly scoped keys. The imported database and `StatsCards` are application adapters.

### Pattern 3: Server Actions for Mutations

> The [Server Actions chapter](10.4.3.02-server-actions.md#basic-server-action) owns the validated form mutation. Perform the write after authentication/authorization, invalidate the affected route or shared tag, then redirect; a mutation does not invalidate a cache automatically.

### Pattern 4: Client-Side Fetching with React Query

```typescript
// For data that's highly interactive: search, live updates, optimistic UI
'use client';

import { useQuery } from '@tanstack/react-query';

function SearchResults({ query }: { query: string }) {
  const { data, isLoading, error } = useQuery({
    queryKey: ['search', query],
    queryFn: async ({ signal }) => {
      const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal });
      if (!response.ok) throw new Error('Search failed');
      return parseSearchResults(await response.json()); // Runtime decoder for an untrusted API response.
    },
    enabled: query.length > 2,
    staleTime: 30_000,
  });

  if (query.length <= 2) return <p>Enter at least three characters.</p>;
  if (isLoading) return <Spinner />;
  if (error) return <p role="alert">Search failed</p>;
  return <Results data={data ?? []} />;
}
```

Use this for: search-as-you-type, infinite scroll, polling, optimistic updates on data the user is actively interacting with.

### Pattern 5: `useSWR` (Alternative Client Pattern)

```typescript
'use client';
import useSWR from 'swr';

function UserProfile({ id }: { id: string }) {
  const { data, error, isLoading, mutate } = useSWR(`/api/users/${encodeURIComponent(id)}`, fetcher, {
    revalidateOnFocus: true,
    refreshInterval: 0,
  });
  // ...
}
```

SWR is similar to React Query but with a smaller API surface. Choose based on team preference.

### Pattern 6: Parallel Data Fetching (Avoid Waterfalls)

```typescript
// Independent reads can start together.
const [user, catalog] = await Promise.all([getUser(), getCatalog()]);

// A dependent read still waits for its input.
const posts = await getPosts(user.id);
const comments = posts.length ? await getComments(posts[0].id) : [];
```

Parallelization must preserve meaning: comments for a user's first post cannot be replaced with a query for all of that user's comments just to make the calls independent. Deduplication of non-fetch helpers requires a shared React `cache` wrapper; it is not automatic for arbitrary functions.

### Pattern 7: Streaming with Suspense

> [Streaming](10.4.3.04-streaming.md#multiple-suspense-boundaries) owns the independent dashboard sections example. Start independent reads without awaiting a common parent first; Suspense lets their results reveal separately but does not remove true data dependencies.

## Code Examples

### Real-World: E-commerce Product Page

```typescript
// app/products/[id]/page.tsx
import { notFound } from 'next/navigation';
import { Suspense } from 'react';

// Product data is cached; prerender known IDs with generateStaticParams
async function getProduct(id: string) {
  const res = await fetch(`https://api.example.com/products/${encodeURIComponent(id)}`, {
    next: { revalidate: 3600, tags: [`product-${id}`] },
  });
  if (res.status === 404) notFound();
  if (!res.ok) throw new Error('Product fetch failed');
  const data: unknown = await res.json();
  return parseProduct(data);
}

export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params; // params is a Promise in Next.js 15+
  const product = await getProduct(id);
  return (
    <div>
      <h1>{product.name}</h1>
      {/* Reviews are slower, stream them independently */}
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews productId={id} />
      </Suspense>
    </div>
  );
}
```

### Real-World: Search-as-you-Type with React Query

```typescript
'use client';
import { useQuery, keepPreviousData } from '@tanstack/react-query';
import { useDeferredValue, useState } from 'react';

function SearchBox() {
  const [query, setQuery] = useState('');
  const deferred = useDeferredValue(query);

  const { data, isFetching, error } = useQuery({
    queryKey: ['search', deferred],
    queryFn: async ({ signal }) => {
      const response = await fetch(`/api/search?q=${encodeURIComponent(deferred)}`, { signal });
      if (!response.ok) throw new Error('Search failed');
      return parseSearchResults(await response.json());
    },
    enabled: deferred.length > 2,
    placeholderData: keepPreviousData, // smooth transitions
  });

  return (
    <>
      <input aria-label="Search products" value={query} onChange={e => setQuery(e.target.value)} />
      {isFetching && <Spinner />}
    <div aria-busy={isFetching}>
      <Results items={data ?? []} />
    </div>
    </>
  );
}
```

### Form Mutation with Optimistic Feedback

The [Server Actions optimistic example](10.4.3.02-server-actions.md#server-action-with-optimistic-updates) owns that mechanism. The pending overlay is temporary UI, not a database record. When the action finishes, the authoritative base must reflect success or remain unchanged on failure, and the form must report an expected rejection. Otherwise a successful item can disappear when the optimistic overlay ends.

## Real-World Use Cases

1. **Marketing pages** — Server Component reads with a deliberate freshness policy
2. **User dashboards** — Server Component fetch + Suspense for slow sections
3. **Search** — Client Component with React Query + `useDeferredValue`
4. **Forms** — Server Actions with `revalidateTag`/`revalidatePath`
5. **Live data** (chat, stock prices) — Client Component with WebSocket + SWR
6. **Admin panels** — Mixed: Server Component for initial render, Client Component for interactions
7. **E-commerce catalog** — Reuse public descriptions within an agreed freshness window, recheck price and stock at checkout, and mutate the cart through an authorized write path

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `useEffect` + `fetch` in a Server Component | Use `async` + `await` directly in the Server Component |
| Assuming a tag enables caching | Select a cache policy first; use a tag only when invalidation by label is needed |
| Sequential `await`s in a Server Component | Use `Promise.all` to parallelize independent fetches |
| Fetching in Client Components when Server Components would work | Push the boundary down; fetch on the server to avoid waterfalls |
| Using `useEffect` to derive data from props | Compute it directly in render (or use a Server Component) |
| Forgetting stale reads after a mutation | Invalidate the affected path or data tag when the chosen cache model requires it |
| Using Server Actions for reads | Use Server Components for reads, Server Actions for writes |
| Missing tags on shared cached data | Use tags for cross-route invalidation; path invalidation still works |

## Best Practices

1. **Default to a Server Component read** when the result is needed to render the route and does not depend on browser interaction.
2. **Use a server-only data helper for database reads.** Add `unstable_cache` only for deliberate cross-request reuse in the traditional model; with Cache Components, use a supported `use cache` boundary.
3. **Choose the cache policy from the data's freshness and audience.** Leave data uncached when reuse is unsafe or unnecessary; add tags only for data that should be invalidated together.
4. **Parallelize independent fetches with `Promise.all`** — eliminate request waterfalls
5. **Use Suspense boundaries to stream slow sections** — each boundary is an independent streaming unit
6. **Use Server Actions for mutations, Route Handlers for full HTTP endpoints** — they have different semantics
7. **Use tags for shared invalidation groups** — they are labels, not cache opt-in or an authorization boundary
8. **Use React Query for client-side reactive data only** — search, infinite scroll, polling, optimistic UI
9. **Invalidate affected cached reads after mutations** — `revalidateTag`/`revalidatePath` in Server Actions
10. **Pass data through props, not via fetch** — if a Server Component has the data, pass it to a Client Component via props instead of refetching

## Performance Considerations

| Pattern | TTFB | Waterfall Risk | Cache | Use For |
| ------------------------------------- | ------------------------ | ----------------------------- | ----------------------------- | -------------------------------- |
| Server Component `fetch` + revalidate | Cache/network-dependent | Depends on await placement | Data Cache | Static-ish content, dashboards |
| Server Component `fetch` + no-store | Source/network-dependent | Depends on dependencies | None | Personalized/authenticated data |
| Server Component `unstable_cache` | Hit/store-dependent | Depends on dependencies | Argument identity plus labels | DB queries, internal APIs |
| Server Actions | — | — | N/A (mutations) | Forms, mutations |
| React Query (client) | N/A (client-side) | Higher (round trips) | In-memory | Search, infinite scroll, polling |
| SWR (client) | N/A (client-side) | Higher | In-memory | Same as React Query |
| Streaming + Suspense | Shell-dependent | Await placement still matters | Inherits | Slow-data pages with fast shell |

**Decision tree:**
- Read-only, mostly static? → Server Component + `revalidate`
- Read-only, personalized/authenticated? → Server Component + `cache: 'no-store'`
- Mutation? → Server Action + `revalidateTag`/`revalidatePath`
- Highly interactive (search, live updates)? → Client Component + React Query/SWR
- Slow data, fast shell needed? → Server Component + Suspense streaming

## Summary

Choose the read location from its inputs and interaction needs, then decide whether reuse is safe and how fresh it must be. Start independent reads together, keep dependent reads ordered, and stream slow sections when the shell can be useful first. Mutations belong to a separately validated write path; refresh only the cached data that the write actually changed.

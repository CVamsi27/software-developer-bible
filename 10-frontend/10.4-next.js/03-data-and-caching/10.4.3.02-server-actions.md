# Server Actions in Next.js

## Definition

**Server Actions** are Server Functions invoked in a mutation context, commonly by a form or Client Component. A module-level `'use server'` directive makes exported functions callable across the client/server boundary; Next.js provides the transport, while the application owns validation, authorization and write semantics.

> **Textbook Definition:** A Server Action is a framework-invoked server function used to perform a mutation and return its outcome to the interface. Its transport does not remove the need for request validation, authorization or consistency controls.


## First Principles

An action call is a network request even when it looks like a local function call:

1. **A client-callable action is an externally reachable mutation boundary.** The framework creates the POST transport and serializes supported arguments/results. Its implementation stays on the server, but callers can still invoke its public interface. Check identity and resource authorization inside the action; see [Authentication](../04-production/10.4.4.01-authentication.md).
2. **Supported forms can submit before JavaScript connects React to the page.** This is **progressive enhancement**: the form submission works first, then APIs such as `useActionState` and optimistic updates add client behavior. The exact guarantee depends on the framework and how the form is wired.
3. **A write and its read models can become inconsistent.** After the authoritative write succeeds, update or invalidate only the relevant cache according to its freshness contract (→ [Caching](10.4.3.03-caching.md#invalidate-after-the-authoritative-write)).

## Why It Matters

Use Server Actions for mutations coupled to a Next.js interface. Use a Route Handler for a stable HTTP contract needed by external clients, webhooks, custom methods/statuses, or response streaming. Neither transport replaces application validation and authorization.

## How It Works

**Version scope:** The examples target Next.js 16.4 with React 19.3. Use `useActionState` from `react`; the former `useFormState` API is deprecated. A form action rendered by a Server Component can submit before hydration. This guarantee does not apply to arbitrary client event handlers.

The client currently dispatches and awaits Server Functions one at a time; Next.js documents this as an implementation detail. Do not use separate actions as a parallel query API. Fetch in Server Components or perform independent server work together within one action/Route Handler.

Actions are public mutation endpoints: check the session and resource ownership in each action, and validate runtime inputs. `FormData` may contain `null`, repeated values or a `File`; a TypeScript cast validates none of them. Next.js checks the action request's origin against its host; requests without an `Origin` header are allowed with a warning. Configure `allowedOrigins` only for known proxy/origin arrangements; this CSRF check does not authenticate the caller or replace authorization.

`redirect()` throws control-flow machinery; call it outside a catch that would turn that redirect into an error state. `useFormStatus` reads its nearest parent form, so the submit button must be a descendant, not the component creating the form. The upload example permits a 5 MiB file, which requires raising the default 1 MiB raw request-body limit to a bounded value in `experimental.serverActions.bodySizeLimit`. Multipart boundaries add overhead, so a 5 MiB file needs a slightly larger request limit; direct-to-storage upload is preferable for larger files.

### Trace a submission through the write boundary

```text
Form title/content → framework POST → createPost
                  → validate session and fields → commit database write
                  → invalidate affected reads → redirect or return outcome
```

If validation fails, no record should be written. If the write succeeds but later invalidation fails, the database is already changed: a retry must not blindly repeat a payment or append operation. Use unique operation IDs/transactional constraints when repeated submissions matter. A disabled button reduces accidental clicks but cannot enforce server uniqueness across tabs or retries.

Choose an action for a mutation coupled to this React interface. Choose a Route Handler when external clients need stable HTTP methods/statuses, signature-verified webhooks or a custom response stream. Neither transport validates or authorizes an operation automatically.

## Code Examples

### Basic Server Action

```typescript
// app/actions/post.ts
'use server'

import { revalidatePath } from 'next/cache'
import { redirect } from 'next/navigation'
import { db } from '@/lib/database'
import { auth } from '@/auth'
import { z } from 'zod'

export async function createPost(formData: FormData) {
  const session = await auth()
  if (!session?.user?.id) throw new Error('Unauthorized')
  const { title, content } = z.object({
    title: z.string().trim().min(1).max(200), content: z.string().trim().min(1).max(20000),
  }).parse({ title: formData.get('title'), content: formData.get('content') })

  await db.post.create({
    data: { title, content, authorId: session.user.id },
  })

  revalidatePath('/posts')
  redirect('/posts')
}

```

### Server Action with Validation

```typescript
// app/actions/user.ts
'use server'

import { z } from 'zod'
import { revalidatePath } from 'next/cache'
import { db } from '@/lib/database'
import { requireUserAdmin } from '@/lib/authorization'

const userSchema = z.object({
  name: z.string().min(2).max(50),
  email: z.email(),
  age: z.number().int().min(18).max(120),
})

interface ActionState {
  errors?: Record<string, string[]>
  success?: boolean
}

export async function createUser(
  prevState: ActionState,
  formData: FormData
): Promise<ActionState> {
  await requireUserAdmin() // Application adapter validates session and administrative permission.
  const rawData = {
    name: formData.get('name'),
    email: formData.get('email'),
    age: Number(formData.get('age')),
  }

  const validated = userSchema.safeParse(rawData)

  if (!validated.success) {
    return {
      errors: z.flattenError(validated.error).fieldErrors,
    }
  }

  await db.user.create({
    data: validated.data,
  })

  revalidatePath('/users')
  return { success: true }
}

```

### Return expected validation state with `useActionState`

```typescript
// app/users/new/page.tsx
'use client'

import { useActionState } from 'react'
import { createUser } from '@/app/actions/user'

export default function NewUserPage() {
  const [state, formAction, pending] = useActionState(createUser, {})

  return (
    <div>
      <h1>Create User</h1>
      <form action={formAction}>
        <div>
          <label htmlFor="name">Name</label>
          <input type="text" id="name" name="name" required />
          {state.errors?.name && (
            <p className="error">{state.errors.name[0]}</p>
          )}
        </div>
        <div>
          <label htmlFor="email">Email</label>
          <input type="email" id="email" name="email" required />
          {state.errors?.email && (
            <p className="error">{state.errors.email[0]}</p>
          )}
        </div>
        <div>
          <label htmlFor="age">Age</label>
          <input type="number" id="age" name="age" required />
          {state.errors?.age && (
            <p className="error">{state.errors.age[0]}</p>
          )}
        </div>
        <button type="submit" disabled={pending}>{pending ? 'Creating…' : 'Create'}</button>
        {state.success && <p className="success">User created!</p>}
      </form>
    </div>
  )
}

```

### Server Action with useFormStatus

```typescript
// app/actions/subscribe.ts
'use server'

import { z } from 'zod'
import { db } from '@/lib/database'

export async function subscribe(formData: FormData) {
  const email = z.email().parse(formData.get('email'))
  await db.subscriber.upsert({
    where: { email }, create: { email }, update: {},
  })

  // A direct form action returns void; useActionState is needed for returned state.
}

```

```typescript
// components/subscribe-form.tsx
'use client'

import { useFormStatus } from 'react-dom'
import { subscribe } from '@/app/actions/subscribe'

function SubmitButton() {
  const { pending } = useFormStatus()

  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Subscribing...' : 'Subscribe'}
    </button>
  )
}

export function SubscribeForm() {
  return (
    <form action={subscribe}>
      <input
        aria-label="Newsletter email"
        type="email"
        name="email"
        placeholder="Enter your email"
        required
      />
      <SubmitButton />
    </form>
  )
}

```

The subscriber example assumes a unique email constraint. It shows form ancestry and pending status; production signup also needs abuse limits, consent/confirmation policy and recoverable validation feedback through `useActionState`. An email-shaped string does not establish control of that mailbox.

### Server Action with useTransition

```typescript
// app/actions/like.ts
'use server'

import { z } from 'zod'
import { auth } from '@/auth'
import { db } from '@/lib/database'
import { requirePostAccess } from '@/lib/authorization'
import { revalidatePath } from 'next/cache'

export async function setLike(postId: string, liked: boolean) {
  const session = await auth() // Configured application adapter
  if (!session?.user?.id) throw new Error('Unauthorized')
  const id = z.string().min(1).max(100).parse(postId)
  const desired = z.boolean().parse(liked)
  await requirePostAccess(session.user.id, id)
  // Schema has a unique (userId, postId) constraint; retries express desired state.
  if (desired) {
    await db.like.upsert({
      where: { userId_postId: { userId: session.user.id, postId: id } },
      create: { userId: session.user.id, postId: id }, update: {},
    })
  } else {
    await db.like.deleteMany({ where: { userId: session.user.id, postId: id } })
  }
  revalidatePath('/posts')
}

```

```typescript
// components/like-button.tsx
'use client'

import { useTransition, useState } from 'react'
import { setLike } from '@/app/actions/like'

export function LikeButton({ postId, initialLiked }: {
  postId: string
  initialLiked: boolean
}) {
  const [isPending, startTransition] = useTransition()
  const [error, setError] = useState<string | null>(null)

  return (
    <div>
    <button
      type="button"
      aria-pressed={initialLiked}
      onClick={() => startTransition(async () => {
        setError(null)
        try { await setLike(postId, !initialLiked) }
        catch { setError('Could not update the like. Please try again.') }
      })}
      disabled={isPending}
      className={initialLiked ? 'liked' : ''}
    >
      {initialLiked ? 'Unlike' : 'Like'}
    </button>
    {error && <p role="alert">{error}</p>}
    </div>
  )
}

```

A read-then-toggle sequence is vulnerable to concurrent requests and retry ambiguity. This action writes the desired state and relies on a database uniqueness constraint. Competing opposite requests still need a version/order policy if last completed write is insufficient. The parent must read the same authorized base after revalidation so `initialLiked` updates.

### Server Action with Optimistic Updates

```typescript
// components/todo-list.tsx
'use client'

import { useOptimistic, useState } from 'react'
import { addTodo } from '@/app/actions/todo'

interface Todo {
  id: string
  text: string
  completed: boolean
  pending?: boolean
}

export function TodoList({ initialTodos }: { initialTodos: Todo[] }) {
  const [optimisticTodos, addOptimisticTodo] = useOptimistic(
    initialTodos,
    (state, newTodo: Todo) => [...state, newTodo]
  )

  const [error, setError] = useState<string | null>(null)
  async function handleSubmit(formData: FormData) {
    const text = formData.get('text')
    if (typeof text !== 'string' || !text.trim()) return
    setError(null)
    addOptimisticTodo({ id: 'temp-' + crypto.randomUUID(), text, completed: false, pending: true })
    try { await addTodo(formData) }
    catch { setError('Could not save the todo. Please try again.') }
  }

  return (
    <div>
      <form action={handleSubmit}>
        <input name="text" aria-label="New todo" required />
        <button type="submit">Add</button>
      </form>
      <ul>
        {optimisticTodos.map(todo => (
          <li key={todo.id} className={todo.completed ? 'done' : ''}>
            {todo.text}{todo.pending && ' (Saving…)'}
          </li>
        ))}
      </ul>
      {error && <p role="alert">{error}</p>}
    </div>
  )
}

```

The imported `addTodo` must authorize the caller, validate text, commit the record and revalidate `/todos`, whose server page rereads that user's list into `initialTodos`. Successful refreshed props become the base before the temporary overlay ends; failure leaves the old base and reports an error. If another mutation changes the base while pending, React reapplies the pure optimistic reducer to that base. Generate temporary IDs outside the reducer; do not perform time/random reads during reapplication.

### Server Action with Cookies

```typescript
// app/actions/preferences.ts
'use server'

import { cookies } from 'next/headers'

export async function updatePreferences(formData: FormData) {
  const theme = formData.get('theme')
  const language = formData.get('language')
  if ((theme !== 'light' && theme !== 'dark') ||
      (language !== 'en' && language !== 'es' && language !== 'fr')) {
    throw new Error('Invalid preference')
  }

  const cookieStore = await cookies()

  cookieStore.set('preferences', JSON.stringify({ theme, language }), {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/',
    maxAge: 60 * 60 * 24 * 365, // 1 year
  })

  // Setting a cookie in a Server Action refreshes the current UI tree.
}

```

### Server Action with Error Handling

```typescript
// app/actions/upload.ts
'use server'

import { revalidatePath } from 'next/cache'

interface UploadState {
  error?: string
  success?: boolean
  fileUrl?: string
}

export async function uploadFile(
  prevState: UploadState,
  formData: FormData
): Promise<UploadState> {
  await requireUploadPermission() // Configured session/resource/quota adapter
  const file = formData.get('file')

  if (!(file instanceof File)) {
    return { error: 'No file provided' }
  }

  if (file.size > 5 * 1024 * 1024) {
    return { error: 'File size must not exceed 5 MiB' }
  }

  const allowedTypes = ['image/jpeg', 'image/png', 'image/webp']
  if (!allowedTypes.includes(file.type)) {
    return { error: 'File type not allowed' }
  }

  try {
    const buffer = Buffer.from(await file.arrayBuffer())
    const filename = `uploads/${crypto.randomUUID()}`

    // Upload to storage (e.g., S3, Cloudflare R2)
    const url = await uploadToStorage(buffer, filename)

    revalidatePath('/gallery')
    return { success: true, fileUrl: url }
  } catch (error) {
    return { error: 'Upload failed. Please try again.' }
  }
}

```

The upload adapter must inspect/re-encode bytes, enforce object visibility and handle orphan cleanup if later database work fails. A caller-controlled MIME string is only a hint. The 5 MiB check bounds this example after body parsing; configure upstream limits and use direct-to-storage flows for large files. Node `Buffer` requires a Node-compatible action runtime.

### Inline Server Action

```typescript
// app/posts/page.tsx
import { revalidatePath } from 'next/cache'

export default function PostsPage() {
  async function deletePost(formData: FormData) {
    'use server'

    const postId = formData.get('postId')
    if (typeof postId !== 'string' || !postId || postId.length > 100) throw new Error('Invalid post ID')

    const session = await auth() // Import your session helper; never trust the hidden field
    if (!session?.user?.id) throw new Error('Unauthorized')
    await db.post.delete({
      where: { id: postId, authorId: session.user.id },
    })

    revalidatePath('/posts')
  }

  return (
    <div>
      <h1>Posts</h1>
      {/* Server action defined inline */}
      <form action={deletePost}>
        <input type="hidden" name="postId" value="123" />
        <button type="submit">Delete</button>
      </form>
    </div>
  )
}

```

### Upload Visibility Is an Application Policy

The [bounded upload action](#server-action-with-error-handling) owns file validation and recovery. A public blob URL is unsuitable for private documents; choose private storage and an authorized download path when needed. Storage and database writes do not form one automatic transaction: use durable state/cleanup policy so a failure cannot leave an untracked object or a record pointing at a missing one.

### Use a GET form when search is a read

```typescript
// app/products/search-form.tsx — GET keeps the query shareable and in history.
export function ProductSearchForm() {
  return (
    <form action="/products" method="get">
      <label htmlFor="product-query">Search products</label>
      <input id="product-query" name="q" maxLength={200} />
      <button type="submit">Search</button>
    </form>
  )
}

```

The destination must still validate query parameters, and private search results still require authorization. Use a Server Action only when a search submission performs a mutation or needs a specific POST contract.

## Real-World Use Cases

| Use Case | Server Action Benefit |
| ----------------- | -------------------------------------------------------------------------------------- |
| Form submission | Progressive enhancement, no API needed |
| CRUD operations | Typed callers, explicit revalidation |
| File uploads | Server-side processing, security |
| Search/filtering | URL updates, server-side logic |
| Authentication | A mutation surface for sign-in/out flows; still validate credentials and session state |
| Newsletter signup | Simple data mutation |
| Contact forms | Generated POST interface without a manual route |
| Shopping cart | Type-safe operations |

## Common Mistakes

### 1. Not Using 'use server' Directive

```typescript
// BAD: Missing directive
export async function createPost(formData: FormData) {
  await db.post.create({ data: { title: formData.get('title') } })
  // This won't work as a Server Action!
}

// GOOD: Add directive
'use server'

export async function createPost(formData: FormData) {
  await db.post.create({ data: { title: formData.get('title') } })
}

```

### 2. Returning Non-Serializable Data

```typescript
// BAD: Returning non-serializable data
'use server'

export async function getData() {
  return {
    date: new Date(), // Native Date is supported by React serialization
    fn: () => {}, // Ordinary callbacks are not supported
  }
}

// GOOD: Return serializable data
'use server'

export async function getData() {
  return {
    date: new Date().toISOString(), // String
    value: 42, // Primitive
  }
}

```

### 3. Catching Errors Without Protecting the Write

Returning a friendly error does not make an unvalidated `updateUser(id, name)` safe. Validate supported field values, derive identity from the session and enforce resource ownership before writing. Use `useActionState` for expected validation/denial outcomes and retain enough input for recovery; log unexpected failures server-side without disclosing secrets.

### 4. Forgetting Which Cache the Write Changed

The [basic action](#basic-server-action) invalidates `/posts` only after its write succeeds. When several routes reuse tagged data, choose the appropriate tag policy too: in Next.js 16, `revalidateTag(tag, 'max')` permits stale-while-revalidate, while Server Action `updateTag(tag)` supports immediate read-your-writes. These are different freshness contracts; see [Caching](10.4.3.03-caching.md#invalidate-after-the-authoritative-write). Do not report an already committed write as rolled back merely because refresh failed.

### 5. Calling Server Action from Server Component

A Server Component may call a Server Function directly, but reads should generally use a server-only data helper rather than exposing a new client-callable action. Never perform a mutation during rendering: prerendering, retries, or navigation may render more than once. Keep the mutation in a form/action invocation.

## Best Practices

1. **Use 'use server' directive** — Always at the top of the file or function

2. **Return React-serializable data** — Built-ins such as Date/Map are supported; ordinary callbacks/class instances are not

3. **Handle errors gracefully** — Return error states to client

4. **Use revalidation** — Call `revalidatePath` or `revalidateTag` after mutations

5. **Validate inputs at runtime** — `FormData` is untrusted even when callers are typed

6. **Keep actions focused** — One action per operation

7. **Use `useActionState` for expected form outcomes** — Return validation state without exposing internal exceptions

8. **Use useFormStatus for loading** — Show pending state during submission

9. **Test authorization and retry behavior** — Include cross-user access, duplicate requests and cache refresh after a committed write
10. **Document action contracts** — Define clear input/output types

## Performance Considerations

The action implementation stays on the server, but interactive callers, pending UI and optimistic logic still need client code. Measure submission latency, database contention, duplicate-request handling and refresh behavior. TypeScript helps authored callers; runtime validation remains necessary. Keep writes focused and cache invalidation scoped to the changed data. Progressive enhancement depends on the actual form wiring, not merely the directive.

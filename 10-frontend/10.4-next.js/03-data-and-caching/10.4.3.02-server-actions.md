# Server Actions in Next.js

A create-post form can submit to an async server function and return validation state to the same UI. The call still crosses the network, so its inputs and caller must be treated as untrusted.

```tsx
// app/actions/posts.ts
'use server';

export async function createPost(_previous: CreatePostState, formData: FormData) {
  const session = await requireSession(); // identity from the server, never a hidden field
  const parsed = postInput.safeParse({ title: formData.get('title'), content: formData.get('content') });
  if (!parsed.success) return { errors: parsed.error.flatten().fieldErrors };
  await db.post.create({ data: { ...parsed.data, authorId: session.user.id } });
  revalidatePath('/posts');
  return { saved: true };
}
```

## Definition

A **Server Action** is a React Server Function used to perform a mutation. Next.js exposes it through a network request so a form or Client Component can ask the server to change data and return an outcome.

> **Textbook Definition:** A Server Action is an asynchronous server-side function invoked through a framework-managed request in a mutation context. Its transport integrates with React forms and rendering, while the application remains responsible for input validation, authorization, write consistency, and cache refresh.

## First Principles

Submitting “Create post” changes an authoritative record. The browser can be stale, modified, retried, or used by a different account. Therefore the action must rebuild the decision from trusted server-side state:

```text
untrusted form values → validate → authenticate → authorize this operation
                       → commit the write → refresh affected reads → return or redirect
```

Validation checks whether values have the right shape. Authentication identifies the caller. Authorization checks whether that caller may perform this operation on this resource. A typed client call proves none of these.

## How It Works

### 1. Validate and Authorize at the Action Boundary

Use `'use server'` on an async function or at the top of a dedicated action module. A Server Component form can pass the action directly; a Client Component can import the module-level action and use React form hooks around it.

```typescript
// app/actions/posts.ts
'use server';

import { revalidatePath } from 'next/cache';
import { z } from 'zod';
import { db } from '@/lib/database';
import { requireSession } from '@/lib/auth';

const postInput = z.object({
  title: z.string().trim().min(1).max(200),
  content: z.string().trim().min(1).max(20_000),
});

type CreatePostState = { errors?: Record<string, string[]>; saved?: boolean };

export async function createPost(
  _previous: CreatePostState,
  formData: FormData,
): Promise<CreatePostState> {
  const session = await requireSession();
  const parsed = postInput.safeParse({
    title: formData.get('title'),
    content: formData.get('content'),
  });

  if (!parsed.success) {
    return { errors: z.flattenError(parsed.error).fieldErrors };
  }

  // Identity comes from the verified session, never a hidden form field.
  await db.post.create({ data: { ...parsed.data, authorId: session.user.id } });
  revalidatePath('/posts');
  return { saved: true };
}
```

`FormData` is runtime input: a field may be missing, repeated, or a `File`. Use `getAll()` for repeated fields and check the returned type before using a file or string. The example derives the author from the verified session, so changing a submitted `authorId` cannot impersonate another user. For updates or deletes, perform a resource-level authorization check as part of the write, ideally in the same database operation or transaction.

### 2. Show Validation and Pending State in the Same Form

`useActionState` passes the previous state to the action and returns the latest state, a form action, and a pending flag. `useFormStatus` reads the pending status of the nearest parent form, so its button component must be nested inside that form.

```tsx
'use client';

import { useActionState } from 'react';
import { useFormStatus } from 'react-dom';
import { createPost } from '@/app/actions/posts';

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Saving…' : 'Save post'}</button>;
}

export function CreatePostForm() {
  const [state, formAction, pending] = useActionState(createPost, {});

  return (
    <form action={formAction} aria-busy={pending}>
      <label htmlFor="title">Title</label>
      <input id="title" name="title" required maxLength={200} />
      {state.errors?.title && <p role="alert">{state.errors.title[0]}</p>}

      <label htmlFor="content">Content</label>
      <textarea id="content" name="content" required />
      {state.errors?.content && <p role="alert">{state.errors.content[0]}</p>}

      <SubmitButton />
      {state.saved && <p role="status">Post saved.</p>}
    </form>
  );
}
```

React forms can submit before hydration completes; a Client Component form queues an early submission for hydration. This progressive enhancement works because the action is attached to a form. A form with JavaScript validation that intercepts submission has a different no-JavaScript contract. Expected outcomes such as field errors belong in returned state; unexpected failures should reach the application's error handling and be logged server-side without exposing internals.

### 3. Commit First, Then Refresh the Affected View

The action above invalidates `/posts` only after the database write succeeds. A tag can be better when several routes share the changed data. In Next.js 16, `revalidateTag(tag, 'max')` allows stale-while-revalidate, while `updateTag(tag)` in a Server Action immediately expires data for a read-your-writes flow. `revalidatePath` targets route output; `router.refresh()` requests a new client render but does not itself invalidate persistent server data. Choose the API from the cache model and the freshness promise. The [Caching chapter](10.4.3.03-caching.md) explains those boundaries.

Do not catch a broad block that contains `redirect()`: redirect uses a thrown framework control-flow signal. Finish the write and invalidation, then call `redirect()` outside expected-error handling. If invalidation fails after a committed write, report that the view may be stale; do not tell the user the write rolled back. A repeated submission can reach the same action again, so important operations need idempotency keys or database uniqueness/transaction rules.

### 4. Choose an Action for Writes, Not Ordinary Search

A Server Action is a good fit when a mutation belongs to the Next.js interface and benefits from an updated React response. A read-only search form should usually use `GET`: the query can be bookmarked, copied, and navigated with browser history.

```tsx
export function ProductSearchForm() {
  return (
    <form action="/products" method="get">
      <label htmlFor="q">Search products</label>
      <input id="q" name="q" maxLength={200} />
      <button type="submit">Search</button>
    </form>
  );
}
```

The page still validates query parameters and authorizes private results. Use a Route Handler when callers need a stable HTTP API, explicit status codes, custom methods, webhooks, or a streamed response. Server Actions are POST-based and currently dispatched one at a time by the Next.js client; that is an implementation detail, not a read-parallelization strategy. Fetch page data in Server Components or run independent server work inside one request.

### 5. Security and Operational Boundaries

Treat every exported action as a public endpoint: clients can send direct requests, and arguments are caller-controlled. Check authentication and authorization inside each action, validate every value at runtime, and avoid trusting hidden fields or client-provided role/owner IDs. Next.js compares the request `Origin` with the host as CSRF protection; add `serverActions.allowedOrigins` only for known reverse-proxy or multi-domain setups. That origin check does not identify the user or grant access to a record.

React's Server Function transport supports values beyond JSON, including `Date`, `Map`, and `Set`. Ordinary callbacks and arbitrary class instances are not serializable. Returning a `Date` is valid; convert it to an ISO string only when the receiving API or storage contract calls for a string.

Cookie changes made in an action can re-render the current route tree so session-dependent UI reflects the new cookie. Set appropriate `httpOnly`, `secure`, `sameSite`, `path`, and expiry options. A sign-out action should also clear or reset client state that is held outside the server-rendered tree.

Uploads need an explicit size and visibility policy. The default Server Action request-body limit is 1 MiB; `experimental.serverActions.bodySizeLimit` can raise it, but the limit covers the whole request, including multipart overhead. A file's declared MIME type is not proof of its contents. Inspect or re-encode bytes, enforce quotas and object access, and use direct-to-storage uploads for large files. Database and object-storage writes are not one transaction, so define cleanup and retry behavior.

### 6. Real-World Decisions

| Need | Preferred path | Why |
| ----------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------- |
| Create or update data from a Next.js form | Server Action | React form state and refreshed server UI can share a roundtrip |
| Search or filter without changing data | `GET` form or route query | URLs remain shareable and browser history works naturally |
| Public integration, webhook, custom status or HTTP contract | Route Handler | The caller gets explicit HTTP semantics and independent request verification |
| Large file transfer | Direct upload to controlled storage | Avoid buffering a large body through the action runtime |

For optimistic UI, display a provisional state only as an overlay on the authoritative server result. Reconcile it when the action completes, and remove or correct it on failure. The database remains the source of truth; client optimism does not make a write durable or idempotent.

## Summary

A Server Action gives a React interface a network-backed mutation path. Validate runtime inputs, authenticate and authorize each operation, commit safely under retries, then refresh the affected data. Use returned state for expected form outcomes, reserve redirects for successful control flow, and choose a Route Handler or `GET` request when the HTTP contract calls for it.

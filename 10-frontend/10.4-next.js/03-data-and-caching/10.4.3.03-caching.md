# Caching in Next.js

Few topics in modern web architecture create more confusion, debate, and subtle production bugs than caching in Next.js. Cache too aggressively, and users see another person's session data, updated product prices fail to appear, or stale data persists indefinitely. Cache too conservatively, and every page visit hammers your origin database with duplicate queries, multiplying cloud costs and degrading Time to First Byte (TTFB).

Next.js tackles performance through a multi-tiered caching architecture operating across four distinct boundaries:
1. **Request Memoization:** Deduplicating identical `fetch` calls within a single React render pass.
2. **Data Cache:** Persisting data fetch results across requests and serverless cold starts.
3. **Full Route Cache:** Storing pre-rendered HTML and RSC payloads at the server or edge CDN.
4. **Router Cache:** Storing RSC payload segments in browser memory during client-side navigation.

Mastering Next.js caching requires peeling back each layer, understanding how Next.js 15 reset `fetch` to uncached by default, how Next.js 16 introduces compiler-driven memoization via Cache Components (`'use cache'`), and how to surgically purge stale entries using cache tags and path revalidation.

## Definition

A **cache** reuses an earlier result instead of recomputing it. Next.js can reuse server data, rendered output and client navigation state, but each has a different lifetime and identity boundary.

> **Textbook Definition:** Caching reuses stored computation or data under an identity and freshness policy. Next.js has several caches with different lifetimes and invalidation boundaries; correct reuse depends on version, configuration and the data's authorization scope.

Suppose a page shows public product information beside the signed-in user's account. Reusing the product description can save work; reusing another user's account result can disclose data. Ask **what may repeat, for whom, and until when** before choosing an API.

## First Principles

Repeated work is avoidable only when the result remains valid for the next consumer. That requires a correct key, a freshness policy and an invalidation path. “Cached” alone answers none of them.

Deduplicating two reads during one render is also different from sharing data between visitors. Keep request-local and cross-request reuse separate, then choose the framework model configured by the application.

## Choose the model before following the example

| Installed configuration | Read next | Avoid mixing in |
| ------------------------------------------------ | ------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Next.js 15, or 16 with Cache Components disabled | Traditional layers and explicit fetch policy | Assuming the newer use-cache configuration applies |
| Next.js 16 with cacheComponents: true | Cached function/component boundaries and streamed request-time work | Traditional dynamic/revalidate/fetchCache segment settings as equivalent controls |

This chapter scopes examples to those configurations. Framework defaults have changed across versions: since Next.js 15, fetch responses and GET Route Handlers are not persistently cached by default. Consult the installed version's documentation when upgrading. [Previous caching model](https://nextjs.org/docs/app/guides/caching-without-cache-components)

A **React Server Component (RSC) payload** carries server-rendered component information to the client. **ISR** (Incremental Static Regeneration) refreshes reusable route output; it is not the same mechanism as request-local read deduplication.

## Trace one request in the traditional model

```text
Server render → identical reads deduplicated within that render
             → explicitly reusable fetch data may come from Data Cache
             → eligible static HTML/RSC output may come from Full Route Cache
Browser navigation → Router Cache may reuse previously obtained RSC segments
```

| Layer | Reused value | Lifetime/boundary |
| ------------------- | ------------------------------------------------------ | -------------------------------------------------------------------- |
| Request memoization | Identical GET fetch work during React server rendering | One render/request context; not a shared persistent store |
| Data Cache | Explicitly cached server fetch results | Across requests, subject to deployment/store and invalidation policy |
| Full Route Cache | Eligible rendered HTML and RSC output | Static route output; invalidated/rebuilt with its dependencies |
| Router Cache | Client-side RSC route segments | Browser navigation/prefetch state, not a server database cache |

Request memoization belongs to the React component tree, not arbitrary Route Handler code. React `cache(fn)` can deduplicate other server-render helpers within the request context; define the wrapper once and use stable arguments. It is not a cross-request database cache.

### Declare public data reuse and private reads separately

```typescript
export async function readPublicProducts() {
  const response = await fetch('https://api.example.com/products', {
    next: { revalidate: 60, tags: ['products'] },
  });
  if (!response.ok) throw new Error('Product read failed');
  return response.json(); // Parse the response contract before production use.
}

export async function readAccount(sessionToken: string) {
  const response = await fetch('https://api.example.com/account', {
    headers: { Authorization: `Bearer ${sessionToken}` },
    cache: 'no-store',
  });
  if (!response.ok) throw new Error('Account read failed');
  return response.json();
}
```

The public result becomes eligible for time-based revalidation after 60 seconds; this is not a scheduler promising a fresh result at exactly second 60. `force-cache` instead opts into persistent reuse without that time limit; entries can still be invalidated/evicted. Tags label entries for invalidation and do not enable caching by themselves.

The account read still needs authentication and server-side resource authorization. `no-store` avoids persistent fetch reuse in this model; it does not secure an endpoint, erase all client state or override an independently configured CDN cache.

### Rendered output has its own eligibility

An uncached or request-time read can make the route dynamically rendered while other explicitly cached reads remain reusable. Segment settings such as `dynamic = 'force-dynamic'`, `dynamic = 'force-static'`, `revalidate` and `fetchCache` affect the traditional model; force-dynamic bypasses route/data caching under that configuration.

Do not force-static an authenticated route to improve its cache rate. Request APIs and route configuration must agree. The [ISR chapter](10.4.3.05-incremental-static-regeneration.md#follow-a-catalog-page-from-build-to-refresh) owns the full regeneration route example.

## Trace the same page with Cache Components enabled

Enable `cacheComponents: true` in Next.js 16 configuration. Reusable work is declared with `use cache`; request-time work lives under an appropriate Suspense boundary. The result can combine a prerendered shell with streamed dynamic content.

```tsx
import { Suspense } from 'react';
import { cacheLife, cacheTag } from 'next/cache';
import { cookies } from 'next/headers';
import { z } from 'zod';

const countSchema = z.object({ count: z.number().int().nonnegative() });

async function ProductCount() {
  'use cache';
  cacheLife('minutes');
  cacheTag('products');
  const response = await fetch('https://api.example.com/products/count');
  if (!response.ok) throw new Error('Product count unavailable');
  const data = countSchema.parse(await response.json());
  return <p>{data.count} public products</p>;
}

async function AccountStatus() {
  const jar = await cookies();
  // Display only presence here, not identity or authorization proof.
  return <p>{jar.has('session') ? 'Session cookie present' : 'No session cookie'}</p>;
}

export default function Page() {
  return <main>
    <h1>Catalog</h1>
    <Suspense fallback={<p>Loading products…</p>}><ProductCount /></Suspense>
    <Suspense fallback={<p>Loading account…</p>}><AccountStatus /></Suspense>
  </main>;
}
```

`use cache` caches a supported function/component's serialized result, not just a fetch response. A database helper can also sit behind a cached function. Cache identity includes the function and serializable arguments/captured values; a tag is an invalidation label, not a tenant-isolation key.

Do not read cookies or headers inside an ordinary shared cached scope. Obtain request-specific values outside it; cache only a result whose arguments, authorization and data policy make sharing safe. A patient/account result should start from request-time isolation unless there is a justified, verified scoped cache design. [Cache Components model](https://nextjs.org/docs/app/getting-started/caching)

`cacheLife` supplies lifetime profiles or custom stale/revalidate/expire settings. It controls freshness behavior rather than promising permanent residency. `cacheTag` supplies labels for invalidation. A Suspense boundary lets other output proceed while dynamic work is pending; it does not turn the pending work into cached data.

## Invalidate after the authoritative write

| Intent | Next.js 16 API | Caller/result boundary |
| ------------------------------------------------ | --------------------------------- | ---------------------------------------------------------- |
| Mark tagged data stale and refresh on demand | revalidateTag(tag, 'max') | Stale-while-revalidate; readers may briefly see prior data |
| Writer must immediately read updated tagged data | updateTag(tag) | Server Actions only; read-your-writes flow |
| Verified webhook requires immediate tag expiry | revalidateTag(tag, { expire: 0 }) | Route Handler-compatible expiry policy |
| Invalidate a route's data/output | revalidatePath(path) | Path scope, not every unrelated route using the same tag |
| Request fresh client route rendering | router.refresh() | Does not by itself clear persistent server Data Cache |

The older one-argument `revalidateTag(tag)` immediate-expiry form is deprecated in 16; do not copy it into a 16 example. Invalidation is not an eager rebuild of every affected route. [revalidateTag API](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)

Authenticate and authorize mutation/revalidation callers, validate inputs and allowlist paths/tags. A public endpoint accepting arbitrary tags can disrupt caches. For signed webhooks, verify the signature against the raw payload and deduplicate processing before changing state/invalidation.

A Route Handler can mark server entries for subsequent visits without pushing a refreshed view into every open browser. Server Actions integrate differently with the current UI. Router Cache behavior also depends on version, prefetch, stale-time configuration and navigation direction: do not assume every forward visit or back/forward transition causes a new server fetch. Authentication changes need a deliberate client-state refresh/reset path.

## Distinguish HTTP caches and post-response work

An API response's Cache-Control headers configure browsers/proxies/CDNs, a separate boundary from Next's server data cache. Use public caching only for genuinely public responses; user-specific responses need appropriate private/no-store handling. Provider-specific CDN headers can override the intended policy, so verify the deployed adapter's behavior.

`connection()` from next/server can explicitly await request-time execution and exclude work below it from prerendering. With Cache Components, place that uncached work under Suspense; dynamic APIs such as cookies already establish request dependence.

`after(fn)` schedules post-response/prerender work within the host's execution limits. It is suitable for best-effort work, not a durable replacement for a queue. Rendering can occur during prerendering, so it is not an exactly-once visitor-event mechanism. The old experimental dynamicIO flag is not the supported Next.js 16 configuration.

## Verify behavior rather than reporting static “healthy” labels

Test a production build with two identities, repeat reads, mutate the source and observe both writer and independent reader behavior. Check stale responses, tag/path scope, authorization changes and failed revalidation. Development HMR can reuse fetches in ways that confuse no-store experiments.

Measure actual hit/miss behavior, backend calls, stale age, regeneration latency and failures where the host exposes them. A handler returning `dataCache: 'active'` measures nothing. Cross-instance coherence and persistence depend on hosting/adapter configuration; document the deployed store.

## Summary

Choose the installed caching model, then define identity, freshness and invalidation for each reused value. Request deduplication, persistent server reuse and browser navigation are different boundaries. Shared public data can be cached deliberately; authenticated data requires verified isolation, and invalidation must match the writer's freshness needs.

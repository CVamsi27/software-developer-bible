# Caching in Next.js

## Definition

Next.js implements a multi-layered caching system that improves performance by storing and reusing rendered results, data fetches, and static assets. The caching system includes **Data Cache**, **Full Route Cache**, **Router Cache**, and **Request Memoization**.


## Choose the model for your installed version

This chapter covers both the traditional cache-layer model and Next.js Cache Components. Check the installed version and `cacheComponents` configuration first: examples using route-level `dynamic`, `revalidate` or `fetchCache` settings are not interchangeable with the Cache Components model. Start with one request: which data may be reused, for which identity, and until which invalidation event? Then study the matching model below.

A React Server Component (RSC) payload is the serialized representation React uses to reconstruct server-rendered component output on the client. Incremental Static Regeneration (ISR) refreshes reusable route output. These are different responsibilities from request-local deduplication.

## First Principles

In the traditional model, separate request-local, persistent-data, route-output and client-navigation reuse because their keys and lifetimes differ:

1. **Request memoization (per-request dedup), Data Cache (cross-request, keyed by fetch args), Full Route Cache (rendered RSC payload), Router Cache (client-side)** — each answers "who is asking, and for how long can the answer repeat?"; a bug is almost always the wrong layer's lifetime assumed.
2. **Invalidation follows dependency**: tags, time, paths, and action-only `updateTag` affect different scopes; invalidating data also affects rendered output that depends on it (→ 30.3.4.03's invalidation economics).
3. **Opt out explicitly (`dynamic`, `no-store`)** when data is user-specific — the framework cannot know; caching authed data at the wrong layer is a data-leak class.

## Why It Matters

Senior engineers reason about each cache separately: opt out of Data Cache with `cache: 'no-store'`, use `revalidate` for time-based ISR, use `revalidateTag`/`revalidatePath` from Server Actions for on-demand invalidation. The interview signal is knowing which cache to invalidate when data changes.

## How It Works

**Version scope:** The four-cache model and segment configuration below describe Next.js 15 (and Next.js 16 with Cache Components disabled). Since 15, fetch responses and GET Route Handlers are not persistently cached by default. Shared layouts/loading states are still reused on navigation; page segments are not ordinarily reused for forward navigation unless configured, but back/forward and prefetch behavior still apply.

Request memoization deduplicates identical GET reads during one React server render; React `cache` provides request-local deduplication for other helpers. A refresh of the browser Router Cache does not clear the server Data Cache, while invalidating data can force dependent HTML/RSC regeneration. A Route Handler invalidation marks server entries for future visits and does not immediately push refreshed UI to every open browser.

**Tag versions:** One-argument `revalidateTag(tag)` below is the Next.js 15 immediate-expiry API. In 16 use `revalidateTag(tag, 'max')` for stale-while-revalidate; use `updateTag(tag)` only in Server Actions when the writer needs fresh reads immediately, or `revalidateTag(tag, { expire: 0 })` for immediate-expiry webhook behavior. A call marks/invalidates entries; it is not an eager rebuild of every page.

## Code Examples

### Data Cache — Time-Based Revalidation

```typescript
// app/products/page.tsx
export default async function ProductsPage() {
  // Cache for 60 seconds
  const products = await fetch('https://api.example.com/products', {
    next: { revalidate: 60 },
  }).then(res => res.json())

  return (
    <div>
      <h1>Products</h1>
      {products.map(product => (
        <div key={product.id}>{product.name}</div>
      ))}
    </div>
  )
}

```

### Tag-Based Revalidation

```typescript
// app/api/revalidate/route.ts
import { revalidateTag } from 'next/cache'
import { NextRequest, NextResponse } from 'next/server'

export async function POST(request: NextRequest) {
  const { tag, secret } = await request.json()

  if (!process.env.REVALIDATION_SECRET || secret !== process.env.REVALIDATION_SECRET) {
    return NextResponse.json({ error: 'Invalid secret' }, { status: 401 })
  }

  revalidateTag(tag)

  return NextResponse.json({ revalidated: true, timestamp: Date.now() })
}

```

### Incremental Static Regeneration (ISR)

> [ISR](10.4.3.05-incremental-static-regeneration.md#2-isr-with-dynamic-params-generatestaticparams) owns the product route's regeneration example. Persistent fetch entries and cached HTML/RSC output are separate: an uncached/request-time read bypasses the Full Route Cache but can coexist with other cached reads.

### On-Demand Revalidation via Webhook

```typescript
// app/api/webhooks/stripe/route.ts
import { revalidateTag } from 'next/cache'
import { NextRequest, NextResponse } from 'next/server'
import Stripe from 'stripe'

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!)

export async function POST(request: NextRequest) {
  const body = await request.text()
  const sig = request.headers.get('stripe-signature')!

  let event: Stripe.Event

  try {
    event = stripe.webhooks.constructEvent(
      body,
      sig,
      process.env.STRIPE_WEBHOOK_SECRET!
    )
  } catch (err) {
    return NextResponse.json({ error: 'Invalid signature' }, { status: 400 })
  }

  if (event.type === 'product.updated') {
    const product = event.data.object as Stripe.Product
    revalidateTag(`product-${product.id}`)
    revalidateTag('products')
  }

  return NextResponse.json({ received: true })
}

```

### Cache Monitoring

A handler returning fixed strings such as `dataCache: 'active'` does not measure cache health. Instrument actual store hits/misses, tag invalidation, and regeneration latency; inspect production cache headers/logs where the host exposes them. Verify with `next build && next start` because development HMR can reuse fetches even with `no-store`.

| Use Case | Caching Strategy |
| ------------------- | ---------------------------------- |
| E-commerce products | ISR with 60s revalidation |
| Blog posts | ISR with on-demand revalidation |
| User dashboard | No cache (always fresh) |
| Static pages | Full Route Cache |
| API responses | Data Cache with tags |
| Search results | Data Cache with short revalidation |
| User preferences | No cache |
| Public data | Force cache with long revalidation |

## Common Mistakes

### 1. Caching Sensitive Data

```typescript
// BAD: Caching user-specific data
export default async function Dashboard() {
  const data = await fetch('https://api.example.com/dashboard', {
    next: { revalidate: 300 } // Cached for all users!
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <div>{data.privateInfo}</div>
}

// GOOD: Don't cache personalized data
export default async function Dashboard() {
  const data = await fetch('https://api.example.com/dashboard', {
    cache: 'no-store' // Always fresh
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <div>{data.privateInfo}</div>
}

```

### 2. Not Invalidating Stale Cache

```typescript
// BAD: The completed write does not promptly invalidate its read cache
export default async function ProductsPage() {
  const products = await fetch('https://api.example.com/products', {
    next: { revalidate: 3600, tags: ['products'] } // Refresh after an hour or explicit invalidation
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <ProductList products={products} />
}

// GOOD: Use on-demand revalidation
export async function addProduct(product) {
  'use server'
  await db.product.create({ data: product })
  revalidateTag('products') // Invalidate cache
}

```

### 3. Over-Caching

```typescript
// BAD: Caching everything aggressively
export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    cache: 'force-cache' // Never updates!
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <div>{data.value}</div>
}

// GOOD: Cache appropriately
export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 } // Eligible for refresh after a minute
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <div>{data.value}</div>
}

```

### 4. Not Handling Cache Errors

```typescript
// BAD: No error handling for cache misses
export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 }
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <div>{data.value}</div> // What if fetch fails?
}

// GOOD: Handle errors gracefully
export default async function Page() {
  try {
    const data = await fetch('https://api.example.com/data', {
      next: { revalidate: 60 }
    })
    if (!data.ok) throw new Error('Failed to fetch')
    const json = await data.json()
    return <div>{json.value}</div>
  } catch (error) {
    return <div>Failed to load data</div>
  }
}

```

### 5. Mixing Cache Strategies Incorrectly

```typescript
// BAD: Conflicting cache settings
export const dynamic = 'force-dynamic' // No Full Route Cache
export const revalidate = 60 // But trying to ISR?

export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    cache: 'force-cache' // And force cache?
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <div>{data.value}</div>
}

// GOOD: Consistent cache strategy
export const revalidate = 60 // ISR

export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 }
  }).then(res => {
    if (!res.ok) throw new Error('Data fetch failed')
    return res.json()
  })
  return <div>{data.value}</div>
}

```

## Best Practices

1. **Cache deliberately** — Opt public reusable data in; preserve isolation for user-specific data

2. **Use tags for granular invalidation** — More precise cache control

3. **Implement on-demand revalidation** — Update cache when data changes

4. **Cache at the right level** — Data cache for fetches, route cache for pages

5. **Monitor cache hit rates** — Track and optimize cache usage

6. **Handle cache misses gracefully** — Fallback for uncached content

7. **Use Request Memoization** — Deduplicate fetches automatically

8. **Implement proper error handling** — Cache failures shouldn't break the app

9. **Document caching strategies** — Team needs to understand the approach
10. **Test cache behavior** — Verify in development and production

## Modern Paradigm: `use cache` and Partial Prerendering

Everything above is the fetch-level API. The newer model inverts the defaults: instead of configuring each fetch, you **declare what is cacheable** with the `use cache` directive, and everything else is dynamic. Enabled with `cacheComponents: true` in Next.js 16. Next.js 15 experiments used different flags/APIs; do not treat the 16 configuration as a stable 15.5 feature.

```typescript
// app/products/page.tsx
import { Suspense } from 'react';
import { cacheLife, cacheTag } from 'next/cache';

export default async function ProductsPage() {
  return (
    <main>
      {/* Static shell — prerendered, ships instantly */}
      <h1>Products</h1>
      <Suspense fallback={<ProductSkeleton />}>
        {/* Cached subtree — eligible for prerendering into the shell */}
        <ProductList />
      </Suspense>
    </main>
  );
}

async function ProductList() {
  'use cache'; // Cache this function's result across requests
  cacheLife('hours'); // Revalidation profile (see below)
  cacheTag('products'); // Tag for on-demand invalidation

  const products = await db.query('SELECT * FROM products');
  return <ul>{products.map(p => <ProductCard key={p.id} product={p} />)}</ul>;
}
```

Key ideas:

1. **`use cache` at a file/function/component boundary** — supported async functions and Server Components can cache their result. The cached value is the serialized result, not just a fetch response (DB queries are cacheable too).
2. **`cacheLife(profile)`** — time-based revalidation using named profiles (`default`, `seconds`, `minutes`, `hours`, `days`, `weeks`, `max`) or a custom `{ stale, revalidate, expire }` object.
3. **`cacheTag(...)`** — labels the cached result; `revalidateTag`/`updateTag` performs the corresponding invalidation.
4. **Partial Prerendering (PPR)** — the static shell renders at build time; dynamic parts (cookies, headers, uncached data) are *holes* streamed in at request time. One route gets static speed AND per-request freshness — no more choosing between SSG and SSR for the whole page.
5. **Suspense boundaries are the contract** — anything dynamic must sit inside a `<Suspense>` so the shell can ship without it.

```text
Mental model shift:

Fetch-config model:      use cache model:
┌───────────────────┐    ┌───────────────────┐
│ Route = all-or-   │    │ Route = static    │
│ nothing (SSG/SSR) │ ─► │ shell + dynamic   │
│ per-fetch options │    │ holes, per-function│
│ per-route config  │    │ 'use cache'       │
└───────────────────┘    └───────────────────┘
```

### The dynamic-API surface: `after()` and `connection()`

In Next.js 16, `cacheComponents` sets the cache model; `connection` and `after` describe request-time and post-response work:

```typescript
import { after, connection } from 'next/server';
import { Suspense } from 'react';

export default function CheckoutPage() {
  return <Suspense fallback={<div>Loading checkout...</div>}><CheckoutContent /></Suspense>;
}

async function CheckoutContent() {
  const user = await getUser(); // request-time read below Suspense

  after(async () => {
    // Runs AFTER the response is streamed — logging, analytics,
    // best-effort side work. It does not delay the response.
    await logCheckout(user.id);
  });

  return <Checkout user={user} />;
}

async function getUser() {
  // In a prerendered shell, non-cached reads need a real request.
  // connection() marks this function as request-time only (the
  // successor of unstable_noStore): the shell streams first, this
  // resolves during the request phase.
  await connection();
  return session.read();
}
```

- **`after(fn)`** — schedule work after the response/prerender completes, within the host execution-duration limit. Rendering may also occur during prerendering, so this is not guaranteed to run exactly once per visitor; use request handlers for visitor events and a durable queue for work that must survive a crash.
- **`connection()`** — explicitly opt a component/function into request-time execution inside an otherwise-prerendered route (replaces `unstable_noStore`). The framework then *knows* the dynamic boundary instead of inferring it from ambient reads.
- **`cacheComponents`** — uncached request-time work must have an appropriate Suspense boundary. `connection()` is awaited to exclude work below it from prerendering; `dynamicIO` is an older experimental name, removed in 16, rather than another supported configuration switch.

Interview frame: the old model asked "which fetch option did you set?"; the new model asks "where is the dynamic boundary and who declared it?" — `use cache` declares the cached side, `connection()`/dynamic APIs declare the request-time side, `after()` moves work past the boundary entirely.

## Performance Considerations

```text
Cache Performance Impact:

- First request: Normal performance (cache miss)
- Subsequent requests: Fast performance (cache hit)
- Revalidation: Background regeneration
- Cache invalidation: Triggers fresh fetch

Optimization:

- Set appropriate revalidation times
- Use on-demand revalidation for critical updates
- Implement cache warming for popular content
- Monitor cache hit rates

```

## Summary

First choose the configured model. Traditional cache layers distinguish request memoization, persistent data, reusable route output and client navigation. Cache Components instead makes reusable server work explicit with its cache directives, lifetime and tagging APIs; follow the dedicated section and its version-specific restrictions. In either model, identity, authorization, freshness and invalidation must agree.

The table below summarizes the traditional model, not every Cache Components configuration.

| Cache Layer | Location | Purpose | Revalidation |
| ------------------- | ------------------- | --------------------- | -------------- |
| Request Memoization | Server (in-memory) | Deduplicate fetches | Per request |
| Data Cache | Server (persistent) | Cache fetch results | Time/On-demand |
| Full Route Cache | Server (persistent) | Cache rendered routes | Time/On-demand |
| Router Cache | Client (browser) | Cache RSC payload | Navigation |

# Streaming in Next.js

## Definition

**Streaming** in Next.js allows you to progressively render and send HTML from the server to the client. Instead of waiting for all data to load before rendering, the server can send the ready page shell before every section completes and streams in slower components as they become ready.

> **Textbook Definition:** Streaming sends a response incrementally so ready content can arrive before slower work completes. Suspense boundaries coordinate independently available UI regions, while response status and headers become constrained once transmission begins.


## First Principles

A dashboard title does not need the three-second analytics query. Waiting for that query before sending anything makes unrelated content wait too.

1. **Ready output can be sent before unavailable output.** Mark a region that may wait and provide a fallback so the surrounding shell can complete without it.
2. **True dependencies cannot be skipped.** If recommendations need a user ID, that read starts after identity exists. Streaming changes reveal timing; scheduling independent work changes completion time.
3. **An HTTP response becomes committed as bytes leave.** Status and headers cannot be rewritten afterward. Authentication or checks that require a real redirect/status must happen before the relevant shell is sent.

## Why It Matters

Streaming is useful when part of a page can help the user before another part finishes. Choose boundaries around meaningful regions, and measure when useful content arrives; an early shell alone does not prove the page feels fast.

## How It Works

A Suspense boundary controls when a subtree reveals; it does not start queries or parallelize dependent awaits. A non-streaming page can also use `Promise.all` to start independent reads together. It still waits to deliver its complete output; streaming can reveal ready regions earlier.

Once response headers have been sent, the HTTP status cannot be changed: later `notFound()`/redirect/error handling must use the streamed protocol/UI. Do required authentication and checks that need a real 401/404/redirect before sending the shell. Browser/CDN buffering can delay visible chunks, so verify the production proxy path as well as local development.

`loading.tsx` wraps the segment's page and descendants beneath its layout. It does not cover work awaited by that parent layout, so put request-dependent reads close to their own Suspense boundary or move them below the segment fallback.

For some bots and crawlers, Next.js waits for data and sends the fully rendered page rather than progressive chunks. Verify the crawler behavior required by the product; browser streaming alone is not an SEO delivery guarantee.

### Trace three independent regions

Assume the shell has no unfinished work and three independent helpers finish after 1, 2 and 3 seconds. These illustrative durations exclude network/host buffering and are not a benchmark.

```text
Shell ready: title + activity/stats/chart fallbacks can be sent
1 second: activity result replaces its fallback
2 seconds: stats result replaces its fallback
3 seconds: chart result replaces its fallback
```

One boundary around all three would reveal that region as a unit after its slowest dependency. Separate boundaries allow distinct reveal regions; they do not guarantee frame-by-frame arrival or JSX order. React/Next send protocol instructions with streamed content; internal helper names are implementation details, not APIs to call from application code.

## Code Examples

### Basic Streaming with loading.tsx

```typescript
// loading.tsx provides automatic Suspense boundary
// app/dashboard/loading.tsx
export default function Loading() {
  return (
    <div className="animate-pulse">
      <div className="h-8 bg-gray-200 rounded w-1/3 mb-4" />
      <div className="h-4 bg-gray-200 rounded w-full mb-2" />
      <div className="h-4 bg-gray-200 rounded w-2/3" />
    </div>
  )
}

```

The file is separate from the page. `loading.tsx` covers the segment page and descendants beneath its layout; use explicit boundaries inside the page when several regions should reveal independently. Skeletons should match expected geometry and honor reduced-motion preferences.

### Multiple Suspense Boundaries

```typescript
// app/dashboard/page.tsx
import { Suspense } from 'react'
import { StatsSkeleton, ChartSkeleton, ActivitySkeleton } from './skeletons'
import { fetchStats, fetchAnalytics, fetchActivity } from './data'
import { Chart } from './chart'

export default function DashboardPage() {
  return (
    <div className="grid grid-cols-12 gap-6">
      {/* Header renders immediately */}
      <div className="col-span-12">
        <h1>Dashboard</h1>
      </div>

      {/* Stats section streams independently */}
      <div className="col-span-4">
        <Suspense fallback={<StatsSkeleton />}>
          <StatsOverview />
        </Suspense>
      </div>

      {/* Chart section streams independently */}
      <div className="col-span-8">
        <Suspense fallback={<ChartSkeleton />}>
          <AnalyticsChart />
        </Suspense>
      </div>

      {/* Activity section streams independently */}
      <div className="col-span-12">
        <Suspense fallback={<ActivitySkeleton />}>
          <RecentActivity />
        </Suspense>
      </div>
    </div>
  )
}

async function StatsOverview() {
  const stats = await fetchStats() // 2 seconds
  return (
    <div className="border rounded-lg p-4">
      <h2>Stats</h2>
      <p>Total Users: {stats.users}</p>
      <p>Revenue: ${stats.revenue}</p>
    </div>
  )
}

async function AnalyticsChart() {
  const data = await fetchAnalytics() // 3 seconds
  return (
    <div className="border rounded-lg p-4">
      <h2>Analytics</h2>
      <Chart data={data} />
    </div>
  )
}

async function RecentActivity() {
  const activity = await fetchActivity() // 1 second
  return (
    <div className="border rounded-lg p-4">
      <h2>Recent Activity</h2>
      {activity.map(item => (
        <div key={item.id}>{item.description}</div>
      ))}
    </div>
  )
}

```

The application data helpers and chart/skeleton modules are required adapters. Authorize the dashboard before returning private output, and keep reads scoped to that visitor. With the illustrative completion times above, activity can reveal before stats even though its JSX appears later. Reserving space prevents a fallback replacement from unexpectedly pushing focused or visible content down.

### Nested Streaming

```typescript
// app/dashboard/page.tsx
import { Suspense } from 'react'

export default function DashboardPage() {
  return (
    <div>
      <h1>Dashboard</h1>

      <Suspense fallback={<DashboardSkeleton />}>
        <DashboardContent />
      </Suspense>
    </div>
  )
}

async function DashboardContent() {
  // This component streams in
  const user = await getUser()

  return (
    <div>
      <p>Welcome, {user.name}</p>

      {/* Nested Suspense for deeper streaming */}
      <Suspense fallback={<OrdersSkeleton />}>
        <UserOrders userId={user.id} />
      </Suspense>

      <Suspense fallback={<RecommendationsSkeleton />}>
        <Recommendations userId={user.id} />
      </Suspense>
    </div>
  )
}

```

The orders and recommendations cannot start until `getUser()` supplies identity. Once the outer user read finishes, their independent boundaries can reveal separately. A failure to establish identity belongs to the outer policy; putting it behind a fallback must not accidentally expose a private shell or lose a required HTTP status.

### Streaming with Error Handling

```typescript
// app/dashboard/page.tsx
import { Suspense } from 'react'

export default function DashboardPage() {
  return (
    <div>
      <h1>Dashboard</h1>

      <Suspense fallback={<Loading />}>
        <DashboardData />
      </Suspense>
    </div>
  )
}

async function DashboardData() {
  const data = await fetchDashboardData()
  return <div>{data.content}</div>
}
```

```typescript
// app/dashboard/error.tsx — a route error boundary must be a Client Component.
'use client'

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string }
  reset: () => void
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <p>We could not load the dashboard. Try again.</p>
      {error.digest && <p>Reference: {error.digest}</p>}
      <button onClick={() => reset()}>Try again</button>
    </div>
  )
}
```

Suspense handles pending work; `error.tsx` handles failures beneath its route boundary. Because it runs in the browser, show a safe message and a support reference instead of raw server error text. A nearer custom boundary is useful only when that region needs its own recovery path.

### Parallel Streaming

> The [multiple-boundary dashboard](#multiple-suspense-boundaries) already runs independent stats, chart, and activity work. Their completion order follows latency, not JSX order; putting sequential awaits in one ancestor can still serialize everything before these boundaries are reached.

### Selective Streaming

> The [nested-streaming example](#nested-streaming) preserves the outer shell and suspends deeper sections. Put only the slow subtree inside the fallback: anything the shell awaits outside it must finish before that shell can be sent.

### Reveal Essential Content Before Optional Detail

```typescript
// app/dashboard/page.tsx
import { Suspense } from 'react'

export default function DashboardPage() {
  return (
    <div>
      <h1>Dashboard</h1>

      {/* Essential content renders first */}
      <DashboardSummary />

      {/* Detailed content streams in */}
      <Suspense fallback={<DetailsSkeleton />}>
        <DashboardDetails />
      </Suspense>

      {/* Charts reveal when ready; source order does not impose completion order */}
      <Suspense fallback={<ChartsSkeleton />}>
        <DashboardCharts />
      </Suspense>
    </div>
  )
}

async function DashboardSummary() {
  const summary = await fetchSummary() // Fast
  return (
    <div className="summary">
      <p>Total: {summary.total}</p>
      <p>Active: {summary.active}</p>
    </div>
  )
}

async function DashboardDetails() {
  const details = await fetchDetails() // Slow
  return (
    <div className="details">
      {details.map(item => (
        <div key={item.id}>{item.name}</div>
      ))}
    </div>
  )
}

async function DashboardCharts() {
  const chartData = await fetchChartData() // Very slow
  return <Chart data={chartData} />
}

```

## Real-World Use Cases

| Use Case | Streaming Benefit |
| -------------- | ---------------------------------------- |
| Dashboard | Stats load first, charts stream in |
| E-commerce | Product info first, reviews stream in |
| Blog | Article loads first, comments stream in |
| Admin panel | Overview first, details stream in |
| Analytics | Summary first, detailed charts stream in |

## Common Mistakes

### 1. Leaving a slow subtree without an intentional boundary

> Compare the [multiple-boundary example](#multiple-suspense-boundaries) with a page that returns a slow async child directly. Without a local boundary, the child suspends to the nearest ancestor—possibly `loading.tsx`—so more of the page is replaced by that ancestor's fallback.

### 2. Making Everything a Suspense Boundary

```typescript
// BAD: Too many boundaries
export default function Page() {
  return (
    <div>
      <Suspense fallback={<Loading />}>
        <Header />
      </Suspense>
      <Suspense fallback={<Loading />}>
        <Navigation />
      </Suspense>
      <Suspense fallback={<Loading />}>
        <Content />
      </Suspense>
      <Suspense fallback={<Loading />}>
        <Footer />
      </Suspense>
    </div>
  )
}

// GOOD: Strategic boundaries for slow content
export default function Page() {
  return (
    <div>
      <Header /> {/* Fast, no boundary needed */}
      <Navigation /> {/* Fast, no boundary needed */}
      <Suspense fallback={<ContentSkeleton />}>
        <Content /> {/* Slow, needs boundary */}
      </Suspense>
      <Footer /> {/* Fast, no boundary needed */}
    </div>
  )
}

```

### 3. Not Handling Loading States

```typescript
// BAD: No loading state
export default function Page() {
  return (
    <div>
      <h1>Page</h1>
      <Suspense>
        <SlowComponent />
      </Suspense>
    </div>
  )
}

// GOOD: Always provide fallback
export default function Page() {
  return (
    <div>
      <h1>Page</h1>
      <Suspense fallback={<LoadingSkeleton />}>
        <SlowComponent />
      </Suspense>
    </div>
  )
}

```

### 4. Streaming Too Much Content

A single whole-page boundary is valid when the page should reveal as a unit. It gives less incremental feedback than [separate dashboard sections](#multiple-suspense-boundaries); choose boundaries around meaningful regions rather than assuming any large streamed subtree is an error.

### 5. Not Using loading.tsx

Manual `<Suspense>` and `loading.tsx` solve different scopes. `loading.tsx` automatically wraps the segment page and its children beneath the layout, providing route-navigation feedback; explicit boundaries control partial reveal inside that page. Neither is intrinsically a BAD pattern.

## Best Practices

- Put boundaries around user-meaningful regions, not every component.
- Start independent work before awaiting a shared ancestor; keep real dependencies ordered.
- Give pending regions useful, dimension-matched fallbacks and keep them understandable to assistive technology.
- Handle failures with an error boundary. Show a safe message and a support reference, not raw server error text.
- Test chunk arrival through the production proxy/CDN and compare the shell, largest content, layout shift and failure behavior.

## Performance Considerations

```text
Streaming Performance Benefits:

- TTFB: Shell can ship once work outside Suspense completes
- FCP: May improve when the shell or fallback is useful and arrives early
- LCP: Depends on when the largest visible content arrives
- CLS: Reserve matching geometry; placeholders alone are insufficient

Optimization:

- Parallel data fetching
- Strategic Suspense boundaries
- Loading state design
- Error handling per boundary

```

# Streaming in Next.js

A dashboard can render its title quickly while a chart query takes seconds. If the route waits for the chart, ready content waits too; a Suspense boundary can let the useful shell arrive while that region is pending.

```text
t=0ms    Server sends HTML shell (<h1>Dashboard</h1> + skeletons)
t=120ms  Stats resolves  ─► streamed chunk replaces <StatsSkeleton />
t=850ms  Chart resolves  ─► streamed chunk replaces <ChartSkeleton />
```

## Definition

**Streaming** sends a rendered response in parts. A useful shell can reach the browser while a slower region is still waiting; that region replaces its fallback when its work is ready.

> **Textbook Definition:** Streaming is incremental delivery of a response as independent portions become available. In React, Suspense boundaries define pending UI regions; the server and transport determine when their completed output can reach the client.

## First Principles

A fallback gives the renderer a useful place to pause while the slow region is unresolved. Streaming helps only when the shell is useful and the slow work can proceed separately: if a recommendation query needs the user ID, it must wait for the user read. A Suspense boundary controls when UI reveals — never data dependencies, and never automatic request parallelization.

## 1. Place the Boundary Where Waiting Begins

Start independent work before awaiting it, then place a boundary around each region whose delay should not block the rest:

```tsx
import { Suspense } from 'react';
import { Activity, Chart, Stats } from './dashboard-sections';
import { ActivitySkeleton, ChartSkeleton, StatsSkeleton } from './skeletons';
import { getActivity, getChartData, getStats } from './data';

export default function DashboardPage() {
  // These application reads begin before any result is awaited.
  const activity = getActivity();
  const chart = getChartData();
  const stats = getStats();

  return (
    <main>
      <h1>Dashboard</h1>
      <section aria-label="Activity">
        <Suspense fallback={<ActivitySkeleton />}>
          <Activity result={activity} />
        </Suspense>
      </section>
      <section aria-label="Statistics">
        <Suspense fallback={<StatsSkeleton />}>
          <Stats result={stats} />
        </Suspense>
      </section>
      <section aria-label="Analytics">
        <Suspense fallback={<ChartSkeleton />}>
          <Chart result={chart} />
        </Suspense>
      </section>
    </main>
  );
}
```

Each async section awaits its own promise and renders the result, so the three reads can finish in any order regardless of JSX position.

Every section must still authorize and scope its reads to the signed-in user. If a later read depends on an earlier result, start it after that input exists and place its fallback around the dependent region.

## 2. Pick Route-Wide or Local Loading by Scope

`loading.tsx` gives a route segment an automatic `<Suspense>` fallback around its page and descendants beneath that segment's layout. It is useful for navigation-level feedback. A local `<Suspense>` gives finer control when a page has several regions with different waiting and reveal behavior.

A fallback must be useful, accessible, and close to the final region's geometry — a full-page spinner hides ready content, and a mismatched skeleton causes layout shift when replaced.

An awaited request in a parent layout sits outside that segment's `loading.tsx`. Move that read below the boundary or wrap it in a nearer `<Suspense>` boundary. For parallel routes (`@analytics` and `@feed`), placing `loading.tsx` and `error.tsx` inside each slot folder gives sibling slots independent streaming and recovery boundaries within the same layout.

## 3. Keep HTTP Decisions Ahead of the First Bytes

Once streaming begins, the HTTP status and response headers are already committed. A later `notFound()`, `redirect()`, or exception can update the streamed UI, but it cannot rewrite the HTTP status already sent.

Authenticate and run any checks that must return a real `401`, `404`, or redirect before sending the shell. Never emit private or misleading content in the shell while authorization is still pending.

`<Suspense>` handles pending work, not failures. A thrown error bubbles to the nearest error boundary; route-level `error.tsx` is a Client Component exposing `retry` (Next.js 16.3+, re-fetches and re-renders) or `reset` (clears boundary state).

Show a safe fallback message and log diagnostic details on the server rather than rendering raw exception text. Add a narrower error boundary only when a region needs its own recovery path.

## 4. Account for Crawlers and the Production Path

Streaming metadata differs by crawler capability. Next.js waits for `generateMetadata` when an HTML-limited bot needs metadata in the initial `<head>`, whereas full browsers and DOM-capable crawlers can receive streamed metadata updates.

With Cache Components enabled, HTML-limited bots render the page dynamically rather than using the prerendered shell so metadata is present in `<head>`. Make sure the data required by that path is available at request time.

Even when Next.js streams progressively, a reverse proxy, CDN, serverless adapter, or compression layer can buffer the response. HTTP/1.1 and HTTP/2 frame streamed chunks differently, so verify progressive delivery through the production path rather than only the dev server.

In browser DevTools, inspect document timing alongside when useful content actually paints — a fast first byte alone does not prove the main content arrived sooner.

## 5. Decide What Streams Separately

Use separate boundaries for independently useful dashboard panels, product information and optional reviews, or an article and its comments. Keep authentication, the title, or any content needed to understand the page outside a slow optional boundary when those values are ready sooner. Keep sections together when revealing them separately would mislead, break a task, or cause disruptive layout movement.

Measure the user-visible result. Streaming can improve Time to First Byte (TTFB) and first paint when the shell is useful, but Largest Contentful Paint (LCP) still depends on the largest content element. Reserve space for fallbacks and watch layout shift as sections resolve.

## Summary

Streaming lets ready UI arrive before slower work, while Suspense boundaries define which region waits. Start independent reads together, keep true dependencies intact, and choose boundaries around meaningful content. Make status and access decisions before sending bytes, handle failures separately from pending states, and verify that production infrastructure forwards the stream.

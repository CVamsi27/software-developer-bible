# Incremental Static Regeneration (ISR)

A large catalog may contain more routes than a build should pre-render, while its public descriptions still change after deployment. ISR reuses generated output and lets later requests trigger its refresh under a defined freshness policy.

```tsx
// app/products/[id]/page.tsx — traditional model
export const revalidate = 300; // eligible for refresh after 5 minutes

export async function generateStaticParams() {
  const popular = await getPopularProductIds(); // prebuild the top 100
  return popular.slice(0, 100).map((id) => ({ id }));
}
```

## Definition

**Incremental Static Regeneration (ISR)** reuses rendered route output and refreshes it after deployment, without rebuilding the whole site. In the traditional App Router model, a revalidation interval makes output eligible for refresh. A later request triggers regeneration; visitors can receive the previous successful output while the new version is prepared.

> **Textbook Definition:** Incremental static regeneration is request-driven regeneration of cached static route output in a supported server runtime. Time-based or on-demand invalidation controls eligibility, and successful output replaces the previous cached version.

## First Principles

A product catalog may contain hundreds of thousands of pages, while a build can afford to render only the most popular ones. The site still needs a rule for pages that were not built and for content that changes after deployment. ISR combines three decisions: which pages to prebuild, how stale a shared copy may be, and what event should make a page eligible for replacement. The interval is a freshness threshold, not a scheduled job. Without a later request, an expired page may not be regenerated.

## How It Works

### Follow a catalog page from build to refresh

**Version scope:** This chapter covers the traditional App Router cache model in Next.js 16.4 with `cacheComponents` disabled. Cache Components has a separate model for prerendered shells and cached functions; see [ISR with Cache Components](https://nextjs.org/docs/app/guides/incremental-static-regeneration-cache-components). Traditional ISR requires a supported server runtime. Next.js documents support for Node.js servers and Docker, no support for static export, and platform-specific adapter support.

Prebuild popular product IDs and let other valid IDs render on first request. In the traditional model, `generateStaticParams` runs during the build; ISR does not call it again when new products appear. With the default `dynamicParams = true`, unbuilt IDs can render on demand. Set it to `false` when every permitted route must be listed at build time.

```tsx
// app/products/[id]/page.tsx
import { notFound } from 'next/navigation';

export const revalidate = 300;

export async function generateStaticParams() {
  const response = await fetch('https://catalog.example.com/products/popular');
  if (!response.ok) throw new Error('Product index unavailable');
  const products = parseProductIndex(await response.json());

  return products.slice(0, 100).map((product) => ({ id: product.id }));
}

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const response = await fetch(
    `https://catalog.example.com/products/${encodeURIComponent(id)}`,
  );

  if (response.status === 404) notFound();
  if (!response.ok) throw new Error('Product service unavailable');

  const product = parseProduct(await response.json());
  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <p>Price: {product.displayPrice}</p>
    </main>
  );
}
```

The parsers represent runtime validation of upstream data. The route segment's `revalidate` policy makes this output eligible for regeneration after five minutes. If price or availability must be current, check them again when committing checkout; a cached product page is a display copy, not inventory authority.

For an already generated page, the request timeline is:

| State | What the visitor gets | What the runtime does |
| -------------------------------- | -------------------------------- | ----------------------------- |
| Fresh cached page | Current cached output | Reuse it |
| Interval elapsed; page requested | Last successful output | Start background regeneration |
| Regeneration succeeds | Updated output on later requests | Replace the cache entry |
| Regeneration throws | Last successful output | Retry on a later request |
| Unbuilt valid ID requested | Wait for an initial render | No old output exists to serve |

### 1. Match Invalidation to the Writer's Freshness Promise

After a CMS update, use a verified signal to invalidate the affected path or tagged data. A Route Handler calling `revalidatePath` invalidates the route so a later request regenerates it. In Next.js 16, `revalidateTag(tag, 'max')` uses stale-while-revalidate: a reader may see the previous tagged value while refresh runs. For immediate tag expiry from a webhook, use the appropriate expiry profile; `updateTag` is limited to Server Actions and supports a writer's read-your-writes flow. These APIs do not eagerly rebuild every affected route.

```typescript
// app/api/cms-webhook/route.ts — bounded-body and CMS adapters are app-specific
import { revalidatePath, revalidateTag } from 'next/cache';
import {
  cmsEventSchema,
  readBodyLimited,
  recordEventOnce,
  verifyCmsSignature,
} from '@/lib/cms';

export async function POST(request: Request) {
  // Application helper stops reading and returns null once the limit is exceeded.
  const rawBody = await readBodyLimited(request, 256_000);
  if (!rawBody) return Response.json({ error: 'Payload too large' }, { status: 413 });

  const signature = request.headers.get('x-cms-signature');
  if (!signature || !verifyCmsSignature(rawBody, signature)) {
    return Response.json({ error: 'Invalid signature' }, { status: 401 });
  }

  let body: unknown;
  try {
    body = JSON.parse(new TextDecoder().decode(rawBody));
  } catch {
    return Response.json({ error: 'Malformed JSON' }, { status: 400 });
  }
  const parsed = cmsEventSchema.safeParse(body);
  if (!parsed.success) return Response.json({ error: 'Invalid event' }, { status: 400 });

  const event = parsed.data; // Schema allowlists event types and validates IDs.
  await recordEventOnce(event.id, async () => {
    if (event.type !== 'product.updated') return;
    revalidateTag(`product:${event.productId}`, 'max');
    revalidateTag('products', 'max');
    revalidatePath(`/products/${encodeURIComponent(event.productId)}`);
  });

  return Response.json({ accepted: true });
}
```

The CMS adapter must verify the provider's signature over the expected raw bytes, enforce replay limits, validate the event schema, and durably deduplicate its ID. It must record completion only after invalidation succeeds, or use a durable retry/outbox design; otherwise a crash can lose an accepted event. Bound the request body before buffering it. Allowlist event types and derive paths/tags from validated IDs instead of accepting arbitrary invalidation targets. An accepted webhook means the signal was recorded; it does not prove that every route has regenerated or every open browser has refreshed.

When list membership depends on a threshold, compare both the stored value before and after a change. If a rating falls from 4.8 to 4.0, checking only the new rating misses that the item must leave the bestseller list:

```typescript
const beforeRating = before?.rating ?? 0;
const afterRating = after?.rating ?? 0;

if (beforeRating > 4.5 || afterRating > 4.5) {
  revalidateTag('bestsellers', 'max');
}
```

Apply the same reasoning to create, delete, stock, ordering, and permission changes. If the event does not contain enough old state to know whether membership changed, invalidate the affected list rather than guessing.

### 2. Keep Route, Data, and CDN Caches Distinct

For a prerendered route, the lowest `revalidate` value among its fetches controls when the route becomes eligible for regeneration; each fetch still keeps its own data-cache policy. A fetch with `revalidate: 0` or `cache: 'no-store'` makes the route dynamically rendered rather than ISR output. An HTTP/CDN cache can add another freshness window, but response headers alone do not create an ISR runtime.

On-demand ISR requests do not execute `proxy.ts`, so invalidate the actual route path after rewrites. On self-hosted multi-instance deployments, the default filesystem cache is per instance; a shared cache handler is needed when invalidation must coordinate across instances. Test the adapter and CDN that will serve production traffic.

The Pages Router has an explicit `getStaticPaths` fallback setting. App Router uses `generateStaticParams` with `dynamicParams` instead:

| Pages Router `fallback` | Unbuilt route behavior |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| `false` | Return 404 |
| `true` | Serve a fallback state while generating; client navigation and bots have additional behavior |
| `'blocking'` | Generate on first request, then respond with the completed page |

Do not transfer this table mechanically to the App Router; its route and loading boundaries use different conventions.

### 3. Verify the Production Behavior

Run a production build and server (`next build` followed by `next start`, or the target deployment adapter). Warm a route, change its source record, observe a request after the interval, and confirm that the old successful output is served while regeneration runs. Then test a successful refresh, a failing refresh, an unbuilt ID, webhook replay, rewritten paths, and more than one instance when production uses them.

Where available, inspect `x-nextjs-cache` (`HIT`, `STALE`, `MISS`, or `REVALIDATED`) alongside source age, backend reads, refresh duration, and failures. A configured TTL is not a measured freshness guarantee; traffic, failed refreshes, adapter behavior, and CDN policy all affect what visitors receive.

## Real-World Use Cases

ISR fits public content whose age can be bounded: product descriptions, published articles, documentation, or category pages. Choose the interval from the tolerated staleness and origin capacity, then add on-demand invalidation when a publish or withdrawal event needs a quicker refresh. Recheck authoritative values such as stock, account permissions, or a job's active status at the operation that depends on them.

Keep user-specific pages request-time and authorized unless a verified per-identity cache design makes shared reuse safe. A route ID being unique does not authorize every visitor to see the record at that path.

## Summary

ISR reuses public route output and regenerates it in response to later traffic. Time-based expiry only makes output eligible; a request starts the work. On-demand invalidation marks selected data or paths for later refresh, and each API has its own stale-versus-fresh contract. Choose what may be stale, preserve the last successful version on failure, and verify the runtime and cache topology that production will use.

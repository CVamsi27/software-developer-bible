# Incremental Static Regeneration (ISR)

## Definition

**Incremental Static Regeneration (ISR)** reuses generated pages and updates them after deployment without rebuilding the entire application. Pages can be generated at build time, then served from a cache. Under time-based revalidation, expiry makes a page eligible for regeneration; a later request can trigger the background work. Visitors may receive the previous successful page while that work runs. This is **stale-while-revalidate**: serve the stored result while preparing its replacement. Refresh triggers and blocking behavior depend on the route and revalidation API.

> **Textbook Definition:** Incremental static regeneration refreshes previously generated route output through a supported server runtime. Time-based or explicit invalidation determines refresh eligibility; failed regeneration can leave the last successful output available.


## First Principles

A catalog has more pages than a build can reasonably render, and descriptions can change after deployment. Reusing completed output needs a way to create missing pages and replace obsolete ones.

1. **Stored output avoids another render only while it remains acceptable.** Define a tolerated age and which data must be checked at the authoritative operation instead, such as price at checkout.
2. **A clock cannot fetch new data by itself.** Under request-driven revalidation, expiry changes eligibility; a visit starts work. Lack of traffic or a failed refresh can keep output older than the interval.
3. **A completed write knows what changed.** Its invalidation signal can target affected routes/tags sooner than periodic eligibility, but the chosen API still decides whether readers see stale data or wait for a replacement.

## Why It Matters

Senior engineers use ISR for: large content sites (e-commerce catalogs, blogs), pages with mostly-static data, and reducing origin load. They know the failure modes: stale data between revalidations, build-time fetch errors blocking deploys, and the need for cache tags for fine-grained invalidation.

## How It Works

**Version scope:** This chapter uses the Next.js 15-style ISR model, also supported in 16 with Cache Components disabled. ISR needs a runtime that supports regeneration (Node.js for the standard server); it is unavailable in pure static export and the Edge runtime. A CDN may sit in front of the server, but ISR's route/data stores are framework/host concerns rather than an automatic universal edge cache.

Time-based expiry is request-driven, not a scheduled job. On-demand path invalidation from a Route Handler marks the route for regeneration on its next visit; it does not eagerly regenerate every affected page during the webhook. `generateStaticParams` runs at build time and is not rerun during ISR. For a static route containing several cached fetches, the lowest revalidation interval governs the route regeneration; the individual data entries retain their own caching policy.

### Trace the last successful version

Assume `/products/123` already has version A and a 60-second interval:

| Event | Visitor result | Server work |
| ---------------------------------------- | ---------------------------------- | ----------------------------------- |
| Request before expiry | A | Reuse stored output |
| Request after expiry | A while eligible refresh starts | Read source and prepare replacement |
| Refresh succeeds with B | Later requests receive B | Replace successful stored output |
| Refresh fails | A remains usable | Retry on a later request |
| First visit to an ungenerated allowed ID | Wait for initial successful output | No previous version exists to serve |

The framework's Data Cache and Full Route Cache participate in this model; an optional HTTP/CDN cache has its own policy. A response header does not itself install a regeneration runtime. [Caching](10.4.3.03-caching.md) owns the layer definitions and invalidation API choices.

## Code Examples

### 1. Basic ISR with revalidate

```typescript
// app/products/[id]/page.tsx
export async function generateStaticParams() { return []; } // Generate initially on demand

interface ProductPageProps {
  params: Promise<{ id: string }>;
}

async function getProduct(id: string) {
  const res = await fetch(`https://api.example.com/products/${encodeURIComponent(id)}`, {
    next: { revalidate: 60 },
  });
  if (!res.ok) throw new Error('Product fetch failed');
  return res.json();
}

export default async function ProductPage({ params }: ProductPageProps) {
  const { id } = await params;
  const product = await getProduct(id);

  return (
    <div>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <p>Price: ${product.price}</p>
      <p className="text-sm text-gray-500">
        Price updated at: {new Date(product.updatedAt).toLocaleString()}
      </p>
    </div>
  );
}
```

```typescript
// This generates static pages + ISR at request time
// Both of these are App Router options with Cache Components disabled:

// Option A: revalidate in fetch
fetch('https://api.example.com/products/123', {
  next: { revalidate: 60 }, // ISR with 60-second revalidation

// Option B: Segment config

```

### 2. ISR with Dynamic Params (generateStaticParams)

```typescript
// app/products/[id]/page.tsx
interface ProductPageProps {
  params: Promise<{ id: string }>;
}

// Pre-generate popular products at build time
export async function generateStaticParams() {
  const response = await fetch('https://api.example.com/products');
  if (!response.ok) throw new Error('Product list unavailable');
  const products = await response.json();

  // Pre-generate only top 100 products
  return products.slice(0, 100).map((product: { id: string }) => ({
    id: product.id,
  }));
  // Non-pre-generated IDs will be generated on first visit (ISR fallback)
}

// Eligible for request-driven regeneration after 60 seconds
export const revalidate = 60;

export default async function ProductPage({ params }: ProductPageProps) {
  const { id } = await params;

  const product = await fetch(
    `https://api.example.com/products/${encodeURIComponent(id)}`,
    { next: { revalidate: 60 } } // Per-fetch revalidation
  ).then(async r => {
    if (!r.ok) throw new Error('Product unavailable');
    return r.json();
  });

  return (
    <div>
      <h1>{product.name}</h1>
      <p>Price: ${product.price}</p>
      <p>Generated at: {new Date().toISOString()}</p>
    </div>
  );
}
```

### 3. On-Demand Revalidation

> [Caching](10.4.3.03-caching.md#invalidate-after-the-authoritative-write) owns the cache model and invalidation freshness policy. On Next.js 15 its single-argument tag API expires entries; on 16 use `revalidateTag(tag, 'max')` for stale-while-revalidate, `{ expire: 0 }` for an immediate-expiry webhook, or action-only `updateTag` for read-your-writes.

### 4. Tag-Based Revalidation

```typescript
// lib/api.ts — Tagged fetch helpers
interface FetchOptions {
  tags?: string[];
  revalidate?: number;
}

async function fetchWithCache<T>(
  url: string,
  options?: FetchOptions
): Promise<T> {
  const res = await fetch(url, {
    next: {
      revalidate: options?.revalidate ?? false,
      tags: options?.tags ?? [],
    },
  });

  if (!res.ok) throw new Error(`Fetch failed: ${url}`);

  return res.json();
}

// Usage in Server Components
export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params; // params is a Promise in Next.js 15+
  const product = await fetchWithCache<Product>(
    `https://api.example.com/products/${encodeURIComponent(id)}`,
    {
      tags: [`product-${id}`, 'products'],
      revalidate: 60,
    }
  );

  const reviews = await fetchWithCache<Review[]>(
    `https://api.example.com/products/${encodeURIComponent(id)}/reviews`,
    {
      tags: [`reviews-${id}`, 'reviews'],
      revalidate: 300, // Reviews can be more stale
    }
  );

  return (
    <div>
      <ProductDetail product={product} />
      <ReviewList reviews={reviews} />
    </div>
  );
}

// Next.js 16 policy helper, invoked only after verified/authorized mutation
import { revalidateTag, revalidatePath } from 'next/cache';
export function handleProductUpdate(productId: string) {
  // Mark data tagged product-123 for refresh; page rebuilding happens on access
  revalidateTag(`product-${productId}`, 'max');

  // Also revalidate the specific path
  revalidatePath(`/products/${encodeURIComponent(productId)}`);

  // Bulk revalidate all products
  revalidateTag('products', 'max');
}
```

### 5. Verify a CMS Signal Before Invalidating

```typescript
// app/api/cms-webhook/route.ts — Next.js 16; provider adapters are application code
import { revalidateTag, revalidatePath } from 'next/cache';
import { z } from 'zod';
import { verifyCmsSignature, acceptCmsEventOnce } from '@/lib/cms-webhook';

const eventSchema = z.object({
  eventId: z.string().min(1).max(100),
  model: z.enum(['product', 'category']),
  entry: z.object({ id: z.string().regex(/^[a-zA-Z0-9_-]{1,100}$/) }),
});

export async function POST(request: Request) {
  const rawBody = await request.text();
  const signature = request.headers.get('x-cms-signature');
  const secret = process.env.CMS_WEBHOOK_SECRET;
  if (!secret || !signature || !verifyCmsSignature(rawBody, signature, secret)) {
    return Response.json({ error: 'Invalid signature' }, { status: 401 });
  }
  let body: unknown;
  try { body = JSON.parse(rawBody); }
  catch { return Response.json({ error: 'Malformed JSON' }, { status: 400 }); }
  const parsed = eventSchema.safeParse(body);
  if (!parsed.success) return Response.json({ error: 'Invalid event' }, { status: 400 });
  const event = parsed.data;
  // Adapter durably coordinates acceptance and replay-safe invalidation/retry.
  await acceptCmsEventOnce(event.eventId, async () => {
    if (event.model === 'product') {
      revalidateTag(`product-${event.entry.id}`, 'max');
      revalidateTag('products', 'max');
      revalidatePath(`/products/${event.entry.id}`);
      revalidatePath('/products');
    } else {
      revalidateTag(`category-${event.entry.id}`, 'max');
      revalidateTag('categories', 'max');
      revalidatePath('/categories');
    }
  });
  return Response.json({ accepted: true });
}
```

This is a provider-adapter sketch, not a universal CMS signature implementation. Verification must use the provider's algorithm, raw bytes and replay/timestamp contract. `acceptCmsEventOnce` must record durable success after its callback succeeds, or arrange retryable work; marking an event completed before invalidation can lose its signal. Enforce a request-body limit before buffering. The fixed model mapping allowlists tags/paths, and product routes use the same ID scheme as this chapter. Returning `accepted` does not prove every affected route has regenerated or every open browser has refreshed.

### 6. ISR with Conditional Revalidation

A bestseller list must update when a product enters **or leaves** its selection rule. Checking only `after.rating > 4.5` misses a drop from 4.8 to 4.0: the old list can retain an ineligible item.

```typescript
import { revalidateTag } from 'next/cache';
type ProductSelection = { rating: number; isNew: boolean };
export function invalidateSelections(before: ProductSelection | null, after: ProductSelection | null) {
  if ((before?.rating ?? 0) > 4.5 || (after?.rating ?? 0) > 4.5) {
    revalidateTag('bestsellers', 'max');
  }
  if (before?.isNew || after?.isNew) revalidateTag('new-arrivals', 'max');
}
```

Use authoritative before/after values for updates, creation and deletion. If the event lacks the old state, conservatively invalidate the affected list tag rather than guessing. Changes to sorting, stock, permissions or displayed fields may also change a list even when membership stays the same.

### 7. ISR with Stale-While-Revalidate Headers

Next.js generates ISR page cache headers; changing a header in Middleware does not change the Data Cache interval or reliably override the framework's final page header. For an independent public HTTP endpoint, choose an explicit `Cache-Control` in a [Route Handler](../02-routing-and-middleware/10.4.2.02-route-handlers.md#route-handler-with-isr). Treat CDN TTL and route regeneration as separate settings.

### 8. ISR with Fallback Strategies

```typescript
// pages/products/[id].tsx — Pages Router (has explicit fallback)
import { GetStaticPaths, GetStaticProps } from 'next';

interface ProductPageProps {
  product: { id: string; name: string; price: number };
}

// Pre-generate some pages
export const getStaticPaths: GetStaticPaths = async () => {
  const response = await fetch('https://api.example.com/products');
  if (!response.ok) throw new Error('Product list unavailable');
  const products = await response.json();

  const paths = products.slice(0, 100).map((p: { id: string }) => ({
    params: { id: p.id },
  }));

  return {
    paths,
    // 'blocking': Wait for SSR on first request (SEO-friendly)
    // true: direct visits may show fallback; client navigation/crawlers block
    // false: Return 404 for non-pre-generated paths
    fallback: 'blocking',
  };
};

export const getStaticProps: GetStaticProps<ProductPageProps> = async ({ params }) => {
  const response = await fetch(`https://api.example.com/products/${encodeURIComponent(String(params!.id))}`);
  if (response.status === 404) return { notFound: true };
  if (!response.ok) throw new Error('Product unavailable');
  const product = await response.json();

  return {
    props: { product },
    revalidate: 60, // ISR
  };
};
```

### 9. ISR with Time-Based Cascading

```typescript
// app/posts/[slug]/page.tsx
// Different revalidation times for different sections
import { sanitizeCmsHtml } from '@/lib/sanitize-cms-html'

interface PostPageProps {
  params: Promise<{ slug: string }>;
}

export default async function PostPage({ params }: PostPageProps) {
  const { slug } = await params;

  // Core content — revalidate every 5 minutes
  const post = await fetch(`https://cms.example.com/posts/${encodeURIComponent(slug)}`, {
    next: { revalidate: 300, tags: [`post-${slug}`] },
  }).then(async r => {
    if (!r.ok) throw new Error('Content source unavailable');
    return r.json();
  });

  // Comments — revalidate every 30 seconds
  const comments = await fetch(`https://cms.example.com/posts/${encodeURIComponent(slug)}/comments`, {
    next: { revalidate: 30, tags: [`comments-${slug}`] },
  }).then(async r => {
    if (!r.ok) throw new Error('Content source unavailable');
    return r.json();
  });

  // CMS HTML is a stored-XSS vector — sanitize before injecting.
  // (Better: sanitize once when the CMS content is ingested, not per render.)
  const safeBody = sanitizeCmsHtml(post.body); // Application helper using a server-compatible HTML sanitizer.

  return (
    <article>
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: safeBody }} />
      <h2>Comments ({comments.length})</h2>
      <ul>{comments.map(c => <li key={c.id}>{c.text}</li>)}</ul>
    </article>
  );
}
```

In an eligible static route, the 30-second comments read makes the route eligible sooner than the 300-second post entry. The post may still reuse its longer-lived data. These reads are shown sequentially; because they depend only on the slug, start them together when latency matters. Server HTML timestamps describe generation, not the visitor's current time.

### 10. ISR with Incremental Adoption

```typescript
// app/page.tsx — Hybrid rendering: ISR + Client-side fetch
import { DailyDeals } from './daily-deals'; // Client module with its own data states

// ISR for the main page shell
export const revalidate = 3600; // 1 hour

export default async function HomePage() {
  // This data ISR-caches
  const categories = await fetch('https://api.example.com/categories', {
    next: { revalidate: 3600 },
  }).then(async r => {
    if (!r.ok) throw new Error('Content source unavailable');
    return r.json();
  });

  return (
    <div>
      <h1>Store</h1>
      <nav>
        {categories.map((cat: any) => (
          <a key={cat.id} href={`/category/${cat.slug}`}>{cat.name}</a>
        ))}
      </nav>

      {/* Browser data freshness depends on its fetch/cache policy */}
      <DailyDeals /> {/* Effect-based fetching uses this component's pending/error state. */}
    </div>
  );
}
```

## Real-World Use Cases

| Use Case | Revalidation Strategy | Why ISR |
| ---------------------------------- | ----------------------------------- | ---------------------------------------------------------------------- |
| **E-commerce product pages** | Chosen interval plus write signals | Share descriptions; checkout rechecks current price/stock |
| **Blog/News articles** | Chosen interval plus publish signal | Refresh completed content without rebuilding every page |
| **Documentation site** | Interval or verified update signal | Public content with an explicit tolerated age |
| **Marketing pages** | 86400s (1 day) | Rare changes, instant load |
| **Public aggregate dashboard** | Interval chosen for tolerated age | Shared aggregate only; regeneration still consumes server work |
| **Category/Listing pages** | 60s + on-demand on stock change | Fresh inventory, high traffic |
| **Job listings** | 300s | Balances freshness vs CDN hit rate |
| **Time-sensitive displays** | Product-specific freshness contract | Label age; operations requiring current values must recheck the source |

## Common Mistakes

### 1. Over-Revalidating

```typescript
// BAD: Revalidating too frequently negates ISR benefits
export const revalidate = 1; // Eligible after one second; not a one-second timer!
// Compare measured regeneration work and tolerated staleness with request rendering.

// GOOD: Use longer intervals + on-demand for freshness
export const revalidate = 300; // 5 minutes
// Plus on-demand revalidation via webhooks
```

### 2. Forgetting On-Demand Revalidation

```typescript
// BAD: Time-based only — users see stale data until window expires
export const revalidate = 3600; // 1 hour stale!

// GOOD: Mark content stale/expired on a write instead of waiting for its timer
// Call this from CMS webhooks
await revalidatePath('/products/123');
revalidateTag('product-123', 'max'); // Next.js 16 stale-while-revalidate policy
```

### 3. Not Handling Missing Data

If background regeneration throws, Next.js retains the last successful page and retries on a later request. Catching the failure and returning an error placeholder counts as a successful render and may replace the useful cached page. Distinguish `404` from other failed responses, parse JSON, and let unexpected failures propagate to preserve stale output.

```typescript
const res = await fetch('https://api.example.com/data', { next: { revalidate: 60 } });
if (!res.ok) throw new Error('Upstream data unavailable');
const data = await res.json();
```

### 4. ISR with User-Specific Content

A route parameter is a cache key, so `/users/alice` and `/users/bob` are distinct routes; the danger is allowing every visitor to fetch the same cached private representation without authorization. Keep personal data behind a verified session and an uncached/request-time read. Never turn a user's private account page into shared ISR output merely to improve latency.

### 5. Not Using generateStaticParams for Large Sets

```typescript
// BAD: Letting ISR generate every page on first request
// First user for each product ID pays the cold-start penalty

// GOOD: Pre-generate popular pages
export async function generateStaticParams() {
  const popularProducts = await fetch('https://api.example.com/products/popular')
    .then(r => r.json());

  return popularProducts.map(p => ({ id: p.id }));
  // These are pre-built, others generate on-demand
}
```

## Best Practices

1. **Use on-demand revalidation** — Webhooks signal writes promptly; regeneration happens on access, don't rely only on time

2. **Match invalidation scope** — Tags group reused data; paths target routes; neither is always more granular

3. **Graceful degradation** — Handle API failures during revalidation (stale cache persists)

4. **Pre-generate an evidence-based popular subset** — Balance first-visit latency against build time

5. **Don't ISR user-specific pages** — Use SSR or client-side fetch for personalized content

6. **Set appropriate revalidation windows** — Align with your content update frequency

7. **Monitor revalidation rates** — Track how often pages are regenerating

8. **Verify each cache layer** — CDN caching and framework regeneration need compatible privacy/freshness policies

9. **Test cache invalidation** — Verify webhooks actually trigger revalidation

10. **Combine ISR with client-side fetching** — ISR for shell, client fetch for real-time data

## Performance Considerations

A revalidation interval cannot predict a cache-hit percentage or regeneration count without traffic distribution, number of active routes, misses, failures and host coordination. With 1,000 continuously visited routes and one successful regeneration per route per 60 seconds, the idealized average is about 1,000 regenerations per minute; sparse visits reduce it, retries and instances can add work. This is a capacity thought experiment, not a production measurement.

Verify with `next build` and `next start` (or the deployed adapter): warm a route, change source data, cross the interval, observe the stale response and eventual replacement, then make regeneration fail. Check an ungenerated ID and two replicas as separate cases. Track backend reads, served age, refresh duration and failures rather than reporting a configured TTL as measured freshness.

## Summary

ISR reuses successful shared output and replaces it under a regeneration policy. Time-based revalidation provides request-driven background refresh, while on-demand revalidation marks affected content for refresh on access. For maximum performance, pre-generate popular pages, use tag-based invalidation, and pair ISR with CDN caching for optimal cache hit ratios.

# Static Exports in Next.js

## Definition

**Static export** (`output: 'export'` + `next build`) is a Next.js feature that generates a fully static version of your application as HTML, CSS, and JS files — with no Node.js server required. The output can be served from any static file server, CDN, or hosting provider (S3, Nginx, GitHub Pages, Netlify). All pages are pre-rendered at build time, and Server Components and static GET Route Handlers can run at build time; request-time handlers, Server Actions, and Middleware/Proxy are unsupported.

> **Textbook Definition:** A static export produces route HTML and assets at build time for deployment without a Next.js application server. Features requiring per-request framework execution must be removed, replaced or provided by a separate service.


## First Principles

A static host can return an existing file, but it cannot run a Next.js request handler. That capability boundary determines what the build must provide.

1. **Every served page must already exist.** Enumerate dynamic route values during the build; an unknown value cannot trigger runtime generation.
2. **Visitor-specific server work needs another service.** Sessions, protected reads and mutations move to an authorized API rather than a missing Next server. A static shell may still contain interactive browser code.
3. **Content changes require a publication path.** Rebuild/deploy files or fetch from an external runtime. A cached JSON file is the build snapshot, not live data merely because a browser fetches it later.

## Why It Matters

Use a static export when every route can be produced at build time or in the browser and the host only needs to serve files. It removes the Next.js request runtime, so it also removes framework-managed authentication, request-time data access, mutations and regeneration.

## How It Works

`next export` was removed in Next.js 14: setting `output: 'export'` makes `next build` emit `out/` directly. Request-independent App Router GET handlers may export files at build time with `dynamic = 'force-static'`; request-dependent handlers, non-GET methods, and Pages Router API routes need a separate runtime.

In App Router dynamic segments, enumerate all intended values with `generateStaticParams` and use `dynamicParams = false`; `fallback` belongs to Pages Router's `getStaticPaths`. Exported browser JavaScript still performs client navigation and can call an external API. That API—not a hidden client component—must enforce access control for private data.

### Trace an exported product page

```text
Build: enumerate ID 42 → read product → render HTML → write out/products/42/
Host: request /products/42/ → existing index.html plus assets
Host: request unknown ID 99 → configured 404 (no Next runtime to generate it)
Browser: hydrate client controls → call separate authorized API if needed
```

Server Components execute during the build; their rendered output becomes public files. Never put private records or secrets in that output. Request-dependent handlers, Server Actions, Proxy, ISR and the default image optimizer require runtime support and are unavailable here. A request-independent static GET can export output when explicitly marked `dynamic = 'force-static'`. Client navigation and external data fetching remain possible because the browser still executes JavaScript.

The static host owns path mapping, redirects and response headers. An App Router `error.tsx` handles client/render failures in the emitted app; it is not a request-time HTTP 500 handler on that host.

## Code Examples

### 1. Basic Static Export Configuration

```typescript
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  output: 'export', // Enables static export mode

  // Optional: configure export settings
  // Keep framework build output settings separate from the exported files.

  // Disable image optimization (requires server)
  images: {
    unoptimized: true,
  },

  // Optional: ensure trailing slash for static hosting
  trailingSlash: true,

};

export default nextConfig;
```

```bash
# Build and export
npm run build
# or
npx next build

# Output goes to ./out/
ls out/
# 404.html index.html _next/ products/
```

### 2. Using generateStaticParams for Dynamic Routes

```typescript
// app/products/[id]/page.tsx
interface ProductPageProps {
  params: Promise<{ id: string }>;
}

// Pre-generate ALL product pages at build time
export const dynamicParams = false; // No request-time generation in export mode

export async function generateStaticParams() {
  const products = await fetch('https://api.example.com/products')
    .then(async r => {
      if (!r.ok) throw new Error('Build data unavailable');
      return r.json();
    });

  return products.map((product: { id: string }) => ({
    id: product.id,
  }));
}

// During static export, this runs at BUILD TIME
export default async function ProductPage({ params }: ProductPageProps) {
  const { id } = await params;

  // Data fetching happens at build time
  const product = await fetch(`https://api.example.com/products/${encodeURIComponent(id)}`)
    .then(async r => {
      if (!r.ok) throw new Error('Build data unavailable');
      return r.json();
    });

  return (
    <div>
      <h1>{product.name}</h1>
      <p>Price: ${product.price}</p>
    </div>
  );
}
```

### 3. Emit a static GET resource

```typescript
// app/catalog.json/route.ts
export const dynamic = 'force-static';

export async function GET() {
  const catalog = await loadBuildTimeCatalog(); // Application adapter; result becomes a public file.
  return Response.json(catalog);
}
```

Only `GET` Route Handlers can be exported. The request cannot affect the result; accessing `Request`, cookies or headers requires a runtime and is incompatible with export mode.

### 4. Static Export with Client-Side Data

```typescript
// app/dashboard/page.tsx — Static shell + client-side public data
import { DashboardData } from './DashboardData';
export const dynamic = 'force-static';

export default function DashboardPage() {
  return (
    <div>
      <h1>Dashboard</h1>
      <p>This shell is statically generated.</p>

      {/* Client component fetches live data */}
      <DashboardData />
    </div>
  );
}

// app/dashboard/DashboardData.tsx
'use client';

import { useState, useEffect } from 'react';

export const DashboardData = () => {
  const [data, setData] = useState<DashboardSnapshot | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(false);

  useEffect(() => {
    const controller = new AbortController();
    fetch('/data/products.json', { signal: controller.signal }) // Build-generated public snapshot, not a live API
      .then(r => { if (!r.ok) throw new Error('Data unavailable'); return r.json(); })
      .then((value: unknown) => { if (!controller.signal.aborted) setData(parseSnapshot(value)); })
      .catch(() => { if (!controller.signal.aborted) setError(true); })
      .finally(() => { if (!controller.signal.aborted) setLoading(false); });
    return () => controller.abort();
  }, []);

  if (loading) return <p role="status">Loading public catalog…</p>;
  if (error) return <p role="alert">Could not load the snapshot.</p>;
  return <div>{JSON.stringify(data)}</div>;
};
```

`DashboardSnapshot` and `parseSnapshot` are application-owned types/decoder. The example fetches `/data/products.json`, which the build script must write before `next build`; it is still the last deployed snapshot. For private or changing account data, use a separately deployed API with server-side authorization and the required CORS/session contract; never embed credentials in the bundle or generated JSON.

### 5. Custom 404 and Error Pages

```typescript
// app/not-found.tsx — Custom 404 page
// In static export, this generates 404.html
export default function NotFound() {
  return (
    <div style={{ textAlign: 'center', padding: 100 }}>
      <h1>404 — Page Not Found</h1>
      <p>The page you're looking for doesn't exist.</p>
      <a href="/">Go Home</a>
    </div>
  );
}

// app/error.tsx — Custom error page
'use client';

export default function Error({ reset }: { error: Error; reset: () => void }) {
  return (
    <div style={{ textAlign: 'center', padding: 100 }}>
      <h1>Something went wrong</h1>
      <button onClick={() => reset()}>Try Again</button>
    </div>
  );
}
```

### 6. Static Export with Images

```typescript
// next.config.ts
const nextConfig = {
  output: 'export',
  images: {
    unoptimized: true, // Alternative: loader: 'custom' + loaderFile for your CDN
  },
};

// Usage — works without optimization
import Image from 'next/image';

export default function StaticPage() {
  return (
    <Image
      src="/images/hero.jpg"
      alt="Hero"
      width={1200}
      height={600}
      preload // Next.js 16; older supported versions use priority
      // In static export, images are served as-is from /public
    />
  );
}
```

### 7. Pages Router paths must be known at build time

```typescript
// pages/products/[id].tsx — Pages Router
import { GetStaticPaths, GetStaticProps } from 'next';

export const getStaticPaths: GetStaticPaths = async () => {
  const products = await fetch('https://api.example.com/products')
    .then(async r => {
      if (!r.ok) throw new Error('Build data unavailable');
      return r.json();
    });

  const paths = products.map((p: { id: string }) => ({
    params: { id: p.id },
  }));

  return {
    paths,
    // In static export, ALL paths must be specified at build time
    // fallback: false is required (blocking not supported)
    fallback: false,
  };
};

export const getStaticProps: GetStaticProps = async ({ params }) => {
  const id = params?.id;
  if (typeof id !== 'string') return { notFound: true };

  const response = await fetch(
    `https://api.example.com/products/${encodeURIComponent(id)}`
  );
  if (response.status === 404) return { notFound: true };
  if (!response.ok) throw new Error('Product data unavailable during build');
  const product: unknown = await response.json();
  const parsedProduct = parseProduct(product); // Runtime decoder for the upstream contract.

  return {
    props: { product: parsedProduct },
    // revalidate is NOT supported in static export
  };
};
```

### 8. Generate a public JSON snapshot during the build

```typescript
// Generate static JSON files at build time
// app/api/data/route.ts can export a request-independent static GET;
// the public JSON script below is an alternative.

// Instead, generate .json files in /public during build:
// scripts/generate-data.ts
import { mkdirSync, writeFileSync } from 'fs';
import path from 'path';

async function generateStaticData() {
  const products = await fetch('https://api.example.com/products')
    .then(async r => {
      if (!r.ok) throw new Error('Build data unavailable');
      return r.json();
    });

  // Create the target directory before writing.
  mkdirSync(path.join(process.cwd(), 'public', 'data'), { recursive: true });
  writeFileSync(
    path.join(process.cwd(), 'public', 'data', 'products.json'),
    JSON.stringify(products)
  );

  console.log('Generated static data files for export');
}

generateStaticData();

// Then in package.json:
// "build": "tsx scripts/generate-data.ts && next build"
```

### 9. Serve files using the host's route mapping

```nginx
# nginx.conf — Serve static export
server {
    listen 80;
    server_name example.com;
    root /var/www/out;

    # Serve static files
    location / {
        try_files $uri $uri.html $uri/ =404;
    }

    # 404 fallback
    error_page 404 /404.html;
    location = /404.html {
        internal;
    }
}
```

## Real-World Use Cases

| Use Case | Why Static Export | Hosting |
| ---------------------- | ----------------------------------------------------- | ------------------------------ |
| **Documentation site** | Stable versioned content and search index | Any static host |
| **Marketing site** | Public content changes only on deployment | Object storage behind a CDN |
| **Portfolio** | Public pages and assets; no request-time account data | Any static host |
| **Knowledge base** | Build-time documents with optional browser search | Object storage or Nginx |

## Choose the Host by Its Routing Contract

Compare nested-path handling, custom 404 status, subpath deployment, HTTPS, redirects, response-header control, cache invalidation and current billing. A provider name or a blank feature-table cell does not establish that configuration. For a GitHub project site under `/repo`, configure the build's `basePath` and ensure links/assets resolve under that prefix; test direct visits and client navigation. Keep deployment workflow action and tool versions pinned and maintained for the chosen host.

## Common Mistakes

### 1. Using Unsupported Features

```typescript
// BAD: ISR in static export
export const revalidate = 60; // Error during export!

// BAD: A request-dependent or mutation Route Handler
// A request-independent GET with dynamic = 'force-static' can export.

// GOOD: Use static generation or client-side fetching
export async function generateStaticParams() { /* ... */ }
// Use client-side fetch for dynamic data
```

### 2. Missing generateStaticParams for Dynamic Routes

```typescript
// BAD: Dynamic route without generateStaticParams
// app/products/[id]/page.tsx
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params; // params is a Promise in Next.js 15+
  return <div>Product {id}</div>;
}
// Error: Dynamic routes need generateStaticParams in static export

// GOOD: Specify all paths
export async function generateStaticParams() {
  return [{ id: '1' }, { id: '2' }, { id: '3' }];
}
```

### 3. Forgetting to Configure Images

```typescript
// BAD: Default image optimization (requires server)
// Build will fail with: Image Optimization requires a server

// GOOD: Disable image optimization
// next.config.ts
const nextConfig = {
  output: 'export',
  images: { unoptimized: true },
};
```

## Best Practices

1. **Use `generateStaticParams` for dynamic App Router paths** — every path the export should serve must be produced at build time; unknown IDs cannot render later
2. **Choose an export-compatible image path** — Use unoptimized images or a supported external custom loader
3. **Use client-side fetching for dynamic data** — Fetch JSON from `/data/*.json` or external APIs
4. **Generate static JSON files during build** — Write data to `/public` before export
5. **Match path shape to the host** — Choose trailing-slash/file mapping and test nested direct visits
6. **Add and test the 404 route** — the host must serve the emitted `404.html` with the intended status
7. **Test export locally** — Use `npx serve out/` before deploying
8. **Consider incrementally adopting** — Start with static pages, add client-side data as needed

Inspect the emitted output with `du -sh out/` and `tree out/`, then test direct visits to nested routes and missing paths on the intended static host. Serving the folder locally does not verify that the production host maps `/route/` or `/route.html` correctly.

## Summary

- Static exports generate static HTML/CSS/JS without a Next request-time server
- Request-time APIs, middleware/Proxy, ISR, Server Actions, and the default image optimizer are unsupported
- App dynamic routes enumerate `generateStaticParams` and disable unknown params; Pages Router uses `getStaticPaths` with `fallback: false`
- Server data fetching happens during the build; browser fetching happens after load
- The host must map deep links, subpaths and not-found paths to the emitted files correctly

# Authentication in Next.js

A request for /reports/42 carries a cookie, but that cookie alone does not establish who the caller is or whether they may read that report. A secure Next.js app verifies a session, resolves the current account, and checks access where the data is read or changed.

```typescript
// lib/reports.ts — authorize beside the data, never in the layout alone
import 'server-only';

export async function getVisibleReport(reportId: string) {
  const principal = await requireCurrentPrincipal(); // verified session or throw
  return db.report.findFirst({
    where: { id: reportId, tenant: { members: { some: { userId: principal.id } } } },
    select: { id: true, title: true, summary: true },
  });
}
```

## Definition

**Authentication** verifies a caller's identity. **Session management** carries that identity across requests. **Authorization** decides whether the authenticated principal may perform a particular operation on a particular resource.

> **Textbook Definition:** Authentication establishes a principal from verified credentials; session management preserves that principal across requests; authorization evaluates the principal, operation, resource, and current policy before access is granted.

## First Principles

A URL is only one entry point to protected data — the same operation may arrive through a Route Handler, Server Action, prefetched navigation, or direct request. So **a presented credential must be verified**: a cookie is input, not proof — validate the token or look up the opaque session. **A valid identity is not a permission**: resolve account state, tenant membership, and resource policy before returning or changing data. **A session has a revocation delay**: define behavior after expiry, logout, disablement, role change, or theft. **A shared response has shared readers**: personalized output must never enter a public cache unless its key and policy isolate every reader.

## How It Works

### 1. Use Proxy for Navigation Feedback

In Next.js 16, Proxy runs before route rendering and can send an anonymous browser to sign-in. A cookie-presence check is only an optimistic routing hint; it must not be the application's access-control check.

```typescript
// proxy.ts — early redirect only
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  if (request.cookies.get('session')?.value) return NextResponse.next();

  const login = new URL('/login', request.url);
  login.searchParams.set(
    'callbackUrl',
    request.nextUrl.pathname + request.nextUrl.search,
  );
  return NextResponse.redirect(login);
}

export const config = {
  matcher: ['/dashboard/:path*', '/admin/:path*'],
};
```

Validate callback URLs as same-origin relative paths before redirecting after sign-in. Keep Proxy cheap: it can run on prefetched requests, and it does not protect Route Handlers or Server Actions excluded by its matcher. Next.js 15 and earlier use the Middleware convention; Next.js 16 uses Proxy on Node.js.

### 2. Authorize Beside the Data

```text
Cookie or bearer credential
  → verify signature / expiry or load active session
  → resolve current principal and account status
  → authorize operation against tenant and resource
  → return a minimal DTO or commit the mutation
```

Put session verification and resource checks in a server-only data-access layer. Do not rely on a shared layout alone: layouts can remain mounted during client navigation. Do not treat hiding an admin button as permission enforcement.

```typescript
// lib/reports.ts — ORM relation names are application-specific
import 'server-only';
import { requireCurrentPrincipal } from '@/lib/session';
import { db } from '@/lib/database';

export async function getVisibleReport(reportId: string) {
  const principal = await requireCurrentPrincipal();

  const report = await db.report.findFirst({
    where: {
      id: reportId,
      tenant: {
        members: {
          some: { userId: principal.id, active: true },
        },
      },
    },
    select: { id: true, title: true, summary: true },
  });

  // A null result can avoid disclosing whether another tenant owns the ID.
  return report;
}
```

The session helper must reject invalid, expired, revoked, or disabled identities and return current permission data. Scope the query by tenant and resource permission, then select only fields the caller may see. For HTTP APIs, 401 means there is no valid identity; 403 means the identity is known but lacks permission. Some systems return 404 to conceal a resource's existence.

Each Route Handler and Server Action must perform its own checks, even when Proxy or a page already checked. React cache can deduplicate a session helper during one Server Component render; it does not memoize Route Handler or Server Action calls. For token formats, cookie semantics, OAuth, and role-policy models, use the linked backend chapters rather than copying a second implementation here.

### 3. Choose Session Storage from the Revocation Requirement

| Session form | What the server stores | Main trade-off |
| --------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Opaque ID with a database/session store | Active session and its expiry | Central revocation and device management; protected reads depend on the store |
| Signed or encrypted token | Claims and expiry carried by the credential | Fewer lookups; copied tokens and stale role claims remain valid until expiry or a revocation check |

Deleting a browser cookie ends that browser's session presentation; it does not revoke a copied self-contained token. Use bounded lifetimes, rotation, or a server-side revocation check when immediate invalidation matters. A signed role claim is a snapshot, so resolve current permissions for sensitive operations.

### 4. Issue and Clear Credentials Safely

A login flow should validate the submitted shape at runtime, rate-limit by normalized account and trusted client signal, verify a password hash, return a generic failure, then create the chosen session. Do not store raw passwords, bearer tokens, or reusable credentials in localStorage. Password verification and recovery policies belong to the authentication service; see [Authentication Fundamentals](../../../20-backend/20.5-security/01-auth/20.5.1.01-auth-fundamentals.md).

Set browser session cookies on the server with HttpOnly, Secure in production, an explicit SameSite policy, Path, and bounded expiry. HttpOnly prevents JavaScript from reading the credential; injected script can still issue requests as the visitor or read data the page exposes. Refresh or clear identity-scoped client state after sign-in, sign-out, or account change.

### 5. Protect Mutation Entry Points from CSRF

Server Actions are network-callable mutation endpoints. Next.js checks their Origin against the host by default, but that check does not authorize a user or protect arbitrary cookie-authenticated Route Handlers. For custom browser mutations, validate Origin against a configured trusted application origin or use the authentication library's session-bound CSRF token. SameSite cookies are defense in depth, not a substitute for resource authorization. Webhooks and bearer-authenticated machine clients need their own signature or credential policy.

A return path from a query parameter is also untrusted input. Allow only intended same-origin paths; otherwise a correct login can become an open redirect.

### 6. Keep Client Session State in Its Lane

A React context or library hook can show loading, sign-in, and sign-out feedback in Client Components. Server Components cannot read that client context, and client state cannot authorize data. Resolve identity on the server for protected reads and writes.

After a cookie changes, refresh the server-rendered tree and clear or partition client query caches by identity. A client generation counter can ignore stale UI responses, but it cannot order competing Set-Cookie responses; serialize account-changing operations and define cross-tab sign-out behavior.

### 7. Pin the Integration and Verify the Trust Boundary

For production, prefer a maintained authentication library or hosted identity service when its provider, adapter, runtime, recovery, MFA, and data-location contracts fit. As of October 2026, Auth.js lists NextAuth.js v4 in maintenance mode and v5 as beta; pin the selected release and matching adapter, then verify its support status before adoption.

The App Router integration shapes differ:

```typescript
// Imports and options omitted; this shows the NextAuth.js v4 route export shape.
const handler = NextAuth(options);
export { handler as GET, handler as POST };

// Auth.js v5: handlers and server helpers returned from configuration
export const { handlers, auth } = NextAuth(options);
// In app/api/auth/[...nextauth]/route.ts:
// export const { GET, POST } = handlers;
```

Do not mix a v4 adapter or session assumptions with a v5 configuration. Library-managed login flows have their own CSRF behavior; custom mutation endpoints still need their own policy.

Test direct requests, not only page navigation:

- Anonymous and expired sessions cannot read protected data.
- A valid user in another tenant cannot read or mutate the resource.
- Disabled accounts and changed roles follow the promised revocation delay.
- Foreign-origin cookie mutations fail; expected same-origin actions still work.
- Logout clears the active browser state, and copied-token behavior matches the chosen revocation model.
- Sign-in and sign-out do not leave another account's cached UI visible.

## Summary

Authentication in Next.js connects a verified session to current resource permissions. Use Proxy only for early routing feedback, enforce authorization in the data-access layer and every mutation endpoint, and choose a session model whose revocation delay is acceptable. Keep browser context for user experience, isolate personalized caches, and test direct requests across tenant, role, expiry, and logout boundaries.

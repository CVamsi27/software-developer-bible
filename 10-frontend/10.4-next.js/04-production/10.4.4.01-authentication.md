# Authentication in Next.js

## Definition

**Authentication** in Next.js involves verifying user identity and managing access to protected resources across different rendering strategies (SSR, SSG, CSR, ISR). Next.js supports authentication through middleware/Proxy for optimistic route redirects, server components for server-side session validation, client components for client-side auth state, and API route handlers for token issuance and verification.

> **Textbook Definition:** Authentication establishes a principal's identity, and session management carries that identity across requests. Authorization then decides whether that principal may perform a specific operation on a resource.


## First Principles

A dashboard URL and its data endpoint are two ways to reach protected information. Hiding one path leaves the other reachable.

1. **Every protected operation needs a principal.** A cookie is only presented input; validate the session's signature/expiry or look it up in a trusted store before using its identity.
2. **Identity does not imply permission.** After identifying Alice, check whether Alice may read this account or mutate this record. Enforce this near the data operation so direct calls, prefetch and alternate navigation cannot bypass it.
3. **A remembered identity can outlive its authority.** Decide how expiry, logout, stolen tokens, disabled accounts and role changes take effect. A signed role claim is a snapshot; immediate changes need an authoritative check or revocation design.
4. **Shared output has shared readers.** Do not cache one visitor's private representation as public route output. Server execution and an HTTP-only cookie do not by themselves prevent serialized-data or cache leaks.

## Why It Matters

Senior engineers design auth that works across SSR, RSC, and CSR. They use middleware for redirects, server components for protected data fetching, and libraries like Auth.js (NextAuth), Clerk, or custom JWT. They know to never trust client-side auth checks and to use HTTP-only cookies for sessions.

## How It Works

**Version scope:** The custom routing examples use Next.js 15 middleware; in 16 rename the entry point/export to Proxy, which runs on Node.js. Cookie-presence checks are optimistic UX only: a visitor can forge an arbitrary cookie, so never treat presence as authentication. Verify signature/expiry and current account/resource permissions close to each protected read/write.

The integration below is explicitly **NextAuth.js v4** (`NextAuth(options)` returning a handler), not Auth.js v5's `handlers/auth/signIn/signOut` configuration. Use the adapter package matching the pinned auth version, add TypeScript module augmentation for custom `id`/`role` fields, and put `SessionProvider` in a client wrapper. JWT sessions are possible without a database, while database sessions and persisted users/accounts need an adapter.

Clearing a JWT cookie logs this browser out but does not revoke a stolen token; choose short expiry, rotation, or server revocation checks for that requirement. The custom login/context example uses consistent user fields and relies on a session endpoint that verifies the cookie rather than echoing a client token.

### Trace a forged cookie versus a valid session

```text
Browser presents session-token → optional early redirect checks presence
Protected read → verify token/store session → resolve current principal
               → authorize resource → return only permitted fields
Client context → displays that result; cannot grant access itself
```

A forged nonempty cookie can pass the early presence gate but fails verification at the protected read. A valid token for a downgraded administrator can still contain the old role; resolve current permissions when prompt revocation is required. Logout clears this browser's cookie, but a copied JWT remains usable until expiry or server-side revocation rejects it.

A stateful session stores an opaque session ID and consults its record. A JWT can be verified without that lookup, but adds token-size, stale-claim and revocation tradeoffs. Either approach can scale with suitable infrastructure; neither is restricted to SSR, SPA or Edge. An HTTP-only cookie blocks direct JavaScript token reads while CSRF/XSS defenses and authoritative resource checks remain necessary.

## Code Examples

### 1. Auth Middleware (Route Protection)

```typescript
// middleware.ts — root of project
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(request: NextRequest) {
  const sessionToken = request.cookies.get('session-token')?.value;
  const { pathname } = request.nextUrl;

  // Public routes (no auth required)
  const publicRoutes = ['/login', '/register', '/forgot-password', '/api/auth'];
  const isPublicRoute = publicRoutes.some(route => pathname === route || pathname.startsWith(route + '/'));

  // Static files and assets
  const isStaticAsset = (pathname === '/_next' || pathname.startsWith('/_next/')) ||
    (pathname === '/static' || pathname.startsWith('/static/')) ||
    pathname === '/favicon.ico';

  // Allow access to public routes and static assets
  if (isPublicRoute || isStaticAsset) {
    // A present cookie is not enough to redirect away from login.
    return NextResponse.next();
  }

  // Protected routes — redirect to login
  if (!sessionToken) {
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('callbackUrl', pathname);
    return NextResponse.redirect(loginUrl);
  }

  return NextResponse.next();
}

export const config = {
  matcher: [
    '/((?!_next/static|_next/image|favicon.ico).*)',
  ],
};
```

### 2. JWT Token Based Auth

```typescript
// lib/auth.ts — JWT utilities
import { SignJWT, jwtVerify } from 'jose';

const secret = process.env.JWT_SECRET;
if (!secret || new TextEncoder().encode(secret).length < 32) {
  throw new Error('JWT_SECRET must be a high-entropy secret of at least 32 bytes');
}
const JWT_SECRET = new TextEncoder().encode(secret);

export interface JWTPayload {
  userId: string;
  email: string;
  role: 'user' | 'admin' | 'superadmin';
}

export async function createToken(payload: JWTPayload): Promise<string> {
  return new SignJWT({ ...payload })
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuer('my-app')
    .setAudience('my-app-session')
    .setIssuedAt()
    .setExpirationTime('7d')
    .sign(JWT_SECRET);
}

export async function verifyToken(token: string): Promise<JWTPayload | null> {
  try {
    const { payload } = await jwtVerify(token, JWT_SECRET, {
      algorithms: ['HS256'], issuer: 'my-app', audience: 'my-app-session',
      requiredClaims: ['exp', 'iat', 'iss', 'aud'],
    });
    if (typeof payload.userId !== 'string' || typeof payload.email !== 'string' ||
        !['user', 'admin', 'superadmin'].includes(String(payload.role))) return null;
    return payload as unknown as JWTPayload;
  } catch {
    return null;
  }
}

// app/api/auth/login/route.ts — Login API
import { z } from 'zod';
import { requireSameOrigin } from '@/lib/csrf';
import { NextResponse } from 'next/server';
import { cookies } from 'next/headers';
import { createToken } from '@/lib/auth';

export async function POST(request: Request) {
  const forbidden = requireSameOrigin(request);
  if (forbidden) return forbidden;
  let body: unknown;
  try { body = await request.json(); }
  catch { return NextResponse.json({ error: 'Malformed JSON' }, { status: 400 }); }
  const parsed = z.object({
    email: z.string().email().max(254), password: z.string().min(1).max(1000),
  }).safeParse(body);
  if (!parsed.success) return NextResponse.json({ error: 'Invalid input' }, { status: 400 });
  const { email, password } = parsed.data;

  // Verify credentials (replace with DB lookup)
  const user = await authenticateUser(email, password);
  if (!user) {
    return NextResponse.json(
      { error: 'Invalid credentials' },
      { status: 401 }
    );
  }

  // Create JWT
  const token = await createToken({
    userId: user.id,
    email: user.email,
    role: user.role,
  });

  // Set httpOnly cookie
  const response = NextResponse.json({
    user: { id: user.id, email: user.email, name: user.name, role: user.role },
  });
  response.cookies.set('session-token', token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    maxAge: 60 * 60 * 24 * 7, // 7 days
    path: '/',
  });

  return response;
}

// app/api/auth/logout/route.ts — Logout
export async function POST(request: Request) {
  const forbidden = requireSameOrigin(request);
  if (forbidden) return forbidden;
  const response = NextResponse.json({ success: true });
  response.cookies.delete('session-token');
  return response;
}
```

Each labeled file is separate and must import its used helpers. `authenticateUser` is an application adapter for bounded credential checks, password verification, account status and abuse controls. Validate environment keys at startup; length alone cannot establish entropy. This custom JWT is a teaching sketch, not a complete rotation/revocation/session system.

### 3. Server-Side Auth in Server Components

```typescript
// lib/server-auth.ts
import 'server-only';
import { resolveCurrentPrincipal } from '@/lib/current-principal'; // Authoritative account/role adapter
import { cookies } from 'next/headers';
import { verifyToken, JWTPayload } from '@/lib/auth';

export async function getServerSession(): Promise<JWTPayload | null> {
  const cookieStore = await cookies();
  const token = cookieStore.get('session-token')?.value;

  if (!token) return null;
  const claims = await verifyToken(token);
  return claims ? resolveCurrentPrincipal(claims.userId) : null;
}

// app/dashboard/page.tsx — Server Component
import { redirect } from 'next/navigation';
import { getServerSession } from '@/lib/server-auth';

export default async function DashboardPage() {
  const session = await getServerSession();

  if (!session) {
    redirect('/login');
  }

  // Fetch user-specific data
  const userData = await fetchUserData(session.userId);

  return (
    <div>
      <h1>Welcome back, {userData.name}!</h1>
      <p>Email: {session.email}</p>
      <p>Role: {session.role}</p>
      {/* Server-rendered dashboard content */}
      <UserDashboard data={userData} />
    </div>
  );
}

// app/admin/page.tsx — Role-based server component
export default async function AdminPage() {
  const session = await getServerSession();

  if (!session || !['admin', 'superadmin'].includes(session.role)) {
    redirect('/unauthorized');
  }

  return <AdminPanel />;
}
```

The current-principal adapter must reject disabled/revoked accounts and return current permitted identity fields. Authorize `fetchUserData` for the session's resource scope and return a safe projection. A signed snapshot can be enough only when its chosen revocation delay is acceptable; do not silently substitute it for current-role enforcement.

### 4. Client-Side Auth with Context

```typescript
// lib/auth-context.tsx
'use client';

import { createContext, useContext, useState, useEffect, useCallback, useRef } from 'react';
import { useRouter } from 'next/navigation';

interface User {
  id: string;
  email: string;
  name: string;
  role: 'user' | 'admin' | 'superadmin';
}

interface AuthContextType {
  user: User | null;
  loading: boolean;
  error: string | null;
  login: (email: string, password: string) => Promise<void>;
  logout: () => Promise<void>;
  isAuthenticated: boolean;
}

const AuthContext = createContext<AuthContextType | null>(null);

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [loading, setLoading] = useState(true);
  const router = useRouter();
  const [error, setError] = useState<string | null>(null);
  const generation = useRef(0);

  // Check session on mount
  useEffect(() => {
    const version = ++generation.current;
    let active = true;
    fetch('/api/auth/session')
      .then(async res => {
        if (!res.ok) throw new Error('Session check failed');
        return res.json();
      })
      .then(data => { if (active && version === generation.current) setUser(data.user ?? null); })
      .catch(() => { if (active && version === generation.current) setError('Could not check the session.'); })
      .finally(() => { if (active && version === generation.current) setLoading(false); });
    return () => { active = false; };
  }, []);

  const login = useCallback(async (email: string, password: string) => {
    const version = ++generation.current;
    setLoading(true); setError(null);
    try {
      const res = await fetch('/api/auth/login', {
        method: 'POST', headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ email, password }),
      });
      if (!res.ok) throw new Error('Sign-in failed');
      const data = await res.json();
      if (version !== generation.current) return;
      setUser(data.user); router.replace('/dashboard'); router.refresh();
    } catch {
      if (version === generation.current) setError('Could not sign in. Please try again.');
      throw new Error('Sign-in failed');
    } finally { if (version === generation.current) setLoading(false); }
  }, [router]);

  const logout = useCallback(async () => {
    const version = ++generation.current;
    setLoading(true); setError(null);
    try {
      const res = await fetch('/api/auth/logout', { method: 'POST' });
      if (!res.ok) throw new Error('Sign-out failed');
      if (version !== generation.current) return;
      setUser(null); router.replace('/login'); router.refresh();
    } catch {
      if (version === generation.current) setError('Could not sign out. Please try again.');
      throw new Error('Sign-out failed');
    } finally { if (version === generation.current) setLoading(false); }
  }, [router]);

  return (
    <AuthContext.Provider value={{
      user,
      loading,
      error,
      login,
      logout,
      isAuthenticated: !!user,
    }}>
      {children}
    </AuthContext.Provider>
  );
}

export function useAuth(): AuthContextType {
  const context = useContext(AuthContext);
  if (!context) {
    throw new Error('useAuth must be used within an AuthProvider');
  }
  return context;
}

// app/layout.tsx — Wrap app with AuthProvider
import { AuthProvider } from '@/lib/auth-context';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <AuthProvider>{children}</AuthProvider>
      </body>
    </html>
  );
}

// Usage in client component
const ProtectedPage = () => {
  const { user, loading, error, logout } = useAuth();

  if (loading) return <Spinner />;
  if (error) return <p role="alert">{error}</p>;
  if (!user) return <a href="/login">Sign in</a>;

  return (
    <div>
      <p>Welcome, {user.name}</p>
      <button type="button" onClick={() => { void logout().catch(() => {}); }}>Logout</button>
    </div>
  );
};
```

The session endpoint must verify the same cookie and return `{ user: null }` for an anonymous visitor, rather than echo a supplied token. Parse its response shape at the application boundary. The generation guard keeps late session/login completions from overwriting newer UI intent, but does not order concurrent cookie-setting responses or cancel server writes. Serialize authentication operations in the real UI, refresh/reset identity-scoped client caches on an account change, and handle tab-to-tab/logout synchronization explicitly.

### 5. NextAuth.js / Auth.js Integration

```typescript
// app/api/auth/[...nextauth]/route.ts
import NextAuth from 'next-auth';
import GithubProvider from 'next-auth/providers/github';
import GoogleProvider from 'next-auth/providers/google';
import CredentialsProvider from 'next-auth/providers/credentials';
import { PrismaAdapter } from '@next-auth/prisma-adapter'; // NextAuth.js v4 adapter
import { prisma } from '@/lib/prisma';

const handler = NextAuth({
  adapter: PrismaAdapter(prisma),
  providers: [
    GithubProvider({
      clientId: process.env.GITHUB_ID!,
      clientSecret: process.env.GITHUB_SECRET!,
    }),
    GoogleProvider({
      clientId: process.env.GOOGLE_CLIENT_ID!,
      clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
    }),
    CredentialsProvider({
      name: 'Credentials',
      credentials: {
        email: { label: 'Email', type: 'email' },
        password: { label: 'Password', type: 'password' },
      },
      async authorize(credentials) {
        if (!credentials?.email || !credentials?.password) return null;

        const user = await prisma.user.findUnique({
          where: { email: credentials.email },
        });

        if (!user) return null;

        const isValid = await verifyPassword(credentials.password, user.password);
        if (!isValid) return null;

        return { id: user.id, email: user.email, name: user.name, role: user.role };
      },
    }),
  ],
  session: { strategy: 'jwt', maxAge: 30 * 24 * 60 * 60 }, // 30 days
  pages: {
    signIn: '/login',
    error: '/auth/error',
  },
  callbacks: {
    async jwt({ token, user }) {
      if (user) {
        token.role = user.role;
        token.id = user.id;
      }
      return token;
    },
    async session({ session, token }) {
      if (session.user) {
        session.user.role = token.role as string;
        session.user.id = token.id as string;
      }
      return session;
    },
  },
});

export { handler as GET, handler as POST };

// components/AuthButtons.tsx — Client component
'use client';

export function AuthButtons() {

    );
  }

  return (
    <div>
      <button onClick={() => signIn('github')}>Sign in with GitHub</button>
      <button onClick={() => signIn('google')}>Sign in with Google</button>
    </div>
  );
}

// components/auth-session-provider.tsx (separate file)

}

}
```

### 6. Role-Based Access Control

```typescript
// lib/authorization.ts
import { getServerSession } from './server-auth';

type Role = 'user' | 'admin' | 'superadmin';

const roleHierarchy: Record<Role, number> = {
  user: 1,
  admin: 2,
  superadmin: 3,
};

export function hasRole(userRole: Role, requiredRole: Role): boolean {
  return roleHierarchy[userRole] >= roleHierarchy[requiredRole];
}

// Middleware-based RBAC
// middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';
import { verifyToken } from '@/lib/auth';

const routePermissions: Record<string, Role[]> = {
  '/admin': ['admin', 'superadmin'],
  '/admin/users': ['superadmin'],
  '/dashboard': ['user', 'admin', 'superadmin'],
};

export async function middleware(request: NextRequest) {
  const token = request.cookies.get('session-token')?.value;
  const { pathname } = request.nextUrl;

  if (!token) {
    return NextResponse.redirect(new URL('/login', request.url));
  }

  const payload = await verifyToken(token); // Early signed snapshot gate; current roles checked at data access
  if (!payload) {
    return NextResponse.redirect(new URL('/login', request.url));
  }

  // Check role-based access
  for (const [route, allowedRoles] of Object.entries(routePermissions).sort((a, b) => b[0].length - a[0].length)) {
    if (pathname === route || pathname.startsWith(route + '/')) {
      if (!allowedRoles.includes(payload.role as Role)) {
        return NextResponse.redirect(new URL('/unauthorized', request.url));
      }
      break;
    }
  }

  return NextResponse.next();
}

export const config = { matcher: ['/admin/:path*', '/dashboard/:path*'] };
```

### 7. API Route Protection

```typescript
// lib/api-auth.ts
import { NextResponse } from 'next/server';
import { verifyToken, JWTPayload } from '@/lib/auth';
import { resolveCurrentPrincipal } from '@/lib/current-principal';

export async function authenticateApi(
  request: Request
): Promise<{ payload: JWTPayload; response: null } | { payload: null; response: NextResponse }> {
  const authorization = request.headers.get('authorization');
  const token = authorization?.match(/^Bearer ([^\s]+)$/i)?.[1];

  if (!token) {
    return {
      payload: null,
      response: NextResponse.json(
        { error: 'Authentication required' },
        { status: 401 }
      ),
    };
  }

  const claims = await verifyToken(token);
  const payload = claims ? await resolveCurrentPrincipal(claims.userId) : null;
  if (!payload) {
    return {
      payload: null,
      response: NextResponse.json(
        { error: 'Invalid or expired token' },
        { status: 401 }
      ),
    };
  }

  return { payload, response: null };
}

// app/api/users/route.ts — Protected API route
import { NextResponse } from 'next/server';
import { authenticateApi } from '@/lib/api-auth';

export async function GET(request: Request) {
  const { payload, response } = await authenticateApi(request);
  if (response) return response; // Unauthorized

  // Only admins can list all users
  if (!['admin', 'superadmin'].includes(payload.role)) {
    return NextResponse.json(
      { error: 'Forbidden' },
      { status: 403 }
    );
  }

  const users = await fetchAllUsers();
  return NextResponse.json({ users });
}
```

This API sketch uses bearer credentials for non-cookie clients; the browser context above instead calls a cookie-based session endpoint. Do not expose the HTTP-only token to browser JavaScript to connect the two. Role-gated listing also needs tenant scope, bounded pagination and safe field projection.

### 8. CSRF Protection

Cookie-authenticated Route Handlers need their own CSRF policy; Next's Server Action origin checks do not automatically protect arbitrary handlers. For same-origin browser mutations, validate `Origin` against a configured trusted application origin and reject missing/foreign origins; bearer-authenticated webhooks require a separate signature policy.

```typescript
// lib/csrf.ts — called by each cookie-authenticated mutation handler
export function requireSameOrigin(request: Request) {
  const expected = process.env.APP_ORIGIN; // Canonical origin, not a client-supplied Host
  if (!expected) throw new Error('APP_ORIGIN must be configured');
  if (request.headers.get('origin') !== new URL(expected).origin) {
    return Response.json({ error: 'Invalid request origin' }, { status: 403 });
  }
  return null;
}

// app/api/profile/route.ts
export async function PATCH(request: Request) {
  const forbidden = requireSameOrigin(request);
  if (forbidden) return forbidden;
  // Verify session, validate fields, authorize resource ownership, then update.
  return Response.json({ success: true });
}
```

Where clients cannot supply a trusted Origin, use the auth library's session-bound CSRF token protocol. A reusable JWT saying `userId: 'csrf'` is not bound to a browser session and must not also be accepted as an authentication token.

## Real-World Use Cases

| Pattern | When to Use | Implementation |
| ---------------- | ------------------------ | -------------------------------------------- |
| **Simple Auth** | Small apps, prototypes | JWT in httpOnly cookie + middleware |
| **NextAuth.js** | Production apps, OAuth | Social login, credentials, database sessions |
| **Clerk/Auth0** | Enterprise, multi-tenant | Pre-built UI, MFA, SSO, user management |
| **Iron Session** | Server-rendered apps | Encrypted session cookies, no DB needed |
| **Custom JWT** | API-heavy apps | Stateless tokens, custom claims |

### Choose Session Ownership by Requirements

Compare revocation delay, current-role enforcement, OAuth/account linking, MFA, tenant isolation, recovery, audit events, data residency and operational ownership. A hosted provider changes who operates the identity system; custom code leaves more of those protocols to your team. Check current version support and provider capabilities rather than treating fixed setup-time, cost or provider-count claims as architectural evidence.

## Common Mistakes

### 1. Storing Tokens in localStorage

```typescript
// BAD: XSS vulnerable
localStorage.setItem('token', jwtToken);

// GOOD: httpOnly cookie (inaccessible to JavaScript)
// Server-side: Set cookie with httpOnly flag
response.cookies.set('session-token', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'lax',
});
```

### 2. Not Validating on Server

```typescript
// BAD: Client-only check
'use client';
const Dashboard = () => {
  const { user } = useAuth();
  if (!user) return null; // Hiding UI does not protect the endpoint or serialized data
  return <SensitiveData />;
};

// GOOD: Server-side validation
// Server Component validates before rendering
const Dashboard = async () => {
  const session = await getServerSession();
  if (!session) redirect('/login');
  return <SensitiveData userId={session.userId} />;
};
```

### 3. Mixing Rendering Strategies Incorrectly

```typescript
// BAD: Assuming session in SSG
export async function getStaticProps() {
  // SSG runs at build time — no user session!
  const session = await getSession(); // No incoming visitor request at build time
  return { props: { session } };
}

// GOOD: Use client-side fetching for SSG
// The page is static, session is checked client-side
```

### 4. Exposing Protected Data in Client Bundle

```typescript
// BAD: Server action returns too much data
async function getUserData() {
  return {
    id: 1,
    name: 'Alice',
    ssn: 'XXX-XX-XXXX', // Exposed!
    creditCard: 'XXXX', // Exposed!
  };
}

// GOOD: Only return what's needed
async function getUserProfile() {
  const user = await db.user.findUnique({ where: { id: userId } });
  return {
    name: user.name,
    email: user.email,
    // Only safe-to-expose fields
  };
}
```

## Best Practices

1. **Use httpOnly cookies** for token storage — blocks direct JS token reads; XSS can still issue requests as the user

2. **Validate on the server** — Always check auth in Server Components and API routes

3. **Choose and pin a maintained authentication integration** — Verify its actual version, adapter and session/CSRF contracts

4. **Redirect early** — Use middleware/Proxy for UX; authorize reads, handlers, and actions themselves

5. **Implement CSRF protection** — For mutations on cookie-based auth

6. **Handle token refresh** — Implement refresh token rotation for long sessions

7. **Rate limit auth endpoints** — Prevent brute force attacks

8. **Use secure headers** — Content-Security-Policy, Strict-Transport-Security

9. **Define expiry and revocation requirements** — Choose bounded lifetimes and rotation/revocation behavior for the application risk

10. **Audit auth flows** — Log login attempts and suspicious activity

## Summary

Authentication in Next.js spans middleware/Proxy (optimistic route redirects), Server Components (server-side session validation), and Client Components (auth state and UX). Use a version-pinned session integration, verify current identity and resource permission at protected reads/mutations, keep personalized caches scoped, and treat client auth state as presentation. Expiry, revocation, CSRF and concurrent account changes are part of the session contract.

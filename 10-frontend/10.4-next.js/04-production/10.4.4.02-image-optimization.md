# Image Optimization in Next.js

## Definition

Next.js provides an **Image component** (`next/image`) with responsive image delivery and default lazy loading. Its default optimizer can generate configured formats; dimensions and supported placeholder data help establish the initial layout. Correct sizing and loading policy can reduce layout shift and improve loading metrics, but using the component alone does not guarantee those outcomes.

> **Textbook Definition:** Image optimization selects and delivers an appropriate encoded image for the requested dimensions and supported formats. Responsive sizing, loading policy and cache identity govern the resulting bandwidth, layout stability and processing cost.


## First Principles

A 4,000-pixel photo can occupy a 400-pixel card. Sending the original wastes bytes, while omitting its geometry can move the page when it finishes loading.

1. **Displayed size and device density determine useful pixels.** A 400 CSS-pixel slot on a density-2 display may need roughly 800 source pixels. The browser chooses among available `srcset` candidates using `sizes`; the optimizer does not know the actual CSS layout by itself.
2. **Encoding and transformation consume work.** Smaller output can save network time, but a new variant needs processing unless prebuilt. Reuse transformed variants under a source/dimensions/quality/format identity.
3. **Layout must exist before the image arrives.** Intrinsic dimensions or a sized `fill` parent reserve space. Loading hints decide when bytes are requested; a blur preview is optional and does not reserve geometry on its own.

## Why It Matters

Senior engineers use `next/image` for LCP wins. They preload only the likely LCP image (`priority` in Next.js 15; `preload` in 16), use `sizes` for responsive images, configure `remotePatterns` for external CDNs, and customize the loader for non-Next-image backends. The interview question is: how does Next.js decide image dimensions? Answer: `width`/`height` props or parent's `fill`.

## How It Works

The default optimizer transforms requested image variants at request time, not during `next build`. `formats` defaults to WebP; AVIF needs explicit opt-in and the proxy must forward `Accept` for format negotiation. The actual byte savings depend on source content, dimensions, quality and encoding; measure the delivered variant.

`width`/`height` supply intrinsic aspect ratio; CSS determines displayed size. `sizes` tells the browser which candidate to request from `srcset`, so it must describe the actual layout, not simply copy breakpoints. `fill` requires a positioned parent with a defined size; `sizes` is particularly important there. Static image imports can supply dimensions and supported blur data automatically.

**Version scope:** Priority examples target Next.js 15; Next.js 16 deprecates `priority` in favor of `preload`. For 16 choose `preload`, eager loading, or `fetchPriority` deliberately rather than combining all hints. Long `minimumCacheTTL` values retain old image variants: there is no tag-based image invalidation API, so update the source URL/version when content changes.

### Follow one card image request

```text
CSS slot + device density → browser considers sizes/srcset candidates
Selected URL → optimizer/cache → resize/encode on a miss → image bytes
Reserved aspect ratio → stable slot while bytes arrive → decoded image
```

A `sizes` value claiming `100vw` for a one-third-width card can make the browser request a larger candidate than needed. Conversely, an understated value can produce a soft image on a dense display. The optimizer cache and a host CDN are separate deployment concerns; neither makes an unchanged source URL reflect an overwritten image immediately. Plain `<img>` can also use native responsive/lazy features—`next/image` packages those choices with the configured optimizer.

## Code Examples

### Basic Image Usage

```typescript
// app/page.tsx
import Image from 'next/image'

export default function Page() {
  return (
    <div>
      <h1>My Page</h1>
      <Image
        src="/hero.jpg"
        alt="Hero image"
        width={1200}
        height={600}
        priority
      />
    </div>
  )
}

```

### Remote Images

```typescript
// app/page.tsx
import Image from 'next/image'

export default function Page() {
  return (
    <Image
      src="https://example.com/photo.jpg"
      alt="Remote image"
      width={800}
      height={600}
    />
  )
}

```

```typescript
// next.config.js
module.exports = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'example.com',
      },
      {
        protocol: 'https',
        hostname: 'my-public-images.s3.amazonaws.com',
        pathname: '/catalog/**',
        search: '', // Reject arbitrary query variants when this source needs none
      },
    ],
  },
}

```

Allow only the intended image origin/path. A wildcard spanning other tenants' buckets expands which remote resources your optimizer will fetch. The default optimizer does not forward browser authorization headers; private sources need an explicitly authorized image-delivery design.

### Responsive Images

```typescript
// app/page.tsx
import Image from 'next/image'

export default function Page() {
  return (
    <Image
      src="/hero.jpg"
      alt="Hero image"
      width={1200}
      height={600}
      sizes="(max-width: 767px) 100vw, (max-width: 1279px) 50vw, 33vw"
      style={{ width: '100%', height: 'auto' }}
    />
  )
}

```

The responsive example assumes its parent is full width below 768px, half width until 1280px, and one-third width above it. `width: 100%` fills that parent, not necessarily the viewport. Account for container limits/gaps when specifying `sizes`, then inspect `currentSrc` at representative widths and pixel densities.

Blur metadata is generated from supported static imports, not enabled by `minimumCacheTTL`. A string path or remote URL needs its own small `blurDataURL`; a placeholder is optional and does not alter downloaded image quality.

  md: 48,

### Product Image with Zoom

```typescript
// components/product-image.tsx
'use client'

import { useState } from 'react'
import Image from 'next/image'

export function ProductImage({ src, alt }: { src: string; alt: string }) {
  const [isZoomed, setIsZoomed] = useState(false)

  return (
    <button
      type="button"
      aria-label={isZoomed ? 'Reset product image zoom' : 'Zoom product image'}
      aria-pressed={isZoomed}
      className="relative overflow-hidden"
      onClick={() => setIsZoomed(value => !value)}
    >
      <Image
        src={src}
        alt={alt}
        width={800}
        height={600}
        style={{
          objectFit: 'contain',
          transition: 'transform 0.3s',
          transform: isZoomed ? 'scale(1.5)' : 'scale(1)',
        }}
      />
    </button>
  )
}

```

The zoom sketch keeps the intrinsic box stable and provides keyboard activation. It scales the existing pixels; if detail needs a higher-resolution variant, request it deliberately rather than changing the layout dimensions on hover. Disable the transform transition for reduced-motion users in the component stylesheet.

### Image with Loading States

```typescript
// components/image-with-loading.tsx
'use client'

import { useState } from 'react'
import Image from 'next/image'

export function ImageWithLoading({
  src,
  alt,
  width,
  height,
}: {
  src: string
  alt: string
  width: number
  height: number
}) {
  const [loadedSource, setLoadedSource] = useState<string | null>(null)
  const [failedSource, setFailedSource] = useState<string | null>(null)
  const failed = failedSource === src
  const isLoading = loadedSource !== src && !failed

  return (
    <div className="relative">
      {isLoading && (
        <div
          className="absolute inset-0 bg-gray-200 animate-pulse"
          style={{ width, height }}
        />
      )}
      <Image
        src={src}
        alt={alt}
        width={width}
        height={height}
        onLoad={() => setLoadedSource(src)}
        onError={() => setFailedSource(src)}
        className={isLoading ? 'opacity-0' : 'opacity-100'}
      />
      {failed && <p role="status">Image unavailable.</p>}
    </div>
  )
}

```

Loading state is tied to the source so replacing `src` gets a new pending/error outcome. Remount this component with `key={src}` when changing image identity. This gives the new source its own state owner, so a late event from the discarded image cannot change the current loading/error state. Error feedback is separate from a successful load.

### Next.js Image Configuration

```typescript
// next.config.js
module.exports = {
  images: {
    // Device sizes for responsive images
    deviceSizes: [640, 750, 828, 1080, 1200, 1920, 2048, 3840],

    // Image sizes for srcset
    imageSizes: [16, 32, 48, 64, 96, 128, 256, 384],

    // Allowed remote patterns
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'images.example.com',
        pathname: '/public/**',
        search: '',
      },
    ],

    // Formats to use
    formats: ['image/avif', 'image/webp'],

    // Minimum cache TTL (seconds)
    minimumCacheTTL: 60 * 60 * 24 * 30, // 30 days

    // Disable static imports
    disableStaticImages: false,

    // Content security policy
    contentSecurityPolicy: "default-src 'self'; script-src 'none'; sandbox;",
  },
}

```

## Common Mistakes

### 1. Not Setting Width and Height

```typescript
// BAD: String src without dimensions or fill fails component validation
<Image src="/photo.jpg" alt="Photo" />

// GOOD: Give dimensions (or use a static import/sized fill parent)
<Image src="/photo.jpg" alt="Photo" width={800} height={600} />

```

### 2. Using Priority on All Images

```typescript
// BAD: All images marked as priority
<Image src="/photo1.jpg" alt="1" width={800} height={600} priority />
<Image src="/photo2.jpg" alt="2" width={800} height={600} priority />
<Image src="/photo3.jpg" alt="3" width={800} height={600} priority />

// GOOD: Only above-the-fold images get priority
<Image src="/hero.jpg" alt="Hero" width={1200} height={600} priority />
<Image src="/content.jpg" alt="Content" width={800} height={600} />

```

### 3. Not Using Remote Patterns

```typescript
// BAD: Remote image not configured
<Image src="https://example.com/photo.jpg" alt="Photo" width={800} height={600} />
// Error: Invalid src prop

// GOOD: Configure remote patterns
// next.config.js
module.exports = {
  images: {
    remotePatterns: [
      { protocol: 'https', hostname: 'example.com' },
    ],
  },
}

```

### 4. Ignoring Aspect Ratio

```typescript
// BAD: Incorrect aspect ratio
<Image src="/photo.jpg" alt="Photo" width={800} height={800} />
// Image will be stretched if original is not square

// GOOD: Match aspect ratio or use fill
<Image
  src="/photo.jpg"
  alt="Photo"
  width={800}
  height={600}
  style={{ objectFit: 'cover' }}
/>

```

### 5. Treating a Blur Preview as Required or as Layout Protection

A placeholder is optional. Choose a matching skeleton, solid color or tiny valid blur image when it improves the waiting experience; do not ship a large preview that competes with the actual image. Width/height or parent geometry prevent layout movement. A remote URL needs supplied blur data; supported static imports can provide it automatically.

## Best Practices

1. **Reserve the image area** — Use intrinsic dimensions, static imports, or a sized fill parent

2. **Preload selectively** — Use priority on 15, preload on 16 for the likely LCP image

3. **Choose intentional waiting feedback** — A small placeholder is optional; reserve geometry independently

4. **Configure remote patterns** — For external images

5. **Use responsive sizes** — Serve appropriate sizes

6. **Lazy load below-the-fold images** — Save bandwidth

7. **Use fill mode for backgrounds** — For flexible layouts

8. **Optimize image formats** — Enable WebP/AVIF

9. **Test on different devices** — Verify responsive behavior
10. **Monitor image performance** — Track loading metrics

## Performance Considerations

Inspect delivered bytes, variant dimensions, `currentSrc`, request priority, cache behavior and decode time on representative devices. Preloading a likely largest-content image can help; preloading several candidates can compete with critical resources. Intrinsic dimensions reduce image-related layout shift only when CSS preserves the intended box. Lazy loading saves requests for unseen content but should not delay a critical visible image. No one prop guarantees LCP, FCP or CLS improvement.

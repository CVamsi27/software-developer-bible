# Image Optimization in Next.js

A product card may occupy 400 CSS pixels while its source photo is 4,000 pixels wide. Sending the original wastes bandwidth; choosing a candidate that is too small looks soft on a high-density display.

```tsx
import Image from 'next/image';

export function ProductCardImage({ src, alt }: { src: string; alt: string }) {
  return (
    <Image
      src={src}
      alt={alt}
      width={1200}
      height={900}
      sizes="(max-width: 767px) 100vw, (max-width: 1279px) 50vw, 33vw"
      style={{ width: '100%', height: 'auto' }}
    />
  );
}
```

## Definition

The Next.js Image component adds responsive source selection and, with the default loader, on-demand resizing and encoding. Its benefit depends on accurate layout hints, a suitable loading policy, trusted sources, and a cache policy that fits how images change.

> **Textbook Definition:** Image optimization selects and delivers an encoded image variant suited to the rendered dimensions and supported format. Responsive sizing, loading policy, cache identity, and layout reservation govern bandwidth, processing cost, and visual stability.

## First Principles

Three facts govern image delivery. **The rendered slot determines useful pixels**: the browser combines CSS width, device density, and the sizes hint to choose a srcset candidate. **The layout must exist before the image arrives**: intrinsic dimensions or a sized fill parent reserve space and reduce shift. **Each transformed variant costs work and storage**: reuse needs stable source identity, and changed content needs a refresh path.

## How It Works

### Follow the image to the browser

```text
CSS slot + device density
  → browser selects a srcset candidate using sizes
  → Next loader resizes and encodes on a cache miss
  → browser decodes bytes inside the reserved layout box
```

For a card that is full width on small screens, half width on medium screens, and one-third width on wide screens, describe those widths in sizes:

```tsx
import Image from 'next/image';

export function ProductCardImage({ src, alt }: { src: string; alt: string }) {
  return (
    <Image
      src={src}
      alt={alt}
      width={1200}
      height={900}
      sizes="(max-width: 767px) 100vw, (max-width: 1279px) 50vw, 33vw"
      style={{ width: '100%', height: 'auto' }}
    />
  );
}
```

The browser uses sizes to choose a candidate; the optimizer does not infer the card's CSS width. Inspect currentSrc and transferred bytes at representative viewport widths and pixel densities. Use meaningful alt text for informative images and alt="" when a decorative image adds no information beyond nearby content.

When the parent owns the crop, use fill and give that parent a position and stable aspect ratio:

```tsx
<div className="relative aspect-[4/3]">
  <Image
    src={src}
    alt={alt}
    fill
    sizes="(max-width: 767px) 100vw, 50vw"
    style={{ objectFit: 'cover' }}
  />
</div>
```

Fill does not set the parent's height. A zero-height or unbounded parent can still collapse the layout.

### 1. Limit Source and Cache Work

Remote images must match remotePatterns. Restrict protocol, host, path, and query string to sources the application intends to fetch. Local images can also be limited with localPatterns.

```typescript
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'images.example.com',
        pathname: '/catalog/**',
        search: '',
      },
    ],
    localPatterns: [{ pathname: '/assets/images/**', search: '' }],
    qualities: [75, 90],
    formats: ['image/avif', 'image/webp'],
    minimumCacheTTL: 3600,
    maximumRedirects: 1,
    maximumResponseBody: 5_000_000,
    dangerouslyAllowLocalIP: false,
  },
};

export default nextConfig;
```

In Next.js 16, configure the qualities allowlist; the default optimized quality is 75. WebP is the default output format. AVIF is opt-in and can reduce transfer size at the cost of more encoding work and cached variants. If a proxy or CDN sits in front of Next.js, forward Accept so format negotiation works.

The default optimizer does not forward authorization headers. Do not use it for a private source that requires caller credentials; use an explicitly authorized image service or an unoptimized path. Redirect targets are not checked against remotePatterns again, so allow only trusted sources and limit redirects when appropriate. Keep dangerouslyAllowLocalIP disabled unless a reviewed private-network design requires it.

The optimizer caches by source and transformation inputs. It has no tag-based invalidation, and a longer upstream Cache-Control lifetime can exceed minimumCacheTTL. Version the source URL when replacing content; route revalidation does not purge a transformed image. Next.js 16.1.2 and later can cap source response bytes with maximumResponseBody.

### 2. Choose Loading Behavior and Runtime

Images are lazy-loaded by default. Keep that behavior below the fold. For a measured above-the-fold LCP image, choose one suitable hint, usually loading="eager" or fetchPriority="high". In Next.js 16, priority is deprecated. Use preload only when the LCP image is unambiguous; do not combine preload with loading or fetchPriority.

A supported static image import can provide intrinsic dimensions and blur metadata. A remote URL or string path needs its own blurDataURL for a blur placeholder. The placeholder is optional feedback, not layout reservation; dimensions or the parent aspect ratio reserve the box.

When a remote image can fail, present a deliberate fallback and keep loading/error state tied to the current source. A late load event from an old source must not hide an error for its replacement.

The default optimizer runs on the Next.js server when a requested variant is first needed, then uses its configured cache. That requires a runtime capable of serving the image endpoint. Static export has no Next.js image optimizer; use unoptimized images or a custom loader to an external service. Managed hosts and self-hosted deployments differ in cache persistence, cost, and transformation limits.

Measure LCP contribution, transferred bytes, request priority, and layout shift on the deployed page. Intrinsic geometry can reduce image-related CLS, but it does not guarantee faster LCP; selected bytes, connection, decode, and host cache still matter.

## Summary

Match sizes to the actual layout, reserve geometry before loading, and restrict sources and variants the optimizer may fetch. Choose one loading hint from measured LCP behavior, version URLs when content changes, and verify the runtime and cache policy serving the image.

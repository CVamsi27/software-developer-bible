# Deploying Next.js

## Definition

**Deploying Next.js** means choosing where its server features will run. These include Server Component rendering, Route Handlers, middleware, regenerated pages and image processing. You can use Vercel's managed infrastructure, operate a Node.js server in a container or on a VM, or create a static export if the app needs no request-time server features. The choice changes who manages caching, environment configuration and scaling.

> **Textbook Definition:** Deployment maps a built application to a hosting runtime and its operational resources. Next.js deployment must preserve the rendering, image, cache and mutation capabilities actually used by the chosen build configuration.

## First Principles

A built route may still need to read a session, regenerate output or transform an image after the files are deployed. The host must supply each capability that the route assumes.

1. **A static file host cannot run request-time code.** Either export only supported build/browser behavior or deploy a compatible server/adapter for runtime features.
2. **A process is not a durable shared store.** Replicas and replacement containers have independent memory/filesystems unless storage is explicitly shared. Cache keys, tag invalidation and regeneration coordination must work across that topology.
3. **A build artifact freezes some configuration.** Browser constants and prerendered values may be captured during the build; changing runtime environment variables cannot rewrite bytes already shipped.
4. **A rollout changes versions while requests continue.** Keep old/new assets, action compatibility, draining and rollback behavior coherent during overlap rather than validating only one idle process.

## Why It Matters

Deployment questions dominate senior screens because they expose whether you understand what the framework actually does at runtime: which caches exist where, why a rebuilt container lost its ISR cache, why changing an env var did nothing until rebuild, and what breaks when you leave Vercel. The standalone Dockerfile is also a common take-home exercise — doing it correctly (multi-stage, non-root, static assets copied) signals production maturity.

**Concretely:**

1. **Compliance and cost**: Data residency, network placement or ownership requirements can favor a self-hosted runtime — you must know exactly what Vercel was doing for you.
2. **Container correctness**: Naive `node .next` deployments ship megabytes of dev dependencies and break on missing static assets.
3. **Cache coherence**: Multiple replicas each keep private in-memory ISR caches unless you provide a shared cache/invalidation design — users can see stale/divergent pages.
4. **Config sanity**: Mixing build-time and runtime env vars causes "works locally, wrong in prod" bugs that waste days.
5. **Operability**: Health checks, graceful shutdown, structured logs, and traces are your job the moment you own the process.

## How It Works

**Version scope:** The standalone/cache-handler examples target the traditional Next.js 15 cache model, also available in 16 without Cache Components. Next.js 16's Proxy uses Node.js; routing at a network boundary does not imply Edge execution. Public environment values and statically rendered server output may be frozen at build time, while a dynamic server request can read runtime variables. Never pass true secrets as Docker build arguments: intermediate layers/build logs can retain them.

The sample Dockerfile expects a `public/` directory and a lockfile. Add a `.dockerignore` excluding local `node_modules`, `.next`, `.git`, and secret environment files before `COPY . .`; otherwise local artifacts can overwrite the clean dependencies and secrets can enter the image.

### Follow the Standalone Artifact Into a Container

```text
Build source + dependencies → .next/standalone/server.js + traced files
                           → .next/static chunks (copy separately)
                           → public assets (copy separately)
Runtime env + mounted/shared resources → Node listener → reverse proxy → requests
```

A successful build is not a deployment check. Verify chunk URLs, image processing, protected reads, cache refresh, health probes and a request active during termination. Test both sides of a rolling version change; old browsers may still request old chunks or invoke an older action reference. Keep a rollback artifact and a compatible cache/data policy.

### Standalone Output + Multi-Stage Dockerfile

`output: 'standalone'` makes the build emit `.next/standalone` — a folder containing only the traced runtime files and pruned `node_modules`.

```javascript
// next.config.mjs
/** @type {import('next').NextConfig} */
export default {
  output: "standalone",
  // Self-hosted ISR with a shared cache handler (see below):
  cacheHandler: "./isr-cache-handler.mjs",
  cacheMaxMemorySize: 0, // disable per-instance LRU; rely on shared store
};
```

```dockerfile
# syntax=docker/dockerfile:1

# ── Stage 1: dependencies ───────────────────────────────────────
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# ── Stage 2: build ──────────────────────────────────────────────
FROM node:22-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ARG NEXT_PUBLIC_API_URL            # baked into the CLIENT bundle here!
ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL
RUN npm run build

# ── Stage 3: runtime ────────────────────────────────────────────
FROM node:22-alpine AS runner
WORKDIR /app
# Bind all container interfaces so the proxy can connect.
ENV NODE_ENV=production \
    PORT=3000 \
    HOSTNAME=0.0.0.0

RUN addgroup --system --gid 1001 nodejs \
 && adduser  --system --uid 1001 nextjs

# standalone server.js + pruned node_modules
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
# static chunks are NOT traced — copy explicitly:
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public

USER nextjs
EXPOSE 3000
CMD ["node", "server.js"]
```

Before building, use a `.dockerignore` such as:

```text
node_modules
.next
.git
.env*
!.env.example
```

Review any additional generated/private files before copying the context. The three classic failures this file prevents: shipping dev dependencies (no multi-stage), serving broken CSS/JS chunks (forgot `.next/static`), and binding localhost inside the container (missing `HOSTNAME=0.0.0.0`).

### Compare Managed and Operated Responsibilities

| Concern | Managed framework host | Self-hosted Node/container |
| --------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Runtime compatibility | Verify supported Next version/features and adapter behavior | Pin Node/framework dependencies and verify the runtime artifact |
| Cache and images | Confirm persistence, invalidation and regional behavior | Implement storage/coherence, image dependencies and capacity |
| Rollout/previews | Understand platform routing, asset retention and rollback | Operate pipeline, overlapping versions, probes and draining |
| Data placement | Verify available regions/network access and residency contract | Choose location and operate its network/security controls |
| Cost | Measure the workload against current usage pricing | Include infrastructure, idle capacity, operations and failure recovery |

The provider's marketing label is not evidence of compliance, latency or unlimited capacity. Confirm the actual deployment configuration and contractual requirements.

### Edge Runtime Limits

Segments opting into the edge runtime (`runtime = 'edge'`) use a different execution/API environment; startup and limits depend on the host:

| Limit class | Reality |
| --------------------- | ------------------------------------------------------------------- |
| Node APIs | Mostly absent — no `fs`, limited `crypto`, no native modules |
| CPU/duration | Provider-specific limits; verify current plan and workload |
| Payload/response size | Capped |
| Libraries | Must be edge-compatible; many npm packages fail at import time |
| Middleware | Next 15 defaults to Edge; 15.5 allows Node; 16 Proxy runs Node |

Design rule: choose Edge only when its API compatibility, data placement and measured limits suit the route. A globally close function can still call a distant database; Node-bound work needs a compatible runtime.

### ISR Cache Handler on Self-Hosted

The Next.js 15-style `cacheHandler` contract stores the **entire `data` argument**, wrapped with `lastModified`, and receives tags in `set(key, data, ctx)`. A backing store must preserve those tags and invalidate every matching entry across replicas; inventing a fixed 30-second miss threshold discards stale entries the framework may need during regeneration.

```javascript
// isr-cache-handler.mjs — integration adapter, not a complete Redis implementation
import { sharedStore } from './shared-cache-store.mjs';

export default class SharedCacheHandler {
  async get(key) {
    // Store contract returns { value, lastModified, tags } or null.
    return sharedStore.get(key);
  }

  async set(key, data, ctx) {
    await sharedStore.set(key, {
      value: data,
      lastModified: Date.now(),
      tags: ctx?.tags ?? [],
    });
  }

  async revalidateTag(tags) {
    await sharedStore.invalidateTags(Array.isArray(tags) ? tags : [tags]);
  }

  resetRequestCache() {} // This adapter has no request-local layer.
}
```

Implement `sharedStore` with atomic tag indexing/invalidation, a binary-safe serialization strategy for the cache's value types, and deployment-aware keys; test the adapter against the exact pinned Next version. This illustrates the traditional cache API, not Next.js 16 Cache Components' separate `cacheHandlers` interface. The default self-hosted image optimizer also needs its own functioning image cache/runtime dependencies.

### Multi-Zone / Micro-Frontends

Zones route different path sets to independent deployments. Keep each zone's asset namespace distinct (for example with `assetPrefix`); a local rewrite from `/shop/:path*` back to `/shop/:path*` does not proxy to another deployment.

```javascript
// Shell next.config.mjs; each origin is a trusted deployment setting.
export default {
  async rewrites() {
    return [
      { source: '/marketing/:path*', destination: `${process.env.MARKETING_ORIGIN}/marketing/:path*` },
      { source: '/shop/:path*', destination: `${process.env.SHOP_ORIGIN}/shop/:path*` },
    ];
  },
};
```

The zone apps must own those paths (using `basePath` when appropriate), and the ingress must also forward their asset-prefix paths. Use ordinary links for navigation between zones: crossing a zone unloads the first app, while navigation within a zone can remain client-side. Module federation requires its own compatible tooling and is not automatic App Router support.

### Environment Variables: Build Time vs Runtime

| Variable type | When read | Changing it requires |
| ---------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `NEXT_PUBLIC_*` | **Build time** — inlined into JS bundles | Rebuild + redeploy |
| Server-only environment (`DATABASE_URL`) | Runtime for request-time code; build if build-time code reads it | Restart/redeploy for runtime reads; rebuild if captured during prerender |
| `.env.production` files | Loaded by Next at build/start; browser/static use may be frozen | Rebuild for compiled uses, restart for runtime uses |

```typescript
// The trap: this value is frozen into the bundle at build time.
// Pointing the same image at staging vs prod API needs a REBUILD,
// not just new env vars — unless you proxy through server code.
const apiBase = process.env.NEXT_PUBLIC_API_URL;

// Pattern for runtime-configurable values: read them server-side
// and inject through a server component or route handler.
```

In Docker: pass `NEXT_PUBLIC_*` as `ARG` during stage 2; pass secrets as runtime `ENV` on the final container.

### Observability Hooks

```typescript
// instrumentation.ts — runs once when the server boots
export async function register(): Promise<void> {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { initOtel } = await import("./otel-node");
    initOtel(); // OpenTelemetry traces for renders, route handlers, fetches
  }
}
```

- Next has first-class OpenTelemetry spans (`base.get.render`, fetch instrumentation) — export to any OTLP collector.
- Add `/api/health` route handlers (liveness: process up; readiness: required dependencies usable under bounded checks).
- Log JSON with request IDs; establish and propagate your request ID at the trusted ingress, and correlate with OTel trace IDs.
- Watch cache metrics: ISR hit ratio, revalidation latency, image optimizer queue depth.

### Kubernetes Deployment Snippet

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.42.0
          ports: [{ containerPort: 3000 }]
          env:
            - name: DATABASE_URL          # runtime secret, not baked
              valueFrom:
                secretKeyRef: { name: web-secrets, key: database-url }
          readinessProbe:
            httpGet: { path: /api/health, port: 3000 }
          lifecycle:
            preStop:
              exec: { command: ["sleep", "5"] } # drain behind LB
          resources:
            requests: { cpu: 250m, memory: 256Mi }
            limits:   { cpu: "1",  memory: 512Mi }
```

### Graceful Shutdown in the Standalone Server Context

The generated standalone `server.js` does not expose a `server` binding you can reference from an unrelated wrapper. Configure the orchestrator's readiness, connection draining, and termination grace period, and test `SIGTERM` while requests are active. If you use a custom HTTP server, it must own the handle used by `server.close`; a custom server is a separate deployment choice and is not interchangeable with generated standalone output.

## Real-World Use Cases

1. **Series-B SaaS on Vercel**: preview deploys accelerate PR review; team accepts usage pricing until traffic profile stabilizes.
2. **Banking portal self-hosted**: compliance demands on-prem; standalone image, shared cache and OTLP traces address runtime operations; compliance also needs verified access, retention, residency and organizational controls.
3. **High-traffic media site**: ISR pages served from CDN in front of three replicas sharing a cache handler; measure origin regeneration load and failure behavior under actual route traffic.
4. **Multi-brand commerce**: zones split `/shop`, `/blog`, `/checkout` into separately owned repos deploying independently under one domain.
5. **Embedded analytics widget**: static shell on a CDN, with any private/live data provided by a separately authorized API.

## Common Mistakes

### 1. Baking Secrets Into Client Bundles

```typescript
// BAD: NEXT_PUBLIC_ prefix publishes it to every browser
const key = process.env.NEXT_PUBLIC_STRIPE_SECRET_KEY;

// GOOD: secrets stay server-side; clients call your route handlers
export async function POST() {
  const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!); // server-only
}
```

### 2. Expecting Env Changes Without a Rebuild

```bash
# BAD: redeploy same image with new NEXT_PUBLIC_API_URL — nothing changes;
# the old URL is compiled into the JS already shipped to users.
docker run -e NEXT_PUBLIC_API_URL=https://staging.api web

# GOOD: rebuild with the ARG, or make the value runtime-resolvable
# server-side (proxy/route handler reads process.env at request time).
```

### 3. Running the Non-Standalone Build in Docker

```dockerfile
# BAD: copies everything; node_modules includes dev deps; huge image
COPY . .
CMD ["npm", "start"]
```

```dockerfile
# GOOD: standalone trace + explicit static copies
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public
```

### 4. Multi-Replica ISR With Default Cache

Three pods revalidate independently → users bounce between stale and fresh versions. Fix: `cacheHandler` on shared storage, and propagate tag invalidation across all readers; sticky routing alone does not make independent caches coherent.

### 5. Heavy Work in Middleware (Edge)

```typescript
// BAD: JWT signature verification with a Node-only crypto lib in
// middleware → runtime crash or CPU-limit timeouts
export function middleware(req: Request) {
  verifyJwtWithNodeCrypto(req); // explodes on edge
}
```

```typescript
// GOOD: lightweight session cookie presence check at edge;
// full verification in Node runtime (route handlers/layouts)
```

### 6. Ignoring HOSTNAME Binding

Logs look healthy, external traffic times out: the server bound to `localhost` inside the container. Always set `HOSTNAME=0.0.0.0` for the standalone server.

## Best Practices

1. **Use a deliberate runtime artifact** — Standalone tracing is useful for containers; verify its dependencies, assets and actual startup behavior.
2. **Copy `.next/static` and `public` explicitly** in the final image stage; standalone tracing does not copy those asset directories.
3. **Treat `NEXT_PUBLIC_*` as public constants**, versioned with builds; route all true secrets through server runtime.
4. **Share the ISR cache across replicas** from day one of horizontal scaling; test by hitting different pods directly.
5. **Keep routing gates thin**; choose dependencies for Edge middleware or Node Proxy and authorize in handlers/actions.
6. **Ship health/readiness endpoints and preStop drains** so rollouts don't drop in-flight requests.
7. **Wire OpenTelemetry via `instrumentation.ts` before launch**, not after the first incident.

## Performance Considerations

| Lever | Effect |
| ------------------------------- | ----------------------------------------------------------------------------------------------- |
| Standalone image | Removes untraced dependencies; measure actual image and cold-start reduction |
| Shared ISR cache | Can coordinate reuse/invalidation; consistency depends on atomic store and versioned key design |
| `sharp` present | Native image pipeline speed (vs wasm fallback) |
| Edge segments | Constrained APIs; latency depends on host, location, and dependencies |
| PreStop drain + readiness gates | Helps drain traffic; rollout settings and termination timeout still matter |
| OTel sampling tuned | Controls telemetry volume; measure overhead under load |

## Summary

- Three deployment targets are managed hosting, self-hosted Node, and static export. Managed hosting supplies framework infrastructure; a Node deployment makes caching, images, scaling, and logs your responsibility.
- `output: 'standalone'` + a three-stage Dockerfile (deps → build → slim runtime) is the canonical self-host artifact; copy static assets and bind `HOSTNAME=0.0.0.0`.
- Horizontal scaling demands a shared `cacheHandler`; otherwise replicas serve divergent ISR content.
- `NEXT_PUBLIC_*` variables are compile-time constants; runtime configurability requires server-side resolution.
- Edge runtime trades Node API compatibility for host-specific startup/placement benefits — use it for gating, not computing.
- Zones give pragmatic micro-frontends via basePath + rewrites; observability hooks (`instrumentation.ts`, health endpoints, OTel) complete the production picture.

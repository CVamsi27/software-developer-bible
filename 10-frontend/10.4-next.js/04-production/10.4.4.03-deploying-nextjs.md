# Deploying Next.js

A build can pass and still fail after release: a static host cannot read a session, a container may omit the chunks its HTML references, and two replicas can disagree about cached data. Deployment is the contract between the built application and the infrastructure that runs it.

```javascript
// next.config.mjs — package a self-contained runtime
export default {
  output: 'standalone',
  deploymentId: process.env.DEPLOYMENT_VERSION,
};
```

## Definition

Deploying Next.js means producing an application build and running it on infrastructure that supports the features the application uses. That contract includes request-time rendering, routes and mutations, image processing, caching, assets, configuration, and safe rollout behavior.

> **Textbook Definition:** Deployment maps a versioned application artifact to a runtime and its operational resources while preserving the execution, data, and availability guarantees required by that application.

## First Principles

Four facts shape every deployment. **A static host serves files; a server handles requests** — choose by whether the app needs request-time identity, Route Handlers, Server Actions, Proxy, regeneration, or image optimization. **A process-local cache is not a shared cache** — replicas and replacement containers have separate memory and filesystems unless shared storage and invalidation exist. **A build freezes some values and files** — browser-visible `NEXT_PUBLIC` values and prerendered output bake in at build time; runtime config cannot rewrite shipped bytes. **A rollout serves multiple versions at once** — old clients may request old chunks or invoke old actions, so release and rollback plans must cover overlap.

## How It Works

### 1. Choose the Execution Contract

| Deployment | What it runs | Main boundary |
| --------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Static export | Prebuilt HTML, assets, and browser code | No request-time Next.js features; use a custom image loader if images need optimization |
| Node.js server or compatible platform adapter | Next.js request runtime and the features supported by that host | Verify the exact adapter and platform support for streaming, caching, image optimization, and background work |

A single Node.js process can run the framework features, while adapters and managed platforms may impose additional behavior or limits. Read the platform's compatibility contract and test the built artifact. A successful build alone does not prove the target host supports the app's runtime assumptions.

### 2. Build Once and Package the Runtime

For a container deployment, standalone output packages traced runtime files and pruned dependencies. The static chunks and public assets still need to be copied. This example assumes npm and an existing public directory:

```javascript
// next.config.mjs
export default {
  output: 'standalone',
  deploymentId: process.env.DEPLOYMENT_VERSION,
};
```

```dockerfile
FROM node:24-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:24-slim AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:24-slim AS runner
WORKDIR /app
ENV NODE_ENV=production PORT=3000 HOSTNAME=0.0.0.0
RUN addgroup --system --gid 1001 nodejs \
 && adduser --system --uid 1001 nextjs
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public
USER nextjs
EXPOSE 3000
CMD ["node", "server.js"]
```

Add a .dockerignore for node_modules, .next, .git, and local secret files so local build output cannot overwrite clean dependencies or enter the image. Omit the public copy if the application has no public directory. Use a maintained Node.js LTS image, keep build and runtime base environments compatible with native modules, and pin the image digest in a production lockfile or build process.

Promote the same artifact through environments. Set deployment-specific public values before building because NEXT_PUBLIC values are inlined into browser JavaScript. Server code that reads an environment value during dynamic rendering can use runtime configuration, which allows one image to move between environments. Never put real secrets in Docker ARG values or client-exposed variables.

If the application uses Server Actions across multiple instances, provide the same NEXT_SERVER_ACTIONS_ENCRYPTION_KEY before building; Next.js embeds it in the output. It must be a base64-encoded AES key of a supported length. Supply it through the CI secret environment and prevent it from appearing in logs or image layers.

### 3. Make Caches Agree with the Application

The correct cache integration depends on the feature being cached:

| Cache path | Next.js integration | Deployment decision |
| ------------------------------------------------------------------------------------ | ------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| ISR and server cache paths such as route output, patched fetch, and optimized images | cacheHandler | The default cache is local to each server; choose durable shared storage when replicas or ephemeral disks require consistency |
| Values cached with use cache or use cache: remote | cacheHandlers | Configure a handler for the required storage scope; the default in-memory implementation is per process |

Do not assume the singular cacheHandler and plural cacheHandlers configure the same subsystem. For the previous server-cache model, a durable handler must preserve the full cache value and timestamp. Page and route tags are carried in the data headers under x-next-cache-tags; cached fetch tags come from ctx.tags. Binary and map-like values need a serializer that preserves their types.

Shared storage alone does not propagate invalidations. Current self-hosting guidance calls for a refreshTags() implementation that synchronizes tag state from shared storage before requests use the cache. Validate the handler API against the pinned Next.js version, then test invalidation initiated on one replica and reads served by another. Cache Components use cacheHandlers; follow the selected handler contract and test its invalidation behavior across replicas.

### 4. Keep Overlapping Releases Compatible

Use one build across all replicas and give each release a deploymentId. Next.js uses that identifier to detect client/server version mismatch and trigger a hard navigation; it does not route old clients to a separate server. Keep immutable assets available for clients on the previous release, and test rollback with the previous artifact and data format.

The same deploymentId belongs to all replicas of one release. The Server Actions encryption key must also match the key embedded in that build. Check that a rolling update does not mix incompatible assets, build output, database migrations, or cache formats.

### 5. Put the Server Behind an Operational Boundary

For self-hosting, place a reverse proxy or platform ingress in front of the Next.js process. Apply TLS, connection and request-size limits, rate controls, and malformed-request handling there so rendering capacity is not spent on unbounded inputs.

If the application streams Server Component output, ensure every proxy and load balancer passes streaming responses without buffering. Otherwise the page may work but arrive as one delayed response. Confirm this with a real request through the production path.

On shutdown, send SIGTERM or SIGINT and allow the server's configured drain period. Current Next.js self-hosting guidance says the server finishes in-flight requests and pending after() callbacks before exit; test that behavior through the actual orchestrator and ingress, not just with a local process.

### 6. Verify the Deployed Artifact

Before release, exercise the built container through the same ingress and dependencies used in production:

- Fetch a deep route and every referenced JavaScript, CSS, public, and optimized-image URL.
- Exercise an authenticated request, a Server Action, and a Route Handler when the app uses them.
- Revalidate one tagged entry on replica A, then confirm the expected result from replica B.
- Confirm runtime-only server configuration changes without rebuilding, while public NEXT_PUBLIC changes require a new build.
- Stream a response through the proxy and verify the client receives early content.
- Send SIGTERM while a request is active and confirm the request and required after() work finish within the drain window.
- Roll forward and back while a client still has the previous release loaded.

The smallest meaningful deployment test is an end-to-end request through the real container, proxy, cache, and data store. Unit tests of configuration cannot prove that traffic reaches the artifact and resources the configuration describes.

## Summary

Choose hosting from the features the app needs at request time, then promote one artifact with the correct runtime settings, assets, cache behavior, and release identity. Treat cache invalidation, version overlap, streaming, and shutdown as tested deployment properties rather than assumptions.

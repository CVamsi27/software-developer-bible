# Next.js Interview Questions

## First Principles

This bank tests whether you can locate behavior at the right rendering, request, data, or deployment boundary:

1. **Name the version and cache model.** Next.js 15's previous cache model and Next.js 16 Cache Components have different opt-in rules and APIs.
2. **Trace the data and trust boundary.** Say what runs on the server or browser, what crosses the RSC/HTTP boundary, and where identity, authorization, validation, and cache isolation are enforced.
3. **State the failure and evidence.** Explain stale data, retries, partial outages, and what test or production signal would falsify the design.

## Why It Matters

Senior interviews can cover either router. Establish the pinned Next.js version, router, deployment target, and enabled cache model before naming an API. Explain the mechanism, its boundary, and the trade-off rather than reciting a feature list.

## Overview

**Version scope:** Examples use the Next.js 15 App Router and previous cache model unless marked Next.js 16. Next.js 16 deprecates `middleware.ts` in favor of Node.js `proxy.ts`; Cache Components is opt-in and requires `partialPrefetching` to be set explicitly. The previous cache model remains a separate configuration. The one-argument `revalidateTag` example is scoped to Next.js 15; Next.js 16 uses a profile argument or, inside a Server Action, `updateTag` for read-your-writes behavior. Separate file labels mean separate examples.

This bank contains 40 questions. The difficulty labels organize practice; they do not imply a particular company's interview format.

## Beginner Questions (1-10)

### 1. What is Next.js and why would you use it?

**Answer:**
Next.js is a React framework that combines routing, rendering, and build conventions. Depending on the router and deployment target, an application can use:

- **Request-time rendering or reusable output** — Choose from the route's data and freshness needs.
- **Server and Client Components** — Keep server-only work out of browser bundles and add browser interactivity at explicit client boundaries.
- **Route Handlers and API Routes** — Implement HTTP endpoints; they do not supply a database, authorization policy, or service operations for you.
- **Image and asset tooling** — Produce optimized image variants when the selected runtime supports the optimizer.

```typescript
// Example: Simple page in Next.js
// app/page.tsx
export default function Home() {
  return <h1>Welcome to Next.js</h1>
}

```

Choose Next.js when its routing, server rendering, build, and deployment model solves a real application requirement. It does not guarantee SEO, low latency, or lower cost without correct data, caching, and hosting decisions.

---

### 2. What is the difference between Pages Router and App Router?

**Answer:**

| Concern | Pages Router | App Router |
| ------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Route files | `pages/` pages and optional `pages/api/` endpoints | `app/` segments with `page`, `layout`, `route` and boundary files |
| Component model | Traditional React components; no React Server Components | Server Components by default; `'use client'` starts a client boundary |
| Data model | `getServerSideProps`, `getStaticProps`, or client fetching | Server Component data access, Route Handlers, and explicit cache policy |
| Shared UI | `_app` and `_document`; nested layouts need application composition | Nested layouts and route-level loading/error boundaries |

```typescript
// Pages Router: pages/about.tsx
export default function About() {
  return <h1>About</h1>
}

// App Router: app/about/page.tsx
export default function About() {
  return <h1>About</h1>
}

```

Pages Router components can be rendered to HTML on the server; that does not make them Server Components. Choose a router based on the project’s required conventions and migration cost, then keep both routers' data, error, and caching contracts explicit.

### 3. What is Server-Side Rendering (SSR)?

**Answer:**
**Server-side rendering (SSR)** produces HTML during request handling instead of requiring that exact HTML to be produced only at build time. Rendering can still be reused by a CDN or another cache when response policy allows it, and request-time rendering does not guarantee fresh upstream data.

```typescript
// Pages Router SSR
export const getServerSideProps: GetServerSideProps = async () => {
  const res = await fetch('https://api.example.com/data')
  if (!res.ok) throw new Error('Data fetch failed')
  return { props: { data: await res.json() } }
}

// App Router, previous cache model (Cache Components disabled): request-time data
export default async function Page() {
  const response = await fetch('https://api.example.com/data', {
    cache: 'no-store' // Bypass Next's persistent Data Cache
  })
  if (!response.ok) throw new Error(`Data request failed: ${response.status}`)
  const data = await response.json()
  return <div>{data.value}</div>
}

```

**Boundary:** Request-time HTML can expose readable content without hydration, but data freshness still depends on upstream caching and interaction may require JavaScript.

---

### 4. What is Static Site Generation (SSG)?

**Answer:**
**Static site generation (SSG)** produces reusable HTML ahead of a visitor request, commonly during the build. A CDN may serve that output, but hosting and cache headers determine whether it does. Regeneration adds a freshness policy; it is not a guarantee that every request triggers a rebuild.

```typescript
// Pages Router SSG
export const getStaticProps: GetStaticProps = async () => {
  const res = await fetch('https://api.example.com/data')
  if (!res.ok) throw new Error('Data fetch failed')
  return { props: { data: await res.json() } } // SSG; add revalidate for ISR
}

// App Router, previous cache model (Cache Components disabled): public cached data
export default async function Page() {
  const response = await fetch('https://api.example.com/data', {
    cache: 'force-cache', // Explicit public-data reuse
  })
  if (!response.ok) throw new Error(`Data request failed: ${response.status}`)
  const data = await response.json()
  return <div>{data.value}</div>
}

```

**Boundary:** Reused output reduces origin rendering work. CDN configuration, payload size, resource latency and content quality still affect delivery and discoverability.

### 5. What is the App Router's layout system?

**Answer:**
Shared layouts can preserve their mounted client state during navigation within the same layout tree. Their children change; state/context changes and crossing a layout boundary still matter.

```typescript
// app/layout.tsx — Root layout (required)
export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <nav>Global Nav</nav>
        <main>{children}</main>
      </body>
    </html>
  )
}

// app/dashboard/layout.tsx — Nested layout
export default function DashboardLayout({ children }) {
  return (
    <div className="flex">
      <aside>Sidebar</aside>
      <main>{children}</main>
    </div>
  )
}

```

Layouts compose persistent shared UI and receive the active route through `children` and named slots. Keep request-specific data in the component or data layer that needs it; a shared layout is not a safe place for assumptions about when every descendant's data changes.

### 6. What are Server Components?

**Answer:**
Server Components execute on the server and serialize an RSC payload; Next also prerenders HTML for the initial full load. They cannot use state/effect hooks or browser APIs.

```typescript
// Server Component (default in App Router)
export default async function Page() {
  // Direct database access!
  const posts = await db.post.findMany()
  return posts.map(p => <div key={p.id}>{p.title}</div>)
}

```

**Boundary:** Server Component implementation code stays on the server, but nested Client Components still send JavaScript. Project only permitted data into the serialized output; server execution alone does not authorize access.

---

### 7. What are Client Components?

**Answer:**
Client Components normally prerender HTML on the server for first load, then hydrate and run interactively in the browser. Use `'use client'` directive.

```typescript
'use client'
import { useState } from 'react'

export function Counter() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>
}

```

**When to use:** State, effects, and event handlers. Browser APIs still belong in effects/handlers because the initial render can run on the server.

### 8. How do you handle navigation in Next.js?

**Answer:** Use `next/link` for application links and `useRouter` in a Client Component for programmatic transitions. A link preserves client navigation behavior; a plain anchor performs a full navigation.

For logout, await a successful authenticated POST, then replace the current route and refresh server output. Show failure without claiming logout succeeded; disable/serialize session-changing operations while pending. The [authentication chapter](../04-production/10.4.4.01-authentication.md) owns the complete context lifecycle. Navigation does not revoke a session or authorize a destination.

### 9. How do you fetch data in Next.js?

**Answer:**
In App Router, fetch data directly in Server Components.

```typescript
// Server Component — direct fetch
export default async function Page() {
  const response = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 } // Become eligible for revalidation after 60s; not a background timer
  })
  if (!response.ok) throw new Error(`Data request failed: ${response.status}`)
  const data = await response.json()

  return <div>{data.value}</div>
}

```

For expected absence, return a deliberate result or call `notFound()`. Let unexpected failures reach the route's error boundary; a broad catch that renders a success-shaped page can hide an outage.

```typescript
import { notFound } from 'next/navigation'

export default async function Page() {
  const response = await fetch('https://api.example.com/data')
  if (response.status === 404) notFound()
  if (!response.ok) throw new Error(`Data request failed: ${response.status}`)
  const data = await response.json()
  return <div>{data.value}</div>
}

```

### 10. What is Middleware, and what is Proxy in Next.js 16?

**Answer:**
Middleware is the Next.js 15-and-earlier convention for code that can redirect, rewrite, or modify a request before routing. In Next.js 16 it is deprecated and renamed to Proxy (`proxy.ts` exporting `proxy`); Proxy runs on Node.js. It is an early request-routing layer, not a replacement for authorization where data is read or changed.

```typescript
// proxy.ts — Next.js 16; Next.js 15 uses middleware.ts / middleware()
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  const token = request.cookies.get('auth-token')

  if (!token && request.nextUrl.pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/login', request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ['/dashboard/:path*'],
}

```

**Use cases:** Narrow redirects, rewrites, and request routing. Use a matcher to limit work. A Proxy check may improve navigation but can also run on prefetched requests; verify identity and current permissions inside every protected operation.

## Intermediate Questions (11-20)

### 11. How do you implement authentication in Next.js?

**Answer:** Authentication establishes a verified identity; authorization checks whether that current identity may perform this operation on this resource. A cookie-presence redirect is only early routing feedback.

Trace a login: validate the origin and input → verify credentials through the application's account service → issue a properly scoped secure session cookie → resolve the current account at each protected read/write → project permitted output. A forged cookie fails verification; a demoted account must fail its current permission check even if old token claims still say admin.

Use `NextResponse` when setting response cookies, rather than assuming ordinary `Response.json()` has a cookies API. The [authentication chapter](../04-production/10.4.4.01-authentication.md) owns the signed-token example, current-principal adapter, cookie lifecycle and pinned NextAuth.js v4 integration. Session revocation, CSRF/origin protection and tenant/resource authorization remain explicit contracts.

### 12. How do you handle forms with Server Actions?

**Answer:**
Server Actions are async server functions invoked through framework-managed HTTP requests. Their generated action identifiers and POST boundary are not an authorization mechanism. At the action itself, verify the caller, authorize the specific operation and resource, parse untrusted values with a runtime schema, and handle commit/retry outcomes. If the form must work before hydration, use a serializable state shape with React 19's `useActionState` and keep the action progressively enhanced.

```typescript
// app/actions/post.ts
'use server'

import { auth } from '@/auth'
import { revalidatePath } from 'next/cache'
import { redirect } from 'next/navigation'
import { z } from 'zod'

const PostSchema = z.object({
  title: z.string().trim().min(3, 'Title must be at least 3 characters').max(200),
  content: z.string().trim().min(10, 'Content must be at least 10 characters').max(20000),
})

export type FormState = {
  errors?: { title?: string[]; content?: string[] }
  message?: string
}

export async function createPost(
  prevState: FormState,
  formData: FormData
): Promise<FormState> {
  const session = await auth()
  if (!session?.user?.id) {
    return { message: 'Unauthorized — please log in.' }
  }

  const validated = PostSchema.safeParse({
    title: formData.get('title'),
    content: formData.get('content'),
  })

  if (!validated.success) {
    return { errors: z.flattenError(validated.error).fieldErrors } // Zod 4
  }

  await db.post.create({
    data: {
      ...validated.data,
      authorId: session.user.id,
    },
  })

  revalidatePath('/posts')
  redirect('/posts')
}
```

```typescript
// app/posts/new/post-form.tsx (Client Component for interactive feedback)
'use client'

import { useActionState } from 'react'
import { useFormStatus } from 'react-dom'
import { createPost } from '@/app/actions/post'
import type { FormState } from '@/app/actions/post'

function SubmitButton() {
  const { pending } = useFormStatus()
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Publishing...' : 'Create Post'}
    </button>
  )
}

export default function NewPostForm() {
  const initialState: FormState = {}
  const [state, formAction] = useActionState(createPost, initialState)

  return (
    <form action={formAction}>
      {state.message && <p className="error">{state.message}</p>}

      <div>
        <label htmlFor="post-title">Title</label>
        <input id="post-title" name="title" required aria-describedby="title-error" />
        {state.errors?.title && <p id="title-error" role="alert">{state.errors.title[0]}</p>}
      </div>

      <div>
        <label htmlFor="post-content">Content</label>
        <textarea id="post-content" name="content" required aria-describedby="content-error" />
        {state.errors?.content && <p id="content-error" role="alert">{state.errors.content[0]}</p>}
      </div>

      <SubmitButton />
    </form>
  )
}
```

The database/auth imports are application adapters: `auth()` must resolve a current account allowed to publish; `db` must enforce its storage invariants. Handle expected commit failures as typed feedback. A timeout after commit requires reconciliation/idempotency, not a blind retry. Progressive enhancement depends on the rendered action/form integration; `useActionState` alone does not make arbitrary browser-only logic work without JavaScript.

**Interview follow-up points:**
- **Security:** Next.js checks Server Action origins against the host by default; configure additional trusted origins only when required. Still authorize the mutation against the current user and resource. This does not automatically protect arbitrary cookie-authenticated Route Handlers.
- **Cache invalidation:** Invalidate only after the durable write succeeds. In Next.js 16, use action-only `updateTag` when the next read must see the write immediately, or `revalidateTag(tag, 'max')` for stale-while-revalidate behavior. Invalidation does not update every already-open browser atomically.

### 13. How do you optimize images in Next.js?

**Answer:** Reserve image geometry with dimensions or a sized `fill` container, describe its real CSS width through `sizes`, and allowlist remote sources. The browser selects a `srcset` variant from width and display density; the optimizer generates/caches configured variants.

A 400-CSS-pixel card on a density-2 display may need roughly 800 source pixels. Giving every card `sizes="100vw"` can download oversized variants. In Next.js 16, `priority` is deprecated. Usually use `loading="eager"` or `fetchPriority="high"`; use `preload` only when the LCP image is unambiguous, and do not combine the hints. Blur is optional preview feedback, not layout protection. CDN behavior depends on the host.

The [image chapter](../04-production/10.4.4.02-image-optimization.md) owns responsive, loading/error and accessible zoom examples. Do not use an ellipsis as a supposedly valid base64 placeholder.

### 14. How do you implement caching strategies?

**Answer:** First name the cache model and the data's acceptable staleness. In Next.js 15's previous App Router model, caching is explicit for `fetch`; a revalidation interval makes an entry eligible for refresh, while tag/path invalidation requests a refresh. In Next.js 16 Cache Components, data is dynamic by default; opt into reuse with `'use cache'`, choose a lifetime with `cacheLife`, and tag entries with `cacheTag`. Reuse is safe only when the cache key and policy give every reader of that entry the same authorized result.

```typescript
// Previous App Router cache model (Next.js 15, or Next.js 16 without Cache Components)
const revalidated = await fetch(url, { next: { revalidate: 60, tags: ['posts'] } })

// Bypass the persistent Next Data Cache; upstream caches still exist
const requestTime = await fetch(url, { cache: 'no-store' })

// Opt into persistent public-data reuse; retention depends on deployment/policy
const reusable = await fetch(url, { cache: 'force-cache' })
```

```typescript
// Separate Server Action in Next.js 15's previous cache model
// app/actions/revalidate-posts.ts
'use server'
import { revalidatePath, revalidateTag } from 'next/cache'

export async function refreshPosts() {
  await writePosts() // Invalidate only after the durable mutation succeeds.
  revalidateTag('posts')
  revalidatePath('/posts')
}
```

```typescript
// Next.js 16 Cache Components: cache a function deliberately
// lib/public-posts.ts
import { cacheLife, cacheTag } from 'next/cache'
import { db } from '@/lib/db' // Server-only persistence adapter.

export async function getPublicPosts() {
  'use cache'
  cacheLife('minutes')
  cacheTag('posts')
  return db.post.findMany({ select: { id: true, title: true } })
}
```

### 15. How do you implement API routes?

**Answer:** Route Handlers expose Web Request/Response endpoints in `app/.../route.ts`; await dynamic params in the scoped Next.js 15+ API.

For a user write, the order matters: authenticate → enforce role and resource scope → reject malformed JSON → parse an allowlisted writable shape → commit database invariants → return a safe projection and status. Never pass the entire request body into an ORM create/update. A users list needs bounded pagination and permitted fields; a missing resource returns 404, and a resource the caller is not allowed to discover may also be concealed with 404 by policy.

The [Route Handler chapter](../02-routing-and-middleware/10.4.2.02-route-handlers.md) owns validated search, authenticated mutation boundaries, upload and event examples. Exporting GET/POST alone does not supply authorization or input validation.

### 16. How do you handle error boundaries?

**Answer:** `error.tsx` is a Client Component that Next.js uses as an error boundary for a route segment's descendants. It does not catch errors in that segment's own layout; put a boundary above the failing layout or use the root `global-error.tsx` for root-layout failures. In Next.js 16.3+, the stable `retry` callback re-fetches and re-renders the boundary's children after a transient failure. The `reset` callback clears the error state and rerenders without refetching; use it only when that is the intended recovery. Neither callback undoes a database write or makes a failed operation safe to repeat. Use `notFound()` for expected absence instead of converting every error into a 404.

```typescript
// app/error.tsx — Next.js 16.3+; earlier versions expose their pinned error props
'use client'

export default function Error({
  retry,
}: {
  error: Error & { digest?: string }
  retry: () => void
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <p>Please try again. If the issue continues, contact support.</p>
      <button onClick={() => retry()}>Try again</button>
    </div>
  )
}

// app/not-found.tsx — 404 page
import Link from 'next/link'

export default function NotFound() {
  return (
    <div>
      <h2>404 - Page Not Found</h2>
      <Link href="/">Return home</Link>
    </div>
  )
}

```

### 17. How do you implement metadata for SEO?

**Answer:** Export `metadata` for values known at build/render time or `generateMetadata` when a route's title and preview depend on route data. Next.js combines metadata from layouts and pages; nested objects such as `openGraph` are replaced rather than deeply merged, so preserve parent fields deliberately when needed. Set `metadataBase` for relative canonical and social-image URLs. Metadata can help crawlers and sharing clients, but it cannot guarantee a search ranking.

```typescript
// app/layout.tsx — Static metadata
export const metadata: Metadata = {
  title: { template: '%s | MyApp', default: 'MyApp' },
  description: 'My application description',
}

// app/blog/[slug]/page.tsx — Dynamic metadata
export async function generateMetadata({ params }) {
  const { slug } = await params
  const post = await getPost(slug)

  return {
    title: post.title,
    description: post.excerpt,
    openGraph: {
      title: post.title,
      images: [post.coverImage],
    },
  }
}

```

In Next.js 15+, route `params` are promises, as shown above. Handle a missing record with `notFound()` and distinguish a failed content service from a genuinely absent post. Metadata work may be prerendered or deferred with the page, depending on the route's data and cache policy.

### 18. How do you implement parallel routes?

**Answer:**

```typescript
// app/layout.tsx — root layout owns the document elements
export default function RootLayout({ children, modal }) {
  return (
    <html lang="en">
      <body>{children}{modal}</body>
    </html>
  )
}

// app/@modal/(.)photos/[id]/page.tsx — intercepted route; sibling files are separate modules
import Image from 'next/image'
import { notFound } from 'next/navigation'

export default async function PhotoModal({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const photo = await getPhoto(id)
  if (!photo) notFound()

  return (
    <div className="modal">
      <Image src={photo.src} alt={photo.alt} width={photo.width} height={photo.height} />
    </div>
  )
}

```

```typescript
// app/@modal/default.tsx — fallback for unmatched modal-slot state on a hard load
export default function DefaultModalSlot() {
  return null
}
```

**Use cases:** Modals over existing pages, split views, and dashboards. The root layout must return `<html>` and `<body>`. A slot's `default.tsx` is its fallback when a hard load cannot recover that slot's active route; without a fallback, Next.js returns 404 for the unmatched slot. The implicit `children` slot can also need an intentional fallback for an unrecoverable parent state.

On soft navigation, the router can retain a slot's prior state even when its route does not match the new URL. On a hard navigation, a default handles unmatched state. Both slot pages still execute on the server, so authorize protected reads in the data-access boundary; choosing which slot to display does not prevent the other slot's work from running.

### 19. How do you handle streaming and Suspense?

**Answer:** A Suspense boundary lets React send the surrounding shell while a descendant is waiting on supported asynchronous work. Put independently slow work below a boundary when the rest of the page is useful without it; the fallback becomes visible until that subtree can render. `loading.tsx` supplies a route-segment loading boundary. Suspense does not make synchronous work nonblocking or cancel an operation when a user navigates away.

```typescript
// app/dashboard/page.tsx
import { Suspense } from 'react'

export default function DashboardPage() {
  return (
    <div>
      <h1>Dashboard</h1>

      {/* Fast content renders immediately */}
      <DashboardSummary />

      {/* Slow content streams in */}
      <Suspense fallback={<LoadingSkeleton />}>
        <SlowDataComponent />
      </Suspense>
    </div>
  )
}

// app/dashboard/loading.tsx — Automatic Suspense boundary
export default function Loading() {
  return <div>Loading dashboard...</div>
}

```

### 20. How do you implement i18n (internationalization)?

**Answer:**

```typescript
// proxy.ts — Next.js 16; locale negotiation is an early routing choice
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

const supportedLocales = ['en', 'es', 'fr'] as const

export function proxy(request: NextRequest) {
  const preferred = request.headers.get('accept-language')
    ?.split(',')[0]?.split(';')[0]?.split('-')[0]
  const locale = supportedLocales.find((value) => value === preferred) ?? 'en'
  const pathname = request.nextUrl.pathname

  // Check if locale is already in URL
  const pathnameHasLocale = /^\/(en|es|fr)(?:\/|$)/.test(pathname)

  if (!pathnameHasLocale) {
    const destination = request.nextUrl.clone()
    destination.pathname = `/${locale}${pathname}`
    return NextResponse.redirect(destination)
  }

  return NextResponse.next()
}

export const config = {
  // Add project-specific public files and route exclusions as needed.
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
}

// This simplified preference parser ignores quality weights; use a locale negotiator.

// app/[locale]/layout.tsx
export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode
  params: Promise<{ locale: string }>
}) {
  const { locale } = await params
  return (
    <html lang={locale}>
      <body>{children}</body>
    </html>
  )
}

```

## Senior Questions (21-30)

### 21. Design a rendering strategy for a large-scale application.

**Answer:** Begin with route classes, not labels such as “SSR” or “ISR.”

| Workload | Rendering and cache decision | Required boundary |
| --------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Public product description | Reuse a static or cached result for an agreed stale window | Invalidate after a durable content update; measure regeneration |
| Account dashboard | Resolve the current session and read request-specific data | Do not share one user's representation through a public cache |
| Price, stock, checkout | Read and enforce authoritative transactional state at mutation time | A cached page can inform the UI but cannot authorize or commit a purchase |
| Slow independent widgets | Stream behind separate Suspense boundaries where partial output helps | Bound queries and cancellation; do not let a slow widget block critical content |

With Next.js 16 Cache Components, data is dynamic by default; opt into shared reuse with `'use cache'`, `cacheLife`, and tags, and set `partialPrefetching` explicitly when enabling the feature. With the previous cache model, use that model's route/data revalidation APIs. State the freshness and failure contract for either choice, then test cold, warm, invalidated, personalized, and failed-regeneration paths.

### 22. How would you implement a micro-frontend architecture?

**Answer:**

```typescript
// Illustrative client composition; remote/App needs separately configured compatible tooling
// components/remote-shell.tsx
'use client'
import dynamic from 'next/dynamic'

const RemoteApp = dynamic(() => import('remote/App'), {
  loading: () => <div>Loading remote app...</div>,
  ssr: false,
})

export default function RemoteShell({ children }) {
  return (
    <div>
      <nav>Shell Navigation</nav>
      <RemoteApp />
      {children}
    </div>
  )
}

```

**Key considerations:**

- **Runtime contract:** The host and remote must agree on React/runtime versions and the bundler's remote-module protocol; Next.js does not provide a built-in remote-module deployment system.
- **Release boundary:** Independent deploys create runtime dependencies. Version the remote contract, define behavior when it is unavailable, and support a rollback that does not require rebuilding the host.
- **Rendering boundary:** Decide whether the remote must render on the server. Client-only remotes can delay interaction and need a useful loading/error state; SSR requires compatible server loading and hydration behavior.
- **Ownership:** Assign routes, navigation, shared state, authentication and design-system compatibility to explicit owners. Keep cross-application state and duplicated React roots small.

### 23. How do you optimize performance for a high-traffic application?

**Answer:** First measure the request mix, cache hit rate, database and downstream latency, payload sizes, and the p95/p99 budget. Reduce repeated work only where reuse is correct: cache public data with an explicit stale window, keep personalized data partitioned by identity or uncached, and make checkout writes authoritative. Bound database pools and background work across the replica count; use CDN caching for assets and public responses only when the cache key and headers preserve the contract. Stream independent slow regions, split expensive client code after measurement, and test cold cache, stampedes, invalidation, overload and rollback.

In Next.js 16, Cache Components is one opt-in caching model: set both `cacheComponents: true` and `partialPrefetching: true`, then use `'use cache'` for deliberate cross-request reuse. React `cache()` deduplicates work within a server request; it is not a durable shared cache. Load-test the deployed artifact with production-like traffic rather than deriving capacity from daily active users alone.

---

### 24. How would you implement real-time features?

**Answer:** Choose Server-Sent Events (SSE) for one-way server updates or WebSockets for bidirectional interaction. Authorize the subscription, scope its messages, bound buffering and release the producer when the response aborts or the consumer cancels.

Trace one SSE update: an authorized producer emits data → encode an SSE frame → stream it → the client validates and applies it. A reconnect does not automatically replay missed messages; design event IDs/resumption or refetch an authoritative snapshot. Guard late callbacks after cleanup. The [canonical SSE example](../02-routing-and-middleware/10.4.2.02-route-handlers.md) demonstrates stream cancellation; production subscription/replay adapters remain application-specific.
---

### 25. How do you implement comprehensive testing?

**Answer:** Test a meaningful contract at each boundary. A component test checks pending/error feedback and user interaction. An integration test exercises the real authenticated handler, validation and persistence. Browser tests cover rendered navigation, hydration and the production deployment path.

For the counter in question 7, click its initial accessible button name `0` and assert its name becomes `1`; an assertion against nonexistent “Increment”/“Count: 1” text proves nothing about that example. Add unauthorized/forbidden/malformed cases for protected writes and a failed regeneration case for ISR. A passing homepage heading test does not prove cache coherence or deployment compatibility.

Use a compatible runner for each layer; Playwright's request fixture is not a Jest callback fixture. Document whether tests use a real service or a stub and run production behavior in a production build where relevant.
---

### 26. How would you implement feature flags?

**Answer:** Separate a global deployment toggle from a user-targeted rollout or experiment. An environment boolean is evaluated from the server process/build configuration and usually changes only after a restart or rebuild; it is not a live flag service. A targeting provider needs a stable subject/tenant context, an explicit fallback when unavailable, and audited changes. Evaluate authorization independently, keep server-only flags out of client bundles, and include the variant in any cache key whose output differs.

Treat Proxy as an optional early routing layer in Next.js 16, not the feature-flag system or security boundary. Test both flag states, provider failure, rollout changes and rollback.

---

### 27. How do you handle complex state management?

**Answer:**

```typescript
// app/components/filters.tsx — URL state is shareable and survives reloads
'use client'
import { useSearchParams, useRouter } from 'next/navigation'

export function Filters() {
  const searchParams = useSearchParams()
  const router = useRouter()

  const category = searchParams.get('category') || 'all'

  const setCategory = (cat: string) => {
    const params = new URLSearchParams(searchParams.toString())
    params.set('category', cat)
    router.push(`?${params.toString()}`)
  }

  return (
    <select value={category} onChange={(e) => setCategory(e.target.value)}>
      <option value="all">All</option>
      <option value="electronics">Electronics</option>
    </select>
  )
}
```

Keep draft input and transient UI in local state, use Context for narrowly scoped shared UI state, and keep server-owned records behind a data/cache policy. Do not put secrets or authorization claims in URLs, Context, or client state.

---

### 28. How would you implement monitoring and observability?

**Answer:** Instrument request and dependency boundaries with traces, structured logs and a small set of service-level metrics. Correlate them with request/trace IDs, record route and cache outcomes, and redact credentials, personal data and query values. On the browser, collect Web Vitals separately and treat client-submitted telemetry as untrusted. Set sampling, retention and alert thresholds from user-facing latency and error budgets; verify the exporter and dashboards before an incident. The deployment chapter owns the Next.js OpenTelemetry hook.

---

### 29. How do you implement A/B testing?

**Answer:** Define the eligible population, assignment unit, exposure event, success metric, guardrail metrics and stopping rule before splitting traffic. Assign a stable variant for each experiment and subject; record exposure only when the user can actually see the variant. Apply consent and retention policy, exclude staff/bots where appropriate, and analyze sample-ratio mismatch and interference. If a response varies by cookie or identity, make the cache key respect that variation or bypass shared caching. A Proxy may route an already assigned variant, but random per-request assignment and client-provided variant headers are not reliable experiment state.

---

### 30. How would you migrate from Pages Router to App Router?

**Answer:** Inventory routes, data dependencies, auth checks, metadata, error behavior, client-only code, and tests first. Move a bounded route group while `pages/` and `app/` coexist, preserve its URL and HTTP contract, and explicitly replace `getServerSideProps`/`getStaticProps` with the chosen App Router server/cache behavior. Keep `pages/api` handlers separate from `app/api` Route Handlers; do not create ambiguous ownership for the same path. Compare output, permissions, cache headers, latency and rollback on the production build before expanding the migration. Pin the target Next.js version and migrate deprecated APIs in a separate, reviewable step.

## System Design Scenarios (31-35)

### 31. Design a system for 1M+ daily active users.

**Answer:** Daily active users do not determine capacity by themselves. Ask for peak requests per second, burst shape, request/read/write mix, payload sizes, geographic distribution, freshness, availability, and latency goals. Then:

1. Serve immutable assets and genuinely public output from a CDN; make cache keys and invalidation match locale, tenant, and content variation.
2. Run request-time Next.js work on a supported runtime near the data it calls. Choose Node or a compatible edge host per dependency and measured latency, not because one is assumed faster.
3. Budget database connections as `pool size × maximum replicas`; use a pooler or bounded service concurrency before read replicas when connection pressure is the bottleneck.
4. Keep authenticated reads private and make checkout/inventory writes transactional and idempotent. Use a queue only for work whose asynchronous acceptance contract is explicit.
5. Load-test cold and warm caches, dependency slowdown, regional loss, and rollout overlap. Add capacity from observed bottlenecks and service objectives rather than a DAU multiplier.

---

### 32. How would you implement a real-time collaborative editing system?

**Answer:** Use a collaboration protocol to identify operations and reconcile concurrent edits, then use WebSockets as transport. Operational Transformation (OT) transforms concurrent operations; a conflict-free replicated data type (CRDT) gives operations/state explicit merge semantics. The transport alone supplies neither.

A connection belongs to one document effect: capture its socket locally, ignore callbacks after cleanup, close that same instance and validate incoming operations. Reconnect from a known document version/snapshot and replay permitted operations with stable identities. Authenticate membership on both read and write. Editing A → switching to B must prevent a late A message from changing B; an acknowledged operation and a sent operation have different recovery states.
---

### 33. Design a globally distributed application.

**Answer:** Choose the consistency and data-residency model before selecting regions. Assign each write to an authoritative region or use a datastore with the required cross-region consistency; a nearby read replica can be stale and is not automatically safe for authorization or checkout. Cache only public, versioned output at the edge. Keep user-specific data in the allowed region, define failover behavior and acceptable data loss, and test recovery as well as normal latency. Geo headers are provider-specific routing hints: trust them only when the ingress overwrites client-supplied values. Rewriting `/eu/...` inside one Next.js deployment changes the route; it does not route execution or data to an EU region.

---

### 34. How would you implement a microservices architecture?

**Answer:** Next.js can act as a Backend for Frontend (BFF), translating a browser-facing contract into calls to internal services. Internal DNS/configured URLs locate services; this is not a full dynamic discovery protocol.

Authenticate the browser request, authorize resource scope, choose an allowlisted internal endpoint and project the service response. Set a timeout/cancellation budget and classify failures. Retry only safe/idempotent operations with a bounded policy. A try/catch that rethrows is not a circuit breaker: a breaker records outcomes and controls closed/open/half-open admission. Avoid forwarding client-supplied destinations or arbitrary credentials into an internal fetch.
---

### 35. Design a system for handling Black Friday traffic spikes.

**Answer:** Establish peak request/checkout rates, cacheable public reads, write invariants and acceptable degradation first. Pre-render popular products and share suitable public output; checkout still verifies current price, stock and identity.

A queue boundary should authenticate → validate an allowlisted cart → use a stable checkout operation key → durably accept the job/order → return 202 with a status resource. “Queued” means accepted for processing, not paid or fulfilled. A worker must handle retries without duplicate orders/charges, and admission/backpressure must protect capacity. If database state and the queue must agree, design their atomicity or use an outbox.

For product reads, a last-successful snapshot may be an explicitly labeled fallback; fail safely when no snapshot exists. Never use that snapshot as authoritative checkout stock or price.

## Follow-Up Questions (36-40)

### 36. What are the trade-offs between SSR and ISR?

**Answer:**

| Aspect | Request-time rendering (SSR) | Incremental Static Regeneration (ISR) |
| ------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| Freshness | Reads request-time data; an upstream/cache layer may still be stale | Reuses generated output until it is eligible for or receives revalidation |
| Response cost | Includes request rendering and uncached dependency latency | Warm output can avoid rendering; cold generation and revalidation still cost work |
| Privacy | Can use request-specific data when authorization and cache headers are correct | Shared output is suitable only when every cache reader may see the same representation |
| Use case | Personal or rapidly changing data | Public content with an explicit stale window |

Choose from required freshness, personalization and failure behavior, not the page's name. “SSR” does not guarantee a fresh database read if an upstream cache reuses its response.

These labels describe the previous App Router cache model and Pages Router choices; they are not an exhaustive Next.js 16 model. With Cache Components enabled, routes can render a static shell and stream dynamic content while selected components/functions opt into caching. Do not cache personalized output as shared ISR data.

---

### 37. How do you handle database connections in Server Components?

**Answer:**

```typescript
// lib/db.ts
import { Pool } from 'pg'

const globalForDb = globalThis as unknown as {
  pool: Pool | undefined
}

export const pool = globalForDb.pool ?? new Pool({
  connectionString: process.env.DATABASE_URL,
})

if (process.env.NODE_ENV !== 'production') {
  globalForDb.pool = pool
}

// Usage in Server Component
export async function getVisibleUserCount(tenantId: string) {
  // tenantId must come from the authenticated, authorized request context.
  const result = await pool.query<{ count: string }>(
    'SELECT COUNT(*)::text AS count FROM users WHERE tenant_id = $1',
    [tenantId],
  )
  return result.rows[0]?.count ?? '0'
}

```

**Connection pooling:** A module-level pool is reused per server process; the global development reference additionally survives hot reload. PostgreSQL `COUNT(*)` can exceed a 32-bit integer, so the query returns its exact decimal representation as text. Limit each replica's pool so total connections stay below the database budget.

---

### 38. How do you implement rate limiting?

**Answer:** Apply limits at the operation that consumes the protected resource, such as login, expensive search, or a write. Choose a key with a documented policy (account, API key, tenant, or trusted client IP), use an atomic shared limiter across replicas, return `429` with a useful retry policy, and instrument rejected/allowed requests. Proxy may reject obvious abuse early, but a per-process map is neither a global quota nor durable under serverless restarts. Trust forwarding headers only when the ingress replaces them; an IP limit alone is not an identity limit.

### 39. How do you handle offline support?

**Answer:** Register a service worker over HTTPS, precache an allowlisted public shell, choose a network/cache policy for each asset class, and show users which data is available offline. Version the cache and remove obsolete entries on activation. Never cache private/API responses by default; define how stale writes synchronize and conflict when connectivity returns. Test install, update, offline navigation, quota pressure and recovery. Next.js prerendering and Cache Components do not themselves provide browser offline storage; the [PWA chapter](../../10.7-html-css/10.7.05-pwa.md) owns the implementation patterns.

### 40. How do you monitor and debug Next.js applications?

**Answer:** Start with user-facing service objectives: route availability and latency, server/client error rates, cache hit and revalidation behavior, and dependency saturation. Instrument the Next.js server through `instrumentation.ts` and OpenTelemetry; add browser Web Vitals separately. Correlate traces and structured logs with request IDs, redact credentials and personal data, and avoid logging raw URLs with sensitive query values. Set sampling and retention deliberately. For debugging, reproduce against the pinned production build and compare server logs, traces, browser errors and deployment/version identifiers. The [deployment chapter](../04-production/10.4.4.03-deploying-nextjs.md) owns the registration example.

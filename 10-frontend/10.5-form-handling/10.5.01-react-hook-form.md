# React Hook Form

A disabled button can prevent a second click, but it cannot tell whether a timed-out booking committed. The form must retain useful input while the server decides whether the booking is valid and unique.

```tsx
const { register, handleSubmit, formState: { errors, isSubmitting } } = useForm<Values>();

<form noValidate onSubmit={handleSubmit(save)}>
  <input {...register('patientId')} aria-invalid={Boolean(errors.patientId)} />
  <p role="alert">{errors.patientId?.message}</p>
  <button disabled={isSubmitting}>{isSubmitting ? 'Saving…' : 'Save'}</button>
</form>
```

## Definition

**React Hook Form (RHF)** connects inputs to a form model, checks their values, handles submission and notifies components about relevant form-state changes. Native inputs can keep their current values in the DOM. Widgets whose values are controlled by React can connect through `Controller`.

> **Textbook Definition:** React Hook Form manages field registration, validation and submission through a form controller and subscriptions. Uncontrolled inputs can retain DOM-owned values, while adapters connect widgets that require controlled values.

RHF coordinates that lifecycle; the server still owns authorization and booking invariants.

## First Principles

Keeping every keystroke in a root React state object re-renders more UI than that keystroke requires — native inputs already hold a value, so RHF registers their refs and handlers and notifies only subscribed views. And validation is not commitment: a valid form can still conflict with another booking, so field feedback, pending state, and server-failure handling are three separate designs.

## 1. Trace Validation, Submission and a Server Error

```tsx
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';

const appointmentSchema = z.object({
  patientId: z.string().trim().min(1, 'Choose a patient'),
  startsAt: z.iso.datetime(),
});
type Values = z.input<typeof appointmentSchema>;
type Parsed = z.output<typeof appointmentSchema>;

export function AppointmentForm({ save }: {
  save: (values: Parsed) => Promise<void>;
}) {
  const { register, handleSubmit, setError, clearErrors,
    formState: { errors, isSubmitting } } = useForm<Values, unknown, Parsed>({
      defaultValues: { patientId: '', startsAt: '' },
      resolver: zodResolver(appointmentSchema),
      mode: 'onBlur',
    });

  async function submit(values: Parsed) {
    clearErrors('root.server');
    try {
      await save(values);
    } catch {
      setError('root.server', { message: 'Could not save. Check the result before retrying.' });
    }
  }

  return <form noValidate onSubmit={handleSubmit(submit)}>
    <label htmlFor="patient">Patient ID</label>
    <input id="patient" {...register('patientId')}
      aria-invalid={Boolean(errors.patientId)} aria-describedby="patient-error" />
    <p id="patient-error" role="alert">{errors.patientId?.message}</p>
    <label htmlFor="starts">Start time (UTC ISO string)</label>
    <input id="starts" {...register('startsAt')}
      aria-invalid={Boolean(errors.startsAt)} aria-describedby="starts-error" />
    <p id="starts-error" role="alert">{errors.startsAt?.message}</p>
    <p role="alert">{errors.root?.server?.message}</p>
    <button disabled={isSubmitting}>{isSubmitting ? 'Saving…' : 'Save'}</button>
  </form>;
}
```

This teaching form uses an ISO-text field to isolate validation; a production date picker needs timezone handling. `register` connects the input, `handleSubmit` validates, the resolver supplies parsed values and the awaited callback keeps `isSubmitting` true while saving. The example deliberately retains values after failure.

Map trusted server field errors to known fields with `setError`; use a root error for network/general failures. An uncertain timeout requires checking the result or retrying with the same logical-operation key. Disabling a button is useful UI feedback, not a durable idempotency guarantee.

## 2. Choose the Field Integration

| Field | Integration | What to connect |
| ----------------------------- | ----------------------------- | -------------------------------------------------------------------------- |
| Native uncontrolled input | register | name, ref, onChange and onBlur |
| Controlled select/date picker | Controller or useController | value, onChange, onBlur, name and focusable ref through the widget's API |
| Repeated rows | useFieldArray | Stable generated field.id as React key; index in the registered field path |
| Nested component | FormProvider + useFormContext | Same form instance, not another independent useForm |

Do not double-register a Controller field. Avoid undefined defaults for controlled widgets; use their documented empty value, such as null. Disabled inputs can be omitted/undefined on submission; use read-only behavior when a displayed value must remain part of the payload.

**Adapt a controlled widget explicitly.** This native controlled select makes the Controller contract visible without a third-party dependency. For a date picker, map its `selected`/`onChange`/focus-ref API in the same way instead of spreading props it does not support.

```tsx
import { Controller, useForm } from 'react-hook-form';

function VisitTypeForm() {
  const { control, handleSubmit } = useForm<{ visitType: string }>({
    defaultValues: { visitType: '' },
  });
  return <form onSubmit={handleSubmit(() => { /* Submit through an awaited API callback. */ })}>
    <label htmlFor="visit-type">Visit type</label>
    <Controller name="visitType" control={control}
      rules={{ required: 'Choose a visit type' }}
      render={({ field, fieldState }) => <>
        <select id="visit-type" name={field.name} ref={field.ref}
          value={field.value} onBlur={field.onBlur}
          onChange={event => field.onChange(event.target.value)}
          aria-invalid={Boolean(fieldState.error)} aria-describedby="visit-type-error">
          <option value="">Choose…</option>
          <option value="consultation">Consultation</option>
          <option value="follow-up">Follow-up</option>
        </select>
        <p id="visit-type-error" role="alert">{fieldState.error?.message}</p>
      </>} />
    <button>Save</button>
  </form>;
}
```

A native select can normally use register; it is controlled here only to isolate the adapter mechanism. Do not call register again for the same Controller field.

**Repeated rows have two identities:**

```tsx
const { fields, append, remove } = useFieldArray({ control, name: 'items' });
// Inside this form's JSX:
fields.map((field, index) => (
  <div key={field.id}>
    <input {...register(`items.${index}.name` as const)} />
    <button type="button" onClick={() => remove(index)}>Remove</button>
  </div>
));
```

This fragment assumes `control`/`register` from a form whose items are `{ name: string }[]`. `field.id` preserves React row identity; the indexed path identifies the row's current place in form data. `append` needs the new row's defaults. Watch current values when calculating totals; the fields array is structural metadata, not a live computed-value subscription.

## 3. Subscribe Only Where the Display Needs Updates

`watch()` at the form root can rerender that root as values change. `useWatch` in a subtotal component narrows the value subscription; `useFormState` can narrow form-state subscriptions. Reading errors, dirty state or a watched value still creates relevant updates. Uncontrolled inputs do not mean “nothing rerenders.”

`dirty` compares values with defaults; `touched` records interaction. Validation mode selects when feedback runs: onSubmit, onBlur, onChange, onTouched or all. Choose from usability and validation cost, rather than making onBlur a universal rule.

Defaults are a baseline, not a prop that automatically tracks every server refresh. Use async defaultValues or `reset(loadedValues)` when loading an edit. Decide whether a refetch should preserve dirty fields before resetting; otherwise it can overwrite unsaved typing.

## 4. Navigate Steps Without Losing the Earlier Values

The following complete mechanism validates only the visible step before advancing and retains unmounted values with `shouldUnregister: false`.

```tsx
import { useRef, useState } from 'react';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';
import { FormProvider, useForm, useFormContext } from 'react-hook-form';

const valuesSchema = z.object({
  name: z.string().trim().min(1, 'Enter your name'),
  email: z.email(),
  preference: z.enum(['', 'email', 'phone', 'none'])
    .pipe(z.enum(['email', 'phone', 'none'], { error: 'Choose a preference' })),
});
type Values = z.input<typeof valuesSchema>;
type ParsedValues = z.output<typeof valuesSchema>;
const fieldsByStep: (keyof Values)[][] = [['name'], ['email'], ['preference']];

function MultiStepForm({ save }: { save: (values: ParsedValues) => Promise<void> }) {
  const methods = useForm<Values, unknown, ParsedValues>({
    resolver: zodResolver(valuesSchema),
    mode: 'onChange',
    defaultValues: { name: '', email: '', preference: '' },
    shouldUnregister: false,
  });
  const [step, setStep] = useState(0);
  const [checking, setChecking] = useState(false);
  const navigationLock = useRef(false);
  async function submit(values: ParsedValues) {
    methods.clearErrors('root.server');
    try {
      await save(values);
    } catch {
      methods.setError('root.server', { message: 'Could not save. Check the result before retrying.' });
    }
  }
  async function next() {
    if (navigationLock.current || step >= fieldsByStep.length - 1) return;
    const validatedStep = step;
    navigationLock.current = true;
    setChecking(true);
    try {
      if (await methods.trigger(fieldsByStep[validatedStep])) {
        setStep(current => current === validatedStep ?
          Math.min(current + 1, fieldsByStep.length - 1) : current);
      }
    } finally {
      navigationLock.current = false;
      setChecking(false);
    }
  }
  return (
    <FormProvider {...methods}>
      <form onSubmit={event => {
        event.preventDefault();
        if (step < fieldsByStep.length - 1) void next();
        else void methods.handleSubmit(submit)(event);
      }}>
        <StepField name={fieldsByStep[step][0]} />
        {step > 0 && <button type="button" disabled={checking} onClick={() => setStep(previous => previous - 1)}>Back</button>}
        {methods.formState.errors.root?.server?.message && (
          <p role="alert">{methods.formState.errors.root.server.message}</p>
        )}
        <button type="submit" disabled={checking || methods.formState.isSubmitting}>
          {methods.formState.isSubmitting ? 'Saving…' : step === fieldsByStep.length - 1 ? 'Submit' : 'Next'}
        </button>
      </form>
    </FormProvider>
  );
}

function StepField({ name }: { name: keyof Values }) {
  const { register, formState: { errors } } = useFormContext<Values>();
  const field = register(name);
  return <>
    <label htmlFor={name}>{name}</label>
    {name === 'preference' ? (
      <select id={name} {...field} aria-invalid={Boolean(errors[name])} aria-describedby={`${name}-error`}>
        <option value="">Choose a contact preference</option>
        <option value="email">Email</option>
        <option value="phone">Phone</option>
        <option value="none">No preference</option>
      </select>
    ) : (
      <input id={name} type={name === 'email' ? 'email' : 'text'} {...field}
        aria-invalid={Boolean(errors[name])} aria-describedby={`${name}-error`} />
    )}
    <p id={`${name}-error`} role="alert">{errors[name]?.message}</p>
  </>;
}
```

`trigger` checks the named step before navigation; `handleSubmit` applies the complete schema before calling `save`. A rejected save leaves the values in place and displays a root error. The server must still validate, authorize and enforce any uniqueness or retry-safety invariant. The email field checks email syntax; the preference field accepts a blank editing value but requires one of the listed choices in parsed output. FormProvider shares the form instance; it does not persist data across a page reload.

## 5. Keep Asynchronous Checks Advisory

A username or slot-availability check can become outdated before submit. Debounce appropriately, encode query values, handle non-success responses and prevent older responses from replacing feedback for newer input. Display pending validation separately from pending submission.

Async checks improve feedback; a server uniqueness constraint or booking transaction enforces the invariant. Offline/error responses must not be interpreted as “available.” Do not log patient data or credentials through a demo submit callback in production.

## Summary

RHF connects field values to validation and an awaited submission lifecycle. Choose register or Controller from the widget contract, subscribe where feedback is displayed, preserve edit defaults deliberately and validate the full payload at the server boundary. Field state and business correctness remain separate responsibilities.

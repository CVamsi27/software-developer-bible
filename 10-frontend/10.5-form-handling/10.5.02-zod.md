# Zod

## Definition

**Zod** checks runtime values against schemas and derives TypeScript types from those schemas. This chapter targets Zod 4. `parse` returns parsed data or throws; `safeParse` returns a success/error result.

> **Textbook Definition:** Zod is a runtime schema system that parses values into a checked result or a structured failure and derives corresponding TypeScript types. Transformations can give a schema different input and output types.

An API can declare `age: number` in TypeScript and still receive `"42"`, null or an object over HTTP. Static types disappear at runtime. A schema checks the actual value before application code treats it as valid data.

## First Principles

Serialized data crosses a trust boundary without carrying a runtime TypeScript guarantee. A cast changes the compiler's belief, not the value. A parser must either produce a value satisfying the contract or explain why it cannot.

Normalization makes the result different from the raw input. A schema can accept a string and produce a number; therefore **input type** and **output type** must remain separate.

## Trace a string into a parsed value

```typescript
import { z } from 'zod';

export const ageSchema = z.string().trim().regex(/^\d+$/)
  .transform(Number).pipe(z.number().int().min(0).max(150));
type AgeInput = z.input<typeof ageSchema>;   // string
type AgeOutput = z.output<typeof ageSchema>; // number; z.infer is also output

const result = ageSchema.safeParse(' 42 ');
if (result.success) {
  console.log(result.data + 1); // 43, not string concatenation
} else {
  console.log(result.error.issues.map(issue => issue.path));
}
```

Trim runs before the digit check; the transform converts only accepted digit strings; the pipe validates the resulting numeric range. Empty text and `"abc"` fail instead of silently becoming a usable age. Neither parse style performs authorization or establishes that the person exists.

## Build schemas from distinct mechanisms

### Express shapes and derive their output types

```typescript
import { z } from 'zod';

// Primitives
const name = z.string();
const age = z.number().int().positive();
const isActive = z.boolean();

// String validators
const email = z.email();
const url = z.url();
const uuid = z.uuid();
const slug = z.string().regex(/^[a-z0-9-]+$/);

// Object schema
const userSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1).max(100),
  email: z.string().email(),
  age: z.number().int().min(0).max(150).optional(),
  role: z.enum(['admin', 'user', 'guest']).default('user'),
  createdAt: z.date(),
});

// Type inference — single source of truth
type User = z.infer<typeof userSchema>;
// → { id: string; name: string; email: string; age?: number; role: 'admin' | 'user' | 'guest'; createdAt: Date }
```

### Compose nested values and tagged alternatives

```typescript
// Nested objects
const addressSchema = z.object({
  street: z.string(),
  city: z.string(),
  state: z.string().length(2),
  zip: z.string().regex(/^\d{5}(-\d{4})?$/),
  country: z.string().default('US'),
});

// Arrays with constraints
const tagsSchema = z.array(z.string().min(1)).min(1).max(10);

// Tuples
const coordSchema = z.tuple([z.number(), z.number()]);

// Discriminated unions (great for API responses)
const eventSchema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('click'), x: z.number(), y: z.number() }),
  z.object({ type: z.literal('keypress'), key: z.string() }),
  z.object({ type: z.literal('scroll'), offset: z.number() }),
]);

// Records
const metadataSchema = z.record(z.string(), z.union([z.string(), z.number()]));
```

### Normalize after a check or preprocess before it

```typescript
// Transform: normalize on parse
const formSchema = z.object({
  email: z.string().trim().toLowerCase().pipe(z.email()),
  age: ageSchema, // Reuse the canonical string-to-number parser above.
  birthday: z.iso.date().transform((v) => new Date(`${v}T00:00:00Z`)).pipe(z.date()),
});

// Preprocess: accept multiple input shapes
const numberFromAnything = z.preprocess(
  (v) => (typeof v === 'string' && v.trim() !== '' ? Number(v) : v),
  z.number()
);

// Coercion (built-in shortcut)
const numberFromForm = z.string().trim().min(1).pipe(z.coerce.number());
// z.coerce.number() alone follows Number(): null and an empty string become 0.
```

### Attach cross-field issues to the right path

```typescript
const passwordSchema = z
  .object({
    password: z.string().min(8),
    confirmPassword: z.string(),
  })
  .superRefine((data, ctx) => {
    if (data.password !== data.confirmPassword) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        message: 'Passwords do not match',
        path: ['confirmPassword'],
      });
    }
  });

// Alternative: .refine (single-condition, single-path)
const sameAs = z
  .object({ password: z.string(), confirm: z.string() })
  .refine((d) => d.password === d.confirm, {
    message: 'Passwords do not match',
    path: ['confirm'],
  });
```



### Decide what omitted, null and extra fields mean

| Schema choice | Contract |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| optional() | Accept undefined/omission; does not imply null |
| nullable() | Accept null; does not imply omission |
| nullish() | Accept both null and undefined |
| default(value) | Supply a value for undefined; in Zod 4 it short-circuits parsing with an output-compatible default |
| z.object(...) | Strip unknown keys by default |
| z.strictObject(...) | Reject unknown keys |
| z.looseObject(...) | Preserve unknown keys |

Composition with extend, pick, omit and partial derives related shapes. Making every field optional does not by itself define a safe PATCH contract: restrict writable fields and decide whether an empty update is valid. Extending refined objects requires care; use a compatible composition strategy, including safeExtend where appropriate, to preserve refinement behavior.

Coercion follows JavaScript conversion rules: `z.coerce.number()` accepts an empty string or null as zero; `z.coerce.boolean()` turns the nonempty string `"false"` into true. Gate input shapes or explicitly map accepted textual values before conversion. A brand creates a static type distinction; it is not runtime authorization. [Zod schema API](https://zod.dev/api)

## Choose error control flow at the boundary

Use safeParse when invalid input is an expected result and parse when exception-based handling fits the caller. Both execute the schema. Issues carry paths, codes and messages; `z.flattenError(error)` is useful for shallow field feedback, while nested paths need a suitable mapping/tree representation.

Refinements can collect multiple issues. They do not universally stop at the first invalid field, and a refinement may not run after a non-continuable type failure. Keep refinements pure where possible. Async refinements/transforms require parseAsync or safeParseAsync; remote checks can become outdated before a transaction commits.

### Revalidate responses as well as requests when needed

```typescript
// Client-side: validate API response
const userResponseSchema = z.object({
  id: z.string().uuid(),
  name: z.string(),
  email: z.string().email(),
  createdAt: z.string().datetime(),
});

export async function fetchUser(id: string) {
  const res = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data = userResponseSchema.parse(await res.json());
  return data; // inferred response shape: createdAt remains an ISO string, not Date
}

```

This response contract keeps createdAt as an ISO string. `z.date()` expects a Date object, which ordinary JSON does not preserve. Parse before converting dates or consuming a response whose runtime shape is untrusted. A malformed JSON body can fail before Zod runs; an HTTP handler must map that error too.

For request writes, allowlist writable fields, authenticate the caller, enforce tenant/resource access and commit database invariants transactionally. Passing parsed.data directly to an unrestricted ORM write can still permit a business-security bug.

## Validate startup configuration without leaking it

```typescript
const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']),
  DATABASE_URL: z.url(),
  API_KEY: z.string().min(1),
  PORT: z.string().trim().regex(/^\d+$/)
    .transform(Number).pipe(z.number().int().min(1).max(65535))
    .default(3000),
});
// Export the parsed result; do not log the raw environment or secret values.
const env = envSchema.parse(process.env);
```

Fail startup on missing required configuration. A URL parser checks structure, not whether the database is reachable. Add operational readiness checks separately.

## Place each integration at its own boundary

Share contracts between client/server when they express the same public shape. Revalidate on the server even when the browser has already parsed the form. Use separate internal/storage schemas when their permissions or representations differ.

The [RHF chapter](10.5.01-react-hook-form.md) owns resolver wiring and field feedback. tRPC can attach input/output schemas at procedure boundaries; generated static client types still do not validate every arbitrary external value. Avoid replacing unconstrained input with z.any; use unknown until it is parsed.

Benchmark representative schemas and payload sizes. Async I/O can dominate parsing cost; Zod Mini has a separate functional API for bundle-sensitive cases. Do not infer a fixed bundle size from one method import.

## Summary

Parse actual values at trust boundaries and consume the parsed output. Composition, refinement, transformation and coercion have different responsibilities. Preserve input/output types, map errors to the intended UI/API contract and enforce authorization and transactional business rules beyond schema validity.

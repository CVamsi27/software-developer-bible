# Formik

## Definition

Formik coordinates a React form's controlled values, field interaction, validation and submission. `<Formik>` supplies context; `useFormik` exposes the same core helpers directly. `<Field>` and `useField` connect inputs to that model.

> **Textbook Definition:** Formik is a form-state library that manages controlled values and validation/submission state through React state and context. Application services remain responsible for authorization, persistence and business invariants.

Consider a login form: typing changes the form model, blur changes whether an error is visible, and submit must distinguish a rejected password from a network failure. These are related states, but they mean different things.

## First Principles

A controlled input displays the value held in React state. Its change handler must update that value or typing cannot persist. Several fields also need shared state: validation may compare two values, and submission needs one complete payload. Context supplies that common owner.

A value change, a field blur and a completed server write are separate events. `touched` describes interaction; `isSubmitting` describes the submission cycle. Neither proves a business operation committed. Keep validation feedback and server failure recovery separate.

## Follow an edit through submit

```text
change → update values → run configured validation → update errors
blur   → mark touched → show relevant feedback
submit → touch fields → validate all → await valid submission → settle pending
```

Formik's submit cycle touches fields so errors in unvisited controls can become visible. Invalid values stop the submit handler. An async handler's returned promise lets Formik settle pending state; a synchronous handler must call `setSubmitting(false)` itself. Calling an async service without returning/awaiting it breaks that ownership contract.

## Submit and retain input after failure

This Formik 2 example accepts an application adapter that resolves only after the login operation succeeds and throws on failure. It catches expected feedback without clearing the entered values.

```tsx
import { Formik, Form, Field, ErrorMessage } from 'formik';
import * as Yup from 'yup';

type Values = { email: string; password: string };
const loginSchema = Yup.object({
  email: Yup.string().email('Enter a valid email').required('Required'),
  password: Yup.string().required('Required'),
});

export function LoginForm({ login }: { login: (values: Values) => Promise<void> }) {
  return <Formik<Values>
    initialValues={{ email: '', password: '' }}
    validationSchema={loginSchema}
    onSubmit={async (values, helpers) => {
      helpers.setStatus(undefined);
      try {
        await login(values);
      } catch {
        helpers.setStatus('Could not sign in. Check the result before retrying.');
      }
    }}>
    {({ isSubmitting, errors, touched, status }) => <Form noValidate>
      <label htmlFor="login-email">Email</label>
      <Field id="login-email" name="email" type="email" autoComplete="username"
        aria-invalid={Boolean(touched.email && errors.email)} aria-describedby="email-error" />
      <ErrorMessage id="email-error" name="email" component="p" />
      <label htmlFor="login-password">Password</label>
      <Field id="login-password" name="password" type="password" autoComplete="current-password"
        aria-invalid={Boolean(touched.password && errors.password)} aria-describedby="password-error" />
      <ErrorMessage id="password-error" name="password" component="p" />
      {status && <p role="alert">{status}</p>}
      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? 'Signing in…' : 'Sign in'}
      </button>
    </Form>}
  </Formik>;
}
```

A login form accepts the existing credential policy; imposing a new registration password length here could prevent a valid existing account from logging in. Never log credential values. Button disabling is feedback, not a server-side repeated-operation guarantee.

## Connect reusable fields to context

```tsx
import { useField } from 'formik';

type TextFieldProps = { name: string; label: string; type?: string };
export function TextField({ name, label, type = 'text' }: TextFieldProps) {
  const [field, meta] = useField<string>(name);
  const hasError = Boolean(meta.touched && meta.error);
  return <div>
    <label htmlFor={name}>{label}</label>
    <input {...field} id={name} type={type}
      aria-invalid={hasError} aria-describedby={`${name}-error`} />
    <p id={`${name}-error`}>{hasError ? meta.error : ''}</p>
  </div>;
}
```

Render this inside a Formik provider with a matching initial value. `useField` accepts a field name/configuration; `FieldProps` is a render-prop result containing field/form/meta, so it is not the right props type for a component called as `<TextField name="email" ... />`. A richer input wrapper can add typed field paths and native attributes deliberately.

`useFormik` returns helpers directly. Its hook alone does not create context for `<Field>`, `<ErrorMessage>` or `useField`; use its controlled helpers or provide compatible Formik context when using those components.

## Array rows have both identity and position

`FieldArray` supplies `push`, `remove` and related structural helpers. A path such as `items.1.name` identifies the second current value; a stable row ID identifies the same row as its position changes.

```tsx
// Fragment inside Formik's render function; values.items contains { id, name }.
<FieldArray name="items">
  {({ push, remove }) => <>
    {values.items.map((item, index) => <div key={item.id}>
      <label htmlFor={`item-${item.id}`}>Item name</label>
      <Field id={`item-${item.id}`} name={`items.${index}.name`} />
      <button type="button" onClick={() => remove(index)}>Remove item</button>
    </div>)}
    <button type="button" onClick={() => push({ id: crypto.randomUUID(), name: '' })}>
      Add item
    </button>
  </>}
</FieldArray>
```

Import `FieldArray` and `Field` from Formik. Generate initial row IDs once when loading/creating the form, not during every render. Removing row zero shifts the remaining indexed paths, while stable React keys preserve each remaining row's local UI state. Validate array-level and individual-row constraints separately; nested errors can be strings or nested structures, so inspect them before rendering.

## Validation, conversion and defaults have distinct jobs

Yup can be supplied through `validationSchema`; a custom `validate(values)` returns an error shape corresponding to the values. Field validators check local requirements, and form-level checks handle dependencies. Show feedback on blur, change or submit according to interaction needs and validation cost.

A validation adapter does not automatically replace Formik's stored/submitted values with a schema's transformed result. Parse explicitly at the submission boundary when normalization is required. Zod needs a compatible adapter/custom validate function; passing a Zod object directly as Yup's `validationSchema` is not the same API. Verify adapter support against pinned versions.

`initialValues` defines the baseline. `resetForm({ values: acceptedValues })` can establish a confirmed new baseline; resetting in `finally` discards input on failure. `enableReinitialize` responds to changed initial values, but can overwrite unsaved edits. Decide what a background refetch should do before enabling it.

## Advance a wizard without confusing it with completion

One Formik owner can retain the full value shape while individual steps mount/unmount. Validate the visible step before advancing; validate the full schema again before the final write. A server must enforce the full contract regardless of which client steps were visited.

If “Next” is handled through a synchronous `onSubmit`, call `setSubmitting(false)` after changing steps. Otherwise the form can remain pending and the next button stay disabled. A cleaner design can use `type="button"` for step navigation and an explicit validation helper, reserving submit for final commitment. Serialize asynchronous navigation and prevent an older validation result from skipping a newer step.

Keeping values in context survives step unmounts, not a page reload. Use the [draft chapter](10.5.06-autosave-draft-recovery.md) for recovery, write ordering and conflicts.

## Choose by the actual interaction contract

| Concern | Formik | React Hook Form | TanStack Form |
| ----------------- | ------------------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------- |
| Value integration | Controlled state/context | Native registration plus controlled-widget adapters | Controlled model with field/store subscriptions |
| Existing code | Preserve useful Formik/Yup integrations | Preserve RHF defaults/resolver contracts | Preserve typed defaults/validator contracts |
| Rendering cost | Profile context consumers; FastField isolates suitable independent fields | Profile watch/form-state subscribers and Controllers | Profile chosen field/store selectors |
| Schema output | Parse normalized output explicitly | Compatible resolver can supply parsed output | Parse normalized output explicitly |

Do not infer bundle size, release status or a universal winner from the library name. Measure the chosen production imports, representative editing workload, accessibility, tests and migration cost. `FastField` is useful only when its field is sufficiently independent; dependent cross-field displays still need appropriate subscriptions.

## Common Mistakes

| Mistake | Repair |
| ---------------------------------------------------------------- | -------------------------------------------------------------- |
| Fire-and-forget the service inside onSubmit | Return/await its promise and handle failure feedback |
| Reset after every settled attempt | Reset after confirmed success with the intended baseline |
| Keep isSubmitting true on a synchronous step advance | Explicitly settle the synchronous cycle or separate navigation |
| Key removable rows by index | Use stable row identity and current indexed field paths |
| Treat browser validation as authoritative | Parse and authorize again at the server write |
| Migrate solely from an unsupported maintenance/performance claim | Verify project needs, compatibility and measured cost |

## Summary

Formik gives controlled inputs one shared state owner. Trace change, blur, validation and awaited submission separately; retain useful input on failure and establish reset baselines deliberately. Stable row identity, complete final validation and server authorization protect behavior that a form library cannot guarantee.

# Server Actions & Modern Form Patterns

A form needs a clear path from editable values to an authorized server write and useful feedback. Follow that path through a Next.js Server Action, pending state and recoverable validation errors.

```tsx
// app/contact/ContactForm.tsx
'use client';
import { useActionState } from 'react';
import { submitContact } from './actions';

export function ContactForm() {
  const [state, formAction, pending] = useActionState(submitContact, { ok: false });
  return (
    <form action={formAction}>
      <input name="email" type="email" required />
      <button disabled={pending}>{pending ? 'Sending…' : 'Send'}</button>
      {state.errors?.email?.[0] && <p role="alert">{state.errors.email[0]}</p>}
    </form>
  );
}
```

## Definition

A React **Server Function** runs on the server and can be invoked through a framework-supported form action. Next.js calls these mutation handlers **Server Actions**. React Router route actions are a separate request/response mechanism; do not copy their imports or lifecycle into a Next.js action.

> **Textbook Definition:** A server-backed form transports submitted values to an authoritative mutation handler and presents pending, validation and completion states. Framework-supported actions coordinate that transport; business invariants and duplicate-write protection remain application responsibilities.

This chapter targets React 19 with the Next.js App Router. The framework supplies transport; the application still owns validation, authorization, persistence, error feedback and cache refresh.

## First Principles

Three facts shape every server-backed form. **A response can disappear after the write commits** — pending UI reduces accidental clicks, but only a server-side idempotency contract handles retries. **Every invocation crosses a trust boundary** — TypeScript types, bound arguments, and browser constraints neither authorize the caller nor validate received values. **A form needs a recovery path** — expected errors return safe state the UI can display while preserving input; unexpected failures belong in error handling and observability.

## How It Works

### 1. Follow the Submission to the Server

The browser submits successful named controls as `FormData`. A stateful action receives the previous state followed by that payload, validates it, performs an authorized mutation and returns the next state. `useActionState` connects that result to the form. A direct action that redirects instead may return `Promise<void>` and omit the stateful wrapper.

A framework-supported server action can submit before hydration. For a dynamic page, the optional `permalink` passed to `useActionState` names the page that must render the same form with the same action so React can carry returned state there. An `onSubmit` handler that waits for client JavaScript and then calls a server function is a different path; it does not provide that form-action behavior.

### 2. Validate the Received Fields Before Writing

```typescript
// app/contact/actions.ts
'use server';
import { z } from 'zod';
import { revalidatePath } from 'next/cache';
import { saveContactMessage } from '@/lib/contact-service';

export type ContactState = {
  ok: boolean;
  errors?: { email?: string[]; message?: string[] };
};
const schema = z.object({
  email: z.email(),
  message: z.string().trim().min(10).max(5000),
});

export async function submitContact(
  _previous: ContactState,
  formData: FormData,
): Promise<ContactState> {
  const parsed = schema.safeParse({
    email: formData.get('email'),
    message: formData.get('message'),
  });
  if (!parsed.success) {
    return { ok: false, errors: z.flattenError(parsed.error).fieldErrors };
  }
  // Application service: enforce abuse limits, safe persistence and any
  // authentication/authorization required by this particular operation.
  await saveContactMessage(parsed.data);
  revalidatePath('/contact');
  return { ok: true };
}
```

`saveContactMessage` is an application dependency, not a built-in API. This public contact example intentionally stores no passwords. Registration belongs in an authentication service that hashes passwords and enforces its credential policy.

### 3. Return Errors That the Form Can Explain

```tsx
// app/contact/ContactForm.tsx
'use client';
import { useActionState } from 'react';
import { submitContact, type ContactState } from './actions';

const initialState: ContactState = { ok: false };
export function ContactForm() {
  const [state, formAction, pending] = useActionState(
    submitContact, initialState, '/contact',
  );
  return (
    <form action={formAction}>
      <label htmlFor="contact-email">Email</label>
      <input id="contact-email" name="email" type="email" required
        aria-invalid={Boolean(state.errors?.email)}
        aria-describedby={state.errors?.email ? 'email-error' : undefined} />
      {state.errors?.email?.[0] && (
        <p id="email-error" role="alert">{state.errors.email[0]}</p>
      )}
      <label htmlFor="contact-message">Message</label>
      <textarea id="contact-message" name="message" required minLength={10}
        maxLength={5000} aria-invalid={Boolean(state.errors?.message)}
        aria-describedby={state.errors?.message ? 'message-error' : undefined} />
      {state.errors?.message?.[0] && (
        <p id="message-error" role="alert">{state.errors.message[0]}</p>
      )}
      <button type="submit" disabled={pending}>
        {pending ? 'Sending…' : 'Send'}
      </button>
      <p role="status">{state.ok ? 'Message sent.' : ''}</p>
    </form>
  );
}
```

The `/contact` route renders this same component. When the action resolves, React resets uncontrolled controls — even if the returned state contains validation errors. To preserve submitted values, return safe values in the state and restore them deliberately, or use controlled fields. Never echo credentials into action state.

**A reusable button with `useFormStatus`:**

```tsx
'use client';
import { useFormStatus } from 'react-dom';
export function SubmitButton() {
  const { pending } = useFormStatus();
  return <button type="submit" disabled={pending}>
    {pending ? 'Saving…' : 'Save'}
  </button>;
}
```

Render this button **inside** the form. A hook called in the component that creates that form cannot observe its own newly created descendant form.

### 4. Receive Files Within an Explicit Policy

`FormData.get('attachment')` returns a `File` or `null`. The browser's `accept` attribute and the submitted filename or MIME type are hints, not proof of content. On the server, allow only the formats the product needs, enforce size limits, and validate content with signature checks plus format-aware decoding where appropriate. Apply decompressed-size limits to archives. Generate the storage name and keep uploads private until any required scanning or processing passes. Authorize both upload and later download; never use the supplied filename as a storage path.

Next.js limits a Server Action request body to 1 MB by default. That is the full multipart request, including boundaries and form fields, so the usable file limit is lower. For larger files, upload to object storage with a short-lived, scoped policy, then have an authorized server action verify ownership and finalize the stored object. Increasing `serverActions.bodySizeLimit` is a deliberate resource decision, not a substitute for file validation or infrastructure limits. See the [Next.js configuration](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions) and [OWASP File Upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

### 5. Decide What Happens After the Write

Binding an object ID with `action.bind(null, id)` is convenient transport, not authorization. Resolve the current session and verify permission to modify that object inside the action. Treat hidden fields and bound values as untrusted inputs.

Refresh the paths or tags whose cached data changed using the APIs appropriate to the installed Next.js version. A write does not automatically invalidate every cache. See the canonical [Next.js Server Actions chapter](../10.4-next.js/03-data-and-caching/10.4.3.02-server-actions.md) for cache semantics, redirects and error boundaries.

For payments or other costly effects, use a stable operation key enforced by the persistence service. A disabled button and a transport retry policy cannot guarantee a single effect. Optimistic state is provisional: reconcile it with the authoritative server result and display failure recovery. See [React hooks](../10.3-react/INDEX.md).

### 6. Choosing the Form Boundary

| Need | Starting point |
| --------------------------------------------------- | ----------------------------------------------------- |
| Simple mutation with navigation on success | Server action plus redirect |
| Inline validation and pending feedback | Direct server function passed to `useActionState` |
| Rich client field arrays or cross-field interaction | RHF or TanStack Form, with explicit server validation |
| HTTP clients beyond this React application | A documented API endpoint |
| React Router application | Its route action and `<Form method="post">` contract |

A client library may improve editing behavior, but an `onSubmit` JavaScript handler alone needs JavaScript to run. Test the actual no-JavaScript and pre-hydration paths before promising progressive enhancement. `useActionState` returns expected validation failures as state; thrown unexpected failures reach the nearest error boundary. Its state and the function's arguments must follow React's supported serialization contract when they cross the server boundary.

## Summary

Connect the server function directly to the framework-supported form path, use action state for expected errors, and place form-status consumers inside the form. Validate and authorize every invocation, refresh affected caches explicitly, and enforce retry safety where the effect commits. Keep client editing conveniences separate from the server's trust boundary.

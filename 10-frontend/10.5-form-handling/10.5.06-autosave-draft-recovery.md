# Autosave & Draft Recovery

> Long forms lose users when a tab crashes, a session expires, or a laptop dies mid-entry. This file covers the full draft-recovery stack: debounced autosave, localStorage vs IndexedDB trade-offs, multi-step form resume, dirty-state guards, versioned draft migrations, and conflict resolution when the server copy moved on.

## Definition

**Autosave** writes an evolving draft without an explicit submission. **Draft recovery** loads a saved snapshot, validates its envelope, migrates its schema and offers it back to the user. Saving a draft and submitting a finished record are different operations: an incomplete draft must not be rejected merely because the final form requires every field.

## First Principles

1. **A keystroke is not a durable write.** Debouncing deliberately creates a loss window; continuous typing can postpone a trailing debounce indefinitely unless a maximum wait is configured.
2. **Reads and writes can race.** Restoring after autosave starts can overwrite the saved draft; two asynchronous saves can complete in reverse order; a delayed save can recreate a cleared draft.
3. **A timestamp is not a conflict protocol.** Device clocks differ. Detect server conflicts with a revision/ETag and conditional write, then ask the user to merge or choose a version.

## Why It Matters

A recovery feature only builds trust if it can say what was saved and when saving failed. Start with one form: edit, wait for a saved acknowledgment, reload, restore, submit and verify that the draft stays deleted. Then test failure, concurrent tabs and an application update with an older draft.

## How It Works

```text
load → validate envelope → migrate → validate draft values → offer recovery
                                                        ↓
                                            enable form + subscription
                                                        ↓
edit → capture snapshot → debounce + max wait → serialize saves → acknowledge

successful submit → stop subscription/timers → drain writes → clear draft
```

The UI distinguishes **editing**, **saving**, **saved**, **save failed** and **conflict**. `isDirty` from a form library compares values to its default/reset baseline; it is not a persistence acknowledgment. A restored draft can be pristine relative to that baseline and still need a final submit.

### Choose the store

| Concern | localStorage | IndexedDB | Server draft |
| -------- | ------------------------------------------- | ----------------------------------------- | ---------------------------- |
| API | Synchronous strings | Asynchronous structured clone | Network request |
| Best fit | Small snapshots | Larger data and blobs | Cross-device recovery |
| Failure | Policy/quota/serialization | Quota/abort/blocked upgrade | Offline/conflicting revision |
| Lifetime | Can be cleared or evicted by browser policy | Best effort unless persistence is granted | Server retention policy |

Neither browser store makes a “never lose input” guarantee. `visibilitychange` when hidden is a useful best-effort flush signal, but an async write started on `pagehide` or unmount may be terminated before commit. Save during normal use, report failures and design server recovery for important records. Read [Browser Storage](../10.7-html-css/10.7.08-browser-storage.md) for the canonical IndexedDB connection and transaction helpers.

## Code Examples

### A versioned envelope with a base revision

```typescript
interface DraftEnvelope<T> {
  v: number;
  formId: string;            // include account/tenant identity in the storage key
  updatedAt: number;         // display/audit hint, not ordering authority
  baseRevision: string;      // server revision this edit started from
  step?: number;
  values: T;
}

interface DraftStore<T> {
  save(draft: DraftEnvelope<T>): Promise<void>; // resolves only after commit
  clear(formId: string): Promise<void>;
}
```

Avoid patient records or other sensitive payloads in an unencrypted shared-device draft by default. Authentication cookies do not protect JavaScript-readable storage. Decide account scoping, logout clearing and retention with the actual product threat model.

### Serialize saves and prevent resurrection after submit

```typescript
function createDraftWriter<T>(
  store: DraftStore<T>,
  formId: string,
  onError: (error: unknown) => void,
  delayMs = 800,
  maxWaitMs = 5000,
) {
  if (delayMs < 0 || maxWaitMs <= 0 || !Number.isFinite(delayMs + maxWaitMs)) {
    throw new RangeError('Invalid save delay');
  }
  let active = true;
  let editSequence = 0;
  let latest: DraftEnvelope<T> | undefined;
  let timer: ReturnType<typeof setTimeout> | undefined;
  let maxTimer: ReturnType<typeof setTimeout> | undefined;
  let queue: Promise<void> = Promise.resolve();

  function cancelTimers() {
    clearTimeout(timer);
    clearTimeout(maxTimer);
    timer = maxTimer = undefined;
  }

  function flush() {
    cancelTimers();
    if (!active || !latest) return queue;
    const snapshot = latest;
    const snapshotSequence = editSequence;
    latest = undefined;
    queue = queue.then(async () => {
      try {
        await store.save(snapshot);
      } catch (error) {
        // Keep the failed snapshot unless a newer edit has already arrived.
        if (active && snapshotSequence === editSequence) latest ??= snapshot;
        onError(error);
      }
    });
    return queue;
  }

  return {
    schedule(draft: DraftEnvelope<T>) {
      if (!active) return;
      if (draft.formId !== formId) throw new Error('Wrong draft identity');
      editSequence++;
      latest = structuredClone(draft); // callers may continue editing their object
      clearTimeout(timer);
      timer = setTimeout(() => { void flush(); }, delayMs);
      maxTimer ??= setTimeout(() => { void flush(); }, maxWaitMs);
    },
    flush,
    async stopAndClear() {
      active = false;
      cancelTimers();
      latest = undefined;
      await queue;                    // already-started saves finish before deletion
      await store.clear(formId);
      latest = undefined;             // discard any failed-save recovery snapshot
    },
  };
}
```

One writer serializes saves for **one form in one tab**. It does not coordinate other tabs or devices. In production expose a saved revision and pending/error state, retry failed writes deliberately and bound queue growth if the store is slow. Use a cross-tab ownership/merge policy where concurrent browser editing is allowed.

### Validate and migrate before restoring

```typescript
import { z } from 'zod';

const envelopeSchema = z.object({
  v: z.number().int().positive(),
  formId: z.string(),
  updatedAt: z.number().finite(),
  baseRevision: z.string(),
  step: z.number().int().nonnegative().optional(),
  values: z.unknown(),
});
const oldValues = z.object({ name: z.string(), coverLetter: z.string() });
const draftValues = z.object({
  fullName: z.string().max(200),         // incomplete input is a valid draft
  motivation: z.string().max(2000),
});

function restoreDraft(raw: unknown, expectedFormId: string) {
  const draft = envelopeSchema.parse(raw);
  if (draft.formId !== expectedFormId) throw new Error('Wrong draft identity');
  if (draft.v === 1) {
    const old = oldValues.parse(draft.values);
    return {
      ...draft, v: 2,
      values: draftValues.parse({ fullName: old.name, motivation: old.coverLetter }),
    };
  }
  if (draft.v !== 2) throw new Error('Unsupported draft version');
  return { ...draft, values: draftValues.parse(draft.values) };
}
```

Catch load/parse errors at the recovery UI and preserve the original bytes for an explicit recovery/export path. An unknown version must not silently “break” a migration loop and enter the new form. Do not cast `unknown` to a record and dereference its nested values.

### Wire the form lifecycle

With React Hook Form, finish loading/validating the draft, call `reset(restored.values)`, and only then enable autosave and input editing. Prefer the documented `subscribe({ formState: { values: true }, callback })` API for observation without rendering; `watch()` in render serves a different purpose. Unsubscribe before successful-submit cleanup, call `writer.stopAndClear()`, and create a fresh writer if the user starts another draft.

A “Start over” button inside a form needs `type="button"`. Keep default values for a genuinely blank form: `reset()` without arguments after `reset(restored.values)` restores the *restored* baseline, not necessarily empty values. Persist wizard step and values together, validate that `0 <= step < steps.length`, and do not read undeclared envelope fields.

## Conflict Resolution

Save the server's revision when editing begins. Send a conditional mutation (`If-Match` or a transaction comparing that revision). A mismatch returns a conflict containing the current server version; the UI preserves the local draft and lets the user merge or choose deliberately. `updatedAt` helps explain the two copies but cannot establish which device's write is authoritative.

## Common Mistakes

| Mistake | Consequence | Correction |
| ------------------------------------------ | ------------------------------------- | ---------------------------------------------------- |
| Trailing debounce with continuous typing | Nothing commits until typing stops | Add maximum wait and visible saved state |
| Resolve IndexedDB write on request success | Transaction can later abort | Resolve on transaction complete; reject on abort |
| Autosave before recovery finishes | Empty/new values overwrite saved work | Gate editing and subscription on recovery completion |
| Clear while a save is in flight | Deleted draft reappears | Stop scheduling, drain writes, then clear |
| Use final required schema for a draft | Partial work fails restoration | Define a bounded incomplete-draft schema |
| Trust a client timestamp | Clock skew silently wins a conflict | Compare authoritative server revisions |
| Suppress quota/policy errors | UI falsely says saved | Report failure and preserve unsaved input |

## Summary

Draft recovery is an ordering and acknowledgment contract. Restore before subscribing, serialize saves, acknowledge actual commits and stop pending work before clearing. Versioned partial-input schemas protect old drafts; server revisions detect conflicts. Debounce and lifecycle flushes reduce loss but do not make browser storage infallible.

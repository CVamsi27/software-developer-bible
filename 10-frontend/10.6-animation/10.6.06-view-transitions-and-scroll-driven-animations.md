# View Transitions API & CSS Scroll-Driven Animations

A navigation update needs its old and new visual states captured at the right time. A scroll-linked effect needs progress tied to position rather than elapsed time. These browser APIs provide those lifecycles while ordinary navigation and visible content remain the fallback.

```javascript
function toggleTheme() {
  const update = () => document.documentElement.classList.toggle('dark');
  if (!document.startViewTransition ||
      matchMedia('(prefers-reduced-motion: reduce)').matches) {
    update();
    return;
  }
  document.startViewTransition(() => { update(); });
}
```

## Definition

A **view transition** animates between images of the old and new visual states, called **snapshots**. For a change within the same document, put the DOM update inside `document.startViewTransition`. For compatible navigation between documents from the same origin, both documents can opt in through CSS. A **scroll-driven animation** uses scroll progress rather than elapsed time. Its timeline can follow the scroll position or an element moving through the visible scrolling area, called the **scrollport**.

> **Textbook Definition:** View transitions interpolate visual snapshots across a document-state change or eligible navigation. Scroll-driven animations instead derive their progress from a scroll or view timeline, linking effect evaluation to spatial progress rather than elapsed time.

## First Principles

Three constraints govern these APIs. **The browser needs both states**: capture the old visual state before changing the DOM — starting a transition in an effect after a route has committed is too late. **Matching needs unique identity**: a shared `view-transition-name` identifies one element per snapshot; duplicates make matching ambiguous and can skip the transition. **A different timeline does not remove rendering cost**: transform/opacity effects may composite, but layout- or paint-heavy effects still cost work — and feature support plus reduced-motion handling are separate contracts.

## How It Works

### 1. Capture Before the State Update and Animate After It

```text
old snapshot → run/await update callback → new snapshot → animate snapshots
                    ↓                         ↓                 ↓
            updateCallbackDone               ready            finished

scroll()/view() timeline → animation progress → keyframe effect
```

`skipTransition()` skips the visual transition but still runs the update callback. `ready` may reject when the animation is skipped or names conflict; catch that rejection if you customize animations. Keep navigation/content updates working when animations are unavailable.

**Cross-document navigation:** put this stylesheet in **both** same-origin pages. Ordinary anchors keep URL/history/loading behavior; do not fetch an entire HTML document and inject `body.innerHTML` as a homemade router.

```css
@view-transition {
  navigation: auto;
}

@media (prefers-reduced-motion: reduce) {
  ::view-transition-group(*) {
    animation: none;
  }
}
```

Cross-document support is distinct from `document.startViewTransition` support. The browser handles unsupported CSS by retaining ordinary navigation.

**A same-document state change:**

```javascript
function toggleTheme() {
  const update = () => document.documentElement.classList.toggle('dark');
  if (!document.startViewTransition ||
      matchMedia('(prefers-reduced-motion: reduce)').matches) {
    update();
    return;
  }
  const transition = document.startViewTransition(() => { update(); });
  void transition.ready.catch(() => {}); // skip/name failure must not break content
}
```

For React, commit the state update inside the callback (for a small local update, `flushSync` can make the new DOM available synchronously), or let a router's integration control capture and commit. Merely scrolling inside an effect does not transition the route.

### 2. Router Integration and Shared-Element Identity

```tsx
// React Router v7 Data/Framework mode with a configured router.
import { Link } from 'react-router';

export function ProductLink({ id }: { id: string }) {
  return <Link to={`/products/${encodeURIComponent(id)}`} viewTransition>Open product</Link>;
}
```

The router wraps its navigation commit at the correct moment. Configure reduced-motion CSS and loading/error views for the route. This avoids duplicating the router's history, response-error, script and cleanup behavior.

For shared elements, assign the name to exactly one element per snapshot:

```css
/* Only the selected card in the old view has this name. */
.card[data-selected="true"] { view-transition-name: selected-product; }
.product-detail-image { view-transition-name: selected-product; }

::view-transition-old(selected-product),
::view-transition-new(selected-product) {
  animation-duration: 300ms;
  animation-timing-function: ease;
}
```

Do not assign the same name to every card in a visible grid. If source and destination are simultaneously rendered, only one may carry that name in a given snapshot.

### 3. Scroll Progress and Reveal Without Hiding the Fallback

A reading-progress bar binds scale to scroll position:

```css
.reading-progress {
  position: fixed;
  inset: 0 auto auto 0;
  width: 100%;
  height: 4px;
  background: currentColor;
  transform-origin: left;
  transform: scaleX(0);
}

@media (prefers-reduced-motion: no-preference) {
  @supports (animation-timeline: scroll()) {
    .reading-progress {
      animation: reading-progress auto linear;
      animation-timeline: scroll(root block);
    }
  }
}

@keyframes reading-progress {
  from { transform: scaleX(0); }
  to { transform: scaleX(1); }
}
```

Declare `animation-timeline` **after** the `animation` shorthand, which resets it. A scroll timeline tracks a scroll container's available scroll range. `view()` instead tracks an element's passage through its scrollport; use `entry`, `exit`, `cover` or `contain` ranges only with the timeline they describe.

Reveal-on-scroll must keep content visible without the timeline:

```css
.reveal { opacity: 1; transform: none; }

@supports (animation-timeline: view()) {
  @media (prefers-reduced-motion: no-preference) {
    .reveal {
      animation: reveal auto linear both;
      animation-timeline: view(block);
      animation-range: entry 0% entry 100%;
    }
  }
}

@keyframes reveal {
  from { opacity: 0; transform: translateY(24px); }
  to { opacity: 1; transform: none; }
}
```

Unsupported browsers and users requesting less motion see visible content. Do not leave `opacity: 0` in the base rule while only adding the timeline inside a feature query. If an element is taller than its scrollport, “fully visible” is not a useful assumption; choose its named range and test that geometry.

### 4. Check Each Browser Capability and Rendering Cost

Feature-detect the specific capability instead of using one “full support” browser/version table for several APIs. Same-document transitions, cross-document transitions, transition types, `scroll()`, `view()` and named ranges can have different support. Consult the linked compatibility tables when selecting your target browsers.

Snapshotting has memory and paint costs. Scroll-driven effects avoid a JavaScript scroll listener but do not automatically eliminate jank. Profile layout/paint/composite work and keep important content readable during loading, failed animation and reduced-motion modes.

## Summary

Capture before the update, identify shared elements uniquely and keep navigation correct without animation. Cross-document transitions use page opt-in; router transitions use commit integration. Scroll and view timelines drive different kinds of progress. Feature detection, visible fallbacks and explicit reduced-motion behavior matter as much as the effect itself.

# HTML Fundamentals — Semantic HTML, Forms, Accessibility

> HTML is the backbone of every web page. This covers semantic elements, forms, accessibility attributes, meta tags, and document structure.

## Definition

**Semantic HTML** means choosing elements for what content means, rather than how it looks by default. Examples include `<article>` for a self-contained article, `<nav>` for navigation, `<label>` for an input's label and `<time>` for a date or time. Element choice gives the browser information about behavior, such as focus and form participation. It also provides roles for assistive technology and structure that machines can use for search, autocomplete and rich results.

> **Textbook Definition:** Semantic HTML uses element types to encode document structure and built-in interaction meaning. Those semantics inform browser behavior and accessibility mappings; visual styling does not by itself establish equivalent semantics.

## First Principles

HTML is a semantic contract, not a visual language:

1. **Elements declare *meaning*, browsers supply default behavior** — a `<button>` is focusable, keyboard-activatable, and exposed with button semantics *because it's a button* (→ 50.2.02); the visual-reset mistake (styling divs into buttons) buys pixels and loses the entire behavior contract.
2. **The document outline is the API**: headings, landmarks, lists, and tables are how assistive technology (AT) navigates — semantics are *structure for machines*, which is why div-soup is invisible to them.
3. **Forms are the semantic high ground** (→ 50.2.05): labels, types, autocomplete tokens — each attribute is a contract with the browser (validation, password managers, AT) you either honor or hand-reimplement.

## Why It Matters

A component framework does not choose every element for you. Choose meaning and behavior before styling. Interviews probe it via accessibility questions ("how does a screen reader know this is a button?") and via forms (label/autocomplete/validation contracts). It's also self-documenting code: `<article>` needs no comment.

## Follow one form submission

A label supplies an input's accessible name, the input's `name` determines its submitted key, and a submit button requests form submission. The browser checks applicable constraints before the normal submission; the server must still validate and authorize received data.

```html
<form action="/appointments" method="post">
  <label for="confirmation-email">Confirmation email</label>
  <input id="confirmation-email" name="email" type="email"
         autocomplete="email" required aria-describedby="email-help">
  <p id="email-help">We will send the appointment details here.</p>
  <button type="submit">Book appointment</button>
</form>
```

Trace: activation → applicable native validation → successful named controls become form data → request → server response. If JavaScript intercepts submission, it inherits responsibility for response/error presentation while server validation remains necessary. A syntactically valid email does not prove ownership or deliverability.

Inside a form, a `<button>` defaults to `type="submit"`; set `type="button"` for an action that must not submit the form.

The tables below explain which parts of that contract come from elements and attributes. Use them after following the interaction rather than as an isolated vocabulary list.

## Elements give the document structure

| Element | Use Case | Replaces |
| --------------------------- | ----------------------------------------- | ----------------------- |
| `<header>` | Page/section header | `<div class="header">` |
| `<nav>` | Navigation links | `<div class="nav">` |
| `<main>` | Primary content | `<div class="main">` |
| `<article>` | Self-contained content | `<div class="post">` |
| `<section>` | Thematic grouping, usually with a heading | `<div class="section">` |
| `<aside>` | Sidebar content | `<div class="sidebar">` |
| `<footer>` | Page/section footer | `<div class="footer">` |
| `<figure>` + `<figcaption>` | Image with caption | `<div>` wrapper |
| `<details>` + `<summary>` | Expandable content | Custom JS accordion |
| `<time datetime="...">` | Machine-readable date | `<span>` |

Use one visible `<main>` landmark for the page's primary content; a page may contain multiple `<nav>` landmarks when each has a distinct purpose or accessible name.

### Why Semantics Matter
- **Accessibility:** Screen readers use semantics to convey structure
- **SEO:** Search engines use semantics to understand content hierarchy
- **Maintainability:** Code is self-documenting

## Attributes add the form contract

### Key Attributes

| Attribute | Purpose | Example |
| ------------------------- | ---------------------------------- | ----------------------------- |
| `required` | Field must have a value | `<input required>` |
| `pattern` | Regex validation | `pattern="[A-Za-z]{3}"` |
| `minlength` / `maxlength` | String length limits | `minlength="2"` |
| `min` / `max` | Numeric/date limits | `min="0" max="100"` |
| `type` | Input type + validation + keyboard | `type="email"`, `type="tel"` |
| `aria-describedby` | Links to error/help text | `aria-describedby="error-id"` |
| `aria-invalid` | Validation state | `aria-invalid="true"` |

### Input Types

| Type | Mobile Keyboard | Validation |
| -------- | ---------------- | ---------------------------------------------------------- |
| `email` | Email keyboard | Email format |
| `tel` | Phone keyboard | No built-in phone-number validation |
| `number` | Numeric keyboard | Numeric value; use for quantities, not numeric-looking IDs |
| `date` | Date picker | Date format |
| `url` | URL keyboard | URL format |
| `search` | Search keyboard | None |

## Metadata describes the document

```html
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <title>Patient Dashboard — Docita</title>
  <meta name="description" content="Manage patient appointments securely." />
  <meta name="robots" content="noindex" />
  <!-- This illustrative private dashboard requires access control. noindex is not security. -->
  <meta property="og:title" content="Patient Dashboard — Docita" />
  <meta property="og:description" content="Manage patient appointments securely." />
  <meta property="og:image" content="/og-image.png" />
  <meta name="twitter:card" content="summary_large_image" />
  <meta name="theme-color" content="#1a73e8" />
</head>
```

| Tag | Purpose | Best Practice |
| -------------------- | --------------------------- | ------------------------------------------- |
| `<title>` | Browser tab / search result | Distinct, descriptive and useful |
| `<meta description>` | Search snippet | Accurate summary; snippets can be rewritten |
| `<link canonical>` | Preferred URL | Identify the preferred public URL |
| `og:*` | Social sharing | Title, description, image |

## Accessible names and focus connect the interaction

### ARIA Attributes

| Attribute | Purpose | Example |
| ------------------ | ------------------------------------------ | ------------------------------------------- |
| `aria-label` | Accessible name (no visible text) | `<button aria-label="Close">` |
| `aria-labelledby` | References one or more elements for a name | `<section aria-labelledby="section-title">` |
| `aria-describedby` | References description | `<input aria-describedby="help">` |
| `aria-live` | Dynamic changes announced | `aria-live="polite"` |
| `aria-hidden` | Hides from screen readers | `aria-hidden="true"` for icons |
| `role` | Explicit role | `role="alert"`, `role="status"` |

When using `aria-labelledby`, point it at the `id` of visible text that names the region or control. A generic `<div>` cannot gain useful region semantics from a label alone; use the right native element or an appropriate role.

### Keyboard Navigation
- Use `<button>`, `<a>`, `<input>` — not `<div onclick>`
- Tab order: logical, no positive `tabindex`
- Focus must be visible (don't remove `:focus` outline)
- Skip links: `<a href="#main" class="skip-link">Skip to content</a>`
- Do not put `aria-hidden="true"` on a focusable control or an ancestor of one.

---

## Interview Tips
- Explain why a generic `<div>` does not supply button/link behavior
- Know `aria-label` vs `aria-labelledby` vs `aria-describedby`
- Explain resource hints: preload requests a resource for this navigation, prefetch hints at likely future use, and preconnect prepares a connection to an origin; none guarantees loading priority or reuse
- Know why `<button>` beats `<div onclick>` (keyboard, focus, semantics)

### Suggestions do not constrain form values

```html
<label for="clinic">Clinic</label>
<input id="clinic" name="clinic" list="clinics" autocomplete="off">
<datalist id="clinics">
  <option value="City Medical">
  <option value="Riverside Health">
</datalist>
```

The browser may offer these as suggestions, but users can enter another value. Use `<select>` when the value must come from a fixed set, and validate submitted data on the server either way.

## Real-World Use Cases

- **Design-system resets gone wrong** — styling `div`s into buttons loses focus rings and keyboard activation; prefer the real element and restyle it (→ 10.7.06 for the styling layer).
- **SEO audits** — meaningful headings, landmarks and route-specific metadata give crawlers and users a clearer structure (→ 10.7.04).
- **Forms that pass review** — labels, `autocomplete` tokens, input types, and `aria-describedby` for errors support accessible form use and browser autofill; focus, errors, contrast and complete interaction still need assessment.

## Common Mistakes

1. **Div/button-soup** — `<div onclick>` instead of `<button>`: loses keyboard activation, focus, and role in one stroke.
2. **Labels as placeholders** — placeholder text disappears and is an unreliable naming strategy; prefer a visible associated label, with placeholder text only as a hint.
3. **Skipping `lang` and meta viewport** — `<html lang="en">` and responsive viewport are one-line fixes that break screen-reader pronunciation and mobile layout when missing.
4. **Heading hierarchy as decoration** — choosing `<h3>` because it *looks* smaller misrepresents structure; size is CSS's job.

## Best Practices

- **Pick the element before the CSS** — if a native element exists (`button`, `dialog`, `details`, `output`), use it and restyle.
- **Validate structure, not heading size**: use a logical heading hierarchy, meaningful landmarks and `alt` text (empty `alt=""` for decorative images). A skipped heading level is not automatically an accessibility failure; do not choose levels for their default font size.
- **Let the browser do the work**: native validation, `autocomplete` tokens, `<datalist>`, `<details>` — then test the complete interaction; native defaults do not prove accessibility conformance.

## Summary

1. **Semantic HTML is the accessibility and SEO foundation** — pick elements by meaning, never by default styling
2. **Forms expose browser contracts** — labels name controls; `name` supplies submitted keys; constraint validation and error descriptions have separate jobs
3. **Meta tags provide document-level instructions and hints** — viewport for responsive behavior, description/OG for sharing, `theme-color` for polish
4. **`<button>` beats `<div onclick>`** every time: keyboard focus, screen-reader role, and form submission for free
5. **Resource hints are browser hints** — `preload`, `prefetch` and `preconnect` can affect fetching but do not guarantee a performance result

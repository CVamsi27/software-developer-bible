# HTML Fundamentals — Semantic HTML, Forms, Accessibility

An appointment form must tell the browser what each control means, submit the right values, and explain errors to people using a keyboard or screen reader. HTML provides much of that contract when the page uses the right elements and attributes.

```html
<form action="/appointments" method="post">
  <label for="confirmation-email">Confirmation email</label>
  <input id="confirmation-email" name="email" type="email"
         autocomplete="email" required aria-describedby="email-help">
  <p id="email-help">We will send the appointment details here.</p>
  <button type="submit">Book appointment</button>
</form>
```

## Definition

**Semantic HTML** means choosing elements for what content means, rather than how it looks by default. Examples include `<article>` for a self-contained article, `<nav>` for navigation, `<label>` for an input's label and `<time>` for a date or time. Element choice gives the browser information about behavior, such as focus and form participation, and exposes structure to assistive technology. Form autofill depends on appropriate control names and autocomplete tokens; crawlers may use page structure and structured data, but neither search display nor rich results are guaranteed.

> **Textbook Definition:** Semantic HTML uses element types to encode document structure and built-in interaction meaning. Those semantics inform browser behavior and accessibility mappings; visual styling does not by itself establish equivalent semantics.

## First Principles

HTML is a semantic contract, not a visual language. **Elements carry meaning and default behavior**: a `<button>` is focusable and keyboard-activatable because it is a button — styling a `<div>` to look similar grants none of that. **Structure supports navigation**: headings and landmarks let people move through a page with assistive technology, while a `<div>` announces no role at all. **Forms define a browser contract** (→ 50.2.05): labels, input types, names, and autocomplete tokens drive accessible names, validation, password managers, and submitted data.

## 1. What Happens When a User Submits a Form?

A label supplies an input's accessible name, the input's `name` determines its submitted key, and a submit button requests form submission. The browser checks applicable constraints before the normal submission; the server must still validate and authorize received data.

```html
<form action="/appointments" method="post">
  <label for="confirmation-email">Confirmation email</label>
  <input id="confirmation-email" name="email" type="email"
         autocomplete="email" required aria-describedby="email-help">
  <p id="email-help">We will send the appointment details here.</p>
  <button type="submit">Book appointment</button>
</form>
```

Trace: activation → applicable native validation → successful named controls become form data → request → server response. If JavaScript intercepts submission, it inherits responsibility for response/error presentation while server validation remains necessary. A syntactically valid email does not prove ownership or deliverability.

Inside a form, a `<button>` defaults to `type="submit"`; set `type="button"` for an action that must not submit the form.

The tables below explain which parts of that contract come from elements and attributes. Use them after following the interaction rather than as an isolated vocabulary list.

## 2. Which Elements Communicate Document Structure?

| Element | Meaning or behavior |
| --------------------------- | ----------------------------------------- |
| `<header>` | Page/section header |
| `<nav>` | Navigation links |
| `<main>` | Primary content |
| `<article>` | Self-contained content |
| `<section>` | Thematic grouping, usually with a heading |
| `<aside>` | Sidebar content |
| `<footer>` | Page/section footer |
| `<figure>` + `<figcaption>` | Image with caption |
| `<details>` + `<summary>` | Expandable content |
| `<time datetime="...">` | Machine-readable date |

Use one visible `<main>` landmark for the page's primary content; a page may contain multiple `<nav>` landmarks when each has a distinct purpose or accessible name.

## 3. Which Attributes Control Form Behavior and Submitted Data?

| Attribute | Effect | Example |
| ------------------------- | ---------------------------------------- | ------------------------------ |
| `name` | Submitted field key | `<input name="email">` |
| `autocomplete` | Browser autofill hint | `<input autocomplete="email">` |
| `required` | Empty value fails native constraints | `<input required>` |
| `pattern` | Regex rule for supported text-like types | `pattern="[A-Za-z]{3}"` |
| `minlength` / `maxlength` | Text length limits | `minlength="2"` |
| `min` / `max` | Value range limits | `min="0" max="100"` |
| `type` | Validation and input behavior | `type="email"`, `type="tel"` |
| `aria-describedby` | Links help or error text | `aria-describedby="error-id"` |
| `aria-invalid` | Signals a known invalid state | `aria-invalid="true"` |
| `disabled` | Omits the control from submission | `<input disabled>` |

**Choose an input type for its value:**

| Type | Mobile Keyboard | Validation |
| -------- | ---------------- | ---------------------------------------------------------- |
| `email` | Email keyboard | Email format |
| `tel` | Phone keyboard | No built-in phone-number validation |
| `number` | Numeric keyboard | Numeric value; use for quantities, not numeric-looking IDs |
| `date` | Date picker | Date format |
| `url` | URL keyboard | URL format |
| `search` | Search keyboard | None |

---

A control is submitted only when it has a `name` and is successful: disabled controls are omitted, while read-only controls are submitted; unchecked checkboxes and radio buttons are omitted too. Browser constraint validation helps with user input, but JavaScript can bypass it and clients can send requests directly; validate and authorize on the server. A label should remain visible rather than being replaced by a disappearing placeholder.

**Suggestions do not constrain form values:**

```html
<label for="clinic">Clinic</label>
<input id="clinic" name="clinic" list="clinics" autocomplete="off">
<datalist id="clinics">
  <option value="City Medical">
  <option value="Riverside Health">
</datalist>
```

The browser may offer these as suggestions, but users can enter another value. Use `<select>` when the value must come from a fixed set, and validate submitted data on the server either way.

## 4. How Do Names, Errors and Focus Make a Control Usable?

**Use native semantics before ARIA:**

| Attribute | Purpose | Example |
| ------------------ | -------------------------------------------- | ------------------------------------------- |
| `aria-label` | Accessible name (no visible text) | `<button aria-label="Close">` |
| `aria-labelledby` | References one or more elements for a name | `<section aria-labelledby="section-title">` |
| `aria-describedby` | References description | `<input aria-describedby="help">` |
| `aria-live` | Announces relevant updates inside the region | `aria-live="polite"` |
| `aria-hidden` | Removes content from the accessibility tree | `aria-hidden="true"` for decorative icons |
| `role` | Explicit role | `role="alert"`, `role="status"` |

Prefer a visible associated `<label>` for a form control. Use `aria-labelledby` when visible text elsewhere supplies the name, and `aria-describedby` for help or error details. Set `aria-invalid="true"` only while the field is known to be invalid; keep the referenced error text in the DOM and move focus deliberately after a failed submission. A generic `<div>` does not gain useful region semantics from a label alone; choose the right native element or an appropriate role. Use `alt=""` for a decorative image so it does not add redundant words to the accessibility tree.

```html
<label for="confirmation-email">Confirmation email</label>
<input id="confirmation-email" name="email" type="email"
       aria-invalid="true" aria-describedby="email-error">
<p id="email-error" role="alert">Enter a valid email address.</p>
```

This is the rendered error state after validation; remove `aria-invalid` and the error association when the value becomes valid. A summary that takes focus after a failed form submit should link each message to its control.

Native controls supply focus, keyboard behavior and accessibility semantics together: use a `<button>` for an action and an `<a href>` for navigation instead of a clickable `<div>`. Keep tab order in document order, avoid positive `tabindex`, preserve a visible focus indicator, and never put `aria-hidden="true"` on a focusable control or its ancestor. A skip link such as `<a href="#main">Skip to content</a>` gives keyboard users a direct route past repeated navigation.

## 5. What Information Does the Document Expose?

```html
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <title>Patient Dashboard — Docita</title>
  <meta name="description" content="Manage patient appointments securely." />
  <meta name="robots" content="noindex" />
  <!-- This illustrative private dashboard requires access control. noindex is not security. -->
  <meta property="og:title" content="Patient Dashboard — Docita" />
  <meta property="og:description" content="Manage patient appointments securely." />
  <meta property="og:image" content="/og-image.png" />
  <meta name="twitter:card" content="summary_large_image" />
  <meta name="theme-color" content="#1a73e8" />
</head>
```

| Tag | Purpose | Practice |
| ----------------------------- | --------------------------- | ------------------------------------------- |
| `<title>` | Tab and result title | Write a distinct title |
| `<meta name="description">` | Possible search snippet | Be accurate; crawlers may rewrite it |
| `<link rel="canonical">` | Preferred public URL | Use for equivalent pages |
| `og:*` | Social sharing preview | Set title, description and image |

---

A canonical link identifies the preferred URL for public content; it does not redirect or enforce access. A `noindex` instruction also does not protect private content; access control must protect the response itself.

## Summary

Choose elements by meaning, then use attributes to connect controls, names, submitted values and validation. Let native browser behavior carry the interaction where it fits, describe custom errors accessibly, and validate and authorize every submitted value on the server. Metadata helps browsers and crawlers interpret public pages; it never substitutes for access control.

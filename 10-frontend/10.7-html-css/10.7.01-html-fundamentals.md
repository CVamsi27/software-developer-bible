# HTML Fundamentals — Semantic HTML, Forms, Accessibility

> HTML is the backbone of every web page. This covers semantic elements, forms, accessibility attributes, meta tags, and document structure.

## TL;DR

Semantic HTML is the cheapest quality multiplier in the stack: `<button>`/`<label>`/`<time>` carry keyboard, AT, and validation behavior for free; div-soup surrenders it. Cover: semantic elements, forms, meta tags, and the accessibility attributes HTML itself provides.

## First Principles

HTML is a semantic contract, not a visual language:

1. **Elements declare *meaning*, browsers supply default behavior** — a `<button>` is focusable, keyboard-activatable, and announced as a button *because it's a button* (→ 50.2.02); the visual-reset mistake (styling divs into buttons) buys pixels and loses the entire behavior contract.
2. **The document outline is the API**: headings, landmarks, lists, and tables are how AT navigates — semantics are *structure for machines*, which is why div-soup is invisible to them.
3. **Forms are the semantic high ground** (→ 50.2.05): labels, types, autocomplete tokens — each attribute is a contract with the browser (validation, password managers, AT) you either honor or hand-reimplement.

## Definition

**Semantic HTML** is the practice of choosing elements for their *meaning* — `<article>`, `<nav>`, `<label>`, `<time>` — rather than their default rendering. The element name is a contract with the browser: behavior (focus, activation, form participation), semantics (roles exposed to assistive tech), and machine-readability (SEO, autocomplete, rich results) all derive from it.

## Why It Matters

Every framework ships you divs by default; knowing which element *should* be there is the difference between a UI and a document. Interviews probe it via accessibility questions ("how does a screen reader know this is a button?") and via forms (label/autocomplete/validation contracts). It's also self-documenting code: `<article>` needs no comment.

## Semantic Elements

| Element | Use Case | Replaces |
| --------------------------- | ---------------------- | ----------------------- |
| `<header>` | Page/section header | `<div class="header">` |
| `<nav>` | Navigation links | `<div class="nav">` |
| `<main>` | Primary content | `<div class="main">` |
| `<article>` | Self-contained content | `<div class="post">` |
| `<section>` | Thematic grouping | `<div class="section">` |
| `<aside>` | Sidebar content | `<div class="sidebar">` |
| `<footer>` | Page/section footer | `<div class="footer">` |
| `<figure>` + `<figcaption>` | Image with caption | `<div>` wrapper |
| `<details>` + `<summary>` | Expandable content | Custom JS accordion |
| `<time datetime="...">` | Machine-readable date | `<span>` |

### Why Semantics Matter
- **Accessibility:** Screen readers use semantics to convey structure
- **SEO:** Search engines use semantics to understand content hierarchy
- **Maintainability:** Code is self-documenting

## Forms

### Key Attributes
| Attribute | Purpose | Example |
| ------------------------- | ---------------------------------- | ----------------------------- |
| `required` | Field must have a value | `<input required>` |
| `pattern` | Regex validation | `pattern="[A-Za-z]{3}"` |
| `minlength` / `maxlength` | String length limits | `minlength="2"` |
| `min` / `max` | Numeric/date limits | `min="0" max="100"` |
| `type` | Input type + validation + keyboard | `type="email"`, `type="tel"` |
| `aria-describedby` | Links to error/help text | `aria-describedby="error-id"` |
| `aria-invalid` | Validation state | `aria-invalid="true"` |

### Input Types
| Type | Mobile Keyboard | Validation |
| -------- | --------------- | ------------- |
| `email` | Email keyboard | Email format |
| `tel` | Phone keyboard | None |
| `number` | Number keyboard | Number format |
| `date` | Date picker | Date format |
| `url` | URL keyboard | URL format |
| `search` | Search keyboard | None |

## Meta Tags

```html
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <title>Patient Dashboard — Docita</title>
  <meta name="description" content="Manage patient appointments securely." />
  <meta name="robots" content="index, follow" />
  <link rel="canonical" href="https://docita.work/dashboard" />
  <meta property="og:title" content="Patient Dashboard — Docita" />
  <meta property="og:description" content="Manage patient appointments securely." />
  <meta property="og:image" content="/og-image.png" />
  <meta name="twitter:card" content="summary_large_image" />
  <meta name="theme-color" content="#1a73e8" />
</head>
```

| Tag | Purpose | Best Practice |
| -------------------- | --------------------------- | ---------------------------- |
| `<title>` | Browser tab / search result | 50-60 chars, primary keyword |
| `<meta description>` | Search snippet | 150-160 chars, compelling |
| `<link canonical>` | Preferred URL | Self-referencing |
| `og:*` | Social sharing | Title, description, image |

## Accessibility (HTML Level)

### ARIA Attributes
| Attribute | Purpose | Example |
| ------------------ | --------------------------------- | --------------------------------- |
| `aria-label` | Accessible name (no visible text) | `<button aria-label="Close">` |
| `aria-labelledby` | References visible label | `<div aria-labelledby="title">` |
| `aria-describedby` | References description | `<input aria-describedby="help">` |
| `aria-live` | Dynamic changes announced | `aria-live="polite"` |
| `aria-hidden` | Hides from screen readers | `aria-hidden="true"` for icons |
| `role` | Explicit role | `role="alert"`, `role="status"` |

### Keyboard Navigation
- Use `<button>`, `<a>`, `<input>` — not `<div onclick>`
- Tab order: logical, no positive `tabindex`
- Focus must be visible (don't remove `:focus` outline)
- Skip links: `<a href="#main" class="skip-link">Skip to content</a>`

## Interview Tips
- Explain why `<div>` is not semantic
- Know `aria-label` vs `aria-labelledby` vs `aria-describedby`
- Explain `preload` vs `prefetch` vs `preconnect`
- Know why `<button>` beats `<div onclick>` (keyboard, focus, semantics)

## Code Examples

```html
<!-- Semantic structure with form contract -->
<article class="appointment">
  <header>
    <h2>Consultation</h2>
    <time datetime="2026-09-20T14:00">Sat, Sep 20 — 2:00 PM</time>
  </header>

  <form action="/api/appointments" method="post">
    <label for="clinic">Clinic</label>
    <input id="clinic" name="clinic" list="clinics" required autocomplete="off" />

    <label for="email">Confirmation email</label>
    <input id="email" name="email" type="email" autocomplete="email"
           required placeholder="you@example.com" />

    <button type="submit">Book appointment</button>
  </form>

  <datalist id="clinics">
    <option value="City Medical"></option>
    <option value="Riverside Health"></option>
  </datalist>
</article>
```

The semantic wins here: `label for` ties label to input (click target + AT name), `type="email"` brings validation + mobile keyboard, `autocomplete="email"` lets password managers fill it, `time datetime` is machine-readable, and the `<button type="submit">` is focusable and Enter-activatable with zero JS.

## Real-World Use Cases

- **Design-system resets gone wrong** — styling `div`s into buttons loses focus rings and keyboard activation; the fix is always "use the real element, restyle it" (→ 10.7.06 for the styling layer).
- **SEO audits** — one `<h1>`, landmark regions (`main`/`nav`/`aside`), and `<meta>` description/OG tags are 80% of on-page SEO structure (→ 10.7.04).
- **Forms that pass review** — labels, `autocomplete` tokens, input types, and `aria-describedby` for errors satisfy both WCAG (→ 50.2.05) and browser autofill in one pass.

## Common Mistakes

1. **Div/button-soup** — `<div onclick>` instead of `<button>`: loses keyboard activation, focus, and role in one stroke.
2. **Labels as placeholders** — placeholder text disappears on input and isn't a name for AT; `<label>` is required, placeholder is a hint.
3. **Skipping `lang` and meta viewport** — `<html lang="en">` and responsive viewport are one-line fixes that break screen-reader pronunciation and mobile layout when missing.
4. **Heading hierarchy as decoration** — choosing `<h3>` because it *looks* smaller breaks the document outline; size is CSS's job.

## Best Practices

- **Pick the element before the CSS** — if a native element exists (`button`, `dialog`, `details`, `output`), use it and restyle.
- **Validate the outline**, not the pixels: headings nest without skipping, landmarks exist (`main`, `nav`), every image has `alt` (empty `alt=""` for decoration).
- **Let the browser do the work**: native validation, `autocomplete` tokens, `<datalist>`, `<details>` — JS you don't write is a11y you don't break.

## Summary

1. **Semantic HTML is the accessibility and SEO foundation** — pick elements by meaning, never by default styling
2. **Forms are state machines** — inputs, labels, validation attributes, and error semantics (`aria-describedby`, `role="alert"`)
3. **Meta tags control the platform** — viewport for responsive behavior, description/OG for sharing, `theme-color` for polish
4. **`<button>` beats `<div onclick>`** every time: keyboard focus, screen-reader role, and form submission for free
5. **Resource hints (`preload`/`prefetch`/`preconnect`) are performance levers** declared in plain HTML

## Cheat Sheet

```text
STRUCTURE   header · nav · main · aside · footer · section · article
SEMANTIC    time[datetime] · figure+figcaption · details+summary · mark
FORMS       label[for] · input[type] · autocomplete tokens · datalist
A11Y        alt (or alt="") · lang on <html> · landmarks instead of divs
META        viewport · charset · description · OG tags (→ 10.7.04)
RULE        element for meaning, CSS for looks, JS only for what's left
```

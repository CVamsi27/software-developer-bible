# Browser Rendering — Critical Rendering Path, Reflow, Paint

> **How browsers turn HTML/CSS/JS into pixels — and how to avoid performance pitfalls.**

---

## Definition

Browser rendering turns document content and styles into displayed pixels. A useful model is style calculation → layout → paint recording/rasterization → composition. Engines may split, cache and schedule those stages differently; a change invalidates the work needed to represent its effect.

## First Principles

A browser must know what exists, how it looks, where it fits and which pixels to display. Moving an element by changing its layout position can alter geometry calculations. A transform changes its visual position without changing normal-flow geometry, so an eligible composited transform animation can reuse prior rasterized content. Whether it actually does so depends on the element and rendering engine.

## Follow a box from a rule to pixels

```text
HTML → DOM                  CSS → parsed style rules
      └──── style calculation ─────┘
                   ↓
          layout: geometry/boxes
                   ↓
         paint: draw instructions
                   ↓
        raster: instructions → pixels
                   ↓
         composite: assemble output
```

Suppose a box has `width: 100px`. Changing width to 200px invalidates its geometry and may affect related boxes; the browser updates required layout and visual output. Changing only its background usually keeps geometry while invalidating painted content. Changing an eligible composited transform can update composition without repeating layout and paint. Paint can be more expensive than layout for some scenes; there is no universal stage ranking or fixed 10–100× ratio.

`display: none` removes boxes from layout, while visibility/opacity choices have different layout, interaction and accessibility effects. A simplified render-tree diagram does not replace the actual box and stacking-context rules.

## A geometry read can demand work immediately

```javascript
const boxes = [...document.querySelectorAll('.box')];
const widths = boxes.map(box => box.getBoundingClientRect().width);
boxes.forEach((box, index) => {
  box.style.width = `${widths[index] + 10}px`;
});
```

Here all reads precede writes. If instead each iteration writes width and then requests fresh geometry, it can force pending layout repeatedly. Geometry reads demand a current answer only when the relevant work is dirty; not every read causes a new full-page layout. `getComputedStyle` may force style calculation and, for particular conditions/properties, layout.

Batch compatible reads and writes. A rAF callback still forces layout if it interleaves them; scheduling does not erase dependencies. ResizeObserver reports observed size changes but can create feedback loops if its callback repeatedly resizes the observed box.

## Composition is an optimization with conditions

Transforms and opacity are good candidates for efficient animation because they do not normally change flow geometry. They do not automatically promote every element, guarantee GPU work or eliminate paint. Filters, large layers, clipping, blending and SVG details can change the cost.

`will-change` hints at a possible upcoming change; it can alter stacking behavior and consume resources. Use it for a demonstrated need and remove it when appropriate. `translateZ(0)` is not a universal performance fix. An oversized layer may make rasterization and memory more expensive even while reducing some main-thread work.

Containment constrains how a subtree participates in surrounding layout/style/paint according to the selected values; it is not isolation of every effect. `content-visibility: auto` can skip eligible offscreen rendering work, with intrinsic sizing to reduce jumps. Keep content semantics and accessibility intact.

## Loading controls when the first picture can exist

A parser-inserted classic script without `async`/`defer` usually pauses HTML parsing while it is fetched/executed. `defer` classic scripts execute after parsing in document order; `async` executes when ready, with order not guaranteed and parsing possibly interrupted during execution. Module scripts are deferred by default unless async behavior is requested. CSS and dependency loading can further constrain when execution/rendering proceeds.

Fonts can delay text visibility or change layout when swapped. `font-display` selects a display strategy; metric-compatible fallback sizing can reduce shifts. A font preload must match the actual fetched resource and applicable CORS behavior. Preloading every resource can compete with the truly critical ones.

## Measure the work that misses the deadline

Display refresh and browser scheduling determine the available interval; 16.7 ms is only the interval at 60 Hz, and JavaScript does not own all of it. Use DevTools to find long tasks, style/layout, raster/paint and composition costs. Long Animation Frames observations can help where supported; a rAF callback counter measures callbacks rather than displayed frames.

Distinguish page-load metrics from interaction and animation performance. A fast first paint does not prove smooth scrolling or a responsive click. Capture the trigger and slow frame, change one mechanism and compare under representative device/content conditions.

## Summary

Trace document/style inputs into geometry and pixels, then ask which work a change invalidates. Batch dependent reads/writes, treat composition as conditional and measure the full workload before choosing containment, loading or animation changes.

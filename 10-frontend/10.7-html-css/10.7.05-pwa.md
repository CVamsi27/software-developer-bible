# Progressive Web Apps (PWA) — Service Workers, Manifest, Offline

> **Making web apps installable, offline-capable, and app-like — the full PWA implementation guide.**

## Definition

A **Progressive Web App** progressively adds app-like capabilities to a web application. Installability, offline behavior and background features are separate capabilities, implemented with a web app manifest (name, icons, display mode), a service worker (a proxy script with its own lifecycle intercepting network requests), and a secure context. The service worker's fetch handler + a Cache Storage instance implement every offline behavior.

## First Principles

A PWA is the web app with an installed-shell contract:

1. **The service worker is a programmable proxy**: it intercepts fetch — which is why caching strategies (cache-first for assets, network-first for data) are *code you write*, and why an incorrect SW can persist until updated or unregistered (the update problem: versioned SW + skipWaiting discipline).
2. **The manifest is the installability contract**: icons, name, display — the browser needs the declaration to offer install; offline capability is what makes install *worth it*.
3. **PWA = reliability before offline**: even online users get instant loads from cache — the value is latency and resilience, with offline as the limiting case (→ 30.3.4.03's CDN philosophy, client-side).

## Why It Matters

The service worker is the most powerful frontend primitive most engineers never use: a programmable proxy for your origin. It powers offline-first apps, install prompts, push notifications, and background sync — and it's a favorite senior interview topic because it tests lifecycle reasoning (install → waiting → active, skipWaiting, clients.claim) and cache-invalidation design in one thread.

## PWA Requirements

For an offline-capable installable app, plan these three pieces; browser install criteria vary and a service worker is not a universal install prerequisite:
1. **HTTPS** — must be served over HTTPS (service workers require secure context)
2. **Service Worker** — enables offline and background features
3. **Web App Manifest** — enables "Add to Home Screen"

## Service Worker Lifecycle

```
Register → Install → Activate → Idle → Fetch Events
                │ │ │
                ▼ ▼ ▼
          Cache assets Clean Intercept
          for offline old network
                       caches requests
```

### Registration

```typescript
// main.ts — register service worker
if ('serviceWorker' in navigator) {
  window.addEventListener('load', async () => {
    try {
      const registration = await navigator.serviceWorker.register('/sw.js', {
        scope: '/',
      });
      console.log('SW registered:', registration.scope);

      // Listen for updates
      registration.addEventListener('updatefound', () => {
        const newWorker = registration.installing;
        newWorker?.addEventListener('statechange', () => {
          if (newWorker.state === 'installed' && navigator.serviceWorker.controller) {
            // An update may now be waiting; offer reload/activation according to policy
            showUpdateBanner();
          }
        });
      });
    } catch (error) {
      console.error('SW registration failed:', error);
    }
  });
}
```

### Service Worker Implementation

```javascript
// sw.js — full service worker
const CACHE_VERSION = 'v2';
const STATIC_CACHE = `docita-static-${CACHE_VERSION}`;
const DYNAMIC_CACHE = `docita-dynamic-${CACHE_VERSION}`;

const STATIC_ASSETS = [
  '/',
  '/index.html',
  '/app.js',
  '/styles.css',
  '/icons/icon-192.png',
  '/icons/icon-512.png',
];

// Install: cache static assets
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(STATIC_CACHE).then((cache) => {
      return cache.addAll(STATIC_ASSETS);
    })
  );
  // Immediate activation is a deliberate policy: it can mix an old page
  // with a new worker. For incompatible updates, offer an update/reload flow.
  self.skipWaiting();
});

// Activate: clean old caches
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) => {
      return Promise.all(
        keys
          .filter((key) => key.startsWith('docita-') && key !== STATIC_CACHE && key !== DYNAMIC_CACHE)
          .map((key) => caches.delete(key))
      );
    })
  );
  // Include activation work in the event lifetime.
  event.waitUntil(self.clients.claim());
});

// Fetch: different strategies for different request types
self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);

  // Skip non-GET requests
  if (request.method !== 'GET') return;

  // Do not intercept other origins or authenticated API responses.
  if (url.origin !== self.location.origin) return;
  if (url.pathname.startsWith('/api/')) return;

  if (url.pathname.startsWith('/static/')) {
    // Cache-first for static assets
    event.respondWith(cacheFirst(request));
  } else if (['/', '/offline.html'].includes(url.pathname)) {
    // Only a public-page allowlist; private dashboards stay network-only.
    event.respondWith(staleWhileRevalidate(request, event));
  }
});

// Cache-first strategy
async function cacheFirst(request) {
  const cached = await (await caches.open(STATIC_CACHE)).match(request);
  if (cached) return cached;

  const response = await fetch(request);
  if (response.ok) {
    const cache = await caches.open(STATIC_CACHE);
    await cache.put(request, response.clone());
  }
  return response;
}

// Network-first strategy
async function networkFirst(request) {
  try {
    const response = await fetch(request);
    if (response.ok) {
      const cache = await caches.open(DYNAMIC_CACHE);
      await cache.put(request, response.clone());
    }
    return response;
  } catch (error) {
    const cached = await (await caches.open(DYNAMIC_CACHE)).match(request);
    if (cached) return cached;
    return new Response(JSON.stringify({ error: 'Offline' }), {
      status: 503,
      headers: { 'Content-Type': 'application/json' },
    });
  }
}

// Stale-while-revalidate for the public allowlist only.
function staleWhileRevalidate(request, event) {
  const cached = caches.open(DYNAMIC_CACHE).then((c) => c.match(request));
  const refresh = fetch(request).then(async (response) => {
    if (response.ok) {
      const cache = await caches.open(DYNAMIC_CACHE);
      await cache.put(request, response.clone());
    }
    return response;
  }).catch(async () =>
    (await cached) ?? new Response('Offline', { status: 503 })
  );
  event.waitUntil(refresh.then(() => {})); // retain background refresh after cache hit
  return cached.then((hit) => hit ?? refresh);
}
```

## Caching Strategies Deep-Dive

| Strategy | How It Works | Pros | Cons | Use Case |
| -------------------------- | ---------------------------------- | --------------------------- | ---------------------------------------- | -------------------------------- |
| **Cache-first** | Check cache → fallback to network | Fast, offline support | Stale data possible | Static assets, images |
| **Network-first** | Try network → fallback to cache | Fresh on network success | May serve stale offline | Explicitly cacheable public data |
| **Stale-while-revalidate** | Return cache, update in background | Fast, potentially stale now | Background lifetime and failure handling | Public semi-dynamic pages |
| **Cache-only** | Only serve from cache | Instant, offline | Never updates | App shell |
| **Network-only** | Only serve from network | Always fresh | No offline | Analytics, tracking |

```
Cache-first: Network-first: Stale-while-revalidate:
┌────────────────────────────────────────────────┐ ┌──────────┐ ┌──────────┐
│ Cache? │──Yes──→ │ Network? │──Yes──→ │ Cache? │──Yes──→ Return cache
└────┬───────────────────────────────────────────┘ └────┬─────┘ │ │ + update in bg
     │No │No └────┬─────┘
     ▼ ▼ │No
┌──────────┐ ┌──────────┐ ▼
│ Fetch │ │ Cache?                               │ ┌──────────┐
│ Network │ └────┬─────┘ │ Fetch │
└────────────────────────────────────────────────┘            │No └──────────┘
                            ▼
                       ┌──────────┐
                       │ 503      │
                       │ Offline  │
                       └──────────┘
```

## Background Sync

Background Sync lets you defer actions until the user has connectivity.

Background Sync support is not universal and retries are browser-scheduled, not a delivery guarantee. Keep a foreground retry path. Use a persistent job id as the server's idempotency key, because a crash after server commit but before local deletion will replay the POST.

```typescript
// Module/shared setup using idb. Private offline payloads need their own
// account scoping, retention and device-security decision.
import { openDB } from 'idb';

const dbPromise = openDB('offline-jobs', 1, {
  upgrade(db) { db.createObjectStore('pending', { keyPath: 'id' }); },
});

async function syncPendingAppointments() {
  const db = await dbPromise;
  for (const job of await db.getAll('pending')) {
    const response = await fetch('/api/appointments', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', 'Idempotency-Key': job.id },
      body: JSON.stringify(job.payload),
    });
    if (!response.ok) {
      // Preserve the job. Surface 401/validation conflicts in the foreground;
      // retries alone cannot fix an expired session or rejected input.
      throw new Error(`Sync failed: HTTP ${response.status}`);
    }
    await db.delete('pending', job.id); // committed server result acknowledged
  }
}

// sw.ts — module service worker; import the shared sync function.
self.addEventListener('sync', (event) => {
  if (event.tag === 'sync-appointments') event.waitUntil(syncPendingAppointments());
});

// main.ts — enqueue durably before requesting background work.
async function queueAppointment(payload: AppointmentData) {
  const db = await dbPromise;
  const id = crypto.randomUUID();
  await db.put('pending', { id, payload });
  const registration = await navigator.serviceWorker.ready;
  if ('sync' in registration) await registration.sync.register('sync-appointments');
  // Also call syncPendingAppointments on reconnect/app open when unsupported.
  return id;
}
```

## Push Notifications

Request notification permission from a user gesture and provide a service-worker `push` handler that displays a notification; subscription alone does not display one. Treat denied permissions and unsupported contexts as normal states.

```typescript
// Request permission
async function requestNotificationPermission() {
  if (!('Notification' in window)) return 'unsupported';

  const permission = await Notification.requestPermission();
  return permission; // 'granted', 'denied', or 'default'
}

// Subscribe to push
async function subscribeToPush() {
  const registration = await navigator.serviceWorker.ready;
  const subscription = await registration.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlBase64ToUint8Array(VAPID_PUBLIC_KEY),
  });

  // Send subscription to server
  await fetch('/api/push/subscribe', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(subscription),
  });
}

// Helper
function urlBase64ToUint8Array(base64String: string) {
  const padding = '='.repeat((4 - (base64String.length % 4)) % 4);
  const base64 = (base64String + padding).replace(/-/g, '+').replace(/_/g, '/');
  const rawData = atob(base64);
  const outputArray = new Uint8Array(rawData.length);
  for (let i = 0; i < rawData.length; i++) {
    outputArray[i] = rawData.charCodeAt(i);
  }
  return outputArray;
}
```

## Install Prompt

```typescript
// Capture beforeinstallprompt event
let deferredPrompt: any;

window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault();
  deferredPrompt = e;
  // Show install button
  showInstallButton();
});

async function installApp() {
  if (!deferredPrompt) return;

  deferredPrompt.prompt();
  const { outcome } = await deferredPrompt.userChoice;

  if (outcome === 'accepted') {
    console.log('User installed PWA');
  }

  deferredPrompt = null;
}

// Detect if already installed
window.addEventListener('appinstalled', () => {
  console.log('PWA was installed');
  deferredPrompt = null;
});
```

## Real-World Use Cases

- **Field/clinical apps with dead zones** — offline-first appointment capture queued via background sync, reconciled on reconnect (Docita's mobile use case).
- **App-shell architecture** — shell cached precache-first at install; only data fetches hit the network; instant loads even on flaky hotel wifi.
- **Push re-engagement** — web push + notification click-through deep into the app, without an app-store release (→ 10.8.05's OTA philosophy).

## Common Mistakes

| Pitfall | Problem | Fix |
| ------------------------- | ----------------------- | --------------------------------------- |
| **Not updating SW** | Users see stale content | Use `skipWaiting()` + `clients.claim()` |
| **Caching API responses** | Stale data displayed | Use network-first for API |
| **No offline fallback** | Blank page when offline | Return cached app shell |
| **Forgetting HTTPS** | SW won't register | Use Let's Encrypt or cloudflare |
| **Large cache** | Storage quota exceeded | Limit cache size, use LRU eviction |

## Interview Questions

**Q: "How do you handle app updates in a PWA?"**

> Register service worker with `updatefound` listener. When a new SW is installed, it enters `installing` state — show an "Update available" banner. Call `registration.waiting.postMessage({ type: 'SKIP_WAITING' })` to activate the new SW. In the new SW, call `self.clients.claim()` to take control of all open tabs. For data consistency: use cache versioning (e.g., `docita-v2`) and delete old caches in the `activate` event.

**Q: "When would you use cache-first vs network-first?"**

> Cache-first for static assets (CSS, JS, images) — they don't change often, and offline support is critical. Network-first for API calls — data should always be fresh, fall back to cache only when offline. Stale-while-revalidate for semi-dynamic content (product pages, blog posts) — return cached version immediately, update in background. For Docita: cache-first for app shell, network-first for appointments API, stale-while-revalidate for patient profiles.

## Summary

1. **The service worker is a programmable network proxy** — installs, activates, then intercepts fetches
2. **Cache strategies are per-resource decisions** — cache-first for static assets, network-first for HTML, stale-while-revalidate for the middle ground
3. **The web app manifest is the install experience** — icons, display mode, theme colors
4. **Updates are opt-in** — skipWaiting + clients.claim patterns, and why you should show a "new version available" toast
5. **Offline is a feature of reliability**, not a gimmick — cache the app shell, queue mutations when possible

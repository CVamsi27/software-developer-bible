# Progressive Web Apps (PWA) — Service Workers, Manifest, Offline

A clinic app may need to open a schedule when the network drops, but caching an authenticated response can expose private data on a shared device. A PWA combines a manifest, worker and storage policies; each capability needs its own boundary and recovery behavior.

## Definition

A **Progressive Web App** is a web application enhanced with capabilities such as installation, offline use or background work where the browser supports them. These are separate capabilities: a web app manifest describes presentation, while a service worker is an event-driven worker that can mediate requests from controlled pages in a secure context. Its fetch handler can serve deliberately cached responses offline; application data and queued edits need their own storage and recovery rules.

> **Textbook Definition:** A progressive web application incrementally adopts supported installation, offline and background capabilities. A manifest describes application presentation, while a service worker can mediate requests and implement an explicit caching lifecycle.

## First Principles

The network can fail after an application has been opened once. Reproducing a usable response requires storing known resources and deciding which request may consume each one. A service worker gives those requests a programmable owner; it does not make arbitrary data safe to cache.

The page and worker have different lifetimes. A new worker can install while an older worker still controls open tabs. Updating therefore needs an explicit compatibility/activation policy, not merely a new cache name. Installation metadata, offline reads and retryable writes remain separate capabilities.

## Which capabilities does this app actually need?

For this offline-capable design, use a secure context (normally HTTPS; browsers treat `localhost` as secure for development), a service worker to intercept requests, and a manifest to describe installed presentation. These are separate capabilities: a manifest does not guarantee an install prompt, and a service worker is not a universal installation prerequisite. Browser criteria vary by browser and operating system.

```text
manifest → presentation/install metadata
page request → controlling service worker → allowed cache or network response
queued edit → durable operation ID → authenticated server write → acknowledgment
```

Trace an offline reload after a successful install: the worker receives the public navigation, finds its stored shell and serves the shell's precached scripts/styles. Without serving those subresources too, cached HTML alone can produce a broken application. A private dashboard needs its own explicit data/security design; the worker below caches only a public example shell.

| `minimal-ui` | Minimal browser controls | When user needs back/forward |

The browser may not support every mode, and install UI differs by browser and operating system. Treat the manifest as metadata consumed by the platform, not as proof that installation is available.

## How does a service worker update without mixing versions?

```
Register → Install → Activate → Idle → Fetch Events
                │ │ │
                ▼ ▼ ▼
          Cache assets Clean Intercept
          for offline old network
                       caches requests
```

### Register the worker and offer updates deliberately

```typescript
// main.ts — register service worker
if ('serviceWorker' in navigator) {
  window.addEventListener('load', async () => {
    try {
      const registration = await navigator.serviceWorker.register('/sw.js', {
        scope: '/',
      });
      console.log('SW registered:', registration.scope);

      // Listen for updates
      registration.addEventListener('updatefound', () => {
        const newWorker = registration.installing;
        newWorker?.addEventListener('statechange', () => {
          if (newWorker.state === 'installed' && navigator.serviceWorker.controller) {
            // An update may now be waiting; offer reload/activation according to policy
            showUpdateBanner();
          }
        });
      });
    } catch (error) {
      console.error('SW registration failed:', error);
    }
  });
}
```

### Serve the public shell and known assets offline

```javascript
// sw.js — full service worker
const CACHE_VERSION = 'v2';
const STATIC_CACHE = `docita-static-${CACHE_VERSION}`;

const STATIC_ASSETS = [
  '/offline.html',
  '/app.js',
  '/styles.css',
  '/icons/icon-192.png',
  '/icons/icon-512.png',
];

// Install: cache static assets
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(STATIC_CACHE).then((cache) => {
      return cache.addAll(STATIC_ASSETS);
    })
  );
  // Immediate activation can mix an old page with a new worker.
  // Choose an accepted-update protocol only when versions remain compatible.
  // Default update policy: wait until older controlled clients close.
});

// Activate: clean old caches
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) => {
      return Promise.all(
        keys
          .filter((key) => key.startsWith('docita-') && key !== STATIC_CACHE)
          .map((key) => caches.delete(key))
      );
    })
  );
  // Include activation work in the event lifetime.
  event.waitUntil(self.clients.claim());
});

// Never cache a navigation response solely because its path looks public.
// SSR pages can vary by cookie or account even when they share a URL.
self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);

  // Skip non-GET requests
  if (request.method !== 'GET') return;

  // Do not intercept other origins or authenticated API responses.
  if (url.origin !== self.location.origin) return;
  if (url.pathname.startsWith('/api/')) return;

  if (request.mode === 'navigate') {
    event.respondWith(networkWithOfflineFallback(request));
    return;
  }

  if (STATIC_ASSETS.includes(url.pathname) && url.pathname !== '/offline.html') {
    event.respondWith(cacheFirst(request));
  }
});

// Cache-first for versioned, same-origin static assets only. Cache failure
// must not turn a successful network response into a failed page load.
async function cacheFirst(request) {
  try {
    const cached = await (await caches.open(STATIC_CACHE)).match(request);
    if (cached) return cached;
  } catch {
    // Storage can be unavailable or over quota; try the network.
  }

  const response = await fetch(request);
  if (response.ok) {
    try {
      const cache = await caches.open(STATIC_CACHE);
      await cache.put(request, response.clone());
    } catch {
      // The fetched response remains usable even if it could not be cached.
    }
  }
  return response;
}

async function networkWithOfflineFallback(request) {
  try {
    return await fetch(request); // HTML is not written to this shared cache.
  } catch {
    const fallback = await caches.open(STATIC_CACHE)
      .then((cache) => cache.match('/offline.html'))
      .catch(() => undefined);
    return fallback ?? new Response('Offline', {
      status: 503,
      headers: { 'Content-Type': 'text/plain; charset=utf-8' },
    });
  }
}
```

If an application needs a fully offline public SPA shell, handle only its known app routes and serve a shell that contains no user-specific data. Protect API responses separately. A URL allowlist alone cannot establish that a response is public.

## Which cache strategy matches this resource?

| Strategy | How It Works | Pros | Cons | Use Case |
| -------------------------- | ---------------------------------- | -------------------------------------------- | ---------------------------------------- | -------------------------------- |
| **Cache-first** | Check cache → fallback to network | Fast, offline support | Stale data possible | Static assets, images |
| **Network-first** | Try network → fallback to cache | Fresh on network success | May serve stale offline | Explicitly cacheable public data |
| **Stale-while-revalidate** | Return cache, update in background | Fast, potentially stale now | Background lifetime and failure handling | Public semi-dynamic pages |
| **Cache-only** | Only serve from cache | Instant, offline | Never updates | App shell |
| **Network-only** | Bypass this application cache | Current network response; upstream may cache | No offline fallback | Private/noncacheable requests |

```text
cache-first: cache hit → return; miss → fetch → optional cache write → return
network-first: fetch succeeds → return/store; transport fails → cache or failure
stale-while-revalidate: hit → return now + refresh; miss → await refresh/failure
```

Cache API keys and storage are application-controlled; ordinary HTTP cache headers do not automatically expire entries. Distinguish an HTTP error response from a network failure: the server did respond, so do not silently replace a meaningful `401`, `404` or `500` with stale data. Bound retention and classify cache-write failures so the UI never claims durable offline capability from an unsuccessful installation.

For network-first data caching, require an explicit public-data contract and keep that policy separate from private account routes. A `Cache-Control` header is useful evidence for HTTP caches but does not automatically govern Cache API storage.

## How should an offline write recover?

Background Sync lets you defer actions until the user has connectivity.

Background Sync support is not universal and retries are browser-scheduled, not a delivery guarantee. Keep a foreground retry path. Use a persistent job id as the server's idempotency key, because a crash after server commit but before local deletion will replay the POST.

```typescript
// Module/shared setup using idb. Private offline payloads need their own
// account scoping, retention and device-security decision.
import { openDB } from 'idb';

const dbPromise = openDB('offline-jobs', 1, {
  upgrade(db) { db.createObjectStore('pending', { keyPath: 'id' }); },
});

async function syncPendingAppointments() {
  const db = await dbPromise;
  for (const job of await db.getAll('pending')) {
    const response = await fetch('/api/appointments', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', 'Idempotency-Key': job.id },
      body: JSON.stringify(job.payload),
    });
    if (!response.ok) {
      // Preserve the job. Surface 401/validation conflicts in the foreground;
      // retries alone cannot fix an expired session or rejected input.
      throw new Error(`Sync failed: HTTP ${response.status}`);
    }
    await db.delete('pending', job.id); // committed server result acknowledged
  }
}

// sw.ts — module service worker; import the shared sync function.
self.addEventListener('sync', (event) => {
  if (event.tag === 'sync-appointments') event.waitUntil(syncPendingAppointments());
});

// main.ts — enqueue durably before requesting background work.
async function queueAppointment(payload: AppointmentData) {
  const db = await dbPromise;
  const id = crypto.randomUUID();
  await db.put('pending', { id, payload });
  const registration = await navigator.serviceWorker.ready;
  if ('sync' in registration) await registration.sync.register('sync-appointments');
  // Also call syncPendingAppointments on reconnect/app open when unsupported.
  return id;
}
```

## When is a push notification appropriate?

Request permission from a user gesture. A push subscription only gives the server an endpoint; the worker also needs a `push` handler to display a notification. Treat denied permission and unsupported contexts as normal states.

```typescript
// Request permission
async function requestNotificationPermission() {
  if (!('Notification' in window)) return 'unsupported';

  const permission = await Notification.requestPermission();
  return permission; // 'granted', 'denied', or 'default'
}

// Subscribe to push
async function subscribeToPush() {
  if (!('serviceWorker' in navigator) || !('PushManager' in window) ||
      !('Notification' in window) || Notification.permission !== 'granted') {
    throw new Error('Push is unavailable or permission was not granted');
  }
  const registration = await navigator.serviceWorker.ready;
  const subscription = await registration.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlBase64ToUint8Array(VAPID_PUBLIC_KEY),
  });

  // Send subscription to server
  const response = await fetch('/api/push/subscribe', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(subscription),
  });
  if (!response.ok) throw new Error('Subscription was not saved');
}

// Helper
function urlBase64ToUint8Array(base64String: string) {
  const padding = '='.repeat((4 - (base64String.length % 4)) % 4);
  const base64 = (base64String + padding).replace(/-/g, '+').replace(/_/g, '/');
  const rawData = atob(base64);
  const outputArray = new Uint8Array(rawData.length);
  for (let i = 0; i < rawData.length; i++) {
    outputArray[i] = rawData.charCodeAt(i);
  }
  return outputArray;
}
```

```javascript
// sw.js — display a user-visible message and keep click-through same-origin.
self.addEventListener('push', (event) => {
  let payload = {};
  try {
    const value = event.data?.json();
    if (value && typeof value === 'object') payload = value;
  } catch { /* ignore malformed payload */ }
  const title = typeof payload.title === 'string' ? payload.title : 'Update';
  const body = typeof payload.body === 'string' ? payload.body : '';
  const path = typeof payload.path === 'string' && payload.path.startsWith('/') && !payload.path.startsWith('//')
    ? payload.path : '/';
  event.waitUntil(self.registration.showNotification(title, { body, data: { path } }));
});

self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  const path = event.notification.data?.path ?? '/';
  const destination = new URL(path, self.location.origin);
  event.waitUntil(self.clients.openWindow(destination.href));
});
```

Associate subscriptions with an authenticated account on the server, and remove expired endpoints. Push delivery is best effort; do not make it the only channel for a critical alert.

## How can installation work across browsers?

`beforeinstallprompt` is experimental, non-standard and unavailable in some widely used browsers. Feature-detect it and keep the app usable without a custom install button; where it is absent, explain the platform's ordinary install path if useful. [MDN documents its limited support](https://developer.mozilla.org/en-US/docs/Web/API/BeforeInstallPromptEvent).

```typescript
// This experimental event is not in the standard TypeScript DOM event map.
type InstallPromptEvent = Event & {
  prompt(): Promise<void>;
  userChoice: Promise<{ outcome: 'accepted' | 'dismissed' }>;
};

let deferredPrompt: InstallPromptEvent | null = null;

window.addEventListener('beforeinstallprompt', (event: Event) => {
  event.preventDefault();
  deferredPrompt = event as InstallPromptEvent;
  showInstallButton();
});

async function installApp() {
  if (!deferredPrompt) return;

  await deferredPrompt.prompt(); // call from the user's install-button action
  const { outcome } = await deferredPrompt.userChoice;

  if (outcome === 'accepted') {
    console.log('User accepted the install prompt');
  }

  deferredPrompt = null;
}

// Detect if already installed
window.addEventListener('appinstalled', () => {
  console.log('PWA was installed');
  deferredPrompt = null;
});
```

## What changes when offline data is sensitive?

| Feature | Implementation |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| **Offline appointment viewing** | Explicit permitted dataset, account scoping, retention and current/stale labels |
| **Offline form submission** | Durable scoped job IDs, foreground retry and server-side duplicate/conflict policy |
| **Push notifications** | Appointment reminders, prescription updates |
| **Install on tablet** | Clinic tablets install as standalone app |
| **Offline patient lookup** | Product/security approval of device exposure, minimum dataset and logout policy |

---

These are design options, not evidence that every capability is implemented in Docita. A clinical shell must not silently store private responses through a blanket cache-first rule.

## Summary

A PWA is a set of independently supported capabilities. The manifest describes an installed presentation; a service worker owns explicit request and cache rules; background work depends on browser scheduling; and private offline data needs account scoping, retention and recovery. Version compatibility and server authorization remain part of the design even when the app appears to work offline.

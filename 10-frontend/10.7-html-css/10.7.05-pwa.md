# Progressive Web Apps (PWA) — Service Workers, Manifest, Offline

A clinic app may need to open a schedule when the network drops, but caching an authenticated response can expose private data on a shared device. A progressive web app (PWA) combines browser capabilities; each one needs its own support, lifecycle and recovery policy.

## Definition

A **Progressive Web App** is a web application that uses supported web-platform capabilities to provide experiences such as installation, offline access or background work. These capabilities are independent: installation does not universally require a service worker. A manifest describes an installed presentation; a service worker can mediate requests for controlled pages; storage keeps selected responses or application data. None of them guarantees that the app is installable, always available offline or safe to cache.

> **Textbook Definition:** A progressive web application incrementally adopts supported installation, offline and background capabilities. A manifest describes application presentation, while a service worker can mediate requests and implement an explicit caching lifecycle.

## First Principles

A network failure matters only if the app has a response or operation it can safely use without the server. That requires choosing what to store, how long it remains valid and what happens when an update or retry overlaps an open client. A service worker gives those rules an event-driven owner; it does not make stored data private or writes exactly-once.

## Choose the capability the user needs

| Capability | Owner | Boundary to decide |
| ------------------------------ | ----------------------------- | --------------------------------------------------------------- |
| Install presentation | Web app manifest | Browser and operating-system install criteria vary |
| Request interception | Service worker | Secure context, scope, lifecycle and version compatibility |
| Cached responses | Cache API | The app must set freshness, keys, retention and deletion policy |
| Offline records or queued work | IndexedDB | Schema, account scope, quota and replay behavior |
| Deferred sync or push | Browser-managed worker events | Support, permission and delivery timing are not guaranteed |

The browser's ordinary HTTP cache is separate from the Cache API. Cache API entries do not automatically expire from HTTP cache headers. See [Browser Storage](10.7.08-browser-storage.md) for storage quotas, database transactions and client-data trust boundaries.

## Describe the installed presentation

A manifest supplies a name, launch URL, display preference and icon metadata. The browser decides whether and how to offer installation; a manifest alone does not install the app or guarantee a prompt.

```json
{
  "name": "Clinic Schedule",
  "short_name": "Schedule",
  "start_url": "/app/",
  "scope": "/app/",
  "display": "standalone",
  "theme_color": "#163d73",
  "icons": [
    { "src": "/icons/192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

`standalone` removes ordinary browser chrome where supported; it does not remove operating-system controls. `browser`, `minimal-ui` and `fullscreen` describe other display preferences, but platforms may vary in how they honor them. Keep the site usable when no install offer appears.

## Keep the worker and its clients compatible

On first registration, the page may not yet be controlled by the new worker. On an update, the browser normally lets the current worker continue serving existing clients while the new worker waits. Only after old clients are gone does the new worker activate. This protects a tab that still refers to older assets.

Register from the page with `navigator.serviceWorker.register('/sw.js')` when `navigator.serviceWorker` is available. Workers require a secure context (normally HTTPS; `localhost` is treated as secure for development), and the registration scope determines which pages they can control.

A safe update therefore keeps the old worker and its assets available to its clients. Delete the old cache only when the new worker activates under a compatible deployment policy. `skipWaiting()` and `clients.claim()` change that lifecycle; use them only with an update protocol that prevents old pages from requesting removed or incompatible resources.

The example below precaches a small set of same-origin, versioned assets and one offline page. It leaves private APIs and document navigations out of the shared cache. Change the cache version with the asset set; deploy the matching files before activating the worker.

```javascript
const STATIC_CACHE = 'clinic-shell-v4';
const STATIC_ASSETS = new Set([
  '/assets/app.a13d.js',
  '/assets/app.3ac0.css',
]);
const OFFLINE_PAGE = '/offline.html';

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(STATIC_CACHE).then((cache) =>
      cache.addAll([...STATIC_ASSETS, OFFLINE_PAGE]),
    ),
  );
});

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const keys = await caches.keys();
    await Promise.all(keys
      .filter((key) => key.startsWith('clinic-shell-') && key !== STATIC_CACHE)
      .map((key) => caches.delete(key)));
  })());
});

self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);
  if (request.method !== 'GET' || url.origin !== self.location.origin) return;

  if (request.mode === 'navigate') {
    event.respondWith(networkOrOffline(request));
  } else if (STATIC_ASSETS.has(url.pathname)) {
    event.respondWith(cachedAsset(request));
  }
});

async function cachedAsset(request) {
  const cache = await caches.open(STATIC_CACHE);
  return (await cache.match(request)) ?? fetch(request);
}

async function networkOrOffline(request) {
  try {
    return await fetch(request);
  } catch {
    const offline = await caches.open(STATIC_CACHE)
      .then((cache) => cache.match(OFFLINE_PAGE))
      .catch(() => undefined);
    return offline ?? new Response('Offline', {
      status: 503,
      headers: { 'Content-Type': 'text/plain; charset=utf-8' },
    });
  }
}
```

`install` fails if an asset in `addAll()` cannot be fetched, so an incomplete version does not replace the working worker. The navigation handler falls back only when `fetch()` rejects; an HTTP `404` or `500` is a real server response and remains visible. A cached HTML shell must also reference assets that the worker can serve offline.

## Match the cache rule to the data

| Rule | Useful for | Important limit |
| ----------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------- |
| Cache-first | Versioned static assets | Stale content unless filenames/cache versions change |
| Network-first with offline fallback | Navigations where a generic offline page is acceptable | The fallback may be generic or stale; do not replace meaningful HTTP errors |
| Stale-while-revalidate | Public data that tolerates a briefly stale response | The caller must handle the asynchronous refresh and its failure |
| Network-only | Account-specific or non-cacheable requests | No offline response unless another deliberate design supplies one |

A URL that looks public is not proof its response is public. Server-rendered routes can vary by cookie or account. Cache only explicitly approved responses, bound retention and remove obsolete entries. If a product needs sensitive offline records, define the permitted fields, account/device scoping, stale-data label, re-authentication and logout/retention policy. Cache API and IndexedDB contents are accessible to same-origin script and may be cleared or evicted; a client-side cache never replaces server authorization.

## Replay an offline write as an idempotent operation

A queued edit is a local operation, not yet a confirmed server write. Store it in IndexedDB and wait for its transaction to complete before telling the user it is saved to this device. When connectivity returns, send the same ID as an idempotency key. The server must atomically enforce that key and return the original committed outcome for a replay; generating a new key on retry can duplicate the effect.

```typescript
async function sendQueuedAppointment(job: {
  id: string;
  payload: AppointmentData;
}) {
  const response = await fetch('/api/appointments', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Idempotency-Key': job.id,
    },
    body: JSON.stringify(job.payload),
  });

  if (response.ok) {
    await db.delete('pending', job.id); // delete only after server acknowledgment
    return;
  }

  if ([401, 409, 422].includes(response.status)) {
    await markForUserAction(job.id, response.status);
    return; // authentication, conflict or corrected input needs foreground recovery
  }

  throw new Error(`Retry later: HTTP ${response.status}`);
}
```

Here, `db` is the application's IndexedDB wrapper and `markForUserAction` records an error the user must resolve. Background Sync can ask a service worker to retry when the browser has connectivity, but support and scheduling vary. Run the same sender when the app opens or observes reconnection. Preserve jobs on transport or server failure; present authentication, validation and conflict problems for user action instead of retrying them forever. Never describe a queued write as server-confirmed until its result is acknowledged.

## Treat installation and notifications as enhancements

A custom install button can use `beforeinstallprompt` where the browser exposes it. The event is non-standard and has limited availability; feature-detect it, prevent the default browser UI only when replacing it, retain the event for the user's button action, and keep the ordinary site usable when it never fires. [MDN documents the event's support limits](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeinstallprompt_event).

Push requires permission and a subscription associated with a service worker. Ask after explaining the value to the user, associate and remove subscriptions under the authenticated account, and treat delivery as best effort. Keep sensitive details out of notification text because it may appear on a locked screen. A worker's `push` handler shows a notification; its click handler should validate destinations as same-origin before opening them.

```javascript
function sameOriginUrl(value) {
  try {
    const url = new URL(typeof value === 'string' ? value : '/', self.location.origin);
    return url.origin === self.location.origin ? url.href : self.location.origin;
  } catch {
    return self.location.origin;
  }
}

self.addEventListener('push', (event) => {
  let payload = {};
  try {
    const data = event.data?.json();
    if (data && typeof data === 'object') payload = data;
  } catch { /* malformed push payload */ }

  const title = typeof payload.title === 'string' ? payload.title : 'Update';
  const body = typeof payload.body === 'string' ? payload.body : '';
  event.waitUntil(self.registration.showNotification(title, {
    body,
    data: { url: sameOriginUrl(payload.url) },
  }));
});

self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  const url = sameOriginUrl(event.notification.data?.url);
  event.waitUntil(self.clients.openWindow(url));
});
```

These are optional capabilities, not a checklist every web product should implement. A trustworthy offline experience is smaller than “cache everything”: serve a known shell, report whether a write is local or acknowledged, and provide a safe path back to current server state.

## Summary

A PWA combines optional browser capabilities with separate support and failure rules. The manifest describes launch presentation; the worker owns a versioned request policy; storage owns offline records; retries need server-enforced idempotency. Keep authenticated data out of shared caches unless the product has a deliberate, tested offline privacy policy.

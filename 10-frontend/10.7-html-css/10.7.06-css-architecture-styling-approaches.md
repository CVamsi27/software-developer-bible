# CSS Architecture & Styling Approaches

> Styling at scale is an architecture problem: how you manage specificity, name things, layer concerns, and pick between CSS Modules, CSS-in-JS, and utility-first Tailwind. This file covers cascade layers (`@layer`), BEM, CUBE CSS, ITCSS, a full decision matrix, stylelint governance, and migration strategies between approaches.

## TL;DR

CSS architecture is dependency management for styles: naming (BEM), scoping (CSS Modules, scoped styles), layers (@layer), and utility systems (Tailwind) — each a different answer to the cascade's global-scope problem.

## First Principles

CSS architecture is the management of *cascade globalization*:

1. **CSS has no modules: every selector is global** — BEM (naming), CSS Modules (build-time scoping), styled-components (runtime scoping), Tailwind (utility composition) are four answers to the same problem: preventing accidental rule collisions at scale (→ 10.7.02's cascade as the root cause).
2. **Specificity inflation is the entropy**: architecture exists to keep specificity flat — `!important` wars are the end-state of unmanaged specificity; utilities and single-class selectors keep the cascade predictable.
3. **The trade is runtime cost vs DX**: CSS-in-JS pays runtime/parse cost for co-location and dynamism; Tailwind pays no runtime and verbose markup for total cascade predictability — modern default: zero-runtime (Tailwind/CSS Modules), CJS-in-JS for truly dynamic theming only.

## Definition

**CSS architecture** is the set of conventions that keeps a growing stylesheet predictable: controlled specificity, consistent naming, explicit ordering of concerns, and a styling *approach* (scoped files, runtime-injected JS styles, or utility classes) chosen deliberately for the framework and rendering model in use.

## Why It Matters

- **Specificity wars are a tax** — unmanaged selectors escalate to `!important` arms races
- **The approach choice is now a stack decision** — it affects bundle cost, SSR/RSC compatibility, and design tokens
- **Cascade layers changed the game (2022+)** — `@layer` solves ordering without specificity hacks
- **Interviews probe trade-offs**, not loyalty — "why Tailwind here but Modules there?" expects a reasoned answer

## How It Works

### 1. Specificity management with cascade layers

```text
ORIGIN LAYERS (lowest → highest priority):
┌─────────────────────────────────────────────────────────┐
│ @layer reset < theme < base < components < utilities    │
│                                                         │
│ • Un-layered styles beat ALL layered styles             │
│ • !important inside a layer beats lower layers' normal  │
│   declarations but inverts within its own layer         │
│ • Layer order is declared once; later @layer statements │
│   only append                                           │
└─────────────────────────────────────────────────────────┘
```

```css
@import 'reset.css' layer(reset);
@layer theme, base, components, utilities;

@layer base {
  a { color: var(--color-accent); }
}

@layer components {
  .card__link { color: var(--color-heading); } /* wins over base regardless of specificity */
}

@layer utilities {
  .text-brand { color: var(--color-brand) !important; }
}
```

Before `@layer`, teams fought source-order with specificity escalation or ITCSS-style file ordering. Now the layer list *is* the architecture: one line documents precedence for the whole codebase.

### 2. BEM naming

`block__element--modifier` — flat class names that encode structure without nesting:

```css
.card { }
.card__title { }
.card__body { }
.card--featured { }
.card__title--muted { }
```

Wins: no descendant selectors (specificity stays 0-1-0), greppable, safe to move markup. Costs: verbosity, naming debates, no scoping enforcement (it's convention, not compiler).

### 3. CUBE CSS ideas

CUBE = **Composition, Utility, Block, Exception**. Blocks are minimal structural components; utilities do the visual heavy-lifting; exceptions handle deviations via data-attributes instead of modifier explosion:

```html
<article class="card" data-state="featured">...</article>
```

```css
.card { display: block; padding-block: var(--space-4); }
[data-state='featured'] { border-color: var(--color-brand); }
```

Take-away even if you don't adopt CUBE wholesale: prefer composition of small pieces over ever-growing modifier matrices, and let state live on attributes.

### 4. ITCSS layering (pre-cascade-layers classic)

Inverted Triangle CSS orders files from low-specificity/global to high-specificity/local:

```text
Settings  → tokens (SCSS vars / custom properties)
Tools     → mixins, functions
Generic   → reset, normalize
Elements  → bare h1, a, ul styling
Objects   → layout patterns (.o-container, .o-grid)
Components→ .c-card, .c-button
Utilities → .u-hidden, .u-mt-8   (highest priority, last)
```

Still a good mental model; today it maps almost 1:1 onto named `@layer`s.

### 5. The three approaches compared

| Dimension | CSS Modules | CSS-in-JS (styled-components / Emotion) | Utility-first (Tailwind) |
| --------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Scoping | build-time hash per file | generated class per component | global utility classes |
| Runtime cost | none | Runtimes inject styles at runtime (zero-runtime variants exist) | none |
| Bundle growth | grows ~linearly with styles | similar + runtime KB (~10–12 kB) | near-zero marginal once JIT sees used classes only |
| SSR | fine | needs style extraction setup; React Server Components incompatible with runtime versions | fine |
| RSC compatibility | yes | runtime libraries problematic in server components | yes |
| Design tokens | via CSS custom properties | via theme JS objects (typed) | via `tailwind.config` theme extension |
| Dead-code elimination | manual | manual | automatic (only seen classes ship) |
| Learning curve | low | medium | medium (memorize utility vocabulary) |
| Best fit | design-system components, mixed frameworks | highly dynamic theming in client-heavy apps | fast product iteration, consistent spacing/type scales |

Decision shortcut:

```text
RSC / server-heavy Next.js app?      ──▶ CSS Modules or Tailwind (not runtime CSS-in-JS)
Design system consumed by many apps? ──▶ CSS Modules + tokens in custom properties
Client-only dashboard, dynamic themes?──▶ zero-runtime CSS-in-JS (vanilla-extract/panda) or Tokens+Modules
Small team, velocity first?           ──▶ Tailwind
Legacy SCSS codebase?                 ──▶ keep BEM/ITCSS discipline; migrate incrementally
```

## Code Examples

### 1. CSS Modules component

```css
/* Button.module.css */
.button {
  appearance: none;
  border-radius: var(--radius-md);
  background: var(--color-primary);
}
.variantSecondary {
  background: transparent;
  border: 1px solid var(--color-border);
}
```

```tsx
import styles from './Button.module.css';

export function Button({ variant = 'primary' }: { variant?: 'primary' | 'secondary' }) {
  return (
    <button className={variant === 'secondary'
      ? `${styles.button} ${styles.variantSecondary}`
      : styles.button} />
  );
}
```

### 2. styled-components with typed theme

```tsx
import styled, { ThemeProvider } from 'styled-components';

interface Theme { color: { primary: string }; radius: { md: string } }

const Button = styled.button<{ $variant: 'primary' | 'ghost' }>`
  background: ${({ theme, $variant }) =>
    $variant === 'primary' ? theme.color.primary : 'transparent'};
  border-radius: ${({ theme }) => theme.radius.md};
`;

<ThemeProvider theme={theme}>
  <Button $variant="primary">Save</Button>
</ThemeProvider>
```

### 3. Tailwind with token-backed config

```javascript
// tailwind.config.js — tokens defined once, consumed as utilities
module.exports = {
  content: ['./app/**/*.{ts,tsx}'],
  theme: {
    extend: {
      colors: {
        primary: 'var(--color-primary)',
        border: 'var(--color-border)',
      },
      borderRadius: { md: 'var(--radius-md)' },
    },
  },
};
```

```tsx
<button className="rounded-md bg-primary px-4 py-2 text-white">Save</button>
<button className="rounded-md border border-border bg-transparent px-4 py-2">Cancel</button>
```

### 4. stylelint governance

```json
{
  "extends": ["stylelint-config-standard"],
  "rules": {
    "max-nesting-depth": 2,
    "selector-max-specificity": "0-2-0",
    "declaration-property-value-disallowed-list": {
      "/^font/": ["12px", "14px"],
      "/^color/": ["red", "#f00"]
    },
    "no-invalid-position-at-import-rule": true,
    "annotation-no-unknown": true
  },
  "overrides": [
    {
      "files": ["**/*.module.css"],
      "rules": { "selector-class-pattern": "^[a-z][a-zA-Z0-9]*$" }
    }
  ]
}
```

Enforce in CI alongside ESLint/Prettier — lint rules encode the architecture so code review argues about features, not formatting or specificity creep.

### 5. Migration: CSS-in-JS to Tailwind (incremental)

```text
WAVE 1  Add Tailwind alongside; new features must use it (lint-enforced)
WAVE 2  Map existing theme object → tailwind.config + :root custom props
        so both systems read the SAME tokens during transition
WAVE 3  Convert leaf components (buttons, inputs) page by page;
        snapshot visual tests guard each conversion
WAVE 4  Delete runtime provider + babel plugin; drop ~12 kB runtime,
        re-test hydration timing
```

The token bridge in wave 2 is the load-bearing step: when both systems reference identical custom properties, converting a component becomes a mechanical find-and-replace with no visual drift.

## Real-World Use Cases

- **Design-system package consumed by many apps** — CSS Modules or utility classes for scoping; tokens (→ 10.7.07) for theming.
- **Legacy + new CSS coexisting** — `@layer` puts resets < legacy < components, ending the specificity war without rewriting anything.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------- | --------------------------------------------------------------------- |
| Escalating specificity (`div nav ul li a.active`) | Keep selectors ≤ 0-2-0; use single class names + layers |
| Sprinkling `!important` to win fights | Move rules into ordered `@layer`s instead |
| Runtime CSS-in-JS inside React Server Components | Use CSS Modules/Tailwind in server trees; zero-runtime libs if needed |
| Hard-coded hex/px scattered across files | Route every value through semantic custom properties/tokens |
| Deeply nested SCSS mirroring DOM | Flatten with BEM-style names or composable utilities |
| Two sources of truth for tokens (JS + CSS) | Generate one from the other in CI |

## Best Practices

1. **Declare your layer order once** (`reset, theme, base, components, utilities`) and document it at the top of the entry stylesheet
2. **Pick the approach per app, not per file** — mixing all three in one repo multiplies review cost; if unavoidable, fence each into clear directories
3. **Tokens are the contract** — whatever the approach, colors/space/radii resolve through custom properties so theming (see next chapter) works everywhere
4. **Lint the architecture**: specificity caps, nesting depth, disallowed raw values in stylelint
5. **Prefer build-time scoping** (Modules/Tailwind/vanilla-extract) unless you have a concrete need for runtime injection
6. **Migrate incrementally behind a token bridge**, never a big-bang rewrite
7. **Keep utilities last** in precedence — they are escape hatches, not defaults

## Performance Considerations

- Runtime CSS-in-JS costs both KB and main-thread time during render; zero-runtime variants shift cost to compile time
- Tailwind's JIT output stays roughly constant as the codebase grows — a real advantage past ~100 screens
- Unlayered legacy styles override everything layered — during migrations, wrap old code in a low-priority layer rather than fighting rule-by-rule
- Critical CSS extraction matters most for SSR apps; Modules and Tailwind extract cleanly, runtime-injected styles complicate it

## Summary

- Cascade layers give declarative, documented precedence — adopt `@layer` before reaching for `!important`
- BEM/CUBE/ITCSS remain useful naming-and-ordering disciplines underneath any tooling
- Approach choice = runtime cost + SSR/RSC compatibility + token story: Modules for systems, runtime CSS-in-JS only where dynamism demands it, Tailwind for velocity
- Stylelint turns architecture into enforceable rules
- Migrations succeed via shared custom-property tokens and incremental waves with visual regression coverage

## Cheat Sheet

```text
CSS ARCHITECTURE CHEAT SHEET
════════════════════════════════════════════════════════════════

LAYERS:
  @layer reset, theme, base, components, utilities;
  unlayered > layered · order declared once · later = append

NAMING:
  BEM block__element--modifier · specificity stays 0-1-0
  CUBE: Composition · Utility · Block · Exception (data-state)

ITCSS ORDER: settings → tools → generic → elements
             → objects → components → utilities

APPROACHES:
  Modules    build-time scope · no runtime · RSC-safe
  CSS-in-JS  theme JS objects · runtime cost (~12kB) · avoid in RSC
  Tailwind   JIT · auto dead-code · tokens via config → vars

GOVERNANCE (stylelint):
  selector-max-specificity: 0-2-0 · max-nesting-depth: 2
  ban raw hex/px outside token definitions

MIGRATION:
  new code on target system → bridge tokens via :root vars
  convert leaf-first w/ visual snapshots → delete runtime last
```

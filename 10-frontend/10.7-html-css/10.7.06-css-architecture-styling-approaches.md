# CSS Architecture & Styling Approaches

When two components accidentally override one another, separate three questions: who owns each selector, which rule wins, and where shared values come from.

```css
/* excerpt: scope selectors cleanly and separate cascade precedence from source order */
@scope (.card) {
  .title { font-weight: 600; }
}
```

## Definition

CSS architecture organizes ownership, naming, and precedence so styling remains predictable as components grow. Scoping tools, utility classes, layers, and tokens address different parts of that problem. Choose them around the application's rendering and maintenance needs.

> **Textbook Definition:** CSS architecture assigns style ownership, scope, and precedence across a growing interface. Naming conventions, scoped outputs, cascade layers, and tokens provide different controls over conflicts and reuse.

## First Principles

Two components can accidentally match the same selector or depend on stylesheet order. Giving a rule a clear owner reduces unintended matches; giving concerns explicit precedence reduces override surprises. Those are separate decisions: a hashed class does not solve theme precedence, and cascade layers do not prevent an overly broad selector from matching the wrong elements.

## 1. Follow One Component Override

```css
@layer reset, theme, components, utilities;

@layer theme {
  :root { --action-bg: #163d73; }
}
@layer components {
  .button { background: var(--action-bg); padding: 0.5rem 1rem; }
}
@layer utilities {
  .compact { padding: 0.25rem 0.5rem; }
}
```

For an element with classes `button compact`, both padding rules match as normal author declarations in different layers, so the later `utilities` layer wins before specificity is compared and the background resolves from `--action-bg`.

An unlayered normal rule still outranks these layered rules, and `!important` declarations reverse layer precedence — choose ordering deliberately instead of claiming utilities always win.

```text
selector ownership → matching rules → cascade precedence → token values → component style
```

## 2. Choose How Selectors Find Their Owner

Block Element Modifier (BEM) uses names such as `card__title--muted` to express ownership by convention. CSS Modules typically transform local class names during a build and expose a mapping to the component, while utility-first CSS composes shared narrowly focused classes in markup and Shadow DOM constrains style participation with host, slot, and custom-property rules. Ordinary stylesheets often have document-wide reach, though `@scope` and module boundaries narrow that reach deliberately.

CUBE CSS (Composition, Utility, Block, Exception) and Inverted Triangle CSS (ITCSS, organizing rules from broad low-specificity base styles to focused utilities) are architectural disciplines rather than one-to-one mappings to cascade layers. State can live in modifier classes, attributes, or framework props; pick whichever keeps ownership clear.

Native `@scope` also supports an explicit lower boundary (donut scoping) and proximity-based cascade ties: `@scope (.card) to (.card-content)` applies rules inside `.card` while stopping at `.card-content`, preventing outer card styles from leaking into nested widgets. When two `@scope` rules tie on layer and specificity, the rule whose scope root is closer in the DOM wins regardless of stylesheet order:

```css
@scope (.card) to (.card-content) {
  :scope { border: 1px solid var(--border-subtle); }
  .title { font-weight: 600; }
}
```

## 3. Rendering Cost and Authoring Style Are Distinct

| Approach | Main ownership mechanism | Cost or constraint to assess |
| -------------------- | --------------------------------------------------------- | ----------------------------------------------------------------- |
| CSS Modules | Build-generated local names | Imports, global escapes, and emitted stylesheet ordering |
| Runtime CSS-in-JS | Generated rules linked to component execution | Runtime, SSR extraction and streaming, and framework integration |
| Build-time CSS-in-JS | Extracted static styles plus supported dynamic mechanisms | Compiler constraints and output ordering |
| Utilities | Shared classes composed at call sites | Source detection, generated variants, and readable component APIs |

All emitted CSS still participates in style calculation and rendering. "Zero runtime" means no required style-generation runtime, not zero browser cost. Dynamic theming can use custom properties with any approach; it does not necessarily require runtime CSS-in-JS.

Runtime-injection libraries need framework- and version-specific support for SSR and Server Components. Do not infer compatibility from generic React support. Bundles depend on versions, imports, and generated rules, so measure actual output rather than quoting fixed kilobytes or constant growth beyond a screen count.

## 4. Tailwind's Version Changes Configuration

For Tailwind v4, CSS-first theme definitions create utilities from theme variables. Existing JavaScript configurations belong to a different configuration path and are not automatically the current default.

```css
@import "tailwindcss";
@theme inline {
  --color-action: var(--action-bg);
}
```

`bg-action` now resolves through the application's `--action-bg`. Keep complete detectable class names in source, or use the supported source and safelisting mechanisms. Building a class name from unrestricted runtime fragments can leave its CSS absent. Source detection does not prove every unused selector is eliminated, and new utility and variant combinations still grow output. See [Tailwind theme variables](https://tailwindcss.com/docs/theme).

## 5. Govern Changes Through a Small Contract

Define the preferred selector and style ownership, layer order, and token vocabulary. Stylelint can check specificity, nesting, and prohibited value patterns, but every rule needs an intentional exception policy. Enforce useful constraints rather than insisting every literal dimension must become a token.

A migration can share semantic custom properties between old and new styles, then move one component at a time. Matching tokens helps preserve color and spacing intent; it does not make conversion a visual no-op. Reset rules, specificity, ordering, typography, and interaction states can differ. Compare representative responsive, focus, disabled, and theme states before removing old providers and plugins.

A low-priority layer can contain legacy normal declarations when tooling permits, but importing old CSS into a layer changes precedence and may reveal dependencies. Inventory important rules and unlayered exceptions before assuming the layer ends all conflicts. Register tokens with `@property` when they require type validation, safe typed fallbacks, or smooth CSS transitions (such as animating gradient stops or alpha tokens), while keeping lightweight unregistered custom properties for standard inherited theme values (see [Theming & Design Tokens](10.7.07-theming-design-tokens.md) for the full token system).

## Summary

Separate selector ownership, precedence, and value sharing. Trace one override, choose a tool compatible with the rendering model, and measure emitted and runtime cost. Migrate through deliberate contracts and visual and interaction evidence instead of promising automatic predictability.

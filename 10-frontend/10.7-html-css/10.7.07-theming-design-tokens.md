# Theming & Design Tokens

> Design tokens are the named decisions — colors, spacing, radii, type — that every component consumes. This file covers the primitive vs semantic token tiers, CSS custom-property theming, the `prefers-color-scheme` + manual toggle strategy, FOUC prevention with a pre-paint inline script, `data-theme` attributes vs classes, distributing tokens to Tailwind and CSS-in-JS, and WCAG contrast recaps.

## TL;DR

Design tokens are the API between design and code: named decisions (color, space, type) carried by CSS custom properties, themed by re-mapping tokens at a scope root.

## First Principles

Tokens are the named-value layer between design and code:

1. **A token is a decision with a name** (`--color-action-primary`) — semantic names mean a theme change *is a value swap*: light/dark (→ 10.7.02's custom-property inheritance), brand variants, density — the cascade propagates decisions everywhere at once.
2. **Three layers**: primitive (raw values) → semantic (intent) → component (consumption) — components consume only the semantic layer, which is what makes re-theming possible without touching components.
3. **Contrast and a11y are token-level guarantees** (→ 50.2.04): validated pairs at the primitive layer beat per-screen audits.

## Definition

A **design token** is a platform-agnostic name for a reusable style value (`--color-action-primary: #2563eb`). Tokens come in two tiers: **primitives** (raw palette/scale values: `blue-600`, `space-4`) and **semantic** (intent-referencing aliases: `color-bg-surface`, `color-text-muted`) that point at primitives. **Theming** swaps which primitives the semantics point to — light/dark, brand variants — via custom properties redefined under a theme scope.

```text
┌─────────────────────────────────────────────────────────────────────┐
│ TOKEN TIERS                                                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ PRIMITIVES (never used directly by components)                      │
│   --blue-600: #2563eb   --gray-950: #0a0a0a   --space-4: 1rem       │
│        ▲                                    ▲                       │
│        │ alias                              │ alias                 │
│ SEMANTICS (components consume only these)                           │
│   [data-theme="light"] {                                            │
│     --color-bg-page: white;                                         │
│     --color-bg-surface: var(--gray-50);                             │
│     --color-text-body: var(--gray-950);                             │
│     --color-action-primary: var(--blue-600);                        │
│   }                                                                 │
│   [data-theme="dark"] {                                             │
│     --color-bg-page: var(--gray-950);                               │
│     ...same semantic names, new values...                           │
│   }                                                                 │
│                                                                     │
│ COMPONENTS: background: var(--color-bg-surface);  ← intent only     │
└─────────────────────────────────────────────────────────────────────┘
```

## Why It Matters

- **One rename, everywhere** — rebranding means editing token files, not grepping hex codes
- **Dark mode is expected** in modern products; it falls out almost free from semantic tokens
- **Cross-platform consistency** — the same token JSON feeds web, iOS, Android, Figma
- **Interview signal** — "how would you implement dark mode without a flash of wrong theme?" is a senior-level question about FOUC and SSR

## How It Works

### 1. Primitive vs semantic tiers

| Tier | Example | Changes when | Consumed by |
| --------- | ----------------------- | ------------------------ | ------------------- |
| Primitive | `--violet-500: #8b5cf6` | rarely (palette refresh) | semantic layer only |
| Semantic | `--color-border-subtle` | per theme/brand | all components |

The discipline rule: if a component stylesheet ever references `--violet-500`, the tier system is broken. Components speak *intent* (`--color-action-primary`); themes decide what fulfills that intent.

### 2. Theme switching mechanics

Three viable scopes:

| Approach | Markup | Notes |
| ------------------------------------ | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `data-theme` attribute (recommended) | `<html data-theme="dark">` | attribute selectors `[data-theme='dark']`; extensible to arbitrary themes (`contrast-high`, brand B) without class-name collisions |
| Class on root | `<html class="dark">` | Tailwind's built-in `dark:` convention targets this; fine for exactly two themes |
| Media query only | none | zero-JS but user cannot override — never ship alone |

Prefer `data-theme` + media query as the default source:

```css
/* default = light */
:root, [data-theme="light"] {
  color-scheme: light;
  --color-bg-page: #ffffff;
  --color-text-body: #171717;
}

[data-theme="dark"] {
  color-scheme: dark;
  --color-bg-page: #0a0a0a;
  --color-text-body: #ededed;
}

/* honor OS preference only while the user has not chosen explicitly */
@media (prefers-color-scheme: dark) {
  :root:not([data-theme]) {
    color-scheme: dark;
    --color-bg-page: #0a0a0a;
    --color-text-body: #ededed;
  }
}
```

`color-scheme` also flips native UI: scrollbars, form controls, and the canvas behind `<html>`.

### 3. The three-way toggle strategy

Persist one of `light | dark | system` and resolve before paint:

```typescript
type ThemeChoice = 'light' | 'dark' | 'system';

function resolveTheme(choice: ThemeChoice): 'light' | 'dark' {
  if (choice !== 'system') return choice;
  return window.matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';
}

export function applyTheme(choice: ThemeChoice) {
  const resolved = resolveTheme(choice);
  document.documentElement.dataset.theme = resolved;
}
```

While on `system`, subscribe to changes so flipping the OS theme live-updates:

```typescript
const mq = window.matchMedia('(prefers-color-scheme: dark)');
mq.addEventListener('change', () => {
  if (localStorage.getItem('theme') === 'system') applyTheme('system');
});
```

### 4. FOUC prevention: inline script before paint

Stylesheets are render-blocking but scripts placed in `<head>` run before first paint — use a tiny blocking snippet that sets the attribute before the body renders:

```html
<head>
  <script>
    // Must be inline and blocking: runs before first paint.
    (function () {
      try {
        var c = localStorage.getItem('theme') || 'system';
        var d = c === 'system'
          ? matchMedia('(prefers-color-scheme: dark)').matches
          : c === 'dark';
        document.documentElement.dataset.theme = d ? 'dark' : 'light';
      } catch (e) {}
    })();
  </script>
  <!-- then your stylesheets -->
</head>
```

Without this, SSR HTML ships `data-theme="light"` by default, first paint flashes white for dark-mode users, then React hydrates and corrects — the classic FOUC. In Next.js App Router, put the snippet in the root layout's `<head>` via a plain `<script dangerouslySetInnerHTML>`.

### 5. Distributing tokens to Tailwind / CSS-in-JS

Single source of truth: a JSON/YAML token file compiled by a build step (Style Dictionary is the standard tool):

```json
{
  "color": {
    "action": {
      "primary": { "value": "{color.violet.600}" }
    }
  }
}
```

Output 1 — CSS custom properties consumed by everything:

```css
:root { --color-action-primary: #7c3aed; }
```

Output 2 — Tailwind config reading those variables:

```javascript
// tailwind.config.js
module.exports = {
  theme: {
    extend: {
      colors: { action: { primary: 'var(--color-action-primary)' } },
    },
  },
};
// <button class="bg-action-primary"> works in BOTH themes automatically
```

Output 3 — typed constants for CSS-in-JS consumers:

```typescript
export const tokens = {
  colorActionPrimary: 'var(--color-action-primary)',
} as const;

const Button = styled.button`
  background: ${tokens.colorActionPrimary}; /* theme-aware at runtime */
`;
```

Because every output references the *custom property* rather than the raw hex, theme switching stays instant with zero JS re-render — no `ThemeProvider` propagation needed even in styled-components codebases.

## Code Examples

### 1. Complete toggle button (React)

```tsx
'use client';

import { useEffect, useState } from 'react';

const ORDER = ['system', 'light', 'dark'] as const;
type Choice = (typeof ORDER)[number];

export function ThemeToggle() {
  const [choice, setChoice] = useState<Choice>('system');

  useEffect(() => {
    setChoice((localStorage.getItem('theme') as Choice) || 'system');
  }, []);

  const cycle = () => {
    const next = ORDER[(ORDER.indexOf(choice) + 1) % ORDER.length];
    setChoice(next);
    localStorage.setItem('theme', next);
    applyTheme(next);
  };

  return (
    <button onClick={cycle} aria-label={`Theme: ${choice}`}>
      {choice === 'system' ? 'System' : choice === 'light' ? 'Light' : 'Dark'}
    </button>
  );
}
```

### 2. Next.js App Router wiring

```tsx
// app/layout.tsx
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en" suppressHydrationWarning>
      <head>
        <script
          dangerouslySetInnerHTML={{
            __html: `(function(){try{var c=localStorage.getItem("theme")||"system";var d=c==="system"?matchMedia("(prefers-color-scheme: dark)").matches:c==="dark";document.documentElement.dataset.theme=d?"dark":"light";}catch(e){}})();`,
          }}
        />
      </head>
      <body>{children}</body>
    </html>
  );
}
```

`suppressHydrationWarning` silences the attribute mismatch the pre-paint script introduces — intentional and localized.

### 3. Contrast-safe token pairs

```css
:root {
  --text-on-action: #ffffff;
}
[data-theme="light"] {
  --color-action-primary: #7c3aed; /* contrast vs white text: 5.9:1 — AA pass */
}
[data-theme="dark"] {
  --color-action-primary: #8b5cf6; /* lighter step keeps ≥4.5:1 on dark bg */
}
```

Verify pairs, not colors in isolation: a primitive can pass in one theme and fail in another. Compute ratios in CI (e.g., style-dictionary plugin or a small script over token JSON).

### 4. View-transition theme swap (progressive enhancement)

```typescript
function setTheme(next: 'light' | 'dark') {
  if (!document.startViewTransition) {
    document.documentElement.dataset.theme = next;
    return;
  }
  document.startViewTransition(() => {
    document.documentElement.dataset.theme = next;
  });
}
```

One API call cross-fades the entire theme change where supported; unsupported browsers just switch instantly.

## Real-World Use Cases

- **Multi-tenant theming** — per-clinic brand tokens swapped at `:root` scope; one component library, N themes (Docita's white-label story).
- **Dark mode done right** — semantic tokens (`--surface`, `--text`) remapped under `[data-theme="dark"]`; components never reference raw colors.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Components referencing primitives (`var(--gray-800)`) | Only semantic tokens in component styles |
| Dark mode via media query alone | Add manual override stored in localStorage |
| FOUC: theme applied during hydration | Inline pre-paint script in `<head>` |
| Forgetting `color-scheme` property | Set per theme or native controls stay wrong-colored |
| New hardcoded hex sneaks into a review | Stylelint `declaration-property-value-disallowed-list` for raw values outside token files |
| Token names encode appearance (`--blue-btn-bg`) | Name by role/intent (`--color-action-primary`) so themes can remap freely |

## Best Practices

1. **Two tiers minimum**: primitives for palettes, semantics for intent — enforce with lint rules
2. **Default to `data-theme` on `<html>`**, resolved pre-paint from `localStorage` + `prefers-color-scheme`
3. **Store the user's choice** (`system` included) so "follow OS" survives reloads
4. **Set `color-scheme`** alongside colors for native widget correctness
5. **Compile one token source** (JSON → CSS vars + Tailwind config + TS constants) in CI
6. **Check contrast per theme pair in CI**, targeting 4.5:1 body text and 3:1 large text/UI borders (WCAG 1.4.3 / 1.4.11)
7. **Respect `forced-colors: active`** — let forced-colors mode strip decorative theming instead of fighting it

## Performance Considerations

- Custom-property theme swaps repaint without JS re-render — cheaper than state-driven styled-components themes for large trees
- Keep the pre-paint script under ~1 kB and synchronous; anything heavier delays first paint for everyone to save a flash for some users
- Avoid transitioning every property globally on theme change; transition `background-color`/`color` selectively or use one view transition

## Summary

- Tokens have two tiers: primitives hold values, semantics hold intent; components touch only semantics
- Theme scope lives on `<html data-theme="...">`; the media query fills the default until the user chooses
- A blocking inline head-script resolves the theme before first paint — the only reliable FOUC fix with SSR
- One token source compiles to CSS variables, Tailwind config, and typed JS constants; everything references variables so switches are instant
- Contrast is verified per theme pair against WCAG AA, ideally automated in CI

# Theming & Design Tokens

> A theme switch should change every relevant surface without losing contrast or flashing the wrong colors. Trace one user choice through shared design values into a rendered component.

## Definition

**Design tokens** are names for design values that should be reused. **Primitive tokens** name raw choices, such as palette colors or spacing sizes. **Semantic tokens** name a purpose, such as a surface background or action text. **Component tokens** can name choices specific to a component. A theme changes the values used for these purposes within the relevant part of the application.

> **Textbook Definition:** A design token is a named design value or reference used to express a reusable visual decision. Semantic tokens bind values to purpose, allowing themes to replace underlying choices without changing the component's intent.

## First Principles

If a button refers directly to a particular blue, a brand change requires finding every place that blue was used for an action rather than an unrelated purpose. If it refers to `action-background`, the theme can change that role's value once. Tokens help communicate intent; the resulting foreground/background combinations still need verification in their actual states.

## Follow one theme value into a component

```css
:root {
  color-scheme: light;
  --page-bg: #fff;
  --page-text: #171717;
}
:root[data-theme="dark"] {
  color-scheme: dark;
  --page-bg: #0a0a0a;
  --page-text: #ededed;
}
@media (prefers-color-scheme: dark) {
  :root:not([data-theme]) {
    color-scheme: dark;
    --page-bg: #0a0a0a;
    --page-text: #ededed;
  }
}
body { background: var(--page-bg); color: var(--page-text); }
```

With no explicit attribute, the media query follows the system. With `data-theme="light"`, the dark media rule no longer matches; with `dark`, the explicit dark values apply. `color-scheme` communicates compatible native UI styling; custom properties supply application colors. Setting the attribute changes those values through the cascade, without requiring React to recalculate every component.

```text
user choice/system preference → effective theme → semantic values → component styles
```

A component can legitimately use a primitive for a palette preview or a tightly controlled fixed role. Semantic consumption is a useful default, not proof that any primitive reference breaks the system. Tokens need not have exactly two mandatory tiers.

## Persist choice separately from effective appearance

A choice of `system` is different from the effective `light` or `dark` appearance. Keep the choice so a later OS change can update the effective theme. Validate stored data and tolerate storage failures.

```javascript
function installTheme() {
  const media = matchMedia('(prefers-color-scheme: dark)');
  const valid = value => ['light', 'dark', 'system'].includes(value) ? value : 'system';
  const read = () => {
    try { return valid(localStorage.getItem('theme')); }
    catch { return 'system'; }
  };
  let choice = read();
  const apply = () => {
    document.documentElement.dataset.theme = choice === 'system'
      ? (media.matches ? 'dark' : 'light') : choice;
  };
  const onSystemChange = () => { if (choice === 'system') apply(); };
  const onStorage = event => {
    if (event.key === 'theme' || event.key === null) {
      choice = read();
      apply();
    }
  };
  media.addEventListener('change', onSystemChange);
  window.addEventListener('storage', onStorage);
  apply();
  return {
    getChoice: () => choice,
    setChoice(value) {
      choice = valid(value);
      try { localStorage.setItem('theme', choice); } catch {}
      apply();
    },
    dispose() {
      media.removeEventListener('change', onSystemChange);
      window.removeEventListener('storage', onStorage);
    }
  };
}
```

One application owner calls `installTheme`, connects accessible controls to `setChoice` and disposes the listeners when that owner ends. A choice still applies locally if persistence fails. Cross-tab changes update the effective theme; a visible selector also needs its own state/subscription synchronization, which this small controller does not supply.

## Prevent a flash using the delivery model

CSS system preference works before client hydration without an explicit override. A server-readable cookie can let SSR emit an appropriate initial theme. A small validated pre-paint script can resolve a local-storage override before content paints, subject to script ordering and the site's CSP nonce/hash policy. These are alternative mechanisms; an inline script is not the only reliable solution.

Keep first-render UI text and controls consistent with the server output. If a deliberate pre-paint script changes only the root attribute, a localized hydration warning exception may be justified, but suppressing warnings does not fix unrelated content mismatches. A theme preference must not be interpolated into executable code as arbitrary user data.

## Share decisions without duplicating sources

A token source can generate CSS, typed constants and native-platform values. Use a documented token schema and transformation pipeline, validate references/cycles and account for platform units/color capabilities. Generated outputs should derive from one authoritative source; CSS custom properties are a web mechanism rather than the entire cross-platform token standard.

Tailwind v4 can consume semantic variables through CSS `@theme inline`; the prior JavaScript `theme.extend` approach is version-specific. CSS-in-JS components can also reference custom properties without a provider update for each color swap. Browser style/paint work still occurs, and component state may rerender for the control itself.

## Verify pairs, states and user overrides

Check text contrast against its actual background in every theme and interaction state. WCAG AA text contrast is generally 4.5:1, or 3:1 for qualifying large text; relevant non-text UI/graphical contrast has its own 3:1 rules and exceptions. A decorative border does not universally require 3:1.

Token-pair checks catch shared mistakes but do not prove full accessibility: opacity, overlays, images, font size, focus, content and forced-colors behavior can change the result. Respect reduced motion for animated theme swaps, and keep an immediate visible fallback. Manual overrides are useful where required; a deliberately system-only experience can also be valid.

## Summary

Trace choice → effective theme → semantic value → component. Preserve `system` as a choice, validate persistence, plan first paint and hydration, and test actual pairs/states. Tokens communicate shared intent while the rendered interaction supplies the final evidence.

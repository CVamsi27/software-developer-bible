# Browser Storage

> **Everything is cache; nothing here is source of truth.** The browser gives you five or six places to keep data on someone else's machine — cookies, `localStorage`, `sessionStorage`, IndexedDB, the Cache API, and the new origin-private file system. They differ in size, lifetime, whether they block the main thread, and crucially *who else can read them*. Choosing wrong is how teams ship XSS-readable session tokens, 5 MB quota failures, and 40 ms frame drops from a synchronous write.

## TL;DR

- **HTTP is stateless, so some client-side state is unavoidable** — but the client is hostile territory, so treat every store as a cache you can lose at any time, never as a database of record.
- **The decisive question is threat model, not size.** Only `HttpOnly` cookies are unreadable by JavaScript; everything else (`localStorage`, IndexedDB, Cache API) is fully readable by any XSS payload on your origin.
- **`localStorage` is synchronous and blocks the main thread.** Reading a large JSON blob on every render or keystroke is a measurable performance bug, not a style preference.
- **`sessionStorage` dies with the tab; `localStorage` and IndexedDB persist per origin** until the user clears data or the browser evicts under storage pressure.
- **IndexedDB is the only real client-side database** — async, transactional, indexed, structured-clone values, and quotas measured in hundreds of MB. It is also the most verbose API, so wrap it.
- **Cookies are the only store the server can read on every request** — which is exactly why they carry session identity, and exactly why they need `HttpOnly` + `Secure` + `SameSite`.
- **Quota is per origin and eviction is real:** `navigator.storage.estimate()` tells you the budget, `persist()` asks to be exempt from eviction, and Safari's script-writable storage can be cleared after ~7 days of non-use.
- **In interviews: never say "store the JWT in localStorage" without naming the XSS consequence.** The expected answer is a threat-model comparison, not a preference.

## First Principles

Four constraints determine every storage decision. Each one eliminates a convenient option:

1. **HTTP is stateless, so the client must carry state.** Either every request re-authenticates, or something on the client persists identity, preference, and in-progress work. Given that sessions and drafts must survive navigation, *some* client-side store is structurally required — the only question is which.
2. **The client is not your machine.** A shared laptop, a compromised browser extension, and above all an XSS payload all live inside your origin with your users' privileges. Therefore no client store can be trusted as authoritative: it must be *reconstructible* from the server (cache, preference, draft), never the only copy of anything that matters. This is why "the client says it's paid" is not a design.
3. **Browsers are storage landlords, not tenants.** They must bound total disk usage across millions of origins, so **eviction is inevitable** — under pressure, or on Safari's inactivity policy. Any store's contents can vanish between visits; designs must tolerate that (and may *ask* for exemption via `persist()` rather than assume it).
4. **JavaScript runs on one thread per origin, so synchronous storage APIs block rendering.** A store with a synchronous read/write surface (`localStorage`, `document.cookie`) couples your frame budget to disk speed — which is why the platform's larger, more capable stores (IndexedDB, Cache API) are deliberately asynchronous.
5. **Because each API exposes a different capability profile — size, lifetime, sync/async, string vs structured data — the choice is forced by the workload**, not by familiarity. The decision procedure is: *who may read this? → how big is it? → can it block the main thread? → what lifetime must it have?*

Corollary worth stating in interviews: **storage choice is a security and lifecycle decision. Size and convenience are consequences of that decision, not the basis for it.**

## Definition

**Browser storage** is the set of origin-scoped, client-side persistence APIs available to web pages and workers. They share one boundary — the **origin** (`scheme://host:port`) — and differ in capacity, lifetime, synchronicity, value types, and whether the server can read them.

| Store | Capacity | Lifetime | API | Server reads it? | JS-readable |
| -------------------- | --------------------- | --------------------- | ----------------------- | ---------------------- | ----------------- |
| **Cookies** | ~4 KB each | `Max-Age`/`Expires` | Sync | **Yes, every request** | Unless `HttpOnly` |
| **`localStorage`** | ~5–10 MB | Until cleared/evicted | **Sync** | No | Yes |
| **`sessionStorage`** | ~5–10 MB | Tab lifetime | **Sync** | No | Yes |
| **IndexedDB** | Quota-scale (100s MB) | Until cleared/evicted | Async | No | Yes |
| **Cache API** | Quota-scale | Until cleared/evicted | Async | No | Yes |
| **OPFS** (newer) | Quota-scale | Until cleared/evicted | Async (sync in workers) | No | Yes |
| In-memory (JS) | RAM | Page lifetime | Sync | No | Yes |

```text
┌─────────────────────────── ORIGIN BOUNDARY ───────────────────────────┐
│  https://app.example.com            (scheme + host + port = the key)  │
│                                                                       │
│   SERVER-VISIBLE            JS-VISIBLE ONLY                           │
│   ┌──────────────┐          ┌──────────────────────────────────────┐  │
│   │  Cookies     │          │  localStorage   sessionStorage       │  │
│   │  (sent on    │          │  IndexedDB      Cache API            │  │
│   │   every req) │          │  OPFS                                │  │
│   └──────────────┘          └──────────────────────────────────────┘  │
│          ▲                              ▲                             │
│          │ HttpOnly hides from JS ──────┘  XSS reads ALL of this      │
└───────────────────────────────────────────────────────────────────────┘
```

## Why It Matters

1. **It is a security boundary.** Where session material lives decides whether one XSS payload equals full account takeover. This is the highest-stakes frontend decision most teams make.
2. **It is a performance boundary.** `localStorage` is synchronous; a careless read in a render path produces jank you cannot fix with memoization.
3. **It is a reliability boundary.** Quota exhaustion throws, eviction deletes silently, and Safari drops script-writable storage — all of which must degrade rather than crash.
4. **It is asked constantly in interviews** — "cookies vs localStorage", "where do you keep a JWT", "how do you make an offline draft survive a refresh". The answer is a threat-model story, and interviewers can tell immediately who has one.
5. **It underpins PWA capability.** Offline support, background sync, and instant shell loads are all Cache API plus IndexedDB ([PWA](10.7.05-pwa.md)).

## How It Works

### The origin is the key — and partitioning is the privacy fix

Every store is scoped to an origin; `https://app.example.com` and `http://app.example.com` are *different* origins, as are different ports. Two consequences:

- **Same-origin iframes share storage** with the parent (and can therefore read its `localStorage`) — a reason to be wary of embedding untrusted same-origin content.
- **Third-party storage is partitioned** by modern browsers: a widget embedded cross-site gets a separate, first-party-scoped store, so it can no longer use storage as a cross-site tracking join key. If your embedded widget "lost its state", partitioning is usually why.

### Cookies: the only server-readable store

A cookie is a small name/value pair attached automatically to matching requests. That automatic attachment is its superpower and its weakness:

```text
Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600

  HttpOnly   → invisible to document.cookie, so XSS cannot exfiltrate it
  Secure     → HTTPS only (never send identity over plaintext)
  SameSite   → Lax/Strict/None — the primary CSRF control
  Max-Age    → lifetime; omit both it and Expires for a session cookie
```

**Why session identity belongs here and not in `localStorage`:** the server can read a cookie directly, so no JavaScript needs access to the token — and `HttpOnly` makes the token unreadable *even to an attacker with XSS*. The trade-off is CSRF exposure (mitigated by `SameSite` and CSRF tokens) and the automatic per-request cost. `__Host-`/`__Secure-` prefixes pin scope and `Secure`; `domain`-wide cookies widen the blast radius to every subdomain.

### `localStorage` / `sessionStorage`: convenient, synchronous, small

Both expose the same string-only, synchronous `getItem`/`setItem` interface (with a `Storage` object facade). The differences that matter:

- **Lifetime:** `sessionStorage` is per tab (and survives reload, not duplicate-tab), so it is not a place to put anything a second tab needs.
- **Synchronous + main-thread:** the browser serializes reads to a single-threaded store. A cold read hits disk; a large `JSON.parse` costs CPU. Both occur inside your frame budget.
- **String-only:** objects require `JSON.stringify`/`parse`, doubling memory and inviting `[object Object]` bugs.
- **Shared by same-origin tabs**, which is precisely why it is the fallback transport for cross-tab signalling — see [Cross-Tab Communication](../10.1-javascript/06-modern-and-interview/10.1.6.04-cross-tab-communication.md).
- **Throws rather than fails quietly:** quota exceeded in private mode or under storage pressure surfaces as a `QuotaExceededError` (and `setItem` in Safari private mode historically threw outright).

### IndexedDB: the actual client-side database

IndexedDB is asynchronous, transactional, and typed via *structured clone* (so you can store `Blob`, `ArrayBuffer`, `Date`, `Map` — anything cloneable):

```text
open(db) ─► upgrade (onupgradeneeded) ─► object stores + indexes
   │
   └─ transaction(scope, mode) ─► request ─► onsuccess / onerror
        • mode: readonly | readwrite (transactions auto-commit when idle)
        • cursors for iteration; indexes for lookups by non-key fields
```

The design consequences:

- **Versioned schema:** you declare a version and perform migrations in `onupgradeneeded`. There is no SQL — plan migrations as explicitly as you would server-side.
- **Blocking upgrade pitfall:** if another tab holds an old connection, the upgrade *waits*. Handle `onblocked` and close connections on `versionchange`, or users strand on a frozen state.
- **Async means no jank:** because the API is promise/event-based, it is the correct store for anything large or written on a hot path.

### Cache API and OPFS

- **Cache API** stores `Request`→`Response` pairs, driven almost entirely by service workers. It is a *HTTP-shaped* cache (great for precaching an app shell, stale-while-revalidate, offline fallbacks) rather than a general key/value store.
- **OPFS (Origin Private File System)** exposes a private, origin-scoped filesystem with high-performance synchronous access *inside workers* — the modern answer for large binary workloads (image editing, WASM data files) that would be awkward in IndexedDB.

### Quota, eviction, and asking to persist

Storage is a shared, bounded resource. Two APIs make it observable rather than mysterious:

```text
navigator.storage.estimate()
  → { usage, quota }   ← the origin's budget; quota varies by device and pressure

navigator.storage.persist()
  → true/false         ← "don't evict me without user action" (best-effort grant,
                          influenced by install/PWA status and engagement)
```

**Eviction** generally follows least-recently-used across origins under disk pressure, and Safari applies an inactivity policy that can clear script-writable storage after roughly seven days without interaction. Practical reading: *design drafts and caches to be re-obtainable, and call `persist()` only when losing data would genuinely harm the user.*

### The threat model, in one table

| Store | Readable by XSS? | Read by network/server | CSRF exposure | Right for |
| --------------------- | ---------------- | ---------------------- | ---------------- | ------------------------------------------ |
| `HttpOnly` cookie | **No** | Yes | Yes (→ SameSite) | Session identity, auth tokens |
| Non-`HttpOnly` cookie | Yes | Yes | Yes | Small server-visible flags/prefs |
| `localStorage` | Yes | No | No | Non-sensitive prefs, feature flags, drafts |
| `sessionStorage` | Yes | No | No | Per-tab ephemeral state (wizard steps) |
| IndexedDB | Yes | No | No | Large structured data, offline datasets |
| Cache API | Yes | No | No | HTTP responses, app shell, offline assets |

The asymmetric row is the whole lesson: **an auth token in `localStorage` is one XSS away from exfiltration; the same token in an `HttpOnly` cookie is not reachable by the attacker's JavaScript at all.**

## Code Examples

A defensive `localStorage` wrapper — namespaced, quota-aware, and never fatal:

```typescript
const NS = "app:v1:";

function read<T>(key: string, fallback: T): T {
  try {
    const raw = localStorage.getItem(NS + key);
    return raw === null ? fallback : (JSON.parse(raw) as T);
  } catch {
    // Malformed JSON, or storage disabled/blocked by policy.
    return fallback;
  }
}

function write(key: string, value: unknown): boolean {
  try {
    localStorage.setItem(NS + key, JSON.stringify(value));
    return true;
  } catch (err) {
    // QuotaExceededError (or Safari private-mode rejection): degrade, don't crash.
    if (err instanceof DOMException && err.name === "QuotaExceededError") {
      console.warn("storage full — dropping cached value for", key);
      return false;
    }
    throw err;
  }
}

function remove(key: string): void {
  localStorage.removeItem(NS + key);
}
```

Measuring the quota before you rely on it — and asking to persist:

```typescript
async function storageBudget() {
  if (!navigator.storage?.estimate) return null;
  const { usage = 0, quota = 0 } = await navigator.storage.estimate();
  return {
    usedMB: +(usage / 1_048_576).toFixed(2),
    quotaMB: +(quota / 1_048_576).toFixed(2),
    percent: quota ? +((usage / quota) * 100).toFixed(2) : 0,
  };
}

// Best-effort: grant depends on engagement/install state. Never assume true.
const persisted = await navigator.storage.persist?.();
console.log({ budget: await storageBudget(), persisted });
```

A minimal promisified IndexedDB helper — the wrapper almost every codebase ends up writing:

```typescript
function openDB(name: string, version: number, migrate: (db: IDBDatabase) => void) {
  return new Promise<IDBDatabase>((resolve, reject) => {
    const req = indexedDB.open(name, version);
    req.onupgradeneeded = () => migrate(req.result);
    req.onsuccess = () => {
      const db = req.result;
      // Another tab wants to upgrade: stop holding an old connection hostage.
      db.onversionchange = () => db.close();
      resolve(db);
    };
    req.onerror = () => reject(req.error);
    // Fires when another tab is blocking our upgrade — surface it, don't hang.
    req.onblocked = () => console.warn("IndexedDB upgrade blocked by another tab");
  });
}

async function put(db: IDBDatabase, store: string, value: unknown) {
  return new Promise<void>((resolve, reject) => {
    const tx = db.transaction(store, "readwrite");
    tx.objectStore(store).put(value);
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
  });
}
```

Storing structured data that `localStorage` cannot hold, and reading it back:

```typescript
async function cacheDocuments(db: IDBDatabase, docs: Array<{ id: string; blob: Blob }>) {
  const tx = db.transaction("docs", "readwrite");
  const store = tx.objectStore("docs");
  for (const d of docs) {
    store.put(d); // Blobs clone natively — no base64 bloat, unlike localStorage
  }
  await new Promise((r) => (tx.oncomplete = r));
}
```

Server-side cookie flags — the security half of the storage decision:

```typescript
// Express: session cookie that XSS cannot read and cross-site requests cannot send.
res.cookie("sid", sessionId, {
  httpOnly: true,      // invisible to document.cookie → immune to XSS exfiltration
  secure: true,        // HTTPS only
  sameSite: "lax",     // blocks cross-site POST CSRF; "strict" breaks inbound links
  path: "/",
  maxAge: 60 * 60 * 1000,
});
// Read on the server without any client-side token handling:
const sid = req.cookies.sid;
```

Precaching an app shell with the Cache API — HTTP-shaped storage, not a key/value store:

```typescript
// In a service worker
const SHELL = "shell-v3";
const ASSETS = ["/", "/app.js", "/styles.css", "/offline.html"];

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(SHELL).then((c) => c.addAll(ASSETS)).then(() => self.skipWaiting()),
  );
});

self.addEventListener("fetch", (event) => {
  const req = event.request;
  if (req.method !== "GET" || new URL(req.url).origin !== self.location.origin) return;

  event.respondWith(
    caches.match(req).then(
      (hit) =>
        hit ??
        fetch(req).catch(() => caches.match("/offline.html")), // offline fallback
    ),
  );
});
```

## Real-World Use Cases

### 1. Where the session token goes

The canonical decision. A same-site web app uses an `HttpOnly` + `Secure` + `SameSite=Lax` cookie so JavaScript never touches the token; a native/third-party client uses an `Authorization: Bearer` header because it has no cookie jar. Storing that same token in `localStorage` "because it's simpler" converts any XSS from a defacement into account takeover ([JWT](../../20-backend/20.5-security/01-auth/20.5.1.05-jwt.md), [Sessions & Cookies](../../20-backend/20.5-security/01-auth/20.5.1.04-sessions-cookies.md)).

### 2. Draft auto-save that survives a refresh

Long forms write debounced snapshots — small ones to `localStorage`, large attachments to IndexedDB — and clear them on successful submit. The lifecycle rules (when to restore, when to discard, how to avoid resurrecting a submitted draft) matter more than the store ([Autosave & Draft Recovery](../10.5-form-handling/10.5.06-autosave-draft-recovery.md)).

### 3. Preference persistence without a theme flash

The theme choice must be readable *before first paint*, which rules out anything async. This is the one place `localStorage` is genuinely the right tool: a tiny synchronous read in a blocking inline script, with the cookie alternative used when the server must also render the right theme ([Theming & Design Tokens](10.7.07-theming-design-tokens.md)).

### 4. Offline-first app shell and data

A PWA precaches its shell in the Cache API and its structured data in IndexedDB, then reconciles on reconnect. The hard parts are cache versioning (stale shells serving old bundles) and conflict resolution on sync — not the storage calls ([PWA](10.7.05-pwa.md)).

### 5. Feature flags and kill switches without a round trip

Non-sensitive rollout state can be cached client-side so a flag read costs nothing on the hot path — while the *authoritative* decision stays server-side, because a client-side flag is advisory only.

### 6. Caching API responses in a SPA

A request-shaped cache (Cache API or a service worker) can serve repeat GETs from disk. Beware the interaction with auth: cached responses for a logged-out user are a data-leak class, so scope caches per user or clear them on logout.

## Common Mistakes

| Mistake | Consequence | Fix |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Storing the session token in `localStorage` | Any XSS exfiltrates the token; no server-side mitigation | `HttpOnly` + `Secure` + `SameSite` cookie (or in-memory + silent refresh) |
| Using `localStorage` for anything large or hot | Synchronous main-thread work → jank; `QuotaExceededError` at ~5 MB | IndexedDB for volume; keep only tiny values in `localStorage` |
| Assuming storage persists | Eviction, private mode, and Safari's inactivity policy erase it silently | Treat as cache; `navigator.storage.persist()` only for genuine need |
| Forgetting to handle `QuotaExceededError` | Feature crashes in private mode or under pressure | Wrap writes; degrade gracefully |
| Putting per-tab state in `localStorage` | Two tabs clobber each other's wizard state | `sessionStorage` for tab-scoped, or namespace by tab id |
| Ignoring the `versionchange`/`onblocked` upgrade path | IndexedDB upgrades hang for users with another tab open | Close connections on `versionchange`; handle `onblocked` |
| Trusting client-side values in decisions | "Is admin", "is paid" forged in devtools | Authorize server-side; the client sends *requests*, not authority |
| Caching authenticated responses globally | Logged-out users served a prior user's data | Scope caches per user/session; purge on logout |
| `JSON.parse` failures left unguarded | One corrupted value breaks the whole feature | Parse inside `try`/`catch` with a fallback |
| Treating a cookie `domain` broadly | Every subdomain (including ones you don't control) shares the cookie | Prefer host-only `__Host-` cookies; avoid `domain` unless required |
| Assuming third-party iframe storage is shared | Partitioning silently isolates it | Plan for partitioned, first-party-scoped storage |

## Best Practices

1. **Decide by threat model first.** Ask "who may read this?" before "how big is it?" — `HttpOnly` cookie for identity, JS-visible storage for everything non-sensitive.
2. **Never make the client the record of truth.** Anything that must not be lost lives server-side; the client holds a replica.
3. **Wrap every store behind a small module.** Namespacing, JSON handling, quota errors, and migrations belong in one place, not sprinkled through components.
4. **Namespace keys with a version** (`app:v1:`) so a schema change can migrate or discard predictably.
5. **Keep synchronous storage off hot paths.** Read once at startup (or in a blocking pre-paint script when the value affects first render) and hold it in memory.
6. **Choose IndexedDB for volume and structure, `localStorage` for tiny sync-required values, Cache API for HTTP responses.**
7. **Handle all three failure modes explicitly:** quota exceeded, malformed/corrupt value, and blocked/absent storage (private mode, disabled cookies, partitioned third-party context).
8. **Clear client state on logout** — including caches and drafts — so a shared device cannot leak the previous session.
9. **Ask for `persist()` only when the user would be harmed by loss**, and be prepared to be refused.

## Performance Considerations

- **`localStorage` cost scales with the *whole origin's* data, not just your key.** Implementations may load the origin's store into memory on first access; a single large value penalises every subsequent read. Keep total `localStorage` usage small.
- **Serialize once, cache in memory.** Repeated `JSON.parse` of the same value on every render is pure waste — parse at startup, keep a typed reference, re-serialize only on write.
- **Debounce and batch writes.** Rapid writes (keystroke-level auto-save) should coalesce; a write per keystroke × synchronous disk access is how you lose frames.
- **IndexedDB transactions are the batching mechanism.** One `readwrite` transaction over many operations is dramatically cheaper than many small transactions; transactions auto-commit when idle, so don't interleave awaits that let them close early.
- **Serve reads from memory, not from disk.** For offline datasets, hydrate from IndexedDB into an in-memory index (or a `Map`) and query that; treat IndexedDB as durable backing store.
- **Mind cache size for memory-constrained devices.** A multi-hundred-megabyte cache is fine on a laptop and harmful on a low-end phone — the quota is per-origin, but the device is shared.
- **Measure with the Performance panel:** long tasks attributed to `localStorage`/storage reads are trivially visible, and they are usually easy to remove.

## Summary

Browser storage is not one thing but a family of origin-scoped stores whose differences decide security, reliability, and frame rate. HTTP's statelessness forces client-side state to exist, the client's untrustworthiness forces it to be replicable rather than authoritative, browsers' need to bound disk forces eviction, and single-threaded JavaScript forces the asynchronous APIs for anything large. Cookies are the only store the server can read on every request — which is why identity lives there, protected by `HttpOnly` and `SameSite` — while `localStorage`/`sessionStorage` handle small synchronous values, IndexedDB is the real structured database, and the Cache API stores HTTP responses for offline work. Quota is finite and eviction is real, so every design must tolerate loss, surface `QuotaExceededError` as a degraded path, and never treat client state as the system of record. Get the threat model right first, and the size and lifetime questions answer themselves.

# Browser Storage

> Choose storage by visibility, lifetime and failure behavior, then trace one write through recovery.

## Definition

Browser storage APIs keep data on the user's device, but differ in what they store, how long it lasts and who can read it. Web Storage and IndexedDB are generally scoped to an **origin**, the combination of scheme, host and port. Browser privacy rules can further partition that storage. Cookies follow separate domain, path, Secure and SameSite rules; they are not isolated by port.

> **Textbook Definition:** Browser storage persists client-side data through APIs with distinct data models, isolation rules and eviction policies. Storage availability and durability are conditional, and client storage is not an authoritative trust boundary.

## First Principles

A draft must survive reload, a session credential must accompany authorized requests and an offline asset must reproduce a response. These are different workloads. Choose by who can access the data, what persistence is needed and what a failure would mean. Browser storage can hold authoritative local user work in an offline/local-first application; it cannot prove server-side authorization or a payment outcome.

## Follow a small preference write

```javascript
function savePreference(key, value) {
  try {
    const serialized = JSON.stringify(value);
    if (serialized === undefined) return false;
    localStorage.setItem(`app:v1:${key}`, serialized);
    return true;
  } catch {
    return false; // serialization, quota or policy failure
  }
}

function readPreference(key, fallback) {
  try {
    const value = localStorage.getItem(`app:v1:${key}`);
    return value === null ? fallback : JSON.parse(value);
  } catch {
    return fallback;
  }
}
```

Trace: serialize → synchronous storage write → report success or failure. Reading distinguishes a missing key from malformed/unavailable storage, then returns parsed data. This generic parsing helper does not validate shape: a theme caller must still accept only `light`, `dark` or `system`. Never label a critical draft "saved" after the write returned false.

```text
user intent → serialize/validate → store → confirmed persistence outcome
reload      → read/parse         → validate/migrate → restore or explain failure
```

## Select the capability the workload needs

| Store | Values and access | Lifetime/visibility boundary |
| ---------------- | ------------------------------------------------- | ----------------------------------------------------------------------------- |
| Cookie | Small name/value, sent on matching requests | Cookie scope/expiry/credential rules; `HttpOnly` blocks direct script reading |
| `localStorage` | String key/value; synchronous window API | Shared by compatible same-origin contexts, subject to privacy/policy |
| `sessionStorage` | String key/value; synchronous window API | Origin plus page session/tab; reload survives |
| IndexedDB | Structured-clone values, indexes and transactions | Larger asynchronous client database, with schema/connection lifecycle |
| Cache API | Request/Response entries | Application-controlled HTTP-shaped cache, usable outside workers too |
| OPFS | Origin-private files | File workloads; synchronous access handles are restricted to suitable workers |
| Memory | Live runtime values | Ends with that runtime; no reload persistence |

A new tab with an opener can initially receive a copy of session storage; later changes are independent. Duplicate/restore behavior should not be described as a universal clean empty session. Third-party storage may be partitioned, blocked or accessed through permission mechanisms depending on browser/context.

## Structured storage has transaction and upgrade rules

IndexedDB accepts supported structured-clone values such as Dates, Maps, buffers and Blobs, but not arbitrary functions or DOM nodes. Its asynchronous I/O avoids synchronous Web Storage calls; cloning and application processing can still consume main-thread time.

Choose a database version and perform schema migration in the upgrade transaction. Close old connections when they receive `versionchange`, and surface `blocked` when another context prevents upgrading. Observe transaction completion before reporting a group of writes as saved; a request can succeed and its transaction later abort.

Transactions auto-commit when they have no pending work and become inactive across unsuitable scheduling boundaries. Do not start unrelated network work mid-transaction and assume it will still accept new requests afterward. Group related changes atomically, then perform external effects through a separate lifecycle.

A Cache API entry does not automatically expire according to normal HTTP caching headers. The application defines freshness, keys, version cleanup and response handling. An offline HTML fallback should apply to navigations rather than every failed script/API request, and `respondWith` must produce a Response. See the [PWA chapter](10.7.05-pwa.md) for the canonical cache implementation.

## Credentials and local data have different trust rules

An `HttpOnly` cookie protects against direct JavaScript reading of that cookie; XSS can still perform authenticated actions, alter the UI and read other accessible data. Secure cookies, appropriate same-site policy, CSRF defenses and server authorization address additional boundaries. `SameSite=Lax` generally omits cookies on cross-site unsafe requests while allowing eligible top-level safe navigation; it is not complete CSRF protection.

Cookie prefixes have specific requirements: `__Secure-` requires Secure in a secure setting; `__Host-` also requires Path `/` and no Domain attribute. Broad domain scope includes compatible subdomains. A native or third-party client may also support cookies; an Authorization header is an API/client choice, not proof it has no cookie jar.

JavaScript-readable credentials can be exfiltrated by same-origin script execution. Sensitive drafts and cached responses can also leak, so data classification matters beyond credentials. Namespace by account/tenant where needed, restore only into the correct identity and clear or retain identity-specific data under a deliberate logout/retention policy. Client feature flags are advisory; enforce protected behavior at the server.

## Quota is an observable limitation

Web Storage has small fixed limits in common implementations; IndexedDB, Cache API and OPFS share browser-managed storage quotas. `navigator.storage.estimate()` gives estimates, not a reservation for the next write. `persist()` can request protection from ordinary storage-pressure eviction where supported, but may be refused and cannot prevent user clearing or device loss.

Best-effort data may be evicted; eviction is not inevitable on every regular visit. Private browsing, privacy policy and embedded contexts can change lifetime/availability. Catch quota/policy failures, bound retained data and offer export or synchronization for important locally authored work. A server replica helps recovery when the application supports it, but is not a universal requirement for every local-first tool.

## Keep cost and recovery visible

Read small preferences once when practical, and update an in-memory view with explicit cross-tab synchronization. Debounce draft writes with a maximum-loss-window policy; debounce alone can postpone persistence indefinitely. Large data may be better queried through IndexedDB indexes rather than hydrating the entire database into RAM.

Measure serialization, cloning, transaction work and retained memory. Synchronous APIs execute on the calling window's thread; there is not one JavaScript thread for an entire origin. Quoted universal cold-read times or speed multipliers hide implementation and device differences.

## Summary

Trace what is stored, who can read it and when persistence is confirmed. Pick the API by data shape and lifetime, validate restored values and handle quota/upgrade failures. Protect server authority while giving important local work a deliberate backup, export or synchronization story.

# HTML/CSS Interview Questions


## Definition

This set probes the rendering fundamentals senior frontend engineers are assumed to have: how layout, paint, and composite interact; when a styling choice costs a reflow; why z-index "doesn't work"; and how a design system stays consistent without a wall of `!important`. Each question includes the follow-up that distinguishes lived understanding from reference lookup.

## First Principles

This set probes rendering physics and cascade reasoning (→ 10.7.02, → 10.7.03):

1. **The senior tells are causal**: "that reflows because width invalidates layout" — not property recall. Specificity debugging, stacking-context explanations, and layout-thrashing fixes are the differentiators.
2. **Architecture questions** (→ 10.7.06) test whether you've felt cascade pain at scale — the answer shapes (BEM/Modules/Tailwind trade-offs) matter more than the pick.

### Q1. Explain margin collapsing — when does it happen, when doesn't it, and why does the browser do it at all?

**Model answer:** Adjacent block margins can collapse. For all-positive margins the result is the largest; mixed signs combine the largest positive and most negative, and all-negative margins use the most negative. Parent/child and empty-block cases have additional conditions. Flex/grid item margins do not collapse. Identify the actual formatting context before choosing a gap-based layout or a deliberate separation.

### Q2. z-index: 9999 isn't working. Diagnose.

**Model answer:** Find the element’s stacking context and compare its root with competing roots. A high child z-index cannot escape a lower ancestor context. Inspect computed positioning, z-index, transforms, opacity, isolation and containment. A portal can change ancestry; the top layer used by suitable dialog/popover mechanisms is another boundary. A compositor layer is not identical to a stacking context, and adding isolation while probing changes the layout’s stacking behavior.

### Q3. When do you choose flexbox, when grid, and when both?

**Model answer:** Use Flexbox for main-axis distribution and Grid when related rows/columns should align. They compose naturally: a grid page shell can contain flex toolbars. Check automatic minimum sizes, wrapping and implicit tracks against actual content instead of deciding from a fixed element count.

### Q4. A card hover animation drops frames on mid-range phones. Reflow, repaint, composite — which did you trigger and how do you fix it?

**Model answer:** Capture a slow frame and identify layout, paint/raster or compositing work. Geometry changes may invalidate layout; color often changes paint; eligible transforms/opacity can reuse rasterized content. Promotion is conditional, so verify the actual trace and memory rather than promising a GPU-only path. Containment can reduce relevant propagation but is not automatic isolation of every size effect.

### Q5. Beyond alt text — what does 'accessibility as structure' mean in day-to-day HTML?

**Model answer:** Use meaningful elements, associated accessible names, logical headings and visible focus. Test the whole interaction with keyboard and representative assistive technology. Modal focus containment/return and route focus behavior depend on the interaction design. Native controls reduce reimplementation; ARIA can add necessary semantics but does not supply missing keyboard behavior. Automated checks find a subset of issues.

### Q6. How do you keep CSS sane at the scale of dozens of engineers?

**Model answer:** Choose selector ownership, explicit precedence and a shared semantic value vocabulary. Document layer order including important/unlayered exceptions, constrain accidental nesting/specificity and test responsive/interaction/theme states. Modules, utilities and runtime styles can each work. A linter cannot prove all selectors are used or all accessibility states are correct.

### Q7. Walk me through how the cascade actually resolves two competing rules.

**Model answer:** Filter relevant declarations, then compare origin/importance and layer precedence. Compare specificity only within the same competing precedence, then scoping proximity and source order. Normal layer precedence favors later/unlayered rules; important layer ordering reverses. Importance does not increase specificity. Transitions, animations and inline declarations have further defined precedence. :where contributes zero; :is/:not/:has use their argument-list specificity.

### Q8. What do `contain` and `content-visibility` actually buy, and what do they cost?

**Model answer:** Containment limits specified layout/style/paint interactions but can change sizing, containing blocks and clipping. content-visibility:auto lets the browser skip eligible offscreen rendering work while preserving relevant content semantics; intrinsic sizes help reserve space. Verify scrolling, anchors, focus and accessibility under real content. Measure benefit rather than treating every subtree as isolated.

### Q9. How would you build a responsive card component without a single media query?

**Model answer:** A fluid grid can use repeat(auto-fit, minmax(min(18rem, 100%), 1fr)) and fluid typography can use clamp. Container queries adapt a card to its available container rather than viewport width. A base layout must remain useful where the queried feature is unavailable; test overflowing content and zoom as well as a few viewport widths.

### Q10. rem, em, px — how do you actually allocate them, and what does the choice have to do with accessibility?

**Model answer:** rem relates to root font size; em usually relates to the element’s font size, with property-specific behavior such as font-size resolving against its parent. CSS px are reference pixels and still participate in browser zoom. ch relates to the advance of the zero glyph, not a universal actual character count. Pick units by scaling intent and test text resizing/reflow; no unit alone guarantees accessibility.

### Q11. What promotes an element to its own compositor layer, and why is 'just add will-change' not the answer?

**Model answer:** Layer allocation is an engine decision influenced by effects, animations and resource constraints. A stacking context does not prove a separate composited layer. Transform/opacity animation is a useful candidate; will-change is a hint with memory and stacking consequences. Verify the rendered workload and remove unnecessary hints instead of listing guaranteed promoters.

### Q12. `height: 100%` isn't working. Why, and what are the modern fixes?

**Model answer:** A percentage height commonly needs a definite containing-block size, with layout-specific rules and exceptions. Inspect the containing block and flex/grid sizing before extending a height chain. dvh follows a dynamic viewport, svh uses its small size and lvh its large size; choose whether browser-chrome changes should resize the UI. aspect-ratio can reserve proportion, but overriding dimensions can alter the result.

### Q13. A style will not apply and DevTools shows it struck through. Walk me through your diagnosis.

**Model answer:** Inspect whether the declaration lost precedence, is invalid or is inactive in the current layout context. Check origin/importance/layer, specificity, scope proximity, source order and shorthand resets. Changing layer order affects other rules too, so verify the smallest intended override. An intentional important rule can be valid; unexplained escalation usually hides the mechanism.

### Q14. Where do pseudo-elements bite you in accessibility?

**Model answer:** Generated content’s exposure and interaction vary by content/browser/assistive technology. Keep essential text and controls in semantic DOM nodes rather than relying on pseudo-element content alone. Decorative images can have empty alt text; hide decorative icons appropriately without hiding focusable controls. Test announcement and selection where generated content matters.

### Q15. CSS Modules, Tailwind, CSS-in-JS, vanilla CSS — how do you actually choose for a team?

**Model answer:** Choose by ownership, framework rendering constraints, runtime/build costs and team maintenance needs. Runtime CSS-in-JS remains a valid option with an assessed integration contract; it is not obsolete because a year changed. Modules, utilities and plain layered CSS each have tradeoffs. Include the migration path and actual emitted output in the decision.

### Q16. How do you find and prevent dead CSS in a large codebase?

**Model answer:** Coverage reports show what executed under captured pages/states, not proof that all remaining CSS is dead. Inventory dynamic variants, routes, themes and responsive/interaction states before deleting rules. Utilities need detectable source names or supported safelisting. Couple component deletion with style ownership and representative regression checks.

### Q17. `position: sticky` works on the demo and fails in the app. Diagnose.

**Model answer:** Find the relevant scroll container, sticky inset and containing-block constraints. An overflow ancestor can become the relevant scrolling mechanism even when it does not visibly scroll. Check available travel range and stretched item sizing. Fixed positioning has different flow/containing-block rules, so substituting it does not preserve sticky semantics.

### Q18. What does good form validation styling look like beyond red borders?

**Model answer:** Communicate errors through text and an associated description, with aria-invalid reflecting the validated state. Keep visible focus and a deliberate announcement/focus policy on submission. :user-invalid can delay native invalid styling, subject to browser interaction rules. :focus-visible is a modality heuristic, not “keyboard only.” Server validation and accessible error recovery still matter.

### Q19. How do you ship dark mode that isn't just an inverted stylesheet?

**Model answer:** Keep user choice light/dark/system separate from effective appearance. Resolve semantic variables, set the effective color-scheme, validate persisted values and react to OS/cross-tab changes under system mode. Plan CSS/SSR/pre-paint behavior to avoid inappropriate initial colors, then check images, focus and contrast in actual states. Tokens reduce repeated decisions without proving accessibility.

### Q20. What breaks in an RTL layout, and what is the modern fix?

**Model answer:** Use logical spacing/alignment properties where the design should follow writing direction. Verify source/read order, input content and scripts under the actual direction and language. Mirror genuinely directional glyphs selectively; logos and some media controls should remain unchanged. Test mixed-direction text rather than assuming setting dir mirrors every visual detail correctly.

### Q21. How do you load web fonts without wrecking LCP and CLS?

**Model answer:** Choose font-display behavior, preload only genuinely critical matching resources and use appropriate fallback metrics. Subsets and variable fonts can reduce transfer in some workloads; one variable file is not always smaller than the needed static subset. Measure LCP/CLS and text readability before claiming benefit. A measured CLS improvement is not evidence of a particular revenue effect.

### Q22. Design the image loading strategy for a media-heavy page.

**Model answer:** Reserve appropriate image space, provide supported responsive candidates with accurate sizes, and prioritize the actual LCP resource. Avoid lazy loading an image needed immediately. Format, quality and CDN transformations should match supported browsers and content. Width/height help avoid shifts but CSS and changing layout can still cause them.

### Q23. Compare display:none, visibility:hidden, opacity:0, content-visibility:hidden, and the hidden attribute — and when focus gets dangerous.

**Model answer:** display:none removes layout boxes and ordinarily accessibility exposure. visibility:hidden keeps layout but hides the element, with descendant visibility rules. opacity:0 can leave focus and accessibility exposure. content-visibility:hidden skips subtree rendering and hides skipped descendants from accessibility; auto has different relevance behavior. hidden can be overridden by CSS and hidden=until-found has separate behavior. inert disables subtree interaction/accessibility without being a visual hide rule.

### Q24. What is your strategy for browser support in 2026, concretely?

**Model answer:** Define support from the actual user/device requirements and current feature evidence. Baseline is a useful interoperability signal rather than the complete product matrix. Keep a working base experience, use feature detection for enhancement and test engines/devices representative of the supported floor. Do not infer that every newly common feature is automatically safe for every embedded browser.

### Q25. Production reports a CSS bug only in Safari. Walk me through your method.

**Model answer:** Reproduce on the relevant engine, OS and device; reduce to a small case, inspect computed rules/geometry and verify the documented mechanism. A supports query detects supported syntax/features, not whether an implementation is free of a particular bug. Use a scoped workaround when necessary, test the retained base behavior and record a minimal upstream issue when evidence supports an engine defect.

## Common Mistakes

- Reciting property syntax without the layout, paint and interaction mechanism.
- Answering a11y with ARIA attributes instead of semantic HTML.
- Treating CSS architecture as "BEM vs Tailwind" tribalism instead of cascade discipline and token design.

## Best Practices

- Name the browser's *reason* (typographic flow, compositing, accessibility tree derivation) before the fix — that's what makes the answer transferable.
- Tie every mechanism to a debugging story or a lint/CI enforcement.

## Summary

Explain the mechanism, trace the interaction and state what evidence would confirm the diagnosis. Use the source chapters to revisit weak answers, then test the same idea against a changed scenario.

### Q1. Explain margin collapsing — when does it happen, when doesn't it, and why does the browser do it at all?

**Model answer:** "Adjacent vertical margins of block-level siblings collapse to the larger of the two; parent and first/last child collapse through each other unless padding, border, or a block formatting context separates them. It does *not* happen in flex or grid containers — flex items never collapse margins — which is the practical reason switching a layout to flexbox 'fixes' mysterious spacing. The why: collapsing comes from typographic document flow — paragraphs in prose were the original use case, where consecutive `<p>` spacing should be max(margin-bottom, margin-top), not a sum. My rule in production: don't fight it with zero-margins-and-padding hacks; use gap in flex/grid layouts, where collapsing doesn't apply and spacing is a container concern."

### Q2. z-index: 9999 isn't working. Diagnose.

**Model answer:** "z-index only competes within its stacking context, so the modal at 9999 is losing inside a context whose root sits below the other element's context root. Stacking contexts are created by far more than z-index: `position` with a z-index, `opacity < 1`, `transform`, `filter`, `will-change`, `isolation: isolate`, even `contain: paint`. The diagnosis is to walk up the DOM from the misbehaving element, find the ancestor that creates a context, and fix the ordering at that level — or restructure so the modal mounts at the document root (portals exist for exactly this). The senior habit: reach for `isolation: isolate` to fence a subtree's stacking deliberately, instead of ever-larger magic numbers."

**Probe:** "How do you find which ancestor creates the context?" → "DevTools' 3D/layers view, or bisect: set `isolation: isolate` on ancestors from the target upward — the level where the rendering changes is the context boundary."

### Q3. When do you choose flexbox, when grid, and when both?

**Model answer:** "I choose by dimension of control. Grid when alignment must hold in *two* axes and the structure is the design — page shells, card walls, form rows with label/column pairing; `grid-template-areas` makes that layout readable as a picture. Flex when it's one-axis distribution of content whose size I don't control — toolbars, button rows, tag lists; content-out, not container-in. Production layouts are usually both: grid for the macro structure, flex inside cells for content flow. The tell of experience is naming the failure modes: flexbox's `space-between` orphans on wrap (use grid `auto-fit`/`minmax` for responsive card counts without media queries), and grid's implicit-track surprises when content exceeds the defined columns."

### Q4. A card hover animation drops frames on mid-range phones. Reflow, repaint, composite — which did you trigger and how do you fix it?

**Model answer:** "If the animation changes `width`, `top`, or `margin`, every frame re-runs layout — the expensive one — then paint, then composite. If it changes `background` or `color`, layout is skipped but paint runs per frame. Only `transform` and `opacity` are compositor-friendly: the browser promotes the element to its own layer and the GPU moves/fades existing pixels. So the fix is to animate `transform: scale/translate` instead of size/position, verify promotion in DevTools' Layers panel (and that it didn't blow up memory by promoting too many layers), and add `will-change` sparingly — it's a hint that costs memory, not a decoration. `contain: layout paint` on complex subtrees bounds the damage the other way: it tells the browser a subtree's internal changes can't leak layout outside it."

### Q5. Beyond alt text — what does 'accessibility as structure' mean in day-to-day HTML?

**Model answer:** "The accessibility tree is derived from the DOM, so semantics are the API: a `<button>` ships focus, Enter/Space activation, and role for free — a `<div onClick>` has to rebuild all of it and never quite does. Landmarks (`nav`, `main`, `aside`) give screen-reader users the page's map; a real heading hierarchy is their table of contents; labels bound to inputs via `for`/`id` are non-negotiable. Focus management is where senior depth shows: modals must trap and restore focus, route changes must move focus to the new content, and skip links must actually be first in tab order. My enforcement bias: ARIA is a patch layer, not a foundation — 'no ARIA is better than bad ARIA' — and the linter (jsx-a11y or equivalent) plus an axe pass in E2E keep the floor honest. The Docita angle: 25+ clinics mean keyboard-heavy data-entry users, so forms were labeled, grouped with fieldset/legend, and tested with keyboard-only runs."

### Q6. How do you keep CSS sane at the scale of dozens of engineers?

**Model answer:** "Layers of discipline, in order. Design tokens as custom properties are the vocabulary — spacing, color, type ramp as semantic names (`--color-surface`, not `--gray-2`), so theming (including `prefers-color-scheme` and manual toggles) is a variable swap, not a rewrite. Cascade control is the architecture: either utility-primitive composition (Tailwind-style, consistency by restricted vocabulary) or component-scoped styles (CSS Modules) — both work; the failure mode they share is ad-hoc global selectors leaking in. Specificity rules: single-class selectors, `!important` reserved for utility overrides only, and `@layer` to make the cascade order explicit rather than emergent. And dead-style hygiene is a CI concern — unused-token and unused-class checks — because CSS only grows unless someone is paid to prune."

### Q7. Walk me through how the cascade actually resolves two competing rules.

**Model answer:** "Order of operations: origin and importance first — user-agent styles lose to author styles, but an `!important` author style loses to an `!important` user-agent one, which is why important-flipped precedence surprises people. Then cascade layers: unlayered styles beat layered ones, and within layers, later layers win — so `@layer reset, base, components, utilities` gives you an explicit architecture where utilities override components without specificity tricks. Then specificity, then source order. The senior tell: saying `!important` 'raises specificity' — it does not; it moves the rule to a higher-precedence origin. And `:where()` contributes zero specificity — it is the tool for writing resettable defaults, where `:is()` takes the specificity of its most specific argument."

**Probe:** "Where do layers beat specificity?" → "A single-class selector in a later layer beats a triple-nested selector in an earlier one — layer order is checked before specificity, which is exactly why you can delete `!important` wars by moving utilities into the last layer."

### Q8. What do `contain` and `content-visibility` actually buy, and what do they cost?

**Model answer:** "`contain: layout paint` on a subtree tells the browser its internal changes cannot leak layout or paint outside it — so a mutation re-renders the subtree alone instead of invalidating up the tree. `content-visibility: auto` goes further: offscreen subtrees skip layout, paint, and often style entirely, which is why long feeds drop initial render cost dramatically — but you must pair it with `contain-intrinsic-size` or the scrollbar jumps as sections render in. The costs are subtle: find-in-page and anchor navigation into skipped content need the browser to force-render, and without intrinsic sizes you trade CLS for paint time. My rule: `contain` on known-isolated widgets, `content-visibility` on below-the-fold uniform sections, measured — not sprayed."

### Q9. How would you build a responsive card component without a single media query?

**Model answer:** "Two tools. Fluid sizing: `clamp()` with viewport-relative preferred values — `font-size: clamp(1rem, 0.5rem + 2vw, 1.5rem)` scales smoothly instead of stepping at breakpoints. And container queries: `container-type: inline-size` on the wrapper, then `@container (min-width: 30rem)` inside — the card adapts to the space its *parent gives it*, not the viewport, which is what design systems actually need: the same card renders one-column in a sidebar and three-up in a grid with no coordination between page and component. Media queries stay for page-level decisions — nav collapsing, layout-mode changes — because those genuinely are viewport concerns."

**Probe:** "What is the fallback story?" → "Feature-query the container rules behind `@supports (container-type: inline-size)` and let the base layout be the narrow variant — old browsers get the mobile layout, which is always a valid rendering of the component."

### Q10. rem, em, px — how do you actually allocate them, and what does the choice have to do with accessibility?

**Model answer:** "rem is the default for type and spacing because it scales with the user's root font-size preference — the whole point is that a user who sets 24px base text gets proportionally larger everything, which media-query and spacing in px would silently deny them. em is for component-internal scaling — padding that should grow with the element's own font-size, like a button. px survives on borders, shadows, and hairlines where physical alignment matters. The trap worth naming: the `62.5%` root hack (making 1rem = 10px) trades accessibility familiarity for arithmetic convenience — it re-couples rem to px in the author's head, and every utility written against it breaks if a team ever removes the hack. `ch` for measure (max line length ~60–75ch) is the sleeper answer — it is the only unit that tracks the actual typeface."

### Q11. What promotes an element to its own compositor layer, and why is 'just add will-change' not the answer?

**Model answer:** "Transform, opacity, filter, `will-change`, and fixed positioning are the common promoters — the browser gives the element its own layer so the compositor can move or fade existing pixels without re-painting. The cost is real: each layer is a texture in GPU memory, and promoting hundreds of elements (a classic over-eager `will-change: transform` on list items) can blow memory budgets and force evictions that are *worse* than the jank. The disciplined version: animate transform/opacity so promotion happens naturally, verify in DevTools' Layers panel that only the intended elements promoted, and treat `will-change` as a targeted fix for a measured promotion-timing problem — applied at animation start, removed after — not as a permanent decoration."

### Q12. `height: 100%` isn't working. Why, and what are the modern fixes?

**Model answer:** "Percentage heights resolve against the containing block's *actual* height — a parent with only `height: auto` has no defined height, so the child's 100% computes to auto. Fixing the chain with `html, body { height: 100% }` works but is brittle. Modern answers: flex/grid parents stretch children by default, so the layout system often dissolves the problem; `min-height: 100dvh` for app shells; and the mobile-specific answer — `100vh` on iOS Safari includes the area behind the collapsing URL bar, so dynamic viewport units (`dvh` for UI that tracks the bar, `svh` for stable minimums) are the 2026-correct spelling. Same family: `aspect-ratio: 16/9` to reserve media space without padding-top hacks — the CLS killer."

### Q13. A style will not apply and DevTools shows it struck through. Walk me through your diagnosis.

**Model answer:** "Struck-through in the Styles panel means the rule *lost*, not that it is missing — so it is a cascade question with a decision tree. Same specificity? Later source order wins, and shorthand-over-longhand (`background` resetting `background-color`) is the classic silent killer. Different specificity? Recount it — `:is()` taking the max of its arguments has bitten every team once. In a layer? Unlayered beats layered regardless of specificity. `!important` on the winner? Check importance-flipped origins before escalating. The fix discipline: resolve by ordering — move the rule to a later layer, reduce the winner's specificity with `:where()`, or explicitly re-order layers — and never respond with `!important`, which converts a cascade bug into a cascade *debt*."

### Q14. Where do pseudo-elements bite you in accessibility?

**Model answer:** "`::before`/`::after` content is inserted into the accessibility tree — screen readers may announce it, but find-in-page, translation, copy-paste, and selection all miss it. So generated content is fine for decorative markers (quotation marks, bullets, icons) and wrong for meaningful text: an 'required' or 'new' badge built with pseudo-content is a real-world screen-reader and copy bug. The rules I enforce: pseudo-elements for decoration only; meaningful text in the DOM; `alt=""` for genuinely decorative images so they vanish from the a11y tree; and remembering `::marker` and `::selection` exist before hand-rolling list bullets or highlight styling with extra elements."

### Q15. CSS Modules, Tailwind, CSS-in-JS, vanilla CSS — how do you actually choose for a team?

**Model answer:** "By the failure mode you can afford. Tailwind buys consistency by restricting vocabulary — great for fast-moving product teams, costly where the markup noise hurts (design-system components with complex variants). CSS Modules buys scoping with zero runtime and keeps CSS skills relevant — the default for component libraries. CSS-in-JS buys co-location and dynamic theming, and costs runtime extraction (which is why the ecosystem moved to compile-time variants like vanilla-extract/Panda — the runtime version is a 2020 answer). Plain CSS with `@layer` is newly viable at scale and the honest choice for content sites. The senior shape of the answer: name the team and product constraints, pick per context, and — the real tell — describe the *migration* path out, because every one of these choices gets revisited in three years."

### Q16. How do you find and prevent dead CSS in a large codebase?

**Model answer:** "Detection first: Chrome DevTools' Coverage tab for a spot check, then a build-step class inventory — extract every class the CSS could emit, instrument or crawl the real app, and diff. The trap is dynamic composition: `cls={variants[size]}` and template strings mean grep cannot see usage, so the inventory has to come from the same source of truth the styles use (Tailwind's content scanning works for exactly this reason). Prevention is governance: stylelint rules flagging unknown tokens, unused-custom-property checks in CI, and a review norm that deleting a component deletes its styles in the same PR. CSS only grows unless someone is paid to prune — so the pruning has to be a pipeline, not a quarterly heroic audit."

### Q17. `position: sticky` works on the demo and fails in the app. Diagnose.

**Model answer:** "The two classic killers, in order. An ancestor with `overflow: hidden/auto/scroll` becomes the sticky element's scroll container — the element sticks within *that*, which on a non-scrolling ancestor means it never appears to stick. Find it by walking ancestors in DevTools; the fix is removing the overflow or making the intended scroller explicit. Second: the sticky element's *parent* defines its range — it can only stick while the parent is in view, so a wrapper with less height than the sticky content ends the effect early. And name the difference: sticky is in-flow and reserves space with a scroll-range constraint; fixed is viewport-anchored and out of flow — switching to fixed 'to make it work' is usually the wrong model."

### Q18. What does good form validation styling look like beyond red borders?

**Model answer:** "The states discipline: `:focus-visible` so keyboard users get rings and mouse users don't; `:user-invalid` instead of `:invalid` so a half-typed email isn't screamed at on the first keystroke — the browser only applies it after the user has interacted; `:user-valid` for the matching positive. Reset native chrome with `appearance: none` but then you own the states — focus, disabled, error — for every control you skin. Error UX: message tied to the input via `aria-describedby`, announced via `aria-live` or focus moved to the first invalid field on submit, never color alone. And the senior framing: constraint validation (`required`, `type`, `pattern`) is free progressive enhancement — do the JS validation *on top of* the platform, not instead of it."

### Q19. How do you ship dark mode that isn't just an inverted stylesheet?

**Model answer:** "Semantic tokens are the whole design: `--color-surface`, `--color-text`, `--color-border` — components reference roles, never literal colors, so dark mode is a token re-mapping under `prefers-color-scheme`, and the manual toggle is the same mapping behind a `data-theme` attribute that overrides the media query. Then the details that separate shipped from demoed: `color-scheme: light dark` (meta and CSS) so form controls, scrollbars, and UA backgrounds adapt; images and brand assets audited for dark backgrounds — an inverted screenshot is not a dark theme; contrast re-verified in *both* palettes, because a token swap can silently drop WCAG ratio; and persistent choice + system-default as the two-way default."

### Q20. What breaks in an RTL layout, and what is the modern fix?

**Model answer:** "Physical properties hard-code direction: `margin-left`, `text-align: left`, `padding-right` — in `dir="rtl"` the layout mirrors but those values don't, producing the classic broken form. The fix is logical properties as a coding standard: `margin-inline-start`, `padding-block`, `border-inline-end` — direction flows from the writing mode. Beyond spacing: directional icons (arrows, progress) must flip — `transform: scaleX(-1)` under `[dir="rtl"]` for truly directional glyphs, *not* for logos or media controls; `text-align: start` not left; and truncation re-checked — ellipsis assumptions and line-height tuned for Latin break with Arabic's ascenders/descenders or CJK's lack of word spaces, so `overflow-wrap` and measure need per-script review."

### Q21. How do you load web fonts without wrecking LCP and CLS?

**Model answer:** "Four moves, in order of impact. `font-display: swap` (or `optional` for non-critical faces) so text renders in a fallback instead of invisible. Preload only the fonts the first paint needs — `preload` on every weight is the classic self-inflicted wound that delays LCP. Kill the layout shift with fallback metric matching: `size-adjust`, `ascent-override`, `line-gap-override` tune the fallback to the web font's metrics so the swap doesn't reflow — this is what `next/font` automates, and knowing what it does under the hood is the senior answer. Subset and prefer variable fonts — one file covering the weight axis beats five static weights. And self-host: the third-party stylesheet handshake is real latency."

**Probe:** "What CLS number makes this worth the effort?" → "A font swap moving the hero heading reflows everything below it — a 0.05→0.02 CLS on a content page is measurable revenue at conversion-sensitive metrics, which is why font loading is a business question, not a fiddle."

### Q22. Design the image loading strategy for a media-heavy page.

**Model answer:** "Correctness first: `width`/`height` attributes (or `aspect-ratio`) on every image so space is reserved — CLS from images is entirely preventable and entirely common. Responsiveness: `srcset` with both width descriptors and `sizes` so the browser picks by layout slot, not device width — getting `sizes` wrong is the usual bug that makes phones download desktop images. Format: AVIF/WebP via `<picture>` with a JPEG fallback. Priority: the LCP image gets `fetchpriority="high"` and is *never* `loading="lazy"` — lazy-loading the hero is the most common self-own in Core Web Vitals work; lazy-load below the fold only. Edge-cached derivatives (the CDN stack's transform pipelines) so variants are compute-once."

### Q23. Compare display:none, visibility:hidden, opacity:0, content-visibility:hidden, and the hidden attribute — and when focus gets dangerous.

**Model answer:** "The matrix that matters: layout — none removes it, visibility and opacity keep the box; paint — visibility and opacity still cost paint/composite; accessibility tree — none, hidden, and `visibility: hidden` remove it from AT, while `opacity: 0` and offscreen-positioning *leave it exposed*: the element is invisible but focusable, which is the classic keyboard trap — focus lands on nothing the user can see. `content-visibility: hidden` hides rendering while keeping the a11y tree. `inert` is the modern big gun: an entire subtree non-interactive and invisible to AT — what you want behind a modal. So the rules: `hidden`/`display: none` for true removal; `inert` for background content under overlays; and never hide with opacity or clip-path alone."

### Q24. What is your strategy for browser support in 2026, concretely?

**Model answer:** "Baseline, not IE folklore. Define the support matrix from analytics plus the Baseline 'widely available' line — features like container queries and `:has()` crossed it, so they are *on* by default now. Write the modern syntax as the default; gate genuinely new-but-unbaseline'd features behind `@supports` with a graceful degraded path, which is progressive enhancement by construction rather than UA sniffing (fragile, lies with evergreen browsers, breaks for anyone spoofing). The testing story matches the matrix: latest Chrome/Firefox/Safari + the analytics floor, WebKit first-party for iOS Safari since that is where the real bugs live. And the senior habit: a bug that only reproduces in one engine goes to that engine's bug tracker with a reduced case — sometimes the fix is upstream."

### Q25. Production reports a CSS bug only in Safari. Walk me through your method.

**Model answer:** "Reproduce, isolate, understand, then fix behind a feature line. Reproduce on the actual engine/OS — Safari-on-iOS is a different beast than macOS Safari, and I keep a device matrix for exactly this. Reduce to a minimal case (a codepen-style repro often reveals the bug to *me* before it reveals it to anyone else). Then check the known-difference map rather than guessing: flexbox `gap` history, scroll behavior, date input rendering, `100vh` semantics, `position: fixed` with transforms — most 'Safari bugs' are documented engine differences, and caniuse plus the WebKit bug tracker is faster than trial and error. The fix ships behind `@supports` when it is genuinely a feature difference, and the reduced case goes upstream if it is a defect. The anti-pattern I coach out of: UA-conditional CSS, which converts a one-line engine difference into permanent conditional debt."

## Common Mistakes

- Reciting property syntax without the rendering cost model (Q4 is the standard senior filter).
- Answering a11y with ARIA attributes instead of semantic HTML.
- Treating CSS architecture as "BEM vs Tailwind" tribalism instead of cascade discipline and token design.

## Best Practices

- Name the browser's *reason* (typographic flow, compositing, accessibility tree derivation) before the fix — that's what makes the answer transferable.
- Tie every mechanism to a debugging story or a lint/CI enforcement.

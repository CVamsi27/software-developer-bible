# React Native & Cross-Platform

> **TL;DR:** React Native renders **real native views** driven by your JS/TS code — old-architecture JS bridge, new architecture (JSI + Fabric + TurboModules) removes it. Choose RN when a web-TS team must ship both platforms fast; choose native for deep platform/perf edges; PWA for reach-first surfaces. In interviews: know the architecture shift, the Expo decision, and the honest trade-off list.

## TL;DR

React Native trades DOM for native widgets via a JS-to-native bridge (now Fabric/TurboModules): one React codebase, real iOS/Android UIs — and the platform-divergence costs that come with it.

---

## First Principles

React Native's bet: same architecture (→ 10.3.1), different rendering host:

1. **JS drives, native renders**: the bridge (old) / JSI+fabric (new) let React describe UI while native views materialize it — the trade is a serialization boundary (old arch) or C++ bindings (new): "learn once, write anywhere" with per-platform polish.
2. **You get native *widgets*, not a webview** — which is why RN apps feel native and why web CSS/DOM APIs don't exist: the platform boundary is real, and the skill is knowing which side each library lives on.

## Definition

React Native = React programming model → native UI components per platform (UIKit/Android View equivalents). You write TSX; RN maps elements to real views and executes logic in a JS runtime (Hermes).

## How It Works

### Architecture: bridge → JSI

```text
OLD ARCHITECTURE NEW ARCHITECTURE
JS thread ⟷ async JSON bridge JS calls host objects synchronously via JSI
⟷ native (serialization tax) Fabric: sync, prioritized rendering pipeline
                                    TurboModules: lazy-loaded native modules
```

Interview one-liner: *"The bridge serialized every cross-boundary call as JSON — batched but asynchronous and lossy for high-frequency updates. JSI lets JS hold direct references to C++ host objects; Fabric/TurboModules build on that, which is why new-architecture RN closes most of the perf gap."*

### Expo vs bare React Native

| Expo (managed/workflow) | Bare RN |  |
| ----------------------- | ------------------------------------------------------------------ | ------------------------------------- |
| Start speed / DX | instant, OTA updates (EAS), config plugins | slower setup |
| Native modules | Most needs covered (expo-*); custom via dev clients/config plugins | anything |
| When | Default choice today — start Expo, eject surface only if forced | exotic BLE/background/native-UI needs |

**Answer template:** "Expo first — its module coverage now covers 90% of products, OTA updates ship fixes without store review; drop to bare/dev-client only for genuinely exotic native needs."

### Code sharing with your web monorepo

```text
packages/
├── types/ ← shared Zod schemas + API types reuse
├── data-access/ ← API clients mostly reuse (swap fetch adapter)
├── hooks/ ← pure logic hooks reuse
└── ui/ ← styled-components/tamagui-style partial (renderers differ)
apps/mobile/ ← screens/navigation (expo-router/react-navigation)
```

This is exactly your Docita monorepo shape — say "the mobile app becomes a fifth app consuming the same typed contracts."

## The Decision Matrix (memorize this)

| Factor | React Native | Native (Swift/Kotlin) | PWA |
| ------------------------------------------------ | ------------------------------- | --------------------- | ---------------- |
| Team is web/TS |  | new skills |  |
| Time to both stores | one codebase | two teams | no store |
| Deep platform APIs (widgets, health sensors, BT) | via modules |  |  |
| Animation-heavy / 60fps complex UIs | good w/ reanimated, care needed |  |  |
| Offline-first local DB | (WatermelonDB/SQLite/MMKV) |  | IndexedDB limits |
| Store distribution/review burden | yes (OTA softens) | yes | none |
| Discoverability/push/install UX | store presence |  | weaker |

**Health-domain note worth adding:** patient-facing apps often need offline resilience + push reminders + biometric auth — all achievable in RN (SQLite/MMKV, expo-notifications, LocalAuthentication); say it with those library names.

## Real-World Use Cases

| Scenario | Choice & why |
| --------------------------------------------------------------- | ------------------------------------------------------------ |
| Studio client MVP on iOS+Android in 10 weeks | RN/Expo — one team, shared TS contracts with the web product |
| Fitness app reading HealthKit/HealthConnect continuously | Native modules inside RN, or full native |
| Clinic info + booking surface for low-end devices | PWA first (your SW-caching experience applies) |
| Longevity/blood-analysis tracker (MVST's CARE case study shape) | RN shell + cloud/AI backend integrations |

## Common Mistakes

| Mistake | Fix |
| -------------------------------------------------- | ------------------------------------------------ |
| Reaching for native modules before checking expo-* | Inventory Expo coverage first |
| Porting web CSS habits blindly | Learn Yoga layout differences early |
| Keeping business logic in screens | Share domain/hooks packages; screens are shells |
| Skipping release discipline (OTA vs store) | Plan update channels + rollout strategy day one |
| Assuming web performance instincts transfer | Profile on low-end Android devices from week one |

## Performance Considerations

- Lists: `FlashList` over `FlatList`; avoid re-render storms with memoized rows.
- Animations on the UI thread (`react-native-reanimated` worklets), never across the JS boundary.
- Startup: Hermes, lazy routes, deferred hydration of heavy screens.
- Images: right-sized remote assets; avoid base64 payloads.

## Summary

RN = React model over native views; new architecture (JSI/Fabric) removed the bridge bottleneck. Expo-first strategy covers most products; share your TS domain layer from the same monorepo. Pick native for platform depth, PWA for reach — and always answer with the decision matrix, not preference.

## Cheat Sheet

```text
ARCH bridge(JSON,async) → JSI(sync)+Fabric+TurboModules
CHOOSE web-team→both-platforms fast = RN · platform-depth = native · reach = PWA
START Expo default · bare for exotic modules
SHARE types/clients/hooks packages reused; UI partially
PERF FlashList · reanimated worklets · Hermes · profile on cheap Android
MOBILE offline DB (SQLite/MMKV) · push · biometrics · OTA vs store releases
```

# React Native & Cross-Platform

A shared React screen can still jank on one device, fail to open a camera, or lose data offline. Cross-platform code shares some implementation; it does not remove the native runtime and product constraints.

```tsx
import Animated, { useSharedValue, useAnimatedStyle, withSpring } from 'react-native-reanimated';

export function AnimatedCard() {
  const scale = useSharedValue(1);
  const style = useAnimatedStyle(() => ({ transform: [{ scale: scale.value }] }));
  return <Animated.View style={[{ width: 200, height: 120 }, style]} />;
  // Animation runs on the UI thread — no per-frame JS round-trip.
}
```

## Definition

**React Native** uses React components to build iOS and Android applications from a shared codebase. JavaScript or TypeScript runs in a JavaScript engine, commonly **Hermes**. React Native renders native platform UI components rather than browser DOM nodes. The **JavaScript Interface (JSI)** connects JavaScript to native APIs and objects. Performance still depends on React rendering, native work and the calls crossing that connection.

> **Textbook Definition:** React Native renders a React component model through native host components and platform APIs rather than the browser DOM. JavaScript execution, native rendering and cross-language calls jointly determine application behavior and performance.

---

## First Principles

An app must respond to input, calculate layout and draw platform views before the next frame. Sharing React code does not remove those costs. It introduces a boundary between JavaScript and the native runtime, so explain both where work runs and how it reaches the screen.

React Native uses host components such as `View` and `Text`, not browser DOM nodes. **Yoga** calculates layout from supported style properties. Platform behavior, permissions and native dependencies remain separate integration work even when domain logic is shared.

## How It Works

### 1. From a React Update to a Native Screen

```text
input → React computes elements → Fabric builds a shadow tree
      → Yoga calculates layout → commit accepts the tree
      → mount updates native host views on the UI thread
```

A **shadow tree** is the renderer's description of the native layout, separate from the visible platform views. For example, changing a card's text may change its measured height; the committed layout then updates the displayed card. Optimizations may flatten layout-only views, so one `View` in JSX need not produce one native view.

The supporting components have different jobs:

- **Fabric** owns this native rendering pipeline. Ordinary rendering/layout commonly run on the JavaScript thread; higher-priority paths can run synchronously on the UI thread. Host-view manipulation belongs to the UI thread.
- **JSI (JavaScript Interface)** lets JavaScript interact with native objects/functions through C++ interfaces. It removes the old requirement to serialize every interaction through the asynchronous JSON bridge. Whether a particular API is synchronous depends on its contract; JSI does not move all work to a single native thread.
- **TurboModules** provide the native-module system, including lazy initialization. Startup gains depend on which modules the application uses.
- **Codegen** turns supported typed native-module/component specifications into binding code at build time. It helps keep the two sides consistent; it does not validate arbitrary network input or eliminate native bugs.

The New Architecture is the supported architecture in current React Native releases; [React Native 0.82 removed the Legacy Architecture](https://reactnative.dev/blog/2025/10/08/react-native-0.82). Check the [architecture guide](https://reactnative.dev/architecture/overview) and each native library's compatibility before upgrading. Architecture names alone do not prove that a dependency or custom native module has migrated correctly.

### 2. Decide Who Owns the Native Project

Expo and manually maintained native projects are not mutually exclusive. Expo **Prebuild** generates iOS/Android projects from configuration and config plugins; a **development build** is your own native app with development tools. Expo Go has a fixed native runtime and cannot exercise arbitrary custom native modules.

| Choice | What you own | Changed condition |
| -------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Generate native projects with Prebuild | App config, plugins and native dependencies | Manual generated-file changes need a reproducible plugin or another ownership strategy |
| Check in and maintain native projects | Xcode/Gradle project changes alongside app code | Keep Expo packages/configuration synchronized if you use them |
| Use EAS cloud builds | Source archive, profiles, credentials and build evidence | Local native builds still require the platform toolchain; cloud builds do not replace device testing |

Choose according to required SDKs, reproducibility and team ownership, rather than a fixed percentage of apps.

### 3. Animate a Logical Target, Not a Moving Value

Reanimated runs supported animation work on the UI thread through **worklets**, functions prepared for that runtime. This can avoid waiting for each JavaScript frame; expensive UI-thread work can still miss the frame budget.

```typescript
import { useState } from 'react';
import { Button, View } from 'react-native';
import Animated, {
  ReduceMotion, useSharedValue, useAnimatedStyle, withSpring,
} from 'react-native-reanimated';

export function AnimatedCard() {
  const [expanded, setExpanded] = useState(false);
  const scale = useSharedValue(1);
  const style = useAnimatedStyle(() => ({ transform: [{ scale: scale.value }] }));

  function toggle() {
    const next = !expanded;
    setExpanded(next);
    scale.value = withSpring(next ? 1.1 : 1, { reduceMotion: ReduceMotion.System });
  }

  return (
    <View>
      <Animated.View style={[{ width: 200, height: 120, backgroundColor: '#2563eb' }, style]} />
      <Button title={expanded ? 'Collapse card' : 'Expand card'} onPress={toggle} />
    </View>
  );
}
```

First tap selects `1.1`. A second tap during the spring selects `1`, even though the current value may be `1.04`. Comparing the moving value with `1` would confuse progress with intent. Configure the library's required native/build integration and test reduced motion on each platform.

### 4. Persist a Public Catalog with Asynchronous SQLite Calls

Local storage survives a network outage; it does not synchronize itself with the server. This example caches non-sensitive catalog records. Await opening, schema setup and writes, and surface failures to the caller.

```typescript
import * as SQLite from 'expo-sqlite';

type Product = { id: string; name: string; updatedAt: number };

export async function openCatalog() {
  const db = await SQLite.openDatabaseAsync('catalog.db');
  try {
    await db.execAsync(`
      PRAGMA journal_mode = WAL;
      CREATE TABLE IF NOT EXISTS products (
        id TEXT PRIMARY KEY NOT NULL,
        name TEXT NOT NULL,
        updated_at INTEGER NOT NULL
      );
    `);
  } catch (error) {
    await db.closeAsync();
    throw error;
  }
  return {
    async save(product: Product) {
      await db.runAsync(
        `INSERT INTO products (id, name, updated_at) VALUES (?, ?, ?)
         ON CONFLICT(id) DO UPDATE SET
           name = excluded.name, updated_at = excluded.updated_at`,
        product.id, product.name, product.updatedAt,
      );
    },
    async list() {
      return db.getAllAsync<Product>(
        'SELECT id, name, updated_at AS updatedAt FROM products ORDER BY updated_at DESC',
      );
    },
    close: () => db.closeAsync(),
  };
}
```

The owner opens one catalog, awaits writes and closes it after outstanding work finishes. A failed write must not display a saved state. `ON CONFLICT ... DO UPDATE` updates the existing row; `INSERT OR REPLACE` can delete and reinsert it, affecting references and triggers. Multiple related writes need a transaction. Account-specific offline data additionally needs retention, logout cleanup and conflict-resolution rules; this public cache is not that design.

### 5. Choose the Platform by Capability and Ownership

| Requirement | React Native | Native Swift/Kotlin | PWA |
| ------------------------------ | -------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------- |
| Shared web/mobile domain logic | Strong TypeScript reuse; UI/platform adapters remain | Shared contracts, usually separate client implementations | Web code runs in the browser |
| Native SDK integration | Available through compatible modules or custom bindings | Direct platform SDK integration | Limited to available browser APIs |
| Animation and large lists | Profile JS and native work on target devices | Profile native layout/drawing on target devices | Profile browser layout/paint/compositing |
| Offline persistence | Native databases; explicit sync/retention design | Native databases; explicit sync/retention design | Browser storage, quotas and eviction rules |
| Release path | Native build/review plus eligible compatible OTA updates | Native build/review; remote configuration where appropriate | Web deployment; installed service-worker lifecycle still matters |
| Background execution/push | Platform permissions and lifecycle restrictions apply | Platform restrictions still apply | Browser/platform support and lifecycle vary |

A requirement such as sustained background location can decide feasibility before code-sharing benefits matter. None of these choices guarantees smooth animation, durable offline data or unrestricted background work.

### 6. Keep Shared Code Inside Its Real Boundary

| Workload or requirement | Engineering decision |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shared validation, API contracts and domain rules | Put them in platform-neutral packages; keep UI and platform adapters at the edges. |
| Long lists | Start with a virtualized list such as `FlatList`; consider a compatible recycling library only after profiling allocation, item rendering and memory. |
| Sensitive credentials | Use platform-backed secure storage with explicit backup, access and logout-cleanup behavior; ordinary preferences storage is not a credential vault. |
| CPU-heavy computation | Bound or chunk synchronous work, or use a supported off-thread mechanism. `async` does not move CPU work off the JavaScript thread. |
| Animation | A UI-thread worklet avoids waiting on JavaScript for each frame, but expensive UI-thread work can still miss the frame budget. |
| Offline records | Specify retention, sync, conflict resolution and logout behavior; local persistence is not synchronization. |

Hermes and bytecode can reduce startup parsing work, but release startup, memory and peak throughput still depend on the app and devices. Measure release builds rather than assuming the engine or a library name guarantees performance.

---

## Summary

React Native shares React code while retaining native rendering, platform integration and release constraints. Trace updates through renderer, layout, commit and mounting; then profile the thread doing the work. Choose native-project ownership deliberately, and treat animation, sensitive storage and offline persistence as explicit platform contracts.

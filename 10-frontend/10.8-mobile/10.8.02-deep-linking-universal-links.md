# Deep Linking, Universal Links & App Links

When someone taps an appointment link, they should reach the appointment whether the app is installed, closed, or already running. The link still needs validation and authorization after the operating system chooses an app.

```typescript
// excerpt: verify the parsed inbound link matches an allowed domain and pattern before routing
const match = /^\/appointments\/([a-zA-Z0-9_-]{1,64})$/.exec(parsedUrl.pathname);
if (!match) navigate('NotFound');
```

## Definition

**Deep linking** routes a user to specific in-app content from outside the app using one of three mechanisms. **Custom URI schemes** (`myapp://product/42`) have no verified domain ownership and fail unreliably when the app is absent.

**Universal Links (iOS)** and **App Links (Android)** use regular `https://` URLs verified against domain-hosted manifests (`apple-app-site-association` on iOS, `assetlinks.json` on Android), keeping the HTTPS page as the fallback.

> **Textbook Definition:** Deep linking maps an externally supplied URI to application navigation state. Verified HTTPS associations establish a domain-to-app relationship; routing and authorization must still validate the requested destination and resource.

## First Principles

A link arrives before the app necessarily has a router, restored session, or loaded data. Treat it as an untrusted navigation request: identify an allowed destination, wait for application readiness, then authorize access to the resource. Domain verification chooses an eligible handler; it does not authenticate the person tapping the link.

```text
HTTPS link → OS association/user choice → app receives URL
           → validate destination → restore session/navigation
           → authorize resource → show screen or safe fallback
no eligible installed handler → deliberately implemented web page
```

The URL must remain useful outside the app. Opening a store does not automatically preserve it through installation.

## 1. Mechanism Comparison

| Mechanism | Custom URI scheme | Universal Links (iOS) | App Links (Android) |
| ---------------------- | ------------------------------- | --------------------------------------------------------- | --------------------------------------------------------- |
| Format | `myapp://path` | `https://domain/path` | `https://domain/path` |
| Ownership proof | none | Apple App Site Association (AASA) JSON on your domain | `assetlinks.json` on your domain |
| Works when app missing | no (error or no-op) | yes — loads in browser | yes — loads in browser |
| Eligible handling | browser and platform dependent | verified association plus opening context and user choice | verified association plus opening context and user choice |
| Setup surface | Xcode and `AndroidManifest.xml` | Apple entitlement + HTTPS file | manifest + HTTPS file |

## 2. iOS Setup (Associated Domains)

1. Enable the Associated Domains capability: `applinks:app.example.com`
2. Host (over HTTPS, no redirects) at `https://app.example.com/.well-known/apple-app-site-association`:

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["TEAMID123.com.example.app"],
        "components": [
          { "/": "/product/*", "comment": "Product detail pages" },
          { "/": "/invite/*" }
        ]
      }
    ]
  }
}
```

3. Serve JSON without redirects and verify the association on-device. On iOS 14+, Apple's CDN caches AASA. Devices check for updates approximately weekly; reinstalling downloads the CDN copy, which may still reflect a cached response. Use Apple's diagnostics or developer mode for controlled testing; there is no direct CDN invalidation option.

For staging QA, append `?mode=developer` to the Associated Domains entitlement on builds with iOS Developer Mode enabled so the device fetches AASA directly from your server and bypasses Apple's CDN cache. Also note that iOS invokes Universal Links reliably only on cross-domain user taps — same-domain navigation, programmatic JavaScript redirects, and many embedded WebViews stay inside the browser.

## 3. Android Setup (Intent Filter + Asset Links)

```xml
<!-- AndroidManifest.xml -->
<intent-filter android:autoVerify="true">
  <action android:name="android.intent.action.VIEW" />
  <category android:name="android.intent.category.DEFAULT" />
  <category android:name="android.intent.category.BROWSABLE" />
  <data android:scheme="https" android:host="app.example.com"
        android:pathPrefix="/product/" />
</intent-filter>
```

```json
// https://app.example.com/.well-known/assetlinks.json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "com.example.app",
    "sha256_cert_fingerprints": ["AB:CD:..."]
  }
}]
```

The SHA-256 fingerprint must match the certificate signing the installed app. With Play App Signing, use the app-signing certificate, not merely the upload certificate. Keep debug and staging associations on separate development domains rather than trusting every developer key on the production domain.

On Android 15+ devices with Google services, Dynamic App Links can refine server-side path and query rules from `assetlinks.json`, though they cannot expand the manifest's declared scope. Devices periodically re-fetch dynamic rules, so changes can take up to seven days to propagate everywhere.

Android 14 and earlier ignore dynamic rules and rely solely on manifest intent filters. Test both paths across supported OS versions, and never treat association-file edits as an instant emergency kill switch.

## 4. Cold vs. Warm Start

| State | API to catch the link |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Cold (process dead) | `Linking.getInitialURL()` — resolve once during bootstrap |
| Warm (backgrounded) | React Navigation handles the configured subscription, or a manual owner listens with `Linking.addEventListener('url', ...)` |
| Push-notification entry | notification payload URL routed through the same parser |

Handle both paths through one router config (below) so a campaign link lands identically whether the app was fresh-installed, killed yesterday, or backgrounded since morning.

## 5. Preserve Context Explicitly Across Installation

Without the app, `/invite/abc9` opens the website. Sending the user through an app store does not guarantee that iOS or Android will deliver that original URL on first launch. A reliable fallback is to show a short invitation code, or save the pending invitation to an authenticated account and resume it after sign-in.

Android install-referrer integrations can carry attribution and context under their documented contract. Provider SDKs have platform-specific matching and privacy constraints; probabilistic device matching is not proof of identity or authorization. Avoid assuming clipboard access or an automatic store-to-app handoff. Test a fresh installation and offer a manual recovery path.

## 6. Linking Config, Validation, and Web Fallback

React Navigation linking config (Expo-compatible):

```tsx
// App.tsx / navigation container
import { NavigationContainer } from '@react-navigation/native';

const linking = {
  prefixes: ['https://app.example.com', 'example://'],
  config: {
    screens: {
      Product: 'product/:id',
      Invite: 'invite/:code',
      Settings: {
        path: 'settings',
        screens: { Notifications: 'notifications' },
      },
    },
  },
};

export function App() {
  return (
    <NavigationContainer linking={linking} fallback={<Splash />}>
      <RootNavigator />
    </NavigationContainer>
  );
}
```

`Splash` and `RootNavigator` are application components. React Navigation owns initial and event URL handling with this configuration; do not also install a competing manual listener. The route map is not resource authorization: restore session state, retain a validated pending destination, and check access before showing protected data.

**Validate the URL and own the initial and event race.** The parser below accepts only the two documented product-link formats. An unknown domain, credential-bearing URL, or invalid ID produces no route. Use an appropriate URL implementation or polyfill for the supported React Native runtime.

```typescript
export function parseProductLink(raw: string): { id: string } | null {
  try {
    const url = new URL(raw);
    if (url.username || url.password || url.search || url.hash) return null;
    let path: string;
    if (url.origin === 'https://app.example.com') {
      path = url.pathname;
    } else if (url.protocol === 'example:' && url.hostname === 'product' && !url.port) {
      path = `/product${url.pathname}`;
    } else return null;
    const match = /^\/product\/([a-zA-Z0-9_-]{1,64})$/.exec(path);
    return match ? { id: match[1] } : null;
  } catch {
    return null;
  }
}
```

Reject protocol-relative paths (`//evil.com`) and arbitrary external redirect parameters inside inbound links, and never forward an unvalidated deep-link URL directly into a `WebView` or `Linking.openURL()` call.

For the manual alternative, mount one listener owner during bootstrap. `handleUrl` validates and queues the destination; it does not bypass navigation and session readiness. Keep both callbacks stable, for example with `useCallback`, so renders do not restart bootstrap.

```typescript
import { useEffect } from 'react';
import { Linking } from 'react-native';

export function useDeepLinks(
  handleUrl: (url: string) => void,
  onError: (error: unknown) => void,
) {
  useEffect(() => {
    let active = true;
    let receivedEvent = false;
    const sub = Linking.addEventListener('url', ({ url }) => {
      if (!active) return;
      receivedEvent = true;
      handleUrl(url);
    });
    void Linking.getInitialURL().then((url) => {
      // A newer event takes precedence over a late bootstrap result.
      if (active && !receivedEvent && url) handleUrl(url);
    }).catch((error) => { if (active) onError(error); });
    return () => { active = false; sub.remove(); };
  }, [handleUrl, onError]);
}
```

Trace the race: `/product/42` starts resolving at launch; an event for `/product/43` arrives first. The listener selects `43` and the late initial result cannot replace it. Unmount disables pending completion. The app still needs an explicit queue and deduplication policy and resource-access check; this hook only owns link delivery.

**Web fallback page (no app installed):**

```tsx
// app.example.com/product/42 — server-rendered page IS the fallback
export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params; // params is a Promise in Next.js 15+
  return (
    <main>
      <h1>Product {id}</h1>
      <a href="https://apps.apple.com/app/id123456">Get the app</a>
      {/* smart banner logic: hide when already in-app */}
      <a href={`example://product/${encodeURIComponent(id)}`}>Open in app</a>
    </main>
  );
}
```

Because Universal and App Links are plain `https://` URLs, the same URL can serve the uninstalled user. Implement real content, availability and error states, and store calls to action; the association file does not create that page. Never rely on `example://` buttons as the primary path — iOS Safari will error on missing handlers.

## 7. Testing Approaches

```bash
# iOS simulator — trigger a universal link
xcrun simctl openurl booted "https://app.example.com/product/42"

# Android emulator — fire an adb view intent
adb shell am start -W -a android.intent.action.VIEW \
  -d "https://app.example.com/product/42"

# Verify Android domain verification status
adb shell pm get-app-links com.example.app
```

```typescript
// excerpt
// E2E with Detox: simulate cold-start link open
await device.launchApp({
  newInstance: true,
  url: 'https://app.example.com/invite/abc9',
});
await expect(element(by.id('invite-screen'))).toBeVisible();
```

Checklist per platform: test cold AND warm starts, both `https://` and custom-scheme prefixes, the uninstalled fallback in a real mobile browser, and AASA and `assetlinks.json` reachability (`curl -I` — no redirects, correct content type).

## Summary

- Prefer HTTPS links: Universal Links (AASA) and App Links (`assetlinks.json`) verify a domain-to-app association; the HTTPS page remains the web fallback
- Route cold (`getInitialURL`) and warm (`Linking` event) starts through one owner and parser; wait for session and navigation readiness
- Deferred deep linking preserves campaign and invite context across an install; provide an explicit recovery path; a payload in the original URL alone does not survive the store journey
- Association data is cached: Apple devices check AASA approximately weekly; Android 15 dynamic rules may take up to seven days, so keep static manifest rules sufficient for older versions
- Test real cold and warm and uninstalled paths with production signing identities, `simctl openurl`, Android intents, and the HTTPS fallback

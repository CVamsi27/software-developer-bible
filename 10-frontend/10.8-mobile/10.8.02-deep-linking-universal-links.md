# Deep Linking, Universal Links & App Links

> Getting users from an email, QR code, or web page into the right in-app screen is table stakes for mobile products. This file covers custom URI schemes vs iOS Universal Links vs Android App Links, the associated-domain/intent-filter setup, cold vs warm start handling, deferred deep linking after install, React Navigation integration, testing, and graceful web fallback.

## TL;DR

Deep links route users into app screens from URLs: custom schemes vs Universal Links/App Links, fallbacks for uninstalled apps, and the web/app routing contract.

## First Principles

Deep links are URLs as app entry points — the identity problem is trust:

1. **Custom schemes have no owner verification** (any app can claim `myapp://`); universal links/app links bind HTTPS domains to apps via hosted files (apple-app-site-association / assetlinks) — the platform verifies *domain control*, which is the whole security model (→ 20.5.1.03's trust anchors).
2. **The URL is the contract across install states**: installed → app opens to that screen; not installed → the web page loads (→ 10.4.2.01's routing continuity) — routing must be designed URL-first, not screen-first.

## Definition

**Deep linking** routes a user to specific in-app content from outside the app. Three mechanisms:

1. **Custom URI schemes** (`myapp://product/42`) — oldest, works everywhere, but claims any scheme with no ownership proof and fails when the app is not installed (browser shows an error or nothing)
2. **Universal Links (iOS)** — regular `https://` URLs that iOS verifies against a `apple-app-site-association` (AASA) file on your domain; opens the app when installed, otherwise falls back to Safari normally
3. **App Links (Android)** — the Android equivalent: `https://` intents verified via `assetlinks.json`, auto-open the verified app without disambiguation dialogs

```text
┌─────────────────────────────────────────────────────────────────────┐
│ LINK → SCREEN FLOW                                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ https://app.example.com/product/42                                  │
│   │                                                                 │
│   ├─ iOS: AASA at app.example.com/.well-known/apple-app-site-       │
│   │       association lists team ID + bundle → opens app            │
│   │                                                                 │
│   └─ Android: assetlinks.json lists signing cert SHA-256 +          │
│           package → auto-opens (autoVerify=true)                    │
│                │                                                    │
│                ▼                                                    │
│   App launch state:                                                 │
│     COLD  (not running)  → getInitialURL / initialNotification      │
│     WARM  (backgrounded) → subscribe(url/Linking event)             │
│                │                                                    │
│                ▼                                                    │
│   Router parses path → navigation.navigate('Product', {id: '42'})   │
│                                                                     │
│ NOT INSTALLED?                                                      │
│   Universal/App Link → URL just loads in browser (web fallback)     │
│   Custom scheme        → broken UX (or "Open in App Store?" prompt) │
└─────────────────────────────────────────────────────────────────────┘
```

## Why It Matters

- **Campaigns live on links** — push notifications, emails, QR codes all need reliable in-app routing
- **Ownership matters** — schemes are squat-able; Universal/App Links prove domain control via hosted verification files
- **Fallback is free with https links** — no app? The link is still a working web page; custom schemes dead-end
- **Deferred linking is the hard edge** — new install must still land on the linked content (attribution + routing)
- **Interview framing** — compare all three mechanisms plus cold/warm start handling and you cover the expected surface

## How It Works

### 1. Mechanism comparison

| URI scheme | Universal Links (iOS) | App Links (Android) |  |
| ---------------------- | --------------------- | ------------------------------ | ------------------------------ |
| Format | `myapp://path` | `https://domain/path` | `https://domain/path` |
| Ownership proof | none | AASA JSON on your domain | assetlinks.json on your domain |
| Works when app missing | no (error/no-op) | yes — loads in browser | yes — loads in browser |
| Browser dialogs | varies | none | none (if autoVerify) |
| Setup surface | Xcode/AndroidManifest | Apple entitlement + HTTPS file | manifest + HTTPS file |

### 2. iOS setup (associated domains)

1. Enable the Associated Domains capability: `applinks:app.example.com`
2. Host (over HTTPS, no redirects) at `https://app.example.com/.well-known/apple-app-site-association`:

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["TEAMID123.com.example.app"],
        "components": [
          { "/": "/product/*", "comment": "Product detail pages" },
          { "/": "/invite/*" }
        ]
      }
    ]
  }
}
```

3. Reinstall the app so iOS re-fetches and caches the AASA (CDN must serve `application/json`)

### 3. Android setup (intent filter + asset links)

```xml
<!-- AndroidManifest.xml -->
<intent-filter android:autoVerify="true">
  <action android:name="android.intent.action.VIEW" />
  <category android:name="android.intent.category.DEFAULT" />
  <category android:name="android.intent.category.BROWSABLE" />
  <data android:scheme="https" android:host="app.example.com"
        android:pathPrefix="/product" />
</intent-filter>
```

```json
// https://app.example.com/.well-known/assetlinks.json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "com.example.app",
    "sha256_cert_fingerprints": ["AB:CD:..."]
  }
}]
```

The SHA-256 fingerprint ties the domain to your signing certificate — debug vs release keystores produce different fingerprints, so register both for local testing.

### 4. Cold vs warm start

| State | API to catch the link |
| ----------------------- | --------------------------------------------------------- |
| Cold (process dead) | `Linking.getInitialURL()` — resolve once during bootstrap |
| Warm (backgrounded) | `linking.subscribe` / `url` event listener |
| Push-notification entry | notification payload URL routed through the same parser |

Handle both paths through one router config (below) so a campaign link lands identically whether the app was fresh-installed, killed yesterday, or backgrounded since morning.

### 5. Deferred deep linking

A user clicks `https://app.example.com/invite/abc9` *without* the app. Universal/App Links degrade to the website; if they then install from the App Store, plain linking loses the original context. Deferred solutions bridge it:

```text
click /invite/abc9 ──▶ shortlink service records {device fingerprint,
                                        target: invite/abc9}
                                   │
install + first open ──▶ SDK queries service ──▶ returns pending route
                                   │
                     navigate('Invite', {code: 'abc9'}) + attribute install
```

Practical guidance: for invite codes, encode the payload in the link itself (the web page shows a "Get the app" button carrying the code through the store's install-referrer on Android, or a clipboard/manual code on iOS) before reaching for paid attribution SDKs (AppsFlyer/Branch) which add privacy review weight.

## Code Examples

### 1. React Navigation linking config (Expo-compatible)

```typescript
// App.tsx / navigation container
import { NavigationContainer } from '@react-navigation/native';

const linking = {
  prefixes: ['https://app.example.com', 'example://'],
  config: {
    screens: {
      Product: 'product/:id',
      Invite: 'invite/:code',
      Settings: {
        path: 'settings',
        screens: { Notifications: 'settings/notifications' },
      },
    },
  },
};

export function App() {
  return (
    <NavigationContainer linking={linking} fallback={<Splash />}>
      <RootNavigator />
    </NavigationContainer>
  );
}
```

React Navigation parses incoming URLs against this map and navigates declaratively — including nested screens — replacing manual `getInitialURL` plumbing for most apps.

### 2. Manual cold/warm start handling (when you need full control)

```typescript
import { useEffect } from 'react';
import { Linking } from 'react-native';

function useDeepLinks(handleUrl: (url: string) => void) {
  useEffect(() => {
    // COLD START: resolve once on mount
    Linking.getInitialURL().then((url) => {
      if (url) handleUrl(url);
    });

    // WARM START: subscribe while foregrounded
    const sub = Linking.addEventListener('url', ({ url }) => handleUrl(url));
    return () => sub.remove();
  }, [handleUrl]);
}
```

### 3. Web fallback page (no app installed)

```tsx
// app.example.com/product/42 — server-rendered page IS the fallback
export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params; // params is a Promise in Next.js 15+
  return (
    <main>
      <h1>Product {id}</h1>
      <a href="https://apps.apple.com/app/id123456">Get the app</a>
      {/* smart banner logic: hide when already in-app */}
      <button onClick={() => (location.href = `example://product/${id}`)}>
        Open in app
      </button>
    </main>
  );
}
```

Because Universal/App Links are plain https URLs, the uninstalled case costs you nothing extra: content renders in the browser, with store CTAs. Never rely on `example://` buttons as the primary path — iOS Safari will error on missing handlers.

### 4. Testing approaches

```bash
# iOS simulator — trigger a universal link
xcrun simctl openurl booted "https://app.example.com/product/42"

# Android emulator — fire an adb view intent
adb shell am start -W -a android.intent.action.VIEW \
  -d "https://app.example.com/product/42"

# Verify Android domain verification status
adb shell pm get-app-links com.example.app
```

```typescript
// E2E with Detox: simulate cold-start link open
await device.launchApp({
  newInstance: true,
  url: 'https://app.example.com/invite/abc9',
});
await expect(element(by.id('invite-screen'))).toBeVisible();
```

Checklist per platform: test cold AND warm starts, both `https://` and custom-scheme prefixes, the uninstalled fallback in a real mobile browser, and AASA/assetlinks reachability (`curl -I` — no redirects, correct content type).

## Real-World Use Cases

- **Email/SMS appointment links** — Universal Link opens the app to the booking screen when installed, the website when not; one URL, both worlds (→ 10.7.05's install path).
- **Push notification routing** — tap → deep link into the referenced entity, not the home screen; the difference between notification UX that works and one that doesn't.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Serving AASA/assetlinks behind redirects or wrong MIME type | Serve directly over HTTPS as `application/json`; CDNs often need explicit config |
| Only handling warm-start events | Also call `getInitialURL()` for cold launches |
| Registering only the release cert fingerprint on Android | Add debug + staging fingerprints too, or local builds fail verification |
| Testing universal links by typing the URL in Safari | Type-in-Safari is exempt on some browsers/situations — use `simctl openurl`, messages, or notes app links |
| Custom scheme as primary campaign link | Use https links; keep schemes only as a legacy secondary prefix |
| Losing deferred context at the store | Encode route payloads in the link/web page; consider attribution SDKs only with privacy sign-off |

## Best Practices

1. **One canonical link format**: https URLs on your domain, parsed by one React Navigation `linking` config
2. **Keep verification files redirect-free**, versioned, and monitored (a broken AASA silently kills all iOS links)
3. **Route cold and warm starts through the same parser** — one source of truth for URL → screen mapping
4. **Design the web fallback deliberately** — it doubles as your install-conversion page
5. **Log received URLs** (with consent) in dev builds — misrouted campaigns are common and hard to reproduce otherwise
6. **Test on real devices** after every provisioning/signing change — verification caching hides breakage from simulators

## Performance Considerations

- First-launch deep-link routing should happen before heavy hydration: pass the initial URL into navigation synchronously where possible
- AASA files can be CDN-cached aggressively by Apple — plan for slow propagation of rule changes (hours)
- Avoid redirect chains on marketing links; each hop risks dropping the universal-link handoff to the app

## Summary

- Custom schemes are legacy glue: no ownership proof, poor fallback — prefer https-based links
- Universal Links (AASA) and App Links (assetlinks.json) bind your domain to the binary via hosted JSON; they fall back to the browser for free
- Handle cold (`getInitialURL`) and warm (`subscribe`) starts through a single React Navigation linking config
- Deferred deep linking preserves campaign/invite context across an install; encode payloads in links before adopting attribution SDKs
- Test cold/warm/fallback paths on devices and simulators with `simctl openurl` and `adb` intents

## Cheat Sheet

```text
DEEP LINKING CHEAT SHEET
════════════════════════════════════════════════════════════════

MECHANISMS:
  myapp://path          scheme · no proof · bad fallback
  https://… (iOS)       Universal Links · AASA file · browser fallback
  https://… (Android)   App Links · assetlinks.json · autoVerify

SETUP:
  iOS   entitlement applinks:domain +
        /.well-known/apple-app-site-association {appIDs, components}
  And.  intent-filter autoVerify + /.well-known/assetlinks.json
        (register debug + release SHA-256)

CAPTURE:
  cold  Linking.getInitialURL()         (once, bootstrap)
  warm  Linking.addEventListener('url') (subscribe)
  both  → React Navigation linking.config.screens map

DEFERRED:
  click w/o app → record target (shortlink/referrer)
  first open    → fetch pending route → navigate

TESTING:
  xcrun simctl openurl booted <url>
  adb shell am start -a android.intent.action.VIEW -d <url>
  Detox: device.launchApp({url})
  verify files: curl -I (200, application/json, no redirects)
```

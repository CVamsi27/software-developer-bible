# Deep Linking, Universal Links & App Links

> Getting users from an email, QR code, or web page into the right in-app screen is table stakes for mobile products. This file covers custom URI schemes vs iOS Universal Links vs Android App Links, the associated-domain/intent-filter setup, cold vs warm start handling, deferred deep linking after install, React Navigation integration, testing, and graceful web fallback.

## Definition

**Deep linking** routes a user to specific in-app content from outside the app. Three mechanisms:

> **Textbook Definition:** Deep linking maps an externally supplied URI to application navigation state. Verified HTTPS associations establish a domain-to-app relationship; routing and authorization must still validate the requested destination and resource.

1. **Custom URI schemes** (`myapp://product/42`) — supported through platform/browser-specific handling, with no verified domain ownership and an unreliable fallback when the app is absent
2. **Universal Links (iOS)** — regular `https://` URLs that iOS verifies against an `apple-app-site-association` (AASA) file on your domain; eligible link taps can open the associated installed app, while a working HTTPS page provides a web fallback
3. **App Links (Android)** — the Android equivalent: `https://` intents verified via `assetlinks.json`, can open a verified app without disambiguation; association, user settings and the link-opening context still matter

## First Principles

A link arrives before the app necessarily has a router, restored session or loaded data. Treat it as an untrusted navigation request: identify an allowed destination, wait for application readiness, then authorize access to the resource. Domain verification chooses an eligible handler; it does not authenticate the person tapping the link.

```text
HTTPS link → OS association/user choice → app receives URL
           → validate destination → restore session/navigation
           → authorize resource → show screen or safe fallback
no eligible installed handler → deliberately implemented web page
```

The URL must remain useful outside the app. Opening a store does not automatically preserve it through installation.

## Why It Matters

- **Campaigns live on links** — push notifications, emails, QR codes all need reliable in-app routing
- **Ownership matters** — schemes are squat-able; Universal/App Links prove domain control via hosted verification files
- **HTTPS supports a web fallback** — implement a useful page for users who do not enter the app; a valid URL alone does not provide that page
- **Deferred linking is the hard edge** — new install must still land on the linked content (attribution + routing)
- **Interview framing** — compare all three mechanisms plus cold/warm start handling and you cover the expected surface

## How It Works

### 1. Mechanism comparison

| Mechanism | Custom URI scheme | Universal Links (iOS) | App Links (Android) |
| ---------------------- | -------------------------- | ----------------------------------------------------- | ----------------------------------------------------- |
| Format | `myapp://path` | `https://domain/path` | `https://domain/path` |
| Ownership proof | none | AASA JSON on your domain | assetlinks.json on your domain |
| Works when app missing | no (error/no-op) | yes — loads in browser | yes — loads in browser |
| Eligible handling | browser/platform dependent | verified association plus opening context/user choice | verified association plus opening context/user choice |
| Setup surface | Xcode/AndroidManifest | Apple entitlement + HTTPS file | manifest + HTTPS file |

### 2. iOS setup (associated domains)

1. Enable the Associated Domains capability: `applinks:app.example.com`
2. Host (over HTTPS, no redirects) at `https://app.example.com/.well-known/apple-app-site-association`:

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["TEAMID123.com.example.app"],
        "components": [
          { "/": "/product/*", "comment": "Product detail pages" },
          { "/": "/invite/*" }
        ]
      }
    ]
  }
}
```

3. Serve JSON without redirects and verify the association on-device. On iOS 14+, Apple’s CDN caches AASA; reinstalling requests the CDN copy, not guaranteed fresh origin content. Use Apple’s diagnostics/developer mode for controlled testing; there is no direct CDN invalidation option.

### 3. Android setup (intent filter + asset links)

```xml
<!-- AndroidManifest.xml -->
<intent-filter android:autoVerify="true">
  <action android:name="android.intent.action.VIEW" />
  <category android:name="android.intent.category.DEFAULT" />
  <category android:name="android.intent.category.BROWSABLE" />
  <data android:scheme="https" android:host="app.example.com"
        android:pathPrefix="/product/" />
</intent-filter>
```

```json
// https://app.example.com/.well-known/assetlinks.json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "com.example.app",
    "sha256_cert_fingerprints": ["AB:CD:..."]
  }
}]
```

The SHA-256 fingerprint must match the certificate signing the installed app. With Play App Signing, use the app-signing certificate, not merely the upload certificate. Keep debug/staging associations on separate development domains rather than trusting every developer key on the production domain.

On Android 15+ devices with Google services, Dynamic App Links can refine server-side path/query rules from `assetlinks.json`; they cannot expand the manifest's declared scope. Android 15+ periodically re-fetches dynamic rules, and changes can take up to seven days to reach all devices. Android 14 and earlier ignore dynamic rules and use manifest rules. Test both paths on supported OS versions, and do not use association-file changes as an emergency switch.

### 4. Cold vs warm start

| State | API to catch the link |
| ----------------------- | --------------------------------------------------------- |
| Cold (process dead) | `Linking.getInitialURL()` — resolve once during bootstrap |
| Warm (backgrounded) | `linking.subscribe` / `url` event listener |
| Push-notification entry | notification payload URL routed through the same parser |

Handle both paths through one router config (below) so a campaign link lands identically whether the app was fresh-installed, killed yesterday, or backgrounded since morning.

### 5. Preserve context explicitly across installation

Without the app, `/invite/abc9` opens the website. Sending the user through an app store does not guarantee that iOS or Android will deliver that original URL on first launch. A reliable fallback is to show a short invitation code, or save the pending invitation to an authenticated account and resume it after sign-in.

Android install-referrer integrations can carry attribution/context under their documented contract. Provider SDKs have platform-specific matching and privacy constraints; probabilistic device matching is not proof of identity or authorization. Avoid assuming clipboard access or an automatic store-to-app handoff. Test a fresh installation and offer a manual recovery path.

## Code Examples

### 1. React Navigation linking config (Expo-compatible)

```typescript
// App.tsx / navigation container
import { NavigationContainer } from '@react-navigation/native';

const linking = {
  prefixes: ['https://app.example.com', 'example://'],
  config: {
    screens: {
      Product: 'product/:id',
      Invite: 'invite/:code',
      Settings: {
        path: 'settings',
        screens: { Notifications: 'notifications' },
      },
    },
  },
};

export function App() {
  return (
    <NavigationContainer linking={linking} fallback={<Splash />}>
      <RootNavigator />
    </NavigationContainer>
  );
}
```

`Splash` and `RootNavigator` are application components. React Navigation owns initial/event URL handling with this configuration; do not also install a competing manual listener. The route map is not resource authorization: restore session state, retain a validated pending destination and check access before showing protected data.

### 2. Validate the URL and own the initial/event race

The parser below accepts only the two documented product-link formats. An unknown domain, credential-bearing URL or invalid ID produces no route. Use an appropriate URL implementation/polyfill for the supported React Native runtime.

```typescript
export function parseProductLink(raw: string): { id: string } | null {
  try {
    const url = new URL(raw);
    if (url.username || url.password || url.search || url.hash) return null;
    let path: string;
    if (url.origin === 'https://app.example.com') {
      path = url.pathname;
    } else if (url.protocol === 'example:' && url.hostname === 'product' && !url.port) {
      path = `/product${url.pathname}`;
    } else return null;
    const match = /^\/product\/([a-zA-Z0-9_-]{1,64})$/.exec(path);
    return match ? { id: match[1] } : null;
  } catch {
    return null;
  }
}
```

For the manual alternative, mount one listener owner during bootstrap. `handleUrl` validates and queues the destination; it does not bypass navigation/session readiness. Keep both callbacks stable, for example with `useCallback`, so renders do not restart bootstrap.

```typescript
import { useEffect } from 'react';
import { Linking } from 'react-native';

export function useDeepLinks(
  handleUrl: (url: string) => void,
  onError: (error: unknown) => void,
) {
  useEffect(() => {
    let active = true;
    let receivedEvent = false;
    const sub = Linking.addEventListener('url', ({ url }) => {
      if (!active) return;
      receivedEvent = true;
      handleUrl(url);
    });
    void Linking.getInitialURL().then((url) => {
      // A newer event takes precedence over a late bootstrap result.
      if (active && !receivedEvent && url) handleUrl(url);
    }).catch((error) => { if (active) onError(error); });
    return () => { active = false; sub.remove(); };
  }, [handleUrl, onError]);
}
```

Trace the race: `/product/42` starts resolving at launch; an event for `/product/43` arrives first. The listener selects `43` and the late initial result cannot replace it. Unmount disables pending completion. The app still needs an explicit queue/deduplication policy and resource-access check; this hook only owns link delivery.

### 3. Web fallback page (no app installed)

```tsx
// app.example.com/product/42 — server-rendered page IS the fallback
export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params; // params is a Promise in Next.js 15+
  return (
    <main>
      <h1>Product {id}</h1>
      <a href="https://apps.apple.com/app/id123456">Get the app</a>
      {/* smart banner logic: hide when already in-app */}
      <a href={`example://product/${encodeURIComponent(id)}`}>Open in app</a>
    </main>
  );
}
```

Because Universal/App Links are plain https URLs, the same URL can serve the uninstalled user. Implement real content, availability/error states and store calls to action; the association file does not create that page. Never rely on `example://` buttons as the primary path — iOS Safari will error on missing handlers.

### 4. Testing approaches

```bash
# iOS simulator — trigger a universal link
xcrun simctl openurl booted "https://app.example.com/product/42"

# Android emulator — fire an adb view intent
adb shell am start -W -a android.intent.action.VIEW \
  -d "https://app.example.com/product/42"

# Verify Android domain verification status
adb shell pm get-app-links com.example.app
```

```typescript
// E2E with Detox: simulate cold-start link open
await device.launchApp({
  newInstance: true,
  url: 'https://app.example.com/invite/abc9',
});
await expect(element(by.id('invite-screen'))).toBeVisible();
```

Checklist per platform: test cold AND warm starts, both `https://` and custom-scheme prefixes, the uninstalled fallback in a real mobile browser, and AASA/assetlinks reachability (`curl -I` — no redirects, correct content type).

## Real-World Use Cases

- **Email/SMS appointment links** — Universal Link opens the app to the booking screen when installed, the website when not; one URL, both worlds (→ 10.7.05's install path).
- **Push notification routing** — tap → deep link into the referenced entity, not the home screen; the difference between notification UX that works and one that doesn't.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Serving AASA/assetlinks behind redirects or wrong MIME type | Serve directly over HTTPS as `application/json`; CDNs often need explicit config |
| Only handling warm-start events | Also call `getInitialURL()` for cold launches |
| Registering only the release cert fingerprint on Android | Use the actual installed signing certificate; isolate development associations from the production domain |
| Testing universal links by typing the URL in Safari | Type-in-Safari is exempt on some browsers/situations — use `simctl openurl`, messages, or notes app links |
| Custom scheme as primary campaign link | Use https links; keep schemes only as a legacy secondary prefix |
| Losing deferred context at the store | Offer an explicit code/account-resume path; verify any install-referrer/provider contract |

## Best Practices

1. **One canonical link format**: https URLs on your domain, parsed by one React Navigation `linking` config
2. **Keep verification files redirect-free**, versioned, and monitored (a broken AASA silently kills all iOS links)
3. **Route cold and warm starts through the same parser** — one source of truth for URL → screen mapping
4. **Design the web fallback deliberately** — it doubles as your install-conversion page
5. **Log sanitized route diagnostics** in dev builds — redact invitation tokens and personal data before logging
6. **Test on real devices** after every provisioning/signing change — verification caching hides breakage from simulators

## Performance Considerations

- Resolve the initial URL during bootstrap; show a loading state while session/navigation readiness is established rather than navigating early
- AASA files can be CDN-cached aggressively by Apple — inspect CDN/device diagnostics rather than promising a fixed propagation time
- Avoid redirect chains on marketing links; each hop risks dropping the universal-link handoff to the app

## Summary

- Custom schemes are legacy glue: no ownership proof, poor fallback — prefer https-based links
- Universal Links (AASA) and App Links (assetlinks.json) bind your domain to the binary via hosted JSON; a deliberately implemented HTTPS page supplies the web fallback
- Handle cold (`getInitialURL`) and warm (`subscribe`) starts through a single React Navigation linking config
- Deferred deep linking preserves campaign/invite context across an install; provide an explicit recovery path; a payload in the original URL alone does not survive the store journey
- Test cold/warm/fallback paths on devices and simulators with `simctl openurl` and `adb` intents

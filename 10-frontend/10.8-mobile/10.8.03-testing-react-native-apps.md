# Testing React Native Apps

> RN testing is a pyramid like web's — Jest units, React Native Testing Library components, and a thin device-level E2E layer — plus two mobile-only problems: native modules that must be mocked, and CI that needs real simulators (including macOS runners for iOS builds). This file covers the stack, the Detox vs Maestro decision, debugging tools, and visual regression options.

## Definition

A production-grade RN test setup layers:

> **Textbook Definition:** Mobile application testing checks behavior at logic, component and installed-application boundaries. Test fidelity increases when real native services and device conditions participate, while execution cost and failure diagnosis become more demanding.

1. **Unit tests** (Jest) — pure logic, hooks, reducers, API mappers
2. **Component tests** (React Native Testing Library) — render React components with React Native's test renderer and assert accessible behavior, not implementation details
3. **E2E tests** (Detox or Maestro) — drive real apps on simulators/devices through flows
4. **Visual regression** — screenshot diffs to catch layout drift

## First Principles

A test can only observe behavior inside its runtime. Replacing a native permission service with a JavaScript mock lets a component test check its response to permission denial; it cannot prove the device presents the real permission prompt correctly.

Use the cheapest boundary that can expose the failure: plain logic tests for calculations, component tests for interaction/state, and installed-app tests for navigation, keyboard, permissions and lifecycle. Device tests cost more to run and diagnose, so concentrate them on important platform seams rather than assuming either layer replaces the other.

## Which failures escape a JavaScript test?

- **Mobile breakage is expensive** — native changes require a new binary and store distribution; compatible JavaScript updates may have a separate delivery path
- **Native boundary is the new risk** — web testing skills transfer, but modules like `react-native-fs` crash differently under mocks than reality
- **CI needs hardware** — iOS builds require macOS runners; this shapes pipeline cost and design
- **Detox vs Maestro** is a common senior-level "pick your tooling and justify it" question

## Match the test boundary to the production boundary

### Which layer can observe the failure?

| Layer | Tool | Speed | Runs where |
| --------- | ------------------------------------------------------------------ | --------------------------------- | -------------------------------------------------------- |
| Unit | Jest with the project's Babel/TypeScript transform | milliseconds | any CI machine |
| Component | React Native Testing Library | depends on the component and test | Node with an RN test renderer; no browser DOM |
| E2E | Detox (builds app w/ test hooks) or Maestro (drives installed app) | minutes | macOS/Linux runners + simulators/emulators, device farms |
| Visual | Detox screenshots / Maestro screenshot + diff tool | minutes | same as E2E |

## Follow one form from validation to device behavior

### 1. Jest config for a bare RN workspace

```javascript
// jest.config.js
module.exports = {
  preset: '@react-native/jest-preset',
  setupFilesAfterEnv: ['./jest.setup.ts'],
  transformIgnorePatterns: [
    // RN ships untranspiled ESM in node_modules — whitelist what Jest must parse
    'node_modules/(?!(react-native|@react-native|@expo|react-native-reanimated|react-native-gesture-handler)/)',
  ],
  moduleNameMapper: {
    '\\.(png|jpg)$': '<rootDir>/__mocks__/fileMock.js',
  },
};
```

For bare React Native 0.85 and later, use the extracted `@react-native/jest-preset`; Expo projects should use the matching `jest-expo` preset, and older React Native releases must follow their version's setup guide. The `transformIgnorePatterns` allowlist is a common integration point: transform packages that ship syntax your runtime cannot parse, while leaving other dependencies untransformed for speed.

### 2. Unit test of shared domain logic

```typescript
// pricing.test.ts
import { computeTotal } from './pricing';

describe('computeTotal', () => {
  it('applies percentage discounts before tax', () => {
    expect(computeTotal({ items: [1000, 500], discountPct: 10, taxPct: 20 }))
      .toBe(1620); // (1500 - 150) * 1.2 in minor units
  });

  it('never returns negative totals after clamping', () => {
    expect(computeTotal({ items: [100], discountPct: 150 })).toBe(0);
  });
});
```

Keep business rules in plain TS modules (your shared monorepo packages) so they test without any RN runtime at all.

### 3. Exercise the user interaction in the React layer

The following example targets **RNTL v14**: rendering and user interactions are awaited, matchers are built in, and the package uses its documented `test-renderer` peer. An older v13 suite has different renderer/API requirements; migrate against its installed-version guide rather than mixing configuration. [RNTL quick start](https://oss.callstack.com/react-native-testing-library/docs/start/quick-start).

```tsx
import { useState } from 'react';
import { Button, Text, TextInput, View } from 'react-native';
import { render, screen, userEvent } from '@testing-library/react-native';

function EmailForm({ onSubmit }: { onSubmit: (email: string) => void }) {
  const [email, setEmail] = useState('');
  const [error, setError] = useState('');
  function submit() {
    const value = email.trim();
    if (!value) { setError('Email is required'); return; }
    setError('');
    onSubmit(value);
  }
  return (
    <View>
      <TextInput accessibilityLabel="Email" value={email} onChangeText={setEmail} />
      {error ? <Text accessibilityRole="alert">{error}</Text> : null}
      <Button title="Sign in" onPress={submit} />
    </View>
  );
}

test('rejects empty input and submits the entered email', async () => {
  const onSubmit = jest.fn();
  const user = userEvent.setup();
  await render(<EmailForm onSubmit={onSubmit} />);
  await user.press(screen.getByRole('button', { name: 'Sign in' }));
  expect(screen.getByText('Email is required')).toBeOnTheScreen();
  expect(onSubmit).not.toHaveBeenCalled();
  await user.type(screen.getByLabelText('Email'), 'a@b.co');
  await user.press(screen.getByRole('button', { name: 'Sign in' }));
  expect(onSubmit).toHaveBeenCalledWith('a@b.co');
  expect(screen.queryByText('Email is required')).toBeNull();
});
```

This test observes the React-side validation and callback. It does not open a native keyboard, verify Android/iOS layout, or authenticate a user. Those outcomes need their own integration/device evidence.

RNTL principles carried over from web: query by accessibility role/label (`getByRole`, `getByLabelText`) — which checks some accessible relationships, but does not establish device screen-reader behavior or conformance — never by `testID` internals unless necessary.

### 4. Replace the native boundary without hiding failures

Anything touching Objective-C/Kotlin does not exist in Jest's Node world:

```typescript
// __mocks__/react-native-fs.ts — hand-rolled mock for a native module
export const readFile = jest.fn().mockResolvedValue('{"version":2}');
export const writeFile = jest.fn().mockResolvedValue(undefined);
export const exists = jest.fn().mockResolvedValue(true);
```

```typescript
// jest.setup.ts — explicit boundary replacements for this suite
jest.mock('react-native-fs', () => require('./__mocks__/react-native-fs'));
jest.mock('react-native-haptic-feedback', () => ({ trigger: jest.fn() }));
jest.mock('react-native-permissions', () => ({
  PERMISSIONS: { IOS: {}, ANDROID: {} },
  request: jest.fn().mockResolvedValue('granted'),
  RESULTS: { GRANTED: 'granted', DENIED: 'denied' },
}));
```

For a denial case, make `request` resolve to `RESULTS.DENIED` and assert the app explains recovery without accessing the protected feature. A mock that always grants hides that path. Then verify prompt/denial behavior on the supported devices.

Rules that keep mocks honest: implement the boundary contract and relevant success/failure behavior; prefer `jest.spyOn` over reimplementation when the JS wrapper has logic worth exercising; and if a library offers official mocks (AsyncStorage, Reanimated), use them.

### 5. Drive the installed app where Node tests cannot reach

| Dimension | Detox | Maestro |
| ------------ | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Model | grey-box: links app against test harness (`detox` build), syncs with app via native APIs | black-box: drives supported installed apps with YAML flows and accessibility selectors |
| Language | TypeScript (Jest/Mocha runner) | declarative YAML (`runFlow`, `runScript` escape hatch in JS) |
| Setup weight | high — per-platform build configs, Xcode/Gradle hooks | low — install CLI, point at simulator/app binary |
| Speed/flake | fast once built; synchronization reduces sleeps | no universal speed ordering; compare waits, diagnostics and reliability for the actual flows |
| CI fit | needs the same mac toolchain as your builds | requires a supported device/emulator host; iOS simulators need macOS |
| Best fit | teams owning the app binary wanting tight control & speed | quick coverage, cross-app flows, QA-authored tests |

```yaml
# .maestro/login.yaml — Maestro flow
appId: com.example.app
---
- launchApp
- tapOn: "Email"
- inputText: "a@b.co"
- tapOn: "Sign In"
- assertVisible: "Welcome back"
```

```typescript
// Detox equivalent
await device.launchApp({ newInstance: true });
await element(by.id('email')).typeText('a@b.co');
await element(by.text('Sign In')).tap();
await expect(element(by.text('Welcome back'))).toBeVisible();
```

These E2E sketches assume an installed app whose successful sign-in renders “Welcome back” and whose input exposes the shown label/test ID. The earlier `EmailForm` only calls a callback; it does not implement that complete authentication journey.

Choose by the required platforms, selectors, synchronization, diagnostics and ownership. Neither tool alone proves release performance; profile representative release builds separately.

### 6. Visual regression options

| Option | How it works | Notes |
| --------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------- |
| Detox `.takeScreenshot()` + Jest image snapshot | captures simulator screenshots, diffs committed baselines | free, tied to Detox runs |
| Maestro `takeScreenshot` + external differ (e.g., reg-suit) | upload artifacts, comment diffs on PRs | works with black-box flows |
| Storybook (web) for shared UI packages | visual-test RN components rendered on web | only valid for truly platform-agnostic components |
| Cloud device farms (Firebase Test Lab, AWS Device Farm, BrowserStack) | run suites across many OS/device combos | catches device-specific layout breaks |

Pin simulator model + OS version or diffs become noise; treat font-rendering differences across devices as expected variance.

### 7. Give device tests the toolchain and runtime they need

A device-test job needs more than `yarn test`. Establish these project-specific prerequisites in order:

1. Select the macOS/Xcode or Android SDK/emulator image compatible with the app, and pin the simulator model/OS used for assertions.
2. Install the reviewed Node and package-manager versions, then restore dependencies from the lockfile using that manager's immutable-install option. Repeat this setup in each independent job; a unit job's environment does not carry into an E2E job.
3. Install native dependencies using the project's locked CocoaPods/Gradle tooling. Build the configured app and ensure its backend/test account fixtures are available.
4. Launch the simulator/emulator, run the selected Detox/Maestro configuration and retain logs/screenshots and artifact/version identities on failure.

Cloud farms can supply a broader device matrix. A hosted-runner label alone does not prove the toolchain or simulator is compatible. Keep the project's real CI configuration as the executable contract; this chapter does not prescribe an incomplete generic workflow.

### 8. Debugging toolchain

```text
React Native DevTools (RN 0.76+): Chrome-DevTools-style debugger,
  React component inspector, Hermes console — replaces Flipper.
Flipper: legacy desktop debugger (network, layout, Redux plugins);
  still present in older codebases but no longer the recommended debugger —
  recognize it in interviews, then check the current RN tools for new setups.
```

Day-to-day: `npx react-native log-android` / Console.app for native logs, Metro bundler errors for JS, and DevTools breakpoints for logic. Configure network mocks explicitly for the test environment. A device's `localhost` is that device, not automatically the development machine; interception support differs across JavaScript and native networking.

## Real-World Use Cases

- **Navigation regression safety** — E2E smoke over the 5 critical flows (auth → core action → sync) catches the deep-link/dark-mode regressions unit tests can't see.
- **Offline-mode testing** — use tool-supported network controls or a device-level test procedure to exercise connectivity loss; queue transitions also need deterministic unit/integration tests; device tests cover lifecycle and connectivity integration.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------- | --------------------------------------------------------------------------------------------- |
| Querying by `testID` everywhere | Prefer role/label queries; keep `testID` for E2E only |
| Mocking native modules with fake behavior | Use contract-faithful fakes; test wrapper logic and verify critical native behavior on-device |
| E2E suite covering everything | Keep E2E to money paths (auth, checkout, deep links); push down the pyramid |
| Unpinned simulators in visual tests | Pin device model + OS version in CI config |
| Skipping `transformIgnorePatterns` tuning | Maintain the explicit allowlist or Jest chokes/fails mysteriously |
| Running iOS E2E on Linux runners | iOS requires macOS runners (or cloud Macs); plan budget accordingly |

## Best Practices

1. **Share tests with web** — monorepo packages holding domain logic reuse their Jest suites unchanged on mobile
2. **One mock directory per native module**, registered in `jest.setup.ts`, reviewed like source code
3. **Smoke-first E2E**: login → core action → logout on both platforms; expand only when flake budget allows
4. **Run units + components on every PR** (Linux, cheap); E2E nightly or pre-release
5. **Name accessibility labels deliberately** — they power RNTL queries, Maestro/Detox selectors, and screen readers simultaneously
6. **Adopt React Native DevTools**; mention Flipper only as legacy context
7. **Investigate flakes with artifacts** — if a test must be quarantined, assign an owner, expiry and replacement coverage for the release-critical behavior

## Performance Considerations

- Jest transforms dominate unit-test wall time — narrow `transformIgnorePatterns` and consider `jest-light-runner` style runners for large repos
- Simulator E2E is CPU-bound; parallelize by splitting Detox workers per simulator instance
- Visual diffs are storage-heavy: retain baselines per platform branch, prune old artifact buckets regularly

## Summary

- The RN pyramid mirrors web: Jest units, RNTL component tests, thin Detox/Maestro E2E, visual snapshots on top
- The mobile-specific skills are mocking native modules honestly and wiring CI with macOS runners for iOS
- Detox integrates a test harness; Maestro drives supported installed apps through declarative flows — compare reliability and diagnostics on the actual journey
- Query components by role and label: better tests, better accessibility, shared selectors with E2E
- Debug with React Native DevTools; treat Flipper as historical context
- Keep E2E small and pinned to critical flows — store-review cycles make regressions too expensive to risk on a flaky mega-suite

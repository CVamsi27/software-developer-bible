# Testing React Native Apps

A Jest test can prove that a button calls a handler; it cannot prove that Android showed the permission prompt or that a deep link reached the right screen after a cold launch. Choose tests by the boundary where the failure can occur.

```typescript
// pricing.test.ts — domain rules run in plain Node, no mobile runtime needed
import { computeTotal } from './pricing';

test('applies the discount before tax', () => {
  expect(computeTotal({ items: [1000, 500], discountPct: 10, taxPct: 20 }))
    .toBe(1620); // (1500 - 150) * 1.2, in minor currency units
});
```

## Definition

React Native testing checks application behavior at several runtime boundaries: plain JavaScript logic, rendered React Native host components, and the installed app running with platform services.

> **Textbook Definition:** Mobile application testing evaluates behavior at logic, component and installed-application boundaries. Higher-fidelity tests include more native services and device conditions, but cost more to run and diagnose.

## First Principles

A test observes only the environment it runs in. Replacing a permission API with a JavaScript mock can prove that the screen recovers from denial; it cannot prove that the operating system displays the prompt or returns the expected result. Use the cheapest test boundary that can expose the failure, then add device evidence for behavior that crosses into native code.

## 1. Prove Domain Rules Without a Mobile Runtime

Keep business rules in plain TypeScript modules so they run quickly under Jest and can be shared with a web app.

```typescript
// pricing.test.ts
import { computeTotal } from './pricing';

describe('computeTotal', () => {
  it('applies the discount before tax', () => {
    expect(computeTotal({ items: [1000, 500], discountPct: 10, taxPct: 20 }))
      .toBe(1620); // (1500 - 150) * 1.2, in minor currency units
  });

  it('clamps an excessive discount at zero', () => {
    expect(computeTotal({ items: [100], discountPct: 150 })).toBe(0);
  });
});
```

The test runs in Node and catches calculation regressions. It says nothing about how a user enters the values or how the native keyboard behaves.

## 2. Check the React Interaction with React Native Testing Library

React Native Testing Library (RNTL) renders React Native host components in a JavaScript test environment. It does not run an iOS or Android renderer. The following example uses **RNTL v14**, whose render and user-event APIs are asynchronous; await them and prefer accessible queries over component internals.

```tsx
import { useState } from 'react';
import { Button, Text, TextInput, View } from 'react-native';
import { render, screen, userEvent } from '@testing-library/react-native';

function EmailForm({ onSubmit }: { onSubmit: (email: string) => void }) {
  const [email, setEmail] = useState('');
  const [error, setError] = useState('');

  function submit() {
    const value = email.trim();
    if (!value) { setError('Email is required'); return; }
    setError('');
    onSubmit(value);
  }

  return (
    <View>
      <TextInput accessibilityLabel="Email" value={email} onChangeText={setEmail} />
      {error ? <Text accessibilityRole="alert">{error}</Text> : null}
      <Button title="Sign in" onPress={submit} />
    </View>
  );
}

test('shows validation, then submits the trimmed address', async () => {
  const onSubmit = jest.fn();
  const user = userEvent.setup();
  await render(<EmailForm onSubmit={onSubmit} />);

  await user.press(screen.getByRole('button', { name: 'Sign in' }));
  expect(screen.getByText('Email is required')).toBeOnTheScreen();
  expect(onSubmit).not.toHaveBeenCalled();

  await user.type(screen.getByLabelText('Email'), ' a@b.co ');
  await user.press(screen.getByRole('button', { name: 'Sign in' }));
  expect(onSubmit).toHaveBeenCalledWith('a@b.co');
  expect(screen.queryByText('Email is required')).toBeNull();
});
```

This covers the React-side interaction and callback. It does not verify a native keyboard, OS accessibility tree, network request or successful login. RNTL v14 uses the `test-renderer` peer package; install the version declared by the RNTL release in your project. Expo projects generally use the `jest-expo` preset. Bare React Native 0.85 and later uses `@react-native/jest-preset`; follow the setup guide for the installed version rather than copying a preset across releases.

```javascript
// jest.config.js for a bare React Native 0.85+ project
module.exports = {
  preset: '@react-native/jest-preset',
  setupFilesAfterEnv: ['./jest.setup.ts'],
  transformIgnorePatterns: [
    'node_modules/(?!(react-native|@react-native|@expo|react-native-reanimated|react-native-gesture-handler)/)',
  ],
};
```

The allowlist is project-specific: transform only dependencies whose syntax the test runtime cannot parse. For new tests, query what a user can identify — roles, labels and visible text. A `testID` can be useful for device automation, but a test built entirely on internal IDs can pass while accessible interaction is broken.

## 3. Mock the Native Edge, Including Its Failure Path

Node cannot load a module implemented in Kotlin or Swift. Replace that edge with a small fake that preserves the contract relevant to the test, then check success and failure behavior.

```typescript
// __mocks__/react-native-permissions.ts
export const RESULTS = { GRANTED: 'granted', DENIED: 'denied' };
export const request = jest.fn();
```

```typescript
// jest.setup.ts
jest.mock('react-native-permissions', () => require('./__mocks__/react-native-permissions'));
```

For a denial test, make `request` return `DENIED` and assert that the app explains recovery without opening the protected feature. A mock that always grants permission hides the most important branch. Verify the real prompt, denial and settings-return behavior on supported devices.

## 4. Test the Installed App Where the OS Participates

Use a simulator, emulator or device for the small set of journeys whose result depends on native behavior: permission prompts, cold-start deep links, keyboard/layout interaction, background/resume and native-module integration. Keep ordinary calculations and most screen logic below this layer; a large device suite is slower and harder to diagnose.

| Tool | How it drives the app | Useful when | Costs to evaluate |
| ------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Detox | Engineer-authored tests connect to a built app through its test integration | Your team owns native build configuration and wants code-level control | Per-platform build setup, simulator capacity and failure diagnosis |
| Maestro | Declarative flows drive a supported installed app through accessibility selectors | You want readable smoke flows or QA-owned scenarios | Platform/runtime support, selector stability and diagnostics for your app |

Neither tool is universally faster or more reliable. Run the same critical flow on the platforms you support, then compare setup, synchronization, logs and flake rate. An E2E pass proves the flow in that test build; measure performance on a release or production-like build.

```yaml
# .maestro/login.yaml
appId: com.example.app
---
- launchApp
- tapOn: "Email"
- inputText: "a@b.co"
- tapOn: "Sign In"
- assertVisible: "Welcome back"
```

This flow assumes the installed app exposes those accessible controls and that a test account can sign in. Keep test accounts and backend fixtures deterministic; do not depend on production user data.

## 5. Make CI Evidence Repeatable

The device job needs a compatible platform toolchain, not just `yarn test`. A reliable sequence is:

1. Pin the Node/package-manager versions and install from the lockfile.
2. Select compatible Xcode or Android SDK/emulator images and pin the simulator/emulator version used for assertions.
3. Install CocoaPods/Gradle dependencies, build the test app and provision deterministic backend fixtures.
4. Run the selected device flow and retain app logs, screenshots, source revision and artifact identity on failure.

JavaScript unit and component tests usually fit Linux CI. iOS simulator builds and tests require macOS; Android runners need an available emulator or a supported device farm. A hosted-runner label alone does not guarantee compatible SDKs or a booted device. Configure those prerequisites in the actual workflow and rerun the test after changing native build inputs.

## 6. Investigate Failures at the Layer That Owns Them

When a test passes but the shipped app fails, first identify what the passing test actually observed. Use RNTL for React state and accessible output; use OS/device evidence for native prompts, focus, lifecycle, rendering and real networking. Keep screenshots only for stable, high-value screens, and pin the device model, OS, fonts and locale so visual diffs remain meaningful.

React Native DevTools is the current integrated JavaScript and component debugger. Older applications may still use Flipper, but choose tools from the supported React Native release rather than copying an old setup. For device logs, combine the platform log stream with Metro and the app's release crash reports; preserve source maps and native symbols for the exact shipped build.

## Summary

Test each behavior at the least expensive boundary that can observe it: Jest for domain rules, RNTL for React interaction, and a thin installed-app suite for OS and native behavior. Mocks should expose failure paths rather than erase them. Make device jobs reproducible, keep accessibility selectors stable and retain enough build and diagnostic evidence to explain a release failure.

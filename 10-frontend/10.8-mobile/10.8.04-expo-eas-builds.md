# Expo EAS Build — Cloud Builds, Profiles & Submitting

> A JavaScript project becomes an installable mobile app after native compilation and signing. EAS Build runs that pipeline in a managed environment; build profiles choose the artifact and its distribution route.

## Definition

`npx expo run:ios` builds locally using your Xcode installation. **EAS Build** performs the native build on Expo's infrastructure. `eas build --platform ios` uploads a project archive and queues a cloud job that unpacks it. It runs `prebuild` if native projects are absent, or builds the native projects already checked in. The job compiles with Xcode or Gradle, signs when the target requires it and returns an artifact such as `.ipa`, `.aab`, `.apk` or an iOS Simulator build. A clean build can reveal native dependencies on local machine state. Cloud iOS builds also let you start a build without owning a local Mac.

> **Textbook Definition:** EAS Build creates signed native application artifacts from a configured source project and build environment. Build profiles, native dependencies and signing credentials determine the artifact; submission and over-the-air updates are separate operations.

Keep three operations separate: **EAS Build compiles a native artifact; EAS Submit uploads a store-compatible artifact; EAS Update distributes compatible JavaScript and assets** (see [OTA updates](10.8.05-codepush-ota-updates.md)). Uploading to a store does not complete review or make the app available to users.

## First Principles

EAS moves the native build from your machine to a managed pipeline:

1. **Native output depends on more than JavaScript source.** Toolchains, dependencies, configuration and signing affect the result. A managed environment reduces machine drift; pin inputs and record artifact provenance. Cloud execution alone does not prove byte-identical output.
2. **A release needs an explicit distribution target.** Simulator, direct-device and store installation require different artifacts or signing. Profiles make those choices reviewable; their names alone do not establish behavior.

## Why It Matters

- **iOS builds need macOS** — EAS hosts the Mac, so Windows/Linux engineers can ship iOS builds
- **Fresh environment** — the builder unpacks your uploaded source archive; verify what that archive contains
- **Profiles encode the release policy** — development tools, internal installation and store artifacts require explicit settings
- **Credentials live in one place** — EAS manages your Apple/Google signing keys instead of a teammate's Keychain
- **Interviews test the release story** — "how does a new build actually get made and shipped?" separates people who've only seen `npm start`

## How It Works

### The build request lifecycle

```text
eas build --platform ios --profile production
        │
        ▼
1. Package source according to the VCS/ignore configuration
2. Upload the project archive and queue the remote build
3. Cloud: unpack → install locked dependencies → prebuild if needed → compile
4. Sign: Apple distribution cert + provisioning profile (managed by EAS)
5. Output: .ipa / .aab artifact + install link
        │
        ▼
eas submit --platform ios  (a separate store-upload step)
```

### Build profiles (`eas.json`)

```json
{
  "cli": { "appVersionSource": "remote" },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "ios": { "simulator": false }
    },
    "development-simulator": {
      "extends": "development",
      "ios": { "simulator": true }
    },
    "preview": {
      "channel": "preview",
      "distribution": "internal",
      "ios": { "simulator": false },
      "android": { "buildType": "apk" }
    },
    "production": {
      "autoIncrement": true,
      "channel": "production"
    }
  }
}
```

These settings produce a device development client, a separate iOS Simulator client, a directly installable preview and a store-compatible production artifact. `distribution: 'internal'` uses direct installation, such as iOS ad hoc provisioning or an Android APK. TestFlight and Play's internal testing track instead receive store-compatible builds. Simulator builds do not install on a physical iPhone. The preview/production channels apply after EAS Update is configured with a runtime-version policy; development clients can load updates from any channel, so a channel field does not isolate them. Build and update jobs must also select consistent application environment values.

### Trace a distribution mismatch

An iOS `preview` build is signed for direct installation on permitted devices. If a teammate then uploads that artifact to TestFlight, the wrong distribution/signing contract cannot be repaired by renaming the profile. Build a store-compatible artifact from the same reviewed source, record its effective build number and submit that exact artifact.

### Credentials & signing

EAS can auto-generate and manage your Apple certificates and provisioning profiles (`eas credentials`) — including push notification keys and Google service credentials. The value: no more "which Mac has the distribution cert" problems, and CI can build signed store artifacts without a human touching Keychain. For teams that prefer control, EAS supports **local credentials** (you keep the files, reference them in the profile) and even fully **local builds** (`eas build --local`) that use your machine's toolchain.

### Versioning & the store

The user-facing `version` is separate from `ios.buildNumber` and `android.versionCode`, which identify builds. With the remote version source above, EAS increments build versions and applies them to the native build; it does not rewrite local `app.json`. A local version source has a different ownership contract. Record effective versions with the artifact and coordinate the runtime-version policy for [OTA compatibility](10.8.05-codepush-ota-updates.md).

## Code — The Commands

```bash
# login + first build (creates project, prompts for credentials)
eas login && eas build:configure

# three-profile builds
eas build --platform android --profile development
eas build --platform ios --profile development-simulator
eas build --platform ios --profile preview
eas build --platform all --profile production   # both stores

# ship the artifact
eas submit --platform ios            # to TestFlight/App Store Connect
eas submit --platform android        # to Play Console; the selected submit profile sets the track

# manage credentials when you must
eas credentials
eas build:list --platform ios         # audit what was built
```

For CI (GitHub Actions): `expo/expo-github-action` + `eas build --platform all --profile production --non-interactive`, with the EAS token in secrets. The build runs on EAS servers; your CI just triggers it and watches for success.

## Real-World Patterns

- **The web engineer's first mobile release** — a web team uses EAS for remote iOS compilation and store upload: `eas build` on cloud, TestFlight via `eas submit`, then store approval. Local Macs are still needed for local iOS builds/simulators; real-device testing remains necessary (matches the [code-sharing decision](10.8.01-react-native-cross-platform.md)).
- **Dev-client iteration loop** — install a development build once (it contains the native binary), then iterate JS via Fast Refresh / [EAS Update](10.8.05-codepush-ota-updates.md) without rebuilding native every change.
- **Release trains** — production profile with `autoIncrement`, triggered from a Git tag by CI, artifact stored in the build list for rollback reference.
- **Docita anchor (web analog)** — the healthcare stack deploys web via its [CI pipeline](../../40-platform/40.3-ci-cd/INDEX.md); a mobile addition would trigger EAS from the same pipeline, gated by the same review rules — the pipeline *pattern* transfers, the tool changes.

## Real-World Use Cases

- **Web team shipping native** — EAS Build removes the Xcode/Gradle local-setup tax; profiles encode signing so releases are `eas build --profile production`.
- **CI-built releases** — build on tag, submit via EAS Submit, distribute TestFlight builds per merge to main (→ 10.8.06).

## Common Mistakes

- Treating EAS Build like `npm run build` — it's a **native** compile; a native config change (new library with native code, `app.json` icons/splash) forces a **new build**, not an OTA update
- Forgetting `autoIncrement` — stores reject an upload whose buildNumber/versionCode didn't increase
- Building `production` for every internal test — preview defines internal distribution and may still use a release/minified build; developmentClient enables a development build
- Committing credentials or letting every dev run `eas credentials` ad hoc — let EAS manage them centrally (or use local creds deliberately, documented)
- Ignoring the dev-client distinction — `expo start` with Expo Go can't exercise custom native modules; that's what development builds are for
- No `--non-interactive` in CI — interactive credential prompts hang pipelines

## Best Practices

- Keep named build profiles in `eas.json`; separate simulator and device targets where needed
- Pin your Expo SDK + `expo` CLI versions; upgrade deliberately (SDK majors change the native project)
- Use a controlled release lane that records source, toolchain, profiles and artifact IDs; CI on a release tag is one implementation
- Set `autoIncrement: true` on production and coordinate the version source across parallel pipelines or outside builds; it is not a blanket collision guarantee
- Keep native config (`app.json`, `eas.json`) reviewable in PRs — it's infrastructure
- Use `eas submit` in the same CI job as the successful build for a one-command release, but keep a manual approval step before store submission
- Document the SDK-upgrade path (Expo's `npx expo-doctor`, `npx expo install --fix`) so native drift doesn't build up

## Summary

1. **EAS Build moves the native toolchain to the cloud** — `eas build` produces signed `.ipa`/`.aab` artifacts without local Xcode/Android Studio, so the developer does not need a local Mac for the cloud build (the remote iOS builder still uses macOS/Xcode)
2. **Build profiles are release policy as code** — direct preview installation, simulator installation and store testing are distinct targets
3. **Fresh environments expose machine drift** — archive contents and dependency/toolchain inputs still need verification
4. **EAS Build, EAS Submit, and EAS Update are three separate services** — the artifact is built by one, shipped to stores by another, and hotfixed OTA by the third
5. **Version bumps and credentials are mechanized** — `autoIncrement` handles buildNumber/versionCode; EAS manages signing keys instead of a teammate's Keychain

# Expo EAS Build — Cloud Builds, Profiles & Submission

> `npm run build` can package JavaScript, but a store release also needs platform toolchains, native configuration and signing. EAS Build runs that native pipeline in a managed cloud environment; EAS Submit uploads the resulting artifact to a store.

## Definition

**EAS Build** is Expo's hosted service for compiling React Native or Expo source into an installable native artifact. A build profile supplies the target configuration; the job prepares dependencies and native projects, compiles with Xcode or Gradle and signs when required. The result can be an iOS `.ipa`, Android `.aab`/`.apk`, or simulator artifact.

> **Textbook Definition:** EAS Build produces a native application artifact from a source archive and configured build environment. Platform settings, native dependencies, distribution target and signing credentials determine what that artifact can run on and how it can be installed.

Build, submit and update are separate operations:

| Operation | Result | What it does not mean |
| -------------- | ---------------------------------------------------------- | --------------------------------------- |
| **EAS Build** | Compiled native artifact | The store has received or approved it |
| **EAS Submit** | Artifact uploaded to App Store Connect or Play Console | The release is available to all users |
| **EAS Update** | Compatible JavaScript/assets offered to installed binaries | A native module or permission was added |

## First Principles

A native artifact depends on more than JavaScript: the source archive, dependency lockfile, Expo/React Native versions, platform toolchain, native configuration and signing identity all affect it. A fresh cloud machine removes reliance on one developer's local state, but a managed build alone does not prove byte-for-byte reproducibility or correct runtime behavior. Record the source revision, build profile, effective versions and artifact ID.

## Follow one release artifact through the build

### Choose the native project owner

EAS supports both Expo-generated projects and existing React Native projects. If the `ios/` or `android/` project is absent, Expo Prebuild can generate it from app configuration and config plugins before native compilation. If a native project is checked in, its Xcode/Gradle changes are build inputs. Keep manual native edits in a reproducible ownership path; generated output that is discarded and regenerated must be expressible through configuration or plugins.

Expo Go is a prebuilt client with a fixed native module set. A **development build** is your app's own native binary with development tools and selected native libraries. Use it when Expo Go cannot load a custom native module.

### Encode targets in `eas.json`

```json
{
  "cli": { "appVersionSource": "remote" },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal"
    },
    "simulator": {
      "extends": "development",
      "ios": { "simulator": true }
    },
    "preview": {
      "distribution": "internal",
      "android": { "buildType": "apk" }
    },
    "production": {
      "autoIncrement": true,
      "environment": "production",
      "channel": "production"
    }
  }
}
```

Profiles are named configuration, not magic release tiers. `distribution: "internal"` produces direct-install builds, such as an Android APK or iOS ad hoc/enterprise build. A simulator artifact is for an iOS Simulator, not a physical iPhone. TestFlight and Play testing tracks use store-compatible artifacts. The `channel` matters only when the app is configured for EAS Update; it routes update requests and does not change the native artifact's signing or distribution type.

Set the EAS environment for each profile deliberately. Build-time variables can change app configuration, bundle identifiers or API endpoints; an update must use the environment intended for the binary it targets. SDK 55 and later also require an explicit `--environment` when publishing an update.

### Build once, then submit that artifact

```bash
# Configure the project and credentials interactively once.
eas build:configure
eas credentials

# A production build can run from Linux/Windows because EAS hosts the toolchain.
eas build --platform all --profile production --non-interactive

# Submit the exact successful build ID recorded by CI.
eas submit --platform ios --id <ios-build-id> --non-interactive
eas submit --platform android --id <android-build-id> --non-interactive
```

Cloud iOS builds do not require a local Mac. Local iOS compilation and simulators still require macOS, and device testing remains necessary. A profile can use EAS-managed credentials or credentials the team manages itself; keep ownership, access and rotation documented rather than passing certificates among developer machines.

The user-facing app `version` is distinct from `ios.buildNumber` and `android.versionCode`, which stores use to distinguish builds. With `appVersionSource: "remote"`, EAS stores and increments build numbers remotely; it applies the effective values to the artifact without rewriting local `app.json`. Coordinate parallel pipelines and any local builds against that shared version source. An auto-increment setting prevents some duplicate-version mistakes but is not a concurrency guarantee.

### Treat preview and production as different contracts

An iOS preview build signed for direct installation on registered devices cannot be made store-compatible by renaming its profile. Build the store-targeted artifact from the reviewed source, retain its artifact ID, and submit that exact result. Similarly, a change to a native module, permission, entitlement, icon or native configuration needs a new binary; an OTA update can only replace code and assets the installed runtime can already support.

## Automate the repeatable steps; gate the release decision

CI can trigger a build from a reviewed tag or commit, store the resulting IDs and symbols, then submit the same artifacts. EAS can auto-submit a successful build, but the team should still make approval, track selection and public rollout explicit release decisions.

```bash
# Example release job after tests and review have passed.
eas build --platform all --profile production --non-interactive
# Capture build IDs from the EAS result; do not submit an implicit "latest" build.
eas submit --platform ios --id "$IOS_BUILD_ID" --non-interactive
eas submit --platform android --id "$ANDROID_BUILD_ID" --non-interactive
```

For a reproducible job, install from the lockfile, pin compatible Node/Expo and native toolchains, define EAS environment variables explicitly, and retain logs, source revision and artifact metadata. If the build succeeds locally but fails in EAS, compare the uploaded archive and locked dependencies before blaming the cloud builder.

## Summary

EAS Build compiles and signs native artifacts from a project archive; EAS Submit uploads a chosen artifact, while store review and rollout determine availability. Profiles should describe the real install target and environment. Preserve source, effective version, credentials ownership and artifact identity so the release can be audited and reproduced.

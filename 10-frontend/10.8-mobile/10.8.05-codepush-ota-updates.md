# Over-the-Air Updates — EAS Update, CodePush & the JS/Native Boundary

> OTA updates let you ship **JavaScript/asset changes instantly** to installed apps — no App Store/Play review, no new binary. This file covers how OTA works under the hood (bundle URL + runtime version matching), EAS Update vs legacy CodePush (App Center), what can and cannot go OTA, update channels and rollouts, and the release-safety discipline that keeps OTA from becoming a foot-gun.

## Definition

A React Native release has two layers: the **native binary** (compiled .ipa/.aab — UIKit/Android views, native modules, the Hermes runtime) and the **JS bundle** (your app code, fetched at runtime). An OTA update replaces only the JS bundle + assets on devices that already run a compatible native binary. The app checks an update server on launch, downloads a new bundle when one exists for its runtime version, and swaps it — the user sees the new code without reinstalling.

**EAS Update** is Expo's OTA service (the modern path); **CodePush** was Microsoft's App Center service that pioneered the pattern for bare React Native. The mechanics are the same; EAS Update is what Expo SDK apps use today.

## Why It Matters (TL;DR)

- **Store review takes days** — OTA fixes a typo or a JS crash in minutes, not after an approval cycle
- **No install friction** — users on an old binary get the fix without updating from the store
- **Rollout control** — push to 10% first, watch crash-free rate, ramp to 100%
- **Instant rollback** — a bad update is *reverted*, not re-reviewed
- **Interviews love the boundary question** — "what can you fix OTA, and what forces a store build?" is the whole discipline in one question

## How It Works

### The runtime-compatibility contract

```text
Installed binary:  native code + runtime version R (e.g. "1.2.3")
Update server:     holds bundles tagged with the runtime version they target

app launch → check server: "any update for runtime R on channel 'production'?"
  ─ yes → download bundle → verify → swap on next reload
  ─ no  → run bundled JS (the version that shipped with the binary)
```

The critical rule: **an OTA bundle is only valid for binaries whose runtime version it matches.** If you add a native module (or bump the Expo SDK), the new JS won't run on old binaries — the update is rejected and the app keeps its bundled JS until users update from the store.

### EAS Update concepts

- **Channel** — a named update target (`production`, `staging`, `internal`). A build's `runtimeVersion` + channel determine which updates it receives. You point the *production* build at the `production` channel; push an update to that channel and every production app picks it up.
- **runtimeVersion** — replaces the old fragile "native version must match" heuristics. Set it to your `app` version (e.g. `"1.2.3"`) or an automatic policy tied to native fingerprints so the server knows which binaries can run which bundles.
- **Update groups & rollouts** — a rollout (`eas update --rollout 10`) serves an update to 10% of clients on that channel, ramping without a full push.

```bash
# build a bundle and push it to a channel
eas update --channel production --message "fix checkout crash"

# staged rollout (10% → observe → 100%)
eas update --channel production --rollout 10
eas update --channel production --rollout 100

# audit / rollback
eas update:list --channel production
eas update:rollback --channel production   # revert to last known-good
```

## Code — What Can Go OTA vs What Forces a Store Build

```text
OTA-SAFE (JS/asset layer):                    STORE BUILD REQUIRED (native layer):
  • UI fixes, styling, layout                    • New native module / library
  • Business logic, validation                   • Expo SDK major upgrade
  • API client changes, env config               • New permissions (iOS Info.plist)
  • JS-level bug fixes, crash patches            • Deep-link scheme / app icon / splash
  • Assets: images, fonts, l10n strings          • Background modes / push config
  • Performance work in JS/React                 • Anything touching the native binary
```

The interview one-liner: *"If the change is expressible in JavaScript or assets, it can go OTA. If it needs a new capability from the OS — a permission, a native module, an SDK bump — it needs a new binary and a store review. Mixing the two is how teams ship 'OTA' updates that crash old clients."*

## Real-World Patterns

- **The hotfix lane** — a JS crash ships to 100% of users by mistake → push a revert OTA in minutes, then fix properly and ship the next store build on the normal train. OTA is the emergency brake; the store build is the permanent fix.
- **Release-notes discipline** — a store release *and* an OTA can target the same channel; keep a manifest (binary version → OTA version → what's live) so "what are users actually running?" has an answer.
- **Docita anchor (web analog)** — the web stack's deploy pipeline ([CI/CD](../../40-platform/40.3-ci-cd/INDEX.md), zero-downtime deploys) is the same *release-safety* story OTA brings to mobile: fast rollouts, instant rollback, staged percentages. Mobile just adds the store-review latency that makes OTA valuable.

## Common Mistakes

- **Pushing native-dependent JS as OTA** — the classic: bump the Expo SDK, push JS to old binaries, crashes everywhere. runtimeVersion exists to prevent exactly this — respect it
- **No channel separation** — pushing a staging update to `production` by pointing the wrong channel
- **OTA for everything** — skipping store builds entirely means native upgrades pile up until one is forced, and the gap becomes unmanageable
- **No rollback plan** — pushing to 100% with no monitoring; OTA's superpower is 10%→100% with a crash-free check between
- **Forgetting assets** — a large asset bundle over a slow connection is a worse experience than waiting for a store update; watch bundle size
- **Confusing EAS Update with EAS Build** — one ships JS over the air, the other compiles native artifacts; interviewers probe whether you can say which is which

## Best Practices

- Set `runtimeVersion` deliberately and bump it only on native-affecting releases
- Use channels that mirror your environments (`development` → `staging` → `production`), and point each build profile at its channel
- Roll out in stages: 10% → monitor crash-free rate + adoption → 100%
- Keep OTA bundles small (slim the JS bundle; assets via the update or a CDN)
- Version-stamp every update message; keep a release manifest for "what's live where"
- Gate native upgrades on a real store release — never try to force new native code through OTA
- Test the *update path itself*: fresh install (bundled JS) and updated install (OTA JS) both need to boot cleanly

## Cheat Sheet

```text
OTA = JS bundle + assets swap at runtime; native binary unchanged
MATCH: bundle runtimeVersion must equal the binary's → else rejected
CHANNELS: development / staging / production — builds point at their channel
ROLLOUT: eas update --channel production --rollout 10 → 100 (watch crash-free)
ROLLBACK: update:rollback — instant revert, no store wait
OTA-SAFE: JS logic, UI, assets, config | STORE-ONLY: native modules, permissions, SDK bumps
```

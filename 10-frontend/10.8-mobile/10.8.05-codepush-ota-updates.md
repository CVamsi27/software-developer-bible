# Over-the-Air Updates — EAS Update, CodePush & the JS/Native Boundary

A JavaScript hotfix can reach an installed mobile app only if its native runtime can execute it. Compatibility, rollout and device adoption determine whether an over-the-air update repairs the affected users.

```bash
# Make an update available to a small cohort, then inspect its health.
eas update --channel production --environment production --rollout-percentage=10 --message "checkout fix"
eas update:list --channel production
```

## Definition

A React Native release has a **native binary** (`.ipa` or `.aab`) and a JavaScript bundle. The binary supplies the native modules and runtime available to the JavaScript. An **over-the-air (OTA) update** delivers JavaScript and assets to an installed binary that can run them. It can fix compatible application code without reinstalling the native app; it cannot add a native module, permission or entitlement that the binary does not contain.

> **Textbook Definition:** An over-the-air update distributes application code and assets to an already installed compatible native runtime. It cannot introduce native capabilities absent from that binary; compatibility and rollback policy constrain which update a device may apply.

**EAS Update** is Expo's current update service for apps using `expo-updates`, including existing React Native projects. Microsoft's hosted CodePush service ended on **March 31, 2025**. Microsoft released a standalone server, then archived both that server and the React Native CodePush client on **May 20, 2025**; the repositories are read-only and Microsoft provides no support for the standalone code. Treat CodePush as a legacy system or a self-maintained fork, not as an actively supported hosted service. Moving an installed app from CodePush to EAS Update requires replacing the update integration and shipping a new native binary; existing clients cannot change update providers through the old OTA channel.

## First Principles

An installed binary fixes the native capabilities available to JavaScript — replacing its bundle cannot add a missing module, permission, or entitlement, so every update needs a compatibility contract with the binary, not just a release label. Devices also choose when to connect, download, and reload: publishing a fix changes what the service offers, never what every client runs. Keep a usable cached or embedded fallback and measure adoption separately from publication.

## How It Works

### 1. Follow One Update from Publish to Device

```text
Installed binary:  native code + platform + runtime version R
EAS Update:        update branch linked to a build's channel

publish → choose channel/branch + platform + runtime version
app launch → check for an eligible update
  ─ yes → download → verify → apply according to the app's update policy
  ─ no / offline → keep using an eligible cached update or embedded bundle
```

The runtime version is the compatibility label connecting an update to native code in a build. EAS also targets a platform and the build's channel, which maps to an update branch. These labels prevent some mismatches; they do not inspect application behavior or prove an update works. If native code changes, use a new runtime version and build. Reusing an old value can allow JavaScript that calls a missing native capability to reach an incompatible binary.

**Choose the runtime policy deliberately.** An Expo `runtimeVersion` can be managed manually or derived by a policy. An `appVersion` policy works when every native change also bumps the app version; Expo's `fingerprint` policy derives compatibility from native-affecting inputs and can require more frequent builds. Confirm the runtime value in the actual binary and update metadata before publishing. No naming convention can compensate for a missed native change.

**Publish to a controlled channel:**

```bash
# SDK 55 and later require the named EAS environment for `eas update`.
eas update --channel production --environment production --message "fix checkout crash"

# Make an update available to a small cohort, then inspect its health.
eas update --channel production --environment production --rollout-percentage=10 --message "checkout fix"
eas update:edit                    # choose the update and set a larger percentage
eas update:list --channel production
eas update:revert-update-rollout   # revert an active per-update rollout
```

EAS supports per-update rollouts and branch-based rollouts. They have different control points: `eas update:edit` changes the percentage for one update; `eas channel:rollout` shifts a channel between branches. During a branch rollout, publish with `--branch`; `--channel` cannot choose between the channel's two candidate branches. End an active per-update rollout before publishing another update for that runtime on its branch. Check the [current EAS CLI guide](https://docs.expo.dev/eas-update/rollouts/) before automating commands.

For SDK 55 and later, `eas update` requires `--environment`; use the named environment configured for the target build. Older SDK versions may use the earlier command contract, so follow the installed SDK's guide when maintaining a legacy app.

Publishing makes an update eligible; it does not install it immediately on every device. Devices may be offline, delay their next check or need a later launch to apply the downloaded bundle. A rollback changes what the service offers to eligible clients; it cannot recall an already running binary or instantly repair a device that cannot reach the service. Keep the embedded bundle viable and monitor update downloads, launches, errors and the binary/runtime versions actually in use.

### 2. Choose OTA or a New Native Build

| Change | Release path |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Compatible JavaScript, styling or assets | OTA only if runtime compatibility and store policy both permit the change |
| New native module, native SDK, permission, entitlement, URL scheme or native configuration | Build and distribute a new binary |
| Switching from CodePush to EAS Update | Replace the integration, build a new binary containing `expo-updates`, and distribute it through the stores |

An Expo migration cannot be completed by changing the server URL: the installed native binary must contain the EAS update client and configuration. Expo's [migration guide](https://docs.expo.dev/eas-update/codepush/) recommends moving to a supported SDK, removing CodePush, configuring EAS Update, then rebuilding and resubmitting. Older apps may need a separately planned migration because the current guide does not cover every legacy React Native/Expo combination.

### 3. Add End-to-End Verification When the Threat Model Requires It

EAS Update supports optional end-to-end code signing: a private key signs the update, and a certificate embedded in the binary lets the client verify it before applying it. Keep the private key outside source control, restrict who can publish, and plan key rotation. Changing the embedded certificate requires a new binary/runtime. Check the current [EAS code-signing guide](https://docs.expo.dev/eas-update/code-signing/) for plan eligibility and setup; signing does not replace authorization, staged rollout or store-policy review.

### 4. Test the Release and Its Recovery Path

For a real release, verify the staged update on each intended platform/runtime, then observe health before increasing exposure. Exercise a compatible update, a wrong-runtime update, a no-update response, offline launch, interrupted download, a bad update followed by rollback, and a device that crashes before its next normal check. Track binary version, runtime version, update ID, channel/branch and update launch outcome together. Publishing, downloading and successfully running are different states.

## Summary

OTA is a constrained release path for code that an installed native runtime can execute and platform rules permit. Runtime compatibility, platform and channel decide eligibility; devices decide when to fetch and apply. Stage and observe updates, preserve an embedded recovery path, and ship a new binary for native changes or provider migrations. CodePush is now legacy infrastructure; EAS Update is the maintained Expo path.

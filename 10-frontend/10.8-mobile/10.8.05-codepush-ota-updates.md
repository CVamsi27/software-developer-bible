# Over-the-Air Updates — EAS Update, CodePush & the JS/Native Boundary

> A JavaScript hotfix can reach an installed mobile app only if its native runtime can execute it. Compatibility, rollout and device adoption determine whether an over-the-air update repairs the affected users.

## Definition

A React Native release has two parts. The **native binary**, such as `.ipa` or `.aab`, contains native UI code, native modules and the JavaScript runtime. The **JavaScript bundle** contains application code. An **over-the-air (OTA) update** replaces the bundle and assets on devices that already have a compatible native binary. The app checks an update server, downloads an update for its runtime version and applies it according to its update policy. Users can receive that code without reinstalling the native app.

> **Textbook Definition:** An over-the-air update distributes application code and assets to an already installed compatible native runtime. It cannot introduce native capabilities absent from that binary; compatibility and rollback policy constrain which update a device may apply.

**EAS Update** is Expo's update service for compatible Expo projects. **CodePush** was Microsoft's App Center service for React Native. Microsoft retired the hosted App Center service on **March 31, 2025**; Microsoft published a standalone CodePush server for teams that choose to host and maintain the service themselves. Similar delivery goals do not make the clients, protocols or recovery behavior interchangeable. Expo documents EAS Update as its migration path; select a provider that matches the app's native runtime and support requirements.

## First Principles

An installed binary fixes the native capabilities available to JavaScript. Replacing its bundle cannot add a missing native module, permission or runtime. Therefore each update needs a compatibility contract with the binary, not just a release label.

Devices also choose when to connect, download and reload. Publishing a fix changes server availability; it does not instantly change every installed client. Keep a usable cached/embedded fallback and measure adoption separately from publication. Technical compatibility does not establish store-policy compliance:

| Platform | Policy boundary | Engineering consequence |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Apple App Store | Guideline 2.5.2 restricts downloaded code that introduces or changes app features or functionality. | Do not treat a runtime-compatible bundle as automatic approval to ship a feature change. Check the current guideline and provider guidance for the exact release. |
| Google Play | The policy prohibits self-updating and downloading executable code outside Play. Its interpreted-language provision still requires the loaded code to comply with Play policies. | Do not download native executables through an OTA service; review the current policy and app architecture before enabling interpreted updates. |

These are policy constraints, not a technical compatibility check. Recheck the linked rules when designing a release process.

## Why It Matters

- **Separate delivery path** — a compatible update can be published without a new binary; users still need to download and apply it
- **No install friction** — users on an old binary get the fix without updating from the store
- **Rollout control** — push to 10% first, watch crash-free rate, ramp to 100%
- **Rollback publication** — publish a rollback/revert; clients must still fetch and apply it
- **Interviews love the boundary question** — "what can you fix OTA, and what forces a store build?" is the whole discipline in one question

## How It Works

### The runtime-compatibility contract

```text
Installed binary:  native code + runtime version R (e.g. "1.2.3")
Update server:     holds bundles tagged with the runtime version they target

app launch → check server: "any update for runtime R on channel 'production'?"
  ─ yes → download bundle → verify → swap on next reload
  ─ no / offline → run an eligible cached update, or the embedded bundle
```

The critical rule: **EAS selects updates matching platform, runtime version and the configured channel/branch. Matching labels are necessary, not proof that the application works.** A correctly changed runtime version prevents old binaries from receiving incompatible updates. If you reuse the old runtime version by mistake, the server cannot inspect the JS and discover missing native capabilities: it can serve the update and the app may crash.

### EAS Update concepts

- **Channel** — a named update target (`production`, `staging`, `internal`). A build’s platform, `runtimeVersion` and channel help determine eligible updates. You point the *production* build at the `production` channel; compatible clients can receive its updates according to branch mapping, rollout and their download/apply policy.
- **runtimeVersion** — replaces the old fragile "native version must match" heuristics. Set it to your `app` version (e.g. `"1.2.3"`) or an automatic policy tied to native fingerprints so the server knows which binaries can run which bundles.
- **Update groups & rollouts** — a per-update rollout (`eas update --rollout-percentage=10`) makes an update available to a selected percentage of eligible clients on the target branch. Increase the percentage after checking crash and adoption data; publishing to a cohort does not mean every device in it has applied the update.

```bash
# build a bundle and push it to a channel
eas update --channel production --environment production --message "fix checkout crash"

# staged rollout (10% → observe → 100%)
eas update --channel production --environment production --rollout-percentage=10 --message "checkout fix"
eas update:edit  # select that update, then increase its rollout percentage

# audit / rollback
eas update:list --channel production
eas update:revert-update-rollout  # revert an active per-update rollout
```

Per-update rollouts differ from branch-based rollouts (`eas channel:rollout`). During a branch rollout, publish with `--branch`; `--channel` is ambiguous because the channel has two candidate branches. Finish or revert a per-update rollout before publishing another update for that runtime on its branch.

For Expo SDK 55 and later, EAS Update requires `--environment`; use the same named environment configured for the target build. Older SDK versions may use the earlier command contract, so follow the installed Expo SDK's guide when maintaining a legacy app.

Rollback is not an instant fleet-wide recall: offline devices retain their current update, download/apply timing depends on configuration, and a crash can prevent normal update checks. Test embedded fallback, error recovery and rollback on each supported runtime.

## Code — What Can Go OTA vs What Forces a Store Build

```text
POTENTIAL OTA CANDIDATE (if policy and runtime allow):  STORE BUILD REQUIRED (native layer):
  • Compatible bug fixes and assets               • New native module / library
  • JS changes that do not add prohibited features • Native SDK or Expo SDK change
  • API-client changes matching backend contract   • New permissions or entitlements
                                                    • URL schemes, icons, native config
                                                    • Background modes / push capability
```

The interview one-liner: *"An OTA candidate must match the installed native runtime and backend contract, and comply with the platform's downloaded-code rules. A native capability change needs a new binary and store submission. Even compatible JavaScript is not automatically eligible for OTA delivery."*

## Real-World Patterns

- **The hotfix lane** — a JS crash ships to 100% of users by mistake → publish a compatible revert and monitor which devices actually apply it. A corrected JS-only change may remain an OTA fix; native repairs require another binary. Offline or crash-looping devices need a tested recovery path.
- **Release-notes discipline** — a store release *and* an OTA can target the same channel; keep a manifest (binary version → OTA version → what's live) so "what are users actually running?" has an answer.
- **Web deployment comparison** — [CI/CD](../../40-platform/40.3-ci-cd/INDEX.md) gates, staged rollout and monitoring also apply to OTA delivery. Recovery differs: an installed offline device cannot receive a replacement immediately.

## Real-World Use Cases

- **Hotfix delivery** — publish a compatible JS fix independently of a new binary, then measure successful adoption. Native changes require a new binary; downloaded-code policy remains a separate constraint.
- **Staged update rollout** — expose a policy-eligible update to a small cohort, check crash and adoption signals, then increase exposure. Keep the rollback command and offline-device recovery path in the runbook (see [canary releases](../../40-platform/40.3-ci-cd/03-releases-and-metrics/40.3.3.01-blue-green-canary.md)).

## Common Mistakes

- **Pushing native-dependent JS as OTA** — the classic: bump the Expo SDK, push JS to old binaries, crashes everywhere. runtimeVersion exists to prevent exactly this — respect it
- **No channel separation** — pushing a staging update to `production` by pointing the wrong channel
- **OTA for everything** — skipping store builds entirely means native upgrades pile up until one is forced, and the gap becomes unmanageable
- **No rollback plan** — pushing to 100% with no monitoring; OTA's superpower is 10%→100% with a crash-free check between
- **Forgetting assets** — a large asset bundle over a slow connection is a worse experience than waiting for a store update; watch bundle size
- **Confusing EAS Update with EAS Build** — one ships JS over the air, the other compiles native artifacts; interviewers probe whether you can say which is which

## Best Practices

- Set `runtimeVersion` deliberately and bump it only on native-affecting releases
- Use channels that mirror your environments (`development` → `staging` → `production`), and point each build profile at its channel
- Roll out in stages: 10% → monitor crash-free rate + adoption → 100%
- Keep OTA bundles small (slim the JS bundle; assets via the update or a CDN)
- Version-stamp every update message; keep a release manifest for "what's live where"
- Gate native upgrades on a real store release — never try to force new native code through OTA
- Test the *update path itself*: fresh install (bundled JS) and updated install (OTA JS) both need to boot cleanly

## Summary

1. **OTA replaces only the JS bundle + assets** — the native binary is unchanged; publication and device adoption are separate events
2. **The runtime-version contract gates compatibility** — an update only applies to binaries whose `runtimeVersion` it matches; native changes force a store build
3. **Channels + staged rollouts bound risk** — push to 10%, watch adoption/crashes, ramp; rollback still requires devices to receive and apply the replacement
4. **Choose a supported update service** — App Center CodePush hosting retired in 2025; self-hosting CodePush means owning its operations, while EAS Update serves compatible Expo projects
5. **Discipline matters more than speed** — technical compatibility, tests and rollout monitoring remain necessary; eligible OTA delivery does not exempt the app from store policy

# App-Store Release Automation — Review, Rollout & Recovery

A successful upload is not a release, and a paused rollout cannot remove a broken binary already installed on a phone. Follow the exact signed artifact through review, availability, adoption and repair.

```bash
# CI runs tests, then records the IDs returned by the successful build.
eas build --platform all --profile production --non-interactive

# Submit those exact artifacts; avoid selecting an implicit "latest" build.
eas submit --platform ios --id "$IOS_BUILD_ID" --non-interactive
eas submit --platform android --id "$ANDROID_BUILD_ID" --non-interactive
```

## Definition

Mobile release automation coordinates tests, native builds and signing, store submission, approval, staged availability and post-release observation. It makes those steps repeatable, but installed binaries persist until a user updates or a separate compatible repair reaches the device.

> **Textbook Definition:** A mobile release pipeline promotes a signed application artifact through validation, store review, controlled distribution and health monitoring. Because client versions remain installed independently, recovery may require a feature control, a policy-compliant compatible update or a higher-version corrective binary.

## First Principles

Track three separate facts: which artifact was built, which artifact the store approved, and which versions users actually installed. A build ID and source revision connect them — “submitted” is not “approved,” and “available” is not “adopted.” If health drops during rollout, stop further exposure first, then repair installed clients through a remote flag, an eligible OTA update, or a new binary — each gated by connectivity, compatibility, store policy, and adoption.

## 1. Trace One Artifact from Source to Users

```text
reviewed source → tests → build/sign → retain artifact ID and symbols
                → upload that exact artifact → store checks/review
                → testing or production track → observe adoption and health
failure → stop expansion → contain the feature → deliver and measure repair
```

**Apple App Store.** EAS Submit uploads an iOS artifact to App Store Connect. You can distribute it to TestFlight testers before review, then submit the selected build for App Review. After approval, choose immediate release or **phased release**. Apple gradually offers the update to a random share of eligible users with automatic updates enabled over seven days: 1%, 2%, 5%, 10%, 20%, 50%, then 100%. Anyone can still download it manually, so the percentage is not a hard cap on installations. You can pause the automatic phased release for up to 30 total days; users who already installed remain on that version.

**Google Play.** EAS Submit uploads the artifact to the track configured by the submission profile. Internal or closed testing can validate a candidate before production. Play staged rollout applies to updates, not an app's first publication; for an eligible update, select the initial percentage and increase it as health evidence supports. Halting prevents more users from receiving that release through the staged rollout, but does not downgrade devices that already installed it. Account checks and policy review can still delay availability.

These controls have different store-specific semantics. Do not describe either percentage as the share of all devices currently running the binary; measure installed-version adoption separately.

**Automate the artifact path, retain a human release decision:**

```bash
# CI runs tests, then records the IDs returned by the successful build.
eas build --platform all --profile production --non-interactive

# Submit those exact artifacts; avoid selecting an implicit "latest" build.
eas submit --platform ios --id "$IOS_BUILD_ID" --non-interactive
eas submit --platform android --id "$ANDROID_BUILD_ID" --non-interactive
```

Configure store credentials and the intended track in the submission profiles. Before the job starts, gate it on the tests and device checks appropriate to the change, a valid build number, reviewed release notes and required store metadata. Store promotion can remain a separate approval step: a person should confirm the candidate and health evidence before public rollout. Build, submission and promotion should all point back to the same source and artifact IDs.

Retain the JavaScript source map and native symbols for each binary, alongside its version, commit, build ID and any OTA update ID. Without matching symbols, native and minified JavaScript crash reports may be difficult to interpret.

## 2. Make Rollback a Repair Plan

When crash or error rates rise, group reports by binary version, operating-system version, device class and OTA update. Halt further store rollout, disable the affected feature if a safe server-side control exists, then choose a compatible OTA repair or a new binary. Verify the exact candidate on affected platforms and runtimes before resuming distribution.

Mobile clients may stay on older versions for weeks or longer. Keep APIs and stored data backward-compatible until adoption evidence supports removal. If the product needs a minimum-version policy, define a grace period and recovery path for users who cannot update immediately.

## Summary

A safe mobile release ties tests and store actions to one signed artifact, then measures actual client adoption. Apple phased release and Play staged rollout limit further exposure in different ways; neither recalls installed binaries. Plan containment and repair separately, preserve symbols and version identity, and keep older clients compatible while users catch up.

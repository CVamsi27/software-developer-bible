# App-Store Release Automation — Release Trains, Store Review & Rollout Safety

> Shipping a mobile release is a **train, not a push**: code is frozen, a native build is made and signed, it goes through App Store / Play review (days, not minutes), and rollout is staged with monitoring and a rollback path. This file covers the end-to-end automated release pipeline — CI-triggered builds, store submission (TestFlight, Play internal), review management, staged/progressive rollouts, phased releases, and the release-readiness checks that keep a train from derailing.

## Definition

Mobile releases can remain installed for a long time. Three delays shape the release process: the store must review the build, users install approved updates on their own schedule, and installed binaries cannot silently be replaced with an older release. Recovery may require a new binary or a remote control that disables the affected feature. Release automation makes builds, checks, rollout and monitoring repeatable. It can support recovery, but it cannot give installed mobile binaries the immediate replacement behavior of a typical web deployment.

The pieces: **build** (CI compiles + signs the binary), **submit** (upload to App Store Connect / Play Console), **review** (store-side, managed via APIs), **rollout** (staged percentages / phased release), **monitor** (crash-free sessions, adoption per version), **rollback** (remote disable, a higher-version corrective binary, or [OTA](10.8.05-codepush-ota-updates.md) for JS issues).

## First Principles

Release automation turns store submission into a pipeline:

1. **The release is a signed artifact plus metadata**: build → signing → screenshots/metadata → phased rollout — each step is scriptable (fastlane/EAS submit); manual steps are the release-day risk (→ 40.3.2.03's pipeline philosophy, mobile edition).
2. **Phased release + crash monitoring is the safety net**: store-managed percentage ramps with ability to halt — the rollback story is *store-side* because binaries can't be recalled, only superseded.

## Why It Matters

- **Review is the scheduling constraint** — a Monday feature needs submission by Thursday to make the weekly train
- **Adoption is lagging** — a critical fix only reaches users as fast as they update; that gap is what [OTA](10.8.05-codepush-ota-updates.md) exists to close
- **Rollout is a decision, not a default** — staged % release bounds the blast radius of a bad build
- **Automation removes the human bottleneck** — the same CI that tests the app can build, submit, and promote
- **Interviews test release ownership** — "walk me through shipping a mobile release safely" is the senior-mobile question

## How It Works

### The release train

```text
Git tag v1.2.3 ──▶ CI: test (Jest/RNTL) ─▶ EAS Build (production profile)
        │                                       │
        ▼                                       ▼
   changelog                            artifact (.ipa/.aab) + signed
        │                                       │
        ▼                                       ▼
   eas submit ──▶ App Store Connect / Play Console
        │                                       │
        ▼                                       ▼
   TestFlight beta / Play internal ──▶ store review (human, hours–days)
        │                                       │
        ▼                                       ▼
   approve ──▶ staged rollout (10% → 50% → 100%) or phased release
        │                                       │
        ▼                                       ▼
   monitor: crash-free %, adoption, ratings ──▶ rollback if bad
```

### Store-specific mechanics

**iOS (App Store Connect):** `eas submit --platform ios` uploads to TestFlight first — TestFlight is a beta-distribution option, not a required testing stage before App Review. You then submit the build for App Review from the console or via the App Store Connect API. Once approved you control **phased release** (Apple's built-in 1%→100% over days) or release at once. App Review has appeal/expedite paths for urgent fixes, but you don't rely on them.

**Android (Play Console):** `eas submit --platform android` uploads to the track selected in the submit profile. Internal testing is a useful optional first stage; first-time submission, account checks and policy review can still delay availability. Promote the artifact through the testing tracks appropriate for your team, then **production**; the **production** rollout can be staged in percentage increments (e.g., 10% over 7 days) from the console or via the Google Play Developer API. Both stores can apply automated checks and human review; do not promise approval time from a platform stereotype.

### The automation layer

```bash
# CI job on a release tag — build then submit in one pipeline
eas build --platform all --profile production --non-interactive
eas submit --platform ios --profile production   # to TestFlight
eas submit --platform android --profile production  # track comes from eas.json submit profile

# promote on the store side (App Store Connect API / Play Developer API)
#   iOS:  TestFlight → submit for review → phased release ON
#   Play: chosen testing track → production (10% staged)
```

Release-readiness gates that run *before* the tag is cut: full test suite green, [E2E on simulators](10.8.03-testing-react-native-apps.md), changelog written, store assets (screenshots, privacy labels) updated, and a `buildNumber`/`versionCode` bump ([autoIncrement](../../10-frontend/10.8-mobile/10.8.04-expo-eas-builds.md)) so the store accepts the artifact.

## Real-World Patterns

- **The weekly cadence** — most product teams run a 1–2 week release train: features merge to main all week, a release tag is cut on Thursday, TestFlight/Play-internal is live Friday, review over the weekend, staged rollout Monday. Features that miss the train wait for the next one — this is why [OTA](10.8.05-codepush-ota-updates.md) exists for urgent JS fixes between trains.
- **Phased release as the safety net** — even a fully tested build goes 10% → 50% → 100% with crash-free monitoring between steps; a crash spike at 10% pauses the rollout, not the whole user base.
- **Remote control = rollback** — App Store Connect's ability to pause/delay a phased release, and Play's ability to halt a staged rollout, are the "kill switch" — pair them with [feature flags](../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.04-feature-flags-kill-switches.md) so a bad release can be neutralized without waiting for user adoption of a fix.
- **Docita anchor (web analog)** — the platform stack's [zero-downtime deploys](../../30-architecture/30.3-infra-patterns/05-shipping-and-evolution/30.3.5.01-zero-downtime-deployments.md) and [CI pipeline](../../40-platform/40.3-ci-cd/INDEX.md) map one-to-one: build → gate → promote → staged → monitor → rollback. Mobile replaces instant-deploy with review + adoption lag, which is exactly why the release *train* discipline matters.

## Real-World Use Cases

- **Weekly release trains** — Fastlane lanes in CI: bump build number, build, upload, screenshots, metadata; humans approve, machines do the rest.
- **Review-response loop** — rejection telemetry (common: metadata, permissions strings) feeds a preflight checklist; the second submission usually passes.

## Common Mistakes

- **Shipping 100% on day one** — no staged rollout, so a bad build hits every user before monitoring can react
- **No adoption awareness** — forgetting that a fix only reaches users who update; measuring "released" instead of "installed and crash-free"
- **Releasing on Friday** — a bad build discovered Saturday means a weekend incident with no one to cut the next train
- **Versioning collisions** — forgetting `buildNumber`/`versionCode` bumps so the store rejects the upload (see [EAS Build](10.8.04-expo-eas-builds.md))
- **Store assets as an afterthought** — screenshots, privacy labels, and review notes blocking an otherwise-ready release at the last gate
- **No rollback plan** — every release should know its answer to "if this is bad at 10%, what do we do?" (halt rollout, remote-disable the feature, ship an OTA or hotfix binary)
- **Automating submission but not monitoring** — a pipeline that ships and then goes silent; release automation must end with crash-free + adoption dashboards

## Best Practices

- Run a fixed cadence (weekly or biweekly train) so review latency is predictable
- Gate the train: tests green, changelog, store assets, version bump — a checklist the CI enforces, not a human remembers
- Use the store's staged/phased rollout for every production release; monitor between steps
- Keep a "what's live" manifest: binary version, OTA version, rollout %, crash-free rate
- Automate build + submit; keep store *promotion* semi-manual (approval = a human confirming monitoring)
- Rehearse the rollback: pause/halt rollout, remote-disable via flags, and know whether a fix is OTA-able or needs a hotfix train
- Pair every native release with an [OTA](10.8.05-codepush-ota-updates.md)-ready posture for JS hotfixes between trains

## Summary

1. **The release train is a pipeline, not an event** — tag → CI tests → build → submit → TestFlight/internal → review → phased rollout
2. **Both stores impose review and policy gates** — plan for variable approval time and use each store's rollout controls
3. **Rollout + rollback are one motion** — 10% → 50% → 100% with crash-free monitoring between; halting a rollout is the primary rollback tool
4. **Version bumps are mechanical, store assets are not** — buildNumber/versionCode via auto-increment; screenshots and review notes still need a human
5. **Release ≠ adoption** — users update on their own schedule, so monitor installed-version distribution before shipping native-only fixes

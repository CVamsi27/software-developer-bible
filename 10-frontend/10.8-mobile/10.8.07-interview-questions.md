# Mobile & Cross-Platform Interview Questions

> 30+ curated questions on React Native and cross-platform mobile — architecture (bridge → JSI/Fabric), platform choice, deep linking, testing, and the mobile-specific production concerns a senior full-stack engineer must own.

## TL;DR

Senior-level React Native questions: bridge/new-architecture internals, native module authoring, OTA trade-offs, and store review strategy.

## First Principles

This set probes the JS↔native boundary (→ 10.8.01) and mobile delivery (→ 10.8.04–06):

1. **The senior tells are boundary precision**: what crosses the bridge, why the new architecture exists, where native modules are unavoidable.
2. **OTA-vs-store questions** (→ 10.8.05) test knowing the compliance line — the constraint candidates often haven't felt.

## Definition

This guide covers the questions a senior full-stack engineer should be able to answer about shipping mobile: how React Native actually runs code, when to pick RN vs native vs PWA, how deep linking works end-to-end, how you test mobile apps, and the operational concerns (stores, release trains, crash reporting) that a web-only engineer typically underestimates. Grouped by difficulty.

## Why It Matters

- **Architecture fluency** — "explain the bridge" is the single most-asked RN question; the JSI/Fabric answer separates seniors
- **Decision ownership** — "which would you pick?" questions test trade-off reasoning, not trivia
- **Cross-platform reach** — EU studios/agencies (MVST-class) and product companies ship mobile from TS monorepos; the code-sharing story is a Docita-strength answer
- **Operational gaps** — release trains, store review, crash reporting, and device fragmentation are where web engineers look junior

## Answer Framework

```text
ANSWER STRUCTURE:
  1. Platform choice (web skills? UI customness? platform-API depth?)
  2. Architecture (which renderer/threading model applies)
  3. Implementation (navigation, linking, native modules)
  4. Testing + release (pyramid, CI, store rollout)
  5. Ops (crash rate, adoption, app-store review, rollback)
```

## Beginner

**Q1: React Native vs Flutter vs native vs PWA — how do you decide?**

A: Score against four axes: (1) **team skills** — RN reuses your TS/React talent, PWA reuses everything; (2) **UI customness** — pixel-perfect custom design favors native or a mature RN/Fabric setup; (3) **platform-API depth** — AR, health sensors, background audio favor native modules; (4) **reach/install friction** — a content surface may not justify store installs. PWA wins when instant reach and zero-install matter; RN wins when you need real app-store presence with a web team; native wins for deep platform integration or perf-critical animation.

**Q2: What is Expo and when do you use it?**

A: Expo is the managed React Native toolchain — build service, dev client, and a large SDK of prebuilt native modules. Use it by default for new apps: it removes the native build/Xcode-AndroidStudio setup and over-the-air JS updates are built in. You "eject" (now: prebuild + development build) when you need a custom native module the Expo SDK doesn't cover. Expo-first is the industry-default recommendation today.

**Q3: What is the difference between a PWA and React Native?**

A: A PWA is a web app with a service worker, manifest, and offline shell — runs in the browser, installable, no store. RN is a native app (real UIKit/Android views) written in JS/React. PWA: instant reach, no review, weaker platform APIs (push on iOS is restricted), cannot ship to the App Store as a first-class app. RN: store presence, full APIs via modules, but requires builds/releases and store review.

**Q4: What is a "deep link"?**

A: A URL or URI that opens your app to a specific screen instead of just launching it — e.g. `myapp://checkout/123` or an `https://` Universal Link that resolves to `checkout/123` when the app is installed. Users click a link in email/SMS/web and land on the exact content, not the home screen.

**Q5: URI scheme vs Universal Link vs App Link — what's the difference?**

A: **URI schemes** (`myapp://`) are app-specific, work everywhere but are unverified (any app can claim one) and don't work from the browser unless you use a fallback page. **Universal Links** (iOS, `apple-app-site-association` JSON on your domain) and **App Links** (Android, `assetlinks.json`) verify domain ownership over HTTPS and fall back to the website when the app is missing — the modern default for production linking.

**Q6: How does a React component become pixels on a native screen?**

A: RN renders your components to a **shadow tree** (a JS-side layout tree), computes layout with **Yoga** (a cross-platform flexbox engine), and then creates/updates real native views (UIView / android.view) from that computed layout. The rendering contract: business logic runs in JS, but layout and drawing happen natively — which is why styling maps to a flexbox subset, why `shadow`/blur props differ per platform, and why the New Architecture's synchronous JSI path matters for high-frequency updates.

**Q7: What is Hermes, and what changes when you enable it?**

A: Hermes is Meta's JavaScript engine built for RN: it compiles JS to **bytecode ahead-of-time** at build time, which removes parse/compile cost from startup, shrinks memory, and improves TTI on low-end Android. Consequences: faster cold start, but debugging needs the right symbolicated bytecode maps, and `eval`-style dynamic code is unavailable. On modern RN it's the default engine — the interview point is knowing *why* AOT bytecode beats a JIT on mid-range phones (startup cost and memory beat peak throughput).

**Q8: Expo Go, a development build, and a bare workflow — what's the difference?**

A: **Expo Go** is the generic sandbox client — instant start, but only SDK-native modules are available. A **development build** is *your* app binary with expo-dev-client baked in — custom native modules work, OTA JS updates work, and it's the recommended default. **Bare/prebuild** means you own the native projects outright (`expo prebuild` generates them from config; you can still eject fully). The mental model: Go = demo, dev build = daily work, bare = when native ownership is unavoidable.

**Q9: How do you handle notches, safe areas, and soft keyboards?**

A: Use `react-native-safe-area-context` (`SafeAreaView`/insets) rather than hard-coded paddings — notch, status-bar, and home-indicator geometry differ per device and orientation. For the keyboard: `KeyboardAvoidingView` behaves differently per platform, so wrap input surfaces with `react-native-keyboard-controller` (the modern option — animated, per-screen control) or `react-native-keyboard-aware-scroll-view`, and test on a device with a third-party keyboard installed (resize/pan bugs hide there). The senior tell is treating geometry as data (insets) instead of magic numbers per screen.

**Q10: `Dimensions.get('window')` vs `useWindowDimensions()` — which and why?**

A: `Dimensions.get` is an imperative snapshot — it does **not** update on rotation, split-screen, or foldables, so anything rendered from it goes stale. `useWindowDimensions` is the React-subscription version: re-renders on every dimension change. Build responsive layouts from the hook (or a `useBreakpoint` wrapper over it); keep `Dimensions` for one-shot metrics outside render. On foldables and tablets this is the difference between a layout that adapts and one that needs an app restart.

## Intermediate

**Q1: Explain the React Native "bridge" and why it was replaced.**

A: Pre-Fabric RN ran JS on a separate thread and communicated with native through an async serialized JSON bridge — every prop update, event, and call crossed it. It worked but caused latency, jank on high-frequency updates (scroll/gestures), and made synchronous native calls impossible. Fabric replaced the bridge with a **JSI** (JavaScript Interface) layer that lets JS hold references to native objects and call them synchronously — enabling the new renderer, better startup, and synchronous native module calls. Interviews want: bridge = serialized async bottleneck → JSI = direct, shared, low-overhead.

**Q2: What is the New Architecture (Fabric + TurboModules)?**

A: The two pillars of RN's New Architecture: **Fabric** is the new rendering system — it uses JSI and a shared C++ core so UI updates don't round-trip through the async bridge, and it enables **React 18 concurrent features**. **TurboModules** lazily load native modules on first use and expose them via JSI instead of eagerly registering them on the bridge. Codegen generates the type-safe interface between JS and native. Legacy modules still work through an interop layer.

**Q3: How do you share code between web and mobile in a TypeScript monorepo?**

A: Extract shared code into workspace packages (pnpm/Turborepo): `packages/ui` (React components that work in RN and web via `react-native-web` or platform-agnostic primitives), `packages/domain` (types, validation with Zod, business logic — the bulk of the win), `packages/api` (API client). Keep platform-specific leaf components in the app. Docita's own `pnpm-workspace.yaml` with `apps/*` + `packages/*` is the real-world shape: one monorepo, shared types/hooks/utils, platform shells at the edges.

**Q4: How does deep linking actually work on iOS from a cold start?**

A: When the OS opens a Universal Link and the app is installed, iOS launches the app and delivers the URL via `application(_:continue:userActivity:)` (or `onOpenURL` in RN). On a **cold start** the link may arrive before React Navigation mounts — so you must store the pending URL and resolve it once navigation is ready, not just listen for `linking` events. The `linking` config in React Navigation maps `https://domain.com/checkout/:id` to a route; test cold/warm/deferred paths with `simctl` or adb and verify the AASA file serves with the correct content-type over HTTPS.

**Q5: What is deferred deep linking and why does it need a fallback?**

A: Deferred linking captures a link clicked *before* the app is installed and routes to the content after first launch (via the attribution/install provider). It requires a web fallback page (the link opens the browser → prompts install → hands off the payload on first open). It matters because most marketing links are clicked on cold audiences — without deferral you lose the funnel to install.

**Q6: How do you test a React Native app?**

A: Same pyramid as web with mobile deltas: **unit** with Jest (pure logic, reducers, utils), **component** with React Native Testing Library (render, fire events, assert), and **E2E** with Detox or Maestro (real device/simulator flows). The native-specific problems: **mocking native modules** (jest mocks for modules not present in the test env) and **macOS/device-farm CI runners** (E2E needs simulators, which changes your CI image and cost). Add visual regression options (screenshot diffing) for UI-heavy screens.

**Q7: When do you write a native module, and what does it involve?**

A: When no existing module covers a platform capability (BLE specifics, proprietary SDKs, hardware integrations). The shape: a Kotlin/Swift(Obj-C) implementation registered with the RN runtime, a typed JS spec, and — on the New Architecture — a **codegen** interface (TurboModule spec) that generates the glue. Costs to name: you own bridging bugs, thread-safety (native side may be called off the JS thread), and permission plumbing. First check the Expo SDK and the community registry — a native module is a maintenance liability you take on deliberately.

**Q8: What are the storage options on mobile, and when is each right?**

A: **AsyncStorage/MMKV** for small key-value settings (MMKV is synchronous and much faster — default choice); **SQLite** (or WatermelonDB/OP-SQLite) for relational data and queryable caches; **secure storage** (Keychain/Keystore) for tokens and secrets — never AsyncStorage, which is unencrypted; **file system** for large blobs. Sync layer: an offline queue with retries for writes, and a TTL/purge strategy so the local DB doesn't grow unbounded. The interview signal: knowing storage is both a *performance* choice (MMKV vs AsyncStorage is measurable in app startup) and a *security* boundary (what's allowed near Keychain).

**Q9: How do push notifications work end-to-end, and what's app-side vs server-side?**

A: Server: your backend asks FCM (Android) / APNs (iOS, usually via a relay like Expo Push) with the device token obtained at registration. Device: the OS displays it — your app only controls presentation when foregrounded or via notification-service extensions (iOS rich push). App-side ownership: **permission UX** (ask in context, not on first launch — iOS degrades permanently after denial), token refresh handling, deep-link routing from the payload, and the Android channel model (API ≥ 26 channels control importance per category). Background delivery is not guaranteed — anything critical needs data-sync-on-open, not just the notification.

**Q10: How do you keep a React Native app's bundle and binary small?**

A: Binary size comes from architectures and assets: ship **ABI splits** (arm64 only where possible — x86 belongs to emulators), enable **Hermes bytecode**, and prune unused native modules (each static pod/library links into the binary). JS side: enable Hermes + Minify (Metro), and tree-shake icon/chart libraries — single-package imports instead of barrel files. Assets: vector icons over PNG sets, WebP/HEIC for imagery, and lazy routes (React.lazy / dynamic imports on the JS side) so cold start loads the shell, not the catalog. Measure per release (size report on the build artifact) — a budget without a measured dashboard drifts.

## Advanced

**Q1: You're asked to add real-time chat to an RN app. What's the architecture?**

A: WebSockets through a gateway — same transport question as web (see the [Realtime stack](../../60-realtime/60.1-websockets/INDEX.md)) with mobile deltas: (1) **background/foreground transitions** — sockets drop on background; reconnect and resync unread counts on foreground; (2) **push fallback** — when the app is killed, APNs/FCM must carry the message; (3) **offline queue** — sent-message persistence with retry, so a user in a tunnel still sees their message send; (4) **battery/data awareness**. The Docita shape (NestJS gateway + Redis adapter for multi-instance fan-out) is the backend you'd pair with the RN client.

**Q2: How do you handle a crash or janky animation that only happens on low-end Android?**

A: Reproduce with a device matrix (the low-end device is non-negotiable — emulators lie), then profile: (1) check whether it's JS-thread work (Hermes bytecode, reduce re-renders, move work off-thread) or native rendering; (2) animation jank on Android usually means main-thread work — use `useNativeDriver: true` (or the Fabric equivalent) so animations run off the JS thread, keep `transform`/`opacity` animations composited; (3) ship a **crash-only fix** first if it's a release-blocker, then a proper fix on the next train. Release management: staged rollouts (e.g., 10% → 50% → 100% on the Play Store) bound the blast radius.

**Q3: Should the whole app be React Native, or a hybrid (web views for some flows)?**

A: Prefer RN for the core user flows that need native feel/platform APIs, and be careful with web views: they feel foreign, break deep linking continuity, and complicate the offline story. Web views earn their place for genuinely web-only content (legacy CMS pages, complex document editors you already built) — but each one is a UX compromise and a testing seam. The senior answer: define the rule ("native shell for nav/perf-critical flows, web view only for content we cannot feasibly rebuild"), not the dogma.

**Q4: How do you release a mobile app safely, given store review?**

A: Two release tracks in parallel: **store** (App Store review takes days; TestFlight/Play internal testing shortens the loop) and **OTA** (EAS Update ships JS-only fixes instantly without review — but never OTA a native-module change). Use **staged rollouts** (percentage-based on Play, phased on iOS), monitor crash-free sessions and adoption per version, and keep a **rollback path** (a prior binary is still live on the store; disable the bad version remotely). The web mindset — "ship and fix in minutes" — does not transfer; mobile release is a train, not a push.

**Q5: Compare Detox and Maestro for E2E.**

A: **Detox** is JS-first, ties into Jest, and synchronizes with the app (waits for the app to be idle before asserting) — stable but heavier setup and slower; it's the RN-community default for CI. **Maestro** is YAML-driven, works across iOS/Android/Flutter/RN with the same flow files, and is faster to adopt, but synchronization is more implicit. Pick Detox for deep RN integration in a mature app; pick Maestro when you want cross-platform flow parity and quick authoring. Either way the flows run on simulator/device farms in CI — that's the real cost center.

**Q6: What is `useNativeDriver` and why does it matter?**

A: It tells RN's Animated API to run the animation on the **native side** instead of sending every frame update over the bridge/JS thread. With it, transforms/opacity animate at 60fps because native drives the frames; without it (JS-driven), each frame round-trips through JS and you jank on busy screens. Under the New Architecture the boundary shifts (Fabric + JSI make the JS→native path cheap), but the principle survives: keep animations off the JS thread.

**Q7: What can you ship over the air (OTA), and what forces a new store build?**

A: OTA (EAS Update — the standard hosted service since Microsoft retired App Center CodePush in March 2025) replaces the **JS bundle + assets** on devices whose native binary is compatible. So anything expressible in JavaScript — UI fixes, business logic, API-client changes, config, images/l10n — can ship instantly. Anything touching the **native layer forces a new binary + store review**: a new native module, a permission, an Expo SDK upgrade, app icons/splash, deep-link schemes, background modes. The compatibility contract is the `runtimeVersion`: an OTA bundle is only valid for binaries whose runtime version it matches — push JS that needs a native module you haven't shipped and old clients reject it (or crash). The one-liner: "JS = OTA; capability = store build."

**Q8: Walk me through your mobile release automation — how does a fix actually reach users?**

A: "We run a release train. A Git tag triggers CI: tests → EAS Build with the production profile (cloud, signed, `autoIncrement` version) → EAS Submit to TestFlight / Play internal. After store review we roll out staged (Play percentage or iOS phased release), monitoring crash-free rate between steps. If the release is bad at 10% we halt the rollout and either remote-disable the feature via a flag or ship a revert — a JS-only issue goes OTA in minutes, a native issue becomes a hotfix train. The web instinct is 'deploy and roll back in seconds'; mobile is a train with review latency and adoption lag, so automation + staged rollout + a rollback plan are non-negotiable." (See the [EAS Build](10.8.04-expo-eas-builds.md), [OTA](10.8.05-codepush-ota-updates.md), and [release automation](10.8.06-app-store-release-automation.md) chapters for the depth behind this.)

**Q9: How do you instrument crash reporting and performance monitoring on mobile?**

A: Sentry (or Crashlytics) for crashes + performance: capture native crashes, JS exceptions, and **symbolicated** stack traces — upload dSYM/mapping files per build or traces are unreadable. The metrics that matter: **crash-free sessions/users per release** (gate your staged rollout on it), cold-start and screen-load spans (Sentry performance / Firebase Performance Monitoring), and ANRs on Android. Tie into release: the rollout automation halts if crash-free rate drops below the release gate. The web delta: crashes are per-OS-version × device × app-version — build the triage dimensions in from day one, not after the first spike.

**Q10: Your OTA update shipped and crash-free rate drops — walk the response.**

A: First isolate scope: which runtime versions / app versions / OS versions are crashing (Sentry release health answers this directly) — if it's only clients on one runtime version, the OTA bundle drifted from the native contract (a new module call against an old binary). Response: **republish the previous OTA bundle** (instant rollback on the OTA channel) or remote-disable the feature via a flag; store-binary issues can't roll back — the fix train goes through review. Postmortem: the `runtimeVersion` policy and a staging OTA channel (dogfood devices first) are what prevent the repeat. The question tests whether you treat OTA as a deployment with its own rollback story, not a magic patch channel.

## Anti-Patterns & Red Flags

- Saying "we used React Native" without being able to explain the bridge → JSI migration — the #1 depth probe
- Recommending PWA as a universal answer without naming the iOS push and store-install limitations
- Deep linking answer that stops at "we registered a scheme" — no cold-start handling, no Universal Link verification
- "Detox tests run in CI" without mentioning simulator runners, native-module mocks, or flakiness handling
- Releasing 100% to the store on day one with no staged rollout or rollback story
- Confusing Expo updates (JS OTA) with native releases — shipping a native module change OTA is a crash vector
- No answer for "what happens to the socket/chat when the app backgrounds" — the mobile-specific realtime gap

## Summary

1. **Mobile interviews test the boundary twice** — native vs JS (OTA question) and online vs offline (storage/sync question)
2. **The release story is a differentiator** — candidates who can narrate build → submit → review → staged rollout stand out against UI-only candidates
3. **Linking and deep navigation are systems questions**, not string handling — universal links involve app-site association, fallbacks, and routing state
4. **Testing answers should follow the pyramid** — Jest for logic, RNTL for components, E2E selectively on real devices
5. **Every answer should name the failure mode it prevents** — e.g. runtimeVersion mismatch, lost review weeks, zombie deep links

## Cheat Sheet

```text
CHOICE:  web-team TS, store presence needed → RN (Expo first)
         deep platform APIs / perf-critical → native
         instant reach, no store → PWA
ARCH:    pre-Fabric = async JSON bridge (jank) → JSI/Fabric/TurboModules = sync, shared C++
LINKING: scheme = unverified fallback → Universal/App Links = HTTPS-verified, web fallback
TESTING: Jest units → RNTL components → Detox/Maestro E2E on simulators in CI
RELEASE: store train (review days) + OTA for JS-only + staged % rollout + remote disable
```

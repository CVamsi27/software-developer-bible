# Mobile & Cross-Platform Interview Questions

> 30 curated questions on React Native and cross-platform mobile — architecture (bridge → JSI/Fabric), platform choice, deep linking, testing, and the mobile-specific production concerns a senior full-stack engineer must own.

## Definition

This guide covers the questions a senior full-stack engineer should be able to answer about shipping mobile: how React Native actually runs code, when to pick RN vs native vs PWA, how deep linking works end-to-end, how you test mobile apps, and the operational concerns (stores, release trains, crash reporting) that a web-only engineer typically underestimates. Grouped by difficulty.

## First Principles

This set probes the JS↔native boundary (→ 10.8.01) and mobile delivery (→ 10.8.04–06):

1. **The senior tells are boundary precision**: what crosses the bridge, why the new architecture exists, where native modules are unavoidable.
2. **OTA-vs-store questions** (→ 10.8.05) test knowing the compliance line — the constraint candidates often haven't felt.

## Why It Matters

- **Architecture fluency** — explain the JS/native boundary and its current mechanisms
- **Decision ownership** — "which would you pick?" questions test trade-off reasoning, not trivia
- **Cross-platform reach** — EU studios/agencies (MVST-class) and product companies ship mobile from TS monorepos; explain demonstrated shared-code patterns and identify any mobile experience you have not yet implemented
- **Operational gaps** — release trains, store review, crash reporting, and device fragmentation are where web engineers look junior

## Answer Framework

```text
ANSWER STRUCTURE:
  1. Platform choice (web skills? UI customness? platform-API depth?)
  2. Architecture (which renderer/threading model applies)
  3. Implementation (navigation, linking, native modules)
  4. Testing + release (pyramid, CI, store rollout)
  5. Ops (crash rate, adoption, app-store review, rollback)
```

## Beginner

**Q1: React Native vs Flutter vs native vs PWA — how do you decide?**

A: Score against four axes: (1) **team skills** — RN reuses your TS/React talent, PWA reuses everything; (2) **UI customness** — pixel-perfect custom design favors native or a mature RN/Fabric setup; (3) **platform-API depth** — AR, health sensors, background audio favor native modules; (4) **reach/install friction** — a content surface may not justify store installs. PWA wins when instant reach and zero-install matter; RN wins when you need real app-store presence with a web team; native wins for deep platform integration or perf-critical animation.

**Q2: What is Expo and when do you use it?**

A: Expo provides React Native libraries and tooling, with optional hosted build/update services. Expo Go contains a fixed set of native capabilities; a development build contains your app's chosen native modules. Prebuild generates native projects from configuration/plugins, and custom native code can coexist with Expo. Cloud builds can avoid local build-tool setup, but local native builds still need the appropriate toolchain.

**Q3: What is the difference between a PWA and React Native?**

A: A PWA uses browser capabilities and optional installation/offline support; React Native produces an app using native components and modules. Compare needed APIs, background behavior, accessibility, distribution and maintenance on the target devices. Browser and store-wrapper distribution options exist, with store rules and platform limits; 'PWA can never enter a store' is too absolute.

**Q4: What is a "deep link"?**

A: A URL or URI that opens your app to a specific screen instead of just launching it — e.g. `myapp://checkout/123` or an `https://` Universal Link that resolves to `checkout/123` when the app is installed. Users click a link in email/SMS/web and land on the exact content, not the home screen.

**Q5: URI scheme vs Universal Link vs App Link — what's the difference?**

A: Custom schemes are generally unverified and can collide with another app. iOS Universal Links and Android App Links associate HTTPS domains with an app through platform verification files and signing/application identities. Actual opening behavior depends on installation, association, browser context and user settings; keep a working website fallback and validate route input regardless of verification.

**Q6: How does a React component become pixels on a native screen?**

A: React renders a React element tree; Fabric creates and reconciles a C++ shadow tree representing native UI, computes layout with Yoga, and commits/mounts changes into platform views. This is not a JavaScript DOM or a purely JS-side shadow tree. JS, renderer and platform execution have scheduling/thread constraints; synchronous access through JSI does not mean every update is synchronous or jank-free.

**Q7: What is Hermes, and what changes when you enable it?**

A: Hermes is the JavaScript engine commonly used by React Native. Release tooling can precompile bundles into bytecode to reduce startup parsing/compilation work. Startup, memory and peak-throughput trade-offs still depend on the app and engine version. Preserve release source maps for useful JS stack traces; do not infer that all dynamic evaluation is universally unavailable or that bytecode eliminates all startup work.

**Q8: Expo Go, a development build, and a bare workflow — what's the difference?**

A: Expo Go is a prebuilt client with a fixed native module set. A development build is your own binary containing development tooling and chosen native capabilities. Prebuild generates native projects from configuration/plugins; you can regenerate them or maintain native projects directly. Native ownership and Expo services are separate decisions, not a one-way 'eject to lose Expo' boundary.

**Q9: How do you handle notches, safe areas, and soft keyboards?**

A: Use `react-native-safe-area-context` (`SafeAreaView`/insets) rather than hard-coded paddings — notch, status-bar, and home-indicator geometry differ per device and orientation. For the keyboard: `KeyboardAvoidingView` behaves differently per platform, so wrap input surfaces with `react-native-keyboard-controller` (the modern option — animated, per-screen control) or `react-native-keyboard-aware-scroll-view`, and test on a device with a third-party keyboard installed (resize/pan bugs hide there). The senior tell is treating geometry as data (insets) instead of magic numbers per screen.

**Q10: `Dimensions.get('window')` vs `useWindowDimensions()` — which and why?**

A: A saved result of `Dimensions.get('window')` is a snapshot and can become stale. `Dimensions` itself can be read again and provides change events; `useWindowDimensions()` subscribes and updates a React component. Use the hook for responsive render decisions and include font scale, rotation, split-screen and foldable scenarios in testing.

## Intermediate

**Q1: Explain the React Native "bridge" and why it was replaced.**

A: The legacy bridge exchanged batched asynchronous serialized messages between JavaScript and native code. The New Architecture combines Fabric, TurboModules and JSI, allowing direct native integration and synchronous access where an API requires/supports it. Fabric is the renderer, not the entire bridge replacement. Direct calls still need careful scheduling, ownership and bounded work; fewer serialization boundaries do not remove every latency source.

**Q2: What is the New Architecture (Fabric + TurboModules)?**

A: Fabric owns rendering and its shared C++ shadow tree. TurboModules provide typed native-module integration and lazy loading; Codegen generates interface glue from supported specs. JSI is the engine integration interface these mechanisms use. Compatibility layers support some legacy libraries, but verify each dependency against the chosen React Native version rather than promising universal interoperability.

**Q3: How do you share code between web and mobile in a TypeScript monorepo?**

A: Extract shared code into workspace packages (pnpm/Turborepo): `packages/ui` (React components that work in RN and web via `react-native-web` or platform-agnostic primitives), `packages/domain` (types, validation with Zod, business logic — the bulk of the win), `packages/api` (API client). Keep platform-specific leaf components in the app. Docita's own `pnpm-workspace.yaml` with `apps/*` + `packages/*` is the real-world shape: one monorepo, shared types/hooks/utils, platform shells at the edges.

**Q4: How does deep linking actually work on iOS from a cold start?**

A: The OS verifies the app-domain association and delivers the URL through native lifecycle integration. React Native exposes an initial URL and later URL events through Linking; React Navigation's linking configuration can resolve them into navigation state. Handle authentication/restoration readiness and validate route parameters. SwiftUI `onOpenURL` is not the React Native API. Test cold and warm launches plus browser fallback with verified association files.

**Q5: What is deferred deep linking and why does it need a fallback?**

A: Deferred linking tries to preserve a pre-install destination for first launch. A verified HTTPS link alone does not guarantee that install handoff. Attribution providers and platforms have differing capabilities and privacy constraints; use an explicit fallback/resume path and avoid promising exact recovery when attribution is unavailable.

**Q6: How do you test a React Native app?**

A: Same pyramid as web with mobile deltas: **unit** with Jest (pure logic, reducers, utils), **component** with React Native Testing Library (render, fire events, assert), and **E2E** with Detox or Maestro (real device/simulator flows). The native-specific problems: **mocking native modules** (jest mocks for modules not present in the test env) and **macOS/device-farm CI runners** (E2E needs simulators, which changes your CI image and cost). Add visual regression options (screenshot diffing) for UI-heavy screens.

**Q7: When do you write a native module, and what does it involve?**

A: When no existing module covers a platform capability (BLE specifics, proprietary SDKs, hardware integrations). The shape: a Kotlin/Swift(Obj-C) implementation registered with the RN runtime, a typed JS spec, and — on the New Architecture — a **codegen** interface (TurboModule spec) that generates the glue. Costs to name: you own bridging bugs, thread-safety (native side may be called off the JS thread), and permission plumbing. First check the Expo SDK and the community registry — a native module is a maintenance liability you take on deliberately.

**Q8: What are the storage options on mobile, and when is each right?**

A: Use key-value storage for suitable preferences, SQLite for transactional/queryable local records, platform-backed secure storage for sensitive credentials, and files for blobs. MMKV is synchronous and can be useful, but benchmark actual workload and account for JS blocking and compatibility. Secure storage has backup, access-control and device-compromise constraints too. Offline writes need stable identity, retries, reconciliation and a bounded retention policy.

**Q9: How do push notifications work end-to-end, and what's app-side vs server-side?**

A: The backend sends through APNs/FCM or a relay using registered tokens. OS and payload type determine foreground/background presentation and execution. Handle permissions, token rotation, channels and navigation when opened. A denied permission can often be changed in device settings; neither registration nor provider acceptance guarantees delivery. Refresh authoritative state on opening rather than treating push as the only data channel.

**Q10: How do you keep a React Native app's bundle and binary small?**

A: Measure separate native-binary, asset and JavaScript costs in release artifacts. Android App Bundles can select architecture/resources for devices; keep the supported-device policy explicit. Prune unused assets/modules and verify Metro's actual optimization behavior. Hermes bytecode and dynamic imports do not automatically shrink every binary or create production route chunks; lazy evaluation and network code splitting are different capabilities.

## Advanced

**Q1: You're asked to add real-time chat to an RN app. What's the architecture?**

A: Use a persisted message identity and a server acknowledgment protocol over a suitable realtime transport. On reconnect, reconcile missing messages from durable server history. Preserve outgoing offline messages and retry idempotently. Background sockets may stop; push is a notification hint, not a guaranteed replacement message log. Redis fan-out coordinates gateway instances but does not by itself supply durable history or delivery acknowledgment.

**Q2: How do you handle a crash or janky animation that only happens on low-end Android?**

A: Reproduce on representative hardware and use release-build native/JS traces plus symbolicated crash reports. Distinguish JS work, UI-thread layout/drawing, memory pressure and network effects. A supported native-driven animation can reduce JS-frame dependence; there is no generic 'Fabric equivalent' that makes every effect cheap. Roll out a validated fix gradually with crash/performance gates and a capability-compatible update path.

**Q3: Should the whole app be React Native, or a hybrid (web views for some flows)?**

A: Prefer RN for the core user flows that need native feel/platform APIs, and be careful with web views: they feel foreign, break deep linking continuity, and complicate the offline story. Web views earn their place for genuinely web-only content (legacy CMS pages, complex document editors you already built) — but each one is a UX compromise and a testing seam. The senior answer: define the rule ("native shell for nav/perf-critical flows, web view only for content we cannot feasibly rebuild"), not the dogma.

**Q4: How do you release a mobile app safely, given store review?**

A: Test the candidate binary, distribute through store testing tracks, and use the store's supported rollout controls while monitoring release health. Compatible JS/assets updates have a different delivery path but still need runtime compatibility, rollout checks and store-policy compliance. A halted rollout does not downgrade devices already updated; remote flags can contain some issues, while native repairs generally need another binary.

**Q5: Compare Detox and Maestro for E2E.**

A: Detox synchronizes with instrumented app behavior and supports engineer-authored device tests. Maestro drives supported installed apps using declarative flows. Compare supported platforms, selectors, idle handling, diagnostics and existing build integration on real flows. Neither a universal speed ordering nor a single 'community default' decides fit.

**Q6: What is `useNativeDriver` and why does it matter?**

A: `useNativeDriver` sends an Animated configuration to the native side so supported animation frames do not depend on the JavaScript loop. The classic driver supports a limited property set. React Native 0.85 introduced a separate experimental backend that can animate layout properties when opted in; check the version and channel your app actually ships. Neither driver guarantees smooth frames when native work is overloaded.

**Q7: What can you ship over the air (OTA), and what forces a new store build?**

A: EAS Update can deliver compatible JavaScript/assets to binaries sharing the intended runtime contract, but runtime matching is only a technical check. Apple restricts downloaded code that introduces or changes features; Google Play restricts self-updates and external executable downloads. Check the current store rules for the change. Native module, permission, entitlement or SDK changes require a rebuilt binary. OTA delivery is not instant on every device. See the OTA chapter for policy, lifecycle and rollback controls.

**Q8: Walk me through your mobile release automation — how does a fix actually reach users?**

A: Describe the pipeline you actually operate: test the commit, build/sign the intended runtime, distribute a candidate, review release evidence, then expand the rollout with health gates. Keep build IDs, source maps, update IDs and monitoring aligned. Halting limits new exposure; it does not revert installed binaries. Use a compatible update or flag when safe, otherwise publish a validated replacement binary. The EAS chapters contain the concrete automation mechanisms.

**Q9: How do you instrument crash reporting and performance monitoring on mobile?**

A: Sentry (or Crashlytics) for crashes + performance: capture native crashes, JS exceptions, and **symbolicated** stack traces — upload dSYM/mapping files per build or traces are unreadable. The metrics that matter: **crash-free sessions/users per release** (gate your staged rollout on it), cold-start and screen-load spans (Sentry performance / Firebase Performance Monitoring), and ANRs on Android. Tie into release: the rollout automation halts if crash-free rate drops below the release gate. The web delta: crashes are per-OS-version × device × app-version — build the triage dimensions in from day one, not after the first spike.

**Q10: Your OTA update shipped and crash-free rate drops — walk the response.**

A: Identify affected update/runtime/app/OS/device groups and distinguish logic bugs from compatibility or delivery mistakes. Stop further exposure and use a tested compatible rollback/republication or feature flag where possible. Existing clients apply changes through the configured fetch/restart lifecycle, so rollback is not instant. Restore monitoring and test the exact candidate on affected runtimes before expanding it again. A runtime mismatch is one possible cause, not the automatic diagnosis.

## Anti-Patterns & Red Flags

- Saying "we used React Native" without being able to explain the bridge → JSI migration — a useful depth probe
- Recommending PWA as a universal answer without naming the iOS push and store-install limitations
- Deep linking answer that stops at "we registered a scheme" — no cold-start handling, no Universal Link verification
- "Detox tests run in CI" without mentioning simulator runners, native-module mocks, or flakiness handling
- Releasing 100% to the store on day one with no staged rollout or rollback story
- Confusing Expo updates (JS OTA) with native releases — shipping a native module change OTA is a crash vector
- No answer for "what happens to the socket/chat when the app backgrounds" — the mobile-specific realtime gap

## Summary

1. **Mobile interviews test the boundary twice** — native vs JS (OTA question) and online vs offline (storage/sync question)
2. **The release story is a differentiator** — candidates who can narrate build → submit → review → staged rollout stand out against UI-only candidates
3. **Linking and deep navigation are systems questions**, not string handling — universal links involve app-site association, fallbacks, and routing state
4. **Testing answers should follow the pyramid** — Jest for logic, RNTL for components, E2E selectively on real devices
5. **Every answer should name the failure mode it prevents** — e.g. runtimeVersion mismatch, lost review weeks, zombie deep links

# Node.js Event Loop

Why can a fast database call still produce a slow request? Follow one request rather than memorizing queue names:

## Definition

The event loop decides when Node runs callbacks for timers and input/output (I/O), such as network activity. Each callback runs on one JavaScript execution thread. libuv is the library that connects the loop to operating-system I/O. Node also uses native threads, a worker pool, and optional JavaScript worker threads.
The rule is “one callback at a time on this JavaScript thread”; the process can contain many threads.

> **Textbook Definition:** The Node.js event loop is a scheduling mechanism that dispatches ready asynchronous callbacks on a JavaScript execution thread while the runtime delegates supported I/O and other work to the operating system or native workers.

## First Principles

1. A request often waits for an external resource, such as a database. The operating system can track several waiting connections while Node runs another request's callback. This is multiplexing: handling several connections without assigning a separate operating-system thread to each one.
2. JavaScript callbacks still execute synchronously until they return or suspend. A long callback delays unrelated requests on the same loop.
3. Scheduling adds ordering constraints, not deadlines. An eligible timer cannot preempt a running callback, and an async function does not move CPU work to another thread.

## 1. Follow the request past the database

The database can finish while the resumed handler still has synchronous work to do:

```text
JS handler submits database query over a socket
    → kernel observes socket readiness
    → poll callback processes data and resolves a promise
    → promise continuation resumes the handler
    → synchronous JSON parsing/serialization occupies this JS thread
    → response write may wait for the client to drain
```

Database and Simple Mail Transfer Protocol (SMTP) network I/O normally use kernel readiness mechanisms. File-system work, `dns.lookup`, and selected crypto/zlib operations use libuv's worker pool. They are different resources: increasing the pool does not make a database server faster or parallelize an arbitrary JavaScript loop.

## 2. How scheduling changes the trace

| Mechanism | When its callback becomes eligible | Boundary to remember |
| ----------------- | ------------------------------------- | ------------------------------------------------------------------- |
| Timer | After its delay threshold | No exact execution-time guarantee; delays below 1 ms are normalized |
| Pending callbacks | Deferred I/O callbacks | Some operations resume in a later iteration |
| Poll | I/O readiness and callback processing | May wait when there is no ready work |
| Check | `setImmediate` callbacks | Runs after poll |
| Close callbacks | Certain handle-close callbacks | A stream's `end` event is not its `close` event |

The full loop includes internal idle/prepare phases. Starting with libuv 1.45 / Node 20, timers run after poll rather than both before and after it. Treat phase diagrams as cycles, not a guarantee that every program begins by executing a timer.

At normal callback boundaries, Node drains its next-tick queue and then V8's promise/`queueMicrotask` queue before advancing. Recursively refilling either queue can starve I/O. ES module top-level evaluation already runs through asynchronous machinery, so promise microtasks can precede `nextTick` scheduled there.
Do not apply a CommonJS top-level trace to every module context.

## 3. Code: compare two scheduling contexts

Run this as `ordering.cjs`:

```javascript
const fs = require('node:fs');
console.log('start');
process.nextTick(() => console.log('tick'));
Promise.resolve().then(() => console.log('promise'));
console.log('end');

fs.readFile(__filename, (error) => {
  if (error) throw error;
  setTimeout(() => console.log('timeout in I/O'), 0);
  setImmediate(() => console.log('immediate in I/O'));
});
```

The initial sequence is `start → end → tick → promise`. Within this I/O callback, immediate precedes the newly scheduled zero-delay timer. If both are instead scheduled at top level, their relative order is not a portable guarantee.

`setImmediate` does not wait for every outstanding I/O operation to finish. It yields to the next check opportunity.

## 4. Code: share CPU time without hiding failure

This helper yields between time-bounded slices. It assumes an individual item operation is short; a single expensive item can exceed the budget.

```typescript
import { setImmediate as yieldToLoop } from 'node:timers/promises';
import { performance } from 'node:perf_hooks';

async function processInSlices<T>(
  items: readonly T[],
  processItem: (item: T) => void,
  signal?: AbortSignal,
): Promise<void> {
  let index = 0;
  while (index < items.length) {
    signal?.throwIfAborted();
    const deadline = performance.now() + 5;
    do {
      processItem(items[index++]); // throws reject this async function
    } while (index < items.length && performance.now() < deadline);
    if (index < items.length) await yieldToLoop(undefined, { signal });
  }
}
```

Yielding improves opportunities for other callbacks; it does not reduce the total CPU requirement. Move sustained CPU work to a bounded [worker pool](../03-processes-and-concurrency/20.1.3.02-child-processes-workers.md). Starting a new worker for every request adds startup overhead and permits unbounded resource growth.

## 5. Measure the resource that is saturated

```typescript
import { monitorEventLoopDelay, performance } from 'node:perf_hooks';
const delay = monitorEventLoopDelay({ resolution: 20 });
delay.enable();
let previous = performance.eventLoopUtilization();
const timer = setInterval(() => {
  const current = performance.eventLoopUtilization();
  const interval = performance.eventLoopUtilization(current, previous);
  previous = current;
  console.log({ p99DelayMs: delay.percentile(99) / 1e6, utilization: interval.utilization });
  delay.reset();
}, 5000);
timer.unref();
// On monitoring shutdown: clearInterval(timer); delay.disable();
```

Pair delay/utilization with a CPU profile, database latency, memory (`rss`, heap, external buffers), and queue/active-worker metrics from the pool library you use. A high delay suggests work is delaying the loop; it does not identify which function caused it. A simple interval probe measures scheduling drift rather than exact request latency.

Set `UV_THREADPOOL_SIZE` in the launch environment before the process starts. The pool defaults to four threads; increasing it helps only relevant pool-backed workloads and may increase CPU/memory contention.

## 6. Match the remedy to the saturated resource

| Situation | Choose | Check |
| ------------------------------ | -------------------------------------- | ----------------------------------------------------------- |
| Socket/database wait | Async client APIs | Deadlines, cancellation, connection limits |
| Brief CPU work over many items | Slices with a loop yield | Largest single-item cost and fairness |
| Sustained CPU computation | Bounded workers/processes | Queue limit, startup cost, timeout, result/error/exit paths |
| Streaming response | `pipeline` or explicit drain handling | Disconnects, end-of-stream, source cleanup |
| Process shutdown | Stop admission, drain, close resources | A deadline and forced fallback |

See [Streams](../02-io-and-data/20.1.2.01-streams.md), [Process & Environment](../03-processes-and-concurrency/20.1.3.03-process-environment.md), and the [atomic Redis limiter](../../20.8-caching/20.8.03-advanced-redis-patterns.md) for complete versions. A timestamp array limiter is process-local; it does not enforce a shared quota across replicas.

Keep the test contract as narrow as the runtime contract: assert callback order only where Node documents it, and catch expected failures at the request boundary. A global rejection handler does not replace request error handling, and `nextTick` is not a resource-cleanup mechanism.

## Summary

I/O can overlap while callbacks on one JavaScript thread execute serially. Scheduling controls eligibility; long synchronous work still delays other callbacks. Match the remedy to the saturated resource and verify the failure path as well as the successful trace.

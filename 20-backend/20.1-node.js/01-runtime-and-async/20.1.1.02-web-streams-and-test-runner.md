# Web Streams and the Node.js Test Runner

Why an export runs out of memory. A database cursor can emit rows lazily while a response still buffers every row.

## Definition

Have you streamed a response only to see memory keep growing, or watched a test pass while work was still running? Both failures come from losing control of a resource's lifetime.

Web Streams are standard interfaces for moving data a chunk at a time: `ReadableStream` supplies data, `WritableStream` receives it, and `TransformStream` changes it while passing it along. Their standard is maintained by the Web Hypertext Application Technology Working Group (WHATWG). `node:test` is Node's built-in test runner. Assertions, the checks that decide whether a result is correct, come separately from `node:assert` or another assertion library.

> **Textbook Definition:** Web Streams define asynchronous readable, writable and transforming interfaces with backpressure and cancellation contracts. Node's test runner executes registered tests and reports their outcomes; assertions separately evaluate whether observed behavior meets expectations.

## First Principles

1. A producer supplies data and a consumer processes it. If the producer is faster, queued data grows. To keep that queue within a limit, the consumer must slow the producer; this is backpressure. Promises help only when the caller awaits them before producing more.
2. A stream has an owner and a lifetime. Reading, piping, cancellation, and error propagation determine who must release resources.
3. A test needs a completion boundary. Unawaited work may fail after a test appears to pass, so the runner must observe the promise or explicitly awaited subtest.

## How It Works


### 1. Why an export runs out of memory

A database cursor can emit rows lazily while a response still buffers every row. If `res.write()` returns false and the loop continues, the export has ignored its slow client. Fix the entire path:

```text
cursor → encode one bounded row → stream queue → response socket
   ↑                                                   │
   └──────────── demand / cancellation ─────────────────┘
```

Node streams remain appropriate for Node file/socket APIs. Web Streams are useful for `fetch` and cross-runtime libraries. Choose the interface at the boundary rather than calling either one universally obsolete.
Web Streams have been stable since Node 21, the Node stream adapters used below since Node 22.17.0 and 24.0.0, and the test runner since Node 20. Individual test features have separate version and stability status: `mock.module`, for example, is still early-development and requires a flag. Check the exact runtime you deploy.

### 2. Let demand and cleanup flow through the pipeline

The following is a complete two-chunk fixture. The array is deliberately bounded by those two inputs; a production sink would await durable work under its own storage contract.

```typescript
const received: string[] = [];
let closed = false;
const source = () => ReadableStream.from((async function* () {
  try {
    yield 'hello';
    yield 'world';
  } finally {
    closed = true; // A real generator closes its owned cursor/file here.
  }
})());

const upper = new TransformStream<string, string>({
  transform(chunk, controller) { controller.enqueue(chunk.toUpperCase()); },
});
const sink = new WritableStream<string>({
  async write(chunk) { await Promise.resolve(); received.push(chunk); },
});
await source().pipeThrough(upper).pipeTo(sink);
console.log(received, closed); // ['HELLO', 'WORLD'], true
```

`pipeTo` coordinates pressure and, by default, abort/cancel propagation on failure. The fixture transforms hello/world, awaits each sink write and closes its source on completion. If the sink rejects, the default pipeline cancels upstream; resources owned by a started generator are closed through its finally.
A cancelled fetch also needs its request/deadline contract.

A stream is consumed once: create another source to demonstrate `for await` separately. A reader locks its stream until released; `writer.write()` must be awaited to avoid piling up promises and queued chunks. For large individual chunks, choose a byte-length queuing strategy and bound chunk sizes, not only the number of chunks.

### 3. Decode text after the byte boundary

This boundary fragment assumes a trusted url, an AbortSignal signal with a bounded deadline, and an asynchronous consumeText(text) supplied by the application. It emits decoded chunks, not automatically complete lines or records; a record parser must retain partial records with a size bound.

```typescript
const response = await fetch(url, { signal }); // trusted URL and bounded deadline
if (!response.ok) throw new Error(`HTTP ${response.status}`);
if (!response.body) throw new Error('No response body');
await response.body
  .pipeThrough(new TextDecoderStream())
  .pipeTo(new WritableStream<string>({
    async write(text) { await consumeText(text); }, // domain helper
  }), { signal });
```

A UTF-8 character can span byte chunks. Calling `Buffer.toString()` on each chunk independently can corrupt it; a streaming decoder retains the incomplete sequence. Limit total bytes and decoded-record sizes when input is untrusted.

### 4. Adapt at the Node HTTP boundary

```typescript
import { createServer } from 'node:http';
import { Readable } from 'node:stream';
import { pipeline } from 'node:stream/promises';

const server = createServer((req, res) => {
  if (req.method !== 'POST' || req.url !== '/echo') {
    res.writeHead(404).end();
    return;
  }
  const bytes = Readable.toWeb(req) as ReadableStream<Uint8Array>;
  res.setHeader('Content-Type', 'application/octet-stream');
  void pipeline(Readable.fromWeb(bytes), res).catch((error) => {
    // pipeline may already have destroyed the response; do not send another body.
    console.error('echo pipeline failed', error);
    if (!res.destroyed) res.destroy(error);
  });
});
server.listen(3000);
```

The adapters live on `node:stream`'s `Readable`: `toWeb` and `fromWeb`. There is no `ReadableStream.toNodeStream`. This echo sketch demonstrates adaptation; production admission also needs authentication, upload-byte limits, and timeouts.

For NDJSON exports, encode a tenant-authorized cursor's rows and pass a `Readable.from(asyncGenerator)` to `pipeline(res)`. Ensure the generator's `finally` closes its cursor and cap each serialized record. The [Node streams chapter](../02-io-and-data/20.1.2.01-streams.md) follows backpressure in detail.

### 5. Separate compression from publishing the backup

```typescript
import { createReadStream, createWriteStream } from 'node:fs';
import { Readable } from 'node:stream';
import { pipeline } from 'node:stream/promises';

async function backupFile(src: string, dest: string): Promise<void> {
  const input = Readable.toWeb(createReadStream(src)) as ReadableStream<Uint8Array>;
  const compressed = input.pipeThrough(new CompressionStream('gzip'));
  await pipeline(Readable.fromWeb(compressed), createWriteStream(dest, { flags: 'wx' }));
}
```

This produces compressed bytes. It does not guarantee that a crash leaves either a complete backup or no backup. Decide how to remove partial files, name temporary files, flush bytes to storage, and rename the completed file.
Compression formats vary by runtime; Node may support formats that other runtimes do not.

#### Let the runner observe every operation that can fail

Create a disposable `test/` directory and save as `test/math.test.mjs`:

```javascript
import { test } from 'node:test';
import assert from 'node:assert/strict';

function divide(a, b) {
  if (b === 0) throw new RangeError('division by zero');
  return a / b;
}

test('division handles its boundary', () => {
  assert.equal(divide(5, 2), 2.5);
  assert.throws(() => divide(1, 0), RangeError);
});

test('await a collaborator result', async (t) => {
  const fetchUser = t.mock.fn(async (id) => ({ id, name: 'Test' }));
  const user = await fetchUser('123');
  assert.equal(user.id, '123');
  assert.equal(fetchUser.mock.callCount(), 1);
});

test('parent waits for each child', async (t) => {
  await t.test('positive input', () => assert.equal(divide(6, 2), 3));
  await t.test('negative input', () => assert.equal(divide(-6, 2), -3));
});
```

Context-scoped mocks are cleaned up with their test. `mock.module` remains version/flag-sensitive (including `--experimental-test-module-mocks` where required); set it up before the import under test and restore it. Function injection often avoids the need for module interception entirely.

### 6. Isolate the resources each test can change

```bash
node --test
node --test --watch
node --test test/math.test.mjs
node --test --test-reporter=tap
node --test --test-concurrency=4
node --test --experimental-test-coverage
```

Default discovery follows Node's documented filename patterns, not only files under `test/`. With the default process isolation, each test file runs in a child process, and several files may run at once. Tests within a file run sequentially unless concurrency is configured.
Separate processes still collide when they mutate the same database, output path, or fixed port.

Use `before`/`after` for resource startup and cleanup, and `beforeEach`/`afterEach` only for per-test isolation. Create an isolated test database, run migrations deliberately, and never point truncation helpers at a production URL. For an HTTP integration test, bind to `127.0.0.1` with port 0, await listen, consume response bodies, and await server close.

Current Node releases stably strip erasable TypeScript syntax by default, but do not type-check or apply `tsconfig` transformations. This became the default in Node 22.18 and 23.6 and stable in 24.12 and 25.2; early Node 22 releases require a flag. Run `tsc --noEmit` separately, and use a compiler or loader when syntax, module resolution, or project configuration requires it.

### 7. Choose by who owns the resource

| Need | Useful starting point | Verify |
| ---------------------------------------- | ------------------------ | ---------------------------------------------------- |
| `fetch` body or runtime-portable library | Web Streams | Available APIs, encodings, cancellation |
| Node files, compression or sockets | Node streams or adapters | Pipeline error and cleanup behavior |
| Built-in library tests | `node:test` | Required mocking, snapshots, coverage and CI tooling |
| Existing framework/plugin suite | Its supported runner | Migration cost and feature differences |

`pipeTo` coordinates demand and cancellation, and an awaited test lets the runner observe completion. The application still owns durable acknowledgments, request limits, shared-fixture isolation, and cleanup for external resources.

## Summary

Streams control demand and ownership across producers and consumers. Tests control completion and fixture lifetime. Both work when the caller respects those boundaries, regardless of whether the selected interface is built in or supplied by a library.

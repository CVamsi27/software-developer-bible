# Node.js Streams

## Definition

A multi-gigabyte upload can pass through a small-memory service only when every stage keeps its queue and each record bounded.


Node streams let a program read data, write data, or do both a chunk at a time. They emit events like other Node event emitters. A stream also defines when more data may be produced, when a write finishes processing, and which component closes resources after a failure.

> **Textbook Definition:** A Node.js stream is an event-based abstraction for incremental data production or consumption, with lifecycle, error and backpressure contracts that coordinate producers and consumers without requiring the whole payload in memory.

## First Principles

1. Data size can exceed memory. Incremental processing lowers the required working set only if each stage and each record remains bounded.
2. A slow consumer cannot accept data forever from a faster producer. Backpressure is the signal telling the producer to pause until the consumer can accept more. Adding a buffer only postpones failure if the producer ignores that signal.
3. Bytes arrive in transport chunks, not application records. Decoding and framing must retain partial input and validate it before invoking business logic.

## Why a small stream can still use too much memory

```text
file read → parser → transform → socket
  queue      partial   queue      queue
             record
```

The working set is the memory needed while processing data. It includes every queue, the largest chunk being processed, parser state kept between chunks, and buffering inside libraries. A stream does not automatically keep memory use constant. An image decoder may buffer a whole image; an object-mode queue may hold only a few objects but use a lot of memory if those objects are huge.

## How the four interfaces fit

| Type | Role | Example |
| --------- | --------------------------------------- | ----------------------------------- |
| Readable | Produces data in response to demand | File reader, async iterable adapter |
| Writable | Accepts data and reports completion | File writer, HTTP response |
| Duplex | Independent readable and writable sides | TCP socket |
| Transform | Writable input drives readable output | Gzip, byte-to-object decoder |

A transform inherits duplex behavior. Its writable and readable modes can differ: a JSON parser takes bytes and emits objects. A custom echo duplex must wake pending reads when new writes arrive, finish its readable side, and bound its own queue; `Transform` is a better fit for a simple echo.

## Trace one write under pressure

1. `destination.write(chunk)` accepts that chunk. A false return means stop issuing further writes until `drain`.
2. The destination invokes its internal write callback when it finishes processing the chunk. Keeping that callback pending communicates the pace upstream.
3. When buffered writes have drained enough for production to resume, `drain` is emitted. Listen on the actual destination, not a wrapper waiting for itself.
4. `end()` says there will be no more writes. `finish` means the writable has processed them; it does not prove disk fsync or remote receipt.

`highWaterMark` is a threshold, not a hard memory cap. Defaults depend on stream type and Node version; configure and measure deliberately. In object mode it counts objects, while byte-mode buffering generally counts bytes (decoded readable strings use code units). `read()` can return available data below the threshold; `null` means there is currently no data for that read, not “buffer below highWaterMark.”

## Let `pipeline` own the lifecycle

```typescript
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';

async function compressFile(input: string, output: string, signal?: AbortSignal): Promise<void> {
  await pipeline(
    createReadStream(input),
    createGzip(),
    createWriteStream(output, { flags: 'wx' }),
    { signal },
  );
}
```

`pipeline` propagates failure and destroys ordinary unfinished streams. The rejected promise is the caller's error path: logging and swallowing it would report success to the caller. An aborted output may contain partial bytes, so decide temporary-file cleanup and atomic replacement separately.

`.pipe()` manages pressure, but it does not coordinate every error and sibling cleanup. Registering error loggers alone does not turn a chain into a safe lifecycle. Pipelines can destroy HTTP responses before a fallback error body is sent; validate what you can before headers and do not write a second response after destruction. Reuse of failed stream objects may also retain listeners; normally create fresh stages.

## Let demand control production

```typescript
import { Readable } from 'node:stream';

class NumberStream extends Readable {
  private current = 0;
  constructor(private readonly max: number) {
    super({ objectMode: true, highWaterMark: 4 });
    if (!Number.isSafeInteger(max) || max < 0) throw new RangeError('Invalid maximum');
  }
  _read(): void {
    while (this.current <= this.max) {
      if (!this.push(this.current++)) return;
    }
    this.push(null);
  }
}

for await (const number of new NumberStream(10)) {
  await new Promise<void>(resolve => setImmediate(resolve));
  console.log(number); // 0 through 10: eleven objects, paced by this consumer
}
```

Choose one consumption style per source: flowing `data` events, manual `readable`/`read`, or async iteration. Mixing them obscures ownership. `Readable.from(iterable)` already adapts a sync/async iterable and keeps its iterator; a hand-written `_read` that creates a fresh iterator on each call can restart the source forever.

## Turn byte chunks into complete records

**NDJSON** means newline-delimited JSON: each line is a complete JSON value. Stream chunks are transport boundaries, not record boundaries. For example, one chunk could end with `{"id":` and the next begin with `1}\n{"id":2}\n`. A parser must buffer the incomplete first line and can then emit two records; parsing each chunk as a complete JSON document would fail.

This generator accepts byte chunks and yields parsed objects. The source owns a valid UTF-8 input contract; StringDecoder replaces malformed sequences, so add a rejecting incremental decoder if the protocol requires strict encoding. Its limit is decoded UTF-16 code units; input chunks are separately bounded by the source. Blank lines are ignored; malformed records fail the flow rather than disappearing silently.

```typescript
import { StringDecoder } from 'node:string_decoder';

async function* parseNdjson(
  source: AsyncIterable<Uint8Array>,
  maxRecordUnits = 64 * 1024,
): AsyncGenerator<unknown> {
  if (!Number.isSafeInteger(maxRecordUnits) || maxRecordUnits <= 0) {
    throw new RangeError('Positive record limit required');
  }
  const decoder = new StringDecoder('utf8');
  let pending = '';
  function parse(line: string): unknown {
    if (line.length > maxRecordUnits) throw new RangeError('Record too large');
    return JSON.parse(line);
  }
  for await (const bytes of source) {
    pending += decoder.write(Buffer.from(bytes));
    let newline: number;
    while ((newline = pending.indexOf('\n')) !== -1) {
      const line = pending.slice(0, newline);
      pending = pending.slice(newline + 1);
      if (line.length > maxRecordUnits) throw new RangeError('Record too large');
      if (line.trim()) yield parse(line);
    }
    if (pending.length > maxRecordUnits) throw new RangeError('Record too large');
  }
  pending += decoder.end();
  if (pending.length > maxRecordUnits) throw new RangeError('Record too large');
  if (pending.trim()) yield parse(pending);
}
```

Use `Readable.from(parseNdjson(source))` to feed an object-mode consumer. Yields allow downstream demand to pace records rather than pushing every record from a large chunk into an unbounded object queue. Validate the parsed shape before aggregation or persistence. Bound the number of distinct metric keys too; a small stream buffer cannot bound an ever-growing map.

If a source emits complete strings as objects (`Readable.from(arrayOfJsonStrings)`), parsing each object can be correct. File/TCP chunks provide no such record guarantee. Flush the final unterminated record according to the format policy.

## Serialize records at the byte boundary

```typescript
import { Transform, type TransformCallback } from 'node:stream';

class EncodeNdjson extends Transform {
  constructor() { super({ writableObjectMode: true }); }
  _transform(value: unknown, _encoding: BufferEncoding, callback: TransformCallback): void {
    try {
      const json = JSON.stringify(value);
      if (json === undefined) throw new TypeError('Not a JSON value');
      if (Buffer.byteLength(json) > 256 * 1024) throw new RangeError('Record too large');
      callback(null, json + '\n');
    } catch (error) { callback(error as Error); }
  }
}
```

A byte-mode destination cannot accept arbitrary objects. Set the input side's object mode explicitly; setting only `objectMode` on a source does not change the destination. A string's UTF-8 byte length can exceed its character count. The serialization itself allocates the full record, so constrain upstream object size as well.

## The same rules apply to images and encryption

A file chunk is not a complete image. Pipe the whole input to one Sharp processor, which owns decoding, resizing, and encoding:

```typescript
import sharp from 'sharp';
await pipeline(
  createReadStream(inputPath),
  sharp({ limitInputPixels: 20_000_000 }).resize(800, 600).jpeg({ quality: 85 }),
  createWriteStream(outputPath, { flags: 'wx' }),
);
```

The pixel limit is an example policy; decoded images and codecs still need concurrency and memory limits. Recreating `sharp(chunk)` for arbitrary input chunks fails because most chunks are not independently decodable images.

Encryption is also a protocol, not merely another transform. Prefer an authenticated mode with a fresh nonce per message/file, preserve its tag and nonce, manage keys outside the example, and reject unauthenticated output before acting on it. A CBC cipher stream with one reused IV and no integrity check is not a secure file format.

## Keep the whole flow bounded under load

Let `pipeline` coordinate ordinary chains, keep record framing separate from business processing, and test aborts, malformed input, and slow destinations. Bound concurrent pipelines as well as each pipeline’s buffers: creating a promise for every file still builds a large queue even when only a few workers run at once.

- Collecting every chunk into an array restores whole-input memory use. If collection is required, enforce a total-byte/object limit and say that it buffers the result.
- Calling a transform callback only after a timer means serialized delay; it does not debounce multiple input chunks into a latest-value result. Debounce requires a separate bounded state/flush/cancellation policy.
- A throttled wrapper waiting for its own `drain` before calling its write callback can deadlock. Wait on the downstream consumer that returned false, and handle its error/close path too.
- Progress counters that increment both processed and total for each chunk always report 100%. Obtain a known total before calculating a percentage; otherwise report bytes and elapsed time.
- Increasing buffer sizes does not guarantee higher throughput. Measure syscall overhead, per-stage memory, CPU, and concurrent flows.

Measure throughput using a monotonic clock, which does not jump when the system clock changes. Avoid dividing by zero in very short samples. Deliberately slow the destination, then inspect `readableLength`/`writableLength`, process memory (RSS and external memory), and whether queues keep growing.

## Summary

A useful stream design bounds data and work at every stage, distinguishes chunks from records, and connects pressure, errors, and completion across the chain. The API name alone establishes none of those properties.

# File System (fs)

Why a config update can look empty. A normal overwrite opens/truncates the target before completing its writes.

## Definition

How can a successful file update still expose partial contents or overwrite a concurrent writer’s change?

`node:fs` provides operations for file contents, directories, file information, open file handles, and change notifications. It offers callback and synchronous APIs; `node:fs/promises` offers promise-based operations. None of these APIs makes several concurrent operations on the same path behave like one all-or-nothing transaction.

> **Textbook Definition:** The Node.js file-system API provides operations on files, directories and descriptors through synchronous and asynchronous interfaces. Ordering, atomicity and durability of multiple operations require explicit coordination and the underlying file system's guarantees.

## First Principles

1. A path names shared mutable state. Checking existence and then opening are separate operations, so another actor can change the file in between.
2. A handle owns an operating-system resource. Every explicit open needs a close path, including decoding, validation, and write failures.
3. A successful write and a crash-durable replacement are different contracts. Buffering, filesystem operations, synchronization, and directory updates each matter.

## How It Works


### 1. Why a config update can look empty

A normal overwrite opens/truncates the target before completing its writes. A concurrent reader or crash can observe an incomplete file. A safer replacement stages a complete new file in the same directory, closes it, then renames it to the target:

```text
create unique temporary file → write → optional sync → close → rename
     failure: close and remove temporary file
     success: target names the replacement
```

Same-filesystem rename can provide atomic namespace replacement on the supported filesystem. It does not provide a read-modify-write transaction or automatically establish power-loss durability. Concurrent writers still need a serialization/version policy.

#### Choose an API by lifetime

| Need | API | Boundary |
| ------------------------ | ---------------------------------- | ------------------------------------------------------------ |
| Small bounded config | `readFile` / `writeFile` | Whole contents are buffered |
| Large input/output | Streams and `pipeline` | Pressure, error, abort and finalization |
| Header or positioned I/O | `open` and `FileHandle.read/write` | Partial reads/writes and explicit close |
| Startup-only script | Sync APIs may fit | They block this JavaScript thread |
| Directory listing | `readdir({ withFileTypes: true })` | Avoid per-entry metadata calls when type alone is sufficient |

No fixed 100-MB threshold decides when to stream. Consider input bounds, concurrency, parsing memory, and the process's memory budget.

### 2. Close a handle on every path

```javascript
const fs = require('node:fs/promises');

async function readPrefix(filePath, limit = 100) {
  if (!Number.isSafeInteger(limit) || limit < 0 || limit > 64 * 1024) {
    throw new RangeError('Invalid prefix limit');
  }
  const handle = await fs.open(filePath, 'r');
  try {
    const buffer = Buffer.alloc(limit);
    const { bytesRead } = await handle.read(buffer, 0, limit, 0);
    return buffer.subarray(0, bytesRead);
  } finally { await handle.close(); }
}
```

For an owned fixture file containing {"revision":1} in UTF-8, a three-byte prefix is the bytes for {"r. A shorter file returns only its actual bytes; the helper does not manufacture a padded header.

A single read may return fewer bytes than requested. This helper returns a prefix, not an exact fixed-length header; an exact-read protocol must loop until it has the required bytes or reaches EOF. Returning bytes also avoids decoding an incomplete UTF-8 sequence at the prefix boundary.

For callbacks, handle both the I/O error and parse failure inside the callback. A surrounding try/catch cannot catch a later asynchronous callback throw. Promise rejections should reach the caller unless the function has an explicit recovery result.

### 3. Replace a file without exposing a partial document

```javascript
const fs = require('node:fs/promises');
const path = require('node:path');
const { randomUUID } = require('node:crypto');

async function replaceJson(target, value) {
  const json = JSON.stringify(value);
  if (json === undefined) throw new TypeError('Not a JSON value');
  const text = json + '\n';
  if (Buffer.byteLength(text) > 1024 * 1024) throw new RangeError('Config too large');
  const temp = path.join(path.dirname(target), `.${path.basename(target)}.${randomUUID()}.tmp`);
  let handle;
  let created = false;
  try {
    handle = await fs.open(temp, 'wx', 0o600);
    created = true;
    await handle.writeFile(text, 'utf8');
    await handle.sync();
    await handle.close();
    handle = undefined;
    await fs.rename(temp, target);
  } finally {
    try { if (handle) await handle.close(); }
    finally {
      if (created) await fs.unlink(temp).catch(error => {
        if (error.code !== 'ENOENT') throw error;
      });
    }
  }
}
```

Calling replaceJson twice with revision1 then revision2 leaves a complete revision2 JSON document and removes the temporary pathname on success. A serialization failure before staging leaves the earlier target intact. Two concurrent calls still do not compare versions; the last successful rename can overwrite another writer's state.

The target and directory must be controlled by the application; this is not protection against an attacker replacing symlinks or the parent directory. Replacement sets the new file's permissions, so choose preservation deliberately. On systems where durable directory entries require directory fsync, file sync alone is insufficient.
Test the required protocol on the deployed filesystem; local disk, container volumes, Windows and network filesystems need distinct assumptions.

### 4. A path check does not grant access

```javascript
const path = require('node:path');

function resolveInside(root, relativeName) {
  const base = path.resolve(root);
  const candidate = path.resolve(base, relativeName);
  const rel = path.relative(base, candidate);
  if (rel === '..' || rel.startsWith('..' + path.sep) || path.isAbsolute(rel)) {
    throw new Error('Path escapes root');
  }
  return candidate;
}
```

A plain string prefix check accepts sibling paths such as `/uploads-old` when the root is `/uploads`. The relative-path check above establishes lexical containment only. Symlinks can still escape it, and a realpath check can race with later access.
Prefer server-generated identifiers and a directory tree untrusted actors cannot mutate; use platform-specific safe opening where the threat model requires it.

A finite config-name allowlist is simpler than accepting arbitrary paths. Cache entries need an invalidation/version policy; a shared mutable cached config can also be changed by its callers.

### 5. Read metadata for what it actually tells you

- `stat` follows a symlink; `lstat` describes the link itself. Use the right one when asking `isSymbolicLink`.
- `mode` includes type bits; `(mode & 0o777).toString(8)` selects ordinary Unix permission bits. Windows and mount behavior differ.
- `access` can distinguish ENOENT, EACCES and other failures, but grants no guarantee about a later open. Open and handle the actual operation's result.
- `mkdir(..., { recursive: true })` creates parent directories; `readdir` with dirents avoids a stat request for each entry when extra metadata is unnecessary.
- `copyFile` copies a file; `cp` supports directory trees. `rename` can fail across filesystems (`EXDEV`); copy/delete is a different, non-atomic protocol.
- `unlink` removes a file name, `rmdir` removes an empty directory, and `rm` supports recursive removal. Keep the deletion root controlled and validate it before recursive cleanup.

### 6. Watches invalidate; they do not certify contents

```javascript
const fs = require('node:fs');
const watcher = fs.watch(configDirectory, (eventType, filename) => {
  // filename may be null; a rename may replace the watched inode.
  // Invalidate relevant cache entries, then debounce/reload/validate from disk.
  invalidateConfigCache(filename); // application helper
});
watcher.on('error', reportWatchFailure);
// During shutdown: watcher.close();
```

`fs.watch` returns an event-emitting watcher, while `fs/promises.watch` returns an async iterator; their consumption styles differ. Events can be coalesced, duplicated or missed, recursive support is platform/version-sensitive, and filename may be unavailable. Watching a file's inode may not follow a replacement; watching its directory and reconciling content is often more suitable.
Polling via `watchFile` trades latency and I/O for different behavior; close/unwatch it when finished.

Log rotation also needs the writer's cooperation: renaming a file does not move an already-open descriptor to a new file. Serialize rotation with writes, reopen the destination deliberately, and bound retention. A rename-and-prune helper alone does not establish safe logging.

### 7. Choose the contract for the job

A config service needs bounded read/parse, schema validation, controlled names and coherent cache invalidation. An upload needs generated storage identifiers, size/content limits and authorization. A log writer needs a bounded queue and a rotation protocol.
These workflows share fs primitives but have different correctness boundaries.

See [Streams](20.1.2.01-streams.md) for byte-safe transformation rather than uppercasing arbitrary Buffer chunks independently.

## Summary

Filesystem correctness depends on naming, ownership and concurrency, not just choosing promises. A complete operation states what is buffered, when handles close, which replacement guarantee it offers, and what can change between steps. Bound concurrent I/O, propagate operational errors, and verify the deployed filesystem’s lifecycle assumptions.

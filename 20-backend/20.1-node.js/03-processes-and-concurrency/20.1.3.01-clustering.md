# Node.js Clustering

Why adding workers can overload a database. one process:     one pool × 10 database connections

## Definition

If one Node process cannot use the host’s available CPU capacity, what should replicate—and who owns the state each copy needs?

`node:cluster` starts Node worker processes that can share a listening port. Each worker has its own JavaScript heap, where its objects live, and its own event loop. Workers communicate with the primary process through inter-process communication (IPC). Cluster uses `child_process.fork`; workers do not share a JavaScript thread pool.

> **Textbook Definition:** Clustering is process-based concurrency in which independently executing Node.js workers serve requests through shared listening infrastructure. Each worker owns its heap and event loop; coordination occurs through inter-process communication or external state.

## First Principles

1. One JavaScript event loop executes callbacks serially, but a host can run several execution contexts in parallel. Additional processes are one way to use that capacity; native threads and worker threads are other ways.
2. Process-local state is independent. More workers multiply caches, sessions, memory and connection pools unless an external authority coordinates them.
3. A worker can fail mid-request. A replacement restores capacity, not the lost response or an uncertain external side effect.

## How It Works


### 1. Why adding workers can overload a database

```text
one process:     one pool × 10 database connections
four workers:   four pools × 10 database connections
three replicas: twelve pools × 10 database connections
```

A pool created in each worker belongs to that worker. Plan capacity across all processes: count each worker's resident memory (RSS), native threads, database connections, and use of external quotas. Use `os.availableParallelism()` as a starting point, then measure CPU and memory limits.
One worker per core is not always the best choice. Heap-only restart thresholds can miss Buffer or native memory pressure and can interrupt requests without relieving the constrained resource.

### 2. How the port is shared

With `SCHED_RR` (default except Windows), the primary accepts connections and distributes them to workers with balancing logic. With `SCHED_NONE`, workers accept on the supplied listening socket; distribution can be uneven. This is not automatically the same as independent `SO_REUSEPORT` listeners.

Distribution happens at the **connection** boundary. Ten keep-alive requests on one connection remain with its worker; a long WebSocket remains with the worker that accepted its upgrade. Round-robin therefore does not promise equal request counts or CPU load.

| Lifecycle event | What it establishes | What remains to check |
| --------------- | ----------------------------------------------- | --------------------------------------------- |
| `fork` | Worker creation began | Initialization may fail |
| `online` | Worker is running and has contacted the primary | Dependencies/server may not be ready |
| `listening` | A server is listening | Application-specific readiness |
| `disconnect` | IPC disconnected | Process can still be alive with other handles |
| `exit` | Worker process terminated | Capacity replacement and uncertain requests |

A `listening` event does not prove that required dependencies are ready. Readiness checks need a reply deadline, and a worker crash can lose an in-flight response or leave an external side effect uncertain. A primary-process crash affects coordination for the whole cluster; the external supervisor defines recovery.

### 3. Replace capacity without racing shutdown

Save as `cluster-server.cjs`. This is a small HTTP lifecycle demonstration, with an example cap and restart budget that should be measured for a real deployment.

```javascript
const cluster = require('node:cluster');
const http = require('node:http');
const { availableParallelism } = require('node:os');
const workerCount = Number(process.env.WORKERS ?? Math.min(availableParallelism(), 4));
const port = Number(process.env.PORT ?? 3000);
if (!Number.isInteger(workerCount) || workerCount < 1 || workerCount > 32) {
  throw new RangeError('WORKERS must be 1..32');
}
if (!Number.isInteger(port) || port < 0 || port > 65535) throw new RangeError('Invalid PORT');

if (cluster.isPrimary) {
  let stopping = false;
  let hardStop;
  const pendingRestarts = new Set();
  let recentFailures = [];
  const workers = new Set();
  const live = () => [...workers];

  function shutdown(code = 0) {
    if (stopping) return;
    stopping = true;
    process.exitCode = code;
    for (const timer of pendingRestarts) clearTimeout(timer);
    pendingRestarts.clear();
    for (const worker of live()) {
      if (worker.isConnected()) worker.send({ type: 'shutdown' }, error => {
        if (error) worker.process.kill('SIGTERM');
      });
      else worker.process.kill('SIGTERM');
    }
    if (live().length) hardStop = setTimeout(() => {
      process.exitCode = 1;
      for (const worker of live()) worker.process.kill('SIGKILL');
    }, 8000);
  }

  cluster.on('exit', (worker, code, signal) => {
    workers.delete(worker);
    console.log(JSON.stringify({ event: 'exit', pid: worker.process.pid, code, signal }));
    if (stopping) {
      if (live().length === 0) clearTimeout(hardStop);
      return;
    }
    const now = Date.now();
    recentFailures = recentFailures.filter(time => now - time < 60_000);
    recentFailures.push(now);
    if (recentFailures.length > 5) { shutdown(1); return; }
    const timer = setTimeout(() => {
      pendingRestarts.delete(timer);
      if (!stopping) cluster.fork();
    }, Math.min(2000, 100 * 2 ** (recentFailures.length - 1)));
    pendingRestarts.add(timer);
  });
  cluster.on('listening', (worker, address) => {
    console.log(JSON.stringify({ event: 'listening', pid: worker.process.pid, port: address.port }));
  });
  cluster.on('fork', worker => {
    workers.add(worker);
    worker.on('error', error => console.error('worker IPC error', error));
  });
  process.on('SIGTERM', () => shutdown());
  process.on('SIGINT', () => shutdown());
  for (let index = 0; index < workerCount; index++) cluster.fork({ WORKER_SLOT: String(index) });
} else {
  let draining = false;
  const server = http.createServer((req, res) => {
    if (draining) { res.writeHead(503, { Connection: 'close' }).end(); return; }
    res.end(`Worker ${process.pid}`);
  });
  function drain() {
    if (draining) return;
    draining = true;
    server.close(error => {
      if (error) process.exitCode = 1;
      // Close owned database/log resources here before disconnecting.
      if (process.connected) process.disconnect();
    });
  }
  process.on('message', message => { if (message?.type === 'shutdown') drain(); });
  process.on('SIGTERM', drain);
  process.on('disconnect', drain);
  server.on('error', error => { console.error(error); process.exitCode = 1; drain(); });
  server.listen(port, '127.0.0.1');
}
```

Shutdown disables replacement first and waits for actual worker exits. A disconnected worker with leaked timers or resources is still subject to the deadline. Unexpected clean exit while serving still reduces capacity, so the example replaces it too.
The worker branch has no database/websocket resources; adding them requires extending the drain protocol.

Cluster workers calling `listen(0)` for the same server share the selected random port; it does not independently choose a unique port for each worker. Use a readiness protocol that includes initialization of all required resources before listening/admitting requests.

### 4. State and IPC are separate designs

`worker.send` and `process.send` serialize messages. Default serialization is JSON; advanced serialization supports more data types but is still copying/serialization, not a general zero-copy Buffer channel. A send callback does not mean the application completed a task.
Include task IDs, acknowledgments, bounded queues, and an error policy when IPC carries business work.

Sending a plain request description does not transfer its response socket. A custom connection router also needs readiness, socket handoff/backpressure, disconnect handling and a zero-worker policy. Prefer cluster's supported port sharing or a maintained front proxy when that is sufficient.

A primary can aggregate worker metrics in its own memory, but that authority dies with the primary and does not cover another host. Shared quotas, sessions and durable job ownership belong in an external store or protocol. See [Redis atomic patterns](../../20.8-caching/20.8.03-advanced-redis-patterns.md); a per-worker limit of 100 can become roughly 100 times the worker count across independent buckets.

### 5. When a user needs the same worker

Raw WebSocket messages already stay on one established connection; no additional IP affinity is required for those messages. Reconnects need external session/room state. Transports that use multiple requests for one logical session, such as Socket.IO polling, may need affinity plus a shared adapter.

An `IP:remotePort` key changes on reconnect, so it cannot identify a session reliably. Network address translation (NAT) can put many users behind one public IP address; routing only by IP may therefore send all of them to one worker. Sending a session back to the same worker is called affinity.
Affinity does not verify identity, authorize access, or make session state available after a worker fails.

## Deployment decisions

| Requirement | Useful option | Cost / limit |
| --------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| Several isolated HTTP event loops on one host | Cluster or process supervisor | Multiplied memory/pools and primary lifecycle |
| CPU job parallelism within one process | Worker pool | Heap/message/shared-memory protocol |
| Independently scheduled containers/hosts | Replicas and external load balancer | Readiness, distributed state and external admission |
| Restart during deployment | Supervisor/orchestrator or explicit rolling protocol | New worker must become ready before retiring old one |

Cluster and containers can coexist when resource and lifecycle budgets are deliberate. Workers are scheduled by the operating system, not pinned to numbered cores. Async database I/O already yields to the event loop, so moving those calls to cluster workers is not CPU offload.
One process per container is a common simpler choice, not a universal constraint. A “zero downtime” claim requires deployment, drain, and retry evidence; respawning after exit alone cannot establish it. PM2 or systemd can supervise processes, but do not remove application shutdown and consistency responsibilities.

## Summary

Cluster multiplies isolated event loops while sharing a listening port. Measure total process and external-resource use, establish readiness before admission, bound restarts, and keep shared-state contracts independent of connection balancing. Cluster alone cannot provide shared quotas, durable jobs, or uninterrupted deployment.

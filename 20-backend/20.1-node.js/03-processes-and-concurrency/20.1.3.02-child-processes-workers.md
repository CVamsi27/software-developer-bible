# Child Processes & Worker Threads

Why a naive pool gives a request the wrong result. Suppose worker 0 is busy and worker 1 finishes.

## Definition

When image processing stalls request handling, should the work move to a worker thread, a child process, or a separately scheduled job?

A child process has its own address space: memory addresses refer to that process's memory. A Node child created with `fork` has its own instance of V8, Node's JavaScript engine, and its own event loop. A spawned executable may instead be Python, a media encoder/decoder (codec), or another program. Inter-process communication (IPC) is optional.
Standard output (`stdout`) and standard error (`stderr`) provide separate channels for output.

> **Textbook Definition:** Child processes isolate execution in separate address spaces; worker threads isolate JavaScript execution contexts within one process. Communication uses messages, transferable memory or explicitly shared memory according to the isolation boundary.

A Node worker thread lives in the same process but has a separate V8 execution environment, called an isolate. It has its own JavaScript heap, module instances, and event loop. Workers do not normally share objects. They can exchange copied messages through structured cloning, transfer ownership of an ArrayBuffer, or deliberately share bytes through a SharedArrayBuffer.
The copy, transfer, and share choices are compared below.

## First Principles

1. CPU work on a JavaScript thread delays its other callbacks. A different execution context provides parallelism; slicing can provide fairness when parallelism is unnecessary.
2. Sending data has a cost and an ownership rule. Copy, transfer and shared-memory access produce different lifetimes and failure modes.
3. Parallelism needs a limit on accepted work, called admission control. A pool must limit running jobs, queued jobs, and message sizes, and define what cancellation does. Starting a new worker for every request can exhaust resources instead of fixing the original bottleneck.

## How It Works


### 1. Why a naive pool gives a request the wrong result

Suppose worker 0 is busy and worker 1 finishes. A global `active` count changes from two to one, but that does not mean worker index 1 is the next available worker after subsequent completions. Attaching `once('message')` for each request to a randomly chosen worker can also let one message satisfy several requests.

```text
job identity → selected idle worker → one in-flight assignment
   → result/error/exit/timeout → settle that job once → release worker
```

Track worker state and task IDs explicitly, or use a maintained pool that implements the lifecycle. A count of active jobs is not an idle-worker map.

### 2. Choose the boundary

| Tool | Execution / output | Fit |
| ---------- | -------------------------------------------------- | ------------------------------------ |
| `spawn` | Executable + argument array; streaming stdio | Long output and external tools |
| `execFile` | Executable + arguments; buffered output by default | Bounded tool results without a shell |
| `exec` | Command through a shell; buffered output | Intentionally trusted shell syntax |
| `fork` | Node module with IPC channel | Process-separated Node work |
| `Worker` | Node thread with its own isolate | CPU tasks within the process |

`spawn` defaults to no shell. An argument array avoids shell interpolation, but an executable can still interpret malicious arguments as options; validate values and use an option terminator when supported. A child process is not by itself a security sandbox: inherited filesystem, network and OS privileges still apply.

### 3. Run an executable with bounded output

```javascript
const { execFile } = require('node:child_process');
const { promisify } = require('node:util');
const executeFile = promisify(execFile);

async function nodeVersion() {
  const { stdout, stderr } = await executeFile(process.execPath, ['--version'], {
    timeout: 5000,
    maxBuffer: 64 * 1024,
    encoding: 'utf8',
  });
  return { stdout: stdout.trim(), stderr }; // stderr alone does not mean failure
}
```

Nonzero exit, launch failure and maxBuffer errors reject the promise. A timeout requests termination; OS/process-tree behavior still needs a policy for tools that ignore signals or spawn descendants. Do not pass untrusted text into a shell command and assume maxBuffer makes it safe.

For streaming output, use `spawn` plus `pipeline` into a controlled destination, drain both stdout and stderr, and handle `error` and `close`. `exit` does not guarantee stdio is closed; `close` follows closure of those channels. Apply a total output policy too: streaming to an unbounded collector or growing log file remains unbounded.

### 4. Settle a one-shot worker task exactly once

Save the helper as `run-one.cjs`. It demonstrates lifecycle ownership, not a per-request production pool.

```javascript
const { Worker } = require('node:worker_threads');

function runOne(workerFile, workerData, { timeoutMs = 5000 } = {}) {
  if (!Number.isSafeInteger(timeoutMs) || timeoutMs <= 0) {
    return Promise.reject(new RangeError('Invalid timeout'));
  }
  return new Promise((resolve, reject) => {
    const worker = new Worker(workerFile, { workerData });
    let settled = false;
    const timer = setTimeout(() => finish(new Error('Worker deadline exceeded')), timeoutMs);
    const onMessage = result => finish(null, result);
    const onError = error => finish(error);
    const onExit = code => finish(new Error(`Worker exited without a result (${code})`));
    async function finish(error, result) {
      if (settled) return;
      settled = true;
      clearTimeout(timer);
      try {
        await worker.terminate(); // wait for owned worker to stop
        if (error) reject(error); else resolve(result);
      } catch (terminationError) { reject(error ?? terminationError); }
      finally {
        worker.off('message', onMessage);
        worker.off('error', onError);
        worker.off('exit', onExit);
      }
    }
    worker.once('message', onMessage);
    worker.on('error', onError);
    worker.once('exit', onExit);
  });
}
module.exports = { runOne };
```

An exit code zero without a result still rejects; otherwise a request could wait forever. Once a result arrives, termination releases resources for this one-shot protocol. A persistent pool instead releases the worker for its next correlated task.
Bound input/output sizes and validate the result shape at the caller.

Save as `compute-worker.cjs`:

```javascript
const { parentPort, workerData } = require('node:worker_threads');
if (!Number.isSafeInteger(workerData.iterations) || workerData.iterations < 0 || workerData.iterations > 10_000_000) {
  throw new RangeError('Invalid iteration count');
}
let result = 0;
for (let index = 0; index < workerData.iterations; index++) result += Math.sqrt(index);
parentPort.postMessage({ result });
```

From a caller in the same disposable directory, runOne(require('node:path').resolve(__dirname,'compute-worker.cjs'),{iterations:4}) resolves to {result:4.146264369941973}. The helper terminates its one-shot worker before settling. Changing iterations to -1 rejects through the worker error path; a clean exit with no message is also failure, and a worker that never answers reaches the deadline.

### 5. Bound accepted work before it reaches the pool

This example pins the current stable Piscina 5.3.2 release with `npm install --save-exact piscina@5.3.2`. Its published support range starts at Node.js 24; Piscina 6 is currently a prerelease. Check the release notes and runtime contract when changing either version.
Save this module as pool.cjs beside pool-worker.cjs.

```javascript
const Piscina = require('piscina');
const path = require('node:path');
const { availableParallelism } = require('node:os');

const maxThreads = Math.min(availableParallelism(), 4);
const maxOutstanding = maxThreads + 32;
let outstanding = 0;
let accepting = true;
const pool = new Piscina({
  filename: path.resolve(__dirname, 'pool-worker.cjs'),
  minThreads: 1,
  maxThreads,
  maxQueue: 32,
});
pool.on('error', error => console.error('pool failed', error));
async function computeTask(iterations, signal = AbortSignal.timeout(5000)) {
  if (!accepting) throw new Error('Worker pool is closing');
  if (outstanding >= maxOutstanding) throw new Error('Worker admission limit reached');
  outstanding++;
  try {
    return await pool.run({ iterations }, { signal });
  } finally {
    outstanding--;
  }
}
async function closePool() {
  accepting = false;
  await pool.close();
}
module.exports = { pool, computeTask, closePool };
// On graceful shutdown: await closePool().
// On forced shutdown/cancellation: await pool.destroy() as required by the policy.
```

`pool-worker.cjs` exports the task function rather than manually using parentPort:

```javascript
module.exports = ({ iterations }) => {
  if (!Number.isSafeInteger(iterations) || iterations < 0 || iterations > 10_000_000) {
    throw new RangeError('Invalid iteration count');
  }
  let result = 0;
  for (let index = 0; index < iterations; index++) result += Math.sqrt(index);
  return { result };
};
```

The wrapper counts accepted work until settlement, including queued tasks with abort signals. This gives an application admission bound independently of the pool library's internal scheduling or cancellation queues. The queue/thread numbers are example limits.
Handle queue-full rejection and aborted tasks as operational outcomes; pool cancellation cannot undo an external side effect. A batch API must also validate concurrency and define empty-input behavior instead of calculating a zero chunk size and looping forever.

### 6. Choose who owns the task data

| Operation | Sender after send | Receiver / synchronization |
| -------------------------- | -------------------- | ------------------------------------------------------------------- |
| Ordinary message | Retains its value | Structured clone; prototypes/functions are not generally preserved |
| Transfer owned ArrayBuffer | Buffer is detached | Receiver owns bytes; original views cannot keep using them |
| SharedArrayBuffer | Retains shared bytes | Both observe shared storage; use an agreed synchronization protocol |

Do not transfer the backing ArrayBuffer of an arbitrary pooled Buffer: it may be non-transferable or include an entire slab outside the visible range. Allocate deliberately owned storage for transfer and specify exactly which bytes cross the boundary. SharedArrayBuffer is shared, not a transferable object.

For a shared integer counter, each increment must be atomic:

```javascript
// counter-worker.cjs
const { workerData, parentPort } = require('node:worker_threads');
const counter = new Int32Array(workerData.shared);
for (let index = 0; index < 100_000; index++) Atomics.add(counter, 0, 1);
parentPort.postMessage('done');
```

Create one `SharedArrayBuffer(4)` in the parent and send that same shared storage to two workers; after both report completion, the counter is 200,000. Atomic operations do not make arbitrary multi-step shared-state algorithms correct, and signed 32-bit counters can still overflow. Avoid blocking the main event loop with `Atomics.wait`.

### 7. Offload work only when parallelism helps

Image codecs may already use native threads; stacking worker pools over them can oversubscribe CPU and memory. External video/Python tools need process-tree, stdio, timeout and privilege policies. A HTTP CPU endpoint needs a bounded queue plus result correlation, and should stop/cancel work when the client no longer needs it according to the side-effect policy.

Worker startup/memory varies with Node, imports and payloads. Measure cold/warm execution and queue wait; fixed “1–5 ms” startup claims or a mandatory core-count cap are not portable. Each worker loads module state separately, and JS resource limits do not cap every native/external allocation.

## Summary

Parallel execution needs a data contract and an owned lifecycle. Processes isolate address spaces; workers isolate JavaScript heaps while allowing explicit transfer or shared memory. Correlate each task, cap queues and payloads, settle once on every terminal path, and close workers during shutdown.

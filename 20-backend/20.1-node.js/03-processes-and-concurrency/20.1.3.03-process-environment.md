# Process & Environment

## Definition

`process` exposes this Node process's environment, arguments, standard I/O, runtime identity, resource measurements and lifecycle events. These values describe the current execution context; they do not establish a service's readiness or persist changes into the parent shell.

## First Principles

1. One application artifact runs in several deployments. Injecting configuration at startup separates the artifact from deployment-specific addresses, policy and secrets.
2. Environment values are strings. Parsing and validating at one boundary prevents an empty value, `"0"`, or malformed integer from silently selecting a different behavior.
3. Shutdown is a state transition with a deadline. Stop admitting work before closing the dependencies that in-flight work still needs.

## Why a “30-second shutdown” exits after 30 seconds of uptime

A shutdown timer created during startup starts counting immediately. `unref()` means it does not keep the process alive by itself; it does not defer the timer until a signal. Create the deadline when shutdown begins:

```text
running → mark unready / stop admission → drain HTTP/jobs
        → close owned pools/files/logs → natural exit
        ↘ deadline expires → forced failure exit
```

A status of zero reports success; it does not prove cleanup completed. `process.exit()` can terminate queued output and pending I/O. Prefer setting `exitCode` and releasing handles for ordinary completion, with explicit forced exit only at the chosen fallback boundary.

## Code: parse configuration without silently replacing valid zero

```javascript
function readConfig(env = process.env) {
  function integer(name, fallback, min, max) {
    const raw = env[name] ?? String(fallback);
    if (!/^(0|[1-9]\d*)$/.test(raw)) throw new Error(`Invalid ${name}`);
    const value = Number(raw);
    if (!Number.isSafeInteger(value) || value < min || value > max) throw new Error(`Invalid ${name}`);
    return value;
  }
  const mode = env.NODE_ENV ?? 'development';
  if (!['development', 'test', 'production'].includes(mode)) throw new Error('Invalid NODE_ENV');
  const debugRaw = env.DEBUG ?? 'false';
  if (!['true', 'false'].includes(debugRaw)) throw new Error('Invalid DEBUG');
  const databaseRaw = env.DATABASE_URL;
  if (!databaseRaw) throw new Error('Missing DATABASE_URL');
  let database;
  try { database = new URL(databaseRaw); }
  catch { throw new Error('Invalid DATABASE_URL'); } // do not print credentials
  if (!['postgres:', 'postgresql:'].includes(database.protocol) || !database.hostname) {
    throw new Error('Invalid DATABASE_URL');
  }
  return Object.freeze({
    mode,
    port: integer('PORT', 3000, 0, 65535), // zero deliberately permits a test port
    poolSize: integer('DB_POOL', 10, 1, 100),
    timeoutMs: integer('TIMEOUT_MS', 5000, 1, 60_000),
    debug: debugRaw === 'true',
    databaseUrl: databaseRaw,
  });
}
```

The ranges and PostgreSQL-only URL are application policy. Validate authorization/transport requirements separately; parsing a URL does not prove a reachable or authorized database. `NODE_ENV` influences libraries that read it, not a universal Node production-safety switch.

Changes to `process.env` affect this process and environments inherited by subsequently spawned children. They do not update an already-running child or parent shell. Worker threads normally receive a copy; `SHARE_ENV` is an explicit different contract. Build a restricted child environment when a subprocess does not need the application's secrets.

## Load local configuration deliberately

```bash
node --env-file=.env app.cjs
```

Modern Node supports env-file loading; values already in the launch environment take precedence over that file. Check the pinned Node version when using optional-file or programmatic loading features. A maintained dotenv parser is also an option; a hand-written split-on-equals parser mishandles quoting, comments, empty values and multiline syntax.

Keep files containing credentials out of version control and log output. A non-secret `.env.example` can document the contract. Secret managers may inject environment values or mounted files; the chosen transport still needs access controls, rotation and a documented precedence policy.

## Code: parse only the CLI options you support

```javascript
const { parseArgs } = require('node:util');
const { values, positionals } = parseArgs({
  args: process.argv.slice(2),
  options: {
    name: { type: 'string' },
    verbose: { type: 'boolean', short: 'v' },
  },
  allowPositionals: true,
  strict: true,
});
console.log({ name: values.name, verbose: values.verbose ?? false, positionals });
```

For a normal script, argv contains the executable path, script path and remaining arguments. `process.execPath` gives the resolved executable; `process.argv0` preserves the original launch argv[0], which need not be a resolved binary path. Define the CLI's own exit-code meanings; code 2 has no automatic “shell builtin misuse” meaning in Node.

## Code: one idempotent shutdown path

```javascript
function installShutdown(server, closeResources, deadlineMs = 10_000) {
  if (!Number.isSafeInteger(deadlineMs) || deadlineMs <= 0) throw new RangeError('Invalid deadline');
  let draining = false;
  let shutdownPromise;
  function shutdown() {
    if (shutdownPromise) return shutdownPromise;
    draining = true;
    const deadline = setTimeout(() => {
      server.closeAllConnections(); // upgraded sockets require separate ownership
      process.exit(1);
    }, deadlineMs);
    deadline.unref();
    shutdownPromise = (async () => {
      try {
        try {
          await new Promise((resolve, reject) => server.close(error => error ? reject(error) : resolve()));
        } finally { await closeResources(); }
        process.exitCode = 0;
        clearTimeout(deadline);
      } catch (error) {
        process.exitCode = 1;
        console.error('Shutdown failed', error);
        // Keep the deadline armed if another live handle prevents natural exit.
      }
    })();
    return shutdownPromise;
  }
  process.on('SIGTERM', shutdown);
  process.on('SIGINT', shutdown);
  return {
    shutdown,
    isDraining: () => draining,
    removeHandlers() {
      process.off('SIGTERM', shutdown);
      process.off('SIGINT', shutdown);
    },
  };
}
```

Wire readiness and request/job admission to `isDraining()`. After stopping HTTP admission, drain requests while their database connections remain usable; close those resources afterward. On supported modern Node versions, `server.close()` also handles idle keep-alive connections. Track upgraded/WebSocket connections, worker pools, consumers and recurring timers separately.

Registering signal listeners changes the default signal behavior. On POSIX, the default termination status is commonly 128 plus the signal number; graceful zero/failure exit is an application decision. Windows signal support and process-manager behavior differ. Repeated signals here return the same promise rather than running cleanup twice.

## Unexpected failures and final events

| Event / action | Appropriate purpose | Boundary |
| ---------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `beforeExit` | Observe natural exhaustion of referenced work | Not a reliable cleanup hook for explicit exit or uncaught failure; scheduling work can trigger it again |
| `exit` | Minimal synchronous final reporting | Async cleanup cannot complete there |
| `uncaughtExceptionMonitor` | Observe failure without overriding normal termination | Report safely; it is not a recovery mechanism |
| `uncaughtException` listener | Explicit fatal-error policy | Continuing ordinary service may use inconsistent state |
| `unhandledRejection` | Explicit unexpected rejection policy | Default behavior depends on Node flags/listeners; a logging listener can alter termination behavior |

Catch expected operational failures near their request/job boundary. For an unexpected uncaught failure, perform only the recovery policy's safe reporting/cleanup and let an external supervisor restart the service. Do not install a listener solely to suppress the failure and keep serving.

## Measure process resources correctly

```javascript
const before = process.cpuUsage();
const wallStart = process.hrtime.bigint();
// Perform a measured operation here.
const cpu = process.cpuUsage(before);
const elapsedMs = Number(process.hrtime.bigint() - wallStart) / 1e6;
const memory = process.memoryUsage();
console.log({ elapsedMs, cpuMicroseconds: cpu.user + cpu.system,
  rss: memory.rss, heapUsed: memory.heapUsed, external: memory.external,
  arrayBuffers: memory.arrayBuffers });
```

CPU time is not elapsed latency and can exceed elapsed time when multiple threads consume CPU. `arrayBuffers` is included in `external`; do not sum both as independent categories. RSS covers the process's resident memory, not just the JavaScript heap. For workers, some measurements are per isolate while RSS is process-wide; use the documented scope.

`process.resourceUsage()` provides OS resource counters, including `ipcSent` and `ipcReceived`; there is no generic `ipcMessages` field. `maxRSS` uses KiB in Node's documented contract. Platform support and counter meaning vary, so this is not a substitute for per-operation application metrics.

Identity/cwd/title/umask are process-wide context. Guard POSIX-only APIs such as `getuid/getgroups` before using them on Windows. `process.umask()` controls creation permission bits; it does not retroactively fix existing files. `chdir()` changes the base for later relative paths and is unavailable in workers.

## Standard I/O is also a lifetime

Use `readline` for line-oriented stdin and close its interface when finished. Use one consumption style per stdin stream. stdout/stderr buffering and synchronous behavior depend on the platform and destination; large writes can require backpressure handling. Setting an exit code and allowing natural exit can preserve output that immediate `process.exit()` would truncate.

## Real-world choices

A service needs typed startup config, readiness tied to admission, and a signal-driven drain protocol. A CLI needs strict argument parsing, bounded input/output, meaningful exit status and resource cleanup. An operator diagnostic should report enough runtime identity and metrics without publishing credentials, full environment dumps or internal health details to unauthenticated clients.

## Common mistakes

Using `parseInt('10junk')`, truthiness for `"false"`, or `Number(value) || fallback` silently accepts or replaces values. Closing a database before HTTP drains breaks in-flight requests. A startup-created shutdown timer kills a healthy service, and an `exit` listener cannot rescue unfinished async cleanup.

## Best Practices

Parse once, validate explicit ranges, and keep secret-bearing configuration out of logs. Make one owned shutdown function handle signals and programmatic shutdown, test repeated calls and deadline failure, and release every recurring handle before expecting natural exit.

## Summary

Process configuration and lifecycle are explicit contracts. Typed startup parsing selects intended behavior; ordered admission/drain/cleanup and a deadline determine when termination is successful.

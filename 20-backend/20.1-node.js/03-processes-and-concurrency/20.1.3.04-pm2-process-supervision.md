# PM2 Process Supervision

The server accepts a payment request, commits it, then crashes before sending the response. A process supervisor can restore a server process; it cannot tell the client whether the payment committed or recreate the missing response.

## Definition

PM2 is a Node.js process manager: its daemon, a long-running background process, starts and monitors application processes, records them in a process list, and can replace a process that exits. Its job is to restore service capacity. Readiness, graceful shutdown, durable state and safe retries still belong to the application and deployment.

> **Textbook Definition:** Process supervision is the external control of a program's lifecycle: a supervisor starts the program, observes its termination or health, applies a restart policy and reports its state. It does not roll back side effects or guarantee that work in progress completed.

## First Principles

1. A process is the operating system's unit of execution and resource isolation. A supervisor can create another process after one exits, but the replacement starts with a new heap and no copy of the old process's in-memory state.
2. A process can fail between any two observable events. If a client times out after a database commit, repeating the request is safe only when the operation has an idempotency or reconciliation contract.
3. Starting is not readiness. Listening on a port may happen before required dependencies or caches are usable, so deployments need an explicit readiness condition.

## 1. Follow one process from CLI to restart

The `pm2` command-line interface (CLI) is a client. It asks the PM2 daemon to manage an application and can exit while the daemon and application continue:

```text
operator → pm2 CLI → PM2 daemon / process list
                         │ start, monitor, replace
                         ▼
                 Node process or cluster workers
                         │
                 operating system / container
```

`pm2 start app.js` both starts the script and registers it in the daemon's process list. `pm2 ls` shows that managed state. A saved process list is a separate step: `pm2 save` writes the list to disk, while the host's startup integration must be configured to resurrect it after a reboot. Neither action preserves the application's memory or in-flight work.
See the [PM2 process-management guide](https://pm2.io/docs/runtime/guide/process-management/).

Fork mode launches each instance as a separate child process. Cluster mode uses Node's cluster machinery to create server processes behind a shared listening port. Fork mode is the simpler boundary for a single instance or independent workers that do not need a shared port.
Cluster mode is useful for HTTP capacity across cores, but each worker has its own heap, connection pools and local caches. See [Node.js clustering](20.1.3.01-clustering.md) before treating multiple workers as one stateful application.

## 2. Make replacement safe for requests

A useful lifecycle is:

```text
start → initialize dependencies → become ready → admit work
  → receive stop/reload → stop new work → drain accepted work
  → close owned resources → exit
```

In cluster mode, PM2 can reload workers one at a time. Set `wait_ready: true` in the ecosystem configuration and have the application send `process.send('ready')` only after its prerequisites and listener are ready:

```javascript
module.exports = {
  apps: [{
    script: './server.js',
    instances: 2,
    exec_mode: 'cluster',
    wait_ready: true,
    listen_timeout: 10_000,
    kill_timeout: 10_000,
  }],
};
```

In the application's startup sequence, send the ready message after connecting required dependencies and binding the server:

```javascript
async function start() {
  await connectDatabase();
  server.listen(port, () => process.send?.('ready'));
}
start();
```

Choose timeouts to match measured startup and shutdown budgets. A `listen_timeout` is not a health check: PM2 may consider a worker ready when the wait expires even if it never sent the ready message. Alert on that condition and use the deployment's health policy to reject or roll back an unhealthy release.
The reload path can fall back to a regular restart if it cannot reload within its timeout. A rolling reload therefore reduces the availability gap, but it does not prove every in-flight request finishes. The old worker must drain correctly, and a lost response still requires client-safe retry semantics.
See [PM2 load balancing](https://pm2.io/docs/runtime/guide/load-balancing/) and [graceful startup and shutdown](https://pm2.io/docs/runtime/best-practices/graceful-shutdown/).

Bound crash loops with a restart policy, minimum uptime and backoff appropriate to the service. A process that repeatedly starts and fails is not healthy capacity; alert on restart frequency and time spent unavailable. Memory-triggered restarts are a recovery action, not a memory limit: they can interrupt requests and do not fix a leak or an oversized workload.

| Failure | What PM2 can help with | What still needs an explicit design |
| ----------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| One application process exits | Start a replacement according to policy | Rebuild readiness; account for lost in-flight requests and process-local state |
| PM2 daemon is unavailable | Recover the control channel according to the host setup | Application processes may still be running; verify their state and recovery instead of assuming both layers share one lifetime |
| Host or container is lost | Nothing on that failed host can restart itself | Use host/container orchestration, replicas, external state and traffic failover |

On a VM, systemd commonly owns the long-lived service/host startup boundary, while PM2 manages Node application processes within it. In a container platform, the orchestrator owns placement and replica recovery. Stacking supervisors is reasonable only when each has a clear boundary and signal/exit behavior; otherwise operators can get duplicate restarts and confusing health reports.

## Summary

PM2 restores process capacity and exposes process state; it does not restore memory, complete requests or reverse side effects. Choose fork or cluster mode for the execution topology, define readiness and draining in the application, bound restart loops, and assign host or container recovery to the layer that can survive that failure.

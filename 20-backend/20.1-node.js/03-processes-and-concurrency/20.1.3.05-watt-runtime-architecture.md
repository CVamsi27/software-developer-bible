# Watt Runtime Architecture

A team wants separate API, frontend and background applications, but running each as a separate service adds ports, network calls, deployment work and operational ownership. Keeping them as ordinary modules in one process removes those costs, but also shares one event loop, module graph and deployment boundary.

## Definition

Watt is a Node.js application runtime between those choices. The `wattpm` command creates and operates a Watt project; the runtime process coordinates configured applications, runs each application in worker threads and routes supported internal HTTP requests between them. The result gives applications separate JavaScript execution contexts while keeping them in one process and one deployment unit.

> **Textbook Definition:** An application runtime is a host environment that initializes, supervises and coordinates application components. Watt hosts applications in worker threads within one Node.js process, providing isolate-level memory and event-loop separation without process-level failure or deployment isolation.

## First Principles

1. A JavaScript module boundary is not a runtime boundary. Modules in one isolate can share globals and block the same event loop; separate worker threads create separate V8 isolates, heaps, module registries and event loops.
2. A worker thread is not a process. It provides an independent JavaScript execution context, but the operating system still sees the surrounding Node process as the main resource and failure boundary.
3. Code isolation and deployment independence are different choices. Watt provides the first across applications in one runtime; moving one application on an independent release schedule still requires a separate deployment.

## How It Works

### 1. One process, several application workers

The runtime's main thread manages the application lifecycle; application code runs in worker threads:

```text
one Node.js process
┌────────────────────────────────────────────────────┐
│ Runtime main thread: startup order, worker health, │
│ shared logging/metrics/tracing configuration       │
│                                                    │
│  worker: web app     worker: API     worker: jobs  │
│  own isolate/heap    own isolate     own isolate   │
└────────────────────────────────────────────────────┘
             one process and deployment boundary
```

An isolate is the V8 JavaScript engine's separate execution environment. A worker's ordinary objects and module cache are not shared with another worker, and CPU-bound JavaScript in one worker does not block another worker's event loop. Native code, process-wide memory pressure, operating-system resources and the runtime process remain shared concerns. Watt's architecture documentation describes this as hard application boundaries within a shared deployment unit; see [Watt architecture](https://docs.platformatic.dev/docs/concepts/watt-architecture).

The runtime starts applications according to their declared dependencies, allowing independent applications to start in parallel after prerequisites are ready. It monitors worker health and can restart or replace an unhealthy worker. Shared runtime facilities such as logs and telemetry can present activity from multiple applications together, but that does not make application-local state shared.

### 2. Follow an internal request

An application can call another application with an HTTP-shaped URL such as `http://catalog.plt.local/items`. In Watt's internal mesh, the worker's Undici dispatcher recognizes the `.plt.local` host and routes the request through a `MessagePort` to the destination worker:

```text
web worker → fetch(catalog.plt.local) → Watt dispatcher
           → MessagePort → catalog worker → HTTP response
```

That path does not open a TCP connection or perform a Domain Name System (DNS) lookup. The caller still uses familiar `fetch` request and response semantics, but the body and response cross a thread boundary through Node's `MessagePort` (a thread-to-thread messaging endpoint). Internal calls avoid network setup and wire transport; they are not free, and a chatty call graph or large payload still costs time and memory.
Keep deadlines, error handling, authorization and payload limits at the application boundary. The [Watt architecture guide](https://docs.platformatic.dev/docs/concepts/watt-architecture) documents the internal hostname and routing model.

### 3. Know which failures stay contained

If one worker exits, the runtime can restore that worker and the other workers may continue. Requests already assigned to the failed worker can still fail, and process-local state in that worker is gone. A native crash, process-wide out-of-memory condition or runtime exit can affect every application in the process.
Threads also cannot receive independent container CPU or memory quotas.

| Requirement | Watt runtime | Separate process/runtime |
| ----------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------- |
| Keep application heaps and event loops separate | Yes, with worker-thread isolates | Yes, with process boundaries |
| Recover one application worker | Runtime can replace a worker | External process supervisor or orchestrator replaces the process |
| Contain a process-wide native crash or OOM | No | A separate process limits this failure domain, subject to host limits |
| Release applications independently | No; applications in one runtime start, stop and deploy together | Yes, if deployed and operated separately |
| Internal service call | In-process thread routing for `.plt.local` | Network protocol and its operational costs |

Watt fits a modular application whose teams benefit from enforced runtime boundaries but can share a release and process-level resource budget. Split an application into its own runtime or service when it needs independent scaling, compliance, release cadence or process-level containment. URL-shaped calls make that move easier, but do not make network behavior identical: timeouts, retries, authentication, availability and serialization must be designed at the new boundary.

### 4. Observe the boundary yourself

Create two small Watt applications: configure one worker for a counter app that exposes an incrementing in-memory value, and have a second app call it through `.plt.local`. Send several requests, then restart the counter application's worker. Record which counter state survives, what the caller observes during replacement and whether the runtime process ID changes.
Repeat with an external database-backed counter: the comparison separates worker-local memory from state owned outside the process. Do not infer a latency improvement from a single local run; this exercise is about lifecycle and ownership.

## Summary

Watt places each application in its own worker-thread isolate and coordinates those workers through one Node runtime. Internal `.plt.local` calls use thread messaging rather than TCP, while application state remains local to its worker. This buys code isolation with shared process and deployment costs; choose separate runtimes when the failure, scaling or release boundary must also be independent.

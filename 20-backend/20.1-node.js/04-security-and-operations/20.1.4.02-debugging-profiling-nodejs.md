# Debugging & Profiling Node.js

## Definition

Debugging examines execution state to explain incorrect behavior; profiling samples or records execution to explain resource use. In Node.js, the inspector, CPU profiles, heap snapshots, diagnostic reports and `perf_hooks` answer different questions about the same process.

## First Principles

1. **End-to-end latency is a sum of waits and work.** A slow request may wait for a socket, database connection, CPU time, lock or downstream response. Measuring one component cannot identify the whole cause.
2. **Observation changes the process.** Breakpoints pause execution, profiles add work, and heap snapshots stop the thread and allocate memory. Pick the least intrusive instrument that answers the current question.
3. **Reachability explains heap retention.** Garbage collection cannot reclaim an object still reachable from a root. A retained object is not necessarily a leak; distinguish intentional bounded caches from state that grows beyond its lifecycle.
4. **An aggregate hides where work happens.** Process CPU includes multiple threads, whereas event-loop utilization describes one loop. Correlate the measurements with the request path and deployment resources.

## Start with a slow request, then select a tool

Suppose request latency rises from 50 ms to 800 ms after a release. First reproduce the traffic shape and compare traces, queue depth, CPU, memory and event-loop metrics across the same time window:

| Evidence | Next investigation | What it does not prove |
| ---------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------- |
| High loop delay and CPU | Sample CPU stacks, inspect synchronous hot paths and GC | That every delay is application JavaScript |
| High process CPU, lower loop utilization | Inspect workers/native pools/other isolates and CPU throttling | That offloading more work will help |
| Low CPU, long downstream spans | Check pool wait, connection setup and downstream latency | That the local service has no capacity limit |
| Rising heap at comparable load | Compare retained objects and lifecycle owners | That all increased allocations are leaks |
| Rising RSS with stable heap | Inspect buffers/native allocations, worker heaps and allocator behavior | That a main-isolate heap snapshot explains all RSS |

These are hypotheses. CPU throttling, pauses and workload changes can produce overlapping patterns. Record deployment markers and request correlation IDs so the next instrument measures the relevant interval.

## Measure the loop over one interval

`monitorEventLoopDelay` samples timer delay in nanoseconds. Event-loop utilization tracks active/idle time; it is not a CPU percentage. Take a difference between snapshots rather than printing the lifetime average next to an interval histogram.

```javascript
const { monitorEventLoopDelay, performance } = require('node:perf_hooks');

function startLoopMetrics(emit, intervalMs = 15000) {
  if (!Number.isSafeInteger(intervalMs) || intervalMs < 1) {
    throw new RangeError('Invalid interval');
  }
  const histogram = monitorEventLoopDelay({ resolution: 10 });
  histogram.enable();
  let previous = performance.eventLoopUtilization();
  const timer = setInterval(() => {
    const current = performance.eventLoopUtilization();
    const delta = performance.eventLoopUtilization(current, previous);
    previous = current;
    const sample = histogram.count === 0 ? null : {
      p50Ms: histogram.percentile(50) / 1e6,
      p99Ms: histogram.percentile(99) / 1e6,
      maxMs: histogram.max / 1e6,
    };
    emit({ loopDelay: sample, utilization: delta.utilization });
    histogram.reset();
  }, intervalMs);
  timer.unref();
  return () => {
    clearInterval(timer);
    histogram.disable();
  };
}
```

Choose alert thresholds from the service latency budget and baseline; 100 ms is not a universal boundary. A single late timer cannot distinguish blocking from OS scheduling or GC. Ensure the telemetry emitter itself is bounded and does not throw from the timer callback.

## Profile CPU while the symptom is present

A sampling profile records the stacks observed at intervals. Read the hot functions and their callers, then change one mechanism and repeat the same load to test the hypothesis.

```bash
# Built-in inspector-format CPU profile, written when the process exits
node --cpu-prof --cpu-prof-dir=./diagnostics dist/server.js

# Alternative V8 tick log and text summary
node --prof dist/server.js
node --prof-process isolate-0xEXAMPLE-v8.log > processed.txt
```

The log filename is illustrative; select the actual file rather than passing a wildcard matching several isolates. A main-thread profile cannot explain every worker or native-thread cost. Warm the workload consistently and record concurrency, payload sizes, error rate and CPU limits; profiler overhead must be measured on that workload.

For a bounded programmatic capture, the promise-based inspector API is available in the Node 24 example below. The process keeps serving while sampling; this helper does not call `process.exit` or enable a network listener:

```javascript
const { Session } = require('node:inspector/promises');
const { setTimeout: wait } = require('node:timers/promises');
const { writeFile } = require('node:fs/promises');

async function captureCpuProfile(filename, durationMs = 1000) {
  if (!Number.isSafeInteger(durationMs) || durationMs < 1 || durationMs > 60000) {
    throw new RangeError('Invalid capture duration');
  }
  const session = new Session();
  session.connect();
  try {
    await session.post('Profiler.enable');
    await session.post('Profiler.start');
    await wait(durationMs);
    const { profile } = await session.post('Profiler.stop');
    await writeFile(filename, JSON.stringify(profile), { flag: 'wx', mode: 0o600 });
  } finally {
    session.disconnect();
  }
}
```

Treat the path as an operator-controlled private destination. The exclusive write avoids replacing an existing artifact. Protect and expire profiles because function names, paths and captured metadata may reveal sensitive application structure.

## Use the inspector for state, with a private listener

```bash
node --inspect=127.0.0.1:9229 dist/main.js
# --inspect-brk pauses before user code until the debugger proceeds
node --inspect-brk=127.0.0.1:9229 dist/main.js

# POSIX: activate the inspector on an owned running Node process
kill -USR1 <pid>

# Forward a remote loopback listener through SSH
ssh -L 9229:127.0.0.1:9229 user@host
```

Open `chrome://inspect` or attach the editor to the forwarded port. SIGUSR1 activation predates Node 22 and is platform/permission dependent. Node's permission flags can restrict inspector activation. Do not bind `0.0.0.0` for an SSH tunnel: the tunnel works with the remote listener on loopback.

The debugger can execute code in the process. Breakpoints also stop the event loop and distort timing, so use them to inspect state rather than proving production latency behavior.

## Trace retained objects back to their owner

A heap snapshot is the object graph of a V8 isolate. Compare snapshots after warm-up under comparable traffic:

1. Warm the suspected code path so initialization allocations are already present.
2. Capture baseline A on an instance whose interruption or loss is acceptable.
3. Repeat the suspected operation and capture B; repeat for C if needed.
4. In DevTools Memory → Comparison, inspect positive count/size deltas, then follow retaining references to the owner.
5. Remove that owner's unintended reference or bound its lifecycle, then repeat the workload to verify stabilization.

Examples include a request-ID map never evicted, a listener retaining request bodies, or an unbounded cache. An allocation flamegraph identifies allocation sites; it does not by itself identify the references keeping objects alive.

```bash
# Operator-triggered snapshots on supported POSIX deployments
node --heapsnapshot-signal=SIGUSR2 dist/server.js
```

`v8.writeHeapSnapshot()` is another synchronous trigger. Snapshot creation stops work in its thread and can need enough additional memory to crash the process, including roughly doubling heap use. Do not automatically snapshot an instance already close to OOM, or expose an unauthenticated HTTP trigger. Drain a disposable replica, retain spare capacity and verify diagnostic storage first.

Snapshots include object contents and may contain credentials or personal data. Apply private storage, access control and retention. A main-isolate snapshot omits other worker heaps and cannot explain all external/native allocations.

## Capture process state without pretending it is an FD count

A diagnostic report contains JavaScript/native stacks, libuv state, resource usage and system information. It is a one-time state artifact, not a CPU profile or an exact historical explanation.

```bash
node --report-on-signal --report-signal=SIGUSR2 --report-directory=./diagnostics --report-uncaught-exception dist/server.js
```

Choose one meaning for a signal; do not configure both snapshots and reports on SIGUSR2 unless you deliberately want both expensive captures. Signal support differs by platform. Reports can include environment and network information; use available exclusion settings for the pinned Node version and protect the output.

```javascript
function resourceSummary() {
  const memory = process.memoryUsage();
  const counts = Object.create(null);
  for (const type of process.getActiveResourcesInfo()) {
    counts[type] = (counts[type] ?? 0) + 1;
  }
  return {
    rssBytes: memory.rss,
    heapUsedBytes: memory.heapUsed,
    externalBytes: memory.external,
    activeResourceTypes: counts,
  };
}
```

Active resource types identify work keeping the loop alive. Counting `TCPSocketWrap` resources is not an OS open-file-descriptor count. Use platform process metrics for descriptors, and scope diagnostics to an authorized operator route or existing telemetry pipeline rather than a placeholder token middleware that always calls `next()`.

## Choose maintained tools and measure the outcome

Clinic Doctor, Flame, Bubbleprof and Heap Profiler were useful wrappers around Node diagnostics. The [project's maintenance notice](https://github.com/clinicjs/node-clinic) now says it is not actively maintained and results may be inaccurate as Node internals change. Start with built-in profiles/reports; verify compatibility before using Clinic on a pinned runtime. A successful tool exit does not constitute a latency regression gate.

For performance CI, define a repeatable load scenario and explicit latency/error/resource budgets with warm-up and variance handling. Compare the corrected code against the baseline under the same constraints; avoid fixed "profiler costs 1–5%" or "monitoring costs nanoseconds" claims without measurements.

## Summary

Start with the slow request and its waits, then select a tool that can test the suspected resource. Correlate interval loop metrics, CPU samples and downstream traces; follow retained references for memory growth. Keep inspector listeners private and treat snapshots, reports and profiles as sensitive artifacts with measurable capture costs.

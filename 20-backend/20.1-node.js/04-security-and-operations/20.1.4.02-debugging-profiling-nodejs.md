# Debugging & Profiling Node.js

> **TL;DR:** Node ships a full diagnostics stack: `node --inspect` attaches Chrome DevTools to any running process, `--prof` writes V8 tick logs you post-process, heap snapshots (and snapshot *comparison*) hunt memory leaks, and Clinic.js automates the doctor/heapprofiler loop. The senior skill is triage — first classify the problem as CPU-bound, memory-bound, or I/O-bound, then pick the tool; and in production, use signals + `--report-on-signal` to get a diagnostics report without restarting or pausing traffic.

>
> **Why it matters:** "The service is slow" is the most common production escalation you will face. Interviews probe whether you can name the actual workflow: measure event-loop lag first, then profile the right resource — not guess.

## Definition

**Node.js debugging and profiling** is the set of runtime tools for observing what a live process is doing:

- **Debugger**: V8 Inspector Protocol (`node --inspect`), consumed by Chrome DevTools or VS Code
- **CPU profiler**: `--prof` (V8 sampling profiler) or DevTools' JavaScript Profiler panel
- **Heap snapshots**: point-in-time object graphs, comparable two-at-a-time to find leaks
- **Clinic.js**: wrapper toolkit (`clinic doctor`, `clinic heapprofiler`, `clinic flame`) that runs your app under load and diagnoses it
- **Event-loop lag monitoring**: measures how late timers fire — the single best "is my event loop blocked" signal
- **Diagnostics report**: JSON state dump (`process.report`, `--report-on-signal`) covering handles, memory, libuv, and OS data

## Why Do We Need It?

1. **Single-threaded blindness** — one blocked callback freezes every request; you need event-loop visibility, not just CPU graphs.
2. **Memory leaks are silent** — RSS creeps up over days; without heap snapshot comparison you cannot tell a leak from a cache.
3. **Latency regressions are multi-cause** — p99 spikes can be GC pauses, a hot synchronous function, or a saturated downstream. Guessing wastes days.
4. **Production debugging is constrained** — you usually cannot attach a debugger to prod at will; you need signal-based, low-overhead diagnostics.
5. **Interview signal** — "How do you debug a memory leak?" separates engineers who have done on-call from those who have read about it.

## Code Examples

### Inspecting a Running Process with Chrome DevTools

```bash
# Start with the inspector (waits for a debugger before running user code)
node --inspect-brk dist/main.js

# Or attach to an ALREADY RUNNING process without restart (Node 22+)
kill -USR1 <pid>          # activates the inspector listener
node inspect -p <pid>     # or connect via chrome://inspect

# Remote host (bind outside localhost ONLY behind SSH tunnel)
node --inspect=0.0.0.0:9229 dist/main.js
ssh -L 9229:localhost:9229 user@host
```

```typescript
// Programmatic inspector access — e.g., dump a session's scripts
import inspector from 'node:inspector';
import fs from 'node:fs';

const session = new inspector.Session();
session.connect();

session.post('Runtime.enable');
session.post('Profiler.enable', () => {
  session.post('Profiler.start', () => {
    setTimeout(() => {
      session.post('Profiler.stop', (err, { profile }: { err: Error | null; profile: unknown }) => {
        if (!err) fs.writeFileSync('cpu-profile.cpuprofile', JSON.stringify(profile));
        process.exit(0);
      });
    }, 10_000);
  });
});
```

### CPU Profiling with --prof

```bash
# 1. Run under the V8 sampling profiler (~1 sample/ms)
node --prof dist/server.js

# 2. Generate load against it
autocannon -c 100 -d 30 http://localhost:3000/heavy

# 3. Stop (Ctrl+C), then summarize the tick log
node --prof-process isolate-0x*-v8.log > processed.txt

# 4. Read processed.txt:
#    [Summary]   ticks by type
#    [JavaScript] ticks per function  <-- start here
#    [C++]        ticks per native function
#    [Bottom up]  callers of hot functions
```

### Heap Snapshots and Leak Hunting by Comparison

```typescript
// leak-probe.ts — take snapshots programmatically, compare in DevTools
import { writeHeapSnapshot } from 'node:v8';

export function scheduleSnapshot(label: string): void {
  const file = writeHeapSnapshot();
  console.log(JSON.stringify({ msg: 'heap_snapshot', label, file }));
}

// In a test or canary route: capture baseline, apply load, capture again
let requestCount = 0;

export function registerProbe(app: { get: (p: string, h: () => void) => void }): void {
  app.get('/__debug/snapshot', () => {
    requestCount += 1;
    if (requestCount % 1000 === 0) {
      scheduleSnapshot(`after-${requestCount}`);
    }
  });
}
```

```text
Comparison workflow (Chrome DevTools > Memory):

 1. Load snapshot A (t0), B (t0+30min), C (t0+60min).
 2. Select C, switch view to "Comparison" vs B.
 3. Sort by "# Delta" descending.
 4. Filter out noise: ignore system contexts and constructors
    whose delta oscillates (arrays reused by pools).
 5. A real leak: monotonic growth across A→B→C in ONE constructor
    (e.g., "+18,400 Closure").
 6. Expand a retained object -> read the "retained size" chain:
    the shortest path from a GC root tells you WHO holds the ref.
```

### Event-Loop Lag Monitoring

```typescript
// elu.ts — event-loop utilization + lag histogram (production-safe, always on)
import { monitorEventLoopDelay, performance } from 'node:perf_hooks';
import { eventLoopUtilization } from 'node:perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 10 });
histogram.enable();

setInterval(() => {
  const ms = (ns: number) => Number((ns / 1e6).toFixed(2));
  // p99 lag > ~100ms sustained means the loop is starving
  console.log(
    JSON.stringify({
      metric: 'event_loop_lag_ms',
      p50: ms(histogram.percentile(50)),
      p99: ms(histogram.percentile(99)),
      max: ms(histogram.max),
      mean: ms(histogram.mean),
      elu: eventLoopUtilization().utilization.toFixed(3),
    }),
  );
  histogram.reset();
}, 15_000).unref(); // .unref() so this timer never keeps the process alive

// One-lag-sample probe: how LATE did a 1ms timer fire?
function sampleLag(): Promise<number> {
  return new Promise((resolve) => {
    const start = performance.now();
    setTimeout(() => resolve(performance.now() - start - 1), 1);
  });
}
```

### Production-Safe Diagnostics Without Restarts

```bash
# Enable report generation without code changes
node \
  --report-on-signal \          # SIGUSR2 triggers a full report
  --report-signal=SIGUSR2 \
  --report-filename=/var/diagnostics \
  --report-uncaught-exception \ # also auto-report on crashes
  dist/server.js
```

```typescript
// diag-controller.ts
import { Router } from 'express';
import { getActiveResourcesInfo } from 'node:process';
import os from 'node:os';

export const diagRouter = Router();

diagRouter.get('/internal/diag', requireInternalToken, (_req, res) => {
  const mem = process.memoryUsage();
  res.json({
    pid: process.pid,
    uptime_s: Math.round(process.uptime()),
    node: process.version,
    rss_mb: +(mem.rss / 1048576).toFixed(1),
    heap_used_mb: +(mem.heapUsed / 1048576).toFixed(1),
    external_mb: +(mem.external / 1048576).toFixed(1),
    open_fd_estimate: getActiveResourcesInfo().filter((r) => r === 'TCPSocketWrap').length,
    load_1m: os.loadavg()[0],
  });
});

function requireInternalToken(req: unknown, _res: unknown, next: () => void): void {
  // verify an ops-only token here; never expose diagnostics publicly
  next();
}
```

### Clinic.js Doctor and Heap Profiler

```bash
# doctor: detects event-loop blocking, high delay, suspicious patterns
npx clinic doctor -- node dist/server.js
# run your load script in another terminal; clinic opens an HTML diagnosis

# heapprofiler: samples allocations while load runs -> flamegraph of retainers
npx clinic heapprofiler -- node dist/server.js

# flame: CPU flamegraph (wraps 0x)
npx clinic flame -- node dist/cpu-heavy.js
```

## Real-World Use Cases

1. **OOM kills in Kubernetes after 3 days** — Take three heap snapshots via a canary endpoint (`writeHeapSnapshot`) hours apart, compare deltas, discover a module-level `Map` keyed by request ID that is never evicted. Add an LRU with TTL.
2. **p99 latency spike at 09:00 daily** — `monitorEventLoopDelay` shows p99 lag jumping to 800ms exactly when the report cron fires. Move report generation into a child process.
3. **CPU pegged but requests fine** — `--prof-process` shows 60% ticks inside `zlib.deflateSync`; someone replaced async gzip with sync in a middleware. Revert, or stream compression instead.
4. **Debugging only in staging-like conditions** — Attach `clinic doctor` under `autocannon` load in CI nightly to catch event-loop regressions before they reach prod.
5. **Crash forensics** — `--report-uncaught-exception` leaves a JSON report with the exact handle table and stack at crash time, turning "it just died" into a reproducible investigation.

## Common Mistakes

| Mistake                                                            | Fix                                                                                                     |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| Attaching `--inspect` on a public interface in production          | Bind localhost only; use an SSH tunnel. The inspector allows arbitrary code execution.                  |
| Comparing heap snapshots taken minutes apart under changing load   | Take snapshots at steady state, same traffic shape, ideally 3+ snapshots and compare consecutive pairs. |
| Reading `process.memoryUsage().heapUsed` and calling "not leaking" | `heapUsed` excludes external/buffers and fragmentation; track `rss` trend + snapshots.                  |
| Profiling in development and assuming production behaves the same  | Profile under representative load (`autocannon` with production-shaped payloads).                       |
| Leaving `monitorEventLoopDelay` disabled because "overhead"        | Overhead is nanoseconds-scale; the real mistake is having no lag telemetry during incidents.            |
| Treating one slow timer sample as proof of blocking                | Look at percentiles over a window (p99/max), not single samples.                                        |

## Best Practices

1. **Triage before profiling** — classify CPU-bound vs memory-bound vs I/O-bound with lag + ELU metrics first; each has a different tool.
2. **Keep a diagnostics endpoint behind auth** — RSS, heap, fd count, uptime, node version; it pays for itself in the first incident.
3. **Use `.unref()` on monitoring timers** — observability must never keep the process alive.
4. **Automate heap snapshot capture on OOM approach** — when `rss > threshold * limit`, dump a snapshot once, upload it, then let the process die cleanly.
5. **Gate performance CI on clinic doctor exit codes** — a nightly load test that fails on detected event-loop blocking prevents regressions.
6. **Never ship `--inspect` flags to production images** — enforce via Dockerfile lint or startup assertions.
7. **Correlate lag metrics with deploy markers** — a p99-lag dashboard is only actionable next to release annotations.

## Performance Considerations

- **Sampling profilers cost ~1–5% overhead** — safe for staging, acceptable briefly in prod; continuous `--prof` in prod is usually wrong.
- **Heap snapshots pause the process** — hundreds of MB to seconds for large heaps; take them on a pod you remove from the LB first.
- **`--prof` log files grow fast** — one isolate log per worker; rotate/clean them or disk fills during soak tests.
- **Event-loop delay histograms need reset** — call `reset()` per window or percentiles smear across hours.
- **Diagnostics reports are cheap** — they are a one-shot dump; ideal default for crash forensics since overhead is zero until triggered.

## Summary

- Start every performance incident with event-loop lag + ELU measurement to classify the bottleneck: CPU-bound (JS), memory-bound (GC/leaks), or I/O-bound (downstream/pools).
- `node --inspect` + Chrome DevTools is the interactive debugger; `--prof` + `--prof-process` gives function-level CPU attribution; Clinic.js packages these workflows with visual verdicts.
- Memory leaks are proven by comparing multiple heap snapshots at steady state; the delta + retained-size chain names the culprit.
- Production-safe diagnostics rely on `--report-on-signal` (SIGUSR2), programmatic `writeHeapSnapshot()`, and always-on lag histograms — no restarts, near-zero overhead.
- The inspector executes arbitrary code: bind to localhost, tunnel over SSH, and never enable it in public production interfaces.

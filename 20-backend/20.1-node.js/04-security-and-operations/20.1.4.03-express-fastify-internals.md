# Express & Fastify Internals

> **TL;DR:** Express is a middleware chain: every handler gets `(req, res, next)`, work flows forward via `next()`, and error handling is a *different function shape* — arity-4 `(err, req, res, next)` — that the router dispatches to when anything throws or `next(err)` fires. Fastify replaces this with a fixed hook lifecycle (`onRequest` → `preValidation` → `preHandler` → handler → `onSend`) plus a plugin tree with encapsulated contexts; its speed comes from schema-based serialization and route precompilation. Migration Express→Fastify mostly means converting middleware to hooks and rethinking shared-state scoping.

>
> **Why it matters:** Interviewers use "how does Express actually route a request?" and "why is Fastify faster?" to test whether you understand framework abstractions — not just how to call them. The answers are pure mechanics: linked lists of functions vs compiled per-route machines.

## First Principles

Express and Fastify are dispatch mechanisms, and their differences follow from how they dispatch:

1. **A router maps (method, path) → handler chain.** That's all a framework fundamentally is; middleware is the chain-of-responsibility pattern over requests. Every "framework feature" — body parsing, auth, CORS — is middleware composition, which is why understanding the chain explains everything else.
2. **Fastify's speed is architecture, not tuning**: schema-based serialization (compile JSON schemas into fast serializers) and a no-dynamic-dispatch router (radix tree) vs Express's per-request option-resolution. The lesson: performance came from *removing per-request work*, the only real speed.
3. **Plugin encapsulation is Fastify's real product**: per-plugin contexts prevent global state soup — the same module-boundary thinking (→ 10.1.5.01) applied to a server. Choosing between them is ecosystem vs throughput, and both answers are legitimate.

## Definition

**Express** builds each route as an ordered **stack (linked list) of layers**: middleware and handlers sharing one signature contract. A request walks the stack; `next()` hands control to the following layer; a 4-arity layer is an error handler that only error-path dispatches reach.

**Fastify** compiles each route into a specialized async function with named **hooks** executed at deterministic phases, organized in a **plugin tree** where every `.register()` creates a child context with its own decorators/hooks — inheritance downward by default, isolation sideways.

## Why Do We Need It?

1. **Predictable debugging** — knowing the chain/hook order tells you exactly which code runs before your handler and after your response.
2. **Correct error semantics** — Express error middleware silently never fires if arity is wrong (3 args = normal middleware); this is a top production bug.
3. **Performance literacy** — understanding *why* Fastify wins (serialization schemas, less abstraction per request) beats quoting benchmark numbers.
4. **Framework choice evidence** — migration decisions need real knowledge of what breaks: middleware assumptions, plugin scoping, body parsing.
5. **Interview staple** — "trace a request through Express" and "explain fastify-plugin's module hack" are senior-tier questions.

## How It Works

### Express Middleware Chain Model

```text
Request arrives
     │
     ▼
Router resolves path+method ──► collects matching LAYERS
     │
     ▼
┌──────────────────────────────────────────────────────┐
│ Layer stack (singly-linked list):                    │
│                                                      │
│ [logger]──►[auth]──►[json parser]──►[handler]        │
│    │         │            │              │           │
│    ▼         ▼            ▼              ▼           │
│  next()    next(err?)   next()       res.send(...)   │
│    │         │            │              │           │
│    └─────────┴────────────┴──► advance to next layer │
│                                                      │
│ If ANY layer calls next(err) or throws (sync):       │
│   router SKIPS FORWARD to the next ARITY-4 layer     │
│   skipping all remaining normal middleware           │
└──────────────────────────────────────────────────────┘
```

```text
Arity-4 semantics (THE Express interview detail):

 function (err, req, res, next) { ... }   ← ERROR HANDLER
 function (req, res, next)       { ... }  ← NORMAL MIDDLEWARE

 • Express decides role by FUNCTION.LENGTH at registration time.
 • Error handlers must be declared AFTER routes they cover.
 • next('router') exits THIS router instance entirely.
 • Unhandled error with no arity-4 layer left → default handler:
   HTML error page + stack trace (leaks internals!).
```

### Mount Paths and Sub-Routers

```text
app.use('/api', apiRouter)
      │ mount path stripped from req.url for inner matching,
      │ RESTORED for outer logging; req.baseUrl='/api',
      │ req.path inside router excludes '/api'
      │
      ├─ apiRouter.use('/users', usersRouter)  → nests again
      └─ app.use(express.static('public'))      → terminal fallthrough

Gotchas:
 • Mounting at '/' matches EVERY method AND path (incl. OPTIONS).
 • A middleware not calling next() and not responding = hung request.
 • Router order IS priority: first match wins, no reordering later.
```

### Fastify Hook Lifecycle

```text
onRequest          ← raw request; NO body parsed yet; auth/rate-limit
   │
preParsing         ← payload stream available; size limits
   │
onParsing/body     ← content-type parser runs (JSON default)
   │
preValidation      ← body available as raw object; transform BEFORE schema validation
   │
validation         ← route JSON Schema validates params/query/body
   │
preHandler         ← fully typed+validated input; business-logic guards
   │
handler            ← your logic; return value becomes payload
   │
onSend             ← serialize NOW; can modify/reject payload (e.g., redact)
   │
onResponse         ← response flushed; metrics/logging only (no more changes)

onError            ← fires on any thrown error at ANY phase above
                     (does NOT fire if response already sent)
```

### Plugin Encapsulation Model

```text
root (fastify())
 ├── register(pluginA)          Context A
 │    ├── decorator 'db'
 │    └── onRequest hook X
 │
 ├── register(fastifyPlugin(shared))   ← BREAKOUT: same context as root
 │
 └── register(async child => {
        child.register(subB)    Context B (child of root, sibling of A)
     })

Rules:
 • Hooks/decorators added in context A do NOT exist in B (isolation).
 • Children INHERIT everything from ancestors (encapsulated downward).
 • Wrapping a plugin in fastify-plugin() skips context creation →
   its hooks/decorators land in the PARENT scope (how official
   plugins like @fastify/env share decorators globally).
```

### Why Fastify Is Faster

```text
1. SCHEMA-BASED SERIALIZATION
   Express: res.json(obj) → JSON.stringify(obj) EVERY request.
   Fastify: responseSchema compiled ONCE into a writer function that
            emits ONLY declared fields — serialization is ~2x faster
            AND strips undeclared data (security win).

2. ROUTE PRECOMPILATION
   Fastify uses find-my-way radix trie + compiles handlers into
   optimized closures at registration; Express re-walks layer lists
   per request with regex path tests.

3. LOWER ABSTRACTION OVERHEAD
   Express wraps each request in its layer-dispatch machinery;
   Fastify's hot path is an async function chain with minimal
   per-request allocation.

4. VALIDATION MOVED OFF JS
   JSON Schema compiles to native validation code (via fast-json-
   stringify / ajv) instead of per-request library branching.
```

## Code Examples

### Express Chain and Arity-4 Error Handling

```javascript
// express-app.js — canonical chain + error-handler placement
const express = require('express');
const app = express();

// 1. Normal middleware (arity 3)
app.use((req, _res, next) => {
  console.log(`${req.method} ${req.originalUrl}`);
  next();
});

// 2. Mounted sub-router — mount path stripped internally
const ordersRouter = express.Router();
ordersRouter.get('/:id', async (req, res, next) => {
  try {
    const order = await db.orders.find(req.params.id);
    if (!order) {
      // Skip forward to the NEXT ARITY-4 layer
      return next({ status: 404, message: 'Order not found' });
    }
    res.json(order); // terminal — stops chain advancement
  } catch (err) {
    next(err); // sync throw would land here too, but be explicit for async
  }
});
app.use('/orders', ordersRouter);

// 3. Error handler MUST be arity-4 and LAST
app.use((err, _req, res, _next) => {
  const status = err.status ?? 500;
  res.status(status).json({
    error: err.message,
    ...(process.env.NODE_ENV === 'production' ? {} : { stack: err.stack }),
  });
});
```

```typescript
// WRONG vs RIGHT: the classic silent bug
function brokenErrorHandler(req: unknown, res: unknown, next: () => void): void {
  // 3 args => Express treats this as NORMAL middleware.
  // It NEVER receives errors; it even consumes requests meant for routes!
}

const correctErrorHandler = (
  err: Error & { status?: number },
  _req: unknown,
  res: import('express').Response,
  next: () => void, // must accept 4th param even if unused
): void => {
  res.status(err.status ?? 500).json({ error: err.message });
};
void brokenErrorHandler; void correctErrorHandler;
```

### Fastify Hooks in Practice

```typescript
// server.ts — lifecycle hooks mapped to real responsibilities
import Fastify, { FastifyInstance, FastifyReply, FastifyRequest } from 'fastify';

const app = Fastify({
  logger: { level: 'info' },
  bodyLimit: 1024 * 1024,
});

// onRequest: no body yet — cheapest place for auth/rate limits
app.addHook('onRequest', async (req: FastifyRequest, reply: FastifyReply) => {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token && req.url !== '/health') {
    await reply.code(401).send({ error: 'unauthorized' }); // send() stops the chain
  }
});

// preValidation: mutate raw payload before schema validation
app.addHook('preValidation', async (req: FastifyRequest) => {
  if (typeof req.body === 'object' && req.body !== null && 'email' in req.body) {
    (req.body as Record<string, unknown>).email =
      String((req.body as Record<string, unknown>).email).toLowerCase();
  }
});

// preHandler: validated input; load user for downstream handlers
app.addHook('preHandler', async (req: FastifyRequest) => {
  if (req.headers.authorization) {
    (req as FastifyRequest & { user?: unknown }).user =
      await verifyToken(req.headers.authorization);
  }
});

// onSend: last chance to touch outgoing payload
app.addHook('onSend', async (_req, reply, payload: string) => {
  reply.header('x-request-id', reply.request.id);
  return typeof payload === 'string' ? payload : JSON.stringify(payload);
});

// onResponse: response already gone — metrics only
app.addHook('onResponse', async (_req, reply) => {
  app.log.info({ status: reply.statusCode, ms: reply.elapsedTime }, 'request done');
});

// onError: central error shaping
app.addHook('onError', async (_req, _reply, error) => {
  app.log.error(error);
});

app.get('/health', async () => ({ status: 'ok' }));
await app.listen({ port: 3000 });
```

### Plugin Encapsulation and the Escape Hatch

```typescript
// plugins.ts — scoping rules demonstrated
import fp from 'fastify-plugin';
import { FastifyInstance, FastifyPluginAsync } from 'fastify';

declare module 'fastify' {
  interface FastifyInstance {
    db: DatabasePool;          // decorated via breakout plugin
    tenantScope: (t: string) => FastifyInstance;
  }
}

// WITHOUT fp(): these decorators stay PRIVATE to this plugin's context.
// WITH fp(): they propagate to the ROOT — visible everywhere after registration.
const databasePlugin: FastifyPluginAsync = async (app: FastifyInstance) => {
  const pool = await createPool(process.env.DATABASE_URL);
  app.decorate('db', pool);
  app.addHook('onClose', async () => pool.end()); // lifecycle tie-in
};
export default fp(databasePlugin, { name: 'database' });

// Encapsulated admin area — its hooks DON'T leak to public routes
export const adminRoutes: FastifyPluginAsync = async (app) => {
  app.addHook('onRequest', requireRole('admin')); // scoped here only

  app.get('/admin/stats', async () => {
    return app.db.stats(); // inherited decoration from root
  });
};

// Public area unaffected by admin's onRequest hook
export const publicRoutes: FastifyPluginAsync = async (app) => {
  app.get('/public/info', async () => ({ version: '1.0' }));
};
```

### Route Schemas: The Performance Lever

```typescript
// routes.ts — schema-driven validation AND serialization
interface OrderReply {
  id: string;
  totalCents: number;
  internalFraudScore: number; // MUST NOT leave the service
}

app.route<{ Params: { id: string } }>({
  method: 'GET',
  url: '/orders/:id',
  schema: {
    params: {
      type: 'object',
      properties: { id: { type: 'string', format: 'uuid' } },
      required: ['id'],
    },
    response: {
      200: {
        type: 'object',
        properties: {
          id: { type: 'string' },
          totalCents: { type: 'number' },
          // internalFraudScore deliberately absent →
          // fast-json-stringify emits ONLY listed props
        },
      },
    },
  },
  handler: async (req) => getOrder(req.params.id), // leaks impossible by construction
});
```

## Real-World Use Cases

1. **Legacy Express API hardening** — add one final arity-4 error handler returning JSON without stack traces; suddenly all previously-swallowed async rejections surface consistently.
2. **High-throughput JSON API rewrite** — porting hot endpoints to Fastify with response schemas cut p50 latency ~40% in typical benchmarks, largely from serialization savings.
3. **Multi-tenant plugin architecture** — each tenant's feature flags/routes registered as encapsulated plugins; one tenant's experimental hooks cannot break others.
4. **Gradual Express→Fastify migration** — mount Fastify inside Express (`app.use('/v2', fastifyApp)` pattern) or run both behind a router, migrating route-by-route.
5. **Uniform observability** — replace scattered per-middleware timing logs with a single `onResponse` hook emitting structured request telemetry.

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Writing error handlers with 3 args | Express classifies by arity: exactly 4 parameters `(err, req, res, next)` makes it an error handler. |
| Not calling `next(err)` from async route wrappers | Express 4 does not catch rejected promises — wrap handlers or upgrade to Express 5. |
| Registering error middleware before routes | Arity-4 layers only catch errors raised EARLIER in the chain; declare last. |
| Expecting Express-style global middleware in Fastify | Use hooks (`addHook`) — and know they are context-scoped unless wrapped in `fastify-plugin`. |
| Sharing state across Fastify plugins via globals | Decorate instances (`app.decorate`) inside `fp()` plugins; respect encapsulation instead of bypassing it with module-level mutable exports. |
| Trusting microbenchmarks blindly | Published Fastify-vs-Express deltas assume JSON-only payloads, no middleware, keep-alive tuned; your app's numbers will differ — measure with YOUR workload. |

## Best Practices

1. **Keep Express chains shallow** — deep nested routers obscure flow; prefer composing small routers mounted at clear paths.
2. **Always end with a catch-all error handler** — sanitize messages by environment; log the original error server-side.
3. **In Fastify, choose the narrowest hook that works** — `onRequest` for auth (no parsing cost), `preHandler` for logic needing validated bodies.
4. **Wrap cross-cutting plugins in `fastify-plugin`** with a `name` + dependency metadata; let encapsulation protect feature-specific concerns.
5. **Declare response schemas for external APIs** — you gain speed AND a whitelist against accidental data exposure.
6. **Version routes explicitly** (`/v2/orders`, or Fastify `prefix` in `register`) rather than mutating shared stacks.
7. **Benchmark with production-shaped traffic** — include your middleware stack, payload sizes, and connection churn before choosing frameworks.

## Performance Considerations

- **Express overhead scales with middleware count** — every layer adds function-call dispatch; audit for dead middleware quarterly.
- **Fastify schema compilation costs startup time** — hundreds of routes pay one-time compile cost; amortized instantly under load.
- **Serialization dominates JSON-heavy workloads** — `fast-json-stringify` is where most Fastify wins come from; apps doing heavy I/O fan-out see smaller deltas.
- **Body parsing defaults differ** — Fastify rejects unsupported content-types by default (415), Express parses whatever you attach parsers for; align behavior during migration.
- **Benchmark caveats** — watch for: warm JIT vs cold starts, `--prof`-verified hot paths, proxy/TLS termination differences, and cluster worker counts; single-process hello-world numbers mislead.

### Migration Notes: Express → Fastify

```text
Concept map:

 EXPRESS                        FASTIFY
 ─────────────────────────────────────────────────────────────
 app.use(mw)                    app.addHook(phase, fn)
 req/res augmentation           instance decorators (scoped!)
 express.Router()               fastify.register(routes, {prefix})
 body-parser json               built-in content-type parser
 helmet/cors middleware         @fastify/helmet / @fastify/cors
 res.json(x); end               return x (or reply.send)
 next(err)                      throw err
 error arity-4 middleware       setErrorHandler(fn)
 app.set('view engine')         @fastify/view
 req.baseUrl                    request.routeOptions? / prefix ctx

Steps that survive contact with reality:
 1. Inventory middleware → classify per hook phase.
 2. Port DTO validation to JSON Schema (or TypeBox) — biggest win.
 3. Migrate leaf routes first behind a versioned prefix.
 4. Re-test error shapes: Fastify's default error serializer differs.
 5. Load-test BOTH stacks with identical traffic before cutover.
```

## Summary

- Express routes requests through ordered middleware layers dispatched via `next()`; error handling is selected purely by 4-argument function arity and must be registered last.
- Mount paths create sub-stacks with URL stripping semantics; order defines priority and first-match wins.
- Fastify formalizes the request into named hooks (`onRequest` → `preValidation` → `preHandler` → `onSend` → `onResponse`) plus `onError`, with plugin-tree encapsulation governing visibility; `fastify-plugin` opts out into the parent scope.
- Fastify's performance edge comes mainly from schema-based serialization (`fast-json-stringify`), precompiled radix routing, and thinner per-request abstraction — not magic.
- Migrations fail on unported middleware assumptions and error-shape differences; succeed with phased, versioned, load-tested rollouts.

## Cheat Sheet

```text
EXPRESS INTERNALS CHEAT SHEET
═══════════════════════════════════════

CHAIN MODEL:
  Layers = linked list; next() advances
  next(err) -> jump to next ARITY-4 layer
  First matching route/middleware WINS (order matters)

ARITY SEMANTICS:
  (req,res,next)          normal middleware
  (err,req,res,next)      error handler (length==4)
  Declare error handlers AFTER routes

MOUNTING:
  app.use('/api', r)  -> req.baseUrl='/api', url stripped
  No next()+no send() = hung socket

FASTIFY HOOKS (in order):
  onRequest        auth, rate limit (no body yet)
  preParsing       stream access, limits
  preValidation    mutate raw body pre-schema
  preHandler       validated input, RBAC
  handler          return value = payload
  onSend           edit/redact outgoing payload
  onResponse       metrics only (response sent)
  onError          any-phase failure shaping

PLUGIN MODEL:
  register()       child context (isolated sideways)
  inheritance      children see ancestors' stuff
  fastify-plugin   escape hatch -> parent scope
  app.decorate     share db/config safely

WHY FASTIFY FASTER:
  1 fast-json-stringify response schemas
  2 find-my-way radix router, precompiled
  3 minimal per-request abstraction
  Benchmark caveat: measure YOUR workload

MIGRATION MAP:
  middleware -> hook | next(err) -> throw
  Router -> register(prefix) | arity-4 -> setErrorHandler
```

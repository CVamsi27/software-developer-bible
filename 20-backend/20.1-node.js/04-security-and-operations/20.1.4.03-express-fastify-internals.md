# Express & Fastify Internals

## Definition

Express and Fastify turn Node HTTP requests into application handlers. Express dispatches through ordered middleware and route stacks. Fastify gives a matched route a lifecycle of hooks, validation, handler execution and response serialization, with those facilities scoped by a plugin tree.

## First Principles

1. **Several operations must share one request.** Parsing, authentication, authorization and business logic need a defined execution order and an agreement on who completes the response.
2. **Failures need a second path.** An exception or rejected promise must reach a handler that knows whether headers have already been sent. Detached callbacks need explicit error ownership.
3. **A feature's configuration needs a scope.** A hook for admin routes should not affect public routes; shared database access should be inherited where it is needed.
4. **Repeated work can move to registration time.** Routing tables and trusted schemas can be prepared once, but the resulting speed depends on the actual workload and still needs measurement.

## Trace one Express request through its stacks

`app.use('/api', router)` adds a router layer to the application stack. That router has its own ordered layers. Express scans for matching method/path layers as dispatch advances; it does not first gather all matching handlers into a linked list.

```text
GET /api/orders/7
  app logger → next()
      ↓
  /api mount → router sees /orders/7
      ↓
  GET /orders/:id → await lookup
      ├─ found → send DTO → response completes
      └─ missing/rejected → next(error) → four-argument error handler
```

Express router stacks are arrays of layers, not singly linked lists. The first matching handler need not finish the request: `next()` can continue to later matches. A middleware that neither responds nor calls `next()` leaves the request pending.

Within the mounted router, `req.url` has the mount path stripped, `req.baseUrl` identifies the mount and `req.originalUrl` retains the original URL. Nested routers repeat that relationship. `next('route')` skips remaining handlers of the current route; `next('router')` exits the current router.

### Own the promise and the response

This example targets Express 5. Returned rejected promises automatically enter error dispatch. Express 4 needs an explicit `try/catch(next)` or a promise wrapper.

```javascript
const express = require('express');

function createExpressApp(findOrder, trace = () => {}) {
  const app = express();
  app.disable('x-powered-by');
  app.use((req, _res, next) => {
    trace({ stage: 'app', url: req.url, originalUrl: req.originalUrl });
    next();
  });

  const router = express.Router();
  router.get('/orders/:id', async (req, res) => {
    trace({ stage: 'route', url: req.url, baseUrl: req.baseUrl });
    if (!/^[0-9]{1,8}$/.test(req.params.id)) {
      const error = new Error('Invalid ID');
      error.status = 400;
      throw error;
    }
    const order = await findOrder(req.params.id);
    if (!order) {
      const error = new Error('Order not found');
      error.status = 404;
      throw error;
    }
    res.json({ id: order.id, totalCents: order.totalCents });
  });
  app.use('/api', router);
  app.use((_req, res) => res.status(404).json({ error: 'Not found' }));

  app.use((error, _req, res, next) => {
    trace({ stage: 'error', error });
    if (res.headersSent) return next(error);
    const status = [400, 404].includes(error.status) ? error.status : 500;
    const message = status === 400 ? 'Invalid request' :
      status === 404 ? 'Not found' : 'Internal server error';
    res.status(status).json({ error: message });
  });
  return app;
}
module.exports = { createExpressApp };
```

The four declared parameters identify an error handler through function arity. Defaults/rest parameters can change `function.length`, so preserve the signature. Place error handlers after the routes whose failures they cover. If a streamed response has already started, delegate rather than trying to send a second JSON response; the default handler may close the connection.

The default handler omits stack traces in production mode. A custom handler must still avoid exposing arbitrary internal `error.message` values. Also, Express 5 cannot catch an error in an unrelated timer or a promise the handler neither returns nor awaits; forward those failures explicitly.

## Locate a Fastify hook inside the request lifecycle

A hook is code attached to a lifecycle phase for routes in its plugin scope. Read the surrounding lifecycle before choosing the hook:

```text
routing → onRequest → preParsing → body parsing
        → preValidation → schema validation → preHandler → handler
        → preSerialization → serialization → onSend → response → onResponse
```

| Phase | Available input/output | Typical purpose |
| ------------------ | ------------------------------------------------------ | ------------------------------------------------ |
| `onRequest` | Headers/raw request; body not parsed | Early authentication or rejection |
| `preParsing` | Incoming payload stream | Transform stream with correct size accounting |
| `preValidation` | Parsed body, before schema checks | Deliberate normalization |
| `preHandler` | Validated input | Resource lookup and authorization |
| `preSerialization` | Object payload before serialization | Shape the object; skipped for some payload types |
| `onSend` | Serialized payload, possibly stream/buffer/string/null | Headers or final payload transformation |
| `onResponse` | Response already sent | Completion telemetry |

`onError` observes errors entering error handling; `setErrorHandler` chooses the error response. Do not call `reply.send()` from `onError`. Timeout, abort and error paths have their own hooks and constraints; they are not all equivalent to successful completion.

Do not mix callback `done` and `async` styles for the same hook. In an async hook that sends an early response, return the reply so lifecycle completion is owned explicitly.

## Put scoped behavior into the plugin tree

Each ordinary `register(plugin)` creates an encapsulated child context. Descendants inherit their ancestors' decorations and hooks; sibling contexts do not inherit each other's additions. `fastify-plugin` normally skips that encapsulation for its own registration, exposing additions to its parent scope. That parent may itself be an encapsulated feature, so "wrapped" does not automatically mean globally visible.

```text
root: request ID header, shared findOrder decoration
 ├─ public plugin: /health
 └─ admin plugin: authentication/role hook
       └─ /admin/orders/:id
```

Fastify 5 example, with authentication supplied as an application dependency. The default denies access; the chapter does not implement token verification:

```javascript
const Fastify = require('fastify');
const fp = require('fastify-plugin');

function buildFastify({ findOrder, verifyPrincipal = async () => null }) {
  const app = Fastify({ logger: false, bodyLimit: 100 * 1024 });
  app.addHook('onSend', async (request, reply, payload) => {
    reply.header('x-request-id', request.id);
    return payload; // do not JSON.stringify an already serialized value
  });
  app.addHook('onError', async (_request, _reply, error) => {
    app.log.error({ err: error }, 'request failed');
  });
  app.setErrorHandler((error, _request, reply) => {
    const status = error.validation ? 400 : error.statusCode === 404 ? 404 : 500;
    reply.code(status).send({ error: status === 400 ? 'Invalid request' :
      status === 404 ? 'Not found' : 'Internal server error' });
  });

  app.register(fp(async shared => {
    shared.decorate('findOrder', findOrder);
    // If this plugin creates a DB pool, bind its close to onClose here.
  }, { name: 'order-store' }));

  app.register(async publicRoutes => {
    publicRoutes.get('/health', async () => ({ status: 'ok' }));
  });
  app.register(async admin => {
    admin.addHook('onRequest', async (request, reply) => {
      const principal = await verifyPrincipal(request.headers.authorization);
      if (!principal) return reply.code(401).send({ error: 'Unauthorized' });
      if (principal.role !== 'admin') return reply.code(403).send({ error: 'Forbidden' });
      // Real multi-tenant handlers also need server-owned tenant/resource context.
    });
    admin.get('/orders/:id', {
      schema: {
        params: {
          type: 'object', required: ['id'], additionalProperties: false,
          properties: { id: { type: 'string', pattern: '^[0-9]{1,8}$' } },
        },
        response: {
          200: {
            type: 'object', required: ['id', 'totalCents'], additionalProperties: false,
            properties: {
              id: { type: 'string' },
              totalCents: { type: 'integer' },
            },
          },
        },
      },
    }, async request => {
      const order = await admin.findOrder(request.params.id);
      if (!order) {
        const error = new Error('Order not found');
        error.statusCode = 404;
        throw error;
      }
      return order;
    });
  }, { prefix: '/admin' });
  return app;
}
module.exports = { buildFastify };
```

The admin hook applies only inside its subtree. Public `/health` remains accessible, and `findOrder` is inherited from the shared parent. In a real service, role membership alone may not authorize a particular tenant's order; carry verified context into the lookup and enforce the resource policy.

## Separate validation, typing and serialization

Fastify compiles trusted request schemas through Ajv and response schemas through `fast-json-stringify`. Those compilers generate **JavaScript**, not native validation running outside the event loop. Schema definitions are application code; never accept arbitrary schemas from clients.

The declared response schema above excludes `internalFraudScore` from this object response. That does not make leaks impossible: `additionalProperties: true`, a different status/content-type schema, raw writes, streams or later hooks can change what leaves the service. Review every response path. Request validation can also coerce values or remove additional properties according to Ajv configuration; test the chosen policy instead of assuming rejection.

TypeScript route generics describe compile-time types; runtime schemas establish the input contract. They do not automatically make every `request.body` fully typed, and neither mechanism establishes authorization. Perform database-backed policy checks after inexpensive shape validation rather than inside an expensive asynchronous validator.

## Compare behavior before choosing or migrating

| Decision | Express | Fastify |
| ------------------- | ------------------------------------------------- | ------------------------------------------------ |
| Request composition | Ordered middleware and route stacks | Lifecycle hooks in plugin scopes |
| Promise rejection | Automatic for returned promises in v5; wrap in v4 | Async handler/hook failures enter error handling |
| Body handling | Attach explicit parsers and limits | Configured content-type parsers and limits |
| Response projection | Construct a DTO or use an application serializer | Optional response schemas plus explicit policy |
| Shared facilities | Router/middleware/application composition | Decorations and plugin inheritance |

Fastify's radix routing and prepared serializers can reduce repeated work, but no fixed 2× speed or 40% latency improvement follows for a database-bound service. Measure the full stack with representative payloads, connection reuse, validation, logging and CPU limits.

For migration, map each middleware to its lifecycle phase, preserve authorization and error shapes, and test unsupported content types, parser limits and mounted paths. A Fastify instance is not an Express middleware function that can be passed to `app.use('/v2', fastifyApp)`. Route both servers behind a proxy or use an explicitly compatible integration with its lifecycle constraints.

## Summary

Follow an Express request through its ordered stacks and a Fastify request through its lifecycle within a plugin scope. Own promises, response completion and failures explicitly. Trusted schemas prepare validation/serialization work and help project responses; authorization and migration behavior still need separate, representative tests.

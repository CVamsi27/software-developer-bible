# Node.js Interview Questions

## Definition

This bank contains 44 Node.js interview prompts. Use it after the chapter/category revision passes to practice explaining a mechanism and its failure boundary in your own words.

## First Principles

An interview answer must specify the setting in which its claim holds. A runtime scheduling answer needs its execution context; a distributed guarantee needs the transaction, acknowledgment and failure boundary. When a question is underspecified, state an assumption, trace one operation and explain the consequence of a failure.

## Practice one decision at a time

For each prompt, give a brief answer before reading the explanation. Then answer its follow-up using a concrete request, byte sequence, process event or failure trace. The links lead to canonical implementations; the bank avoids duplicating large snippets that drift from them.

## Runtime foundations

### Q1: What is Node.js and why is it used?

**Answer:** Node runs JavaScript with V8 and provides server-side I/O through native APIs and libuv. JavaScript normally executes on one thread per isolate; the process also has native/V8 threads and can create workers. Concurrent network I/O can progress without one application thread per connection. CPU-heavy callbacks still delay that isolate's requests. Choose it based on the workload and ecosystem, then measure latency and capacity. See [the execution trace](../01-runtime-and-async/20.1.1.01-event-loop.md).

**Follow-up:** Which part of a database request runs locally, and which part waits on the database?

### Q2: What is the event loop in Node.js?

**Answer:** The loop dispatches callbacks when timers and I/O become eligible. Poll handles incoming I/O; check runs `setImmediate`; close callbacks handle certain closures. Native I/O may rely on the OS or libuv pool rather than running in the JavaScript callback. Microtask checkpoints and `nextTick` processing occur around execution; they are not extra libuv phases. Node 20's libuv change runs timers after poll. Top-level `setTimeout(0)` versus `setImmediate` order is not fixed. See [event-loop examples](../01-runtime-and-async/20.1.1.01-event-loop.md).

**Follow-up:** Why does a completed socket read still wait behind a long synchronous callback?

### Q3: What is the difference between process.nextTick and setImmediate?

**Answer:** `nextTick` schedules work before advancing the event loop after the current JavaScript operation; `setImmediate` runs in check and can yield across an I/O turn. Recursive next ticks can starve I/O. Promise microtask order relative to next ticks depends on the scheduling context, including ESM top-level execution. Use a deliberately bounded task queue or CPU slices rather than treating either callback as free concurrency.

**Follow-up:** Why can `setImmediate` improve responsiveness without reducing total computation?

### Q4: What are streams in Node.js?

**Answer:** Streams move bytes or objects with a demand/pressure contract. Readable produces, Writable accepts, Duplex has both directions, and Transform relates input to output. `write(false)` means the chunk was accepted but the producer should pause until `drain`; `highWaterMark` is a buffering threshold rather than a universal memory cap. Use `pipeline` to own errors and cleanup. Text decoding must preserve multibyte characters split across chunks. See [bounded NDJSON and pipeline examples](../02-io-and-data/20.1.2.01-streams.md).

**Follow-up:** Which extra allocations can defeat a correctly backpressured pipeline?

### Q5: What is the difference between require and import?

**Answer:** `require` uses CommonJS and usually loads synchronously; static `import` belongs to ESM and participates in linking, live bindings and module evaluation. ESM may evaluate asynchronously through top-level await. Dynamic `import()` is available in both contexts. Explicit `.cjs`, `.mjs` and package `type` select module interpretation; ambiguous-source behavior and CommonJS-to-ESM interoperability depend on the Node version. Modern Node can require some synchronous ESM graphs, but not a graph requiring asynchronous evaluation. Tree shaking is a bundler capability, not a promise that Node removes unused imports.

**Follow-up:** What changes if an imported dependency uses top-level await?

### Q6: What is middleware in Express.js?

**Answer:** A matched middleware layer receives request, response and `next`. It may add context, complete the response or continue dispatch. Order matters, but middleware does not necessarily run on every route: mounts and route-specific handlers restrict it. Four-argument functions are error middleware. Presence of an Authorization header is not authentication; verify its credential and resource policy. See [the mounted-router trace](20.1.4.03-express-fastify-internals.md).

**Follow-up:** What happens when a middleware neither responds nor calls `next`?

### Q7: How do you handle errors in Node.js?

**Answer:** Own each operation's failure channel: error-first callback, rejected promise, synchronous throw or stream/emitter `error`. A `try/catch` does not catch a later callback throw. Await or return the promise a framework owns; Express 5 forwards returned promise rejections, while Express 4 needs a wrapper. Expected failures can become controlled responses; unexpected process-level failures require telemetry and a termination policy rather than indefinite recovery. See [framework errors](20.1.4.03-express-fastify-internals.md).

**Follow-up:** Who owns an error from a timer started by an already completed request?

### Q8: What is a Buffer in Node.js?

**Answer:** Buffer is a mutable `Uint8Array` subclass representing bytes. Its backing storage contributes to external memory/RSS, but its lifetime still participates in garbage collection. Strings represent UTF-16 code units, so string length differs from encoded byte length. `Buffer.from(buffer)` copies; `subarray` shares storage. Small retained slices can keep a much larger backing allocation alive. Choose byte order and field width explicitly for binary protocols. See [the frame decoder](../02-io-and-data/20.1.2.02-buffers.md).

**Follow-up:** Why can a small cached view retain megabytes?

### Q9: What is the module.exports object?

**Answer:** CommonJS returns `module.exports` to callers. `exports` initially aliases that object; adding a property works, but reassigning `exports` alone changes only the local variable. The cache is keyed by resolved module filename, so a module is not a universal singleton across separate processes or distinct resolved copies. Cycles may expose partially initialized exports. Extract shared dependencies when possible rather than depending on initialization order.

**Follow-up:** Would a worker thread share a module-level Map with the main thread?

### Q10: What is npm and how do you use it?

**Answer:** `package.json` describes dependencies/scripts; the lockfile records the resolved dependency graph and integrity metadata. `npm ci` requires an aligned lockfile and removes the existing install before installing that graph. Platform-specific dependencies and lifecycle scripts mean a lockfile alone does not guarantee byte-identical build outputs. `npx`/`npm exec` runs package commands and can download/install missing packages into a cache; it is not "execution without installation." Review dependencies and build credentials. See [supply-chain boundaries](20.1.4.01-node-security.md).

**Follow-up:** What authority does a dependency install script have in CI?

## Operational mechanisms

### Q11: What is the difference between process.nextTick and setImmediate in terms of execution order?

**Answer:** For a synchronous CommonJS entry point scheduling nextTick, Promise.then and setImmediate, the familiar order is main output → nextTick → promise callback → immediate. ESM evaluation already runs through the microtask machinery, so a top-level promise can precede the next tick. In an I/O callback, an immediate generally runs before a timer scheduled there. Explain the context before predicting output, and avoid claims that one scheduling API always wins in every nesting pattern.

**Follow-up:** Write one probe for CommonJS and another for ESM, then explain the differing order.

### Q12: How do you implement rate limiting in Node.js?

**Answer:** Choose identity, algorithm, state location and failure policy. A process-local limit applies independently in each worker; shared limits need an atomic shared operation. Fixed windows permit boundary bursts; sliding logs require unique members and bounded retention; a token bucket allows a defined burst/refill rate. Bound identity cardinality, trust proxy headers deliberately and return useful retry guidance. See [the verified Redis token bucket](../../20.8-caching/20.8.03-advanced-redis-patterns.md).

**Follow-up:** How do NAT and spoofed forwarding headers change an IP-only policy?

### Q13: What is the difference between spawn, exec, execFile, and fork?

**Answer:** `spawn` exposes streaming stdio; `exec` runs a shell command with buffered output; `execFile` directly starts an executable unless a shell is requested; `fork` starts another Node process with an IPC channel. Shell-free argument arrays prevent shell expansion, but executable options and file access still need a narrow policy. Handle spawn errors, exit status, stdio closure, timeout and output limits. See [the process boundary examples](../03-processes-and-concurrency/20.1.3.02-child-processes-workers.md).

**Follow-up:** Why does child `exit` not guarantee all stdout has been consumed?

### Q14: How do you handle unhandled promise rejections?

**Answer:** Catch failures at the operation that can decide their meaning. With the modern default `--unhandled-rejections=throw`, a rejection with no owning handler can become an uncaught exception; a registered `unhandledRejection` listener changes that default behavior. Installing a logging listener is therefore not automatically a fatal-exit policy. Define bounded shutdown for unrecoverable failures and preserve a failing exit status. Do not continue merely because a process listener printed the error. See [process lifecycle](../03-processes-and-concurrency/20.1.3.03-process-environment.md).

**Follow-up:** How would a telemetry listener accidentally suppress the default termination?

### Q15: What is the difference between Buffer.alloc and Buffer.allocUnsafe?

**Answer:** `alloc` initializes bytes, normally to zero. `allocUnsafe` may expose previous memory contents until every observable byte is overwritten; eligible small allocations can use a shared pool. "Temporary" or "internal" is not enough if a later write returns fewer bytes than expected. Track the initialized length and expose only that range, or choose zero initialization. Neither buffer type automatically clears memory when released. See [allocation and partial-write boundaries](../02-io-and-data/20.1.2.02-buffers.md).

**Follow-up:** What leaks if a short file read is followed by sending the whole unsafe allocation?

### Q16: How do you implement authentication in Node.js?

**Answer:** Choose a session or token flow, verify credentials centrally, and authorize each resource independently. JWT verification needs the intended algorithms, signature, expiry, issuer and audience; revocation/key rotation still need a policy. Browser cookies need Secure/HttpOnly and an appropriate SameSite/CSRF strategy; HttpOnly does not make XSS harmless. OAuth delegates authorization, while OpenID Connect adds an identity layer. Use a password hashing scheme with measured parameters and bounded login work. See [security](../../20.5-security/INDEX.md).

**Follow-up:** How can a valid token still lack permission to read a particular order?

### Q17: What is the difference between readFile and createReadStream?

**Answer:** `readFile` returns the complete file content; a stream lets the consumer process bytes incrementally with pressure. A stream's high-water threshold is not a promise that every chunk has exactly that size or that total memory remains fixed. The decision depends on file size, simultaneous work and whether processing requires the entire document. Handle errors and cancellation through an owned pipeline. See [filesystem reading](../02-io-and-data/20.1.2.03-file-system.md).

**Follow-up:** Why can ten individually small whole-file reads still exhaust memory?

### Q18: How do you implement caching in Node.js?

**Answer:** Define what may be stale, key authorization context, invalidation and a bounded storage policy. Cache-aside reads may miss, load the source and populate the cache; concurrent fills can race with writes, even when writers delete the key. TTL bounds key residence, not necessarily source staleness. Distinguish missing values from valid false/zero/null, and own Redis connection/errors/timeouts. Do not cache every response by raw URL across tenants. See [cache-aside boundaries](../../20.8-caching/20.8.01-caching-deep-dive.md).

**Follow-up:** Trace a stale fill that occurs after a writer commits and deletes the cache key.

### Q19: What is the difference between cluster and worker_threads?

**Answer:** Cluster workers are separate processes with separate heaps and pools; they can share an HTTP listening port. Worker threads use separate V8 isolates within one process; data is cloned, transferred or explicitly shared. Transfers change ownership rather than creating concurrent shared access. Neither is required merely to overlap ordinary network I/O. Choose processes for the isolation/deployment boundary and workers for suitable CPU tasks with bounded admission. See [workers](../03-processes-and-concurrency/20.1.3.02-child-processes-workers.md) and [cluster](../03-processes-and-concurrency/20.1.3.01-clustering.md).

**Follow-up:** Does one worker's CPU task justify multiplying every database pool?

### Q20: How do you implement logging in Node.js?

**Answer:** Use structured events, correlation/trace context, meaningful levels, redaction and a bounded transport. Do not log full request bodies, cookies or tokens. Console/file/remote transports have different pressure and loss behavior; decide what happens if the sink is slow or unavailable. Collect logs outside the compromised application where integrity matters, and control retention/access. A logger choice alone does not guarantee high throughput or audit durability.

**Follow-up:** How do you preserve a request ID without putting user IDs into every metric label?

## Service decisions

### Q21: How would you design a scalable microservices architecture with Node.js?

**Answer:** Start with a concrete ownership or scaling requirement for the split. Bound synchronous calls with deadlines and concurrency limits; use durable asynchronous delivery where the product tolerates delay. Discovery health checks filter unhealthy endpoints but do not necessarily delete registry entries; configure deregistration/lifecycle deliberately. Define data ownership, idempotency, retry limits and trace propagation. A modular monolith may satisfy the requirements with less distributed failure surface. See [microservices](../../20.6-microservices/INDEX.md).

**Follow-up:** Which failed dependency can be degraded, and which failure must fail the request?

### Q22: How would you implement real-time features with WebSockets?

**Answer:** Authenticate the handshake, check permitted origins for browser access and authorize each message/room. Bound frame size, send queues and active connections; handle parse/promise errors and heartbeat timeouts. Browsers cannot set arbitrary headers through the standard WebSocket constructor, so use an appropriate cookie or short-lived ticket flow without leaking durable tokens in URLs. For replicas, route fan-out to each node's local connections and define message history separately. Established sockets remain on one connection; polling/reconnect flows may need additional routing/adapter policy.

**Follow-up:** What happens when a slow client accumulates outbound messages?

### Q23: How do you optimize Node.js performance?

**Answer:** Reproduce the symptom, identify queue wait versus work and profile the suspected resource. Correct blocking calls, N+1 requests, excess serialization, unbounded fan-out and buffer retention before guessing at V8 micro-optimizations. Streaming reduces whole-payload retention only if every stage respects pressure and avoids accumulating output. Scaling workers also multiplies memory/pools. Compare before/after latency, errors and resource use under identical load. See [the triage workflow](20.1.4.02-debugging-profiling-nodejs.md).

**Follow-up:** Why could adding workers lower throughput against a saturated database?

### Q24: How would you implement a task queue system?

**Answer:** Separate durable enqueue from execution. If a database change must produce a job, commit an outbox record in the same database transaction; adding to Redis inside that transaction is not an atomic cross-system commit. Consumers need idempotent side effects, bounded retries/backoff, poison-job handling, monitoring and fair capacity for job classes. Lease expiry or a lost acknowledgment can cause repeated execution. Use the documented API for the locked queue-library version rather than copying Bull APIs into BullMQ. See [brokers and outbox](../../20.9-message-brokers/INDEX.md).

**Follow-up:** How can the side effect succeed while the worker still reports failure?

### Q25: How do you implement monitoring and observability?

**Answer:** Use metrics for rates/distributions, traces for request timing/relationships and logs for contextual events. Initialize an actual OpenTelemetry provider/exporter and instrument before application modules; importing the API alone yields no exported traces. Propagate active context across hops. Metric labels need bounded cardinality: use route templates and a fixed unmatched-route label, never a raw path fallback. Include aborted requests without double-counting completion. See [Node diagnostics](20.1.4.02-debugging-profiling-nodejs.md).

**Follow-up:** How do you distinguish database execution time from waiting for a pool connection?

### Q26: How would you implement API versioning?

**Answer:** Write a compatibility policy before adding a route prefix or header. Additive optional fields can still break strict consumers, signatures or closed enums, so compatibility depends on the contract and client behavior. Path, header or media-type selection changes caching and observability; header selection may require Vary. Track use, document migration and sunset policy, and test supported versions. Avoid unvalidated fallbacks that silently interpret unknown versions as v1. See [REST API evolution](../../20.3-rest-apis/INDEX.md).

**Follow-up:** What evidence permits removing an old version safely?

### Q27: How do you handle database connections in a clustered environment?

**Answer:** Budget pool maximum × processes × replicas, including workers/jobs and headroom for operations. Create pools where queries run, not an unnecessary large pool in the cluster primary. Close pools after request admission/draining. PgBouncer transaction pooling reassigns backends between transactions, so session locks and persistent session settings are unsuitable. Protocol-level prepared statements can be supported with the appropriate PgBouncer version/configuration; SQL PREPARE is different. Never blindly retry a mutation after a connection reset because commit outcome may be uncertain.

**Follow-up:** How would you resolve an unknown commit outcome without a duplicate payment?

### Q28: How would you implement a message queue system?

**Answer:** Specify publish acceptance, broker persistence/replication, delivery and acknowledgment separately. A durable RabbitMQ queue and persistent message are insufficient to prove a publish was accepted; use confirms, handle unroutable messages where needed and respect channel write pressure. Set consumer prefetch; parse/validate before handling, acknowledge only the completed outcome and cap retries rather than immediate infinite requeue. Redelivery still requires idempotent effects. See [broker examples](../../20.9-message-brokers/INDEX.md).

**Follow-up:** What does a publisher confirm say about the consumer's database transaction?

### Q29: How do you implement error boundaries in Express?

**Answer:** Use downstream four-argument error middleware for failures Express owns. Forward callback failures and Express 4 async rejections; Express 5 handles returned/awaited promise rejections. Return validated public error shapes for expected failures, log unexpected details server-side and use a generic 500. If headers were sent, delegate so the connection can be closed rather than writing another response. A custom error's name or `isOperational` flag alone is not proof its message is safe. See [the executable Express example](20.1.4.03-express-fastify-internals.md).

**Follow-up:** Can this middleware recover from an unrelated process-level exception?

### Q30: How would you implement a distributed caching system?

**Answer:** Redis Cluster assigns keys to 16,384 hash slots and redistributes slots during resharding; it is not an automatic consistent-hash ring. A cluster-aware client follows redirects/topology. Replicas provide failover with asynchronous replication, so acknowledged writes can still be lost in some failures. Multi-key operations generally need the same slot. Cache tenant projections with bounded TTL/invalidation, avoid production-wide KEYS scans and recognize that SCAN is not an atomic snapshot. See [advanced Redis patterns](../../20.8-caching/20.8.03-advanced-redis-patterns.md).

**Follow-up:** What happens to a lease if failover loses its acquisition write?

## System design

### Q31: Design a URL shortener service like bit.ly

**Answer:** Persist a unique short code → validated HTTP(S) destination mapping. Random codes need a uniqueness constraint plus collision retry; an enumerable counter has privacy/abuse implications. Keep redirect latency bounded and send analytics through a deliberate durable or best-effort path. Choose permanent versus temporary redirects with revocation and browser/CDN caching in mind: a cached 301 can outlive later deletion. Validate scheme, control abuse and define expiry/ownership. A hash or short code alone does not authorize a private destination.

**Follow-up:** How quickly can a reported phishing link stop redirecting from every cache?

### Q32: Design a real-time chat application

**Answer:** Separate durable messages, live fan-out, membership, presence and receipts. Persist a message ID/order before the chosen acknowledgment; authorize room membership on every action. Redis Pub/Sub delivers only to connected subscribers and is not offline history. Track local sockets per user/device rather than overwriting one socket, bound slow-client queues and expire presence through heartbeats. Define deduplication, reconnect history and what sent/delivered/read mean. See [broker delivery semantics](../../20.9-message-brokers/INDEX.md).

**Follow-up:** How does a reconnecting client recover messages missed while the node was restarting?

### Q33: Design a distributed file storage system

**Answer:** Define the object/version metadata and chunk placement across distinct failure domains. Hashes verify integrity and can support deduplication, but dedup requires reference/lifecycle accounting and must not leak cross-tenant existence. Publish a completed version only after its chosen durability threshold; incomplete uploads remain staging state. Stream transfer and recovery with bounded buffers, verify checksums, repair replicas and garbage-collect unreferenced chunks. Choose explicit concurrent-write semantics; no universal replication factor or chunk size fits every system.

**Follow-up:** Which metadata transaction prevents a download observing an incomplete upload?

### Q34: Design a task scheduling system

**Answer:** Separate schedule identity/time from job execution identity. Define timezone/DST behavior, missed-run catch-up and overlap policy. Replicated triggers need durable deduplication for each occurrence; a temporary SET NX lease can coordinate, but expiry/failover does not guarantee exactly one side effect. Consumers still need idempotency/fencing where appropriate. Track heartbeat, backlog, next expected occurrence and failed runs, and use the locked scheduler's current API. See [leases](../../20.8-caching/20.8.03-advanced-redis-patterns.md).

**Follow-up:** What if the original worker resumes after a lease expires and a replacement starts?

### Q35: How would you implement a payment processing system?

**Answer:** Use a stable idempotency key for one business operation and reuse it with identical parameters on retries; generating a new random key per retry defeats the purpose. Store local operation/outcome state durably and handle the provider's retention policy. Verify webhook signatures over the unmodified raw body before JSON parsing, persist/deduplicate events and process repeat/out-of-order delivery safely. Reconcile provider and internal records. Do not treat metadata supplied by a client as authoritative prices or inventory. Prefer provider tokenization and keep card secrets out of logs.

**Follow-up:** Which HTTP status should a temporary webhook persistence failure return so delivery can retry?

### Q36: Design a content delivery network edge

**Answer:** Define eligible shared-cache responses and their full representation: status, headers, body, authorization policy, host and Vary dimensions. Do not replay every cached response as 200 or cache private/Set-Cookie responses blindly. Normalize only dimensions the origin treats equivalently; changing query order can change semantics. Bound origin deadlines/body size and listener lifetime. Define stale serving, health/failover, purge propagation and content-hash URLs. Register proxy event handlers once, not once per request. See [HTTP ownership](../02-io-and-data/20.1.2.04-http-module.md).

**Follow-up:** Can a shared stale response contain a previous tenant's data?

### Q37: How would you implement feature flags in Node.js?

**Answer:** Evaluate a validated rule snapshot against server-owned user/tenant/environment context. Never spread client query fields over trusted targeting context. Use deterministic bucketing that includes flag identity and stable subject identity; validate percentages/variant weights and define missing-context fallback. Feature enablement does not grant authorization. Every flag needs an owner, expiry, kill-switch test, audit trail and a bounded stale/failure policy.

**Follow-up:** Why should enabling an experiment not bypass a resource permission check?

### Q38: Design a real-time analytics pipeline

**Answer:** Carry event ID, event time and trusted tenant context from ingestion. Define duplicate detection, late-event windows, retention and correction policy; windowing alone does not deduplicate repeated events. A Kafka handler must await bounded processing or explicitly pause/buffer with limits; a separate stream does not automatically backpressure Kafka. Coordinate effects and source progress for retry safety, avoid partial aggregate updates and preserve event time instead of replacing it with ingestion time. See [Kafka lag and delivery](../../20.9-message-brokers/INDEX.md).

**Follow-up:** How do you repair an aggregate after a duplicate or late event?

### Q39: How would you implement a service mesh for microservices?

**Answer:** A mesh is infrastructure managing service-to-service traffic and identity, not a JavaScript class wrapping gRPC. Depending on the implementation, proxies may be sidecars or shared/node-level data-plane components. Define which traffic they intercept, mTLS identity, policy, retries/deadlines and telemetry; application resource authorization and idempotency still remain. Measure proxy/control-plane costs and adopt capabilities against an actual shared operational need. See [microservices](../../20.6-microservices/INDEX.md).

**Follow-up:** What happens when both mesh and application retry the same mutation?

### Q40: Design a distributed rate limiter

**Answer:** Define a strict global budget or explicitly regional approximation. Update allowed state atomically; Redis pipelines batch transport but do not make a read/decide/write algorithm atomic. Sliding logs need unique request members; token buckets need consistent time/refill units, bounded key TTL and state updates for denied calls too. Select a product-specific failure posture rather than universal fail-open guidance, and measure latency/capacity. See [the runnable token-bucket implementation](../../20.8-caching/20.8.03-advanced-redis-patterns.md).

**Follow-up:** How can many requests with the same millisecond timestamp defeat a sorted-set limiter?

## Runtime supervision and application boundaries

### Q41: How do you keep PM2 from sending traffic to an application before its dependencies are ready?

**Answer:** Separate process start from readiness. Configure PM2 to wait for the application's ready signal, and send that signal only after required initialization and admission checks succeed. `listen_timeout` bounds the wait; PM2 may consider the worker ready when the timeout expires, so the timeout is not a failed health check. Alert on missing readiness and make the deployment health policy reject or roll back the release. See [PM2 process supervision](../03-processes-and-concurrency/20.1.3.04-pm2-process-supervision.md).

**Follow-up:** Which readiness dependencies are essential to serve this route, and which can degrade independently?

### Q42: PM2 reloads cluster workers one at a time. Why can a request still fail during the reload?

**Answer:** A rolling replacement keeps other workers available, but a request already executing on the retiring worker can be cut off if shutdown does not drain it before the deadline. PM2 can fall back to a regular restart when a worker does not reload in time. Availability therefore depends on readiness, graceful shutdown, capacity headroom and client retry semantics; a reload command alone does not prove zero failed requests. See [PM2 graceful startup and shutdown](../03-processes-and-concurrency/20.1.3.04-pm2-process-supervision.md).

**Follow-up:** How would you test whether a committed mutation with a lost response is safe to retry?

### Q43: Compare PM2 cluster workers with Watt application workers under a crash.

**Answer:** PM2 cluster mode supervises separate Node processes, each with its own process heap and operating-system boundary; Watt runs application workers as threads with separate V8 isolates inside one Node process. A worker-local failure can be replaced at its layer, but both can lose in-flight work. A Watt process-wide native crash or OOM can affect all its applications, while process separation costs more memory and operational setup. See [PM2 process supervision](../03-processes-and-concurrency/20.1.3.04-pm2-process-supervision.md) and [Watt runtime architecture](../03-processes-and-concurrency/20.1.3.05-watt-runtime-architecture.md).

**Follow-up:** Which state must leave worker memory before either recovery mechanism can be safe?

### Q44: When should a Watt application become a separately deployed network service?

**Answer:** Split it when it needs an independent release cadence, scaling policy, compliance boundary or process-level fault containment. The `.plt.local` call can become an HTTP URL to a network service, but the boundary now has network timeouts, availability, authentication and retry semantics. Design those contracts before moving the code; URL substitution does not preserve in-process reliability or latency. See [Watt runtime architecture](../03-processes-and-concurrency/20.1.3.05-watt-runtime-architecture.md).

**Follow-up:** Which observable production signal would tell you the shared deployment boundary has become a constraint?

## Summary

A useful answer names who owns the work, what state can change, when success is acknowledged and how the mechanism behaves under overload or failure. Use the canonical chapters for implementation details and these prompts for explanations and trade-offs.

# LLM App Architecture

> **TL;DR:** Production LLM features are systems, not API calls. The three levers are **prompting** (cheapest, format-limited), **RAG** (adds private/fresh knowledge via retrieval), and **fine-tuning** (changes behavior; expensive — last resort). Outputs that feed code must be **structured** (JSON schema / function calling). Everything streams. Every call is metered, traced, and fallback-protected.

---

## First Principles

LLM application architecture follows from the model's three economic properties:

1. **Inference is expensive, slow, and non-deterministic.** Every design choice defends against one of those: caching and batching against cost, streaming against latency, temperature and structured outputs against variance. Architecture is constraint management, not prompt cleverness.
2. **The model is stateless per call — context is the memory.** Everything the model "knows" about this conversation must be re-sent every call (context window as the scarce resource): conversation history, retrieved documents, tool results. Context engineering (→ 20.12.02) is therefore the core engineering discipline, not a preprocessing step.
3. **Capabilities compose as tools, not training.** The app gives the model *functions* (search, DB, APIs); the model decides when to call them (function calling). The architecture is a loop — model ↔ tools ↔ results — which is why evals and observability (→ 50.1) matter more here than anywhere.

## Definition

An LLM application = model + retrieval + prompt assembly + structured output handling + guardrails + observability. The model is the least durable part of the stack — architect so you can swap providers.

## Why Do We Need It?

Naive integrations fail in predictable ways: hallucinated answers without grounding, brittle string-parsed outputs, 30-second synchronous requests blocking event loops, surprise invoices, PII leaving the perimeter. Architecture is what makes LLM features shippable.

## How It Works

### The three knowledge levers

| Lever | What it changes | Cost | When |
| --------------- | --------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------ |
| **Prompting** | Instructions only | ~0 | Default start; narrow tasks, stable formats |
| **RAG** | What context the model sees per request | Retrieval infra + embedding costs | Private docs, fresh data, citations needed |
| **Fine-tuning** | Model weights/behavior | High: data ops + training + evals + redeploy per model bump | Style/format compliance at scale, latency via smaller tuned models |

**Interview rule:** always say "prompt → RAG → fine-tune, in that order" and name a fine-tuning trigger ("when prompt engineering plateaus on a measurable metric and volume justifies it").

### RAG pipeline

```text
INGEST documents → chunk (~500–1000 tok, overlap) → embed → vector store
QUERY question → embed → top-k similarity search (+ metadata filters)
AUGMENT assemble prompt: system + retrieved chunks (with sources) + question
GENERATE stream tokens; attach citations from chunk metadata
EVAL groundedness · relevance · cost/latency per answer
```

```typescript
// retrieval sketch (NestJS-shaped)
const embedding = await embedder.embed(question);
const chunks = await vectorStore.search(embedding, {
  topK: 5,
  filter: { clinicId }, // tenancy applies to vectors too!
});
const answer = await llm.stream({
  system: SYSTEM_PROMPT,
  messages: [{ role: 'user', content: buildContext(chunks, question) }],
});
```

 *Traps:* "Why not dump everything in context?" (cost × latency × lost-in-the-middle degradation). "How do you chunk?" (structure-aware boundaries; overlap; evaluate recall). "Multi-tenant RAG leaks?" (filter embeddings by tenant AT QUERY TIME — never share an index namespace blindly).

### Streaming & backpressure

SSE/streaming tokens keep perceived latency low. Server-side: async generators, flush per chunk, client renders progressively; timeouts + abort signals bound runaway generations.

### Function calling / structured output

Give the model typed tools (`zod` schema → JSON schema); the provider returns arguments to *validate and execute yourself*. Never trust-and-execute raw output: validate with Zod, permission-check the action, then run.

## Code Examples

**1. The provider is a dependency, not a foundation.** One interface, swappable adapters, routed per feature — so moving a single feature to a cheaper model never touches its call site.

```typescript
export interface LlmProvider {
  name: string;
  stream(req: ChatRequest, signal: AbortSignal): AsyncIterable<Chunk>;
  complete(req: ChatRequest): Promise<Completion>;
  countTokens(text: string): number;
  pricePerKToken: { in: number; out: number };
}

// Route by capability and price, not by allegiance. The eval decides who serves what.
const ROUTES: Record<Feature, string> = {
  "ask-docs": "claude-sonnet",
  "classify-intent": "haiku",        // ~10× cheaper; the golden set says it clears the bar
  "summarize-nightly": "batch-large",
};

export const providerFor = (f: Feature) => registry[ROUTES[f]];
```

**2. The agent loop: the model proposes, the app validates, authorizes, and executes.** Model output is untrusted input — validate it exactly like an HTTP request body.

```typescript
const TOOLS: Record<string, Tool> = {
  searchRecords: {
    schema: z.object({ query: z.string().max(200) }),
    allow: (ctx) => ctx.role !== "guest",
    run: (args, ctx) => records.search(args.query, { tenantId: ctx.tenantId }),
  },
  issueRefund: {
    schema: z.object({ orderId: z.string().uuid(), reason: z.string().min(10) }),
    allow: (ctx) => ctx.role === "admin",     // the model must never widen its own authority
    run: (args) => billing.refund(args.orderId, args.reason),
  },
};

async function runTools(messages: Message[], ctx: Ctx, maxTurns = 6): Promise<string> {
  for (let turn = 0; turn < maxTurns; turn++) {
    const res = await providerFor("ask-docs").complete({ messages, tools: describe(TOOLS) });
    const call = res.toolCalls?.[0];
    if (!call) return res.content;                  // no tool requested → final answer

    const tool = TOOLS[call.name];
    const deny = !tool ? "unknown tool"
      : !tool.allow(ctx) ? "not authorized"
      : null;
    if (deny) {
      messages.push(toolResult(call, { error: deny }));   // feed the refusal back, don't throw
      continue;
    }

    const args = tool.schema.safeParse(call.arguments);   // schema check before any side effect
    messages.push(args.success
      ? toolResult(call, await tool.run(args.data, ctx))
      : toolResult(call, { error: "invalid arguments" }));
  }
  throw new Error("tool loop exceeded maxTurns — refuse rather than burn budget");
}
```

**3. Streaming with a hard ceiling.** SSE out, abort signal in — because the client will navigate away mid-generation.

```typescript
async function streamAnswer(req: Request, res: Response) {
  const controller = new AbortController();
  req.on("close", () => controller.abort());        // client disconnected → stop billing
  const deadline = setTimeout(() => controller.abort(), 60_000);

  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");
  res.setHeader("X-Accel-Buffering", "no");         // defeat proxy buffering, or nothing streams

  try {
    for await (const chunk of providerFor("ask-docs").stream(req.body, controller.signal)) {
      res.write(`data: ${JSON.stringify({ delta: chunk.text })}\n\n`);
    }
    res.write("event: done\ndata: {}\n\n");
  } catch {
    // Headers are already sent: we can no longer change the status code,
    // so an in-band error frame is the only honest signal left.
    res.write(`event: error\ndata: ${JSON.stringify({ message: "generation_failed" })}\n\n`);
  } finally {
    clearTimeout(deadline);
    res.end();
  }
}
```

**4. Meter at the boundary**, where attribution is still cheap — tokens become money here and nowhere else.

```typescript
async function measured<T>(feature: Feature, tenantId: string, fn: () => Promise<Usage<T>>) {
  const started = performance.now();
  const { value, usage } = await fn();
  const p = providerFor(feature).pricePerKToken;

  metrics.observe("llm.request", {
    feature, tenantId, model: ROUTES[feature],
    ttftMs: usage.ttftMs,
    totalMs: performance.now() - started,
    inTokens: usage.input, outTokens: usage.output,
    cents: (usage.input / 1000) * p.in + (usage.output / 1000) * p.out,
  });
  return value;
}
// Alert on cents per tenant and on the ratio inTokens/outTokens drifting upward:
// both move before the invoice does.
```

## Real-World Use Cases

| Feature | Architecture choice |
| ----------------------------------------- | ----------------------------------------------------------------------------------- |
| Clinical suggestion w/ ICD codes (Docita) | Structured-output normalizer over domain corpus + human-in-loop review UI |
| "Ask our docs" support bot | RAG over versioned docs; citations mandatory; refusal when retrieval confidence low |
| Invoice OCR → fields | Vision/OCR extraction + schema validation + confidence thresholds |
| Semantic search over records | Embeddings + pgvector-style store, tenant-filtered |

## Common Mistakes

| Mistake | Fix |
| ------------------------------------- | --------------------------------------------------- |
| Parsing free-text answers for logic | Structured output + schema validation |
| One giant prompt accreted over months | Versioned prompts as reviewed artifacts |
| Sync request holding connection 60s | Streaming + timeouts + queue for long jobs |
| No eval before changing a prompt | Golden-set regression evals in CI |
| Vector index ignores tenancy | Tenant-scoped namespaces/filters |
| Provider outage = feature outage | Cached responses → smaller model → graceful degrade |

## Best Practices

- **Start at the cheapest lever that could work** (prompting) and escalate only on a *measured* failure — "the golden set plateaus" beats "the model seems weak".
- **Pin the model version.** Treat an automatic minor-version bump as a production change: it needs its own eval run, not a silent rollout.
- **Put the provider behind your own interface on day one.** Retrieval and observability can be retrofit; a hard-coded SDK call spread across 40 files cannot.
- **Validate every model output at the boundary** — schema *and* authorization, in that order — then execute. Never trust-and-execute a tool call.
- **Stream anything a human waits on, batch anything nobody waits on.** Embeddings and nightly summaries belong in a queue.
- **Log `feature@promptVersion@modelVersion` with each call** so any output can be reproduced and any regression attributed to exactly one change.
- **Design the degradation path before launch:** cached response → smaller model → queue for later → honest "try again". A provider outage should never be a feature outage.

## Performance Considerations

- Latency budget: TTFT (time-to-first-token) matters more than total time for UX; stream early.
- Cache aggressively: exact-match response cache + semantic cache where staleness tolerable.
- Batch offline work (embeddings, summarization) through queues — your Postgres queue pattern applies verbatim.
- Token accounting = money: log input/output tokens per request, alert on drift.

## Summary

- Prompting → RAG → fine-tuning, cheapest lever first; fine-tune only on evidence.
- Grounded generation (RAG) + citations beats clever prompting for factual domains.
- Structure outputs; validate like any untrusted input.
- Stream, meter, trace, and fall back — treat providers as unreliable dependencies.

## Cheat Sheet

```text
LEVERS prompt → RAG → fine-tune
RAG chunk → embed → top-k(+tenant filter) → assemble+sources → cite
OUTPUT JSON schema/function calling → Zod validate → execute
STREAMING SSE + abort + timeout; TTFT is the UX metric
RESILIENCE cache → smaller model → degrade; breaker around provider
COST tokens logged per call; budgets + alerts
```

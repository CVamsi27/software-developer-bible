# LLM App Architecture

An “ask our policies” feature can look like one model call. In production, it is a chain of decisions: which records the user may see, what evidence enters the prompt, how output is checked, and what happens when the provider is slow or unavailable. Architecture makes those boundaries explicit.

---

## Definition

An LLM application combines model inference with retrieval, prompt assembly, output validation, authorization and operational controls. A provider adapter can isolate operations your application uses, but it cannot make model capabilities, tool protocols, pricing or data-handling policies interchangeable.

> **Textbook Definition:** An LLM application architecture composes probabilistic model inference with deterministic data access, control flow, validation and operational controls. The application owns the correctness and authorization of effects initiated from model output.

## First Principles

LLM application architecture follows from three constraints: inference consumes resources, model calls use bounded context, and tool proposals must cross an application-controlled boundary:

1. **Inference is a metered remote operation with variable latency and output.** Cost and timing depend on the selected model, request shape, service conditions and provider pricing. Measure a representative workload; use batching, streaming or a smaller model only when each fits the product contract.
2. **The model can use only the context supplied to its inference.** Many APIs treat calls as independent unless the application resends history or uses provider-managed conversation state. Either way, the application must know which history, retrieval results and tool outputs are included, authorized and within the context budget. Context engineering (→ 20.12.02) is part of request design, not merely preprocessing.
3. **A tool-calling flow lets the model propose an operation.** The application decides which tools to expose, validates each proposal, authorizes it and executes it. The protocol is a loop — model proposal → application action → correlated result → another model call — which makes bounded steps, evals and observability important.

## How It Works


### 1. Follow one request

The model is one component in an application-owned path. Awaiting network I/O does not itself block Node.js, but slow generations still hold connections and provider capacity; bound them with deadlines, admission limits, and a defined failure path.

### 2. The three knowledge levers

| Lever | What it changes | Cost | When |
| ---------------------------------------- | --------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------ |
| **Prompting** | Instructions/examples/context | Engineering and input-token cost | Default start; narrow tasks, stable formats |
| **Retrieval-augmented generation (RAG)** | What context the model sees per request | Retrieval infra + embedding costs | Private docs, fresh data, citations needed |
| **Fine-tuning** | Model weights/behavior | High: data ops + training + evals + redeploy per model bump | Style/format compliance at scale, latency via smaller tuned models |

**Selection rule:** prompting supplies instructions/examples, retrieval supplies request-time evidence, and fine-tuning updates model weights from examples. Choose based on the measured failure; consider tuning only when the behavior gap and data, evaluation, serving, and maintenance costs justify it.

### 3. RAG pipeline

```text
INGEST documents → split at useful boundaries → embed → vector store
QUERY question → embed → top-k similarity search (+ metadata filters)
AUGMENT assemble prompt: system + retrieved chunks (with sources) + question
GENERATE stream tokens; attach citations from chunk metadata
EVAL groundedness · relevance · cost/latency per answer
```

Chunk size and overlap are workload and provider choices, not universal constants. Start with structure-aware boundaries, then measure retrieval quality, context use and citation fidelity on representative queries. If a managed service supplies a default strategy, verify the current setting and evaluate it for your documents.

```typescript
// retrieval sketch (NestJS-shaped)
const embedding = await embedder.embed(question);
const chunks = await vectorStore.search(embedding, {
  topK: retrievalPolicy.validatedCandidateLimit, // choose from recall/latency evaluation
  filter: { tenantId: principal.tenantId }, // derive scope from authenticated server context
});
const answer = await llm.stream({
  system: SYSTEM_PROMPT,
  messages: [{ role: 'user', content: buildContext(chunks, question) }],
});
```

Apply tenant authorization in the retrieval path before any candidate can be returned to the caller. A vector engine may apply metadata filters after an approximate scan, which can reduce the number of eligible hits; inspect its behavior and measure recall per tenant. A filter in application code is not an isolation boundary unless the store query enforces it.

The retrieval result is evidence, not authorization. Scope the query using the authenticated principal, then check access to each source again before exposing its content or citation. Context size and ordering are evaluated for the selected model and task; more text is not automatically more useful.

### 4. Streaming & backpressure

Server-Sent Events (SSE) and other streaming transports can improve perceived responsiveness by showing output as it arrives. The server can use async iterators; the client renders partial content according to its format. Deadlines and cancellation signals bound the request, but the provider adapter must honor cancellation.

### 5. Function calling / structured output

Give the model typed tools (`zod` schema → JSON schema); the provider returns arguments to *validate and execute yourself*. Never trust-and-execute raw output: validate with Zod, permission-check the action, then run.

### 6. The release contract

Before launch, demonstrate the paths that protect the feature under normal and failed conditions:

- A prompt or model change runs representative quality, refusal, and grounding evaluations; keep versions and results so regressions can be attributed.
- Every structured response is schema-validated. Every proposed action is separately authorized against current server-side state.
- Interactive streams have a deadline, cancellation path, and backpressure handling. Long offline work uses a durable queue and idempotent retry policy.
- Cost is attributed by feature and model using actual usage categories. Any reservation or cap is enforced before dispatch.
- A fallback is eligible only if its data policy, capacity, and evaluated quality fit the request. Cache only when answer, permissions, and source revisions make reuse safe.

## Code Examples

These adapter-oriented TypeScript sketches require the declared domain types, trusted principal, provider implementations and bounded service dependencies. They illustrate application boundaries rather than a complete SDK integration. The orchestration chapter supplies an executable local control-loop model.

**1. The provider is a dependency, not a foundation.** An internal interface can centralize routing and provider-specific adapters. A caller stays stable only when its required capabilities fit the interface; provider differences still need explicit mapping and compatibility tests.

```typescript
export interface LlmProvider {
  name: string;
  stream(req: ChatRequest, signal: AbortSignal): AsyncIterable<Chunk>;
  complete(req: ChatRequest, signal: AbortSignal): Promise<Completion>;
  countTokens(text: string): number;
  estimateCostCents(usage: UsageBreakdown): number; // model/version/category-specific pricing
}

// Route by capability and price, not by allegiance. The eval decides who serves what.
const ROUTES: Record<Feature, string> = {
  "ask-docs": "docs-answer-model",
  "classify-intent": "small-classifier", // configured adapter/model; justify routing with your evals
  "summarize-nightly": "batch-large",
};

export const providerFor = (f: Feature) => registry[ROUTES[f]];
```

**2. Tool calls belong to the orchestration boundary.** A provider may return typed tool-call data, but the application still validates arguments, checks resource-level authorization, enforces budgets, executes the operation, and returns a correlated result. Mutations also need atomic business invariants and idempotency; see [Agent Orchestration](20.12.04-agent-orchestration-patterns.md) for the control loop.

**2. Streaming with a hard ceiling.** SSE out, abort signal in — because the client will navigate away mid-generation.

```typescript
import { once } from 'node:events';
import type { Request, Response } from 'express';

async function streamAnswer(req: Request, res: Response) {
  const controller = new AbortController();
  const onClose = () => { if (!res.writableEnded) controller.abort(); };
  res.on('close', onClose); // response transport closed, not request body completed
  const deadline = setTimeout(() => controller.abort(), 60_000);
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('X-Accel-Buffering', 'no');
  res.flushHeaders();

  async function send(frame: string) {
    if (controller.signal.aborted || res.destroyed) throw new Error('stream aborted');
    if (!res.write(frame)) await once(res, 'drain', { signal: controller.signal });
  }
  try {
    for await (const chunk of providerFor('ask-docs').stream(req.body, controller.signal)) {
      await send(`data: ${JSON.stringify({ delta: chunk.text })}\n\n`);
    }
    await send('event: done\ndata: {}\n\n');
  } catch {
    if (!controller.signal.aborted && !res.destroyed) {
      try { await send('event: error\ndata: {"message":"generation_failed"}\n\n'); }
      catch { /* transport no longer writable */ }
    }
  } finally {
    clearTimeout(deadline);
    res.off('close', onClose);
    if (!res.destroyed) res.end();
  }
}
```

The provider adapter must honor the signal; closing the local response cannot promise immediate remote cancellation or zero billing. Waiting for `drain` keeps a slow client from building an unbounded output buffer. Test disconnect, provider failure, and deadline paths.

**3. Meter at the boundary**, where attribution is still cheap — tokens become money here and nowhere else.

```typescript
async function measured<T>(feature: Feature, tenantId: string, fn: () => Promise<Usage<T>>) {
  const started = performance.now();
  const { value, usage } = await fn();
  const costCents = providerFor(feature).estimateCostCents(usage);

  metrics.observe("llm.request", {
    feature, model: ROUTES[feature], // avoid unbounded tenant-id metric labels; attribute spend in a ledger
    ttftMs: usage.ttftMs,
    totalMs: performance.now() - started,
    inTokens: usage.input, outTokens: usage.output, // include cached-input/cache-write/reasoning categories in cost
    cents: costCents,
  });
  return value;
}
// Alert on cents per tenant and on the ratio inTokens/outTokens drifting upward:
// both move before the invoice does.
```

## Real-World Use Cases

| Feature | Architecture choice |
| ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| Clinical-code suggestion (illustrative design) | Structured-output normalizer over domain corpus + human-in-loop review UI |
| "Ask our docs" support bot | RAG over versioned docs; citations mandatory; refusal when retrieval confidence low |
| Invoice OCR → fields | Vision/OCR extraction + schema validation + confidence thresholds |
| Semantic search over records | Embeddings + pgvector-style store, tenant-filtered |

## Summary

Choose prompting for task instructions, retrieval for request-time evidence, and tuning only for a measured behavior gap. Keep retrieval authorization, output validation, and side-effect permission in deterministic application code. Bound and observe provider calls, and use only fallbacks that are permitted and tested for the same task.

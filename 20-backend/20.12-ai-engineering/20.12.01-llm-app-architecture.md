# LLM App Architecture

You can wire an "Ask our policies" chat box to one Large Language Model (LLM) API call in an afternoon. In the first week of production, four things break: one user's answer leaks another tenant's private document, a slow model stream holds server connections open until pods run out of memory, a hallucinated tool argument triggers an invalid write, and the monthly token bill jumps tenfold. None of those is a model bug — every one is a missing **application architecture** boundary.

## Definition

An **LLM application architecture** wraps a probabilistic language model inside deterministic backend services that handle authentication, authorization, retrieval, prompt assembly, output validation, streaming, and cost metering. The model proposes text or structured tool calls; your backend — never the model — owns security, data access, business invariants, and reliability.

> **Textbook Definition:** An LLM application architecture composes probabilistic model inference with deterministic data access, control flow, validation, and operational controls. The application owns the correctness and authorization of every side effect initiated from model output.

## First Principles

Every production LLM design pattern follows from three hard constraints of language models:

1. **Inference is slow, metered, non-deterministic network I/O.** A normal database query finishes in single-digit milliseconds for fractions of a cent. An LLM call can take 2–30 seconds, bills per input and output token (with separate pricing for cached prefixes and reasoning tokens), and may return different text on identical inputs. Every call needs deadlines, concurrency limits, cost tracking, and evaluation gates.
2. **The model only knows what fits inside the request's context window.** Stateless chat APIs do not remember earlier turns unless you send conversation history back (or opt into provider-managed conversation state). Your application must explicitly choose which instructions, retrieved documents, and tool results fit within the token budget — and prove the current user is authorized to see every piece of text inserted into the prompt (→ 20.12.02).
3. **Tool calls are proposals, not trusted executions.** When you give an LLM a tool schema, the model does not run your code; it returns a JSON payload saying *"please run `refundInvoice({ id: 'inv_123' })`."* Your backend must validate the arguments against a strict schema, verify the authenticated user has permission to refund `inv_123`, execute the action, and pass the correlated result back to the model.

## 1. Follow One Request End to End

Treat the model as one downstream dependency inside an application-owned pipeline, not the center of your system:

```text
Client
  │  HTTPS request + auth token
  ▼
API Gateway / Backend (AuthN + AuthZ + Pre-flight Budget Check)
  │
  ├──► 1. Retriever (tenant-scoped search over authorized documents)
  │
  ├──► 2. Prompt Assembler (system rules + retrieved chunks + token budget)
  │
  ├──► 3. Provider Adapter (stream + AbortSignal + wall-clock deadline)
  │         │
  │         ▼  (optional tool-call loop)
  │       Schema Validate (Zod) ──► Permission Check ──► Execute Tool
  │
  └──► 4. Output Validator + SSE Stream (with backpressure) + Cost/Latency Ledger
```

Awaiting an LLM HTTP call does not block Node.js's single-threaded event loop, but long-lived generations still hold open HTTP sockets, memory buffers, and upstream rate-limit slots. Always cap concurrent in-flight generations, enforce a hard wall-clock deadline, and define an explicit fallback or graceful error path when the provider times out.

## 2. Choose the Right Knowledge Lever: Prompting, RAG, or Fine-Tuning

When an LLM gives wrong answers, engineers often jump straight to fine-tuning. In practice, three levers solve different problems at very different costs:

| Lever | What it changes | Ongoing cost | Reach for it when… |
| ---------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **Prompting** | Instructions, examples, output format in the request | Low (engineering time + input tokens) | The model already has the knowledge; it needs clearer rules, edge-case examples, or structured output |
| **Retrieval-Augmented Generation (RAG)** | Evidence injected into the prompt at query time | Medium (indexing pipeline + embeddings + search store) | Answers depend on private, tenant-scoped, or frequently changing data and need source citations |
| **Fine-tuning** | The model's weights | High (curated dataset, training runs, evals, retraining on every base-model upgrade) | Prompting and RAG cannot match a strict style, domain syntax, or low-latency budget on a smaller model |

**Decision rule:** start with prompting to lock down behavior, add RAG whenever the model needs fresh or private facts, and consider fine-tuning only when measured evaluation failures justify maintaining a custom training pipeline.

## 3. How a RAG Pipeline Works — and Its Two Silent Failure Modes

RAG splits into an offline **ingestion** pipeline and an online **query** pipeline:

```text
INGEST:  Raw Docs ─► Structure-Aware Split ─► Embed ─► Vector + Keyword Index (with tenantId & ACL metadata)
QUERY:   Question ─► Embed ─► Tenant-Filtered Top-K Search ─► Assemble Prompt ─► Stream Answer + Citations
EVAL:    Measure retrieval recall, answer groundedness, refusal accuracy, latency, and cost per query
```

### Why chunk boundaries matter

Documents rarely fit whole into a prompt, so you split them into chunks before embedding:
- **Too small** (e.g., splitting mid-sentence or isolated 40-word fragments): a chunk says *"refunds are prohibited"* without the preceding heading (*"Custom Enterprise Hardware"*), causing false refusals.
- **Too large** (e.g., dumping entire 20-page manuals): embeddings average too many unrelated topics, retrieval precision drops, and irrelevant text bloats token cost.

Start by splitting along natural document structure (headings, sections, paragraphs) with light overlap so boundary sentences stay intact, then tune chunk size against a labeled retrieval evaluation set for your actual corpus.

### Two production traps in RAG

```typescript
// excerpt: tenant-scoped retrieval sketch (server-side principal only)
const embedding = await embedder.embed(question);
const chunks = await vectorStore.search(embedding, {
  topK: retrievalPolicy.validatedCandidateLimit, // tuned via recall/latency evals
  filter: { tenantId: principal.tenantId },      // ALWAYS from verified server auth, never req.body
});
const answer = await llm.stream({
  system: SYSTEM_PROMPT,
  messages: [{ role: 'user', content: buildContext(chunks, question) }],
});
```

1. **Post-filtering recall collapse:** Some Approximate Nearest Neighbor (ANN) vector indexes fetch the global `topK` matches *first* and apply `filter: { tenantId }` *afterward*. If tenant A owns only 1% of the index, a global `topK = 10` can leave 0 results after filtering. Check whether your vector store supports pre-filtering or iterative filtered scans, and measure recall per tenant — not just on a single-tenant test index.
2. **Retrieval is not authorization:** Filtering in application code after an unscoped database query is fragile and leaks recall. Enforce tenant scope inside the store query using the authenticated server principal, and re-verify document-level permissions (ACLs) before inserting content into the prompt or returning citations.

## 4. Stream Responses Safely: SSE, Backpressure, and Disconnects

Waiting 15 seconds for a full paragraph feels broken; streaming tokens over **Server-Sent Events (SSE)** drops **Time to First Token (TTFT)** to under a second so users start reading immediately.

Production streaming requires handling three real network realities:
- **Backpressure:** If a mobile client reads slowly, `res.write(chunk)` returns `false`, meaning Node's kernel send buffer is full. If you keep pumping tokens without awaiting the response's `drain` event, memory grows unboundedly until the process crashes with out-of-memory (OOM).
- **Client disconnect vs. request end:** Users close tabs mid-generation. Listen for `res.on('close')` (when `!res.writableEnded`) to abort an `AbortController` and stop reading from the LLM provider. Do **not** rely on `req.on('close')` — in modern Node.js, `req`'s `close` fires as soon as the incoming request body finishes reading, before streaming even starts.
- **Hard deadline:** Always attach a timeout (`setTimeout(() => controller.abort(), 60_000)`) so a stalled upstream model cannot hold a socket forever. Note that aborting locally stops reading and closes the connection, but whether the provider halts remote billing immediately depends on the adapter and vendor API.

## 5. Structured Outputs and Tool-Calling Loops

When downstream code consumes model output, request **structured output** constrained to a JSON Schema (often generated from `zod`) instead of parsing free-form prose with regexes.

When the model calls tools, the conversation follows a strict correlated protocol:

```text
1. User:      "Refund invoice INV-42 if eligible."
2. Assistant: tool_calls: [{ id: "call_1", name: "getInvoice", args: { id: "INV-42" } }]
3. Backend:   Validate args (Zod) ─► Check principal can access INV-42 ─► Execute DB read
4. Tool msg:  { role: "tool", tool_call_id: "call_1", content: "{\"status\":\"paid\",\"daysAgo\":5}" }
5. Assistant: "Invoice INV-42 is within the 14-day window..." (or proposes next tool call)
```

**Critical protocol rule:** Always preserve the assistant's `tool_calls` message in conversation history immediately before appending the matching `role: "tool"` result message. Provider APIs match each tool result back to its exact `tool_call_id` — dropping the assistant message breaks correlation, especially when a model returns multiple parallel tool calls in a single turn.

Never execute raw model arguments directly: validate types and ranges with Zod, re-check server-side authorization against current database state, enforce idempotency on mutations, and bound total steps (see [Agent Orchestration](20.12.04-agent-orchestration-patterns.md)).

## 6. The Production Release Contract

Before shipping an LLM feature to real users, verify five non-negotiable operational gates:

- **Versioned evals on every change:** Run representative quality, grounding, and refusal evaluations whenever a prompt, model version, or retriever changes, and store results alongside the version so regressions are traceable.
- **Strict validation and server-side auth:** Validate every structured payload against a schema, and authorize every read or write against the authenticated principal's current permissions.
- **Bounded lifetimes:** Interactive streams enforce deadlines, cancellation, and backpressure; long-running batch jobs move to durable queues with idempotent retries.
- **Boundary cost attribution:** Record input, cached-input, cache-write, reasoning, and output tokens per feature and model, and enforce spending caps *before* dispatching new requests.
- **Eligible fallbacks and permission-safe caching:** Only fall back to a secondary model if its data-residency policy, capacity, and evaluated quality meet the feature's contract. Cache answers only when the cache key includes tenant/permission scope and document revision.

## Code Examples

These TypeScript excerpts show the three backend boundaries you should build first: a swappable provider adapter, a backpressure-safe SSE endpoint, and boundary cost metering. (They assume your domain types, authenticated principal, and concrete vendor SDK adapters.)

### 1. Isolate Vendor SDKs Behind a Narrow Provider Interface

An internal interface keeps routing and metering in one place. Note the realistic boundary: an adapter decouples your callers from SDK boilerplate, but it does **not** make model capabilities, tool protocols, pricing, or data-handling policies interchangeable — test every routed model on your own evals.

```typescript
// excerpt: internal provider contract and feature-level routing
export interface LlmProvider {
  name: string;
  stream(req: ChatRequest, signal: AbortSignal): AsyncIterable<Chunk>;
  complete(req: ChatRequest, signal: AbortSignal): Promise<Completion>;
  countTokens(text: string): number;
  estimateCostCents(usage: UsageBreakdown): number; // accounts for input, cached, reasoning & output rates
}

// Route each feature by measured quality, latency, and unit cost.
const ROUTES: Record<Feature, string> = {
  'ask-docs': 'docs-answer-model',
  'classify-intent': 'small-classifier',
  'summarize-nightly': 'batch-large',
};

export const providerFor = (feature: Feature): LlmProvider => registry[ROUTES[feature]];
```

### 2. Stream SSE with Backpressure, Disconnect Abort, and a Hard Deadline

```typescript
// excerpt: backpressure-safe SSE streaming endpoint (Express + Node.js)
import { once } from 'node:events';
import type { Request, Response } from 'express';

async function streamAnswer(req: Request, res: Response) {
  const controller = new AbortController();

  // Detect client disconnect (res 'close' before stream ends — not req 'close').
  const onClose = () => {
    if (!res.writableEnded) controller.abort();
  };
  res.on('close', onClose);

  // Hard ceiling so a stalled upstream model cannot pin this connection forever.
  const deadline = setTimeout(() => controller.abort(), 60_000);

  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('X-Accel-Buffering', 'no'); // prevent Nginx from buffering SSE chunks
  res.flushHeaders();

  async function send(frame: string) {
    if (controller.signal.aborted || res.destroyed) throw new Error('stream aborted');
    if (!res.write(frame)) {
      // Slow client: pause upstream reads until kernel buffer drains, or abort on disconnect.
      await once(res, 'drain', { signal: controller.signal });
    }
  }

  try {
    for await (const chunk of providerFor('ask-docs').stream(req.body, controller.signal)) {
      await send(`data: ${JSON.stringify({ delta: chunk.text })}\n\n`);
    }
    await send('event: done\ndata: {}\n\n');
  } catch {
    if (!controller.signal.aborted && !res.destroyed) {
      try {
        await send('event: error\ndata: {"message":"generation_failed"}\n\n');
      } catch {
        // Transport closed while writing error frame; safe to ignore.
      }
    }
  } finally {
    clearTimeout(deadline);
    res.off('close', onClose);
    if (!res.destroyed) res.end();
  }
}
```

### 3. Meter Cost and Latency at the Provider Boundary

Attribute tokens and cost where the provider returns actual usage metadata. Keep high-cardinality `tenantId` values in a billing/usage ledger rather than Prometheus metric labels so you do not blow up time-series cardinality.

```typescript
// excerpt: boundary metering for latency, token mix, and cost
async function measured<T>(feature: Feature, tenantId: string, fn: () => Promise<Usage<T>>) {
  const started = performance.now();
  const { value, usage } = await fn();
  const costCents = providerFor(feature).estimateCostCents(usage);

  metrics.observe('llm.request', {
    feature,
    model: ROUTES[feature], // low-cardinality labels only; log tenantId to usage ledger
    ttftMs: usage.ttftMs,
    totalMs: performance.now() - started,
    inTokens: usage.input,
    outTokens: usage.output, // include cached-input/cache-write/reasoning in estimateCostCents
    cents: costCents,
  });

  await usageLedger.record({ tenantId, feature, model: ROUTES[feature], costCents, usage });
  return value;
}
```

## Real-World Use Cases

| Feature | Recommended architecture |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Clinical-code suggestion (illustrative)** | Structured-output normalizer over domain catalog + mandatory human-in-the-loop review UI |
| **"Ask our docs" support assistant** | Tenant-scoped RAG over versioned docs + mandatory citations + refusal when retrieval confidence is low |
| **Invoice OCR to structured fields** | Vision/OCR extraction + Zod schema validation + confidence thresholds routing low-confidence items to review |
| **Semantic search over records** | Hybrid vector (`pgvector`) + keyword search, tenant-filtered inside the query engine |

## Summary

Start with prompting for instructions, use RAG for fresh or private evidence, and reserve fine-tuning for measured gaps that simpler levers cannot close. Treat the LLM as an untrusted, metered remote dependency: enforce tenant authorization inside retrieval, validate every structured output and tool argument, preserve assistant `tool_calls` before tool results, stream SSE with `drain` backpressure and `res.on('close')` cancellation, and meter token costs at the provider boundary before shipping to production.

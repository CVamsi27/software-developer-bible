# Prompts, Context & Evals

Your support assistant worked well on Monday. By Friday, users report wrong refund dates and broken JSON responses. Nothing in your UI changed — so what broke? It could be a subtle prompt edit, a model snapshot update, a chunker tweak that shifted which documents entered the window, or a history summary that dropped an earlier fact. Because language models have no compiler to catch behavioral regressions, you need to treat the entire assembled request as a versioned input and measure changes with automated evaluations (**evals**).

---

## Definition

Three closely related practices keep a model's behavior predictable in production:

- **Prompt engineering:** writing clear instructions, examples, and output rules that guide what the model should do.
- **Context engineering:** choosing, ordering, and trimming *what information* goes into the model's limited input window — retrieved documents, conversation history, tool definitions, and schemas.
- **Evaluations (evals):** running a fixed test suite of inputs against your AI pipeline and scoring the outputs automatically so you can spot regressions before users do.

> **Textbook Definition:** Prompt engineering specifies instructions to a model; context engineering selects and structures the information supplied for inference; evaluation measures observed behavior against a defined task and dataset. Evaluation results characterize the tested conditions rather than guaranteeing future outputs.

## First Principles

A language model is a probabilistic function: the same request can yield slightly different answers, and a tiny change in wording or input data can flip accuracy sharply. Three engineering principles follow directly from that reality:

1. **Prompts are production code — versioned, reviewed, and tested.** Without a type checker or compiler, a one-line prompt edit is an unverified behavior change. Keep prompts in git, review edits in pull requests, log the exact prompt ID and version on every call, and run evals before shipping.
2. **Context is a scarce budget, not a dumping ground.** Instructions, tool schemas, chat history, and retrieved chunks all compete for the model's attention and token limit. Dumping more text often *hurts* accuracy and inflates latency and cost. Engineering the context means deciding what earns a slot and what gets dropped (→ 20.12.03).
3. **Evals replace guesswork with evidence.** Eyeballing five chat transcripts ("looks better to me") fails the moment you have 50 edge cases. Automated rule checks plus calibrated model grading give you the same release discipline that unit and performance tests give deterministic code (→ 50.1, → 50.4).

## 1. Structure a Prompt That Survives Code Review

Start with a clean, inspectable layout:

1. **Role and boundary** — what the assistant does and what it must refuse.
2. **Task instructions** — step-by-step rules and edge-case handling.
3. **Delimited context** — clearly wrapped reference documents or user data so instructions and data are easy to tell apart.
4. **Output contract** — the exact JSON schema or format the caller expects.

Treat this layout as a strong baseline rather than a rigid law: different models respond differently to where rules sit (beginning vs end), so test placement on your target model.

Four prompting techniques you should know when to reach for (and explain in interviews):

- **Zero-shot vs few-shot:** zero-shot gives instructions alone; few-shot adds 2–5 concrete input-output examples showing tricky edge cases or exact formatting.
- **Task decomposition:** split one complicated prompt ("extract entities, classify risk, write an email") into smaller, testable steps where each step has a narrow schema.
- **Verifiable intermediate steps:** ask for concise structured reasoning fields (such as matched policy clauses) when auditing decisions — note that dedicated reasoning models handle internal thinking tokens differently, so avoid forcing legacy "think step by step" boilerplate onto them without testing.
- **Self-consistency:** for high-stakes offline tasks, sample the model $N$ times and take the majority answer; expensive, so reserve it for workflows where error cost outweighs latency.

## 2. Budget the Entire Context Window

A common production bug is counting only the user's question and retrieved documents, then wondering why requests fail with a context-length error. In reality, **every byte of the serialized request** consumes tokens:

```text
Total window = system prompt
             + tool definitions & JSON output schema
             + conversation history (or rolling summary)
             + retrieved chunks + XML/JSON framing markers
             + user message
             + reserved output tokens (+ reasoning tokens, if applicable)
```

Follow three rules when assembling context:

- **Count the serialized payload, not individual strings.** Tokenization is not strictly additive across fields; message wrappers and JSON keys add overhead. Recount the full request for the exact model tokenizer before sending.
- **Never truncate silently.** If the request exceeds `window - outputReserve`, apply an explicit policy: drop the lowest-ranked retrieved chunks first, summarize older conversation turns (and test that summaries keep critical facts and pending tool-call and tool-result pairs), or return a clear error or fallback if required evidence will not fit.
- **Measure placement instead of guessing.** Some models pay less attention to facts buried in the middle of very long contexts (often called "lost in the middle"). How strong that effect is varies by model and task, so test chunk ordering on your eval set rather than assuming a universal rule. Also verify your retrieval index updates cleanly when source documents change so stale text never crowds out current policy.
- **Keep cacheable prefixes immutable from token zero.** Provider prompt caching reuses cached KV state only across the longest identical token prefix starting at index zero: placing dynamic values (such as current timestamps, request identifiers, or retrieved chunks) ahead of static system instructions, tool schemas, or few-shot examples invalidates cached prefixes on every request. Place immutable rules and tool definitions first and append dynamic evidence and user turns last.

## 3. Design a Multi-Layer Eval Suite

Good evals run cheap, deterministic checks first and reserve slower LLM-as-judge calls for nuances that rules cannot capture.

| Layer | What it checks | Concrete example |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **Golden set** | Representative labeled inputs, including held-out and noisy cases | 100 support queries with expected policy IDs and unanswerable and refusal cases |
| **Rule checks** | Fast, deterministic code assertions | Valid JSON schema, required citation IDs present, payload under byte cap |
| **Model-graded** | An LLM judge scoring against an explicit rubric | Groundedness 0–5: is every claim directly supported by the retrieved text? |
| **CI gate** | Automated run on every prompt, model, or retrieval change | Fast subset on PRs; full suite nightly, blocking merges on regression |

Watch out for two classic interview traps:

- **"Are LLM judges objective?"** No. Judges drift, favor longer answers, and carry biases toward their own model family. Give the judge a narrow rubric, pass it the supporting evidence, and regularly compare its scores against human-labeled samples.
- **"Which single metric matters most?"** None in isolation. Ship decisions pair **task failure rate by category** (extraction, citation, refusal) with **cost per request** and **p95 latency** — not legacy text-overlap scores like BLEU.

## 4. Turn Eval Results Into a Release Decision

To make an eval run tell you *what* caused a regression, lock down your experiment hygiene:

- **Keep a held-out test set** that engineers do not tune against directly, and include adversarial, refusal, and unanswerable inputs alongside happy paths.
- **Version every moving part** on each run: prompt version, model and deployment snapshot, retrieval and index version, and decoding parameters (such as temperature).
- **Change one variable at a time** when you need to attribute a delta. If a new model requires a prompt rewrite at the same time, evaluate the combinations explicitly so you know which change helped.
- **Protect user privacy in eval traces.** Only store traces allowed by your data retention and access policy; strip or anonymize personal data before building shared golden sets.

## Code Examples

The first helper (`checkAnswer`) and the prompt registry (`PROMPTS`) are self-contained. The context assembly and eval-harness snippets illustrate production boundaries using injected tokenizer, schema, and judge adapters.

### One deterministic evaluation trace

A structural check can prove that a response is valid JSON and only cites permitted document IDs, but it **cannot** prove that the cited document actually supports the claim. Keeping that boundary explicit prevents false confidence:

```javascript
export function checkAnswer(raw, authorizedSources) {
  // Cap raw size before JSON.parse so an oversized reply cannot exhaust CPU/memory.
  if (typeof raw !== 'string' || raw.length > 32_768 ||
      new TextEncoder().encode(raw).byteLength > 32_768) return ['response size or type'];
  let value;
  try { value = JSON.parse(raw); } catch { return ['not JSON']; }
  if (!value || typeof value !== 'object' || Array.isArray(value) ||
      typeof value.answer !== 'string' || value.answer.length > 4000 ||
      !Array.isArray(value.sources) || value.sources.length > 20 ||
      value.sources.some(id => typeof id !== 'string')) return ['schema'];
  const missing = value.sources.filter(id => !authorizedSources.has(id));
  return missing.length ? ['unauthorized or invented source'] : [];
}
```

Walk through three cases:
- `{"answer":"Returns take seven days.","sources":["policy-4"]}` passes only if `policy-4` is in `authorizedSources`.
- Citing an invented ID like `"policy-99"` fails immediately with `['unauthorized or invented source']`.
- A fabricated claim paired with a real ID (`"policy-4"`) still passes `checkAnswer` — your separate claim-support grader must catch it. Report structural pass rate and claim-support pass rate separately. Also enforce byte limits at the HTTP and provider streaming layer so huge responses are stopped before they are buffered in memory.

### 1. Version prompts in a typed registry

Logging `${id}@${version}` on every inference call lets you trace any production spike back to an exact git commit (note that versioning identifies the input artifact; model outputs remain stochastic).

```typescript
export const PROMPTS = {
  "clin-suggest": {
    version: 7,
    system: "You assist clinicians with suggestions. You never diagnose.",
    rules: [
      "Cite every claim with a <doc id> from the CONTEXT.",
      "Refuse when the context is insufficient.",
      "Reply with JSON matching the supplied schema.",
    ],
  },
} as const;

type PromptId = keyof typeof PROMPTS;
export const load = (id: PromptId) => PROMPTS[id];
// Log `${id}@${version}` on every call (e.g. "clin-suggest@7") — never an unversioned string.
```

### 2. Enforce a hard context budget before dispatch

Count the full serialized request, drop the lowest-ranked chunks until input plus reserved output fits, and fail loudly if required evidence cannot fit.

```typescript
const WINDOW = configuredModelContextWindow; // model/version-specific
const OUTPUT_RESERVE = configuredOutputAndReasoningReserve; // includes output + reasoning budget

async function assemble(question: string, chunks: RetrievedChunk[], history: Turn[]) {
  const { system, rules } = load("clin-suggest");
  const summary = await rollingSummary(history); // verify summaries keep required facts
  const kept = [...chunks];                      // ordered highest-ranked first
  const request = () => ({ system, rules, summary, question, tools, outputSchema, chunks: kept });
  let inputTokens = countSerializedRequestTokens(request());

  while (inputTokens + OUTPUT_RESERVE > WINDOW && kept.length > 0) {
    kept.pop();                                  // drop lowest-ranked chunk, then recount whole request
    inputTokens = countSerializedRequestTokens(request());
  }

  if (kept.length === 0 || inputTokens + OUTPUT_RESERVE > WINDOW) {
    throw new Error("required context does not fit — refuse or use an approved fallback");
  }
  return { system, rules, summary, kept, question, inputTokens, outputReserve: OUTPUT_RESERVE };
}
```

### 3. Run deterministic rules before model-graded checks

Notice how refusal checks use a dedicated task-specific grader rather than searching for the word `"cannot"` — a model can write *"I cannot officially advise you, however here is how to do it..."* and still violate policy.

```typescript
type EvalCase = {
  id: string;
  input: string;
  expect: {
    schema?: ZodTypeAny;      // structured-output contract
    mustInclude?: string[];   // e.g. a required citation marker
    mustRefuse?: boolean;     // unsafe or unanswerable input
    judgeRubric?: string;     // groundedness 0–5, evaluated against retrieved evidence
  };
};

async function runCase(c: EvalCase, run: (input: string) => Promise<string>) {
  const out = await run(c.input);
  const fails: string[] = [];

  if (c.expect.mustRefuse) {
    const verdict = await evaluateRefusal(c.input, out); // human-calibrated refusal grader
    if (!verdict.refused || verdict.containsForbiddenAssistance) fails.push("expected refusal");
    return { id: c.id, fails };
  }

  if (c.expect.schema) {
    let parsed: unknown;
    try {
      parsed = JSON.parse(out);
    } catch {
      fails.push("not JSON");
      return { id: c.id, fails };
    }
    if (!c.expect.schema.safeParse(parsed).success) fails.push("schema");
  }

  for (const needle of c.expect.mustInclude ?? []) {
    if (!out.includes(needle)) fails.push(`missing ${needle}`);
  }

  if (c.expect.judgeRubric) {
    const score = await judge({
      rubric: c.expect.judgeRubric,
      input: c.input,
      output: out,
      evidence: evalEvidenceFor(c.id),
    });
    if (!Number.isFinite(score) || score < 0 || score > 5) fails.push("invalid judge score");
    else if (score < 4) fails.push(`judge ${score}/5`);
  }
  return { id: c.id, fails };
}
```

### 4. Wire a CI regression gate

Keep in-flight concurrency bounded so your eval suite does not trip provider rate limits, and pair pass-rate gates with separate cost and latency checks.

```typescript
const THRESHOLDS = { passRate: 0.95 }; // illustrative quality bar; track cost/latency separately

const results = [];
for (const c of goldenSet) results.push(await runCase(c, runFeature));
// Sequential loop bounds concurrency; scale larger suites with a bounded worker pool.
if (results.length === 0) throw new Error("empty eval set");
const passRate = results.filter((r) => r.fails.length === 0).length / results.length;

if (passRate < THRESHOLDS.passRate) {
  throw new Error(`eval regression: passRate ${passRate.toFixed(3)} < ${THRESHOLDS.passRate}`);
}
// Hold the model fixed to isolate a prompt change; when both change, test combinations explicitly.
```

### 5. Calibrate your LLM judge against humans

Before trusting a model judge to gate releases, measure how often it agrees with human reviewers on a labeled sample:

```typescript
if (humanLabels.length === 0 || humanLabels.length !== judgeScores.length ||
    [...humanLabels, ...judgeScores].some(s => !Number.isFinite(s))) {
  throw new Error("invalid calibration samples");
}
const agree = humanLabels.filter((h, i) => Math.abs(h - judgeScores[i]) <= 1).length
  / humanLabels.length;
if (agree < 0.8) {
  console.warn(`judge agreement ${(agree * 100).toFixed(0)}% — tighten the rubric`);
}
```

## Real-World Use Cases

| Scenario | Approach |
| -------------------------------------- | ------------------------------------------------------------------------------- |
| Clinical suggestions must cite sources | RAG + citation-membership check + claim-support eval; refuse when no chunk fits |
| Support bot tone consistency | Few-shot examples versioned in git alongside product-copy updates |
| Extraction across messy invoices | Schema-validated JSON output + calibrated review routing for low-certainty rows |

## Summary

Treat prompts and context assembly as versioned code backed by automated evidence. Count the full serialized request including framing and reserved output tokens, enforce raw byte caps before parsing JSON, run fast deterministic checks before calibrated LLM-as-judge rubrics, and track quality by category separately from latency and spend.

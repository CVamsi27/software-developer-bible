# Prompts, Context & Evals

When a model update makes a support assistant less reliable, the prompt may not be the cause: the model, retrieved evidence, context order, or output contract may have changed too. Treat the whole request as a versioned input and use evaluations to locate the regression.

---

## Definition

- **Prompt engineering:** structuring instructions, examples, and constraints for reliable model behavior.
- **Context engineering:** deciding *what* enters the limited window — retrieval, compression, history strategy.
- **Evals:** automated scoring of outputs against expectations; the regression suite of AI features.

> **Textbook Definition:** Prompt engineering specifies instructions to a model; context engineering selects the information supplied for inference; evaluation measures observed behavior against a defined task and dataset. Evaluation results characterize the tested conditions rather than guarantee future outputs.

## First Principles

Prompt/context/eval engineering treats the prompt as a versioned input contract for a probabilistic component. The application controls what information and constraints it supplies; it measures behavior rather than assuming that a prompt guarantees it.

1. **Prompts are code — versioned, tested, reviewed.** A prompt change is a behavior change with no compiler to catch regressions; hence prompts in git, changes via PR, and *evals as behavioral evidence*: datasets of inputs with expected behaviors, run on every prompt/model change.
2. **Context is the scarce resource; relevance is the design goal.** The window fills with history + retrieval + instructions that compete for attention — the engineering is *selecting and compressing* what earns a slot (→ 20.12.03). More context need not improve an answer; evaluate placement, relevance and truncation on the chosen model.
3. **Evals measure what users experience.** LLM-as-judge, golden sets, and regression suites approximate quality because "it seems better" is not a deployment criterion — the same evidence-over-vibes discipline as perf testing (→ 50.4), applied to a non-deterministic system.

## Build the request you intend to evaluate

### Prompt anatomy that survives review

One useful prompt layout is role and scope, task instructions, clearly delimited context, and an output contract. It is a starting point, not a universal ordering rule: test instruction placement and examples with the selected model and task.

Techniques worth naming in interviews: zero-shot vs **few-shot** examples, task decomposition and concise verifiable intermediate artifacts (reasoning-model prompting is model-specific), **self-consistency** (sample N, majority), **decomposition** (multi-step pipelines over one mega-prompt).

### Context-window budgeting

Budget the complete serialized request: instructions, tool definitions, schemas, retrieved text, history, message framing, and reserved output. Growing history eventually exceeds a model's usable context, so select, summarize, or reject it under an explicit policy; validate that summaries preserve required facts and pending tool-call/result pairs. Some model/task evaluations find a positional effect often called "lost in the middle"; its size and mitigation depend on the model and task, so measure placement rather than assuming that first or last is always best. Also test stale indexes after document updates and reject silent truncation.

### Evaluation needs a representative contract

| Layer | What | Example |
| ---------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Golden set** | A representative labeled set, with held-out cases and repeated noisy comparisons | clinical suggestion cases with known ICD codes |
| **Rule checks** | Deterministic assertions | valid JSON schema · required citations present · refusal phrases on unsafe input |
| **Model-graded** | LLM-as-judge with rubric | groundedness 0–5 against retrieved chunks |
| **CI gate** | Run on prompt/model change; block on regression | nightly job + PR check |

 *Traps:* "LLM judges are objective?" (no — rubric them, spot-check judge agreement, keep humans in the loop for high-stakes sets). "Which metric matters most?" (task failure rate on golden set + cost/latency SLOs — not BLEU-style magic numbers).

## Code Examples

The registry is self-contained; the context and model-grade sketches require adapters for request tokenization, history, schema validation and calibrated grading. Count source markers/framing as well as chunk text, then recount the complete selected request before dispatch. Counts and output/reasoning reserves are model-specific.

### One deterministic evaluation trace

A valid source id proves membership, not that it supports a claim. This executable JavaScript check makes that narrower contract explicit. A separate evidence grader must assess claim support and refusal safety.

```javascript
export function checkAnswer(raw, authorizedSources) {
  const maxResponseBytes = 16_384; // illustrative cap; derive it from this feature's output contract
  if (new TextEncoder().encode(raw).byteLength > maxResponseBytes) return ['output too large'];
  let value;
  try { value = JSON.parse(raw); } catch { return ['not JSON']; }
  if (!value || typeof value !== 'object' || Array.isArray(value) ||
      typeof value.answer !== 'string' || value.answer.length > 4000 ||
      !Array.isArray(value.sources) || value.sources.length > 20 ||
      value.sources.some(id => typeof id !== 'string')) return ['schema'];
  const missing = value.sources.filter(id => !authorizedSources.has(id));
  return missing.length ? ['unauthorized or invented source'] : [];
}
```

`{"answer":"Returns take seven days.","sources":["policy-4"]}` passes only if `policy-4` is in the permitted set. An invented id fails. A plausible false sentence with a permitted id still passes this structural check; the support grader must reject it. Report these measurements separately.


**1. Prompts are code: one registry, versioned by id.** The version string identifies the prompt artifact used; it does not make a stochastic output reproducible by itself.

```typescript
export const PROMPTS = {
  "clin-suggest": {
    version: 7,
    system: "You assist clinicians with suggestions. You never diagnose.",
    rules: [
      "Cite every claim with a <doc id> from the CONTEXT.",
      "Refuse when the context is insufficient.",
      "Reply with JSON matching the supplied schema.",
    ],
  },
} as const;

type PromptId = keyof typeof PROMPTS;
export const load = (id: PromptId) => PROMPTS[id];
// Log `${id}@${version}` on every call (e.g. "clin-suggest@7") — never a bare prompt.
```

**2. Context is a budget, not a bucket.** Count before you send, drop the least valuable chunks, and assert rather than truncate silently.

```typescript
const WINDOW = configuredModelContextWindow; // model/version-specific
const OUTPUT_RESERVE = configuredOutputAndReasoningReserve; // model/provider-specific

async function assemble(question: string, chunks: RetrievedChunk[], history: Turn[]) {
  const { system, rules } = load("clin-suggest");
  const summary = await rollingSummary(history); // validate summaries against required facts
  const kept = [...chunks];                      // retrieval order is highest-ranked first
  const request = () => ({ system, rules, summary, question, tools, outputSchema, chunks: kept });
  let inputTokens = countSerializedRequestTokens(request());
  // Count the complete final request; token counts are not additive across fields.
  while (inputTokens + OUTPUT_RESERVE > WINDOW && kept.length > 0) {
    kept.pop();                                  // remove the lowest-ranked chunk, then recount
    inputTokens = countSerializedRequestTokens(request());
  }

  if (kept.length === 0 || inputTokens + OUTPUT_RESERVE > WINDOW) {
    throw new Error("required context does not fit — refuse or use an approved fallback");
  }
  return { system, rules, summary, kept, question, inputTokens, outputReserve: OUTPUT_RESERVE };
}
```

The token counter must match the selected model/provider's request format. The reserve includes the expected output and any provider-specific reasoning allowance; it is not a universal constant.

**3. The harness: deterministic checks first (cheap, explainable), a judge second.** Rule checks catch measurable format/contract violations, so the model call is reserved for what rules cannot express.

```typescript
type EvalCase = {
  id: string;
  input: string;
  expect: {
    schema?: ZodTypeAny;      // structured-output contract
    mustInclude?: string[];   // e.g. a citation marker that must appear
    mustRefuse?: boolean;     // unsafe / unanswerable input
    judgeRubric?: string;     // groundedness 0–5, judged separately
  };
};

async function runCase(c: EvalCase, run: (input: string) => Promise<string>) {
  const out = await run(c.input);
  const fails: string[] = [];

  if (c.expect.mustRefuse) {
    const verdict = await evaluateRefusal(c.input, out); // task-specific human-calibrated grader
    if (!verdict.refused || verdict.containsForbiddenAssistance) fails.push("expected refusal");
    return { id: c.id, fails };
  }

  if (c.expect.schema) {
    let parsed: unknown;
    try {
      parsed = JSON.parse(out);                       // free text is not an output format
    } catch {
      fails.push("not JSON");
      return { id: c.id, fails };
    }
    if (!c.expect.schema.safeParse(parsed).success) fails.push("schema");
  }

  for (const needle of c.expect.mustInclude ?? []) {
    if (!out.includes(needle)) fails.push(`missing ${needle}`);
  }

  if (c.expect.judgeRubric) {
    const score = await judge({ rubric: c.expect.judgeRubric, input: c.input, output: out,
      evidence: evalEvidenceFor(c.id) }); // groundedness requires the supporting context
    if (!Number.isFinite(score) || score < 0 || score > 5) fails.push("invalid judge score");
    else if (score < 4) fails.push(`judge ${score}/5`);
  }
  return { id: c.id, fails };
}
```

**4. The CI gate: fail on regression, and change one variable at a time** so the delta is attributable.

```typescript
const THRESHOLDS = { passRate: 0.95 }; // illustrative quality threshold, not a cost/latency gate

const results = [];
for (const c of goldenSet) results.push(await runCase(c, runFeature));
// Sequential here bounds in-flight model calls; larger runs need a bounded worker pool.
if (results.length === 0) throw new Error("empty eval set");
const passRate = results.filter((r) => r.fails.length === 0).length / results.length;

if (passRate < THRESHOLDS.passRate) {
  throw new Error(`eval regression: passRate ${passRate.toFixed(3)} < ${THRESHOLDS.passRate}`);
}
// Hold the model constant to attribute a prompt delta; if both must change,
// evaluate the relevant combinations so the effect is not confounded.
```

**5. A judge is a model too — calibrate it before you trust it.** The cheapest way to catch a judge that has drifted into rewarding verbosity.

```typescript
if (humanLabels.length === 0 || humanLabels.length !== judgeScores.length ||
    [...humanLabels, ...judgeScores].some(s => !Number.isFinite(s) || s < 0 || s > 5)) {
  throw new Error("invalid calibration samples");
}
const agree = humanLabels.filter((h, i) => Math.abs(h - judgeScores[i]) <= 1).length
  / humanLabels.length;
if (agree < 0.8) {
  console.warn(`judge agreement ${(agree * 100).toFixed(0)}% — tighten the rubric`);
}
```

## Real-World Use Cases

| Scenario | Approach |
| -------------------------------------- | ------------------------------------------------------------------------------ |
| Clinical suggestions must cite sources | RAG + citation-required rule check in evals; refuse when no supporting chunk |
| Support bot tone consistency | Few-shot exemplars versioned alongside product copy changes |
| Extraction across messy invoices | Schema-validated structured output + confidence threshold → human review queue |

## Turn results into a release decision

Keep a representative held-out set; include adversarial, refusal, and unanswerable cases. On a change, record the prompt, model/deployment, retrieval/index, and decoding versions, then compare quality by task category alongside cost and latency. Change one factor at a time when you need causal attribution; when several must change together, evaluate the relevant combinations. Calibrate model-graded scores against human labels and report their disagreement rather than presenting a judge score as objective truth. Store only traces permitted by the feature's access and retention policy.

## Summary

A prompt change needs a versioned testable contract. Count the serialized request, evaluate refusal and grounding against actual inputs/evidence, and report uncertainty and cost/latency separately from a quality pass rate.

# Prompts, Context & Evals


---

## Definition

- **Prompt engineering:** structuring instructions, examples, and constraints for reliable model behavior.
- **Context engineering:** deciding *what* enters the limited window — retrieval, compression, history strategy.
- **Evals:** automated scoring of outputs against expectations; the regression suite of AI features.

## First Principles

Prompt/context/eval engineering follows from one fact: the prompt is a program you can only steer probabilistically.

1. **Prompts are code — versioned, tested, reviewed.** A prompt change is a behavior change with no compiler to catch regressions; hence prompts in git, changes via PR, and *evals as the type system*: datasets of inputs with expected behaviors, run on every prompt/model change.
2. **Context is the scarce resource; relevance is the design goal.** The window fills with history + retrieval + instructions that compete for attention — the engineering is *selecting and compressing* what earns a slot (→ 20.12.03). More context ≠ better; misplaced context actively degrades output.
3. **Evals measure what users experience.** LLM-as-judge, golden sets, and regression suites approximate quality because "it seems better" is not a deployment criterion — the same evidence-over-vibes discipline as perf testing (→ 50.4), applied to a non-deterministic system.

## Why Do We Need It?

Prompts rot: models update, usage drifts, edge cases accumulate. Teams without evals ship regressions silently and argue about quality anecdotally. Evals convert "the bot feels dumber" into a number on a dashboard.

## How It Works

### Prompt anatomy that survives review

```text
1. ROLE who the model is + scope limits ("You assist clinicians. Never diagnose.")
2. RULES hard constraints (format, refusals, safety) — short, numbered
3. CONTEXT retrieved chunks / user data — clearly delimited
4. TASK the actual ask
5. FORMAT output schema or few-shot example(s)
```

Techniques worth naming in interviews: zero-shot vs **few-shot** examples, task decomposition and concise verifiable intermediate artifacts (reasoning-model prompting is model-specific), **self-consistency** (sample N, majority), **decomposition** (multi-step pipelines over one mega-prompt).

### Context-window budgeting

```text
[ system + rules ] small, stable, cached if provider supports it
[ retrieved knowledge ] biggest variable — retrieve less, compress more
[ conversation state ] rolling summary + last-N turns (never full history forever)
[ task + format ] precise, at the end (recency helps)
```

Traps: "lost in the middle" (models under-use mid-context facts → put critical context first/last); stale embeddings after doc updates (re-index pipeline!); silent truncation (assert token counts server-side).

### Evals — the minimum credible setup

| Layer | What | Example |
| ---------------- | --------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Golden set** | 50–200 real (input, expected) pairs from production | clinical suggestion cases with known ICD codes |
| **Rule checks** | Deterministic assertions | valid JSON schema · required citations present · refusal phrases on unsafe input |
| **Model-graded** | LLM-as-judge with rubric | groundedness 0–5 against retrieved chunks |
| **CI gate** | Run on prompt/model change; block on regression | nightly job + PR check |

```typescript
type EvalCase = { input: string; expect: { mustInclude: string[]; schema?: ZodSchema; refuse?: boolean } };
// score = passed/total per category; alert when any drops below threshold
```

 *Traps:* "LLM judges are objective?" (no — rubric them, spot-check judge agreement, keep humans in the loop for high-stakes sets). "Which metric matters most?" (task failure rate on golden set + cost/latency SLOs — not BLEU-style magic numbers).

## Code Examples

**1. Prompts are code: one registry, versioned by id.** The version string identifies the prompt artifact used; it does not make a stochastic output reproducible by itself.

```typescript
export const PROMPTS = {
  "clin-suggest": {
    version: 7,
    system: "You assist clinicians with suggestions. You never diagnose.",
    rules: [
      "Cite every claim with a <doc id> from the CONTEXT.",
      "Refuse when the context is insufficient.",
      "Reply with JSON matching the supplied schema.",
    ],
  },
} as const;

type PromptId = keyof typeof PROMPTS;
export const load = (id: PromptId) => PROMPTS[id];
// Log `${id}@${version}` on every call (e.g. "clin-suggest@7") — never a bare prompt.
```

**2. Context is a budget, not a bucket.** Count before you send, drop the least valuable chunks, and assert rather than truncate silently.

```typescript
const WINDOW = configuredModelContextWindow; // model/version-specific
const RESERVE = 4_000;   // headroom for the answer itself

async function assemble(question: string, chunks: RetrievedChunk[], history: Turn[]) {
  const { system, rules } = load("clin-suggest");
  const summary = await rollingSummary(history);        // compress old turns once
  let tokens = countSerializedRequestTokens({ system, rules, summary, question, tools, outputSchema });
  // Include message framing, tool definitions, schema, and model-specific overhead.

  const kept: RetrievedChunk[] = [];
  for (const c of chunks) {                             // highest-ranked first
    const t = countTokens(c.text);
    if (tokens + t > WINDOW - RESERVE) continue;
    tokens += t;
    kept.push(c);
  }

  // Nothing fit → refuse. Sending an empty context invites a confident hallucination.
  if (kept.length === 0) throw new Error("no context fits — refuse instead of guessing");
  if (tokens > WINDOW - RESERVE) throw new Error("context overflow");   // never silent
  return { system, rules, summary, kept, question, tokens };
}
```

**3. The harness: deterministic checks first (cheap, explainable), a judge second.** Rule checks catch most regressions for free, so the model call is reserved for what rules cannot express.

```typescript
type EvalCase = {
  id: string;
  input: string;
  expect: {
    schema?: ZodTypeAny;      // structured-output contract
    mustInclude?: string[];   // e.g. a citation marker that must appear
    mustRefuse?: boolean;     // unsafe / unanswerable input
    judgeRubric?: string;     // groundedness 0–5, judged separately
  };
};

async function runCase(c: EvalCase, run: (input: string) => Promise<string>) {
  const out = await run(c.input);
  const fails: string[] = [];

  if (c.expect.mustRefuse) {
    const verdict = await evaluateRefusal(c.input, out); // task-specific human-calibrated grader
    if (!verdict.refused || verdict.containsForbiddenAssistance) fails.push("expected refusal");
    return { id: c.id, fails };
  }

  if (c.expect.schema) {
    let parsed: unknown;
    try {
      parsed = JSON.parse(out);                       // free text is not an output format
    } catch {
      fails.push("not JSON");
      return { id: c.id, fails };
    }
    if (!c.expect.schema.safeParse(parsed).success) fails.push("schema");
  }

  for (const needle of c.expect.mustInclude ?? []) {
    if (!out.includes(needle)) fails.push(`missing ${needle}`);
  }

  if (c.expect.judgeRubric) {
    const score = await judge({ rubric: c.expect.judgeRubric, input: c.input, output: out,
      evidence: evalEvidenceFor(c.id) }); // groundedness requires the supporting context
    if (score < 4) fails.push(`judge ${score}/5`);
  }
  return { id: c.id, fails };
}
```

**4. The CI gate: fail on regression, and change one variable at a time** so the delta is attributable.

```typescript
const THRESHOLDS = { passRate: 0.95 }; // illustrative quality threshold, not a cost/latency gate

const results = await Promise.all(goldenSet.map((c) => runCase(c, runFeature)));
if (results.length === 0) throw new Error("empty eval set");
const passRate = results.filter((r) => r.fails.length === 0).length / results.length;

if (passRate < THRESHOLDS.passRate) {
  throw new Error(`eval regression: passRate ${passRate.toFixed(3)} < ${THRESHOLDS.passRate}`);
}
// Pin the model version when changing a prompt (and vice versa) — otherwise a
// simultaneous swap makes the score delta uninterpretable.
```

**5. A judge is a model too — calibrate it before you trust it.** The cheapest way to catch a judge that has drifted into rewarding verbosity.

```typescript
const agree = humanLabels.filter((h, i) => Math.abs(h - judgeScores[i]) <= 1).length
  / humanLabels.length;
if (agree < 0.8) {
  console.warn(`judge agreement ${(agree * 100).toFixed(0)}% — tighten the rubric`);
}
```

## Real-World Use Cases

| Scenario | Approach |
| -------------------------------------- | ------------------------------------------------------------------------------ |
| Clinical suggestions must cite sources | RAG + citation-required rule check in evals; refuse when no supporting chunk |
| Support bot tone consistency | Few-shot exemplars versioned alongside product copy changes |
| Extraction across messy invoices | Schema-validated structured output + confidence threshold → human review queue |

## Common Mistakes

- Prompt sprawl: dozens of near-duplicate prompts with no owner — consolidate into a registry.
- Testing only happy paths: include adversarial/PII/refusal cases in the golden set.
- Changing model and prompt simultaneously — never; evals can't attribute the delta.
- Ignoring cost regression: a "better" answer that triples tokens fails the budget gate.

## Best Practices

- Prompts live in code, reviewed via PR, tagged by feature.
- Every production AI feature has: golden set ≥ 50 cases, CI eval job, cost+latency dashboards.
- Log prompt/model versions, source revisions, decoding settings, and completion IDs for auditability; keep traces under a deliberate privacy/retention policy.

## Summary

A prompt change needs a versioned testable contract. Count the serialized request, evaluate refusal and grounding against actual inputs/evidence, and report uncertainty and cost/latency separately from a quality pass rate.

# Retrieval Quality — Hybrid Search & Reranking

A user asks your support bot: *"Why did invoice `INV-2026-00317` fail?"* Pure vector search returns five generic billing articles and misses the one ticket mentioning `INV-2026-00317`. Another user asks *"Can I get my money back if a package arrives late?"* — pure keyword search misses a policy titled *"Delayed Shipment Refunds"* because the words don't overlap.

Your language model can only answer as well as the evidence you put in its prompt. Combining keyword and vector retrieval — and optionally reranking the shortlist — fixes both failure modes, provided you measure whether the right passage actually reaches the top of the list.

---

## Definition

A modern retrieval pipeline works in two stages: first gather a broad candidate shortlist cheaply, then order the best passages to the top.

- **Lexical (keyword) search** matches exact words and identifiers, typically via **full-text search (FTS)** or **BM25** (a scoring formula that rewards matching rare terms while normalizing for document length).
- **Dense-vector (semantic) search** turns queries and passages into numeric embeddings so paraphrases land close together. To search millions of vectors quickly, indexes use **ANN (approximate nearest-neighbor)** structures like **HNSW** (a multi-layer proximity graph) that trade a small amount of exactness for speed.
- **Hybrid search** runs both lexical and semantic retrieval in parallel and merges their ranked lists.
- **Reranking** passes the top candidates through a heavier scoring model that reads the query and each passage together to refine the final order.

> **Textbook Definition:** Hybrid retrieval combines rankings from lexical and semantic indexes to form candidate results; reranking then estimates query-document relevance over those candidates. Reranking cannot recover a relevant document excluded by retrieval.

```text
                query
                  │
         ┌────────┴────────┐
         ▼                 ▼
   lexical FTS        vector ANN (pgvector/HNSW)
   ranked list        ranked list
         └────────┬────────┘
                  ▼
   Reciprocal Rank Fusion → bounded candidate shortlist
                  ▼
   cross-encoder reranker (e.g. cohere-rerank / bge-reranker)
                  ▼
      top 5–8 chunks → LLM context
```

## First Principles

Three underlying truths explain why production RAG systems rarely stop at plain cosine similarity:

1. **Semantic similarity is not exactness.** Embeddings blur rare strings like `Error E-402` into general "error handling" neighborhoods. Keyword search nails exact IDs and acronyms; vector search nails paraphrases. Running both covers each channel's blind spot (→ 20.4.5.05).
2. **Recall and precision need different budgets.** Scanning 100,000 chunks has to be fast (cheap bi-encoder vectors and inverted indexes). Once you narrow that down to 30–50 candidates, you can afford a slower, more accurate cross-encoder reranker to pick the best 5–8. Two-stage retrieval follows the same cheap-filter-then-precise-work shape as caching (→ 20.8.01).
3. **Chunking determines what is even findable.** Embed a 20-page PDF as one vector and its meaning averages out into mush. Chop it into 50-word fragments and each piece loses surrounding context ("it applies only to EU accounts" — *what* applies?). Chunk boundaries are an information-design decision, not an arbitrary character count.

## 1. Match the Retrieval Channel to the Query Failure Mode

Before tuning weights, inspect which real user queries fail today:

| Query failure mode | Concrete example | What fixes it |
| ------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| Exact identifiers | invoice `INV-2026-00317` | Exact-match filter or lexical analyzer on identifier fields |
| Acronyms and jargon | "K8s PSP deprecation" vs verbose docs | Lexical term matching with inverse document frequency (IDF) |
| Rare proper nouns | customer name "Ondrej Spanel" | BM25; embeddings drift toward more common names |
| Negation | "not covered by warranty" | Evaluate a cross-encoder reranker on negation cases explicitly |
| Internal codenames | internal project or SKU names | Lexical channel + curated synonym map + reranker |

A practical rule of thumb: if a human would press `Ctrl+F` to locate the answer, make sure your pipeline has a lexical path.

## 2. Merge Rankings with Reciprocal Rank Fusion (RRF)

BM25 scores (unbounded positive numbers) and cosine similarities (`-1` to `1`) live on incompatible scales, so adding their raw scores directly breaks whenever one channel shifts range. **Reciprocal Rank Fusion (RRF)** avoids score normalization completely by combining only each document's *rank position*:

```text
RRF(d) = Σ  1 / (k + rank_i(d))       (k is a smoothing constant, commonly 60)

Example (k = 60):
  doc A: lexical rank 1, vector rank 12  → 1/61 + 1/72 = 0.0303
  doc B: lexical rank 5, vector rank 2   → 1/65 + 1/62 = 0.0315  ← B wins fusion
  doc C: vector rank 1 only              → 1/61        = 0.0164
```

Documents that show up strongly in *both* channels rise above documents that only spike in one. When one channel is empirically stronger for your corpus, you can use **weighted RRF** (`α/(k + lexicalRank) + (1 − α)/(k + semanticRank)`, omitting absent channels), or calibrated linear score fusion if you control both scorers.

## 3. Why Rerankers Work: Bi-Encoder vs Cross-Encoder

Why not use the reranker for everything? Because the two model architectures compute relevance in fundamentally different ways:

```text
BI-ENCODER (first-stage retrieval)       CROSS-ENCODER (second-stage rerank)
  q → vec(q)   d → vec(d)                  [q ⊕ d] → transformer → relevance score
  document vectors precomputed offline     full attention across query + doc tokens
  fast ANN lookup per query                one forward pass per candidate: O(N)
  lossy single-vector compression          sees negation, exact phrase & nuance
```

A bi-encoder embeds every document *once* at ingest time so query latency stays tiny, but compressing a whole paragraph into one vector throws away fine token interactions. A cross-encoder reads the query and candidate together at query time — far sharper, but only affordable on a small shortlist (say 20–50 candidates).

Choose a hosted or self-hosted reranker by measuring its quality, language coverage, data-handling terms, latency, and total cost on your own queries. Pin the model version and record its batch and token limits explicitly.

## 4. Choose Your ANN Index: HNSW vs IVF

When your vector table outgrows exact linear scans, you pick an approximate nearest-neighbor index:

| Property | HNSW (hierarchical graph) | IVF (inverted file clusters) |
| -------------------- | --------------------------------------------------------------- | ----------------------------------------------- |
| Query speed | Fast approximate graph walk; tune `ef_search` | Probes a subset of clusters (`probes` dial) |
| Recall | High at moderate query latency | Tunable recall-vs-QPS trade-off |
| Build & updates | Slower build; handles incremental inserts well | Faster initial build; needs retraining on drift |
| Memory footprint | Higher (multi-layer neighbor graph in RAM) | Lower (centroids + posting lists) |
| Filtered search | Selective filters can starve candidate recall; inspect plans | Post-filtering can leave empty result sets |
| Common homes | `pgvector` (`hnsw`), Qdrant, Weaviate, Pinecone | FAISS classic, `pgvector` (`ivfflat`) |

**Filtered-search watch-out in `pgvector`:** when you combine `WHERE tenant_id = $1` with an approximate `ORDER BY embedding <=> $2 LIMIT 20`, an ANN index may inspect its top neighbors and discard most of them for belonging to other tenants — returning fewer than 20 rows or missing closer matches. Always run `EXPLAIN ANALYZE` and measure **filtered recall**; use iterative scans (`hnsw.iterative_scan`), partitioning by tenant, partial indexes, or exact scans for small tenant subsets when needed.

**Vector quantization trade-off:** storing `pgvector` embeddings as 16-bit `halfvec` roughly halves index and memory footprint with minimal recall loss on high-dimensional models, whereas binary quantization (`bit` vectors) shrinks storage 32× but loses ranking nuance unless you oversample a larger candidate shortlist and rescore candidates against full-precision (`float32` or `halfvec`) vectors.

## 5. How Chunking Shapes Recall

Test chunking strategies against labeled queries rather than guessing:

- **Fixed-size with overlap:** simple baseline; tune chunk size and overlap for your tokenizer and document layout.
- **Structure-aware:** split on headings, paragraphs, tables, or code AST boundaries so logical units stay intact.
- **Parent–child (small-to-big):** embed small, focused child chunks for sharp retrieval, then pass the larger parent section to the LLM so it has surrounding context.
- **Contextual enrichment:** prepend a short situating header before embedding (e.g., *"From Refunds Manual §3.2 — EU Return Windows:"*) so pronoun-heavy paragraphs make sense on their own.

Remember that chunk size interacts with `k`: smaller chunks require a higher `k` to cover the same context. Measure `recall@k` per chunking policy in your eval harness.

## 6. Measure Each Stage Separately

Never judge retrieval solely by reading final LLM answers — an eloquent model can hide missing evidence by guessing, or fumble a great retrieval result. Measure retrieval directly on a labeled golden set:

```text
recall@k  = |relevant ∩ top-k| / |relevant|      (did the right chunk appear in top k?)
MRR       = mean(1 / rank_of_first_hit)           (how high did the first right chunk land?)
nDCG@k                                            (graded relevance when order across top k matters)
```

Evaluate three checkpoints on every corpus, chunker, embedding, or index change:
1. **Pre-rerank candidate recall** — if the right document is missing here, no reranker can invent it.
2. **Post-rerank `recall@k` and `MRR`** — confirms the reranker actually earns its latency and cost.
3. **End-to-end claim support** — confirms the LLM cites and follows the retrieved passages (→ 20.12.02).

Include exact IDs, paraphrases, negations, unanswerable questions, cross-tenant isolation checks, and recently updated documents. Version the corpus snapshot, chunker, embedding model, index parameters, fusion rule, and reranker together. For RAM sizing, raw float32 vectors alone take `rows × dimensions × 4` bytes before HNSW graph overhead. Plan dual-read and backfill migrations whenever you switch embedding models because vectors from different models live in incompatible spaces.

## Code Examples

### PostgreSQL + `pgvector` schema with FTS sibling column

Store a generated `tsvector` alongside the embedding column and scope every row and unique constraint by an authenticated `tenant_id`:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE documents (
  id         BIGSERIAL PRIMARY KEY,
  tenant_id  TEXT NOT NULL,                    -- derived from authenticated server context
  source_id  TEXT NOT NULL,                    -- stable external document key
  title      TEXT NOT NULL,
  content    TEXT NOT NULL,
  tsv        tsvector GENERATED ALWAYS AS (
               setweight(to_tsvector('english', title), 'A') ||
               setweight(to_tsvector('english', content), 'B')) STORED,
  embedding  vector(1536),                     -- matches configured embedding dimension
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, source_id)
);

CREATE INDEX documents_tsv_idx   ON documents USING gin(tsv);
CREATE INDEX documents_embed_idx ON documents
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

### Hybrid retrieval + RRF in one SQL round trip

Select each channel's top `LIMIT $4` candidates **first**, then assign ranks and fuse them. Putting `ORDER BY ... LIMIT` inside each candidate CTE ensures the planner selects the actual nearest neighbors (and can use the HNSW index) rather than attaching window numbers to an arbitrary subset:

```sql
WITH lexical_candidates AS (
  SELECT id, ts_rank(tsv, q) AS score
  FROM documents, websearch_to_tsquery('english', $2) q
  WHERE tenant_id = $1 AND tsv @@ q
  ORDER BY score DESC, id LIMIT $4
), semantic_candidates AS (
  SELECT id, embedding <=> $3::vector AS distance
  FROM documents WHERE tenant_id = $1 AND embedding IS NOT NULL
  ORDER BY embedding <=> $3::vector LIMIT $4
), lexical AS (
  SELECT id, row_number() OVER (ORDER BY score DESC, id) AS rank
  FROM lexical_candidates
), semantic AS (
  SELECT id, row_number() OVER (ORDER BY distance, id) AS rank
  FROM semantic_candidates
), fused AS (
  SELECT id, sum(1.0 / (60 + rank)) AS rrf FROM (
    SELECT id, rank FROM lexical UNION ALL SELECT id, rank FROM semantic
  ) s GROUP BY id
)
SELECT d.id, d.title, d.content, f.rrf
FROM fused f JOIN documents d ON d.id = f.id
WHERE d.tenant_id = $1
ORDER BY f.rrf DESC, d.id LIMIT $4;
```

Note that PostgreSQL's `ts_rank` is a built-in FTS scorer rather than full BM25; for strict BM25 inside Postgres you would add a dedicated extension, or run an external search engine. Reinforce the `tenant_id` filter with PostgreSQL Row-Level Security where appropriate, and inspect `EXPLAIN ANALYZE` on filtered queries.

### Trace fusion independently of any provider

This self-contained JavaScript function lets you verify RRF math locally with deterministic tie-breaking by `id`:

```javascript
export function fuse(channels, k = 60) {
  if (!Number.isFinite(k) || k < 0) throw new RangeError('invalid fusion constant');
  const scores = new Map();
  for (const ranked of channels) {
    const seen = new Set();
    ranked.forEach((id, index) => {
      if (typeof id !== 'string' || seen.has(id)) throw new Error('invalid ranked identity');
      seen.add(id);
      scores.set(id, (scores.get(id) ?? 0) + 1 / (k + index + 1));
    });
  }
  return [...scores].map(([id, score]) => ({ id, score }))
    .sort((a, b) => b.score - a.score || a.id.localeCompare(b.id));
}
```

With `k = 60`, doc `A` at ranks 1 and 12 scores `0.0303`, while doc `B` at ranks 5 and 2 scores `0.0315` and takes first place. Any document missing from every input channel stays absent after fusion and reranking.

### Rerank + eval harness in TypeScript (adapter sketch)

Request at least `k` final candidates when computing `recall@k` (never report `recall@10` on a list truncated to 6 items), deduplicate returned IDs, and reject cases with empty ground-truth labels instead of dividing by zero:

```typescript
// ai/retrieval.ts
type Candidate = { id: string; title: string; content: string; rrf: number };

export async function retrieve(tenantId: string, query: string): Promise<Candidate[]> {
  const embedding = await embed(query);
  const candidateLimit = configuredAndValidatedCandidateLimit; // tenantId from auth context
  const { rows } = await pool.query(hybridSql, [tenantId, query, toPgVector(embedding), candidateLimit]);
  return rows;
}

export async function rerank(query: string, cands: Candidate[], topK = configuredAndValidatedTopK) {
  const res = await rerankAdapter.rerank({
    query,
    documents: cands.map((c) => `${c.title}\n${c.content}`),
    topN: topK,
  });
  return res.results.map((r) => ({ ...cands[r.index], score: r.relevanceScore }));
}

// --- Golden-set evaluation -------------------------------------------------
type Case = { tenantId: string; q: string; relevant: Set<string> };

function recallAtK(ranked: string[], rel: Set<string>, k: number): number {
  if (!Number.isSafeInteger(k) || k < 1) throw new RangeError("invalid k");
  if (rel.size === 0) throw new Error("recall requires at least one labeled relevant item");
  return new Set(ranked.slice(0, k).filter((id) => rel.has(id))).size / rel.size;
}
function mrr(ranked: string[], rel: Set<string>): number {
  const hit = ranked.findIndex((id) => rel.has(id));
  return hit === -1 ? 0 : 1 / (hit + 1);
}

export async function evaluate(cases: Case[]) {
  if (cases.length === 0) throw new Error("empty eval set");
  let sumRecall10 = 0, sumMrr = 0;
  for (const c of cases) {
    const fused = await retrieve(c.tenantId, c.q);
    const final = await rerank(c.q, fused, 10); // toggle rerank on/off to A/B stages
    const ids = final.map((f) => f.id);
    sumRecall10 += recallAtK(ids, c.relevant, 10);
    sumMrr += mrr(ids, c.relevant);
  }
  const n = cases.length;
  return { recallAt10: sumRecall10 / n, mrr: sumMrr / n };
}
// Evaluate unanswerable-query refusal separately from answerable retrieval recall.
```

### Self-hosted reranker option (`bge-reranker`)

Pass `(query, document)` as separate paired inputs so the tokenizer formats pair boundaries properly — never manually concatenate literal `[SEP]` tokens:

```python
from sentence_transformers import CrossEncoder

model = CrossEncoder("BAAI/bge-reranker-v2-m3")
pairs = [(query, doc["text"]) for doc in documents]
scores = model.predict(pairs)
ranked = sorted(zip(documents, scores), key=lambda item: float(item[1]), reverse=True)
```

Pin the model revision and runtime, check max token truncation and multilingual quality on your queries, and bound batch sizes; self-hosting avoids third-party egress but adds GPU and operational cost.

## Real-World Use Cases

1. **Enterprise docs assistant** — Confluence + PDFs: hybrid search fixes ticket-ID lookups, parent–child chunking keeps policy sections whole, and evals confirm whether reranking raises grounded answers enough to justify its latency.
2. **E-commerce support bot** — SKU and order-ID questions lean on the lexical channel while "returns policy" questions lean on semantic search; weighted RRF tunes the blend per traffic class.
3. **Legal discovery** — self-hosted `bge-reranker` keeps confidential documents in-house; the eval suite prioritizes `recall@20` because downstream summarization tolerates extra noise better than missing a key clause.
4. **Codebase copilot** — split chunks by AST boundaries (functions and classes), route exact symbol searches straight to lexical or index lookup, and measure MRR against real refactor commits.
5. **Multilingual helpdesk (DE and EN)** — pair a multilingual embedding model and reranker with language-specific lexical analyzers (→ 20.4.5.05).

## Summary

Lexical and dense-vector channels cover different retrieval failures: exact strings versus paraphrases. Merge their top-`k` candidates with Reciprocal Rank Fusion, add a cross-encoder reranker only when measured `recall@k` and `MRR` justify the latency, keep tenant filtering inside the query plan, and version your chunker, embedder, and index together.

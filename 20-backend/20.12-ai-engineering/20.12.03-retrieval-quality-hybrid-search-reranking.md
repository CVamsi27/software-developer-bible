# Retrieval Quality — Hybrid Search & Reranking

>
> **Why it matters:** A support answer is only as useful as the evidence the system retrieves. This chapter shows how to combine exact term matching with semantic search, then measure whether the right evidence reaches the model.

## Definition

**Hybrid search** combines lexical search, including full-text search (FTS), with dense-vector search, which compares numerical representations of query and document meaning. BM25 is a lexical ranking function using term frequency, document-length normalization, and corpus term rarity. It combines their ranked results. A vector index may use **ANN (approximate nearest-neighbor) search** to trade exactness for speed; **HNSW** is a graph-based ANN index. **Reranking** applies a query-document scoring model to a retrieved shortlist. The first stage aims for adequate recall at acceptable cost; reranking may improve ordering, but the measured result depends on the corpus, query set, and model.

> **Textbook Definition:** Hybrid retrieval combines rankings from lexical and semantic indexes to form candidate results; reranking then estimates query-document relevance over those candidates. Reranking cannot recover a relevant document excluded by retrieval.

```text
        query
          │
   ┌──────┴───────┐
   ▼              ▼
 lexical FTS    vector ANN (pgvector/HNSW)
 ranked list   ranked list
   └──────┬───────┘
          ▼
 Reciprocal Rank Fusion → bounded candidate list (tune by evaluation)
          ▼
 cross-encoder reranker  (cohere-rerank / bge-reranker)
          ▼
    top 5-8 chunks → LLM context
```

## First Principles

Retrieval quality is derivable from one failure mode: embedding similarity is not relevance.

1. **Vectors capture meaning but miss exactness.** "Error code E-402" semantically neighbors every error discussion but *is* one specific page — embeddings dilute it. Hybrid search (vector + keyword/BM25, → 20.4.5.05) exists because their strengths often complement each other; neither channel guarantees relevance: semantic for paraphrase, lexical for identifiers.
2. **Reranking exists because retrieval is recall-oriented.** The first stage fetches *plausibly* relevant candidates cheaply (ANN over vectors); the reranker (cross-encoder) scores the shortlist *with more computation; accuracy remains an evaluated property*. Two-stage is the architecture: cheap recall, precise ranking — the same shape as cache-then-DB (→ 20.8.01).
3. **Chunking is the silent quality lever.** Embedding a whole document dilutes signal; chunking too fine loses context — chunk boundaries are an information-design decision (by structure, overlap, hierarchy), not a character count.

## Trace the evidence through retrieval

### Start with the query's failure mode

An error code, product identifier, paraphrase, and a policy question need not rank the same way. Use the failure cases below to decide whether lexical search, semantic search, or both belong in the candidate stage.

| Failure mode | Example | Hybrid fix |
| ----------------- | ------------------------------------- | ----------------------------------------------------------------- |
| Exact identifiers | invoice `INV-2026-00317` | Test an exact identifier field or suitable lexical analyzer |
| Acronyms/jargon | "K8s PSP deprecation" vs verbose docs | Lexical term match + IDF weighting |
| Rare entities | customer name "Ondrej Spanel" | BM25; embedding drifts to common names |
| Negation | "not covered by warranty" | Evaluate a reranker on negation cases; polarity is not guaranteed |
| Long-tail domains | internal product codenames | BM25 over curated synonyms + rerank |

As a practical heuristic, if a person would use Ctrl+F to find an identifier or exact phrase, include and evaluate a lexical retrieval path.

### Reciprocal Rank Fusion

RRF merges ranked lists using rank positions only (no score normalization needed between incompatible scorers):

```text
RRF(d) = Σ_over_systems  1 / (k + rank_i(d))         k is a tuning parameter

Example (k=60):
  doc A: BM25 rank 1, vector rank 12  → 1/61 + 1/72 = 0.0303
  doc B: BM25 rank 5, vector rank 2   → 1/65 + 1/62 = 0.0315  ← B wins fusion
  doc C: vector rank 1 only           → 1/61 = 0.0164
```

Variants worth naming: weighted RRF (`α/(k+lexicalRank) + (1−α)/(k+semanticRank)`, omitting missing ranks) when one channel is empirically stronger; score-normalized linear fusion as the alternative when scores are calibrated.

### Rerankers: bi-encoder vs cross-encoder

```text
BI-ENCODER (retrieval)                CROSS-ENCODER (rerank)
  q → vec(q)   d → vec(d)              [q ⊕ d] → transformer → score ∈ R
  cosine precomputed                   full attention across both inputs
  no document model pass per query; ANN/distance work remains           O(N) forward passes per query
  lossy compression of meaning         sees token-level interactions
```

Choose a managed or self-hosted reranker by evaluating its quality, supported languages, data policy, latency, and total cost on the workload. Pin the provider/model version where possible and record the exact configuration; batch and candidate limits are provider- and runtime-specific.

### ANN index trade-offs: HNSW vs IVF

| Property | HNSW (graph) | IVF (inverted file / clustering) |
| -------------------- | ------------------------------------------------------------------------ | ------------------------------------ |
| Query speed | Approximate graph search; measure against the workload | Cluster probes tune search work |
| Recall | High at modest memory | Tunable via probes (recall/QPS dial) |
| Build time & updates | Slow build; incremental inserts OK | Fast train; rebalancing on drift |
| Memory | High (multi-layer neighbor lists) | Lower (centroid lists) |
| Filtered search | Filtering can reduce returned candidates/recall; tune/search iteratively | Post-filter can empty result sets |
| Where you meet it | pgvector optional HNSW index, Pinecone, Weaviate | FAISS classic, pgvector `ivfflat` |

pgvector guidance: HNSW and IVFFlat have configurable construction and query parameters; choose them by measuring recall, latency, memory, and update behavior for the corpus. IVFFlat's clustering depends on representative data. Approximate-index filtering may return fewer qualifying rows than requested; measure filtered recall and consider exact search, iterative scans, partial indexes, or partitioning where appropriate.

### Chunking impact on recall

- **Fixed-size overlap**: a simple baseline; choose chunk size and overlap for the tokenizer, document structure, and retrieval task, then compare on labeled queries.
- **Structure-aware**: split by headings/paragraphs/code blocks — keeps semantic units intact; compare against fixed-size on labeled queries.
- **Small-to-big / parent-child**: retrieve precise child chunks, feed their parent section to the LLM — best of precision and context.
- **Contextual enrichment** (Anthropic-style contextual retrieval): prepend a generated sentence situating the chunk ("From the X manual §3.2 about returns...") before embedding — fixes chunks whose text is meaningless alone.
- Chunk size interacts with k: smaller chunks need larger k; measure recall@k per size in the harness, not by intuition.

### Eval harness metrics

```text
recall@k  = |relevant ∩ top-k| / |relevant|          (did we fetch it at all?)
MRR       = mean(1 / first_relevant_rank)            (how high does the first hit land?)
precision@k, nDCG@k                                   (graded relevance variants)

Golden set: representative queries with relevant chunk/document labels and explicit handling for unanswerable cases.
Run it on index/model/chunking changes; size it to cover material query types and detect changes at acceptable evaluation cost.
```

## Code Examples

### pgvector schema with FTS sibling column

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE documents (
  id         BIGSERIAL PRIMARY KEY,
  tenant_id  TEXT NOT NULL,                    -- authenticated tenant boundary
  source_id  TEXT NOT NULL,             -- stable external key
  title      TEXT NOT NULL,
  content    TEXT NOT NULL,
  tsv        tsvector GENERATED ALWAYS AS (
               setweight(to_tsvector('english', title), 'A') ||
               setweight(to_tsvector('english', content), 'B')) STORED,
  embedding  vector(1536),                     -- matches your embed model
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, source_id)
);

-- Two indexes, two channels
CREATE INDEX documents_tsv_idx   ON documents USING gin(tsv);
CREATE INDEX documents_embed_idx ON documents
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

### Hybrid retrieval + RRF in one SQL round trip

```sql
WITH lexical_candidates AS (
  SELECT id, ts_rank(tsv, q) AS score
  FROM documents, websearch_to_tsquery('english', $2) q
  WHERE tenant_id = $1 AND tsv @@ q
  ORDER BY score DESC, id LIMIT $4
), semantic_candidates AS (
  SELECT id, embedding <=> $3::vector AS distance
  FROM documents WHERE tenant_id = $1 AND embedding IS NOT NULL
  ORDER BY embedding <=> $3::vector LIMIT $4
), lexical AS (
  SELECT id, row_number() OVER (ORDER BY score DESC, id) AS rank
  FROM lexical_candidates
), semantic AS (
  SELECT id, row_number() OVER (ORDER BY distance, id) AS rank
  FROM semantic_candidates
), fused AS (
  SELECT id, sum(1.0 / (60 + rank)) AS rrf FROM (
    SELECT id, rank FROM lexical UNION ALL SELECT id, rank FROM semantic
  ) s GROUP BY id
)
SELECT d.id, d.title, d.content, f.rrf
FROM fused f JOIN documents d ON d.id = f.id
WHERE d.tenant_id = $1
ORDER BY f.rrf DESC, d.id LIMIT $4;
```

The inner ORDER BY/LIMIT selects each channel's actual candidates before rank assignment; a window rank alone is not an output-order contract and can prevent the direct ANN index plan. PostgreSQL FTS with ts_rank is a lexical channel, not BM25. Inspect EXPLAIN and filtered recall; row-level security can reinforce the authenticated tenant parameter.

### Trace fusion independently of any provider

This complete JavaScript model uses one-based ranks, counts a document once per channel and breaks tied scores by id. With k=60, A at ranks 1/12 scores about 0.0303; B at 5/2 scores about 0.0315 and wins. A document absent from both lists cannot appear after fusion or reranking.

```javascript
export function fuse(channels, k = 60) {
  if (!Number.isFinite(k) || k < 0) throw new RangeError('invalid fusion constant');
  const scores = new Map();
  for (const ranked of channels) {
    const seen = new Set();
    ranked.forEach((id, index) => {
      if (typeof id !== 'string' || seen.has(id)) throw new Error('invalid ranked identity');
      seen.add(id);
      scores.set(id, (scores.get(id) ?? 0) + 1 / (k + index + 1));
    });
  }
  return [...scores].map(([id, score]) => ({ id, score }))
    .sort((a, b) => b.score - a.score || a.id.localeCompare(b.id));
}
```

### Rerank + eval harness in TypeScript (adapter sketch)

```typescript
// ai/retrieval.ts
type Candidate = { id: string; title: string; content: string; rrf: number };

export async function retrieve(tenantId: string, query: string): Promise<Candidate[]> {
  const embedding = await embed(query);                       // model-configured dimension
  const candidateLimit = configuredAndValidatedCandidateLimit; // tenantId must come from authenticated server context
  const { rows } = await pool.query(hybridSql, [tenantId, query, toPgVector(embedding), candidateLimit]);
  return rows;
}

export async function rerank(query: string, cands: Candidate[], topK = configuredAndValidatedTopK) {
  // Adapter selects a pinned provider model/version and enforces its limits.
  const res = await rerankAdapter.rerank({
    query,
    documents: cands.map((c) => `${c.title}\n${c.content}`),
    topN: topK,
  });
  return res.results.map((r) => ({ ...cands[r.index], score: r.relevanceScore }));
}

// --- Golden-set evaluation -------------------------------------------------
type Case = { tenantId: string; q: string; relevant: Set<string> };             // chunk/source ids

function recallAtK(ranked: string[], rel: Set<string>, k: number): number {
  if (!Number.isSafeInteger(k) || k < 1) throw new RangeError("invalid k");
  if (rel.size === 0) throw new Error("recall requires at least one labeled relevant item");
  return new Set(ranked.slice(0, k).filter((id) => rel.has(id))).size / rel.size;
}
function mrr(ranked: string[], rel: Set<string>): number {
  const hit = ranked.findIndex((id) => rel.has(id));
  return hit === -1 ? 0 : 1 / (hit + 1);
}

export async function evaluate(cases: Case[]) {
  if (cases.length === 0) throw new Error("empty eval set");
  let sumRecall10 = 0, sumMrr = 0;
  for (const c of cases) {
    const fused = await retrieve(c.tenantId, c.q);
    const final = await rerank(c.q, fused, 10);                  // toggle to A/B stages
    const ids = final.map((f) => f.id);
    sumRecall10 += recallAtK(ids, c.relevant, 10);
    sumMrr += mrr(ids, c.relevant);
  }
  const n = cases.length;
  return { recallAt10: sumRecall10 / n, mrr: sumMrr / n };
}
// This retrieval-only set contains answerable cases; test unanswerable-query refusal separately.
// Gate changes using repeated runs or uncertainty bounds appropriate to the set size.
```

### Self-hosted reranker option (bge)

```python
from sentence_transformers import CrossEncoder

model = CrossEncoder("BAAI/bge-reranker-v2-m3")
pairs = [(query, doc["text"]) for doc in documents]
scores = model.predict(pairs)  # query/document are separate paired inputs
ranked = sorted(zip(documents, scores), key=lambda item: float(item[1]), reverse=True)
```

Use the model's supported pair tokenizer and output semantics. Concatenating a literal `[SEP]` and taking a generic classification probability may not produce comparable relevance scores. Pin the checkpoint/runtime, test truncation and multilingual behavior, and bound batches; self-hosting still costs hardware and operations.

## Real-World Use Cases

1. **Enterprise docs assistant** — Confluence + PDFs: hybrid fixes ticket-number lookups; parent-child chunking keeps policy sections coherent; measure whether reranking improves grounded-answer rate on the labeled set.
2. **E-commerce support bot** — SKU/order-id questions routed by BM25-first heuristic; vector channel handles "returns policy" style intents; weighted fusion tuned per traffic class.
3. **Legal discovery** — bge-reranker self-hosted (confidentiality); eval harness tracks recall@20 because downstream summarization tolerates noise better than misses.
4. **Codebase copilot** — chunks split by AST boundaries; symbol-exact queries bypass vectors entirely (lexical shortcut), measured by MRR on refactor-commit replay.
5. **Multilingual helpdesk (DE/EN)** — multilingual embedder + cohere rerank; language-specific BM25 analyzers from the Search Infrastructure chapter supply the lexical channel.

## Validate the retrieval boundary

Evaluate each stage on a privacy-approved, representative labeled set: candidate recall before reranking, final ranking with recall@k/MRR or nDCG, and answer support after generation. Include exact identifiers, paraphrases, negation, unanswerable queries, tenant filters, and stale-document updates. Reranking cannot recover a document that retrieval omitted; an ANN filter can also return too few eligible rows, so inspect the query plan and filtered recall.

Version the source snapshot, chunker, embedding model, index configuration, fusion rule, and reranker with each result. Compare changes against held-out queries, then choose candidate count, `hnsw.ef_search`, and p95 stage budgets from measured quality and latency. For capacity, raw float32 vectors alone need roughly `rows × dimensions × 4` bytes; measure index overhead. Batch ingestion embeddings, plan dual-read/backfill when changing embedding models, and benchmark HNSW versus IVFFlat against both query and update patterns.

## Summary

Lexical and semantic retrieval cover different query failures; fusion improves the candidate set only when measured on the real corpus. Rerankers can improve ordering but cannot restore omitted evidence. Keep tenant authorization and source freshness in the retrieval path, and use a labeled evaluation set to choose chunking, index, candidate count, and latency budget.

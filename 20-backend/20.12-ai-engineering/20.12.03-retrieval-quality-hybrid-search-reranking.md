# Retrieval Quality — Hybrid Search & Reranking

> **TL;DR:** Pure vector search fails predictably on lexical gaps: exact SKUs, acronyms, error codes, names, negations. Production RAG retrieval is a three-stage pipeline — hybrid recall (BM25 + vector fused with Reciprocal Rank Fusion), rerank (cross-encoders like Cohere Rerank or bge-reranker score query-document pairs jointly), then top-k to the LLM. Index choice matters for latency/recall (HNSW vs IVF), chunking strategy quietly decides the retrieval ceiling, and an eval harness with recall@k / MRR on a golden set is how you *prove* improvements instead of vibes.
>
> **Why it matters:** The difference between "we added embeddings" and "we engineered retrieval" is exactly what separates senior AI-engineering candidates. This chapter pairs with Search Infrastructure at Scale (Postgres/OpenSearch mechanics) and Prompts, Context & Evals (the golden-set discipline).

## First Principles

Retrieval quality is derivable from one failure mode: embedding similarity is not relevance.

1. **Vectors capture meaning but miss exactness.** "Error code E-402" semantically neighbors every error discussion but *is* one specific page — embeddings dilute it. Hybrid search (vector + keyword/BM25, → 20.4.5.05) exists because the two failure modes are disjoint: semantic for paraphrase, lexical for identifiers.
2. **Reranking exists because retrieval is recall-oriented.** The first stage fetches *plausibly* relevant candidates cheaply (ANN over vectors); the reranker (cross-encoder) scores the shortlist *expensively and accurately*. Two-stage is the architecture: cheap recall, precise ranking — the same shape as cache-then-DB (→ 20.8.01).
3. **Chunking is the silent quality lever.** Embedding a whole document dilutes signal; chunking too fine loses context — chunk boundaries are an information-design decision (by structure, overlap, hierarchy), not a character count.

## Definition

**Hybrid search** runs lexical (BM25) and dense-vector retrieval in parallel and fuses their rankings; **reranking** re-scores the fused candidates with a heavier model that reads query and document together. Recall stage optimizes coverage (cheap, broad); rerank stage optimizes precision at small k (expensive, focused).

```text
        query
          │
   ┌──────┴───────┐
   ▼              ▼
 BM25/FTS      vector ANN (pgvector/HNSW)
 top ~50       top ~50
   └──────┬───────┘
          ▼
 Reciprocal Rank Fusion → candidate list (~40-60)
          ▼
 cross-encoder reranker  (cohere-rerank / bge-reranker)
          ▼
    top 5-8 chunks → LLM context
```

## Why Do We Need It?

1. **Embeddings blur exact tokens** — "ERR_CONN_RESET_1042", part number "ABX-4471", or a person's rare surname retrieve neighbors semantically near but lexically wrong; BM25 nails them.
2. **Lexical-only misses paraphrase** — "how do I cancel" vs "terminate my subscription": vector similarity bridges vocabulary gaps.
3. **Rerankers recover precision cheaply** — bi-encoder retrieval compresses documents into one vector each (lossy); cross-encoders attend across query+document tokens jointly and typically lift nDCG/precision@k substantially on the same corpus.
4. **Latency/cost budgets are asymmetric** — scanning thousands of candidates with a cross-encoder is impossible; scanning 60 is fine. Hybrid + rerank spends compute where it pays.
5. **Chunking silently caps quality** — wrong chunk size buries answers mid-chunk or starves context; retrieval metrics make the cap visible.
6. **Evals prevent regression theater** — every knob (fusion constant, reranker model, chunk size) shifts quality; without recall@k/MRR baselines you cannot tell improvement from noise.

## How It Works

### Why pure vector search fails (failure taxonomy)

| Failure mode | Example | Hybrid fix |
| ----------------- | ------------------------------------- | -------------------------------------- |
| Exact identifiers | invoice `INV-2026-00317` | BM25 exact match dominates |
| Acronyms/jargon | "K8s PSP deprecation" vs verbose docs | Lexical term match + IDF weighting |
| Rare entities | customer name "Ondrej Spanel" | BM25; embedding drifts to common names |
| Negation | "not covered by warranty" | Cross-encoder rerank catches polarity |
| Long-tail domains | internal product codenames | BM25 over curated synonyms + rerank |

Rule of thumb interviewers accept: if a human would use Ctrl+F, the query has a lexical component.

### Reciprocal Rank Fusion

RRF merges ranked lists using rank positions only (no score normalization needed between incompatible scorers):

```text
RRF(d) = Σ_over_systems  1 / (k + rank_i(d))         k ≈ 60 (dampens top-rank domination)

Example (k=60):
  doc A: BM25 rank 1, vector rank 12  → 1/61 + 1/72 = 0.0303
  doc B: BM25 rank 5, vector rank 2   → 1/65 + 1/62 = 0.0316  ← B wins fusion
  doc C: vector rank 1 only           → 1/61 = 0.0164
```

Variants worth naming: weighted RRF (`α·BM25 + (1−α)·vector`) when one channel is empirically stronger; score-normalized linear fusion as the alternative when scores are calibrated.

### Rerankers: bi-encoder vs cross-encoder

```text
BI-ENCODER (retrieval)                CROSS-ENCODER (rerank)
  q → vec(q)   d → vec(d)              [q ⊕ d] → transformer → score ∈ R
  cosine precomputed                   full attention across both inputs
  O(1) per doc at query time           O(N) forward passes per query
  lossy compression of meaning         sees token-level interactions
```

Practical picks: Cohere `rerank-v3.5` (managed, strong multilingual), `bge-reranker-v2-m3` (open weights, self-hosted), voyage `rerank-2`. Budget: rerank latency scales linearly with candidates — 50–100 candidates × ~10–30 ms is typical managed-API territory.

### ANN index trade-offs: HNSW vs IVF

| Property | HNSW (graph) | IVF (inverted file / clustering) |
| -------------------- | ------------------------------------ | ------------------------------------ |
| Query speed | Very fast, log-ish | Fast with `nprobe` tuning |
| Recall | High at modest memory | Tunable via probes (recall/QPS dial) |
| Build time & updates | Slow build; incremental inserts OK | Fast train; rebalancing on drift |
| Memory | High (multi-layer neighbor lists) | Lower (centroid lists) |
| Filtered search | Degrades gracefully-ish | Post-filter can empty result sets |
| Where you meet it | pgvector default, Pinecone, Weaviate | FAISS classic, pgvector `ivfflat` |

pgvector guidance: start HNSW (`m=16`, `ef_construction=64`; raise `hnsw.ef_search` at query time for recall); IVF needs training rows (~clusters × 40) and retraining when data distribution shifts.

### Chunking impact on recall

- **Fixed-size overlap** (300–800 tokens, 10–20% overlap): baseline, predictable.
- **Structure-aware**: split by headings/paragraphs/code blocks — keeps semantic units intact; usually beats fixed-size immediately.
- **Small-to-big / parent-child**: retrieve precise child chunks, feed their parent section to the LLM — best of precision and context.
- **Contextual enrichment** (Anthropic-style contextual retrieval): prepend a generated sentence situating the chunk ("From the X manual §3.2 about returns...") before embedding — fixes chunks whose text is meaningless alone.
- Chunk size interacts with k: smaller chunks need larger k; measure recall@k per size in the harness, not by intuition.

### Eval harness metrics

```text
recall@k  = |relevant ∩ top-k| / |relevant|          (did we fetch it at all?)
MRR       = mean(1 / first_relevant_rank)            (how high does the first hit land?)
precision@k, nDCG@k                                   (graded relevance variants)

Golden set: 50-200 real queries annotated with the chunk(s)/doc ids that MUST appear
Run on every index/model/chunking change; gate deploys like unit tests.
```

## Code Examples

### pgvector schema with FTS sibling column

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE documents (
  id         BIGSERIAL PRIMARY KEY,
  source_id  TEXT NOT NULL UNIQUE,             -- stable external key
  title      TEXT NOT NULL,
  content    TEXT NOT NULL,
  tsv        tsvector GENERATED ALWAYS AS (
               setweight(to_tsvector('english', title), 'A') ||
               setweight(to_tsvector('english', content), 'B')) STORED,
  embedding  vector(1536),                     -- matches your embed model
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Two indexes, two channels
CREATE INDEX documents_tsv_idx   ON documents USING gin(tsv);
CREATE INDEX documents_embed_idx ON documents
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

### Hybrid retrieval + RRF in one SQL round trip

```sql
WITH lexical AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank(tsv, q) DESC) AS rank
  FROM documents, websearch_to_tsquery('english', $1) q
  WHERE tsv @@ q LIMIT 50
),
semantic AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> $2::vector) AS rank
  FROM documents LIMIT 50
),
fused AS (
  SELECT id, sum(1.0 / (60 + rank)) AS rrf FROM (
    SELECT id, rank FROM lexical UNION ALL SELECT id, rank FROM semantic
  ) s GROUP BY id
)
SELECT d.id, d.title, d.content, f.rrf
FROM fused f JOIN documents d ON d.id = f.id
ORDER BY f.rrf DESC LIMIT 30;                    -- candidates out to reranker
```

### Rerank + eval harness in TypeScript

```typescript
// ai/retrieval.ts
type Candidate = { id: string; title: string; content: string; rrf: number };

export async function retrieve(query: string): Promise<Candidate[]> {
  const embedding = await embed(query);                       // 1536-dim vector
  const { rows } = await pool.query(hybridSql, [query, toPgVector(embedding)]);
  return rows;
}

export async function rerank(query: string, cands: Candidate[], topK = 6) {
  const res = await cohere.v2.rerank({
    model: 'rerank-v3.5',
    query,
    documents: cands.map((c) => `${c.title}\n${c.content}`),
    topN: topK,
  });
  return res.results.map((r) => ({ ...cands[r.index], score: r.relevanceScore }));
}

// --- Golden-set evaluation -------------------------------------------------
type Case = { q: string; relevant: Set<string> };             // chunk/source ids

function recallAtK(ranked: string[], rel: Set<string>, k: number): number {
  return ranked.slice(0, k).filter((id) => rel.has(id)).length / rel.size;
}
function mrr(ranked: string[], rel: Set<string>): number {
  const hit = ranked.findIndex((id) => rel.has(id));
  return hit === -1 ? 0 : 1 / (hit + 1);
}

export async function evaluate(cases: Case[]) {
  let sumRecall10 = 0, sumMrr = 0;
  for (const c of cases) {
    const fused = await retrieve(c.q);
    const final = await rerank(c.q, fused);                  // toggle to A/B stages
    const ids = final.map((f) => f.id);
    sumRecall10 += recallAtK(ids, c.relevant, 10);
    sumMrr += mrr(ids, c.relevant);
  }
  const n = cases.length;
  return { recallAt10: sumRecall10 / n, mrr: sumMrr / n };
}
// CI gate: fail PR when recallAt10 drops > 1pt vs stored baseline JSON
```

### Self-hosted reranker option (bge)

```typescript
import { pipeline } from '@xenova/transformers';

const reranker = await pipeline('text-classification',
  'Xenova/bge-reranker-base');                                // ONNX runtime

export async function localRerank(query: string, docs: { id: string; text: string }[]) {
  const scored = await Promise.all(docs.map(async (d) => ({
    id: d.id,
    score: (await reranker(`${query} [SEP] ${d.text}`, { topk: 1 }))[0].score,
  })));
  return scored.sort((a, b) => b.score - a.score);
}
```

Self-hosting trades ops burden for data residency and zero marginal cost at volume; managed APIs win time-to-market and multilingual strength out of the box.

## Real-World Use Cases

1. **Enterprise docs assistant** — Confluence + PDFs: hybrid fixes ticket-number lookups; parent-child chunking keeps policy sections coherent; rerank lifts grounded-answer rate from 71% to 89% on the golden set.
2. **E-commerce support bot** — SKU/order-id questions routed by BM25-first heuristic; vector channel handles "returns policy" style intents; RRF α tuned per traffic class.
3. **Legal discovery** — bge-reranker self-hosted (confidentiality); eval harness tracks recall@20 because downstream summarization tolerates noise better than misses.
4. **Codebase copilot** — chunks split by AST boundaries; symbol-exact queries bypass vectors entirely (lexical shortcut), measured by MRR on refactor-commit replay.
5. **Multilingual helpdesk (DE/EN)** — multilingual embedder + cohere rerank; language-specific BM25 analyzers from the Search Infrastructure chapter supply the lexical channel.

## Common Mistakes

| Mistake | Fix |
| -------------------------------------------- | ---------------------------------------------------------------------- |
| Vector-only retrieval shipped to prod | Hybrid from day one; identifiers/negation failures are immediate |
| Cosine similarity treated as relevance score | It ranks, not grades; rerank before threshold-based decisions |
| Reranking 500 candidates "for safety" | Latency explodes linearly; fuse to 30–80 candidates first |
| One global chunk size for all doc types | Structure-aware splitting; measure recall per type |
| No golden set until after launch | Build 50-case minimum during prototype week; grow from production logs |
| Changing embedder without reindex plan | Version embeddings per column; backfill jobs; dual-read compare |
| Ignoring index staleness | CDC/outbox sync into documents table (see search infra chapter) |
| Tuning knobs against vibes | One change → run harness → keep/discard by metric deltas |

## Best Practices

1. **Three-stage default**: hybrid recall → fuse (RRF) → cross-encoder rerank → top-k to LLM.
2. **Keep candidates ~30–100 between stages** — wide enough for recall, narrow enough for rerank latency.
3. **Version everything retrievable**: embedder, chunker, index params, reranker — store alongside results for reproducible evals.
4. **Golden set from real queries**, refreshed monthly from logs where users clicked/rephrased (implicit labels).
5. **Report recall@k AND MRR** — recall shows coverage, MRR shows user-perceived quality.
6. **Prefer parent-child chunking** for prose corpora; keep code/markdown structure-aware.
7. **Monitor online proxies**: citation-click rate, answer-groundedness judge score, "no answer" rate — offline harness plus online guardrails.
8. **Budget latency explicitly**: p95 target per stage (embed ~50 ms, SQL hybrid ~40 ms, rerank ~200 ms) and alert on drift.

## Performance Considerations

- HNSW memory ≈ vectors × dims × 4 bytes × ~1.5–2× graph overhead; plan instance RAM before corpus growth.
- Raise `hnsw.ef_search` (e.g., 40→120) only where recall metrics demand; it costs QPS linearly.
- Batch embedding calls (32–128 texts/request); embed at write time, never inside the request path.
- Cache query embeddings for repeated queries; dedupe near-duplicate queries before hitting rerank APIs.
- Cold-start IVF needs training data; HNSW starts serving immediately but builds slower on bulk loads — bulk-insert first, create HNSW index after.

## Summary

- Pure vector search fails on exactness; pure BM25 fails on paraphrase — hybrid + RRF covers both.
- Rerankers (Cohere, bge) convert candidate breadth into final precision; budget them 30–100 candidates.
- HNSW favors recall/speed with RAM cost; IVF trades tuning effort for memory — pick by scale and update pattern.
- Chunking choices bound achievable quality; structure-aware and parent-child beat naive fixed-size.
- An eval harness (golden set, recall@k, MRR, CI gates) is the difference between engineering and superstition.

## Cheat Sheet

| Concept | Description |
| ---------------------------- | -------------------------------------------------- |
| Hybrid search | Parallel BM25 + vector channels merged per query |
| RRF | `Σ 1/(k+rank)` fusion; no score calibration needed |
| Cross-encoder | Joint query-doc scoring; rerank-stage workhorse |
| bge-reranker / cohere-rerank | Open-weights vs managed rerank options |
| HNSW | Graph ANN: high recall/speed, high memory |
| IVF | Cluster-based ANN: tunable probes, cheaper memory |
| `ef_search` / `nprobe` | Per-query recall-latency knobs for HNSW/IVF |
| Parent-child chunks | Retrieve small, feed large context upstream |
| Contextual retrieval | Prepend situating context before embedding |
| recall@k | Fraction of relevant items present in top-k |
| MRR | Mean reciprocal rank of first relevant hit |

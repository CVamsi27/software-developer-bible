# Agent Orchestration Patterns

>
> **Why it matters:** A model call that can invoke tools creates a control loop. The application must decide which actions are allowed, how progress is measured, and what happens when a tool fails or the run reaches its budget.

## Definition

In this guide, an **agent** is a system in which a language model proposes actions (often tool calls) toward a goal and receives observations before a later decision. **Orchestration** is the application-controlled execution around those proposals: it validates calls, authorizes effects, manages state, enforces budgets, and decides whether to continue. The term *agent* is used differently across frameworks, so state the behavior rather than relying on the label.

> **Textbook Definition:** Agent orchestration controls an iterative system in which model-selected actions produce observations that inform subsequent actions. The orchestrator defines permitted tools, state transitions, budgets and termination conditions independently of the model's proposed plan.

```text
            ┌────────────────────────────────────────────┐
            │              ORCHESTRATOR                  │
            │   state · budgets · guards · memory        │
            └──────┬─────────────────────▲───────────────┘
                   │ prompt + history    │ observations
                   ▼                     │
              ┌───────────────────────────────┐          ┌──────────┐
              │   LLM   │ ───────► │  TOOLS   │──► external world
              └───────────────────────────────┘ action └──────────┘      (APIs, DBs,
                 ▲       proposal                     search, code)
                 │
            plan → act → observe → (repeat until DONE | guard trips)
```

## First Principles

Agents are LLMs in a control loop — every pattern follows from that loop's failure modes:

1. **The loop is proposal → validated action → observation → next decision.** The model may return an invalid call or an unhelpful result; the application owns validation, execution, and stopping. A hard bound is required because the system must remain safe and affordable even when the model makes no progress.
2. **State needs an explicit lifetime.** A model's context window and application deadline are finite. Scratchpads, checkpoints, and durable state (→ 20.12.01 axiom 2) can support resumability, but persisted traces need privacy, access, and retention rules. Select what enters each model call.
3. **Autonomy follows data sensitivity and effect impact.** A read-only tool can expose confidential data; a write can be low risk or irreversible. Apply authorization to every call, and add deterministic checks or human review where the impact requires them.

## Build the control loop

### Anatomy of the plan-act-observe loop (ReAct)

The application can be understood as a **decision → action → observation** loop. A model's private reasoning is neither required nor a reliable audit artifact; record the proposed call, validated action, and bounded result instead:

```text
Iteration 1: Decision: look up the authorized account's latest invoice
             Action:   invoices.get(invoice_id="INV-2026-00317")
             Observation: { id: "INV-2026-00317", total: 129.00, status: "open" }
Iteration 2: Decision: check the refund policy for this invoice
             Action:   policy.search("refund window open invoice")
             Observation: "Refunds allowed within 14 days of charge ..."
Iteration 3: Decision: request a refund after the server-side eligibility check
             Action:   refunds.create(invoice_id="INV-2026-00317")
             Observation: { refund_id: "rf_991", status: "pending" }
Final:       Answer: Refund rf_991 requested; current state is pending ...
```

The orchestration layer — not the model — parses actions, executes tools, appends observations, checks guards, and decides whether another iteration may start.

### Stopping criteria and max-step guards

Layer multiple independent stops; any single signal firing halts the run:

| Guard | Trigger | Rationale |
| -------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------- |
| Terminal action | Model emits `final_answer` / `DONE` | Happy path |
| Max steps | `iteration >= configured limit` | Hard ceiling chosen from task, latency, and cost requirements |
| Token budget | cumulative tokens > B | Cost ceiling independent of steps |
| Wall-clock deadline | elapsed > the task's deadline | Bound the request or job lifetime |
| No-progress detector | same tool+args recur without state change beyond a task-specific limit | Detects likely spinning without rejecting useful repeated reads |
| Review gate | task-specific validated evidence is insufficient | Route to an approved review/refusal path |

On guard trip, return a structured incomplete/stopped status. Include partial content only when the product contract allows it, and mark it incomplete so downstream code cannot treat it as a validated success.

### Loop-cost guards (runaway-agent defense)

Treat an agent like an untrusted worker process: sandbox it with budgets and a circuit breaker.

- **Step budget** per run AND per user session (an agent that restarts itself can still multiply).
- **Token/cost budget** enforced *before* each LLM call — reject the call, not after billing.
- **Circuit breaker** per tool: after M consecutive failures, open the circuit, inject "this tool is unavailable" as observation, let the planner route around it instead of hammering.
- **Rate limiter** per tool target so parallel agents can't DDoS your own downstream services.
- **Kill switch**: feature-flag off at the gateway level (Docita's `AI_EXTERNAL_ENABLED` pattern).

### State machines vs graph orchestration (LangGraph-style)

Two dominant ways to make control flow inspectable:

| Aspect | Hand-rolled state machine | Graph framework (LangGraph et al.) |
| ------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Mental model | Explicit states + transition guards | Nodes = steps; edges = conditional routing |
| Determinism | You own every branch | State updates/reducers and concurrency rules depend on the runtime |
| Persistence/checkpointing | Implement and operate it | Checkpointing is available with a configured checkpointer; verify runtime and recovery semantics |
| Human-in-the-loop | Ad hoc | Interrupt-before-node primitives |
| Multi-agent | DIY message passing | First-class subgraphs, supervisor nodes |
| Cost | No added orchestration framework; implementation burden is yours | Learning curve + version churn |

Use a plain state machine when the transitions are few and local. Consider a graph runtime when the workflow needs durable checkpoints, branching, replay, or human interruption. A framework does not supply correct authorization, termination, or recovery policy; verify its persistence and concurrency semantics.

```text
GRAPH VIEW (LangGraph-style)          STATE MACHINE VIEW
                                      ┌─────────┐
 START ──► classify ──► retrieve       │ state:  │ event/guard
             │           │             │ IDLE →                   │ ──► PLANNING
             │ no docs   ▼             │                          │ ──► ACTING
             └──────► respond ◄── grade│         │ ──► OBSERVING ─┐
                        │        │     └─────────┘ ◄── retry(≤2) ─┘
                        ▼        ▼ rewrite
                      END     retrieve
```

Both encode the same invariant: transitions happen in *your* code after guards pass; a graph still needs explicit budgets and authorization, and its model-dependent branches remain stochastic.

### Tool-calling patterns

- **Parallel tool calls**: model returns several independent invocations in one turn (e.g., fetch weather AND calendar); execute concurrently with bounded concurrency and merge ordered observations. Big latency win; only valid when calls are side-effect-free or commutative.
- **Chained (sequential) calls**: output of tool A feeds arguments of tool B (`search → pick_id → fetch_detail`); inherently sequential, keep dependency explicit in the scratchpad.
- **Mixed plans**: dependency plans need explicit references and a reviewed scheduler; ordinary tool-call arrays provide arguments, not a standardized dependency graph. Run truly dependent calls on later model turns or implement an explicit plan format.
- **Validation boundary**: schema-check every argument against the tool contract before execution; reject with a corrective observation rather than throwing raw errors into context.

### Standardized tool interfaces: Model Context Protocol (MCP)

The **Model Context Protocol (MCP)** standardizes how an AI host connects to tools and external context, reducing the need for every host to implement a separate adapter for every service. The current specification revision, `2026-07-28`, uses JSON-RPC messages with standard `stdio` and Streamable HTTP transports. Servers can expose tools, resources, and prompts; clients can expose elicitation, while optional extensions add capabilities such as long-running tasks. Earlier revisions have different session and transport rules, so pin the protocol and SDK versions you implement.
```text
┌────────────────────────────────────────────────────────┐
│                   MCP Client / Host                    │
│            (Agent Runtime / IDE / LLM App)             │
└───────────────────────────┬────────────────────────────┘
                            │ JSON-RPC 2.0 (stdio / Streamable HTTP)
                            ▼
┌────────────────────────────────────────────────────────┐
│           MCP Server (Git / DB / SaaS APIs)            │
│  • Tools:     Executable functions (JSON Schema args)  │
│  • Resources: Read-only context (files, tables, logs)  │
│  • Prompts:   Pre-packaged prompt templates            │
└────────────────────────────────────────────────────────┘
```

The transport makes discovery and invocation interoperable; it does not make the server trusted or sandboxed. A `stdio` server is a child process with the host's permissions unless separately isolated. Validate discovered schemas and results, authenticate remote servers, scope capabilities, and enforce authorization before every effect.

### Multi-agent topologies

```text
SUPERVISOR / WORKER                DEBATE                    HANDOFF (pipeline)
                                   ┌────────┐  critique
        ┌──────────┐               ▼        ▼  exchange        A ──handoff──► B ──► C
   ┌──► │ Worker A │ research   proposer  critic              (transfer state +
   │    └──────────┘               └───┬────┘                    ownership)
supervisor                           judge/arbitrator
   │    ┌──────────┐
   └──► │ Worker B │ coding       Use when: adversarial      Use when: distinct
        └──────────┘               quality matters and        competencies/domains;
   Routes tasks, merges results    cost is secondary          each stage owns its tools
```

- **Supervisor/worker**: router agent delegates to specialist agents; an option for broad task spaces; compare against a simpler single-agent baseline. Failure domain: supervisor becomes a bottleneck/single point of confusion — cap its context.
- **Debate / generator-critic**: two or more agents argue, a judge (or the same model with a rubric) decides. Can help some tasks but may reinforce shared mistakes; measure task quality and added token cost — reserve for high-stakes low-volume paths.
- **Handoff**: agent-to-agent transfer with explicit state serialization (like warm transfers in call centers); the receiving agent re-plans from the handed summary, keeping each context small and focused.

### Memory tiers

| Tier | What it holds | Lifetime | Implementation |
| ----------------------- | ------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------ |
| Scratchpad (working) | Current goal, constraints, recent observations | One run | Typed state object, compacted by task-specific relevance |
| Vector store (semantic) | Distilled facts, past solutions, corpus knowledge | Weeks–forever | Embeddings + ANN retrieval (see Retrieval Quality chapter) |
| Episodic | Full trajectories of past runs, outcomes, lessons | Months | Append-only log keyed by task type; retrieved as few-shot exemplars or "last time you tried X and it failed" hints |

Keep temporary notes in the scratchpad first. At the end of a run, a summarizer can save facts that will be useful later in the vector store. Archive the full run separately so it can be evaluated or recalled. Do not put the entire history into the model's context at every step: irrelevant older material uses space needed for the current task.

### Evaluating agentic systems: trajectory evals

Judge the *path*, not just the destination:

- **Outcome metrics**: task success rate (human- or judge-graded), groundedness of final answer.
- **Trajectory metrics**: number of steps vs reference-efficient baseline; redundant/duplicate tool calls; illegal tool sequences; tool-choice accuracy per step; recovery quality after injected failures.
- **Method**: record only traces permitted by the privacy and retention policy; replay golden tasks on prompt/model/tool changes; use task-specific human or model grading with a checked rubric; gate meaningful regressions (see Prompts, Context & Evals).
- **Failure injection**: deliberately break a tool (latency spike, empty result, 500) in staging and assert the agent degrades gracefully — this is the agent equivalent of chaos testing.

### Failure modes to design against

- **Tool error cascades**: one flaky tool fails → error string enters context → model misreads it as signal → wrong next action → compensating wrong calls. Fix: typed errors, circuit breakers, and never letting raw stack traces become observations.
- **Context rot**: long runs accumulate stale, contradictory, or verbose observations; attention dilutes and early instructions decay. Fix: periodic summarization/compaction of the scratchpad, drop superseded observations, re-inject the original goal every K steps.
- **Goal drift / loss**: after many edits the agent optimizes a mutated version of the objective. Fix: immutable goal field in state, restated verbatim in each planning prompt.
- **Looping**: same (tool, args) repeatedly without a state change. Fix: detect non-progress under a task-specific policy, then bound replanning or return a structured halt.

## Code Examples

Only the local loop below is self-contained. The later framework/MCP and trajectory fragments are adapter sketches with injected types/helpers; verify a pinned SDK and protocol version before treating them as integrations.

### An executable control loop with injected read tools

This JavaScript model bounds model turns, proposed calls, answer bytes, and the amount of serialized content forwarded as observations. It accepts injected read tools; each tool must validate its arguments, enforce access, and bound results before allocating them. The model answer remains untrusted. The loop has no provider wire protocol or durable effects; a mutating implementation additionally needs authoritative checks, durable operation identity, and outcome reconciliation.

```javascript
export async function runAgent(model, tools, limits) {
  const { maxTurns, maxCalls, timeoutMs, maxAnswerBytes, maxObservationBytes } = limits;
  for (const n of [maxTurns, maxCalls, timeoutMs, maxAnswerBytes, maxObservationBytes]) {
    if (!Number.isSafeInteger(n) || n < 1) throw new RangeError('invalid limit');
  }
  const signal = AbortSignal.timeout(timeoutMs);
  const observations = [];
  const ids = new Set();
  const withinBytes = (value, maxBytes) => {
    try {
      const encoded = JSON.stringify(value);
      return typeof encoded === 'string' && new TextEncoder().encode(encoded).byteLength <= maxBytes;
    } catch { return false; }
  };
  let calls = 0;
  for (let turn = 0; turn < maxTurns; turn++) {
    if (signal.aborted) return { status: 'halted', reason: 'deadline', observations };
    let step;
    try { step = await model(observations, signal); }
    catch { return { status: 'halted', reason: signal.aborted ? 'deadline' : 'provider_error', observations }; }
    if (signal.aborted) return { status: 'halted', reason: 'deadline', observations };
    if (!withinBytes(step, maxObservationBytes)) return { status: 'halted', reason: 'model_output_too_large', observations };
    if (step?.kind === 'answer' && typeof step.text === 'string') {
      if (!withinBytes(step.text, maxAnswerBytes)) return { status: 'halted', reason: 'answer_too_large', observations };
      return { status: 'done', answer: step.text, observations };
    }
    if (step?.kind !== 'calls' || !Array.isArray(step.calls) || step.calls.length === 0) {
      return { status: 'halted', reason: 'invalid_step', observations };
    }
    for (const call of step.calls) {
      if (++calls > maxCalls) return { status: 'halted', reason: 'call_budget', observations };
      if (!call || typeof call.id !== 'string' || call.id.length === 0 ||
          typeof call.name !== 'string' || ids.has(call.id)) {
        return { status: 'halted', reason: 'invalid_call_id', observations };
      }
      ids.add(call.id);
      const tool = Object.hasOwn(tools, call.name) ? tools[call.name] : undefined;
      let result;
      if (!tool) result = { ok: false, error: 'unknown_tool' };
      else {
        try {
          const value = await tool(call.args, signal);
          result = withinBytes(value, maxObservationBytes)
            ? { ok: true, value }
            : { ok: false, error: 'result_too_large_or_unserializable' };
        } catch { result = { ok: false, error: 'tool_failed' }; }
      }
      observations.push({ id: call.id, result });
      if (signal.aborted) return { status: 'halted', reason: 'deadline', observations };
    }
  }
  return { status: 'halted', reason: 'turn_budget', observations };
}
```

Turn one may propose `search` with call id `c1`; the injected tool returns documents. Turn two receives that exact observation and returns an answer. Unknown tools receive a safe failure observation; repeated ids halt rather than attaching a result to an ambiguous call. A sequence of invalid/unknown proposals still consumes turn/call budgets. Tool adapters must honor the signal and bound query results before materializing them; the serialization check bounds what this loop forwards but cannot undo memory already allocated by a tool. This model cannot forcibly stop an ignored abort or undo a completed effect.

For a financial/token ceiling, reserve a conservative bound on the whole serialized input and maximum output before **each** inference, including cached input/write and reasoning categories under the provider's price contract. Settle actual usage once against the durable reservation; count malformed and failed requests too. A turn count alone is not a spend cap. Keep the raw assistant call message and all required call/result pairs in the provider adapter; this local observation array is not a universal provider message format.

### Parallel tool execution with bounded concurrency

```typescript
// agent/tools-parallel.ts
export async function runBatch(calls: ToolCall[], tools: Tool[], concurrency: number): Promise<Observation[]> {
  if (!Number.isSafeInteger(concurrency) || concurrency < 1) throw new RangeError("invalid concurrency");
  const queue = [...calls];
  const out: Observation[] = [];
  async function worker() {
    while (queue.length) {
      const call = queue.shift()!;
      const tool = tools.find(t => t.name === call.name);
      if (!tool) {
        out.push(toObservation(call, { ok: false, error: "unknown tool", retryable: false }));
        continue;
      }
      const parsed = tool.schema.safeParse(call.args);
      const result = parsed.success
        ? await tool.fn(parsed.data, AbortSignal.timeout(15_000)).catch(() =>
            ({ ok: false as const, error: "tool failed", retryable: true }))
        : { ok: false as const, error: "schema violation", retryable: false };
      out.push(toObservation(call, result));       // order preserved via index below
    }
  }
  await Promise.all(Array.from({ length: Math.min(concurrency, calls.length) }, worker));
  return sortById(out, calls);                     // re-align with model's ordering
}
```

This fragment illustrates concurrency only. Authorize read calls too, bound their results, and classify retryable failures. Parallelize only independent read-only calls; mutations stay sequential behind the supervisor's validation and idempotency boundary.

### Connecting an MCP server safely

Treat a discovered tool as an untrusted integration contract. Pin an SDK that supports the protocol revision you deploy; paginate discovery; namespace names; validate argument and result schemas; cap result size; authorize each operation in the host; and close transports during shutdown. For remote servers, configure authentication and transport security. A subprocess launched over `stdio` is not sandboxed by MCP.

### Graphs make allowed transitions visible

A workflow with evidence review might follow `START → retrieve → assess → answer` when evidence is sufficient, or `assess → bounded rewrite → retrieve` once before returning an unsupported result. Put the transition rule in reviewed code. If the run can pause for approval or survive a worker restart, checkpoint the minimal state needed to resume; persist a durable operation id for effects and apply access and retention policy to saved state.

A graph library can provide checkpoint primitives, but verify which state is persisted, how concurrent updates merge, and how replay handles external effects. A checkpoint does not make a payment or write idempotent.

### Trajectory evaluation harness

```typescript
// eval/trajectory.ts
type Episode = { steps: StepRecord[]; outcome: "success" | "fail"; costUsd: number };

function scoreEpisode(ep: Episode, expected: GoldenCase) {
  const toolSteps = ep.steps.filter(s => s.kind === "tool");
  const duplicateCalls = toolSteps.length - new Set(toolSteps.map(s => s.signature)).size;
  return {
    success: ep.outcome === "success",
    steps: ep.steps.length,
    stepRatio: ep.steps.length / Math.max(expected.referenceSteps, 1),    // interpret only when tasks and outcomes are comparable
    redundantCallRatio: duplicateCalls / Math.max(toolSteps.length, 1),
    costUsd: ep.costUsd,
    usedForbiddenTool: ep.steps.some(s => s.tool && expected.forbidden.includes(s.tool)),
  };
}

// Compare repeated runs with uncertainty and task-specific quality/cost budgets; avoid universal score cutoffs.
```

Replay the same golden task suite across prompt/model changes; store traces so any score is explainable step-by-step.

## Where the pattern helps

| Workflow | Orchestration decision |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Support refund request | Read policy and eligibility first; authorize and idempotently execute the mutation on the server; require review when policy says so. |
| Code migration assistant | Let tools inspect, propose a patch, and run tests; keep repository writes behind a human-reviewed commit step. |
| On-call investigation | Allow read-only dashboard/log tools, bound investigation time, and return evidence plus a proposed change rather than granting production write access. |

## Operational invariants

- Count every inference and tool proposal against a run budget, even malformed or unknown calls. Reserve spend before each model call; step limits alone are not cost limits.
- Give every tool a narrow schema, server-side authorization, timeout, typed error, and bounded result. Mutations also need idempotency and reconciliation for uncertain outcomes.
- Stop on a terminal result, exhausted step/token budget, deadline, or task-specific no-progress condition. Return an explicit incomplete status when a guard trips.
- Persist only what the workflow must resume. Compaction must preserve the goal, evidence references, pending actions, and approval state; test it against lost or contradictory facts.
- Evaluate final task success and the path: forbidden calls, duplicate work, recovery after injected failures, latency, and cost. Compare with a simpler baseline before adding agents or debate.

## Summary

An agent is a model inside an application-owned decision/action/observation loop. The host owns tool permission, state transitions, budgets, stopping, and recovery. Add graph persistence or multiple agents only when the workflow needs those capabilities and evaluations show the added coordination is worthwhile.

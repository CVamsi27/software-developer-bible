# Agent Orchestration Patterns

Give a language model access to tools and you immediately stop having a single request-response call. Instead, you have a control loop: the model proposes a tool call, your application executes it and feeds back the result, and the model decides what to do next. Without tight boundaries in *your* code, one confused model can spin through fifty API calls, burn your daily budget, or trigger an unauthorized refund.

---

## Definition

- An **agent** is a system where a language model proposes actions (typically tool calls) across one or more turns, using the results of earlier actions to decide what to do next.
- **Orchestration** is the deterministic application code wrapped around that loop: it validates tool arguments, checks user permissions, manages state and memory, enforces budgets and timeouts, and decides when to stop.

Because frameworks use the word *agent* loosely, always describe the actual control loop and authority boundaries instead of relying on the buzzword.

> **Textbook Definition:** Agent orchestration controls an iterative system in which model-selected actions produce observations that inform subsequent actions. The orchestrator defines permitted tools, state transitions, budgets and termination conditions independently of the model's proposed plan.

```text
          ┌──────────────────────────────────────────────────┐
          │                  ORCHESTRATOR                    │
          │     state · budgets · permissions · memory       │
          └──────────┬───────────────────────────▲───────────┘
                     │ prompt + history          │ observations
                     ▼                           │
              ┌─────────────────────────────────────────┐  action     ┌─────────────┐
              │     LLM     │ ──────────► │    TOOLS    │ ──► external world
              └─────────────────────────────────────────┘  proposal   └─────────────┘     (APIs, DBs, search)
                     ▲
                     └──── plan → act → observe (until DONE or guard trips)
```

## First Principles

An agent is just an LLM inside a `while` loop. Almost every production pattern exists to control three failure modes of that loop:

1. **The model proposes; your code decides.** The model can hallucinate a tool name, invent malformed arguments, or repeat the same failing call forever. Your orchestrator validates every call, enforces a hard ceiling on turns, calls, tokens, and wall-clock time, and counts *failed or invalid proposals* against the budget too.
2. **State needs an explicit lifetime and privacy boundary.** Context windows and HTTP timeouts are finite. Checkpoints and scratchpads let long jobs resume (→ 20.12.01), but anything persisted needs retention and access rules, and only relevant state should re-enter each model prompt.
3. **Permission follows impact, not convenience.** Read-only tools can still leak confidential tenant records; write tools can cause irreversible financial or data damage. Authorize every tool call against the authenticated caller on the server, and require human review before high-impact mutations.

## 1. Design the Control Loop

### Anatomy of a Plan–Act–Observe Loop (ReAct)

Each turn follows **decision → validated action → bounded observation**. Do not rely on hidden model reasoning text as an audit trail; log the proposed call, the validated server action, and the bounded observation instead:

```text
Iteration 1: Decision:    look up the authorized account's latest invoice
             Action:      invoices.get(invoice_id="INV-2026-00317")
             Observation: { id: "INV-2026-00317", total: 129.00, status: "open" }

Iteration 2: Decision:    check the refund policy for an open invoice
             Action:      policy.search("refund window open invoice")
             Observation: "Refunds allowed within 14 days of charge..."

Iteration 3: Decision:    request refund after server-side eligibility check
             Action:      refunds.create(invoice_id="INV-2026-00317")
             Observation: { refund_id: "rf_991", status: "pending" }

Final:       Answer:      "Refund rf_991 requested; current state is pending."
```

Your orchestrator — never the model — parses arguments, runs tools, checks budgets, and decides whether another turn is permitted.

### Layer Independent Stopping Guards

Never rely on the model deciding it is "done." Layer independent stops so any single condition halts the run cleanly:

| Guard | Trigger | Why it exists |
| ---------------------- | ------------------------------------------------------------- | ----------------------------------------------------------- |
| Terminal action | Model emits a final answer (`DONE`) | Normal completion |
| Max turns and calls | `turn >= maxTurns` or `calls >= maxCalls` | Hard loop bound even when proposals are invalid |
| Spend and token budget | Reserved tokens or cost exceed run or session ceiling | Stops a single huge context turn from blowing spend |
| Wall-clock deadline | Elapsed time exceeds request or job deadline | Protects upstream callers and worker pools |
| No-progress detector | Same `(tool, args)` repeats without state change | Catches spinning early without blocking valid retries |
| Review gate | High-impact action or insufficient validated evidence | Routes to human approval or explicit refusal |

When any guard trips, return a structured `halted` status with the stop reason. Only include partial content if the product contract allows it, and mark it incomplete so downstream systems never treat it as a validated result.

### Defend Against Runaway Loops

Treat an agent like an untrusted worker process:

- **Bound both per-run and per-session budgets** so an agent that retries or restarts itself cannot multiply spend.
- **Reserve token and spend budget *before* each inference call**, not after the provider bills you.
- **Add per-tool circuit breakers:** after $M$ consecutive failures, open the breaker and return a structured `"tool unavailable"` observation so the model can degrade cleanly instead of hammering a failing dependency.
- **Rate-limit downstream tool targets** so parallel agents cannot overload your own APIs.
- **Wire a gateway kill switch** (such as Docita's `AI_EXTERNAL_ENABLED` flag) to shut off external calls immediately during incidents.

### Hand-Rolled State Machine vs Graph Framework (LangGraph-style)

Once a workflow branches or pauses, make transitions explicit in code:

| Aspect | Hand-rolled state machine | Graph framework (e.g. LangGraph) |
| ------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------- |
| Mental model | Explicit states + transition guards in ordinary code | Nodes = steps; conditional edges = routing |
| Determinism | You control every branch and merge rule | State reducers and concurrency depend on the runtime |
| Checkpointing and resume | You build and operate persistence yourself | Built-in checkpointer adapters; verify recovery semantics |
| Human-in-the-loop | Custom pause and resume storage | First-class interrupt-before-node primitives |
| Multi-agent | Explicit function calls or message passing | Subgraphs and supervisor patterns built in |
| Maintenance cost | Zero extra framework lock-in; more boilerplate | Faster scaffolding, higher learning curve and version churn |

Start with a plain state machine when transitions are small and local. Reach for a graph runtime when you genuinely need durable checkpoints, replay, or pause-for-approval workflows. Either way, transitions still live in *your* code, and frameworks do not give you authorization or idempotency for free.

```text
GRAPH VIEW (LangGraph-style)              STATE MACHINE VIEW

 START ──► classify ──► retrieve          ┌────────────┐  event / guard
             │            │               │    IDLE    │ ──► PLANNING
             │ no docs    ▼               │            │ ──► ACTING
             └──────► respond ◄── grade   │            │ ──► OBSERVING ──┐
                         │          │     └────────────┘ ◄── retry (≤2) ─┘
                         ▼          ▼ rewrite
                        END     retrieve
```

### Tool-Calling Execution Patterns

- **Parallel calls:** when the model requests multiple independent reads in one turn (e.g., check weather and check calendar), run them with a bounded concurrency limit and re-align observations to the model's call order. Only parallelize side-effect-free or commutative calls.
- **Sequential (chained) calls:** when tool B needs tool A's output (`search → pick_id → get_detail`), run them across turns or via an explicit reviewed scheduler — ordinary tool-call arrays carry arguments, not a dependency graph.
- **Validation boundary:** validate every argument against a strict schema before execution; if validation fails, return a concise corrective error observation instead of dumping raw stack traces into the context.

### Standardized Tool Interfaces: Model Context Protocol (MCP)

The **Model Context Protocol (MCP)** provides a standard JSON-RPC boundary between an AI host (your agent runtime or IDE) and external servers that expose capabilities, avoiding bespoke per-service adapters. The `2026-07-28` specification uses stateless requests over `stdio` or Streamable HTTP transports. Servers can expose **tools**, **resources**, and **prompts**; user elicitation travels as a multi-round-trip `input_required` result rather than server-initiated JSON-RPC, and optional extensions support long-running tasks. Because earlier revisions use different session rules, pin both the protocol revision and SDK version together.

```text
┌────────────────────────────────────────────────────────┐
│                   MCP Client / Host                    │
│            (Agent Runtime / IDE / LLM App)             │
└───────────────────────────┬────────────────────────────┘
                            │ JSON-RPC 2.0 (stdio / Streamable HTTP)
                            ▼
┌────────────────────────────────────────────────────────┐
│           MCP Server (Git / DB / SaaS APIs)            │
│  • Tools:     Executable functions (JSON Schema args)  │
│  • Resources: Read-only context (files, tables, logs)  │
│  • Prompts:   Pre-packaged prompt templates            │
└────────────────────────────────────────────────────────┘
```

Interoperability is **not** sandboxing. Treat an MCP server's trust boundaries at four moments:
1. **Initialize:** negotiate an exact supported protocol revision and fail closed on mismatch.
2. **Discover (`tools/list`):** namespace server tool names (e.g., `github__create_issue`) so a server cannot shadow local tools, and treat annotations like `readOnlyHint` as untrusted hints rather than permissions.
3. **Invoke (`tools/call`):** validate arguments against both the schema and host range limits, authorize against the authenticated user and target resource, cap result bytes before materializing, and treat returned text as untrusted data (a hostile server output must never gain execution authority).
4. **Shutdown:** a `stdio` server is a child process with the host's permissions unless isolated separately; close transports cleanly and reap child processes. For remote servers, keep credentials in transport auth configuration — never in arguments the model can read.
5. **Watch for manifest drift ("rug pulls"):** a compromised or upgraded MCP server can rewrite tool descriptions or JSON Schema metadata across sessions to smuggle indirect prompt injections (for example, instructing the model to copy secrets into a benign argument). Pin approved tool manifests or hash-verify `tools/list` schemas at connect time and require explicit review before accepting changes.

### Multi-Agent Topologies

Only split work across multiple agents after a single agent with clean tools hits a measurable limit (such as context bloat across distinct domains).

```text
SUPERVISOR / WORKER               DEBATE                      HANDOFF (pipeline)
                                  ┌────────┐  critique
       ┌──────────┐               ▼        ▼  exchange        A ──handoff──► B ──► C
  ┌──► │ Worker A │ research   proposer  critic              (transfer summary +
  │    └──────────┘               └───┬────┘                  tool ownership)
supervisor                            ▼
  │    ┌──────────┐            judge / arbitrator
  └──► │ Worker B │ coding
       └──────────┘            Use when: high-stakes          Use when: distinct
  Routes tasks, merges output  review justifies extra cost    domains own distinct tools
```

- **Supervisor and worker:** a router delegates subtasks to specialists and merges outputs. Watch for the supervisor becoming a context bottleneck.
- **Debate (generator–critic):** one agent proposes, another critiques, and a judge decides. Debate can catch errors on high-stakes, low-volume paths, but it can also amplify shared blind spots at 2–3× token cost — always benchmark against a single-agent baseline.
- **Handoff:** pass a concise serialized state summary from one specialist stage to the next so each stage keeps a small, focused context and minimal tool permissions.

### Memory Tiers

Do not stuff the entire raw history into every prompt step. Separate memory by lifetime:

| Tier | What it stores | Lifetime | How it works |
| ------------------------ | ------------------------------------------------ | -------------- | ------------------------------------------------------------------------ |
| **Scratchpad (working)** | Current goal, constraints, recent observations | One run | Typed state object, compacted when observations grow stale |
| **Vector store** | Distilled facts, past solutions, domain corpus | Weeks–forever | Embedded chunks retrieved via hybrid search (→ 20.12.03) |
| **Episodic log** | Full past run trajectories, outcomes, failures | Months | Append-only log keyed by task type; retrieved as few-shot hints or evals |

### Evaluating Agents: Trajectory Evals

For agents, grading only the final answer misses loops that stumbled into the right answer after twelve wasted calls or touched a forbidden tool along the way. Measure both **outcome** and **trajectory**:

- **Outcome metrics:** task success rate (human- or rubric-graded) and factual groundedness.
- **Trajectory metrics:** step count vs reference baseline, redundant or duplicate tool calls, illegal tool sequences, per-step tool accuracy, and recovery after injected tool errors.
- **Failure injection:** deliberately inject timeouts, empty results, and HTTP 500s in staging to prove the agent degrades gracefully instead of spiraling.

### Four Classic Agent Failure Modes

- **Tool error cascades:** a flaky tool throws a raw stack trace → model misreads it → fires wrong compensating calls. *Fix:* typed error objects, circuit breakers, never pass raw traces as observations.
- **Context rot:** long runs pile up stale or contradictory tool outputs until early instructions fade. *Fix:* compact the scratchpad periodically, drop superseded outputs, and keep the immutable goal pinned in every planning prompt.
- **Goal drift:** after several retries, the agent starts solving a side problem instead of the user's request. *Fix:* store the original goal in an immutable state field restated on every turn.
- **Spinning:** calling the same `(tool, args)` repeatedly with identical results. *Fix:* track call signatures and halt or force a replan when state does not change.

## 2. Where Orchestration Patterns Fit

| Workflow | Recommended orchestration boundary |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Support refund request | Read policy and eligibility first; validate and execute the refund idempotently on the server; gate above-threshold amounts on human review |
| Code migration assistant | Let tools inspect files, propose patches, and run tests; keep repository commits behind human review |
| On-call investigation | Grant read-only metrics and log tools with a tight deadline; return evidence and a proposed fix rather than production write access |

## 3. Operational Invariants

- Count every inference turn and every proposed tool call (including invalid or unknown ones) against hard budgets; reserve financial spend before each call.
- Give every tool a narrow schema, server-side authorization, timeout, typed error contract, and bounded response size; mutations also require idempotency keys and reconciliation.
- Stop on completion, budget exhaustion, deadline, or non-progress, and return an explicit `halted` status when stopped by a guard.
- Checkpoint only the minimal state needed to resume, apply access and retention rules to stored traces, and remember that a graph checkpoint never makes an external write idempotent.
- Benchmark multi-agent or debate patterns against a simpler single-agent baseline before paying their latency and token cost.

## Code Examples

`runAgent` below is self-contained JavaScript you can run directly. The parallel runner and trajectory scorer are adapter sketches illustrating concurrency and eval metrics.

### An executable control loop with injected read tools

This loop enforces turn limits, call limits, a wall-clock `AbortSignal.timeout`, and byte caps on both model outputs and tool observations. Notice that unknown or failing tools still consume the turn and call budgets, and duplicate call IDs halt the run rather than attaching a result to the wrong call:

```javascript
export async function runAgent(model, tools, limits) {
  const { maxTurns, maxCalls, timeoutMs, maxAnswerBytes, maxObservationBytes } = limits;
  for (const n of [maxTurns, maxCalls, timeoutMs, maxAnswerBytes, maxObservationBytes]) {
    if (!Number.isSafeInteger(n) || n < 1) throw new RangeError('invalid limit');
  }
  const signal = AbortSignal.timeout(timeoutMs);
  const observations = [];
  const ids = new Set();
  const withinBytes = (value, maxBytes) => {
    try {
      const encoded = JSON.stringify(value);
      return typeof encoded === 'string' && new TextEncoder().encode(encoded).byteLength <= maxBytes;
    } catch { return false; }
  };
  let calls = 0;
  for (let turn = 0; turn < maxTurns; turn++) {
    if (signal.aborted) return { status: 'halted', reason: 'deadline', observations };
    let step;
    try { step = await model(observations, signal); }
    catch { return { status: 'halted', reason: signal.aborted ? 'deadline' : 'provider_error', observations }; }
    if (signal.aborted) return { status: 'halted', reason: 'deadline', observations };
    if (!withinBytes(step, maxObservationBytes)) return { status: 'halted', reason: 'model_output_too_large', observations };
    if (step?.kind === 'answer' && typeof step.text === 'string') {
      if (!withinBytes(step.text, maxAnswerBytes)) return { status: 'halted', reason: 'answer_too_large', observations };
      return { status: 'done', answer: step.text, observations };
    }
    if (step?.kind !== 'calls' || !Array.isArray(step.calls) || step.calls.length === 0) {
      return { status: 'halted', reason: 'invalid_step', observations };
    }
    for (const call of step.calls) {
      if (++calls > maxCalls) return { status: 'halted', reason: 'call_budget', observations };
      if (!call || typeof call.id !== 'string' || call.id.length === 0 ||
          typeof call.name !== 'string' || ids.has(call.id)) {
        return { status: 'halted', reason: 'invalid_call_id', observations };
      }
      ids.add(call.id);
      const tool = Object.hasOwn(tools, call.name) ? tools[call.name] : undefined;
      let result;
      if (!tool) result = { ok: false, error: 'unknown_tool' };
      else {
        try {
          const value = await tool(call.args, signal);
          result = withinBytes(value, maxObservationBytes)
            ? { ok: true, value }
            : { ok: false, error: 'result_too_large_or_unserializable' };
        } catch { result = { ok: false, error: 'tool_failed' }; }
      }
      observations.push({ id: call.id, result });
      if (signal.aborted) return { status: 'halted', reason: 'deadline', observations };
    }
  }
  return { status: 'halted', reason: 'turn_budget', observations };
}
```

Important production boundaries beyond this local model:
- Each tool adapter must validate arguments, enforce caller authorization, honor `signal`, and bound database and API responses *before* allocating them in memory.
- For real spend limits, reserve a conservative token and cost estimate (including cached-input, cache-write, and reasoning categories) before **each** model call and settle actual usage once afterward.
- Preserve the provider's exact assistant tool-call messages paired with their tool results in your provider adapter — this local `observations` array is a simplified stand-in.

### Parallel read-tool execution with bounded concurrency

Use bounded worker concurrency for independent read-only calls, then restore the model's original call ordering. Keep mutating calls sequential behind authorization and idempotency checks:

```typescript
// agent/tools-parallel.ts
export async function runBatch(calls: ToolCall[], tools: Tool[], concurrency: number): Promise<Observation[]> {
  if (!Number.isSafeInteger(concurrency) || concurrency < 1) throw new RangeError("invalid concurrency");
  const queue = [...calls];
  const out: Observation[] = [];
  async function worker() {
    while (queue.length) {
      const call = queue.shift()!;
      const tool = tools.find(t => t.name === call.name);
      if (!tool) {
        out.push(toObservation(call, { ok: false, error: "unknown tool", retryable: false }));
        continue;
      }
      const parsed = tool.schema.safeParse(call.args);
      const result = parsed.success
        ? await tool.fn(parsed.data, AbortSignal.timeout(15_000)).catch(() =>
            ({ ok: false as const, error: "tool failed", retryable: true }))
        : { ok: false as const, error: "schema violation", retryable: false };
      out.push(toObservation(call, result));
    }
  }
  await Promise.all(Array.from({ length: Math.min(concurrency, calls.length) }, worker));
  return sortById(out, calls); // re-align with the model's original call order
}
```

### Trajectory evaluation harness

Replay the same golden tasks across prompt, model, or tool changes and log step-by-step traces so every score regression is inspectable:

```typescript
// eval/trajectory.ts
type Episode = { steps: StepRecord[]; outcome: "success" | "fail"; costUsd: number };

function scoreEpisode(ep: Episode, expected: GoldenCase) {
  const toolSteps = ep.steps.filter(s => s.kind === "tool");
  const duplicateCalls = toolSteps.length - new Set(toolSteps.map(s => s.signature)).size;
  return {
    success: ep.outcome === "success",
    steps: ep.steps.length,
    stepRatio: ep.steps.length / Math.max(expected.referenceSteps, 1),
    redundantCallRatio: duplicateCalls / Math.max(toolSteps.length, 1),
    costUsd: ep.costUsd,
    usedForbiddenTool: ep.steps.some(s => s.tool && expected.forbidden.includes(s.tool)),
  };
}
```

## Summary

An agent is a model inside an application-owned decision → action → observation loop. Your orchestrator owns tool schemas, user authorization, state transitions, step, cost, and time budgets, and recovery. Use MCP to standardize tool connections without mistaking discovery for trust, and add graph persistence or multi-agent topologies only when evals show the extra complexity pays off.

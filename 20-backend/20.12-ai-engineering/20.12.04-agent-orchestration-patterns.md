# Agent Orchestration Patterns

> **TL;DR:** An agent is an LLM in a loop with tools — which means the hard engineering is not prompting, it's *bounding the loop*: stopping criteria, step budgets, token budgets, and circuit breakers on runaway agents. Orchestration is choosing the right control topology — a hand-rolled state machine, a LangGraph-style graph, a supervisor/worker fleet — and the right memory tier (scratchpad vs vector store vs episodic store). You evaluate agents on trajectories (did it take sane steps?), not just final answers, and you design for failure modes up front: tool error cascades and context rot kill more agents than bad models do.
>
> **Why it matters:** Single-shot LLM calls are commodities; agents are where senior candidates get grilled. Interviewers probe exactly the seams this chapter covers: "how do you stop an infinite loop?", "what happens when a tool starts returning 500s mid-run?", "how do you test nondeterministic multi-step behavior?" Your Docita credit-guard story maps directly onto loop-cost guards here.

## Definition

An **agent** is a system where an LLM decides *actions* (usually tool calls) iteratively toward a goal, observing results between rounds. An **orchestration layer** owns that iteration: it enforces control flow (steps, branches, termination), budgets (tokens, time, cost), and coordination between multiple agents or tools.

```text
            ┌────────────────────────────────────────────┐
            │              ORCHESTRATOR                  │
            │   state · budgets · guards · memory        │
            └──────┬─────────────────────▲───────────────┘
                   │ prompt + history    │ observations                
                   ▼                     │
              ┌─────────┐          ┌──────────┐
              │   LLM   │ ───────► │  TOOLS   │──► external world
              └─────────┘ thought/ └──────────┘      (APIs, DBs,
                 ▲       action                       search, code)
                 │
            plan → act → observe → (repeat until DONE | guard trips)
```

## Why Do We Need It?

1. **LLMs don't know when to stop** — left unguarded, an agent will re-plan forever, retry a failing tool indefinitely, or burn your API budget at 3 a.m. Termination must be engineered, not hoped for.
2. **Single-agent loops don't scale to complex workflows** — research + write + review have different tools, prompts, and risk profiles; topologies (supervisor/worker, handoff) decompose the problem.
3. **Control flow needs determinism somewhere** — you cannot ship a workflow whose branching lives entirely inside probabilistic model output; graphs/state machines give you auditable, testable structure around stochastic decisions.
4. **Cost compounds multiplicatively** — every extra step multiplies tokens × calls × latency; without explicit budgets, agent features are unshippable in production (see Safety, Cost & Governance).
5. **Failures cascade** — a tool returning garbage gets absorbed into context, poisoning every subsequent decision ("context rot"); orchestration must detect and quarantine degradation.
6. **Nondeterminism demands new eval methods** — unit tests on outputs don't work when the path varies; trajectory evaluation (step quality, tool-choice correctness, efficiency) is how agentic systems get tested.

## How It Works

### Anatomy of the plan-act-observe loop (ReAct)

The canonical agent loop interleaves reasoning traces (**Thought**) with **Action** (tool invocation) and **Observation** (tool result), until the model emits a terminal answer:

```text
Iteration 1: Thought: I need the user's latest invoice first
             Action:  invoices.get(user_id="u_42")
             Observation: { id: "INV-2026-00317", total: 129.00, status: "open" }
Iteration 2: Thought: Invoice is open; check refund eligibility rules
             Action:  policy.search("refund window open invoice")
             Observation: "Refunds allowed within 14 days of charge ..."
Iteration 3: Thought: Eligible → issue refund and summarize
             Action:  refunds.create(invoice_id="INV-2026-00317")
             Observation: { refund_id: "rf_991", status: "pending" }
Final:       Answer: Refund rf_991 issued for INV-2026-00317 ...
```

The orchestration layer — not the model — parses actions, executes tools, appends observations, checks guards, and decides whether another iteration may start.

### Stopping criteria and max-step guards

Layer multiple independent stops; any single signal firing halts the run:

| Guard                | Trigger                                            | Rationale                         |
| -------------------- | -------------------------------------------------- | --------------------------------- |
| Terminal action      | Model emits `final_answer` / `DONE`                | Happy path                        |
| Max steps            | `iteration >= N` (typical 8–25 by task class)      | Hard ceiling on loops             |
| Token budget         | cumulative tokens > B                              | Cost ceiling independent of steps |
| Wall-clock deadline  | elapsed > T (e.g., 60 s interactive, 10 min batch) | Latency SLOs                      |
| No-progress detector | same tool+args repeated k times                    | Detects spinning                  |
| Confidence gate      | self-check score < threshold                       | Quality floor before shipping     |

On guard trip: return best-effort partial result plus a structured `stopped_reason` — never silently truncate into a confident-sounding hallucination.

### Loop-cost guards (runaway-agent defense)

Treat an agent like an untrusted worker process: sandbox it with budgets and a circuit breaker.

- **Step budget** per run AND per user session (an agent that restarts itself can still multiply).
- **Token/cost budget** enforced *before* each LLM call — reject the call, not after billing.
- **Circuit breaker** per tool: after M consecutive failures, open the circuit, inject "this tool is unavailable" as observation, let the planner route around it instead of hammering.
- **Rate limiter** per tool target so parallel agents can't DDoS your own downstream services.
- **Kill switch**: feature-flag off at the gateway level (Docita's `AI_EXTERNAL_ENABLED` pattern).

### State machines vs graph orchestration (LangGraph-style)

Two dominant ways to make control flow inspectable:

| Aspect                    | Hand-rolled state machine           | Graph framework (LangGraph et al.)                      |
| ------------------------- | ----------------------------------- | ------------------------------------------------------- |
| Mental model              | Explicit states + transition guards | Nodes = steps; edges = conditional routing              |
| Determinism               | You own every branch                | Framework serializes state transitions                  |
| Persistence/checkpointing | Build yourself (save state JSON)    | Built-in: checkpoint per super-step, resume after crash |
| Human-in-the-loop         | Ad hoc                              | Interrupt-before-node primitives                        |
| Multi-agent               | DIY message passing                 | First-class subgraphs, supervisor nodes                 |
| Cost                      | Zero deps, fits simple flows        | Learning curve + version churn                          |

Rule of thumb: ≤ 4 states and one tool domain → plain state machine; branching workflows needing replay/resume/human approval → graph runtime.

```text
GRAPH VIEW (LangGraph-style)          STATE MACHINE VIEW
                                      ┌─────────┐
 START ──► classify ──► retrieve       │ state:  │ event/guard
             │           │             │ IDLE →  │ ──► PLANNING
             │ no docs   ▼             │         │ ──► ACTING
             └──────► respond ◄── grade│         │ ──► OBSERVING ─┐
                        │        │     └─────────┘ ◄── retry(≤2) ─┘                
                        ▼        ▼ rewrite
                      END     retrieve
```

Both encode the same invariant: transitions happen in *your* code after guards pass — the LLM proposes, the graph disposes.

### Tool-calling patterns

- **Parallel tool calls**: model returns several independent invocations in one turn (e.g., fetch weather AND calendar); execute concurrently with bounded concurrency and merge ordered observations. Big latency win; only valid when calls are side-effect-free or commutative.
- **Chained (sequential) calls**: output of tool A feeds arguments of tool B (`search → pick_id → fetch_detail`); inherently sequential, keep dependency explicit in the scratchpad.
- **Mixed plans**: modern models emit a batch where some calls depend on earlier results — the orchestrator must topologically sort the batch and interleave.
- **Validation boundary**: schema-check every argument against the tool contract before execution; reject with a corrective observation rather than throwing raw errors into context.

### Multi-agent topologies

```text
SUPERVISOR / WORKER                DEBATE                    HANDOFF (pipeline)
                                   ┌────────┐  critique
        ┌──────────┐               ▼        ▼  exchange        A ──handoff──► B ──► C
   ┌──► │ Worker A │ research   proposer  critic              (transfer state +
   │    └──────────┘               └───┬────┘                    ownership)
supervisor                           judge/arbitrator
   │    ┌──────────┐
   └──► │ Worker B │ coding       Use when: adversarial      Use when: distinct
        └──────────┘               quality matters and        competencies/domains;
   Routes tasks, merges results    cost is secondary          each stage owns its tools
```

- **Supervisor/worker**: router agent delegates to specialist agents; best cost/quality balance for broad task spaces. Failure domain: supervisor becomes a bottleneck/single point of confusion — cap its context.
- **Debate / generator-critic**: two or more agents argue, a judge (or the same model with a rubric) decides. Lifts reasoning quality on hard judgments; multiplies token cost 3–10× — reserve for high-stakes low-volume paths.
- **Handoff**: agent-to-agent transfer with explicit state serialization (like warm transfers in call centers); the receiving agent re-plans from the handed summary, keeping each context small and focused.

### Memory tiers

| Tier                    | What it holds                                     | Lifetime      | Implementation                                                                                                     |
| ----------------------- | ------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------ |
| Scratchpad (working)    | Current plan, thoughts, recent observations       | One run       | Messages array / typed state object, truncated by recency+relevance                                                |
| Vector store (semantic) | Distilled facts, past solutions, corpus knowledge | Weeks–forever | Embeddings + ANN retrieval (see Retrieval Quality chapter)                                                         |
| Episodic                | Full trajectories of past runs, outcomes, lessons | Months        | Append-only log keyed by task type; retrieved as few-shot exemplars or "last time you tried X and it failed" hints |

Escalation rule: scratchpad first; promote durable facts to vector store at run end (a summarizer writes them); archive the whole episode for evals and episodic recall. Never dump the entire history into context every step — that is how context rot begins.

### Evaluating agentic systems: trajectory evals

Judge the *path*, not just the destination:

- **Outcome metrics**: task success rate (human- or judge-graded), groundedness of final answer.
- **Trajectory metrics**: number of steps vs reference-efficient baseline; redundant/duplicate tool calls; illegal tool sequences; tool-choice accuracy per step; recovery quality after injected failures.
- **Method**: record full traces (steps, prompts, tool i/o, costs) to a store; replay golden tasks on every prompt/model/tool change; LLM-as-judge scores each step with a rubric; regression-gate like any CI metric (see Prompts, Context & Evals).
- **Failure injection**: deliberately break a tool (latency spike, empty result, 500) in staging and assert the agent degrades gracefully — this is the agent equivalent of chaos testing.

### Failure modes to design against

- **Tool error cascades**: one flaky tool fails → error string enters context → model misreads it as signal → wrong next action → compensating wrong calls. Fix: typed errors, circuit breakers, and never letting raw stack traces become observations.
- **Context rot**: long runs accumulate stale, contradictory, or verbose observations; attention dilutes and early instructions decay. Fix: periodic summarization/compaction of the scratchpad, drop superseded observations, re-inject the original goal every K steps.
- **Goal drift / loss**: after many edits the agent optimizes a mutated version of the objective. Fix: immutable goal field in state, restated verbatim in each planning prompt.
- **Looping**: same (tool, args) repeatedly. Fix: no-progress detectors + escalating temperature/diverse replan prompts.

## Code Examples

### Guarded ReAct loop in TypeScript (pseudocode)

```typescript
// agent/react-loop.ts
type Tool = {
  name: string;
  description: string;
  schema: z.ZodTypeAny;                          // args contract
  fn: (args: unknown) => Promise<ToolResult>;
};

type ToolResult =
  | { ok: true; value: unknown }
  | { ok: false; error: string; retryable: boolean };

type AgentState = {
  goal: string;                                  // IMMUTABLE — re-stated every step
  messages: ChatMessage[];                       // scratchpad
  step: number;
  tokensUsed: number;
  lastCalls: string[];                           // signature of last calls, for loop detect
};

type Limits = {
  maxSteps: number;                              // e.g. 12
  maxTokens: number;                             // e.g. 40_000
  deadlineMs: number;                            // e.g. 90_000
  maxRepeatCalls: number;                        // no-progress threshold, e.g. 2
};

const TERMINAL = "final_answer";

export async function runAgent(
  goal: string,
  tools: Tool[],
  llm: LlmClient,
  limits: Limits,
): Promise<AgentRunResult> {
  const startedAt = Date.now();
  const state: AgentState = { goal, messages: [systemPrompt(tools)], step: 0, tokensUsed: 0, lastCalls: [] };
  const breaker = new CircuitBreaker(tools.length ? Object.fromEntries(tools.map(t => [t.name, { fails: 0, open: false }])) : {});

  while (state.step < limits.maxSteps) {
    // ---- Budget gates BEFORE spending -------------------------------------
    if (state.tokensUsed >= limits.maxTokens) return halt(state, "token_budget");
    if (Date.now() - startedAt >= limits.deadlineMs) return halt(state, "deadline");

    // ---- Plan/Act: ask the model for the next action ----------------------
    state.messages.push(systemReminder(state.goal));               // fight goal drift
    const completion = await llm.chat({
      messages: compact(state.messages),                           // context-rot defense
      tools: toolSpecs(tools.filter(t => !breaker.isOpen(t.name))),// hide broken tools
    });
    state.tokensUsed += usage(completion);

    const call = parseToolCall(completion);
    if (!call || call.name === TERMINAL) {
      return { status: "done", answer: extractAnswer(completion), trace: state };
    }

    // ---- No-progress detector --------------------------------------------
    const sig = `${call.name}:${stableJson(call.args)}`;
    if (state.lastCalls.slice(-limits.maxRepeatCalls).filter(s => s === sig).length >= limits.maxRepeatCalls) {
      state.messages.push(observation(sig, { error: "Repeated identical call detected — change approach." }));
      state.messages.push({ role: "user", content: "You are looping. Re-plan from the original goal." });
      continue;
    }
    state.lastCalls.push(sig);
    state.step += 1;

    // ---- Observe: execute with validation, timeout, circuit breaking ------
    const tool = tools.find(t => t.name === call.name);
    if (!tool) {
      state.messages.push(toolError(call.name, "Unknown tool"));   // typed, not thrown
      continue;
    }
    const parsed = tool.schema.safeParse(call.args);
    if (!parsed.success) {
      state.messages.push(toolError(call.name, `Invalid args: ${parsed.error.message}`));
      continue;
    }
    if (breaker.isOpen(call.name)) {
      state.messages.push(toolError(call.name, "Temporarily unavailable; choose another path."));
      continue;
    }

    try {
      const result = await withTimeout(tool.fn(parsed.data), 15_000);
      breaker.recordSuccess(call.name);
      state.messages.push(observation(sig, result.ok ? result.value : { error: result.error }));
      if (!result.ok && !result.retryable) breaker.recordFailure(call.name);
    } catch (e) {
      breaker.recordFailure(call.name);
      state.messages.push(toolError(call.name, e instanceof Error ? e.message.slice(0, 300) : "failed"));
    }
  }
  return halt(state, "max_steps");
}

function halt(state: AgentState, reason: string): AgentRunResult {
  return { status: "halted", stoppedReason: reason, partial: summarize(state), trace: state };
}
```

Every guard from this chapter appears once, in the only place it belongs: the loop.

### Parallel tool execution with bounded concurrency

```typescript
// agent/tools-parallel.ts
export async function runBatch(calls: ToolCall[], tools: Tool[], concurrency = 4): Promise<Observation[]> {
  const queue = [...calls];
  const out: Observation[] = [];
  async function worker() {
    while (queue.length) {
      const call = queue.shift()!;
      const tool = tools.find(t => t.name === call.name)!;
      const parsed = tool.schema.safeParse(call.args);
      const result = parsed.success
        ? await withTimeout(tool.fn(parsed.data), 15_000)
        : { ok: false as const, error: "schema violation", retryable: false };
      out.push(toObservation(call, result));       // order preserved via index below
    }
  }
  await Promise.all(Array.from({ length: Math.min(concurrency, calls.length) }, worker));
  return sortById(out, calls);                     // re-align with model's ordering
}
```

Parallelize only independent, read-only calls; anything mutating stays sequential behind the supervisor's validation gate.

### LangGraph-style graph skeleton (framework-agnostic TypeScript)

```typescript
// agent/graph.ts
type NodeFn = (s: GraphState) => Promise<Partial<GraphState>>;
const graph = new Graph<GraphState>()
  .addNode("classify", classifyQuery)
  .addNode("retrieve", retrieveDocs)
  .addNode("grade", gradeDocuments)
  .addNode("rewrite", rewriteQuery)
  .addNode("respond", generateAnswer)
  .addEdge(START, "classify")
  .addEdge("classify", "retrieve")
  .addConditionalEdge("grade", (s) =>
    s.documents.length > 0 ? "respond" : "rewrite")   // guard lives HERE, in code
  .addEdge("rewrite", "retrieve")
  .addEdge("respond", END)
  .compile({ checkpoint: postgresCheckpointer });     // resume after crash/approval

const out = await graph.invoke({ question }, { configurable: { thread_id: caseId } });
```

Conditional edges are the deterministic seam: the model may propose, but the edge function — reviewed, tested, logged — decides the next node.

### Trajectory evaluation harness

```typescript
// eval/trajectory.ts
type Episode = { steps: StepRecord[]; outcome: "success" | "fail"; costUsd: number };

function scoreEpisode(ep: Episode, expected: GoldenCase) {
  const duplicateCalls = ep.steps.length -
    new Set(ep.steps.filter(s => s.kind === "tool").map(s => s.signature)).size;
  return {
    success: ep.outcome === "success",
    steps: ep.steps.length,
    efficiency: expected.referenceSteps / ep.steps.length,   // closer to 1 = tighter path
    redundantCallRatio: duplicateCalls / Math.max(ep.steps.length, 1),
    costUsd: ep.costUsd,
    usedForbiddenTool: ep.steps.some(s => s.tool && expected.forbidden.includes(s.tool)),
  };
}

// CI gate: fail when success rate drops >2pts OR median steps grows >25% vs stored baseline
```

Replay the same golden task suite across prompt/model changes; store traces so any score is explainable step-by-step.

## Real-World Use Cases

1. **Customer-support resolution agent** — supervisor routes billing vs technical intents; billing worker chains `orders.get → refunds.eligibility → refunds.create`; refund-mutation tools sit behind a human-approval interrupt node; step budget 10, token budget 30k, hard wall clock 45 s.
2. **Codebase migration agent** — plan (find usages) → act (codemod tool) → observe (diff + tests) loops; test-runner circuit breaker opens after 3 consecutive infra failures so the agent reports blocked instead of thrashing; episodic memory stores prior migration recipes.
3. **Research/deep-dive assistant** — parallel web-search + internal-wiki fan-out per question, debate topology (proposer vs skeptic) before citing; trajectory evals track "redundant search ratio" as the key efficiency metric.
4. **Data-pipeline repair agent (on-call)** — reads alert, queries dashboards, proposes fix PR; forbidden-tools list excludes prod mutation endpoints; every run's trace lands in episodic store for postmortem learning.
5. **Sales-outreach drafter** — handoff pipeline: prospect-researcher agent hands a structured brief to copywriter agent, which hands to compliance-checker agent; each keeps its own small context and toolset — no single mega-context to rot.

## Common Mistakes

| Mistake                                              | Fix                                                                                                   |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| No step/token ceiling because "the model is smart"   | Every loop ships with maxSteps + token budget + deadline wired to alerts                              |
| Raw exceptions pushed into context as observations   | Typed `{ ok: false, error, retryable }` results; sanitize/truncate messages                           |
| Retrying failing tools inline forever                | Per-tool circuit breaker + retryable flag respected by the planner                                    |
| Letting history grow monotonically all run           | Compact/summarize scratchpad; drop superseded observations; restate goal                              |
| Branching logic buried inside free-text model output | Conditional edges / state-machine transitions in reviewed code                                        |
| Testing only final answers                           | Trajectory evals: steps, duplicates, forbidden tools, recovery-after-failure                          |
| Parallel calls on mutating tools                     | Parallelize read-only batches only; serialize side effects behind validation                          |
| One mega-agent with 30 tools                         | Decompose into specialists (supervisor/handoff); fewer tools per decision improves selection accuracy |
| Memory = paste everything into context               | Tiered memory: scratchpad now, vector store for facts, episodic for lessons                           |
| Ignoring cost per resolved task                      | Track USD/successful-task as a first-class SLO next to latency                                        |

## Best Practices

1. **Design the loop before the prompt**: enumerate states, guards, budgets, and terminal conditions first; prompts fill the slots afterward.
2. **Defense in depth on termination**: terminal action + max steps + token budget + deadline + no-progress detection, each independently sufficient.
3. **Make tools boring contracts**: strict schemas, timeouts, typed errors, idempotency keys on mutations — the agent inherits reliability from its tools.
4. **Prefer few well-described tools per agent**; split into supervisor/worker or handoff topologies when tool count passes roughly 10–15.
5. **Checkpoint state every super-step** (graph runtimes make this cheap) so crashes, approvals, and long jobs resume instead of restart.
6. **Compact context proactively**: summarize when scratchpad exceeds ~50% of budget; re-inject the immutable goal each planning step.
7. **Gate deploys on trajectory metrics** like any other CI signal; keep a stored baseline JSON and diff on PRs.
8. **Chaos-test the tools**: inject failures in staging and assert graceful degradation — the mark of a production agent, not a demo.
9. **Log every step with cost attribution** (tokens, USD, latency per step) — you cannot tune what you cannot see.

## Performance Considerations

- Latency is dominated by sequential LLM round trips: each act-observe cycle pays full inference + tool time; parallel tool batches and streaming cut wall clock substantially.
- Context length is a hidden perf lever: doubling scratchpad size roughly doubles prefill cost per step — compaction is a performance feature, not just hygiene.
- Small models fine-tuned or well-prompted for tool selection often beat frontier models per-dollar inside fixed graphs; reserve big models for planning nodes.
- Cache identical (model, messages-prefix) calls during development replays; trajectory eval suites get 5–10× cheaper with prefix caching.
- Measure p95 per-phase (plan ms, tool ms, total steps distribution) separately — aggregate "agent latency" hides whether to optimize prompts, tools, or topology.

## Summary

- An agent = LLM + tools + a loop owned by *your* orchestration code; the loop's guards are the product.
- Stop conditions come in layers (terminal, steps, tokens, deadline, repetition); halting must produce structured partial results, never silent truncation.
- Choose topology honestly: state machine for small flows, graph runtime when you need checkpoint/resume/approvals, supervisor-worker or handoff when domains diverge, debate only where quality justifies 3–10× token cost.
- Memory is tiered — scratchpad, semantic store, episodic log — with promotion rules, not an ever-growing transcript.
- Evaluate trajectories (step efficiency, tool choice, failure recovery) alongside outcomes, and chaos-test tool failures before users do.
- Runaway-agent protection (budgets, breakers, kill switches) turns demos into shippable features.

| -------------------- | ------------------------------------------------------------------------ |

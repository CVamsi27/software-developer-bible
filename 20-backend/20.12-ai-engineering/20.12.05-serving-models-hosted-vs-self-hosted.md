# Serving Models — Hosted APIs vs Self-Hosted

>
> **Why it matters:** Hosted and self-hosted inference place different costs, data paths, and operational duties on the application team. Compare them against the workload and its data policy, then measure the path you choose.

## Definition

**Hosted serving**: a provider operates the inference runtime and exposes it through an API. The application team still owns integration, security, data classification, authorization, reliability, and verification of the provider's applicable processing and retention terms.

> **Textbook Definition:** Model serving exposes inference through a runtime that schedules model execution and manages capacity. Hosted serving delegates runtime operation to a provider; self-hosting assigns infrastructure, model deployment and operational responsibility to the consuming organization.

**Self-hosting**: you run open-weight model binaries on your own (or cloud-tenant) GPUs behind an inference server (vLLM, TGI, SGLang); you own deployment, capacity, upgrades and the configured data/telemetry paths.

```text
HOSTED                                SELF-HOSTED
app ──► api.vendor.com ──► their GPUs app ──► your LB ──► vLLM pods ──► your GPUs
        (data crosses boundary)              (verify all egress, logs, storage and administration)
control: prompt + params + contract   control: weights, quantization,
                                       batching, region, everything
```

## First Principles

Serving decisions follow from the ownership-vs-economics trade:

1. **The serving boundary changes who operates what.** A hosted provider runs inference infrastructure; your team still integrates and governs the service. With self-hosting, your team also operates capacity, model releases, and serving infrastructure. In both cases, evaluate model quality and data handling for the actual workload.
2. **Inference cost follows hardware and pricing constraints**: GPU memory limits the active workload; batching changes throughput and queueing; utilization shapes cost per token. Self-hosted operators tune memory, batching and cache behavior, while hosted users compare provider pricing and eligible discounts (see [LLM App Architecture](20.12.01-llm-app-architecture.md)).
3. **An internal interface can reduce coupling** (see [LLM App Architecture](20.12.01-llm-app-architecture.md)), but it cannot make provider capabilities, pricing, data policies, or failure behavior identical. Keep provider-specific options explicit and test each supported implementation.

## Compare the workload

### Decision matrix

| Dimension | Hosted API | Self-hosted open weights |
| --------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Time to first token shipped | Depends on integration | Depends on existing infrastructure, evals and controls |
| Quality | Compare the selected hosted deployment on the task eval set | Compare eligible open-weight models on the same task eval set |
| Unit economics | Provider pricing and discounts; calculate from current usage categories | Capacity, utilization, operations, and support; calculate from measured load |
| Latency p95 | Network + provider queue variance | Tunable; measure queueing and mixed-load tail latency |
| Data handling and transfers | Verify endpoint region, processing, retention, access, and transfer terms for the data class | Verify telemetry, storage, administration, network paths, and dependencies |
| Control over serving | API parameters and provider-supported options | Runtime, quantization, batching, scheduling, and cache configuration |
| Ops burden | Provider-operated inference; your integration, security, and governance remain | GPUs, drivers, CUDA versions, scaling, upgrades, on-call |
| Model lifecycle | Follow the provider's version and deprecation policy | Choose upgrade timing where weights/runtime can be pinned; re-evaluate changes |
| Assurance evidence | Review provider controls and endpoint terms | Operate and evidence your own controls; deployment control alone does not establish compliance |

A useful design summary: compare measured quality, full cost, latency, data policy, and the team's operational capacity for each workload class. GDPR Chapter V does not impose a blanket ban on transfers outside the EEA; a transfer needs an applicable legal mechanism and appropriate protection, alongside the other processing obligations.

### vLLM basics: PagedAttention and continuous batching

Two ideas make modern open-weight serving economically viable:

- **Paged KV-cache management** (introduced by PagedAttention): each sequence's attention history is stored in fixed-size blocks rather than one contiguous buffer sized to the maximum sequence length. This reduces fragmentation; reuse and throughput gains depend on the runtime, model and workload. vLLM's current kernels have evolved beyond the original PagedAttention paper, so verify details against the pinned release.
- **Continuous batching**: instead of waiting for a whole batch of requests to finish before admitting new ones (static batching), the scheduler admits new requests at every iteration boundary as others finish. GPU utilization stays high under mixed-length traffic.

```text
STATIC BATCHING                    CONTINUOUS BATCHING (vLLM)
t0 [A A A A]                       t0 [A A B C]
t1 [A A _ _]  ← idle slots waste   t1 [A A B C D]   ← D admitted as A/B finish
t2 [A _ _ _]     GPU cycles        t2 [A E F G D]   ← slots refilled each iter
t3 done → admit next batch         ...measure throughput and tail latency under the same workload/SLO
```

Also worth naming: **prefix caching** (reuse KV for eligible identical token prefixes), **chunked prefill**, speculative decoding, and tensor parallelism across GPUs for models larger than single-GPU VRAM.

### Quantization ladder

Weights stored at lower precision = less VRAM, faster memory-bound decode, some quality loss:

| Format | Bits/weight | ~Quality vs fp16 | Typical use |
| ------------------------------ | ----------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| fp32 | 32 | baseline (training) | Rarely served |
| fp16/bf16 | 16 | Different numeric ranges/precision; compare on the target task and runtime | Common serving choices where supported |
| int8 or FP8 (distinct formats) | 8 | Task/model/hardware-dependent; measure it | Use only with compatible kernels and hardware; benchmark the target workload |
| int4 GPTQ | 4 | Task/model/calibration dependent; measure quality and kernel support | May reduce weight memory; actual fit depends on runtime, KV cache, and GPU memory |
| int4 AWQ | 4 | Activation-aware calibration; quality depends on model/task/kernel | One quantization option; benchmark on the chosen runtime and task |

At the raw-weight level, four-bit weights use about one quarter of the storage of 16-bit weights. Quantization metadata, kernels, KV cache, and model quality change the actual footprint and behavior. Evaluate each task on the target runtime; no task category has a universal degradation threshold.

### GPU sizing rough math

```text
VRAM(model)  = params × bytes_per_weight          bf16: ×2,  int8: ×1,  int4: ×0.5
VRAM(KV)     = 2 × layers × kv_heads × head_dim × seq_len × batch × bytes
               (×2 because K and V; fp16 assumed)
Total        = weights + peak KV cache + runtime/workspace overhead (measure for the chosen stack)

Worked example — Llama-3.1 70B, 8k context, bf16:
  weights: 70e9 × 2 B            ≈ 140 GB (≈130.4 GiB) before quantization metadata and runtime overhead
  KV cache: 2 × 80 layers × 8 kv_heads × 128 head_dim × 8192 tok × 2 B × batch
          = 2.5 GiB per concurrent request (under these stated BF16 KV assumptions)
  → 20 such requests need about 50 GiB of KV cache plus 130.4 GiB of raw weights, before runtime overhead. Decimal GB and binary GiB are different units; this estimate does not establish whether a particular GPU layout will fit.
```

Do not infer fit from parameter count alone. Check the exact checkpoint, quantization format, runtime, GPU memory, context length, batching, and KV-cache budget, then load-test the intended concurrency.

### Throughput vs latency vocabulary

| Term | Meaning | Why it matters |
| ---------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------- |
| TTFT | Time To First Token — transport + queue + prefill + first decode | Perceived responsiveness; choose a product-specific target |
| TPOT / ITL | Time Per Output Token (inter-token latency) | Output cadence; tokenizer and rendering change perception |
| Prefill | Processing the prompt (compute-bound, parallel) | Dominated by input length; prefix caching cuts it |
| Decode | Generating tokens one-by-one (memory-bandwidth-bound) | Dominated by output length × TPOT |
| Throughput | Tokens/sec aggregate across all users | Cost efficiency metric; batching raises it |
| Goodput | Throughput measured only on requests meeting SLO | What you actually sell; vLLM benchmarks report it |

The tension: larger admitted batches can raise throughput while increasing queueing/decode latency; the curve depends on workload and scheduler — SLO-aware schedulers maximize goodput, not raw throughput.

### Routing and fallback across providers

Production clients treat model providers like any unreliable dependency:

```text
request ──► router ──► policy select ──► primary (hosted-A)
              │            │                │ fail/timeout/429?
              │            │                ▼
              │            │           fallback (hosted-B)
              │            │                │ fail?
              │            │                ▼
              │            │           self-hosted vLLM (degraded-but-alive tier)
              │            ▼
              └──► authoritative data class restricts approved endpoints
                   optional detector may tighten the class, never relax it;
                   availability chooses only among approved endpoints
```

Key mechanics: health-aware pools, hedging (duplicate slow requests), retry budgets, response-schema compatibility checks across models (structured outputs differ!), and cost-aware routing (route by measured task class; use only calibrated escalation signals).

### Self-host operational realities

- **Cold GPUs**: scale-from-zero can be slow because images and weights must load into memory; measure cold-start time, keep a warm floor if the SLO requires it, and autoscale on workload-relevant signals such as queue depth.
- **Capacity planning**: KV cache can cap concurrency; include realistic high-context requests in sizing; load-test with realistic mixed lengths.
- **Model updates**: new checkpoint ≠ drop-in — rerun evals, shadow-test against current, canary by traffic slice; keep rollback images.
- **Driver/CUDA/version matrix**: pin compatible components and validate upgrades in staging; driver/runtime mismatches can prevent model workers from starting.
- **Multi-tenancy**: one GPU pool, many models — swap-in-time costs (model reload) vs memory (co-resident LoRA adapters are cheap; full models are not).
- **Observability**: tokens/sec, TTFT/TPOT histograms, KV-cache eviction rate, queue depth, goodput per SLO class.

### Combining serving paths

1. **Different serving paths by data class**: authoritative application classification restricts which endpoints are eligible; an auxiliary detector may tighten the restriction but cannot relax it. Verify each endpoint and its processing terms before enabling the route.
2. **Hosted primary, self-hosted fallback**: open-weight tier keeps you alive through provider outages and rate-limit storms.
3. **Self-hosted bulk, hosted premium**: routine summarization/extraction on your GPUs; gnarly reasoning escalates to the frontier API.
4. **In-region managed endpoints**: hosted convenience may fit when the endpoint, processing terms, access paths, retention, and transfer mechanism satisfy the workload policy; a region label alone is not proof.

## Code Examples

### Provider router with fallback chains and data-class policy

```typescript
// llm/router.ts
type DataClass = "public" | "internal" | "personal" | "regulated";
type TaskClass = "general" | "regulated" | "background";
type CompletionRequest = { dataClass: DataClass; timeoutMs?: number; /* messages, model parameters, and request metadata */ };
type Provider = {
  name: string;
  approvedDataClasses: readonly DataClass[]; // verified policy, not a location nickname
  complete(req: CompletionRequest, signal: AbortSignal): Promise<CompletionResponse>;
};

type RoutePolicy = { primary: string; fallbacks: string[] };

const POLICIES: Record<TaskClass, RoutePolicy> = {
  general:    { primary: "openai-eu",  fallbacks: ["anthropic-eu", "vllm-self"] },
  regulated:  { primary: "vllm-self",  fallbacks: ["azure-openai-de"] },  // Illustrative names; actual policy must verify the endpoint contract
  background: { primary: "vllm-self",  fallbacks: ["openai-eu"] },        // cheap bulk tier
};

export async function complete(req: CompletionRequest & { taskClass: TaskClass }, callerSignal: AbortSignal): Promise<CompletionResponse> {
  const deadlineSignal = AbortSignal.timeout(req.timeoutMs ?? 30_000);
  const signal = AbortSignal.any([callerSignal, deadlineSignal]); // one deadline covers the whole fallback chain
  const policy = POLICIES[req.taskClass];
  const chain = [policy.primary, ...policy.fallbacks].map(n => {
    const provider = registry[n];
    if (!provider) throw new Error(`unknown provider ${n}`);
    return provider;
  });

  let lastError: unknown;
  for (const provider of chain) {
    if (signal.aborted) throw new Error("request cancelled or deadline exceeded");
    if (!provider.approvedDataClasses.includes(req.dataClass)) continue;   // hard residency gate
    const breaker = breakers.for(provider.name);
    if (breaker.isOpen()) continue;
    try {
      const res = await provider.complete(req, signal); // adapter must propagate cancellation
      breaker.recordSuccess();
      metrics.route(provider.name, req.taskClass);
      return res;
    } catch (e) {
      lastError = e;
      if (signal.aborted) throw e; // a caller cancel or total deadline must not try another provider
      const failure = classifyProviderError(e);
      if (!failure.retryable) throw e;
      breaker.recordFailure();                                      // count only classified retryable failures
      warn("provider_fallback", { provider: provider.name, err: failure.code }); // allowlisted fields only
    }
  }
  throw new AllProvidersFailedError(chain.map(p => p.name), lastError);
}
```

This is an adapter sketch. Apply authoritative data classification and a total deadline before routing. Each provider must honor cancellation; a Promise timeout alone leaves remote work running. Classify retryable failures, bound the fallback chain, and never automatically replay uncertain tool side effects. Names such as “EU” do not establish policy approval.

### OpenAI-compatible client pointed at self-hosted vLLM

```typescript
// llm/vllm-client.ts — vLLM speaks the OpenAI protocol, so the SDK just works
import OpenAI from "openai";

const local = new OpenAI({
  // Use a private, authenticated TLS endpoint in production; validate configuration before construction.
  baseURL: process.env.VLLM_BASE_URL!,
  apiKey: process.env.VLLM_API_KEY!,
});

export async function summarizeApprovedTicket(text: string): Promise<string> {
  const completion = await local.chat.completions.create({
    model: process.env.VLLM_SERVED_MODEL!, // advertised server name; pin weights at deployment
    messages: [
      { role: "system", content: "Summarize support tickets in <=3 sentences." },
      { role: "user", content: text },
    ],
    max_tokens: 200,
    temperature: 0.2,
  });
  return completion.choices[0]?.message?.content ?? "";
}
```

Compatibility is endpoint/model/runtime-specific. Verify chat templates, parameters, structured output, streaming, authentication and cancellation; an SDK type check alone does not prove compatibility.

### VRAM sizing calculator

```typescript
// llm/sizing.ts
type SizeInput = {
  paramsB: number;                 // e.g. 70 for 70B
  bitsPerWeight: 16 | 8 | 4;
  layers: number;
  kvHeads: number;                 // after GQA
  headDim: number;
  ctxLen: number;
  concurrency: number;
  gpuVramGiB: number; // all calculated capacities below use binary GiB
};

export function estimateVram(i: SizeInput) {
  if (Object.values(i).some(n => !Number.isFinite(n) || n <= 0) ||
      ![4, 8, 16].includes(i.bitsPerWeight) ||
      [i.layers, i.kvHeads, i.headDim, i.ctxLen, i.concurrency].some(n => !Number.isSafeInteger(n))) {
    throw new RangeError("invalid sizing inputs");
  }
  const round = (n: number) => Math.round(n * 100) / 100;
  const weightsGiB = (i.paramsB * 1e9 * i.bitsPerWeight / 8) / 1024 ** 3;
  const kvPerReqGiB =
    (2 * i.layers * i.kvHeads * i.headDim * i.ctxLen * 2 /*bytes per bf16 element; leading 2 counts K and V*/) /
    (1024 ** 3);
  const kvTotalGiB = kvPerReqGiB * i.concurrency;
  const overheadGiB = 2 + 0.10 * (weightsGiB + kvTotalGiB);          // CUDA + activations
  const totalGiB = weightsGiB + kvTotalGiB + overheadGiB;
  return {
    weightsGiB: round(weightsGiB),
    kvPerRequestGiB: round(kvPerReqGiB),
    totalGiB: round(totalGiB),
    fitsOneGpu: totalGiB <= i.gpuVramGiB,
    idealAggregateLowerBound: Math.ceil(totalGiB / i.gpuVramGiB) // not a deployability guarantee,
  };
}

// estimateVram({ paramsB: 70, bitsPerWeight: 4, layers: 80, kvHeads: 8,
//   headDim: 128, ctxLen: 8192, concurrency: 16, gpuVramGiB: 80 })
// → weights ≈ 33 GiB, KV ≈ 40 GiB, total ≈ 82 GiB → aggregate lower bound 2 GPUs (or cut context/concurrency)
```

### Deploying vLLM (the operational minimum)

```bash
# Set these to an eval-approved image digest, compatible model repository, and commit.
: "${VLLM_IMAGE:?pin vLLM image by digest}"
: "${MODEL_ID:?choose a supported model/checkpoint}"
: "${MODEL_REVISION:?pin the Hugging Face commit}"
: "${VLLM_API_KEY:?configure authentication}"
docker run --gpus all --ipc=host \
  -p 127.0.0.1:8000:8000 \
  -e VLLM_API_KEY \
  "$VLLM_IMAGE" \
  --model "$MODEL_ID" --revision "$MODEL_REVISION" \
  --tensor-parallel-size 2 --max-model-len 16384 \
  --gpu-memory-utilization 0.90 --enable-prefix-caching \
  --api-key "$VLLM_API_KEY"
```

The image entrypoint/flags, tensor-parallel compatibility, model licensing, tokenizer/chat template, and quantization kernels must be verified for the pinned release. The memory-utilization setting allocates a budget; it is not a proof against OOM. vLLM's API-key check covers only documented inference path prefixes, so keep the service private behind network policy and an authenticated TLS gateway; do not treat the built-in key as complete perimeter security. Multi-node vLLM communication is also insecure by default: isolate and firewall its internal network paths. This deployment sketch was not executed on GPU hardware.

Data classification is an eligibility gate, not a provider preference. Keep its authoritative derivation and the rule that a detector may only tighten policy in [Safety, Cost & Governance](20.12.06-safety-cost-governance.md); the serving router should choose availability only among already-approved endpoints.

## Real-World Use Cases

1. **Illustrative EU SaaS helpdesk** — classify ticket data and purpose from trusted application context, then allow only endpoints whose processing and transfer terms have been reviewed. A minimized interaction audit supports operations but is not a substitute for required records of processing activities.
2. **High-volume document pipeline** — compare provisioned GPU utilization, operations, and measured task quality against eligible hosted pricing; escalate only where the fallback clears the quality and policy bar.
3. **Real-time voice agent** — a product-specific TTFT budget motivates measuring serving location, model size, batching, and speculative decoding under realistic peaks; keep only changes that meet quality and latency targets.
4. **Startup MVP** — hosted inference may reduce initial infrastructure work. Revisit self-hosting when measured cost, data policy, latency, or reliability requirements justify the additional operating responsibility.
5. **Fintech on-call copilot** — hybrid #2: hosted primary for reasoning quality; an evaluated self-hosted fallback can reduce provider dependency; test its capacity and quality under the full outage load; circuit breakers shared with the orchestration layer.

## Decide and validate the serving path

For each workload, compare the same task evaluation across eligible models, then calculate full cost at measured utilization: hosted request categories or self-hosted hardware, idle capacity, operations, and upgrades. Set TTFT/TPOT and goodput targets from the product SLO, and load-test realistic prompt/output lengths before choosing batch size or concurrency. A model that fits by raw weight size may still exceed VRAM once KV cache, runtime workspaces, and headroom are included.

If self-hosting, pin compatible image, model revision, tokenizer/chat template, runtime, and hardware settings; verify licensing and endpoint authentication; shadow or canary upgrades against the same evaluation set and retain rollback artifacts. Quantization, prefix caching, speculative decoding, and routing are hypotheses to measure on the actual task and runtime, not automatic wins. A fallback is useful only when its data policy, quality, and outage capacity have been tested. Provider names or regions alone do not establish residency or transfer compliance; for EU workloads, assess the actual processing/transfer path and applicable legal mechanism with the responsible privacy/legal team.

## Summary

- The hosted-vs-self-hosted choice is per-workload, driven by four axes: unit economics at your volume, latency profile, data residency, and control/reproducibility.
- Data policy is workload-specific: GDPR transfer obligations, contractual residency, retention, access, and vendor terms must be assessed together; self-hosting alone is not compliance.
- vLLM uses paged KV-cache management and continuous batching to improve serving efficiency for suitable workloads; measure prefix caching and quantization on the actual model, runtime, and traffic mix.
- VRAM planning is arithmetic: `params × bytes` for weights plus KV cache at p99 context × concurrency — the KV term can be a major concurrency constraint.
- Speak the vocabulary fluently: TTFT/TPOT, prefill vs decode, throughput vs goodput; they map directly onto user-perceived quality and cost.
- A router with data-class gates and health-aware fallback can reduce reliance on one serving path when the fallback is independent, permitted, tested, and adequately sized. Record and evaluate model revisions wherever version pinning is available.

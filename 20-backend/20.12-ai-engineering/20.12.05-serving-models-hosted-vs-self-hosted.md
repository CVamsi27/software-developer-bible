# Serving Models — Hosted APIs vs Self-Hosted

Your team's monthly OpenAI bill just crossed €15,000, and someone suggests: *"Let's host an open-weight model on our own GPUs — it'll be cheaper and GDPR-compliant."* Before spinning up GPU nodes, do the full math: two 80 GiB GPUs running 24/7 plus on-call operations, cold-start buffering, and eval migrations can easily cost *more* than a hosted API at bursty traffic, and self-hosting alone does not establish compliance if logs or telemetry still leak sensitive data.

Deciding how to serve models is a per-workload engineering trade-off across quality, total cost, latency, data policy, and operational capacity.

---

## Definition

- **Hosted serving:** an external provider runs the GPU fleet and inference engine behind an API. You pay per token (or provisioned throughput), while still owning integration, data classification, authorization, reliability, and verifying the vendor's processing and retention terms.
- **Self-hosting:** you deploy open-weight models on your own or cloud-tenant GPUs using an inference server such as **vLLM**, **SGLang**, or **Hugging Face TGI**. You control weights, quantization, batching, and network boundaries — and you own GPU capacity, drivers, upgrades, and 3 a.m. incidents.

> **Textbook Definition:** Model serving exposes inference through a runtime that schedules model execution and manages capacity. Hosted serving delegates runtime operation to a provider; self-hosting assigns infrastructure, model deployment and operational responsibility to the consuming organization.

```text
HOSTED API                                    SELF-HOSTED OPEN WEIGHTS
app ──► api.vendor.com ──► vendor GPUs        app ──► internal LB ──► vLLM pods ──► your GPUs
        (data crosses org boundary)                   (control egress, logs & network policy)
control: prompt, params, endpoint contract    control: weights, quantization, batching, region
```

## First Principles

Three constraints govern almost every model-serving decision:

1. **Ownership shifts the failure surface, not the need for governance.** Hosted providers absorb GPU ops; self-hosting hands you driver matrices, scaling, and upgrades. Neither option exempts you from evaluating model quality on your task or enforcing data-access rules.
2. **Inference economics are GPU memory physics.** GPU VRAM limits how many requests can sit in memory at once; concurrency limits throughput; throughput determines cost per token. Self-hosters tune quantization, batching, and prefix caches directly; API consumers feel the same physics through prompt-caching and batch-API pricing tiers (→ 20.12.01).
3. **A common client interface reduces coupling, not differences.** Speaking an OpenAI-compatible HTTP shape makes switching easier (→ 20.12.02), but providers still differ in structured outputs, tool calling, streaming errors, pricing categories, and data retention. Test every supported backend explicitly.

## 1. Compare Hosted vs Self-Hosted on Your Workload

| Dimension | Hosted API | Self-hosted open weights |
| ------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| Time to ship | Fast — integrate SDK and controls | Slower — provision GPUs, serving runtime, autoscaling, and monitoring |
| Quality | Benchmark the target hosted model on your eval set | Benchmark eligible open-weight checkpoints on the same eval set |
| Unit economics | Pay per input/cached/output token; scales down to zero | Fixed GPU + idle-headroom + engineering-ops cost; wins at steady high load |
| Latency (p95) | Network hop + shared vendor queue variance | Tunable per SLO; still sensitive to local queue depth and long contexts |
| Data & transfer policy | Verify processing region, retention, subprocessors, and transfer terms | Verify network isolation, storage, logs, telemetry, and admin access |
| Serving control | API parameters and vendor options only | Full control over quantization, batching, prefix cache, and weight pinning |
| Operations | Vendor runs GPUs; you run integration, fallbacks, and governance | You run GPUs, CUDA/drivers, images, autoscaling, and on-call |
| Model lifecycle | Follow vendor deprecations and snapshot retirements | Pin exact weight revisions; re-evaluate before upgrading |

**EU / GDPR note:** GDPR Chapter V does not impose a blanket ban on transfers outside the EEA — transfers require a valid legal mechanism and safeguards alongside ordinary processing rules. Equally, an endpoint named "EU" or a self-hosted cluster does not automatically prove compliance; review the full data path with legal/privacy owners.

## 2. How Modern Serving Works: PagedAttention & Continuous Batching

Early inference servers wasted huge amounts of GPU memory and compute. Two mechanisms popularized by **vLLM** fixed that:

- **PagedAttention:** During generation, the model caches previous tokens' attention keys and values (the **KV cache**). Older servers reserved one giant contiguous block sized to `max_seq_len` for every request, wasting memory on short prompts. PagedAttention splits the KV cache into fixed-size blocks (just like OS virtual memory pages), slashing fragmentation and allowing requests that share a system prompt to share KV blocks.
- **Continuous batching:** With static batching, the GPU waits for the longest response in a batch to finish before starting new requests, leaving slots idle. Continuous batching checks after *every single generated token* and immediately fills any finished slot with a waiting request.

```text
STATIC BATCHING                       CONTINUOUS BATCHING (vLLM)
t0 [A A A A]                          t0 [A A B C]
t1 [A A _ _]  ← idle GPU slots        t1 [A A B C D]  ← D joins as soon as a slot frees
t2 [A _ _ _]    burn money            t2 [A E F G D]  ← slots refilled every iteration
t3 wait for A → admit next batch      (keeps GPU busy under mixed request lengths)
```

Other high-leverage serving features worth knowing: **prefix caching** (reuse KV blocks for identical prompt prefixes), **chunked prefill** (break huge prompts into slices so they don't stall active decodes), **speculative decoding** (use a tiny draft model to propose tokens verified in parallel by the main model), and **tensor parallelism** (split a model's layers across multiple GPUs).

## 3. The Quantization Ladder

Decoding tokens is mostly **memory-bandwidth bound**: the GPU spends its time reading model weights out of VRAM. Storing weights in fewer bits shrinks VRAM usage and speeds up decoding, at a potential quality trade-off:

| Format | Bits / weight | Memory vs fp16 | Practical guidance |
| ---------------- | ------------- | -------------- | --------------------------------------------------------------------------- |
| `fp32` | 32 | 2× | Training baseline; rarely used for serving |
| `fp16` / `bf16` | 16 | 1× | Default full-precision serving where hardware supports `bf16` |
| `int8` / `FP8` | 8 | ~0.5× | Needs compatible kernels/GPUs (e.g. Hopper/Blackwell for FP8); benchmark it |
| `int4` (GPTQ) | 4 | ~0.25× | Post-training calibration; measure task accuracy and kernel speed |
| `int4` (AWQ) | 4 | ~0.25× | Activation-aware quantization; benchmark on your actual eval set |

Raw 4-bit weights take roughly a quarter of 16-bit weight storage, but quantization scales/metadata, KV cache, and runtime workspaces still add up. Always test quantized checkpoints against your real eval set — never assume a universal accuracy drop.

## 4. GPU Memory Math (Don't Forget the KV Cache!)

Fitting a model's weights into VRAM does **not** mean it can serve production traffic. Concurrent users each hold their own KV cache in the same GPU memory:

```text
VRAM(weights) = params × bytes_per_weight        (bf16: 2 B, int8: 1 B, int4: 0.5 B)
VRAM(KV)      = 2 × layers × kv_heads × head_dim × seq_len × batch × bytes_per_kv
                (leading 2 = K and V tensors; 2 bytes for bf16 KV cache)
Total VRAM    = weights + peak KV cache + CUDA/activation workspace headroom

Worked example — Llama-3.1 70B at 8k context (bf16 weights & KV):
  weights:   70e9 × 2 B ≈ 140 GB (130.4 GiB) before runtime overhead
  KV cache:  2 × 80 layers × 8 kv_heads × 128 head_dim × 8192 tokens × 2 B
           = 2.5 GiB per concurrent request
  20 concurrent requests → 50 GiB KV + 130.4 GiB weights = 180.4 GiB before overhead
```

Keep decimal **GB** ($10^9$) and binary **GiB** ($2^{30}$) consistent, and always load-test realistic mixed prompt/output lengths before committing to a GPU SKU.

## 5. Serving Metrics Vocabulary

Speak these six terms accurately in design reviews and interviews:

| Metric | Meaning | Why it matters |
| -------------- | -------------------------------------------------------------- | --------------------------------------------------------------------- |
| **TTFT** | Time To First Token (network + queue + prefill + first decode) | Drives perceived responsiveness in streaming UIs |
| **TPOT / ITL** | Time Per Output Token (inter-token latency) | Controls streaming reading cadence |
| **Prefill** | Processing all input prompt tokens in parallel | Compute-bound; prefix caching speeds it up |
| **Decode** | Generating output tokens one by one | Memory-bandwidth-bound; dominates long answers |
| **Throughput** | Aggregate output tokens/sec across all active users | Drives hardware cost efficiency |
| **Goodput** | Throughput counting *only* requests that meet TTFT/TPOT SLOs | What users actually experience; optimize goodput, not raw throughput |

Larger batches push throughput up but stretch queueing and TPOT. SLO-aware schedulers balance batch size to maximize **goodput**.

## 6. Routing, Fallbacks, and Hybrid Topologies

Treat model providers like any flaky external dependency — with one extra rule: **data policy gates eligibility *before* availability routing.**

```text
request ──► router ──► data-class policy filter ──► primary (hosted-A)
                            │                            │ 429 / 5xx / timeout?
                            │                            ▼
                            │                       fallback (hosted-B)
                            │                            │ fail?
                            │                            ▼
                            │                       self-hosted vLLM (degraded tier)
                            ▼
                authoritative data class restricts approved endpoints;
                an optional PII detector may tighten class, never relax it
```

Common hybrid patterns in production:
1. **Route by data class:** regulated data stays on approved in-house or contracted endpoints; public traffic uses frontier hosted APIs.
2. **Hosted primary + self-hosted fallback:** stay online through vendor outages and rate-limit storms (provided your fallback is load-tested for outage volume!).
3. **Self-hosted bulk + hosted frontier:** run high-volume extraction/summarization on your GPUs and escalate complex reasoning to a frontier API.
4. **In-region managed endpoints:** combine managed operations with regional data contracts where legal/privacy review approves the full processing path.

## 7. Operational Realities of Self-Hosting

Before committing to GPUs, budget for six day-two realities:
- **Slow cold starts:** pulling container images and loading tens of gigabytes of weights takes minutes; keep a warm replica floor if interactive SLOs demand it, and autoscale on queue depth or KV-cache pressure.
- **KV-cache concurrency caps:** a sudden wave of 16k-token prompts can trigger KV evictions or queueing spikes even when GPU compute looks calm.
- **Non-drop-in model upgrades:** new checkpoints change tone, schema adherence, and tool calls — shadow-test, canary, and keep rollback digests pinned.
- **Driver / CUDA / runtime matrix:** pin image digests and validate CUDA/driver upgrades in staging.
- **Multi-tenancy:** swapping full models in and out of VRAM is slow; serving multiple lightweight LoRA adapters over one shared base model is much faster.
- **Serving observability:** graph TTFT/TPOT percentiles, KV-cache utilization and evictions, queue depth, and goodput per SLO tier.

## Code Examples

### Provider router with data-class gate and fallback chain

Enforce one total request deadline across the entire fallback chain (`AbortSignal.any`), verify `approvedDataClasses` before every attempt, and count only retryable provider failures against circuit breakers:

```typescript
// llm/router.ts
type DataClass = "public" | "internal" | "personal" | "regulated";
type TaskClass = "general" | "regulated" | "background";
type CompletionRequest = { dataClass: DataClass; timeoutMs?: number };
type Provider = {
  name: string;
  approvedDataClasses: readonly DataClass[]; // verified contract, not a region nickname
  complete(req: CompletionRequest, signal: AbortSignal): Promise<CompletionResponse>;
};

type RoutePolicy = { primary: string; fallbacks: string[] };

const POLICIES: Record<TaskClass, RoutePolicy> = {
  general:    { primary: "openai-eu",  fallbacks: ["anthropic-eu", "vllm-self"] },
  regulated:  { primary: "vllm-self",  fallbacks: ["azure-openai-de"] }, // verify endpoint contracts
  background: { primary: "vllm-self",  fallbacks: ["openai-eu"] },
};

export async function complete(
  req: CompletionRequest & { taskClass: TaskClass },
  callerSignal: AbortSignal,
): Promise<CompletionResponse> {
  const deadlineSignal = AbortSignal.timeout(req.timeoutMs ?? 30_000);
  const signal = AbortSignal.any([callerSignal, deadlineSignal]);
  const policy = POLICIES[req.taskClass];
  const chain = [policy.primary, ...policy.fallbacks].map(n => {
    const provider = registry[n];
    if (!provider) throw new Error(`unknown provider ${n}`);
    return provider;
  });

  let lastError: unknown;
  for (const provider of chain) {
    if (signal.aborted) throw new Error("request cancelled or deadline exceeded");
    if (!provider.approvedDataClasses.includes(req.dataClass)) continue; // hard data-policy gate
    const breaker = breakers.for(provider.name);
    if (breaker.isOpen()) continue;
    try {
      const res = await provider.complete(req, signal);
      breaker.recordSuccess();
      metrics.route(provider.name, req.taskClass);
      return res;
    } catch (e) {
      lastError = e;
      if (signal.aborted) throw e; // never fall back after caller cancel or overall deadline
      const failure = classifyProviderError(e);
      if (!failure.retryable) throw e;
      breaker.recordFailure();
      warn("provider_fallback", { provider: provider.name, err: failure.code });
    }
  }
  throw new AllProvidersFailedError(chain.map(p => p.name), lastError);
}
```

Ensure every provider adapter propagates `signal` to cancel in-flight HTTP requests, and never automatically retry uncertain tool side effects across providers.

### OpenAI-compatible client pointed at self-hosted vLLM

```typescript
// llm/vllm-client.ts
import OpenAI from "openai";

const local = new OpenAI({
  // Keep self-hosted inference on a private, authenticated TLS endpoint.
  baseURL: process.env.VLLM_BASE_URL!,
  apiKey: process.env.VLLM_API_KEY!,
});

export async function summarizeApprovedTicket(text: string): Promise<string> {
  const completion = await local.chat.completions.create({
    model: process.env.VLLM_SERVED_MODEL!,
    messages: [
      { role: "system", content: "Summarize support tickets in <=3 sentences." },
      { role: "user", content: text },
    ],
    max_tokens: 200,
    temperature: 0.2,
  });
  return completion.choices[0]?.message?.content ?? "";
}
```

Verify chat templates, structured-output support, streaming behavior, and cancellation on the actual vLLM release — sharing an SDK shape does not make every feature identical.

### VRAM sizing calculator

This self-contained TypeScript helper computes a quick binary-GiB lower bound and rejects invalid inputs before arithmetic:

```typescript
// llm/sizing.ts
type SizeInput = {
  paramsB: number;                 // e.g. 70 for 70B
  bitsPerWeight: 16 | 8 | 4;
  layers: number;
  kvHeads: number;                 // after Grouped-Query Attention (GQA)
  headDim: number;
  ctxLen: number;
  concurrency: number;
  gpuVramGiB: number;              // binary GiB per GPU
};

export function estimateVram(i: SizeInput) {
  if (Object.values(i).some(n => !Number.isFinite(n) || n <= 0) ||
      ![4, 8, 16].includes(i.bitsPerWeight) ||
      [i.layers, i.kvHeads, i.headDim, i.ctxLen, i.concurrency].some(n => !Number.isSafeInteger(n))) {
    throw new RangeError("invalid sizing inputs");
  }
  const round = (n: number) => Math.round(n * 100) / 100;
  const weightsGiB = (i.paramsB * 1e9 * i.bitsPerWeight / 8) / 1024 ** 3;
  const kvPerReqGiB =
    (2 * i.layers * i.kvHeads * i.headDim * i.ctxLen * 2 /* bf16 bytes; leading 2 = K and V */) /
    (1024 ** 3);
  const kvTotalGiB = kvPerReqGiB * i.concurrency;
  const overheadGiB = 2 + 0.10 * (weightsGiB + kvTotalGiB); // CUDA + activation headroom
  const totalGiB = weightsGiB + kvTotalGiB + overheadGiB;
  return {
    weightsGiB: round(weightsGiB),
    kvPerRequestGiB: round(kvPerReqGiB),
    totalGiB: round(totalGiB),
    fitsOneGpu: totalGiB <= i.gpuVramGiB,
    idealAggregateLowerBound: Math.ceil(totalGiB / i.gpuVramGiB), // lower bound, not a deploy guarantee
  };
}

// estimateVram({ paramsB: 70, bitsPerWeight: 4, layers: 80, kvHeads: 8,
//   headDim: 128, ctxLen: 8192, concurrency: 16, gpuVramGiB: 80 })
// → weights 32.6 GiB, KV 40 GiB (2.5/req), total 81.86 GiB → needs >= 2 × 80 GiB GPUs (or cut ctx/concurrency)
```

### Operational minimum for deploying vLLM

Pin both the container image digest and the Hugging Face model commit, bind privately behind an authenticated TLS gateway (vLLM's built-in `--api-key` only covers inference prefixes, and multi-node communication is unauthenticated by default), and verify flags for your pinned release:

```bash
: "${VLLM_IMAGE:?pin vLLM image by digest}"
: "${MODEL_ID:?choose a supported model/checkpoint}"
: "${MODEL_REVISION:?pin the Hugging Face commit}"
: "${VLLM_API_KEY:?configure authentication}"
docker run --gpus all --ipc=host \
  -p 127.0.0.1:8000:8000 \
  -e VLLM_API_KEY \
  "$VLLM_IMAGE" \
  --model "$MODEL_ID" --revision "$MODEL_REVISION" \
  --tensor-parallel-size 2 --max-model-len 16384 \
  --gpu-memory-utilization 0.90 --enable-prefix-caching \
  --api-key "$VLLM_API_KEY"
```

Keep authoritative data classification rules in [Safety, Cost & Governance](20.12.06-safety-cost-governance.md); the serving router should pick availability only among endpoints that already passed policy.

## Real-World Use Cases

1. **EU SaaS helpdesk** — derive ticket data class from trusted application state, allow only endpoints with approved processing/transfer terms, and keep a minimized operational audit trail.
2. **High-volume document extraction** — compare provisioned GPU cost plus engineering ops against hosted batch pricing; self-host only when steady utilization clears both quality and total-cost bars.
3. **Real-time voice agent** — strict TTFT budgets drive model size, regional placement, prefix caching, and speculative decoding decisions verified under peak load.
4. **Early-stage startup MVP** — start on hosted APIs to avoid GPU ops; revisit self-hosting only when volume, data policy, or latency data proves it pays off.
5. **Fintech on-call copilot** — hosted primary for complex reasoning paired with a load-tested self-hosted fallback sharing the same circuit breakers.

## Summary

- Decide hosted vs self-hosted per workload across four axes: measured task quality, full cost at real utilization, latency/goodput SLOs, and verified data-handling terms.
- Modern open-weight serving relies on PagedAttention and continuous batching; benchmark quantization and prefix caching on your own workload.
- Size GPU VRAM from **weights + peak KV cache + runtime headroom**, keeping GB and GiB straight and validating under realistic concurrency.
- Optimize **goodput** (requests meeting TTFT/TPOT SLOs), not raw tokens per second.
- Enforce data-class eligibility *before* availability fallback, and pin exact model revisions and container digests.

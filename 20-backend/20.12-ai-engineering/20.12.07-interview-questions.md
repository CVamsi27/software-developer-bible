# AI Engineering Interview Questions

> **Format:** Question → 30-second answer → senior follow-up boundary. 28 authored questions covering senior-level LLM architecture, retrieval, agents, serving, and governance. Pair with the [track files](INDEX.md) for depth.

---

## How to Use This Bank

Answer each question aloud before reading the model answer. The 30-second answer gives you a crisp opening contract; the follow-up highlights the failure boundary that separates senior engineers from memorized buzzwords. Use [Revision](REVISION.md) to repair mechanism gaps and return here for timed spoken drills.

## First Principles

1. **A model proposes output; your application owns its consequences.** Derive authorization, validation, and audit boundaries from the effect being attempted.
2. **Quality varies across inputs and runs.** Compare labeled eval cases and repeated measurements instead of trusting one demo transcript.
3. **Every extra inference or tool step adds a failure boundary.** Explain budgets, deadlines, cancellation, and recovery before naming an orchestration framework.

## Architecture

### Q1. "When would you choose RAG over fine-tuning?"

**30-sec:** Choose RAG when the gap is *knowledge* — private, per-tenant, or rapidly changing facts that need citations and instant updates. Choose fine-tuning when the gap is *behavior* — consistent style, domain phrasing, or cutting latency/cost by teaching a smaller model a narrow task.

**Follow-up:** They often work together (a tuned model grounded by retrieval). Diagnose retrieval misses separately from generation errors on your eval set instead of escalating blindly, and watch for silent RAG regressions: stale indexes after doc edits, chunking changes, and broken tenant filters.

### Q2. "Design 'ask questions over our documentation' end-to-end."

**30-sec:** Split into two pipelines. Ingestion chunks documents by structure, generates embeddings, and stores content-hashed revisions with tenant metadata. Query time runs hybrid retrieval (lexical + vector) with tenant filters, optional reranking, prompt assembly with source IDs, streaming answers with citations, and an explicit refusal path when evidence is missing.

**Follow-up:** Checking that cited source IDs exist catches invented citations, not unsupported claims — add claim-support evals and unanswerable test cases. Re-index incrementally on content hash changes, and version chunking, index, prompt, and model artifacts together so regressions are attributable.

### Q3. "Your AI feature must not send patient data to a third-party provider. Options?"

**30-sec:** Enforce it in layers: (1) a default-off kill switch that skips constructing external provider clients; (2) authoritative data classification before any routing; (3) local or self-hosted inference for extractive/clinical tasks (like local OCR); and (4) minimized audit logs.

**Follow-up:** Clarify whether "zero-retention vendor endpoint" meets the rule — a third-party vendor endpoint still processes data outside your org. If zero third-party processing is required, route only to approved self-hosted/local paths or deny the request, because regex redaction cannot prove all sensitive free text was removed.

### Q4. "How do you make LLM output safe to feed your database?"

**30-sec:** Request structured JSON output via schema/tool calling, cap raw bytes before parsing, validate the parsed payload with Zod, and enforce server-side authorization and business invariants before touching the database. Treat model output exactly like untrusted user input.

**Follow-up:** Schemas validate shape, not authority or state. Check user permissions, tenant ownership, and balances atomically inside the database transaction (with DB constraints as the final backstop), and require idempotency keys on retries.

### Q5. "Sync or async for LLM workloads?"

**30-sec:** Use streaming HTTP/SSE with timeouts and abort propagation for interactive UI features. Push slow or bulk jobs (batch summarization, embedding backfills, long reports) onto durable worker queues with idempotency keys, backoff, and progress polling.

**Follow-up:** Awaiting a slow provider over async I/O doesn't block the Node.js event loop, but long-lived requests still consume connection pools, reverse-proxy timeouts, and concurrency budgets. Define cancellation and result retention explicitly for queued jobs.

### Q6. "How do you prevent agentic loops from runaway spend or infinite cycling?"

**30-sec:** Layer independent guards in the orchestrator: a hard max-turn and max-call ceiling, a cumulative spend/token budget checked *before* every call, a wall-clock deadline, and a no-progress detector that catches repeated `(tool, args)` loops. Return typed errors instead of raw stack traces.

**Follow-up:** Count *every* model turn and proposal — including invalid or unknown tool calls — toward the budget. Reserve conservative input-plus-output spend before each inference, and propagate `AbortSignal` to cancel upstream requests (a `Promise.race` timeout leaves remote work running and billing).

### Q7. "What is Model Context Protocol (MCP), and what does it standardize?"

**30-sec:** MCP defines a standard JSON-RPC boundary between AI hosts and external servers that expose tools, read-only resources, and prompt templates. The `2026-07-28` specification uses stateless requests over `stdio` or Streamable HTTP; pin both protocol revision and SDK version.

**Follow-up:** In `2026-07-28`, user elicitation travels as a multi-round-trip `input_required` result rather than a server-initiated JSON-RPC request, and long-running tasks live in an optional extension. Discovery grants zero trust: namespace tool names, authorize every `tools/call` in the host, and isolate/reap `stdio` child processes.

## Prompts & Context

### Q8. "What goes into your context window and why?"

**30-sec:** Put only what earns its slot: concise instructions, relevant retrieved evidence, required workflow state, and the current user task — all under a hard token budget that trims or summarizes older history instead of silently overflowing.

**Follow-up:** Count the *complete serialized request* (message framing, tool definitions, output schema, and reserved output/reasoning tokens), not just document text. Validate that conversation summaries retain critical facts and pending tool-call/result pairs, and measure chunk ordering on your target model.

### Q9. "Users report the bot 'got dumber' after we switched models. What do you do?"

**30-sec:** Reproduce the reported failures first, then run your golden-set eval suite across both the old and new models, breaking down pass rates by task category (extraction, citation, refusal). If no golden set exists, build one from privacy-approved failure cases and representative traffic before tweaking prompts.

**Follow-up:** Because model outputs are noisy, run repeated trials on a held-out set and compare category deltas plus latency/cost before declaring a regression fixed. Hold prompts constant first so you can tell model drift apart from prompt mismatch.

### Q10. "What is prompt injection and how do you defend?"

**30-sec:** Prompt injection happens when untrusted text — from a user or a retrieved document — hijacks the model's instructions to leak data or trigger unintended actions. Defend by separating instructions from data, enforcing strict server-side authorization and least-privilege tools, and running adversarial evals.

**Follow-up:** Delimiters and JSON serialization reduce ambiguity but never make a model immune. A prompt injection can still trick the model into emitting schema-valid arguments for an unauthorized refund — deterministic server-side authorization is the real security boundary.

### Q11. "Few-shot examples — how many and where?"

**30-sec:** Add one example per distinct edge case or formatting failure you observe, keep them versioned with the prompt, and verify in your eval suite that each example improves accuracy enough to justify its token cost.

**Follow-up:** There is no magic number or universal placement rule across models. Always evaluate changes against a *held-out* test set so your examples improve generalization instead of overfitting to the cases you pasted into the prompt.

## Production

### Q12. "LLM costs tripled month-over-month. Debug."

**30-sec:** Pull token telemetry grouped by feature, prompt version, and model first. The usual culprits are runaway retries, unbounded chat history, missing response caches, or a loop calling a frontier model per item instead of batching or routing easy cases to smaller models.

**Follow-up:** Separate organic traffic growth from tokens-per-request growth, retry amplification, and model-tier mix shifts. Before relying on semantic caching to cut spend, audit cache hit accuracy and tenant scoping so you don't trade spend for wrong or leaked answers.

### Q13. "Provider has an outage during peak. What do users see?"

**30-sec:** Under a tested fallback policy: the circuit breaker trips → serve a permitted cache entry when staleness is acceptable → route to an approved fallback model whose quality clears your bar → queue non-urgent jobs → show clear degraded UX instead of hanging spinners.

**Follow-up:** Every fallback must already be approved for the request's data class and sized for outage traffic. Mid-stream failures aren't magically invisible: define whether the UI preserves partial tokens with a retry button or cleanly restarts, and never replay uncertain side effects.

### Q14. "How do you rate-limit an AI endpoint differently from normal APIs?"

**30-sec:** Meter two dimensions: requests per minute *and* token/cost spend per window, because one long prompt can cost 100× another. Combine per-tenant budgets with global spend caps and active-concurrency limits since streaming calls hold connections open.

**Follow-up:** Reserve an upper-bound cost estimate atomically *before* calling the provider and settle actual usage afterward. Because input, cached-input, reasoning, and output tokens carry different prices across models, a plain request counter cannot cap financial spend.

### Q15. "What do you log for an AI interaction?"

**30-sec:** Log the metadata needed to debug and audit without hoarding sensitive text: prompt ID and version, model snapshot, completion ID, TTFT and total latency, token/cost breakdown, retrieved source IDs, authoritative data class, and user outcome (accepted/edited/refused).

**Follow-up:** Logged versions let you trace and investigate incidents, not deterministically replay a stochastic output. Even source IDs can be personal data in sensitive domains, so apply strict access control and retention limits — and remember an app log is not a full GDPR Record of Processing Activities.

### Q16. "A clinician follows the AI's wrong suggestion. Walk me through your accountability design."

**30-sec:** Treat consequential AI outputs as decision support, never silent execution: display supporting source citations, show uncertainty only when calibrated, require explicit human review before writes, test dangerous failure cases in evals, and log minimized audit evidence.

**Follow-up:** Human reviewers suffer from automation bias and fatigue, so design review UX that surfaces underlying evidence rather than one-click "Accept All" buttons. Server-side invariants still enforce hard limits, and human sign-off alone never substitutes for safety evals or regulatory compliance.

## Frontend & UX

### Q17. "Streaming UX — what matters beyond rendering tokens?"

**30-sec:** Optimize TTFT alongside total completion time, render partial structured/markdown output smoothly without layout jank, wire working Cancel buttons that abort upstream generation, and handle mid-stream network drops with clear recovery states.

**Follow-up:** On the server, respect SSE backpressure (`res.write` returning `false` → wait for `drain` with abort handling) and watch the *response* transport close event rather than request-body completion. Propagate aborts to the provider SDK immediately, knowing tokens already generated before cancel still incur cost.

### Q18. "How do you show AI uncertainty honestly in UI?"

**30-sec:** Attach clickable citations to claims, render explicit *"not enough evidence"* refusals clearly, provide fast accept/edit/reject controls, and visually distinguish AI drafts from confirmed records.

**Follow-up:** Never display raw model self-confidence scores ("95% sure") unless you have calibrated them against real task accuracy on labeled data — models routinely sound confident when hallucinating.

### Q19. "Optimistic UI with AI actions?"

**30-sec:** Extend standard optimistic rollback with streaming states: `pending → partial → validated → committed`. If server validation or authorization rejects the output, roll back cleanly with an actionable message instead of silently wiping what the user read.

**Follow-up:** Optimistic rendering is purely provisional; the server still validates and authorizes every mutation. Distinguish a lost network response from a rejected write so clicking "Retry" uses an idempotency key instead of duplicating a committed action.

## Strategy & Trade-offs

### Q20. "Build vs buy vs open-weight model?"

**30-sec:** Almost every product team builds the application layer (retrieval, evals, UX, guardrails) and buys or hosts the model. Start on hosted APIs when quality and data terms fit; move specific workloads to self-hosted open weights when steady volume, strict data boundaries, or custom latency budgets justify GPU operations.

**Follow-up:** Compare measured eval quality, *full* cost (including idle GPU headroom and ops), and verified legal/data-transfer terms per workload. Neither "zero retention" nor "self-hosted" automatically proves compliance without checking the entire data path.

### Q21. "When is a small model the right answer?"

**30-sec:** Narrow, high-volume tasks — classification, routing, extraction, or simple summarization — where evals prove a smaller model hits your quality bar at a fraction of the latency and cost.

**Follow-up:** If you cascade from a small model to a frontier model, calibrate the escalation trigger on labeled examples rather than trusting the small model's self-reported confidence. Account for the extra latency and cost of re-running escalated prompts.

### Q22. "Semantic caching — risks?"

**30-sec:** The big risk is a *wrong hit*: two queries that look close in embedding space ("cancel my plan" vs "pause my plan") can need completely different answers, or leak data across tenants and user roles.

**Follow-up:** Always scope cache keys by tenant, user permissions, prompt/model version, and source revision; tune similarity thresholds on labeled pairs; set strict TTLs; and keep response caching completely separate from idempotency records for mutations.

### Q23. "Multi-tenancy in vector stores?"

**30-sec:** Enforce tenant isolation at the storage/query layer — mandatory `tenant_id` filters derived from authenticated server context, plus namespace/partition isolation where supported. Never rely on prompt instructions to hide another tenant's documents.

**Follow-up:** Test cross-tenant isolation in CI like an auth boundary (seeded two-tenant denial tests across lexical, vector, rerank, and fallback paths), check filtered ANN recall so selective tenant filters don't starve results, and re-verify source authorization before exposing cited documents.

### Q24. "How would you add citations to generated answers?"

**30-sec:** Pass numbered/ID-tagged retrieved chunks in the prompt, require structured JSON mapping claims to source IDs, verify every returned ID exists in the authorized retrieved set, and refuse or strip uncited claims.

**Follow-up:** Source-ID membership catches invented citations, not misquoted or contradicted facts. Pair structural checks with claim-support (entailment) evals on held-out cases and link directly to the underlying source spans so users can verify quickly.

### Q25. "What's your CI for prompts?"

**30-sec:** Store prompts in git, review changes via PR, run a fast golden-set eval on every PR that gates on task-success regressions and cost/latency deltas, and run a broader suite nightly — treating prompt edits with the same rigor as database query-plan changes.

**Follow-up:** Version prompts, datasets, model snapshots, retrieval configs, and decoding params together. Keep held-out cases out of prompt tuning, repeat noisy evals, and calibrate any LLM judge independently of the model you are testing.

### Q26. "Where do embeddings live in your stack and why?"

**30-sec:** Start with PostgreSQL + `pgvector` when its filtered recall, latency, update rate, and memory footprint fit your workload — you avoid operating a second database and keep metadata transactions atomic. Move to a dedicated vector database when benchmarked scale or operational needs clearly exceed it.

**Follow-up:** Skip arbitrary folklore cutoffs like "switch at 1 million vectors." Benchmark your actual vector dimensions, tenant-filtered recall, write rate, QPS, and RAM overhead. Even in Postgres, make sure your ingestion pipeline keeps text edits and re-embeddings in sync.

### Q27. "Final: 60 seconds on shipping AI features responsibly."

**30-sec:** "Start with a default-off kill switch and authoritative data-class routing before any provider call. Validate structured outputs and authorize every action on the server, put human review in front of irreversible writes, enforce atomic token budgets, gate prompt and model changes with held-out evals, and log minimized versioned audit trails."

**Follow-up:** Back each point with concrete evidence you can point to: a tested denied-egress case, a schema/authz rejection test, an atomic spend-reservation query, a golden-set diff, and explicit clarity about the failure boundaries that still remain.

### Q28. "A team is shipping an AI feature in the EU. How do you scope AI Act work?"

**30-sec:** Start from the feature's concrete *intended purpose* and your legal role (provider vs deployer). That determines whether the Act applies, which risk tier it falls into, and which staged deadline governs it (general rules from 2 Aug 2026; Annex III high-risk from 2 Dec 2027; Annex I regulated-product systems from 2 Aug 2028).

**Follow-up:** Never guess obligations from the model vendor or industry label alone. Map the resulting requirements — transparency notices, human oversight, logging, and technical documentation — to engineering owners and release evidence together with legal and privacy teams.

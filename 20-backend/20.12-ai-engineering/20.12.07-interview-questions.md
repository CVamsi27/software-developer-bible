# AI Engineering Interview Questions

> **Format:** Question → 30-second answer → follow-up traps. 27 questions covering what senior loops actually ask about LLM features in 2025+. Pair with the [track files](INDEX.md) for depth.

---

## How to Use This Bank

Answer the question aloud before reading its model answer. The short answer gives a starting contract; the follow-up adds the failure boundary that a memorized slogan misses. Use [Revision](REVISION.md) to repair mechanism gaps and return here for concise design explanations.

## First Principles

1. **A model proposes output; the system owns its consequences.** Derive authorization, validation, and audit boundaries from the effect being attempted.
2. **Quality varies across inputs and runs.** Compare labeled cases and repeated measurements instead of inferring safety from a convincing example.
3. **Every additional inference/tool step adds a failure boundary.** Explain budget, deadline, cancellation, and recovery before naming an orchestration framework.

## Architecture

### Q1. "When would you choose RAG over fine-tuning?"

**30-sec:** RAG when the gap is *knowledge* (private/fresh facts, citations, per-tenant data) — retrieval is updatable and auditable. Fine-tuning when the gap is *behavior* (format/style compliance at scale, latency via smaller tuned models). Order of operations: prompt → RAG → fine-tune; fine-tune only on measured plateau.

 *"Why not both?"* (common at scale — tuned model + grounded retrieval). *"What breaks RAG silently?"* (stale index after doc updates; chunking changes; tenant-filter regressions).

**Follow-up:** Retrieval and tuning can coexist. The choice is a diagnosis: missing/updating knowledge needs a retrieval pipeline; repeated behavioral failures may justify tuning. Measure retrieval misses separately from generation errors instead of escalating automatically through a fixed ladder.


### Q2. "Design 'ask questions over our documentation' end-to-end."

**Skeleton:** ingest pipeline (chunk → embed → store, versioned by deploy) → query API (embed → top-k with metadata filters → assemble prompt with sources → stream answer with citations) → refusal path when retrieval confidence low → evals on golden set → cost/latency dashboards.

 *"How do you stop it answering from its own training instead of the docs?"* (grounding instructions plus tests that claims are supported by their cited evidence). *"Docs updated hourly?"* (re-index triggers keyed on content hash).

**Follow-up:** Test ingestion updates, tenant authorization, supported citations, and unanswerable questions. Merely placing source ids in the answer does not prove its claims are supported. Version chunking, indexing, and generation artifacts so an eval regression can be attributed.


### Q3. "Your AI feature must not send patient data to a third-party provider. Options?"

**30-sec:** Layered: (1) default-off kill-switch gating client construction; (2) PII classification/redaction before egress; (3) private/zero-retention endpoints where contracts exist; (4) local inference for extractive tasks (on-device OCR); (5) audit every interaction. Describe only controls you can demonstrate.

**Follow-up:** A private or zero-retention vendor endpoint still processes the data at a third party. If the requirement is genuinely no third-party patient-data processing, use an approved local path or deny the request; regex redaction cannot prove sensitive free text was removed.


### Q4. "How do you make LLM output safe to feed your database?"

**30-sec:** Structured output via JSON schema/function calling, validated with Zod before anything executes; tool calls permission-checked server-side; treat model output exactly like untrusted user input.

 *"Model returns valid JSON that violates invariants?"* (schema validates shape, app validates semantics; DB constraints as final backstop).

**Follow-up:** Schemas validate shape; server authorization and authoritative business invariants decide whether an operation may happen. Enforce balance/ownership checks atomically with the write, and make retries idempotent. The UI or model cannot grant permission.


### Q5. "Sync or async for LLM workloads?"

**30-sec:** Interactive = streaming request/response with timeouts + aborts. Heavy jobs (batch summarization, embedding backfills) go through queues with idempotency keys and retry/backoff — same discipline as any worker system.

**Follow-up:** Awaiting a provider over asynchronous I/O does not block the Node.js event loop, but long requests consume transport/concurrency budgets. Minutes-long work can be a queued job with polling or a progress stream; define cancellation and result retention separately.


### Q6. "How do you prevent agentic loops from runaway spend or infinite cycling?"

**30-sec:** Multi-layered bounds: hard max-step ceiling (8–15 steps), cumulative token budget checked before every LLM call, wall-clock deadline, and a no-progress detector that flags duplicate consecutive `(tool, args)` calls. Break looping early with typed error observations rather than raw stack traces.

**Follow-up:** Count every model turn, including malformed/repeated calls. Before each call, reserve serialized input plus bounded output spend and enforce the remaining deadline. A Promise timeout that leaves the underlying operation running is not a cancellation guarantee.


### Q7. "What is Model Context Protocol (MCP) and how does it change tool integration?"

**30-sec:** MCP is an open standard (JSON-RPC 2.0 over stdio or Streamable HTTP) that decouples AI hosts/clients from tools and resources. It replaces $M \times N$ custom tool adapters with standardized JSON Schema contracts, capability negotiation, and clean process isolation boundaries.

**Follow-up:** Current standard transports are stdio and Streamable HTTP; legacy HTTP+SSE is deprecated. Stdio launches a subprocess but does not itself sandbox it. Authenticate remote servers, constrain permissions, validate discovered tools, handle pagination, and close transports deliberately.

## Prompts & Context

### Q8. "What goes into your context window and why?"

**30-sec:** Budget explicitly: stable system+rules first, retrieved knowledge next (compressed, cited), rolling summary + recent turns for history, task/format last for recency. Never full unbounded history.

**Follow-up:** Count the actual serialized request including message framing, tools, schemas, and output reserve. Summaries can lose facts; preserve important source references and pending tool-call/result pairs. Ordering strategies must be evaluated for the selected model/task.


### Q9. "Users report the bot 'got dumber' after we switched models. What do you do?"

**30-sec:** Investigate the reported cases and run the golden-set eval against old and new models, diff failures by category, then fix prompts/degrade paths with numbers. If no golden set exists, build one from logged real queries first (that's the actual root cause).

**Follow-up:** Use reported examples to reproduce the regression, then compare old/new configurations on a labeled set with category-level results. Multiple runs and sampling uncertainty matter: one noisy score does not establish a quality change.


### Q10. "What is prompt injection and how do you defend?"

**30-sec:** Untrusted content (user input OR retrieved docs) hijacking instructions. Defenses: separate instruction/data channels, sanitize delimiters, validate all tool calls server-side, least-privilege tools, output filtering, injection probes in evals.

**Follow-up:** Instruction/data separation reduces ambiguity but does not eliminate injection. JSON-valid tool arguments can still request unauthorized actions. The decisive boundary is deterministic least-privilege access and authorization, tested with hostile retrieved content.


### Q11. "Few-shot examples — how many and where?"

**30-sec:** 1–3 high-quality diverse examples beat many redundant ones; place near the format spec; keep them versioned — exemplars are code. Measure whether they pay for their tokens in evals.

**Follow-up:** Choose examples for distinct failure cases, then measure their cost/quality contribution. No universal example count or prompt position guarantees reliability; preserve held-out eval cases to avoid tuning only to the examples.

## Production

### Q12. "LLM costs tripled month-over-month. Debug."

**30-sec:** Token telemetry first: which feature/prompt version drove growth? Usual suspects: runaway retries, unbounded history, missing response cache, a loop calling the model per item instead of batching. Fixes: caches (exact + semantic), input trimming, smaller-model routing for easy cases, budget meters with alerts.

**Follow-up:** Separate billed token growth, request growth, retries, and per-feature routing changes. Similarity-cache hits can be wrong or cross-personalization leaks; measure hit quality before counting them as savings.


### Q13. "Provider has an outage during peak. What does users see?"

**30-sec:** Nothing dramatic: circuit breaker opens → serve cached responses → route to fallback model where quality allows → queue non-urgent jobs → UI shows degraded mode. Providers are unreliable dependencies; design like it.

**Follow-up:** A fallback must be allowed for the data class and clear the feature quality/capacity bar. Mid-stream fallback is not automatically transparent: preserve or restart partial output under an explicit UX contract, and avoid repeating side effects.


### Q14. "How do you rate-limit an AI endpoint differently from normal APIs?"

**30-sec:** Two dimensions: requests/min AND token spend/min — a single request can be 100× another's cost. Per-user/per-tenant budgets metered in tokens, plus global caps, plus concurrency limits since generations hold connections while streaming.

**Follow-up:** Admission needs both per-request limits and aggregate reservations; settle real usage afterward. Token prices differ across models and cached/reasoning/output categories, so a fixed request count is not a financial cap.


### Q15. "What do you log for an AI interaction?"

**30-sec:** Prompt version, model ID, completion ID, latency/TTFT, token counts, retrieved-source IDs, redacted input class, outcome (accepted/edited/refused). Enough to reproduce and audit without storing raw PHI.

**Follow-up:** Versioned references aid investigation, not deterministic reproduction of a stochastic answer. Inputs/outputs and even source identifiers may be personal data; minimize access and retention. An interaction audit is not a complete legal record of processing activities.


### Q16. "A clinician follows the AI's wrong suggestion. Walk me through your accountability design."

**30-sec:** Consequential outputs are suggestions, never silent actions: confidence display, mandatory human confirmation on write-paths, full audit trail (who saw what, which version), eval coverage of known-dangerous cases, and honest positioning — decision support, not decision maker.

**Follow-up:** Human review can fail through fatigue or misleading confidence. Show supporting evidence and calibrated uncertainty, test high-risk failure cases, and enforce authorization/invariants on the server. Human confirmation alone does not establish safety or regulatory compliance.

## Frontend & UX

### Q17. "Streaming UX — what matters beyond rendering tokens?"

**30-sec:** TTFT is the perceived-speed metric; render progressively but keep markdown/code blocks atomic until complete to avoid flicker; cancellable requests (abort controller); graceful mid-stream error recovery; disable-on-submit + resumable states.

**Follow-up:** Respect response backpressure, propagate cancellation, and preserve partial output safely. In Node.js, observe response transport closure rather than request-body completion; remote generation may have already incurred cost.


### Q18. "How do you show AI uncertainty honestly in UI?"

**30-sec:** Citations with sources, confidence indicators where calibrated, "no supporting info" refusals, edit-distance affordances (accept/edit/reject), and never styling suggestions as confirmed facts.

**Follow-up:** Use confidence only when its meaning has been calibrated on the task. A model self-rating is not an accuracy probability. Link claims to evidence and make unsupported/refused output visibly distinct.


### Q19. "Optimistic UI with AI actions?"

**30-sec:** Same rules as any optimistic update — rollback on failure — but add streaming-aware states: pending → partial → validated → committed; validation failure rolls back with explanation rather than silently dropping generated content.

**Follow-up:** An optimistic display is provisional; the server still validates and authorizes the actual effect. Distinguish transport failure from confirmed write failure: retries must not repeat an already committed action.

## Strategy & Trade-offs

### Q20. "Build vs buy vs open-weight model?"

**30-sec:** Buy API for speed + quality ceiling; open-weight/self-host for data-residency, unit economics at volume, or offline needs; "build" means building the *system around* the model, almost never the model. Regulated health data pushes toward zero-retention APIs or self-hosting.

**Follow-up:** Use a workload-specific comparison of measured quality, full cost, data policy, and operational capacity. Hosted/self-hosted compatibility is a tested contract, not a promise that every provider supports identical tools, schemas, and cancellation.


### Q21. "When is a small model the right answer?"

**30-sec:** High-volume narrow tasks (classification, extraction, routing) where evals show parity — wins on cost, latency, and privacy. Route: small model default, escalate to large on low-confidence/complexity signals.

**Follow-up:** Calibrate the escalation signal against labeled tasks; a model claiming confidence is not enough. Track quality and capacity in both tiers as traffic changes, including the cost of rerunning the same prompt on the larger model.


### Q22. "Semantic caching — risks?"

**30-sec:** Wrong-hit risk: semantically similar ≠ interchangeable answers, especially with personalization or tenancy. Mitigate: scope cache keys by tenant/task/version, similarity thresholds, TTLs, and never cache consequential-action outputs.

**Follow-up:** Scope by every input that changes the answer, including authorization and source revisions. Cache generated suggestions only where interchangeable/stale answers are permitted. Reusing an idempotency result for the same authorized mutation is a separate mechanism from semantic response caching.


### Q23. "Multi-tenancy in vector stores?"

**30-sec:** Tenant filter at query time AND namespace separation where supported; never rely on prompt-level scoping. Test cross-tenant leakage like an auth test — seeded two-tenant denial suites.

**Follow-up:** Tenant identity comes from authenticated server context. Put authorization in the retrieval/data-access layer, test every search/filter/fallback path, and check source authorization again before exposing a cited document.


### Q24. "How would you add citations to generated answers?"

**30-sec:** Ground generation in retrieved chunks with explicit source markers required by the prompt; post-process to verify each claim maps to a provided source; strip/refuse uncited claims. Citation enforcement lives in evals too.

**Follow-up:** Source-id membership catches invented references; it does not establish entailment. Compare each claim to its cited evidence using task-specific automated/human grading, test unsupported-but-plausible claims, and expose exact source spans when available.


### Q25. "What's your CI for prompts?"

**30-sec:** Prompts in repo, PR-reviewed; eval job runs golden set on change; gates on task-success regression + cost delta; nightly full run; results posted on the PR. Changing a prompt feels exactly like changing a query plan.

**Follow-up:** Version prompts, datasets, models, retrieval, and parameters. Use held-out cases, repeat noisy comparisons, and gate meaningful quality/cost regressions. A changing judge must be calibrated independently of the model under test.


### Q26. "Where do embeddings live in your stack and why?"

**30-sec:** Postgres + pgvector when scale fits — one less stateful system, transactional consistency with business data, works with existing tenancy/backup discipline. Dedicated vector DBs earn their keep at very large scale or exotic filtering needs.

**Follow-up:** There is no universal one-million-vector cutoff. Benchmark dimensions, filtered recall, update volume, QPS, latency, memory, and recovery cost on the real workload. A database transaction can align row/embedding revisions; the ingestion pipeline must still ensure the embedding matches the content.


### Q27. "Final: 60 seconds on shipping AI features responsibly."

**Pitch template:** "Default-off flag-gated integration; PII gate before egress; structured validated outputs; human-in-loop on consequential actions; token budgets with alerts; evals wired so quality claims are measurable; audit trail tying outputs to versions. With those seven controls, AI features meet the same bar as the rest of the system — report the evidence for the deployment you actually operated."

**Follow-up:** Name the implemented mechanism and evidence for each claim: a working kill switch, denied egress cases, validated/authorized outputs, review UX, atomic budget admission, held-out evals, and a minimized audit trail. Report remaining failure boundaries instead of claiming these controls guarantee compliance.

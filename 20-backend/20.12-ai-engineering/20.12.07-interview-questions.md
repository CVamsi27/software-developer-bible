# AI Engineering Interview Questions

## TL;DR

Senior-level AI-engineering questions with model answers and follow-ups — retrieval quality and chunking for RAG, prompt and context engineering, evaluation harnesses, streaming UX, token-cost and latency budgets, and guardrails. The senior signal is treating an LLM feature as an **unreliable dependency**: bounded context, measured evals, deterministic fallbacks, and cost per request tracked like any other resource.

## Architecture

### Q1. "When would you choose RAG over fine-tuning?"

**30-sec:** RAG when the gap is *knowledge* (private/fresh facts, citations, per-tenant data) — retrieval is updatable and auditable. Fine-tuning when the gap is *behavior* (format/style compliance at scale, latency via smaller tuned models). Order of operations: prompt → RAG → fine-tune; fine-tune only on measured plateau.

 *"Why not both?"* (common at scale — tuned model + grounded retrieval). *"What breaks RAG silently?"* (stale index after doc updates; chunking changes; tenant-filter regressions).

**Deep dive:** the full answer names the moving parts of the decision — knowledge volatility (RAG updates at doc speed; fine-tuning freezes knowledge at training time), auditability (retrieved chunks are citable evidence; weights are not), and failure modes (stale index vs. catastrophic forgetting). The sequence prompt → RAG → fine-tune is a cost ladder, not a dogma: each rung adds data pipeline, eval burden, and ops surface. Teams that fine-tune first almost always discover their real problem was retrieval.


### Q2. "Design 'ask questions over our documentation' end-to-end."

**Skeleton:** ingest pipeline (chunk → embed → store, versioned by deploy) → query API (embed → top-k with metadata filters → assemble prompt with sources → stream answer with citations) → refusal path when retrieval confidence low → evals on golden set → cost/latency dashboards.

 *"How do you stop it answering from its own training instead of the docs?"* (strict grounding prompt + citation-required rule check in evals). *"Docs updated hourly?"* (re-index triggers keyed on content hash).

**Deep dive:** the parts worth expanding: chunking is chosen per content shape (headers for docs, fixed-window with overlap for prose, AST-aware for code) because chunk boundaries are where retrieval quality is usually lost, not in the vector math. The refusal path is a *requirement*, not polish — 'I don't know' with sources beats a confident hallucination, and the eval set must contain unanswerable questions to prove it. Version the whole pipeline: chunker + index + prompt move together, and an eval regression is a rollback trigger.


### Q3. "Your AI feature must not send patient data to a third-party provider. Options?"

**30-sec:** Layered: (1) default-off kill-switch gating client construction; (2) PII classification/redaction before egress; (3) private/zero-retention endpoints where contracts exist; (4) local inference for extractive tasks (on-device OCR); (5) audit every interaction. This is my production pattern — cite it concretely.

**Deep dive:** the layering is ordered by blast radius: the kill-switch is one flag flip that protects everything downstream; redaction shrinks what can leak; private endpoints contractually bound what does flow; local inference is for the tasks where egress must be zero. The senior addition: classify *once* at ingress and carry the classification on the data — decisions downstream should trust a label, not re-run heuristics. And the audit trail is what turns 'we think we're compliant' into a demonstrable control.


### Q4. "How do you make LLM output safe to feed your database?"

**30-sec:** Structured output via JSON schema/function calling, validated with Zod before anything executes; tool calls permission-checked server-side; treat model output exactly like untrusted user input.

 *"Model returns valid JSON that violates invariants?"* (schema validates shape, app validates semantics; DB constraints as final backstop).

**Deep dive:** why the layering matters: JSON schema constrains *shape*, Zod constrains your *contract*, DB constraints constrain *reality* — three independently failing gates, which is what makes one bad generation harmless. The permission check on tool calls is the part juniors skip: the model is an untrusted caller with a natural-language interface, so every tool call gets the same authorization a user request would. Worth naming: structured-output APIs (json_schema mode) make the shape gate nearly free now — the app-level semantic validation is the irreplaceable layer.


### Q5. "Sync or async for LLM workloads?"

**30-sec:** Interactive = streaming request/response with timeouts + aborts. Heavy jobs (batch summarization, embedding backfills) go through queues with idempotency keys and retry/backoff — same discipline as any worker system.

**Deep dive:** the decision rule: anything a user waits on stays synchronous (streaming, with client aborts and per-request timeouts); anything measured in minutes belongs to a queue where idempotency keys make retries safe and dead-letter queues make failures visible. The classic middle case — 'the user waits but it might take 30s' — is where designs fail: stream progress events from the queued job instead of holding a fragile HTTP request open. Same discipline as any worker system, and the interview point is that LLM jobs get *no* exemption from it.

## Prompts & Context

### Q6. "What goes into your context window and why?"

**30-sec:** Budget explicitly: stable system+rules first, retrieved knowledge next (compressed, cited), rolling summary + recent turns for history, task/format last for recency. Never full unbounded history.

**Deep dive:** the allocation logic: stable instructions first (they're the prefix every generation depends on), retrieved knowledge compressed and *cited* next (so the answer can point at its evidence), then a rolling summary for history — a fixed-size window of the conversation that gets cheaper than full replay — and the task/format spec last for recency. The senior tell: treating context as a budget with per-section rents measured in eval scores, not 'stuff everything in'. Context rot is real: relevance decays for tokens far from the question.


### Q7. "Users report the bot 'got dumber' after we switched models. What do you do?"

**30-sec:** Refuse anecdotes — run the golden-set eval against old and new models, diff failures by category, then fix prompts/degrade paths with numbers. If no golden set exists, build one from logged real queries first (that's the actual root cause).

**Deep dive:** the eval discipline: the golden set is versioned alongside prompts, run against old and new model on every candidate swap, and diffs are triaged by failure *category* (retrieval miss vs. wrong format vs. tone drift) because each has a different fix. Two senior additions: pin the decoding parameters when comparing (temperature changes swamp model changes) and log enough per-case detail that a human can spot-check five failures per category — the harness finds where, humans find why.


### Q8. "What is prompt injection and how do you defend?"

**30-sec:** Untrusted content (user input OR retrieved docs) hijacking instructions. Defenses: separate instruction/data channels, sanitize delimiters, validate all tool calls server-side, least-privilege tools, output filtering, injection probes in evals.

**Deep dive:** the framing that elevates the answer: injection is a *confused deputy* problem — the model can't distinguish instructions from data unless the architecture makes the distinction. Concrete channel separation: system-role instructions the retrieved text can never reach, structured tool calls instead of free-text commands, and output schemas that make 'ignore previous instructions' just another string. The eval piece is what seniors add: injection probes belong in the test suite — adversarial corpora, not just happy-path golden sets.


### Q9. "Few-shot examples — how many and where?"

**30-sec:** 1–3 high-quality diverse examples beat many redundant ones; place near the format spec; keep them versioned — exemplars are code. Measure whether they pay for their tokens in evals.

**Deep dive:** the selection logic: examples teach format and edge-case handling, so diversity across *failure-relevant* axes matters more than count — three examples covering different input shapes beat ten near-duplicates that waste context and bias the model toward one pattern. Versioned with the prompt because they're part of the instruction surface; measured because exemplars silently shape behavior beyond the format they teach (tone, verbosity, refusal style all leak from examples).

## Production

### Q10. "LLM costs tripled month-over-month. Debug."

**30-sec:** Token telemetry first: which feature/prompt version drove growth? Usual suspects: runaway retries, unbounded history, missing response cache, a loop calling the model per item instead of batching. Fixes: caches (exact + semantic), input trimming, smaller-model routing for easy cases, budget meters with alerts.

**Deep dive:** the telemetry cuts that find it: cost per feature × prompt version × model (the guilty tuple is usually one cell), input vs. output token share (input growth = context bloat; output growth = verbosity or retries), and cache hit rate over time (a falling hit rate often *is* the incident). The fixes ranked by ROI: exact-match cache first (free wins), semantic cache second (with the tenant-scoping caveat from Q20), model routing third — small model default, escalate on confidence. Budget alerts belong on *projected* spend, not month-to-date — alerts that fire after the money's gone are postmortems, not controls.


### Q11. "Provider has an outage during peak. What does users see?"

**30-sec:** Nothing dramatic: circuit breaker opens → serve cached responses → route to fallback model where quality allows → queue non-urgent jobs → UI shows degraded mode. Providers are unreliable dependencies; design like it.

**Deep dive:** the design principle: provider outages are *when*, not *if* — so the degradation ladder is a product decision made before the incident, not improvised during it. Ordering by blast radius: cache hits first (free, instant), fallback model second (quality-validated on the golden set — never a model that's never been evaled), queue-and-notify third, honest degraded UX last. The senior addition: pre-agree the quality bar per feature with the product owner, so 'degraded mode' has a definition and the on-call isn't making product calls at 3am.


### Q12. "How do you rate-limit an AI endpoint differently from normal APIs?"

**30-sec:** Two dimensions: requests/min AND token spend/min — a single request can be 100× another's cost. Per-user/per-tenant budgets metered in tokens, plus global caps, plus concurrency limits since generations hold connections while streaming.

**Deep dive:** why tokens: request counts are a proxy with 100× variance — one call can be a 50-token classification or a 50k-token document analysis, so per-request limiting protects neither the user nor you. The metering stack: per-tenant token budgets (hard cap + alert at 80%), per-request max_tokens (a runaway generation is one bug away), and concurrency caps because streaming holds connections open — cost, latency, and capacity all couple through it. Surface usage to users via headers/dashboard; silent throttling of a paid tier is a churn machine.


### Q13. "What do you log for an AI interaction?"

**30-sec:** Prompt version, model ID, completion ID, latency/TTFT, token counts, retrieved-source IDs, redacted input class, outcome (accepted/edited/refused). Enough to reproduce and audit without storing raw PHI.

**Deep dive:** the design tension: enough to reproduce and audit, little enough to be a liability. The senior line: log *references* (prompt version, model ID, retrieved-chunk IDs) rather than raw content wherever possible — then any interaction can be reconstructed deterministically from versioned artifacts, and the log store holds no PII to leak. Redaction class labels ('contained PHI: yes/no') keep the analytics useful. Retention policy set deliberately: interaction logs age out, audit events don't.


### Q14. "A clinician follows the AI's wrong suggestion. Walk me through your accountability design."

**30-sec:** Consequential outputs are suggestions, never silent actions: confidence display, mandatory human confirmation on write-paths, full audit trail (who saw what, which version), eval coverage of known-dangerous cases, and honest positioning — decision support, not decision maker.

**Deep dive:** the accountability chain: every consequential output is a *suggestion* with visible confidence and evidence; write-paths require explicit human confirmation (the UI affordance is the control — accept/edit/reject, with edits logged); the audit trail ties output → prompt version → model → reviewer so blame and learning both have a substrate. The positioning sentence matters in interviews: decision support, not decision maker — and the eval suite covers known-dangerous cases (the clinician-fatigue scenario, the ambiguous-presentation case) so the safety claim is measured, not aspirational.

## Frontend & UX

### Q15. "Streaming UX — what matters beyond rendering tokens?"

**30-sec:** TTFT is the perceived-speed metric; render progressively but keep markdown/code blocks atomic until complete to avoid flicker; cancellable requests (abort controller); graceful mid-stream error recovery; disable-on-submit + resumable states.

**Deep dive:** the UX physics: perceived latency is TTFT, not total time — so stream early even if the full answer is slow. Rendering discipline: markdown/code blocks stay atomic until complete (partial markdown flickers and reflows — buffer block-level, stream inline text). Cancellation is a first-class feature, not an edge case: client aborts must actually cancel the server-side generation (money and latency both), and mid-stream errors need a recovery affordance that preserves the partial answer. Disable-on-submit plus visible generation state kills the double-submit class.


### Q16. "How do you show AI uncertainty honestly in UI?"

**30-sec:** Citations with sources, confidence indicators where calibrated, "no supporting info" refusals, edit-distance affordances (accept/edit/reject), and never styling suggestions as confirmed facts.

**Deep dive:** the design principle: uncertainty is information — hiding it makes confident-looking wrongness the product's signature failure. Concretely: citations link to *the evidence* (not a source list the claim may not be in), refusals are styled as answers ('no supporting info in your docs') rather than errors, and edit affordances (accept/edit/reject) convert users from victims of output into correctors of it — which also generates the labeled feedback evals need. The anti-pattern to name: styling speculation in the same visual register as verified facts.


### Q17. "Optimistic UI with AI actions?"

**30-sec:** Same rules as any optimistic update — rollback on failure — but add streaming-aware states: pending → partial → validated → committed; validation failure rolls back with explanation rather than silently dropping generated content.

**Deep dive:** the state machine that makes it safe: pending → streaming → validated → committed, with rollback as a first-class transition carrying an explanation (not a silent revert that leaves users guessing what happened to their content). The validation gate is the difference from normal optimistic UI: generated content often needs server-side validation (schema, policy, business rules) before it can commit, so the optimistic state must be visually distinct from confirmed state. Mid-stream failure keeps the partial content and offers retry — discarding 30 seconds of user-visible generation reads as data loss.

## Strategy & Trade-offs

### Q18. "Build vs buy vs open-weight model?"

**30-sec:** Buy API for speed + quality ceiling; open-weight/self-host for data-residency, unit economics at volume, or offline needs; "build" means building the *system around* the model, almost never the model. Regulated health data pushes toward zero-retention APIs or self-hosting.

**Deep dive:** the decision inputs: data sensitivity (zero-retention API vs. self-host is a contract question before it's an architecture question), unit economics at *your* volume (API wins at low volume; the crossover is calculable, not vibes), latency requirements (self-hosted small models often win), and the real meaning of 'build' — the moat is in the system: evals, retrieval, guardrails, UX. The senior tell: framing the model itself as a commodity swap-part with an abstraction layer, because provider lock-in is a pricing negotiation you will lose.


### Q19. "When is a small model the right answer?"

**30-sec:** High-volume narrow tasks (classification, extraction, routing) where evals show parity — wins on cost, latency, and privacy. Route: small model default, escalate to large on low-confidence/complexity signals.

**Deep dive:** the engineering pattern: routing as a first-class pipeline stage — a fast classifier (or the small model itself) scores complexity/confidence and escalates the tail to the large model. The economics: if 70% of traffic handles at 1/20th the cost, the blended price collapses and the eval suite is what proves quality parity per tier. Where small models win beyond cost: latency (interactive UX) and privacy (sensitive text never leaves the boundary). The failure mode to name: escalation hysteresis — a router tuned once drifts as traffic mix changes, so route quality is monitored per tier forever.


### Q20. "Semantic caching — risks?"

**30-sec:** Wrong-hit risk: semantically similar ≠ interchangeable answers, especially with personalization or tenancy. Mitigate: scope cache keys by tenant/task/version, similarity thresholds, TTLs, and never cache consequential-action outputs.

**Deep dive:** the risk taxonomy: wrong-hit (semantically similar ≠ interchangeable — 'refund policy for X' vs 'for Y' differ by tenant, time, or jurisdiction), staleness (underlying facts changed; the cache doesn't know), and personalization leakage (user A's context warm-serving user B — the tenancy incident waiting to happen). The controls that make it shippable: cache keys scoped by tenant/task/prompt-version, similarity thresholds tuned per use case, TTLs aligned to source-document freshness, and the hard rule — consequential-action outputs never cache. Monitor hit *quality*, not just hit rate: sampled human checks on cache-served answers.


### Q21. "Multi-tenancy in vector stores?"

**30-sec:** Tenant filter at query time AND namespace separation where supported; never rely on prompt-level scoping. Test cross-tenant leakage like an auth test — seeded two-tenant denial suites.

**Deep dive:** the threat model: a missing tenant filter isn't an information leak, it's a data breach across customers — and it fails *silent* (results come back confident and plausible). Defense in depth: namespace-level isolation at the store (the wall), tenant filters in every query (the check), and the test suite that proves both (seeded two-tenant corpora, assert cross-tenant retrieval returns zero, run it in CI like an auth test). The senior addition: tenant checks live in the *data access layer*, not prompt assembly — scoping by prompt instruction is hoping, not enforcing.


### Q22. "How would you add citations to generated answers?"

**30-sec:** Ground generation in retrieved chunks with explicit source markers required by the prompt; post-process to verify each claim maps to a provided source; strip/refuse uncited claims. Citation enforcement lives in evals too.

**Deep dive:** the enforcement chain: the prompt requires per-claim source markers; post-processing verifies each claim's citation actually appears in the provided chunks (string-anchored, not vibes); uncited or mis-cited claims get stripped or force refusal. Two senior refinements: citations should be *chunk-level and character-anchored* where possible (highlighting the exact span beats citing a whole document), and the eval set includes adversarial cases — claims that sound right but have no source — because 'the model usually cites' is not a property, it's a hope. The measured claim: citation precision/recall on the golden set.


### Q23. "What's your CI for prompts?"

**30-sec:** Prompts in repo, PR-reviewed; eval job runs golden set on change; gates on task-success regression + cost delta; nightly full run; results posted on the PR. Changing a prompt feels exactly like changing a query plan.

**Deep dive:** the maturity ladder: prompts in repo (any better-than-nothing), PR-reviewed with eval deltas posted (the floor for production), gated on task-success regression *and* cost delta (both matter — a 2% quality gain for 3× tokens is usually a loss), nightly full runs catching drift (model providers update endpoints silently; your nightly eval is the detector). The cultural endpoint: changing a prompt has the same ritual as changing a query plan — diff, eval numbers, reviewer, deploy. Teams that treat prompts as config snippets are running A/B tests on production with no instrumentation.


### Q24. "Where do embeddings live in your stack and why?"

**30-sec:** Postgres + pgvector when scale fits — one less stateful system, transactional consistency with business data, works with existing tenancy/backup discipline. Dedicated vector DBs earn their keep at very large scale or exotic filtering needs.

**Deep dive:** the honest calculus: pgvector up to ~1M vectors is the boring-right answer — one stateful system fewer, transactional consistency with your business data (the row and its embedding update atomically), and the existing backup/tenancy/monitoring story applies. The escalation triggers: billion-scale (sharding expertise required), exotic filtering (pre-filter vs post-filter semantics actually matter — check that your DB's hybrid filter+ANN plan doesn't silently degrade recall), or extreme QPS where a dedicated engine's HNSW tuning pays. The anti-pattern: adopting a vector DB before having retrieval-quality problems — infrastructure is not the hard part of RAG.


### Q25. "Final: 60 seconds on shipping AI features responsibly."

**Pitch template:** "Default-off flag-gated integration; PII gate before egress; structured validated outputs; human-in-loop on consequential actions; token budgets with alerts; evals wired so quality claims are measurable; audit trail tying outputs to versions. With those six controls, AI features meet the same bar as the rest of the system — that's how I shipped ours in healthcare."

**Deep dive:** the template's six controls, each with its failure mode named: flag-gating (roll back without redeploy), PII gate (the compliance story is a mechanism, not a promise), structured validated outputs (model output is untrusted input), human-in-loop on consequential actions (the liability boundary), token budgets with alerts (cost is a runaway risk like any other resource), and evals wired to deployment (quality claims become numbers). The closing frame: AI features meet the *same* engineering bar as everything else — the discipline transfers; only the failure modes are new.

# Java — Language Fundamentals

An order cache can return the right values and still behave incorrectly: a caller mutates a list through an alias, a map key changes after insertion, or a sort comparator reverses order on overflow. These are Java value, equality, and collection contracts. Follow one value through them before using the standard-library catalog.

## Definition

**Java** is a strongly and statically typed, class-based language. Java programs are normally compiled to **bytecode** and executed by a Java Virtual Machine (JVM), separating language rules from runtime implementation:

> **Textbook Definition:** Java is a statically and nominally typed language whose compiled class files execute on a Java Virtual Machine. Its language semantics, bytecode format and managed runtime jointly define type checking, execution and memory behavior.

```text
Source (.java) ──javac──▶ Bytecode (.class) ──JVM──▶ machine code
                                   │
                    JVM  = loads/verifies classes, executes code, and manages runtime memory
                    JDK  = JVM + standard libraries + compiler and tools
```

Three properties define the language's behavior and are what interviewers probe:

1. **Static + nominal typing** — every variable has a statically known type, declared explicitly or inferred with `var`; compatibility follows declared class/interface relationships, not matching structure. This is why Java needs explicit interfaces where TypeScript can accept a matching shape.
2. **Reference values and object identity** — the language exposes object references; a JVM may optimize allocations without changing observable semantics; assignment copies the reference, and `==` compares identity while `.equals()` follows the class's equality contract (`Object` defaults to identity). Shared mutation needs a separate ownership and concurrency policy.
3. **Managed memory** — the garbage collector reclaims unreachable objects, so "leaks" are usually unintended *retention* (caches, static collections, listeners) rather than forgotten frees.

The language's collections framework (`List`/`Set`/`Map` implementations) and its `Comparable`/`Comparator` ordering contract are part of the definition of everyday Java: choose an implementation by lookup, ordering, mutation and concurrency requirements.

## First Principles

The bytecode/JVM boundary is Java's portability model: compile source against language and library contracts, then let a compatible runtime execute the class files.

1. **Compile once, run anywhere requires a VM contract.** Bytecode + JVM is the abstraction: source → portable bytecode → platform-specific execution. The runtime owns loading and execution; garbage collection manages memory, verification checks bytecode constraints, and JIT compilation is an implementation choice.
2. **Static typing supports safer refactoring**: the compiler checks statically visible calls, while reflection, serialization and external clients need separate checks. Java has reduced boilerplate with local type inference, records and pattern matching while retaining compile-time type checks.
3. **Primitive and reference values have different costs and contracts.** Generics work with reference types, so boxing bridges primitives into collections and generic APIs. Erasure preserves compatibility but limits runtime type information. Records reduce data-carrier boilerplate while remaining reference types.

## Trace references, copies and collection order

Save this example as `LanguageTrace.java`, then run `javac --release 21 LanguageTrace.java` and `java LanguageTrace`. It traces assignment, method calls, equality, text indexing, and collection mutability—the contracts that explain many later surprises.

```java
import java.util.*;

public class LanguageTrace {
    static void replace(List<String> value) {
        value.add("shared change");
        value = new ArrayList<>(); // only the local parameter is reassigned
        value.add("local change");
    }
    public static void main(String[] args) {
        List<String> original = new ArrayList<>(List.of("Ada"));
        List<String> alias = original;
        List<String> copy = new ArrayList<>(original);
        replace(alias);
        System.out.println(original); // [Ada, shared change]
        System.out.println(copy);     // [Ada]
        System.out.println(original == alias); // true
        String text = new String("Ada");
        System.out.println(text.equals("Ada")); // true
        System.out.println(text == "Ada");      // false
        String emoji = "😀";
        System.out.println(emoji.length()); // 2 UTF-16 units
        System.out.println(emoji.codePointCount(0, emoji.length())); // 1 code point
        System.out.println(Arrays.toString(new int[]{3, 1})); // [3, 1]
        List<Integer> frozen = List.of(1, 2);
        try { frozen.add(3); }
        catch (UnsupportedOperationException expected) {
            System.out.println("unmodifiable list");
        }
    }
}
```

Java is pass-by-value: the copied value may be a primitive or an object reference. Reassigning the parameter does not replace the caller's variable. `new ArrayList<>(original)` copies the list structure, not mutable elements; a deep-copy requirement needs an element-copy contract. `List.of` forbids nulls and structural modification, but mutable element objects can still change. A code point is also not necessarily a whole user-perceived grapheme.

## Follow one class into the JVM

The source-level contract explains what Java code means. The JVM path explains when a class becomes executable and why startup, memory use, and steady-state latency can differ.

```text
.java ── javac ──> .class bytecode
                       │
          load → link → initialize
                       │
          interpret and collect runtime feedback
                       │
          compile hot code when the VM chooses
                       │
          execute machine code; deoptimize if an assumption no longer holds
```

1. **Load:** a class loader locates class bytes and defines the class. The JVM specification allows built-in and user-defined loaders; class identity includes both the binary name and the defining loader.
2. **Link:** verification checks bytecode constraints, preparation creates static fields with default values, and resolution connects symbolic references to classes, fields, and methods. Some resolution can be deferred until first use.
3. **Initialize:** before the first active use that requires initialization, the VM runs the class initializer (`<clinit>`) once under the class-initialization rules. A class can load successfully yet fail later during resolution or initialization.
4. **Execute:** each thread has frames for active methods; the JVM model puts ordinary object storage in the shared heap. HotSpot can eliminate some allocations when doing so preserves behavior. The specification names per-thread stacks, a heap, and a method area, but leaves their physical layout to the implementation. In HotSpot, class metadata is managed in native-memory Metaspace; it is not the Java object heap.
5. **Optimize:** HotSpot can begin by interpreting bytecode, collect execution profiles, and compile frequently used methods in tiers. Speculative compiled code can be invalidated when observed types or call targets change. A short-lived process may exit before compilation repays its startup cost.

```text
JVM-specification model                 HotSpot example
shared: heap, method area              class metadata → native Metaspace
thread: pc + stack of method frames    compiled machine code → code cache
                                       objects → Java heap
```

The diagram connects logical areas with one implementation; it is not a complete physical memory map. A process can exhaust native memory or the code cache even when the Java heap still has room.

The class-file and run-time-area rules belong to the JVM specification. **HotSpot's** tiering, Metaspace layout, garbage collectors, and diagnostic flags are implementation choices. HotSpot uses safepoints to coordinate operations that need a consistent view of Java thread state. Collectors may do much of their work concurrently but still pause threads for some phases; time to reach a safepoint and time spent in a collection pause are distinct contributors to latency. The pause and throughput profile also depends on collector, heap size, allocation rate, and live data. Do not infer a pause guarantee or memory layout from Java syntax.

For a real incident, compare startup with warmed-up throughput and collect evidence from the target JDK: unified class-loading, GC, and safepoint logs (`-Xlog:class+load=info`, `-Xlog:gc*`, and `-Xlog:safepoint`), Java Flight Recorder, and heap/GC metrics. A single cold-loop timing cannot separate compilation, allocation, I/O, and application work.

These runtime mechanisms do not change Java's equality, visibility, or type contracts. The examples use Java 21 language and APIs as a portable baseline without preview features; the linked specification documents the current Java SE 27 VM contract. Primitive patterns in `instanceof` and `switch` remain a preview feature in Java 27, so using them requires preview support enabled in the matching compiler and runtime.

## Values, types, and scope

### Primitive Types

| Type | Language width | Default | Range |
| --------- | -------------------------- | -------- | ----------------- |
| `byte` | 1 byte | 0 | -128 to 127 |
| `short` | 2 bytes | 0 | -32,768 to 32,767 |
| `int` | 4 bytes | 0 | -2³¹ to 2³¹-1 |
| `long` | 8 bytes | 0L | -2⁶³ to 2⁶³-1 |
| `float` | 4 bytes | 0.0f | ±3.4×10³⁸ |
| `double` | 8 bytes | 0.0d | ±1.7×10³⁰⁸ |
| `char` | 2 bytes | '\u0000' | 0 to 65,535 |
| `boolean` | Storage layout unspecified | false | true/false |

Defaults above apply to fields and array elements. Local variables must be definitely assigned before use. Floating-point types also represent infinities, NaN, and much smaller positive values than the listed maximum magnitudes. Fragments assume the named inputs and standard-library imports.

### Reference Types

```java
// Strings are immutable objects
String name = "Alice";
String greeting = new String("Hello"); // a distinct object; usually unnecessary

// Arrays
int[] nums = new int[5];
String[] names = {"Alice", "Bob", "Charlie"};

// 2D Arrays
int[][] matrix = new int[3][3];
int[][] grid = { {1, 2, 3}, {4, 5, 6} };

```

### Autoboxing and Unboxing

```java
// Autoboxing: primitive → wrapper
Integer a = 10; // int → Integer
Double b = 3.14; // double → Double
Boolean c = true; // boolean → Boolean

// Unboxing: wrapper → primitive
int x = a; // Integer → int
double y = b; // Double → double

```

Unboxing a null wrapper throws `NullPointerException`; wrapper `==` compares identity when both operands are references. Integer arithmetic normally wraps on overflow: use `Math.addExact` when overflow must reject an operation. Floating-point equality and rounding need a domain policy; represent exact decimal money with integer units or a validated `BigDecimal` scale.

### Variable Scope and Shadowing

        int y = 20; // block scope
        System.out.println(x + y); // 30
    }

}

## Text and indexed data

### Strings

#### String immutability

```java
String s = "Hello";
s = s + " World"; // Produces a new string value; the original remains unchanged

// String pool: JVM maintains a pool of strings
String a = "hello";
String b = "hello";
System.out.println(a == b); // true (same reference from pool)

String c = new String("hello");
System.out.println(a == c); // false (different objects)
System.out.println(a.equals(c)); // true (same content)

```

#### Methods that change a text-processing decision

```java
String raw = " Ada, 42 ";
String normalized = raw.strip().toUpperCase(Locale.ROOT); // stable machine-oriented case
String[] fields = raw.strip().split(",", 2); // ["Ada", " 42"]
boolean blank = " \t".isBlank(); // true; different from empty
String maybeName = null;
boolean same = Objects.equals(maybeName, "Ada"); // null-safe value comparison
```

`length()`, `charAt()` and substring indices count UTF-16 code units, not Unicode code points or user-perceived graphemes. `trim()` removes only characters up to U+0020; `strip()` uses `Character.isWhitespace`. Use an explicit locale for case conversion, and choose Unicode-aware processing when the requirement is a grapheme rather than a code unit.

#### StringBuilder (mutable)

```java
// Build incrementally when a loop performs many concatenations.
StringBuilder sb = new StringBuilder();
for (int i = 0; i < n; i++) {
    if (i > 0) sb.append(' ');
    sb.append(i);
}
String result = sb.toString();
```

For strings, `==` checks whether both references name the same object; `equals` checks content. Use `Objects.equals(a, b)` when either reference may be null.

### Arrays

#### Array operations

```java
// Declaration and initialization
int[] arr = new int[5]; // [0, 0, 0, 0, 0]
int[] arr2 = {1, 2, 3, 4, 5}; // literal initialization
int[] arr3 = new int[]{1, 2, 3}; // anonymous array

// Common operations
int length = arr.length; // 5 (field, not a method)
arr[0] = 10; // set
int val = arr[0]; // get

// Array copy
int[] copy1 = Arrays.copyOf(arr, arr.length);
int[] copy2 = Arrays.copyOfRange(arr, 1, 4); // [arr[1], arr[2], arr[3]]
int[] copy3 = new int[arr.length];
System.arraycopy(arr, 0, copy3, 0, arr.length);

// Sorting
Arrays.sort(arr); // ascending
Integer[] boxed = {1, 2, 3};
Arrays.sort(boxed, Collections.reverseOrder()); // descending requires reference elements

// Searching requires the array to be sorted with this same ordering.
int idx = Arrays.binarySearch(arr, target);

// Fill
Arrays.fill(arr, 0); // fill all with 0

// toString
System.out.println(Arrays.toString(arr)); // [0, 0, 0, 0, 0] after fill

```

#### Two-dimensional arrays

## Choose a collection by its contract

Choose the structure from the operations and guarantees the caller needs. List, Set, and Queue are Collection types; Map is a separate key-to-value abstraction. The names describe contracts, while the implementation determines ordering and performance.

| Need | Common choice | Contract that changes the decision |
| ----------------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Indexed, ordered values | ArrayList | Constant-time indexed reads and amortized append; inserting or removing in the middle shifts later elements. |
| Frequent edits at a known node or at either end | LinkedList | End operations are constant-time; finding an index is linear and node allocation has overhead. For ordinary queues/deques, ArrayDeque is usually the better default. |
| Membership without a promised iteration order | HashSet / HashMap | Expected constant-time lookup when hashes distribute well; equality and hash fields must stay stable while stored. HashMap permits null; ConcurrentHashMap does not. |
| Preserve insertion or access order | LinkedHashSet / LinkedHashMap | Adds ordering bookkeeping; LinkedHashMap can implement access-order caches, but eviction policy still needs explicit bounds. |
| Sorted keys and range queries | TreeSet / TreeMap | Logarithmic navigation; ordering equality (compare returns zero) defines uniqueness, which may differ from equals. Range views are backed by the original collection. |
| Repeatedly take the smallest or largest item | PriorityQueue | Head follows its comparator; iterating the queue does not produce sorted order. |
| FIFO, LIFO, or both ends | ArrayDeque | Efficient in-memory deque; rejects null and is not thread-safe. |

ArrayList also exposes an overload trap: remove(1) removes index 1, while remove(Integer.valueOf(1)) removes the value 1. Hash-based maps and sets use hashCode to find candidates and equals to confirm a key. In current OpenJDK, crowded buckets may become tree bins at sufficient capacity; those thresholds are implementation details, and collision behavior is not a portable worst-case complexity promise.

Use computeIfAbsent or merge for a map update whose lookup-and-change should be one map operation. Use a comparator with a safe comparison such as Integer.compare, never subtraction that can overflow.

```java
Map<String, Integer> counts = new HashMap<>();
counts.merge("Ada", 1, Integer::sum);
counts.merge("Ada", 1, Integer::sum);

Deque<String> queue = new ArrayDeque<>();
queue.offerLast("first");
String next = queue.pollFirst(); // FIFO

PriorityQueue<Task> byDeadline =
    new PriorityQueue<>(Comparator.comparing(Task::deadline));
Task earliest = byDeadline.poll(); // poll removes the head
```

These default implementations are not generally safe for concurrent mutation. Choose a concurrent collection or coordinate access when multiple threads share the structure; wrapping an individual collection does not make a multi-call workflow atomic.

## Define equality and ordering

```java
// Comparable: natural ordering (implements Comparable interface)
class Student implements Comparable<Student> {
    String name;
    int age;

    @Override
    public int compareTo(Student other) {
        return Integer.compare(this.age, other.age); // ascending by age
    }
}

// Comparator: custom ordering (passed to sort methods)
Comparator<Student> byName = Comparator.comparing(s -> s.name);
Comparator<Student> byAge = Comparator.comparingInt(s -> s.age);
Comparator<Student> byAgeDesc = byAge.reversed();
Comparator<Student> composite = byName.thenComparing(byAge);

List<Student> students = new ArrayList<>();
Collections.sort(students, byName); // by name
students.sort(byAgeDesc); // by age descending
students.sort(composite); // by name, then by age

```

A comparator must be transitive and consistent in its sign relationships. Sorted sets/maps identify keys by a zero comparison; inconsistent ordering and `equals` can produce membership surprises. Hash-based keys must keep equality and hash fields stable while stored.

If you override `equals`, preserve reflexivity, symmetry, transitivity and consistency; equal objects must return the same `hashCode`, though unequal objects may collide. Records generate component-based equality and hashing, which is useful for value keys when their components are themselves stable.

## Transform data without hiding its cost

### Lambda Expressions

```java
// Functional interface: one abstract method contract after inheritance and Object-method rules
@FunctionalInterface
interface Calculator {
    int calculate(int a, int b);
}

// Lambda syntax
Calculator add = (a, b) -> a + b;
Calculator multiply = (a, b) -> a * b;

// With body
Calculator divide = (a, b) -> {
    if (b == 0) throw new ArithmeticException("Division by zero");
    return a / b;
};

// No parameters
Runnable runnable = () -> System.out.println("Hello");

// Method references (shorthand for lambdas)
List<String> names = Arrays.asList("Alice", "Bob", "Charlie");
names.forEach(name -> System.out.println(name)); // lambda
names.forEach(System.out::println); // method reference

```

### Streams API

Intermediate operations such as filter, map, and flatMap are lazy; a terminal operation drives traversal, and a stream is consumed once. Use collect for a result container and reduce for an aggregate. Collectors.toList() does not promise a specific mutability contract; Stream.toList() returns an unmodifiable list. Prefer a loop when mutation, early exit, or debugging is clearer than a pipeline.

```java
List<List<Integer>> batches = List.of(List.of(1, 2), List.of(3, 4, 4));
List<Integer> distinct = batches.stream()
    .flatMap(Collection::stream) // turn each batch into one stream of values
    .filter(n -> n % 2 == 0)
    .distinct()
    .toList(); // [2, 4], unmodifiable

int total = batches.stream()
    .flatMapToInt(batch -> batch.stream().mapToInt(Integer::intValue))
    .sum(); // terminal reduction

Map<Boolean, List<Integer>> byParity = distinct.stream()
    .collect(Collectors.groupingBy(n -> n % 2 == 0));
```

Use anyMatch, allMatch, and noneMatch for short-circuiting predicates; use min/max with a comparator for ordered extrema. Avoid side effects inside intermediate operations, and use a parallel stream only when its CPU-bound workload and execution policy are appropriate (see the concurrency chapter).

## Represent absence

Use `Optional<T>` primarily as a return type when absence is an ordinary result. It does not make null safe by itself: `Optional.of(null)` throws, and `orElse(value)` evaluates its fallback eagerly while `orElseGet(supplier)` evaluates it only when empty.

```java
// Convert a nullable boundary result into an explicit absence value
Optional<String> opt = Optional.ofNullable(getName());
opt.ifPresent(name -> System.out.println(name));
String name = opt.orElse("Unknown");
String name2 = opt.orElseThrow(() -> new RuntimeException("Name not found"));

// Chaining
String result = Optional.ofNullable(user)
    .map(User::getAddress)
    .map(Address::getCity)
    .orElse("Unknown");

// Filtering
Optional<Integer> filtered = Optional.of(10)
    .filter(n -> n > 5); // Optional[10]
Optional<Integer> empty = Optional.of(5)
    .filter(n -> n > 5); // Optional.empty()

```

## Propagate failures and release resources

Use an exception when the current operation cannot meet its contract and a caller can respond. Checked exceptions must be caught or declared; unchecked exceptions usually indicate invalid state or programming errors. Use try-with-resources for owned resources so close runs deterministically, even when the body throws.

```java
// Try-Catch-Finally
try {
    int result = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println("Error: " + e.getMessage());
} finally {
    System.out.println("Runs on normal/exceptional exit, unless execution is terminated");
}

// Multi-catch
try {
    // code
} catch (IOException | SQLException e) {
    // handle both
}

// Try-with-resources (AutoCloseable)
try (BufferedReader br = Files.newBufferedReader(
        Path.of("file.txt"), StandardCharsets.UTF_8)) {
    String line = br.readLine();
} // br is automatically closed

// Custom exceptions
class InsufficientFundsException extends Exception {
    private final long deficitCents;

    public InsufficientFundsException(long deficitCents) {
        super("Insufficient funds. Deficit cents: " + deficitCents);
        this.deficitCents = deficitCents;
    }

    public long getDeficitCents() { return deficitCents; }
}

// Checked vs Unchecked
// Checked: IOException, SQLException → must catch or declare (throws)
// Unchecked: NullPointerException, ArrayIndexOutOfBounds → runtime exceptions

```

## Model a fixed set of values

An enum makes the allowed values explicit and gives each one a stable type. Use it for a closed domain state; do not persist ordinal positions, because reordering constants changes their numbers. External protocols should use an explicit wire representation rather than assume the Java constant name is permanent.

```java
enum OrderStatus { PENDING, PAID, CANCELLED }

String label(OrderStatus status) {
    return switch (status) {
        case PENDING -> "Awaiting payment";
        case PAID -> "Confirmed";
        case CANCELLED -> "Stopped";
    };
}
```

`OrderStatus.valueOf("PAID")` parses the exact enum constant name and throws for an unknown value. For user input or a versioned wire format, map explicitly and represent an unknown value as a validation failure instead of leaking that exception.

## Preserve type relationships with generics

Most generic type information is erased from runtime object representations. `List<String>` and `List<Integer>` share the same runtime class; the compiler inserts checks/casts and rejects many unsafe operations. Raw types can bypass those checks and cause later `ClassCastException`s. Primitive types are not generic type arguments; use wrapper types such as `Integer` instead.

```java
import java.util.*;

// Generic class
class Box<T> {
    private T content;

    public Box(T content) { this.content = content; }
    public T getContent() { return content; }
    public void setContent(T content) { this.content = content; }
}

Box<Integer> intBox = new Box<>(10);
Box<String> strBox = new Box<>("Hello");

// Bounded type parameters
class MathUtils {
    public static <T extends Comparable<? super T>> T max(T a, T b) {
        return a.compareTo(b) >= 0 ? a : b;
    }
}

class GenericExamples {
    public static void main(String[] args) {
        List<Integer> integers = Arrays.asList(1, 2, 3);
        List<Number> numbers = new ArrayList<>();

        numbers.addAll(integers); // reads Integer values through ? extends Number
        addNumbers(numbers);      // writes Integer values through ? super Integer
        System.out.println(sum(integers));
        printList(numbers);
    }

    // Upper-bounded wildcard: read Numbers from a list of Number or a subtype.
    static double sum(List<? extends Number> values) {
        return values.stream().mapToDouble(Number::doubleValue).sum();
    }

    // Lower-bounded wildcard: write Integers to a list of Integer or a supertype.
    static void addNumbers(List<? super Integer> values) {
        values.add(1);
        values.add(2);
    }

    // Unknown element type: cannot add a non-null typed value.
    // This is not read-only: removal and clear() may be supported.
    static void printList(List<?> values) {
        for (Object item : values) System.out.println(item);
    }
}

```

## Stop at the concurrency boundary

Learn thread creation, wait/notify, bounded buffers, executors, and futures together in [Concurrency & Multithreading](20.13.03-java-concurrency-multithreading.md). A collection that works in one thread does not become safe merely because its reference is `final`.

## Summary

1. **Runtime stages have different failure points.** Loading does not prove initialization will succeed; HotSpot's compilation, memory layout, and pause behavior need evidence from the deployed JDK.
2. **Types and references set the boundaries.** Compile-time checks do not replace runtime validation; assignment copies a reference, not the referenced object.
3. **Equality and collection contracts determine behavior.** Keep key state stable, pair `equals` with `hashCode`, and choose ordering and mutation guarantees deliberately.
4. **Text and indexed data have representation limits.** String indexes count UTF-16 code units; choose code-point or grapheme processing when the requirement needs it.
5. **Streams and Optional express transformations and ordinary absence.** Their APIs do not erase execution cost or make a loop less clear by default.
6. **Exceptions and resource ownership define failure cleanup.** Use try-with-resources for deterministic close and explicit enums for closed domain states.
7. **Generics preserve relationships at compile time.** Erasure and boxing still affect runtime checks and costs.

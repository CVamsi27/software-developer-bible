# Java — OOP Principles, Interfaces & SOLID


---

> Object-oriented design in Java: encapsulation, abstraction, inheritance, polymorphism, composition, interfaces vs abstract classes and the SOLID principles.

---

## Definition

**Java's object model** is a nominal, single-inheritance type system: every class except `Object` has one superclass (implicitly `Object`), and a class may implement many interfaces. Overridable instance methods dispatch against the runtime type; overload selection and static calls follow compile-time rules.

```text
class      = state (fields) + behaviour (methods), instantiable
abstract   = incomplete class; cannot instantiate; may hold state + partial impl
interface  = contract plus optional default/static/private implementations; no instance fields
                       ▲
   single inheritance ──┘── multiple interface implementation
```

Four consequences define how Java code is structured:

1. **Interfaces are types, not base classes** — a variable typed as an interface accepts any implementer, which is how Java achieves polymorphism *without* sharing an implementation. This is the mechanism behind dependency injection (`PaymentGateway` injected into `CheckoutService`).
2. **Dynamic dispatch by default** — `instanceof`-and-cast chains are a symptom that the behavior should have been a method on the interface; the OOP answer to a growing type switch is usually a new interface implementation.
3. **Overloading is compile-time, overriding is runtime** — this distinction explains why an overloaded method chosen by declared type can surprise you, and why `@Override` should always be present (it makes a broken override a compile error).
4. **Composition is the default over inheritance** — Java's single inheritance makes deep hierarchies brittle, so "implements an interface and holds a collaborator" is the idiomatic reuse mechanism.

SOLID enters here as the tool for choosing *where the interfaces go*: SRP decides the unit, DIP decides the direction of the dependency (details toward policy), LSP decides whether a subtype is safe to substitute, and ISP keeps clients from implementing methods they never use.

## First Principles

OOP principles are consequences of one goal: change without breakage.

1. **Dependency direction is the whole game (DIP).** High-level policy depending on low-level detail means every detail change ripples upward; invert it (depend on interfaces) and details become swappable. DI containers (→ 20.2.1.04) are this principle industrialized.
2. **Open-closed and Liskov are contract discipline.** Extension without modification requires that subclasses be *substitutable* — LSP defines what substitutable means (no strengthened preconditions, no weakened postconditions). Repeated type checks can reveal misplaced behavior, but an exhaustive switch over a deliberately sealed hierarchy is also a valid design.
3. **Interface segregation follows from coupling cost**: a fat interface forces implementors to depend on methods they don't need — every unneeded method is a future break. Small, purposeful interfaces keep change local (the same boundary discipline as module design, → 10.1.5.01).

## OOP Principles

### 1. Encapsulation

```java
// Bundle data and methods, hide internal details
class BankAccount {
    private long balanceCents;
    private final String owner;

    public BankAccount(String owner, long initialCents) {
        this.owner = java.util.Objects.requireNonNull(owner);
        if (initialCents < 0) throw new IllegalArgumentException("Negative balance");
        this.balanceCents = initialCents;
    }
    public void deposit(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("Amount must be positive");
        balanceCents = Math.addExact(balanceCents, cents);
    }
    public boolean withdraw(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (cents > balanceCents) return false;
        balanceCents -= cents;
        return true;
    }
    public long getBalanceCents() { return balanceCents; }
}
// One fixed currency with cent units; not a concurrent account or a durable ledger.

```

### 2. Abstraction

```java
// Hide complexity, show only essential features
abstract class Shape {
    abstract double area();
    abstract double perimeter();

    // Template method pattern
    public void describe() {
        System.out.println("Area: " + area() + ", Perimeter: " + perimeter());
    }
}

class Circle extends Shape {
    double radius;

    Circle(double radius) { this.radius = radius; }

    @Override
    double area() { return Math.PI * radius * radius; }

    @Override
    double perimeter() { return 2 * Math.PI * radius; }
}

class Rectangle extends Shape {
    double width, height;

    Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    double area() { return width * height; }

    @Override
    double perimeter() { return 2 * (width + height); }
}

```

### 3. Inheritance

```java
// IS-A relationship — code reuse
class Animal {
    String name;

    Animal(String name) { this.name = name; }

    void speak() { System.out.println(name + " speaks"); }
}

class Dog extends Animal {
    Dog(String name) { super(name); }

    @Override
    void speak() { System.out.println(name + " barks"); }

    void fetch() { System.out.println(name + " fetches"); }
}

// Multi-level inheritance
class Puppy extends Dog {
    Puppy(String name) { super(name); }

    @Override
    void speak() { System.out.println(name + " yips"); }
}

```

### 4. Polymorphism

```java
// Compile-time (method overloading)
class Calculator {
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; }
    String add(String a, String b) { return a + b; }
}

// Runtime (method overriding)
void makeSound(Animal animal) {
    animal.speak(); // calls the overridden version at runtime
}

Dog dog = new Dog("Rex");
Animal animal = dog;
makeSound(animal); // "Rex barks" — polymorphism in action

```

### 5. Composition (HAS-A relationship)

```java
// Prefer composition over inheritance
class Engine {
    void start() { System.out.println("Engine started"); }
}

class Car {
    private Engine engine; // composition
    private List<Wheel> wheels;

    Car() {
        this.engine = new Engine();
        this.wheels = Arrays.asList(new Wheel(), new Wheel(), new Wheel(), new Wheel());
    }

    void start() {
        engine.start();
        System.out.println("Car started");
    }
}

```

## Interfaces vs Abstract Classes

```java
// Interface — contract (can have multiple inheritance)
interface Flyable {
    void fly(); // abstract by default

    default void glide() { // default method (Java 8+)
        System.out.println("Gliding");
    }

    static boolean canFly(Flyable f) {
        return f != null;
    }
}

interface Swimmable {
    void swim();
}

// A class can implement multiple interfaces
class Duck extends Animal implements Flyable, Swimmable {
    Duck(String name) { super(name); }

    @Override public void fly() { System.out.println(name + " flies"); }
    @Override public void swim() { System.out.println(name + " swims"); }
}

// Abstract class — partial implementation (single inheritance only)
abstract class Vehicle {
    String name;

    Vehicle(String name) { this.name = name; }

    abstract void start(); // must be implemented

    void stop() { // concrete method
        System.out.println(name + " stopped");
    }
}

```

## SOLID Principles

The following sketches assume domain types `User` and `PaymentResult`; payment adapters deliberately throw until implemented. Geometry examples above assume finite non-negative dimensions.

```java
// S — Single Responsibility Principle
// Each class should have only one reason to change
class UserValidator {
    boolean validate(User user) { return user != null; }
}
class UserRepository {
    void save(User user) { /* persistence logic */ }
}
class EmailService {
    void sendWelcomeEmail(User user) { /* email logic */ }
}

// O — Open/Closed Principle
// Open for extension, closed for modification
interface DiscountStrategy {
    double applyDiscount(double price);
}

class SeasonalDiscount implements DiscountStrategy {
    public double applyDiscount(double price) { return price * 0.9; }
}

class LoyaltyDiscount implements DiscountStrategy {
    public double applyDiscount(double price) { return price * 0.85; }
}

// Adding new discounts doesn't require modifying existing code!

// L — Liskov Substitution Principle
// Subtypes must be substitutable for their base types
interface PaymentProcessor {
    PaymentResult process(double amount);
}

class CreditCardProcessor implements PaymentProcessor {
    public PaymentResult process(double amount) {
        throw new UnsupportedOperationException("Connect payment adapter here");
    }
}

class PayPalProcessor implements PaymentProcessor {
    public PaymentResult process(double amount) {
        throw new UnsupportedOperationException("Connect payment adapter here");
    }
}

// I — Interface Segregation Principle
// Clients shouldn't depend on interfaces they don't use
interface Workable {
    void work();
}

interface Feedable {
    void eat();
}

interface Sleepable {
    void sleep();
}

class Robot implements Workable {
    public void work() { /* robots work */ }
    // doesn't implement eat() or sleep() — doesn't need to
}

// D — Dependency Inversion Principle
// Depend on abstractions, not concretions
class OrderService {
    private final PaymentProcessor processor; // depends on interface

    OrderService(PaymentProcessor processor) {
        this.processor = processor;
    }

    void processOrder(double amount) {
        processor.process(amount);
    }
}

```

## Closed data models

Use a sealed hierarchy when the permitted variants are intentionally closed. Java 21 supports exhaustive pattern switches; a record supplies component-based equality and accessors, but remains a reference type and is only shallowly immutable.

```java
sealed interface Outcome permits Success, Failure {}
record Success(String receipt) implements Outcome {}
record Failure(String reason) implements Outcome {}

static String describe(Outcome outcome) {
    return switch (outcome) {
        case Success s -> "Receipt: " + s.receipt();
        case Failure f -> "Failed: " + f.reason();
    };
}
```

Use open interface implementations when independently extensible behavior is the requirement. An exhaustive data switch is not inherently a SOLID violation.

## Composition vs Inheritance

| Aspect | Inheritance | Composition |
| ------------ | ---------------------------- | ------------------- |
| Relationship | IS-A | HAS-A |
| Coupling | Tight | Loose |
| Flexibility | Limited (single inheritance) | High |
| Reuse | Code reuse | Behavior delegation |
| When to use | Clear hierarchy | Flexible, testable |

**Rule of thumb:** Favor composition over inheritance unless there's a clear IS-A relationship.

## Summary

1. Interfaces expose roles; composition delegates behavior without a deep hierarchy.
2. Overloading chooses a signature at compile time; overriding dispatches at runtime.
3. Encapsulation must enforce invariants, including negative amounts and overflow.
4. SOLID describes dependency and substitution contracts rather than a required class count.
5. A `final` reference prevents reassignment; it does not freeze the referenced object. Defensive copies and deeply immutable state require separate decisions.

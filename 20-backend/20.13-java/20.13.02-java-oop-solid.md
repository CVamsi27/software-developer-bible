# Java — OOP Principles, Interfaces & SOLID

A `Square` is mathematically a rectangle, but a mutable `Square` can violate a caller's promise that changing a rectangle's width leaves its height alone. That mismatch is the central design question here: what behavior does a type promise, and which implementations can safely keep it?

## Definition

Java models objects with classes and interfaces. A class has at most one direct superclass and can implement several interfaces; an interface can extend several interfaces. A variable's declared type controls which members are available and which overload is selected.
For an overridable instance method, the object's runtime class selects the implementation. Static, private and final methods do not participate in that dispatch.

> **Textbook Definition:** Object-oriented design organizes state and behavior behind types and their contracts. Java expresses those types through classes and interfaces, with encapsulation controlling access and subtyping allowing one implementation to stand in for another when it preserves the contract. SOLID principles are design heuristics for managing change and dependencies, not Java language rules.

```text
class      = declared state + behavior; concrete classes may be instantiated
abstract   = incomplete class; cannot instantiate; may hold state + partial impl
interface  = contract plus optional default/static/private implementations; no instance fields
                       ▲
   single inheritance ──┘── multiple interface implementation
```

Four consequences define how Java code is structured:

1. **Interfaces are types, not base classes** — a variable typed as an interface accepts any implementer, which is how Java achieves polymorphism *without* sharing an implementation. This is the mechanism behind dependency injection (`PaymentGateway` injected into `CheckoutService`).
2. **Dispatch follows the method contract** — Overridable instance methods select behavior at runtime. Static/private/final methods and overload selection have different rules; a type switch can be appropriate for a deliberately closed data model.
3. **Overloading is compile-time, overriding is runtime** — this distinction explains why an overloaded method chosen by declared type can surprise you, and why `@Override` should always be present (it makes a broken override a compile error).
4. **Composition is the default over inheritance** — Java's single inheritance makes deep hierarchies brittle, so "implements an interface and holds a collaborator" is the idiomatic reuse mechanism.

SOLID enters here as the tool for choosing *where the interfaces go*: SRP decides the unit, DIP decides the direction of the dependency (details toward policy), LSP decides whether a subtype is safe to substitute, and ISP keeps clients from implementing methods they never use.

## First Principles

Design choices matter when a requirement changes. If every new payment provider forces edits through checkout, the variation point is in the wrong place. If a subtype breaks an assumption callers rely on, reuse spreads incorrect behavior.
If one interface makes unrelated clients implement methods they cannot support, the contract is too broad. SOLID gives names to these pressure points; apply each principle only where its failure mode exists.

Dependency inversion is about source-code ownership: policy defines the abstraction and details implement it. Dependency injection is one way to supply an implementation at runtime, but a container does not establish inversion by itself. Likewise, a type switch is not automatically a design flaw; it is appropriate when the set of variants is intentionally closed and the switch is kept exhaustive.

## 1. OOP Principles

Each principle answers a concrete change or correctness question. Encapsulation asks which operations preserve the invariant; abstraction asks what callers must know; inheritance asks whether a subtype keeps the contract; polymorphism selects an implementation through that contract; composition delegates to an owned collaborator.

For the account below, `new BankAccount("Ada", 100)` starts with 100 cents. Withdrawing 30 returns true and leaves 70; withdrawing 90 returns false and leaves 70. A negative request throws, and overflow in a deposit throws before changing the balance.
Private fields alone would not enforce these rules. The example deliberately omits concurrency, multiple currencies and durable accounting; those belong in the authoritative ledger/transaction design.

#### 1. Encapsulation

```java
// Bundle data and methods, hide internal details
class BankAccount {
    private long balanceCents;
    private final String owner;

    public BankAccount(String owner, long initialCents) {
        this.owner = java.util.Objects.requireNonNull(owner);
        if (initialCents < 0) throw new IllegalArgumentException("Negative balance");
        this.balanceCents = initialCents;
    }
    public void deposit(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("Amount must be positive");
        balanceCents = Math.addExact(balanceCents, cents);
    }
    public boolean withdraw(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (cents > balanceCents) return false;
        balanceCents -= cents;
        return true;
    }
    public long getBalanceCents() { return balanceCents; }
}
// One fixed currency with cent units; not a concurrent account or a durable ledger.

```

#### 2. Abstraction

Abstraction chooses the operations callers need and hides representation details behind them. It is not simply making fields private: a useful abstraction gives callers a small contract that remains stable when its implementation changes. An abstract class can share implementation as well as declare operations; an interface can express a role without requiring a shared superclass.

```java
abstract class Shape {
    abstract double area();

    final String dimensionsSummary() {
        return "Area: " + area();
    }
}

final class Circle extends Shape {
    private final double radius;

    Circle(double radius) {
        if (!Double.isFinite(radius) || radius < 0) {
            throw new IllegalArgumentException("radius must be finite and non-negative");
        }
        this.radius = radius;
    }

    @Override
    double area() { return Math.PI * radius * radius; }
}

final class Rectangle extends Shape {
    private final double width;
    private final double height;

    Rectangle(double width, double height) {
        if (!Double.isFinite(width) || width < 0
                || !Double.isFinite(height) || height < 0) {
            throw new IllegalArgumentException("dimensions must be finite and non-negative");
        }
        this.width = width;
        this.height = height;
    }

    @Override
    double area() { return width * height; }
}
```

Callers can use `Shape.area()` without knowing how each shape stores or calculates its dimensions. The private final fields and constructor checks protect the example's invariant; the abstract method supplies the variation point.

#### 3. Inheritance

Inheritance declares a subtype relationship: `Dog` promises to satisfy the operations and behavioral expectations of `Animal`. It also inherits implementation, but code reuse alone is not a sound reason to create a subtype. The base contract must make sense for every permitted child.

```java
abstract class Animal {
    private final String name;

    Animal(String name) {
        this.name = java.util.Objects.requireNonNull(name);
    }

    final String name() { return name; }
    abstract String sound();
}

final class Dog extends Animal {
    Dog(String name) { super(name); }

    @Override
    String sound() { return "barks"; }
}
```

`Dog` inherits the stable name behavior and supplies the operation that varies. Keep the superclass contract small; protected mutable state and overridable methods create coupling between the base class and every subclass.

#### 4. Polymorphism

Polymorphism lets code use a value through a shared type while the concrete value supplies the behavior. Java has two distinct rules here: overload resolution uses compile-time types, while overriding dispatches an eligible instance method using the runtime class.

```java
final class OverloadExample {
    static String kind(Object value) { return "object"; }
    static String kind(String value) { return "string"; }

    public static void main(String[] args) {
        Object value = "hello";
        System.out.println(kind(value)); // object: overload chosen from declared type
    }
}
```

```java
interface Speaker {
    String sound();
}

final class DogSpeaker implements Speaker {
    @Override
    public String sound() { return "barks"; }
}

final class PolymorphismExample {
    static void announce(Speaker speaker) {
        System.out.println(speaker.sound());
    }

    public static void main(String[] args) {
        Speaker speaker = new DogSpeaker();
        announce(speaker); // barks: implementation selected from runtime class
    }
}
```

This distinction explains why changing a variable's declared type can change the selected overload without changing the object. `@Override` asks the compiler to verify that a method really overrides an inherited declaration.

#### 5. Composition (HAS-A relationship)

Composition builds behavior by holding collaborators and delegating work to them. Unlike inheritance, it does not make the outer type a subtype of the collaborator. Inject collaborators when construction policy belongs outside the class or tests need controlled substitutes.

```java
import java.util.List;
import java.util.Objects;

interface Engine {
    void start();
}

record Wheel(String position) {}

final class Car {
    private final Engine engine;
    private final List<Wheel> wheels;

    Car(Engine engine, List<Wheel> wheels) {
        this.engine = Objects.requireNonNull(engine);
        this.wheels = List.copyOf(wheels);
        if (this.wheels.size() != 4) {
            throw new IllegalArgumentException("a car needs four wheels");
        }
    }

    void start() {
        engine.start();
    }
}
```

The constructor makes the dependencies and four-wheel invariant visible. Java stores references; a field alone does not establish exclusive ownership or lifecycle. The domain model must define whether a collaborator is shared, owned, replaceable or independently managed.

## 2. Interfaces vs Abstract Classes

Both can define contracts and methods, but they express different relationships:

| Choose | When | State and inheritance |
| -------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Interface | A type has a role that unrelated classes can implement | No per-instance fields; classes can implement several interfaces; interfaces can extend several interfaces |
| Abstract class | Related classes share state or a protected implementation contract | May have constructors, instance fields and concrete methods; a class can extend only one class |

An interface may supply `default`, `static` and `private` methods. If a class inherits conflicting defaults for the same signature from unrelated interfaces, it must resolve the conflict; Java does not choose arbitrarily.

```java
interface Auditable {
    default String label() { return "audit"; }
}

interface Displayable {
    default String label() { return "display"; }
}

final class Invoice implements Auditable, Displayable {
    @Override
    public String label() {
        return Auditable.super.label() + ":" + Displayable.super.label();
    }
}
```

## 3. SOLID Principles

SOLID helps locate the cost of change. Apply the principle that addresses the observed coupling; splitting every class, adding an interface for every implementation or forbidding every edit makes a design harder to follow.

#### S — Single Responsibility

A module should group behavior that changes for the same policy or actor. Validation rules, persistence format and email delivery usually change for different reasons, so a registration flow can coordinate separate collaborators. “One reason to change” is a diagnostic, not a rule that every method needs its own class.

#### O — Open/Closed

Keep a stable workflow independent of a known variation. Here checkout delegates the discount rule; adding a policy adds an implementation without editing the checkout calculation. The boundary is only useful if the policy contract is stable and new policies truly fit it.

```java
interface DiscountPolicy {
    // subtotal is non-negative; result must be between zero and subtotal.
    long discountCents(long subtotalCents);
}

final class Checkout {
    private final DiscountPolicy discount;

    Checkout(DiscountPolicy discount) {
        this.discount = java.util.Objects.requireNonNull(discount);
    }

    long totalCents(long subtotalCents) {
        if (subtotalCents < 0) throw new IllegalArgumentException();
        long reduction = discount.discountCents(subtotalCents);
        if (reduction < 0 || reduction > subtotalCents) {
            throw new IllegalStateException("discount violates its contract");
        }
        return subtotalCents - reduction;
    }
}

final class TenPercentDiscount implements DiscountPolicy {
    @Override
    public long discountCents(long subtotalCents) {
        return subtotalCents / 10;
    }
}
```

#### L — Liskov Substitution

A subtype must preserve the observable contract callers rely on. Matching method signatures is not enough: a subtype must not reject valid inputs, weaken promised results or add side effects that violate the base type's postconditions.

```java
class Rectangle {
    private int width;
    private int height;

    Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    void setWidth(int width) { this.width = width; }
    void setHeight(int height) { this.height = height; }
    int width() { return width; }
    int height() { return height; }
}

final class Square extends Rectangle {
    Square(int side) { super(side, side); }

    @Override
    void setWidth(int side) {
        super.setWidth(side);
        super.setHeight(side);
    }

    @Override
    void setHeight(int side) {
        super.setHeight(side);
        super.setWidth(side);
    }
}

final class GeometryLspExample {
    static void widen(Rectangle rectangle) {
        int oldHeight = rectangle.height();
        rectangle.setWidth(5);
        // The Rectangle contract says changing width leaves height unchanged.
        if (rectangle.height() != oldHeight) throw new AssertionError();
    }
}
```

Calling `widen(new Square(2))` fails that postcondition because changing the square's width also changes its height. The mathematical “is-a” relationship does not make this mutable API substitutable. Use an immutable common shape contract or redesign the mutation operations.

#### I — Interface Segregation

Clients should depend only on operations they can meaningfully support. A single `Worker` interface with `work()` and `eat()` forces an automated device either to fake eating or throw at runtime. Separate `Workable` and `Feedable` roles let each implementation take only the contract it fulfills.

```java
interface Workable { void work(); }
interface Feedable { void eat(); }

final class Robot implements Workable {
    @Override
    public void work() { /* perform assigned task */ }
}
```

#### D — Dependency Inversion

High-level policy should own the abstraction it needs; infrastructure implements that abstraction. Dependency injection is the act of supplying the implementation. It can support dependency inversion, but injecting a concrete detail into policy code does not invert ownership.

```java
interface PaymentGateway {
    PaymentResult charge(long amountCents, String idempotencyKey);
}

record PaymentResult(boolean accepted, String reference) {}

final class CheckoutService {
    private final PaymentGateway gateway;

    CheckoutService(PaymentGateway gateway) {
        this.gateway = java.util.Objects.requireNonNull(gateway);
    }

    PaymentResult pay(long amountCents, String idempotencyKey) {
        if (amountCents <= 0) throw new IllegalArgumentException();
        return gateway.charge(amountCents, idempotencyKey);
    }
}
```

The application composition root creates `CheckoutService` and a provider adapter, then passes the adapter through `PaymentGateway`. Every adapter must honor the same amount, idempotency and failure contract; an interface declaration alone cannot guarantee provider behavior.

## 4. Closed data models

Use a sealed hierarchy when the permitted variants are intentionally closed. Java 21 finalized pattern matching for `switch`; a record supplies component-based equality and accessors, but remains a reference type and is only shallowly immutable.

```java
sealed interface Outcome permits Success, Failure {}
record Success(String receipt) implements Outcome {}
record Failure(String reason) implements Outcome {}

final class OutcomeDescription {
    static String describe(Outcome outcome) {
        return switch (outcome) {
            case Success s -> "Receipt: " + s.receipt();
            case Failure f -> "Failed: " + f.reason();
        };
    }
}
```

Use open interface implementations when independently extensible behavior is the requirement. An exhaustive data switch is not inherently a SOLID violation.

---

## Summary

1. Interfaces expose roles; composition delegates behavior without a deep hierarchy.
2. Overloading chooses a signature at compile time; overriding dispatches at runtime.
3. Encapsulation must enforce invariants, including negative amounts and overflow.
4. SOLID describes dependency and substitution contracts rather than a required class count.
5. A `final` reference prevents reassignment; it does not freeze the referenced object. Defensive copies and deeply immutable state require separate decisions.

# Java — Concurrency & Multithreading

A stock service has one item left. Two requests both read `1`, both approve an order, then both write `0`. Each method was correct in isolation; the shared-state protocol was not. Java concurrency is about preserving invariants while independent work overlaps.

## Definition

A **Java thread** is a unit of execution: platform threads are scheduled by the OS, while virtual threads run on JVM-managed carrier threads. Each thread shares the heap and keeps its own **stack** (locals, call frames). Concurrency in Java is therefore defined by two separate specifications that must both be satisfied:

> **Textbook Definition:** Java concurrency coordinates independently progressing threads that may share memory. Correct shared-state access requires atomic operations and the visibility and ordering relationships specified by the Java Memory Model.

```text
Thread A: local stack ─┐
                       ├── shared heap
Thread B: local stack ─┘

happens-before edges make prior writes visible to later reads:
monitor/lock, volatile access, thread start/join, or a concurrent API contract
```

For each shared invariant, answer three questions separately: what makes the update atomic, what publishes the result to other threads, and what bounds the resources consumed? A `volatile` flag provides visibility and ordering for that variable, not an atomic check-then-act operation. `AtomicInteger` gives a linearizable counter update; `LongAdder` is useful for contended statistics, but its sum is not a reservation snapshot. Publish fully constructed objects through a documented synchronization edge; `final` fields have special guarantees only when the constructor does not leak `this`.

## First Principles

Once tasks share state, correctness depends on the Java Memory Model rather than the order observed in one test run:

1. **A race is an interleaving that breaks an invariant.** Two `count++` operations can both read the old value before either writes; the final count then misses one update.
2. **Choose the smallest primitive that owns the invariant.** Use an atomic operation for one variable, a lock for a multi-step state transition, or a concurrent collection for its documented compound operation. A thread-safe container does not make a sequence of calls atomic.
3. **Separate task cost from downstream capacity.** Virtual threads make blocked tasks cheaper; they do not add database connections, memory, remote-service quota, or deadlines.

## How It Works


### 1. Give each task an owner

```java
// A Callable returns a value; the executor owns scheduling and shutdown.
Callable<Integer> callable = () -> {
    Thread.sleep(100);
    return 42;
};
try (ExecutorService executor = Executors.newSingleThreadExecutor()) { // Java 21
    Future<Integer> future = executor.submit(callable);
    int result = future.get(); // blocks; caller must handle checked exceptions
}

// For many mostly-blocked tasks, create one virtual thread per task (Java 21+).
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Integer> result = executor.submit(callable);
    System.out.println(result.get());
}

```

#### Protect a state transition

```java
class Inventory {
    private int available = 1;

    synchronized boolean reserveOne() {
        if (available == 0) return false;
        available--;
        return true;
    }
}

```

Both the check and decrement use one monitor, so a second request observes the first request's update before it can reserve. Every reader and writer must use this same lock for the invariant to hold. `ReentrantLock` adds interruptible acquisition, timed attempts, and multiple conditions; use `ArrayBlockingQueue` when its queue contract fits instead of recreating it.

### 2. Coordinate on conditions

#### Producer-Consumer

```java
class BoundedBuffer<T> {
    private final Queue<T> queue = new LinkedList<>();
    private final int capacity;
    private final Lock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    BoundedBuffer(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("Positive capacity required");
        this.capacity = capacity;
    }

    public void put(T item) throws InterruptedException {
        java.util.Objects.requireNonNull(item);
        lock.lockInterruptibly();
        try {
            while (queue.size() == capacity) notFull.await();
            queue.add(item);
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.isEmpty()) notEmpty.await();
            T item = queue.poll();
            notFull.signal();
            return item;
        } finally {
            lock.unlock();
        }
    }
}

```

#### Follow a full put/take cycle

With capacity one, `put(A)` acquires the lock, inserts A, signals not-empty and releases. A subsequent producer of B sees the queue full and awaits not-full; await releases the lock. A consumer removes A, signals not-full and releases.
The producer must then reacquire and recheck the condition before inserting B. A signal is permission to retry the condition, not a reserved slot; spurious wakes and other contenders explain the `while` loops.

These fragments need `java.util.*`, `java.util.concurrent.*`, `java.util.concurrent.atomic.*` and `java.util.concurrent.locks.*` imports plus an enclosing class for standalone statements/methods. The buffer methods propagate interruption; callers must not swallow it. Production queue shutdown, deadlines and rejection behavior require their own policy.
Prefer a standard blocking queue when its contract fits.

#### Readers-Writers Problem

```java
class SharedValue {
    private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
    private int value;

    public int read() {
        rwLock.readLock().lock();
        try { return value; }
        finally { rwLock.readLock().unlock(); }
    }
    public void write(int replacement) {
        rwLock.writeLock().lock();
        try { value = replacement; }
        finally { rwLock.writeLock().unlock(); }
    }
}
// A read lock permits concurrent readers; do not mutate shared counters under it.

```

#### Dining Philosophers

```java
// All callers assign a stable, unique rank to each fork resource.
record Fork(int rank, ReentrantLock lock) {}

static void withForks(Fork left, Fork right, Runnable eat) throws InterruptedException {
    if (left.rank() == right.rank()) throw new IllegalArgumentException("Distinct fork ranks required");
    Fork first = left.rank() < right.rank() ? left : right;
    Fork second = first == left ? right : left;
    first.lock().lockInterruptibly();
    try {
        second.lock().lockInterruptibly();
        try { eat.run(); }
        finally { second.lock().unlock(); }
    } finally { first.lock().unlock(); }
}
```

Ordering removes a circular wait only if every participant uses the same resource order. A timeout needs a release/retry policy; it does not guarantee eventual progress by itself.

### 3. CompletableFuture

```java
// Domain helpers below are placeholders. Keep blocking I/O off the common pool.
try (ExecutorService io = Executors.newVirtualThreadPerTaskExecutor()) {
    CompletableFuture<Void> total = CompletableFuture
        .supplyAsync(() -> fetchUser(userId), io)
        .thenCompose(user -> CompletableFuture.supplyAsync(
            () -> fetchOrders(user.getId()), io))
        .thenApply(this::calculateTotal)
        .thenAccept(value -> System.out.println("Total: " + value))
        .exceptionally(ex -> {
            System.out.println("Error: " + ex.getMessage());
            return null;
        });

    CompletableFuture<String> serviceA = CompletableFuture.supplyAsync(this::callServiceA, io);
    CompletableFuture<String> serviceB = CompletableFuture.supplyAsync(this::callServiceB, io);

    // First completion, including an exceptional completion; not first success.
    CompletableFuture<Object> first = CompletableFuture.anyOf(serviceA, serviceB);
    first.thenAccept(value -> System.out.println("First completed: " + value));

    // allOf signals completion; it does not collect values or cancel siblings on failure.
    CompletableFuture<Void> both = CompletableFuture.allOf(serviceA, serviceB);
    both.thenRun(() -> System.out.println(serviceA.join() + serviceB.join()));
    CompletableFuture.allOf(total, both).join(); // keep the owned executor alive for the work
}

```

#### Completion, timeout and work cancellation are separate

`allOf` completes when all component futures complete; it does not return their values or automatically stop siblings after one fails. `anyOf` chooses the first completion, including failure. `orTimeout` makes the future complete exceptionally after a deadline, but does not prove its underlying I/O stopped. `CompletableFuture.cancel(true)` does not use interruption to control its computation; configure the transport deadline/cancellation and own the executor lifecycle.

The no-executor `*Async` overloads use `ForkJoinPool.commonPool()` by default. Use that default for suitable CPU-bound tasks; choose and own an executor for blocking work, and separately bound scarce downstream resources such as database connections.

A virtual thread makes blocked execution cheaper, not unlimited: database connections, memory, rate budgets and deadlines remain finite. Avoid pooling virtual threads to impose downstream concurrency; admit that resource with a semaphore or bounded queue. JDK 24 removed carrier pinning while blocked inside `synchronized`; native and foreign-function calls can still pin a carrier.
Code on older JDKs has the earlier monitor-pinning behavior, so diagnose the runtime actually deployed.

### 4. Thread Safety Patterns

```java
// Deeply immutable, properly constructed objects can be safely shared
final class ImmutablePoint {
    private final int x;
    private final int y;

    ImmutablePoint(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }
}

// Thread-local storage
ThreadLocal<Integer> threadLocal = ThreadLocal.withInitial(() -> 0);
try {
    threadLocal.set(42);
    int value = threadLocal.get();
} finally { threadLocal.remove(); } // important when pool threads outlive requests

// Atomic operations
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet(); // atomic increment
counter.compareAndSet(5, 10); // CAS operation

// ConcurrentHashMap
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
map.putIfAbsent("key", 1);
map.compute("key", (k, v) -> v == null ? 1 : v + 1);

```

### 5. Choose CPU parallelism deliberately

Parallel streams suit independent, CPU-bound transformations when splitting and joining costs less than the work. Keep the pipeline stateless and use a reduction or collector instead of mutating shared objects. They use fork/join execution whose pool is not a portable per-request configuration boundary; do not use them to schedule blocking I/O.
Compare against a warmed JMH benchmark, not one cold wall-clock run.

```java
List<Result> results = inputs.parallelStream()
    .map(this::pureCpuBoundTransform)
    .toList();
```

### 6. Distinguish deadlock, starvation, and livelock

| Failure | What stops progress | What an operator may observe |
| ---------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Deadlock | A cycle of threads waits on resources held by one another | The involved threads stay blocked; unrelated work may continue |
| Starvation | A contender repeatedly loses access to a resource or execution slot | Other work continues while one task waits without a progress bound |
| Livelock | Threads keep reacting and changing state without completing useful work | Threads remain active, but the operation does not finish |

Consistent global lock ordering removes circular wait only when every participant follows it. Fair locks can reduce barging but do not guarantee scheduler fairness or system-wide progress; timed acquisition needs an explicit release, retry, and backoff policy. Bounded executor queues also need a rejection policy so overload becomes visible instead of unbounded latency.

## Summary

1. **The Java Memory Model defines visibility** — `volatile`, `synchronized`, `final` semantics
2. **`java.util.concurrent` raises the abstraction** — executors, `CompletableFuture`, concurrent collections
3. **Virtual threads (21+) change the calculus** — cheap blocking tasks still need bounded database connections, memory, and deadlines
4. **Race conditions hide in check-then-act and compound operations** — atomicity via `Atomic*` or locks
5. **Deadlock prevention needs a consistent resource order** — timed attempts also need release/backoff and progress policy

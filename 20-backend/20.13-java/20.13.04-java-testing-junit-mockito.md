# Java — Testing with JUnit & Mockito

A test that mocks a repository can prove the service chose the expected branch, but it cannot prove PostgreSQL accepted the query or constraint. The useful question is not “unit or integration?”; it is “which real contract could fail here, and what is the least costly test that exercises it?”

## Definition

The JUnit project discovers and runs tests; its Jupiter programming model supplies lifecycle annotations and assertions. **Mockito** creates controllable test doubles for collaborators. A unit test does not require mocks: use a real value object and isolate only an external or independently owned boundary.

> **Textbook Definition:** Java testing compares observed behavior with expectations using a test execution framework such as JUnit. Mockito substitutes controllable collaborators and records interactions; those substitutes do not establish the correctness of real integrations.

```text
JUnit                             Mockito
@BeforeEach / @AfterEach          @Mock        → stub a collaborator
@Test / @ParameterizedTest        when(...).thenReturn(...)  → arrange
assertEquals / assertThrows       verify(...)  → assert the interaction
@ExtendWith(MockitoExtension)     @InjectMocks → wire the SUT
```

The split matters because each tool answers a different question:

- **JUnit checks the behavior you specify** — arrange the input, invoke one behavior, and assert on its observable result or failure. State assertions usually survive implementation changes better than verifying every call.
- **Mockito answers what crossed a collaborator boundary** — mocks can return controlled outcomes and record calls. Mockito can mock concrete and final types with its inline mock maker; that capability does not make every class a good seam or every mock useful.

Distinguish a **mock** (records interactions), a **stub** (returns configured answers), and a **fake** (a lightweight working implementation). Assert on outcomes first; verify interactions when the interaction itself is the contract, such as publishing a message. Keep tests against a real database or HTTP boundary separate because a mock cannot reveal SQL, serialization, transaction, or concurrency behavior.

## First Principles

Java's testing stack begins with a boundary: the compiler can check declared types, while tests need to exercise behavior that only appears at runtime.

1. **The compiler and tests establish different facts.** Static typing checks declared type relationships; JUnit checks runtime behavior such as values, failures and boundaries. Parameterized tests make the selected input variations visible.
2. **Mockito supplies a controllable collaborator at a seam.** An interface makes that seam explicit, but Mockito can also substitute concrete and final classes. Hard-to-control dependencies may reveal a missing design seam; mocking capability alone is not a design verdict.
3. **Test cost should match risk.** Keep fast behavior checks easy to run; add real-infrastructure tests where the database, broker, framework wiring, or HTTP contract can fail. A test pyramid is a useful pressure toward fast feedback, not a target ratio.

## How It Works


### 1. Increase test fidelity at the boundary

| Test boundary | What it establishes | What it leaves open |
| --------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| JUnit behavior test with real domain objects | Branches, invariants, exceptions, and returned values | Framework wiring and external-system semantics |
| Mockito at a collaborator seam | How the unit reacts to a controlled success, failure, or timeout | Whether the real collaborator honors the assumed contract |
| Spring test slice such as `@WebMvcTest` | MVC mapping, validation, serialization, filters, and configured authorization | A real server, token verification unless explicitly configured, and database behavior |
| `@DataJpaTest` with PostgreSQL Testcontainers | ORM mappings, generated SQL, constraints, migrations, and selected database behavior | Production topology, load, failover, and independently committed transactions |
| `@SpringBootTest` | The configured application context, optionally with an embedded server | Deployment environment and production traffic behavior |

JUnit Jupiter normally creates a fresh test instance per method; static state, shared dependencies, files, containers, and databases still need isolation. Spring caches compatible application contexts to reduce startup cost. A test annotated `@Transactional` rolls back its test-thread transaction by default, but a request through a real server runs in another thread and transaction.
Testcontainers needs an available container runtime and should use the production database family and relevant version; an in-memory compatibility mode does not reproduce PostgreSQL's planner, extensions, or concurrency semantics.

## Code Examples

Examples use Java 21 syntax with JUnit 6.0.3, Mockito 5, Spring Boot 4.1.1 / Framework 7, and Testcontainers 2.0.5. They target the current stable Spring Boot generation; Boot 4 split several test and web modules, and Testcontainers 2 moved database container classes into module packages. Pin compatible versions through the framework BOM and verify them against the project build.
Application types below are illustrative, not a complete project.

### JUnit Jupiter: lifecycle and parameterized inputs

```java
import org.junit.jupiter.api.*;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import static org.junit.jupiter.api.Assertions.*;

@DisplayName("Calculator Engine Tests")
class CalculatorTest {

    static class Calculator {
        double divide(int a, int b) {
            if (b == 0) throw new ArithmeticException("Division by zero");
            return (double) a / b;
        }
        int add(int a, int b) { return Math.addExact(a, b); }
    }
    private Calculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new Calculator();
    }

    @Test
    @DisplayName("Should divide cleanly and assert with delta tolerance")
    void shouldDivideTwoNumbers() {
        assertEquals(2.5, calculator.divide(5, 2), 0.001);
    }

    @Test
    @DisplayName("Should throw ArithmeticException when dividing by zero")
    void shouldThrowExceptionWhenDividingByZero() {
        ArithmeticException ex = assertThrows(ArithmeticException.class,
            () -> calculator.divide(5, 0));
        assertEquals("Division by zero", ex.getMessage());
    }

    @ParameterizedTest(name = "{0} + {1} should equal {2}")
    @CsvSource({
        "1, 1, 2",
        "2, 3, 5",
        "10, 20, 30",
        "-5, 5, 0"
    })
    void shouldAddMultiplePairs(int a, int b, int expected) {
        assertEquals(expected, calculator.add(a, b));
    }
}
```

### Mock only the external decision boundary

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.Captor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import java.util.Optional;
import static org.mockito.Mockito.*;
import static org.junit.jupiter.api.Assertions.*;

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;

    @Mock
    private PaymentGateway paymentGateway;

    @Mock
    private NotificationService notificationService;

    @Captor
    private ArgumentCaptor<Order> orderCaptor;

    @InjectMocks
    private OrderService orderService;

    @Test
    void shouldCreateOrderAndCapturePersistedEntity() {
        // Arrange
        OrderRequest request = new OrderRequest("prod-456", 2, 99.50);
        when(paymentGateway.charge(eq("prod-456"), anyDouble()))
            .thenReturn(new PaymentResult(true, "tx-999"));
        when(orderRepository.save(any(Order.class)))
            .thenAnswer(inv -> inv.getArgument(0));

        // Act
        Order created = orderService.createOrder(request);

        // Assert on return state
        assertNotNull(created);
        assertEquals(OrderStatus.CONFIRMED, created.getStatus());

        // Verify side-effect interactions and capture saved payload
        verify(orderRepository).save(orderCaptor.capture());
        Order savedOrder = orderCaptor.getValue();
        assertEquals("prod-456", savedOrder.getProductId());
        assertEquals("tx-999", savedOrder.getPaymentTransactionId());

        verify(notificationService).sendReceipt(eq(savedOrder));
    }
}
```

### Test HTTP behavior in the MVC slice

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.http.MediaType;
import org.springframework.security.test.context.support.WithMockUser; // spring-security-test
import org.springframework.test.web.servlet.MockMvc;
import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(UserController.class)
class UserControllerSliceTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private UserService userService;

    @Test
    @WithMockUser // adapt authorities to the real route policy; this does not test JWT decoding
    void shouldReturnUserPayloadWhenFound() throws Exception {
        when(userService.findById("usr-100"))
            .thenReturn(new UserResponse("usr-100", "Alice", "alice@example.com"));

        mockMvc.perform(get("/api/users/usr-100")
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(content().contentType(MediaType.APPLICATION_JSON))
            .andExpect(jsonPath("$.id").value("usr-100"))
            .andExpect(jsonPath("$.name").value("Alice"))
            .andExpect(jsonPath("$.email").value("alice@example.com"));
    }
}
```

### Exercise the real database contract

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.postgresql.PostgreSQLContainer;
import static org.junit.jupiter.api.Assertions.*;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.NONE)
@Testcontainers
@org.springframework.transaction.annotation.Transactional
class UserRepositoryIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine")
        .withDatabaseName("testdb")
        .withUsername("testuser")
        .withPassword("testpass");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private UserRepository userRepository;

    @Autowired
    private jakarta.persistence.EntityManager entityManager;

    @Test
    void shouldPersistAndQueryUsingRealPostgres() {
        UserEntity user = new UserEntity("usr-1", "alice@example.com");
        userRepository.saveAndFlush(user); // force SQL/constraints before the assertion
        entityManager.clear(); // next lookup must load from the database, not the same entity instance

        UserEntity retrieved = userRepository.findById("usr-1").orElseThrow();
        assertEquals("alice@example.com", retrieved.getEmail());
    }
}
```

The test transaction rolls back fixture rows after this in-process repository test. Apply the actual migrations and production-relevant settings; separately test commits, concurrent sessions, and remote HTTP effects. A container validates the selected database contract, not cluster failover.

### Keep larger fixtures readable

```java
public class UserTestDataBuilder {
    private String id = "usr-default";
    private String name = "Default User";
    private String email = "user@example.com";
    private boolean active = true;

    public UserTestDataBuilder withId(String id) { this.id = id; return this; }
    public UserTestDataBuilder withName(String name) { this.name = name; return this; }
    public UserTestDataBuilder withEmail(String email) { this.email = email; return this; }
    public UserTestDataBuilder inactive() { this.active = false; return this; }

    public User build() {
        return new User(id, name, email, active);
    }

    public static UserTestDataBuilder aUser() {
        return new UserTestDataBuilder();
    }
}

// Usage in tests:
User activeUser = UserTestDataBuilder.aUser().withEmail("alice@company.com").build();
```

## Summary

1. **JUnit runs checks; Jupiter defines the common test model.**
2. **Use Mockito for a boundary whose behavior you need to control.**
3. **Assert outcomes first; verify only interactions that are part of the contract.**
4. **Choose the smallest Spring test boundary that exercises the risk.**
5. **Use the target database in integration tests when its semantics matter.**

# Java — Testing with JUnit & Mockito


---

> Java unit and integration testing: JUnit 5, Mockito mocking, test data builders and API/integration testing patterns.

---

## Definition

JUnit and Mockito are two commonly cooperating tools with different responsibilities; a unit test does not require mocking: **JUnit** supplies the test *lifecycle and assertions*, and **Mockito** supplies *test doubles* for collaborators.

> **Textbook Definition:** Java testing compares observed behavior with expectations using a test execution framework such as JUnit. Mockito substitutes controllable collaborators and records interactions; those substitutes do not establish the correctness of real integrations.

```text
JUnit                             Mockito
@BeforeEach / @AfterEach          @Mock        → stub a collaborator
@Test / @ParameterizedTest        when(...).thenReturn(...)  → arrange
assertEquals / assertThrows       verify(...)  → assert the interaction
@ExtendWith(MockitoExtension)     @InjectMocks → wire the SUT
```

The definitional split matters because each answers a different question:

- **JUnit executes specified checks** — it defines a test as a method with a lifecycle: arrange state, act once, assert on outcomes. Assertion *on state* (return values, thrown exceptions) is preferred over assertion on interactions because it does not couple the test to the implementation.
- **Mockito answers "what did the SUT ask of its collaborators?"** — a mock is a *generated* implementation of an interface that records calls. It exists to isolate the unit under test from real I/O, and it is the enforcement point for dependency inversion: Mockito can mock concrete and final classes with its inline mock maker, though interface boundaries often simplify design, which is the testability signal behind DIP.

Three distinctions separate a good test suite from a slow brittle one: a **mock** (records interactions for verification) versus a **stub** (canned answers) versus a **fake** (working lightweight implementation; an in-memory repository, for example); asserting on **outcomes** rather than every interaction; and keeping **integration tests** (real DB/HTTP, separate lifecycle) distinct from unit tests, because mocking an ORM can miss real SQL and concurrency failures.

## First Principles

Java's testing stack follows from static typing plus DI:

1. **Types are the first test.** The compiler eliminates a class of bugs dynamically-typed languages catch at runtime — so tests focus on *behavior*, not shape. JUnit's assertions encode expected behavior; parameterized tests encode its variation space.
2. **Mockito works because Java's objects are substitutable by interface** (→ 20.13.02 DIP): mock the dependency, inject the mock (→ 20.2.1.04). The corollary: hard-to-control dependencies may reveal a missing design seam; Mockito can mock many statics and finals, so capability alone is not a design verdict.
3. **Test pyramid economics**: unit (fast, many, mock externals) → integration (slower, real DB/container via Testcontainers) → e2e (fewest, real everything). The pyramid exists because feedback latency is the binding constraint on refactoring confidence.

## How It Works

### JUnit 5 Architecture

JUnit 5 separates the testing engine into three modular layers:
- **JUnit Platform**: The foundation layer providing test discovery, execution APIs, and reporting interfaces used by IDEs (IntelliJ, Eclipse) and build tools (Maven, Gradle).
- **JUnit Jupiter**: The programming and extension model containing core annotations (`@Test`, `@BeforeEach`, `@ParameterizedTest`), assertions (`assertAll`, `assertThrows`), and the `@ExtendWith` extension mechanism.
- **JUnit Vintage**: A backwards-compatibility engine allowing legacy JUnit 3 and JUnit 4 tests to execute seamlessly on the modern platform.

By default, JUnit creates a new test class instance for every individual test method (`Lifecycle.PER_METHOD`), isolating ordinary instance fields; static state, reused dependencies, and external resources can still leak across tests.

### Mockito Internals & Test Double Seams

Mockito uses Byte Buddy-based mock makers. The inline mock maker can instrument many concrete/final types; mocks of interfaces and other types may use generated implementations. Its capabilities are not limited to subclassable interfaces.
- **Invocation Recording**: Every method call on a mock proxy is intercepted and appended to an internal invocation log.
- **Stub Matching**: When a method is called, Mockito inspects the invocation log against declared `when(...).thenReturn(...)` patterns using argument matchers (`any()`, `eq()`, `argThat()`).
- **Interaction Verification**: `verify(mock).method()` replays the recorded invocations to confirm whether specific interactions occurred, how many times (`times(n)`, `never()`, `atLeastOnce()`), and in what sequence (`inOrder()`).
- **Argument Capture**: `ArgumentCaptor<T>` extracts arguments passed to collaborator mocks during execution, allowing deep assertions on complex payloads that cannot easily be matched with static equality.

### Spring Boot Test Slicing vs Full Context

Spring Boot provides specialized slice annotations that load only the beans required for testing a specific application layer:
- **`@WebMvcTest`**: Boots only the web infrastructure (controllers, JSON serialization, validation, security filters). Collaborating business services are injected as `@MockitoBean` (Spring Framework 6.2+, including Boot 3.4+). Startup time depends on the configuration and context-cache reuse.
- **`@DataJpaTest`**: Configures only the persistence layer (JPA repositories, entities, EntityManager) and wraps every test in a database transaction with automatic rollback at completion.
- **`@SpringBootTest`**: Boots the complete `ApplicationContext` with all services, repositories, and configurations. It tests the configured application context; production deployment behavior still needs separate evidence but carries significant startup latency.

### Testcontainers: Real Infrastructure Over In-Memory Fakes

In-memory databases like H2 or Fongo historically provided fast integration tests, but introduced catastrophic divergence from production: H2 does not reproduce PostgreSQL's JSONB indexes, extensions, planner, or concurrency semantics. A compatibility mode is not a PostgreSQL implementation; check the specific syntax/version rather than assuming every locking clause is unsupported.

Testcontainers solves this by launching containers running the selected infrastructure versions (e.g. `postgres:16-alpine`, `confluentinc/cp-kafka`) via the Docker daemon for the duration of the test suite. With `@Testcontainers` and Dynamic Property Source (`@DynamicPropertySource`), Spring Boot dynamically binds database connection URLs to the ephemeral container port.

## Code Examples

Examples target Java 21, JUnit Jupiter 5.11, Mockito 5, Spring Boot 3.4+ / Framework 6.2+, and Testcontainers 1.x. Application types are illustrative dependencies, not a complete project. Boot 4 and Testcontainers 2 reorganize some packages; use the documentation for the versions in your build.

### 1. JUnit 5 Lifecycle and Parameterized Tests

```java
import org.junit.jupiter.api.*;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import static org.junit.jupiter.api.Assertions.*;

@DisplayName("Calculator Engine Tests")
class CalculatorTest {

    static class Calculator {
        double divide(int a, int b) {
            if (b == 0) throw new ArithmeticException("Division by zero");
            return (double) a / b;
        }
        int add(int a, int b) { return Math.addExact(a, b); }
    }
    private Calculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new Calculator();
    }

    @Test
    @DisplayName("Should divide cleanly and assert with delta tolerance")
    void shouldDivideTwoNumbers() {
        assertEquals(2.5, calculator.divide(5, 2), 0.001);
    }

    @Test
    @DisplayName("Should throw ArithmeticException when dividing by zero")
    void shouldThrowExceptionWhenDividingByZero() {
        ArithmeticException ex = assertThrows(ArithmeticException.class,
            () -> calculator.divide(5, 0));
        assertEquals("Division by zero", ex.getMessage());
    }

    @ParameterizedTest(name = "{0} + {1} should equal {2}")
    @CsvSource({
        "1, 1, 2",
        "2, 3, 5",
        "10, 20, 30",
        "-5, 5, 0"
    })
    void shouldAddMultiplePairs(int a, int b, int expected) {
        assertEquals(expected, calculator.add(a, b));
    }
}
```

### 2. Collaborator Mocking with Mockito & Argument Captor

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.Captor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import java.util.Optional;
import static org.mockito.Mockito.*;
import static org.junit.jupiter.api.Assertions.*;

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;

    @Mock
    private PaymentGateway paymentGateway;

    @Mock
    private NotificationService notificationService;

    @Captor
    private ArgumentCaptor<Order> orderCaptor;

    @InjectMocks
    private OrderService orderService;

    @Test
    void shouldCreateOrderAndCapturePersistedEntity() {
        // Arrange
        OrderRequest request = new OrderRequest("prod-456", 2, 99.50);
        when(paymentGateway.charge(eq("prod-456"), anyDouble()))
            .thenReturn(new PaymentResult(true, "tx-999"));
        when(orderRepository.save(any(Order.class)))
            .thenAnswer(inv -> inv.getArgument(0));

        // Act
        Order created = orderService.createOrder(request);

        // Assert on return state
        assertNotNull(created);
        assertEquals(OrderStatus.CONFIRMED, created.getStatus());

        // Verify side-effect interactions and capture saved payload
        verify(orderRepository).save(orderCaptor.capture());
        Order savedOrder = orderCaptor.getValue();
        assertEquals("prod-456", savedOrder.getProductId());
        assertEquals("tx-999", savedOrder.getPaymentTransactionId());

        verify(notificationService).sendReceipt(eq(savedOrder));
        verifyNoMoreInteractions(notificationService);
    }
}
```

### 3. Spring Boot Web Slice Testing (@WebMvcTest)

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.http.MediaType;
import org.springframework.security.test.context.support.WithMockUser; // spring-security-test
import org.springframework.test.web.servlet.MockMvc;
import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(UserController.class)
class UserControllerSliceTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private UserService userService;

    @Test
    @WithMockUser // adapt authorities to the real route policy; this does not test JWT decoding
    void shouldReturnUserPayloadWhenFound() throws Exception {
        when(userService.findById("usr-100"))
            .thenReturn(new UserResponse("usr-100", "Alice", "alice@example.com"));

        mockMvc.perform(get("/api/users/usr-100")
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(content().contentType(MediaType.APPLICATION_JSON))
            .andExpect(jsonPath("$.id").value("usr-100"))
            .andExpect(jsonPath("$.name").value("Alice"))
            .andExpect(jsonPath("$.email").value("alice@example.com"));
    }
}
```

### 4. Integration Testing with Testcontainers & PostgreSQL

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import static org.junit.jupiter.api.Assertions.*;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.NONE)
@Testcontainers
@org.springframework.transaction.annotation.Transactional
class UserRepositoryIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine")
        .withDatabaseName("testdb")
        .withUsername("testuser")
        .withPassword("testpass");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private UserRepository userRepository;

    @Autowired
    private jakarta.persistence.EntityManager entityManager;

    @Test
    void shouldPersistAndQueryUsingRealPostgres() {
        UserEntity user = new UserEntity("usr-1", "alice@example.com");
        userRepository.saveAndFlush(user); // force SQL/constraints before the assertion
        entityManager.clear(); // next lookup must load from the database, not the same entity instance

        UserEntity retrieved = userRepository.findById("usr-1").orElseThrow();
        assertEquals("alice@example.com", retrieved.getEmail());
    }
}
```

The transaction rolls back fixture rows after this in-process repository test. Apply the actual migrations and production-relevant settings; a test transaction can hide missing service boundaries, so separately test commits, concurrent sessions and remote HTTP effects. Container availability requires Docker and does not prove cluster failover.

### 5. Test Data Builders

```java
public class UserTestDataBuilder {
    private String id = "usr-default";
    private String name = "Default User";
    private String email = "user@example.com";
    private boolean active = true;

    public UserTestDataBuilder withId(String id) { this.id = id; return this; }
    public UserTestDataBuilder withName(String name) { this.name = name; return this; }
    public UserTestDataBuilder withEmail(String email) { this.email = email; return this; }
    public UserTestDataBuilder inactive() { this.active = false; return this; }

    public User build() {
        return new User(id, name, email, active);
    }

    public static UserTestDataBuilder aUser() {
        return new UserTestDataBuilder();
    }
}

// Usage in tests:
User activeUser = UserTestDataBuilder.aUser().withEmail("alice@company.com").build();
```

## Real-World Use Cases

- **Core Banking Ledger Transaction Verification**: Verifying that debit and credit operations succeed atomically against real PostgreSQL containers without risking test data pollution or schema drift.
- **External Payment Provider Seam (Stripe Webhook Handler)**: Using Mockito to simulate network timeouts, card declines, and idempotency key replays without making outbound HTTP calls to third-party APIs.
- **Security & Authorization Contract Verification**: Using `@WebMvcTest` with `@WithMockUser` to verify RBAC rules (403 Forbidden vs 200 OK) without running the heavy database tier.

## Common Mistakes

| Mistake | Root Cause | Fix |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Mocking value objects, records, and DTOs | Mocks represent stateful collaborator seams; mocking passive data couples tests to shapes | Instantiate real records/DTOs directly or use Test Data Builders |
| Over-verifying internal method interactions | `verify(collaborator, times(1)).step()` asserts internal implementation details | Assert on output state and return values; verify only external side effects (e.g. email sent) |
| Using in-memory H2 for JPA tests targeting PostgreSQL | H2 dialect hides PostgreSQL-specific SQL syntax, JSONB operators, and lock behaviors | Use Testcontainers with a real `@Container static PostgreSQLContainer<?>` |
| Overusing `@DirtiesContext` across test classes | Forces Spring Boot to discard and rebuild the ApplicationContext between test runs | Avoid modifying Spring beans; isolate test side-effects with `@Transactional` rollbacks |
| Retaining mutable static state across tests | Test methods execute with non-deterministic ordering, causing flaky state leaks | Use `@BeforeEach` resets or stick with JUnit 5 default `PER_METHOD` instance lifecycle |

## Best Practices

1. **Follow the AAA pattern (Arrange, Act, Assert)** — keep test phases visually separated with clear comments or line breaks
2. **Test behavior over implementation** — assert observable outputs, return values, and persisted state; avoid verifying internal private delegators
3. **Use ArgumentCaptor for assertions on collaborator payloads** — avoids complex matcher nests inside `verify()`
4. **Prefer Testcontainers over in-memory databases** — exercises the actual selected database dialect; match versions, migrations, and relevant configuration, and separately test deployment differences
5. **Use Spring test slices for targeted verification** — prefer `@WebMvcTest` or `@DataJpaTest` over full `@SpringBootTest` whenever possible to measure and improve feedback time
6. **Use Test Data Builders** — centralize entity instantiation defaults to keep test files clean and resilient to constructor refactors
7. **Keep unit tests fast enough for frequent feedback** — isolate unit tests completely from I/O, threads, and network calls

## Summary

1. **JUnit Platform executes engines such as Jupiter** — lifecycle, parameterized tests, assertions, tags
2. **Mockito for collaborators, never for value objects** — mocking data is a design smell
3. **Test behavior, not implementation** — verify() sparingly; state assertions first
4. **Spring Boot Test slices** — `@WebMvcTest` vs `@DataJpaTest` vs full `@SpringBootTest`
5. **Testcontainers beat in-memory databases** — real Postgres semantics without a shared staging env

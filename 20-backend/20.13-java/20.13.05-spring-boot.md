# Java — Spring Boot Essentials

An HTTP request can pass authentication and still return an uncommitted result, leak another tenant's data, or trigger a query per response row. Follow one request through Boot's container, MVC, service transaction, and database; each layer owns a different contract.

## Definition

**Spring Boot** is an opinionated application framework that turns the Spring Framework's dependency-injection container into a runnable service: it supplies **auto-configuration** (beans chosen from what is on the classpath), an **embedded server**, and a **starter** dependency model, so a service can start from a main class with concise configuration.

> **Textbook Definition:** Spring Boot builds runnable Spring applications through conditional auto-configuration, dependency starters and runtime conventions. Auto-configuration selects components from classpath and configuration conditions; it does not remove application ownership of behavior or operations.

```text
@SpringBootApplication  = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan

container lifecycle:  scan → instantiate beans → inject by type → run CommandLineRunner
                       └─ singleton scope by default; proxies for AOP concerns

the DI triangle (NestJS analogy):
  @Component/@Service  ↔  @Injectable() provider
  @Autowired ctor      ↔  constructor injection
  @Configuration bean  ↔  custom provider / module
```

Three ideas define its behavior, and they are the ones that cause production surprises:

1. **Constructor injection is the contract** — dependencies are visible in the signature, required at construction, and can be held in final fields. Field injection with `@Autowired` hides the dependency and prevents a plain constructor in tests.
2. **Auto-configuration is conditional** — beans are selected by each auto-configuration’s specific classpath, property and bean conditions; auto-configuration matches are explained by the **condition evaluation report** (`--debug`), which is the first tool to reach for when a bean is unexpectedly missing or unexpectedly present.
3. **Proxies change semantics** — `@Transactional`, `@Cacheable`, and `@Async` work by wrapping the bean in a proxy, so a self-invocation (calling your own annotated method from inside the class) bypasses that interception in proxy mode; an existing caller transaction may still apply.

The container enforces configured bean scopes (`singleton` default, `request`, `prototype`); it does not enforce the application's controller → service → repository architecture. A singleton is shared within its owning context, not globally across every context or process.

## First Principles

A service needs compatible dependencies, predictable wiring and explicit operational configuration. Spring Boot supplies conventions for those recurring requirements.

1. **Convention over configuration is the product.** Auto-configuration reads the classpath and wires sensible defaults — you override only what differs. The magic is conditional wiring (`@ConditionalOnClass`), which is why "how does Spring know?" is answerable by reading the conditions, not fearing them.
2. **DI is the substrate (→ 20.2.1.04)**: Boot adds opinionated auto-configuration on top of Spring's container — starters bundle a coherent dependency set so compatible versions are managed together. The starter system is supply-chain management as a feature.
3. **Production concerns are first-class**: actuator (health, metrics, → 50.1), externalized config profiles, graceful shutdown. Boot's thesis: a backend framework's job includes operating the thing, not just running it.

## 1. Carry the model over from NestJS

The architecture transfers, but enforcement points differ. Use this mapping to orient yourself, then explain the Spring lifecycle and boundary rather than translating annotations one for one:

| Concept | NestJS | Spring Boot |
| -------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------ |
| App bootstrap | `NestFactory.create(AppModule)` | `@SpringBootApplication` → `SpringApplication.run` |
| DI container | module providers + `@Injectable()` | IoC context + `@Component`/`@Service`/`@Repository` |
| Modules | `@Module({ imports, controllers, providers })` | `@Configuration` classes + component scan + starters |
| Controllers | `@Controller()` + `@Get/@Post` | `@RestController` + `@GetMapping/@PostMapping` |
| Pipes/validation | class-validator + ValidationPipe | Bean Validation (`@Valid`, `jakarta.validation`) |
| Guards | `CanActivate` + RolesGuard | Spring Security filter chain + `@PreAuthorize` |
| Interceptors | `@UseInterceptors` | `HandlerInterceptor` / `OncePerRequestFilter` |
| Exception filters | `@Catch` + `ExceptionFilter` | `@ControllerAdvice` + `@ExceptionHandler` |
| Background execution | BullMQ / durable queue workers | `@Scheduled` / `@Async` are in-process; durable queues need broker integration |
| Config | `@nestjs/config` + env validation | `application.yml` + `@ConfigurationProperties` |

**Transferable explanation template (use only your actual experience):** *"I've built this in Nest; in Spring it's the same architecture — the DI container, guards as the security filter chain, pipes as bean validation — compare the lifecycle and enforcement boundary, not just annotation names."*

## Trace one request through the whole application

For `POST /api/orders`, the security filter authenticates a permitted bearer token before MVC dispatch. MVC binds and validates the request DTO. The controller calls an injected service through its proxy; the transaction begins there.
The service checks tenant ownership and business state, and the repository executes parameterized SQL on that transaction's connection. The method returns, the transaction commits, and only then should the response claim the local operation committed.

If an exception is thrown, configured rollback rules choose whether the local transaction rolls back. A remote payment cannot be rolled back merely by a JPA rollback; use durable intent and uncertain-outcome recovery. A singleton service can receive concurrent requests, so keep request state in method arguments, not mutable instance fields.
Actuator readiness describes an operational policy, not the success of every request.

The snippets below are focused wiring sketches with omitted imports/domain implementations. They do not constitute a tested complete Spring application. Follow the pinned version's packages and verify security, database, HTTP and transaction boundaries separately.

## 2. Start-up, wiring, and request ownership

#### 1. Inversion of control & the bean lifecycle
`@SpringBootApplication` combines `@SpringBootConfiguration`, `@EnableAutoConfiguration`, and component scanning. Ordinary singleton beans are usually created eagerly; lazy configuration and special scopes change the lifecycle. Prefer constructor injection so required dependencies are visible.
Auto-configuration contributes beans when classpath, property, and existing-bean conditions match; use `--debug` and the condition report to understand a surprising result. Boot adds defaults and managed dependencies; plain Spring can also use Java configuration without XML.

A prototype bean is created when requested from the container; injecting it once into a singleton does not create a new instance per method call. Use an `ObjectProvider` or suitable scoped proxy when repeated lookup is intended. The container does not run prototype destruction callbacks: the consumer owns cleanup.

The self-invocation trap in code — `@Transactional` works by wrapping the bean in a proxy, so a call through `this` bypasses this interception; any transaction already active at the caller can still apply:

```java
@Service
public class OrderService {

    public void place(Order order) {
        validate(order);
        audit(order);            // self-invocation: this annotation does not start a transaction
    }

    @Transactional
    public void audit(Order order) { /* ... */ }
}
```

Fixes: move `@Transactional` to the public entry point (`place`), split `audit` into a second bean, or inject the proxy and call through it (`self.audit(...)`). Interviewers use this exact shape to test whether you know *why* it breaks, not just that it breaks.

#### 2. Starters and the dependency model
For Boot 4, the MVC starter is `spring-boot-starter-webmvc`; `spring-boot-starter-web` is deprecated in favor of it. Other focused modules include `spring-boot-starter-data-jpa`, `spring-boot-starter-security`, `spring-boot-starter-validation`, `spring-boot-starter-test`, and `spring-boot-starter-actuator`. The Boot BOM keeps a compatible dependency set; override a managed version only with compatibility and security validation.

#### 3. Layered request pipeline
`Servlet filter → DispatcherServlet → HandlerMapping → @RestController → @Service → @Repository/DataSource`. Keep filters for cross-cutting request boundaries, controllers for HTTP translation, services for use-case policy and transaction ownership, and repositories for persistence. The framework does not enforce this architecture for you.

#### 4. Configuration
`application.yml` supplies defaults; profile-specific files add environment differences. Select active profiles through deployment configuration rather than hard-coding `prod` in the packaged defaults. Externalize secrets with environment-backed configuration such as `${DB_PASSWORD}`; never commit them.
Bind related values with `@ConfigurationProperties` and validate them instead of scattering `@Value` fields.

```yaml
# application.yml
app:
  tenant:
    default-locale: de-DE
    max-upload-mb: 25
```

```java
@ConfigurationProperties(prefix = "app.tenant")
@Validated
public record TenantProps(
        @NotBlank String defaultLocale,
        @Min(1) int maxUploadMb) {}
```

Register the record with `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties(TenantProps.class)` and include the validation starter. A missing required bound value fails validation; unknown properties are ignored by default, so validation alone does not reject every typo — the same fail-fast contract as Nest's validated `ConfigModule`.

#### 5. Data access: Spring Data JPA
Repositories such as `PatientRepository extends JpaRepository<Patient, UUID>` are implemented by Spring. Choose a fetch plan for each use case so a loop does not trigger an N+1 query:

```java
// N+1: one query per lazy association
List<Order> orders = orderRepo.findByStatus(PENDING); // 1 query
orders.forEach(o -> o.getCustomer().getName());      // +N queries

// Fetch the association with the repository query
@EntityGraph(attributePaths = "customer")
List<Order> findByStatus(OrderStatus status);
```

Open Session in View (OSIV) can keep the persistence context open through MVC and hide lazy queries in response mapping; disable it when the service should own fetch planning (`spring.jpa.open-in-view=false`). Return DTOs for public APIs so persistence loading and serialization graphs do not define the contract. Use versioned migrations such as Flyway or Liquibase to evolve the schema.

#### 6. Transactions
`@Transactional` on service methods (default propagation REQUIRED, rollback on `RuntimeException` and `Error` by default — checked exceptions normally do not trigger rollback under the default policy; configure rollback rules deliberately):

```java
@Transactional
public void importFile(Path p) throws IOException {   // checked exception does not trigger rollback under the default policy
    /* ... */
}

@Transactional(rollbackFor = IOException.class)      // explicit: now it rolls back
public void importFileWithRollback(Path p) throws IOException { /* ... */ }
```
`@Transactional(readOnly = true)` marks a read-oriented transaction; treat it as a transaction-manager hint, not a universal write prohibition. Isolation, MVCC, serialization failures and deadlock retries depend on the selected database and transaction manager, so carry those guarantees through from the database chapter.

#### 7. Spring Security

Use the supported OAuth2 resource-server integration for bearer JWTs rather than a handwritten parsing filter. Authentication verifies signatures, expiry and issuer/audience policy; authorization then checks authorities and tenant/resource ownership. `@EnableMethodSecurity` enables method rules.

The following requires `spring-boot-starter-oauth2-resource-server` plus a trusted decoder configured with issuer, signing keys, and audience checks. Domain authorization remains in the service. Disabling CSRF is appropriate here only because credentials arrive exclusively in an explicit Authorization header; stateless cookie or browser-managed credentials can still need CSRF protection.

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .csrf(AbstractHttpConfigurer::disable)
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health").permitAll()
            .requestMatchers("/api/admin/**").hasAuthority("SCOPE_admin")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}
```

CORS is a separate browser-origin policy. Validate tenant access from trusted identity and persisted membership rather than accepting a tenant header as authority. Authentication failures normally produce 401; authenticated access denials produce 403.

#### 8. Actuator & operations
With the default base path, health and metrics are `/actuator/health` and `/actuator/metrics`. Choose a minimal public health response; expose detailed health, metrics, and info only to authorized operators. Never expose sensitive endpoints such as `env`, `beans`, or `heapdump` publicly.

## Summary

1. **Auto-configuration is conditional and inspectable.**
2. **A request crosses distinct HTTP, authorization, transaction, and persistence boundaries.**
3. **Proxy-based features apply only when execution crosses the proxy.**
4. **An ORM transaction cannot undo an external side effect.**
5. **Health and management endpoints need an explicit exposure policy.**

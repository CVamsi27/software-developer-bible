# Java — Spring Boot Essentials

> **TL;DR:** **Spring Boot is auto-configuration and starters wrapped around the Spring dependency-injection container, plus an embedded server — the product is the auto-configuration.** Know the container's semantics (bean scopes, qualifiers, lifecycle callbacks, and the proxies that make `@Transactional` and `@Async` work), how properties bind to typed configuration, what Actuator exposes, and the traps that follow from proxying: self-invocation silently skipping a transaction boundary, circular dependencies at startup, and a property name that never binds to the bean you think it does.

---

> TL;DR: Spring Boot is the Java-backend default: it *conventions-over-configures* the Spring Framework (DI container + MVC + transactions) into a runnable, opinionated app with embedded Tomcat, auto-configuration, and production ops built in (actuator, health, profiles). If you know NestJS, you already know Spring's architecture — the interview skill is mapping one to the other.

## First Principles

Spring Boot's design follows from one insight: configuration is the dominant cost of Java backends.

1. **Convention over configuration is the product.** Auto-configuration reads the classpath and wires sensible defaults — you override only what differs. The magic is conditional wiring (`@ConditionalOnClass`), which is why "how does Spring know?" is answerable by reading the conditions, not fearing them.
2. **DI is the substrate (→ 20.2.1.04)**: Boot adds opinionated auto-configuration on top of Spring's container — starters bundle a coherent dependency set so versions can't fight. The starter system is supply-chain management as a feature.
3. **Production concerns are first-class**: actuator (health, metrics, → 50.1), externalized config profiles, graceful shutdown. Boot's thesis: a backend framework's job includes operating the thing, not just running it.

---

## Definition

**Spring Boot** is an opinionated application framework that turns the Spring Framework's dependency-injection container into a runnable service: it supplies **auto-configuration** (beans chosen from what is on the classpath), an **embedded server**, and a **starter** dependency model, so a service is one `main` class rather than a set of XML files.

```text
@SpringBootApplication  = @Configuration + @EnableAutoConfiguration + @ComponentScan

container lifecycle:  scan → instantiate beans → inject by type → run CommandLineRunner
                       └─ singleton scope by default; proxies for AOP concerns

the DI triangle (NestJS analogy):
  @Component/@Service  ↔  @Injectable() provider
  @Autowired ctor      ↔  constructor injection
  @Configuration bean  ↔  custom provider / module
```

Three ideas define its behaviour, and they are the ones that cause production surprises:

1. **Constructor injection is the contract** — dependencies are visible in the signature, required (fails at startup, not at first request), and final/immutable. Field injection with `@Autowired` hides the dependency and prevents a plain constructor in tests.
2. **Auto-configuration is conditional** — beans are created *if* a class is present and no user bean already satisfies the type; the whole wiring is explained by the **condition evaluation report** (`--debug`), which is the first tool to reach for when a bean is unexpectedly missing or unexpectedly present.
3. **Proxies change semantics** — `@Transactional`, `@Cacheable`, and `@Async` work by wrapping the bean in a proxy, so a self-invocation (calling your own annotated method from inside the class) bypasses the annotation entirely; this single fact explains most "why didn't my transaction roll back?" bugs.

The scope boundaries (`singleton` default vs `request`/`prototype`) and the layered structure (controller → service → repository) are conventions the framework does not enforce — Spring's value is wiring, not architecture.

## The mental model: NestJS → Spring mapping

If you can explain Spring in terms of Nest, you prove transferable architecture understanding instead of rote recall:

| Concept | NestJS | Spring Boot |
| ----------------- | ---------------------------------------------- | ---------------------------------------------------- |
| App bootstrap | `NestFactory.create(AppModule)` | `@SpringBootApplication` → `SpringApplication.run` |
| DI container | module providers + `@Injectable()` | IoC context + `@Component`/`@Service`/`@Repository` |
| Modules | `@Module({ imports, controllers, providers })` | `@Configuration` classes + component scan + starters |
| Controllers | `@Controller()` + `@Get/@Post` | `@RestController` + `@GetMapping/@PostMapping` |
| Pipes/validation | class-validator + ValidationPipe | Bean Validation (`@Valid`, `jakarta.validation`) |
| Guards | `CanActivate` + RolesGuard | Spring Security filter chain + `@PreAuthorize` |
| Interceptors | `@UseInterceptors` | `HandlerInterceptor` / `OncePerRequestFilter` |
| Exception filters | `@Catch` + `ExceptionFilter` | `@ControllerAdvice` + `@ExceptionHandler` |
| Async queue | BullMQ / Postgres queue | `@Scheduled` + `@Async` (and full integrations) |
| Config | `@nestjs/config` + env validation | `application.yml` + `@ConfigurationProperties` |

**Interview opener:** *"I've built this in Nest; in Spring it's the same architecture — the DI container, guards as the security filter chain, pipes as bean validation — the names change, the design doesn't."*

## Core concepts (know each in one sentence + one detail)

### 1. Inversion of control & the bean lifecycle
`@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`. Beans are singleton by default, created eagerly, wired by type (constructor injection preferred). Lifecycle hooks: `@PostConstruct`, `InitializingBean`, `@PreDestroy`. Auto-configuration is the killer feature: conditional beans based on the classpath (e.g., `spring-boot-starter-data-jpa` on the classpath → `DataSource`/`JpaRepository` auto-wired). **Interview answer to "what does Spring Boot give you over Spring?"** = embedded server + starters + auto-configuration + actuator, removing the XML-config era.

### 2. Starters and the dependency model
`spring-boot-starter-web` (embedded Tomcat + MVC), `-data-jpa` (Hibernate), `-security`, `-validation`, `-test`, `-actuator`. One dependency pulls a coherent, version-managed set — the Maven/Gradle analogue of a Nest module with all its peers. Version management comes from the Spring Boot parent BOM — never pin transitive versions by hand.

### 3. Layered request pipeline
`Filter (servlet) → DispatcherServlet → HandlerMapping → @RestController → @Service → @Repository/DataSource`. Analogy to Nest: middleware → router → controller → provider → data access. Keep controllers thin (HTTP concerns), services transactional (business rules), repositories data-shaped. The layered architecture question is the Spring equivalent of "how do you structure a Nest app?"

### 4. Configuration
`application.yml` + `application-{profile}.yml`; profiles (`dev`/`test`/`prod`) via `spring.profiles.active`. Externalize secrets with env vars (`${DB_PASSWORD}`) — never commit them. Strongly-typed config via `@ConfigurationProperties(prefix="app.tenant")` + `@Validated`, instead of scattered `@Value`. **Same discipline as Nest's validated ConfigModule** — say exactly that.

### 5. Data access: Spring Data JPA
Repositories are interfaces (`interface PatientRepository extends JpaRepository<Patient, UUID>`) — Spring implements them at runtime. Watch the classic traps interviewers test:
- **N+1**: `@EntityGraph` / `join fetch` in `@Query`, never lazy-load in a loop.
- **The `open-in-view` default** (OSIV keeps the session open through the view/controller) — know it exists, know why it hides lazy-loading bugs, and that you can disable it (`spring.jpa.open-in-view=false`) and map DTOs in the service layer.
- Entity vs DTO: never return entities from REST endpoints (serialization cycles, schema leakage) — map to DTOs/records.
- Migrations: **Flyway/Liquibase** are the standard (Prisma migrate is the Nest-world analogue).

### 6. Transactions
`@Transactional` on service methods (default propagation REQUIRED, rollback on `RuntimeException` only — checked exceptions do NOT roll back unless you configure `rollbackFor`). Read-only hint (`@Transactional(readOnly=true)`) on queries. The isolation/ACID discussion is identical to the database chapter — bring the Postgres knowledge: MVCC, `REPEATABLE READ`, deadlock handling.

### 7. Spring Security
The filter chain is the framework's heart: `SecurityFilterChain` beans add filters in order — authentication (username/password, JWT, OAuth2) → authorization (`@PreAuthorize("hasRole('ADMIN')")` or `hasAuthority`, method security needs `@EnableMethodSecurity`) → CSRF (stateless APIs: disable; stateful session apps: keep) → CORS config. Stateless JWT APIs: `OncePerRequestFilter` parses the token and seeds the `SecurityContext`; the rest of the chain consults it. **Map to Nest**: `AuthGuard` + `RolesGuard` = this filter + method security. For a multi-tenant app you'd add a tenant filter setting context before data access — the exact TenantGuard pattern from Docita.

### 8. Actuator & ops
`/actuator/health`, `/metrics`, `/info` — the same signals as a Node health endpoint + Prometheus metrics. Production defaults: expose only `health` and `info` publicly, never `env`/`beans`/`heapdump` on the open internet.

## Common interview questions

**Q. Difference between `@Component`, `@Service`, `@Repository`, `@Controller`?**
All are `@Component` stereotypes registering beans; the subtypes add semantics: `@Service` = business layer (just a marker), `@Repository` = data access + translates persistence exceptions into Spring's `DataAccessException`, `@Controller`/`@RestController` = web layer with MVC handling. Pick the stereotype that names the layer — it documents intent and enables targeted AOP.

**Q. What is auto-configuration, and how do you debug it?**
Spring Boot inspects the classpath and conditionally creates beans (`@ConditionalOnClass`, `@ConditionalOnMissingBean`). Debug with `--debug` (auto-configuration report) and the `ConditionEvaluationReport`. Override by defining your own bean — your definition wins because of `@ConditionalOnMissingBean`.

**Q. `@Autowired` field vs constructor injection?**
Constructor injection: final fields, immutable, trivially testable, impossible to forget a dependency (fails fast). Field injection hides dependencies and breaks testing. **Constructor injection is the default answer.**

**Q. How would you secure a stateless REST API with JWT in Spring?**
1) Add `spring-boot-starter-security`; 2) define a `SecurityFilterChain` bean; 3) add a `JwtAuthenticationFilter extends OncePerRequestFilter` that validates the token and sets `SecurityContextHolder`; 4) stateless session, disable CSRF, configure CORS; 5) method security with `@PreAuthorize` for role/authority checks; 6) remember the 401 vs 403 story — authentication failures → 401 (`AuthenticationEntryPoint`), authorization failures → 403 (`AccessDeniedHandler`). Nest equivalent: `AuthGuard` + `RolesGuard` + exception filters.

**Q. How do you test a controller/service?**
`@WebMvcTest` (controller slice with mocked services + MockMvc), `@DataJpaTest` (repository slice, in-memory or Testcontainers Postgres), `@SpringBootTest` + `Testcontainers` for full integration, Mockito for collaborators. Same pyramid as the testing chapter — the slices are Spring's way of keeping tests fast.

**Q. Eureka + Zuul/Spring Cloud Gateway — defend the resume bullet.**
Eureka = service registry (each service registers its instance + heartbeat; clients fetch the registry and load-balance via Ribbon/Spring Cloud LoadBalancer). Zuul/Spring Cloud Gateway = the API gateway: routing, filtering (auth), rate limiting at the edge. The design questions are identical to the microservices chapter's discovery/gateway sections — the trade-offs (client-side discovery vs DNS, gateway as the auth edge, what happens when the registry is down) transfer 1:1.

## Common mistakes

- Returning JPA entities from controllers (serialize DTOs).
- Letting OSIV mask N+1 until production.
- `@Transactional` on private/self-invoked methods — **it silently does nothing** (proxy-based AOP).
- Forgetting checked exceptions don't roll back by default.
- Field injection everywhere → untestable, hidden dependency graph.
- Exposing actuator `env`/`beans` endpoints publicly.
- Copy-pasting security config instead of understanding the filter order.

## Summary

1. **Auto-configuration is the product** — starters + conditional beans replace manual wiring
2. **The dependency-injection container is Spring's core** — scopes, qualifiers, lifecycle hooks
3. **Spring MVC vs WebFlux** — servlet-blocking vs reactive; pick by I/O profile, not fashion
4. **Configuration profiles and externalization** follow 12-factor
5. **Spring Boot Actuator** — production endpoints for health/metrics that plug into your observability stack

## Cheat sheet

- Bootstrap: `@SpringBootApplication` (config + auto-config + component scan)
- DI: constructor injection of `@Service`/`@Repository` beans; singletons by default
- Web: `@RestController` + `@GetMapping`; validation with `@Valid` + `@ControllerAdvice`
- Data: `JpaRepository<Entity, Id>` interfaces; migrations via Flyway/Liquibase
- TX: `@Transactional` (readOnly for queries, rollbackFor for checked)
- Security: `SecurityFilterChain` + JWT filter → `SecurityContext` → `@PreAuthorize`
- Ops: actuator health/metrics, profiles, externalized config
- Map every concept to NestJS and you sound senior in either stack

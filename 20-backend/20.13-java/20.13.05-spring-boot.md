# Java — Spring Boot Essentials


## Definition

**Spring Boot** is an opinionated application framework that turns the Spring Framework's dependency-injection container into a runnable service: it supplies **auto-configuration** (beans chosen from what is on the classpath), an **embedded server**, and a **starter** dependency model, so a service can start from a main class with concise configuration.

```text
@SpringBootApplication  = @Configuration + @EnableAutoConfiguration + @ComponentScan

container lifecycle:  scan → instantiate beans → inject by type → run CommandLineRunner
                       └─ singleton scope by default; proxies for AOP concerns

the DI triangle (NestJS analogy):
  @Component/@Service  ↔  @Injectable() provider
  @Autowired ctor      ↔  constructor injection
  @Configuration bean  ↔  custom provider / module
```

Three ideas define its behavior, and they are the ones that cause production surprises:

1. **Constructor injection is the contract** — dependencies are visible in the signature, required at construction, and can be held in final fields. Field injection with `@Autowired` hides the dependency and prevents a plain constructor in tests.
2. **Auto-configuration is conditional** — beans are created *if* a class is present and no user bean already satisfies the type; the whole wiring is explained by the **condition evaluation report** (`--debug`), which is the first tool to reach for when a bean is unexpectedly missing or unexpectedly present.
3. **Proxies change semantics** — `@Transactional`, `@Cacheable`, and `@Async` work by wrapping the bean in a proxy, so a self-invocation (calling your own annotated method from inside the class) bypasses the annotation entirely; this single fact explains most "why didn't my transaction roll back?" bugs.

The scope boundaries (`singleton` default vs `request`/`prototype`) and the layered structure (controller → service → repository) are conventions the framework does not enforce — Spring's value is wiring, not architecture.

## First Principles

Spring Boot's design follows from one insight: configuration is the dominant cost of Java backends.

1. **Convention over configuration is the product.** Auto-configuration reads the classpath and wires sensible defaults — you override only what differs. The magic is conditional wiring (`@ConditionalOnClass`), which is why "how does Spring know?" is answerable by reading the conditions, not fearing them.
2. **DI is the substrate (→ 20.2.1.04)**: Boot adds opinionated auto-configuration on top of Spring's container — starters bundle a coherent dependency set so compatible versions are managed together. The starter system is supply-chain management as a feature.
3. **Production concerns are first-class**: actuator (health, metrics, → 50.1), externalized config profiles, graceful shutdown. Boot's thesis: a backend framework's job includes operating the thing, not just running it.

## Why this matters

Boot brings container wiring, HTTP, persistence, and operational endpoints into one application lifecycle. Study how each boundary is configured and tested rather than memorizing annotations.

These examples target Java 21 and Spring Boot 3.4+ / Spring Framework 6.2+ (Boot 3 packages). When using Boot 4, check the reorganized starter/test packages against its reference.

## The mental model: NestJS → Spring mapping

If you can explain Spring in terms of Nest, you prove transferable architecture understanding instead of rote recall:

| Concept | NestJS | Spring Boot |
| -------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------ |
| App bootstrap | `NestFactory.create(AppModule)` | `@SpringBootApplication` → `SpringApplication.run` |
| DI container | module providers + `@Injectable()` | IoC context + `@Component`/`@Service`/`@Repository` |
| Modules | `@Module({ imports, controllers, providers })` | `@Configuration` classes + component scan + starters |
| Controllers | `@Controller()` + `@Get/@Post` | `@RestController` + `@GetMapping/@PostMapping` |
| Pipes/validation | class-validator + ValidationPipe | Bean Validation (`@Valid`, `jakarta.validation`) |
| Guards | `CanActivate` + RolesGuard | Spring Security filter chain + `@PreAuthorize` |
| Interceptors | `@UseInterceptors` | `HandlerInterceptor` / `OncePerRequestFilter` |
| Exception filters | `@Catch` + `ExceptionFilter` | `@ControllerAdvice` + `@ExceptionHandler` |
| Background execution | BullMQ / durable queue workers | `@Scheduled` / `@Async` are in-process; durable queues need broker integration |
| Config | `@nestjs/config` + env validation | `application.yml` + `@ConfigurationProperties` |

**Interview opener:** *"I've built this in Nest; in Spring it's the same architecture — the DI container, guards as the security filter chain, pipes as bean validation — compare the lifecycle and enforcement boundary, not just annotation names."*

## Core concepts (know each in one sentence + one detail)

### 1. Inversion of control & the bean lifecycle
`@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`. Beans are singleton by default, created eagerly, wired by type (constructor injection preferred). Lifecycle hooks: `@PostConstruct`, `InitializingBean`, `@PreDestroy`. Auto-configuration is the killer feature: conditional beans based on the classpath (e.g., `spring-boot-starter-data-jpa` on the classpath → `DataSource`/`JpaRepository` auto-wired). **Interview answer to "what does Spring Boot give you over Spring?"** = embedded server + starters + auto-configuration + actuator, removing the XML-config era.

The self-invocation trap in code — `@Transactional` works by wrapping the bean in a proxy, so a call through `this` never enters the transaction boundary:

```java
@Service
public class OrderService {

    public void place(Order order) {
        validate(order);
        audit(order);            // self-invocation: bypasses the proxy — NO transaction
    }

    @Transactional
    public void audit(Order order) { /* ... */ }
}
```

Fixes: move `@Transactional` to the public entry point (`place`), split `audit` into a second bean, or inject the proxy and call through it (`self.audit(...)`). Interviewers use this exact shape to test whether you know *why* it breaks, not just that it breaks.

### 2. Starters and the dependency model
`spring-boot-starter-web` (embedded Tomcat + MVC), `-data-jpa` (Hibernate), `-security`, `-validation`, `-test`, `-actuator`. One dependency pulls a coherent, version-managed set — the Maven/Gradle analogue of a Nest module with all its peers. Version management comes from the Spring Boot parent BOM — override managed versions only deliberately, with compatibility and security validation.

### 3. Layered request pipeline
`Filter (servlet) → DispatcherServlet → HandlerMapping → @RestController → @Service → @Repository/DataSource`. Analogy to Nest: middleware → router → controller → provider → data access. Keep controllers thin (HTTP concerns), services transactional (business rules), repositories data-shaped. The layered architecture question is the Spring equivalent of "how do you structure a Nest app?"

### 4. Configuration
`application.yml` + `application-{profile}.yml`; profiles (`dev`/`test`/`prod`) via `spring.profiles.active`. Externalize secrets with env vars (`${DB_PASSWORD}`) — never commit them. Strongly-typed config via `@ConfigurationProperties(prefix="app.tenant")` + `@Validated`, instead of scattered `@Value`. **Same discipline as Nest's validated ConfigModule** — say exactly that.

```yaml
# application.yml
app:
  tenant:
    default-locale: de-DE
    max-upload-mb: 25
```

```java
@ConfigurationProperties(prefix = "app.tenant")
@Validated
public record TenantProps(
        @NotBlank String defaultLocale,
        @Min(1) int maxUploadMb) {}
```

Register the record with `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties(TenantProps.class)` and include the validation starter. A missing required bound value fails validation; unknown properties are ignored by default, so validation alone does not reject every typo — the same fail-fast contract as Nest's validated `ConfigModule`.

### 5. Data access: Spring Data JPA
Repositories are interfaces (`interface PatientRepository extends JpaRepository<Patient, UUID>`) — Spring implements them at runtime. Watch the classic traps interviewers test:
- **N+1**: `@EntityGraph` / `join fetch` in `@Query`, never lazy-load in a loop:

  ```java
  // N+1: one query per lazy association
  List<Order> orders = orderRepo.findByStatus(PENDING);   // 1 query
  orders.forEach(o -> o.getCustomer().getName());         // +N queries

  // fixed: the association ships with the query
  @EntityGraph(attributePaths = "customer")
  List<Order> findByStatus(OrderStatus status);
  ```
- **The `open-in-view` default** (OSIV keeps the session open through the view/controller) — know it exists, know why it hides lazy-loading bugs, and that you can disable it (`spring.jpa.open-in-view=false`) and map DTOs in the service layer.
- Entity vs DTO: never return entities from REST endpoints (serialization cycles, schema leakage) — map to DTOs/records.
- Migrations: **Flyway/Liquibase** are the standard (Prisma migrate is the Nest-world analogue).

### 6. Transactions
`@Transactional` on service methods (default propagation REQUIRED, rollback on `RuntimeException` and `Error` by default — checked exceptions do NOT roll back unless you configure `rollbackFor`):

```java
@Transactional
public void importFile(Path p) throws IOException {   // checked exception → NO rollback
    /* ... */
}

@Transactional(rollbackFor = IOException.class)      // explicit: now it rolls back
public void importFile(Path p) throws IOException { /* ... */ }
```
Read-only hint (`@Transactional(readOnly=true)`) on queries. The isolation/ACID discussion is identical to the database chapter — bring the Postgres knowledge: MVCC, `REPEATABLE READ`, deadlock handling.

### 7. Spring Security

Use the supported OAuth2 resource-server integration for bearer JWTs rather than a handwritten parsing filter. Authentication verifies signatures, expiry and issuer/audience policy; authorization then checks authorities and tenant/resource ownership. `@EnableMethodSecurity` enables method rules.

The following requires `spring-boot-starter-oauth2-resource-server` plus a trusted decoder configured with issuer, signing keys, and audience checks. Domain authorization remains in the service. Disabling CSRF is appropriate here only because credentials arrive exclusively in an explicit Authorization header; stateless cookie or browser-managed credentials can still need CSRF protection.

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .csrf(AbstractHttpConfigurer::disable)
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health").permitAll()
            .requestMatchers("/api/admin/**").hasAuthority("SCOPE_admin")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}
```

CORS is a separate browser-origin policy. Validate tenant access from trusted identity and persisted membership rather than accepting a tenant header as authority. Authentication failures normally produce 401; authenticated access denials produce 403.

### 8. Actuator & ops
`/actuator/health`, `/metrics`, `/info` — the same signals as a Node health endpoint + Prometheus metrics. Choose a minimal public health response; expose detailed health, metrics, and info only to authorized operators, never `env`/`beans`/`heapdump` on the open internet.

## Common mistakes

- Returning JPA entities from controllers (serialize DTOs).
- Letting OSIV mask N+1 until production.
- `@Transactional` on private/self-invoked methods — the annotation does not create a new interception boundary in proxy mode (an existing caller transaction can still apply).
- Forgetting checked exceptions don't roll back by default.
- Field injection everywhere → untestable, hidden dependency graph.
- Exposing actuator `env`/`beans` endpoints publicly.
- Copy-pasting security config instead of understanding the filter order.

## Summary

1. **Auto-configuration is the product** — starters + conditional beans replace manual wiring
2. **The dependency-injection container is Spring's core** — scopes, qualifiers, lifecycle hooks
3. **HTTP, persistence and security are separate boundaries** — configure and test each explicitly
4. **Configuration profiles and externalization** follow 12-factor
5. **Spring Boot Actuator** — production endpoints for health/metrics that plug into your observability stack

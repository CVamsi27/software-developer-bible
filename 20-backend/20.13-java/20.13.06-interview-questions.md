# Java Interview Questions

> 30 questions across the Java chapters — fundamentals, collections, OOP/SOLID, concurrency, and testing. Ask yourself the question, answer out loud in 60–90 seconds, then check the model answer.

## Language & Data Types

**Q1. What is the difference between `==` and `.equals()`?**
`==` compares *references* (or primitives by value); `.equals()` compares *logical content* as defined by the class. `Integer a = 127; Integer b = 127; a == b` is `true` only because of the Integer cache (−128..127); at 128 it flips to `false`. Strings are the classic trap: `"a" == "a"` can be true via interning, but any `new String("a")` breaks it. Rule: primitives → `==`; objects → `.equals()` (and `Objects.equals()` for null-safe).

**Q2. Why is `String` immutable, and what are the consequences?**
Immutability gives: safe interning/caching, thread safety, and security (no mutation of a value used in a class name or key). Consequences: every concatenation allocates a new object — use `StringBuilder` in loops, and `StringBuilder` over `StringBuffer` unless you need the (rarely justified) thread safety.

**Q3. Explain the difference between `ArrayList` and `LinkedList`, and when each is the right choice.**
`ArrayList` = resizable array: O(1) indexed access, O(n) amortized append, O(n) middle insert/remove (shifting). `LinkedList` = doubly-linked nodes: O(1) head/tail insert, O(n) random access and O(n) middle removal *unless* you already hold the node. Interviews usually want `ArrayList` — locality of reference beats pointer-chasing; `LinkedList` wins only for queue-like head/tail workloads (where `ArrayDeque` is still the better default).

**Q4. How does `HashMap` work internally? Walk through put and get.**
Backing array of buckets (default 16) + linked list (Java 7) or tree (Java 8+: buckets ≥ 8 convert to red-black trees, back at ≤ 6). `put`: hash(key) → spread (high bits XOR) → index = (n−1) & hash → if bucket empty, place node; else compare by `hashCode` then `equals`; equal → replace value; else append to chain/tree; if size > threshold (load factor 0.75 × capacity) → resize (double) and rehash. `get` follows the same index + equality path. Never use mutable keys — a key whose `hashCode` changes after insertion is unreachable.

**Q5. What happens if you override `equals()` but not `hashCode()`?**
You break the `hashCode`/`equals` contract: equal objects must produce equal hashes. Two "equal" objects land in different buckets, so `HashSet`/`HashMap` treat them as distinct — duplicates and lost lookups. Always override both together, and keep the hash based only on the fields `equals` uses.

**Q6. What is autoboxing and where does it bite you?**
Primitive ↔ wrapper conversion is automatic. It bites in: `Integer` caching (−128..127), NPEs from unboxing nulls, accidental boxing in hot loops (`sum += i` with `Integer sum` boxes every iteration), and `==` on wrappers comparing references.

**Q7. Difference between `abstract class` and `interface` (modern Java)?**
Abstract class: single inheritance, can hold state/fields, constructors, concrete methods. Interface: multiple inheritance of type, and since Java 8 `default`/`static` methods, since Java 9 private methods. Post-Java-8 the practical rule: use an interface to define a contract/role, an abstract class to share implementation state. Prefer interfaces for the API; abstract classes for skeletal implementations.

**Q8. What do `final`, `finally`, and `finalize()` do — and why is the third one gone?**
`final` = constant/not-overridable/not-extendable; `finally` = always-run cleanup block in exception handling; `finalize()` was a pre-GC hook — deprecated since Java 9 and removed in Java 14 because it's unpredictable (may never run, resurrects objects, breaks GC). Use `try`-with-resources for closeable things.

## OOP & SOLID

**Q9. Explain encapsulation, abstraction, inheritance, and polymorphism with a one-liner each.**
Encapsulation = hide state behind behavior (private fields + public methods). Abstraction = expose only the essential contract (interfaces). Inheritance = code reuse and an "is-a" relationship between types. Polymorphism = one interface, many implementations — the runtime picks the actual method via dynamic dispatch. Prefer composition over inheritance: it avoids the fragile-base-class problem and lets you swap behavior at runtime.

**Q10. What is the fragile base class problem?**
Subclasses depend on the *implementation* details of a superclass; changing the parent (even a private method's call pattern) can silently break children. Mitigations: favor composition/delegation, design the parent API deliberately, or seal the class.

**Q11. Walk through the SOLID principles from memory.**
S — Single Responsibility: a class has one reason to change. O — Open/Closed: open for extension, closed for modification (strategy/interface). L — Liskov Substitution: subtypes must be usable wherever their supertype is. I — Interface Segregation: don't force clients to depend on methods they don't use. D — Dependency Inversion: depend on abstractions, not concretions; inject dependencies. The interview tell is when you can name a violation in your own code and the fix.

## Concurrency

**Q12. What is the difference between a process and a thread?**
A process owns its address space and resources; threads share the process's memory and are the unit of scheduling. Threads are cheap to create and communicate via shared memory (needs synchronization); processes are isolated (crash-safe, communicate via IPC) but heavier.

**Q13. What is a deadlock, and what are the four Coffman conditions?**
A deadlock = threads each holding a resource and waiting for one another's, forever. Conditions: (1) mutual exclusion, (2) hold-and-wait, (3) no preemption, (4) circular wait. Break any one to prevent it — most common fixes: lock ordering (total order on resources), timeouts/tryLock, or single lock. `synchronized` blocks can deadlock; `ReentrantLock` with `tryLock(timeout)` degrades to failure instead of hanging.

**Q14. What is the difference between `synchronized` and `volatile`?**
`volatile` gives visibility only: reads/writes go to main memory, but compound operations (check-then-act, i++) are not atomic. `synchronized` gives visibility *and* mutual exclusion for a whole block. If two threads only need to *see* a flag change → `volatile`; if they mutate shared state in multiple steps → `synchronized`/locks/atomics.

**Q15. What is a starvation vs a livelock?**
Starvation: a thread never gets the resource it needs because others always win (unfair scheduling, low priority). Livelock: threads are not blocked but keep reacting to each other and make no progress (e.g., two polite threads both "you first"). Deadlock is the classic; interviews ask for the contrast to check whether you understand *why* threads stop progressing.

**Q16. What does `CompletableFuture` give you over raw threads?**
Composition of async work: `thenApply`/`thenCompose`/`thenCombine`, `exceptionally`/`whenComplete` for error paths, and `allOf`/`anyOf` for fan-out. It replaces callback nesting and lets you express a DAG of dependent tasks declaratively, with a shared pool (or a custom one you must supply for blocking work).

## Testing

**Q17. Unit vs integration vs API testing — what does each catch?**
Unit: one class/behavior in isolation, mocks for collaborators — catches logic bugs fast. Integration: real collaborators (DB, filesystem) — catches contract/assumption breaks. API/contract testing: drives the whole HTTP surface — catches serialization, auth, and schema regressions. A pyramid-shaped split (many unit, fewer integration, fewest e2e) keeps the suite fast and trustworthy.

**Q18. When would you mock, and what is the danger of over-mocking?**
Mock when the collaborator is slow, non-deterministic, or not yet written (external APIs, time, randomness). Danger: tests assert the *mock's behavior*, not real behavior — a suite where everything is mocked can be green while the system is broken (mocked `UserService` never reveals the real SQL bug). Prefer real collaborators or test doubles at the boundary; verify one mock interaction per test at most.

**Q19. What is a test data builder and why use it over inline object setup?**
It's a fluent factory (`UserBuilder.aUser().withRole(ADMIN).build()`) that defaults every field to a valid value and lets each test override only what it cares about. Fixes: setup duplication, tests breaking en masse when a field is added, and the "which of these 30 lines actually matters" readability problem. Pair with `assertThat` (AssertJ-style) for readable assertions.

**Q20. How do you test code that depends on time or randomness?**
Inject a clock and a random source (constructor injection), then control them in tests: fixed `Instant` for expiry logic, seeded generator or a stub sequence for "random" selection. Never read `System.currentTimeMillis()` or `Math.random()` directly inside the code under test — that's untestable by design.

## Language & Data Types

**Q1. What is the difference between `==` and `.equals()`?**
`==` compares *references* (or primitives by value); `.equals()` compares *logical content* as defined by the class. `Integer a = 127; Integer b = 127; a == b` is `true` only because of the Integer cache (−128..127); above that guaranteed range, identity is not portable: an implementation may cache more values. Strings are the classic trap: `"a" == "a"` can be true via interning, but any `new String("a")` breaks it. Rule: primitives → `==`; objects → `.equals()` (and `Objects.equals()` for null-safe).

**Q2. Why is `String` immutable, and what are the consequences?**
Immutability gives: safe interning/caching, thread safety, and security (no mutation of a value used in a class name or key). Consequences: runtime concatenation can allocate; constants are folded and implementations may optimize allocations — use `StringBuilder` in loops, and `StringBuilder` over `StringBuffer` unless you need the (rarely justified) thread safety.

**Q3. Explain the difference between `ArrayList` and `LinkedList`, and when each is the right choice.**
`ArrayList` = resizable array: O(1) indexed access, O(1) amortized append, O(n) middle insert/remove (shifting). `LinkedList` = doubly-linked nodes: O(1) head/tail insert, O(n) random access and O(n) middle removal *unless* a positioned iterator already identifies the node. Interviews usually want `ArrayList` — locality of reference beats pointer-chasing; `LinkedList` wins only for queue-like head/tail workloads (where `ArrayDeque` is still the better default).

**Q4. How does `HashMap` work internally? Walk through put and get.**
Backing array of buckets (default 16) + linked list (Java 7) or tree (Java 8+: crowded buckets can become tree bins only at sufficient table capacity (64 in OpenJDK); thresholds are implementation details). `put`: hash(key) → spread (high bits XOR) → index = (n−1) & hash → if bucket empty, place node; else compare by `hashCode` then `equals`; equal → replace value; else append to chain/tree; if size > threshold (load factor 0.75 × capacity) → resize (double) and rehash. `get` follows the same index + equality path. Never use mutable keys — a key whose equality/hash changes after insertion can lose lookup/membership correctness.

**Q5. What happens if you override `equals()` but not `hashCode()`?**
You break the `hashCode`/`equals` contract: equal objects must produce equal hashes. Two equal objects may have different hashes/buckets, so `HashSet`/`HashMap` treat them as distinct — duplicates and lost lookups. Always override both together, and keep the hash based only on the fields `equals` uses.

**Q6. What is autoboxing and where does it bite you?**
Primitive ↔ wrapper conversion is automatic. It bites in: `Integer` caching (−128..127), NPEs from unboxing nulls, accidental boxing in hot loops (`sum += i` with `Integer sum` boxes every iteration), and `==` on wrappers comparing references.

**Q7. When should you choose an interface or an abstract class in modern Java?**
Use an interface for a role that unrelated classes can implement. A class can implement several interfaces, and an interface can extend several interfaces; interfaces may define constants and `default`, `static` and `private` methods, but have no per-instance state. Use an abstract class when related implementations need shared instance state, constructors or protected implementation. A class can extend only one class. If two inherited interface defaults conflict, the class must resolve the conflict explicitly.

**Q8. What do `final`, `finally`, and `finalize()` do — and why is the third one gone?**
`final` = no reassignment/override/subclassing (not deep immutability); `finally` = cleanup on ordinary control flow (not guaranteed after process termination) in exception handling; `finalize()` is an unreliable finalization hook — deprecated since Java 9 and deprecated for removal in Java 18 (JEP 421), still present in Java 21 because it's unpredictable (may never run, resurrects objects, breaks GC). Use `try`-with-resources for closeable things.

## OOP & SOLID

**Q9. Explain encapsulation, abstraction, inheritance and polymorphism with a one-liner each.**
Encapsulation protects state by routing changes through invariant-preserving operations. Abstraction exposes the stable operations callers need while hiding representation. Inheritance creates a subtype and shares implementation; use it only when the child preserves the parent's behavioral contract. Polymorphism lets callers use a shared type while an overriding instance method is selected from the runtime class. Prefer composition for independent behavior that should be delegated or replaced.

**Q10. What is the fragile base class problem?**
Subclasses depend on the *implementation* details of a superclass; changing the parent (even a private method's call pattern) can silently break children. Mitigations: favor composition/delegation, design the parent API deliberately, or make the class final; sealing only limits permitted subclasses and still needs deliberate contracts.

**Q11. Walk through SOLID and explain when a principle changes the design.**
S — group behavior that changes for the same policy or actor; do not split classes mechanically. O — put a stable workflow behind an intentional variation point so a fitting new policy can be added without changing that workflow. L — preserve the supertype's accepted inputs, guarantees and observable postconditions; a square that changes a rectangle's height when only width is set violates a mutable rectangle contract. I — keep contracts small enough that each client can implement and use the operations it needs. D — let high-level policy own the abstraction and make infrastructure implement it. Constructor injection supplies an object; it is not dependency inversion if policy still depends on a concrete detail. Name the actual coupling and the cost it causes before proposing more interfaces.

## Concurrency

**Q12. What is the difference between a process and a thread?**
A process owns its address space and resources; threads share the process's memory and are the unit of scheduling. Platform threads have stack and OS costs; virtual threads reduce blocked-task overhead. Shared memory needs coordination. Processes use IPC and isolate many failures, but isolation does not guarantee crash safety.

**Q13. What is a deadlock, and what are the four Coffman conditions?**
A deadlock = threads each holding a resource and waiting for one another's, forever. Conditions: (1) mutual exclusion, (2) hold-and-wait, (3) no preemption, (4) circular wait. Break any one to prevent it — most common fixes: lock ordering (total order on resources), timeouts/tryLock, or single lock. `synchronized` blocks can deadlock; `ReentrantLock` with `tryLock(timeout)` can bound a particular acquisition attempt; callers must release held resources and define backoff/progress.

**Q14. What is the difference between `synchronized` and `volatile`?**
`volatile` provides visibility and ordering guarantees through the Java Memory Model; it is not a promise to bypass physical CPU caches, but compound operations (check-then-act, i++) are not atomic. `synchronized` gives visibility *and* mutual exclusion for a whole block. If two threads only need to *see* a flag change → `volatile`; if they mutate shared state in multiple steps → `synchronized`/locks/atomics.

**Q15. What is a starvation vs a livelock?**
Starvation: a thread never gets the resource it needs because others always win (unfair scheduling, low priority). Livelock: threads are not blocked but keep reacting to each other and make no progress (e.g., two polite threads both "you first"). Deadlock is the classic; interviews ask for the contrast to check whether you understand *why* threads stop progressing.

**Q16. What does `CompletableFuture` give you over raw threads?**
Composition of async work: `thenApply`/`thenCompose`/`thenCombine`, `exceptionally`/`whenComplete` for error paths, and `allOf`/`anyOf` for fan-out. It replaces callback nesting and lets you express a DAG of dependent tasks declaratively, with an explicit executor for blocking work. Non-async continuations may run on the completing/calling thread; timeouts and future cancellation do not prove the underlying work stopped.

## Testing

**Q17. Unit vs integration vs API testing — what does each catch?**
Unit: one class/behavior in isolation, mocks for collaborators — catches logic bugs fast. Integration: real collaborators (DB, filesystem) — catches contract/assumption breaks. API/contract testing: drives the whole HTTP surface — catches serialization, auth, and schema regressions. A pyramid-shaped split (many unit, fewer integration, fewest e2e) keeps the suite fast and trustworthy.

**Q18. When would you mock, and what is the danger of over-mocking?**
Mock when the collaborator is slow, non-deterministic, or not yet written (external APIs, time, randomness). Danger: tests assert the *mock's behavior*, not real behavior — a suite where everything is mocked can be green while the system is broken (mocked `UserService` never reveals the real SQL bug). Prefer real collaborators or test doubles at the boundary; verify the interactions needed to establish the external contract; there is no universal one-interaction limit.

**Q19. What is a test data builder and why use it over inline object setup?**
It's a fluent factory (`UserBuilder.aUser().withRole(ADMIN).build()`) that defaults every field to a valid value and lets each test override only what it cares about. Fixes: setup duplication, tests breaking en masse when a field is added, and the "which of these 30 lines actually matters" readability problem. Pair with `assertThat` (AssertJ-style) for readable assertions.

**Q20. How do you test code that depends on time or randomness?**
Inject a clock and a random source (constructor injection), then control them in tests: fixed `Instant` for expiry logic, seeded generator or a stub sequence for "random" selection. Direct time/random reads make deterministic boundary tests harder; an injected source provides precise control.

## Spring

**Q21. What does Spring Boot actually add over plain Spring?**
Four things: an embedded server (the app is a runnable jar, no external Tomcat), starters (one dependency pulls a version-managed, coherent set — override managed versions deliberately and validate compatibility), auto-configuration (beans chosen from the classpath, overridable by defining your own), and actuator (production endpoints for health/metrics). Plain Spring also supports Java configuration; Boot adds conditional conventions and integration.

**Q22. How does auto-configuration work, and how do you debug a missing or unexpected bean?**
Conditional wiring: `@ConditionalOnClass` creates beans when a class is on the classpath, `@ConditionalOnMissingBean` steps aside when you define your own — whether it backs off depends on that auto-configuration's conditions. Debug with `--debug` and the `ConditionEvaluationReport`, which lists every condition evaluated and why it matched or didn't. "How does Spring know?" is answered by reading the conditions, not fearing them.

**Q23. Why does `@Transactional` silently do nothing on a self-invoked or private method?**
Transactions are implemented by wrapping the bean in a proxy — a call through `this` never enters the proxy, so the annotation is bypassed in proxy mode (private methods cannot supply that proxy boundary); an existing caller transaction may still apply. Fixes: move the annotation to the public entry point, split the method into a second bean, or inject the proxy and call through it. Interviewers use this exact shape to test whether you know *why* it breaks.

**Q24. Constructor vs field injection — which, and why is it not a style debate?**
Constructor injection: dependencies are visible in the signature, required at construction, and can be stored in final fields (the dependency object may remain mutable) — trivially testable without Spring. Field `@Autowired` hides the dependency graph and forces reflection or a container to construct the class in tests. Constructor injection makes required dependencies and ordinary test construction explicit; field injection remains technically possible with container/reflection support.

**Q25. What is the open-session-in-view default, and why do teams disable it?**
OSIV keeps the Hibernate session open through the controller/view layer, so a lazy association accessed in a template triggers a query — hiding N+1 problems until production traffic. Disabling (`spring.jpa.open-in-view=false`) forces mapping to DTOs in the service layer and makes fetch strategy an explicit decision (`@EntityGraph`, `join fetch`) instead of an accident at render time.

**Q26. A checked exception is thrown inside a `@Transactional` method — rollback or not?**
Not by default: rollback fires on `RuntimeException` and `Error` only. `rollbackFor = IOException.class` (or whatever the checked type is) opts in. The production discipline is stating it the other way too — a silent no-rollback on a file-parsing method is a partial write waiting to happen.

**Q27. How do you secure a stateless REST API with JWT in Spring Security?**
Use OAuth2 resource-server JWT support with a trusted decoder, signature/issuer/audience/time validation, stateless sessions, and explicit route plus resource authorization. Method security requires `@EnableMethodSecurity`. Disable CSRF only for the verified credential transport, such as explicit bearer headers; stateless cookies remain susceptible. Configure CORS separately. Authentication failures normally use 401, access denials 403.

**Q28. Which actuator endpoints do you expose in production, and why?**
A minimal health response may be public; detailed health and info should be restricted to operators according to their content. `env`, `beans`, `heapdump`, and `threaddump` leak configuration, secrets, and memory contents — exposing them on the open internet is an instant finding in any security review. Behind an internal network or with Spring Security role-gating, the fuller set is fine for operators.

**Q29. `@ConfigurationProperties` vs `@Value` — when and why?**
`@ConfigurationProperties(prefix="app.tenant")` with `@Validated` binds a whole typed tree (a record with validation annotations), can fail startup on a missing required or invalid value when registered with validation; unknown properties are ignored by default, and groups related config in one injectable type. `@Value` suits one-off scalars; scattered across a service it becomes an unvalidated, untyped config surface. Same discipline as Nest's validated ConfigModule.

**Q30. Your resume lists Eureka and Zuul — defend that line in 2026.**
Name the concepts, then the modernization: Eureka is client-side service discovery (register + heartbeat, clients fetch the registry and load-balance); Zuul/Spring Cloud Gateway is the API gateway (edge routing, filtering, rate limiting). The honest addendum: Spring Cloud Gateway is a common modernization path from Spring Cloud Netflix Zuul 1, and Kubernetes Services, ingress, and service meshes offer alternatives to self-run registries; select according to the deployment platform — but the design trade-offs (client vs server-side discovery, gateway as the auth edge, registry-down behavior) remain relevant, while concrete lifecycle and failure behavior must be rechecked.

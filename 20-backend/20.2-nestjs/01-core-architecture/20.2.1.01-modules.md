# NestJS Modules

## Definition

A **Nest module** is a class decorated with `@Module()` that groups related providers and controllers. It tells Nest which dependencies it owns, which it needs from other modules, and which it makes available to those modules. These declarations form a dependency-injection boundary: they control where Nest can construct or supply a provider.

> **Textbook Definition:** A NestJS module declares a dependency-injection scope through its providers, controllers, imports and exports. Import and export relationships determine which provider tokens are available for dependency resolution across modules.

Suppose appointments need to check whether a user exists. The appointments feature should consume the users feature's public service without owning another copy of its internal dependencies. Modules express that relationship.

## First Principles

Before constructing an appointments service, a container must know how to construct its dependencies. If every class were available everywhere, accidental coupling would be invisible. If every feature registered its own copy of a shared service, caches and connections could be duplicated.

An explicit module graph answers both questions: **who owns this provider, and who may consume it?** A source-code import makes a class name available to TypeScript; a Nest module import makes exported providers available to the container. They are different operations.

## Read the four declarations as a dependency graph

| Declaration | Meaning inside this module |
| ----------- | ---------------------------------------------------------------------- |
| providers | Providers Nest can construct here, including token-based registrations |
| controllers | Request handlers owned by this module |
| imports | Modules whose exported providers this module consumes |
| exports | The provider tokens or imported modules exposed to consumers |

The root `AppModule` connects feature modules. Importing UsersModule into AppModule does not automatically expose UsersService to every sibling feature. AppointmentsModule must import the module that exports the provider it needs. [Nest module boundaries](https://docs.nestjs.com/modules)

## Trace one exported provider

This single-file example isolates wiring; a real project normally splits the classes into feature files.

```typescript
import { Inject, Injectable, Module } from '@nestjs/common';

@Injectable()
export class UsersService {
  exists(id: string): boolean {
    return id === 'u1'; // Teaching fixture, not persistence or authorization.
  }
}

@Module({
  providers: [UsersService],
  exports: [UsersService],
})
export class UsersModule {}

@Injectable()
export class AppointmentsService {
  constructor(@Inject(UsersService) private readonly users: UsersService) {}

  canSchedule(userId: string): boolean {
    return this.users.exists(userId);
  }
}

@Module({
  imports: [UsersModule],
  providers: [AppointmentsService],
  exports: [AppointmentsService],
})
export class AppointmentsModule {}

@Module({ imports: [AppointmentsModule] })
export class AppModule {}
```

1. Nest discovers AppointmentsModule through the root's imports.
2. AppointmentsModule imports UsersModule, which owns UsersService.
3. UsersModule exports the UsersService token, so Nest can resolve the constructor dependency.
4. AppointmentsService receives that provider and can call it.

In a Nest application context, `app.get(AppointmentsService).canSchedule('u1')` returns true and the same call with u2 returns false. This result means only that the fixture user exists; it does not check calendar conflicts or permission. The [provider fixture](20.2.1.03-providers.md#trace-a-token-into-one-operation) shows the complete application-context setup and cleanup.

Remove the export or the consuming import and this graph no longer resolves. Re-registering UsersService in AppointmentsModule may conceal the missing boundary while creating another provider instance. Import its owning module instead. A module-graph test should compile AppointmentsModule with its real imports so a missing export fails at the boundary where it matters.

## Sharing is different from provider lifetime

Default-scope providers are shared within their registration context. Importing the same ordinary feature module from several consumers shares its exported default-scope provider; registering the class separately in several modules can create separate instances.

Request-scoped and transient providers have different lifetimes. Changing scope affects allocation and dependency resolution; it is not a substitute for declaring imports/exports. Keep tenant identity out of mutable singleton fields: concurrent requests can otherwise overwrite each other's context.

A module is a code and container boundary, not automatically a separate process, deployment or microservice.

## Configure reusable modules with a dynamic module

A **dynamic module** returns module metadata from a configuration method. `forRoot()` and `forFeature()` are naming conventions, not special language syntax. Commonly, forRoot supplies application-wide configuration and forFeature registers feature-specific adapters or repositories.

```typescript
import { DynamicModule, Module } from '@nestjs/common';

export const MAIL_OPTIONS = Symbol('MAIL_OPTIONS');
export interface MailOptions {
  sender: string;
}

@Module({})
export class MailModule {
  static forRoot(options: MailOptions): DynamicModule {
    return {
      module: MailModule,
      providers: [{ provide: MAIL_OPTIONS, useValue: options }],
      exports: [MAIL_OPTIONS],
    };
  }
}
```

A consumer imports `MailModule.forRoot({ sender: 'notifications@example.com' })` and injects MAIL_OPTIONS using `@Inject(MAIL_OPTIONS)`. In a real mail module, export the sending service when that is the intended public API; configuration need not itself be public.

For asynchronous configuration, a `forRootAsync()` implementation typically returns a provider with `useFactory`, `inject` and any required `imports`. Nest resolves the factory's dependencies and awaits its result before constructing dependent providers. Putting ConfigModule first in an array is not a general initialization-order guarantee.

Different dynamic registrations can intentionally create different configurations. Avoid repeating root registration just to make a token visible; import/re-export the configured module through a clear owning boundary.

## Choose explicit imports before broader visibility

| Need | Mechanism | Boundary to remember |
| ------------------------------------------ | ---------------------------------------------------- | -------------------------------------------------------------------- |
| Several features consume one service | Export it from its owner; consumers import the owner | Do not register copies in each consumer |
| Facade module exposes another module's API | Import and re-export that module | A TypeScript barrel alone does not change DI visibility |
| Infrastructure needed almost everywhere | A narrowly scoped @Global module | Register it once; global visibility can hide dependencies |
| Rare, expensive provider work | LazyModuleLoader | Appropriate for provider logic, not adding HTTP routes after startup |
| Two features depend on each other | Refactor shared responsibility first | forwardRef is an escape hatch, not a design cure |

With `forwardRef`, module references on both sides of a module cycle must be handled; a provider-constructor cycle needs its own injection treatment. Prefer extracting an orchestrator or shared contract so dependencies point in one direction.

### Lazy loading has specific limits

Inject `LazyModuleLoader` from `@nestjs/core`, dynamically import the ordinary feature module, then call `loader.load(() => FeatureModule)`. Use the returned module reference to retrieve its provider. There is no framework `LazyModule` decorator to import from `@nestjs/core`.

Lazy-loaded module/service lifecycle hooks are not invoked. Controllers, gateways, resolvers and on-demand middleware cannot be treated as dynamically registered routes through this mechanism. Do not depend on normal bootstrap hooks to initialize a lazily loaded service. [Lazy-loading API and limitations](https://docs.nestjs.com/fundamentals/lazy-loading-modules)

## Summary

A module states which parts of the application it owns and which providers other modules may use. A provider belongs to the module where it is registered. To use an exported provider, another module imports that module. First make these connections clear; then decide whether dynamic configuration, provider lifetimes, global access, or lazy loading solves a specific need.

# NestJS Controllers

## Definition

A controller translates an HTTP request into an application operation and translates its result into an HTTP response. Nest reads `@Controller` and method decorators at startup to connect a method/path to a handler. The controller receives dependencies from its module; services own reusable product rules and persistence.

> **Textbook Definition:** A NestJS controller is a transport boundary whose registered route handlers extract request input, invoke application behavior and produce HTTP responses through the selected platform adapter.

## First Principles

A URL, JSON body and HTTP status have transport meanings; checking stock or creating an appointment has a product meaning. A queue consumer may need the same product rule without any HTTP request. Separating the boundary lets both transports call the service while mapping their own input, acknowledgments and errors.

Untrusted bytes do not become valid data merely because TypeScript names their type. The boundary needs runtime parsing/validation, verified caller context, resource permission and an explicit response projection. Each protects a different contract.

## Locate the handler inside the request

```text
HTTP adapter → middleware → guards → interceptors (before)
              → parameter pipes → controller → service
              → interceptors (after) → adapter response
                         failure → applicable exception filter
```

Routing selects a handler before its parameter pipes can validate input. Nest extracts `@Param`, `@Query` and `@Body` values, runs the attached pipes, then invokes the method. An exception changes the path; successful after-interceptor work is not automatically run as if the operation succeeded. [Request lifecycle](https://docs.nestjs.com/faq/request-lifecycle)

For Nest 11 with its Express adapter, put a literal route such as `/users/search` before `/users/:id`; otherwise the parameter route can consume `search` and its ParseIntPipe rejects it. A pipe does not ask the router to try a later handler. Adapter/version behavior belongs in migration tests.

## Run one create/read fixture

This complete single-file fixture targets Nest 11's Express adapter. It has no authentication or durable storage and belongs on loopback only. Save it as `controllers.ts` in a scratch directory with these packages:

```bash
npm install @nestjs/common@11 @nestjs/core@11 @nestjs/platform-express@11 reflect-metadata rxjs class-validator class-transformer
npm install --save-dev typescript@5 @types/node
npx tsc controllers.ts --target ES2022 --module commonjs --experimentalDecorators --emitDecoratorMetadata --strict --skipLibCheck --outDir dist
node dist/controllers.js
```

Retain the scratch lockfile to repeat the same package versions. Nest relies on legacy decorator metadata here; native Node TypeScript stripping alone does not compile this example.

```typescript
import 'reflect-metadata';
import {
  Body, Controller, Get, Inject, Injectable, Module,
  NotFoundException, Param, ParseIntPipe, Post, ValidationPipe,
} from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { IsEmail, IsString, Length } from 'class-validator';

class CreateUserDto {
  @IsString() @Length(2, 50)
  name!: string;
  @IsEmail()
  email!: string;
}

interface UserRow { id: number; name: string; email: string; internalNote: string }
@Injectable()
class UsersService {
  private nextId = 1;
  private readonly rows = new Map<number, UserRow>();
  create(dto: CreateUserDto): UserRow {
    const user = { id: this.nextId++, name: dto.name, email: dto.email,
      internalNote: 'fixture-only' };
    this.rows.set(user.id, user);
    return user;
  }
  find(id: number): UserRow | undefined { return this.rows.get(id); }
}
function publicUser(row: UserRow) {
  return { id: row.id, name: row.name, email: row.email };
}
@Controller('users')
class UsersController {
  constructor(@Inject(UsersService) private readonly users: UsersService) {}
  @Post()
  create(@Body() dto: CreateUserDto) { return publicUser(this.users.create(dto)); }
  @Get(':id')
  find(@Param('id', ParseIntPipe) id: number) {
    const user = this.users.find(id);
    if (!user) throw new NotFoundException('User not found');
    return publicUser(user);
  }
}
@Module({ controllers: [UsersController], providers: [UsersService] })
class AppModule {}
async function main() {
  const app = await NestFactory.create(AppModule, { logger: false });
  app.useGlobalPipes(new ValidationPipe({
    transform: true, whitelist: true, forbidNonWhitelisted: true,
  }));
  try {
    await app.listen(0, '127.0.0.1');
    const origin = await app.getUrl();
    const created = await fetch(origin + '/users', {
      method: 'POST', headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ name: 'Ada', email: 'ada@example.test' }),
    });
    console.log(created.status, await created.json());
    for (const id of ['1', 'nope', '2']) {
      const response = await fetch(origin + '/users/' + id);
      console.log(response.status, await response.json());
    }
  } finally { await app.close(); }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

The POST produces 201 and `{ id: 1, name: 'Ada', email: 'ada@example.test' }`. Nest uses 201 for POST by default; other handlers normally default to 200. Creation stores one row, then explicitly excludes its internal note. Reading `/users/1` returns 200 with the same projection. `/users/nope` fails ParseIntPipe with 400 before the service. `/users/2` passes parsing but the service returns no row, so the handler throws 404.

Change the POST to include `role: 'admin'`: the global pipe returns 400 for the undeclared field before creation. Without the registered ValidationPipe, DTO annotations alone perform no runtime validation. `transform: true` creates the DTO instance used for validation; it does not make every nested object, query or arbitrary string safe. Nested DTOs need their own validators and transformation metadata. A TypeScript `number` annotation alone does not parse a query string. Set an adapter-level body-size limit as well: DTO validation runs after the request parser has received the body, so it cannot bound bytes already buffered.

## Keep validation separate from authorization and commit

The fixture validates shape but grants no real permission. Production guards must verify a credential and establish trusted context; the operation must also authorize the particular resource/tenant. Client `role`, `tenantId`, query fields or route nesting are not that evidence. Avoid spreading request bodies into records or allowing them to overwrite a server-generated ID.

A service success is not necessarily durable: this fixture loses its Map on restart and each process has a separate copy. Real create operations need database constraints/transactions and an explicit acknowledgment contract. If a client loses the 201 after commit, retry can create another operation unless the API has a durable idempotency contract. Awaiting a promise owns its rejection; `async` does not move synchronous CPU work off the loop.

## Choose who owns the response

| Choice | Owner and consequence |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Return a value/promise | Nest owns the response; object/array serialization and applicable interceptors remain in the managed path |
| `@HttpCode(204)` | Declares a no-content response; do not promise a useful JSON body with 204 |
| `@Header('Cache-Control', 'no-store')` | Declares a fixed header; cache policy still depends on data and authorization context |
| `@Res()` | The native Express/Fastify response becomes the handler's responsibility; send/end it or the request can remain pending |
| `@Res({ passthrough: true })` | Set a header/cookie through the adapter, then return the value for Nest to send |

Native `@Res()` does not prevent all interceptors from running. It bypasses Nest's standard returned-value response path, so a response-mapping interceptor cannot project bytes already sent with `res.json`. Similarly, `plainToInstance(ResponseDto, row)` by itself is not proof that unknown sensitive properties are excluded: configure exclusion or construct a narrow projection as above, and test the actual response.

## Add transport variants where their contract differs

- **Lists:** parse defaults deliberately, then bound page size and validate filters/sort identifiers. An `@Query('page') page: number` annotation is insufficient. Parameterize SQL values and keep authorization in the data query; an unbounded list consumes memory even without a malicious field.
- **Versioning:** `@Version` metadata needs application versioning configuration. Paths, headers and media types have different cache/migration behavior. See [API versioning](../../20.3-rest-apis/01-design-and-contract/20.3.1.03-versioning.md).
- **Nested resources:** `/users/:userId/posts/:postId` expresses two IDs; verify that the post belongs to the authorized user. A route prefix does not establish that relation.
- **Uploads:** the Express Multer interceptor needs parser-level file/field/count limits before the post-parse file pipe. Size/type checks do not establish authorized storage paths or benign content. Fastify requires its compatible upload mechanism. See [file upload APIs](../../20.3-rest-apis/03-payloads-errors-integration/20.3.3.04-file-upload-apis.md).
- **Files and server-sent events:** define cancellation, source cleanup, byte/queue bounds and error behavior after headers. Use Nest's StreamableFile/SSE facilities where appropriate; an unowned `fileStream.pipe(res)` omits source failure ownership. A timer observable is a demonstration, not durable event history.
- **Sessions:** `@Session()` reads adapter-provided session state; configure middleware/storage/cookies first. Process-local storage differs across replicas, and an unchecked read-modify-write counter can lose concurrent updates.
- **GraphQL:** resolvers form another transport boundary around shared services; HTTP controller decorators do not define its schema. Its mechanism lives in [GraphQL execution](../../20.7-graphql/02-execution/INDEX.md).
- **Controller inheritance:** inherited route methods still need correct metadata, DI and response policy. Reusable service operations are often clearer than a broad generic controller with accidental endpoints.

## Summary

A controller owns the HTTP translation around a reusable service operation. Trace routing, parameter pipes, invocation and the chosen response owner. Runtime validation needs registered behavior, authorization needs trusted context, and persistence/retry correctness belongs to the operation's durable contract. Project the response deliberately and test its actual status and bytes.

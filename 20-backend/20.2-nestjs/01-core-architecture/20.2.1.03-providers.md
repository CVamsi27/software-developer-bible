# NestJS Providers

Trace a token into one operation. Save this complete fixture as `providers.ts`.

## Definition

A provider is a dependency registration that Nest can supply to a consumer. The registration binds a runtime token to a class, an existing object, a factory result or another provider. A controller can receive an orders service; that service can receive a repository without constructing or configuring it itself.

> **Textbook Definition:** A NestJS provider is a token-bound registration resolved by the container within module visibility and lifetime rules. Its binding selects a class instance, value, factory result or existing provider instance.

## First Principles

Before an operation can use a database client, someone must choose its implementation/configuration, wait for readiness, and eventually close it. If every controller constructs a client, each owns a separate pool and cannot readily substitute a test repository. A registration centralizes that construction decision while the consumer states the dependency it needs.

Construction and execution have separate failure boundaries. A correct container graph can supply a repository whose next query fails. Nest manages configured instances and lifecycle callbacks; it does not automatically invent shutdown behavior for every returned client or make a service transactionally correct.

## How It Works


### Trace a token into one operation

Save this complete fixture as `providers.ts`. Use the [controllers scratch setup](20.2.1.02-controllers.md#run-one-createread-fixture) and the same TypeScript flags, replacing its filename. This is a standalone application context, so it does not start HTTP routes.

```typescript
import 'reflect-metadata';
import { Inject, Injectable, Module, OnModuleDestroy } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';

export const USER_STORE = Symbol('USER_STORE');
export const USER_STORE_ALIAS = Symbol('USER_STORE_ALIAS');
interface UserStore { findName(id: string): Promise<string | null> }
@Injectable()
class MemoryUserStore implements UserStore, OnModuleDestroy {
  private readonly names = new Map([['u1', 'Ada']]);
  async findName(id: string) { return this.names.get(id) ?? null; }
  onModuleDestroy() { this.names.clear(); }
}
@Injectable()
class GreetingService {
  constructor(@Inject(USER_STORE) private readonly store: UserStore) {}
  async greet(id: string) {
    const name = await this.store.findName(id);
    return name === null ? null : `Hello, ${name}`;
  }
}
@Module({
  providers: [
    MemoryUserStore,
    { provide: USER_STORE, useExisting: MemoryUserStore },
    { provide: USER_STORE_ALIAS, useExisting: USER_STORE },
    GreetingService,
  ],
})
class AppModule {}
async function main() {
  const app = await NestFactory.createApplicationContext(AppModule, { logger: false });
  try {
    console.log(app.get(USER_STORE) === app.get(USER_STORE_ALIAS));
    console.log(await app.get(GreetingService).greet('u1'));
    console.log(await app.get(GreetingService).greet('u2'));
  } finally { await app.close(); }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

Nest registers MemoryUserStore once. USER_STORE points to that registration; USER_STORE_ALIAS points to the same resolved dependency. GreetingService receives it and returns `Hello, Ada` for u1, then null for u2.
The first output is true: `useExisting` aliases a provider; there is no `useAlias` registration option. Closing the context calls the fixture's declared cleanup hook.

Change both aliases to `useClass: MemoryUserStore` and they become separate registrations with separate instances. The class name matches but the identity comparison becomes false. Registering `MemoryUserStore` in a second feature module can likewise create another owner.
[Modules](20.2.1.01-modules.md) explains cross-module import/export sharing.

### 1. Select a binding after the ownership decision

| Binding | Construction decision | Consequence |
| --------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Class shorthand `GreetingService` | Token and implementation are the class | Nest resolves constructor dependencies |
| `useClass` | Construct a chosen implementation for this token | Two registrations can make two instances of the same class |
| `useValue` | Supply an existing object/value | Mutability and external ownership remain your responsibility |
| `useFactory` with `inject` | Call a function with resolved dependencies | Positional inject entries must match factory arguments; returned promises are awaited |
| `useExisting` | Resolve another registered token | Alias its resolved dependency; do not create another class instance |

`@Injectable()` supplies class metadata; it does not register the class in every module. Register it and make its token visible to the consumer. TypeScript interfaces disappear at runtime, so the UserStore interface cannot serve as a token.
Import the same exported Symbol constant rather than constructing another `Symbol('USER_STORE')` with a matching description.

A factory can supply an immutable configuration object or a third-party client. Check configuration before allocating that client; reject an unknown strategy instead of returning undefined or constructing every payment provider just to select one. For async initialization, dependent providers wait for the returned promise.
If initialization rejects, fail readiness; if it allocated resources before failing, clean those up explicitly. An arbitrary providers-array order is not a general startup-order contract.

### 2. Choose the lifetime of state

A **scope** specifies how the container shares an instance; it does not serialize concurrent method calls.

| Scope | Sharing | Practical boundary |
| --------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| DEFAULT | Shared in its registration context, normally for the application lifetime | Good for a stateless service or owned bounded pool; keep caller/tenant state out of mutable fields |
| REQUEST | One instance for a request/context, shared within that DI context | Construction propagates to consumers that depend on it; it costs allocations and is not process-wide state |
| TRANSIENT | A dedicated instance per consumer/inquirer | Does not mean a new object on every method call, and does not make the consumer request-scoped |

A default-declared service depending on a request-scoped service generally becomes request-scoped through **scope bubbling**. It is not universally a forbidden singleton/request mismatch. Request injection uses the REQUEST token from `@nestjs/core` with `@Inject(REQUEST)`, not an undecorated Express Request interface.
Gateways, durable shared connections and infrastructure that must remain singleton need particular care; prefer passing small verified operation context into business methods where that meets the requirement.

Request lifetime is not an authorization policy. A request header naming a tenant is untrusted until verified; even a separate RequestContext instance must carry that verified identity and the intended resource policy. Asynchronous calls can interleave on one JavaScript thread, so a singleton `this.currentTenant = ...` can leak between requests after an await.

For worker/standalone operations, HTTP request scope is not automatically created. [Dependency injection](20.2.1.04-dependency-injection.md) explains context-aware resolution instead of treating a request-scoped object as obtainable through every `app.get` call.

### 3. Own resources and side effects explicitly

A repository registration often owns one database pool per process, not one connection per repository method or one pool for the whole deployment. Budget workers/replicas together and let a lifecycle-owning provider close the actual client after admission/draining. Nest lifecycle hooks on request-scoped classes do not follow the singleton application-lifecycle contract.
See [shutdown](../04-quality-and-operations/20.2.4.03-lifecycle-hooks-graceful-shutdown.md).

Service methods still need transaction/constraint semantics. A read-then-update existence check can race with deletion; a cache fill can race with invalidation. Include verified tenant/projection in keys and bound TTL/admission.
Those mechanisms belong in [database transactions](../../20.4-database/03-transactions-and-replication/INDEX.md) and [caching](../../20.8-caching/INDEX.md), rather than a generic provider example.

An in-process event emitter has neither durable enqueue nor a database/broker atomic commit. Emitting `user.created` after a database write can lose the event if the process fails in between; synchronous listener throws and rejected asynchronous listeners need their own ownership. Use an outbox when that event is required.
A decorator extracting a user is a request-boundary helper, not authentication and not a new provider category. TypeOrmModule.forFeature registers repositories; an entity class itself is not thereby an instantiated business service.

## Summary

A provider binds a token to an owned dependency with a chosen lifetime. Trace one registration into its consumer before selecting a binding or scope. Alias existing resources when sharing is intended, await readiness, and declare cleanup.
Container correctness does not replace per-operation authorization, concurrency, transaction or durable event behavior.

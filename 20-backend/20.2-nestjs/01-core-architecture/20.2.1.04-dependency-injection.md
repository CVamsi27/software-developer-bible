# NestJS Dependency Injection

Nest starts, then throws a resolution error for a service whose imports all compile. The container needs a runtime identity for the dependency, a visible registration, and a construction context — three facts that a TypeScript type annotation does not provide. Follow one dependency from the consumer's constructor to the instance that answers it.

## Definition

Dependency injection means a component receives collaborators from outside instead of choosing and constructing them internally. Nest's container resolves a runtime token through the consumer's module graph, builds the dependency using its registration, and supplies the result according to its scope.

> **Textbook Definition:** Dependency injection separates dependency construction from dependency use. A container resolves registered tokens under visibility and lifetime rules, allowing application wiring to vary without changing the consumer's operation contract.

## First Principles

An orders service needs a repository operation; it does not need to know which database credentials, pool or fake implements it. If the service constructs the repository itself, implementation and readiness decisions become hidden inside the consumer. Supplying it externally makes those decisions observable at the application boundary.

The container needs three facts: a runtime identity for the dependency, a visible registration for that identity, and a construction context. A TypeScript source import gives the compiler a name; it does not provide all three facts to Nest. This explains why a class can compile yet fail during container resolution.

## How It Works


### 1. Follow resolution through the graph

```text
consumer constructor requests token
  → locate registration visible in owning module/imported exports
  → resolve that registration's dependencies
  → construct or await factory result in its scope/context
  → inject value into consumer
```

[Modules](20.2.1.01-modules.md) owns the import/export graph. [Providers](20.2.1.03-providers.md) owns binding and scope variants, including the runnable shared-alias fixture. Here the question is which identity/context the container resolves and how to diagnose a failed resolution.

With legacy TypeScript decorator metadata, Nest can infer many class constructor tokens. Interfaces, generics and type-only imports do not provide reliable runtime class identities; explicit `@Inject(TOKEN)` states the intended dependency. Explicit class tokens are also valid, not an antipattern.
A Symbol must be imported from its canonical declaration: another Symbol with the same text is unequal.

### 2. Resolve one request context explicitly

Save this Nest 11 example as `contexts.ts` and use the [controllers scratch compiler setup](20.2.1.02-controllers.md#run-one-createread-fixture) with this filename. It creates no HTTP listener. The context carries a fixture tenant supplied by the trusted caller, not a header read from an unverified request.

```typescript
import 'reflect-metadata';
import { Inject, Injectable, Module, Scope } from '@nestjs/common';
import { ContextIdFactory, ModuleRef, NestFactory, REQUEST } from '@nestjs/core';
interface OperationRequest { tenantId: string }
@Injectable({ scope: Scope.REQUEST })
class OperationContext {
  constructor(@Inject(REQUEST) private readonly request: OperationRequest) {}
  tenant() { return this.request.tenantId; }
}
@Injectable()
class ReportService {
  constructor(@Inject(OperationContext) private readonly context: OperationContext) {}
  tenant() { return this.context.tenant(); }
}
@Module({ providers: [OperationContext, ReportService] })
class AppModule {}
async function main() {
  const app = await NestFactory.createApplicationContext(AppModule, { logger: false });
  try {
    const ref = app.get(ModuleRef);
    const clinicA = ContextIdFactory.create();
    const clinicB = ContextIdFactory.create();
    ref.registerRequestByContextId({ tenantId: 'clinic-a' }, clinicA);
    ref.registerRequestByContextId({ tenantId: 'clinic-b' }, clinicB);
    const a1 = await ref.resolve(ReportService, clinicA);
    const a2 = await ref.resolve(ReportService, clinicA);
    const b = await ref.resolve(ReportService, clinicB);
    console.log(a1 === a2, a1 === b, a1.tenant(), b.tenant());
  } finally { await app.close(); }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

Output is `true false clinic-a clinic-b`. Nest gives resolutions in the same context the same request-scoped graph; another context gets another graph. Although ReportService's decorator declares the default scope, its request-scoped dependency bubbles scope to it.
The two tenants stay in their respective context objects.

`ModuleRef.get` retrieves already available static providers; it is not the way to retrieve request/transient scoped dependencies. `resolve` builds a scoped DI sub-tree. Calling resolve twice without a shared context ID can make separate trees. Register the actual request/context object when a resolved provider needs REQUEST; a newly generated ID alone supplies no verified caller identity.
In an HTTP handler, reuse its existing ContextIdFactory context when that is the intended lifetime.

### 3. Replace a dependency without changing its consumer

For an isolated provider test, use `Test.createTestingModule`, register the consumer and supply its dependency token with `useValue`, or call `overrideProvider(TOKEN).useValue(fake)` before `compile`. The fake must implement the operations the consumer uses, including asynchronous results and failure behavior. Close the testing module after use.

The provider fixture's GreetingService can then receive a fake store returning 'Grace' and produce `Hello, Grace` without changing the service. Removing USER_STORE produces a resolution failure during compile; registering a fake in an unrelated sibling module does not make it visible. A mocked isolated module does not validate production exports, database readiness or transaction behavior: also compile/test the actual feature graph.

### 4. Diagnose the identity before broadening visibility

| Symptom | Check | Why a quick workaround can hide it |
| -------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Cannot resolve constructor dependency | Exact token, its registration, importing module and owner's export | Re-registering a service can create another pool/cache |
| Interface typed but runtime token undefined/Object | Canonical runtime token and `@Inject` | TypeScript's structural type does not survive as an injection key |
| Factory receives wrong collaborator | Ordered `inject` tokens versus function parameters | All dependencies may exist but arrive in the wrong positions |
| Scoped provider unavailable through get | Correct resolve/context/request association | Making it global does not change lifetime or establish identity |
| Startup waits or rejects | Factory readiness, timeout and cleanup | Swallowing failure can let traffic reach a broken client |
| Repeated class has different state | Separate registration/module/dynamic-module identity | Same class name is not a process-wide singleton guarantee |

A narrowly chosen `@Optional()` dependency can model a documented fallback; it should not conceal an infrastructure requirement. `ModuleRef.get(token, { strict: false })` broadens lookup beyond the local module, so use it deliberately rather than as the usual repair for missing imports. Dynamic string-to-token dispatch can turn arbitrary client text into a service locator; validate an allowlisted operation and keep required collaborators visible.

### 5. Break construction cycles before using forwardRef

If UsersService requires OrdersService and OrdersService requires UsersService, neither can be fully constructed first in an ordinary acyclic graph. Often an orchestration service can depend on both without the two depending on each other. A shared repository/contract or domain event can also remove the cycle, with event durability chosen separately.

When a genuine cycle remains, `forwardRef` defers evaluation of the referenced token. Module-import cycles and provider-constructor cycles need their respective treatment on both sides. It does not make initialization order dependable or permit constructors to call a collaborator before it is usable.
JavaScript barrel/file-import cycles are another problem and may need file-structure changes. Request-scoped cycles have additional runtime identity hazards; prefer refactoring. [Circular dependencies](https://docs.nestjs.com/fundamentals/circular-dependency)

### 6. Preserve operational boundaries

Resolving a payment client supplies an object; it does not validate an amount, authenticate a caller or make a charge idempotent. Factories should validate configuration and await bounded readiness, not perform irreversible business operations during construction. A process-local event emitter does not coordinate a database commit with delivery.

A resource owner must implement cleanup through its lifetime contract; simply returning a pool from a factory is insufficient. Application signals need enabled shutdown behavior, admission/drain ordering and a deadline. Request-scoped objects do not receive application lifecycle hooks as if each request were a miniature application.
See [shutdown](../04-quality-and-operations/20.2.4.03-lifecycle-hooks-graceful-shutdown.md).

Do not impose a total providers-array construction order on unrelated async factories, rely on a container to enforce runtime method contracts, or put a current tenant in mutable singleton state. Measure scope allocation under representative load; there is no universal percentage overhead or automatic lazy first-use behavior.

## Summary

DI separates how a dependency is built from how it is used. Correct resolution needs a matching runtime token, visible registration and appropriate scope/context. Trace those facts before changing the graph.
Shared context IDs control scoped identity; tests can replace bindings, while real operations retain their authorization, transaction and recovery requirements.

# NestJS Middleware

## Definition

Middleware handles an HTTP request before Nest's handler-level guards, interceptors and pipes. It receives the adapter's request, response and continuation (`next`). It may attach transport context, finish the response, report an error, or pass control onward.

> **Textbook Definition:** NestJS middleware composes transport-level behavior through request/response/continuation interfaces before route execution. Its registration determines matching and order; class middleware can receive dependencies from its module.

## First Principles

A request identifier must exist before a logger uses it. Session parsing must happen before authentication reads a session. These dependencies require ordered work before the protected handler. Middleware provides that early transport boundary; it does not yet have a guard's selected controller/handler execution context.

The continuation transfers ownership. If middleware neither responds nor continues, the request remains pending. If it sends a response and then continues, another component can attempt a second response. Asynchronous callbacks also need explicit failure ownership: a later throw is outside the earlier synchronous call stack.

## Trace correlation and one terminal event

This Nest 11 Express fixture generates a server-owned request ID and records one response terminal event. Save as `middleware.ts` using the [core fixture compiler setup](../01-core-architecture/20.2.1.02-controllers.md#run-one-createread-fixture), adding `npm install --save-dev @types/express`. The endpoint is a loopback teaching fixture without authentication.

```typescript
import 'reflect-metadata';
import {
  Controller, Get, Injectable, MiddlewareConsumer, Module,
  NestMiddleware, NestModule, Req,
} from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { randomUUID } from 'node:crypto';
import { performance } from 'node:perf_hooks';
import type { Request, Response, NextFunction } from 'express';
type IdentifiedRequest = Request & { requestId: string };
const events: Array<Record<string, unknown>> = [];
@Injectable()
class CorrelationMiddleware implements NestMiddleware {
  use(req: IdentifiedRequest, res: Response, next: NextFunction) {
    req.requestId = randomUUID();
    res.setHeader('x-request-id', req.requestId);
    events.push({ stage: 'identified', requestId: req.requestId });
    next();
  }
}
@Injectable()
class CompletionMiddleware implements NestMiddleware {
  use(req: IdentifiedRequest, res: Response, next: NextFunction) {
    const started = performance.now();
    let recorded = false;
    const terminal = (kind: 'finished' | 'closed') => {
      if (recorded) return;
      recorded = true;
      res.removeListener('finish', finished);
      res.removeListener('close', closed);
      events.push({ stage: kind, requestId: req.requestId,
        status: res.statusCode, elapsedMs: performance.now() - started });
    };
    const finished = () => terminal('finished');
    const closed = () => terminal('closed');
    res.once('finish', finished);
    res.once('close', closed);
    next();
  }
}
@Controller('probe')
class ProbeController {
  @Get()
  get(@Req() req: IdentifiedRequest) {
    events.push({ stage: 'handler', requestId: req.requestId });
    return { requestId: req.requestId };
  }
}
@Module({ controllers: [ProbeController] })
class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(CorrelationMiddleware, CompletionMiddleware).forRoutes(ProbeController);
  }
}
async function main() {
  const app = await NestFactory.create(AppModule, { logger: false });
  try {
    await app.listen(0, '127.0.0.1');
    const response = await fetch((await app.getUrl()) + '/probe', {
      headers: { 'x-request-id': 'untrusted-client-value' },
    });
    console.log(response.status, await response.json());
    console.log(events.map(event => event.stage));
  } finally { await app.close(); }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

Output is 200 with a generated UUID and stages `identified, handler, finished`. The response header/body and terminal log use the same ID; the client field does not choose it. On an early disconnect, `close` can arrive before `finish`; record `closed` once and remove both listeners. `finish` means the server handed response bytes to the transport, not that the client received or processed them. Monitoring needs both terminal paths and bounded logging transport, not one success-only callback.

Changing registration to put CompletionMiddleware first can capture missing context. Set headers before calling next: downstream may synchronously send a response before control returns. Request IDs are useful log/trace fields, but unbounded IDs/raw URLs should not become metric label values.

## Register only the intended route surface

`consumer.apply(...).forRoutes(Controller)` scopes middleware to that controller. Route objects can select a method/path; `exclude` removes deliberate matches. `app.use` installs application-level adapter middleware, while class registration supports Nest DI. A module-scoped provider can be injected into a middleware class; middleware is not inherently outside the container.

Global middleware runs before module-bound middleware; root-module and imported-module registration affect ordering. Test dependencies across module boundaries instead of assuming provider-array order establishes the request order. Nest 11/Express 5 route wildcards use named forms such as `{*splat}` to include the root; use explicit controllers/routes when possible and test root, nested and excluded matches.

Function middleware is suitable when it has no injected dependencies. Express and Fastify expose different middleware/native interfaces; do not call Express response helpers on raw Fastify objects just because both use Node streams. Handler policy belongs in a guard with ExecutionContext when it depends on route metadata.

## Parsing and security need their receiving boundaries

Nest's Express adapter installs JSON/urlencoded parsers by default. Configure a parser's byte limit before expensive DTO validation; when replacing parsers through middleware, disable the default body parser deliberately. A handwritten `data` listener that concatenates unlimited text can exhaust memory, split UTF-8 characters, miss cancellation and throw outside owned error handling. Use the framework parser or [bounded HTTP reader](../../20.1-node.js/02-io-and-data/20.1.2.04-http-module.md).

Webhook signature verification must use the provider's unmodified bytes with configured raw-body support; reserializing a parsed object is not equivalent. Unsupported content types, decompression and multipart uploads need their own byte/count/time limits.

CORS is a browser response-read policy, not authentication. Configure credentials/origins/preflight deliberately through the adapter; `*` is unsuitable for credentialed responses. Trust proxy IP fields only for configured proxies. An `x-internal-request` header supplied by a client must never skip authentication. Validate a tenant selection against the verified principal's membership instead of treating a looked-up existing tenant as permission.

A regex deleting script tags is not a general sanitizer: SQL values need parameters, HTML needs contextual output encoding, and file/URL operations need resource policies. Keep request shape validation in pipes and authorization in guards/services. See [Node security boundaries](../../20.1-node.js/04-security-and-operations/20.1.4.01-node-security.md).

## Own asynchronous work and overload

Call `next(error)` for adapter callbacks whose errors need to enter the request failure path; do not throw from an unrelated timer/event listener or start an unowned promise. Return/await supported Nest middleware promises and ensure a deliberate terminal action. Process-level failure policy remains separate.

A process-local rate-limit Map needs bounded cardinality/expiry and differs across replicas; caching middleware results cannot create a global quota. Use an atomic shared limiter when that is the contract, then separately cap concurrent expensive work. Async/await does not move synchronous computation off the event loop. Middleware runs on every matching request, so measure logging, auth lookup and parser costs under the real workload.

## Summary

Middleware owns early transport work through an ordered continuation. Establish context before using it, respond or continue exactly as intended, and observe success/disconnect once. Parsing, authorization and resource limits protect distinct boundaries; adapter registration and asynchronous failure ownership must be tested in the real request path.

# NestJS Pipes

Trace a bounded query argument. Save this standalone Nest 11 pipe fixture as `pipes.ts` using the [core compiler setup](../01-core-architecture/20.2.1.02-controllers.md#run-one-createread-fixture).

## Definition

A pipe receives one extracted handler argument, checks or transforms it, then returns the value the handler should receive. Throwing an exception rejects the invocation. A pipe can parse a query string, validate a body or supply a default; it does not parse arbitrary HTTP bytes or authorize a resource.

> **Textbook Definition:** A NestJS pipe implements PipeTransform to validate or replace a handler argument before invocation. Its runtime contract is independent of the handler's erased TypeScript annotations.

## First Principles

`?limit=10` arrives as transport data. The handler needs a bounded integer, but `parseInt('10junk')` accepts a numeric prefix and an `|| 10` fallback silently changes zero or invalid data. A boundary must distinguish absent input, valid input and malformed input instead of treating all three as defaults.

Runtime validation also needs an actual schema. Interfaces and generic annotations disappear during compilation. A DTO class plus registered validation behavior can establish shape; it cannot prove prices, membership, uniqueness or capacity in concurrently changing systems.

## How It Works


### 1. Trace a bounded query argument

Save this standalone Nest 11 pipe fixture as `pipes.ts` using the [core compiler setup](../01-core-architecture/20.2.1.02-controllers.md#run-one-createread-fixture). It calls the pipe directly to isolate its conversion contract; HTTP registration is demonstrated in the controller chapter.

```typescript
import 'reflect-metadata';
import { BadRequestException, Injectable, PipeTransform } from '@nestjs/common';
@Injectable()
export class PageSizePipe implements PipeTransform<unknown, number> {
  transform(value: unknown): number {
    if (value === undefined) return 10;
    if (typeof value !== 'string' || !/^[1-9][0-9]{0,2}$/.test(value)) {
      throw new BadRequestException('Invalid page size');
    }
    const number = Number(value);
    if (!Number.isSafeInteger(number) || number > 100) {
      throw new BadRequestException('Invalid page size');
    }
    return number;
  }
}
const pipe = new PageSizePipe();
for (const value of [undefined, '25', '0', '10junk', '101', ['10']]) {
  try { console.log('accepted', pipe.transform(value)); }
  catch (error) {
    if (!(error instanceof BadRequestException)) throw error;
    console.log('rejected', error.getStatus());
  }
}
```

Outputs are accepted 10, accepted 25, then four rejected 400 results. The three-digit lexical limit bounds conversion work; the numerical bound establishes the product limit. `@Query('limit', PageSizePipe) limit: number` attaches this pipe to that argument. Here an empty string, null or repeated-value array is invalid, not absent.
If compatibility requires another policy, state and test it rather than coercing everything.

For multiple query fields, parse a narrow object: allowlist sort identifiers/order, bound pagination, and construct only accepted fields. Binding a SQL value does not allow arbitrary ORDER BY identifiers. Pagination counts and access filters belong to the data query, not the pipe's number conversion.

### 2. Select built-in parsing after stating the domain

| Pipe | What it establishes | What still needs checking |
| ------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- |
| ParseIntPipe / ParseFloatPipe | Supported numeric input becomes a number or rejects | Safe integer, sign, range and exact money units |
| ParseBoolPipe | Recognized boolean forms become boolean | Do not use truthiness of string `'false'` |
| ParseUUIDPipe / ParseEnumPipe | Specified format/enum membership | Resource existence, tenant ownership and current policy |
| ParseArrayPipe | Parses/checks configured array items | Item count, nested shape and aggregate work |
| DefaultValuePipe before parsing | Substitutes its documented missing-value default | It is not a catch-all repair for malformed nonmissing input |
| ValidationPipe | Uses DTO metadata and configured validator/transformer | Registration, runtime metatype, nested rules and business constraints |

A string ID may be the correct domain type; converting every parameter to number is not inherently an improvement. MongoDB ObjectId validation should match the locked driver's accepted format, with a stricter lexical contract if the public API requires it. Do not reflect the entire invalid value in a public error.

### 3. Understand the DTO configuration

The [controller fixture](../01-core-architecture/20.2.1.02-controllers.md#run-one-createread-fixture) owns the executable DTO create/read path and demonstrates rejected undeclared fields. `whitelist` removes properties without validation metadata; `forbidNonWhitelisted` rejects them instead. These are schema choices, not automatic authorization. Annotating a client `role` field as valid would still allow that role into the validated object unless business policy excludes it.

`transform: true` can return a DTO instance and configured primitive conversion. `enableImplicitConversion` is a broader class-transformer coercion choice; for example converting a nonempty `'false'` to Boolean can yield true. Prefer explicit domain parsing where representations differ. Nested validation requires `@ValidateNested`, an actual nested class instance (commonly `@Type(() => ChildDto)`), and child decorators.
Collections need array/count/item bounds, not merely `{ each: true }` on one field.

Define required versus optional deliberately. In class-validator, `@IsOptional` skips other validators for null and undefined; it does not mean only absence is accepted. PATCH's omission means leave unchanged, while null may mean clear or invalid according to the field contract.
Do not trim passwords, signed payloads or identifiers without a stated normalization rule.

### 4. Compare schema libraries without changing the boundary

Class-validator uses class decorators; Joi and Zod use explicit runtime schemas. All can implement a PipeTransform boundary, with their own coercion/unknown-field/error policies. A schema factory can supply the pipe; it need not depend on class reflection.
A manually constructed pipe without dependencies can be valid; `@Injectable` matters for container-managed construction/metadata rather than every possible `new Pipe()` call.

For Zod 4, `safeParse` returns success/data or error; its error details are `error.issues`, not the removed `error.errors` alias. Return safe public validation fields or a fixed message, then log only suitably redacted details. Async refinements need parseAsync/safeParseAsync.
Joi's converted `value` is the result to pass onward; returning the original input discards configured normalization. See the [Zod migration guide](https://zod.dev/v4/changelog).

A generic recursive trim/merge using attacker-controlled property names can alter prototype behavior or corrupt arrays. Construct known fields instead; bound input bytes/depth before schema processing. A schema cannot undo memory spent by an unbounded body parser.

### 5. Database checks and uploads retain their own contracts

An async “unique email” pipe can provide early feedback but cannot enforce uniqueness: two requests can both see no row, then insert. Keep a database unique constraint and map its known conflict; authorize resource lookups and avoid leaking another tenant's existence. An order's submitted price/customer/status may be well formed but still must be derived or authorized server-side.
Quantity needs an integer bound, not any floating number >= 1.

File pipes see an already parsed upload. Parser-level size/count/duration limits come first. A supplied MIME label alone does not prove file content; use the locked validator's content check where appropriate, then storage/content-safety policy.
The canonical [upload chapter](../../20.3-rest-apis/03-payloads-errors-integration/20.3.3.04-file-upload-apis.md) owns that lifecycle.

### 6. Registration and failure ordering

Pipes run after guards, so a guard that reads a raw ID or body field must validate the part it uses itself. Global, controller and route pipes run in binding order; parameter pipes then resolve from the last handler parameter to the first. For `update(@Body() body, @Param('id', ParseUUIDPipe) id)`, the ID pipe runs before body-parameter pipes.
Do not make parameter validation depend on side effects in another parameter's pipe.

`APP_PIPE` allows module DI for global registration; manually constructed instances need their dependencies supplied. Keep irreversible effects in an owned service operation after validation. Test both direct transform cases and real HTTP registration/DTO errors.

## Summary

A pipe establishes one argument's runtime contract before handler invocation. Distinguish absent, valid and malformed values; define coercion, bounds and unknown/null policies. DTO/library validation needs actual registration and runtime metadata.
Authorization, concurrent constraints, body parsing and upload resource limits remain separate boundaries.

# Request Context & AsyncLocalStorage

Trace interleaving, a retained timer and outside work. Save this complete standalone Node TypeScript fixture as `context.ts`; it uses no Nest decorators.

## Definition

Request context associates a small set of request facts with the asynchronous execution that needs them. Node's AsyncLocalStorage (ALS) propagates a store through supported asynchronous resources created inside `run(store, callback)`. Layers can read that store without a mutable global “current request”.

> **Textbook Definition:** Asynchronous context propagation associates metadata with an execution chain across supported async boundaries. AsyncLocalStorage preserves store association; it does not authenticate values, make them immutable, transfer them across processes or extend resource validity.

## First Principles

Two requests can overlap on one JavaScript thread: A sets a global tenant, waits for a database query, B changes the tenant, then A resumes with B's value. A global variable follows the process, not A's operation. Context storage instead follows the asynchronous resources created for each operation.

Ambient data is also a hidden dependency. A function can look parameter-free while reading a tenant or transaction. Keep such inputs narrow, document their required lifetime and fail when a required fact is absent.
Explicit business parameters and request-scoped DI remain valid choices; ALS is not the only correct mechanism or universally faster.

## How It Works


### 1. Trace interleaving, a retained timer and outside work

Save this complete standalone Node TypeScript fixture as `context.ts`; it uses no Nest decorators. Compile with `npx tsc context.ts --target ES2022 --module commonjs --strict --skipLibCheck --outDir dist` in a scratch directory with TypeScript and @types/node, then `node dist/context.js`.

```typescript
import { AsyncLocalStorage } from 'node:async_hooks';
import { setTimeout as wait } from 'node:timers/promises';
interface Context { readonly requestId: string; readonly tenantId: string }
const context = new AsyncLocalStorage<Readonly<Context>>();
function tenantId() {
  const store = context.getStore();
  if (!store) throw new Error('Verified operation context required');
  return store.tenantId;
}
async function main() {
  let retainedTimer: Promise<string> | undefined;
  const results = await Promise.all([
    context.run(Object.freeze({ requestId: 'r1', tenantId: 'clinic-a' }), async () => {
      retainedTimer = wait(30).then(() => tenantId());
      await wait(10);
      return tenantId();
    }),
    context.run(Object.freeze({ requestId: 'r2', tenantId: 'clinic-b' }), async () => {
      await wait(5);
      return tenantId();
    }),
  ]);
  console.log(results);
  console.log(await retainedTimer);
  console.log(context.getStore());
  try { tenantId(); }
  catch (error) { console.log(error instanceof Error ? error.message : 'unexpected'); }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

Outputs are `[clinic-a, clinic-b]`, `clinic-a`, undefined, then Verified operation context required. B resumes first, but Promise.all preserves input order and each continuation sees its own store. The timer created inside A still sees A after A's main callback finishes.
Outside those roots no store is established, so required access rejects.

`run` restores the surrounding context after the synchronous callback invocation; supported descendant resources can retain the inner association beyond that return. Timers created inside a request are not automatically detached into empty context merely because they run later. Conversely, a pre-existing scheduler/pool callback or another process does not gain the caller's store just because it eventually runs related work.

### 2. Establish identity in the actual lifecycle order

HTTP middleware runs before guards. It can establish a validated/generated correlation ID and an empty unauthenticated context; it cannot read a principal from a guard that has not run yet. Two deliberate designs are possible:

1. Authenticate in earlier middleware, then enter a frozen context with verified identity.
2. Enter an early context for correlation, let the guard verify identity, then wrap the downstream continuation in a new verified context at a handler-level boundary.

If an interceptor enters ALS around Observable work, enter around the actual subscription. For example, with RxJS `Observable` imported and a verified store supplied, `new Observable(subscriber => context.run(verifiedStore, () => next.handle().subscribe(subscriber)))` enters context when subscribed and returns the inner subscription for teardown. Test the actual async continuation: merely constructing a lazy Observable inside `run` may not cover its later subscription.
Alternatively keep one early store with an explicitly controlled identity-establishment API, documented mutability and no parallel work before identity is set. Do not claim a readonly TypeScript interface freezes a runtime object; Object.freeze is shallow.

A client request ID is untrusted correlation metadata. Generate a local ID as in [middleware](20.2.2.01-middleware.md), or validate length/format and retain a distinct trusted identity policy. Parse traceparent through the tracing library: the whole header is not a trace ID.
Trust configured proxy context deliberately and never turn a client tenant header into authorization merely by storing it.

### 3. Carry facts across new roots deliberately

| Boundary | Default association | Required decision |
| --------------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Supported await/promise/timer created inside run | Retains the store | Bound work and context/resource lifetime |
| Long-lived callback/custom thenable/native async boundary | May use its creation/emission context or lose association | Reproduce loss, use supported AsyncResource/bind/snapshot where appropriate |
| Queue/broker/network hop | No automatic process-local transfer | Serialize safe correlation/operation fields and validate/re-authorize at receiver |
| Worker thread/child process | Separate execution context | Pass safe fields in a message, establish the worker's own run |
| Cron/bootstrap work | No HTTP principal by default | Establish explicit job/system context or use an authorized separate path |

EventEmitter listeners run in the context where emission occurs; registering a listener inside a request does not generally bind every later emitter invocation to that request. Binding can retain its captured context and needs a lifetime policy. Use the pinned Node API's bind/snapshot availability and AsyncResource for unsupported boundaries; call `disable()` only when disposing an ALS owner, not as per-request cleanup that disrupts other requests.

A queue worker must validate the job's business identity and open a fresh transaction for that job. A request transaction handle cannot be serialized or remain usable after its callback completes. A job's tenant field can be stale or attacker-influenced; checking current authorization/ownership and its intended service-account policy is separate from correlation.

### 4. Enforce tenant access through a narrow operation

A required tenant accessor should reject absent verified context. The repository then constructs a query with the tenant and operation-specific allowed fields, for example `findMany({ where: { tenantId, status: 'open' }, select: ... })` on the intended model. Absence must not silently fall through to an unrestricted query “for background/admin”.
Give explicitly authorized administrative operations their own reviewed interface.

A generic Prisma `$allOperations` extension that adds `args.where.tenantId` is not universal isolation: create/createMany use data, nested writes and relations differ, raw SQL bypasses model query hooks, and some models/operations do not have tenant fields. Scope each supported operation, check relations/updates and use database RLS with the appropriate role/policy where needed. See [Prisma advanced patterns](../../20.4-database/04-orm-and-access/20.4.4.02-prisma-advanced.md) and [RLS](../../20.4-database/01-postgresql-foundations/20.4.1.06-row-level-security.md).

ALS propagates identity; it cannot make an incorrect policy correct. RLS also has owner/bypass roles, transaction settings, permissive-policy combination and connection reuse boundaries. Exercise denial and concurrent tenant paths at the actual data layer.

### 5. A transaction store binds a handle, not an automatic transaction

A unit-of-work can enter `AsyncLocalStorage<TransactionClient>` inside a database transaction callback. Every nested repository must deliberately use that stored transaction client; queries through the root client still escape it. Set RLS context on the same transaction/connection, using parameterized set_config or the canonical ORM operation.
A context value alone does not switch clients or bind every SQL statement.

Await all transaction work before leaving the callback. A timer/fire-and-forget promise can retain ALS after commit/rollback while its transaction handle is closed; accessing it then fails or escapes the intended contract. Define nested-call behavior: join an existing unit or reject incompatible nesting instead of quietly opening another transaction.
External provider/broker effects are not rolled back with SQL; use an outbox/reconciliation contract when required.

Do not create a generic `currentTx()` call in a worker that only established request metadata. It needs a real fresh transaction boundary first. Optional log context can return undefined; tenant/transaction enforcement should usually fail closed unless an explicit privileged path supplies a different policy.

### 6. Bound retention, cardinality and retry identity

Keep identifiers, a small immutable locale/feature snapshot and deliberately scoped resource handles. Large request bodies, mutable business aggregates or entire native requests retained by long-lived timers/cache listeners can multiply memory use. A singleton client must read current context per operation instead of caching the first request's store.

Request/trace/user IDs are useful structured log/span fields; unbounded IDs should not be Prometheus metric labels. Reuse route templates and bounded outcome dimensions. Log redaction/access/retention remain necessary even when every event has context.

A fresh request ID is not a stable business idempotency key: a retry may arrive with another request ID, while unrelated operations can share correlation. Carry the client's validated operation key with a scope and persist its parameter/outcome contract. Context can transport it; it cannot invent durable deduplication.
See [idempotency](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md).

Measure ALS and request-scoped DI under representative asynchronous load rather than declaring a universal winner. Tests should include interleaving, outside-context calls, timers outliving response/transaction, worker re-entry, unsupported callback boundaries and actual scoped queries. The simple fixture proves its own continuation paths, not every dependency's behavior or production tenant isolation.

## Summary

ALS associates a store with supported async execution, so overlapping operations can carry distinct context. It does not establish trust, make state immutable, cancel retained work or keep a transaction valid. Enter context at the correct lifecycle boundary, reject missing enforcement facts, and establish fresh identity/resource ownership across jobs, processes and network hops.

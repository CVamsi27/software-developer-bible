# Request Context & AsyncLocalStorage

> **A request is a fact that many layers need but none should pass around.** The trace id, the authenticated user, the tenant, the open transaction — every log line, every query and every downstream call wants them, and threading them through fifteen function signatures is how a codebase becomes impossible to change. `AsyncLocalStorage` makes that context ambient; using it carelessly makes bugs that only appear under concurrency.

## Definition

**Request context** is the set of facts about the request that several application layers need. It can include the request ID, authenticated user (the principal), tenant, open database transaction, trace and span identifiers used to connect diagnostic events, and configuration fixed for that request.

**`AsyncLocalStorage`** is a Node API (`async_hooks`) that stores a value for the duration of a callback chain: `store.run(value, fn)` establishes it, `store.getStore()` reads it anywhere inside that chain — including inside `await`s, promise callbacks and timers created within it — and it is automatically *not* visible outside.

What belongs in it, and what does not:

| Belongs in context | Belongs as a parameter |
| ------------------------------------------------ | --------------------------------------- |
| request id / trace id / span | request body and query params |
| authenticated subject (id, roles) | domain entities and aggregates |
| tenant / organisation id | connection or repository choices |
| locale, timezone, feature-flag snapshot | business configuration values |
| the open transaction handle (RLS/tenant binding) | anything mutable per business step |
| logger with bound fields | large objects (never: memory retention) |

## First Principles

Context propagation exists because of two unavoidable facts about server programming:

1. **One request uses several layers.** A repository may need to attribute a query to a request without passing a `traceId` through every business method. Context storage provides that shared identification separately from business parameters.
2. **Several requests overlap on one JavaScript thread.** A global “current request” variable can be overwritten while another request waits. Context must follow each request's asynchronous callback chain; `AsyncLocalStorage` provides that mechanism.
3. **Hidden inputs need limits.** Reading context removes parameters from signatures, but makes some dependencies less visible. Keep the store small and documented: identifiers, immutable facts, and any deliberately bound transaction handle. Pass business data explicitly.
4. **New execution roots need their own context.** Queue workers, cron tasks started outside a request, worker threads, and other processes must establish it explicitly. Timers created inside a request can retain its context; a timer created elsewhere does not inherit that request merely because it runs later.

The consequence: use ALS for **identification and enforcement** (who/where/what-tenant, transaction binding, logging), and pass **business data** explicitly.

## Why it matters

Two failure modes make this worth a chapter. Without a context mechanism, teams build globals (`currentUser = null` as a module variable) that leak between concurrent requests — a data-leak class bug that passes every single-threaded test. With an over-broad context mechanism, teams hide real dependencies and discover that nothing is testable. Knowing where the line sits is a senior signal, and it is asked directly: "how do you get the tenant id into the query layer without passing it through every method?" (→ [30.3.4.04](../../../30-architecture/30.3-infra-patterns/04-data-at-scale/30.3.4.04-multi-tenant-saas-architecture.md))

## How it works

### 1. The mechanism

```ts
import { AsyncLocalStorage } from 'node:async_hooks';

export interface RequestContext {
  requestId: string;
  userId?: string;
  tenantId?: string;
  locale: string;
  traceId: string;
}

export const requestContext = new AsyncLocalStorage<RequestContext>();

/** Read context, or undefined outside a request (cron, boot, tests). */
export const getContext = () => requestContext.getStore();
```

Everything created *inside* `run()` inherits the store: `await` continuations, `.then()` callbacks, `setTimeout`, `process.nextTick`, event emitters fired within it. Everything created *outside* — a module-level interval, a job pulled from Redis — does not.

### 2. Enter it exactly once, at the boundary

```ts
// HTTP boundary: one middleware establishes context for the whole request.
@Injectable()
export class ContextMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: () => void) {
    const ctx: RequestContext = {
      requestId: req.headers['x-request-id']?.toString() ?? randomUUID(),
      userId: (req as any).user?.id,          // set by auth guard, if it ran earlier
      tenantId: (req as any).user?.tenantId,
      locale: parseLocale(req.headers['accept-language']),
      traceId: req.headers['traceparent']?.toString() ?? randomUUID(),
    };
    // Echo the id so clients and support can correlate a complaint to a log line.
    res.setHeader('x-request-id', ctx.requestId);
    requestContext.run(ctx, () => next());
  }
}
```

Creating context in one place makes it easier to audit. Keeping its values to identifiers and immutable facts prevents code from changing those facts midway through the request. Here, immutable means callers must not modify a value after context creation.

### 3. Why ALS beats request-scoped DI

```ts
// Request-scoped providers: correct, but they rebuild the injection subtree
// for EVERY request and only reach injected classes.
@Injectable({ scope: Scope.REQUEST })
export class TenantService { constructor(@Inject(REQUEST) private req: Request) {} }

// ALS: no scope bubbling, and it reaches plain functions, repositories,
// loggers and third-party code that DI never touches.
export function currentTenantId(): string {
  const id = requestContext.getStore()?.tenantId;
  if (!id) throw new Error('No tenant in context — called outside a request?');
  return id;
}
```

Scope bubbling is the hidden cost: once a request-scoped provider is injected into a singleton, everything above it becomes request-scoped too, and the DI container rebuilds that chain per request. ALS is a plain module-level object with no container involvement.

### 4. Propagate across every new root

| Boundary | What happens by default | What to do |
| ---------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------- |
| `await` / promises / timers inside the request | Context is preserved | Nothing |
| Queue job (BullMQ, SQS) | Context is **lost** — new root | Serialize ids into the job payload, re-enter with `run()` in the worker |
| Cron / scheduled task | Lost (no request exists) | Enter a synthetic context (`requestId: 'cron:<name>'`) |
| Outbound HTTP | Lost across the wire | Send `x-request-id` / `traceparent` headers explicitly |
| Worker threads / child processes | Lost | Pass ids in the message; re-establish in the worker |
| Cached/pooled object storing context | Silent leak or wrong tenant | Never store context on long-lived objects |

## Code Examples

### Tenant-scoped data access without threading the tenant everywhere

```ts
// A Prisma extension reads the store and enforces the tenant filter on every
// query, so a forgotten `where` clause cannot leak across tenants.
export const tenantExtension = Prisma.defineExtension((client) =>
  client.$extends({
    query: {
      $allModels: {
        async $allOperations({ args, query }) {
          const tenantId = requestContext.getStore()?.tenantId;
          if (!tenantId) return query(args);                 // background/admin path
          args.where = { ...(args.where ?? {}), tenantId };  // hard scope
          return query(args);
        },
      },
    },
  }),
);
```

### Bind the logger once, so every line carries the request

```ts
// Logging context is the highest-value use: one field, and a support ticket
// becomes a single log query.
export function requestLogger() {
  const ctx = requestContext.getStore();
  return logger.child({
    requestId: ctx?.requestId,
    traceId: ctx?.traceId,
    tenantId: ctx?.tenantId,
    userId: ctx?.userId,
  });
}

// call site: no parameters, no imports of the request object
requestLogger().info({ event: 'invoice.issued', invoiceId }, 'issued');
```

### Carry the transaction through the layers (RLS pattern)

```ts
// The open transaction lives in the store, so a service deep in the call stack
// joins the caller's transaction instead of opening a second one.
export const txContext = new AsyncLocalStorage<Prisma.TransactionClient>();

export function currentTx(): Prisma.TransactionClient {
  const tx = txContext.getStore();
  if (!tx) throw new Error('No transaction in context — wrap the unit of work');
  return tx;
}

await prisma.$transaction(async (tx) => {
  await txContext.run(tx, async () => {
    await tx.$executeRaw`SELECT set_config('app.tenant_id', ${tenantId}, true)`; // RLS bind
    await invoiceService.issue(id);   // every query inside joins this tx
  });
});
```

### Re-establish context in a worker (the step everyone forgets)

```ts
new Worker('email', async (job) => {
  // A job is a new async root: context does NOT arrive on its own.
  await requestContext.run(
    { requestId: `job:${job.id}`, traceId: job.data.traceId, tenantId: job.data.tenantId, locale: 'en' },
    async () => {
      const tx = currentTx();          // or a fresh transaction, opened deliberately
      await deliverInvoice(job.data.invoiceId);
    },
  );
}, { connection });
```

### Test that context does not leak between concurrent requests

```ts
it('keeps tenant context isolated under concurrency', async () => {
  const results = await Promise.all([
    requestContext.run({ tenantId: 'A', requestId: '1', locale: 'en', traceId: 't1' },
      () => new Promise((r) => setTimeout(() => r(currentTenantId()), 10))),
    requestContext.run({ tenantId: 'B', requestId: '2', locale: 'en', traceId: 't2' },
      () => new Promise((r) => setTimeout(() => r(currentTenantId()), 5))),
  ]);
  expect(results).toEqual(['A', 'B']);   // the interleaving is the point
});
```

## Real-World Patterns

- **Log correlation** — bind `requestId`/`traceId` once; every downstream log line, metric label and error report carries it (→ [40.4.1.03](../../../40-platform/40.4-observability/01-pillars/40.4.1.03-tracing.md)).
- **Multi-tenant SaaS** — tenant id in context, enforced in the query layer *and* backed by database row-level security, so application bugs cannot cross tenants (→ [20.4.1.06](../../20.4-database/01-postgresql-foundations/20.4.1.06-row-level-security.md)).
- **Transaction propagation** — unit-of-work enters a transaction once; services deep in the stack join it rather than opening their own (the Docita RLS pattern: `active-tx.storage.ts` hands the open transaction to session setters).
- **Audit trails** — an append-only audit writer reads `userId`, `tenantId`, `requestId` from context so every write is attributable without changing a single service signature.
- **Feature flags & locale** — snapshot per request so one request sees one consistent flag set instead of re-evaluating mid-request.
- **Idempotency keys** — derive from request context plus the route, so a retried request maps to the same key (→ [30.3.2.03](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md)).

## Common Mistakes

1. **Module-level "current request" variables** — the classic cross-request leak; it works in every test and corrupts data under load.
2. **Storing business data or large objects in the store** — it lives as long as the async chain, so it becomes a memory retention bug (and a leak source for anything that outlives the request).
3. **Assuming context crosses a queue or a timer boundary** — jobs and detached timers start a *new* root with an empty store; the failure is a missing tenant filter, not an exception.
4. **`getStore()` without a fallback** — code that also runs from cron or boot throws `undefined is not an object` in production only.
5. **Request-scoped DI for everything** — container rebuild per request, hidden `Scope.REQUEST` bubbling, measurable latency, and it still does not help non-injected code.
6. **Using context instead of parameters for domain values** — a service that quietly reads the tenant from ambient state is untestable and surprising.
7. **Capturing context in a cached client or singleton** — a pooled object that keeps the first request's tenant serves later requests with the wrong tenant.
8. **Forgetting to re-enter context in workers** — logs lose correlation and tenant enforcement silently disappears.
9. **No isolation test** — nothing catches leakage until an incident.

## Best Practices

- **One entry point per boundary.** HTTP middleware/interceptor enters the store; queue workers, cron jobs and consumers enter it explicitly at their own root.
- Keep the store **small, immutable and identifier-only**; treat it as a passport, not a backpack.
- Provide **typed accessors with explicit failure** (`currentTenantId()` throws; `tryGetContext()` returns `undefined`) so "outside a request" is a deliberate decision.
- **Prefer ALS over request-scoped providers**; reserve `Scope.REQUEST` for genuinely per-request object instances.
- Treat context as **required plumbing at every new async root**: document the five boundaries (queue, cron, HTTP out, worker, detached timer).
- **Enforce multi-tenancy in two places** — context-driven application filter *and* database RLS — as defense in depth.
- Expose `x-request-id` in responses and accept one from clients, so a support conversation maps to a trace.
- **Write the concurrency isolation test**; it is the only thing that proves the mechanism works.
- Log the context once per request (start/end with duration), not on every line.

## Performance Considerations

- `AsyncLocalStorage` has a small per-async-operation overhead; in modern Node it is low enough for request-scoped context, but it is not free in extremely hot micro-loops — avoid creating a store *per operation* inside a loop.
- Enabling `async_hooks`-based tracking disables some promise-hook fast paths historically; measure with realistic load before deciding it is the bottleneck (it rarely is, compared to database or network time).
- Request-scoped DI is usually the bigger cost: it rebuilds the injection subtree per request, which matters at thousands of RPS.
- Keep the store object **small and stable in shape**; large payloads are retained for the async lifetime and can multiply memory under concurrency.
- Anything stored here is retained as long as the longest async chain that captured it — including fire-and-forget promises, which is a common leak path.
- Prefer reading the store once per function and passing the values down within that function, rather than repeated `getStore()` calls in tight loops.

## Summary

- Request context is unavoidable cross-cutting state; `AsyncLocalStorage` is the mechanism that propagates it across `await` boundaries without parameter plumbing or globals.
- Enter the store once at the boundary, keep it to identifiers and immutable facts, and provide typed accessors with explicit failure modes.
- Context does **not** cross queue jobs, cron ticks, child processes or the network — every new root must re-establish it, and forgetting is the most common production bug in this area.
- ALS is generally preferable to request-scoped DI: no container rebuild per request, and it reaches code DI cannot.
- Multi-tenancy gets two layers: context-driven filtering in the data layer plus database RLS, so a forgotten `where` cannot leak.

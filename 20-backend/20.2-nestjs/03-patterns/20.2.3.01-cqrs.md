# CQRS in NestJS

How a request reaches its handler. HTTP request -> controller -> CommandBus -> command handler -> write repository

## Definition

CQRS means **Command Query Responsibility Segregation**: give a request that changes state a different interface from a request that reads it. For example, `ReserveSeat` enforces booking rules, while `GetAvailableSeats` returns a display-friendly view.

> **Textbook Definition:** CQRS separates the model or interface used to perform state-changing commands from the model or interface used to answer side-effect-free queries. It does not require different databases, event sourcing or a message broker.

Nest's `@nestjs/cqrs` package routes command, query and event objects to registered handlers. The package supplies dispatch machinery; the application still owns authorization, transactions, durable work and business rules.

## First Principles

A booking write must decide whether a seat can be reserved now. A screen may need the seat, passenger and departure details in one response. Those operations have different jobs, even when they use the same database.

If one generic repository method tries to serve both, its inputs and results can become difficult to reason about. Separate interfaces let the write enforce its invariant and the read return its view. Add a separate read store only when the query workload warrants the extra synchronization problem.

## How It Works


### 1. How a request reaches its handler

```text
HTTP request -> controller -> CommandBus -> command handler -> write repository
HTTP request -> controller -> QueryBus   -> query handler   -> read repository
                                   state change -> EventBus -> event handlers
```

A **bus** is the dispatcher: it looks up the handler associated with the object's class. A command or query has one matching handler. An event announces a fact and can have multiple handlers, such as a projection updater and an audit subscriber.

A **projection** is a read view built from changes. It might be a SQL view, a denormalized table or a search index. When a projection updates asynchronously, successful command completion and projection visibility are different moments.

### 2. One complete in-process example

Install `@nestjs/common`, `@nestjs/core`, `@nestjs/cqrs`, `reflect-metadata` and `rxjs`. Use a TypeScript configuration with `experimentalDecorators` and `emitDecoratorMetadata`. This application context has no HTTP server and keeps its data only in memory; restarting it resets the seats.

```typescript
import 'reflect-metadata';
import { Injectable, Module } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import {
  CqrsModule, CommandBus, QueryBus, CommandHandler, QueryHandler,
  ICommandHandler, IQueryHandler,
} from '@nestjs/cqrs';

class ReserveSeat {
  constructor(public readonly seatId: string) {}
}
class GetAvailableSeats {}

@Injectable()
class Seats {
  private available = new Set(['A1', 'A2']);
  reserve(id: string): string {
    if (!this.available.delete(id)) throw new Error('Seat unavailable');
    return id;
  }
  list(): string[] { return [...this.available]; }
}

@CommandHandler(ReserveSeat)
class ReserveSeatHandler implements ICommandHandler<ReserveSeat> {
  constructor(private readonly seats: Seats) {}
  async execute(command: ReserveSeat): Promise<string> {
    return this.seats.reserve(command.seatId);
  }
}

@QueryHandler(GetAvailableSeats)
class AvailableSeatsHandler implements IQueryHandler<GetAvailableSeats> {
  constructor(private readonly seats: Seats) {}
  async execute(): Promise<string[]> { return this.seats.list(); }
}

@Module({
  imports: [CqrsModule.forRoot()],
  providers: [Seats, ReserveSeatHandler, AvailableSeatsHandler],
})
class AppModule {}

async function main() {
  const app = await NestFactory.createApplicationContext(AppModule, { logger: false });
  try {
    const commands = app.get(CommandBus);
    const queries = app.get(QueryBus);
    console.log(await queries.execute(new GetAvailableSeats())); // ['A1', 'A2']
    console.log(await commands.execute(new ReserveSeat('A1'))); // 'A1'
    console.log(await queries.execute(new GetAvailableSeats())); // ['A2']
    try { await commands.execute(new ReserveSeat('A1')); }
    catch (error) { console.log((error as Error).message); } // Seat unavailable
  } finally { await app.close(); }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

The first query does not mutate the set. Reserving `A1` removes it before the command promise resolves. The next query sees `A2`, and a second reservation of `A1` fails.
This example has separate handlers and one shared state owner; it demonstrates CQRS without eventual consistency.

The synchronous `Set.delete` operation is safe for this one process. It is not a distributed reservation rule. With several processes, use a database conditional write or unique constraint inside a transaction.
Retrying a successful reservation also needs an operation identity if the caller must receive the original result rather than an “unavailable” error.

Keep authorization and output projection in the application contract: dispatching a command does not prove the actor may reserve that seat, and returning a persistence object does not make every field safe for a client. The HTTP or message adapter should translate its own identity and response format around the same operation.

### 3. Publishing a fact does not make delivery durable

After a committed reservation, an event might contain `reservationId`, `seatId` and a monotonically increasing version. A projection handler can upsert its read view and reject duplicate or older versions.

With the default in-memory event publisher, returning from `EventBus.publish()` does not mean asynchronous event handlers have finished. A crash can also occur between the database commit and publishing the event. If another store must eventually receive every committed change, write an **outbox** record in the same database transaction; a relay sends it later and consumers tolerate repeat delivery.
See the canonical [transactional outbox chapter](../../20.6-microservices/03-data-and-consistency/20.6.3.06-transactional-outbox.md).

Trace the failure: a seat commits at version 8, but its search projection still holds version 7. The command can return the reservation identifier and version 8. A later read can wait for that version within a deadline or explicitly show “updating”; silently promising immediate visibility would be misleading.

### 4. Event sourcing and sagas solve different problems

**Event sourcing** stores the accepted event history as the authoritative state and rebuilds state by replaying it. An aggregate collecting pending events in memory is not an event store. Replay needs stable event schemas, event ordering and an expected-version check on append. Follow the [event sourcing chapter](../../20.6-microservices/03-data-and-consistency/20.6.3.03-event-sourcing.md) for persistence and evolution.

A **saga** coordinates several local transactions and compensations. Nest's `@Saga()` maps an event stream into commands; it does not automatically persist workflow progress or roll back other services.

For a booking, react to `SeatReserved` by requesting payment. Only `PaymentConfirmed` should request confirmation email. Emitting reserve, payment and email commands together after `OrderCreated` allows the email to run before reservation or payment succeeds.
Completion events, durable workflow state, duplicate suppression and a defined compensation path establish the actual ordering.

### 5. Decide whether the separation pays for itself

| Situation | Useful choice | Cost to check |
| ---------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------- |
| Simple CRUD with the same write and read shape | One service/repository may be enough | A bus adds registration and indirection |
| Business actions enforce distinct rules | Command handlers with an explicit transaction | Prevent rules from spreading into controllers |
| Reads need large joined or aggregated views | Dedicated read interface, initially on the same database | Measure query cost before adding another store |
| Search or analytics can lag | Asynchronous projection | Track lag, replay failures and stale results |
| A caller needs immediate authoritative state | Read the write store or implement a version barrier | CQRS does not require every query to use a replica |

## Summary

Nest CQRS makes the command/query split explicit through registered handlers. A single store can satisfy both sides. Separate projections, event history and multi-service workflows add their own consistency and recovery requirements; the buses do not supply those guarantees.

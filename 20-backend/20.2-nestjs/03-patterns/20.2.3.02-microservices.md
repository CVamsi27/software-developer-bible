# NestJS Microservices


## Definition

Nest microservice support lets a handler receive messages through a network transport instead of an HTTP route. For example, a gateway sends `get_seat` to a booking service, whose `@MessagePattern()` handler delegates to its application service.

> **Textbook Definition:** A microservice is an independently deployable service organized around a business capability and an explicit contract. Nest's microservice mode adapts controllers and clients to request-response or event transports; choosing it does not by itself create independent data ownership or failure isolation.

**TCP** is a direct connection between processes. **gRPC** is a remote procedure call protocol with schema-defined messages. Kafka, RabbitMQ, Redis pub/sub, NATS and MQTT involve a messaging server. Their persistence, routing and acknowledgment rules differ.

## First Principles

Two processes do not share a call stack. The caller serializes input, sends it across a connection and waits for a reply or transport outcome. During that interval the connection can fail, the remote handler can fail, or the handler can commit while its reply is lost.

A transport adapter hides some framing and routing, but cannot tell a timed-out caller whether a business change committed. That uncertainty determines deadlines, operation identities, retries and reconciliation. Splitting processes also makes deployment and data contracts part of correctness; shared databases and queues can still couple overload across services.

## How one message reaches the application

```text
Gateway ClientProxy -> TCP connection -> Nest pattern lookup -> booking handler
                                                -> booking service -> database
Gateway ClientProxy <- correlated response <---- handler result
```

For a broker transport, insert the broker between the client and the service. A message pattern is the routing key registered by the controller, not a network address. A response is correlated with its originating request.

`send()` returns a cold RxJS Observable: subscribing starts the request. `firstValueFrom()` subscribes and turns its first result into a promise. `emit()` immediately attempts event publication and has no application reply; observing its result helps surface transport errors but does not prove downstream business completion.

## A complete local TCP service and client

Install `@nestjs/common`, `@nestjs/core`, `@nestjs/microservices`, `reflect-metadata` and `rxjs`. Enable TypeScript decorator metadata. This demonstration runs two Nest contexts in one operating-system process while communicating through an actual loopback TCP socket. Port 3001 must be free.

```typescript
import 'reflect-metadata';
import { Controller, Module } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import {
  ClientProxyFactory, MessagePattern, Payload, RpcException,
  Transport, MicroserviceOptions,
} from '@nestjs/microservices';
import { firstValueFrom, timeout } from 'rxjs';

@Controller()
class SeatsController {
  @MessagePattern({ cmd: 'get_seat' })
  getSeat(@Payload() data: { id?: string }) {
    if (data.id !== 'A1') throw new RpcException('Seat not found');
    return { id: data.id, available: true };
  }
}
@Module({ controllers: [SeatsController] })
class SeatsModule {}

async function main() {
  const server = await NestFactory.createMicroservice<MicroserviceOptions>(
    SeatsModule,
    { transport: Transport.TCP, options: { host: '127.0.0.1', port: 3001 }, logger: false },
  );
  const client = ClientProxyFactory.create({
    transport: Transport.TCP, options: { host: '127.0.0.1', port: 3001 },
  });
  try {
    await server.listen();
    await client.connect();
    const seat = await firstValueFrom(
      client.send<{ id: string; available: boolean }>({ cmd: 'get_seat' }, { id: 'A1' })
        .pipe(timeout(1000)),
    );
    console.log(seat); // { id: 'A1', available: true }
    try {
      await firstValueFrom(client.send({ cmd: 'get_seat' }, { id: 'B1' }).pipe(timeout(1000)));
    } catch (error) {
      console.log((error as { message: string }).message); // Seat not found
    }
  } finally {
    client.close();
    await server.close();
  }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

`connect()` makes connection failure visible before the first request. The service dispatches `get_seat`, then the client receives its returned object. The second request reaches the same handler and receives an RPC error. Closing the client and server releases the socket.

This example uses trusted local input. A production handler still needs payload validation and authenticated service identity, with resource authorization in the application layer. Bind only to the intended network interface and use the transport's supported authentication/encryption boundary for remote peers; a private address alone does not establish identity. A TypeScript annotation disappears at runtime and does not validate the message.

## A deadline bounds waiting, not the remote side effect

Suppose `reserve_seat` commits after 800 ms, but the caller times out at 500 ms. The caller sees failure although the seat changed. Unsubscribing from the response stream does not roll back that remote transaction. Retry with the same durable operation identity, or query its result before submitting a new booking.

For read-only lookups, bounded retries can be reasonable within the caller's total deadline. For writes, establish idempotency before retrying. Rejecting excess work, limiting concurrency and opening a circuit breaker protect resources; none turns an uncertain write into a known failure.

## Pick transport behavior deliberately

| Transport | Where the message goes | Delivery boundary to understand |
| --------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| TCP | Direct service connection | No broker persistence; reply loss can leave a committed write uncertain |
| Redis | Redis pub/sub channels | Offline subscribers miss publications; Redis persistence does not persist this pub/sub delivery |
| Kafka | Partitioned topic log | Keys determine partition order; consumer offsets and transactions constrain replay/deduplication |
| RabbitMQ | Exchange/queue routing | Durable queues, persistent messages, publisher confirms and consumer acknowledgments are separate settings |
| NATS | Subjects and subscribers | Core NATS and JetStream have different persistence contracts; do not assume a core Nest transport uses JetStream |
| gRPC | Schema-defined service method | Deadlines, stream cancellation and status codes; not a durable job queue |
| MQTT | Broker topics | Quality-of-service and session settings govern delivery; the business effect still needs duplicate handling |

The Nest transport does not erase its underlying protocol. In Kafka request-response, configure the response-topic subscription before connecting the client; response partition allocation limits how many clients can receive replies. For RabbitMQ jobs, acknowledge after the durable business result, and route bounded retry failures to a reviewable dead-letter path. See the linked transport chapters for configuration.

## HTTP and message handlers can share a Nest application

A **hybrid application** starts an HTTP server and an attached microservice:

```typescript
// AppModule must register the HTTP and message controllers/providers.
const app = await NestFactory.create(AppModule);
app.connectMicroservice<MicroserviceOptions>(
  { transport: Transport.TCP, options: { host: '127.0.0.1', port: 3001 } },
  { inheritAppConfig: true },
);
await app.startAllMicroservices();
await app.listen(3000);
```

`inheritAppConfig` controls inheritance of global pipes, guards, interceptors and filters. Even when inherited, they must support the RPC execution context rather than assuming an HTTP request or response. RPC exception filters return an error Observable; an HTTP filter that writes `response.status().json()` is not a portable substitute.

A readiness endpoint should distinguish “the process responds” from “this service can accept its required work.” Test the selected downstream dependency with a short deadline, and drain in-flight work during shutdown. A TCP port being open does not verify a schema, authorization or successful database transaction.

## Summary

Nest connects handlers to transports through message/event patterns and clients. Understand subscription, connection, deadline and acknowledgment boundaries before choosing a protocol. Service independence comes from clear contracts and ownership; delivery recovery and uncertain writes remain application responsibilities.

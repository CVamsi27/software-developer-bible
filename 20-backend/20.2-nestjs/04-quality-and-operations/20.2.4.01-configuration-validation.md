# Configuration & Validation in NestJS


## Definition

**Configuration** supplies settings such as database URLs and feature flags. Nest's `ConfigModule` from `@nestjs/config` loads environment variables or configured files and makes their values available through an injected `ConfigService`. Check those values against a schema during startup. Request validation is a separate check: `ValidationPipe` can use `class-validator` decorators on data transfer objects (DTOs) to reject invalid handler arguments with a 400 response before the controller method runs.

> **Textbook Definition:** Configuration validation checks application settings against required types and constraints before operation. Request validation checks incoming arguments at the application boundary; these checks protect different lifecycles even when both use schemas.

## First Principles

Environment variables and HTTP inputs arrive as untrusted strings or JSON. A type annotation cannot constrain either at runtime. A missing database address should prevent startup; an invalid email should reject one request. These failures belong to different lifecycles and need separate schemas.

Validate the settings needed to construct the application before accepting work. Validate each incoming request at its boundary, then enforce business rules against authoritative state in the service. A valid DTO can still request an unauthorized role or race with another transaction.

## Why Do We Need It?

1. **Boot-time fail-fast** — Validate environment values before the app accepts traffic. A missing `DATABASE_URL` should fail startup; the orchestrator's health and rollout policy determines how that failure affects deployment.
2. **Type safety** — DTO classes describe compile-time fields; their registered decorators independently enforce runtime constraints. Keep both aligned and verify the boundary.
3. **Centralization** — One place to read config, one place to override it in tests, one place to namespace by feature.
4. **Security** — Reject unexpected decorated-DTO fields with `whitelist: true` and `forbidNonWhitelisted: true`; these options do not constitute a general prototype-pollution defense.
5. **Env-specific overrides** — `.env.development`, `.env.production`, `.env.test`; no manual swapping in CI.
6. **Avoid `process.env` sprawl** — Greppable `configService.get(...)` is better than 200 `process.env.X` reads.
7. **Transformation** — `class-transformer` turns plain JSON into a typed DTO instance so handlers receive a class, not a bag of properties.

## How It Works

### Config Flow

```text
.env file ──▶ ConfigModule.forRoot({...})
                  │
                  ├── validationSchema (Joi), or validate (custom function)
                  │ └─ fails boot if env is invalid
                  │
                  ├── load: [fileLoader, fileLoader({ env: NODE_ENV })]
                  │
                  └── ConfigService (injectable)
                        │
                        ▼
                  configService.get<string>('DB.host')
                  configService.getOrThrow('JWT_SECRET') // throws if missing
```

### Validation flow with `transform: true`

```text
HTTP Request Body (plain JSON)
   │
   ▼
ValidationPipe (global)
   │
   ├── class-transformer: plainToInstance(CreateUserDto, body, configured options)
   │
   ├── class-validator: validate(instance) → errors[]
   │
   ├── if errors.length > 0 → throw BadRequestException(errors)
   │
   └── otherwise → instance passed to handler
```

## Code Examples

### ConfigModule with Joi Schema Validation at Boot

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule, ConfigService } from '@nestjs/config';
import * as Joi from 'joi';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true, // available everywhere without re-import
      cache: true, // cache process.env lookups
      envFilePath: [
        `.env.${process.env.NODE_ENV}.local`,
        `.env.${process.env.NODE_ENV}`,
        '.env.local',
        '.env',
      ],
      validationSchema: Joi.object({
        NODE_ENV: Joi.string().valid('development', 'test', 'production').default('development'),
        PORT: Joi.number().integer().min(1).max(65535).default(3000),
        DATABASE_URL: Joi.string().uri().required(),
        JWT_SECRET: Joi.string().min(32).required(), // length is not proof of key entropy
        REDIS_URL: Joi.string().uri().optional(),
        LOG_LEVEL: Joi.string().valid('debug', 'info', 'warn', 'error').default('info'),
      }),
      validationOptions: { abortEarly: false, allowUnknown: true },
    }),
    // feature modules...
  ],
})
export class AppModule {}
```

For a symmetric signing key, provision cryptographically random key material through the secret-delivery mechanism. A schema character minimum checks shape; it does not establish entropy. Validate URL protocols and transport requirements for the actual clients as well.

### Namespaced Config for One Feature

```typescript
// config/database.config.ts
import { registerAs } from '@nestjs/config';

export default registerAs('database', () => {
  const rawPool = process.env.DB_POOL_SIZE ?? '10';
  if (!/^[1-9][0-9]{0,2}$/.test(rawPool) || Number(rawPool) > 100) {
    throw new Error('DB_POOL_SIZE must be an integer from 1 to 100');
  }
  return {
    url: process.env.DATABASE_URL, // validated by the startup environment schema
    poolSize: Number(rawPool),
    ssl: process.env.NODE_ENV === 'production', // example transport policy
  };
});

// app.module.ts
ConfigModule.forRoot({
  isGlobal: true,
  load: [databaseConfig], // merged under 'database' namespace
});

// usage in a service
@Injectable()
export class UsersService {
  constructor(private readonly config: ConfigService) {}

  getPoolSize() {
    return this.config.get<number>('database.poolSize'); // 10
  }
}
```

### Typed Config Service Wrapper

```typescript
// config/typed-config.service.ts
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

@Injectable()
export class TypedConfigService {
  constructor(private readonly cs: ConfigService) {}

  get databaseUrl(): string {
    return this.cs.getOrThrow<string>('DATABASE_URL');
  }
  get jwtSecret(): string {
    return this.cs.getOrThrow<string>('JWT_SECRET');
  }
  get isProd(): boolean {
    return this.cs.get<string>('NODE_ENV') === 'production';
  }
}

// module
@Module({
  providers: [
    { provide: TypedConfigService, useFactory: (cs: ConfigService) => new TypedConfigService(cs), inject: [ConfigService] },
  ],
  exports: [TypedConfigService],
})
export class ConfigTypedModule {}
```

### Global ValidationPipe + DTO

```typescript
// main.ts
import { ValidationPipe } from '@nestjs/common';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true, // strip unknown properties
      forbidNonWhitelisted: true, // 400 if unknown property sent
      transform: true, // plainToInstance before validation
    }),
  );
  await app.listen(process.env.PORT ?? 3000);
}

// users/dto/create-user.dto.ts
import { IsEmail, IsString, MinLength } from 'class-validator';

export class CreateUserDto {
  @IsEmail()
  email!: string;

  @IsString()
  @MinLength(2)
  name!: string;

}

// users.controller.ts
@Post()
create(@Body() dto: CreateUserDto) { // already validated + transformed
  return this.usersService.create(dto);
}
```

The DTO declares accepted email/name fields; a body that includes `role: "admin"` receives 400 because that field has no validation metadata. The service assigns permissions from the authenticated policy rather than accepting a client-selected role. For numeric query fields, prefer explicit parsing pipes or `@Type(() => Number)` with numeric constraints; implicit conversion can turn surprising inputs into apparently valid values.

Configuration fragments require their shown packages (`@nestjs/config`, `joi`) and ordinary Nest module imports. `get<number>()` is a compile-time hint, not a conversion. Validate custom `load` factories too: the factory above rejects `DB_POOL_SIZE=garbage` and `10junk` before returning settings. `validationSchema` does not automatically validate every custom configuration factory. Runtime environment values take precedence over env files by default; among the listed files, the first matching value wins. The environment used to choose a file must exist before module construction.

### Custom validators state only the property they check

A length validator is a useful decorator example; it cannot prove that a password is difficult to guess. Composition checks for uppercase, lowercase and digits do not establish that property either. Keep the actual password policy in [authentication fundamentals](../../20.5-security/01-auth/20.5.1.01-auth-fundamentals.md).

```typescript
import { registerDecorator, ValidationOptions } from 'class-validator';

export function IsPasswordLength(opts?: ValidationOptions) {
  return function (object: object, propertyName: string) {
    registerDecorator({
      name: 'isPasswordLength',
      target: object.constructor,
      propertyName,
      options: opts,
      validator: {
        validate(value: unknown) {
          if (typeof value !== 'string' || value.length > 256) return false;
          const codePoints = [...value].length;
          return codePoints >= 15 && codePoints <= 128;
        },
      },
    });
  };
}
```

The 15–128 code-point range is an example single-factor password policy, with a preliminary UTF-16 bound to limit allocation. It accepts long passphrases without mandatory character classes. A complete policy also screens common/compromised passwords, permits password managers, bounds login work and stores a suitably salted password hash. See [NIST SP 800-63B-4, password verifiers](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver). Do not trim or log the supplied password.

## Real-World Use Cases

1. **Deployment settings** — validate externally supplied values at boot; keep their schema in code.
2. **Multi-tenant** — deployment config is process-wide. Resolve tenant settings from an authenticated tenant identity in a separate service; `ConfigService` does not read request headers.
3. **Feature flags** — Validate and convert static environment values explicitly before treating them as booleans. For dynamically changed flags, use a feature-flag service rather than assuming `process.env` refreshes at runtime.
4. **Request validation** — `ValidationPipe` rejects malformed bodies before they reach the service, then services enforce authorization and state-dependent rules.
5. **Migration safety** — `Joi` schema with `abortEarly: true` and required fields makes application startup reject a missing `STRIPE_SECRET`; deployment promotion still needs a readiness gate.
6. **Test override** — `ConfigModule.forRoot({ ignoreEnvFile: true, load: [() => testConfig] })` removes file loading; isolate process.env too when a test needs complete control.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `process.env.X` in 200 places | Inject `ConfigService` or a typed wrapper |
| Validating env vars only at first read | Use `validationSchema` so boot fails fast |
| Unknown-field handling left implicit | Choose stripping or rejection deliberately and test it; closed DTOs commonly use whitelist plus forbidNonWhitelisted |
| A type-only DTO mistaken for runtime validation | Register a supported runtime schema: DTO validators, Zod, Joi or an explicit pipe |
| Deployment-specific values scattered through code | Resolve external settings through the chosen startup configuration boundary; fixed internal constants may remain code |
| Putting secrets in `.env` checked into git | Use `.env.example` for shape; real secrets from a secret manager |
| `transform: false` on `ValidationPipe` | The returned value may remain plain; set `transform: true` and configure explicit field conversions when required |
| Loading `.env` in production | `ignoreEnvFile: process.env.NODE_ENV === 'production'` |

## Best Practices

1. **Validate at boot** — Use a `Joi` or custom schema so missing required values fail application startup, before the app accepts traffic. The deployment platform determines whether that failure blocks rollout or triggers a restart.
2. **Namespace by feature** — `registerAs('feature', ...)` keeps config organized and makes per-feature overrides trivial.
3. **Global ValidationPipe** — Set `whitelist`, `forbidNonWhitelisted` and deliberate transformations in `main.ts`.
4. **Type your config** — A `TypedConfigService` with `getOrThrow` for required keys rejects missing reads; startup validation must still run before accepting traffic.
5. **Cache the config** — `ConfigModule.forRoot({ cache: true })` caches environment-variable lookups; env file parsing occurs at initialization, not on every get.
6. **Env files per environment** — `.env.development`, `.env.test`, `.env.production`; in prod, use real secret stores and `ignoreEnvFile: true`.
7. **DTOs at the boundary only** — Keep shape validation at each input boundary; services still enforce invariants and authorization, including calls from jobs or other modules.
8. **Custom validators for domain rules** — pure input constraints can be reusable; authorization and database invariants need their own race-safe service checks.
9. **Use `class-transformer` `@Type(() => Date)`** — when using class-transformer, configure the desired field conversion and validate its result; a custom pipe can provide another explicit conversion.
10. **Log validated config at boot (without secrets)** — Print the resolved env (DB host, port, feature flags) once at startup so you can verify what shipped.

## Performance Considerations

Measure validation with realistic payload sizes and nested collections; there is no universal per-request duration. Reject oversized bodies before expensive transformation. `cache: true` is an explicit optimization for environment lookups, not a guarantee that configuration can never become a hotspot. Separate immutable deployment settings from dynamically refreshed flags.

## Summary

- `ConfigModule` loads env vars (or files) and can validate `process.env` at boot; custom `load` factories need their own validation. It exposes resolved values through `ConfigService`.
- `ValidationPipe` + `class-validator` + `class-transformer` validates and transforms DTOs at the request boundary.
- Namespace by feature, type your config (`getOrThrow`), set `whitelist + forbidNonWhitelisted + transform` on the global pipe.
- Validate env at boot so missing config fails startup, not a later request; deployment health and rollout policy handle the resulting process failure.

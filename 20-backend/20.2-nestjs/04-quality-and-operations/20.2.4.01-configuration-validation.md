# Configuration & Validation in NestJS

A service fails its first database call because production was missing `DATABASE_URL`. That failure belongs at startup, before the service accepts requests. An invalid email belongs at the request boundary and should reject that request alone. Both are validation, but they protect different lifecycles.

## Definition

`ConfigModule` from `@nestjs/config` loads process variables and optional environment files, then exposes configuration through an injected `ConfigService`. A startup schema checks required deployment settings before the application is ready. Request validation checks HTTP input before the handler acts on it.

Current NestJS supports two request-validation styles. `ValidationPipe` validates class-based DTOs decorated with `class-validator`. `StandardSchemaValidationPipe` validates schemas from Zod, Valibot, ArkType, or another Standard Schema-compatible library. Choose one style for each boundary and enforce domain authorization and state rules in the service as well.

> **Textbook Definition:** Configuration validation checks deployment settings against constraints during application initialization; request validation checks external input at an application boundary. Both establish runtime evidence about values, but neither replaces authorization or state-dependent business rules.

## First Principles

Environment variables and network payloads arrive as runtime data. TypeScript annotations disappear at runtime and cannot prove either value is valid. The point of validation is to reject malformed data before it controls construction or behavior, at the earliest boundary that has enough information to decide.

Settings such as a database URL are process-wide and normally fixed for that process lifetime. A user's tenant, permissions, or live feature flags are request- or service-level data; do not hide them in global configuration. After input passes a schema, authorization and race-sensitive invariants still belong beside the authoritative state they protect.

## Validate settings before constructing the application

In NestJS 12, `validationSchema` accepts Standard Schema-compatible validators. Nest recommends a library such as Zod for new projects. Joi remains supported with Joi 18 or later; library-specific options now go under `validationOptions.libraryOptions`.

For example, a Joi migration keeps the schema but moves its options:

```typescript
import * as Joi from 'joi';
import { ConfigModule } from '@nestjs/config';

ConfigModule.forRoot({
  validationSchema: Joi.object({ PORT: Joi.number().integer().min(1).max(65535).default(3000) }),
  validationOptions: {
    libraryOptions: { allowUnknown: true, abortEarly: false },
  },
});
```

```typescript
// app.module.ts — @nestjs/config with Zod
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { z } from 'zod';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: ['.env.local', '.env'],
      validationSchema: z.object({
        NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
        PORT: z.coerce.number().int().min(1).max(65535).default(3000),
        DATABASE_URL: z.url(),
        JWT_SECRET: z.string().min(32),
        LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
      }),
    }),
  ],
})
export class AppModule {}
```

The Zod examples use Zod 4 syntax, including `z.url()` and `z.email()`.

Environment values are strings, so `z.coerce.number()` converts `PORT` before checking its range. The runtime environment takes precedence over `.env` values by default; within `envFilePath`, the first matching file wins. Use `ignoreEnvFile: true` when production settings should come only from the process environment or a secret-delivery system. Keep real secrets out of committed files: a minimum string length checks shape, not entropy or secret provenance.

The schema validates environment variables, not every custom configuration file. Validate or transform values inside a `registerAs()` factory when it reads YAML, JSON, or nested settings. A TypeScript generic on `ConfigService.get<number>()` is only a type hint; it does not parse a string. Use a required lookup for a value that must exist:

```typescript
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

@Injectable()
export class DatabaseSettings {
  constructor(private readonly config: ConfigService) {}

  get url(): string {
    return this.config.getOrThrow<string>('DATABASE_URL');
  }

  get port(): number {
    return this.config.getOrThrow<number>('PORT'); // parsed by the startup schema
  }
}
```

Treat startup validation as one part of deployment readiness. A bad setting should stop this process from serving traffic; the orchestrator or deployment controller decides whether that blocks or rolls back the release.

## Reject invalid input at the request boundary

For class-based DTOs, decorators carry runtime validation metadata. The global `ValidationPipe` constructs the DTO when `transform` is enabled. `whitelist` strips properties without validation decorators; adding `forbidNonWhitelisted` rejects those properties instead. A TypeScript interface alone supplies no runtime validation.

```typescript
// main.ts
app.useGlobalPipes(new ValidationPipe({
  transform: true,
  whitelist: true,
  forbidNonWhitelisted: true,
}));

// create-user.dto.ts
export class CreateUserDto {
  @IsEmail()
  email!: string;

  @IsString()
  @MinLength(2)
  name!: string;
}
```

In a NestJS 12 schema-first route, the same Standard Schema validates the value and supplies its inferred TypeScript type:

```typescript
import { Body, Controller, Post, StandardSchemaValidationPipe } from '@nestjs/common';
import { z } from 'zod';
import { UsersService } from './users.service';

const createUserSchema = z.strictObject({
  email: z.email(),
  name: z.string().min(2),
});
type CreateUserInput = z.infer<typeof createUserSchema>;

@Controller('users')
export class UsersController {
  constructor(private readonly users: UsersService) {}

  @Post()
  create(@Body({ schema: createUserSchema }) input: CreateUserInput) {
    return this.users.create(input);
  }
}

// Register the schema pipe once during bootstrap.
app.useGlobalPipes(new StandardSchemaValidationPipe());
```

Here `z.strictObject()` rejects unknown fields. A regular Zod object strips them; choose the policy intentionally. If a route uses class-validator instead, keep its rules on the DTO and use `ValidationPipe` for that boundary. Nest still supports both patterns; do not register both global pipes and assume they validate every value in the same way.

Pipes establish shape and conversion rules, not access rights. A validated body containing `role: "admin"` must not grant that role. Derive permissions from authenticated identity, and check ownership and current state against authoritative storage when performing the operation. For numeric query parameters, use an explicit parser or documented schema coercion; never assume a generic type annotation transformed the incoming string.

## Keep settings and request data in their own lifecycle

`ConfigService` is appropriate for deployment-wide values such as a pool limit or static feature switch. It does not read request headers or provide tenant isolation. Resolve a tenant from authenticated request context in a dedicated service. For feature flags that change while the process runs, use a source with a refresh and consistency policy instead of expecting `process.env` to update.

Configuration can also be replaced in tests. Disable env-file loading and provide a test configuration, then control `process.env` separately if the code reads it directly. Prefer injecting settings so the test can state exactly which values the application received.

For large or nested payloads, enforce request-size limits before expensive transformation and validation. Validation is not a substitute for resource limits, error redaction, observability, or authorization checks.

## Summary

Validate deployment settings before the app serves traffic, and validate each request before its handler acts. Use Standard Schema for new schema-first validation, retain class-validator DTOs where they fit, and keep authorization and state-dependent rules at the service boundary that owns them.

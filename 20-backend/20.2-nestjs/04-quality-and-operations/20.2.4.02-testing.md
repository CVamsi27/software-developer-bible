# Testing NestJS Applications

A service test passes, but clients still receive an invalid response because the global validation pipe was never installed. The gap is not a missing assertion inside that service; it is a missing test at the HTTP boundary.

## Definition

NestJS testing builds a chosen part of an application's dependency graph so a test can check its behavior. A **unit test** focuses on one component, often replacing its collaborators. An **integration test** checks connected components against real infrastructure such as PostgreSQL. An **end-to-end (E2E) test** sends requests through the application's HTTP pipeline. Nest's `@nestjs/testing` package provides `TestingModule` for assembling those graphs; it works with different test runners.

The current Nest CLI selects a default runner based on module format: new ESM projects use Vitest, and CommonJS projects use Jest. Existing projects can keep their runner. The examples below use Jest APIs so that the runner-specific calls are explicit. With NestJS 12's ESM packages, Jest requires Node.js 24.9 or later; use Vitest or a compatible CommonJS setup on an older runtime.

> **Textbook Definition:** NestJS testing evaluates component behavior, module integration, or complete request paths using controlled dependency-injection graphs. Replacing a dependency isolates a test; using the real dependency establishes evidence about its integration contract.

## First Principles

Dependency injection gives tests control over construction. A test can replace a repository while keeping the service, or keep the real HTTP application while replacing only an external payment provider. That control is useful only when the test includes the components whose interaction it claims to verify.

Choose the boundary from the question:

| Test boundary | Keep real | Replace or isolate | Evidence it can provide |
| ------------- | ----------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------- |
| Unit | Component and its local logic | External collaborators | The component's decisions for selected inputs and outcomes |
| Integration | Connected module and relevant infrastructure | Unrelated external systems | Mapping, SQL, migrations, serialization, or acknowledgment across that boundary |
| E2E | HTTP app, routing, pipes, guards, filters, and serialization under test | Remote systems that should not be contacted | The observed request and response through the configured application |

These are boundaries, not a required test-count pyramid. A mock proves how the configured caller handles that mock's behavior. It cannot prove a database query, queue acknowledgment, or production provider registration works.

## Build the smallest graph that proves the behavior

`Test.createTestingModule()` accepts module metadata, like `@Module()`. Provider overrides are applied before asynchronous `compile()`. Retrieve ordinary providers with `get()`; request-scoped or transient providers need `resolve()` and a context. Close the compiled module or application so pools and other resources are released.

```text
Test.createTestingModule(metadata)
  → override selected provider tokens
  → await compile()
  → get() static providers or resolve() scoped providers
  → exercise behavior
  → close the module or application
```

For a unit test, mock collaborators rather than the component being tested. Give each mock the behavior of the failure or success under test; a mock that returns the same value for every method can hide a broken contract.

```typescript
// users.service.spec.ts — Jest example
import { Test, type TestingModule } from '@nestjs/testing';
import { NotFoundException } from '@nestjs/common';
import { UsersService } from './users.service';
import { UsersRepository } from './users.repository';

describe('UsersService', () => {
  let module: TestingModule;
  let service: UsersService;
  let repository: jest.Mocked<UsersRepository>;

  beforeEach(async () => {
    module = await Test.createTestingModule({
      providers: [
        UsersService,
        {
          provide: UsersRepository,
          useValue: { findById: jest.fn(), save: jest.fn() },
        },
      ],
    }).compile();

    service = module.get(UsersService);
    repository = module.get(UsersRepository);
  });

  afterEach(async () => {
    await module.close();
  });

  it('reports a missing user', async () => {
    repository.findById.mockResolvedValue(null);
    await expect(service.getById('missing'))
      .rejects.toBeInstanceOf(NotFoundException);
  });

  it('returns the user found by the repository', async () => {
    const user = { id: '42', email: 'reader@example.test' };
    repository.findById.mockResolvedValue(user);

    await expect(service.getById('42')).resolves.toEqual(user);
    expect(repository.findById).toHaveBeenCalledWith('42');
  });
});
```

The test checks observable service behavior and its repository call. It says nothing about whether the production module registers `UsersRepository`; compile the real owning module separately if that wiring is part of the risk. An override can make a test graph compile even when the production graph is incomplete.

## Use real infrastructure when the contract depends on it

When a query, migration, constraint, or transaction is the behavior under test, connect to the actual database engine. Testcontainers can provide a disposable PostgreSQL instance. Run the same migrations used by the application; `synchronize: true` does not test migration correctness and can conceal drift.

```typescript
// test/users.integration-spec.ts — abbreviated Jest/Testcontainers example
import { Test } from '@nestjs/testing';
import { INestApplication } from '@nestjs/common';
import { PostgreSqlContainer, type StartedPostgreSqlContainer } from '@testcontainers/postgresql';
import { TypeOrmModule } from '@nestjs/typeorm';
import { UsersModule } from '../src/users/users.module';
import { UsersService } from '../src/users/users.service';

describe('UsersService with PostgreSQL', () => {
  let container: StartedPostgreSqlContainer | undefined;
  let app: INestApplication | undefined;

  beforeAll(async () => {
    const postgres = await new PostgreSqlContainer('postgres:18-alpine').start();
    container = postgres;
    const moduleRef = await Test.createTestingModule({
      imports: [
        TypeOrmModule.forRoot({
          type: 'postgres',
          url: postgres.getConnectionUri(),
          autoLoadEntities: true,
          synchronize: false,
          migrations: [/* the application's migration classes */],
          migrationsRun: true,
        }),
        UsersModule,
      ],
    }).compile();

    app = moduleRef.createNestApplication();
    await app.init();
  }, 60_000);

  afterAll(async () => {
    await app?.close();
    await container?.stop();
  });

  it('persists and reads a user', async () => {
    const service = app!.get(UsersService);
    const created = await service.create({ email: 'reader@example.test', name: 'A' });
    await expect(service.getById(created.id)).resolves.toMatchObject({
      email: 'reader@example.test',
    });
  });
});
```

This is an integration example, not a complete fixture: supply the entities, migrations, packages, imports, and `INestApplication` import for the application. Give parallel tests isolated databases or schemas. A rollback on one connection does not undo writes made by HTTP handlers through another pooled connection.

## Exercise the HTTP contract through the configured app

An E2E test should run the same prefixes, pipes, filters, and serialization settings as production. Move that setup from `main.ts` into one shared function and call it from both places; importing `AppModule` does not execute `main.ts`. This example uses NestJS 12's Standard Schema pipe. The schema must be attached to the route parameter; the global pipe passes parameters without a schema through unchanged.

```typescript
import { Body, Controller, Post } from '@nestjs/common';
import { z } from 'zod';
import { UsersService } from './users.service';

const createUserSchema = z.object({
  email: z.email(),
  name: z.string().min(1),
});
type CreateUserDto = z.infer<typeof createUserSchema>;

@Controller('users')
export class UsersController {
  constructor(private readonly users: UsersService) {}

  @Post()
  create(@Body({ schema: createUserSchema }) body: CreateUserDto) {
    return this.users.create(body);
  }
}
```

Start the test app with `app.init()` and send requests through Supertest without binding a public port.

```typescript
// src/configure-http-app.ts — use this from main.ts and the E2E test
import { StandardSchemaValidationPipe, type INestApplication } from '@nestjs/common';

export function configureHttpApp(app: INestApplication): void {
  app.setGlobalPrefix('api');
  app.useGlobalPipes(new StandardSchemaValidationPipe());
}
```

```typescript
// test/app.e2e-spec.ts — Jest example
import { Test } from '@nestjs/testing';
import type { INestApplication } from '@nestjs/common';
import request from 'supertest'; // configure the project's interop setting as needed
import { AppModule } from '../src/app.module';
import { configureHttpApp } from '../src/configure-http-app';
import { UsersService } from '../src/users/users.service';

describe('Users API', () => {
  let app: INestApplication | undefined;
  let usersService: UsersService;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app = moduleRef.createNestApplication();
    configureHttpApp(app);
    await app.init();
    usersService = app.get(UsersService);
  });

  afterAll(async () => {
    await app?.close();
  });

  it('rejects malformed input before creating a user', async () => {
    const create = jest.spyOn(usersService, 'create');
    await request(app!.getHttpServer())
      .post('/api/users')
      .send({ email: 'not-an-email', name: 'A' })
      .expect(400);
    expect(create).not.toHaveBeenCalled();
  });
});
```

The E2E assertion proves that the configured request pipeline rejects this body before the service writes. Other request tests should assert their own public status, response fields, and side-effect contract rather than depending on an incidental validation-error message shape.

Import the real guards and pipes when their behavior is under test. If an authentication guard is replaced for an unrelated route test, keep separate requests that prove both allowed and denied access. Likewise, importing `AppModule` may connect to external systems or run startup code; use a test module or provider overrides when those side effects are outside the test's purpose.

## Keep the evidence trustworthy in CI

Assert status, public fields, headers, and forbidden side effects at the boundary the test exercises. For a message-driven service, a mocked `ClientProxy` proves the submitted message shape; a real transport test is needed for serialization, timeout, and acknowledgment behavior. For scheduled work, test the handler's domain behavior separately from registration, timezone, overlap, and distributed coordination.

Close every app, module, container, and database client the test creates. Reset mutable data before reusing expensive fixtures. Parallelize only after each worker has isolated data and enough database connections; more workers can increase contention and setup cost. CI should run the test projects required by the release gate rather than silently excluding a slow suite.

## Summary

Choose a test boundary from the claim you need to establish, then keep real the components whose interaction matters. Nest's testing module controls dependency construction; mocks isolate behavior, real infrastructure verifies integration, and an HTTP test verifies the configured request pipeline.

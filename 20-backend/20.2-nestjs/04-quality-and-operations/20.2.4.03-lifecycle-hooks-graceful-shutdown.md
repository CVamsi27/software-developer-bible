# Lifecycle Hooks & Graceful Shutdown

A rollout replaces processes while requests or jobs may still own database connections. Hook order matters when it decides whether those dependencies remain usable until accepted work finishes.

## Definition

**Lifecycle hooks** are interfaces NestJS calls at well-defined moments of application startup and teardown:

> **Textbook Definition:** Lifecycle hooks expose defined startup and teardown stages of a NestJS application. Graceful shutdown coordinates admission, completion of in-flight work and resource closure within a bounded termination period.

| Hook | When Nest calls it | Applies to |
| ------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------- |
| `onModuleInit()` | After the host module's dependencies resolve | modules, providers, controllers |
| `onApplicationBootstrap()` | After all modules initialize, before the server listens | modules, providers, controllers |
| `onModuleDestroy()` | At teardown, after `app.close()` or an enabled termination signal | modules, providers, controllers |
| `beforeApplicationShutdown(signal?)` | After destroy hooks, before Nest closes the server connections | modules, providers, controllers |
| `onApplicationShutdown(signal?)` | After Nest closes server connections | modules, providers, controllers |

**Graceful shutdown** is the practice of handling termination signals so that in-flight work completes, new work is rejected cleanly (load balancer stops routing), and external resources close in a controlled order.

## First Principles

Lifecycle management exists because processes die and connections end — the design question is whether it's orderly:

1. **Stop new work before releasing its dependencies.** First stop accepting requests or jobs, then finish accepted work, close pools, and flush buffers. A load balancer (LB) also needs time to stop routing new requests. Kubernetes' termination grace period allows time for these steps.
2. **Hooks identify startup and shutdown phases.** `onModuleInit` can initialize a module's dependencies; shutdown hooks provide places to drain work and close resources. `enableShutdownHooks` connects the shutdown sequence to process signals. Document which component owns each resource so it is not closed while another component still needs it.
3. **Correctness must survive abrupt termination too.** SIGKILL, out-of-memory failures (OOM), and node crashes may prevent cleanup. Idempotent consumers (→ 20.3.3.05) make repeated work safe; the transactional outbox (→ 20.6.3.06) preserves a pending event with its database change. Graceful shutdown reduces interruption but cannot replace those protections.

## How It Works


### 1. Startup and shutdown have different ownership stages

#### From bootstrap to close

```text
STARTUP — ordinary HTTP application
════════════════════════════════════════════════════════════
NestFactory.create(AppModule) → construct modules and dependencies
   │
app.init() or app.listen() → initialize application
   ├─ onModuleInit()             ← module dependencies available
   ├─ onApplicationBootstrap()   ← all module initialization complete
   └─ app.listen() binds HTTP server → accepts connections

SHUTDOWN
════════════════════════════════════════════════════════════
app.close(), or supported signal with enableShutdownHooks()
   ├─ onModuleDestroy()
   ├─ beforeApplicationShutdown(signal?)
   ├─ close underlying connections
   └─ onApplicationShutdown(signal?)

app.close() alone does not terminate the Node.js process.
```

#### Hook order is not a dependency contract

Initialization hooks run after dependencies have been resolved, and Nest awaits asynchronous initialization before accepting connections. Nest 12 changed lifecycle-hook ordering to follow component hierarchy levels; relative order can therefore change when upgrading from Nest 11. Do not rely on incidental module-import or provider order when one service needs another service's initialized state.
Inject that dependency and expose an explicit readiness operation. Request-scoped classes do not receive application lifecycle hooks.

For shutdown, stop new business work and drain accepted work before releasing the resources it needs. The hook names alone do not ensure that your consumer stops before its database pool closes. Assign those responsibilities deliberately.

### 2. Kubernetes gives the rollout one shared deadline

```text
kubectl delete pod
   │
   ├─ Pod marked terminating; grace-period budget begins
   ├─ Endpoint routing updates propagate asynchronously
   │
   ├─ preStop hook runs, if configured (uses grace-period time)
   ├─ Container receives TERM after preStop completes
   │      │
   │      ▼
   │   App: stop admission, finish accepted work, close dependencies
   │      │
   │      ├─ app exits within budget → orderly termination
   │      └─ budget expires → SIGKILL → unfinished work interrupted
   │
   └─ Measure routing delay and reserve time for drain and cleanup.
```

The grace period starts before `preStop` completes, so its delay consumes the same budget as draining and cleanup. A fixed sleep does not prove that routing has stopped; measure propagation and leave margin before the final kill deadline. Each request or job needs a deadline inside that shared budget.

### 3. Assign each resource a cleanup boundary

#### Give each resource one cleanup owner

```typescript
// database.module.ts — a provider owning an expensive resource
import { Injectable, OnApplicationShutdown } from '@nestjs/common';
import { Pool } from 'pg';

@Injectable()
export class DatabaseService implements OnApplicationShutdown {
  private readonly pool = new Pool({ max: 20 });

  query<T>(sql: string, params: unknown[] = []): Promise<T[]> {
    return this.pool.query(sql, params).then((result) => result.rows as T[]);
  }

  async onApplicationShutdown(): Promise<void> {
    await this.pool.end(); // close after HTTP and consumer work has drained
  }
}
```

```typescript
// cache-warming.service.ts — heavy startup belongs in bootstrap, not ctor
import { Injectable, OnApplicationBootstrap, Logger } from '@nestjs/common';

@Injectable()
export class CacheWarmingService implements OnApplicationBootstrap {
  private readonly logger = new Logger(CacheWarmingService.name);

  constructor(private readonly catalog: CatalogService) {}

  async onApplicationBootstrap(): Promise<void> {
    // All onModuleInit hooks completed; coordinate any separate async readiness explicitly.
    const started = Date.now();
    await this.catalog.warmTopProducts();
    this.logger.log(`Cache warmed in ${Date.now() - started}ms`);
  }
}
```

### 4. Connect process signals to Nest once

```typescript
// main.ts — the ONE line people forget
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create(AppModule);
  app.enableShutdownHooks(); // wires SIGTERM + SIGINT listeners
  await app.listen(3000);
}
bootstrap().catch(error => { console.error(error); process.exitCode = 1; });
```

> `enableShutdownHooks()` makes Nest listen for termination signals. Without it, a signal does not automatically run Nest's shutdown hooks. Calling `app.close()` still runs those hooks. Initialization hooks do not depend on this option.

### 5. Drain accepted work before closing pools

```typescript
// graceful-shutdown.service.ts — orchestrated teardown
import {
  Injectable, OnApplicationShutdown, BeforeApplicationShutdown, Logger,
} from '@nestjs/common';
import { Server } from 'http';

@Injectable()
export class ShutdownOrchestrator implements BeforeApplicationShutdown, OnApplicationShutdown {
  private readonly logger = new Logger(ShutdownOrchestrator.name);
  private static readonly DRAIN_TIMEOUT_MS = 20_000;

  private server?: Server;
  private drainPromise?: Promise<void>;

  attachServer(server: Server): void {
    this.server = server;
  }

  /** Idempotent against double signals — safe if invoked twice. */
  private beginDrain(): void {
    if (this.drainPromise) return; // idempotent against double signals
    this.logger.log('Draining: closing keep-alive, refusing new connections');
    if (!this.server) { this.drainPromise = Promise.resolve(); return; }
    const server = this.server;
    this.drainPromise = new Promise((resolve) => {
      const timeout = setTimeout(() => {
        this.logger.warn('Drain timeout — destroying remaining sockets');
        server.closeAllConnections();
        resolve();
      }, ShutdownOrchestrator.DRAIN_TIMEOUT_MS);
      server.close(() => {
        clearTimeout(timeout);
        resolve();
      });
      server.closeIdleConnections(); // after stopping intake, avoiding an idle-close race
    });
  }

  async beforeApplicationShutdown(signal?: string): Promise<void> {
    this.logger.log(`beforeApplicationShutdown (${signal}) — draining in-flight requests`);
    // Nest's SIGTERM handler (enableShutdownHooks) drives this hook;
    // no manual process.on('SIGTERM') anywhere — single owner.
    if (!this.drainPromise) this.beginDrain();
    await this.drainPromise; // consumers/DB still usable here if needed
  }

  async onApplicationShutdown(signal?: string): Promise<void> {
    this.logger.log(`onApplicationShutdown (${signal}) — last chance cleanup`);
  }
}
```

```yaml
# deployment.yaml — give the drain enough runway
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45   # > DRAIN_TIMEOUT_MS (20s) + buffer
      containers:
        - name: api
          lifecycle:
            preStop:                      # let LB endpoint removal propagate
              exec:
                command: ["sleep", "5"]
```

Register `ShutdownOrchestrator` as a provider and call `app.get(ShutdownOrchestrator).attachServer(app.getHttpServer())` before listening. This fragment drains ordinary HTTP connections. Upgraded WebSocket connections and long-running jobs require separate tracking/cancellation; `closeAllConnections()` does not cover every upgraded socket.
Its 20-second timer resolves after forcing socket closure. That closes transport, not arbitrary service promises: track accepted handlers/jobs and await their settlement or apply their explicit cooperative cancellation policy before releasing dependencies. At the final termination deadline, unfinished work may be interrupted and must remain retry/recovery safe.

### 6. Stop consumers before closing their dependencies

These snippets compose safely only when all consumers finish in `onModuleDestroy` and tracked HTTP business work settles in `beforeApplicationShutdown`; forcing sockets closed does not by itself prove the latter. Close the database and Redis afterward in `onApplicationShutdown`. That final phase must contain no business work that still needs those resources; coordinate dependent cleanup explicitly.

```typescript
// redis + broker consumer teardown done right
import { Injectable, OnModuleDestroy, OnApplicationShutdown, Logger } from '@nestjs/common';
import Redis from 'ioredis';

@Injectable()
export class RedisService implements OnApplicationShutdown {
  private readonly client = new Redis(process.env.REDIS_URL);

  async onApplicationShutdown(): Promise<void> {
    await this.client.quit(); // QUIT: flush pending commands, then close
  }
}

@Injectable()
export class OrdersConsumer implements OnModuleDestroy {
  private readonly logger = new Logger(OrdersConsumer.name);
  private consuming = false;

  constructor(private readonly orders: OrdersProcessor) {}

  async loop(): Promise<void> {
    this.consuming = true;
    while (this.consuming) {
      const job = await this.orders.poll();
      if (!this.consuming) {
        if (job) await this.orders.releaseForRetry(job); // defined poll/lease ownership contract
        break;
      }
      if (job) await this.orders.handle(job);
    }
  }

  async onModuleDestroy(): Promise<void> {
    // 1. stop pulling new jobs FIRST...
    this.consuming = false;
    // 2. ...then unblock poll(), allow the current handler to settle
    await this.orders.drainInFlight(); // must unblock poll and await this loop plus its handler
    this.logger.log('Consumer stopped cleanly');
  }
}
```

`OrdersProcessor` is an application-owned interface, not a Nest API. Its drain must settle the pending poll and wait for the loop/active handler; if a poll hands back claimed work after admission stops, release that claim according to the queue contract. Include that race and a stuck poll in the shutdown test.

### 7. Keep the runtime and termination contract explicit

The sample's `closeIdleConnections()` and `closeAllConnections()` require Node.js 18.2 or later. Since Node.js 19, `server.close()` also closes idle connections; calling `closeIdleConnections()` after `close()` remains the documented race-safe order for older supported runtimes. These methods do not drain upgraded WebSocket sockets, so track and close those separately.
If the runtime is older than 18.2, use explicit socket tracking instead of calling these methods.

A database statement timeout does not bound how long application code holds its checked-out connection.

Enable Nest's signal listeners in one application-level owner. They are opt-in, and multiple Nest apps in one Node process can exceed the listener warning threshold (a common test-suite issue). `app.close()` runs the hooks but does not exit Node while intervals or other handles remain. Test the real boundary: signal wiring, repeated shutdown, a poll that completes after intake stops, a stuck handler, and abrupt termination.
Use awaited startup hooks for dependency readiness; run schema migrations as an explicit release step when application startup should not own them.

## Summary

Nest runs startup hooks before listening and shutdown hooks around connection closure. Use those phases to stop admission, settle accepted work, and then close its dependencies inside the deployment's shared termination deadline. Treat hook order as a lifecycle boundary, not an implicit dependency graph; abrupt termination still requires recoverable work.

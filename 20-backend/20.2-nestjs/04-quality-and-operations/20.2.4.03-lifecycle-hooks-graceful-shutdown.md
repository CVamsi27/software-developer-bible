# Lifecycle Hooks & Graceful Shutdown


A rollout replaces processes while requests or jobs may still own database connections. Hook order matters when it decides whether those dependencies remain usable until accepted work finishes.

## Definition

**Lifecycle hooks** are interfaces NestJS calls at well-defined moments of application startup and teardown:

> **Textbook Definition:** Lifecycle hooks expose defined startup and teardown stages of a NestJS application. Graceful shutdown coordinates admission, completion of in-flight work and resource closure within a bounded termination period.

| Hook (in execution order) | Phase | Runs for |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `OnModuleInit` | during module initialization | modules, providers, controllers |
| `OnApplicationBootstrap` | once ALL modules initialized | modules, providers, controllers |
| `onModuleDestroy` equivalent: `OnModuleDestroy` | first step of teardown (per module) | modules, providers, controllers |
| `BeforeApplicationShutdown` | after all `OnModuleDestroy`, before Nest closes underlying connections; receives `(signal?: string)` | same |
| `OnApplicationShutdown` | after underlying connections close; receives `(signal?: string)`; `app.close()` alone does not exit the process | same |

**Graceful shutdown** is the practice of handling termination signals so that in-flight work completes, new work is rejected cleanly (load balancer stops routing), and external resources close in a controlled order.

## First Principles

Lifecycle management exists because processes die and connections end — the design question is whether it's orderly:

1. **Stop new work before releasing its dependencies.** First stop accepting requests or jobs, then finish accepted work, close pools, and flush buffers. A load balancer (LB) also needs time to stop routing new requests. Kubernetes' termination grace period allows time for these steps.
2. **Hooks identify startup and shutdown phases.** `onModuleInit` can initialize a module's dependencies; shutdown hooks provide places to drain work and close resources. `enableShutdownHooks` connects the shutdown sequence to process signals. Document which component owns each resource so it is not closed while another component still needs it.
3. **Correctness must survive abrupt termination too.** SIGKILL, out-of-memory failures (OOM), and node crashes may prevent cleanup. Idempotent consumers (→ 20.3.3.05) make repeated work safe; the transactional outbox (→ 20.6.3.06) preserves a pending event with its database change. Graceful shutdown reduces interruption but cannot replace those protections.

## Why Do We Need It?

1. **Bounded rollout interruption** — Kubernetes provides a termination window. Drain accepted work within that budget and measure interruption; hooks alone do not establish zero downtime.
2. **Resource hygiene** — DB pools, Redis clients, message-broker consumers hold sockets and leases; termination interrupts work; lock release and redelivery depend on the database, broker or lease protocol. Database locks release when the backend transaction ends, which need not coincide with local process death.
3. **Ordered dependencies matter** — a repository must not outlive its pool; a consumer that acks messages must not die before it flushes offsets.
4. **Deterministic startup** — migrations, seed caches, and schedulers should start only when the DI graph is fully built (`OnApplicationBootstrap`, not constructors).
5. **Interview signal** — "What happens between SIGTERM and pod death?" tests real production experience more than any decorator question.

## How It Works

### Full Lifecycle Map

```text
STARTUP — ordinary HTTP application
════════════════════════════════════════════════════════════
NestFactory.create(AppModule) → construct modules and dependencies
   │
app.init() or app.listen() → initialize application
   ├─ onModuleInit()             ← module dependencies available
   ├─ onApplicationBootstrap()   ← all module initialization complete
   └─ app.listen() binds HTTP server → accepts connections

SHUTDOWN
════════════════════════════════════════════════════════════
app.close(), or supported signal with enableShutdownHooks()
   ├─ onModuleDestroy()
   ├─ beforeApplicationShutdown(signal?)
   ├─ close underlying connections
   └─ onApplicationShutdown(signal?)

app.close() alone does not terminate the Node.js process.
```

### What hook ordering guarantees—and what you must coordinate

Initialization hooks run after dependencies have been resolved. Nest awaits asynchronous initialization before accepting connections. Request-scoped classes do not receive these application lifecycle hooks.

Hooks are not a substitute for an explicit dependency between two pieces of work. If one service needs another service's initialized cache, coordinate that readiness directly. Do not assume that every provider hook inside a module finishes sequentially.

For shutdown, stop new business work and drain accepted work before releasing the resources it needs. The hook names alone do not ensure that your consumer stops before its database pool closes. Assign those responsibilities deliberately.

### The Kubernetes Termination Dance

```text
kubectl delete pod
   │
   ├─ Pod marked terminating; grace-period budget begins
   ├─ Endpoint routing updates propagate asynchronously
   │
   ├─ preStop hook runs, if configured (uses grace-period time)
   ├─ Container receives TERM after preStop completes
   │      │
   │      ▼
   │   App: stop accepting new work, finish accepted work
   │   App: close external resources
   │      │
   │      ├─ app exits within budget → orderly termination
   │      └─ budget expires → SIGKILL → unfinished work interrupted
   │
   └─ Measure routing delay; reserve time for drain and cleanup too.
```

## Code Examples

### Give a resource one cleanup owner

```typescript
// database.module.ts — a provider owning an expensive resource
import { Injectable, OnApplicationShutdown } from '@nestjs/common';
import { Pool } from 'pg';

@Injectable()
export class DatabaseService implements OnApplicationShutdown {
  private readonly pool = new Pool({ max: 20 });

  query<T>(sql: string, params: unknown[] = []): Promise<T[]> {
    return this.pool.query(sql, params).then((result) => result.rows as T[]);
  }

  async onApplicationShutdown(): Promise<void> {
    await this.pool.end(); // close after HTTP and consumer work has drained
  }
}
```

```typescript
// cache-warming.service.ts — heavy startup belongs in bootstrap, not ctor
import { Injectable, OnApplicationBootstrap, Logger } from '@nestjs/common';

@Injectable()
export class CacheWarmingService implements OnApplicationBootstrap {
  private readonly logger = new Logger(CacheWarmingService.name);

  constructor(private readonly catalog: CatalogService) {}

  async onApplicationBootstrap(): Promise<void> {
    // All onModuleInit hooks completed; coordinate any separate async readiness explicitly.
    const started = Date.now();
    await this.catalog.warmTopProducts();
    this.logger.log(`Cache warmed in ${Date.now() - started}ms`);
  }
}
```

### Enabling Shutdown Hooks in main.ts

```typescript
// main.ts — the ONE line people forget
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create(AppModule);
  app.enableShutdownHooks(); // wires SIGTERM + SIGINT listeners
  await app.listen(3000);
}
bootstrap().catch(error => { console.error(error); process.exitCode = 1; });
```

> `enableShutdownHooks()` makes Nest listen for termination signals. Without it, a signal does not automatically run Nest's shutdown hooks. Calling `app.close()` still runs those hooks. Initialization hooks do not depend on this option.

### Draining Connections Before Closing Pools

```typescript
// graceful-shutdown.service.ts — orchestrated teardown
import {
  Injectable, OnApplicationShutdown, BeforeApplicationShutdown, Logger,
} from '@nestjs/common';
import { Server } from 'http';

@Injectable()
export class ShutdownOrchestrator implements BeforeApplicationShutdown, OnApplicationShutdown {
  private readonly logger = new Logger(ShutdownOrchestrator.name);
  private static readonly DRAIN_TIMEOUT_MS = 20_000;

  private server?: Server;
  private drainPromise?: Promise<void>;

  attachServer(server: Server): void {
    this.server = server;
  }

  /** Idempotent against double signals — safe if invoked twice. */
  private beginDrain(): void {
    if (this.drainPromise) return; // idempotent against double signals
    this.logger.log('Draining: closing keep-alive, refusing new connections');
    if (!this.server) { this.drainPromise = Promise.resolve(); return; }
    const server = this.server;
    this.drainPromise = new Promise((resolve) => {
      const timeout = setTimeout(() => {
        this.logger.warn('Drain timeout — destroying remaining sockets');
        server.closeAllConnections();
        resolve();
      }, ShutdownOrchestrator.DRAIN_TIMEOUT_MS);
      server.close(() => {
        clearTimeout(timeout);
        resolve();
      });
      server.closeIdleConnections(); // after stopping intake, avoiding an idle-close race
    });
  }

  async beforeApplicationShutdown(signal?: string): Promise<void> {
    this.logger.log(`beforeApplicationShutdown (${signal}) — draining in-flight requests`);
    // Nest's SIGTERM handler (enableShutdownHooks) drives this hook;
    // no manual process.on('SIGTERM') anywhere — single owner.
    if (!this.drainPromise) this.beginDrain();
    await this.drainPromise; // consumers/DB still usable here if needed
  }

  async onApplicationShutdown(signal?: string): Promise<void> {
    this.logger.log(`onApplicationShutdown (${signal}) — last chance cleanup`);
  }
}
```

```yaml
# deployment.yaml — give the drain enough runway
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45   # > DRAIN_TIMEOUT_MS (20s) + buffer
      containers:
        - name: api
          lifecycle:
            preStop:                      # let LB endpoint removal propagate
              exec:
                command: ["sleep", "5"]
```

Register `ShutdownOrchestrator` as a provider and call `app.get(ShutdownOrchestrator).attachServer(app.getHttpServer())` before listening. This fragment drains ordinary HTTP connections. Upgraded WebSocket connections and long-running jobs require separate tracking/cancellation; `closeAllConnections()` does not cover every upgraded socket. Its 20-second timer resolves after forcing socket closure. That closes transport, not arbitrary service promises: track accepted handlers/jobs and await their settlement or apply their explicit cooperative cancellation policy before releasing dependencies. At the final termination deadline, unfinished work may be interrupted and must remain retry/recovery safe.

### Closing Resources After Their Dependents

These snippets compose safely only when all consumers finish in `onModuleDestroy` and tracked HTTP business work settles in `beforeApplicationShutdown`; forcing sockets closed does not by itself prove the latter. Close the database and Redis afterward in `onApplicationShutdown`. That final phase must contain no business work that still needs those resources; coordinate dependent cleanup explicitly.

```typescript
// redis + broker consumer teardown done right
import { Injectable, OnModuleDestroy, OnApplicationShutdown, Logger } from '@nestjs/common';
import Redis from 'ioredis';

@Injectable()
export class RedisService implements OnApplicationShutdown {
  private readonly client = new Redis(process.env.REDIS_URL);

  async onApplicationShutdown(): Promise<void> {
    await this.client.quit(); // QUIT: flush pending commands, then close
  }
}

@Injectable()
export class OrdersConsumer implements OnModuleDestroy {
  private readonly logger = new Logger(OrdersConsumer.name);
  private consuming = false;

  constructor(private readonly orders: OrdersProcessor) {}

  async loop(): Promise<void> {
    this.consuming = true;
    while (this.consuming) {
      const job = await this.orders.poll();
      if (!this.consuming) {
        if (job) await this.orders.releaseForRetry(job); // defined poll/lease ownership contract
        break;
      }
      if (job) await this.orders.handle(job);
    }
  }

  async onModuleDestroy(): Promise<void> {
    // 1. stop pulling new jobs FIRST...
    this.consuming = false;
    // 2. ...then unblock poll(), allow the current handler to settle
    await this.orders.drainInFlight(); // must unblock poll and await this loop plus its handler
    this.logger.log('Consumer stopped cleanly');
  }
}
```

`OrdersProcessor` is an application-owned interface, not a Nest API. Its drain must settle the pending poll and wait for the loop/active handler; if a poll hands back claimed work after admission stops, release that claim according to the queue contract. Include that race and a stuck poll in the shutdown test.

## Real-World Use Cases

1. **Reducing rollout errors** — enable shutdown hooks, drain connections, and allow measured time for routing updates. Test under load; a fixed five-second sleep cannot guarantee every rollout has zero 502 responses.
2. **BullMQ worker fleet scale-in** — a process signal or Nest shutdown hook calls the queue worker's documented close/drain API. Stop acquisition and settle accepted jobs within the deadline; SIGTERM is a process event, not a BullMQ Worker event.
3. **Distributed lock safety** — a Redis leader elected via `onApplicationBootstrap` stops protected work before conditionally releasing its still-owned lease. A crash or lost release still requires expiry/recovery; lease release alone does not fence a paused former leader.
4. **Test isolation** — e2e suites call `app.close()` which triggers the identical destroy chain; forgetting it leaks PG connections and CI hangs at exit.
5. **Migrations on boot** — finish migration before starting services that need the new schema. Use an explicit awaited startup step or deployment migration job; placing a module first in `imports` does not establish that dependency.

## Common Mistakes

| Mistake | Fix |
| -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Forgetting `app.enableShutdownHooks()` — hooks never fire on SIGTERM | Call it in `main.ts` right after `create`. It is opt-in by design. |
| Heavy work in service **constructors** (I/O, warmups) | Use `onApplicationBootstrap`; constructors run before the DI graph is complete. |
| Assuming `onModuleInit` of module A means ALL modules are ready | Bootstrap starts after module initialization; explicitly await the particular readiness dependency. |
| Grace period shorter than drain time → SIGKILL mid-request | Budget for `preStop`, draining, and cleanup together; choose the margin from measurements. |
| Closing the DB pool while requests or consumers still need it | Drain business work in earlier phases, then close the pool in `onApplicationShutdown`; do not leave dependent writes in that same final phase. |
| Not calling `.unref()`/draining long-running intervals | Intervals keep the event loop alive and block clean exit after hooks complete. |
| Double-binding SIGTERM handlers manually AND via Nest | Pick one owner; manual `process.on('SIGTERM', ...)` plus Nest hooks leads to double drains. |

## Best Practices

1. **Choose one shutdown owner** for each long-lived entrypoint. Enable Nest signal hooks when they own termination; a controlled standalone script can use `try/finally` and `app.close()` instead.
2. **Keep construction controlled** — use awaited factories or initialization stages for readiness-dependent I/O, with cleanup if initialization fails. Do not perform irreversible business effects during construction.
3. **Teardown in dependency-safe order**: stop intake (server/consumers) → settle accepted work → close resources in the order their actual dependency graph requires.
4. **Make signal handling idempotent** — repeated shutdown requests must not double-drain or throw. Kubernetes normally escalates from TERM to SIGKILL when the grace period expires.
5. **Log each phase with duration** — `drain took 4120ms` makes grace-period sizing data-driven, not guesswork.
6. **Set `terminationGracePeriodSeconds` per workload** — check whether the default 30 seconds covers routing delay, accepted work, and cleanup. Adjust it when measurements show that the workload needs a different budget.
7. **Allow for routing propagation** — choose any `preStop` delay from measurements of your load balancer and cluster. Its time is part of the termination grace period, so reserve enough time for draining and cleanup too.
8. **Verify with chaos drills** — send SIGTERM under load in staging and measure interrupted requests and leaked connections.

## Performance Considerations

- **Hook latency adds deploy time** — sequential `await` chains in many `onModuleInit`s multiply; parallelize independent warmups with `Promise.all`.
- **Drain windows trade latency vs drops** — longer grace periods delay pod recycling. Use measured slow requests and jobs plus explicit deadlines to size the window; an observed maximum cannot bound all future work.
- **Check keep-alive behavior for the Node version.** Since Node 19, `server.close()` closes idle connections. Older versions may need `closeIdleConnections()`. Active requests and upgraded connections still need a drain policy.
- **Connection pool close cost** — `pool.end()` waits for checked-out clients. Always release clients and set deadlines for work that holds them; a statement timeout limits a query, not the time application code keeps a client.

## Summary

- Startup order: construct dependencies → `onModuleInit` → `onApplicationBootstrap` → listen for connections.
- Shutdown order: `onModuleDestroy` → `beforeApplicationShutdown(signal)` → close connections → `onApplicationShutdown(signal)`. Signals trigger this sequence when shutdown hooks are enabled; `app.close()` also triggers it.
- Production correctness = stop intake first, drain in-flight work within `terminationGracePeriodSeconds`, then close dependencies after their consumers have stopped using them.
- The Kubernetes grace period must cover routing delay, draining, and cleanup together. A `preStop` sleep uses part of that shared budget.
- Test repeated shutdown, late poll completion, hanging cleanup and abrupt termination; hook presence cannot establish those behaviors.

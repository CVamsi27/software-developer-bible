# Lifecycle Hooks & Graceful Shutdown

> **TL;DR:** NestJS modules, providers, and controllers expose ordered lifecycle hooks — `OnModuleInit` → `OnApplicationBootstrap` on the way up, `OnModuleDestroy` → `BeforeApplicationShutdown` → `OnApplicationShutdown` on the way down. Shutdown only runs if you call `app.enableShutdownHooks()`, which wires SIGTERM/SIGINT handlers. The senior-level production concern is the Kubernetes dance: stop accepting connections, drain in-flight requests within `terminationGracePeriodSeconds`, then close DB/Redis pools in reverse initialization order — otherwise you drop requests or leak connections.

>
> **Why it matters:** Every rolling deploy exercises this code path. Getting hook order or shutdown sequencing wrong causes 502 bursts during deploys and connection-pool exhaustion after them — classic "works in dev, fails in prod" interview material.

## Definition

**Lifecycle hooks** are interfaces NestJS calls at well-defined moments of application startup and teardown:

| Hook (in execution order)                       | Phase                                                                                                | Runs for                        |
| ---------------------------                       | -------                                                                                                | ----------                        |
| `OnModuleInit`                                  | during module initialization                                                                         | modules, providers, controllers |
| `OnApplicationBootstrap`                        | once ALL modules initialized                                                                         | modules, providers, controllers |
| `onModuleDestroy` equivalent: `OnModuleDestroy` | first step of teardown (per module)                                                                  | modules, providers, controllers |
| `BeforeApplicationShutdown`                     | after all `OnModuleDestroy`, before process exit signals are processed; receives `(signal?: string)` | same                            |
| `OnApplicationShutdown`                         | last step; receives `(signal?: string)`; Nest then calls `process.kill` / exits                      | same                            |

**Graceful shutdown** is the practice of handling termination signals so that in-flight work completes, new work is rejected cleanly (load balancer stops routing), and external resources close in a controlled order.

## Why Do We Need It?

1. **Zero-downtime deploys** — Kubernetes sends SIGTERM with a grace window; the app must stop listening and finish current requests instead of being killed mid-flight.
2. **Resource hygiene** — DB pools, Redis clients, message-broker consumers hold sockets and leases; abrupt kills leave locks held until timeout.
3. **Ordered dependencies matter** — a repository must not outlive its pool; a consumer that acks messages must not die before it flushes offsets.
4. **Deterministic startup** — migrations, seed caches, and schedulers should start only when the DI graph is fully built (`OnApplicationBootstrap`, not constructors).
5. **Interview signal** — "What happens between SIGTERM and pod death?" tests real production experience more than any decorator question.

## How It Works

### Full Lifecycle Map

```text
BOOT SEQUENCE
════════════════════════════════════════════════════════════
NestFactory.create(AppModule)
   │
   ├─ instantiate modules (dependency order, leaves first)
   │    └─ for EACH class (providers + controllers + module):
   │         constructor()            ← DI only, do NOT touch other services
   │
   ├─ for each instance (module init order):
   │    onModuleInit()                ← per-class, awaited sequentially
   │      └─ if it returns a promise, Nest awaits it
   │
   ├─ listen on transport(s)          ← HTTP server binds here
   │
   └─ for each instance:
        onApplicationBootstrap()      ← everything wired, safe to start work
             │
             ▼
        APPLICATION READY (serving traffic)

SHUTDOWN SEQUENCE  (only if enableShutdownHooks())
════════════════════════════════════════════════════════════
SIGTERM / SIGINT received
   │
   ├─ for each instance:
   │    onModuleDestroy()             ← release per-module resources
   │
   ├─ HTTP server: stop accepting NEW connections,
   │  wait for in-flight requests to finish (or force-close)
   │
   ├─ for each instance:
   │    beforeApplicationShutdown(signal?)   ← pre-exit cleanup,
   │                                           can still use connections
   │
   ├─ for each instance:
   │    onApplicationShutdown(signal?)       ← final cleanup;
   │                                          transport servers closed
   │
   └─ process exits (code 0 unless overridden)
```

### Ordering Guarantees

```text
Rules you can rely on:

 1. Constructors run in DEPENDENCY order (deps before dependents).
 2. Hooks run AFTER the whole graph is constructed — no half-built deps.
 3. onModuleInit is called per-instance as soon as ITS module subtree
    finished initializing → module A's onModuleInit may run BEFORE
    unrelated module B's instances even exist.
 4. onApplicationBootstrap runs ONLY after every onModuleInit resolved.
 5. Teardown mirrors boot: onModuleDestroy (all) → transports closed
    → beforeApplicationShutdown (all) → onApplicationShutdown (all).
 6. Within one lifecycle stage, ordering follows module registration
    order (imports first). Do not build cross-module logic on this —
    use explicit coordination (events, promises) instead.
```

### The Kubernetes Termination Dance

```text
kubectl delete pod
   │
   ├─ Endpoint removed from Service (async! ~propagation delay)
   ├─ SIGTERM sent to PID 1 in container
   │      │
   │      ▼
   │   App: stop accept() → respond Connection: close on keep-alive
   │   App: finish in-flight requests
   │      │
   ├─ terminationGracePeriodSeconds counts down (default 30s)
   │      │
   │      ├── app finishes first → exits 0 → clean
   │      └── timer expires → SIGKILL → dropped requests, leaked conns
   │
   └─ NOTE: LB still routes briefly after SIGTERM → either sleep 2-5s
      before draining (preStop hook) or rely on readiness probe flip.
```

## Code Examples

### Implementing Every Hook Correctly

```typescript
// database.module.ts — a provider owning an expensive resource
import { Injectable, OnModuleDestroy } from '@nestjs/common';
import { Pool } from 'pg';

@Injectable()
export class DatabaseService implements OnModuleDestroy {
  private readonly pool = new Pool({ max: 20 });

  query<T>(sql: string, params: unknown[] = []): Promise<T[]> {
    return this.pool.query(sql, params) as Promise<T[]>;
  }

  async onModuleDestroy(): Promise<void> {
    await this.pool.end(); // waits for idle clients, closes all
  }
}
```

```typescript
// cache-warming.service.ts — heavy startup belongs in bootstrap, not ctor
import { Injectable, OnApplicationBootstrap, Logger } from '@nestjs/common';

@Injectable()
export class CacheWarmingService implements OnApplicationBootstrap {
  private readonly logger = new Logger(CacheWarmingService.name);

  constructor(private readonly catalog: CatalogService) {}

  async onApplicationBootstrap(): Promise<void> {
    // Runs after ALL modules initialized — CatalogService fully usable.
    const started = Date.now();
    await this.catalog.warmTopProducts();
    this.logger.log(`Cache warmed in ${Date.now() - started}ms`);
  }
}
```

### Enabling Shutdown Hooks in main.ts

```typescript
// main.ts — the ONE line people forget
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create(AppModule);
  app.enableShutdownHooks(); // wires SIGTERM + SIGINT listeners
  await app.listen(3000);
}
void bootstrap();
```

> Without `enableShutdownHooks()`, SIGTERM kills the process immediately:
> all five hooks above exist but never fire. It is opt-in by design.

### Draining Connections Before Closing Pools

```typescript
// graceful-shutdown.service.ts — orchestrated teardown
import {
  Injectable, OnApplicationShutdown, BeforeApplicationShutdown, Logger,
} from '@nestjs/common';
import { Server } from 'http';

@Injectable()
export class ShutdownOrchestrator implements BeforeApplicationShutdown, OnApplicationShutdown {
  private readonly logger = new Logger(ShutdownOrchestrator.name);
  private static readonly DRAIN_TIMEOUT_MS = 20_000;

  private server?: Server;
  private drainPromise?: Promise<void>;

  attachServer(server: Server): void {
    this.server = server;
  }

  /** Idempotent against double signals — safe if invoked twice. */
  private beginDrain(): void {
    if (this.drainPromise) return; // idempotent against double signals
    this.logger.log('Draining: closing keep-alive, refusing new connections');
    this.server?.closeIdleConnections();
    this.drainPromise = new Promise((resolve) => {
      const timeout = setTimeout(() => {
        this.logger.warn('Drain timeout — destroying remaining sockets');
        this.server?.closeAllConnections();
        resolve();
      }, ShutdownOrchestrator.DRAIN_TIMEOUT_MS);
      this.server?.close(() => {
        clearTimeout(timeout);
        resolve();
      });
    });
  }

  async beforeApplicationShutdown(signal?: string): Promise<void> {
    this.logger.log(`beforeApplicationShutdown (${signal}) — draining in-flight requests`);
    // Nest's SIGTERM handler (enableShutdownHooks) drives this hook;
    // no manual process.on('SIGTERM') anywhere — single owner.
    if (!this.drainPromise) this.beginDrain();
    await this.drainPromise; // consumers/DB still usable here if needed
  }

  async onApplicationShutdown(signal?: string): Promise<void> {
    this.logger.log(`onApplicationShutdown (${signal}) — last chance cleanup`);
  }
}
```

```yaml
# deployment.yaml — give the drain enough runway
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45   # > DRAIN_TIMEOUT_MS (20s) + buffer
      containers:
        - name: api
          lifecycle:
            preStop:                      # let LB endpoint removal propagate
              exec:
                command: ["sleep", "5"]
```

### Closing Resources in Reverse Initialization Order

```typescript
// redis + broker consumer teardown done right
import { Injectable, OnModuleDestroy, Logger } from '@nestjs/common';
import Redis from 'ioredis';

@Injectable()
export class RedisService implements OnModuleDestroy {
  private readonly client = new Redis(process.env.REDIS_URL);

  async onModuleDestroy(): Promise<void> {
    await this.client.quit(); // QUIT: flush pending commands, then close
  }
}

@Injectable()
export class OrdersConsumer implements OnModuleDestroy {
  private readonly logger = new Logger(OrdersConsumer.name);
  private consuming = false;

  constructor(private readonly orders: OrdersProcessor) {}

  async loop(): Promise<void> {
    this.consuming = true;
    while (this.consuming) {
      const job = await this.orders.poll();
      if (job) await this.orders.handle(job);
    }
  }

  async onModuleDestroy(): Promise<void> {
    // 1. stop pulling new jobs FIRST...
    this.consuming = false;
    // 2. ...then unblock poll(), allow the current handler to settle
    await this.orders.drainInFlight();
    this.logger.log('Consumer stopped cleanly');
  }
}
```

## Real-World Use Cases

1. **Rolling deploy without 502s** — `enableShutdownHooks()` + `closeIdleConnections()` + a `preStop: sleep 5` keeps error rate flat across every rollout.
2. **BullMQ worker fleet scale-in** — workers register `Worker.on('SIGTERM')`-equivalent via `onModuleDestroy`: stop picking jobs, finish the active one, report completion, then exit inside the grace period.
3. **Distributed lock safety** — a Redis leader elected via `onApplicationBootstrap` releases its lock in `onModuleDestroy` so failover starts immediately instead of after TTL expiry.
4. **Test isolation** — e2e suites call `app.close()` which triggers the identical destroy chain; forgetting it leaks PG connections and CI hangs at exit.
5. **Migrations on boot** — schema migration runs in `onModuleInit` of a dedicated module imported first, guaranteeing tables exist before repositories initialize.

## Common Mistakes

| Mistake                                                                                                        | Fix                                                                                            |
| ---------                                                                                                        | -----                                                                                            |
| Forgetting `app.enableShutdownHooks()` — hooks never fire on SIGTERM                                           | Call it in `main.ts` right after `create`. It is opt-in by design.                             |
| Heavy work in service **constructors** (I/O, warmups)                                                          | Use `onApplicationBootstrap`; constructors run before the DI graph is complete.                |
| Assuming `onModuleInit` of module A means ALL modules are ready                                                | Only `onApplicationBootstrap` guarantees full-graph readiness.                                 |
| Grace period shorter than drain time → SIGKILL mid-request                                                     | Size `terminationGracePeriodSeconds` ≥ drain timeout + connection close buffer (~1.5x).        |
| Closing the DB pool in `beforeApplicationShutdown` while other services still write in `onApplicationShutdown` | Close pools LAST (`onApplicationShutdown`) or strictly reverse init order; document ownership. |
| Not calling `.unref()`/draining long-running intervals                                                         | Intervals keep the event loop alive and block clean exit after hooks complete.                 |
| Double-binding SIGTERM handlers manually AND via Nest                                                          | Pick one owner; manual `process.on('SIGTERM', ...)` plus Nest hooks leads to double drains.    |

## Best Practices

1. **Always call `enableShutdownHooks()`** in every entrypoint (HTTP, microservice, standalone scripts).
2. **Constructors only assign fields** — anything touching I/O or other services' state belongs in bootstrap hooks.
3. **Teardown in strict reverse-init order**: stop intake (server/consumers) → finish in-flight work → close caches → close DB pools last.
4. **Make signal handling idempotent** — double SIGTERM (K8s escalates) must not double-drain or throw.
5. **Log each phase with duration** — `drain took 4120ms` makes grace-period sizing data-driven, not guesswork.
6. **Set `terminationGracePeriodSeconds` explicitly per workload** — default 30s is wrong for batch-heavy pods and wasteful for tiny ones.
7. **Use a `preStop` sleep** equal to your endpoint-propagation lag (usually 2–5s) to avoid the LB race.
8. **Verify with chaos drills** — send SIGTERM under load in staging and assert zero 5xx and zero leaked connections.

## Performance Considerations

- **Hook latency adds deploy time** — sequential `await` chains in many `onModuleInit`s multiply; parallelize independent warmups with `Promise.all`.
- **Drain windows trade latency vs drops** — longer grace periods delay pod recycling; measure p100 request duration to size it.
- **Keep-alive sockets hide in `close()`** — Node's `server.close()` waits for open keep-alive connections indefinitely; always pair with `closeIdleConnections()`.
- **Connection pool close cost** — `pool.end()` waits for checked-out clients; cap checkout time upstream with statement timeouts.

## Summary

- Startup order: constructors (dependency order) → `onModuleInit` (per module) → transports bind → `onApplicationBootstrap` (full graph ready).
- Shutdown order (opt-in via `enableShutdownHooks()`): `onModuleDestroy` → transport close → `beforeApplicationShutdown(signal)` → `onApplicationShutdown(signal)` → exit.
- Production correctness = stop intake first, drain in-flight work within `terminationGracePeriodSeconds`, then close resources reverse-order with DB pools last.
- The K8s interplay has three clocks: endpoint propagation (preStop sleep), drain timeout, grace period — grace must be the largest.
- Most deploy bugs are one-liners: missing `enableShutdownHooks()`, sync work in constructors, or a pool closed too early.

## Cheat Sheet

| Concept                              | Description                                                       |
| ---------                              | -------------                                                       |
| `OnModuleInit`                       | Per-instance hook once its module subtree initialized; awaited    |
| `OnApplicationBootstrap`             | Runs after ALL `onModuleInit` — safe to start background work     |
| `OnModuleDestroy`                    | First teardown step; release per-module resources                 |
| `BeforeApplicationShutdown(signal?)` | After destroys, before transports killed; drain here              |
| `OnApplicationShutdown(signal?)`     | Final cleanup; close DB pools here or earlier-reverse             |
| `app.enableShutdownHooks()`          | Wires SIGTERM/SIGINT to the destroy chain — mandatory             |
| `terminationGracePeriodSeconds`      | K8s budget; must exceed drain timeout or SIGKILL fires            |
| `preStop: sleep N`                   | Covers LB endpoint-propagation lag after SIGTERM                  |
| `closeIdleConnections()`             | Keep-alive sockets would otherwise block `server.close()` forever |
| Idempotent drain                     | Guard double-SIGTERM; K8s may escalate quickly                    |

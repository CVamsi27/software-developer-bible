# Scheduling & Background Jobs


>
> **Why it matters:** "Why did the nightly report send 12 times?" is the canonical distributed-cron interview story. Seniors are expected to know the cron-vs-queue decision, lock semantics, backoff strategies, and how to make handlers safe to re-run.

## Definition

Two complementary mechanisms:

> **Textbook Definition:** Scheduling determines when work becomes eligible to run; a job queue records work and assigns it to workers. Persistence, retries and duplicate execution depend on the queue and worker contracts rather than the scheduling expression.

- **`@nestjs/schedule`** — decorator-driven timers inside the app process: `@Cron` (cron expressions), `@Interval` (fixed period), `@Timeout` (one-shot delay), all manageable at runtime through `SchedulerRegistry` (pause, resume, add, delete).
- **BullMQ** — Redis-backed job queue: producers `add()` named jobs with payloads; workers process them with configured retries and backoff, per-queue rate limits, priorities, delayed jobs, and persistent job schedules (API depends on the BullMQ version).

A schedule decides when work should start. A queue records work so a worker can process it and apply the configured retry policy if it fails. An in-process cron trigger disappears when its process stops. A queued job can survive a worker restart when Redis retains the job data; durability still depends on the Redis deployment.

## First Principles

Background work exists because request-scoped time limits can't hold for everything:

1. **Work can outlast a request's allowed wait.** If the task exceeds the application or proxy timeout (often around 30 seconds; → 20.3.3.03), move execution out of the request. A scheduler or queue separates accepting the work from finishing it.
2. **A schedule does not promise an exact execution instant.** Every replica may run the same cron trigger. A distributed lock (→ 20.8.03) or leader election can coordinate which replica starts a run. Make handlers idempotent, meaning repeating the same logical operation does not duplicate its effect, because coordination can still fail.
3. **Queues need a failure policy.** Backoff increases the delay between retries; dead-letter handling separates work that has exhausted retries; visibility or ownership timeouts allow another worker to recover unfinished work. With at-least-once delivery (→ 20.6.2.05), a handler must tolerate receiving the same job again.

## Why Do We Need It?

1. **Time-based work** — nightly digests, token cleanup, cache warming: nothing should run them inside a request.
2. **Durability beyond the process** — an in-memory interval dies with the pod; a BullMQ job persisted in Redis resumes after redeploy.
3. **Load smoothing** — 10k email sends should trickle out at a rate limit, not stampede SMTP.
4. **Retry discipline** — flaky downstreams need exponential backoff with jitter, not a tight loop.
5. **Coordinated triggers** — a lease reduces overlapping schedulers; a durable run identity and duplicate-safe effect handle repeats.

## How It Works

### Decision Model: Queue vs Cron vs Both

```text
                 ┌───────────────────────────────┐
                 │ Does it need to SURVIVE a     │
                 │ crash / deploy?               │
                 └──────┬────────────────┬───────┘
                     yes│                        │no
                        ▼                ▼
                  BULLMQ QUEUE      @nestjs/schedule
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
   Triggered by events            Triggered by TIME?
   (user uploads, webhooks)              │
        │                          yes   ▼
        │                     ┌────────────────────────────┐
        │                     │ Multi-replica deployment?  │
        │                     └──────┬───────────────┬─────┘
        │                         yes│               │no
        │                            ▼               ▼
        │                    cron + LOCK       plain @Cron
        │
        ▼
   HYBRID: @Cron (locked) ENQUEUES a BullMQ job
   → coordinated trigger, durable enqueue identities, duplicate-safe workers
```

### How Distributed Cron Locking Works

```text
Pod A handler starts:
  SET jobs:nightly-digest:2026-08-25 <podA> NX PX 3600000
        │
        ├── OK    → I hold this lease until expiry. Run. Owner-checked release.
        └── nil   → another pod holds the lock → skip silently.

Key design points:
 • Key includes a RUN ID (date/bucket) → next run never blocked by
   yesterday's stale lock; stale locks self-expire via PX.
 • Value = unique token per acquisition, with pod identity logged separately.
 • Release with a Lua check-and-del → only the owner deletes it.
 • A lease can expire while its holder still runs; compare coordination options
   against the resource's required guarantees. DB advisory locks
   (PostgreSQL pg_advisory_lock) when Redis is not already present.
```

### BullMQ Execution Flow

```text
Producer add() -> Redis records waiting/delayed job
Worker claims job -> owns a renewable processing lease -> executes handler
  success -> completed state
  exception -> retry after configured delay, or failed after attempts are exhausted
  lost lease/crashed worker -> stalled-job recovery may run the job again
```

A job's state belongs to the queue; the email, bank transfer or database effect belongs to another system. A crash between those two updates explains why a completed business operation can be delivered again. Internal Redis commands and data structures are version details, not the contract to memorize.

## Code Examples

### Declarative Scheduling with @nestjs/schedule

```typescript
// reports.scheduler.ts
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression, Interval, Timeout } from '@nestjs/schedule';

@Injectable()
export class ReportsScheduler {
  private readonly logger = new Logger(ReportsScheduler.name);

  constructor(private readonly digests: DigestService) {}

  // Every day 06:00 Europe/Berlin — each process registers its own trigger
  @Cron(CronExpression.EVERY_DAY_AT_6AM, { name: 'nightly-digest', timeZone: 'Europe/Berlin' })
  async nightlyDigest(): Promise<void> {
    this.logger.log('nightly digest started');
    await this.digests.sendAll();
  }

  // Every 30s — cheap liveness-sensitive sweeps
  @Interval('stale-session-sweep', 30_000)
  async sweepStaleSessions(): Promise<void> {
    await this.digests.expireSessions();
  }

  // Once, 10s after boot — warm caches after full init
  @Timeout('warm-cache', 10_000)
  async warmCache(): Promise<void> {
    await this.digests.warmCache();
  }
}
```

// app.module.ts — registration

### Dynamic API: SchedulerRegistry

```typescript
// dynamic-jobs.service.ts — create/manage crons at runtime
import { Injectable, OnModuleDestroy } from '@nestjs/common';
import { SchedulerRegistry } from '@nestjs/schedule';
import { CronJob } from 'cron';

@Injectable()
export class DynamicJobsService implements OnModuleDestroy {
  constructor(private readonly scheduler: SchedulerRegistry) {}

  addTenantCron(tenantId: string, expression: string): void {
    const name = `tenant-${tenantId}-sync`;
    if (this.scheduler.doesExist('cron', name)) {
      this.scheduler.deleteCronJob(name); // replace, don't duplicate
    }
    const job = new CronJob(expression, async () => {
      await this.syncTenant(tenantId);
    });
    this.scheduler.addCronJob(name, job);
    job.start();
  }

  pauseAll(): void {
    for (const name of this.scheduler.getCronJobs().keys()) {
      this.scheduler.getCronJob(name).stop();
    }
  }

  async onModuleDestroy(): Promise<void> {
    // hooks chapter: stop intake first, then release resources
    this.pauseAll();
  }

  private async syncTenant(tenantId: string): Promise<void> {
    /* ... */
  }
}
```

### A Lease Reduces Overlapping Cron Runs

```typescript
// redis-lock.service.ts — owner-safe lock with Lua release
import { Injectable } from '@nestjs/common';
import Redis from 'ioredis';
import { randomUUID } from 'node:crypto';

@Injectable()
export class RedisLockService {
  constructor(private readonly redis: Redis) {}

  private static readonly RELEASE_LUA =
    `if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1]) else return 0 end`;

  async acquire(key: string, ttlMs: number): Promise<string | null> {
    const ownerId = randomUUID();
    const ok = await this.redis.set(key, ownerId, 'PX', ttlMs, 'NX');
    return ok === 'OK' ? ownerId : null;
  }

  async release(key: string, ownerId: string): Promise<void> {
    await this.redis.eval(
      RedisLockService.RELEASE_LUA, 1, key, ownerId,
    );
  }
}
```

```typescript
// locked-digest.scheduler.ts — lease coordination, not durable deduplication
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression } from '@nestjs/schedule';

@Injectable()
export class LockedDigestScheduler {
  private readonly logger = new Logger(LockedDigestScheduler.name);

  constructor(private readonly locks: RedisLockService, private readonly digests: DigestService) {}

  @Cron(CronExpression.EVERY_DAY_AT_6AM)
  async nightlyDigest(): Promise<void> {
    // This example uses UTC days. Align the run ID with the chosen business timezone.
    // PX guards against a crashed holder blocking tomorrow's run.
    const runId = new Date().toISOString().slice(0, 10);
    const ownerId = await this.locks.acquire(`locks:nightly-digest:${runId}`, 3_600_000);
    if (!ownerId) return; // another replica won; skip quietly
    try {
      await this.digests.sendAll();
    } finally {
      await this.locks.release(`locks:nightly-digest:${runId}`, ownerId);
    }
  }
}
```

These Nest fragments require providers such as `DigestService`/`Mailer`, `@nestjs/schedule`, `@nestjs/bullmq`, BullMQ, `cron` and a configured Redis client. Register the scheduler and processor classes as providers. In-process timers do not catch up missed execution automatically, and an interval can overlap its previous asynchronous invocation. Choose a skip/queue policy explicitly; for cron, version-supported `waitForCompletion` skips overlapping ticks only within that process.

Releasing the daily lease allows a delayed replica to acquire it again. Expiry can also admit a second worker while the first continues. Record a unique durable run ID and make each resulting job/effect duplicate-safe. Owner-checked release prevents deleting another holder's lease; it cannot prevent an expired holder from writing to an external resource.

### BullMQ Queues, Retries, Backoff, Rate Limits

```typescript
// queue.module.ts
import { Module } from '@nestjs/common';
import { BullModule } from '@nestjs/bullmq';

@Module({
  imports: [
    BullModule.forRoot({
      connection: { host: process.env.REDIS_HOST, port: 6379 },
      defaultJobOptions: {
        attempts: 5,
        backoff: { type: 'exponential', delay: 1_000, jitter: 0.5 },
        removeOnComplete: 1_000,
        removeOnFail: 5_000,
      },
    }),
    BullModule.registerQueue({ name: 'email' }, { name: 'report' }),
  ],
  exports: [BullModule],
})
export class JobsModule {}
```

```typescript
// email.producer.ts
import { InjectQueue } from '@nestjs/bullmq';
import { Queue } from 'bullmq';

export interface SendEmailJob {
  userId: string;
  template: string;
  idempotencyKey: string;
}

@Injectable()
export class EmailProducer {
  constructor(@InjectQueue('email') private readonly emailQueue: Queue<SendEmailJob>) {}

  async enqueueWelcome(userId: string): Promise<void> {
    await this.emailQueue.add(
      'send-email',
      { userId, template: 'welcome', idempotencyKey: `welcome:${userId}` },
      { priority: 5, delay: 60_000 },
    );
  }

  async enqueueDigestBatch(runId: string, userIds: string[]): Promise<void> {
    // Batch enqueue reduces network round trips; it does not order worker completion.
    await this.emailQueue.addBulk(
      userIds.map((userId) => ({
        name: 'send-email',
        data: { userId, template: 'daily-digest', idempotencyKey: `digest:${runId}:${userId}` },
        opts: { priority: 1 },
      })),
    );
  }
}
```

```typescript
// email.processor.ts — worker with rate limiting
import { Processor, WorkerHost, OnWorkerEvent } from '@nestjs/bullmq';
import { Job } from 'bullmq';
import { Logger } from '@nestjs/common';
import { Mailer } from './mailer';

@Processor('email', {
  limiter: { max: 100, duration: 60_000 }, // max 100 starts/minute across workers on this queue
  concurrency: 10,
})
export class EmailProcessor extends WorkerHost {
  private readonly logger = new Logger(EmailProcessor.name);

  constructor(private readonly mailer: Mailer) {
    super();
  }

  async process(job: Job<SendEmailJob>): Promise<void> {
    this.logger.log(`Processing ${job.name} #${job.id} attempt ${job.attemptsMade + 1}`);
    await this.mailer.sendWithIdempotencyKey(
      job.data.idempotencyKey,   // dedupe at provider side too
      job.data.userId,
      job.data.template,
    );
  }

  @OnWorkerEvent('failed')
  onFailed(job: Job, err: Error): void {
    this.logger.warn(`job ${job.id} failed (${err.message}); attempts made ${job.attemptsMade}`);
  }

  @OnWorkerEvent('completed')
  onCompleted(job: Job): void {
    this.logger.log(`job ${job.id} completed in ${job.finishedOn! - job.processedOn!}ms`);
  }
}
```

### A Payout Claim Does Not Resolve an Uncertain Bank Transfer

An atomic database transition from `pending` to `processing` prevents two workers from claiming the same row at the same instant. It does not make the remote bank call transactional with that row. If the bank accepts a transfer and the reply is lost, resetting the row to `pending` invites a second transfer.

Use an operation identity that is persisted before the external call and accepted by the provider as an idempotency key. Keep the identity stable across attempts, and define how the provider reports an existing result. If the provider offers neither duplicate suppression nor a reliable lookup, a timeout may require manual reconciliation rather than an automatic new transfer.

| Observed state/outcome | Next action |
| ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| Already `paid` with the stored provider result | Return that result; do not call the bank again |
| A live worker owns `processing` | Let it finish; do not acknowledge the payout as paid |
| Ownership expired, result not known | Look up the persisted operation identity at the provider |
| Provider confirms acceptance | Persist `paid` and its reference before reporting completion |
| Provider confirms rejection with no effect | Apply the documented retry/terminal policy |
| Timeout or ambiguous provider status | Keep `unknown`/reconciling state; preserve the identity and alert after a deadline |

Trace a crash: payout `p7` stores key `payout-p7`, the bank accepts it, then the worker stops before marking `paid`. A later worker queries or resubmits that same key under the provider's documented contract. It records the accepted result instead of submitting `payout-p7-attempt2`. The queue can now complete without duplicating the transfer.

The database claim also needs an expiry/owner and recovery policy so a stopped worker does not leave work stuck forever. A lease and a durable business-operation identity solve different parts of the problem.

### Scheduled-Job Observability

```typescript
// jobs.metrics.ts — expose queue health to Prometheus-style scrapes
import { Controller, Get } from '@nestjs/common';
import { Queue } from 'bullmq';
import { InjectQueue } from '@nestjs/bullmq';

@Controller('internal/jobs')
export class JobsMetricsController {
  constructor(@InjectQueue('email') private readonly emailQueue: Queue) {}

  @Get('health')
  async health(): Promise<Record<string, number>> {
    const counts = await this.emailQueue.getJobCounts(
      'waiting', 'active', 'completed', 'failed', 'delayed',
    );
    return counts;
  }
}

// Alert rules worth wiring:
//   waiting > threshold for > 10min   -> producer outpacing workers
//   failed > 0 sustained              -> poison messages or outage
//   oldest active job age > SLA       -> stuck worker / missing event loop
// Also log job.duration, job.attemptsMade, and dead-letter anything
// that exhausts attempts (BullMQ event 'failed' plus attemptsMade/opts.attempts checks).
```

## Real-World Use Cases

1. **Nightly billing across 20 replicas** — cron enqueues one BullMQ job per account behind a daily lock; workers process with concurrency 50 and exponential backoff against a flaky payment API.
2. **Email marketing sends** — producer `addBulk`s 100k jobs; queue limiter caps at provider-compliant rates; a provider-enforced idempotency contract can suppress duplicate effects; merely including a payload field cannot.
3. **Per-tenant sync schedules** — `SchedulerRegistry.addCronJob` creates tenant-specific expressions at runtime; deleting a tenant removes its cron without redeploy.
4. **Webhook deliveries with retries** — recipient timeouts get 5 attempts with jittered exponential backoff; exhausted jobs remain failed unless the application explicitly routes them to a dead-letter workflow.
5. **Cache warming after deploys** — `@Timeout` warms hot keys 10 seconds post-bootstrap, while a locked `@Cron(EVERY_HOUR)` refreshes them continuously.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plain `@Cron` in a multi-replica deployment | Every pod fires the job. Add a distributed lock keyed by run ID, or elect a leader. |
| Non-idempotent handlers under at-least-once delivery | Use durable operation identities and recovery for uncertain effects; a state claim only coordinates ownership. |
| Fixed-delay retries hammering a struggling dependency | Use exponential backoff with jitter; cap attempts and dead-letter the rest. |
| Lock TTL shorter than job duration | Second runner acquires the expired lock and duplicates work. Renew within measured deadlines and handle lease loss; no observed worst case guarantees future runtimes. |
| Forgetting `ScheduleModule.forRoot()` | Decorators compile fine but nothing schedules; silent no-op. |
| Testing schedulers with real sleeps | Trigger handlers directly, or use `SchedulerRegistry.getCronJob(...)` to control timing deterministically. |
| Unbounded `removeOnComplete` growth | Set retention counts/max age, otherwise Redis memory balloons. |

## Best Practices

1. **Use the hybrid pattern when work is scheduled and retriable** — a coordinated cron trigger enqueues jobs for BullMQ workers. Use a durable run identifier and duplicate-safe enqueueing; a lock alone does not guarantee exactly one fan-out.
2. **Name every scheduled task** (`{ name: '...' }`) — required for `SchedulerRegistry` management and for meaningful logs/metrics.
3. **Set explicit `timeZone`** on crons — server TZ drift breaks business-day logic.
4. **Make every job handler idempotent even if you think it cannot double-run** — at-least-once is a property of the transport, not your intentions.
5. **Include a run ID / idempotency key in payloads** — the handler must use it to recognize a previously completed operation and avoid repeating its effect.
6. **Expose queue depth + failure counters** — scheduling failures are invisible unless you measure them.
7. **Keep cron expressions in config, not code** — ops changes schedules without releases.

## Performance Considerations

- **Every cron tick wakes the whole event loop** — prefer fewer, batched intervals over many high-frequency timers; `.unref()` non-critical ones.
- **BullMQ polling vs blocking** — use the supported worker API; its implementation changes across versions. Avoid busy polling.
- **Concurrency tuning is per-worker** — in-process JavaScript concurrency does not add CPU parallelism. Use sandboxed processors/worker processes for CPU work, and measure I/O concurrency against downstream capacity.
- **Rate limits are queue-wide** — the `limiter` option applies across workers sharing the queue, which is usually what you want for provider quotas.
- **Redis latency bounds throughput** — colocate Redis with workers or accept added p50 per job; monitor `event_loop_lag` on worker pods too.

## Summary

- `@nestjs/schedule` covers in-process triggers (declarative decorators + dynamic `SchedulerRegistry`); BullMQ covers durable, retriable, rate-limited background work in Redis.
- Multi-replica cron needs a distributed lock keyed by run ID with owner-checked release — it still needs durable run/effect deduplication.
- Choose cron for "when", queues for "what if it fails", and both together for scheduled fan-out of resilient work.
- Handlers must be idempotent: combine durable operation identities, provider contracts and recovery because executions can repeat.
- Observability closes the loop: queue counts, failure events, durations, and dead-letter handling turn silent breakage into alerts.

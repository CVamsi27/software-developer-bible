# Scheduling & Background Jobs

A nightly digest can run once in each replica, or repeat after a worker loses its acknowledgment. Separate when a run becomes eligible from durable job ownership and duplicate-safe business effects.

## Definition

Two complementary mechanisms:

> **Textbook Definition:** Scheduling determines when work becomes eligible to run; a job queue records work and assigns it to workers. Persistence, retries and duplicate execution depend on the queue and worker contracts rather than the scheduling expression.

- **`@nestjs/schedule`** — decorator-driven timers inside the app process: `@Cron` (cron expressions), `@Interval` (fixed period), `@Timeout` (one-shot delay), all manageable at runtime through `SchedulerRegistry` (pause, resume, add, delete).
- **BullMQ** — Redis-backed queue: producers add named jobs and workers process them with configured concurrency, retries, backoff, priorities and rate limits. BullMQ v6 uses `queue.upsertJobScheduler(...)` for recurring work; the old `Queue.add({ repeat })` and repeat-management APIs were deprecated in v5.16 and removed in v6. Redis persistence and failover settings determine how much queued work survives infrastructure failure.

A schedule decides when work should start. A queue records work so a worker can process it and apply the configured retry policy if it fails. An in-process cron trigger disappears when its process stops.
A queued job can survive a worker restart when Redis retains the job data; durability still depends on the Redis deployment.

## First Principles

Background work exists because request-scoped time limits can't hold for everything:

1. **Work can outlast a request's allowed wait.** If the task exceeds the application or proxy timeout (set by the actual deployment; → 20.3.3.03), move execution out of the request. A scheduler or queue separates accepting the work from finishing it.
2. **A schedule does not promise an exact execution instant.** Every replica may run the same cron trigger. A distributed lock (→ 20.8.03) or leader election can coordinate which replica starts a run. Make handlers idempotent, meaning repeating the same logical operation does not duplicate its effect, because coordination can still fail.
3. **Queues need a failure policy.** Backoff increases the delay between retries; dead-letter handling separates work that has exhausted retries; visibility or ownership timeouts allow another worker to recover unfinished work. With at-least-once delivery (→ 20.6.2.05), a handler must tolerate receiving the same job again.

## How It Works


### 1. Choose the trigger and the work contract separately

| Requirement | Mechanism | What it guarantees—and what it does not |
| ----------------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A best-effort in-process timer | `@nestjs/schedule` | A running process invokes a callback. It does not persist missed ticks or coordinate replicas. |
| Durable, event-triggered work | BullMQ `queue.add()` | A job is stored in Redis and can be retried by workers. Delivery may repeat; Redis durability depends on deployment settings. |
| Recurring work that should create durable jobs | BullMQ `queue.upsertJobScheduler()` | A scheduler produces jobs from an interval or cron pattern. Production depends on worker capacity: a busy queue can cause generated jobs to arrive less frequently than the configured interval. |
| A time-based run that fans out and needs durable processing | Coordinated scheduler plus BullMQ | The trigger starts one logical run and queues work; a stable run ID and idempotent effects handle duplicate triggers and enqueue retries. |

Use the hybrid only when both timing and durable processing matter. A queue does not make the original database write and enqueue atomic: commit an outbox row with the business change, then relay it to the queue (→ transactional outbox). Otherwise a process can commit the change and crash before `queue.add()`, leaving work unscheduled.

An in-process timer is appropriate for recomputable maintenance where a missed tick is acceptable. It is the wrong owner for money movement, compliance events or work whose omission needs recovery. A BullMQ job is not exactly-once business execution: a worker can complete an effect and lose the acknowledgment, so the queue may run it again.

#### How Distributed Cron Locking Works

```text
Pod A handler starts:
  SET jobs:nightly-digest:2026-08-25 <podA> NX PX 3600000
        │
        ├── OK    → I hold this lease until expiry. Run. Owner-checked release.
        └── nil   → another pod holds the lock → skip silently.

Key design points:
 • Key includes a RUN ID (date/bucket) → next run never blocked by
   yesterday's stale lock; stale locks self-expire via PX.
 • Value = unique token per acquisition, with pod identity logged separately.
 • Release with a Lua check-and-del → only the owner deletes it.
 • A lease can expire while its holder still runs; compare coordination options
   against the resource's required guarantees. DB advisory locks
   (PostgreSQL pg_advisory_lock) when Redis is not already present.
```

#### BullMQ Execution Flow

```text
Producer add() -> Redis records waiting/delayed job
Worker claims job -> owns a renewable processing lease -> executes handler
  success -> completed state
  exception -> retry after configured delay, or failed after attempts are exhausted
  lost lease/crashed worker -> stalled-job recovery may run the job again
```

A job's state belongs to the queue; the email, bank transfer or database effect belongs to another system. A crash between those two updates explains why a completed business operation can be delivered again. Internal Redis commands and data structures are version details, not the contract to memorize.

For recurring work, register the scheduler with a stable ID so deployment restarts update the same schedule instead of creating another one:

```typescript
await emailQueue.upsertJobScheduler(
  'daily-digest',
  { pattern: '0 0 6 * * *', tz: 'Europe/Berlin' },
  {
    name: 'daily-digest',
    data: {},
    opts: { attempts: 5, backoff: { type: 'exponential', delay: 1_000 } },
  },
);
```

BullMQ's scheduler is a job factory, not a wall-clock guarantee: it produces the next job as its prior job starts processing. Queue saturation or a worker outage can therefore shift the effective cadence. If the business requirement is “run for every calendar date even while workers are down,” persist each expected date/run ID and reconcile gaps; do not infer completion from the scheduler's existence.

### 2. Implement the trigger, work and recovery path

#### Declarative Scheduling with @nestjs/schedule

```typescript
// reports.scheduler.ts
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression, Interval, Timeout } from '@nestjs/schedule';

@Injectable()
export class ReportsScheduler {
  private readonly logger = new Logger(ReportsScheduler.name);

  constructor(private readonly digests: DigestService) {}

  // Every day 06:00 Europe/Berlin — each process registers its own trigger
  @Cron(CronExpression.EVERY_DAY_AT_6AM, { name: 'nightly-digest', timeZone: 'Europe/Berlin' })
  async nightlyDigest(): Promise<void> {
    this.logger.log('nightly digest started');
    await this.digests.sendAll();
  }

  // Every 30s — cheap liveness-sensitive sweeps
  @Interval('stale-session-sweep', 30_000)
  async sweepStaleSessions(): Promise<void> {
    await this.digests.expireSessions();
  }

  // Once, 10s after boot — warm caches after full init
  @Timeout('warm-cache', 10_000)
  async warmCache(): Promise<void> {
    await this.digests.warmCache();
  }
}
```

```typescript
// app.module.ts — registration
import { Module } from '@nestjs/common';

@Module({
  imports: [ScheduleModule.forRoot()], // once, in AppModule
```

#### Dynamic API: SchedulerRegistry

```typescript
// dynamic-jobs.service.ts — create/manage crons at runtime
import { Injectable, Logger, OnModuleDestroy } from '@nestjs/common';
import { SchedulerRegistry } from '@nestjs/schedule';
import { CronJob } from 'cron';

@Injectable()
export class DynamicJobsService implements OnModuleDestroy {
  private readonly active = new Set<Promise<void>>();
  private readonly logger = new Logger(DynamicJobsService.name);
  constructor(private readonly scheduler: SchedulerRegistry) {}

  addTenantCron(tenantId: string, expression: string): void {
    const name = `tenant-${tenantId}-sync`;
    if (this.scheduler.doesExist('cron', name)) {
      this.scheduler.deleteCronJob(name); // replace, don't duplicate
    }
    const job = new CronJob(expression, () => {
      const task = this.syncTenant(tenantId);
      this.active.add(task);
      void task.catch(() => this.logger.error('Tenant synchronization failed'))
        .finally(() => this.active.delete(task));
    });
    this.scheduler.addCronJob(name, job);
    job.start();
  }

  pauseAll(): void {
    for (const name of this.scheduler.getCronJobs().keys()) {
      this.scheduler.getCronJob(name).stop();
    }
  }

  async onModuleDestroy(): Promise<void> {
    // hooks chapter: stop intake first, then release resources
    this.pauseAll(); // stops future ticks, not an already running callback
    await Promise.allSettled([...this.active]);
  }

  private async syncTenant(tenantId: string): Promise<void> {
    /* ... */
  }
}
```

Authorize the tenant/schedule operation before calling `addTenantCron`, validate an allowed timezone and expression, and cap registered schedules plus active work. The snippet tracks completion for teardown but does not impose those admission limits or prevent overlapping callbacks. A shared shutdown deadline still bounds hanging work.

#### A Lease Reduces Overlapping Cron Runs

```typescript
// redis-lock.service.ts — owner-safe lock with Lua release
import { Injectable } from '@nestjs/common';
import Redis from 'ioredis';
import { randomUUID } from 'node:crypto';

@Injectable()
export class RedisLockService {
  constructor(private readonly redis: Redis) {}

  private static readonly RELEASE_LUA =
    `if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1]) else return 0 end`;

  async acquire(key: string, ttlMs: number): Promise<string | null> {
    const ownerId = randomUUID();
    const ok = await this.redis.set(key, ownerId, 'PX', ttlMs, 'NX');
    return ok === 'OK' ? ownerId : null;
  }

  async release(key: string, ownerId: string): Promise<void> {
    await this.redis.eval(
      RedisLockService.RELEASE_LUA, 1, key, ownerId,
    );
  }
}
```

```typescript
// locked-digest.scheduler.ts — lease coordination, not durable deduplication
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression } from '@nestjs/schedule';

@Injectable()
export class LockedDigestScheduler {
  private readonly logger = new Logger(LockedDigestScheduler.name);

  constructor(private readonly locks: RedisLockService, private readonly digests: DigestService) {}

  @Cron(CronExpression.EVERY_DAY_AT_6AM, { timeZone: 'UTC' })
  async nightlyDigest(): Promise<void> {
    // This example uses UTC days. Align the run ID with the chosen business timezone.
    // PX guards against a crashed holder blocking tomorrow's run.
    const runId = new Date().toISOString().slice(0, 10);
    const ownerId = await this.locks.acquire(`locks:nightly-digest:${runId}`, 3_600_000);
    if (!ownerId) return; // another replica won; skip quietly
    try {
      await this.digests.sendAll();
    } finally {
      await this.locks.release(`locks:nightly-digest:${runId}`, ownerId);
    }
  }
}
```

These Nest fragments require providers such as `DigestService`/`Mailer`, `@nestjs/schedule`, `@nestjs/bullmq`, BullMQ, `cron` and a configured Redis client. Register the scheduler and processor classes as providers. In-process timers do not catch up missed execution automatically, and an interval can overlap its previous asynchronous invocation.
Choose a skip/queue policy explicitly; where the installed `@nestjs/schedule` version supports `waitForCompletion`, it skips overlapping ticks only within that process.

Releasing the daily lease allows a delayed replica to acquire it again. Expiry can also admit a second worker while the first continues. Record a unique durable run ID and make each resulting job/effect duplicate-safe.
Owner-checked release prevents deleting another holder's lease; it cannot prevent an expired holder from writing to an external resource.

#### BullMQ Queues, Retries, Backoff, Rate Limits

```typescript
// queue.module.ts
import { Module } from '@nestjs/common';
import { BullModule } from '@nestjs/bullmq';

@Module({
  imports: [
    BullModule.forRoot({
      connection: { host: process.env.REDIS_HOST, port: 6379 },
      defaultJobOptions: {
        attempts: 5,
        backoff: { type: 'exponential', delay: 1_000, jitter: 0.5 },
        removeOnComplete: 1_000,
        removeOnFail: 5_000,
      },
    }),
    BullModule.registerQueue({ name: 'email' }, { name: 'report' }),
  ],
  exports: [BullModule],
})
export class JobsModule {}
```

```typescript
// email.producer.ts
import { InjectQueue } from '@nestjs/bullmq';
import { Queue } from 'bullmq';

export interface SendEmailJob {
  userId: string;
  template: string;
  idempotencyKey: string;
}

@Injectable()
export class EmailProducer {
  constructor(@InjectQueue('email') private readonly emailQueue: Queue<SendEmailJob>) {}

  async enqueueWelcome(userId: string): Promise<void> {
    await this.emailQueue.add(
      'send-email',
      { userId, template: 'welcome', idempotencyKey: `welcome:${userId}` },
      { priority: 5, delay: 60_000 },
    );
  }

  async enqueueDigestBatch(runId: string, userIds: string[]): Promise<void> {
    // Batch enqueue reduces network round trips; it does not order worker completion.
    await this.emailQueue.addBulk(
      userIds.map((userId) => ({
        name: 'send-email',
        data: { userId, template: 'daily-digest', idempotencyKey: `digest:${runId}:${userId}` },
        opts: { priority: 1 },
      })),
    );
  }
}
```

```typescript
// email.processor.ts — worker with rate limiting
import { Processor, WorkerHost, OnWorkerEvent } from '@nestjs/bullmq';
import { Job } from 'bullmq';
import { Logger } from '@nestjs/common';
import { Mailer } from './mailer';

@Processor('email', {
  limiter: { max: 100, duration: 60_000 }, // max 100 starts/minute across workers on this queue
  concurrency: 10,
})
export class EmailProcessor extends WorkerHost {
  private readonly logger = new Logger(EmailProcessor.name);

  constructor(private readonly mailer: Mailer) {
    super();
  }

  async process(job: Job<SendEmailJob>): Promise<void> {
    this.logger.log(`Processing ${job.name} #${job.id} attempt ${job.attemptsMade + 1}`);
    await this.mailer.sendWithIdempotencyKey(
      job.data.idempotencyKey,   // dedupe at provider side too
      job.data.userId,
      job.data.template,
    );
  }

  @OnWorkerEvent('failed')
  onFailed(job: Job | undefined, err: Error): void {
    // Job may be absent; publish redacted diagnostics under an operator policy.
    this.logger.warn(`job ${job?.id ?? 'unknown'} failed; attempts made ${job?.attemptsMade ?? 'unknown'}`);
  }

  @OnWorkerEvent('completed')
  onCompleted(job: Job): void {
    this.logger.log(`job ${job.id} completed in ${job.finishedOn! - job.processedOn!}ms`);
  }
}
```

#### A Payout Claim Does Not Resolve an Uncertain Bank Transfer

An atomic database transition from `pending` to `processing` prevents two workers from claiming the same row at the same instant. It does not make the remote bank call transactional with that row. If the bank accepts a transfer and the reply is lost, resetting the row to `pending` invites a second transfer.

The `sendWithIdempotencyKey` method above represents a provider contract; many email providers do not expose one. A field in the job payload alone cannot suppress a duplicate. For an external effect, persist an operation identity before the call and pass it to the provider when supported.
Define how the provider reports an existing result. Without duplicate suppression or a reliable lookup, a timeout may require manual reconciliation rather than an automatic new transfer.

| Observed state/outcome | Next action |
| ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| Already `paid` with the stored provider result | Return that result; do not call the bank again |
| A live worker owns `processing` | Let it finish; do not acknowledge the payout as paid |
| Ownership expired, result not known | Look up the persisted operation identity at the provider |
| Provider confirms acceptance | Persist `paid` and its reference before reporting completion |
| Provider confirms rejection with no effect | Apply the documented retry/terminal policy |
| Timeout or ambiguous provider status | Keep `unknown`/reconciling state; preserve the identity and alert after a deadline |

Trace a crash: payout `p7` stores key `payout-p7`, the bank accepts it, then the worker stops before marking `paid`. A later worker queries or resubmits that same key under the provider's documented contract. It records the accepted result instead of submitting `payout-p7-attempt2`.
The queue can now complete without duplicating the transfer.

The database claim also needs an expiry/owner and recovery policy so a stopped worker does not leave work stuck forever. A lease and a durable business-operation identity solve different parts of the problem.

#### Scheduled-Job Observability

```typescript
// jobs.metrics.ts — expose queue health to Prometheus-style scrapes
import { Controller, Get } from '@nestjs/common';
import { Queue } from 'bullmq';
import { InjectQueue } from '@nestjs/bullmq';

@Controller('internal/jobs')
export class JobsMetricsController {
  constructor(@InjectQueue('email') private readonly emailQueue: Queue) {}

  @Get('health')
  async health(): Promise<Record<string, number>> {
    const counts = await this.emailQueue.getJobCounts(
      'waiting', 'active', 'completed', 'failed', 'delayed',
    );
    return counts;
  }
}

// Restrict this route to the internal monitoring network or an authenticated scraper.

// Alert rules worth wiring:
//   waiting > threshold for > 10min   -> producer outpacing workers
//   new terminal failures / rising failure rate -> investigate current failures
//   retained failed count             -> review backlog, not a live failure-rate counter
//   oldest active job age > SLA       -> stuck worker / missing event loop
// Also record duration, attempts and the oldest waiting-job age. Route jobs
// that exhaust attempts through an explicit, replayable dead-letter workflow.
```

### 3. Test the failure boundaries

Use deterministic tests for the decisions this chapter describes, not long real-time sleeps:

| Test | Setup | Assert |
| ------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Schedule registration | Compile the scheduler module with a fake service | The intended expression, time zone and stable schedule name are registered once. |
| Duplicate trigger | Invoke the same run twice with a stable run ID | Only one logical fan-out/effect is committed. |
| Retryable worker failure | Make the dependency fail, then recover | The same job identity retries according to the configured attempts/backoff. |
| Ambiguous external result | Simulate provider acceptance followed by a lost response | Recovery looks up or reuses the same operation identity; it does not create a second transfer. |
| Saturated queue / outage | Pause workers or delay processing | Queue age alerts fire, and any missed calendar run can be reconciled. |

Use a real disposable Redis instance for the queue integration contract: test that registered processors consume jobs, retries become eligible again, and shutdown closes workers. A mocked `Queue.add()` cannot establish those Redis-backed behaviors. The [Nest testing chapter](20.2.4.02-testing.md) covers module boundaries and resource cleanup.

Tune concurrency against downstream capacity, not just worker throughput. JavaScript concurrency overlaps I/O but does not parallelize CPU-bound work; use sandboxed processors or separate worker processes for CPU-heavy jobs. BullMQ's limiter is global across workers on the same queue, which makes it useful for a shared provider quota.
Retain completed and failed jobs by a bounded count or age, and protect queue inspection/metrics endpoints with internal access controls.

## Summary

Timers decide when work becomes eligible; queues persist work and coordinate attempts. Neither guarantees exactly-once effects. Use stable run identities, recoverable enqueueing, duplicate-safe handlers, and queue-age/failure alerts with an explicit replay policy.

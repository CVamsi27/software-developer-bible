# Scheduling & Background Jobs


>
> **Why it matters:** "Why did the nightly report send 12 times?" is the canonical distributed-cron interview story. Seniors are expected to know the cron-vs-queue decision, lock semantics, backoff strategies, and how to make handlers safe to re-run.

## Definition

Two complementary mechanisms:

- **`@nestjs/schedule`** — decorator-driven timers inside the app process: `@Cron` (cron expressions), `@Interval` (fixed period), `@Timeout` (one-shot delay), all manageable at runtime through `SchedulerRegistry` (pause, resume, add, delete).
- **BullMQ** — Redis-backed job queue: producers `add()` named jobs with payloads; workers process them with automatic retries + exponential backoff, per-queue rate limits, priorities, delayed jobs, and repeatable (cron-like) jobs.

The dividing line: **schedule answers "when", queue answers "what happens if it fails"**. Cron triggers are fire-and-forget; queued jobs survive restarts and crashes.

## First Principles

Background work exists because request-scoped time limits can't hold for everything:

1. **"Later" needs infrastructure.** Anything beyond ~30s (→ 20.3.3.03) can't live in a request; a scheduler (@Cron) or queue (BullMQ) moves work out of the request path — the acceptance/completion split, implemented.
2. **Cron semantics are "at least the trigger time," never exact.** Clustered deployments multiply this (every instance fires!) — distributed locks (→ 20.8.03) or leader election decide *who* runs it. The senior default: jobs are idempotent and lock-protected, because both duplication and loss will happen.
3. **Queues trade latency for reliability**: retries with backoff, dead-letter handling, visibility timeouts — each is the at-least-once contract (→ 20.6.2.05) made operational. The handler must assume it will run twice.

## Why Do We Need It?

1. **Time-based work** — nightly digests, token cleanup, cache warming: nothing should run them inside a request.
2. **Durability beyond the process** — an in-memory interval dies with the pod; a BullMQ job persisted in Redis resumes after redeploy.
3. **Load smoothing** — 10k email sends should trickle out at a rate limit, not stampede SMTP.
4. **Retry discipline** — flaky downstreams need exponential backoff with jitter, not a tight loop.
5. **Exactly-once perception** — replicas multiply cron triggers; locks make N pods behave like one scheduler.

## How It Works

### Decision Model: Queue vs Cron vs Both

```text
                 ┌───────────────────────────────┐
                 │ Does it need to SURVIVE a     │
                 │ crash / deploy?               │
                 └──────┬────────────────┬───────┘
                     yes│                        │no
                        ▼                ▼
                  BULLMQ QUEUE      @nestjs/schedule
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
   Triggered by events            Triggered by TIME?
   (user uploads, webhooks)              │
        │                          yes   ▼
        │                     ┌────────────────────────────┐
        │                     │ Multi-replica deployment?  │
        │                     └──────┬───────────────┬─────┘
        │                         yes│               │no
        │                            ▼               ▼
        │                    cron + LOCK       plain @Cron
        │
        ▼
   HYBRID: @Cron (locked) ENQUEUES a BullMQ job
   → one trigger fan-out, N durable worker executions
```

### How Distributed Cron Locking Works

```text
Pod A handler starts:
  SET jobs:nightly-digest:2026-08-25 <podA> NX PX 3600000
        │
        ├── OK    → I am leader for this (job, day). Run. Release/Del.
        └── nil   → another pod holds the lock → skip silently.

Key design points:
 • Key includes a RUN ID (date/bucket) → next run never blocked by
   yesterday's stale lock; stale locks self-expire via PX.
 • Value = pod identity → forensics when debugging double-runs.
 • Release with a Lua check-and-del → only the owner deletes it.
 • Alternative: Redlock for strictness; DB advisory locks
   (PostgreSQL pg_advisory_lock) when Redis is not already present.
```

### BullMQ Execution Flow

```text
Producer (API)                Redis                    Worker(s)
    │                           │                          │
    ├─ add('send-email', data) ►│ LIST: bull:email:wait    │
    │                           │                          │
    │                           │◄──── BRPOPLPUSH ─────────┤
    │                           │ moves to 'active' list   │
    │                           │                          ├─ handler(job)
    │                           │                          │   fail?
    │                           │◄─ retry w/ backoff ──────┤   moved to 'failed',
    │                           │   delayed zset           │   retried until attempts
    │                           │                          │   exhausted → 'failed' set
    │                           │                          │   success?
    │                           │◄─ move to 'completed' ───┤   (+ events for metrics)
```

## Code Examples

### Declarative Scheduling with @nestjs/schedule

```typescript
// reports.scheduler.ts
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression, Interval, Timeout } from '@nestjs/schedule';

@Injectable()
export class ReportsScheduler {
  private readonly logger = new Logger(ReportsScheduler.name);

  constructor(private readonly digests: DigestService) {}

  // Every day 06:00 server-time — single replica or locked (see below)
  @Cron(CronExpression.EVERY_DAY_AT_6AM, { name: 'nightly-digest', timeZone: 'Europe/Berlin' })
  async nightlyDigest(): Promise<void> {
    this.logger.log('nightly digest started');
    await this.digests.sendAll();
  }

  // Every 30s — cheap liveness-sensitive sweeps
  @Interval('stale-session-sweep', 30_000)
  async sweepStaleSessions(): Promise<void> {
    await this.digests.expireSessions();
  }

  // Once, 10s after boot — warm caches after full init
  @Timeout('warm-cache', 10_000)
  async warmCache(): Promise<void> {
    await this.digests.warmCache();
  }
}
```

### Dynamic API: SchedulerRegistry

```typescript
// dynamic-jobs.service.ts — create/manage crons at runtime
import { Injectable, OnModuleDestroy } from '@nestjs/common';
import { SchedulerRegistry } from '@nestjs/schedule';
import { CronJob } from 'cron';

@Injectable()
export class DynamicJobsService implements OnModuleDestroy {
  constructor(private readonly scheduler: SchedulerRegistry) {}

  addTenantCron(tenantId: string, expression: string): void {
    const name = `tenant-${tenantId}-sync`;
    if (this.scheduler.doesExist('cron', name)) {
      this.scheduler.deleteCronJob(name); // replace, don't duplicate
    }
    const job = new CronJob(expression, async () => {
      await this.syncTenant(tenantId);
    });
    this.scheduler.addCronJob(name, job);
    job.start();
  }

  pauseAll(): void {
    for (const name of this.scheduler.getCronJobs().keys()) {
      this.scheduler.getCronJob(name).stop();
    }
  }

  async onModuleDestroy(): Promise<void> {
    // hooks chapter: stop intake first, then release resources
    this.pauseAll();
  }

  private async syncTenant(tenantId: string): Promise<void> {
    /* ... */
  }
}
```

### Distributed Lock So Cron Runs Once

```typescript
// redis-lock.service.ts — owner-safe lock with Lua release
import { Injectable } from '@nestjs/common';
import Redis from 'ioredis';

@Injectable()
export class RedisLockService {
  constructor(private readonly redis: Redis) {}

  private static readonly RELEASE_LUA =
    `if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1]) else return 0 end`;

  async acquire(key: string, ttlMs: number): Promise<string | null> {
    const ownerId = `${process.pid}-${Math.random().toString(36).slice(2, 8)}`;
    const ok = await this.redis.set(key, ownerId, 'PX', ttlMs, 'NX');
    return ok === 'OK' ? ownerId : null;
  }

  async release(key: string, ownerId: string): Promise<void> {
    await this.redis.eval(
      RedisLockService.RELEASE_LUA, 1, key, ownerId,
    );
  }
}
```

```typescript
// locked-digest.scheduler.ts — multi-replica-safe cron
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression } from '@nestjs/schedule';

@Injectable()
export class LockedDigestScheduler {
  private readonly logger = new Logger(LockedDigestScheduler.name);

  constructor(private readonly locks: RedisLockService, private readonly digests: DigestService) {}

  @Cron(CronExpression.EVERY_DAY_AT_6AM)
  async nightlyDigest(): Promise<void> {
    // Run ID = UTC date → each day gets a fresh lock namespace;
    // PX guards against a crashed holder blocking tomorrow's run.
    const runId = new Date().toISOString().slice(0, 10);
    const ownerId = await this.locks.acquire(`locks:nightly-digest:${runId}`, 3_600_000);
    if (!ownerId) return; // another replica won; skip quietly
    try {
      await this.digests.sendAll();
    } finally {
      await this.locks.release(`locks:nightly-digest:${runId}`, ownerId);
    }
  }
}
```

### BullMQ Queues, Retries, Backoff, Rate Limits

```typescript
// queue.module.ts
import { Module } from '@nestjs/common';
import { BullModule } from '@nestjs/bullmq';

@Module({
  imports: [
    BullModule.forRoot({
      connection: { host: process.env.REDIS_HOST, port: 6379 },
      defaultJobOptions: {
        attempts: 5,
        backoff: { type: 'exponential', delay: 1_000 },
        removeOnComplete: 1_000,
        removeOnFail: 5_000,
      },
    }),
    BullModule.registerQueue({ name: 'email' }, { name: 'report' }),
  ],
  exports: [BullModule],
})
export class JobsModule {}
```

```typescript
// email.producer.ts
import { InjectQueue } from '@nestjs/bullmq';
import { Queue } from 'bullmq';

export interface SendEmailJob {
  userId: string;
  template: string;
  idempotencyKey: string;
}

@Injectable()
export class EmailProducer {
  constructor(@InjectQueue('email') private readonly emailQueue: Queue<SendEmailJob>) {}

  async enqueueWelcome(userId: string): Promise<void> {
    await this.emailQueue.add(
      'send-email',
      { userId, template: 'welcome', idempotencyKey: `welcome:${userId}` },
      { priority: 5, delay: 60_000 },
    );
  }

  async enqueueDigestBatch(userIds: string[]): Promise<void> {
    // Bulk path: one round-trip, respects group ordering
    await this.emailQueue.addBulk(
      userIds.map((userId) => ({
        name: 'send-email',
        data: { userId, template: 'daily-digest', idempotencyKey: `digest:${userId}` },
        opts: { priority: 1 },
      })),
    );
  }
}
```

```typescript
// email.processor.ts — worker with rate limiting
import { Processor, WorkerHost, OnWorkerEvent } from '@nestjs/bullmq';
import { Job } from 'bullmq';
import { Logger } from '@nestjs/common';
import { Mailer } from './mailer';

@Processor('email', {
  limiter: { max: 100, duration: 60_000 }, // max 100 emails/minute per worker
  concurrency: 10,
})
export class EmailProcessor extends WorkerHost {
  private readonly logger = new Logger(EmailProcessor.name);

  constructor(private readonly mailer: Mailer) {
    super();
  }

  async process(job: Job<SendEmailJob>): Promise<void> {
    this.logger.log(`Processing ${job.name} #${job.id} attempt ${job.attemptsMade + 1}`);
    await this.mailer.sendWithIdempotencyKey(
      job.data.idempotencyKey,   // dedupe at provider side too
      job.data.userId,
      job.data.template,
    );
  }

  @OnWorkerEvent('failed')
  onFailed(job: Job, err: Error): void {
    this.logger.warn(`job ${job.id} failed (${err.message}); retries left ${job.attemptsMade}`);
  }

  @OnWorkerEvent('completed')
  onCompleted(job: Job): void {
    this.logger.log(`job ${job.id} completed in ${job.finishedOn! - job.processedOn!}ms`);
  }
}
```

### Idempotent Job Handlers

```typescript
// idempotent.handler.ts — at-least-once delivery handled correctly
import { Injectable } from '@nestjs/common';

@Injectable()
export class PayoutJobHandler {
  constructor(private readonly db: DatabaseService, private readonly bank: BankClient) {}

  async handle(job: { data: { payoutId: string } }): Promise<void> {
    const { payoutId } = job.data;

    // Claim pattern: atomic state transition is the idempotency gate.
    // Only ONE execution can flip pending -> processing.
    const claimed = await this.db.query(
      `UPDATE payouts SET status = 'processing'
         WHERE id = $1 AND status = 'pending'
         RETURNING amount, iban`,
      [payoutId],
    );
    if (claimed.rowCount === 0) {
      return; // already processed or in-flight by another worker: no-op
    }

    try {
      await this.bank.transfer(/* ... */);
      await this.db.query(`UPDATE payouts SET status = 'paid' WHERE id = $1`, [payoutId]);
    } catch (err) {
      // Revert claim so the retry can proceed
      await this.db.query(`UPDATE payouts SET status = 'pending' WHERE id = $1`, [payoutId]);
      throw err; // let BullMQ schedule the backoff retry
    }
  }
}
```

### Scheduled-Job Observability

```typescript
// jobs.metrics.ts — expose queue health to Prometheus-style scrapes
import { Controller, Get } from '@nestjs/common';
import { Queue } from 'bullmq';
import { InjectQueue } from '@nestjs/bullmq';

@Controller('internal/jobs')
export class JobsMetricsController {
  constructor(@InjectQueue('email') private readonly emailQueue: Queue) {}

  @Get('health')
  async health(): Promise<Record<string, number>> {
    const counts = await this.emailQueue.getJobCounts(
      'waiting', 'active', 'completed', 'failed', 'delayed',
    );
    return counts;
  }
}

// Alert rules worth wiring:
//   waiting > threshold for > 10min   -> producer outpacing workers
//   failed > 0 sustained              -> poison messages or outage
//   oldest active job age > SLA       -> stuck worker / missing event loop
// Also log job.duration, job.attemptsMade, and dead-letter anything
// that exhausts attempts (BullMQ event 'failed' + maxRetriesReached).
```

## Real-World Use Cases

1. **Nightly billing across 20 replicas** — cron enqueues one BullMQ job per account behind a daily lock; workers process with concurrency 50 and exponential backoff against a flaky payment API.
2. **Email marketing sends** — producer `addBulk`s 100k jobs; queue limiter caps at provider-compliant rates; `idempotencyKey` prevents double sends on worker restart mid-job.
3. **Per-tenant sync schedules** — `SchedulerRegistry.addCronJob` creates tenant-specific expressions at runtime; deleting a tenant removes its cron without redeploy.
4. **Webhook deliveries with retries** — recipient timeouts get 5 attempts with jittered exponential backoff; exhausted jobs land in a dead-letter set surfaced on the observability dashboard.
5. **Cache warming after deploys** — `@Timeout` warms hot keys 10 seconds post-bootstrap, while a locked `@Cron(EVERY_HOUR)` refreshes them continuously.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Plain `@Cron` in a multi-replica deployment | Every pod fires the job. Add a distributed lock keyed by run ID, or elect a leader. |
| Non-idempotent handlers under at-least-once delivery | Gate side effects with an atomic state claim (`status = 'pending'` transition) or idempotency keys. |
| Fixed-delay retries hammering a struggling dependency | Use exponential backoff with jitter; cap attempts and dead-letter the rest. |
| Lock TTL shorter than job duration | Second runner acquires the expired lock and duplicates work. TTL ≥ worst-case runtime, or renew. |
| Forgetting `ScheduleModule.forRoot()` | Decorators compile fine but nothing schedules; silent no-op. |
| Testing schedulers with real sleeps | Trigger handlers directly, or use `SchedulerRegistry.getCronJob(...)` to control timing deterministically. |
| Unbounded `removeOnComplete` growth | Set retention counts/max age, otherwise Redis memory balloons. |

## Best Practices

1. **Default to the hybrid pattern** — locked cron as trigger, BullMQ as execution engine; you get exactly-one fan-out and durable processing.
2. **Name every scheduled task** (`{ name: '...' }`) — required for `SchedulerRegistry` management and for meaningful logs/metrics.
3. **Set explicit `timeZone`** on crons — server TZ drift breaks business-day logic.
4. **Make every job handler idempotent even if you think it cannot double-run** — at-least-once is a property of the transport, not your intentions.
5. **Include a run ID / idempotency key in payloads** — retries become no-ops instead of duplicates.
6. **Expose queue depth + failure counters** — scheduling failures are invisible unless you measure them.
7. **Keep cron expressions in config, not code** — ops changes schedules without releases.

## Performance Considerations

- **Every cron tick wakes the whole event loop** — prefer fewer, batched intervals over many high-frequency timers; `.unref()` non-critical ones.
- **BullMQ polling vs blocking** — workers use blocking reads (BRPOPLPUSH); do not implement custom polling loops that hammer Redis.
- **Concurrency tuning is per-worker** — CPU-bound handlers should set `concurrency` near vCPU count; I/O-bound can go much higher.
- **Rate limits are per-worker-group** — the `limiter` option applies across the worker group sharing the queue, which is usually what you want for provider quotas.
- **Redis latency bounds throughput** — colocate Redis with workers or accept added p50 per job; monitor `event_loop_lag` on worker pods too.

## Summary

- `@nestjs/schedule` covers in-process triggers (declarative decorators + dynamic `SchedulerRegistry`); BullMQ covers durable, retriable, rate-limited background work in Redis.
- Multi-replica cron needs a distributed lock keyed by run ID with owner-checked release — otherwise N pods means N executions.
- Choose cron for "when", queues for "what if it fails", and both together for scheduled fan-out of resilient work.
- Handlers must be idempotent: use atomic state claims or idempotency keys because delivery is at-least-once.
- Observability closes the loop: queue counts, failure events, durations, and dead-letter handling turn silent breakage into alerts.

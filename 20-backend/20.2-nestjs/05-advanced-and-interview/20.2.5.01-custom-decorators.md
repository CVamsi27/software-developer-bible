# NestJS Custom Decorators


---

## Definition

A **decorator** attaches behavior or metadata to a class, method, or parameter when the class is defined. Nest reads that information later. For a custom parameter decorator, the decorator is registered once, but its extraction callback runs for each request:

> **Textbook Definition:** A NestJS custom decorator attaches metadata or registers argument extraction behavior on a declaration. Framework components interpret that registration during execution; metadata alone does not enforce an access rule.

```typescript
function Roles(...roles: string[]) {
  return SetMetadata('roles', roles);   // writes metadata onto the handler
}
@Roles('admin')        // ← design-time: stores metadata
@Get('/users')
list() {}
```
```text
                where it attaches        what it is for
class       @Controller/@Injectable      registration in the DI container
method      @Get/@Roles/@UseGuards       route + metadata for the request pipeline
parameter   @Body/@Param/@CurrentUser    which argument the framework supplies
property    @Inject/@Column              injection / ORM mapping
```

The definitional point is the **split between declaration and execution**, which explains the whole runtime model:

1. **Decorators attach data; the framework acts on it later.** `@Roles('admin')` stores metadata; a `Reflector`-based `RolesGuard` reads it per request. This is why a decorator alone can never enforce anything — enforcement requires a guard, interceptor, or pipe that consumes the metadata.
2. **Custom parameter decorators are the idiomatic composition tool** — `@CurrentUser()` replaces repeating `@Req() req` and `req.user` across controllers, and it is the NestJS equivalent of an extractor (in Nest's own words, "what the handler needs, not what the framework passes").
3. **Execution order is fixed and worth memorising** — middleware → guards → interceptors (before) → pipes → handler → interceptors (after) → exception filters. Decorator bugs are almost always a choice made in the wrong stage (e.g. authentication in an interceptor instead of a guard).

Because decorators are `experimentalDecorators` TypeScript (or Stage 3 with different semantics), the metadata is only available if `emitDecoratorMetadata`/`reflect-metadata` is enabled — the reason Nest requires it in `tsconfig` and a `reflect-metadata` import at bootstrap.

## First Principles

1. **Repeated checks can be forgotten.** A decorator can record a required role on a handler. A registered guard reads that metadata and enforces it for each request. This centralizes the check while keeping the requirement visible at the handler; metadata alone provides no enforcement.
2. **Repeated request extraction couples handlers to HTTP details.** `createParamDecorator` puts extraction in one place and passes the result as a handler argument. For example, handlers can receive a user rather than repeatedly reading `req.user`. This reduces duplication and makes the handler easier to test; direct request access does not make testing impossible.
3. **Declaration and request execution happen at different times.** Decorator registration cannot read a future request. A custom parameter decorator's callback can read the current request when Nest invokes it. Keep access checks in guards or interceptors and business logic in services so each responsibility can be tested separately.

## Parameter Decorators

NestJS uses decorators for routing, validation, and dependency injection. A custom parameter decorator extracts request data and passes it to a controller method. For example, `@CurrentUser()` reads the user already verified and attached by the authentication layer; it does not verify a JWT itself. `@ClinicId()` can extract a tenant ID, and `@Pagination()` can extract a page or cursor from query parameters. These callbacks avoid repeating extraction in every controller method.


```typescript
// Current user decorator
import { createParamDecorator, ExecutionContext } from '@nestjs/common';

export const CurrentUser = createParamDecorator(
  (data: string, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();
    const user = request.user;
    return data ? user?.[data] : user;
  }
);

// Usage
@Controller('appointments')
export class AppointmentController {
  @Get()
  findAll(@CurrentUser() user: User) {
    return this.appointmentService.findAll(user.clinicId);
  }

  @Get('mine')
  findMine(@CurrentUser('id') userId: string) {
    return this.appointmentService.findByUser(userId);
  }
}
```

```typescript
// Clinic ID decorator (extracts from JWT)
export const ClinicId = createParamDecorator(
  (data: unknown, ctx: ExecutionContext): string => {
    const request = ctx.switchToHttp().getRequest();
    return request.user?.clinicId;
  }
);

// Usage
@Get()
findAll(@ClinicId() clinicId: string) {
  return this.service.findAll(clinicId);
}
```

```typescript
// Pagination decorator
export const Pagination = createParamDecorator(
  (data: unknown, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();
    const query = request.query;
    return {
      page: parseInt(query.page) || 1,
      limit: Math.min(parseInt(query.limit) || 20, 100),
      cursor: query.cursor || null
    };
  }
);

// Usage
@Get()
findAll(@Pagination() pagination: PaginationDto) {
  return this.service.findAll(pagination);
}
```

## Method Decorators

```typescript
// Rate limit decorator
import { SetMetadata } from '@nestjs/common';

export const RATE_LIMIT_KEY = 'rateLimit';
export const RateLimit = (limit: number, windowMs: number) =>
  SetMetadata(RATE_LIMIT_KEY, { limit, windowMs });

// Usage
@RateLimit(10, 60000) // 10 requests per minute
@Post()
create(@Body() data: CreateAppointmentDto) {
  return this.service.create(data);
}
```

```typescript
// Cache decorator
export const CACHE_KEY = 'cache';
export const Cache = (ttl: number) =>
  SetMetadata(CACHE_KEY, { ttl });

// Usage
@Cache(300) // 5 minutes
@Get(':id')
findOne(@Param('id') id: string) {
  return this.service.findOne(id);
}
```

```typescript
// Audit log decorator
export const AUDIT_KEY = 'audit';
export const Audit = (action: string, resource: string) =>
  SetMetadata(AUDIT_KEY, { action, resource });

// Usage
@Audit('create', 'appointment')
@Post()
create(@Body() data: CreateAppointmentDto, @CurrentUser() user: User) {
  return this.service.create(data, user);
}
```

## Class Decorators

```typescript
// ApiTags decorator (already exists in @nestjs/swagger)
// Custom version with versioning
export const ApiResource = (resource: string) => {
  return (target: Function) => {
    SetMetadata('resource', resource)(target);
  };
};

// Usage
@ApiResource('appointments')
@Controller('appointments')
export class AppointmentController {}
```

## Custom Decorator Composition

```typescript
// Compose multiple decorators
export const AuthenticatedEndpoint = () => {
  return applyDecorators(
    UseGuards(AuthGuard, RolesGuard),
    Roles('clinician', 'receptionist'),
    ApiBearerAuth(),
    ApiOperation({ summary: 'Get appointments' })
  );
};

// Usage
@AuthenticatedEndpoint()
@Get()
findAll(@ClinicId() clinicId: string) {
  return this.service.findAll(clinicId);
}
```

## Interceptor with Decorator

```typescript
// Transform response decorator
export const TransformResponse = (transformer: (data: any) => any) => {
  return SetMetadata('transformer', transformer);
};

// Interceptor that uses the metadata
@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler) {
    const transformer = this.reflector.get('transformer', context.getHandler());

    if (!transformer) {
      return next.handle();
    }

    return next.handle().pipe(
      map(data => transformer(data))
    );
  }
}

// Usage
@TransformResponse(data => ({
  success: true,
  data,
  timestamp: new Date()
}))
@Get()
findAll() {
  return this.service.findAll();
}
```

## Interview Tips
- Know param decorators (@CurrentUser, @ClinicId, @Pagination)
- Know method decorators (@RateLimit, @Cache, @Audit)
- Explain decorator composition with applyDecorators
- Know how to create custom decorators with createParamDecorator
---
## Summary

1. **Decorators compose metadata via Reflect** — `SetMetadata` + `Reflector` is the built-in pattern
2. **Param decorators (`createParamDecorator`) extract per-request data** — the typed alternative to reaching into `req`
3. **Composite decorators** — combine route + guards + interceptors into one declarative unit
4. **Metadata keys need namespaces** — collisions across libraries are a real bug class
5. **Test decorators in isolation** — they're functions; the reflection behavior is unit-testable

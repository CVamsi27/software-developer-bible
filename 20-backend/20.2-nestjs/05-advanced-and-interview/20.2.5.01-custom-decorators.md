# NestJS Custom Decorators

One declaration, two execution times. Suppose several controllers need the authenticated clinic ID.

## Definition

A Nest decorator records route metadata or declares how a handler argument is extracted. Nest reads that declaration later; a custom parameter decorator's extraction callback runs for each request.

> **Textbook Definition:** A NestJS custom decorator attaches metadata or registers argument extraction on a declaration. A framework component must consume that metadata during execution; the declaration alone does not enforce policy.

## First Principles

Without decorators, handlers repeatedly read transport objects or repeat policy declarations. A decorator packages that contract, but it runs while the class is defined—before any request has a user, tenant or query string. Nest therefore needs a second step: invoke an extraction callback for the current request or let a registered component consume the saved metadata.
This timing explains why extraction is not authentication and metadata is not authorization.

## 1. One declaration, two execution times

Suppose several controllers need the authenticated clinic ID. Reading `req.user.clinicId` in every method repeats transport plumbing, while adding `@Roles('admin')` may look like security even though it only records a requirement. These are two different decorator jobs: extract a value after authentication, or describe a policy for a registered guard to enforce.

```typescript
import { createParamDecorator, ExecutionContext, UnauthorizedException } from '@nestjs/common';

interface Principal { id: string; clinicId: string }

export const CurrentUser = createParamDecorator(
  (field: keyof Principal | undefined, context: ExecutionContext) => {
    const principal = context.switchToHttp().getRequest().user as Principal | undefined;
    if (!principal) throw new UnauthorizedException();
    return field ? principal[field] : principal;
  },
);

@Get('mine')
findMine(@CurrentUser('id') userId: string) {
  return this.appointments.findForUser(userId);
}
```

The authentication guard must run first and attach the verified principal. `@CurrentUser()` extracts it; it does not validate a credential, authorize a clinic or check that a resource belongs to that clinic. A clinic ID should reach the service only after the caller is allowed to act in that tenant. Custom parameter decorators also do not automatically pass through ordinary DTO validation; use an explicit pipe or opt in to validating custom arguments.
For pagination, prefer the parsing and bounds already established by the [Pipes chapter](../02-request-lifecycle/20.2.2.03-pipes.md) over embedding a second numeric parser in `@Pagination()`.

## 2. Metadata needs a consumer

Nest's `SetMetadata` stores values on a method or class. A guard can read those values with `Reflector`; until that guard is registered and runs, the metadata changes no request behavior.

```typescript
import { SetMetadata } from '@nestjs/common';

export const ROLES_KEY = 'appointments:roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

@Roles('clinician', 'receptionist')
@Get()
findAll() { /* handler */ }
```

A role guard owns the check: it reads handler/class metadata under the exact key used by the decorator, combines it with the verified principal, then decides whether execution may proceed. The [guard chapter](../02-request-lifecycle/20.2.2.02-guards.md) uses one shared Symbol for that contract; this fragment uses the string `ROLES_KEY`, so adapt both its writer and its reader together. Equal descriptions do not make different Symbols equal. `@Cache(ttl)`, `@RateLimit(limit)` and `@Audit(action)` are application conventions, not built-in policies: respectively, a cache interceptor, throttling guard and audit owner must interpret them. Keep units and precedence explicit.
An audit marker does not make a database change and its event durable.

## 3. Compose declarations when they always belong together

`applyDecorators` packages a repeated set of Nest decorators. It improves consistency only when every composed consumer is registered and the security/documentation metadata describe the same endpoint.

Assume `AuthGuard` and `RolesGuard` are application-defined. Here authentication attaches the verified principal to `req.user` for `CurrentUser`, and the role guard must read that same principal and this fragment's `ROLES_KEY`. The guard chapter's separate fixture uses `req.principal` and a Symbol key; changing only the decorators does not adapt those consumers.

```typescript
import { applyDecorators, SetMetadata, UseGuards } from '@nestjs/common';

export const AuthenticatedClinician = () => applyDecorators(
  UseGuards(AuthGuard, RolesGuard),
  SetMetadata(ROLES_KEY, ['clinician']),
);

@AuthenticatedClinician()
@Get()
findAll(@CurrentUser('clinicId') clinicId: string) {
  return this.appointments.findForClinic(clinicId);
}
```

Add OpenAPI decorators to the composition only when its documented security scheme matches the runtime guard. If a route has a different policy, use the individual decorators so the exception stays visible. Class decorators follow the same rule: attaching resource metadata does not register a controller, alter Swagger output or create a provider unless the relevant Nest component consumes it.

Nest's examples use TypeScript's legacy `experimentalDecorators` semantics. `emitDecoratorMetadata` supplies design-type metadata for some implicit injection; it does not create custom `SetMetadata` values. TypeScript's newer proposal-based decorators have a different contract and are not drop-in replacements for Nest's current decorator APIs.

## Summary

Use parameter decorators to centralize extraction after the correct authentication boundary. Use method or class metadata to declare policy, then verify the registered guard, interceptor or other consumer that gives it behavior. Composition reduces repeated declarations; it does not replace validation, authorization or durable operations.

## Beginner Level (Questions 1-10)

### Q1: What is NestJS and why would you use it?

**Answer:** NestJS is a progressive Node.js framework for building efficient, scalable server-side applications. It uses TypeScript and combines OOP (Object-Oriented Programming), FP (Functional Programming), and FRP (Functional Reactive Programming).

**Why use it:**

- Built-in dependency injection
- Modular architecture
- TypeScript-first
- Excellent testing support
- Microservices ready
- Wide ecosystem (TypeORM, GraphQL, WebSockets)
- Strong community and documentation

### Q2: What are the main components of a NestJS application?

**Answer:**

- **Modules**: Organize code into related capabilities
- **Controllers**: Handle HTTP requests and define routes
- **Providers/Services**: Business logic and data access
- **Middleware**: Execute logic before route handlers
- **Guards**: Authorization and access control
- **Interceptors**: Cross-cutting concerns (logging, caching)
- **Pipes**: Data validation and transformation
- **Exception Filters**: Error handling

### Q3: What is the difference between NestJS and Express?

**Answer:**

| Feature | NestJS | Express |
| ------------- | -------------------- | ----------------------------- |
| Architecture | Opinionated, modular | Unopinionated, minimal |
| TypeScript | First-class support | Optional |
| DI | Built-in | Manual |
| Testing | Integrated | Manual setup |
| Structure | Enforced patterns | Flexible |
| Microservices | Built-in support | Requires additional libraries |

NestJS uses Express (or Fastify) under the hood but adds structure and features.

The 'why' is boundary enforcement at scale: Express hands you the HTTP loop and leaves architecture as convention, so structure decays as the team grows. Nest bakes the decisions in — a DI container makes every dependency explicit and mockable in tests, modules make boundaries real (you cannot import what a module doesn't export), and decorators give pipelines, guards, and interceptors a uniform dispatch model. The cost is ceremony and framework lock-in — which is exactly the trade a large codebase wants.

### Q4: What is a module in NestJS?

**Answer:** A module is a class decorated with `@Module()` that organizes closely related set of capabilities. Every NestJS app has at least one module (root module).

Properties:

- `providers`: Services available within the module
- `controllers`: Request handlers
- `imports`: Other modules whose exports are needed
- `exports`: Providers available to importing modules

### Q5: What is dependency injection in NestJS?

**Answer:** DI is a design pattern where NestJS's IoC container manages and injects dependencies into components through constructor parameters.


The mechanism that matters: the container resolves the *entire dependency graph once at startup* — module imports are compiled into providers, and each constructor parameter is matched against registered tokens — so a missing or circular dependency fails at boot, not mid-request. That fail-fast property is the practical win; testability is the famous one (swap any provider via a test module). The follow-ups interviewers probe: circular imports need `forwardRef` on *both* sides (a smell worth fixing via module extraction), and non-class dependencies require an injection token, which is Q6's territory.
```typescript
@Injectable()
export class UserService {
  constructor(
    private readonly userRepo: UserRepository, // Injected
    private readonly cacheService: CacheService, // Injected
  ) {}
}

```

Benefits: Loose coupling, testability, reusability.

### Q6: What is the difference between `@Injectable()` and `@Inject()`?

**Answer:**

- `@Injectable()`: Marks a class as a provider that can be managed by DI container
- `@Inject()`: Used to inject dependencies using custom tokens when type alone isn't sufficient


The split is demand-side versus supply-side: `@Injectable()` marks a *class* as something the container may instantiate and manage, while `@Inject(token)` is how a consumer *asks for* a specific dependency when the token is not the class itself — a string config key, a symbol, a connection object. In the common case `@Inject` is implicit: a typed constructor parameter resolves by its class token. Explicit `@Inject` appears exactly where classes cannot express the dependency — interfaces (erased at runtime), primitives, or a value chosen by a factory. Saying this order — implicit by default, explicit by token — is the answer.
```typescript
@Injectable() // Class is injectable
export class UserService {}

constructor(
  @Inject('CUSTOM_TOKEN') // Custom token injection
  private custom: any,
) {}

```

### Q7: What are the different HTTP method decorators in NestJS?

**Answer:**

- `@Get()` - GET requests
- `@Post()` - POST requests
- `@Put()` - PUT requests (full update)
- `@Patch()` - PATCH requests (partial update)
- `@Delete()` - DELETE requests
- `@Options()` - OPTIONS requests
- `@Head()` - HEAD requests
- `@All()` - All HTTP methods

### Q8: How do you validate request data in NestJS?

**Answer:** Use DTOs with class-validator and the global ValidationPipe:


The pipe runs once, globally, before the handler — so validation is a boundary property, not handler discipline. The options carry the security weight: `whitelist: true` strips properties the DTO never declared (closing mass-assignment — an attacker-sent `role: admin` dies here), `forbidNonWhitelisted` goes further and rejects instead of stripping, and `transform: true` converts payloads into DTO instances with primitive coercion. Two follow-ups: nested objects validate only if the DTO's properties are themselves decorated classes (`@ValidateNested` with `@Type` from class-transformer), and the error response shape should be mapped by an exception filter so clients never see class-validator internals.
```typescript
// DTO
class CreateUserDto {
  @IsString()
  name: string;

  @IsEmail()
  email: string;
}

// Global validation
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,
  transform: true,
}));

// Controller
@Post()
create(@Body() dto: CreateUserDto) {
  return this.userService.create(dto);
}

```

### Q9: What is the purpose of `@Controller()` decorator?

**Answer:** `@Controller()` marks a class as a controller that handles HTTP requests. It accepts an optional route prefix:


The decorator does two things worth naming: it registers the class as a controller in the module and it prefixes routes from the path argument — but its deeper role is as *metadata host* for the framework: route decorators, guards, interceptors, and pipes attached to it or its methods are read by reflection at bootstrap. The design consequence interviewers want: controllers stay thin — parse the request, delegate to a service, shape the response. Business logic in controllers cannot be reused by other transports (microservice handlers, WebSocket gateways), which is exactly where it tends to get duplicated.
```typescript
@Controller('users') // All routes start with /users
export class UserController {
  @Get() // GET /users
  findAll() {}

  @Get(':id') // GET /users/:id
  findOne(@Param('id') id: string) {}
}

```

### Q10: How do you run a NestJS application?

**Answer:**


The bootstrap line hides the real work: `NestFactory.create` compiles the module graph, resolves every provider's dependencies in order, and runs initializers — so anything wrong in wiring fails here, before the server accepts a request. `app.listen()` then binds the transport. The follow-ups worth offering: global pipes/guards/filters registered on the app instance apply to every route; `enableShutdownHooks()` is what makes SIGTERM run lifecycle shutdown (Q30's graceful-deploy story); and for microservice transports it is `createMicroservice` with a hybrid app when HTTP and messaging share a process.
```bash
# Development
npm run start:dev

# Production
npm run build
npm run start:prod

# With debugging
npm run start:debug

```

The entry point is `main.ts`:

```typescript
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(3000);
}
bootstrap();

```

## Intermediate Level (Questions 11-20)

### Q11: What is middleware and how does it differ from guards?

**Answer:**

- **Middleware**: Executes before routing, handles cross-cutting concerns (logging, CORS)
- **Guard**: Executes after routing, handles authorization


The distinction is *what each layer knows*: middleware runs before route matching in the Express sense, so it sees the request but not the handler — right for CORS, parsing, request IDs; guards run *after* route matching with access to the execution context, so they can read handler and class metadata via `Reflector` — which is why authorization (`@Roles`) belongs in guards and not middleware. The lifecycle order completes the answer: middleware → guards → interceptors (pre) → pipes → handler → interceptors (post) → exception filters. Choosing by position-in-that-chain, not by preference, is the senior habit.
```text
Request → Middleware → Guard → Interceptor → Pipe → Controller

```

Middleware:

```typescript
@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    console.log('Request...');
    next();
  }
}

```

### Q12: What is the difference between `@Put()` and `@Patch()`?

**Answer:**

- `@Put()`: Full replacement of the resource
- `@Patch()`: Partial update of specific fields


The semantic difference drives real decisions: PUT replaces the resource — the request body should carry the complete new state, and missing fields mean *absent*; PATCH applies a partial change, and only the provided fields move. That maps directly onto DTO design: PUT uses the full DTO, PATCH a `PartialType(DTO)` — and validation subtleties follow (PATCH must not require fields PUT requires). Idempotency is the classic probe: PUT is naturally idempotent (same body, same result), PATCH may not be (an increment operator is not). The HTTP-purist edge — PUT to a collection URL creates at a known path — rarely survives contact with real APIs, but naming it shows the spec was read.
```typescript
@Put(':id')
replace(@Body() dto: FullUserDto) {
  // Replaces entire user
}

@Patch(':id')
update(@Body() dto: PartialUserDto) {
  // Updates only provided fields
}

```

### Q13: What is a DTO and why is it important?

**Answer:** DTO (Data Transfer Object) defines the shape of data for requests/responses. It enables:

- Input validation
- Type safety
- API documentation (Swagger)
- Data transformation


Three jobs at once, and naming all three is the point: the DTO is the *validation contract* (class-validator decorators), the *documentation contract* (`@ApiProperty` feeds Swagger), and the *type contract* (a class, so the type survives at runtime — interfaces do not, which is why DTOs are classes in NestJS). It also draws the security line: only declared and whitelisted properties enter the domain, so the DTO is the attack surface limiter. The follow-up: reusing domain entities as request bodies couples your wire format to your database schema and leaks fields — the DTO exists precisely to keep those two evolvable separately.
```typescript
export class CreateUserDto {
  @IsString()
  @MinLength(2)
  name: string;

  @IsEmail()
  email: string;
}

```

### Q14: How do you implement authentication in NestJS?

**Answer:**

1. Use `@nestjs/jwt` for JWT tokens

2. Create an AuthGuard

3. Apply guard to protected routes


The architecture that scales: a passport strategy verifies the credential and attaches the user, a guard enforces presence (global by default via `APP_GUARD`), and a `@Public()` decorator opts public routes out by setting metadata the guard checks — fail-closed, so a forgotten guard is secure rather than exposed. Token verification lives in the strategy (signature, expiry, issuer), never re-implemented in handlers. The follow-ups: authorization is a *separate* guard reading role metadata (Q11's distinction), and refresh-token or session revocation strategy determines whether JWT expiry alone is acceptable — stateless tokens cannot be un-issued.
```typescript
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {}

@Controller('users')
@UseGuards(JwtAuthGuard)
export class UserController {
  @Get('profile')
  getProfile(@Request() req) {
    return req.user;
  }
}

```

### Q15: What is the difference between a Guard and an Interceptor?

**Answer:**

| Feature | Guard | Interceptor |
| --------------------- | -------------- | ---------------------- |
| Purpose | Authorization | Cross-cutting concerns |
| Executes | Before handler | Before/after handler |
| Can modify response | No | Yes |
| Has access to handler | No | Yes |
| Can be async | Yes | Yes |

The pipeline position is the definition: guards run first and answer 'may this request proceed' — they see auth state but never the handler or response. Interceptors wrap the handler entirely (before and after, around the RxJS response stream) for caching, transformation, logging, timeout. The classic bug this ordering prevents: putting authorization in an interceptor, where the handler may already have executed work before the check lands. Guards decide; interceptors decorate.

### Q16: How do you handle errors in NestJS?

**Answer:**

1. Throw HTTP exceptions:


The pattern is exceptions as control flow plus a filter as the formatter: services throw `NotFoundException`/`ConflictException` (or custom `HttpException` subclasses), and exception filters convert anything thrown into one response shape — error codes, correlation IDs, no stack traces. The global catch-all filter is the security boundary here: an unhandled error leaking a stack trace or SQL fragment is an information-disclosure bug. The follow-up: filters do not replace logging — log at the throw site or in a logging interceptor, because the filter deliberately *sanitizes* what reaches the client, and only the server side holds the truth.
```typescript
throw new NotFoundException('User not found');

```

2. Use exception filters:

```typescript
@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse();
    response.status(exception.getStatus()).json({
      statusCode: exception.getStatus(),
      message: exception.message,
    });
  }
}

```

### Q17: What is the difference between `useClass`, `useFactory`, `useValue`, and `useExisting`?

**Answer:**


The three answer three different construction problems: `useValue` supplies a static instance (tests, defaults); `useClass` substitutes the token's implementation with another class (a fake mailer in dev, or aliasing one token to another); `useFactory` builds the value at startup with injected dependencies — the only option for async clients (database connections, SDK clients awaiting config). The factory's `inject` array is the detail interviewers check: it declares what the factory itself needs. Choosing by question — *what* to provide (value), *which class* (class), *how to build* (factory) — beats memorizing syntax.
```typescript
// useClass: Instantiate a class
{ provide: 'SERVICE', useClass: MyService }

// useFactory: Use factory function
{ provide: 'SERVICE', useFactory: (config) => new MyService(config), inject: [Config] }

// useValue: Use static value
{ provide: 'CONFIG', useValue: { host: 'localhost' } }

// useExisting: Alias to existing provider
{ provide: 'Alias', useExisting: MyService }

```

### Q18: What is the purpose of `@nestjs/config`?

**Answer:** It provides Type-safe configuration management:


The value is not reading env vars — it is making configuration *injected, validated, and typed*: a Joi (or Zod) schema validates the environment at boot so a missing `DATABASE_URL` fails startup instead of failing at first connection; namespaced `registerAs` modules let features import exactly their config; and `ConfigService` is mockable in tests like any provider. Scattering `process.env.X` across the codebase defeats all three — no validation point, no type, no test seam. The follow-up: secrets still belong in a secrets manager with rotation; env vars are the delivery mechanism, not the storage.
```typescript
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: '.env',
    }),
  ],
})
export class AppModule {}

// Usage
@Injectable()
export class AppService {
  constructor(private config: ConfigService) {}

  getDbHost() {
    return this.config.get<string>('DB_HOST');
  }
}

```

### Q19: How do you test a NestJS service?

**Answer:**


The trick the framework plays: `Test.createTestingModule` compiles a *real* DI container for the unit under test — so you override exactly one provider (`{ provide: UserRepository, useValue: fakeRepo }`) and the service constructor is satisfied exactly as in production. That is why NestJS tests read differently from hand-rolled mock injection: the graph, not the test, does the wiring. The follow-ups: `overrideProvider` beats manual constructor mocking because it survives refactors; e2e tests bootstrap the full module with supertest against the HTTP layer; and unit tests should not import database modules — that is the integration suite's job.
```typescript
describe('UserService', () => {
  let service: UserService;
  let mockRepo: Partial<UserRepository>;

  beforeEach(async () => {
    mockRepo = { findAll: jest.fn().mockResolvedValue([]) };

    const module = await Test.createTestingModule({
      providers: [
        UserService,
        { provide: UserRepository, useValue: mockRepo },
      ],
    }).compile();

    service = module.get<UserService>(UserService);
  });

  it('should return empty array', async () => {
    expect(await service.findAll()).toEqual([]);
  });
});

```

### Q20: What is Swagger and how do you integrate it?

**Answer:** Swagger provides API documentation:


The integration is decorator-driven because NestJS already collects the metadata: DTO classes with `@ApiProperty`, controllers with route and status decorators, and the plugin (or explicit decorators) turns those into an OpenAPI schema at build. The honest follow-ups: a Swagger page is a contract claim, so stale docs are a *bug* — generate the schema in CI and diff it, which this repo's own gate philosophy generalizes; authentication must be declared (`@ApiBearerAuth`) or clients will not send tokens; and response DTOs need explicit typing or Swagger documents `any` — the silent lie.
```typescript
import { SwaggerModule, DocumentBuilder } from '@nestjs/swagger';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  const config = new DocumentBuilder()
    .setTitle('API')
    .setVersion('1.0')
    .addBearerAuth()
    .build();

  const document = SwaggerModule.createDocument(app, config);
  SwaggerModule.setup('api', app, document);

  await app.listen(3000);
}

```

Controller:

```typescript
@ApiTags('users')
@Controller('users')
export class UserController {
  @ApiOperation({ summary: 'Get all users' })
  @ApiResponse({ status: 200, description: 'Success' })
  @Get()
  findAll() {}
}

```

### Q21: How would you design a scalable NestJS application?

**Answer:**

1. **Modular Architecture**: Group by feature

2. **CQRS**: Separate read/write models

3. **Event-Driven**: Use message brokers for async communication

4. **Caching**: Redis for response caching

5. **Database**: Read replicas, connection pooling

6. **Microservices**: Split by bounded context

7. **Load Balancing**: Multiple instances behind load balancer

8. **Monitoring**: Logging, metrics, tracing

### Q22: Explain the NestJS request lifecycle

**Answer:**


The order is the answer, and each stage's *knowledge* justifies its place: middleware sees raw requests (parsing, correlation IDs), guards see the matched handler (authentication, authorization via metadata), interceptors wrap everything (mapping, caching, timeouts, logging around the handler), pipes transform and validate arguments, and exception filters are last — catching anything thrown after route matching. The practical test interviewers pose: where does request-tenant resolution go? (middleware or guard, before anything downstream needs it) Where does response-mapping go? (interceptor, so handlers stay raw) Where does DTO validation go? (pipe — it operates on arguments, not requests)
```text
Request
  → Global Middleware
    → Route Matching
      → Controller Guards
        → Interceptor (before)
          → Pipe (validation)
            → Controller Handler
          ← Interceptor (after)
      ← Exception Filter (if error)
  ← Response

```

### Q23: What is the difference between Singleton, Transient, and Request scope?

**Answer:**

- **Singleton (Default)**: One instance per module
- **Transient**: New instance per consumer
- **Request**: New instance per HTTP request


The default is singleton for a reason: one instance, shared across the process, no per-request cost — and the other two are paid exceptions. Request-scoped rebuilds the *entire dependent subtree* for every request (the service, and everything that injects it, transitively), which is both CPU and garbage-collector load; it exists for state that genuinely is per-request (a tenant-specific connection, a request-scoped context object). Transient gives each consumer its own instance — for stateful helpers. The senior reflex: reach for explicit state passing or an AsyncLocalStorage context before reaching for request scope, and know that request-scoped providers cannot be injected into singletons without a context bridge.
```typescript
@Injectable() // Singleton
class SingletonService {}

@Injectable({ scope: Scope.TRANSIENT })
class TransientService {}

@Injectable({ scope: Scope.REQUEST })
class RequestService {
  constructor(private request: Request) {}
}

```

### Q24: How do you implement CQRS in NestJS?

**Answer:**


The separation has a purpose beyond ceremony: commands (CreateUser) express *intent that mutates state* and flow through the command bus to exactly one handler — a natural place for transactions, domain events, and authorization; queries express *reads* and may bypass the domain entirely (a raw optimized query is fine). The honest assessment interviewers want: NestJS's `@nestjs/cqrs` is a light bus, not Event Sourcing; the pattern pays off when handlers accumulate cross-cutting logic (validation, audit, outbox) or when command/query scaling needs to diverge — and is ceremony when a service method would do. Name the trigger you would adopt it on.
```typescript
// Command
export class CreateUserCommand {
  constructor(public name: string, public email: string) {}
}

// Command Handler
@CommandHandler(CreateUserCommand)
export class CreateUserHandler implements ICommandHandler<CreateUserCommand> {
  async execute(command: CreateUserCommand) {
    const user = await this.userRepo.create(command);
    this.eventBus.publish(new UserCreatedEvent(user));
    return user;
  }
}

// Controller
@Post()
async create(@Body() dto: CreateUserDto) {
  return this.commandBus.execute(new CreateUserCommand(dto.name, dto.email));
}

```

### Q25: What is the difference between `ClientProxy.send()` and `ClientProxy.emit()`?

**Answer:**

- `send()`: Request-response pattern, expects response
- `emit()`: Event pattern, fire-and-forget


The difference is the conversation: `send()` opens a request-response exchange — it returns an Observable that completes with the reply, keyed by a correlation ID the framework manages, and it *can fail* (timeout, no responder), so callers handle errors. `emit()` is fire-and-forget: the broker accepts the event and nobody waits — delivery semantics are the broker's (at-least-once in practice), and the sender cannot know who consumed it. The design rule: emit for facts that have happened (user_created), send for questions that need answers right now (get_user) — and the trap is send-ing across services where a queue would decouple, because that re-couples services with worse latency than HTTP.
```typescript
// Request-response
const user = await this.client.send({ cmd: 'get_user' }, { id }).toPromise();

// Event
this.client.emit('user_created', userData);

```

### Q26: How do you implement rate limiting in NestJS?

**Answer:**
Using `@nestjs/throttler`:


The named-tier shape is the interesting part — short bursts, medium sessions, long horizons are different budgets, and a login route needs all three considered separately. What the sketch leaves out is what production requires: the in-memory store is per-process, so behind three replicas the effective limit is 3× — swap in the Redis store so the counter is global; apply per-route overrides with `@Throttle`/`@SkipThrottle` (auth tighter, health checks skipped); and key by identity, not just IP (NAT collapses thousands of users onto one address — Q18 of the security bank's point). The 429 response should carry `Retry-After`.
```typescript
@Module({
  imports: [
    ThrottlerModule.forRoot([
      { name: 'short', ttl: 1000, limit: 3 },
      { name: 'medium', ttl: 10000, limit: 20 },
      { name: 'long', ttl: 60000, limit: 100 },
    ]),
  ],
})
export class AppModule {}

// Or with guard
@UseGuards(ThrottlerGuard)
@Get('expensive')
expensiveEndpoint() {}

```

### Q27: How do you implement file uploads in NestJS?

**Answer:**


The interceptor wraps multer, and the decisions that matter live in its configuration: memory storage buffers the whole file in RAM (`file.buffer`) — fine for avatars, an outage for 2 GB uploads, where disk streaming or direct-to-object-storage presigned URLs belong; file filters should check mimetype *and* size limits before buffering; and the security layer is entirely yours — multer validates nothing beyond the filter. The follow-ups: uploaded files are untrusted input (the security bank's file-upload answer: randomize names, serve from another origin); and FileInterceptor's field name must match the client's form field, the classic silent `undefined`.
```typescript
import { FileInterceptor, FilesInterceptor } from '@nestjs/platform-express';

@Controller('upload')
export class UploadController {
  @Post('single')
  @UseInterceptors(FileInterceptor('file'))
  uploadFile(@UploadedFile() file: Express.Multer.File) {
    return { filename: file.originalname, size: file.size };
  }

  @Post('multiple')
  @UseInterceptors(FilesInterceptor('files', 10))
  uploadFiles(@UploadedFiles() files: Express.Multer.File[]) {
    return files.map(f => ({ filename: f.originalname }));
  }
}

```

### Q28: How do you implement WebSocket in NestJS?

**Answer:**


The gateway is a provider with socket semantics: it participates in DI (inject services normally), joins namespaces/rooms for routing, and — the part interviews probe — *authentication is not built in*: the `handleConnection` hook must verify the handshake's token (short-lived, since browsers cannot set WS headers) and close with a policy violation code otherwise. Origin checking is likewise manual. For scale: a single Node process cannot broadcast across replicas, so the Redis adapter pub-subes events between instances — the moment you run two pods, this stops being optional. Message validation reuses pipes/DTOs where possible.
```typescript
// Gateway
@WebSocketGateway()
export class EventsGateway {
  @WebSocketServer()
  server: Server;

  @SubscribeMessage('message')
  handleMessage(client: Socket, payload: string): void {
    this.server.emit('message', payload);
  }
}

// Module
@Module({
  imports: [ClientsModule.register([
    { name: 'WEBSOCKET', transport: Transport.TCP },
  ])],
  providers: [EventsGateway],
})
export class EventsModule {}

```

### Q29: How do you handle database transactions in NestJS?

**Answer:**
Using TypeORM:


The QueryRunner pattern is explicit transaction management: create, connect, `startTransaction`, and — the detail the code must get right — `release()` in a `finally`, because a leaked runner holds a pool connection until timeout. Transactions stay narrow (network calls inside a transaction are how deadlocks and pool exhaustion happen), and the alternative patterns are worth naming: a `Transactional` decorator via CLS (auto-wraps the method), or TypeORM's `transaction()` callback. The interview edge: isolation levels and what concurrent writes do under the default — and the outbox pattern when the transaction must also publish an event (the write and the publish are two systems; one transaction cannot span them).
```typescript
@Injectable()
export class UserService {
  constructor(private dataSource: DataSource) {}

  async createUserWithProfile(dto: CreateUserDto) {
    const queryRunner = this.dataSource.createQueryRunner();
    await queryRunner.connect();
    await queryRunner.startTransaction();

    try {
      const user = await queryRunner.manager.save(User, dto);
      const profile = await queryRunner.manager.save(Profile, { userId: user.id });
      await queryRunner.commitTransaction();
      return { user, profile };
    } catch (err) {
      await queryRunner.rollbackTransaction();
      throw err;
    } finally {
      await queryRunner.release();
    }
  }
}

```

### Q30: What is the purpose of `OnModuleInit` and `OnApplicationShutdown`?

**Answer:** Lifecycle hooks:


The hooks exist because the DI container finishes wiring *before* the process is useful — `OnModuleInit` runs after dependencies resolve, so it is where connections open, caches warm, and consumers subscribe (a query at request time must not be the first thing that connects). `OnApplicationShutdown` is the graceful-deploy half: on SIGTERM (with `enableShutdownHooks()`), close servers, finish or abandon in-flight work, close connections — so a rolling deploy does not sever mid-request or drop consumers. The follow-up: init failures should crash the process (fail fast, let the orchestrator restart), and shutdown must be bounded by a timeout so a hung close does not outlive the pod's grace period.
```typescript
@Injectable()
export class AppService implements OnModuleInit, OnApplicationShutdown {
  async onModuleInit() {
    // Called once module is initialized
    await this.initializeConnection();
  }

  async onApplicationShutdown(signal?: string) {
    // Called when application shuts down
    await this.closeConnection();
  }
}

```

### Q31: Design a multi-tenant NestJS application

**Answer:**


The design question under the code is *where tenant isolation is enforced*: middleware resolving `x-tenant-id` (better: a token claim — headers are spoofable at internal hops) only *identifies* the tenant; enforcement must follow every query. Three enforcement tiers: application discipline (an injected tenant-scoped repository — works until one query forgets), ORM-level (Prisma client extensions or TypeORM subscriber auto-adding `tenantId`), and database-level (Postgres RLS, the strongest — a missing filter becomes an error, not a leak). The senior answer names the failure mode — one forgotten `where` clause crossing tenant data — and picks enforcement that survives forgetfulness. Caching, connection pooling, and per-tenant config each add tenant dimensions too.
```typescript
// Tenant middleware
@Injectable()
export class TenantMiddleware implements NestMiddleware {
  async use(req: Request, res: Response, next: NextFunction) {
    const tenantId = req.headers['x-tenant-id'];
    const config = await this.configService.getTenantConfig(tenantId);
    req.tenantConfig = config;
    next();
  }
}

// Tenant-aware service
@Injectable()
export class UserService {
  constructor(
    @Inject('TENANT_CONNECTION')
    private connection: Connection,
  ) {}

  async findAll() {
    return this.connection.getRepository(User).find();
  }
}
```

### Q32: How would you implement distributed caching?

**Answer:**


The Redis-backed CacheModule solves the problem the default in-memory cache has: three replicas hold three different answers. The design decisions past the setup: key namespacing (`svc:entity:id`, versioned when shapes change), TTLs chosen per data class (reference data minutes-to-hours, user state seconds) with explicit invalidation on writes — and the honest rule that *cache-aside on read with delete-on-write* is the durable default; time-based invalidation alone is a stale-data wager. Stampede protection is the follow-up that separates answers: a hot key expiring sends every replica to the database at once — single-flight locks or short jittered TTLs blunt it.
```typescript
// Redis cache module
@Module({
  imports: [
    CacheModule.registerAsync({
      useFactory: (config: ConfigService) => ({
        store: redisStore,
        host: config.get('REDIS_HOST'),
        port: config.get('REDIS_PORT'),
        ttl: 60,
      }),
      inject: [ConfigService],
    }),
  ],
})
export class CacheModule {}

// Service
@Injectable()
export class ProductService {
  constructor(@Inject(CACHE_MANAGER) private cache: Cache) {}

  async findAll(): Promise<Product[]> {
    const cached = await this.cache.get<Product[]>('products');
    if (cached) return cached;

    const products = await this.productRepo.find();
    await this.cache.set('products', products, 300);
    return products;
  }
}
```

### Q33: Design a circuit breaker pattern in NestJS

**Answer:**


The state machine is the answer; the code shows only the closed half. Three states: CLOSED (requests flow; failures counted on a sliding window), OPEN (calls fail fast without touching the dependency — protecting both sides — until the reset timeout), and HALF-OPEN (probe with a few real requests; success closes, failure re-opens). The details interviews probe: count *consecutive-or-windowed* failures not lifetime counts; per-dependency (not global) breakers; what an OPEN breaker returns to callers — a fallback, a cached answer, or a 503 with `Retry-After` — because fail-fast without a fallback just relocates the outage. In production, prefer a hardened library (opossum) with metrics exported, and consider a mesh for the cross-service policy.
```typescript
@Injectable()
export class CircuitBreakerService {
  private state = 'CLOSED';
  private failureCount = 0;
  private threshold = 5;
  private resetTimeout = 30000;

  async execute<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === 'OPEN') {
      throw new ServiceUnavailableException('Circuit is open');
    }

    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }

  private onSuccess() {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }

  private onFailure() {
    this.failureCount++;
    if (this.failureCount >= this.threshold) {
      this.state = 'OPEN';
      setTimeout(() => { this.state = 'HALF_OPEN'; }, this.resetTimeout);
    }
  }
}

```

### Q34: How would you implement event sourcing in NestJS?

**Answer:**


The commitment event sourcing makes: the event store is the *only* source of truth — state is derived by replaying a stream in order, so every handler must be idempotent, every event immutable, and the append must be ordered per aggregate (optimistic concurrency via expected version). The design consequences: snapshots every N events so replays stay bounded; projections (read models) rebuilt off the stream — which is also the migration story; and event *schema* evolution, because the store outlives every version of the code — versioned events and upconverters beat mutating history. The honest cost statement: this buys audit and temporal debugging at the price of eventual consistency and a query model to maintain — worth it for a domain that needs history, ceremony otherwise.
```typescript
// Event store
@Injectable()
export class EventStore {
  async save(event: DomainEvent) {
    await this.eventTable.insert({
      aggregateId: event.aggregateId,
      eventType: event.eventType,
      payload: JSON.stringify(event),
      version: event.version,
      timestamp: new Date(),
    });
  }

  async getEvents(aggregateId: string): Promise<DomainEvent[]> {
    return this.eventTable.find({ where: { aggregateId } });
  }
}

// Aggregate
export class OrderAggregate {
  private events: DomainEvent[] = [];

  static fromEvents(events: DomainEvent[]): OrderAggregate {
    const aggregate = new OrderAggregate();
    events.forEach(event => aggregate.apply(event));
    return aggregate;
  }

  apply(event: DomainEvent) {
    this.events.push(event);
    this.applyEvent(event);
  }
}

```

### Q35: Design a real-time notification system

**Answer:**


The architecture splits into three planes, and conflating them is the design smell: the *event* (something happened — order shipped), the *decision* of who cares (user preferences, channel matrix, quiet hours), and the *delivery* (push, email, SMS with retries and receipts). The service in the sketch is the middle plane — it should consume domain events off a queue (not be called synchronously by feature code), fan out per preference, and deduplicate/batch (five events in a minute is one notification). Delivery belongs behind its own retrying queue with idempotent sends — providers retry too, so message IDs must dedupe. The follow-up: rate limiting and priority lanes, because a marketing blast must not delay an OTP.
```typescript
// Notification service
@Injectable()
export class NotificationService {
  constructor(
    @Inject('WEBSOCKET') private wsClient: ClientProxy,
    private emailService: EmailService,
    private pushService: PushService,
  ) {}

  async notify(userId: string, notification: NotificationDto) {
    // Real-time
    this.wsClient.emit('notification', { userId, ...notification });

    // Email
    if (notification.channels.includes('email')) {
      await this.emailService.send(notification);
    }

    // Push
    if (notification.channels.includes('push')) {
      await this.pushService.send(userId, notification);
    }
  }
}

// WebSocket gateway
@WebSocketGateway()
export class NotificationGateway {
  @WebSocketServer()
  server: Server;

  @SubscribeMessage('subscribe')
  handleSubscribe(client: Socket, userId: string) {
    client.join(`user:${userId}`);
  }

  sendNotification(userId: string, notification: any) {
    this.server.to(`user:${userId}`).emit('notification', notification);
  }
}

```

### Q36: How would you implement API versioning?

**Answer:**


The mechanism is cheap — `enableVersioning` plus `@Controller({ version: '1' })` — so the interview is really about *policy*: version at the service boundary only (internal modules never branch by version), choose the scheme deliberately (URI is cache-friendly and greppable; header/media-type keeps URLs stable but is harder to route and debug), and treat deprecation as a product process — sunset headers, a migration window, and usage metrics per version before shutdown. The deeper point: most changes need *no* new version — additive optional fields are compatible; removing fields, changing semantics, or altering validation is what earns a v2. Versioning without a compatibility rule degenerates into version sprawl.
```typescript
// main.ts
app.enableVersioning({
  type: VersioningType.URI,
});

// Controller
@Controller({ path: 'users', version: '1' })
export class UsersV1Controller {
  @Get()
  findAll() { return 'v1 users'; }
}

@Controller({ path: 'users', version: '2' })
export class UsersV2Controller {
  @Get()
  findAll() { return 'v2 users with new fields'; }
}

```

### Q37: Design a feature flag system

**Answer:**


The two halves are evaluation and lifecycle. Evaluation: `isEnabled` needs *context* (user id, tenant, environment) — the moment targeting exists, flags are a rules engine, so the read path must be cached (a Redis-backed snapshot with short TTL) because it runs on hot paths. Lifecycle is the part teams skip: every flag is a promise to delete it — an owner, an expiry date, and a kill-switch test in CI (flag-off must boot and serve). Flags-as-config-debt is the classic failure: thousands of dead combinations nobody dares remove, tests only ever covering flag-on, and the follow-up interviewers love: how do you test a feature that is on for 5% of users? (deterministic bucketing by stable user id, and integration tests that pin the bucket).
```typescript
@Injectable()
export class FeatureFlagService {
  constructor(private config: ConfigService) {}

  async isEnabled(flag: string, context?: any): Promise<boolean> {
    const flags = await this.getFlags();
    const feature = flags[flag];

    if (!feature) return false;

    if (feature.percentage !== undefined) {
      const hash = this.hashContext(context);
      return (hash % 100) < feature.percentage;
    }

    return feature.enabled;
  }

  private hashContext(context: any): number {
    const str = JSON.stringify(context);
    let hash = 0;
    for (let i = 0; i < str.length; i++) {
      hash = ((hash << 5) - hash) + str.charCodeAt(i);
    }
    return Math.abs(hash) % 100;
  }
}

// Guard
@Injectable()
export class FeatureFlagGuard implements CanActivate {
  constructor(private featureService: FeatureFlagService) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const flag = this.reflector.get<string>('feature', context.getHandler());
    if (!flag) return true;
    return this.featureService.isEnabled(flag);
  }
}

```

### Q38: How would you implement zero-downtime deployments?

**Answer:**

1. **Health Checks**: Ensure service is ready before accepting traffic

2. **Graceful Shutdown**: Complete in-flight requests before stopping

3. **Load Balancer**: Route traffic away from old instances


The deployment story is a chain, and the weak link names itself: readiness probes gate traffic (health endpoint checks *dependencies*, not just the process), SIGTERM triggers `OnApplicationShutdown` (Q30) so in-flight requests finish, and the orchestrator's termination grace period must exceed the longest request. The half that kills zero-downtime in practice is schema migration: version N and N+1 run *simultaneously* during a rolling deploy, so migrations must be backward-compatible — expand (add nullable, dual-write), then contract (drop old) in separate releases. A single non-backward-compatible migration converts your rolling deploy into an outage with extra steps.
```typescript
async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // Health check endpoint
  app.useLogger(['error', 'warn', 'log', 'debug', 'verbose']);

  // Graceful shutdown
  app.enableShutdownHooks();

  await app.listen(3000);
}

// OnApplicationShutdown hook
@Injectable()
export class AppService implements OnApplicationShutdown {
  async onApplicationShutdown() {
    // Close database connections
    await this.database.disconnect();
    // Finish in-flight requests
    await this.server.close();
  }
}

```

### Q39: Design a distributed tracing system

**Answer:**


The interceptor generates IDs, but that is only step one — tracing's real problem is *propagation*: every service must continue the same trace, which means reading W3C `traceparent` (or B3) from inbound headers, passing context to outbound calls, queues, and threads, and recording spans around real I/O — hand-rolled UUIDs cannot do any of that, which is why the senior answer is OpenTelemetry's SDK (auto-instrumentation for HTTP, gRPC, and database drivers) exporting to a collector. Then the judgment questions: sampling (100% is unaffordable at scale; tail-based sampling keeps the interesting failures), span attributes as the queryable surface (tenant, route template — not raw user IDs, a PII rule), and the point of it all — a trace turns "p99 spiked" from a dashboard mystery into a waterfall you can read.
```typescript
// Trace interceptor
@Injectable()
export class TraceInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const traceId = uuid();
    const spanId = uuid();

    // Add to request
    const request = context.switchToHttp().getRequest();
    request.traceId = traceId;
    request.spanId = spanId;

    // Add to response headers
    const response = context.switchToHttp().getResponse();
    response.setHeader('X-Trace-Id', traceId);

    const startTime = Date.now();

    return next.handle().pipe(
      tap({
        next: () => this.exportSpan(traceId, spanId, startTime, 'OK'),
        error: (err) => this.exportSpan(traceId, spanId, startTime, 'ERROR'),
      }),
    );
  }

  private exportSpan(traceId: string, spanId: string, startTime: number, status: string) {
    const duration = Date.now() - startTime;
    // Export to Jaeger/Zipkin
    this.tracer.export({ traceId, spanId, duration, status });
  }
}

```

# NestJS Interview Questions


## First Principles

A framework runs within a process, while its callers, databases and brokers can fail independently. Container registration determines what exists locally; input validation, authorization and transactions determine which work is permitted; delivery and recovery determine what survives interruption.

Answer with the mechanism, one concrete failure trace and the condition that changes the design. These 40 prompts are a practice set, not a measured ranking of employer question frequency. Read the chapters before using the bank; code and transport setup live in their canonical chapters.

## Questions 1–10

### Q1: What is NestJS and why would you use it?

**Answer:** Nest is a TypeScript-oriented Node framework with modules, dependency injection and transport adapters. It can run HTTP through Express or Fastify and supports message, GraphQL and socket integrations. Choose its consistent wiring when a growing application needs it; measure the ceremony and framework coupling against a smaller service's needs. Its structure does not automatically establish scalability or clean business boundaries.

### Q2: What are the main components of a NestJS application?

**Answer:** Modules register related controllers and providers and expose selected dependencies. Controllers adapt requests to application services. Providers own business/data work; middleware runs early, guards decide access, pipes validate arguments, interceptors wrap execution and filters format uncaught errors. Trace a create request through authentication, resource authorization, input validation and the transaction rather than treating these as interchangeable components.

### Q3: What is the difference between NestJS and Express?

**Answer:** Express provides the HTTP routing/middleware layer. Nest usually runs on an Express or Fastify adapter and adds a container, module graph and metadata-driven pipeline. Express can support disciplined boundaries too; Nest makes many wiring conventions explicit. The cost is decorators, registration and adapter-specific behavior. Switching HTTP adapters does not automatically make Express middleware or Multer compatible.

### Q4: What is a module in NestJS?

**Answer:** A `@Module()` class describes `imports`, `providers`, `controllers` and `exports`. Importing a module makes its exported providers available, not every private implementation. Register one owner for a provider and export it when other modules need it; re-registering the class elsewhere can create another instance. The decorator supplies metadata; the module must be reachable from the application's root graph.

### Q5: What is dependency injection in NestJS?

**Answer:** The container resolves a constructor token to a registered provider within the module's visibility. Singleton dependencies are generally constructed at startup; request-scoped and lazy graphs have later lifetimes. Missing tokens can fail resolution. Extracting a shared capability is usually clearer than a circular graph; `forwardRef` is an escape hatch where the relevant module/provider references must be coordinated.

### Q6: What is the difference between `@Injectable()` and `@Inject()`?

**Answer:** `@Injectable()` supplies provider metadata; the module still registers the class. `@Inject(token)` tells a consumer which token it needs, especially for symbols, strings or interfaces erased by TypeScript. `useExisting` aliases a registered provider; `useClass` constructs a provider for that registration. Two tokens do not imply two instances when one is an alias.

### Q7: What are the different HTTP method decorators in NestJS?

**Answer:** `@Get`, `@Post`, `@Put`, `@Patch`, `@Delete`, `@Head`, `@Options` and `@All` register route methods. A decorator does not enforce the HTTP semantic contract: a PUT handler must implement replacement/idempotency, and a GET must avoid requested mutation. Default POST success is 201; use `@HttpCode` when a different documented result is appropriate.

### Q8: How do you validate request data in NestJS?

**Answer:** Use concrete DTO classes, validation decorators and an enabled `ValidationPipe`. `whitelist` keeps decorated properties; `forbidNonWhitelisted` rejects extras instead of stripping them. `transform` returns DTO instances, but explicit parsing/conversion rules are still needed. Nested validation requires nested type metadata and validators. Authorization and database invariants remain service responsibilities after the input shape passes.

### Q9: What is the purpose of `@Controller()` decorator?

**Answer:** `@Controller('users')` stores a route prefix; register the class in a module's `controllers` list. Method metadata then contributes the full route. Keep the controller as an adapter that extracts input, delegates the use case and maps its response. Services can then serve HTTP, messages or scheduled work without copying the business rule.

### Q10: How do you run a NestJS application?

**Answer:** `NestFactory.create(AppModule)` builds an HTTP application and dependency graph. `app.init()` or `app.listen()` runs initialization hooks; `listen()` binds the server. Register global pipes/filters and enable signal shutdown deliberately before accepting traffic. Standard npm scripts are application conventions, not Nest guarantees. A standalone context or microservice has a different bootstrap entry point.

## Questions 11–20

### Q11: What is middleware and how does it differ from guards?

**Answer:** Middleware sees transport request/response data and can handle correlation IDs or parsing. Guards receive an `ExecutionContext`, including the matched handler/class, and can read role metadata. The usual pipeline is middleware, guards, interceptors before execution, argument pipes, handler, then interceptor output/error handling. Exception filters handle uncaught errors; an interceptor may catch an error before it reaches a filter.

### Q12: What is the difference between `@Put()` and `@Patch()`?

**Answer:** PUT describes creation/replacement of the target resource at its known URI and is idempotent. PATCH applies a patch whose format defines its operations; setting a value can be idempotent, incrementing may not be. `PartialType` makes fields optional but does not define null/removal semantics. Enforce the chosen wire contract and protect concurrent updates with a version or precondition where needed.

### Q13: What is a DTO and why is it important?

**Answer:** A data transfer object separates the accepted/emitted wire shape from persistence entities. Concrete classes give Nest runtime constructors for metadata; field types still erase. Validation decorators enforce shape only when a pipe runs, and OpenAPI decorators describe it separately. A response DTO should omit credentials and internal fields rather than returning the whole entity.

### Q14: How do you implement authentication in NestJS?

**Answer:** Authenticate a credential using a configured strategy/guard, validate signature and relevant issuer/audience/expiry, then attach a safe principal. A separate resource policy decides authorization. A global guard with an explicit public-route escape can reduce accidental exposure. JWTs can be subject to revocation checks; expiration alone is only one policy. Never accept a tenant or role merely because a client submitted it.

### Q15: What is the difference between a Guard and an Interceptor?

**Answer:** A guard decides whether execution may proceed and can read handler/class metadata. An interceptor surrounds the downstream Observable, so it can measure, transform, short-circuit or catch errors. A before-phase interceptor could reject execution, but guard semantics make access policy explicit. After-phase checks are too late to prevent a side effect. Neither is a database transaction.

### Q16: How do you handle errors in NestJS?

**Answer:** Throw a meaningful domain/application error and translate it into a safe transport error. HTTP filters write HTTP responses; RPC filters use the RPC contract. A catch-all filter should avoid stack/SQL/secret disclosure while preserving server-side diagnostics and correlation. Log once at the responsible boundary. A filtered response proves the client shape, not that background event errors were handled.

### Q17: What is the difference between `useClass`, `useFactory`, `useValue`, and `useExisting`?

**Answer:** `useValue` supplies an object, `useClass` constructs a class for the token, `useFactory` builds a value with declared `inject` dependencies and may return a promise, and `useExisting` aliases another registration. Use `useExisting` when two tokens must refer to the same instance. A factory is useful for asynchronous connection setup, but asynchronous initialization is not limited to factories.

### Q18: What is the purpose of `@nestjs/config`?

**Answer:** `ConfigModule` loads deployment settings and injects `ConfigService`. Add startup validation separately through a schema or custom validation function. `get<number>()` does not convert a raw string, and custom factory outputs need validation too. Runtime environment values normally override env files. Secrets need external storage/rotation and should not appear in logs; namespaced config is still process-wide.

### Q19: How do you test a NestJS service?

**Answer:** Construct the service directly with collaborators for a narrow rule test, or use `Test.createTestingModule` when container wiring is under test. Replace external dependencies rather than the service being tested. Assert both missing and existing outcomes and close the module. A mocked repository cannot validate SQL, transaction isolation or schema migrations; use the target database for those contracts.

### Q20: What is Swagger and how do you integrate it?

**Answer:** `@nestjs/swagger` reads controller/DTO metadata into OpenAPI and Swagger UI renders it. Document actual response types, status codes, errors and matching security scheme names. Security metadata does not install a guard, and schema metadata does not install validation. Generate a separate current artifact, compare compatibility and freshness, and test representative real responses against the claimed contract.

## Questions 21–30

### Q21: How would you design a scalable NestJS application?

**Answer:** Start from the workload, latency/failure targets and business invariants. Measure event-loop delay, database queries, connection use and queue backlog before adding replicas. Feature modules establish code boundaries; a shared pool needs a total replica budget. Add caching, read models or service splits only when their measured benefit justifies invalidation, consistency and operational costs. CQRS and microservices are choices, not a scalability checklist.

### Q22: Explain the NestJS request lifecycle

**Answer:** Trace middleware, global/controller/route guards, interceptors before execution, argument pipes, handler, then returning interceptor transformations. Filters format uncaught errors at their applicable scope. Pipes validate arguments after guards, so a guard cannot rely on a DTO pipe having already sanitized its input. Interceptors can short-circuit the handler. Explain which component knows the authenticated principal and which owns resource authorization.

### Q23: What is the difference between Singleton, Transient, and Request scope?

**Answer:** Default providers are shared per registration/context graph, not inherently one instance of a class in every module. Request scope shares an instance within one request context and can make its consumers request-scoped. Transient providers give consumers separate instances. Inject HTTP requests with `@Inject(REQUEST)` rather than a TypeScript `Request` interface. Explicit state passing or AsyncLocalStorage may avoid unnecessary request-scoped graphs.

### Q24: How do you implement CQRS in NestJS?

**Answer:** Register `CqrsModule`, command/query classes and decorated handlers. The buses dispatch each command/query to its handler. Separate interfaces can share storage. The handler owns authorization and its transaction; default local event publication does not await all asynchronous projections or provide crash-safe delivery. Use an outbox for committed changes that must reach another store, and define read-after-write behavior.

### Q25: What is the difference between `ClientProxy.send()` and `ClientProxy.emit()`?

**Answer:** `send()` initiates a request-response exchange on subscription to its cold Observable. `firstValueFrom(client.send(...).pipe(timeout(...)))` waits for a result with a deadline. `emit()` attempts event delivery immediately and has no business response; observe errors deliberately. Guarantees depend on the transport: Redis pub/sub is not a durable backlog. A timeout does not prove a remote write failed.

### Q26: How do you implement rate limiting in NestJS?

**Answer:** Configure named limits and register `ThrottlerGuard` at the relevant scope. Use the documented time units and a shared counter implementation when limits must span replicas. Key by trusted identity/tenant/IP according to the abuse model and validated proxy settings; a client-supplied forwarding header is not automatically trustworthy. Choose fail-open/closed behavior, route exemptions and a retry signal explicitly.

### Q27: How do you implement file uploads in NestJS?

**Answer:** On the Express adapter, `FileInterceptor` uses Multer and the field name must match the upload. Set multipart size/count limits before accepting large buffers. Client MIME and filenames are untrusted; inspect allowed content, store under generated keys and control serving permissions. Large files often warrant direct object-storage upload plus finalization/scanning. Validate missing files. Fastify needs its compatible multipart path.

### Q28: How do you implement WebSocket in NestJS?

**Answer:** Register a gateway provider and configure the selected socket adapter. Authenticate the handshake, check permitted origins and authorize each operation/room; an authenticated connection is not permission to subscribe to any user. Browser native WebSocket and Socket.IO have different protocols. Cross-replica broadcasts need a compatible coordination adapter; Socket.IO polling may also require session affinity. Offline delivery needs durable replay outside pub/sub.

### Q29: How do you handle database transactions in NestJS?

**Answer:** Use the transaction's manager/client for every participating query. TypeORM's transaction callback can manage cleanup; a manual QueryRunner must release in a finally that includes connection/start failures, and roll back only an active transaction. Keep external calls out of a long transaction where possible. Isolation and retry rules come from the database. An outbox joins state and publication intent within one local transaction.

### Q30: What is the purpose of `OnModuleInit` and `OnApplicationShutdown`?

**Answer:** `onModuleInit` runs during initialization after dependencies resolve. `onApplicationBootstrap` follows module initialization; explicit readiness dependencies still matter. Shutdown runs module destruction, before-shutdown hooks, closes underlying connections, then application-shutdown hooks. Enable signal hooks for supported process signals; `app.close()` also runs teardown. Drain users of a pool before closing it, and bound cleanup against abrupt termination.

## Questions 31–40

### Q31: Design a multi-tenant NestJS application

**Answer:** Resolve tenant identity from authenticated membership, then enforce it on every resource access. Headers only select a candidate tenant; authorize that selection. Tenant-aware repositories and PostgreSQL row-level security can reinforce isolation, but table owners/bypass roles and pooled connection state need explicit treatment. Cache keys, jobs, object storage and exports also carry tenant scope. Test a forgotten filter and a cross-tenant identifier.

### Q32: How would you implement distributed caching?

**Answer:** Share Redis-backed cache storage through the version-supported Keyv/cache-manager adapter; pin versions and verify TTL units. Include tenant, authorization scope and schema version where relevant. Cache-aside may race with invalidation, so delete-on-write alone is not a consistency guarantee. Define stale-result tolerance, stampede protection, memory bounds and outage behavior. The caching chapter owns the full invalidation trace.

### Q33: Design a circuit breaker pattern in NestJS

**Answer:** A breaker is closed while calls flow, open while calls fail fast, then half-open while bounded probes test recovery. Count classified failures within the chosen window, set call deadlines and limit probe concurrency. Late completions from the previous state must not incorrectly close a newer open state. Scope it per dependency/operation and observe transitions. A fallback must preserve the caller's correctness requirements.

### Q34: How would you implement event sourcing in NestJS?

**Answer:** Store immutable accepted events ordered per aggregate with an atomic expected-version append. Replay applies state transitions without generating new external effects or pending events. Separate aggregate history from newly accepted events, and sort reads by version. Snapshots reduce replay work but need a schema/version contract. Projections can lag; schema evolution and replay recovery are deliberate costs, not properties supplied by `@nestjs/cqrs`.

### Q35: Design a real-time notification system

**Answer:** Persist the notification decision and channel work, honoring preferences, quiet hours and priority. Authenticate sockets and join the room derived from the verified principal, never an arbitrary supplied user ID. Pub/sub provides live hints; durable IDs/cursors support offline replay. Email/push sends need bounded retries and provider-specific duplicate/reconciliation contracts. A provider acknowledgment is not proof the person received or read it.

### Q36: How would you implement API versioning?

**Answer:** Enable the chosen URI/header/media-type scheme and use versioned controller contracts where semantics differ. Keep internal business rules shared when valid, document migration and sunset, and measure usage before removal. Adding fields is compatible only for consumers that tolerate them; enum additions or tighter validation can break clients. Compare actual consumer expectations rather than assuming all additive changes are safe.

### Q37: Design a feature flag system

**Answer:** Evaluate a flag against stable authenticated context and versioned rules. A disabled flag must remain off before percentage evaluation. For rollout, hash a stable identity plus flag key into a reproducible bucket and test 0%, 100% and boundaries. Define outage defaults by risk, cache snapshots with freshness evidence and assign an owner/removal date. A rollout flag is not a substitute for authorization.

### Q38: How would you implement zero-downtime deployments?

**Answer:** Readiness, routing propagation, bounded draining and sufficient capacity reduce rollout interruption; they do not guarantee zero downtime. A preStop hook shares the termination budget. Stop new work, settle or recover accepted work, then close resources. Keep schema changes compatible while versions coexist through expand/migrate/contract stages. Exercise SIGTERM under load and measure interrupted requests, duplicate jobs and leaked resources.

### Q39: Design a distributed tracing system

**Answer:** Use OpenTelemetry-compatible instrumentation to extract/propagate trace context and record spans around real work, including outbound calls and queue processing. A new UUID per request is correlation, not distributed context propagation. Export through a collector and choose sampling/attribute policy by cost and diagnostic need. Record safe route templates and avoid secret/personal payloads. Check that asynchronous and message boundaries retain their parent context.

### Q40: How would you optimize NestJS application performance?

**Answer:** Measure a representative workload before choosing a change: slow SQL, serialization, CPU blocking, payload size, pool waits and downstream calls require different remedies. Cache within the allowed staleness contract, paginate bounded results, control concurrency and isolate CPU work. Compression trades bandwidth for CPU. Fastify may help a measured HTTP workload but requires adapter-compatible middleware. Retest latency tails, failure behavior and resource usage after each change.

## Summary

Explain the container and request stages first, then the boundary between local dispatch, remote delivery and durable business work. Senior answers identify the transaction owner, failure recovery and evidence that supports a claimed guarantee.

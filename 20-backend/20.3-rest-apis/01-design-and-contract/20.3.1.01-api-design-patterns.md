# API Design Patterns — REST, GraphQL, gRPC, Webhooks

> **4 API styles + the patterns that go with them.** Every system design that has an API needs to pick one. Know the trade-offs, know the use cases. This is the foundation of "how do clients talk to your service."

## TL;DR

- **REST** — resource-oriented, HTTP methods, JSON. Default for public APIs.
- **GraphQL** — client specifies what they need. For complex data with many relations.
- **gRPC** — binary, strongly-typed, fast. For service-to-service.
- **WebSocket** — full-duplex, persistent. For real-time.
- **Webhook** — server calls back. For async events.
- **SSE (Server-Sent Events)** — server pushes, one-way. For live updates.
- **Pick per use case, not "one API for everything."**

---

## Why it matters

In a system design interview, the API is the first thing you design (or should design). It defines:
- What clients can do
- How clients interact
- How the system scales
- What the team will build for the next 3 years

Pick wrong and you have API spaghetti. Pick right and everything flows.

## REST (Representational State Transfer)

**Definition:** Resource-oriented. Each URL is a resource. HTTP methods (GET, POST, PUT, DELETE) operate on resources. Standard HTTP semantics (status codes, headers, caching).

```
GET /users/123 → get user
GET /users/123/orders → get user's orders
POST /users → create user
PUT /users/123 → update user
DELETE /users/123 → delete user
```

**Pros:**
- **Familiar.** Most developers know REST.
- **Standard tooling.** curl, Postman, OpenAPI.
- **HTTP semantics.** Caching, ETags, status codes, all work.
- **Stateless.** Each request is independent. Easy to scale.
- **Discoverable.** URLs are self-describing.

**Cons:**
- **Over-fetching.** GET /users/123 returns the whole user even if you only need the name.
- **Under-fetching.** GET /users/123 doesn't return related data. Need another call.
- **Multiple round trips.** To get a user + their posts + their comments = 3 calls.
- **Versioning is awkward.** /v1/users vs /v2/users, or content negotiation.
- **No real-time.** HTTP request-response only.

**When to use:**
- Public APIs
- CRUD operations
- Simple data models
- When you want standard tooling

**Best practices:**
- Use nouns for resources (`/users`, not `/getUsers`)
- Use HTTP methods correctly (GET is safe + idempotent, POST creates, PUT is idempotent update, DELETE is idempotent delete)
- Use proper status codes (200, 201, 204, 400, 401, 403, 404, 409, 500)
- Use plural nouns (`/users`, not `/user`)
- Use sub-resources for relationships (`/users/123/orders`)
- Use query parameters for filtering, sorting, pagination (`/users?role=admin&page=2&limit=20`)
- Use HATEOAS for hypermedia (rare in practice)
- Version: `/api/v1/...` or `Accept: application/vnd.myapi.v1+json` (header)
- Use ETags for caching
- Document with OpenAPI

**See:** [Rest Principles](20.3.1.02-rest-principles.md), [Authentication](../04-edge-and-scale/20.3.4.04-authentication.md), [Pagination](../03-payloads-errors-integration/20.3.3.01-pagination.md), [Openapi Swagger](20.3.1.05-openapi-swagger.md) in this section for the deep dive.

## GraphQL

**Definition:** Client specifies the shape of the response. Single endpoint. Schema defines what's possible.

```graphql
# Query
query {
  user(id: 123) {
    name
    posts {
      title
      comments {
        text
      }
    }
  }
}

# Response
{
  "data": {
    "user": {
      "name": "Alice",
      "posts": [
        {
          "title": "Hello",
          "comments": [{"text": "Great post!"}]
        }
      ]
    }
  }
}
```

**Pros:**
- **No over-fetching or under-fetching.** Client gets exactly what it asks for.
- **Single endpoint.** One URL, one schema.
- **Self-documenting.** Schema is the API.
- **Powerful for complex data.** Mobile apps with many screens can share data.

**Cons:**
- **Complex server-side.** Resolvers, N+1 query problems, batching.
- **Caching is harder.** Single endpoint, no HTTP cache.
- **Security is harder.** Don't expose fields the user can't see (auth per field).
- **File uploads are awkward.** Not in the spec.
- **Error handling is weird.** Partial success in one response.
- **Versioning is hard.** Schema deprecation instead of version bump.

**When to use:**
- Mobile apps with multiple views
- Complex relational data
- Frontend teams want to control their data
- Public API for third parties (Facebook, GitHub use it)

**When NOT to use:**
- Simple CRUD
- Server-to-server
- High-throughput microservices (gRPC is faster)
- File uploads

**Used by:** Facebook, GitHub, Shopify, Pinterest, Twitter, Yelp.

**In interviews:** "We have a mobile app that shows a user dashboard with profile, posts, comments, likes. We use GraphQL so the client can fetch all that in one query, reducing round trips from 5 to 1."

## gRPC (Remote Procedure Call)

**Definition:** Binary protocol, strongly typed, uses Protocol Buffers. Service-to-service communication.

```protobuf
// service.proto
service UserService {
  rpc GetUser(GetUserRequest) returns (User);
  rpc ListUsers(ListUsersRequest) returns (stream User);
}

message GetUserRequest {
  int64 id = 1;
}

message User {
  int64 id = 1;
  string name = 2;
  string email = 3;
}
```

**Pros:**
- **Fast.** Binary protocol, HTTP/2, ~10x faster than REST/JSON.
- **Strongly typed.** Schema generates client/server code. Compile-time errors.
- **Streaming.** Unary, server, client, bidirectional.
- **Backward compat.** Add fields without breaking old clients.
- **Code generation.** Client SDKs in 10+ languages.

**Cons:**
- **Not human-readable.** Need tools to inspect.
- **Limited browser support.** No native gRPC in browsers (use gRPC-Web).
- **Harder to debug.** Binary protocol, harder to curl.
- **Steeper learning curve.** Proto files, generated code.
- **Less ecosystem.** OpenAPI has more tooling.

**When to use:**
- Service-to-service (microservices)
- Polyglot teams (generate code for each language)
- High-throughput, low-latency
- Streaming RPC

**When NOT to use:**
- Public APIs (REST or GraphQL is better)
- Browser clients
- When simplicity matters more than performance

**Used by:** Google (invented it), Netflix, Square, many large microservices.

**In interviews:** "We use gRPC for service-to-service. Our Node.js API gateway translates REST to gRPC for internal calls. We get 10x throughput and strong typing across services."

## WebSocket

**Definition:** Full-duplex, persistent connection. Client and server can both send messages at any time.

```
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade

# Connection established

# Client → Server
{ "type": "chat", "message": "hello" }

# Server → Client
{ "type": "chat", "from": "Alice", "message": "hi" }
```

**Pros:**
- **Real-time.** Sub-100ms latency.
- **Bi-directional.** Both sides can send.
- **Persistent.** No connection setup per message.
- **Efficient.** One TCP connection, multiple messages.

**Cons:**
- **Stateful.** Server has to track connections.
- **Harder to scale.** Sticky sessions needed, or use a message bus.
- **No caching.** Real-time = no cache.
- **Firewall issues.** Some networks block WebSocket.
- **Reconnection logic.** Client must handle dropped connections.

**When to use:**
- Real-time chat
- Live dashboards (metrics, monitoring)
- Collaborative editing (Google Docs)
- Multiplayer games
- Live notifications

**When NOT to use:**
- One-way data (use SSE)
- Request-response (use REST)
- High-throughput service-to-service (use gRPC)

**See:** [../../6-Real-Time-Stack/21-WebSockets/](../../../60-realtime/60.1-websockets/INDEX.md) for the full deep-dive.

**In interviews:** "We use WebSocket for the chat feature. Each user maintains a persistent connection to the chat server. The chat server publishes to a Kafka topic; other chat servers consume and forward to their connected users."

## Webhooks

**Definition:** Server makes HTTP POST to a client URL when something happens. The reverse of an API call.

```
# Client registers a webhook URL
POST /webhooks
{ "url": "https://myapp.com/webhook", "events": ["order.created"] }

# Server calls the URL when event happens
POST https://myapp.com/webhook
{ "event": "order.created", "data": { ... } }
```

**Pros:**
- **No polling.** Server pushes when there's an event.
- **Decoupled.** Server doesn't need to know about consumers.
- **Standard HTTP.** Easy to debug, easy to integrate.

**Cons:**
- **Unreliable.** If the client's URL is down, the event is lost (unless you retry).
- **Security concerns.** Need to verify the webhook is from the right sender (HMAC signature).
- **Replay attacks.** Need timestamps + nonces.
- **Client must expose a public URL.** Behind firewalls, this is hard.
- **No ordering guarantee.** Events can arrive out of order.

**When to use:**
- Third-party integrations (Stripe sends webhooks to your server on payment events)
- GitHub, GitLab webhooks on push events
- Notifications
- Async workflows where the consumer has a public URL

**Best practices:**
- Sign with HMAC-SHA256, verify on receipt
- Include timestamp to prevent replay
- Retry with exponential backoff
- Make webhooks idempotent (consumer should handle duplicates)
- Log everything (webhook delivery is async, hard to debug)

**In interviews:** "Stripe sends us a webhook on payment success. We verify the HMAC signature, process the order, and return 200. If we return 5xx, Stripe retries with exponential backoff."

## SSE (Server-Sent Events)

**Definition:** Server pushes events to client over HTTP. One-way (server → client only). Uses `text/event-stream` content type.

```
GET /events HTTP/1.1
Accept: text/event-stream

# Response
HTTP/1.1 200 OK
Content-Type: text/event-stream

event: message
data: {"price": 100}

event: message
data: {"price": 101}

```

**Pros:**
- **Simple.** Just HTTP. No protocol upgrade.
- **Auto-reconnect.** Browser EventSource API handles reconnection.
- **One-way is fine for many use cases.** News feed, notifications, prices.

**Cons:**
- **One-way only.** Client can't send messages back (use POST for that).
- **Limited browser support.** Mostly OK now, but older browsers had issues.
- **Connection limits.** HTTP/1.1 limits per domain.

**When to use:**
- Live news feed
- Price updates
- Notifications
- Server logs streaming

**vs WebSocket:** SSE is simpler but one-way. WebSocket is bidirectional.

## Comparison

| API | Direction | Type | Speed | Use case |
| ------------- | ------------------------------- | ----------------- | --------- | --------------------------- |
| **REST** | Request-response | JSON over HTTP | Medium | Public APIs, CRUD |
| **GraphQL** | Request-response | Query language | Medium | Mobile apps, complex data |
| **gRPC** | Request-response (or streaming) | Protobuf | Very fast | Service-to-service |
| **WebSocket** | Bi-directional streaming | Binary/JSON | Very fast | Real-time chat, games |
| **Webhook** | Server-to-server push | JSON over HTTP | Medium | Async notifications |
| **SSE** | Server-to-client stream | text/event-stream | Fast | Live updates, notifications |

## Choosing the right API

```
Need real-time? → WebSocket (bi-dir) or SSE (one-way)
Need type safety + perf? → gRPC (service-to-service) or GraphQL (typed schema)
Need public API? → REST or GraphQL
Need to send to external systems? → Webhook
Need to query related data efficiently? → GraphQL
Need service-to-service? → gRPC
```

**In interviews:** Name the API style, justify the choice, mention the trade-offs.

## Common API patterns

### 1. API Gateway

A single entry point for all clients. Routes to backend services, handles cross-cutting concerns (auth, rate limiting, logging).

```
Client → API Gateway → Service A
                     → Service B
                     → Service C
```

**Used by:** Most microservices (Kong, AWS API Gateway, Envoy).

### 2. Backend for Frontend (BFF)

A separate API per client type (web, mobile, third-party). Each BFF is tailored to the client.

```
Web App → Web BFF → Service A
Mobile → Mobile BFF → Service A
3rd party → Public BFF → Service A
```

**Used by:** Netflix, Spotify, SoundCloud.

### 3. API Versioning

- **URL version:** `/api/v1/users` (most common)
- **Header version:** `Accept: application/vnd.myapi.v1+json` (more "correct")
- **Query param:** `/api/users?version=1` (rare)

### 4. Idempotency

For POST / PUT / DELETE, use an `Idempotency-Key` header. Server stores the result for 24h. Duplicate requests return the cached result.

```
POST /payments
Idempotency-Key: abc-123
{ "amount": 100, "currency": "USD" }
```

**Used by:** Stripe, AWS.

### 5. Pagination

For large lists, paginate. Common patterns:
- **Offset:** `?page=2&limit=20` (simple, but slow for large offsets)
- **Cursor:** `?cursor=xyz&limit=20` (efficient, but no "jump to page 5")
- **Keyset:** `?after_id=123&limit=20` (efficient for time-series)

**See:** [Pagination](../03-payloads-errors-integration/20.3.3.01-pagination.md) for the full deep-dive.

### 6. Error handling

Use standard HTTP status codes. Return a structured error body.

```json
{
  "error": {
    "code": "invalid_request",
    "message": "Email is required",
    "details": { "field": "email" }
  }
}
```

**RFC 7807 (Problem Details for HTTP APIs)** is the standard.

### 7. Versioning strategies

- **URL versioning** — simplest, most common
- **Header versioning** — cleaner URLs, but harder to test
- **Semantic versioning** — version the API like code (v1.0.0)

### 8. API Documentation

- **OpenAPI / Swagger** — for REST
- **GraphQL introspection** — built into GraphQL
- **gRPC reflection** — built into gRPC

## Anti-patterns

- **REST as a one-size-fits-all.** Use the right tool.
- **Chatty APIs.** 10 calls to render a page. Aggregate or use GraphQL.
- **No versioning.** Breaking changes break clients.
- **No idempotency for non-GET.** Network retries cause double charges.
- **Webhooks without signing.** Anyone can forge events.
- **gRPC for public APIs.** No browser support, no curl.
- **GraphQL for simple CRUD.** Overkill.
- **No pagination.** Return all 10M rows. OOM.

## When to discuss in interviews

| Scenario | API style | Why |
| ---------------------------- | --------------- | ------------------------------- |
| Public CRUD API | REST | Familiar, standard tooling |
| Mobile app with complex data | GraphQL | Single query for multiple views |
| Service-to-service | gRPC | Fast, typed |
| Real-time chat | WebSocket | Bi-directional, low latency |
| Price updates | SSE | One-way, simpler than WS |
| Stripe-like events | Webhook | Server-to-server async |
| Internal admin tool | REST or GraphQL | Whatever the team knows |

## Summary

Choosing the right API pattern is the first architectural decision in any system. REST is the default for CRUD. GraphQL excels when clients need flexible queries. gRPC is best for internal service-to-service communication. WebSocket and SSE handle real-time. Webhooks enable async notifications. The right choice depends on client flexibility, performance needs, real-time requirements, and team expertise. In interviews, compare 2-3 options and justify your pick.

## Cheat Sheet
```text
API DESIGN PATTERNS CHEAT SHEET
═══════════════════════════════════════════════════════════════

REST — Resource-oriented, HTTP methods, stateless
• Best for: CRUD, public APIs, simple domains
• Pros: Cacheable, human-readable, tooling
• Cons: Over/under-fetching, multiple round trips

GRAPHQL — Client queries, single endpoint, typed schema
• Best for: Complex UIs, mobile, multiple clients
• Pros: No over/under-fetching, strong typing
• Cons: Caching harder, N+1 queries, complexity

GRPC — HTTP/2, Protobuf, bidirectional streaming
• Best for: Internal services, high performance
• Pros: Fast (binary), streaming, code generation
• Cons: Browser needs proxy, harder to debug

WEBSOCKET — Full-duplex, bidirectional, persistent
• Best for: Chat, gaming, live collaboration
• Pros: Low latency, real-time
• Cons: Stateful, harder to scale, no HTTP caching

SSE — Server-Sent Events, unidirectional, auto-reconnect
• Best for: Notifications, live feeds, AI streaming
• Pros: Simple, auto-reconnect, HTTP/2 compatible
• Cons: One-way only, connection limits

WEBHOOK — Async push, HTTP callback
• Best for: Integrations, event notifications
• Pros: Async, decoupled
• Cons: Reliability, ordering, debugging

IN INTERVIEWS:
• Name 2-3 options and compare
• Justify based on requirements
• Mention trade-offs explicitly
• Default to REST unless there's a reason not to
```

# API Design Patterns — REST, GraphQL, gRPC, Webhooks

See the interaction before choosing its style. REST is not synonymous with JSON or CRUD.

## Definition

An API design combines how participants interact, how they describe operations and how values are encoded. A shop may expose resource reads over HTTP, typed internal calls, browser progress streams and payment webhooks within the same product.

> **Textbook Definition:** An API interaction pattern specifies the exchange of requests, responses or events between participants. Transport, operation semantics and payload representation are independent dimensions that a system combines according to its client and reliability constraints.

## First Principles

A remote call crosses a trust boundary and can finish without its response arriving. A browser cannot necessarily use the same protocol as an internal service, and an intermittently connected client cannot rely on a live channel to retain its history. Start with who communicates, who initiates and what must survive failure before selecting a protocol or encoding.

The client depends on an external contract, not your database layout. Stable field meanings, authorization, bounded work and recovery rules matter across every style. Changing transport does not remove these obligations.

## How It Works


### 1. See the interaction before choosing its style

| Pattern | Exchange | Contract / common transport |
| --------- | ------------------------------------------------------- | ------------------------------------------------------------------------ |
| REST | Client requests a resource representation or transition | Architectural constraints; commonly HTTP with JSON or other media types |
| GraphQL | Client selects fields permitted by a schema | Query/execution contract; commonly HTTP POST, optionally GET for queries |
| gRPC | Client invokes a typed procedure | Service schema and RPC semantics; commonly HTTP/2 and protobuf |
| WebSocket | Either side sends messages over a live connection | Application message protocol over a full-duplex channel |
| Webhook | Producer calls a registered consumer endpoint | Event, verification, acceptance and retry contract over HTTP |
| SSE | Server sends a sequence of events to a client | `text/event-stream` over an HTTP response |

REST is not synonymous with JSON or CRUD. GraphQL does not promise an error-free result containing every selected field: authorization, nullability and execution errors still apply. A WebSocket channel does not define your message acknowledgments or persistence.
Define those separately.

### 2. Trace one product across several boundaries

A customer opens an order screen. `GET /orders/42` returns its current state under resource and HTTP semantics. A complex dashboard might instead request selected order/customer fields with GraphQL. In either case, the server must authorize the order and bound related collection sizes.

The service asks an inventory service to reserve stock through a gRPC method or another internal API. A deadline expires after inventory committed, so the caller reconciles the same reservation identity rather than blindly making a second reservation. Binary encoding does not change that uncertainty.

The browser watches export progress with SSE, or sends collaborative messages over WebSocket when communication is bidirectional. If the connection drops, it reloads authoritative state and resumes from a documented event cursor where supported. Separately, a payment provider delivers a signed webhook.
The shop commits durable acceptance before acknowledging, then processes the event without repeating an already-applied payment transition.

### 3. REST uses resource and HTTP semantics

Resource identifiers give operations stable targets, such as `/orders/42`. GET reads safely; PUT replaces according to its documented representation; POST can create a resource or request another operation. DELETE's intended effect is idempotent even if later responses differ.
PATCH idempotence depends on its patch operation.

HTTP caching, validators and conditional writes can serve suitable contracts. They are not automatically correct just because a route uses GET. A resource can expose sparse fields or aggregated views, so over-fetching and multiple round trips are API-shape choices rather than unavoidable REST properties.
Real-time delivery can coexist with its ordinary read API.

See [REST Principles](20.3.1.02-rest-principles.md) and the [HTTP mechanics](../02-http-mechanics/INDEX.md) for their canonical mechanisms.

### 4. GraphQL trades client shaping for server work control

A schema describes selectable fields and input types. Resolvers fetch their values; nesting may fan out into many database or downstream requests. A single network request can reduce client round trips while increasing server work.
Batch appropriate loads, authorize fields/resources and impose query-cost and collection limits.

Queries may use supported GET transport and persisted documents for HTTP caching; normalized client caches and server caches are other options. Caching is not forbidden by a single endpoint, but keys must represent the operation, variables and access scope. Partial results need explicit client error handling.
GraphQL can suit internal or external consumers; it is not categorically unsuitable for service-to-service use.

### 5. gRPC makes the procedure contract explicit

A `.proto` service declares methods and message types. Generated clients/server interfaces reduce manual encoding work; unary, server-streaming, client-streaming and bidirectional-streaming methods support different exchanges. Field evolution and runtime int64 handling still need tests.

Native browser constraints often require a supported gRPC-Web path or another browser-facing interface. This adds translation and supported-streaming limits to the design. Use gRPC when its client ecosystem, schemas and RPC/streaming semantics help; do not claim a universal tenfold speed or throughput advantage over REST.
Public clients can use it when their tooling supports the contract.

### 6. Live channels need recovery rules

WebSocket supports two-way messages over a persistent connection. Define authentication renewal, message IDs, ordering, acknowledgment, backpressure and reconnection. A connection belongs to one process, but sticky routing is not a universal requirement; routing, connection ownership and cross-process delivery depend on the deployment and broker design.
A Kafka consumer group normally distributes records among members, so it does not by itself broadcast each message to every socket server.

SSE is one-way server-to-client delivery. Browser EventSource supports reconnection, but the server must retain or reconstruct an appropriate event history and interpret Last-Event-ID for recovery. HTTP version, intermediary buffering and connection limits affect operation.
A live transport alone provides neither a latency guarantee nor durable history.

#### Webhooks hand responsibility to another server

The producer delivers an event to a consumer's endpoint under its verification and retry rules. A lost acknowledgment can cause repetition, and separate deliveries can arrive out of order. Durable inbox acceptance and duplicate-safe business processing are distinct.
Use the provider's signature scheme instead of assuming every scheme includes timestamps and nonces. Redact diagnostics; “log everything” can expose sensitive bodies or secrets.

See [Webhooks](../03-payloads-errors-integration/20.3.3.05-webhooks.md) for the complete ingress and delivery contract.

### 7. Cross-cutting patterns have their own homes

An [API gateway](../04-edge-and-scale/20.3.4.02-api-gateway.md) handles edge routing and shared policies; a [backend for frontend](../04-edge-and-scale/20.3.4.03-bff.md) shapes data for a particular client. Neither should become an accidental owner of all domain logic.

[Versioning](20.3.1.03-versioning.md) selects incompatible contracts and governs migration; compatible additions may not need another version. [Pagination](../03-payloads-errors-integration/20.3.3.01-pagination.md) bounds collections; a cursor is a continuation token and keyset is one possible implementation. [Error design](../03-payloads-errors-integration/20.3.3.02-error-handling-design.md) separates safe messages from machine recovery decisions.

Idempotency keys preserve operation identity across retries under a documented durable scope and retention policy. Twenty-four hours is a particular provider's contract, not a default law of APIs. [OpenAPI](20.3.1.05-openapi-swagger.md), GraphQL schemas and protobuf service schemas describe different contracts; introspection/reflection can be disabled and generated types do not enforce runtime authorization.

## Decisions and mistakes

Choose based on client support, data shape, interaction direction, latency/work budgets, failure recovery, compatibility and team operations. Avoid a universal ranking by “speed”. Compare representative end-to-end work, including fan-out, serialization, authorization, caching and connection recovery.

In a senior interview, trace one operation through failure and explain why the choice satisfies its constraints. A credible answer names a deadline, an uncertain effect, a recovery identity and an operating cost instead of listing companies that allegedly use a technology.

## Summary

Select interaction and contract before transport or encoding. Resource APIs, typed RPC, client-shaped queries, live streams and callbacks can coexist; every choice still needs authorization, bounded work, compatibility and explicit recovery from uncertain outcomes.

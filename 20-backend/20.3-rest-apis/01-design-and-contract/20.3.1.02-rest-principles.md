# REST Principles

## Definition

REST, or Representational State Transfer, is an architectural style for distributed hypermedia systems. Clients operate on identified resources through representations and self-descriptive messages, following controls supplied by those representations.

> **Textbook Definition:** REST combines client-server separation, stateless communication, cache constraints, a uniform interface and a layered system, with optional code on demand. These constraints define the style; HTTP JSON routes and plural nouns alone do not.

## First Principles

Independent participants need to communicate without depending on each other's internal implementations. A uniform interface lets intermediaries interpret messages, resource representations hide storage decisions, and client-held interaction context makes an individual request understandable on its own. These constraints trade specialized efficiency for visibility and independent evolution.

Caching can avoid repeated communication but introduces stale data. Layers can isolate components and share policies but add hops. REST is a chosen set of trade-offs, not a promise that any HTTP service is fast, reliable or secure.

## Resources and representations are different

A **resource** is a conceptual target, such as an order. Its URI identifies it; a **representation** is information about its current state in a selected media type. The same order might have JSON and HTML representations without exposing its database row or storage location.

The client submits a representation or follows a documented control to request a transition. The server validates authorization and domain invariants before changing resource state. Naming a route `/orders` is a useful convention, while pluralization itself is not a REST constraint.

## The constraints work together

| Constraint | Mechanism | Trade-off / boundary |
| ------------------------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Client-server | Separate presentation concerns from resource/service implementation | Independent evolution still needs a stable external contract |
| Stateless | Each request carries the context needed to understand it | Repeated context can increase transfer size; resource state remains on the server |
| Cache | Identify when equivalent responses may be reused | Freshness and access scope determine whether reuse is correct |
| Uniform interface | Resources, representations, self-descriptive messages and hypermedia | Specialized operations may require more explicit modeling |
| Layered system | Components interact through their adjacent layer | Proxies/gateways can add latency and failure modes |
| Code on demand, optional | Transfer executable code to extend a capable client | Client policy and visibility constrain its use |

Stateless does not mean “no database”, “no durable idempotency records” or “JWT required”. Server-held conversational session context is a different state-management trade-off. A token format alone cannot prove stateless behavior, and a stateless interface still needs current authorization and domain state.

## Trace an order representation and transition

The following JSON is an illustrative application media contract, not a standardized meaning assigned to `_links` by JSON:

```json
{
  "id": "42",
  "state": "pending",
  "totalCents": 1250,
  "version": 7,
  "_links": {
    "self": { "href": "/orders/42", "method": "GET" },
    "cancel": { "href": "/orders/42/cancellation", "method": "POST" }
  }
}
```

The client understands the media type's link relation and follows `cancel` instead of constructing the target URI from assumptions. The server checks the caller and the current order state when the request arrives. If another writer shipped the order meanwhile, the control the client saw is stale; reject or reconcile the transition according to the contract. Omitting a link does not replace server authorization.

After cancellation, the next representation contains state `cancelled` and omits the cancellation control. Resource state stayed on the server; the request still carried its authentication and expected state/version. The client's application flow advances through meaningful response controls, rather than a hardcoded list of paths alone. That is **hypermedia as the engine of application state (HATEOAS)**.

## Uniform messages let HTTP infrastructure participate

For HTTP implementations, methods express operation semantics, Content-Type identifies representation format, statuses describe general outcomes and headers specify relevant conditions. GET should not perform a requested destructive action. PUT describes replacement under its contract; it is not a universal synonym for “merge arbitrary body fields”. PATCH may or may not be idempotent depending on its operation.

Use suitable validators for conditional reads and writes. A strong If-Match write precondition must be checked with the update atomically in authoritative storage; comparing an old ETag and writing later can lose concurrent changes. A 304 is a conditional read result with no representation body, not a generic write-conflict response.

Cacheability can be indicated by explicit directives or protocol rules. Personal responses need intentional private/no-store policies according to the use case; a public product response may permit shared reuse under a freshness policy. A cache hit does not eliminate authorization requirements for private data. The detailed mechanisms live in [HTTP Methods](../02-http-mechanics/20.3.2.01-http-methods.md), [Status Codes](../02-http-mechanics/20.3.2.02-status-codes.md) and [HTTP Caching](../02-http-mechanics/20.3.2.04-http-caching.md).

## Applying the style to domain decisions

An ecommerce product catalog has reusable representations and bounded collection reads. Checkout creates an order or payment operation with durable retry identity and current price/inventory checks. A social feed may have a live cursor and mutable visibility rules; pagination does not automatically produce a snapshot. A banking transfer should be a durable business operation with balanced local changes and explicit handling of remote uncertainty.

An operation-oriented HTTP API can be a valid design even when it does not satisfy every REST constraint. Describe it accurately instead of forcing every workflow into generic CRUD or claiming that any noun route is fully RESTful. JSON is optional; REST predates today's JSON API conventions and is not simply a historical replacement for SOAP.

## Mistakes and best practices

Map allowed inputs into domain commands rather than spreading a request body over an ORM entity. Bound collections, choose error and authorization contracts, test stale versions and repeat writes, and keep representations separate from private storage fields. Document the media/control semantics if clients are expected to follow hypermedia; unexplained links alone do not deliver independent evolution.

Use the constraints as reasoning tools. They do not substitute for security, resource budgets, observability or measured performance. A layered gateway can help apply policy, while every domain service still needs the authority appropriate to its trust boundary.

## Summary

REST constrains interactions to support visible messages, resource representations and independent evolution. Its uniform interface includes hypermedia; practical HTTP semantics remain useful even for APIs that deliberately use a less complete resource-oriented contract.

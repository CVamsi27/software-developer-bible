# API Versioning

Trace two contracts over one domain model. Version 1 represents a display name as `name`; version 2 exposes `displayName`.

## Definition

API versioning lets a client choose between externally different contracts while the provider supports their migration. It does not make a breaking change harmless; it gives the old and new behavior identities and a governed transition window.

> **Textbook Definition:** API versioning identifies distinct external contracts so consumers and providers can evolve on different schedules. Compatibility testing, deprecation and retirement policies govern whether supported consumers remain functional during that evolution.

## First Principles

A mobile installation or partner integration can outlive many server releases. The server cannot atomically upgrade every client. If a response renames `name` to `fullName`, an old reader can fail even though the underlying database migration succeeded.
Either preserve the old behavior or offer an opt-in incompatible replacement with a migration path.

Compatibility includes semantics, not just parseable JSON. Changes to units, enum values, ordering, defaults, nullability, errors, rate limits or authorization can change clients' behavior. A new optional field is often compatible with tolerant readers, but not with every strict validator or generated client.

## 1. Trace two contracts over one domain model

Version 1 represents a display name as `name`; version 2 exposes `displayName`. Both adapters use the same domain record. The executable Node.js example below has no database or authentication and demonstrates only path selection and representation mapping.

```javascript
import { createServer } from 'node:http';
const user = { id: '42', displayName: 'Ada' };
export const server = createServer((request, response) => {
  const path = new URL(request.url, 'http://localhost').pathname;
  if (request.method !== 'GET') {
    response.writeHead(405, { Allow: 'GET' }).end(); return;
  }
  const match = /^\/api\/v([12])\/users\/42$/.exec(path);
  if (!match) { response.writeHead(404).end(); return; }
  const version = match[1];
  response.setHeader('Content-Type', 'application/json');
  response.setHeader('Cache-Control', 'no-store');
  if (version === '1') {
    const deprecatedAt = new Date('2026-10-01T00:00:00Z');
    response.setHeader('Deprecation', `@${Math.floor(deprecatedAt.getTime() / 1000)}`);
    response.setHeader('Sunset', new Date('2027-04-01T00:00:00Z').toUTCString());
    response.setHeader('Link', '</api/migration>; rel="deprecation"');
    response.end(JSON.stringify({ id: user.id, name: user.displayName }));
  } else {
    response.end(JSON.stringify({ id: user.id, displayName: user.displayName }));
  }
});
server.listen(3000);
```

`GET /api/v1/users/42` still returns `name` after version 2 ships. `GET /api/v2/users/42` returns `displayName`. The old version's headers describe a sample lifecycle policy; they do not redirect it to an incompatible response. The migration documentation URI is illustrative and must exist in a real API.
Unknown paths/versions return the defined 404 in this fixture rather than silently selecting the newest version.

In production, version-specific request/response adapters can share domain services. Avoid copying payment or authorization logic into each router, but do not let a “shared” serializer silently change the supported old contract. Database expansion/backfill/contraction must preserve both adapters until retirement.

## 2. Choose one clear selection policy

| Selection | Example | Operating boundary |
| ----------------- | ----------------------------------------- | -------------------------------------------------------------------------------- |
| URL path | `/api/v2/users/42` | Visible and normally part of URL cache keys; keep links/pagination version-aware |
| Query parameter | `/api/users/42?version=2` | Validate the whole value; caches/proxies must preserve it |
| Custom header | `API-Version: 2` | Define missing/unsupported values and vary relevant caches on that header |
| Media negotiation | `Accept: application/vnd.example.v2+json` | Correctly parse alternatives/quality values and emit matching Content-Type/Vary |

Header versioning is not inherently wrong or impossible to test. A regex that finds one `v2` substring is not a complete Accept parser. Query arrays, malformed values and contradictory selectors need a documented rejection/precedence policy.
Supporting every strategy at once adds ambiguity; use one clear public contract unless there is an explicit migration need.

The API contract identifier, OpenAPI `info.version`, application build version and package semantic version can differ. A semantic major/minor/patch scheme can describe releases without forcing new route versions for each patch. Publish what each identifier means.

## 3. Deprecation and sunset describe different events

**Deprecation** says a contract is discouraged and should be migrated away from. Under RFC 9745, the Deprecation header uses a structured-field date such as `@1790812800`, not the old boolean `true` examples. A Link relation can point to deprecation documentation.

**Sunset** announces the expected time a resource will become unavailable, using an HTTP-date under RFC 8594. It is not an ISO-date-only string and is not an absolute uptime promise. Neither header alone migrates clients. Communicate scope, change rationale, examples, deadline and support contact through the channels your consumers actually use. If browsers must read these headers cross-origin, expose them through the relevant CORS policy.

## 4. A migration must preserve a usable old path

1. Identify affected consumers and define old/new behavior with fixtures, including errors and security rules.
2. Publish the replacement and migration guide. Test adapters and database changes against both contracts.
3. Observe version usage by bounded route/client categories. Find unresolved partners and clients instead of equating low traffic with no dependency.
4. Announce deprecation and sunset with enough lead time for the actual support policy.
5. Retire deliberately, using a documented response such as 410 when appropriate. Do not silently reinterpret an old write as the new contract.

A redirect can be appropriate for a moved compatible resource. It is not a general solution for incompatible versions: clients may follow it and receive a shape they cannot understand. Method-preserving redirects still do not prove semantic compatibility.
Cache mappings and payloads by selected version and authorized representation.

## Decisions and mistakes

Prefer a compatible addition when it meets the requirement; version an incompatible replacement only when its support cost is justified. There is no universal “two or three versions” maximum or retirement traffic percentage. Scope the window to client lifetime, security maintenance and organizational commitments.

Common failures are permissive partial-number parsing, conflicting selectors, exposing new semantics through an old serializer, stale SDKs, forgotten webhook event versions and obsolete versions with unpatched authorization. Keep contract tests, upgrade examples, deprecation usage evidence and rollback plans together.

## Summary

Versioning selects a contract; compatibility and migration make that selection useful. Preserve supported behavior, keep version negotiation and caches consistent, publish valid lifecycle signals and retire old clients through an evidence-based policy.

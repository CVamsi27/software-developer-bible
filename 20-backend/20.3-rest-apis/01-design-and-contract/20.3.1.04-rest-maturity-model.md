# REST Maturity Model & API Versioning

> **TL;DR:** **The Richardson Maturity Model is a precision tool, not a scorecard: it separates HTTP-as-transport from HTTP-as-application-protocol.** Level 1 gives you resources instead of a single endpoint, level 2 adds real methods and honest status codes, level 3 adds hypermedia controls — and for most internal APIs level 2 with disciplined semantics is the pragmatic target, because HATEOAS costs more client complexity than it returns. Versioning follows from the same reasoning: prefer additive, backward-compatible change, negotiate through media types, and treat a breaking change as a new major version with a published deprecation window.

---

## First Principles

The Richardson maturity model is derivable from "how much of HTTP are you actually using?":

1. **Level 0 — one endpoint, POST everything.** You're using HTTP as a tunnel; the protocol carries no meaning, so nothing generic (caches, proxies, monitoring) can help you.
2. **Level 1 — resources.** Multiple URIs give the platform *handles* to act on and clients something cacheable and linkable.
3. **Level 2 — methods + status codes.** Now the protocol carries semantics: GET is safe and cacheable, 4xx vs 5xx distinguishes blame. Most "REST" APIs live here — correctly.
4. **Level 3 — hypermedia (HATEOAS).** Clients discover transitions from responses instead of hardcoding URIs — the only level where clients survive server redesign uncoupled. It's rarely worth its cost; knowing *why* is the senior signal.

---

## Definition

The **Richardson Maturity Model** is a four-level ladder describing how much of HTTP's design a "REST" API actually uses. It exists to make an argument precise: *most APIs called REST are level 2, and level 3 is rarely worth it.*

```text
level 0  The Swamp of POX   one URL, one verb (POST /api)  — "RPC over HTTP"
level 1  Resources          many URLs (/orders/42)         — many nouns, still one verb
level 2  HTTP Verbs         GET/POST/PUT/PATCH/DELETE      ← status codes + safe/idempotent
                                                             semantics (where production lives)
level 3  Hypermedia (HATEOAS) responses carry links to the  — the client discovers
                             next available transitions        transitions, not URLs
```

Three facts define how to use the model:

1. **The levels are cumulative capabilities, not a quality score** — level 2 is the target for essentially every public API because it is the level at which HTTP's contract (`GET` safe, `PUT`/`DELETE` idempotent, status codes meaningful, caching by `ETag`) pays off.
2. **Level 3's real cost is discoverability vs. tooling** — HATEOAS buys evolvability (clients follow links, so URLs can move) at the cost of payload size, harder caching, and clients that still hardcode paths in practice. It is appropriate where a generic client must navigate an evolving workflow, not for a mobile app with a compiled SDK.
3. **The model is about the *interface*, not the data model** — an API can be level 2 while its internals are not resource-shaped (a search endpoint, a batch endpoint, and an RPC-style action like `POST /orders/42/cancel` are all legitimate; the distinction is whether the URL names a state or an operation).

Versioning sits adjacent to the model and follows from it: if the interface is resources + verbs, breaking changes to either need an explicit strategy — **URI versioning** (`/v2/orders`, explicit, easy to route), **header/media-type versioning** (`Accept: application/vnd.api.v2+json`, purer, harder to test), and **additive evolution** (no version bump when the change is backward-compatible), with deprecation handled by a published timeline, `Sunset` headers, and observability on which clients still call the old surface.

## Richardson Maturity Model

**What is it?** A framework for classifying REST APIs from "not REST at all" (L0) to "fully RESTful" (L3). L0: single URI, single method, everything in the body. L1: multiple resources (different URIs for different things). L2: proper HTTP verbs (GET reads, POST creates, PUT updates, DELETE removes). L3: HATEOAS — responses include links to related resources, so the client doesn't need to hardcode URLs. In practice, most "REST" APIs are L2 — L3 (HATEOAS) is rare because the added complexity rarely justifies the benefit.


| Level | Name | Description | Example |
| ------ | ------------ | --------------------------------------------- | ------------------------------------------------ |
| **L0** | Swamp of POX | Single URI, single HTTP method, XML/JSON body | `POST /api` with `{ "action": "getUsers" }` |
| **L1** | Resources | Multiple URIs for different resources | `GET /users`, `POST /appointments` |
| **L2** | HTTP Verbs | Proper use of GET/POST/PUT/PATCH/DELETE | `GET /users/123`, `DELETE /appointments/456` |
| **L3** | HATEOAS | Hypermedia links in responses | Response includes `_links` for related resources |

### L3 HATEOAS Example
```json
{
  "id": "apt-123",
  "status": "scheduled",
  "scheduledAt": "2024-03-15T10:00:00Z",
  "_links": {
    "self": { "href": "/appointments/apt-123", "method": "GET" },
    "cancel": { "href": "/appointments/apt-123/cancel", "method": "POST" },
    "reschedule": { "href": "/appointments/apt-123/reschedule", "method": "POST" },
    "patient": { "href": "/patients/pat-456", "method": "GET" },
    "clinician": { "href": "/clinicians/doc-789", "method": "GET" }
  }
}
```

## API Versioning Strategies

### URL Versioning
```typescript
// Version in URL path (most common)
// GET /api/v1/appointments
// GET /api/v2/appointments

@Controller('api/v1/appointments')
export class AppointmentsV1Controller {
  @Get()
  findAll(): AppointmentV1[] { ... }
}

@Controller('api/v2/appointments')
export class AppointmentsV2Controller {
  @Get()
  findAll(): AppointmentV2[] { ... }
}
```

**Pros:** Clear, explicit, easy to route  
**Cons:** URL pollution, duplication across versions

### Header Versioning
```typescript
// Version in Accept header
// Accept: application/vnd.docita.v1+json
// Accept: application/vnd.docita.v2+json

@Get()
@Header('Content-Type', 'application/vnd.docita.v2+json')
findAll(@Headers('accept') accept: string): Appointment[] {
  const version = accept.includes('v2') ? 2 : 1;
  return this.service.findAll(version);
}
```

**Pros:** Clean URLs, content negotiation  
**Cons:** Harder to test in browser, less visible

### Query Parameter Versioning
```typescript
// Version in query parameter
// GET /appointments?version=2

@Get()
findAll(@Query('version') version: string): Appointment[] {
  return this.service.findAll(parseInt(version) || 1);
}
```

**Pros:** Easy to implement, visible in URL  
**Cons:** Cache-busting issues, pollutes query string

### Versioning Strategy Comparison
| Strategy | Cache | Discoverability | Complexity | Recommended |
| ------------------- | ------ | --------------- | ---------- | ----------------- |
| URL path | Easy | High | Low | Most projects |
| Header | Medium | Low | Medium | API-first teams |
| Query param | Hard | Medium | Low | Quick prototyping |
| Content negotiation | Medium | Low | High | Mature APIs |

## Deprecation Strategy

```typescript
// NestJS deprecation decorator
@Get('v1/appointments')
@Deprecated('Use /api/v2/appointments instead')
findAllV1(): AppointmentV1[] { ... }

// Response headers for deprecation
@Get('v1/appointments')
@Header('Deprecation', 'true')
@Header('Sunset', 'Sat, 01 Jan 2025 00:00:00 GMT')
@Header('Link', '</api/v2/appointments>; rel="successor-version"')
findAllV1(): AppointmentV1[] { ... }
```

### Deprecation Timeline
```markdown
## API Deprecation Process
1. **Announce** (3 months before): Add `Deprecation` header, log usage
2. **Monitor** (2 months): Track v1 usage, identify consumers
3. **Notify** (1 month): Direct email to high-volume consumers
4. **Sunset** (day 0): Return 410 Gone with migration guide
5. **Remove** (1 month after): Remove v1 endpoints
```

## Versioning in Practice (Docita)

```typescript
// Docita API versioning strategy
const apiVersioning = {
  strategy: 'URL path versioning',
  baseUrl: '/api/v1',

  // What triggers a major version bump:
  majorBumps: [
    'Breaking change to response shape',
    'Removing a field',
    'Changing field type',
    'Changing authentication mechanism',
    'Changing error response format'
  ],

  // What does NOT trigger a version bump:
  minorChanges: [
    'Adding a new optional field',
    'Adding a new endpoint',
    'Adding a new query parameter',
    'Adding a new header'
  ],

  // Deprecation policy:
  deprecation: {
    notice: '3 months minimum',
    headers: ['Deprecation', 'Sunset', 'Link'],
    monitoring: 'Track v1 usage daily, alert if >1000 requests/day'
  }
};
```

## Interview Tips
- Explain Richardson Maturity Model (L0-L3)
- Know URL vs header vs query parameter versioning trade-offs
- Discuss deprecation strategy and timeline
- Explain what constitutes a breaking change
- Know HATEOAS and when it's useful (rarely in practice)
---
## Summary

1. **Richardson's four levels: POX → resources → methods → hypermedia** — most real APIs sit at level 2
2. **Level 2 (proper verbs + status codes) is the pragmatic target** — level 3/HATEOAS is rarely worth full adoption
3. **The model is a diagnostic, not a scorecard** — use it to name what your API is missing
4. **Method semantics carry safety/idempotency contracts** — that's what makes caching and retries possible
5. **Uniform interface beats bespoke RPC-in-URL** — the actual point of REST

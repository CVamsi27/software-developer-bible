# REST Maturity Model

Trace one appointment through the levels. At level 0, HTTP still provides transport security, routing and other generic facilities; it does not become useless.

## Definition

The Richardson Maturity Model describes which resource, HTTP-method and hypermedia capabilities an HTTP API exposes. It helps explain why two APIs both called “REST” may use very different interfaces.

> **Textbook Definition:** The Richardson Maturity Model classifies HTTP interfaces into cumulative levels: a transport tunnel, resource identification, HTTP method/status semantics and hypermedia controls. It is not a complete test of REST constraints or overall service quality.

## First Principles

A gateway can observe a URI, method, headers and status without understanding arbitrary application fields. Putting every operation behind one POST hides the distinction between reading and deleting from generic HTTP infrastructure. Distinct resource targets and method semantics progressively reveal useful information.
Hypermedia adds controls a client can follow as state changes, provided both sides understand their meaning.

Each addition supports particular behavior, not a guaranteed quality improvement. Security, durability, consistency and resource limits remain outside this ladder.

## How It Works


### 1. Trace one appointment through the levels

| Level | Request shape | What became visible |
| ------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 0, transport tunnel | `POST /api` with `{ "action": "read", "appointmentId": "42" }` | HTTP carries the call; the body defines the operation |
| 1, resources | `POST /appointments/42` with `{ "action": "read" }` | Appointment 42 has a distinct target, while method semantics still hide the read |
| 2, HTTP semantics | `GET /appointments/42` or `DELETE /appointments/42` | Read/delete intent, safe/idempotent methods and meaningful outcomes |
| 3, hypermedia | Read a representation and follow a typed rescheduling control | The server communicates the available next transition and its target |

At level 0, HTTP still provides transport security, routing and other generic facilities; it does not become useless. Level 1 resource URLs do not themselves make unsafe POST reads cacheable. At level 2, apply actual method/cache/precondition rules instead of using GET for mutations or calling every PATCH idempotent.

### 2. Hypermedia describes a changing workflow

```json
{
  "id": "42",
  "state": "scheduled",
  "_links": {
    "self": { "href": "/appointments/42", "method": "GET" },
    "reschedule": { "href": "/appointments/42/rescheduling", "method": "POST" }
  }
}
```

This is an illustrative application media contract. JSON alone does not define these relation names, method annotations or input requirements; clients need those semantics. A client follows the reschedule control, supplies the documented input and handles a conflict if the appointment's state changed since the read.
Once completed, the representation omits the control.

Following controls can reduce dependence on hardcoded URI construction, but it does not make clients independent of field meanings, authentication, media types or workflow rules. Simply appending an unexplained `_links` map is not a complete hypermedia contract. Server-side validation remains authoritative when a displayed link becomes stale.

### 3. Use the model as a diagnostic

A resource-oriented HTTP API can make useful use of level 2 semantics without adopting a fully hypermedia-driven client. A workflow that needs generic navigation may justify level 3; a tightly coordinated client may prefer a documented fixed contract. Explain the trade-off rather than claiming level 3 is always wasteful or level 2 is right for every public API.

The model does not assess statelessness, layered architecture, database transactions, authorization or operations. An RPC or GraphQL interface can be appropriate without being high on this ladder. API versioning is a separate compatibility decision, and a resource operation URI is not automatically illegitimate merely because its domain transition has a verb in its name.

### 4. Mistakes and interview decisions

Keep level 1 examples method-neutral so they do not accidentally demonstrate level 2. Explain what each step enables and what remains unknown. For the appointment case, ask how a client discovers rescheduling, what a cache may reuse and how a stale cancellation is rejected.
A rank is less useful than that concrete trace.

## Summary

The model names visible interface capabilities: transport, resources, HTTP semantics and hypermedia. Use it to diagnose missing semantics and explain client coupling; it does not certify REST compliance, security or production readiness.

# OpenAPI / Swagger Documentation

A generated client can be type-safe and still send a request the server rejects. That happens when the document describes a different wire contract from the deployed implementation.

## Definition

OpenAPI describes an HTTP API in a machine-readable JSON or YAML document. It identifies operations, parameters, request/response schemas and security requirements. Swagger names related authoring and presentation tools, including Swagger UI; those tools are not the specification itself.

> **Textbook Definition:** The OpenAPI Specification defines a language-independent description of HTTP API capabilities. It enables consumers and tools to interpret the declared contract without inspecting its implementation; declaration alone does not enforce runtime behavior.

## First Principles

Independent clients and servers need one description of what each request and response means. A machine-readable schema gives tools a way to interpret that contract consistently. Because the document is still metadata, it cannot enforce behavior or prove that the running service conforms to it.

## 1. The contract feeds tools, then needs runtime evidence

```text
spec-first document OR implementation metadata
                    ↓
              OpenAPI artifact
                    ↓
         docs / client / mock / lint / compatibility diff
                    ↓
       representative requests against real implementation
```

**Spec-first** authoring agrees on the document before implementing it. **Code-first** generation derives it from controllers/types/decorators. Both can work: choose a reviewed authority and test that implementation and consumers match it. Keep the concrete NestJS integration in [Swagger & OpenAPI in NestJS](../../20.2-nestjs/04-quality-and-operations/20.2.4.05-swagger-openapi-nestjs.md).

The `openapi` field selects specification syntax; `info.version` identifies your document or API release policy. Neither changes route versioning. This example uses OpenAPI 3.2.1, the latest published version as of 13 October 2026.
Version 3.2 adds descriptions for the `QUERY` method and other methods through `additionalOperations`, plus per-item schemas for streaming content. Use those features only when validators, gateways and client generators in your stack support them. Nest's native Standard Schema conversion described in the framework chapter targets OpenAPI 3.0, so keep the emitted version honest instead of relabeling generated output.

## 2. A complete small description

Save this JSON as `openapi.json`. It describes one operation, not a running server. Example hostnames are placeholders.

```json
{
  "openapi": "3.2.1",
  "info": { "title": "Books API", "version": "1.0.0" },
  "servers": [{ "url": "https://api.example.com" }],
  "paths": {
    "/books/{id}": {
      "get": {
        "operationId": "getBook",
        "summary": "Read an authorized book",
        "parameters": [{
          "name": "id", "in": "path", "required": true,
          "schema": { "type": "string", "minLength": 1 }
        }],
        "security": [{ "accessToken": [] }],
        "responses": {
          "200": {
            "description": "Book representation",
            "content": { "application/json": {
              "schema": { "$ref": "#/components/schemas/Book" }
            } }
          },
          "401": {
            "description": "Authentication required",
            "headers": { "WWW-Authenticate": {
              "schema": { "type": "string" },
              "description": "Applicable Bearer authentication challenge"
            } }
          },
          "404": { "description": "Book unavailable to this caller" }
        }
      }
    }
  },
  "components": {
    "securitySchemes": {
      "accessToken": { "type": "http", "scheme": "bearer" }
    },
    "schemas": {
      "Book": {
        "type": "object",
        "required": ["id", "title"],
        "properties": {
          "id": { "type": "string", "minLength": 1 },
          "title": { "type": "string", "minLength": 1 }
        }
      }
    }
  }
}
```

The path parameter is required because it is part of the path template. A successful response's `$ref` resolves to Book; the client expects both string fields. Missing title violates the declared 200 schema even if the response is valid JSON.
The security requirement names a declared scheme, but the implementation must still verify credentials and authorize the book.

An example value is illustrative, not validation or a default. `required` controls property presence; OpenAPI 3.1 and 3.2 express nullability through their JSON Schema-compatible types and constructs, rather than OpenAPI 3.0's `nullable` field. Tool support and the declared JSON Schema dialect still matter.

## 3. Security declarations have precise meanings

Two schemes within one Security Requirement Object mean both are required. Two separate objects in the security array are alternatives. An empty requirement object allows anonymous access; operation-level requirements override the top-level declaration.
Confirm the emitted document represents your intended rule, then verify the running endpoint enforces it.

Document cookie/API-key/bearer/OAuth behavior accurately. Swagger UI's Authorize button supplies credentials; it does not install server-side guards. Persisting tokens in the UI is a deliberate security choice.
Publish public API docs when appropriate and restrict private descriptions/UI according to the actual audience; “all production docs must be hidden” is not a universal rule.

## 4. Validate different contracts with different checks

- Parse and validate the OpenAPI structure and references using pinned compatible tooling. Lint descriptions, unique operation IDs and your naming rules separately.
- Compare the committed contract against the target release/base artifact. A syntactic diff is evidence to review, not proof that every semantic change is compatible.
- Test representative success, validation, authorization, conflict and failure responses against the description. Include actual headers and media types, not only the JSON body.
- Generate a client/mock where useful, then run consumer fixtures. Generator-specific signatures differ; do not invent a universal `getOrder` call shape.

Run contract fuzzing against a disposable or appropriately isolated target, because generated requests can execute writes. A successful mock demonstrates the description's behavior, not the real backend's. Generated TypeScript types are not runtime validation of network data, and generated clients can have substantial runtime dependencies and behavior.

## 5. Evolution and operational decisions

Keep operation IDs stable independently of controller renames if SDK compatibility requires it. Define precise DTO/wire types, error variants, bounds and examples. An ORM field addition must not silently become a public schema addition.
Generic envelopes and array responses need explicit descriptions; metadata cannot recover erased generic types automatically.

Serve a reviewed artifact rather than regenerating a different document on each request. Scope versions and audience deliberately, track client/tool support and review regeneration diffs. Avoid fixed universal claims about generation milliseconds, bundle size or “zero runtime cost”; measure the actual tooling and deployment.

## Summary

OpenAPI makes an HTTP contract inspectable by tools. Select a clear authoring authority, declare precise schemas/security/outcomes and verify references, compatibility and real responses; generated documentation and clients alone cannot establish runtime agreement.

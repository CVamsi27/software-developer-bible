# HTTP Methods

Match the method to the operation. POST is broader than creation: it can submit a search, start a job or perform a bulk operation.

## Definition

An **HTTP method** states what a client asks the server to do with the resource identified by a URL. The URL names the target; the method gives the operation its meaning.

> **Textbook Definition:** An HTTP method defines the semantics of an operation on a target resource. Safety concerns intended state changes; idempotence concerns the intended effect of repeated identical requests, rather than equality of their responses.

Consider an appointment API: reading appointment `42`, replacing its editable representation and creating a new appointment are different contracts. Choosing a method tells clients, caches and retrying intermediaries how to treat each request.

## First Principles

A network timeout leaves the client uncertain: the server may have completed the operation before the response was lost. A retry must therefore be evaluated by its **effect**, not by whether the previous response arrived. Read operations also need a contract that lets crawlers and caches retrieve information without requesting a business mutation.

These constraints produce two separate properties:

- **Safe:** the client does not request a state change. Logging, metrics and other incidental effects can still occur.
- **Idempotent:** repeating the same request has the same intended effect as making it once. Responses can differ, and another client may change the resource between requests.

## 1. Match the method to the operation

| Method | Requested operation | Safe? | Idempotent by defined semantics? |
| ------- | ----------------------------------------------------------------------- | ----- | -------------------------------- |
| GET | Retrieve a representation | Yes | Yes |
| HEAD | Retrieve GET-like response metadata without response content | Yes | Yes |
| POST | Process the supplied representation according to the target's contract | No | No |
| PUT | Create or replace the target resource's state | No | Yes |
| PATCH | Apply a described set of changes | No | Depends on the patch operation |
| DELETE | Remove the target resource's association with its current functionality | No | Yes |
| OPTIONS | Describe communication options for the target | Yes | Yes |

POST is broader than creation: it can submit a search, start a job or perform a bulk operation. PUT targets a client-known URL; POST creation commonly lets the server choose the new resource URL. DELETE does not promise physical erasure of every stored record: retention and audit rules belong to the application contract.

GET request content has no generally defined semantics. Prefer query parameters for ordinary retrieval; do not rely on a GET body working across clients, proxies and servers. Safe and idempotent describe protocol semantics, not authorization or automatic cacheability.
[HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html)

## 2. Trace a lost response

```http
PUT /appointments/42 HTTP/1.1
Content-Type: application/json

{"patientId":"p7","startsAt":"2026-10-05T09:00:00Z","status":"scheduled"}
```

Assume this API permits full replacement of those editable fields. The server commits the replacement, but the connection fails before the client receives the response. Sending the same PUT again leaves the same requested state.
Sending an unprotected `POST /appointments` again could create a second appointment.

Repeated DELETE may return `204` first and `404` later. That difference does not invalidate idempotency: both leave the target removed. Likewise, repeated GET can observe different appointment data without requesting any mutation.

#### PATCH depends on what the change means

```json
{"status":"cancelled"}
```

A contract that interprets this as “set status to cancelled” is idempotent. A custom patch meaning “increment visitCount by one” is not. JSON Patch operations must also be evaluated individually: adding to an array can repeat a side effect.
State the patch media type, missing-field behavior, allowed fields and atomicity; do not pass an arbitrary request body directly into a database update.

PUT replacement is different from PATCH omission: define what omitted editable fields mean for PUT rather than accidentally implementing a partial update under that method.

#### Protect against another client's update

Idempotency does not prevent lost updates. Suppose two receptionists read version 7, then each edits the appointment. The second write can overwrite the first unless the server checks a precondition.

```http
PATCH /appointments/42 HTTP/1.1
If-Match: "appointment-42-v7"
Content-Type: application/json

{"startsAt":"2026-10-05T10:00:00Z"}
```

The server atomically checks the current version and applies the change. If version 7 is no longer current, return `412 Precondition Failed`; the client reloads and resolves the conflict. The ETag is a representation validator, not an authorization token.

For GET, `If-None-Match` can instead produce `304 Not Modified`, letting the client reuse its cached representation. Cache policy still needs the correct user/tenant scope and `Cache-Control` directives.

## 3. Choose responses that express the outcome

| Outcome | Typical response | Important boundary |
| ------------------------------------------- | ----------------- | ---------------------------------------------------- |
| Resource returned or update result included | 200 | Representation describes the result |
| New resource created | 201 with Location | PUT can also create if that endpoint permits it |
| Work accepted for later processing | 202 | Acceptance is not completion; expose status tracking |
| Success with no response content | 204 | Do not attach a JSON body |
| Conditional GET representation unchanged | 304 | Client reuses its stored representation |
| Method unsupported for this resource | 405 with Allow | Different from a missing resource |
| Business-state conflict | 409 | For example, slot already occupied |
| Supplied precondition failed | 412 | For example, outdated If-Match |

Validation, authentication, tenant authorization and transaction boundaries apply to every method. A method name does not make unsafe implementation code correct.

## 4. Make retries an explicit application contract

For payment or appointment-creation POST requests, an **idempotency key** can identify one logical operation across retries. A durable implementation scopes the key to the actor/tenant and operation, checks a request fingerprint, claims concurrent ownership atomically and stores a reproducible outcome. An in-memory Map cannot coordinate multiple API instances or survive a restart.

Use bounded retries for transient failures, with backoff and jitter. A timeout is an unknown result, not proof of failure; validation errors usually require a changed request. The full durable algorithm belongs in [Idempotency Keys](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md).

## 5. Practical boundaries

- Keep reads free of requested business mutations. A `GET /delete-user` route breaks the safety contract even if the handler works.
- HEAD should expose the metadata relevant to the corresponding GET without leaking sensitive information or sending content. Framework GET-to-HEAD handling should be understood before adding a separate handler.
- OPTIONS and its Allow information describe supported communication. A browser's CORS preflight is a related OPTIONS exchange; CORS permission is not user authorization.
- Bulk work can use POST with a documented operation contract. Pagination and compression address payload cost, not method correctness.
- Cache GET only when scope, freshness and invalidation permit it. POST caching requires explicit support; safe/idempotent/cacheable are distinct properties.

## Summary

Choose a method by the requested effect. Safety enables retrieval without requested mutation; idempotency makes repeated effects predictable. Conditional writes prevent lost updates, while durable idempotency keys protect logical operations that ordinary POST semantics do not protect.

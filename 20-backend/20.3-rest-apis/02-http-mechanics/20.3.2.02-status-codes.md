# HTTP Status Codes

>
> **Why it matters:** This is a Backend interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

A status code tells the client how the server handled a request. Creating a record, accepting a job and rejecting an outdated edit are distinct outcomes even when all responses contain JSON.

> **Textbook Definition:** An HTTP status code is a three-digit response code whose class and specific semantics communicate the request outcome. Headers and content supply the additional information needed for authentication, retry, caching and application errors.

## First Principles

A browser, gateway or client library may need to react before understanding an application's body. A common outcome vocabulary lets it redirect, validate stored data or request credentials. The code must describe what actually happened; an error body inside an ordinary 200 response can be counted as success by intermediaries.

The broad class alone is insufficient. Retrying an invalid request unchanged will not fix it, and retrying a timed-out payment can duplicate its effect. Method semantics, headers and the application's operation identity determine the next safe action.

## Start with the outcome class

| Class | Meaning | What the client still needs to know |
| ----- | ------------------------------------------------------- | ------------------------------------------------------------ |
| 1xx | Interim information before the final response | Whether to continue sending or switch protocol |
| 2xx | Successful handling under that code's semantics | Creation, completion or acceptance for later work? |
| 3xx | Redirection or conditional reuse | Location, method handling or the cached representation |
| 4xx | Request cannot be fulfilled under the stated conditions | Fix input, credentials, permissions or another precondition? |
| 5xx | Server/gateway failed to fulfill it | Is retry bounded and safe for this particular operation? |

100 Continue can tell a client using Expect that it may proceed with sending content; the final response still determines the request outcome. In HTTP/1.1, 101 confirms an agreed protocol switch, such as a WebSocket upgrade. An ordinary route returning JSON does not implement that switch.

## Pick a precise contract

### Success is not always completion

| Code | Typical use | Boundary |
| ------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------- |
| 200 OK | Return a representation/result | Also valid for successful POST processing that creates nothing |
| 201 Created | Create a resource | Identify it with Location when useful; the target URI can identify it when Location is absent |
| 202 Accepted | Accept asynchronous work | Not a guarantee of completion; provide an authorized status resource |
| 204 No Content | Successful operation with no content | End the response without a JSON body |
| 206 Partial Content | Satisfy an accepted range request | Supply valid range metadata; an unsatisfiable range can produce 416 |

If a report request receives 202, the caller can poll its status, which may later be `failed`. Sending 201 for a completed report or 202 for its queued operation changes what the client can assume.

### Redirects and validation are different exchanges

301 and 308 describe permanent redirection; 302 and 307 describe temporary redirection. 307/308 preserve the request method, while historical 301/302 handling can change a POST into GET. Use a Location header and consider credential forwarding across destinations.

304 is a conditional GET/HEAD result: the stored representation still matches the validator under the request's conditions. It has no response content, and the client combines the received metadata with its stored response. It is not a generic “nothing changed” response for an arbitrary write.

### Client errors describe different repair actions

| Code | Meaning for the caller | Relevant detail |
| -------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------ |
| 400 Bad Request | Request malformed or unacceptable under the API contract | For example, invalid JSON |
| 401 Unauthorized | Valid authentication credentials are absent | Include a WWW-Authenticate challenge for the applicable scheme |
| 403 Forbidden | Server refuses the request | Authentication is not a prerequisite for every possible 403 |
| 404 Not Found | No current representation disclosed | Can also conceal existence from an unauthorized caller |
| 405 Method Not Allowed | Method not supported for this target | Include Allow with supported methods |
| 408 Request Timeout | Server did not receive the request in time | Different from a gateway waiting for upstream work |
| 409 Conflict | Request conflicts with the current resource state | For example, an occupied appointment slot |
| 410 Gone | Access is no longer available and likely permanent | Different from unknown/missing information |
| 412 Precondition Failed | A supplied condition such as If-Match failed | Reload/reconcile the concurrent edit |
| 413 Content Too Large | Content exceeds the accepted limit | Enforce size before buffering a huge upload |
| 415 Unsupported Media Type | Representation format/encoding unsupported | Select an accepted Content-Type |
| 422 Unprocessable Content | Syntax/type understood, instructions invalid | Use consistently for declared semantic validation |
| 429 Too Many Requests | Request exceeds a rate policy | Retry-After can communicate a wait, not a promise of later success |

The application may choose 400 for some validation errors rather than 422. Document the choice and error codes. 402 is reserved by the HTTP specification; a payment API's use of it is a provider contract, not a universal card-decline rule.

### A gateway failure is not the same as an application failure

500 reports an unexpected server condition. 501 concerns unsupported functionality, such as an unrecognized method; it is not a default status for an unfinished business feature. A gateway can use 502 for a bad upstream response and 504 when it cannot obtain an upstream response in time. 503 describes temporary unavailability or overload; Retry-After can state an estimated delay.

None proves whether a remote side effect occurred. Keep provider references and operation identities for reconciliation instead of blindly retrying every 5xx.

## One runnable status trace

Save as `status-demo.mjs` and run with Node 22 or later. This loopback demonstration stores one record in memory, uses no external packages and does not implement authentication or persistence.

```javascript
import http from 'node:http';
import { once } from 'node:events';
import assert from 'node:assert/strict';

let item = null;
const server = http.createServer(async (req, res) => {
  const send = (status, body, headers = {}) => {
    res.writeHead(status, { ...headers, ...(body === undefined ? {} : { 'Content-Type': 'application/json' }) });
    res.end(body === undefined ? undefined : JSON.stringify(body));
  };
  if (req.url !== '/item') return send(404, { code: 'NOT_FOUND' });
  if (req.method === 'GET') return item ? send(200, item) : send(404, { code: 'NOT_FOUND' });
  if (req.method === 'DELETE') { item = null; return send(204); }
  if (req.method !== 'POST') return send(405, { code: 'METHOD_NOT_ALLOWED' }, { Allow: 'GET, POST, DELETE' });
  if (req.headers['content-type'] !== 'application/json') return send(415, { code: 'JSON_REQUIRED' });
  const chunks = []; let length = 0;
  for await (const chunk of req) {
    length += chunk.length;
    if (length > 1024) return send(413, { code: 'TOO_LARGE' });
    chunks.push(chunk);
  }
  let data;
  try { data = JSON.parse(Buffer.concat(chunks).toString()); }
  catch { return send(400, { code: 'INVALID_JSON' }); }
  if (!data || typeof data.name !== 'string' || data.name.length < 2) {
    return send(422, { code: 'INVALID_NAME' });
  }
  if (item) return send(409, { code: 'ALREADY_EXISTS' });
  item = { name: data.name };
  return send(201, item, { Location: '/item' });
});
server.listen(0, '127.0.0.1'); await once(server, 'listening');
const origin = `http://127.0.0.1:${server.address().port}`;
try {
  for (const [method, body, expected] of [
    ['GET', undefined, 404], ['POST', '{', 400],
    ['POST', '{"name":"A"}', 422], ['POST', '{"name":"Ada"}', 201],
    ['POST', '{"name":"Ada"}', 409], ['GET', undefined, 200],
    ['PUT', undefined, 405], ['DELETE', undefined, 204], ['GET', undefined, 404],
  ]) {
    const response = await fetch(origin + '/item', {
      method, body, headers: body === undefined ? {} : { 'Content-Type': 'application/json' },
    });
    assert.equal(response.status, expected);
    if (expected === 201) assert.equal(response.headers.get('location'), '/item');
    if (expected === 405) assert.equal(response.headers.get('allow'), 'GET, POST, DELETE');
    if (expected === 204) assert.equal(await response.text(), '');
    else await response.arrayBuffer();
    console.log(method, response.status);
  }
} finally { await new Promise((resolve) => server.close(resolve)); }
```

The initial GET finds nothing. Malformed JSON fails before semantic validation; a short name fails without creating a record. Creation returns its location, a repeat conflicts, and deletion sends no content. The Map-like in-process state and synchronous claim here do not establish distributed uniqueness; a real database constraint owns that rule.

## Common Mistakes and Best Practices

- Send required headers before ending the body. Setting Retry-After after `res.json()` is too late.
- Register Express error middleware after routes and forward unexpected failures. JavaScript cannot use multiple typed catch clauses.
- Return safe application codes/details and correlate server diagnostics; keep credentials and internal stack/SQL out of public errors.
- Treat 401/403/404 as policy choices with a consistent existence-disclosure boundary.
- Support range requests through a validated parser and complete streaming/error contract; returning arbitrary byte bounds with 206 is insufficient.
- Document acceptance, completion and retry separately. Rate and overload responses may be retryable, but writes still need duplicate-safe operation identities.
- A WebSocket upgrade is handled through the server's upgrade mechanism and adapter. An ordinary Express GET route does not automatically perform it.

## Summary

Return the status that matches the actual outcome, together with its headers and safe application details. Creation, asynchronous acceptance, conflict and conditional reuse have different contracts. A status code helps a client choose its next step; it cannot settle an uncertain remote side effect.

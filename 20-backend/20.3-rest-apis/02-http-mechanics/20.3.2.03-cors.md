# CORS (Cross-Origin Resource Sharing)

>
> **Why it matters:** This is a Backend interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

A page on `https://app.example.com` calling `https://api.example.com` crosses an **origin** boundary: scheme, host and port identify an origin. CORS lets the API tell a browser whether the page may read that response.

> **Textbook Definition:** Cross-Origin Resource Sharing is a browser-enforced protocol in which request/response headers control script access to cross-origin responses. Some requests require a permission-checking preflight; CORS does not authenticate a caller or authorize a business operation.

## First Principles

A browser can carry a user's credentials to several sites. A hostile page must not automatically read another site's private data simply because the user is signed in there. The same-origin policy restricts those reads.

A legitimate frontend may live on another origin, so the server needs a way to permit selected readers. CORS supplies that permission. It governs browser script access, while server authorization governs the operation itself. A request can reach the server even when its response is unreadable to the page.

## Trace the two request paths

### A safelisted request can reach the server directly

A cross-origin GET or a qualifying POST with safelisted headers/content type may be sent without preflight. The browser then checks the response headers. If the API does not permit the page's origin, JavaScript cannot read the response. That check does not undo a POST's server-side mutation.

“Simple request” is shorthand for the relevant safelist rules, not permission to bypass authentication. Cookies alone do not trigger preflight. Other details such as an unsafe header or request body stream can affect eligibility.

### JSON or an Authorization header commonly triggers preflight

```http
OPTIONS /data HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type, Authorization
Vary: Origin
```

The browser checks whether the requested method and header names are permitted. It sends the actual POST only if the preflight passes, then separately checks CORS on the POST response. Preflight ordinarily does not carry the application's cross-origin cookies, so an authentication guard demanding those credentials on OPTIONS can prevent legitimate traffic. Authenticate and authorize the actual operation.

## Credentials and readable headers are separate permissions

| Header/option | Responsibility | Boundary |
| -------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| Access-Control-Allow-Origin | Allow this page origin to read | One exact origin or `*`, not a comma-separated origin list |
| Access-Control-Allow-Credentials: true | Permit credentialed response access | Credentialed mode cannot use `*` as the allowed origin |
| Access-Control-Allow-Methods | Allow preflight's requested method | Does not implement that method or authorize its caller |
| Access-Control-Allow-Headers | Allow preflight's requested headers | Explicitly allow Authorization when used |
| Access-Control-Expose-Headers | Make extra response headers readable to JS | Does not expose Set-Cookie to scripts |
| Access-Control-Max-Age | Cache successful preflight permission | Browser caps differ; choose a revocation/freshness tradeoff |
| Vary: Origin | Distinguish origin-dependent response variants | Required cache-key reasoning when headers vary by origin |

For cross-origin cookies, the frontend typically chooses `credentials: 'include'`, and the API permits the exact origin plus credentials. Cookie SameSite, Secure and browser third-party-cookie policy still apply. CORS permission cannot override them. A manually supplied bearer header and browser-managed cookies have different handling; both require normal server-side verification.

## One runnable Express configuration

Install `express` and `cors`, save this as `cors-demo.mjs`, and run it. Start a local frontend separately on `http://127.0.0.1:3000` and fetch `/data` from its page. `localhost` is a different host from `127.0.0.1` and is not on this allow-list.

```javascript
import express from 'express';
import cors from 'cors';

const app = express();
const allowedOrigins = new Set(['http://127.0.0.1:3000']);
app.use(cors({
  origin(origin, callback) {
    // No CORS header for absent/disallowed origins; this is not authorization.
    callback(null, origin !== undefined && allowedOrigins.has(origin));
  },
  methods: ['GET', 'POST'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  exposedHeaders: ['X-Request-ID'],
  credentials: true,
  maxAge: 600,
}));
app.use(express.json({ limit: '16kb' }));
app.get('/data', (_req, res) => {
  res.set('X-Request-ID', 'demo-1').json({ message: 'hello' });
});
app.post('/data', (_req, res) => res.json({ accepted: true }));
app.listen(3001, '127.0.0.1');
```

```javascript
// Run in the allowed frontend page, not Node/curl.
const response = await fetch('http://127.0.0.1:3001/data', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ message: 'hello' }),
});
console.log(await response.json()); // { accepted: true }
```

Application-level `cors` middleware handles eligible OPTIONS preflights; no extra wildcard OPTIONS route is needed. Exact origin comparison avoids substring/suffix mistakes. A request without Origin gets no CORS permission header and still reaches the handler, as a server-to-server client can. This demo has no authentication, cookies or business mutation. A production route must add those controls independently.

When using different policies for public and credentialed endpoints, scope the middleware deliberately; a global policy can end OPTIONS handling before a later route-specific policy runs. Public anonymous read data can legitimately use `*`. Sensitive credentialed data needs an explicit trusted-origin policy.

## Decisions and failure diagnosis

- Check the actual page origin, requested method/headers, preflight status and final response headers in browser developer tools. A successful curl request does not test browser enforcement.
- Return CORS headers on allowed-origin error responses too, so the page can read an authorized 401 or 422 result. Otherwise it sees only a generic network/CORS failure.
- Keep edge and origin policies consistent. Reflect an origin only after validating it, and ensure shared caches do not reuse an origin-specific header set incorrectly.
- Do not treat `.internal` suffixes, absent Origin or user-supplied headers as proof of service identity. Authenticate server-to-server traffic.
- Do not solve a CORS error with `mode: 'no-cors'`: the result is opaque and cannot be read normally by JavaScript.
- CORS cannot replace cross-site request forgery protection for cookie-authenticated mutations. A safelisted hostile request may still execute.
- Use encrypted transport for sensitive traffic. Different-origin HTTP development can work technically; CORS does not provide encryption.

## Summary

CORS grants a browser page access to selected cross-origin responses. Preflight gates some requests, while other requests reach the server before the read permission is checked. Set exact credentialed origins, headers and cache variants deliberately, and keep authentication, authorization and CSRF defenses in their own boundaries.

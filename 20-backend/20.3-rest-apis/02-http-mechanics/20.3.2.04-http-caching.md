# HTTP Caching Strategies


## Definition

An HTTP cache stores a response so a later request can reuse it. A public product description may be reusable across users; a private account balance needs a different policy. The server states who may store a response, how long it remains fresh and how a stale copy can be checked.

> **Textbook Definition:** HTTP caching reuses stored responses according to method, status, cache-key, freshness and validation rules. Cache-Control governs reuse policy, validators support conditional requests and Vary identifies request fields that select different representations.

## First Principles

Retrieving the same representation repeatedly can repeat transfer, serialization and database work. A stored copy avoids some of that work, but it can disagree with the origin after a change.

A safe design must answer three questions: which requests select the same representation, how long a copy is acceptable without checking, and how to check whether it remains current. Identity, freshness and validation are distinct; an ETag does not make a private response safe to share.

## Trace freshness before validation

```text
First GET -> cache miss -> origin 200, body, ETag, freshness policy -> store
Later GET while fresh -> reusable cached body, without contacting origin
Later GET when stale -> conditional request with stored validator
  origin unchanged -> 304 plus metadata -> reuse stored body
  origin changed   -> 200 plus new body/validator -> replace stored response
```

A fresh cache can serve a conditional request itself when its rules permit; ordinary fresh reuse is not inherently a 304 exchange. A 304 has no response content and relies on an existing stored representation. Validation saves body transfer, but may still require origin computation to decide whether the representation changed.

Freshness considers the response's age, including time already spent in intermediary caches. `max-age=60` does not mean “60 new seconds each time another cache forwards it.” An Age header communicates accumulated age; transport/clock calculations also participate in the cache's rules.

## Choose storage and freshness deliberately

| Directive | What it controls | Boundary |
| -------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------- |
| `public` | Allows shared storage under the applicable rules | Use only when all allowed readers can receive the shared representation |
| `private` | Restricts storage to private caches | Not encryption or a defense against a malicious browser owner |
| `no-store` | Directs caches not to store this response | Does not retroactively erase older copies or prevent all application logging |
| `no-cache` | Requires validation before reuse | Storage can still occur; it does not mean no storage |
| `max-age=N` | Freshness lifetime in seconds | Stale after the allowed age unless another rule permits reuse |
| `s-maxage=N` | Shared-cache freshness override | Separate from the private browser's max-age |
| `must-revalidate` | Disallows stale reuse once validation is required | Failed connectivity must not silently permit stale reuse under this directive |
| `stale-while-revalidate=N` | Allows bounded stale reuse while refreshing | A freshness/availability choice, not an always-correct default |

A response carrying Set-Cookie is not automatically uncacheable. State its policy explicitly. Responses to Authorization have special shared-cache restrictions; deliberate directives can change them. Do not apply `public` casually to personalized data or assume `Vary: Authorization` alone establishes an authorization policy.

## Validators compare representations

A **strong ETag** represents byte-level identity of the selected representation. A **weak ETag**, prefixed `W/`, permits semantic equivalence without promising identical bytes. Neither is a timestamp or authorization token. A resource-version-derived tag must also account for every change that affects the representation, including serializer/schema changes and negotiation variants.

For GET/HEAD, `If-None-Match` uses weak comparison: if the representation matches, return 304. Conditional writes with `If-Match` use strong comparison. A weak tag cannot protect a byte-sensitive range operation or satisfy an If-Match strong comparison merely because its textual version agrees.

`Last-Modified` supplies a date validator when meaningful; `If-Modified-Since` can reduce retransmission, but second-level timestamps may miss rapid changes. When applicable If-None-Match is supplied, it takes precedence over If-Modified-Since. Use a framework/library that handles lists, `*`, quoting, methods and precedence rather than checking one raw header for string equality.

## A complete conditional-read and write example

Install Express 5 and `fresh`, save as `cache-demo.mjs` and run with Node 22+. The product is anonymous public data in one process. The demo requires exactly one known strong If-Match tag for its full replacement; a production implementation must handle its documented precondition grammar and database transaction.

```javascript
import express from 'express';
import fresh from 'fresh';
import { createHash } from 'node:crypto';
import { once } from 'node:events';

const app = express();
app.use(express.json({ limit: '16kb' }));
let product = { name: 'Book', price: 10 };
const serialize = () => JSON.stringify(product);
const tagFor = (body) => '"' + createHash('sha256').update(body).digest('hex') + '"';

app.get('/product', (req, res) => {
  const body = serialize();
  res.set({
    'Content-Type': 'application/json',
    ETag: tagFor(body),
    'Cache-Control': 'public, max-age=60',
  });
  // Compare the applicable representation validator, independent of reload directives.
  if (fresh({ 'if-none-match': req.headers['if-none-match'] }, { etag: tagFor(body) })) {
    return res.status(304).end();
  }
  res.send(body);
});
app.put('/product', (req, res) => {
  const expected = req.headers['if-match'];
  if (!expected) return res.status(400).json({ code: 'IF_MATCH_REQUIRED' });
  if (expected !== tagFor(serialize())) return res.status(412).json({ code: 'STALE_VERSION' });
  const data = req.body;
  if (!data || typeof data.name !== 'string' || !Number.isFinite(data.price) || data.price < 0) {
    return res.status(422).json({ code: 'INVALID_PRODUCT' });
  }
  // Check and replacement are synchronous here, with no await between them.
  product = { name: data.name, price: data.price };
  res.set({ ETag: tagFor(serialize()), 'Cache-Control': 'no-store' }).status(204).end();
});
const server = app.listen(0, '127.0.0.1');
await once(server, 'listening');
console.log(`http://127.0.0.1:${server.address().port}/product`);
```

This endpoint supports ETag-based read validation; it supplies no Last-Modified validator. The helper checks If-None-Match lists, weak tags and `*` against the known representation. Express's implicit freshness path can treat a client no-cache reload as a full 200; this explicit origin check keeps matching representation validation separate from freshness policy.

The first GET returns the product and its tag. A second GET with that tag in If-None-Match receives 304 and reuses the stored body. A PUT with the current strong tag replaces the product and changes its tag. Reusing the old write tag fails with 412; a later conditional GET with the old tag gets the new body.

In this one process, synchronous check-and-replacement prevents an intervening handler from changing the product between those steps. A database-backed read-then-update with an `await` gap can race. Put the expected version in the conditional UPDATE predicate or use a suitable locked transaction; a precondition checked only in application memory does not prevent lost updates across instances.

## Cache keys must reflect the selected representation

`Vary: Accept-Language` tells a cache that two requests differing in language may need separate stored responses. `Vary: Origin` distinguishes origin-dependent CORS headers; `Vary: Accept-Encoding` distinguishes negotiated content encoding. Multiple variation dimensions can multiply the number of variants, reducing hit rate and increasing storage.

Include tenant/authorization scope in application-cache keys where applicable, and use private/no-store HTTP policy when required. HTTP Vary and an internal Redis key are different mechanisms; setting one does not configure the other.

## Writes and authorization changes challenge cached copies

A successful unsafe request can invalidate applicable stored responses in caches that see it, but it does not purge every related list, another URL, offline browser or independent CDN. Choose a bounded stale window, explicit purge, versioned immutable URL or a combination for those paths. URL fingerprinting can be excellent for immutable assets; it is not inherently bad for cacheability.

Trace a stale-price failure: the cached page advertises 10 while the authoritative price is 12. Revalidating display data improves freshness but does not reserve a price or inventory. The purchase transaction must enforce the actual price/availability contract. Likewise, logout or a new no-store response does not automatically remove every previously stored account representation.

For stale-while-revalidate, define whether accepting a stale result is safe, which cache implements the extension, and how failed refresh affects the next read. A dashboard may tolerate delay; revoked access or an authoritative booking decision usually needs a stricter boundary.

## Best Practices and Performance

Measure hit ratio, response age, validation cost, body bytes, origin load and latency tails for the actual cache/CDN. Cache hits still have lookup/network/rendering costs. No universal thousandfold speedup, one-megabyte limit or fixed edge latency applies to every provider and workload.

Use explicit policies for sensitive data, realistic TTLs for changing public data, correct validators and representation variants. Test changed-state, permission and outage cases as well as the cache-hit path. A high hit ratio is useful only when the results are correct for their readers.

## Summary

Freshness permits reuse without checking; validation checks a stored representation without necessarily retransmitting it. Cache-Control, validators and Vary solve different parts of the contract. Keep personalized responses scoped, make write preconditions atomic and enforce business decisions at the authoritative transaction.

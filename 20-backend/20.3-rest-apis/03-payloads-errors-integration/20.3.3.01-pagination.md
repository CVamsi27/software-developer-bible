# API Pagination

Choose the traversal contract. A **cursor** is the API's continuation token. **Keyset pagination** is one way to implement it: seek after the last returned sort key.

## Definition

Pagination returns a large collection in bounded chunks. A response should tell the client how to request the next chunk; an exact total is optional and should be included only when the product needs it and the cost is acceptable.

> **Textbook Definition:** Pagination partitions a collection result into bounded responses using a continuation rule such as an offset or cursor. Ordering and concurrent mutations determine whether traversing those responses yields duplicates, omissions or a consistent snapshot.

## First Principles

Collections can grow beyond the response's time, memory and rendering budget. A page-size bound limits rows returned, while indexes, projections and timeouts bound the work needed to produce them. A small result does not imply a cheap query.

Requests also happen at different times. Offset positions can shift as rows change; a keyset follows sort values instead, but mutable sort values or filters can still move a row across the continuation boundary. A continuation token alone does not establish a snapshot.

## 1. Choose the traversal contract

| Contract | Useful when | Boundary |
| ------------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------- |
| Offset (`page`, `limit`) | Small administrative lists or direct page-number navigation | Deep skips cost work; positions shift under mutations |
| Keyset behind an opaque cursor | Large ordered feeds, messages or logs | Requires a unique stable order and an index matching the query |
| Snapshot/export job | A reproducible complete dataset is required | Owns snapshot lifetime, retention and resource cost |

A **cursor** is the API's continuation token. **Keyset pagination** is one way to implement it: seek after the last returned sort key. A timestamp-only cursor is keyset pagination too, but it is incomplete when timestamps can tie. A personalized ranking can require a different, versioned continuation contract.

## 2. Trace tied timestamps without skipping a row

Take rows ordered newest first by `(created_at, id)`:

```text
(10:02, 42)   page 1
(10:02, 41)   page 1 → cursor contains BOTH values
(10:02, 40)   page 2
(10:01, 39)   page 2
```

Seeking only `created_at < 10:02` skips row 40. Seeking the pair `(created_at, id) < (10:02, 41)` includes it. Use the same sort direction in the predicate and ORDER BY; both columns are non-null and the pair has a unique tie-breaker.

For PostgreSQL, bind parameters rather than interpolating them:

```sql
CREATE INDEX users_tenant_created_id
ON users (tenant_id, created_at DESC, id DESC);

-- Following page: $1 is the authorized tenant; $2/$3 are the validated key.
-- $4 is the validated page size plus one.
SELECT id, created_at, name
FROM users
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT $4;
```

For the first page, omit the continuation predicate. Keep tenant/visibility filters on **every** page. Preserve the database's full timestamp precision and ID representation in the cursor: converting a microsecond timestamp to a millisecond JavaScript Date can alter the boundary.
Nullable sort keys need an explicit null-placement and seek policy.

The index can support a seek followed by a short scan; selective filters, joins or an unsuitable plan can still do much more work. Inspect the real query plan and test deep pages rather than promising universal O(log n) request cost.

## 3. Validate once, then build the continuation

These TypeScript helpers illustrate strict row limits and the extra-row rule. An API adapter maps validation errors to a documented 400 response; the query layer applies authorized filters and supplies ordered rows.

```typescript
export function parsePageSize(raw: unknown): number {
  if (raw === undefined) return 20;
  if (typeof raw !== 'string' || !/^[1-9]\d{0,2}$/.test(raw)) {
    throw new RangeError('limit must be a positive decimal integer');
  }
  const limit = Number(raw);
  if (limit > 100) throw new RangeError('limit must be at most 100');
  return limit;
}

type Row = { id: string; createdAt: string; name: string };

export function finishPage(rows: Row[], limit: number) {
  if (!Number.isSafeInteger(limit) || limit < 1 || limit > 100 || rows.length > limit + 1) {
    throw new RangeError('invalid page assembly');
  }
  const data = rows.slice(0, limit);
  const hasMore = rows.length > limit;
  const last = data.at(-1);
  const nextCursor = hasMore && last
    ? Buffer.from(JSON.stringify({
        v: 1, sort: 'created-desc', createdAt: last.createdAt, id: last.id,
      })).toString('base64url')
    : null;
  return { data, pagination: { limit, hasMore, nextCursor } };
}
```

Fetch `limit + 1` rows, return at most `limit`, and encode the **last returned** row, not the look-ahead row. Exactly `limit` rows without a look-ahead row does not prove another page exists. An empty page returns an empty collection and null cursor.

`Row.createdAt` is the lossless database timestamp string and `id` is a string to preserve large integers. Before using an incoming cursor, bound its encoded/decoded size, parse it safely, validate its version, sort and key types/ranges, and reject malformed input. Query arrays/objects, `20junk`, zero and excessive limits are invalid rather than silently defaulting or truncating through `parseInt`.

Base64url is encoding, not encryption or authorization. Bind the continuation to the chosen filters, sort, tenant and any snapshot/version contract; reject a token used with an incompatible query. Signing or server-held opaque tokens can prevent tampering when required, but still authorize the caller and scope the SQL query independently.
Return only fields the caller may see.

## 4. Add counts and navigation when the product needs them

An exact total is optional. A `hasMore` flag or next cursor can support traversal without counting all matches. A count and page fetched in separate statements can observe different database states; use an agreed snapshot when they must agree, or document the weaker contract.
Cached totals are estimates with a freshness policy.

Offset navigation can expose first/previous/next links. Generate them from the validated query and preserve its filters; an empty collection should not invent a “last page 0” URL. Set a maximum offset or switch to a cursor/export route when deep page-number access exceeds the resource budget.

For descending keysets, the next/older page uses `<`. Previous/newer traversal needs the opposite predicate and reversed query order, followed by reversing the bounded results for display. State whether a UI displays chat messages chronologically or newest first; the boundary is the last row in traversal order, not whichever endpoint looks oldest on screen.

## 5. Filtering, sorting and field selection share the query contract

Allow-list public filter fields, sort keys/directions and selectable fields. Bind values; SQL identifiers generally require a trusted mapping, not a parameter placeholder containing a user-supplied column name. Add a unique tie-breaker to each supported order.

Index decisions depend on selectivity, workload and write cost. B-tree indexes can serve suitable equality/range/order queries; PostgreSQL trigram indexes can support some substring searches, so `%term%` does not universally imply a sequential scan. JSONB indexing also depends on the exact operator and index class.
Measure the permitted query shapes rather than creating an index for every field without a workload argument.

Sparse field selection reduces payload, but must not expose credentials or private columns. Preserve fields needed by the client's contract and the server's continuation builder. Echo applied sort/filter settings when useful, so rejected or normalized input is visible.

## 6. Real-world decisions and consistency

- **Feed or audit list:** use an immutable order and seek cursor for efficient forward traversal. Newly inserted rows before the cursor normally appear on refresh; deletion and visibility changes can shorten later pages.
- **Editable catalog:** a price/ranking change can move an item across the cursor and cause duplication or omission. Accept that live-view behavior explicitly, deduplicate displayed IDs when useful, or provide a snapshot contract.
- **Chat history:** authorize conversation membership on every request and use a timestamp/ID pair or another unique sequence. Never treat possession of a cursor as membership evidence.
- **Complete export:** a cursor over live data is not a completeness guarantee. Choose a retained snapshot, materialized export or a database-specific consistency strategy with bounded duration.

A `hasMore` result describes the query that just ran. Data may change before the client follows it, so a later empty page can be legitimate. Short pages caused by filtering after a query are harder to interpret; apply visibility filters inside the authoritative query whenever possible.

## 7. Which boundary cases need contract tests?

Test equal sort keys at a page boundary, an empty collection, exactly `limit` rows and `limit + 1`. Reject malformed, oversized or wrong-version cursors and attempts to reuse one with another sort, filter, tenant or conversation. Change rows between requests to verify the documented live-view behavior.
Also verify authorization on every page, allowed field selection, query limits and the worst permitted query plan. These tests separate stable API guarantees from data that may legitimately change between requests.

## Summary

A useful pagination API bounds work, defines a stable traversal order and tells the client how to continue. A cursor preserves that order's full key and query contract; authorization and snapshot consistency remain separate decisions.

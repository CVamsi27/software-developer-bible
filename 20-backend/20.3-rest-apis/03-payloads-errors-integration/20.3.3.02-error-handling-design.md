# API Error Handling & Response Design



## Definition

An API error contract tells a client what failed, what it can do next and how to identify this occurrence for support. The HTTP status expresses the general outcome; stable machine fields distinguish application conditions. Human messages help readers without exposing internal diagnostics.

> **Textbook Definition:** API error handling maps failed operations into documented transport semantics and a machine-readable representation. RFC 9457 defines Problem Details, including problem type, title, status, detail and instance, with application-specific extensions.

## First Principles

A client cannot inspect the server's exception or database. It sees a status, headers and bytes. A changing prose message cannot safely drive a retry or form correction, so the response needs stable identifiers. The server also knows facts the caller must not learn: SQL, tokens, file paths and other users' data. Therefore the public contract and the diagnostic record must be constructed separately.

A failed response does not always mean a failed effect. If a payment provider accepted a charge before a timeout, returning 504 describes the communication failure without establishing whether the charge happened. Retrying safely requires an operation identity and reconciliation, not a more reassuring error message.

## How a failure becomes a response

```text
request → validation / authorization / domain operation
                   ↓ failure
       boundary maps known condition to safe public problem
                   ↓
       HTTP status + headers + problem body
                   ↘ protected diagnostic record, same occurrence ID
```

Keep domain conditions separate from framework exceptions. A missing resource, a version conflict and a database outage have different client actions even if all originate in a repository. Map known failures deliberately; unexpected exceptions become a safe 500. Record enough protected context to investigate, with redaction and access controls rather than indiscriminately logging complete requests.

## Problem Details fields have different jobs

| Field | Meaning | Contract boundary |
| ---------- | ---------------------------------------------- | --------------------------------------------------------------------- |
| `type` | URI identifying the problem class | Clients branch on this or a documented extension, never on prose |
| `title` | Short summary of that class | Stable except for localization |
| `status` | Origin's HTTP status for this occurrence | Advisory in the body; generate it consistently with the actual status |
| `detail` | Safe explanation of this occurrence | Do not put secrets or debugging dumps here |
| `instance` | URI identifying this occurrence | An opaque incident URI avoids copying sensitive request queries |
| Extensions | Application-defined data, such as field errors | Document meaning and limits; clients ignore unknown extensions |

Use `application/problem+json`. `about:blank` means the HTTP status alone defines the type; its title should use the status's standard phrase. A custom type URI should identify your documented condition. A custom JSON envelope can also work, but it needs the same stable semantics and consistent handling across validation, authentication and unknown failures. Do not install two competing global filters with different envelopes.

## A safe mapper you can execute independently

Save this as `problem.ts`. It uses Node.js and has no NestJS dependencies. The domain classes expose only reviewed public details; internal exceptions are never reflected. In an HTTP adapter, set the returned status and media type, then serialize `body`. Generate one request ID at ingress and pass it through logging and this mapper; do not trust an arbitrary incoming ID.

```typescript
import { randomUUID } from 'node:crypto';
import { STATUS_CODES } from 'node:http';

type Fields = Record<string, string[]>;
export class PublicProblem extends Error {
  constructor(
    readonly status: number,
    readonly code: 'RESOURCE_NOT_FOUND' | 'VERSION_CONFLICT' | 'VALIDATION_FAILED',
    readonly publicDetail: string,
    readonly fields?: Fields,
  ) { super(publicDetail); }
}
function isPublicProblem(error: unknown): error is PublicProblem {
  return error instanceof PublicProblem && Number.isInteger(error.status) &&
    error.status >= 400 && error.status <= 599;
}
export function problemResponse(error: unknown, occurrenceId = randomUUID()) {
  const id = /^[0-9a-f]{8}-[0-9a-f]{4}-[1-8][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i.test(occurrenceId) ? occurrenceId : randomUUID();
  const known = isPublicProblem(error);
  const status = known ? error.status : 500;
  const body = known ? {
    type: `https://api.example.com/problems/${error.code.toLowerCase()}`,
    title: error.code.replaceAll('_', ' '), status,
    detail: error.publicDetail,
    instance: `urn:uuid:${id}`, code: error.code,
    ...(error.fields ? { errors: error.fields } : {}),
  } : {
    type: 'about:blank', title: STATUS_CODES[500]!, status,
    detail: 'The request could not be completed.',
    instance: `urn:uuid:${id}`, code: 'INTERNAL_ERROR',
  };
  return { status, contentType: 'application/problem+json', body };
}
console.log(problemResponse(new PublicProblem(422, 'VALIDATION_FAILED',
  'Correct the highlighted fields.', { 'address.postcode': ['Invalid postcode'] })).status);
console.log(problemResponse(new Error('secret database connection')).body.detail);
// 422
// The request could not be completed.
```

This mapper is a boundary example, not a complete exception filter. A real adapter must also handle framework validation failures, preserve required headers such as a 401 authentication challenge, avoid writing after a response has started, and log unexpected exceptions using the same occurrence ID. Only construct `PublicProblem` with vetted messages; wrapping arbitrary `error.message` defeats the boundary.

For nested validation, walk child errors into paths such as `items.0.quantity`, not only the top-level `constraints`. Bound the number and length of returned errors. Never include rejected secret values. Document whether malformed JSON is 400 and semantic field validation is 400 or 422, then apply that distinction consistently.

## Trace a conflict and its recovery

A client edits resource version 7. Another writer commits version 8. The database condition `WHERE id = ? AND version = 7` updates no row, so the API returns the documented stale-version condition (often 412 with `If-Match`, or a domain 409). The client reloads, compares changes and submits a new edit. Blindly replaying the stale edit is not recovery.

For creation retries, a matching idempotency key and request fingerprint should recover the stored operation or response. The same key with a different request is a conflict. Enforce the scoped key atomically in durable storage; a lookup followed by an unprotected insert races. A 409 alone does not prevent duplicate charges.

## Retry decisions depend on the effect

| Condition | Useful client action |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| Invalid field | Correct input; repeating the same request cannot help |
| Expired credentials | Follow the authentication contract; avoid infinite refresh loops |
| Rate limit | Honor a valid `Retry-After` within a total deadline and retry budget |
| Temporary dependency failure | Retry only when the operation is safe or protected by a durable idempotency contract |
| Timeout after a write | Query/reconcile the same operation identity before creating a new effect |

`Retry-After` can contain delay seconds or an HTTP date. It is guidance, not a guarantee that a client will wait or that the next attempt will succeed. Use capped backoff and jitter where appropriate.

## Real-world decisions and mistakes

Document realistic errors in OpenAPI and test their status, headers and body together. Keep codes stable across wording changes. Choose bounded metric labels such as route template and error class; identifiers and arbitrary tenant codes can create unbounded cardinality. Alert on user impact and sustained changes, not every individual 500 or a blanket rule that 404 never matters.

Common failures are returning 200 with a hidden error, exposing framework exception messages, treating an empty or non-JSON upstream body as a parser success, and retrying writes under fresh keys. A support identifier connects records; it is not authorization to retrieve private logs.

## Summary

A useful error contract combines correct HTTP semantics, stable machine identifiers, safe occurrence details and a documented recovery action. Public responses and protected diagnostics share an occurrence ID, while retry safety comes from the operation's effect and durable identity.

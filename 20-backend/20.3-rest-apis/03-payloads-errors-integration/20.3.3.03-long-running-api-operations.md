# Long-Running API Operations (202 Accepted Pattern)

> **TL;DR:** When an API call cannot finish inside a request budget (video transcode, bulk import, report generation, ML training), return `202 Accepted` immediately with a `Location` header pointing at an **operation resource**. The client polls that resource (or receives a webhook/callback) until a terminal state (`succeeded`, `failed`, `cancelled`) arrives. Persist the operation, support idempotent resubmission via an `Idempotency-Key`, expose cancellation explicitly, and represent progress and partial results as data — never by holding the HTTP connection open.
>
> **Why it matters:** This is a senior API design interview staple (Google AIP-151, Microsoft REST Guidelines, Stripe all formalize it). Interviewers probe: what does the response body look like, how do you survive a server restart mid-operation, how does the client know *when* to poll again, and what happens when the client retries the original POST.

## First Principles

Long operations break HTTP's implicit contract, and the fixes all follow:

1. **A request-response call assumes the answer arrives before something times out.** Any operation beyond ~30s violates that assumption at some layer (LB idle timeout, client timeout, connection reset) — no amount of tuning makes 2-hour jobs request-shaped.
2. **The fix is decoupling acceptance from completion.** Return `202 Accepted` + a status resource immediately (`/operations/{id}`); completion is discovered by polling or pushed by callback/webhook. The operation becomes a *resource* — which is the REST way of representing "work in progress."
3. **Idempotency moves to creation.** Since the client can't know if the create-request landed (timeout before response), creation needs idempotency keys; the operation itself needs checkpointing so a crashed worker resumes rather than restarts.

## Definition

A **long-running operation** is work whose duration exceeds acceptable synchronous request latency (typically anything over ~10–30 seconds, or past your load balancer timeout). The **operation resource pattern** turns that work into a first-class REST resource:

```text
POST /videos               →  202 Accepted
Location: /operations/op_01H9X...
Body: { "operation": {...} }        (snapshot of the queued operation)

GET  /operations/op_01H9X  →  200 OK   (status: queued | running | succeeded | failed | cancelled)
DELETE /operations/op_01H9X →  202 Accepted (cancellation requested)
```

The operation resource is **addressable**, **persistent**, and **stateful** — the exact opposite of holding a request thread open for 20 minutes.

## Why Do We Need It?

1. **Infrastructure reality** — Load balancers, proxies (default nginx `proxy_read_timeout` 60s), browsers (~300s), and serverless platforms (API Gateway 29s) all kill long connections before your work finishes.
2. **Failure isolation** — A client disconnect should not cancel or corrupt server-side work; decoupling submission from execution makes retries safe.
3. **Progress visibility** — Users watching a 45-minute export need a progress bar; that requires queryable state (`percent`, `stage`, `etaSeconds`).
4. **Backpressure** — Queued operations expose the true load; you can cap concurrency, shed load, or return `429` at admission instead of dying mid-request.
5. **Retry safety** — The client can safely re-POST with the same `Idempotency-Key`; the server returns the *same* operation rather than duplicating the work.
6. **Multi-channel completion** — Polling suits UIs; webhooks suit machine clients; SSE/streaming suits dashboards. The operation resource is the shared substrate for all three.
7. **Auditability** — Who requested what, when, with which parameters, and how it ended — persisted by design.

## How It Works

### Lifecycle state machine

```text
                    ┌─────────────────────────────────────────────┐
   POST /resource   │          │   client cancels     ┌───────────┐
  ────────────────► │  QUEUED  │ ─────────────────►   │ CANCELLING│
                    │          │                      └─────┬─────┘
                    └────┬────────────────────────────────────────┘                            │ worker observes
                         │ worker picks up                  ▼
                         ▼                            ┌───────────┐
                    ┌─────────────────────────────────────────────┐                      │ CANCELLED │
                    │ RUNNING  │─────────────────────►└───────────┘
                    └────┬────────────────────────────────────────┘
              success    │    failure
                 ┌───────┴────────┐
                 ▼                ▼
           ┌───────────────────────────┐    ┌──────────┐
           │ SUCCEEDED │    │  FAILED  │   ← terminal states carry result / error
           └───────────────────────────┘    └──────────┘
```

Terminal states are immutable and retained for a TTL (e.g., 24 h – 7 days) so late pollers get an answer instead of a 404.

### Submission → polling flow

```text
Client                          API                          Worker
  │  POST /exports               │                             │
  │  Idempotency-Key: k1         │                             │
  │─────────────────────────────►│ persist op QUEUED           │
  │                              │ enqueue job                 │
  │◄────── 202 + Location ───────│                             │
  │       /operations/op_1       │                             │
  │                              │                             │
  │  GET /operations/op_1        │                             │
  │─────────────────────────────►│ 200 {status:"running",      │
  │◄─────────────────────────────│      progress:{42%}}        │
  │         ...poll w/ backoff...│        job executes         │
  │  GET /operations/op_1        │────────────────────────────►│
  │─────────────────────────────►│ 200 {status:"succeeded",    │
  │◄─────────────────────────────│      result:{url,...}}      │
```

### Completion push (webhook variant)

```text
Client subscribes:  POST /webhook-endpoints {url, events:["operation.completed"]}
API finishes op  ─► signs payload (HMAC) ─► POST https://client.example/hooks
                    retries with exponential backoff on 2xx failure (at-least-once)
Client verifies signature + dedupes by operation id (delivery may repeat)
```

Polling and webhooks are complementary: ship polling first (works everywhere), add webhooks for machine consumers, keep the operation resource as the reconciliation source of truth.

### Operation resource schema

```json
{
  "id": "op_01H9XQ2V7K",
  "type": "video.transcode",
  "status": "running",
  "progress": { "percent": 42, "message": "encoding segment 7/16", "etaSeconds": 180 },
  "partialResults": [
    { "index": 0, "status": "done", "url": "https://cdn.example.com/v/seg-0.ts" },
    { "index": 1, "status": "pending" }
  ],
  "request": { "sourceUrl": "https://cdn.example.com/in/master.mov", "preset": "1080p" },
  "result": null,
  "error": null,
  "createdAt": "2026-08-25T10:00:00Z",
  "updatedAt": "2026-08-25T10:03:12Z",
  "expiresAt": "2026-09-01T10:00:00Z",
  "links": {
    "self": "/operations/op_01H9XQ2V7K",
    "cancel": "/operations/op_01H9XQ2V7K/cancel"
  }
}
```

Key decisions baked into this shape:

- `status` is a closed enum; unknown values must be treated as "still running" by tolerant clients.
- `progress.percent` is advisory; `message` is human-readable and safe to log.
- `partialResults` lets chunked work surface value before full completion.
- `result` appears only in `succeeded`; `error` uses your standard error envelope (RFC 7807-style) only in `failed`.
- `links.cancel` makes affordance discoverable (HATEOAS-lite).

## Code Examples

### NestJS controller — submit, poll, cancel

```typescript
// operations/operations.controller.ts
import {
  Body, Controller, Delete, Get, HttpStatus, Param,
  Post, Res, SetMetadata, UseGuards,
} from '@nestjs/common';
import { Response } from 'express';
import { OperationsService, CreateOperationDto } from './operations.service';

@Controller('operations')
export class OperationsController {
  constructor(private readonly ops: OperationsService) {}

  // Generic operation status endpoint
  @Get(':id')
  async status(@Param('id') id: string) {
    const op = await this.ops.get(id);
    // 200 while running, 200 at terminals too — the STATUS differentiates,
    // never a 4xx/5xx for "not done yet"
    return op.toPublicJson();
  }

  @Delete(':id')
  async cancel(@Param('id') id: string, @Res({ passthrough: true }) res: Response) {
    await this.ops.requestCancel(id);
    res.status(HttpStatus.ACCEPTED);
    return { id, status: 'cancelling' };
  }
}

@Controller('videos')
export class VideosController {
  constructor(private readonly ops: OperationsService) {}

  @Post()
  async submit(
    @Body() dto: CreateOperationDto,
    @Headers('idempotency-key') idempotencyKey?: string,
    @Res({ passthrough: true }) res?: Response,
  ) {
    // Idempotent resubmission: same key → same operation, never a duplicate job
    const existing = idempotencyKey && (await this.ops.findByIdempotencyKey(idempotencyKey));
    const op = existing ?? (await this.ops.enqueue('video.transcode', dto, idempotencyKey));

    res!.status(HttpStatus.ACCEPTED);                       // 202 — accepted, not complete
    res!.setHeader('Location', `/operations/${op.id}`);     // where to poll
    res!.setHeader('Retry-After', '2');                     // polite first poll hint
    return op.toPublicJson();
  }
}
```

### Service — persistence + idempotency + cancellation semantics

```typescript
// operations/operations.service.ts
import { Injectable, ConflictException, NotFoundException } from '@nestjs/common';

export type OpStatus = 'queued' | 'running' | 'succeeded' | 'failed' | 'cancelling' | 'cancelled';

@Injectable()
export class OperationsService {
  constructor(
    private readonly repo: OperationRepo,   // Postgres — survives deploys
    private readonly queue: JobQueue,       // SQS/BullMQ/Kafka
  ) {}

  async enqueue(type: string, request: unknown, idempotencyKey?: string) {
    try {
      const op = await this.repo.insert({
        id: newOpId(), type, status: 'queued', request,
        idempotencyKey, createdAt: new Date(),
      });
      await this.queue.send(`ops.${type}`, { operationId: op.id });
      return op;
    } catch (e) {
      if ((e as any).code === '23505') {            // unique violation on idempotency_key
        return this.repo.findByIdempotencyKey(idempotencyKey!);
      }
      throw e;
    }
  }

  async requestCancel(id: string) {
    const op = await this.repo.mustFind(id);
    if (TERMINAL.has(op.status)) return op;          // cancel-after-done is a no-op, not an error
    if (op.status === 'queued') return this.repo.casStatus(id, 'queued', 'cancelled');
    return this.repo.casStatus(id, 'running', 'cancelling'); // worker honors cooperative flag
  }

  /** Called by the worker through checkpoints */
  async heartbeat(id: string, percent: number, message: string, partial?: unknown[]) {
    await this.repo.updateProgress(id, { percent, message, partial });
    const op = await this.repo.mustFind(id);
    if (op.status === 'cancelling') throw new CancelledError(); // worker aborts itself
  }

  async complete(id: string, result: unknown) { await this.repo.casStatus(id, 'running', 'succeeded'); /* set result */ }
  async fail(id: string, err: unknown)      { await this.repo.casStatus(id, 'running', 'failed');   /* set error  */ }
}
const TERMINAL = new Set(['succeeded', 'failed', 'cancelled']);
function newOpId(): string { return `op_${crypto.randomUUID().replace(/-/g, '')}`; }
class CancelledError extends Error {}
```

### Worker with cooperative cancellation + progress heartbeats

```typescript
// workers/transcode.worker.ts
export async function handleTranscode(job: { operationId: string }) {
  const op = await ops.mustFind(job.operationId);
  const segments = splitIntoSegments(op.request.sourceUrl);

  for (let i = 0; i < segments.length; i++) {
    await ops.heartbeat(job.operationId, Math.round((i / segments.length) * 100),
      `encoding segment ${i + 1}/${segments.length}`);
    await encode(segments[i]);                       // throws CancelledError if cancelling
    await ops.appendPartial(job.operationId, i, 'done', urlFor(segments[i]));
  }
  await ops.complete(job.operationId, { playlistUrl: playlistFor(op.id) });
}
```

### Client-side polling with capped exponential backoff

```typescript
async function waitForOperation<T>(location: string, signal?: AbortSignal): Promise<T> {
  let delayMs = 500;
  const maxDelayMs = 10_000;
  for (;;) {
    const res = await fetch(location, { signal });
    if (!res.ok && res.status !== 429) throw new Error(`operation poll failed: ${res.status}`);
    if (res.status === 429) delayMs = Number(res.headers.get('Retry-After') ?? 5) * 1000;

    const op = await res.json();
    switch (op.status) {
      case 'succeeded': return op.result as T;
      case 'failed':    throw Object.assign(new Error(op.error?.title ?? 'operation failed'), { op });
      case 'cancelled': throw new Error('operation cancelled');
      default:          break; // queued | running | unknown → keep polling
    }
    await sleep(delayMs);
    delayMs = Math.min(delayMs * 2, maxDelayMs);     // cap: don't punish the API for long jobs
  }
}
```

## Real-World Use Cases

1. **Media pipelines** — YouTube-style transcodes return an operation id; the processing page polls progress and plays segments as `partialResults` land.
2. **Bulk import/export** — CRM exports of 2M rows produce a downloadable artifact URL; the operation carries `rowsProcessed` counters in progress.
3. **Payments/settlement** — Card capture settles asynchronously; the payment resource exposes an embedded operation mirroring gateway state transitions.
4. **ML training / embedding jobs** — Dataset training takes hours; cancellation must free GPU capacity promptly, hence the cooperative `cancelling` state.
5. **Provisioning** — Cloud providers (Google AIP-151 `google.longrunning.Operations`, Azure `Operation-Location`) create databases/clusters via 202 + operation polling; Terraform waits on exactly these endpoints.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| Holding the request open and returning `200` after 15 minutes | Return `202` + operation resource; respect proxy/LB timeouts |
| `201 Created` for submitted work that doesn't exist yet | `201` implies the resource exists; use `202 Accepted` |
| In-memory operation map lost on every deploy | Persist operations in Postgres/DynamoDB; queue holds only references |
| Client fixed-interval polling every 200 ms for an hour-long job | Exponential backoff with a cap + honor server `Retry-After` |
| Returning `404` once a finished operation is cleaned up during TTL | Return `410 Gone` (or retain terminals longer than typical client lifetimes) |
| Cancel deletes the operation immediately | Move to `cancelling` → `cancelled`; keep the record for audit |
| Retried POST creates a second identical job | Unique constraint on `Idempotency-Key`; return the original operation |
| `progress.percent` computed from wall-clock guesses | Checkpoint real units processed (segments, rows, bytes) |

## Best Practices

1. **Always `202` + `Location`** — the response body may embed a snapshot, but `Location` is the contract every HTTP client understands.
2. **Persist before enqueue** — write the operation row, commit, then publish the job; otherwise a crash between enqueue and persist loses work silently.
3. **Closed status enum, tolerant readers** — servers may add states; clients treat unknown as "in flight".
4. **Heartbeat progress from the worker** — stale progress is worse than none; timestamp every update and let clients show "last updated 2 min ago".
5. **Support BOTH completion modes** — polling as baseline; webhooks (signed, retried, at-least-once) for servers; document both.
6. **Idempotency keys on submission AND cancellation** — network retries happen there most often.
7. **TTL + `expiresAt` on terminals** — garbage-collect old operations, tell clients when results disappear.
8. **Authorize operation access like the parent resource** — `GET /operations/{id}` must verify ownership; operation ids are capability leaks otherwise.
9. **Cap concurrency per tenant** — admission control at enqueue time (`429` early) beats killing running jobs.
10. **Version the result schema** — long-lived operations outlive deploys; `apiVersion` inside the operation snapshot prevents decode errors.

## Performance Considerations

- Status reads are hot: cache `GET /operations/:id` briefly (2–5 s) or serve from a replica; add `ETag` so pollers can send `If-None-Match`.
- Batch progress writes: heartbeats every N units or T seconds, not per item — one UPDATE per row processed kills the primary.
- Webhook fan-out belongs in a queue with per-endpoint rate limiting; never sign+send inline in the completing transaction.
- Terminal cleanup: partition the operations table by month and drop expired partitions instead of mass DELETEs.

## Summary

- Turn slow work into an operation resource: `202 Accepted` + `Location`, closed status enum, immutable terminals.
- Persist operations; queues reference them; idempotency keys make resubmission safe.
- Polling with backoff is the universal completion mode; signed webhooks are the push upgrade.
- Represent progress and partial results as data; implement cooperative cancellation via a `cancelling` state.
- Authorize, cache, and TTL the operation endpoints — they become production traffic magnets.

## Cheat Sheet

| Concept | Description |
| ---------------------------- | -------------------------------------------------------------- |
| `202 Accepted` | Request accepted for processing; completion not guaranteed yet |
| `Location` header | URL of the operation resource to poll |
| Operation resource | Persistent `{id,status,progress,result,error,links}` document |
| Terminal states | `succeeded`, `failed`, `cancelled` — immutable, TTL-retained |
| `Retry-After` | Server hint for next poll; clients also back off exponentially |
| Idempotency-Key | Deduplicates resubmitted POSTs; unique index in the ops table |
| Cooperative cancel | `cancelling` flag checked at worker heartbeats |
| Webhook completion | Signed, at-least-once callback; operation remains reconciler |
| Partial results | Chunk-level artifacts surfaced before overall completion |
| AIP-151 / Operation-Location | Google/Azure formalizations of this exact pattern |

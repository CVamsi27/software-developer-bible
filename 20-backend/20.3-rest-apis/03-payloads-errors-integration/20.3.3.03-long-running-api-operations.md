# Long-Running API Operations (202 Accepted Pattern)

Acceptance is a durable promise. POST /exports → commit operation + dispatch intent → 202 + operation URL

## Definition

A long-running API operation separates accepting work from finishing it. A request starts an export, migration or report and receives an operation ID. The client later reads that operation to discover progress, failure or a result.

> **Textbook Definition:** An asynchronous operation resource represents the durable lifecycle of work whose completion is not returned by the initiating request. Acceptance, execution, cancellation and terminal outcome have distinct states and contracts.

## First Principles

A connection can end before work does. Client, proxy and deployment timeouts differ, and a disconnected caller cannot tell whether the server stopped. Holding a Node.js connection also consumes capacity even though it need not hold a dedicated thread.
Durable operation identity lets both sides resume communication without starting the same work again.

There is no universal duration that requires this design. Use it when completion exceeds your synchronous budget, progress or cancellation matters, or recovery must survive process restarts. Fast bounded reads may remain synchronous.

## How It Works


### 1. Acceptance is a durable promise

```text
POST /exports → commit operation + dispatch intent → 202 + operation URL
                              ↓
                   relay → queue → worker
                              ↓
GET /operations/id ← durable state and result / safe failure
```

Commit the operation and its dispatch intent in one database transaction. The dispatch intent is an **outbox** row: a durable record a relay can publish later. Inserting an operation and then sending to a queue leaves a crash gap that can strand accepted work.
Returning 202 before either is durable makes the acceptance promise weaker than the client expects.

For resubmission, scope an idempotency key to the caller and operation kind. Persist a fingerprint of validated input and enforce a unique key atomically. A repeated matching request returns the same operation; a mismatching fingerprint returns a conflict.
Retain the mapping for the documented retry window and do not catch every database uniqueness error as if it were this conflict.

### 2. The operation resource explains what happened

An illustrative response contract:

```json
{
  "id": "op-42",
  "state": "running",
  "version": 3,
  "progress": { "completed": 20, "total": 100 },
  "createdAt": "2026-10-09T09:00:00Z",
  "updatedAt": "2026-10-09T09:00:05Z"
}
```

The POST returns 202 with a documented `Location` (or a contract-specific operation-location header) and may include `Retry-After`. GET normally returns 200 because reading the status succeeded, even when the operation's state is `failed`. Its safe error field describes the job failure.
A completed operation may contain a result URL or redirect with 303 if that is the published contract. Authorize both operation and result access; use private caching rules for user data and expiring result grants.

| State | Meaning | Permitted next states |
| ------------------------------------ | ------------------------------------------------- | ---------------------------------------------------------- |
| `queued` | Accepted; no worker owns execution yet | running, cancelled, failed |
| `running` | Worker holds a bounded execution lease | succeeded, failed, cancelling; reclaim after lease expiry |
| `cancelling` | Cancellation requested; worker is stopping safely | cancelled, succeeded, failed |
| `succeeded` / `failed` / `cancelled` | Terminal outcome | Normally immutable; correction requires an explicit policy |

A **lease** grants a worker ownership until a deadline. A token or generation lets storage reject writes from an expired owner after a new worker takes over. Lease expiry does not stop a paused process or reverse its remote calls.
Persist checkpoints at boundaries the task can replay safely; the next owner resumes or reconciles using the same operation and effect identities.

### 3. Trace completion and cancellation races

Suppose export `op-42` has finished 20 of 100 records. The worker writes a durable checkpoint only after the corresponding batch is committed. A crash after the checkpoint lets another owner resume at 20.
A crash after a remote effect but before the checkpoint needs reconciliation or a stable remote idempotency key; simply repeating can duplicate work.

Cancellation is a request, not proof of reversal. Atomically change a cancellable operation to `cancelling`; a worker observes it between bounded steps and records `cancelled` after cleanup. If completion commits first, cancellation returns the current completed state.
Keep business compensation separate: cancelling a delivery operation cannot unsend an email already accepted by a provider.

Progress is an estimate unless units and total are stable. Explain whether partial results are committed, recoverable or discarded. Version state updates and prevent stale workers from replacing terminal results; replicas and caches may otherwise show old progress after success.

### 4. A bounded polling client

This executable JavaScript helper requires a Node.js runtime with global `fetch`, `AbortSignal.timeout()`, `AbortSignal.any()` and `node:timers/promises`. It follows one operation URL you obtained from a trusted API; it does not follow arbitrary URLs returned by untrusted data. It handles non-JSON throttling responses before parsing, respects the requested Retry-After wait and imposes a total deadline.
A wait longer than the remaining deadline ends through cancellation; it is not shortened into an early retry.

```javascript
import { setTimeout as sleep } from 'node:timers/promises';

export function retryDelay(value, now = Date.now()) {
  if (!value) return 1000;
  let milliseconds;
  if (/^\d+$/.test(value)) {
    const seconds = Number(value);
    if (!Number.isFinite(seconds)) throw new RangeError('Retry delay is too large');
    milliseconds = seconds * 1000;
  } else {
    milliseconds = Date.parse(value) - now;
    if (!Number.isFinite(milliseconds)) return 1000;
  }
  if (milliseconds > 2147483647) throw new RangeError('Retry delay exceeds timer range');
  return Math.max(250, milliseconds); // never shorten the server's requested wait
}
export async function pollOperation(url, { signal, timeoutMs = 30000 } = {}) {
  const deadlineSignal = AbortSignal.timeout(timeoutMs);
  const combined = signal ? AbortSignal.any([signal, deadlineSignal]) : deadlineSignal;
  for (;;) {
    combined.throwIfAborted();
    const response = await fetch(url, { signal: combined, cache: 'no-store' });
    const delay = retryDelay(response.headers.get('retry-after'));
    if (response.status === 429 || response.status === 503) {
      await response.body?.cancel();
    } else {
      if (!response.ok) {
        await response.body?.cancel();
        throw new Error(`Status read failed: ${response.status}`);
      }
      const operation = await response.json();
      if (operation.state === 'succeeded') return operation.result;
      if (operation.state === 'failed') throw new Error('Operation failed');
      if (operation.state === 'cancelled') throw new Error('Operation cancelled');
      if (!['queued', 'running', 'cancelling'].includes(operation.state)) {
        throw new Error('Unsupported operation state');
      }
    }
    await sleep(delay, undefined, { signal: combined });
  }
}
```

The helper's timeout stops polling; it does not cancel the server job. Its sample timing is a client budget, not an infrastructure limit. Production clients also need credentials, operation-schema validation, appropriate response-size limits and a policy for transient network errors.
Do not parse every 429 as JSON or loop forever on unknown states.

### 5. Choosing how clients learn completion

Polling is simple and can recover after a browser reload. Webhooks suit another server that can durably accept callbacks. Server-sent events provide server-to-browser progress over a live connection, but need reconnection and a durable read endpoint.
WebSockets support bidirectional communication when that complexity is justified. Push transports do not replace the operation's authoritative durable state.

Track queue age, oldest unresolved operation, lease recoveries, completion latency and cancellation delay. Bound retention, result expiry, work size and tenant concurrency. Treat a stuck operation as a recoverable state with an owner and a runbook, not as an invisible queue message.

## Summary

Accept work durably under a stable operation identity, dispatch through a recoverable path and persist owned state transitions. Clients distinguish acceptance from completion, poll within a budget and treat cancellation and unknown remote effects according to their explicit contracts.

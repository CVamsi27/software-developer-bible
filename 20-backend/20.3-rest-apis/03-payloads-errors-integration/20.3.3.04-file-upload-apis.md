# File Upload APIs

Choose the byte path. proxy:  client → API streaming / staging → private storage

## Definition

An upload API authorizes a client to transfer bytes, verifies the resulting object and decides when it may be used. The transfer can pass through the application or go directly to object storage. Completion of the byte transfer is separate from approval for publication.

> **Textbook Definition:** A file upload protocol controls transfer, integrity, metadata and lifecycle of client-supplied binary content. A secure upload boundary combines authorization, resource limits, object identity and content validation before release.

## First Principles

A filename, MIME type and declared size come from an untrusted client. They describe intended bytes without proving what arrived. Transfers can stop halfway, and parsers or scanners can consume far more resources than the compressed input size.
Thus authorization, transport limits, inspection and publication require separate decisions.

A storage grant also has a lifetime. If the holder can overwrite an object after scanning, a clean verdict for yesterday's bytes says nothing about the replacement. Verification and publication must refer to the same immutable object version or another enforced write-once identity.

## How It Works


### 1. Choose the byte path

```text
proxy:  client → API streaming / staging → private storage
 direct: client → private storage, using a bounded grant from API
                                      ↓
                         verify exact object → scan → publish
```

Proxy uploads let the server control streaming limits closely and work with clients that cannot use storage protocols. They consume application bandwidth and connections. Direct upload moves the large transfer away from the API, while the API retains ownership, quota and publication checks.
Scanners may still read the bytes; direct upload does not mean no application component ever touches them.

| Mechanism | What it does | Boundary |
| ------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `multipart/form-data` | Carries named fields and file parts in one HTTP body | Not the same as object-storage multipart upload |
| Presigned storage request | Grants a holder a specific storage action for a limited time | A bearer capability; not inherently one-time |
| Storage multipart upload | Uploads numbered parts and commits an assembled object | Abort abandoned sessions; provider part/checksum rules apply |
| Resumable protocol such as tus | Tracks a durable byte offset across requests | Concurrency and offset mismatch have defined semantics |

### 2. Trace a direct upload safely

1. Authenticate the caller. Validate the allowed type, intended size and quota. Create a pending upload record owned by that caller with a random private object key. Store expected integrity metadata instead of trusting it again at completion.
2. Issue a short-lived grant for that key and method, with supported signed headers and storage policy restrictions. A declared JSON size does not itself constrain a presigned PUT. Enforce actual size and quota at verification; choose a policy-supported size condition when available.
3. The client sends bytes and reports completion. Completion is a request to verify, not evidence that the object exists or is safe.
4. Read storage metadata for the authorized key and exact version. Check actual size and supported checksum semantics; retrieve checksum fields with the provider's required options and permissions. Do not treat an absent checksum as a match.
5. Scan that exact version with bounded resources. If transformation is required, inspect and publish the transformed output under its own immutable identity.
6. Atomically move the upload record to an approved state and serve only that approved version. Delete or expire rejected objects and unfinished sessions according to retention policy.

Amazon S3 presigned URLs can be reused until they expire (or their credentials cease to be valid), and a PUT to an existing key can replace it. A unique staging key alone does not prevent a later overwrite by the same grant. Bind approval and downloads to an immutable version, enforce conditional/write-once behavior supported by your design, or publish a protected copy and stop serving the mutable staging key.
Bucket tags alone are not an access-control policy.

### 3. Checksums prove integrity, not safety

A checksum compares bytes against an expected digest. It does not establish that those bytes are authorized, malware-free or a valid document. Provider multipart checksums and ETags can have different meanings; do not assume every ETag is a SHA-256 or MD5 digest.

For a SHA-256 header requiring base64, encode the digest bytes, not the printable hexadecimal characters:

```javascript
import { createHash } from 'node:crypto';
export function sha256HexToBase64(hex) {
  if (typeof hex !== 'string' || !/^[0-9a-f]{64}$/i.test(hex)) {
    throw new Error('Expected a 64-digit SHA-256 digest');
  }
  return Buffer.from(hex, 'hex').toString('base64');
}
const digest = createHash('sha256').update('hello').digest();
console.log(sha256HexToBase64(digest.toString('hex')) === digest.toString('base64'));
// true
```

### 4. Resuming requires authoritative offsets

In tus, the server reports the current offset with HEAD. A client PATCH supplies `Upload-Offset` and the required content type; an offset mismatch returns 409 without changing the resource. After an interrupted request, query the authoritative offset before continuing.
Persist accepted bytes and offset consistently so a crash cannot claim bytes that were lost.

Two clients cannot safely append to the same file by reading one offset and independently writing. Serialize ownership or atomically check the expected offset; reject stale writers. `Content-Range` alone does not define a complete resumable-upload protocol, and it is not interchangeable with tus or S3's upload-ID/part-number protocol.

For form multipart encoding, a boundary is a delimiter, not a filename:

```text
Content-Type: multipart/form-data; boundary=example-boundary

--example-boundary
Content-Disposition: form-data; name="file"; filename="report.txt"
Content-Type: text/plain

hello
--example-boundary--
```

The wire uses CRLF line endings. Let FormData or a vetted multipart library generate it. When a browser submits FormData, do not manually set Content-Type without the generated boundary.

### 5. Inspection and resource limits

Check extensions and MIME declarations against an allowlist, then sniff and parse the stored bytes using maintained tools. A magic-byte match is only a clue; polyglot files and hostile content can still pass it. Isolate scanning/decoding where appropriate.
Bound upload bytes, decompressed bytes, image pixels, archive members, nesting, processing time and per-tenant concurrent work.

For proxy uploads, configure disk or streaming storage explicitly. Multer's memory storage provides a buffer, not a disk `file.path`. Use random staging names, avoid client path components, handle aborted requests and remove temporary files in a finally/cleanup path.
Small files can legitimately use memory if the total concurrency budget is bounded.

Sharp removes metadata by default unless preservation methods are used; there is no need for an invented `withoutExif()` call. Removing metadata is useful for privacy, but decoding/re-encoding still needs pixel and memory limits. A malware scanner's success is not proof that all downstream renderers are safe.

Serve downloads with intentional MIME type, disposition and `nosniff` policy. A separate origin reduces exposure only if its cookies, authorization, allowed content and browser behavior are designed accordingly. Never assume that an arbitrary separate hostname cannot receive cookies.

## Decisions and operational mistakes

Choose limits from product requirements and measured resource budgets rather than a universal file-size recommendation. Store original filename only as sanitized display metadata. Scope access to ownership on every start, resume, complete and download action.
Apply backpressure; stream where the processor supports it instead of loading every large object into a buffer.

Monitor rejected size/type checks, unfinished sessions, scan queue age, processing failures and temporary-storage usage. Clean up abandoned storage multipart sessions explicitly, and distinguish expired grants from corrupted content so clients know whether to resume or request a new grant.

## Summary

Authorize the transfer, bound its resources and verify the exact stored bytes before publication. Direct grants are reusable capabilities unless constrained otherwise; resumable transfers need authoritative offsets, and checksum or scanning results must remain bound to the object version actually served.

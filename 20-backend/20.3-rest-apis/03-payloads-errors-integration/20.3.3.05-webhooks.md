# Webhooks

Delivery and processing are different steps. producer domain change + outbox

## Definition

A webhook is an HTTP callback: when an event occurs, a producer sends a request to a receiver's registered endpoint. For example, a payment provider tells a shop that a payment succeeded so the shop can update the order without continuously polling.

> **Textbook Definition:** A webhook is an event-driven integration in which a producer delivers event notifications to a consumer-controlled HTTP endpoint. Delivery authentication, acknowledgment, retries and event processing form separate parts of its contract.

## First Principles

The producer and receiver cannot commit one local transaction together. A receiver may store an event and lose its response, so the producer cannot distinguish acceptance from a failed connection. Retrying can therefore deliver the same event again.
Conversely, acknowledging before durable acceptance can lose the event permanently if the process crashes.

A request arriving at the right URL does not prove who sent it. Verification must authenticate the exact bytes and metadata required by the producer's scheme. A valid delivery may still describe an event the application already handled or a state older than one it has seen.

## How It Works


### 1. Delivery and processing are different steps

```text
producer domain change + outbox
             ↓ durable relay, bounded retry
     signed HTTP delivery
             ↓ receiver verifies raw request
     inbox + processing intent committed
             ↓ acknowledge successful acceptance
     worker applies duplicate-safe business transition
```

An **inbox** is a durable record of accepted incoming events. An **outbox** is a durable record of outgoing work to dispatch after a transaction commits. At ingress, commit the event and its processing intent together before returning success.
A Redis SET NX followed by a queue send has a crash gap: recording “seen” before the send can suppress the retry that would recover lost work.

A successful acknowledgment means the receiver accepted responsibility under its contract, not that every downstream effect completed. Keep the ingress path bounded and execute slower work asynchronously. If acceptance fails, return an appropriate non-success response so the producer's backoff has a signal — a 429/503 with `Retry-After` when overloaded, never a 2xx for work you have not durably accepted; retries depend on the producer's documented status and timeout policy.

### 2. Trace a lost acknowledgment

1. Producer sends event `evt-42` saying order 7 was paid.
2. Receiver verifies it and commits its inbox/outbox transaction.
3. The receiver's 2xx response is lost.
4. Producer retries `evt-42`. The receiver finds the durable record, verifies that the payload matches and acknowledges it again without adding new processing work.
5. A worker updates the order and records processing completion in the same database transaction. A worker retry observes that transition already applied.

Deduplicating delivery is not enough for a remote side effect. If processing calls a shipping service and times out, that service may have created a shipment. Use the same durable effect identity for retries and reconcile unknown outcomes.
Different event IDs can also describe the same business fact; guard the business transition or its stable business key where the provider contract requires it.

### 3. A complete custom HMAC byte contract

The following Node.js helper defines **our own example protocol**. It does not implement Stripe, GitHub, Shopify or Slack. A keyed hash (HMAC) proves possession of a shared secret and detects signed-byte changes.
It does not encrypt the body; HTTPS supplies transport protection.

The signed message is `timestamp + '.' + rawBody`. The event ID is inside the signed body, so changing an unsigned header cannot create a fresh deduplication identity. Timestamp seconds and a symmetric five-minute window are this example's explicit policy, not a universal webhook rule.

```javascript
import { createHmac, timingSafeEqual } from 'node:crypto';

function digest(secret, timestamp, rawBody) {
  return createHmac('sha256', secret)
    .update(`${timestamp}.`, 'utf8').update(rawBody).digest();
}
export function signDelivery(secret, rawBody, nowSeconds) {
  if (!secret || !Buffer.isBuffer(rawBody) || !Number.isSafeInteger(nowSeconds)) {
    throw new Error('Invalid signing input');
  }
  return `t=${nowSeconds},v1=${digest(secret, nowSeconds, rawBody).toString('hex')}`;
}
export function verifyDelivery(secret, rawBody, header, nowSeconds) {
  if (!secret || !Buffer.isBuffer(rawBody) || rawBody.length > 65536 ||
      typeof header !== 'string' || !Number.isSafeInteger(nowSeconds)) {
    throw new Error('Invalid delivery');
  }
  const match = /^t=(0|[1-9]\d{0,15}),v1=([0-9a-f]{64})$/.exec(header);
  if (!match) throw new Error('Invalid signature header');
  const timestamp = Number(match[1]);
  if (!Number.isSafeInteger(timestamp) || Math.abs(nowSeconds - timestamp) > 300) {
    throw new Error('Expired or future delivery');
  }
  const supplied = Buffer.from(match[2], 'hex');
  if (!timingSafeEqual(supplied, digest(secret, timestamp, rawBody))) {
    throw new Error('Invalid signature');
  }
  const event = JSON.parse(new TextDecoder('utf-8', { fatal: true }).decode(rawBody));
  if (!event || typeof event.id !== 'string' ||
      !/^[A-Za-z0-9_-]{1,100}$/.test(event.id) ||
      typeof event.type !== 'string' || typeof event.data !== 'object' ||
      event.data === null || Array.isArray(event.data)) {
    throw new Error('Invalid event envelope');
  }
  return event;
}
const secret = 'local-test-only';
const raw = Buffer.from(JSON.stringify({ id: 'evt-42', type: 'order.paid', data: { id: 7 } }));
const header = signDelivery(secret, raw, 1800000000);
console.log(verifyDelivery(secret, raw, header, 1800000001).id);
// evt-42
```

Use a maintained provider verifier for real integrations. Keep secrets in configuration, fail startup if absent, and rotate without dropping valid deliveries: publish the new secret, verify incoming deliveries against both the current and the previous secret during a bounded overlap, then retire the old one. Where the provider versions secrets with key IDs, select the verifier by the delivery's version rather than looping over an unbounded secret set. Count verifications that still use the previous secret so a sender that never migrates is visible, and alert if old-secret use persists past the overlap window. Verify before JSON reserialization: whitespace, key order and Unicode encoding affect bytes.
Constant-time digest comparison requires equal-length decoded inputs; validate encoding first. Clock checks require synchronized time and still do not replace durable deduplication.

The helper validates only the envelope. Before acting, validate the subscribed event type and its specific data schema, tenant/account binding and business authorization. A valid signature does not authorize an arbitrary object identifier in your application's domain.

### 4. Preserve raw bytes before parsing

With Express, install route-specific `express.raw({ type: 'application/json', limit: '64kb' })` before a global JSON parser for that route. With NestJS, configure its documented raw-body support and use the resulting buffer. An object reconstructed with `JSON.stringify(req.body)` is not the original body.

Only after verification and schema checks should the receiver accept the event durably. Keep the success path `verify → await durable acceptance → 2xx`, never `2xx → fire-and-forget queue send`. Authentication rejection and storage failure have different operational meanings; monitor both without logging signing secrets or full sensitive payloads.

### 5. Atomic inbox acceptance in PostgreSQL

This fixture shows the transaction boundary. Save and run it against a disposable PostgreSQL database. It assumes verification already succeeded.
Production parameterizes provider, event ID, fingerprint and payload, then acknowledges only after COMMIT succeeds.

```sql
CREATE TABLE webhook_inbox (
  provider text NOT NULL,
  event_id text NOT NULL,
  payload jsonb NOT NULL,
  processed_at timestamptz,
  PRIMARY KEY (provider, event_id)
);
CREATE TABLE webhook_work (
  provider text NOT NULL,
  event_id text NOT NULL,
  PRIMARY KEY (provider, event_id),
  FOREIGN KEY (provider, event_id) REFERENCES webhook_inbox
);
BEGIN;
WITH accepted AS (
  INSERT INTO webhook_inbox(provider, event_id, payload)
  VALUES ('example', 'evt-42', '{"orderId":7}')
  ON CONFLICT DO NOTHING
  RETURNING provider, event_id
)
INSERT INTO webhook_work SELECT provider, event_id FROM accepted;
COMMIT;
SELECT count(*) FROM webhook_inbox; -- 1
SELECT count(*) FROM webhook_work;  -- 1
```

Run the BEGIN-to-COMMIT block again: both counts remain 1. Concurrent inserts contend on the same unique identity; only the insertion winner creates work. An existing identity still needs a stored-payload/fingerprint comparison: a different authenticated payload under the same ID is a contract violation to investigate, not a new event.
Namespace identities by the relevant provider/account/endpoint scope.

The relay may publish a work row repeatedly. The worker must claim work recoverably and atomically couple local domain changes with completion. Do not hold a database transaction open around a remote HTTP send or assume SKIP LOCKED alone provides ownership after the transaction ends.
The [transactional outbox](../../20.6-microservices/03-data-and-consistency/20.6.3.06-transactional-outbox.md) owns that delivery mechanism.

### 6. Provider contracts differ

| Provider | Verification and delivery boundary |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stripe | Verify the raw body and `Stripe-Signature` with the endpoint secret. In live mode, automatic retries run for up to three days; sandbox retries are three attempts over a few hours. Events may arrive out of order. Dashboard resend is available for 15 days and CLI resend for 30 days; a manual resend does not cancel automatic retries. |
| GitHub | Verify `X-Hub-Signature-256` against the request body. `X-GitHub-Delivery` identifies a delivery but is not included in that body signature. Failed deliveries are not automatically redelivered; an authorized operator or integration can manually redeliver a delivery from the past three days. |
| Shopify | Verify `X-Shopify-Hmac-SHA256` against the raw body. Deduplicate a delivery with `X-Shopify-Webhook-Id`; use `X-Shopify-Event-Id` to correlate separate deliveries caused by one merchant action. Shopify retries failures up to eight times over four hours; after repeated failure, an Admin API-managed subscription can be removed. |
| Slack Events API | Verify the versioned signature base `v0:timestamp:raw_body` and reject timestamps more than five minutes from local time. Acknowledge within three seconds; failed deliveries are retried up to three times (nearly immediately, then around one and five minutes). The optional Delayed Events setting adds hourly attempts for 24 hours; without it, Slack does not attempt Events more than two hours late. These timing rules are for the Events API; interaction and other Slack APIs have their own contracts. |

Use each provider's current documentation for encoding, secret rotation, retry windows, replay and identity rules. Verify first, then treat headers not covered by that provider's signature as untrusted metadata. An unsigned delivery ID can deduplicate ordinary retries, but it cannot prove freshness or authorize a tenant/resource; bind authorization to the verified event and configured account, and protect effects with business-level idempotency.
Stripe's event creation timestamp is not a reliable total ordering key. For out-of-order events, enforce a versioned state transition or retrieve authoritative current state rather than blindly assigning whichever event arrived last. Retain deduplication records for retry/manual-replay windows and your reconciliation needs.

### 7. Producer retries and destination security

A producer records events with the originating domain change, then retries deliveries within a finite budget. Use stable event IDs, fresh attempt authentication where the protocol requires it, timeouts, capped backoff and jitter. A dead-letter queue records exhausted deliveries for alerting and deliberate replay; it is not an automatic consequence of every queue failure.
Classify permanent endpoint/authentication errors and avoid infinite retries.

A registered callback URL can trigger server-side request forgery: the server is induced to request an internal address. Validate scheme, host, resolved addresses and ports at every attempt, constrain egress, and control redirects and DNS changes. Registration-time string checks alone do not prevent DNS rebinding.
The producer must validate the destination's TLS certificate; requiring a client certificate is a separate mutual-TLS contract.

Webhooks suit server-to-server notifications. Polling suits clients without public ingress. Server-sent events push from server to browser; WebSockets permit two-way messages.
Every push path still needs a recovery/authoritative-state strategy.

## Summary

Authenticate the producer's exact signed bytes, validate the event contract and commit durable acceptance before acknowledgment. Delivery retries, duplicate-safe business effects, ordering, replay retention and destination security require their own explicit boundaries.

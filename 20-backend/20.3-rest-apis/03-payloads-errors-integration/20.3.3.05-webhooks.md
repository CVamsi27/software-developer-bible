# Webhooks

> **"Don't call us, we'll call you" — the inverse of an API.** Instead of polling `/orders/123` every 30s to see if it's shipped, the seller **POSTs to your URL** the moment the order ships. Webhooks are how Stripe tells you a payment succeeded, how GitHub tells you a PR was opened, how Shopify tells you a customer paid. Get them right and the integration is invisible. Get them wrong and the customer blames your product when their webhooks silently drop, replay incorrectly, or arrive out of order with no way to debug.

## TL;DR

- **Webhook** = an HTTP POST that one service sends to a URL you registered, when an event happens. The "reverse API".
- **Three guarantees you must provide**: (1) **delivery** (at-least-once, with retries), (2) **security** (HMAC signature verification, replay protection), (3) **ordering** (best-effort, with idempotency keys so the receiver can dedup).
- **Producer side**: the `event_id`, `timestamp`, `signature`, `retry-with-backoff`, **signed payload** are the five things every webhook must have.
- **Consumer side**: verify the signature, dedup by `event_id`, respond 2xx fast (work async), and **always be idempotent**.
- **Common mistakes**: no signature verification, no idempotency, no retry visibility, no DLQ, response timeout 30s (worker dies), accepting infinite redirects.
- **In interviews: name the delivery guarantee, name the security mechanism, name the consumer's responsibility, name the failure mode.**

---

## Why it matters

Polling is the naive answer. It has 4 problems:
1. **Latency** — you see the change on your next poll, up to N seconds late.
2. **Cost** — N× rate of calls, N× rate of empty results.
3. **Scaling** — at 10K customers polling every 30s, you get 333 req/sec just for "no, nothing changed".
4. **Battery / rate limits** — bad on mobile clients, hits your own rate limit.

Webhooks fix all four. But they introduce new problems: delivery, security, ordering, and debugging. The senior-level question is how to handle each.

## Anatomy of a Webhook

A webhook is a single HTTP POST from the producer to a registered URL. The wire format is usually JSON, but could be anything.

```http
POST /webhooks/stripe HTTP/1.1
Host: api.yourapp.com
Content-Type: application/json
User-Agent: Stripe/1.0 Webhook
X-Webhook-Id: evt_2O5Kq3L8X9nE4
X-Webhook-Timestamp: 1737158400
X-Webhook-Signature: t=1737158400,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
X-Webhook-Event: order.shipped
X-Webhook-Delivery-Attempt: 3
X-Request-Id: 01HQF8XY9V3J2K1N5C0B5V8R7M
Content-Length: 412

{
  "id": "evt_2O5Kq3L8X9nE4",
  "type": "order.shipped",
  "created_at": "2026-01-17T14:30:00.000Z",
  "data": {
    "order_id": "ord_42",
    "tracking": "1Z999AA10123456784",
    "carrier": "UPS"
  }
}
```

The headers are the contract:
- `X-Webhook-Id` — globally unique, **idempotency key**. The consumer dedups on this.
- `X-Webhook-Timestamp` — when the event was created. Used for replay protection.
- `X-Webhook-Signature` — HMAC-SHA256 of the body using a shared secret. The consumer verifies this.
- `X-Webhook-Delivery-Attempt` — which retry this is. Producers should include this for visibility.
- `X-Request-Id` — for tracing. The consumer should propagate this to its own logs.

The body is the event. The producer's `id` field should match the `X-Webhook-Id` header.

## How it works (producer + consumer)

### Producer: emit a webhook

```typescript
import { createHmac, randomUUID } from "node:crypto";

interface WebhookEvent<T = unknown> {
  id: string;
  type: string;
  createdAt: string;
  data: T;
}

async function emitWebhook<T>(url: string, secret: string, event: WebhookEvent<T>) {
  const body = JSON.stringify(event);
  const timestamp = Math.floor(Date.now() / 1000);
  const signature = createHmac("sha256", secret)
    .update(`${timestamp}.${body}`)
    .digest("hex");

  const signatureHeader = `t=${timestamp},v1=${signature}`;

  const res = await fetch(url, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "User-Agent": "YourApp/1.0 Webhook",
      "X-Webhook-Id": event.id,
      "X-Webhook-Timestamp": timestamp.toString(),
      "X-Webhook-Signature": signatureHeader,
      "X-Webhook-Event": event.type,
    },
    body,
    signal: AbortSignal.timeout(10_000), // 10s hard ceiling
  });

  if (!res.ok) {
    // Schedule retry (handled by a queue, not the request itself).
    await scheduleRetry(url, event, attempt + 1);
  }
}
```

### Consumer: verify, dedup, process

```typescript
import { createHmac, timingSafeEqual } from "node:crypto";

const WEBHOOK_SECRET = process.env.WEBHOOK_SECRET!;
const seen = new Set<string>(); // In production: Redis with TTL

app.post("/webhooks/stripe", async (req, res) => {
  // 1. Read headers.
  const id = req.headers["x-webhook-id"] as string;
  const timestamp = parseInt(req.headers["x-webhook-timestamp"] as string, 10);
  const sigHeader = req.headers["x-webhook-signature"] as string;

  // 2. Reject if too old (replay protection — 5 min window).
  if (Date.now() / 1000 - timestamp > 300) {
    return res.status(400).json({ error: "stale webhook" });
  }

  // 3. Verify signature.
  const expected = "v1=" + createHmac("sha256", WEBHOOK_SECRET)
    .update(`${timestamp}.${req.rawBody}`)
    .digest("hex");
  if (!timingSafeEqual(Buffer.from(sigHeader), Buffer.from(expected))) {
    return res.status(401).json({ error: "bad signature" });
  }

  // 4. Deduplicate.
  if (seen.has(id)) {
    return res.status(200).json({ received: true, dedup: true });
  }
  seen.add(id);
  // In production: redis.set(`wh:${id}`, "1", "EX", 86400 * 7) for 7-day window.

  // 5. ACK fast, process async.
  res.status(200).json({ received: true });

  // 6. Hand off to a worker / queue — DON'T block the response.
  await webhookQueue.add("process", { id, event: req.body });
});
```

## The 5 Things Every Webhook Must Have

### 1. Idempotency key

Every webhook must have a globally unique `id` (UUID v4 or producer's prefix + ULID). The consumer **deduplicates by this id**. Without it, retries cause double-processing (double-charge, double-fulfill, double-email).

```typescript
// Producer
const id = `evt_${ulid()}`; // evt_01HQF8XY9V3J2K1N5C0B5V8R7M

// Consumer
const isNew = await redis.set(`wh:${id}`, "1", "NX", "EX", 86400 * 7);
if (!isNew) return; // already processed
```

### 2. Timestamp + signature (HMAC-SHA256)

The standard is `Stripe`-style: `t=<unix>,v1=<hmac-sha256(timestamp + "." + body)>`. The consumer:
1. Reads the timestamp.
2. Rejects if too old (replay window, typically 5 min).
3. Recomputes the HMAC with the shared secret.
4. Compares using **timing-safe equality** (no `===`, no string compare — use `crypto.timingSafeEqual`).

```typescript
const signed = `${timestamp}.${rawBody}`;
const expected = createHmac("sha256", secret).update(signed).digest("hex");

// timing-safe
const a = Buffer.from(received, "hex");
const b = Buffer.from(expected, "hex");
if (a.length !== b.length || !timingSafeEqual(a, b)) {
  return res.status(401).end();
}

// NOT timing-safe — vulnerable to timing attacks
if (received !== expected) {
  return res.status(401).end();
}
```

### 3. Retry with exponential backoff

A producer must retry on:
- Network errors (timeout, connection reset)
- 5xx responses (server error)
- 429 (rate limited — respect `Retry-After`)

**Standard retry schedule (Stripe-style):** attempts at 0s, 5s, 5min, 30min, 2h, 5h, 10h, then give up. Total: 24h window.

```text
attempt 1 → immediate
attempt 2 → +5s
attempt 3 → +5min
attempt 4 → +30min
attempt 5 → +2h
attempt 6 → +5h
attempt 7 → +10h
give up → move to DLQ + alert producer-side
```

The consumer should return **2xx fast** and process async. A consumer that takes 30s to process will time out and get retried, making the problem worse.

### 4. Asynchronous processing on the consumer

**The cardinal rule: ACK in < 1 second, process in a worker.**

```typescript
// Don't do this
app.post("/webhook", async (req, res) => {
  await updateDatabase(req.body); // takes 30s
  res.status(200).end();
});
// Producer times out at 10s, retries, you process the same event twice.

// Do this
app.post("/webhook", async (req, res) => {
  await queue.add("process-webhook", req.body);
  res.status(200).end(); // 50ms response
});
// Worker processes the event; failures retry inside your own queue.
```

### 5. A delivery dashboard + manual replay

The producer must have a UI where the customer can:
- See every delivery attempt (status, response code, latency, request/response body).
- Manually replay a failed event.
- Rotate the signing secret.

Without this, every webhook integration becomes "the customer says it didn't work; you say it did; you spend 2 weeks debugging in email". Stripe's dashboard is the canonical example.

## Security: Beyond HMAC

HMAC signature verification is the baseline. Production-grade webhooks add:

| Risk | Mitigation |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Forged webhook** (attacker POSTs to your URL) | HMAC signature verification with shared secret |
| **Replayed old webhook** | Reject if timestamp is older than 5 min |
| **Secret leak** (in git, in logs) | Secret rotation; per-endpoint secrets; log redactor |
| **Server-side request forgery (SSRF)** | Validate the registered URL: no localhost, no private IPs, no file://, no redirect-to-arbitrary-host |
| **Man-in-the-middle** | TLS 1.2+ on the consumer endpoint (and on the producer's outbound) |
| **DDoS your consumer** | Rate-limit by source IP and signing key |
| **Phishing via webhook payload** | Treat the body as untrusted data, never as code |

### Per-endpoint secrets (the right answer)

Don't share one secret across all your customers. Each registered webhook endpoint has its **own secret**, displayed once at creation time, rotatable from the dashboard. This way:
- One customer's secret leaks → only their endpoint is compromised.
- Rotation: customer adds the new secret, then deletes the old. Two-secret transition window.

### TLS certificate pinning (optional, for paranoid cases)

Some high-security integrations pin the producer's TLS cert. If the producer's cert rotates, the consumer breaks. Usually not worth it.

## Failure Modes

| Failure | Producer's response | Consumer's response |
| ------------------------------------ | -------------------------------------------------------- | ------------------------------------------ |
| Network error (timeout, reset) | Retry with backoff | Retry inside its own queue |
| 5xx response | Retry with backoff | Check logs, fix, replay |
| 4xx response (e.g. 400, 401) | **Do not retry** (the consumer is permanently rejecting) | Log, fix code, replay manually after fix |
| 429 response | Retry after `Retry-After` header | Throttle, queue |
| Consumer URL changed without notice | All retries fail | Producer alerts customer via email |
| Consumer is down for 10h | All retries within 10h fail; after DLQ, alert | Get back up; replay DLQ |
| HMAC mismatch (secret rotated) | Re-try with new secret | Verify both secrets during rotation window |
| Clock skew | Old timestamps → consumer rejects | Use NTP; allow ±5 min skew |
| Body too large | Producer's request fails | Document max body size; reject larger |
| TLS handshake failure (cert expired) | Retry indefinitely until consumer fixes | Renew cert, replay |

## Real-World Patterns

### Stripe — the canonical example

- **Signature**: `Stripe-Signature: t=<ts>,v1=<hmac>`. Header includes version (`v1`) for future rotation.
- **Retry schedule**: 0s, 5s, 5min, 30min, 2h, 5h, 10h.
- **Tolerance window**: 5 min (configurable in some SDKs).
- **Idempotency**: every event has `event.id` (`evt_...`).
- **Dashboard**: full delivery log with manual replay, secret rotation, endpoint enable/disable.

### GitHub

- **Signature**: `X-Hub-Signature-256: sha256=<hmac>` (note: HMAC of body only, no timestamp).
- **Replay protection**: GitHub does NOT include a timestamp. The consumer must track `X-GitHub-Delivery` (UUID) for dedup. **This is a security gap** — always implement your own timestamp check.
- **Ping event**: GitHub sends a `ping` event when you register the webhook. The consumer must respond 2xx to confirm.
- **Content-Type**: `application/json` is default; can be `application/x-www-form-urlencoded` for legacy.

### Shopify

- **Signature**: `X-Shopify-Hmac-Sha256: <base64-hmac>` (base64, not hex).
- **Idempotency**: `X-Shopify-Webhook-Id` (UUID).
- **Topics**: webhooks are scoped to topics (`orders/create`, `products/update`).

### Slack (events API)

- **Signature**: `X-Slack-Signature: v0=<hmac>` over `v0:${timestamp}:${body}`.
- **Timestamp**: `X-Slack-Request-Timestamp` (unix seconds).
- **3-second rule**: reject if timestamp is more than 5 min old.

## Webhooks vs Polling vs WebSockets vs Server-Sent Events

| Mechanism | Direction | Latency | Server cost | Client cost | Best for |
| ---------------------- | -------------------- | -------------------------- | --------------------------------- | --------------------------- | ----------------------------------- |
| **Polling** | Client → Server | N× poll interval | Low (but many empty hits) | High (continuous requests) | Status checks where staleness is OK |
| **Webhooks** | Server → Your server | Seconds (depends on retry) | Medium (storage + delivery infra) | Low (just respond 2xx) | Async events, B2B integrations |
| **WebSockets** | Bidirectional | Milliseconds | High (per-connection memory) | High (must hold connection) | Real-time UIs, chat, live data |
| **Server-Sent Events** | Server → Browser | Milliseconds | Medium (per-connection) | Low (EventSource API) | Live feeds, notifications in UI |
| **Long polling** | Client → Server | Sub-second | High (held connection) | High | Legacy real-time |

**Webhooks** are for **server-to-server** async events. **SSE** is for **browser-to-server** push. **WebSockets** is for **bidirectional real-time**. Don't conflate.

## Code Examples

### Verifying Stripe signatures (the gold standard)

```typescript
import Stripe from "stripe";
import express from "express";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!, { apiVersion: "2024-12-18.acacia" });
const WEBHOOK_SECRET = process.env.STRIPE_WEBHOOK_SECRET!;

const app = express();

// IMPORTANT: Stripe needs the RAW body for signature verification.
// Use express.raw() BEFORE express.json() for this route only.
app.post(
  "/webhooks/stripe",
  express.raw({ type: "application/json" }),
  async (req, res) => {
    const sig = req.headers["stripe-signature"] as string;

    let event: Stripe.Event;
    try {
      event = stripe.webhooks.constructEvent(req.body, sig, WEBHOOK_SECRET);
    } catch (err) {
      return res.status(400).send(`Webhook Error: ${(err as Error).message}`);
    }

    // Idempotency
    const seen = await redis.set(`wh:stripe:${event.id}`, "1", "NX", "EX", 86400 * 7);
    if (!seen) return res.status(200).json({ received: true, dedup: true });

    // ACK fast, process async
    res.status(200).json({ received: true });
    await webhookQueue.add("stripe", { id: event.id, type: event.type, data: event.data });
  },
);
```

### Webhook signature from scratch (no Stripe SDK)

```typescript
import { createHmac, timingSafeEqual } from "node:crypto";
import express from "express";

const WEBHOOK_SECRET = process.env.WEBHOOK_SECRET!;

app.post(
  "/webhooks/yourapp",
  express.raw({ type: "application/json" }),
  (req, res) => {
    const sigHeader = req.headers["x-webhook-signature"] as string;
    const tsHeader = req.headers["x-webhook-timestamp"] as string;

    // Parse "t=<ts>,v1=<sig>"
    const parts = Object.fromEntries(sigHeader.split(",").map((p) => p.split("=")));
    const ts = parseInt(parts.t, 10);
    const sig = parts.v1;

    // Replay protection
    if (Math.abs(Date.now() / 1000 - ts) > 300) {
      return res.status(400).send("stale");
    }

    // Verify signature
    const expected = createHmac("sha256", WEBHOOK_SECRET)
      .update(`${ts}.${req.body}`)
      .digest("hex");

    const a = Buffer.from(sig, "hex");
    const b = Buffer.from(expected, "hex");
    if (a.length !== b.length || !timingSafeEqual(a, b)) {
      return res.status(401).send("bad signature");
    }

    // Idempotency
    const id = req.headers["x-webhook-id"] as string;
    redis.set(`wh:${id}`, "1", "NX", "EX", 86400 * 7).then((ok) => {
      if (!ok) return res.status(200).send("ok");
      res.status(200).send("ok");
      webhookQueue.add("process", { id, body: JSON.parse(req.body.toString()) });
    });
  },
);
```

### Webhook producer with retry queue (Postgres + worker)

```typescript
// Outbox table for webhooks (same pattern as the outbox & CDC file)
CREATE TABLE webhook_outbox (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  url TEXT NOT NULL,
  event_type TEXT NOT NULL,
  payload JSONB NOT NULL,
  attempt INT NOT NULL DEFAULT 0,
  next_attempt TIMESTAMPTZ NOT NULL DEFAULT now(),
  dispatched_at TIMESTAMPTZ,
  last_error TEXT
);

// Worker: pull pending, attempt delivery, schedule next retry on failure
async function webhookRelay() {
  while (true) {
    const { rows } = await db.query(`
      SELECT id, url, event_type, payload, attempt
      FROM webhook_outbox
      WHERE dispatched_at IS NULL AND next_attempt <= now()
      ORDER BY next_attempt
      LIMIT 50
      FOR UPDATE SKIP LOCKED
    `);

    for (const row of rows) {
      const result = await deliver(row.url, row.event_type, row.payload);
      if (result.ok) {
        await db.query("UPDATE webhook_outbox SET dispatched_at = now() WHERE id = $1", [row.id]);
      } else {
        // Exponential backoff: 5s, 30s, 2m, 10m, 1h, 6h
        const backoffSec = [5, 30, 120, 600, 3600, 21600][row.attempt] ?? 86400;
        await db.query(
          `UPDATE webhook_outbox
           SET attempt = attempt + 1,
               next_attempt = now() + ($1 || ' seconds')::interval,
               last_error = $2
           WHERE id = $3`,
          [backoffSec, result.error, row.id],
        );
        if (row.attempt >= 7) {
          // DLQ — alert the user
          await sendDlqAlert(row);
        }
      }
    }
    if (rows.length === 0) await sleep(1000);
  }
}
```

## Common Mistakes

- **No signature verification.** Anyone who learns your URL can POST forged events. Always verify HMAC.
- **Using `===` for signature compare.** Timing attack. Use `crypto.timingSafeEqual`.
- **No timestamp / no replay protection.** An attacker who captures one valid webhook can replay it forever.
- **Synchronous processing in the request handler.** Times out → producer retries → double processing.
- **No idempotency.** Retries cause double-charges, double-emails, double-fulfillment.
- **No 4xx vs 5xx distinction.** A 400 (bad request from the consumer) should NOT be retried. A 500 (transient error) SHOULD.
- **Retrying 4xx forever.** "I get 401 because my auth is wrong" is not fixable by retrying. Alert and stop.
- **No manual replay UI.** When it breaks (and it will), customers have no recourse.
- **Single shared secret across all customers.** One leak = compromise of all integrations.
- **Storing the secret in source control or logs.** Always env var, with log-redaction middleware.
- **No delivery dashboard.** "Did the webhook arrive?" should be answerable in 5 seconds.
- **Trusting the URL at registration time.** Validate that it's not localhost, not a private IP, doesn't redirect to one.
- **Skipping TLS certificate validation in dev mode.** Habit carries to prod. Never `rejectUnauthorized: false` in production.
- **Long-lived delivery queue items without DLQ.** When a delivery permanently fails, you need to know.

## Best Practices

1. **Always include an idempotency key.** UUID v4 or `prefix_ulid()`. Producer sets it, consumer dedups on it.
2. **HMAC-SHA256 with timestamp.** `t=<ts>,v1=<hmac(t.body)>`. Reject timestamps older than 5 min.
3. **Timing-safe signature compare.** Never `===`. Use `crypto.timingSafeEqual`.
4. **ACK in < 1 second, process in a worker.** This is the most important rule. Process sync = retry storm.
5. **Retry with exponential backoff.** 5s, 5min, 30min, 2h, 5h, 10h. Then DLQ + alert.
6. **Per-endpoint secrets.** One secret per registered URL, rotatable from a dashboard.
7. **Validate the URL at registration.** Reject localhost, private IPs, redirects.
8. **Build a delivery dashboard.** Status of every attempt, response code, latency, manual replay.
9. **Differentiate 4xx from 5xx in retries.** 4xx = don't retry (permanent). 5xx = retry.
10. **Version the signature scheme.** `v1=...`, `v2=...`. Allow rotation without breaking existing consumers.
11. **Use the outbox pattern for the producer.** Write the event to a `webhook_outbox` table in the same transaction as the business event. A worker handles delivery. See [Outbox & CDC](../../../30-architecture/30.2-system-design/01-theory/30.2.1.18-outbox-and-cdc.md).
12. **Test the failure modes.** Inject 5xx, inject 0-byte responses, inject 60-second responses. Does your retry kick in? Does your timeout?

## Performance Considerations

| Concern | Producer | Consumer |
| ---------- | --------------------------------------------------- | ----------------------------------- |
| Latency | Event → URL | URL → ACK |
| Target | < 1 second event-to-URL | < 1 second ACK |
| Throughput | Outbox worker can do 1K-10K deliveries/sec/instance | Limited by consumer's worker pool |
| Storage | Outbox table; bounded by retention policy | Idempotency window (7 days typical) |
| Memory | Per-event payload | Tiny |
| Cost | Outbox storage + worker compute | Idempotency dedup storage (Redis) |

## Summary

- **Webhook** = HTTP POST from producer to a registered URL. "Reverse API".
- **Five must-haves**: idempotency key, HMAC signature with timestamp, retry-with-backoff, async processing, delivery dashboard.
- **Security**: HMAC-SHA256 with timing-safe compare, replay protection, per-endpoint secret, URL validation at registration.
- **Consumer**: ACK in < 1s, process in worker, dedup by `event_id`, always idempotent.
- **Producer**: outbox + relay worker, exponential backoff, DLQ for permanent failures.
- **In interviews: name the 5 must-haves, name the failure mode, name the security mechanism.**

## Cheat Sheet

```text
WEBHOOKS CHEAT SHEET
═══════════════════════════════════════════════════════════════════

ANATOMY
  POST /your/webhook/url
  Headers:
    X-Webhook-Id: evt_<ulid> ← idempotency key
    X-Webhook-Timestamp: 1737158400 ← replay protection
    X-Webhook-Signature: t=<ts>,v1=<hmac> ← HMAC-SHA256
    X-Webhook-Delivery-Attempt: 3 ← visibility
    X-Request-Id: <trace id> ← for tracing
  Body:
    { "id": "evt_<ulid>", "type": "...", "created_at": "...", "data": {...} }

PRODUCER MUST
  1. Unique event id (idempotency key)
  2. HMAC-SHA256 of (timestamp + "." + body)
  3. Timestamp in signature
  4. Retry with exponential backoff (5s, 5m, 30m, 2h, 5h, 10h)
  5. Outbox pattern for durability
  6. Delivery dashboard + manual replay
  7. Per-endpoint secrets
  8. URL validation at registration (no localhost / private IPs)

CONSUMER MUST
  1. Verify signature with timing-safe compare
  2. Reject timestamps older than 5 min
  3. Deduplicate by event id (Redis with 7-day TTL)
  4. ACK in < 1 second (process in worker)
  5. Be idempotent end-to-end

RETRY SCHEDULE (Stripe-style)
  0s → 5s → 5min → 30min → 2h → 5h → 10h → DLQ

INTERVIEW FORMULA
  • State idempotency
  • State signature scheme (HMAC-SHA256 + timestamp)
  • State retry policy (exponential backoff with DLQ)
  • State consumer responsibility (ACK fast, process async, dedup)
  • State one failure mode (replay, secret leak, URL hijack)
```

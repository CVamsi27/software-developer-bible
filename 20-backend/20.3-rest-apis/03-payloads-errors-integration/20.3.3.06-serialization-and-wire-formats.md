# Serialization & Wire Formats

> **Every network boundary is a translation.** Two processes share bytes, not objects — so something has to turn a struct into a byte stream and back, and that choice fixes your payload size, your CPU bill, your schema-evolution rules, and whether a field rename breaks a client you have never met.

## TL;DR

- **Serialization is a contract about bytes**, not a convenience API: the format decides size, speed, debuggability, and how safely it can change.
- **JSON is the default for public/browser-facing APIs** because it is universal, human-readable and debuggable in `curl` — and it is the slowest, largest and least typed of the common options.
- **Binary formats (protobuf, Avro, MessagePack, CBOR) trade readability for 3–10× smaller payloads and typed schemas** — worth it for service-to-service and streaming, usually not for a browser-facing REST endpoint.
- **Schema evolution is the real decision**: a format that cannot rename a field safely (JSON) forces additive-only discipline; one with a schema registry (Avro, protobuf) can evolve with rules, but only if you follow them.
- **The classic production bugs are all boundary bugs**: a `Date` that became a string, a 64-bit `BigInt` that lost precision as a JS number, a field renamed in one service only, an unbounded `JSON.parse` on a 50 MB body.
- **In interviews: name the format, name the size/latency trade, name the evolution rule, name the failure mode.**

---

## First Principles

A wire format exists because of an unavoidable constraint: **two processes do not share memory.**

1. **Bytes are the only interface.** Everything else — language, runtime, ORM, type system — stops at the socket. So a serialization boundary is where type information is *lost* by default and must be re-established explicitly (a schema, a type declaration, or defensive parsing).
2. **A format is a position on a fixed triangle: size, speed, opacity.** Optimizing size costs readability (binary), optimizing readability costs size (JSON), and no format wins all three — which is why every mature system ends up with more than one.
3. **Every field you ship is a contract you must keep.** Once a client parses `created_at`, its name, type and nullability are public API; renaming is a breaking change whether or not a schema exists.
4. **Parsing is attack surface and unbounded work.** A `JSON.parse` on attacker-sized input is a denial-of-service primitive; a schema-driven decoder can enforce limits that text formats cannot.

The consequence: choose the format per boundary, and treat the schema as an artifact you version and review — not as whatever the ORM happens to emit.

## Why it matters

Payload format is one of the few backend decisions that touches **every** request, so a small constant error becomes a large absolute one: a 15% size increase on 100M requests/day is real egress, and a 2 ms parse cost is real CPU. It also determines how safely you can ship changes — teams that treat JSON field names as private have all broken a mobile client that updates on the App Store's schedule, not theirs.

## Definition

**Serialization** is the encoding of an in-memory data structure into a byte sequence for transport or storage; **deserialization** is its reconstruction. The **wire format** is the specification of that encoding.

The three families you actually choose between:

| Family | Examples | Schema | Human-readable | Typical payload | Best boundary |
| ------------------------ | ---------------------------------------------------- | ------------------------------- | -------------- | ------------------------------------------------- | ---------------------------------------------------------- |
| Text / self-describing | JSON, YAML, XML, `application/x-www-form-urlencoded` | Optional (JSON Schema, OpenAPI) | Yes | Largest | Public REST APIs, browsers, webhooks, config |
| Binary / self-describing | MessagePack, CBOR, BSON | Optional | No | ~30–50% smaller than JSON | Caches, queues, mobile sync where a schema is inconvenient |
| Binary / schema-driven | Protobuf, Avro, Thrift, Cap'n Proto | Required | No | Smallest (often 3–10× smaller), fastest to decode | Service-to-service RPC, event streams, telemetry |

## How it works

### 1. JSON and its real limits

JSON (RFC 8259) is universal because it is text, self-describing and trivially debuggable — the same reasons it is a poor choice for hot internal paths. What actually bites in production:

| Limit | Symptom | Fix |
| ------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| No date type | `createdAt` arrives as a string; someone's `new Date()` shifts time zone | ISO 8601 with explicit offset, documented in the contract |
| Numbers are IEEE-754 doubles | A Postgres `bigint` id > 2^53 arrives with the wrong last digits | Serialize 64-bit ids as **strings** at the boundary |
| `undefined` silently disappears | Optional field vanishes; validators see "missing" not "null" | Normalize to `null` explicitly at the response mapper |
| No bytes type | Buffers become `{type:"Buffer",data:[…]}` | Base64-encode binary fields; keep them small |
| No schema on the wire | A rename is invisible until runtime | Adopt OpenAPI/JSON Schema and validate at the edge |
| Parsing is unbounded | A 50 MB body stalls the event loop | Body-size limits *before* parsing, plus streaming for large payloads |

### 2. Protocol Buffers

Protobuf is schema-first: a `.proto` file compiles to typed classes per language, and the wire format encodes **field numbers**, not names — which is exactly why renames are free and type changes are not.

```proto
syntax = "proto3";

message Order {
  string id = 1;                 // field numbers are the contract
  int64 total_cents = 2;
  int64 created_at_ms = 3;
  repeated Line items = 4;
  Address shipping = 5;          // added later: must be optional/absent-safe
}

message Line {
  string sku = 1;
  uint32 quantity = 2;
}
```

Rules that follow from field numbers being the contract:

- **Never renumber or reuse a field number** — an old client will read the new field as the old type. Retire numbers with `reserved`.
- **Unknown fields are preserved**, so adding a field is backward compatible; removing one is forward compatible only if readers tolerate absence.
- **Writes are not self-describing**: you cannot decode a protobuf payload without the schema, which is why gRPC ships a reflection service and proto files are published.

### 3. MessagePack, CBOR and Avro

- **MessagePack / CBOR** are "binary JSON": same data model (maps, arrays, strings, numbers, plus real bytes and floats), no schema required, noticeably smaller and faster. Good for caches, queues and mobile sync where a schema is more friction than it is worth.
- **Avro** keeps a schema but stores/negotiates it out-of-band (a registry keyed by id) and is explicitly designed around **reader vs writer schemas** — the strongest story for schema evolution in data pipelines.
- **Cap'n Proto / FlatBuffers** are zero-copy: the encoded bytes can be read in place without a decode step, which is why they appear in game engines and latency-critical systems.

### 4. Compression layers on top

Almost every format is compressed in transit (`gzip`, `br`, `zstd`). Two consequences worth knowing: compressing already-binary payloads gains less, and **compression of attacker-controlled input can amplify** (a small request that decompresses to gigabytes) — so decompression limits are part of the boundary, not an afterthought.

## Code Examples

### Enforce the JSON boundary before parsing it

```ts
// NestJS: cap the raw body BEFORE any parser sees it. JSON.parse on an
// unbounded body is a denial-of-service primitive, not just slow.
app.use(express.json({ limit: '1mb' }));

// Preserve 64-bit ids by shipping them as strings at the edge.
function toWire(order: OrderRow): OrderDto {
  return {
    id: String(order.id),                     // bigint -> string, never a JS number
    totalCents: order.totalCents,             // fits in double precision
    createdAt: order.createdAt.toISOString(), // explicit UTC instant
    items: order.items.map(i => ({
      sku: i.sku,
      quantity: i.quantity,
    })),
  };
}
```

### Validate against the schema at the boundary

```ts
// The DTO is the contract; parsing is strict so drift fails loudly.
const OrderSchema = z.object({
  id: z.string(),
  totalCents: z.number().int().nonnegative(),
  createdAt: z.string().datetime(),
  items: z.array(z.object({ sku: z.string().min(1), quantity: z.number().int().positive() })).max(500),
});

type OrderDto = z.infer<typeof OrderSchema>;

function parseWire(raw: unknown): OrderDto {
  const r = OrderSchema.safeParse(raw);
  if (!r.success) throw new BadRequestException(r.error.flatten()); // 400 with field paths
  return r.data;
}
```

### Generate protobuf types once, use them on both sides

```ts
// packages/proto/order.proto -> generated TypeScript via protoc / buf
import { Order } from '@acme/proto/order_pb';

const bytes = Order.encode({ id, totalCents, createdAtMs, items }).finish(); // Uint8Array
const decoded = Order.decode(bytes);                                          // typed, no mapping layer
```

### Compare the cost before committing

```ts
// A one-off benchmark beats an opinion in a design review.
const payload = { id: 'ord_123', items: Array.from({ length: 50 }, (_, i) => ({ sku: `sku-${i}`, qty: 2 })) };
console.log('json   ', Buffer.byteLength(JSON.stringify(payload)), 'bytes');
console.log('msgpack', encode(payload).byteLength, 'bytes');
// Then measure parse + serialize in a loop with realistic payloads, not one sample.
```

## Real-World Patterns

- **Public REST API → JSON, always.** Debuggability with `curl` and universal client support outweigh a smaller payload; add `ETag`/`Cache-Control` (→ [20.3.2.04](../02-http-mechanics/20.3.2.04-http-caching.md)) instead of a binary format to cut transfer.
- **Internal service-to-service → protobuf/gRPC** (→ [20.6.2.01](../../20.6-microservices/02-communication-and-messaging/20.6.2.01-grpc.md)). Typed clients, streaming, and a schema that a service cannot silently break.
- **Event streams (Kafka) → Avro with a schema registry**, because producers and consumers are deployed independently and a registry is what makes compatibility checkable at publish time.
- **Cache values → MessagePack or CBOR**: half the Redis memory of JSON, with the option of a schema where you want one.
- **Public webhooks → JSON with a documented schema and an explicit version field** — the consumer is someone else's code, and they cannot be redeployed on your schedule (→ [20.3.3.05](20.3.3.05-webhooks.md)).
- **Big integers anywhere → strings.** The most common cross-language bug in the entire topic.

## Common Mistakes

1. **Shipping 64-bit ids as JSON numbers** — JavaScript clients silently round past 2^53; the bug appears only for large ids, in production.
2. **Renaming or renumbering protobuf fields** — the name is free to change, the number is not; reusing a retired number corrupts old clients.
3. **Treating JSON field names as private** — mobile clients and third-party integrations make them public API.
4. **Serializing ORM entities directly** — internal columns, lazy relations and null shapes leak into a contract you now must keep (→ [20.4.4.01](../../20.4-database/04-orm-and-access/20.4.4.01-prisma.md)).
5. **No body-size or nesting limit** — deep nesting plus large bodies is a cheap server-side DoS.
6. **Decoding untrusted binary without limits** — a schema-driven decoder still allocates from attacker-controlled length prefixes.
7. **Optimizing the format when compression was the answer** — for text payloads, `br`/`zstd` often beats switching to binary, with no ecosystem change.
8. **Assuming protobuf is automatically smaller** — tiny messages can be *larger* (field tags and varint overhead dominate).

## Best Practices

- Pick the format per boundary, and write the reason in the ADR: public JSON, internal protobuf, stream Avro, cache MessagePack.
- **Publish the schema** (OpenAPI for JSON, `.proto` for gRPC, registry for events) and validate at the edge — the schema is the contract, the code is one implementation of it.
- Treat **field names, types, nullability and 64-bit handling** as public API for text formats; make changes additive and deprecate in the open.
- Normalize at the edge: one response mapper per resource decides wire shape, so no ORM entity reaches the wire.
- Put limits *before* parsers: max body size, max array length, max nesting depth, max decompressed size.
- Benchmark with realistic payloads before adopting a binary format, and include the client-side cost (generated code, build step, debugging friction).
- Version by **addition**, not mutation: new optional field, dual-write/dual-read during a migration window (→ [30.3.5.01](../../../30-architecture/30.3-infra-patterns/05-shipping-and-evolution/30.3.5.01-zero-downtime-deployments.md)).

## Performance Considerations

- **Size**: JSON → MessagePack/CBOR is typically 30–50% smaller; JSON → protobuf commonly 3–10× smaller on structured, repetitive data (field names are the cost in JSON).
- **CPU**: schema-driven decoders are usually meaningfully faster than `JSON.parse` at volume, but the win is frequently dwarfed by *serialization on the client* and by network RTT — measure end-to-end, not in isolation.
- **Compression interaction**: gzip/brotli shrink JSON dramatically (repeated field names compress well) and binary formats only mildly, so the *on-the-wire* gap is often far smaller than the raw-size gap. Always compare compressed bytes.
- **Event-loop safety**: parsing is synchronous and CPU-bound in Node; large payloads should stream (→ [20.1.2.01](../../20.1-node.js/02-io-and-data/20.1.2.01-streams.md)) or move to a worker thread (→ [20.1.3.02](../../20.1-node.js/03-processes-and-concurrency/20.1.3.02-child-processes-workers.md)).
- **Memory**: `JSON.parse` materializes the whole structure; streaming parsers (`stream-json`) keep peak memory bounded for imports and exports.
- **Idempotency of the boundary**: canonical encodings matter if you hash payloads (webhook signatures, ETags) — key order and number formatting must be deterministic.

## Summary

- The wire format is a contract about bytes; it fixes size, speed, debuggability and evolution rules at once.
- JSON for public/browser boundaries, protobuf for internal RPC and typed streams, MessagePack/CBOR for caches and mobile sync, Avro for registry-governed event pipelines.
- Field names in text formats and **field numbers** in protobuf are the real contract; changes must be additive unless you own every client.
- The recurring production bugs are boundary bugs: 64-bit precision, dates as strings, silent field renames, unbounded parsing.
- Limits belong before the parser — body size, array length, nesting depth and decompression all need caps.

## Cheat Sheet

```text
CHOOSING A FORMAT
public REST / webhooks / browser   -> JSON (+ OpenAPI schema, gzip/brotli)
internal RPC, typed streaming      -> protobuf over gRPC
events between teams, long-lived   -> Avro + schema registry
cache values, mobile sync          -> MessagePack / CBOR
latency-critical, zero-copy        -> FlatBuffers / Cap'n Proto

JSON RULES
bigint > 2^53        -> ship as string
Date                 -> ISO 8601 with offset
undefined vs null    -> normalize to null explicitly
binary               -> base64, and keep it small
body size            -> cap BEFORE parsing (1 MB default)
schema               -> validate at the edge, 400 with field paths

PROTOBUF RULES
field numbers are the contract  -> never renumber, never reuse
add field    -> backward compatible
remove field -> reserve the number
rename field -> safe (names are not on the wire)

DEBUGGING
curl + jq for JSON; grpcurl for gRPC; protoc --decode_raw for raw bytes
compare COMPRESSED bytes, not raw bytes
```

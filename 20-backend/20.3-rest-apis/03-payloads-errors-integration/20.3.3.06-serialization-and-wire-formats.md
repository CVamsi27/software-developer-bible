# Serialization & Wire Formats

Trace a JSON precision failure. This complete Node.js example demonstrates the difference between JSON number grammar and JavaScript's number representation:

## Definition

Serialization turns application values into bytes another system can store or transmit. Deserialization interprets those bytes under an agreed format. A wire contract also defines what the decoded values mean: whether an omitted field differs from null, how dates are expressed and how large identifiers retain all their digits.

> **Textbook Definition:** A serialization format specifies an encoding and decoding relation between values and byte sequences. A wire schema additionally constrains field identities, types, presence and evolution across independently running producers and consumers.

## First Principles

Two processes do not share in-memory objects or language types. A database bigint, JavaScript number and Java long can represent different ranges. The network carries bytes without preserving those distinctions automatically.
Therefore choosing JSON or protobuf does not finish the contract: both sides must agree on value semantics and compatibility.

A reader may be older than a writer. Deployment order is not atomic across browser clients, mobile installations or services. Changes must remain readable within the supported version window, and resource limits must keep even valid encodings from exhausting memory or CPU.

## How It Works


### 1. Trace a JSON precision failure

```javascript
const parsed = JSON.parse('{"id":9007199254740993}');
console.log(parsed.id); // 9007199254740992: JavaScript rounded it
const preserved = JSON.parse('{"id":"9007199254740993"}');
console.log(preserved.id); // 9007199254740993: every digit retained
console.log(JSON.stringify({ absent: undefined, cleared: null }));
// {"cleared":null}
console.log(JSON.stringify([undefined])); // [null]
```

JSON permits decimal numbers; it does not mandate that every decoder use IEEE 754 doubles. JavaScript normally does, so interoperable integer values outside its safe range need an explicit policy such as decimal strings. Do not stringify a value after it was already rounded.
Native `JSON.stringify` cannot serialize bigint directly; map it at the boundary.

Absent, null and empty have distinct meanings if your contract says so. In a PATCH request, absent may mean “keep the value” and null may mean “clear it”. Normalizing everything to null can destroy that distinction.
Dates need a documented string format, timezone and precision; a JSON string does not become a Date automatically. Monetary values need an explicit unit and precision rather than an undocumented floating-point amount.

### 2. Formats trade different costs

| Format | Mechanism | When to consider it |
| ------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------ |
| JSON | Text fields and values, broad tooling | Public/browser interfaces where inspectability and client support matter |
| Protocol Buffers | Numbered fields encoded according to a schema | Schema-governed RPC/messages with suitable client tooling |
| MessagePack / CBOR | Binary typed values with different supported types | Binary data, constrained clients or measured storage/transfer needs |
| Avro | Schema-driven records, often with writer/reader schema management | Event pipelines that deliberately govern schema resolution |
| BSON | Binary document types including database-specific values | Boundaries already built around its document ecosystem |

Binary is not automatically smaller or faster. Field-name repetition, value distribution, payload size, runtime libraries and compression affect the result. Measure representative compressed bytes, encode/decode CPU, allocations and end-to-end latency.
Include generated-client build and debugging costs. A cache encoding change only saves memory if measurements include object overhead and how data is actually stored.

### 3. Protobuf field numbers are identities

A complete schema fragment:

```protobuf
syntax = "proto3";
package example;
message Order {
  string id = 1;
  optional string note = 2;
  int64 total_cents = 3;
  reserved 4;
  reserved "legacy_reference";
}
```

The binary tag identifies field 1 even if a source-level name changes. Never reuse removed field numbers; reserve names too when text representations or tooling may depend on them. Adding a field can be compatible with binary readers that ignore unknown fields, but changing its meaning or type can still break consumers.
Presence matters: an optional note can distinguish unset from an explicitly empty string.

Binary compatibility does not imply ProtoJSON or generated-source compatibility. JSON names, enum spellings and language accessor names can be public contracts. Unknown-field preservation depends on the runtime and transformation path; a conversion through JSON or rebuilding field-by-field can discard them.
Generated JavaScript handling of int64 also varies: configure and test strings/bigint/long objects rather than assuming numbers retain precision.

Publish schemas and pin compiler/runtime versions. A `Message.encode(...).finish()` API belongs to particular JavaScript libraries, not to protobuf universally. gRPC reflection is an optional server facility; clients need the schema or another supported discovery path when it is disabled.

### 4. Validate values after decoding

A parser checks format syntax, not all business constraints. A valid JSON quantity can still be negative, a protobuf string can still be huge and an unknown field can still violate your public request policy. Build a boundary mapper that validates allowed properties, value ranges, length, nesting and authorization before passing data to domain code.

Define whether unknown request fields are rejected, ignored or retained. For example, a validator that silently strips them does not enforce a “reject unknown fields” contract. Keep response DTOs separate from ORM rows so private fields cannot appear simply because a model gained a column.

### 5. Limits must cover the complete resource path

Bound transport body bytes before parsing, then validate array sizes, string lengths and structural depth. An input byte limit does not cap a decompressed archive or decoded image. Enforce decompressed limits at the decompression stage as well.
In NestJS/Express, configure parsing before it consumes the request; adding another parser after the framework's default parser cannot retroactively enforce a smaller limit.

`JSON.parse` and `JSON.stringify` materialize whole values and execute synchronously in JavaScript. Large imports may use a streaming format/parser with record boundaries and backpressure, or move CPU work to a worker thread. A streaming parser still needs limits for an individual record.
Binary parsers also require bounded lengths and maintained dependencies.

For signatures, verify the original received bytes under the specified scheme. Re-encoding equivalent JSON can change whitespace or key order. If your own protocol requires a canonical encoding for hashes, publish the canonicalization rule; do not call arbitrary `JSON.stringify` output universally canonical.

### 6. Evolution decisions and mistakes

Add a compatible optional field, deploy readers and writers within a deliberate compatibility window, then retire old fields only after supported consumers migrate. A new “optional” field may still break strict old validators or closed generated schemas, so test representative old clients. Unit changes, nullability changes and repurposed identifiers are semantic breaks even if the encoding parses.

Common failures include precision loss, accidental ORM-field exposure, treating null as absent, reusing protobuf tags, benchmarking only uncompressed tiny payloads, and assuming a schema eliminates denial-of-service risks. Keep golden contract fixtures for unusual numbers, Unicode, missing fields and old/new schemas.

## Summary

Choose an encoding together with value semantics, limits and evolution rules. Preserve large identifiers and field presence deliberately, measure format costs with real payloads and test compatibility across the actual decoder/tooling path.

# Transactional Email & Notification Delivery

From a business event to a notification. business transaction → domain change + notification outbox

## Definition

A transactional notification communicates a recipient-specific application event: a receipt, invitation, security alert or password-reset message. The application decides that the event needs a message, a provider accepts delivery work, and a receiving system later decides whether to deliver or reject it.

> **Textbook Definition:** A transactional notification system records application-triggered communication intent and manages its delivery through an external channel. Event creation, dispatch, provider acceptance, recipient delivery and user engagement are distinct states with separate evidence.

## First Principles

The application's transaction cannot include a recipient's mailbox. A provider response can be lost after acceptance; retries may duplicate a message. A later bounce can contradict an earlier successful send request.
Therefore reliable notification design needs durable intent, stable effect identity and asynchronous outcome handling.

The channel also has limits and reputation. Unbounded retry bursts can worsen an outage or damage deliverability. Password resets expire, while receipts may remain useful much longer; work must have purpose-specific priority, expiry and failure policy rather than one generic retry loop.

## How It Works


### 1. From a business event to a notification

```text
business transaction → domain change + notification outbox
                                  ↓ recoverable relay
                          queue → worker → provider
                                            ↓
                              accepted ID, or unknown outcome
                                            ↓
                            delivery / bounce / complaint events
```

Commit the notification intent with the domain change, using a unique business key such as `invoice/8421/issued`. A relay may enqueue more than once, so the worker still needs duplicate-safe processing. Keep template version, recipient reference, purpose and required data durable enough to reproduce the intended message without accidentally rendering a different event after a deployment.

A queue job ID helps suppress duplicates only while that job identity is retained under the queue's rules. BullMQ custom IDs must not contain `:`; hash a business key or use permitted separators. Queue deduplication is not a permanent record of the external effect.

### 2. Trace an ambiguous provider call

1. Worker sends receipt `invoice/8421/issued` with the provider's supported idempotency key.
2. Provider accepts message `msg-9`, but the response times out.
3. Worker records an unresolved attempt and retries/reconciles the same business identity according to the provider's contract.
4. Within a supported provider window, a matching keyed retry can recover the original accepted result without another send.
5. The application records `accepted`, then separately processes a later `delivered` or `bounced` outcome for `msg-9`.

A local `sent_at` lookup before the call does not close the timeout gap, and two workers can both pass that lookup. Enforce durable ownership and preserve the provider key across attempts. If the provider lacks idempotency or the window expires, define reconciliation and duplicate-risk handling explicitly; a database unique index cannot make a remote send exactly once.

Resend currently retains idempotency keys for 24 hours. This is a provider-specific retry boundary, not a lifetime guarantee for every email service. Changing provider requires validating its identity scope, retention, errors, templates, rate limits and event taxonomy; it is more than replacing a configuration value.

### 3. A stable queue identity and a bounded demonstration

This Node.js example simulates a provider that remembers keys. It proves the local retry identity, not actual delivery or a production provider guarantee.

```javascript
import { createHash } from 'node:crypto';
const businessKey = 'invoice/8421/issued';
export function queueId(key) {
  return `notification-${createHash('sha256').update(key, 'utf8').digest('hex')}`;
}
const accepted = new Map();
let effects = 0;
async function fakeProvider(key) {
  if (!accepted.has(key)) {
    accepted.set(key, { messageId: `msg-${++effects}` });
    throw new Error('Response lost after acceptance');
  }
  return accepted.get(key);
}
try { await fakeProvider(businessKey); } catch { /* simulate an unknown outcome */ }
console.log(await fakeProvider(businessKey)); // { messageId: 'msg-1' }
console.log(effects); // 1
console.log(queueId(businessKey).includes(':')); // false
```

The Map is process-local and never expires in this fixture. Real providers persist under their own finite contract. Production handling must distinguish permanent rejection, rate limiting and unknown acceptance, and must not swallow failures without recording state.

### 4. Mail authentication explains different identities

| Mechanism | What it establishes | What it does not establish |
| --------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| SPF | Sending host is authorized for the envelope sender domain (or HELO identity in the applicable case) | Authentication of every visible From address or message content |
| DKIM | A domain signed selected message headers and body; a DNS key lets receivers verify it | That the signer is the displayed author or that the message is wanted |
| DMARC | The visible From domain aligns with a passing SPF **or** DKIM identity, with published policy/reporting | Guaranteed inbox placement or unconditional enforcement by every receiver |

SPF and DMARC publish DNS records; DKIM uses a message signature plus a published key. DMARC can pass through either aligned authentication path; both SPF and DKIM need not pass simultaneously. A `p=none` policy expresses no DMARC-specific handling preference and is commonly used with aggregate reports for monitoring. `quarantine` and `reject` express the domain owner's requested handling for failing messages.
Receivers can apply their own policy.

Inventory legitimate senders before tightening DMARC and examine aggregate reports. Separate transactional and promotional streams or subdomains when useful, but do not assume complete reputation isolation across shared domains, IPs or providers. Follow current provider configuration and sending requirements instead of a universal warm-up schedule.

### 5. Delivery, suppression and preferences

A provider's `accepted` event, receiving-server delivery, inbox placement and reading are different observations. Webhooks, provider queries or other supported status channels can supply later evidence. An open-tracking pixel is not proof of reading: privacy proxies, image blocking and automated fetches distort it.

Classify hard/permanent bounces and temporary failures using the provider's documented codes. Providers may already retry temporary delivery failures; creating a new message on every soft bounce can duplicate their work. Handle complaints and suppression according to purpose, user preferences and applicable policies.
Marketing unsubscribe and essential account communications need explicit scope; avoid one vague rule that every event disables all future messages.

Verify and durably accept provider webhooks using the [webhook contract](20.3.3.05-webhooks.md). Apply event deduplication, notification-state updates and local suppression changes transactionally where they share storage. Do not mark an event “seen” and then crash before suppressing its address.
Out-of-order outcomes need a defined transition policy; do not turn a permanent bounce back into generic success because an older acceptance event arrived later.

### 6. Operational decisions and mistakes

Use finite retries with backoff, jitter, provider pacing and a recovery queue/runbook for exhausted work. Bound queue age; expire stale reset links rather than delivering them after they cease to be useful. Keep channel priority intentional so a bulk backlog does not starve urgent security notifications.
Measure oldest pending intent, provider acceptance latency, unknown outcomes, bounce/complaint rates and suppression activity.

Render reviewed templates with escaped untrusted values, trusted action URLs and a plain-text alternative. Bind reset/invitation links to single-use, expiring domain tokens; the email queue identity is not that authorization token. Redact recipient data from broad logs and avoid placing identifiers or addresses in unbounded metric labels.

Transactional and promotional messages have different purpose and consent requirements, which depend on jurisdiction and context. Treat the technical pipeline as a delivery mechanism, not as proof of legal permission. Keep consent and preference decisions explicit in the relevant product policy.

## Summary

Record notification intent with the business event, dispatch recoverably and preserve stable effect identity across ambiguous sends. Provider acceptance does not establish delivery; authentication, later outcomes, scoped suppression and purpose-specific budgets complete the operational contract.

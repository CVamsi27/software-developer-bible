# API Rate Limiting

Separate rate, concurrency and backlog. A rate limit caps admission over time.

## Definition

Rate limiting decides whether to admit work under a usage budget over time. For example, a tenant may submit at most a configured burst of exports and then earn new capacity gradually. Limits can protect shared resources, enforce a paid quota or constrain abuse; those policies need different identities and failure behavior.

> **Textbook Definition:** A rate limiter controls admission by comparing usage for an identified principal or resource against a time-dependent budget. Algorithm, accounting scope, atomicity and failure policy determine burst tolerance and enforcement accuracy.

## First Principles

A request consumes CPU, memory, connections or downstream quota, and those resources are finite. A cheap read and an expensive export do not consume equal capacity, so request counts are a proxy for cost rather than a complete resource model. Rejecting excess work early preserves capacity for admitted work.

Counting also has an owner. Two instances that independently read one shared token and both consume it can admit two requests for a one-request budget. A global exact policy therefore needs an atomic admission decision over the relevant shared state.
Local limits can deliberately protect each instance without claiming to enforce a fleet-wide quota.

## How It Works


### 1. Separate rate, concurrency and backlog

A rate limit caps admission over time. A concurrency limit caps simultaneous active work. A bounded queue caps waiting work.
At ten requests per second with jobs lasting thirty seconds, many jobs can remain active even though the rate is respected. Combine the appropriate protections instead of assuming a rate counter alone prevents exhaustion.

Place coarse IP/connection/body controls at the edge, then use authenticated tenant, user and operation budgets where that identity and cost are known. Domain services may need their own downstream/concurrency limits; not every decision can or should live only at the gateway.

### 2. Algorithms permit different bursts

| Algorithm | Mechanism | Boundary |
| -------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Fixed window | Count admissions in a named interval | A limit of 100 can admit 100 near one boundary and 100 just after it |
| Sliding log | Retain accepted timestamps in the last interval | Accurate rolling counts, but storage/work grow with admissions |
| Sliding counter | Weight neighboring interval counts | Less state with approximate boundary behavior |
| Token bucket | Earn tokens at a rate up to a capacity; spend them on work | Capacity permits bursts while refill constrains sustained admission |
| Leaky bucket / paced queue | Release queued work at a controlled rate, or enforce equivalent admission timing | Queue capacity/wait deadline must be bounded; full queues reject work |

Define whether failed/rejected requests count toward a policy. Counting every denied attempt can be useful for abuse controls but differs from a rolling budget of admitted work. A queue is not normally allowed to grow without bound whenever a leaky bucket is full.

### 3. Trace fractional refill correctly

A bucket starts with 3 tokens and earns 1 token per second. Three immediate requests consume it. A fourth is rejected with an estimated one-second wait.
At 0.4 seconds there are 0.4 tokens; another rejection must not discard that fraction. At 1.0 second one token is available.

Save the complete JavaScript model below as `bucket.mjs`. It uses a caller-supplied monotonic elapsed-time value, so tests can trace time deterministically. The example models one process and one fixed policy; it is not a shared production store.

```javascript
export class TokenBuckets {
  #states = new Map();
  constructor(capacity, tokensPerSecond, maxKeys = 1000) {
    if (!Number.isFinite(capacity) || capacity < 1 ||
        !Number.isFinite(tokensPerSecond) || tokensPerSecond <= 0 ||
        !Number.isSafeInteger(maxKeys) || maxKeys < 1) throw new Error('Invalid policy');
    this.capacity = capacity; this.rate = tokensPerSecond; this.maxKeys = maxKeys;
  }
  admit(key, nowMs, cost = 1) {
    if (typeof key !== 'string' || key.length < 1 || key.length > 200 ||
        !Number.isFinite(nowMs) || nowMs < 0 ||
        !Number.isFinite(cost) || cost <= 0 || cost > this.capacity) {
      throw new Error('Invalid admission input');
    }
    let state = this.#states.get(key);
    if (!state) {
      if (this.#states.size >= this.maxKeys) throw new Error('Local key budget exhausted');
      state = { tokens: this.capacity, last: nowMs };
    }
    if (nowMs < state.last) throw new Error('Clock moved backwards');
    state.tokens = Math.min(this.capacity, state.tokens + (nowMs - state.last) * this.rate / 1000);
    state.last = nowMs;
    const allowed = state.tokens >= cost;
    if (allowed) state.tokens -= cost;
    this.#states.set(key, state);
    return {
      allowed, tokens: state.tokens,
      retryAfterSeconds: allowed ? 0 : Math.ceil((cost - state.tokens) / this.rate),
    };
  }
  evictFull(nowMs) {
    for (const [key, state] of this.#states) {
      if (nowMs >= state.last &&
          state.tokens + (nowMs - state.last) * this.rate / 1000 >= this.capacity) {
        this.#states.delete(key);
      }
    }
  }
}
const bucket = new TokenBuckets(3, 1);
console.log([0, 0, 0, 0, 400, 1000].map(time => bucket.admit('tenant-a', time).allowed));
// [true, true, true, false, false, true]
```

`last` advances together with the fractional token balance, so repeated sub-second requests cannot prevent refill. The previous whole-interval pattern that reset lastRefill after every request lost fractional time and could starve a busy key indefinitely. Use `performance.now()` or another appropriate monotonic clock for the local model.
A backwards clock is rejected deliberately here.

The key cap protects model memory; choose an explicit fallback when it is reached. Periodically evict only buckets that have fully refilled, so forgetting them is equivalent to keeping a full bucket. Policy changes require new interpretation or a policy-versioned key; silently resetting a live paid quota can grant extra capacity.

### 4. Shared decisions must be atomic

For a shared bucket, the read, refill, compare, consume and expiry update belong to one atomic store operation. A Redis pipeline batches commands but does not make their combined decision atomic. Independent HGETALL/HSET calls race.
Use a correctly designed script/function or another store-specific conditional transaction, and handle errors before assuming a decision succeeded.

Redis script execution is atomic relative to other commands on that server; it is not a guarantee of rollback after a script's runtime error or durability across every failover. Keep involved keys compatible with cluster routing rules, choose a consistent clock basis and document replication/failover tolerance. Global multi-region quotas can use a coordinated authority, partitioned budgets or explicitly approximate accounting; they trade latency, availability and overshoot differently.

Do not claim global exactness for unsynchronized local caches. A deliberate per-instance emergency limit can still reduce damage during a shared-store outage without pretending to preserve the usual fleet budget.

### 5. Identity and outage policy are security decisions

Use verified user/tenant or validated API-key identity, not an arbitrary X-API-Key string supplied before authentication. IP limits can help unauthenticated endpoints but shared NATs and IPv6 address rotation affect fairness. Trust forwarded IP headers only through configured trusted proxies that strip/overwrite client values; `trust proxy = true` under an uncontrolled path can enable spoofing.

**Fail open** favors availability when enforcement storage is down but can permit abuse or overspend. **Fail closed** protects a hard quota or sensitive action but can deny legitimate users. **Degraded local limits** are another explicit policy. Select by operation and threat model; “always fail open” is unsafe guidance. Store outage is usually a service-availability failure, not evidence the caller exhausted a quota.

### 6. Responses and operation-specific budgets

Use 429 for the documented caller-budget rejection and publish useful `Retry-After` guidance. Seconds are delays, not an epoch timestamp; a reset timestamp has a separate documented meaning. X-RateLimit-* fields are conventions, not universally standardized names.
Choose a supported header contract and expose it through CORS when browser code needs it.

A Retry-After estimate can become stale as concurrent callers spend capacity. Clients need capped waiting, jitter and an overall budget. Protect login attempts by relevant source/account signals without enabling easy account-lockout denial of service.
Give exports, uploads and expensive search appropriate cost/concurrency budgets; paid tiers should derive from trusted entitlements and not bypass infrastructure safety caps. Administrators can still exhaust resources.

Measure admitted/rejected work, decision latency, store errors, key cardinality, queue age and upstream saturation by bounded policy labels. Test boundary bursts, fractional refill, concurrent admissions, proxy identity spoofing, restart/failover and outage behavior. Avoid one Redis connection per middleware/attempt; manage a bounded reusable client lifecycle.

## Summary

A limiter admits work under an explicit algorithm, identity, cost and scope. Preserve atomic accounting for shared budgets, combine rate with concurrency/backlog protections and choose outage/retry behavior from the operation's actual capacity and risk.

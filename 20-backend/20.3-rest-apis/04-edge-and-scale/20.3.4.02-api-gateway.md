# API Gateway Pattern

## Definition

An API gateway mediates a public request boundary and forwards approved requests to selected upstreams. It can apply shared transport policy such as TLS handling, coarse admission, request tracking and route selection while preserving a stable external contract.

> **Textbook Definition:** An API gateway is an intermediary that routes requests and applies common edge policies between clients and backend services. It does not replace resource-specific authorization, domain invariants or service ownership.

## First Principles

Clients should not need to track every internal hostname or service move. An intermediary maps a stable public surface onto changing upstream topology. It can reject some malformed or excessive traffic before expensive services see it.

The intermediary becomes another component that can saturate, misroute or fail. Its policy and forwarding behavior therefore need bounded resources, trustworthy configuration and observable rollout. Centralization can improve consistency, but it does not automatically remove every security obligation downstream or make a gateway mandatory for all microservice systems.

## Trace the request and its authority

```text
client → edge transport / coarse admission → authenticated principal
                                      ↓
                         fixed routing policy, bounded forwarding
                                      ↓
                     service authorization + domain operation
                                      ↓
                        status / headers / representation → client
```

Authenticate before adding internal identity context. Strip incoming identity/forwarded headers the client could spoof, then add verified context only over an authenticated trusted hop. Backend services must either verify the original credential appropriately or trust an explicitly protected gateway assertion and still authorize the target resource. A plain X-User-Id received from the public internet is not identity evidence.

Public-route matching must be exact under a documented path normalization policy. A broad startsWith('/login') exemption can accidentally cover `/login-admin` or another protected route. Consistent routing and authorization must interpret the same path.

## Forwarding is more than calling fetch

A proxy must preserve relevant method, path and query, status, headers, and body semantics. Stream opaque bodies where appropriate, manage backpressure, and propagate client cancellation. A parsed request body cannot be forwarded by blindly passing the already-consumed original stream; deliberate transformation requires reserialization and correct content headers and signature rules.

Do not parse every upstream response as JSON. A 204/304 has no representation body, an error can be text and a download can be binary. Copy only the appropriate end-to-end headers; hop-by-hop connection headers and untrusted identity fields need explicit handling. Redirects, cookies, content encoding, cache validators, upgrades and streaming each require a policy. A response res.json monkeypatch does not transform a proxy's raw response stream.

## A runnable, deliberately limited read gateway

This Node.js example forwards only public product GET reads to one fixed loopback upstream. It does not authenticate users, proxy writes, cookies, or upgrades, or implement a general production gateway. Run a controlled product service on port 3001 and save this as `gateway.mjs`.

```javascript
import { createServer, request as send } from 'node:http';
import { randomUUID } from 'node:crypto';

export const gateway = createServer((clientRequest, clientResponse) => {
  let url;
  try { url = new URL(clientRequest.url, 'http://localhost'); }
  catch { clientResponse.writeHead(400).end(); return; }
  const route = /^\/api\/products(?:\/([A-Za-z0-9_-]+))?$/.exec(url.pathname);
  if (!route) { clientResponse.writeHead(404).end(); return; }
  if (clientRequest.method !== 'GET') {
    clientResponse.writeHead(405, { Allow: 'GET' }).end(); return;
  }
  if (clientRequest.headers['transfer-encoding'] ||
      Number(clientRequest.headers['content-length'] || 0) > 0) {
    clientResponse.writeHead(400).end(); return;
  }
  const requestId = randomUUID();
  clientResponse.setHeader('X-Request-Id', requestId);
  let timedOut = false;
  const upstream = send({
    hostname: '127.0.0.1', port: 3001, method: 'GET',
    path: `/products${route[1] ? '/' + route[1] : ''}${url.search}`,
    headers: { Accept: 'application/json', 'X-Request-Id': requestId },
  });
  const timer = setTimeout(() => {
    timedOut = true; upstream.destroy(new Error('Upstream deadline'));
  }, 1000);
  clientResponse.on('close', () => {
    clearTimeout(timer);
    if (!clientResponse.writableFinished) upstream.destroy();
  });
  upstream.on('response', response => {
    clientResponse.statusCode = response.statusCode || 502;
    for (const name of ['content-type', 'cache-control', 'etag', 'vary', 'www-authenticate']) {
      if (response.headers[name]) clientResponse.setHeader(name, response.headers[name]);
    }
    response.on('error', () => clientResponse.destroy());
    response.on('aborted', () => clientResponse.destroy());
    response.on('end', () => clearTimeout(timer));
    response.pipe(clientResponse);
  });
  upstream.on('error', () => {
    clearTimeout(timer);
    if (clientResponse.destroyed) return;
    if (clientResponse.headersSent) { clientResponse.destroy(); return; }
    clientResponse.writeHead(timedOut ? 504 : 502).end();
  });
  upstream.end();
});
gateway.listen(8080);
```

`/api/products/42?view=compact` becomes `/products/42?view=compact`. Client-supplied X-User-Id and X-Request-Id are not forwarded. A normal product response preserves its status, body, and selected headers. A connection failure becomes 502; the one-second illustrative total upstream deadline becomes 504. If a response already started, the gateway terminates the stream instead of writing a second JSON error body.

This narrow fixture intentionally does not forward Content-Encoding or arbitrary response headers. Expand only with a tested policy for the actual upstream contract; use a maintained gateway/proxy for broader requirements rather than treating this sample as complete. Configure target destinations from trusted deployment data, never a client-supplied URL that can reach internal networks.

## Timeouts, retries and health are separate controls

Allocate an end-to-end deadline among gateway work and downstream calls. Cancelling waiting does not reverse an already-committed upstream write. Retry only safe or durably idempotent operations within one bounded budget; independent retries at every hop can multiply attempts. A circuit breaker limits repeated calls to a failing dependency, but a timer alone is not a breaker and library timeout errors do not necessarily cancel underlying work.

Load balancing selects an available upstream using the configured algorithm and health evidence. A successful fetch call does not prove a healthy endpoint when it returned500; inspect statuses and bound probes. Readiness is a routing signal, not proof every request will succeed. Connection pools, active-stream limits and bounded buffering protect the gateway itself.

## Keep composition and transformation intentional

Protocol translation maps a public contract to an internal one, including errors, deadlines, identity and value types. It cannot assume every internal gRPC method accepts a direct JSON equivalent. Client-specific aggregation commonly belongs in a [BFF](20.3.4.03-bff.md); gateway aggregation is possible but needs a deliberate ownership and partial-failure policy.

Response transformation can change bytes, validators, Content-Length, content encoding and cache identity. Do not remove a password field from every arbitrary request body: a login handler may require it. Prefer explicit route-specific mappings and avoid turning edge configuration into the hidden owner of domain rules.

## Decisions and mistakes

Replicate the gateway where needed and roll out route/auth policies with validation, canaries and rollback. Track route-level latency, upstream errors, deadline exhaustion, active connections and policy rejects. Keep logs redacted and metric labels bounded; a random request ID is useful correlation but is not automatically a distributed trace.

Avoid placing authentication after forwarding middleware, trusting unsigned identity headers, bypassing domain authorization, returning successful fallback data for a failed write, or treating a gateway as a mandatory cure for every service topology. Meshes and internal clients can apply other policies without requiring every east-west request through the public gateway.

## Summary

A gateway stabilizes the external boundary through trusted routing and bounded forwarding. Preserve HTTP semantics, protect identity propagation, define cancellation/retry/health behavior and keep resource authorization and domain correctness authoritative in their owning services.

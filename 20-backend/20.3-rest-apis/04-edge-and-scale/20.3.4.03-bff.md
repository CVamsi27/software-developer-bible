# BFF — Backend for Frontend

When a mobile screen and a web dashboard need different data, one shared endpoint may return too much to one client or force another to make several calls. A Backend for Frontend (BFF) is one way to shape APIs around those client needs.

## Definition

A Backend for Frontend (BFF) is a server-side layer that composes and shapes domain capabilities for a particular client experience. A mobile profile may need a compact identity summary; a web dashboard may also need recent activity. A BFF can give each a useful contract without turning every domain service into a screen-specific API.

> **Textbook Definition:** A Backend for Frontend adapts and composes backend service APIs to the needs of a client experience. Its representation and release boundary follow that experience, while authoritative domain rules and resource authorization remain with their owners.

## First Principles

Clients can have different network budgets, screens and release schedules while using the same domain data. Asking each client to repeat service composition adds round trips and exposes service topology. Asking every domain service to know every screen couples unrelated releases.
A composition layer is one way to absorb that mismatch.

It also adds a hop, ownership and failure paths. A shared API or field selection may be simpler when needs are similar. Client count alone does not determine whether a BFF is worthwhile.

## How It Works


### 1. Place it within the whole request path

```text
mobile → gateway → mobile composition ─┐
                                      ├→ authorized domain APIs
web    → gateway → web composition ────┘
```

The gateway can handle shared transport policy, while the BFF aggregates and maps a client-facing result. Boundaries can coexist in one deployable or separate services; choose ownership and scaling deliberately. Aggregation is possible in gateways too, so the distinction is responsibility rather than an absolute feature prohibition.

Pass verified identity over a trusted connection. Field selection is not authorization: asking for only `id` and `displayName` does not prove a partner is allowed to read that user. The data-owning service validates access.
The BFF can enforce additional client policy but must not become a bypass around domain invariants or tenant scoping.

### 2. Trace required and optional data

A profile response requires the authorized user's display name. Recent activity is optional. The BFF starts both bounded calls, waits within the screen budget and maps the profile.
If activity fails, it returns an explicit unavailable state; if the profile fails, it fails the operation. An empty activity list means “no activity” and must not silently stand in for an outage.

This complete JavaScript composition helper accepts service adapters as arguments. They must enforce authorization, return validated data and obey the supplied signal. The helper does not provide HTTP credentials, a database or actual services.

```javascript
export async function mobileProfile(principal, services, { signal, timeoutMs = 1000 } = {}) {
  if (!principal || typeof principal.userId !== 'string' || !principal.userId) {
    throw new Error('Verified principal required');
  }
  const deadline = AbortSignal.timeout(timeoutMs);
  const combined = signal ? AbortSignal.any([signal, deadline]) : deadline;
  const [profile, activity] = await Promise.allSettled([
    Promise.resolve().then(() => services.profile(principal, { signal: combined })),
    Promise.resolve().then(() => services.activity(principal, { signal: combined, limit: 5 })),
  ]);
  combined.throwIfAborted();
  if (profile.status === 'rejected') throw new Error('Profile unavailable');
  const user = profile.value;
  return {
    id: user.id,
    displayName: user.displayName,
    activity: activity.status === 'fulfilled'
      ? { state: 'available', items: activity.value }
      : { state: 'unavailable', items: null },
  };
}
const result = await mobileProfile({ userId: '42' }, {
  profile: async () => ({ id: '42', displayName: 'Ada', privateNote: 'do not expose' }),
  activity: async () => { throw new Error('Activity dependency failed'); },
});
console.log(JSON.stringify(result));
// {"id":"42","displayName":"Ada","activity":{"state":"unavailable","items":null}}
```

The mapper selects permitted fields instead of returning an entire internal object. Promise.allSettled observes both outcomes, but it cannot stop an adapter that ignores cancellation or never settles. Real adapters need transport deadlines and bounded response work; Promise.race alone would only stop waiting, not cancel the losing task.
Define whether a total timeout fails the whole response or permits a separately budgeted optional fallback.

A web mapper can include authorized, bounded activity and other required screen data, while preserving machine-readable dates/amount units. If it renders user Markdown to HTML, sanitize under the display policy; a client-specific response shape does not make untrusted content safe. Image variant URLs require a real media transformation contract, not arbitrary `?w=` parameters presumed to work.

### 3. Variants choose different ownership costs

| Variant | What changes | Boundary |
| ----------------------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| Client routes in one application | Separate client mappings, shared deployment | Low operating cost but shared rollout/capacity |
| Dedicated client services/functions | Independent ownership and scaling | More deployments, monitoring and compatibility work |
| GraphQL composition | Clients select fields from a governed schema | Authorize resolvers and bound query cost/fan-out |
| Regional composition layer | Place client-facing work near data/client requirements | Define cross-region data and failure behavior explicitly |

GraphQL is not automatically a BFF just because clients choose fields, and composing multiple subgraphs does not mean one service exposes three isolated schemas or authentication flows. Federation and general GraphQL API design have their own contracts. Nested BFF calls can be justified by a deliberate platform boundary, but avoid accidental chains whose owners and deadlines are unclear.

### 4. Keep domain truth separate from presentation

Price computation, stock reservation and cancellation eligibility must be consistent across clients. Their domain service owns the invariant and transaction. The BFF may map a price into a client representation or combine it with other permitted data, but should not fork pricing rules or claim a multi-service read is an atomic snapshot.

Repeated composition may justify a shared domain/read API or a small shared adapter library. It does not automatically require another network service. Avoid BFF-to-BFF calls solely because one client happened to implement the shared rule first.

### 5. Cache and retry within the client contract

Key caches by all relevant tenant, identity/permission, locale, query and representation dimensions; “client=mobile” alone cannot isolate private users. Define TTL, invalidation and stale/failure visibility. A new permission or revocation must not expose data through an old cached result.

Parallel calls reduce sequential waiting but multiply downstream load. Bound fan-out and collection sizes, propagate an overall deadline and avoid nested retry amplification. Retry only safely repeatable operations under a budget.
A write composition spanning services needs an explicit workflow/consistency owner rather than assuming Promise.all creates a transaction.

Browser-facing cookie sessions require appropriate CSRF and cookie policy. CORS matters for actual cross-origin browser requests, not automatically every internal proxy call. Service credentials stay server-side with bounded scopes and rotation; tokens and personal response bodies do not belong in broad logs.

## Decisions and operational mistakes

Choose a client experience whose benefit justifies the deployable boundary and assign an owner who can operate it. Track end-to-end latency, fan-out count, required/optional failures, cache hit/staleness and payload size with representative traffic. Team ownership can support independent releases but does not guarantee them without stable downstream contracts.

Common mistakes include unbounded dashboard fan-out, invented payload-size wins, empty successful fallbacks for unavailable data, publishing fields based only on client type, and bypassing domain APIs to access their database. A BFF can be useful without multiple clients or heavy aggregation; judge its actual adaptation responsibility.

## Summary

A BFF adapts domain APIs to a client experience. Make composition, required/optional outcomes, identity, fan-out and cache scope explicit while keeping authoritative business and data-access rules in their owning services.

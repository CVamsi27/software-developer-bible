# BFF — Backend for Frontend

When a mobile screen and a web dashboard need different data, one shared endpoint may return too much to one client or force another to make several calls. A Backend for Frontend (BFF) is one way to shape APIs around those client needs.

## Definition

A **Backend for Frontend (BFF)** is an API layer designed around the needs of a client experience, such as a mobile app or web interface. Teams often use a separate BFF for each client or client group, but a strict one-to-one mapping is a design choice, not a requirement. A general-purpose API gateway handles shared edge concerns; a BFF shapes and composes responses for its clients.

```text
                ┌─────────────────┐
   mobile app ──│ mobile BFF   │──┐
                └─────────────────┘  │        ┌───────────────┐
                ┌──────────────────────────────────────────┐  ├───────▶│ domain services│
   web app ─────│ web BFF      │──┤        │ (user, catalog│
                └──────────────────────────────────────────┘  │        │  order, pay)  │
                ┌─────────────────┐  │        └───────────────┘
   partner  ────│ partner API  │──┘
                └─────────────────┘
```

Consider a BFF when:

1. **Clients need meaningfully different responses.** For example, a mobile view may need a compact response while an internal dashboard needs a larger aggregate. One shared endpoint can still work if the differences are small.
2. **A client experience needs a small number of service calls composed into one response.** The BFF can combine and reshape data, while business rules remain in domain services.
3. **The team can own the extra layer.** A separate BFF adds deployment, monitoring, and failure paths. Add it when client-specific needs justify that cost.

Keep business rules in domain services so every client gets the same rule. Also watch for duplicate composition logic across BFFs; share a stable service API when the same operation is needed by several clients.

---

## First Principles

The BFF pattern addresses a mismatch between shared domain data and client-specific screens:

1. A shared API is simpler when clients need the same data.
2. When their needs diverge, a BFF can combine service calls and return a client-specific shape.
3. That flexibility costs another layer to deploy and operate. Keep business rules in domain services and add BFFs only where the client-specific benefit outweighs that cost.

## Why it matters

There is no endpoint count or client count at which a BFF becomes mandatory. The decision depends on how different the clients' data needs are and whether a separate layer is worth operating.

**The breaking point:**

```text
Mobile app:
  GET /api/users/123/profile → returns 14 fields, 18KB JSON
  - Mobile drops 12 of those fields
  - Mobile wants profile picture in 3 sizes
  - Mobile wants locale-specific formatting
  - 18KB is fine for wifi; not fine for cellular in India

Web app:
  GET /api/users/123/profile → same 14 fields, 18KB
  - Web uses all 14 fields
  - Web wants the full bio markdown rendered as HTML
  - Web wants activity history inline (5 more API calls)

Partner API:
  GET /api/users/123/profile → same 14 fields, 18KB
  - Partner wants minimal: just ID + display name
  - Partner has different auth (OAuth client credentials)
  - Partner has its own rate limit (1000 req/sec)
```

This example is illustrative: a shared endpoint may return unnecessary fields to mobile and still require extra calls for the dashboard. A BFF can compose the dashboard response and return a smaller mobile response. Separate partner authentication and rate limits can be enforced at an API gateway or another trusted edge layer; they do not require a separate BFF by themselves.

The other big reason: **team ownership**. When the web team owns the web BFF, they ship the web BFF at the web team's pace. They don't have to wait for the mobile team. The mobile BFF is owned by the mobile team. Each team deploys independently.

## How it works

### Architecture

```text
┌──────────────────────────────┐ ┌─────────┐ ┌─────────┐
│ Mobile │ │ Web │ │ Partner   │
│ Client │ │ Client │ │ Client │
└────┬─────────────────────────┘ └────┬────┘ └────┬────┘
     │ │ │
     ▼ ▼ ▼
┌────────────────────────────┐ ┌─────────┐ ┌─────────┐
│ Mobile │ │ Web │ │ Partner │
│ BFF │ │ BFF │ │ BFF        │
└────┬───────────────────────┘ └────┬────┘ └────┬────┘
     │ │ │
     │ ┌───────────┴──────────┐ │
     │ │ │ │
     ▼ ▼ ▼ ▼
  ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ user │ │ order │ │ notif │ ← underlying services
  │ service                  │ │ service │ │ service │
  └─────────┘ └─────────┘ └─────────┘
```

Each BFF, depending on where edge responsibilities live:
- **Authenticates the client or consumes verified identity** from a trusted gateway.
- **Authorizes** the request (what can THIS client do?).
- **Aggregates** calls to the underlying services.
- **Shapes** the response (per-client payload).
- **Caches** aggressively (per-client cache keys).
- **Rate-limits** (per-client limits).
- **Logs / traces** the request (with a `client` attribute).

### Pattern Variants

**1. API Gateway with BFF routes** — single gateway, routes per client. Cheapest to start. Hard to scale team ownership.

```yaml
# AWS API Gateway / Kong / Express Gateway
routes:
  - path: /mobile/*
    upstream: mobile-bff.internal
  - path: /web/*
    upstream: web-bff.internal
  - path: /partner/*
    upstream: partner-bff.internal
```

**2. Dedicated BFF services per client** — each BFF is its own deployable. This gives teams independent ownership and release timing, at the cost of more services to operate.

```text
3 services:
  mobile-bff/ (Node.js, deployed independently)
  web-bff/ (Node.js, deployed independently)
  partner-bff/ (Node.js, deployed independently)
```

**3. GraphQL as a BFF** — GraphQL is a natural BFF because the client controls the query. One GraphQL endpoint serves all clients; the schema and resolvers shape per-client payloads.

```typescript
// Apollo Federation
const server = new ApolloServer({
  schema: buildSubgraphSchema([
    { typeDefs, resolvers: mobileResolvers }, // mobile-specific
    { typeDefs, resolvers: webResolvers }, // web-specific
    { typeDefs, resolvers: partnerResolvers }, // partner-specific
  ]),
});
```

This is what Shopify, Yelp, Expedia use. The mobile app queries for the fields it needs; the web app queries for different fields; the partner API queries for minimal fields. **One service, three schemas, three auth flows.**

**4. BFF in a BFF** (nested) — sometimes a regional or platform BFF sits in front of a client BFF. Common in large orgs (Amazon, Google).

## What Goes in a BFF

| Concern | Usual place | Boundary to preserve |
| --------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------ |
| Payload shaping | BFF | Return only fields the client needs; enforce data access in a trusted backend. |
| Aggregation | BFF or domain API | Bound fan-out, deadlines and partial-failure behavior. |
| Client authentication | Gateway or BFF | Forward identity only across a trusted, authenticated connection. |
| Authorization | Domain service; sometimes BFF too | The service owning the data must enforce access to it. |
| Client-specific rate limits | Gateway or BFF | Choose limits from abuse risk and measured capacity. |
| Client-specific caching | BFF, gateway or cache layer | Include the right identity and vary dimensions; define freshness and invalidation. |
| Client-facing errors | BFF | Map errors safely; never expose internal stack traces. |
| Retries and circuit breaking | BFF or shared client | Retry only when the operation is safe to repeat; use deadlines and budgets. |
| Business rules | Domain service | Keep the rule consistent across clients. |
| Database access | Data-owning service | Avoid a BFF bypassing service authorization and transaction boundaries. |
| Service-to-service credentials | BFF runtime / identity layer | Use scoped credentials and rotate them through the platform. |

---

## What Does NOT Go in a BFF

**Business rules that must be shared.** If `mobile-bff/calculatePrice` is the only place that computes prices, other clients may duplicate or depend on mobile-specific code. Put the rule in the pricing service and let each BFF call it.

**Rule:** if two BFFs need the same logic, **extract it to a shared service**. BFFs are thin adapters; services own the domain.

```typescript
// Distributed monolith
// mobile-bff/src/pricing.ts
export function calculatePrice(cart: Cart): Price {
  // 200 lines of business logic
  return ...;
}

// Now web-bff has to call mobile-bff for pricing
// web-bff/src/checkout.ts
import { calculatePrice } from "mobile-bff/pricing";
```

```typescript
// BFF as thin adapter; pricing in the pricing service
// pricing-service/src/pricing.ts
export function calculatePrice(cart: Cart): Price {
  // 200 lines of business logic
  return ...;
}

// mobile-bff/src/checkout.ts
const price = await pricingService.calculatePrice(cart);
// BFF just orchestrates; doesn't own logic.
```

## Code Example

```typescript
// mobile-bff/src/routes/profile.ts
// Mobile BFF: small payload, image variants, locale formatting.

import express from "express";
import { userService } from "../services/user";
import { mediaService } from "../services/media";
import { formatCurrency, formatDate } from "../utils/locale";

export const profileRouter = express.Router();

profileRouter.get("/me", async (req, res) => {
  const { userId, locale } = req.user; // JWT payload

  // Two underlying service calls in parallel
  const [user, mediaPrefs] = await Promise.all([
    userService.getUser(userId),
    mediaService.getPreferences(userId),
  ]);

  // Mobile-specific: only the fields the mobile app uses
  res.json({
    id: user.id,
    displayName: user.displayName,
    avatar: {
      small: `${user.avatarUrl}?w=64`,
      medium: `${user.avatarUrl}?w=128`,
      large: `${user.avatarUrl}?w=256`,
    },
    memberSince: formatDate(user.createdAt, locale), // locale-aware
    preferredCurrency: mediaPrefs.currency,
    formattedBalance: formatCurrency(user.balance, mediaPrefs.currency, locale),
    // 14 fields → 6 fields; 18KB → 1.2KB
  });
});
```

```typescript
// web-bff/src/routes/profile.ts
// Web BFF: rich payload, full bio, activity inline.

profileRouter.get("/me", async (req, res) => {
  const { userId } = req.user;

  // Five service calls in parallel; web can afford this
  const [user, bio, activity, badges, preferences] = await Promise.all([
    userService.getUser(userId),
    userService.getBio(userId),
    userService.getRecentActivity(userId, 20),
    badgesService.getUserBadges(userId),
    preferencesService.getUserPreferences(userId),
  ]);

  // Web-specific: full payload, rendered HTML, sorted by recency
  res.json({
    id: user.id,
    displayName: user.displayName,
    email: user.email, // web can see
    bio: { markdown: bio.markdown, html: renderMd(bio.markdown) },
    avatar: { full: user.avatarUrl },
    memberSince: user.createdAt,
    balance: user.balance,
    activity: activity.sort((a, b) => b.ts - a.ts),
    badges,
    preferences,
    // 14 fields + 20 activity items + badges + preferences; 18KB → 220KB
  });
});
```

```typescript
// partner-bff/src/routes/profile.ts
// Partner BFF: minimal, different auth, different rate limit.

import { partnerAuth } from "../middleware/partner-auth";
import { partnerRateLimit } from "../middleware/partner-rate-limit";

profileRouter.get("/:userId", partnerAuth, partnerRateLimit(1000), async (req, res) => {
  const { userId } = req.params;
  const { partnerId } = req.partner; // OAuth client credentials

  // Field-level auth: partner can't see email or balance
  const user = await userService.getUser(userId, { fields: ["id", "displayName", "avatarUrl"] });

  res.json({
    id: user.id,
    displayName: user.displayName,
    avatar: user.avatarUrl,
  });
});
```

Notice how the **same domain question** (who is this user?) gets **three completely different responses** based on the client. That's the BFF pattern.

## Common Mistakes

- **Putting business logic in the BFF.** Creates a distributed monolith. Extract to a service.
- **Chains of BFF calls.** They add latency and make ownership harder to trace. Prefer calling domain services directly unless a deliberate composition boundary justifies the chain.
- **Sharing the BFF between teams.** Mobile and web teams fighting over a single BFF defeats the purpose. Each client team owns its BFF.
- **No compatibility plan.** A BFF can break when a service changes its response shape. Use a stable contract, compatibility tests, or another explicit change process.
- **Skipping aggregation.** Mobile BFF making the client make 5 round trips is not a BFF. Aggregate, then ship.
- **Bypassing auth at the BFF.** If the underlying service has its own auth, fine — but the BFF must enforce client-specific auth (e.g. "partners can't see email"). Trust no upstream.
- **Forgetting CORS / preflight for web.** Web BFFs that proxy internal services need CORS handling if the SPA is on a different origin.
- **No per-client rate limit.** Partner and mobile shouldn't share the same rate limit. Tag with client type.
- **Same response cache for all clients.** Web cache of "60s" might be wrong for mobile (need 5 min) and partner (need 0). Use per-client cache keys.
- **Deploying BFFs that aren't in the team's domain.** If the platform team owns all BFFs, you have a bottleneck. Each client team should own theirs.
- **Skipping traces.** A BFF that aggregates 5 service calls is exactly where distributed tracing pays off. Tag the root span with `client=mobile|web|partner`.

## Best Practices

1. **Each client team owns its BFF.** The mobile team owns mobile-bff. The web team owns web-bff. The platform team provides the underlying services.
2. **Keep BFFs focused on composition and response shaping.** Move reusable business rules to domain services.
3. **Keep service-call paths understandable.** Avoid BFF-to-BFF chains unless they have a clear ownership and failure model.
4. **BFFs have their own auth, rate limit, cache.** Per-client policies.
5. **BFFs propagate trace context.** The root span is tagged with `client=...`. Every downstream call carries `traceparent`.
6. **Set an SLO from the client experience.** Measure the end-to-end latency budget, then allocate only part of it to the BFF. Any sample p99 value is a proposed target until the product validates it with representative traffic.
7. **Use the same HTTP client / fetch lib for all BFFs.** Different retry / circuit-breaker configs are fine; rewriting the HTTP layer per BFF is waste.
8. **Version the BFF independently of the service.** A BFF can pin a service version; a new service release doesn't break the BFF.
9. **Consider GraphQL as a BFF.** If the payload-shaping cost is high, GraphQL is a natural fit (one schema, three clients).
10. **Run the BFF as a separate deployable** (not a Lambda function called from a gateway). Stateless, fast to deploy, easy to scale.

## When to Use BFF

| Scenario | Use BFF? |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Situation | Consider a BFF when… |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| One client | It still needs a distinct aggregation layer; client count alone does not decide. |
| Mobile and web | Their payload, network or interaction needs differ enough to justify separate shaping. |
| Partners and first-party clients | They need different stable contracts or release ownership; auth and limits can also live at the gateway. |
| Multiple client teams | Independent ownership is valuable enough to justify extra deployments. |
| Similar clients and payloads | A shared API is usually simpler. |
| Small product with no client-specific composition | A BFF may add more operational work than value. |

Client count is only a clue. Compare the cost of client-specific API logic with the cost of another service and its failure paths.

## BFF vs API Gateway

| Concern | API Gateway | BFF |
| ---------------------------------------------- | ------------------------------------------------------------- | -------------------------------- |
| **Routing** | Yes | Yes (own routing) |
| **Cross-cutting auth** (e.g. mTLS termination) | Yes | Inherited |
| **Rate limiting** | Often global defaults; may also enforce client-specific rules | May apply client-specific policy |
| **Payload shaping** | Minimal | **The whole point** |
| **Aggregation** | No | **The whole point** |
| **Client-specific business logic** | No | Should be minimal |
| **Team ownership** | Platform team | **Client team** |

**Pattern in production:** API gateway at the edge (TLS termination, global rate limit, CORS), BFFs behind the gateway (per-client logic, aggregation, shaping). They are complementary, not competing.

## BFF + GraphQL

GraphQL can serve a BFF role when clients benefit from selecting and composing fields. A shared GraphQL schema can serve several clients; separate schemas are not required by the BFF pattern.

```graphql
# Mobile schema (small payload)
type Query {
  me: MobileUser
}
type MobileUser {
  id: ID!
  displayName: String!
  avatar: Avatar!
  formattedBalance: String!
}

# Web schema (rich payload)
type Query {
  me: WebUser
}
type WebUser {
  id: ID!
  displayName: String!
  email: String!
  bio: Bio!
  activity: [Activity!]!
  badges: [Badge!]!
  preferences: Preferences!
}

# Partner schema (minimal payload)
type Query {
  user(id: ID!): PartnerUser
}
type PartnerUser {
  id: ID!
  displayName: String!
  avatarUrl: String!
}
```

Federation or schema composition can combine fields from underlying services. Decide who owns the schema and authorization rules; a separate schema per client also adds maintenance work.

**Trade-off:** GraphQL adds operational complexity (caching, N+1, query depth limits, query whitelisting). For B2B APIs, REST + BFF is often simpler.

## Performance Considerations

| Concern | BFF |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Latency added | Measure it; depends on network hops, runtime, and service fan-out |
| Network hops | +1 (client → BFF → services) |
| Aggregation cost | Parallel calls can reduce sequential waiting, but the slowest dependency and failure handling still affect the response |
| Cache effectiveness | Measure hit rate and staleness by key; per-client keys can improve fit but do not guarantee more hits |
| Bundle / payload size | Measure the response size before and after shaping |
| Failure domain | **Bigger** — if BFF is down, the client is down. Mitigate with HA + circuit breakers per downstream |
| Observability | Trace context propagates; tag root span with `client=...` |

## Example from the Pattern's Origin

SoundCloud's 2015 article describes a backend tailored to a particular frontend and discusses how to keep frontend-specific needs from distorting shared services. Treat it as one design example, not evidence that every product needs a BFF.

## Summary

- **BFF** = API layer shaped around a client experience; it may be deployed separately or as routes in a shared service.
- **What it does**: payload shaping, aggregation, client-specific auth, rate limit, cache.
- **What it does NOT do**: own business logic. That's in the underlying services.
- **Variants**: dedicated services, GraphQL schemas, API gateway routes.
- **BFF and API gateway can coexist**: the gateway commonly handles shared edge concerns; the BFF composes and shapes client responses.
- **In interviews: name the per-client optimization, name the team ownership, name what the BFF does NOT own.**

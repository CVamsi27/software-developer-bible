# API Authentication

Trace a protected object read. request → parse credential → validate trusted credential and lifecycle

## Definition

API authentication verifies the credential evidence presented by a caller and establishes a principal for the request. Authorization then decides whether that principal may perform the operation on the particular resource. Valid credentials alone do not grant access to every object.

> **Textbook Definition:** Authentication establishes a security principal by validating credential evidence under a trusted issuance and lifecycle contract. Authorization separately evaluates permissions, resource relationships and current policy for that principal's requested action.

## First Principles

A remote request can claim any user or tenant ID. The server needs evidence it trusts, not an asserted identity field. Bearer credentials can be replayed by whoever steals them, so issuance, TLS transport, storage, expiry and revocation belong to the same design.

The API also knows which object is being accessed. A signed subject claim does not prove ownership of an arbitrary path ID. Identity validation and resource authorization are therefore distinct checkpoints, even when one middleware performs part of both.

## How It Works


### 1. Trace a protected object read

```text
request → parse credential → validate trusted credential and lifecycle
                                              ↓ principal
                              authorize tenant + target + operation
                                              ↓
                             bounded domain read → permitted representation
```

If credentials are missing or invalid, return a `401 Unauthorized` response with the applicable `WWW-Authenticate` challenge and a safe error. If the request is forbidden, use the documented `403 Forbidden` or concealment `404 Not Found` policy. Do not turn dependency or storage outages into “invalid credentials” by catching every error under one `401` response.
Validate object ownership inside the authoritative query or transaction, not only through a broad role check.

### 2. Credential choices prove different things

| Mechanism | Validation | Lifecycle boundary |
| -------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Server session / opaque token | Resolve an unpredictable credential to current trusted state | Shared state can support scaling/revocation; protect lookup availability and expiry |
| Signed access token, such as JWT | Verify the trusted issuer's signature and intended claims | Local verification needs key rotation and may still need current revocation/permission state |
| API key | Validate a scoped machine/application credential | Hash appropriate high-entropy keys at rest, rotate, expire and restrict privileges |
| OAuth access token | Validate/introspect under the authorization server contract | Delegated authorization is distinct from user login; token need not be a JWT |
| HTTP Basic | Decode supplied username/password then verify them | Base64 is encoding; TLS is essential and repeated password exposure needs careful control |
| Client certificate | Verify configured certificate trust and client identity | Map certificate identity to permissions and manage renewal/revocation |

JWT is a format, not a default requirement or an encryption guarantee. OAuth2 is an authorization framework; OpenID Connect adds an identity/login contract. An ID token intended for a client is not automatically an API access token.
Sessions are not inherently unscalable, and a cryptographically valid access token may still represent a revoked or unauthorized principal.

### 3. JWT validation needs an intended token contract

Use a maintained library with an explicit algorithm allowlist and trusted key source. Validate issuer, audience, expiry, not-before where present and required subject/claim types. Separate access, refresh and other token contexts so a token intended for one purpose cannot be substituted for another.
Do not let an untrusted header select an arbitrary URL, file or query during key lookup.

Decoding reads claims; it does not authenticate them. A TypeScript cast also does not validate runtime claims. Keep signature keys/secrets out of code and fail startup when required configuration is absent.
Cache trusted issuer keys with an intentional rotation/failure policy and bounded lookup behavior; do not accept unverified tokens when retrieval fails.

A service credential authenticates an application or workload, not necessarily a user. Preserve delegation/actor context when required instead of pretending a client-credentials token proves an interactive user's identity.

### 4. An executable object-authorization boundary

This TypeScript example begins **after credential verification**. It does not mint or validate tokens. It shows why a principal and target tenant are separate inputs to the domain boundary.

```typescript
export type Principal = {
  subject: string;
  tenantId: string;
  permissions: readonly string[];
};
export type Invoice = { id: string; tenantId: string; ownerId: string; totalCents: number };
export function canReadInvoice(principal: Principal, invoice: Invoice): boolean {
  return principal.tenantId === invoice.tenantId &&
    (principal.subject === invoice.ownerId || principal.permissions.includes('invoice:read:any'));
}
const alice: Principal = { subject: 'alice', tenantId: 'a', permissions: [] };
console.log(canReadInvoice(alice, { id: '1', tenantId: 'a', ownerId: 'alice', totalCents: 100 }));
console.log(canReadInvoice(alice, { id: '2', tenantId: 'a', ownerId: 'bob', totalCents: 100 }));
console.log(canReadInvoice({ ...alice, permissions: ['invoice:read:any'] },
  { id: '3', tenantId: 'b', ownerId: 'alice', totalCents: 100 }));
// true, false, false (one value per line)
```

The privileged permission remains tenant-scoped in this sample. A real global-administrator policy would need a separate explicit authority. Read permission does not imply update/delete permission.
Apply the same check inside authoritative selection for sensitive data rather than fetching unauthorized rows for later presentation filtering.

With PostgreSQL connection pools, request tenant context must be scoped to the same transaction/connection as the query. A global `SET app.tenant_id` on an arbitrary pooled connection can leak context or miss the actual query connection. Bind values and use transaction-local settings under the RLS/data-access contract; an interpolated tenant ID is not safe SQL.

### 5. Refresh and logout change durable state

A refresh token grants continued token issuance and must not work as an access credential. Rotation replaces it while retaining a family relationship for reuse detection. Validate expiry/client/session status, then atomically consume the previous credential and persist its successor.
A lookup followed by separate mark-as-used and insert calls can race or leave the client without a usable replacement after a crash.

For public OAuth clients, current best practice requires sender-constrained refresh credentials or rotation. Concurrent legitimate refreshes and lost responses need a documented recovery policy; client-side single-flight helps but does not solve the server transaction. Record hashed/high-entropy token identifiers appropriately, avoid deterministic same-second signed refresh tokens without unique identity, and do not store raw credentials in broad logs.

Logout revokes the appropriate caller-owned session/refresh family. Deleting a supplied refresh token without validating its ownership is insufficient. Existing signed access tokens may remain valid until expiry unless resource servers enforce revocation/current state; describe this delay instead of promising instantaneous global logout.

### 6. Browser and OAuth boundaries

HttpOnly cookies reduce JavaScript access to the credential but do not stop an XSS script from issuing authenticated requests. Secure/SameSite/domain/path settings and CSRF defenses have distinct jobs. Browser localStorage exposes bearer tokens to script access; select storage with a deliberate threat model.
CORS is a browser response-access policy and does not replace authorization or CSRF controls.

For OAuth/OIDC authorization-code login, use the provider/client library's current protected flow: exact registered redirects, transaction-bound PKCE with S256, state/nonce protections under the chosen contract, trusted issuer discovery, and token validation. Current OAuth security guidance requires PKCE for public clients and recommends it for confidential clients. Bind the callback to the login attempt.
An emailed identity claim alone must not automatically link accounts across issuers; use a trusted issuer/subject mapping and explicit linking policy.

Do not copy an incomplete callback that exchanges any supplied code, omits correlation/PKCE and treats arbitrary userinfo as an existing account. The canonical [security authentication track](../../20.5-security/01-auth/INDEX.md) owns the full session/JWT/OAuth mechanisms; this chapter applies them to the API boundary.

## Decisions and mistakes

Choose expiry and refresh policy from risk, client lifetime, and revocation needs rather than imposing one universal 15-minute value. Rate-limit costly credential checks and recovery flows, use modern password hashing under the dedicated security guidance, and maintain generic safe credential failures without pretending uniform wording removes all enumeration and timing risks.

Track authentication/refresh/revocation failures, dependency outages and denied object access without logging tokens/passwords. Test wrong issuer/audience/type, expired credentials, cross-tenant IDs, refresh races, key rotation and logout delay. Authentication is one control; it does not by itself establish compliance or protect an unbounded API.

## Summary

Verify credential evidence under its actual lifecycle, then authorize the target resource and operation. Token format, browser storage, trusted propagation, rotation and revocation are separate decisions; secure API behavior depends on enforcing them together at the authoritative boundary.

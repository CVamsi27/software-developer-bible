# API Authentication

An authenticated user swaps `/invoices/1` for `/invoices/2` and reads another tenant's data because the handler verified the token signature without checking object ownership. Authentication establishes who the caller is; authorization still governs which resource and operation they may reach.

## Definition

API authentication verifies the credential evidence presented by a caller and establishes a principal for the request. Authorization then decides whether that principal may perform the operation on the particular resource. Valid credentials alone do not grant access to every object.

> **Textbook Definition:** Authentication establishes a security principal by validating credential evidence under a trusted issuance and lifecycle contract. Authorization separately evaluates permissions, resource relationships, and current policy for that principal's requested action.

## First Principles

A remote request can claim any user or tenant ID. The server needs evidence it trusts, not an asserted identity field. Bearer credentials can be replayed by whoever steals them, so issuance, Transport Layer Security (TLS) transport, storage, expiry, and revocation belong to the same design.

The API also knows which object is being accessed. A signed subject claim does not prove ownership of an arbitrary path ID. Identity validation and resource authorization are therefore distinct checkpoints, even when one middleware performs part of both.

## 1. Trace a protected object read

```text
request → parse credential → validate trusted credential and lifecycle
                                              ↓ principal
                              authorize tenant + target + operation
                                              ↓
                             bounded domain read → permitted representation
```

If credentials are missing or invalid, return a `401 Unauthorized` response with the applicable `WWW-Authenticate` challenge and a safe error. If the request is forbidden, use the documented `403 Forbidden` or concealment `404 Not Found` policy. Do not turn dependency or storage outages into "invalid credentials" by catching every error under one `401` response; validate object ownership inside the authoritative query or transaction rather than through a broad role check alone.

## 2. Credential choices prove different things

| Mechanism | Validation | Lifecycle boundary |
| ------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Server session or opaque token | Resolve an unpredictable credential to current trusted state | Shared state can support scaling and revocation; protect lookup availability and expiry |
| Signed access token, such as JSON Web Token (JWT) | Verify the trusted issuer's signature and intended claims | Local verification needs key rotation and may still need current revocation and permission state |
| API key | Validate a scoped machine or application credential | Hash appropriate high-entropy keys at rest, rotate, expire, and restrict privileges |
| OAuth access token | Validate or introspect under the authorization server contract | Delegated authorization is distinct from user login; token need not be a JWT |
| HTTP Basic | Decode supplied username and password then verify them | Base64 is encoding; TLS is essential and repeated password exposure needs careful control |
| Client certificate | Verify configured certificate trust and client identity | Map certificate identity to permissions and manage renewal and revocation |

JWT is a format, not a default requirement or an encryption guarantee. OAuth2 is an authorization framework; OpenID Connect adds an identity and login contract. An ID token intended for a client is not automatically an API access token. Sessions are not inherently unscalable, and a cryptographically valid access token may still represent a revoked or unauthorized principal.

## 3. JWT validation needs an intended token contract

Use a maintained library with an explicit algorithm allowlist and trusted key source. Validate issuer, audience, expiry, not-before where present, and required subject and claim types. Separate access, refresh, and other token contexts so a token intended for one purpose cannot be substituted for another. Do not let an untrusted header select an arbitrary URL, file, or query during key lookup.

Decoding reads claims; it does not authenticate them. A TypeScript cast also does not validate runtime claims. Keep signature keys and secrets out of code and fail startup when required configuration is absent. Cache trusted issuer keys with an intentional rotation and failure policy and bounded lookup behavior; do not accept unverified tokens when retrieval fails.

A service credential authenticates an application or workload, not necessarily a user. Preserve delegation and actor context when required instead of pretending a client-credentials token proves an interactive user's identity.

## 4. An executable object-authorization boundary

This TypeScript example begins **after credential verification**. It does not mint or validate tokens. It shows why a principal and target tenant are separate inputs to the domain boundary.

```typescript
export type Principal = {
  subject: string;
  tenantId: string;
  permissions: readonly string[];
};
export type Invoice = { id: string; tenantId: string; ownerId: string; totalCents: number };
export function canReadInvoice(principal: Principal, invoice: Invoice): boolean {
  return principal.tenantId === invoice.tenantId &&
    (principal.subject === invoice.ownerId || principal.permissions.includes('invoice:read:any'));
}
const alice: Principal = { subject: 'alice', tenantId: 'a', permissions: [] };
console.log(canReadInvoice(alice, { id: '1', tenantId: 'a', ownerId: 'alice', totalCents: 100 }));
console.log(canReadInvoice(alice, { id: '2', tenantId: 'a', ownerId: 'bob', totalCents: 100 }));
console.log(canReadInvoice({ ...alice, permissions: ['invoice:read:any'] },
  { id: '3', tenantId: 'b', ownerId: 'alice', totalCents: 100 }));
// true, false, false (one value per line)
```

The privileged permission remains tenant-scoped in this sample. A real global-administrator policy would need a separate explicit authority. Read permission does not imply update or delete permission; apply the same check inside authoritative selection for sensitive data rather than fetching unauthorized rows for later presentation filtering.

With PostgreSQL connection pools, request tenant context must be scoped to the same transaction and connection as the query. A global `SET app.tenant_id` on an arbitrary pooled connection can leak context or miss the actual query connection. Bind values and use transaction-local settings under the Row-Level Security (RLS) and data-access contract; an interpolated tenant ID is not safe SQL.

## 5. Refresh and logout change durable state

A refresh token grants continued token issuance and must not work as an access credential. Rotation replaces it while retaining a family relationship for reuse detection. Validate expiry, client, and session status, then atomically consume the previous credential and persist its successor. A lookup followed by separate mark-as-used and insert calls can race or leave the client without a usable replacement after a crash.

For public OAuth clients, current best practice requires rotation or sender-constrained tokens—such as **Demonstrating Proof-of-Possession (DPoP, RFC 9449)**, which binds access and refresh tokens to a client-held asymmetric key via a signed per-request proof header, or **mutual-TLS certificate-bound tokens (RFC 8705)** for workloads with client certificates. Concurrent legitimate refreshes and lost responses need a documented recovery policy; client-side single-flight helps but does not solve the server transaction. Record hashed, high-entropy token identifiers appropriately, avoid deterministic same-second signed refresh tokens without unique identity, and do not store raw credentials in broad logs.

Logout revokes the appropriate caller-owned session and refresh family. Deleting a supplied refresh token without validating its ownership is insufficient. Existing signed access tokens may remain valid until expiry unless resource servers enforce revocation and current state; describe this delay instead of promising instantaneous global logout.

## 6. Browser and OAuth boundaries

`HttpOnly` cookies reduce JavaScript access to the credential but do not stop a Cross-Site Scripting (XSS) payload from issuing authenticated requests. `Secure`, `SameSite`, domain, and path settings plus Cross-Site Request Forgery (CSRF) defenses have distinct jobs. Browser `localStorage` exposes bearer tokens to script access; select storage with a deliberate threat model. CORS is a browser response-access policy and does not replace authorization or CSRF controls.

For OAuth and OpenID Connect (OIDC) authorization-code login, use the provider and client library's current protected flow: exact registered redirects, transaction-bound Proof Key for Code Exchange (PKCE) with `S256`, state and nonce protections under the chosen contract, trusted issuer discovery, and token validation. Current OAuth security guidance requires PKCE for public clients and recommends it for confidential clients. Bind the callback to the login attempt; an emailed identity claim alone must not automatically link accounts across issuers without a trusted issuer and subject mapping and explicit linking policy.

Do not copy an incomplete callback that exchanges any supplied code, omits correlation and PKCE, and treats arbitrary userinfo as an existing account. The canonical [security authentication track](../../20.5-security/01-auth/INDEX.md) owns the full session, JWT, and OAuth mechanisms; this chapter applies them to the API boundary.

## Decisions and mistakes

Choose expiry and refresh policy from risk, client lifetime, and revocation requirements. Rate-limit costly credential checks and recovery flows, use modern password hashing under the dedicated security guidance, and maintain generic safe credential failures without pretending uniform wording removes all enumeration and timing risks.

Track authentication, refresh, and revocation failures, dependency outages, and denied object access without logging tokens or passwords. Test wrong issuer, audience, and type, expired credentials, cross-tenant IDs, refresh races, key rotation, and logout delay. Authentication is one control; it does not by itself establish compliance or protect an unbounded API.

## Summary

Verify credential evidence under its actual lifecycle, then authorize the target resource and operation. Token format, browser storage, trusted propagation, rotation, and revocation are separate decisions; secure API behavior depends on enforcing them together at the authoritative boundary.

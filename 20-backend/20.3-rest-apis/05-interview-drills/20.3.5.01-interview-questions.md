# REST API Interview Questions


## Definition

Use this bank to practice reasoning about HTTP contracts and API boundaries. Preserve the stated setup, trace one operation, then change a condition and explain the outcome. The examples are interview exercises, not verified company-frequency claims.

## First Principles

Remote effects, untrusted inputs and independently released clients produce uncertainty. A strong answer names the invariant, authority, budget and recovery identity rather than memorizing a technology list. The source chapters contain runnable mechanisms and their limits.

## Deep-Dive Answers

### Question 1: What is REST?

**Answer:** REST is a constrained architectural style, not a synonym for JSON CRUD. Name client-server, stateless communication, cache constraints, uniform interface, layered components and optional code on demand. The uniform interface includes resource identification, representations, self-descriptive messages and hypermedia controls.

Trace an order representation with a cancellation control: the client follows its understood relation, then the server validates current authorization/state and returns the new representation or a conflict. Resource state can remain in a database; statelessness concerns conversational context required to understand a request. JWT is not required. A practical resource-oriented HTTP API may use useful semantics without fully adopting hypermedia-driven REST.

Source: [REST constraints and transition trace](../01-design-and-contract/20.3.1.02-rest-principles.md).

### Question 2: What is the difference between PUT and PATCH?

**Answer:** PUT replaces the target's state according to its representation contract and is idempotent in intended effect. PATCH applies a documented patch operation and may be idempotent. Repeating an absolute assignment can be safe; repeating an increment or an array insertion may change the result again. Neither method gives authorization or prevents a concurrent stale write automatically.

For a version 7 edit, use a strong If-Match or domain version condition atomically with storage. If version 8 committed first, reject the stale condition and let the client reconcile. A later response can differ even when the repeated intended effect is idempotent; PUT can create a resource under its contract, and 200/204/201 outcomes are not fixed by the method alone. Do not spread arbitrary request fields over a stored entity.

Source: [HTTP method semantics](../02-http-mechanics/20.3.2.01-http-methods.md).

### Question 3: Design a URL Shortener API

**Answer:** Define creation, redirect, ownership, deletion and analytics contracts first. Validate allowed URL schemes and code alphabet/length; enforce code uniqueness atomically, retry random collisions within a budget and return a conflict for an already-owned custom code. A lookup before insert is not the concurrency guard. Cache entries must honor expiry, deletion and destination changes.

Select redirect/cache policy from mutability and analytics needs. Permanent redirects can be cached, while temporary redirects can also be cached when their headers allow it; 302 does not guarantee every click reaches your service. Decide whether analytics can lose events or need durable buffering and avoid blocking the redirect on an unbounded write. URL preview/fetch features add SSRF risks beyond simply returning a redirect.

Explain traffic, retention and hot-key behavior before choosing replicas or sharding. Illustrative tier limits and TTLs are proposals to measure, not default production facts.

Source: [Status/redirect semantics](../02-http-mechanics/20.3.2.02-status-codes.md) and [HTTP caching](../02-http-mechanics/20.3.2.04-http-caching.md).

### Question 4: How do you implement pagination?

**Answer:** Bound and strictly validate page size. Offset supports page-number access but can scan skipped rows and shift under inserts/deletes. A cursor is a continuation token; keyset seek is one implementation, not a separate mutually exclusive API scheme. Use a unique full sort tuple, lossless values and the same authorized filters/order on every page.

For descending rows 42/41/40 with one timestamp and limit 2, return 42 and 41 and encode timestamp plus 41. Fetch one extra row to establish hasMore; using the look-ahead row as the cursor would skip it. A live keyset avoids positional shifts but mutable ranks, filters and visibility can still cause gaps/repeats. O(1) request cost and snapshot completeness are not universal guarantees. Token encoding/signing is separate from authorization.

Source: [Executed tied-key pagination trace](../03-payloads-errors-integration/20.3.3.01-pagination.md).

### Question 5: Explain CORS and why it matters

**Answer:** CORS is a browser response-access contract, not server authentication. A cross-origin simple GET or safelisted POST can reach the server even when script cannot read its response. JSON content type or non-safelisted headers can trigger a preflight; if that fails, the browser does not send the actual non-simple request. Cookies alone do not cause preflight.

For credential-mode reads, allow an exact approved origin and credentials under the contract; wildcard Allow-Origin is incompatible. Vary dynamic origins, allow needed methods/headers and expose response headers that script must read. CORS does not replace CSRF defenses, and ordinary servers/curl do not enforce it. The actual request still needs authorization and input validation.

Source: [CORS byte/request trace and browser cases](../02-http-mechanics/20.3.2.03-cors.md).

### Question 6: How do you implement rate limiting?

**Answer:** Choose identity, resource cost, burst behavior, coordination scope and outage policy. A token bucket earns fractional tokens up to capacity and atomically spends cost; preserve fractions on rejected sub-second checks. A rate budget does not cap concurrent long-running jobs or queue size, so protect those separately.

Local buckets can protect one instance. A fleet-wide quota requires coordinated atomic admission or a documented approximation; a Redis pipeline or read-then-write sequence races. Use validated caller identity and trusted proxy handling, publish 429/retry guidance, and select fail-open/fail-closed/degraded behavior from the operation's risk. Multi-region partitioned budgets trade latency and overshoot; consistent hashing alone is not global enforcement.

Source: [Rate-limiter model and atomicity boundary](../04-edge-and-scale/20.3.4.01-rate-limiting.md).

### Question 7: Design authentication for a REST API

**Answer:** Start with client type, delegated access and revocation requirements. Sessions, opaque access tokens, signed tokens, scoped API keys and client certificates have different validation/lifecycle costs. OAuth 2 is an authorization framework; OIDC adds login identity. Verify trusted issuance, intended audience/type and expiry before authorizing the actual tenant/resource.

Refresh rotation needs atomic consume-and-replace and a policy for reuse, concurrency and lost responses. Logout may leave a signed access token valid until expiry unless resource servers check revocation/current state. HttpOnly reduces credential reads by JavaScript but does not make XSS harmless; cookie policies and CSRF defenses remain necessary. Choose browser storage deliberately and keep credentials out of logs/URLs.

Source: [API identity and object-authorization boundary](../04-edge-and-scale/20.3.4.04-authentication.md).

### Question 8: What is HATEOAS and why is it important?

**Answer:** Hypermedia as the engine of application state lets a client discover available transitions through representations instead of constructing every path. Relation names, media semantics, input requirements and methods must be understood; an unexplained links object is insufficient.

A pending order exposes cancellation; after shipment the next representation can omit that control. If the client follows an old control meanwhile, the server still enforces current state and authorization. Hypermedia can reduce URI coupling but does not erase schema, security or workflow dependencies. Judge its benefit for the client rather than treating level 3 as universally required or wasteful.

Source: [Maturity levels and appointment controls](../01-design-and-contract/20.3.1.04-rest-maturity-model.md).

### Question 9: How do you handle API versioning?

**Answer:** Version an incompatible replacement when preserving the old contract is impractical; compatibility includes units, ordering, defaults, enum/presence/error behavior and supported strict readers. Path, query, header and media negotiation all work with explicit selection and cache rules. Do not silently default unsupported values to the newest contract or redirect old clients to an incompatible serializer.

Keep old/new adapters over a shared domain model, publish fixtures and a migration guide, observe unresolved consumers and retire under the support policy. RFC 9745 Deprecation uses a structured-field date; Sunset uses an HTTP-date. Headers are lifecycle hints, not a migration or uptime guarantee. There is no universal N/N−1 support rule.

Source: [Versioned-server trace and lifecycle signals](../01-design-and-contract/20.3.1.03-versioning.md).

### Question 10: Design a REST API for a social media feed

**Answer:** Define feeds, posts, comments, reactions and media lifecycles with authentication/visibility rules. Choose an ordered feed continuation that includes the complete stable key or a ranking snapshot/version. A mutable personalized ranking needs an explicit live-view or snapshot policy; chronological cursor rules cannot be assumed to preserve arbitrary rankings.

Fetch limit + 1 to prove another page, cap fan-out and choose read-time, precomputed or hybrid assembly from measured traffic and freshness. Direct media transfer uses a private grant followed by verification/scanning of the exact version before publication. Creating a post invalidates more than its author's cache if followers' feeds contain it. Live events need reconnect and authoritative-state recovery, not only a WebSocket connection.

Source: [Pagination consistency](../03-payloads-errors-integration/20.3.3.01-pagination.md), [uploads](../03-payloads-errors-integration/20.3.3.04-file-upload-apis.md) and [API interactions](../01-design-and-contract/20.3.1.01-api-design-patterns.md).

## Interview Questions

### Beginner (10)

1. **What is REST?**
   Name REST’s constraints and distinguish resource state from conversational request context. A JSON route using GET is not by itself a complete uniform/hypermedia interface.

2. **What are the HTTP methods?**
   GET/HEAD are safe reads; POST requests processing; PUT replaces; PATCH applies a patch; DELETE removes the target association; OPTIONS describes communication options. Safety/idempotence and allowed bodies/statuses need their actual method contracts.

3. **What is a resource in REST?**
   A resource is an identified conceptual target; a representation describes its selected current state. A URI can identify a collection, order or operation without exposing an ORM row.

4. **What is idempotency?**
   Idempotence means repeated identical requests have the same intended server effect, not identical responses. Safe methods, PUT and DELETE are idempotent by semantics; POST/PATCH may need a documented operation identity or idempotent operation.

5. **What are the main HTTP status code classes?**
   1xx reports progress, 2xx successful handling, 3xx redirect/conditional outcomes, 4xx request-related failures and 5xx server-side failures. The class alone does not establish whether a timed-out write committed.

6. **What is the difference between 401 and 403?**
   401 indicates missing/invalid applicable authentication and requires an appropriate challenge. 403 is refusal under policy and does not always imply authentication already succeeded. A service can conceal a protected object with 404 under its contract.

7. **What is a URI?**
   A URI identifies a resource. A URL is a kind that supplies a location/access mechanism; define how relative links resolve and never treat possession of an identifier as authority.

8. **What is content negotiation?**
   Accept expresses desired response media; Content-Type describes the supplied representation. Select a supported response, emit its type and vary caches appropriately. Unsupported request media and unacceptable response negotiation are different errors.

9. **Why use plural nouns in URIs?**
   Plural collection names are a consistency convention. They can make collections legible but do not define REST compliance or the authority/behavior of a route.

10. **What is a stateless API?**
   Each request supplies the context needed to understand it instead of depending on stored conversational state. Domain resources and durable operation records may remain on the server; JWT is not a requirement.

### Intermediate (10)

11. **Explain HATEOAS**
   Clients follow meaningful representation controls to advance a workflow. They still need known media/relation semantics and must handle stale controls; links do not bypass authorization or current-state checks.

12. **What is API versioning?**
   A version selects an external contract. Supported old clients retain their behavior while incompatible replacements have opt-in selection, compatibility evidence and migration/retirement policy.

13. **What is the difference between PUT and PATCH?**
   PUT defines replacement under the representation contract; PATCH applies a format-specific change. Use validation and atomic version conditions where concurrent updates matter; neither authorizes arbitrary fields.

14. **How do you implement pagination?**
   Validate bounded limits, select offset or an explicit cursor implementation and use a unique lossless sort key. Fetch one look-ahead row, bind the query contract and authorize every page. A live cursor is not a snapshot.

15. **What is CORS?**
   CORS controls when browser script may access a cross-origin response. Some denied simple requests still execute; preflight can block non-simple actual requests. It is independent of authentication and CSRF protection.

16. **What is rate limiting?**
   A limiter admits work against a budget by identity/cost/time. State scope and atomicity determine accuracy; rate, concurrency and queue bounds protect different resources.

17. **What is an API gateway?**
   A gateway applies shared edge routing/transport policy. It adds capacity/failure costs and must preserve trustworthy forwarding; domain services retain authoritative resource checks.

18. **How do you handle errors in REST APIs?**
   Return consistent status/headers plus stable safe machine fields. Problem Details is one format; public detail must not expose internal messages. Retryability depends on effect identity and the possibility of an already-completed write.

19. **What is content negotiation?**
   Negotiate a supported representation through the documented header/media contract. Test alternatives and cache variants; a regex matching one Accept substring is not a full quality-aware parser.

20. **What is the Richardson Maturity Model?**
   Levels describe transport tunnel, resource targets, HTTP semantics and hypermedia controls. They do not score security, transaction correctness, all REST constraints or production readiness.

### Senior (10)

21. **Design a URL shortener API**
   Define create/redirect/ownership/deletion/analytics contracts. Enforce code uniqueness atomically, constrain destinations and cache invalidation, and choose redirect freshness with mutability and analytics requirements.

22. **How do you version a REST API?**
   Choose one unambiguous path/query/header/media selection rule. Preserve old adapters, validate unsupported selectors and cache variants, communicate valid deprecation/sunset signals and test representative consumers.

23. **Explain cache strategies for REST APIs**
   Separate storage, freshness, validation and cache identity. ETags can reduce transfer; private/no-store and Vary serve different rules. Conditional writes require atomic strong-version comparison, while CDN reuse needs explicit public scope.

24. **How do you handle N+1 query problems?**
   Observe query counts, then batch/eager-load appropriate bounded relations. GraphQL can produce N+1 too; introducing it does not solve the resolver/data-access pattern by itself.

25. **Design a REST API for microservices**
   Start from service ownership and client contracts. A gateway may stabilize public routing, while bounded calls, trusted identity, domain authorization, compatibility, deadlines and recovery need service-level designs.

26. **How do you ensure API security?**
   Validate identity and object/tenant authorization, control input/output and resource work, protect transport and credentials, and observe failures. CORS applies to browser access; it is not a server-to-server security boundary.

27. **Explain eventual consistency in REST**
   Eventual consistency describes a replica/projection lag contract, not a universal property of REST. Specify what reads may be stale, how a caller follows its own write and which invariants require an authority.

28. **How do you handle file uploads?**
   Choose proxy/direct/resumable transfer from client and resource needs. Authorize the key, verify actual size/checksum, scan an immutable version and publish only that approved identity; a presigned URL is not inherently one-time.

29. **Design a REST API for real-time features**
   Combine ordinary authoritative reads with SSE for server push or WebSocket for two-way messages when appropriate. Define event identity, retention, reconnection, backpressure and fallback rather than promising live delivery alone.

30. **How do you test REST APIs?**
   Test contract status/headers/body, tenant/object denial, malformed inputs, stale versions and retries under lost responses. Include meaningful database/integration, load/resource and failure-recovery evidence; a mock alone does not prove deployment behavior.

### FAANG-style (10)

31. **Design a global rate limiting system**
   Define exact versus approximate scope, authority/partitioned budgets, atomic decisions, clock and failover policies. Regions and consistent hashing introduce failure/overshoot trade-offs rather than automatically making counters global.

32. **How would you migrate from v1 to v2 without breaking changes?**
   Offer both contracts while keeping the supported old behavior. Use compatibility fixtures and migration guidance, measure unresolved consumers and retire deliberately; feature flags alone do not update old clients.

33. **Design authentication for a multi-tenant SaaS**
   Bind a verified principal to current tenant/resource policy and transaction-scoped data access. RLS may add enforcement but pooled context must stay on the same transaction/connection. Test cross-tenant identifiers and role changes.

34. **Design a webhook delivery system**
   Commit producer event/intent together, verify raw signed deliveries, commit durable receiver inbox/work before acknowledgment, and make business effects duplicate-safe. Bound retries/replay, handle ordering and protect callback destinations.

35. **How do you handle API design for mobile apps?**
   Account for intermittent connections, limited transfer and slow upgrades. Bound responses, preserve offline conflict/operation identity and support a realistic compatibility window; compact payloads cannot replace authorization or recovery.

36. **Design a payment processing API**
   Keep amounts/units explicit, create durable operation identity and atomically couple local changes with send intent. Reconcile unknown provider outcomes, verify callbacks and record an audit trail. Integration architecture alone cannot certify payment compliance.

37. **How would you implement API analytics?**
   Measure latency, outcome classes, route/client usage and resource pressure with bounded labels and redacted logs. Distinguish edge-accepted, completed and downstream-unknown operations before using metrics for billing or success claims.

38. **Design a real-time collaboration API**
   Choose ordered or convergent edit semantics from collaboration needs. WebSocket carries messages; server authority/CRDT/operational-transform rules, persistence, acknowledgment, reconnect and presence expiry handle concurrency and recovery.

39. **How do you handle API design for IoT devices?**
   Choose device identity, enrollment/revocation, connectivity and protocol requirements. MQTT may fit constrained event exchange but needs its own session/QoS/topic authorization rules. HTTP translation must preserve security and value semantics.

40. **Design an API marketplace**
   Define developer enrollment, scoped credentials, discoverable contracts, durable usage accounting and billing reconciliation. Quota checks are not authoritative billing evidence unless metering semantics and failure recovery are specified.

### Follow-ups (10)

41. **What are the tradeoffs between REST and GraphQL?**
   Compare resource/HTTP semantics with schema-selected fields and resolver work. Either can cache under the right keys/contracts. Measure fan-out, client tooling, compatibility and operations; avoid categorical speed or suitability rules.

42. **How do you handle API design for different clients?**
   Use a shared contract where needs overlap, selected fields or a BFF where composition differs materially. Keep domain rules/access authoritative and bound per-client fan-out, caches and release compatibility.

43. **What is API-first design?**
   Agree on capabilities and wire/error/security behavior before implementation. A machine description enables mocks and parallel work, while real implementation/consumer tests establish that the agreed behavior exists.

44. **How do you handle backward compatibility?**
   Preserve documented field meanings, types, presence, units and outcomes. Additive changes can still break strict clients or enum handling; test them and offer an opt-in replacement when compatibility cannot hold.

45. **What is contract testing?**
   Contract tests check consumer/provider expectations and schema behavior; some run against a real provider or an adapter. They complement broader integration/end-to-end tests rather than proving all system behavior without integration.

46. **How do you handle API design for internationalization?**
   Keep machine timestamps, zones, units and currency codes explicit, then localize presentation where appropriate. Accept-Language can select text and requires correct cache variation; it does not select an exchange rate or convert money automatically.

47. **What is API governance?**
   Govern standards, ownership, compatibility/security review and exceptions with executable checks and evidence. A naming checklist alone does not establish correctness or independent deployability.

48. **How do you handle API deprecation?**
   Announce scope, rationale, replacement and timeline, emit valid date-based lifecycle hints, observe remaining users and support migration. Deprecation does not itself change a resource’s behavior, and sunset hints do not guarantee availability.

49. **What is API design-first approach?**
   Author a reviewed description and implement its contract, or generate under a code-first authority. Test real status/headers/schemas and consumers; Swagger UI or code generation does not enforce runtime authorization.

50. **How do you handle API design for accessibility?**
   Provide stable meaningful fields, localized safe errors and data clients can present accessibly. Keyboard navigation and screen-reader interaction belong in client UI tests; an API alone cannot certify those experiences.

## Summary

Explain the contract, trace the effect and identify what changes under retries, stale state, another client version or a failed dependency. Link choices to their conditions and evidence rather than promising universal behavior.

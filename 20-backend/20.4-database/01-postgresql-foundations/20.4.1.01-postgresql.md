# PostgreSQL for Backend Engineers

>
> **Why it matters:** This is a Backend interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

PostgreSQL is a database server that stores related facts in tables and accepts SQL requests from clients. A table describes one kind of fact; columns describe its attributes; constraints reject invalid combinations. A transaction groups changes into one commit or rollback. PostgreSQL also supports document-shaped values, custom types and extensions without giving up its relational model.

> **Textbook Definition:** PostgreSQL is an extensible object-relational database management system. It combines SQL execution, integrity constraints, multi-version concurrency control and write-ahead recovery; isolation and durability configuration determine the precise guarantees.

## First Principles

Consider an API that records an order. It needs more than a file containing JSON. Two requests might reserve the same unit, a customer reference might point to nobody, or the machine might fail between writing the order and reducing stock.

The server must therefore coordinate concurrent changes, reject states outside the schema's rules and recover after a crash. Those jobs are related but distinct: a foreign key checks references; isolation controls interference between transactions; a recovery log protects durable changes. None replaces the others. Indexes address another constraint: finding a small set of rows should not require reading every unrelated row.

## How It Works

### Follow a request from client to rows

A **client** is a program such as `psql` or a Node.js database driver. A **connection** is its communication channel to the server; a **session** is the associated server-side state, including settings and an open transaction. A pool lets many application requests reuse a bounded set of connections.

```text
HTTP request → application → application pool → PostgreSQL backend process
                                               │
                                      SQL parse and validation
                                               ↓
                                        planner → executor
                                               │
                                    shared pages, locks and WAL
                                               ↓
                                   result rows → application
```

The main `postgres` process accepts connections and starts a backend process for each. That backend handles the connected client's statements. Pooling belongs to the application or a separate service such as PgBouncer; it is not a built-in pool inside the supervisor. Clients can connect over TCP or a local Unix socket.

The parser recognizes SQL syntax. Analysis resolves names and types; rewriting can incorporate views and policies. The **planner** chooses an execution plan, such as an index scan followed by a join. The **executor** follows that plan and returns rows. It also applies relevant checks and concurrency rules. A plan is a choice based on estimates, not a promise that a query will always use its index.

Authentication determines which database role connects. SQL privileges determine which objects that role may access. Neither proves that an API user is entitled to a particular customer's data: application authorization and any row-level policy still need an explicit design.

### Shared pages and per-operation memory have different owners

PostgreSQL reads table and index **pages**, fixed-size blocks of storage, into `shared_buffers`, a cache shared by backend processes. The operating system also caches files. A cache miss in PostgreSQL therefore does not by itself prove physical disk I/O.

A sort or hash operation can need working memory while executing a plan. `work_mem` is a base limit for individual operations, not a single allocation for the whole server or query. Multiple plan nodes, workers and sessions can consume memory concurrently; hash operations also use `hash_mem_multiplier`. Maintenance work such as building an index uses a separate budget, `maintenance_work_mem`, with its own operation and worker rules.

`effective_cache_size` is different: it tells the planner how much cache is plausibly available. It does not reserve that memory. Inspect settings with `SHOW` and measure spills and concurrency before increasing budgets; the [performance chapter](20.4.1.05-postgresql-performance.md) owns the tuning workflow.

### WAL makes recovery possible without flushing every table at commit

A modified cached page is **dirty**: its in-memory content differs from the data file. PostgreSQL records changes in the **write-ahead log (WAL)**. The corresponding WAL must reach durable storage before the dirty data page is written to permanent storage.

```text
change → WAL records + dirty cached pages
                  │                 │
             durable WAL       later page writes
                  │                 │
          durable commit       checkpoint progress
                  │
        crash → recovery replays required WAL
```

With normal durable settings (`fsync` enabled and an appropriate `synchronous_commit` setting), a commit waits for the required WAL flush, not a rewrite of every changed table page. The checkpointer and background writer spread page writes over time; checkpoints bound how far recovery must replay. WAL writing and page writing overlap, so the diagram is a dependency model rather than three mutually exclusive phases.

If the server crashes after durable commit but before a changed page is saved, recovery can redo that change from WAL. If a transaction never committed, its changes must not become committed application data. Asynchronous commit can acknowledge before local WAL is durable and therefore lose recently acknowledged transactions after a crash. Disabling `fsync` has a more severe corruption risk. WAL protects recovery on surviving storage; it does not replace backups or a verified failover plan.

### MVCC controls visibility, while constraints control valid states

An update creates a later row version. Ordinary readers choose versions visible to their snapshot. At default Read Committed isolation, each statement gets a fresh snapshot; a transaction does not automatically freeze all later reads. Same-row writes can still block each other.

The [MVCC chapter](20.4.1.03-mvcc.md) owns the two-session trace. A unique constraint, foreign key or check constraint establishes a different rule: which data states are allowed. Use both concurrency controls and constraints when needed. A transaction that reads stock and then writes an unconditional decrement is not safe merely because it uses PostgreSQL.

## Code Examples

### Create related facts, then observe a rejected reference

Use PostgreSQL 16 or later in a disposable database. These names are local to this example; run once or use a fresh schema when repeating it.

```sql
CREATE TABLE customers (
    id integer PRIMARY KEY,
    name text NOT NULL,
    email text NOT NULL UNIQUE
);
CREATE TABLE orders (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id integer NOT NULL REFERENCES customers(id),
    total numeric(10, 2) NOT NULL CHECK (total >= 0),
    status text NOT NULL CHECK (status IN ('pending', 'paid', 'shipped')),
    created_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO customers VALUES (1, 'Ada', 'ada@example.test');
INSERT INTO orders (customer_id, total, status)
VALUES (1, 12.50, 'paid'), (1, 7.50, 'pending');

SELECT c.name, sum(o.total) AS paid_total
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid'
GROUP BY c.id, c.name;
-- Ada | 12.50
```

The foreign key connects each order to an existing customer. The join follows that link, the filter retains the paid order, and aggregation produces one result for Ada. `numeric` represents decimal amounts exactly within its declared precision; the currency and rounding policy are still application decisions. `timestamptz` stores an instant and displays it in the session's time zone; it does not preserve the original named time zone.

Try the following statement independently, outside a transaction you intend to keep:

```sql
INSERT INTO orders (customer_id, total, status)
VALUES (999, 3.00, 'pending');
-- ERROR: foreign-key violation (SQLSTATE 23503)
```

No customer 999 exists, so no order is inserted. A `CHECK` alone would allow null unless `NOT NULL` also excludes it. `UNIQUE` alone does not require a value either. Constraints encode precise rules, not a general promise that all business facts are correct.

### Roll back a group of writes on one connection

```sql
BEGIN;
UPDATE orders SET status = 'shipped' WHERE id = 1;
SELECT status FROM orders WHERE id = 1;
-- shipped: the transaction sees its own preceding update
ROLLBACK;
SELECT status FROM orders WHERE id = 1;
-- paid
```

Rollback cancels the update. In an application, every statement between BEGIN and COMMIT or ROLLBACK must use the same checked-out connection. Two calls to a pool's convenience query method need not use the same session. Release the connection in a `finally` block after ending the transaction; otherwise requests can exhaust the pool or inherit unfinished session state.

### Extend the value model without changing the transaction model

A column can hold an array or a `jsonb` document. For example, tags stored as `text[]` form a collection within one value, while `jsonb` can hold optional product attributes. Choose these when the value is naturally owned and replaced by one row. Independently referenced entities or relationships that need foreign keys usually belong in separate tables.

`->` extracts JSON while `->>` extracts text; that difference changes comparisons and sorting. GIN indexes organize searchable elements of composite values, while B-tree indexes can support a particular extracted scalar. A whole-document index does not accelerate every expression. The [JSONB chapter](../02-querying-and-optimization/20.4.2.05-jsonb.md) owns the complete operator and index examples.

A **common table expression (CTE)** names a query result inside one statement; a recursive CTE repeatedly expands from initial rows, such as a manager to direct reports. Cyclic input needs a termination strategy. A **window function** calculates over related rows while retaining those rows, unlike GROUP BY, which collapses them. The [window-functions chapter](../02-querying-and-optimization/20.4.2.04-window-functions.md) owns the ordering and frame trace.

## Real-World Decisions

### Keep one durable owner and make derived data rebuildable

An order table can be authoritative while a search index and dashboard are derived copies. A database transaction does not automatically commit changes in all three systems. Define how publication retries, duplicate events and rebuilding work before adding another store.

A materialized view stores the result of a query and changes only when refreshed. It can make an expensive dashboard cheap to read, but readers accept a freshness gap. `REFRESH ... CONCURRENTLY` needs an already populated view and an eligible unique index; it is not a free modifier for any view. Verify that a join counts orders once rather than counting one order per line item.

### Use extensions and ORMs with a versioned contract

An **extension** installs database objects implementing a feature, such as text similarity or a custom data type. Availability and installation privileges depend on the service. An ORM such as Prisma maps application operations to SQL; it does not remove the need to know isolation, indexes or migrations. The [Prisma chapter](../04-orm-and-access/20.4.4.01-prisma.md) owns its current setup and schema syntax.

### Choose PostgreSQL from requirements

PostgreSQL is useful when transactions, relational constraints and varied queries match the workload. Large tables do not automatically require another database: selective queries, partitioning and operational capacity matter. Search relevance, graph traversal or very large analytical scans may justify a specialized system. The [database-choice chapter](20.4.1.04-nosql-vs-sql.md) develops those decisions.

## Common Mistakes

| Mistake | Why it fails | Better decision |
| ---------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------- |
| Create a pool for each request | Repeated connection setup and unbounded aggregate connections | Reuse a bounded pool and budget all instances |
| Interpolate a SQL value | User text becomes executable syntax | Bind values; allowlist identifiers that cannot be bound |
| Assume an index guarantees speed | Low selectivity can make a scan cheaper | Inspect the plan with representative data |
| Treat a commit as protection from every outage | Durability settings, storage and replica state matter | Document and test recovery requirements |
| Skip vacuum on a managed service | Old versions and transaction IDs still need maintenance | Monitor maintenance and retained snapshots |

## Best Practices

Keep the application role separate from the migration/administration role. Restrict table privileges and protect database credentials and transport. Add database constraints for invariants that SQL can express; use explicit authorization for the caller's access.

Measure before changing configuration. `EXPLAIN ANALYZE` executes the statement, including writes, so diagnostic use must respect side effects and load. Bulk loading with server-side `COPY` reads the server's filesystem; `psql`'s `\copy` uses the client. Partitioning helps when query or retention boundaries match partition keys, and needs future partitions ready before writes arrive.

Monitor pool queueing, statement and transaction age, storage capacity, replica lag and vacuum progress. Test restoration from backups, not just successful backup creation. Design application retries to distinguish a confirmed rollback from an uncertain commit after a network failure; an idempotency key or reconciliation query may be needed.

## Summary

PostgreSQL coordinates SQL execution, constraints, row-version visibility and durable recovery. A client session owns transaction state; a backend executes its statements using shared storage and caches. WAL protects recoverable durable changes, while MVCC and locks handle concurrent access. Good application design makes ownership, isolation, authorization and recovery explicit instead of relying on the database's feature list.

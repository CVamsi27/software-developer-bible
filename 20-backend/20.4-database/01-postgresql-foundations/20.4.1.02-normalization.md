# Database Normalization

How do dependencies change the table boundaries? A **functional dependency** `X → Y` means that any two valid rows agreeing on X must also agree on Y.

## Definition

Normalization organizes relational tables according to which facts determine other facts. It separates facts that otherwise repeat and can disagree, then reconnects them with keys. Normal forms are tests of those relationships; they are not a requirement to split every column into another table.

> **Textbook Definition:** Relational normalization decomposes relations using dependencies to reduce redundancy and modification anomalies. A decomposition must be checked for lossless reconstruction and, separately, preservation of its dependencies.

## First Principles

Suppose every order line repeats a customer's email. Changing one line leaves two answers to “what is this customer's current email?” A transaction can update all copies, but every future write path must remember the same rule. Separating the current customer fact gives that fact one owner.

The same duplication explains two other failures. You cannot register a customer if the only table requires an order, and deleting their last order removes the only record of the customer. These are **insertion** and **deletion anomalies**.
Normalization derives table boundaries from facts and their dependencies so that changing one fact does not accidentally change another.

The word *current* matters. An invoice's purchased price and shipping destination can be historical facts owned by that invoice. They are not duplicate copies of the customer's current address or product's current price.

## 1. How do dependencies change the table boundaries?

#### Establish keys and dependencies before choosing a form

A **functional dependency** `X → Y` means that any two valid rows agreeing on X must also agree on Y. It is a rule of the domain, not a coincidence in today's sample. A **determinant** is the X side of that rule.

A **superkey** determines all attributes in the relation. A **candidate key** is a minimal superkey: no part can be removed while keeping that property. The **primary key** is the candidate key chosen for SQL identification.
An attribute belonging to any candidate key is **prime**; other attributes are non-prime. Adding a generated ID gives convenient identity but does not remove dependencies among the other columns.

For our order example, assume:

- Each order has a customer and order date: `order_id → customer_id, order_date`.
- Each customer has one current email: `customer_id → customer_email`.
- Each product has one current catalog name: `product_id → product_name`.
- Each order has at most one line per product: `(order_id, product_id) → quantity, purchased_unit_price`.

That last condition determines the line key. If a product can appear twice with different options or prices, use a line identifier instead; the proposed key would reject valid orders.

#### First normal form gives line facts rows

A design with `product1`, `product2`, and `product3` columns imposes an arbitrary item limit and requires different expressions to query each position. Represent each item as a row instead:

| order_id | product_id | customer_id | customer_email | product_name | quantity | purchased_unit_price |
| -------- | ---------- | ----------- | ---------------- | ------------ | -------: | -------------------: |
| 10 | 101 | 1 | ada@example.test | Pen | 2 | 3.00 |
| 10 | 102 | 1 | ada@example.test | Notebook | 1 | 5.00 |
| 11 | 101 | 1 | ada@example.test | Pen | 1 | 3.00 |

**First normal form (1NF)** describes a relation whose attribute values are single values from their domains, without repeating groups in the relational representation. What counts as a domain value depends on the model: SQL arrays and documents exist, so “never use an array” is not a complete normalization test. Our row model makes item identity and dependencies explicit.

The key is `(order_id, product_id)`, not `order_id` alone. Order 10 needs two rows. Converting columns to rows resolves the repeating-group problem, but email and product name still repeat.

#### Second normal form separates facts depending on only part of a key

`product_id` alone determines the product name, and `order_id` alone determines customer and date. They each need only part of the line's composite key. A **partial dependency** means a non-prime attribute depends on a proper subset of a candidate key.

**Second normal form (2NF)** requires 1NF and no such partial dependency on any candidate key. Split the sample into:

```text
Products(product_id, product_name)
Orders(order_id, customer_id, customer_email, order_date)
OrderItems(order_id, product_id, quantity, purchased_unit_price)
```

The line's quantity and purchased price belong to the entire line key under our assumptions. Product name belongs to Products. Customer email no longer repeats for every line, but still repeats for every order from the same customer.
The remaining problem is different from a partial-key dependency.

#### Third normal form separates a fact reached through another non-key fact

In Orders, `order_id → customer_id → customer_email`. The email is a fact about the customer, reached indirectly through the order. Moving it into Customers removes that **transitive dependency** in this example:

```text
Customers(customer_id, customer_email)
Orders(order_id, customer_id, order_date)
Products(product_id, product_name)
OrderItems(order_id, product_id, quantity, purchased_unit_price)
```

**Third normal form (3NF)** formally requires each non-trivial dependency `X → A` to have X as a superkey or A as a prime attribute. *Non-trivial* means A is not already contained in X. The common shortcut “no non-key attribute depends on another non-key attribute” explains simple schemas, but the prime-attribute exception matters when candidate keys overlap.

#### BCNF removes a dependency that 3NF can still permit

Consider `Teaching(student, course, instructor)`. Assume a student has one instructor per course, and each instructor teaches exactly one course. Then:

```text
(student, course) → instructor
instructor → course
```

Both `(student, course)` and `(student, instructor)` are candidate keys. Therefore all three attributes are prime, and the relation satisfies 3NF. However, `instructor` does not determine the student: it is not a superkey.
Its course repeats for every student.

**Boyce–Codd normal form (BCNF)** requires the determinant of every non-trivial functional dependency to be a superkey. Decompose into `InstructorCourse(instructor, course)` and `StudentInstructor(student, instructor)`. Joining on instructor reconstructs the original rows because each instructor has only one course. That makes the split **lossless**: it introduces no invented student/course/instructor combinations.

There is a cost. The original rule “one instructor per student per course” now spans the two tables. Separate uniqueness constraints cannot fully enforce it.
This split loses **dependency preservation**, the ability to enforce all original dependencies locally without joining tables. Depending on the requirement, retaining 3NF with local constraints may be preferable to BCNF with cross-table enforcement. BCNF does not mean every conceivable domain rule is solved.

## 2. What does this decomposition preserve?

#### Run the customer and order-line decomposition

Use a fresh PostgreSQL 16+ database or schema. This implements the dependencies stated above; it is independent of the PostgreSQL overview's fixture.

```sql
CREATE TABLE norm_customers (
    customer_id integer PRIMARY KEY,
    email text NOT NULL
);
CREATE TABLE norm_products (
    product_id integer PRIMARY KEY,
    name text NOT NULL,
    current_price numeric(10, 2) NOT NULL CHECK (current_price >= 0)
);
CREATE TABLE norm_orders (
    order_id integer PRIMARY KEY,
    customer_id integer NOT NULL REFERENCES norm_customers(customer_id),
    order_date date NOT NULL
);
CREATE TABLE norm_order_items (
    order_id integer REFERENCES norm_orders(order_id),
    product_id integer REFERENCES norm_products(product_id),
    quantity integer NOT NULL CHECK (quantity > 0),
    purchased_unit_price numeric(10, 2) NOT NULL CHECK (purchased_unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);
INSERT INTO norm_customers VALUES (1, 'ada@example.test');
INSERT INTO norm_products VALUES (101, 'Pen', 3.00), (102, 'Notebook', 5.00);
INSERT INTO norm_orders VALUES (10, 1, DATE '2026-10-08'), (11, 1, DATE '2026-10-08');
INSERT INTO norm_order_items VALUES (10, 101, 2, 3.00), (10, 102, 1, 5.00), (11, 101, 1, 3.00);

UPDATE norm_customers SET email = 'ada.new@example.test' WHERE customer_id = 1;
SELECT o.order_id, c.email, sum(i.quantity * i.purchased_unit_price) AS total
FROM norm_orders o
JOIN norm_customers c USING (customer_id)
JOIN norm_order_items i USING (order_id)
GROUP BY o.order_id, c.email
ORDER BY o.order_id;
-- 10 | ada.new@example.test | 11.00
-- 11 | ada.new@example.test |  3.00
```

One email update changes the answer for both orders because both references resolve to the same customer row. The join reconstructs line context without storing the current email in each line. A customer can exist before placing an order, and removing order lines does not remove the customer.

Now update `norm_products.current_price` for product 101 to `4.00` and repeat the query. Totals stay `11.00` and `3.00`: purchased price is an order-line fact. Recalculating old orders from today's catalog price would change their history.
Storing an immutable invoice address works for the same reason; reference a historical snapshot or store the invoice-owned values under an explicit retention policy.

Keys and foreign keys enforce the demonstrated dependencies, but not every business rule. For example, SQL can still represent an order with no items. If a completed order must have an item, its lifecycle needs additional enforcement.
Cross-row invariants require transaction and concurrency reasoning as well as table design.

## 3. Where do normalization rules meet product decisions?

#### Denormalization makes a new consistency obligation

**Denormalization** deliberately stores a repeated or derived fact to reduce read work. Suppose the UI needs `order_total` without aggregating lines. Choose its owner and update contract:

| Approach | When the result changes | Failure boundary |
| --------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------- |
| Compute from lines | Every query | Read cost, with no separate copy to repair |
| Update total in the same transaction as lines | At the line commit | All insert/update/delete paths must maintain it; concurrent writers need safe mutations |
| Materialized view | At successful refresh | Stale between refreshes; failed refresh retains an older result |
| Event-fed projection | After consumer applies the event | Lag, duplicates and out-of-order events need handling and rebuild support |

An insert-only trigger is insufficient if reviews or lines can later change or be deleted. A trigger that recomputes an aggregate under concurrent writes also needs a locking/isolation design; “use a trigger” does not establish correctness. Decide whether temporary staleness is acceptable before selecting asynchronous maintenance.

When building a revenue projection, aggregate line amounts or ensure each order appears once. Joining Orders to OrderItems and summing the order total counts a multi-item order repeatedly. This is a query-grain problem, not proof that normalization itself is too slow.

#### Separate domain evolution from unnecessary lookup tables

A list of phone labels that never changes can be a check constraint. A separately managed list with metadata, localization or administrative changes can justify a referenced table. These choices do not imply that one phone per customer is sufficient.
Decide relationship cardinality first, then how to represent its labels.

Normalize according to actual rules and expected lifecycle; measure queries before adding copies. Joins are not automatically slow, and normalized writes are not automatically faster. Indexes, row counts, contention and update paths determine the cost.

## 4. What should a schema review test?

Write down candidate keys and dependencies from domain rules, not just sample rows. Review insert, update and delete cases as well as the happy-path query. For each decomposition, prove that a join reconstructs the intended facts and separately check which dependencies remain enforceable locally.
Enforce local rules with keys, foreign keys, checks and nullability; document those requiring application or transaction logic.

For each deliberate stored copy, name its update owner, freshness contract, repair/rebuild path, access rules and retention policy. A second copy of customer data is another place that deletion and authorization rules must reach.

## Summary

Normalization derives table boundaries from dependencies so that one fact has a clear owner. 1NF represents relational values without repeating groups; 2NF addresses partial-key dependencies; 3NF addresses further dependency cases; BCNF requires superkey determinants. Verify lossless reconstruction and constraint preservation separately.
Keep historical facts distinct from current facts, and treat deliberate duplication as a consistency and recovery obligation.

# MVCC (Multi-Version Concurrency Control)

A report can read an account balance while another transaction updates it. The reader needs a consistent version; the writer needs to commit without rewriting the row underneath that reader. MVCC defines which version each snapshot can see and how long older versions must remain available.

## Definition

MVCC (Multi-Version Concurrency Control) keeps several versions of a row so that reads can use a consistent **snapshot**: the set of committed changes visible to that statement or transaction. The isolation level determines when the snapshot is taken. Ordinary reads usually do not need to block row updates, but concurrent writes can still wait on each other or fail.

> **Textbook Definition:** Multi-Version Concurrency Control maintains row versions and applies visibility rules to select the versions a statement or transaction may observe. It reduces conflicts between ordinary reads and writes without eliminating write conflicts or all blocking.

## First Principles

MVCC is the answer to one cost problem in locking:

1. **Reads should not unnecessarily delay writes.** Keeping older row versions lets an ordinary reporting query read its snapshot while other transactions update rows.
2. **Old versions cannot always be removed immediately.** `DELETE` marks a row version as deleted; `UPDATE` creates a new version. An older snapshot may still need the previous version. `VACUUM` reclaims space once those versions are no longer needed.
3. **Long transactions can delay cleanup.** Their snapshots may keep old versions alive and cause table bloat, meaning unused versions occupy space. MVCC reduces some blocking by paying for version storage and later cleanup.

## How does a snapshot choose a row version?

### A snapshot decides which version a read can use

Start with one committed account balance of `100`. A writer changes it to `500` but has not committed. PostgreSQL creates a new **row version**, also called a tuple, while retaining the previous version for readers that may need it.

```text
Committed row version: balance = 100
              |
              +--- writer updates ---> new version: balance = 500, uncommitted
                                       |
                                       +--- COMMIT ---> eligible for newer snapshots

Ordinary reader before commit: 100
Read Committed, next SELECT after commit: 500
Repeatable Read, same established snapshot after commit: 100
```

The arrows describe creation and commitment of a version, not replacement of every reader's view. A **snapshot** records which transactions were in progress and a transaction-ID range when it was taken. Visibility combines that information with transaction outcomes and the reader's own changes. A transaction that has committed now may still be outside an older snapshot.

A transaction ID identifies a transaction; it is not a timestamp or the snapshot itself. `BEGIN` also does not necessarily assign an ordinary transaction ID immediately. PostgreSQL assigns one when needed. In Repeatable Read, the stable snapshot is established by the first non-transaction-control statement, rather than by `BEGIN` alone.

### Isolation chooses when the snapshot changes

**Read Committed** is PostgreSQL's default: each ordinary statement starts with a new snapshot. A SELECT does not start showing another transaction's newly committed rows halfway through its execution, but a later SELECT can see them.

**Repeatable Read** keeps an established transaction snapshot. Repeated reads therefore retain their view of other transactions' data. The transaction still sees its own preceding writes. Snapshot consistency is not global serializability: separate transactions can make decisions that violate an invariant spanning several rows.

**Serializable** builds on the snapshot model and detects dependencies that could make committed results inconsistent with some serial execution. PostgreSQL can abort a transaction with SQLSTATE `40001`; the application must retry the whole transaction, including its reads and decisions. It does not simply run every transaction one at a time.

| Situation | Read Committed | Repeatable Read | Serializable |
| -------------------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------- |
| Another transaction commits between two ordinary SELECTs | Second SELECT can see it | Existing snapshot excludes it | Existing snapshot excludes it |
| Transaction reads its own preceding write | Visible | Visible | Visible |
| Concurrent update to the same row | Can wait, then recheck the updated row | Can wait, then fail if the row changed since the snapshot | Conflict can require whole-transaction retry |
| Invariant spanning several rows | Needs an appropriate mutation/locking design | A stable snapshot alone can permit a serialization anomaly | Dependency detection can reject an unsafe execution |

This table describes ordinary transactional table data. Sequences have separate behavior: advancing a sequence is visible independently of transaction rollback. Do not infer that every database object follows row-version visibility rules.

### Tuple fields help diagnose versions; they are not a complete visibility test

PostgreSQL exposes **system columns**, fields present on ordinary tables in addition to application columns:

- `xmin` identifies the inserting transaction for this row version.
- `xmax` can identify a deleting/updating transaction or encode row-lock information. A nonzero value is not proof that the visible row has been deleted.
- `ctid` locates a physical row version within the table. An update or table rewrite can change it, so it is not a durable business identifier.

For an ordinary read, the creating transaction must be visible under the snapshot, unless the version is one of the reader's own visible writes. A committed deletion hides the older version only when that deletion is visible to the reader's snapshot. If a deletion aborts, the old version can remain visible; the whole row does not become “aborted” just because its `xmax` transaction aborted.

Frozen transaction markers, lock-only values, multiple lockers and command ordering add implementation details. Use these columns for diagnosis rather than implementing a homemade `xmin`/`xmax` predicate as authorization, an audit trail or a replacement for PostgreSQL's visibility machinery.

## What changes between two concurrent sessions?

### Compare two readers with the same writer

The following SQL works on PostgreSQL 16 and later. Open two `psql` connections to the **same disposable database**, called Session A and Session B. Run each numbered step in its indicated connection; the code blocks are an interleaving, not one script for a single connection. Do not run the reset while another test transaction is open.

First, create the fixture once in either session:

```sql
CREATE TABLE accounts (
    id integer PRIMARY KEY,
    balance integer NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 100);
```

For **Read Committed**, run these steps in order:

```sql
-- 1. Session A: reader
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM accounts WHERE id = 1;
-- 100

-- 2. Session B: writer; leave this transaction open
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;

-- 3. Session A: writer's uncommitted version is invisible
SELECT balance FROM accounts WHERE id = 1;
-- 100

-- 4. Session B
COMMIT;

-- 5. Session A: this statement takes a new snapshot
SELECT balance FROM accounts WHERE id = 1;
-- 500
COMMIT;
```

The first reader does not take a row lock that prevents the writer's UPDATE. After the writer commits, a **new statement snapshot** makes `500` visible even though the reader has not ended its transaction.

Reset the fixture, then change only the reader's isolation level:

```sql
-- 1. Session B: outside a transaction
UPDATE accounts SET balance = 100 WHERE id = 1;

-- 2. Session A: establish a stable snapshot with this SELECT
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;
-- 100

-- 3. Session B: this UPDATE commits automatically
UPDATE accounts SET balance = 500 WHERE id = 1;

-- 4. Session A: the existing snapshot still excludes that commit
SELECT balance FROM accounts WHERE id = 1;
-- 100
COMMIT;

-- 5. Session A: now outside the old transaction
SELECT balance FROM accounts WHERE id = 1;
-- 500
```

The different second result comes from snapshot lifetime, not from one transaction having a smaller numeric ID. To observe own writes, begin another transaction, update the balance to `200`, read it, then roll back: the transaction reads `200`, while the next transaction reads the prior committed `500`.

### Change the ordinary reader into a writer

Repeat the Repeatable Read trace through step 3, then execute this in Session A **before its COMMIT**:

```sql
UPDATE accounts SET balance = balance + 1 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update
-- SQLSTATE 40001
ROLLBACK;
```

Session A cannot update this row using the old snapshot after Session B changed it. Retry the whole transaction with a new snapshot; do not retry only the failed UPDATE inside an aborted transaction.

A second writer also blocks while Session B holds an uncommitted conflicting update. In another connection, `SET lock_timeout = '200ms'` followed by an UPDATE to that row can produce SQLSTATE `55P03`. This contrasts with the ordinary SELECT that returned the old value immediately. Locks and MVCC solve different parts of concurrency control.

### Inspect the visible row and cleanup pressure

```sql
SELECT id, balance, xmin, xmax, ctid
FROM accounts
WHERE id = 1;

SELECT relname, n_live_tup, n_dead_tup,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'accounts';

-- Run outside an explicit transaction block:
VACUUM ANALYZE accounts;
```

The first query returns the version visible to that statement, not all physical historical versions. Its transaction IDs and `ctid` vary with the database's prior work; do not expect literal values such as `xmin = 100`. Statistics such as `n_dead_tup` are estimates and can update asynchronously. One UPDATE followed immediately by a statistics query need not report exactly one dead tuple.

## Which application decisions still need a concurrency rule?

### A stock reservation must guard its own invariant

Two customers can both read `stock = 1`. MVCC gives each a valid view; it does not reserve that unit for either customer. Move the condition into the mutation so PostgreSQL checks it while updating the authoritative row.

```sql
CREATE TABLE products (
    id integer PRIMARY KEY,
    stock integer NOT NULL CHECK (stock >= 0)
);
CREATE TABLE orders (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id integer NOT NULL REFERENCES products(id),
    user_id integer NOT NULL
);
INSERT INTO products VALUES (1, 1);

WITH reserved AS (
    UPDATE products
    SET stock = stock - 1
    WHERE id = 1 AND stock > 0
    RETURNING id
)
INSERT INTO orders (product_id, user_id)
SELECT id, 123 FROM reserved
RETURNING id;
```

With the fixture unchanged by other work, the first execution returns one order ID and sets stock to zero. The next returns no rows and creates no order. Under Read Committed, a competing update waits and rechecks `stock > 0` against the updated row. This statement makes reservation and order creation one atomic operation; retries of the **whole purchase** still need a business idempotency contract.

An ORM transaction is subject to the same rules. Reading an account balance, checking it in JavaScript and later decrementing it is not made safe by a stable snapshot alone. The transaction and locking chapters own the complete mutation, isolation and retry choices; apply those rules when configuring Prisma.

### Reporting trades a stable view for retained versions

One Read Committed SELECT over many rows gets one statement snapshot. A report split into several SELECTs may need Repeatable Read if all parts must use the same view. The report's ordinary reads can coexist with row updates, but an old snapshot can retain versions those updates leave behind. Decide whether the report needs that consistency before keeping a transaction open for a long time.

MVCC history is temporary storage for concurrency, not a permanent audit log. Vacuum eventually removes versions no longer needed. Audit requirements need an explicit retained change record, event history or approved logging design with its own access and retention rules.

## How do old snapshots affect cleanup and operations?

Keep transactions short enough for their work and correctness needs. Monitor old snapshots and **idle-in-transaction** sessions, where a client has opened a transaction but stopped sending work. A statement timeout bounds each statement; use an idle-in-transaction policy for abandoned sessions and version-supported transaction deadlines when needed.

Keep autovacuum enabled and monitor whether it keeps up with updates and deletes. Ordinary `VACUUM` makes reclaimable space reusable within the table and normally permits ordinary reads and writes, though it can contend with other maintenance or locks. `VACUUM FULL` rewrites the table, can return space to the operating system and takes an exclusive lock; it is a maintenance decision, not a routine response to every dead-tuple count.

PostgreSQL's ordinary transaction-ID field has a finite 32-bit range, so old tuples must be **frozen** before wraparound can make their visibility ambiguous. Monitor `age(datfrozenxid)` and table `age(relfrozenxid)`, and investigate blockers to vacuum. Extended transaction-ID functions and wraparound monitoring are distinct from manually comparing ordinary `xmin` numbers.

Version creation adds write and storage work. Old snapshots postpone reclamation, but a large table alone does not prove bloat; measure transaction age, dead-tuple estimates, vacuum progress, relation size and query plans together. A replica can already lag before a snapshot starts, so snapshot consistency there does not guarantee a current primary balance.

Choose concurrency controls for the invariant: a conditional mutation, explicit lock or Serializable transaction with whole-transaction retry can each fit. Financial data alone does not dictate the isolation level; the transaction's reads, writes and cross-row conditions do.

## Summary

MVCC lets ordinary reads select committed row versions under a snapshot while writes create later versions. Read Committed refreshes the snapshot per statement; Repeatable Read retains an established transaction view; Serializable can reject unsafe dependencies. Writes and locks still conflict, and retained snapshots delay cleanup. Design mutations around business invariants rather than assuming that a transaction or MVCC alone makes a read-then-write sequence safe.

# SQL vs NoSQL — Choosing the Right Database

Checkout needs one authoritative answer about remaining stock; product search needs relevant matches; a customer page needs bounded order history. A database that fits one operation may add work or weaken guarantees for another.

## Definition

A **relational database** stores facts in tables connected through keys and supports operations over those relations, commonly with SQL. **NoSQL** groups several other data models: documents, key-value records, wide-column rows and graphs. Search engines also serve specialized retrieval workloads. These labels describe models, not universal speed, durability or transaction guarantees.

> **Textbook Definition:** Database selection matches a product's data model, query capabilities, consistency guarantees and operational constraints to a workload. Relational and non-relational classifications do not by themselves specify transactional or distribution semantics.

## First Principles

Begin with the operation and its required result. How stale may a read be? Which facts must change atomically?
How many keys or nodes must a request touch? How does the service recover if a write succeeds but its response is lost? These constraints determine the model and configuration; a brand name or the size of a JSON payload does not.

## How It Works


### 1. Choose a model from the query and ownership shape

#### Understand what each model makes easy to address

A **key-value** model locates a value by its key, like `session:42`. It fits direct lookups but does not automatically support “all sessions created last week” without another access structure. A **document** model groups nested facts into one record, such as an order and its items; it is attractive when those facts share a read and update lifecycle.
Independently updated shared facts can need references rather than embedding.

A **wide-column** model organizes partitioned rows around designed keys and clustering/order fields. It can make a bounded partition's time-ordered queries efficient, while arbitrary joins or cross-partition searches become separate work. A **graph** model represents entities and edges directly; a request follows relationships rather than reconstructing each hop through application-side lookups.
A **search** engine organizes terms in an inverted index, mapping searchable content to candidate documents and ranking results. It usually serves a derived view whose freshness needs a contract.

The relational model makes constraints and joins between independently owned facts explicit. It can also hold arrays and documents. Conversely, document products can offer schema validation, joins and multi-document transactions.
Compare a specific product's supported operation rather than assuming all members of a category behave alike.

#### Partitioning and replication change the trace

A **partition key** chooses where a record belongs. If every order for a very active customer has the same key, that customer's traffic can concentrate on one partition even when the database has many nodes. High cardinality helps spread distinct keys but does not fix one extremely hot key.

A **replica** is another copy of data. Replication can support failover or reads, but an asynchronously updated replica may lag. A read routed to it after a primary write can return old data.
Calling both operations from the same application process or reusing a connection is not sufficient unless the product and routing provide the required guarantee.

```text
write to authoritative store → committed record → publication → derived copy
           │                                           │
     immediate read                              search/dashboard read
   needs owner guarantee                         can lag or miss the event
```

Every arrow is a place where failure or delay matters. If publication fails after commit, the authoritative record exists while the derived copy is stale. Use a durable publication mechanism, idempotent consumers and a rebuild process when the derived result matters.
The [transactional outbox chapter](../../20.6-microservices/03-data-and-consistency/20.6.3.06-transactional-outbox.md) owns that trace.

#### CAP describes behavior during a partition

A network partition prevents groups of nodes from communicating. Suppose one side accepts a write changing balance from 100 to 50, while a client on the other side asks for the balance. A system cannot both guarantee that this read reflects a single current register value and always complete reads/writes on both reachable sides while communication is unavailable.

In the CAP theorem, **consistency** means linearizable behavior: operations appear to occur atomically in an order respecting real-time completion. **Availability** means every request to a non-failing node eventually receives a successful operation response; an error or refused operation does not satisfy it. **Partition tolerance** means reasoning includes communication failures. This is a conflict during partitions, not “pick any two features” in normal operation.

Refusing or delaying operations protects a strong consistency requirement at an availability cost. Serving each side can preserve operation availability but allow conflicting or stale observations needing later resolution. Classifying all PostgreSQL, MongoDB or DynamoDB deployments as one permanent CP/AP choice hides configuration, topology and operation-specific behavior.
A standalone server also has failures; CAP is not a complete availability model for it.

#### Consistency guarantees answer different questions

| Guarantee | What a reader may rely on | What it does not imply |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Serializable transactions | Committed transactions have an equivalent serial execution | Every read is the globally newest value in real-time order |
| Read-your-writes | A client's later read includes its prior successful write under the provided session/routing contract | All clients see the same latest state |
| Causal consistency | Effects respect specified cause-before-effect dependencies | Unrelated concurrent writes have one real-time total order |
| Eventual convergence | Replicas converge if updates stop and propagation succeeds under the model | A fixed millisecond staleness bound or safe immediate financial decisions |

A product can provide several guarantees at different scopes. State which operation, region, index, replica or transaction the guarantee applies to. **ACID** names atomicity, consistency, isolation and durability; its consistency refers to preserved constraints, not CAP's linearizability.

### 2. Trace one order through three data models

#### Trace one order as a relational join

Use a disposable PostgreSQL 16+ schema:

```sql
CREATE TABLE choice_customers (id integer PRIMARY KEY, name text NOT NULL);
CREATE TABLE choice_orders (
    id integer PRIMARY KEY,
    customer_id integer NOT NULL REFERENCES choice_customers(id),
    total_cents integer NOT NULL CHECK (total_cents >= 0),
    status text NOT NULL
);
INSERT INTO choice_customers VALUES (1, 'Ada');
INSERT INTO choice_orders VALUES (10, 1, 1250, 'paid'), (11, 1, 750, 'pending');
SELECT c.name, sum(o.total_cents) AS paid_cents
FROM choice_customers c
JOIN choice_orders o ON o.customer_id = c.id
WHERE o.status = 'paid'
GROUP BY c.id, c.name;
-- Ada | 1250
```

The customer fact has one owner; the query joins it to qualifying orders. Changing the customer name changes the next result without rewriting both orders. If an invoice needs the historical name, store that distinct fact under the invoice's own lifecycle.
A join does not itself reserve stock or execute a payment.

#### Trace the same read boundary as one document

This Node.js fragment assumes an already connected MongoDB driver `db` and an isolated collection. It demonstrates document ownership, not a measured performance comparison:

```typescript
const inserted = await db.collection('choiceOrders').insertOne({
  customerId: 'customer-1',
  items: [{ sku: 'pen', quantity: 2, unitPriceCents: 300 }],
  totalCents: 600,
  status: 'pending',
});
const found = await db.collection('choiceOrders').findOne({
  _id: inserted.insertedId,
});
// found contains this order's items and total in one document
```

Embedding lets the order own its item list. MongoDB's single-document mutation is atomic, but a stored total does not automatically equal the sum of its items: the update path must preserve that rule. Independently owned inventory is another record, so reserving it and creating an order needs the product's transaction or workflow design.
MongoDB supports multi-document transactions on appropriate deployments; binary floating-point amounts are a representation problem, not a reason to say the product cannot handle money. Use a deliberate exact representation and rounding policy.

#### Trace a designed key and an explicit read-consistency option

This AWS SDK v3 fragment assumes a DynamoDB table `ChoiceOrders` whose string partition and sort keys are `PK` and `SK`, credentials, region and table capacity already configured:

```typescript
import { DynamoDBClient, PutItemCommand, GetItemCommand } from '@aws-sdk/client-dynamodb';
const client = new DynamoDBClient({ region: 'us-east-1' });
const key = {
  PK: { S: 'CUSTOMER#1' },
  SK: { S: 'ORDER#2026-10-08#10' },
};
await client.send(new PutItemCommand({
  TableName: 'ChoiceOrders',
  Item: { ...key, totalCents: { N: '600' }, status: { S: 'pending' } },
  ConditionExpression: 'attribute_not_exists(PK)',
}));
const { Item } = await client.send(new GetItemCommand({
  TableName: 'ChoiceOrders',
  Key: key,
  ConsistentRead: true,
}));
// Item describes the committed record if no later operation has removed it
```

The partition key groups this customer's orders; the sort key identifies one order. The condition prevents replacement of that key on a repeated put, which instead fails with a conditional-check error. That failure is not a complete idempotency protocol: reconcile the existing item and request identity before treating a duplicate as the same purchase.

For a table in this region, the explicit strong-read option avoids the default eventual-read behavior. Global secondary indexes do not support that option; global-table consistency also depends on the configured mode and regions. One GetItem is not a transaction across stock and order records.
Network, throttling, contention and service failures still need handling; low-latency service design is not a guarantee of a particular application's p99 latency.

#### Specialized reads still require setup and ownership

Redis can cache the serialized customer under `customer:1` with a TTL, a time-to-live expiry. A hit returns the cached value without loading the owner; a miss loads the owner and repopulates it. Updates can make a hit stale before expiry, while eviction or restart can cause a miss earlier than expiry.
The [caching chapter](../../20.8-caching/20.8.01-caching-deep-dive.md) owns the invalidation and stampede trace.

An Elasticsearch product search first analyzes text into indexed terms, finds candidates and ranks them. Documents must have been indexed with compatible mappings; indexing success does not necessarily mean an immediate search sees the change before refresh. The [search chapter](../05-operations-and-scaling/20.4.5.05-search-infrastructure-at-scale.md) owns indexing and refresh behavior.

A Neo4j query following `User → FRIEND_OF → User → PURCHASED → Product` counts reachable purchase paths. Several friends buying the same product can raise its count; repeated paths and relationship direction alter the result. Define whether you want distinct friends, purchases or paths, and bound traversal depth.
A graph store is justified by measured traversal requirements, not an arbitrary relationship-count threshold.

### 3. Keep an authoritative owner for each fact

A relational order owner plus a derived search index can be a good fit when purchases need constraints and discovery needs relevance. It also adds publication, lag and rebuilding work. Start with one store if its capabilities meet both requirements, and add another when the requirement or measurement justifies the operational cost.

Time-series data can fit a relational partitioned table or a specialized store depending on retention, ingest volume and queries. Analytical columnar systems can suit large aggregations; graph systems can suit repeated relationship traversals. Neither “structured data” nor “10 TB” alone selects a model.

For each candidate, test representative distributions, hot keys, query shapes and failure recovery. Include restoration, authorization, retention/deletion, observability and cost. Managed services reduce infrastructure work but do not remove ownership of schema, capacity or access.
An audit log can share the primary database only when permissions and retention provide the required immutability.

Use the smallest operational system that meets the measured requirements. Name each fact's owner, atomicity and freshness contract; make derived stores rebuildable where possible. Plan a migration and rollback before changing keys or projections, and verify configured product guarantees instead of inferring them from a model label.

## Summary

Choose a database by tracing the required read or mutation through its model, indexes, partitions, replicas and recovery behavior. Relational, document, key-value, wide-column, graph and search models make different operations convenient; product and configuration determine guarantees. Specify the authoritative owner, acceptable staleness, concurrency invariant and failure response before adding another store.

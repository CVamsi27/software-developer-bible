# PostgreSQL Performance Tuning

An API endpoint is slow, and adding an index is the first suggestion. But the request may be waiting for a pooled connection or a lock, while a new index could slow every write. Find where the time goes before changing the plan.

## Definition

PostgreSQL performance tuning finds where a workload spends time or exceeds capacity, then changes its queries, access paths or resource budgets to meet a measured objective. A **workload** is the mix of queries and concurrency the service actually runs. Improving one isolated query is useful only when it improves that workload without unacceptable write, memory or operational costs.

> **Textbook Definition:** Database performance tuning measures execution cost and resource constraints, then adjusts plans, data structures and allocation to improve latency or throughput under defined workload conditions. Planner estimates guide execution choices but do not guarantee the fastest execution.

## First Principles

A request can wait before PostgreSQL sees it, spend time executing a plan, wait for another transaction, or send a large result back to the application. These have different remedies. An index cannot remove pool queueing; a larger memory budget cannot release a lock held by an idle transaction.

Even execution is not one fixed cost. A statement reading 100 rows once differs from one scanning 100 rows a million times. The planner estimates work from statistics, and the executor performs the chosen plan.
Compare those estimates with observations before changing settings. Configuration is not universally “last”: an exhausted connection or memory budget may be the immediate constraint.

## How It Works


### 1. Follow latency from the request to the execution plan

#### Locate the delay before interpreting a plan

```text
request latency = application work + pool/network wait
                + database execution/waits + result handling

workload evidence → expensive query/queue → explain or wait diagnosis
                  → one targeted change → repeat comparable measurement
```

Start with the application's latency distribution and operation name. Correlate pool wait, active database time and row counts. **Tail latency**, such as p99, describes the slowest fraction of requests and can worsen sharply under saturation even when an average remains acceptable.

`pg_stat_activity` observes current sessions and their wait state. `pg_stat_statements` aggregates similar statements and helps choose workload priorities. A query with high total execution time can dominate capacity even if each execution is quick; a rare slow query may instead dominate a particular user's latency.

The following diagnostics assume privileges to see the relevant sessions and SQL text. Query text can contain sensitive data; restrict access and logging.

```sql
SELECT pid, state, wait_event_type, wait_event,
       clock_timestamp() - xact_start AS transaction_age,
       clock_timestamp() - query_start AS query_age,
       pg_blocking_pids(pid) AS blockers,
       query
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;
```

An `idle` session is not executing a query, so its old query_start is not evidence of a currently slow query. `idle in transaction` is different: an unfinished transaction can retain locks or old snapshots. A `Lock` wait points toward blockers; I/O waits point toward storage activity. Absence of a wait event is not a complete CPU measurement.
Correlate with host and application metrics rather than making EXPLAIN a universal wait profiler.

#### Enable workload statistics with their actual prerequisites

On a server where you administer configuration, include `pg_stat_statements` in `shared_preload_libraries` without removing other required modules, and restart when the preload change requires it. Query-ID calculation must be enabled (`compute_query_id = auto` or `on` on supported versions). Managed services expose their own configuration process.
Then install the extension in the database:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

CREATE EXTENSION alone does not satisfy the preload requirement. These times are cumulative for the statistics interval, not current requests or an end-to-end service SLA. Compare a defined observation window and account for resets and changing traffic.
Prioritize by the objective: capacity, a critical path, or a tail-latency incident.

#### Read a plan from its inputs toward its result

`EXPLAIN` shows the planned operations without executing the statement. `EXPLAIN (ANALYZE, BUFFERS)` executes it and adds measurements. **Cost** is the planner's relative unit, not milliseconds. **Rows** estimates how many rows a node emits; **actual rows** reports observed output per loop. Node times and row counts must be interpreted with `loops`; adding every parent and child time double-counts work.

A scan supplies rows; a filter rejects candidates; a join combines inputs; a sort orders its input. A sequential scan is reasonable when much of a table is needed or the table is small. An index can save visits for selective predicates but adds lookup and write costs.
A sort spill indicates temporary I/O; increasing work_mem is only one remedy, since fewer or narrower rows or an appropriate ordering access path may remove the work.

Buffer **hits** found pages in PostgreSQL's cache. Buffer **reads** loaded pages into that cache, possibly from the operating system's cache rather than physical storage. Timing instrumentation and OS metrics help distinguish those cases.
A high global hit ratio does not guarantee one important query is fast.

### 2. Compare one query before and after an access-path change

#### Trace a selective list query with a repeatable fixture

Use PostgreSQL 16+ in a disposable schema. This fixture creates 10,000 visits spread across 100 clinics; it is a learning dataset, not production performance evidence.

```sql
CREATE TABLE perf_visits (
    id integer PRIMARY KEY,
    clinic_id integer NOT NULL,
    slot_start timestamptz NOT NULL,
    status text NOT NULL
);
INSERT INTO perf_visits
SELECT g, g % 100,
       timestamptz '2026-01-01 00:00:00+00' + (g % 365) * interval '1 day',
       CASE WHEN g % 3 = 0 THEN 'booked' ELSE 'cancelled' END
FROM generate_series(1, 10000) AS g;
ANALYZE perf_visits;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, slot_start
FROM perf_visits
WHERE clinic_id = 42 AND status = 'booked'
ORDER BY slot_start, id;
```

The filter selects IDs congruent to 42 modulo 100 that are also divisible by three: 34 rows. Initially there is no index matching clinic/status, so the planner can scan all rows, discard 9,966 and sort the 34 results. The primary-key index cannot directly locate the clinic.
The ORDER BY includes ID to make equal-time results deterministic.

Now give this particular read a narrower access path:

```sql
CREATE INDEX perf_booked_clinic_slot
ON perf_visits (clinic_id, slot_start, id)
WHERE status = 'booked';
ANALYZE perf_visits;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, slot_start
FROM perf_visits
WHERE clinic_id = 42 AND status = 'booked'
ORDER BY slot_start, id;
```

This **partial index** contains only booked visits. Its leading clinic key locates the requested clinic, and its following keys match the requested order. The result remains the same 34 rows.
The planner can choose an ordered index path or another path such as a bitmap scan plus sort; the exact choice depends on estimates and settings. Check the actual plan rather than promising a fixed node name or latency improvement.

Change the predicate to `status = 'cancelled'`: the partial index no longer covers the requested rows. Remove clinic filtering: many more rows may be needed, changing the trade-off again. An index designed for one query is not a universal improvement.
The [indexes chapter](../02-querying-and-optimization/20.4.2.01-indexes.md) owns index types and general key-order rules.

ANALYZE refreshes planner statistics; it does not compact the table. EXPLAIN ANALYZE of an UPDATE or DELETE actually changes data unless controlled by a transaction, and rollback does not undo every external side effect or sequence advance. Choose a safe environment and operation for diagnostics.

### 3. Budget connections, memory and maintenance under concurrency

#### Budget connections and memory together

Each database connection has a backend process and session state. Add the potential pools across application replicas, job workers and tools before comparing with server capacity. Reusing an application pool or a proxy can reduce connection setup and cap active backends; it can also move waiting into a queue.
There is no universal safe connection count or mandatory pooler at a particular table size.

One query may have several sorts/hashes and parallel workers. `work_mem` is per operation, and hash budgets can be multiplied by `hash_mem_multiplier`. Raising it globally can trade spills for memory exhaustion under concurrency. Try a bounded session/transaction change for a measured query, estimate aggregate use, and observe the representative load before applying it broadly.

`shared_buffers` is PostgreSQL's page cache. `effective_cache_size` is a planner estimate, not allocated memory. `maintenance_work_mem` budgets maintenance work. Settings differ in reload/restart requirements; inspect the parameter context and service controls rather than assuming ALTER SYSTEM immediately applies every setting.

#### Interpret index statistics over a meaningful interval

```sql
SELECT schemaname, relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan, indexrelname;
```

Size is not bloat. Zero recorded scans since a reset does not prove an index is unnecessary: it may enforce a constraint or support rare but critical work. Compare a representative interval, application changes and constraint ownership before dropping it.
A new index adds build cost, locks/resource demands and ongoing write maintenance; concurrent construction has its own failure/cleanup contract.

#### Keep cleanup and statistics as separate maintenance jobs

```sql
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup::numeric / greatest(n_live_tup, 1) * 100, 2)
           AS estimated_dead_to_live_pct,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

The counts are estimates of row versions, not a direct measurement of wasted bytes. VACUUM reclaims eligible dead versions for reuse and freezes old transaction IDs; ANALYZE updates planner statistics. Long snapshots can prevent reclamation even while vacuum runs.
A larger table can reflect live growth, reserved space or old versions; combine size, workload and cleanup evidence before diagnosing bloat.

Ordinary VACUUM normally allows reads/writes and primarily makes space reusable inside a table. VACUUM FULL rewrites the table with an exclusive lock and can return space to the operating system. It needs maintenance capacity and a deliberate outage plan.
The [MVCC chapter](20.4.1.03-mvcc.md) owns the visibility and cleanup mechanism.

#### Partitioning helps only when the workload can use its boundary

Range partitions can separate visits by month. A query whose predicate identifies a relevant month can skip other partitions through **partition pruning**. A query without the partition key may still touch many partitions; partitioning is not a replacement for suitable indexes.

Create future partitions before writes reach their range, and decide whether a default partition is appropriate. Detaching or dropping an old partition is a retention operation with locking and data-loss consequences, not a routine speed tweak. Validate retention, backup and recovery requirements before removal.
The [scaling material](../../../30-architecture/30.3-infra-patterns/04-data-at-scale/30.3.4.01-database-scaling.md) develops broader scale choices.

### 4. Read the evidence before optimizing

| Mistake | Why it misdiagnoses the workload | Better evidence |
| ---------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------- |
| Treat every sequential scan as bad | Reading most of a small table can be cheaper | Rows needed, buffer work and measured alternatives |
| Kill every old idle session | Query start can describe completed work; termination disrupts clients | State, transaction age, blockers and connection ownership |
| Read table/index size as bloat | Live data and normal free space also consume bytes | Maintenance, version estimates and targeted inspection |
| Increase global work_mem after one spill | Concurrent operations multiply memory demand | Bounded experiment under representative concurrency |
| Optimize the largest mean duration only | Frequent short queries can consume more total capacity | Total time, critical-path latency and observation window |

### 5. Validate one change under a representative workload

State the objective, traffic distribution and observation interval before tuning. Capture the original plan and metrics, change one relevant factor, then compare under similar load. Include write cost and tail latency when judging an index or configuration change.

Monitor active work, blocking, pool queueing, transaction age, temporary I/O, storage capacity, vacuum and replica lag. Timeouts bound waiting but do not establish successful outcomes: aborted transactions need rollback, and uncertain commits need reconciliation. Keep a rollback path for operational changes and verify that an apparent improvement did not merely move waiting into another component.

## Summary

Performance tuning follows evidence from request latency to workload priorities, waits and execution plans. Explain plan nodes through rows, loops and buffer activity before changing an index or memory budget. Evaluate configuration, pooling, maintenance and partitioning under the actual concurrency and recovery requirements.
A changed plan or high cache ratio is evidence to interpret, not proof that the service meets its objective.

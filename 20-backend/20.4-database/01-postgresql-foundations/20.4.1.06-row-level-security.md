# PostgreSQL Row-Level Security (RLS)

> Stage 5 of the [PostgreSQL Foundations](INDEX.md) — prev: [PostgreSQL Performance](20.4.1.05-postgresql-performance.md)
>
>
> **Why it matters:** This is a Database interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Row-Level Security (RLS) adds rules to a PostgreSQL table deciding which rows a database role may read or change. Table privileges answer “may this role SELECT this table?” RLS answers “which rows may that SELECT return?” Both must permit the operation.

> **Textbook Definition:** PostgreSQL row-level security applies command- and role-specific policy predicates to eligible row reads and mutations, in addition to ordinary privileges. Bypass roles, policy composition and checks on proposed rows are part of its security contract.

## First Principles

A multi-tenant API can authenticate a caller correctly yet forget `WHERE tenant_id = ...` in one query. If all tenants share a table, that missing predicate can expose another tenant's records. A table-attached rule supplies the boundary even when that query forgets its filter.

However, the database does not know which tenant the HTTP caller belongs to. If every request uses one application database role, the application must supply trustworthy request context. RLS therefore protects against a missing filter under a defined trust model; it cannot authenticate a forged tenant value or stop a privileged role from bypassing the policy.

A second constraint is connection reuse. Session state can outlive an HTTP request. The tenant value and every protected query must belong to the same database transaction, and the context must end before that connection is reused.

## How It Works

### Follow identity into one transaction

```text
verified user → authorized tenant → checkout database connection
                                             ↓
                                           BEGIN
                                             ↓
                                 transaction-local tenant setting
                                             ↓
                         statement + privileges + applicable RLS policy
                                             ↓
                             COMMIT / ROLLBACK → release connection
```

Authentication establishes the caller; application authorization validates the tenant selection. The database connection uses a non-owner role without superuser or `BYPASSRLS` privileges. Within that connection's transaction, `SET LOCAL` or `set_config(..., true)` supplies the context that policies read. Every repository call in that operation uses the transaction client, not the outer pool/client.

Policies become effective only after `ENABLE ROW LEVEL SECURITY`. For a subject role, an enabled table with no applicable policy denies row access by default. An ordinary SELECT can return zero rows; an INSERT of a denied row errors. Missing mutation policies do **not** grant unrestricted writes.

### Existing rows and proposed rows are checked separately

A policy's **USING** expression decides whether an existing row is accessible. For UPDATE and DELETE it restricts candidate rows; for SELECT it restricts returned rows. A policy's **WITH CHECK** expression validates a proposed INSERT or updated row. This prevents a visible row from being moved into another tenant by changing its tenant ID.

For a policy applying to ALL commands, omitting WITH CHECK uses the USING expression for the new-row check where applicable. Writing both makes the intended boundary explicit. UPDATE often also needs a suitable SELECT policy to access its target rows. Table privileges still apply, and an RLS policy does not grant those privileges.

### Applicable policies can broaden or intersect access

**Permissive** policies, the default, combine with OR. A broad policy allowing a tenant's whole table can override the intended narrowing effect of a separate “doctor sees assigned patients” policy: matching either is enough.

**Restrictive** policies combine with AND, but do not grant access alone. At least one applicable permissive policy must allow the row, and every applicable restrictive policy must pass. A useful composition is “permissive role grants” intersected with “restrictive tenant boundary.” Check actual inherited role memberships and command applicability rather than reading one policy in isolation.

This chapter's runnable example deliberately uses one policy and one application role. A per-user doctor restriction requires verified user context as well as tenant context, plus an explicit policy composition and mutation design; adding a narrow permissive policy to the example would not establish that restriction.

## Code Examples

### Create a fixture that cannot silently test as its owner

Use PostgreSQL 16+ in a disposable database. Run setup as an administrative role able to create roles. `rls_api` is intentionally separate from the table owner. Reuse neither these names nor this role in production.

```sql
CREATE ROLE rls_api NOLOGIN NOSUPERUSER NOBYPASSRLS;
CREATE TABLE rls_patients (
    id integer PRIMARY KEY,
    tenant_id uuid NOT NULL,
    name text NOT NULL
);
INSERT INTO rls_patients VALUES
    (1, '00000000-0000-0000-0000-000000000001', 'Ada'),
    (2, '00000000-0000-0000-0000-000000000002', 'Lin');
GRANT SELECT, INSERT, UPDATE, DELETE ON rls_patients TO rls_api;
ALTER TABLE rls_patients ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_boundary ON rls_patients
    FOR ALL TO rls_api
    USING (
        tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid
    )
    WITH CHECK (
        tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid
    );
```

The fixture uses valid UUIDs, not labels such as `clinic-abc` cast to UUID. `current_setting(..., true)` returns null for a missing setting; `NULLIF(..., '')` also handles an empty placeholder after a previous transaction-local value has ended. Equality with null does not produce true, so absent context denies access. A malformed nonempty UUID still errors rather than selecting a default tenant.

### Trace the same connection across requests

Run these statements on one `psql` connection after setup:

```sql
SET ROLE rls_api;
SELECT current_user;
-- rls_api: this is the subject role, not the owner

BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000001';
SELECT id, name FROM rls_patients ORDER BY id;
-- 1 | Ada
UPDATE rls_patients SET name = 'Hidden' WHERE id = 2;
-- UPDATE 0: tenant 2's row is not an eligible target
COMMIT;

SELECT count(*) FROM rls_patients;
-- 0: the transaction-local tenant value is no longer active

BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000002';
SELECT id, name FROM rls_patients ORDER BY id;
-- 2 | Lin
ROLLBACK;
```

The first request reads only Ada. Its attempt to change Lin does not target a visible row. After COMMIT, a query on the same reused connection sees no rows until another transaction supplies valid context. The second request selects tenant 2 and sees Lin unchanged. Returning no rows alone does not prove that a user lacks data: a missing context, wrong role, or denying policy can produce the same observation.

### Try to create or move a row into another tenant

Run each failed mutation in its own transaction, since an error aborts the transaction until rollback:

```sql
BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000001';
INSERT INTO rls_patients VALUES
    (3, '00000000-0000-0000-0000-000000000002', 'Wrong tenant');
-- ERROR: row-level security policy violation (SQLSTATE 42501)
ROLLBACK;

BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000001';
UPDATE rls_patients
SET tenant_id = '00000000-0000-0000-0000-000000000002'
WHERE id = 1;
-- ERROR: proposed row fails WITH CHECK (SQLSTATE 42501)
ROLLBACK;
RESET ROLE;
```

USING permits the old Ada row as an UPDATE target, but WITH CHECK rejects its proposed tenant 2 version. That distinction is why merely filtering old rows is an incomplete write-boundary explanation.

### Bind the tenant and queries to Prisma's transaction client

This TypeScript fragment assumes a configured Prisma client, a Patient model mapped to the protected table, and a tenant ID already validated and authorized by an authentication/authorization guard:

```typescript
async function listPatients(authorizedTenantId: string) {
  return prisma.$transaction(async (tx) => {
    await tx.$queryRaw`
      SELECT set_config('app.current_tenant', ${authorizedTenantId}, true)
    `;
    return tx.patient.findMany();
  });
}
```

The tagged query binds the value, and `true` scopes it to the transaction. `tx.patient` uses the connection that owns that setting. Calling `prisma.patient` instead could use another connection without the context. NestJS middleware commonly runs before authentication guards, so it cannot assume that `req.user` has already been established; set database context after identity and tenant authorization are complete.

For creates, the repository must supply the authorized tenant in the row and let WITH CHECK enforce it. Never trust a request body's tenant ID merely because it has valid UUID syntax. Apply policies to related tables too: a relation included by the ORM is not protected just because Patient is protected.

## Real-World Decisions

### Keep the role and context inside the trust boundary

A normal application role capable of executing arbitrary SQL can often change custom settings. RLS based on those settings therefore assumes trusted application code chooses context and untrusted callers cannot issue arbitrary SQL. It is defense against missing filters, not containment of a fully compromised application credential or SQL injection. Parameter binding, authorization and credential separation still matter.

`GRANT ALL` does not make a role the table owner. Ownership comes from creation or an ownership change. Ordinary owners normally bypass RLS; `FORCE ROW LEVEL SECURITY` can subject an owner to it, but superusers and BYPASSRLS roles still bypass. Use a separate migration role and avoid granting the API a way to assume a bypass role.

### Decide which other operations require controls

RLS does not govern TRUNCATE or REFERENCES privileges. Integrity checks can bypass row security and reveal information through errors, such as a conflicting unique value. An application should avoid exposing raw constraint errors as a cross-tenant existence oracle. Functions running with an owner's privileges and views also need an explicit role/security review; a protected base table alone does not prove every access path safe.

A global lookup table can intentionally be shared. Other tables may use separate schemas or databases. Choose boundaries from data ownership and access requirements rather than blindly enabling a policy on every table. RLS is not itself evidence of legal compliance.

## Common Mistakes

| Mistake | Observable consequence | Correction |
| ------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| Test as table owner or superuser | Tests return both tenants despite enabled RLS | Verify current role and test the real subject role |
| Set context outside the query transaction | Queries use the wrong session or leaked context | Set local context and use the same transaction client |
| Add a broad permissive policy | Narrow policy no longer restricts rows | Review OR/AND composition and role inheritance |
| Assume missing policies allow writes | False security model and misleading tests | Enabled RLS defaults to deny for subject roles |
| Omit new-row checks | A mutation may cross the intended boundary | Define WITH CHECK alongside old-row visibility |
| Treat application context as authentication | A caller-selected tenant may be trusted | Authorize before setting database context |

## Best Practices

Test read, insert, update, delete, missing/malformed context, owner behavior and a reused connection. Keep each error test in a transaction that is rolled back. Test relation loading and background jobs through their actual database role and transaction path, not just hand-run SQL.

Review policies with role grants and migration changes. Tenant-leading indexes can help selective requests, but policies can contain expressions or subqueries with significant cost and concurrency implications. Use actual plans and realistic roles to measure them. Preserve explicit application filters when they improve clarity or planning; RLS supplies a safety boundary rather than a reason to hide query intent.

## Summary

RLS combines table privileges with row policies. USING selects eligible existing rows; WITH CHECK validates proposed rows. Enabled RLS denies subject roles without an applicable policy, while owners and bypass roles need special attention. A safe shared-role application authorizes identity first, binds tenant context and queries to one transaction, understands policy composition and verifies both reads and writes through the actual role.

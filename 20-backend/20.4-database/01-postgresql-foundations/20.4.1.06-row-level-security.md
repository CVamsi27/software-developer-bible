# PostgreSQL Row-Level Security (RLS)

> Stage 5 of the [PostgreSQL Foundations](INDEX.md) — prev: [PostgreSQL Performance](20.4.1.05-postgresql-performance.md)
>
>
> **Why it matters:** This is a Database interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Row-Level Security (RLS) is a PostgreSQL feature (since 9.5) that lets database administrators define which rows a database role may read or change. When enabled, policies are applied to queries, subject to important exceptions: superusers and roles with `BYPASSRLS` always bypass them, and table owners normally bypass them unless `FORCE ROW LEVEL SECURITY` is set. RLS does not govern `TRUNCATE` or `REFERENCES` privileges.

> **Textbook Definition:** PostgreSQL row-level security applies policy predicates to eligible row reads and mutations in addition to table privileges. Role exemptions and policy-combination rules are part of its access-control contract.

**Key terms:**
- **RLS policy** — a rule attached to a table that evaluates per-row
- **Policy expression** — a SQL expression evaluated for each row; if it returns `true`, the row is visible/modifiable
- **Role** — a PostgreSQL user/role; RLS policies can be per-role or role-independent
- **`current_setting()`** — reads a session variable set by the application (e.g., `app.current_tenant`)

## First Principles

Row-level security exists because application-side filtering cannot be made exhaustive:

1. **One forgotten WHERE clause is a data breach.** If isolation depends on every developer remembering `WHERE tenant_id = $1` in every query forever, the guarantee is only as strong as the most tired engineer. RLS moves the filter into the engine, applied to *every* access regardless of source.
2. **Policies use database roles and request context.** An application can set transaction-scoped values such as the current tenant, then policies can read them. This reduces the risk of a missed filter, but the application still controls which values it sets, so database credentials and transaction handling remain part of the trust boundary.
3. **The cost is invisible complexity**: policies apply silently, superusers bypass them, and debugging "why no rows?" means reasoning about policy expressions. RLS trades developer discipline for engine guarantees — the right trade for multi-tenancy, a wrong one for simple single-tenant apps.

## Why Do We Need It?

1. **Defense in depth** — even if the application has a bug (missed WHERE clause), the database prevents data leaks
2. **Multi-tenant isolation** — an additional database control for applications that need tenant-scoped access; RLS can support a documented security design, but laws and standards do not generally require this specific PostgreSQL feature.
3. **Simplified queries** — developers don't need to remember `WHERE tenant_id = ?` on every query
4. **Audit compliance** — database-level enforcement is auditable and provable
5. **Zero trust** — the database itself enforces the policy, not just the application

## How It Works

### RLS Architecture

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Query Flow with RLS                                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Application                                                        │
│  ├── SET LOCAL app.current_tenant = 'clinic-abc'                    │
│  └── SELECT * FROM patients WHERE name = 'John'                     │
│                                                                     │
│  PostgreSQL Parser                                                  │
│  ├── Parses SQL                                                     │
│  ├── Checks: Is RLS enabled on `patients`?                          │
│  ├── Checks: Are there policies for current role?                   │
                                                                      │  ├── Evaluates policy: tenant_id = current_setting('app.current_tenant')::uuid
                                                                      │  └── Rewrites query: WHERE name = 'John' AND tenant_id = 'clinic-abc'
│                                                                     │
│  Storage Engine                                                     │
│  └── Only returns rows matching the rewritten WHERE clause          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Enabling RLS

```sql
-- Step 1: Enable RLS on the table
ALTER TABLE patients ENABLE ROW LEVEL SECURITY;

-- Step 2: Create a policy
-- Policy: users can only see rows where tenant_id matches their session
CREATE POLICY tenant_isolation ON patients
  USING (tenant_id = current_setting('app.current_tenant')::uuid);

-- Step 3: Also restrict writes (INSERT/UPDATE/DELETE)
CREATE POLICY tenant_isolation_insert ON patients
  FOR INSERT
  WITH CHECK (tenant_id = current_setting('app.current_tenant')::uuid);

CREATE POLICY tenant_isolation_update ON patients
  FOR UPDATE
  USING (tenant_id = current_setting('app.current_tenant')::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant')::uuid);

CREATE POLICY tenant_isolation_delete ON patients
  FOR DELETE
  USING (tenant_id = current_setting('app.current_tenant')::uuid);
```

### Per-Role Policies

```sql
-- Admin can see all patients in their tenant
CREATE POLICY admin_read ON patients
  FOR SELECT
  TO clinic_admin
  USING (tenant_id = current_setting('app.current_tenant')::uuid);

-- Doctor can only see their own patients
CREATE POLICY doctor_read ON patients
  FOR SELECT
  TO doctor
  USING (
    tenant_id = current_setting('app.current_tenant')::uuid
    AND assigned_doctor_id = current_setting('app.current_user_id')::uuid
  );

-- Receptionist can see all patients in their tenant but cannot delete
CREATE POLICY receptionist_read ON patients
  FOR SELECT
  TO receptionist
  USING (tenant_id = current_setting('app.current_tenant')::uuid);
-- (No DELETE policy = receptionist cannot delete patients)
```

PostgreSQL policies are **permissive by default**: applicable permissive policies are combined with `OR`. A user who belongs to multiple database roles may therefore gain access allowed by any one of those policies. Review role inheritance and policy composition; where every request must satisfy a tenant boundary, use a restrictive policy for that boundary or another design that enforces the intersection.

## Code Examples

### NestJS Middleware — Set Tenant Context

```typescript
// tenant-context.middleware.ts
import { Injectable, NestMiddleware } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';

@Injectable()
export class TenantContextMiddleware implements NestMiddleware {
  use(req: any, _res: any, next: () => void) {
    const tenantId = req.user?.tenantId;
    if (!tenantId) {
      next();
      return;
    }

    // Set session variables for RLS — this is the key line
    req.prismaTx = async (tx: any) => {
      await tx.$queryRaw`SELECT set_config('app.current_tenant', ${tenantId}, true)`;
      if (req.user?.sub) {
        await tx.$queryRaw`SELECT set_config('app.current_user_id', ${req.user.sub}, true)`;
      }
    };

    next();
  }
}
```

### Prisma Transaction with Tenant Context

```typescript
// patient.repository.ts
@Injectable()
export class PatientRepository {
  constructor(private prisma: PrismaService) {}

  async findMany(tenantId: string) {
    // Prisma interactive transaction sets the session variable
    return this.prisma.$transaction(async (tx) => {
      // Set the tenant context for RLS
      await tx.$queryRaw`SELECT set_config('app.current_tenant', ${tenantId}, true)`;

      // RLS automatically filters — no WHERE tenant_id needed
      return tx.patient.findMany({
        include: { appointments: true, prescriptions: true },
      });
    });
  }

  async create(tenantId: string, data: CreatePatientDto) {
    return this.prisma.$transaction(async (tx) => {
      await tx.$queryRaw`SELECT set_config('app.current_tenant', ${tenantId}, true)`;

      // RLS WITH CHECK ensures tenant_id is correct
      return tx.patient.create({ data });
    });
  }
}
```

### Testing RLS Policies

```sql
-- Test: set tenant context and verify isolation
BEGIN;
SET LOCAL app.current_tenant = 'clinic-abc';
SELECT count(*) FROM patients; -- only clinic-abc's patients
-- Expected: 42

-- Switch tenant
SET LOCAL app.current_tenant = 'clinic-xyz';
SELECT count(*) FROM patients; -- only clinic-xyz's patients
-- Expected: 17
COMMIT;

-- Test: verify INSERT policy
BEGIN;
SET LOCAL app.current_tenant = 'clinic-abc';
INSERT INTO patients (name, tenant_id) VALUES ('Test', 'clinic-xyz');
-- ERROR: new row violates row-level security policy for table "patients"
ROLLBACK;
```

## Real-World Use Cases

| Use Case | RLS Strategy | Why |
| --------------------------------- | ------------------------------ | ---------------------------------------------- |
| **Multi-tenant SaaS** | `tenant_id` column + RLS | Healthcare, finance require provable isolation |
| **Organization hierarchy** | `org_id` + role-based policies | Admin sees all, user sees own |
| **Personal data** | `user_id` column + RLS | Users can only see their own data |
| **Multi-tenant with sub-tenants** | `tenant_id` + `clinic_id` | Tenant A's clinics don't see each other |
| **Shared reference data** | No RLS on lookup tables | Countries, currencies are tenant-independent |

## Common Mistakes

### 1. Forgetting to Enable RLS

```sql
-- BAD: Table exists but RLS is not enabled — policies have no effect
ALTER TABLE patients ADD COLUMN tenant_id uuid;
-- Policies exist but are NOT enforced!

-- GOOD: Enable RLS explicitly
ALTER TABLE patients ENABLE ROW LEVEL SECURITY;
```

### 2. Table Owner Bypasses RLS

```sql
-- The table owner (usually the role that created the table) bypasses RLS
-- This is by design — but means your API role must NOT be the table owner

-- BAD: API connects as the table owner
-- GRANT ALL ON patients TO api_role; -- api_role is now the table owner

-- GOOD: API connects as a separate role
CREATE ROLE api_role;
GRANT SELECT, INSERT, UPDATE, DELETE ON patients TO api_role;
-- api_role is subject to RLS policies
```

### 3. Missing INSERT/UPDATE/DELETE Policies

```sql
-- BAD: Only SELECT policy — users can INSERT/UPDATE/DELETE any row
CREATE POLICY tenant_read ON patients FOR SELECT
  USING (tenant_id = current_setting('app.current_tenant')::uuid);
-- INSERT/UPDATE/DELETE have NO policies = unrestricted!

-- GOOD: Policies for all operations
CREATE POLICY tenant_insert ON patients FOR INSERT
  WITH CHECK (tenant_id = current_setting('app.current_tenant')::uuid);
CREATE POLICY tenant_update ON patients FOR UPDATE
  USING (tenant_id = current_setting('app.current_tenant')::uuid);
CREATE POLICY tenant_delete ON patients FOR DELETE
  USING (tenant_id = current_setting('app.current_tenant')::uuid);
```

### 4. Forgetting to Set Session Variable

```sql
-- BAD: Forgot to SET LOCAL — current_setting returns NULL, policy fails
SELECT * FROM patients; -- ERROR or empty results

-- GOOD: Always set the session variable first
BEGIN;
SET LOCAL app.current_tenant = 'clinic-abc';
SELECT * FROM patients; -- works, filtered to clinic-abc
COMMIT;
```

## Best Practices

1. **Enable RLS on every tenant-facing table** — no exceptions.
2. **Defense in depth** — application WHERE clause + RLS + ORM middleware. Never rely on a single layer.
3. **Separate API role from table owner** — the API database user must be subject to RLS.
4. **Policies for all operations** — SELECT, INSERT, UPDATE, DELETE.
5. **Use `SET LOCAL`** — session-scoped, automatically cleared on COMMIT/ROLLBACK.
6. **Test cross-tenant isolation** — automated tests that verify tenant A cannot see tenant B's data.
7. **Audit policy changes** — track who modified RLS policies in production.
8. **Use named policies** — `tenant_isolation`, `doctor_read` — not `policy_1`.
9. **Performance** — RLS adds a WHERE clause to every query; ensure `tenant_id` is indexed.
10. **Document the pattern** — every developer must know how tenant context is set and enforced.

## Summary

PostgreSQL Row-Level Security can add a database-enforced tenant boundary to a multi-tenant application. Use policies based on a transaction-scoped tenant value, keep the application role subject to RLS, review policy-combination rules, and test every operation. RLS is one defense in depth control; it does not by itself prove legal or standards compliance, and it does not cover operations such as `TRUNCATE`.

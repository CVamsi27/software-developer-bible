# PostgreSQL Row-Level Security (RLS)

> Stage 6 of the [PostgreSQL Foundations](INDEX.md) — after [PostgreSQL Performance](20.4.1.05-postgresql-performance.md)

## Definition

When enabled, Row-Level Security (RLS) applies table policies that determine which rows a PostgreSQL role subject to those policies may read or change. Table privileges answer “may this role SELECT this table?” RLS answers “which rows may that SELECT return?” Both must permit the operation.

> **Textbook Definition:** PostgreSQL row-level security evaluates command- and role-specific Boolean policy expressions for eligible row reads and mutations, in addition to ordinary SQL privileges. Policy composition, bypass roles and checks on proposed rows are part of its security contract.

## First Principles

RLS is an enforcement layer for a defined database trust model, not proof of caller identity. A policy that reads a tenant setting trusts whoever can set that value. It can catch an omitted tenant predicate in trusted application code; it cannot validate a client-supplied tenant ID or contain arbitrary SQL executed with the application's ability to change the setting.

That is why the example keeps the API role separate from the table owner, sets verified context transaction-locally, and sends all protected queries through that transaction's client.

## How It Works


### 1. When one tenant filter is missing

A multi-tenant API can authenticate a caller correctly and still leak data if one query forgets `WHERE tenant_id = ...`. When tenants share a table, that omission may expose another tenant's rows. For a role subject to RLS, an enabled deny-by-default policy can enforce the boundary even when a query omits its filter.

The database sees the executing role and row values; it does not know which HTTP user was authenticated. If requests share one application role, trusted application code must authorize the tenant and provide its context. A pooled connection can outlive a request, so that context and every protected query must stay within the same transaction.

### 2. Place the policy inside the request's trusted path

#### Follow identity into one transaction

```text
verified user → authorized tenant → checkout database connection
                                             ↓
                                           BEGIN
                                             ↓
                                 transaction-local tenant setting
                                             ↓
                         statement + privileges + applicable RLS policy
                                             ↓
                             COMMIT / ROLLBACK → release connection
```

Authentication establishes the caller; application authorization validates the tenant selection. The database connection uses a non-owner role without superuser or `BYPASSRLS` privileges. Within that connection's transaction, `SET LOCAL` or `set_config(..., true)` supplies the context that policies read.
Every repository call in that operation uses the transaction client, not the outer pool/client.

Policies become effective only after `ENABLE ROW LEVEL SECURITY`. For a subject role, an enabled table with no applicable policy denies row access by default. An ordinary SELECT can return zero rows; an INSERT of a denied row errors.
Missing mutation policies do **not** grant unrestricted writes.

#### Existing rows and proposed rows are checked separately

A policy's **USING** expression decides whether an existing row is accessible. For UPDATE and DELETE it restricts candidate rows; for SELECT it restricts returned rows. A policy's **WITH CHECK** expression validates a proposed INSERT or updated row.
This prevents a visible row from being moved into another tenant by changing its tenant ID.

For a policy applying to ALL commands, omitting WITH CHECK uses the USING expression for the new-row check where applicable. Writing both makes the intended boundary explicit. UPDATE often also needs a suitable SELECT policy to access its target rows.
Table privileges still apply, and an RLS policy does not grant those privileges.

#### Applicable policies can broaden or intersect access

**Permissive** policies, the default, combine with OR. A broad policy allowing a tenant's whole table can override the intended narrowing effect of a separate “doctor sees assigned patients” policy: matching either is enough.

**Restrictive** policies combine with AND, but do not grant access alone. At least one applicable permissive policy must allow the row, and every applicable restrictive policy must pass. A useful composition is “permissive role grants” intersected with “restrictive tenant boundary.” Check actual inherited role memberships and command applicability rather than reading one policy in isolation.

This chapter's runnable example deliberately uses one policy and one application role. A per-user doctor restriction requires verified user context as well as tenant context, plus an explicit policy composition and mutation design; adding a narrow permissive policy to the example would not establish that restriction.

### 3. Exercise policy behavior as the runtime role

#### Create a fixture that cannot silently test as its owner

Use PostgreSQL 16 or later in a disposable database. Run setup as a superuser. A non-superuser setup role must also be a member of `rls_api` before it can run `SET ROLE rls_api`.
The example role is intentionally separate from the table owner. Reuse neither these names nor this role in production.

```sql
CREATE ROLE rls_api NOLOGIN NOSUPERUSER NOBYPASSRLS;
CREATE TABLE rls_patients (
    id integer PRIMARY KEY,
    tenant_id uuid NOT NULL,
    name text NOT NULL
);
INSERT INTO rls_patients VALUES
    (1, '00000000-0000-0000-0000-000000000001', 'Ada'),
    (2, '00000000-0000-0000-0000-000000000002', 'Lin');
GRANT SELECT, INSERT, UPDATE, DELETE ON rls_patients TO rls_api;
ALTER TABLE rls_patients ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_boundary ON rls_patients
    FOR ALL TO rls_api
    USING (
        tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid
    )
    WITH CHECK (
        tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid
    );
```

The fixture uses valid UUIDs, not labels such as `clinic-abc` cast to UUID. `current_setting(..., true)` returns null for a missing setting; `NULLIF(..., '')` also handles an empty placeholder after a previous transaction-local value has ended. Equality with null does not produce true, so absent context denies access. A malformed nonempty UUID still errors rather than selecting a default tenant.

#### Trace the same connection across requests

Run these statements on one `psql` connection after setup:

```sql
SET ROLE rls_api;
SELECT current_user;
-- rls_api: this is the subject role, not the owner

BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000001';
SELECT id, name FROM rls_patients ORDER BY id;
-- 1 | Ada
UPDATE rls_patients SET name = 'Hidden' WHERE id = 2;
-- UPDATE 0: tenant 2's row is not an eligible target
COMMIT;

SELECT count(*) FROM rls_patients;
-- 0: the transaction-local tenant value is no longer active

BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000002';
SELECT id, name FROM rls_patients ORDER BY id;
-- 2 | Lin
ROLLBACK;
```

The first request reads only Ada. Its attempt to change Lin does not target a visible row. After COMMIT, a query on the same reused connection sees no rows until another transaction supplies valid context.
The second request selects tenant 2 and sees Lin unchanged. Returning no rows alone does not prove that a user lacks data: a missing context, wrong role, or denying policy can produce the same observation.

#### Try to create or move a row into another tenant

Run each failed mutation in its own transaction, since an error aborts the transaction until rollback:

```sql
BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000001';
INSERT INTO rls_patients VALUES
    (3, '00000000-0000-0000-0000-000000000002', 'Wrong tenant');
-- ERROR: row-level security policy violation (SQLSTATE 42501)
ROLLBACK;

BEGIN;
SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000001';
UPDATE rls_patients
SET tenant_id = '00000000-0000-0000-0000-000000000002'
WHERE id = 1;
-- ERROR: proposed row fails WITH CHECK (SQLSTATE 42501)
ROLLBACK;
RESET ROLE;
```

USING permits the old Ada row as an UPDATE target, but WITH CHECK rejects its proposed tenant 2 version. That distinction is why merely filtering old rows is an incomplete write-boundary explanation.

#### Bind the tenant and queries to Prisma's transaction client

This TypeScript fragment assumes a configured Prisma client, a Patient model mapped to the protected table, and a tenant ID already validated and authorized by an authentication/authorization guard:

```typescript
async function listPatients(authorizedTenantId: string) {
  return prisma.$transaction(async (tx) => {
    await tx.$queryRaw`
      SELECT set_config('app.current_tenant', ${authorizedTenantId}, true)
    `;
    return tx.patient.findMany();
  });
}
```

The tagged query binds the value, and `true` scopes it to the transaction. `tx.patient` uses the connection that owns that setting. Calling `prisma.patient` instead could use another connection without the context. NestJS middleware commonly runs before authentication guards, so it cannot assume that `req.user` has already been established; set database context after identity and tenant authorization are complete.

For creates, the repository must supply the authorized tenant in the row and let WITH CHECK enforce it. Never trust a request body's tenant ID merely because it has valid UUID syntax. Apply policies to related tables too: a relation included by the ORM is not protected just because Patient is protected.

### 4. Understand which access paths RLS does not secure

#### Keep the role and context inside the trust boundary

A normal application role capable of executing arbitrary SQL can often change custom settings. RLS based on those settings therefore assumes trusted application code chooses context and untrusted callers cannot issue arbitrary SQL. It is defense against missing filters, not containment of a fully compromised application credential or SQL injection.
Parameter binding, authorization and credential separation still matter.

`GRANT ALL` does not make a role the table owner. Ownership comes from creation or an ownership change. Ordinary owners normally bypass RLS; `FORCE ROW LEVEL SECURITY` can subject an owner to it, but superusers and BYPASSRLS roles still bypass.
Use a separate migration role and avoid granting the API a way to assume a bypass role.

Enabling RLS does not make every policy fail closed. This expression intentionally allows every row while its rollout switch is absent or off:

```sql
current_setting('app.rls_enabled', true) IS DISTINCT FROM 'on'
OR "clinicId" = current_setting('app.current_clinic_id', true)
```

The [Docita tenant-isolation case](../../../projects/docita/02-multi-tenancy-rls.md) documents this staged policy and the need to verify that the runtime path always sets its switch. Read the policy expression itself: a missing setting denies rows only when the predicate is written to deny them.

#### Decide which other operations require controls

RLS does not govern TRUNCATE or REFERENCES operations. Integrity checks can bypass row security and reveal information through errors, such as a conflicting unique value. An application should avoid exposing raw constraint errors as a cross-tenant existence oracle.

A view normally applies base-table RLS using the view owner's identity; PostgreSQL 15+ supports `security_invoker = true`, which uses the invoking user's privileges and policies. A `SECURITY DEFINER` function executes with its owner's privileges and can therefore take a different RLS path. Treat both as privileged access paths: review ownership and `EXECUTE` grants, and pin a security-definer function's `search_path` to trusted schemas with `pg_temp` last.
Keep policy predicates row-local where possible; a predicate that reads a separate authorization table can race with concurrent permission changes unless the access and revocation paths coordinate their locks or transaction boundaries.

For an export that must not silently omit rows, PostgreSQL's `row_security = off` makes a query error if a policy would filter its result; it does **not** bypass RLS. Run the export with an explicitly reviewed role and handle that error as a failed completeness check.

A global lookup table can intentionally be shared. Other tables may use separate schemas or databases. Choose boundaries from data ownership and access requirements rather than blindly enabling a policy on every table.
RLS is not itself evidence of legal compliance.

### 5. Verify the policy at the real access boundary

Run these cases as the same non-owner role used by the application, through the same transaction and pool path:

| Case | Expected result |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Missing or empty tenant context | No rows are visible; inserts fail their row check |
| Tenant A selects, updates or deletes tenant B's row | The row is not an eligible target |
| Tenant A inserts a tenant B row or changes a visible row to tenant B | `WITH CHECK` rejects the proposed row |
| A connection is reused after COMMIT or ROLLBACK | The prior transaction's tenant setting is gone |
| A query runs as owner, superuser or `BYPASSRLS` role | The test exposes the bypass; the runtime role must not have it |
| ORM relation or background-job path accesses protected rows | The actual relation/job role and transaction still enforce the intended boundary |

Keep error cases in transactions that are rolled back. Review policy changes alongside role grants and migrations. Tenant-leading indexes may help selective queries, but policy expressions and subqueries have workload costs; inspect plans under the actual role.
Keep explicit application filters when they clarify intent or help planning. RLS is a second enforcement boundary, not a reason to hide query scope.

## Summary

RLS combines table privileges with row policies. USING selects eligible existing rows; WITH CHECK validates proposed rows. Enabled RLS denies subject roles without an applicable policy, while owners and bypass roles need special attention.
A safe shared-role application authorizes identity first, binds tenant context and queries to one transaction, understands policy composition and verifies both reads and writes through the actual role.

# Database Indexes

A dashboard asks for the newest three paid orders for one tenant. An index helps only if its membership, key order and operators match that request—and PostgreSQL can still need the heap to verify row visibility.

## Definition

A database index keeps an additional searchable representation of stored values so a query can find candidate rows without examining every table row. PostgreSQL still must determine which row versions are visible to the query. The index costs storage and maintenance, and its supported operators determine which queries it can help.

> **Textbook Definition:** A database index is an auxiliary access structure containing ordered keys, inverted entries or block summaries. For supported operators, it narrows candidate rows or supplies order at the cost of storage and maintenance; visibility and planner choice still matter.

## First Principles

Without an access structure, an equality query may have to examine all visible rows. Keeping values in a navigable order lets the engine discard large regions before inspecting candidates. Keeping a term-to-document list or summaries of physical blocks offers different ways to discard work; an index is not always a sorted copy of one column.

A new row must become discoverable through the relevant indexes. Updating indexed values or an index predicate can also change entries. This creates storage, WAL, page and maintenance costs alongside the read benefit.
PostgreSQL's heap-only tuple (HOT) optimization can avoid new index entries for eligible updates; it is incorrect to assign identical work to every index on every UPDATE or to treat DELETE as immediate physical removal everywhere.

Even a useful access structure can lose to scanning when the query needs much of the table or returns wide rows from scattered pages. The requirement is reduced total work for the measured workload, not a preferred plan-node name.

## How It Works


### 1. Follow the access path

#### Follow a B-tree lookup into visible table versions

A B-tree orders keys through branch and leaf pages. Equality descends to the relevant key range; a range lookup then walks matching entries. PostgreSQL index entries locate table tuples in the **heap**, the table's row storage.
Ordinary index scans visit those tuples to retrieve values and check visibility.

A composite key is ordered lexicographically. With (tenant_id, created_at, id), fixing tenant_id makes its ordered time/ID range contiguous. A query on time alone may search across many tenant regions.
PostgreSQL 18 can use B-tree skip scan when the leading key has few distinct values: it repeatedly searches for each leading-key value while applying a condition on a later key. That can avoid scanning irrelevant key ranges, but becomes unattractive when it must repeat across many distinct values. This chapter's executable fixture uses PostgreSQL 16 and does not depend on skip scan.
Check the server version, leading-key distribution and actual plan before concluding a trailing-key condition is unusable.

An index can support compatible ORDER BY without a sort, including forward/backward scans and deliberate mixed directions. Null ordering and collation must match the query. INCLUDE columns are payload for retrieval, not additional search/sort keys or part of a unique key.

#### Distinguish access methods from index properties

| Access method | What it keeps | Consequential boundary |
| ------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| B-tree | Ordered comparable keys | Equality/ranges/order under supported operators and collation |
| Hash | Hash codes for equality candidates | No range/order capability; collisions/rechecks and output still cost work |
| GIN, generalized inverted index | Component-to-row candidate lists | Arrays, text search and JSONB depend on the selected operator class |
| GiST | Balanced search tree with extensible predicates | Range/spatial/nearest-neighbor capability depends on type and operator class |
| SP-GiST | Partitioned search tree for space-partitionable data | Search behavior depends on the type-specific partitioning and operator class |
| BRIN, block range index | Summaries of values in physical block ranges | Excludes impossible ranges; surviving ranges still need examination/recheck |

An **operator class** defines which operations a method supports for a type. Partial, unique, expression and covering indexes are properties of an index definition, not additional access methods. A BRIN on time works best when time correlates with physical row placement, not merely because a table is large.

A unique index enforces the chosen key rule even if the planner does not use it for reads. PostgreSQL normally permits multiple NULLs in a unique key; PostgreSQL 15+ supports `NULLS NOT DISTINCT` when nulls must conflict. Primary/unique constraints already create supporting indexes.
Foreign keys do not automatically create an index on the referencing columns; assess parent modification checks and lookup workload rather than duplicating every key index.

### 2. Build an access path for the dashboard query

#### Match predicate, ordering and retrieval to one index

Use PostgreSQL 16+ in a fresh disposable schema. Integer amounts are fixture units, not a currency conversion example.

```sql
CREATE TABLE index_orders (
    id integer PRIMARY KEY,
    tenant_id integer NOT NULL,
    created_at timestamptz NOT NULL,
    amount integer NOT NULL,
    status text NOT NULL
);
INSERT INTO index_orders
SELECT n, n % 100,
       timestamptz '2026-01-01 00:00:00+00' + n * interval '1 minute',
       n * 10, CASE WHEN n % 2 = 0 THEN 'paid' ELSE 'open' END
FROM generate_series(1, 10000) AS n;
ANALYZE index_orders;

CREATE INDEX index_paid_tenant_time
ON index_orders(tenant_id, created_at DESC, id DESC)
INCLUDE(amount)
WHERE status = 'paid';

SELECT id, amount FROM index_orders
WHERE tenant_id = 42 AND status = 'paid'
ORDER BY created_at DESC, id DESC LIMIT 3;
-- 9942 | 99420
-- 9842 | 98420
-- 9742 | 97420
```

The partial index contains only paid rows. Within tenant 42, keys are already in the requested newest-first order; amount is available as payload. The planner may choose the access path according to its costs.
The result must stay identical with or without the index.

Change status to open: this index cannot supply that excluded subset. A parameterized/generic predicate may also prevent the planner from proving the partial predicate at planning time. The query must imply the predicate under PostgreSQL's supported implication checks, rather than merely looking similar in application code.

#### Observe visibility, not just coverage

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount FROM index_orders
WHERE tenant_id = 42 AND status = 'paid'
ORDER BY created_at DESC, id DESC LIMIT 3;

VACUUM (ANALYZE) index_orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount FROM index_orders
WHERE tenant_id = 42 AND status = 'paid'
ORDER BY created_at DESC, id DESC LIMIT 3;
```

An index-only scan is possible when the method can return all required values. PostgreSQL still checks visibility: an all-visible heap-page bit in the **visibility map** can avoid the heap visit; otherwise it fetches the tuple. In the isolated PostgreSQL 16.15 fixture, the same Index Only Scan reported three Heap Fetches before vacuum and zero afterward.
That is an observed fixture trace, not a production promise. Subsequent changes can clear all-visible bits, and long-lived snapshots can constrain cleanup.

VACUUM must run outside an explicit transaction block here. It does not make every page universally all-visible while concurrent changes continue. Wide INCLUDE payloads increase index size and can exceed tuple limits; use them when measured avoided heap work justifies the cost.

#### Index a derived expression deliberately

```sql
CREATE TABLE index_accounts(id integer PRIMARY KEY, email text NOT NULL);
CREATE UNIQUE INDEX index_accounts_normalized_email
ON index_accounts(lower(email));
INSERT INTO index_accounts VALUES (1, 'Ada@example.test');
SELECT id FROM index_accounts WHERE lower(email) = 'ada@example.test';
-- 1

BEGIN;
INSERT INTO index_accounts VALUES (2, 'ADA@example.test');
-- ERROR: SQLSTATE 23505
ROLLBACK;
```

This policy makes lowercase-equivalent addresses conflict; it is a chosen application normalization rule. The expression must be immutable for an index, and query/expression/operator/collation compatibility matters. An ordinary index on email does not automatically index lower(email).
Avoid redundant indexes that re-enforce an already declared equivalent unique constraint.

### 3. Choose the index from workload evidence

Choose leading keys from the equality/range/order contract across the workload. If both a and b are constrained by equality, either leading order may serve that query; other queries and distributions decide the portfolio. Low distinct-value count alone is insufficient: a rare status can be selective even in a two-value column.
A partial index can target that rare relevant subset.

For each important query, record its predicate, ordering, expected selectivity, supported operator class and representative parameter values. Compare equivalent results and observed rows/buffers, including pagination, tenant skew and write load. A sequential scan over a large table can be correct for a broad report.
An index-only scan is not automatically the fastest option. A bitmap scan can combine one or several indexes but usually loses key order and may recheck lossy pages. Evaluate the read benefit against write work and storage before retaining another index.

### 4. Maintenance and Failure Boundaries

pg_stat_user_indexes reports scans and tuple activity over a statistics window, not business value or physical bloat. Zero scans may reflect a recent reset, standby-only workload, infrequent critical lookup or uniqueness enforcement. Inspect dependencies and a representative observation window before removing an index. pg_relation_size reports allocated size; it does not alone measure reclaimable bloat.

CREATE INDEX ordinarily blocks writes while building. CREATE INDEX CONCURRENTLY avoids that ordinary write-blocking build pattern but still has locks, waits, resource costs and failure states; it cannot run inside a transaction block. A failed concurrent build can leave an invalid index, including a unique index that still affects writes in some failure phases.
Inspect validity and use the documented cleanup/retry procedure. [Migrations](../05-operations-and-scaling/20.4.5.02-migration-strategies.md) owns the deployment protocol.

Updates/deletes leave version/maintenance consequences under MVCC; vacuum handles cleanup, and long-lived transactions can delay it. Monitor write latency, WAL, storage and index health alongside read wins. Bind values and enforce tenant/access policy: an efficient lookup does not authorize the returned row.

## Summary

An index precomputes an access path whose method, key order, predicate and operator class must fit the query. PostgreSQL still handles visible versions, and covering an output does not guarantee avoiding the heap. Choose a measured portfolio, distinguish allocated size from bloat, and preserve constraint/concurrent-build/cleanup boundaries when changing it.

# SQL Joins

A patient list needs to show each patient's appointments while keeping patients who have none. The query must decide which rows match and which unmatched rows survive.

## Definition

A **join** constructs result rows from two input tables according to a matching condition. An inner join returns matching pairs; an outer join also preserves selected unmatched rows, filling the missing side with `NULL`.

> **Textbook Definition:** A relational join combines rows from input relations according to a condition. Inner joins retain matching combinations; outer joins additionally retain designated unmatched rows with nulls for the absent input.

## First Principles

Keeping facts in separate tables avoids copying a patient's name into every appointment. Reading those related facts requires pairing rows by an explicit condition. A match may be missing or may occur more than once, so the query must define both which pairs qualify and which unmatched rows survive.

The requested result comes first. PostgreSQL can use different physical algorithms to produce it; changing the algorithm should not change the join's logical meaning.

## Trace matching and unmatched rows

Use PostgreSQL 16+ in a fresh disposable schema. These statements make the inputs explicit:

```sql
CREATE TABLE patients(id integer PRIMARY KEY, name text NOT NULL);
CREATE TABLE appointments(
    id integer PRIMARY KEY,
    patient_id integer NOT NULL REFERENCES patients(id),
    status text NOT NULL
);
INSERT INTO patients VALUES (1, 'Ada'), (2, 'Ben'), (3, 'Cy');
INSERT INTO appointments VALUES (10, 1, 'booked'), (11, 1, 'cancelled'), (12, 2, 'booked');
```

The resulting inputs are:

| Patient ID | Name |
| ---------- | ---- |
| 1 | Ada |
| 2 | Ben |
| 3 | Cy |

| Appointment ID | Patient ID | Status |
| -------------- | ---------- | --------- |
| 10 | 1 | booked |
| 11 | 1 | cancelled |
| 12 | 2 | booked |

```sql
SELECT p.id, p.name, a.id AS appointment_id, a.status
FROM patients AS p
LEFT JOIN appointments AS a ON a.patient_id = p.id;
```

| Patient ID | Name | Appointment ID | Status |
| ---------- | ---- | -------------- | --------- |
| 1 | Ada | 10 | booked |
| 1 | Ada | 11 | cancelled |
| 2 | Ben | 12 | booked |
| 3 | Cy | NULL | NULL |

Ada appears twice because she has two matching appointments. Cy remains because this is a left join. An inner join with the same condition would omit Cy; a join does not automatically deduplicate repeated matches. Without `ORDER BY`, the displayed row order is illustrative rather than guaranteed.

## ON chooses matches; WHERE filters the joined result

To retain every patient but match only booked appointments, put `a.status = 'booked'` in `ON`. Cy still receives a NULL-extended result row. Putting that condition in `WHERE` instead rejects Cy's NULL status, so the query no longer preserves every patient:

```sql
-- Keep all patients; only booked appointments count as matches.
SELECT p.id, p.name, a.id AS appointment_id
FROM patients AS p
LEFT JOIN appointments AS a
  ON a.patient_id = p.id AND a.status = 'booked'
ORDER BY p.id, a.id;

-- Keep only rows whose joined appointment is booked; Cy disappears.
SELECT p.id, p.name, a.id AS appointment_id
FROM patients AS p
LEFT JOIN appointments AS a ON a.patient_id = p.id
WHERE a.status = 'booked'
ORDER BY p.id, a.id;
```

| Join type | Result policy |
| --------- | ---------------------------------------------------------------------- |
| INNER | Matching pairs only |
| LEFT | Matching pairs plus unmatched left rows |
| RIGHT | Matching pairs plus unmatched right rows |
| FULL | Matching pairs plus unmatched rows from either side |
| CROSS | Every left/right pair; result size grows as the product of input sizes |

Use explicit join predicates and qualified column names. A missing condition or an unintended many-to-many relationship can multiply rows, inflate aggregates and consume resources even when the syntax is valid.

## How PostgreSQL can produce the same pairs

| Algorithm | Mechanism | Main boundary |
| ----------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Nested loop | For each outer row, find matching inner rows | Without a useful lookup it can compare many pairs; an index can make selected inner lookups economical |
| Hash join | Build a hash table for one input, then probe it | Useful for equality matching; memory pressure can force batching/spill |
| Merge join | Walk compatibly ordered inputs together | Input sorting may be costly; existing order can help |

The naive nested loop can cost roughly `n × m` comparisons. A hash join can approach `n + m` work under favorable conditions. Those are teaching bounds, not latency predictions: output multiplicity, skew, I/O, sorting and memory affect actual work. A typical B-tree lookup is not universally constant-time.

Inspect `EXPLAIN (ANALYZE, BUFFERS)` on a safe representative query to compare estimated and actual rows. `ANALYZE` executes the query; do not treat it as a harmless production-only planning command. Statistics, data distribution, predicates and indexes influence planner choices. Diagnose the measured bottleneck rather than assuming every slow join is a statistics problem.


## Preserve the side the result requires

In the first query above, Ada and Ben match booked appointments; Cy remains with NULL appointment columns. Changing LEFT to INNER removes Cy. Reversing the inputs and using RIGHT expresses the same preserved side, but LEFT usually makes the entity being retained easier to read.

FULL preserves both unmatched sides. In this fixture all appointments reference a patient, so there are no unmatched appointments. If a relationship has an enforced foreign key, explain that constraint rather than inventing orphan rows to illustrate FULL. FULL is useful for reconciliation between independent datasets that can each contain unmatched keys.

### Count matches, not the placeholder row

```sql
SELECT p.id, p.name, COUNT(a.id) AS appointment_count
FROM patients AS p
LEFT JOIN appointments AS a ON a.patient_id = p.id
GROUP BY p.id, p.name
ORDER BY p.id;
```

The result counts are Ada 2, Ben 1 and Cy 0. `COUNT(*)` would count Cy's NULL-extended result row as 1. Count a non-null match identifier; aggregates and NULL behavior belong to the result shape.

### Use existence when you do not need matching rows

```sql
SELECT p.id, p.name
FROM patients AS p
WHERE EXISTS (
  SELECT 1 FROM appointments AS a
  WHERE a.patient_id = p.id AND a.status = 'booked'
);
```

This returns each qualifying patient once, even with many matching bookings. A join returns matching pairs and may repeat the patient. Adding DISTINCT to hide that fan-out can conceal the wrong result contract. NOT EXISTS expresses “no matching appointment”; a LEFT join followed by `WHERE a.id IS NULL` can also express this when a.id is a non-null match key.

An IN subquery is not automatically slower than a join; the planner can transform suitable queries into similar plans. Choose semantics first and compare actual plans second. Beware NOT IN when the subquery can produce NULL: its three-valued logic differs from ordinary absence testing.

## Correlate a per-patient result with LATERAL

LATERAL lets a FROM subquery reference preceding inputs. Use it when each patient needs their own limited result:

```sql
SELECT p.id, p.name, latest.id AS appointment_id
FROM patients AS p
LEFT JOIN LATERAL (
  SELECT a.id
  FROM appointments AS a
  WHERE a.patient_id = p.id
  ORDER BY a.id DESC
  LIMIT 1
) AS latest ON true
ORDER BY p.id;
```

For this fixture, “latest” means greatest ID: Ada 11, Ben 12, Cy NULL. For real chronology, order by the relevant timestamp **and a deterministic ID tie-breaker**. Matching `MAX(created_at)` can return several rows when timestamps tie.

LEFT LATERAL preserves patients whose subquery returns no rows; CROSS LATERAL drops them. Change LIMIT to 3 for top-three-per-patient. The same mechanism can rank nearest locations using a supported spatial distance operator and appropriate index; operator/class requirements belong to the spatial data implementation. [PostgreSQL table expressions and LATERAL](https://www.postgresql.org/docs/current/queries-table-expressions.html)

## Recognize intentional products and self-matches

CROSS JOIN returns every combination. Sizes × colors can generate variants; dates × hours can generate reporting buckets. Estimate the multiplied row count before adding another dimension.

A **self join** reads one table under two aliases. For employees and managers, join employee.manager_id to manager.id with LEFT if top-level employees should remain. For unique coworker pairs, match department and constrain `e1.id < e2.id`; otherwise both (A,B) and (B,A), plus self-pairs, can appear.

Multiple joins chain relationships: order → order_items → product → category. Each join can change cardinality. Repeating order.total once per line item and then summing it inflates order revenue. Aggregate each independent one-to-many relationship to the intended grain before combining results.

## Keep report predicates aligned with the metric

### Inventory Check

The following is a schema-dependent reporting fragment, assuming products(id,name,stock), order_items(product_id,order_id,quantity), and orders(id,created_at). The runnable patient fixture above owns the join mechanics.

The date predicate controls which orders match; it does not remove old `order_items` rows from this left join. The aggregate therefore counts quantities only when an order actually matched. Keep current stock separate: subtracting recent sales from stock that already reflects them would count the reduction twice. This illustrative total also needs domain-specific rules for cancelled orders, returns and refunds before being used as a net-sales metric.

```sql
-- Products with stock and sales data
SELECT
    p.name,
    p.stock AS current_stock,
    COALESCE(SUM(oi.quantity) FILTER (WHERE o.id IS NOT NULL), 0) AS total_sold_last_30_days
FROM products p
LEFT JOIN order_items oi ON p.id = oi.product_id
LEFT JOIN orders o ON oi.order_id = o.id
AND o.created_at >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY p.id, p.name, p.stock;

```



For a sales dashboard, select item-level quantity and unit price at an explicitly stated grain. For an activity report, LEFT LATERAL can retrieve one latest action per active user while retaining users with no activity. These are applications of the same mechanisms, rather than new join types.

## Protect tenant scope and measure physical cost

If identifiers are only unique within a tenant, join on both tenant_id and entity ID. Filter the permitted tenant and enforce database/application access policy; an entity-only match can cross tenant boundaries even when each table's shape is valid.

Use qualified aliases and explicit conditions. Indexes on selective lookup keys can help, but “always index every join column” adds write/storage cost without proving usefulness. For the latest-appointment query, a composite patient/timestamp/tie-breaker index may support the lookup; test the actual predicate and ordering.

Estimated/actual row differences expose skew or stale statistics; repeated inner scans expose expensive nested-loop work; hash/sort spill exposes memory pressure. PostgreSQL may reorder eligible joins, so source-text order is not execution order. There is no general built-in SQL join-hint syntax to assume. Keep the planner's logical correctness separate from tuning choices.

A single statement observes rows under its isolation snapshot. Separate count/page statements under Read Committed can see different committed states, so a report requiring one coherent state needs a defined transaction/isolation contract. Index tuning does not establish report consistency or fix duplicated business measures.

## Summary

A join returns qualifying row pairs and, for outer joins, selected unmatched rows. Decide result grain and preservation first; then place predicates, handle NULLs and control fan-out. EXISTS answers presence, LATERAL produces correlated per-row results, and measured plans guide physical tuning.

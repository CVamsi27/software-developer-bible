# Execution Plans & Query Optimization

Two queries can return the same three rows while one reads thousands of candidates and the other reads only a few. An execution plan makes that difference inspectable.

## Definition

An execution plan shows how PostgreSQL intends to evaluate a query: scans produce rows, joins combine them, and operators such as sorts or aggregates shape the result. Plain EXPLAIN reports estimates. EXPLAIN ANALYZE runs the statement and adds observed work to those estimates.

> **Textbook Definition:** An execution plan is an operator tree with estimated cardinalities, widths and costs; instrumented execution adds observed rows, loops, timings and resources for diagnosing the selected strategy.

## First Principles

The same SQL result can come from scanning all rows, looking up selected keys, or combining sorted/hash-organized inputs. SQL specifies the requested result rather than prescribing those steps. Choosing a strategy therefore requires estimates of input size, matching fraction and resource cost.

If an inner lookup runs once for every outer row, a cheap-looking individual operation can become expensive in aggregate. If a sort consumes a child's rows, its displayed elapsed time includes time obtaining those inputs. Diagnosing the tree requires following row flow and repetition rather than choosing the largest printed number blindly.

Application latency also includes connection-pool wait, client/network transfer and application decoding outside the plan's execution time. Lock and I/O waits that occur while the executor runs contribute to elapsed execution time. In PostgreSQL 18+, `EXPLAIN ...
SERIALIZE` can measure server-side result conversion; it still does not send results over the network. Separate these measurements before changing access paths.

## 1. Trace the chosen work

#### Read one node's estimates and observations

```text
Index Scan ... (cost=0.29..8.31 rows=1 width=24)
               (actual time=0.02..0.03 rows=1 loops=50)
```

These numbers are a format illustration, not a fixture measurement. cost is the planner's relative work unit, not milliseconds; the first/second values are estimated startup/total cost. rows is estimated output cardinality, and width is estimated average output bytes. actual time is milliseconds to first/last output for a loop, while observed rows/time are averaged across loops. In this example roughly fifty rows came from fifty one-row executions. Multiply rows by loops for repeated-node output; do not sum parent/child times as independent totals.

An operator can stop early under LIMIT, so its observed work need not cover everything its full-cost estimate describes. Parallel plans add worker-specific execution and overlapping time; inspect those details before treating total loops as sequential duration. Planning Time and Execution Time are separate measurements; instrumentation can add overhead.

#### Map row flow to the access strategy

| Operator | What to inspect | What its name does not prove |
| ------------------- | -------------------------------------------------- | -------------------------------------------------------- |
| Seq Scan | rows examined/removed, predicate selectivity | A large-table scan is necessarily wrong |
| Index Scan | index conditions, residual filter, heap fetch work | Every predicate is handled by the index |
| Index Only Scan | coverage and Heap Fetches | No table visibility checks occurred |
| Bitmap scan | candidate bitmap, exact/lossy blocks, recheck | It preserves the index's order or needs multiple indexes |
| Nested Loop | outer size, repeated inner rows/loops | The inner lookup has constant or negligible total cost |
| Hash join/aggregate | build rows, batches, memory/spill | It is inferior to an indexed nested loop |
| Merge Join | compatible ordering and duplicate matches | A new sort is always required |
| Sort | rows/width, sort method and disk/memory | All displayed time belongs exclusively to sorting |

The [join chapter](20.4.2.02-joins.md) owns result pairing and the physical join mechanisms. Here their measurements explain observed work. Costs compare alternatives for a query under one cost model; a lower number across different workloads is not an independently measured speedup.

#### Compare estimates before changing configuration

Large estimate errors can result from stale statistics, skew, correlated columns or predicates without useful statistics. ANALYZE updates table statistics; EXPLAIN ANALYZE executes a statement with instrumentation. They are different operations.
Extended statistics or a different expression/schema may help some cases, but not every error has the same remedy.

A well-estimated query can still be slow because it must return/process much data. Some nodes may spill to temporary files; increasing work_mem can help one operation while multiplying memory across concurrent queries/operators/workers. Hash memory also depends on hash_mem_multiplier.
Avoid a global large setting based on one query.

## 2. Compare actual work safely

#### Trace a selective filter before and after an access path

Use PostgreSQL 16+ in a fresh disposable schema. This fixture keeps plan interpretation here; broader workload/pool/maintenance diagnosis belongs to [PostgreSQL performance](../01-postgresql-foundations/20.4.1.05-postgresql-performance.md).

```sql
CREATE TABLE plan_events(
    id integer PRIMARY KEY,
    tenant_id integer NOT NULL,
    payload text NOT NULL
);
INSERT INTO plan_events
SELECT n, n % 100, repeat('x', 100)
FROM generate_series(1, 10000) AS n;
ANALYZE plan_events;

EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT id FROM plan_events WHERE tenant_id = 42 ORDER BY id LIMIT 3;

CREATE INDEX plan_events_tenant_id ON plan_events(tenant_id, id);
ANALYZE plan_events;

EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT id FROM plan_events WHERE tenant_id = 42 ORDER BY id LIMIT 3;

SELECT id FROM plan_events WHERE tenant_id = 42 ORDER BY id LIMIT 3;
-- 42, 142, 242
```

The table has 100 matching tenant rows. Before the new index, the existing primary-key index can satisfy ORDER BY while filtering tenant values until LIMIT is met. Adding (tenant_id,id) allows restricting the tenant and producing compatible ID order.
The same three rows result; compare actual examined/removed rows and buffers rather than promising one universal Seq Scan → Index Scan transition.

Now run `SELECT id, payload FROM plan_events ORDER BY id;`. It returns the whole table, asks for much more work and cannot be covered by `(tenant_id, id)` because that index omits `payload` and does not provide global `id` order. The planner may choose a sequential scan even though the composite index exists.
Observe the actual version, settings and cache state; do not paste invented fixed timings as proof.

#### Separate instrumentation safety from SQL correctness

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
UPDATE plan_events SET payload = 'changed' WHERE id = 42;
SELECT payload FROM plan_events WHERE id = 42; -- changed inside this transaction
ROLLBACK;
SELECT length(payload) FROM plan_events WHERE id = 42; -- 100
```

ANALYZE performed the UPDATE. Rollback reverts this fixture's transactional change, but executing still takes locks and writes work; sequence increments or external function side effects are not generally rolled back. Use a safe disposable/representative environment for statements whose effects are unacceptable.
Plain EXPLAIN does not execute the main statement, though planning still has resource/lock/privilege consequences.

## 3. Read buffers, waits and newer plan output

Buffers: shared hit means PostgreSQL found a page in its shared buffer cache; shared read means it brought a page into that cache. A read may be served by the operating system cache, so it does not prove a physical device access. I/O timing requires the relevant setting and instrumentation; hits still cost CPU and synchronization work.
Parent buffer measurements include child activity, so summing the tree can double-count.

Rows Removed by Filter/Recheck exposes rejected candidates; it is generally a per-loop figure where applicable. Index Cond versus Filter distinguishes access restriction from later rejection. Heap Fetches measures index-only visibility visits.
Sort Method/Disk and hash batches can indicate temporary work; use the version's plan output and monitoring together.

PostgreSQL 18 adds `Index Searches` to index and bitmap scan nodes. Read it with `loops`: one node execution can perform multiple index searches, for example for an `IN`/`ANY` condition or a B-tree skip scan. It helps explain repeated index work that a loop count alone does not show.

When application parameters are skewed, compare the plan PostgreSQL can make without concrete values with a representative executed plan. PostgreSQL 18's `GENERIC_PLAN` shows a parameterized plan without executing the query; it cannot be combined with `ANALYZE`:

```sql
EXPLAIN (GENERIC_PLAN)
SELECT id FROM plan_events WHERE tenant_id = $1 ORDER BY id LIMIT 3;
```

PostgreSQL 18's `SERIALIZE` option measures converting result values to text or binary on the server. It can help distinguish executor work from expensive output conversion, but it excludes network transfer and client decoding. The default is `SERIALIZE NONE`:

```sql
EXPLAIN (ANALYZE, BUFFERS, SERIALIZE TEXT)
SELECT id, payload FROM plan_events WHERE tenant_id = 42;
```

These options are PostgreSQL 18 features; the executable fixture above remains compatible with PostgreSQL 16.

Reproduce the authorized query with representative bound values. Parameterized statements may use custom or generic plans, so literals can differ from the application's plan for skewed tenants. Include the relevant role/RLS/session settings; capturing a query with sensitive literals or explain output also requires appropriate access.

## 4. Diagnose the endpoint before changing the plan

For a slow list endpoint, measure acquisition, server execution and result transfer separately. In the plan, trace how many rows the filters keep, whether ORDER BY stops early, and whether a repeated lookup amplifies work. Keep the query, representative parameters, PostgreSQL version, role/session settings, schema and observed plan together; skew, cache state and RLS can change the result.
Check result correctness before replacing a join or aggregate: an apparently cheaper query may count the wrong grain.

Change one relevant condition—index, statistics, predicate, selected columns or bounded session setting—then compare equivalent results and observed work. Do not disable scan/join methods globally to force the desired screenshot. Statistics counters and artificial benchmarks do not establish a missing-index diagnosis by themselves.

## Summary

A plan connects the requested result to an estimated operator tree, and instrumented execution shows observed rows, loops, timing and resources. Interpret repeated/inclusive work, early stopping, visibility and cache layers correctly. Tune the actual bottleneck with safe representative experiments instead of assigning a performance verdict to a node name or cost number.

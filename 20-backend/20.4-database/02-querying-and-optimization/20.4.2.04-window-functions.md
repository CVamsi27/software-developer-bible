# PostgreSQL Window Functions

An analyst needs to show every employee alongside a department total and salary rank. Grouping alone would discard the employee rows; a window calculation keeps them visible.

## Definition

A window function computes a value using rows related to the current row while keeping that row in the result. GROUP BY instead reduces those employees to a grouped result. A window's partition, ordering and, for frame-sensitive functions, frame determine which relationships it uses.

> **Textbook Definition:** A window function evaluates over a partition or frame associated with an output row without collapsing the input rows; its function semantics, ordering and frame specify the related rows used.

## First Principles

Showing each employee's share of departmental pay needs both the individual row and a total across its peers. Ordinary grouping alone discards the individual row identity. A window attaches that cross-row calculation while preserving the input grain.

“Previous” and “top” have no meaning without an order. Equal salaries or timestamps need a policy: treat ties as equal for ranking, or choose a deterministic row order for limited results. Adding an ID tie-breaker changes which rows are peers, so it is not interchangeable with ranking solely by salary.

A moving calculation also needs a unit. Seven preceding stored rows may cover more than seven days when dates are missing. Distinguish positional neighbors, ordering-value ranges and peer groups before choosing syntax.

## How It Works


### 1. Choose the rows each calculation can see

#### Define the partition, order and frame separately

PARTITION BY divides the post-filter input into independent sets. A partition is not a peer group: **peers** are rows equal under the window's ORDER BY keys. The window order describes calculation order; a final ORDER BY independently specifies displayed result order.

The frame selects a subset around the current row:

| Frame mode | Unit | Boundary |
| ---------- | ---------------------------------- | ----------------------------------------------------------------------------------- |
| ROWS | Positions in the ordered partition | Ties need a deterministic order for repeatable per-row accumulation |
| RANGE | Ordering values, including peers | Bounded offsets depend on ordering type; offset RANGE needs one ordering expression |
| GROUPS | Groups of equal ordering keys | Moves across peer groups rather than individual rows |

With an ORDER BY and no explicit frame, the usual default is RANGE from the partition start through the current row's last peer. Without ORDER BY, the default covers the whole partition. Aggregate windows and first_value/last_value/nth_value use the frame; ranking and lag/lead have their own partition/order semantics and do not turn into frame-local functions merely because a frame clause is added.

Windows see the rows after FROM/joins, WHERE, grouping and HAVING. An outer query can then filter their computed values; PostgreSQL 18 has no `QUALIFY` clause. Joining duplicates before the window or filtering before it changes its input; moving a filter to the outer query can change the denominator/ranking rather than being a cosmetic rewrite.

### 2. Trace ranking, frames and neighboring rows

#### Trace ties and totals in one complete fixture

Use PostgreSQL 16+ in a fresh disposable schema. Salary values are small illustrative units.

```sql
CREATE TABLE window_employees(
    id integer PRIMARY KEY,
    department text NOT NULL,
    salary integer NOT NULL,
    hired_on date NOT NULL
);
INSERT INTO window_employees VALUES
    (1, 'A', 100, '2026-01-01'),
    (2, 'A', 80,  '2026-01-02'),
    (3, 'A', 80,  '2026-01-02'),
    (4, 'A', 60,  '2026-01-04'),
    (5, 'B', 50,  '2026-01-01');

SELECT id, salary,
    row_number() OVER (ORDER BY salary DESC, id) AS row_position,
    rank() OVER (ORDER BY salary DESC) AS salary_rank,
    dense_rank() OVER (ORDER BY salary DESC) AS distinct_salary_rank,
    sum(salary) OVER () AS total
FROM window_employees WHERE department = 'A'
ORDER BY salary DESC, id;
-- id | salary | row_position | salary_rank | distinct_salary_rank | total
-- 1  | 100    | 1            | 1           | 1                    | 320
-- 2  | 80     | 2            | 2           | 2                    | 320
-- 3  | 80     | 3            | 2           | 2                    | 320
-- 4  | 60     | 4            | 4           | 3                    | 320
```

The row_number order deterministically separates IDs 2 and 3. Salary-only rank keeps them peers and skips rank 3; dense_rank counts distinct salary groups. Department B is removed before every window, so the total is 320, not the whole-table 370.
A department-share expression can use salary * 100.0 / NULLIF(sum(salary) OVER (PARTITION BY department),0); specify what a zero/empty denominator means for the product.

#### Select two rows or two salary groups deliberately

```sql
WITH ranked AS (
    SELECT id, department, salary,
        row_number() OVER (
            PARTITION BY department ORDER BY salary DESC, id
        ) AS rn
    FROM window_employees
)
SELECT id, department, salary FROM ranked WHERE rn <= 2
ORDER BY department, rn;
-- 1 | A | 100
-- 2 | A | 80
-- 5 | B | 50
```

Replacing row_number with salary-only dense_rank and filtering <=2 includes ID 3 as well: two distinct salary levels can contain more than two rows. salary-only rank expresses ranking positions with gaps. Decide the business tie policy before selecting a function; a tie-breaker in that rank's ordering would remove salary equality.

#### Show the default peer frame versus row-by-row accumulation

```sql
SELECT id,
    sum(salary) OVER (ORDER BY salary DESC) AS through_current_peers,
    sum(salary) OVER (
        ORDER BY salary DESC, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS through_current_row,
    last_value(salary) OVER (ORDER BY salary DESC) AS last_in_default_frame,
    last_value(salary) OVER (
        ORDER BY salary DESC, id
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS last_in_partition
FROM window_employees WHERE department = 'A'
ORDER BY salary DESC, id;
-- 1 | 100 | 100 | 100 | 60
-- 2 | 260 | 180 | 80  | 60
-- 3 | 260 | 260 | 80  | 60
-- 4 | 320 | 320 | 60  | 60
```

Both salary-80 peers see 260 in the default frame. last_value means the last value in its frame, not automatically the partition's final value; the full-frame expression deliberately returns 60 everywhere. first_value and nth_value follow the same frame boundary, and nth_value returns NULL if the selected position is absent.

#### Compare neighbors under a deterministic order

```sql
SELECT id,
    lag(salary) OVER (PARTITION BY department ORDER BY hired_on, id) AS prior_salary,
    lead(salary) OVER (PARTITION BY department ORDER BY hired_on, id) AS next_salary
FROM window_employees
ORDER BY department, hired_on, id;
-- 1 | NULL | 80
-- 2 | 100  | 80
-- 3 | 80   | 60
-- 4 | 80   | NULL
-- 5 | NULL | NULL
```

No prior/next row gives the default NULL. A provided lag/lead default applies to an absent neighbor, not a NULL value in an existing neighbor. PostgreSQL 18 does not implement `IGNORE NULLS`; these functions always respect NULL values.
A monthly LAG(...,1) means the prior stored month: if February is absent, March compares to January. Generate/join a calendar at the intended grain before promising month-over-month or year-over-year comparisons.

### 3. Consequential Analytics Variants

#### Distribution functions use different tie policies

For salaries 60,80,80,100 in ascending order, rank is 1,2,2,4. percent_rank is (rank-1)/(partition_rows-1), with the single-row partition case returning zero. cume_dist is the fraction of rows preceding or peer with the current row: 1/4,3/4,3/4,1 here. It is not simply rank divided by row count when ties exist.

ntile(n) divides ordered positions as evenly as possible; bucket sizes can differ by one, ties can be split, and some buckets are absent when there are fewer rows than buckets. It is not an exact percentile-value calculation or a promise to keep equal salaries together.

#### Row windows and calendar windows answer different questions

AVG(value) over ROWS BETWEEN 6 PRECEDING AND CURRENT ROW averages up to seven stored rows. It is a seven-day average only after the input has the required one-row-per-day calendar, missing-day policy and ordering. An interval RANGE can represent a time range but still needs an explicit denominator/daily grain if the metric is daily rather than per event.

The same mechanism derives consecutive-date islands. Deduplicate at day grain, order days, subtract row_number from each date, then group equal shifted dates:

```sql
WITH days(day) AS (
    VALUES (date '2026-01-01'), (date '2026-01-02'), (date '2026-01-04')
), labeled AS (
    SELECT day, day - row_number() OVER (ORDER BY day)::integer AS island
    FROM days
)
SELECT min(day), max(day), count(*) FROM labeled
GROUP BY island ORDER BY min(day);
-- 2026-01-01 | 2026-01-02 | 2
-- 2026-01-04 | 2026-01-04 | 1
```

Repeated day rows would shift the sequence incorrectly, which is why deduplication precedes numbering. Date arithmetic and timezone/day selection must match the reporting calendar.

#### Derive sessions from time gaps without losing their identity

```sql
WITH events(id, occurred_at) AS (
    VALUES (1, timestamp '2026-01-01 10:00'),
           (2, timestamp '2026-01-01 10:20'),
           (3, timestamp '2026-01-01 10:50'),
           (4, timestamp '2026-01-01 11:21')
), prior AS (
    SELECT *, lag(occurred_at) OVER (ORDER BY occurred_at,id) AS previous
    FROM events
), boundaries AS (
    SELECT *, CASE WHEN previous IS NULL OR occurred_at-previous > interval '30 minutes'
                   THEN 1 ELSE 0 END AS starts_session
    FROM prior
), numbered AS (
    SELECT *, sum(starts_session) OVER (
        ORDER BY occurred_at,id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS session_id FROM boundaries
)
SELECT session_id,min(occurred_at),max(occurred_at),count(*)
FROM numbered GROUP BY session_id ORDER BY session_id;
-- 1 | 10:00 | 10:50 | 3
-- 2 | 11:21 | 11:21 | 1  (full timestamps are returned)
```

Exactly thirty minutes does not create a new session under this chosen > rule; changing it to >= splits at 10:50. For multiple users, carry and partition by user/tenant in both windows and group by that identity plus session_id. Late arriving events can change the calculated sessions, so persistent session IDs/aggregates need a correction/version policy rather than treating each analytical run as immutable history.

### 4. Real-World Decisions and Boundaries

Choose the input grain and authorized scope before computing totals/ranks. A duplicated join input can double a salary or event count; filtering tenant data after a whole-table window can leak other tenants through derived values. For each result, state the tie policy, frame unit and whether a missing calendar period is meaningful.
Windows read under the statement's snapshot; independent reporting statements need a defined isolation contract to share a coherent state.

Window order may require sorting; compatible existing order can help, and several incompatible windows can require additional sorts. Larger frames/partitions and sort spill affect resources. A universal O(N log N) label for ranking or O(N) for lag hides the cost of establishing order.
Inspect EXPLAIN and memory/concurrency before adding indexes or global work_mem.

## Summary

A window preserves its input rows while computing related values. Partition scope, ordering/peers, function semantics and frames jointly determine the result; displayed order and later filtering are separate decisions. Use explicit tie and calendar policies, verify a complete trace, and measure sorting/resource work before assigning performance expectations.

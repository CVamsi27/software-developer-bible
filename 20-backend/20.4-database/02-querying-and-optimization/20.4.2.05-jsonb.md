# PostgreSQL JSONB

>
> **Why it matters:** JSONB appears in system design interviews for flexible schemas, event storage, and metadata. Knowing when to use JSONB vs relational columns is a senior-level decision.

## Definition

JSONB (JSON Binary) is a PostgreSQL data type that stores JSON in a decomposed binary format. Unlike JSON (which stores text), JSONB:
- Eliminates duplicate keys
- Preserves key order
- Supports indexing
- Enables efficient containment queries

```sql
-- JSON (text) vs JSONB (binary)
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    metadata JSON, -- Stores as text, no indexing
    data JSONB -- Stores as binary, supports indexing
);

-- JSONB is decomposed
SELECT '{"a": 1, "a": 2}'::jsonb; -- {"a": 2} (duplicate removed)
SELECT '{"a": 1, "a": 2}'::json; -- {"a": 1, "a": 2} (kept as-is)
```

## First Principles

JSONB is Postgres's answer to a real tension: relational rigor vs schema-flexible data:

1. **Some data has no fixed shape worth a table.** Product attributes, integration payloads, ML feature vectors — forcing them into 40 nullable columns creates sparse-table misery; storing them as opaque text loses queryability. JSONB is the compromise: parsed, indexable hierarchy *inside* a relational row.
2. **The trade is write cost and statistics.** Parsed structure per value costs writes; internal keys aren't first-class columns, so the planner estimates poorly on JSONB predicates and GIN indexes trade size for lookup. The discipline: relational columns for what you query and join on *in bulk*, JSONB for what you occasionally reach into.
3. **It is not an excuse to skip schema design** — validation moves to CHECK constraints and app-layer schema (zod) — it just changes *where* the schema lives.

## Why Do We Need It?

| Problem | Solution |
| ---------------------- | -------------------------------------------- |
| **Flexible schema** | Store varying attributes without ALTER TABLE |
| **Event metadata** | Store arbitrary event properties |
| **User preferences** | Store settings as key-value pairs |
| **Product attributes** | Different attributes per category |
| **API responses** | Cache external API responses |
| **Audit logs** | Store before/after snapshots |

## How It Works

### JSONB Operators

```text
┌─────────────────────────────────────────────────────────────┐
│ JSONB OPERATORS                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ GETTING VALUES                                              │
│ ├── -> Get JSON object field (returns JSONB)                │
│ ├── ->> Get JSON object field (returns TEXT)                │
│ ├── #> Get JSON object at path (returns JSONB)              │
│ ├── #>> Get JSON object at path (returns TEXT)              │
│ └── @> Contains (JSONB @> JSONB → boolean)                  │
│                                                             │
│ CHECKING                                                    │
│ ├── ? Has key (JSONB ? text → boolean)                      │
│ ├── ?| Has any key (JSONB ?| text[] → boolean)              │
│ └── ?& Has all keys (JSONB ?& text[] → boolean)             │
│                                                             │
│ MODIFYING                                                   │
│ ├── || Concatenate (JSONB || JSONB)                         │
│ ├── - Delete key (JSONB - text)                             │
│ ├── #- Delete at path (JSONB - text[])                      │
│ └── #= Set at path                                          │
│                                                             │
│ CONTAINMENT                                                 │
│ ├── @> Contains ({"a":1} @> {"a":1} → true)                 │
│ └── <@ Contained by                                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## Code Examples

### 1. Basic Operations

```sql
-- Create table with JSONB
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Insert with JSONB
INSERT INTO products (name, attributes) VALUES
('Laptop', '{
    "brand": "Apple",
    "model": "MacBook Pro",
    "specs": {
        "cpu": "M3 Pro",
        "ram": "18GB",
        "storage": "512GB SSD"
    },
    "tags": ["electronics", "computers", "portable"],
    "price": 1999.99
}'),
('Phone', '{
    "brand": "Samsung",
    "model": "Galaxy S24",
    "specs": {
        "cpu": "Snapdragon 8 Gen 3",
        "ram": "8GB",
        "storage": "256GB"
    },
    "tags": ["electronics", "mobile"],
    "price": 899.99
}');

-- Get field as JSONB
SELECT name, attributes->'brand' as brand FROM products;
-- brand: "Apple"

-- Get field as TEXT
SELECT name, attributes->>'brand' as brand FROM products;
-- brand: Apple

-- Get nested field
SELECT name, attributes->'specs'->>'cpu' as cpu FROM products;
-- cpu: M3 Pro

-- Get array element
SELECT name, attributes->'tags'->0 as first_tag FROM products;
-- first_tag: "electronics"
```

### 2. Querying JSONB

```sql
-- Check if key exists
SELECT name FROM products WHERE attributes ? 'brand';

-- Check if multiple keys exist
SELECT name FROM products WHERE attributes ?& ARRAY['brand', 'model'];

-- Check if any key exists
SELECT name FROM products WHERE attributes ?| ARRAY['brand', 'color'];

-- Containment (JSONB @> JSONB)
SELECT name FROM products WHERE attributes @> '{"brand": "Apple"}';

-- Containment with nested values
SELECT name FROM products WHERE attributes @> '{
    "specs": {"cpu": "M3 Pro"}
}';

-- Array contains
SELECT name FROM products WHERE attributes->'tags' @> '["electronics"]';

-- Compare values
SELECT name FROM products WHERE (attributes->>'price')::numeric > 1000;

-- Pattern matching on text
SELECT name FROM products WHERE attributes->>'brand' ILIKE '%apple%';

-- Exists in array
SELECT name FROM products WHERE
    EXISTS (
        SELECT 1 FROM jsonb_array_elements_text(attributes->'tags') AS tag
        WHERE tag = 'electronics'
    );
```

### 3. JSONB Functions

```sql
-- Get all keys
SELECT jsonb_object_keys(attributes) FROM products;
-- brand, model, specs, tags, price

-- Get array length
SELECT jsonb_array_length(attributes->'tags') FROM products;

-- Check if value is array
SELECT jsonb_typeof(attributes->'tags') FROM products;
-- array

-- Check if value is object
SELECT jsonb_typeof(attributes->'specs') FROM products;
-- object

-- Flatten nested JSONB
SELECT
    name,
    attributes->>'brand' as brand,
    attributes->'specs'->>'cpu' as cpu,
    (attributes->>'price')::numeric as price
FROM products;

-- Aggregate to JSONB array
SELECT jsonb_agg(name) FROM products;
-- ["Laptop", "Phone"]

-- Build JSONB object
SELECT jsonb_build_object(
    'name', name,
    'brand', attributes->>'brand'
) FROM products;
```

### 4. Modifying JSONB

```sql
-- Add/Update field
UPDATE products
SET attributes = attributes || '{"color": "silver"}'::jsonb
WHERE name = 'Laptop';

-- Add nested field
UPDATE products
SET attributes = jsonb_set(
    attributes,
    '{specs, display}',
    '"14.2-inch Liquid Retina XDR"'::jsonb
)
WHERE name = 'Laptop';

-- Delete field
UPDATE products
SET attributes = attributes - 'color'
WHERE name = 'Laptop';

-- Delete nested field
UPDATE products
SET attributes = attributes #- '{specs, display}'
WHERE name = 'Laptop';

-- Merge JSONB objects
UPDATE products
SET attributes = attributes || '{
    "warranty": "1 year",
    "color": "Space Black"
}'::jsonb
WHERE name = 'Laptop';
```

### 5. JSONB Aggregation

```sql
-- Count products per brand
SELECT
    attributes->>'brand' as brand,
    COUNT(*) as count
FROM products
GROUP BY attributes->>'brand';

-- Aggregate attributes
SELECT
    jsonb_build_object(
        'total_products', COUNT(*),
        'brands', jsonb_agg(DISTINCT attributes->>'brand'),
        'avg_price', ROUND(AVG((attributes->>'price')::numeric), 2)
    ) as summary
FROM products;

-- Group by array element
SELECT
    tag,
    COUNT(*) as count
FROM products,
    jsonb_array_elements_text(attributes->'tags') AS tag
GROUP BY tag
ORDER BY count DESC;
```

### 6. JSONB Indexing

```sql
-- GIN index for containment queries
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);

-- GIN index for key existence
CREATE INDEX idx_products_attributes_keys ON products USING GIN (attributes jsonb_path_ops);

-- B-tree index for specific path
CREATE INDEX idx_products_brand ON products ((attributes->>'brand'));

-- B-tree index for numeric value
CREATE INDEX idx_products_price ON products (((attributes->>'price')::numeric));

-- Composite index
CREATE INDEX idx_products_brand_price ON products (
    (attributes->>'brand'),
    ((attributes->>'price')::numeric)
);

-- Query using index
EXPLAIN ANALYZE
SELECT * FROM products WHERE attributes @> '{"brand": "Apple"}';
-- Uses GIN index

EXPLAIN ANALYZE
SELECT * FROM products WHERE attributes->>'brand' = 'Apple';
-- Uses B-tree index on (attributes->>'brand')
```

### 7. Real-World: Event Metadata

```sql
-- Events table with flexible metadata
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    event_type VARCHAR(50) NOT NULL,
    user_id INT,
    metadata JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Different event types have different metadata
INSERT INTO events (event_type, user_id, metadata) VALUES
('page_view', 123, '{
    "url": "/products/456",
    "referrer": "https://google.com",
    "device": "mobile",
    "browser": "Safari"
}'),
('purchase', 123, '{
    "product_id": 456,
    "amount": 29.99,
    "currency": "USD",
    "payment_method": "credit_card"
}'),
('signup', 456, '{
    "source": "organic",
    "plan": "pro",
    "referrer": "https://twitter.com"
}');

-- Query by event type and metadata
SELECT * FROM events
WHERE event_type = 'purchase'
AND metadata @> '{"currency": "USD"}';

-- Get all purchase amounts
SELECT
    (metadata->>'amount')::numeric as amount,
    created_at
FROM events
WHERE event_type = 'purchase'
ORDER BY created_at DESC;

-- Count by device
SELECT
    metadata->>'device' as device,
    COUNT(*) as count
FROM events
WHERE event_type = 'page_view'
GROUP BY metadata->>'device';
```

## Common Mistakes

### 1. Querying Without Index

```sql
-- Bad: Full table scan
SELECT * FROM products WHERE attributes->>'brand' = 'Apple';
-- Scans ALL rows

-- Good: Add index for frequent queries
CREATE INDEX idx_products_brand ON products ((attributes->>'brand'));
SELECT * FROM products WHERE attributes->>'brand' = 'Apple';
-- Uses index
```

### 2. Using JSON Instead of JSONB

```sql
-- Bad: JSON type (no indexing, no containment queries)
CREATE TABLE events (
    metadata JSON -- Can't create GIN index
);

-- Good: JSONB type
CREATE TABLE events (
    metadata JSONB -- Supports GIN index
);
```

### 3. Storing Everything in JSONB

```sql
-- Bad: Storing frequently queried fields in JSONB
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    data JSONB -- data->>'email' queried often
);
-- Every query needs JSONB extraction

-- Good: Mix of relational and JSONB
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) NOT NULL, -- Frequently queried
    name VARCHAR(255) NOT NULL, -- Frequently queried
    preferences JSONB DEFAULT '{}', -- Flexible, rarely queried
    metadata JSONB DEFAULT '{}' -- Flexible, rarely queried
);
```

### 4. Not Using jsonb_path_ops

```sql
-- Slower for containment queries
CREATE INDEX idx_data ON table USING GIN (data);

-- Faster for containment queries (but slower for key existence)
CREATE INDEX idx_data ON table USING GIN (data jsonb_path_ops);

-- Choose based on query patterns:
-- @> containment → jsonb_path_ops
-- ? key existence → default GIN
```

## Performance Considerations

| Operation | Without Index | With GIN Index | With B-tree Index |
| ---------------------- | ------------- | -------------- | ----------------- |
| `@>` containment | O(N) | O(1) | N/A |
| `?` key exists | O(N) | O(1) | N/A |
| `->>'field' = 'value'` | O(N) | N/A | O(log N) |
| Insert/Update | O(1) | O(log N) | O(log N) |

### When to Use JSONB

| Use Case | Recommendation |
| ----------------------------------- | ---------------------- |
| **Frequently queried fields** | Use relational columns |
| **Flexible, rarely queried fields** | Use JSONB |
| **Event metadata** | Use JSONB |
| **API response caching** | Use JSONB |
| **Schema evolves frequently** | Use JSONB |
| **Need ACID transactions** | Use JSONB (PostgreSQL) |

## Summary

| Feature | JSONB |  |  |
| ------------- | ---------------------------------------- | --- | --- |
| **Storage** | Binary, decomposed |  |  |
| **Indexing** | GIN (containment), B-tree (paths) |  |  |
| **Operators** | ->, ->>, @>, ?, |  | , - |
| **Best for** | Semi-structured data, flexible schemas |  |  |
| **Avoid for** | Frequently queried fields, complex joins |  |  |

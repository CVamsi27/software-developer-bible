# PostgreSQL JSONB

An integration sends optional fields that vary by source, while the application still needs typed prices, searchable brands and stable tenant ownership. JSONB holds the variable shape; SQL constraints and query contracts still define what the data means.

## Definition

JSONB stores parsed JSON values inside a PostgreSQL row. It supports structured extraction, containment and indexes while discarding original whitespace, object-key order and duplicate object keys. Relational constraints and transactions still apply to the containing row; choosing JSONB does not define the document's valid shape or update ownership.

> **Textbook Definition:** JSONB is PostgreSQL's decomposed JSON representation supporting structured value operators and index access. It preserves the resulting JSON value semantics rather than original formatting or duplicate object keys.

## First Principles

An integration's optional attributes may vary by source, while its tenant, identifier and lifecycle still need stable relational rules. Keeping variable attributes in a structured value makes them queryable without turning every optional path into a column. Stable keys, constraints and relationships can remain ordinary columns in the same row.

The choice trades strictness and locality. A path extraction can fail or return NULL when the shape differs, and a cast can reject a value that is valid JSON but not valid business data. A large document update also locks and produces a new version of the containing row, not an independently concurrent field store.

Searching inside the value requires an access structure compatible with the operator/expression. One general JSONB index cannot accelerate every extracted range, text pattern or derived sort. Decide validation and workload first, then select representation/indexes.

## 1. Distinguish JSON values from SQL values

#### Separate JSON values from SQL values

| Operation | Result | Key boundary |
| ------------------------------- | ------------------------------------ | --------------------------------------------------------------------- |
| attrs -> 'brand' | JSONB value | String retains its JSON string type |
| attrs ->> 'brand' | SQL text | JSON string is extracted as text; conversion loses type distinctions |
| attrs #> / #>> path | JSONB / text at nested path | Missing/incompatible extraction generally yields SQL NULL |
| attrs @> document | Boolean containment | Checks structured JSON value/type containment, not a string substring |
| attrs ? key | Top-level key/array-string existence | Does not recursively search all nested keys |
| jsonb_set(value,path,new_value) | Updated JSONB value | Existing intermediate path and create-missing behavior matter |
| `value \|\| other` | Top-level concatenation | Object merge is shallow; overlapping right keys replace left values |
| value - key / #- path | Removed key/path | Returns a value; persistence requires an UPDATE |

SQL NULL means no SQL value; JSON null is a stored JSON value. Extraction to text can make JSON null and a missing field both look like SQL NULL. Test existence/type when the distinction matters.
JSONB accepts arrays/scalars as well as objects unless the schema constrains it.

The json type retains input text and duplicate keys, while JSONB retains the last duplicate object-key value. It is inaccurate to say json can never be indexed: a suitable extracted/cast expression can have an expression index. JSONB supplies the native structured operators/GIN choices described here.
If exact original signed/audit payload bytes matter, preserve those bytes independently under the required integrity/retention contract.

## 2. Validate and query a variable document

#### Constrain the shape you rely on and inspect types

Use PostgreSQL 16+ in a fresh disposable schema. Stable identity/tenant/version live outside the variable document.

```sql
CREATE TABLE json_products(
    id integer PRIMARY KEY,
    tenant_id integer NOT NULL,
    version integer NOT NULL DEFAULT 1,
    attributes jsonb NOT NULL,
    CHECK (jsonb_typeof(attributes) = 'object'),
    CHECK (NOT (attributes ? 'price') OR jsonb_typeof(attributes->'price') = 'number')
);
INSERT INTO json_products(id,tenant_id,attributes) VALUES
    (1, 7, '{"brand":"Acme","price":12.5,"specs":{"cpu":"A","ram":8},"tags":["portable","audio"],"note":null}'),
    (2, 7, '{"brand":"Other","price":5,"specs":{},"tags":["audio"]}');

SELECT id, attributes->>'brand', attributes#>>'{specs,cpu}'
FROM json_products ORDER BY id;
-- 1 | Acme  | A
-- 2 | Other | NULL

SELECT attributes ? 'note', jsonb_typeof(attributes->'note'),
       attributes->>'note' IS NULL, attributes ? 'missing'
FROM json_products WHERE id=1;
-- true | null | true | false
```

`note` exists with JSON null; `missing` does not exist. The optional price check accepts absence but rejects a string or JSON null in a present price. JSON syntax alone would accept those. `NOT NULL` plus object/type conditions establish this fixture's minimal contract; production validation still needs ranges, required keys, schema version and field-level authorization as appropriate.

#### Project JSON into typed columns with SQL/JSON

PostgreSQL 17 added SQL/JSON functions, including `JSON_TABLE`, which turns matching document values into relational rows and typed columns. Choose explicit behavior for missing paths and conversion errors instead of silently accepting NULLs:

```sql
SELECT p.id, jt.brand, jt.price
FROM json_products AS p
CROSS JOIN LATERAL JSON_TABLE(
    p.attributes, '$'
    COLUMNS (
        brand text PATH '$.brand' ERROR ON EMPTY,
        price numeric PATH '$.price' ERROR ON EMPTY ERROR ON ERROR
    )
) AS jt
ORDER BY p.id;
```

`JSON_TABLE` is laterally joined to its input row by definition. `JSON_VALUE` extracts one scalar, `JSON_QUERY` extracts a JSON value such as an object or array, and `JSON_EXISTS` tests whether a path matches; choose the function whose result contract fits the question. This example requires PostgreSQL 17+, while the chapter's core fixtures remain PostgreSQL 16+.

#### Match containment without hiding value types

```sql
SELECT id FROM json_products
WHERE tenant_id=7 AND attributes @> '{"tags":["audio"]}'::jsonb
ORDER BY id;
-- 1, 2
SELECT
    '{"price":12.5}'::jsonb @> '{"price":12.5}'::jsonb AS numeric_match,
    '{"price":12.5}'::jsonb @> '{"price":"12.5"}'::jsonb AS string_match;
-- true | false
```

Nested containment must preserve the required structure. Array containment is not sequence equality and does not count repeated elements; choose the operator matching the product question. Extracted price range comparisons need a safe numeric contract, then a compatible expression/column access path.
Binding tenant/documents avoids SQL interpolation, but authorization must still derive permitted tenant and mutable fields from a trusted identity.

#### Trace a nested mutation and the shallow-merge boundary

```sql
UPDATE json_products SET attributes=jsonb_set(attributes,'{specs,ram}','16'::jsonb),
                         version=version+1
WHERE id=1;
SELECT attributes#>>'{specs,cpu}',attributes#>>'{specs,ram}',version
FROM json_products WHERE id=1;
-- A | 16 | 2

SELECT '{"specs":{"cpu":"A","ram":8}}'::jsonb
       || '{"specs":{"ram":16}}'::jsonb;
-- {"specs":{"ram":16}}: the right specs object replaces the old one, so cpu disappears.
SELECT jsonb_set('{}'::jsonb,'{specs,ram}','16'::jsonb);
-- {}: a missing intermediate specs object is not recursively created.
```

The first update changes a nested field in the database's current row value. The second expression is a shallow top-level merge: the right specs value replaces the left specs value, so cpu disappears. There is no built-in JSONB #= assignment operator in this contract.
Choose jsonb_set, subscripting where supported, or a deliberate transformation under the deployed version.

#### Reject a stale whole-document replacement

```sql
UPDATE json_products
SET attributes='{"brand":"Edited","price":13}'::jsonb,version=version+1
WHERE id=1 AND tenant_id=7 AND version=1
RETURNING id,version;
-- no row: the earlier mutation already made version 2
```

A client that read version 1 cannot replace version 2 under this expected-version check. Handle the no-row result as a conflict/authorization/existence boundary, then decide whether to reread and merge. Replacing a stale client document without this check can discard another writer's fields even if the writers edited different logical paths.

A current-row jsonb_set UPDATE still locks the containing row. Under PostgreSQL Read Committed, a waiting UPDATE can re-evaluate against the committed updated row; stricter isolation can raise a serialization error. Every writer of version/document state must participate in the selected protocol.
The [locking chapter](../03-transactions-and-replication/20.4.3.03-optimistic-pessimistic-locking.md) owns the concurrency implementation.

## 3. Index the Operator You Actually Query

The default GIN jsonb_ops supports top-level key-existence operators as well as containment and supported JSON-path matching. jsonb_path_ops supports containment and supported JSON-path matching, **not** ?, ?| or ?&. It is not a slower alternative for existence; that operation is unsupported by this operator class. It may produce smaller/more selective containment structures but has different empty-structure/query boundaries.

```sql
CREATE INDEX json_products_document ON json_products USING gin(attributes);
CREATE INDEX json_products_brand ON json_products((attributes->>'brand'));
ANALYZE json_products;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM json_products WHERE attributes @> '{"brand":"Acme"}'::jsonb;
```

The document GIN can support the containment operator; the expression B-tree supports matching brand extraction/equality and appropriate ordering, not arbitrary JSON containment. The two-row fixture can favor a sequential scan. Neither index guarantees a latency complexity or that every plan must use it.
A numeric expression index requires valid casts on every relevant row, including future writes; a generated/ordinary typed column can make a stable heavily queried field's constraints/statistics clearer.

A document index does not automatically cover attributes->'tags' @> ... applied to an extracted value. Rewrite to a compatible whole-document containment or choose the exact extracted-expression index. PostgreSQL's JSON-path operators have their own syntax/three-valued/error behavior; do not assume they share every extraction/cast boundary.

## 4. Expansion, Aggregation and Schema Decisions

jsonb_array_elements(_text) expands array elements into rows, changing result grain like a join. Missing or non-array input needs a defined policy; the function can reject a scalar. Duplicate tags can count several memberships for one product, so use deliberate DISTINCT when the metric is products rather than occurrences.

```sql
SELECT tag,count(*) AS product_memberships
FROM json_products AS p
CROSS JOIN LATERAL jsonb_array_elements_text(p.attributes->'tags') AS tags(tag)
GROUP BY tag ORDER BY tag;
-- audio | 2
-- portable | 1

SELECT jsonb_agg(attributes->>'brand' ORDER BY id) FROM json_products;
-- ["Acme", "Other"]
```

The fixture has unique tags and array-valued tags. A production validator/check must guarantee that shape or the query must branch explicitly. jsonb_agg without input order does not guarantee array order; empty-input/null handling needs an explicit product policy. Build response objects with jsonb_build_object rather than hand-concatenating JSON text, and authorize which fields may be returned.

Promote a path to a relational column when its stable identity, foreign key, uniqueness, range/statistics or independent mutation workload benefits from that representation. JSONB can still serve frequently queried paths with appropriate indexes; “frequently queried” alone is not a prohibition. Schema flexibility moves validation/evolution into a document contract rather than removing it.
Vector representations should follow the actual vector-search type/model/index requirements rather than assuming JSONB is an ML vector engine.

## Failure and Recovery Boundaries

Numeric casts can fail even when the input is valid JSON, and CHECK expressions that evaluate SQL NULL pass unless explicitly prevented. Verify absent, JSON-null, SQL-null and wrong-type cases. Large documents produce row/version/WAL/index costs and contention; separate independently hot state when measured ownership demands it.

Payloads can contain unexpected sensitive fields. Apply bounded size/shape validation and explicit writable-field policies, retain the minimum data, and avoid exposing complete integration payloads through logs or generic serialization. Version document schemas and migrate/rebuild derived indexes deliberately; restore tests must cover both typed columns and valid document shapes.

## Summary

JSONB stores a structured value inside an ordinary PostgreSQL row. Shape/type/null validation, operator-compatible indexing and whole-row concurrency still determine correctness and cost. Distinguish extraction from containment, shallow merge from nested replacement, and idempotent updates from stale-document conflict handling.

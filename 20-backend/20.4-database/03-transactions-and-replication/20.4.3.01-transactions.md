# Database Transactions

## Definition

A **transaction** groups database statements into one commit or rollback boundary. In a transfer, the debit and credit must both become committed data, or neither should. A transaction also selects how concurrent changes affect its reads; that is its **isolation level**.

> **Textbook Definition:** A database transaction defines a unit of work with a commit or rollback outcome. Atomicity, consistency, isolation and durability describe distinct properties whose practical behavior depends on database rules and configuration.

## First Principles

A crash can interrupt a sequence after any statement. Grouping the statements gives recovery one decision about their changes. Concurrency adds a different problem: another transaction can change the facts used to choose those writes. Atomic grouping alone cannot validate that decision.

Constraints express invariants the database can check; isolation, conditional writes, and locks protect decisions between statements. External effects need their own protocol because a database rollback cannot recall an email or reverse an already accepted payment.

## Follow a transfer through its commit boundary

Use PostgreSQL 16 for the SQL examples. Create this fixture once in a disposable database:

```sql
CREATE TABLE transfer_accounts (
  id integer PRIMARY KEY,
  balance_cents bigint NOT NULL CHECK (balance_cents >= 0)
);
INSERT INTO transfer_accounts VALUES (1, 10000), (2, 0);
```

A transfer of 2500 cents has these stages:

```text
BEGIN → lock both accounts → verify both exist and debit is affordable
      → debit → credit → COMMIT → report success
                         failure → ROLLBACK
```

This SQL raises an error on an invalid transfer. After any error, the caller must issue `ROLLBACK` and report failure, rather than treating a later `COMMIT` command as success.

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '5s';
DO $$
DECLARE
  locked_id integer;
  account_count integer := 0;
BEGIN
  -- Every writer of these accounts uses the same immutable ID order.
  FOR locked_id IN
    SELECT id FROM transfer_accounts
    WHERE id IN (1, 2) ORDER BY id FOR UPDATE
  LOOP
    account_count := account_count + 1;
  END LOOP;
  IF account_count <> 2 THEN
    RAISE EXCEPTION 'Account unavailable';
  END IF;
  UPDATE transfer_accounts
    SET balance_cents = balance_cents - 2500
    WHERE id = 1 AND balance_cents >= 2500;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Insufficient funds';
  END IF;
  UPDATE transfer_accounts SET balance_cents = balance_cents + 2500
    WHERE id = 2;
END $$;
COMMIT;
```

The `DO` block executes within the surrounding transaction; it is not an independent commit boundary. The fixed positive amount and distinct IDs make this a teaching fixture. An API must validate its amount, authorize both accounts within the tenant, and use an idempotency key to handle repeated requests. See the linked Prisma implementation for parameterized application code.

## Separate the four ACID responsibilities

| Property | Transfer consequence | What it does not supply |
| ----------- | ------------------------------------------------------ | ---------------------------------------- |
| Atomicity | Both row changes commit together | Atomicity with a remote payment provider |
| Consistency | Defined constraints remain satisfied | A rule you never encoded or checked |
| Isolation | Concurrent operations obey the chosen level | Every level behaving as serial execution |
| Durability | Committed changes survive the configured failure model | Survival of every site/storage loss |

PostgreSQL normally flushes commit WAL locally before acknowledging success. `synchronous_commit = off` changes that acknowledgment boundary; a recent acknowledged transaction can be lost after a crash. Keep the WAL and storage configuration part of the durability contract. A durable local commit also says nothing about an asynchronous replica having replayed it.

## Choose which concurrent changes a read may see

PostgreSQL's default **Read Committed** takes a new snapshot for each command. **Repeatable Read** uses a snapshot established by the first non-control statement. **Serializable** additionally checks dependencies between transactions and may abort an execution that cannot fit a serial order.

| PostgreSQL level | Two reads after another session commits | Cross-row decision anomalies |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------- |
| Read Uncommitted | Behaves as Read Committed; no dirty reads | Possible |
| Read Committed | May observe the newer committed value | Possible |
| Repeatable Read | Retains the snapshot, including matching row sets | Write skew remains possible |
| Serializable | Retains snapshot; conflicting execution may abort | Successful participating transactions must fit a serial order |

Set the level before the transaction's data statements:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance_cents FROM transfer_accounts WHERE id = 1;
-- A second session now commits a change to that row.
SELECT balance_cents FROM transfer_accounts WHERE id = 1;
COMMIT;
```

Repeat the experiment with `READ COMMITTED`; the second read can change. An ordinary read does not lock the row against writers. At Read Committed, an `UPDATE ... WHERE balance_cents >= amount` waits for a concurrent updater if necessary and rechecks its predicate on the updated row. This makes a single-row conditional debit useful without an earlier unlocked balance check.

## Trace write skew before choosing Serializable

Suppose at least one of two staff members must remain on call. Each transaction reads a count of two, then turns **its own** row off. Repeatable Read gives both the same stable snapshot; they update different rows, so both can commit and leave nobody on call.

Serializable can reject that overlapping decision with SQLSTATE `40001`. Alternatively, serialize changes through one shared guard row, with every writer following that protocol. A row version on each staff member alone does not protect the aggregate count. Correctness depends on the invariant and all its writers, not the label “financial” or “high traffic.”

## Recover a local step with a savepoint

```sql
BEGIN;
UPDATE transfer_accounts SET balance_cents = balance_cents + 100 WHERE id = 2;
SAVEPOINT optional_step;
UPDATE transfer_accounts SET balance_cents = balance_cents + 50 WHERE id = 2;
ROLLBACK TO SAVEPOINT optional_step;
RELEASE SAVEPOINT optional_step;
COMMIT;
```

Only the 100-cent change remains. A savepoint can also recover from a statement error if the caller rolls back to it before continuing. Use this when the earlier work is still a valid outcome; it cannot make a required failed credit optional. Sequence increments are another boundary: `nextval()` values are not reclaimed on rollback, so generated identifiers can have gaps.

## Keep retries inside a known outcome

- For `40001` (serialization failure) or `40P01` (deadlock), roll back and retry the **whole transaction**, with bounded attempts and jitter. Recompute reads and decisions.
- A network failure during commit can leave the outcome unknown. Resolve through a durable operation key/result; blindly repeating a transfer can charge twice.
- Commit an outbox row alongside a business change, then let a separate worker deliver the external event. Delivery still needs deduplication.
- Use the same checked-out connection/transaction client for every participating statement. A query through the root ORM client can escape the transaction.

## Diagnose the transaction that remains open

```sql
SELECT pid, state, now() - xact_start AS transaction_age,
       wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE datname = current_database() AND xact_start IS NOT NULL
ORDER BY xact_start;
```

`xact_start` measures transaction age; `query_start` measures the current/last query. An idle transaction can retain locks and an old snapshot while doing no useful work. Keep remote calls and user interaction outside the boundary, and configure an idle-in-transaction timeout appropriate to the service.

PostgreSQL supports transactional `CREATE TABLE` and many other DDL changes; it does not implicitly commit every DDL statement. Some commands, including `CREATE INDEX CONCURRENTLY`, cannot run inside a transaction block. Check the migration operation's contract instead of borrowing another database's rule.

## Summary

First define the invariant and commit boundary. Then choose the conditional write, constraint, lock, or isolation level that protects its decision under concurrency. Retry known rollbacks as complete units, resolve unknown commit outcomes through operation identity, and deliver external effects after durable intent is recorded.

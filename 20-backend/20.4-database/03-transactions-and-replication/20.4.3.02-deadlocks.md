# Deadlocks

Two transfers lock the same accounts in opposite order. Each now waits for a lock held by the other, so neither can make progress until PostgreSQL breaks the cycle.

## Definition

A **deadlock** is a cycle of waits: transaction A holds a resource B needs, while B holds a resource A needs. In PostgreSQL, the detector breaks the cycle by aborting one transaction with SQLSTATE `40P01`. A long wait without a cycle is blocking, and needs a different diagnosis.

> **Textbook Definition:** A deadlock occurs when a cycle of resource dependencies prevents participating transactions from progressing. A database resolves a detected cycle by aborting a participant; retry must restart the transaction with valid inputs.

## First Principles

Locks can conflict, remain held while another lock is requested, and be acquired in different orders. Those conditions allow a cycle. Requiring every participating path to acquire resources in one total order removes the circular-wait condition.
Shorter transactions reduce the time available for a cycle but do not prove it impossible.

## 1. Watch two sessions form the cycle

Use `transfer_accounts` from [Transactions](20.4.3.01-transactions.md). Open two PostgreSQL sessions and run one numbered step at a time:

| Step | Session A | Session B |
| ---- | --------------------------------------------------------------- | --------------------------------------------------------- |
| 1 | `BEGIN;` | `BEGIN;` |
| 2 | `SELECT id FROM transfer_accounts WHERE id=1 FOR UPDATE;` | `SELECT id FROM transfer_accounts WHERE id=2 FOR UPDATE;` |
| 3 | `SELECT id FROM transfer_accounts WHERE id=2 FOR UPDATE;` waits |  |
| 4 |  | `SELECT id FROM transfer_accounts WHERE id=1 FOR UPDATE;` |
| 5 | One transaction receives `40P01` | The other can proceed when its blocker aborts |
| 6 | `ROLLBACK;` | `ROLLBACK;` |

The victim is not a contract an application should predict. Neither client should publish success until commit. The aborted client rolls back and may retry the complete operation.

## 2. Know what the lock belongs to

A statement can hold **table-level locks** as well as **row-level locks**. PostgreSQL table-mode names such as `ROW EXCLUSIVE` are historical names; they do not mean one tuple is locked.

| Operation | Table mode typically acquired | Consequence |
| ------------------------------- | ----------------------------- | ----------------------------------------------------- |
| Ordinary `SELECT` | `ACCESS SHARE` | Can coexist with ordinary writes |
| `INSERT`, `UPDATE`, `DELETE` | `ROW EXCLUSIVE` | Compatible with other `ROW EXCLUSIVE` holders |
| `SELECT ... FOR UPDATE` | `ROW SHARE`, plus row locks | Conflicting locks on selected rows wait |
| `TRUNCATE`, many DDL operations | `ACCESS EXCLUSIVE` | Blocks even ordinary reads |

`FOR UPDATE` blocks competing updates and conflicting row-lock requests; ordinary multiversion concurrency control (MVCC) readers can still read a visible row version. Foreign keys, triggers, unique checks, and data definition language (DDL) can add resources to a wait graph. Ordering only the two explicit SQL statements is insufficient if another path acquires those hidden resources in reverse order.

## 3. Make the order part of the operation

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
SELECT id FROM transfer_accounts
WHERE id IN (1, 2)
ORDER BY id FOR UPDATE;
-- Verify the rows and perform both changes on this connection.
COMMIT;
```

All paths touching this account set must use the same immutable ID order. Locking an account by “source then destination” changes the order when the transfer direction reverses. Avoid concurrent lock requests inside one operation; sequential acquisition makes the intended order visible.

Lock upgrades can also cycle: two transactions take compatible shared locks and later both request exclusive access. Request the strongest mode the operation genuinely needs initially, while limiting the set of rows held.

## 4. Select a wait policy deliberately

| Policy | Behavior | Suitable consequence |
| ---------------- | ------------------------------------- | ---------------------------------------------------------------------- |
| Default row lock | Waits for a conflicting holder | Bound the wait with a timeout |
| `NOWAIT` | Errors immediately, typically `55P03` | Tell the caller the record is busy |
| `SKIP LOCKED` | Omits locked rows | Claim other queue work; do not interpret as a complete business result |

After `NOWAIT` or a lock-timeout error inside a transaction, roll back before reusing the connection. A pessimistic lock does not guarantee success: deadlocks, timeouts, constraints, and connection failures still exist.

`deadlock_timeout` controls when PostgreSQL checks a wait for cycles, not a maximum query duration. Its tuning has detection-cost and diagnostic tradeoffs and may require administrative privileges. `lock_timeout` bounds each lock acquisition wait; `statement_timeout` bounds a statement, not an entire multi-statement request.

## 5. Find the blocker through the server's wait graph

```sql
SELECT waiting.pid AS waiting_pid,
       waiting.query AS waiting_query,
       blocker.pid AS blocker_pid,
       blocker.state AS blocker_state,
       clock_timestamp() - blocker.xact_start AS blocker_transaction_age,
       blocker.query AS blocker_query
FROM pg_stat_activity AS waiting
CROSS JOIN LATERAL (
  SELECT DISTINCT pid
  FROM unnest(pg_blocking_pids(waiting.pid)) AS blocker_pids(pid)
) AS blocked_by
LEFT JOIN pg_stat_activity AS blocker ON blocker.pid = blocked_by.pid
WHERE waiting.datname = current_database();
```

A row-update wait often appears as a transaction-ID lock, not as an obvious tuple in `pg_locks`. Joining nullable relation/page/tuple fields can miss it. `pg_blocking_pids` can return duplicate process IDs, so the query de-duplicates them. A prepared transaction is reported with process ID `0`; it has no `pg_stat_activity` row, so inspect `pg_prepared_xacts` when the blocker columns are null.
For a live backend, inspect its transaction age, application identity, and logs. Canceling a statement and terminating a session have different rollback effects; choose intervention for an identified operation and recovery plan.

## 6. Give advisory locks a bounded lifetime

An advisory lock protects an **application-defined key**, not a row automatically. Every participant must cooperate. Use a stable namespace and key; a hash collision can serialize unrelated resources.

```sql
BEGIN;
SELECT pg_try_advisory_xact_lock(42, 7) AS acquired;
-- Continue the protected operation only when acquired is true.
COMMIT;
```

The transaction-scoped lock releases at transaction end. A session-scoped `pg_advisory_lock()` can survive rollback and leak protection across pool borrowers if it is not explicitly unlocked. Do not mix the two lifetimes accidentally.

## Summary

A deadlock is a cycle, so fix acquisition order and inspect every participating resource path. Keep work short, bound waits, use the server's blocker graph, and treat `40P01` as a rollback of the whole operation. Advisory locks require a shared key protocol and an explicit lifetime.

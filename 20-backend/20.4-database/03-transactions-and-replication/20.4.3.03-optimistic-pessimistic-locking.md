# Optimistic & Pessimistic Locking

Two people open the same profile at version 1. One saves first; if the second save replaces the row without checking the version, it silently erases the first edit.

## Definition

**Optimistic concurrency control** validates that the facts used for a write are still current, commonly by including an expected version in its `UPDATE` predicate. **Pessimistic concurrency control** acquires a conflicting lock before making the protected decision and holds it until the transaction ends.

> **Textbook Definition:** Optimistic concurrency control validates that a write's assumptions remain valid before committing it; pessimistic control acquires protective locks before the critical decision. Both must define conflict handling and the scope of protected invariants.

The optimistic update still takes database write locks. Its distinction is that the application does not hold a protective lock throughout the earlier read or editing period.

## First Principles

The version must be checked as part of the write because a separate check has a race: another edit can commit between the check and mutation. An expected-version predicate makes compare-and-change one statement. A lock prevents another transaction from making the protected change while the decision is open. Both require every relevant writer to participate.

The choice depends on how long the decision lasts, its conflict rate, and whether a stale decision can be recomputed. A human editing a form cannot keep a database transaction open for minutes. A short inventory reservation often needs only one conditional update.

## Reject a stale replacement at the write

Create this independent fixture on PostgreSQL 16+:

```sql
CREATE TABLE editable_profiles (
  id integer PRIMARY KEY,
  display_name text NOT NULL,
  version bigint NOT NULL DEFAULT 1 CHECK (version > 0)
);
INSERT INTO editable_profiles (id, display_name) VALUES (1, 'Original');
SELECT id, display_name, version FROM editable_profiles WHERE id = 1;
```

Two clients both read version 1. The first writes:

```sql
UPDATE editable_profiles
SET display_name = 'First edit', version = version + 1
WHERE id = 1 AND version = 1
RETURNING id, display_name, version;
```

It returns version 2. Repeating the same expected-version predicate for the second edit returns **zero rows**. Validation occurs when this statement executes, not magically at commit. If it is part of a larger transaction, final success still requires that transaction to commit.

A zero-row result can also mean the row is missing or outside an authorized tenant filter. An API must distinguish allowed cases without leaking another tenant's data. For a stale form, return a conflict/precondition response and let the user reconcile; automatically retrying the same replacement with a new version defeats the protection.

Every writer must increment the version. Allowing a different path to update the name without changing the token makes stale clients appear current. A bigint avoids the small range of a 32-bit token, but still has a finite range.

## Hold a row lock for a short decision

Use the account fixture from [Transactions](20.4.3.01-transactions.md):

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
SELECT id, balance_cents FROM transfer_accounts
WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
-- Validate both results; make both updates before COMMIT.
COMMIT;
```

At Read Committed, a second locking reader waits and then obtains the newly committed row version. At Repeatable Read, an update after its snapshot can cause a serialization failure instead. An ordinary reader can still see a committed MVCC version while the lock is held.

All protected reads and writes must use the **same open transaction**. Committing the locking read releases its locks; performing writes later does not retain that protection. The canonical [Prisma transfer](../04-orm-and-access/20.4.4.02-prisma-advanced.md) keeps ordered locks, tenant checks, conditional debit, and credit together.

## Use a predicate when one statement can express the rule

```sql
CREATE TABLE reservation_stock (
  id integer PRIMARY KEY,
  stock integer NOT NULL CHECK (stock >= 0)
);
INSERT INTO reservation_stock VALUES (1, 10);

UPDATE reservation_stock
SET stock = stock - 1
WHERE id = 1 AND stock >= 1
RETURNING stock;
```

Concurrent reservations at Read Committed serialize their updates to this row and recheck `stock >= 1`. At most ten can succeed from this fixture. A preceding unlocked `SELECT stock` is unnecessary for the rule. Add order/outbox records in the **same transaction** if those must exist with the reservation.

Likewise, `SET counter = counter + 1` avoids overwriting a counter with a stale application-computed value. Row locks are not required before every arithmetic update. A rule spanning several rows still needs a protocol that protects the whole set.

## Claim queue work without waiting on another worker

```sql
CREATE TABLE claim_jobs (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'processing', 'done')),
  claimed_at timestamptz
);
INSERT INTO claim_jobs DEFAULT VALUES;
INSERT INTO claim_jobs DEFAULT VALUES;

BEGIN;
WITH candidate AS (
  SELECT id FROM claim_jobs
  WHERE status = 'pending'
  ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
)
UPDATE claim_jobs AS job
SET status = 'processing', claimed_at = clock_timestamp()
FROM candidate
WHERE job.id = candidate.id
RETURNING job.id;
COMMIT;
```

The selection and state transition belong to one transaction. A second worker can claim another unlocked job. After commit, process the returned job outside this short transaction. A crashed worker can leave it `processing`, so a production queue needs leases, attempt limits, recovery, and idempotent effects. Lease-based recovery also needs an ownership token to reject completion from an expired worker.

`SKIP LOCKED` does not guarantee fairness or strict FIFO ordering: an earlier locked job is skipped. An empty result does not prove the queue contains no pending work.

## Choose the mechanism for the actual decision

| Decision | Mechanism to consider | Boundary to keep visible |
| ---------------------------------- | --------------------------------------------- | ---------------------------------------------- |
| Save a user-edited document | Expected version / HTTP precondition | Let the user reconcile stale intent |
| Reserve from one stock row | Conditional atomic update | Check returned row/count |
| Transfer between two accounts | One transaction with ordered locks and checks | Preserve both changes and tenant authorization |
| Enforce an aggregate staffing rule | Shared guard lock or Serializable | Per-row versions do not protect an aggregate |
| Claim independent background jobs | Atomic claim with `SKIP LOCKED` | Recover worker crashes and duplicate effects |

Measure conflicts, lock wait time, retries, transaction age, and end-to-end latency. High contention can make optimistic recomputation expensive, but switching to locks does not remove serialization of a hot row. Sometimes redesigning the shared resource or limiting admission is the larger improvement.

## Summary

A version binds a write to a prior read; a held lock protects a short decision inside one transaction. Prefer one conditional statement when it fully expresses the invariant. Reconcile stale human intent, retry known aborted computational work as a whole, and never let a locking read escape its transaction boundary.

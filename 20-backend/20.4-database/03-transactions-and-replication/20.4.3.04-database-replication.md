# Database Replication Patterns

An order write commits on the primary, but the next request reads from a standby that has not replayed it yet. The order appears to vanish unless the application knows what “committed” and “caught up” mean.

## Definition

**Replication** propagates database changes to other nodes. The protocol determines when a copy receives, durably stores, and applies a committed change. Those are separate milestones: a replica can have the write-ahead log (WAL) needed for recovery while its queries still return older data.

> **Textbook Definition:** Database replication propagates changes from one database node to others according to a replication protocol. Receipt, durable storage and application are separate stages that determine recovery and read-consistency behavior.

## First Principles

A second machine cannot learn a write before a message reaches it. Acknowledging earlier leaves a loss or stale-read window; waiting for another machine adds latency and a dependency on its availability. Multiple writable copies also need a rule for conflicting changes and writer authority.

Copies improve availability only when recovery can select an eligible replacement and prevent the old writer from returning. They cannot undo a mistaken deletion that was faithfully propagated; recoverable backups need another retention boundary.

## 1. Follow a write from commit to visibility

```text
primary: execute → write WAL → flush WAL → acknowledge local commit
                                 │
standby:                        receive → write → flush → replay
                                                              │
                                                        query can see it
```

This trace shows a primary with the default local durable commit and an asynchronous standby. Configured synchronous replication adds a required standby acknowledgment; `synchronous_commit = off` can acknowledge before local WAL flush and does not wait for a standby.

Asynchronous replication does not wait for the standby milestones. On a healthy connection it may be quick; during an outage it can lag indefinitely. Read scaling adds capacity for eligible reads.
Ordinary single-primary PostgreSQL replication still executes application writes on one primary, and replication itself consumes resources.

## 2. Choose the unit being copied

| PostgreSQL mechanism | What follows the publisher | What you must manage |
| -------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Physical streaming | WAL for the cluster, replayed by a compatible standby | Base backup, retention, same-major compatibility, standby recovery |
| Built-in logical | Published table changes, decoded and applied to subscriber tables | Compatible schema, replica identity, privileges, conflicts, sequence state |

Physical replication reproduces database changes through recovery; describing two nodes as permanently “byte-identical” obscures replay lag and node-local configuration. A physical hot standby serves read-only queries while in recovery.

Logical replication can support selective copies and cross-major migrations when the versions and schemas are compatible. It does **not** automatically replicate data definition language (DDL) or sequence state. UPDATE/DELETE need suitable replica identity; TRUNCATE has publication and related-table restrictions.
Plan the final sequence synchronization before making a migration target writable.

A logical subscriber can accept local writes, but this is not a built-in multi-primary conflict-resolution protocol. Incoming changes may overwrite locally changed values; constraint/permission conflicts can stop application until resolved. “Last-write-wins” is not a general safe description of the system.

## 3. Specify what a synchronous acknowledgment proves

When synchronous standbys are configured, `synchronous_commit` controls the required milestone:

| Setting | Acknowledgment waits for |
| -------------- | ------------------------------------------------------------ |
| `local` | Local durable WAL; no standby acknowledgment |
| `remote_write` | Standby filesystem write, which may not survive its OS crash |
| `on` | Durable WAL on the configured synchronous standby set |
| `remote_apply` | That set also replays the commit, making it query-visible |
| `off` | Does not wait even for local durable WAL |

Without a configured synchronous set, the non-`off` settings reduce to local WAL synchronization. `synchronous_standby_names` can select priority-based or quorum acknowledgments; quorum configuration changes how many eligible acknowledgments are needed, not a third copying mechanism.

With durable synchronous acknowledgment, an acknowledged write can survive primary loss **if failover selects a copy that has that write** and the relevant storage survives. Promoting an arbitrary asynchronous standby breaks that guarantee. A required standby outage can stall commits unless the operational policy changes the requirement. `on` alone does not make every replica read current; `remote_apply` concerns the selected synchronous set, not arbitrary read endpoints.

## 4. Route a read according to its freshness requirement

For immediate read-your-writes, reading from the authoritative primary is the simplest route. A fixed 200-ms pin is only a heuristic: lag can exceed the timer, and a process-local map cannot preserve session state across all application instances.

A more precise route uses a trusted WAL watermark:

1. Commit the write on the primary, then obtain a WAL position from that primary in the same known timeline. A position sampled afterward is conservative: it can include unrelated later writes.
2. Carry the position through trusted session state along with its primary/timeline identity.
3. On the chosen standby, check whether replay has reached that position. Bound the wait and fall back to a suitable primary if it has not.
4. Start the business read with a fresh snapshot **after** the successful check. An existing Repeatable Read snapshot stays old even if replay later catches up.

```sql
-- Primary, after the write transaction commits:
SELECT pg_current_wal_lsn()::text AS watermark;

-- Standby: bind $1 to the trusted watermark using the driver.
SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn AS ready;
```

This is a protocol outline, not a standalone routing function: failover invalidates assumptions about node identity and history, and a null replay position is not success. Do not accept an arbitrary public-client position that can force unbounded waiting. Monotonic reads also require remembering the highest observed position, not just the last write.

PgBouncer can expose separately configured primary and replica aliases. Choosing those aliases belongs to the application/router; setting `search_path` does not select a different server or route queries by whether they read or write.

## 5. Prepare replication before running the backup command

For physical replication, configure WAL senders, authenticated/TLS replication access, retention or slots, and a dedicated replication role. Some server settings require restart; `ALTER SYSTEM` alone does not activate them. Provision an empty standby data directory and a protected credential source such as a permission-restricted password file.

```bash
# Preparation example; run on the standby host with its paths/credentials set.
pg_basebackup -h primary.example -U replicator \
  -D /srv/postgresql/standby -R -X stream -P
```

`-R` writes standby configuration, including `standby.signal`; it does not start the server. A replication slot helps retain required WAL, but a stalled consumer can fill the primary's disk. Monitor retention and recovery paths.
A standalone `wal_keep_size` budget cannot promise that a disconnected replica will always catch up.

For logical replication, prepare the target schema, publication, authenticated subscription connection, and required privileges. Treat connection strings as secrets, coordinate DDL explicitly, and rehearse initial synchronization and the final cutover.

## 6. Fail over through writer authority

A tested runbook must:

1. Detect failure while distinguishing a failed node from a network partition.
2. Fence the old primary from writes, through infrastructure or a proven authority/lease protocol.
3. Select a standby whose replay/durable position meets the recovery-point objective.
4. Promote it, redirect/reconnect clients, and resolve uncertain in-flight writes through operation identity.
5. Rewind or rebuild the former primary as a follower before permitting it to rejoin.

`pg_promote()` changes recovery state; it does not perform the entire runbook. Patroni and similar high-availability (HA) systems coordinate these responsibilities, but their failure behavior depends on the deployment configuration. Neither an automatic 30-second recovery nor lossless failover follows from installing a tool.
Test partitions, stale replicas, missing quorum, and the old primary's return.

## 7. Monitor where propagation stopped

```sql
-- Primary; permissions determine visibility of session details.
SELECT application_name, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_gap_bytes,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
```

The primary-to-replay gap includes WAL not yet sent. A sent-to-replay gap measures a narrower interval. Treat a NULL replay position as unavailable evidence, not a healthy zero gap.
Lag times describe recent observed acknowledgment delays; they are not a universal estimate of time to catch up and can become null when idle. Alert on missing replicas, retained WAL, byte backlog trends, apply failures, and freshness objectives for the actual read workload.

Choose replicas from measured read pressure and availability/recovery objectives. A client or customer count alone cannot establish an appropriate topology. Long analytical queries can also conflict with standby recovery; configure and measure that tradeoff.

## Summary

Choose the copied unit, commit acknowledgment milestone, and freshness requirement separately. Protect writer authority during failover, route sensitive reads by a valid replay boundary, and monitor both apply progress and retained WAL. Preserve independent backups and rehearse recovery against explicit data-loss and downtime objectives.

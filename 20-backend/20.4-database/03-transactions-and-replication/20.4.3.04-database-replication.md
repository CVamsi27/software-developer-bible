# Database Replication Patterns

> **Streaming replication, logical replication, read replicas, and failover strategies for PostgreSQL.**

---

## Why Replication Matters

Replication solves three problems: **read scaling** (serve more queries), **high availability** (survive node failure), and **disaster recovery** (survive data center failure). For Docita, read replicas handle dashboard queries while the primary handles writes — preventing complex report queries from blocking appointment creation.

```
                    ┌─────────────────┐
                    │ App Servers │
                    │ (NestJS APIs) │
                    └────────┬────────┘
                             │
                    ┌────────┴────────┐
                    │ PgBouncer │
                    └────────┬────────┘
                             │
                    ┌────────┴────────┐
                    │ Primary │ ← Writes (appointments, prescriptions)
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │ │ │
     ┌────────┴───────┐ ┌───┴────────┐ ┌───┴────────┐
     │ Read Replica 1 │ │Replica 2 │ │ Replica 3 │ ← Reads (dashboards, reports)
     │ (Dashboard) │ │(Analytics) │ │(Search) │
     └────────────────┘ └────────────┘ └────────────┘
```

## Streaming Replication (Physical)

Streaming replication copies the entire database cluster at the byte level. The primary sends WAL (Write-Ahead Log) segments to replicas, which replay them to maintain an exact copy.

### How It Works

```
Primary Replica
  │ │
  ├── Write to table ──→ WAL ──────┤
  │ ├── Replay WAL
  │ ├── Maintain copy
  │ │
  ├── SELECT (write path) ├── SELECT (read path)
  │ │
  └── Return result └── Return result
```

### Setup

```sql
-- On PRIMARY: enable replication
ALTER SYSTEM SET wal_level = 'replica';
ALTER SYSTEM SET max_wal_senders = 3;
ALTER SYSTEM SET wal_keep_size = '1GB';

-- Create replication user
CREATE USER replicator WITH REPLICATION ENCRYPTED PASSWORD 'secure_password';

-- In pg_hba.conf:
-- host replication replicator replica_ip/32 md5

-- On REPLICA: base backup and start streaming
pg_basebackup -h primary_host -D /var/lib/postgresql/data -U replicator -P

-- Create standby.signal file
touch /var/lib/postgresql/data/standby.signal

-- In postgresql.conf on replica:
-- primary_conninfo = 'host=primary_host port=5432 user=replicator password=xxx'
```

### Key Characteristics

| Property             | Value                                          |
| ----------             | -------                                          |
| **Consistency**      | Eventually consistent (lag depends on network) |
| **Write capability** | Read-only replicas                             |
| **Lag measurement**  | `pg_stat_replication`                          |
| **Failover**         | Manual or with Patroni/pg_auto_failover        |
| **Use case**         | HA, read scaling, backup                       |

## Logical Replication

Logical replication copies data at the table level using a publish/subscribe model. Unlike streaming, it allows selective replication, schema changes, and even replicating between different PostgreSQL major versions.

### How It Works

```
Primary (Publisher) Replica (Subscriber)
  │ │
  ├── Table A ──→ Logical Decode ──┤── Apply changes
  ├── Table B ──→ Logical Decode ──┤── Apply changes
  │ │
  ├── DDL changes (filtered) ├── DDL not replicated (manual)
  │ │
  └── INSERT/UPDATE/DELETE └── Apply only published tables
```

### Setup

```sql
-- On PRIMARY (Publisher):
-- Enable logical replication
ALTER SYSTEM SET wal_level = 'logical';

-- Create publication for specific tables
CREATE PUBLICATION clinic_data FOR TABLE
  patients, appointments, prescriptions;

-- On REPLICA (Subscriber):
-- Create subscription
CREATE SUBSCRIPTION clinic_primary
  CONNECTION 'host=primary_host dbname=mydb user=replicator password=xxx'
  PUBLICATION clinic_data;

-- Check replication status
SELECT * FROM pg_stat_subscription;
SELECT * FROM pg_replication_slots;
```

### Logical vs Streaming Comparison

| Feature                 | Streaming                | Logical                        |
| ---------                 | -----------                | ---------                        |
| **Granularity**         | Entire cluster           | Table-level                    |
| **Schema changes**      | Replicated automatically | Not replicated                 |
| **DML only**            | No (copies everything)   | Yes (INSERT/UPDATE/DELETE)     |
| **Cross-version**       | No (same major version)  | Yes                            |
| **Selective tables**    | No                       | Yes                            |
| **Conflict resolution** | N/A (single writer)      | Last-write-wins                |
| **Use case**            | HA, backup               | Partial replication, migration |

## Read Replica Patterns

### Pattern 1: Application-Level Routing

```typescript
// Prisma with read replicas
const prismaPrimary = new PrismaClient({
  datasources: {
    db: { url: "postgresql://primary:5432/mydb" },
  },
});

const prismaReplica = new PrismaClient({
  datasources: {
    db: { url: "postgresql://replica:5432/mydb" },
  },
});

// Route reads to replica, writes to primary
async function getAppointments(clinicId: string) {
  // Read from replica (eventually consistent, but fast)
  return prismaReplica.appointment.findMany({
    where: { clinicId },
  });
}

async function createAppointment(data: CreateAppointmentInput) {
  // Write to primary (consistent, slightly slower)
  return prismaPrimary.appointment.create({ data });
}
```

### Pattern 2: Read-Your-Writes Consistency

Problem: User creates an appointment, then immediately sees a list that doesn't include it (replica lag).

```typescript
// Solution: Track last write timestamp, use primary if read is within lag window
class ReplicaRouter {
  private lastWriteTimestamp: Map<string, Date> = new Map();

  async write(clinicId: string, operation: () => Promise<any>) {
    const result = await operation();
    this.lastWriteTimestamp.set(clinicId, new Date());
    return result;
  }

  async read(clinicId: string, operation: () => Promise<any>) {
    const lastWrite = this.lastWriteTimestamp.get(clinicId);
    const REPLICATION_LAG_THRESHOLD = 200; // ms

    if (lastWrite && Date.now() - lastWrite.getTime() < REPLICATION_LAG_THRESHOLD) {
      // Read from primary (write-your-writes consistency)
      return prismaPrimary.appointment.findMany({
        where: { clinicId },
      });
    }

    // Safe to read from replica
    return prismaReplica.appointment.findMany({
      where: { clinicId },
    });
  }
}
```

### Pattern 3: Connection Routing with PgBouncer

```ini
[databases]
mydb_primary = host=primary port=5432 dbname=mydb
mydb_replica = host=replica port=5432 dbname=mydb

[pgbouncer]
pool_mode = transaction

# Route reads to replica, writes to primary
# Application sets search_path or uses different connection strings
```

## Failover Strategies

### Manual Failover

```sql
-- 1. Stop writes to primary
-- 2. Promote replica
SELECT pg_promote();

-- 3. Update connection strings in app
-- 4. Former primary becomes new replica after re-sync
```

### Automated Failover with Patroni

Patroni uses distributed consensus (etcd/Consul/ZooKeeper) to manage PostgreSQL HA.

```
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ etcd 1 │ │ etcd 2 │ │ etcd 3 │
└──────┬──────┘ └──────┬──────┘ └──────┬──────┘
       │ │ │
       └───────────────────┼───────────────────┘
                           │
              ┌────────────┴────────────┐
              │ Patroni Cluster │
              │ │
              │ Primary ──→ Replica 1 │
              │ Replica 2 │
              └─────────────────────────┘
```

```yaml
# patroni.yml
scope: docita-cluster
namespace: /db/
name: node-1

etcd3:
  hosts: etcd1:2379,etcd2:2379,etcd3:2379

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    postgresql:
      use_pg_rewind: true
      parameters:
        max_connections: 200
        shared_buffers: 256MB
        wal_level: replica
        max_wal_senders: 3
        max_replication_slots: 3
```

## Monitoring Replication Lag

```sql
-- Check replication lag (in bytes and time)
SELECT
  client_addr,
  state,
  sent_lsn,
  write_lsn,
  flush_lsn,
  replay_lsn,
  pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_lag_bytes,
  replay_lag
FROM pg_stat_replication;

-- Alert if lag > 1MB or > 10 seconds
SELECT
  client_addr,
  pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS lag
FROM pg_stat_replication
WHERE pg_wal_lsn_diff(sent_lsn, replay_lsn) > 1048576; -- 1MB
```

## Docita Recommendation

| Scale              | Strategy                                                    |
| -------              | ----------                                                    |
| **25 clinics**     | Single primary, no replicas (monitor with pg_stat_activity) |
| **50-100 clinics** | Add 1 read replica for dashboards/reports                   |
| **100+ clinics**   | 1 primary + 2 replicas (1 for reads, 1 for DR) + PgBouncer  |
| **500+ clinics**   | Consider read replicas per region + connection routing      |

## Interview Questions

**Q: "When would you choose logical replication over streaming?"**

> Logical replication when you need: (1) selective table replication — only replicate sensitive tables, (2) cross-version migration — replicate from PostgreSQL 14 to 16, (3) partial replication — only replicate patient data, not audit logs, (4) schema flexibility — primary changes schema without breaking replica. Streaming when you need: (1) exact byte-level copy for HA, (2) PITR from replica, (3) zero configuration overhead.

**Q: "How do you handle read-your-writes consistency with replicas?"**

> Track the timestamp of each write operation. When reading, check if the read is within the replication lag threshold (typically 100-200ms). If yes, read from the primary. If no, read from the replica. Alternative: use synchronous replication for critical reads (adds latency to writes). For Docita, appointment creation routes to primary, dashboard queries route to replica with 200ms consistency window.

**Q: "What happens during a primary failure with streaming replication?"**

> Without automated failover: the cluster is down until manual intervention. With Patroni: the distributed consensus system detects the failure (within TTL, typically 30s), promotes the most up-to-date replica, and updates DNS/service discovery. The former primary rejoins as a replica after re-syncing. During the failover window (30-60s), writes are unavailable but reads continue on replicas.

## 30-Second Interview Version

> Database replication in PostgreSQL has two flavors: streaming (byte-level, entire cluster, HA) and logical (table-level, publish/subscribe, selective). For read scaling, use read replicas with application-level routing — writes to primary, reads to replica. Handle read-your-writes by tracking write timestamps and routing to primary within the lag window. Use Patroni for automated failover with etcd consensus. Monitor lag via pg_stat_replication. For Docita: add 1 read replica at 50 clinics, 2 at 100+ clinics.

# Prisma ORM

## Definition

Prisma supplies a schema/model contract, client tooling and database access APIs. An ORM call translates application values into database operations; it does not replace the database's constraints, query planner or concurrency rules.

> **Textbook Definition:** Prisma is a database toolkit that derives typed application access from a declared model and coordinates schema migrations. Its client operations execute under the database's constraint, transaction and concurrency rules.

## First Principles

1. **Application objects and database rows have different contracts.** Generated types catch many mismatched queries, while the database enforces constraints against all writers. Neither validates an untrusted HTTP body automatically.
2. **A change has two consumers.** The database needs reviewed DDL; the application needs a client generated for the compatible schema/API. Generating the client does not apply the migration.
3. **The database executes the final operation.** Indexes, joins, locks and isolation still determine cost and correctness. Inspect emitted SQL and test concurrent behavior instead of inferring it from an API name.
4. **An API example needs a version.** A valid client call in one major version may not exist in another. Pin CLI/client together and follow documentation for that major.

## Choose the version contract before copying code

The executable examples in this chapter and [Prisma Advanced](20.4.4.02-prisma-advanced.md) use **Prisma CLI and Client 6.19.0 with PostgreSQL**, the `prisma-client-js` generator and its Rust-engine connection pool. They teach the widely deployed legacy API deliberately; this is not a claim that version 6 is the latest release or the right choice for a new project. Prisma's release-status page says v6 receives security patches only through 19 November 2026.

As of 11 October 2026, the official [release-status page](https://www.prisma.io/docs/orm/release-status) still labels **Prisma ORM 8 a release candidate**, and the [release list](https://github.com/prisma/orm/releases) shows v7.10.0 as the latest stable release. The v8 RC documentation describes a different contract/runtime and `db.orm`, `db.sql` and `db.transaction(callback)` APIs, with different transaction options and database support. Recheck the release status and supported-database matrix before adopting it. Prisma ORM 7 changed client configuration and made the `prisma-client` generator the default; that generator became generally available in v6.16. Use the [major-version migration guide](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7) when upgrading; do not mix a v6 schema/client constructor with v8 calls.

```text
v6 schema.prisma ──generate──→ PrismaClient types/query API
       │                              │
       └─migration SQL──→ PostgreSQL ←┘
                           planner + locks + constraints
```

For v6, the client hands work to its query engine and pool. Driver-adapter/engine choices in other versions change who owns that pool. Database portability is limited by the provider's actual features: PostgreSQL arrays, UUID types or locking SQL do not become portable merely because CRUD uses an ORM.

## Generate one client from a complete schema

Use this small schema for the chapter examples. Related models and indexed fields are defined explicitly; no preview features or PostgreSQL extensions are needed for client-generated `uuid()` IDs.

```prisma
// schema.prisma — Prisma 6.19.0, PostgreSQL
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id        String   @id @default(uuid()) @db.Uuid
  email     String   @unique
  name      String?
  posts     Post[]
  profile   Profile?
  createdAt DateTime @default(now()) @map("created_at")
  @@map("users")
}

model Post {
  id        String   @id @default(uuid()) @db.Uuid
  title     String
  content   String?  @db.Text
  published Boolean  @default(false)
  authorId  String   @db.Uuid @map("author_id")
  author    User     @relation(fields: [authorId], references: [id])
  tags      String[] @default([])
  metadata  Json     @default("{}")
  createdAt DateTime @default(now()) @map("created_at")
  @@index([authorId])
  @@index([published, createdAt, id])
  @@map("posts")
}

model Profile {
  id     String  @id @default(uuid()) @db.Uuid
  bio    String? @db.Text
  userId String  @unique @db.Uuid @map("user_id")
  user   User    @relation(fields: [userId], references: [id])
  @@map("profiles")
}

model Account {
  id           String @id @default(uuid()) @db.Uuid
  tenantId     String @map("tenant_id")
  balanceCents BigInt @default(0) @map("balance_cents")
  version      Int    @default(0)
  @@index([tenantId])
  @@map("accounts")
}

model Product {
  id       String @id @default(uuid()) @db.Uuid
  tenantId String @map("tenant_id")
  stock    Int    @default(0)
  @@index([tenantId])
  @@map("products")
}

model OutboxEvent {
  id          String   @id @default(uuid()) @db.Uuid
  aggregateId String   @map("aggregate_id")
  kind        String
  payload     Json
  createdAt   DateTime @default(now()) @map("created_at")
  @@map("outbox_events")
}
```

The index on a foreign-key field is a workload decision, not automatically created by PostgreSQL's foreign key. `uuid()` is a Prisma-side default; raw database writers must provide an ID or use an explicit database default. A Prisma JSON type does not establish the business schema of arbitrary JSON values.

For an isolated learning database:

```bash
npm install --save-exact @prisma/client@6.19.0
npm install --save-dev --save-exact prisma@6.19.0
npx prisma validate
npx prisma migrate dev --name initial --create-only
# Review/edit the generated migration SQL, then apply in development:
npx prisma migrate dev
npx prisma generate
```

Add database invariants to the reviewed migration:

```sql
ALTER TABLE accounts ADD CONSTRAINT accounts_nonnegative CHECK (balance_cents >= 0);
ALTER TABLE products ADD CONSTRAINT products_nonnegative CHECK (stock >= 0);
```

For deployment, use `migrate deploy` on reviewed migration history. It does not generate your client or perform the development shadow-database workflow. `db push` changes the database without creating migration history; keep it for deliberate prototyping. Studio is a data browser that needs appropriate access, not a production authorization layer.

## Shape one write and its returned fields

Create `client.ts` once per long-running application process and close the client during the owned shutdown lifecycle, rather than connecting/disconnecting after each request:

```typescript
// client.ts — v6 client/engine contract
import { PrismaClient } from '@prisma/client';
export const prisma = new PrismaClient();
```

A nested write groups related records atomically; `select` chooses the returned projection:

```typescript
import { prisma } from './client';

export async function createAuthor(email: string, name: string) {
  return prisma.user.create({
    data: {
      email, name,
      profile: { create: { bio: 'New author' } },
      posts: { create: [{ title: 'First draft' }] },
    },
    select: { id: true, email: true, posts: { select: { id: true, title: true } } },
  });
}
```

Validate request input before calling this function. A pre-check for duplicate email cannot replace the unique constraint under concurrency; handle the resulting v6 `P2002` conflict deliberately. `update`/`delete` can fail when the record is absent, and deleting this author's related records needs an explicit referential-action or transaction policy. `upsert` can express create-or-update, but its concurrency behavior depends on whether the operation can become a database-native upsert; test conflicts.

## Page a relation with deterministic ordering

```typescript
import { prisma } from './client';

export async function publishedPage(afterId?: string, size = 20) {
  if (!Number.isSafeInteger(size) || size < 1 || size > 100) {
    throw new RangeError('Invalid page size');
  }
  return prisma.post.findMany({
    where: { published: true },
    orderBy: [{ createdAt: 'asc' }, { id: 'asc' }],
    ...(afterId ? { cursor: { id: afterId }, skip: 1 } : {}),
    take: size,
    select: { id: true, title: true, createdAt: true, author: { select: { name: true } } },
  });
}
```

The ID cursor is unique, while the timestamp-plus-ID order breaks ties. `skip: 1` excludes the cursor row. Define what a deleted/missing cursor and concurrent inserts mean for the API; cursor pagination alone does not give a snapshot across requests. Offset pagination remains useful for small bounded pages, but large offsets need more work.

An `include` relation does not itself imply N+1 or a single SQL statement. The v6 relation strategy/configuration may use joins or additional batched queries. The automatic dataloader batches certain `findUnique` calls, not arbitrary `findMany` calls. Inspect query count, selected fields and relation cardinality. Avoid loading every child simply to count or aggregate it.

## Keep raw SQL parameterized and results honest

```typescript
import { prisma } from './client';

export async function authorPostCounts(email: string) {
  return prisma.$queryRaw<Array<{ id: string; post_count: bigint }>>`
    SELECT u.id, COUNT(p.id) AS post_count
    FROM users AS u LEFT JOIN posts AS p ON p.author_id = u.id
    WHERE u.email = ${email}
    GROUP BY u.id
  `;
}
```

Tagged-template values are parameters here; table/column identifiers cannot be replaced with value parameters. Keep identifiers static or allowlisted. `$queryRaw<T>` describes the expected result to TypeScript; it does not validate returned rows. PostgreSQL `COUNT` is a bigint, and native JavaScript `JSON.stringify` needs an explicit conversion policy for bigint values.

Unsafe raw APIs can still bind separate value parameters, but building SQL by string concatenation is dangerous. Interpolating `Prisma.raw(untrustedText)` into an otherwise tagged template also defeats the protection. For important row contracts, validate results or test them against the real schema.

## Move read-modify-write logic to its database boundary

A transaction makes its writes commit/rollback together; it does not automatically make a preceding application read safe from another transaction. Two transfers can both observe enough funds before either decrements. Use an atomic condition or appropriate locks/isolation, and let constraints reject invalid state. The complete [transfer/stock examples](20.4.4.02-prisma-advanced.md) show the boundary rather than duplicating an unsafe check-then-decrement here.

For independent v6 client operations, `$transaction([...])` executes them in sequence atomically. Dependent ID creation is usually a nested write or interactive callback. Inside the callback use `tx` for every participating query; calls on the root client use another transaction/connection. Network calls and external effects are outside database rollback, so record an outbox event in the transaction instead.

## Account for pool ownership and query cost

For this v6 Rust-engine example, URL `connection_limit` and `pool_timeout` configure its pool. These are not universal Prisma 7/8 driver-adapter settings. Total connection pressure includes every app/worker process, replica and separately created client. Review [connection pooling](../05-operations-and-scaling/20.4.5.01-connection-pooling.md) with the chosen runtime/adapter.

Use query logs in a controlled environment to inspect SQL and duration without leaking sensitive parameter values. Measure pool acquisition, database work and result shaping separately. Type-safe CRUD does not automatically create an appropriate index or choose a good execution plan.

## Summary

Pin the Prisma contract, generate the matching client and review migrations independently. Construct bounded projections and relations, parameterize raw values and test result shapes. Transactions group database effects, while constraints, conditional writes and isolation protect concurrent invariants; the ORM's types do not establish authorization or replace those mechanisms.

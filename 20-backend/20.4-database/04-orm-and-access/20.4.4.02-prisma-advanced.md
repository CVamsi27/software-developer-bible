# Prisma Advanced — Concurrent Writes, Raw SQL and Tenant Context

Two checkout requests both see one unit in stock. A transaction groups each request's writes, but correctness still depends on making the reservation decision against the current database row.

## Definition

Advanced ORM work makes the database boundary explicit: which rows a transaction owns, which condition makes a mutation valid, which connection carries tenant context and which effects survive a retry. This chapter uses the complete schema and **Prisma 7.10.0/PostgreSQL contract** from [Prisma fundamentals](20.4.4.01-prisma.md); do not mix its client with the still-changing Prisma ORM 8 release-candidate APIs.

> **Textbook Definition:** Advanced ORM usage coordinates transaction boundaries, conditional writes and connection-scoped state with application invariants. Typed client operations do not independently establish atomicity across external effects or correctness under concurrent retries.

## First Principles

1. **An application observation can become stale before its write.** Put the decision into an atomic database condition, lock the relevant state, or select isolation that detects the conflict.
2. **Database rollback covers database work in that transaction.** An email, HTTP charge or root-client query outside its connection is not undone when the callback throws.
3. **A pooled connection outlives a request.** Tenant settings must be scoped to the participating transaction so the next borrower does not inherit them.
4. **A retry repeats the whole operation.** Reuse business identity, bound attempts and ensure repeated external effects are either avoided or explicitly deduplicated.

## How It Works


### 1. Trace two transfers before choosing the lock

With a balance of 100 cents, two callbacks can both read 100 and each decide that a 70-cent debit is allowed. Merely putting each callback in a transaction does not prevent that read/check race at Read Committed.

```text
unsafe: A reads100 ─ B reads100 ─ A debits70 ─ B debits70
safe:   A locks rows ─ B waits ─ A checks/debits/credits/commits
                                      └─ B sees current balance and rejects
```

Locking both participating accounts in ID order also reduces opposite-direction transfer deadlocks. A conditional debit and nonnegative database constraint protect the invariant even if some future writer omits the application pre-check.

```typescript
import { prisma } from './client';

export async function transferCents(
  tenantId: string, fromId: string, toId: string, amount: bigint,
) {
  if (typeof amount !== 'bigint' || amount <= 0n || amount > 9_223_372_036_854_775_807n) {
    throw new RangeError('Invalid transfer amount');
  }
  if (!tenantId || fromId === toId) throw new TypeError('Invalid transfer');
  return prisma.$transaction(async tx => {
    const locked = await tx.$queryRaw<Array<{ id: string }>>`
      SELECT id FROM accounts
      WHERE tenant_id = ${tenantId}
        AND id IN (${fromId}::uuid, ${toId}::uuid)
      ORDER BY id FOR UPDATE
    `;
    if (locked.length !== 2) throw new Error('Account unavailable');
    const debit = await tx.account.updateMany({
      where: { id: fromId, tenantId, balanceCents: { gte: amount } },
      data: { balanceCents: { decrement: amount }, version: { increment: 1 } },
    });
    if (debit.count !== 1) throw new Error('Insufficient funds');
    await tx.account.update({
      where: { id: toId, tenantId },
      data: { balanceCents: { increment: amount }, version: { increment: 1 } },
    });
    return tx.account.findMany({
      where: { id: { in: [fromId, toId] }, tenantId },
      orderBy: { id: 'asc' },
      select: { id: true, balanceCents: true },
    });
  }, { maxWait: 2000, timeout: 5000 });
}
```

Tenant identity comes from verified server context; application authorization must also establish permission to transfer between these accounts. Validate ID syntax before querying if the API needs a controlled validation response. This is a concurrency illustration, not a complete financial ledger: durable operation IDs, ledger entries, provider integration and reconciliation need their own design.
BigInt cents avoid floating-point money arithmetic; the database rejects a destination overflow and rolls back the debit.

### 2. Reserve stock through one predicate, then append the event

A stock read followed by an unconditional decrement can oversell. This operation atomically checks current stock and records the event in the same database transaction:

```typescript
import { prisma } from './client';

export async function reserveStock(
  tenantId: string, productId: string, quantity: number, operationId: string,
) {
  if (!tenantId || !Number.isSafeInteger(quantity) || quantity < 1 || quantity > 10000) {
    throw new RangeError('Invalid reservation');
  }
  return prisma.$transaction(async tx => {
    const result = await tx.product.updateMany({
      where: { id: productId, tenantId, stock: { gte: quantity } },
      data: { stock: { decrement: quantity } },
    });
    if (result.count !== 1) throw new Error('Stock unavailable');
    return tx.outboxEvent.create({
      data: {
        id: operationId,
        tenantId,
        aggregateId: productId,
        eventType: 'STOCK_RESERVED',
        payload: { tenantId, productId, quantity },
      },
    });
  });
}
```

The caller supplies a stable validated operation ID for one intended reservation. A duplicate event-ID constraint failure rolls back its stock decrement. To return the original result on retries, retrieve the recorded operation and compare its owner and parameters; do not treat every `P2002` as permission to return someone else's outcome.
The outbox publisher can still deliver twice after a crash, so consumers need durable deduplication.

For multi-product orders, merge duplicate product IDs and validate all quantities before writes, acquire/update in a consistent order, derive prices from server-owned product data and keep the order/items/reservations in the same transaction. A network payment request does not become atomic by putting it in the callback.

### 3. Share a transaction with helpers; do not invent nesting

The transaction client intentionally omits `$transaction`. Calling `tx.$transaction(...)` does not create a supported nested savepoint. Calling the root `prisma.$transaction` within a callback opens another transaction, whose commit the outer callback cannot roll back.

```typescript
import { Prisma } from './generated/prisma/client';

export async function accountBalance(tx: Prisma.TransactionClient, id: string, tenantId: string) {
  return tx.account.findFirst({
    where: { id, tenantId },
    select: { balanceCents: true },
  });
}
```

Pass `tx` explicitly through participating helpers. Database savepoints are a SQL mechanism; use carefully controlled SQL and tested error recovery only if the application really needs them. A caught database error may leave PostgreSQL's transaction aborted until rollback/savepoint recovery, so "catch and continue" is not automatically valid.

`maxWait` is time acquiring an interactive transaction; `timeout` limits that transaction's callback lifetime. `isolationLevel` changes the database isolation contract. These options do not cancel an external HTTP side effect or make `Promise.all` queries execute in parallel on the single transaction connection. Prisma ORM 8 is a separate release-candidate contract; consult its current [transaction reference](https://www.prisma.io/docs/orm/v8/reference/transactions-and-runtime) and [release status](https://www.prisma.io/docs/orm/release-status) before evaluating an upgrade.

### 4. Make a conflict retry narrow and bounded

For this pinned v7 client, known transaction conflict/deadlock failures use `P2034`. Retry the whole transaction with bounded jitter; do not retry every error or an uncertain network commit as if it definitely rolled back.

```typescript
import { Prisma } from './generated/prisma/client';
import { setTimeout as wait } from 'node:timers/promises';

export async function retryConflict<T>(run: () => Promise<T>, attempts = 3): Promise<T> {
  if (!Number.isSafeInteger(attempts) || attempts < 1 || attempts > 5) {
    throw new RangeError('Invalid retry count');
  }
  for (let attempt = 1; ; attempt++) {
    try { return await run(); }
    catch (error) {
      if (!(error instanceof Prisma.PrismaClientKnownRequestError) ||
          error.code !== 'P2034' || attempt === attempts) throw error;
      await wait(Math.floor(Math.random() * 25 * 2 ** (attempt - 1)));
    }
  }
}
```

`run` must create a fresh transaction on every attempt; do not reuse a failed transaction client. Random jitter here is scheduling, not a security token. Add an overall request deadline and cancellation policy in the caller.
Retry classification is version-specific; do not carry the v7 `P2034` assumption into Prisma ORM 8 without checking its current contract.

### 5. Carry tenant context on the same connection

AsyncLocalStorage carries context through application async execution; it does not add SQL predicates, constrain raw SQL or establish a trusted identity. Prisma 7 query extensions do not cover nested operations; a model-scoped hook also misses top-level raw calls, while `$allOperations` can hook those raw calls explicitly. None replaces authorization or RLS, and a root-client call still escapes the current transaction.
Prisma removed the old `$use` middleware API in v6.14; use supported extensions where appropriate, but test the whole access surface.

For PostgreSQL RLS, set transaction-local context with `set_config`, then use `tx` for the protected queries:

```typescript
import { prisma } from './client';

export async function tenantAccounts(tenantId: string) {
  if (!tenantId) throw new TypeError('Verified tenant required');
  return prisma.$transaction(async tx => {
    await tx.$queryRaw`SELECT set_config('app.current_tenant', ${tenantId}, true)`;
    return tx.account.findMany({
      where: { tenantId },
      select: { id: true, balanceCents: true },
    });
  });
}
```

A parameterized `SET app.current_tenant = ${tenantId}` is not the correct value-binding form. `set_config(..., true)` lasts only for the current transaction; root-client queries would use a different connection/context.

The policy must already exist and the application role must not bypass it. A conceptual migration for this chapter's account table is:

```sql
ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;
CREATE POLICY accounts_tenant ON accounts
  USING (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid);
```

Ordinary owners bypass RLS unless forced; superusers and BYPASSRLS roles bypass it regardless of a normal application expectation. Use a least-privilege runtime role and test reads/writes with that exact role. RLS trusts the chosen setting; an attacker able to issue arbitrary SQL under the same role can change it, so context assignment still needs an application trust boundary.
See [Row-Level Security](../01-postgresql-foundations/20.4.1.06-row-level-security.md).

### 6. Choose soft delete, audit and versions as mechanisms

- A `deletedAt` field does not automatically filter ORM reads, relations, aggregates or raw SQL. Define unique-key reuse/restoration and database retention separately; see [soft delete](../05-operations-and-scaling/20.4.5.03-soft-delete-and-tombstones.md).
- An audit row must have an explicit actor/tenant/event identity and redacted payload. To require it for a business write, append it in the same transaction; immutable retention depends on privileges and storage policy.
- A version field protects optimistic writes only when the update compares the expected version and increments it atomically. On zero rows, distinguish stale state or an unavailable resource according to the API policy; see [locking](../03-transactions-and-replication/20.4.3.03-optimistic-pessimistic-locking.md).

A field or index name alone establishes none of these guarantees. Use the complete model in the fundamentals chapter or add every referenced field/relation before generating the client.

### 7. Verify the failure trace, not only the happy path

Use a disposable database and generated client to check competing reservations, rollback after an outbox failure, opposite-direction transfers and missing/cross-tenant accounts. Inspect emitted SQL and pool behavior under representative concurrency.

An "overlap test" that throws before any mutation proves rejection but not rollback of a prior write. Include a write followed by a forced failure and assert that no effects committed. Isolate database/schema state across parallel test workers; unscoped deleteMany cleanup can erase another test's fixtures.

## Summary

Put concurrent decisions in the database through predicates, ordered locks, isolation and constraints. Pass the transaction client through helpers, keep external effects out of the rollback claim and bind tenant context to the same transaction connection. Pin error/options APIs and verify competing operations plus deliberate failures against the real database.

# Prisma Advanced — Transactions, Raw Queries, Performance, Multi-Tenancy

> **TL;DR:** **Prisma is a schema-first ORM: `schema.prisma` generates a typed client that translates calls into SQL through a query engine — so the advanced work is controlling the SQL it emits.** Know where it leaks: `select`/`include` decide over-fetching, missing relation loads become N+1 (or need `relationJoins`), and anything subtle goes through `$queryRaw` with parameters. The rest is transactions (sequential vs interactive, and the isolation level you actually need), and multi-tenancy, where the tenant boundary must be enforced in every query path rather than trusted to callers.

---

## First Principles

Advanced ORM use is mostly about the gaps between the object model and the database's actual execution:

1. **Batching and connection behavior are the real performance levers.** Every query pays pool acquisition + round trip; the ORM's batching (Prisma's dataloader-style `findMany` coalescing) exists because the N+1 shape is the default failure of object navigation.
2. **Transactions don't cross the abstraction automatically.** Interactive transactions hold a pool connection for the callback's duration — long callbacks starve the pool (→ 20.4.5.01). The abstraction's convenience has a capacity cost that only shows at load.
3. **Raw escape hatches are part of the design, not a failure.** Recursive CTEs, window functions, locking clauses — when the generated API can't express it, `$queryRaw` keeps type-safety at the boundary while letting SQL be SQL.

---

## Definition

**Prisma** is a schema-first ORM: a single `schema.prisma` is the source of truth, from which Prisma generates a **typed client** that talks to a **query engine** which translates client calls into SQL. Its advanced surface is defined by the places where that abstraction leaks or costs:

```text
schema.prisma ──migrate──▶ SQL migrations (the source of truth for the DB)
              ──generate─▶ typed Client  ──▶ Query Engine ──▶ SQL
                              ^
   the leak points: explicit transactions, raw SQL, N+1 selection,
                    multi-tenancy filters, and connection/engine lifecycle
```

Four concerns define the advanced usage:

1. **Transactions and isolation** — `$transaction` comes in two forms: an array of operations (one atomic batch, no control flow) and an **interactive** callback (a real transaction with a timeout, for read-then-write logic). Concurrency-visible behavior (serialization failures, deadlocks, lock waits) belongs to the database, so retry-on-conflict is the caller's responsibility, not Prisma's.
2. **Avoiding N+1 by shaping the query** — the client's relational reads (`include`/`select`/nested writes) generate either a join or a batched second query; unbounded relations in a loop produce one query per row. The fixes are explicit `select` projections, `relationLoadStrategy: join` where appropriate, and cursor-based pagination instead of `skip/take` on large offsets.
3. **Raw SQL as an escape hatch, typed at the boundary** — `$queryRaw` with a tagged template (parameterised, injection-safe) for what the client cannot express (window functions, `FOR UPDATE SKIP LOCKED`, CTEs), plus `$queryRawUnsafe` which must never see user input.
4. **Multi-tenancy and connection lifecycle** — tenant scoping must be enforced in one place (a client extension/middleware that injects the tenant predicate) because a missing filter is a cross-tenant data leak; and the query engine's connection pool must be sized with the process count in mind, or serverless deployments exhaust the database.

The definitional skill this chapter teaches is knowing **where the abstraction ends** — Prisma is a typed query builder plus migrations, not a database; every performance or consistency property that matters is still the database's.

## Interactive Transactions

**What are interactive transactions?** Prisma's `$transaction` lets you run multiple queries in a single database transaction. All queries share the same connection and transaction context — if any query fails, all previous queries in the transaction are rolled back. This is critical for operations that must be atomic: booking an appointment AND creating a notification event must both succeed or both fail. Without transactions, you could book the appointment but fail to create the notification, leaving the system in an inconsistent state.


```typescript
// Prisma interactive transactions
const result = await prisma.$transaction(async (tx) => {
  // All queries share the same database connection
  // and transaction context

  // 1. Lock the patient row
  const patient = await tx.$queryRaw`
    SELECT * FROM patients
    WHERE id = ${patientId}
    FOR UPDATE
  `;

  // 2. Check for overlapping appointments
  const overlap = await tx.appointment.findFirst({
    where: {
      patientId,
      scheduledAt: { equals: appointmentTime },
      status: 'booked'
    }
  });

  if (overlap) {
    throw new ConflictException('Patient already has appointment at this time');
  }

  // 3. Create the appointment
  const appointment = await tx.appointment.create({
    data: {
      patientId,
      clinicianId,
      scheduledAt: appointmentTime,
      status: 'booked'
    }
  });

  // 4. Create outbox event
  await tx.outboxEvent.create({
    data: {
      eventType: 'APPOINTMENT_CREATED',
      payload: appointment,
      aggregateId: appointment.id
    }
  });

  return appointment;
});
```

## Transaction Options

```typescript
// Transaction with timeout
const result = await prisma.$transaction(
  async (tx) => {
    // Long-running transaction
    return await tx.appointment.updateMany({
      where: { clinicId },
      data: { status: 'cancelled' }
    });
  },
  {
    maxWait: 5000, // Max time to wait for transaction slot (ms)
    timeout: 30000 // Max time transaction can run (ms)
  }
);

// Nested transactions (savepoints)
const result = await prisma.$transaction(async (tx) => {
  // Outer transaction
  const outer = await tx.appointment.create({ data: outerData });

  // Inner transaction (savepoint)
  const inner = await tx.$transaction(async (innerTx) => {
    return await innerTx.appointment.create({ data: innerData });
  });

  return { outer, inner };
});
```

## Raw Queries

```typescript
// Raw query with parameters
const appointments = await prisma.$queryRaw`
  SELECT
    a.*,
    p.name as patient_name,
    c.name as clinician_name
  FROM appointments a
  JOIN patients p ON a.patient_id = p.id
  JOIN clinicians c ON a.clinician_id = c.id
  WHERE a.clinic_id = ${clinicId}
  AND a.scheduled_at >= ${startDate}
  AND a.scheduled_at <= ${endDate}
  ORDER BY a.scheduled_at ASC
`;

// Raw query with Prisma client
const result = await prisma.$executeRaw`
  UPDATE appointments
  SET status = 'cancelled'
  WHERE clinic_id = ${clinicId}
  AND scheduled_at < ${new Date()}
  AND status = 'booked'
`;

// Raw query with OUT parameter
const count = await prisma.$queryRaw`
  SELECT COUNT(*) as count
  FROM appointments
  WHERE clinic_id = ${clinicId}
`;
```

## Performance Optimization

```typescript
// 1. Use select to fetch only needed fields
const appointments = await prisma.appointment.findMany({
  where: { clinicId },
  select: {
    id: true,
    scheduledAt: true,
    status: true,
    patient: {
      select: { id: true, name: true }
    }
  }
});

// 2. Use cursor pagination for large datasets
const appointments = await prisma.appointment.findMany({
  where: { clinicId },
  take: 20,
  cursor: { id: lastId },
  orderBy: { id: 'asc' }
});

// 3. Use distinct for unique values
const clinicians = await prisma.appointment.findMany({
  where: { clinicId },
  distinct: ['clinicianId'],
  select: { clinicianId: true }
});

// 4. Use include sparingly (N+1 risk)
// Bad: includes everything
const bad = await prisma.clinic.findMany({
  include: {
    appointments: true,
    patients: true,
    clinicians: true
  }
});

// Good: specific includes with filtering
const good = await prisma.clinic.findMany({
  where: { id: clinicId },
  include: {
    appointments: {
      where: { status: 'booked' },
      take: 10,
      orderBy: { scheduledAt: 'desc' }
    }
  }
});
```

## Multi-Tenancy with Prisma

```typescript
// Tenant context using AsyncLocalStorage
import { AsyncLocalStorage } from 'async_hooks';

const tenantStorage = new AsyncLocalStorage<{ clinicId: string }>();

// Middleware to set tenant context
function tenantMiddleware(clinicId: string) {
  return async (params, next) => {
    // Add clinicId to all queries
    if (params.action === 'findMany' || params.action === 'findFirst') {
      params.args.where = {
        ...params.args.where,
        clinicId
      };
    }
    return next(params);
  };
}

// Usage in service
async function getAppointments(clinicId: string) {
  return tenantStorage.run({ clinicId }, async () => {
    return prisma.appointment.findMany({
      where: { clinicId } // Explicit is better than middleware
    });
  });
}

// RLS with Prisma
async function getAppointmentsWithRLS(clinicId: string) {
  return prisma.$transaction(async (tx) => {
    // Set RLS context
    await tx.$executeRaw`
      SET app.current_clinic = ${clinicId}
    `;

    // All queries within this transaction are scoped
    return tx.appointment.findMany({
      where: { clinicId }
    });
  });
}
```

model Appointment {
  id String @id @default(uuid())

model AuditLog {
  id String @id @default(uuid())

## Prisma Testing

```typescript
// Test with isolated database
beforeEach(async () => {
  // Clean database
  await prisma.appointment.deleteMany();
  await prisma.patient.deleteMany();
});

// Test transaction rollback
it('should rollback on conflict', async () => {
  // Create first appointment
  await prisma.appointment.create({
    data: { patientId, scheduledAt, status: 'booked' }
  });

  // Try to create overlapping appointment
  await expect(
    prisma.$transaction(async (tx) => {
      const overlap = await tx.appointment.findFirst({
        where: { patientId, scheduledAt, status: 'booked' }
      });
      if (overlap) throw new ConflictException('Overlap');
      return tx.appointment.create({ data: { patientId, scheduledAt } });
    })
  ).rejects.toThrow('Overlap');
});
```

---
## Summary

1. **Prisma's query engine maps your schema to SQL** — knowing the generated SQL is still your job
2. **`select`/`include` shape queries** — over-fetching is the default-N+1 cousin
3. **Transactions via interactive transactions** — keep them short; they hold real connections
4. **Raw SQL is a feature, not a failure** — escape hatch for CTEs, window functions, and RLS policies
5. **Migrations are code review artifacts** — `prisma migrate diff` and shadow databases catch drift

# ORM & Query Builder Landscape — Choose the Boundary You Need

## Definition

A database access layer sits between application operations and the driver/database. A raw driver sends SQL and maps rows; a query builder composes SQL; an ORM also provides a model/relation API. Migration tooling is a separate concern even when shipped in the same package.

> **Textbook Definition:** A database access layer translates application operations into driver or database requests. Query builders compose statements; object-relational mappers add model and relation abstractions, with different effects on query visibility and control.

## First Principles

1. **Someone must own the row-to-application contract.** Generated types, manually declared interfaces and runtime validators solve different parts of that mapping. A TypeScript assertion does not inspect a database result.
2. **The database still owns execution and concurrency.** Any access layer can issue an inefficient query or use the wrong transaction connection. Compare emitted SQL and invariant behavior before blaming abstraction overhead.
3. **More abstraction is not a monotonic safety scale.** Raw SQL can be safely parameterized; an ORM raw escape hatch can inject unsafe text. Safety depends on the actual boundary and operation.
4. **Schema evolution must have one operational owner.** Generating a diff is not a rollout plan. Pick a workflow that produces reviewed changes and tracks deployed history.

## Start with the operation, then compare its owners

Suppose a reporting endpoint needs the top five authors by published post count since a timestamp. The database should filter, group, order and limit before returning results; loading every author and all posts to aggregate in JavaScript changes the workload and is not an equivalent comparison.

```text
HTTP contract → repository operation → query construction → shared driver pool
                                                           ↓
                                PostgreSQL filter/group/order/limit
                                                           ↓
                                 result mapping → public DTO
```

A repository seam describes the operation and result without exporting a vendor's entity/client types to controllers. It also needs to define transaction participation: a helper opening its own pool/transaction can break the caller's atomicity even if it implements the same interface.

## Compare capabilities, not a single abstraction ranking

| Access style | Query contract | Relation/result shaping | Migration responsibility |
| ------------------ | ------------------------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------- |
| `pg` raw driver | SQL plus separate value parameters | Explicit row mapping; optional runtime validation | Separate migration tool/process |
| Knex query builder | Composable SQL clauses and bindings | Explicit joins/projections; TypeScript generics have limitations | Usually hand-authored migration functions |
| TypeORM | Entity/repository APIs plus SQL-shaped builder | Entity metadata and explicit/eager/lazy relations | Entity diffs or authored migrations; review SQL |
| Prisma | Version-specific model/query contract | Generated model/result types and relation operations | Version-specific contract/schema and migration workflow |
| Drizzle | TypeScript table definitions and typed SQL-shaped APIs | Explicit joins plus relational-query APIs | Drizzle Kit or another deliberate DDL owner |

Knex is not inherently untyped and raw `pg` results can have TypeScript interfaces. Conversely, string aliases, raw queries and SQL casts can escape static guarantees in every tool. TypeORM's entity API has typed parts; its string query expressions have weaker checks. Drizzle is not merely "manual joins only," and an ORM does not necessarily maintain an identity map/unit of work.

Prisma examples elsewhere in this category deliberately pin **6.19.0**. Current ORM 8 changes APIs/provider support; do not infer MySQL support or `$queryRaw` availability from the older comparison. Pin each tool, driver and database combination before adopting a feature. Edge/serverless support depends on the runtime's networking/module/native-addon capabilities and the chosen adapter, not a universal ORM label.

## Execute the report where the data lives

A PostgreSQL raw-driver implementation using the [fundamentals schema](20.4.4.01-prisma.md):

```javascript
async function topAuthors(pool, since, limit = 5) {
  if (!(since instanceof Date) || !Number.isFinite(since.getTime())) {
    throw new TypeError('Invalid timestamp');
  }
  if (!Number.isSafeInteger(limit) || limit < 1 || limit > 100) {
    throw new RangeError('Invalid limit');
  }
  const { rows } = await pool.query(`
    SELECT u.id, u.name, COUNT(p.id)::text AS post_count
    FROM users u JOIN posts p ON p.author_id = u.id
    WHERE p.published = true AND p.created_at >= $1
    GROUP BY u.id, u.name
    ORDER BY COUNT(p.id) DESC, u.id ASC
    LIMIT $2
  `, [since, limit]);
  return rows.map(row => {
    if (typeof row.id !== 'string' ||
        !(row.name === null || typeof row.name === 'string') ||
        typeof row.post_count !== 'string' || !/^[0-9]+$/.test(row.post_count)) {
      throw new TypeError('Unexpected report row');
    }
    return { id: row.id, name: row.name, postCount: row.post_count };
  });
}
module.exports = { topAuthors };
```

`COUNT` is converted to decimal text deliberately, avoiding unsafe integer coercion and making the DTO JSON serializable. The tie-breaker makes ordering deterministic. Value parameters bind timestamp/limit; table or column identifiers need separate static/allowlisted construction. The repository receives the existing pool and does not create another pool per call.

The same relational operation can be expressed by Knex or Drizzle builders, a TypeORM builder, or Prisma's version-specific SQL escape hatch/builder. The old Prisma 6 model API can group posts by author and fetch author projections, or use the [tagged query example](20.4.4.01-prisma.md); compare the resulting round trips and row counts. Pick one canonical implementation rather than maintaining four long snippets that silently compute different results.

## Decide with a representative slice

Work through these questions before adopting or replacing the access layer:

1. **Does the tool express the required operation?** Check recursive CTEs, correlated/lateral queries, locks, bulk COPY, range types and provider constraints. A raw statement can handle one feature without requiring a whole-service rewrite.
2. **Who owns schema changes?** If Flyway/Atlas or another team owns DDL, use introspection/manual mappings deliberately instead of running competing automatic diff workflows.
3. **Which guarantees survive the seam?** Test transaction propagation, authorization/tenant context, affected-row counts and result validation on both ordinary and raw paths.
4. **What does the team understand?** Generated types help refactors but do not remove SQL knowledge. Reusing a well-understood existing stack may lower risk more than adopting a new tool.
5. **Where is the measured cost?** Include driver pool wait, SQL work, network, serialization and runtime startup under the actual deployment limits.

There is no universal QPS threshold at which raw SQL wins, and no assured sub-millisecond cold start from choosing a particular builder. A missing index or over-fetched relation can dominate all access-layer overhead. Start with one hot/relevant operation and its failure cases, then measure.

## Keep migration generation and rollout separate

Examples of the tooling shape, using each project's configured and locked CLI:

```bash
# Prisma 6 schema workflow: create a reviewed SQL artifact in development
npx prisma migrate dev --name add_post_index --create-only
# Deployment applies existing migration history:
npx prisma migrate deploy

# Drizzle Kit: generate SQL/history from the configured table definitions
npx drizzle-kit generate --name add_post_index
npx drizzle-kit migrate

# Knex: create an authored migration, then apply tracked migrations
npx knex migrate:make add_post_index
npx knex migrate:latest

# TypeORM: -d is the DataSource module, not the migration directory
npx typeorm migration:generate ./src/migrations/AddPostIndex -d ./dist/data-source.js
npx typeorm migration:run -d ./dist/data-source.js
```

The TypeORM command assumes compiled JavaScript. Use the appropriate configured TS runner when the DataSource contains TypeScript/decorators. CLI syntax/configuration changes by major; verify the locked version before running a mutation.

Prisma's development workflow uses a shadow database to replay history and detect drift. Do not assume Drizzle's ordinary SQL generation uses the same shadow-database mechanism. A deployment command applying pending migrations does not necessarily detect every manually introduced production drift. All tools need reviewed SQL, privilege controls and an expand/backfill/contract plan for online changes; see [Migration Strategies](../05-operations-and-scaling/20.4.5.02-migration-strategies.md).

## Mix access paths without splitting guarantees

Keep exceptional raw statements beside their ordinary repository methods. Preserve parameterization, the same participating transaction/tenant connection and the public DTO boundary. For bulk ingestion, a driver COPY path may be appropriate; validate data, stage it and define commit/recovery semantics rather than bypassing invariants for speed.

Tests should exercise both paths against the actual database schema and role. Useful cases include null/numeric/date representations, duplicate/conflict behavior, connection loss, tenant denial and migration compatibility. A raw generic such as `$queryRaw<CustomerRow[]>` does not make SQL/interface drift fail compilation; it needs validation or a meaningful integration assertion.

When adopting incrementally, choose a module boundary whose operation contract can be preserved. Avoid swapping transaction helpers underneath an in-flight caller or silently creating independent clients/pools. One interface can hide a vendor; it cannot hide a changed consistency guarantee.

## Summary

Locate the access layer between the operation contract and the driver/database, then choose which component owns query construction, row mapping, transactions and migrations. Compare equivalent operations with real constraints and measured costs. Keep raw escape paths intentional and versioned; generated types help development but do not replace runtime validation or database invariants.

# ORM & Query Builder Landscape — Prisma, Drizzle, TypeORM, Knex, Raw SQL

> **TL;DR:** The Node data-access spectrum runs from raw `pg` (full control, zero safety) through query builders (Knex — composable SQL, no domain model), schema-first ORMs with compile-time types (Drizzle, Prisma), and decorator/entity ORMs (TypeORM — mature but runtime-magic-heavy). There is no "best" — there is fit: Prisma for product CRUD velocity and type-safe teams; Drizzle when you want SQL-shaped code with edge/bundle constraints; Knex for migration-centric or multi-database shops; raw SQL for hot paths, window functions, CTEs, and exotic Postgres features. Decide with a decision tree, not vibes.
>
> **Why it matters:** Senior interviews ask "Prisma vs TypeORM vs raw queries — how do you choose?" The winning answer shows the trade-off axes (type-safety timing, abstraction leak risk, migration ownership, performance ceilings) plus a concrete adoption story.

## Definition

The four access styles, precisely:

```text
Type-safety & abstraction spectrum (low → high)

 raw driver        query builder       entity ORM           schema-first typed ORM
 (node-postgres)   (Knex)              (TypeORM)            (Prisma / Drizzle)
 ─────────────     ─────────────       ──────────────       ─────────────────────────
 you write SQL     composable DSL      classes+decorators   schema file drives
 strings; manual   → parameterized     → runtime query      generated client AND
 row mapping       SQL; mapping is     construction;        TS types; migrations
                   yours               decorators decide    from schema diff
                                       shape                (Prisma) or infer types
                                                            from TS (Drizzle)
```

| Style | You write | Safety net | Escape hatch |
| --------------------- | ---------------------------------------------- | ------------------------------------------- | -------------------------------- |
| Raw (`pg`) | SQL strings | Parameterization only | — |
| Query builder (Knex) | JS function calls shaped like SQL | Column/table typos caught at runtime | `.knexRaw()` passthrough trivial |
| Entity ORM (TypeORM) | `@Entity()` classes + `QueryBuilder`/relations | Partial (string-based `where`s are untyped) | `manager.query(raw)` |
| Schema-first (Prisma) | `schema.prisma` → generated client | Compile-time on every query result | `$queryRaw` tagged templates |
| SQL-in-TS (Drizzle) | Table defs in TS → typed builder | Compile-time, SQL-faithful | `sql` template literal |

## Why Do We Need It?

1. **Team velocity** — Generated clients with autocomplete collapse the "check column name in psql" loop; juniors ship correct CRUD without mastering SQL first.
2. **Safety floor** — Every layer above raw gives parameterized queries by default; SQL injection risk drops structurally.
3. **Refactor leverage** — Rename a column once; typed clients turn every broken call site into a compile error instead of a 3 a.m. incident.
4. **Migration discipline** — Bundled tooling (prisma migrate, drizzle-kit, knex migrate) creates reviewable, ordered migration history instead of ad-hoc psql scripts.
5. **Escape hatches exist for a reason** — Knowing *when* to drop to `$queryRaw`/`db.execute(sql...)` separates seniors from framework tourists.
6. **Hiring reality** — Prisma dominates new TS startups; TypeORM still rules NestJS enterprise estates; knowing both makes you portable.

## How It Works

### Decision tree

```text
START
  │
  ├─ Is this a HOT PATH (p99-critical, >1k QPS per endpoint)?
  │     └─ yes → profile first; prefer raw SQL or Drizzle; keep Prisma out of the inner loop
  │             (or use Prisma with prepared-query caching / driver adapters and measure)
  │
  ├─ Does the feature need EXOTIC SQL? (recursive CTEs, lateral joins,
  │   custom operators, advisory locks, materialized views)
  │     └─ yes → raw SQL for that statement; ORM elsewhere. Never fight the mapper.
  │
  ├─ Multi-database support needed (MySQL + Postgres + SQLite)?
  │     ├─ yes → Knex (builder) or TypeORM (entities); Prisma supports all three too,
  │     │        but Mongo-style documents push you to dedicated drivers
  │     └─ no ↓
  │
  ├─ Team is TS-strong, wants compile-time guarantees, SQL-literate?
  │     └─ Drizzle — SQL-shaped API, tiny runtime, edge-compatible
  │
  ├─ Team wants max velocity, schema-as-contract, rich tooling (Studio, Pulse)?
  │     └─ Prisma — best DX, guardrails, ecosystem
  │
  └─ Existing NestJS estate with entities/decorators + legacy migrations?
        └─ TypeORM — stay consistent; greenfield should think twice
```

### Trade-off matrix

| Axis | Prisma | Drizzle | TypeORM | Knex | Raw pg |
| ---------------------- | ------------------------------------ | ---------------------- | -------------------------- | ---------------------- | ---------------------- |
| Type safety of results | Excellent (generated) | Excellent (inferred) | Weak–medium | None | None |
| SQL fidelity | Medium (its own query model) | High (SQL-shaped) | Medium | High | Total |
| Migration tooling | `prisma migrate` (diff engine) | `drizzle-kit` | CLI + decorators | First-class | BYO (node-pg-migrate…) |
| Runtime cost | Higher (engine/driver adapter) | Tiny | Medium | Small | Smallest |
| Learning curve | Low–medium | Medium (needs SQL) | Medium | Low (needs SQL anyway) | High discipline |
| N+1 resistance | `include`/`select` batching | Manual joins, explicit | `relations` w/ eager traps | Explicit joins | Explicit |
| Edge/serverless | OK now (driver adapters, Accelerate) | Native fit | Poor | Poor | OK with HTTP drivers |
| Escape hatch | `$queryRaw` | `sql` template | `query()` | `.raw()` | native |

### Same query, four dialects

"Top 5 customers by lifetime value, with their latest order":

```typescript
// RAW — full control, zero help
const { rows } = await pool.query(
  `SELECT c.id, c.name, SUM(o.total) AS ltv
   FROM customers c JOIN orders o ON o.customer_id = c.id
   WHERE o.created_at >= $1
   GROUP BY c.id, c.name ORDER BY ltv DESC LIMIT 5`, [since]);

// KNEX — composable, still stringly columns
const top = await db('customers as c')
  .join('orders as o', 'o.customer_id', 'c.id')
  .where('o.created_at', '>=', since)
  .groupBy('c.id', 'c.name')
  .select('c.id', 'c.name')
  .sum({ ltv: 'o.total' })
  .orderBy([{ column: 'ltv', order: 'desc' }])
  .limit(5);

// PRISMA — typed results, aggregation via its own model
const top = await prisma.customer.findMany({
  where: { orders: { some: { createdAt: { gte: since } } } },
  select: {
    id: true, name: true,
    orders: { where: { createdAt: { gte: since } }, select: { total: true } },
  },
});
// then reduce totals in JS (or drop to groupBy raw when it matters)

// DRIZZLE — SQL-shaped, fully typed
const top = await db
  .select({ id: customers.id, name: customers.name, ltv: sum(orders.total) })
  .from(customers)
  .innerJoin(orders, eq(orders.customerId, customers.id))
  .where(gte(orders.createdAt, since))
  .groupBy(customers.id, customers.name)
  .orderBy(desc(sum(orders.total)))
  .limit(5);
```

The tell: the moment the aggregate must happen *in the database* at scale, Prisma's object-graph model bends first; Drizzle/Knex/raw stay straight.

### When NOT to use Prisma

1. **Hot request paths** — historically extra layers (engine binary, JSON protocol) added p99 latency; driver adapters narrowed the gap, but measure before committing latency-SLO endpoints.
2. **Exotic SQL** — recursive CTEs with cycles, `LATERAL` correlation, exclusion constraints, range types, partial-index-backed upserts: `$queryRaw` becomes the main path and the ORM adds ceremony.
3. **Massive batch ETL** — millions-row COPY/bulk updates belong to scripts using `pg-copy-streams`, not any ORM's unit-of-work.
4. **Strict cold-start budgets** — Lambda snapshots mitigate, but engine-less Drizzle/Knex start faster on edge runtimes.
5. **Schema owned by another system** — if DDL comes from dbmate/Atlas/Flyway pipelines, Prisma's schema-as-source-of-truth workflow fights the existing flow.

## Code Examples

### Typed repository seam — swap engines without leaking either

```typescript
// repositories/customer-repo.ts
export interface CustomerRepo {
  findById(id: string): Promise<CustomerRow | null>;
  search(term: string, limit: number): Promise<CustomerRow[]>;
}

export class PrismaCustomerRepo implements CustomerRepo {
  constructor(private prisma: PrismaClient) {}
  async findById(id: string) {
    return this.prisma.customer.findUnique({ where: { id } });
  }
  async search(term: string, limit: number) {
    return this.prisma.$queryRaw<CustomerRow[]>`
      SELECT * FROM customers
      WHERE search_vector @@ websearch_to_tsquery('english', ${term})
      ORDER BY ts_rank(search_vector, websearch_to_tsquery('english', ${term})) DESC
      LIMIT ${limit}`;
  }
}
```

The interface keeps controllers testable and lets a hot service migrate Prisma → Drizzle per-module, not big-bang.

### Migration tooling comparison

```bash
# PRISMA — schema file is source of truth; diff engine writes SQL
npx prisma migrate dev --name add_orders_total_index
# → creates migrations/<timestamp>_add_orders_total_index/migration.sql
# review it like code; `migrate deploy` applies pending in CI

# DRIZZLE — generate from TS table defs
npx drizzle-kit generate --name add_orders_total_index
npx drizzle-kit migrate

# KNEX — hand-write up/down pairs (max control, max responsibility)
npx knex migrate:make add_orders_total_index

# TYPEORM — migrations can be autogenerated from entity diffs
npx typeorm migration:generate -d ./src/migrations AddOrdersTotalIndex
```

| Tooling concern | Prisma migrate | drizzle-kit | Knex | TypeORM |
| ---------------------- | ------------------------ | -------------------- | ---------------- | ------------------ |
| Diff generation | Automatic (schema → SQL) | Automatic (TS → SQL) | Manual up/down | Auto from entities |
| Shadow DB for diffing | Yes | Yes (optional) | n/a | n/a |
| Squash/history editing | Supported, guarded | Supported | Manual files | Manual files |
| CI apply command | `migrate deploy` | `migrate` | `migrate:latest` | `migration:run` |
| Drift detection | Strong (provider state) | Good | Manual | Weaker |

### Mixing safely: ORM default, raw for the sharp edges

```typescript
@Injectable()
export class LedgerService {
  constructor(private prisma: PrismaClient) {}

  // 99% of service: plain typed ORM calls
  async balance(accountId: string) {
    const agg = await this.prisma.entry.aggregate({
      where: { accountId }, _sum: { amountCents: true },
    });
    return agg._sum.amountCents ?? 0;
  }

  // The 1% hot/reporting path: one raw statement, still parameterized
  async monthlyStatement(accountId: string, from: Date, to: Date) {
    return this.prisma.$queryRaw<StatementLine[]>`
      WITH months AS (
        SELECT date_trunc('month', d)::date AS m
        FROM generate_series(${from}::date, ${to}::date, interval '1 month') d
      )
      SELECT m, COALESCE(SUM(e.amount_cents), 0)::bigint AS cents
      FROM months LEFT JOIN entries e
        ON e.account_id = ${accountId}
       AND date_trunc('month', e.posted_at)::date = m
      GROUP BY m ORDER BY m`;
  }
}
```

Rules that keep the mix sane: raw SQL lives in repositories (never controllers), every raw statement uses tagged-template parameters, and integration tests cover both paths against real Postgres.

## Real-World Use Cases

1. **Series-A startup, 6 engineers** — Prisma everywhere; velocity wins; `$queryRaw` for two reporting endpoints. Migration reviews in PRs keep the schema honest.
2. **NestJS enterprise monolith, 8 years old** — TypeORM stays (rewrite risk beats benefit); new bounded-context modules may adopt Drizzle internally behind repository interfaces.
3. **Edge-rendered SaaS dashboard** — Drizzle + Neon/PlanetScale HTTP drivers: sub-ms cold starts, bundle fits worker limits, SQL-shaped queries match the team's skillset.
4. **Multi-tenant analytics product** — Knex for cross-schema dynamic queries (tenant-per-schema), because building identifiers programmatically is the whole job.
5. **Fintech ledger** — Any ORM for CRUD screens; raw SQL + explicit transactions for double-entry postings where lock ordering and isolation are load-bearing.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------- | ------------------------------------------------------------------------------ |
| Choosing an ORM "so we don't need SQL" | The team needs SQL regardless; ORMs generate SQL someone must review |
| Blaming the ORM for N+1s | Log emitted SQL in dev; batch with `include`/joins/DataLoader deliberately |
| Two access layers interleaved arbitrarily | Repository boundary decides; raw SQL lives beside its ORM siblings |
| Letting `prisma db push` hit staging/prod | Only `migrate deploy` of reviewed migrations in non-dev envs |
| TypeORM lazy relations in serverless | Lazy loads explode after context loss; use explicit eager/joins or move stacks |
| Rewriting everything to escape a slow ORM query | Profile first; usually one index or one raw statement fixes it |
| Trusting ORM defaults for transactions | Interactive transactions hold connections; scope them tightly or go raw |

## Best Practices

1. **Standardize one primary layer per service** — polyglot data access within a module is a bug factory; exceptions live at the repository seam.
2. **Treat migrations as code review artifacts** — read generated SQL, require expand/contract steps for online changes (see Migration Strategies).
3. **Keep the escape hatch first-class** — document which statements are raw and why; grep-ability (`$queryRaw`, `db.execute(sql`) is your audit trail.
4. **Pin provider capabilities, not abstractions** — choosing Knex "for portability" while using Postgres-only SQL buys nothing; commit to your database.
5. **Type raw results explicitly** — `<CustomerRow[]>` on every `$queryRaw`; drift between SQL and interface fails tests, not prod.
6. **Load-test the hot path with the real stack** — include connection pooling semantics (Prisma's pool vs PgBouncer transaction mode) in benchmarks.
7. **Adopt incrementally in brownfields** — strangulate per module behind interfaces; never big-bang swap access layers.
8. **Upgrade deliberately** — Prisma major versions changed client init/engine behavior; schedule upgrades with load tests.

## Performance Considerations

- Prisma's cost centers were the Rust engine hop and JSON serialization; driver adapters (`@prisma/adapter-pg`) remove much of it — re-measure on your workload before ruling it out.
- Drizzle compiles to near-hand-written SQL with negligible overhead; its cost is human (SQL fluency required).
- All layers pay connection-pool taxes: Prisma pools inside each app instance; pair with PgBouncer in transaction mode carefully (prepared-statement caveats).
- Raw wins measurable only beyond ~hundreds of QPS per statement shape; below that, developer throughput dominates total cost.

## Summary

- Spectrum: raw → builder (Knex) → entity ORM (TypeORM) → schema-first typed (Prisma/Drizzle); each step trades control for safety.
- Choose by workload: velocity + type safety → Prisma; SQL fidelity + edge/small runtime → Drizzle; legacy Nest estates → TypeORM; dynamic SQL → Knex; hot/exotic → raw.
- Migration tooling differs more than query APIs — pick the workflow your team will actually review.
- Escape hatches ($queryRaw, sql``) are mandatory features, not admissions of failure.
- Repository seams let you mix and later migrate per module without rewrites.

## Cheat Sheet

| Concept | Description |
| ---------------- | --------------------------------------------------------------------------- |
| Prisma | Schema-file source of truth, generated typed client, strong migrate tooling |
| Drizzle | TS-first tables, SQL-shaped typed builder, tiny runtime, edge-friendly |
| TypeORM | Decorator entities, deep NestJS integration, weaker typing on queries |
| Knex | Battle-tested SQL builder + first-class migrations; no result typing |
| node-postgres | Raw parameterized SQL; maximum control and ceiling |
| `$queryRaw` | Tagged-template escape hatch; parameters safe, results typed manually |
| Decision inputs | Hot path? Exotic SQL? Multi-DB? Team SQL fluency? Legacy estate? |
| Migration review | Read generated SQL; expand/contract for zero-downtime changes |
| N+1 fix | `include`/`select` (Prisma), joins (others), DataLoader at resolver edges |

# Connection Pooling


## Definition

A connection pool owns a bounded set of reusable database connections. An operation borrows one, uses it and releases it. If no connection is available, the operation can wait in a queue or fail at a deadline. Reusing a connection saves setup work; bounding the set limits the work admitted to the database.

> **Textbook Definition:** A connection pool assigns reusable database connections to borrowers under admission, timeout and lifetime rules. Those rules determine contention and which connection-scoped state may safely survive between operations.

## First Principles

A PostgreSQL connection requires communication setup, authentication and a backend session. Repeating that for every query wastes work. Yet keeping one connection per incoming HTTP request would let a traffic spike exhaust database resources. Reuse and admission limits address these separate constraints.

When demand exceeds the number of connections, the work does not disappear: it waits, is rejected or moves elsewhere. Adding a larger pool may reduce its queue while increasing database contention. The correct size therefore comes from end-to-end load and available capacity, not a formula using CPU cores and disk spindles.

A reused session also retains state. An open transaction, session setting or session advisory lock can affect the next borrower. Pooling requires both resource ownership and a clean release boundary.

## How It Works

### Locate the application pool and an optional proxy

```text
application instance A → local driver pool ─┐
application instance B → local driver pool ─┼→ optional PgBouncer → PostgreSQL backends
job worker             → local driver pool ─┘       client queue       active work
```

A driver pool exists inside an application process; another replica typically owns another pool. A proxy such as PgBouncer sits between those client connections and database connections. These are two layers with different counts and queues. PgBouncer is optional when the application pools already provide the required budget and behavior; its presence does not remove the need to bound client demand.

For example, eight replicas with a maximum of ten direct connections can use up to 80 database connections, before job workers, migrations and administration. With a proxy, 80 client connections need not imply 80 PostgreSQL backends, but proxy limits apply according to database/user pools and configuration. Count all components, not just one `max` option.

### Follow a borrower through checkout and release

```text
request connection
  ├─ idle connection exists → checkout
  ├─ under maximum          → create/authenticate → checkout
  └─ at maximum             → queue → release makes one available / deadline fails
checkout → statement or transaction → clean release → idle reuse / close
```

**Idle** in pool metrics means available to borrow. **Checked out** means owned by a borrower, even if that borrower is not executing SQL. **Waiting** describes requests in the acquisition queue, not a third kind of physical connection. Database `pg_stat_activity.state` is a different observation: a checked-out connection can be `idle in transaction` while the application pauses.

Release must happen on both success and failure. A transaction must be committed or rolled back before returning its connection. If recovery cannot establish a usable connection, destroy it rather than lending an aborted/broken session to another operation.

### Pooling modes change how long a server session belongs to a client

PgBouncer **session pooling** pins a PostgreSQL connection for the client's session. **Transaction pooling** can reassign it after COMMIT/ROLLBACK, so the client's next transaction cannot rely on the same backend or its session state. Transaction-local tenant context fits when set and used within that transaction; a session SET does not establish context for every later transaction.

**Statement pooling** releases after a statement and disallows multi-statement transactions. It cannot implement an operation that requires one session across BEGIN, several statements and COMMIT.

Prepared-statement support is version/configuration specific: some transaction-pooling configurations support named protocol prepared statements, but that does not make all SQL session features portable. Check the current feature matrix for LISTEN, temporary tables, session advisory locks and the actual driver protocol before choosing a mode. Transaction pooling saves idle backend ownership; it does not let two statements execute simultaneously on one backend connection.

## Code Examples

### Observe waiting with a one-connection pool

Use Node.js with node-postgres (`pg` 8.x) and a reachable disposable PostgreSQL database. This CommonJS script needs `DATABASE_URL`; no tables are required:

```javascript
const { Pool } = require('pg');

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 1,
  connectionTimeoutMillis: 1000,
  idleTimeoutMillis: 30000,
});
pool.on('error', (error) => {
  console.error('Idle database connection failed:', error.message);
});

async function main() {
  const first = await pool.connect();
  let second;
  try {
    const pending = pool.connect();
    const waiting = pool.waitingCount;
    first.release();
    console.log(waiting); // 1: observed before release
    second = await pending;
    const { rows } = await second.query('SELECT 42 AS answer');
    console.log(rows[0].answer); // 42
  } finally {
    if (second) second.release();
    await pool.end();
  }
}
main().catch((error) => {
  console.error(error.message);
  process.exitCode = 1;
});
```

The first checkout uses the only connection. The second queues instead of opening another backend. Release transfers capacity to the waiting borrower, which runs the query and releases it. This is acquisition behavior, not proof of an optimal production pool size.

For a single independent statement, `pool.query(...)` checks out and releases automatically. A transaction needs `pool.connect()` and `client.query(...)` throughout; separate pool.query calls can use different sessions. A pool's `min` option can retain idle clients but does not automatically create that many connections. `allowExitOnIdle` helps short scripts exit with idle sockets; it is not a graceful-drain strategy for a server.

If the first client is never released, the waiting acquisition times out according to this configuration. That deadline is distinct from a query execution or lock timeout. Bound the HTTP request and admitted queue as well: a small pool with an unbounded queue can still consume application memory and produce unusable tail latency.

### End a transaction before releasing its session

This helper receives the existing pool and a callback using its checked-out client:

```javascript
async function withTransaction(pool, work) {
  const client = await pool.connect();
  let destroy = false;
  let committing = false;
  try {
    await client.query('BEGIN');
    const result = await work(client);
    committing = true;
    await client.query('COMMIT');
    return result;
  } catch (error) {
    if (committing) destroy = true; // commit outcome may be uncertain
    try { await client.query('ROLLBACK'); }
    catch { destroy = true; }
    throw error;
  } finally {
    client.release(destroy);
  }
}
```

A callback error rolls back prior database writes before release. A failed rollback discards the connection. A COMMIT communication failure may leave the transaction's outcome unknown; this helper rethrows and does not blindly retry the callback. A durable operation identity/reconciliation protocol belongs to the caller. External charges or emails inside `work` are not undone by ROLLBACK.

### Observe the pool and server independently

```javascript
console.log({
  total: pool.totalCount,
  idle: pool.idleCount,
  waiting: pool.waitingCount,
});
```

```sql
SELECT datname, state, count(*)
FROM pg_stat_activity
GROUP BY datname, state;
SHOW max_connections;
```

Driver metrics show local acquisition pressure; PostgreSQL metrics show server sessions, including other pools. PgBouncer's SHOW POOLS/CLIENTS/SERVERS/STATS commands run on its administrative endpoint, not as PostgreSQL SQL. Measure wait duration and rejected acquisition as well as counts; a sampled zero queue does not prove that requests never wait.

## Real-World Decisions

### Connect the pool budget to deployment growth

Reserve headroom for administration, migrations, failover and workers, then load-test a budget across the maximum expected application replicas. Add bounded admission when database concurrency saturates. A separate reporting pool can isolate acquisition slots but still shares CPU, storage and locks with interactive work; it is not complete resource isolation.

Serverless bursts can multiply clients quickly. A proxy can reduce backend growth, but queue capacity, credentials, network access and connection reuse across warm instances remain design decisions. Consider transaction duration and service recovery behavior rather than assuming every serverless invocation should create or retain a dedicated backend.

### Pin who owns Prisma's pool

The [Prisma fundamentals](../04-orm-and-access/20.4.4.01-prisma.md) examples pin the 6.19.0 Rust-engine client, whose URL options include `connection_limit` and `pool_timeout`. Other major versions, engines and driver adapters have different pool owners/settings. `relationMode = "prisma"` changes relation enforcement behavior; it is not a connection-pool option and should not be added to configure pooling.

Create one intentionally owned client per application process rather than per request, and connect/disconnect at the process lifecycle. Query logging can expose sensitive values, so enable it under a controlled observability policy.

### Drain work before shutting down or rotating connections

Stop accepting new requests, give admitted operations a bounded opportunity to finish, then await pool.end. A leaked borrower can prevent draining. Set an overall shutdown deadline and decide what happens to unfinished work; forced process exit is not evidence that transactions completed.

An idle-connection error event is different from a rejected query on a checked-out client. Handle both, discard unusable connections and classify operation outcomes before retry. DNS/credential changes and failover may require connection rotation; a newly connected socket does not establish that an uncertain earlier mutation rolled back.

## Common Mistakes

| Mistake | Why it fails | Correction |
| -------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| Pool per request | Multiplies connections and repeats setup | Own a shared process pool |
| Use pool.query for a transaction | Statements can reach different sessions | Hold one client across the boundary |
| Release without rollback after an error | Next borrower inherits aborted/open transaction state | End the transaction or discard the connection |
| Treat waiting as a physical connection state | Queue and backend activity become confused | Observe local borrowers and server sessions separately |
| Size by CPU/disk formula alone | Ignores query work and deployment concurrency | Measure latency, saturation and queueing |
| Add a proxy without testing session features | Context/prepared/listener behavior can change | Match mode to the actual driver and workload |

## Best Practices

Bind values, protect credentials/transport and keep tenant/session state inside its documented lifetime. Keep transactions short and free of user interaction or avoidable remote waits. Define acquisition, statement, lock and request deadlines separately.

Monitor aggregate connection demand, acquisition latency, abandoned requests, active transaction age and database saturation. Use retries only for outcomes the application can safely repeat; a pool recovering a connection does not deduplicate a business operation.

## Summary

Pooling reuses sessions and controls admission. Trace a request through checkout, queueing, cleanup and release, and count budgets across every process. A proxy's mode changes backend ownership and session compatibility. Measure the actual workload, scope context to the right lifetime and recover operation outcomes separately from connection recovery.

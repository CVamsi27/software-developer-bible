# Database Migrations & Zero-Downtime Schema Changes

During a rolling deploy, old code may still read `total` while new code needs `total_cents`. A rename breaks the old reader; a stale backfill can overwrite a newer payment. Safe migration must handle both versions and the data race.

## Definition

A migration is a versioned transition in database structure or stored data. A live migration must preserve the application behavior needed while old and new code coexist. **Expand and contract** first introduces a compatible shape, then transitions writers/data/readers, and finally removes the retired shape after its consumers and rollback requirements are gone.

> **Textbook Definition:** Database migration sequences schema and data changes under application compatibility, integrity and operational constraints. A migration's reverse SQL is distinct from a recovery plan for data already removed or transformed.

## First Principles

A rolling deployment is not an atomic switch. One server can run new code while another still runs old code; background jobs or an old client may survive longer. Renaming a column immediately breaks any remaining query using its old name.

Data also changes while it is copied. A backfill reading an old value and later writing its conversion can overwrite a newer write. A valid plan therefore needs a writer transition and a race-safe data transition, not just a loop and feature flag.

Even a short schema command acquires locks. A fast metadata operation waiting behind a long transaction can queue other traffic. “No table rewrite” and “no application downtime” are different claims, and availability must be measured rather than inferred from a keyword.

## How It Works


### 1. Give each migration phase an owner and exit condition

#### Give each phase an owner and an exit condition

```text
expand schema → make writers compatible → repair/copy existing data
             → verify and switch readers → retire old reads/writes
             → end old rollback window → contract schema
```

The schema owner reviews/applies DDL. Application deployments change the write/read contract. A worker owns bounded backfill progress.
Verification checks both data and remaining consumers before contraction. Different operations can require different release counts; the dependency order matters more than a fixed number of deploys.

At every phase, state the authoritative representation. Dual writes to columns in one transaction can be atomic, but independent writes to two databases can partially succeed and need publication/reconciliation. A feature flag routing some writes to only the new table does not make the old table current for a later fallback read.

#### Migration tools manage history, not the whole release

A migration tool records applied versions and executes an ordered change set. A schema-diff generator can suggest SQL, while an authored migration states it directly. Neither establishes that the SQL is safe under current traffic or that every application version is compatible.

Pick one operational owner for DDL history. Review locks, conversions, defaults, constraints, privileges and replay on a fresh database. Development drift/shadow-database features and deployment checks vary by tool/version.
The [Prisma fundamentals chapter](../04-orm-and-access/20.4.4.01-prisma.md) pins Prisma 7.10.0: `migrate dev` creates and applies migrations in development; CI/CD uses `migrate deploy` to apply pending history in testing and production. `migrate deploy` does not detect schema drift or generate Prisma Client, so verify schema/data and generate artifacts in separate gates. See the [Prisma 7 migration workflow](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production).

### 2. Convert a changing representation without stale writes

#### Migrate exact decimal amounts to cents without a stale copy

Use PostgreSQL 16+ in a disposable schema. This fixture assumes one currency with exactly two decimal places, nonnegative amounts fitting bigint cents, and integer IDs. Other currencies or rounding policies need a different conversion contract.

```sql
CREATE TABLE migration_orders (
    id integer PRIMARY KEY,
    total numeric(18, 2) NOT NULL CHECK (total >= 0)
);
INSERT INTO migration_orders VALUES (1, 12.50), (2, 7.25);

-- Phase 1: compatible addition; the DDL still acquires a table lock.
BEGIN;
SET LOCAL lock_timeout = '500ms';
ALTER TABLE migration_orders ADD COLUMN total_cents bigint;
COMMIT;
```

Old readers/writers can still use total. The new field initially has no value for existing rows. A short lock timeout bounds waiting for this attempt; retry the migration deliberately after investigating blockers rather than letting queued DDL wait indefinitely.

Phase 2 deploys writers that set both representations in **one statement/transaction**, while readers still use total. For example:

```sql
UPDATE migration_orders
SET total = 8.00, total_cents = 800
WHERE id = 2;
```

Do not begin read cutover until every relevant legacy writer has been retired or a tested compatibility bridge covers it. A legacy writer can change total after an earlier dual write and leave non-null cents stale. Therefore “backfill only nulls” is insufficient in that overlap.
The following backfill repairs mismatches as well as missing values, using exact database arithmetic rather than Number/Math.round conversion.

#### Lock and convert the current rows in one bounded batch

Run each batch as its own short transaction after the writer gate. All active writers now maintain matching old/new values:

```sql
BEGIN;
SET LOCAL lock_timeout = '500ms';
SET LOCAL statement_timeout = '5s';
WITH batch AS MATERIALIZED (
    SELECT id
    FROM migration_orders
    WHERE total_cents IS DISTINCT FROM (total * 100)::bigint
    ORDER BY id
    LIMIT 500
    FOR UPDATE SKIP LOCKED
)
UPDATE migration_orders AS target
SET total_cents = (target.total * 100)::bigint
FROM batch
WHERE target.id = batch.id
RETURNING target.id, target.total_cents;
COMMIT;
-- Initial fixture after the dual write: 1 | 1250
```

The batch selects mismatched IDs, locks those rows and converts their current authoritative total on the same connection. A concurrent writer either completes before the row is locked or waits until the batch ends; it must itself maintain both values. No external application snapshot is copied back later.
Committing each batch limits lock duration and WAL bursts; SKIP LOCKED lets workers avoid waiting on each other.

A repeat returns no rows for this fixture. That makes the conversion rerunnable, but an empty batch during concurrency can mean all remaining candidates were locked. Confirm completion with a separate verification after workers/legacy writers have been accounted for:

```sql
SELECT count(*) AS mismatches
FROM migration_orders
WHERE total_cents IS DISTINCT FROM (total * 100)::bigint;
-- 0
```

For larger datasets, persist repairable batch progress and failures, expose stop/resume controls, and adapt batch size to measured lock/WAL/replica pressure. A cursor can bound scanning but must not skip late-created or changed candidates forever. Repeating an insert under a primary key does not automatically make a copy idempotent: define conflict updates or deduplication and verify the resulting data.

#### Verify before requiring or retiring the representation

After a complete backfill, add a validated required-value rule:

```sql
ALTER TABLE migration_orders ADD CONSTRAINT cents_present
    CHECK (total_cents IS NOT NULL) NOT VALID;
ALTER TABLE migration_orders VALIDATE CONSTRAINT cents_present;
ALTER TABLE migration_orders ALTER COLUMN total_cents SET NOT NULL;
ALTER TABLE migration_orders DROP CONSTRAINT cents_present;
```

NOT VALID avoids scanning old rows at initial addition while the new rule constrains subsequent changes. Validation checks existing rows with a less restrictive lock than a full blocking change. A validated proving constraint can let SET NOT NULL avoid another scan, but each operation still acquires its required locks and consumes resources.
Test the exact version and sequence.

Readers can now use cents while writers continue maintaining both fields. Before a later application version stops referencing total, end rollback to versions that read total, relax any old constraints/default requirements that would reject new-only inserts, and deploy the new-only contract while both columns still exist. Wait until every old writer/query has gone before dropping total.
In this example, `total NOT NULL` must be relaxed before new-only inserts; otherwise the supposedly independent new writer fails.

Dropping total makes the original decimal representation unavailable. Retained cents permit an exact reverse conversion only under this fixture's currency/rounding assumptions. Other transformations can lose information permanently.
Preserve an appropriate recovery source and rehearse the chosen path before contraction.

### 3. Account for lock and constraint trade-offs

#### Distinguish concurrent index construction from lock freedom

A regular CREATE INDEX blocks conflicting writes while building. CREATE INDEX CONCURRENTLY uses a different locking/build sequence that permits ordinary writes but still acquires locks, waits for relevant transactions/snapshots and uses CPU/I/O. It can fail and leave an invalid index needing inspection and cleanup.
Run it outside an explicit transaction block, and choose timeouts/maintenance capacity deliberately.

Concurrent does not promise a fixed build-time multiplier or zero latency impact. Check `pg_index.indisvalid`, build progress and application latency before treating it as successful.

#### Understand fast defaults without inventing a lazy-write phase

PostgreSQL can add a column with a non-volatile default without rewriting every existing tuple immediately. It stores the missing value as metadata so old tuples return it; later row changes or a rewrite can materialize values. This is not a background batch performed on each row's first SELECT.
Volatile defaults or other clauses can still require a rewrite, and fast-default DDL still requires locks.

Use a direct fast default when it correctly defines existing/new rows. Use an explicit backfill when values depend on each row or need business validation. “Always add nullable first” is not a universal rule independent of the operation and supported version.

#### Tighten rules only after measuring invalid states

A NOT NULL, unique or foreign-key requirement can reject existing data or new writes during overlap. Identify and repair invalid states, validate the rule using supported methods, then enforce it at the required lifecycle point. NOT VALID is not available for every kind of constraint; uniqueness requires a different index/constraint plan.

A type change, table split or cross-database migration can also require a publication bridge, foreign-key repair or cutover watermark. A local down migration does not roll back a remote copy or restore deleted values. Review the specific failure trace rather than treating every change as the same add/drop recipe.

## Summary

A live migration preserves a versioned contract across schema, writers, data and readers. Give each phase an authority and a completion gate, convert current data without stale-copy races, and verify before enforcing or removing fields. Locks, index-build failures, concurrent updates and rollback windows determine availability and recovery; no tool, flag or release count establishes those guarantees alone.

# Soft Delete & Tombstones

> Soft deletion, hard deletion and tombstones solve different problems. Soft deletion keeps a row but marks it inactive; hard deletion removes it from a store; a tombstone records a deletion so replicas or consumers can learn about it. For personal data, decide what a delete request requires before choosing a storage pattern.

## Definition

**Soft delete**, **hard delete**, and **tombstones** are three answers to "what should happen to a row when the user deletes it", differing in **what state remains in the store**:

```text
                 row remains?   what remains                      can be read as live?
hard delete      no             nothing (row + children gone)     n/a
soft delete      yes            deleted_at IS NOT NULL            no (needs a filter)
tombstone        system-specific marker                         no; prevents stale data returning
                                (for example, a keyed null in Kafka)
```

The choice is not cosmetic — each defines a different set of obligations:

1. **Soft delete can support undo and preserve references**, but it does not create an audit trail by itself. Each query must deliberately include or exclude deleted rows. Unique constraints also need a clear policy: a partial unique index on active rows can allow a deleted email to be registered again. The two common failure modes are showing inactive records accidentally and retaining uniqueness across records the product treats as deleted.
2. **Erasure obligations may require removing personal data.** GDPR Article 17 provides a right to erasure in defined circumstances and lists exceptions. Whether a record can be retained depends on the facts and legal basis; a soft-deleted row remains stored personal data and must not be treated as erased.
3. **A tombstone is a deletion *fact*, not a flag** — in sync, replication, or multi-region (CRDT) systems, "the record is gone" must be communicated, otherwise a node that still has the old copy will re-introduce it on the next sync. A tombstone therefore needs a TTL/compaction policy of its own, and it is what keeps deletes *causally* correct.

Choose a policy per data type. Soft deletion can support an undo or moderation workflow. When an erasure request requires removing personal data, follow the applicable retention rules and propagate removal to derived stores. A grace period is a product and legal-policy decision, not a universal pattern.

---

## First Principles

Soft delete exists because deletion has consequences beyond the row:

1. **DELETE can remove context needed by the product.** Foreign keys may block or cascade deletion, and an application may need an undo period or retained business record. Keeping a row and setting `deleted_at` can support those needs, but a separate audit record may still be needed.
2. **The cost: every query must account for deleted rows.** Forgetting the filter can expose inactive records. Views or carefully designed data-access helpers can centralize the rule; row-level security is an authorization boundary, not a substitute for sound deletion semantics (→ 20.4.1.06).
3. **Tombstones are the replication/sync answer**: a delete must propagate as *data*, because an absence cannot be replicated. This is why event systems and sync engines speak of tombstones — deletion is information.

## Why it matters

Three forces pull at the "what does delete mean?" question:

1. **Users want undo.** "I accidentally deleted the wrong project. Can you bring it back?" Soft delete makes this trivial.
2. **Auditors want a trail.** "Who deleted this order? When?" Hard delete loses that.
3. **Erasure requests need a retention decision.** GDPR Article 17 applies in specified circumstances and has exceptions, including legal obligations and certain claims or public-interest purposes. A soft-deleted row remains stored personal data; assess the applicable rules and propagate required erasure to derived stores.

These three forces are in tension. The senior-level question is how to balance them.

## Soft Delete

### Definition

A row is "deleted" by setting a `deleted_at` timestamp. The row stays in the table. Queries filter on `deleted_at IS NULL` to exclude it.

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL,
  display_name TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ, -- NULL = active, NOT NULL = soft-deleted
  deleted_by BIGINT -- who deleted it (for audit)
);

-- Index for active rows (most queries hit this)
CREATE INDEX users_active_idx ON users (id) WHERE deleted_at IS NULL;
```

```sql
-- Soft delete
UPDATE users SET deleted_at = now(), deleted_by = $1 WHERE id = $2;

-- Restore (undo)
UPDATE users SET deleted_at = NULL, deleted_by = NULL WHERE id = $1;

-- Query active only
SELECT * FROM users WHERE id = $1 AND deleted_at IS NULL;

-- Query all (admin)
SELECT * FROM users WHERE id = $1;
```

### When to use

| Scenario | Soft delete? | Why |
| ---------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **User-initiated "delete my account"** | Depends on product and obligations | A restore window may be offered where appropriate; required erasure should not be delayed just to preserve undo. |
| **Content moderation (delete post)** | Yes | Audit, undo if moderator error |
| **Order / invoice deletion** | Follow the retention policy | Some records must be retained; others may be removable or redactable. |
| **Staging / test data** | Just hard delete | No retention need |
| **Erasure request** | Assess the applicable obligation | Remove or anonymize data where required; exceptions and retention duties can apply. |
| **Logically deleted but not yet purged** | Yes | Append-only, then a sweeper hard-deletes after retention window |

### When NOT to use

- **High-cardinality deletions.** If 95% of rows are soft-deleted (e.g. event log retention), the table is bloated. Use **partitioning + drop partition** instead.
- **Foreign key cascades.** Soft delete + cascade = deleted rows block their children forever. Orphans accumulate.
- **When a request requires erasure.** A soft-deleted row is still stored data. Apply the relevant retention and erasure policy rather than assuming the flag completes the request.

### Performance

**Consider a partial index when active-row queries need it.** Check the query plan and workload before adding one.

```sql
-- Without a suitable index, PostgreSQL may scan many rows. Check with EXPLAIN.
SELECT * FROM users WHERE email = $1 AND deleted_at IS NULL;

-- With partial index on active rows only:
CREATE INDEX users_active_email_idx ON users (email) WHERE deleted_at IS NULL;
-- This index contains active rows; confirm it helps the target query.
```

Other performance tips:
- **Consider partitioning or archival** when retention and table size justify the extra operational complexity.
- **Use a purge job only when policy allows it.** Make its retention period configurable, observable, and safe to retry.
- **Don't soft-delete high-write tables** (events, sessions). Use TTL + partition drop.

## Hard Delete

```sql
DELETE FROM users WHERE id = $1;
```

This removes the row from the table. The operation cannot be undone through the row itself; keep a separate audit record if policy requires one. PostgreSQL normally reclaims dead-row space through vacuum rather than immediately shrinking the table file.

Use when the data-retention policy calls for physical removal, such as expired test data or an erasure request that applies. A security incident may require disabling access, revoking credentials, preserving evidence, or removing specific data; it does not automatically mean deleting the entire account record.

### Example: reversible deletion followed by permanent removal

Some products allow an account to be restored for a defined period before removing its data. The example period below is illustrative, not a GDPR rule. Do not delay an erasure request when applicable obligations require prompt removal.

```text
t=0 User clicks "Delete my account" and the product policy allows a restore period
          → soft-delete: UPDATE users SET deleted_at = now()
          → publish `user.deleted` event
          → schedule removal for the configured restore-period end

t=0 to period end User can log in to "undo" (only soft-deleted user can)
          → if undo: UPDATE users SET deleted_at = NULL

t=period end Removal job:
          → DELETE FROM users WHERE deleted_at < now() - configured_period
          → DELETE FROM user_profiles WHERE user_id IN (...)
          → DELETE FROM user_orders_archive WHERE user_id IN (...)
          → Delete S3 keys (avatar, uploads)
          → Delete CDN cache (CloudFront invalidation)
          → Delete search index (Algolia / Elasticsearch)
          → Publish a deletion event if downstream systems need it
          → Record completion without retaining unnecessary personal data
```

Choose a restore period only after checking product needs and applicable obligations. A successful delete from the primary database does not prove every replica, backup or derived store has been erased.

**Watch out**: cascading hard delete must reach **every copy** of the data:
- Primary DB 
- Read replicas (replication catches up)
- Backups (define retention and what happens if a backup is restored)
- Cache (Redis) (must invalidate)
- Search index (Algolia / Elasticsearch) (must delete)
- Data warehouse (Snowflake / BigQuery) (must delete or use retention)
- Object storage (S3) (must delete or use retention)
- Logs (if you log the user.email anywhere) (must redact)

An erasure workflow must identify the applicable data and systems, perform required deletion or anonymization, handle replicas and derived stores, and record completion without retaining unnecessary personal data. The exact workflow depends on the system and applicable obligations.

## Tombstones

### Definition

A **tombstone** is a marker that says "this key was deleted" so a replica or compacted log does not treat an older value as current. Systems use different representations; not every CDC delete event is itself called a tombstone.

### Why tombstones exist

In a **change data capture (CDC) stream**, committed row changes are emitted as events such as `INSERT`, `UPDATE`, and `DELETE`. The consumer applies the delete to its own store. Some systems also use a tombstone marker for compaction or synchronization.

```json
{
  "before": { "id": 42, "email": "alice@example.com" },
  "after": null,
  "op": "d", // Debezium delete event envelope; distinct from a Kafka null-value tombstone
  "ts_ms": 1737158400000
}
```

Here, `after: null` is part of Debezium's delete-event envelope. It is not the same as Kafka's separate null-value tombstone record. **The consumer must apply the delete to its own store** (cache, search index, secondary DB), or its copy can remain.

### Deletion events in event-sourced systems

In an event log, "delete" is itself an event:

```json
{ "type": "UserDeleted", "userId": 42, "deletedAt": "2026-01-17T...", "reason": "gdpr" }
```

When the event store replays the log, the consumer applies the events. The `UserDeleted` event tells the read model "remove this user". The event itself stays in the log forever (immutable history), but the read model "forgets" the user.

The deletion event is part of the event history. A read model may remove the row, mark it deleted, or retain a minimal marker. Choose based on application needs and retention rules; the event itself is not automatically safe to keep forever.

### Tombstones in CDC

With Debezium, a database delete is emitted as a change event. Depending on connector configuration and the converter, Kafka may also receive a key with a null value (a Kafka tombstone) so log compaction can remove the prior keyed value. Consumers must apply the delete to their own stores; Kafka compaction markers and database delete events are related but distinct mechanisms.

```typescript
// Debezium consumer
await consumer.run({
  eachMessage: async ({ message }) => {
    const change = JSON.parse(message.value!.toString());
    if (change.op === "c" || change.op === "u") {
      // Insert or update
      await replicaDb.upsert(change.after);
    } else if (change.op === "d") {
      // Tombstone: hard-delete from the replica
      await replicaDb.delete(change.before.id);
    }
  },
});
```

If you have **soft delete in the source DB** (i.e. the source row's `deleted_at` is set, but the row is still there), Debezium publishes an `UPDATE` event — not a `DELETE`. The consumer sees a row with `deleted_at` set. **You must decide at the consumer: do I treat this as a hard delete or a soft delete?**

This is the most common CDC bug. The source does soft delete; the consumer's replica now has a "deleted" row. If the consumer's API queries that replica, it gets the soft-deleted record. **The bug is silent — only noticed in production.**

### Tombstones and the "lost delete" problem

In a **compacted log such as Kafka**, a tombstone must remain long enough for the consumers and recovery process that depend on it. If it expires before a consumer catches up, a rebuilt consumer may no longer learn that an older value was deleted:

```text
t=0 Consumer falls behind and still has the old value
t=1 Producer writes a delete marker for the key
t=2 The marker reaches its configured retention limit and is compacted away
t=3 Consumer rebuilds from the compacted log and cannot learn about the old value
t=4 The consumer may restore a stale copy from another source
```

For Kafka, configure `delete.retention.ms` to cover consumer and recovery needs. Cassandra uses tombstones for replica reconciliation; coordinate `gc_grace_seconds` with repair behavior and the cluster's recovery model. These settings solve related but different problems, so choose and test them for the actual topology.

### Deletion events and personal data

A deletion marker can still contain personal data. An identifier is not anonymous merely because it is hashed: if it can be linked back to a person using available information, it may remain identifiable. Minimize marker contents, define retention, and ensure consumers can process the delete before compaction removes it. Decide how backups and event histories are handled under the applicable policy.

## Soft Delete vs Hard Delete vs Tombstone

| Concept | Where it lives | What it means | Reversible? |
| --------------- | --------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| **Soft delete** | A column in the row (`deleted_at`) | "This row exists but is logically deleted" | Easy to undo |
| **Hard delete** | The row is removed | "This row is gone" | No undo (unless backups) |
| **Tombstone** | A deletion marker in a log or replicated data model | "Do not resurrect this older value" | The marker may expire under a retention or compaction policy |

**They can work together:** a product may mark a row inactive, later physically remove it when policy permits, and publish a deletion event so downstream stores can remove their copies. The timeline, marker contents, and required destinations depend on product behavior and retention obligations.

## Code Example

### Example deletion workflow with a configurable restore period

```typescript
// 1. User clicks "delete my account"
async function softDeleteUser(userId: string, deletedBy: string, restorePeriodEnd: Date) {
  return db.tx(async (tx) => {
    await tx.update(users)
      .set({ deletedAt: new Date(), deletedBy })
      .where(eq(users.id, userId));

    // Schedule a purge according to the configured product policy.
    await tx.insert(scheduledJobs).values({
      runAt: restorePeriodEnd,
      type: "hard-delete-user",
      payload: { userId, restorePeriodEnd },
    });

    // Publish event (outbox pattern)
    await tx.insert(outbox).values({
      aggregateId: userId,
      eventType: "user.soft_deleted",
      payload: { userId, deletedAt: new Date(), restorePeriodEnd },
    });
  });
}

// 2. User changes their mind
async function restoreUser(userId: string) {
  return db.tx(async (tx) => {
    await tx.update(users)
      .set({ deletedAt: null, deletedBy: null })
      .where(eq(users.id, userId));

    await tx.delete(scheduledJobs)
      .where(and(eq(scheduledJobs.type, "hard-delete-user"),
                 eq(scheduledJobs.payload.userId, userId)));

    await tx.insert(outbox).values({
      aggregateId: userId,
      eventType: "user.restored",
      payload: { userId },
    });
  });
}

// 3. At the configured purge time, remove data if policy permits.
async function hardDeleteExpiredUsers(purgeCutoff: Date) {
  const expired = await db.select().from(users)
    .where(lt(users.deletedAt, purgeCutoff));

  for (const user of expired) {
    await db.tx(async (tx) => {
      // Keep the deletion and durable event atomic. A worker handles external stores.
      await tx.delete(users).where(eq(users.id, user.id));
      await tx.insert(outbox).values({
        aggregateId: user.id,
        eventType: "user.purged",
        payload: { userId: user.id, purgedAt: new Date() },
      });
    });
  }
}
```

### CDC Consumer with Tombstone Handling

```typescript
// Pseudocode: adapt decoding to the connector and serialization configuration.
await consumer.run({
  eachMessage: async ({ topic, message }) => {
    const key = decodeKey(message.key);

    // Kafka compaction marker: null value for a key. It is distinct from
    // Debezium's JSON delete-event envelope, whose `op` is "d".
    if (message.value === null) {
      await replicaDb.delete(key.id);
      await searchIndex.delete(key.id);
      return;
    }

    const change = decodeDebeziumEvent(message.value);

    if (change.op === "c" || change.op === "u") {
      // Insert or update. This example treats soft-deleted rows as absent.
      if (change.after.deleted_at !== null) {
        await replicaDb.delete(change.after.id);
        await searchIndex.delete(change.after.id);
      } else {
        await replicaDb.upsert(change.after);
        await searchIndex.upsert(change.after);
      }
    } else if (change.op === "d") {
      // Database delete event; idempotently remove downstream copies.
      await replicaDb.delete(change.before.id);
      await searchIndex.delete(change.before.id);
    }
  },
});
```

The example omits query-builder setup and retry details. An idempotent worker should process the outbox event, retry external-store cleanup, and record completion. A CDC connector can also publish database deletes, but its configuration determines the event shape.

## Common Mistakes

- **Assuming a partial index is always needed.** Compare query plans and write costs; add an index when the active-row query benefits.
- **Treating a soft-delete flag as erasure.** The row and its personal data still exist. Assess applicable obligations and retention exceptions.
- **No cascade on hard delete.** `DELETE FROM users WHERE id = 1` orphans rows in `user_orders`, `user_profiles`, `user_uploads`. The DB rejects it; the app doesn't know.
- **Forgetting the search index.** "I deleted the user from the DB" — but Algolia still has them. They show up in search results for weeks.
- **Forgetting S3 / object storage.** User avatar still in S3. The URL still resolves.
- **Ignoring backups.** Document backup retention and what happens when restoring a backup that predates a deletion. The right approach depends on the storage design and applicable policy.
- **Ignoring soft-delete updates in CDC.** A `deleted_at` update is still an update event. Consumers must apply the same active/deleted policy as the source.
- **Tombstones with too-short retention.** Log compaction drops the tombstone before consumers have caught up. The consumer's data store has a ghost.
- **Soft delete on high-write tables.** Soft-deleting an events table bloats it. Use TTL + partition drop instead.
- **Assuming foreign-key cascades implement soft delete.** A database `ON DELETE` action runs on physical deletion, not when an application updates `deleted_at`; define child-row behavior explicitly.
- **No audit log of who deleted what.** Soft delete is the only record; if `deleted_by` is null, you have no idea.
- **Not testing the restore path.** "I clicked delete; I clicked undo; nothing happened." The restore is rarely tested.

## Best Practices

1. **Choose the deletion state deliberately.** Decide whether users need restore, whether records must remain for business reasons, and when physical removal applies.
2. **Set any restore period from product and policy requirements.** There is no universal duration.
3. **Use soft delete, hard delete, and deletion events only where each solves a real requirement.**
4. **Propagate deletion to derived stores.** Use durable events and idempotent consumers, with retries and observable completion.
5. **Capture who or what initiated deletion when useful and permitted.** Keep audit data to the minimum required by policy.
6. **Capture `deleted_reason`.** User action, GDPR request, moderation, etc. For audit.
7. **Test the restore path.** Verify permissions, related records and concurrent updates as well as the basic undo.
8. **Test the deletion fan-out.** Simulate downstream failures. Does the worker retry safely, and can operators see partial completion?
9. **For deletion markers in compacted logs:** set retention to cover consumer lag and recovery needs, then test replay behavior.
10. **Minimize identifiers in deletion markers.** Hashing alone does not guarantee anonymization.
11. **Document the retention policy** for every "deleted" record: when is it soft-deleted, when hard-deleted, when the audit log itself is purged.
12. **Handle applicable erasure requests as an end-to-end workflow.** Include source data, derived stores, backups, retries, and completion evidence.

## Performance Considerations

| Concern | Soft delete | Hard delete | Tombstone |
| ---------------- | ------------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------- |
| Query overhead | Depends on filters, index design, and data distribution | Depends on constraints and cascades | N/A |
| Storage overhead | All deleted rows retained | None | Event log grows |
| Index size | Partial: small. Without: bloated | N/A | N/A |
| Write throughput | Slightly slower (extra column) | Slightly slower (FK cascade) | 0 |
| Backup size | Same as table (deleted rows included) | Smaller after sweep | N/A |
| CDC stream | `UPDATE` event when `deleted_at` changes | `DELETE` event for physical row removal | Separate log or replication marker, depending on the system |

## Summary

- **Soft delete** = `deleted_at` column. Reversible by the application; it does not physically remove stored data.
- **Hard delete** = `DELETE` statement. The row is removed from that store; broader erasure depends on policy and other copies.
- **Tombstone** = a system-specific deletion marker that prevents an older value from reappearing.
- **Possible workflow**: mark inactive, later remove data when policy allows, and notify downstream stores that need to remove their copies.
- **Performance**: index active-row queries when measurements show a benefit; account for added write and storage costs.
- **Erasure**: a soft-delete flag alone does not remove data. Apply the requirements and exceptions that fit the case, including relevant replicas and derived stores.
- **In interviews: explain the product's deletion semantics, retention constraints, downstream propagation, and measured query trade-offs.**

# Soft Delete & Tombstones

> **Hard delete is the easy choice — until you need to undo, audit, comply with GDPR, or replicate via CDC.** Soft delete = mark the row as deleted (with a `deleted_at` timestamp) but keep it. Tombstones = a special marker for "this record existed and is now gone" used in event logs, CDC streams, and event-sourced systems. The two patterns solve different problems, but they're commonly confused. This file covers when to use each, the trade-offs, the implementation patterns, the GDPR interaction (which is the senior-level question), and the cross-system replication implications.

## Definition

**Soft delete**, **hard delete**, and **tombstones** are three answers to "what should happen to a row when the user deletes it", differing in **what state remains in the store**:

```text
                 row remains?   what remains                      can be read as live?
hard delete      no             nothing (row + children gone)     n/a
soft delete      yes            deleted_at IS NOT NULL            no (needs a filter)
tombstone        yes (marker)   id + deleted_at, no payload       no; propagates deletion
                                (sync/CRDT, distributed systems)
```

The choice is not cosmetic — each defines a different set of obligations:

1. **Soft delete buys undo, audit, and referential safety** at the cost of a mandatory filter. Every query, unique constraint, count, and join must now say what it means — `deleted_at IS NULL` (or worse, `deleted_at IS NULL OR deleted_at > …` for grace windows). The two failure modes are a forgotten filter (deleted records appearing in lists) and a unique index that ignores the flag (so a re-registered email collides with a soft-deleted user — solved by a **partial unique index** on `deleted_at IS NULL`).
2. **Hard delete is required where retention is forbidden** — GDPR's right to erasure and security incidents demand actual removal, and "we soft-deleted it" is not compliance. It also keeps the working set small, which matters because soft-deleted rows still occupy indexes and buffers.
3. **A tombstone is a deletion *fact*, not a flag** — in sync, replication, or multi-region (CRDT) systems, "the record is gone" must be communicated, otherwise a node that still has the old copy will re-introduce it on the next sync. A tombstone therefore needs a TTL/compaction policy of its own, and it is what keeps deletes *causally* correct.

The realistic production pattern is per-table policy rather than one global choice: soft delete for user-generated content (undo window + moderation), hard delete plus tombstone propagation for personal data (erasure), and a retention job that converts soft-deleted rows to hard-deleted ones once the grace period and derived copies (caches, search index, warehouse) have been purged.

## First Principles

Soft delete exists because deletion has consequences beyond the row:

1. **DELETE is irreversible and referentially violent.** FKs cascade or block, audits lose their subject, and "undo" is impossible. Keeping the row and flagging `deleted_at` preserves history, enables restore, and makes deletes as cheap as an UPDATE.
2. **The cost: every query must now exclude the dead.** Forget one WHERE and ghosts appear in prod. The mitigations (views, default scopes, RLS (→ 20.4.1.06)) each move the filter somewhere it can't be forgotten — the same "make it structural, not remembered" principle.
3. **Tombstones are the replication/sync answer**: a delete must propagate as *data*, because an absence cannot be replicated. This is why event systems and sync engines speak of tombstones — deletion is information.

## Why it matters

Three forces pull at the "what does delete mean?" question:

1. **Users want undo.** "I accidentally deleted the wrong project. Can you bring it back?" Soft delete makes this trivial.
2. **Auditors want a trail.** "Who deleted this order? When?" Hard delete loses that.
3. **GDPR says "really, really gone".** The "right to erasure" (Article 17) means the data subject can demand deletion, and **soft-deleted rows still count as personal data**. A soft-deleted user record is still in the database.

These three forces are in tension. The senior-level question is how to balance them.

## Soft Delete

### Definition

A row is "deleted" by setting a `deleted_at` timestamp. The row stays in the table. Queries filter on `deleted_at IS NULL` to exclude it.

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL,
  display_name TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ, -- NULL = active, NOT NULL = soft-deleted
  deleted_by BIGINT -- who deleted it (for audit)
);

-- Index for active rows (most queries hit this)
CREATE INDEX users_active_idx ON users (id) WHERE deleted_at IS NULL;
```

```sql
-- Soft delete
UPDATE users SET deleted_at = now(), deleted_by = $1 WHERE id = $2;

-- Restore (undo)
UPDATE users SET deleted_at = NULL, deleted_by = NULL WHERE id = $1;

-- Query active only
SELECT * FROM users WHERE id = $1 AND deleted_at IS NULL;

-- Query all (admin)
SELECT * FROM users WHERE id = $1;
```

### When to use

| Scenario | Soft delete? | Why |
| ---------------------------------------- | ----------------------- | --------------------------------------------------------------- |
| **User-initiated "delete my account"** | Yes (with 30-day grace) | Allows undo. Becomes hard delete after grace period. |
| **Content moderation (delete post)** | Yes | Audit, undo if moderator error |
| **Order / invoice deletion** | Never hard delete | Finance / legal retention. |
| **Staging / test data** | Just hard delete | No retention need |
| **GDPR right-to-erasure** | Becomes hard delete | "Deleted" must mean gone. |
| **Logically deleted but not yet purged** | Yes | Append-only, then a sweeper hard-deletes after retention window |

### When NOT to use

- **High-cardinality deletions.** If 95% of rows are soft-deleted (e.g. event log retention), the table is bloated. Use **partitioning + drop partition** instead.
- **Foreign key cascades.** Soft delete + cascade = deleted rows block their children forever. Orphans accumulate.
- **GDPR before the erasure window.** Soft-deleted rows are still personal data; you can't keep them past the user's request.

### Performance

**The number one mistake: no partial index.**

```sql
-- Without partial index: every query on `WHERE deleted_at IS NULL`
-- scans the full table (or uses a non-selective index).
SELECT * FROM users WHERE email = $1 AND deleted_at IS NULL;
-- Index on email matches both active AND deleted rows; PG picks the wrong one.

-- With partial index on active rows only:
CREATE INDEX users_active_email_idx ON users (email) WHERE deleted_at IS NULL;
-- Index is small (only active rows); queries are fast.
```

Other performance tips:
- **Move soft-deleted rows to a partition.** `users_active` (no deleted rows) + `users_deleted` (audit / undo). Queries hit only the active partition.
- **Use a sweep job.** Run a daily cron: `DELETE FROM users WHERE deleted_at < now() - interval '30 days'`. After 30 days, soft-deleted rows become hard-deleted.
- **Don't soft-delete high-write tables** (events, sessions). Use TTL + partition drop.

## Hard Delete

```sql
DELETE FROM users WHERE id = $1;
```

Trivial. The row is gone. **No undo. No audit trail. Storage is reclaimed.**

Use for:
- **GDPR right-to-erasure** (mandatory).
- **Security incident** (a compromised account must be purged).
- **Data the user has no right to retain** (test data, logs past retention).
- **The end of the soft-delete grace period.**

### The GDPR Hard-Soft-Hard Pattern

For "delete my account" features, the production pattern is:

```text
t=0 User clicks "Delete my account"
          → soft-delete: UPDATE users SET deleted_at = now()
          → publish `user.deleted` event
          → schedule hard-delete for t=30 days

t=0-30d User can log in to "undo" (only soft-deleted user can)
          → if undo: UPDATE users SET deleted_at = NULL

t=30d Hard delete job:
          → DELETE FROM users WHERE deleted_at < now() - interval '30 days'
          → DELETE FROM user_profiles WHERE user_id IN (...)
          → DELETE FROM user_orders_archive WHERE user_id IN (...)
          → Delete S3 keys (avatar, uploads)
          → Delete CDN cache (CloudFront invalidation)
          → Delete search index (Algolia / Elasticsearch)
          → Publish `user.purged` event
          → Audit log: "user X purged at t=30d"
```

**The 30-day grace** matches user expectations (most SaaS use 14-30 days). After it, the data is truly gone.

**Watch out**: cascading hard delete must reach **every copy** of the data:
- Primary DB 
- Read replicas (replication catches up)
- Backups (the row is in yesterday's backup, possibly forever — this is a known GDPR tension)
- Cache (Redis) (must invalidate)
- Search index (Algolia / Elasticsearch) (must delete)
- Data warehouse (Snowflake / BigQuery) (must delete or use retention)
- Object storage (S3) (must delete or use retention)
- Logs (if you log the user.email anywhere) (must redact)

The "GDPR deletion" interview answer is rarely "we run a DELETE". It's "we run a DELETE on the primary + a Kafka event that fans out to every downstream system, with audit logs of the deletion".

## Tombstones

### Definition

A **tombstone** is a special marker that says "this record existed and is now gone". It's the way **event logs, CDC streams, and event-sourced systems** represent deletion.

### Why tombstones exist

In a **CDC stream**, every committed row change is a message: `INSERT`, `UPDATE`, `DELETE`. The `DELETE` event is the tombstone. The consumer must process it to know the row is gone.

```json
{
  "before": { "id": 42, "email": "alice@example.com" },
  "after": null,
  "op": "d", // delete
  "ts_ms": 1737158400000
}
```

The `after: null` is the tombstone. **The consumer must propagate this to its own data store** (cache, search index, secondary DB) — otherwise the row stays there forever.

### Tombstones in event-sourced systems

In an event log, "delete" is itself an event:

```json
{ "type": "UserDeleted", "userId": 42, "deletedAt": "2026-01-17T...", "reason": "gdpr" }
```

When the event store replays the log, the consumer applies the events. The `UserDeleted` event tells the read model "remove this user". The event itself stays in the log forever (immutable history), but the read model "forgets" the user.

**Key insight:** in event-sourced systems, the **tombstone is in the read model**, not the log. The log is append-only; the read model is what reflects current state.

### Tombstones in CDC

If you use Debezium to replicate a Postgres DB to Kafka, every `DELETE` becomes a Kafka message. The consumer must:
1. Apply the deletion to its data store (cache, search index, etc.).
2. Eventually hard-delete the row from the consumer's data store.
3. **NOT** lose the tombstone — if you do, the data store will have a "ghost" row that should have been deleted.

```typescript
// Debezium consumer
await consumer.run({
  eachMessage: async ({ message }) => {
    const change = JSON.parse(message.value!.toString());
    if (change.op === "c" || change.op === "u") {
      // Insert or update
      await replicaDb.upsert(change.after);
    } else if (change.op === "d") {
      // Tombstone: hard-delete from the replica
      await replicaDb.delete(change.before.id);
    }
  },
});
```

If you have **soft delete in the source DB** (i.e. the source row's `deleted_at` is set, but the row is still there), Debezium publishes an `UPDATE` event — not a `DELETE`. The consumer sees a row with `deleted_at` set. **You must decide at the consumer: do I treat this as a hard delete or a soft delete?**

This is the most common CDC bug. The source does soft delete; the consumer's replica now has a "deleted" row. If the consumer's API queries that replica, it gets the soft-deleted record. **The bug is silent — only noticed in production.**

### Tombstones and the "lost delete" problem

In a **distributed log with compaction** (e.g. Kafka with log compaction, or Cassandra with TTL'd tombstones), the tombstone must outlive the consumers' processing window. Otherwise:

```text
t=0 Producer writes `delete` event
t=0 Log compaction runs immediately, sees no recent UPDATE for the key,
     decides to compact the delete away
t=1 Consumer reads the log, never sees the delete
t=2 Consumer's replica has a ghost row
```

**Rule:** tombstones must be retained for **at least the consumer's max processing time** (typically 7-30 days). Kafka `delete.retention.ms`; Cassandra `gc_grace_seconds`.

### Tombstones and "right to be forgotten"

GDPR + tombstones is interesting: the user says "delete my data". You do a soft delete (with 30-day grace), then hard delete. The tombstone in the **CDC stream** says "this row is gone". But:
- The tombstone in the **event log** is personal data? Arguably not (it has user_id but no email). But if the user_id is itself PII (because the company's user_id is derivable to a person), then yes.
- **Most production systems** either:
  1. **Pseudonymize** the user_id in the tombstone (replace with a one-way hash that's not reversible to a person), or
  2. **Don't tombstone**; use compaction + retention to ensure the delete is propagated and then dropped.

## Soft Delete vs Hard Delete vs Tombstone

| Concept | Where it lives | What it means | Reversible? |
| --------------- | ---------------------------------- | ------------------------------------------ | -------------------------------------------------- |
| **Soft delete** | A column in the row (`deleted_at`) | "This row exists but is logically deleted" | Easy to undo |
| **Hard delete** | The row is removed | "This row is gone" | No undo (unless backups) |
| **Tombstone** | An event in a log / CDC stream | "This row existed and is now gone" | The event is permanent; the data state reflects it |

**They work together:**
- Source DB uses **soft delete** for the 30-day grace.
- After 30 days, **hard delete** runs.
- The hard delete emits a **tombstone** via CDC.
- Downstream services (search, cache, warehouse) receive the tombstone and remove the data.

## Code Example

### Full Soft-Delete + Grace-Period + Hard-Delete Pipeline

```typescript
// 1. User clicks "delete my account"
async function softDeleteUser(userId: string, deletedBy: string) {
  return db.tx(async (tx) => {
    await tx.update(users)
      .set({ deletedAt: new Date(), deletedBy })
      .where(eq(users.id, userId));

    // Schedule hard delete (30 days from now)
    await tx.insert(scheduledJobs).values({
      runAt: new Date(Date.now() + 30 * 24 * 60 * 60 * 1000),
      type: "hard-delete-user",
      payload: { userId },
    });

    // Publish event (outbox pattern)
    await tx.insert(outbox).values({
      aggregateId: userId,
      eventType: "user.soft_deleted",
      payload: { userId, deletedAt: new Date(), graceUntil: ... },
    });
  });
}

// 2. User changes their mind
async function restoreUser(userId: string) {
  return db.tx(async (tx) => {
    await tx.update(users)
      .set({ deletedAt: null, deletedBy: null })
      .where(eq(users.id, userId));

    await tx.delete(scheduledJobs)
      .where(and(eq(scheduledJobs.type, "hard-delete-user"),
                 eq(scheduledJobs.payload.userId, userId)));

    await tx.insert(outbox).values({
      aggregateId: userId,
      eventType: "user.restored",
      payload: { userId },
    });
  });
}

// 3. After 30 days, hard delete (sweeper job)
async function hardDeleteExpiredUsers() {
  const expired = await db.select().from(users)
    .where(lt(users.deletedAt, new Date(Date.now() - 30 * 24 * 60 * 60 * 1000)));

  for (const user of expired) {
    // 1. Hard delete from primary
    await db.delete(users).where(eq(users.id, user.id));

    // 2. The CDC stream emits a tombstone automatically
    // (if Debezium is configured for op=d events)

    // 3. Or emit an explicit tombstone event for downstream services
    await outbox.insert({
      aggregateId: user.id,
      eventType: "user.purged", // tombstone
      payload: { userId: user.id, purgedAt: new Date() },
    });

    // 4. Delete ancillary data: S3, Algolia, etc.
    await s3.deleteObjectsByPrefix(`users/${user.id}/`);
    await algolia.deleteObject(`users/${user.id}`);
    await redis.del(`user:${user.id}`);

    // 5. Audit log
    await auditLog.append({
      type: "user.purged",
      userId: user.id,
      by: "system.sweeper",
    });
  }
}
```

### CDC Consumer with Tombstone Handling

```typescript
// Debezium CDC consumer
await consumer.run({
  eachMessage: async ({ topic, message }) => {
    const change = JSON.parse(message.value!.toString());

    if (change.op === "c" || change.op === "u") {
      // Insert or update — apply to replica + downstream
      await replicaDb.upsert(change.after);

      // Skip rows that are soft-deleted in the source
      if (change.after.deleted_at !== null) {
        // Treat as tombstone: hard delete from replica
        await replicaDb.delete(change.after.id);
        await searchIndex.delete(change.after.id);
      } else {
        await searchIndex.upsert(change.after);
      }
    } else if (change.op === "d") {
      // Hard delete from source — propagates as tombstone
      await replicaDb.delete(change.before.id);
      await searchIndex.delete(change.before.id);
    }
  },
});
```

## Common Mistakes

- **Soft-delete without partial index.** Every query scans the full table. Slows down by 10-100× as the deleted-row pile grows.
- **Soft-delete and calling it GDPR-compliant.** It's not. The regulator will fine you.
- **No cascade on hard delete.** `DELETE FROM users WHERE id = 1` orphans rows in `user_orders`, `user_profiles`, `user_uploads`. The DB rejects it; the app doesn't know.
- **Forgetting the search index.** "I deleted the user from the DB" — but Algolia still has them. They show up in search results for weeks.
- **Forgetting S3 / object storage.** User avatar still in S3. The URL still resolves.
- **Forgetting backups.** The row is in yesterday's backup. The GDPR question is "what's your backup retention / erasure process?" The answer is usually "encrypted backups with a deletion key, and we rotate the key on erasure" — but most companies don't have this.
- **No tombstones in CDC.** Soft-delete in the source; the CDC consumer's replica still has the row. Ghost users in the search index.
- **Tombstones with too-short retention.** Log compaction drops the tombstone before consumers have caught up. The consumer's data store has a ghost.
- **Soft delete on high-write tables.** Soft-deleting an events table bloats it. Use TTL + partition drop instead.
- **Soft delete + FK cascade.** Soft-deleted parent + cascaded children = everyone is soft-deleted. Orphans accumulate.
- **No audit log of who deleted what.** Soft delete is the only record; if `deleted_by` is null, you have no idea.
- **Not testing the restore path.** "I clicked delete; I clicked undo; nothing happened." The restore is rarely tested.

## Best Practices

1. **Always use a partial index on the active set.** `WHERE deleted_at IS NULL`. Don't soft-delete without it.
2. **Set a grace period.** 14-30 days for "delete my account" features. Match user expectations.
3. **Combine soft + hard + tombstone.** Soft for undo, hard for GDPR, tombstone for CDC.
4. **Fan out the hard delete.** Primary DB, search index, cache, object storage, warehouse, audit log. One event, many consumers.
5. **Capture `deleted_by`.** Audit. Required for most compliance regimes.
6. **Capture `deleted_reason`.** User action, GDPR request, moderation, etc. For audit.
7. **Test the restore path.** It almost never works on the first try.
8. **Test the hard-delete fan-out.** Use Toxiproxy. Kill S3. Kill Algolia. Does the sweeper retry? Does the audit log reflect partial completion?
9. **For tombstones in compacted logs:** set retention > max consumer lag. Default: 7 days for most systems; 30 days for compliance-heavy.
10. **Pseudonymize the user_id in tombstones** if your user_id is itself PII.
11. **Document the retention policy** for every "deleted" record: when is it soft-deleted, when hard-deleted, when the audit log itself is purged.
12. **Handle the GDPR "right to erasure"** as a single workflow: soft-delete → grace → hard-delete → fan-out → audit.

## Performance Considerations

| Concern | Soft delete | Hard delete | Tombstone |
| ---------------- | ------------------------------------------- | ---------------------------- | --------------- |
| Query overhead | +0ms (with partial index), +50ms+ (without) | 0 | N/A |
| Storage overhead | All deleted rows retained | None | Event log grows |
| Index size | Partial: small. Without: bloated | N/A | N/A |
| Write throughput | Slightly slower (extra column) | Slightly slower (FK cascade) | 0 |
| Backup size | Same as table (deleted rows included) | Smaller after sweep | N/A |
| CDC stream | `UPDATE` events for soft-delete | `DELETE` events (tombstone) | `DELETE` events |

## Summary

- **Soft delete** = `deleted_at` column. Reversible. Doesn't satisfy GDPR by itself.
- **Hard delete** = `DELETE` statement. Irreversible. Required for GDPR.
- **Tombstone** = a marker in a log/CDC stream that says "this record is gone". The way CDC propagates deletion.
- **The full pattern**: soft-delete → grace period → hard delete → fan-out tombstone to all downstream systems.
- **Performance**: partial index on `deleted_at IS NULL` is mandatory. Without it, queries slow as the deleted pile grows.
- **GDPR**: soft delete is not enough. You must hard-delete (and propagate the tombstone to every copy of the data).
- **In interviews: name the retention requirement, name the GDPR interaction, name the replication impact, name the performance fix.**

# Soft Delete & Tombstones

A restore request can race a scheduled purge, while another account reuses the deleted user’s email. The flag alone cannot protect either lifecycle: the purge must recheck which deletion cycle it belongs to, and restoration must satisfy current uniqueness and authorization rules.

## Definition

Deletion is a lifecycle transition with several possible owners. An application can mark a retained row inactive (**soft deletion**), remove a row from its live store (**hard deletion**), or publish a marker telling another store that a key was deleted (**a tombstone**). These mechanisms can work together, but each establishes a different result.

> **Textbook Definition:** Soft deletion marks retained data inactive; hard deletion removes a live record; tombstones represent deletion for synchronization or log compaction. Visibility, restoration, retention and propagation rules determine each mechanism's guarantees.

## First Principles

A user deleting a project might want undo, while another service still needs to remove its search copy. Removing the primary row does not tell that service what happened unless it receives a deletion fact or rebuilds from an authoritative snapshot. Keeping the row for undo, however, requires every live-data access to exclude it deliberately.

A purge job introduces concurrency: it can read a row as expired while the user restores it. If the job later deletes solely by ID, it removes the restored account. The deletion state must therefore be revalidated at the mutation, and an old scheduled job must not match a later deletion cycle.

Retention is another independent condition. A soft-deleted row still contains stored data. Whether personal data must be erased or may be retained depends on the applicable request, purpose and retention obligations; a flag is not evidence of erasure.

## Follow one deletion through restore, purge and propagation

### Follow one deletion cycle through restoration or purge

```text
active → mark inactive + record durable event → restore window
                      │                              ├→ restore active
                      │                              └→ eligible purge
                      ↓                                     │
               derived stores update              recheck state + generation
                                                            ↓
                                                   delete + durable event
                                                            ↓
                                             downstream cleanup/retry evidence
```

A deletion **generation** identifies the lifecycle state a job observed. Increment it on deletion/restoration so a job for an older cycle cannot act on the new one. A purge checks the current inactive flag, current deadline and expected generation in one protected operation. Every writer of these fields must follow the protocol.

A durable event can be appended in the same database transaction as a lifecycle mutation. Delivery happens afterward; it can be duplicated or delayed. Downstream consumers need idempotency and ordering rules, while the user-facing outcome must distinguish “inactive in the owner” from “purged everywhere.” The [outbox chapter](../../20.6-microservices/03-data-and-consistency/20.6.3.06-transactional-outbox.md) owns the delivery mechanism.

### Retained rows change references, uniqueness and access

Soft deletion is an UPDATE. A foreign key still sees an existing parent, and an ON DELETE action does not run. Decide whether children become inactive, remain visible to authorized users, or must prevent parent restoration/purge. Hard deletion invokes the configured foreign-key actions: it can be blocked, cascade or apply another rule; children do not automatically disappear.

A unique email constraint covering every row reserves the email even after soft deletion. A **partial unique index** covering only active rows lets a new account reuse it. Restoration can then fail because an active replacement owns the same email. That is a product conflict to resolve, not permission to silently replace the new account.

Live queries, relations, counts, exports and raw SQL must all follow the intended visibility policy. A view or repository helper can centralize it; RLS can participate in an explicit access policy but is not an automatic soft-delete rule. Restoration must also recheck authorization and related state. Revoked credentials or sessions must not be revived accidentally.

## Make lifecycle transitions conditional and durable

### Make the lifecycle and email rule explicit

Use PostgreSQL 16+ in a fresh disposable schema. The ten-minute restore period is only a fixture choice, not a required product or legal period.

```sql
CREATE TABLE deletion_users (
    id integer PRIMARY KEY,
    email text NOT NULL,
    deleted_at timestamptz,
    purge_after timestamptz,
    deletion_generation bigint NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX deletion_active_email
ON deletion_users(email) WHERE deleted_at IS NULL;
CREATE TABLE deletion_outbox (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type text NOT NULL,
    user_id integer NOT NULL,
    generation bigint NOT NULL
);
INSERT INTO deletion_users(id, email) VALUES (1, 'ada@example.test');
```

This index uses exact email equality; normalization/case rules are a separate chosen policy. The outbox deliberately has no foreign key to a soon-purged user, because the durable deletion event must survive removal of its subject. Its identifier/retention still need a privacy policy.

### Mark inactive and record intent atomically

```sql
WITH marked AS (
    UPDATE deletion_users
    SET deleted_at = now(), purge_after = now() + interval '10 minutes',
        deletion_generation = deletion_generation + 1
    WHERE id = 1 AND deleted_at IS NULL
    RETURNING id, deletion_generation
)
INSERT INTO deletion_outbox(event_type, user_id, generation)
SELECT 'user.inactive', id, deletion_generation FROM marked;

SELECT id, deleted_at IS NULL AS active, deletion_generation
FROM deletion_users WHERE id = 1;
-- 1 | false | 1
```

The row transition and event are one statement transaction. Repeating it while already inactive affects no row and appends no new event. An authorized worker can schedule a purge carrying ID 1 and generation 1; it must use the current database deadline at execution rather than trusting only a previously read schedule.

### Restore, then reject the stale purge job

```sql
WITH restored AS (
    UPDATE deletion_users
    SET deleted_at = NULL, purge_after = NULL,
        deletion_generation = deletion_generation + 1
    WHERE id = 1 AND deleted_at IS NOT NULL
    RETURNING id, deletion_generation
)
INSERT INTO deletion_outbox(event_type, user_id, generation)
SELECT 'user.restored', id, deletion_generation FROM restored;

-- A job captured generation 1, but the row is now active at generation 2.
WITH removed AS (
    DELETE FROM deletion_users
    WHERE id = 1
      AND deletion_generation = 1
      AND deleted_at IS NOT NULL
      AND purge_after <= now()
    RETURNING id, deletion_generation
)
INSERT INTO deletion_outbox(event_type, user_id, generation)
SELECT 'user.purged', id, deletion_generation FROM removed;

SELECT id, deleted_at IS NULL AS active, deletion_generation
FROM deletion_users WHERE id = 1;
-- 1 | true | 2
```

The stale job removes nothing and publishes no purge event. If the user deletes again, the new generation also prevents this old job from removing that later lifecycle. Competing restore/purge statements serialize on the row; only a mutation whose current conditions pass can act. If purge wins and commits first, there is no retained row to restore. The API must state that boundary rather than promising undo after completed purge.

A production purge includes permitted child cleanup and the durable event in the same transaction. Remote object/search deletions occur through an idempotent worker with observable retries, not inside a rollback promise that the database cannot fulfill.

### Observe active-key reuse and the restoration conflict

After the restoration above, mark user 1 inactive again, then insert an active replacement with the same email:

```sql
UPDATE deletion_users
SET deleted_at = now(), purge_after = now() + interval '10 minutes',
    deletion_generation = deletion_generation + 1
WHERE id = 1;
INSERT INTO deletion_users(id, email) VALUES (2, 'ada@example.test');

BEGIN;
UPDATE deletion_users SET deleted_at = NULL, purge_after = NULL,
    deletion_generation = deletion_generation + 1
WHERE id = 1;
-- ERROR: unique violation (SQLSTATE 23505)
ROLLBACK;
```

The final block is a fixture to demonstrate the constraint; the earlier atomic event pattern remains the production mutation contract. User 1 stays inactive, and user 2 remains active. Resolve restoration using an authorized product policy, such as selecting another verified address; do not delete or merge accounts based solely on matching text.

## Tombstones and Downstream Copies

### Distinguish a database delete event from a compaction marker

**Change data capture (CDC)** publishes committed database changes. A Debezium PostgreSQL delete envelope uses `op: "d"` and `after: null`, with key/before information determined by connector and replica-identity configuration. It is distinct from a Kafka record whose **whole value is null** for a key, the log-compaction tombstone.

A soft-delete UPDATE is an update event, not a database DELETE. A consumer must decide whether to retain an inactive representation or remove it from its live index. Snapshot/read events also need handling when initializing a consumer. The following is a decoder/state-machine outline, not a complete vendor client:

```text
decode key and connector envelope under the configured serialization contract
if whole value is null:
    handle keyed compaction deletion according to the consumer contract
else if event represents create/update/snapshot:
    if source row is inactive: apply derived-store deletion
    else: apply upsert
else if event represents database delete:
    apply deletion from trusted key/before identity
acknowledge progress only after the required effects are durable
```

An upsert/delete being individually idempotent is not enough for ordering: an old upsert arriving after a newer delete can resurrect data. Serialize per key or retain a version/deletion watermark that rejects older events, and define snapshot/replay behavior. A deleted document's version may disappear with it, so a separate marker or authoritative current-state check can be necessary.

### Retention must cover consumer lag and rebuilding

Kafka compaction retains keyed current state and eventually removes deletion markers according to its configuration. A consumer with an existing stale store can miss a tombstone if it falls behind beyond the marker-retention window. By contrast, rebuilding into an empty store from a complete valid current-state snapshot does not require every historical deletion to be present.

Choose `delete.retention.ms` and the replay/recovery procedure together; it is not a general permanent-delete memory. Cassandra tombstone/repair rules use a different mechanism and must follow that product's topology and repair contract rather than borrowing Kafka settings. Event-sourced histories also have separate retention and privacy requirements: a UserDeleted event may remove a read model while personal data in earlier events still remains.

## Set retention across personal and derived data

Choose a restore window only when product and retention requirements permit it. GDPR's erasure right has conditions and exceptions; retained personal data remains stored despite logical inactivity. Identify which facts may remain, which must be removed or appropriately anonymized, and how to handle derived stores and restored backups under the applicable policy.

Inventory primary tables, replicas, caches, search, objects, logs, exports and event history. Record completion per destination so a failed object delete does not look like full erasure. Keep deletion markers and audit payloads minimal: a hash or identifier that can still be linked to a person is not automatically anonymous.

For high-volume expiry, partition removal or TTL mechanisms can fit retention boundaries better than retaining every inactive row. They have their own locking, propagation and recovery contracts. A fixed deleted-row percentage or write rate alone does not decide the model; measure table/index cost, query behavior and required restoration.

In PostgreSQL, `DELETE` leaves dead row versions for vacuum to reclaim. Compare that cleanup and index cost with the storage and write cost of retaining inactive rows; neither approach is free.

## Summary

Soft deletion retains data under an explicit live/restore policy; hard deletion removes a row subject to its relationships; tombstones communicate deletion to other owners. Revalidate a purge's current lifecycle and generation, decide how uniqueness and references affect undo, and define durable ordered propagation. Completion and erasure require evidence across the relevant stores, not a single flag or successful DELETE.

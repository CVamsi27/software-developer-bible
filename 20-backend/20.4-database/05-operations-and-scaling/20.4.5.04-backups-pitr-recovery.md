# Backups, PITR & Recovery

> **TL;DR:** A backup is only real if you have restored it. Logical dumps (`pg_dump`) protect against logic errors and ease cross-version moves but are slow to restore; physical base backups + WAL archiving give you Point-In-Time Recovery (PITR) to any second — `recovery_target_time` — with RPO measured in minutes or less. Production Postgres runs pgBackRest or WAL-G: scheduled full/differential/incremental backups, continuous WAL shipping to object storage, retention policies, and — non-negotiably — automated restore drills. Choose targets by writing down your RPO (how much data may vanish) and RTO (how long you may be down) first.
>
> **Why it matters:** "We take nightly pg_dumps" is the junior answer. The senior answer names the tool, the WAL pipeline, the restore time for a 500 GB database, where copies live (cross-region, immutable), and when the last drill ran.

## Definition

**Backup and recovery strategy for Postgres** combines:

- **Logical backups** — `pg_dump` / `pg_restore`: SQL-level export of schema + data; portable across versions/platforms; restore = replay all statements.
- **Physical backups** — byte-level copy of the data directory at a checkpoint (pg_basebackup, pgBackRest full/incr backups); restore fast, same-major-version bound.
- **WAL archiving** — every write-ahead-log segment (16 MB default) shipped to durable storage as the primary generates it; the delta between base backup and any moment in time.
- **PITR** — restore a base backup, then **replay archived WAL up to an exact target** (`recovery_target_time`, `recovery_target_lsn`), stopping precisely at "one second before the `DROP TABLE`".
- **RPO / RTO** — Recovery Point Objective: maximum tolerable data loss window. Recovery Time Objective: maximum tolerable downtime. Every tooling choice derives from these two numbers.

```text
Timeline ───────────────────────────────────────────────────────────►
            ▲full backup        ▲diff backup      ▲DISASTER
            │                   │                 │ desired recovery point
   WAL: ──[16MB]─[16MB]─[16MB]─[16MB]─[16MB]─[16MB]──► archive storage
                                                        │
   Restore: base backup + WAL replay ───────────────────┘ recovery_target_time
```

## Why Do We Need It?

1. **Human error dominates** — `DROP TABLE` without `WHERE`, bad migrations, batch UPDATEs gone wrong. Replicas replicate the mistake instantly; only PITR rewinds it.
2. **Replication is not a backup** — a standby faithfully applies the destructive transaction too; logical corruption needs independent history.
3. **Compliance mandates shape retention** — SOC 2/ISO 27001/PCI require documented retention, encryption, immutability, and tested restores.
4. **Cloud outages are zonal/regional** — cross-region copies turn "region down" from existential to an RTO line item.
5. **Ransomware targets backups first** — immutable (object-lock) buckets and separated credentials decide whether you pay.
6. **Restore speed is architecture** — a 2 TB `pg_restore` can take days; physical restore + WAL roll-forward takes hours; that difference IS your RTO.

## How It Works

### WAL archiving pipeline

```text
Postgres primary
  │ writes WAL segments (pg_wal/)
  │ archive_command / archive_mode=on
  ▼
pgBackRest / WAL-G agent
  │ compress (zstd/lz4) + encrypt + checksum
  ▼
Object storage (S3/GCS/Azure) ── versioning + object-lock (WORM)
  ├── repo/backup/  full|diff|incr base backups (scheduled)
  └── repo/wal/     continuous segments     (continuous)

Standby (optional): streaming replication keeps warm copy;
backups may be taken FROM the standby to offload the primary.
```

`archive_command = 'pgbackrest --stanza=app archive-push %p'` (or the WAL-G equivalent) is the whole contract: exit 0 only after durable upload, else Postgres retries the segment forever and `pg_wal` fills disk — monitor `archive_failure_count`.

### PITR restore procedure

```bash
# 1. Stop Postgres, move broken data dir aside (keep for forensics!)
systemctl stop postgresql@16-main
mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main.broken

# 2. Restore chosen base backup (latest taken BEFORE the target time)
pgbackrest --stanza=app --set=20260824-030002F \
  --target-time="2026-08-25 09:59:30+00" \
  --type=time --delta restore

# 3. pgBackRest writes restore_command + recovery signal automatically:
#    restore_command = 'pgbackrest --stanza=app archive-get %f %p'
#    recovery_target_time = '2026-08-25 09:59:30+00'
#    recovery_target_action = 'promote'

# 4. Start → WAL replays until target → promotes into a new timeline
systemctl start postgresql@16-main
tail -f log/postgresql.log   # "redo done", "selected new timeline ID: 5"
```

Target types: `--type=time` (wall clock), `--type=lsn` (exact position), `--type=xid` (before the offending transaction), plus `--target-exclusive`. Wall clock is easiest but assumes trustworthy clocks; LSN/XID are surgical for known-bad transactions.

### Tool landscape: pgBackRest vs WAL-G vs raw

| Capability                   | pgBackRest                     | WAL-G                           | pg_basebackup (DIY) |
| ---------------------------- | ------------------------------ | ------------------------------- | ------------------- |
| Full/diff/incremental        | Yes (block-level incr)         | Full + incr (delta)             | Base only           |
| Parallelism (backup/restore) | Excellent, tunable             | Good                            | Limited             |
| Compression/encryption       | Built-in (zstd/lz4/gzip + AES) | Built-in                        | DIY                 |
| WAL archive mgmt             | Integrated, retention-aware    | Integrated                      | Manual              |
| Verification commands        | `check`, `verify` (checksums)  | `backup-list` + validate        | Manual md5 dance    |
| S3/GCS/Azure                 | Native repos                   | Native purpose-built            | Via scripts         |
| Typical fit                  | Dedicated Postgres estates     | Cloud-native/K8s (CNPG uses it) | Learning/toy        |

Managed alternatives worth naming in interviews: AWS RDS snapshots + PITR window, Cloud SQL automated backups, Aiven/Neon branching. Same concepts, different knobs — the RPO/RTO math and drill discipline transfer verbatim.

### Choosing RPO/RTO targets

```text
Ask the business, per service tier:
  Tier 1 (payments, orders):  RPO ≤ 1 min   RTO ≤ 15 min
       → streaming replica + WAL archiving every segment + hourly incr backups
  Tier 2 (core SaaS features): RPO ≤ 5 min   RTO ≤ 1 hr
       → WAL archiving + daily full + 15-min incr
  Tier 3 (internal tools):     RPO ≤ 1 hr    RTO ≤ 8 hrs
       → daily physical backup + archived WAL, on-demand restore
Cost scales super-linearly as RPO→0; get signatures on the numbers,
not vibes. Document per-database in the runbook.
```

### Restore drills (the part everyone skips)

```yaml
# .github/workflows/restore-drill.yml  (weekly, staging cluster)
name: restore-drill
on:
  schedule: [{ cron: "0 4 * * 1" }]          # Monday 04:00 UTC
jobs:
  drill:
    runs-on: [self-hosted, staging]
    steps:
      - name: Provision throwaway Postgres container
        run: docker run -d --name drill-pg -p 55432:5432 postgres:16
      - name: Restore latest backup via pgBackRest
        run: |
          pgbackrest --stanza=app --set=$(cat latest.set) \
                     --target-action=promote --type=default \
                     --pg1-port=55432 restore
      - name: Replay WAL to latest and verify
        run: ./scripts/drill-verify.sh         # row counts, checksums, FK sanity
      - name: App smoke test against restored instance
        run: npm run test:smoke -- --db=postgres://localhost:55432/app
      - name: Report duration → RTO dashboard; alert on regression
        run: ./scripts/publish-drill-metrics.sh || true
```

Verification levels, cheapest to strongest: file exists → pgBackRest `verify` (checksums all blocks) → spin up restored cluster → application smoke tests → business queries ("yesterday's revenue matches"). Automate at least level three continuously; level five quarterly.

## Code Examples

### Server configuration for archiving

```ini
# postgresql.conf
archive_mode = on
archive_command = 'pgbackrest --stanza=app archive-push %p'
archive_timeout = 60          # force segment switch so idle DBs still get ≤60s RPO
wal_level = replica
max_wal_senders = 5           # also allows streaming standby
```

`archive_timeout` matters: without traffic, the last partial segment would sit unarchived for hours — your silent RPO killer on quiet systems.

### Retention policy definition

```ini
# pgbackrest.conf
[global]
repo1-type=s3
repo1-path=/prod/app-db
repo1-s3-bucket=acme-db-backups-eu-central-1
repo1-cipher-type=aes-256-cbc
repo1-retention-full=4                  # keep 4 fulls (weekly → ~28 days)
repo1-retention-diff=7                  # 7 differentials (~daily cadence)
repo1-storage-upload-chunk-size=8MiB
repo1-bundle=y                          # pack small files; fewer objects, faster restore
repo1-block=y                           # block-level incrementals: tiny incr backups

[app]
pg1-path=/var/lib/postgresql/16/main
```

Schedule pattern (GFS-flavored): Sunday full, daily differential, WAL continuous; monthly/yearly fulls copied to cold storage per legal hold. GDPR erasure vs backups tension: document that backups restore to a point in time by design; erasure applies going forward, and retention windows cap exposure — write this down, auditors ask.

### Cross-region copy with immutability

```bash
# Nightly: sync repo to another region, WORM-locked, separate credentials
aws s3 sync s3://acme-db-backups-eu-central-1/prod/app-db \
             s3://acme-db-backups-eu-west-1/prod/app-db \
  --exact-timestamps

# Once: object-lock (compliance mode) so even root cannot delete before expiry
aws s3api put-object-lock-configuration \
  --bucket acme-db-backups-eu-west-1 \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": { "DefaultRetention": { "Mode": "COMPLIANCE", "Days": 14 } } }'
```

Separate IAM principal for the copier (write-only to region B) means compromised prod credentials cannot delete both copies — the ransomware scenario interviewers probe.

### Restore verification queries

```sql
-- After drill restore: prove business-critical invariants
SELECT count(*) AS orders_24h FROM orders WHERE created_at > now() - interval '24 hours';
SELECT pg_is_in_recovery();                      -- must be false post-promote
SELECT timeline_id FROM pg_control_checkpoint(); -- new timeline ≠ source (proof of fork)
ANALYZE;                                         -- refresh planner stats before load tests
VACUUM;                                          -- optional; visibility map rebuild
```

Plus application-level checks: login works, one golden read per service, ledger sums match pre-incident export.

## Real-World Use Cases

1. **Bad migration at 10:42** — Expand step added a column fine; contract step dropped the wrong one at 11:00. PITR to 10:59:58 on a restored instance, export the table, patch forward. Total downtime 40 minutes instead of restoring last night's dump and losing 11 hours.
2. **Ransomware encrypts prod and deletes bucket** — Region-B WORM copy under a different principal survives; restore from 6-hour-old full + WAL to a clean VPC; forensic copy of `main.broken` retained.
3. **Region outage** — Cross-region copy promoted into secondary region; RTO dominated by DNS/Terraform bring-up (~35 min) rather than data movement.
4. **Pre-upgrade safety net** — Before major-version upgrade (15→16), take a labeled full; upgrade rehearsal restores it into staging and replays a week of WAL to validate timing.
5. **Audit evidence** — Quarterly drill reports (duration, checksum verification, smoke-test results) exported as PDFs satisfy SOC 2 CC7.5 without heroics.

## Common Mistakes

| Mistake                                           | Fix                                                                                  |
| ------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Backups never restored until disaster             | Scheduled automated drills; alert when drill fails or regresses                      |
| `archive_command` failing silently                | Monitor `pg_stat_archiver` (`failed_count`, `last_failed_time`); page on failures    |
| No `archive_timeout` on low-traffic DBs           | Set 60s; otherwise RPO is "until next segment fills"                                 |
| Replicas counted as backups                       | Standbys replicate corruption instantly; keep independent history                    |
| Backup creds can delete backups                   | Separate principal, object-lock/WORM, versioning on                                  |
| Single-region copies                              | Cross-region sync; region outage then equals restore-from-zero                       |
| Dump-only strategy at TB scale                    | `pg_restore` runtime explodes; physical + WAL for RTO, dumps for portability/archive |
| Restoring onto same cluster while clients connect | Restore into isolated instance; verify; then cutover                                 |
| Ignoring new timeline after promote               | Old replicas/wal gaps confuse re-cloning; rebuild standbys from the promoted node    |

## Best Practices

1. **Write RPO/RTO per database tier first** — tooling follows numbers; revisit quarterly as data volume grows.
2. **3-2-1(-1-0)** — 3 copies, 2 media, 1 offsite; add: 1 immutable, 0 errors after verification.
3. **Full + incremental cadence matched to change rate** — write-heavy OLTP wants frequent block-level incrementals, not weekly fulls alone.
4. **Automate the drill end-to-end** — provision → restore → verify → smoke test → publish metrics; humans click nothing.
5. **Track restore duration trend** — RTO is a function of data growth; capacity-plan storage AND restore throughput.
6. **Encrypt everywhere** — at rest (repo cipher or bucket KMS) and in transit; key access separated from backup access.
7. **Document the runbook with exact commands** — 3 a.m. execution must be copy-paste; include "stop here and call the DBA" checkpoints.
8. **Test upgrades via restore** — rehearsal environments built from real backups catch extension/version surprises.
9. **Monitor freshness like an SLI** — `seconds_since_last_successful_backup`, `bytes_behind_wal_archive`; alert before users notice.
10. **Pair with platform-level strategy** — this chapter covers the database engine view; the org-wide policy lives in the infra-patterns stack: see 30.3.2.05-backup-strategy-restore-drills.md under 30-architecture/30.3-infra-patterns/02-failure-and-recovery/.

## Performance Considerations

- Backups compete for I/O with production: schedule fulls off-peak, throttle parallelism (`process-max`), or back up from a standby.
- Block incrementals shrink backup windows dramatically on multi-TB databases (only changed blocks stored).
- Restore speed ≈ min(storage throughput, CPU decompress, WAL replay single-threadedness) — long WAL stretches between fulls lengthen the tail of replay.
- `repo1-bundle` reduces small-file overhead on S3-class stores (fewer PUTs, faster listing during restore).
- Keep `main.broken` on cheap storage, not the hot NVMe array — forensics rarely needs performance.

## Summary

- RPO/RTO are contracts signed before tooling choices; everything else implements them.
- Physical base backups + continuous WAL archiving enable second-granularity PITR; `pg_dump` complements for portability and archival, not RTO.
- pgBackRest/WAL-G provide the production loop: fulls/diffs/incrementals, compression, encryption, retention, verification.
- Unverified backups are hope, not protection: automate restore drills with app-level smoke tests and track duration as a metric.
- Cross-region, immutable, separately-credentialed copies are what survive targeted attacks and regional failure.

| Concept                | Description                                                |
| ---------------------- | ---------------------------------------------------------- |
| RPO                    | Max tolerable data loss (time window)                      |
| RTO                    | Max tolerable downtime (restore duration)                  |
| `pg_dump/pg_restore`   | Logical, portable, slow at scale; good archive format      |

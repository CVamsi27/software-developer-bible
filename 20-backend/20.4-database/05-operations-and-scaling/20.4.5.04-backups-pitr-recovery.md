# Backups, PITR & Recovery

If a replica applies a destructive `UPDATE`, it may copy the mistake immediately. Yesterday’s dump avoids that commit but also loses yesterday’s valid work. Point-in-time recovery uses a base backup and retained WAL to reach a verified state between those outcomes.

## Definition

A database backup preserves a recoverable state outside the live database. Recovery reconstructs that state and checks that the application can use it. **Point-in-time recovery (PITR)** combines a physical base backup with later write-ahead log (WAL) records and stops at a chosen recovery target.

> **Textbook Definition:** Recovery reconstructs a consistent database state from retained backup artifacts and, when supported, subsequent log records. The recovery point objective (RPO) limits acceptable data loss; the recovery time objective (RTO) limits acceptable service interruption.

## First Principles

A replica can survive a machine failure while faithfully applying an unwanted DELETE. Recovering from that mistake requires history that the live database no longer exposes. A logical export taken before the mistake can provide an older state; a physical backup plus an unbroken log history can provide a later, more precise state.

Recovery also needs more than rows. The restored service must have compatible extensions, required identities, configuration, encryption keys and network access. A valid backup that takes longer to provision and validate than the permitted interruption still misses the service objective.

Retaining a base backup while deleting a log segment it requires breaks the recovery chain. The unit to preserve is a usable chain and its dependencies, rather than an arbitrary number of backup objects.

## Preserve a path from the base backup to a target

### Choose a representation before choosing a tool

| Representation | What it preserves | Recovery boundary |
| ------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Logical export, such as pg_dump | SQL-level database objects/data under its selected scope | Recreates the exported state; cannot replay physical WAL onto it |
| Physical base backup | Cluster files plus the information/WAL needed to make the online copy consistent | Requires compatible PostgreSQL major version and storage/extension environment |
| Physical base plus archived WAL | The base state and subsequent logged history | Replays a continuous required chain to an available target |

A pg_dump archive is not necessarily a text script: custom/directory formats support pg_restore's selection and parallel restore features. A database dump does not include cluster-wide roles/tablespaces; capture required globals/configuration separately. Cross-version logical migration still needs compatibility checks, especially for extensions and newer-to-older targets.

PostgreSQL 18 also supports incremental `pg_basebackup` runs against an earlier backup manifest. An incremental is not an independent base: retain every dependent backup and manifest, combine the chain from oldest to newest with `pg_combinebackup`, check backup integrity with `pg_verifybackup`, and preserve the required WAL. Integrity checks still do not replace a full restore drill.

An online physical backup is not a simultaneous byte snapshot of all files. The backup protocol and required WAL reconcile files copied at different moments. Use a supported backup tool or correctly coordinated snapshot procedure; copying a running data directory casually is insufficient.

### Follow WAL from commit to the recoverable archive

```text
committed changes → local WAL → completed segment → archive upload
                                                    │
base backup + required contiguous segments + history files
                                                    ↓
                      isolated restore → replay → verify → cutover
```

Ordinary archive_command runs for completed segments, normally 16 MiB unless configured differently at cluster creation. A quiet workload can leave recent records in an incomplete segment. archive_timeout can force switches when applicable, but upload delay, failure and archive durability still affect the newest recoverable point. A sixty-second setting alone does not prove a sixty-second RPO.

The archiver may retry. Its command must acknowledge only the intended persisted archive result, refuse conflicting overwrites and handle identical retries correctly. Monitor backlog, failures, local disk and restore availability. pg_stat_archiver uses failed_count/last_failed_time, but some process/shell failures are not recorded there; include logs and end-to-end checks. An accumulating unarchived backlog can fill pg_wal and stop service.

Physical recovery also needs files outside WAL's scope: edits to postgresql.conf/pg_hba.conf and secrets are not reconstructed by replay. Separate copies and tested access to those dependencies are part of recovery.

### The target is a commit boundary, not a guessed second

A recovery target can be a timestamp, named restore point, transaction ID or WAL position (**log sequence number**, LSN). For time/XID/LSN targets, recovery_target_inclusive determines whether the matching boundary is included. Transaction IDs are allocated before commit and do not imply commit order. Select the target using incident evidence and verify the resulting state.

The target must be reachable after the chosen base backup completed. Missing required WAL can prevent reaching it; choosing a backup taken after the desired state cannot rewind that backup. recovery_target_action='pause' permits inspection with hot standby enabled before deciding to finish recovery. Promotion creates a new history timeline; subsequent archiving/replicas must follow that lineage.

Restoring before a bad transaction also excludes legitimate later transactions. Decide whether to recover the entire service to that point or export selected corrected data from an isolated restore and repair the live database. Both need reconciliation; PITR does not automatically retain only the good later writes.

## Test a logical restore and a named recovery target

### Restore a logical fixture into another database

Use PostgreSQL 16 clients and a disposable local cluster. Create an empty database named recovery_source first. The shell commands below assume its connection is already configured through the ordinary PostgreSQL client environment, and run from a disposable working directory.

```sql
-- Connect to recovery_source.
CREATE TABLE recovery_fixture(id integer PRIMARY KEY, value integer NOT NULL);
INSERT INTO recovery_fixture VALUES (1, 1);
```

```bash
pg_dump --dbname=recovery_source --format=custom --file=fixture.dump
createdb recovery_logical
pg_restore --dbname=recovery_logical --exit-on-error fixture.dump
psql --dbname=recovery_logical --command='SELECT id, value FROM recovery_fixture;'
```

The recovered row is (1,1). Changing the source after the export does not change the archive. The fixture exercises export/restore, not production restore time, roles, extension installation or disaster access to storage. Preserve the command exit status; a started server alone is not evidence of successful object/data restoration.

### Trace a named target before a bad update

This is a physical-recovery lab contract for **two isolated PostgreSQL 16 clusters**, not a command to restore over a live production directory. Prepare archive storage and a supported archiver, establish a base backup after the fixture row is 1, and verify that backup's required WAL is available. Then run on the source:

```sql
UPDATE recovery_fixture SET value = 2 WHERE id = 1;
SELECT pg_create_restore_point('before_bad');
UPDATE recovery_fixture SET value = 999 WHERE id = 1;
SELECT pg_switch_wal();
```

Each statement commits separately under ordinary autocommit. Confirm that the completed segment containing the target is successfully archived. pg_switch_wal initiates a switch; it is not an upload-completion acknowledgment.

Restore the base into a separate empty data/tablespace location with correct ownership. Configure archive retrieval, recovery.signal, an isolated socket/port and access rules. For a prepared pgBackRest repository/stanza, this **operator fragment** selects a named target and pauses:

```bash
# Replace both placeholders using the prepared isolated recovery runbook.
pgbackrest --stanza=recovery_lab --set=BACKUP_COMPLETED_BEFORE_TARGET \
  --pg1-path=/isolated/recovery-lab/data \
  --type=name --target=before_bad --target-action=pause restore
```

The repository configuration, credentials, compatible binaries, mapped tablespaces and empty destination are prerequisites. pgBackRest writes recovery configuration but does not start PostgreSQL. Inspect it and the service's actual data_directory before starting the isolated instance. This fragment was checked against official options; the runnable local probe used pg_basebackup and a local demonstration archive instead of a cloud pgBackRest repository.

Once replay reaches and pauses at the target, query the recovered instance:

```sql
SELECT id, value FROM recovery_fixture;               -- 1 | 2
SELECT pg_is_in_recovery(), pg_is_wal_replay_paused(); -- true | true
```

The source still contains 999; the restored cluster contains 2. If the marker were placed after the bad commit, this target would include 999. After inspection, finish recovery/promote through the approved runbook and verify that recovery has ended, a new timeline is recorded, and future backups/standbys work. Do not attach production writers before deciding the recovery result is acceptable.

## Measure recovery time and protect the history chain

### Turn objectives into a measured recovery procedure

Agree on acceptable lost business work and interruption for each service. A target such as five minutes of data loss is an example of a business requirement, not a property assigned universally to a database tier. Measure the newest independently recoverable point, including archive gaps and the durability of the archive destination.

Measure interruption from detection through provision, artifact/key retrieval, restore, replay, application verification and traffic cutover. Record dataset size, storage/network throughput, replay distance, extensions and drill environment. A tiny fixture cannot substantiate a multi-terabyte RTO; a successful dump command cannot substantiate recovery availability.

More frequent physical backups can shorten the WAL replay tail while increasing backup I/O/cost. Parallel restore, compression and incremental chains have tool/version/storage tradeoffs. pgBackRest and WAL-G manage different repository/backup features; pin and test the deployed tool's options. pg_basebackup is a supported PostgreSQL building block, not inherently a toy, but retention, offsite protection and monitoring remain the operator's responsibility.

### Separate the failure domain of retained history

Choose independent storage/credentials and geographic placement according to the failures the service must survive. A cross-region copy is useful only if its complete chain, keys and restore path are available. A generic file sync does not establish object-lock configuration, retained versions or protection from a compromised principal.

Retention and immutability must cover the intended historical window and any backup dependencies. Test that restore credentials can read/decrypt while production identities cannot destroy all copies. Preserve an incident source when feasible for investigation and reconciliation; do not overwrite it merely to save a provisioning step.

Privacy and retention policies also apply to backups. A restored old copy can reintroduce data deleted later. Restrict drill environments and reapply required deletion/access policies before exposure. Compliance evidence must map to the applicable control and organization; a quarterly PDF does not automatically satisfy every standard.

## Failure and Recovery Boundaries

A drill should cover missing/corrupt objects, missing WAL, inaccessible keys, incompatible extensions and a target beyond available history. Keep application background jobs, payment/email publishers and production integrations disabled in the isolated environment; otherwise a data verification exercise can repeat real side effects.

Validate both engine and business state: expected records at the selected boundary, constraints/ledger invariants, representative authorized reads, required roles/extensions and service startup. Row counts alone miss wrong values or missing tenant restrictions. Promotion status or a new timeline proves a state transition, not business correctness.

After cutover, ensure one authorized writer, reconfigure/rebuild standbys as required, reconcile later work, and prove the new backup/archive chain. Infrastructure provisioning, fencing and routing belong to the [platform recovery chapter](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.05-backup-strategy-restore-drills.md).

Keep these steps in a versioned runbook with artifact selection, key/access prerequisites, target evidence, isolation, validation, cutover and post-recovery backup checks. Preserve drill failures in the reported result; a wrapper that swallows the restore command’s exit status turns failure into a false pass. Rehearse representative volume and failure conditions often enough to expose drift in the actual recovery assumptions.

## Summary

A recoverable database needs a usable backup chain, accessible dependencies and a tested path back to service. Logical exports recover their selected snapshot; physical base backups plus continuous required WAL enable a reachable historical target. Verify the commit boundary, reconcile excluded legitimate work, isolate side effects and measure the entire recovery against the service's RPO/RTO.

# Search Infrastructure at Scale

## Definition

Search infrastructure turns stored documents into a structure that can find matches and order them for a user's query. A document can be a database row, product description or page. Search inside PostgreSQL can share the row's transaction; a separately maintained engine owns a derived copy with its own publication, freshness and recovery rules.

> **Textbook Definition:** Search infrastructure maintains representations and access structures for document retrieval and relevance scoring. An external index is a derived representation whose synchronization, deletion, visibility and rebuild contracts determine consistency with its authoritative source.

## First Principles

A customer searching “wireless headphones” needs more than an exact ID lookup. The system must turn text into comparable terms, find documents containing those terms and decide which matches to show first. A substring search, a language-aware term match and a typo-tolerant match answer different questions.

Updating a row and a remote search engine involves two failure domains. If the database commits while the remote call fails, search retains old data. If the remote change happens first and the database rolls back, search can expose nonexistent data. A durable publication obligation after the source commit is therefore necessary when separate stores are involved.

Deletion adds an ordering constraint: retrying an old update after a newer delete can recreate the document. Independently repeatable operations do not establish their correct order. A rebuild faces the same problem if its older snapshot overwrites changes arriving during the scan.

## How It Works

### Derive text terms, retrieve candidates, then rank

An **analyzer** transforms text into searchable terms, possibly by splitting words, normalizing case and reducing language variants. PostgreSQL calls a normalized searchable term a **lexeme** and stores terms/positions in a tsvector. A tsquery represents matching conditions. The @@ operator tests whether a vector satisfies them.

An **inverted index** maps terms to documents containing them. PostgreSQL's GIN index can accelerate this candidate lookup. Ranking then scores matching documents; PostgreSQL provides ts_rank and ts_rank_cd. SQL can both filter and rank, so relevance does not inherently require a separate engine.

Language configuration changes results. The same surface word can normalize differently or be ignored as a stop word. A query parser's syntax also matters: PostgreSQL websearch_to_tsquery accepts familiar search text, but does not interpret a user's text as the prefix-operator syntax of to_tsquery. Typo tolerance, substring matching and language normalization are distinct capabilities.

### Fit a separate engine to a measured product requirement

OpenSearch/Elasticsearch, Meilisearch and Typesense offer different search/query, deployment and recovery contracts. Evaluate the deployed version's analyzer, typo, facet, filtering, language and vector capabilities with your actual documents. These products do not share one universal ranking formula or memory/storage architecture.

A ranking option such as **BM25** reduces the incremental value of repeated terms, accounts for document length and weights rarer terms. Field boosts can prioritize a title over a description. These choices can improve one query set and hurt another; product labels or corpus size alone do not prove better relevance.

Measure retrieval against labeled query/result expectations. Recall at k asks how much relevant material appears within k candidates; mean reciprocal rank (MRR) measures how early the first relevant result appears. Also test latency, updates, authorization, languages, typos and empty queries. A benchmark must include the conditions of the proposed deployment.

A dedicated store can separate search resource pressure from transactional writes, but adds publication, storage, operations and another outage path. PostgreSQL search also has indexing, vacuum, storage and query costs. There is no universal document-count threshold or “zero operations” option.

## Code Examples

### Build and query a complete PostgreSQL text-search fixture

Use PostgreSQL 16+ in a fresh disposable schema. English normalization is chosen explicitly; it is not a multilingual default.

```sql
CREATE TABLE search_products (
    id integer PRIMARY KEY,
    tenant_id integer NOT NULL,
    name text NOT NULL,
    description text NOT NULL,
    search tsvector GENERATED ALWAYS AS (
        setweight(to_tsvector('english', name), 'A') ||
        setweight(to_tsvector('english', description), 'B')
    ) STORED
);
CREATE INDEX search_products_terms ON search_products USING gin(search);
INSERT INTO search_products(id, tenant_id, name, description) VALUES
    (1, 7, 'Wireless headphones', 'Portable sound'),
    (2, 7, 'Audio stand', 'Stand for wireless headphones'),
    (3, 8, 'Wireless headphones', 'Private tenant item'),
    (4, 7, 'Wired headphones', 'Portable sound');

WITH query AS (
    SELECT websearch_to_tsquery('english', 'wireless headphones') AS q
)
SELECT p.id, p.name
FROM search_products AS p CROSS JOIN query
WHERE p.tenant_id = 7 AND p.search @@ query.q
ORDER BY ts_rank(p.search, query.q) DESC, p.id
LIMIT 20;
-- 1 | Wireless headphones
-- 2 | Audio stand
```

The parser normalizes both query words and combines them as required matches. IDs 1 and 2 contain both; title-weighted matches rank first. ID 3 is excluded by the trusted tenant predicate, while ID 4 lacks wireless. Equal scores use id as a deterministic tie-breaker. The tiny fixture need not use GIN: a sequential scan can be cheaper. Confirm actual plans at representative volume.

For an application, bind tenant/query values rather than interpolating them. Derive the tenant from authenticated authorization; a client-supplied filter is not an access boundary. Raw search snippets, facets, counts and autocomplete also must respect visibility.

### Change the query from full term to prefix

```sql
SELECT
    to_tsvector('english', 'wireless headphones')
        @@ websearch_to_tsquery('english', 'wirel') AS ordinary_term,
    to_tsvector('english', 'wireless headphones')
        @@ to_tsquery('english', 'wirel:*') AS explicit_prefix;
-- false | true
```

The first parser searches the normalized full term wirel; it does not automatically complete wireless. The second explicitly requests the prefix. Building structured query syntax from untrusted input needs a deliberate escaping/parser contract; do not pass arbitrary user text to to_tsquery and promise the forgiving behavior of websearch_to_tsquery. Prefix matching still does not correct a misspelling.

### Publish a derived document without claiming two-store atomicity

For an external engine, choose either **change data capture (CDC)** from committed database changes or an explicit transactional outbox. The [outbox chapter](../../20.6-microservices/03-data-and-consistency/20.6.3.06-transactional-outbox.md) owns its complete schema/worker example; this chapter specifies the search-specific obligations.

```text
source transaction:
    mutate authorized product + increment its monotonic search version
    append durable upsert/delete intent with tenant, key and version
    commit both or neither

publication worker:
    acquire bounded recoverable work under an ordering/claim contract
    end the claim transaction before remote network work
    publish the intended state under per-key order/version protection
    inspect each operation's actual result
    persist completion only for confirmed outcomes
    retry uncertain/failed work without accepting an older state
```

There are three separate milestones: source committed, remote operation accepted/applied, and document visible to search. OpenSearch bulk responses can contain failed items alongside successful items; an HTTP-level success is insufficient. Refresh controls affect search visibility after writes. Meilisearch returns asynchronous tasks; receiving a task identifier does not mean its indexing operation succeeded or is already searchable. Monitor the required milestone rather than calling every acknowledgment “indexed.”

A worker crash after remote success but before recording completion creates a repeat. A stable document key and version help make repeated upserts safe. Deletions need an equally durable order rule: if the engine removes the document/version, retain a deletion watermark elsewhere or serialize/reconcile against authoritative current state. A later consumer may not infer the last version from an absent document.

FOR UPDATE SKIP LOCKED alone is not per-product event ordering. Different workers can skip an older locked event and apply a newer event first. Claims also need lease/fencing behavior if a slow old worker resumes after another claims the same work. Choose and test a real protocol rather than inferring delivery safety from a lock clause.

CDC needs publications/slots, permissions, schema evolution, serialization, replay and retention management. An outbox needs every relevant writer to append its intent, cleanup after safe delivery and recoverable claims. Either can retain a durable publication obligation; neither removes all partial-failure or ordering problems automatically.

## Rebuild and Query Boundaries

### Build a new index while changes continue

Create a new physical index with explicit fields/analyzers and an authorization-compatible projection. Establish a consistent snapshot and a corresponding change-stream watermark, then backfill the snapshot and replay all later changes under the same version/delete rules. This ordering depends on the chosen CDC/outbox system; scanning rows while independently guessing a “last ID” is insufficient.

Compare counts plus representative field values, deleted records, tenant restrictions and relevance. Catch the new index up to a defined safe point before switching the search alias/routing atomically where the engine supports it. An alias switch changes routing; it does not repair missed writes or authorize documents. Keep a rollback path and continue publication to whatever destination rollback will need.

A missing event beyond retained history can require a fresh rebuild rather than more retries. Snapshot/replay procedures must remove stale documents and retain deletion ordering; copying only current upserts onto an existing stale index leaves deleted documents behind.

### Decide which stale results the product can accept

A committed product edit may take time to appear in external search. Define a measured visibility objective and, when necessary, a version/task wait with a deadline or an authoritative confirmation read. Do not present an unbounded wait as read-your-writes.

A stale search hit must not grant permission to access the primary object. Recheck current authorization and existence before sensitive detail/actions. Revoked access can affect result names, snippets, facets and counts as well; decide whether filtering through a stale projection is acceptable for those fields. Index only the minimum required sensitive data.

Lexical matching retrieves term-based candidates; vector search retrieves candidates according to an embedding model and distance function. Hybrid search needs a specified fusion/reranking policy: sorting lexical score first and vector distance second is not automatically balanced hybrid relevance. Corpus/model/version and fallback authorization rules belong to the [retrieval-quality chapter](../../20.12-ai-engineering/20.12.03-retrieval-quality-hybrid-search-reranking.md).

## Real-World Decisions

An admin keyword box may be well served by PostgreSQL term matching and ranking. A catalog may require tuned typo handling, facets or language analysis from another engine even at modest size. A document portal may need semantic recall and reranking. Treat these as scenarios to evaluate, not performance claims about a fixed number of rows.

Measure indexing lag, oldest unfinished work, retries/permanent failures, search latency and relevance separately. A recently processed event does not prove that an older failed event has caught up. Reconcile source versions and sampled projections, and exercise a full rebuild.

Tune GIN, batching, refresh interval, shards and pagination only against the actual product/version/workload. Index maintenance can affect database writes; large bulk requests can increase retry cost; deferred refresh delays visibility. Exact engine defaults and scaling advice can change, so pin operational settings and validate them rather than borrowing universal throughput multipliers or shard-size numbers.

## Common Mistakes

- **Assume SQL cannot rank.** PostgreSQL text search supports ranking; compare capabilities and observed quality.
- **Expect websearch_to_tsquery to provide prefix or typo handling.** Its parser contract is specific.
- **Dual-write without retained delivery intent.** One successful store does not imply the other committed.
- **Acknowledge an entire bulk batch or task immediately.** Verify item/task outcome and the required visibility milestone.
- **Call idempotent upserts sufficient ordering.** An older update can recreate a newer deletion.
- **Alias-switch an incomplete backfill.** Establish snapshot/change coverage and authorization before routing readers.

## Best Practices

Give the source row, document key, tenant, version, deletion marker and publication milestone explicit contracts. Keep remote calls outside database transactions used for short work claims; recover them with replay-safe ordering. Verify relevant queries and failed/reordered delivery before scaling infrastructure. Keep mappings, analyzer configuration and rebuild procedures versioned with their source/projection contract.

## Summary

Search analyzes text, retrieves candidates and ranks them under a chosen product/query contract. PostgreSQL can do term search and ranking; a dedicated engine adds capabilities alongside another publication and recovery boundary. Verify the query parser, authorization, item/task outcomes, visibility lag, deletion ordering and snapshot/replay coverage so a useful derived index remains recoverable and safe.

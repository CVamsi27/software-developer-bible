# Search Infrastructure at Scale

> **TL;DR:** Postgres full-text search (tsvector + GIN) is excellent to roughly the millions-of-rows scale and should be your default. It hits a ceiling on ranking quality (crude `ts_rank` vs BM25 with field boosts), write-heavy GIN maintenance, and horizontal scaling of search-specific workloads. When relevance tuning, faceting, typo tolerance, or tens of millions of documents become the product, move to a dedicated engine — Elasticsearch/OpenSearch (full power, heavy ops), Meilisearch/Typesense (batteries-included, product-search sweet spot). Keep Postgres the source of truth and sync indexes via CDC/outbox pipelines, never dual writes.
>
> **Why it matters:** "Why not just use Elasticsearch?" is asked in every senior loop — the expected answer is a cost-aware decision table, not tool worship in either direction.

## Definition

**Search infrastructure** spans three layers:

1. **In-Postgres FTS** — `to_tsvector` documents, GIN-indexed lexemes, `tsquery` matching, `ts_rank` scoring. Zero extra infrastructure; one transactional truth.
2. **Dedicated engines** — inverted indexes with per-field analyzers, BM25 ranking, aggregations/facets, typo tolerance: Elasticsearch/OpenSearch (JVM clusters), Meilisearch/Typesense (single-binary, RAM-friendly).
3. **Sync layer** — how changes flow from OLTP Postgres into the engine: CDC (logical decoding → Debezium → Kafka → indexer) or outbox pattern, replacing naive after-commit dual writes.

```text
OLTP Postgres ──(WAL/logical decoding)──► Debezium ──► Kafka topic
                                              │ outbox alternative:
                                              │ tx writes row + outbox event atomically
                                              ▼
                                        Indexer worker
                                              │ bulk index (5-15s lag typical)
                                              ▼
                              OpenSearch / Meilisearch / Typesense
```

## Why Do We Need It?

1. **Search quality is product surface** — "did you mean", field boosting, synonyms, facets drive conversion; `ts_rank` cannot compete with BM25 + tuning once users care.
2. **GIN indexes get expensive under write load** — every update rewrites lexeme postings; hot tables with frequent updates show pending-list bloat and latency spikes (`fastupdate` flushes).
3. **Different scaling axes** — OLTP scales by rows and transactions; search scales by documents × QPS × facets; forcing both into one cluster couples failure domains.
4. **Multilingual reality** — per-language stemming/normalization (ICU, CJK segmentation) is configuration in dedicated engines, an extension matrix in Postgres.
5. **Cost honesty** — a JVM search cluster is 2–6 nodes of RAM-hungry ops burden; adopting it for a 200k-row catalog is negative ROI.

## How It Works

### Postgres FTS mechanics and its ceiling

```sql
-- Setup: generated tsvector column + GIN
ALTER TABLE products ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(name,'')), 'A') ||
    setweight(to_tsvector('english', coalesce(description,'')), 'B')
  ) STORED;
CREATE INDEX products_search_idx ON products USING gin(search);

-- Query with ranking + prefix support for typeahead
SELECT id, name,
       ts_rank(search, q) AS rank
FROM products, websearch_to_tsquery('english', 'wireless headphones') q
WHERE search @@ q
ORDER BY rank DESC
LIMIT 20;
```

Where it strains:

| Symptom | Root cause | Scale ballpark |
| ---------------------------------------- | ------------------------------------------------------------------ | -------------------------------- |
| Write latency spikes | GIN pending list flushes; HOT updates defeated by indexed column | >10k updates/min on indexed text |
| Slow counts/facets | Every facet = another scan+aggregate | >5–10M docs |
| Weak relevance | `ts_rank` ignores term frequency saturation/field length norms | Any user-facing search |
| No typo tolerance / synonyms without DIY | Engine features absent | Product search expectations |
| Vertical-only growth | FTS shares OLTP resources; replicas help reads but not index bloat | Shared cluster pain |

### When each engine wins

| Need | Postgres FTS | Elasticsearch/OpenSearch | Meilisearch/Typesense |
| --------------------------------------- | :-------------------: | :---------------------------------: | :----------------------------------: |
| CRUD filters + occasional keyword box | Yes | Overkill | Fine too |
| BM25 tuning, per-field boosts, synonyms | Limited | Yes (full DSL) | Good defaults |
| Typo tolerance | No | Yes (fuzzy) | Yes (default on) |
| Facets/aggregations | Expensive | Excellent | Good (built-in) |
| Geo + hybrid vector search | pgvector extension | kNN + full DSL | Vector search built-in |
| Ops appetite | None (already run PG) | High: JVM heap, shards, rebalancing | Low: single binary, snapshot restore |
| Data size comfort | ≤ ~10M docs typically | Billions | ~tens of millions, RAM-bound |

Decision shortcut: if search is *a feature*, stay in Postgres; if search is *the product* (marketplace, docs portal, e-commerce discovery), adopt a dedicated engine.

### Relevance tuning basics (BM25)

BM25 scores query-term matches with three ideas: term frequency saturates (the 5th occurrence adds little), rare terms matter more (IDF), long documents are discounted (length normalization). Engines expose it as tunables (`k1` saturation, `b` length norm) plus practical levers:

```json
// OpenSearch: boost SKU/name over description; recency function score on top
{
  "query": {
    "function_score": {
      "query": {
        "multi_match": {
          "query": "wireless headphones",
          "fields": ["name^4", "brand^2", "description"],
          "type": "best_fields", "fuzziness": "AUTO"
        }
      },
      "functions": [
        { "gauss": { "createdAt": { "scale": "180d" } } },
        { "field_value_factor": { "field": "popularity", "modifier": "log1p", "factor": 0.5 } }
      ],
      "boost_mode": "sum"
    }
  }
}
```

Tuning workflow that survives review: build a labeled query set (50–200 queries with expected top results), compute recall@k/MRR before and after each change, ship only measured improvements. This mirrors the retrieval-eval harness used for RAG (see See Also).

### Multilingual analysis

- Choose analyzers per language: `english` stemmer drops plurals/suffixes; `german` compounds ("Donaudampfschifffahrt") need decomposition; CJK requires n-gram/ICU tokenization since words lack spaces.
- Multi-language fields: index one sub-field per language with language-specific analyzer, route queries by locale.
- Postgres equivalent exists (`to_tsvector('german', ...)`, ICU collations) but per-language columns multiply schema complexity — another nudge toward engines when i18n breadth grows.

## Code Examples

### CDC/outbox sync pipeline

```sql
-- Outbox written in the SAME transaction as the domain change
CREATE TABLE search_outbox (
  id          BIGSERIAL PRIMARY KEY,
  aggregate   TEXT NOT NULL,             -- 'product'
  aggregate_id UUID NOT NULL,
  op          TEXT NOT NULL CHECK (op IN ('upsert','delete')),
  payload     JSONB NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX search_outbox_pending_idx ON search_outbox (id) WHERE dispatched_at IS NULL;
```

```typescript
// workers/search-indexer.ts — at-least-once consumer; idempotent upserts make it safe
export async function drainOutbox(batchSize = 500): Promise<number> {
  const rows = await db.tx(async t => {
    const pending = await t.query(
      `SELECT id, aggregate, aggregate_id, op, payload
       FROM search_outbox WHERE dispatched_at IS NULL
       ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED`, [batchSize]);
    if (!pending.rows.length) return [];

    await bulkIndex(pending.rows);                       // OpenSearch _bulk / Meili batch
    await t.query(
      `UPDATE search_outbox SET dispatched_at = now()
       WHERE id = ANY($1::bigint[])`, [pending.rows.map(r => r.id)]);
    return pending.rows;
  });
  return rows.length;
}
// Scheduled every second; monitor max lag = now() - min(created_at of undrained rows)
```

CDC variant (Debezium): publication on the tables, logical slot → Kafka topics keyed by PK; indexer consumes change events. CDC wins when many tables feed search and you want zero app-code involvement; outbox wins when you control payloads and want explicit contracts. Both eliminate the classic dual-write bug where DB commits but engine write fails (or vice versa).

### Hybrid lexical+vector inside Postgres (bridge tier)

```sql
-- pgvector alongside FTS: semantic recall without new infrastructure
SELECT p.id, p.name,
       ts_rank(p.search, q) AS lexical,
       1 - (p.embedding <=> $2::vector) AS semantic
FROM products p, websearch_to_tsquery('english', $1) q
WHERE p.search @@ q OR p.embedding <=> $2::vector < 0.35
ORDER BY lexical DESC NULLS LAST, semantic DESC NULLS LAST
LIMIT 50;
```

Good enough to delay engine adoption; when ranking experiments outgrow SQL, graduate the corpus but keep this query as the fallback path during migration.

### Meilisearch product-search setup (the fast path)

```bash
# Index settings: typo tolerance + facet distribution out of the box
curl -X PATCH 'http://localhost:7700/indexes/products/settings' \
  -H 'Authorization: Bearer '$MEILI_KEY \
  -d '{
    "searchableAttributes": ["name", "brand", "description"],
    "filterableAttributes": ["category", "price", "in_stock"],
    "sortableAttributes": ["price", "created_at"],
    "rankingRules": ["words","typo","proximity","attribute","sort","exactness","popularity:desc"]
  }'

curl -X POST 'http://localhost:7700/indexes/products/documents' \
  -H 'Authorization: Bearer '$MEILI_KEY --data-binary @products-bulk.json
```

## Real-World Use Cases

1. **E-commerce catalog (30M SKUs)** — Postgres source of truth; Debezium→Kafka→OpenSearch; name^4/brand^2 boosts, price facets, A/B-tested synonym lists; p99 <120 ms.
2. **SaaS admin search (400k records)** — stays in Postgres forever; GIN + `websearch_to_tsquery`; zero added infra; team reallocates the would-be cluster budget.
3. **Docs/helpdesk portal** — Typesense single node 32 GB RAM; typo tolerance is 80% of perceived quality; snapshots to S3 nightly.
4. **Multi-tenant CRM** — per-tenant index filtering with document-level security; OpenSearch index-per-large-tenant template, shared index for small tenants.
5. **Job board multilingual (DE/EN/PL)** — per-language sub-fields with language analyzers; cross-language synonym expansion at query time.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------ | ---------------------------------------------------------------------- |
| Dual-writing to DB + engine after commit | Outbox/CDC pipeline; treat engine as derived data |
| Adopting Elasticsearch because "we will be big" | Decision table first; infra follows measured need |
| One giant index, no aliases | Time/versioned aliases from day 1; reindex = swap alias, zero downtime |
| Reindexing by DELETE-all then re-insert | Build new index behind alias; atomic switch |
| Mapping explosion / dynamic everything | Explicit mappings; `dynamic: strict` for curated indices |
| Ignoring replica shard count until split-brain lessons | Shards ≈ target data volume / (20–40 GB); replicas per HA needs |
| Trusting engine as source of truth | Postgres remains canonical; full rebuilds must be routine and tested |
| Facets computed client-side from full result dumps | Use engine aggregation APIs; paginate normally |

## Best Practices

1. **Start in Postgres; graduate deliberately** — define the trigger metrics (doc count, write rate, relevance complaints) in advance.
2. **Derived-data mindset** — the search index is a cache with a rebuild procedure; practice full reindexes quarterly.
3. **Idempotent indexing** — same document version produces same state; consumers may retry safely.
4. **Monitor freshness as SLI** — `now() - last_event_applied` per index; alert beyond product tolerance (usually 1–5 min).
5. **Version mappings like code** — new mapping → new index → backfill → alias flip; never mutate live mappings in place.
6. **Tune relevance with eval sets** — recall@k/MRR on golden queries; every boost/synonym change ships with numbers.
7. **Secure multi-tenancy at the filter layer** — tenant predicate injected server-side, never trusted from client params.
8. **Capacity-plan RAM honestly** — Meili/Typesense are memory-resident; OpenSearch heap ≤ 50% of node RAM, leave page cache.

## Performance Considerations

- GIN `fastupdate` batches pending inserts — periodic spikes; tune `gin_pending_list_limit` and watch autovacuum on FTS-heavy tables.
- OpenSearch refresh interval default 1 s trades indexing throughput for visibility; batch import windows set `refresh_interval=-1`.
- Bulk indexing beats single-doc API calls by 10–100×; size bulks 5–15 MB.
- Deep pagination kills engines (`from+size` window); teach clients cursors (`search_after`) past ~10k results.
- Cross-cluster replication for DR doubles cost; decide via RPO/RTO (Backups & PITR chapter) whether warm standby suffices.

## Summary

- Postgres FTS is the right default until relevance/write-scale demands say otherwise; know its ceiling symptoms.
- Dedicated engines trade ops weight for BM25 tuning, typo tolerance, facets, and horizontal search scale.
- Sync via outbox or CDC with idempotent consumers; never after-commit dual writes; monitor replication lag as an SLI.
- Relevance is engineered: BM25 knobs, field boosts, synonyms — validated on golden query sets, not vibes.
- Mappings evolve through alias-flipped reindexing; the engine is derived data, Postgres stays canonical.

## Cheat Sheet

| Concept | Description |
| ------------------------ | ------------------------------------------------------------ |
| `tsvector` + GIN | Postgres FTS core; generated column keeps it in sync |
| `websearch_to_tsquery` | User-safe query syntax (quoted phrases, OR, minus) |
| `ts_rank` limits | No TF saturation/IDF strength; weak for serious ranking |
| BM25 | TF saturation + IDF + length norm; engine default scorer |
| Field boost (`name^4`) | Weighted multi_match; primary relevance lever |
| CDC / outbox | Change-capture pipelines keeping engine in sync |
| Alias flip | Atomic cutover between index versions |
| Meilisearch/Typesense | Single-binary engines; typo tolerance + facets, RAM-resident |
| OpenSearch/Elasticsearch | JVM clusters; full DSL, aggregations, billions of docs |
| recall@k / MRR | Retrieval quality metrics for tuning regressions |

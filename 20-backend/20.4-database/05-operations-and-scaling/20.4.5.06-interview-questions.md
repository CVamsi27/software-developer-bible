# Database Interview Questions


## First Principles

This set probes database internals (→ 20.4.1), query execution plans (→ 20.4.2), transaction isolation and replication (→ 20.4.3), and production scaling (→ 20.4.5):

1. **The senior tells are trade-off statements**: "X when Y, Z when not-Y" — seniors state the constraints, failure modes, and operational trade-offs rather than reciting isolated definitions.
2. **Every question maps to an axiom chain, not a fact**: snapshot visibility, lock graphs, durability logging, and connection lifecycles govern valid production behavior. Derive the answer from underlying storage and concurrency invariants.

## Using this interview bank

These 30 authored questions are practice after the learning chapters. State the mechanism, trace a concrete result, then give the condition under which your answer changes. Code examples and their full setup belong in the linked source chapters; the short expressions here support an answer rather than forming one combined executable script.

Use [foundations revision](../01-postgresql-foundations/REVISION.md) and [transactions revision](../03-transactions-and-replication/REVISION.md) for recall before attempting this drill.

## Beginner Questions (5)

### 1. What is PostgreSQL?

**Answer:**
PostgreSQL is an extensible relational database server: clients send SQL through sessions, and backend processes execute plans over transactional data. Constraints govern valid states, MVCC governs visible row versions, and WAL supports durable recovery under the configured settings. JSONB and extensions expand the value/query model; they do not remove the need to understand concurrency or operations.

Follow-up: Explain which component owns a transaction and why creating a connection pool per HTTP request is wasteful.

### 2. What is a primary key and foreign key?

**Answer:**
A primary key uniquely identifies a row and excludes nulls. A foreign key requires a non-null reference to match an eligible referenced key, which can be a primary key or another supported unique key; the reference may also point to the same table. A nullable foreign-key value does not require a referenced row, so add NOT NULL if the relationship is mandatory.

A foreign key enforces referential integrity, but a join is possible without one and a foreign key does not itself establish a caller's authorization.

### 3. What is the difference between WHERE and HAVING?

**Answer:**
WHERE removes input rows before grouping; HAVING removes groups after aggregation. For example, `WHERE status = 'paid'` limits the orders counted, while `HAVING count(*) > 5` keeps only customers with more than five of those paid orders. Moving the status condition to HAVING is not the same operation: the condition needs to apply to each input row.

### 4. What is an index and why use it?

**Answer:**
An index organizes keys so an eligible query can locate or order candidate rows with less work than a full scan. A selective email lookup may use a B-tree path, while returning nearly the entire table can make a scan cheaper. A B-tree key lookup has tree-navigation cost, but returning many matches and fetching pages adds work; “every indexed query is O(log n)” is incomplete.

Indexes cost storage, build work and write maintenance. Unique indexes can enforce uniqueness. Verify the actual plan and workload benefit rather than promising that CREATE INDEX forces its use.

### 5. What is a JOIN?

**Answer:**
A join combines rows according to a condition. INNER retains matching pairs; LEFT retains every left row and supplies null right-side columns when no match exists; RIGHT reverses that direction; FULL preserves unmatched rows from both sides; CROSS creates all pairs.

If one customer has three orders, joining customer to orders produces three rows, not one customer summary. Group deliberately when computing totals; summing a repeated order-level total after joining its lines can overcount.

## Intermediate Questions (5)

### 6. Explain normalization and its forms.

**Answer:**
Normalization derives table boundaries from functional dependencies. 1NF removes repeating groups in the relational representation; 2NF removes partial dependencies of non-prime attributes on any candidate key; 3NF permits a non-trivial dependency only when its determinant is a superkey or its dependent attribute is prime. BCNF requires a superkey determinant for every non-trivial dependency.

In an order-line relation, product name depends on product ID while quantity depends on the whole line key. Separating those facts prevents a product rename from needing many line updates. Check lossless reconstruction and dependency preservation separately: a BCNF split can move a constraint across tables. Purchased price is a historical line fact, not a duplicate current catalog price.

### 7. What is the difference between DELETE and TRUNCATE?

**Answer:**
In PostgreSQL, DELETE removes selected rows and can use WHERE; TRUNCATE removes the whole table with an ACCESS EXCLUSIVE lock. Both are transactional and can be rolled back. DELETE fires row DELETE triggers; TRUNCATE fires TRUNCATE triggers rather than row DELETE triggers.

TRUNCATE does not reset sequences by default: specify RESTART IDENTITY to request that. Foreign-key relationships and RLS differ too: TRUNCATE has related-table restrictions and is outside RLS, so control its privilege separately. Faster bulk removal is not permission to bypass retention requirements.

### 8. What is the difference between INNER JOIN and LEFT JOIN?

**Answer:**
INNER JOIN excludes a customer without orders. LEFT JOIN retains that customer with null order columns. A condition such as `WHERE o.status = 'paid'` after a LEFT JOIN rejects those null rows, effectively removing unmatched customers; placing the condition in the join's ON clause instead can retain them.

Also distinguish `count(*)` from `count(o.id)`: the unmatched left row counts in the former but not the latter.

### 9. What is a transaction?

**Answer:**
A transaction gives its participating database statements one commit or rollback boundary. A transfer must debit and credit together; if the credit fails, rollback must undo the debit. ACID separates atomicity, encoded consistency, isolation and configured durability.

Atomicity alone does not protect a stale read-then-write decision. Use a condition, constraint, lock or appropriate isolation for the invariant. All statements must use the same session, and a rollback cannot recall an external charge or email.

### 10. What is an execution plan?

**Answer:**
A plan describes scans, filters, joins, sorts and their estimated costs and row counts. EXPLAIN does not execute the statement; EXPLAIN ANALYZE does and adds actual timing, rows and loops. Read inputs toward output and compare estimates with actual rows; account for repeated loops and avoid adding inclusive parent/child times.

A plan is not a complete explanation of end-to-end latency. Pool queueing, network transfer and application result processing need separate evidence. Lock and I/O waits during execution contribute to elapsed execution time. PostgreSQL 17+ supports `EXPLAIN ... SERIALIZE` to measure server-side result conversion, but not network transfer or client decoding. Executing a write for diagnostics has real side effects.

## Senior Questions (10)

### 11. Explain MVCC and how PostgreSQL implements it.

**Answer:**
MVCC keeps row versions so an ordinary read can choose the version visible to its snapshot. Read Committed refreshes its snapshot per statement; Repeatable Read and Serializable retain an established transaction snapshot. The transaction sees its own preceding writes in either case.

An ordinary reader can read 100 while a writer has an uncommitted 500. After commit, a later Read Committed SELECT can see 500 while an established Repeatable Read SELECT still sees 100. Same-row writers and locking reads can still wait or fail; some table locks block ordinary reads.

`xmin` identifies a version's creator; `xmax` can encode deletion/update or lock information, so nonzero does not prove deletion. A visible-row query is not a complete version history, and vacuum eventually reclaims versions no longer needed.

### 12. What is WAL and why is it important?

**Answer:**
WAL records changes before the corresponding data pages can be written durably. Under normal durable-commit settings, PostgreSQL can acknowledge after the required WAL flush without flushing every changed table page. Crash recovery replays required records to reconstruct committed state.

Archived WAL plus an appropriate base backup can support point-in-time recovery, but WAL on failed storage is not a backup. Asynchronous commit can acknowledge before local durability; synchronous replication adds a separately configured acknowledgment milestone.

### 13. How does PostgreSQL handle concurrent updates?

**Answer:**
PostgreSQL does not apply one universal “last-commit-wins” rule. At Read Committed, an UPDATE conflicting with an uncommitted updater waits; after that writer commits, it rechecks the predicate against the updated row. `SET balance = balance + 1` can incorporate the current balance, while an unconditional application-computed replacement can discard a prior change.

At Repeatable Read, a conflicting update to a row changed since the snapshot can fail with 40001. Serializable also rejects unsafe dependency patterns. Retry a known aborted transaction as a whole; do not predict failure solely from the isolation label without the interleaving and operation.

### 14. What is a GIN index?

**Answer:**
A Generalized Inverted Index (GIN) maps elements of composite values to rows containing them. It can support eligible array, JSONB containment or text-search predicates. For example, an array containment predicate `tags @> ARRAY['premium']` fits the appropriate array operator class; do not assume every expression such as `ANY(tags)` has the same index support.

Specify the operator and operator class. A whole-document JSONB GIN index does not automatically accelerate a text extraction comparison; an expression B-tree index may fit that scalar lookup instead. GIN writes and maintenance can be expensive.

### 15. What is the difference between logical and physical replication?

**Answer:**
Physical replication replays WAL for the PostgreSQL cluster on a compatible same-major standby; the hot standby is read-only while in recovery. Built-in logical replication applies published table changes to subscriber tables and can support selective copies and compatible cross-major migrations.

Logical replication needs schema coordination, replica identity for relevant mutations, sequence-state handling and conflict recovery. Allowing local subscriber writes does not establish safe multi-primary conflict resolution. Receipt, flush and replay are separate milestones in either operational design.

### 16. What is table partitioning?

**Answer:**
Partitioning exposes one logical table backed by child tables whose boundaries use ranges, lists or hashes. A time filter can let the planner prune irrelevant range partitions; a query without the relevant key may still read many partitions.

A monthly partition needs to exist before writes enter its range, unless an intentional default partition handles them. Indexes still matter, and global uniqueness constraints have partition-key restrictions. Retiring a partition is a data-retention and locking decision, not a harmless query optimization.

### 17. What is the N+1 query problem?

**Answer:**
N+1 means one query loads N parents and another query is issued per parent for children. Latency grows with round trips as well as database work. Eager loading or batching can reduce that sequence, but a Prisma include is not a universal promise of exactly one SQL statement: relation loading strategy and version matter.

Measure emitted queries, selected columns and result size. Loading every child into memory can replace a query-count problem with a memory/transfer problem; pagination and bounded relationships remain necessary.

### 18. How do you handle schema migrations in production?

**Answer:**
Expand the schema so old and new application versions can coexist, backfill with a race-safe resumable path, switch reads/writes, then contract only after old consumers are gone. Compatibility must cover APIs, jobs, replicas and rollback, not just one deployed process.

Use the production migration command and inspect locks, timeouts, volume and constraints. A concurrent index build permits ordinary writes while it runs, but still takes locks, can wait for transactions or snapshots, consumes resources and may leave an invalid index after failure. No tool or keyword alone guarantees zero downtime.

### 19. What is connection pooling and why is it needed?

**Answer:**
A pool reuses and bounds database connections, whose backend processes consume memory and scheduling capacity. Size the total budget across applications, workers and administration and measure queueing and active concurrency; there is no universal collapse threshold at 100 or 300 connections.

In session pooling, a client keeps its server connection for its session. In transaction pooling, the proxy can reassign it after transaction end, so a later transaction must not rely on server session state. Prepared-statement support is version/configuration specific; consult the pooler's feature matrix. Queues and client limits also need deadlines, overload handling and capacity tests.

### 20. What is a materialized view?

**Answer:**
A materialized view stores a query result, so reads avoid recomputing it. It changes when refreshed, whether manually or by a scheduled process; until then it can be stale. Choose and monitor the acceptable freshness gap.

PostgreSQL REFRESH CONCURRENTLY requires a populated view and a suitable unique index covering its rows. The keyword does not make every aggregation eligible, and a failed refresh does not create new current data. Check aggregation grain so joining line items does not multiply order totals.

## Systems and scaling questions (5)

### 21. Design a schema for a social media platform.

**Answer:**
Begin with access and integrity rules: one user owns each post, follows connect users, and a like is unique per user/post if that is the product rule. A composite key can prevent duplicate follows or likes; mandatory ownership needs NOT NULL as well as a foreign key. Decide whether self-follow is permitted and encode that rule.

Index the actual feed and reverse-lookup paths, paginate with a deterministic order, and plan deletion/retention. A list of four CREATE TABLE statements is not a complete social platform: feed generation, visibility, moderation, hot users and authorization still need decisions.

### 22. How would you optimize a query on a billion-row table?

**Answer:**
Ask which query and objective are failing. A selective lookup can work well on a billion rows with a suitable access path; an unbounded aggregate can still be expensive with indexes. Inspect representative plans, statistics, row distribution and concurrency before choosing the remedy.

Partitioning helps pruning/retention, a materialized view trades freshness for aggregation cost, and a replica offloads eligible reads but may lag. BRIN can help physically correlated ranges; table size alone does not make it suitable. Compare the resulting write, storage and recovery costs.

### 23. Design a multi-tenant SaaS schema.

**Answer:**
Separate schemas or databases can give tenants distinct namespaces and operational boundaries, while shared tables use tenant keys and explicit row authorization. The appropriate boundary depends on isolation, recovery, migration and tenant-count requirements; separate databases are not automatically separate infrastructure.

For shared-table RLS, authorize the tenant, set context locally in one transaction and use a subject database role. Test SELECT, INSERT, UPDATE, DELETE and missing context; owners and BYPASSRLS roles can bypass. Composite tenant-aware references may also be needed to prevent cross-tenant relationships.

### 24. Design a real-time leaderboard.

**Answer:**
A PostgreSQL score table needs a clear score-update rule and unique user identity. Rank functions distinguish ties from row positions; define whether “top ten” means ten users or every user tied at the cutoff, and use a deterministic secondary ordering where appropriate.

A Redis sorted set can maintain scores and retrieve ranked members, but you must define its authoritative owner, persistence and rebuild path. It is not universally better for every real-time workload. Retries of additive scoring need idempotent event identity to avoid counting twice.

### 25. Design a distributed transaction system.

**Answer:**
A database transaction cannot atomically commit arbitrary remote inventory, payment and shipping operations. A saga records workflow progress, performs each step with stable operation identity and uses compensating actions where the business permits them. A refund is a new action, not erasure of a charge.

Persist state before acknowledging workflow progress and recover after every process/network failure. A charge timeout may mean the provider accepted it; reconcile before retry or compensation. Compensation can also fail and needs retries/escalation, while shipping may become irreversible. A try/catch chain without durable state is only a happy-path sketch.

## Follow-up Questions (5)

### 26. When would you choose MongoDB over PostgreSQL?

**Answer:**
Consider MongoDB when records are naturally document-owned and its querying, indexing, distribution and operational model meet the workload. Consider PostgreSQL when relational constraints, joins and SQL fit the requirements. Both can evolve schemas and support transactions; neither label determines correctness or speed.

Compare actual access paths, write ownership, transaction scope, consistency settings, recovery and team skills. Frequently changing fields can also fit PostgreSQL JSONB, and MongoDB can validate schemas. Do not use “ACID required” or “money” alone as a product verdict.

### 27. How do you handle schema changes without downtime?

**Answer:**
Make the expand phase compatible with both deployed versions, maintain both representations during overlap, and backfill without overwriting newer writes. The read cutover and later cleanup need explicit release/rollback gates. Dropping the old column too early breaks old jobs or rollback.

PostgreSQL can avoid a rewrite for supported non-volatile defaults, but ALTER TABLE still needs locks; “metadata-only” does not mean lock-free. NOT VALID is supported for specific constraints and avoids the initial full validation scan, not every lock; subsequent validation still consumes resources. Batch large backfills when their WAL, lock and replica cost justify it, and verify completeness rather than stopping after one empty batch.

### 28. What is the impact of isolation level on performance?

**Answer:**
Read Uncommitted behaves as Read Committed in PostgreSQL. Read Committed uses statement snapshots; Repeatable Read retains a transaction snapshot and can reject changed-row updates; Serializable additionally detects unsafe dependencies and can require complete retries.

There is no fixed speed ranking independent of workload, and stronger isolation does not simply mean more row locking. Stable snapshots can retain versions, contention can increase retry cost, and correctness needs depend on the invariant. Measure overhead and retries for the actual operation instead of selecting “Serializable for finance” by label.

### 29. How do you monitor PostgreSQL in production?

**Answer:**
Monitor workload execution time, end-to-end latency, pool queueing, active/waiting sessions, blockers, transaction age, temporary I/O, storage capacity, maintenance and replica progress. Distinguish cumulative statistics from current activity and define the measurement interval.

Dead/live tuple counts are estimates, not a byte-level bloat measurement. Query_start on an idle session describes its last query, not ongoing execution. Secure SQL/log visibility and connect an alert to an actionable diagnostic and recovery path.

### 30. What is the difference between optimistic and pessimistic locking?

**Answer:**
Optimistic control validates an expected version in the write predicate and increments it atomically; a stale token causes zero rows instead of overwriting newer intent. Every relevant writer must maintain that token. Automatically repeating a stale human replacement with the new token defeats the protection.

Pessimistic control holds a conflicting lock across a short decision and its writes in one transaction. Ordinary MVCC reads can still proceed, while conflicting writers wait or fail. Deadlocks, timeouts and connection failures mean retries/recovery can be necessary under either strategy; a single conditional update can be simpler when it expresses the invariant.

## Summary

A useful answer explains ownership, operation and observable result under stated conditions. Keep transaction outcome, concurrent decision safety, replica freshness and recovery as separate questions. Follow up with a changed interleaving, failed dependency or different query rather than relying on a feature name.

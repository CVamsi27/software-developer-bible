# PostgreSQL Performance Tuning


## Connection Tuning

**Why tune connections?** PostgreSQL creates a new process for every connection (unlike MySQL which uses threads). Each process uses ~5-10MB of memory. Too many connections = memory exhaustion and context switching overhead. Too few = queries queue and latency spikes. The formula: `connections = (CPU cores × 2) + 1` for SSDs. For a 4-core server, that's ~9 connections. PgBouncer multiplexes thousands of app connections onto these few database connections.


```sql
-- Check current connections
SELECT count(*) FROM pg_stat_activity;

-- Check connection by state
SELECT state, count(*) FROM pg_stat_activity GROUP BY state;

-- Kill idle connections
SELECT pg_terminate_backend(pid) 
FROM pg_stat_activity 
WHERE state = 'idle' 
AND query_start < now() - interval '10 minutes';

-- Optimal connection formula: (CPU cores × 2) + effective_spindle_count
-- For SSD: connections ≈ (cores × 2) + 1
-- For 4-core server: ~9 connections per PgBouncer instance
```


## Memory Tuning

**Key memory settings:** `shared_buffers` (25% of RAM) — the cache for data pages; `effective_cache_size` (75% of RAM) — tells the query planner how much memory is available for caching; `work_mem` (per-connection) — memory for sorting and hash operations. Too little `work_mem` means sorts spill to disk (slow). Too much means each connection consumes too much memory. Balance based on your workload — write-heavy apps need more `shared_buffers`, read-heavy apps need more `work_mem`.


```sql
-- shared_buffers: 25% of system memory
ALTER SYSTEM SET shared_buffers = '4GB'; -- For 16GB server

-- effective_cache_size: 75% of system memory
ALTER SYSTEM SET effective_cache_size = '12GB';

-- work_mem: 25MB per connection (be careful with many connections)
ALTER SYSTEM SET work_mem = '25MB';

-- maintenance_work_mem: 10-20% of memory for VACUUM, CREATE INDEX
ALTER SYSTEM SET maintenance_work_mem = '1GB';
```

## Query Optimization

```sql
-- Enable query statistics
CREATE EXTENSION pg_stat_statements;

-- Find slow queries
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Find queries with high total time
SELECT query, calls, total_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

## Index Optimization

```sql
-- Check index usage
SELECT 
  schemaname,
  tablename,
  indexname,
  idx_scan as scans,
  idx_tup_read as tuples_read,
  idx_tup_fetch as tuples_fetched
FROM pg_stat_user_indexes
ORDER BY idx_scan DESC;

-- Find unused indexes
SELECT 
  schemaname,
  tablename,
  indexname,
  idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
AND indexname NOT LIKE '%_pkey';

-- Check index bloat
SELECT 
  indexname,
  pg_size_pretty(pg_relation_size(indexname::regclass)) as size
FROM pg_indexes
WHERE tablename = 'appointments';
```

## VACUUM and ANALYZE

```sql
-- Check table bloat
SELECT 
  relname,
  n_live_tup,
  n_dead_tup,
  round(n_dead_tup::float / greatest(n_live_tup, 1) * 100, 2) as dead_ratio
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC;

-- Run VACUUM ANALYZE
VACUUM ANALYZE appointments;

-- Check autovacuum settings
SHOW autovacuum_vacuum_scale_factor;
SHOW autovacuum_analyze_scale_factor;

-- Tune for high-write tables
ALTER TABLE appointments SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_analyze_scale_factor = 0.005
);
```

## Partitioning

```sql
-- Check partition sizes
SELECT 
  schemaname,
  tablename,
  pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) as size
FROM pg_tables
WHERE tablename LIKE 'appointments_%'
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC;

-- Create partition for next month
CREATE TABLE appointments_2024_04 PARTITION OF appointments
  FOR VALUES FROM ('2024-04-01') TO ('2024-05-01');

-- Drop old partition
DROP TABLE appointments_2023_01;
```

## Monitoring Queries

```sql
-- Cache hit ratio (should be > 99%)
SELECT 
  sum(blks_hit) as cache_hits,
  sum(blks_read) as disk_reads,
  round(sum(blks_hit)::float / greatest(sum(blks_hit) + sum(blks_read), 1) * 100, 2) as hit_ratio
FROM pg_stat_database;

-- Active queries
SELECT 
  pid,
  now() - pg_stat_activity.query_start as duration,
  query,
  state
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC;

-- Lock monitoring
SELECT 
  l.pid,
  l.mode,
  l.granted,
  a.query,
  a.state
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
WHERE NOT l.granted;
```

## EXPLAIN ANALYZE Walkthrough

### Reading Query Plans

```sql
EXPLAIN ANALYZE
SELECT a.*, p.name as patient_name
FROM appointments a
JOIN patients p ON p.id = a.patient_id
WHERE a.clinic_id = 'clinic-123'
AND a.slot_start >= '2024-01-01'
AND a.status = 'booked'
ORDER BY a.slot_start;
```

**Sample output:**
```

  Sort Key: a.slot_start
  Sort Method: quicksort Memory: 25kB
  -> Hash Join (cost=100.00..1234.00 rows=1 width=50) (actual time=12.000..12.300 rows=10 loops=1)
        Hash Cond: (a.patient_id = p.id)

              Index Cond: ((clinic_id = 'clinic-123') AND (slot_start >= '2024-01-01'))

              Rows Removed by Filter: 20

```

### Key Metrics to Check

| Metric | What It Means | Action if Bad |
|--------|---------------|---------------|
| **Seq Scan** | Full table scan (slow for large tables) | Add index on filtered columns |
| **Rows Removed by Filter** | Rows scanned but not returned | Add more specific index |
| **Sort Method: Disk** | Sorting spilled to disk | Increase work_mem |
| **Nested Loop** | Join method (good for small sets) | OK if small rows |
| **Hash Join** | Join method (good for medium sets) | OK for most cases |
| **Merge Join** | Join method (good for sorted data) | OK if both sides sorted |

### Common Fixes

```sql
-- Problem: Seq Scan on large table
-- Fix: Add index
CREATE INDEX idx_appointments_clinic_slot ON appointments(clinic_id, slot_start);

-- Problem: Filter removes many rows after index scan
-- Fix: Add partial index
CREATE INDEX idx_appointments_booked ON appointments(clinic_id, slot_start)
WHERE status = 'booked';

-- Problem: Sort spills to disk
-- Fix: Increase work_mem (per session)
SET work_mem = '50MB';

-- Problem: Join uses Nested Loop with many rows
-- Fix: Ensure statistics are up to date
ANALYZE appointments;
ANALYZE patients;
```

## Common Interview Questions

**Q: How do you identify a slow query?**
1. Check pg_stat_statements for high mean_exec_time
2. Run EXPLAIN ANALYZE on the slow query
3. Look for Seq Scan, Sort on disk, Nested Loop with many rows
4. Add indexes or rewrite query

**Q: What's the difference between VACUUM and VACUUM FULL?**
- VACUUM: marks dead tuples as reusable, doesn't reclaim disk space
- VACUUM FULL: rewrites table, reclaims disk space, but locks the table
- Use VACUUM for routine maintenance, VACUUM FULL only for severe bloat

**Q: How do you prevent table bloat?**
- Tune autovacuum for high-write tables (lower scale_factor)
- Monitor dead tuple ratio
- Run VACUUM ANALYZE regularly
- Consider partitioning for time-series data

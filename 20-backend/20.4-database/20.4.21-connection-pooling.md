# Connection Pooling Deep-Dive

> **Why connections are expensive, how poolers work, and how to tune them for production PostgreSQL.**

---

## Why Connection Pooling Matters

Every PostgreSQL connection spawns a new backend process (~5-10MB RAM). At 200 connections, that's 1-2GB just for connection overhead. More critically, PostgreSQL's query planner degrades with too many concurrent connections — context switching, lock contention, and memory pressure all increase.

```
Without Pooling:
App Server 1 ──→ PostgreSQL (200 connections)
App Server 2 ──→ PostgreSQL (200 connections)
App Server 3 ──→ PostgreSQL (200 connections)
Total: 600 backend processes 💥

With PgBouncer:
App Server 1 ──→ PgBouncer ──→ PostgreSQL (20 connections)
App Server 2 ──→ PgBouncer ──→ PostgreSQL (20 connections)
App Server 3 ──→ PgBouncer ──→ PostgreSQL (20 connections)
Total: 60 logical connections, 20 actual processes ✅
```

---

## PgBouncer Architecture

PgBouncer is a lightweight connection pooler that sits between your application and PostgreSQL. It maintains a pool of actual PostgreSQL connections and multiplexes many client connections onto fewer server connections.

### Pooling Modes

| Mode | How It Works | Pros | Cons | Use Case |
|------|--------------|------|------|----------|
| **Session** | Client gets a server connection for entire session | Full PostgreSQL feature support | No actual pooling — just connection limiting | Legacy apps, LISTEN/NOTIFY |
| **Transaction** | Client gets a server connection per transaction | Best balance of features and efficiency | Prepared statements don't persist across transactions | Most applications (Recommended) |
| **Statement** | Client gets a server connection per statement | Maximum multiplexing | Breaks multi-statement transactions, no prepared statements | Simple CRUD only |

### Transaction Mode — The Sweet Spot

```sql
-- PgBouncer transaction mode:
-- 1. BEGIN → get connection from pool
-- 2. Execute queries
-- 3. COMMIT/ROLLBACK → return connection to pool
-- 4. Next transaction may use a DIFFERENT server connection
```

**Critical implication:** In transaction mode, `PREPARE` and `LISTEN/NOTIFY` won't work as expected because the server connection changes between transactions. Prisma uses prepared statements by default — you must disable them:

```typescript
// Prisma with PgBouncer transaction mode
const prisma = new PrismaClient({
  datasources: {
    db: {
      url: "postgresql://user:pass@localhost:6432/mydb?pgbouncer=true",
    },
  },
});
```

## Pool Sizing Formula

The right pool size depends on your workload. Too few connections = requests queue. Too many = PostgreSQL degrades.

### Rule of Thumb

```
Pool Size = (CPU Cores × 2) + Disk Spindles
```

| CPU Cores | Disk | Recommended Pool Size |
|-----------|------|-----------------------|
| 4 | SSD | 9 |
| 8 | SSD | 17 |
| 16 | NVMe | 33 |
| 8 | HDD | 10 |

### Measuring Actual Concurrency

```sql
-- Check how many connections are actually active
SELECT
  state,
  COUNT(*)
FROM pg_stat_activity
WHERE datname = 'mydb'
GROUP BY state;

-- If you consistently see 50+ active queries, your pool is too large
-- or you need query optimization, not more connections.
```

## PgBouncer Configuration

```ini
[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt

pool_mode = transaction
max_client_conn = 1000        # Max client connections (virtual)
default_pool_size = 20        # Actual server connections per pool
min_pool_size = 5             # Keep at least 5 connections warm
reserve_pool_size = 5         # Extra connections for traffic spikes
reserve_pool_timeout = 3      # Seconds before using reserve pool

server_lifetime = 3600        # Recycle server connections every hour
server_idle_timeout = 600     # Close idle server connections
client_idle_timeout = 0       # No timeout for idle clients

log_connections = 1
log_disconnections = 1
stats_period = 60
```

## Prisma-Specific Connection Management

### Common Pitfalls

```typescript
// ❌ BAD: Creating new PrismaClient per request (fork bomb)
app.get('/users', async (req, res) => {
  const prisma = new PrismaClient(); // Creates new connection pool!
  const users = await prisma.user.findMany();
  res.json(users);
});

// ✅ GOOD: Singleton PrismaClient
// lib/prisma.ts
const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};
export const prisma = globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma;
}
```

### Connection Pool Configuration

```typescript
const prisma = new PrismaClient({
  datasources: {
    db: {
      url: process.env.DATABASE_URL,
    },
  },
  // Prisma pool defaults:
  // - connection_limit: num_cpus * 2 + 1
  // - pool_timeout: 10 seconds
});
```

## Monitoring Pool Health

### PgBouncer Stats

```sql
-- Connect to PgBouncer admin port
psql -h localhost -p 6432 -U admin pgbouncer

-- Show pool statistics
SHOW POOLS;

-- Key columns to watch:
-- cl_active:    Client connections currently active
-- cl_waiting:   Client connections waiting for a server connection
-- sv_active:    Server connections currently active
-- sv_idle:      Server connections idle in pool

-- If cl_waiting > 0 consistently, your pool is too small.
```

### Prometheus Metrics

```yaml
# PgBouncer exporter config
scrape_configs:
  - job_name: 'pgbouncer'
    static_configs:
      - targets: ['localhost:9127']
    metrics_path: /metrics

# Key alerts
groups:
  - name: pgbouncer
    rules:
      - alert: PgBouncerWaitingClients
        expr: pgbouncer_pools_client_waiting_connections > 5
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "PgBouncer has {{ $value }} waiting clients"
```

## Connection Pooling Strategies

| Strategy | Description | When to Use |
|----------|-------------|-------------|
| **PgBouncer** | External pooler, sits between app and DB | Multiple app servers sharing one DB |
| **Application-level** | Prisma/HikariCP manages pool internally | Single app server, simple deployment |
| **PgBouncer + App-level** | Double pooling for maximum control | High-traffic production systems |
| **RDS Proxy** | AWS managed PgBouncer equivalent | AWS RDS/Aurora users |

### Docita Recommendation

For Docita with 25-100 clinics:
- Use **Prisma's built-in pool** (connection_limit: 10) for a single app server
- Add **PgBouncer** when scaling to multiple app servers or when using serverless (AWS Lambda)
- Set **pool_mode = transaction** to avoid prepared statement issues

## Interview Questions

**Q: "How would you configure connection pooling for a NestJS app with PostgreSQL?"**

> Use Prisma's built-in connection pool with connection_limit set to 10 (for a single app server). The pool mode is effectively "transaction" because Prisma returns connections after each query. If scaling to multiple app servers, add PgBouncer in front of PostgreSQL with pool_mode=transaction and default_pool_size=20. Monitor cl_waiting in PgBouncer stats — if it's consistently > 0, increase pool size or optimize slow queries.

**Q: "What happens when all connections in the pool are exhausted?"**

> Prisma throws "Too many database connections" error. The request will fail. Prevention: set pool_timeout to a reasonable value (10s), monitor active connections via pg_stat_activity, implement circuit breaker to stop sending requests when pool is saturated, and optimize queries to release connections faster.

**Q: "Why can't you use LISTEN/NOTIFY with PgBouncer transaction mode?"**

> LISTEN/NOTIFY requires a persistent server connection — the NOTIFY is delivered to the specific backend process that issued LISTEN. In transaction mode, the server connection changes between transactions, so the notification may go to a different backend. Workaround: use a dedicated connection (session mode) for LISTEN/NOTIFY, or use an in-memory pub/sub like Redis instead.

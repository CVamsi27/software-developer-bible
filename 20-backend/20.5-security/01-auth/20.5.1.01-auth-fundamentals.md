# Auth Fundamentals — Identity, Credentials & Crypto Primitives

> **Track position:** Stage 0 of the [auth track](INDEX.md) — read this before sessions/JWT/OAuth.

---

## Definition

**Authentication** verifies evidence for a claimed identity. **Authorization** decides whether that identity may perform a particular operation on a particular resource. Successfully validating an account's password does not prove that its presenter is the intended human, nor grant access to every record. Stolen evidence and missing resource checks are separate failure modes.

> **Textbook Definition:** Authentication verifies a claimed identity using accepted evidence; authorization evaluates an operation against access policy for that identity and resource. Identification, credential verification and permission evaluation are distinct security decisions.

| Term | Meaning |
| -------------------------- | ------------------------------------------------------------------------------------- |
| **Authentication (AuthN)** | Verifying evidence for a claimed user or service identity |
| **Authorization (AuthZ)** | Deciding which operations that identity may perform on which resources |
| **Identification** | Claiming an identity, such as a username or client ID |
| **Credential** | Evidence used for authentication, such as a password, OTP or key |
| **Hashing** | Mapping input to a digest without a decryption key; guesses can still be tested |
| **Encryption** | Reversible transformation with a key, used for confidentiality |
| **Signing** | Private-key operation verified with a public key, used for integrity and authenticity |
| **MFA** | Verifying evidence from at least two distinct factor categories |

---

## First Principles

Authentication rests on three unavoidable facts about proving identity over a wire:

1. **The server receives a claim, not direct knowledge of its presenter.** An account name is just bytes. A verifier needs accepted credential evidence or a valid assertion from a trusted issuer, with appropriate freshness and audience checks. Evidence can be stolen or replayed; confidence depends on that evidence and the protocol, not the name alone.
2. **Credentials are attack surface by existing.** Anything presented can be stolen, phished, replayed, or guessed — so the design limits the value of theft through slow salted hashing, short and justified lifetimes, rotation, multi-factor authentication, and rate limits. A verifier leak still permits guesses, and weak passwords can still be recovered.
3. **Authentication and authorization are different questions.** "Who are you?" ≠ "what may you do?" — conflating them (roles baked into identity, scopes implied by login) couples systems that change at different rates. RBAC/ABAC (→ 20.5.1.09) exist because authorization deserves its own model.

## How It Works


### 1. Protect each boundary in the authentication path

#### Store password verifiers, not passwords

Passwords need a password-specific, deliberately expensive hash. Give every password a unique random salt and store the encoded verifier with its algorithm and cost parameters. A maintained library generates salts and verifies candidates; do not encrypt passwords, use a fast general-purpose digest such as SHA-256, or compare password hashes with ordinary string equality.

```text
Password verification: password + salt + cost → Argon2id verifier
                       candidate + stored verifier → match / reject
Authenticated encryption: plaintext + key + nonce → ciphertext + tag
                          valid key + nonce + tag → plaintext / reject
Digital signature: message + private key → signature
                   message + signature + trusted public key → valid / invalid
```

Argon2id makes offline guesses consume configurable memory and time; bcrypt primarily raises compute cost. Benchmark the selected parameters under bounded login concurrency. No parameter choice makes a weak password unguessable.

```typescript
// Registration/login adapter sketch: password and candidatePassword are validated inputs.
import argon2 from 'argon2';

// register
const hash = await argon2.hash(password, {
  type: argon2.argon2id,
  memoryCost: 65536, // 64 MB
  timeCost: 3,
  parallelism: 1,
});
// login — the library verifies the encoded algorithm, salt and parameters
const ok = await argon2.verify(hash, candidatePassword);
```

```text
Example encoded format: $argon2id$v=19$m=65536,t=3,p=1$<salt>$<hash>
→ carries salt and parameters, allowing a successful login to rehash with a newer policy.
```

### 2. Generate credentials that cannot be guessed

Session IDs, reset tokens and other bearer credentials need cryptographically secure random bytes. `Math.random()` is designed for simulation, not secrecy.

```typescript
import { randomBytes } from 'node:crypto';

const sessionId = randomBytes(32).toString('base64url'); // 256 bits of CSPRNG entropy
```

### 3. Give signing and encryption separate jobs

A plain hash detects no attacker who can replace both a message and its digest. A **message authentication code (MAC)** such as HMAC uses a shared secret; every verifier that holds that secret can also forge a valid MAC. A digital signature separates private signing authority from public verification.
Neither mechanism encrypts its message. Verification must also bind the expected issuer, audience, message format and replay policy.

| Property | Shared-secret mechanisms (AES, HMAC) | Public-key mechanisms (RSA, ECDSA) |
| --------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Keys | Participating services share secret key material | A private key and related public key; roles depend on the operation |
| Capability | Each HMAC verifier can also create valid MACs | A signature verifier need not have signing capability |
| Key distribution | Protect the secret at every holder | Public keys may be distributed, but their identity and trust must be authenticated |
| Use when | Services share a trust boundary, such as a webhook HMAC contract | Many services verify tokens while one issuer retains signing authority |

Authenticated encryption, such as AES-GCM, protects confidentiality and detects ciphertext modification. It does not establish which application user may read the decrypted record.

### 4. Protect credentials in transit with TLS

Use TLS for every credential-bearing hop, including internal traffic. In a full certificate-based TLS 1.3 handshake, peers negotiate keys and authenticate the server before ordinary application data; resumed and early-data modes have different properties. **Mutual TLS (mTLS)** additionally authenticates the client through its certificate. Trusted certificate identity does not authorize every operation or protect a compromised endpoint.
See [TLS and the certificate lifecycle](../../../30-architecture/30.2-system-design/01-theory/30.2.1.23-tls-https-and-certificates.md) for handshake and replay boundaries.

### 5. Bound the work and exposure of login

An attacker can send many guesses or deliberately trigger expensive password verifications. Bound request size and attempts before Argon2id work, use asynchronous library APIs with bounded concurrency, and budget the memory cost across simultaneous logins. Combine account-oriented and network signals; IP-only limits are easy to distribute around and can penalize people behind shared networks.
Avoid permanent lockouts that an attacker can trigger. Screen new passwords against known-compromised credentials through a privacy-preserving mechanism, and use risk-based step-up authentication instead of treating a new IP alone as proof of compromise.

Argon2 verification is intentionally memory- and time-expensive and belongs at credential verification. Protected requests normally use cheaper session or token checks, though a remote session store can add network latency. Measure hash tail latency and memory use on deployed hardware; queue or reject excess load instead of accepting unbounded memory demand or silently weakening the hash policy.

For fixed-length secret verifiers such as MACs, use the cryptographic library's constant-time comparison after validating input shape. Password libraries already perform password-hash verification; do not replace their verifier with a custom digest comparison. Constant-time byte comparison does not make the entire request constant-time.

Record authentication outcomes, refresh and revocation events, and permission denials with correlation IDs. Keep credentials and full tokens out of logs, restrict access to the protected audit trail, and rehearse key and certificate rotation. Authentication still precedes authorization: default protected operations to deny, define anonymous access deliberately, and apply a resource and tenant policy to each authenticated operation.

## Summary

Verify identity with the right evidence: store passwords as salted, costed verifiers; generate bearer credentials with a CSPRNG; use MACs or signatures according to who may verify and who may issue; and protect every credential-bearing hop with TLS. Bound login work, keep authentication separate from authorization, and operate credential rotation and audit trails deliberately.

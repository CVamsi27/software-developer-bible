# Auth Fundamentals — Identity, Credentials & Crypto Primitives

>
> **Track position:** Stage 0 of the [auth track](INDEX.md) — read this before sessions/JWT/OAuth.

---

## Definition

**Authentication** verifies evidence for a claimed identity. **Authorization** decides whether that identity may perform a particular operation on a particular resource. Successfully validating an account's password does not prove that its presenter is the intended human, nor grant access to every record. Stolen evidence and missing resource checks are separate failure modes.

> **Textbook Definition:** Authentication verifies a claimed identity using accepted evidence; authorization evaluates an operation against access policy for that identity and resource. Identification, credential verification and permission evaluation are distinct security decisions.

| Term | Meaning | Interview one-liner |
| -------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **Authentication (AuthN)** | Verifying *identity* of a user/service | "Proving you are who you claim to be" |
| **Authorization (AuthZ)** | Verifying *permissions* of that identity | "Deciding what you're allowed to do" |
| **Identification** | Claiming an identity (username, client ID) | Comes before AuthN |
| **Credential** | Proof used for AuthN (password, OTP, biometric, key) | Something you know / have / are |
| **Hashing** | Maps input to a digest without a decryption key; guesses can still be tested | Choose a password-specific slow hash for password verification |
| **Encryption** | Two-way with a key: reversible | For *confidentiality* |
| **Signing** | Private-key operation over a message; verified with its public key | For *integrity + authenticity* |
| **MFA** | Two or more independent factors | Knows / has / is |

## First Principles

Authentication rests on three unavoidable facts about proving identity over a wire:

1. **The server receives a claim, not direct knowledge of its presenter.** An account name is just bytes. A verifier needs accepted credential evidence or a valid assertion from a trusted issuer, with appropriate freshness and audience checks. Evidence can be stolen or replayed; confidence depends on that evidence and the protocol, not the name alone.
2. **Credentials are attack surface by existing.** Anything presented can be stolen, phished, replayed, or guessed — so the entire discipline is reducing what a stolen credential is worth: slow salted hashing (a verifier leak makes guessing costly, but weak passwords can still be recovered), expiry, rotation, MFA (possession factor), and rate limits.
3. **Authentication and authorization are different questions.** "Who are you?" ≠ "what may you do?" — conflating them (roles baked into identity, scopes implied by login) couples systems that change at different rates. RBAC/ABAC (→ 20.5.1.09) exist because authorization deserves its own model.

## Why Do We Need It?

- HTTP is stateless and untrusted: protected requests need validated identity evidence; public endpoints can intentionally permit anonymous access.
- Password databases leak — the storage format determines whether leaked data is usable by attackers.
- Tokens/cookies travel over networks — primitives decide whether interception matters.
- Sensitive applications need least privilege, traceable access and a recovery policy; applicable legal obligations depend on jurisdiction, role and data.

**Choosing the wrong primitive creates predictable failure modes:**

| Mistake | Consequence |
| ---------------------------------------------- | ---------------------------------------------------------------------------- |
| Storing passwords with MD5/SHA-256 (fast hash) | Fast offline guessing; time depends on password strength and attack hardware |
| Encrypting passwords instead of hashing | Decryptable with the app's own key |
| Using `Math.random()` for tokens | Predictable session/token IDs |
| Rolling your own crypto ("XOR with key") | No established security analysis or misuse-resistant contract |
| Skipping TLS on internal hops | MITM inside the perimeter |

## How It Works

### 1. The three primitives

```text
Password verification: password + salt + cost → Argon2id verifier
                       candidate + stored verifier → match / reject
Authenticated encryption: plaintext + key + nonce → ciphertext + tag
                          valid key + nonce + tag → plaintext / reject
Digital signature: message + private key → signature
                   message + signature + trusted public key → valid / invalid
```

A plain hash does not authenticate a message: an attacker can replace both message and digest. A **message authentication code (MAC)** uses a shared secret, as in HMAC webhooks. Every holder of that secret can produce a valid MAC. A digital signature instead separates private signing capability from public verification. Neither encrypts the message. Verification must also bind the expected issuer, audience, message format and replay policy.

### 2. Password storage done right

```text
password ──► Argon2id(password, salt, memory=64MB, iterations=3) ──► store(digest + params)
login ──► recompute with SAME params ──► timing-safe compare
```

A fast digest makes each offline guess cheap. Argon2id makes guesses consume configurable memory and time; bcrypt primarily raises compute cost. Benchmark the selected parameters under bounded login concurrency. No parameter choice makes a weak password unguessable.

```typescript
// Registration/login adapter sketch: password and candidatePassword are validated inputs.
import argon2 from 'argon2';

// register
const hash = await argon2.hash(password, {
  type: argon2.argon2id,
  memoryCost: 65536, // 64 MB
  timeCost: 3,
  parallelism: 1,
});
// login — constant-time compare inside the lib
const ok = await argon2.verify(hash, candidatePassword);
```

```text
Stored format (self-describing): $argon2id$v=19$m=65536,t=3,p=1$<salt>$<digest>
→ lets you raise cost params later without invalidating old hashes (rehash-on-login).
```

### 3. Randomness for tokens

```typescript
import { randomBytes } from 'node:crypto';

const sessionId = randomBytes(32).toString('base64url'); // 256 bits of CSPRNG entropy
// NEVER Math.random() — not cryptographically secure.
```

### 4. Symmetric vs asymmetric (the mental model for JWT/webhooks/TLS)

| Property | Symmetric mechanisms (AES, HMAC) | Asymmetric mechanisms (RSA, ECDSA) |
| --------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Keys | Parties share secret key material | A private key and related public key; their roles depend on the operation |
| Capability | HMAC verifiers can also forge valid MACs | Signature verifiers need not have signing capability |
| Cost | Generally less work per operation; benchmark the actual choice | Algorithm, key size, operation and hardware dependent |
| Key distribution | Protect the secret at every holder | Public keys can be shared, but their identity and trust must still be authenticated |
| Use when | Same trust domain (sessions, webhook HMAC) | Different trust domains (JWT verified by many services, TLS, JWKS rotation) |

### 5. TLS — the non-negotiable base

Use TLS to protect credential-bearing traffic in transit. In a full certificate-based TLS 1.3 handshake, the peers negotiate keys and authenticate the server before ordinary application data; resumed and early-data modes have different properties. **Mutual TLS (mTLS)** additionally authenticates the client through its certificate. Trusted certificate identity does not authorize every operation or protect a compromised endpoint. See [TLS and the certificate lifecycle](../../../30-architecture/30.2-system-design/01-theory/30.2.1.23-tls-https-and-certificates.md) for the full handshake and replay boundaries.

## Code Examples

### Timing-safe comparison (why it exists)

This complete helper compares fixed-format SHA-256 verifier bytes. It does not replace the password library's verification routine or make the entire request constant-time.

```typescript
import { timingSafeEqual } from "node:crypto";

export function equalSha256(a: string, b: string): boolean {
  if (!/^[a-f0-9]{64}$/i.test(a) || !/^[a-f0-9]{64}$/i.test(b)) return false;
  return timingSafeEqual(Buffer.from(a, "hex"), Buffer.from(b, "hex"));
}
```

### Credential-stuffing defense stack

```text
1. Bound request sizes and authentication attempts BEFORE expensive Argon2id work
2. Per-account backoff with an abuse-resistant recovery path; indefinite lockout enables denial of service
3. Per-IP + per-device rate limiting
4. Check password against breached-corpus (haveibeenpwned k-anonymity API)
5. MFA prompt on new device/IP
```

## Real-World Use Cases

| Scenario | Primitive choice | Why |
| --------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Clinic SaaS storing clinician passwords | Argon2id, params versioned | Leak-resistant; upgradeable via rehash-on-login |
| Payment webhook from provider | Provider-defined HMAC over the required raw payload | Verify before parsing/mutation; include the provider's timestamp and replay contract |
| Microservices verifying user JWTs | RS256/ES256 + JWKS | Services verify with public key; issuer keeps private key; rotate without redeploying everyone |
| PHI columns at rest | AES-256-GCM envelope encryption | Confidentiality + tamper detection (GCM auth tag) |
| Session IDs | Unpredictable CSPRNG-generated identifiers | Also require protected transport/storage, lifetime, revocation and CSRF policy |

> Healthcare-grade pattern worth citing in interviews: per-row DEK encrypts each record; a KEK wraps the DEKs — rotating the KEK means re-wrapping small DEKs, not re-encrypting the whole dataset (envelope encryption).

## Common Mistakes

| Mistake | Why it fails | Instead |
| ------------------------------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| SHA-256 for passwords | Too fast → brute-forceable | Argon2id / bcrypt / scrypt |
| Salt = username or constant | Rainbow tables per-app | Unique random salt per password |
| Base64 "encryption" | Encoding ≠ encryption | AES-GCM with real KMS-managed keys |
| Secrets in env files committed to git | Permanent leak | Secret manager + rotation |
| Comparing hashes with `===` | Timing attack | `timingSafeEqual` |
| Unlimited login attempts | Credential stuffing | Rate limit + backoff + lockout |
| Treating internal TLS as complete access control | Transport protection does not authorize a caller's operation | Authenticate service identities and enforce resource-level permissions |

## Best Practices

- **Deny protected operations by default**; enumerate deliberately public routes and their anonymous policy.
- **Layer defenses**: TLS → credential check → rate limits → session/token issuance → authorization → row-level scoping. Each layer assumes the previous can fail.
- **Version your crypto parameters** so algorithms/costs can evolve (stored alongside each hash/token header).
- **Log security events** (login success/failure, token refresh, permission denial) to an append-only audit trail — but never log passwords or full tokens.
- **Rehearse rotation**: keys, certificates, and signing credentials must be rotatable without downtime.

---

## Performance Considerations

- Argon2id at 64 MiB × simultaneous verifications: budget concurrent logins accordingly (this is why login endpoints get dedicated rate limits and queues at scale).
- Verify-cost asymmetry is intentional: make *verification* expensive once per login, keep *per-request* checks cheap (measure token verification and session-store tail latency on the actual deployment).
- Use the library's asynchronous implementation and bound worker/concurrency queues. Reject excess load instead of accepting unbounded memory demand or silently weakening password costs.

---

## Summary

- AuthN ≠ AuthZ; interviews probe whether you keep them separate in design and in code enforcement points.
- Hashing verifies, encryption conceals, signatures authenticate — pick by job, never invent.
- Slow salted hashes (Argon2id) for passwords; CSPRNG for anything that must be unpredictable; appropriate library verification and fixed-format timing-safe secret comparisons.
- TLS/mTLS is the floor, not the ceiling.

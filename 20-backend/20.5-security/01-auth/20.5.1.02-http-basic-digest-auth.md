# HTTP Basic & Digest Authentication

> Stage 1 of the [Auth Learning Track](INDEX.md) — prev: [Auth Fundamentals](20.5.1.01-auth-fundamentals.md) · next: [API Keys](20.5.1.03-api-keys.md)


## Definition

HTTP Basic authentication (RFC 7617) sends `username:password` as Base64 in the `Authorization` request header. The server or reverse proxy decodes and verifies those credentials. When credentials are missing or invalid, an origin server responds with `401 Unauthorized` and a `WWW-Authenticate` challenge; a browser may show a login prompt, while other clients may prompt or use configured credentials.

> **Textbook Definition:** HTTP Basic sends encoded credentials within an authentication exchange; HTTP Digest computes a credential-derived response to a server challenge. Neither scheme alone provides the transport confidentiality and peer authentication of Transport Layer Security (TLS).

HTTP Digest authentication (RFC 7616) is a challenge-response scheme: the client derives a response from the credentials, server nonce and request details without sending the password itself. The standard supports SHA-256 and SHA-512/256 as well as legacy MD5. Digest does not replace TLS, and its verifier-storage and interoperability costs must be considered when maintaining an existing integration.

## First Principles

Basic/Digest auth are derivable from the simplest possible credential transport:

1. **Basic has no session exchange — credentials ride with each protected request.** Basic sends base64 (not encryption!) of user:password; protection comes entirely from TLS. That's the minimal viable credential transport: universal support, zero redirects, no session infrastructure.
2. **A reusable credential remains valuable after one leak.** TLS protects the channel, but a proxy or application can still expose an authorization header in logs. Digest avoids sending the password directly; bearer tokens still need protection against theft and replay.
3. **Credential transport does not define lifecycle policy.** Basic provides no standardized browser logout or token expiry. The server can disable an account, revoke a credential or restrict its permissions, but these controls must be implemented around the scheme.

## Why Do We Need It?

1. **It is the simplest possible HTTP credential mechanism** — no cookies, no redirects, no token endpoints; any HTTP client from curl to a smart lightbulb can speak it.
2. **It is stateless by design** — every request carries its own proof, so servers need no session store and load balancers need no affinity.
3. **It survives where browsers cannot run** — routers, IP cameras, proxy servers, and monitoring scrapers often only support Basic.
4. **It bootstraps understanding** — the `Authorization` header and the `401 / WWW-Authenticate` handshake introduced here are reused by Bearer tokens, API keys, and OAuth in later stages of this track.
5. **Digest exposes a challenge-response trade-off** — avoiding direct password transmission changes what verification material the server must retain.

## How It Works

### The Authorization Header Mechanics

The client concatenates a user ID, a colon and a password, Base64-encodes the resulting bytes, and prefixes them with the scheme name:

```http
credentials = Base64( username ":" password )

GET /admin HTTP/1.1
Host: internal.example.com
Authorization: Basic YWRtaW46czNjcmV0IQ==
```

Decoding `YWRtaW46czNjcmV0IQ==` yields `admin:s3cret!`. Anyone who sees the header can recover the password; Base64 is not a one-way function. TLS protects the exchange in transit, while plain HTTP exposes reusable credentials.

RFC 7617 uses the first colon as the separator, so a user ID cannot contain a colon but a password can. The default character encoding is unspecified for compatibility; a server can advertise `charset="UTF-8"` in its challenge, though that parameter is advisory and older clients may differ.

### The 401 Challenge Handshake

```text
┌────────────────────────────────────────────────────────────┐                                      ┌──────────┐
│  Client  │                                      │  Server  │
└────┬───────────────────────────────────────────────────────┘                                      └────┬─────┘
     │                                                 │
     │ 1. GET /admin                                   │
     │────────────────────────────────────────────────>│
     │                                                 │
     │ 2. 401 Unauthorized                             │
     │    WWW-Authenticate: Basic realm="Admin",       │
     │        charset="UTF-8"                          │
     │<────────────────────────────────────────────────│
     │                                                 │
     │ 3. User agent may prompt for credentials        │
     │    (other clients use configured credentials)   │
     │                                                 │
     │ 4. GET /admin                                   │
     │    Authorization: Basic YWRtaW46...             │
     │────────────────────────────────────────────────>│
     │                                                 │
     │ 5. Decode + verify credentials                  │
     │ 6. 200 OK (and Basic header resent on every     │
     │    subsequent request for the realm)            │
     │<────────────────────────────────────────────────│
```

Key details seniors are expected to know:

- The `realm` identifies a protection space in the challenge. A Basic authorization header carries the encoded credentials, not the realm value.
- Basic has no standardized browser logout operation. Browser credential caching varies; the server can still reject a disabled account or revoked credential on the next request.
- The server re-sends `401` if credentials fail; repeated failures should be rate-limited like a login endpoint.
- Because credentials ride every request, TLS termination must happen at a reviewed boundary; protect onward hops according to their threat model.

### Digest challenge-response and its storage cost

Digest demonstrates how to prove knowledge of a password without transmitting it. This trace uses the legacy MD5 variant for comparison; new compatible deployments should negotiate a supported stronger algorithm from RFC 7616.

```text
1. Server -> Client:
   WWW-Authenticate: Digest realm="example.com",
                     qop="auth",
                     nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093",
                     opaque="5ccc069c403ebaf9f0171e9517f40e41",
                     algorithm=MD5

2. Client computes:
   HA1 = MD5(username : realm : password)
   HA2 = MD5(method : uri)
   response = MD5(HA1 : nonce : nc : cnonce : qop : HA2)

3. Client -> Server:
   Authorization: Digest username="Mufasa",
                  realm="example.com",
                  nonce="...", uri="/dir/index.html",
                  qop=auth, nc=00000001,
                  cnonce="0a4f113b", response="6629fae4..."

4. Server recomputes the same hash from ITS copy of the
   password (or HA1) and compares. Match -> 200.
```

Replay resistance depends on nonce validation and freshness; the nonce count (`nc`) can help the server detect repeated requests. The client nonce (`cnonce`) varies the hash input to mitigate chosen-plaintext attacks. `qop=auth` binds authentication to request details; `auth-int` also includes a hash of the entity body. Neither encrypts the traffic. Important implementation costs remain:

| Weakness | Consequence |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Algorithm negotiation | RFC 7616 adds SHA-256 and SHA-512/256; legacy MD5 compatibility must not silently weaken policy |
| Password or credential-derived verifier | HA1 is password-equivalent for its realm; an ordinary Argon2/bcrypt password hash cannot directly verify the Digest response |
| Offline dictionary attacks | Capture one exchange, brute-force the password locally forever |
| Complexity | Interoperability bugs across browsers/proxies/clients |
| TLS still required | Digest provides no transport confidentiality; Basic over TLS permits conventional password-hash verification |

The decision boundary is verifier storage and the clients you must support. A challenge-response scheme can avoid sending a password while still leaving valuable credential-equivalent material on the server.

### Reverse-Proxy Pattern (nginx Basic Auth)

In real deployments Basic auth usually lives at the edge, not in application code:

```text
Internet ──TLS──> nginx ──internal hop──> app service
                    │
                    ├─ auth_basic checks .htpasswd
                    └─ forwards request only if authorized
```

This protects whole locations (`/stub_status`, admin UIs, staging environments) without touching app code. The same pattern fronts Prometheus, Grafana, Kibana, and legacy services that lack their own auth.

## Code Examples

### curl (the fastest sanity check)

```bash
# -u builds and attaches the Authorization header for you
curl -u admin:s3cret! https://internal.example.com/admin

# Explicitly — what -u does under the hood:
curl -H "Authorization: Basic $(printf 'admin:s3cret!' | base64)" \
     https://internal.example.com/admin

# Inspecting the challenge first:
curl -i https://internal.example.com/admin
# HTTP/1.1 401 Unauthorized
# WWW-Authenticate: Basic realm="Admin", charset="UTF-8"
```

### Server-side fetch client

```typescript
const callAdminApi = async (): Promise<Response> => {
  const username = process.env.ADMIN_USER;
  const password = process.env.ADMIN_PASS;
  if (!username || !password) throw new Error("Missing admin credentials");
  const token = Buffer.from(`${username}:${password}`, "utf8").toString("base64");

  const res = await fetch("https://internal.example.com/admin/users", {
    headers: {
      Authorization: `Basic ${token}`,
    },
  });

  if (res.status === 401) {
    throw new Error("Basic auth rejected — check credentials/realm");
  }
  return res;
};
```

### NestJS BasicAuthGuard

```typescript
import {
  CanActivate,
  ExecutionContext,
  Injectable,
  UnauthorizedException,
} from "@nestjs/common";
import * as argon2 from "argon2";

interface BasicCredentials {
  username: string;
  password: string;
}

@Injectable()
export class BasicAuthGuard implements CanActivate {
  private readonly passwordHash: string;

  constructor() {
    const hash = process.env.OPS_BOT_PASSWORD_HASH;
    if (!hash) throw new Error("Missing configured Argon2 password hash");
    this.passwordHash = hash;
  }

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest();
    const response = context.switchToHttp().getResponse();
    const credentials = this.parseHeader(request.headers.authorization);

    if (!credentials || !(await this.verify(credentials))) {
      response.setHeader(
        "WWW-Authenticate",
        'Basic realm="Internal", charset="UTF-8"'
      );
      throw new UnauthorizedException();
    }
    return true;
  }

  private parseHeader(header?: string | string[]): BasicCredentials | null {
    if (typeof header !== "string" || header.length > 4096) return null;
    const match = /^Basic +([A-Za-z0-9+/]+={0,2})$/i.exec(header);
    if (!match) return null;

    try {
      const bytes = Buffer.from(match[1], "base64");
      const canonical = bytes.toString("base64");
      if (match[1] !== canonical && match[1] !== canonical.replace(/=+$/, "")) {
        return null;
      }
      const decoded = new TextDecoder("utf-8", { fatal: true }).decode(bytes);
      const separator = decoded.indexOf(":"); // passwords may contain ':'
      if (separator === -1 || /[\x00-\x1f\x7f]/.test(decoded)) return null;
      return {
        username: decoded.slice(0, separator),
        password: decoded.slice(separator + 1),
      };
    } catch {
      return null;
    }
  }

  private async verify({ username, password }: BasicCredentials): Promise<boolean> {
    // Run password verification for every parsed username in this single-account example.
    const valid = await argon2.verify(this.passwordHash, password);
    return username === "ops-bot" && valid;
  }
}

// Controller usage
// @UseGuards(BasicAuthGuard)
// @Controller('internal')
// export class InternalController { ... }
```

This guard illustrates one configured service account on Nest's Express adapter. Install `argon2`, supply a provisioned Argon2id hash, and apply bounded authentication concurrency and rate limits; expensive password verification can otherwise exhaust the server. Keep these credentials in server-side clients rather than browser bundles. A multi-account implementation needs account-state checks and a consistent unknown-account verification path.

## Real-World Use Cases

### 1. Internal tools behind VPN/mTLS

- Admin panels and staging environments where users already sit on a trusted network
- Basic acts as a coarse outer gate; the app may add its own session layer inside

### 2. Health, metrics, and scrape endpoints

- `/healthz`, Prometheus targets, and status pages protected from public access
- Scrapers (which rarely speak OAuth) handle Basic natively

### 3. Legacy machine-to-machine integration

- Old ERP/CCTV/router integrations that predate token auth
- Contained by: TLS, IP allowlists, dedicated low-privilege accounts

### 4. Edge-of-network devices and proxies

- Routers, IP cameras, forward proxies (squid), and API gateways
- These ecosystems never migrated; risk accepted + segmented instead

### 5. One-off scripts and smoke tests

- A cron job hitting an internal endpoint benefits from a simple credential flow, with credential provisioning and rotation still required
- Evaluate separately scoped API keys or short-lived workload credentials when it becomes long-lived infrastructure

## Common Mistakes

1. **Serving Basic auth without TLS**: The header is trivially reversible; on plain HTTP every observer on the path captures reusable credentials.

2. **Treating Base64 as hashing**: Encoding is not protection. Interviewers reject candidates who say "it's hashed".

3. **Using user passwords with Basic on APIs**: No expiry, no logout, no rotation story. Prefer a browser session or a suitable delegated identity flow for user-facing products.

4. **Storing plaintext credentials for verification**: Digest forces password-equivalent storage, and naive Basic implementations often do too. Verify against Argon2id hashes, or use external identity.

5. **No rate limiting on the protected route**: Each request is a login attempt; unlimited retries enable brute force even over TLS.

6. **Assuming Digest replaces TLS or password-storage design**: Its stronger hash variants still need transport protection, nonce validation and credential-equivalent verifier storage.

## Best Practices

1. **Always terminate TLS before parsing Basic headers** — non-negotiable.

2. **Prefer dedicated service accounts per consumer**, so revocation does not break everyone sharing one credential.

3. **Rate-limit and alert on 401 storms** per IP and per username (credential stuffing detector).

4. **Verify stored password hashes with a password-hashing library** and handle unknown accounts consistently. A constant-time comparison of plaintext secrets does not protect password storage.

5. **Scope it down**: reserve Basic for internal/edge cases; user-facing products belong in stages 3-5 (sessions, JWT, OAuth).

6. **Put it in the proxy, not the app**, when the goal is blanket protection of a location tree.

7. **Document the logout limitation** to stakeholders — closing the tab does not end the session.

8. **Rotate via password change runbooks** and treat each rotation as an outage-risk event for integrated machines.

## Performance Considerations

| Aspect | Consideration |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Per-request verification | Password-hash verification is intentionally expensive; measure cost and bound authentication concurrency |
| Credential source | A configured service account may avoid a lookup; multiple accounts still need current revocation and permission state |
| TLS and keep-alive | Connection reuse changes handshake cost; measure it alongside the chosen verifier rather than assuming it dominates |
| Browser credential caching | Reduces prompts; server-side credential rejection still takes effect when verified on each request |
| Proxy offload | Moving auth to nginx removes work from app workers |

## Summary

HTTP Basic and Digest are the historical foundation of HTTP authentication. Key takeaways:

- Basic = `Base64(user:pass)` in `Authorization`, challenged via `401` + `WWW-Authenticate`
- Security depends entirely on TLS; the encoding provides none
- Each protected request carries credential evidence; browser logout is not standardized, while server-side revocation remains possible
- Digest sends a challenge response rather than the password; stronger algorithm variants exist, but TLS and verifier-storage controls remain necessary
- Legitimate remaining niche: internal tools, health/scrape endpoints, legacy machine-to-machine — behind TLS, rate limits, and least privilege
- Modern replacements: API keys (stage 2), sessions/JWT (stages 3-4), OAuth/OIDC (stage 5)

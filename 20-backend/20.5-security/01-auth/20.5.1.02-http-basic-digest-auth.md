# HTTP Basic & Digest Authentication

> Stage 1 of the [Auth Learning Track](INDEX.md) — prev: [Auth Fundamentals](20.5.1.01-auth-fundamentals.md) · next: [API Keys](20.5.1.03-api-keys.md)

> **TL;DR:** HTTP Basic auth sends `Base64(username:password)` in the `Authorization` header on every request — it is encoding, not encryption, so it is only acceptable over TLS. Digest auth was a challenge-response fix for the cleartext problem, built on MD5; TLS made it pointless and browsers have removed it. Seniors know the exact handshake, why Basic + no-TLS is fatal, and the narrow places Basic is still fine (internal tools, health endpoints, legacy machine-to-machine).
>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## First Principles

Basic/Digest auth are derivable from the simplest possible credential transport:

1. **HTTP has no login concept — credentials ride *with every request*.** Basic sends base64 (not encryption!) of user:password; protection comes entirely from TLS. That's the minimal viable credential transport: universal support, zero redirects, no session infrastructure.
2. **The password itself is the weakness.** Sending reusable secrets on every request means one TLS bypass or log leak = total compromise. Digest's hash challenge was the pre-TLS mitigation; it's obsolete because TLS made "never send the reusable secret" achievable properly (tokens, → 20.5.1.05).
3. **No logout, no expiry, no granularity.** Because credentials are replayed per-request and browsers cache them, the server controls nothing after the fact — the missing capabilities are exactly what session/token systems were invented to provide.

## Definition

HTTP Basic authentication is a scheme defined in RFC 7617 where the client proves identity by sending the string `username:password` Base64-encoded in the `Authorization` request header. The server (or reverse proxy) decodes it, verifies the credentials, and either processes the request or replies `401 Unauthorized` with a `WWW-Authenticate: Basic` header to trigger the browser's native login prompt.

HTTP Digest authentication (RFC 7616) is a challenge-response scheme: the server sends a nonce and the client responds with an MD5-derived hash of the credentials plus that nonce, so the raw password never crosses the wire. It is a legacy mechanism — deprecated in practice, removed from Chrome, and superseded entirely by "Basic over TLS" or bearer tokens.

## Why Do We Need It?

1. **It is the simplest possible HTTP credential mechanism** — no cookies, no redirects, no token endpoints; any HTTP client from curl to a smart lightbulb can speak it.
2. **It is stateless by design** — every request carries its own proof, so servers need no session store and load balancers need no affinity.
3. **It survives where browsers cannot run** — routers, IP cameras, proxy servers, and monitoring scrapers often only support Basic.
4. **It bootstraps understanding** — the `Authorization` header and the `401 / WWW-Authenticate` handshake introduced here are reused by Bearer tokens, API keys, and OAuth in later stages of this track.
5. **Digest teaches why challenge-response matters** — and why it still failed, which is exactly the tradeoff analysis interviewers probe.

## How It Works

### The Authorization Header Mechanics

The client concatenates username and password with a colon, Base64-encodes the result, and prefixes it with the scheme name:

```http
credentials = Base64( username ":" password )

GET /admin HTTP/1.1
Host: internal.example.com
Authorization: Basic YWRtaW46czNjcmV0IQ==
```

Decoding `YWRtaW46czNjcmV0IQ==` yields `admin:s3cret!`. Anyone who sees the header holds the password — there is no one-way function involved. This is why the scheme's security reduces entirely to the transport: **over HTTPS the encoding is irrelevant because the channel is encrypted; over plain HTTP it is equivalent to posting the password on a billboard**.

### The 401 Challenge Handshake

```text
┌────────────────────────────────────────────────────────────┐                                      ┌──────────┐
│  Client  │                                      │  Server  │
└────┬───────────────────────────────────────────────────────┘                                      └────┬─────┘
     │                                                 │
     │ 1. GET /admin                                   │
     │────────────────────────────────────────────────>│
     │                                                 │
     │ 2. 401 Unauthorized                             │
     │    WWW-Authenticate: Basic realm="Admin",       │
     │        charset="UTF-8"                          │
     │<────────────────────────────────────────────────│
     │                                                 │
     │ 3. Browser shows native login dialog            │
     │    (or client library injects credentials)      │
     │                                                 │
     │ 4. GET /admin                                   │
     │    Authorization: Basic YWRtaW46...             │
     │────────────────────────────────────────────────>│
     │                                                 │
     │ 5. Decode + verify credentials                  │
     │ 6. 200 OK (and Basic header resent on every     │
     │    subsequent request for the realm)            │
     │<────────────────────────────────────────────────│
```

Key details seniors are expected to know:

- The `realm` value scopes the credential prompt and is echoed by clients on later requests to the same protection space.
- There is **no logout**: the browser caches credentials until the tab/window closes, and some browsers keep them even longer. Revocation means changing the password.
- The server re-sends `401` if credentials fail; repeated failures should be rate-limited like a login endpoint.
- Because credentials ride every request, TLS termination must happen as close to zero plaintext hops as possible.

### Digest Challenge-Response (and Why It Died)

Digest was designed for the pre-TLS web: prove you know the password without transmitting it.

```text
1. Server -> Client:
   WWW-Authenticate: Digest realm="example.com",
                     qop="auth",
                     nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093",
                     opaque="5ccc069c403ebaf9f0171e9517f40e41",
                     algorithm=MD5

2. Client computes:
   HA1 = MD5(username : realm : password)
   HA2 = MD5(method : uri)
   response = MD5(HA1 : nonce : nc : cnonce : qop : HA2)

3. Client -> Server:
   Authorization: Digest username="Mufasa",
                  realm="example.com",
                  nonce="...", uri="/dir/index.html",
                  qop=auth, nc=00000001,
                  cnonce="0a4f113b", response="6629fae4..."

4. Server recomputes the same hash from ITS copy of the
   password (or HA1) and compares. Match -> 200.
```

The `nonce` blocks trivial replay, `nc` and `cnonce` defend against chosen-plaintext attacks, and `qop=auth` adds message integrity options. On paper this is elegant. In production it failed:

| Weakness | Consequence |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Built on MD5 | Hash family is broken; no migration path ever deployed at scale |
| Server must store the password (or unsalted HA1) | A DB leak is instantly usable offline; incompatible with bcrypt/Argon2 best practice |
| Offline dictionary attacks | Capture one exchange, brute-force the password locally forever |
| Complexity | Interoperability bugs across browsers/proxies/clients |
| TLS became ubiquitous | The problem Digest solved disappeared; Basic-over-TLS is simpler and compatible with real password hashing |
| Browser abandonment | Chrome deprecated Digest support in 2023 and has been phasing it out since; ecosystem is effectively dead |

Interview soundbite: *"Digest tried to fix the wire but poisoned the vault — to verify MD5 digests the server needs password-equivalent material, which breaks modern salted-slow-hash storage. TLS fixed the wire properly instead."*

### Reverse-Proxy Pattern (nginx Basic Auth)

In real deployments Basic auth usually lives at the edge, not in application code:

```text
Internet ──TLS──> nginx ──internal hop──> app service
                    │
                    ├─ auth_basic checks .htpasswd
                    └─ forwards request only if authorized
```

This protects whole locations (`/stub_status`, admin UIs, staging environments) without touching app code. The same pattern fronts Prometheus, Grafana, Kibana, and legacy services that lack their own auth.

## Code Examples

### curl (the fastest sanity check)

```bash
# -u builds and attaches the Authorization header for you
curl -u admin:s3cret! https://internal.example.com/admin

# Explicitly — what -u does under the hood:
curl -H "Authorization: Basic $(printf 'admin:s3cret!' | base64)" \
     https://internal.example.com/admin

# Inspecting the challenge first:
curl -i https://internal.example.com/admin
# HTTP/1.1 401 Unauthorized
# WWW-Authenticate: Basic realm="Admin", charset="UTF-8"
```

### fetch / browser client

```typescript
const callAdminApi = async (): Promise<Response> => {
  // btoa is available in browsers and Node >= 16
  const token = btoa(`${process.env.ADMIN_USER}:${process.env.ADMIN_PASS}`);

  const res = await fetch("https://internal.example.com/admin/users", {
    headers: {
      Authorization: `Basic ${token}`,
    },
  });

  if (res.status === 401) {
    throw new Error("Basic auth rejected — check credentials/realm");
  }
  return res;
};
```

### NestJS BasicAuthGuard

```typescript
import {
  CanActivate,
  ExecutionContext,
  Injectable,
  UnauthorizedException,
} from "@nestjs/common";
import crypto from "crypto";

interface BasicCredentials {
  username: string;
  password: string;
}

@Injectable()
export class BasicAuthGuard implements CanActivate {
  private readonly users = new Map<string, string>([
    // In production: load hashed credentials from config/vault
    ["ops-bot", process.env.OPS_BOT_PASSWORD ?? ""],
  ]);

  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const credentials = this.parseHeader(request.headers.authorization);

    if (!credentials || !this.verify(credentials)) {
      request.res?.setHeader(
        "WWW-Authenticate",
        'Basic realm="Internal", charset="UTF-8"'
      );
      throw new UnauthorizedException();
    }
    return true;
  }

  private parseHeader(header?: string): BasicCredentials | null {
    if (!header?.startsWith("Basic ")) return null;

    try {
      const decoded = Buffer.from(header.slice(6), "base64").toString("utf8");
      const separator = decoded.indexOf(":"); // passwords may contain ':'
      if (separator === -1) return null;
      return {
        username: decoded.slice(0, separator),
        password: decoded.slice(separator + 1),
      };
    } catch {
      return null;
    }
  }

  private verify({ username, password }: BasicCredentials): boolean {
    const expected = this.users.get(username);
    if (!expected || !password) return false;
    // Constant-time compare defeats timing oracles
    const a = Buffer.from(password);
    const b = Buffer.from(expected);
    return a.length === b.length && crypto.timingSafeEqual(a, b);
  }
}

// Controller usage
// @UseGuards(BasicAuthGuard)
// @Controller('internal')
// export class InternalController { ... }
```

### nginx Reverse-Proxy Protection

```bash
# Create the credentials file (bcrypt-hashed via htpasswd -B)
htpasswd -Bc /etc/nginx/.htpasswd opsuser
```

```text
server {
    listen 443 ssl;

    location /grafana/ {
        auth_basic           "Ops Tools";
        auth_basic_user_file /etc/nginx/.htpasswd;
        # limit_req zone=basicauth burst=10;  # rate-limit retries too
        proxy_pass http://127.0.0.1:3000/;
    }
}
```

## Real-World Use Cases

### 1. Internal tools behind VPN/mTLS

- Admin panels and staging environments where users already sit on a trusted network
- Basic acts as a coarse outer gate; the app may add its own session layer inside

### 2. Health, metrics, and scrape endpoints

- `/healthz`, Prometheus targets, and status pages protected from public access
- Scrapers (which rarely speak OAuth) handle Basic natively

### 3. Legacy machine-to-machine integration

- Old ERP/CCTV/router integrations that predate token auth
- Contained by: TLS, IP allowlists, dedicated low-privilege accounts

### 4. Edge-of-network devices and proxies

- Routers, IP cameras, forward proxies (squid), and API gateways
- These ecosystems never migrated; risk accepted + segmented instead

### 5. One-off scripts and smoke tests

- A cron job hitting an internal endpoint benefits from zero-setup statelessness
- Prefer migrating to API keys (next stage) once the script becomes infrastructure

## Common Mistakes

1. **Serving Basic auth without TLS**: The header is trivially reversible; on plain HTTP every observer on the path captures reusable credentials.

2. **Treating Base64 as hashing**: Encoding is not protection. Interviewers reject candidates who say "it's hashed".

3. **Using user passwords with Basic on APIs**: No expiry, no logout, no rotation story. Use tokens or keys for anything user-facing.

4. **Storing plaintext credentials for verification**: Digest forces password-equivalent storage, and naive Basic implementations often do too. Verify against Argon2id hashes, or use external identity.

5. **No rate limiting on the protected route**: Each request is a login attempt; unlimited retries enable brute force even over TLS.

6. **Choosing Digest for "extra security" today**: You inherit MD5-era constraints, lose slow-hash compatibility, and ship dead protocol code. Basic + TLS beats it.

## Best Practices

1. **Always terminate TLS before parsing Basic headers** — non-negotiable.

2. **Prefer dedicated service accounts per consumer**, so revocation does not break everyone sharing one credential.

3. **Rate-limit and alert on 401 storms** per IP and per username (credential stuffing detector).

4. **Compare credentials in constant time** (`timingSafeEqual`) to avoid timing leaks.

5. **Scope it down**: reserve Basic for internal/edge cases; user-facing products belong in stages 3-5 (sessions, JWT, OAuth).

6. **Put it in the proxy, not the app**, when the goal is blanket protection of a location tree.

7. **Document the logout limitation** to stakeholders — closing the tab does not end the session.

8. **Rotate via password change runbooks** and treat each rotation as an outage-risk event for integrated machines.

## Performance Considerations

| Aspect | Consideration |
| ------------------------------- | ------------------------------------------------------------------- |
| Per-request cost | Decode + compare is nanoseconds — cheaper than sessions/JWT signing |
| No lookup needed (static creds) | Fastest possible check when credentials live in config |
| TLS overhead dominates | Handshake/resumption cost dwarfs the auth scheme itself |
| Browser credential caching | Reduces prompts but prevents instant revocation |
| Proxy offload | Moving auth to nginx removes work from app workers |

## Summary

HTTP Basic and Digest are the historical foundation of HTTP authentication. Key takeaways:

- Basic = `Base64(user:pass)` in `Authorization`, challenged via `401` + `WWW-Authenticate`
- Security depends entirely on TLS; the encoding provides none
- Every request carries the credential: stateless, but unrevokable without password change and unlogoutable
- Digest solved cleartext transmission with nonce/MD5 challenges but required password-equivalent storage and is now dead (browser removal, TLS ubiquity)
- Legitimate remaining niche: internal tools, health/scrape endpoints, legacy machine-to-machine — behind TLS, rate limits, and least privilege
- Modern replacements: API keys (stage 2), sessions/JWT (stages 3-4), OAuth/OIDC (stage 5)

## Cheat Sheet
| Concept | Value |
| -------------------- | ----------------------------------------------------------- |
| Header (client) | `Authorization: Basic <base64(user:pass)>` |
| Challenge (server) | `401` + `WWW-Authenticate: Basic realm="..."` |
| Encoding vs security | Base64 encodes; TLS secures |
| Credential carriage | Every single request |
| Logout | Not supported (clears on browser close at best) |
| Digest core | `response = MD5(HA1 : nonce : nc : cnonce : qop : HA2)` |
| Digest fatal flaw | Requires password-equivalent storage (no bcrypt/Argon2) |
| Digest status | Legacy/dead — Chrome removed it; use Basic over TLS |
| Still OK for | Internal tools, health/metrics, legacy M2M, proxies |
| Never OK for | Public user-facing apps, plain HTTP, shared human passwords |

# HTTP Basic & Digest Authentication

> Stage 1 of the [Auth Learning Track](INDEX.md) — prev: [Auth Fundamentals](20.5.1.01-auth-fundamentals.md) · next: [API Keys](20.5.1.03-api-keys.md)

## Definition

HTTP Basic authentication (RFC 7617) sends `username:password` as Base64 in the `Authorization` request header. The server or reverse proxy decodes and verifies those credentials. When credentials are missing or invalid, an origin server responds with `401 Unauthorized` and a `WWW-Authenticate` challenge; a browser may show a login prompt, while other clients may prompt or use configured credentials.

> **Textbook Definition:** HTTP Basic sends encoded credentials within an authentication exchange; HTTP Digest computes a credential-derived response to a server challenge. Neither scheme alone provides the transport confidentiality and peer authentication of Transport Layer Security (TLS).

HTTP Digest authentication (RFC 7616) is a challenge-response scheme: the client derives a response from the credentials, server nonce and request details without sending the password itself. The standard supports SHA-256 and SHA-512/256 as well as legacy MD5. Digest does not replace TLS, and its verifier-storage and interoperability costs must be considered when maintaining an existing integration.

## First Principles

Basic and Digest solve a narrow problem: let an HTTP client prove possession of a credential on a protected request.

1. **Basic resends reusable credentials.** The header is Base64-encoded, not encrypted; TLS must protect every hop, and proxies or applications must redact it from logs.
2. **Digest changes what crosses the network, not the whole trust model.** Its challenge response avoids sending the password directly, but requires password-equivalent verifier material and still needs TLS, replay controls and careful client compatibility.
3. **The scheme does not define account lifecycle.** The application must provide revocation, rate limits and permissions. Basic has no standardized browser logout or credential-expiry mechanism.

## 1. Follow the credential through a request

#### The Authorization Header Mechanics

The client concatenates a user ID, a colon and a password, Base64-encodes the resulting bytes, and prefixes them with the scheme name:

```http
credentials = Base64( username ":" password )

GET /admin HTTP/1.1
Host: internal.example.com
Authorization: Basic YWRtaW46czNjcmV0IQ==
```

Decoding `YWRtaW46czNjcmV0IQ==` yields `admin:s3cret!`. Anyone who sees the header can recover the password; Base64 is not a one-way function. TLS protects the exchange in transit, while plain HTTP exposes reusable credentials.

RFC 7617 uses the first colon as the separator, so a user ID cannot contain a colon but a password can. The default character encoding is unspecified for compatibility; a server can advertise `charset="UTF-8"` in its challenge, though that parameter is advisory and older clients may differ.

#### The 401 Challenge Handshake

```text
┌────────────────────────────────────────────────────────────┐                                      ┌──────────┐
│  Client  │                                      │  Server  │
└────┬───────────────────────────────────────────────────────┘                                      └────┬─────┘
     │                                                 │
     │ 1. GET /admin                                   │
     │────────────────────────────────────────────────>│
     │                                                 │
     │ 2. 401 Unauthorized                             │
     │    WWW-Authenticate: Basic realm="Admin",       │
     │        charset="UTF-8"                          │
     │<────────────────────────────────────────────────│
     │                                                 │
     │ 3. User agent may prompt for credentials        │
     │    (other clients use configured credentials)   │
     │                                                 │
     │ 4. GET /admin                                   │
     │    Authorization: Basic YWRtaW46...             │
     │────────────────────────────────────────────────>│
     │                                                 │
     │ 5. Decode + verify credentials                  │
     │ 6. 200 OK (and Basic header resent on every     │
     │    subsequent request for the realm)            │
     │<────────────────────────────────────────────────│
```

Key details seniors are expected to know:

- The `realm` identifies a protection space in the challenge. A Basic authorization header carries the encoded credentials, not the realm value.
- Basic has no standardized browser logout operation. Browser credential caching varies; the server can still reject a disabled account or revoked credential on the next request.
- The server re-sends `401` if credentials fail; repeated failures should be rate-limited like a login endpoint.
- Because credentials ride every request, TLS termination must happen at a reviewed boundary; protect onward hops according to their threat model.

#### Digest challenge-response and its storage cost

Digest demonstrates how to prove knowledge of a password without transmitting it. This trace uses the legacy MD5 variant for comparison; new compatible deployments should negotiate a supported stronger algorithm from RFC 7616.

```text
1. Server -> Client:
   WWW-Authenticate: Digest realm="example.com",
                     qop="auth",
                     nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093",
                     opaque="5ccc069c403ebaf9f0171e9517f40e41",
                     algorithm=MD5

2. Client computes:
   HA1 = MD5(username : realm : password)
   HA2 = MD5(method : uri)
   response = MD5(HA1 : nonce : nc : cnonce : qop : HA2)

3. Client -> Server:
   Authorization: Digest username="Mufasa",
                  realm="example.com",
                  nonce="...", uri="/dir/index.html",
                  qop=auth, nc=00000001,
                  cnonce="0a4f113b", response="6629fae4..."

4. Server recomputes the same hash from ITS copy of the
   password (or HA1) and compares. Match -> 200.
```

Replay resistance depends on nonce validation and freshness; the nonce count (`nc`) can help the server detect repeated requests. The client nonce (`cnonce`) varies the hash input to mitigate chosen-plaintext attacks. `qop=auth` binds authentication to request details; `auth-int` also includes a hash of the entity body. Neither encrypts the traffic.
Important implementation costs remain:

| Weakness | Consequence |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Algorithm negotiation | RFC 7616 adds SHA-256 and SHA-512/256; legacy MD5 compatibility must not silently weaken policy |
| Password or credential-derived verifier | HA1 is password-equivalent for its realm; an ordinary Argon2/bcrypt password hash cannot directly verify the Digest response |
| Offline dictionary attacks | Capture one exchange, brute-force the password locally forever |
| Complexity | Interoperability bugs across browsers/proxies/clients |
| TLS still required | Digest provides no transport confidentiality; Basic over TLS permits conventional password-hash verification |

The decision boundary is verifier storage and the clients you must support. A challenge-response scheme can avoid sending a password while still leaving valuable credential-equivalent material on the server.

## 2. Put verification at a controlled boundary

#### curl (the fastest sanity check)

```bash
# -u builds and attaches the Authorization header for you
curl -u admin:s3cret! https://internal.example.com/admin

# Explicitly — what -u does under the hood:
curl -H "Authorization: Basic $(printf 'admin:s3cret!' | base64)" \
     https://internal.example.com/admin

# Inspecting the challenge first:
curl -i https://internal.example.com/admin
# HTTP/1.1 401 Unauthorized
# WWW-Authenticate: Basic realm="Admin", charset="UTF-8"
```

#### Server-side fetch client

```typescript
const callAdminApi = async (): Promise<Response> => {
  const username = process.env.ADMIN_USER;
  const password = process.env.ADMIN_PASS;
  if (!username || !password) throw new Error("Missing admin credentials");
  const token = Buffer.from(`${username}:${password}`, "utf8").toString("base64");

  const res = await fetch("https://internal.example.com/admin/users", {
    headers: {
      Authorization: `Basic ${token}`,
    },
  });

  if (res.status === 401) {
    throw new Error("Basic auth rejected — check credentials/realm");
  }
  return res;
};
```

#### NestJS BasicAuthGuard

```typescript
import {
  CanActivate,
  ExecutionContext,
  Injectable,
  UnauthorizedException,
} from "@nestjs/common";
import * as argon2 from "argon2";

interface BasicCredentials {
  username: string;
  password: string;
}

@Injectable()
export class BasicAuthGuard implements CanActivate {
  private readonly passwordHash: string;

  constructor() {
    const hash = process.env.OPS_BOT_PASSWORD_HASH;
    if (!hash) throw new Error("Missing configured Argon2 password hash");
    this.passwordHash = hash;
  }

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest();
    const response = context.switchToHttp().getResponse();
    const credentials = this.parseHeader(request.headers.authorization);

    if (!credentials || !(await this.verify(credentials))) {
      response.setHeader(
        "WWW-Authenticate",
        'Basic realm="Internal", charset="UTF-8"'
      );
      throw new UnauthorizedException();
    }
    return true;
  }

  private parseHeader(header?: string | string[]): BasicCredentials | null {
    if (typeof header !== "string" || header.length > 4096) return null;
    const match = /^Basic +([A-Za-z0-9+/]+={0,2})$/i.exec(header);
    if (!match) return null;

    try {
      const bytes = Buffer.from(match[1], "base64");
      const canonical = bytes.toString("base64");
      if (match[1] !== canonical && match[1] !== canonical.replace(/=+$/, "")) {
        return null;
      }
      const decoded = new TextDecoder("utf-8", { fatal: true }).decode(bytes);
      const separator = decoded.indexOf(":"); // passwords may contain ':'
      if (separator === -1 || /[\x00-\x1f\x7f]/.test(decoded)) return null;
      return {
        username: decoded.slice(0, separator),
        password: decoded.slice(separator + 1),
      };
    } catch {
      return null;
    }
  }

  private async verify({ username, password }: BasicCredentials): Promise<boolean> {
    // Run password verification for every parsed username in this single-account example.
    const valid = await argon2.verify(this.passwordHash, password);
    return username === "ops-bot" && valid;
  }
}

// Controller usage
// @UseGuards(BasicAuthGuard)
// @Controller('internal')
// export class InternalController { ... }
```

This guard illustrates one configured service account on Nest's Express adapter. Install `argon2`, supply a provisioned Argon2id hash, and apply bounded authentication concurrency and rate limits; expensive password verification can otherwise exhaust the server. Keep these credentials in server-side clients rather than browser bundles.
A multi-account implementation needs account-state checks and a consistent unknown-account verification path.

## 3. When Basic or Digest still fits

Basic can be a reasonable coarse gate for a protected internal tool, a scraper, a legacy integration or a one-off server-side client when every hop uses TLS and each caller has a dedicated, low-privilege credential. A reverse proxy can protect a whole location tree, but that edge check does not replace application authorization for user- or resource-specific operations. Do not use a human's everyday password as a new API credential.

Rate-limit attempts and bound password-hash concurrency: Basic verification can perform expensive password-hash work on every request. If the integration needs long-lived machine identity, independent scopes or frequent rotation, a scoped API key or short-lived workload credential usually gives a clearer lifecycle. Digest is rarely a good new-system choice: its challenge-response math and verifier storage add complexity without replacing TLS or replay controls.

## Summary

Basic sends reusable credentials in an encoded header; Digest sends a challenge response derived from credential material. Neither supplies TLS, an account lifecycle or resource authorization. Keep them only where client compatibility or a coarse internal gate justifies the cost, and bound verification work, protect every hop and make revocation explicit.

# API Keys

> Stage 2 of the [Auth Learning Track](INDEX.md) — prev: [HTTP Basic & Digest](20.5.1.02-http-basic-digest-auth.md) · next: [Sessions & Cookies](20.5.1.04-sessions-cookies.md)

> **TL;DR:** An API key is a long-lived, high-entropy secret that identifies an application (not a human) to your API. Done right: generate with a CSPRNG, show the customer only a prefix (`sk_live_...`), store only a SHA-256 hash, scope every key, bind rate limits, and rotate via dual-key grace windows. Done wrong: an unscoped password-equivalent blob in a `.env` file that leaks once and owns your platform.
>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## First Principles

API keys answer one narrow question: *which application is calling?*

1. **A key identifies an app, not a human.** No user context, no consent flow, no scopes-per-user — that's its honesty and its limit. Whenever you need "acting on behalf of user X," keys alone are the wrong tool (OAuth, → 20.5.1.06).
2. **A static secret is only as safe as its storage.** Keys leak via repos, logs, and frontend bundles — hence server-side-only, environment storage, rotation, and scoping (keys that can only read) as the entire defense. Detection (leak scanners) matters as much as prevention because leaks are statistical certainties.
3. **Keys are infrastructure auth, not user auth.** Rate limiting, billing, and service identification are what they're for — using them as login credentials couples app identity to user identity and blocks per-user permission models.

## Definition

An API key is a cryptographically random token issued to a developer, service, or partner so their applications can call your API. Unlike a session cookie or JWT it does not represent a signed-in human; unlike Basic auth it is generated server-side, revocable independently of any user account, and (when stored hashed) safe at rest.

The industry-standard shape is a prefixed random string:

```text
sk_live_7fJd2Kx9QmLpV4nRtY8wZ3aB6cD0eF1gH5iJ
└─┬──┘ └┬┘ └──────────── 32 bytes CSPRNG ───────┘
  │     └─ environment marker (live vs test)
  └─ key family / brand prefix
```

## Why Do We Need It?

1. **Machine-to-machine identity without user context** — cron jobs, CI pipelines, backend services, and third-party developers need credentials with no login flow.
2. **Independent lifecycle** — issue, scope, rotate, and revoke per application, without touching user accounts or passwords.
3. **Billing and attribution** — usage metering, quotas, and per-customer analytics key off the key record.
4. ** blast-radius control** — scopes + rate limits + IP allowlists mean one leaked key exposes a slice, not the whole API.
5. **Developer experience** — keys are trivially usable from curl/SDKs; no redirects, certificates, or signing libraries required.
6. **A stepping stone** — understanding where static keys stop working leads directly to OAuth client-credentials (stage 5).

## How It Works

### Generation: CSPRNG Only

Keys must come from a Cryptographically Secure Pseudo-Random Number Generator. `Math.random()` is seeded predictably and must never touch credential material. In Node.js:

```text
crypto.randomBytes(32).toString("base64url")
-> 256 bits of entropy, URL-safe, no padding characters
```

32 bytes (256 bits) makes offline brute force impossible even though you hash with fast SHA-256 — the entropy does the work bcrypt would do for low-entropy passwords.

### Storage: Hash at Rest, Show the Prefix

```text
Issuance time:
  full_key   = sk_live_a1B2c3D4...        (shown ONCE to developer)
  prefix     = sk_live_a1B2c3D4           (first ~12-16 chars)
  key_hash   = SHA-256(full_key)          (stored in DB)

Verification time:
  incoming -> sha256(incoming) -> constant-time compare vs key_hash
```

Why SHA-256 instead of bcrypt/Argon2-style slow hashes? Passwords are chosen by humans and must resist offline guessing; API keys are 256-bit random values with nothing to guess. A fast hash lets you index/lookup by hash directly and keeps verification O(1). This asymmetry is a favorite interview probe — see Common Mistakes #4 for the reverse error.

The prefix is stored in plaintext on purpose: dashboards display `sk_live_a1B2…` so users can identify which key to rotate without the system ever holding the full secret.

### Lookup-by-Prefix Pattern

```text
1. Client sends:  Authorization: Bearer sk_live_a1B2c3D4e5F6...
2. Extract prefix = first N chars up to a fixed boundary
3. SELECT * FROM api_keys WHERE prefix = 'sk_live_a1B2' AND revoked_at IS NULL
4. candidate_hash = SHA-256(presented key)
5. timingSafeEqual(candidate_hash, row.key_hash)?
      yes -> load scopes/rate limits onto request
      no  -> 401 (and increment failure counters)
```

Prefix lookup turns an unindexed full-table scan into a single indexed hit, while the final comparison still uses the full hash — a leaked prefix alone is useless.

### Rotation & Revocation Strategies

```text
Dual-key rotation window (zero downtime):

 Day 0        key v1 active
              create key v2 (same scopes), mark rotated_at
 Day 0..N     BOTH accepted; dashboards nudge "migrate to v2"
 Day N        v1 auto-expires (grace window); audit shows who never moved

Hard revoke:  revoked_at = now()  -> 401 within cache TTL (keep TTL seconds!)
```

Rules seniors state out loud:

- **Rotation** = planned, graceful, dual-active; **revocation** = emergency, immediate, breaking by design.
- Grace windows should be short (24h-7d) and enforced by `expires_at`, not human memory.
- Never rotate by in-place mutation of the hash — create a new row so audit history survives.

### Per-Key Scopes, Rate Limits, IP Binding

```text
api_keys
├── id, owner_id, name, prefix, key_hash
├── scopes          ["invoices:read", "invoices:write"]
├── rate_limit_tier "standard" | "premium"       -> bucket per key
├── ip_allowlist    ["203.0.113.7", "198.51.100.0/24"]
└── expires_at, last_used_at, revoked_at
```

Every property is checked in the guard *before* the handler runs: scopes gate authorization, the rate limiter consumes tokens per key id, and the allowlist rejects unexpected source IPs even when the key itself is valid.

## Code Examples

### Key Generation (TypeScript)

```typescript
import crypto from "crypto";

interface GeneratedKey {
  fullKey: string;
  prefix: string;
  keyHash: string;
}

const generateApiKey = (env: "live" | "test" = "live"): GeneratedKey => {
  const raw = crypto.randomBytes(32).toString("base64url");
  const fullKey = `sk_${env}_${raw}`;
  const prefix = fullKey.slice(0, 16); // enough to identify, useless alone
  const keyHash = crypto.createHash("sha256").update(fullKey).digest("hex");

  return { fullKey, prefix, keyHash };
};

const hashIncomingKey = (presentedKey: string): string =>
  crypto.createHash("sha256").update(presentedKey).digest("hex");
```

### NestJS ApiKeyGuard (lookup-by-prefix, scopes, timing-safe)

```typescript
import {
  CanActivate,
  ExecutionContext,
  ForbiddenException,
  Injectable,
  SetMetadata,
  UnauthorizedException,
} from "@nestjs/common";
import crypto from "crypto";
import { Reflector } from "@nestjs/core";

export const SCOPES_KEY = "required_scopes";
export const RequireScopes = (...scopes: string[]) =>
  SetMetadata(SCOPES_KEY, scopes);

interface ApiKeyRecord {
  id: string;
  ownerId: string;
  keyHash: string;
  scopes: string[];
  ipAllowlist: string[];
  expiresAt: Date | null;
}

@Injectable()
export class ApiKeyGuard implements CanActivate {
  constructor(
    private readonly reflector: Reflector,
    private readonly keys: ApiKeyRepository // thin Prisma/service wrapper
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const req = context.switchToHttp().getRequest();
    const presented = this.extractBearer(req);

    if (!presented?.startsWith("sk_")) throw new UnauthorizedException();

    const record = await this.keys.findByPrefix(presented.slice(0, 16));
    const presentedHash = crypto
      .createHash("sha256")
      .update(presented)
      .digest();

    if (
      !record ||
      !crypto.timingSafeEqual(Buffer.from(record.keyHash, "hex"), presentedHash)
    ) {
      await this.keys.recordFailure(record?.id ?? null);
      throw new UnauthorizedException();
    }

    if (record.expiresAt && record.expiresAt < new Date()) {
      throw new UnauthorizedException("API key expired");
    }

    if (
      record.ipAllowlist.length > 0 &&
      !record.ipAllowlist.includes(req.ip)
    ) {
      throw new ForbiddenException("Source IP not allowlisted for this key");
    }

    const required = this.reflector.get<string[]>(
      SCOPES_KEY,
      context.getHandler()
    ) ?? [];
    const missing = required.filter((s) => !record.scopes.includes(s));
    if (missing.length > 0) {
      throw new ForbiddenException(`Missing scopes: ${missing.join(", ")}`);
    }

    req.apiKey = { id: record.id, ownerId: record.ownerId, scopes: record.scopes };
    return true;
  }

  private extractBearer(req: { headers: Record<string, string> }): string | null {
    const header = req.headers.authorization;
    return header?.startsWith("Bearer ") ? header.slice(7) : null;
  }
}

interface ApiKeyRepository {
  findByPrefix(prefix: string): Promise<ApiKeyRecord | null>;
  recordFailure(id: string | null): Promise<void>;
}
```

### Controller Wiring

```typescript
@Controller("invoices")
@UseGuards(ApiKeyGuard)
export class InvoiceController {
  @Get()
  @RequireScopes("invoices:read")
  list(@Req() req: RequestWithApiKey) {
    return this.invoices.listForOwner(req.apiKey.ownerId);
  }

  @Post()
  @RequireScopes("invoices:write")
  create(@Body() dto: CreateInvoiceDto) {
    return this.invoices.create(dto);
  }
}
```

## Real-World Use Cases

### 1. Public developer platforms

- Stripe/Twilio style `sk_live_` / `sk_test_` pairs
- Test-mode keys hit sandbox data; live keys are scoped and billed separately

### 2. First-party internal services

- Cron workers and queue consumers authenticate with scoped keys when OAuth/mTLS is overkill
- Each job gets its own key so logs attribute failures precisely

### 3. CI/CD deploy pipelines

- Pipeline holds a deployment-scoped key limited to release endpoints
- Rotated automatically by secrets manager on schedule

### 4. Rate-limited partner tiers

- Partners buy throughput: key maps to a quota bucket (e.g., 1k req/min)
- Overage returns `429` with headers, not silent throttling

### 5. Webhook consumers

- Outbound webhooks signed/identified by the receiving party's key id
- Revoking the key instantly silences delivery to a misbehaving consumer

## Common Mistakes

1. **Generating keys with `Math.random()`**: Predictable output makes keys guessable. Only `crypto.randomBytes` (or equivalent CSPRNG).

2. **Storing full keys in plaintext**: One SQL dump leaks every customer's identity and billing. Store SHA-256 hashes plus prefixes only.

3. **No scopes — one god-key per customer**: Any leak becomes total compromise. Default-deny with explicit scope grants.

4. **Using bcrypt/Argon2 for API keys**: Not wrong cryptographically, but pointless — 256-bit random has no brute-force surface, and slow hashes break hash-indexed lookup. Save slow hashing for passwords.

5. **Revocation delayed by caching**: If guards cache key records for 60s, "immediate" revocation lies. Short-TTL caches must check `revokedAt` freshness for destructive operations.

6. **Silent rotation**: Swapping keys without dual-active windows breaks every customer integration overnight. Rotate with overlap and comms.

## Best Practices

1. **Generate with CSPRNG, 256-bit minimum**, URL-safe encoding.

2. **Show the full key exactly once**, then persist only `SHA-256(key)` and an identifying prefix.

3. **Namespace prefixes by environment** (`sk_live_`, `sk_test_`) to make wrong-environment mistakes visible in logs.

4. **Scope every key** and enforce scopes in the guard layer, not deep in business logic.

5. **Bind rate-limit buckets and optional IP allowlists per key** so abuse is contained and attributable.

6. **Rotate via dual-key grace windows** with hard `expires_at`; automate expiry.

7. **Track `last_used_at`** and surface stale keys in dashboards — unused keys are standing risk.

8. **Log key id (never the key)** on every authenticated request for forensics.

9. **Rate-limit failed verifications** like login attempts to blunt brute-force probing.

10. **Prefer OAuth client-credentials when delegation, consent, or short-lived tokens matter** — see the decision table below.

## Performance Considerations

| Aspect | Consideration |
| --------------------- | ------------------------------------------------------------------- |
| Verification cost | SHA-256 + indexed prefix lookup ≈ sub-millisecond |
| Caching | Cache records by key id but re-check `revokedAt` within a small TTL |
| DB growth | Rotation creates rows — archive dead keys periodically |
| Rate limiter coupling | Token buckets keyed by key id add Redis hop; budget p99 accordingly |

## Summary

API keys are the workhorse credential for application-to-API traffic. Key takeaways:

- Keys identify applications/services, not humans — user flows belong to later stages
- CSPRNG generation (256-bit), SHA-256-at-rest, prefix-only visibility is the canonical triple
- Prefix schemes (`sk_live_`) enable lookup-by-prefix indexing and environment safety
- Scopes + rate limits + IP binding turn a flat credential into a controllable contract
- Rotate with dual-key windows; revoke immediately with cache-awareness
- Choose OAuth client-credentials when you need delegation, expiry, or consent semantics

## Cheat Sheet
| Concept | Recommendation |
| --------------- | --------------------------------------------------------------------------- |
| Entropy source | `crypto.randomBytes(32)` — never `Math.random()` |
| Length | 256 bits, base64url encoded |
| Storage | SHA-256 hash + plaintext prefix; full key shown once |
| Prefix scheme | `sk_live_` / `sk_test_` + first ~12 chars |
| Lookup pattern | Indexed prefix query → constant-time hash compare |
| Scopes | Explicit per key, deny-by-default in guard |
| Rotation | Dual-key grace window (24h-7d) then hard expiry |
| Revocation | Immediate flag + cache TTL awareness |
| Leak response | Assess → rotate/revoke → audit → postmortem |
| Key vs OAuth CC | Static/simple → key; delegated/expiring/scoped-consent → client-credentials |

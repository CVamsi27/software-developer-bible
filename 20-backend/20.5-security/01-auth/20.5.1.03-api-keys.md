# API Keys

> Stage 2 of the [Auth Learning Track](INDEX.md) — prev: [HTTP Basic & Digest](20.5.1.02-http-basic-digest-auth.md) · next: [Sessions & Cookies](20.5.1.04-sessions-cookies.md)


## Definition

An API key is a cryptographically random token issued to a developer, service, or partner so their applications can call your API. It commonly identifies an application or service, though a provider can associate a key with a user account. It can be revoked independently of the user's password. Hashing a high-entropy key limits reuse after a verifier-store leak; transport, logs and caller-side storage still require protection.

> **Textbook Definition:** An API key is an issued credential that identifies and grants configured access to an application or principal. A bearer key authorizes by possession, so its scope, storage, rotation and revocation rules define the security boundary.

A common recognizable shape is a prefixed random string:

```text
sk_live_7fJd2Kx9QmLpV4nRtY8wZ3aB6cD0eF1gH5iJ
└─┬──┘ └┬┘ └──────────── 32 bytes CSPRNG ───────┘
  │     └─ environment marker (live vs test; enforced by the verifier)
  └─ key family / brand prefix
```

The marker is a label, not an isolation control. The verifier must accept only the configured environment and query records in that same environment; separate credentials or stores per environment provide a stronger boundary.

## First Principles

API keys prove possession of an issued secret associated with a configured principal.

1. **A key often identifies an app; a provider may associate it with a user.** The key alone does not establish a current human login or an interactive consent flow. Whenever you need "acting on behalf of user X," keys alone are the wrong tool (OAuth, → 20.5.1.06).
2. **A static secret is only as safe as its storage and response plan.** Keep keys out of repositories, logs and frontend bundles. Use a secret manager or protected runtime configuration, least-privilege scopes, leak detection, and a tested revoke-and-reissue path; environment variables alone do not provide the whole defense.
3. **Separate the caller from the effective user.** Keys support workload identification, rate limits, billing and attribution. When they conflate caller identity with user identity, delegated access, per-user authorization and audit trails become harder.

## Why Do We Need It?

1. **Machine-to-machine identity without user context** — cron jobs, CI pipelines, backend services, and third-party developers need credentials with no login flow.
2. **Independent lifecycle** — issue, scope, rotate, and revoke per application, without touching user accounts or passwords.
3. **Billing and attribution** — usage metering, quotas, and per-customer analytics key off the key record.
4. **Blast-radius control** — scopes + rate limits + IP allowlists mean one leaked key exposes a slice, not the whole API.
5. **Developer experience** — keys are trivially usable from curl/SDKs; no redirects, certificates, or signing libraries required.
6. **A stepping stone** — understanding where static keys stop working leads directly to OAuth client-credentials (stage 5).

## How It Works

### Generation: CSPRNG Only

Keys must come from a Cryptographically Secure Pseudo-Random Number Generator. `Math.random()` is seeded predictably and must never touch credential material. In Node.js:

```text
crypto.randomBytes(32).toString("base64url")
-> 256 bits of entropy, URL-safe, no padding characters
```

32 bytes (256 bits) makes exhaustive offline guessing infeasible under ordinary cryptographic assumptions even though you hash with fast SHA-256 — the entropy does the work bcrypt would do for low-entropy passwords.

### Storage: Hash at Rest, Show the Prefix

```text
Issuance time:
  full_key   = sk_live_a1B2c3D4...        (shown ONCE to developer)
  prefix     = sk_live_a1B2c3D4           (first ~12-16 chars)
  key_hash   = SHA-256(full_key)          (stored in DB)

Verification time:
  incoming -> sha256(incoming) -> constant-time compare vs key_hash
```

Why SHA-256 instead of bcrypt/Argon2-style slow hashes? Passwords are chosen by humans and must resist offline guessing; API keys are 256-bit random values with nothing to guess. A fast hash lets you index/lookup by hash directly and supports an indexed lookup; database index and network costs still apply. This asymmetry is a favorite interview probe — see Common Mistakes #4 for the reverse error.

The prefix is stored in plaintext on purpose: dashboards display `sk_live_a1B2…` so users can identify which key to rotate without the system ever holding the full secret.

### Lookup-by-Prefix Pattern

```text
1. Client sends:  Authorization: Bearer sk_live_a1B2c3D4e5F6...
2. Extract prefix = first N chars up to a fixed boundary
3. SELECT * FROM api_keys WHERE prefix = 'sk_live_a1B2' AND revoked_at IS NULL
4. candidate_hash = SHA-256(presented key)
5. timingSafeEqual(candidate_hash, row.key_hash)?
      yes -> load scopes/rate limits onto request
      no  -> 401 (and increment failure counters)
```

A prefix is not inherently unique. Reserve it with a unique constraint and regenerate on collision, or look up by the full digest using a unique index. Prefix lookup can then select one indexed candidate, while the final comparison still uses the full hash — a leaked prefix alone is useless.

### Rotation & Revocation Strategies

```text
Dual-key rotation window (overlap reduces cutover risk):

 Day 0        key v1 active
              create key v2 (same scopes), mark rotated_at
 Day 0..N     BOTH accepted; dashboards nudge "migrate to v2"
 Day N        v1 auto-expires (grace window); audit shows who never moved

Hard revoke:  revoked_at = now()  -> 401 within cache TTL (keep TTL seconds!)
```

Rules seniors state out loud:

- **Rotation** = planned, graceful, dual-active; **revocation** = emergency rejection with an explicit propagation deadline; caches and in-flight operations define its actual window.
- Grace windows should match integration rollout and risk and enforced by `expires_at`, not human memory.
- Never rotate by in-place mutation of the hash — create a new row so audit history survives.

### Per-Key Scopes, Rate Limits, IP Binding

```text
api_keys
├── id, owner_id, name, environment, prefix, key_hash
├── scopes          ["invoices:read", "invoices:write"]
├── rate_limit_tier "standard" | "premium"       -> bucket per key
├── ip_allowlist    ["203.0.113.7", "198.51.100.34"]
└── expires_at, last_used_at, revoked_at
```

The guard verifies the key, checks its environment and scopes, and applies the exact-IP allowlist. A separate rate-limit policy should consume quota by key ID before business work. The application must still constrain each query and mutation to the key owner's tenant or resources.

## Code Examples

### Key Generation (TypeScript)

```typescript
import crypto from "crypto";

interface GeneratedKey {
  fullKey: string;
  prefix: string;
  keyHash: string;
}

const generateApiKey = (env: "live" | "test" = "live"): GeneratedKey => {
  const raw = crypto.randomBytes(32).toString("base64url");
  const fullKey = `sk_${env}_${raw}`;
  const prefix = fullKey.slice(0, 16); // enough to identify, useless alone
  const keyHash = crypto.createHash("sha256").update(fullKey).digest("hex");

  return { fullKey, prefix, keyHash };
};

const hashIncomingKey = (presentedKey: string): string =>
  crypto.createHash("sha256").update(presentedKey).digest("hex");
```

### NestJS ApiKeyGuard (lookup-by-prefix, scopes, timing-safe)

```typescript
import {
  CanActivate,
  ExecutionContext,
  ForbiddenException,
  Injectable,
  InternalServerErrorException,
  SetMetadata,
  UnauthorizedException,
} from "@nestjs/common";
import crypto from "crypto";
import { Reflector } from "@nestjs/core";

type ApiKeyEnvironment = "live" | "test";

export const SCOPES_KEY = "required_scopes";
export const RequireScopes = (...scopes: string[]) =>
  SetMetadata(SCOPES_KEY, scopes);

interface ApiKeyRecord {
  environment: ApiKeyEnvironment;
  revokedAt: Date | null;
  id: string;
  ownerId: string;
  keyHash: string;
  scopes: string[];
  ipAllowlist: string[];
  expiresAt: Date | null;
}

export abstract class ApiKeyRepository {
  abstract findByPrefix(
    prefix: string,
    environment: ApiKeyEnvironment
  ): Promise<ApiKeyRecord | null>;
  abstract recordFailure(id: string | null): Promise<void>;
}

@Injectable()
export class ApiKeyGuard implements CanActivate {
  constructor(
    private readonly reflector: Reflector,
    private readonly keys: ApiKeyRepository, // thin Prisma/service wrapper
    private readonly expectedEnvironment: ApiKeyEnvironment // validated deployment config
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const required = this.reflector.getAllAndOverride<string[]>(
      SCOPES_KEY, [context.getHandler(), context.getClass()]
    );
    if (!required || required.length === 0) {
      throw new InternalServerErrorException("Protected API-key route has no scope policy");
    }

    const req = context.switchToHttp().getRequest();
    const presented = this.extractBearer(req);
    if (
      !presented ||
      !presented.startsWith(`sk_${this.expectedEnvironment}_`) ||
      !/^sk_(live|test)_[A-Za-z0-9_-]{43}$/.test(presented)
    ) {
      throw new UnauthorizedException();
    }

    const record = await this.keys.findByPrefix(
      presented.slice(0, 16), this.expectedEnvironment
    );
    const presentedHash = crypto
      .createHash("sha256")
      .update(presented)
      .digest();

    if (
      !record || record.environment !== this.expectedEnvironment ||
      !/^[a-f0-9]{64}$/i.test(record.keyHash) ||
      !crypto.timingSafeEqual(Buffer.from(record.keyHash, "hex"), presentedHash)
    ) {
      await this.keys.recordFailure(record?.id ?? null);
      throw new UnauthorizedException();
    }

    if (record.revokedAt || (record.expiresAt && record.expiresAt <= new Date())) {
      throw new UnauthorizedException("API key expired");
    }

    if (
      record.ipAllowlist.length > 0 &&
      !record.ipAllowlist.includes(req.ip)
    ) {
      throw new ForbiddenException("Source IP not allowlisted for this key");
    }

    const missing = required.filter((s) => !record.scopes.includes(s));
    if (missing.length > 0) {
      throw new ForbiddenException(`Missing scopes: ${missing.join(", ")}`);
    }

    req.apiKey = { id: record.id, ownerId: record.ownerId, scopes: record.scopes };
    return true;
  }

  private extractBearer(req: {
    headers: { authorization?: string | string[] };
  }): string | null {
    const header = req.headers.authorization;
    if (typeof header !== "string") return null;
    return /^Bearer +([^\s]+)$/i.exec(header)?.[1] ?? null;
  }
}

```

HTTP authentication scheme names are case-insensitive, while the credential value itself remains case-sensitive. This adapter requires a repository whose database constraint makes `(environment, prefix)` unique; inject `expectedEnvironment` from validated deployment configuration and include it in the lookup. Bind `ApiKeyRepository` to a concrete provider, validate trusted proxy configuration before using `req.ip`, and rate-limit malformed and failed credentials before expensive work. The allowlist supports exact IP strings only, not Classless Inter-Domain Routing (CIDR) ranges. Scopes authorize operations; every query and mutation must still enforce owner or tenant scope.

### Controller Wiring

This wiring sketch assumes imported decorators, validated DTOs and an injected invoice service; the service constrains both reads and writes using trusted ownership.

```typescript
@Controller("invoices")
@UseGuards(ApiKeyGuard)
export class InvoiceController {
  @Get()
  @RequireScopes("invoices:read")
  list(@Req() req: RequestWithApiKey) {
    return this.invoices.listForOwner(req.apiKey.ownerId);
  }

  @Post()
  @RequireScopes("invoices:write")
  create(@Req() req: RequestWithApiKey, @Body() dto: CreateInvoiceDto) {
    return this.invoices.createForOwner(req.apiKey.ownerId, dto);
  }
}
```

## Real-World Use Cases

### 1. Public developer platforms

- Stripe/Twilio style `sk_live_` / `sk_test_` pairs
- Test-mode keys hit sandbox data; live keys are scoped and billed separately

### 2. First-party internal services

- Each workload or integration gets its own credential, and logs record the credential ID without recording its secret.
- Choose API keys when a static secret and its revocation lifecycle fit; use short-lived workload identity or mutual TLS (mTLS) when that better matches the trust boundary.

### 3. CI/CD deploy pipelines

- Pipeline holds a deployment-scoped key limited to release endpoints
- Rotated automatically by secrets manager on schedule

### 4. Rate-limited partner tiers

- Partners buy throughput: key maps to a quota bucket (e.g., 1k req/min)
- Overage returns `429` with headers, not silent throttling

### 5. Webhook consumers

- A webhook receiver may use an API key to authenticate the caller, but this is separate from signing outbound payloads.
- Outbound keyed-hash message authentication code (HMAC) signatures require the sender to retrieve or derive the signing secret; a one-way API-key verifier hash cannot sign a payload. Include a timestamp and enforce replay limits when the webhook protocol supports them.

## Common Mistakes

1. **Generating keys with `Math.random()`**: Predictable output makes keys guessable. Use `crypto.randomBytes` or an equivalent cryptographically secure pseudorandom number generator (CSPRNG).

2. **Storing full keys in plaintext**: A database dump can expose reusable credentials that let an attacker act within each key's privileges. Store SHA-256 hashes and identifying prefixes, not full keys.

3. **No scopes — one god-key per customer**: Any leak becomes total compromise. Default-deny with explicit scope grants.

4. **Using bcrypt/Argon2 for API keys**: Not wrong cryptographically, but pointless — a 256-bit random key has no practical brute-force surface, and slow hashes prevent direct hash-indexed lookup. Save slow hashing for passwords.

5. **Revocation delayed by caching**: If guards cache key records for 60 seconds, revocation is delayed by that cache lifetime and any in-flight request. Short time-to-live (TTL) caches need a freshness policy, especially for sensitive operations.

6. **Assuming overlap guarantees zero downtime**: A dual-active window reduces cutover risk, but deployment order, client adoption, cache propagation and expiry still determine whether callers see errors. Monitor migration and define a hard end to the overlap.

## Best Practices

1. **Generate with CSPRNG, 256-bit minimum**, URL-safe encoding.

2. **Show the full key exactly once**, then persist only `SHA-256(key)` and an identifying prefix.

3. **Send keys only over TLS.** Redact `Authorization` in application, proxy, tracing and error logs; never put credentials in URLs.

4. **Separate environments at verification time.** Prefixes such as `sk_live_` and `sk_test_` help people spot mistakes, while the configured verifier environment and database query enforce the boundary.

5. **Scope every key** and enforce scopes in the guard layer, not deep in business logic.

6. **Bind rate-limit buckets and optional IP allowlists per key** so abuse is contained and attributable.

7. **Rotate via dual-key grace windows** with hard `expires_at`; automate expiry.

8. **Track `last_used_at`** and surface stale keys in dashboards — unused keys are standing risk.

9. **Log key ID (never the key)** on every authenticated request for forensics.

10. **Rate-limit failed verifications** like login attempts to blunt brute-force probing.

11. **Prefer OAuth client-credentials when short-lived machine tokens matter; user delegation/consent requires a user authorization flow, not client credentials** — see the decision table below.

## Performance Considerations

| Aspect | Consideration |
| --------------------- | ------------------------------------------------------------------- |
| Verification cost | Measure digest plus indexed lookup and tail latency |
| Caching | Cache records by key id but re-check `revokedAt` within a small TTL |
| DB growth | Rotation creates rows — archive dead keys periodically |
| Rate limiter coupling | Token buckets keyed by key id add Redis hop; budget p99 accordingly |

## Summary

API keys are the workhorse credential for application-to-API traffic. Key takeaways:

- Keys prove possession for a configured principal; distinguish workload identity from a current human session
- CSPRNG generation (256-bit), SHA-256-at-rest, prefix-only visibility is the canonical triple
- Prefix schemes support indexed lookup and make environments legible; the verifier must enforce environment separation
- Scopes + rate limits + IP binding turn a flat credential into a controllable contract
- Rotate with dual-key windows; revoke within an explicit cache/in-flight propagation bound
- Choose OAuth client credentials for eligible machine access; user delegation and consent use a separate user flow

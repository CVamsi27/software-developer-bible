# Sessions & Cookies

> Stage 3 of the [Auth Learning Track](INDEX.md) — prev: [API Keys](20.5.1.03-api-keys.md) · next: [JWT](20.5.1.05-jwt.md)


## Definition

**Sessions** are server-side storage mechanisms that maintain user state across multiple HTTP requests. A session stores user data on the server and associates it with a unique session ID sent to the client.

> **Textbook Definition:** A server-side session associates successive requests with retained state through a session identifier. A cookie is a browser-managed value whose delivery is governed by origin, path, security and same-site rules; it is one possible session transport.

**Cookies** are small values stored by a browser and attached to requests that match their domain, path, security and same-site rules. They can store session IDs, user preferences, authentication tokens, and other state information.

Sessions and cookies work together: cookies typically store the session ID, while the session data lives on the server. This combination enables stateful interactions in the stateless HTTP protocol.

## First Principles

Session auth follows from where state can live:

1. **The server must remember the login — the only question is where.** Server-side session store (central revocation with a defined cache/in-flight window, protected requests pay a lookup) vs client-side token (signature verification can avoid a lookup; current revocation/permissions may still require state). Sessions pick the server-side half of that trade.
2. **The cookie is the transport because browsers made it one.** Automatic sending is both the feature (no JS needed, HttpOnly prevents script from reading its value; XSS can still issue authenticated requests) and the liability (CSRF: other origins' requests carry it too — hence SameSite, CSRF tokens, → 20.5.2.02).
3. **Fixation and hijacking exploit possession of the bearer identifier**: the session ID *is* the identity for its lifetime. Protect it like a password — rotate on login, secure transport, a server-enforced idle limit plus an absolute lifetime.

## Why Do We Need It?

- **State Maintenance**: HTTP is stateless; sessions/cookies maintain user state
- **Authentication**: Keep users logged in across requests
- **Personalization**: Store user preferences and settings
- **Shopping Carts**: Maintain cart contents across page loads
- **CSRF Protection**: Session-based CSRF tokens
- **Analytics**: Track user behavior across sessions

## How It Works

### A cookie points to server-side state

```text
Browser -- POST /login + credential --> verifier
        <-- Set-Cookie: opaque ID ---- session store: ID -> userId, timestamps
Browser -- Cookie: opaque ID --------> lookup -> current user -> authorization
```

The session identifier is a bearer credential. A valid signature on the cookie prevents changing its value; it does **not** encrypt the identifier or prove that its server-side session is still live. The server must load and validate the session.

| Cookie attribute | What it controls | Boundary |
| ---------------- | -------------------------------------- | ---------------------------------------------------------------- |
| `Secure` | Send over HTTPS | Does not encrypt database/log copies |
| `HttpOnly` | Prevent script from reading the cookie | XSS can still send requests using it |
| `SameSite` | Restrict cross-site delivery | Site is not origin; sibling subdomains and login flows need care |
| Omitted `Domain` | Host-only delivery | Setting `.example.com` broadens the subdomain trust boundary |
| `Path` | Request paths receiving the cookie | Not an access-control boundary between applications |
| `Max-Age` | Browser retention lifetime | Server expiry/revocation must be enforced independently |

A shared session store lets multiple application instances serve the same identifier without sticky routing. Store failure needs an explicit fail-closed policy; a local fallback could bypass revocation or split state. JWT and session designs both need a current authorization policy, and either can use cookies as transport.

## Code Examples

### One login-to-logout flow

This complete Express 5 / `express-session` 1.18 module injects a session store and credential verifier. The verifier returns `{ id }` or `null`, and owns password checking, account state, rate limits and bounded work. Use a maintained shared store in deployment; `MemoryStore` is for the local example only. The middleware still requires TLS and reviewed proxy configuration when `Secure` cookies are enabled.

```js
const express = require('express');
const session = require('express-session');
const { randomBytes, timingSafeEqual } = require('node:crypto');

function createSessionApp({ store, authenticate, secret, origin,
  secure = true, now = Date.now, idleMs = 900_000, absoluteMs = 28_800_000 }) {
  if (typeof secret !== 'string' || secret.length < 32) throw new Error('provision a strong session secret');
  const expectedOrigin = new URL(origin).origin;
  if (![idleMs, absoluteMs].every(x => Number.isSafeInteger(x) && x > 0)) {
    throw new RangeError('session lifetimes must be positive integer milliseconds');
  }
  const app = express();
  const cookie = { httpOnly: true, secure, sameSite: 'lax', path: '/' };
  app.use(express.json({ limit: '8kb' }));
  app.use(session({ store, secret, name: 'sessionId', resave: false,
    saveUninitialized: false, cookie: { ...cookie, maxAge: idleMs } }));
  const operation = (req, name) => new Promise((resolve, reject) =>
    req.session[name](err => err ? reject(err) : resolve()));
  const token = () => randomBytes(32).toString('hex');
  const validCsrf = (presented, stored) => typeof presented === 'string' &&
    /^[a-f0-9]{64}$/.test(presented) && typeof stored === 'string' &&
    /^[a-f0-9]{64}$/.test(stored) &&
    timingSafeEqual(Buffer.from(presented, 'hex'), Buffer.from(stored, 'hex'));

  // This browser-only flow requires its configured Origin for unsafe requests,
  // including login. Add an explicit policy for non-browser clients if needed.
  app.use((req, res, next) => {
    if (!['GET', 'HEAD', 'OPTIONS'].includes(req.method) &&
        req.get('Origin') !== expectedOrigin) {
      return res.status(403).json({ error: 'Origin rejected' });
    }
    next();
  });
  app.post('/login', async (req, res) => {
    if (typeof req.body?.email !== 'string' || typeof req.body?.password !== 'string') {
      return res.status(400).json({ error: 'Invalid login shape' });
    }
    const user = await authenticate(req.body.email, req.body.password);
    if (!user) return res.status(401).json({ error: 'Invalid credentials' });
    await operation(req, 'regenerate'); // discard the pre-login bearer identifier
    req.session.userId = user.id;
    req.session.createdAt = req.session.lastSeen = now();
    req.session.csrfToken = token();
    await operation(req, 'save'); // ensure the store accepts state before replying
    res.json({ csrfToken: req.session.csrfToken });
  });
  app.use(async (req, res, next) => {
    const state = req.session;
    if (!state.userId) return res.status(401).json({ error: 'Not authenticated' });
    const at = now();
    if (!Number.isFinite(state.createdAt) || !Number.isFinite(state.lastSeen) ||
        at < state.lastSeen || at - state.lastSeen >= idleMs ||
        at - state.createdAt >= absoluteMs) {
      await operation(req, 'destroy');
      res.clearCookie('sessionId', cookie);
      return res.status(401).json({ error: 'Session expired' });
    }
    state.lastSeen = at;
    if (!['GET', 'HEAD', 'OPTIONS'].includes(req.method) &&
        !validCsrf(req.get('X-CSRF-Token'), state.csrfToken)) {
      return res.status(403).json({ error: 'Invalid CSRF token' });
    }
    next();
  });
  app.get('/profile', (req, res) => res.json({ userId: req.session.userId }));
  app.post('/logout', async (req, res) => {
    await operation(req, 'destroy');
    res.clearCookie('sessionId', cookie); // same host/path attributes as issuance
    res.sendStatus(204);
  });
  app.use((err, req, res, next) => {
    if (res.headersSent) return next(err);
    res.status(500).json({ error: 'Session operation failed' });
  });
  return app;
}
module.exports = { createSessionApp };
```

Trace: the browser logs in with the configured `Origin`; regeneration discards its earlier ID, and the response gives a CSRF token. `/profile` uses the new cookie. `/logout` also sends that CSRF token, destroys server state and clears the cookie. Reusing the old cookie cannot recover destroyed state. Expiry uses both inactivity and time since login; frequent activity cannot extend the absolute lifetime forever.

This example teaches the session boundary, not complete product authorization. Load current account/tenant/permission state before protected business operations. Role changes, account disablement and in-flight requests need explicit revocation semantics. Parallel requests can race idle timestamps and logout/store writes; select a store with appropriate touch/update behavior and test that concurrency instead of treating local sequential tests as proof.

### Swap the persistence adapter

The app's store contract is independent of cookie transport. A Redis, PostgreSQL or MongoDB adapter must support expiry, cleanup, deployment compatibility and failure handling. Modern `connect-redis` documents a named `RedisStore` export and a `redis` client; confirm the pinned adapter instead of mixing old default exports with an unsupported client. Initialize/connect it before accepting traffic and close it on shutdown. A store TTL must not permit renewal beyond the server's absolute session lifetime.

Preference cookies do not automatically sync devices; that needs an account-level preference record. Signed preference cookies prevent tampering, while sensitive data still needs confidentiality. To clear a cookie, match its name, host/domain and path; broad-domain and host-only cookies with the same name are distinct.

## Real-World Use Cases

### 1. E-commerce Shopping Carts

- Store cart contents in session
- Persist across page loads
- Handle guest vs authenticated carts

### 2. User Authentication

- Keep users logged in
- Session-based access control
- Automatic logout on inactivity

### 3. Multi-Step Forms

- Store form data across steps
- Prevent data loss on navigation
- Validate each step

### 4. A/B Testing

- Store user variant in cookie
- Consistent experience across requests
- Long-term tracking with cookies

### 5. Language/Theme Preferences

- Store preferences in cookies
- Persist across sessions
- Sync across devices through an authenticated account preference record

## Common Mistakes

1. **Not using Secure flag**: Cookies sent over HTTP can be intercepted

2. **Not using HttpOnly**: JavaScript can steal session cookies via XSS

3. **Storing sensitive data in cookies**: Cookies are client-side; don't store secrets

4. **Not regenerating session ID**: Session fixation attacks

5. **Using default session configuration**: Default settings are often insecure

6. **Not implementing session expiration**: Sessions should expire

7. **Storing session data in cookies**: Keep data server-side

8. **Treating SameSite as complete CSRF prevention**: Same-site sibling origins and allowed navigations still require an explicit policy

## Best Practices

1. **Use Secure flag** on all cookies in production

2. **Use HttpOnly** for session cookies

3. **Choose SameSite for the browser flow**, then validate unsafe requests with CSRF/origin defenses; it is not a complete substitute

4. **Regenerate session ID** after login

5. **Implement session expiration** and timeout

6. **Use secure session stores** (Redis, PostgreSQL)

7. **Encrypt session data** if storing sensitive information

8. **Implement session revocation** for logout

9. **Monitor session activity** for anomalies
10. **Use short session lifetimes** for sensitive applications

## Performance Considerations

| Aspect | Consideration |
| ---------------- | ------------------------------------------------------------------------ |
| Redis Store | Fast, scalable, supports TTL |
| PostgreSQL Store | Persistent, ACID compliant |
| Cookie Size | Keep identifiers small; browser limits and aggregate header budgets vary |
| Session Data | Keep minimal for performance |
| Serialization | Use efficient formats (JSON, MessagePack) |

## Summary

Sessions and cookies are fundamental to maintaining state in web applications. Key takeaways:

- Use httpOnly, Secure, SameSite cookies for session IDs
- Store session data server-side (Redis, PostgreSQL)
- Regenerate session ID after login
- Implement session expiration and timeout
- Use secure session stores in production
- Monitor session activity for anomalies
- Implement session revocation for logout
- Keep the cookie an opaque identifier; server expiry and current authorization remain separate checks

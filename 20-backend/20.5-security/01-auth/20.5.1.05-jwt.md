# JWT (JSON Web Tokens)

> Stage 4 of the [Auth Learning Track](INDEX.md) — prev: [Sessions & Cookies](20.5.1.04-sessions-cookies.md) · next: [OAuth2/OIDC](20.5.1.06-oauth2-oidc.md)


## Definition

A JSON Web Token (JWT) is a compact, URL-safe representation of claims exchanged between parties, defined by RFC 7519. Common signed JWTs let a recipient verify protected claims without a session lookup. Authentication and authorization still require issuer, audience, time and application-policy validation; current account state or revocation requirements may also need server-side checks.

> **Textbook Definition:** A JSON Web Token is a compact representation of claims conveyed through a JSON Web Signature or JSON Web Encryption structure. Trust requires validation of protection, issuer, audience and application-specific claims; the token format alone proves no permission.

A valid signature establishes integrity under a trusted key. It does not by itself establish that the token is intended for this API or that its subject may access a particular resource.

## First Principles

JWTs follow from one requirement: **verification without a shared store.**

1. **The token carries its own proof.** Sign the payload (HMAC: shared secret; RSA/ECDSA: private sign, public verify) and any holder of the key can verify offline — no session DB, which removes shared session lookup from that verification step. Key distribution, current permissions and incident revocation still need an operational policy.
2. **The cost is the mirror: you cannot unissue a token.** No central store means no instant revocation — mitigations (short TTL + refresh rotation, denylists, `jti`) each reintroduce some state. The senior position: *revocation requirements dictate statefulness*, not fashion.
3. **Signing and encryption are different contracts.** The signed JWS form used here exposes its base64url-encoded claims; JWTs can also use encrypted JWE structures. Do not place secrets in a signed payload. Treat the header as untrusted input and pin acceptable algorithms and keys server-side.

## Why Do We Need It?

- **Stateless Authentication**: Self-contained validation may avoid a session lookup; current revocation and permissions can still require state
- **Scalability**: Verifiers can scale independently when they share a trusted key/claim policy
- **Interoperability**: Standard format understood across languages, frameworks, and services
- **Microservices**: One possible service credential format; audience and workload identity still matter
- **Performance**: Measure verification cost; online state checks depend on the policy
- **Decoupled Authorization**: The token carries claims, allowing services to make authorization decisions independently

## How It Works

### Read the compact representation

The compact signed/MAC-protected **JWS** form has three dot-separated base64url segments:

```text
encoded header . encoded claims . encoded signature or MAC
```

The header describes the algorithm and optional key selector; the payload contains claims. Protection covers the encoded header and payload together. Decode either segment to inspect it, but accept neither as trusted until verification under the server's configured key and algorithm policy. A compact encrypted **JWE** has five segments and a different processing contract.

### Trace issuance and resource access

```text
Client → issuer: credential evidence under the login protocol
Issuer → client: access token for a defined audience and purpose
Client → API: Authorization: Bearer <access token>
API: validate protection → issuer/audience/time/profile → principal
API: enforce operation + object/tenant policy → response
```

Issuance does not replace resource authorization. The JWT format does not require a password login, a refresh token or a 15-minute lifetime; those are application/authorization-server choices. The complete access-token example below chooses a 900-second profile explicitly.

A separate refresh credential can obtain another access token after validating its own expiry, session state and rotation contract. It must not be accepted by an API simply because it resembles a valid access token. The refresh transition below is the canonical treatment of that lifecycle.

## Code Examples

### A complete, narrow access-token contract

This `jsonwebtoken` 9 example uses one provisioned HMAC key inside one trust domain. Every verifier holding this key can also mint tokens; use an asymmetric issuer/public-verifier boundary when that is unacceptable. Provision the 32-byte key from a secret manager, and do not choose a human password.

```js
const jwt = require('jsonwebtoken');
const { randomUUID } = require('node:crypto');

function createAccessTokens(key) {
  if (!Buffer.isBuffer(key) || key.length < 32) throw new Error('key requires at least 32 random bytes');
  const issuer = 'https://identity.example';
  const audience = 'invoice-api';
  const principalShape = value => value && typeof value === 'object' &&
    typeof value.sub === 'string' && value.sub.length > 0 &&
    typeof value.tenantId === 'string' && value.tenantId.length > 0 &&
    Array.isArray(value.permissions) && value.permissions.length <= 50 &&
    value.permissions.every(x => typeof x === 'string' && x.length <= 100);
  function issue(principal) {
    if (!principalShape(principal)) throw new TypeError('invalid principal');
    return jwt.sign({ sub: principal.sub, tenantId: principal.tenantId,
      permissions: principal.permissions, tokenUse: 'access' }, key,
      { algorithm: 'HS256', issuer, audience, expiresIn: 900, jwtid: randomUUID() });
  }
  function verify(token) {
    if (typeof token !== 'string' || token.length > 8192) throw new Error('invalid token size');
    const claims = jwt.verify(token, key, { algorithms: ['HS256'], issuer, audience });
    // verify() checks supplied exp/nbf, but this profile also REQUIRES exp/iat/jti.
    const at = Math.floor(Date.now() / 1000);
    if (!principalShape(claims) || claims.tokenUse !== 'access' ||
        !Number.isSafeInteger(claims.exp) || !Number.isSafeInteger(claims.iat) ||
        claims.iat > at || claims.exp <= claims.iat || claims.exp - claims.iat > 900 ||
        typeof claims.jti !== 'string' || claims.jti.length === 0) {
      throw new Error('invalid access-token profile');
    }
    return { sub: claims.sub, tenantId: claims.tenantId,
      permissions: claims.permissions, jti: claims.jti, exp: claims.exp };
  }
  return { issue, verify };
}
module.exports = { createAccessTokens };
```

Trace: an authenticated issuer creates a token for tenant A and `invoice-api`. The API verifies signature, fixed algorithm, issuer, audience, time and runtime shape before attaching a principal. A correctly signed token for another audience fails. A refresh or ID token fails this access-token profile. A valid principal still needs an invoice lookup constrained by tenant and current permission policy. A TypeScript cast cannot perform any of these runtime checks.

Invalid/missing/expired bearer evidence normally receives `401` with an appropriate `WWW-Authenticate` challenge. A valid caller denied by operation/resource policy receives `403`. Roles are not a single ordered slot: test the required policy against all verified grants, then enforce object/tenant access in the query or mutation.

### Refresh rotation is a state transition

A refresh token is a separate, long-lived credential, often opaque random bytes. Its issuer stores a one-way verifier, family/session identity, expiry and used/revoked state. In one transaction, consume the unused old token and create its successor; two concurrent uses must not both succeed. A replay of a consumed token follows an explicit family-revocation policy. Handle lost responses and legitimate concurrent requests deliberately rather than silently accepting unlimited reuse.

```text
old unused -> atomic consume + successor insert -> new access token + refresh token
old reused -> detect replay -> apply family incident policy
```

Rotating a refresh token does not revoke already issued access tokens. Short access lifetimes bound exposure; immediate disablement needs a current session/account version or denylist check. Retain a denylist marker for the verified remaining lifetime plus configured clock tolerance, keyed by issuer and `jti` or a token digest—not the raw bearer token. The verifier must check it on every protected path, with a documented outage policy. `jwt.decode` only parses untrusted bytes and cannot establish a safe expiry for a revocation record.

### Public-key verification changes who can issue

RS256/ES256 let the issuer keep the private signing key while APIs receive public verification keys. Pin accepted algorithms and the issuer's configured key-discovery endpoint; a header's `kid` is a selector, not a URL to fetch. Reject unknown keys after bounded refresh, protect the fetch cache against attacker-driven churn, and overlap retiring keys for the lifetime of permitted old tokens. Removing a compromised key and ordinary planned rotation require different response policies.

## Real-World Use Cases

### 1. Single Sign-On (SSO)

- User authenticates with a central identity provider
- The issuer supplies tokens with explicit audiences; do not blindly reuse an ID token as an API credential
- Each service validates the JWT independently

### 2. API Gateway Authentication

- API gateway validates JWT before routing to microservices
- Claims are forwarded to downstream services
- Downstream services accept only an authenticated gateway boundary or independently validated tokens; they still enforce operation/object/tenant access

### 3. Mobile and SPA Authentication

- Tokens stored securely on client
- Short-lived access tokens minimize risk if compromised
- Refresh tokens enable seamless re-authentication

### 4. Third-Party API Access

- OAuth access tokens may be opaque or JWTs; the resource-server contract defines validation
- Scoped permissions encoded in token claims
- Time-limited access without sharing credentials

## Common Mistakes

1. **Storing sensitive data in a signed payload**: JWS claims are base64url-encoded, not encrypted. Keep passwords, personal identifiers and secrets out of these tokens.

2. **Using weak signing secrets**: Using short or predictable secrets makes tokens forgeable. Use cryptographically strong secrets (256+ bits for HMAC).

3. **No token expiration**: Tokens without expiration remain valid forever if compromised.

4. **Storing JWT in localStorage**: Vulnerable to XSS attacks. Use httpOnly cookies or memory storage.

5. **Not validating the `iss` and `aud` claims**: Without validation, tokens from other issuers may be accepted.

6. **Giving every verifier issuing capability unintentionally**: HMAC verifiers hold the minting secret. Use public-key verification when verifiers must not be able to issue tokens.

7. **Neglecting refresh token rotation**: Not rotating refresh tokens increases the window of opportunity for attackers.

8. **Leaking tokens in logs or URLs**: Tokens in URLs or logs can be captured by proxies or logging systems.

## Best Practices

1. **Choose short access lifetimes** from the exposure and refresh policy; the example uses 15 minutes

2. **Implement refresh token rotation** with single-use refresh tokens

3. **Choose browser transport deliberately**: HttpOnly cookies prevent direct script reads but need CSRF controls; in-memory tokens still face XSS-driven requests

4. **Separate issuing capability from verification when required**; select a supported asymmetric algorithm and trusted key lifecycle rather than using service count as the rule

5. **Require and validate the profile's claims**; libraries do not necessarily require absent `exp` or reject future `iat` automatically

6. **Implement token revocation** for logout and security incidents

7. **Never store sensitive data** in the JWT payload

8. **Use strong secrets** (minimum 256-bit for HMAC algorithms)

9. **Keep tokens small** to avoid HTTP header size issues
10. **Implement rate limiting** on token refresh endpoints

## Performance Considerations

| Aspect | Consideration |
| ------------------- | ------------------------------------------------------------------------------------------------------------ |
| Token Size | Larger tokens increase HTTP header overhead; keep payloads minimal |
| Signing Performance | Measure signing cost; cache public verification keys under a rotation policy, not arbitrary issued tokens |
| Verification | Symmetric verification is fast; asymmetric requires public key operations |
| State footprint | Offline checks avoid one session lookup; revocation, refresh families and key caches may still require state |
| Network Overhead | Overhead depends on claim size and algorithm; measure header budgets |

## Summary

JWT is a claims format whose usefulness depends on the issuer, verifier and authorization contract. Key takeaways:

- The compact signed JWT form consists of header, payload and signature; encrypted forms have a different structure
- Choose symmetric/asymmetric keys from who may issue and verify, rather than server count
- Require the application profile and validate its issuer, audience, purpose, times and runtime shapes
- Select storage/transport with explicit XSS, CSRF and revocation controls
- Implement refresh token rotation for security
- Never store sensitive data in JWT payloads
- Plan for token revocation from the start

# JWT (JSON Web Tokens)

> Stage 4 of the [Auth Learning Track](INDEX.md) — prev: [Sessions & Cookies](20.5.1.04-sessions-cookies.md) · next: [OAuth2/OIDC](20.5.1.06-oauth2-oidc.md)

## Definition

A JSON Web Token (JWT) is a compact, URL-safe representation of claims exchanged between parties, defined by RFC 7519. Common signed JWTs let a recipient verify protected claims without a session lookup. Authentication and authorization still require issuer, audience, time and application-policy validation; current account state or revocation requirements may also need server-side checks.

> **Textbook Definition:** A JSON Web Token is a compact representation of claims conveyed through a JSON Web Signature or JSON Web Encryption structure. Trust requires validation of protection, issuer, audience and application-specific claims; the token format alone proves no permission.

A valid signature establishes integrity under a trusted key. It does not by itself establish that the token is intended for this API or that its subject may access a particular resource.

## First Principles

JWTs follow from one requirement: **verification without a shared store.**

1. **The token carries its own proof.** Sign the payload and let a verifier check it with a trusted key, without a session-store lookup. An HMAC verifier also holds the power to issue tokens; asymmetric signing keeps the private key at the issuer and gives APIs only a public verification key. Key distribution, current permissions and incident revocation still need an operational policy.
2. **The cost is the mirror: you cannot unissue a token.** No central store means no instant revocation — mitigations (short TTL + refresh rotation, denylists, `jti`) each reintroduce some state. The senior position: *revocation requirements dictate statefulness*, not fashion.
3. **Signing and encryption are different contracts.** The signed JWS form used here exposes its base64url-encoded claims; JWTs can also use encrypted JWE structures. Do not place secrets in a signed payload. Treat the header as untrusted input and pin acceptable algorithms and keys server-side.

## How It Works


### 1. Read and validate the token format

#### Read the compact representation

The compact signed/MAC-protected **JWS** form has three dot-separated base64url segments:

```text
encoded header . encoded claims . encoded signature or MAC
```

The header describes the algorithm and optional key selector; the payload contains claims. Protection covers the encoded header and payload together. Decode either segment to inspect it, but accept neither as trusted until verification under the server's configured key and algorithm policy.
A compact encrypted **JWE** has five segments and a different processing contract.

#### Trace issuance and resource access

```text
Client → issuer: credential evidence under the login protocol
Issuer → client: access token for a defined audience and purpose
Client → API: Authorization: Bearer <access token>
API: validate protection → issuer/audience/time/profile → principal
API: enforce operation + object/tenant policy → response
```

Issuance does not replace resource authorization. The JWT format does not require a password login, a refresh token or a 15-minute lifetime; those are application/authorization-server choices. The complete access-token example below chooses a 900-second profile explicitly.

Claims are data until a token profile defines how the resource server must interpret them:

| Claim | Meaning | Validation question |
| ------------- | -------------------------------- | --------------------------------------------------------------- |
| `iss` | Issuer identifier | Is this an issuer the API trusts? |
| `sub` | Subject identifier | Which principal does this profile identify? |
| `aud` | Intended recipient or recipients | Is this API an allowed audience? |
| `exp` / `nbf` | Expiration / not-before time | Is the token within its accepted time window? |
| `iat` | Issued-at time | Is it plausible for this profile and lifetime? |
| `jti` | Token identifier | Does the application need replay tracking or revocation lookup? |

These registered claims are optional in the base format; a token profile can require them. A custom `permissions` claim is meaningful only under the issuer/API contract, and it does not replace current object or tenant authorization.

A separate refresh credential can obtain another access token after validating its own expiry, session state and rotation contract. It must not be accepted by an API simply because it resembles a valid access token. The refresh transition below is the canonical treatment of that lifecycle.

### 2. Enforce the access and refresh contracts in code

#### A complete, narrow access-token contract

This `jsonwebtoken` 9 example uses one provisioned HMAC key inside one trust domain. Every verifier holding this key can also mint tokens; use an asymmetric issuer/public-verifier boundary when that is unacceptable. Provision the 32-byte key from a secret manager, and do not choose a human password.

```js
const jwt = require('jsonwebtoken');
const { randomUUID } = require('node:crypto');

function createAccessTokens(key) {
  if (!Buffer.isBuffer(key) || key.length < 32) throw new Error('key requires at least 32 random bytes');
  const issuer = 'https://identity.example';
  const audience = 'invoice-api';
  const principalShape = value => value && typeof value === 'object' &&
    typeof value.sub === 'string' && value.sub.length > 0 &&
    typeof value.tenantId === 'string' && value.tenantId.length > 0 &&
    Array.isArray(value.permissions) && value.permissions.length <= 50 &&
    value.permissions.every(x => typeof x === 'string' && x.length <= 100);
  function issue(principal) {
    if (!principalShape(principal)) throw new TypeError('invalid principal');
    return jwt.sign({ sub: principal.sub, tenantId: principal.tenantId,
      permissions: principal.permissions, tokenUse: 'access' }, key,
      { algorithm: 'HS256', issuer, audience, expiresIn: 900, jwtid: randomUUID() });
  }
  function verify(token) {
    if (typeof token !== 'string' || token.length > 8192) throw new Error('invalid token size');
    const claims = jwt.verify(token, key, { algorithms: ['HS256'], issuer, audience });
    // verify() checks supplied exp/nbf, but this profile also REQUIRES exp/iat/jti.
    const at = Math.floor(Date.now() / 1000);
    if (!principalShape(claims) || claims.tokenUse !== 'access' ||
        !Number.isSafeInteger(claims.exp) || !Number.isSafeInteger(claims.iat) ||
        claims.iat > at || claims.exp <= claims.iat || claims.exp - claims.iat > 900 ||
        typeof claims.jti !== 'string' || claims.jti.length === 0) {
      throw new Error('invalid access-token profile');
    }
    return { sub: claims.sub, tenantId: claims.tenantId,
      permissions: claims.permissions, jti: claims.jti, exp: claims.exp };
  }
  return { issue, verify };
}
module.exports = { createAccessTokens };
```

Trace: an authenticated issuer creates a token for tenant A and `invoice-api`. The API verifies signature, fixed algorithm, issuer, audience, time and runtime shape before attaching a principal. A correctly signed token for another audience fails.
A refresh or ID token fails this access-token profile. A valid principal still needs an invoice lookup constrained by tenant and current permission policy. A TypeScript cast cannot perform any of these runtime checks.

Invalid/missing/expired bearer evidence normally receives `401` with an appropriate `WWW-Authenticate` challenge. A valid caller denied by operation/resource policy receives `403`. Roles are not a single ordered slot: test the required policy against all verified grants, then enforce object/tenant access in the query or mutation.

JWT is a token format, not a requirement for OAuth access tokens to be JWTs. Some providers issue opaque access tokens that only their resource server can validate. Parse and validate a token only when the issuer's contract says it is a JWT; do not infer the format from a dot-separated string or attempt to interpret an opaque value.

#### Refresh rotation is a state transition

A refresh token is a separate, long-lived credential, often opaque random bytes. Its issuer stores a one-way verifier, family/session identity, expiry and used/revoked state. In one transaction, consume the unused old token and create its successor; two concurrent uses must not both succeed.
A replay of a consumed token follows an explicit family-revocation policy. Handle lost responses and legitimate concurrent requests deliberately rather than silently accepting unlimited reuse.

```text
old unused -> atomic consume + successor insert -> new access token + refresh token
old reused -> detect replay -> apply family incident policy
```

Rotating a refresh token does not revoke already issued access tokens. Short access lifetimes bound exposure; immediate disablement needs a current session/account version or denylist check. Retain a denylist marker for the verified remaining lifetime plus configured clock tolerance, keyed by issuer and `jti` or a token digest—not the raw bearer token.
The verifier must check it on every protected path, with a documented outage policy. `jwt.decode` only parses untrusted bytes and cannot establish a safe expiry for a revocation record. Rate-limit refresh by grant and client, and make the rejection window and behavior after a lost response explicit.

#### Choose storage and transport for the client

| Client storage | What it changes | Remaining requirement |
| ------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| HttpOnly cookie | Blocks direct JavaScript reads; the browser sends it automatically | Secure cookie scope and CSRF defenses; active XSS can still act through the session |
| In-memory browser state | Avoids persistent storage and automatic cookie attachment | Active XSS can use or steal the token; reload requires a renewal flow |
| `localStorage` | Persists across reloads and tabs | Any script running in the origin can read it; avoid long-lived bearer credentials here |
| Native platform secure storage | Uses OS-provided credential storage | Protect the authorization flow, limit credential lifetime, and account for compromised devices |

Never put bearer tokens in URLs: browser history, referrers, proxies and logs can retain them. Redact authorization headers from diagnostics. If a gateway forwards authenticated identity to another service, that service must accept only the defined gateway trust boundary or validate the token itself, and still enforce its own operation and object policy.

#### Public-key verification changes who can issue

RS256/ES256 let the issuer keep the private signing key while APIs receive public verification keys. Pin accepted algorithms and the issuer's configured key-discovery endpoint; a header's `kid` is a selector, not a URL to fetch. Reject unknown keys after bounded refresh, protect the fetch cache against attacker-driven churn, and overlap retiring keys for the lifetime of permitted old tokens.
Removing a compromised key and ordinary planned rotation require different response policies.

### 3. Budget token size and verification cost

Every request carrying a JWT pays its header-size and verification cost. Keep claims minimal, cap token and total-header sizes at values supported by the complete proxy-to-service path, and test the largest legitimate token. Measure signing and verification latency for the chosen algorithm and target traffic rather than assuming one key type is always fast enough.
Cache trusted public keys under a bounded issuer/key-rotation policy; do not fetch an endpoint named by an untrusted token header or cache arbitrary issued tokens as a substitute for profile validation.

## Summary

JWT carries claims; it does not make them private, current or authorized. Verify the exact issuer profile before creating a principal, choose signing keys according to who may issue, and define refresh, revocation, browser storage and resource-policy behavior around the allowed exposure window.

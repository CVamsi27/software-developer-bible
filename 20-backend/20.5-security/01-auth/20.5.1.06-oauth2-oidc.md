# OAuth 2.0 & OpenID Connect

> Stage 5 of the [Auth Learning Track](INDEX.md) — prev: [JWT](20.5.1.05-jwt.md) · next: [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md)

## Definition

OAuth 2.0 lets a client obtain limited access to a protected API without collecting the resource owner's password. For example, a calendar application can receive permission to read a user's calendar while the provider keeps control of login and the authorized scope. The client and API can belong to different organizations or to the same organization.

> **Textbook Definition:** OAuth 2.0 is an authorization framework in which a client obtains an access token from an authorization server and presents it to a resource server under an authorized grant. OpenID Connect (OIDC) adds an authentication layer: the client receives and validates an ID token describing an end-user authentication.

An **access token** authorizes access to its intended API. An **ID token** conveys authentication claims to its intended client. A successful OAuth exchange alone does not define a universal login assertion; OIDC supplies that separate contract.
Neither token automatically creates your application's local session or grants access to every local resource.

## First Principles

Suppose a calendar application asks for a user's provider password. The application now holds a credential that can authorize more than reading a calendar, and the provider cannot distinguish the application's intended use from other uses of that credential. Changing the password also disrupts every application that received it.

Delegation therefore needs a separate credential with a defined recipient, permitted operations and lifetime. The provider decides whether to issue that credential; the API enforces its meaning. Redirecting the browser for approval introduces another problem: the callback must belong to the transaction this browser actually started.
Authentication, callback correlation, code redemption and API authorization are separate trust boundaries, so one successful check cannot replace the others.

## 1. Four roles divide approval from API access

| Role | Job in the calendar example |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| Resource owner | The user who can authorize access to their calendar |
| Client | The application requesting calendar access |
| Authorization server | The provider component that authenticates the user as needed, evaluates the grant and issues tokens |
| Resource server | The calendar API that validates the access credential and enforces permissions |

These are protocol roles, not a requirement for four processes. A provider can host its authorization and resource servers together. The client may be a backend, browser application or native application.
The user's browser transports redirects; it is not the calendar API.

A **confidential client** can protect an authentication credential in its deployment, such as a backend. A **public client**, such as shipped browser or native code, cannot keep an embedded secret confidential. Authorization code with PKCE fits both; confidential clients also authenticate at the token endpoint using their registered method.
Client credentials fits a service using its own authority rather than an interactive user's grant.

## 2. Trace authorization code from approval to use

This trace uses a web application with a backend. A public client has the same code/PKCE binding but redeems the code itself without a client secret.

| Step | Message and resulting state |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. Start | The client stores a short-lived, browser-bound login transaction containing state, a PKCE verifier and, for this OIDC login, a nonce. |
| 2. Redirect | The browser visits the authorization endpoint with the registered client ID, exact redirect URI, requested scopes, state and PKCE challenge. OIDC includes `openid` and the nonce. |
| 3. Authorize | The authorization server authenticates the user as needed and evaluates permission, including consent where required. It can reject the request or reuse an existing approved grant. |
| 4. Return | The server redirects the browser to the client's callback with a short-lived authorization code and state. The code is not an API access credential. |
| 5. Redeem | The client validates and consumes its pending transaction, then sends the code, original verifier and redirect URI to the token endpoint over TLS. The server checks the code's bindings and client authentication where applicable. |
| 6. Establish identity | The client validates the returned OIDC ID token before mapping the provider subject to a local account. A refresh token may be issued; it is not guaranteed. |
| 7. Call the API | The client presents the access token to the intended resource server. The API validates its own token contract and the requested operation's authorization. |

A scope such as `calendar.read` describes delegated permission. The API still decides which calendar the caller may read, and may need current account or resource state. A valid token with the wrong audience, insufficient permission or disabled account must not be treated as universal authority.

## 3. PKCE proves possession of the transaction verifier

**Proof Key for Code Exchange (PKCE)** starts with a high-entropy verifier kept by the client. The authorization request sends `BASE64URL(SHA256(verifier))` as the challenge with method `S256`. When redeeming the code, the client sends the original verifier; the server hashes it and compares it with the challenge bound to that code.

Someone who obtains only the code lacks the verifier and cannot complete that exchange. PKCE does not authenticate the user or make a browser-held access token safe from malicious JavaScript. `state` correlates the returned transaction, while the OIDC `nonce` binds the ID token to the expected authentication request. This chapter uses all three.
RFC 9700 permits appropriately implemented PKCE or OIDC nonce mechanisms to provide callback CSRF protection under their stated conditions; an unconditional claim that every secure client must always use state would overstate the protocol requirement.

## 4. Device authorization moves approval to a second device

The **Device Authorization Grant** is designed for an input-constrained client that cannot conveniently complete a browser redirect, such as a television. The device asks the authorization server for a transaction and receives a `device_code` for polling, a shorter `user_code`, a verification URI, an expiry and a polling interval. It displays the URI and code (or a QR code that opens the URI); the user completes sign-in and approval in a browser on another device.
The client then polls the token endpoint using the `device_code` until approval succeeds or the transaction ends.

The code entered by the user is a pairing code, not an access token and not proof of identity by itself. A safe authorization page should identify the requesting client and requested access so the user can reject a code they did not initiate. Treat `device_code` as a secret because anyone holding it may poll for the resulting tokens.
A public device cannot protect an embedded client secret.

The client must follow the server-provided polling interval, or use the protocol default of five seconds if none is supplied. `authorization_pending` means wait at least that interval before trying again; `slow_down` means add five seconds to the interval for this and all later polls. After a connection timeout, reduce polling frequency before retrying; exponential backoff is recommended. Stop polling on every other token-endpoint error, including denial and expiry, and show an appropriate result to the user.
The authorization server should rate-limit guesses of the short user code. Start a device authorization transaction in response to a user action rather than automatically at app startup or expiry. Faster polling does not accelerate human approval and can overload the authorization server.
An ordinary browser or mobile app should use Authorization Code with PKCE instead.

| Step | Device authorization trace |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Request | After the user asks to sign in, the device sends its client ID and requested scope to the device authorization endpoint over TLS; the server returns codes, verification URI, interval and expiry. |
| 2. Display | Device shows the user code and URI, with concise instructions and a timeout. |
| 3. Approve | User opens the URI on a separate device, authenticates at the authorization server, reviews the client and scope, then approves or denies. |
| 4. Poll | Device polls the token endpoint with `grant_type=urn:ietf:params:oauth:grant-type:device_code` and its secret `device_code`; it handles pending, `slow_down`, denial, timeout backoff and expiry responses. |
| 5. Use | After approval, the device receives tokens and presents the access token only to its intended resource server. |

## Code Examples

### Bind state, PKCE and nonce before redirecting

`state` correlates the callback with the initiating browser transaction. **PKCE** (Proof Key for Code Exchange) prevents someone who intercepts only the authorization code from redeeming it. An OIDC `nonce` binds the returned ID token to the expected login transaction. These values serve different boundaries; create them independently and store them in a protected, expiring transaction record.

This complete Node module builds and consumes that record. `consumePending` is synchronous only for this local teaching model; a shared deployment requires an atomic compare-and-consume store operation bound to the authenticated browser session. Pin issuer metadata and endpoint configuration when the transaction starts, not from callback input. A client supporting multiple authorization servers must verify the response issuer (for example, RFC 9207's `iss` parameter) or use another documented mix-up defense before redeeming a code.
This sample binds the expected issuer into the pending transaction; set `requireIssuerResponse` when the provider supports RFC 9207, or use a separate documented defense.

```js
const { randomBytes, createHash, timingSafeEqual } = require('node:crypto');

function beginLogin(config, now = Date.now()) {
  const codeVerifier = randomBytes(32).toString('base64url');
  if (typeof config.issuer !== 'string' || !config.issuer) throw new Error('configure a trusted issuer');
  const pending = { state: randomBytes(32).toString('base64url'), codeVerifier,
    nonce: randomBytes(32).toString('base64url'), issuer: config.issuer,
    requireIssuerResponse: config.requireIssuerResponse === true, expiresAt: now + 300_000 };
  const url = new URL(config.authorizationEndpoint);
  if (url.protocol !== 'https:') throw new Error('authorization endpoint must use TLS');
  const scopes = new Set(config.scopes);
  if (config.oidc) scopes.add('openid');
  for (const [key, value] of Object.entries({ response_type: 'code',
    client_id: config.clientId, redirect_uri: config.redirectUri,
    scope: [...scopes].join(' '), state: pending.state,
    code_challenge: createHash('sha256').update(codeVerifier).digest('base64url'),
    code_challenge_method: 'S256', ...(config.oidc ? { nonce: pending.nonce } : {}) })) {
    url.searchParams.set(key, value);
  }
  return { url: url.toString(), pending };
}
function consumePending(browserSession, callback, now = Date.now()) {
  const pending = browserSession.pending;
  const state = typeof callback?.state === 'string' ? callback.state : '';
  const expectedState = typeof pending?.state === 'string' ? pending.state : '';
  const validState = /^[A-Za-z0-9_-]{43}$/.test(state) &&
    /^[A-Za-z0-9_-]{43}$/.test(expectedState) &&
    timingSafeEqual(Buffer.from(state), Buffer.from(expectedState));
  if (!pending || now >= pending.expiresAt || !validState) {
    throw new Error('invalid login transaction');
  }
  const responseIssuer = callback?.iss;
  if (typeof pending.issuer !== 'string' ||
      (responseIssuer !== undefined && responseIssuer !== pending.issuer) ||
      (pending.requireIssuerResponse && responseIssuer !== pending.issuer)) {
    throw new Error('authorization server mismatch');
  }
  delete browserSession.pending; // consume before any asynchronous exchange
  if (callback.error) throw new Error('provider authorization rejected');
  if (typeof callback.code !== 'string' || callback.code.length === 0 || callback.code.length > 2048) {
    throw new Error('invalid authorization code');
  }
  return { code: callback.code, codeVerifier: pending.codeVerifier, nonce: pending.nonce,
    issuer: pending.issuer };
}
module.exports = { beginLogin, consumePending };
```

Trace: create/store a transaction, redirect to the provider, receive `code` and `state`, atomically consume the matching record, then redeem the code at the token endpoint pinned to the stored issuer, using its original verifier and exact redirect URI. A missing state must never match a missing stored state. A second callback cannot reuse the record.
Bound stored attempts per browser and decide whether concurrent login tabs have separate transaction IDs or intentionally replace earlier attempts. Save session state before redirecting; assigning `req.session = { ... }` discards the session middleware contract.

### The token exchange and resulting identity

Use a maintained OAuth/OIDC library for the provider's token-endpoint authentication method and ID-token validation. Request only the scopes the application needs. For authorization code redemption, send `grant_type=authorization_code`, the code, exact registered `redirect_uri` and stored `code_verifier`; native loopback redirect handling follows its registered-client profile.
Confidential clients additionally use the registered authentication method; public clients never ship a client secret. Use TLS, a total deadline and a bounded response body; a failed or uncertain exchange does not justify logging the code/secret or endlessly retrying a single-use code.

Access-token responses need runtime validation. `expires_in` and `refresh_token` are not universally present. Some providers return a form-encoded response unless the client requests JSON; errors can appear in the body as well as HTTP status. Keep provider tokens server-side when using a browser backend, and protect its opaque session cookie with the [session contract](20.5.1.04-sessions-cookies.md).
Log safe correlation identifiers, not codes, tokens, verifiers or client secrets. Introspection adds a network and availability dependency; caching its result creates a bounded stale-authorization window.

For **OIDC**, request the `openid` scope and validate the ID token with trusted issuer configuration: signature/algorithm/key, exact `iss`, your client ID in `aud`, applicable `azp` rules, `exp`, the stored `nonce`, and any requested authentication age/assurance. Apply required hash checks for the selected response flow. Map the local account using the stable `(issuer, sub)` identity; do not auto-link accounts solely by an unverified or mutable email address.
Regenerate the local session only after this succeeds. An ID token is intended for the client and is not a general API access token.

### GitHub OAuth is a provider-specific access flow

GitHub OAuth Apps authorize GitHub API access; their ordinary authorization flow does not return an OIDC ID token. Use its documented code/PKCE/state contract, request only necessary scopes (for example, reading user identity does not require broad `repo` access), request the expected token-response format, and call the authenticated user API when implementing login. Treat the immutable provider user ID as the account key and validate any email-based linking policy separately.
GitHub Actions workload OIDC is a different flow.

### Refresh is serialized per grant

A rotating refresh credential must be consumed and its successor stored as one coordinated state transition. Two concurrent requests can otherwise redeem the same token, trigger provider reuse detection, or overwrite the newer successor. Use a per-grant serialization/CAS policy and handle the lost-response boundary.
For public clients, RFC 9700 requires refresh-token rotation or sender-constrained refresh tokens. Provider refresh rotation and API access-token revocation are separate; logout cannot guarantee immediate rejection by an offline verifier unless that verifier checks current state. Client-credentials grants identify a machine and do not represent an interactive user's consent.

## Real-World Decisions

| Situation | Choose and verify |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider login for a web application | OIDC authorization code with PKCE; validate identity, then create a local session. A backend can retain provider tokens and give the browser an opaque session cookie. |
| Third-party calendar integration | OAuth authorization code with the smallest required scopes; model the provider grant separately from the application's login session. |
| Scheduled backend job | Client credentials when the job acts with its own service authority; use a user grant only when it must act for a particular user. |
| Native application | Authorization code with PKCE through the system browser; protect retained credentials using platform secure storage. An embedded client secret does not make it confidential. |
| Browser application calling an API directly | Authorization code with PKCE; evaluate JavaScript token exposure, refresh policy and cross-origin API requirements. Memory storage reduces persistence but does not stop active malicious JavaScript. |

### Choose the browser-to-API architecture

A browser application can use OAuth with three distinct architectures. They trade proxy and server costs against how much token authority reaches JavaScript:

| Pattern | Token boundary | Main cost or remaining risk |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Backend for Frontend (BFF)** | The backend is the confidential OAuth client, stores access and refresh tokens, and proxies every resource-server request. The browser holds an application session cookie. | Strongest token isolation of these patterns, but all API traffic passes through a backend that must be operated and secured. Cookie-authenticated endpoints still need CSRF defenses; active XSS can still act through the user's browser. |
| **Token-mediating backend** | The backend performs OAuth and retains refresh credentials, then gives access tokens to browser code for direct API calls. | Avoids proxying every request, but active XSS can steal or use exposed access tokens and can request another token through the backend. |
| **Browser-based OAuth client** | JavaScript is a public client and handles authorization-code redemption with PKCE; any returned tokens are available to the browser application. | Simplest server footprint, but active XSS can act as the user and may steal tokens. A client secret embedded in the bundle is not confidential. |

RFC 10017 presents these patterns in decreasing order of security and strongly recommends a BFF for business, sensitive and personal-data applications. A token-mediating backend is a compromise when proxying is impractical; assess whether its remaining access-token exposure is acceptable. A BFF reduces token theft, but does not stop malicious code from issuing requests through the user's live session.
For every cookie-authenticated backend, define the [CSRF contract](../02-attacks-and-defense/20.5.2.02-csrf.md); `HttpOnly` prevents direct script reads, not authenticated actions by active XSS.

## How SAML and Passkeys Fit

OIDC and SAML can both support federated authentication; choose according to the customer's identity provider (IdP) and integration contract. SAML 2.0 exchanges XML messages containing assertions between an IdP and a service provider (SP); the SP validates the signed message object and its profile-specific bindings. SCIM provisioning and just-in-time account creation are separate lifecycle mechanisms: just-in-time creation at login does not by itself deliver later deprovisioning.
The flows, assertion validation and protocol comparison live in [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md).

Strengthening the login itself — TOTP, WebAuthn ceremonies, passkeys, assurance levels, and why passkeys are phishing-resistant — lives in [MFA & Passkeys](20.5.1.08-mfa-passkeys-webauthn.md).

## Summary

OAuth separates a client's delegated API access from the resource owner's credentials. OIDC adds a validated authentication assertion for the client. A safe integration binds the initiating browser transaction, code redemption, provider identity, local session and API authorization at their respective boundaries.
Choose the grant from the client's capabilities, and make token exposure, refresh coordination and revocation delays explicit.

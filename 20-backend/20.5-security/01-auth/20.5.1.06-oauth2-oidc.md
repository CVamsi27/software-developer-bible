# OAuth 2.0 & OpenID Connect

> Stage 5 of the [Auth Learning Track](INDEX.md) — prev: [JWT](20.5.1.05-jwt.md) · next: [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md)


## Definition

OAuth 2.0 lets a client obtain limited access to a protected API without collecting the resource owner's password. For example, a calendar application can receive permission to read a user's calendar while the provider keeps control of login and the authorized scope. The client and API can belong to different organizations or to the same organization.

> **Textbook Definition:** OAuth 2.0 is an authorization framework in which a client obtains an access token from an authorization server and presents it to a resource server under an authorized grant. OpenID Connect (OIDC) adds an authentication layer: the client receives and validates an ID token describing an end-user authentication.

An **access token** authorizes access to its intended API. An **ID token** conveys authentication claims to its intended client. A successful OAuth exchange alone does not define a universal login assertion; OIDC supplies that separate contract. Neither token automatically creates your application's local session or grants access to every local resource.

## First Principles

Suppose a calendar application asks for a user's provider password. The application now holds a credential that can authorize more than reading a calendar, and the provider cannot distinguish the application's intended use from other uses of that credential. Changing the password also disrupts every application that received it.

Delegation therefore needs a separate credential with a defined recipient, permitted operations and lifetime. The provider decides whether to issue that credential; the API enforces its meaning. Redirecting the browser for approval introduces another problem: the callback must belong to the transaction this browser actually started. Authentication, callback correlation, code redemption and API authorization are separate trust boundaries, so one successful check cannot replace the others.

## How It Works

### Four roles divide approval from API access

| Role | Job in the calendar example |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| Resource owner | The user who can authorize access to their calendar |
| Client | The application requesting calendar access |
| Authorization server | The provider component that authenticates the user as needed, evaluates the grant and issues tokens |
| Resource server | The calendar API that validates the access credential and enforces permissions |

These are protocol roles, not a requirement for four processes. A provider can host its authorization and resource servers together. The client may be a backend, browser application or native application. The user's browser transports redirects; it is not the calendar API.

A **confidential client** can protect an authentication credential in its deployment, such as a backend. A **public client**, such as shipped browser or native code, cannot keep an embedded secret confidential. Authorization code with PKCE fits both; confidential clients also authenticate at the token endpoint using their registered method. Client credentials fits a service using its own authority rather than an interactive user's grant.

### Trace authorization code from approval to use

This trace uses a web application with a backend. A public client has the same code/PKCE binding but redeems the code itself without a client secret.

| Step | Message and resulting state |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. Start | The client stores a short-lived, browser-bound login transaction containing state, a PKCE verifier and, for this OIDC login, a nonce. |
| 2. Redirect | The browser visits the authorization endpoint with the registered client ID, exact redirect URI, requested scopes, state and PKCE challenge. OIDC includes `openid` and the nonce. |
| 3. Authorize | The authorization server authenticates the user as needed and evaluates permission, including consent where required. It can reject the request or reuse an existing approved grant. |
| 4. Return | The server redirects the browser to the client's callback with a short-lived authorization code and state. The code is not an API access credential. |
| 5. Redeem | The client validates and consumes its pending transaction, then sends the code, original verifier and redirect URI to the token endpoint over TLS. The server checks the code's bindings and client authentication where applicable. |
| 6. Establish identity | The client validates the returned OIDC ID token before mapping the provider subject to a local account. A refresh token may be issued; it is not guaranteed. |
| 7. Call the API | The client presents the access token to the intended resource server. The API validates its own token contract and the requested operation's authorization. |

A scope such as `calendar.read` describes delegated permission. The API still decides which calendar the caller may read, and may need current account or resource state. A valid token with the wrong audience, insufficient permission or disabled account must not be treated as universal authority.

### PKCE proves possession of the transaction verifier

**Proof Key for Code Exchange (PKCE)** starts with a high-entropy verifier kept by the client. The authorization request sends `BASE64URL(SHA256(verifier))` as the challenge with method `S256`. When redeeming the code, the client sends the original verifier; the server hashes it and compares it with the challenge bound to that code.

Someone who obtains only the code lacks the verifier and cannot complete that exchange. PKCE does not authenticate the user or make a browser-held access token safe from malicious JavaScript. `state` correlates the returned transaction, while the OIDC `nonce` binds the ID token to the expected authentication request. This chapter uses all three. RFC 9700 permits appropriately implemented PKCE or OIDC nonce mechanisms to provide callback CSRF protection under their stated conditions; an unconditional claim that every secure client must always use state would overstate the protocol requirement.

## Code Examples

### Bind state, PKCE and nonce before redirecting

`state` correlates the callback with the initiating browser transaction. **PKCE** (Proof Key for Code Exchange) prevents someone who intercepts only the authorization code from redeeming it. An OIDC `nonce` binds the returned ID token to the expected login transaction. These values serve different boundaries; create them independently and store them in a protected, expiring transaction record.

This complete Node module builds and consumes that record. `consumePending` is synchronous only for this local teaching model; a shared deployment requires an atomic compare-and-consume store operation bound to the authenticated browser session. The authorization endpoint/configuration comes from trusted provider setup, not callback input.

```js
const { randomBytes, createHash, timingSafeEqual } = require('node:crypto');

function beginLogin(config, now = Date.now()) {
  const codeVerifier = randomBytes(32).toString('base64url');
  const pending = { state: randomBytes(32).toString('base64url'), codeVerifier,
    nonce: randomBytes(32).toString('base64url'), expiresAt: now + 300_000 };
  const url = new URL(config.authorizationEndpoint);
  if (url.protocol !== 'https:') throw new Error('authorization endpoint must use TLS');
  for (const [key, value] of Object.entries({ response_type: 'code',
    client_id: config.clientId, redirect_uri: config.redirectUri,
    scope: config.scopes.join(' '), state: pending.state,
    code_challenge: createHash('sha256').update(codeVerifier).digest('base64url'),
    code_challenge_method: 'S256', ...(config.oidc ? { nonce: pending.nonce } : {}) })) {
    url.searchParams.set(key, value);
  }
  return { url: url.toString(), pending };
}
function consumePending(browserSession, callback, now = Date.now()) {
  const pending = browserSession.pending;
  if (!pending || now >= pending.expiresAt || typeof callback.state !== 'string' ||
      callback.state.length !== pending.state.length ||
      !timingSafeEqual(Buffer.from(callback.state), Buffer.from(pending.state))) {
    throw new Error('invalid login transaction');
  }
  delete browserSession.pending; // consume before any asynchronous exchange
  if (callback.error) throw new Error('provider authorization rejected');
  if (typeof callback.code !== 'string' || callback.code.length === 0 || callback.code.length > 2048) {
    throw new Error('invalid authorization code');
  }
  return { code: callback.code, codeVerifier: pending.codeVerifier, nonce: pending.nonce };
}
module.exports = { beginLogin, consumePending };
```

Trace: create/store a transaction, redirect to the provider, receive `code` and `state`, atomically consume the matching record, then exchange with its original verifier and exact redirect URI. A missing state must never match a missing stored state. A second callback cannot reuse the record. Bound stored attempts per browser and decide whether concurrent login tabs have separate transaction IDs or intentionally replace earlier attempts. Save session state before redirecting; assigning `req.session = { ... }` discards the session middleware contract.

### The token exchange and resulting identity

Use a maintained OAuth/OIDC library for the provider's token-endpoint authentication method and ID-token validation. For authorization code redemption, send `grant_type=authorization_code`, the code, exact registered `redirect_uri` and stored `code_verifier`. Confidential clients additionally use the registered authentication method; public clients never ship a client secret. Use TLS, a total deadline and a bounded response body; a failed or uncertain exchange does not justify logging the code/secret or endlessly retrying a single-use code.

Access-token responses need runtime validation. `expires_in` and `refresh_token` are not universally present. Some providers return a form-encoded response unless the client requests JSON; errors can appear in the body as well as HTTP status. Keep provider tokens server-side when using a browser backend, and protect its opaque session cookie with the [session contract](20.5.1.04-sessions-cookies.md).

For **OIDC**, request the `openid` scope and validate the ID token with trusted issuer configuration: signature/algorithm/key, exact `iss`, your client ID in `aud`, applicable `azp` rules, `exp`, the stored `nonce`, and any requested authentication age/assurance. Apply required hash checks for the selected response flow. Map the local account using the stable `(issuer, sub)` identity; do not auto-link accounts solely by an unverified or mutable email address. Regenerate the local session only after this succeeds. An ID token is intended for the client and is not a general API access token.

### GitHub OAuth is a provider-specific access flow

GitHub OAuth Apps authorize GitHub API access; their ordinary authorization flow does not return an OIDC ID token. Use its documented code/PKCE/state contract, request only necessary scopes (for example, reading user identity does not require broad `repo` access), request the expected token-response format, and call the authenticated user API when implementing login. Treat the immutable provider user ID as the account key and validate any email-based linking policy separately. GitHub Actions workload OIDC is a different flow.

### Refresh is serialized per grant

A rotating refresh credential must be consumed and its successor stored as one coordinated state transition. Two concurrent requests can otherwise redeem the same token, trigger provider reuse detection, or overwrite the newer successor. Use a per-grant serialization/CAS policy and handle the lost-response boundary. Provider refresh rotation and API access-token revocation are separate; logout cannot guarantee immediate rejection by an offline verifier unless that verifier checks current state. Client-credentials grants identify a machine and do not represent an interactive user's consent.

## Real-World Decisions

| Situation | Choose and verify |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider login for a web application | OIDC authorization code with PKCE; validate identity, then create a local session. A backend can retain provider tokens and give the browser an opaque session cookie. |
| Third-party calendar integration | OAuth authorization code with the smallest required scopes; model the provider grant separately from the application's login session. |
| Scheduled backend job | Client credentials when the job acts with its own service authority; use a user grant only when it must act for a particular user. |
| Native application | Authorization code with PKCE through the system browser; protect retained credentials using platform secure storage. An embedded client secret does not make it confidential. |
| Browser application calling an API directly | Authorization code with PKCE; evaluate JavaScript token exposure, refresh policy and cross-origin API requirements. Memory storage reduces persistence but does not stop active malicious JavaScript. |

An `HttpOnly` cookie hides its value from JavaScript, but the browser sends it automatically under its cookie rules. A backend session therefore needs the [CSRF contract](../02-attacks-and-defense/20.5.2.02-csrf.md). Putting a token in a cookie does not by itself solve storage, authorization or CSRF. Choose the browser/backend boundary before choosing the storage location.

## SSO, SAML, and Passkeys

OIDC covers consumer-style federated login, but enterprise workforce SSO is its own protocol world: SAML 2.0 exchanges signed XML assertions between an IdP and your SP, and pairs with SCIM/JIT provisioning so accounts follow HR lifecycle. ## Common Mistakes

- **Treating any provider token as proof of local login.** Validate the intended identity protocol and provider-specific subject contract. An ID token is not a general API access token.
- **Using implicit or password grants for new integrations.** RFC 9700 advises against implicit access-token delivery and prohibits the resource-owner password credentials grant. Authorization code with PKCE supports provider-controlled authentication without giving the client the user's password.
- **Trusting callback-supplied provider endpoints.** Bind the expected issuer and endpoints to the pending transaction. A multi-provider client must prevent issuer mix-up rather than redeeming a code at whichever endpoint the callback names.
- **Embedding secrets in public clients.** Distributed browser/native code cannot keep a shared client secret confidential.
- **Promising instant revocation.** Grant revocation, refresh rejection, already-issued access-token rejection and local logout can have different enforcement times.
- **Sharing or caching credentials without grant ownership.** Key storage and refresh coordination by the correct user/client grant and provider, and preserve the required tenant boundary.

## Best Practices

Use trusted provider metadata and a maintained OAuth/OIDC implementation. Apply exact redirect URI matching subject to the protocol's documented native loopback exception; do not accept arbitrary callback destinations or open redirects. Use PKCE for public clients and for confidential clients as recommended by RFC 9700. Bind and expire each transaction, prevent reuse and implement the provider's required token and issuer validation.

Request the minimum scopes needed. If refresh tokens are issued to public clients, RFC 9700 requires rotation or sender-constrained tokens: credentials whose use also requires proof from the intended sender. Rotation needs coordinated successor storage and a recovery policy for an uncertain response, as described above. Do not assume a provider issues refresh tokens or supports a client-selected lifetime.

Define separate logout and revocation policies for the local session, provider grant and API access. Log outcomes and safe correlation identifiers, excluding codes, tokens, verifiers and client secrets. Rate-limit and monitor failures without turning callback URLs into credential-bearing logs.

## Performance Considerations

Code redemption and refresh require provider network calls. Use bounded requests and measure provider latency; do not retry an uncertain single-use code without understanding its outcome. Local JWT verification avoids a per-request introspection call but needs trusted key management and a revocation policy. Introspection adds network dependency; caching its result introduces a bounded stale-authorization window. Cache tokens and validation results only within their audience, grant, lifetime and tenant boundaries.

## Summary

OAuth separates a client's delegated API access from the resource owner's credentials. OIDC adds a validated authentication assertion for the client. A safe integration binds the initiating browser transaction, code redemption, provider identity, local session and API authorization at their respective boundaries. Choose the grant from the client's capabilities, and make token exposure, refresh coordination and revocation delays explicit.

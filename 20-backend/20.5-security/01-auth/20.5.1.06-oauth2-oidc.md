# OAuth 2.0 & OpenID Connect

> Stage 5 of the [Auth Learning Track](INDEX.md) — prev: [JWT](20.5.1.05-jwt.md) · next: [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md)

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

OAuth 2.0 is an authorization framework that enables applications to obtain limited access to user resources on a third-party service without exposing the user's credentials. It is defined by RFC 6749 and provides a standardized protocol for delegated authorization. OAuth 2.0 separates the roles of resource owner, client, authorization server, and resource server, enabling secure delegated access.

> **Textbook Definition:** OAuth 2.0 defines delegated authorization between clients, authorization servers and resource servers. OpenID Connect adds an identity layer with authentication assertions and validation rules; an access token and an identity token have different purposes.

OAuth 2.0 is NOT an authentication protocol — it's an authorization protocol. OpenID Connect (OIDC) extends OAuth 2.0 to provide authentication.

## First Principles

OAuth exists because of one delegation problem:

1. **Apps need access without your password.** Sharing credentials gives away everything, forever, to everyone — so OAuth inverts it: the resource server trusts *tokens* issued by an authorization server that handled the user interaction. The client never receives the user's provider password; the browser sends it only to the intended provider over its protected login channel.
2. **Flows differ by client capability, by necessity.** A confidential server can authenticate itself; a public SPA/mobile client cannot safely keep a client secret. Both can use authorization code with PKCE, which binds redemption to a transaction verifier, not the user's identity. Backend service with no user → client credentials. Each flow exists because a trust assumption died; knowing which assumption each flow patches is the understanding.
3. **OIDC is OAuth + identity, not OAuth rebranded.** OAuth answers "what may this client access?"; OIDC adds the ID token ("who is the user?") on the same rails — one protocol answering the two questions apps actually have.

## Why Do We Need It?

- **Credential Separation**: Users never share passwords with third-party applications
- **Granular Access Control**: Users can grant limited permissions (scopes)
- **Revocable Access**: Users can revoke access without changing passwords
- **Standard Protocol**: Universal standard supported by all major platforms
- **Delegated Authorization**: Applications can act on behalf of users
- **Mobile/SPA Support**: Designed for modern application architectures

## Code Examples

### Bind state, PKCE and nonce before redirecting

`state` correlates the callback with the initiating browser transaction. **PKCE** (Proof Key for Code Exchange) prevents someone who intercepts only the authorization code from redeeming it. An OIDC `nonce` binds the returned ID token to the expected login transaction. These values serve different boundaries; create them independently and store them in a protected, expiring transaction record.

This complete Node module builds and consumes that record. `consumePending` is synchronous only for this local teaching model; a shared deployment requires an atomic compare-and-consume store operation bound to the authenticated browser session. The authorization endpoint/configuration comes from trusted provider setup, not callback input.

```js
const { randomBytes, createHash, timingSafeEqual } = require('node:crypto');

function beginLogin(config, now = Date.now()) {
  const codeVerifier = randomBytes(32).toString('base64url');
  const pending = { state: randomBytes(32).toString('base64url'), codeVerifier,
    nonce: randomBytes(32).toString('base64url'), expiresAt: now + 300_000 };
  const url = new URL(config.authorizationEndpoint);
  if (url.protocol !== 'https:') throw new Error('authorization endpoint must use TLS');
  for (const [key, value] of Object.entries({ response_type: 'code',
    client_id: config.clientId, redirect_uri: config.redirectUri,
    scope: config.scopes.join(' '), state: pending.state,
    code_challenge: createHash('sha256').update(codeVerifier).digest('base64url'),
    code_challenge_method: 'S256', ...(config.oidc ? { nonce: pending.nonce } : {}) })) {
    url.searchParams.set(key, value);
  }
  return { url: url.toString(), pending };
}
function consumePending(browserSession, callback, now = Date.now()) {
  const pending = browserSession.pending;
  if (!pending || now >= pending.expiresAt || typeof callback.state !== 'string' ||
      callback.state.length !== pending.state.length ||
      !timingSafeEqual(Buffer.from(callback.state), Buffer.from(pending.state))) {
    throw new Error('invalid login transaction');
  }
  delete browserSession.pending; // consume before any asynchronous exchange
  if (callback.error) throw new Error('provider authorization rejected');
  if (typeof callback.code !== 'string' || callback.code.length === 0 || callback.code.length > 2048) {
    throw new Error('invalid authorization code');
  }
  return { code: callback.code, codeVerifier: pending.codeVerifier, nonce: pending.nonce };
}
module.exports = { beginLogin, consumePending };
```

Trace: create/store a transaction, redirect to the provider, receive `code` and `state`, atomically consume the matching record, then exchange with its original verifier and exact redirect URI. A missing state must never match a missing stored state. A second callback cannot reuse the record. Bound stored attempts per browser and decide whether concurrent login tabs have separate transaction IDs or intentionally replace earlier attempts. Save session state before redirecting; assigning `req.session = { ... }` discards the session middleware contract.

### The token exchange and resulting identity

Use a maintained OAuth/OIDC library for the provider's token-endpoint authentication method and ID-token validation. For authorization code redemption, send `grant_type=authorization_code`, the code, exact registered `redirect_uri` and stored `code_verifier`. Confidential clients additionally use the registered authentication method; public clients never ship a client secret. Use TLS, a total deadline and a bounded response body; a failed or uncertain exchange does not justify logging the code/secret or endlessly retrying a single-use code.

Access-token responses need runtime validation. `expires_in` and `refresh_token` are not universally present. Some providers return a form-encoded response unless the client requests JSON; errors can appear in the body as well as HTTP status. Keep provider tokens server-side when using a browser backend, and protect its opaque session cookie with the [session contract](20.5.1.04-sessions-cookies.md).

For **OIDC**, request the `openid` scope and validate the ID token with trusted issuer configuration: signature/algorithm/key, exact `iss`, your client ID in `aud`, applicable `azp` rules, `exp`, the stored `nonce`, and any requested authentication age/assurance. Apply required hash checks for the selected response flow. Map the local account using the stable `(issuer, sub)` identity; do not auto-link accounts solely by an unverified or mutable email address. Regenerate the local session only after this succeeds. An ID token is intended for the client and is not a general API access token.

### GitHub OAuth is a provider-specific access flow

GitHub OAuth Apps authorize GitHub API access; their ordinary authorization flow does not return an OIDC ID token. Use its documented code/PKCE/state contract, request only necessary scopes (for example, reading user identity does not require broad `repo` access), request the expected token-response format, and call the authenticated user API when implementing login. Treat the immutable provider user ID as the account key and validate any email-based linking policy separately. GitHub Actions workload OIDC is a different flow.

### Refresh is serialized per grant

A rotating refresh credential must be consumed and its successor stored as one coordinated state transition. Two concurrent requests can otherwise redeem the same token, trigger provider reuse detection, or overwrite the newer successor. Use a per-grant serialization/CAS policy and handle the lost-response boundary. Provider refresh rotation and API access-token revocation are separate; logout cannot guarantee immediate rejection by an offline verifier unless that verifier checks current state. Client-credentials grants identify a machine and do not represent an interactive user's consent.

## Real-World Use Cases

### 1. Social Login

- "Sign in with Google/GitHub/Facebook"
- User grants access to basic profile information
- Application doesn't store or handle user passwords

### 2. API Access (Machine-to-Machine)

- Server-to-server communication using Client Credentials flow
- No user involvement; service authenticates directly
- Used for backend services, cron jobs, microservices

### 3. Third-Party Integrations

- Accessing user's Google Drive, Dropbox, or GitHub repos
- Granular scope-based permissions
- User can revoke access at any time

### 4. Mobile Applications

- Authorization Code flow with PKCE (no client secret on device)
- Tokens stored in secure storage (Keychain/Keystore)
- Refresh tokens for seamless session management

### 5. SPA + API Architecture

- Authorization Code flow with PKCE
- Tokens stored in httpOnly cookies or memory
- API validates tokens on each request

## SSO, SAML, and Passkeys

OIDC covers consumer-style federated login, but enterprise workforce SSO is its own protocol world: SAML 2.0 exchanges signed XML assertions between an IdP and your SP, and pairs with SCIM/JIT provisioning so accounts follow HR lifecycle. ## Common Mistakes

1. **Using implicit flow**: Deprecated due to token exposure in URL fragments. Use Authorization Code with PKCE.

2. **Not validating the `state` parameter**: Enables CSRF attacks. Always generate, store, and validate state.

3. **Storing client_secret in frontend code**: Exposes the secret to attackers. Only use in server-side applications.

4. **Not requesting minimal scopes**: Request only the scopes needed. Excessive scopes violate the principle of least privilege.

5. **Assuming a universal response shape**: Some providers omit expiry/refresh tokens. Validate the actual token profile and handle expired/revoked API responses.

6. **Not using PKCE for public clients**: PKCE prevents authorization code interception attacks.

7. **Sharing tokens between users**: Each user should have their own token. Sharing tokens compromises audit trails and security.

8. **Not implementing token revocation**: Without revocation, compromised tokens remain valid until expiry.

## Best Practices

1. **Always use Authorization Code flow with PKCE** for public clients (SPA, mobile)

2. **Validate the `state` parameter** to prevent CSRF attacks

3. **Request minimal scopes** — only what's needed

4. **Store tokens securely**: httpOnly cookies for web, secure storage for mobile

5. **Implement refresh token rotation** with single-use tokens

6. **Validate OIDC ID-token and resource-server access-token contracts separately**; opaque tokens require their own trusted validation/introspection policy

7. **Choose access lifetimes from provider policy and exposure**; do not assume every provider lets the client set them

8. **Define logout at each boundary**: local session, provider grant and already-issued API token

9. **Log and monitor** OAuth usage for anomaly detection
10. **Keep client secrets secure** — never expose in client-side code

## Performance Considerations

| Aspect | Consideration |
| ---------------- | ---------------------------------------------------- |
| Token Exchange | Network round-trip to auth server adds latency |
| Token Caching | Cache tokens locally to reduce network calls |
| Token Validation | JWT validation is fast; introspection adds latency |
| PKCE | Slight overhead for challenge generation, negligible |
| Refresh Flow | Additional network request when tokens expire |

## Summary

OAuth 2.0 is the standard framework for delegated authorization, enabling secure third-party access without sharing credentials. Key takeaways:

- Authorization Code flow with PKCE is the gold standard for most use cases
- Always validate the `state` parameter to prevent CSRF
- Use short-lived access tokens with refresh token rotation
- Store tokens securely (httpOnly cookies, secure storage)
- Request minimal scopes
- Implement token revocation for security
- OAuth 2.0 is authorization, not authentication (use OIDC for auth)

# SSO, SAML & Federation

> Stage 6 of the [Auth Learning Track](INDEX.md) — prev: [OAuth2 / OIDC](20.5.1.06-oauth2-oidc.md) · next: [MFA & Passkeys](20.5.1.08-mfa-passkeys-webauthn.md)

An employee signs in through the company's identity provider, then opens your product from an app tile. The identity provider can authenticate the person, but your service still has to prove that the returned assertion was issued for this service, create its own session, and decide what that account may do. Follow that one login from redirect to local authorization; the same boundaries also explain offboarding and replay risk.

## Definition

Single Sign-On (SSO) lets a user authenticate through a central **Identity Provider (IdP)** and access multiple **Service Providers (SPs)** without separately entering credentials each time, while the IdP session and policy permit. Federation is the trust framework that lets an IdP make an identity claim that each SP validates under an agreed contract.

> **Textbook Definition:** Identity federation establishes trust between an identity provider and relying services. Single sign-on reuses an IdP authentication for access to multiple services. SAML Web Browser SSO conveys an assertion in a response; the service provider validates its signature, issuer, recipient, audience and time conditions, and in SP-initiated flow, request correlation.

SAML 2.0 (Security Assertion Markup Language, an OASIS standard published in 2005) is widely used for enterprise workforce federation. In the Web Browser SSO profile, an IdP sends a response containing an XML **assertion** about a subject and authentication event. The response or assertion must be signed according to the agreed profile; the SP validates the signature using a trusted IdP key, checks the response conditions and creates its own local session.

## First Principles

SSO exists because identity is a perimeter problem:

1. **Every app holding its own user store multiplies risk and friction.** One IdP centralizes the credential attack surface, MFA, and offboarding (centralize the source of lifecycle changes, then propagate them to each app) — SSO is the org-scale application of "one fact, one place" (→ 20.4.1.02).
2. **Federation needs an authenticated trust contract.** SAML and OIDC differ in message format, transport and validation. Metadata describes entity IDs, endpoints and keys, but receiving a metadata file does not by itself make its contents trustworthy. Establish its provenance through an authenticated channel or validate its signature under an already trusted key; manage key rollover as a security change.
3. **The single point of failure is chosen, not eliminated.** IdP down = nobody logs in (hopefully — existing local sessions survive for their configured lifetime or until revoked). That concentration is the trade SSO makes deliberately.

## 1. What SSO Actually Means

SSO means each service can reuse an IdP authentication when the IdP session and policy allow it. It does not create one shared session cookie for every application. Each service provider (SP) validates the federation response, maps the identity to its own account and permissions, and creates its own local session.
A person can therefore be logged out of one SP while remaining logged in to the IdP and other SPs.

## 2. SAML Building Blocks

| Concept | What it is |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assertion | XML claims about a subject, authentication event and attributes; the response or assertion must be signed as required by the selected profile |
| Conditions | `NotBefore` / `NotOnOrAfter` validity window + `AudienceRestriction` (which SP may consume it) |
| Signing key | IdP signing certificate or public key trusted by the SP; validate the response or assertion signature required by the profile |
| Metadata | XML describing entity IDs, endpoints, bindings and signing keys; validate who supplied it before trusting those values |
| ACS URL | Assertion Consumer Service — the SP endpoint that receives `SAMLResponse` |
| RelayState | Binding parameter returned with the response; use a random, request-bound value or an allowlisted local destination, never an unchecked redirect URL |
| NameID | The identifier the IdP asserts (usually email or a stable opaque id) |

Metadata is exchanged during setup and refreshed for endpoint or certificate changes. Authenticate the initial metadata source or verify its signature using an already trusted key; then pin the expected entity ID, ACS/SSO endpoints and signing keys. Treat changes and overlapping certificate rollover as controlled trust updates.

## 3. SP-Initiated Flow (the default)

1. The browser requests a protected SP page. With no valid local session, the SP creates a unique `AuthnRequest` ID and stores short-lived correlation state bound to the initiating browser and tenant.
2. The SP redirects the browser to the IdP. With the HTTP Redirect binding, the request is commonly DEFLATE-compressed, Base64-encoded and URL-encoded.
3. The IdP authenticates the user or reuses its IdP session, applying its own policy and any required MFA.
4. The IdP returns a `SAMLResponse` to the SP's Assertion Consumer Service (ACS), commonly in an auto-submitted cross-site form POST. `RelayState` returns the SP's validated local state.
5. The SP's maintained validator checks the trusted signature, issuer, destination, audience, time conditions, subject confirmation, `InResponseTo` and replay state before consuming the signed identity.
6. The SP maps the verified subject to a local account, applies local authorization, rotates or creates the local session, and redirects to the validated destination.

If request correlation depends on a browser cookie, test the cross-site POST against the cookie's `SameSite` policy: a `Lax` or `Strict` cookie may not accompany the ACS POST. Prefer server-side request correlation where possible; if a cross-site cookie is required, choose and test its scope and `SameSite=None; Secure` behavior deliberately. Bind `RelayState` to the request and validate any return path to prevent open redirects.

## 4. Assertion Validation Checklist (what your SP must verify)

Before creating a local session, require the maintained validator to check:

- The response or assertion signature against the IdP key provisioned through authenticated metadata. Never trust a key supplied only by the response.
- The expected IdP issuer, exact ACS destination, allowed response binding and audience.
- `NotBefore`, `NotOnOrAfter`, subject confirmation recipient and expiry, using only a small configured clock tolerance.
- For SP-initiated flow, `InResponseTo` against a live request ID created for this tenant and browser flow.
- An atomic, expiring replay check for the assertion ID, scoped to the IdP/tenant.
- The exact signed assertion selected by the validator. Do not parse a second XML element independently; this disagreement can enable signature-wrapping attacks.

Bound XML and form sizes, reject ambiguous or unexpected response structures, and define the behavior when the request/replay cache is unavailable.

## 5. IdP-Initiated Flow ("unsolicited response")

An IdP can post an assertion after a user clicks an application tile without a preceding SP `AuthnRequest`. The SP can still verify issuer, signature, destination, audience, time window, subject confirmation and assertion replay ID, but it has no SP request ID to bind through `InResponseTo`.

That missing request matters at the browser boundary: an attacker may plant a valid assertion for the attacker's own account in a victim's browser, producing login CSRF or session swapping. `RelayState` alone does not create browser-bound request correlation. Prefer SP-initiated flow. If IdP-initiated login is a customer requirement, make it an explicit policy and add an appropriate user-confirmation or transaction-binding control.

## 6. SAML vs OIDC Comparison

| Decision | SAML 2.0 Web Browser SSO | OpenID Connect |
| ---------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Identity message | XML assertion in a SAML response | ID token (JWT) plus OIDC protocol fields |
| Common browser flow | Redirect to IdP, then browser POST to ACS | OAuth 2.0 authorization-code flow with OIDC validation |
| Main validation work | XML signature coverage, metadata trust, assertion conditions, destination and request correlation | Token issuer/audience/signature/nonce, key rotation and OAuth transaction checks |
| Typical integration pressure | Common in workforce SSO and existing enterprise IdPs | Common in web, mobile and modern enterprise integrations |
| Lifecycle | Not provided by the SSO assertion; commonly paired with SCIM | Also separate from login; provisioning and session revocation need their own policy |

Choose from the customer's IdP, supported clients, existing deployment and security profile. Workforce IdPs can support either protocol. Protocol age alone is not a security decision; a maintained implementation and correct validation matter more than XML versus JSON.

SAML is often a customer integration requirement for workforce or B2B federation, while OIDC is common across web and mobile clients. Confirm the customer's protocol, provisioning and admin workflow before choosing. A domain can route a user to an allowlisted tenant IdP, but it does not prove identity or tenant membership.
An IdP may require phishing-resistant MFA; each SP must check the asserted authentication context and freshness against its own policy. Centralized login and audit logs contribute evidence, but do not alone establish authorization or regulatory compliance.

## Turn the validated response into a local session

### Configure a maintained SAML validator

This configuration factory targets `@node-saml/node-saml` 5.1.0, the patched release used for this example. It pins tenant-specific trust and rejects unsolicited responses. Keep one request-ID cache per IdP; across application instances, use shared storage with a separate namespace for each IdP and expiry matching `requestIdExpirationPeriodMs`.
This version’s `CacheProvider` has separate read and remove operations, so simultaneous copies of one response can race even though later replays fail. Serialize ACS validation per request ID across all instances, or use a version whose cache contract supports atomic consumption. Maintain a separate atomic replay check for assertion IDs.
The default in-memory provider only works when the same provider instance handles request creation and response validation. This is validator configuration, not a complete ACS/session implementation.

```typescript
import { SAML, ValidateInResponseTo, type CacheProvider } from '@node-saml/node-saml';

export function createSamlValidator(idpCert: string, cacheProvider: CacheProvider) {
  if (!idpCert.trim()) throw new Error('provision the trusted IdP signing certificate');
  return new SAML({
    issuer: 'https://app.example.com/metadata',
    audience: 'https://app.example.com/metadata',
    callbackUrl: 'https://app.example.com/auth/saml/acs',
    entryPoint: 'https://idp.customer.example/sso',
    idpIssuer: 'https://idp.customer.example/metadata',
    idpCert,
    wantAssertionsSigned: true,
    wantAuthnResponseSigned: true, // configure the IdP to sign both
    validateInResponseTo: ValidateInResponseTo.always,
    requestIdExpirationPeriodMs: 300_000,
    maxAssertionAgeMs: 300_000,
    acceptedClockSkewMs: 60_000,
    cacheProvider,
    signatureAlgorithm: 'sha256',
    digestAlgorithm: 'sha256',
  });
}
```

An ACS integration receives bounded form input, calls the configured validator, checks the protocol/profile requirements actually enforced by the pinned library, then creates a local session from the validated assertion. For this pinned 5.1.0 release, serialize response validation by request ID across the deployment: `validateInResponseTo` performs a cache read and removal as separate operations, so it does not by itself reject two copies racing concurrently. `InResponseTo` also does not bind the response to the initiating browser by itself; validate a separately stored, browser-bound RelayState transaction before session creation. Consume assertion IDs through an expiring atomic replay store as well.
Never extract identity with a second unrelated XML query: XML signature wrapping exploits disagreement about which element was signed and consumed. Disable external-entity expansion and reject unexpected/ambiguous response structure through a maintained validator.

Map identities using trusted tenant + IdP issuer + a contracted stable subject identifier, not email alone. Just-in-time (**JIT**) provisioning creates a local account after successful authentication; it does not prove that the account remains active tomorrow. Require allowed membership/account state, map only approved group attributes to local privileges, regenerate the session ID, and retain the required authentication assurance/time for step-up policy.
The redirect after ACS success does not automatically create a session cookie.

### What reaches the ACS

This abbreviated XML illustrates the named fields; omitted namespaces, status, subject confirmation and signature values mean it is not a valid test assertion. Its timestamp values are internally consistent examples, not values to accept in a live response.

```xml
<samlp:Response xmlns:samlp="..." Destination="https://app.example.com/auth/saml/acs"
                InResponseTo="_4f2a9c..." ID="_8e7d31...">
  <saml:Assertion xmlns:saml="..." ID="_a1ssert10n">
    <saml:Issuer>https://idp.customer.example/metadata</saml:Issuer>
    <ds:Signature><!-- XML-DSig over the assertion --></ds:Signature>
    <saml:Subject>
        <saml:NameID Format="urn:oasis:names:tc:SAML:2.0:nameid-format:persistent">idp-user-9f2a</saml:NameID>
    </saml:Subject>
    <saml:Conditions NotBefore="2036-08-25T10:00:00Z"
                     NotOnOrAfter="2036-08-25T10:05:00Z">
      <saml:AudienceRestriction>
        <saml:Audience>https://app.example.com/metadata</saml:Audience>
      </saml:AudienceRestriction>
    </saml:Conditions>
    <saml:AuthnStatement AuthnInstant="2036-08-25T09:59:58Z">
      <saml:AuthnContext>
        <saml:AuthnContextClassRef>
          urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport
        </saml:AuthnContextClassRef>
      </saml:AuthnContext>
    </saml:AuthnStatement>
    <saml:AttributeStatement>
      <saml:Attribute Name="groups">
        <saml:AttributeValue>engineering</saml:AttributeValue>
      </saml:Attribute>
    </saml:AttributeStatement>
  </saml:Assertion>
</samlp:Response>
```

Cache parsed, trusted metadata instead of rereading it on every login, and bound XML/form size and validation concurrency. Measure the ACS path under expected traffic. Keep assertion validity short, but choose local session lifetime and revocation independently.
Log privacy-safe correlation IDs and validation outcomes; avoid logging full assertions or personal NameIDs by default.

## When identity access changes

```text
Directory disable -> IdP refuses new login
SCIM deactivation -> local account disabled -> app rejects current requests
Local/session revocation -> existing SP session rejected within its propagation bound
```

**SCIM** (System for Cross-domain Identity Management) provides account/group provisioning operations; it is not a login protocol. Authenticate its endpoints, enforce tenant ownership, make repeated updates safe, and monitor delivery/retry failures. If provisioning is delayed, a local session can remain usable even though the IdP user is disabled. Define the allowed delay and a fallback current-state check. Single logout, session revocation and deprovisioning are different mechanisms; browser logout at the IdP is not proof that every app session ended.

## Summary

Federation lets an SP reuse an IdP authentication under a configured trust contract. The SP must validate the exact signed response, bind it to the expected tenant and login transaction, apply local authorization, and create a separate local session. SP-initiated flow gives the clearest request correlation; provisioning and session revocation still need their own lifecycle contract.

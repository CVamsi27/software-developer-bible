# SSO, SAML & Federation

> Stage 6 of the [Auth Learning Track](INDEX.md) — prev: [OAuth2 / OIDC](20.5.1.06-oauth2-oidc.md) · next: [MFA & Passkeys](20.5.1.08-mfa-passkeys-webauthn.md)

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Single Sign-On (SSO) is an architecture in which a user authenticates once — against a central **Identity Provider (IdP)** — and subsequently accesses multiple **Service Providers (SPs)** without re-entering credentials. Federation is the trust framework that makes this work: the IdP cryptographically vouches for the user's identity to each SP.

> **Textbook Definition:** Identity federation establishes trust between an identity provider and relying services; single sign-on uses that trust to reuse authentication across services. SAML conveys signed assertions subject to recipient, audience and time validation.

SAML 2.0 (Security Assertion Markup Language, OASIS standard, 2005) is the dominant federation protocol for enterprise workforce SSO. The IdP issues an XML **assertion** stating "this subject authenticated at this time by this method," digitally signed with the IdP's private key; the SP validates the signature against a pre-exchanged X.509 certificate and creates its own local session.

## First Principles

SSO exists because identity is a perimeter problem:

1. **Every app holding its own user store multiplies risk and friction.** One IdP centralizes the credential attack surface, MFA, and offboarding (centralize the source of lifecycle changes, then propagate them to each app) — SSO is the org-scale application of "one fact, one place" (→ 20.4.1.02).
2. **Federation needs a trust contract.** SAML (XML, enterprise standard) and OIDC (modern, web-first) share an assertion trust model but have different validation, transport and session contracts: principal, IdP assertion, SP reliance on signatures. The metadata exchange *is* the trust root — everything else is protocol.
3. **The single point of failure is chosen, not eliminated.** IdP down = nobody logs in (hopefully — existing local sessions survive for their configured lifetime or until revoked). That concentration is the trade SSO makes deliberately.

## Why Do We Need It?

1. **One login, many apps** — employees touch dozens of internal tools; per-app passwords increase reuse and recovery burden.
2. **Centralized policy** — MFA enforcement, conditional access, and device checks are applied once at the IdP (Okta, Microsoft Entra ID, Ping) instead of N times.
3. **Coordinated offboarding** — directory disablement stops new provider logins, while SCIM/session revocation/current-state checks terminate app access; without SSO+provisioning, ex-employees keep orphan accounts.
4. **Enterprise sales requirement** — Many B2B buyers require enterprise federation without "SAML SSO" on the feature list.
5. **Auditability** — every authentication event funnels through one provider with centralized logs, while each app still needs its own access/audit evidence under its applicable requirements.
6. **Reduced phishing surface** — users type credentials only into the IdP, which can enforce phishing-resistant MFA (stage 7).

## How It Works

### What SSO Actually Means

```text
                 ┌──────────────────────────────┐
                 │        Identity Provider     │
                 │  (Okta / Entra ID / Keycloak)│
                 │   ONE session for the user   │
                 └───────┬───────────┬──────────┘
              assertion  │                        │  assertion
            ┌────────────┘           └────────────┐
            ▼                                     ▼
   ┌───────────────────────────────────────────────────────┐                   ┌─────────────────┐
   │   SP: Jira      │                   │   SP: Salesforce│
   │ local session   │                   │ local session   │
   └───────────────────────────────────────────────────────┘                   └─────────────────┘

Login once at the IdP -> every SP trusts the IdP's signed word.
Each SP still keeps its OWN authorization data (roles, entitlements).
```

SSO is about **authentication delegation**. Authorization stays local to each SP: the IdP proves who you are; Jira still decides what you may see inside Jira.

### SAML Building Blocks

| Concept | What it is |
| ------------ | --------------------------------------------------------------------------------------------------- |
| Assertion | Signed XML document: subject, authn statement (time/method), attributes (email, groups), conditions |
| Conditions | `NotBefore` / `NotOnOrAfter` validity window + `AudienceRestriction` (which SP may consume it) |
| Signing cert | IdP X.509 certificate; assertions are signed with the private key, SP verifies with the public cert |
| Metadata | XML both sides exchange up front: entityID, ACS URL, SSO URL, NameID format, signing certs |
| ACS URL | Assertion Consumer Service — the SP endpoint that receives `SAMLResponse` |
| RelayState | Opaque round-trip token carrying "where the user was headed" |
| NameID | The identifier the IdP asserts (usually email or a stable opaque id) |

Metadata is exchanged during setup and maintained through endpoint/certificate changes ("upload your metadata XML"), eliminating ad-hoc parameter sharing and pinning the trust anchors.

### SP-Initiated Flow (the default)

```text
┌───────────────────────────────────────────────────────┐         ┌──────────┐                ┌──────────┐
│ User │         │    SP    │                │   IdP    │
│(brow)│         │ (your API│                │          │
└──┬────────────────────────────────────────────────────┘         │  /app)   │                └────┬─────┘
   │                    │                     │
   │ 1. GET /dashboard (unauthenticated)      │
   │───────────────────>│                     │
   │                    │                     │
   │ 2. 302 Redirect to IdP SSO URL           │
   │    ?SAMLRequest=<deflate+base64 AuthnRequest>│
   │<───────────────────│                     │
   │                    │                     │
   │ 3. GET SSO URL (browser follows)         │
   │─────────────────────────────────────────>│
   │                    │                     │
   │ 4. Login + MFA at IdP (skipped if   │
   │    IdP session already exists)           │
   │<─────────────────────────────────────────│
   │                    │                     │
   │ 5. 200 HTML form auto-POSTing SAMLResponse │
   │    (signed assertion) + RelayState to ACS│
   │<─────────────────────────────────────────│
   │                    │
   │ 6. POST https://sp.example.com/acs       │
   │    SAMLResponse=...&RelayState=...       │
   │───────────────────>│
   │                    │ 7. Validate: signature vs IdP cert,
   │                    │    InResponseTo matches our request ID,
   │                    │    NotBefore/NotOnOrAfter, audience = us,
   │                    │    replay cache on assertion ID
   │                    │ 8. Provision/JIT user, create SP session
   │ 9. 302 -> /dashboard (logged in)
   │<───────────────────│
```

### IdP-Initiated Flow ("unsolicited response")

```text
┌─────────────────────────────────────────────────────────────────────┐                        ┌──────────┐               ┌──────────┐
│ User │                        │   IdP    │               │    SP    │
└──┬──────────────────────────────────────────────────────────────────┘                        └────┬─────┘               └────┬─────┘
   │                                 │                          │
   │ 1. User clicks app tile         │                          │
   │    on IdP portal/dashboard      │                          │
   │────────────────────────────────>│                          │
   │                                 │ 2. Build SIGNED assertion│
   │                                 │    WITHOUT a prior       │
   │                                 │    AuthnRequest          │
   │ 3. Auto-POST SAMLResponse ----->│─────────────────────────>│
   │                                 │    directly to ACS       │
   │                                 │                          │ 4. Validate
   │                                 │                          │    (no
   │                                 │                          │  InResponseTo!)
   │ 5. Session established          │                          │
```

Because step 2 has no request to tie to (`InResponseTo` absent), IdP-initiated flow is vulnerable to **login CSRF** — an attacker can harvest an assertion for their own account and plant it in a victim's browser, logging the victim in as the attacker. Mature IdPs/SPs prefer SP-initiated or assess the missing request/browser binding explicitly. An unsolicited RelayState string alone cannot recreate a browser-bound request that never existed.

### Assertion Validation Checklist (what your SP must verify)

```text
[x] Signature valid against the KNOWN IdP certificate (pinned via metadata,
    not from the message itself)
[x] InResponseTo == an AuthnRequest ID we issued recently (anti-replay)
[x] Destination == our ACS URL exactly
[x] Issuer/entityID == the expected IdP
[x] Conditions: now within NotBefore..NotOnOrAfter (allow ~60s clock skew)
[x] AudienceRestriction contains OUR entityID
[x] SubjectConfirmationData: valid recipient, expiry and applicable request binding
[x] Consume the exact signed assertion selected by the validator (no wrapping ambiguity)
[x] Assertion ID not seen before (atomic replay cache through expiry + allowed skew)
```

### SAML vs OIDC Comparison

| Dimension | SAML 2.0 | OpenID Connect |
| ----------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Format | XML assertions | JSON / JWT |
| Era | 2005, SOAP/web-services lineage | 2014, REST/mobile-native |
| Transport | Browser redirects + auto-submitting POST forms | Standard HTTP redirects + token endpoint |
| Signature | XML-DSig over whole assertion (XML canonicalization pain) | JOSE/JWS over compact JWT |
| Parsing libraries | Heavy, config-driven, error-prone | Lightweight, JSON-native |
| Client types | Browser web apps | Web, SPA, mobile, native |
| Natural home | Enterprise workforce SSO (IT-managed devices/directories) | Consumer social login + modern B2C/B2B |
| Where you meet it | Okta/Entra/Ping selling you SSO; enterprise customers demanding it | Google OIDC or modern enterprise IdPs; ordinary GitHub OAuth is not OIDC |
| Interoperability quirks | Metadata drift, clock skew, cert rollover ceremonies | JWKS rotation, alg confusion (stage 4/5 topics) |

Choose from the customer identity system, required clients and supported security profile. Workforce IdPs can use SAML or OIDC; browser-heavy legacy integrations often require SAML. Avoid treating protocol age as a security decision.

## Code Examples

### Configure a maintained SAML validator

This complete configuration factory targets `@node-saml/node-saml` 5.1.0. It pins tenant-specific trust and rejects unsolicited responses. The injected `CacheProvider` must be shared, expiry-aware and isolated by tenant/request; the default in-memory cache cannot correlate requests across application instances. This is validator configuration, not a complete ACS/session implementation.

```typescript
import { SAML, ValidateInResponseTo, type CacheProvider } from '@node-saml/node-saml';

export function createSamlValidator(idpCert: string, cacheProvider: CacheProvider) {
  if (!idpCert.trim()) throw new Error('provision the trusted IdP signing certificate');
  return new SAML({
    issuer: 'https://app.example.com/metadata',
    audience: 'https://app.example.com/metadata',
    callbackUrl: 'https://app.example.com/auth/saml/acs',
    entryPoint: 'https://idp.customer.example/sso',
    idpIssuer: 'https://idp.customer.example/metadata',
    idpCert,
    wantAssertionsSigned: true,
    wantAuthnResponseSigned: true, // configure the IdP to sign both
    validateInResponseTo: ValidateInResponseTo.always,
    requestIdExpirationPeriodMs: 300_000,
    maxAssertionAgeMs: 300_000,
    acceptedClockSkewMs: 60_000,
    cacheProvider,
    signatureAlgorithm: 'sha256',
    digestAlgorithm: 'sha256',
  });
}
```

An ACS integration receives bounded form input, calls the configured validator, checks the protocol/profile requirements actually enforced by the pinned library, then creates a local session from the validated assertion. Never extract identity with a second unrelated XML query: XML signature wrapping exploits disagreement about which element was signed and consumed. Disable external-entity expansion and reject unexpected/ambiguous response structure through a maintained validator.

Map identities using trusted tenant + IdP issuer + a contracted stable subject identifier, not email alone. Just-in-time (**JIT**) provisioning creates a local account after successful authentication; it does not prove that the account remains active tomorrow. Require allowed membership/account state, map only approved group attributes to local privileges, regenerate the session ID, and retain the required authentication assurance/time for step-up policy. The redirect after ACS success does not automatically create a session cookie.

### Reading an Assertion (what arrives at the ACS)

This abbreviated XML illustrates the named fields; omitted namespaces, status, subject confirmation and signature values mean it is not a valid test assertion.

```xml
<samlp:Response xmlns:samlp="..." Destination="https://app.example.com/auth/saml/acs"
                InResponseTo="_4f2a9c..." ID="_8e7d31...">
  <saml:Assertion xmlns:saml="..." ID="_a1ssert10n">
    <saml:Issuer>https://idp.customer.com/sso</saml:Issuer>
    <ds:Signature><!-- XML-DSig over the assertion --></ds:Signature>
    <saml:Subject>
      <saml:NameID>maya@customer.com</saml:NameID>
    </saml:Subject>
    <saml:Conditions NotBefore="2026-08-25T10:00:00Z"
                     NotOnOrAfter="2026-08-25T10:05:00Z">
      <saml:AudienceRestriction>
        <saml:Audience>https://app.example.com</saml:Audience>
      </saml:AudienceRestriction>
    </saml:Conditions>
    <saml:AuthnStatement AuthnInstant="2026-08-25T09:59:58Z">
      <saml:AuthnContext>
        <saml:AuthnContextClassRef>
          urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport
        </saml:AuthnContextClassRef>
      </saml:AuthnContext>
    </saml:AuthnStatement>
    <saml:AttributeStatement>
      <saml:Attribute Name="groups">
        <saml:AttributeValue>engineering</saml:AttributeValue>
      </saml:Attribute>
    </saml:AttributeStatement>
  </saml:Assertion>
</samlp:Response>
```

## Real-World Decisions

### Offboarding crosses more than one session

```text
Directory disable -> IdP refuses new login
SCIM deactivation -> local account disabled -> app rejects current requests
Local/session revocation -> existing SP session rejected within its propagation bound
```

**SCIM** (System for Cross-domain Identity Management) provides account/group provisioning operations; it is not a login protocol. Authenticate its endpoints, enforce tenant ownership, make repeated updates safe, and monitor delivery/retry failures. If provisioning is delayed, a local session can remain usable even though the IdP user is disabled. Define the allowed delay and a fallback current-state check. Single logout, session revocation and deprovisioning are different mechanisms; browser logout at the IdP is not proof that every app session ended.

## Real-World Use Cases

### 1. Enterprise workforce SSO

- 500-person company buys your SaaS; IT mandates Okta as the single door
- Your product becomes one SP among dozens behind their IdP

### 2. B2B SaaS multi-tenancy

- Each customer tenant brings its own IdP: tenant -> IdP metadata mapping at login
- Email-domain discovery routes `@customer.com` to their SSO URL

### 3. Internal tool consolidation

- Company replaces 15 per-app password stores with Entra ID + SAML/OIDC federation
- Offboarding becomes a single directory deactivation (with SCIM below)

### 4. Regulated industries (healthcare/fintech)

- Centralized authentication logs and enforced assurance contribute to security evidence; they do not alone establish regulatory compliance
- Conditional access (managed device required) enforced before a new login; existing local sessions need separate enforcement

### 5. Partner/agency access

- Contractors authenticate through their own employer's IdP (cross-domain federation)
- No account sprawl inside your directory

## Common Mistakes

1. **Accepting the certificate embedded in the SAML response**: Trust anchors come from pinned metadata. Verifying with an attacker-supplied cert equals no verification.

2. **Skipping `InResponseTo` checking**: Replayed responses become fresh sessions. Track issued request IDs and reject unsolicited assertions unless IdP-initiated flow is explicitly enabled.

3. **Ignoring `NotBefore`/`NotOnOrAfter` and audience**: Assertions live ~5 minutes for a reason; accepting expired or foreign-audience assertions breaks the trust model.

4. **Treating SSO as authorization**: The IdP says who the user is; roles/entitlements still need local management (or SCIM group sync). Confusing them causes privilege leaks when people change teams.

5. **JIT without de-provisioning**: Creating accounts on first login but never disabling them means departed employees retain access until someone notices. Pair JIT with SCIM deactivation.

6. **Enabling IdP-initiated flow casually**: It disables your strongest anti-CSRF control (`InResponseTo`). Keep it off unless a workflow genuinely requires portal-launched logins.

## Best Practices

1. **Exchange metadata files, don't hand-copy URLs/certs** — entityID, ACS, and signing certs all travel together.

2. **Pin and rotate IdP certificates deliberately**: support two simultaneous IdP certs for zero-downtime rollover.

3. **Prefer SP-initiated flow**; if IdP-initiated is required, bind and validate RelayState strictly.

4. **Allow small clock skew (~60s), nothing more**, and sync clocks everywhere.

5. **Atomically reject repeated assertion IDs** through expiry plus allowed skew; specify cache outage and multi-instance behavior.

6. **Map approved IdP groups to local policy**, then define how later group removals revoke cached/local grants.

7. **Add SCIM (RFC 7643/7644)** for lifecycle: create/update/deactivate driven by HR events rather than first-login heuristics.

8. **Log non-secret correlation IDs with a privacy policy**; NameIDs may contain personal data (never raw assertions full of PII) for incident forensics.

9. **Offer SAML + OIDC both** if you sell B2B: SAML for procurement checkboxes, OIDC for everything modern.

## Performance Considerations

| Aspect | Consideration |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| Login latency | Each SP runs its own assertion exchange; an existing IdP session can skip another credential prompt |
| XML overhead | Bound XML/form sizes and concurrency; measure validator/parser cost |
| Cert validation | Cache parsed IdP metadata; avoid disk reads per request |
| Session strategy | Choose local session lifetime and revocation independently of short assertion validity |
| Multi-tenant lookup | Index tenant routing table by email domain for instant IdP resolution |

## Summary

Federation lets one IdP session unlock many SPs under cryptographic trust. Key takeaways:

- SSO = authenticate once at the IdP; SPs create their own local sessions from signed proof
- SAML moves signed XML assertions through browser redirects/forms; validation = signature + `InResponseTo` + conditions + audience + replay cache
- SP-initiated is the safe default; IdP-initiated lacks request/browser correlation; valid replay caches still matter, but login CSRF needs an explicit policy
- SAML vs OIDC: XML/SOAP-era/workforce vs JSON/REST-era/consumer — most enterprises need you to speak SAML anyway
- Authentication is delegated; authorization stays local (map groups, don't assume)
- SSO without provisioning is half a solution: add SCIM so joiners/movers/leavers propagate

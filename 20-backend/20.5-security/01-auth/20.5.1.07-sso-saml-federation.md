# SSO, SAML & Federation

> Stage 6 of the [Auth Learning Track](INDEX.md) — prev: [OAuth2 / OIDC](20.5.1.06-oauth2-oidc.md) · next: [MFA & Passkeys](20.5.1.08-mfa-passkeys-webauthn.md)


## Definition

Single Sign-On (SSO) lets a user authenticate through a central **Identity Provider (IdP)** and access multiple **Service Providers (SPs)** without separately entering credentials each time, while the IdP session and policy permit. Federation is the trust framework that lets an IdP make an identity claim that each SP validates under an agreed contract.

> **Textbook Definition:** Identity federation establishes trust between an identity provider and relying services. Single sign-on reuses an IdP authentication for access to multiple services. SAML Web Browser SSO conveys an assertion in a response; the service provider validates its signature, issuer, recipient, audience and time conditions, and in SP-initiated flow, request correlation.

SAML 2.0 (Security Assertion Markup Language, an OASIS standard published in 2005) is widely used for enterprise workforce federation. In the Web Browser SSO profile, an IdP sends a response containing an XML **assertion** about a subject and authentication event. The response or assertion must be signed according to the agreed profile; the SP validates the signature using a trusted IdP key, checks the response conditions and creates its own local session.

## First Principles

SSO exists because identity is a perimeter problem:

1. **Every app holding its own user store multiplies risk and friction.** One IdP centralizes the credential attack surface, MFA, and offboarding (centralize the source of lifecycle changes, then propagate them to each app) — SSO is the org-scale application of "one fact, one place" (→ 20.4.1.02).
2. **Federation needs an authenticated trust contract.** SAML and OIDC differ in message format, transport and validation. Metadata describes entity IDs, endpoints and keys, but receiving a metadata file does not by itself make its contents trustworthy. Establish its provenance through an authenticated channel or validate its signature under an already trusted key; manage key rollover as a security change.
3. **The single point of failure is chosen, not eliminated.** IdP down = nobody logs in (hopefully — existing local sessions survive for their configured lifetime or until revoked). That concentration is the trade SSO makes deliberately.

## Why Do We Need It?

1. **One login, many apps** — employees touch dozens of internal tools; per-app passwords increase reuse and recovery burden.
2. **Centralized policy** — MFA enforcement, conditional access, and device checks are applied once at the IdP (Okta, Microsoft Entra ID, Ping) instead of N times.
3. **Coordinated offboarding** — directory disablement stops new provider logins, while SCIM/session revocation/current-state checks terminate app access; without SSO+provisioning, ex-employees keep orphan accounts.
4. **Customer integration requirement** — enterprise customers may require a specific IdP, protocol, admin workflow or provisioning path. Confirm these requirements before choosing SAML, OIDC or both.
5. **Auditability** — every authentication event funnels through one provider with centralized logs, while each app still needs its own access/audit evidence under its applicable requirements.
6. **Central login policy** — an IdP can offer phishing-resistant MFA, but the SP must validate the asserted authentication context and freshness against its own policy. A redirect through the IdP alone does not establish the assurance level of an SP session.

## How It Works

### What SSO Actually Means

SSO means each service can reuse an IdP authentication when the IdP session and policy allow it. It does not create one shared session cookie for every application. Each service provider (SP) validates the federation response, maps the identity to its own account and permissions, and creates its own local session. A person can therefore be logged out of one SP while remaining logged in to the IdP and other SPs.

### SAML Building Blocks

| Concept | What it is |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assertion | XML claims about a subject, authentication event and attributes; the response or assertion must be signed as required by the selected profile |
| Conditions | `NotBefore` / `NotOnOrAfter` validity window + `AudienceRestriction` (which SP may consume it) |
| Signing key | IdP signing certificate or public key trusted by the SP; validate the response or assertion signature required by the profile |
| Metadata | XML describing entity IDs, endpoints, bindings and signing keys; validate who supplied it before trusting those values |
| ACS URL | Assertion Consumer Service — the SP endpoint that receives `SAMLResponse` |
| RelayState | Binding parameter returned with the response; use a random, request-bound value or an allowlisted local destination, never an unchecked redirect URL |
| NameID | The identifier the IdP asserts (usually email or a stable opaque id) |

Metadata is exchanged during setup and refreshed for endpoint or certificate changes. Authenticate the initial metadata source or verify its signature using an already trusted key; then pin the expected entity ID, ACS/SSO endpoints and signing keys. Treat changes and overlapping certificate rollover as controlled trust updates.

### SP-Initiated Flow (the default)

1. The browser requests a protected SP page. With no valid local session, the SP creates a unique `AuthnRequest` ID and stores short-lived correlation state bound to the initiating browser and tenant.
2. The SP redirects the browser to the IdP. With the HTTP Redirect binding, the request is commonly DEFLATE-compressed, Base64-encoded and URL-encoded.
3. The IdP authenticates the user or reuses its IdP session, applying its own policy and any required MFA.
4. The IdP returns a `SAMLResponse` to the SP's Assertion Consumer Service (ACS), commonly in an auto-submitted cross-site form POST. `RelayState` returns the SP's validated local state.
5. The SP's maintained validator checks the trusted signature, issuer, destination, audience, time conditions, subject confirmation, `InResponseTo` and replay state before consuming the signed identity.
6. The SP maps the verified subject to a local account, applies local authorization, rotates or creates the local session, and redirects to the validated destination.

If request correlation depends on a browser cookie, test the cross-site POST against the cookie's `SameSite` policy: a `Lax` or `Strict` cookie may not accompany the ACS POST. Prefer server-side request correlation where possible; if a cross-site cookie is required, choose and test its scope and `SameSite=None; Secure` behavior deliberately. Bind `RelayState` to the request and validate any return path to prevent open redirects.

### IdP-Initiated Flow ("unsolicited response")

1. A user clicks an application tile in the IdP portal.
2. The IdP posts a response to the SP's ACS without a preceding SP `AuthnRequest`.
3. The SP can validate the issuer, signature, destination, audience, time window, subject confirmation and assertion replay ID, but there is no SP request ID to bind through `InResponseTo`.
4. The SP creates a local session only under an explicit policy for unsolicited login.

Without the SP-created request, the browser has no prior request state to correlate. An attacker may plant a valid assertion for the attacker's own account in a victim's browser, producing login CSRF or session swapping. `RelayState` by itself does not supply the missing browser-bound request. Prefer SP-initiated flow; if IdP-initiated login is required, assess this residual risk and add an explicit user-confirmation or transaction-binding control appropriate to the product.

### Assertion Validation Checklist (what your SP must verify)

Before creating a local session, require the maintained validator to check:

- The response or assertion signature against the IdP key provisioned through authenticated metadata. Never trust a key supplied only by the response.
- The expected IdP issuer, exact ACS destination, allowed response binding and audience.
- `NotBefore`, `NotOnOrAfter`, subject confirmation recipient and expiry, using only a small configured clock tolerance.
- For SP-initiated flow, `InResponseTo` against a live request ID created for this tenant and browser flow.
- An atomic, expiring replay check for the assertion ID, scoped to the IdP/tenant.
- The exact signed assertion selected by the validator. Do not parse a second XML element independently; this disagreement can enable signature-wrapping attacks.

Bound XML and form sizes, reject ambiguous or unexpected response structures, and define the behavior when the request/replay cache is unavailable.

### SAML vs OIDC Comparison

| Decision | SAML 2.0 Web Browser SSO | OpenID Connect |
| ---------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Identity message | XML assertion in a SAML response | ID token (JWT) plus OIDC protocol fields |
| Common browser flow | Redirect to IdP, then browser POST to ACS | OAuth 2.0 authorization-code flow with OIDC validation |
| Main validation work | XML signature coverage, metadata trust, assertion conditions, destination and request correlation | Token issuer/audience/signature/nonce, key rotation and OAuth transaction checks |
| Typical integration pressure | Common in workforce SSO and existing enterprise IdPs | Common in web, mobile and modern enterprise integrations |
| Lifecycle | Not provided by the SSO assertion; commonly paired with SCIM | Also separate from login; provisioning and session revocation need their own policy |

Choose from the customer's IdP, supported clients, existing deployment and security profile. Workforce IdPs can support either protocol. Protocol age alone is not a security decision; a maintained implementation and correct validation matter more than XML versus JSON.

## Code Examples

### Configure a maintained SAML validator

This configuration factory targets `@node-saml/node-saml` 5.1.0, the patched release used for this example. It pins tenant-specific trust and rejects unsolicited responses. Keep one request-ID cache per IdP; across application instances, use shared storage with a separate namespace for each IdP and expiry matching `requestIdExpirationPeriodMs`. This version’s `CacheProvider` has separate read and remove operations, so simultaneous copies of one response can race even though later replays fail. Serialize ACS validation per request ID across all instances, or use a version whose cache contract supports atomic consumption. Maintain a separate atomic replay check for assertion IDs. The default in-memory provider only works when the same provider instance handles request creation and response validation. This is validator configuration, not a complete ACS/session implementation.

```typescript
import { SAML, ValidateInResponseTo, type CacheProvider } from '@node-saml/node-saml';

export function createSamlValidator(idpCert: string, cacheProvider: CacheProvider) {
  if (!idpCert.trim()) throw new Error('provision the trusted IdP signing certificate');
  return new SAML({
    issuer: 'https://app.example.com/metadata',
    audience: 'https://app.example.com/metadata',
    callbackUrl: 'https://app.example.com/auth/saml/acs',
    entryPoint: 'https://idp.customer.example/sso',
    idpIssuer: 'https://idp.customer.example/metadata',
    idpCert,
    wantAssertionsSigned: true,
    wantAuthnResponseSigned: true, // configure the IdP to sign both
    validateInResponseTo: ValidateInResponseTo.always,
    requestIdExpirationPeriodMs: 300_000,
    maxAssertionAgeMs: 300_000,
    acceptedClockSkewMs: 60_000,
    cacheProvider,
    signatureAlgorithm: 'sha256',
    digestAlgorithm: 'sha256',
  });
}
```

An ACS integration receives bounded form input, calls the configured validator, checks the protocol/profile requirements actually enforced by the pinned library, then creates a local session from the validated assertion. For this pinned 5.1.0 release, serialize response validation by request ID across the deployment: `validateInResponseTo` performs a cache read and removal as separate operations, so it does not by itself reject two copies racing concurrently. `InResponseTo` also does not bind the response to the initiating browser by itself; validate a separately stored, browser-bound RelayState transaction before session creation. Consume assertion IDs through an expiring atomic replay store as well. Never extract identity with a second unrelated XML query: XML signature wrapping exploits disagreement about which element was signed and consumed. Disable external-entity expansion and reject unexpected/ambiguous response structure through a maintained validator.

Map identities using trusted tenant + IdP issuer + a contracted stable subject identifier, not email alone. Just-in-time (**JIT**) provisioning creates a local account after successful authentication; it does not prove that the account remains active tomorrow. Require allowed membership/account state, map only approved group attributes to local privileges, regenerate the session ID, and retain the required authentication assurance/time for step-up policy. The redirect after ACS success does not automatically create a session cookie.

### Reading an Assertion (what arrives at the ACS)

This abbreviated XML illustrates the named fields; omitted namespaces, status, subject confirmation and signature values mean it is not a valid test assertion.

```xml
<samlp:Response xmlns:samlp="..." Destination="https://app.example.com/auth/saml/acs"
                InResponseTo="_4f2a9c..." ID="_8e7d31...">
  <saml:Assertion xmlns:saml="..." ID="_a1ssert10n">
    <saml:Issuer>https://idp.customer.com/sso</saml:Issuer>
    <ds:Signature><!-- XML-DSig over the assertion --></ds:Signature>
    <saml:Subject>
      <saml:NameID>maya@customer.com</saml:NameID>
    </saml:Subject>
    <saml:Conditions NotBefore="2026-08-25T10:00:00Z"
                     NotOnOrAfter="2026-08-25T10:05:00Z">
      <saml:AudienceRestriction>
        <saml:Audience>https://app.example.com</saml:Audience>
      </saml:AudienceRestriction>
    </saml:Conditions>
    <saml:AuthnStatement AuthnInstant="2026-08-25T09:59:58Z">
      <saml:AuthnContext>
        <saml:AuthnContextClassRef>
          urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport
        </saml:AuthnContextClassRef>
      </saml:AuthnContext>
    </saml:AuthnStatement>
    <saml:AttributeStatement>
      <saml:Attribute Name="groups">
        <saml:AttributeValue>engineering</saml:AttributeValue>
      </saml:Attribute>
    </saml:AttributeStatement>
  </saml:Assertion>
</samlp:Response>
```

## Real-World Decisions

### Offboarding crosses more than one session

```text
Directory disable -> IdP refuses new login
SCIM deactivation -> local account disabled -> app rejects current requests
Local/session revocation -> existing SP session rejected within its propagation bound
```

**SCIM** (System for Cross-domain Identity Management) provides account/group provisioning operations; it is not a login protocol. Authenticate its endpoints, enforce tenant ownership, make repeated updates safe, and monitor delivery/retry failures. If provisioning is delayed, a local session can remain usable even though the IdP user is disabled. Define the allowed delay and a fallback current-state check. Single logout, session revocation and deprovisioning are different mechanisms; browser logout at the IdP is not proof that every app session ended.

## Real-World Use Cases

### 1. Enterprise workforce SSO

- 500-person company buys your SaaS; IT mandates Okta as the single door
- Your product becomes one SP among dozens behind their IdP

### 2. B2B SaaS multi-tenancy

- Each customer tenant brings its own IdP: tenant -> IdP metadata mapping at login
- An allowlisted email-domain mapping can route `@customer.com` to its IdP; the domain is a routing hint, not proof of identity or tenant membership

### 3. Internal tool consolidation

- Company replaces 15 per-app password stores with Entra ID + SAML/OIDC federation
- Offboarding becomes a single directory deactivation (with SCIM below)

### 4. Regulated industries (healthcare/fintech)

- Centralized authentication logs and enforced assurance contribute to security evidence; they do not alone establish regulatory compliance
- Conditional access (managed device required) enforced before a new login; existing local sessions need separate enforcement

### 5. Partner/agency access

- Contractors authenticate through their own employer's IdP (cross-domain federation)
- No account sprawl inside your directory

## Common Mistakes

1. **Accepting the certificate embedded in the SAML response**: Trust anchors come from pinned metadata. Verifying with an attacker-supplied cert equals no verification.

2. **Skipping `InResponseTo` checking**: Replayed responses become fresh sessions. Track issued request IDs and reject unsolicited assertions unless IdP-initiated flow is explicitly enabled.

3. **Ignoring `NotBefore`/`NotOnOrAfter` and audience**: Assertions live ~5 minutes for a reason; accepting expired or foreign-audience assertions breaks the trust model.

4. **Treating SSO as authorization**: The IdP says who the user is; roles/entitlements still need local management (or SCIM group sync). Confusing them causes privilege leaks when people change teams.

5. **JIT without de-provisioning**: Creating accounts on first login but never disabling them means departed employees retain access until someone notices. Pair JIT with SCIM deactivation.

6. **Enabling IdP-initiated flow casually**: It disables your strongest anti-CSRF control (`InResponseTo`). Keep it off unless a workflow genuinely requires portal-launched logins.

## Best Practices

1. **Provision metadata through an authenticated channel or verify its signature**; validate entityID, ACS/SSO endpoints, bindings and signing keys before accepting it.

2. **Pin and rotate IdP certificates deliberately**: support an overlap where the library and IdP permit it, but test rollout order, cache refresh and the actual expiry boundary.

3. **Prefer SP-initiated flow**; if IdP-initiated is required, document login-CSRF/session-swapping risk and validate RelayState destinations without treating RelayState as request correlation.

4. **Allow only the skew the IdP requires**, synchronize clocks and test the configured time boundary.

5. **Atomically reject repeated assertion IDs** through expiry plus allowed skew; for Node-SAML 5.1.0, serialize `InResponseTo` validation per request ID because that release reads and removes request IDs separately. Specify cache outage and multi-instance behavior.

6. **Map approved IdP groups to local policy**, then define how later group removals revoke cached/local grants.

7. **Add SCIM (RFC 7643/7644)** for lifecycle: create/update/deactivate driven by HR events rather than first-login heuristics.

8. **Log non-secret correlation IDs with a privacy policy**; NameIDs may contain personal data (never raw assertions full of PII) for incident forensics.

9. **Offer the protocol your customers and IdPs support**; provide SAML and OIDC when both integration paths are part of the product contract.

## Performance Considerations

| Aspect | Consideration |
| ------------------- | --------------------------------------------------------------------------------------------------------------- |
| Login latency | Each SP runs its own assertion exchange; an existing IdP session can skip another credential prompt |
| XML overhead | Bound XML/form sizes and concurrency; measure validator/parser cost |
| Cert validation | Cache parsed IdP metadata; avoid disk reads per request |
| Session strategy | Choose local session lifetime and revocation independently of short assertion validity |
| Multi-tenant lookup | Route only through an allowlisted domain-to-IdP mapping; domain discovery does not establish account membership |

## Summary

Federation lets one IdP session unlock many SPs under cryptographic trust. Key takeaways:

- SSO reuses an IdP authentication while policy permits; each SP validates the response and creates its own local session
- SAML Web Browser SSO commonly returns a signed response/assertion through a browser POST; validate signature coverage, issuer, recipient, audience, time, request correlation and replay
- SP-initiated is the safe default; IdP-initiated lacks request/browser correlation; valid replay caches still matter, but login CSRF needs an explicit policy
- Choose SAML or OIDC from the customer IdP, client flow and security profile; both are used for enterprise federation
- Authentication is delegated; authorization stays local (map groups, don't assume)
- Plan account lifecycle as well as login; use SCIM or another authoritative path for joiner, mover and leaver changes

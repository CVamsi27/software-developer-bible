# MFA, Passkeys & WebAuthn

> Stage 7 of the [Auth Learning Track](INDEX.md) — prev: [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md) · next: [RBAC / ABAC](20.5.1.09-rbac-abac.md)


## Definition

Multi-factor authentication (MFA) requires evidence from **at least two distinct factor categories** before access is granted. A multi-factor cryptographic authenticator can combine possession with an activation factor such as a PIN or biometric, when the authenticator and the required assurance policy recognize that combination:

> **Textbook Definition:** MFA verifies evidence from at least two distinct factor categories. WebAuthn authenticates with a public-key credential scoped to a relying-party identifier (RP ID), while the relying party validates the challenge and client origin. User verification may activate a second factor, but a passkey label alone does not establish MFA or an assurance level.

| Factor | Category | Examples |
| --------------------------------------- | ----------------- | -------------------------------------------------------------------------- |
| Password, PIN | Knowledge (know) | Something memorized |
| Authenticator, security key, smart card | Possession (have) | Something held or controlled |
| Biometric comparison | Inherence (are) | Something intrinsic; commonly checked locally to activate an authenticator |

A password plus TOTP is MFA; a password plus PIN is not because both are knowledge factors. In NIST guidance, a biometric comparison is not an authenticator by itself: it can activate a physical authenticator or accompany another factor. **Passkeys** are discoverable WebAuthn public-key credentials that can replace password entry. The authenticator or credential provider manages the private key; it may be device-bound or syncable. Your server stores the public credential, never the private key. A ceremony is bound to an RP ID and includes a client origin that the server must validate; an RP ID may cover multiple approved origins, so it is not always the exact site origin.

## First Principles

MFA and passkeys follow from one property of credentials:

1. **Combine factors with different failure modes.** A password and a separate authenticator usually force an attacker to overcome more than one control, but factor failures are not statistically independent: malware, device takeover, real-time phishing or a weak recovery path can defeat both.
2. **Bind public-key authentication to the RP and validate the client origin.** OTPs can be relayed in real time. WebAuthn responses cover authenticator data, a server challenge and a hash of client data containing the origin; the browser scopes the credential to an RP ID, which can be a registrable domain suffix of an origin. The RP must still validate the expected origin; allowing untrusted subdomains expands the attack surface. This blocks ordinary lookalike-site relays, while compromised allowed origins, endpoints and recovery remain risks.
3. **Public verification keys cannot be reused as private login credentials.** Passkeys store public keys; a verifier-database leak does not reveal private credentials. An attacker controlling the live server can still alter enrollment, sessions or account state.

## Why Do We Need It?

1. **Password-only access has a concentrated risk** — breached/reused credentials enable automated takeover.
2. **A second factor raises the work for a password-only attacker** — but real-time phishing can capture both a password and OTP, and compromised endpoints can expose multiple factors.
3. **Assurance requirements** — select factors and session policy from the applicable standard/version and system risk; compliance is not established by adding any two prompts.
4. **Phishing resistance requires protocol binding** — manual OTP entry can be relayed; correctly validated WebAuthn origin and RP ID checks prevent an unrelated lookalike site from using the credential.
5. **Passwordless UX** — passkeys remove the need to type a reusable password, but users still need accessible enrollment, device-loss recovery and a protected fallback policy.

## How It Works

### TOTP Mechanics (RFC 6238)

Enrollment generates a random shared secret (base32). Both sides compute a code from time:

```text
secret K (shared during enrollment; store encrypted, encode for provisioning)
T0 = 0; X = 30 seconds
counter   T  = floor( (unix_time - T0) / X )   # 30-second window
digest    D  = HMAC-SHA1(K, T as 8-byte BE)   # RFC 4226 HOTP core
offset       = D[last byte] & 0x0f
code         = ((D[offset..offset+3] & 0x7fffffff) mod 10^6)   # 6 digits
result       -> "482913"

Server accepts only its configured counter window for clock drift,
then atomically records the matched counter per credential to prevent replay.
```

The secret is symmetric (the verifier must retain it, so a database leak can expose seeds). Six-digit codes have about 10^6 possibilities, so enforce attempt limits. A code is not bound to an origin and can be relayed by a phishing site.

### Why SMS OTP Is Weak

```text
Attack: SIM swap
1. Attacker collects target PII (phishing dump, social media)
2. Calls carrier posing as victim: "lost my SIM"
3. Victim number ports to attacker SIM
4. Victim's SMS OTPs now land on the attacker handset
5. Password reset + OTP interception = full account takeover

Also: SS7 signaling interception, voicemail fallback brute force,
number recycling (new owner inherits old OTPs), Android SMS malware.
```

NIST SP 800-63B-4 classifies PSTN delivery, including SMS and voice, as a *restricted authenticator*. Number porting, reassignment and interception weaken the evidence that the same user controls the registered device. Where policy permits PSTN fallback, assess the required risk indicators and provide an alternative authenticator.

### WebAuthn registration creates a public-key credential

1. The authenticated user asks to register a credential. The relying party (RP) creates a fresh random challenge, stores it in short-lived account- and browser-bound state, and returns creation options. These include the RP ID, opaque user handle, supported algorithms, discoverability and user-verification policy.
2. The browser calls `navigator.credentials.create()`. The authenticator creates or retrieves a credential scoped to the RP ID. Its private key stays under authenticator or credential-provider control and may be device-bound or syncable.
3. The browser returns a credential ID, an attestation object and client data. The client data contains the challenge and origin; the attestation object carries authenticator data and attestation fields. With `attestation: "none"`, the RP does not request identifying attestation evidence.
4. The RP consumes the pending attempt once, verifies the challenge, expected origin, RP ID and required user-verification flag, then stores the credential ID and public key with its account binding. It applies an explicit attestation policy if the deployment requires one.

### WebAuthn authentication proves possession of the credential

1. The RP creates a fresh, short-lived challenge and binds it to the browser transaction. It may return an `allowCredentials` list for a known account, or omit it to allow discoverable-credential account selection.
2. The browser calls `navigator.credentials.get()`. After any required user verification, the authenticator signs `authenticatorData || SHA-256(clientDataJSON)` with the credential's private key.
3. The browser sends the credential ID, client data, authenticator data, signature and any user handle to the RP. The server loads the matching stored public key and checks the transaction, signature, expected origin, RP ID hash, user-presence and required user-verification flags, and credential/account binding.
4. The RP applies its authenticator-counter policy and current account/session rules, then creates a new local session. A successful signature alone does not grant access if the account is disabled or the credential is no longer authorized.

### Why passkeys resist lookalike-site phishing

The signature covers authenticator data and a hash of client data. Authenticator data includes the RP ID hash and user-presence/verification flags; client data includes the one-time challenge and calling origin. A lookalike origin such as `examp1e.com` cannot use a credential scoped to `example.com`. The RP must still check the exact expected origin (or a deliberately narrow allowlist) and expected RP ID. Do not allow untrusted subdomains to share the RP ID. Manually entered OTPs lack this verifier binding and can be relayed. WebAuthn does not prevent session theft, endpoint compromise or recovery takeover.

### Authenticators, Passkeys, and Sync

| Term | Meaning |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Roaming authenticator | Separate hardware (YubiKey); moves between devices via USB/NFC |
| Platform authenticator | Built into the device (TPM, Secure Enclave, Android Keystore) |
| Discoverable credential | Authenticator can find the credential without an RP-supplied `allowCredentials` list; enables username-less flows |
| Passkey | User-facing term for a discoverable WebAuthn credential; may be device-bound or syncable |
| Sync | A credential provider copies or synchronizes credential key material across devices through its sync fabric |

Sync improves device availability but introduces a sync-fabric and account-recovery trust boundary. NIST treats syncable keys as exportable, so they cannot satisfy AAL3 non-exportability requirements. Assess the provider’s account security, recovery and device-removal behavior.

### Assurance levels constrain the whole authentication transaction (NIST SP 800-63B-4)

| NIST SP 800-63B-4 level | Core authentication requirement | Illustrative shape |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| AAL1 | Single- or multi-factor authentication is permitted, subject to the profile's controls | A single password |
| AAL2 | Two distinct factors, using one multi-factor authenticator or two authenticators; a phishing-resistant option must be available | Password plus TOTP, or a user-verified cryptographic credential |
| AAL3 | Phishing-resistant public-key authentication with a non-exportable, hardware-protected private key, plus the required second factor or activation factor | Hardware-protected key plus password/biometric, or a compliant multi-factor cryptographic authenticator |

AAL is a property of a complete authentication process and its verifier controls, not a label that a product can claim from using a passkey. NIST SP 800-63B-4 defines phishing resistance as preventing disclosure of authentication secrets or valid outputs to an impostor verifier. Syncable keys are exportable and therefore cannot meet AAL3's non-exportability requirement.

## Code Examples

### Compute one TOTP from the RFC mechanism

This Node helper accepts decoded seed bytes and implements the SHA-1 / 30-second profile. Its 20-byte minimum is an example local key-length policy, not a protocol minimum. It is a mechanics example, not an enrollment or production verifier. Seed generation, Base32/QR encoding and secure seed retrieval belong to the chosen maintained OTP library.

```js
const { createHmac } = require('node:crypto');
function totpAt(key, unixSeconds, digits = 6) {
  if (!Buffer.isBuffer(key) || key.length < 20 ||
      !Number.isSafeInteger(unixSeconds) || unixSeconds < 0 ||
      ![6, 8].includes(digits)) throw new TypeError('invalid TOTP input');
  const counter = Buffer.alloc(8);
  counter.writeBigUInt64BE(BigInt(Math.floor(unixSeconds / 30)));
  const digest = createHmac('sha1', key).update(counter).digest();
  const offset = digest[digest.length - 1] & 15;
  const binary = digest.readUInt32BE(offset) & 0x7fffffff;
  return String(binary % (10 ** digits)).padStart(digits, '0');
}
module.exports = { totpAt };
```

At Unix time 59 with RFC seed bytes `12345678901234567890`, the eight-digit code is `94287082`. Verification evaluates only the configured time counters, then atomically records the matched counter for that credential before granting access. Two concurrent uses of the same accepted counter must not both succeed. Marking the six-digit text globally is incorrect because codes can repeat at different counters. Bound attempts before cryptographic work; wider drift windows increase guessing opportunities.

Enrollment is also a state transition: an already authenticated user requests a pending encrypted seed, proves a valid code, and atomically activates it. Re-enrollment, recovery-code replacement and disabling MFA require step-up authentication and notification. Never place unconfirmed enrollment secrets in the active login path.

### Registration binds a fresh challenge to an authenticated account

This adapter factory targets `@simplewebauthn/server` 14.0.3, the current package release checked on 11 October 2026. `pending.put` stores an expiring, browser/account-bound attempt; `pending.take` atomically consumes only a matching, unexpired attempt. `credentials.insert` enforces credential-ID uniqueness. These persistence adapters and an authenticated `user` are injected contracts, not implemented databases.

```js
const { randomUUID } = require('node:crypto');
const { generateRegistrationOptions, verifyRegistrationResponse } =
  require('@simplewebauthn/server');

function createPasskeyRegistration({ pending, credentials }) {
  return {
    async start(user, browserId) {
      const options = await generateRegistrationOptions({
        rpName: 'Acme', rpID: 'example.com', userName: user.name,
        userID: user.webAuthnUserID, // stable opaque Uint8Array, not email/PII
        attestationType: 'none',
        authenticatorSelection: { residentKey: 'required', userVerification: 'required' },
      });
      const attemptId = randomUUID();
      await pending.put(attemptId, { userId: user.id, browserId,
        challenge: options.challenge, expiresAt: Date.now() + 300_000 });
      return { attemptId, options };
    },
    async finish(user, browserId, attemptId, response) {
      const attempt = await pending.take(attemptId, user.id, browserId);
      if (!attempt) throw new Error('registration attempt missing or expired');
      const result = await verifyRegistrationResponse({ response,
        expectedChallenge: attempt.challenge, expectedOrigin: 'https://example.com',
        expectedRPID: 'example.com', requireUserVerification: true });
      if (!result.verified || !result.registrationInfo) throw new Error('registration rejected');
      const { credential, credentialDeviceType, credentialBackedUp } = result.registrationInfo;
      await credentials.insert({ userId: user.id, credential,
        deviceType: credentialDeviceType, backedUp: credentialBackedUp });
      return { registered: true };
    },
  };
}
module.exports = { createPasskeyRegistration };
```

The response's credential ID is not the challenge-store key: it did not exist when registration began. After a consumed attempt fails, create a new attempt instead of accepting a replay. Protect enrollment endpoints against CSRF and require fresh authentication; binding an attacker's new credential to a victim account is an account takeover.

### Authentication verifies the stored credential and intended user

Generate fresh authentication options, store their challenge under a browser-bound attempt ID, and return only allowed credentials for a username flow—or use discoverable credentials for a username-less flow. On completion, load the credential by its untrusted ID, then verify its stored public key, expected challenge/origin/RP ID, user-presence and required user-verification flags. Enforce the pending account/credential ownership or discoverable `userHandle` mapping; a valid signature from another account cannot satisfy the requested identity.

Persist the library's returned counter under a concurrency policy before issuing the local session. Many synced/platform authenticators legitimately return zero; a non-increasing positive counter is a risk signal, not universal proof of cloning. Do not automatically lock every account based on one ambiguous counter observation. Account state, step-up freshness and recovery policy remain server responsibilities.

### Browser adapters convert the binary fields

Server JSON contains Base64URL values, while native WebAuthn APIs expect binary buffers. `@simplewebauthn/browser` handles these conversions through `startRegistration({ optionsJSON })` and `startAuthentication({ optionsJSON })`. Pass the result to the matching finish endpoint with its attempt ID, credentials policy, CSRF header and JSON content type. Check HTTP status before parsing, and surface cancellation/unsupported-device errors. Passing raw server JSON straight to `navigator.credentials.create` is not a complete browser implementation.

## Real-World Use Cases

### 1. Banking-grade step-up authentication

- Login requires password + TOTP/push; wire transfers trigger an AAL3 hardware-key check
- Risk engine escalates factors based on amount, device freshness, and geography

### 2. Consumer platforms going passwordless

- Passkey enrollment nudged after a successful password login (GitHub/Google pattern)
- Passkey becomes primary; password demoted to legacy fallback and then removed

### 3. Enterprise workforce (pairs with stage 6 SSO)

- IdP enforces phishing-resistant MFA once; each SP must validate the required authentication context/freshness; assurance is not inherited merely by trusting the IdP
- Conditional access adds managed-device requirements on top of strong authn

### 4. Admin and internal-tool hardening

- Operator accounts require hardware keys; break-glass accounts sealed in vaults
- Directly counters AiTM proxy kits that target DevOps and finance staff

### 5. Healthcare/fintech compliance evidence

- Documented factor/session/recovery controls and their evidence support assessment; AAL labels alone do not establish HIPAA/PCI compliance
- Recovery-code issuance and consumption logs become audit artifacts

## Common Mistakes

1. **Treating SMS as a strong default factor**: number porting, reassignment, interception and carrier-account takeover weaken PSTN delivery. Prefer phishing-resistant WebAuthn where practical; TOTP can be a fallback but is still phishable.

2. **Storing TOTP secrets in plaintext**: The seed is password-equivalent. Encrypt at rest with KMS like any credential.

3. **Unlimited OTP attempts**: Six digits fall to online guessing without aggressive throttling — cap attempts, add lockout/backoff.

4. **Treating counters as universal clone proof**: Use the library/authenticator policy; synced credentials may return zero and concurrent ceremonies need coordinated persistence.

5. **Building a stronger front door than back door**: Enforcing passkeys while allowing email-link resets with only name and date of birth makes recovery the attack path.

6. **Trusting client-echoed challenges**: Challenges must be generated server-side, stored with TTL, and consumed once.

## Best Practices

1. **Choose against the threat model**: both device-bound hardware credentials and synced passkeys can resist phishing; key exportability, sync/recovery trust and required assurance decide which fits.

2. **Rate-limit every verification endpoint** per user AND per IP.

3. **Encrypt TOTP seeds at rest**; never log tokens or secrets.

4. **Issue hashed single-use recovery codes at enrollment**; consume each code atomically; replacement invalidates the old set under an explicit policy.

5. **Make account recovery deliberately slower than login** — cooling-off periods, notifications to all devices, human review for high-value accounts.

6. **Validate origin and rpId on every ceremony**, not just registration.

7. **Record backup state and credential device type** as risk signals; do not treat them as proof of device security or as authorization.

8. **Support multiple passkeys per account** and a separately protected recovery path so losing one device does not lock out the account.

9. **Monitor second-factor failure spikes** as one possible attack signal; correlate them with account, device and network context before taking action.

10. **Document assurance targets per endpoint** and verify each authenticator and recovery method against the required NIST profile; an AAL label is not a product-wide shortcut.

## Performance Considerations

| Aspect | Consideration |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| TOTP verification | Measure crypto plus seed-store lookup, rate limiting and atomic replay control |
| WebAuthn verification | Algorithm/parser/store costs depend on credential and runtime; measure end-to-end ceremony latency |
| Challenge store | Redis with short TTL keeps API servers stateless |
| Synced vs bound keys | No runtime cost difference; different recovery/risk model |
| Session length | Set reauthentication and step-up from resource sensitivity, authenticator strength and exposure windows; avoid one lifetime for every session |

## Summary

MFA combines distinct factor categories; its value depends on their failure modes and the security of recovery. Key takeaways:

- Factors: know / have / are — two knowledge factors are not MFA
- TOTP (RFC 6238) is HMAC over 30-second windows of a shared secret; beats SMS (SIM swap) but stays phishable and symmetric
- WebAuthn registration stores a public credential; authentication verifies a signed challenge, RP ID hash, allowed origin and required user-verification policy
- Passkeys can be device-bound or synced; sync and recovery change the key trust boundary
- NIST AAL requirements are profile-specific; AAL3 requires phishing resistance and a non-exportable key, which synced passkeys do not provide
- Account recovery is the weakest link: hashed single-use codes, guarded slow resets, monitoring

# MFA, Passkeys & WebAuthn

> Stage 7 of the [Auth Learning Track](INDEX.md) — prev: [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md) · next: [RBAC / ABAC](20.5.1.09-rbac-abac.md)

If an attacker steals a password, a second factor can stop a direct login. A phishable code can still be relayed from a lookalike site; a passkey changes the proof by binding it to the site. That difference explains why factor choice, verification rules and recovery have to be designed together.

## Definition

Multi-factor authentication (MFA) requires evidence from **at least two distinct factor categories** before access is granted. A multi-factor cryptographic authenticator can combine possession with an activation factor such as a PIN or biometric, when the authenticator and the required assurance policy recognize that combination:

> **Textbook Definition:** MFA verifies evidence from at least two distinct factor categories. WebAuthn authenticates with a public-key credential scoped to a relying-party identifier (RP ID), while the relying party validates the challenge and client origin. User verification may activate a second factor, but a passkey label alone does not establish MFA or an assurance level.

| Factor | Category | Examples |
| --------------------------------------- | ----------------- | -------------------------------------------------------------------------- |
| Password, PIN | Knowledge (know) | Something memorized |
| Authenticator, security key, smart card | Possession (have) | Something held or controlled |
| Biometric comparison | Inherence (are) | Something intrinsic; commonly checked locally to activate an authenticator |

A password plus a time-based one-time password (TOTP) is MFA; a password plus PIN is not because both are knowledge factors. In NIST guidance, a biometric comparison is not an authenticator by itself: it can activate a physical authenticator or accompany another factor.

**Passkeys** are discoverable WebAuthn public-key credentials that can replace password entry. The authenticator or credential provider manages the private key; it may be device-bound or syncable.

Your server stores the public credential, never the private key. A ceremony is bound to an RP ID and includes a client origin that the server must validate; an RP ID may cover multiple approved origins, so it is not always the exact site origin.

## First Principles

MFA and passkeys follow from three properties of credentials:

1. **Combine factors with different failure modes.** A password and a separate authenticator usually force an attacker to overcome more than one control, but factor failures are not statistically independent: malware, device takeover, real-time phishing or a weak recovery path can defeat both.
2. **Bind public-key authentication to the RP and validate the client origin.** OTPs can be relayed in real time. WebAuthn responses cover authenticator data, a server challenge and a hash of client data containing the origin; the browser scopes the credential to an RP ID, which can be a registrable domain suffix of an origin. The RP must still validate the expected origin; allowing untrusted subdomains expands the attack surface. This blocks ordinary lookalike-site relays, while compromised allowed origins, endpoints and recovery remain risks.
3. **Public verification keys cannot be reused as private login credentials.** Passkeys store public keys; a verifier-database leak does not reveal private credentials. An attacker controlling the live server can still alter enrollment, sessions or account state.

## 1. Choose a factor by its failure mode

#### TOTP Mechanics (RFC 6238)

Enrollment generates a random shared secret (commonly Base32-encoded for provisioning). Both sides compute a code from time. This trace uses RFC 6238's SHA-1 test profile; a deployment must agree on its algorithm, time step and code length.

```text
secret K (shared during enrollment; store encrypted, encode for provisioning)
T0 = 0; X = 30 seconds
counter   T  = floor( (unix_time - T0) / X )   # 30-second window
digest    D  = HMAC-SHA1(K, T as 8-byte big-endian (BE))   # RFC 4226 HOTP core
offset       = D[last byte] & 0x0f
code         = ((D[offset..offset+3] & 0x7fffffff) mod 10^6)   # 6 digits
result       -> "482913"

Server accepts only its configured counter window for clock drift,
then atomically records the matched counter per credential to prevent replay.
```

The secret is symmetric: the verifier must retain it, so a database leak can expose seeds. Encrypt seeds at rest with a managed key, restrict decryption, and never log the secret or provisioning URI. Six-digit codes have about 10^6 possibilities, so enforce a per-account attempt limit and use network or device signals to detect broader abuse.
A code is not bound to an origin and can be relayed by a phishing site.

#### Why SMS OTP Is Weak

```text
Attack: SIM swap
1. Attacker collects target personally identifiable information (PII) from phishing dumps or social media
2. Calls carrier posing as victim: "lost my SIM"
3. Victim number ports to attacker SIM
4. Victim's SMS OTPs now land on the attacker handset
5. Password reset + OTP interception = full account takeover

Also: Signaling System No. 7 (SS7) interception, voicemail fallback brute force,
number recycling (new owner inherits old OTPs), Android SMS malware.
```

NIST SP 800-63B-4 classifies public switched telephone network (PSTN) delivery, including SMS and voice, as a *restricted authenticator*. Number porting, reassignment and interception weaken the evidence that the same user controls the registered device. Where policy permits PSTN fallback, assess the required risk indicators and provide an alternative authenticator.

#### WebAuthn registration creates a public-key credential

1. The authenticated user asks to register a credential. The relying party (RP) creates a fresh random challenge, stores it in short-lived account- and browser-bound state, and returns creation options. These include the RP ID, opaque user handle, supported algorithms, discoverability and user-verification policy.
2. The browser calls `navigator.credentials.create()`. The authenticator creates or retrieves a credential scoped to the RP ID. Its private key stays under authenticator or credential-provider control and may be device-bound or syncable.
3. The browser returns a credential ID, an attestation object and client data. The client data contains the challenge and origin; the attestation object carries authenticator data and attestation fields. With `attestation: "none"`, the RP does not request identifying attestation evidence.
4. The RP consumes the pending attempt once, verifies the challenge, expected origin, RP ID and required user-verification flag, then stores the credential ID and public key with its account binding. It applies an explicit attestation policy if the deployment requires one.

#### WebAuthn authentication proves possession of the credential

1. The RP creates a fresh, short-lived challenge and binds it to the browser transaction. It may return an `allowCredentials` list for a known account, or omit it to allow discoverable-credential account selection.
2. The browser calls `navigator.credentials.get()`. After any required user verification, the authenticator signs `authenticatorData || SHA-256(clientDataJSON)` with the credential's private key.
3. The browser sends the credential ID, client data, authenticator data, signature and any user handle to the RP. The server loads the matching stored public key and checks the transaction, signature, expected origin, RP ID hash, user-presence and required user-verification flags, and credential/account binding.
4. The RP applies its authenticator-counter policy and current account/session rules, then creates a new local session. A successful signature alone does not grant access if the account is disabled or the credential is no longer authorized.

#### Why passkeys resist lookalike-site phishing

The signature covers authenticator data and a hash of client data. Authenticator data includes the RP ID hash and user-presence/verification flags; client data includes the one-time challenge and calling origin. A lookalike origin such as `examp1e.com` cannot use a credential scoped to `example.com`.
The RP must still check the exact expected origin (or a deliberately narrow allowlist) and expected RP ID. Do not allow untrusted subdomains to share the RP ID. Manually entered OTPs lack this verifier binding and can be relayed.
WebAuthn does not prevent session theft, endpoint compromise or recovery takeover.

#### Authenticators, Passkeys, and Sync

| Term | Meaning |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Roaming authenticator | Separate hardware (YubiKey); moves between devices via USB/NFC |
| Platform authenticator | Built into the device (Trusted Platform Module (TPM), Secure Enclave, Android Keystore) |
| Discoverable credential | Authenticator can find the credential without an RP-supplied `allowCredentials` list; enables username-less flows |
| Passkey | User-facing term for a discoverable WebAuthn credential; may be device-bound or syncable |
| Sync | A credential provider copies or synchronizes credential key material across devices through its sync fabric |

Sync improves device availability but introduces a sync-fabric and account-recovery trust boundary. NIST treats syncable keys as exportable, so they cannot satisfy Authenticator Assurance Level 3 (AAL3) non-exportability requirements. Assess the provider’s account security, recovery and device-removal behavior.

#### Assurance levels constrain the whole authentication transaction (NIST SP 800-63B-4)

| NIST SP 800-63B-4 level | Core authentication requirement | Illustrative shape |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| AAL1 | Single- or multi-factor authentication is permitted, subject to the profile's controls | A single password |
| AAL2 | Two distinct factors, using one multi-factor authenticator or two authenticators; a phishing-resistant option must be available | Password plus TOTP, or a policy-compliant multi-factor cryptographic authenticator |
| AAL3 | Phishing-resistant public-key authentication with a non-exportable, hardware-protected private key and the required factor combination | Hardware-protected key plus password/biometric, or a compliant multi-factor cryptographic authenticator |

AAL is a property of a complete authentication process and its verifier controls, not a label that a product can claim from using a passkey. NIST SP 800-63B-4 defines phishing resistance as preventing disclosure of authentication secrets or valid outputs to an impostor verifier. Syncable keys are exportable and therefore cannot meet AAL3's non-exportability requirement.

## 2. Implement the verification boundaries

#### Compute one TOTP from the RFC mechanism

This Node helper accepts decoded seed bytes and implements the SHA-1 / 30-second profile. Its 20-byte minimum is an example local key-length policy, not a protocol minimum. It is a mechanics example, not an enrollment or production verifier.
Seed generation, Base32/QR encoding and secure seed retrieval belong to the chosen maintained OTP library.

```js
const { createHmac } = require('node:crypto');
function totpAt(key, unixSeconds, digits = 6) {
  if (!Buffer.isBuffer(key) || key.length < 20 ||
      !Number.isSafeInteger(unixSeconds) || unixSeconds < 0 ||
      ![6, 8].includes(digits)) throw new TypeError('invalid TOTP input');
  const counter = Buffer.alloc(8);
  counter.writeBigUInt64BE(BigInt(Math.floor(unixSeconds / 30)));
  const digest = createHmac('sha1', key).update(counter).digest();
  const offset = digest[digest.length - 1] & 15;
  const binary = digest.readUInt32BE(offset) & 0x7fffffff;
  return String(binary % (10 ** digits)).padStart(digits, '0');
}
module.exports = { totpAt };
```

At Unix time 59 with RFC seed bytes `12345678901234567890`, the eight-digit code is `94287082`. Verification evaluates only the configured time counters, then atomically records the matched counter for that credential before granting access. Two concurrent uses of the same accepted counter must not both succeed.
Marking the six-digit code text as consumed globally is incorrect, because the same code can recur at different counters. Bound attempts before cryptographic work; wider drift windows increase guessing opportunities.

Enrollment is also a state transition: an already authenticated user requests a pending encrypted seed, proves a valid code, and atomically activates it. Re-enrollment, recovery-code replacement and disabling MFA require step-up authentication and notification. Never place unconfirmed enrollment secrets in the active login path.

#### Registration binds a fresh challenge to an authenticated account

This adapter factory targets `@simplewebauthn/server` 14.0.3, the current package release checked on 11 October 2026. `pending.put` stores an expiring, browser/account-bound attempt; `pending.take` atomically consumes only a matching, unexpired attempt. `credentials.insert` enforces credential-ID uniqueness. These persistence adapters and an authenticated `user` are injected contracts, not implemented databases.

```js
const { randomUUID } = require('node:crypto');
const { generateRegistrationOptions, verifyRegistrationResponse } =
  require('@simplewebauthn/server');

function createPasskeyRegistration({ pending, credentials }) {
  return {
    async start(user, browserId) {
      const options = await generateRegistrationOptions({
        rpName: 'Acme', rpID: 'example.com', userName: user.name,
        userID: user.webAuthnUserID, // stable opaque Uint8Array, not email/PII
        attestationType: 'none',
        authenticatorSelection: { residentKey: 'required', userVerification: 'required' },
      });
      const attemptId = randomUUID();
      await pending.put(attemptId, { userId: user.id, browserId,
        challenge: options.challenge, expiresAt: Date.now() + 300_000 });
      return { attemptId, options };
    },
    async finish(user, browserId, attemptId, response) {
      const attempt = await pending.take(attemptId, user.id, browserId);
      if (!attempt) throw new Error('registration attempt missing or expired');
      const result = await verifyRegistrationResponse({ response,
        expectedChallenge: attempt.challenge, expectedOrigin: 'https://example.com',
        expectedRPID: 'example.com', requireUserVerification: true });
      if (!result.verified || !result.registrationInfo) throw new Error('registration rejected');
      const { credential, credentialDeviceType, credentialBackedUp } = result.registrationInfo;
      await credentials.insert({ userId: user.id, credential,
        deviceType: credentialDeviceType, backedUp: credentialBackedUp });
      return { registered: true };
    },
  };
}
module.exports = { createPasskeyRegistration };
```

The response's credential ID is not the challenge-store key: it did not exist when registration began. After a consumed attempt fails, create a new attempt instead of accepting a replay. Protect enrollment endpoints against cross-site request forgery (CSRF) and require fresh authentication; binding an attacker's new credential to a victim account is an account takeover.

#### Authentication verifies the stored credential and intended user

Generate fresh authentication options, store their challenge under a browser-bound attempt ID, and return only allowed credentials for a username flow—or use discoverable credentials for a username-less flow. On completion, load the credential by its untrusted ID, then verify its stored public key, expected challenge/origin/RP ID, user-presence and required user-verification flags. Enforce the pending account/credential ownership or discoverable `userHandle` mapping; a valid signature from another account cannot satisfy the requested identity.

Persist the library's returned counter under a concurrency policy before issuing the local session. Many synced/platform authenticators legitimately return zero; a non-increasing positive counter is a risk signal, not universal proof of cloning. Do not automatically lock every account based on one ambiguous counter observation.
Account state, step-up freshness and recovery policy remain server responsibilities.

#### Browser adapters convert the binary fields

Server JSON contains Base64URL values, while native WebAuthn APIs expect binary buffers. `@simplewebauthn/browser` handles these conversions through `startRegistration({ optionsJSON })` and `startAuthentication({ optionsJSON })`. Pass the result to the matching finish endpoint with its attempt ID, credentials policy, CSRF header and JSON content type. Check HTTP status before parsing, and surface cancellation/unsupported-device errors.
Passing raw server JSON straight to `navigator.credentials.create` is not a complete browser implementation.

## 3. Recovery and session freshness finish the design

Recovery is an authentication path: whoever controls it can replace authenticators and take over the account. Offer more than one passkey where practical. Require fresh authentication to add or remove a credential, notify the account owner, and treat backup state as a risk signal rather than proof that the device is secure.

For saved recovery codes, generate at least 64 bits of randomness, show each code once, store only its approved one-way verifier, throttle attempts, and consume it atomically. After use, invalidate it and issue a replacement; notify the user when codes are issued or replaced. At AAL2, NIST SP 800-63B-4 requires recovery to use two codes from different methods, one recovery code plus a bound single-factor authenticator, or repeated identity proofing when the account was identity-proofed.
Choose the method from the system's actual assurance and identity-proofing profile rather than making an email-only reset a hidden bypass.

Authentication strength also affects session policy. Under NIST SP 800-63B-4, AAL2's overall reauthentication timeout should be no more than 24 hours and inactivity timeout no more than 1 hour. AAL3's overall timeout must be no more than 12 hours and inactivity timeout should be no more than 15 minutes.
These are NIST profile limits, not universal defaults for every application; define stricter freshness for sensitive actions such as changing recovery methods, managing credentials or approving a high-impact transaction. A risk signal can trigger step-up, but it is not another authentication factor.

## Summary

MFA combines distinct factor categories, but its value depends on how each factor can fail and how the account is recovered. TOTP is a shared secret that remains phishable; WebAuthn stores a public key and verifies a fresh challenge against the expected RP ID and origin. Passkey sync changes the key's trust boundary.
Match factor, recovery and session policy to each action's assurance requirement, and treat signed-in state as revocable application state rather than proof of permanent authorization.

# MFA, Passkeys & WebAuthn

> Stage 7 of the [Auth Learning Track](INDEX.md) — prev: [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md) · next: [RBAC / ABAC](20.5.1.09-rbac-abac.md)

> **TL;DR:** Multi-factor authentication combines independent factors — something you know (password), have (device/key), are (biometric). TOTP apps beat SMS (SIM-swap-proof) but still phish; WebAuthn/passkeys bind a challenge to an origin so credential phishing stops working by construction. The system's real strength is its weakest link: account recovery. Seniors can walk both WebAuthn ceremonies, explain assurance levels AAL1-3, and defend why passkeys are phishing-resistant.
>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## First Principles

MFA and passkeys follow from one property of credentials:

1. **Factors are independent because they fail independently.** Knowledge (password) and possession (phone, key) and inherence (biometric) are compromised by different attack classes — which is why combining them defeats credential stuffing wholesale. "Something you know + something you have" is the minimum honest pair.
2. **Phishing is the dominant attack, so bind to origin.** OTPs are phishable (user relays the code); WebAuthn/passkeys sign *the origin* — a credential created for evil.com cannot be exercised on your-bank.com. Origin-binding is the structural fix, not user education.
3. **No shared secret means nothing to steal from the server.** Passkeys store public keys; a server breach yields nothing reusable — eliminating phishing and server-breach reuse in one design.

## Definition

Multi-Factor Authentication (MFA) requires proof from **two or more distinct factor categories** before granting access:

| Factor | Category | Examples |
| ------------------------------- | ----------------- | ------------------- |
| Password, PIN, security answers | Knowledge (know) | Something memorized |
| Phone, hardware key, smart card | Possession (have) | Something held |
| Fingerprint, face, voice | Inherence (are) | Something intrinsic |

A password + TOTP code is MFA; password + PIN is not (two knowledge factors). **Passkeys** are WebAuthn credentials that replace the password entirely: a private key lives inside the user's device/authenticator while your server stores only the public key, and every login is a signed challenge-response bound to your exact origin.

## Why Do We Need It?

1. **Passwords alone are finished** — breach corpora and credential stuffing make knowledge-only authentication statistically broken.
2. **Factor independence defeats theft combos** — a phished password is useless without the second factor; a stolen TOTP seed still needs the password.
3. **Compliance mandates** — PCI DSS, HIPAA, SOC 2, and NIST 800-63B all require MFA for sensitive access.
4. **Phishing resistance requires origin binding** — codes can be relayed by attacker proxies in real time; WebAuthn signatures cannot leave the site they were minted for.
5. **UX upside of passkeys** — biometrics unlock login; no password resets, no reuse, no typing secrets into untrusted keyboards.
6. **Insurance and B2B pressure** — cyber insurers and enterprise buyers increasingly audit second-factor enforcement.

## How It Works

### TOTP Mechanics (RFC 6238)

Enrollment generates a random shared secret (base32). Both sides compute a code from time:

```text
secret K (shared at enrollment, stored base32)

counter   T  = floor( unix_time / 30 )        # 30-second window
digest    D  = HMAC-SHA1(K, T as 8-byte BE)   # RFC 4226 HOTP core
offset       = D[last byte] & 0x0f
code         = ((D[offset..offset+3] & 0x7fffffff) mod 10^6)   # 6 digits
result       -> "482913"

Server accepts current window +/- 1 (clock drift tolerance),
then marks used codes so one code cannot be replayed within its window.
```

Properties worth stating in interviews: the secret is symmetric (server holds it too — a server DB leak exposes seeds), codes occupy a ~10^6 space but rate limiting keeps online guessing impractical, and the code is *not* bound to any origin — a user will happily type it into evil.com.

### Why SMS OTP Is Weak

```text
Attack: SIM swap
1. Attacker collects target PII (phishing dump, social media)
2. Calls carrier posing as victim: "lost my SIM"
3. Victim number ports to attacker SIM
4. Victim's SMS OTPs now land on the attacker handset
5. Password reset + OTP interception = full account takeover

Also: SS7 signaling interception, voicemail fallback brute force,
number recycling (new owner inherits old OTPs), Android SMS malware.
```

NIST SP 800-63B classifies SMS/PSTN out-of-band as *restricted* precisely because the "possession" factor is really possession of the phone **number**, which carriers reassign with weak identity checks.

### WebAuthn Registration Ceremony

```text
┌───────────────────────────────────────────────────────────────────┐              ┌────────────┐             ┌───────────────┐
│ Browser │              │ RP Server  │             │ Authenticator │
└────┬──────────────────────────────────────────────────────────────┘              └─────┬──────┘             └───────┬───────┘
     │                         │                            │
     │ 1. POST /webauthn/register/start                     │
     │────────────────────────>│                            │
     │                         │ create random challenge    │
     │ 2. PublicKeyCredentialCreationOptions                │
     │    { rp.id:"example.com", user.id,                   │
     │      challenge, pubKeyCredParams:[ES256],            │
     │      authenticatorSelection:{residentKey,            │
     │        userVerification}, attestation }              │
     │<────────────────────────│                            │
     │ 3. navigator.credentials.create(options)             │
     │─────────────────────────────────────────────────────>│
     │                         │   user gesture + biometric │
     │                         │   generate keypair scoped  │
     │                         │   to rp.id; private key    │
     │                         │   NEVER leaves device      │
     │ 4. AttestationObject { fmt, authData(rpIdHash,       │
     │    flags, signCount), attStmt }, clientDataJSON      │
     │    {challenge, origin, type}                         │
     │<─────────────────────────────────────────────────────│
     │ 5. POST credentials to RP                            │
     │────────────────────────>│ verify challenge + origin, │
     │                         │ store {credentialId,       │
     │                         │ publicKey, signCount}      │
```

### WebAuthn Authentication Ceremony

```text
1. POST /webauthn/login/start {username}
2. RP loads allowCredentials, returns options:
   { challenge, rpId, allowCredentials, userVerification }
3. navigator.credentials.get(options)
     authenticator finds matching credential (discoverable:
     no username typed), user verifies via biometric/PIN,
     signs: sig = Sign(privateKey, authData || sha256(clientDataJSON))
     authData carries NEW signCount + rpIdHash
4. POST assertion -> RP verifies signature with STORED public key,
   checks origin == https://example.com, challenge matches the one
   issued, rpIdHash correct, signCount > stored (clone detection),
   updates counter, creates session cookie/token
```

### Why Passkeys Are Phishing-Resistant

```text
The assertion signature covers:
  ├── challenge issued by YOUR server  (nothing static to relay)
  ├── rpIdHash -> credential only ever works for example.com
  └── origin   -> browser refuses/warns when page origin differs

Fake site examp1e.com cannot obtain signatures for example.com.
There is no secret for the user to "accidentally type" into a
proxy page — AiTM kits (Evilginx-style) simply stop working.
TOTP/push lack exactly this binding: their codes relay fine.
```

### Authenticators, Passkeys, and Sync

| Term | Meaning |
| ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| Roaming authenticator | Separate hardware (YubiKey); moves between devices via USB/NFC |
| Platform authenticator | Built into the device (TPM, Secure Enclave, Android Keystore) |
| Discoverable credential ("resident key") | Credential + user handle stored ON device; enables username-less flows |
| Passkey | Discoverable, SYNCED WebAuthn credential backed by iCloud Keychain or Google Password Manager |
| Sync | Private keys replicate across the user's devices through their cloud account |

Sync trades some isolation for availability: a passkey is only as protected as the cloud account guarding the sync chain — which is why recovery design matters more than ceremony mechanics.

### Assurance Levels (NIST SP 800-63B)

| Level | Requirements | Example |
| ----- | ---------------------------------------------------------------- | ------------------------------ |
| AAL1 | Single factor, basic proofing | Plain password login |
| AAL2 | Two distinct factors, approved crypto, session binding | Password + TOTP or push |
| AAL3 | Hardware-backed authenticator, verifier impersonation resistance | FIDO2 security key, smart card |

"Verifier impersonation resistance" is NIST's formal name for phishing resistance: the protocol binds responses to the legitimate verifier, so attacker-in-the-middle proxies cannot substitute their own site.

## Code Examples

### TOTP Enrollment + Verification (otplib, NestJS)

```typescript
import { authenticator } from "otplib";
import QRCode from "qrcode";

@Injectable()
export class TotpService {
  constructor(
    private readonly users: UsersService,
    private readonly cryptoBox: KmsCryptoService
  ) {}

  async enroll(userId: string, email: string): Promise<string> {
    const secret = authenticator.generateSecret(); // CSPRNG

    await this.users.setTotpSecret(userId, {
      encryptedSecret: this.cryptoBox.encrypt(secret), // seed = credential
      confirmed: false,
    });

    const otpauthUrl = authenticator.keyuri(email, "Acme Corp", secret);
    return QRCode.toDataURL(otpauthUrl); // render as QR for the app scan
  }

  async confirmAndEnable(userId: string, token: string): Promise<void> {
    const rec = await this.users.getTotpSecret(userId);
    const secret = this.cryptoBox.decrypt(rec.encryptedSecret);

    if (!authenticator.verify({ token, secret, window: 1 })) {
      throw new BadRequestException("Invalid code");
    }
    await this.users.enableTotp(userId);
    // Hand back single-use recovery codes here (see below).
  }

  verifyLoginCode(userId: string, token: string): boolean {
    const secret = this.cryptoBox.decrypt(this.cache.totpSecret(userId));
    return authenticator.verify({ token, secret, window: 1 });
  }
}
```

### Manual TOTP Computation (RFC mechanics, no library)

```typescript
import crypto from "crypto";

const totpAt = (base32Secret: string, unixSeconds: number): string => {
  const key = base32Decode(base32Secret);
  const counter = Math.floor(unixSeconds / 30);

  const buf = Buffer.alloc(8);
  buf.writeUInt32BE(Math.floor(counter / 2 ** 32), 0);
  buf.writeUInt32BE(counter % 2 ** 32, 4);

  const digest = crypto.createHmac("sha1", key).update(buf).digest();
  const offset = digest[digest.length - 1] & 0x0f;

  const binary =
    ((digest[offset] & 0x7f) << 24) |
    (digest[offset + 1] << 16) |
    (digest[offset + 2] << 8) |
    digest[offset + 3];

  return String(binary % 1_000_000).padStart(6, "0");
};
```

### Recovery Codes (hashed, single-use)

```typescript
const issueRecoveryCodes = async (userId: string): Promise<string[]> => {
  const codes = Array.from({ length: 10 }, () =>
    crypto.randomBytes(10).toString("base64url")
  );

  await this.recovery.replaceFor(
    userId,
    codes.map((c) => ({
      hash: crypto.createHash("sha256").update(c).digest("hex"),
      usedAt: null as Date | null,
    }))
  );
  return codes; // displayed exactly once, like API keys
};

const consumeRecoveryCode = async (
  userId: string,
  presented: string
): Promise<boolean> => {
  const presentedHash = crypto
    .createHash("sha256")
    .update(presented)
    .digest("hex");
  // Atomic UPDATE ... SET used_at = now() WHERE hash = ? AND used_at IS NULL
  return this.recovery.consume(userId, presentedHash);
};
```

### WebAuthn Server-Side (@simplewebauthn/server)

```typescript
import {
  generateRegistrationOptions,
  verifyRegistrationResponse,
  generateAuthenticationOptions,
  verifyAuthenticationResponse,
} from "@simplewebauthn/server";

@Injectable()
export class PasskeyService {
  async registrationOptions(userId: string, email: string) {
    return generateRegistrationOptions({
      rpName: "Acme Corp",
      rpID: "example.com",
      userName: email,
      attestationType: "none",
      authenticatorSelection: {
        residentKey: "preferred", // discoverable -> passkey UX
        userVerification: "preferred",
      },
    });
  }

  async finishRegistration(userId: string, response: any): Promise<void> {
    const verification = await verifyRegistrationResponse({
      response,
      expectedChallenge: this.challengeStore.take(response.id),
      expectedOrigin: "https://example.com",
      expectedRPID: "example.com",
    });

    if (!verification.verified || !verification.registrationInfo) {
      throw new UnauthorizedException("Registration failed");
    }

    const { credential, credentialDeviceType, credentialBackedUp } =
      verification.registrationInfo;

    await this.creds.save({
      userId,
      credentialId: credential.id,
      publicKey: credential.publicKey,
      counter: credential.counter,
      deviceType: credentialDeviceType,
      backedUp: credentialBackedUp, // synced passkey vs bound key
    });
  }

  async loginStart(username: string) {
    const creds = await this.creds.findByUsername(username);
    const options = await generateAuthenticationOptions({
      rpID: "example.com",
      userVerification: "preferred",
      allowCredentials: creds.map((c) => ({ id: c.credentialId })),
    });
    await this.challengeStore.store(username, options.challenge);
    return options;
  }

  async loginFinish(username: string, response: any): Promise<string> {
    const cred = await this.creds.getByCredentialId(response.id);

    const verification = await verifyAuthenticationResponse({
      response,
      expectedChallenge: this.challengeStore.take(username),
      expectedOrigin: "https://example.com",
      expectedRPID: "example.com",
      credential: {
        id: cred.credentialId,
        publicKey: cred.publicKey,
        counter: cred.counter,
        transports: cred.transports,
      },
    });

    if (!verification.verified) {
      throw new UnauthorizedException("Assertion rejected");
    }

    const { newCounter } = verification.authenticationInfo;
    if (cred.counter > 0 && newCounter <= cred.counter) {
      // Counter regression => possible cloned authenticator
      await this.creds.lock(cred.userId);
      throw new UnauthorizedException("Authenticator clone suspected");
    }

    await this.creds.updateCounter(cred.id, newCounter);
    return this.sessions.issueFor(cred.userId);
  }
}
```

### Browser Side (webauthn-js style)

```typescript
// Registration
const options = await fetch("/webauthn/register/start").then((r) => r.json());
const credential = await navigator.credentials
  .create({ publicKey: options })
  .then(toJSONable);
await fetch("/webauthn/register/finish", {
  method: "POST",
  body: JSON.stringify(credential),
});

// Login (username-less when credentials are discoverable)
const authOptions = await fetch("/webauthn/login/start").then((r) => r.json());
const assertion = await navigator.credentials
  .get({ publicKey: authOptions })
  .then(toJSONable);
await fetch("/webauthn/login/finish", {
  method: "POST",
  body: JSON.stringify(assertion),
});
```

## Real-World Use Cases

### 1. Banking-grade step-up authentication

- Login requires password + TOTP/push; wire transfers trigger an AAL3 hardware-key check
- Risk engine escalates factors based on amount, device freshness, and geography

### 2. Consumer platforms going passwordless

- Passkey enrollment nudged after a successful password login (GitHub/Google pattern)
- Passkey becomes primary; password demoted to legacy fallback and then removed

### 3. Enterprise workforce (pairs with stage 6 SSO)

- IdP enforces phishing-resistant MFA once; every federated SaaS inherits the assurance
- Conditional access adds managed-device requirements on top of strong authn

### 4. Admin and internal-tool hardening

- Operator accounts require hardware keys; break-glass accounts sealed in vaults
- Directly counters AiTM proxy kits that target DevOps and finance staff

### 5. Healthcare/fintech compliance evidence

- AAL mapping per endpoint satisfies HIPAA/PCI assessors
- Recovery-code issuance and consumption logs become audit artifacts

## Common Mistakes

1. **Treating SMS as strong MFA**: SIM swap turns "possession" into an attacker phone call. Use authenticator apps or WebAuthn.

2. **Storing TOTP secrets in plaintext**: The seed is password-equivalent. Encrypt at rest with KMS like any credential.

3. **Unlimited OTP attempts**: Six digits fall to online guessing without aggressive throttling — cap attempts, add lockout/backoff.

4. **Skipping signCount checks**: Cloned authenticators reveal themselves via counter regressions; ignoring them hides duplication until fraud surfaces.

5. **Building a stronger front door than back door**: Enforcing passkeys while allowing email-link resets with only name+DOB makes recovery the attack path.

6. **Trusting client-echoed challenges**: Challenges must be generated server-side, stored with TTL, and consumed once.

## Best Practices

1. **Rank factors by resistance**: passkeys > hardware keys > push/TOTP > email > SMS > none — deploy the strongest users tolerate.

2. **Rate-limit every verification endpoint** per user AND per IP.

3. **Encrypt TOTP seeds at rest**; never log tokens or secrets.

4. **Issue hashed single-use recovery codes at enrollment**; regenerate after each use.

5. **Make account recovery deliberately slower than login** — cooling-off periods, notifications to all devices, human review for high-value accounts.

6. **Validate origin and rpId on every ceremony**, not just registration.

7. **Record `backedUp` and device type** to risk-score sessions (synced passkey vs bound hardware).

8. **Support multiple passkeys per account** plus cross-device activation so losing one device is not losing the account.

9. **Monitor second-factor failure storms** — they are the earliest takeover signal.

10. **Document AAL targets per endpoint** so auditors do not guess your posture.

## Performance Considerations

| Aspect | Consideration |
| --------------------- | ---------------------------------------------------------------------------- |
| TOTP verification | HMAC-SHA1 microseconds — negligible inline |
| WebAuthn verification | One ECDSA P-256 verify (~sub-millisecond) |
| Challenge store | Redis with short TTL keeps API servers stateless |
| Synced vs bound keys | No runtime cost difference; different recovery/risk model |
| Session length | Long post-MFA sessions avoid ceremony fatigue; step up only on risky actions |

## Summary

MFA layers independent factors; the engineering craft is picking factors that resist modern attacks and closing the recovery gap. Key takeaways:

- Factors: know / have / are — two knowledge factors are not MFA
- TOTP (RFC 6238) is HMAC over 30-second windows of a shared secret; beats SMS (SIM swap) but stays phishable and symmetric
- WebAuthn ceremonies: registration stores a public key; authentication verifies signed challenges bound to origin + rpId
- Passkeys are synced discoverable credentials — big UX win, dependent on the cloud account guarding sync
- AAL1-3 grade assurance; AAL3 means hardware-backed, verifier-impersonation-resistant
- Account recovery is the weakest link: hashed single-use codes, guarded slow resets, monitoring

## Cheat Sheet
| Concept | Value |
| ----------------------- | -------------------------------------------------------------------------- |
| Factor categories | Know / Have / Are |
| TOTP formula | HMAC-SHA1(secret, floor(unixtime/30)), 6 digits, ±1 window drift |
| SMS verdict | SIM-swap/SS7 vulnerable — migrate to apps or WebAuthn |
| Registration output | credentialId + publicKey + signCount stored server-side |
| Assertion checks | Signature, challenge, origin, rpIdHash, signCount increment |
| Phishing resistance | Challenge + rpId + origin binding leaves nothing to relay |
| Passkey | Discoverable, synced WebAuthn credential (iCloud/Google PM) |
| Discoverable credential | Lives on device incl. user handle -> username-less login |
| AAL levels | 1 = single factor; 2 = two factors; 3 = hardware + impersonation-resistant |
| Weakest link | Account recovery — design it stronger than login |

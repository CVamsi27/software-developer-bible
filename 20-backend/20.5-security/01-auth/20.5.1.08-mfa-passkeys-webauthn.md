# MFA, Passkeys & WebAuthn

> Stage 7 of the [Auth Learning Track](INDEX.md) — prev: [SSO / SAML / Federation](20.5.1.07-sso-saml-federation.md) · next: [RBAC / ABAC](20.5.1.09-rbac-abac.md)

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Multi-Factor Authentication (MFA) requires proof from **two or more distinct factor categories** before granting access:

> **Textbook Definition:** Multi-factor authentication combines evidence from distinct factor categories. WebAuthn uses relying-party-bound public-key credentials and signed challenges; whether a passkey ceremony satisfies multiple factors depends on authenticator and user-verification policy.

| Factor | Category | Examples |
| ------------------------------- | ----------------- | ------------------- |
| Password, PIN, security answers | Knowledge (know) | Something memorized |
| Phone, hardware key, smart card | Possession (have) | Something held |
| Fingerprint, face, voice | Inherence (are) | Something intrinsic |

A password + TOTP code is MFA; password + PIN is not (two knowledge factors). **Passkeys** are WebAuthn credentials that replace the password entirely: a private key lives inside the user's device/authenticator while your server stores only the public key, and every login is a signed challenge-response bound to your exact origin.

## First Principles

MFA and passkeys follow from one property of credentials:

1. **Factors are independent because they fail independently.** Knowledge (password) and possession (phone, key) and inherence (biometric) are compromised by different attack classes — which is why combining them limits password-only takeover; factor capture, session theft and recovery bypass remain possible. "Something you know + something you have" is the minimum honest pair.
2. **Phishing is the dominant attack, so bind to origin.** OTPs are phishable (user relays the code); WebAuthn/passkeys sign *the origin* — a credential created for evil.com cannot be exercised on your-bank.com. Origin-binding is the structural fix, not user education.
3. **Public verification keys cannot be reused as private login credentials.** Passkeys store public keys; a verifier-database leak does not reveal private credentials. An attacker controlling the live server can still alter enrollment, sessions or account state.

## Why Do We Need It?

1. **Password-only access has a concentrated risk** — breached/reused credentials enable automated takeover.
2. **Factor independence defeats theft combos** — a phished password is useless without the second factor; a stolen TOTP seed still needs the password.
3. **Assurance requirements** — select factors and session policy from the applicable standard/version and system risk; compliance is not established by adding any two prompts.
4. **Phishing resistance requires origin binding** — codes can be relayed by attacker proxies in real time; WebAuthn signatures cannot leave the site they were minted for.
5. **UX upside of passkeys** — biometrics unlock login; no password resets, no reuse, no typing secrets into untrusted keyboards.
6. **Insurance and B2B pressure** — cyber insurers and enterprise buyers increasingly audit second-factor enforcement.

## How It Works

### TOTP Mechanics (RFC 6238)

Enrollment generates a random shared secret (base32). Both sides compute a code from time:

```text
secret K (shared at enrollment, stored base32)

counter   T  = floor( unix_time / 30 )        # 30-second window
digest    D  = HMAC-SHA1(K, T as 8-byte BE)   # RFC 4226 HOTP core
offset       = D[last byte] & 0x0f
code         = ((D[offset..offset+3] & 0x7fffffff) mod 10^6)   # 6 digits
result       -> "482913"

Server accepts current window +/- 1 (clock drift tolerance),
then marks used codes so one code cannot be replayed within its window.
```

Properties worth stating in interviews: the secret is symmetric (server holds it too — a server DB leak exposes seeds), codes occupy a ~10^6 space but rate limiting keeps online guessing impractical, and the code is *not* bound to any origin — a user will happily type it into evil.com.

### Why SMS OTP Is Weak

```text
Attack: SIM swap
1. Attacker collects target PII (phishing dump, social media)
2. Calls carrier posing as victim: "lost my SIM"
3. Victim number ports to attacker SIM
4. Victim's SMS OTPs now land on the attacker handset
5. Password reset + OTP interception = full account takeover

Also: SS7 signaling interception, voicemail fallback brute force,
number recycling (new owner inherits old OTPs), Android SMS malware.
```

NIST SP 800-63B classifies SMS/PSTN out-of-band as *restricted* precisely because the "possession" factor is really possession of the phone **number**, which carriers reassign with weak identity checks.

### WebAuthn Registration Ceremony

```text
┌───────────────────────────────────────────────────────────────────┐              ┌────────────┐             ┌───────────────┐
│ Browser │              │ RP Server  │             │ Authenticator │
└────┬──────────────────────────────────────────────────────────────┘              └─────┬──────┘             └───────┬───────┘
     │                         │                            │
     │ 1. POST /webauthn/register/start                     │
     │────────────────────────>│                            │
     │                         │ create random challenge    │
     │ 2. PublicKeyCredentialCreationOptions                │
     │    { rp.id:"example.com", user.id,                   │
     │      challenge, pubKeyCredParams:[ES256],            │
     │      authenticatorSelection:{residentKey,            │
     │        userVerification}, attestation }              │
     │<────────────────────────│                            │
     │ 3. navigator.credentials.create(options)             │
     │─────────────────────────────────────────────────────>│
     │                         │   user gesture + biometric │
     │                         │   generate keypair scoped  │
     │                         │   to rp.id; private key    │
     │                         │   may be device-bound or synced      │
     │ 4. AttestationObject { fmt, authData(rpIdHash,       │
     │    flags, signCount), attStmt }, clientDataJSON      │
     │    {challenge, origin, type}                         │
     │<─────────────────────────────────────────────────────│
     │ 5. POST credentials to RP                            │
     │────────────────────────>│ verify challenge + origin, │
     │                         │ store {credentialId,       │
     │                         │ publicKey, signCount}      │
```

### WebAuthn Authentication Ceremony

```text
1. POST /webauthn/login/start {username}
2. RP loads allowCredentials, returns options:
   { challenge, rpId, allowCredentials, userVerification }
3. navigator.credentials.get(options)
     authenticator finds matching credential (discoverable:
     no username typed), user verifies via biometric/PIN,
     signs: sig = Sign(privateKey, authData || sha256(clientDataJSON))
     authData carries NEW signCount + rpIdHash
4. POST assertion -> RP verifies signature with STORED public key,
   checks origin == https://example.com, challenge matches the one
   issued, rpIdHash correct, required user-verification flags and
   credential/user binding; apply the authenticator counter policy,
   updates counter, creates session cookie/token
```

### Why Passkeys Are Phishing-Resistant

```text
The assertion signature covers:
  ├── challenge issued by YOUR server  (nothing static to relay)
  ├── rpIdHash -> credential only ever works for example.com
  └── origin   -> browser refuses/warns when page origin differs

Fake site examp1e.com cannot obtain signatures for example.com.
There is no secret for the user to "accidentally type" into a
proxy page — origin-spoofing proxies cannot obtain a valid assertion for the legitimate RP. Session theft, compromised endpoints and weak recovery remain separate attacks.
TOTP/push lack exactly this binding: their codes relay fine.
```

### Authenticators, Passkeys, and Sync

| Term | Meaning |
| ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| Roaming authenticator | Separate hardware (YubiKey); moves between devices via USB/NFC |
| Platform authenticator | Built into the device (TPM, Secure Enclave, Android Keystore) |
| Discoverable credential ("resident key") | Credential + user handle stored ON device; enables username-less flows |
| Passkey | Discoverable FIDO credential; may be device-bound or synced through a credential provider |
| Sync | Private keys replicate across the user's devices through their cloud account |

Sync trades some isolation for availability: a passkey is only as protected as the cloud account guarding the sync chain — which is why recovery design matters more than ceremony mechanics.

### Assurance Levels (NIST SP 800-63B)

| Level | Requirements | Example |
| ----- | ------------------------------------------------------------------------------------------------------ | ------------------------------ |
| AAL1 | Single-factor authentication; identity proofing is a separate IAL | Plain password login |
| AAL2 | Two factors and required controls; current NIST guidance requires offering a phishing-resistant option | Password + TOTP or push |
| AAL3 | Two factors with phishing-resistant public-key authentication and a non-exportable key | FIDO2 security key, smart card |

"Verifier impersonation resistance" is NIST's formal name for phishing resistance: the protocol binds responses to the legitimate verifier, so attacker-in-the-middle proxies cannot substitute their own site.

## Code Examples

### Compute one TOTP from the RFC mechanism

This complete Node helper accepts decoded seed bytes and implements the SHA-1 / 30-second profile. It is a mechanics example, not an enrollment or production verifier. Seed generation, Base32/QR encoding and secure seed retrieval belong to the chosen maintained OTP library.

```js
const { createHmac } = require('node:crypto');
function totpAt(key, unixSeconds, digits = 6) {
  if (!Buffer.isBuffer(key) || key.length < 20 ||
      !Number.isSafeInteger(unixSeconds) || unixSeconds < 0 ||
      ![6, 8].includes(digits)) throw new TypeError('invalid TOTP input');
  const counter = Buffer.alloc(8);
  counter.writeBigUInt64BE(BigInt(Math.floor(unixSeconds / 30)));
  const digest = createHmac('sha1', key).update(counter).digest();
  const offset = digest[digest.length - 1] & 15;
  const binary = digest.readUInt32BE(offset) & 0x7fffffff;
  return String(binary % (10 ** digits)).padStart(digits, '0');
}
module.exports = { totpAt };
```

At Unix time 59 with RFC seed bytes `12345678901234567890`, the eight-digit code is `94287082`. Verification evaluates the explicitly allowed time counters, then atomically records the matched counter for that user/credential before granting access. Two concurrent uses of the same accepted counter must not both succeed. Marking the six-digit text globally is incorrect because codes can repeat at different counters. Bound attempts before cryptographic work; wider drift windows increase guessing opportunities.

Enrollment is also a state transition: an already authenticated user requests a pending encrypted seed, proves a valid code, and atomically activates it. Re-enrollment, recovery-code replacement and disabling MFA require step-up authentication and notification. Never place unconfirmed enrollment secrets in the active login path.

### Registration binds a fresh challenge to an authenticated account

This complete adapter factory targets `@simplewebauthn/server` 14.0.3. `pending.put` stores an expiring, browser/account-bound attempt; `pending.take` atomically consumes only a matching, unexpired attempt. `credentials.insert` enforces credential-ID uniqueness. These persistence adapters and an authenticated `user` are injected contracts, not implemented databases.

```js
const { randomUUID } = require('node:crypto');
const { generateRegistrationOptions, verifyRegistrationResponse } =
  require('@simplewebauthn/server');

function createPasskeyRegistration({ pending, credentials }) {
  return {
    async start(user, browserId) {
      const options = await generateRegistrationOptions({
        rpName: 'Acme', rpID: 'example.com', userName: user.name,
        userID: user.webAuthnUserID, // stable opaque Uint8Array, not email/PII
        attestationType: 'none',
        authenticatorSelection: { residentKey: 'required', userVerification: 'required' },
      });
      const attemptId = randomUUID();
      await pending.put(attemptId, { userId: user.id, browserId,
        challenge: options.challenge, expiresAt: Date.now() + 300_000 });
      return { attemptId, options };
    },
    async finish(user, browserId, attemptId, response) {
      const attempt = await pending.take(attemptId, user.id, browserId);
      if (!attempt) throw new Error('registration attempt missing or expired');
      const result = await verifyRegistrationResponse({ response,
        expectedChallenge: attempt.challenge, expectedOrigin: 'https://example.com',
        expectedRPID: 'example.com', requireUserVerification: true });
      if (!result.verified || !result.registrationInfo) throw new Error('registration rejected');
      const { credential, credentialDeviceType, credentialBackedUp } = result.registrationInfo;
      await credentials.insert({ userId: user.id, credential,
        deviceType: credentialDeviceType, backedUp: credentialBackedUp });
      return { registered: true };
    },
  };
}
module.exports = { createPasskeyRegistration };
```

The response's credential ID is not the challenge-store key: it did not exist when registration began. After a consumed attempt fails, create a new attempt instead of accepting a replay. Protect enrollment endpoints against CSRF and require fresh authentication; binding an attacker's new credential to a victim account is an account takeover.

### Authentication verifies the stored credential and intended user

Generate fresh authentication options, store their challenge under a browser-bound attempt ID, and return only allowed credentials for a username flow—or use discoverable credentials for a username-less flow. On completion, load the credential by its untrusted ID, then verify its stored public key, expected challenge/origin/RP ID, user-presence and required user-verification flags. Enforce the pending account/credential ownership or discoverable `userHandle` mapping; a valid signature from another account cannot satisfy the requested identity.

Persist the library's returned counter under a concurrency policy before issuing the local session. Many synced/platform authenticators legitimately return zero; a non-increasing positive counter is a risk signal, not universal proof of cloning. Do not automatically lock every account based on one ambiguous counter observation. Account state, step-up freshness and recovery policy remain server responsibilities.

### Browser adapters convert the binary fields

Server JSON contains Base64URL values, while native WebAuthn APIs expect binary buffers. `@simplewebauthn/browser` handles these conversions through `startRegistration({ optionsJSON })` and `startAuthentication({ optionsJSON })`. Pass the result to the matching finish endpoint with its attempt ID, credentials policy, CSRF header and JSON content type. Check HTTP status before parsing, and surface cancellation/unsupported-device errors. Passing raw server JSON straight to `navigator.credentials.create` is not a complete browser implementation.

## Real-World Use Cases

### 1. Banking-grade step-up authentication

- Login requires password + TOTP/push; wire transfers trigger an AAL3 hardware-key check
- Risk engine escalates factors based on amount, device freshness, and geography

### 2. Consumer platforms going passwordless

- Passkey enrollment nudged after a successful password login (GitHub/Google pattern)
- Passkey becomes primary; password demoted to legacy fallback and then removed

### 3. Enterprise workforce (pairs with stage 6 SSO)

- IdP enforces phishing-resistant MFA once; each SP must validate the required authentication context/freshness; assurance is not inherited merely by trusting the IdP
- Conditional access adds managed-device requirements on top of strong authn

### 4. Admin and internal-tool hardening

- Operator accounts require hardware keys; break-glass accounts sealed in vaults
- Directly counters AiTM proxy kits that target DevOps and finance staff

### 5. Healthcare/fintech compliance evidence

- Documented factor/session/recovery controls and their evidence support assessment; AAL labels alone do not establish HIPAA/PCI compliance
- Recovery-code issuance and consumption logs become audit artifacts

## Common Mistakes

1. **Treating SMS as strong MFA**: SIM swap turns "possession" into an attacker phone call. Use authenticator apps or WebAuthn.

2. **Storing TOTP secrets in plaintext**: The seed is password-equivalent. Encrypt at rest with KMS like any credential.

3. **Unlimited OTP attempts**: Six digits fall to online guessing without aggressive throttling — cap attempts, add lockout/backoff.

4. **Treating counters as universal clone proof**: Use the library/authenticator policy; synced credentials may return zero and concurrent ceremonies need coordinated persistence.

5. **Building a stronger front door than back door**: Enforcing passkeys while allowing email-link resets with only name+DOB makes recovery the attack path.

6. **Trusting client-echoed challenges**: Challenges must be generated server-side, stored with TTL, and consumed once.

## Best Practices

1. **Choose against the threat model**: both device-bound hardware credentials and synced passkeys can resist phishing; key exportability, sync/recovery trust and required assurance decide which fits.

2. **Rate-limit every verification endpoint** per user AND per IP.

3. **Encrypt TOTP seeds at rest**; never log tokens or secrets.

4. **Issue hashed single-use recovery codes at enrollment**; consume each code atomically; replacement invalidates the old set under an explicit policy.

5. **Make account recovery deliberately slower than login** — cooling-off periods, notifications to all devices, human review for high-value accounts.

6. **Validate origin and rpId on every ceremony**, not just registration.

7. **Record `backedUp` and device type** to risk-score sessions (synced passkey vs bound hardware).

8. **Support multiple passkeys per account** plus cross-device activation so losing one device is not losing the account.

9. **Monitor second-factor failure storms** — they are the earliest takeover signal.

10. **Document AAL targets per endpoint** so auditors do not guess your posture.

## Performance Considerations

| Aspect | Consideration |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| TOTP verification | Measure crypto plus seed-store lookup, rate limiting and atomic replay control |
| WebAuthn verification | Algorithm/parser/store costs depend on credential and runtime; measure end-to-end ceremony latency |
| Challenge store | Redis with short TTL keeps API servers stateless |
| Synced vs bound keys | No runtime cost difference; different recovery/risk model |
| Session length | Long post-MFA sessions avoid ceremony fatigue; step up only on risky actions |

## Summary

MFA layers independent factors; the engineering craft is picking factors that resist modern attacks and closing the recovery gap. Key takeaways:

- Factors: know / have / are — two knowledge factors are not MFA
- TOTP (RFC 6238) is HMAC over 30-second windows of a shared secret; beats SMS (SIM swap) but stays phishable and symmetric
- WebAuthn ceremonies: registration stores a public key; authentication verifies signed challenges bound to origin + rpId
- Passkeys can be device-bound or synced; sync and recovery change the key trust boundary
- AAL1-3 grade assurance; AAL3 means hardware-backed, verifier-impersonation-resistant
- Account recovery is the weakest link: hashed single-use codes, guarded slow resets, monitoring

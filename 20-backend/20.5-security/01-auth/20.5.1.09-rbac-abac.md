# RBAC (Role-Based Access Control)

> Stage 8 of the [Auth Learning Track](INDEX.md) — prev: [MFA & Passkeys](20.5.1.08-mfa-passkeys-webauthn.md) · next: [ABAC Deep Dive](20.5.1.10-abac-access-control.md)


## Definition

Role-Based Access Control (RBAC) is a method of regulating access to resources based on the roles of individual users. In RBAC, permissions are assigned to roles, and users are assigned to roles. Users inherit the permissions of their assigned roles. RBAC simplifies access management by providing a structured approach to assigning and managing permissions across an organization.

> **Textbook Definition:** Role-Based Access Control maps principals to roles and roles to permissions, with optional hierarchies and separation-of-duty constraints. Resource ownership and tenant boundaries may still require checks beyond role membership.

RBAC is widely used in enterprise applications and cloud platforms. NIST SP 800-162 describes **ABAC**, the attribute-based model compared with RBAC later in this chapter.

## First Principles

Authorization models are answers to one question: what must the *decision* depend on?

1. **RBAC: role membership.** When the org chart is the truth ("managers approve expense reports"), roles map cleanly and audits are easy — the model's whole value is reviewability. Its ceiling: roles explode combinatorially when context matters ("manager *of that project*, *during business hours*").
2. **ABAC: attributes of user, resource, environment.** When context is the truth, policies evaluate attributes — expressive but hard to audit ("why was this denied?"). Every ABAC policy is a boolean function; complexity lives in policy management, not evaluation.
3. **Hybrid is the honest answer** (role baseline + attribute conditions), because real orgs have both static structure and contextual exceptions. ReBAC (relationship-based, Google Zanzibar style) enters when *relationships between resources* (doc in folder in team) drive decisions.

## Why Do We Need It?

- **Simplified Management**: Manage permissions at role level, not per user
- **Principle of Least Privilege**: Users get only permissions needed for their role
- **Separation of Duties**: Prevent conflicts by assigning different roles
- **Security evidence**: Reviewable grants help demonstrate access controls; choosing RBAC alone does not establish compliance
- **Auditability**: Clear trail of who has access to what
- **Scalability**: Easy to manage as organization grows

## Code Examples

### Expand permissions through a role hierarchy

This complete TypeScript model accepts already verified role assignments and a role catalog. It has no user/session database: assignment, revocation and tenant scope remain external contracts. Inheritance is an explicit graph, not something implied by names such as `admin`.

```typescript
type Action = 'create' | 'read' | 'update' | 'delete' | 'manage';
interface Permission { resource: string; action: Action }
interface Role { id: string; permissions: Permission[]; inherits?: string[] }

export function createRbac(catalogue: Role[]) {
  if (catalogue.length > 1000) throw new RangeError('role catalogue exceeds local bound');
  const roles = new Map<string, Role>();
  for (const role of catalogue) {
    if (!role.id || roles.has(role.id)) throw new Error('role ids must be unique');
    roles.set(role.id, { id: role.id, permissions: role.permissions.map(p => ({ ...p })),
      inherits: [...(role.inherits ?? [])] });
  }
  function permissions(assigned: string[]): Permission[] {
    const result = new Map<string, Permission>();
    const done = new Set<string>();
    const visiting = new Set<string>();
    function visit(id: string, depth = 0): void {
      if (depth > 100) throw new Error('role hierarchy too deep');
      if (visiting.has(id)) throw new Error('cyclic role inheritance');
      if (done.has(id)) return;
      const role = roles.get(id);
      if (!role) throw new Error('unknown assigned or inherited role');
      visiting.add(id);
      for (const parent of role.inherits ?? []) visit(parent, depth + 1);
      for (const permission of role.permissions) {
        result.set(JSON.stringify([permission.resource, permission.action]), { ...permission });
      }
      visiting.delete(id); done.add(id);
    }
    for (const id of assigned) visit(id);
    return [...result.values()];
  }
  return { permissions, can(assigned: string[], resource: string, action: Action): boolean {
    return permissions(assigned).some(p => p.resource === resource &&
      (p.action === action || p.action === 'manage'));
  } };
}

const rbac = createRbac([
  { id: 'viewer', permissions: [{ resource: 'post', action: 'read' }] },
  { id: 'editor', permissions: [{ resource: 'post', action: 'update' }], inherits: ['viewer'] },
]);
console.log(rbac.can(['editor'], 'post', 'read')); // true via viewer
console.log(rbac.can(['viewer'], 'post', 'delete')); // false
```

Trace: `editor` visits `viewer`, accumulates read and update, then deduplicates exact resource/action pairs. Unknown or cyclic grants are configuration errors, not implicit access. Validate persisted catalog shapes and role-assignment authority before this model; a request must never select its own roles. Resource `manage` is an explicitly defined wildcard for that resource, not a special global admin bypass.

### A permission is necessary, but ownership still constrains the row

A guard can require `invoice:read`, yet the handler must query `WHERE tenant_id = trustedTenant AND id = requestedId`. List queries, export jobs, nested writes and bulk mutations need the same boundary. An `admin` role for clinic A must not become platform-wide access. Give cross-tenant support operations a separate audited elevation contract.

A Nest guard reads metadata from both handler and controller (`getAllAndOverride` or a deliberately chosen merge rule), rejects missing required metadata by default, and runs after authentication. Only explicitly public routes bypass that policy. Fetch current grants or use a permission-version/expiry policy; roles copied into a long-lived token do not automatically observe revocation. The [Nest authorization guide](https://docs.nestjs.com/security/authorization) shows guard/decorator wiring; the [ABAC chapter](20.5.1.10-abac-access-control.md) owns contextual policy evaluation.

### Database Schema (Prisma)

This single-tenant relational sketch makes each assignment and role-permission pair unique. It does not implement hierarchy, expiry or tenant-aware membership. A multi-tenant design must scope assignments and enforce matching tenant ownership with constraints and queries; globally unique email is also a product identity decision.

```text
model User {
  id String @id @default(cuid())
  email String @unique
  roles UserRole[]

  @@map("users")
}

model Role {
  id String @id @default(cuid())
  name String @unique
  permissions RolePermission[]
  users UserRole[]

  @@map("roles")
}

model Permission {
  id String @id @default(cuid())
  resource String
  action String
  roles RolePermission[]

  @@unique([resource, action])
  @@map("permissions")
}

model UserRole {
  userId String
  roleId String
  user User @relation(fields: [userId], references: [id])
  role Role @relation(fields: [roleId], references: [id])

  @@id([userId, roleId])
  @@map("user_roles")
}

model RolePermission {
  roleId String
  permissionId String
  role Role @relation(fields: [roleId], references: [id])
  permission Permission @relation(fields: [permissionId], references: [id])

  @@id([roleId, permissionId])
  @@map("role_permissions")
}

```

### Prisma Query for RBAC

The adapter below assumes an initialized `prisma` client from that schema. It expands direct grants only; the in-memory hierarchy above does not magically appear in this query. Handle account state and tenant context separately.

```typescript
// Get user with roles and permissions
const getUserWithPermissions = async (userId: string) => {
  return prisma.user.findUnique({
    where: { id: userId },
    include: {
      roles: {
        include: {
          role: {
            include: {
              permissions: {
                include: {
                  permission: true,
                },
              },
            },
          },
        },
      },
    },
  });
};

// Check if user has permission
const hasPermission = async (
  userId: string,
  resource: string,
  action: string
): Promise<boolean> => {
  const user = await getUserWithPermissions(userId);

  if (!user) return false;

  return user.roles.some((ur) =>
    ur.role.permissions.some(
      (rp) =>
        rp.permission.resource === resource &&
        (rp.permission.action === action || rp.permission.action === "manage")
    )
  );
};

```

## Real-World Use Cases

### 1. Enterprise Applications

- Employee roles (admin, manager, employee)
- Department-based access (HR, Finance, Engineering)
- Hierarchical permissions

### 2. Cloud Platforms (AWS, GCP, Azure)

- IAM roles and policies
- Service account permissions
- Resource-based access control

### 3. Content Management Systems

- Editor roles (admin, editor, author, viewer)
- Content type permissions
- Workflow approvals

### 4. Multi-Tenant SaaS

- Tenant-specific roles
- Organization-level permissions
- Feature-based access control

## Common Mistakes

1. **Role explosion**: Too many granular roles become unmanageable

2. **Not implementing least privilege**: Granting more permissions than needed

3. **Unreviewed permission changes**: Whether code or data, the catalog needs controlled writes, versioning and review

4. **Not auditing role assignments**: Regular review of who has what access

5. **Assuming inheritance without defining it**: Use an acyclic graph when inheritance helps; flat roles are also valid

6. **Undefined revocation delay**: Specify the cache/token/in-flight window and enforce it

7. **Mixing authentication and authorization**: RBAC is authorization, not authentication

8. **Not testing permission boundaries**: Verify access control in tests

## Best Practices

1. **Implement least privilege**: Grant only necessary permissions

2. **Use hierarchy where useful**: Reject cycles and unknown parents; do not infer privilege from role names

3. **Audit regularly**: Review role assignments and permissions

4. **Separate duties**: Prevent conflicts with role separation

5. **Use descriptive role names**: Clear naming conventions

6. **Implement permission caching**: Reduce database queries

7. **Test access control**: Include RBAC in test suites

8. **Document roles and permissions**: Maintain clear documentation

9. **Implement time-based access**: Temporary role assignments
10. **Use attribute-based access control (ABAC)** for complex scenarios

## Performance Considerations

| Aspect | Consideration |
| ------------------ | ---------------------------------------------------------------------------------------- |
| Permission Caching | Cache user permissions to reduce DB queries |
| Role Hierarchy | Pre-compute inherited permissions |
| Database Queries | Use efficient joins for role/permission lookups |
| Cache Invalidation | Invalidate cache on role/permission changes |
| Change Propagation | Pub/sub invalidation may be lost; bound stale grants with versions/expiry/current checks |

## Summary

RBAC is a scalable and manageable approach to access control that assigns permissions to roles and users to roles. Key takeaways:

- Implement least privilege principle
- Use role hierarchy for inheritance
- Separate duties for critical operations
- Audit role assignments regularly
- Test access control thoroughly
- Use caching for performance
- Document roles and permissions
- Consider ABAC for complex scenarios

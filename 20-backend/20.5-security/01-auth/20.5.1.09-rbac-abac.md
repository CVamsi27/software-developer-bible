# RBAC (Role-Based Access Control)

> Stage 8 of the [Auth Learning Track](INDEX.md) — prev: [MFA & Passkeys](20.5.1.08-mfa-passkeys-webauthn.md) · next: [ABAC Deep Dive](20.5.1.10-abac-access-control.md)

## Definition

Role-Based Access Control (RBAC) grants permissions through roles. An administrator assigns users to roles and permissions to roles; an authorization check considers the roles a user is allowed to activate for the current session. A role represents a responsibility such as `invoice-approver`, not a person or a resource.

> **Textbook Definition:** RBAC is an access-control model in which permissions are associated with roles, users are assigned to roles, and users obtain permissions through the roles active in their sessions. The core model includes users, roles, permissions, user-role assignments, permission-role assignments and sessions. Role hierarchies and static or dynamic separation-of-duty constraints are additional model components; implementations may support some, all or none of them.

A permission usually names an operation on a resource class, such as `invoice:approve`. That answers whether the caller has the capability. It does not, by itself, say which invoice or tenant the caller may access.

## First Principles

Per-user grants repeat the same facts: many people perform the same job, and each job needs a related set of operations. RBAC inserts a role between users and permissions so a permission change can be reviewed and applied once at the role level.

```text
User ── user-role assignment ──▶ Role ── permission-role assignment ──▶ Permission
                                  │
                                  ├── optional hierarchy
                                  └── optional constraints
```

The role is useful when it describes a relatively stable responsibility. If access varies by tenant, ownership, assignment, data classification or time, adding a role for every combination can create a role matrix that is difficult to review. Keep the stable capability in a role and evaluate resource-specific conditions at the enforcement point.

## 1. Core assignments and optional extensions

| Model element | Meaning | Design consequence |
| ------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| User-role assignment (UA) | Which roles a user is authorized to activate | Provision and revoke it through a trusted administrative path. |
| Permission-role assignment (PA) | Which operations a role permits | A permission should identify a clear resource/action pair. |
| Session and active roles | A user may activate an authorized subset for a session | Many web apps simplify this by treating resolved current roles as active; state that assumption. |
| Role hierarchy | A senior role inherits permissions from junior roles | Use only when inheritance matches the real responsibility structure; reject cycles. |
| Separation of duty | A constraint prevents conflicting assignments or activations | Choose static assignment checks, dynamic session checks, or both where the workflow requires them. |

NIST's RBAC model separates Core RBAC from hierarchy and separation-of-duty components. Do not assume that a framework or identity provider implements every component just because it exposes a `roles` claim.

## 2. A permission check is not the complete resource decision

Suppose Mira is an `invoice-approver` in tenant `acme`. That role may permit `invoice:approve`, but the application still needs to verify that the requested invoice belongs to `acme`, is in an approvable state and was not submitted by Mira if the workflow requires independent approval.

```text
Verified identity + tenant membership
                │
                ▼
       active RBAC permissions ── capability check ──┐
                                                      ├── permit operation?
Requested ID ── tenant-scoped resource lookup ────────┤
Resource state + workflow constraints ────────────────┘
```

Perform the object check near the data operation. Scope reads, lists, exports, nested writes and bulk mutations to trusted tenant membership and current resource state. A guard that checked `invoice:approve` cannot protect a later query that fetches an arbitrary invoice ID.

## 3. Expand a role hierarchy safely

This small TypeScript model demonstrates direct permissions and inheritance. It validates catalog data and role references, rejects cycles without recursive traversal, and treats unknown assignments as configuration errors. It deliberately does not implement user provisioning, tenant membership, active-session selection or separation-of-duty constraints; those are separate parts of an authorization system.

```typescript
type Action = 'create' | 'read' | 'update' | 'delete' | 'manage';
interface Permission { resource: string; action: Action }
interface Role { id: string; permissions: Permission[]; inherits?: string[] }

const actions = new Set<Action>(['create', 'read', 'update', 'delete', 'manage']);
const isRecord = (value: unknown): value is Record<string, unknown> =>
  typeof value === 'object' && value !== null && !Array.isArray(value);

export function createRbac(catalogue: readonly Role[]) {
  if (!Array.isArray(catalogue)) throw new TypeError('role catalogue must be an array');
  const roles = new Map<string, Role>();

  for (const candidate of catalogue as readonly unknown[]) {
    if (!isRecord(candidate) || typeof candidate.id !== 'string' || !candidate.id.trim() ||
        !Array.isArray(candidate.permissions)) {
      throw new TypeError('invalid role record');
    }
    const id = candidate.id;
    if (roles.has(id)) throw new Error(`duplicate role id: ${id}`);
    const permissions: Permission[] = candidate.permissions.map((value): Permission => {
      if (!isRecord(value) || typeof value.resource !== 'string' || !value.resource.trim() ||
          typeof value.action !== 'string' || !actions.has(value.action as Action)) {
        throw new TypeError(`invalid permission in role: ${id}`);
      }
      return { resource: value.resource, action: value.action as Action };
    });
    const inherits = candidate.inherits === undefined ? [] : candidate.inherits;
    if (!Array.isArray(inherits) || inherits.some(parent => typeof parent !== 'string' || !parent.trim())) {
      throw new TypeError(`invalid inheritance list in role: ${id}`);
    }
    roles.set(id, { id, permissions, inherits: [...inherits] as string[] });
  }

  // Validate every configured edge, including roles not used by the current request.
  for (const role of roles.values()) {
    for (const parent of role.inherits ?? []) {
      if (!roles.has(parent)) throw new Error(`unknown inherited role: ${parent}`);
    }
  }
  const state = new Map<string, 0 | 1 | 2>(); // unseen, visiting, complete
  for (const start of roles.keys()) {
    if (state.get(start) === 2) continue;
    const stack: Array<{ id: string; nextParent: number }> = [{ id: start, nextParent: 0 }];
    state.set(start, 1);
    while (stack.length) {
      const frame = stack[stack.length - 1];
      const parents = roles.get(frame.id)!.inherits ?? [];
      if (frame.nextParent < parents.length) {
        const parent = parents[frame.nextParent++];
        const parentState = state.get(parent) ?? 0;
        if (parentState === 1) throw new Error('cyclic role inheritance');
        if (parentState === 0) {
          state.set(parent, 1);
          stack.push({ id: parent, nextParent: 0 });
        }
      } else {
        state.set(frame.id, 2);
        stack.pop();
      }
    }
  }

  function permissions(assigned: readonly string[]): Permission[] {
    if (!Array.isArray(assigned) || assigned.some(id => typeof id !== 'string' || !id.trim())) {
      throw new TypeError('assigned roles must be non-empty role ids');
    }
    const result = new Map<string, Permission>();
    const visited = new Set<string>();
    const pending = [...assigned];
    while (pending.length) {
      const id = pending.pop()!;
      const role = roles.get(id);
      if (!role) throw new Error(`unknown assigned role: ${id}`);
      if (visited.has(id)) continue;
      visited.add(id);
      for (const permission of role.permissions) {
        result.set(JSON.stringify([permission.resource, permission.action]), permission);
      }
      for (const parent of role.inherits ?? []) pending.push(parent);
    }
    return [...result.values()];
  }

  return {
    permissions,
    can(assigned: readonly string[], resource: string, action: Action): boolean {
      if (typeof resource !== 'string' || !resource.trim() || !actions.has(action)) {
        throw new TypeError('invalid permission query');
      }
      return permissions(assigned).some(permission => permission.resource === resource &&
        (permission.action === action || permission.action === 'manage'));
    },
  };
}

const rbac = createRbac([
  { id: 'viewer', permissions: [{ resource: 'article', action: 'read' }] },
  { id: 'editor', permissions: [{ resource: 'article', action: 'update' }], inherits: ['viewer'] },
]);
rbac.can(['editor'], 'article', 'read'); // true through viewer
rbac.can(['viewer'], 'article', 'delete'); // false
```

`manage` is a local wildcard convention in this example, not a universal RBAC permission. A production catalog should constrain who can create roles or assignments, version changes, and make revocation behavior explicit. If permissions are cached, define the maximum stale-grant window and invalidate or version the cache when assignments or role permissions change.

## 4. Enforce the capability at the service boundary

Resolve the user's active roles from trusted membership for the selected tenant. Do not let a request choose its own roles or rely on a long-lived token to reflect revocation immediately. In a NestJS application, a guard can check route metadata, but the service or repository must still constrain the actual resource operation:

```typescript
if (!rbac.can(activeRoles, 'invoice', 'approve')) throw new ForbiddenException();

const invoice = await prisma.invoice.findFirst({
  where: { id: invoiceId, tenantId: principal.activeTenantId },
});
if (!invoice) throw new NotFoundException();
```

Here, `activeRoles` and `activeTenantId` have already been resolved and validated server-side. The query is an additional object/tenant boundary; it does not replace the capability check. Apply the same rule to background jobs and non-HTTP entry points.
Database row-level security can add defense in depth if the database session is safely scoped and pooled connections cannot leak tenant context. Test both allowed and denied paths, including the wrong tenant, invalid resource state, missing or revoked role, conflicting duties and malformed catalog; permission expansion alone does not prove object authorization.

## Real-World Decisions

- **Editorial workflow:** `editor` may update articles and `publisher` may publish them. If users must not publish their own submissions, that is a workflow constraint on the particular article, not a reason to create a role for every author/publisher combination.
- **Tenant SaaS:** assign `billing-admin` within an organization, then scope every query to that organization. A tenant-scoped role must never silently become a platform-wide support role.
- **Cloud IAM terminology:** a cloud IAM “role” may be an assumable identity with attached policies. Do not assume it is identical to an organizational RBAC role; inspect the provider's principal, policy and resource semantics.

## Summary

RBAC reduces repeated per-user grants by mapping users to roles and roles to permissions. The core model also includes session role activation; hierarchies and separation-of-duty constraints are optional extensions. A role check establishes a capability, while the service must still authorize the specific object, tenant and workflow state being accessed.

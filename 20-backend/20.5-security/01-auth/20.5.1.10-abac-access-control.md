# ABAC (Attribute-Based Access Control)

> Stage 9 of the [Auth Learning Track](INDEX.md) — prev: [RBAC](20.5.1.09-rbac-abac.md) · next: [Interview Drills](20.5.1.11-interview-questions.md)
>
>
> **Why it matters:** This is a Security interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Attribute-Based Access Control (ABAC) is an authorization model that evaluates access decisions based on attributes (properties) of the subject, resource, action, and environment. Policies are expressed as rules that combine these attributes, enabling fine-grained, dynamic access control that adapts to context.

> **Textbook Definition:** Attribute-Based Access Control evaluates policies over attributes of the subject, object, operation and environment. Trusted attribute sources, policy decisions and enforcement points jointly determine whether a requested operation is permitted.

**Key terms:**
- **Subject attributes** — who is requesting (role, department, clearance level)
- **Resource attributes** — what is being accessed (owner, sensitivity, tenant)
- **Action attributes** — what operation is being performed (read, write, delete)
- **Environment attributes** — context (time, IP, device, location)
- **Policy** — a rule combining attributes to produce an allow/deny decision
- **Policy Decision Point (PDP)** — evaluates policies and returns a decision
- **Policy Enforcement Point (PEP)** — enforces the PDP's decision

## First Principles

ABAC's structure follows from what an attribute policy must compute:

1. **Decisions are functions of (subject, resource, action, environment).** That four-tuple is the model's entire ontology — every "can Alice edit this doc?" reduces to evaluating a policy over those four attribute sets at request time.
2. **Expressiveness and auditability pull in opposite directions.** More attributes = finer control = harder "why denied?" answers — which is why mature deployments version policies, record decision/version/reason with a privacy policy for sensitive inputs, and test policies like code. Versioned policy tests and review help to keep the combinatorics sane.
3. **ABAC's real enemy is evaluation cost and error at scale**: attributes must be fresh (stale group membership = wrong access), complete (missing attribute = deny-by-default or hole), and the PDP must be fast — hence caching decisions with careful invalidation (→ 20.8.01).

## Why Do We Need It?

RBAC works for simple organizations but breaks down when:
1. **Access depends on context** — "doctor can view records only during shifts"
2. **Access depends on resource ownership** — "user can edit only their own posts"
3. **Access depends on data sensitivity** — "only managers can view salary data"
4. **Dynamic rules** — "access denied if IP is from outside the corporate network"
5. **Multi-tenant** — "user in clinic A cannot access clinic B's data"

ABAC represents contextual conditions explicitly; roles can remain subject attributes in a hybrid policy.

## How It Works

### ABAC Architecture

```text
┌────────────────────────────────────────────────────────────────────┐
│ ABAC Policy Evaluation Flow                                        │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  Request                                                           │
│  ├── Subject: { role: 'doctor', clinicId: 'abc', shift: 'on' }     │
│  ├── Resource: { type: 'patient', tenantId: 'abc', ownerId: 'd1' } │
│  ├── Action: 'read'                                                │
│  └── Environment: { time: '14:00', ip: '10.0.0.1' }                │
│                                                                    │
│  Policy Decision Point (PDP)                                       │
│  ├── Load policies for resource type 'patient'                     │
│  ├── Evaluate policy 1: subject.clinicId == resource.tenantId      │
│  │   → true (same clinic)                                          │
                                                                     │  ├── Evaluate policy 2: action == 'read' AND subject.role == 'doctor'
│  │   → true (doctors can read)                                     │
                                                                     │  ├── Evaluate policy 3: environment.time BETWEEN '08:00' AND '20:00'
│  │   → true (within working hours)                                 │
│  ├── Combine: ALL policies must allow → ALLOW                      │
│  └── Decision: ALLOW                                               │
│                                                                    │
│  Policy Enforcement Point (PEP)                                    │
│  └── Enforces the PDP's decision → grant or deny access            │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### RBAC vs ABAC vs ReBAC

| Dimension | RBAC | ABAC | ReBAC |
| --------------------- | ---------------------------- | -------------------------------------------------- | ----------------------------------------------- |
| **Decision basis** | Role → Permission | Attributes of subject/resource/action/env | Relationships (follows, owns, member-of) |
| **Example** | "Admin can delete" | "Owner can delete own posts during business hours" | "Follower can view posts of people they follow" |
| **Policy expression** | Static role map | Boolean rules on attributes | Graph traversal |
| **Complexity** | Low | Medium-High | Medium |
| **Auditability** | High (role = permission) | Medium (need to trace attribute evaluation) | Medium |
| **Best for** | Reviewable role/group grants | Fine-grained, context-aware access | Social graphs, complex hierarchies |
| **When to use** | Most apps start here | When RBAC isn't granular enough | When relationships are the key factor |

## Code Examples

### One deny-overrides patient policy

This complete TypeScript example allows a doctor to read an assigned patient in the same clinic while on duty, with enough clearance for restricted data. A clinic administrator may read within the same tenant under this illustrative policy. Neither role bypasses tenant isolation. The application must assemble attributes from verified identity, current membership, the actual stored resource and trusted schedule/time data.

```typescript
interface PolicyInput {
  subject: { id: string; clinicId: string; role: 'doctor' | 'admin'; clearance: number };
  resource: { id: string; tenantId: string; assignedDoctorId: string;
    sensitivity: 'internal' | 'restricted' };
  action: string;
  environment: { onDuty: boolean };
}
interface Decision { effect: 'allow' | 'deny'; reason: string; policyVersion: 'patient-read-v1' }

export function evaluatePatientRead(input: PolicyInput): Decision {
  const result = (effect: Decision['effect'], reason: string): Decision =>
    ({ effect, reason, policyVersion: 'patient-read-v1' });
  const { subject: s, resource: r, environment: e } = input;
  // Validate runtime inputs at the adapter; also reject unusable required values here.
  if (!s?.id || !s.clinicId || !r?.id || !r.tenantId ||
      !['doctor', 'admin'].includes(s.role) ||
      !['internal', 'restricted'].includes(r.sensitivity) ||
      !Number.isFinite(s.clearance) || typeof e?.onDuty !== 'boolean') {
    return result('deny', 'missing-or-invalid-attribute');
  }
  if (s.clinicId !== r.tenantId) return result('deny', 'cross-tenant');
  if (input.action !== 'read') return result('deny', 'unsupported-action');
  if (r.sensitivity === 'restricted' && s.clearance < 3) {
    return result('deny', 'clearance');
  }
  if (s.role === 'doctor' && (!e.onDuty || r.assignedDoctorId !== s.id)) {
    return result('deny', 'assignment-or-duty');
  }
  return result('allow', 'matched-patient-read');
}
```

A doctor assigned to patient P in clinic A passes each gate. Changing only the stored patient's tenant to B denies before the role can allow. Changing only `onDuty` to false denies that doctor. Missing classification or `NaN` clearance denies instead of bypassing comparison. This is a scoped domain policy, not a generic clinical authorization standard; emergencies/break-glass require a separately designed, time-bounded, audited policy.

### Build attributes at an enforcement point

```text
Verified principal -> current membership/clearance
Requested patient ID -> tenant-scoped database lookup -> actual sensitivity/assignment
Trusted schedule/risk adapter -> current environment
Route metadata -> semantic action 'read' (not the literal HTTP string 'get')
                           -> decision -> constrained operation + audit
```

Do not populate resource tenant, owner or sensitivity from route/body assertions. Do not infer device trust from a spoofable User-Agent string or source identity from untrusted proxy headers. A missing user should fail authentication before the policy runs. The **Policy Information Point** supplies trusted attributes; the **PDP** computes a decision; the **PEP** must actually enforce it in every HTTP, queue, export and internal path.

A decision can become stale before mutation: assignment or classification may change between a read and write. Constrain the mutation by tenant/version/policy-relevant state inside the transaction, then retry/re-evaluate on conflict. List endpoints need policy-aware filtering; authorizing one row does not authorize every returned row. Cache keys include subject/resource/action, relevant attribute versions and policy version; a TTL alone is not proof of immediate revocation.

### Combining policies changes the meaning

A general engine must define `deny`, `allow`, `not-applicable`, and errors. In **deny-overrides**, any explicit deny wins; with no applicable allow, default deny. Treat missing/error attributes as deny unless a reviewed, bounded availability policy says otherwise. An allow-first loop can accidentally bypass a tenant denial, while applying a global deny to unrelated resources can block legitimate access. Test both policy applicability and combination, not just individual predicates.

Audit the decision's subject/tenant/resource/action, policy version, reason code and request correlation. Do not dump every attribute or patient value into logs. Decide whether unavailable audit storage blocks sensitive changes or records them in a durable local transaction/outbox; silently dropping required evidence is not an audit policy.

## Real-World Use Cases

| Use Case | ABAC Pattern | Why |
| -------------------------------- | ---------------------------------------- | ------------------------------------------------------- |
| **Illustrative healthcare SaaS** | Tenant isolation + role + time | Doctors see only their clinic's patients, during shifts |
| **Cloud platforms** (AWS IAM) | Resource-based + identity-based policies | Fine-grained resource access |
| **Enterprise** (Okta) | Role + department + clearance | Dynamic access based on org attributes |
| **Banking** | Role + transaction amount + risk score | High-amount transfers need extra approval |
| **Multi-tenant SaaS** | Tenant + role + resource owner | Users access only their tenant's resources |

## Common Mistakes

- **Trusting requested attributes:** a caller can label a restricted patient as public. Fetch resource attributes from trusted data and verify their tenant/version.
- **Allowing evaluation errors:** a missing clearance or failed policy service is not a matching permission. Fail closed under the stated availability contract.
- **Ignoring policy applicability:** a global allow can defeat a tenant gate; a global deny can block unrelated operations. Make combination and default behavior explicit.
- **Separating decision from enforcement:** a guard that passes is insufficient if the subsequent query/mutation ignores the checked resource and current state.
- **Unbounded sensitive audit payloads:** record enough to explain the decision without duplicating private clinical data.

## Best Practices

1. **Default deny** — no matching policy = no access. Never "allow if not denied."
2. **Deny overrides** — any deny wins over any allow. Security first.
3. **Policy categories** — group by distinct invariants such as tenant, role, sensitivity and ownership; no fixed category count proves clarity.
4. **Audit every decision** — log subject, resource, action, decision, and which policies fired.
5. **Test policies** — unit tests for each policy, integration tests for the evaluator.
6. **Control policy changes** — code-based and configuration-based policies both need versioning, tests and authorized review.
7. **Cache policy decisions** — within a request scope, cache to avoid re-evaluation.
8. **Monitor policy changes** — alert when policies are added/modified in production.
9. **Combine with RBAC** — ABAC enhances RBAC, doesn't replace it. Start with RBAC, add ABAC for fine-grained needs.
10. **Keep it simple** — if a policy is hard to understand, it's hard to audit. Rewrite it.

## Summary

ABAC provides fine-grained, context-aware authorization by evaluating policies based on subject, resource, action, and environment attributes. Unlike RBAC's static role → permission mapping, ABAC adapts to context: who you are, what you're accessing, what you're doing, and when/where you're doing it. The critical patterns: deny-overrides (security first), default deny (no match = no access), policy categories (manageable complexity), and audit logging (compliance). ABAC can combine role grants with contextual conditions; choose the representation from the actual access invariants.

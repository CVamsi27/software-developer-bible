# ABAC (Attribute-Based Access Control)

> Stage 9 of the [Auth Learning Track](INDEX.md) — prev: [RBAC](20.5.1.09-rbac-abac.md) · next: [Interview Drills](20.5.1.11-interview-questions.md)

## Definition

Attribute-Based Access Control (ABAC) decides whether an operation is allowed by evaluating policy against facts about the requester, the resource, the requested operation and, when relevant, the environment. A role can be one of those facts. ABAC does not require every policy to use every attribute category.

> **Textbook Definition:** In NIST's model, ABAC grants or denies a subject's requested operation on an object by evaluating policy over relevant subject, object and action attributes; environmental attributes participate when the policy uses them.

The model describes what a decision can depend on. The application still has to obtain trustworthy attributes, evaluate the applicable policy and enforce the decision on the same resource operation.

### Terms in the decision path

- **Subject:** the user or service principal requesting access.
- **Resource (object):** the record, file, API operation or other protected object.
- **Action:** the semantic operation, such as `invoice:approve`; it need not equal an HTTP method.
- **Environment:** request context such as a trusted device state, time window or verified network zone, if the policy uses it.
- **Policy Administration Point (PAP):** manages policy definitions and versions.
- **Policy Information Point (PIP):** supplies attribute values from authoritative sources.
- **Policy Decision Point (PDP):** evaluates a request against policy and returns a decision.
- **Policy Enforcement Point (PEP):** protects the operation and applies the decision.

These are responsibilities in an architecture, not necessarily separate services. A small application may combine them in one service; a policy engine such as Open Policy Agent (OPA) can separate evaluation from enforcement.

## First Principles

An ABAC rule can use a fact only if the system knows what that fact means, where it came from and how current it is. A `tenantId` copied from a request body is not authoritative membership; a patient classification loaded from the stored patient record may be. Attribute quality and lifecycle are part of the security design, not plumbing details.

A usable decision path therefore has four steps:

1. Identify the subject from authenticated server-side context.
2. Resolve the actual resource and its security-relevant attributes from trusted sources.
3. Evaluate the requested semantic action and relevant context under a versioned policy.
4. Enforce the result against the same object and state that were evaluated.

ABAC can express conditions that would otherwise multiply role combinations, but it does not automatically make a policy simpler or safer. More attributes create more input dependencies, freshness rules and policy cases to test.

## 1. Attribute and decision flow

```text
PAP ── versioned policy ───────────────────────────────▶ PDP
                                                          ▲
Authenticated principal ─┐                               │
Stored resource lookup ───┼── PIP: trusted attributes ───┤
Verified request context ─┘                               │
Request (subject, object, action, context) ──▶ PEP ── ask ┘
                                                │
                         decision + obligations ─┘
                                                ▼
                     PEP enforces the result on that operation
```

For example, a policy might permit reading a restricted patient record only when the caller is an active member of the same clinic, has sufficient clearance, is assigned to the patient and is on duty. Some policies need only a subset of these facts. A policy engine may return a simple allow/deny, or a richer result such as not-applicable, indeterminate or obligations; the application must define how it handles each result.

## 2. Choose the model from the access invariant

| Model | Primary question | Example predicate | Main engineering concern |
| ----- | ----------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| RBAC | Which operations may this active role perform? | `editor` may update an article | Role design, assignment review and role changes. |
| ABAC | Which attributes make this operation valid now? | Same tenant, sufficient classification and trusted device | Attribute authority/freshness and policy evaluation. |
| ReBAC | What relationship connects the subject to the object? | User may read a document shared with their team | Relationship-based access control (ReBAC) storage, graph traversal and consistency. |

These models can be used independently or combined. There is no universal rule that every application must start with RBAC or add ABAC later; choose the representation that matches the facts the access decision must depend on.

## 3. A local patient-read policy

This TypeScript example makes the policy explicit: a clinic administrator may read any patient in their tenant, while a doctor must also be on duty and assigned to that patient. Both need sufficient clearance for restricted data. The rule is illustrative, not a clinical standard.
The caller must construct its input from verified identity, current membership, the stored patient record and trusted duty status.

```typescript
interface PolicyInput {
  subject: { id: string; clinicId: string; role: 'doctor' | 'admin'; clearance: number };
  resource: { id: string; tenantId: string; assignedDoctorId: string;
    sensitivity: 'internal' | 'restricted' };
  action: string;
  environment: { onDuty?: boolean };
}
interface Decision {
  effect: 'allow' | 'deny';
  reason: string;
  policyVersion: 'patient-read-v1';
}

export function evaluatePatientRead(input: PolicyInput): Decision {
  const result = (effect: Decision['effect'], reason: string): Decision =>
    ({ effect, reason, policyVersion: 'patient-read-v1' });
  const { subject: s, resource: r, environment: e } = input;

  if (!s?.id || !s.clinicId || !r?.id || !r.tenantId ||
      !['doctor', 'admin'].includes(s.role) ||
      !['internal', 'restricted'].includes(r.sensitivity) ||
      !Number.isFinite(s.clearance) || s.clearance < 0) {
    return result('deny', 'missing-or-invalid-attribute');
  }
  if (s.clinicId !== r.tenantId) return result('deny', 'cross-tenant');
  if (input.action !== 'read') return result('deny', 'unsupported-action');
  if (r.sensitivity === 'restricted' && s.clearance < 3) {
    return result('deny', 'clearance');
  }
  if (s.role === 'doctor' && typeof e?.onDuty !== 'boolean') {
    return result('deny', 'missing-or-invalid-duty-attribute');
  }
  if (s.role === 'doctor' && (!e.onDuty || r.assignedDoctorId !== s.id)) {
    return result('deny', 'assignment-or-duty');
  }
  return result('allow', 'matched-patient-read');
}
```

The application should validate untrusted runtime data at its adapter boundary; TypeScript types do not validate JSON, database rows or policy-engine responses. A doctor assigned to patient P in clinic A passes only when all required conditions hold. Changing the stored tenant or assignment denies access; changing classification denies access when the caller lacks the required clearance.
A break-glass workflow needs a separate, time-bounded and audited policy rather than a hidden admin bypass.

## 4. Attribute trust, enforcement and freshness

```text
Verified principal ──▶ current tenant membership and clearance
Requested patient ID ─▶ tenant-scoped lookup ─▶ stored sensitivity and assignment
Trusted schedule source ──────────────────────▶ current duty context
Normalized action ────────────────────────────▶ PDP decision
                                                  │
                                                  ▼
                                  constrained operation + audit record
```

Do not trust client-supplied resource tenant, owner or sensitivity. Do not infer device trust from a user-agent string or accept identity from untrusted proxy headers. If an attribute source fails or a required value is missing, the PEP must not grant access.
Preserve the distinction between an authorization denial and an evaluation/availability error so the application can report, retry and alert appropriately.

A check can become stale between reading a resource and changing it. Constrain the mutation by tenant and policy-relevant state inside the transaction, or re-evaluate when the state version changes. Lists need policy-aware filtering; permission to read one row does not authorize every row returned by a query.
Database row-level security can provide another enforcement layer, but only when the database session is correctly scoped.

Decision caches require keys that cover the subject, object, action and relevant attribute/policy versions. A time to live (TTL) bounds staleness; it does not provide immediate revocation. Within one request, memoization is safe only while the inputs remain stable.
Cross-request caching needs a documented freshness and invalidation contract.

## 5. Policy composition and operations

There is no universal policy-combining algorithm. Define the applicable policies, default behavior and precedence explicitly. **Deny-overrides** is one possible contract: an applicable deny wins over an allow. Another engine or domain may use different combination rules.
Test applicability and composition, not only individual predicates.

If policy evaluation is unavailable or returns an indeterminate result, the PEP should not perform the protected operation. Whether the caller receives a denial or a retryable service error is an application contract; do not silently translate an infrastructure failure into an ordinary policy denial. Keep enough decision metadata for diagnosis while redacting sensitive attributes from logs.

A local or sidecar PDP avoids a remote policy-call hop and can reduce dependence on network availability, but still needs health checks and current policy/data distribution. A remote PDP can centralize policy ownership across services, while adding network latency and an availability dependency. Place the PEP close to the protected data operation in either design.

## 6. Wire the PEP in NestJS and test the decision matrix

Place the enforcement point where the evaluated resource is the operated resource. An authentication guard establishes the principal first; a policy guard then evaluates the coarse action and tenant before the handler; the service still constrains the mutation by tenant and policy-relevant state inside its transaction, because assignment or clearance can change between the guard check and the write.

```typescript
import { CanActivate, ExecutionContext, ForbiddenException,
  Injectable, NotFoundException } from '@nestjs/common';

// Coarse check before the handler; the service still constrains the
// mutation by tenant and state inside its own transaction.
@Injectable()
class PatientReadGuard implements CanActivate {
  constructor(
    private readonly patients: PatientPolicyLookup,
    private readonly roster: DutyRoster,
  ) {}
  async canActivate(context: ExecutionContext): Promise<boolean> {
    const req = context.switchToHttp().getRequest();
    const patient = await this.patients.findForPolicy(
      req.params.id, req.principal.clinicId);
    if (!patient) throw new NotFoundException();
    const decision = evaluatePatientRead({
      subject: { id: req.principal.id, clinicId: req.principal.clinicId,
        role: req.principal.role, clearance: req.principal.clearance },
      resource: patient,
      action: 'read',
      environment: req.principal.role === 'doctor'
        ? { onDuty: await this.roster.isOnDuty(req.principal.id) }
        : {},
    });
    if (decision.effect !== 'allow') throw new ForbiddenException(decision.reason);
    req.patient = patient; // Hand the evaluated row downstream; do not re-fetch a different one.
    return true;
  }
}
```

Returning 404 for a missing row and 403 for a denied one leaks existence to an unauthorized caller; returning 404 for both hides that signal but complicates client handling. Choose the contract deliberately and document it. Register the authentication guard before the policy guard so the policy inputs are verified identity, not request headers.

Test the evaluator as a pure matrix, then prove the wiring with transport tests:

| Case | Expected decision |
| ----------------------------------------------- | --------------------------------------------------------------------- |
| Subject tenant differs from resource tenant | `deny` (`cross-tenant`) |
| Doctor off duty or unassigned to the patient | `deny` (`assignment-or-duty`) |
| Restricted sensitivity with clearance below 3 | `deny` (`clearance`) |
| Missing attribute or stale membership | `deny`, fail closed — never allow |
| Policy version bump (`patient-read-v2`) | Old cached decisions re-evaluated; audit records the deciding version |
| Revocation lands between guard check and write | Transaction-scoped predicate still rejects the mutation |

Unit-test every matrix row against `evaluatePatientRead`, including unknown roles and malformed attributes. Add HTTP tests proving guard order, the 401-vs-403 mapping, that a denied request never reaches the service, and that the service's transaction rejects a state change the guard already approved.

## Real-World Decisions

- **Cloud IAM:** AWS identity and access management (IAM) documents ABAC policies that compare principal or session tags with resource tags. A project tag match can make one policy apply to many project resources, while the policy still names the allowed actions and resource conditions.
- **Approval workflow:** a `finance-approver` role can be combined with transaction amount, requester identity and organization attributes. The policy can require another approver above a threshold or reject self-approval.
- **Shared documents:** if permission depends primarily on ownership or a path through groups and folders, a relationship model may express the invariant more directly than many role/attribute combinations.

## Summary

ABAC evaluates policy using trusted attributes of the subject, resource, action and any relevant environment. Its security depends on authoritative, sufficiently fresh inputs and a PEP that enforces the decision on the same operation. Define policy composition, missing-data behavior, failure handling, cache freshness and audit redaction as explicit contracts.

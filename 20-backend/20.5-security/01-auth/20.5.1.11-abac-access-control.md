# ABAC (Attribute-Based Access Control)

> Stage 9 of the [Auth Learning Track](INDEX.md) — prev: [RBAC](20.5.1.09-rbac-abac.md) · next: [Interview Drills](20.5.1.10-interview-questions.md)
>
> **TL;DR:** ABAC evaluates access decisions based on attributes of the subject (who), resource (what), action (how), and environment (when/where). Unlike RBAC's static role → permission mapping, ABAC enables dynamic, context-aware policies: "a doctor can view patient records only for patients in their clinic, during working hours." The senior test is designing a policy engine that is auditable, testable, and doesn't become an unmaintainable mess of conditionals.
>
> **Why it matters:** This is a Security interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Attribute-Based Access Control (ABAC) is an authorization model that evaluates access decisions based on attributes (properties) of the subject, resource, action, and environment. Policies are expressed as rules that combine these attributes, enabling fine-grained, dynamic access control that adapts to context.

**Key terms:**
- **Subject attributes** — who is requesting (role, department, clearance level)
- **Resource attributes** — what is being accessed (owner, sensitivity, tenant)
- **Action attributes** — what operation is being performed (read, write, delete)
- **Environment attributes** — context (time, IP, device, location)
- **Policy** — a rule combining attributes to produce an allow/deny decision
- **Policy Decision Point (PDP)** — evaluates policies and returns a decision
- **Policy Enforcement Point (PEP)** — enforces the PDP's decision

## Why Do We Need It?

RBAC works for simple organizations but breaks down when:
1. **Access depends on context** — "doctor can view records only during shifts"
2. **Access depends on resource ownership** — "user can edit only their own posts"
3. **Access depends on data sensitivity** — "only managers can view salary data"
4. **Dynamic rules** — "access denied if IP is from outside the corporate network"
5. **Multi-tenant** — "user in clinic A cannot access clinic B's data"

ABAC solves these by making policies attribute-driven, not role-driven.

## How It Works

### ABAC Architecture

```text
┌──────────────────────────────────────────────────────────────────┐
│ ABAC Policy Evaluation Flow                                        │
├──────────────────────────────────────────────────────────────────┤
│                                                                    │
│  Request                                                           │
│  ├── Subject: { role: 'doctor', clinicId: 'abc', shift: 'on' }     │
│  ├── Resource: { type: 'patient', tenantId: 'abc', ownerId: 'd1' } │
│  ├── Action: 'read'                                                │
│  └── Environment: { time: '14:00', ip: '10.0.0.1' }                │
│                                                                    │
│  Policy Decision Point (PDP)                                       │
│  ├── Load policies for resource type 'patient'                     │
│  ├── Evaluate policy 1: subject.clinicId == resource.tenantId      │
│  │   → true (same clinic)                                          │
                                                                     │  ├── Evaluate policy 2: action == 'read' AND subject.role == 'doctor'
│  │   → true (doctors can read)                                     │
                                                                     │  ├── Evaluate policy 3: environment.time BETWEEN '08:00' AND '20:00'
│  │   → true (within working hours)                                 │
│  ├── Combine: ALL policies must allow → ALLOW                      │
│  └── Decision: ALLOW                                               │
│                                                                    │
│  Policy Enforcement Point (PEP)                                    │
│  └── Enforces the PDP's decision → grant or deny access            │
│                                                                    │
└──────────────────────────────────────────────────────────────────┘
```

### RBAC vs ABAC vs ReBAC

| Dimension | RBAC | ABAC | ReBAC |
| --------------------- | ------------------------ | -------------------------------------------------- | ----------------------------------------------- |
| **Decision basis** | Role → Permission | Attributes of subject/resource/action/env | Relationships (follows, owns, member-of) |
| **Example** | "Admin can delete" | "Owner can delete own posts during business hours" | "Follower can view posts of people they follow" |
| **Policy expression** | Static role map | Boolean rules on attributes | Graph traversal |
| **Complexity** | Low | Medium-High | Medium |
| **Auditability** | High (role = permission) | Medium (need to trace attribute evaluation) | Medium |
| **Best for** | Simple orgs, <20 roles | Fine-grained, context-aware access | Social graphs, complex hierarchies |
| **When to use** | Most apps start here | When RBAC isn't granular enough | When relationships are the key factor |

## Code Examples

### Policy Types (TypeScript)

```typescript
// abac.types.ts
interface SubjectAttributes {
  role: 'admin' | 'doctor' | 'nurse' | 'receptionist';
  clinicId: string;
  userId: string;
  clearanceLevel: number;
}

interface ResourceAttributes {
  type: 'patient' | 'appointment' | 'invoice' | 'prescription';
  tenantId: string;
  ownerId: string;
  sensitivity: 'public' | 'internal' | 'confidential' | 'restricted';
}

type AbacAction = 'create' | 'read' | 'update' | 'delete' | 'manage';

interface EnvAttributes {
  time: Date;
  ip: string;
  device: string;
}

interface PolicyInput {
  subject: SubjectAttributes;
  resource: ResourceAttributes;
  action: AbacAction;
  env: EnvAttributes;
}

type PolicyDecision = 'allow' | 'deny' | 'not-applicable';
```

### Policy Definitions

```typescript
// policies.ts — ABAC policies as composable functions
const policies: AbacPolicy[] = [
  // Policy 1: Tenant isolation — subject and resource must share tenant
  {
    id: 'tenant-isolation',
    can: (input) => {
      if (input.subject.clinicId !== input.resource.tenantId) {
        return { effect: 'deny', reason: 'cross-tenant access denied' };
      }
      return { effect: 'not-applicable' };
    },
  },

  // Policy 2: Role-based action restrictions
  {
    id: 'role-action-restrict',
    can: (input) => {
      const allowed: Record<string, AbacAction[]> = {
        admin: ['create', 'read', 'update', 'delete', 'manage'],
        doctor: ['create', 'read', 'update'],
        nurse: ['read', 'update'],
        receptionist: ['read'],
      };
      const permitted = allowed[input.subject.role] ?? [];
      if (permitted.includes(input.action)) {
        return { effect: 'allow' };
      }
      return { effect: 'deny', reason: `${input.subject.role} cannot ${input.action}` };
    },
  },

  // Policy 3: Sensitivity-based restrictions
  {
    id: 'sensitivity-gate',
    can: (input) => {
      if (input.resource.sensitivity === 'restricted' && input.subject.clearanceLevel < 3) {
        return { effect: 'deny', reason: 'insufficient clearance' };
      }
      return { effect: 'not-applicable' };
    },
  },

  // Policy 4: Time-based restrictions (e.g., night shift)
  {
    id: 'working-hours',
    can: (input) => {
      const hour = input.env.time.getHours();
      if (hour < 6 || hour > 22) {
        // Outside working hours — only admins can access
        if (input.subject.role !== 'admin') {
          return { effect: 'deny', reason: 'outside working hours' };
        }
      }
      return { effect: 'not-applicable' };
    },
  },
];
```

### Policy Evaluator (Deny-Overrides)

```typescript
// evaluator.ts — deny-overrides combination algorithm
function evaluate(policies: AbacPolicy[], input: PolicyInput): PolicyDecision {
  const decisions = policies.map((p) => p.can(input));

  // Deny-overrides: any deny wins, then allow, then default deny
  const active = decisions.filter((d) => d.effect !== 'not-applicable');

  const deny = active.find((d) => d.effect === 'deny');
  if (deny) return 'deny';

  const allow = active.find((d) => d.effect === 'allow');
  if (allow) return 'allow';

  return 'deny'; // default deny — no matching policy = no access
}
```

### NestJS ABAC Guard

```typescript
// abac.guard.ts
@Injectable()
export class AbacGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const { user } = request;

    const input: PolicyInput = {
      subject: {
        role: user.role,
        clinicId: user.clinicId,
        userId: user.sub,
        clearanceLevel: user.clearanceLevel,
      },
      resource: {
        type: request.params.resourceType,
        tenantId: request.params.tenantId,
        ownerId: request.params.ownerId,
        sensitivity: request.params.sensitivity,
      },
      action: request.method.toLowerCase() as AbacAction,
      env: {
        time: new Date(),
        ip: request.ip,
        device: request.headers['user-agent'],
      },
    };

    const decision = evaluate(policies, input);
    if (decision === 'deny') {
      throw new ForbiddenException('Access denied by ABAC policy');
    }
    return true;
  }
}
```

### Testing ABAC Policies

```typescript
// abac.test.ts
describe('ABAC Policies', () => {
  const baseInput: PolicyInput = {
    subject: { role: 'doctor', clinicId: 'clinic-abc', userId: 'd1', clearanceLevel: 2 },
    resource: { type: 'patient', tenantId: 'clinic-abc', ownerId: 'd1', sensitivity: 'internal' },
    action: 'read',
    env: { time: new Date('2026-01-15T14:00:00'), ip: '10.0.0.1', device: 'Mozilla/5.0' },
  };

  it('allows doctor to read own clinic patients during working hours', () => {
    expect(evaluate(policies, baseInput)).toBe('allow');
  });

  it('denies cross-tenant access', () => {
    const input = { ...baseInput, resource: { ...baseInput.resource, tenantId: 'clinic-xyz' } };
    expect(evaluate(policies, input)).toBe('deny');
  });

  it('denies doctor delete (only admin can delete)', () => {
    const input = { ...baseInput, action: 'delete' as AbacAction };
    expect(evaluate(policies, input)).toBe('deny');
  });

  it('denies access outside working hours for non-admin', () => {
    const input = { ...baseInput, env: { ...baseInput.env, time: new Date('2026-01-15T02:00:00') } };
    expect(evaluate(policies, input)).toBe('deny');
  });
});
```

## Real-World Use Cases

| Use Case | ABAC Pattern | Why |
| ----------------------------- | ---------------------------------------- | ------------------------------------------------------- |
| **Healthcare SaaS** (Docita) | Tenant isolation + role + time | Doctors see only their clinic's patients, during shifts |
| **Cloud platforms** (AWS IAM) | Resource-based + identity-based policies | Fine-grained resource access |
| **Enterprise** (Okta) | Role + department + clearance | Dynamic access based on org attributes |
| **Banking** | Role + transaction amount + risk score | High-amount transfers need extra approval |
| **Multi-tenant SaaS** | Tenant + role + resource owner | Users access only their tenant's resources |

## Common Mistakes

### 1. Policy Sprawl (Too Many Policies)

```typescript
// BAD: 200 individual policies that overlap and contradict
const policies = [
  policy1, policy2, ..., policy200 // impossible to audit
];

// GOOD: Group into 5-10 policy categories
const policies = [
  tenantIsolationPolicy,    // cross-tenant deny
  roleActionPolicy,         // role → allowed actions
  sensitivityPolicy,        // data classification gate
  timeBasedPolicy,          // working hours restriction
  ownershipPolicy,          // user can access own resources
];
```

### 2. Missing Default Deny

```typescript
// BAD: No default — unmatched policies allow access
if (decision === 'allow') return true;
return true; // ← BUG: everything not explicitly denied is allowed

// GOOD: Explicit default deny
if (decision === 'allow') return true;
throw new ForbiddenException('No matching policy — default deny');
```

### 3. Evaluating Policies in the Wrong Order

```typescript
// BAD: Allow overrides — a later allow can override an earlier deny
const allow = decisions.find((d) => d.effect === 'allow');
if (allow) return 'allow'; // ← ignores deny from earlier policy
const deny = decisions.find((d) => d.effect === 'deny');

// GOOD: Deny overrides — deny always wins
const deny = decisions.find((d) => d.effect === 'deny');
if (deny) return 'deny'; // deny wins
const allow = decisions.find((d) => d.effect === 'allow');
```

### 4. Not Auditing Policy Decisions

```typescript
// BAD: No audit trail — can't prove who authorized what
const decision = evaluate(policies, input);

// GOOD: Audit every decision
const decision = evaluate(policies, input);
await auditLog.create({
  subjectId: input.subject.userId,
  resourceType: input.resource.type,
  resourceId: input.resource.ownerId,
  action: input.action,
  decision,
  policies: decisions.map((d) => d.policyId),
  timestamp: new Date(),
});
```

## Best Practices

1. **Default deny** — no matching policy = no access. Never "allow if not denied."
2. **Deny overrides** — any deny wins over any allow. Security first.
3. **Policy categories** — group into 5-10 categories (tenant, role, sensitivity, time, ownership).
4. **Audit every decision** — log subject, resource, action, decision, and which policies fired.
5. **Test policies** — unit tests for each policy, integration tests for the evaluator.
6. **Separate policy from code** — policies should be configurable, not hardcoded.
7. **Cache policy decisions** — within a request scope, cache to avoid re-evaluation.
8. **Monitor policy changes** — alert when policies are added/modified in production.
9. **Combine with RBAC** — ABAC enhances RBAC, doesn't replace it. Start with RBAC, add ABAC for fine-grained needs.
10. **Keep it simple** — if a policy is hard to understand, it's hard to audit. Rewrite it.

## Summary

ABAC provides fine-grained, context-aware authorization by evaluating policies based on subject, resource, action, and environment attributes. Unlike RBAC's static role → permission mapping, ABAC adapts to context: who you are, what you're accessing, what you're doing, and when/where you're doing it. The critical patterns: deny-overrides (security first), default deny (no match = no access), policy categories (manageable complexity), and audit logging (compliance). ABAC enhances RBAC — start with RBAC, add ABAC when fine-grained control is needed.

## Cheat Sheet

```text
ABAC vs RBAC:
├── RBAC: role → permission (static)
├── ABAC: attributes → policy → decision (dynamic)
├── ReBAC: relationships → permission (graph)
└── Use ABAC when RBAC isn't granular enough

ABAC Components:
├── Subject: who (role, clinicId, clearanceLevel)
├── Resource: what (type, tenantId, sensitivity)
├── Action: how (read, write, delete)
├── Environment: when/where (time, IP, device)
└── Policy: combines attributes → allow/deny

Policy Combination:
├── Deny-overrides: any deny wins (recommended)
├── Allow-overrides: any allow wins (less secure)
├── Only-allow: must have explicit allow
└── Default: deny if no matching policy

Checklist:
├── Default deny on all policy sets
├── Deny overrides combination
├── Audit every policy decision
├── Unit tests for each policy
├── 5-10 policy categories max
└── Separate policy from code
```

## First Principles

Use these questions to practice decisions about identity, credential and session lifetimes, and trust boundaries. The [fundamentals chapter](20.5.1.01-auth-fundamentals.md) derives the underlying mechanisms.

1. **Strong answers state conditions and costs.** Choose a control for a threat and operating context, then explain the trade-off and failure mode.
2. **Derive the answer from the trust boundary.** If a constraint changes, revisit the choice instead of repeating a memorized design.

## Stage 0 — Fundamentals

### Q1. "What's the difference between authentication and authorization?"

**30-sec:** Authentication proves identity ("who are you"); authorization decides permissions ("what may you do"). They fail differently: AuthN failures → 401, AuthZ failures → 403. In code they live in different layers — credential verification at login vs policy checks per request.

 *Traps:* "Where does a JWT fit?" (it can carry authenticated claims; it is a token format, not proof by itself). "Can authorization run without login?" (yes: evaluate an anonymous principal against an explicit public-access policy).

### Q2. "Why bcrypt/Argon2 over SHA-256 for passwords?"

**30-sec:** SHA-256 is designed to be fast; password storage needs a deliberately expensive password-hashing function. Fast digests make offline guesses cheap. Argon2id raises memory/time cost, while bcrypt primarily raises computation. Weak passwords remain guessable; no universal crack time, speed ratio or parameter set applies.

 *Traps:* "Which parameters do you tune?" (Argon2id memory, time and parallelism; benchmark under concurrent verification, meet the threat model and keep resource use bounded). "Upgrade parameters without resetting passwords?" (store algorithm and cost parameters with the hash; rehash after successful verification when the stored setting is outdated).

### Q3. "Pick the primitive: password storage / PHI columns / webhook payload."

**30-sec:** Passwords → a password-hashing function for verification. Sensitive data at rest → authenticated encryption when authorized services must recover plaintext; for AES-GCM, never reuse a nonce with the same key. Webhooks → a message authentication code such as HMAC-SHA256 over the provider-defined bytes, with timestamp and replay checks as specified. A valid HMAC shows possession of the shared secret, not unique non-repudiable identity; a digital signature uses a private/public key pair.

 *Traps:* "Why GCM over CBC?" (authenticated encryption — tamper detection built-in). "Why sign the raw body?" (framework re-serialization changes bytes → signature mismatch or bypass).

## Stage 1 — Sessions

### Q4. "Walk me through session-based auth end-to-end."

**30-sec:** Login verifies credentials → server creates state keyed by a cryptographically random, unguessable ID → `Set-Cookie: sid=…; HttpOnly; Secure; SameSite=Lax` → each request carries the cookie → middleware loads session state → logout revokes it. Session-store consistency, cache behavior and in-flight requests define how quickly revocation takes effect.

 *Traps:* "Redis restarts — what happens?" (choose persistence, replication and failover behavior against the session availability objective; a cold store may force reauthentication). "Sticky sessions vs shared store?" (affinity can reduce reads but does not provide failover or shared revocation).

### Q5. "Explain every cookie flag and the attack it stops."

**30-sec:** `HttpOnly` prevents JavaScript from reading the cookie, but XSS can still make authenticated requests; `Secure` sends it only over HTTPS; `SameSite` limits cross-site sending but is not a complete CSRF defense; `Domain` and `Path` scope delivery, not application isolation; `Max-Age` sets persistence. A stolen cookie remains a bearer credential until rejected or expired.

 *Traps:* "Does SameSite=Lax stop all CSRF?" (No — top-level GET navigations still send it; state-changing GETs remain dangerous). "Strict downsides?" (can suppress cookies needed on cross-site returns/email navigations — pair with anti-CSRF tokens instead).

### Q6. "How do you prevent session fixation and hijacking?"

**30-sec:** Fixation — attacker plants a known session ID pre-login: accept only server-issued IDs and rotate the ID after login and privilege elevation. Hijacking — stolen cookie: protect transport, use idle and absolute timeouts, require re-authentication for sensitive operations, and treat device/IP changes as risk signals rather than identity proof.

 *Traps:* "Users complain about daily logouts — what do you trade?" (idle and absolute lifetime against risk and usability; sliding expiry alone must not extend a session forever). "Should an IP change revoke a session?" (usually treat it as a risk signal, not identity proof; mobile networks and VPNs change addresses).

### Q7. "Sessions vs JWT — when do you choose which?"

**30-sec:** A session ID refers to server-side state, so the service can change or revoke that state centrally, at the cost of a store lookup and its availability contract. A signed self-contained access token can be checked offline with trusted keys until expiry, but current permissions or early revocation require additional state or short validity. Choose from the clients, latency, revocation objective and failure model; a hybrid is one option.

 *Traps:* "Compromised account stays valid 14 minutes — options?" (denylist or version check where enforced, shorter access-token lifetime, refresh-family revocation; retiring a signing key only rejects tokens signed by that key after verifier caches refresh, and can invalidate many users at once).

## Stage 2 — Tokens / JWT

### Q8. "Anatomy of a JWT?"

**30-sec:** Compact signed JWS uses three base64url segments: header (`alg`, `kid`), payload (registered claims `iss/sub/aud/exp/iat/nbf/jti` + custom), signature over `header.payload`. Payload is encoded, not encrypted — anyone can read it. Verified integrity covers the signed bytes under the allowed key/algorithm; encrypted JWT forms differ.

 *Traps:* "`alg:none` attack?" (verifier pins allowed algorithms; never trust the header). "HS256 vs RS256?" (shared-key verifiers can also mint tokens; public-key verifiers cannot). "Sensitive claims?" (no — JWE or server-side references).

### Q9. "JWTs can't be revoked — mitigations?"

**30-sec:** Design around it: short expiry bounds blast radius; refresh rotation with family revocation kills stolen chains; `jti` denylist only as bounded emergency brake; `tokenVersion` claim checked on sensitive routes; JWKS rotation for catastrophe.

 *Traps:* "Isn't a denylist just sessions again?" (a denylist adds state wherever it is enforced; routes that do not check it keep accepting the token until expiry). "Can key rotation revoke tokens?" (only if verifiers stop trusting the compromised signing key and refresh their key sets; account for propagation and tokens signed by other keys).

### Q10. "Design refresh-token rotation. What breaks without reuse detection?"

**30-sec:** For a rotating refresh-token family, atomically consume the presented token and issue a replacement; store only a verifier for the new high-entropy token. A consumed token presented again can indicate replay, but legitimate concurrent requests and lost responses need an explicit policy before the family is revoked.

 *Traps:* "Why store hash not raw?" (DB leak ≠ usable tokens). "Two tabs race the refresh?" (coordinate refresh per grant; a conditional consume has one winner. Handle legitimate concurrency and lost responses under the provider/app reuse policy, without broadly exposing the winner's new secret). "SPA vs mobile storage?" (httpOnly same-site cookie vs secure keystore).

### Q11. "Where do tokens live in a browser?"

**30-sec:** In a browser-only OAuth client, JavaScript can use and potentially expose returned tokens; memory avoids persistent storage but does not stop active XSS. A BFF keeps OAuth tokens server-side and gives the browser an opaque session cookie. A token-mediating backend keeps refresh credentials but exposes access tokens to JavaScript.

 *Traps:* "Cookie brings CSRF back?" (yes: cookie-authenticated unsafe endpoints need an explicit CSRF policy). "Which browser architecture for a sensitive application?" (prefer a BFF when feasible; it prevents direct token exposure but still needs CSRF protection and cannot prevent active XSS from making requests through the session).

## Stage 3 — OAuth2 / OIDC

### Q12. "OAuth 2.0 vs OpenID Connect — one sentence each."

**30-sec:** OAuth 2.0 lets a client obtain delegated access to a resource without collecting the user’s password. OpenID Connect adds an authentication contract, including an ID token that a client validates to learn which subject authenticated.

 *Traps:* "'Login with Google' uses which?" (OIDC — identity is required). "Can OAuth alone authenticate?" (provider-specific OAuth login can fetch authenticated user identity, but is not an OIDC ID-token validation contract).

### Q13. "Name the grants and when each is appropriate."

**30-sec:** Authorization Code with PKCE supports interactive user authorization; use it for public clients and commonly for confidential clients too. Client Credentials represents the client, not an end user. Device Authorization is designed for input-constrained clients that cannot conveniently complete a browser redirect. RFC 9700 says the Resource Owner Password Credentials grant **MUST NOT** be used; it also recommends against Implicit because access tokens are exposed in the authorization response.

 *Traps:* "What does `state` do?" (correlates a response to a browser-bound authorization transaction; PKCE can also provide CSRF protection when the server supports and enforces it). "What does OIDC `nonce` do?" (binds the ID token to the login transaction and helps detect replay). "Device-flow polling fails?" (respect the interval, add five seconds after `slow_down`, back off after a timeout, stop on any error other than `authorization_pending` or `slow_down`, and protect the `device_code`). "BFF vs token-mediating backend?" (the BFF proxies resource calls and keeps all OAuth tokens server-side; a token mediator leaves access tokens exposed to browser code).

### Q14. "What does PKCE actually solve?"

**30-sec:** Public clients can't keep secrets, so an intercepted authorization *code* could be exchanged by anyone. PKCE binds exchange to requestor: send `code_challenge` upfront, exchange needs the original random `code_verifier`. Stolen code alone is useless.

 *Traps:* "Confidential clients too?" (RFC 9700 recommends PKCE for them; it helps prevent code injection and misuse). "Does PKCE replace `state`?" (it may provide redirect CSRF protection when correctly supported and transaction-bound; many systems still use `state` for correlation and application state, and OIDC `nonce` serves a distinct ID-token binding role).

### Q15. "Design 'Sign in with X' end-to-end."

**30-sec:** Start a browser-bound transaction with state and PKCE, plus an OIDC nonce when requesting an ID token. After the callback, atomically consume the transaction and redeem the code using the client’s registered token-endpoint method: a backend does this for a confidential client; a public client redeems it without an embedded secret. Validate the ID token’s signature, issuer, audience, expiry and sent nonce before mapping `(issuer, sub)` and creating the local session. Do not auto-link by email alone.

 *Traps:* "Account-linking attack via attacker's verified email?" (link only after re-auth/verification). "IdP outage?" (existing local sessions may continue under policy; cached JWKS cannot perform a new provider login. A secondary provider requires explicit linking/trust, not automatic substitution).

### Q16. "Enterprise wants SSO with their Microsoft Entra ID (formerly Azure AD) — what changes?"

**30-sec:** First establish the tenant’s IdP, supported protocol, account-linking rules and offboarding requirements. With OIDC, validate the configured tenant issuer and audience; map only trusted claims under an explicit policy. With SAML, validate the configured profile, signed message and audience. SCIM can provision lifecycle changes but does not replace login-time and session authorization checks. Store IdP configuration as tenant-owned trusted configuration.

 *Traps:* "How quickly does offboarding take effect?" (define the end-to-end revocation objective across SCIM, local sessions, access-token lifetime and permission caches). "SAML vs OIDC when both are offered?" (select based on the customer’s IdP and profile requirements, ecosystem support, security configuration and maintained implementation; neither is universally superior).

### Q17. "Passkeys/WebAuthn — how do they work and will they replace passwords?"

**30-sec:** During registration, the server issues a challenge and stores the credential’s public key. At login, the authenticator signs a fresh challenge; the server verifies the signature, challenge, RP ID hash and allowed client origin. The credential is scoped to an RP ID, while the origin includes scheme, host and port. Passkeys may be device-bound or synced across devices. A passkey can provide passwordless authentication; whether a login satisfies an MFA policy depends on the required factors and verified user-presence/user-verification properties. Recovery is a separate trust path.

 *Traps:* "What does sync change?" (the credential remains RP-scoped, but the sync provider and account-recovery path become part of the trust model; syncable keys do not meet NIST AAL3 non-exportability requirements). "Does the server receive the fingerprint or PIN?" (no; local user verification activates the authenticator, and the server receives protocol evidence, not the biometric or PIN).

## Stage 4 — Authorization

### Q18. "RBAC vs ABAC vs ReBAC — pick for a hospital system."

**30-sec:** Start with the access invariants. RBAC grants stable capabilities through active roles. ABAC evaluates trusted subject, object, requested-action and, when relevant, environment attributes. ReBAC evaluates relationships such as clinician assignment to a patient or team membership. In a hospital, a role might grant the capability to read; tenant and clearance attributes can constrain that permission, while the clinician-patient assignment is a relationship check. These models can be combined when each represents a distinct fact. Enforce the result at the service operation and keep the data query scoped to the same object and tenant.

*Traps:* "When do roles explode?" (when role names encode changing combinations such as region, product and environment; move those dimensions to policy only if their source and lifecycle are trustworthy). "Where are decisions and enforcement located?" (identify the PDP, the PEP near the protected operation, attribute sources, failure behavior, cache freshness and tests for changes).

Sources: [NIST RBAC FAQs](https://csrc.nist.gov/Projects/role-based-access-control/faqs) · [NIST SP 800-162](https://csrc.nist.gov/publications/detail/sp/800-162/final)

### Q19. "Scopes vs roles vs permissions — untangle them."

**30-sec:** Scopes: what the client app may do on behalf of users (delegated/OAuth world). Roles: coarse grouping within your system. Permissions: atomic actions (`patient:write`) that roles bundle. Enforce on permissions/policies, not just role names; keep tokens minimal.

 *Traps:* "Embed full permission array in the JWT?" (bloat + staleness between issues; carry role+version, expand server-side).

### Q20. "A receptionist replays an API call touching another clinic's patient. Which layers catch it?"

**30-sec:** Authenticate the caller, resolve current staff membership and active clinic, then authorize the action against the actual patient record and assignment. Scope the data operation to the same tenant context; database row-level security can add a backstop when enabled under a non-bypass role with correctly initialized transaction context. Emit a minimal denial event if the audit and privacy policy requires it.

 *Traps:* "If one guard is bypassed, what is the backstop?" (database-enforced tenant constraints can catch query mistakes, but RLS configuration and its database role are part of the trust boundary; it does not replace authentication or policy checks). "How tested?" (seed two clinics and assert cross-tenant reads and writes fail end to end).

### Q21. "Design authorization across 200 microservices."

**30-sec:** Standardize the policy contract and enforcement libraries first. Use a shared policy decision point where cross-service consistency and governance justify the network dependency; let services make local decisions for domain rules when that keeps ownership and availability clearer. Propagate authenticated identity over a defined trust channel, fail closed for sensitive operations, and test policy changes before rollout.

 *Traps:* "Central check latency or outage?" (define bounded caches and their staleness, distinguish low-risk from high-risk actions, and state the fallback explicitly). "Policy ownership?" (domain teams own business rules; platform/security provide policy interfaces, review and rollout controls).

## Cross-Cutting & System-Design Variants

### Q22. "Design auth for a multi-tenant SaaS from scratch." *(whiteboard, 10 min)*

**Skeleton:** Define tenant membership and the authorized way to select an active tenant → authenticate the user and resolve that membership server-side → bind the active tenant to request context → scope every query, write, background job and cache key → test cross-tenant denial → consider database row-level security as defense in depth, with a non-bypass role and transaction-scoped context → audit narrowly controlled support or cross-tenant access. A tenant claim can help carry context, but it is not sufficient authorization by itself. Choose shared-schema, schema-per-tenant or database-per-tenant against isolation, operations, cost and data-residency needs.

 *Traps:* "URL says tenant B while the active membership is A?" (reject or re-resolve through an authorized tenant switch; never trust the URL or token claim alone). "Cross-tenant cache poisoning?" (include tenant and authorization-relevant versioning in cache keys, or avoid sharing the cached object).

### Q23. "Add MFA to an existing password system with zero downtime."

**30-sec:** Roll out in phases while preserving existing sessions: inventory account and recovery paths, offer passkeys/WebAuthn and an appropriate fallback, enroll users with a verified recovery route, then enforce by cohort or risk tier. Encrypt TOTP seeds so the verifier can use them; store recovery codes as one-way hashes and rate-limit their use. Define enrollment deadlines, support capacity, rollback criteria and the effect on active sessions. TOTP is phishable, so use phishing-resistant options where the threat model requires them.

 *Traps:* "Can this be zero downtime?" (you can avoid an application outage, but universal enrollment requires user action and may lock out accounts; measure completion and plan exceptions). "What if a device is lost?" (use pre-established recovery codes or a support process with identity proofing and audit; do not let help desk recovery bypass the factor without controls).

### Q24. "API keys vs JWT vs OAuth — third-party devs want programmatic access."

**30-sec:** These are different layers: an API key is a bearer credential, JWT is a token format, and OAuth is an authorization framework. For a partner acting as itself, issue a high-entropy scoped API key stored as a verifier hash, or use Client Credentials when standardized token issuance, audience restriction or federation helps. For delegated access on behalf of a user, use an interactive authorization flow such as Authorization Code with PKCE. Choose based on attribution, client lifecycle, revocation and interoperability.

 *Traps:* "Key leaks to GitHub?" (revoke and rotate it, investigate use, and bound exposure with narrow scopes, expiry where supported and rate limits; secret scanning is detection, not containment).

### Q25. "p99 login latency spiked after a marketing campaign. Debug it."

**30-sec:** Break latency down by lookup, password verification, MFA, session write and dependencies. Argon2 is intentionally resource-intensive, so compare its measured parameters and bounded verification concurrency with the threat model and capacity budget. Check for credential stuffing, queueing, database contention, dependency timeouts and pool saturation before changing the password-hash policy.

 *Traps:* "Would you lower the Argon2 cost?" (do not make an unmeasured emergency downgrade; first apply admission control, rate limits, bounded queues and capacity changes. If parameters must change, make a documented security decision, benchmark the new setting and plan rehashing).

### Q26. "`POST /login` millisecond by millisecond?"

**Skeleton:** Enforce TLS and abuse controls → perform a bounded account lookup and use generic failure behavior without creating an unbounded dummy-hash denial-of-service path → verify the password using calibrated parameters → complete any required second factor → create session or token state atomically → return the credential with the chosen transport controls. Check password-breach lists mainly at password creation/change unless a specific login-time requirement justifies the dependency. Emit the security event through a reliable, non-secret-bearing audit path. Explain how each stage fails and recovers.

### Q27. "What's wrong with `localStorage.setItem('jwt', token)` in an SPA?"

**30-sec:** Any script running in the origin can read a localStorage token and send it elsewhere, so a single XSS can persist access beyond the page. An HttpOnly cookie blocks direct JavaScript reads but does not stop XSS from issuing authenticated requests and requires CSRF defenses for unsafe cookie-authenticated actions. Memory-only access tokens reduce persistence after page closure but remain usable by active injected script. Keep refresh credentials out of JavaScript-readable storage.

 *Traps:* "Backend is separate-origin — cookies 'won't work'?" (same-origin proxy/BFF; or SameSite=None+Secure with strict CORS allowlist + CSRF tokens).

### Q28. "401 vs 403 — precisely."

**30-sec:** A 401 means the request lacks valid authentication credentials; the server must include a `WWW-Authenticate` challenge. A 403 means the server understood the request but refuses it under the applicable authorization policy. An API may use 404 to avoid disclosing a resource’s existence, if that is part of its consistent contract. Do not assume every client should automatically refresh and retry.

 *Traps:* "Expired-but-validly-signed token?" (401; discuss clock-skew tolerance policy).

### Q29. "How do you test auth?"

**30-sec:** Test representative allow/deny boundaries, missing attributes and policy combinations (role × action × state matrix). Pipeline integration tests: valid/invalid/expired/tampered tokens, cross-tenant denial, refresh replay → family revocation. E2E browser flows incl. MFA step-up. Load-test expensive crypto path. Security regression suite in CI with injected fake clock for exp/nbf windows.

### Q30. "Login rate limiting vs global API rate limiting — differences?"

**30-sec:** Login controls need multiple dimensions: source network/device signals, account identifier and global capacity. Distributed attackers can rotate IPs, while account-only hard lockouts let attackers deny service to victims. Use bounded progressive throttling and generic responses; review timing differences for account enumeration. CAPTCHA or step-up authentication can add friction when risk justifies it, but each has accessibility and abuse trade-offs.

 *Traps:* "How do you avoid a lockout DoS?" (avoid attacker-triggerable permanent lockout; use progressive delays, recovery paths and user notifications, with monitored limits).

### Q31. "What goes into an authorization-failure audit log?"

**30-sec:** Record only what supports investigation and policy evidence: actor and tenant identifiers where needed, resource type, action, allow/deny result, a stable reason code and correlation ID. Minimize or pseudonymize resource identifiers when possible; exclude credentials, tokens and sensitive record contents. Restrict access, protect integrity and set retention under the applicable legal, contractual and operational policy; retention is not one-size-fits-all.

 *Traps:* "PHI in URLs reaches access logs anyway?" (keep identifiers out of URLs where feasible; scrubbers in log pipeline).

### Q32. "Build vs buy: Auth0/Cognito/Keycloak vs rolling your own?"

**30-sec:** Compare managed and self-hosted identity providers against protocol coverage, security operations, recovery, data residency, cost and exit needs. Keep application authorization and resource ownership checks explicit even when authentication is bought. Build domain-specific integration and policy around maintained protocol libraries; never hand-roll protocol cryptography.

 *Traps:* "Lock-in mitigation?" (standard protocols behind a thin identity abstraction; user-export strategy up front).

### Q33. "Is a token ever acceptable in a URL?"

**30-sec:** Do not put reusable access tokens or session credentials in URLs: URLs commonly reach history, logs, analytics and referrer data. A one-time, short-lived magic-link token is a deliberate exception because email needs a clickable handoff; redact it from logs, suppress referrers, and require an explicit confirmation step before consuming the token or creating a session, since mail scanners fetch links automatically. OAuth device flow uses a user code to correlate the browser flow; it is not a reason to put an access token in a URL.

 *Traps:* "The browser WebSocket API cannot set auth headers; what then?" (authenticate over HTTPS to obtain a short-lived, single-use connection ticket, then exchange it at connection setup; prevent ticket leakage and replay).


### Q34. "Sessions meet load balancers and rolling deploys?"

**30-sec:** A shared store lets healthy instances load the same sessions; connection draining bounds in-flight requests during rollout. Store availability, replication/failover, concurrent writes and secret rotation are separate contracts. Test session regeneration, expiry, logout and permission changes during a rolling deploy. Short TTL does not turn an unavailable session store into a harmless re-login: login needs to write new state too.

### Q35. "Design 'logout everywhere' with hybrid tokens."

**30-sec:** Revoke the user’s server-side sessions and refresh-token families. If access tokens carry a version or status reference, verifiers that check it reject old tokens within the documented cache and in-flight window; otherwise those tokens remain usable until expiry. Clients with revoked credentials must reauthenticate. Audit the action and notify the account owner when policy calls for it.

### Q36. "A junior suggests storing role in the session AND the JWT. Concerns?"

**30-sec:** Two sources of truth drift — privilege changes take effect at different times per path. Pick one authority (DB-backed role resolved into short-lived tokens, or session), invalidate coherently, and document which path sees changes within what SLA. The concrete failure: an admin revoked via one path still passes the other until expiry — and the incident ticket says "privilege changes aren't working" with no bug to find.

### Q37. "How does auth differ for first-party web app vs public API platform vs internal tool?"

**30-sec table:**

| Surface | Default choice | Extra concerns |
| ------------------- | ------------------------------------------- | ------------------------------------- |
| First-party web | Session cookie or hybrid tokens | CSRF, cookie flags |
| Public API platform | OAuth2 (auth-code+PKCE, client-credentials) | Developer UX, key rotation, scopes |
| Internal tool | SSO/OIDC behind corporate IdP | Offboarding speed, group→role mapping |

The driver behind each row is the trust boundary, not fashion: a first-party product controls both its application backend and browser client, so it can choose a session-cookie design and its CSRF contract together. API platforms can't control third-party client implementations — hence standardized OAuth2 flows (auth-code+PKCE for user delegation, client-credentials for machine-to-machine) and token lifecycles the platform must document and rotate. Internal tools can delegate primary authentication to a corporate IdP, while the application still owns local account state, authorization and sessions. Directory offboarding must propagate through SCIM or another lifecycle path, grant/session revocation and current permission checks; together they define the actual access window.

### Q38. "Where does authorization belong — gateway, service, or both?"

**30-sec:** The gateway can validate credentials and reject coarse route or scope violations. Each service still enforces authorization for the domain objects it owns. If identity is propagated in headers, the gateway must strip client-supplied copies and forward identity only over a trusted channel or in a verifiable internal assertion; services must authenticate that propagation and apply local policy. Name the owner and freshness rules for each decision.

### Q39. "Explain audience (`aud`) and issuer (`iss`) validation failures you've seen."

**30-sec:** Label the story as hypothetical unless you personally observed it: a token intended for API A is accepted by API B because B fails to check its audience, or a staging issuer is trusted in production. For each configured token profile, validate the signature using a trusted issuer key and allowed algorithm, then check required issuer and audience, token purpose and expiry. Enforce `nbf` when present and required by the profile. Validate transaction-specific claims such as OIDC nonce during login, and check optional claims only when the profile or policy relies on them.

 *Traps:* "How do you prove the boundary?" (test wrong issuer, audience, purpose, expiry, key and environment combinations against every verifier; one passing path is a bypass).

### Q40. "Final: give me your auth architecture in 60 seconds." *(elevator pitch)*

**Pitch template:** "I start from the clients, revocation objective, data boundaries and availability targets. For the browser I would choose a server session or a token flow based on deployment and scaling needs; for machine clients I would use narrowly scoped API keys or audience-restricted OAuth tokens with a defined rotation path. Services enforce object-level authorization, and tenant scope is carried from a server-authorized membership into every data path; I would add database row-level security if its operational model fits. I would define how credential compromise, IdP or session-store outage, permission changes and recovery behave, then test those boundaries."

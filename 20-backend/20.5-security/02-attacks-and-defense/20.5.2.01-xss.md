# XSS (Cross-Site Scripting)

A comment can be harmless while stored and execute later when a moderator page renders it. The security decision happens where that data reaches a browser parser.

## Definition

Cross-Site Scripting (XSS) is an injection vulnerability in which attacker-controlled content executes as script in a browser under the affected application's security context. Despite the name, the payload may be stored or reflected by the same site; the key boundary is that attacker-controlled code runs with the page's origin privileges. A script can inspect rendered page data and issue authenticated requests; stealing a cookie is not required.

> **Textbook Definition:** XSS occurs when untrusted content crosses an application-controlled boundary and the browser interprets it as executable script in the application's security context. Prevention depends on the output context and execution sink, not on a universal input filter.

## First Principles

A browser must distinguish page instructions from the data displayed by the page. It can make that distinction only from the syntax and context the application sends it.

1. **Trace the data flow.** Find the attacker-controlled source, any transformations and the final browser sink. A database, API response or client-side state does not make a value trusted.
2. **Respect the sink's grammar.** HTML text, attributes, URLs, JavaScript and CSS have different parsing rules. Encoding for one context does not protect a value placed into another.
3. **Choose the right output contract.** Render ordinary text through a framework's escaped binding or a text API. When users need rich HTML, sanitize it with a maintained HTML parser and a narrow policy.
4. **Layer browser controls after the primary fix.** Content Security Policy (CSP) and Trusted Types can reduce exploitability or unsafe sink use, but they do not replace safe rendering and sanitization.

## 1. Trace each source to its browser sink

| Form | Example path | What to inspect |
| --------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Stored | A comment is saved and later rendered in a moderator's page | The database value remains untrusted at every output sink. |
| Reflected | A search parameter is embedded into a server-generated HTML response | Encode for the exact response context or use a template that escapes it. |
| DOM-based | Client code copies a URL fragment into `innerHTML` | Follow browser-side sources and sinks even when the server never reflects the value. |

Stored and reflected describe how content is delivered; DOM-based describes how client code processes it. They can overlap. The security decision depends on the final parser or execution sink, not the label.

## 2. Choose output handling from the content contract

#### Untrusted strings must not enter an HTML parser

Both examples below treat an untrusted string as markup. Length or domain validation can reject invalid values, but it does not make a valid string safe for HTML parsing.

```typescript
function vulnerableSearchMarkup(query: string): string {
  return `<p>Search results for: ${query}</p>`; // unsafe if returned as text/html
}

function appendComment(container: Element, comment: string): void {
  container.innerHTML += `<p>${comment}</p>`; // parses comment as HTML
}
```

A value such as `<img src=x onerror=alert(1)>` can create executable markup in a page that uses the returned string or updates `innerHTML`.

#### Render plain text as text

```typescript
function appendPlainTextComment(container: Element, comment: string): void {
  const paragraph = document.createElement('p');
  paragraph.textContent = comment;
  container.append(paragraph);
}
```

For React, render a string as a normal child, such as `<p>{comment}</p>`; the framework escapes text. Avoid `dangerouslySetInnerHTML` unless the content has a deliberate sanitization contract. URL values still need scheme and destination validation: attribute escaping alone does not make `javascript:` a safe link.

#### Sanitize only when the product needs user-authored HTML

Use a maintained parser-based sanitizer rather than a regular expression. This server-side example allows a small set of formatting tags and no attributes:

```javascript
const createDOMPurify = require('dompurify');
const { JSDOM } = require('jsdom');
const window = new JSDOM('').window;
const purify = createDOMPurify(window);

function sanitizeComment(html) {
  if (typeof html !== 'string' || html.length > 10_000) {
    throw new TypeError('invalid comment');
  }
  return purify.sanitize(html, {
    ALLOWED_TAGS: ['p', 'strong', 'em', 'ul', 'li'],
    ALLOWED_ATTR: [],
  });
}
```

The sanitizer keeps allowed formatting and removes disallowed elements such as an image with an event handler. On Node.js, the DOM implementation is part of the security boundary: keep `jsdom` current, patch both dependencies, and do not use an untrusted DOM implementation. Render the sanitized result only in the intended HTML context.
Modifying it afterward or passing it through a transforming library can invalidate the sanitization result.

## 3. Select defenses for the content the product renders

- **Plain comments and profile fields:** store domain text in its normal form and escape it at each output boundary. Do not store an HTML-escaped version and later reuse it in a different context.
- **Rich text editors:** define the small set of tags and attributes the product supports, sanitize with a maintained parser, and regression-test both allowed formatting and hostile markup.
- **CSP rollout:** a nonce-based strict policy uses a fresh unpredictable nonce for each response and attaches it only to trusted scripts. A hash-based policy authorizes exact script content and can suit fixed inline scripts or static pages. Nonces require coordination with HTML generation and caching; hashes must be recalculated when the script changes. Start in report-only mode, fix violations, then enforce a policy tested against real page behavior.
- **DOM sink controls:** where the browser support matrix permits, `require-trusted-types-for 'script'` can require trusted values at covered DOM injection sinks. The application's Trusted Types policy must still perform safe transformation; the directive alone is not a sanitizer.

## Summary

XSS happens when a browser interprets attacker-controlled data as code in a page's security context. Render ordinary strings as text; sanitize intentionally supported HTML; validate URLs separately. CSP and Trusted Types add useful, support-dependent layers, while `HttpOnly` limits direct cookie access without preventing injected code from making authenticated requests.

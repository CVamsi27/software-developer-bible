# XSS (Cross-Site Scripting)


## Definition

Cross-Site Scripting (XSS) is a security vulnerability that allows attackers to inject malicious client-side scripts into web pages viewed by other users. When a victim views the affected page, the malicious script executes in their browser, enabling the attacker to steal data, hijack sessions, or perform actions on behalf of the user. XSS is one of the most common web vulnerabilities, consistently appearing in the OWASP Top 10.

> **Textbook Definition:** Cross-Site Scripting occurs when attacker-controlled content is interpreted as executable code in a victim's web security context. Prevention requires controlling dangerous output contexts and execution sinks, rather than treating all input filtering as equivalent.

## First Principles

XSS is derivable from one confusion the browser cannot resolve:

1. **Data and code share a channel.** HTML mixes both by design; when untrusted input re-enters the page as markup, the browser interprets it under that sink's parsing/execution rules; not every injected HTML fragment executes a script — it cannot know your intent. Every XSS is this boundary crossed: input → stored/transmitted → rendered as code.
2. **Context determines escaping, so one escape function is never enough.** HTML body, attribute, JS string, URL, CSS each have different dangerous characters — the senior insight is *context-aware output encoding* and letting frameworks auto-escape (React), escaping only the gaps.
3. **CSP is the seatbelt for when the boundary fails.** It cannot fix injection; it limits what injected code *reaches* (no inline, script allowlists) — defense in depth, not primary control. HttpOnly cookies cap the blast radius (token theft) the same way.

## Why Do We Need It?

- **Data Theft**: Attackers can steal cookies, session tokens, and personal information
- **Session Hijacking**: Stolen session cookies allow impersonation of users
- **Malware Distribution**: Injected scripts can redirect users to malicious sites
- **Phishing**: Modified pages can present fake login forms
- **Defacement**: Attackers can alter the appearance of web pages
- **Keylogging**: Injected scripts can record user keystrokes

## How It Works

### Follow the source to its execution sink

| Delivery | Concrete trace | Boundary to inspect |
| --------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Stored | A comment is saved, then a moderator's page renders it as HTML | Database storage does not make content trusted; inspect the output sink |
| Reflected | A search URL supplies text which the server embeds into its response | Encode for the actual response context |
| DOM-based | Browser code copies a URL fragment into `innerHTML` | The vulnerable sink can exist without the server reflecting that value |

Stored/reflected describe delivery; DOM-based describes client-side processing. They can overlap. A plain text comment stays harmless when assigned to `textContent`, while the same characters can become markup through `innerHTML`.

## Code Examples

### Vulnerable Code Examples

```typescript
// VULNERABLE: Server-generated HTML containing unencoded user text
app.get("/search", (req, res) => {
  const query = req.query.q as string;
  res.send(`
    <div>
      <p>Search results for: ${query}</p>
    </div>
  `);
});

// VULNERABLE: Template literal injection
app.get("/profile", (req, res) => {
  const name = req.query.name as string;
  res.send(`<h1>Welcome, ${name}!</h1>`);
});

// DANGEROUS: server-side eval is server code execution, not browser XSS
app.get("/calculate", (req, res) => {
  const expression = req.query.expr as string;
  const result = eval(expression); // Never do this!
  res.send(`Result: ${result}`);
});

// VULNERABLE: innerHTML in frontend JavaScript
function displayComment(comment: string) {
  const div = document.getElementById("comments");
  div.innerHTML += `<p>${comment}</p>`; // XSS vulnerability
}

```

### Plain text and permitted markup need different sinks

Keep normal text as text. In React, `<p>{text}</p>` escapes text content; in a browser DOM, `element.textContent = text` avoids HTML parsing. Neither makes a value safe inside every URL, script, style or `dangerouslySetInnerHTML` context. For an HTML **text-node** boundary, this complete helper emits encoded text:

```js
function htmlText(value) {
  if (typeof value !== 'string') throw new TypeError('text must be a string');
  const entities = { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' };
  return value.replace(/[&<>"']/g, char => entities[char]);
}
console.log(`<p>${htmlText('<img src=x onerror=alert(1)>')}</p>`);
// <p>&lt;img src=x onerror=alert(1)&gt;</p>
```

This is not a JavaScript/CSS/URL encoder. Validate URL schemes and destination policy before assigning links; do not construct executable script from untrusted strings. Store validated domain text in its original representation and encode at the output context, rather than storing an HTML escape that later gets double-encoded or placed in another syntax.

When the product intentionally permits rich HTML, sanitize with a maintained parser-based library. This complete server module uses DOMPurify with a maintained JSDOM version; it retains a small formatting allowlist and no link/image attributes:

```js
const createDOMPurify = require('dompurify');
const { JSDOM } = require('jsdom');
const window = new JSDOM('').window;
const purify = createDOMPurify(window);
function sanitizeComment(html) {
  if (typeof html !== 'string' || html.length > 10_000) throw new TypeError('invalid comment');
  return purify.sanitize(html, { ALLOWED_TAGS: ['p', 'strong', 'em', 'ul', 'li'], ALLOWED_ATTR: [] });
}
module.exports = { sanitizeComment };
```

Trace: a comment containing `<strong>Hello</strong><img src=x onerror=...>` retains the permitted emphasis and removes the image/handler. Reinterpreting or modifying the sanitized result can introduce a new unsafe sink, so render it only in the intended HTML context. Browser DOMPurify uses the browser's window; creating JSDOM inside a browser function mixes two different environments. Keep sanitizer and server DOM dependencies patched.

### CSP narrows execution, not the input contract

A restrictive Content Security Policy (**CSP**) can require per-response unpredictable script nonces or hashes and constrain resource loading. Attach the same freshly generated nonce to the allowed script tags and the response policy; a reusable/static nonce loses that boundary. Restrict `object-src`, `base-uri` and framing according to the application. Roll out with violation reports and test permitted scripts; a broad script allowlist can trust an exploitable JSONP/script host. The [web-security chapter](../03-hardening-and-operations/20.5.3.02-web-security.md) owns header configuration.

HttpOnly blocks direct cookie reads, while injected code can still read rendered data or issue authenticated requests. Framework escaping, HTML sanitization, URL validation and CSP solve different conditions; rate limits and generic input filters do not repair an executable sink.

## Common Mistakes

1. **Treating validation as rendering protection**: Validate domain rules, then use the correct text sink or sanitize deliberately permitted HTML

2. **Using innerHTML without sanitization**: Always sanitize or use textContent

3. **Not implementing CSP**: CSP is a critical defense layer

4. **Treating stored text as trusted**: Apply the required output protection where it is rendered; do not assume a past filter matches today's sink

5. **Using eval()**: Never use eval() with user input

6. **Not encoding output**: Always encode user data in HTML responses

7. **Using document.write()**: Avoid document.write() with dynamic content

8. **Ignoring DOM-based XSS**: Client-side scripts can be vulnerable too

## Best Practices

1. **Validate all input** on both client and server

2. **Choose the output contract**: encode plain text; sanitize deliberately permitted HTML

3. **Implement Content Security Policy (CSP)** with strict rules

4. **Use textContent** instead of innerHTML

5. **Use DOMPurify** for HTML sanitization

6. **Avoid executable contexts** and use their proper safe APIs; one HTML encoder does not cover CSS/JavaScript/URLs

7. **Use frameworks** that auto-escape (React, Angular, Vue)

8. **Test dangerous sinks** with hostile strings and permitted formatting; rate limits do not remove an injection flaw

9. **Use HTTPOnly cookies** for session tokens (limits XSS impact)
10. **Regular security audits** and penetration testing

## Summary

XSS is a critical web security vulnerability that allows attackers to inject malicious scripts. Key takeaways:

- Preserve data/code boundaries with context-specific rendering and trusted sanitizer configuration
- Use output encoding to prevent script execution
- Implement Content Security Policy (CSP)
- Use textContent instead of innerHTML
- Use DOMPurify for HTML sanitization
- Use frameworks with auto-escaping (React, Vue, Angular)
- Implement httpOnly cookies to limit XSS impact
- Regular security audits and penetration testing

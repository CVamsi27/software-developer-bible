# CSRF (Cross-Site Request Forgery)

A forged form can try to transfer money while its victim is signed in, even when the attacker cannot read the bank's response.

## Definition

**Cross-site request forgery (CSRF)** makes a victim's browser send an attacker-chosen request that a target application accepts using automatically attached credentials. The attacker need not steal the session cookie or read the response. The defect is accepting valid credentials as sufficient evidence that the request came through an authorized interaction.

> **Textbook Definition:** Cross-Site Request Forgery causes a browser to submit an attacker-chosen request with credentials automatically associated with a target site. The defense must distinguish an authorized state-changing request from one merely carrying valid credentials.

A CSRF attack tries to make the browser perform a state-changing operation with credentials the target site accepts. Safe retrievals must not change business state. The attack relies on browsers attaching eligible credentials under cookie, SameSite, browser and request-mode rules.

## First Principles

CSRF exploits a browser default, so every defense restores an explicit check:

1. **Credentials can accompany a request without the user's page selecting them.** A malicious form can submit to the target application; cookie eligibility determines whether it carries the session. This automatic credential attachment is called **ambient authority**. Checking that session alone does not establish the request's source.
2. **SameSite cookies restrict cross-site delivery, not exact origin.** SameSite=Lax generally withholds cookies on cross-site unsafe requests while permitting some top-level safe navigations; Strict withholds more cross-site requests. Defaults and compatibility details vary, and same-site sibling origins are not the same as same-origin requests.
3. **Anti-CSRF tokens bind the request to a trusted page/session context**: an external site normally cannot read the legitimate page's token under the same-origin policy (SOP, → 20.5.2.01). Requiring that token adds evidence the request passed through the application's trusted client path. Origin/Referer checks add a browser-source signal under an explicit missing-header policy. These controls do not prove human intent, and same-origin XSS can issue authenticated requests. CSP can reduce script-injection risk but does not prove that a request came from an authorized interaction.

## Trace the browser's automatic authority

1. A user signs in to `bank.example`; the bank sets a session cookie.
2. A malicious page submits a form to the bank's transfer endpoint.
3. Browser cookie rules decide whether the session cookie accompanies that request.
4. If the bank checks only the session, the maliciously initiated request can pass.

The same-origin policy usually prevents the malicious page from reading the bank's response. It does not prevent every form submission. Cross-Origin Resource Sharing (**CORS**) governs browser response access and preflight-gated requests; it is not a replacement for authorizing a cookie-authenticated mutation. A different subdomain is a different origin but may still be the same site, so SameSite and exact-origin checks answer different questions.

## Build one end-to-end request proof

### Vulnerable Code

```typescript
// VULNERABLE: No CSRF protection on state-changing endpoint
app.post("/api/transfer", async (req, res) => {
  const { to, amount } = req.body;
  const userId = req.session.userId;

  // Attacker can force user to make this transfer
  await db.transfer(userId, to, amount);
  res.json({ success: true });
});

// VULNERABLE: GET request for state-changing operation
app.get("/api/delete-account", async (req, res) => {
  const userId = req.session.userId;
  await db.deleteUser(userId);
  res.json({ success: true });
});

```

### Choose one token contract end to end

A **synchronizer token** is an unpredictable value retained in the server session and echoed by the legitimate page. The [session chapter](../01-auth/20.5.1.04-sessions-cookies.md) contains a complete login/CSRF/logout flow. Do not mix its token issuer with a different cookie validator.

A naive **double-submit cookie** compares a cookie with a request header. If an attacker can inject a matching cookie (for example through a sibling-domain boundary), equality alone can pass. A signed double-submit token binds that value to the server's current session identity. This complete Node helper verifies both the echoed cookie and its HMAC binding; it expects a currently valid server-issued session ID, not a caller-supplied identifier:

```js
const { randomBytes, createHmac, timingSafeEqual } = require('node:crypto');
function createSignedCsrf(key) {
  if (!Buffer.isBuffer(key) || key.length < 32) throw new Error('provision 32 random key bytes');
  const sessionShape = id => typeof id === 'string' && id.length > 0 && id.length <= 1024;
  const mac = (id, nonce) => createHmac('sha256', key)
    .update(JSON.stringify([id, nonce])).digest();
  function issue(sessionId) {
    if (!sessionShape(sessionId)) throw new TypeError('invalid session id');
    const nonce = randomBytes(32).toString('hex');
    return `${nonce}.${mac(sessionId, nonce).toString('hex')}`;
  }
  function verify(sessionId, cookieToken, headerToken) {
    const shape = token => typeof token === 'string' && /^[a-f0-9]{64}\.[a-f0-9]{64}$/.test(token);
    if (!sessionShape(sessionId) || !shape(cookieToken) || !shape(headerToken)) return false;
    if (!timingSafeEqual(Buffer.from(cookieToken), Buffer.from(headerToken))) return false;
    const [nonce, signature] = headerToken.split('.');
    return timingSafeEqual(Buffer.from(signature, 'hex'), mac(sessionId, nonce));
  }
  return { issue, verify };
}
module.exports = { createSignedCsrf };
```

Trace: session A receives token T in a host-only readable CSRF cookie; the page sends T in `X-CSRF-Token`. The server first validates session A, then verifies cookie/header equality and its session-bound MAC. A token issued for attacker session B fails for A even if the attacker plants matching cookie/header text. Malformed or unequal-length values return false rather than crashing a timing-safe comparison.

### Wire transport before the protected mutation

Set the CSRF cookie with `Secure`, `Path=/`, an appropriate `SameSite`, no `Domain`, and—where supported—the `__Host-` prefix. It is readable when JavaScript must copy it; the authentication cookie remains HttpOnly. Serve the token only under the intended same-origin/session contract and avoid logging it. Protect unsafe cookie-authenticated methods and login/session transitions; GET/HEAD must not cause business state changes. Renew the token on session rotation, and enforce validity through the server session. Per-request single-use tokens are optional and can complicate retries/back navigation.

A same-origin browser client reads the agreed token source and sends exactly that header with `credentials: 'same-origin'`. Check the token-fetch response status, handle logout/session rotation, and disable submission until a usable token exists. For cross-origin clients, define explicit credential/CORS/origin rules instead of assuming CORS blocks ordinary HTML forms. Serve the flow over HTTPS; `Secure` limits cookie transmission to secure connections but does not protect other request data by itself.

Origin/Referer validation, Fetch Metadata headers and SameSite provide additional controls. Compare a parsed exact origin with trusted configuration; suffix/string-prefix tests are unsafe, and missing headers need a documented policy. A BFF's opaque cookie still needs CSRF defenses. A bearer header explicitly supplied by application code does not normally carry ambient authority, but a cookie storing that token does.

## Summary

CSRF exploits automatic credentials on an attacker-chosen request. Keep GET/HEAD safe, protect unsafe cookie-authenticated operations and login transitions with one complete CSRF contract, and use SameSite and trusted-origin checks with explicit policies. A signed double-submit token must bind to the validated session; neither cookie/header equality, CORS nor a POST method alone establishes legitimate initiation. Test sibling origins, session rotation, malformed tokens and missing-header behavior.

# CSRF (Cross-Site Request Forgery)

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Cross-Site Request Forgery (CSRF) is a web security vulnerability that forces an authenticated user to execute unwanted actions on a web application in which they're authenticated. Unlike XSS, which injects malicious scripts, CSRF tricks the user's browser into making unintended requests using the user's existing session. The attacker exploits the trust that a site has in the user's browser.

> **Textbook Definition:** Cross-Site Request Forgery causes a browser to submit an attacker-chosen request with credentials automatically associated with a target site. The defense must distinguish an authorized state-changing request from one merely carrying valid credentials.

CSRF attacks target state-changing operations (not data retrieval) and rely on the fact that browsers attach eligible credentials under cookie, SameSite, browser and request-mode rules.

## First Principles

CSRF exploits a browser default, so every defense restores an explicit check:

1. **The browser attaches cookies automatically.** evil.com's form POSTing to your-bank.com rides the user's session — the server sees a perfectly authenticated request it never should have honored. The vulnerability is *ambient authority*: who-sent-this is unproven.
2. **SameSite cookies restrict cross-site delivery, not exact origin.** Lax/Strict simply stop sending cookies on cross-site posts — same-site sibling origins, permitted top-level navigations and browser compatibility are why tokens still matter.
3. **Anti-CSRF tokens bind the request to a trusted page/session context**: the attacker cannot read your page's token (SOP, → 20.5.2.01), so requiring a random per-session value restores "the user's page initiated this." Origin/Referer checks provide another browser-source signal under an explicit missing-header policy. Neither establishes human intent after XSS. Defense is layered because the vulnerability is structural.

## Why Do We Need It?

- **Session Hijacking**: Attackers can perform actions using the victim's authenticated session
- **State Changes**: CSRF can trigger unwanted state changes (transfers, password changes, account modifications)
- **Financial Impact**: Can lead to unauthorized transactions or purchases
- **Reputation Damage**: Users may lose trust in the application
- **Compliance Violations**: May violate security standards (PCI DSS, GDPR)

## How It Works

### Trace the browser's automatic authority

1. A user signs in to `bank.example`; the bank sets a session cookie.
2. A malicious page submits a form to the bank's transfer endpoint.
3. Browser cookie rules decide whether the session cookie accompanies that request.
4. If the bank checks only the session, the maliciously initiated request can pass.

The same-origin policy usually prevents the malicious page from reading the bank's response. It does not prevent every form submission. Cross-Origin Resource Sharing (**CORS**) governs browser response access and preflight-gated requests; it is not a replacement for authorizing a cookie-authenticated mutation. A different subdomain is a different origin but may still be the same site, so SameSite and exact-origin checks answer different questions.

## Code Examples

### Vulnerable Code

```typescript
// VULNERABLE: No CSRF protection on state-changing endpoint
app.post("/api/transfer", async (req, res) => {
  const { to, amount } = req.body;
  const userId = req.session.userId;

  // Attacker can force user to make this transfer
  await db.transfer(userId, to, amount);
  res.json({ success: true });
});

// VULNERABLE: GET request for state-changing operation
app.get("/api/delete-account", async (req, res) => {
  const userId = req.session.userId;
  await db.deleteUser(userId);
  res.json({ success: true });
});

```

### Choose one token contract end to end

A **synchronizer token** is an unpredictable value retained in the server session and echoed by the legitimate page. The [session chapter](../01-auth/20.5.1.04-sessions-cookies.md) contains a complete login/CSRF/logout flow. Do not mix its token issuer with a different cookie validator.

A naive **double-submit cookie** compares a cookie with a request header. If an attacker can inject a matching cookie (for example through a sibling-domain boundary), equality alone can pass. A signed double-submit token binds that value to the server's current session identity. This complete Node helper verifies both the echoed cookie and its HMAC binding; it expects a currently valid server-issued session ID, not a caller-supplied identifier:

```js
const { randomBytes, createHmac, timingSafeEqual } = require('node:crypto');
function createSignedCsrf(key) {
  if (!Buffer.isBuffer(key) || key.length < 32) throw new Error('provision 32 random key bytes');
  const sessionShape = id => typeof id === 'string' && id.length > 0 && id.length <= 1024;
  const mac = (id, nonce) => createHmac('sha256', key)
    .update(JSON.stringify([id, nonce])).digest();
  function issue(sessionId) {
    if (!sessionShape(sessionId)) throw new TypeError('invalid session id');
    const nonce = randomBytes(32).toString('hex');
    return `${nonce}.${mac(sessionId, nonce).toString('hex')}`;
  }
  function verify(sessionId, cookieToken, headerToken) {
    const shape = token => typeof token === 'string' && /^[a-f0-9]{64}\.[a-f0-9]{64}$/.test(token);
    if (!sessionShape(sessionId) || !shape(cookieToken) || !shape(headerToken)) return false;
    if (!timingSafeEqual(Buffer.from(cookieToken), Buffer.from(headerToken))) return false;
    const [nonce, signature] = headerToken.split('.');
    return timingSafeEqual(Buffer.from(signature, 'hex'), mac(sessionId, nonce));
  }
  return { issue, verify };
}
module.exports = { createSignedCsrf };
```

Trace: session A receives token T in a host-only readable CSRF cookie; the page sends T in `X-CSRF-Token`. The server first validates session A, then verifies cookie/header equality and its session-bound MAC. A token issued for attacker session B fails for A even if the attacker plants matching cookie/header text. Malformed or unequal-length values return false rather than crashing a timing-safe comparison.

### Wire transport before the protected mutation

Set the CSRF cookie with `Secure`, `Path=/`, an appropriate `SameSite`, no `Domain`, and—where supported—the `__Host-` prefix. It is readable when JavaScript must copy it; the authentication cookie remains HttpOnly. Serve the token only under the intended same-origin/session contract and avoid logging it. Protect unsafe cookie-authenticated methods and login/session transitions; GET/HEAD must not cause business state changes. Renew the token on session rotation, and enforce validity through the server session. Per-request single-use tokens are optional and can complicate retries/back navigation.

A same-origin browser client reads the agreed token source and sends exactly that header with `credentials: 'same-origin'`. Check the token-fetch response status, handle logout/session rotation, and disable submission until a usable token exists. For cross-origin clients, define explicit credential/CORS/origin rules instead of assuming CORS blocks ordinary HTML forms.

Origin/Referer validation, Fetch Metadata headers and SameSite provide additional controls. Compare a parsed exact origin with trusted configuration; suffix/string-prefix tests are unsafe, and missing headers need a documented policy. A BFF's opaque cookie still needs CSRF defenses. A bearer header explicitly supplied by application code does not normally carry ambient authority, but a cookie storing that token does.

## Common Mistakes

1. **Using GET for state-changing operations**: GET/HEAD must be safe (no requested business state change); use POST for state changes

2. **Leaving cookie-authenticated mutations unprotected**: Check the chosen CSRF contract on every unsafe method

3. **Using SameSite=None without CSRF tokens**: SameSite cookies don't protect all scenarios

4. **Not validating CSRF tokens**: Must validate on every state-changing request

5. **Confusing CSRF and authentication secrets**: A JavaScript-read token cannot live solely in an HttpOnly cookie; use the selected session/DOM/readable-cookie transport, while protecting bearer credentials separately

6. **Classifying protection by endpoint name**: A cookie-authenticated API can have ambient authority; an explicitly supplied bearer header normally does not

7. **Using predictable CSRF tokens**: Always use cryptographically random tokens

8. **Undefined rotation/retry policy**: Session-bound tokens can be reused during that session; per-request one-use tokens require retry and navigation design

## Best Practices

1. **Use SameSite cookies** (Strict or Lax) as first line of defense

2. **Implement CSRF tokens** for all state-changing operations

3. **Choose synchronizer or signed session-bound double submit**; naive cookie/header equality is insufficient under cookie injection

4. **Validate CSRF tokens** with timing-safe comparison

5. **Use appropriate unsafe methods** (POST/PUT/PATCH/DELETE), protecting each cookie-authenticated mutation

6. **Bind lifetime to the validated session/transaction**, with any additional expiry explicitly checked

7. **Rotate CSRF tokens** after login/logout

8. **Implement Content Security Policy** to limit script execution

9. **Use HTTPS** to prevent token interception
10. **Validate Origin and Referer headers** as additional protection

## Summary

CSRF is a serious web security vulnerability that exploits the trust between a user's browser and web application. Key takeaways:

- Always use SameSite cookies as first line of defense
- Protect cookie-authenticated mutations with a coherent CSRF contract
- Use POST for all state-changing operations
- Validate Origin and Referer headers
- Use one coherent synchronizer or signed double-submit contract
- Rotate and expire CSRF tokens
- Test for CSRF vulnerabilities regularly

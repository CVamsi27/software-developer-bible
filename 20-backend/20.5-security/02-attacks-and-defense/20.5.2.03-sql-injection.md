# SQL Injection

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

SQL Injection (SQLi) is a code injection technique that exploits security vulnerabilities in an application's database layer. It occurs when untrusted values become executable query syntax rather than bound data. Input filtering alone is not a sound separation. SQL injection allows attackers to execute arbitrary SQL code, potentially accessing, modifying, or deleting data. It consistently ranks in the OWASP Top 10 as one of the most critical web application security risks.

> **Textbook Definition:** SQL injection occurs when untrusted values alter the structure of an executed SQL statement. Parameter binding separates values from syntax; dynamic identifiers and fragments require separate allowlisted construction.

## First Principles

SQL injection is the same data/code confusion as XSS (→ 20.5.2.01), in a different channel:

1. **String-concatenated queries make user input executable.** The query planner receives `... WHERE name = '' OR '1'='1'` as *SQL* — it cannot distinguish your intent from attacker syntax. This is structural, not sloppiness: interpolation *is* the vulnerability.
2. **Parameterized queries fix it by construction.** Values travel as typed parameters the parser never reinterprets — data cannot become code. This is why "use prepared statements" is not one mitigation among many but *the* fix; escaping is the fallback for the few places parameters can't reach (identifiers, ORDER BY direction — validate against allowlists).
3. **The blast radius is capped by privilege design.** An injected statement executes with the app's DB user's powers — least privilege, no superuser, RLS can restrict reach only with the right role/context and policies; an attacker may still abuse permitted operations or change user-controlled context.

## Why Do We Need It?

- **Data Breach**: Attackers can access sensitive data (user records, passwords, financial data)
- **Data Modification**: Attackers can insert, update, or delete records
- **Authentication Bypass**: Attackers can bypass login systems
- **Server Compromise**: In some cases, attackers can execute operating system commands
- **Regulatory Violations**: SQLi breaches can violate GDPR, HIPAA, PCI DSS
- **Reputational Damage**: Data breaches destroy user trust

## How It Works

### Trace syntax, rather than just suspicious characters

A concatenated login query such as `WHERE username='admin' --' AND password='...'` can comment out the password predicate. Binding the supplied username as a value prevents it from becoming that syntax. The database role still determines which operations an injected statement could reach.

An attacker may observe returned rows (**in-band**), infer data through differences in errors or timing (**blind**), or use a permitted outbound database channel (**out-of-band**). These observation methods do not change the required syntax/data separation. **Second-order injection** occurs when stored input becomes executable syntax in a later report or job; parameterize that later boundary too.

## Code Examples

### Vulnerable Code

```typescript
// VULNERABLE: Direct string concatenation
app.post("/login", async (req, res) => {
  const { username, password } = req.body;
  const query = `SELECT * FROM users WHERE username='${username}' AND password='${password}'`;
  const result = await db.query(query);
  // Attacker can input: username = admin' --
});

// VULNERABLE: Template literal
app.get("/users", async (req, res) => {
  const { id } = req.query;
  const query = `SELECT * FROM users WHERE id = ${id}`;
  const result = await db.query(query);
});

// VULNERABLE: LIKE clause
app.get("/search", async (req, res) => {
  const { term } = req.query;
  const query = `SELECT * FROM products WHERE name LIKE '%${term}%'`;
  const result = await db.query(query);
});

```

### Bind values while keeping query structure trusted

This complete builder returns a PostgreSQL query object for a `pg` client. The chosen column/direction come from fixed allowlists; the user's search text remains a parameter. The trusted tenant ID comes from validated request context. `%` and `_` are escaped so this example searches literal substrings rather than treating input as a wildcard pattern.

```js
function buildProductSearch({ tenantId, term, sort = 'name', direction = 'asc', limit = 20 }) {
  if (typeof tenantId !== 'string' || !tenantId || typeof term !== 'string' || term.length > 200 ||
      !Number.isInteger(limit) || limit < 1 || limit > 100) throw new TypeError('invalid search');
  const columns = new Map([['name', 'name'], ['price', 'price_minor']]);
  const directions = new Map([['asc', 'ASC'], ['desc', 'DESC']]);
  const column = columns.get(sort), order = directions.get(direction);
  if (!column || !order) throw new Error('unsupported sort');
  const literal = term.replace(/[!%_]/g, char => `!${char}`);
  return { text: `SELECT id, name, price_minor FROM products
    WHERE tenant_id = $1 AND name ILIKE $2 ESCAPE '!'
    ORDER BY ${column} ${order}, id ${order} LIMIT $3`,
    values: [tenantId, `%${literal}%`, limit] };
}
module.exports = { buildProductSearch };
```

An input such as `x' OR 1=1 --` is carried in `values[1]`, not appended to the SQL grammar. A requested sort such as `name; DROP TABLE products` is rejected before a query is built. Parameters cannot normally substitute table/column names or SQL keywords; interpolation is appropriate only for the trusted fragments selected above. Identifier quoting does not itself authorize access to every valid identifier.

### Parameterization does not make password storage safe

For login, bind a username/account identifier, retrieve its stored adaptive password hash, then verify through Argon2id/bcrypt/scrypt under the [authentication contract](../01-auth/20.5.1.01-auth-fundamentals.md). `WHERE password = $2` can avoid SQL injection while still storing/comparing plaintext passwords, which is a separate severe flaw. Use consistent unknown-account work and bound expensive attempts.

### ORM and stored-procedure boundaries

Ordinary ORM methods parameterize values, but raw concatenation, unsafe raw APIs, or fabricated tagged-template objects can restore injection. Prisma's genuine `$queryRaw` tagged interpolation binds values; it cannot safely bind a dynamic identifier. Construct supported filters explicitly rather than passing caller-selected field names/operators to a broad `where` object. A parameterized `isAdmin` update is still mass assignment if the caller lacked permission.

Stored procedures can also inject through internally concatenated dynamic SQL. Parameterize values inside the procedure and allowlist identifiers before database-specific quoting (for example SQL Server `QUOTENAME`). PostgreSQL `$1` syntax, MySQL placeholders and SQL Server parameters are different adapter contracts; do not paste a procedure from one dialect into another.

Second-order injection uses data already stored in a database as a later syntax fragment. The source being your own table does not make it trusted query grammar. Apply value binding at every execution boundary, including reports, exports and administrative jobs.

## Common Mistakes

1. **Using string concatenation**: Never concatenate user input into SQL

2. **Not using parameterized queries**: Always use prepared statements

3. **Trusting user input**: Validate and sanitize all input

4. **Using ORM raw queries unsafely**: Even with ORMs, raw queries need parameterization

5. **Not validating data types**: Validate input types before using in queries

6. **Unrestricted dynamic identifiers**: Select identifiers/operators from an authorized allowlist; quoting alone does not limit data access

7. **Granting excessive database privileges**: Use least privilege principle

8. **Not monitoring database queries**: Log and monitor for suspicious queries

## Best Practices

1. **Use parameterized queries** for all database operations

2. **Use ORM** (Prisma, TypeORM, Sequelize) for automatic parameterization

3. **Validate input types** and formats before using in queries

4. **Implement least privilege** for database accounts

5. **Use stored procedures** with parameters

6. **Implement input validation** with allowlists

7. **Use Web Application Firewalls** (WAF) for additional protection

8. **Regular security audits** and penetration testing

9. **Monitor database queries** for suspicious patterns
10. **Keep database software** up to date

## Summary

SQL Injection is a critical vulnerability that can lead to complete data compromise. Key takeaways:

- Always use parameterized queries
- Use ORMs (Prisma) for automatic parameterization
- Validate domain types and bind values; select dynamic syntax from authorized allowlists
- Implement least privilege for database accounts
- Monitor database queries for suspicious patterns
- Conduct regular security audits and penetration testing
- Keep database software up to date

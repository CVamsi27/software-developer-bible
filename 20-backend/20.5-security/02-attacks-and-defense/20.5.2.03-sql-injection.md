# SQL Injection

## Definition

SQL injection (SQLi) is a code-injection flaw in which attacker-controlled input changes the grammar or structure of a SQL statement the application executes. It arises when code builds query text by concatenating untrusted values instead of passing them through a parameter-binding interface. A quote or punctuation mark is not itself the vulnerability; the failure is allowing data to become executable SQL syntax.

> **Textbook Definition:** SQL injection occurs when untrusted input changes the structure or meaning of an executed SQL statement because the application fails to keep that input separate from SQL syntax.

## First Principles

A SQL statement has a grammar, and values occupy positions within that grammar. If an application joins both into one string before execution, the database parses the resulting text without knowing which part the author meant as data.

1. **String construction loses the boundary.** An email value containing a quote and `OR` can close a quoted literal and add a predicate when it is interpolated into SQL text.
2. **Binding preserves the boundary.** A correctly used driver or query API sends the statement structure separately from parameter values, so SQL-looking characters in a value remain data.
3. **Placeholders represent values, not grammar.** A parameter usually cannot stand for a table name, column name, operator or `ASC`/`DESC` keyword. Select such fragments from fixed, application-owned allowlists or redesign the query.
4. **Database privileges limit impact, not the injection flaw.** The injected statement runs with the connection role's authority. Least privilege and row-level security can reduce reach when roles, policies and context are configured correctly, but they do not replace binding.

## Why It Matters

Consider a search built as `SELECT ... WHERE email = '${email}'`. If the supplied value closes the quote and adds `OR TRUE`, the database receives a different predicate than the developer intended. The returned rows and possible writes depend on the rest of the statement and the connection role; SQL injection does not automatically grant operating-system access or database-superuser privileges.

Parameter binding prevents that syntax change. It does not authorize the requested record: a bound `userId` can still be chosen by an unauthorized caller. Keep query-construction safety separate from tenant, ownership and operation checks.

## How It Works

Trace the value from its source to the database execution call. The risky boundary can be in an HTTP handler, an ORM escape hatch, a report job, a stored procedure or a later query that reuses previously stored data.

| Query construction | Outcome | Required control |
| --------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| User value concatenated into SQL text | The database can parse the value as syntax | Replace concatenation with a binding API. |
| User value passed in a bound parameter | The value remains data | Still enforce authorization, validation and resource limits. |
| User choice becomes a column or sort keyword | The choice changes query grammar | Map a small public enum to fixed SQL fragments. |
| Stored text is concatenated by a later report | Previously accepted data becomes executable syntax | Bind at every execution boundary, including background jobs. |

Attackers may observe results directly, infer them through response differences or timing, or use an available database output channel. These are observation paths; each still depends on the application's query-construction flaw. A WAF may recognize some payloads, but it cannot reliably repair unsafe query construction.

## Code Examples

### Concatenation allows data to change the predicate

```javascript
function findUserByEmail(email) {
  const sql = `SELECT id, email FROM users WHERE email = '${email}'`;
  return db.query(sql);
}
```

With `email = "victim@example.com' OR '1'='1"`, the resulting text contains an additional predicate. Input validation may reject values that violate the email domain, but validation alone is not the code/data boundary.

### Bind values and allowlist query fragments

This PostgreSQL example uses the `pg` query-object contract. The tenant ID must come from verified server-side membership, not a caller-selected tenant field. User text is bound; the sort column and direction are selected from fixed maps. The `LIKE` escape rule keeps `%`, `_` and `!` literal for a literal-substring search.

```javascript
function buildProductSearch({ tenantId, term, sort = 'name', direction = 'asc', limit = 20 }) {
  if (typeof tenantId !== 'string' || !tenantId || typeof term !== 'string' || term.length > 200 ||
      !Number.isInteger(limit) || limit < 1 || limit > 100) throw new TypeError('invalid search');
  const columns = new Map([['name', 'name'], ['price', 'price_minor']]);
  const directions = new Map([['asc', 'ASC'], ['desc', 'DESC']]);
  const column = columns.get(sort), order = directions.get(direction);
  if (!column || !order) throw new Error('unsupported sort');
  const literal = term.replace(/[!%_]/g, char => `!${char}`);
  return {
    text: `SELECT id, name, price_minor FROM products
      WHERE tenant_id = $1 AND name ILIKE $2 ESCAPE '!'
      ORDER BY ${column} ${order}, id ${order} LIMIT $3`,
    values: [tenantId, `%${literal}%`, limit],
  };
}
module.exports = { buildProductSearch };
```

An input such as `x' OR 1=1 --` stays in `values[1]`. A sort choice such as `name; DROP TABLE products` is rejected before SQL is built. The returned object can be passed directly to a `pg` client; the database call should still use the query builder's tenant and pagination contract. Binding also does not make `%` and `_` literal in a `LIKE` pattern by itself; the example escapes them because its product behavior promises literal substring matching.

### ORM and stored-procedure boundaries

Query-builder methods generally bind values, but a raw-SQL API can be used safely or unsafely depending on how it is called. Prisma ORM v6's genuine `$queryRaw` tagged-template interpolation binds values; placeholders cannot substitute identifiers. Do not convert user input into a raw SQL fragment or use an unsafe API with concatenated input. Check the documentation for the Prisma version actually installed.

Stored procedures have the same boundary. A procedure that concatenates parameters into dynamic SQL is still vulnerable; bind values inside it and allowlist grammar fragments. Quoting an identifier prevents syntax break-out only when performed correctly for that database, and it does not authorize a caller to read every valid table or column.

Parameterization also does not solve mass assignment. A safe bound `UPDATE users SET is_admin = $1` remains an authorization flaw if the caller may not change that property. Likewise, a safely bound query can still return another tenant's row if its access predicate is missing or untrusted.

## Common Mistakes

- Treating a type check, email validator, sanitizer or WAF as a substitute for binding values.
- Assuming ORM use makes every raw query, dynamic SQL fragment or stored procedure safe.
- Trying to bind an identifier or keyword with a value placeholder, or accepting arbitrary identifiers from a caller.
- Assuming a parameterized `LIKE` value treats `%` and `_` as literal characters.
- Treating least privilege or row-level security as proof that the query is safe or correctly scoped.
- Logging passwords, tokens or full sensitive query parameters while investigating injection attempts.

## Best Practices

1. Use the database driver's parameter-binding API for every value in a dynamic query.
2. Keep query structure static. For a dynamic sort, filter or report column, map a small public choice to a fixed SQL fragment.
3. Test hostile values and cross-tenant IDs; verify they cannot change query structure or widen the authorized result set.
4. Give each application workload only the database privileges it needs. Treat RLS as a separately tested defense in depth.
5. Review ORM raw-query and stored-procedure paths; bind values within each layer that executes SQL.
6. Escape SQL pattern metacharacters only when the product promises literal `LIKE`/`ILIKE` matching; pattern matching and SQL injection are separate behaviors.
7. Bound result size, statement time and expensive search patterns. Parameterization protects query syntax, not database capacity.
8. Use a WAF only as an additional detection/filtering layer, never as the fix for unsafe SQL construction.

## Summary

SQL injection lets data alter executed SQL because the application combines untrusted values with query grammar. Bind values through the driver's supported API; construct identifiers and keywords from fixed allowlists. Then enforce tenant/object authorization and least privilege separately, since safe SQL syntax does not make a query authorized or inexpensive.

# API Security Best Practices & OWASP API Top 10

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

API security is the discipline of designing, building, and operating HTTP APIs that resist the OWASP API Security Top 10 (2023) — BOLA, broken authentication, broken object-property-level authorization, unrestricted resource consumption, broken function-level authorization, server-side request forgery, security misconfiguration, unrestricted access to sensitive business flows, improper inventory management, and unsafe consumption of APIs. The senior approach is **secure by default** — authn/authz/validation are global middleware, not per-endpoint afterthoughts.

> **Textbook Definition:** API security enforces access, input and resource-use policies at network and application boundaries. Correct enforcement binds permissions to the particular operation, object and properties rather than relying on authentication alone.

## First Principles

API security is the composition of the boundary facts from every preceding chapter:

1. **Every request is untrusted input plus a claim.** Authentication establishes a verified identity; authorization checks it against the resource; input validation assumes the payload is hostile. An API that skips any one layer trusts something it shouldn't.
2. **Fail predictably and leak nothing.** Error responses are attacker reconnaissance — uniform error shapes, no stack traces, rate limiting to slow enumeration, logging with correlation IDs for forensics. Security logging exists because attacks are campaigns, not single requests.
3. **The perimeter is the API itself.** There is no "internal" network to trust (zero trust) — protected operations authenticate callers, every boundary validates input, and responses expose only authorized properties (over-fetching leaks data by volume).

## Why Do We Need It?

Changing `/orders/123` to `/orders/124` is a valid HTTP request. Authentication can establish who sent it without establishing whether that person may read order 124. The application must join the verified identity, trusted tenant context, stored ownership and requested operation before returning data.

Automation introduces a separate problem: a correctly authorized purchase can still be abused to reserve every available ticket. Resource limits protect infrastructure; business-flow limits protect the product's rules. Neither substitutes for object authorization.

## How It Works

### The OWASP API Security Top 10 (2023)

| # | Risk | What it looks like in production |
| ----- | --------------------------------------------------- | --------------------------------------------------------------- |
| API1 | **Broken Object Level Authorization (BOLA)** | `GET /orders/123` returns any user's order by changing the id |
| API2 | **Broken Authentication** | Weak JWT, no key rotation, brute-forceable passwords, alg=none |
| API3 | **Broken Object Property Level Authorization** | `PATCH /users/1` with `{ "isAdmin": true }` escalates role |
| API4 | **Unrestricted Resource Consumption** | No rate limit, no body size limit, no query result limit |
| API5 | **Broken Function Level Authorization** | `POST /admin/users` accessible to non-admin role |
| API6 | **Unrestricted Access to Sensitive Business Flows** | Scripted ticket scalping, mass account creation |
| API7 | **Server Side Request Forgery (SSRF)** | `POST /fetch { url: "http://169.254.169.254/..." }` |
| API8 | **Security Misconfiguration** | Verbose errors, default creds, permissive CORS, missing headers |
| API9 | **Improper Inventory Management** | `/v1/` deprecated but still public; staging env exposed |
| API10 | **Unsafe Consumption of APIs** | Trusting 3rd-party API responses without validation |

## Code Examples

### Scope the read before projecting its response

This is a repository-contract sketch: `identity` comes from verified credentials and current membership, and the repository binds values instead of assembling SQL strings.

```typescript
async function readOrder(id: string, identity: VerifiedIdentity) {
  const order = await repository.findOne({
    id, tenantId: identity.tenantId, ownerId: identity.subject,
  });
  if (!order) throw new NotFoundException();
  return { id: order.id, status: order.status, totalMinor: order.totalMinor };
}
```

An order belonging to another tenant cannot match this query, even when its identifier is guessed. The projection then prevents internal notes or payment metadata from leaking. Administrators and delegated staff need an explicit alternative policy; ownership is not the only legitimate access model. Returning 404 can reduce object enumeration, but use a consistent documented error policy rather than claiming it hides every side channel.

### Operation and property permissions are independent

A role guard must run after authentication, resolve both class and handler metadata, and deny a protected route with missing policy. A role named `admin` does not automatically confer access to every tenant. The complete role-graph example lives in [RBAC](../01-auth/20.5.1.09-rbac-abac.md).

A valid email update does not authorize a role change. Parse only the fields supported by this operation, reject unsupported properties when appropriate, then construct the persistence update explicitly. A privileged role-change endpoint must authorize its own operation, target tenant and allowed transition. Response-property authorization matters too: hiding a field in a request DTO does not remove it from the returned row.

### Reduce SSRF by removing caller-selected destinations

Server-side request forgery (SSRF) occurs when an attacker influences where the server connects, using the server's network position or credentials. Prefer an opaque partner identifier over an arbitrary URL. This complete Node.js helper constructs a fixed endpoint; it does **not** perform a fetch or claim to secure a general URL proxy.

```javascript
function partnerProfileUrl(id) {
  if (typeof id !== 'string' || !/^[A-Za-z0-9_-]{1,64}$/.test(id)) {
    throw new TypeError('invalid partner profile id');
  }
  return new URL(`/v1/profiles/${id}`, 'https://api.partner.example').href;
}
```

`alice_42` selects a path on the configured partner origin. A value such as `https://127.0.0.1` is rejected rather than becoming a destination. Keep the origin in trusted deployment configuration and prevent callers from overriding it.

If the product genuinely accepts URLs, apply protocol/host/port allowlists, reject credentials in URLs, and enforce permitted addresses **at connection time**, including IPv6 and IPv4-mapped addresses. A preliminary DNS lookup followed by an independent `fetch` lookup has a time-of-check/time-of-use gap. Disable redirects or validate every redirect and destination through the same connector policy. Deny internal/metadata networks with egress controls, and bound connection time, total deadline and streamed response bytes. Validate the response schema before using it. A regular expression listing several private prefixes is not a complete network policy.

### Rate Limiting Per Route (NestJS `@nestjs/throttler`)

```typescript
// app.module.ts
// Module recipe: register ThrottlerGuard through APP_GUARD as well.
ThrottlerModule.forRoot([{ name: 'default', ttl: 60_000, limit: 100 }]),

// login.controller.ts
@Post('login')
@Throttle({ default: { limit: 5, ttl: 60_000 } }) // 5/min per IP
async login(@Body() dto: LoginDto) { ... }
```

### Body limits must apply before parsing

```typescript
// main.ts
// Nest with Express: disable the default parser at creation first.
const app = await NestFactory.create(AppModule, { bodyParser: false });
app.use(express.json({ limit: '100kb' }));
// Add bounded URL-encoded/raw parsers only to routes that need them.
```

With Fastify, configure the adapter/server `bodyLimit` rather than installing Express middleware. Keep signed webhook routes on their required bounded raw-body parser. A body limit does not bound pagination, decompression, database work or response size.

### Strict Response Shape (No Leak via JSON)

```typescript
// returning the whole user object including password hash
return this.userRepo.findById(id);

// project to a DTO; never echo back secrets
return { id: user.id, name: user.name }; // fields this caller may read
```

### Security Headers (helmet)

```typescript
// main.ts
import helmet from 'helmet';
app.use(helmet());
```

### CORS Strict

```typescript
// main.ts
app.enableCors({
  origin: ['https://app.example.com'], // explicit allowlist
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
});
```

CORS controls browser access to responses. It does not authenticate non-browser clients and does not stop every cross-origin request from reaching a handler. Use the [CSRF policy](20.5.2.02-csrf.md) for cookie-authenticated unsafe operations.

### Dependency Scanning in CI

```bash
# npm audit (or pnpm audit)
pnpm audit --prod --audit-level=high

# Snyk or Trivy for deeper scans
snyk test
```

## Real-World Use Cases

1. **Public REST API** — Helmet, strict CORS, rate limit, JWT validation, ownership check, DTO validation, structured errors with no stack traces.
2. **Mobile app backend** — Short-lived JWT (15 min) + refresh token rotation, push notifications for new device login, rate limit on auth endpoints.
3. **B2B partner API** — Per-partner API key, mTLS optional, per-partner rate limit, scoped OAuth2.
4. **Internal microservice mesh** — mTLS via service mesh (Istio/Linkerd), service-to-service authn, no public internet ingress.
5. **Webhook receiver** — HMAC signature verification (`X-Signature: sha256=...`), replay protection (timestamp + nonce), idempotency keys.
6. **Public file upload** — Pre-signed URLs (5-min TTL), server-side virus scan, MIME sniff, max-size enforcement.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------ | ---------------------------------------------------------------------------------- |
| BOLA — endpoint returns any resource by id | Check trusted tenant, stored relationships and the specific operation |
| Mass assignment — DTO has `isAdmin` | Separate admin DTO; never trust client-supplied role |
| Verbose errors with stack trace | Catch-all filter returns a safe body; log the full thing server-side |
| `*` CORS | Explicit allowlist; never use `*` with credentials |
| No rate limit on `/login` | Bound attempts per account and network; avoid attacker-triggered permanent lockout |
| Default credentials / sample data in prod | Enforce strong, rotated secrets; no debug routes in prod |
| Internal endpoints exposed by accident | Inventory check in CI; staging/prod parity |
| 3rd-party API responses trusted | Validate every external response against a schema (Zod / io-ts) |
| SSRF — `fetch(userInput)` | Fixed destinations or connection-time policy plus egress controls |
| Verbose logs that include JWTs / API keys | Structured logger with a redact list |

## Best Practices

1. **Default-deny authz** — Protected endpoints require explicit identity and operation/object/property policies; public routes are intentional.
2. **Whitelist DTOs** — `whitelist: true` + `forbidNonWhitelisted: true`; never accept fields you didn't ask for.
3. **Browser boundary controls** — Configure headers and CORS for the application; credentialed responses require explicit permitted origins.
4. **Rate limit per route** — Aggressive on auth, write, and expensive-read endpoints.
5. **BOLA tests in CI** — A test that calls `GET /orders/<other-user-id>` and expects 404/403.
6. **Bound resource use** — Set route-appropriate body, page, execution-time and concurrency budgets; do not log arbitrary request bodies.
7. **Strict JSON response shape** — Project to DTOs; never echo the raw DB row.
8. **No secrets in error messages or logs** — Redact known keys; review log output in code review.
9. **SSRF policy** — Prefer fixed destinations; enforce address policy at connection time and across redirects.
10. **Dependency scanning in CI** — `pnpm audit --audit-level=high` or Snyk; fail the build on criticals.
11. **API inventory** — Every endpoint documented in OpenAPI; track each environment and owner; retirement can return 410 without retaining the old business handler.
12. **Webhook security** — HMAC signature + replay protection (timestamp window) + idempotency keys.

## Performance Considerations

Measure authorization latency, key-cache age, rate-limit store availability and rejected-request cost under realistic load. Local rate limits multiply across replicas; distributed limits add a dependency whose failure policy must be intentional. Cache trusted signing keys with bounded refresh, but never turn a cached signature check into a claim that account membership is current.

## Summary

Protect the operation, object and properties separately. Bound both infrastructure cost and sensitive business flows. Fixed destinations and connection-time network policy address SSRF; DTOs and CORS do not. Test cross-tenant reads, unauthorized writes, response projections and limit failures rather than treating the OWASP list as a certification.

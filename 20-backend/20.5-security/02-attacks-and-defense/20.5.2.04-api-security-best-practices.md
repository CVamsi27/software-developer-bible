# API Security Best Practices & OWASP API Top 10

An authenticated Alice requests order 124. The service still has to establish that she may see it and return only the fields that policy permits.

## Definition

API security is the design and operation of controls that ensure each caller can perform only the intended actions on authorized resources, while request processing and data disclosure stay within defined limits. Authentication establishes an identity or credential; it does not decide what that identity may do.

> **Textbook Definition:** API security is the application of identity verification, authorization, input validation, resource controls and operational safeguards to an interface so that each request produces only an authorized and bounded effect.

## First Principles

An HTTP request tells a service what a caller wants; it does not prove that the caller is entitled to it.

1. **Identity and permission answer different questions.** A verified token identifies a principal and may carry claims. The application still has to decide whether that principal may perform this action on this object now.
2. **The service controls both input and output.** Clients can alter identifiers and submitted fields, while database rows often contain more information than one caller may see. Parse an allowlisted request shape and project an allowlisted response shape.
3. **Every operation consumes resources or affects a business rule.** A request can be valid and authorized yet too large, too frequent, too expensive or out of sequence. Bound technical work and enforce domain invariants separately.
4. **Dependencies extend the trust boundary.** A partner response, webhook payload or forwarded URL can be malformed, compromised or intentionally hostile. Apply limits and validation again at each system boundary.
5. **Network location is context, not identity.** A private subnet or service mesh can reduce exposure, but a reachable service still needs an authenticated caller and an operation-specific authorization policy.

## 1. Place controls at the boundaries a request crosses

#### Use the OWASP list to find risk classes, not as a security specification

The OWASP API Security Top 10 (2023) is an awareness catalog. It helps teams ask where controls may be missing; it is not a complete threat model or a certification that an API is secure.

| Risk | Engineering question |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| API1 — Broken Object Level Authorization | Is this principal allowed to access this particular record in this tenant and state? |
| API2 — Broken Authentication | Does the credential prove the intended identity, audience and validity under the configured protocol? |
| API3 — Broken Object Property Level Authorization | Which fields may this operation accept and which may this caller read? |
| API4 — Unrestricted Resource Consumption | Are bytes, records, execution time, concurrency, retries and paid downstream calls bounded? |
| API5 — Broken Function Level Authorization | May this principal invoke this operation, including administrative actions? |
| API6 — Unrestricted Access to Sensitive Business Flows | Can automation abuse a valid flow such as sign-up, reservations, purchases or referrals? |
| API7 — Server-Side Request Forgery (SSRF) | Can caller-controlled data make the service connect to an unintended destination? |
| API8 — Security Misconfiguration | Are debug routes, permissive policies, unsafe defaults or exposed management surfaces present? |
| API9 — Improper Inventory Management | Do owners know every deployed API version, environment, route and retirement date? |
| API10 — Unsafe Consumption of APIs | Are third-party responses, redirects and costs constrained as carefully as user input? |

## 2. Authorize the object and operation where the resource is known

Authentication middleware can establish a principal for protected routes. Object-level permission usually requires information available only after locating the resource, so enforce it in the service or data-access policy close to that read or mutation. A global guard can provide a default-deny route boundary, but it cannot replace checks for ownership, tenant membership, object state or field-level permission.

The following TypeScript sketch shows the contracts, not a framework-specific implementation. `tenantFromRequest` is caller-controlled until membership lookup confirms it; production code must also validate the identifier format.

```typescript
async function readOrder(request: Request) {
  const actor = await authenticator.requirePrincipal(request);
  const membership = await memberships.requireActive({
    subjectId: actor.subjectId,
    tenantId: tenantFromRequest(request),
  });

  const order = await orders.findVisibleTo({
    orderId: request.params.orderId,
    tenantId: membership.tenantId,
    subjectId: actor.subjectId,
  });
  if (!order) throw new NotFoundError();

  return {
    id: order.id,
    status: order.status,
    totalMinor: order.totalMinor,
  };
}
```

Here `findVisibleTo` applies the application's owner policy in the query, and the response is an explicit projection. A support or administrator workflow needs its own named policy and audit trail; it should not silently weaken the ordinary read path. Choose `403` versus `404` according to the API's resource-disclosure policy and keep the decision consistent.
Neither status removes timing or other side channels by itself.

For a mutation, validate a dedicated request schema, authorize the requested operation against the current object and construct the persistence update from permitted fields. A client-supplied `role`, `tenantId` or `isAdmin` field is not trusted merely because its type is valid. A read projection and a write allowlist are separate controls.

## 3. Bound work at every expensive boundary

Rate limits are one control, not a complete resource budget. Define limits from the cost and expected use of each operation:

| Boundary | Example control | What it does not bound by itself |
| -------------------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| Before parsing | Maximum request and upload bytes | Decompressed size, array cardinality or downstream work |
| Input schema | Maximum string length, array items and batch operations | Database execution time or response size |
| Query | Maximum page size, allowed filters and statement deadline | Expensive joins, unindexed patterns or concurrent work |
| Caller and operation | Per-account/API-key and route-specific rate or quota | Distributed abuse across many identities |
| Downstream call | Deadline, concurrency cap, retries and response-byte cap | Business abuse of a valid operation |
| Business flow | Reservation limits, idempotency and state-transition rules | Infrastructure exhaustion on unrelated routes |

For sign-in, IP-only limits are both easy to distribute around and capable of penalizing people behind shared networks. Combine an account-oriented limit with a network signal, use a trusted client address only when proxy configuration is correct, and avoid permanent account lockout that an attacker can trigger. A per-process counter is not a deployment-wide limit when the service has multiple replicas; choose shared storage and its outage behavior deliberately.

## 4. Make outbound requests and partner data explicit trust boundaries

If the service only needs one known partner, accept a partner record ID and build a URL from a fixed, trusted origin rather than accepting a complete URL.

```javascript
const partnerOrigin = new URL('https://api.partner.example');

function partnerProfileUrl(id) {
  if (typeof id !== 'string' || !/^[A-Za-z0-9_-]{1,64}$/.test(id)) {
    throw new TypeError('invalid partner profile id');
  }
  return new URL(`/v1/profiles/${id}`, partnerOrigin);
}
module.exports = { partnerProfileUrl };
```

This helper chooses a path on one configured origin; it does not make a general URL proxy safe and does not perform a request. If users must submit URLs, parse them with the platform URL parser, allow only required schemes, hosts and ports, reject embedded credentials, and apply address policy through the connector that actually opens the connection. DNS validation followed by a separate connection can resolve to a different address.
Disable redirects or revalidate every redirect, and enforce network egress restrictions as a second layer. Apply time, byte and concurrency limits to the response, then validate its schema before storing or forwarding fields.

The same principle applies to APIs called by your service: use TLS and expected peer identity, set explicit timeouts, avoid blindly forwarding credentials across redirects, validate returned data, and bound how much data and money each integration can consume.

## 5. Keep browser policy, HTTP errors and diagnostics in their proper roles

CORS tells browsers which origins may read certain cross-origin responses. It does not authenticate a caller or stop a non-browser client from sending a request. If browser requests use cookies, apply the CSRF policy as well.
A WAF can filter some known traffic patterns, but it cannot decide whether this principal may access this object. Security headers mainly affect responses that browsers render; configure them for the application and its actual content types rather than treating them as API authorization.

Return documented HTTP status codes and a stable client-facing error format, such as RFC 9457 problem details where appropriate. Expose enough information for clients to recover, but do not return stack traces, SQL, tokens, secrets or internal hostnames. Record a correlation ID and protected diagnostic details in logs; redact credentials and avoid storing request bodies unless a documented need and retention policy justify it.
Do not force identical errors for every case unless the threat model requires reducing a specific enumeration signal.

## 6. Test the policy and its failure boundaries

#### A route is not a complete authorization policy

The order example above demonstrates object scoping and response projection. To make it reviewable, build a test matrix around the actual policy:

| Principal | Request | Expected decision |
| ----------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------- |
| No valid credential | Read any order | Authentication failure |
| Active owner in the order's tenant | Read owned order | Permit with approved fields only |
| Active member in the same tenant, not the owner | Read another member's order | Deny unless the domain policy grants access |
| Member of another tenant | Read the known order ID | Deny without disclosing protected fields |
| Ordinary user | Set a privileged field on profile update | Reject or ignore by explicit schema policy; never persist it |
| Authorized support role | Use support workflow | Permit only the separately defined scope and record the audit event |

Add tests for stale membership, revoked credentials and objects in states that disallow the operation. A passing happy-path test says nothing about these boundaries.

## 7. Verify limits against the expensive operation

For a report endpoint, test that an oversized page is rejected or clamped according to the contract, concurrent exports stay within the worker budget, slow downstream calls stop at the deadline, and a dependency outage follows the documented fail-open or fail-closed policy. Rate-limit tests should cross process boundaries when the production policy claims to be shared across replicas.

## Real-World Decisions

- **Administrative APIs:** use a separate operation policy and, where practical, a distinct audience or deployment boundary. A role name alone does not scope the target tenant or action.
- **Cookie-authenticated browser APIs:** combine exact credentialed-origin CORS policy with CSRF defenses for unsafe operations. Bearer-token and machine clients have different credential-attachment risks.
- **Public or paid operations:** set per-operation request, execution and downstream-spend budgets; return `429` with a documented retry contract when a quota is exceeded.
- **Webhooks:** verify the signature over the provider-defined bytes and signing contract, enforce the timestamp/replay policy, and make event processing idempotent. A valid signature proves the sender knew a key; it does not make the payload valid for the domain.
- **Version retirement:** inventory routes and owners across production, staging and partner environments, measure old-version use, communicate a sunset date, and remove the route and credentials after migration. Hiding the route in OpenAPI does not remove it from the deployed service.

## Summary

Secure API behavior comes from enforcing the right policy at each boundary: identity for the caller, authorization for the operation and object, explicit input and output fields, bounded resource use, and constrained integrations. Middleware and infrastructure can enforce broad defaults, but resource-specific authorization and domain rules need the data and context they govern. Test negative cases and operational failure modes alongside successful requests.

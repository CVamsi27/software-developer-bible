# Encryption, Hashing & TLS

Different keys serve different jobs

## Definition

Encryption uses an algorithm and a key to turn readable data (**plaintext**) into unreadable data (**ciphertext**). The corresponding decryption key restores the plaintext. Encryption protects confidentiality; detecting tampering also requires authentication, such as an authenticated encryption mode.
Symmetric encryption uses the same key to encrypt and decrypt. Asymmetric encryption uses different keys.

> **Textbook Definition:** Encryption transforms plaintext into ciphertext under a key to protect confidentiality. Authenticated encryption additionally detects unauthorized modification; password hashing is a separate one-way verification mechanism.

In web development, encryption protects data in transit (HTTPS/TLS), data at rest and service-to-service communication. Password storage instead uses a salted, deliberately expensive password hash; it should not rely on reversible encryption.

## First Principles

Assume an attacker can copy the stored ciphertext and send modified records to the application. Secrecy must depend on protected key material rather than hiding the algorithm. Decryption must also reject unauthorized modification before any resulting plaintext drives application behavior.

Sharing keys adds a trust problem: encrypting to an attacker-substituted public key protects data for the attacker. Use authenticated key distribution or agreement. Modern TLS authenticates peers and derives symmetric traffic keys; it does not solve trust merely by publishing a key.

Authenticated encryption still has usage rules. AES-GCM requires nonce uniqueness under a key; losing that state or reusing a nonce can defeat its guarantees. Durable key identity, permitted use, rotation and recovery therefore belong to the data format and operating contract, not just the encryption call.

## How It Works


### 1. Different keys serve different jobs

| Mechanism | What the receiver needs | Boundary |
| ---------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------- |
| Symmetric authenticated encryption | The secret key and complete nonce/tag/ciphertext record | Anyone holding the key can encrypt and decrypt |
| Public-key encryption | A private key to decrypt data encrypted to the public key | Suitable for small messages or wrapping data keys, not bulk payloads |
| Digital signature | A trusted public key to verify a private-key signature | Provides authenticity, not confidentiality |
| Key agreement | Authenticated peer key material | Derives shared secrets; must prevent an attacker substituting a peer |

### 2. A TLS 1.3 connection derives fresh traffic keys

```text
ClientHello + supported groups + client key share -> server
ServerHello + selected group + server key share   -> client
Both derive handshake keys from the shared secret and transcript
Server sends encrypted certificate, CertificateVerify and Finished
Client verifies certificate chain + hostname + transcript proof
Client sends Finished; both use derived application traffic keys
```

This is a full certificate-authenticated handshake outline; resumption and client authentication have different messages. Modern TLS 1.3 does not send a pre-master secret encrypted with the server's RSA public key. The certificate authenticates the peer; ephemeral key agreement supplies forward secrecy, so later theft of the certificate private key alone does not decrypt recorded completed sessions.
TLS ends at its termination point: an edge proxy's HTTPS does not automatically encrypt the next hop. Early data (0-RTT) is replayable and needs an application replay policy.

When tuning, measure the handshake and round trips between actual endpoints separately from steady-state encryption throughput; the TLS termination point determines which network paths the measurement covers.

## Code Examples

### Bind encrypted data to its record

This complete Node.js module takes a provisioned random 32-byte key. It bounds input, uses a fresh 12-byte nonce and authenticates a caller-supplied record context with **additional authenticated data (AAD)**. AAD is visible but covered by the authentication tag.

```javascript
const { randomBytes, createCipheriv, createDecipheriv } = require('node:crypto');
function fieldCipher(key) {
  if (!Buffer.isBuffer(key) || key.length !== 32) throw new TypeError('32-byte key required');
  const ownedKey = Buffer.from(key);
  const contextBytes = context => {
    if (typeof context !== 'string' || !context || context.length > 1024) throw new TypeError('invalid context');
    return Buffer.from(context, 'utf8');
  };
  function encrypt(text, context) {
    if (typeof text !== 'string' || Buffer.byteLength(text) > 65_536) throw new TypeError('invalid plaintext');
    const iv = randomBytes(12), cipher = createCipheriv('aes-256-gcm', ownedKey, iv, { authTagLength: 16 });
    cipher.setAAD(contextBytes(context));
    const ciphertext = Buffer.concat([cipher.update(text, 'utf8'), cipher.final()]);
    return [iv, cipher.getAuthTag(), ciphertext].map(x => x.toString('hex')).join(':');
  }
  function decrypt(record, context) {
    if (typeof record !== 'string' || record.length > 131_130 ||
        !/^[a-f0-9]{24}:[a-f0-9]{32}:(?:[a-f0-9]{2})*$/.test(record)) throw new TypeError('invalid record');
    const [iv, tag, ciphertext] = record.split(':').map(x => Buffer.from(x, 'hex'));
    const decipher = createDecipheriv('aes-256-gcm', ownedKey, iv, { authTagLength: 16 });
    decipher.setAAD(contextBytes(context)); decipher.setAuthTag(tag);
    return Buffer.concat([decipher.update(ciphertext), decipher.final()]).toString('utf8');
  }
  return { encrypt, decrypt };
}
module.exports = { fieldCipher };
```

Trace: encrypt a patient's note with `tenant-A/patient-42/note` as context. Decryption with the same key and context succeeds. Moving the ciphertext to patient 43 changes the context and makes authentication fail.
Do not expose plaintext produced by `update` until `final` accepts the tag. Catch errors at the application boundary without returning cryptographic diagnostics.

Random nonces make collisions unlikely, not impossible. Never reuse a nonce with the same GCM key; establish per-key usage limits and rotation from the threat model and library guidance. This helper omits key identifiers and durable key management: production envelopes need a version/key ID selected from a trusted registry, retaining old decrypt keys until data and backups are migrated.
A password-derived key needs a unique random salt and a calibrated KDF; a fixed literal `"salt"` is not a key-management plan.

### Public-key operations do not encrypt arbitrarily large files

RSA-OAEP with SHA-256 on a 2048-bit key accepts at most 190 message bytes. Use a vetted hybrid/envelope scheme: generate a random data-encryption key, encrypt the payload with authenticated encryption, and wrap the data key with KMS or a supported public-key construction. Keep signature and encryption key purposes separate.
Do not generate a new persistent key on every process restart and expect old ciphertext to remain readable.

### Passwords need a verifier, not a decryption key

A password hash includes a per-password salt and work parameters. The server repeats the password-hashing computation during login; it cannot decrypt the password. Use the complete [authentication example](../01-auth/20.5.1.01-auth-fundamentals.md) for calibrated Argon2id and bounded verification.
Argon2id's memory cost also limits concurrent checks, so calibrate it on production-class hardware and cap verification concurrency. Existing bcrypt deployments must account for their implementation's 72-byte input limit and plan migration; raising a cost factor does not repair silent truncation.

### Field encryption changes database behavior

Encrypt and decrypt at an explicit repository boundary. Cover creates, updates, reads, exports, nested operations, background jobs and raw queries. Old Prisma `$use` middleware is not a current transparent-encryption API and never covered every operation in the former example.

Randomized encryption prevents ordinary equality indexes, sorting and uniqueness checks over plaintext. A keyed search digest can support carefully chosen exact-match lookups, but reveals equality and requires a separate key, normalization contract and collision handling. Encryption at rest protects stolen media under its key-access assumptions; it does not hide data from an authorized application or replace row authorization.

## Summary

Encryption protects confidentiality under its key-access assumptions. Use vetted authenticated encryption, preserve its nonce/tag/context metadata, and release plaintext only after authentication succeeds. Public-key encryption, signatures and key agreement have distinct jobs.
Passwords need calibrated salted verifiers; transport needs authenticated TLS appropriate to the endpoints. Plan key identity, usage limits, rotation and old-data recovery together—changing a key without a migration policy can make data unreadable.

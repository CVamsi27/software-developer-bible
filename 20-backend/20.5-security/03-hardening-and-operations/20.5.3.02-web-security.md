# Web Security Headers & HTTPS

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Web security encompasses the practices, technologies, and policies designed to protect web applications and their users from security threats. It includes a wide range of defenses such as Content Security Policy (CSP), HTTP Strict Transport Security (HSTS), Cross-Origin Resource Sharing (CORS), and various security headers. Web security aims to prevent attacks like XSS, CSRF, clickjacking, open redirects, SSRF, and XXE.

> **Textbook Definition:** Web application security manages trust across browser execution, HTTP transport and server-side processing. Origin rules, security headers and application checks provide complementary controls with distinct attack coverage.

## First Principles

Web security headers exist because the browser is the enforcement point you don't control:

1. **You cannot patch the client; you can only instruct it.** CSP, HSTS, X-Content-Type-Options, frame-ancestors are *directives to the browser* — the server's only lever over execution on someone else's machine. Each header maps to one attack class the browser could otherwise be talked into.
2. **HTTPS is the substrate everything else assumes.** Without TLS, no header, cookie, or token is trustworthy in transit; HSTS exists because the *first* HTTP request is the vulnerability (SSL-strip), a learned policy protects subsequent visits; preloading can protect the first visit where supported.
3. **Defaults are the attack surface.** Browsers permit inline scripts, framing, MIME-sniffing by default because pages need them; headers exist to *turn off* what you don't need — the security posture is "deny by default, allow explicitly."

## Why Do We Need It?

- **Attack Prevention**: Protect against common web vulnerabilities
- **Data Protection**: Safeguard user data from theft and manipulation
- **Compliance**: Meet regulatory requirements (GDPR, PCI DSS, HIPAA)
- **Trust**: Build user confidence in application security
- **Reputation**: Avoid security incidents that damage brand reputation
- **Legal**: Prevent lawsuits from security breaches

## How It Works

### Match each header to the browser action

| Control | What it constrains | What it does not establish |
| ------------------ | ------------------------------------------------------ | ----------------------------------------------------------------- |
| CSP | Permitted script/resource execution and loading | Correct application authorization or safe rendering in every sink |
| HSTS | Remembered HTTPS-only host policy | Protection of the first visit without prior/preloaded policy |
| `nosniff` | MIME-sniffing behavior for supported response contexts | A safe uploaded document or correct file access policy |
| `frame-ancestors` | Which parents may embed the response | Which frames this page may itself load |
| Referrer-Policy | Referrer information sent with later requests | Removal of sensitive data already placed in a URL |
| Permissions-Policy | Browser feature availability | A substitute for user permission and application access checks |

## Code Examples

### One response carries one coherent browser policy

This complete Express 5 application emits a fresh nonce in both the CSP header and the rendered script. Install compatible `express`, `helmet` and `cors` packages. The local fixture is HTTP; enable HSTS only on the production HTTPS response path after verifying proxy and domain behavior.

```javascript
const express = require('express');
const helmet = require('helmet');
const cors = require('cors');
const { randomBytes } = require('node:crypto');
function createBrowserApp({ production = false } = {}) {
  const app = express();
  app.disable('x-powered-by');
  app.use((req, res, next) => { res.locals.nonce = randomBytes(16).toString('base64'); next(); });
  app.use(helmet({
    strictTransportSecurity: production ? { maxAge: 31_536_000, includeSubDomains: false } : false,
    contentSecurityPolicy: { useDefaults: false, directives: {
      defaultSrc: ["'none'"],
      scriptSrc: [(req, res) => `'nonce-${res.locals.nonce}'`],
      styleSrc: ["'self'"], imgSrc: ["'self'"], connectSrc: ["'self'"],
      objectSrc: ["'none'"], baseUri: ["'none'"], formAction: ["'self'"], frameAncestors: ["'none'"],
    } },
  }));
  app.use('/api', cors({ origin: ['https://app.example.com'], credentials: true,
    methods: ['GET', 'POST'], allowedHeaders: ['Content-Type', 'X-CSRF-Token'] }));
  app.get('/', (req, res) => {
    res.set('Cache-Control', 'no-store');
    res.type('html').send(`<h1>Account</h1><script nonce="${res.locals.nonce}">document.title='Account';</script>`);
  });
  app.get('/api/status', (req, res) => res.json({ ready: true }));
  return app;
}
module.exports = { createBrowserApp };
```

Trace: response A's script executes only with A's nonce under this policy. Response B gets a different nonce. A fixed `nonce-abc123` is predictable and does not provide this boundary. Never copy untrusted markup into a nonce-bearing script. This small application uses `no-store`; a cached page must keep its header and nonce-bearing body coherent without reusing a publicly predictable nonce scheme.

Do not install several CSP middlewares that overwrite each other's policy. Multiple delivered CSP policies are independently enforced and can become unexpectedly restrictive. Roll out a candidate using report-only mode first, then enforce it after checking required resources. CSP reports are untrusted telemetry: bound request size/rate, redact sensitive URLs and authenticate access to stored reports. Configure `Reporting-Endpoints` and `report-to` if using the Reporting API; a group name alone does not create a collector.

### HSTS is remembered transport policy

Browsers accept HSTS over HTTPS and remember its `max-age`; HTTP delivery does not establish the policy. Start with a short lifetime, verify every relevant host and then increase it. `includeSubDomains` commits descendant hosts to HTTPS too. `preload` is a request signal, not automatic inclusion in browser lists; submit only after meeting eligibility and understanding removal delays. Clearing a learned policy does not instantly remove a preloaded domain. The local HTTP fixture deliberately emits no HSTS.

### CORS and framing constrain different browser actions

The CORS middleware handles preflight requests for `/api` without an Express 5-invalid `app.options('*', ...)` route. An allowed browser origin can read credentialed responses; a disallowed origin cannot rely on an access-control response header. The request may still reach the application, and non-browser clients do not enforce CORS. Authenticate, authorize and apply CSRF policy independently. Missing `Origin` is not evidence of a trusted caller.

`frame-ancestors` controls who can embed this response. `frame-src` controls frames the page itself loads. The policy above forbids embedding; Helmet also emits a compatible `X-Frame-Options` fallback. Neither replaces confirmation for sensitive operations. Disable the legacy XSS auditor (`X-XSS-Protection: 0`) rather than treating it as modern protection.

### Select a redirect target rather than trusting a path prefix

This complete helper maps an opaque choice to a known internal path. The caller supplies a key, not a URL.

```javascript
function redirectTarget(choice) {
  const destinations = new Map([['account', '/account'], ['orders', '/orders']]);
  if (typeof choice !== 'string' || !destinations.has(choice)) return '/dashboard';
  return destinations.get(choice);
}
module.exports = { redirectTarget };
```

A `startsWith('/')` check misses URL parser normalization such as slash/backslash variants. If external redirects are needed, parse and validate the exact HTTPS origin, port and credentials policy against trusted configured destinations. OAuth redirect URIs have their own stricter registered contract.

### Outbound URLs and XML parsers need server-side controls

Headers do not prevent SSRF. Use the canonical [API-security destination policy](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md); a DNS precheck followed by a separate fetch is insufficient.

**XML external entity (XXE)** attacks persuade a parser to load an external entity, possibly reading a local file or internal URL. When XML is required, select a maintained parser and disable DTD/entity resolution and external resource loading according to its actual API; also bound bytes, nesting and expansion. `nonet` blocks network access, not every local-file path. Test malicious DTDs against the exact parser/version instead of assuming a similarly named option proves rejection. JSON removes XML entity syntax from that endpoint, but still needs schema and resource limits. The signed [SAML flow](../01-auth/20.5.1.07-sso-saml-federation.md) requires a protocol-aware verifier rather than a second generic XML parse.

## Common Mistakes

1. **Not implementing CSP**: Critical for preventing XSS

2. **Using unsafe-inline in CSP**: Weakens CSP protection

3. **Not using HSTS**: Allows SSL stripping attacks

4. **Overly permissive CORS**: Unintended origins may read permitted browser responses

5. **Not preventing clickjacking**: Users can be tricked

6. **Ignoring open redirects**: Can lead to phishing

7. **Not preventing SSRF**: Server can be used as proxy

8. **Not preventing XXE**: XML parsing vulnerabilities

## Best Practices

1. **Implement strict CSP** with nonce-based scripts

2. **Use HSTS** with a staged lifetime; cover subdomains only after auditing them

3. **Configure CORS** with specific allowed origins

4. **Prevent clickjacking** with X-Frame-Options and CSP

5. **Validate redirect URLs** to prevent open redirects

6. **Prevent SSRF** through fixed destinations or enforced connection-time policy

7. **Prevent XXE** by disabling external entities

8. **Use security headers** (helmet.js makes this easy)

9. **Regular security audits** and penetration testing
10. **Monitor security headers** with tools like securityheaders.com

## Measure the deployed policy

Observe blocked-resource reports and browser behavior on real routes. Some requests require a CORS preflight, which can add a round trip; cache lifetime and request conditions determine frequency. CSP does not inherently slow the first page load, and relaxing it for caching is not a performance strategy. Test header/body coherence across CDN, proxy and application layers.

## Summary

Web security is a comprehensive approach to protecting web applications from attacks. Key takeaways:

- Implement CSP with nonce-based scripts
- Use HSTS with long max-age
- Configure CORS with specific origins
- Prevent clickjacking with X-Frame-Options and CSP
- Validate redirect URLs to prevent open redirects
- Enforce outbound destination policy at the actual connection
- Prevent XXE by disabling external entities
- Use security headers (helmet.js)
- Regular security audits and testing

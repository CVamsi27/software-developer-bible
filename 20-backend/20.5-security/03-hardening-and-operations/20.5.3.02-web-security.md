# Web Security Headers & HTTPS

Match each header to the browser action

## Definition

Web security controls how browsers render content, how clients establish secure HTTP connections and how servers process untrusted requests. Content Security Policy (CSP), HTTP Strict Transport Security (HSTS), Cross-Origin Resource Sharing (CORS) and other response headers constrain specific browser behaviors; server-side authorization, URL handling and parser configuration protect different boundaries.

> **Textbook Definition:** Web application security manages trust across browser execution, HTTP transport and server-side processing. Origin rules, security headers and application checks provide complementary controls with distinct attack coverage.

## First Principles

The browser processes a response according to its own rules. A server can declare policies for a browser to enforce, but those headers cannot correct unsafe server behavior:

1. **Transport protection comes first.** TLS protects the connection and authenticates the peer under the certificate contract. Without it, an on-path attacker can read or alter HTTP traffic. HSTS lets a browser remember an HTTPS-only policy after receiving it securely; preload can cover first contact only for domains actually included in browser preload lists.
2. **Each browser control has a defined scope.** CSP limits eligible script execution and resource loads, `frame-ancestors` limits who may embed a page, and CORS controls which browser origins may read certain responses. None of them authenticates an API caller or authorizes a database operation.
3. **Parser and routing behavior remains server-owned.** A response header cannot make an unsafe redirect safe, prevent a server-side request to an attacker-chosen host or configure an XML parser. Enforce those rules where the server parses the input or opens the connection.

## How It Works


### 1. Match each header to the browser action

| Control | What it constrains | What it does not establish |
| ------------------ | ------------------------------------------------------ | ----------------------------------------------------------------- |
| CSP | Permitted script/resource execution and loading | Correct application authorization or safe rendering in every sink |
| HSTS | Remembered HTTPS-only host policy | Protection of the first visit without prior/preloaded policy |
| `nosniff` | MIME-sniffing behavior for supported response contexts | A safe uploaded document or correct file access policy |
| `frame-ancestors` | Which parents may embed the response | Which frames this page may itself load |
| Referrer-Policy | Referrer information sent with later requests | Removal of sensitive data already placed in a URL |
| Permissions-Policy | Browser feature availability | A substitute for user permission and application access checks |

## Code Examples

### One response carries one coherent browser policy

This Express 5 application factory emits a fresh nonce in both the CSP header and the rendered script. Install compatible `express`, `helmet` and `cors` packages. The local fixture is HTTP; enable HSTS only on the production HTTPS response path after verifying proxy and domain behavior.

```javascript
const express = require('express');
const helmet = require('helmet');
const cors = require('cors');
const { randomBytes } = require('node:crypto');
function createBrowserApp({ production = false } = {}) {
  const app = express();
  app.disable('x-powered-by');
  app.use((req, res, next) => { res.locals.nonce = randomBytes(16).toString('base64'); next(); });
  if (production) app.use((req, res, next) => {
    if (req.secure) res.set('Strict-Transport-Security', 'max-age=300');
    next();
  });
  app.use(helmet({
    strictTransportSecurity: false,
    contentSecurityPolicy: { useDefaults: false, directives: {
      defaultSrc: ["'none'"],
      scriptSrc: [(_req, res) => `'nonce-${res.locals.nonce}'`],
      styleSrc: ["'self'"], imgSrc: ["'self'"], connectSrc: ["'self'"],
      objectSrc: ["'none'"], baseUri: ["'none'"], formAction: ["'self'"], frameAncestors: ["'none'"],
    } },
    xFrameOptions: { action: 'deny' },
  }));
  app.use('/api', cors({ origin: ['https://app.example.com'], credentials: true,
    methods: ['GET', 'POST'], allowedHeaders: ['Content-Type', 'X-CSRF-Token'] }));
  app.get('/', (req, res) => {
    res.set('Cache-Control', 'no-store');
    res.type('html').send(`<h1>Account</h1><script nonce="${res.locals.nonce}">document.title='Account';</script>`);
  });
  app.get('/api/status', (req, res) => res.json({ ready: true }));
  return app;
}
module.exports = { createBrowserApp };
```

Trace: the rendered inline script carries the same nonce as its response policy, and response B gets a different nonce. A fixed `nonce-abc123` is predictable and does not provide this boundary. Never copy untrusted markup into a nonce-bearing script.
This small application uses `no-store`; a cached page must keep its header and nonce-bearing body coherent without reusing a nonce. `frame-ancestors 'none'` and `X-Frame-Options: DENY` agree for browsers that enforce the respective policy.

Do not install several CSP middlewares that overwrite each other's policy. Multiple delivered CSP policies are independently enforced and can become unexpectedly restrictive. Roll out a candidate using report-only mode first, then enforce it after checking required resources.
CSP reports are untrusted telemetry: bound request size and rate, redact sensitive URLs and authenticate access to stored reports. `report-to` names a collector configured through `Reporting-Endpoints`; the name alone does not create one. Add the legacy `report-uri` directive only when older-browser reporting is part of the support contract.

### HSTS is remembered transport policy

Browsers accept HSTS over HTTPS and remember its `max-age`; HTTP delivery does not establish the policy. Start with a short lifetime, verify every relevant host and then increase it. `includeSubDomains` commits descendant hosts to HTTPS too. `preload` alone does not add a domain to browser lists; submission and inclusion are separate steps, and removal can take time. The factory sets HSTS only when production mode is enabled and Express sees a secure request.
If TLS terminates at a reverse proxy, configure Express to trust only the actual proxy boundary before relying on `req.secure`; enabling trust for arbitrary forwarded headers lets clients forge that signal. The example omits `includeSubDomains` while assuming descendant hosts may not all support HTTPS.

### CORS and framing constrain different browser actions

The CORS middleware handles preflight requests for `/api`; the example does not register an Express 5-invalid `app.options('*', ...)` route. A browser exposes a credentialed response to an allowed origin only when the CORS response permits it. A simple cross-origin request can still reach the application when the browser later withholds its response from script; a failed preflight prevents the preflighted request from being sent.
Non-browser clients do not enforce CORS. Authenticate, authorize and apply CSRF policy independently. Missing `Origin` is not evidence of a trusted caller.

`frame-ancestors` controls who can embed this response. `frame-src` controls frames the page itself loads. The policy and legacy header above both deny framing. Neither replaces confirmation for sensitive operations.

### Select a redirect target rather than trusting a path prefix

This complete helper maps an opaque choice to a known internal path. The caller supplies a key, not a URL.

```javascript
function redirectTarget(choice) {
  const destinations = new Map([['account', '/account'], ['orders', '/orders']]);
  if (typeof choice !== 'string' || !destinations.has(choice)) return '/dashboard';
  return destinations.get(choice);
}
module.exports = { redirectTarget };
```

A `startsWith('/')` check misses URL parser normalization such as slash/backslash variants. If external redirects are needed, parse and validate the exact HTTPS origin, port and credentials policy against trusted configured destinations. OAuth redirect URIs have their own stricter registered contract.

### Outbound URLs and XML parsers need server-side controls

Headers do not prevent SSRF. Use the [API-security destination policy](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md); a DNS precheck followed by a separate fetch is insufficient.

**XML external entity (XXE)** attacks persuade a parser to resolve an external entity, potentially reading a local file, contacting an internal service or exhausting resources. When XML is required, select a maintained parser and disable DTD/entity resolution and external resource loading according to its actual API; also bound bytes and parser work. A setting that blocks network access may still allow local-file access or other resource mechanisms. Treat an unsupported security setting as a configuration failure, and test malicious DTDs against the exact parser and version. JSON removes XML entity syntax from that endpoint, but still needs schema and resource limits. The signed [SAML flow](../01-auth/20.5.1.07-sso-saml-federation.md) requires a protocol-aware verifier rather than a second generic XML parse.

## Verify at deployment

The example begins with a five-minute HSTS lifetime; increase it only after every covered host has been verified. Before enforcing browser policy, inspect the final headers after proxy/CDN processing, exercise allowed and rejected CORS preflights, verify cached nonce/header pairs, and test malicious XML against the exact parser and version. A header set in application code is not evidence that the deployed edge preserves it.

## Summary

Browser policies constrain browser behavior; TLS protects the transport after certificate validation; server-side checks control redirects, outbound requests and parser capabilities. Choose each control for its scope, verify the policy emitted by the complete deployment, and keep authorization and CSRF defenses at their own enforcement points.

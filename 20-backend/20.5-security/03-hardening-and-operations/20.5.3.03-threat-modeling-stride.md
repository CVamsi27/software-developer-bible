# Threat Modeling — STRIDE & Attack Surfaces

A gateway can validate a user's token while an orders service still returns another tenant's order. Asking only whether the system “has authentication” misses the authorization check that joins the caller to the stored order. Threat modeling traces that path before choosing controls.

## Definition

**Threat modeling** is a structured analysis of a system's security requirements, design, likely attack paths and defenses. A **threat** is a way an attacker or failure could violate a security objective; a **vulnerability** is a weakness that may make such a threat possible. **STRIDE** is a six-category prompt for finding design threats. An **attack surface** is the set of reachable entry points and exposed interfaces through which data or control can affect the system. An **attack tree** starts with an attacker goal and decomposes the alternative or required paths to reach it.

> **Textbook Definition:** Threat modeling is the systematic identification and analysis of threats to a system by examining its assets, security objectives, architecture, trust boundaries and attack paths, then selecting and validating risk responses. STRIDE is one threat-classification method; it is not a risk score or proof that the system is secure.

The STRIDE mnemonic stands for Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service and Elevation of Privilege. The categories are prompts for analysis, not a requirement to find one threat on every flow.

## First Principles

A request crosses components that have different permissions and incomplete context. A check in one service does not automatically protect a later database operation. Model the assets, identity evidence, authorization decisions and data origins across the whole flow.
A successful network connection proves only that a connection was established; it does not by itself establish the caller's identity or authority. Copying data into a queue or database does not make it trusted.

Defenders have finite time. A list of possible attacks without affected assets, impact, exposure and an owner cannot guide work. Prioritize credible paths, retain uncertainty, and record assumptions that would change the decision.

## 1. Model the system before listing threats

Scope the system and its important data first. Sketch the external actors, processes, data stores and flows for one user or business scenario. Include application programming interface (API) routes, webhooks, job messages, file parsers and administrative controls in the entry-point inventory.
Mark a **trust boundary** wherever a change in actor, privilege, network, or administrative control changes the assumptions you can safely make. Mark entry points and dependencies so the model exposes the attack surface. A context diagram is enough to begin; break out a component only when its internal detail changes the analysis.

For an order read, the browser is outside the service's trust. The gateway can establish credential evidence, but the orders service still needs to authorize the requested record against trusted tenant and membership data. The database role and row policy limit what a compromised or faulty service can reach.

```text
[Browser] --token + order identifier--> ||public boundary|| --> [Gateway]
[Gateway] --validated caller + identifier--> ||service boundary|| --> [Orders service]
[Orders service] --tenant-scoped query--> ||data boundary|| --> [(Orders DB)]
[Orders service] --minimized audit event--> ||audit boundary|| --> [Audit store]
```

Each `||... boundary||` marks a change in trust assumptions; it is not itself a defense. The arrows name what crosses that boundary, and the receiving component must validate the context and enforce its own authority checks. The audit store is a separate destination with its own access, integrity and retention requirements.
Do not send it raw credentials or every order field.

| STRIDE category | Question on this flow | Concrete control or test |
| ---------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spoofing | Can a caller forge user or service identity? | Validate issuer, audience and credential evidence; reject a forged caller context |
| Tampering | Can an identifier, message or stored row be altered? | Bound input, bind query parameters and enforce authorized updates |
| Repudiation | Could an actor plausibly deny an action because evidence is missing, mutable or unattributable? | Record necessary actor/action/time context; restrict writes and access, protect integrity, and verify collection. Logs support accountability; they do not prove who acted if identity was shared or compromised |
| Information disclosure | Can a different tenant's order or a secret escape? | Tenant/object policy and response projection; test a cross-tenant read |
| Denial of service | Can a cheap request induce unbounded work? | Body, query, deadline and concurrency budgets; exercise limit failure |
| Elevation of privilege | Can ordinary access become an admin operation? | Explicit operation/property policy; test a role-change denial |

Apply the categories to relevant processes, stores, actors and flows. There is neither exactly one threat per boundary nor a requirement that every category produce a finding on every arrow. STRIDE prompts discovery; a separate risk decision considers impact, exposure, credible attacker capability, existing controls and uncertainty.
An idempotency key prevents duplicate effects under its contract; it does not by itself establish trustworthy audit attribution.

## 2. Record a testable threat

This YAML is a design record, not an executable security configuration:

```yaml
id: THREAT-ORD-001
title: Cross-tenant order disclosure through guessed identifier
asset: Order details
flow: Browser -> Gateway -> Orders service -> Database
category: Information disclosure
assumptions:
  - Membership comes from trusted current server context
  - Order identifiers are discoverable and cannot be treated as authorization
impact: Exposure of another tenant's order
mitigations:
  - Scope repository lookup by trusted tenant and authorized relationship
  - Project only permitted response fields
verification:
  - Other-tenant identifier yields the documented denial response
  - Allowed read excludes internal notes and payment secrets
owner: orders-team
status: open
```

After implementation, attach the actual test and deployment evidence. A 404 policy can reduce object enumeration but does not eliminate timing or every other side channel. Close the item only when the agreed verification passes in the relevant environment; changing `status: open` to `closed` is not evidence.

## 3. Use attack trees for a goal with several paths

For “read another tenant's order,” possible branches include bypassing object checks, stealing a privileged credential, reading an overbroad export, or accessing a leaked backup. Defending the request handler covers only one branch. An AND branch requires several conditions together; an OR branch offers alternatives.
Use the tree to compare paths and controls, then keep it bounded to meaningful assets and attacker capabilities.

Signed role claims can be valid evidence under a trusted issuer and freshness contract; they are not inherently untrustworthy. High-impact operations may need current membership lookup because issued claims can outlive a change. Device fingerprints are risk signals, not identity proofs.
Generic login errors reduce enumeration, but equal wording does not guarantee constant execution time.

## 4. Turn threats into owned, verifiable decisions

Use the model as a short engineering loop: identify threats, rank the credible risks, choose a response, then verify that the control works. A response may be mitigation, risk acceptance by an authorized owner, avoidance through a design change, or transfer where that is meaningful. Record the chosen response, owner, target date, evidence and residual risk.
A likelihood/impact matrix is a prioritization aid, not a measured probability.

Update the affected model when a design change alters an asset, data flow, identity path, dependency, deployment boundary or security assumption. Incident findings and scheduled reviews can reveal missing assumptions too. Keep the model focused on changed paths rather than redrawing the whole system for every code edit.

Threat modeling complements code review, penetration testing and production monitoring. It does not establish compliance by itself, and different contractual or regulatory programs have different evidence requirements. Explain the specific controls the system needs rather than claiming every standard mandates the same artifact.

## Summary

Model assets and trust changes, follow a focused flow, and use STRIDE or attack trees to expose concrete failure paths. Turn each important threat into an owned mitigation and a test. Keep residual risk and assumptions visible as the system changes.

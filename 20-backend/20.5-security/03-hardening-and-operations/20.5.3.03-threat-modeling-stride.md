# Threat Modeling — STRIDE & Attack Surfaces

A gateway can validate a user's token while an orders service still returns another tenant's order. Asking whether the system “has authentication” misses the point where identity must be joined to stored ownership. A threat model follows that path before choosing controls.

## Definition

**Threat modeling** examines protected assets, actors, data flows and places where trust changes, then identifies ways security objectives could fail. **STRIDE** is a checklist of six threat categories. An **attack tree** starts with a goal and divides it into paths an attacker could take. Both help produce concrete mitigations, tests and residual-risk decisions.

> **Textbook Definition:** Threat modeling systematically identifies potential violations of a system's security objectives from its assets, data flows and trust boundaries. STRIDE classifies threats; mitigation selection and verification turn the model into actionable controls.

## First Principles

A component receives data and claims from other actors; it cannot infer their trustworthiness merely from a connection succeeding. Different actors have different authority, and copying data into a queue or database does not make it trusted. Model those boundaries before choosing a control.

Defenders also have finite time. A list of possible attacks without asset impact, exposure and ownership cannot guide work. Prioritize credible paths, retain uncertainty, and record the assumptions that would change the decision.

## Trace one order read

```text
untrusted browser -> public gateway -> orders service -> orders database
                            |               |
                    credential check   object/tenant policy
                                            |
                                  restricted audit record
```

The gateway's validation provides credential evidence. The service must validate trusted caller context and authorize this operation on this stored order. The database role limits data reach. The audit system is another destination with its own access and retention rules; it must not receive raw credentials or every order field.

| STRIDE category | Question on this flow | Concrete control or test |
| ---------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Spoofing | Can a caller forge user or service identity? | Validate issuer, audience and credential evidence; reject a forged caller context |
| Tampering | Can an identifier, message or stored row be altered? | Bound input, bind SQL values and enforce authorized updates |
| Repudiation | Can attribution be lost or rewritten? | Restricted append-oriented audit records with actor/action/time and verified collection |
| Information disclosure | Can a different tenant's order or a secret escape? | Tenant/object policy and response projection; test a cross-tenant read |
| Denial of service | Can a cheap request induce unbounded work? | Body, query, deadline and concurrency budgets; exercise limit failure |
| Elevation of privilege | Can ordinary access become an admin operation? | Explicit operation/property policy; test a role-change denial |

Apply categories to relevant processes, stores, actors and flows. There is neither exactly one threat per boundary nor a requirement that every category produce a finding on every arrow. An idempotency key prevents duplicate effects under its contract; it does not by itself establish trustworthy audit attribution.

## Record a testable threat

This YAML is a design record, not an executable security configuration:

```yaml
id: THREAT-ORD-001
title: Cross-tenant order disclosure through guessed identifier
asset: Order details
flow: Browser -> Gateway -> Orders service -> Database
category: Information disclosure
assumptions:
  - Membership comes from trusted current server context
  - Order identifiers are discoverable and cannot be treated as authorization
impact: Exposure of another tenant's order
mitigations:
  - Scope repository lookup by trusted tenant and authorized relationship
  - Project only permitted response fields
verification:
  - Other-tenant identifier yields the documented denial response
  - Allowed read excludes internal notes and payment secrets
owner: orders-team
status: open
```

After implementation, attach the actual test and deployment evidence. A 404 policy can reduce object enumeration but does not eliminate timing or every other side channel. Updating `status: closed` without verification merely changes a document.

## Build an attack tree when several paths reach one goal

For “read another tenant's order,” possible branches include bypassing object checks, stealing a privileged credential, reading an overbroad export, or accessing a leaked backup. Defending the HTTP handler covers only one branch. An AND branch requires several conditions together; an OR branch offers alternatives. Bound the model to meaningful assets and actors instead of expanding every imaginable threat indefinitely.

Signed role claims can be valid evidence under a trusted issuer and freshness contract; they are not inherently untrustworthy. High-impact operations may need current membership lookup because issued claims can outlive a change. Device fingerprints are risk signals, not identity proofs. Generic login errors reduce enumeration, but equal wording does not guarantee constant execution time.

## Turn the model into engineering decisions

Prioritize by plausible impact, exposure and evidence. Record the mitigation owner, target date, verification and residual risk. A likelihood/impact matrix is a decision aid, not a measured probability. Review new trust boundaries, authentication changes, exports, dependencies and incidents; scheduled reviews supplement those triggers.

Threat modeling complements code review, penetration testing and production monitoring. It does not establish compliance by itself, and different contractual or regulatory programs have different evidence requirements. Explain the specific controls the system needs rather than claiming every standard mandates the same artifact.

## Mistakes and best practices

| Mistake | Better decision |
| ---------------------------------------------- | -------------------------------------------------------------------------- |
| “Internal” is treated as automatically trusted | Validate service identity and operation authority at the relevant boundary |
| A diagram is called the entire threat model | Add objectives, credible attack paths, mitigations and verification |
| “Use TLS” closes an object-access threat | Match the control to the failure; transport does not authorize an order |
| Every risk is marked high | State impact/exposure and uncertainty so owners can prioritize |
| A mitigation stays ownerless | Assign a team and an observable closure condition |
| Audit records contain payloads and tokens | Minimize/redact, protect access and define retention |

## Summary

Model assets and trust changes, follow a focused flow, and use STRIDE or attack trees to expose concrete failure paths. Turn each important threat into an owned mitigation and a test. Keep residual risk and assumptions visible as the system changes.

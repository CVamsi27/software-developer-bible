# Secrets Management

A database password copied into every deployment is easy to distribute and hard to revoke. Replacing its value in a central store does not, by itself, reload existing processes, invalidate cached copies, or drain authenticated database connections. Secrets management must cover that whole path.

## Definition

**Secrets management** governs credentials such as database passwords, application programming interface (API) keys and signing keys: how they are issued, stored, delivered, used, rotated and revoked. A secrets manager typically provides protected storage, identity-based access and audit records. Prefer workload identity and short-lived credentials where the destination supports them.

> **Textbook Definition:** Secrets management governs the issuance, storage, distribution, use, rotation and revocation of sensitive credentials. Identity-based access and auditability constrain exposure across the credential lifecycle.

The manager cannot stop an authorized, compromised workload from using a credential it can obtain. Limit that workload's permissions and the credential's destination authority separately.

## First Principles

A copied secret grants authority independently of the process that originally read it. Removing a file or rewriting Git history cannot retract copies. Exposure therefore requires destination-side revocation or rotation, followed by investigation of use.

Rotation crosses systems: the manager publishes a version, the destination accepts it, and consumers reload it. Changing these in the wrong order causes an outage. A short lifetime limits future authentication only under the destination's actual rules; existing sessions and failed revocation jobs require separate handling.

## Follow the credential from identity to use

```text
workload identity -> manager policy -> credential/version or lease
                                           |
                                           v
                                  bounded local cache
                                           |
                                           v
                               destination authentication
                                           |
                              refresh, rotate or revoke
```

Use a distinct workload identity and destination role per service/environment. Grant only required paths and operations. Audit reads without logging values. Environment variables and mounted files are delivery mechanisms; neither is automatically encrypted in process memory or safe from crash dumps. Kubernetes stores Secret data unencrypted in etcd by default, so enable encryption at rest and restrict API access with least-privilege role-based access control (RBAC). Base64 is an encoding, not encryption.

## Validate and refresh one fetched value

This complete JavaScript helper accepts a loader which returns an already validated value. It shares one concurrent load, caches only successful results, and rejects failures rather than silently returning an expired credential. The example clock is injectable for deterministic checks.

```javascript
function cachedSecret(load, ttlMs, now = () => performance.now()) {
  if (typeof load !== 'function' || !Number.isFinite(ttlMs) || ttlMs <= 0) {
    throw new TypeError('loader and positive TTL required');
  }
  let value, valid = false, expiresAt = 0, pending;
  return async function get() {
    if (valid && now() < expiresAt) return value;
    if (!pending) {
      pending = Promise.resolve().then(load).then(next => {
        value = next; valid = true; expiresAt = now() + ttlMs; return next;
      }).finally(() => { pending = undefined; });
    }
    return pending;
  };
}
module.exports = { cachedSecret };
```

At time zero, two callers share a fetch. Before expiry, both receive the cached value. After expiry, a failed refresh rejects; the old value is not returned as though current. Set the time-to-live (TTL) shorter than the manager's remaining lease, accounting for clock and refresh margin. Set bounded provider-client deadlines and retry with jitter; this helper does not implement remote identity, revocation or a database pool.

A Secrets Manager adapter must check `SecretString` versus `SecretBinary`, parse the expected representation, and validate required fields. Parsing JavaScript Object Notation (JSON) with `JSON.parse(...) as T` supplies no runtime validation. Keep secret identifiers trusted, configure region and workload permissions, and avoid returning provider diagnostics to callers.

## Rotate database connections without losing the boundary

For a static credential, provision the new destination credential, publish it, refresh consumers into a new pool, verify authentication and traffic, then drain old connections and revoke the old version. The exact overlap policy depends on whether the destination supports two usable credentials. Rewriting an environment-backed Secret does not update an already running process's environment.

Vault dynamic credentials have a lease ID, duration and renewal policy. Track the actual lease, renew before expiry when permitted, and create a replacement pool if renewal ends. Revocation can fail when the database is unreachable or privileges are insufficient; monitor those failures. Database expiry/revocation and termination of existing authenticated sessions are different contracts. Test the configured plugin and database behavior rather than assuming a TTL drops every connection immediately.

## Synchronize into Kubernetes deliberately

This External Secrets Operator recipe requires the installed `external-secrets.io/v1` custom resource definition (CRD), a configured `ClusterSecretStore` named `vault-backend`, and its authorized provider path:

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: orders-db
spec:
  refreshPolicy: Periodic
  refreshInterval: 15m
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: orders-db-secret
  data:
    - secretKey: DB_PASSWORD
      remoteRef:
        key: orders/db
        property: password
```

The provider configuration determines the path interpretation. This controller materializes a Kubernetes Secret, so Kubernetes permissions and encryption still matter. Projected volume data updates eventually, but a `subPath` mount does not receive automated updates; the application must also reopen or reload the value. Secret-backed environment variables are fixed when the container starts, so consumers need a Pod restart. Decide what happens when provider sync fails and the existing value ages beyond policy.

## A remote signature is not a signing key

Amazon Web Services (AWS) Key Management Service (KMS) `Sign` returns a signature, not a private key to pass into a JSON Web Token (JWT) library's `sign` function. For a JSON Web Signature (JWS), the signed message is the exact byte string `base64url(header).base64url(payload)`, not the payload alone. A vetted JWS integration must assemble that input, select the matching trusted key/algorithm, invoke KMS, and append the correctly encoded signature.

For JWS `RS256` (Rivest–Shamir–Adleman (RSA) PKCS #1 v1.5 with the Secure Hash Algorithm 256 (SHA-256)), KMS `RSASSA_PKCS1_V1_5_SHA_256` signs that input. `MessageType: RAW` lets KMS hash the input within its size limit; `DIGEST` expects the SHA-256 digest and avoids hashing it twice. The Elliptic Curve Digital Signature Algorithm (ECDSA) signature must be converted from KMS's encoding to JWS's fixed-width `R || S` representation. Publish the corresponding public verification key, map the `kid` header to an allowlisted key and algorithm, and retain verification keys while issued tokens remain valid. Use a maintained integration; this chapter does not present an unverified remote JWT signer.

A protected secret store can hold exportable private keys when the threat model permits it. KMS or hardware security module (HSM)-backed non-exportable keys reduce extraction risk but add service availability, quotas, latency and algorithm constraints. Neither option removes signing authorization or rotation requirements.

## Mistakes and operating decisions

| Mistake | Decision that prevents it |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| A secret entered Git, then was deleted | Revoke/rotate at the destination; investigate and remove retained copies as an additional step |
| Every service uses the root database password | Separate least-privilege destination roles and workload read policies |
| A build secret appears in an image layer | Use the builder's secret mount; never copy it into final layers or logs |
| A manager version changes but apps keep the old pool | Test reload, overlap, draining and rollback as one rotation procedure |
| A scanner found no secrets | Treat that as tool coverage, not proof; restrict exposure paths and review logs/artifacts |
| All reads succeed but unauthorized use remains possible | Limit destination authority and monitor usage as well as manager reads |

Choose lifetimes from exposure risk, refresh capability and destination behavior, not a universal 30-day rule. Measure manager/KMS latency and quotas in the actual region; no fixed millisecond figure applies to every deployment. Keep recovery identities protected and test manager outages without printing credentials.

## Summary

A secret is authority that can be copied. Use workload identity, scoped manager and destination permissions, validated delivery, and a tested rotation/revocation path. Caching and Kubernetes synchronization must account for remaining lifetime and consumer reload. Remote signing returns a signature over an exact protocol input; it does not return a key.

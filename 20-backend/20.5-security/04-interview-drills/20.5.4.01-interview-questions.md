# Security Interview Questions

## How to use this bank

These forty authored questions progress from boundary fundamentals to implementation and system scenarios. Answer with a concrete threat, the mechanism that prevents it, a failure case and evidence you would test. Code belongs in the linked learning chapter so each mechanism has one canonical implementation.

## First Principles

An attacker can choose inputs, repeat requests and exploit stale authority. For each answer, trace which boundary accepts untrusted data, which identity and policy authorize the operation, and what happens when a check fails. A control is useful only for the threat it actually blocks: escaping, request-intent checks and object authorization protect different boundaries.

## Boundary fundamentals

### Q1: What is XSS and how do you prevent it?

**Answer:** Attacker-controlled content becomes executable in a victim's browser context. Stored and reflected describe delivery; DOM-based describes client processing and can overlap them. Use textContent or framework text rendering for plain text, a maintained sanitizer for deliberately permitted HTML, and separate URL/scripting policies. CSP adds execution constraints; HttpOnly blocks direct cookie reads but not authenticated actions by injected code.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.01-xss.md).

**Follow-up**: "How would you handle XSS in a React application?"

React escapes ordinary text; audit explicit HTML sinks, validate link destinations, and test sanitizer/CSP behavior in the actual rendering environment.

### Q2: What is CSRF and how do you prevent it?

**Answer:** A browser can attach eligible session credentials to an attacker-initiated request. Protect cookie-authenticated unsafe operations with one coherent synchronizer-token or signed session-bound double-submit contract, plus appropriate SameSite and exact-origin policy. Naive cookie/header equality can fail under cookie injection. CORS does not stop every form submission, and XSS can defeat a page's request-intent checks.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.02-csrf.md).

### Q3: What is SQL injection and how do you prevent it?

**Answer:** Bind values rather than concatenate them into SQL grammar. Parameters generally cannot replace identifiers or keywords; choose those from authorized fixed allowlists. Genuine Prisma tagged interpolation binds values, while unsafe string construction restores injection. Least-privilege roles reduce reach but do not remove the flaw. Pattern wildcards remain meaningful data in LIKE even after binding.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.03-sql-injection.md).

### Q4: What is the difference between authentication and authorization?

**Answer:** Authentication validates identity evidence; authorization decides whether that identity may perform this operation on this object and its properties. A valid signed JWT can carry identity/permission claims under an issuer/freshness contract, but signature verification alone does not establish current object access. Trace trusted tenant context, ownership and response projection after authentication.

Source: [Mechanism and example](../01-auth/20.5.1.09-rbac-abac.md).

### Q5: What is HTTPS and why is it important?

**Answer:** HTTPS is HTTP over authenticated TLS. It protects transport confidentiality/integrity and verifies the peer under certificate/hostname rules. Identify each termination point and secure the next hop separately. HSTS learned over HTTPS protects subsequent connections; a first visit needs prior/preloaded policy for that protection. Automate certificate renewal and test failure without disabling verification.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.01-encryption.md).

### Q6: What is the difference between symmetric and asymmetric encryption?

**Answer:** Symmetric authenticated encryption uses shared secret material for bulk data. Public-key encryption, signatures and key agreement serve distinct jobs; a signature is not reverse encryption. TLS 1.3 authenticates peers and derives symmetric traffic keys through key agreement. Preserve nonce/tag/context metadata and check authentication before exposing plaintext; use the complete field-cipher example rather than an unfinished cipher.update fragment.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.01-encryption.md).

### Q7: What is a security header?

**Answer:** Response headers constrain supported browser behavior: CSP resource/execution rules, HSTS remembered transport policy, nosniff MIME behavior, frame-ancestors embedding, and Referrer-Policy metadata disclosure. Configure them for actual routes; Helmet defaults are a starting point. They do not authorize server objects or enforce every non-browser client behavior.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.02-web-security.md).

### Q8: What is the principle of least privilege?

**Answer:** Grant only the operations and resource scope required for a task. Separate destination roles and workload identities, review accumulated grants, and test denied paths. A read-only role can still disclose all data it may read; short lifetime does not narrow authority. Revoke obsolete access and retain emergency recovery paths under separate controls.

Source: [Mechanism and example](../01-auth/20.5.1.09-rbac-abac.md).

### Q9: What is input validation?

**Answer:** Check types, sizes and domain rules at each untrusted boundary, then use the parsed value. A TypeScript cast does not perform runtime validation. Validation neither authorizes a requested role change nor makes text safe in every output context. Background messages and provider responses introduce additional boundaries. Return safe errors rather than raw schemas or submitted secrets.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md).

### Q10: What is a JWT?

**Answer:** A JWT is a claims container represented using JWS signing/MAC or JWE encryption. The common signed form has encoded header, payload and signature; its payload is readable. Pin trusted issuer, audience, algorithms/key selection and time rules, validate application claims, and distinguish access from ID tokens. Revocation requires a state/freshness decision; cached verification must not extend validity.

Source: [Mechanism and example](../01-auth/20.5.1.05-jwt.md).

## Implementation decisions

### Q11: How would you implement OAuth 2.0 for a single-page application?

**Answer:** For a public SPA, use Authorization Code with S256 PKCE and an exact registered redirect URI. Bind state to the initiating transaction and consume it once; validate an OIDC nonce and ID token when login is in scope. Exchange the code and matching verifier at the token endpoint with the required grant type, client ID and redirect URI. A browser client cannot keep a confidential client secret. A BFF can retain provider tokens server-side but still needs secure cookies and CSRF policy.

Source: [Mechanism and example](../01-auth/20.5.1.06-oauth2-oidc.md).

### Q12: How do you handle session security in a microservices architecture?

**Answer:** Choose an authoritative session store or a short-lived signed-token/freshness model. Define outage and revocation behavior, session-ID rotation, idle and absolute expiry, cookie flags and CSRF policy. Services must validate trusted forwarded context rather than raw user headers. Redis clustering can improve availability but adds failover/consistency contracts; it does not make every session operation automatically safe.

Source: [Mechanism and example](../01-auth/20.5.1.04-sessions-cookies.md).

### Q13: How do you implement RBAC in a NestJS application?

**Answer:** Authenticate before the role/policy guard. Resolve handler and class metadata, intentionally declare public routes and deny protected routes with missing policy. Check current trusted roles/permissions and tenant/object scope; a role alone is insufficient. The RBAC chapter owns permission expansion and resource enforcement; the [NestJS guard chapter](../../20.2-nestjs/02-request-lifecycle/20.2.2.02-guards.md) explains guard wiring and metadata policy.

Source: [Mechanism and example](../01-auth/20.5.1.09-rbac-abac.md).

### Q14: How do you prevent open redirects?

**Answer:** Prefer an opaque redirect choice mapped to trusted internal destinations. If arbitrary external destinations are a real requirement, parse and validate the exact permitted HTTPS origin, port and credential policy. Host substring or slash-prefix tests miss parser normalization and scheme/port differences. OAuth callbacks require their registered redirect contract.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.02-web-security.md).

### Q15: How do you implement CSP for a React application?

**Answer:** Generate an unpredictable nonce per response, put the same value in allowed script tags and CSP, and preserve header/body coherence through caching. Use the framework's supported nonce plumbing and test hydration/resources. Report-only rollout observes compatibility; it does not enforce. A literal string containing ${res.locals.nonce} is not dynamic interpolation, and CSP never repairs every unsafe rendering sink.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.02-web-security.md).

### Q16: How do you handle password security?

**Answer:** Use a salted adaptive verifier such as Argon2id with measured memory/time/concurrency limits, then rehash accepted logins when parameters need migration. Bound attempts independently and check compromised passwords under the applicable identity policy. Avoid arbitrary composition rules and silent truncation; bcrypt's byte limit needs explicit handling. Recovery and MFA are part of the same account-security lifecycle.

Source: [Mechanism and example](../01-auth/20.5.1.01-auth-fundamentals.md).

### Q17: How do you implement rate limiting?

**Answer:** Choose a counting contract and keys from the protected resource: account plus network for login, tenant/user for quota, and endpoint work budgets for expensive reads. Fixed windows can admit a burst near a boundary; token/sliding approaches have other costs. A distributed store needs atomic updates and an outage policy; local limits multiply by replicas. Return documented 429/backoff behavior without enabling attacker-triggered permanent lockout.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md).

### Q18: How do you implement CORS correctly?

**Answer:** Allow exact configured browser origins, the required methods/headers and credential behavior. Credentialed responses cannot use wildcard origin. Some requests need preflight while ordinary forms can reach a handler without it. Missing Origin is not trusted identity; non-browser callers ignore CORS. Apply authentication, object policy and cookie-CSRF checks independently.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.02-web-security.md).

### Q19: How do you handle security in server-side rendering?

**Answer:** Trace server HTML rendering, embedded state serialization, hydration and response caching as separate contexts. Use supported framework serialization and safe text sinks; audit intentionally rendered HTML with the selected sanitizer. A JSON state blob is data, but incorrect embedding can let attacker text escape into executable markup. Prevent cross-user cache reuse and pair nonce-bearing bodies with their response policy.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.01-xss.md).

### Q20: How do you implement security logging?

**Answer:** Record security-relevant actor, action, resource category, outcome, time and correlation ID with minimization/redaction. Do not spread arbitrary request details into a log object or record passwords/tokens. Protect collection, access, retention and integrity; bound telemetry during floods. Test both expected events and secret absence, then connect alerts to an owned response procedure.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.03-threat-modeling-stride.md).

## Senior system scenarios

### Q21: Design a secure authentication system for a financial application.

**Answer:** Threat-model account takeover, recovery abuse and unauthorized sensitive transactions. Use calibrated password verification, phishing-resistant MFA where suitable, session/refresh lifecycle and operation-bound step-up for high-impact actions. Derive the user from validated context, not body userId. Device signals inform risk rather than prove identity. Bind step-up freshness to the actual session and operation, including expiry/replay handling.

Source: [Mechanism and example](../01-auth/20.5.1.08-mfa-passkeys-webauthn.md).

### Q22: Design a zero-trust security architecture.

**Answer:** Do not grant access merely because traffic originates inside a network. Combine verified user/workload identity, least privilege, resource-specific policy and bounded credential freshness. mTLS authenticates peers but not every business operation. Introduce controls incrementally around high-value boundaries; document policy-service outages, credential renewal and residual lateral movement.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.03-threat-modeling-stride.md).

### Q23: How would you implement encryption at scale?

**Answer:** Use vetted envelope encryption: authenticate the payload with a data key and wrap that key under a managed key. Store version/key identifier, nonce, tag, ciphertext and binding context. Key-encryption-key rewrapping differs from rotating a compromised data key, which may require payload re-encryption. Bound plaintext-key caching, test old backups and key retirement, and never expose unauthenticated decrypt output.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.01-encryption.md).

### Q24: How do you handle security in a microservices architecture?

**Answer:** Give services distinct workload identities and narrowly permitted destinations/operations. Authenticate service hops and verify delegated user context, then enforce tenant/object policy at the owning service. Network segmentation reduces reach but does not replace application authorization. Protect message input, secrets rotation, telemetry and recovery; a shared static token expands compromise across services.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md).

### Q25: How do you implement security monitoring and incident response?

**Answer:** Collect minimized security events, establish useful detection baselines, and assign alert severity/ownership. Rehearse containment, evidence preservation, credential revocation, recovery and communications. Treat anomaly scores as fallible signals; automatic blocking needs safeguards and review. Notification duties depend on applicable law, awareness and incident facts; involve the incident/privacy owner rather than asserting one universal clock.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.05-vulnerability-management-patch-governance.md).

### Q26: How do you handle security compliance (GDPR, HIPAA, PCI DSS)?

**Answer:** Determine applicable scope and accountable owners, inventory data/flows/recipients, and map obligations to controls and retained evidence. Minimize data, enforce access and retention, protect sensitive transport/storage, and test deletion/export/recovery paths. Consent is not the only possible legal basis, and retention is not universally seven years. Encryption or a report-generation method does not certify GDPR, HIPAA or PCI DSS compliance.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.03-threat-modeling-stride.md).

### Q27: How do you implement security testing?

**Answer:** Combine static analysis, deployed application probing, dependency/artifact and secrets scans with targeted adversarial tests. Exercise cross-tenant reads, protected property writes, malformed credentials, response projections and limit failures. An escaped substring assertion or null SQL result alone does not prove exploit prevention. Track tool coverage, false negatives, scanner versions and verified closure; human review remains valuable for attack chains.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.05-vulnerability-management-patch-governance.md).

### Q28: How do you handle security in a serverless architecture?

**Answer:** Scope each function's workload role and resource grants; validate every event source and authorize the specific object before using elevated credentials. API keys/usage plans can meter access but are not user authentication. Handle duplicate events, retries, deadlines and destination policy. Environment-backed secrets need appropriate platform permissions and reload/rotation; a manager does not automatically erase all exposure paths.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.04-secrets-management.md).

### Q29: How do you handle security for real-time applications?

**Answer:** Validate the handshake's identity and intended browser origin, then authorize and bound every message. Browser WebSocket construction cannot generally attach a custom Authorization header; choose secure cookies plus origin policy or a narrowly scoped ticket under the protocol contract. Avoid long-lived query tokens in logs. Recheck expiry/revocation, clean up bounded rate-limit state, limit queued bytes and use jittered reconnect/replay rules.

Source: [Mechanism and example](../../../60-realtime/INDEX.md).

### Q30: How do you handle security for file uploads?

**Answer:** Authorize upload creation, cap bytes before buffering and validate actual content rather than trusting MIME/extension. Quarantine until permitted scanning/transformation completes; serve on an isolated origin with correct content/disposition and access policy. Use server-selected object keys and safe parser resources. A presigned URL is temporary authority, not proof of safe content; scanner failure must not publish the file as clean.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md).

### Q31: How do you handle security for APIs?

**Answer:** Separate credential validation, operation/object/property authorization, schema validation and resource budgets. Reject unsupported updates and project permitted response fields. Validate outbound provider data and prevent SSRF through fixed destinations or connection-time policy. Retire exposed old versions and inspect route coverage. OWASP's list is a threat checklist, not evidence that a middleware stack covers every route.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md).

### Q32: How do you handle security for GraphQL APIs?

**Answer:** Bound document bytes, operations, aliases, page sizes, depth and estimated cost, then enforce actual execution/concurrency budgets. Authorize fields and nested objects with trusted context; schema validation is not authorization. Disabling introspection is optional hardening, not a substitute. Automatic persisted-query caching is not an allowlist; only a registered-operation policy restricts submitted operations under its exact contract.

Source: [Operation limits and authorization](../../20.7-graphql/03-clients-and-production/20.7.3.02-performance-security.md).

### Q33: How do you handle security for containerized applications?

**Answer:** Use supported minimal images, a non-root identity, dropped capabilities, read-only filesystem where compatible and enforced runtime profiles. Scan the built artifact and keep it patched. Separate workload/API/network grants; network-policy enforcement depends on the cluster plugin. Avoid secrets in layers, protect registry/provenance and test required writable directories. Non-root alone does not prove containment of an escape.

Source: [Mechanism and example](../../../40-platform/40.1-docker/INDEX.md).

### Q34: How do you handle security for CI/CD pipelines?

**Answer:** Treat pipeline code and dependencies as privileged attack surfaces. Untrusted contributions get no deploy secrets and narrowly scoped tokens; trusted release jobs can use constrained OIDC credentials. Pin and review executable dependencies, verify artifact provenance and protect promotion/rollback. An audit job's successful exit does not prove the released digest was scanned or that every workflow trigger is safe.

Source: [Mechanism and example](../../../40-platform/40.3-ci-cd/INDEX.md).

### Q35: How do you handle security for edge computing?

**Answer:** Check the actual runtime's CPU, crypto and network contracts rather than assuming all edges have identical restrictions. Validate at the edge boundary and preserve origin authorization. Define key-cache freshness, regional policy outage and personalized-cache isolation; canonicalize trusted cache inputs. Never cache an authenticated response across callers merely because its URL matches.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.02-web-security.md).

## Scale and domain scenarios

### Q36: Design a security system for a platform with 1 billion users.

**Answer:** Start with workload, exposure and regional assumptions rather than user count alone. Distribute key verification while preserving issuer, audience and time checks; define revocation freshness, outage behavior and compromise isolation by region/service. Account recovery, abuse budgets and telemetry need explicit capacity models. Cache verification results only until the earlier of token expiry and the relevant key or policy freshness bound; do not share authorization state across principals. One global Redis cluster does not solve regional consistency.

Source: [Mechanism and example](../01-auth/20.5.1.05-jwt.md).

### Q37: How would you implement security for a real-time collaboration platform?

**Answer:** Authorize current document membership on every operation and reconnect replay, validate protocol/schema/size, and bound processing and outbound queues. Operation IDs support idempotency under a stored deduplication contract. Revoke access during live sessions and test replay after removal. Server-side encryption is not end-to-end encryption; true client-held encryption changes key sharing, recovery, indexing and collaboration semantics.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md).

### Q38: How would you implement security for a financial trading platform?

**Answer:** Protect order identity, quantity/price constraints, authorization, sequence/replay and idempotent acceptance within a measured latency budget. If signatures are needed, specify canonical byte representation, key ownership, domain separation and replay/freshness; JSON.stringify alone is not a cross-system canonical format. Fraud scores need calibrated thresholds and review. Security and reporting obligations depend on the venue/product; latency does not justify skipping hot-path authority checks.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.01-encryption.md).

### Q39: How would you implement security for a healthcare platform?

**Answer:** Inventory electronic protected health information and enforce tenant, relationship, operation and property access, with audited emergency-access policy. Protect keys, backups, transport and log redaction; test denied reads and recovery. Do not equate patient consent with the only permitted access basis or imply minimum-necessary rules have no exceptions. Applicable HIPAA safeguards and obligations require policy/legal review; one encryption helper cannot establish compliance.

Source: [Mechanism and example](../03-hardening-and-operations/20.5.3.03-threat-modeling-stride.md).

### Q40: How would you implement security for a global payment platform?

**Answer:** Reduce card-data handling through suitable tokenized integrations while determining remaining PCI scope. Keep payment attempts idempotent, bind provider callbacks and reconcile unknown outcomes against an auditable balanced ledger. Fraud and sanctions checks need governed data, evidence, appeal/review and applicable jurisdiction rules. Define regional data/key boundaries, dual control and recovery. Tokenization or average risk scores do not certify compliance or guarantee fraud prevention.

Source: [Mechanism and example](../02-attacks-and-defense/20.5.2.04-api-security-best-practices.md).

## Summary

Name the trust boundary before the tool. Explain what is authenticated, what is authorized, what remains replayable or stale, and how failure is observed. For regulated scenarios, separate engineering controls from the applicable obligations and evidence.

## Beginner Questions (10)

### Q1: What is XSS and how do you prevent it?

**Answer:**

Cross-Site Scripting (XSS) allows attackers to inject malicious scripts into web pages viewed by other users. There are three types:

- **Stored XSS**: Malicious script saved on server
- **Reflected XSS**: Script reflected in URL/response
- **DOM-based XSS**: Script executes in browser via DOM

**Prevention:**

```typescript
// 1. Output encoding
function escapeHtml(text: string): string {
  const map: Record<string, string> = {
    "&": "&amp;", "<": "&lt;", ">": "&gt;",
    '"': "&quot;", "'": "&#039;", "/": "&#x2F;",
  };
  return text.replace(/[&<>"'/]/g, (char) => map[char]);
}

// 2. Use textContent instead of innerHTML
element.textContent = userInput;

// 3. Implement CSP
res.setHeader("Content-Security-Policy", "script-src 'self' 'nonce-xxx'");

// 4. Use DOMPurify for HTML sanitization
import DOMPurify from "dompurify";
const clean = DOMPurify.sanitize(dirtyHtml);

```

**Follow-up**: "How would you handle XSS in a React application?"

- React auto-escapes JSX
- Avoid dangerouslySetInnerHTML
- Use DOMPurify for user-generated HTML
- Implement CSP headers

### Q2: What is CSRF and how do you prevent it?

**Answer:**

Cross-Site Request Forgery forces authenticated users to execute unwanted actions. The attacker exploits the trust between the user's browser and the application.

**Attack Flow:**

1. User logs into bank.com (session cookie set)

2. User visits attacker's site

3. Attacker's site sends request to bank.com

4. Browser includes session cookie automatically

5. Bank processes the request as legitimate

**Prevention:**

```typescript
// 1. SameSite cookies
cookie: {
  sameSite: "strict", // or "lax"
  secure: true,
  httpOnly: true
}

// 2. CSRF tokens
const csrfToken = crypto.randomBytes(32).toString("hex");
req.session.csrfToken = csrfToken;
// Include in forms and validate on submission

// 3. Double Submit Cookie
// Set cookie with random token, require same token in header
res.cookie("csrf_token", token, { httpOnly: false });
// Client reads cookie and sends as header

```

### Q3: What is SQL injection and how do you prevent it?

**Answer:**

SQL injection inserts malicious SQL code into queries, allowing attackers to access, modify, or delete data.

**Prevention:**


Parameterization works because it separates *code* from *data* at the protocol level — the driver sends the query shape and the values on different channels, so `$1` can never be reinterpreted as SQL. Two follow-ups interviewers probe: first, an ORM is not a defense by itself — Prisma's raw query methods reintroduce injection the moment you interpolate a string; second, parameterization is one layer, not the plan — pair it with a least-privilege database user (so a successful injection reads one table, not the schema), strict input allowlists where dynamic identifiers are unavoidable, and query logging so an attempted `' OR 1=1 --` shows up as an incident, not a mystery.
```typescript
// 1. Parameterized queries
const query = "SELECT * FROM users WHERE id = $1";
const result = await db.query(query, [userId]);

// 2. Use ORM (Prisma)
const user = await prisma.user.findUnique({
  where: { id: userId }
});

// 3. Input validation
import { z } from "zod";
const schema = z.object({
  id: z.string().regex(/^\d+$/)
});

```

### Q4: What is the difference between authentication and authorization?

**Answer:**

- **Authentication**: Verifying identity (who are you?)
- **Authorization**: Checking permissions (what can you do?)

**Example:**


The confusion matters in practice because the two fail differently and are audited differently: authentication failures are global (a forged token is game over for every route), while authorization failures are per-resource (a missing `tenantId` check leaks one tenant's data to another). In code this is why they live in different layers — authentication runs once per request as middleware and attaches the verified identity, while authorization decisions need the identity *and* the target resource, so they belong in guards or policy checks at the service boundary. The common trap question is "which one does JWT do?" — JWT establishes identity claims; it decides nothing about what those identities may touch.
```typescript
// Authentication middleware
const authenticate = (req, res, next) => {
  const token = req.headers.authorization;
  const user = verifyJWT(token);
  req.user = user;
  next();
};

// Authorization middleware
const authorize = (roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) {
    return res.status(403).json({ error: "Forbidden" });
  }
  next();
};

// Usage
app.get("/admin", authenticate, authorize(["admin"]), adminHandler);

```

### Q5: What is HTTPS and why is it important?

**Answer:**

HTTPS is HTTP over TLS/SSL, encrypting all data in transit. It prevents:

- Eavesdropping (man-in-the-middle attacks)
- Data tampering
- Impersonation

**Implementation:**


The non-obvious part is what TLS buys beyond confidentiality: integrity (tampered payloads fail the MAC check) and server identity (the certificate chain is why a DNS-hijacked domain cannot present itself as your API). Interviewers expect the operational edges: HSTS prevents the first-request downgrade that makes SSL-stripping possible, certificates expire so rotation must be automated (ACME), and TLS terminates somewhere — anything behind the load balancer is plaintext again, which is why mTLS or an encrypted service mesh matters internally. Mixed-content browser warnings are the client-side symptom of the same rule: one insecure subresource taints the whole page.
```typescript
// Express with HTTPS
import https from "https";
import fs from "fs";

const options = {
  key: fs.readFileSync("private-key.pem"),
  cert: fs.readFileSync("certificate.pem"),
};

https.createServer(options, app).listen(443);

// HSTS header
app.use((req, res, next) => {
  res.setHeader(
    "Strict-Transport-Security",
    "max-age=31536000; includeSubDomains; preload"
  );
  next();
});

```

### Q6: What is the difference between symmetric and asymmetric encryption?

**Answer:**

| Aspect | Symmetric | Asymmetric |
| -------- | ---------------------------- | ------------------------- |
| Keys | Same key for encrypt/decrypt | Key pair (public/private) |
| Speed | Fast | Slower |
| Use Case | Bulk data encryption | Key exchange, signatures |
| Examples | AES-256, ChaCha20 | RSA, ECC |


The table's speed row is why TLS is a hybrid: asymmetric crypto authenticates and establishes trust (expensive, small payloads), then the session key it negotiated encrypts everything in bulk with AES. The direction confusion to avoid: signatures sign with the *private* key and verify with the public one — the reverse of encryption — which is what makes signatures non-repudiable; only the holder of the private key could have produced it.
```typescript
// Symmetric (AES)
const cipher = crypto.createCipheriv("aes-256-gcm", key, iv);
const encrypted = cipher.update(text, "utf8", "hex");

// Asymmetric (RSA)
const encrypted = crypto.publicEncrypt(publicKey, buffer);
const decrypted = crypto.privateDecrypt(privateKey, encrypted);

```

### Q7: What is a security header?

**Answer:**

Security headers are HTTP response headers that instruct browsers on how to behave securely. Essential headers:

- **CSP**: Controls resource loading
- **HSTS**: Forces HTTPS
- **X-Content-Type-Options**: Prevents MIME sniffing
- **X-Frame-Options**: Prevents clickjacking
- **Referrer-Policy**: Controls referrer information

The senior-level point is that headers defend against different attack classes, so they are not interchangeable: CSP addresses XSS, HSTS addresses SSL-stripping, `X-Frame-Options`/`frame-ancestors` addresses clickjacking, and `X-Content-Type-Options: nosniff` removes the browser's MIME-guessing that turns an uploaded file into an executable context. The interview follow-ups are operational: helmet's defaults are a floor, not a policy (CSP needs your own directives), and headers only protect the browser — APIs consumed by non-browser clients get nothing from them.

```typescript
import helmet from "helmet";
app.use(helmet());

```

### Q8: What is the principle of least privilege?

**Answer:**

Users and systems should only have the minimum permissions necessary for their function.

**Implementation:**


The reason it beats "grant everything, revoke when needed" is blast radius: a compromised credential with scoped grants has a ceiling — it can read users but not drop tables — while a compromised admin credential has none. The hard part in practice is not granting narrowly at creation but *not accumulating*: roles widen over time and service accounts collect permissions nobody remembers granting. The fixes are structural — short-lived credentials over static keys, permission boundaries on IAM roles, audit queries surfacing unused grants — and the same principle reads at the application layer as scoped API tokens (a read-only analytics token, a write-scoped webhook token) rather than one god-token per client.
```typescript
// Database user with limited permissions
// Grant only SELECT, INSERT, UPDATE on specific tables
// Don't grant DROP, ALTER, or admin permissions

// API with scoped permissions
app.get("/api/users", authenticate, requireScope("users:read"), handler);
app.post("/api/users", authenticate, requireScope("users:write"), handler);

```

### Q9: What is input validation?

**Answer:**

Input validation checks user input against expected formats before processing.


The design decision that separates senior answers: validation happens once, at the trust boundary, and everything inside is typed as validated. Re-validating in every function makes the schema a suggestion; validating only at the edge means any code path that skips the boundary is invisible. Zod's value is that the schema is a single source of truth — the parsed result is a TypeScript type, so the compiler propagates the guarantee. Two edges worth naming: allowlists beat denylists (you cannot enumerate every bad input, but you can define the good ones), and validation is not sanitization — escaping for HTML or SQL happens at the *output* layer, in the context where data becomes code.
```typescript
import { z } from "zod";

const userSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8).max(100),
  age: z.number().int().min(0).max(150),
});

const result = userSchema.safeParse(req.body);
if (!result.success) {
  return res.status(400).json({ errors: result.error.errors });
}

```

### Q10: What is a JWT?

**Answer:**

JSON Web Token is a compact, URL-safe token for transmitting claims. It consists of:

- Header (algorithm, type)
- Payload (claims, user data)
- Signature (integrity verification)


The properties that drive every real decision: the token is *signed, not encrypted* (base64-decode any JWT and read the payload — never put secrets in it), and it is *self-contained* (the server verifies without a round-trip, which is why it dominates distributed auth). Self-containment is also the cost: revocation is impossible without state, so the standard answers are short expiry plus refresh tokens, or a denylist keyed on `jti` — noting that the denylist quietly converts the stateless token back into a session. `alg: none` and key confusion (HS256 verified with a public key as the HMAC secret) are the classic implementation bugs a library with pinned algorithms closes.
```typescript
import jwt from "jsonwebtoken";

// Sign
const token = jwt.sign({ userId: "123" }, secret, { expiresIn: "1h" });

// Verify
const decoded = jwt.verify(token, secret);

```

### Q11: How would you implement OAuth 2.0 for a single-page application?

**Answer:**

Use Authorization Code flow with PKCE:


PKCE exists because a SPA cannot hold a client secret — anything in browser-bundled JavaScript is public, so the flow must be secure with only public clients. The `code_verifier`/`code_challenge` pair restores that: the authorization code is bound to the verifier, so an intercepted code (the historical attack via custom URL schemes and referrer leaks) is worthless alone. Two traps interviewers probe: implicit flow (`response_type=token`) is deprecated — tokens in URL fragments leak through history and referrers, which is exactly what PKCE replaced; and for SPAs the stronger architecture is a backend-for-frontend that keeps tokens out of the browser entirely, with refresh-token rotation when they must be held client-side.
```typescript
// 1. Generate PKCE challenge
const codeVerifier = crypto.randomBytes(32).toString("base64url");
const codeChallenge = crypto
  .createHash("sha256")
  .update(codeVerifier)
  .digest("base64url");

// 2. Redirect to authorization server
const authUrl = new URL("https://auth.example.com/authorize");
authUrl.searchParams.set("response_type", "code");
authUrl.searchParams.set("client_id", clientId);
authUrl.searchParams.set("redirect_uri", redirectUri);
authUrl.searchParams.set("code_challenge", codeChallenge);
authUrl.searchParams.set("code_challenge_method", "S256");

// 3. Exchange code for tokens
const response = await fetch("https://auth.example.com/token", {
  method: "POST",
  body: JSON.stringify({
    grant_type: "authorization_code",
    code,
    code_verifier: codeVerifier,
  }),
});

```

### Q12: How do you handle session security in a microservices architecture?

**Answer:**


The load-bearing decision is *where session state lives* when no single service owns the session: a shared Redis-backed store keeps every service honestly stateless — any replica can serve any request — but the cost is that the store becomes both a hotspot and a single point of failure, so cluster it and treat it as tier-0 infrastructure. The alternative (JWTs carrying session claims) removes the lookup but reintroduces revocation pain, which is why the hybrid is common: short-lived stateless JWT for the hot path, Redis for the revocation/session list behind it. The detail the code misses: `HttpOnly; Secure; SameSite` on the cookie, rotation of the session ID on privilege changes, and absolute expiry — a sliding-expiry session with no ceiling lives forever in a stolen tab.
```typescript
// 1. Use centralized session store (Redis Cluster)
const redis = new Redis.Cluster([
  { host: "redis-1", port: 6379 },
  { host: "redis-2", port: 6379 },
]);

// 2. Share session across services
const sessionStore = new RedisStore({ client: redis });

// 3. Validate session at API gateway
const validateSession = async (req, res, next) => {
  const sessionId = req.cookies.sessionId;
  const session = await redis.get(`session:${sessionId}`);
  if (!session) {
    return res.status(401).json({ error: "Invalid session" });
  }
  req.session = JSON.parse(session);
  next();
};

```

### Q13: How do you implement RBAC in a NestJS application?

**Answer:**


The guard pattern works because it separates *policy* (which roles may call this endpoint) from *mechanism* (how the request is verified) — the decorator declares intent at the route, the guard enforces it globally through `APP_GUARD`, and no handler can forget the check. The limits are worth naming before the interviewer does: RBAC answers "what role is this user", not "does this user own this resource" — that second question needs attribute- or policy-based checks (ABAC, or a policy engine like Oso/Casbin) layered on top. Roles also multiply fast; the cure for role explosion is permissions-as-data (role → permission set in the database) with the guard checking permissions, not role names.
```typescript
// 1. Create roles guard
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.get<string[]>(
      "roles",
      context.getHandler()
    );
    if (!requiredRoles) return true;

    const { user } = context.switchToHttp().getRequest();
    return requiredRoles.some((role) => user.roles.includes(role));
  }
}

// 2. Create roles decorator
export const Roles = (...roles: string[]) =>
  SetMetadata("roles", roles);

// 3. Use in controller
@Controller("users")
@UseGuards(AuthGuard, RolesGuard)
export class UsersController {
  @Get()
  @Roles("admin")
  findAll() {
    return this.userService.findAll();
  }
}

```

### Q14: How do you prevent open redirects?

**Answer:**


The attack is phishing infrastructure: the attacker crafts `https://your.com/redirect?url=https://evil.com` and your domain's trust — the real URL, the valid certificate, possibly the user's saved password — launders the jump. Hostname allowlisting is the core fix, but the edges decide the interview: scheme confusion (`javascript:` URLs pass some validators), origin-relative paths are safer than absolute URLs, and URL parsing quirks (backslashes, `@` in the authority) mean the allowlist must check the *parsed* hostname — never a substring match, which `evil-example.com` trivially defeats. The stronger construction for post-login redirects is a server-side map keyed by a short code, so no attacker-controlled URL ever enters the system.
```typescript
// 1. Validate redirect URLs
const validateRedirect = (url: string): boolean => {
  try {
    const parsed = new URL(url);
    const allowed = ["example.com", "www.example.com"];
    return allowed.includes(parsed.hostname);
  } catch {
    return false;
  }
};

// 2. Use relative URLs
const redirect = (path: string) => {
  if (path.startsWith("/") && !path.startsWith("//")) {
    return path;
  }
  return "/dashboard";
};

// 3. Use whitelist
const allowedRedirects = ["/dashboard", "/profile", "/settings"];
if (allowedRedirects.includes(req.query.redirect)) {
  res.redirect(req.query.redirect);
}

```

### Q15: How do you implement CSP for a React application?

**Answer:**


A nonce-based CSP is the strongest practical policy because it reframes the question from "which sources are safe" to "which scripts did *we* generate this request" — every injected script without the per-request nonce fails to execute, which is what actually stops XSS rather than reporting it. The failure modes are operational: `'unsafe-inline'` guts the policy and exists only as a legacy fallback (the nonce/hash directive beside it is what browsers honor); third-party tags demand openings that shrink the policy; and report-only mode exists so you can ship the header, watch violations for a month, then enforce. React makes this easier than it sounds — the framework renders with the nonce when configured, and the CSP stays one header, not component logic.
```typescript
// 1. Generate nonce per request
app.use((req, res, next) => {
  res.locals.nonce = crypto.randomBytes(16).toString("base64");
  next();
});

// 2. Configure CSP
app.use(
  helmet.contentSecurityPolicy({
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'", "'nonce-${res.locals.nonce}'"],
      styleSrc: ["'self'", "'unsafe-inline'"],
    },
  })
);

// 3. Use nonce in React
// In index.html or template:
// <script nonce="${nonce}">...</script>

```

### Q16: How do you handle password security?

**Answer:**


The point of Argon2id is that hashing is deliberately *slow and memory-hard*: one verification costs ~64 MiB and hundreds of milliseconds on your server, but orders of magnitude more at GPU/ASIC scale — which is what actually makes offline cracking uneconomical after a database leak. SHA-256 is the classic wrong answer precisely because it is fast *by design*: a leaked table cracks at billions of guesses per second. The operational details interviewers want: per-user random salt (built into Argon2's output format), rehash-on-login to ride parameter upgrades, breach checks (HIBP's k-anonymity API) before hashing — because no scheme saves `password123` — and login rate limiting independent of hash cost.
```typescript
// 1. Use Argon2id (recommended) or bcrypt
import argon2 from "argon2";

const hashPassword = async (password: string): Promise<string> => {
  return argon2.hash(password, {
    type: argon2.argon2id,
    memoryCost: 65536,
    timeCost: 3,
    parallelism: 4,
  });
};

// 2. Verify password
const verifyPassword = async (
  hash: string,
  password: string
): Promise<boolean> => {
  return argon2.verify(hash, password);
};

// 3. Enforce password policy
const passwordSchema = z.string()
  .min(8)
  .max(100)
  .regex(/[A-Z]/, "Must contain uppercase")
  .regex(/[a-z]/, "Must contain lowercase")
  .regex(/[0-9]/, "Must contain number")
  .regex(/[^A-Za-z0-9]/, "Must contain special character");

```

### Q17: How do you implement rate limiting?

**Answer:**


The design space is bigger than "pick a number": fixed-window counting is cheap but doubles the limit at window boundaries (2N requests in any two-window span), while sliding-window and token-bucket smooth that at slightly higher memory cost — the choice the Redis store encodes. The non-obvious production decisions: limit by user or API key where available and by IP only as fallback (NAT puts thousands of users behind one address), return `429` with `Retry-After` so well-behaved clients back off, and budget per endpoint class — login gets a tight per-account limit (brute force), search a loose global one (cost). Every limit is a denial-of-service surface against your own users, which is why the number is a product decision, not a constant.
```typescript
import rateLimit from "express-rate-limit";
import RedisStore from "rate-limit-redis";

// 1. Basic rate limiting
const limiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100, // limit each IP to 100 requests per windowMs
  message: "Too many requests",
});

app.use(limiter);

// 2. Redis-backed rate limiting
const redisLimiter = rateLimit({
  store: new RedisStore({
    sendCommand: (...args) => redis.call(...args),
  }),
  windowMs: 15 * 60 * 1000,
  max: 100,
});

// 3. Different limits for different routes
const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5, // 5 login attempts per 15 minutes
  skipSuccessfulRequests: true,
});

app.use("/login", authLimiter);

```

### Q18: How do you implement CORS correctly?

**Answer:**


The mental model that prevents every CORS bug: it is not a firewall — the browser *enables* the request and withholds the *response* from a disallowed origin; the server still received and processed the call. CORS protects users from other sites reading your API's responses, not your API from being called (that is auth and rate limiting). The dangerous shortcut is reflecting the `Origin` header back with `credentials: true` — that is "allow any site to make authenticated calls" spelled as code. Preflights exist only for non-simple requests, so a plain GET with no custom headers skips them entirely; and `Access-Control-Allow-Origin: *` is fine for public CDNs, never for cookie-authenticated APIs.
```typescript
import cors from "cors";

const corsOptions = {
  origin: (origin, callback) => {
    const allowed = ["https://example.com", "https://www.example.com"];
    if (!origin || allowed.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error("Not allowed by CORS"));
    }
  },
  methods: ["GET", "POST", "PUT", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization"],
  credentials: true,
  maxAge: 86400,
};

app.use(cors(corsOptions));

```

### Q19: How do you handle security in server-side rendering?

**Answer:**


SSR changes the threat model in one specific way: the server renders *user-controlled data into HTML* on every request, so injection opportunities multiply beyond client-side React's usual escapes. The defenses are the same primitives composed at a different layer: per-request nonces so only scripts you emitted can run (the CSP header must be set per response — a static nonce shared across users defeats the point), a hard rule auditing every `dangerouslySetInnerHTML` with DOMPurify on any path that uses it, and hydration as a boundary — data passed through `__NEXT_DATA__` renders inside a script tag, so untrusted strings must be encoded there. The state blob is the piece engineers forget: it executes, and it is attacker-controllable input.
```typescript
// 1. CSP with nonce for inline scripts
app.use((req, res, next) => {
  res.locals.nonce = crypto.randomBytes(16).toString("base64");
  next();
});

// 2. Set security headers
app.use(helmet());

// 3. Sanitize user data before rendering
const sanitize = (data: any) => {
  if (typeof data === "string") {
    return escapeHtml(data);
  }
  return data;
};

// 4. Use httpOnly cookies for session
app.use(
  session({
    cookie: {
      httpOnly: true,
      secure: true,
      sameSite: "strict",
    },
  })
);

```

### Q20: How do you implement security logging?

**Answer:**


Security logging differs from application logging in its questions: it is written for *detection and forensics*, not debugging — so the events are auth failures, permission denials, token misuse, and privilege changes, and the payload is who/what/when/where with correlation IDs tying a session across services. The classic failure is logging the secrets themselves: tokens, passwords, and PII must be redacted at the logger boundary (a redact format transform, not reviewer vigilance). The second is retention and integrity — logs an attacker can edit are not evidence, which is why shipping to an append-only sink (SIEM, WORM storage) beats local files. ### Q22: Design a zero-trust security architecture.

**Answer:**


The phrase collapses into one testable property: *no request is trusted because of where it comes from* — the VPC, the VPN, and the corporate laptop grant nothing; every call carries verified identity. ### Q23: How would you implement encryption at scale?

**Answer:**


Envelope encryption exists because the alternatives fail at scale: encrypting every field with the KMS master key means a KMS call per operation (latency, cost, rate limits), while one static key for everything means one leak decrypts the dataset. The envelope splits the roles — a per-record data encryption key does the bulk work locally, and only that DEK is wrapped or unwrapped by the master key, so KMS sees one call per record lifecycle, not per byte. The design points interviewers want: key rotation is cheap (re-wrap DEKs rather than re-encrypt data — rotate the KEK and the ciphertext never moves), the DEK cache is a deliberate tradeoff (speed versus how long plaintext keys live in memory), and KMS access logging becomes the audit trail of who decrypted what.
```typescript
// 1. Envelope encryption
class EnvelopeEncryption {
  private kms: AWS.KMS;

  async encrypt(data: Buffer): Promise<{ encryptedData: Buffer; encryptedKey: Buffer }> {
    // Generate data encryption key
    const dek = crypto.randomBytes(32);

    // Encrypt data with DEK
    const cipher = crypto.createCipheriv("aes-256-gcm", dek, iv);
    const encryptedData = Buffer.concat([cipher.update(data), cipher.final()]);

    // Encrypt DEK with KMS
    const encryptedKey = await this.kms.encrypt({
      KeyId: "alias/my-key",
      Plaintext: dek,
    }).promise();

    return { encryptedData, encryptedKey: Buffer.from(encryptedKey.CiphertextBlob) };
  }

  async decrypt(encryptedData: Buffer, encryptedKey: Buffer): Promise<Buffer> {
    // Decrypt DEK with KMS
    const decryptedKey = await this.kms.decrypt({
      CiphertextBlob: encryptedKey,
    }).promise();

    // Decrypt data with DEK
    const decipher = crypto.createDecipheriv("aes-256-gcm", decryptedKey.Plaintext, iv);
    return Buffer.concat([decipher.update(encryptedData), decipher.final()]);
  }
}

// 2. Key rotation
const rotateKeys = async () => {
  // Generate new key version
  const newKey = await generateNewKey();

  // Re-encrypt data with new key
  await reEncryptAllData(newKey);

  // Archive old key
  await archiveOldKey(currentKey);
};
```

### Q29: How do you handle security for real-time applications?

**Answer:**


WebSockets break the request/response assumptions the HTTP layer was hardened for: the handshake is a single URL (often with the token in a query string — which lands in access logs, so prefer a short-lived ticket), there is no built-in origin enforcement (browsers send `Origin`; the server must check it or any page can open the socket), and the connection is long-lived so a session revoked server-side stays live until you push invalidation. Every frame is untrusted input needing the same validation as an HTTP body, and rate limiting must be per-connection *and* per-message — a flood inside an authenticated socket bypasses every HTTP-level limiter. The operational footnote is reconnection storms after a restart: jittered backoff, or every client retries in lockstep.
```typescript
// 1. WebSocket authentication
const wsAuth = (ws, req) => {

  if (!user) {
    ws.close(1008, "Unauthorized");
    return;
  }

  ws.user = user;
};

// 2. Rate limiting for WebSocket

    userLimit.count = 0;
    userLimit.resetTime = now + 60000; // 1 minute
  }

  userLimit.count++;
  wsRateLimit.set(userId, userLimit);

  return userLimit.count <= 100; // 100 messages per minute
};
```

### Q30: How do you handle security for file uploads?

**Answer:**


The defense layering matters because every single check is bypassable alone: magic-byte validation (file-type) defeats extension lies but not a crafted polyglot; the allowlist defeats exotic types but the file still arrives attacker-controlled. The load-bearing decisions surround the check: serve uploads from a *different origin* (or a CDN bucket) so an uploaded HTML or SVG executes without your session cookies — SVG is a script host and this is the classic XSS-via-upload; randomize stored filenames (path traversal and overwrite attacks); enforce size limits *before* buffering (`file.buffer` means the whole file is in memory — stream large uploads and cap at the proxy too, or a 5 GB POST is your next outage); and never let upload paths touch `eval`, shell, or deserialization.

### Q34: How do you handle security for CI/CD pipelines?

**Answer:**


The pipeline is part of the attack surface now — it holds cloud credentials and runs attacker-influenced code (a PR's tests execute with access to secrets) — so the first control is *scope*: pull_request pipelines run with read-only tokens and no secrets, and deploy jobs should use OIDC-federated short-lived role assumption instead of a static AWS key (which makes the sketch's secrets block the weak point, not the strong one). Then the supply-chain layer: pin action versions by SHA (tags are movable), pin base images, and verify provenance with SBOM plus signing (cosign) so what you deploy is provably what you built. The threat model to state: a compromised pipeline is a compromised production — SolarWinds is the case study.
```yaml
# .github/workflows/security.yml
name: Security Scan

on: [push, pull_request]

jobs:
  security:
    runs-on: ubuntu-latest
    steps:

      - uses: actions/checkout@v4

      - name: Run Snyk to check for vulnerabilities
        uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}

      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: "myapp:${{ github.sha }}"

      - name: Run SAST
        uses: github/codeql-action/analyze@v2

      - name: Run dependency check
        run: npm audit --audit-level=high

      - name: Run SLSA provenance
        uses: slsa-framework/slsa-github-generator@v1.4.0
```

### Q35: How do you handle security for edge computing?

**Answer:**


Edge compute changes the calculus on two specifics. The runtime is constrained (no native code, short CPU budgets), so verification must fit the edge — stateless JWT verification with cached JWKS rather than session stores, and edge-replicated key material via services designed for it. And edge functions are *the* new public attack surface: they terminate requests before your origin's middleware ever runs, so the input validation and auth checks in the sketch are not duplicated effort — they are the actual boundary. Cache poisoning is the edge-specific class: attacker-controlled headers (Host, X-Forwarded-*) participating in the cache key let one crafted request serve malicious content to everyone — normalize the cache key before caching.
```typescript
// 1. Edge function security
export const handler = async (event: RequestEvent) => {
  // Validate input
  const validated = validateInput(event.request);

  // Authenticate at edge
  const user = await authenticateAtEdge(event.request);

  // Apply security headers
  const headers = {
    "Content-Security-Policy": "default-src 'self'",
    "Strict-Transport-Security": "max-age=31536000",
  };

  // Process request
  const response = await processRequest(validated, user);

  return new Response(response, { headers });
};
```

### Q36: Design a security system for a platform with 1 billion users.

**Answer:**


At a billion users the security design is a *distribution* problem before it is a cryptography problem: token verification must work at every edge (stateless JWTs with cached JWKS; revocation via short TTLs plus a distributed denylist), the revocation store must survive regional failures (the Redis cluster in the sketch is the standard answer — but decide its consistency posture explicitly, because an eventually-consistent denylist means a revoked token works for seconds, and that is a *choice* to document), and KMS calls become a throughput line item — envelope encryption with DEK caching is not optional. The interview's real test is naming the tradeoff ladder: per-region isolation for blast radius versus global consistency for instant revocation, MFA recovery at scale (a billion-user support queue is itself an attack surface), and the abuse/fraud layer — device fingerprinting and velocity checks — which at this scale catches more attacks than the auth layer does.
```typescript
// 1. Distributed authentication
class DistributedAuth {
  private redisCluster: Redis.Cluster;
  private kms: AWS.KMS;

  async authenticate(token: string): Promise<User> {
    // Check token in Redis Cluster
    const cached = await this.redisCluster.get(`token:${token}`);
    if (cached) return JSON.parse(cached);

    // Verify with KMS
    const user = await this.verifyWithKMS(token);

    // Cache in Redis
    await this.redisCluster.setex(`token:${token}`, 3600, JSON.stringify(user));

    return user;
  }
}

// 2. Global rate limiting
class GlobalRateLimit {
  private redis: Redis.Cluster;

  async checkLimit(userId: string, limit: number): Promise<boolean> {
    const key = `ratelimit:${userId}`;
    const current = await this.redis.incr(key);

    if (current === 1) {
      await this.redis.expire(key, 60);
    }

    return current <= limit;
  }
}

// 3. Security monitoring at scale
class SecurityMonitor {
  private kafka: Kafka;
  private elasticsearch: Elasticsearch;

  async logSecurityEvent(event: SecurityEvent) {
    // Send to Kafka
    await this.kafka.send({
      topic: "security-events",
      messages: [{ value: JSON.stringify(event) }],
    });

    // Index in Elasticsearch
    await this.elasticsearch.index({
      index: "security-events",
      body: event,
    });
  }

  async detectAnomalies(userId: string) {
    // Use machine learning for anomaly detection
    const anomalies = await this.mlService.detect(userId);
    return anomalies;
  }
}
```

### Q37: How would you implement security for a real-time collaboration platform?

**Answer:**


Real-time collaboration stacks three hard problems, and each has a security answer: identity (the WebSocket has no built-in auth, so the handshake carries a short-lived token and the server enforces origin checks — Q29's primitives), input (every frame is attacker-controlled; validate and size-limit before it touches the CRDT/OT engine, because one malformed op can corrupt the whole document), and abuse (per-user message rate limits as the sketch shows, plus per-document permissions checked *server-side* on every op — client-side cursors lie). The one that gets forgotten: after a disconnect, a reconnection replay must re-verify permissions — a revoked collaborator's client replaying queued ops is exactly how deleted users keep writing.
```typescript
// 1. WebSocket security
const wsSecurity = async (ws, req) => {
  // Authenticate connection
  const token = req.headers.authorization;
  const user = await verifyJWT(token);

  if (!user) {
    ws.close(1008, "Unauthorized");
    return;
  }

  // Rate limit messages
  const rateLimiter = new RateLimiter(100, 60000); // 100 msgs/min
  ws.on("message", async (message) => {
    if (!rateLimiter.check(user.id)) {
      ws.close(1008, "Rate limit exceeded");
      return;
    }

    // Validate message
    const validated = validateMessage(message);
    if (!validated.valid) {
      ws.close(1008, "Invalid message");
      return;
    }

    // Process message
    await processMessage(user, validated.data);
  });
};

// 2. Document-level security
class DocumentSecurity {
  async checkAccess(userId: string, documentId: string, action: string) {
    const permissions = await this.getPermissions(userId, documentId);
    return permissions.includes(action);
  }

  async encryptDocument(document: Document, key: string) {
    // End-to-end encryption
    const encrypted = await this.encrypt(document.content, key);
    return { ...document, content: encrypted };
  }
}

// 3. Audit logging
class AuditLogger {
```

### Q38: How would you implement security for a financial trading platform?

**Answer:**


Trading platforms add two constraints most security designs never face: *timing* and *integrity of market data*. Integrity: every order needs idempotency keys, sequence numbers, and server-side validation of price/quantity bands — client-supplied prices are never trusted — plus non-repudiation via signed orders, because "who placed this trade" is a regulatory question. Timing: latency budgets are so tight that some defenses must be chosen carefully — rate limiting per account (the sketch) is non-negotiable, but new cryptographic checks on the hot path need a latency budget, so they go at session establishment and settlement paths instead. Add segregation of duties (the person who deploys the matching engine cannot also approve trades), full audit trails, and market-abuse surveillance (spoofing, wash trades) as a first-class subsystem.
```typescript
// 1. Transaction signing
class TransactionSigner {
  private hsm: HSM;

  async signTransaction(transaction: Transaction): Promise<string> {
    // Hash transaction
    const hash = crypto
      .createHash("sha256")
      .update(JSON.stringify(transaction))
      .digest("hex");

    // Sign with HSM
    const signature = await this.hsm.sign(hash);
    return signature;
  }

  async verifySignature(
    transaction: Transaction,
    signature: string
  ): Promise<boolean> {
    const hash = crypto
      .createHash("sha256")
      .update(JSON.stringify(transaction))
      .digest("hex");

    return await this.hsm.verify(hash, signature);
  }
}

// 2. Real-time fraud detection
class FraudDetector {
  async analyzeTransaction(transaction: Transaction) {
    const features = this.extractFeatures(transaction);
    const prediction = await this.mlModel.predict(features);

    if (prediction.fraudProbability > 0.8) {
      await this.blockTransaction(transaction);
      await this.notifySecurityTeam(transaction);
    }
  }

  extractFeatures(transaction: Transaction) {
    return {
      amount: transaction.amount,
      frequency: this.getFrequency(transaction.userId),
      location: transaction.location,
      time: transaction.timestamp,
    };
  }
}

// 3. Compliance monitoring
class ComplianceMonitor {
  async monitorTrade(trade: Trade) {
    // Check for insider trading patterns
    const insiderTrading = await this.checkInsiderTrading(trade);
    if (insiderTrading) {
      await this.flagTrade(trade, "insider_trading");
    }

    // Check for market manipulation
    const manipulation = await this.checkMarketManipulation(trade);
    if (manipulation) {
      await this.flagTrade(trade, "market_manipulation");
    }

    // Log for regulatory reporting
    await this.logForReporting(trade);
  }
}
```

### Q39: How would you implement security for a healthcare platform?

**Answer:**


Healthcare's driver is HIPAA's structure: technical safeguards name specific controls — access control (unique user IDs, emergency-access procedures, automatic logoff), audit controls (log every ePHI access, reviewable), integrity (checksums on records), and transmission security (TLS everywhere, and ePHI at rest encrypted with keys you rotate). The design consequence: ePHI is *tagged and tracked* as a data class — a data inventory of every store, flow, and backup holding it, because a right-to-access request (patients can demand their records) becomes unanswerable without one. Minimum necessary applies per-field: a scheduling service sees demographics, not diagnoses. And break-glass access — clinicians in emergencies exceeding normal permissions — must exist, be logged loudly, and be reviewed after every use.
```typescript
// 1. PHI encryption
class PHIEncryption {
  async encryptPHI(data: any): Promise<any> {
    const phiFields = ["ssn", "medicalRecordNumber", "diagnosis"];

    for (const field of phiFields) {
      if (data[field]) {
        data[field] = await this.encrypt(data[field]);
      }
    }

    return data;
  }

  async decryptPHI(data: any): Promise<any> {
    const phiFields = ["ssn", "medicalRecordNumber", "diagnosis"];

    for (const field of phiFields) {
      if (data[field]) {
        data[field] = await this.decrypt(data[field]);
      }
    }

    return data;
  }
}

// 2. Access controls
class HealthcareAccessControl {
  async checkAccess(
    userId: string,
    patientId: string,
    action: string
  ): Promise<boolean> {
    // Check role-based access
    const user = await this.getUser(userId);
    if (!this.hasRequiredRole(user, action)) {
      return false;
    }

    // Check patient consent
    const consent = await this.getConsent(patientId, userId);
    if (!consent || !consent.granted) {
      return false;
    }

    // Check minimum necessary principle
    if (!this.isMinimumNecessary(user, action)) {
      return false;
    }

    return true;
  }
}

// 3. Audit logging
class HIPAAAuditLogger {
  async logAccess(
    userId: string,
    patientId: string,
    action: string,
    resource: string
  ) {
    await this.db.auditLog.create({
      data: {
        userId,
        patientId,
        action,
        resource,
        timestamp: new Date(),
        ipAddress: this.getIpAddress(),
        userAgent: this.getUserAgent(),
      },
    });
  }

  async generateReport(startDate: Date, endDate: Date) {
    // Generate compliance report
    const logs = await this.db.auditLog.findMany({
      where: {
        timestamp: { gte: startDate, lte: endDate },
      },
    });

    return this.formatReport(logs);
  }
}
```

### Q40: How would you implement security for a global payment platform?

**Answer:**


At global payment scale the security design is a *layered trust* problem: PCI DSS drives segmentation (the cardholder-data environment is a separate network zone, reachable only through tokenized interfaces — the cheapest compliant system stores no PAN at all, so tokenization is the architecture, not a feature), idempotent transaction processing with double-entry ledger integrity (every mutation is two balanced entries; nothing is ever updated in place), and fraud scoring as a synchronous inline check with asynchronous re-scoring feeding back rules. The design points interviewers reward: dual control on high-value operations, cryptographic key ceremonies and HSM-backed key custody for the PAN vault, regional data residency (payments data is legally sticky — plan the partition key before the first transaction lands), and reconciliation as a security control — an unbalanced ledger is an incident, not an accounting nuance.
```typescript
// 1. PCI DSS compliance
class PCIDSSCompliance {
  async encryptCardData(cardData: CardData): Promise<EncryptedCardData> {
    // Tokenize card number
    const token = await this.tokenize(cardData.number);

    // Store only last 4 digits
    return {
      token,
      last4: cardData.number.slice(-4),
      expiry: cardData.expiry,
    };
  }

  async processPayment(payment: Payment): Promise<PaymentResult> {
    // Validate PCI compliance
    await this.validatePCICompliance();

    // Process with tokenized card
    const result = await this.paymentGateway.charge({
      token: payment.cardToken,
      amount: payment.amount,
      currency: payment.currency,
    });

    return result;
  }
}

// 2. Fraud prevention
class FraudPrevention {
  async analyzeTransaction(transaction: Transaction) {
    const riskScore = await this.calculateRiskScore(transaction);

    if (riskScore > 0.8) {
      // Block transaction
      return { blocked: true, reason: "High risk" };
    }

    if (riskScore > 0.5) {
      // Require additional verification
      return { requireVerification: true };
    }

    return { approved: true };
  }

  async calculateRiskScore(transaction: Transaction): Promise<number> {
    const factors = [
      await this.checkVelocity(transaction),
      await this.checkLocation(transaction),
      await this.checkDevice(transaction),
      await this.checkAmount(transaction),
    ];

    return factors.reduce((a, b) => a + b, 0) / factors.length;
  }
}

// 3. Cross-border compliance
class CrossBorderCompliance {
  async validateCrossBorderPayment(payment: Payment) {
    // Check sanctions lists
    const sanctioned = await this.checkSanctions(payment);
    if (sanctioned) {
      throw new Error("Sanctioned recipient");
    }

    // Check AML requirements
    const amlCheck = await this.checkAML(payment);
    if (!amlCheck.passed) {
      throw new Error("AML check failed");
    }

    // Log for regulatory reporting
    await this.logForReporting(payment);
  }
}
```

# Service Discovery

## Definition

Service Discovery is a mechanism that allows services to find and communicate with each other dynamically in a microservices architecture. Instead of hardcoding instance addresses, callers resolve a logical service name through a registry, DNS or platform routing. Registration can be performed by services or by the platform.

> **Textbook Definition:** Service discovery resolves a logical service identity to currently usable network endpoints. Registration, health information and caching determine how quickly routing adapts to service membership and availability changes.

## First Principles

An instance address changes when a process is rescheduled. A stable service name therefore needs a mapping to current endpoints. Observations take time to propagate and clients cache them, so the mapping is always evidence with an age, not proof that the next connection will succeed.

A process heartbeat proves only that it could send a heartbeat. Readiness asks whether it can serve a defined workload. DNS can support dynamic discovery; it is neither inherently static nor a universal health checker.

## Trace discovery and connection separately

```text
logical name -> membership/health information -> endpoint selection -> connection
                          ^                           |
                          |                    cached until expiry
                    registry or DNS
```

**Client-side discovery** lets the application choose an endpoint from a set. **Server-side discovery** lets a proxy/load balancer choose behind a stable address. Both may use caches. A router need not query a registry on every request; its control plane can distribute updates.

For Kubernetes, a normal ClusterIP Service DNS name resolves to a stable cluster IP whose forwarding path selects endpoints. A headless Service exposes endpoint addresses so the client chooses. Named ports also have SRV records. EndpointSlice readiness normally means serving and not terminating, but a service proxy may still route to serving, terminating endpoints when all backends are terminating. `publishNotReadyAddresses` changes the readiness contract for consumers such as peer discovery. Existing connections, DNS caches and endpoint propagation can retain an old path after a change.

## Select only an unexpired ready endpoint

This complete JavaScript model demonstrates a local snapshot contract, not a distributed registry. A trusted controller supplies readiness and expiry based on its observation; callers cannot register arbitrary destinations through a public endpoint.

```javascript
function selectEndpoint(snapshot, now, cursor = 0) {
  if (!Array.isArray(snapshot) || !Number.isFinite(now) ||
      !Number.isSafeInteger(cursor) || cursor < 0) throw new TypeError('invalid selection');
  const ready = snapshot.filter(x => x !== null && typeof x === 'object' &&
    x.ready === true && Number.isFinite(x.expiresAt) && x.expiresAt > now &&
    typeof x.url === 'string');
  if (!ready.length) throw new Error('no usable endpoint');
  const chosen = ready[cursor % ready.length];
  const url = new URL(chosen.url);
  if (url.protocol !== 'https:' || url.username || url.password) {
    throw new Error('invalid controller endpoint');
  }
  return url.href;
}
module.exports = { selectEndpoint };
```

If A expires at time 10 and B at 30, time 10 excludes A; at time 30 neither is usable. Incrementing a caller-maintained cursor produces round-robin over the current filtered set. Random selection is a different policy. Snapshot filtering does not verify a live connection or authorize the destination; trusted membership and transport verification remain necessary.

## Membership failures and request failures are different

If the registry is unavailable, an explicitly bounded stale snapshot may preserve service for a low-risk read. Record its maximum age and stop using it after policy expires. Silently returning an empty list conceals the difference between “no endpoints” and “lookup failed.” For sensitive paths, current membership may be required.

A refused connection can trigger endpoint refresh/ejection and a bounded retry if the operation is retry-safe. A timeout after a write has an unknown outcome: rediscovery and retrying elsewhere can repeat the effect. Use the operation's idempotency/lookup contract; discovery cannot supply exactly-once behavior.

Long-lived HTTP/2 connections can keep requests on one endpoint despite membership changes. Drain old connections, test failover and consider client/channel balancing for gRPC. Selecting an SRV target requires the record's priority/weight semantics; treating every DNS answer as healthy and uniformly weighted changes that contract.

## Decisions and mistakes

| Condition | Decision |
| -------------------------------------------- | ------------------------------------------------------------------------------ |
| One stable Service forwarding path suffices | Use platform DNS/service routing instead of adding a custom registry |
| Clients need endpoint-aware balancing | Define membership refresh, readiness, connection draining and selection policy |
| Registry failure must not overload instances | Bound stale-cache use and retry/ejection rates |
| Multi-region failover changes data ownership | Coordinate routing with regional authority, not only network reachability |
| Endpoint discovery exposes a destination | Enforce trusted registration, identity and egress policy separately |

Measure lookup/update delay, cache age, connection errors and failed ejections. Choose TTL and health intervals from the recovery objective and load, not universal 30-second constants. An image registry stores artifacts; it is not the application's live endpoint registry.

## Summary

Discovery maps a logical service to endpoints, with membership/readiness observations and caches that can become stale. Selection, connection success, identity and retry safety are separate contracts. Prefer the platform's existing discovery when it meets the required routing and recovery behavior.

# API Gateway

The mobile app needs `/api/orders` to remain stable while checkout and order services deploy independently. A gateway can own that public route and shared edge checks, but it cannot decide whether a caller still owns a particular order.

## Definition

An **API gateway** receives requests for a configured public API and routes approved requests to backend services. It can apply shared policies such as credential checks, rate limits and request transformation. A system can have several gateways or other explicitly secured entry points; the pattern does not require every request to pass through one server.

> **Textbook Definition:** An API gateway mediates external client traffic into a service system by routing requests and enforcing shared edge policies. It does not remove the need for downstream authorization, resilience or service-specific contracts.

## First Principles

Clients need a stable contract while internal services evolve. A shared edge can hide endpoint topology and apply coarse admission, transport and telemetry policy. But the edge cannot infer every object's current ownership, so authoritative services still enforce business access and invariants.

Every extra route and transformation adds work to a shared failure boundary. Keep budgets and rollout explicit instead of building an unbounded application inside the gateway.

## Trace one order request

```text
client -> gateway route + coarse admission -> order service -> owned order data
             |                                  |
       verified credential                 object/property policy
```

The gateway validates credential evidence under the chosen protocol, removes caller-supplied identity headers, and forwards a trusted verifiable context. The service validates that context and current operation/object authority. A gateway check does not imply that bypass routes, messages or internal callers are authorized.

## Select routes on path boundaries

This complete helper chooses a configured service name. It does not proxy requests, validate identity or accept arbitrary destinations:

```javascript
const routes = [
  { prefix: '/api/orders', service: 'orders' },
  { prefix: '/api/products', service: 'products' },
];
function routeService(path) {
  if (typeof path !== 'string') throw new TypeError('path required');
  return routes.find(r => path === r.prefix || path.startsWith(r.prefix + '/'))?.service ?? null;
}
module.exports = { routeService };
```

`/api/orders/42` selects orders; `/api/orders-archive` does not. For overlapping configured routes, define and test precedence, often the most specific route. Parse and normalize the path exactly once under the gateway/framework contract; distinguish raw URL, decoded path and forwarded target to avoid ambiguous encodings.

## Forwarding must preserve HTTP semantics

A production proxy handles query strings, method/status, binary or streamed bodies, repeated response headers and cancellation. Remove hop-by-hop headers, control forwarded host/identity metadata and configure trusted proxies. Parsing a body before forwarding can consume it, invalidate a webhook signature or send a stale Content-Length. A generic `fetch` followed by `response.json()` is not a complete transparent proxy.

Bound upstream connection and total deadlines, queued requests, request/response bytes and per-backend concurrency. A circuit-breaker timeout does not necessarily cancel the upstream effect. Retrying or failing over a mutation needs the operation's idempotency/unknown-outcome contract. Keep errors safe while retaining route and upstream outcome in protected telemetry.

## Cache and aggregate only under an explicit contract

A URL-only cache key can return one user's order to another. Cache only eligible responses with correct authorization scope, representation variation, status/header policy, TTL and invalidation. Many personalized operations should not be cached at the edge. Calling `res.json` wrappers does not automatically intercept streamed proxy responses.

A backend-for-frontend (**BFF**) can compose a client-specific response, but define which dependencies are required and what partial failure means. Bound fan-out and propagate the remaining deadline; a missing recommendation can degrade while a missing payment authorization cannot be fabricated. Avoid hiding domain transactions in a gateway aggregation handler.

## Make shared policy rollout reviewable

Version routes and policy, validate configuration, canary changes and retain a rollback configuration. Multiple gateway replicas reduce one process failure but share bad configuration, identity-provider and discovery dependencies. State outage policy for each. Observe route latency, rejects, queue depth, upstream saturation and cache scope, then test a backend outage without exhausting unrelated routes.

## Summary

A gateway stabilizes the client-facing routing contract and shared edge policy. Services still own object authority and business invariants. Preserve forwarding semantics, bound fan-out and failure work, and treat caching, retries and configuration as explicit contracts.

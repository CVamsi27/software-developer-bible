# Service Mesh

A payment service receives a request over authenticated TLS, commits the charge, then loses its response. A proxy can standardize peer identity and traffic policy, but it cannot know whether repeating that write is safe. That boundary explains both the value and the limit of a service mesh.

## Definition

A **service mesh** is an infrastructure layer that manages selected service-to-service communication policies. It can provide traffic management, telemetry and workload identity through a managed data plane. A sidecar is one deployment model; Istio ambient uses a per-node L4 proxy with optional waypoint proxies for L7 features.
The application still owns business authorization and retry-safe effects.

> **Textbook Definition:** A service mesh applies communication policies through a managed data plane between services. A control plane configures routing, identity and observability; sidecar proxies are one deployment model rather than a defining requirement.

## First Principles

Every service hop needs connection policy and observations, yet application languages and teams implement them differently. A managed data plane can enforce consistent communication behavior while a control plane distributes identities and configuration. Separating these duties reduces repeated plumbing and introduces another system that must be operated.

The proxy sees network/protocol facts, not every domain invariant. It cannot infer whether an order belongs to this tenant or whether repeating a payment is safe.

## 1. Trace the control plane and one data-plane call

```text
control plane -> identities, endpoint and policy configuration -> managed proxies
                                                                  |
service A -> source proxy -> authenticated encrypted hop -> destination proxy -> B
```

Calls use the data plane. The control plane configures it; it does not ordinarily carry each application request. Istio's `istiod` provides discovery, configuration and certificate management.
Historical Pilot/Citadel/Galley labels are not separate current deployment components.

**Mutual TLS (mTLS)** authenticates both communication peers under the mesh identity/certificate rules. Explicit authorization policy determines permitted service calls. Test strict coverage and bypass paths; enabling injection is not proof that every connection is encrypted or that every request is authorized.

## 2. Sidecars and ambient proxies place costs differently

| Model | Where policy/traffic work runs | What to examine |
| ------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Sidecar | A proxy alongside each workload | Per-workload resources, interception, startup/shutdown and upgrade coupling |
| Istio ambient | Per-node ztunnel for secure Layer 4 transport; waypoint proxies for required Layer 7 behavior | Enrollment, waypoint coverage, shared resources and supported policy/features |

Layer 4 describes transport-level handling; Layer 7 describes application protocol handling such as HTTP routes. Neither model is free, and a sidecar count alone does not determine whether a mesh is worthwhile. Compare the actual supported features, traffic shape and platform ownership.
Product/version benchmarks are evidence for their measured workload, not universal 10 MB or 1 ms promises.

## 3. Trace a retry through an order write

A client sends an order creation, the destination commits it, and the response connection fails. A mesh retry can produce a second order unless the application's idempotency contract handles the repeated command. mTLS proves peer identity, not effect uniqueness. Coordinate client, gateway, mesh and service retry budgets so three layers do not multiply attempts.

Propagate application deadlines and cancellation, bound connection pools and concurrent work, and distinguish outlier ejection from end-to-end transaction recovery. Weighted routing can support canaries only when versions share compatible state and contracts. Shadow traffic must not repeat production writes.

## 4. Operate the policies as a system

Roll out to a selected workload group, verify intercepted paths/mTLS/authorization, and measure latency and resource demand under representative load. Test control-plane outages, certificate renewal, denied calls, drain and upgrade. Existing proxies may retain configuration during a control-plane failure while new workloads or identity renewal fail; behavior depends on the actual system and version.

Removing a namespace injection label does not remove proxies from already running Pods. Reverting enrollment/configuration may require workload rollout and compatible traffic policy. Tracing still needs application context propagation; network spans alone do not describe domain work.

## Decisions and mistakes

Use a mesh when shared communication requirements and operational capability justify it. A few services with high-value identity policy can justify one; many services can still use a well-operated library/platform alternative. There is no universal five- or fifty-service threshold.

| Mistake | Better decision |
| --------------------------------------------- | ---------------------------------------------------------------------------------- |
| mTLS is treated as tenant authorization | Keep domain/object/property checks in the authoritative application |
| Every failure is retried | Classify retry-safe operations and enforce one bounded attempt budget |
| Sidecar removal is called an instant rollback | Test policy and workload lifecycle rollback explicitly |
| Telemetry is assumed to need no app changes | Propagate context and instrument domain work separately |
| Mesh resources and ownership are unassigned | Budget the data/control planes and assign upgrades, identity and incident response |

## Summary

A mesh applies managed communication policy through a data plane configured by a control plane. Sidecars and ambient designs place policy and resource costs differently. Verify actual identity/policy coverage, bound retries, and retain application authorization and effect safety.

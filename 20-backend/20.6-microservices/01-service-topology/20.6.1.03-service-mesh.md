# Service Mesh

## Definition

A **Service Mesh** is a dedicated infrastructure layer for handling service-to-service communication in microservices. It applies traffic management, observability and communication security through managed infrastructure. A sidecar proxy is one deployment model; some meshes use shared or node-level proxies. **Istio** and **Linkerd** are examples. The application still owns business-level authorization and retry-safe effects.

> **Textbook Definition:** A service mesh applies communication policies through a managed data plane between services. A control plane configures routing, identity and observability; sidecar proxies are one deployment model rather than a defining requirement.

## First Principles

A service mesh answers one question: where do the *network's* responsibilities live?

1. **Service-to-service calls need TLS, retries, timeouts, mTLS identity, and telemetry — in every service, in every language.** Implementing them in each codebase guarantees drift; the mesh moves them into a per-pod sidecar proxy. Your code speaks plain HTTP; the mesh upgrades it to encrypted, retried, observed traffic — a platform decision, not a library.
2. **The sidecar is the price and the point**: uniform policy enforcement without touching app code (policy-as-code in the mesh config), at the cost of a hop and operational complexity. That trade is worth it at ~50+ services and questionable below.
3. **Traffic management is the hidden product**: canary splits, circuit breaking, and fault injection become config — release engineering (→ 50.4) without redeployment.

## Why Do We Need It?

1. **Traffic management**: Canary deployments, blue-green, circuit breaking, retries, timeouts
2. **Observability**: mTLS, distributed tracing, metrics (golden signals), access logs
3. **Security**: Automatic mTLS encryption, service identity, authorization policies
4. **Resilience**: Timeouts, retries, circuit breaking, fault injection for testing

## Istio vs Linkerd

| Feature | Istio | Linkerd |
| ------------------ | ------------------------------------------ | ------------------------------ |
| Proxy | Envoy (full-featured) | linkerd2-proxy (Rust, minimal) |
| Resource usage | ~100MB RAM per sidecar | ~10MB RAM per sidecar |
| Complexity | High (many CRDs) | Low (simple API) |
| mTLS | Automatic | Automatic |
| Traffic management | Advanced (header routing, fault injection) | Basic (traffic split) |
| Observability | Kiali, Jaeger, Prometheus | Built-in dashboard |
| Learning curve | Steep | Gentle |

**When to use Istio:** Complex traffic management, multi-cluster, need advanced features.
**When to use Linkerd:** Simple mTLS + observability, resource-constrained, faster adoption.

## Real-World Use Cases

- **The compliance-driven adoption is the honest origin story**: most meshes get installed for **mTLS everywhere with zero code changes** — a SOC2/PCI auditor asks "how do you encrypt service-to-service traffic," and per-service library retrofits across 15 teams is a two-year program while mesh mTLS is a namespace label (`istio-injection=enabled`). The traffic-management features then arrive as an unplanned dividend: the first `VirtualService` header-based canary replaces a nginx-weight hack the team was maintaining.
- **Rollout is per-namespace, never big-bang**: injection enabled on one namespace, p99 watched for the ~1-3ms sidecar tax, authorization policies applied there (`ALLOW` rules instead of network-level trust), then the next namespace. The rollback is removing a label — which is why mesh adoption is reversible in a way library-based approaches never are.
- **The sidecar tax spawned the next generation**: Istio's **ambient mode** (GA 2024) splits the data plane into per-node ztunnel proxies (L4/mTLS, Rust, ~KBs per pod) plus optional waypoint proxies (L7 only where policy needs it) — eliminating the per-pod sidecar RAM/CPU tax and the inject-upgrade-restart coupling (sidecar upgrades previously meant restarting every pod to swap the proxy). Cilium's eBPF approach pushes the same direction further (kernel-level, no proxy hop for L4). The interview-shaped point: "sidecar vs sidecar-less" is now the first architecture question, not "which mesh."
- **The operational coupling is the hidden bill**: the mesh is a distributed system managing your distributed system — control-plane HA, proxy upgrades, config CRDs with their own failure modes (a malformed `VirtualService` can blackhole a route). Teams without a platform owner for the mesh end up with the costs and a frozen version; the mesh decision is a staffing decision before it is an architecture one.

## Anti-Patterns

| Mistake | Fix |
| -------------------------------- | ------------------------------------------ |
| Adding mesh for 2-3 services | Mesh overhead > benefit at small scale |
| No resource limits on sidecars | Sidecars can starve application containers |
| Ignoring latency overhead | Each hop adds 1-3ms per sidecar |
| Using mesh for everything | Some services don't need mesh features |
| Not monitoring sidecar resources | Monitor CPU/memory of sidecar containers |
| Mesh without observability stack | Deploy Jaeger/Prometheus alongside mesh |

## When to Use (and When Not To)

**Use a service mesh when:**
- Multiple languages/frameworks (mesh handles cross-cutting concerns uniformly)
- mTLS is required (compliance, zero-trust)
- Canary deployments at L7 (traffic splitting by header/cookie)
- Need distributed tracing across services
- 10+ microservices with complex communication patterns

**Don't use a service mesh when:**
- < 5 services (just use libraries)
- Single language (use SDK-level features)
- Resource-constrained environments (sidecar overhead)
- Simple request-response patterns (REST is fine)

## Summary

- Service mesh abstracts service-to-service communication into a dedicated infrastructure layer
- Sidecar proxies (Envoy) handle traffic management, observability, and security transparently
- Istio and Linkerd are the leading service mesh implementations for Kubernetes
- Provides mTLS encryption, circuit breaking, traffic splitting, and distributed tracing out of the box
- Operational overhead of sidecar injection and resource consumption are key trade-offs to evaluate

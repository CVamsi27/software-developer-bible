# Strangler Fig Pattern

The replacement checkout commits an order, then its response times out. Sending the request to the monolith after that timeout may create a second order, and a route rollback cannot undo the first commit. A safe migration therefore moves both routing and state ownership in deliberate steps.

## Definition

The **Strangler Fig Pattern** is an incremental migration strategy: route selected capabilities to a replacement while the legacy system continues to serve the rest, then retire each old capability when its behavior, data and dependencies have been accounted for. The name comes from a fig that grows around its host over time.

> **Textbook Definition:** The Strangler Fig pattern incrementally replaces a legacy system by routing selected capabilities to a replacement while both systems coexist. Migration completes when replacement ownership and behavior allow the old capability to be retired.

## First Principles

A working legacy system contains behavior, integrations and data that a replacement must respect. Replacing everything at once concentrates uncertainty. Incremental migration makes each capability's boundary and cutover evidence smaller while old and new systems coexist.

A routing switch changes who receives requests; it does not reverse data changes already committed by the replacement. Rollback requires compatible state and authority, not only a feature flag.

## 1. Move one capability through explicit stages

```text
observe legacy contract -> introduce routing seam -> build replacement
           -> backfill + ordered changes -> compare safe reads
           -> controlled cohort cutover -> one write authority
           -> verify recovery and dependencies -> retire old capability
```

The target can be another monolith or module; microservices are not required. Choose a boundary with manageable integrations and meaningful success criteria. Introduce an anti-corruption layer when legacy representations differ, preserving the public contract while translating deliberately.

## 2. Keep cohort selection stable

This complete helper maps a trusted tenant identity to a deterministic cohort. The routing configuration is not supplied by the client. The helper chooses a destination name; it does not implement a proxy or guarantee data compatibility.

```javascript
const { createHash } = require('node:crypto');
function migrationTarget(tenantId, percentage) {
  if (typeof tenantId !== 'string' || !tenantId ||
      !Number.isInteger(percentage) || percentage < 0 || percentage > 100) {
    throw new TypeError('trusted tenant and percentage required');
  }
  const bucket = createHash('sha256').update(tenantId).digest().readUInt32BE(0) % 100;
  return bucket < percentage ? 'replacement' : 'legacy';
}
module.exports = { migrationTarget };
```

The same tenant stays on the same path at a fixed percentage. Increasing the percentage keeps existing selected buckets selected. At zero every tenant remains legacy; at 100 every tenant selects replacement.
Hash cohorts approximate a distribution, not an exact count, and a tenant's related operations may need to cut over together.

## 3. A timeout after a write is an unknown outcome

Suppose replacement checkout commits an order but its response is lost. Automatically calling legacy checkout in `catch` can create another order. Return/resolve the unknown outcome using a durable idempotency or operation-status contract.
A safe read fallback is a separate choice: it still needs acceptable freshness, ownership and consistent response behavior.

Routing rollback is safe only while the legacy path can understand all committed new state and remains the intended writer. If that condition ends after a schema or authority change, use a tested forward recovery or reverse migration. Record that point explicitly rather than promising instant zero-downtime rollback.

## 4. Migrate data without pretending two writes are atomic

`Promise.all([legacyWrite, newWrite])` can leave one database committed after the other fails. Prefer one authoritative writer. Propagate committed changes through either a transactional outbox, which records publication intent atomically with that writer, or database-log change data capture, which tails committed database changes.
Both introduce replication lag: identify versions, apply changes idempotently and in per-entity order, and reconcile after a crash.

Backfill at a known snapshot/watermark while retaining subsequent changes. A slow backfill must not overwrite a newer replicated version. Track deletions, ownership changes and derived relationships as well as inserts.
Row counts alone cannot establish correctness: compare entity IDs, versions and selected semantic checksums under a consistent observation boundary. Investigate mismatches without logging sensitive records.

## 5. Shadow only work that cannot create duplicate effects

For a catalog read, serve legacy while independently comparing replacement status and normalized semantic content. Ignore request IDs, timestamps or ordering only when the contract permits it; latency is measured separately, not compared as response equality. Bound shadow traffic and isolate it from user-critical resources.

A payment or notification cannot be safely shadowed by executing it twice. Use a sandbox, recorded inputs with external effects disabled, or a dry-run contract which is proven not to emit effects. Reusing one consumed request stream for two fetch calls is also not a valid replay mechanism.

## 6. Cut over and retire against evidence

| Gate | Evidence needed |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Contract compatibility | Authorized successes, denials, errors and important integrations match the chosen contract |
| Data readiness | Backfill complete at its watermark, replication lag within policy and semantic reconciliation acceptable |
| Cohort promotion | Outcome/error/latency evidence over a representative observation window, not a stub returning false |
| Recovery | Tested rollback or forward-repair path for writes and new schema/state |
| Retirement | No remaining routes, jobs, reports or external consumers need legacy ownership; backup/retention obligations handled |

Keep owners and milestones visible, including the cost of running both systems. Do not remove legacy merely because the replacement serves all interactive HTTP traffic; scheduled jobs and exports may still depend on it. Nor must every legacy component be split when it has no clear migration benefit.

## Summary

Strangler migration replaces capabilities incrementally through a stable seam. Cohorts, replication and comparison reduce uncertainty, but routing cannot undo committed state. Define write authority, unknown-outcome handling, compatibility and retirement evidence before cutover.

# gRPC

## Definition

**gRPC** is a high-performance, language-agnostic RPC framework developed by Google. It uses Protocol Buffers (protobuf) for serialization and HTTP/2 for transport, enabling bidirectional streaming, flow control, and multiplexing. gRPC is widely adopted for microservice-to-microservice communication where performance matters.

> **Textbook Definition:** gRPC is a remote procedure call framework with typed service contracts and unary or streaming exchanges. Its common Protocol Buffers and HTTP/2 implementation supplies encoding, multiplexing and flow control while applications own operation semantics.

## First Principles

A remote call needs a shared method/message contract and a way to distinguish successful results from transport failure. Protocol Buffers describe the common typed wire contract; generated stubs or runtime loading reduce hand-maintained encoding. A schema still does not prove an identifier is authorized or that a quantity satisfies a business rule.

HTTP/2 multiplexes calls as separate streams on one connection. TCP packet loss can still delay streams sharing that connection. Persistent connection reuse and binary representation can help some workloads, but neither establishes a universal speed or size advantage over an HTTP API using reuse and appropriate encoding.

## Trace one unary request

```text
GetUser({id}) -> /users.v1.UserService/GetUser
             -> server validates request -> result messages + final RPC status
```

A unary call has one request and one response; streaming shapes are taught in the next chapter. Each common gRPC message has a compression flag and a four-byte big-endian payload length. A message may span HTTP/2 DATA frames, and a DATA frame may contain parts of several messages. Compression is negotiated by encoding headers, not inferred solely from the flag.

HTTP status 200 does not prove RPC success: final `grpc-status` communicates the operation result, including trailers-only errors. Treat `UNAVAILABLE`, deadline expiry and application rejection according to the operation's retry/unknown-outcome policy.

## Run one complete local contract

Save this as `user.proto`:

```protobuf
syntax = "proto3";
package users.v1;
service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}
message GetUserRequest { string id = 1; }
message User { string id = 1; string name = 2; }
```

Install compatible `@grpc/grpc-js` and `@grpc/proto-loader`, then save this as `user.cjs` beside it. It exports a server/client factory for local demonstrations; credentials are explicitly insecure **on loopback only**, and there is no user authentication or database integration.

```javascript
const grpc = require('@grpc/grpc-js');
const loader = require('@grpc/proto-loader');
const path = require('node:path');
const definition = loader.loadSync(path.join(__dirname, 'user.proto'), {
  keepCase: true, longs: String, enums: String, defaults: true, oneofs: true,
});
const proto = grpc.loadPackageDefinition(definition).users.v1;
async function localUserService() {
  const server = new grpc.Server();
  server.addService(proto.UserService.service, {
    getUser(call, callback) {
      if (!/^[A-Za-z0-9_-]{1,64}$/.test(call.request.id)) {
        callback({ code: grpc.status.INVALID_ARGUMENT, details: 'invalid user id' }); return;
      }
      if (call.request.id !== 'u1') {
        callback({ code: grpc.status.NOT_FOUND, details: 'user not found' }); return;
      }
      callback(null, { id: 'u1', name: 'Alice' });
    },
  });
  const port = await new Promise((resolve, reject) => server.bindAsync(
    '127.0.0.1:0', grpc.ServerCredentials.createInsecure(),
    (error, port) => error ? reject(error) : resolve(port),
  ));
  const client = new proto.UserService(`127.0.0.1:${port}`, grpc.credentials.createInsecure());
  return { server, client };
}
module.exports = { localUserService };
```

Call `client.getUser({ id: 'u1' }, { deadline: Date.now() + 1000 }, callback)` and handle its error/result separately. `u1` returns Alice; empty ID returns `INVALID_ARGUMENT`; another valid ID returns `NOT_FOUND`. Close the client and gracefully shut down the server after the demo. Dynamic loading does not create compile-time TypeScript types; use generated types when that contract is required.

## Deadlines do not reverse committed effects

Choose a deadline from the caller's total budget and pass the remaining budget downstream through the actual language/runtime integration. Cancellation tells a handler to stop work, but the handler must cooperate and cancel its database/network tasks where supported. It does not roll back a transaction already committed. A write that times out needs idempotency or outcome lookup before retry.

TLS/mTLS authenticates the connection under certificate rules; call metadata credentials and resource policy supply further identity/authorization. Bound message size, active streams and work queues, validate data beyond protobuf shape, and redact telemetry. A guessed user ID must not be sufficient to read another tenant's user.

## Evolve and operate the contract

Reserve removed field numbers/names and never reuse tags. Check wire and application compatibility, optional/presence behavior, enums and JSON mappings under your tooling. A schema is versioned, not immutable. Keep generated clients synchronized without assuming every additive change is harmless.

Measure representative payloads, CPU, latency, connection behavior and error recovery. A Layer 4 balancer can pin one connection to a backend; native client endpoint-aware balancing or a suitable per-call proxy can address distribution without claiming every system requires a mesh. Browser clients use an appropriate gRPC-Web/Connect or HTTP adapter; supported streaming modes depend on the implementation.

## Summary

gRPC supplies method/message contracts and unary or streaming exchanges over its transport. Preserve final RPC status, propagate deadlines deliberately, and make handlers cooperate with cancellation. Schema validation, caller authority, retry safety and measured performance remain application decisions.

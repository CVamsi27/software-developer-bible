# gRPC

## Definition

**gRPC** is a high-performance, language-agnostic RPC framework developed by Google. It uses Protocol Buffers (protobuf) for serialization and HTTP/2 for transport, enabling bidirectional streaming, flow control, and multiplexing. gRPC is widely adopted for microservice-to-microservice communication where performance matters.

## First Principles

gRPC's properties all follow from its two base choices:

1. **HTTP/2 gives multiplexing**: many concurrent calls on one connection — no head-of-line blocking at the HTTP layer, bidirectional streaming as a first-class citizen. The transport enables the API shape.
2. **Protobuf gives the contract**: schemas typed, versioned, and code-generated for every language — with binary encoding an order of magnitude smaller than JSON. The contract-first discipline (→ 20.3.1.05) with a binary wire format.
3. **The trade is browser ubiquity.** Browsers speak JSON natively; gRPC-Web exists but adds a translation layer. So gRPC wins east-west (service-to-service) and loses north-south (public APIs) — knowing *which edge* you're designing is the whole decision.

## Why Do We Need It?

1. **Performance**: 5-10x faster serialization and deserialization compared to text-based JSON over HTTP/1.1.
2. **HTTP/2 Transport**: Stream multiplexing over a single persistent TCP connection eliminates connection setup latency and head-of-line blocking.
3. **Contract-First Rigor**: `.proto` files serve as an immutable, strictly-typed single source of truth across service teams.
4. **Automated Code Generation**: Eliminates hand-maintained API client SDKs by generating idiomatic TypeScript, Go, Java, and Python stubs.
5. **Streaming Primitives**: Native support for Unary, Server Streaming, Client Streaming, and Bidirectional Streaming without bespoke WebSocket protocols.

### REST vs gRPC

| Feature | REST | gRPC |
| --------- | :---------------------------------: | :-----------------------------------------: |
| Payload | JSON (human-readable text) | Protocol Buffers (compact binary) |
| Protocol | HTTP/1.1 (mostly) / HTTP/2 | HTTP/2 (required) |
| Streaming | Unidirectional (SSE / chunked) | Full native bidirectional streaming |
| Code gen | Optional / OpenAPI client gen | Native auto-generated client & server stubs |
| Browser | Native browser HTTP support | Requires gRPC-Web or Connect proxy |
| Contract | Ad-hoc or OpenAPI spec | Strict `.proto` schema definitions |
| Latency | Higher (parsing overhead + headers) | Ultra-low (binary packing + HPACK) |

## How It Works

### Wire Protocol & HTTP/2 Framing

gRPC operations map directly onto HTTP/2 request and response streams:

```text
CLIENT                                                          SERVER
  │                                                               │
  │─── HEADERS frame (:method POST, :path /UserSvc/GetUser) ────▶│
  │─── DATA frame (5-byte prefix [flags + length] + protobuf) ──▶│
  │                                                               │
  │◀── HEADERS frame (:status 200, content-type: application/grpc)│
  │◀── DATA frame (5-byte prefix + protobuf payload) ─────────────│
  │◀── HEADERS frame (trailers: grpc-status 0, grpc-message OK) ──│
  │                                                               │
```

1. **Request Headers**: Initiates a stream with `:method = POST`, `:path = /<package>.<Service>/<Method>`, `content-type = application/grpc`, and `te = trailers`.
2. **Length-Prefixed Message Framing**: Every gRPC message inside a DATA frame begins with a **5-byte header**:
   - `1 byte`: Compression flag (`0` = uncompressed, `1` = compressed with gzip/snappy).
   - `4 bytes`: Big-endian unsigned 32-bit integer indicating the exact length of the following protobuf payload.
3. **Trailers**: The RPC terminates with HTTP/2 trailer headers carrying `grpc-status` (e.g. `0` for OK, `4` for DEADLINE_EXCEEDED, `14` for UNAVAILABLE) and optional `grpc-message`.

### Deadlines & Cancellation Propagation

When service A calls service B, which calls service C, deadlines propagate downstream via the `grpc-timeout` header (e.g. `1000m` for 1000 milliseconds). If service A times out or client cancels, the HTTP/2 stream sends an `RST_STREAM` frame. Downstream servers catch the cancellation event, aborting in-flight DB queries and external calls to prevent cascading resource starvation.

## Code Examples

### Protobuf Definition

```protobuf
syntax = "proto3";

package users.v1;

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
  rpc ListUsers (ListUsersRequest) returns (stream User);
  rpc UpdateUser (stream UpdateUserRequest) returns (User);
  rpc Chat (stream ChatMessage) returns (stream ChatMessage);
}

message GetUserRequest {
  string id = 1;
}

message ListUsersRequest {
  string department = 1;
}

message User {
  string id = 1;
  string name = 2;
  string email = 3;
}

message UpdateUserRequest {
  string id = 1;
  string name = 2;
}

message ChatMessage {
  string user_id = 1;
  string message = 2;
}
```

### Node.js Server (Unary RPC)

```typescript
import * as grpc from '@grpc/grpc-js';
import * as protoLoader from '@grpc/proto-loader';

const packageDefinition = protoLoader.loadSync('user.proto', {
  keepCase: true,
  longs: String,
  enums: String,
  defaults: true,
  oneofs: true,
});

const proto = grpc.loadPackageDefinition(packageDefinition) as any;
const server = new grpc.Server();

server.addService(proto.users.v1.UserService.service, {
  getUser: (call: grpc.ServerUnaryCall<any, any>, callback: grpc.sendUnaryData<any>) => {
    const { id } = call.request;
    if (!id) {
      return callback({
        code: grpc.status.INVALID_ARGUMENT,
        details: 'User ID is required',
      });
    }
    // Simulate database lookup
    callback(null, { id, name: 'Alice', email: 'alice@example.com' });
  },
});

server.bindAsync('0.0.0.0:50051', grpc.ServerCredentials.createInsecure(), (err, port) => {
  if (err) throw err;
  console.log(`gRPC server listening on port ${port}`);
});
```

### Server Streaming

```typescript
// Server streams multiple results over a single HTTP/2 stream
function listUsers(call: grpc.ServerWritableStream<{ department: string }, any>) {
  const department = call.request.department;
  const users = [
    { id: '1', name: 'Alice', email: 'alice@example.com' },
    { id: '2', name: 'Bob', email: 'bob@example.com' },
  ];

  for (const user of users) {
    call.write(user); // Streams each user individually without buffering whole array
  }
  call.end(); // Closes the server-to-client stream
}

// Client consumes the incoming stream
const client = new proto.users.v1.UserService(
  'localhost:50051',
  grpc.credentials.createInsecure()
);

const stream = client.listUsers({ department: 'Engineering' });

stream.on('data', (user: any) => {
  console.log('Received user:', user.name);
});

stream.on('end', () => {
  console.log('Stream completed by server');
});

stream.on('error', (err: grpc.ServiceError) => {
  console.error('Streaming error:', err.message);
});
```

### Bidirectional Streaming

```typescript
// Both sides stream messages concurrently over full-duplex HTTP/2
function chat(call: grpc.ServerDuplexStream<any, any>) {
  call.on('data', async (incomingMessage) => {
    console.log(`Received message: ${incomingMessage.message}`);
    // Echo or broadcast back immediately over the active stream
    call.write({
      user_id: 'SYSTEM',
      message: `Ack: ${incomingMessage.message}`,
    });
  });

  call.on('end', () => {
    call.end(); // Finish writing when client finishes
  });
}
```

### Deadlines & Cancellation

```typescript
// Client initiates RPC with an explicit deadline
const deadline = new Date();
deadline.setSeconds(deadline.getSeconds() + 2); // 2-second timeout

client.getUser({ id: '123' }, { deadline }, (err: grpc.ServiceError | null, response: any) => {
  if (err) {
    if (err.code === grpc.status.DEADLINE_EXCEEDED) {
      console.error('Request timed out: deadline exceeded on call');
    } else {
      console.error('RPC Error:', err.message);
    }
    return;
  }
  console.log('User fetched:', response);
});

// Server detects client cancellation or deadline expiration
function processLongTask(call: grpc.ServerUnaryCall<any, any>, callback: grpc.sendUnaryData<any>) {
  const timer = setTimeout(() => {
    callback(null, { status: 'completed' });
  }, 5000);

  call.on('cancelled', () => {
    clearTimeout(timer);
    console.log('Client cancelled RPC; aborted in-flight background execution');
  });
}
```

## Real-World Use Cases

1. **East-West Microservice Meshes**: Inside Kubernetes clusters, services communicate over gRPC via Envoy/Istio sidecars, saving CPU on serialization and reducing latency across high-volume call graphs.
2. **Telemetry & Log Ingestion**: Client streaming allows agents (like OpenTelemetry collectors or FluentBit) to push batches of metrics and traces over open HTTP/2 streams without per-batch connection overhead.
3. **Financial Order Feeds & Market Data**: Server streaming pushes price ticks and order book deltas in compact binary format with minimal serialization latency.
4. **Polyglot Systems with Shared Domain Logic**: A Python machine learning inference service, a Go high-throughput data worker, and a NestJS BFF all consume the same `.proto` repository without hand-written client drift.

## Common Mistakes

| Mistake | Fix |
| -------------------------------------- | ------------------------------------------------ |
| Using gRPC for browser clients | Use gRPC-Web or REST gateway |
| No deadline set | Always set deadline (5-30s default) |
| Ignoring HTTP/2 connection reuse | gRPC uses long-lived connections; need proper LB |
| Large payloads over gRPC | Binary is fast but large = slow; paginate |
| No error handling in streaming | Handle `cancelled`, `error`, and `end` events |
| Protobuf schema evolution without care | Use field numbers, never reuse field numbers |

## Best Practices

1. **Use deadlines** — every RPC call should have a timeout
2. **Use interceptors** — for auth, logging, metrics (like middleware)
3. **Handle streaming errors** — `cancelled`, `error`, `end` events
4. **Use connection pooling** — HTTP/2 multiplexes, but pool for load balancing
5. **Version your proto files** — use package versions, never break backward compatibility
6. **Use gRPC-Web for browsers** — or proxy through Envoy/Connect
7. **Monitor with OpenTelemetry** — gRPC interceptors + OTel = full visibility

## Summary

- gRPC uses Protocol Buffers for efficient binary serialization and HTTP/2 for multiplexed streaming
- Four communication patterns: Unary, Server Streaming, Client Streaming, and Bidirectional Streaming
- Language-agnostic with auto-generated client/server stubs from .proto files
- Superior performance to REST/JSON for internal service-to-service communication
- Best suited for microservices, real-time streaming, and polyglot environments

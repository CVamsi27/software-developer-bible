# gRPC Streaming

> **TL;DR:** Server, client, and bidirectional streaming with gRPC — when REST falls short.

---

## First Principles

Streaming exists because "many values over time" is not one request-response:

1. **Three shapes cover all flows**: server-streaming (one request, many responses — feeds, logs), client-streaming (many requests, one answer — uploads, metrics batches), bidirectional (chat, live sync). Each is the response to a real interaction shape that unary RPC models awkwardly.
2. **Streams are long-lived connections, so backpressure and lifecycle matter**: flow control (HTTP/2 window), cancellation (context propagation — the client hanging up must cancel server work), and reconnect-with-resume are part of the contract, not edge cases.
3. **The failure mode is the forgotten close**: streams leak connections when neither side terminates — every streaming handler needs cancellation deadlines and explicit completion, the same resource-lifetime discipline as file handles (→ 20.1.2.03).

---

## Definition

**gRPC** is a remote-procedure-call framework that sends **Protocol Buffer**-encoded messages over **HTTP/2**, giving it a typed contract (`.proto`), multiplexed streams, and bidirectional streaming that JSON-over-HTTP/1.1 cannot express.

```text
service Chat {                        four modes — defined by *who* streams:
  rpc Get(Req) returns (Resp);           unary                1 ──▶ 1   request/response
  rpc List(Req) returns (stream Item);   server streaming     1 ──▶ N   push, feeds
  rpc Upload(stream Chunk) returns (Ack);client streaming     N ──▶ 1   uploads, aggregation
  rpc Chat(stream Msg) returns (stream Msg); bidi           N ◀─▶ N   chat, control planes
}
```

Four properties define the framework's behaviour and its limitations:

1. **The contract is compiled, not documented** — a `.proto` file generates client and server stubs in every language, so the schema is enforced at build time; this is the main reason it replaces hand-written REST clients for service-to-service work, and the main cost (schema changes require codegen and a compatibility discipline: never renumber fields, reserve removed tags).
2. **HTTP/2 is the substrate** — multiplexing (many concurrent calls over one connection), header compression, and true streaming come from the transport. It also means a long-lived connection carries state: client-side load balancing needs an L7-aware balancer (`grpc-lb`), because a plain L4 balancer pins the whole connection to one backend.
3. **Streaming changes the failure model** — a stream is a resource with a lifetime: backpressure is HTTP/2 flow control, cancellation is a context cancel propagated through the call tree, and a half-open stream must be bounded by deadlines, or leaked streams consume connection capacity.
4. **Deadlines and status codes are mandatory disciplines** — every call should carry a deadline (propagated, not re-created, downstream) and errors should use gRPC status codes (`UNAVAILABLE`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED`) so callers can decide retryability — which is also how retries stay safe (retry `UNAVAILABLE` with backoff, never a non-retryable status).

Browsers are the boundary: gRPC needs HTTP/2 trailers, which browser APIs do not expose, so browser clients go through **gRPC-Web** (with a proxy translating at the edge) or are served REST/JSON by a BFF — a decision that is usually made per client, not per service.

## What Is gRPC?

gRPC is a high-performance RPC framework built on HTTP/2 and Protocol Buffers. It's 2-10x faster than REST for inter-service communication because of binary serialization and HTTP/2 multiplexing.

```
REST/JSON:
Client → HTTP/1.1 → Serialize JSON → Server → Deserialize JSON → Process → Serialize JSON → HTTP/1.1 → Client
Overhead: ~2-5ms per request (serialization + connection setup)

gRPC:
Client → HTTP/2 (multiplexed) → Serialize Protobuf → Server → Deserialize Protobuf → Process → Serialize Protobuf → HTTP/2 → Client
Overhead: ~0.1-0.5ms per request (binary serialization, connection reuse)
```

## Streaming Modes

| Mode | Direction | Use Case |
| -------------------- | ----------------------------- | ------------------------------- |
| **Unary** | Request → Response | Standard RPC (like REST) |
| **Server Streaming** | Request → Stream of Responses | Real-time feeds, large datasets |
| **Client Streaming** | Stream of Requests → Response | File upload, batch operations |
| **Bidirectional** | Stream ↔ Stream | Chat, real-time collaboration |

## Server Streaming

Server sends a stream of responses to a single client request.

```protobuf
// appointment.proto
service AppointmentService {
  rpc WatchAppointments (WatchRequest) returns (stream AppointmentEvent);
}

message WatchRequest {
  string clinic_id = 1;
}

message AppointmentEvent {
  string type = 1; // "created", "updated", "cancelled"
  Appointment data = 2;
}
```

```typescript
// Server
watchAppointments(call: grpc.ServerDuplexStream<WatchRequest, AppointmentEvent>) {
  const clinicId = call.request.clinic_id;

  // Subscribe to real-time events
  const subscription = this.eventBus.subscribe(
    `clinic:${clinicId}:appointments`,
    (event) => {
      call.write({
        type: event.type,
        data: event.appointment,
      });
    }
  );

  call.on('cancelled', () => subscription.unsubscribe());
}

// Client
const stream = client.watchAppointments({ clinic_id: 'clinic-1' });
stream.on('data', (event) => {
  console.log(`Appointment ${event.type}:`, event.data);
});
stream.on('end', () => console.log('Stream ended'));
```

## Client Streaming

Client sends a stream of requests, server responds once.

```protobuf
service AnalyticsService {
  rpc BatchEvents (stream AnalyticsEvent) returns (BatchResponse);
}

message AnalyticsEvent {
  string event_type = 1;
  string user_id = 2;
  map<string, string> properties = 3;
}
```

```typescript
// Client: stream events
const call = client.batchEvents();
const events = [
  { event_type: 'page_view', user_id: '123', properties: { page: '/dashboard' } },
  { event_type: 'click', user_id: '123', properties: { button: 'export' } },
];

for (const event of events) {
  call.write(event);
}
call.end(); // Signal end of stream

call.on('data', (response) => {
  console.log(`Processed ${response.count} events`);
});
```

## Bidirectional Streaming

Both client and server send streams simultaneously.

```protobuf
service ChatService {
  rpc Chat (stream ChatMessage) returns (stream ChatMessage);
}

message ChatMessage {
  string user_id = 1;
  string content = 2;
  string room_id = 3;
}
```

```typescript
// Server
chat(call: grpc.DuplexStream<ChatMessage, ChatMessage>) {
  call.on('data', (message) => {
    // Broadcast to all connected clients in the room
    this.broadcastToRoom(message.room_id, message);
  });

  call.on('end', () => call.end());
}

// Client
const stream = client.chat();
stream.write({ user_id: '123', content: 'Hello!', room_id: 'general' });
stream.on('data', (msg) => {
  console.log(`${msg.user_id}: ${msg.content}`);
});
```

## Protocol Buffers vs JSON

| Property | Protocol Buffers | JSON |
| ------------------- | ----------------------- | --------------------- |
| **Size** | 2-10x smaller | Text-based, verbose |
| **Speed** | 2-10x faster (binary) | Slower (text parsing) |
| **Schema** | Enforced (.proto files) | Schema-less |
| **Code generation** | Automatic (protoc) | Manual |
| **Human readable** | No | Yes |
| **Browser support** | Via gRPC-Web proxy | Native |

```protobuf
// patient.proto
syntax = "proto3";
package docita;

message Patient {
  string id = 1;
  string name = 2;
  string email = 3;
  string phone = 4;
  repeated MedicalRecord records = 5;
}

service PatientService {
  rpc GetPatient (PatientRequest) returns (Patient);
  rpc ListPatients (ListRequest) returns (stream Patient); // Server streaming
  rpc UploadRecords (stream MedicalRecord) returns (UploadResponse); // Client streaming
}
```

## gRPC-Web (Browser)

Browsers can't make native gRPC calls. Use gRPC-Web proxy (Envoy or grpc-web-proxy):

```
Browser → gRPC-Web (HTTP/1.1) → Envoy Proxy → gRPC (HTTP/2) → Service
```

```typescript
// Client (browser)
import { GrpcWebClient } from 'grpc-web';

const client = new GrpcWebClient({
  hostname: 'https://api.docita.de',
});

const stream = client.watchAppointments({ clinic_id: '123' });
stream.on('data', (event) => {
  updateDashboard(event);
});
```

## When to Use gRPC

| Use Case | Recommendation |
| ------------------------------- | ---------------------------------------------- |
| **Microservice ↔ Microservice** | gRPC (performance, schema enforcement) |
| **API Gateway → Backend** | gRPC (internal communication) |
| **Browser → API** | REST or gRPC-Web (browser compatibility) |
| **Mobile → API** | gRPC-Web or REST (mobile clients support both) |
| **Third-party integration** | REST (public APIs should be REST/JSON) |
| **Real-time bidirectional** | gRPC streaming |

## Interview Questions

**Q: "When would you choose gRPC over REST?"**

> gRPC when: (1) internal microservice communication (2-10x faster), (2) you need streaming (server, client, or bidirectional), (3) you want strict schema enforcement via .proto files, (4) polyglot services (gRPC has code generation for 10+ languages). REST when: (1) public APIs (JSON is universally understood), (2) browser clients (native support), (3) third-party integrations, (4) caching via HTTP semantics (ETags, Cache-Control). For Docita: gRPC for internal service-to-service (NestJS → worker → analytics), REST for public-facing API.

## 30-Second Interview Version

> gRPC is built on HTTP/2 + Protocol Buffers — 2-10x faster than REST for inter-service communication. Four modes: unary (like REST), server streaming (real-time feeds), client streaming (batch upload), bidirectional (chat). Schema enforced via .proto files with auto code generation. For browsers, use gRPC-Web through an Envoy proxy. Use gRPC for internal microservices, REST for public APIs. The performance gain comes from binary serialization (not text JSON) and HTTP/2 multiplexing (not new connections per request).

## Summary

1. **gRPC streaming = client, server, and bidirectional modes** over HTTP/2 multiplexing
2. **Backpressure is built in** — flow control via HTTP/2 windows, unlike naive REST polling
3. **Streaming RPCs complicate load balancing** — L7 balancers need per-call awareness; L4 pins connections
4. **Deadlines and cancellation propagate** — the client context cancels server work end-to-end
5. **Interceptors are the middleware analog** — auth, logging, retry semantics per call

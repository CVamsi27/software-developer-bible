# Apache Kafka

## Definition

**Apache Kafka** stores event records in partitioned, replicated logs. Producers append records; consumers read them while tracking their positions. Retained records let independent consumers replay history. For example, inventory and analytics can read the same order events at different speeds. Capacity, failure recovery and delay depend on the chosen configuration and workload.

> **Textbook Definition:** Apache Kafka is a distributed event log organized into replicated partitions. Producers append records and consumers track offsets; ordering, retention and transaction guarantees are defined at specific partition and processing boundaries.

## First Principles

A durable append-only partition records positions independently of any one reader. Keeping records after consumption lets different groups maintain progress and replay retained history. Partitioning permits parallelism, but moves ordering into each partition rather than creating a global sequence.

A committed source record and a produced output can be separated by a crash. Progress must be coordinated with effects inside a stated boundary; an in-memory processed set disappears on restart and cannot supply that atomicity.

## Trace two consumers of one order history

```text
order producer -> orders partition: [offset 0][1][2]...
                                |                 |
                         inventory group     analytics group
                         own progress        independent progress
```

Inventory and payment need separate groups if both must see every relevant event. Members within a usual group share partitions, so putting them in one group divides work instead. A partition belongs to one active member under that assignment model; asynchronous effects, retries and rebalance can still alter completion order.

Choose a stable entity key such as order ID when per-order order matters. An invented random/timestamp key changes distribution and loses that relationship. Changing partition count can change key mapping; plan ordering and migration. Offsets are decimal positions per partition, not business event IDs.

## Acceptance, retention and progress have separate settings

Producer acknowledgments, replication and minimum in-sync replicas define durability/availability tradeoffs. Idempotent production prevents particular retry duplicates under the client's supported contract; it does not deduplicate a newly issued business command or external payment.

Retention/compaction determines which records remain replayable. Compaction retains latest keyed state and deletion semantics rather than every event forever. `fromBeginning` applies when no usable committed position exists; it does not override saved progress each restart. Keep offsets as strings/BigInt where required instead of rounding them through Number.

## Coordinate Kafka output and the next input offset

This complete TypeScript helper uses KafkaJS's real `Producer` and `EachMessagePayload` APIs. It requires an already connected transactional producer owned for this processing task, a serialized assigned input partition, and an explicitly supplied consumer group. The transform here is local and pure: it validates a JSON envelope and produces an identified projection record.

```typescript
import type { Producer, EachMessagePayload } from 'kafkajs';
export async function transformRecord(
  producer: Producer, input: EachMessagePayload, consumerGroupId: string,
): Promise<void> {
  if (!consumerGroupId || !/^\d+$/.test(input.message.offset) || !input.message.value) {
    throw new Error('group, decimal offset and non-null value required');
  }
  const event: unknown = JSON.parse(input.message.value.toString('utf8'));
  if (typeof event !== 'object' || event === null ||
      !('eventId' in event) || typeof event.eventId !== 'string' || !event.eventId ||
      !('orderId' in event) || typeof event.orderId !== 'string' || !event.orderId) {
    throw new Error('invalid order event');
  }
  const transaction = await producer.transaction();
  try {
    await transaction.send({ topic: 'order-projection-events', messages: [{
      key: event.orderId,
      value: JSON.stringify({ eventId: event.eventId, orderId: event.orderId, projected: true }),
    }] });
    await transaction.sendOffsets({ consumerGroupId, topics: [{
      topic: input.topic, partitions: [{ partition: input.partition,
        offset: (BigInt(input.message.offset) + 1n).toString() }],
    }] });
    await transaction.commit();
  } catch (error) {
    await transaction.abort();
    throw error;
  }
}
```

Use the KafkaJS transaction configuration `idempotent: true`, `maxInFlightRequests: 1`, and a stable task/input-partition transactional ID with fenced ownership. Disable independent consumer auto-commit and ensure rebalance/stale ownership is handled before work commits. Downstream consumers must use the committed-record isolation contract. This helper is not a complete rebalance-aware consumer service.

For input offset 42, successful commit coordinates its Kafka output with next offset 43. If output or offset submission fails, abort and do not independently advance input progress. Transactional fencing/ownership prevents a superseded producer from continuing. A transaction over Kafka outputs/offsets does not include an arbitrary database, email or payment effect: use that destination's local atomic deduplication/idempotency/outbox contract.

A shared constant transactional ID across unrelated active replicas causes fencing conflicts. Random IDs avoid that collision but do not by themselves preserve processing-task ownership across restart. Specify the task and failover model instead of hiding either case.

## Bound processing and recover poison records

Validate envelopes and classify malformed/permanent failures separately from transient dependencies. Bound retry time and attempts, record quarantined work durably and advance progress only under an explicit policy. Sending a failed record to another topic and committing its source position must itself be coordinated when loss is unacceptable. Retrying later can change per-entity completion order; use versions or a deliberate blocking policy.

Long handlers need correct heartbeat/session handling under the chosen client API. Pause or stop stale assignments and avoid committing results from work no longer owned. Monitor end/committed offsets, oldest event age, rebalances, publish failures, transaction aborts and partition skew. Offset lag is a position metric, not elapsed business delay.

## Select the log for the workload

Use retained independent consumption when it serves replay/projection/audit needs. Ordinary routed jobs may fit another broker or database-backed queue better. Kafka Streams is its own library/runtime; KafkaJS does not export fictional `KStream`/`KTable` APIs. An in-memory Map with one consumer is not automatically a durable globally complete table.

Benchmark representative payloads, partition keys, batching, compression, retention and failover. Set replication/ISR requirements from the availability and loss objective rather than asserting every workload has one mandatory configuration. Docita's current outbox/in-process mechanisms should not be presented as an existing Kafka deployment.

## Summary

Kafka retains partitioned records while groups track independent progress. Keys, retention and assignment define ordering/replay boundaries. Transactions can coordinate Kafka outputs and consumed offsets; external effects and rebalance-aware ownership still need explicit contracts.

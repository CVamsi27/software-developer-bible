# RabbitMQ

## Definition

RabbitMQ is an open-source message broker that implements the Advanced Message Queuing Protocol (AMQP). It provides reliable, flexible messaging between services with features like routing, acknowledgment, dead letter queues, and multiple messaging patterns (pub/sub, work queues, request/reply).

> **Textbook Definition:** RabbitMQ is a message broker that routes publications through exchanges to queues and delivers them under acknowledgment and retention rules. Routing topology and queue configuration determine delivery, durability and replay behavior.

## First Principles

A producer and worker can fail independently, so publication acceptance and completed work need separate acknowledgments. Routing adds another question: did any intended queue receive this publication? A local socket buffer accepting bytes answers none of those business questions.

Queues track outstanding deliveries, while exchanges select their destinations. A retry is a new delivery attempt, not merely a variable increment in one process.

## Follow the routing before the acknowledgment

```text
publisher -> exchange --binding--> queue -> worker -> business commit -> consumer ack
                |                    |
          publisher confirm     redelivery if outcome/ack uncertain
```

| Exchange | Binding rule | Example |
| -------- | --------------------------------- | ------------------------------------------------------------ |
| Direct | Exact key | `order.created` matches that key, not a wildcard pattern |
| Topic | `*` one segment, `#` zero or more | `order.*` matches `order.created` but not `order.created.us` |
| Fanout | Every bound queue | Each interested application gets a separate queue copy |
| Headers | Declared header conditions | Match configured attributes under the binding contract |

Workers sharing one queue compete for deliveries; separate bound queues are needed for independent processing. Queue type matters: ordinary classic/quorum queues differ from RabbitMQ Streams' retained replay model.

Queue order does not guarantee business-effect completion order when several consumers run concurrently. Requeue/redelivery and priority can also change which message a worker sees next. For strict serial effects, use a single active consumer and a queue configuration that preserves redelivery order. A Stream preserves append order and replay offsets, but concurrent handlers can still finish effects out of order.

RabbitMQ 4.3 disables non-durable, non-exclusive classic queues by default; use durable queues, exclusive temporary queues or durable queues with a TTL. RabbitMQ 4.3 also adds delayed retries for quorum queues. Configure `delayed-retry-type` and the minimum/maximum delay: selected returned or failed deliveries use linear backoff based on `delivery-count`. The delivery limit and terminal dead-letter policy still need explicit configuration. Older releases and other queue types need a separately designed retry path.

## Confirm one bounded publication

This complete TypeScript demonstration uses `amqplib`. It receives a trusted connection URL and pre-provisioned durable exchange/queue/binding configuration. It opens a dedicated channel for one bounded publication so a returned message belongs to this operation, then closes resources. Install compatible `amqplib` and type declarations. Real deployments usually reuse managed channels with per-publication correlation and bounded concurrency.

```typescript
import { connect } from 'amqplib';
export async function publishJob(url: string, eventId: string, payload: string): Promise<void> {
  if (!eventId || Buffer.byteLength(eventId) > 128 || Buffer.byteLength(payload) > 65_536) {
    throw new Error('invalid job');
  }
  try {
    JSON.parse(payload);
  } catch {
    throw new Error('payload must be valid JSON');
  }
  const connection = await connect(url);
  try {
    const channel = await connection.createConfirmChannel();
    try {
      let returned = false;
      channel.on('return', () => { returned = true; });
      await new Promise<void>((resolve, reject) => {
        channel.publish('jobs', 'pdf.invoice', Buffer.from(payload), {
          persistent: true, mandatory: true, messageId: eventId,
          contentType: 'application/json', timestamp: Math.floor(Date.now() / 1000),
        }, error => {
          if (error) reject(error);
          else if (returned) reject(new Error('job was unroutable'));
          else resolve();
        });
      });
    } finally { await channel.close(); }
  } finally { await connection.close(); }
}
```

A successful confirm means broker acceptance under its topology/queue contract, not consumer completion. `mandatory` lets an unroutable message return, which is distinct from a confirm. `publish()`'s boolean reports local writable pressure; it is not acceptance. This single bounded operation waits for its confirm before closing; a high-throughput publisher must honor pressure/drain and cap outstanding confirms. Add bounded connection/operation deadlines and classify an interrupted confirm as an unknown publication outcome.

Keep a stable event ID across retries. Losing the confirm can require retry even if the broker accepted the first copy. Durable definitions and persistent messages need the intended queue type/replication and publisher policy; a declaration alone does not prove survival of every failure.

## Acknowledge only the durably accepted effect

Use manual acknowledgments and a bounded prefetch. Validate the envelope, commit the business mutation and durable deduplication marker atomically, then acknowledge on the same channel which delivered the message. A crash after commit but before ack can redeliver; a committed marker prevents repeating the local effect. External email/payment needs its receiving-system idempotency or a durable job/outbox boundary.

`msg.fields.redelivered` is a delivery signal, not a proof of whether a business effect happened. Delivery tags are channel-scoped. An ack on a replacement channel cannot complete a delivery from the old channel. A null consume callback means server cancellation; handle it explicitly.

## Define a retry path that really moves the message

`nack(message, false, true)` requests requeue; immediate repeats can create a hot failure loop. `nack(message, false, false)` rejects without requeue and dead-letters only when the required dead-letter topology exists; otherwise work can be discarded. Computing `x-retry-count + 1` in memory changes no broker message.

For a delayed retry topology, define the retry destination, per-message attempt count and delay, and the path back to work. If republishing, confirm the retry publication before acknowledging the original; a crash between these can duplicate, so preserve event identity. Failed retry publication must not acknowledge the original as complete. Broker dead-letter reliability depends on queue/settings/version; choose and test the required at-least-once mode instead of assuming every DLX transfer is atomic.

An exhausted/permanently invalid record goes to a protected dead-letter destination with reason, identity and replay policy. A TTL is not by itself a retry counter. Terminal DLQs should not route themselves into an accidental cycle. Priority/length-limit arguments must actually be configured, not only logged.

## Reconnection, request/reply and shutdown have boundaries

Reconnect with one bounded/backoff loop, recreate intended topology/consumers and stop reconnecting after deliberate shutdown. Track active deliveries as a count or set; one boolean cannot represent concurrent handlers. Finish or release deliveries within the shutdown budget before closing the channel.

Request/reply needs correlation ID, bounded pending state, timeout cleanup and preserved reply properties. A timed-out request may still have executed. Direct Reply-to has special same-connection/channel/ack rules and at-most-once reply behavior; it is not a durable queue to declare on another connection. Use the dedicated protocol contract rather than a generic queue wrapper.

## Decisions and mistakes

Use RabbitMQ queues when routed tasks and per-delivery control fit the workload. Measure prefetch, unacked deliveries, ready queue age, confirms/returns, redelivery and dead-letter backlog. Set resource/attempt budgets and permissions per vhost/application; protect transport credentials. Do not assume persistence, a DLQ or a successful publish boolean proves end-to-end completion.

## Summary

Exchanges route publications; queue configuration and confirms establish broker acceptance; consumer acknowledgments follow completed handling. Unknown acknowledgments permit duplicates, and retry/dead-letter paths must actually move work under tested topology. Keep business effects idempotent and lifecycle work bounded.

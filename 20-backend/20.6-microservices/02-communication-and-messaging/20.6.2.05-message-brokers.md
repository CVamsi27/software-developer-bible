# Message Brokers — Kafka vs RabbitMQ

An invoice needs one PDF worker and two independent readers for reporting and audit. The worker should receive one unfinished job; each reader may need its own retained history. Choosing one broker name before separating those needs can hide the storage and acknowledgment contract the system actually requires.

## Definition

A **message broker** accepts messages from producers and delivers them to consumers. It can buffer work while consumers are unavailable, but its storage, acknowledgment and replay contracts determine what survives a failure.

> **Textbook Definition:** A message broker mediates asynchronous exchange between publishers and consumers through routing and buffering. Acknowledgment, persistence and redelivery rules define what survives failure and where duplicate handling is required.

## First Principles

Producers and consumers run at different speeds and can fail independently. A buffer separates their timing, but introduces questions a direct call did not answer:

- Has the broker accepted the message durably?
- Has a consumer completed the business effect?
- What happens if acknowledgment is lost?
- Can another consumer later read the same history?

Choose the storage/delivery model from those questions before choosing a product.

## 1. Two ways to store the same invoice event

```text
Retained log: producer → topic partition → records remain until retention/compaction
                                           group A: billing projection
                                           group B: analytics projection

Work queue: producer → exchange → queue → available worker → acknowledgment
                                    unfinished deliveries remain eligible for work
```

#### Kafka: position in a retained partition

A **topic** groups records. Its **partitions** hold ordered sequences; an **offset** identifies a position within one partition, not a globally unique business event. A **classic consumer group** coordinates members so each partition is assigned to one active member at a time.
Another group maintains independent progress over the same records. Kafka's **Share Consumer** model instead lets multiple share-group members process records from the same partition and acknowledge individual records. It is useful for queue-like work, but does not preserve the classic group's one-active-consumer-per-partition ordering contract; verify cluster and client support before choosing it.

Consumers commit offsets to record progress. Reading a record does not remove it. Replay is possible while the required records remain available under retention/compaction rules.
Compaction retains latest values by key rather than promising every historical event forever.

Partitioning by invoice ID keeps that invoice's records together. It does not create global order across all invoices. More consumers than assigned partitions do not increase that group's partition-level parallelism.

#### RabbitMQ: route a message to eligible work

An **exchange** routes published messages to **queues** using **bindings**. A consumer processes queue deliveries and acknowledges completion. For ordinary classic/quorum queues, successful acknowledgment removes that delivery from the outstanding work; they are not a retained historical log.

| Exchange | Routing rule | Example |
| -------- | ------------------------------------------------------------ | ------------------------------------------- |
| Direct | Exact routing-key match | pdf.invoice |
| Topic | Pattern match; * matches one segment, # matches zero or more | invoice.*.created |
| Fanout | Every bound queue | Separate notifications and analytics queues |
| Headers | Binding conditions on headers | Route using declared header attributes |

Multiple workers consuming one queue compete for work. Independent consumers that must each receive a copy generally need separate bound queues. Multiple active consumers, requeue/redelivery and priority can affect processing order.
One active consumer may still receive multiple unacknowledged messages, so strict serial handling also needs prefetch one or a serialized handler and a queue contract with the required redelivery order. A Stream preserves append order and replay offsets, but concurrent handlers can still finish effects out of order.

**RabbitMQ Streams are a different storage model:** they retain an append-only log with offset-based consumption and replay. “RabbitMQ cannot replay” is therefore an incorrect product-wide claim. Compare Kafka with the particular RabbitMQ queue/stream type being proposed. [RabbitMQ Streams](https://www.rabbitmq.com/docs/streams)

## 2. Trace the acknowledgment gap

| Failure point | What the application knows | Required response |
| ------------------------------------------------------------ | ------------------------------------------------ | -------------------------------------------------- |
| Publish sent, acceptance acknowledgment lost | Broker may have accepted it | Retry can duplicate; preserve a stable event ID |
| Broker accepted, consumer not started | Work is stored under configured durability rules | Monitor backlog and consumer availability |
| Consumer effect committed, acknowledgment/offset commit lost | Delivery may return | Deduplicate the business effect |
| Consumer acknowledges before its effect commits | Broker may consider unfinished work complete | A crash can lose the effect; reverse that ordering |

Publisher acknowledgment and consumer acknowledgment answer different questions. Neither alone proves end-to-end completion.

For Kafka, durability depends on acknowledgment level, replication and in-sync-replica configuration. Producer idempotence addresses certain duplicate writes caused by producer retries; it does not make an external payment or database mutation exactly once.

For RabbitMQ, durable queue definitions and persistent messages belong with publisher confirms and an appropriate queue type/replication policy. A normal channel's `publish()` returning does not establish a publisher confirm. An unroutable message needs routing/return handling too: a confirm alone does not mean a useful queue received it.
[Confirms and consumer acknowledgments](https://www.rabbitmq.com/docs/confirms)

## 3. Turn delivery guarantees into application behavior

| Delivery contract | How loss/duplication arises | Suitable boundary |
| -------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| At-most-once | Work can be lost when progress advances before completion | Only when loss is acceptable |
| At-least-once | Work returns when completion acknowledgment is uncertain | Idempotent consumer plus durable progress |
| Exactly-once within a defined transaction boundary | Atomic coordination avoids duplicate committed effects inside that boundary | State the participating systems; do not extend the claim to arbitrary external effects |

A consumer should validate the envelope, atomically commit its local business mutation and deduplication marker, then acknowledge. External effects need their own idempotency contract or an outbox. Kafka auto-commit settings must be understood at batch/run boundaries; receiving a message is not proof its effect was committed.
With the Confluent client shown here, `auto.offset.reset` applies only when the group has no usable committed position; it does not override valid saved progress on every restart.

## 4. Keep retries from becoming an outage

Separate transient failures from malformed or permanently rejected work. Bound attempts, apply delay/backoff and route exhausted work to a **dead-letter queue** for inspection. Carry attempt metadata per message; a shared in-memory counter cannot track distributed retries.

Immediate `nack(..., requeue=true)` loops can monopolize workers. A queue TTL expires waiting messages; it is not by itself a correct per-attempt retry policy. A dead-lettered message is not automatically repaired.
Replay needs authorization, an audit trail, fixed failure cause and protection against repeating successful side effects.

Ordering also has a boundary: concurrent workers, redelivery, priorities and separate retry queues can change completion order. Exchange type does not solve that. Serialize work by entity or enforce aggregate versions when the business requires it.

RabbitMQ 4.3 adds broker-managed delayed retries for quorum queues. Configure the return/failure condition and delay bounds; because `delivery-count` does not increase for every return type, test the configured retry mode. Delivery limits, terminal dead-letter policy and monitoring remain application/queue decisions.

## 5. Select a broker from the workload

| Requirement | Starting point | What to verify |
| ------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------- |
| Independent readers and retained replay | Kafka or RabbitMQ Streams | Retention, consumer offsets, partitioning and operational support |
| Routed tasks with worker competition | RabbitMQ queues | Queue type, routing, confirms, acknowledgments and retry policy |
| Large sequential event pipelines | Kafka is a common fit | Actual batch size, partition throughput, lag and recovery cost |
| Flexible routing to separate queues | RabbitMQ exchanges | Binding correctness and unroutable-message handling |
| Small existing application with durable background work | A database-backed queue may suffice | Atomic enqueue, leasing, retry bounds and backlog visibility |

Do not select from unmeasured “1 ms versus 10 ms” or generic messages-per-second tables. Benchmark representative payloads, durability settings, fan-out and failure recovery. Track queue age/consumer lag, retry/dead-letter rates, publish failures and saturation alongside throughput.

Docita's database-backed jobs and transactional outbox should be explained as the implementation actually present; discussing Kafka as an alternative does not establish that Docita runs Kafka.

## Summary

Retained logs preserve records for independent progress and replay; ordinary work queues track unfinished deliveries. Choose the actual storage model, then define durability, acknowledgment, deduplication, retry and ordering boundaries. Broker acceptance is one step toward business completion.

# Message Brokers: Kafka vs RabbitMQ

> **TL;DR:** Message brokers enable asynchronous communication between services. Kafka is a distributed event log optimized for high throughput and replayability. RabbitMQ is a traditional message broker optimized for complex routing and low latency. Choose Kafka for event sourcing, analytics, and streaming. Choose RabbitMQ for task queues, RPC, and complex routing.
>
> **Why it matters:** Message brokers are critical for microservices architecture. They decouple services, enable event-driven patterns, and handle asynchronous workflows. Almost every system design interview involves choosing between Kafka and RabbitMQ.

## TL;DR

- **Kafka = Distributed Event Log.** Append-only, partitioned, replayable, high throughput.
- **RabbitMQ = Traditional Message Broker.** Smart routing, acknowledgments, complex topologies.
- **Kafka for:** Event sourcing, log aggregation, streaming analytics, replay.
- **RabbitMQ for:** Task queues, RPC, complex routing, low-latency delivery.
- **Pattern:** Use Kafka when you need to replay events. Use RabbitMQ when you need complex routing.

## Definition

### Kafka (Distributed Event Log)

Apache Kafka is a distributed event streaming platform designed for high-throughput, fault-tolerant, durable event storage. Events are stored in an append-only log, partitioned by key, and can be replayed from any offset.

**Key concepts:**
- **Topic:** A category/feed name (like a table in DB)
- **Partition:** A topic is split into partitions for parallelism
- **Offset:** Unique ID for each message within a partition
- **Consumer Group:** Multiple consumers reading from the same topic
- **Broker:** A Kafka server that stores and serves messages

### RabbitMQ (Traditional Message Broker)

RabbitMQ is a message broker that implements the Advanced Message Queuing Protocol (AMQP). It provides flexible routing, acknowledgments, and complex topologies.

**Key concepts:**
- **Exchange:** Receives messages and routes them to queues
- **Queue:** Stores messages until consumed
- **Binding:** Rules that connect exchanges to queues
- **Routing Key:** Message attribute used for routing
- **Acknowledgment:** Consumer confirms message processing

## Why Do We Need Them?

| Problem                       | Solution                                            |
| ----------------------------- | --------------------------------------------------- |
| **Service coupling**          | Decouple services via async messaging               |
| **Peak load handling**        | Buffer messages during traffic spikes               |
| **Event-driven architecture** | Publish events for other services to consume        |
| **Data pipeline**             | Stream data from producers to analytics             |
| **Reliability**               | Ensure messages are delivered even if services fail |
| **Replay**                    | Reprocess events from history (Kafka only)          |

│ Producers                                               │

│ │ │ orders-P0 │ │ orders-P1 │ │ orders-P2 │       │          │

│ │└────────────────────────────────────────────────────┘│     │
│ └─────────────────────────────────────────────────────┘ │
│                                                         │
│ Consumer Groups                                         │
│ ├── Group A (order-service):                            │
│ │ ├── Consumer 1 ──▶ orders-P0                                                                                 │

## Code Examples

### 1. Kafka Producer (Node.js)

```typescript
import { Kafka, Partitioners } from 'kafkajs';

const kafka = new Kafka({
  clientId: 'order-service',
  brokers: ['localhost:9092'],
});

const producer = kafka.producer({
  createPartitioner: Partitioners.DefaultPartitioner,
});

await producer.connect();

// Send single message
await producer.send({
  topic: 'orders',
  messages: [
    {
      key: 'order-123', // Used for partitioning
      value: JSON.stringify({
        orderId: '123',
        userId: 'user-456',
        items: [{ productId: 'p1', quantity: 2 }],
        total: 59.99,
      }),
      timestamp: Date.now().toString(),
    },
  ],
});

// Send multiple messages (batch)
await producer.send({
  topic: 'orders',
  messages: [
    { key: 'order-124', value: JSON.stringify({ orderId: '124', ... }) },
    { key: 'order-125', value: JSON.stringify({ orderId: '125', ... }) },
  ],
});

await producer.disconnect();
```

### 2. Kafka Consumer

```typescript
import { Kafka } from 'kafkajs';

const kafka = new Kafka({
  clientId: 'order-service',
  brokers: ['localhost:9092'],
});

const consumer = kafka.consumer({
  groupId: 'order-processing-group', // Consumer group ID
});

await consumer.connect();

await consumer.subscribe({
  topic: 'orders',
  fromBeginning: false, // Start from latest offset
});

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    const order = JSON.parse(message.value.toString());
    
    console.log(`Processing order ${order.orderId}`);
    
    // Process the order
    await processOrder(order);
    
    // Offset is automatically committed after successful processing
  },
});
```

### 3. RabbitMQ Producer (Node.js)

```typescript
import amqp from 'amqplib';

const connection = await amqp.connect('amqp://localhost');
const channel = await connection.createChannel();

// Ensure exchange exists
await channel.assertExchange('orders', 'topic', { durable: true });

// Publish message
const message = {
  orderId: '123',
  userId: 'user-456',
  items: [{ productId: 'p1', quantity: 2 }],
  total: 59.99,
};

channel.publish(
  'orders', // Exchange
  'order.created', // Routing key
  Buffer.from(JSON.stringify(message)),
  {
    persistent: true, // Survive broker restart
    contentType: 'application/json',
  }
);

await channel.close();
await connection.close();
```

### 4. RabbitMQ Consumer

```typescript
import amqp from 'amqplib';

const connection = await amqp.connect('amqp://localhost');
const channel = await connection.createChannel();

// Ensure exchange and queue exist
await channel.assertExchange('orders', 'topic', { durable: true });
await channel.assertQueue('order-processing', { durable: true });

// Bind queue to exchange with routing key
await channel.bindQueue('order-processing', 'orders', 'order.*');

// Prefetch 1 message at a time (backpressure)
await channel.prefetch(1);

// Consume messages
await channel.consume('order-processing', async (msg) => {
  if (!msg) return;

  const order = JSON.parse(msg.content.toString());
  
  try {
    await processOrder(order);
    
    // Acknowledge message (remove from queue)
    channel.ack(msg);
  } catch (error) {
    // Reject message and requeue
    channel.nack(msg, false, true);
  }
});
```

### 5. RabbitMQ Exchange Types

```typescript
// 1. Direct Exchange (exact routing key match)
await channel.assertExchange('notifications', 'direct', { durable: true });
await channel.bindQueue('email-queue', 'notifications', 'email');
await channel.bindQueue('sms-queue', 'notifications', 'sms');
channel.publish('notifications', 'email', Buffer.from('...')); // Goes to email-queue

// 2. Topic Exchange (pattern matching)
await channel.assertExchange('orders', 'topic', { durable: true });
await channel.bindQueue('all-orders', 'orders', 'order.*');
await channel.bindQueue('critical-orders', 'orders', 'order.critical');
channel.publish('orders', 'order.created', Buffer.from('...')); // Goes to all-orders
channel.publish('orders', 'order.critical', Buffer.from('...')); // Goes to both queues

// 3. Fanout Exchange (broadcast to all bound queues)
await channel.assertExchange('broadcast', 'fanout', { durable: true });
await channel.bindQueue('analytics-queue', 'broadcast', '');
await channel.bindQueue('audit-queue', 'broadcast', '');
channel.publish('broadcast', '', Buffer.from('...')); // Goes to both queues

// 4. Headers Exchange (match on message headers)
await channel.assertExchange('headers-ex', 'headers', { durable: true });
await channel.bindQueue('priority-queue', 'headers-ex', '', {
  'x-match': 'all',
  priority: 'high',
  type: 'order',
});
```

## Comparison: Kafka vs RabbitMQ

| Feature               | Kafka                       | RabbitMQ                     |
| --------------------- | --------------------------- | ---------------------------- |
| **Architecture**      | Distributed log             | Message broker               |
| **Message model**     | Pull (consumer polls)       | Push (broker delivers)       |
| **Ordering**          | Per partition               | Per queue                    |
| **Replay**            | Yes (from offset)           | No                           |
| **Throughput**        | Very high (GB/s)            | High (msgs/sec)              |
| **Latency**           | ~10ms                       | ~1ms                         |
| **Durability**        | Disk-based                  | Memory + disk                |
| **Routing**           | Simple (topic/partition)    | Complex (exchanges/bindings) |
| **Consumer groups**   | Native                      | Manual (competing consumers) |
| **Message retention** | Configurable (days/forever) | Until consumed               |
| **Use case**          | Event sourcing, streaming   | Task queues, RPC             |

### When to Use Which?

```text
USE KAFKA WHEN:
├── You need to replay events (event sourcing)
├── You need high throughput (GB/s)
├── You're building a data pipeline
├── You need exactly-once semantics
├── You're doing real-time analytics
└── You need event history for auditing

USE RABBITMQ WHEN:
├── You need complex routing (topic/fanout/direct)
├── You need low latency (~1ms)
├── You're doing RPC (request/reply)
├── You need message priority
├── You're building task queues
└── You need acknowledgments
```

## Common Patterns

### 1. Event Sourcing (Kafka)

```typescript
// Every state change is an event
interface OrderEvent {
  orderId: string;
  type: 'created' | 'paid' | 'shipped' | 'delivered';
  timestamp: number;
  data: any;
}

// Produce events
await producer.send({
  topic: 'order-events',
  messages: [
    {
      key: order.id,
      value: JSON.stringify({
        orderId: order.id,
        type: 'created',
        timestamp: Date.now(),
        data: { items: order.items, total: order.total },
      }),
    },
  ],
});

// Consumer reconstructs state from events
let orderState: Record<string, any> = {};

await consumer.run({
  eachMessage: async ({ message }) => {
    const event: OrderEvent = JSON.parse(message.value.toString());
    
    switch (event.type) {
      case 'created':
        orderState[event.orderId] = { ...event.data, status: 'created' };
        break;
      case 'paid':
        orderState[event.orderId].status = 'paid';
        break;
      case 'shipped':
        orderState[event.orderId].status = 'shipped';
        break;
    }
  },
});
```

### 2. Saga Pattern (RabbitMQ)

```typescript
// Choreography-based saga using RabbitMQ
// Step 1: Order Service publishes "order.created"
channel.publish('orders', 'order.created', Buffer.from(JSON.stringify(order)));

// Step 2: Payment Service consumes "order.created", publishes "payment.completed"
await channel.consume('payment-queue', async (msg) => {
  const order = JSON.parse(msg.content.toString());
  await processPayment(order);
  channel.publish('payments', 'payment.completed', Buffer.from(JSON.stringify(order)));
  channel.ack(msg);
});

// Step 3: Inventory Service consumes "payment.completed", publishes "inventory.reserved"
await channel.consume('inventory-queue', async (msg) => {
  const order = JSON.parse(msg.content.toString());
  await reserveInventory(order);
  channel.publish('inventory', 'inventory.reserved', Buffer.from(JSON.stringify(order)));
  channel.ack(msg);
});
```

### 3. Dead Letter Queue (DLQ)

```typescript
// RabbitMQ DLQ for failed messages
const dlqQueue = 'order-processing-dlq';
const mainQueue = 'order-processing';

await channel.assertQueue(dlqQueue, { durable: true });
await channel.assertQueue(mainQueue, {
  durable: true,
  arguments: {
    'x-dead-letter-exchange': '',
    'x-dead-letter-routing-key': dlqQueue,
    'x-message-ttl': 60000, // 60s TTL before DLQ
  },
});

// Consumer with retry logic
await channel.consume(mainQueue, async (msg) => {
  try {
    await processOrder(JSON.parse(msg.content.toString()));
    channel.ack(msg);
  } catch (error) {
    // Reject and send to DLQ
    channel.nack(msg, false, false);
  }
});

// DLQ consumer (manual intervention or retry)
await channel.consume(dlqQueue, async (msg) => {
  console.log('Failed message:', msg.content.toString());
  // Log to monitoring, alert, or retry
  channel.ack(msg);
});
```

## Performance Considerations

| Metric           | Kafka                         | RabbitMQ               |
| ---------------- | ----------------------------- | ---------------------- |
| **Throughput**   | 100K-1M msgs/sec per broker   | 10K-50K msgs/sec       |
| **Latency**      | 5-10ms (end-to-end)           | 1-5ms (end-to-end)     |
| **Message size** | Up to 1MB (default)           | Up to 128MB            |
| **Storage**      | Disk (retention configurable) | Memory + disk          |
| **Scaling**      | Add partitions/brokers        | Add nodes (clustering) |

### Kafka Tuning

```typescript
// Producer tuning
const producer = kafka.producer({
  maxInFlightRequests: 5, // Batch size
  idempotent: true, // Exactly-once semantics
  transactionalId: 'order-service', // Transactional producer
});

// Consumer tuning
const consumer = kafka.consumer({
  groupId: 'order-processing',
  sessionTimeout: 30000, // 30s session timeout
  heartbeatInterval: 3000, // 3s heartbeat
  maxBytesPerPartition: 1048576, // 1MB per partition
});
```

## Common Mistakes

### 1. Not Using Consumer Groups (Kafka)

```typescript
// Bad: Single consumer reads all partitions
await consumer.run({
  eachMessage: async ({ message }) => {
    // Single consumer bottleneck
  },
});

// Good: Use consumer group for parallelism
// Multiple instances of same service automatically distribute partitions
const consumer = kafka.consumer({ groupId: 'order-service' });
```

### 2. Ignoring Message Ordering (RabbitMQ)

```typescript
// Bad: Using fanout when order matters
await channel.assertExchange('orders', 'fanout');

// Good: Use topic with partitioning key
await channel.assertExchange('orders', 'topic');
// Route by order ID to ensure same order goes to same queue
channel.publish('orders', `order.${order.id}`, Buffer.from(...));
```

### 3. Not Handling Poison Messages

```typescript
// Bad: Infinite retry loop
await channel.consume(queue, async (msg) => {
  try {
    await process(msg);
    channel.ack(msg);
  } catch (error) {
    channel.nack(msg, false, true); // Infinite retry
  }
});

// Good: Use DLQ after N retries
let retryCount = 0;
const MAX_RETRIES = 3;

await channel.consume(queue, async (msg) => {
  try {
    await process(msg);
    channel.ack(msg);
    retryCount = 0;
  } catch (error) {
    retryCount++;
    if (retryCount >= MAX_RETRIES) {
      channel.nack(msg, false, false); // Send to DLQ
      retryCount = 0;
    } else {
      channel.nack(msg, false, true); // Requeue
    }
  }
});
```

## Summary

| Decision         | Kafka                                | RabbitMQ                          |
| ---------------- | ------------------------------------ | --------------------------------- |
| **Architecture** | Distributed log                      | Message broker                    |
| **Best for**     | Event sourcing, streaming, analytics | Task queues, RPC, complex routing |
| **Ordering**     | Per partition                        | Per queue                         |
| **Replay**       | Yes                                  | No                                |
| **Throughput**   | Very high (GB/s)                     | High (msgs/sec)                   |
| **Latency**      | ~10ms                                | ~1ms                              |
| **Routing**      | Simple (topic)                       | Complex (exchanges)               |

## Cheat Sheet

```text
MESSAGE BROKER CHEAT SHEET
═══════════════════════════════════════════════════════════════

KAFKA:
  Architecture: Distributed event log (append-only)
  Key concepts: Topic, Partition, Offset, Consumer Group
  Ordering: Per partition
  Replay: Yes (from any offset)
  Use cases: Event sourcing, streaming, log aggregation
  Throughput: 100K-1M msgs/sec

RABBITMQ:
  Architecture: Traditional message broker
  Key concepts: Exchange, Queue, Binding, Routing Key
  Ordering: Per queue
  Replay: No
  Use cases: Task queues, RPC, complex routing
  Throughput: 10K-50K msgs/sec

WHEN TO USE:
  Kafka: Need replay, high throughput, event history
  RabbitMQ: Need complex routing, low latency, RPC

COMMON PATTERNS:
  Event Sourcing: Store state changes as events (Kafka)
  Saga: Distributed transactions via events (Kafka/RabbitMQ)
  CQRS: Separate read/write models (Kafka)
  Dead Letter Queue: Handle failed messages (RabbitMQ)

INTERVIEW TIPS:
  • Explain at-least-once vs exactly-once semantics
  • Discuss consumer group rebalancing in Kafka
  • Know exchange types in RabbitMQ (direct, topic, fanout)
  • Mention DLQ for poison message handling
```

# Event-Driven Architecture

## Definition

**Event-driven architecture (EDA)** coordinates parts of a system through events: records of facts that have happened. A producer publishes a fact; consumers decide how to react. Asynchronous transport lets consumers process it after the producer's request has finished.

> **Textbook Definition:** Event-driven architecture connects components through records of completed facts that consumers process independently. Event contracts, delivery behavior and consumer state determine coordination and consistency across those components.

For example, billing commits an invoice and publishes `InvoiceCreated`. Document generation and analytics react independently. Billing need not wait for both to finish before returning the committed invoice.

## First Principles

An invoice and a PDF have different correctness and availability requirements. Making every side effect synchronous couples invoice creation to all downstream services. Separating them removes that immediate dependency, but creates a gap between **source state committed** and **downstream effect completed**.

The architecture must make that gap durable, observable and recoverable. An event bus alone does not solve it.

## Distinguish fact, instruction and read

| Message | Meaning | Who decides? |
| ---------------------- | -------------------------- | --------------------------------------------- |
| Command: CreateInvoice | Please attempt this action | Its handler validates and may reject it |
| Event: InvoiceCreated | This fact has occurred | Each interested consumer chooses its reaction |
| Query: GetInvoice | Return current information | The serving read model answers |

A command usually addresses a particular capability. An event can have several consumers, but broadcast is not mandatory: routing may deliver it only to interested subscribers. Producers still own a schema contract; adding a consumer needs no producer change only when the existing event contains the required facts and access policy permits them.

## Trace one invoice from commit to PDF

```text
Request → invoice transaction + outbox row → publish worker → event transport
                                                           ↓
                                               PDF worker → stored document
                                                           ↓
                                               UI sees ready / failed status
```

1. Billing validates tenant access and commits invoice state **with an outbox row in the same database transaction**.
2. A publisher reads pending outbox rows and sends the event. Failed or uncertain publication is retried; duplicates remain possible.
3. The PDF consumer validates the envelope and checks its own idempotency boundary.
4. It completes or durably schedules document work, then acknowledges progress.
5. The UI presents pending, ready or failed document state rather than pretending a committed invoice guarantees an available PDF.

An outbox closes the “database committed, process died before publish” gap. It does not eliminate duplicate delivery. Avoid acknowledging a message after merely swallowing an exception.

### Give the event enough identity to diagnose it

```json
{
  "eventId": "evt-1042",
  "type": "InvoiceCreated",
  "schemaVersion": 1,
  "tenantId": "clinic-7",
  "invoiceId": "invoice-42",
  "aggregateVersion": 3,
  "occurredAt": "2026-10-03T10:00:00Z",
  "correlationId": "request-981"
}
```

This is an illustrative contract, not a claim about Docita's exact payload. **Event ID** identifies this occurrence for deduplication; **correlation ID** connects related work and can cover many events. **Aggregate version** orders changes for one entity; **schema version** identifies the payload format. They are not interchangeable.

Tenant identifiers help route and scope processing, but consumers must still enforce trusted authorization boundaries. Keep clinical details and secrets out of broad event streams when an identifier is sufficient.

## Make the consumer safe after a crash

For a local database projection, this is the logical transaction boundary:

```text
BEGIN
  claim (consumer name, tenant ID, event ID) using a unique constraint
  if already committed: leave projection unchanged
  otherwise: validate entity version and apply projection mutation
COMMIT
acknowledge / commit transport progress
```

The marker and mutation must commit together. A separate “already processed?” read followed by an uncoordinated write races with another delivery. If the consumer crashes after commit but before acknowledgment, the next delivery observes the committed marker and avoids repeating the mutation.

A transaction in this database cannot atomically cover an arbitrary email or payment API. Use a durable job/outbox and the receiving system's idempotency contract. Do not describe an in-memory set or Kafka producer idempotence as end-to-end exactly once.

### Handle ordering and missing history deliberately

Partitioning by entity can preserve transport order within a partition, but concurrent processing or retry paths can still alter completion order. An entity version lets a consumer distinguish a duplicate, a next expected change and a gap.

For a gap, choose a policy: wait/retry, fetch authoritative state, or rebuild from retained history. Silently discarding every unexpected version can lose legitimate changes. A timestamp alone is not a reliable global sequence.

## Choose how much state the event carries

| Contract | Benefit | Cost and boundary |
| --------------------------------------------- | ------------------------------------------- | --------------------------------------------------------------------- |
| Notification: entity ID plus fact | Small payload, less copied sensitive data | Consumer may need the source API; later reads can reflect newer state |
| State-carried event: required values included | Consumer can act without calling the source | Larger/versioned contract; access, retention and deletion obligations |

Use the smallest payload that preserves the intended meaning. If a PDF must represent the invoice at creation time, fetching its mutable current state later may be wrong: use an immutable invoice version or include the necessary snapshot under an appropriate data policy.

Schema evolution should preserve existing consumers. Additive fields are often easier than renaming or changing meanings, but strict readers can still reject additions. Validate compatibility and retain handlers/upcasters for historical versions when replay requires them.

## Separate coordination from storage patterns

**Choreography** lets participants react to events without one process coordinator. It suits independent side effects, but multi-step business progress can become hard to see. **Orchestration** gives a coordinator explicit steps, commands, outcomes and compensation decisions. It adds an owned component but makes long-running process state visible.

EDA does not require Kafka, event sourcing or CQRS:

- A broker or database-backed transport can carry events; durability and replay depend on its implementation.
- **Event sourcing** stores domain events as the authoritative history from which state is reconstructed. Publishing events from an ordinary state database does not make it event-sourced.
- **CQRS** separates command/write and query/read responsibilities. Separate databases and asynchronous projections are optional design choices, not its definition.

Use the dedicated chapters for event-store and projection implementation. Avoid adding those costs merely because a feature needs asynchronous PDF generation.

## Operate the gap between committed and completed

Monitor outbox age, publish failures, consumer lag, oldest unfinished work, retries and dead-letter counts. Include event ID, correlation ID and tenant-safe context in logs. A healthy HTTP API can coexist with a stalled consumer.

Bound transient retries with backoff; isolate invalid events for inspection. Replay must define its range, intended consumers and side-effect policy: rebuilding an analytics projection should not send every historic email again. Fix the failure cause, authorize replay and record what was retried.

For read-model lag, expose a pending state or read the authoritative write result where read-your-writes matters. Not every part of an event-driven system is eventually consistent; consistency belongs to each operation boundary.

## Summary

EDA separates a committed fact from later reactions. An outbox protects publication intent; idempotent consumers protect retries; versions and explicit lag states protect ordering and user expectations. Event sourcing, CQRS and broker choice are separate decisions with their own costs.

# Distributed Transactions

## Definition

**Distributed Transactions** coordinate state changes across multiple microservices while maintaining data consistency. Traditional ACID transactions don't span service boundaries, so distributed patterns like the **Saga pattern** (choreography/orchestration), **Two-Phase Commit (2PC)**, and **Outbox pattern** are used.

## First Principles

Distributed transactions are derivable from one impossibility:

1. **You cannot have atomicity, availability, and partition-tolerance at once (CAP).** Network partitions are physical reality; so every distributed "transaction" chooses: block (2PC: consistent, unavailable during partition) or proceed and reconcile (eventual consistency).
2. **2PC's blocking is the lesson, not a flaw**: a coordinator crash between prepare and commit leaves participants locked — the protocol proves *why* the industry moved to coordination-via-compensation (sagas, → 20.6.3.01) instead of locking across services.
3. **The modern answer: keep ACID local, make the workflow explicit.** One DB transaction per service, sagas across services, outbox for reliable publishing (→ 20.6.3.06) — the composition gives you *observable* eventual consistency instead of *invisible* blocking.

## Why Do We Need It?

1. **Data consistency**: Maintain correctness across service boundaries
2. **Failure recovery**: Handle partial failures gracefully with compensating actions
3. **Idempotency**: Ensure retried operations don't cause duplicates
4. **Auditability**: Track all state changes across services

## How It Works

### Core Consistency Models in Distributed Systems

In monolithic architectures, ACID transactions rely on a shared database engine and local lock managers. In distributed microservice topologies where services maintain private datastores, standard ACID guarantees across service boundaries are impossible without severe operational trade-offs:

1. **Two-Phase Commit (2PC / XA)**:
   - **Phase 1 (Prepare)**: The coordinator sends a `PREPARE` request to all participants. Each participant executes the local transaction up to commit, writes changes to its write-ahead log (WAL), acquires local locks, and responds `VOTE_COMMIT` or `VOTE_ABORT`.
   - **Phase 2 (Commit / Abort)**: If all participants voted `VOTE_COMMIT`, the coordinator writes `GLOBAL_COMMIT` to its log and sends `COMMIT` to all nodes. If any node voted abort or timed out, the coordinator sends `GLOBAL_ABORT`.
   - **The Blocking Flaw**: 2PC is a *blocking protocol*. If the coordinator crashes after participants vote `VOTE_COMMIT`, participants must hold their local database row locks indefinitely until the coordinator recovers, degrading throughput and causing cascading system outages.

2. **The Saga Pattern (Eventual Consistency & Compensations)**:
   - A Saga breaks a distributed business process into a series of local transactions: $T_1, T_2, \dots, T_n$.
   - Each transaction $T_i$ updates local storage and publishes an event or message that triggers $T_{i+1}$.
   - If transaction $T_k$ fails, the saga executes compensating transactions in reverse order ($C_{k-1}, \dots, C_1$) to semantically undo preceding state changes.
   - **Compensating Transaction vs Rollback**: A rollback physically reverts database blocks. A compensation is a new forward transaction that semantically reverses previous business effects (e.g. issuing a credit refund rather than erasing the credit card charge).

3. **Transactional Outbox Pattern**:
   - Solves the *dual-write problem* where an application must write to a database and emit a message to a broker (e.g. Kafka, RabbitMQ).
   - In a single local database transaction, the application inserts the business entity and an event envelope into an `outbox` table.
   - A background relay process (either Change Data Capture via Debezium tailing the DB transaction log, or a dedicated polling worker with `SKIP LOCKED`) reads the outbox records and publishes them to the message broker with at-least-once delivery guarantees.

### Patterns Comparison Matrix

| Pattern | Consistency | Complexity | Throughput | Failure Mode | Best For |
| -------------------------- | :-----------: | :--------: | :--------: | ------------------------------------- | ---------------------------------------- |
| **Saga (Choreography)** | Eventual | Low-Medium | High | Unhandled events, cyclic dependencies | Simple workflows (2-4 services) |
| **Saga (Orchestration)** | Eventual | Medium | Medium | Orchestrator state bottleneck | Complex multi-step workflows (>4 steps) |
| **Two-Phase Commit (2PC)** | Strong | High | Very Low | Coordinator crash causes lock freeze | Financial ledgers within same DC |
| **Transactional Outbox** | At-least-once | Low-Medium | High | Broker publishing delay | Reliable message emission from DB writes |

## Code Examples

### Saga Pattern — Choreography (Event-Driven)

Each service publishes domain events that trigger downstream service actions. There is no central coordinator.

```text
Order Service → [order.created] → Payment Service
                                    ↓ [payment.completed]
                               Inventory Service
                                    ↓ [inventory.reserved]
                               Shipping Service
                                    ↓ [shipping.queued]
                               Order Service (confirmed)
```

```typescript
// Order Service — publishes order.created atomically via Outbox
async function createOrder(order: Order) {
  await db.transaction(async (tx) => {
    await tx.orders.insert({ ...order, status: 'PENDING' });
    await tx.outbox.insert({
      eventType: 'order.created',
      payload: JSON.stringify({ orderId: order.id, amount: order.totalAmount, items: order.items }),
      createdAt: new Date(),
    });
  });
}

// Payment Service — listens for order.created
async function handleOrderCreated(event: OrderCreatedEvent) {
  try {
    const payment = await processPayment(event.orderId, event.amount);
    await publishEvent('payment.completed', {
      orderId: event.orderId,
      paymentId: payment.id,
    });
  } catch (error) {
    // Publish failure event to trigger upstream compensation
    await publishEvent('payment.failed', {
      orderId: event.orderId,
      reason: error instanceof Error ? error.message : 'payment_rejected',
    });
  }
}

// Order Service — compensates on payment failure
async function handlePaymentFailed(event: PaymentFailedEvent) {
  await db.orders.update({
    where: { id: event.orderId },
    data: { status: 'CANCELLED', cancellationReason: event.reason },
  });
}
```

### Saga Pattern — Orchestration (Explicit Workflow Coordinator)

A central orchestrator manages the sequence of forward actions and executes compensating steps in reverse order upon failure.

```text
┌────────────────────────────────────────┐
│ SAGA ORCHESTRATOR                      │
│                                        │
│ 1. Create Order → Order Service        │
│ 2. Process Payment → Payment Service   │
│ 3. Reserve Inventory → Inventory Svc   │
│ 4. Ship → Shipping Service             │
│                                        │
│ On failure: compensate completed steps │
└────────────────────────────────────────┘
```

```typescript
interface SagaStep<TInput, TOutput> {
  name: string;
  action: (data: TInput) => Promise<TOutput>;
  compensate: (data: TInput, result: TOutput) => Promise<void>;
}

class OrderSagaOrchestrator {
  private steps: SagaStep<OrderContext, any>[] = [
    {
      name: 'ReserveInventory',
      action: async (ctx) => inventoryClient.reserve(ctx.orderId, ctx.items),
      compensate: async (ctx, res) => inventoryClient.release(res.reservationId),
    },
    {
      name: 'ProcessPayment',
      action: async (ctx) => paymentClient.charge(ctx.orderId, ctx.amount),
      compensate: async (ctx, res) => paymentClient.refund(res.chargeId),
    },
    {
      name: 'ScheduleDelivery',
      action: async (ctx) => shippingClient.createShipment(ctx.orderId, ctx.address),
      compensate: async (ctx, res) => shippingClient.cancelShipment(res.shipmentId),
    },
  ];

  async execute(context: OrderContext): Promise<void> {
    const completedSteps: { step: SagaStep<OrderContext, any>; result: any }[] = [];

    for (const step of this.steps) {
      try {
        const result = await step.action(context);
        completedSteps.push({ step, result });
      } catch (error) {
        // Rollback completed steps in reverse chronological order
        for (const completed of [...completedSteps].reverse()) {
          try {
            await completed.step.compensate(context, completed.result);
          } catch (compError) {
            // Unrecoverable compensation failure: route to Dead Letter Queue / alert ops
            console.error(`Compensation failed for ${completed.step.name}`, compError);
          }
        }
        throw new Error(`Saga failed at step: ${step.name}. Error: ${error}`);
      }
    }
  }
}
```

### Transactional Outbox Pattern with Atomic Commit

The outbox pattern guarantees that database state updates and event publishing occur atomically.

```sql
-- Step 1: Write business data + event record in the exact same local ACID transaction
BEGIN;
  INSERT INTO orders (id, customer_id, total_amount, status)
    VALUES ('ord-123', 'cust-456', 99.99, 'CREATED');

  INSERT INTO outbox_events (id, aggregate_type, aggregate_id, event_type, payload, created_at)
    VALUES (gen_random_uuid(), 'Order', 'ord-123', 'order.created', '{"orderId":"ord-123","amount":99.99}', NOW());
COMMIT;
```

```typescript
// Step 2: Outbox Relay Worker (polling with row-level locking)
async function pollAndPublishOutboxEvents() {
  await db.transaction(async (tx) => {
    // Select unprocessed events with SKIP LOCKED to allow concurrent workers
    const pendingEvents = await tx.$queryRaw<OutboxEvent[]>`
      SELECT * FROM outbox_events
      WHERE published_at IS NULL
      ORDER BY created_at ASC
      LIMIT 50
      FOR UPDATE SKIP LOCKED
    `;

    for (const event of pendingEvents) {
      await messageBroker.publish(event.event_type, JSON.parse(event.payload));
      await tx.$executeRaw`
        UPDATE outbox_events
        SET published_at = NOW()
        WHERE id = ${event.id}
      `;
    }
  });
}
```

## Real-World Use Cases

- **E-Commerce Checkout Pipeline (Orchestrated Saga)**: Order creation requires charging a card, reserving warehouse stock, and dispatching courier delivery. Because payment processors and warehouses are distinct distributed systems, an orchestrator (e.g. Temporal, Cadence, or AWS Step Functions) manages compensating transactions if stock reservation fails after payment approval.
- **Flight & Hotel Booking Travel Aggregator (Choreographed Saga)**: When booking a multi-city vacation package, each vendor (airline, hotel, car rental) takes seconds or minutes to confirm. Services communicate asynchronously over message topics, listening for cancellation events to release bookings if any segment fails validation.
- **Inter-Bank Account Transfers (Outbox + Idempotent Consumer)**: Account debit and credit operations cannot use 2PC across independent banking institutions. Banks commit debits locally, publish transfer events via the Transactional Outbox pattern, and receiving institutions utilize unique transfer IDs (`idempotency_key`) to ensure funds are credited exactly once even during network retries.

## Common Mistakes

| Mistake | Fix |
| ---------------------------------- | ------------------------------------ |
| Distributed locks for transactions | Use Saga or 2PC instead |
| No compensating actions | Every step must have a rollback plan |
| No idempotency keys | Retries will create duplicates |
| Sync calls across services | Use async events for loose coupling |
| No outbox pattern | Dual-write = inconsistent state |
| Ignoring timeout handling | Set timeouts + dead letter queues |

## Best Practices

1. **Use outbox pattern** for reliable event publishing
2. **Make every step idempotent** — idempotency keys on all writes
3. **Set timeouts** — every step should have a deadline
4. **Use DLQ** — dead letter queues for poison messages
5. **Monitor saga state** — dashboard showing step completion
6. **Prefer choreography** for simple flows, orchestration for complex
7. **Keep compensations fast** — don't block on refunds

## Summary

- Distributed transactions span multiple services and require coordination across independent data stores
- Two-Phase Commit (2PC) provides ACID guarantees but has blocking and scalability limitations
- Saga pattern breaks long-lived transactions into a sequence of local transactions with compensating actions
- Choreography-based sagas use event-driven coordination; orchestration-based sagas use a central coordinator
- Transactional Outbox pattern ensures reliable event publishing by storing events in the same database as business data

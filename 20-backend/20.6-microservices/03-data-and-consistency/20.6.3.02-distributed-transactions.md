# Distributed Transactions

## TL;DR

Patterns for atomicity across services: 2PC, Saga, outbox, and idempotent consumers — and why distributed locks are usually the wrong tool.

**Why it matters:** Tests CAP/PACELC reasoning and the outbox pattern for reliable event publication. Most "impossible" bugs in microservices come from skipping this thinking.

## First Principles

Distributed transactions are derivable from one impossibility:

1. **You cannot have atomicity, availability, and partition-tolerance at once (CAP).** Network partitions are physical reality; so every distributed "transaction" chooses: block (2PC: consistent, unavailable during partition) or proceed and reconcile (eventual consistency).
2. **2PC's blocking is the lesson, not a flaw**: a coordinator crash between prepare and commit leaves participants locked — the protocol proves *why* the industry moved to coordination-via-compensation (sagas, → 20.6.3.01) instead of locking across services.
3. **The modern answer: keep ACID local, make the workflow explicit.** One DB transaction per service, sagas across services, outbox for reliable publishing (→ 20.6.3.06) — the composition gives you *observable* eventual consistency instead of *invisible* blocking.

## Definition

**Distributed Transactions** coordinate state changes across multiple microservices while maintaining data consistency. Traditional ACID transactions don't span service boundaries, so distributed patterns like the **Saga pattern** (choreography/orchestration), **Two-Phase Commit (2PC)**, and **Outbox pattern** are used.

## Why Do We Need It?

1. **Data consistency**: Maintain correctness across service boundaries
2. **Failure recovery**: Handle partial failures gracefully with compensating actions
3. **Idempotency**: Ensure retried operations don't cause duplicates
4. **Auditability**: Track all state changes across services

## Patterns Comparison

| Pattern | Consistency | Complexity | Throughput | Use Case |
| ------------------------ | :---------: | :--------: | :--------: | ------------------------ |
| **Saga (Choreography)** | Eventual | Low | High | Simple workflows |
| **Saga (Orchestration)** | Eventual | Medium | Medium | Complex workflows |
| **2PC** | Strong | High | Low | Short-lived critical ops |
| **Outbox** | Strong | Medium | High | Reliable messaging |

## Saga Pattern — Choreography

Each service publishes events that trigger the next step. No central coordinator.

```text
Order Service → [order.created] → Payment Service
                                    ↓ [payment.completed]
                               Inventory Service
                                    ↓ [inventory.reserved]
                               Shipping Service
                                    ↓ [shipping.queued]
                               Order Service (confirmed)
```

```typescript
// Order Service — publishes order.created
async function createOrder(order: Order) {
  await db.transaction(async (tx) => {
    await tx.orders.insert(order);
    await tx.outbox.insert({
      eventType: 'order.created',
      payload: JSON.stringify(order),
    });
  });
}

// Payment Service — listens for order.created
async function handleOrderCreated(event: OrderCreatedEvent) {
  const payment = await processPayment(event.order);
  await publishEvent('payment.completed', { orderId: event.order.id, paymentId: payment.id });
}

// If payment fails, publish payment.failed → Order Service compensates
async function handlePaymentFailed(event: PaymentFailedEvent) {
  await publishEvent('order.cancelled', { orderId: event.order.id, reason: 'payment_failed' });
}
```

## Saga Pattern — Orchestration

A central orchestrator coordinates all steps and handles compensations.

```text
┌────────────────────────────────────────┐
│ SAGA ORCHESTRATOR                      │
│                                        │
│ 1. Create Order → Order Service        │
│ 2. Process Payment → Payment Service   │
│ 3. Reserve Inventory → Inventory Svc   │
│ 4. Ship → Shipping Service             │
│                                        │
│ On failure: compensate completed steps │
└────────────────────────────────────────┘
```

```typescript
class OrderSaga {
  private steps = [
    { action: this.createOrder.bind(this), compensate: this.cancelOrder.bind(this) },
    { action: this.processPayment.bind(this), compensate: this.refundPayment.bind(this) },
    { action: this.reserveInventory.bind(this), compensate: this.releaseInventory.bind(this) },
    { action: this.shipOrder.bind(this), compensate: this.cancelShipping.bind(this) },
  ];

  async execute(order: Order) {
    const completed: Compensation[] = [];

    for (const step of this.steps) {
      try {
        const result = await step.action(order);
        completed.push({ compensate: step.compensate, result });
      } catch (error) {
        // Compensate all completed steps in reverse order
        for (const c of completed.reverse()) {
          await c.compensate(c.result);
        }
        throw new SagaFailedError(error, completed.length);
      }
    }
  }
}
```

## Transaction Outbox Pattern

The outbox pattern solves the dual-write problem: write business data + publish event in the same transaction.

```sql
-- Write to outbox table in same DB transaction
BEGIN;
  INSERT INTO orders (id, amount) VALUES (?, ?);
  INSERT INTO outbox (event_type, payload, created_at)
    VALUES ('order.created', '{"id": ...}', NOW());
COMMIT;

-- Relay process reads and publishes outbox events
-- Uses CDC (Debezium) or polling
```

```typescript
// Outbox relay (polling-based)
async function relayOutboxEvents() {
  const events = await db.outbox.findMany({
    where: { published: false },
    orderBy: { createdAt: 'asc' },
    take: 100,
  });

  for (const event of events) {
    try {
      await messageBroker.publish(event.eventType, JSON.parse(event.payload));
      await db.outbox.update({
        where: { id: event.id },
        data: { published: true, publishedAt: new Date() },
      });
    } catch (error) {
      // Retry on next poll — idempotent publish
    }
  }
}
```

## Common Mistakes

| Mistake | Fix |
| ---------------------------------- | ------------------------------------ |
| Distributed locks for transactions | Use Saga or 2PC instead |
| No compensating actions | Every step must have a rollback plan |
| No idempotency keys | Retries will create duplicates |
| Sync calls across services | Use async events for loose coupling |
| No outbox pattern | Dual-write = inconsistent state |
| Ignoring timeout handling | Set timeouts + dead letter queues |

## Best Practices

1. **Use outbox pattern** for reliable event publishing
2. **Make every step idempotent** — idempotency keys on all writes
3. **Set timeouts** — every step should have a deadline
4. **Use DLQ** — dead letter queues for poison messages
5. **Monitor saga state** — dashboard showing step completion
6. **Prefer choreography** for simple flows, orchestration for complex
7. **Keep compensations fast** — don't block on refunds

## Summary

- Distributed transactions span multiple services and require coordination across independent data stores
- Two-Phase Commit (2PC) provides ACID guarantees but has blocking and scalability limitations
- Saga pattern breaks long-lived transactions into a sequence of local transactions with compensating actions
- Choreography-based sagas use event-driven coordination; orchestration-based sagas use a central coordinator
- Transactional Outbox pattern ensures reliable event publishing by storing events in the same database as business data

## Cheat Sheet
```text
DISTRIBUTED TRANSACTIONS CHEAT SHEET
═══════════════════════════════════════════════════════════════

2PC (Two-Phase Commit):
• Prepare → Commit
• Strong consistency, blocking, slow
• Use: legacy systems, financial ledgers
• Cons: coordinator SPOF, locks held during prepare

SAGA PATTERN:
• Sequence of local transactions
• Each has a compensating action (rollback)
• Two styles:
  - Choreography: events trigger next step (no coordinator)
  - Orchestration: central coordinator manages flow

COMPENSATING ACTIONS:
• Create order → Compensate: cancel order
• Charge card → Compensate: refund
• Reserve inventory → Compensate: release
• Ship package → Compensate: initiate return

OUTBOX PATTERN:
• Write business data + event in same DB transaction
• Relay process (polling or CDC) publishes events
• Solves dual-write problem
• Use Debezium for CDC-based outbox

IDEMPOTENCY:
• Idempotency key per request
• Deduplication at consumer
• DB unique constraint
• All saga steps must be idempotent

IN INTERVIEWS:
• Name pattern (2PC, Saga, Outbox)
• Explain compensating actions
• Mention idempotency
• Discuss timeout + DLQ strategy
• Prefer outbox for reliable messaging
```

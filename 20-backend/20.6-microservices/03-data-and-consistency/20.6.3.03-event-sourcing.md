# Event Sourcing

## Definition

Event Sourcing is a design pattern where state changes are stored as an immutable sequence of events. Instead of storing current state, you store all events that led to that state. The current state is derived by replaying events. Events describe accepted facts and are normally appended rather than edited. Retention, erasure and correction policies still need explicit design; an event store is not exempt from those obligations.

> **Textbook Definition:** Event sourcing treats an ordered record of accepted domain events as the authoritative history from which state is derived. Event schemas, replay rules and retention policies determine whether past state can be reconstructed safely.

## First Principles

A current balance cannot explain which accepted changes produced it. If that history must be authoritative, store accepted facts and derive state by applying them. Reconstruction then depends on retained events, their order and compatible deterministic interpretation; audit and recovery are capabilities to implement, not free guarantees.

Two commands can both read version four. Accepting both without checking that version can violate a balance invariant. An event store needs atomic expected-version append, not merely a computed “next version” in memory.

## Trace an account's accepted facts

```text
command -> authorize + load version -> enforce balance rule -> expected-version append
                                                               |
                                                        authoritative events
                                                               |
                                                     deterministic replay/view
```

A command requests a withdrawal; `Withdrawn` records an accepted withdrawal. Replaying it changes derived balance without calling a bank/payment API again. A transport event or audit log is not automatically the authoritative event store.

## Replay one complete balance model

This complete JavaScript reducer uses nonnegative integer minor units in one fixed currency. It checks contiguous aggregate versions and does not invoke external effects. `initial` can represent a validated snapshot at a known version.

```javascript
function replayBalance(events, initial = { balanceMinor: 0, version: 0 }) {
  if (!Array.isArray(events) || !Number.isSafeInteger(initial.balanceMinor) ||
      initial.balanceMinor < 0 || !Number.isSafeInteger(initial.version) || initial.version < 0) {
    throw new TypeError('invalid history or snapshot');
  }
  let state = { ...initial };
  for (const event of events) {
    if (event.version !== state.version + 1 || !Number.isSafeInteger(event.amountMinor) ||
        event.amountMinor <= 0 || !['Deposited', 'Withdrawn'].includes(event.type)) {
      throw new Error('invalid event/version');
    }
    const balanceMinor = state.balanceMinor +
      (event.type === 'Deposited' ? event.amountMinor : -event.amountMinor);
    if (!Number.isSafeInteger(balanceMinor) || balanceMinor < 0) throw new Error('invalid balance');
    state = { balanceMinor, version: event.version };
  }
  return state;
}
module.exports = { replayBalance };
```

`Deposited(100)` at version one followed by `Withdrawn(30)` at two yields balance 70/version two. The same history yields the same state. Unknown types, gaps and negative balances fail visibly rather than silently advancing a version. This local example is not a complete monetary ledger: multi-currency, transfer accounting and authorization need their own contracts.

## Append against the version that justified the command

A PostgreSQL sketch supplies one stream row per account and immutable accepted events:

```sql
CREATE TABLE account_streams (
  account_id TEXT PRIMARY KEY,
  version BIGINT NOT NULL DEFAULT 0 CHECK (version >= 0)
);
CREATE TABLE account_events (
  account_id TEXT NOT NULL REFERENCES account_streams(account_id),
  version BIGINT NOT NULL CHECK (version > 0),
  event_id UUID NOT NULL UNIQUE,
  event_type TEXT NOT NULL CHECK (event_type IN ('Deposited', 'Withdrawn')),
  amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
  PRIMARY KEY (account_id, version)
);
```

After validating a command against replayed state, this parameterized statement claims its expected version and inserts one event atomically:

```sql
WITH claimed AS (
  UPDATE account_streams SET version = version + 1
  WHERE account_id = $1 AND version = $2
  RETURNING account_id, version
)
INSERT INTO account_events (account_id, version, event_id, event_type, amount_minor)
SELECT account_id, version, $3, $4, $5 FROM claimed
RETURNING version;
```

No returned row means a conflict/missing stream, not success. Reload and re-evaluate the command's invariant; do not blindly retry an old withdrawal decision. If the event insert fails, the statement rolls back its version claim. Appending several events requires one atomic transaction and contiguous range allocation.

Stream/event identity and tenant scope must be authoritative, and replay must belong to that same stream. A unique event ID rejects duplicate append; command idempotency additionally needs a stable command identity and response/result lookup when commit outcome is unknown. An event sequence field is not an event schema version.

## Snapshots and projections retain their source position

A snapshot needs stream identity, exact event version, state and interpretation/schema version. Replay only subsequent events. A snapshot made from stale state but labeled with the newest version skips real history; store the version belonging to the state, not a newly queried count. Validate snapshots and keep a rebuild path while required history is retained.

A projection tracks progress with its local mutations atomically and handles redelivery under a durable dedup/version policy. Build replacement projections separately, catch them up to a defined watermark and switch reads under a reviewed freshness policy. Timestamp sorting does not supply a globally ordered committed log; choose an actual source-position contract.

## Evolve history without replaying side effects

Retain deterministic handlers/upcasters for historical schema versions and test old fixtures. A correction is usually another fact with explicit meaning, not an edit pretending the original never happened. Avoid calling current mutable prices, time or remote APIs in the reducer, because replay would change history's result.

Do not compact/delete authoritative events merely because Kafka can compact a transport topic. A snapshot may support present-state recovery while losing older temporal reconstruction. Define retention, legal holds, erasure, encryption/key retirement and backup recovery deliberately. Keeping identifiers instead of state can also lose reconstructability if the referenced value later changes.

## Decisions and mistakes

Use event sourcing where authoritative history, recovery and domain interpretation justify its costs. Ordinary state tables with audit/outbox can be simpler. CQRS can complement it but is not required. Separate derived read stores introduce freshness and operating work.

Test concurrent expected-version append, invalid/unknown events, replay from snapshots, historical schema evolution and effect-free rebuild. Monitor append conflicts, stream sizes, replay time, projection lag and restore evidence. Immutable append conventions do not automatically create tamper-proof evidence or establish compliance.

## Summary

Events are authoritative accepted facts; current state is their deterministic interpretation. Atomic expected-version append preserves the decision boundary under concurrency. Snapshots, projections, schema evolution and retention must preserve the history required for reconstruction, while replay avoids external effects.

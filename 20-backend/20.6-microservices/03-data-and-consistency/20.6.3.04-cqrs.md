# CQRS (Command Query Responsibility Segregation)

## Definition

**CQRS (Command Query Responsibility Segregation)** is an architectural pattern that separates read operations (queries) from write operations (commands) into distinct models, services, and often databases. Instead of a single model that handles both reads and writes, CQRS uses separate **command models** for mutations (create, update, delete) and **query models** for reads (select, list, search). This separation allows each side to be optimized independently for its specific workload.

> **Textbook Definition:** Command Query Responsibility Segregation separates state-changing and read operations through distinct models or interfaces. Separate processes, databases and event sourcing are optional implementation choices; asynchronous projections introduce explicit freshness constraints.

## First Principles

The rules for accepting an order differ from the information needed to display an order list. Distinct models can make each task clearer without separate processes or databases. A single database may still serve both well; separation is a deliberate modeling choice, not proof that one model is impossible.

When a read model is projected asynchronously, the accepted write and its visible read representation diverge temporarily. That lag belongs to the chosen synchronization mechanism, not to the definition of CQRS.

## Trace a write result and a later read

```text
place order -> command model: authority + invariants -> authoritative commit
                                                       |
                                          optional async projection
                                                       |
list orders -> query model: permitted summary + freshness policy
```

Commands may return an identifier, accepted representation or version; they need not return “no data.” Queries still validate filters/page budgets and authorize object/property access. A HTTP method is not the definition of a command/query, and a separate model does not automatically add a distributed boundary.

## Project one versioned full-state summary

This complete JavaScript helper illustrates an asynchronous **full-state** event. It includes every field needed for this summary, so a newer snapshot can replace an older one without applying intermediate deltas. These facts come from a trusted validated event pipeline, not a user's arbitrary request.

```javascript
function projectOrder(current, event) {
  if (typeof event.id !== 'string' || !event.id || typeof event.tenantId !== 'string' ||
      !event.tenantId || !Number.isSafeInteger(event.version) || event.version < 1 ||
      !['pending', 'confirmed', 'cancelled'].includes(event.status) ||
      !Number.isSafeInteger(event.totalMinor) || event.totalMinor < 0) {
    throw new Error('invalid order snapshot');
  }
  if (current && (current.id !== event.id || current.tenantId !== event.tenantId)) {
    throw new Error('wrong projection identity');
  }
  if (current && current.version >= event.version) return current;
  return { id: event.id, tenantId: event.tenantId, version: event.version,
    status: event.status, totalMinor: event.totalMinor };
}
module.exports = { projectOrder };
```

Version three updates the summary; a delayed version two leaves three unchanged. A duplicate version three does not increment totals again. Persist that version check and update atomically: two independent read-then-write handlers can still let the older snapshot overwrite a newer one. Divergent payloads with the same version require investigation rather than treating every same-version value as semantically identical.

This rule is unsuitable for delta events such as `ItemAdded`: skipping a missing delta can lose a change. Delta projections need contiguous versions, durable deduplication and a gap/rebuild policy. The [event sourcing chapter](20.6.3.03-event-sourcing.md) owns authoritative replay; the [outbox chapter](20.6.3.06-transactional-outbox.md) owns durable publication and local consumer atomicity.

## Write invariants remain authoritative

Checking inventory then creating an order is a race unless reservation/update happens under the inventory owner's atomic boundary. A command handler validates identity, tenant, fields and business rules, then commits through that owner. Committing a row and separately publishing an event has a crash gap; use transactional publication intent when later projection is required.

A read model can copy permitted display fields, but should not become a second writer of the order's authoritative status. It needs access policy even if the source was already authorized: a copied tenant identifier is not permission to return every tenant's data.

## Make freshness visible to the user

| Required read behavior | Possible contract | Boundary |
| --------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| Show accepted order immediately | Return the committed representation/version from the command | Avoids assuming a projection has caught up |
| Read at least my accepted version | Bounded wait for projection version or authoritative read | Needs timeout and unknown/lag state |
| Dashboard tolerates delay | Expose lag/as-of data under a defined threshold | Must not present stale data as an authorization decision |

An accepted payment can coexist with a lagging summary. Do not prompt another payment merely because that summary still says pending. Polling, push notification and bounded version-aware reads are product choices; they do not remove the recovery obligation.

## Rebuild and scale only what justifies the cost

Separate read stores can isolate query load and index shapes, but add replication, access, retention and operational overhead. Rebuild into a new projection, retain its checkpoint, catch up and switch under a reviewed consistency policy. Independent failure/retry can require both dedup and order handling. A mediator/bus library dispatches handlers; it does not automatically make their storage durable or establish CQRS's benefits.

Start with one process/database when it meets the need. Split only the read models/workloads whose constraints justify it. CQRS does not require event sourcing, Kafka, asynchronous propagation or a normalized write schema. Test capacity rather than promising instant dashboards or universal performance gains.

## Mistakes and best practices

Keep query authorization/input budgets, command invariants, publication recovery and projection progress explicit. Avoid duplicated domain decisions in stale read models, blindly replayed increments, or unmonitored synchronization. Test stale/out-of-order/duplicate snapshots, cross-tenant reads, read-your-writes deadlines and rebuild cutover. Measure projection age and user-visible incomplete work alongside read/write throughput.

## Summary

CQRS separates command and query responsibilities through distinct models. Deployment and synchronization choices determine scaling and freshness. Authoritative writes enforce invariants; read models enforce access and a visible lag contract. Use separate stores or event sourcing only when their added work is justified.

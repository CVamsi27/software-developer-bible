# Decomposing the Monolith Database

A monolith can be split into processes while services still share writable tables. A safe data split must account for ownership, joins, constraints, jobs, reports and recovery; moving rows alone does not create independent services.

## Definition

**Database decomposition** moves a shared monolith database into schemas or stores owned by individual services. The system must keep working during the move. Moving data is harder than redirecting an endpoint: joins, foreign keys (FKs), transactions, and reports may depend on related data being stored together. Those dependencies must be identified and replaced or preserved deliberately.

> **Textbook Definition:** Database decomposition transfers data ownership from a shared schema to independently controlled service boundaries. Cross-boundary queries, integrity rules and transaction dependencies must be preserved or replaced through explicit contracts.

```text
Before: Orders and Catalog services share writable tables in one database.
After:  Orders owns order data; Catalog owns product data. Cross-boundary needs
        use an owner API, a constrained copy/read model, or a deliberate workflow.
```

## First Principles

A transaction and foreign key can enforce a rule only within the database boundary that supports them. Splitting storage changes that boundary. Start with the rules that must remain atomic, then choose ownership and communication around them. Separate deployments sharing writable tables still share schema and release dependencies.

Moving bytes does not move authority. During migration, one store must own accepted writes; copies need an explicit freshness and recovery contract. Two independent writes can diverge when only one succeeds.

## Trace one order boundary through extraction

```text
shared tables -> owner controls writes -> consistent copy + change capture
                                             |
                                     verify target at a watermark
                                             |
                                transfer write authority -> retire old paths
```

Inventory tables, foreign keys, jobs, reports, administrative scripts and actual read/write callers. Query statistics help reveal traffic but can omit rarely used recovery paths. Choose a boundary with understandable invariants and business ownership; a table name or low foreign-key count alone is insufficient.

First route mutations through the owning module/service while it still uses the shared store. Replace foreign reads with owner APIs, narrow local replicas or query composition where suitable. Read and write migration order depends on dependencies; there is no universally safe “reads first” calendar.

## Copy without missing or overwriting accepted changes

**Change data capture (CDC)** turns committed source changes into downstream records. PostgreSQL's write-ahead log (WAL) underlies logical decoding. A **log sequence number (LSN)** identifies a position in that log; it is not necessarily a unique identity for every changed row.

A consistent snapshot and its matching log position must be coordinated by the connector/database protocol. Arbitrarily recording a position and running a later dump does not prove there is no gap. Preserve the log until catch-up finishes; retained replication-slot WAL can exhaust source storage if the consumer stalls.

The target needs per-key ordering and identity from the connector contract, including transaction/record ordering when several changes share a log position. Commit target mutation and its deduplication/checkpoint record atomically where they share a store. A separate “seen LSN” write can lose a change or suppress another row from the same source transaction.

Snapshot rows can arrive after newer live updates. Use a verified source version/order strategy, or stage the snapshot and replay captured changes before publishing the target. Blind `ON CONFLICT DO UPDATE` makes retries repeatable but can still overwrite fresh data with old values. Persist deletion ordering too: a late snapshot must not resurrect a deleted row.

## A small versioned target model

This complete JavaScript helper shows the stale-copy rule for one source key. It assumes the source supplies a monotonically increasing per-key version; it does not invent that property from an LSN or timestamp. A database implementation must atomically compare/update this state, including tombstones, and its checkpoint.

```javascript
const { isDeepStrictEqual } = require('node:util');

function applyChange(current, change) {
  if (!change || typeof change.key !== 'string' || !change.key ||
      !Number.isSafeInteger(change.version) || change.version < 1 ||
      !['upsert', 'delete'].includes(change.op)) throw new Error('invalid change');
  if (current && current.key !== change.key) throw new Error('wrong key');
  if (change.op === 'upsert' && (!change.value || typeof change.value !== 'object')) {
    throw new Error('missing value');
  }
  const deleted = change.op === 'delete';
  const value = deleted ? null : change.value;
  if (current && current.version > change.version) return current;
  if (current && current.version === change.version) {
    if (current.deleted !== deleted || !isDeepStrictEqual(current.value, value)) {
      throw new Error('conflicting change for version');
    }
    return current;
  }
  return { key: change.key, version: change.version,
    deleted, value };
}
module.exports = { applyChange };
```

Apply live version 12, then snapshot version 10: the target keeps 12. Apply deletion 13, then retry 12: the tombstone keeps the deletion. An identical duplicate is safe to ignore; a different value at the same version is a source conflict and fails visibly.

For a batched backfill, use stable keyset ordering and a checkpoint of the correct key type. A UUID key does not have a numeric zero watermark. Keyset progress alone does not cover concurrent insertions behind the cursor, updates or deletions; coordinated change capture must cover those operations. Commit progress only after the target batch is durably accepted.

## Replace each lost integrity rule deliberately

| Dependency | Replacement | Boundary to preserve |
| --------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| Product display fields in order screens | Minimal versioned local replica | Visible lag and policy for missing/deleted references |
| Price accepted for an order | Persist accepted price/currency with the order | A later catalog update must not rewrite historical price |
| Stock reservation | Inventory owner enforces atomic availability | Replicated “stock available” cannot authorize a reservation |
| Cross-store business process | Durable saga or a supported atomic protocol | Intermediate states, uncertainty and compensation policy |
| Analytics joins | Separate read/analytics model | Checkpoint, reconciliation and privacy retention |

API composition adds latency and availability coupling; local replication adds lag, storage and deletion/authorization duties. Neither is automatically the right answer. Keep related invariants together when separation produces more coordination cost than useful independence. A saga is not a replacement for every foreign key or transaction.

## Validate authority before the cutover

Compare target records and business invariants at a common captured watermark. Raw counts can match while different rows or values are wrong. Hashes require canonical serialization and comparable snapshots; counts/checksums alone do not establish completeness across a moving source. Test deletion, nulls, large transactions, replay, connector outage and schema changes.

Quiesce/fence old writers or use a defined authority-transfer protocol before enabling new writes. Include jobs and administrator roles. Narrow grants on the extracted tables rather than revoking all public-schema access and breaking unrelated modules. Table owners, inherited roles, privileged roles and compatibility views/functions can bypass the intended restriction; test using real caller roles.

A compatibility view is a transitional dependency with an owner and retirement condition. Renaming a table is not proof that all old writes are fenced. Once the new store accepts writes that the old one cannot represent, routing back is not a complete rollback; reconcile/copy those writes or roll forward under a documented procedure.

## Operate the transition and retire it

Measure capture/apply lag, oldest pending change, divergence, source WAL/storage pressure and checkpoint recovery. Throttle copying from observed capacity, not a fixed universal batch size or timeline. Plan replication-slot removal, credentials, backups, restore tests, retention and deletion across both stores.

Database-per-service can start with separate schemas and roles on one instance. Physical separation adds failure/resource isolation but also operational cost; it does not by itself improve every latency or compliance boundary. CDC and outbox address different records: CDC captures storage changes; an outbox commits application publication intent. Both require tested delivery, schema and consumer contracts.

## Summary

Decompose around ownership and invariants. Coordinate snapshots with change capture, prevent stale copies and deletion resurrection, validate at a common watermark, and fence every old writer before transferring authority. Retire shims and old data only after recovery, retention and rollback requirements are satisfied.

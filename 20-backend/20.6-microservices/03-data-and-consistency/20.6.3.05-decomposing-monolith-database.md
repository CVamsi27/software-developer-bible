# Decomposing the Monolith Database

> **TL;DR:** Extracting services is easy; extracting *data* is the migration. A shared database couples services through foreign keys, joins, and implicit transactions — every schema change becomes a cross-team negotiation. The escape sequence: pick a bounded context, stop others from reading its tables (API-first), copy data to the service's own store, keep them synchronized during transition with **CDC** (preferred) or carefully-audited **dual writes** (risky), backfill history in batches, then cut reads and finally flip ownership. Never replace referential integrity with distributed transactions — replicate or compose instead, and use sagas for cross-service workflows.
>
> **Why it matters:** "We want microservices but we have one Postgres" describes nearly every enterprise. Interviewers probe exactly here: how do you split the database without a big-bang rewrite and without losing integrity?

## Definition

**Database decomposition** is the process of moving from a shared monolith database to service-owned schemas/stores while keeping the system correct throughout. It differs from code-level strangulation (routing endpoints) because state has gravity: joins, FKs, transactions, and reporting queries all assume co-location.

```text
BEFORE                              AFTER
┌───────────────────────────────────────────────────────────────────┐
│  shared postgres          │       │ orders-db   │   │ catalog-db               │
│  ├ orders*                │  ──►  │ orders only │   │ products                 │
│  ├ order_items ─FK→ users                                         │
│  ├ users                                                          │
│  └ products               │                                                                              │
└───────────────────────────────────────────────────────────────────┘
```

## Why Do We Need It?

1. **Independent deploys require independent schemas** — one `ALTER TABLE` review queue for eight teams is a coordination tax that scales worse than the monolith.
2. **Coupled failure domains** — a reporting query pinning the shared CPU starves checkout; per-service stores isolate load.
3. **Team autonomy needs data autonomy** — Conway's law: shared tables produce shared standups; separate stores let teams choose engine, retention, and tuning.
4. **Security boundaries harden at storage** — card data, PHI, or tenant partitions get their own credentials, encryption keys, and audit trails.
5. **Scaling axes diverge** — orders need OLTP write throughput; search needs denormalized read models; analytics needs columnar copies. One database serves none of them well.
6. **The alternative (big-bang rewrite) fails** — history says: strangulate incrementally or do not start.

## How It Works

### Strangulation order FOR DATA (not just code)

Code stranglers reroute traffic first; data must be strangled in a specific sequence because reads are easier to move than writes, and writes are easier than truth:

```text
Step 0  Inventory: table → owning bounded context map; FK graph; join census
        (which services SELECT from which tables? pg_stat_statements helps)

Step 1  Choose target context = smallest inbound-FK count × highest change pain
        (reference/catalog data often first; money last)

Step 2  READS OUT FIRST
        • Consumers call the owner's API instead of SELECTing its tables
        • Add views as temporary compatibility shims for slow consumers

Step 3  WRITES VIA OWNER ONLY
        • Other services stop INSERT/UPDATE on context tables;
          mutations go through API/events (enforce via grants!)

Step 4  COPY + SYNC (this chapter's core)
        • Bulk snapshot into new store, CDC keeps delta applied

Step 5  VERIFY SHADOW RUN
        • Dual-read compare (counts, checksums) until drift = 0 for N days

Step 6  FLIP OWNERSHIP
        • Old tables become read-only → archived → dropped after retention
        • New store is now canonical; old DB consumers were already migrated
```

### Extraction steps in practice

```text
Weeks 1-2   Boundaries: events storming, context map, FK census
Week 3      Freeze cross-context DDL: migrations touching shared tables need owner sign-off
Week 4      Stand up new service + its schema; deploy behind flags
Week 5-6    Snapshot backfill + CDC pipeline running into shadow tables
Week 7      Read path cutover behind feature flag; shadow-read verification dashboards
Week 8      Write cutover; revoke grants on legacy tables (the real enforcement)
Week 9+     Drop legacy tables after retention window; delete the shim views
```

Enforcement detail worth saying aloud in interviews: **database grants are the strangler's teeth.** Feature flags suggest; `REVOKE UPDATE ON orders FROM legacy_role` guarantees.

### Sync during transition: dual-write vs CDC

| Aspect      | Dual writes                                              | CDC (logical decoding / outbox-fed pipeline)             |
| ----------- | -------------------------------------------------------- | -------------------------------------------------------- |
| Mechanism   | App writes both stores in code                           | Capture changes from source WAL; apply downstream        |
| Consistency | Broken by design — partial failure window between writes | Source-of-truth derived; at-least-once, idempotent apply |
| Code impact | Every write path touched, forever                        | Zero app-code change (Debezium) or one outbox insert     |
| Miss risk   | Silent divergence on crash/retry                         | Replayable log; lag visible and alertable                |
| Verdict     | Avoid except tiny, short-lived, well-monitored windows   | Default choice                                           |

```typescript
// ANTI-PATTERN: dual write — two failure domains, no atomicity
await pg.query('UPDATE orders SET status=$1 WHERE id=$2', [status, id]); // commits...
await es.index({ index: 'orders', id, document: { status } });           // ...then this throws?
// → divergence discovered by customers, not by you.

// PATTERN: outbox — same transaction publishes intent
await pg.tx(async t => {
  await t.query('UPDATE orders SET status=$1 WHERE id=$2', [status, id]);
  await t.query(
    `INSERT INTO outbox(topic, key, payload) VALUES ('orders.events', $1, $2)`,
    [id, JSON.stringify({ type: 'OrderStatusChanged', orderId: id, status })]);
});
// Relay drains outbox → Kafka → consumers (new store, search index, other services)
```

### Backfill strategies

```text
SNAPSHOT + CATCHUP (default)
  1. Record LSN/position at snapshot start
  2. pg_dump/COPY consistent snapshot into new store (bulk, throttled)
  3. Start CDC consumer FROM recorded position — no gap, some overlap (dedupe by PK+version)

BATCHED WATERMARK BACKFILL (when you cannot take snapshots calmly)
  • Iterate PK ranges: WHERE id > $watermark ORDER BY id LIMIT 10_000
  • Sleep/throttle between batches; run off-peak; resume from watermark on crash
  • Upserts (ON CONFLICT DO UPDATE) make re-runs safe

LIVE-TAIL FIRST (small hot tables)
  • Begin CDC immediately, accumulate deltas, snapshot later, replay overlap
```

Operational rules: monitor backfill lag as an SLI; never backfill through the ORM entity layer (memory blowups); verify with row counts + periodic checksum aggregates (`sum(hashtext(row::text))`).

### Referential integrity across services

Once FKs cross service boundaries they cannot exist. Replace each one deliberately:

| Strategy                     | How                                                                 | Cost                                                          |
| ---------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------- |
| **API composition**          | Service B calls A at request time to resolve reference              | Latency + availability coupling; fine for low-QPS admin paths |
| **Local replication**        | B stores just-needed fields (id, name, currency) updated via events | Eventual consistency; queries stay local — default choice     |
| **Id-only + lazy fetch**     | Persist foreign id; resolve on demand with cache                    | Simplest; N+1 risk at edges                                   |
| **Denormalized read models** | CQRS projections join streams offline                               | Query-time simplicity, projection lag                         |

Integrity moves from *enforced* (FK constraint rejects) to *eventually verified*: reconciliation jobs detect orphaned ids, and domain invariants ("order must reference live product") become explicit sagas/workflows rather than constraints.

### No distributed transactions across the seam

The moment two stores would need to commit together, reach for the saga pattern — choreographed events or an orchestrator with compensating actions — not XA/2PC. The extraction itself should be designed so no single business operation spans both stores at steady state; during transition, the outbox + idempotent consumers give effectively-once behavior where it matters.

## Code Examples

### CDC pipeline sketch (Debezium-style event → new store)

```typescript
// workers/cdc-apply.ts — idempotent applier keyed by primary key + source position
type ChangeEvent = {
  op: 'c' | 'u' | 'd' | 'r';
  source: { lsn: string; ts_ms: number };
  key: { id: string };
  after?: Record<string, unknown> | null;
};

export async function apply(evt: ChangeEvent): Promise<void> {
  const seen = await offsets.isApplied(evt.source.lsn);       // dedupe on replays
  if (seen) return;

  switch (evt.op) {
    case 'd':
      await targetStore.delete('orders', evt.key.id);
      break;
    case 'c': case 'r': case 'u':
      await targetStore.upsert('orders', evt.key.id, evt.after!);
      break;
  }
  await offsets.commit(evt.source.lsn);                        // advance AFTER success
}

// Consumer group semantics: partition by PK → per-key ordering preserved;
// retries go to DLQ with full payload; reconciliation job compares nightly.
```

### Batched backfill job with watermark

```typescript
// scripts/backfill-orders.ts
const BATCH = 10_000;

export async function backfill(): Promise<void> {
  let watermark = await state.get('orders.backfill.watermark', 0);
  for (;;) {
    const rows = await source.query(
      `SELECT * FROM orders WHERE id > $1 ORDER BY id LIMIT $2`,
      [watermark, BATCH],
    );
    if (!rows.rowCount) break;

    await target.bulkUpsert('orders', rows.rows);              // idempotent upserts
    watermark = rows.rows[rows.rows.length - 1].id;
    await state.set('orders.backfill.watermark', watermark);   // crash-safe resume

    await sleep(200);                                          // throttle: protect source
  }
}
```

### Replacing a cross-context JOIN with local replication

```typescript
// BEFORE (monolith): one query, coupled schemas
// SELECT o.id, u.email FROM orders o JOIN users u ON u.id = o.user_id;

// AFTER (service-owned):
interface CustomerRef { id: string; email: string; updatedAt: Date; }

@Injectable()
export class OrderService {
  // Local replica table `customer_refs`, maintained by events:
  @EventPattern('customer.changed')
  async onCustomerChanged(e: { id: string; email: string; updatedAt: string }) {
    await this.db.upsertCustomerRef({
      id: e.id, email: e.email,
      updatedAt: new Date(e.updatedAt),
    });
  }

  async listWithContact(limit: number) {
    return this.db.query(
      `SELECT o.id, c.email
         FROM orders o JOIN customer_refs c ON c.id = o.customer_id
        ORDER BY o.created_at DESC LIMIT $1`, [limit]);   // no network hop
  }

  // Reconciliation guard: orphaned references surface in metrics, not crashes
  @Cron('0 3 * * *')
  async reconcile() {
    const missing = await this.db.countOrphanedCustomerRefs();
    if (missing > 0) metrics.orphanedRefs.set(missing);     // alerts; saga repairs
  }
}
```

### Ownership flip with grants

```sql
-- Transition week: legacy readers still allowed (read-only compatibility view)
CREATE VIEW legacy.orders_v AS SELECT * FROM orders_service.orders;

-- Cutover day: enforce what the wiki merely suggested
REVOKE INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public FROM monolith_app_role;
REVOKE USAGE ON SCHEMA public FROM reporting_role;         -- force API/reporting migration
ALTER TABLE orders RENAME TO orders_retired_20260825;      -- rename = instant guard rail
-- After retention window: DROP TABLE orders_retired_20260825;
```

## Real-World Use Cases

1. **Marketplace checkout split** — Orders extracted first (highest change pain); catalog reference data replicated locally; payment kept inside orders' boundary because splitting it created more sagas than value.
2. **Multi-tenant SaaS reporting relief** — Analytics moved to its own store fed by CDC; the monolith instantly shed nightly dashboard load; product teams stopped paging about BI queries.
3. **Regulatory isolation** — Card data extracted to a PCI-scoped service with separate credentials and audit logging; remaining services hold only tokens.
4. **Acquired-company integration** — Their "users" table became a replicated identity reference via events; zero-downtime coexistence for two years before full merge.
5. **Scale-out write path** — Hot `events` append-only table extracted to its own TimescaleDB instance; ingestion p99 dropped 8× without touching business logic elsewhere.

## Common Mistakes

| Mistake                                             | Fix                                                                               |
| --------------------------------------------------- | --------------------------------------------------------------------------------- |
| Splitting tables along entity lines, not contexts   | Bounded-context mapping first; tables follow language                             |
| Dual writes as the permanent sync mechanism         | CDC/outbox; dual writes only as brief, monitored scaffolding                      |
| Backfill through ORM models                         | Raw batched SQL/COPY with watermarks and throttle sleeps                          |
| Dropping FKs and hoping events cover it             | Explicit strategy per relationship (replicate/compose/lazy) + reconciliation jobs |
| Keeping cross-service JOINs alive via views forever | Views are shims with sunset dates; track and burn down                            |
| Distributed transactions (XA) across services       | Sagas with compensations (link below)                                             |
| Big-bang cutover on a Friday                        | Flag-guarded phased flip with shadow-read verification and rollback plan          |
| Forgetting grants enforcement                       | REVOKE is the real migration completion test                                      |

## Best Practices

1. **Map before moving**: FK graph + join census + query stats decide the order; intuition picks wrong targets.
2. **Reads before writes, writes before truth**: each phase independently verifiable and reversible.
3. **One context at a time** — parallel extractions multiply rollback matrices; serialize the hard ones.
4. **Make divergence impossible to miss**: checksum/count comparisons daily during transition; alarm on any drift.
5. **Replicate minimal fields** — local replicas carry ids plus display data, never full entities; freshness follows the decision it supports.
6. **Design workflows as sagas from day one** — compensations documented next to invariants, rehearsed in staging.
7. **Sunset dates on every shim** — views, compat APIs, dual-write flags expire visibly or the monolith regrows.
8. **Rehearse the rollback**: flipping back to legacy tables must remain possible until retention drops them.

## Performance Considerations

- CDC pipelines add seconds-to-minutes staleness; user-facing flows must tolerate it or route synchronously through APIs during transition.
- Backfills compete for I/O: throttle, run off-peak, watch replication slot lag (unbounded slots can bloat WAL retention).
- Local replication trades write amplification for read latency — budget the event fan-in per replica table.
- Post-flip, the freed shared database usually shows surprising headroom; resist immediately re-crowding it.

## Summary

- Data strangulation order: inventory → reads out → writes via owner → copy+sync → shadow verify → flip → retire.
- CDC/outbox synchronization beats dual writes; idempotent appliers make at-least-once safe.
- Backfills are batched, watermarked, throttled, and resumable — never ORM-shaped heroics.
- Cross-service integrity = local replication + reconciliation, not distributed transactions; workflows become sagas.
- Grants, renames, and revocations enforce what documentation cannot.

## Cheat Sheet

| Concept                | Description                                                |
| ---------------------- | ---------------------------------------------------------- |
| Shared-database hazard | Coupled deploys, joins, transactions, failure domains      |
| Strangulation (data)   | Reads → writes → ownership flip, phase by phase            |
| Outbox pattern         | Domain change + event row committed atomically             |
| CDC                    | Logical decoding (Debezium) streams changes; app untouched |
| Dual-write risk        | Two non-atomic writes; silent divergence on failure        |
| Watermark backfill     | Batched PK-range upserts, crash-safe, throttled            |
| API composition        | Resolve references via calls at request time               |
| Local replication      | Minimal foreign fields updated by events                   |
| Saga                   | Workflow across services with compensating actions         |
| Grant revocation       | Enforceable proof the migration finished                   |

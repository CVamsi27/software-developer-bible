# Transactional Outbox Pattern

> Stage 6 of the [Data & Consistency](INDEX.md) — prev: [Decomposing the Monolith Database](20.6.3.05-decomposing-monolith-database.md)
>
>
> **Why it matters:** This is a Backend interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

The Transactional Outbox pattern ensures reliable event publishing by writing events to an "outbox" table within the same database transaction as the business data. A separate relay process (poller or CDC) reads the outbox and publishes events to a message broker. This guarantees that events are only published if the business transaction commits, eliminating the dual-write problem.

**Key terms:**
- **Outbox table** — a database table that stores pending events
- **Relay** — a process that reads the outbox and publishes events to a broker
- **CDC (Change Data Capture)** — monitoring the database's WAL for changes (e.g.,Debezium)
- **Idempotent consumer** — a consumer that safely handles duplicate events
- **DLQ (Dead Letter Queue)** — a queue for events that fail processing after retries

## First Principles

The outbox solves one specific impossibility: atomic "commit to DB + publish to broker."

1. **Two systems cannot share one transaction.** Commit the DB then publish = publish may be lost on crash; publish then commit = events about uncommitted data. Both orders are wrong because the broker isn't transactional (→ 20.6.3.02).
2. **So make the event a row in the same DB transaction.** The outbox table commits atomically with the business change — then a relay publishes outbox rows (poll or CDC/Debezium) and marks them sent. At-least-once delivery is guaranteed; consumers dedupe (→ 20.3.3.05). Atomicity achieved by *renaming the problem*: one transaction, one system.
3. **Ordering and lag are the operational care-abouts**: relay lag = downstream staleness; per-aggregate ordering needs partition-aware relay design. The pattern is now the *default* answer for event publishing — anything else is accepting silent event loss.

## Why Do We Need It?

The **dual-write problem** is the core issue:

```text
The Dual-Write Problem:
─────────────────────────────────────────────────

Scenario 1: DB succeeds, publish fails
  BEGIN;
  INSERT INTO appointments (...);  ← succeeds
  COMMIT;
  publish('appointment.created', data);  ← network error!
  Result: Data saved but event lost — downstream services never notified

Scenario 2: Publish succeeds, DB fails
  publish('appointment.created', data);  ← succeeds
  BEGIN;
  INSERT INTO appointments (...);  ← constraint violation!
  ROLLBACK;
  Result: Event published but data not saved — phantom event

Scenario 3: Both succeed but not atomic
  BEGIN; INSERT INTO appointments (...); COMMIT;  ← succeeds
  publish('appointment.created', data);  ← succeeds
  But what if the app crashes between COMMIT and publish?
  Result: Data saved but event lost (same as Scenario 1)
─────────────────────────────────────────────────
```

**The outbox pattern solves this by making the write and the event atomic.**

## How It Works

### Outbox Architecture

```text
┌────────────────────────────────────────────────────────────────────────┐
│ Transactional Outbox Flow                                              │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  Application                                                           │
│  ├── BEGIN                                                             │
│  ├── INSERT INTO appointments (patient_id, ...) -- business data       │
│  ├── INSERT INTO outbox (event_type, payload, status) -- the event     │
│  └── COMMIT  ← atomic: both succeed or both fail                       │
│                                                                        │
│  Relay (Polling)                                                       │
│  ├── SELECT * FROM outbox WHERE status = 'pending' LIMIT 100           │
│  ├── For each event: publish to broker                                 │
│  └── UPDATE outbox SET status = 'published' WHERE id IN (...)          │
│                                                                        │
│  Relay (CDC)                                                           │
│  ├── Debezium monitors PostgreSQL WAL                                  │
│  ├── Captures INSERT on outbox table                                   │
│  └── Publishes to Kafka/Topic immediately                              │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

### Two Relay Strategies

| Strategy | How it works | Latency | Complexity | Best for |
| ----------- | ------------------------------------------------------ | ------------ | ------------ | ------------------------- |
| **Polling** | Cron polls `SELECT FROM outbox WHERE status='pending'` | Seconds | Low | Low-volume, simple setups |
| **CDC** | Debezium monitors WAL, captures changes in real-time | Milliseconds | Medium | High-volume, low-latency |

## Code Examples

### Outbox Table Schema (Prisma)

```prisma
model OutboxEvent {
  id          String   @id @default(uuid()) @db.Uuid
  tenantId    String   @db.Uuid
  eventType   String   // e.g., "appointment.created"
  aggregateId String   @db.Uuid // ID of the entity that changed
  payload     Json     // the event data
  status      OutboxStatus @default(PENDING)
  attempts    Int      @default(0)
  maxAttempts Int      @default(5)
  lastError   String?
  createdAt   DateTime @default(now())
  processedAt DateTime?

  @@index([status, createdAt])
  @@index([tenantId, status])
}
```

### Writing to Outbox in the Same Transaction

```typescript
// appointment.service.ts
@Injectable()
export class AppointmentService {
  constructor(
    private prisma: PrismaService,
    private outbox: OutboxService,
  ) {}

  async createAppointment(tenantId: string, dto: CreateAppointmentDto) {
    return this.prisma.$transaction(async (tx) => {
      // 1. Business data
      const appointment = await tx.appointment.create({
        data: {
          tenantId,
          patientId: dto.patientId,
          doctorId: dto.doctorId,
          scheduledAt: dto.scheduledAt,
        },
      });

      // 2. Outbox event — same transaction, same commit
      await tx.outboxEvent.create({
        data: {
          tenantId,
          eventType: 'appointment.created',
          aggregateId: appointment.id,
          payload: {
            appointmentId: appointment.id,
            patientId: dto.patientId,
            doctorId: dto.doctorId,
            scheduledAt: dto.scheduledAt,
          },
        },
      });

      return appointment;
    });
    // If commit fails, BOTH the appointment AND the event are rolled back
    // If commit succeeds, BOTH are guaranteed to exist
  }
}
```

### Polling Relay (Simple)

```typescript
// outbox-relay.scheduler.ts
@Injectable()
export class OutboxRelayScheduler {
  constructor(
    private prisma: PrismaService,
    private eventBus: EventBusService,
  ) {}

  @Cron('*/2 * * * * *') // every 2 seconds
  async drain() {
    const events = await this.prisma.outboxEvent.findMany({
      where: {
        status: 'PENDING',
        attempts: { lt: 5 },
      },
      orderBy: { createdAt: 'asc' },
      take: 100,
    });

    for (const event of events) {
      try {
        await this.eventBus.publish(event.eventType, event.payload);

        await this.prisma.outboxEvent.update({
          where: { id: event.id },
          data: {
            status: 'PUBLISHED',
            processedAt: new Date(),
          },
        });
      } catch (error) {
        await this.prisma.outboxEvent.update({
          where: { id: event.id },
          data: {
            attempts: { increment: 1 },
            lastError: error.message,
            status: event.attempts + 1 >= event.maxAttempts ? 'FAILED' : 'PENDING',
          },
        });
      }
    }
  }
}
```

## Real-World Use Cases

| Use Case | Relay Strategy | Why |
| ------------------------ | ----------------- | ------------------------------------------ |
| **Clinic SaaS** (Docita) | Polling (2s cron) | Low volume, simple ops, PostgreSQL-backed |
| **E-commerce** (Shopify) | CDC (Debezium) | High volume, low latency, Kafka downstream |
| **Fintech** (Stripe) | CDC + idempotency | Exactly-once semantics critical |
| **Healthcare** (Epic) | Polling + audit | Compliance requires audit trail of events |
| **SaaS multi-service** | CDC | Many consumers need real-time events |

## Common Mistakes

### 1. Writing Event Before Business Data

```typescript
// BAD: Event written outside the transaction
await this.eventBus.publish('appointment.created', data); // no guarantee
await this.prisma.$transaction(async (tx) => {
  await tx.appointment.create({ data }); // might fail
});

// GOOD: Both in the same transaction
await this.prisma.$transaction(async (tx) => {
  await tx.appointment.create({ data });
  await tx.outboxEvent.create({ data: event }); // same transaction
});
```

### 2. Relay Not Handling Duplicate Events

```typescript
// BAD: Consumer processes the same event twice (relay retried)
async function handleAppointmentCreated(event) {
  await sendEmail(event.patientId); // sent twice!
}

// GOOD: Idempotent consumer with deduplication
async function handleAppointmentCreated(event) {
  const dedupKey = `email:${event.appointmentId}:created`;
  const alreadySent = await cache.get(dedupKey);
  if (alreadySent) return; // skip duplicate

  await sendEmail(event.patientId);
  await cache.set(dedupKey, '1', 'EX', 86400); // 24h dedup window
}
```

### 3. Not Monitoring Relay Lag

```sql
-- BAD: No monitoring — relay falls behind silently
-- GOOD: Alert on pending events
SELECT count(*) as pending_count,
       max(now() - created_at) as oldest_pending
FROM outbox_events
WHERE status = 'PENDING';
-- Alert if pending_count > 1000 or oldest_pending > 30s
```

### 4. Outbox Table Growing Unbounded

```sql
-- BAD: Published events accumulate forever
-- GOOD: Clean up old events
DELETE FROM outbox_events
WHERE status = 'PUBLISHED'
  AND processed_at < now() - interval '7 days';
```

## Best Practices

1. **Same transaction** — business data and outbox event must be in the same `$transaction`.
2. **Idempotent consumers** — assume events will be delivered more than once.
3. **DLQ for failures** — after max retries, move to a DLQ for manual inspection.
4. **Monitor relay lag** — alert when pending events exceed a threshold.
5. **Clean up old events** —定期删除已发布的事件 (retain for audit if needed).
6. **Ordering** — use `createdAt` ordering in the outbox; consumers may need sequence numbers.
7. **CDC for high volume** — polling works for <1000 events/sec; CDC for more.
8. **Batch publishing** — relay should batch events to reduce broker round-trips.
9. **Tenant-scoped outbox** — partition or index by tenant for multi-tenant systems.
10. **Idempotency keys in events** — include a unique event ID so consumers can deduplicate.

## Summary

The transactional outbox pattern solves the dual-write problem by making event publication atomic with business data changes. Write the event to an outbox table in the same database transaction, then relay it asynchronously via polling (simple, seconds latency) or CDC (efficient, milliseconds latency). The critical companion patterns are idempotent consumers (handle duplicates) and DLQ (handle failures). The outbox is the foundation of reliable event-driven architectures.

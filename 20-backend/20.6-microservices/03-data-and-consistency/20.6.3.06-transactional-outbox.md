# Transactional Outbox Pattern

An order can commit while the process crashes before publishing `order.created`; fulfillment then has no durable signal that the order exists.

## Definition

The Transactional Outbox pattern records an event in an "outbox" table within the same database transaction as the business data. A separate relay process reads committed events and publishes them to a message broker. This closes the gap between saving business data and recording publication intent; it does not make broker delivery part of the database commit.

> **Textbook Definition:** The transactional outbox records business state and an event intent in one local database transaction. A relay later publishes committed intents; duplicate publication and eventual delivery still require consumer idempotency and operational recovery.

## First Principles

A local database transaction cannot normally make an arbitrary broker publish atomic. Publish before commit and consumers may act on rolled-back data; commit before publishing and a crash may leave consumers uninformed.

Record the intent alongside the business change instead. Both records commit or neither does. The relay can recover that intent after the writer exits, but publishing and recording relay progress remain separate operations.
An uncertain acknowledgment can therefore cause another publication.

## How It Works


### 1. Trace a committed appointment

```text
Writer: appointment + outbox intent ── one database commit
                              │
Relay: read committed intent → publish event → record progress
                              │
Consumer: receive event → apply chosen effect → acknowledge
```

The **relay** is the publisher that drains the outbox. **Change data capture (CDC)** reads committed database changes from a log, such as PostgreSQL's write-ahead log, instead of querying pending rows. Neither relay choice merges the consumer's effects into the original transaction.

| Crash point | Recovery obligation |
| -------------------------------------------------------- | -------------------------------------------------------------------- |
| Before the writer commits | Roll back both business change and event intent |
| After commit, before publish | Resume from the retained intent |
| After broker acceptance, before relay progress is stored | Republish with the same event ID; consumers must tolerate duplicates |
| After a consumer effect, before acknowledgment | Redelivery is possible; reconcile or deduplicate the effect |

### 2. Commit the mutation and intent together

This Prisma fragment assumes existing `Appointment` and `OutboxEvent` models. Tenant identity comes from the authenticated context; the patient/doctor identifiers must also pass tenant and booking-policy checks inside the authoritative write path.

```typescript
import { randomUUID } from 'node:crypto';

const eventId = randomUUID();
const appointment = await prisma.$transaction(async tx => {
  const saved = await tx.appointment.create({ data: {
    tenantId, patientId, doctorId, scheduledAt,
  }});
  await tx.outboxEvent.create({ data: {
    id: eventId,
    tenantId,
    aggregateId: saved.id,
    eventType: 'appointment.created',
    schemaVersion: 1,
    payload: {
      appointmentId: saved.id,
      patientId: saved.patientId,
      scheduledAt: saved.scheduledAt.toISOString(),
    },
  }});
  return saved;
});
```

An outbox row needs a stable event ID, tenant/aggregate identity, event type, payload/schema version and creation time. A polling relay also needs progress, attempt and claim/retry fields. Store only the data consumers need: payloads can outlive the source row in brokers and backups, so privacy, retention and erasure rules apply.
Do not reconstruct the original event from a business row that may have changed since commit. An uncertain commit can still make a retried API call create another appointment: the command's idempotency/booking invariant is a separate requirement.

### 3. Make relay ownership and acknowledgment explicit

A polling relay claims a bounded batch, publishes each event with its unchanged ID and payload, then records success **after the broker's required acceptance confirmation**. A client method named `publish` is insufficient evidence: document whether its Promise means local buffering, broker receipt or persistence under a configured durability policy.

Multiple workers need atomic claiming, owner-aware progress updates and recovery of expired claims. Database `FOR UPDATE SKIP LOCKED` can claim work without waiting on rows already locked by another transaction; a persisted lease can release database locks before network I/O. Its expiry may overlap a paused old worker, so duplicate publication remains possible.
Bound publish timeouts and retries, and do not hold a database transaction open indefinitely around a broker call.

A failed progress update after successful publication is an uncertain outcome, not proof that the broker rejected the event. Keep the row recoverable and reuse the event ID. Quarantine repeatedly failing events after a bounded attempt budget: record the attempt count, last error, next-eligible-retry time and the owner that last held the claim, then raise an alert carrying the event ID and failure class. A dead-letter queue is another recoverable work store holding the same unchanged event ID, not a substitute for repair — replay from it through an explicit requeue operation rather than automatic redelivery, so consumer deduplication still applies. Separate poison events (schema or authorization failures that will never succeed on retry) from transient ones (broker or timeout failures) so one poison event cannot stall its partition, retain quarantined rows for the audit and replay horizon, and record who replayed them.

#### Polling and CDC have different operational costs

| Choice | What it owns | Boundary to evaluate |
| ------- | -------------------------------------------------- | ---------------------------------------------------------------- |
| Polling | Batch claims, retry schedule and row progress | Database query/write load, backlog and worker overlap |
| CDC | Log position, connector recovery and event routing | Log retention, connector lag, schema mapping and broker delivery |

Choose from measured workload and recovery requirements, not a universal events-per-second threshold. Either approach can meet a low-latency target if configured and operated for it. For Debezium's outbox router, map the actual table/field names to its expected ID, aggregate type/key and payload fields; Prisma model names alone do not configure those mappings.
Keep polling updates and CDC event-table conventions compatible with the chosen connector rather than enabling both publishers by accident.

### 4. Put deduplication at the effect's transaction boundary

For a **database-local** projection, record the consumer/event identity and change the projection in one transaction. A unique `(consumer, event_id)` constraint arbitrates concurrent deliveries:

```sql
BEGIN;
INSERT INTO processed_events (consumer, event_id)
VALUES ($1, $2)
ON CONFLICT (consumer, event_id) DO NOTHING
RETURNING event_id;
-- Application branch: if no row returned, commit and skip the update.
-- Otherwise apply the projection using this same transaction/connection.
UPDATE appointment_counts SET total = total + 1 WHERE tenant_id = $3;
COMMIT;
```

The projection row must exist and the handler must verify its expected update result; otherwise a marker could commit without the intended effect. If processing fails, roll back the marker too. Retain dedup records for the possible replay/redelivery horizon and scope the consumer identity so independent consumers do not suppress each other.

For an **external email or payment**, a database or Redis marker is not atomic with the provider's action:

```text
read "not sent" → provider sends → process crashes → marker never written
retry reads "not sent" → provider sends again
```

Writing the marker first reverses the failure into lost work. Use a stable provider-supported idempotency key with a documented retention/response contract, or reconcile an uncertain outcome from provider records before retrying. If the provider offers neither, choose and expose the duplicate/loss policy; do not label a cache lookup followed by `sendEmail` as exactly-once processing.
A transactional send intent makes the work recoverable but does not remove that provider boundary.

### 5. Preserve ordering and bounded recovery

Sorting pending rows by creation time does not establish end-to-end order: timestamps can tie, workers can race and a retry can arrive after a newer event. When a consumer requires per-aggregate order, include a transactionally assigned aggregate version, serialize/partition publication for that aggregate, and define how consumers detect duplicates, gaps and old versions. Several independent aggregates can still progress concurrently.

Monitor oldest pending age, backlog, retries, quarantined events and consumer lag. Alert on stalled partitions, not just total counts. Apply bounded retries with backoff and control batch/concurrency sizes so an outage does not overwhelm the database when the broker recovers.

Published-row cleanup must respect audit and replay requirements. CDC also needs compatible database-log retention and connector offsets; removing rows is not the same as confirming all downstream consumers have completed. A tenant field helps route work, but every consumer still validates its tenant/resource authorization contract.

## Best Practices

Exercise failures at each boundary in the crash table, including broker acceptance followed by a failed progress update. Retry the same event concurrently and verify the local dedup constraint. Separately test an uncertain external effect, a stalled relay, replay after retention and per-aggregate gaps.
These checks establish the specific delivery contract more clearly than a blanket “exactly once” label.

## Summary

The outbox makes business data and publication intent atomic in one database. Relaying, delivery and consumer effects have their own recovery boundaries. Stable IDs, effect-aware deduplication, ownership, ordering and retention make the intent useful after a failure.

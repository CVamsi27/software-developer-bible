# Circuit Breaker

## Definition

A **circuit breaker** applies an admission policy to calls to a dependency. It tracks configured outcomes, rejects new calls when the failure policy is met, and later admits a limited recovery probe. It does not cancel calls already in flight or determine whether an uncertain write committed.

> **Textbook Definition:** A circuit breaker tracks failures of a protected operation and temporarily rejects calls when a policy threshold is met. Controlled probes test recovery; timeouts and bounded concurrency remain separate resilience controls.

## First Principles

Every slow dependency call occupies resources while the caller waits. Retrying adds work to the same constrained dependency. When observed outcomes indicate sustained failure, rejecting new calls can preserve caller capacity and let the dependency recover. Existing calls still need their own deadlines and resource limits.

A timeout reveals an observation failure, not whether a remote write committed. The breaker controls admission; it does not decide that payment failed, undo a write or make a retry safe.

## Follow one dependency through failure and recovery

```text
CLOSED: admit and record outcomes
   | configured failure policy met
OPEN: reject new protected calls
   | cooldown elapsed, one probe admitted
HALF-OPEN: reject other calls while probe runs
   | success -> CLOSED; failure -> OPEN with new cooldown
```

Closed does not mean electrically healthy: it means the admission policy currently allows traffic. Cooldown expiry does not prove recovery either; a bounded probe supplies new evidence. Opening cannot retract calls already in flight.

## A complete local state-machine example

This JavaScript example uses consecutive counted failures and one recovery probe. It is deliberately process-local, has no retry/fallback implementation and depends on the operation settling. `countsFailure` decides which failures describe the dependency; an authorization or validation rejection normally should not open its circuit.

```javascript
class CircuitBreaker {
  constructor({ threshold = 3, cooldownMs = 1000, clock = () => performance.now(),
                countsFailure = () => true } = {}) {
    if (!Number.isInteger(threshold) || threshold < 1 ||
        !Number.isFinite(cooldownMs) || cooldownMs < 0) throw new Error('invalid policy');
    Object.assign(this, { threshold, cooldownMs, clock, countsFailure });
    this.state = 'closed'; this.failures = 0; this.retryAt = 0; this.epoch = 0;
  }
  open() {
    this.state = 'open'; this.retryAt = this.clock() + this.cooldownMs;
    this.epoch++;
  }
  async execute(operation) {
    if (this.state === 'open') {
      if (this.clock() < this.retryAt) throw new Error('circuit open');
      this.state = 'half-open'; this.epoch++;
    } else if (this.state === 'half-open') throw new Error('probe already running');
    const epoch = this.epoch;
    const probe = this.state === 'half-open';
    try {
      const result = await operation();
      if (epoch === this.epoch) {
        this.failures = 0;
        if (probe) { this.state = 'closed'; this.epoch++; }
      }
      return result;
    } catch (error) {
      if (epoch === this.epoch) {
        if (this.countsFailure(error)) {
          this.failures++;
          if (probe || this.failures >= this.threshold) this.open();
        } else if (probe) {
          this.state = 'closed'; this.failures = 0; this.epoch++;
        }
      }
      throw error;
    }
  }
}
module.exports = { CircuitBreaker };
```

After three consecutive counted failures, a fourth call rejects without invoking its operation. At cooldown expiry, the first caller becomes the only probe; simultaneous callers reject. A late success from an old closed-state call cannot close a newly opened circuit: its captured epoch no longer matches.

The non-counted probe error closes this example because the classifier says it supplies no dependency-failure evidence. Choose that recovery policy deliberately; a production implementation may keep the probe state or require more successes instead. The classifier itself must be reliable and nonthrowing. Failures and successes here are counted by completion order; they are not a rolling-window error percentage.

## Define measurement and isolation scope

Rolling-window policies need minimum call volume, window duration, slow-call criteria and recovery thresholds. A few requests cannot support a meaningful percentage estimate. Libraries may add administrative states such as disabled, forced-open or metrics-only; check the selected implementation's semantics rather than assuming every breaker has only the three teaching states. Use a supported library when its validated concurrency and accounting behavior fits the runtime; avoid presenting a teaching class as a full production client.

One breaker per request never accumulates useful history. One global breaker can make an unrelated endpoint or tenant failure reject everyone. Choose dependency/operation keys with bounded cardinality. Process-local instances recover independently after restart; many replicas can each launch a probe, so fleet-wide probe load still needs a budget.

## Compose deadlines, retries and fallback deliberately

| Control | What it bounds | What it does not guarantee |
| ------------------------ | ---------------------------------------- | --------------------------------------------------- |
| Operation deadline/abort | Caller wait and cooperative cancellation | Remote rollback or immediate resource release |
| Bulkhead | Protected in-flight resources | Dependency recovery or transaction atomicity |
| Retry budget | Additional attempts under one deadline | Duplicate-safe external effects |
| Breaker | New admission from observed outcomes | Cancellation of old calls or accurate write outcome |

Putting the breaker around each retry counts individual attempts; putting it around the entire retry sequence counts one logical result and may hide multiplied load. Decide intentionally and bound attempts, delay and total deadline. Classify typed status/error data, never substring-match an error message for a digit “4”. Jitter/backoff reduces synchronized retries, not duplicate effects.

Fallback is optional. Rejecting a mutation can be the correct safe behavior. Cached recommendations may be useful if tenant, user, age and schema remain valid. Returning a fake guest user for a failed authenticated lookup misrepresents identity. Switching payment providers after an unknown charge outcome can charge twice; reconcile the original operation first.

A `Promise.race` timeout does not cancel its losing operation. Pass a cancellation signal supported by the actual client and retain permits until the work has stopped or settled. Do not recursively call the same failing dependency through fallback.

## Observe and test the control loop

Measure admitted outcomes, rejected calls, state transitions, probe duration and dependency latency separately. Breaker rejection is not another downstream failure. Preserve actual transition timestamps and bounded-cardinality labels. An open optional dependency does not necessarily make the process unready; readiness removal can concentrate load onto other replicas.

Test threshold boundaries, cooldown equality, concurrent probes, probe failure, ignored errors, old completions and process restart. Configure policy from measured traffic/capacity and acceptable degradation rather than a universal failure count. Network chaos tests additionally verify the client deadline and actual resource lifetime.

## Summary

A breaker rejects new calls according to observed outcomes and admits controlled recovery probes. Keep it separate from deadlines, resource limits and write reconciliation. Bound concurrent probes, classify failures explicitly, and ensure old completions cannot undo a newer state transition.

# Bulkhead Pattern

## Definition

The **Bulkhead Pattern** is a resilience design pattern that isolates failures within a system by partitioning resources into separate pools (bulkheads). Named after the watertight compartments on ships that prevent flooding from sinking the entire vessel, the pattern ensures that a failure in one part of the system does not cascade to other parts. In microservices, bulkheads can be implemented at various levels: thread pools, connection pools, semaphores, queues, and even physical infrastructure.

> **Textbook Definition:** A bulkhead partitions constrained resources among workloads to limit the spread of exhaustion or failure. Its isolation is bounded by the partitioned resources; shared downstream dependencies can still propagate failure.

## First Principles

A report query and login may share connections, memory, CPU or downstream capacity. If reporting consumes a shared limit, login waits even when its own code is healthy. Reserving separate budgets limits that coupling only for the resources actually partitioned.

Admission and lifetime must match. A permit released when middleware calls `next()` protects no subsequent handler work. A caller timeout also cannot justify releasing a permit while its underlying query still runs.

## Separate expensive work from critical work

```text
report requests -> report admission budget -> shared or separate database
login requests  -> login admission budget  -> shared or separate database
```

Separate client pools reserve connections; they do not reserve the server's CPU, locks or disk. A report can still lock a login table. Separate worker processes isolate process memory/event-loop work but may still share database and host limits. Choose the failure/resource boundary before choosing a semaphore, pool or deployment.

In Node.js, an asynchronous task limiter limits active promises/operations; it does not create OS threads. CPU-heavy work still blocks the shared event loop unless moved to bounded worker threads/processes or another service.

## A complete fail-fast admission example

This JavaScript limiter has no queue. Saturation rejects immediately, which is useful when waiting would exceed the caller's deadline. The admitted task owns its permit until it actually settles, including rejection. The supplied signal must be honored by the operation itself; this limiter does not fake cancellation.

```javascript
class Bulkhead {
  constructor(limit) {
    if (!Number.isInteger(limit) || limit < 1) throw new Error('invalid limit');
    this.limit = limit; this.active = 0;
  }
  async execute(task, signal) {
    if (signal?.aborted) throw signal.reason ?? new Error('aborted');
    if (this.active >= this.limit) throw new Error('bulkhead full');
    this.active++;
    try { return await task(signal); }
    finally { this.active--; }
  }
}
module.exports = { Bulkhead };
```

With limit two, two unresolved report tasks occupy the report budget. A third rejects without running. A separate login limiter can admit a login task. When a report resolves or throws, its own permit returns. If a report ignores abort, it remains active until settlement; early release would let real concurrency exceed the advertised limit.

Use the task's actual promise, not a wrapper that resolves immediately after starting background work. For an HTTP handler, decide whether the protected resource lasts through database settlement, response completion or stream closure. Detached work needs its own durable queue and budget, not a request permit that disappears at response time.

## Queues trade rejection for bounded waiting

A small queue can absorb a burst when service time and deadlines permit. A zero-length queue is valid; “always queue” is not a resilience rule. A bounded queued implementation additionally needs:

- Maximum waiting count/bytes and a maximum queue wait within the total deadline.
- Removal of cancelled/expired waiters without running their tasks later.
- Atomic permit handoff that cannot over-admit or leak capacity on errors.
- Shutdown behavior that settles queued promises and awaits/cancels active work.
- An explicit fairness policy, including priority starvation where relevant.

Queue wait and active service time are different metrics. Use arrival rate, measured service-time distributions and headroom to size capacity; Little's law relates average population to arrival rate times average time only under its applicable stable-system assumptions. A long queue can consume the whole request deadline before any useful work starts.

## Budget the whole fleet and trusted workload identity

Per-process limit ten across twenty replicas can admit two hundred calls. Sum client pools, background consumers, retries and recovery jobs against the downstream limit, including rollout overlap. Autoscaling the caller can overload a fixed database even when each replica obeys its own bulkhead.

A per-tenant map needs authoritative tenant identity, bounded registry growth and safe eviction only when a pool has no active/waiting work. Arbitrary client strings create unlimited pools and bypass the intended global budget. Per-tenant limits need a global cap/fairness policy; they do not guarantee a minimum service level on their own.

A rate limit controls arrival rate over time; a bulkhead controls concurrent resource occupancy. Ten calls per second can still occupy many permits when each takes thirty seconds. Use both when both constraints matter.

## Combine protection without inventing transaction guarantees

A bulkhead can wrap a breaker and then the operation. The breaker may reject immediately, returning the permit. Recheck admission when queued work actually starts; a breaker checked before a long wait may have opened meanwhile. Retries must share a deliberate total attempt/resource budget, and local saturation should not be counted as evidence that the dependency failed.

Do not start payment, invoice creation and unrelated work in `Promise.all` and describe it as an atomic order. Those independent effects need workflow/transaction decisions. Compensation and reconciliation need their own bounded capacity so failure recovery cannot exhaust the serving path or be starved forever.

## Observe the resource boundary

Track active count, queue depth/age, rejection/cancellation, actual settlement time and downstream utilization. Logs should distinguish local saturation from remote failure. Test that a stuck report cannot consume the reserved login budget, while separately testing the shared database/host failure that the limiter does not isolate.

## Summary

A bulkhead reserves bounded resource capacity for workloads. Hold permits for real work lifetime, choose queueing from deadline and burst needs, and account for fleet-wide and shared downstream limits. Partitioning connections or promises does not guarantee CPU, tenant fairness or business atomicity.

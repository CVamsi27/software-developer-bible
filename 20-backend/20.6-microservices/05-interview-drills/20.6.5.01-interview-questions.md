## Deep-Dive Answers by Level

### Beginner Questions

#### Q1: What is microservices architecture?

**Answer:**
Microservices architecture is an architectural style that structures an application as a collection of loosely coupled, independently deployable services. Each service is self-contained, implements a specific business capability, and communicates with other services through well-defined APIs.

#### Q2: How do microservices communicate?

**Answer:**
Microservices communicate through two primary patterns:

1. **Synchronous Communication** (HTTP/REST, gRPC)

   - Request/response model
   - Direct service-to-service calls
   - Examples: REST API calls, gRPC streams

2. **Asynchronous Communication** (Message Queues, Events)

   - Event-driven architecture
   - Decoupled services
   - Examples: Kafka, RabbitMQ, AWS SQS

```typescript
// Synchronous Communication (REST)
class UserServiceClient {
  async getUser(userId: string): Promise<User> {
    const response = await fetch(`http://user-service/users/${userId}`);
    return response.json();
  }
}

// Asynchronous Communication (Event-driven)
class OrderService {
  async createOrder(order: Order): Promise<void> {
    // Save order
    await this.orderRepository.save(order);

    // Publish event (async, non-blocking)
    await this.eventBus.publish('order.created', {
      orderId: order.id,
      userId: order.userId,
      items: order.items,
    });
  }
}

```

#### Q3: What is service discovery?

**Answer:**
Service discovery is a mechanism that allows services to find and communicate with each other dynamically. Instead of hardcoding network locations, services register with a discovery server and look up other services through it.


The choice that matters is *who holds the registry*: client-side discovery (the consumer queries the registry and load-balances itself — smart clients, fewer hops, but every language needs the logic) versus server-side (a load balancer/ingress resolves — one place to optimize, at the cost of an extra hop and a component to scale). In Kubernetes the registry dissolves into the platform — DNS plus kube-proxy *is* service discovery — which is why hand-rolled registries (Eureka, Consul) are now mostly for VM fleets or multi-cluster. The follow-up trap: health-based deregistration — a registry handing out dead instances is worse than no registry.
```typescript
// Client-side discovery
class ServiceDiscoveryClient {
  constructor(private registry: ServiceRegistry) {}

  async getService(serviceName: string): Promise<ServiceInstance> {
    const instances = await this.registry.getInstances(serviceName);

    // Load balancing (round-robin, random, weighted)
    return this.selectInstance(instances);
  }

  private selectInstance(instances: ServiceInstance[]): ServiceInstance {
    // Round-robin selection
    return instances[Math.floor(Math.random() * instances.length)];
  }
}

```

#### Q4: What is an API Gateway?

**Answer:**
An API Gateway is a server that acts as a single entry point for all client requests. It handles cross-cutting concerns like routing, authentication, rate limiting, and request transformation.


The gateway is a policy boundary, not just a router — that is the senior framing. Cross-cutting concerns (authentication, rate limiting, TLS termination, response shaping) live there once instead of in every service, but the design carries two risks to name: it can become a single point of failure and a change bottleneck (the god-gateway anti-pattern), and business logic that creeps in violates the pattern's whole point. Backpressure and timeouts belong here too — the gateway is where a slow downstream gets converted into a fast 503 instead of a thread-pool collapse. BFF-per-frontend is the standard refinement when one gateway shape no longer fits web and mobile.
```typescript
// API Gateway pattern
const gateway = express();

// Authentication middleware
gateway.use('/api', authenticate);

// Rate limiting
gateway.use('/api', rateLimit({ windowMs: 15 * 60 * 1000, max: 100 }));

// Route to services
gateway.use('/api/users', createProxyMiddleware({ target: 'http://user-service:3001' }));
gateway.use('/api/products', createProxyMiddleware({ target: 'http://product-service:3002' }));
gateway.use('/api/orders', createProxyMiddleware({ target: 'http://order-service:3003' }));

```

**Answer:**

| Aspect | Synchronous | Asynchronous |
| ---------- | ----------------- | ---------------- |
| Coupling | Tight | Loose |
| Timeout | Immediate | Deferred |
| Throughput | Lower | Higher |
| Complexity | Simpler | More complex |
| Use Case | Real-time queries | Event processing |

```typescript
const user = await httpClient.get('/users/123');

// Asynchronous: Fire and forget, process later
await messageQueue.publish('user-events', { type: 'USER_CREATED', data: user });

```

### Intermediate Questions

#### Q6: What is the Saga pattern?

**Answer:**
The Saga pattern manages distributed transactions across multiple services. Instead of a single ACID transaction, sagas use a sequence of local transactions with compensating transactions for rollback.


The insight the code shows: a saga replaces a distributed transaction with a *sequence of local transactions plus compensating actions* — each step commits locally, and a failure runs the compensations in reverse (cancel payment, release inventory, void order). Two orchestration styles exist and interviewers make you compare them: choreography (each service reacts to events — simple to start, the flow becomes invisible at ten services) versus orchestration (a central coordinator drives steps — visible and testable, but a component to keep stateless and scaled). The hard parts worth naming: compensations must be idempotent and retry-safe themselves, and sagas give you *eventual* consistency — reads mid-saga see interim states, so the UI needs to be designed for it.
```typescript
class OrderSaga {
  async execute(order: Order): Promise<void> {
    try {
      // Step 1: Create order
      await this.orderService.create(order);

      // Step 2: Reserve inventory
      await this.inventoryService.reserve(order.items);

      // Step 3: Process payment
      await this.paymentService.charge(order.userId, order.total);

      // Step 4: Confirm order
      await this.orderService.confirm(order.id);

    } catch (error) {
      // Compensate: Undo previous steps
      await this.compensate(order);
    }
  }

  private async compensate(order: Order): Promise<void> {
    await this.paymentService.refund(order.userId, order.total);
    await this.inventoryService.release(order.items);
    await this.orderService.cancel(order.id);
  }
}

```

#### Q7: What is the Circuit Breaker pattern?

**Answer:**
Circuit Breaker prevents cascade failures by stopping requests to failing services. It has three states: CLOSED (normal), OPEN (failing), and HALF-OPEN (testing recovery).


Three states, and the code shows the transitions: CLOSED counts failures over a window (not lifetime — one failure a day for a year should not trip anything), OPEN fails fast *without touching* the dependency — the part people miss is that this protects both sides: the caller gets an instant error, and the dying service gets time to recover instead of being finished off by retries. HALF-OPEN lets a few probes through; success closes, failure re-opens. The follow-up: what the caller receives from an OPEN breaker — a fallback, a cached value, or a 503 — because fail-fast without a fallback just moves the outage upstream. Retry-plus-breaker must be composed carefully: retries inside a broken circuit amplify the exact load the breaker exists to shed.
```typescript
class CircuitBreaker {
  private state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED';
  private failureCount = 0;
  private lastFailureTime = 0;

  async call<T>(operation: () => Promise<T>): Promise<T> {
    if (this.state === 'OPEN') {
      if (Date.now() - this.lastFailureTime > 30000) {
        this.state = 'HALF_OPEN';
      } else {
        throw new Error('Circuit breaker is OPEN');
      }
    }

    try {
      const result = await operation();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }

  private onSuccess(): void {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }

  private onFailure(): void {
    this.failureCount++;
    this.lastFailureTime = Date.now();
    if (this.failureCount >= 5) {
      this.state = 'OPEN';
    }
  }
}

```

#### Q8: What is event sourcing?

**Answer:**
Event Sourcing stores all changes as a sequence of events. Instead of storing current state, you store events that led to that state. Current state is derived by replaying events.


The contract event sourcing makes: state is *derived*, never stored — the append-only event log is the source of truth, and current state is a replay. What that buys: complete audit history, temporal queries (state as of any past moment), and natural integration (other services consume the same events). What it costs, and the interviewer wants these: replays must be bounded (snapshots every N events), read models must be built and rebuilt (that is CQRS territory), event schemas must evolve without mutating history (versioned events and upconverters), and every consumer is forced into eventual consistency. The judgment call to state out loud: worth it for domains where history *is* the product (ledger, orders, medical records), ceremony for a CRUD blog.
```typescript
// Event Store
class EventStore {
  private events: Event[] = [];

  append(event: Event): void {
    this.events.push(event);
  }

  getEvents(aggregateId: string): Event[] {
    return this.events.filter(e => e.aggregateId === aggregateId);
  }

  // Rebuild state from events
  getState(aggregateId: string): any {
    return this.getEvents(aggregateId).reduce(
      (state, event) => this.applyEvent(state, event),
      {}
    );
  }
}

// Example events
const events = [
  { type: 'OrderCreated', data: { id: '123', userId: 'user1' } },
  { type: 'ItemAdded', data: { productId: 'prod1', quantity: 2 } },
  { type: 'PaymentReceived', data: { amount: 100 } },
  { type: 'OrderShipped', data: { trackingNumber: '123456' } },
];

```

#### Q9: What is CQRS?

**Answer:**
Command Query Responsibility Segregation (CQRS) separates read and write operations into different models. Write model handles commands, read model handles queries, optimized independently.


The separation pays when reads and writes have different shapes or scales — and the code shows the tell: the command side runs business rules through a domain model, while the query side may bypass it entirely and read an optimized projection. CQRS does not require event sourcing (plain two-model CQRS is common) and does not require separate databases — the honest version starts with one database, two models. The costs to name: two codebases to evolve, projections that lag (eventual consistency leaks into UX — show your own writes via read-your-writes routing), and a consistency model the team must actually understand. Adopt on divergence of load or shape; skip on principle.
```typescript
// Command Side (Write)
class OrderCommandHandler {
  async createOrder(command: CreateOrderCommand): Promise<void> {
    // Validate, apply business rules
    const order = Order.create(command);
    await this.orderRepository.save(order);

    // Publish event for read model
    await this.eventBus.publish('OrderCreated', order);
  }
}

// Query Side (Read)
class OrderQueryHandler {
  async getOrder(orderId: string): Promise<OrderView> {
    // Optimized read from projection
    return this.orderViewRepository.findById(orderId);
  }
}

```

#### Q10: How do you handle distributed transactions?

**Answer:**
Distributed transactions are handled through:

1. **Saga Pattern** - Compensating transactions

2. **Eventual Consistency** - Accept temporary inconsistency

3. **Two-Phase Commit (2PC)** - Distributed locks (rarely used)

4. **Outbox Pattern** - Reliable event publishing


The framing that opens the answer: distributed ACID transactions do not exist at acceptable cost (2PC blocks on coordinator failure and murders availability), so the question becomes *which consistency you can trade*. The toolkit in order of preference: design for idempotent eventual consistency (events plus local transactions — most systems need nothing more), the outbox pattern (the sketch) when a write and its event must be atomic — insert the event in the same local transaction and publish asynchronously, closing the dual-write gap — and sagas with compensations when a multi-service invariant must hold. The follow-up: why not just publish after commit? Because a crash between commit and publish loses the event forever — the outbox exists precisely for that window.
```typescript
// Outbox Pattern
class OrderService {
  async createOrder(order: Order): Promise<void> {
    await this.database.transaction(async (trx) => {
      // Save order
      await trx('orders').insert(order);

      // Save event to outbox (same transaction)
      await trx('outbox').insert({
        aggregateId: order.id,
        eventType: 'OrderCreated',
        payload: JSON.stringify(order),
      });
    });

    // Separate process publishes events from outbox
  }
}

```

#### Q12: How do you handle service failures in microservices?

**Answer:**
Multi-layered approach:


The layers exist because they answer *different* failure classes: timeouts and retries with jittered backoff for transient blips, circuit breakers to stop hammering a dying dependency (and to fail fast instead of piling up threads), bulkheads to contain exhaustion (each dependency gets its own connection pool, so one slow service cannot starve the others), and graceful degradation — a fallback, cached answer, or feature-flagged-off path — for the failures that outlast all of that. The ordering detail interviewers probe: retry budgets and breaker composition, because naive retries on a broken dependency are a self-inflicted DDoS. And the meta-answer: design each consumer for the failure of every dependency it has — *assume* the outage, don't hope.
```typescript
// 1. Circuit Breaker
const circuitBreaker = new CircuitBreaker({
  failureThreshold: 5,
  timeout: 30000,
});

// 2. Retry with Backoff
const retry = new Retry({
  maxRetries: 3,
  backoff: 'exponential',
});

// 3. Fallback
async function getUserWithFallback(userId: string): Promise<User> {
  try {
    return await circuitBreaker.execute(() =>
      retry.execute(() => userService.getUser(userId))
    );
  } catch (error) {
    // Fallback to cached data or default
    return cache.get(`user:${userId}`) || defaultUser;
  }
}

// 4. Bulkheading
const userPool = new Pool({ max: 10 });
const orderPool = new Pool({ max: 20 });
// Isolate failures to specific services

```

#### Q13: How do you implement distributed tracing?

**Answer:**
Using OpenTelemetry for distributed tracing:


The setup is the easy half; the interview's real content is *propagation and sampling*: context must flow across every hop (W3C `traceparent` headers, injected into queue messages too — an untraced consumer is a broken trace), spans should wrap real I/O (HTTP calls, DB queries) which is why auto-instrumentation beats manual spans for coverage, and 100% sampling is unaffordable at scale — head-based sampling drops most traces, tail-based sampling keeps the interesting ones (errors, high latency) at a fraction of the cost. The payoff to articulate: a trace turns "p99 spiked after deploy" from a dashboard mystery into a readable waterfall with the guilty span highlighted — which is also the debugging story to tell.
```typescript
import { NodeTracerProvider } from '@opentelemetry/sdk-trace-node';
import { JaegerExporter } from '@opentelemetry/exporter-jaeger';

// Initialize tracer
const provider = new NodeTracerProvider();
const exporter = new JaegerExporter();
provider.addSpanProcessor(new BatchSpanProcessor(exporter));
provider.register();

// Instrument HTTP calls
import { HttpInstrumentation } from '@opentelemetry/instrumentation-http';
new HttpInstrumentation().instrument();

// Custom spans
import { trace, SpanStatusCode } from '@opentelemetry/api';

const tracer = trace.getTracer('order-service');

async function processOrder(orderId: string): Promise<void> {
  const span = tracer.startSpan('processOrder');
  try {
    span.setAttribute('order.id', orderId);

    // Your business logic
    await validateOrder(orderId);
    await processPayment(orderId);

    span.setStatus({ code: SpanStatusCode.OK });
  } catch (error) {
    span.setStatus({ code: SpanStatusCode.ERROR, message: error.message });
    throw error;
  } finally {
    span.end();
  }
}

```

#### Q14: How do you ensure data consistency across services?

**Answer:**
Strategies for data consistency:


The answer graders look for: *pick the weakest consistency each invariant actually needs*, because the strong option (2PC across services) is the one you cannot afford. The ladder: same-transaction writes within one service (free), outbox-plus-events for cross-service propagation (eventual, ordered per key), sagas with compensations for multi-step invariants, and — the detail that separates answers — *read-your-writes* handling at the UX layer (route the user's own reads to the primary, everyone else's to replicas) so eventual consistency never surprises the user who caused the write. Reconciliation jobs are the honest backstop: if invariants can drift, a periodic checker converts drift from a silent data bug into an alert.
```typescript
// 1. Eventual Consistency with Events
class OrderService {
  async createOrder(order: Order): Promise<void> {
    // Save locally
    await this.orderRepository.save(order);

    // Publish event (async)
    await this.eventBus.publish('OrderCreated', {
      orderId: order.id,
      userId: order.userId,
    });
  }
}

// 2. Saga Pattern for Strong Consistency
class OrderSaga {
  async execute(order: Order): Promise<void> {
    await this.orderService.create(order);
    await this.inventoryService.reserve(order.items);
    await this.paymentService.charge(order.userId, order.total);
  }

  async compensate(order: Order): Promise<void> {
    await this.paymentService.refund(order.userId, order.total);
    await this.inventoryService.release(order.items);
    await this.orderService.cancel(order.id);
  }
}

// 3. Outbox Pattern for Reliable Events
class OrderService {
  async createOrder(order: Order): Promise<void> {
    await this.database.transaction(async (trx) => {
      await trx('orders').insert(order);
      await trx('outbox').insert({
        aggregateId: order.id,
        eventType: 'OrderCreated',
        payload: JSON.stringify(order),
      });
    });
  }
}

```

#### Q15: How do you handle database per service pattern?

**Answer:**


The pattern's real rule is organizational, not technical: no shared database means each service's schema is *private* — others integrate through its API or events, never by reading its tables. That boundary is what buys independent deploys and independent scaling; the costs are cross-service queries (solved by API composition or a CQRS read model, not by re-sharing a database) and cross-service transactions (sagas, not joins). The follow-up that separates experience: the *shared-integration-database* anti-pattern — one team adds a column, three other services break silently — and the pragmatic exception teams accept: reporting/analytics reads from replicas or CDC-fed warehouses, never from the operational store directly.
```typescript
// Each service has its own database
// No direct database access across services

// User Service
class UserService {
  constructor(private userDatabase: Database) {}

  async getUser(userId: string): Promise<User> {
    return this.userDatabase.query('SELECT * FROM users WHERE id = ?', [userId]);
  }
}

// Order Service (cannot access User database)
class OrderService {
  constructor(
    private orderDatabase: Database,
    private userClient: UserServiceClient // HTTP/gRPC client
  ) {}

  async createOrder(order: Order): Promise<void> {
    // Must call User Service to get user data
    const user = await this.userClient.getUser(order.userId);

    // Save order with user reference (not user data)
    await this.orderDatabase.query(
      'INSERT INTO orders (id, user_id, total) VALUES (?, ?, ?)',
      [order.id, user.id, order.total]
    );
  }
}

// API Composition for queries spanning services
class OrderQueryService {
  async getOrderDetails(orderId: string): Promise<any> {
    const order = await this.orderClient.getOrder(orderId);
    const user = await this.userClient.getUser(order.userId);
    const products = await this.productClient.getProducts(order.itemIds);

    return { ...order, user, products };
  }
}

```

### FAANG-Style Questions

#### Q16: Design a URL shortener like bit.ly

**Answer:**


The design runs on three decisions: the key (a base62 encoding of an auto-increment ID or a hash — the counter scales via segmented ranges per node; hashing spreads better but collides), the read path (cache-first — a hot shortener is 99.9% reads, so Redis in front of a key-value store, with 301s cached at the CDN edge), and analytics as an async side-effect (a click event to a queue, never inline in the redirect — redirect latency is the product). The follow-ups that grade it: custom aliases (uniqueness check plus reserved-word list), expiry and abuse (malicious URLs need scanning and revocation — a moderation queue), and the sharding question — ID ranges survive node addition poorly, which is the moment consistent hashing or a lookup service enters.
```text
┌─────────────────────────────────────────────────────────────────┐
│ URL SHORTENER DESIGN                                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ Client ──> API Gateway ──> URL Service ──> Database             │
│ │ │                                                             │
│ │ ├──> Cache (Redis)                                            │
│ │ │                                                             │
│ └──> Analytics Service                                          │
│                                                                 │
│ Key Components:                                                 │
│ • URL Encoding: Base62 (a-z, A-Z, 0-9)                          │
│ • Storage: Database with short_url, long_url, created_at        │
│ • Cache: Redis for hot URLs                                     │
│ • Analytics: Track clicks, referrers                            │
└─────────────────────────────────────────────────────────────────┘

```

```typescript
// URL Service
class UrlService {
  async createShortUrl(longUrl: string): Promise<string> {
    // Generate unique short code
    const shortCode = this.generateShortCode();

    // Store in database
    await this.database.query(
      'INSERT INTO urls (short_code, long_url, created_at) VALUES (?, ?, ?)',
      [shortCode, longUrl, new Date()]
    );

    // Cache for fast lookup
```

#### Q19: Design a rate limiting system

**Answer:**


The token bucket is the right core algorithm — it allows bursts while enforcing a long-run rate, unlike a fixed window (which doubles the limit at boundaries) — but the interview question is *where the buckets live*: a single-process Map collapses behind replicas, so counters move to Redis (INCR with EXPIRE, or a Lua script for atomicity), and the decision that matters is per-identity keying: API key or user ID first, IP as fallback (NAT collapses thousands of users onto one address). The distributed edge cases graders raise: clock skew argues for local tokens with periodic sync in extreme-scale designs, and *fail-open vs fail-closed* when Redis is down — for most systems, failing open (limiting temporarily off) beats failing the product. The 429 carries `Retry-After`.
```typescript
// Rate Limiter using Token Bucket algorithm
class RateLimiter {
  private buckets: Map<string, { tokens: number; lastRefill: number }> = new Map();

  constructor(
    private maxTokens: number,
    private refillRate: number, // tokens per second
  ) {}

  async isAllowed(key: string): Promise<boolean> {
    const now = Date.now();
    let bucket = this.buckets.get(key);

    if (!bucket) {
      bucket = { tokens: this.maxTokens, lastRefill: now };
      this.buckets.set(key, bucket);
    }

    // Refill tokens
    const timePassed = (now - bucket.lastRefill) / 1000;
    bucket.tokens = Math.min(this.maxTokens, bucket.tokens + timePassed * this.refillRate);
    bucket.lastRefill = now;

    // Check if request is allowed
    if (bucket.tokens >= 1) {
      bucket.tokens--;
      return true;
    }

    return false;
  }
}

// Redis-based distributed rate limiter
class DistributedRateLimiter {
  async isAllowed(key: string, limit: number, windowMs: number): Promise<boolean> {
    const now = Date.now();
    const windowStart = now - windowMs;

    const pipeline = this.redis.pipeline();
    pipeline.zremrangebyscore(key, 0, windowStart); // Remove old entries
    pipeline.zadd(key, now, `${now}-${Math.random()}`); // Add current request
    pipeline.zcard(key); // Count requests in window
    pipeline.expire(key, windowMs / 1000); // Set TTL

    const results = await pipeline.exec();
    const requestCount = results[2][1] as number;

    return requestCount <= limit;
  }
}
```

#### Q20: Design a distributed caching system

**Answer:**


Consistent hashing is the right mechanism and the answer should say *why*: naive `hash % n` remaps nearly every key when a node joins (a full cache cold-start), while the hash ring moves only ~1/n of keys. The refinements interviewers probe: virtual nodes (100–200 points per node, so uneven machines share the ring fairly), replication factor for node-failure survival, and hot-key mitigation (a single celebrity key cannot be split by hashing — it needs local in-memory caching or key salting). The operational layer completes it: eviction policy per node (LRU with a memory ceiling — an unbounded cache is a slow-motion OOM), and what happens on a miss storm when a node dies — request coalescing, not a synchronized stampede onto the database.
```typescript
// Distributed Cache with Consistent Hashing
class DistributedCache {
  private nodes: CacheNode[] = [];
  private ring: ConsistentHashRing;

  constructor(nodeAddresses: string[]) {
    this.ring = new ConsistentHashRing();

    nodeAddresses.forEach(address => {
      const node = new CacheNode(address);
      this.nodes.push(node);
      this.ring.addNode(node);
    });
  }

  async get(key: string): Promise<any> {
    const node = this.ring.getNode(key);
    return node.get(key);
  }

  async set(key: string, value: any, ttl?: number): Promise<void> {
    const node = this.ring.getNode(key);
    await node.set(key, value, ttl);

    // Replicate to nearby nodes
    const replicaNodes = this.ring.getReplicaNodes(key, 2);
    await Promise.all(replicaNodes.map(n => n.set(key, value, ttl)));
  }

  async delete(key: string): Promise<void> {
    const node = this.ring.getNode(key);
    await node.delete(key);

    const replicaNodes = this.ring.getReplicaNodes(key, 2);
    await Promise.all(replicaNodes.map(n => n.delete(key)));
  }
}
```

#### Q21: How do you handle database migrations in microservices?

**Answer:**


The microservices twist that changes everything: with N services deployed independently, migrations must be *backward compatible* — version N and N+1 run simultaneously during a rolling deploy, so the expand/contract discipline is the actual answer: add nullable columns and dual-write in release 1, backfill, switch reads in release 2, drop the old shape in release 3 — each step deploys cleanly alone. Per-service ownership means no cross-service schema edits ever (another service's database is its private state — Q15), and migrations run as a pre-deploy gate with the app version pinned to the schema version. The interview trap: "just run migrations in CI before deploy" breaks the moment two services deploy concurrently — sequencing and compatibility rules, not tooling, are the hard part.
```typescript
// Database migration strategy
class MigrationService {
  async migrate(serviceName: string): Promise<void> {
    const database = this.databaseFactory.create(serviceName);

    // Run migrations in order
    const migrations = await this.getMigrations(serviceName);

    for (const migration of migrations) {
      console.log(`Running migration: ${migration.name}`);

      await database.transaction(async (trx) => {
        await trx.raw(migration.up);
        await trx('migrations').insert({
          name: migration.name,
          executed_at: new Date(),
        });
      });
    }
  }

  async rollback(serviceName: string, steps: number = 1): Promise<void> {
    const database = this.databaseFactory.create(serviceName);

    const executed = await database.query(
      'SELECT * FROM migrations ORDER BY executed_at DESC LIMIT ?',
      [steps]
    );

    for (const migration of executed.reverse()) {
      const migrationFile = await this.getMigration(migration.name);

      await database.transaction(async (trx) => {
        await trx.raw(migrationFile.down);
        await trx('migrations').where('name', migration.name).delete();
      });
    }
  }
}
```

#### Q26: How do you handle circuit breaker in async systems?

**Answer:**


The async twist changes what "failure" means: there is no caller waiting to receive a fast 503, so the breaker protects *the pipeline's backpressure* instead — when the downstream consumer is failing, the publisher either buffers (bounded — an unbounded buffer is tomorrow's OOM), applies backpressure (pause consumption — Kafka's credit-based flow control does this naturally via lag), or diverts to a dead-letter path. The state machine is the same CLOSED/OPEN/HALF-OPEN, but the metrics come from consumer-side signals: processing failure rate and consumer lag, not HTTP error codes. The trap: publishing into an OPEN circuit with retry storms is exactly the cascade the breaker exists to prevent — the rejection path needs its own alerting, because a silently dropped message is a data-loss incident discovered weeks later.
```typescript
// Async Circuit Breaker with Message Queue
class AsyncCircuitBreaker {
  private state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED';
  private failureCount = 0;
  private lastFailureTime = 0;

  async publishWithCircuitBreaker(
    topic: string,
    message: any,
    fallback?: (msg: any) => Promise<any>
  ): Promise<void> {
    if (this.state === 'OPEN') {
      if (Date.now() - this.lastFailureTime > 30000) {
        this.state = 'HALF_OPEN';
      } else {
        // Circuit is open, use fallback
        if (fallback) {
          await fallback(message);
        } else {
          throw new Error('Circuit breaker is OPEN');
        }
        return;
      }
    }

    try {
      await this.messageQueue.publish(topic, message);
      this.onSuccess();
    } catch (error) {
      this.onFailure();

      if (fallback) {
        await fallback(message);
      } else {
        // Send to dead letter queue
        await this.messageQueue.publish('dlq', {
          originalTopic: topic,
          message,
          error: error.message,
        });
      }
    }
  }

  private onSuccess(): void {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }

  private onFailure(): void {
    this.failureCount++;
    this.lastFailureTime = Date.now();
    if (this.failureCount >= 5) {
      this.state = 'OPEN';
    }
  }
}

```

#### Q27: How do you handle idempotency in distributed systems?

**Answer:**


The key's lifecycle is the answer: client-generated (a UUID per user action, sent on retries — server-generated keys like `Date.now()` in the sketch are useless, because a retry re-generates a new key), stored with the response (the processing result is cached against the key for a TTL long enough to cover realistic retries), and checked atomically (SETNX in Redis, or a unique constraint in SQL — the unique-constraint violation *is* the duplicate detection). The subtlety graders probe: what the second request receives — the cached original response (correct), a 409 (annoying but safe), or re-execution (the bug — double charges). Idempotency keys are the sibling of Q14's eventual consistency: whenever at-least-once delivery exists, consumers *must* be idempotent, and the key is how.

```typescript
// Idempotency Key pattern
class IdempotentService {

    const result = await this.paymentGateway.charge(payment);

    // Store result with TTL
    await this.idempotencyStore.set(idempotencyKey, result, 86400);

  }
}
```

#### Q28: How do you handle distributed locking?

**Answer:**


The Redis `SET key value NX EX ttl` is the mechanism, but two properties make or break it: the value must be a *unique owner token* (so release checks ownership before deleting — a Lua script for atomicity — otherwise a slow holder's expired lock gets deleted by its replacement's successor), and the TTL is a *lease the holder must not outlive* — the failure mode to name out loud: GC pause or network partition past the TTL means two holders, so correctness must not *depend* on the lock (fencing tokens — a monotonically increasing number the storage checks — convert a broken lock into a rejected write). Redlock's controversy is the bonus point: for most business purposes, single-instance Redis with fencing is enough; for correctness-critical mutual exclusion, a consensus-backed lock or redesign to avoid the lock entirely (idempotency, optimistic concurrency) is the senior answer.
```typescript
// Redis-based distributed lock
class DistributedLock {
  private redis: RedisClient;

  async acquire(lockName: string, ttl: number = 10000): Promise<string | null> {
    const lockValue = `${Date.now()}-${Math.random()}`;

    const acquired = await this.redis.set(
      `lock:${lockName}`,
      lockValue,
      'NX',
      'PX',
      ttl
    );

    return acquired ? lockValue : null;
  }

  async release(lockName: string, lockValue: string): Promise<boolean> {
    // Lua script for atomic release
    const script = `
      if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
      else
        return 0
      end
    `;

    const result = await this.redis.eval(
      script,
      1,
      `lock:${lockName}`,
      lockValue
    );

    return result === 1;
  }

  async withLock<T>(
    lockName: string,
    fn: () => Promise<T>,
    ttl: number = 10000
  ): Promise<T> {
    const lockValue = await this.acquire(lockName, ttl);

    if (!lockValue) {
      throw new Error(`Failed to acquire lock: ${lockName}`);
    }

    try {
      return await fn();
    } finally {
      await this.release(lockName, lockValue);
    }
  }
}

// Usage
const lock = new DistributedLock();

async function transferFunds(from: string, to: string, amount: number) {
  await lock.withLock(`transfer:${from}:${to}`, async () => {
    // Critical section - only one transfer at a time
    const balance = await accountService.getBalance(from);
    if (balance < amount) {
      throw new Error('Insufficient funds');
    }

    await accountService.debit(from, amount);
    await accountService.credit(to, amount);
  });
}
```

#### Q29: How do you handle service mesh?

**Answer:**


The VirtualService is one rule; the mesh is the *decision to move cross-cutting network policy out of application code*: mTLS between every pair of services (identity without app changes — the security bank's zero-trust per-hop answer), retries, timeouts, and circuit breaking enforced in the sidecar (uniformly, across languages), and traffic management (canary weights, mirroring) as config instead of code. The honest cost statement that grades the answer: sidecars add latency per hop, the control plane is a component to operate and upgrade, and a misconfigured mesh is a self-inflicted outage at the network layer — which is why adoption is incremental (start with mTLS and observability, defer advanced traffic policy) and why many teams now weigh eBPF-based alternatives (Cilium, Istio ambient) that drop the per-pod proxy.

#### Q30: How do you handle event-driven architecture at scale?

**Answer:**


At scale the architecture's problems stop being delivery and start being *coordination*: schema governance (a registry with compatibility rules — one producer's careless change breaks a thousand consumers overnight, the 20.9 bank's Q12), ordering versus throughput (per-key ordering is the ceiling — design keys so related events share one), and consumer backpressure as the universal constraint (lag is the SLI — the 20.9 bank's Q6 — and a slow consumer eventually forces either partitioning changes or capacity work). The design decisions graders probe: event retention as a replay budget (reprocess from seven days back, or rebuild from a snapshot store), exactly-once *where it matters* (transactional producers per-pipeline, not everywhere), and the operational maturity — DLQs monitored, consumer rebalances budgeted, and the org chart matching the topic ownership, because Conway's law applies to event schemas too.
```typescript
// Event-driven architecture with Kafka
class EventDrivenArchitecture {
  private kafka: Kafka;
  private producer: Producer;
  private consumers: Map<string, Consumer> = new Map();

  async initialize(): Promise<void> {
    this.kafka = new Kafka({
      clientId: 'order-service',
      brokers: ['kafka-1:9092', 'kafka-2:9092', 'kafka-3:9092'],
    });

    this.producer = this.kafka.producer({
      idempotent: true,
      transactionalId: 'order-service-producer',
    });

    await this.producer.connect();
  }

  async publishEvent<T>(topic: string, event: T): Promise<void> {
    await this.producer.send({
      topic,
      messages: [
        {
          key: (event as any).id,
          value: JSON.stringify(event),
          timestamp: Date.now().toString(),
        },
      ],
    });
  }

  async subscribe(
    topic: string,
    groupId: string,
    handler: (event: any) => Promise<void>
  ): Promise<void> {
    const consumer = this.kafka.consumer({ groupId });
    await consumer.connect();
    await consumer.subscribe({ topics: [topic] });

    await consumer.run({
      eachMessage: async ({ message }) => {
        const event = JSON.parse(message.value!.toString());
        await handler(event);
      },
    });

    this.consumers.set(`${topic}-${groupId}`, consumer);
  }
}

// Event Sourcing with CQRS
class EventSourcedOrderService {
  async createOrder(command: CreateOrderCommand): Promise<void> {
    // Create aggregate
    const order = OrderAggregate.create(command);

    // Save events
    await this.eventStore.saveEvents(order.id, order.getUncommittedEvents());

    // Update read model (async)

      orderId: order.id,
      ...command,
    });
  }

  async getOrder(orderId: string): Promise<OrderView> {
    // Read from projection (optimized for reads)
    return this.orderProjection.get(orderId);
  }
}
```

## Common Mistakes

1. **Distributed monolith** - Services too coupled

2. **Shared databases** - Violates service independence

3. **Synchronous everything** - Creates tight coupling

4. **Ignoring failure handling** - Cascade failures

5. **Missing monitoring** - Can't debug issues

6. **Over-engineering** - Unnecessary complexity

7. **Wrong service boundaries** - Chatty services

8. **Ignoring data consistency** - Data corruption

## Best Practices

1. **Design for failure** - Assume services will fail

2. **Embrace eventual consistency** - Don't fight it

3. **Use circuit breakers** - Prevent cascade failures

4. **Implement idempotency** - Handle retries safely

5. **Monitor everything** - Metrics, logs, traces

6. **Automate deployments** - CI/CD pipelines

7. **Use API contracts** - Clear service boundaries

8. **Document architecture** - Keep docs updated

## Performance Considerations

- **Async communication** - Don't block on service calls
- **Caching** - Cache frequently accessed data
- **Connection pooling** - Reuse connections
- **Load balancing** - Distribute traffic
- **Circuit breakers** - Prevent cascade failures
- **Bulkheading** - Isolate failures
- **Monitoring** - Track performance metrics

# gRPC

## TL;DR

A high-performance RPC framework using HTTP/2, protobuf, and bidirectional streaming for strongly-typed inter-service communication.

**Why it matters:** Tests contract-first design, streaming patterns, interceptor chains, and load balancing over long-lived HTTP/2 connections. Common in service-mesh and polyglot stacks.

## Definition

**gRPC** is a high-performance, language-agnostic RPC framework developed by Google. It uses Protocol Buffers (protobuf) for serialization and HTTP/2 for transport, enabling bidirectional streaming, flow control, and multiplexing. gRPC is widely adopted for microservice-to-microservice communication where performance matters.

## Why Do We Need It?

1. **Performance**: 5-10x faster than JSON/REST (binary protobuf serialization)
2. **HTTP/2**: Multiplexing, server push, bidirectional streaming, header compression
3. **Strong typing**: `.proto` files define service contracts in any language
4. **Code generation**: Client/server stubs auto-generated from `.proto` files
5. **Streaming**: Unary, server-streaming, client-streaming, bidirectional-streaming

## Code Examples

### Protobuf Definition

```protobuf
syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
  rpc ListUsers (ListUsersRequest) returns (stream User);
  rpc UpdateUser (stream UpdateUserRequest) returns (User);
  rpc Chat (stream ChatMessage) returns (stream ChatMessage);
}

message User {
  string id = 1;
  string name = 2;
  string email = 3;
}
```

### Node.js Server

```typescript
import * as grpc from '@grpc/grpc-js';
import { UserService } from './generated/user_grpc_pb';

const server = new grpc.Server();
server.addService(UserService, {
  getUser: (call, callback) => {
    const { id } = call.request;
    callback(null, { id, name: 'Alice', email: 'alice@example.com' });
  },
});
server.bindAsync('0.0.0.0:50051',
  grpc.ServerCredentials.createInsecure(), () => server.start());
```

## REST vs gRPC

| Feature | REST | gRPC |
|---------|:----:|:----:|
| Payload | JSON (human-readable) | Protobuf (binary) |
| Protocol | HTTP/1.1 | HTTP/2 |
| Streaming | ❌ | ✅ (bidirectional) |
| Code gen | Manual SDK | Auto-generated |
| Browser | Native | Requires gRPC-Web |

## Code Examples (continued)

### Server Streaming

```typescript
// Server streams multiple results
def server_streaming(self, request, context):
    for user in self.db.list_users(request.filter):
        yield user  # Each yield sends a message

// Client receives stream
const stream = client.listUsers({ filter: { active: true } });
stream.on('data', (user) => console.log(user));
stream.on('end', () => console.log('Stream complete'));
```

### Bidirectional Streaming

```typescript
// Both sides stream independently
async function chat(call) {
  call.on('data', async (message) => {
    const response = await processMessage(message);
    call.write(response);  // Send back immediately
  });
  call.on('end', () => call.end());
}
```

### Deadlines & Cancellation

```typescript
// Client sets deadline
const deadline = new Date();
deadline.setSeconds(deadline.getSeconds() + 5);

client.getUser({ id: '123' }, { deadline }, (err, response) => {
  if (err.code === grpc.status.DEADLINE_EXCEEDED) {
    console.log('Request timed out');
  }
});

// Server checks cancellation
call.on('cancelled', () => {
  console.log('Client cancelled');
  // Clean up resources
});
```

## Common Mistakes

| Mistake | Fix |
|---------|-----|
| Using gRPC for browser clients | Use gRPC-Web or REST gateway |
| No deadline set | Always set deadline (5-30s default) |
| Ignoring HTTP/2 connection reuse | gRPC uses long-lived connections; need proper LB |
| Large payloads over gRPC | Binary is fast but large = slow; paginate |
| No error handling in streaming | Handle `cancelled`, `error`, and `end` events |
| Protobuf schema evolution without care | Use field numbers, never reuse field numbers |

## Best Practices

1. **Use deadlines** — every RPC call should have a timeout
2. **Use interceptors** — for auth, logging, metrics (like middleware)
3. **Handle streaming errors** — `cancelled`, `error`, `end` events
4. **Use connection pooling** — HTTP/2 multiplexes, but pool for load balancing
5. **Version your proto files** — use package versions, never break backward compatibility
6. **Use gRPC-Web for browsers** — or proxy through Envoy/Connect
7. **Monitor with OpenTelemetry** — gRPC interceptors + OTel = full visibility

## Summary

- gRPC uses Protocol Buffers for efficient binary serialization and HTTP/2 for multiplexed streaming
- Four communication patterns: Unary, Server Streaming, Client Streaming, and Bidirectional Streaming
- Language-agnostic with auto-generated client/server stubs from .proto files
- Superior performance to REST/JSON for internal service-to-service communication
- Best suited for microservices, real-time streaming, and polyglot environments

## Cheat Sheet
```text
GRPC CHEAT SHEET
═══════════════════════════════════════════════════════════════

PROTOCOL:
• HTTP/2 + Protobuf (binary)
• 5-10x faster than JSON/REST
• Strongly typed via .proto files

4 PATTERNS:
• Unary: request → response (like REST)
• Server streaming: request → stream of responses
• Client streaming: stream of requests → response
• Bidi streaming: stream ↔ stream (chat)

KEY CONCEPTS:
• Deadlines: always set timeout (5-30s)
• Interceptors: auth, logging, metrics (like middleware)
• Status codes: OK, CANCELLED, DEADLINE_EXCEEDED, etc.
• Channels: persistent HTTP/2 connections

DEADLINE FLOW:
Client sets deadline → propagated to server
→ server checks deadline per hop
→ DEADLINE_EXCEEDED if exceeded
→ CANCELLED if client disconnects

LOAD BALANCING:
• Round-robin (not pick-first) for gRPC
• Client-side LB with name resolvers
• Or use service mesh (Istio/Linkerd)

BROWSER:
• gRPC-Web (via Envoy proxy)
• Or Connect protocol (buf.build)
• Not native browser support
```

# GraphQL Overview

## Definition

GraphQL is a **query language for APIs** and a **runtime for executing those queries** against your data. A client selects fields from the server's published schema; the server resolves those fields and builds a matching response.

> **Textbook Definition:** GraphQL is a typed query language and execution specification in which clients select fields from a schema-defined graph. The schema governs permitted operations; authorization, transport and storage behavior remain implementation concerns.

A graph here means related API objects, such as a user and that user's posts. It does not require a graph database. A **resolver** supplies a field's value; it can read a database, call another service or return an existing object property.

## First Principles

A profile screen needs a name and two post titles, while an administration screen needs different fields. An API must express which fields exist, accept a client's selection and determine which work produces it. Without a shared contract, a misspelled field can reach application code unnoticed. Without execution limits, a valid selection can still demand excessive work.

GraphQL addresses selection and structural validation with a typed schema. The implementation must still enforce access, business rules, pagination and cost limits. REST APIs can also offer field selection or combined view endpoints; choose from the workload and client needs rather than assuming one style always transfers less data.

## Why It Matters

GraphQL can serve several evolving interfaces through one shared contract. Its flexibility moves some work from endpoint design into schema governance and execution control. A senior answer should trace those responsibilities, explain failure behavior and compare alternatives.

## How a Selection Becomes a Result

```text
operation text + variables
    → parse into a syntax tree
    → validate against the schema
    → select the operation and coerce its variables
    → resolve selected fields and complete their values
    → response data, with execution errors when applicable
```

Parsing establishes that the text has valid syntax. Validation checks field names, argument types and selection rules against the schema. These are different steps: the server must parse before it can validate the resulting syntax tree.

At execution, a root field finds an object; nested fields then resolve from that object. The default field resolver can read matching object properties. A custom resolver is needed when a field requires a calculation, authorization decision or another data lookup. Fields not selected by the operation are not included in its data result, although a resolver may still over-fetch internally.

### Trace one complete query

The following Node.js ES module uses `graphql` 16.x. Save it as `overview.mjs`, install `graphql`, and run `node overview.mjs`. This in-memory public catalog is an execution example; it has no HTTP server, database or protected user data.

```javascript
import { buildSchema, graphql } from 'graphql';

const schema = buildSchema(`
  type Query { user(id: ID!): User }
  type User { id: ID!, name: String!, posts: [Post!]! }
  type Post { id: ID!, title: String! }
`);

const users = new Map([
  ['1', { id: '1', name: 'Ada', posts: [{ id: 'p1', title: 'Types' }] }],
]);
const rootValue = {
  user: ({ id }) => users.get(id) ?? null,
};

const result = await graphql({
  schema,
  source: `query Profile($id: ID!) {
    user(id: $id) { name posts { title } }
  }`,
  variableValues: { id: '1' },
  rootValue,
});
console.log(JSON.stringify(result));
// {"data":{"user":{"name":"Ada","posts":[{"title":"Types"}]}}}
```

`Query.user` receives the coerced ID and returns Ada's object. Its `name` property supplies the selected name; each post's `title` supplies one selected title. The stored IDs are absent from the result because this operation did not select them. No database calls are implied by the nested shape.

Change the variable to `'missing'`: the nullable `user` field returns `null`. Change the selected field from `name` to `nickname`: validation fails and the root resolver does not execute. If a selected non-null field instead fails during execution, the error can remove a larger part of the result; [schema design](20.7.1.02-schema-design.md) explains that propagation.

## Three Operation Kinds Have Different Execution Contracts

| Kind | Intended job | Execution boundary |
| ------------ | --------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Query | Read selected data | Sibling fields may resolve concurrently; this is not a database snapshot guarantee |
| Mutation | Perform a named change and select its result | Top-level mutation fields execute serially; their nested result fields do not create a shared transaction |
| Subscription | Produce repeated results from an event source | Requires a source stream, transport and lifetime policy; GraphQL does not supply a durable broker |

A mutation such as `createPost` should delegate validation, ownership and persistence to an application service. If a client loses the response after a successful commit, serial GraphQL execution does not prevent a repeated submission from creating another post. Define idempotency at the operation's storage boundary.

A subscription connects events to a selected response. Authentication at connection setup is only one point in its lifetime: permissions can change, consumers can fall behind and connections can disappear. The [subscription chapter](../../../60-realtime/60.1-websockets/03-frameworks-and-paradigms/60.1.3.02-graphql-subscriptions-live-queries.md) owns the complete transport and recovery treatment.

## The Schema Describes Possibilities, Not Storage

The **Schema Definition Language (SDL)** declares types and operations. Object fields describe selectable relationships. Scalars such as `String` terminate a selection; input objects describe arguments; enums restrict values to named choices. Interfaces and unions describe alternative object types. These concepts are developed in [schema design](20.7.1.02-schema-design.md).

**Introspection** exposes schema structure through GraphQL operations, supporting documentation, editors and generated clients. It does not expose database rows by itself, and disabling it does not authorize fields or make a known operation safe.

Schema-first teams author SDL and generate types from it. Code-first teams derive the schema from framework definitions. Both produce a schema that needs review, compatibility checks and runtime enforcement. Neither approach makes database values or caller input trustworthy merely because TypeScript compiled.

## Where Costs and Guarantees Actually Live

### Nested fields can multiply work

If one query loads 20 users and each `User.posts` resolver performs a separate lookup, the application makes one user query plus 20 post queries: the **N+1 problem**. A request-scoped DataLoader can batch compatible keys and reuse results, but joins or a planned aggregate query can also solve the workload. Batch results must match input-key order, and authorization scope must be preserved. See [resolvers](../02-execution/20.7.2.01-resolvers.md).

Batching is not a query budget. A shallow field requesting a million rows can be expensive; repeated aliases can multiply work without much depth. Bound list arguments, expensive fields and total operation cost, then apply timeouts and resource budgets at the actual dependencies.

### Response selection does not imply cheap retrieval

A client can ask for unnecessary fields. A resolver can fetch complete rows even for a small selection. Lists can still under-deliver what a screen needs because they are paginated. GraphQL gives a selection mechanism; it does not guarantee optimal database work, zero over-fetching or a complete view in one round trip.

### Caches have different owners

Read operations can use HTTP GET when the server and client support the GraphQL-over-HTTP conventions; mutations must not use GET. Suitable public GET responses can use HTTP caching. POST-only delivery is common, but is not required by the execution specification.

A normalized client cache reuses objects by identity. A server response cache reuses whole results. A resolver/data cache reuses underlying values. These are separate layers with separate keys, invalidation and access rules. Protected responses must not enter a shared public cache merely because the query text matches.

### Additive evolution still needs compatibility review

Adding an optional field often preserves existing operations; removing or renaming a used field breaks them. New enum values can surprise exhaustive client logic, and changing nullability affects failure behavior. Deprecation provides migration information, not proof that every consumer has moved. GraphQL can evolve without URL version numbers, but it does not eliminate versioning decisions.

## Real-World Decisions

| Situation | Decision to explain |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Several clients need different related views | GraphQL can make selection explicit; budget and authorize nested work |
| A small stable public API benefits from HTTP caching | Compare conventional resource endpoints with supported GraphQL GET/persisted-operation delivery |
| Teams own separate domains | Stitching or federation can compose schemas; ownership, query plans and cross-service failures still need governance |
| A dashboard needs fresh data | Compare polling, subscriptions and server-sent events against latency, scale and recovery requirements |
| Files need upload/download | Use a deliberate transport/storage contract, often signed upload URLs; a schema field alone does not stream bytes safely |

Apollo Server is one server implementation. Apollo Client, Relay and urql are client tools with different cache and workflow choices. A framework name does not change the core parse, validate and execute contract.

## Common Mistakes

- Promising that one endpoint means one database call or one transaction.
- Treating schema validation as business validation or resource authorization.
- Putting a DataLoader in global shared state where one caller can reuse another caller's protected result.
- Reading only the HTTP status: execution can return both `data` and `errors` in a successful HTTP response.
- Treating circular schema relationships as automatic infinite execution. Operations contain finite selections, and validation rejects cyclic fragment spreads; valid selections can still be too costly.
- Installing server, client, pagination and federation machinery before establishing the actual contract and workload.

## Best Practices

Start from a concrete consumer view and define the smallest useful domain contract. Bound collections, choose nullability deliberately and keep application authorization close to the actual data operation. Test selected-field results, rejected operations, partial errors and repeated writes. Observe resolver and dependency costs rather than counting HTTP requests alone.

## Summary

GraphQL turns a schema-validated field selection into a result through resolvers. It can make related views easier to express, while leaving authorization, storage invariants, delivery, caching and cost control to the implementation. Explain those boundaries before choosing a framework or promising fewer requests.

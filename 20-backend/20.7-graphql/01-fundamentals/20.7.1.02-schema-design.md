# Schema Design

An order screen needs an `author` object, but the database stores only `author_id`. Exposing the storage column would make clients depend on today's table layout instead of the relationship they need.

## Definition

GraphQL schema design defines the **types, operations and relationships** that form an API contract. A well-designed schema documents available selections and supports validation and generated types. Runtime values, database integrity and access control still need separate checks.

> **Textbook Definition:** A GraphQL schema declares the types, fields, arguments and root operations available to clients. It defines validation and execution structure, while runtime data integrity and authorization require implementation checks.

The **Schema Definition Language (SDL)** is the declarative notation used below. `User.name: String!` means that clients can select a user's name and that execution must produce a non-null string for it. It says nothing about which database column, service or calculation supplies the value.

## First Principles

Consumers depend on field names, valid inputs and failure behavior even when storage changes. Model the domain view they need; a resolver can translate `author_id` into `author: User!`. Types also distinguish an absent object from a failed required field, an output from supplied input and one concrete result from several possible shapes.

## 1. How the Type System Fits Together

```text
Query/Mutation root → object fields → more objects or scalar/enum leaves
arguments → input objects/scalars/enums → application validation and operation
interface/union → runtime concrete object → that object's selected fields
```

An **object type** groups selectable output fields. An **input object** groups values callers supply; GraphQL keeps these roles separate. Lists and `!` wrap another type.
An enum accepts named values, while a scalar defines how one leaf value crosses the API boundary.

#### Read one complete domain schema

This schema describes public author names, posts, a bounded post connection and a create-post result. Every referenced type is defined. It builds and validates with GraphQL.js 17.0.2, the current stable release checked on 11 October 2026 ([release history](https://github.com/graphql/graphql-js/releases)).
Useful execution still requires resolvers, a `DateTime` scalar implementation and application services. Apollo Server 5.5.1 declares GraphQL.js `^16.11.0` as its peer dependency ([package manifest](https://github.com/apollographql/apollo-server/blob/main/packages/server/package.json)); match the server's supported range instead of assuming every GraphQL.js release is accepted by every integration.

```graphql
scalar DateTime

enum PostStatus { DRAFT PUBLISHED ARCHIVED }
enum UserErrorCode { INVALID_INPUT FORBIDDEN CONFLICT }

interface Node { id: ID! }

type User implements Node {
  id: ID!
  name: String!
  posts(first: Int! = 20, after: String): PostConnection!
}

type Post implements Node {
  id: ID!
  title: String!
  author: User!
  status: PostStatus!
  createdAt: DateTime!
}

union SearchResult = User | Post

input CreatePostInput {
  title: String!
}

input UserLookup @oneOf {
  id: ID
  email: String
}

type UserError {
  field: String
  message: String!
  code: UserErrorCode!
}

type CreatePostPayload {
  post: Post
  errors: [UserError!]!
}

type PostEdge {
  node: Post!
  cursor: String!
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

type PostConnection {
  edges: [PostEdge!]!
  pageInfo: PageInfo!
}

type Query {
  node(id: ID!): Node
  user(id: ID!): User
  userBy(lookup: UserLookup!): User
  post(id: ID!): Post
  search(text: String!, first: Int! = 20): [SearchResult!]!
}

type Mutation {
  createPost(input: CreatePostInput!): CreatePostPayload!
}
```

Start at `Query.user(id: ...)`, which may find no user. If it returns a user, `User.posts` exposes related posts through a connection. Each edge pairs one post with its position cursor; `pageInfo` describes navigation.
The non-null default rejects an explicit null and supplies 20 when omitted, but it does not enforce a positive maximum range. The service must still bound `first`.

`createPost` takes a purpose-specific input and returns a payload. Its service derives the author from the authenticated caller, validates the title and commits the write. The client cannot assign an author or privileged role through this input.
The service should return either a post with an empty error list or a documented domain failure; SDL alone does not enforce that relationship.

`UserLookup` is a **OneOf input object**: `userBy(lookup: { id: "u1" })` supplies one non-null alternative. Its fields are nullable in SDL and cannot have defaults so the schema can distinguish the selected alternative. An empty object, explicit null or two supplied alternatives fails input coercion; the resolver still authorizes the requested user.

## 2. Nullability Controls How Failures Spread

| Type | Permitted result values |
| ---------- | -------------------------------------------------- |
| `Post` | A post or `null` |
| `Post!` | A post; returning `null` causes an execution error |
| `[Post]` | A null list or a list containing nullable posts |
| `[Post!]` | A null list or a list whose items must be posts |
| `[Post]!` | A non-null list whose items may be null |
| `[Post!]!` | A non-null list with non-null posts; `[]` is valid |

Suppose `user` is nullable, `User.name` is non-null and the name resolver fails. Execution cannot complete the promised name, so it replaces the containing user with `null`. The response includes an error with the failing field's path.
An unrelated sibling root field can still succeed.

If `Query.user` were also non-null, the same failure could propagate to the root and make `data` null. This is **non-null error propagation**: the failure travels up until a nullable boundary can contain it. Choose boundaries that match the application's useful partial states; neither “everything nullable” nor “everything required” is a universal policy.

For an unknown user, returning `null` can be an ordinary absence with no error. A permission or dependency failure may instead produce a documented error policy. Clients must not infer the cause from `null` alone.

## 3. Scalars Need a Runtime Contract

Built-in `Int` is a signed 32-bit integer, not an arbitrary JavaScript number or database bigint. `ID` represents an identifier and normally serializes as a string; it does not promise a UUID, secrecy or permission. `String!` allows an empty string, so it does not validate a useful title.

A custom `DateTime` name has no intrinsic format. Define a wire representation, such as an ISO-8601 UTC string, and implement input-variable parsing, literal parsing and output serialization. The built-in `@specifiedBy(url: ...)` directive can link to the scalar's format specification; it documents the contract but does not implement validation.
Generated TypeScript can describe that wire value as `string`; mapping it to `Date` does not create a JavaScript `Date` during a JSON response decode.

A custom Email or URL scalar can validate a documented format, but email ownership, uniqueness and allowed URL destinations are separate application rules. For money, choose currency and integer minor units or an explicit decimal-string contract; GraphQL `Float` cannot make binary floating-point arithmetic exact, and `Int` can be too small for some amounts.

## 4. Interfaces Share Fields; Unions Share Alternatives

`Node` promises an `id` for every implementing object. A client can select that field without knowing whether the result is a user or a post, then use a type-specific fragment for the other fields:

```graphql
query Lookup($id: ID!) {
  node(id: $id) {
    id
    __typename
    ... on User { name }
    ... on Post { title }
  }
}
```

`SearchResult` is a union of `User` and `Post`. It does not itself declare an `id` field, even though both members happen to have one. Select member fields through fragments and use `__typename` to distinguish the returned concrete type.
The server must identify that type through supported runtime resolution, such as a valid `__typename` or resolver implementation.

An interface is useful when consumers depend on common fields. A union is useful when results are alternative shapes without that shared contract. Cycles such as `User.posts → Post.author → User` are legitimate schema relationships.
A finite operation chooses how far to follow them; cost controls govern how much work is allowed, and fragment cycles are invalid.

## 5. Pagination Needs an Ordering Contract

A cursor represents a position in a defined ordering. For posts ordered by `(createdAt DESC, id DESC)`, include the unique ID as a tiebreaker. Encode and validate the position together with its tenant/filter scope as needed; base64 is encoding, not tamper protection or authorization.

For a forward page of size two, read up to three matching rows after the cursor. Return the first two edges and set `hasNextPage` from the extra row. `endCursor` belongs to the last returned edge; on an empty page, both edge cursors are null. Determine `hasPreviousPage` from the connection's supported traversal and actual data, rather than assuming that any supplied cursor proves a preceding visible row exists.

The Relay Connection specification standardizes edge and page-info structure; it does not promise a snapshot across requests or require `totalCount`. Counting an entire filtered population can be expensive. Concurrent inserts, deletes and changes to ordering fields still affect traversal, so define consistency expectations and whether immutable ordering keys or snapshot selection are needed.

Offset pagination can be adequate for a small stable list. Connection/cursor pagination is useful when ordering and concurrent changes warrant it; it is not mandatory for every array. A deliberately small bounded collection can remain a list.

## 6. Input Changes and Schema Evolution Affect Clients

For `UpdatePostInput { title: String }`, an omitted title and an explicit `null` are different inputs. Decide whether omission means “leave unchanged” and whether null means “clear” or “reject.” Defaults also change what the service observes. Do not conflate the two with a truthiness check.

| Change | Compatibility question |
| ----------------------------------------------- | --------------------------------------------------------------------------------------- |
| Add an optional output field | Existing selections normally continue; can resolving it introduce new work or exposure? |
| Add a required input/argument without a default | Existing callers do not supply it; this is generally breaking |
| Add an enum value | Can existing clients handle an unknown case? |
| Make an output field nullable | Existing generated clients may rely on its non-null promise |
| Remove/rename a field | Which active operations still select it? |
| Deprecate a field | Is there a replacement and evidence that consumers have migrated? |

Use the built-in `@deprecated(reason: ...)` directive for migration guidance. It does not block use or establish a removal date. Test schema changes against known operations and consumer expectations; syntactic “additive” changes can still affect behavior.

## 7. Directives and Composition Need Implementations

A directive annotates a schema or operation. Built-in operation directives such as `@include` and `@skip` have specified execution behavior. Declaring `directive @auth ...` merely defines allowed notation; it does not install a guard.
Likewise, `@cacheControl` requires the relevant server integration and a safe cache policy. These are not universal GraphQL built-ins.

Schema-first authoring makes SDL a reviewed artifact. Code-first authoring generates it from framework definitions. Either can support generated types and compatibility checks; review the resulting schema rather than equating one workflow with correctness.

**Schema stitching** combines executable schemas and delegates fields to the appropriate source. **Federation** composes subgraph contracts and entity ownership into a graph served by a router. For example, an accounts subgraph can own a user's name while a posts subgraph owns that user's posts. The composed selection crosses service boundaries, so ownership keys, forwarded identity, query-plan cost and partial failures need explicit contracts. Composition is not a shared database transaction, and neither approach should expose arbitrary backing endpoints as trusted remote schemas.

## Real-World Decisions

A commerce API can expose a `Money` value with currency and amount rather than a bare floating-point price. A content system can use a union for paragraph/image/video blocks, with fragments for each shape. A dashboard can model widget variants the same way.
Keep each type complete in the real schema and avoid adding hundreds of fields merely to mirror every storage column.

Keep fields consumers need together, but separate operations with different privileges. An administrator action can have its own input and service policy instead of letting public registration accept `role: ADMIN`. An opaque identifier can support stable API identity across storage changes; it does not prevent unauthorized access to another user's object.

## Summary

A schema is a public contract for fields, inputs, relationships and failure behavior. Its structure supports validation and tooling; resolvers and services supply runtime values, authority and invariants. Deliberate nullability, pagination, scalar contracts and evolution make the graph understandable and safe to change.

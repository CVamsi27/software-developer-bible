# Queries & Mutations

## Definition

**Queries** retrieve selected data; **mutations** express state-changing operations and select their results; **subscriptions** produce results from an event source over time. They share field-selection syntax but have different execution and lifecycle contracts.

> **Textbook Definition:** A GraphQL operation is a query, mutation or subscription selected from a validated document. Queries select read results; top-level mutation fields execute serially; a subscription selects one event-producing root field and yields results as source events arrive. These contracts do not define transport durability or database transactions.

Query resolvers should be side-effect free. The type system does not physically prevent a resolver from writing; preserving that contract is the implementation's responsibility.

## First Principles

A read can select several independent values, while a write can change what a later operation observes. An event stream adds connection lifetime, delivery and recovery questions. The runtime therefore needs an explicit operation kind and execution contract. Callers also need to supply values without constructing new query syntax, distinguish repeated fields and describe which response values they use.

Variables, aliases and fragments solve those document-construction problems. Application services still own permission, business validation, persistence and retry behavior.

## Why It Matters

A valid mutation document can produce a partial result after an earlier write has committed. A valid input can violate a domain rule. A response with HTTP success can contain execution errors. These distinctions determine whether a client should display data, correct input or reconcile an uncertain write.

## How an Operation Is Selected and Executed

An operation has a kind, an optional name, variable definitions and a selection set. An anonymous query is valid when it is the document's only operation; names help tracing and tooling. When a document contains multiple operations, the request must identify which one to execute with `operationName`. It does not execute them all.

```text
parse document → validate selections and variable use
               → choose operation → coerce supplied variables
               → resolve root fields → resolve each returned object's fields
```

A parent's value must exist before its nested fields can resolve. Sibling query fields may resolve concurrently; the whole nesting tree is not started at once. Top-level mutation fields are completed serially, including their selected result fields, before the next root mutation field begins.

## Build a Selection with Variables, Aliases and Fragments

The next operation uses the complete SDL in [schema design](20.7.1.02-schema-design.md). Send the document and variables separately:

```graphql
query CompareAuthors($left: ID!, $right: ID!, $showPosts: Boolean!) {
  left: user(id: $left) {
    ...AuthorIdentity
    posts(first: 2) @include(if: $showPosts) {
      edges { node { id title } cursor }
      pageInfo { hasNextPage endCursor }
    }
  }
  right: user(id: $right) { ...AuthorIdentity }
}

fragment AuthorIdentity on User {
  id
  name
}
```

```json
{
  "operationName": "CompareAuthors",
  "variables": { "left": "1", "right": "2", "showPosts": false }
}
```

This JSON shows the metadata accompanying the operation; an HTTP JSON request also carries its `query` text. The aliases `left` and `right` become response keys and allow different arguments for the same field. A named fragment reuses a selection; its definition must be included in the sent document or inserted by the client's document composition tool.

`@include` conditionally selects the `posts` field. With `false`, the field is absent rather than present with a null value. `@skip` performs the complementary conditional omission. These directives apply to fields and fragment selections, not to the operation header. Both conditions must allow a selection for it to execute.

Variables keep string content separate from GraphQL syntax. They do not make SQL assembled inside a resolver parameterized, authorize an ID or prevent a valid but expensive operation. A non-null variable must be supplied appropriately; scalar coercion and field argument compatibility are checked before resolvers use it.

### Omission, null and defaults are different

For an optional update field, omission can mean “keep the current value,” while explicit null can mean “clear” or “reject,” according to the domain contract. A default applies when a value is not supplied, not as a replacement for explicit null. Checking `if (input.title)` loses distinctions between omitted, null and empty-string values; inspect property presence and validate the chosen meaning.

## Trace Serial Execution Without Assuming Rollback

This complete Node.js ES module was verified with GraphQL.js 17.0.2 and Node.js 22.23.3. It operates on a toy process-local counter to make execution visible. It is not a transactional database or authenticated endpoint.

```javascript
import { buildSchema, graphql, GraphQLError } from 'graphql';

const schema = buildSchema(`
  type Query { count: Int! }
  type Mutation { add(amount: Int!): Int }
`);
let count = 0;
const order = [];
const rootValue = {
  count: () => count,
  add: async ({ amount }) => {
    order.push(amount);
    await Promise.resolve();
    if (amount < 0) {
      throw new GraphQLError('Amount must be nonnegative', {
        extensions: { code: 'INVALID_INPUT' },
      });
    }
    if (count + amount > 2147483647) {
      throw new GraphQLError('Counter limit reached');
    }
    count += amount;
    return count;
  },
};

const result = await graphql({
  schema,
  rootValue,
  source: `mutation Adjust {
    first: add(amount: 2)
    rejected: add(amount: -1)
    last: add(amount: 3)
  }`,
});
console.log(JSON.stringify({ data: result.data, order, count }));
// {"data":{"first":2,"rejected":null,"last":5},"order":[2,-1,3],"count":5}
console.log(result.errors[0].path); // ['rejected']
```

The first field completes with two. The second raises an execution error; because `add` is nullable, its response key becomes null and the third root field can execute. The first write is not undone. The final state is five, and `errors` identifies the failed field.

If `add` were non-null, that error would propagate to the root, null the data result and prevent completing later root fields in this execution. The earlier side effect would still not acquire a rollback guarantee. Two separate requests can also overlap; serial root fields govern one operation, not all server traffic.

For a real transfer or order, expose one domain mutation whose service commits its related changes together under appropriate concurrency controls. Do not assume several GraphQL root mutations share a transaction, or that a transaction retry should repeat an external payment side effect.

## A Subscription Defines Event Execution, Not Delivery Guarantees

A subscription selects one root field that produces a stream of source events. This schema declares the event and its result type:

```graphql
type Message { id: ID!, text: String! }
type Subscription { messageAdded(roomId: ID!): Message! }
```

A client can request that event stream with:

```graphql
subscription WatchRoom($roomId: ID!) {
  messageAdded(roomId: $roomId) { id text }
}
```

The server authorizes the requested room, subscribes to an event source, and executes the selected fields for each emitted event. The subscription operation defines this mapping; a WebSocket or Server-Sent Events integration owns the connection and wire framing. GraphQL alone does not guarantee durable delivery, replay after reconnect, event ordering, bounded queues or prompt cancellation.

Authenticate when the connection is established, authorize the subscription's resource, and account for permission changes while it remains open. Bound event rate and per-client queued work. If reconnect must resume without gaps, define a cursor or sequence against durable event history and make duplicate delivery safe. A shared in-memory emitter on one server process does not provide cross-instance fanout or replay.

## Separate Request Errors, Execution Errors and Domain Outcomes

| Outcome | What it means | Useful client behavior |
| ---------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Parse/validation/variable-coercion error | The operation cannot execute as requested | Correct the document or inputs; do not infer a committed write from this result |
| Execution error | A selected field failed; data may be partial or null | Inspect error paths and nullability before rendering or retrying |
| Domain error in a payload | The operation executed and returned a modeled outcome, such as a conflict | Show the specific recoverable outcome and retain valid user input |
| Transport loss/timeout | The caller may not know whether the operation committed | Reconcile through an idempotency/status contract before resubmitting |

A payload such as `CreatePostPayload { post, errors }` is ordinary schema data, distinct from the top-level GraphQL `errors` array. Its exact outcome contract belongs to the API. Extension codes on execution errors are implementation conventions, not a universal enum defined by GraphQL.

Mask unexpected internal exceptions and record a correlation identifier through controlled telemetry. Log operation identity and permitted diagnostic fields; query variables can contain passwords, tokens or personal information. Avoid blindly logging the entire document and payload.

An HTTP client must examine both the transport result and GraphQL response body. HTTP status policy depends on the transport/media-type contract; do not promise that every GraphQL error is always HTTP200 or that a 200 response proves all fields succeeded.

## Make Repeated Writes and Optimistic Views Deliberate

An idempotency key identifies an intended operation. The service needs an atomic, caller-scoped reservation, matching request semantics and a retained result/status. A repeated key with a different request must not silently perform another effect. Expiry and uncertain external outcomes need explicit handling. GraphQL's mutation syntax does not supply these storage rules.

An **optimistic update** displays a predicted client result before confirmation. The predicted shape must match the actual selected fields and normalized entity identity. On success, use the authoritative result; on failure, remove or correct the prediction. Pagination/list membership may need an explicit cache update or refetch. The complete client implementation is owned by [Apollo Client](../03-clients-and-production/20.7.3.01-apollo-client.md), rather than repeated here with incompatible payload types.

For registration, ownership and privilege come from a deliberate authentication policy, not unrestricted client input. For chat, use stable message identity and a delivery/status contract. For draft publishing, commit the publish transition and durable notification intent together when needed; notification delivery can still be retried separately.

## Persisted and Incremental Operations Have Separate Contracts

A persisted operation associates a document with an identifier. **Automatic persisted queries (APQ)** commonly let a client send a hash and fall back to registering the full document on a miss. This can reduce repeated transfer, but is not an allowlist if arbitrary documents can register. A trusted-operation allowlist needs controlled registration and rejection of unknown documents. Both still need variable limits and authorization.

`@defer` and `@stream` describe incremental delivery in implementations that support a compatible specification and transport. Do not assume every GraphQL server/client version enables them. Clients must handle initial results, patches, errors and completion correctly; incremental delivery can improve perceived latency without reducing the total data work. See [Apollo Server](../02-execution/20.7.2.02-apollo-server.md) for its current compatibility boundary and [production performance](../03-clients-and-production/20.7.3.02-performance-security.md) for budgets.

## Real-World Decisions

Use variables for dynamic values, names for operation identity and fragments for a shared field contract. Bound filtering, sorting and pagination through accepted inputs and stable ordering. A client that needs atomic business behavior should call one mutation designed for that invariant; combining several root fields is a convenience of document construction, not a substitute for a service transaction. Choose a subscription only when clients need a live event stream, and specify authorization, rate, ordering and recovery separately.

Choose retries from observed outcomes. Correct a known validation failure, reconcile an uncertain commit and retry only within a bounded operation policy. Optimistic rendering helps responsiveness when a prediction is useful and reversible; it is less suitable where presenting an unconfirmed irreversible outcome would mislead the user.

## Common Mistakes

- Using a query resolver for business writes because it technically can call the database.
- Treating all nested mutation fields as serial, or serial root fields as one atomic commit.
- Treating a subscription declaration as a transport, event log or replay guarantee.
- Putting `@skip` on an operation header or sending a fragment spread without its definition.
- Giving optimistic data a payload shape that differs from the schema's actual return type.
- Checking uniqueness before a write without a database constraint that handles a concurrent request.
- Assuming APQ is an allowlist or typed variables prevent every downstream injection.
- Displaying partial data without examining error paths, or blindly retrying a timed-out write.

## Best Practices

Validate operations against the deployed schema and generate types from the actual selections. Test variable coercion, domain outcomes, partial errors and uncertain delivery. Enforce authorization and storage invariants inside the operation service; make client rendering and retry policies follow its result contract.

## Summary

Queries select read results; mutations serialize top-level changes within one operation. Variables, aliases, fragments and conditional selections shape that operation, while services own authority, atomicity and repeated-write behavior. Distinguish rejected requests, field errors, modeled failures and unknown commits before deciding what a client should do next.

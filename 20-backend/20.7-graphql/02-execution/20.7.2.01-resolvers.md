# Resolvers

A feed asks for 20 posts and each author's name. One query can load the posts, then 20 separate relationship lookups can load the authors. The response is correct, but its storage cost grows with the number of posts. The resolver for `Post.author` is where that relationship becomes visible—and where the repeated work can be batched.

## Definition

**Resolvers** are functions that populate fields in a GraphQL schema. They connect the API's declared shape to databases, services and computed values. For example, `Post.author` turns the author ID on a post into the user object requested by a client.

> **Textbook Definition:** A field resolver computes a field value from its parent value, coerced arguments, execution context and field information. The execution engine then completes that value according to the field's declared output type.

## First Principles

The executor follows the selected field tree: a parent resolver returns a value, and that value becomes the parent input for its selected children. Independent query fields may run concurrently, so their order is not a contract. Top-level mutation fields run serially, but that sequence is not a database transaction and does not serialize nested fields.
When many children need related rows, collect their keys, fetch them together and return one result for each key in the original order. Keep the authorization scope attached to the batch.

## 1. How a field receives its inputs

A resolver has the shape `(parent, args, context, info)`:

| Input | Meaning | Example for `Post.author` |
| --------- | ------------------------------------------- | --------------------------------------------- |
| `parent` | The object returned for the enclosing field | `{ id: "p1", authorId: "u1" }` |
| `args` | Arguments after GraphQL input coercion | An empty object if the field has no arguments |
| `context` | Request identity and dependencies | Verified tenant and request-scoped loaders |
| `info` | Schema and operation details for this field | Response path and selected field nodes |

The default resolver reads the property with the field's name, or calls a function-valued property. Thus `User.name` needs no custom resolver when the parent already contains `name`. A custom resolver is useful for a relationship, computed value or policy check; it is not mandatory boilerplate for every scalar.

```text
Query.posts → [Post p1, Post p2]
                  │        │
             authorId   authorId
                  └── author loader ── one batch
                            │
                      User.name values
```

## 2. Example: batch authors without crossing tenants

Save this complete learning example as `resolvers.mjs`. It was verified with GraphQL.js 17.0.2, DataLoader 2.2.3 and Node.js 22.23.3. The in-memory arrays stand in for storage; the principal is already verified by the transport layer.
No client-supplied tenant header becomes an authenticated identity here.

```javascript
import { buildSchema, graphql } from 'graphql';
import DataLoader from 'dataloader';

const schema = buildSchema(`
  type User { id: ID!, name: String! }
  type Post { id: ID!, title: String!, author: User }
  type Query { posts: [Post!]! }
`);
const users = [
  { id: 'u2', tenantId: 't1', name: 'Bo' },
  { id: 'u1', tenantId: 't1', name: 'Ada' },
  { id: 'u1', tenantId: 't2', name: 'Other tenant' },
];
const posts = [
  { id: 'p1', tenantId: 't1', title: 'Batching', authorId: 'u1' },
  { id: 'p2', tenantId: 't1', title: 'Ordering', authorId: 'u2' },
  { id: 'p3', tenantId: 't1', title: 'Missing author', authorId: 'gone' },
];
function makeContext(principal) {
  const context = { principal, batchCalls: 0, authors: null };
  context.authors = new DataLoader(async ids => {
    context.batchCalls++;
    const rows = users.filter(u =>
      u.tenantId === principal.tenantId && ids.includes(u.id));
    const byId = new Map(rows.map(u => [u.id, u]));
    return ids.map(id => byId.get(id) ?? null);
  });
  return context;
}
const context = makeContext({ tenantId: 't1', subject: 'viewer1' });
const rootValue = {
  posts(_args, ctx) {
    return posts.filter(p => p.tenantId === ctx.principal.tenantId)
      .map(p => ({ ...p, author: () => ctx.authors.load(p.authorId) }));
  },
};
const result = await graphql({
  schema, rootValue, contextValue: context,
  source: '{ posts { id title author { id name } } }',
});
console.log(JSON.stringify(result));
console.log('author batches:', context.batchCalls);
```

The result contains Ada for `p1`, Bo for `p2` and `null` for `p3.author`, with one author batch. Storage returned `u2` before `u1`; returning the rows directly would attach the wrong users to posts. DataLoader requires one result per input key in exactly the same order.
Return `null` for an allowed missing value or an `Error` for a key-specific failure; rejecting the whole batch fails every key in that batch.

## 3. Errors follow the schema's null boundaries

The example deliberately declares `author: User`, allowing a missing author without losing the post. With `author: User!`, the missing value produces an execution error and makes that post null. Because the list is `[Post!]!`, the failure then reaches the root and `data` becomes null.
This is **null propagation**: an error moves outward until it reaches a nullable boundary.

GraphQL can return successful sibling data and an `errors` array together. A missing optional value is not automatically an error; a thrown exception or violated non-null promise is. Return safe public error messages and retain diagnostic details in protected logs.

## 4. Test the field path

Keep resolvers thin: invoke an authorized domain operation and return its result. Test representative documents against the actual schema, not only resolver functions; assert key ordering, missing-key behavior, null propagation and tenant isolation. Put atomic business changes in the domain/storage layer, and measure query counts and batch sizes before claiming an optimization.
A loader cannot compensate for an unbounded list or an unindexed query.

## Real-world decisions

**Context lifetime.** Share a long-lived database pool or HTTP client across requests. Create identity, loaders and request counters per request. A global loader keyed only by user ID can serve another tenant's cached record. For long-lived subscriptions, avoid treating one connection's loader as a permanent cache: establish event-level policy and refresh or bound cached data.

**Batching and caching.** DataLoader's memoization is normally limited to one context. Calling `.load(id)` repeatedly shares its promise. Awaiting every load inside a sequential loop can prevent batching; issue independent loads together. Bound batch sizes to storage limits. After a mutation, clear or replace affected loader entries, including related indexes; a fresh row does not invalidate every cached relationship automatically.

**Authorization.** Apply the same resource policy to direct lookups, nested relationships and batch queries. A role check at `Query.posts` does not protect an independently reachable `Query.post(id)`. Decide whether inaccessible records return null or a safe forbidden error, and apply that decision consistently without leaking their existence.

**Pagination.** A loader batches lookups; it does not define list order. For a connection, use a stable order with a unique tie-breaker, bounded page size and cursors bound to the filter and tenant. Do not use a timestamp alone when rows can share it. [Schema design](../01-fundamentals/20.7.1.02-schema-design.md) owns the GraphQL connection contract.

**Computed and polymorphic fields.** Aggregations should use bulk storage queries where possible. Making a CPU-heavy function `async` does not move it off the Node.js event loop; use an appropriate worker or background job. An interface or union needs reliable runtime type identification, such as a known `__typename` or explicit discriminator, rather than guessing from an optional property.

**Selections and projections.** `info` can guide a storage projection, but aliases, fragments, directives and required policy fields complicate selection analysis. Prefer a tested AST-aware helper; do not assume the first field node contains the whole operation. Keep required IDs and policy columns even when a client does not select them.

## Summary

Resolvers bridge the selected field tree and authorized data access. Parents supply child inputs, independent query fields can overlap, and top-level mutation fields are serial without being transactional. Request-scoped loaders reduce repeated lookups only when results preserve key order and policy scope; the schema determines how missing values and errors affect the response.

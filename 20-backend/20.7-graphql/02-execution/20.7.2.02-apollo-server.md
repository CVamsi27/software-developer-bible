# Apollo Server

## Definition

**Apollo Server** is a Node.js GraphQL server library. It accepts operations, validates them against a schema, calls resolvers and returns GraphQL results. A web-framework integration connects this execution engine to HTTP requests; database access and business policy remain application responsibilities.

> **Textbook Definition:** Apollo Server implements a GraphQL request-processing pipeline around GraphQL.js, with schema construction, execution, context and plugin interfaces for transport integrations and operational controls.

## First Principles

An operation needs more than a resolver map. The server must reject invalid syntax and selections, establish identity, select an operation, constrain work and produce a response even when part of execution fails. Its HTTP host must also limit bodies and drain connections during shutdown. Separating the transport, execution engine and domain layer gives each boundary a clear owner.

A schema establishes permitted shapes, not permitted callers or affordable workloads. Therefore authentication, authorization and resource limits must accompany schema validation.

## Why it matters

A server may return HTTP 200 with GraphQL execution errors. A health check can pass while tenant filtering is broken. A senior answer should explain the request boundary, the identity passed to resolvers, the work rejected before execution and how failures are measured.

## How a request moves through the server

```text
HTTP host: body limit, CORS, transport checks
    → request context: verified identity and scoped dependencies
    → GraphQL: parse, validate, select operation
    → admission policy: permitted operation and bounded work
    → resolvers: resource authorization and domain/storage calls
    → response: data plus safe errors, metrics
```

This diagram describes responsibilities, not a universal middleware ordering guarantee. The integration invokes context creation; plugin hooks observe specific GraphQL stages. `didResolveOperation` occurs after parsing and validation and before execution. Parse/validation results may be cached, so a static validation rule must not depend on current credentials or variables.

## Example: Apollo Server 5 with Express 5

Apollo Server 5 requires Node.js 20 or later and GraphQL.js 16.11 or later; use a supported Node.js release in production. Its Express integration is a separate package. Install:

```bash
npm install @apollo/server@5 @as-integrations/express5 express@5 cors graphql@16
```

Save as `server.mjs` and run `node server.mjs`. This is a local authentication fixture: the literal credential lets you observe the boundary; replace the verifier with your identity provider before deployment.

```javascript
import express from 'express';
import cors from 'cors';
import http from 'node:http';
import { ApolloServer } from '@apollo/server';
import { expressMiddleware } from '@as-integrations/express5';
import { ApolloServerPluginDrainHttpServer } from '@apollo/server/plugin/drainHttpServer';
import { GraphQLError } from 'graphql';

const app = express();
const httpServer = http.createServer(app);
const typeDefs = `
  type User { id: ID!, name: String! }
  type Query { me: User! }
`;
const metricsPlugin = {
  async requestDidStart() {
    const started = performance.now();
    return {
      async willSendResponse(ctx) {
        console.log(JSON.stringify({
          event: 'graphql.request',
          operation: ctx.operationName ?? 'anonymous',
          durationMs: Math.round(performance.now() - started),
          errorCount: ctx.errors?.length ?? 0,
        }));
      },
    };
  },
};
const server = new ApolloServer({
  typeDefs,
  resolvers: { Query: { me: (_parent, _args, ctx) => ctx.principal } },
  includeStacktraceInErrorResponses: false,
  plugins: [ApolloServerPluginDrainHttpServer({ httpServer }), metricsPlugin],
});
await server.start();
app.disable('x-powered-by');
app.use('/graphql',
  cors({ origin: 'http://localhost:5173' }),
  express.json({ limit: '32kb' }),
  expressMiddleware(server, {
    context: async ({ req }) => {
      if (req.headers.authorization !== 'Bearer local-demo') {
        throw new GraphQLError('Authentication required', {
          extensions: { code: 'UNAUTHENTICATED', http: { status: 401 } },
        });
      }
      return { principal: { id: 'u1', name: 'Ada' } };
    },
  }),
);
await new Promise(resolve => httpServer.listen(4000, '127.0.0.1', resolve));
console.log('http://127.0.0.1:4000/graphql');
for (const signal of ['SIGINT', 'SIGTERM']) {
  process.once(signal, async () => {
    await server.stop(); // The drain plugin closes the HTTP server.
  });
}
```

Send a JSON POST with the fixture credential:

```bash
curl http://127.0.0.1:4000/graphql \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer local-demo' \
  --data '{"query":"query Viewer { me { id name } }"}'
```

The result is `{"data":{"me":{"id":"u1","name":"Ada"}}}`. Omitting the credential produces an authentication error before `me` runs. A production verifier must check signature or trusted session storage, expiry, issuer and audience as applicable; a client-selected role or tenant header is not verification.

## Context carries identity, not a new pool

Context is created per request by `expressMiddleware`, not by a `context` option on the modern `ApolloServer` constructor. Share safe long-lived database pools at application startup; inject request-scoped loaders and the verified principal into context. Resource-level authorization still belongs in the domain operation or resolver boundary. An authenticated user does not automatically own every object ID.

For tests, `executeOperation` exercises GraphQL processing with an explicitly supplied `contextValue`; it does not run Express middleware or prove CORS, body limits or authentication. Add HTTP-level tests for those boundaries.

## Plugins observe specific stages

`requestDidStart` creates request-local plugin state. Its returned listener can observe parsing, validation, operation resolution, execution, errors and response production. Hooks can be asynchronous; use their documented signatures rather than invented plugin names.

The metric above intentionally records no query text, variables or credential. In production, cap and sanitize operation names or map them to registered IDs before using them as metric labels; arbitrary names cause high-cardinality metrics. Aggregate duration and execution errors as well as HTTP errors. Keep sensitive diagnostic logs access-controlled and correlate them with a request ID.

Cache-control hints describe response cacheability; they do not install a response cache. Studio/GraphOS reporting is optional and requires explicit privacy and service configuration. Neither is required to execute GraphQL.

## Real-world decisions

| Decision | What to establish before choosing |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Standalone server or Express integration | Standalone is convenient for a small service; integration gives explicit middleware, routing and HTTP lifecycle control. |
| Fastify or another host | Use a maintained integration compatible with that host and Apollo version; Apollo core does not expose an old `createHandler` shortcut. |
| Schema-first or prebuilt schema | Pass `typeDefs` and `resolvers`, or pass a constructed `schema`; avoid mixing two conflicting ownership models. |
| Serverless hosting | Reuse safe connections across warm invocations, handle cold starts and platform deadlines, and use the platform integration. A Node HTTP listener is not a Lambda handler. |
| Federation | Compose a reviewed supergraph from owned subgraphs; bound router fan-out and secure service-to-service identity. Do not forward arbitrary public identity headers as trusted claims. |

**Subscriptions.** Apollo's HTTP execution setup does not automatically create a WebSocket subscription server. Add a compatible `graphql-ws` transport, authorized subscription setup and per-event visibility checks. Use a shared event system across instances and define reconnect/replay semantics; in-memory pub/sub is only a single-process fixture.

**Uploads.** Prefer an authorized upload-intent operation followed by direct object-storage transfer and a completion check. If multipart GraphQL uploads are required, add a compatible middleware explicitly, maintain CSRF protection, cap stream sizes and counts, reject unsafe filenames, use backpressure-aware stream handling and clean partial files. Apollo Server 5 does not include an upload scalar or uploader by default.

**Incremental delivery.** `@defer` and `@stream` require matching schema directives, server execution support and client transport handling. Apollo Server 5's documented experimental support has a specific GraphQL.js prerelease constraint; the `graphql@16` example above does not support incremental delivery. Do not enable a flag and assume end-to-end compatibility.

## Mistakes

- Importing the removed `@apollo/server/express4` path in a Server 5 application.
- Catching an invalid credential and silently treating it as anonymous.
- Trusting a raw tenant header, constructing a database pool per request or sharing request loaders globally.
- Treating CORS or disabled introspection as resource authorization.
- Logging raw variables or relying only on HTTP success rates.
- Assuming serial mutations, a drain plugin or a cache hint supplies transactions, dependency cancellation or response caching.

## Best practices

Keep CSRF prevention enabled and restrict browser origins as appropriate; CORS controls browser access, not non-browser clients. HTTP batching is disabled by default: enabling it requires limits and accounting for every contained operation. Add operation-level limits before exposing arbitrary queries. Mask unexpected failures without changing safe expected error codes. Provide a readiness check appropriate to traffic admission and a separate liveness check, without exposing internal dependency details publicly.

Before release, exercise rejected credentials, cross-tenant access, malformed variables, resolver errors, oversized bodies and shutdown with in-flight work. Set deadlines in downstream clients and storage; stopping an HTTP response does not necessarily stop its database query.

## Summary

Apollo Server owns GraphQL processing; its host owns HTTP integration, and the application owns authorized business operations. Server 5 uses separate Express integration packages and per-request context. Build an explicit admission boundary, observe GraphQL errors alongside HTTP status, and verify optional transports and plugins independently.

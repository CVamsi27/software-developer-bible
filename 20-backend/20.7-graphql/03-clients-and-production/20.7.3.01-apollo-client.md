# Apollo Client

A task's project changes from `p1` to `p2`. Apollo can update the normalized `Task:t1` record so every screen sees the new project ID, but it cannot infer which filtered project lists, counts or pages should now include that task. Entity identity is shared; collection membership remains an application decision.

## Definition

**Apollo Client** executes GraphQL operations and manages their results for an application. Its normalized cache can let several screens share the same entity: updating a user's name can update every screen that reads that cached user.

> **Textbook Definition:** Apollo Client is a GraphQL operation and state-management library that combines transport links, observable operation results and a configurable normalized entity cache, with separate UI-framework integrations.

## First Principles

Two queries can return the same user in different shapes. Storing whole responses independently creates competing copies. A normalized cache separates entity identity from the lists and fields that refer to it.
This only works when identities are stable and field arguments distinguish different results.

The cache is a client representation, not the source of truth. It may be stale, incomplete or scoped to a previous login. A write that changes one entity also may change list membership, ordering or totals; updating that entity alone cannot infer those consequences.

## 1. How normalization connects screens

With default identity conventions, a result containing `__typename: "User"` and `id: "u1"` is stored as `User:u1`. A query field points to that record. A second query selecting the same user adds or updates selected fields on the same record.

```text
ROOT_QUERY.user({id:"u1"}) ──→ User:u1 { name: "Ada" }
ROOT_QUERY.team.members   ──→ [User:u1, User:u2]
```

Apollo normally adds `__typename` to operation selections. An entity's key fields must also be selected and available; `keyFields` cannot invent a missing server ID. If IDs are only unique within a tenant, use a selected tenant field in a compound key, or define globally unique IDs.
An entity with no suitable identity can be embedded rather than normalized.

## 2. Example: Client 4 with a typed React query

This example was verified on 13 October 2026 with Apollo Client 4.3.3, GraphQL.js 17.0.2, RxJS 7.8.2, React 19.3.0 and TypeScript 7.0.2. Install:

```bash
npm install @apollo/client@4.3.3 graphql@17.0.2 rxjs@7.8.2 react@19.3.0 react-dom@19.3.0 @graphql-typed-document-node/core@3.2.0
npm install --save-dev typescript@7.0.2 @types/react@19.3.0 @types/react-dom@19.3.0
```

Apollo Client 4's React hooks and provider come from `@apollo/client/react`. Configure an explicit transport link rather than the removed `uri` constructor option. Apollo Client 4 also supports GraphQL.js 16; Apollo Server 5 currently requires GraphQL.js 16, so a client/server monorepo should select a shared compatible GraphQL.js version when practical.

This example expects the following server contract; it does not create a server:

```graphql
type User { id: ID!, name: String! }
type Query { user(id: ID!): User }
type Mutation { renameUser(id: ID!, name: String!): User! }
```

```tsx
import { ApolloClient, HttpLink, InMemoryCache, gql } from '@apollo/client';
import { ApolloProvider, useQuery, useMutation, skipToken } from '@apollo/client/react';
import type { TypedDocumentNode } from '@graphql-typed-document-node/core';

type User = { __typename: 'User'; id: string; name: string };
const USER: TypedDocumentNode<{ user: User | null }, { id: string }> = gql`
  query UserCard($id: ID!) { user(id: $id) { id name __typename } }
`;
const RENAME: TypedDocumentNode<
  { renameUser: User }, { id: string; name: string }
> = gql`
  mutation RenameUser($id: ID!, $name: String!) {
    renameUser(id: $id, name: $name) { id name __typename }
  }
`;
const client = new ApolloClient({
  cache: new InMemoryCache(),
  link: new HttpLink({ uri: '/graphql', credentials: 'same-origin' }),
});

function UserCard({ id }: { id?: string }) {
  const { data, loading, error } = useQuery(
    USER, id ? { variables: { id }, errorPolicy: 'none' } : skipToken,
  );
  const [rename, mutation] = useMutation(RENAME);
  // A skipped query can retain its previous data. Hide it if identity is absent.
  if (!id) return <p>Select a user.</p>;
  if (loading) return <p>Loading user…</p>;
  if (error) return <p>Could not load this user.</p>;
  if (!data?.user) return <p>User not found.</p>;
  const user = data.user;
  return <section>
    <h2>{user.name}</h2>
    <button disabled={mutation.loading} onClick={async () => {
      try {
        await rename({
          variables: { id: user.id, name: 'Ada Lovelace' },
          optimisticResponse: {
            renameUser: { ...user, name: 'Ada Lovelace' },
          },
        });
      } catch {
        // The mutation result below renders a safe failure message.
      }
    }}>Rename</button>
    {mutation.error && <p>Rename failed. Try again.</p>}
  </section>;
}
export function App() {
  return <ApolloProvider client={client}><UserCard id="u1" /></ApolloProvider>;
}
```

The optimistic response temporarily updates the same `User:u1` record. When the server responds, the optimistic layer is removed and the confirmed response supplies the result. A rejected mutation removes its optimistic layer; design the UI to explain the failure.
Optimistic UI is a prediction, not database optimistic locking or proof that a write succeeded.

The manually annotated `TypedDocumentNode` above is a small teaching boundary. A wrong annotation can lie about the operation. [Code generation](20.7.3.03-codegen-schema-safety-ci.md) derives operation types from the actual schema and selections instead.

## 3. Choose the fetch policy deliberately

| Policy | Cache read | Network behavior | Cache write |
| ------------------- | --------------------------------------- | ----------------------------------- | ----------------------------------- |
| `cache-first` | Uses a complete matching cached result | Fetches if the result is incomplete | Yes |
| `cache-and-network` | Can show cached data immediately | Also fetches to refresh it | Yes |
| `network-only` | Does not satisfy the request from cache | Fetches from the network | Yes |
| `no-cache` | Does not use cached data | Fetches from the network | Does not store the operation result |
| `cache-only` | Reads cache only | Does not fetch | No network result to write |

A refresh policy does not set server freshness guarantees. For an account balance or permission change, decide whether cached presentation is acceptable and how stale data is labeled. With `errorPolicy: 'all'`, data and an error can coexist; render useful partial data and identify the failed portion instead of returning early for every error.
Client 4 distinguishes GraphQL and transport error classes; do not assume every failure has an older `graphQLErrors` array.

## 4. Updating entities does not update every list

A mutation returning an existing ID and changed fields can update normalized entity data. A create/delete or filter-changing mutation requires list work. Options are an explicit cache update for a known list shape, invalidation followed by refetch, or `refetchQueries` for known active operations.
Re-fetching is often clearer than a fragile custom merge when correctness matters more than avoiding one request.

`cache.modify` changes a particular cached field representation; it does not understand arbitrary business filters. A connection object with `edges` is not an array of posts. Check nullable `readQuery` results before using them, and match every selected field when writing a query result.
A generic append to every list can place an entity in lists where it does not belong.

For cursor connections, configure a pagination helper or a tested field policy that distinguishes semantic arguments such as tenant, filter and sort while merging page arguments. Deduplicate by stable identity, preserve edge cursors, and define behavior for overlapping or out-of-order responses. A simple concatenation is insufficient when a refresh races an older page request.

## 5. Test state transitions

Test optimistic success and rollback, distinct temporary IDs for concurrent creates, list membership after creates or filter-changing updates, logout and tenant switches, overlapping pages and late responses for superseded input. Keep operation selections near their consumers and derive types through codegen. Use cache inspection to understand records and references, then verify the visible state against the server contract.

## Real-world decisions

**Authentication and cache lifetime.** Add current credentials through a transport link or a trusted cookie. On logout or tenant change, stop or isolate in-flight operations and remove private persisted cache data. `clearStore()` clears without re-fetching active queries; `resetStore()` clears and re-fetches them, so replace credentials before any re-fetch. For server-side rendering, create a client/cache per request rather than sharing private results globally.

**Debounce, cancellation and lazy queries.** `useLazyQuery` lets an event initiate an operation; it does not debounce keystrokes. A fetch policy does not implement debounce either. Manage a stable timer and cancellation/generation checks for search or autosave, and avoid accepting a late response for a superseded input.

**Subscriptions.** A subscription needs an appropriate link, such as `GraphQLWsLink`, and a server implementing that transport. Split subscriptions from HTTP operations, authenticate reconnects and define deduplication/recovery. Receiving an event does not automatically merge it into every filtered query result.

**Batching and persisted operations.** HTTP batching requires explicit server support; Apollo Server disables it by default. Account for latency, independent errors and per-operation rate limits before enabling a batch link. Persisted-query negotiation reduces transmitted query text, but does not authorize an operation or its variables.

**Choosing a client.** Apollo's normalized cache is valuable for shared entities. TanStack Query generally caches query results by keys rather than providing Apollo-style entity normalization. urql's default document cache and its optional Graphcache are different choices. Compare required behavior and measured bundle/runtime cost; unverified fixed bundle-size tables age poorly.

## Summary

Apollo Client connects operation results to a normalized cache and UI subscriptions. Stable identity makes shared entity updates possible; list membership and pagination need explicit policies. Client 4 separates React imports and requires an explicit link.
Fetch policy, error policy, optimistic updates and identity isolation each solve a different boundary.

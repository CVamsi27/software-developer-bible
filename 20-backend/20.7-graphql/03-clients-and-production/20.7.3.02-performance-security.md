# GraphQL Performance and Security

## Definition

**GraphQL performance and security** means keeping each operation affordable and ensuring that every returned or changed resource is permitted for its caller. A small query document can request a large amount of nested work, so request count and HTTP body size alone cannot describe its cost.

> **Textbook Definition:** GraphQL admission and execution controls constrain operation structure, input-dependent work, caller privileges and resource consumption across the selected field graph and its downstream dependencies.

## First Principles

A client chooses selections and list arguments; the server chooses the implementation and permitted bounds. If each of three nested lists returns 100 items, work can grow toward a million combinations despite a shallow document. Aliases can repeat an expensive field without adding depth. Authorization must be enforced on the resulting resources, including those reached through nested fields.

Validation establishes that an operation fits the schema. It cannot establish that a caller owns a row, that a valid integer is a reasonable page size, or that a downstream service will finish before a deadline. These require separate policies.

## Why it matters

A query can be valid and still exhaust a connection pool. A cached response can be fast and still disclose another tenant's records. Explain the cost model, identity scope and dependency limits together; neither “use DataLoader” nor “disable introspection” addresses the whole request.

## How controls fit together

| Boundary | Example control | What it does not replace |
| -------------- | ------------------------------------------------------- | ------------------------------------------------- |
| Transport | Body/URL size, timeout, HTTP batch policy | Resource authorization or list bounds |
| Document | Depth, alias/list-depth and fragment-aware validation | Actual variable-dependent cost |
| Admission | Registered operation, caller quota, variable bounds | Resolver policy and database constraints |
| Execution | Tenant/resource checks, bounded fan-out, DataLoader | Expensive aggregations or global admission limits |
| Dependencies | Pool size, concurrency caps, deadlines and cancellation | Correct schema and permission policy |
| Response/cache | Safe errors, scoped keys and invalidation | Authentication on uncached paths |

Depth is one signal, not a complete cost model. Use a maintained AST-aware validator that handles fragments, aliases and cycles; do not count `{` characters. Static rules can be cached with the document. Checks using current variables or identity must run on every request, including requests using a previously validated document.

## Example: a closed operation set with bounded variables

Automatic persisted queries (**APQ**) negotiate a query hash and let the server remember its text. A client can normally register new text on a cache miss; APQ alone is not an operation allowlist. A trusted allowlist is a deployment artifact whose approved documents are accepted independently of client negotiation.

The following complete `limits.mjs` example registers one named operation. It compares a canonical printed document and selected operation name, then checks the page variable at `didResolveOperation`. It deliberately disables APQ to make the registration boundary visible. Install `@apollo/server@5` and `graphql@16`.

```javascript
import { ApolloServer } from '@apollo/server';
import { GraphQLError, parse, print } from 'graphql';
import { createHash } from 'node:crypto';

const document = 'query Users($first: Int!) { users(first: $first) { id name } }';
const fingerprint = doc => createHash('sha256').update(print(doc)).digest('hex');
// In production, load this trusted manifest from reviewed build artifacts.
const registered = new Map([['Users', fingerprint(parse(document))]]);
function boundedFirst(value) {
  if (!Number.isInteger(value) || value < 1 || value > 50) {
    throw new GraphQLError('first must be an integer between 1 and 50', {
      extensions: { code: 'BAD_USER_INPUT' },
    });
  }
  return value;
}
const admissionPlugin = {
  async requestDidStart() {
    return {
      async didResolveOperation(ctx) {
        const name = ctx.operation.name?.value;
        if (!name || registered.get(name) !== fingerprint(ctx.document)) {
          throw new GraphQLError('Operation is not registered', {
            extensions: { code: 'OPERATION_NOT_ALLOWED' },
          });
        }
        boundedFirst(ctx.request.variables?.first);
      },
    };
  },
};
const rows = [ { id: 'u1', name: 'Ada' }, { id: 'u2', name: 'Bo' } ];
const server = new ApolloServer({
  typeDefs: `
    type User { id: ID!, name: String! }
    type Query { users(first: Int!): [User!]! }
  `,
  resolvers: {
    Query: { users: (_parent, { first }) => rows.slice(0, boundedFirst(first)) },
  },
  persistedQueries: false,
  includeStacktraceInErrorResponses: false,
  plugins: [admissionPlugin],
});
await server.start();
for (const first of [2, 500]) {
  const result = await server.executeOperation({ query: document, variables: { first } });
  console.log(JSON.stringify(result.body));
}
await server.stop();
```

The first execution returns two users; the second is rejected before its resolver runs. The resolver independently enforces the bound so another approved operation cannot bypass it. This small fixture has no authentication or tenant data and is not a production authorization implementation.

The document's variable is required and has no default. For general operations, apply GraphQL variable coercion and defaults consistently before cost calculation; raw JSON variables are not automatically equivalent to resolved argument values. A manifest generator and runtime must use the same canonicalization. Never trust the client to choose the allowed-document map or its hash. Rolling deployments must support the manifest versions still used by active clients.

## Estimate work, then cap actual consumption

For the registered `Users` operation, page size gives a simple bound. A real cost model assigns weights to fields and multiplies list fan-out by bounded arguments. Include expensive database aggregations and external-service calls. Cost points are estimates, not milliseconds; calibrate them with observed resolver/storage latency and periodically review them.

Rejecting large individual operations still leaves repeated small operations. Apply identity- and tenant-based quotas and concurrency limits, with distributed accounting when there are multiple instances. A bearer token string is a poor bucket key: refresh changes it, it can leak in telemetry, and it does not identify shared tenant limits. Bound anonymous clients separately using trusted proxy handling.

Control query text size, alias count, list nesting, response size and HTTP batch size as relevant. Apollo's HTTP batch support is disabled by default. If enabled, inspect and charge every operation in the batch; one HTTP request is not one unit of work. Use bounded caches for parsed documents and APQ entries to avoid uncontrolled memory growth.

## Authorization follows every path to a resource

Authentication establishes a verified principal. Authorization decides whether that principal may act on a specific resource. Resolve a tenant from authenticated membership, not a public `x-tenant-id` header, then include it in every storage predicate and relationship load. Test direct IDs, nested relations, aliases, mutation targets and subscription events.

A custom `@auth` directive is schema metadata until a runtime implementation enforces it. Field and object directives need defined inheritance and default-resolver behavior; one wrapper that misses default fields or alternate paths is incomplete. Prefer a shared domain policy reachable from all resolvers, and use directives only when their enforcement is well specified and tested.

Input types constrain shape, not every business value. Bound string length, pages, upload sizes and batch item counts. Use parameterized storage queries: GraphQL parsing does not prevent SQL injection inside a resolver. Consider whether error messages, list totals or timing reveal inaccessible records.

## Cache the correct scope

Distinguish request-scoped DataLoader memoization, parsed-document caches, client entity caches and server response caches. They cache different values and have different privacy boundaries. Cache-control hints alone do not store responses.

For a private response cache, include verified principal/tenant scope, operation identity, semantic variables and relevant authorization version in the key. Never put a raw credential in a key or log. A “private” hint requires the cache implementation to enforce a private partition; a session ID does not disable caching. Permission changes and mutations require invalidation or appropriately short bounded freshness. Public caching is safe only if every field in the response is public under that policy.

HTTP GET can help cache read-only operations but must never execute mutations, and sensitive variables in URLs may reach history and access logs. A CDN configuration must respect authorization, cookie and cache-control boundaries; a single `/graphql` URL does not automatically provide useful safe caching.

## Real-world decisions

**Introspection.** Keeping it available for authorized tooling supports discovery. Restricting it on public production access may reduce disclosure, but known documents remain executable and resource checks remain mandatory. Federation and schema tooling may need separate trusted access.

**CORS and CSRF.** CORS governs browser cross-origin access; scripts outside browsers can still call the server. Keep Apollo's CSRF prevention enabled, particularly with cookie authentication, GET and multipart transports. Apply actual authentication and authorization independently.

**Timeouts and retries.** Put deadlines and cancellation into database and downstream clients as well as the HTTP layer. Retrying an ambiguous mutation can duplicate effects; use application-level idempotency keys where the business operation needs them. A client disconnect does not inherently cancel backend work.

**Observability.** Record registered operation identity, latency, cost, rejection reasons, storage calls, cache behavior and execution-error rates with bounded labels. Do not send raw variables or credentials to dashboards. Test both HTTP failures and GraphQL errors returned with successful HTTP status.

## Mistakes

- Treating APQ as an allowlist, or importing fictitious persisted-query plugins.
- Putting variable-dependent limits only in cached validation rules.
- Measuring depth while ignoring aliases, list multipliers and expensive fields.
- Trusting a client-selected tenant or caching private results without policy scope.
- Assuming input coercion validates business bounds or GraphQL prevents unsafe SQL.
- Claiming protection from introspection restrictions, CORS or HTTP request limits alone.

## Best practices

Start with the operations the product needs and explicit limits for their variables. Make limits observable and rejection messages actionable. Load-test representative and adversarial operations against actual dependencies, including permission checks and cache misses. Test stale permission caches and cross-tenant paths. Keep a controlled rollout and rollback for schema and manifest changes; lowering limits can break legitimate clients too.

## Summary

GraphQL safety comes from affordable admitted work and resource-level permissions across every path. Static document rules, request-specific bounds, scoped caching, quotas and dependency deadlines complement each other. APQ reduces transmitted text; a trusted allowlist restricts accepted documents, and neither removes variable or authorization checks.

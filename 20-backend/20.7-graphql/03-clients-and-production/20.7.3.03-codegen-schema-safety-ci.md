# Code Generation, Schema Safety and CI

A component reads `data.user.email`, but its operation selected only `id` and `name`. A schema-wide `User` type can let that mismatch look plausible; a generated operation type reflects the actual selection and catches it during compilation. It still cannot prove which schema version is deployed or what a resolver returns at runtime.

## Definition

**GraphQL code generation** derives source artifacts from a schema and the operations an application actually uses. Instead of manually claiming that a query returns an entire `User`, generated operation types describe only its selected fields and their declared nullability.

> **Textbook Definition:** GraphQL code generation is a build-time transformation of schema and executable documents into language-specific types, typed documents or interfaces. Schema compatibility checking compares contract versions; neither process validates live resolver behavior by itself.

## First Principles

A schema describes all available fields; an operation chooses a subset. Therefore a schema-wide object type is usually the wrong type for a query result. The generated result must follow selections, aliases, fragments and nullable boundaries, while its variable type must follow the operation's input declarations.

The generator only sees the schema artifact supplied to it. If that artifact differs from the deployed server, a clean build can still produce failing requests. Safety therefore requires an identified contract version, validation of documents, compilation of consumers and compatible deployment sequencing.

## Example: generate exactly the selected result

This example was verified on 13 October 2026 with GraphQL.js 17.0.2, GraphQL Code Generator CLI 7.4.6, client preset 6.2.3 and TypeScript 7.0.2. Install the build-time tools and typed-document package, plus Apollo Client and React from the [client example](20.7.3.01-apollo-client.md):

```bash
npm install graphql@17.0.2 @graphql-typed-document-node/core@3.2.0
npm install --save-dev @graphql-codegen/cli@7.4.6 @graphql-codegen/client-preset@6.2.3 @graphql-inspector/cli@7.0.1 typescript@7.0.2
```

Save the following local contract as `schema.graphql`:

```graphql
scalar DateTime
type User { id: ID!, name: String!, email: String, joinedAt: DateTime! }
type Query { user(id: ID!): User }
```

Save `src/user.graphql`:

```graphql
fragment UserName on User { id name }
query UserCard($id: ID!) { user(id: $id) { ...UserName joinedAt } }
```

Save `codegen.ts`:

```typescript
import type { CodegenConfig } from '@graphql-codegen/cli';
const config: CodegenConfig = {
  schema: './schema.graphql',
  documents: ['src/**/*.graphql'],
  generates: {
    './src/gql/': {
      preset: 'client',
      config: {
        strictScalars: true,
        scalars: { DateTime: 'string' },
      },
    },
  },
};
export default config;
```

Run `npx --no-install graphql-codegen --config codegen.ts`. The client preset emits typed documents/types in `src/gql/graphql.ts`, helpers in `src/gql/gql.ts` and, with its default fragment masking, fragment helpers in `src/gql/fragment-masking.ts`.

```tsx
import { useQuery } from '@apollo/client/react';
import { UserCardDocument, UserNameFragmentDoc } from './gql/graphql';
import { useFragment, type FragmentType } from './gql/fragment-masking';

function Name({ user }: { user: FragmentType<typeof UserNameFragmentDoc> }) {
  // This generated helper unmasks fragment data; it is not a React hook.
  const person = useFragment(UserNameFragmentDoc, user);
  return <h2>{person.name}</h2>;
}
export function Card({ id }: { id: string }) {
  const { data, loading, error } = useQuery(UserCardDocument, { variables: { id } });
  if (loading) return <p>Loading…</p>;
  if (error) return <p>Could not load user.</p>;
  if (!data?.user) return <p>User not found.</p>;
  return <section><Name user={data.user} /><time>{data.user.joinedAt}</time></section>;
}
```

The result can contain `user: null`. `email` is not selected, so the generated operation result cannot be used as though it contained `email`. Fragment masking makes a component's declared fragment ownership explicit; use its helper to access fields inside that fragment. It is a compile-time organization boundary, not authorization or a guarantee that a server sends no extra data.

## Scalars need a runtime contract

Mapping `DateTime` to `string` means TypeScript expects a string. It does not parse a date, validate an offset or reject a malformed server result at runtime. Define serialization and accepted inputs on the server, and decode on the client when runtime validation matters. `strictScalars` prevents unmapped custom scalar names from silently receiving an overly permissive type; it does not validate values.

Avoid mapping an unconstrained `JSON` scalar to a detailed interface without a decoder or schema contract. Prefer `unknown` when its structure is genuinely unknown. Generated TypeScript types are erased at runtime.

## Choose an output model, then match its imports

| Output choice | Fit and boundary |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Client preset | Typed documents and operation types for supported clients, with fragment masking by default. |
| Near-operation-file preset | Co-located generated files, configured as a separate output target with its own plugins and base types. It is not a second `presets` field inside a client-preset target. |
| Resolver types | Generated resolver interfaces help check server implementation signatures; they do not implement policy or storage. |
| GraphQL-request SDK | The `typescript-graphql-request` plugin generates an SDK accepting a compatible `GraphQLClient`; install its required plugins and runtime. |
| Generic SDK | `typescript-generic-sdk` expects a requester function; do not pass it a GraphQLClient merely because another plugin exposes a function named `getSdk`. |

A `.graphql` document must include or resolve the fragments it uses during generation. Import artifacts from the actual configured output, rather than inventing `UserAvatar.generated.ts` files for a configuration that generates a shared `gql/` directory. Test the emitted code with the selected client's current version.

## Schema compatibility follows direction

Removing a selected field or making an accepted input more restrictive can break callers. Making an output nullable weakens the client's guarantee; making an input non-null can require a value older callers do not provide. Adding enum values may break exhaustive client switches even though old operations remain valid.

Use deprecation descriptions to point consumers to a replacement, measure usage and retire fields only after supported clients migrate. A schema diff is useful evidence, but its classifications require review against actual client behavior, custom scalar semantics, authorization and resolver behavior. A field can keep the same SDL and still change meaning.

## CI proves build agreement, then integration proves execution

A practical sequence is:

1. Obtain the intended schema from a trusted, identified build/release artifact. Do not use a moving endpoint as an unexplained source of truth.
2. Compare it with the previous supported contract using GraphQL Inspector or equivalent tooling, and review breaking/dangerous changes.
3. Validate every operation and fragment against the intended schema while generating artifacts.
4. Compile the actual consumers with strict TypeScript settings, and keep a negative fixture proving that an invalid field or variable fails generation or compilation.
5. Run schema-execution and HTTP integration tests against the build being released, covering policy and null/error behavior.
6. Deploy additive server changes before consumers require them; retain old fields and operation manifests until supported consumers have migrated.

For a project that installs the CLI tools locally and commits generated artifacts, representative commands are:

```bash
npm ci
npx --no-install graphql-inspector diff previous.graphql schema.graphql
npx --no-install graphql-codegen --config codegen.ts
npx --no-install tsc --noEmit
# Fail if regeneration changes committed output. Include untracked-file policy too.
git diff --exit-code -- src/gql
```

`git diff` alone misses untracked files; the project's CI must also reject unexpected generated files or use a clean generation/output comparison. If artifacts are generated during each build rather than committed, compare and compile the build output instead. Pin tool versions through the lockfile. Credentials for fetching a private schema belong in secret storage, never generated source or logs.

## Real-world decisions

**One schema owner.** Schema-first SDL and code-first schema generation can both work; identify which artifact is authoritative and avoid two editable copies. Compose federated schemas before validating operations against the client-visible graph.

**Multiple clients.** Validate the operations of every supported client, including mobile releases still in use. A clean web build cannot prove that an older mobile app survives a removal. Persisted-operation manifests must be versioned and deployed with a compatibility window.

**Monorepos.** Assign schema and generated output ownership, cache builds by schema/documents/tool versions, and keep consumers from importing unrelated server internals. Generate only relevant client selections rather than distributing every schema type as an application model.

**Runtime confidence.** Test nullability promises, custom scalar decoding, authorization and representative resolver outputs. Keep environment/schema identifiers in release evidence so a passing contract check can be connected to the actual deployed server.

## Summary

Code generation aligns schema, selected operations and language types at build time. Correct output configuration and imports make that alignment usable; strict scalar mappings and fragment ownership improve clarity without supplying runtime validation. Schema review, supported-client compatibility and execution tests complete the boundary that a generated build cannot prove alone.

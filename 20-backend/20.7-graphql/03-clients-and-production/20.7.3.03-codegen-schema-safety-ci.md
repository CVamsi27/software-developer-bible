# GraphQL Code Generator — Schema Safety & CI

>
> **Why it matters:** "How do you keep the frontend in sync with the GraphQL schema?" is the senior GraphQL question. The answer is tooling discipline — codegen + schema checks in CI — not careful humans.

## Definition

**Schema-driven code generation** replaces hand-written request/response types with artifacts derived mechanically from the SDL:

```text
schema.graphql  (or introspection of the running server)
      │
      ├── graphql-codegen ──► types.ts            (TS mirrors of every type/input/enum)
      │                    ──► TypedDocumentNode   (queries typed by their RESULT shape)
      │                    ──► sdk.ts              (typed client functions)
      │
      └── graphql-inspector (CI) ──► diff vs published schema
                                     • breaking change → FAIL
                                     • dangerous → warn
                                     • additive → pass + notify consumers
```

`TypedDocumentNode<TData, TVars>` is the key trick: the *document itself* carries its result type, so any hook/client that accepts a `TypedDocumentNode` returns correctly typed data without per-call generics.

## First Principles

Codegen closes the loop: schema → types → compile errors instead of runtime errors.

1. **The schema is the type system; codegen projects it into your language.** TypeScript types from SDL mean a renamed field breaks the build, not production — the same fail-fast-at-contract as generated API clients (→ 20.3.1.05), applied bidirectionally (client ops → typed hooks too).
2. **Operations are validated at build time** against the schema (graphql-inspector-style diffs) — breaking changes are detected in CI by diffing schemas, before any client ships. The contract's evolution becomes a mechanical check.
3. **The discipline: schema-first with generated types, or code-first with generated SDL — but *one* source of truth**. Two hand-maintained representations of the contract always diverge; the tooling's whole job is making divergence impossible.

## Why Do We Need It?

1. **Runtime errors become compile errors** — renaming a field in the schema breaks every query using it at build time, not for users at runtime.
2. **One source of truth kills drift** — no parallel hand-maintained interfaces; backend types and frontend types cannot disagree.
3. **Refactoring velocity** — schema changes propagate as typed compile failures with exact locations; mass renames are mechanical.
4. **Fragment colocation needs generated types** — components own fragments; codegen makes each fragment's result type flow into props automatically.
5. **CI contract enforcement** — GraphQL Inspector classifies diffs as breaking/dangerous/safe, ending "it broke mobile" incidents.
6. **SDK publishing** — internal teams consume typed clients generated from the same schema; integration effort drops to install-and-query.

## How It Works

### Pipeline overview

```text
DEV LOOP                          CI PIPELINE
────────────                      ────────────────────────────────────────
edit .graphql / components        1. server exports schema.graphql artifact
run `codegen watch`               2. codegen regenerates typed artifacts
types update instantly            3. tsc fails on stale/broken usage
                                  4. inspector diff vs last published schema
                                     breaking? → block merge
                                     additive? → allow + version bump hint
                                  5. publish updated client SDK package
```

### Fragment colocation

Each component declares the fields it renders as a fragment; pages compose them:

```graphql
# fragments/UserAvatar.graphql
fragment UserAvatar on User {
  id
  avatarUrl
  displayName
}

# pages/TeamPage.graphql
query TeamPage($id: ID!) {
  team(id: $id) {
    id
    name
    members { ...UserAvatar }
  }
}
```

Benefits: the data requirement travels with the UI piece (delete the component, its fields vanish from queries after regeneration); refactors stay local; and generated types make `props.user.displayName` exist only if the fragment actually asked.

## Code Examples

### Code Generator setup (client preset)

```bash
npm i -D graphql @graphql-codegen/cli @graphql-codegen/client-preset
npm i -D @graphql-typed-document-node/core
```

```typescript
// codegen.ts
import type { CodegenConfig } from '@graphql-codegen/cli';

const config: CodegenConfig = {
  schema: 'http://localhost:4000/graphql',     // or './backend/schema.graphql'
  documents: ['src/**/*.tsx', 'src/**/*.graphql'],
  generates: {
    'src/gql/': {
      preset: 'client',
      config: {
        scalars: {
          DateTime: 'string',        // map custom scalars to TS types once
          UUID: 'string',
          Json: 'Record<string, unknown>',
        },
      },
      presets: [
        [
          'near-operation-file',     // fragment types emitted next to each component
          {
            baseTypesPath: 'types.ts',
            extension: '.generated.tsx',
          },
        ],
      ],
      hooks: { afterOneFileWrite: ['prettier --write'] },
    },
    'src/schema.graphql': { plugins: ['schema-ast'] }, // snapshot for diffing
  },
};
export default config;
```

```jsonc
// package.json scripts
{
  "codegen": "graphql-codegen --config codegen.ts",
  "codegen:watch": "graphql-codegen --config codegen.ts --watch"
}
```

### TypedDocumentNode in React

```tsx
// pages/TeamPage.tsx
import { gql } from '@urql/core';                 // or graphql-tag / Apollo's gql
import { useQuery } from 'urql';

export const TeamPageQuery = gql`
  query TeamPage($id: ID!) {
    team(id: $id) {
      id
      name
      members { ...UserAvatar }
    }
  }
`;

export function TeamPage({ id }: { id: string }) {
  // NO generic parameter needed: TeamPageQuery IS a TypedDocumentNode,
  // so `data` is fully inferred — wrong field names fail `tsc`, not prod
  const [result] = useQuery({ query: TeamPageQuery, variables: { id } });
  if (result.fetching || !result.data) return <Spinner />;
  return (
    <section>
      <h1>{result.data.team.name}</h1>
      {result.data.team.members.map((m) => (
        <UserAvatar key={m.id} user={m} />
      ))}
    </section>
  );
}
```

### Colocated component consumes its generated fragment type

```tsx
// fragments/UserAvatar.tsx
import { FragmentType, useFragment } from '../gql';       // client-preset helpers
import { UserAvatarFragmentDoc } from './UserAvatar.generated';

// FragmentType masks the full entity: callers CANNOT smuggle unqueried fields here
export function UserAvatar(props: { user: FragmentType<typeof UserAvatarFragmentDoc> }) {
  const user = useFragment(UserAvatarFragmentDoc, props.user);
  return <img src={user.avatarUrl} alt={user.displayName} width={40} height={40} />;
}
```

The masking is deliberate: `useFragment` unwraps only what the fragment selected, making accidental reliance on parent-queried-but-not-declared fields a compile error.

### CI schema check with GraphQL Inspector

```yaml
# .github/workflows/schema-check.yml
name: schema-check
on:
  pull_request:
    paths: ['backend/**', 'schema.graphql']
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
        with: { fetch-depth: 0 }              # history for the base schema

      - uses: kamilkisiela/graphql-inspector@master
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          schema: master:schema.graphql       # published/reference schema on main
          endpoint: 'http://localhost:4000/graphql'
          annotations: true                   # inline PR annotations per finding
          fail-on-breaking: true
          rules:
            - require-deprecation-reason
```

Equivalent one-shot CLI form:

```bash
npx @graphql-inspector/cli diff old-schema.graphql new-schema.graphql \
  --rule require-deprecation-reason
# exit code non-zero on BreakingChange — wire directly into any CI system
```

Typical policy: removing a field or changing an argument type = **breaking** (block; require deprecation cycle first — mark `@deprecated(reason: "...")`, ship removal next major); adding nullable fields/types = safe; adding required inputs = breaking for existing clients.

### Publishing a typed client SDK from the schema

```typescript
// Additional generator target consumed by downstream services/scripts
'src/generated-sdk.ts': {
  plugins: [
    'typescript',
    'typescript-operations',
    {
      'typescript-generic-sdk': {
        exportFragmentSpreadSubTypes: true,
        dedupeOperationSuffix: true,
      },
    },
  ],
},
```

```typescript
// Consumer side (a Node job, another service):
import { GraphQLClient } from 'graphql-request';
import { getSdk } from './src/generated-sdk';

const sdk = getSdk(new GraphQLClient(process.env.API_URL!));
// Fully typed: arguments AND results checked against the published schema
const { team } = await sdk.TeamPage({ id: 't_1' });
console.log(team.members.map((m) => m.displayName));
```

Version the SDK with the schema (`sdk@1.4.0` ↔ schema commit), publish to the private registry in the release pipeline, and let consumers pin ranges — Inspector guarantees no breaking change lands without a major bump.

## Real-World Use Cases

1. **Design-system parity** — UI kit ships fragments alongside components; product screens compose them; a field rename in `User` breaks exactly the kit's build, not eight apps independently.
2. **Mobile + web monorepo** — schema artifact published from backend CI; both platforms' codegen runs pinned to the same artifact hash; Inspector gates the backend PR before either client sees it.
3. **Federated graph** — subgraph schemas composed in CI (`rover supergraph compose`), Inspector checks composition-level breakage, gateway publishes the supergraph, clients regenerate from it.
4. **Public API program** — external developers receive generated SDKs per language; changelog entries derive from Inspector's classified diff (breaking/dangerous/additive).
5. **Legacy REST-to-GraphQL migration** — generated types let mixed screens coexist; each migrated screen deletes its REST types, and unused-operation detection prunes the document registry.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------- | ----------------------------------------------------------------------------- |
| Hand-editing files under `src/gql/` | Generated directory is build output; gitignore it and verify in CI |
| Codegen against localhost while CI checks nothing | CI must run codegen + `tsc --noEmit` + inspector diff on every PR |
| Giant page-level queries, no fragments | Colocate; components declare their own fields |
| Passing whole entities into leaf components | Use `FragmentType` masking; components unwrap via `useFragment` |
| Removing fields without deprecation window | `@deprecated` first; remove next major after telemetry shows zero use |
| Custom scalars left as `any` | Map every scalar in codegen config; validate at resolvers too |
| Schema fetched live in CI from dev DB | Publish `schema.graphql` artifact on merge; diff against it deterministically |
| Skipping regeneration after schema bump | Pre-commit/CI check: `codegen && git diff --exit-code src/gql` |

## Best Practices

1. **Schema artifact as release output** — backend CI publishes `schema.graphql` (plus SDL hash) per commit on main; all consumers pin it.
2. **Fail CI on breaking changes** — Inspector with explicit rules; dangerous changes require a labeled review.
3. **Colocate fragments everywhere** — the type system enforces it once `FragmentType` masking is standard.
4. **Regenerate + typecheck in CI, not just locally** — stale-artifact bugs are otherwise invisible until runtime.
5. **Map scalars explicitly and early** — `DateTime`, `UUID`, `Decimal`; document the mapping next to the schema.
6. **Deprecate, measure, then remove** — add usage telemetry per field; the deprecation reason links the removal ticket.
7. **Publish SDKs from the same pipeline** — semantic versions tied to schema compatibility ranges.
8. **Watch mode in development** — `codegen:watch` keeps the loop under a second; friction kills adoption.

## Performance Considerations

- Generated artifacts grow with schema size; `near-operation-file` keeps per-component output small and tree-shakable versus one giant `types.ts`.
- Persisted queries/APQ pairs well with codegen: documents are known at build time, so hashing and registering them can happen in CI (see Performance & Security chapter).
- Masked fragment types prevent over-fetching creep — reviewers see exactly which fields each component demands in the diff.
- Keep `documents` globs tight; scanning test fixtures bloats generation time and false positives.

## Summary

- Schema-first + codegen turns the GraphQL SDL into the compiler-checked contract for every consumer.
- `TypedDocumentNode` gives inferred result types with zero per-call generics; clients/hooks just work.
- Fragment colocation localizes data requirements; `FragmentType` masking prevents undeclared-field leaks.
- GraphQL Inspector in CI classifies schema diffs and blocks breaking changes before merge.
- Client SDKs generated from the same schema make internal and external consumption trivially typed.

# GraphQL Interview Questions

Use these 50 authored prompts after the learning and revision passes. Answer with a concrete mechanism, one example, the failure boundary and a justified decision. A proposed design is interview practice; describe project experience only when supported by actual work.

## First Principles

A selected field tree crosses contract, permission and resource boundaries. A plausible answer must follow that tree to its actual storage/dependency work, then identify what happens when identity changes, a dependency fails or an older client uses the contract. Domain designs also need authoritative invariants and recovery; a schema alone cannot supply them.

## Contract and operation basics

#### 1. What is GraphQL?

GraphQL is a typed API query language and execution model. A client selects fields from an operation; the server validates those selections and resolves them against a schema. It can return partial data with errors. The schema defines shape and nullability, while authentication, resource authorization, storage plans and limits remain application responsibilities.

#### 2. How does GraphQL differ from REST?

GraphQL lets clients choose fields and traverse declared relationships within an operation. REST commonly exposes resource-oriented HTTP routes and representations, often with more direct HTTP caching semantics. Either can batch, paginate or authorize resources. Choose from actual client variability, dependency cost and team ownership rather than assuming GraphQL always means fewer requests or better performance.

#### 3. What is a GraphQL schema?

A schema declares object and input types, fields, arguments, enums, scalars and operation roots. It is the contract used to validate documents and complete results. For example, `user(id: ID!): User` requires an ID but permits a missing user. SDL is one representation; code-first tools can construct the same executable contract. Schema validity does not prove resolver correctness.

#### 4. What are the three root operation types?

Query reads data, mutation represents changes, and subscription defines one event-producing root field. Independent query fields may run concurrently. Top-level mutation fields execute serially, but their effects are not automatically atomic or idempotent. Subscription transport, authorization on setup/events, reconnect and replay semantics require an implementation beyond declaring the root type.

#### 5. What are scalar types in GraphQL?

Built-in scalars are Int, Float, String, Boolean and ID. They define leaf values and input/output coercion; ID is an opaque identifier, not an instruction to use numeric arithmetic. Custom scalars such as DateTime need explicit serialization, input parsing and validation. A TypeScript scalar mapping alone neither implements those functions nor validates runtime responses.

#### 6. What is the `!` (non-null) modifier?

`!` promises a non-null value at that position. An invalid null output produces an execution error that propagates to the nearest nullable parent; nested non-null wrappers can make the whole data result null. On inputs, non-null usually makes a value mandatory, subject to defaults. Choose it from guarantees the service can actually maintain, including permission and dependency failures.

#### 7. What are arguments in GraphQL?

Arguments parameterize fields, for example `posts(first: 20, after: $cursor)`. The schema declares their types and defaults; variables separate values from operation text. Input coercion catches type mismatches, but a valid integer can still be too large. Apply business bounds and permission policy in the authoritative execution/storage path and include semantic arguments in cache identity.

For mutually exclusive lookup choices, a `@oneOf` input object can require exactly one non-null alternative. It validates input shape, not whether the caller may access the selected object.

#### 8. What is introspection?

Introspection exposes schema metadata through GraphQL's built-in schema fields. Tooling uses it for documentation and discovery. A public service may restrict it while offering trusted tooling access, but hiding the schema does not authorize known operations or prevent expensive queries. Protect resources and bound work independently; federation or build tooling may require its own controlled access.

#### 9. What is the difference between `[String]` and `[String!]`?

Both lists are nullable. `[String]` permits null elements, while `[String!]` requires every element to be non-null. Returning an invalid null element in the second case raises an error and nulls the list, because the list itself is nullable. `[String!]!` also requires the list and can propagate a failure farther outward. An empty list is valid for all these forms.

#### 10. What is a fragment?

A fragment names a reusable selection on a type; an inline fragment narrows selections for an interface or union variant. Fragments organize documents but do not create extra independent requests or authorize fields. Validation rejects invalid spreads and cycles. Cost analysis must expand fragment usage correctly, while generated fragment masking controls component-level type access rather than server visibility.

## Execution and implementation

#### 11. What is the N+1 problem in GraphQL?

Loading a collection once, then fetching a relationship separately for every item, creates N+1 storage calls. Twenty posts can yield one post query plus twenty author queries. Batch compatible author IDs or use a deliberate join/projection, while preserving permission scope. Measure calls and actual latency; batching does not fix unbounded lists, missing indexes or expensive nested aggregates.

#### 12. What is DataLoader?

DataLoader collects compatible loads into a batch and memoizes promises within its configured lifetime. The batch result must match input key order and length, even if storage returns rows differently or omits some. Return null or a per-key Error deliberately. Create loaders per identity/request, bound batch sizes and clear relevant entries after writes; global caches can leak tenant data.

#### 13. How do you implement pagination in GraphQL?

Offset pagination is simple but can become costly and drift under inserts. Cursor pagination follows a stable order with a unique tie-breaker; a connection can expose edges/cursors and page information. Bind cursors to tenant, filter and sort, validate them, and cap page size. A timestamp alone is ambiguous when rows share it. Define forward/backward behavior and total-count cost explicitly.

#### 14. What are Input types?

Input object types define structured values accepted by arguments, for example a CreatePostInput containing a title and client mutation identifier. They cannot contain output-only relationships or resolver behavior. Distinguish omitted fields from explicit null when updating data. Input shape validation still needs length bounds, resource authorization, domain invariants and transaction handling.

#### 15. How do you handle errors in GraphQL?

Separate parse/validation failures from execution failures and expected business outcomes. Execution can return useful data alongside errors with response paths. Nullability determines how far a failed field removes data. Publish safe messages/codes, protect internal diagnostics, and monitor GraphQL error rates alongside HTTP status. Do not swallow dependency failures into empty lists or expose raw database exceptions.

#### 16. What is schema-first vs code-first?

Schema-first treats maintained SDL as the contract and binds resolvers to it. Code-first derives the executable schema from language declarations or decorators. Both require generated artifacts, operation validation and compatibility review. Choose one authoritative owner and inspect the emitted schema; decorators or generation do not automatically prove nullability, authorization or compatibility with deployed clients.

#### 17. What are Enums in GraphQL?

Enums define a closed set of named values in the schema and constrain inputs/outputs to those values. Use them for stable domain states rather than user-generated labels. Adding a value can break clients that use exhaustive switches, even if existing operations remain valid. Handle unknown future values where appropriate and review removals, renames and semantic changes with client owners.

#### 18. What are Interfaces and Unions?

An interface declares shared fields implemented by several object types; a union declares alternatives without shared selectable fields beyond built-ins. Clients use inline fragments to select variant fields. Runtime resolution must identify the actual object type through reliable __typename, isTypeOf or resolveType behavior. Do not guess from optional fields; schema evolution and permissions can make those heuristics ambiguous.

#### 19. How do you handle file uploads in GraphQL?

Prefer an authorized upload-intent operation that issues a bounded object-storage upload target, followed by completion validation. This separates large binary transfer from GraphQL execution. Multipart uploads require explicit compatible middleware, CSRF protection, stream/count/size limits, safe names and cleanup. Never concatenate a client filename into a filesystem path. Scan or quarantine content according to the application's requirements.

#### 20. What is the `__typename` field?

`__typename` returns the runtime object type name. Clients use it to distinguish union/interface variants and combine it with stable key fields for normalized identity. It is not a user ID or authorization signal. Apollo typically adds it to selections, but the selected entity key must still be present and unique within the cache's intended tenant/principal scope.

## Architecture and ownership

#### 21. How would you design a schema for a multi-tenant SaaS?

Start with a verified principal and tenant memberships. Derive active tenant access from those memberships, then scope direct lookups, relationships, loaders, mutation targets and cache keys consistently. Use globally unique IDs or explicit tenant-aware identity where needed. Test alternate paths and aggregate leakage. A client-provided tenant header is a requested context, not evidence of permission.

#### 22. Explain your approach to schema governance.

Assign field/domain owners and identify the authoritative schema artifact. Validate client operations, compare contract versions and review breaking/dangerous changes with supported consumers. Deprecate with migration guidance and usage evidence before removal. Include semantic changes, scalar behavior and authorization in review because SDL diffs cannot detect them. Deploy additive server changes before dependent clients and retain old contracts during migration.

#### 23. How do you handle real-time collaboration with GraphQL?

Use subscriptions or another event transport to notify authorized clients, but design collaboration consistency separately. A CRDT or operational-transform protocol needs operation identity, ordering/convergence and recovery. Authenticate connections and recheck event visibility; bound queues and reconnect replay. Shared pub/sub fans out events across instances but is not durable history or proof that clients converged.

#### 24. How would you migrate a REST API to GraphQL?

Introduce GraphQL where client composition provides measurable value, initially wrapping selected existing domain services. Preserve authoritative policy and avoid one REST call per nested field; batch or aggregate deliberately. Support old REST clients during migration, measure workload and compare behavior. Do not claim a past GraphQL evaluation without evidence; present the proposed decision and its validation criteria honestly.

#### 25. Design a schema for a social media feed.

Model Post, Author and a bounded feed connection with stable edge cursors. Decide whose feed is visible, how ranking changes interact with cursors and whether a snapshot boundary is needed. Batch author/media access and cap nested comments. Mutations return changed entities and defined outcomes; clients must update or refresh affected list membership. Separate counts and expensive ranking work from the basic feed path.

#### 26. How do you optimize GraphQL for mobile clients?

Use focused operations that fetch the mobile screen's needed data, stable entity keys and bounded pagination. Persisted query negotiation can reduce text transfer; it does not restrict accepted operations unless backed by an enforced trusted manifest. Account for unreliable networks, retry-safe mutations and old app versions. Measure payload, latency and energy impacts instead of assuming selected fields guarantee efficiency.

#### 27. How do you implement GraphQL in microservices?

Use federation or a gateway when domain-owned services need a coherent client graph, with reviewed composition and explicit entity ownership. Secure router-to-subgraph identity and preserve resource policy. Bound cross-service fan-out, timeouts and failure propagation. A single public endpoint does not remove network hops or transactions across services; distributed workflows still need domain consistency and recovery decisions.

#### 28. How do you handle GraphQL in serverless environments?

Use the platform's maintained integration instead of starting a local HTTP listener inside a handler. Reuse safe pools/clients across warm invocations while keeping identity and loaders scoped per request. Bound concurrency, account for cold starts and align dependency deadlines with the platform limit. Long-lived WebSockets need a suitable separate service or platform capability; function execution does not supply subscription durability.

#### 29. Design a monitoring system for GraphQL.

Track bounded operation identity, duration, estimated/actual workload signals, execution errors, admission rejections, storage calls and cache behavior. HTTP 200 can still contain GraphQL errors, so transport metrics alone miss failures. Avoid raw variables and credentials; restrict sensitive traces. Alert on user-visible error/latency objectives and dependency saturation, then correlate a request with its downstream work.

#### 30. How do you secure a GraphQL API?

Verify identity, apply resource/tenant policy on every access path, constrain variables and documents, and cap concurrency/dependency time. Keep safe error boundaries and scoped caches. Protect cookie-based requests against CSRF and understand that CORS only affects browsers. Introspection restrictions and APQ are separate controls. Test aliases, nested relationships, batches and stale permissions rather than securing only the top-level query.

## Domain design exercises

#### 31. Design a GraphQL API for a ride-sharing service (like Uber).

Define rider/driver/trip visibility and a state machine for requested, accepted, ongoing and completed trips. Location streams need throttling, freshness and access control; GraphQL is a contract/notification layer, not dispatch optimization. Make booking/payment commands idempotent and handle concurrent acceptance with authoritative transactions. Use bounded nearby-driver search and explicit event replay/privacy rules for reconnecting clients.

#### 32. How would you handle GraphQL at scale (10M+ requests/day)?

Translate daily volume into peak operation mix and concurrency; ten million requests a day is not a sufficient capacity model. Measure representative costs, database fan-out and cache misses. Bound expensive operations and tenant concurrency, use appropriate indexes/pools and scale stateless execution with shared admission accounting. Test overload and recovery; response caching and federation add scope and failure boundaries rather than free capacity.

#### 33. Design a real-time collaborative document editor with GraphQL.

Separate document metadata APIs from the collaboration operation protocol. Define CRDT/OT semantics, operation IDs, persistence checkpoints and replay. Authenticate each document subscription and recheck revocation; bound per-client queues and provide resynchronization after gaps. Multiple GraphQL subscription events alone do not guarantee ordered delivery, durable replay, offline merge or convergence among editors.

#### 34. How would you implement a GraphQL API for a financial system?

Represent monetary amounts with explicit currency and precise minor-unit/decimal semantics, not floating-point arithmetic. Keep ledger invariants in authoritative transactions and make commands idempotent. Separate pending, posted and failed outcomes, require resource permissions and retain audit evidence. GraphQL shapes results; serial mutation fields do not create a ledger transaction, exactly-once effects or compliance guarantees.

#### 35. Design a GraphQL API for a content management system.

Model content identity, revisions, publication state and role-specific visibility before designing fields. Draft and published representations need distinct permission/cache policies. Use optimistic concurrency for edits, explicit publication workflows and bounded media references. Cursor pagination and search filters need stable contracts; schema flexibility should not turn arbitrary user-defined content into unvalidated JSON consumed as a trusted client type.

#### 36. How do you handle GraphQL in a micro-frontends architecture?

Give each frontend domain ownership of operations/fragments against a shared governed schema. Decide whether a cache/client instance is intentionally shared; duplicate independent caches can diverge, while sharing private state across identities is unsafe. Align library versions and error/loading conventions. Validate all consumers in CI and deploy additive server changes before separately released frontend modules require them.

#### 37. Design a GraphQL API for a multiplayer game.

GraphQL can expose accounts, inventory, matchmaking and turn-based commands. A fast action game's authoritative simulation often needs a dedicated low-latency protocol rather than per-frame GraphQL mutations. Validate ownership and game rules on the server, make relevant commands replay-safe and bound event streams. Design ordering, anti-cheat checks, reconnect and recovery separately from the API schema.

#### 38. How would you implement GraphQL search with relevance scoring?

Use an explicit search input with bounded query length, filters, sort and pagination, backed by a search engine or indexed storage plan. Relevance scores depend on the query/index and may not define stable pagination across updates; include a tie-breaker or snapshot/search-after policy. Apply visibility filtering in the search path and avoid exposing inaccessible hit counts or snippets.

#### 39. Design a GraphQL API for IoT device management.

Separate device identity, fleet ownership, telemetry ingestion and management commands. High-volume telemetry may use a dedicated ingestion protocol while GraphQL serves bounded state/history views. Commands need authorization, expiry, idempotency and acknowledgment semantics; API acceptance is not device execution. Handle offline devices, firmware compatibility and stale state explicitly, with scoped subscriptions rather than unbounded raw telemetry streams.

#### 40. How do you implement GraphQL API versioning?

Prefer additive schema evolution and deprecation with measured consumer migration. Removing fields or tightening input requirements can break deployed clients; enum and semantic changes also need review. A versioned endpoint can be justified for a major incompatible contract but does not replace supported-client planning. Persisted manifests, custom scalars and federated ownership must evolve with the same compatibility window.

## Failure boundaries and judgment

#### 41. What happens when a resolver returns null for a non-null field?

The engine records an execution error and propagates null outward to the nearest nullable position. If a non-null field belongs to a non-null list element inside a non-null list, the failure can null the root data result. Test the actual schema wrappers and response path; simply throwing from a unit-tested resolver does not demonstrate the completed GraphQL response.

#### 42. How do you test GraphQL resolvers?

Unit-test domain policy and resolver inputs, then execute representative documents against the actual schema to test coercion, null propagation, aliases and batching. Verify ordered loader results, missing keys and cross-tenant isolation. Add HTTP integration tests for credentials, malformed and oversized bodies, safe parser errors and transport behavior. executeOperation with supplied context does not run Express authentication middleware; mocks alone cannot prove storage query plans.

#### 43. What is the difference between `@skip` and `@include`?

Both are built-in conditional selection directives whose if argument is Boolean!. skip omits a selection when true; include keeps it when true. If both occur, the selection must satisfy both conditions. They change whether a field is executed but do not authorize it. Cost analysis must account for effective variables/defaults and must not confuse these executable directives with custom schema metadata.

#### 44. How do you handle batch mutations?

Define whether the batch is atomic, partially successful or asynchronous, then expose per-item identity and outcomes accordingly. Bound item count and authorize every target. A list input or multiple serial top-level mutation fields does not create a database transaction. Use domain transactions for atomic changes and idempotency/recovery for retries or distributed effects; return errors without hiding partial committed work.

#### 45. What is the purpose of the `info` argument?

info describes the current field's schema type, AST nodes, response path, operation and related execution details. It can support tracing or selection-aware projections. Fragments, aliases and directives make naïve AST inspection incomplete, and required policy/identity columns may not be selected. Use a tested helper and avoid coupling storage security to a client's requested projection.

#### 46. How do you handle GraphQL in a monorepo?

Keep one authoritative schema and define ownership of generated server/client artifacts. Each package validates its own operations against the intended schema and compiles generated consumers. Cache generation using schema, document and tool-version inputs. Avoid importing server implementation types as client result types. Contract and deployment checks must cover supported independently released clients, not just packages built in one commit.

#### 47. What are the trade-offs of GraphQL over REST?

GraphQL offers client-selected composition and a typed discoverable contract, but adds field-level execution, variable-dependent workload control and more complex cache/authorization paths. REST can provide simple resource routes, direct HTTP semantics and efficient tailored endpoints. Both require good data access and policy. Choose based on concrete client/access patterns, operational ownership and measured cost rather than a blanket protocol preference.

#### 48. How do you implement GraphQL in Next.js?

Use a browser Apollo Client integration for interactive queries and a request-scoped server client or direct domain/API call for server rendering as appropriate. Keep credentials and private caches isolated per request. Match Next.js runtime capabilities and current route/component APIs, and separate server-only secrets from browser bundles. GraphQL does not bypass framework caching, hydration, error or deployment boundaries.

#### 49. How do you monitor GraphQL in production?

Monitor transport and GraphQL execution separately, then join them through a request identifier and bounded operation signature. Measure latency distributions, dependency time, storage calls, cache hit/miss behavior, cost and admission rejections. Avoid unbounded client operation names and sensitive argument collection. Alert on user-visible objectives and saturation; a healthy process or HTTP 200 rate alone cannot establish correct service behavior.

#### 50. How do you evaluate whether to adopt a new GraphQL capability?

Start with the problem and the expected behavior change. Check whether the feature is standardized or still proposed, then verify the exact server, client and transport support. Review its authorization, cache, cost, observability and recovery effects; trial it against representative operations and define rollback evidence. Adopt it only when the measured result improves the system's stated objective.

## Summary

A strong GraphQL answer connects the schema contract to authorized data access, bounded execution and consumer compatibility. Design exercises require domain invariants and recovery, not just an SDL sketch. Treat generated types, normalized caches, serial mutations and persisted-query negotiation according to their actual limits.

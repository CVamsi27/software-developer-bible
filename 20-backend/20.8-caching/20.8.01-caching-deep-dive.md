# Caching Deep-Dive — Redis, Strategies, Invalidation, Patterns


---

## Definition

A **cache** retains a value so later requests can reuse it instead of repeating a source read or computation. For example, a product page can reuse a stored product representation until its freshness policy requires a reload. The cache must identify which requests may share that value and when serving it is still acceptable.

> **Textbook Definition:** Caching stores reusable representations closer to consumers under a defined freshness and invalidation contract. Correctness depends on cache identity, version selection and failure behavior as well as entry lifetime.

```text
client → CDN → service → in-process → distributed (Redis) → database
         edge   route     local           network           authority
        ▲                       each layer has its own: hit ratio, TTL, invalidation
```

Four questions define any cache, and every layer answers them differently:

1. **What is the key?** The cache key is a contract: it must include every input that changes the response (tenant, user, locale, feature flags, API version) and nothing that does not. Missing an input leaks data across tenants; including a unique request id prevents reuse; session-scoped entries can still have hits.
2. **How long is a value valid?** TTL bounds an installed entry's lifetime under its expiry policy. It does not by itself bound source-data age: a delayed loader, lagging replica or lower cache layer can provide old data just before a new TTL starts. Derive the TTL together with those delays, refresh and permitted stale-serving paths; require authoritative validation when the operation cannot accept that uncertainty.
3. **How is it invalidated?** Three mechanisms with different guarantees — TTL (eventually, no coordination), explicit purge after a committed write (a racing reader can still refill old data), and **versioned keys** (readers select a namespace/version; old entries expire). Versioning avoids deleting each old key, but the version must be coordinated with the source write and read snapshot to guarantee freshness.
4. **What happens on a miss under load?** A normal miss is expected. Many simultaneous misses for one key cause a **stampede**, while a very popular key can exceed one cache shard's capacity even when every request hits. Coalesce duplicate loads and bound source work; distribute hot reads only under an acceptable freshness contract. Negative caching stores an allowed not-found result, not an arbitrary timeout or authorization failure.

**Hit ratio** is the fraction of lookups that reuse an entry; evaluate it together with saved origin cost, payload size and hit/miss latency. **Memoization** caches a function's result by its inputs and needs the same identity and lifetime reasoning. A disposable read cache may fall back to its source with bounded concurrency and load shedding. A store used for authoritative sessions, locks or quotas needs a different failure policy: bypassing it may violate the rule it enforces.

## First Principles

Caching is deducible from one asymmetry:

1. **Reading is repeated; computing is expensive.** Any computation whose inputs change slowly can have its answer stored and reused — the entire justification. Everything else (hit ratio, invalidation, stampedes) is managing the consequences of that storage.
2. **The cache is a copy, so staleness is structural.** A cached value is a second copy that may diverge when the source changes — TTLs, invalidation, and versioning are all strategies for bounding *how wrong* the copy may be. The senior question is always "how stale can this be, per field?" — a product answer that determines TTLs.
3. **Two failure modes follow from popularity skew**: hot keys (one entry concentrates traffic — may need a local copy or distributed reads with explicit freshness) and cache misses under churn (stampede — needs locking or early recomputation). An empty cache must have a survivable policy: bound origin work, shed excess load or serve an allowed stale value. Do not assume the database can absorb full peak traffic.

## Caching Hierarchy

| Layer | Example | Latency | Use Case |
| --------------------- | ------------------------- | ------------------------------------- | ------------------------------------ |
| **Browser cache** | HTTP Cache-Control | Local lookup; disk/memory dependent | Static assets |
| **CDN** | CloudFront, Cloudflare | Network and location dependent | Global static + edge compute |
| **Application cache** | In-memory (Node.js) | Process lookup and serialization cost | Hot data, L1 cache |
| **Distributed cache** | Redis, Memcached | Network, payload and load dependent | Shared state, sessions |
| **Database cache** | PostgreSQL shared buffers | Workload-dependent | Cached disk pages, not query results |

## Cache Patterns

The complete model below is executable on its own. Later TypeScript snippets illustrate sequencing with injected `redis`, `prisma`, DTOs and trusted identifiers; they are not complete application integrations.

### Cache-aside with one complete local trace

The application reads a reusable copy first. On a miss, it reads the authority and stores a copy. This dependency-injected JavaScript model has bounded entry/in-flight counts, caches null distinctly, coalesces identical misses and never treats a rejected source read as a completed fill. Call `read` only after verifying the principal and selecting the same tenant-scoped source query. The key must encode every result-changing input.

```javascript
export function createReadCache(load, { ttlMs = 1000, maxKeys = 100, now = Date.now } = {}) {
  if (typeof load !== 'function' || !Number.isFinite(ttlMs) || ttlMs <= 0 ||
      !Number.isSafeInteger(maxKeys) || maxKeys < 1) throw new TypeError('invalid cache');
  const entries = new Map();
  const pending = new Map();
  return {
    async read(key) {
      const time = now();
      const hit = entries.get(key);
      if (hit && hit.expires > time) return hit.value;
      if (hit) entries.delete(key);
      if (pending.has(key)) return pending.get(key);
      if (pending.size >= maxKeys) throw new Error('origin budget exhausted');
      const work = Promise.resolve().then(() => load(key)).then(value => {
        if (entries.size >= maxKeys) entries.delete(entries.keys().next().value);
        entries.set(key, { value, expires: now() + ttlMs });
        return value;
      }).finally(() => pending.delete(key));
      pending.set(key, work);
      return work;
    },
  };
}
```

With `load` counting calls and returning `{ name: 'Ada' }`, two simultaneous reads of the same key cause one load. A third read before expiry reuses it; a read after expiry loads again. Source rejection removes the in-flight entry so another attempt can recover. This model has no invalidation method, stale-on-error policy, distributed coordination or cancellation; `load` must enforce its deadline. It retains object references, so callers must treat results as immutable or explicitly clone them. It is FIFO eviction, not least-recently-used eviction. `maxKeys` limits retained entries and simultaneous source jobs separately; it is not a byte budget. One large result can still consume substantial memory.

A production Redis adapter adds network timeouts and a chosen cache-outage policy. Independent source reads and fills can still race a write: a reader loads version 7, version 8 commits, then the reader fills version 7. TTL alone limits entry lifetime, not source age. Do not infer current permissions from this copy.

### Write-Through

A write-through design keeps the required source/cache update in the foreground write path. This application-managed sketch commits the source first and then warms the cache; it exposes the partial-failure boundary rather than providing an atomic two-store write.
```typescript
async function updateUser(userId: string, data: UpdateUserDto) {
  // 1. Write to database
  const user = await prisma.user.update({ where: { id: userId }, data });

  // 2. Write to cache after the database commit
  await redis.setex(`user:${userId}`, 300, JSON.stringify(user));
  return user;
}
```
**Pros:** Successful writes warm the cache for subsequent reads.
**Boundary:** Two separate writes are not atomic; a cache failure after DB commit or an older concurrent writer can leave a stale value. Reconcile failures and use source versions/conditional updates when ordering matters.
**Cons:** Write latency includes cache write, unused data cached

### Write-Behind (Write-Back)
```typescript
async function updateUser(userId: string, data: UpdateUserDto) {
  // 1. Write to cache immediately
  await redis.setex(`user:${userId}`, 300, JSON.stringify(data));

  // 2. In-memory queue sketch; a process crash loses this pending write
  writeQueue.push({ userId, data, timestamp: Date.now() });
  return data; // Returns before DB write
}
```
**Pros:** Can reduce foreground write latency and batch origin writes.
**Cons:** The sketch loses acknowledged writes on process failure. A durable write-behind design needs durable intent, ordered replay and an explicit acknowledgment contract; it is not simply a faster read cache.

## Cache Invalidation Strategies

### Time-Based (TTL)
```typescript
// Simple TTL
await redis.setex(`user:${userId}`, 300, data); // 5 minutes

// Jittered TTL spreads expirations across keys; one hot key can still stampede
const jitter = Math.floor(Math.random() * 60); // 0–59 seconds
await redis.setex(`user:${userId}`, 300 + jitter, data);
```

### Event-Based Invalidation

A committed write deletes the old copy and can notify other processes. A reader already loading an older source version can still fill the key after the deletion:

```text
reader loads v7 → writer commits v8 → writer deletes key → reader stores v7
```

Every command succeeded, yet the next cache hit is old. A source-coordinated version/conditional-fill design can reject that refill; otherwise state the remaining stale window. Redis Pub/Sub is an ephemeral hint, so disconnected processes also need expiry, validation or replayable change delivery.
```typescript
// On user update
async function updateUser(userId: string, data: UpdateUserDto) {
  const user = await prisma.user.update({ where: { id: userId }, data });

  // Invalidate cache
  await redis.del(`user:${userId}`);

  // Also invalidate related caches
  await redis.del(`user:${userId}:profile`);
  await redis.del(`clinic:${user.clinicId}:users`);

  // Publish an ephemeral hint; a disconnected subscriber misses it
  await redis.publish('cache-invalidation', JSON.stringify({
    type: 'user',
    id: userId,
    clinicId: user.clinicId
  }));
}
```

### Version-Based Invalidation

A namespace version can retire a serializer's old entries without scanning them. This sketch changes which namespace readers use; it does not coordinate a row update with the version read or prevent an old snapshot filling a new key. A missing version also needs an initialization policy.
```typescript
// Prefix cache key with version
const version = await redis.get('cache-version:user');
const key = `user:v${version}:${userId}`;
await redis.setex(key, 300, data);

// On breaking change, increment version
await redis.incr('cache-version:user');
```

## Cache Stampede Prevention

### Coalesce misses before adding a distributed lease

Within one process, keep a map of in-flight promises keyed by cache key so concurrent readers await the same fetch. Across processes, a Redis lease can reduce duplicate work, but expiry or failover permits overlapping refreshes. Use a random owner token and atomic compare-and-delete release; bound the waiting time and database fallback concurrency. See [Redis lease mechanics](20.8.02-redis-fundamentals.md#expiring-session-and-owner-token-lease) rather than maintaining a second lock implementation here. A lease alone does not prevent a stale holder from overwriting fresh data.

### Probabilistic Early Expiration

This illustrative heuristic assumes a positive TTL in seconds and a millisecond refresh timestamp. It increases refresh probability near expiry; combine it with single-flight and handle background failures. It is not a guarantee against stampedes.
```typescript
function shouldRefresh(ttl: number, lastRefresh: number): boolean {
  const elapsed = Date.now() - lastRefresh;
  const remaining = ttl - elapsed / 1000;
  // Higher probability as TTL approaches
  return remaining <= 0 || Math.random() < Math.min(1, 1 / remaining);
}
```

## Multi-Tenant Cache Invalidation

Tenant id must come from the authenticated context. Include it in every key and in the source query; key prefixes alone do not enforce authorization.

```typescript
async function invalidateTenantCache(tenantId: string) {
  const stream = redis.scanStream({ match: `tenant:${tenantId}:*`, count: 100 });
  for await (const keys of stream) {
    if (keys.length) await redis.unlink(...keys);
  }
}
```

This ioredis example bounds each deletion batch and avoids building an unbounded pipeline. SCAN can return duplicates and observes a changing keyspace; concurrent writers may recreate entries during the pass. Use source-coordinated version namespaces if the contract requires old entries to become unreachable at once. Escape glob metacharacters if tenant identifiers are not restricted opaque ids; cluster scans must cover each primary.

## Redis Data Structures for Caching

| Structure | Use Case | Command |
| -------------- | ---------------------------------------------------------------------------- | --------------------------------- |
| **String** | Simple key-value, sessions | `SET`, `GET`, `SETEX` |
| **Hash** | Object fields, user profiles | `HSET`, `HGET`, `HGETALL` |
| **List** | Queues, activity feeds | `LPUSH`, `RPOP`, `LRANGE` |
| **Set** | Tags, unique items, membership | `SADD`, `SMEMBERS`, `SINTER` |
| **Sorted Set** | Leaderboards, time-series | `ZADD`, `ZRANGE`, `ZRANGEBYSCORE` |
| **Stream** | Append-only message delivery; retention and durability require configuration | `XADD`, `XREAD`, `XRANGE` |

### Practical Examples
```typescript
// User session (Hash)
await redis.hset(`session:${sessionId}`, {
  userId: user.id,
  clinicId: user.clinicId,
  role: user.role,
  lastActivity: Date.now()
});
await redis.expire(`session:${sessionId}`, 3600); // example policy, not universal

// Atomic rate limiting is developed once in Advanced Redis Patterns.
// Separate commands (remove → count → add) allow concurrent requests to overshoot.


// Presence tracking (Set)
await redis.sadd(`online:clinic:${clinicId}`, userId);
await redis.srem(`online:clinic:${clinicId}`, userId);
const onlineUsers = await redis.smembers(`online:clinic:${clinicId}`);
// Set membership does not expire per user. Heartbeats and reconciliation must remove stale presence.
```

---

The session hash write and expiry are separate commands: failure between them can leave a key without the intended expiry. An atomic script or transaction can close that local command boundary; authentication, rotation, revocation and recovery still belong to the [session chapter](../20.5-security/01-auth/20.5.1.04-sessions-cookies.md). Redis atomicity does not by itself guarantee durability across failure.

## Check Your Design

Write down the stale-read budget, source-of-truth boundary, cache failure policy, and worst-case load on a cold miss. Those four decisions make the choice of keys, TTLs, and refresh coordination concrete.
---
## Summary

A useful cache reuses the correct result for the correct caller while meeting an explicit freshness and failure policy. Entry TTL, source-data age, capacity eviction and invalidation are different controls. Trace delayed fills, concurrent writes, lost notifications and cold misses; then choose coordination, source fallback and load limits for the operation's required result.

# Redis for Backend Engineers

>
> **Why it matters:** Redis appears in almost every system design interview. It's the go-to solution for caching, rate limiting, leaderboards, session storage, and pub/sub messaging.

## Definition

Redis (Remote Dictionary Server) is an open-source, in-memory data structure store that can be used as a database, cache, message broker, and session store. It supports atomic operations on data structures like strings, hashes, lists, sets, and sorted sets.

> **Textbook Definition:** Redis is a data structure server supporting commands over keys and structured values. Atomic command execution, expiration, persistence and replication are distinct mechanisms with different failure and durability guarantees.

Redis is single-threaded (for command execution), which eliminates the need for locking and simplifies atomicity. It achieves high performance through:
- All data in memory (no disk I/O for reads)
- Efficient data structures (optimized C implementations)
- Serialized command execution; I/O and persistence may use other threads/processes

## First Principles

Redis is derivable from one design decision and its consequences:

1. **Data lives in memory.** That choice reduces read latency while making memory capacity and recovery from volatile-state loss explicit design constraints. Every Redis feature — eviction policies, RDB/AOF persistence, replication — is an answer to one of those two costs.
2. **Single-threaded command execution is a feature.** No locks, no races on individual commands — which makes INCR, SETNX, and friends atomic by definition and turns Redis into a building block for distributed primitives (locks, rate limiters, counters). The corollary: one slow command (KEYS, big values) blocks *everyone* — hence UNLINK, SCAN, and size discipline.
3. **It's a data-structure server, not a key-value dump.** Lists, sets, sorted sets, streams each exist because the *operation* (leaderboard, queue, membership) defines the structure — choosing the right one is where Redis skill lives.

## Why Do We Need It?

| Problem | Redis Solution |
| ----------------------- | ----------------------------------------------------------- |
| **Database load** | Cache frequently accessed data in Redis |
| **Session management** | Store sessions with automatic expiration |
| **Rate limiting** | Atomic counters with INCR + EXPIRE |
| **Real-time analytics** | Sorted sets for leaderboards, HyperLogLog for unique counts |
| **Message queuing** | Lists for simple queues, Streams for durable messaging |
| **Distributed locks** | SET NX for simple locking, Redlock for distributed |

## Code Examples

### 1. Basic Redis Operations (Node.js)

```typescript
import Redis from 'ioredis';

const redis = new Redis({
  host: 'localhost',
  port: 6379,
  password: process.env.REDIS_PASSWORD,
  db: 0,
});

// String operations
await redis.set('user:123:name', 'Alice');
await redis.get('user:123:name'); // 'Alice'

// Atomic counter (rate limiting, page views)
await redis.incr('page_views:homepage');
await redis.incrby('page_views:homepage', 10);

// Expiration (auto-delete after TTL)
await redis.set('session:abc123', 'user_data', 'EX', 3600); // 1 hour

// Hash operations (user profiles)
await redis.hset('user:123', {
  name: 'Alice',
  email: 'alice@example.com',
  age: '30',
});
const user = await redis.hgetall('user:123');
// { name: 'Alice', email: 'alice@example.com', age: '30' }

// List operations (task queue)
await redis.lpush('tasks', 'task1', 'task2', 'task3');
const task = await redis.rpop('tasks'); // 'task1' (FIFO: first argument inserted first)

// Set operations (tags, categories)
await redis.sadd('tags:post:1', 'javascript', 'react', 'nodejs');
const tags = await redis.smembers('tags:post:1'); // same members; order is unspecified

// Sorted set operations (leaderboard)
await redis.zadd('leaderboard', 1500, 'user1', 2300, 'user2', 1800, 'user3');
const top3 = await redis.zrevrange('leaderboard', 0, 2, 'WITHSCORES');
// ['user2', '2300', 'user3', '1800', 'user1', '1500']
```

### 2. Choose a cache contract before choosing commands

The [Caching Deep-Dive](20.8.01-caching-deep-dive.md) owns cache-aside, write-through, write-behind, invalidation races, and stampede prevention. Redis supplies GET/SET and TTLs; it does not make separate database/cache writes atomic. Keep a missing row distinct from a Redis error and choose whether absence is negatively cached.

### 3. Atomic rate limits

A pipeline batches round trips; it does not isolate a read-modify-write decision from other clients. The [Lua token bucket](20.8.03-advanced-redis-patterns.md#2-rate-limiting-with-lua-scripts) performs refill, admission, update, and expiry in one server-side operation.

### 4. Distributed Lock

```typescript
// Simple distributed lock using Redis
async function acquireLock(
  resource: string,
  ttlMs: number = 10000
): Promise<string | null> {
  const lockValue = crypto.randomUUID(); // import from node:crypto
  const acquired = await redis.set(
    `lock:${resource}`,
    lockValue,
    'PX', // milliseconds
    ttlMs,
    'NX' // Only if not exists
  );
  return acquired ? lockValue : null;
}

async function releaseLock(resource: string, lockValue: string): Promise<boolean> {
  // Use Lua script for atomic check-and-delete
  const script = `
    if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
    else
      return 0
    end
  `;
  const result = await redis.eval(script, 1, `lock:${resource}`, lockValue);
  return result === 1;
}

// Usage
const lockValue = await acquireLock('user:123:profile');
if (lockValue) {
  try {
    // Critical section
    await updateUserProfile(userId, data);
  } finally {
    await releaseLock('user:123:profile', lockValue);
  }
}
```

This is a lease, not an enduring ownership guarantee: a paused process may continue after expiry, and asynchronous replication can lose an acquired lock during failover. Protect correctness with database constraints/transactions or resource-enforced fencing; use the lease only to reduce duplicate work unless those failure cases are addressed.

### 5. Pub/Sub Messaging

```typescript
// Publisher
async function publishEvent(channel: string, data: any): Promise<void> {
  await redis.publish(channel, JSON.stringify(data));
}

// Subscriber
const subscriber = redis.duplicate();
await subscriber.subscribe('user:created');

subscriber.on('message', (channel, message) => {
  console.log(`Received from ${channel}:`, JSON.parse(message));
  // Handle event: send welcome email, update analytics, etc.
});

// Usage
await publishEvent('user:created', { userId: '123', email: 'alice@example.com' });
```

### 6. Leaderboard with Sorted Sets

```typescript
// Update user score
async function updateScore(userId: string, score: number): Promise<void> {
  await redis.zadd('leaderboard', score.toString(), userId);
}

// Get top N users
async function getTopUsers(n: number): Promise<Array<{ userId: string; score: number }>> {
  const results = await redis.zrevrange('leaderboard', 0, n - 1, 'WITHSCORES');

  const topUsers = [];
  for (let i = 0; i < results.length; i += 2) {
    topUsers.push({
      userId: results[i],
      score: Number(results[i + 1]),
    });
  }
  return topUsers;
}

// Get user rank
async function getUserRank(userId: string): Promise<number | null> {
  const rank = await redis.zrevrank('leaderboard', userId);
  return rank !== null ? rank + 1 : null; // 0-indexed, so +1
}

// Get users in score range
async function getUsersInRange(min: number, max: number): Promise<string[]> {
  return redis.zrangebyscore('leaderboard', min, max);
}
```

## Real-World Use Cases

### 1. Session Store

```typescript
// Store session with automatic expiration
async function createSession(sessionId: string, userData: any): Promise<void> {
  await redis.set(
    `session:${sessionId}`,
    JSON.stringify(userData),
    'EX',
    86400 // 24 hours
  );
}

// Get session
async function getSession(sessionId: string): Promise<any> {
  const data = await redis.get(`session:${sessionId}`);
  return data ? JSON.parse(data) : null;
}

// Destroy session
async function destroySession(sessionId: string): Promise<void> {
  await redis.del(`session:${sessionId}`);
}
```

### 2. Real-Time Analytics

```typescript
// Track page views with HyperLogLog (unique visitors)
async function trackPageView(page: string, userId: string): Promise<void> {
  await redis.pfadd(`pageviews:${page}`, userId);
}

async function getUniquePageViews(page: string): Promise<number> {
  return redis.pfcount(`pageviews:${page}`);
}

// Track time series data with Sorted Sets
async function trackMetric(metric: string, value: number): Promise<void> {
  const timestamp = Date.now();
  await redis.zadd(`metrics:${metric}`, timestamp.toString(), `${timestamp}:${value}`);
}

async function getRecentMetrics(metric: string, lastMs: number): Promise<number[]> {
  const min = Date.now() - lastMs;
  const results = await redis.zrangebyscore(`metrics:${metric}`, min, '+inf');
  return results.map(r => parseFloat(r.split(':')[1]));
}
```

### 3. Job Queue

This RPOP example removes work before processing; a crash or sendEmail failure loses that job. Use a pending/acknowledgment design or [Streams consumer groups](20.8.03-advanced-redis-patterns.md#4-redis-streams-with-consumer-groups) for recoverable work.

```typescript
// Simple job queue using Redis Lists
async function addJob(jobType: string, payload: any): Promise<void> {
  await redis.lpush(`queue:${jobType}`, JSON.stringify(payload));
}

async function processNextJob(jobType: string): Promise<any | null> {
  const data = await redis.rpop(`queue:${jobType}`);
  return data ? JSON.parse(data) : null;
}

// Worker loop
async function worker() {
  while (true) {
    const job = await processNextJob('email');
    if (job) {
      await sendEmail(job.to, job.subject, job.body);
    } else {
      await new Promise(resolve => setTimeout(resolve, 1000)); // Wait 1s if empty
    }
  }
}
```

## Common Mistakes

### 1. Not Setting TTL (Memory Exhaustion)

```typescript
// Bad: Data never expires
await redis.set('cache:products', JSON.stringify(products));

// Disposable cache entry: set a TTL appropriate to its freshness budget
await redis.set('cache:products', JSON.stringify(products), 'EX', 3600);
```

### 2. Cache Stampede

Many simultaneous misses can send the same query to the origin. Coalesce requests within each process, add a bounded cross-process refresh lease where useful, and tolerate lease expiry. Background refreshes need caught errors and a bounded refresh pool; recursively retrying forever creates a hidden queue. The [cache strategy chapter](20.8.01-caching-deep-dive.md#cache-stampede-prevention) owns the complete failure contract.

### 3. Using KEYS in Production

```typescript
// Bad: KEYS blocks all other commands
const keys = await redis.keys('user:*'); // O(N), blocks everything

// Good: Use SCAN for iteration
async function* scanKeys(pattern: string) {
  let cursor = '0';
  do {
    const [nextCursor, keys] = await redis.scan(cursor, 'MATCH', pattern, 'COUNT', 100);
    cursor = nextCursor;
    yield* keys;
  } while (cursor !== '0');
}

for await (const key of scanKeys('user:*')) {
  console.log(key);
}
```

### 4. Storing Large Objects

```typescript
// Bad: Storing large objects in single key
await redis.set('user:123:full', JSON.stringify(hugeObject)); // > 1MB

// Good: Store in hash, paginate, or use multiple keys
await redis.hset('user:123:profile', {
  name: 'Alice',
  email: 'alice@example.com',
  // ... only frequently accessed fields
});
// Store large data in database, cache only what's needed
```

## Performance Considerations

| Operation | Time Complexity | Use Case |
| ----------- | --------------- | ------------------- |
| GET/SET | O(1) | Simple key-value |
| HGET/HSET | O(1) | Hash fields |
| LPUSH/RPUSH | O(1) | List append |
| LPOP/RPOP | O(1) | List remove |
| SADD | O(1) | Set add |
| ZADD | O(log N) | Sorted set add |
| ZRANGE | O(log N + M) | Range query |
| KEYS | O(N) | Avoid in production |
| SCAN | O(1) per call | Use for iteration |

## Summary

Redis is an essential tool for senior backend engineers. Key takeaways:

1. **Use cases:** Caching, sessions, rate limiting, leaderboards, pub/sub, job queues
2. **Data structures:** Choose the right one (Strings for simple, Hashes for objects, Sorted Sets for ordered data)
3. **Bound memory:** Use TTLs for disposable entries and explicit retention/capacity policies for durable state
4. **Avoid KEYS:** Use SCAN for iteration
5. **Cache patterns:** Choose a freshness/failure contract; write-through alone does not ensure consistency
6. **Distributed leases:** Owner-token release avoids deleting another lease; expiry/failover still need a correctness backstop
7. **Pub/Sub:** Good for real-time events, but not durable (use Streams for durability)

# Redis for Backend Engineers

Redis can hold reusable read copies or authoritative operational state. Start by deciding which role each key family has; the failure policy differs.

## Definition

Redis is an in-memory data-structure server commonly used for low-latency state, caches, coordination and event processing. Redis Open Source 8.10.1 is the latest stable release checked on 13 October 2026. Starting with Redis 8, the source is offered under a choice of AGPLv3, RSALv2 or SSPLv1; these licenses have different obligations, so verify the terms that apply to your distribution and use.

> **Textbook Definition:** Redis is an in-memory data-structure server that executes commands against keys and typed values. Command atomicity, expiration, persistence and replication are separate mechanisms; none alone guarantees that acknowledged application state survives every failure.

Redis uses a mostly single-threaded command-execution model: one command runs at a time on a server process, so another client's command cannot interleave inside it. Redis 8 also adds configurable I/O threads for network throughput. Multiple commands from an application are still separate unless grouped by a transaction, script or function. Large or slow commands can delay other clients.

## First Principles

Three design choices explain Redis's common tradeoffs:

1. **Memory is the working set.** It gives low-latency access, but capacity, eviction and recovery become explicit design choices. RDB snapshots, AOF fsync policy and replication each have different recovery and data-loss windows.
2. **A command is atomic; a workflow is not.** `INCR` is one indivisible command, but a later database write can fail. Use a script, function or transaction for a Redis-local decision; use database constraints or another shared authority for cross-system invariants.
3. **The data structure follows the operation.** Use a sorted set for rank/order, a set for membership, or a stream for retained events with consumer state. Selecting the right type does not remove memory, cardinality or recovery limits.

## Choose Redis for a Workload

| Problem | Redis Solution |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Database load** | Cache frequently accessed data in Redis |
| **Session management** | Store sessions with automatic expiration |
| **Rate limiting** | A single atomic counter/expiry decision; separate INCR + EXPIRE can race |
| **Real-time analytics** | Sorted sets for ranked results; Redis 8 Time Series for numeric measurements; HyperLogLog for approximate cardinality |
| **Message processing** | Lists for simple destructive queues; Streams when retained entries, consumer groups and explicit recovery are required |
| **Distributed locks** | Expiring owner-token leases; resource-enforced invariants remain necessary |

## What a Redis Command Guarantees

### Command, memory and recovery boundaries

```text
client → network/I/O handling → serialized command execution → in-memory data
                                      ├─ RDB snapshots / AOF, if configured
                                      └─ asynchronous replication and failover
```

I/O threads, persistence workers and replicas change throughput or recovery behavior; they do not turn a Redis command sequence and an external database transaction into one atomic unit. Measure latency and failover against the exact server configuration.

### Choose a data type by access pattern

| Type | Use it for | Boundary |
| ------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| String | Bytes, counters, simple values and expiring tokens | A JSON string is opaque; Redis cannot query its fields without JSON support. |
| Hash | A record of string fields with partial reads/writes | An unbounded hash or `HGETALL` can create large replies. |
| List | Ordered sequence, stack or simple queue | A pop removes work before its effect completes; it has no built-in acknowledgment. |
| Set | Unique membership and set operations | It has no ordering contract. |
| Sorted set | Unique members ranked/ranged by numeric score | Score ties need a defined tie rule; updates alter rank. |
| Stream | Retained entries, independent consumer groups and pending-delivery tracking | Retention, consumer recovery and persistence still need configuration. |
| JSON | Structured documents with field-level access and queries | Requires Redis 8 or a compatible earlier module; schema and indexing costs remain. |
| Time Series | Timestamped numeric samples, range queries and retention/aggregation policies | Choose sampling, retention and downsampling policies; it is not a replacement for every analytical store. |
| Probabilistic types | Approximate membership, cardinality, frequency or quantiles | Results trade exactness for bounded memory; choose the structure for the specific query. |
| Vector sets | Vector similarity search | Feature maturity and search semantics are version-sensitive; validate the release before relying on it. |

Redis Open Source 8 integrates Search and the listed data types in its binary distributions. Older servers and managed services may expose a different feature set.

## Node.js Examples

### Connect one application client

The examples use `node-redis` 6.3.0, the current release checked on 13 October 2026, with Redis Open Source 8.10.1. Redis recommends node-redis for new Node.js applications and its migration guide describes ioredis as deprecated in its favor. Examples below share a connected client and use camel-case command names. Configure TLS, ACL credentials, connection deadlines and bounded retry behavior for the deployed environment.

```typescript
import { createClient } from 'redis';
import { randomUUID } from 'node:crypto';

const redis = createClient({ url: process.env.REDIS_URL });
redis.on('error', error => console.error('Redis client error', error));
await redis.connect();

await redis.set('user:123:name', 'Alice');
const name = await redis.get('user:123:name');

await redis.incr('page_views:home');
await redis.incrBy('page_views:home', 10);

await redis.hSet('user:123', { name: 'Alice', age: '30' });
const user = await redis.hGetAll('user:123');

await redis.lPush('tasks', ['task-1', 'task-2']);
const oldest = await redis.rPop('tasks'); // task-1

await redis.sAdd('tags:post:1', ['javascript', 'react']);
const tags = await redis.sMembers('tags:post:1'); // member order is unspecified

await redis.zAdd('leaderboard', [
  { score: 1500, value: 'user-1' },
  { score: 2300, value: 'user-2' },
]);
const top = await redis.zRangeWithScores('leaderboard', 0, 9, { REV: true });
// [{ value: 'user-2', score: 2300 }, { value: 'user-1', score: 1500 }]

```

In a service, create the client during startup and close it with `redis.close()` during graceful shutdown rather than connecting per request. Each later snippet assumes the shared client remains connected. Bound returned ranges and hash sizes; a single command can still produce an unbounded response.

### Expiring session and owner-token lease

A TTL is a maximum idle-independent lifetime only when the application leaves it unchanged; a sliding session must refresh the expiry after the required authenticated activity. Store only the session fields needed by the service, protect Redis with ACLs/TLS as appropriate, and validate decoded data at the trust boundary.

```typescript
interface Session { userId: string; role: string }

async function saveSession(id: string, session: Session): Promise<void> {
  await redis.set(`session:${id}`, JSON.stringify(session), {
    expiration: { type: 'EX', value: 86_400 },
  });
}

function decodeSession(json: string): Session {
  let value: unknown;
  try { value = JSON.parse(json); } catch { throw new Error('invalid cached session JSON'); }
  if (typeof value !== 'object' || value === null ||
      !('userId' in value) || typeof value.userId !== 'string' ||
      !('role' in value) || typeof value.role !== 'string') {
    throw new Error('invalid cached session shape');
  }
  return { userId: value.userId, role: value.role };
}

async function readSession(id: string): Promise<Session | null> {
  const value = await redis.get(`session:${id}`);
  return value === null ? null : decodeSession(value);
}

async function acquireLease(resource: string, ttlMs: number): Promise<string | null> {
  if (!Number.isSafeInteger(ttlMs) || ttlMs < 1) throw new RangeError('invalid TTL');
  const token = randomUUID();
  const result = await redis.set(`lock:${resource}`, token, {
    condition: 'NX',
    expiration: { type: 'PX', value: ttlMs },
  });
  return result === 'OK' ? token : null;
}

const releaseLeaseScript = `
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
  end
  return 0
`;

async function releaseLease(resource: string, token: string): Promise<boolean> {
  const result = await redis.eval(releaseLeaseScript, {
    keys: [`lock:${resource}`],
    arguments: [token],
  });
  return result === 1;
}
```

Compare-and-delete prevents an old holder from deleting a successor's lease. It does not stop a paused holder from resuming after expiry, and an asynchronous failover can lose a recent acquisition. The protected resource still needs an invariant or an ordered fencing token when overlapping work could corrupt data. A Redis lease is often a duplicate-work optimization, not the authority for a business invariant.

### Publish a best-effort notification

Use a dedicated duplicate connection for subscriptions. Subscribe callbacks receive the message and channel; a disconnected subscriber misses messages, so notifications need a refresh/reconciliation path. Never treat a channel name or tenant prefix as authorization.

```typescript
const subscriber = redis.duplicate();
subscriber.on('error', error => console.error('Redis subscriber error', error));
await subscriber.connect();

function isUserCreated(value: unknown): value is { type: 'USER_CREATED'; userId: string } {
  return typeof value === 'object' && value !== null &&
    'type' in value && value.type === 'USER_CREATED' &&
    'userId' in value && typeof value.userId === 'string';
}

await subscriber.subscribe('user:created', (message, channel) => {
  let event: unknown;
  try { event = JSON.parse(message); } catch {
    console.error('Rejected malformed notification');
    return;
  }
  if (!isUserCreated(event)) {
    console.error('Rejected invalid notification shape');
    return;
  }
  // Authorize the recipient before sending the notification to a user or tenant.
  console.log('validated notification', channel, event.userId);
});

await redis.publish('user:created', JSON.stringify({ type: 'USER_CREATED', userId: '123' }));
subscriber.close();
```

Redis Pub/Sub is at-most-once: disconnected consumers do not receive missed messages. Use it for hints such as refresh notifications when consumers can reconcile from an authoritative source. Use Streams or a durable broker when the work must remain pending and recoverable.

### Choose a purpose-built structure for analytics

A sorted set is appropriate for ranked results or a small custom time-ordered index. It is not a general time-series database: retention, duplicate samples, aggregation and downsampling become application work. Redis Open Source 8 integrates Redis Time Series for numeric samples with time-oriented operations; verify that the deployed Redis distribution exposes it before using those commands. HyperLogLog provides approximate distinct counts when exact membership is unnecessary:

```typescript
await redis.pfAdd('visitors:2026-10-11', ['user-1', 'user-2', 'user-3']);
const estimatedUniqueVisitors = await redis.pfCount('visitors:2026-10-11');
```

The estimate is not a list of visitors and cannot answer membership queries. Set an explicit expiry or retention policy for date-partitioned keys.

### Keep cache policy separate from authoritative state

The [Caching Deep-Dive](20.8.01-caching-deep-dive.md) covers cache-aside, write-through, write-behind, invalidation races and stampede prevention. Redis provides storage primitives and TTLs; it does not make a Redis update and a database transaction atomic. Distinguish a missing key from a Redis failure, decide whether absence is negatively cached, and specify what the request does when Redis is unavailable.

For disposable cache data, a memory limit with an eviction policy can be appropriate. For quotas, sessions or coordination state whose eviction changes correctness, use a separate instance or a policy that rejects writes rather than evicting live state, and define the outage/recovery contract.

## Performance and Operations

Redis executes ordinary commands serially on the server. A large reply, unbounded collection operation or expensive script can delay unrelated clients. Prefer bounded ranges and batches; use incremental scans for maintenance rather than `KEYS` on a live production keyspace.

| Operation | Typical complexity | Practical boundary |
| -------------------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| `GET`, `SET`, `INCR` | O(1) | Network, allocation and persistence still affect latency. |
| `HGET`, `HSET` | O(1) per field | Bound hash cardinality and returned fields. |
| `LPUSH`, `RPOP` | O(1) per element | A destructive pop is not an acknowledged job protocol. |
| `SADD` | O(1) per member | Large set operations scale with supplied/returned members. |
| `ZADD` | O(log N) per member | Bound score-range and leaderboard responses. |
| `ZRANGE` | O(log N + M) | M is the number of returned members. |
| `KEYS` | O(N) | Scans the full keyspace in one blocking command. |
| `SCAN` | O(1) per call on average; O(N) for a full iteration | COUNT is a hint; keys can repeat and iteration is not a snapshot. |

```typescript
for await (const batch of redis.scanIterator({ MATCH: 'cache:*', COUNT: 100 })) {
  for (const key of batch) {
    console.log(key); // process each bounded batch; SCAN is not a snapshot
  }
}
```

Monitor used memory, allocator/resident-memory overhead, evictions, rejected writes, latency outliers, connection health and replication lag together. Inspect a suspected large key with `MEMORY USAGE`; do not infer a safe limit from key count alone. `maxmemory-policy allkeys-lru` may suit disposable cache entries. It can silently evict any key, so it is unsuitable for a deployment where Redis-held authoritative state must remain present. `noeviction` rejects writes at the limit; callers need an explicit response and capacity plan.

## Common Failure Modes

- **Unbounded growth:** choose TTL and retention from the data contract; TTLs on cache entries do not replace stream, list, set or hash cardinality limits.
- **Cache stampede:** coalesce local misses, bound origin concurrency and use refresh leases only with a stated failure path. The [cache strategy chapter](20.8.01-caching-deep-dive.md#cache-stampede-prevention) owns the full contract.
- **Treating a list as a durable queue:** a pop removes work before its external effect completes. Use an acknowledgment/recovery design or [Streams consumer groups](20.8.03-advanced-redis-patterns.md#4-redis-streams-with-consumer-groups).
- **Assuming a pipeline is atomic:** pipelining saves round trips; Lua, Functions, or transactions define Redis-side serialization, with their own error and cluster boundaries.
- **Putting sensitive or tenant-scoped data behind guessable keys:** authenticate and authorize in the application, scope keys from trusted identity, and restrict the Redis user with ACLs.

## Summary

Use Redis by matching each key family to a role and an explicit loss, expiry and recovery contract:

1. **Use cases:** Caches, sessions, counters, ranked results and notifications have different correctness and recovery requirements.
2. **Data structures:** Choose by access pattern, then bound size, result count and retention.
3. **Bound memory:** TTLs suit expiring values; durable state needs explicit retention, capacity and recovery policies.
4. **Avoid KEYS in production scans:** SCAN is incremental, may return duplicates and is not a snapshot.
5. **Cache patterns:** Choose freshness and outage behavior; separate writes remain separate failure points.
6. **Leases:** Owner-token release protects replacement leases; expiry and failover still need a correctness backstop.
7. **Delivery:** Pub/Sub is ephemeral; Streams add retained entries and pending-work recovery, while deployment settings determine durability.

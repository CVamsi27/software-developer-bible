# Advanced Redis Patterns — Distributed Locks, Rate Limiting, Pub/Sub, Streams, Lua Scripting

An appointment worker acquires a Redis lease and pauses past its expiry. Another worker acquires the lease; when the first resumes, both may reach the database. Redis can serialize the lease commands, but only the resource that owns the booking rule can prevent a duplicate booking. The same boundary—what Redis can decide atomically versus what the application must recover—connects the patterns in this chapter.

## Definition

An advanced Redis pattern composes atomic server commands into a larger contract: who may update state, how a request is admitted, or when work is considered complete. The boundary matters: command atomicity does not make a database write, a network side effect, and a Redis acknowledgment one transaction.

> **Textbook Definition:** Advanced Redis patterns coordinate ownership, admission or delivery using server-side data structures and atomic operations. Local atomicity does not establish a transaction with external databases, APIs or independently executing clients.

## First Principles

These Node.js examples use `node-redis` 6.3.0 and a connected shared client initialized as in [Redis Fundamentals](20.8.02-redis-fundamentals.md#connect-one-application-client). Redis recommends node-redis for new JavaScript services.

1. **Read-modify-write decisions need one serialization boundary.** Separate GET and SET commands can interleave; a short Lua script can read, decide, and write without another client entering between those steps.
2. **An expiring lease cannot stop a paused process.** Expiry restores availability, but the old holder may resume. The protected database/resource must reject conflicting or stale writes if overlapping work would corrupt state.
3. **Delivery and completion are different facts.** Pub/Sub retains neither; Streams store entries and track pending deliveries. Acknowledgment means the consumer finished its chosen effect, not that the effect and acknowledgment were atomic.
4. **Atomic scripts still consume shared capacity.** A long script blocks other commands. Keep state bounded and key-local; in Redis Cluster every key used by one script must belong to the same hash slot.

## 1. Distributed Leases and Database Invariants

A Redis lease can reduce duplicate work across application instances. Use a unique holder token, a TTL, and compare-and-delete release as shown in [Redis Fundamentals](20.8.02-redis-fundamentals.md#expiring-session-and-owner-token-lease). Renewal and random backoff improve liveness; they do not stop a holder paused beyond its lease.

For an appointment slot stored in one database, place the availability check and booking in one database transaction, with a uniqueness constraint as the final backstop. Every API replica uses the same database invariant. A Redis lock is an optional optimization, not the authority that prevents two bookings.

| Mechanism | Useful for | Boundary to test |
| ----------------------------- | ----------------------------------- | --------------------------------------------------------- |
| Database row lock/transaction | Coordinating writes in one database | Deadlocks, transaction duration, retry policy |
| Optimistic version check | Low-contention updates | Conflicting writers must retry or reject |
| Redis lease | Reducing duplicate refresh/work | Expiry, paused holder, failover, safe release |
| Resource-enforced fencing | Rejecting stale holders | Tokens must remain ordered and be checked by the resource |

The Redlock algorithm acquires a majority of independent Redis masters within a validity window; giving a library one Redis client is a single-instance lease. Its timing/failure assumptions must match the workload. Do not infer fencing from the library's name or use a lease instead of a booking constraint.

## 2. Rate Limiting with Lua Scripts

A token bucket allows a bounded burst and refills at a stated rate. This `node-redis` 6.3.0 example uses **milliseconds throughout** and tokens per millisecond, obtains server time inside the atomic script, and returns both admission and remaining whole tokens. Each key's capacity/rate must stay fixed while that bucket is live.

```lua
-- token_bucket.lua
local capacity = tonumber(ARGV[1])
local per_ms = tonumber(ARGV[2])
if not capacity or capacity < 1 or not per_ms or per_ms <= 0 then
  return redis.error_reply('invalid bucket configuration')
end
local clock = redis.call('TIME')
local now = tonumber(clock[1]) * 1000 + math.floor(tonumber(clock[2]) / 1000)
local old = redis.call('HMGET', KEYS[1], 'tokens', 'updated_ms')
local tokens = tonumber(old[1]) or capacity
local previous = tonumber(old[2]) or now
-- Protect against a backwards wall-clock jump; do not refill until caught up.
local effective_now = math.max(now, previous)
tokens = math.min(capacity, tokens + (effective_now - previous) * per_ms)
local allowed = 0
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'updated_ms', effective_now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / per_ms) * 2)
return {allowed, math.floor(tokens)}
```

```typescript
import { readFile } from 'node:fs/promises';
const tokenBucketScript = await readFile('token_bucket.lua', 'utf8');

async function checkRateLimit(
  tenantId: string,
  capacity = 100,
  tokensPerSecond = 100 / 60,
): Promise<{ allowed: boolean; remaining: number }> {
  if (!Number.isSafeInteger(capacity) || capacity < 1 ||
      !Number.isFinite(tokensPerSecond) || tokensPerSecond <= 0) {
    throw new RangeError('invalid bucket configuration');
  }
  // tenantId is a trusted, restricted opaque id from the authenticated context.
  const raw: unknown = await redis.eval(tokenBucketScript, {
    keys: [`ratelimit:${tenantId}`],
    arguments: [String(capacity), String(tokensPerSecond / 1000)],
  });
  if (!Array.isArray(raw) || raw.length !== 2 ||
      typeof raw[0] !== 'number' || typeof raw[1] !== 'number') {
    throw new Error('unexpected bucket response');
  }
  return { allowed: raw[0] === 1, remaining: raw[1] };
}
```

The algorithm controls admission on the Redis primary, not an exact global quota across asynchronous replicas or regions. A failover can lose recent bucket state. State the Redis-outage policy, choose an eviction policy that does not silently reset live limits, and use a distinct key/version when configuration changes.
Use EVALSHA or a Redis Function for repeated calls after validating deployment support.

## 3. Pub/Sub for Ephemeral Notifications

```typescript
// node-redis uses a dedicated connection and passes (message, channel) to the listener.
const subscriber = redis.duplicate();
subscriber.on('error', error => console.error('Redis subscriber error', error));
await subscriber.connect();
await subscriber.subscribe('clinic:123:appointment', (message, channel) => {
  try {
    const event: unknown = JSON.parse(message);
    if (typeof event !== 'object' || event === null ||
        !('type' in event) || event.type !== 'APPOINTMENT_CREATED' ||
        !('appointmentId' in event) || typeof event.appointmentId !== 'string') {
      throw new Error('invalid notification');
    }
    // Authorization is still required before broadcasting to a tenant's clients.
    console.log('validated notification', channel, event.appointmentId);
  } catch (error) {
    console.error('Rejected notification', error);
  }
});
await redis.publish('clinic:123:appointment', JSON.stringify({
  type: 'APPOINTMENT_CREATED', appointmentId: 'abc-123',
}));
subscriber.close(); // also close the application client during graceful shutdown
```

Pub/Sub has at-most-once delivery: a disconnected subscriber misses the notification. Pattern subscriptions use PSUBSCRIBE and the `pmessage` event. Use this for hints such as cache invalidation or live updates with a refresh/reconciliation path; use Streams for work that must remain recoverable.
Neither a channel name nor a tenant prefix authorizes access by itself.

## 4. Redis Streams with Consumer Groups

```typescript
// Create the group once at startup; use '0-0' to include retained history.
try {
  await redis.xGroupCreate('appointments:stream', 'workers', '0-0', { MKSTREAM: true });
} catch (error) {
  if (!(error instanceof Error) || !error.message.includes('BUSYGROUP')) throw error;
}

// A blocking read parks its connection. Keep it separate from HTTP/app commands.
const blockingRedis = redis.duplicate();
blockingRedis.on('error', error => console.error('Redis stream reader error', error));
await blockingRedis.connect();
const batches = await blockingRedis.xReadGroup(
  'workers', 'worker-1',
  [{ key: 'appointments:stream', id: '>' }],
  { COUNT: 10, BLOCK: 5000 },
);
for (const { name: stream, messages } of batches ?? []) {
  for (const { id, message: fields } of messages) {
    const event = parseStreamFields(fields); // validate before processing
    await processEventIdempotently(id, event);
    await redis.xAck(stream, 'workers', id);
  }
}
blockingRedis.close(); // close during worker shutdown
```

`>` reads entries never delivered to any consumer in the group. If a consumer restarts with the same name, read its own pending entries with an explicit ID such as `0-0`; if a replacement consumer takes over, inspect XPENDING and reclaim stalled deliveries with XAUTOCLAIM (Redis 6.2+) after an idle interval longer than legitimate processing. Reclaim can overlap an old worker that resumes, so the effect still needs idempotency.
On processing failure, leave the entry pending and apply bounded retries/quarantine; do not swallow the failure and acknowledge it.

A BLOCK timeout returns no batch, which is why the loop uses `batches ?? []`. XACK removes pending-delivery bookkeeping, **not** the stored stream entry.
Retention/trimming can delete entries still needed for recovery: coordinate it with consumer progress and your replay horizon. Use one group per independent processing purpose. Redis 8.2 adds stream trimming/reference controls (`KEEPREF`, `DELREF`, `ACKED`) and `XACKDEL`; Redis 8.8 adds `XNACK`, so use them only when the deployed server version supports them.
Persistence, replication, eviction, backup, and recovery tests determine what survives restart or failover; merely using XADD does not guarantee durable event sourcing.

## 5. Lua: Atomicity Has a Boundary

A script's commands run without interleaving, but Redis does not roll back earlier writes if a later operation errors. Validate arguments and expected key types before mutating state. Do not call a Redis marker followed by an external payment/email “exactly once”: a crash between the two still creates loss or duplicate effects.
Put the effect and dedup record in the same authoritative transaction where possible.

A short-lived Redis dedup hint can still reduce duplicate work:

```typescript
const acquired = await redis.set(`dedup:${eventId}`, 'processing', {
  expiration: { type: 'PX', value: 60_000 },
  condition: 'NX',
});
// This is not a completion record. A crash after acquisition can suppress unfinished
// work for 60 seconds; expiry can allow overlap. Recovery must account for both.
```

Cache-aside and write strategies live in [Caching Deep-Dive](20.8.01-caching-deep-dive.md), rather than being implemented a third time here. Use RDB snapshots for point-in-time recovery and AOF according to its fsync policy when Redis holds state; asynchronous replication and persistence are separate loss windows. Protect coordination state from cache eviction or place it in a separate instance.

## Summary

- A Redis lease limits duplicate work; the protected resource enforces correctness.
- Lua serializes a bounded decision; pipelining only saves round trips.
- Rate limits need consistent units, validated configuration, and a failure/eviction policy.
- Pub/Sub is ephemeral; Streams retain entries and track pending work that must be recovered explicitly.
- Database effects, Redis deduplication, and acknowledgments remain separate failure boundaries unless deliberately made atomic.

# Caching & Redis Interview Questions


## Definition

This set covers the caching surface interviewers actually probe at senior level: strategy selection, invalidation correctness, stampede prevention, Redis data-structure choice, and consistency under failure. Each question includes the answer shape, the follow-up the interviewer fires next, and the tradeoff that separates senior from mid-level.

## First Principles

This set probes cache coherence (→ 20.8.01): invalidation, stampedes, and layering.:

1. **The senior tells are trade-off statements**: "X when Y, Z when not-Y" — juniors memorize answers; seniors recite the *conditions* under which each answer is right.
2. **Every question here maps to an axiom chain, not a fact** — if you can derive the answer from the linked chapters, you can answer the variant questions too (that's the point of → First Principles sections).

### Q1. Walk me through your default caching strategy for a read-heavy API and when you would NOT use it.

**Model answer:** "Default is cache-aside: check cache, miss → read DB, populate with TTL. It's my default because the application owns the cache contract — no infrastructure coupling, and a cache outage degrades to the database instead of failing reads. I would *not* use it when writes invalidate constantly (invalidation traffic exceeds the caching win — then reduce cached scope or TTLs; read-through changes ownership of miss handling, not the invalidation problem), or when the data is authorization-dependent per request, because per-user cache keys explode cardinality and a shared-key mistake is a data leak."

**Follow-up probe:** "How do you prevent the cache being down from melting the database?" → "Timeouts + bounded concurrency on the DB path, serve-stale-on-error, and load-shedding priorities so authenticated traffic wins over crawlers."

**Tradeoff to name unprompted:** cache-aside's first read after invalidation is always a miss — if that latency is contractual, consider explicit warmup or stale-while-revalidate; read-through also misses on its first uncached read.

### Q2. A deploy changes the shape of a cached object. Users see old fields. Diagnose.

**Model answer:** "Three suspects in order. First, application-level object caches with long TTLs that no deploy invalidates — fixed by versioning the cache key namespace on deploy (`v2:{id}`), which invalidates lazily without a flush. Second, a CDN/Full-Route-Cache layer serving pre-rendered responses — fixed by deploy-time `revalidateTag`/purge. Third, the client Router Cache on already-open sessions — fixed by `router.refresh()` or accepting the revalidate window. Naming all three layers — server object cache, edge, client — is the senior signal; stopping at 'clear Redis' is the mid-level signal."

### Q3. Design cache invalidation for `user → orders → order-items` where order items change independently.

**Model answer:** "Never try to invalidate the composed view precisely. I cache each level with its own key and short TTL, and version the *edge* that composes them: a monotonically bumped `user-data-version` per user (stored in Redis) is part of every composed key. Selecting a bumped namespace makes old derived entries unreachable for new readers — O(1) write instead of O(dependencies) deletes. This is the write-or-bump pattern; precise per-entity invalidation only pays when dependency count is small and stable."

**Probe:** "Why not delete the composed keys directly?" → "Fan-out deletes are not atomic — a concurrent read can repopulate a stale child mid-delete. A version bump avoids touching each old key, but the source write, version publication, and read snapshot still need coordination; an old-source read can otherwise fill the new namespace."

### Q4. The hot key: one product page gets 100k QPS and its cache entry expires. What physically happens, and what do you do?

**Model answer:** "Every request misses simultaneously → 100k concurrent DB reads for the same row → connection pool exhaustion, DB CPU spike, cascading timeouts. Prevention is layered: request coalescing (single-flight: one leader recomputes while followers wait on a short lock — per key, with a lock TTL and safe fallback on lock loss), probabilistic early expiry (each reader refreshes slightly before TTL with probability p·t, to reduce synchronized refreshes; it must be paired with coalescing and is not a guarantee), and jittered TTLs so identical batch-populated keys don't die together. If it's already happening: serve last-known-good from a durable layer and let the coalescer absorb the rebuild."

### Q5. Which Redis data structures did you actually use, and what did each cost you?

**Model answer:** "Strings for serialized objects — simple, whole-value TTL, but no partial updates. Hashes for mutable field-level state (session objects) — HSET single fields without read-modify-write races. Sorted sets for anything ranked or time-windowed (rate limiter buckets, leaderboards, delayed-job queues by score = timestamp) — with the cost that ZSET operations are O(log N) and big sets need shard-aware keys. Streams for event logs with consumer groups. The mistakes I warn about: using KEYS in production (O(N) — SCAN instead), unbounded ZSETs without trimming policy, and storing serialized blobs in hashes field-by-field so an entity migration touches millions of field names."

### Q6. Your cache hit ratio drops from 94% to 60% after a feature launch. Investigate.

**Model answer:** "First segment the ratio by key family, not globally — the launch almost certainly shifted the *distribution*, not the cache. Usual causes: new per-user key cardinality explosion (feature keys by user+context), a new low-TTL key family competing for memory (evictions of hot families — check evicted_keys, not just hit ratio), and key-size bloat pushing the working set out of memory. The fix follows the diagnosis: raise maxmemory only after confirming eviction pressure, re-shape the new family's keys to shared prefixes, or accept and isolate the new family on its own pool so it can't evict the hot path."

### Q7. When is Redis persistence worth it, and when is a pure cache (no persistence) the right call?

**Model answer:** "If the cache is *only* a latency layer — every value recomputable from the source of truth — consider disabling persistence only if cold-start origin load is tolerable; snapshots can still shorten recovery and reduce reconstruction load. Persistence and a tested recovery/loss-window policy become necessary when Redis holds state with no cheap recompute: rate-limit counters (losing them resets quotas), distributed locks (losing them can break mutual exclusion; persistence alone does not prevent failover or expiry races), or dedup/idempotency keys. The interview trap is treating Redis as one thing — 'a cache' — instead of separating latency-layer Redis from stateful Redis, which have opposite availability requirements."

### Q8. How do you keep cache and database consistent under concurrent writes?

**Model answer:** "Accept bounded staleness; do not chase linearizability through a cache. The workable contract: write DB first, then invalidate (avoid blind cache updates if concurrent writer ordering is uncontrolled — stale overwrites last until TTL/invalidation), TTL as the consistency backstop, and version-bumped keys for anything where stale-reads window matters. For read-your-own-writes on hot objects: per-user version bump at write time makes the user's next read miss while everyone else rides the cache. Where the window is truly unacceptable, the write path returns the fresh object and the client uses it — bypassing the cache for one read is cheaper than distributed transactions."

### Q9. Compare cache-aside with read-through, write-through, and write-behind. What does each cost you operationally?

**Model answer:** "Cache-aside: the application owns the logic — flexible, infrastructure-agnostic, but every caller reimplements miss handling and the first read after invalidation is always a miss. Read-through: the cache library fetches on miss — one implementation of miss semantics, but now the cache layer is a dependency with its own failure modes. Write-through: the write path synchronously coordinates source and cache writes — successful writes can warm reads, but ordering and partial failures must be defined, but the write path pays double latency and you must define the failure contract when the second write fails. Write-behind: writes land in cache and flush asynchronously — fastest writes, and the dangerous one: a cache crash loses unflushed writes, so it is only correct when the data is recomputable or the loss is acceptable (counters, analytics), never for orders. The senior ordering: name that write-behind is an architectural decision about what you can afford to lose, not a performance knob."

### Q10. How do you choose a TTL? Give the actual methodology, not a number.

**Model answer:** "TTL derives from two properties of the data: the staleness the business tolerates and the cost of recomputation. Start from the staleness budget — 'a user seeing a 60-second-old product price is fine; a 60-second-old permission decision may violate the revocation contract' — that sets a target; entry TTL alone does not bound source age if stale data is repopulated. The recompute cost sets the floor's economics: expensive aggregates justify longer TTLs with explicit invalidation; cheap lookups get short TTLs because freshness is cheap. Then the operational adjustments: jitter (±10-20%) so batch-populated key families don't expire in unison and stampede; shorter TTLs on high-fanout composed views where any component can change; and version-based invalidation where the TTL is a *backstop*, not the primary mechanism — the difference between a cache that is mostly correct and one with a stated consistency contract. The tell of experience: 'it depends' followed immediately by the two variables it depends on."

### Q11. What is negative caching and when does it matter more than positive caching?

**Model answer:** "Caching the *absence* of data — the not-found, the empty result, the failed validation — so repeated probes for things that do not exist stop hitting the source of truth. It matters disproportionately for two threats: scanning (attackers or buggy clients probing millions of nonexistent IDs — without negative caching every miss is a full DB round trip, which is how a modest probing campaign becomes an outage) and hot misses on legitimately empty results (a filtered search returning zero rows, hammered by retry logic). Mechanics: cache the sentinel with its own, usually shorter TTL — the allowed delay before a new record becomes visible should usually be short; be deliberate about what the miss deserializes to so application code can't conflate 'cached: not found' with 'cache unavailable'; and for the security framing, negative caching plus rate limiting is the pair, because caching misses alone just makes probing cheap *after* the first probe."

### Q12. Walk me through a correct distributed lock in Redis. What goes wrong with the naive version?

**Model answer:** "Naive: `SET key value NX EX 30` — atomic acquire with expiry, delete on finish. The failure modes: holder A's work runs past 30s, the lock expires, holder B acquires, and both proceed — the classic split-brain; then A finishes and *deletes B's lock*. Fixes, in order: a fencing token — a monotonically increasing value checked by the resource being protected, so a stale holder's write is rejected regardless of lock state (a robust option when tokens remain ordered and the resource checks them; database constraints/transactions can instead enforce the invariant); holder identity on the lock (delete only if the value matches yours — via a Lua script for atomicity) so you never delete someone else's lock; auto-extension for long work; and social correctness — treat the lock as a performance hint that *usually* prevents duplicate work, and make the underlying operation idempotent so a double-execution is wasteful, not corrupting. When someone answers 'use Redlock' to a single-instance question, they've memorized the heavyweight tool and missed the mechanics."

### Q13. How does Redis Cluster actually shard, and what breaks because of it?

**Model answer:** "16384 hash slots distributed across masters; every key maps to a slot via CRC16 of the key *modulo slots* — so the shard count changes slot ownership, not the mapping. The consequence that bites everyone: multi-key operations (MGET, transactions, Lua on multiple keys) only work when all keys live in the same slot — enforced via hash tags (`{user:42}:profile`, `{user:42}:orders` share the `user:42` slot). Design implication: hash tags are a data-modeling decision that fixes both co-location *and* hotspot risk — tag too coarse and one hot user's slot saturates a shard. Resharding moves slots online, but big keys make migration slow and lumpy — hence big-key hygiene before you scale out. And clients must speak cluster protocol (MOVED/ASK redirects handled automatically); a naive client pinned to one node is a misconfiguration that works until the first failover."

### Q14. Your Redis is at memory capacity. Walk me through the eviction-policy decision.

**Model answer:** "First diagnose *why* — `INFO memory` for fragmentation (actually-allocated vs dataset; high ratio means fragmentation, not data growth, and the fix is the 4.0+ active defragmentation, not eviction), then big keys (`--bigkeys` scan; one large key can dominate memory; eviction cost and count are not proportional to key size). Then the policy choice, which is a data-classification question: `allkeys-lru` for a pure cache — anything can go, including your locks; `volatile-*` only evicts keys with TTL — which protects only keys without expiry; leases and expiring counters remain eviction candidates, and writes error if no eligible key can be evicted; `allkeys-lfu` when access is skewed and popularity is stable (the product-catalog case); and `noeviction` for stateful Redis where eviction is worse than failure — writes error instead, which is a *loud* failure you can alert on. The senior framing: a mixed-workload Redis (cache + state) with one eviction policy is a design smell — separate the latency layer from the state layer before the policy question even arises."

### Q15. Beyond single-flight: what else do you do when one key is 30% of your traffic?

**Model answer:** "Key splitting: shard the hot key into N sub-keys (`page:home:shard-0..7`), each with its own TTL — reads pick one at random, spreading the load across slots and replicas, and the cost is staleness variance between shards, fine for content, wrong for anything consistency-sensitive. L1 in-process caching: a small local LRU (Caffeine, node-lru-cache) in front of Redis — the hot key becomes an in-memory read after the first hop per process, at the cost of N×memory (one copy per instance) and an invalidation story (pub/sub invalidation or short L1 TTLs — 1-5s bounds staleness cheaply). Read-from-replica trade-off: reads spread, but replication lag becomes your staleness — know the lag before choosing. The decision frame: measure first — sometimes the hot key is *fine* (100k QPS against a well-sized Redis is its normal Tuesday), and the fix is only needed when the hot key's slot or the sync-replication path saturates. The anti-pattern to name: 'add more Redis nodes' — a single hot key lives on one slot; more nodes don't help, splitting or L1 does."

### Q16. Pipelining, MULTI/EXEC, and Lua scripts — what problem does each actually solve?

**Model answer:** "Pipelining: batching commands into one round trip — a latency optimization, not atomicity; N commands still execute interleaved with others. Use it for bulk operations; the win is the network RTT, not ordering. MULTI/EXEC (transactions): queue commands, execute as one atomic unit — no other client interleaves — but with no conditionality and no rollback: an error mid-transaction doesn't undo earlier commands, which surprises everyone once. WATCH provides optimistic concurrency: watch a key, exec aborts if it changed — retry-loop concurrency for low contention. Lua: server-side scripting that is atomic *and* conditional — read-modify-write patterns (token bucket, rate limiter, the compare-and-delete lock release) that transactions can't express. The discipline: keep scripts small and fast — a slow script blocks the entire single-threaded server, so a Lua script doing heavy iteration is how you build a self-inflicted outage; hot-path logic belongs in the data structures, not in 200-line scripts."

### Q17. Redis Streams versus Pub/Sub — when does each win, and when is the answer Kafka?

**Model answer:** "Pub/Sub is fire-and-forget: no persistence, no replay — subscribers get messages only while connected; a disconnected consumer silently loses everything. Correct for ephemeral signals: cache invalidation fan-out, live dashboards, presence. Streams add the durable log: entries persist, consumer groups track per-consumer offsets, pending-entry lists make redelivery explicit, and XADD/XRANGE give replay — correct for work queues, event sourcing at modest scale, and anything where 'the consumer was down for ten minutes' must not mean 'ten minutes of data vanished.' The line to Kafka: consumer count and retention horizon — a handful of consumer groups with hours of retention is Streams' sweet spot with vastly less operational surface; hundreds of consumers, multi-day retention, or ecosystem integrations (connectors, exactly-once semantics, schema registry) is Kafka's territory. The senior tell is naming that Redis Streams consumer groups *don't* auto-rebalance like Kafka's — a dead consumer's pending entries need explicit XAUTOCLAIM — so the 'it works like Kafka' assumption is the specific bug to avoid."

### Q18. How do you warm a cache, and when is warming the wrong answer?

**Model answer:** "Warm proactively when the cold path is catastrophic: deploy-time (a post-deploy task that pre-computes the top-N keys — the N from real traffic analysis, not intuition), cron-driven pre-computation of expensive aggregates before known peaks (the morning report generated at 5am, not at first-request), and replay-from-durable-log for restart scenarios — if the cache is reconstructible from Kafka or the DB binlog, cold start is a consumption race you can bound. When it's wrong: warming everything 'just in case' — warm the working set, not the dataset, or you've built a second copy of the database with extra steps; and warming instead of fixing stampede mechanics — coalescing and probabilistic early expiry protect *every* cold start including the ones you didn't predict, which is why they're the foundation and warming is the optimization. The diagnostic that justifies the work: measure the cold-start curve — requests, latency, error rate during a flush — and let its shape (how fast does the hit ratio recover, what breaks first) tell you what to warm."

### Q19. Compare invalidation strategies: TTL-only, pub/sub invalidation, and CDC-driven invalidation.

**Model answer:** "TTL-only: zero coupling, bounded staleness, and the floor every other strategy stands on — the backstop when fancier mechanisms fail. Pub/sub invalidation: the writer publishes 'key X changed' and subscribers drop their entries — near-real-time freshness, but Redis Pub/Sub is at-most-once, so a disconnected subscriber misses invalidations (until TTL rescues you — hence the floor), and the fan-out cost grows with subscriber count. CDC-driven: watch the database's change log (Debezium-style) and invalidate from the *source of truth's* own commit stream — no code path can forget to invalidate because invalidation derives from the write itself; the costs are pipeline infrastructure and replication lag as the freshness bound. The selection logic: TTL alone when staleness tolerance is generous; pub/sub when you have few writers, few cache nodes, and can tolerate the ops; CDC when the write paths are many or owned by many teams — the moment 'every writer must remember to invalidate' spans team boundaries, the promise-based approach has failed and the derived one is justified."

### Q20. What changes when the cache itself is geo-distributed?

**Model answer:** "Three regimes, pick by consistency need. Passive replicas (Redis active-passive replication to a read region): reads are local and fast, writes funnel to the primary — replication lag determines current staleness but is not a fixed bound without an enforced lag/freshness policy, and the failure mode to name is replica promotion lag during failover. Per-region independent caches over per-region data: clean when the data is naturally partitioned by user geography — no cross-region consistency question exists. Genuinely global shared state (a distributed lock or rate-limit counter honored across regions): the hard one — cross-region writes to one primary make every operation pay the wide-area round trip, which defeats the purpose; the honest answers are region-scoped semantics (rate limits per region, with a global approximation via periodic sync) or acknowledging that the correctness requirement belongs in a quorum system (Cosmos/Dynamo-style), not a cache. The senior tell: refusing to pretend a geo-distributed cache is one logical cache — naming which regime each key family lives in is the design."

### Q21. What metrics actually tell you a cache is healthy? What would you alert on?

**Model answer:** "Per key-family, never only global — the global hit ratio hides a 99% family behind a 20% one. The stack: hit ratio per family with the trend (a slow slide is a memory or cardinality problem forming); latency percentiles of the cache itself (p99, not the average — Redis averages lie; one slow command class shows up only in the tail); eviction rate and evicted keys (evictions climbing while hit ratio drops is the memory-pressure signature); memory fragmentation ratio; connected clients and rejected connections (the maxclients signature); and command-class outliers via slowlog — one KEYS call in production shows up here before it shows up as an outage. Alerting philosophy: page on user-impact proxies (latency SLO burn, connection rejections), ticket on leading indicators (eviction trend, fragmentation, memory headroom below 25%). The senior habit: dashboards per key family built *when the family is designed*, because the family taxonomy in metrics should match the one in the cache-key design — the same decision applied twice."

### Q22. How do you secure a Redis that production depends on?

**Model answer:** "Layered, because Redis's historical posture is 'trusted network, fast server' and production networks are not trusted. Network: private subnets, security groups pinned to app tiers — never a public endpoint (the unauthenticated-Redis-on-the-internet incident genre writes itself). Auth: ACLs (Redis 6+) with per-service users and command allowlists — the cache user doesn't need CONFIG or DEBUG; TLS in transit, especially cross-AZ or any shared network segment. Command surface: restrict the destructive class in production — FLUSHALL, KEYS, CONFIG via ACL rules — because the tooling accident is a real incident category. Application: never interpolate untrusted text into Lua source; pass data as ARGV and validate identifiers. Prefixes alone do not stop SCAN or cross-namespace access: enforce ACL key patterns and tenant authorization. And the operational floor: no RDB/AOF world-writable directory issue (the CVE-class where Redis writes a crontab — check your deployment hardening), memory limits set so OOM kills the *cache* and not the host's other tenants."

### Q23. What is client-side caching and when does the complexity pay off?

**Model answer:** "An L1 cache inside the application process in front of Redis — and Redis 6+ makes it coherent: the tracking protocol pushes invalidations for observed keys, reducing polling. Clients must handle disconnects, flush local entries when coherence is uncertain, and account for in-flight read/invalidation races. Payoff conditions: extremely hot, small, read-mostly objects (feature flags, config, session lookups) where the network hop to Redis dominates latency — sub-millisecond reads and the Redis load drops by the hit ratio of the L1. The costs: memory in every app instance (N copies of the hot set), invalidation storms when a 'hot' key updates frequently (every write fans out to every tracking client — a hot-and-churny key makes client-side caching *worse* than none), and one more layer in every staleness conversation. The simpler alternative to weigh first: a tiny uncoordinated L1 with 1-5s TTLs — no protocol dependency, bounded staleness, right answer more often than teams expect. The protocol earns its keep when its tested coherence contract matches the workload; permission revocation may still require authoritative checks."

### Q24. When does a cache quietly become the source of truth — and how do you pull it back?

**Model answer:** "It happens by accretion, not decision: a write-behind cache that flushes 'eventually' starts being the only place the latest value exists; a cache with no TTL that nobody can regenerate because the original computation's inputs changed shape; session data added 'temporarily' with persistence enabled. The audit questions: if Redis vanished right now, what would be *lost* versus merely *slow*? Can every key family be regenerated from a durable source, and has anyone actually run that regeneration at scale? The escape path, applied per family: freeze writes to the orphaned family, backfill the durable store from the cache (the cache is, embarrassingly, the best available source), flip reads to source-of-truth with the cache back in front as a real cache, then delete the write path that fed Redis directly. The prevention is a standing rule from the persistence question: any Redis that holds state with no cheap recompute gets the stateful treatment — persistence, backup, and a documented regeneration path — reviewed on the same cadence as database backups. 'It is just a cache' is not an architecture statement; it is a claim someone stopped verifying."

### Q25. Tell me about the worst cache incident you have run. What did it teach you?

**Model answer:** "The scoring shape: a story with a real invalidation-order or stampede mechanism at its core — not 'Redis was slow.' The strong version: a deploy changed a serializer while the old serialized objects sat in cache with a 24-hour TTL; deserialization failures on the new code turned a routine deploy into a 40% error rate that *grew* as the rollout spread — the cache had converted a code rollback into a data-format rollback problem nobody could do quickly. What the interviewer listens for: the detection gap (error-rate alert fired, but attributing it to cache contents took a screenshot of a stack trace and a hypothesis someone had seen before), the mitigation ordering (flush the affected key family versus code-patch the deserializer — and the flush-induced stampede risk they had to coalesce against), and the class fixes — serializer version embedded in the cache value so formats are co-existing rather than breaking, cache-burn-down canaries in the deploy pipeline, and the TTL audit that found three more families with the same latent shape. The meta-lesson named out loud: cache incidents are time-shifted incidents — the bad decision happened hours before the outage, which is exactly why cache policy belongs in code review, not in ops folklore."

## Common Mistakes

- Answering pattern names without invalidation semantics — knowledge without operation.
- Treating Redis as one homogeneous system instead of latency-layer vs stateful.
- Reaching for Redlock in a single-instance question — naming the heavyweight tool when the question is about mechanics reads as pattern-matching, not experience.

## Best Practices

- Lead with the contract (what staleness is acceptable), then the mechanism — that is the senior order.
- Every design answer ends with its failure mode named unprompted.

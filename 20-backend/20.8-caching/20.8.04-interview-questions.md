# Caching & Redis Interview Questions


## Definition

Use these questions to practice decisions about cache identity, freshness, concurrent writes, Redis operations and recovery. The model answers show reasoning under explicit conditions; adapt them to the question's workload and your verified experience.

## First Principles

Start with the result the caller needs and the state that owns it. Trace a hit, a miss, a source write and a failure. Then explain why a particular key, expiry, coordination or recovery policy preserves the required behavior. Changing one condition should change the answer where that condition matters.

### Q1. Walk me through your default caching strategy for a read-heavy API and when you would NOT use it.

**Model answer:** For a read-heavy API, I start with cache-aside when repeated reads save enough origin work and the data permits the stated stale window. The application reads the cache, loads the source on a miss and coordinates invalidation after source writes. I would avoid caching a cheap, rarely reused or rapidly changing result when the maintenance cost exceeds the benefit. Authorization-dependent results can be cached only with the correct identity scope, revocation contract and capacity budget.

**Follow-up probe:** "How do you prevent the cache being down from melting the database?" → "Bound source concurrency and deadlines; serve an older value only within its policy, and shed excess work using explicit admission priorities."

**Tradeoff to name unprompted:** cache-aside's first read after successful deletion usually misses unless another caller has already filled it — if that latency is contractual, consider explicit warmup or stale-while-revalidate; read-through also misses on its first uncached read.

### Q2. A deploy changes the shape of a cached object. Users see old fields. Diagnose.

**Model answer:** Trace the actual response path and compare the stored format version with the running serializer. An object cache may need a new namespace plus compatibility during rollout; an HTTP cache may need purge, validation or a versioned URL; an already-open client may retain its own result. These are separate layers. Next.js route/tag/client APIs apply only to its configured framework cache, not to an arbitrary CDN. Test mixed application versions and rollback before retiring old entries.

### Q3. Design cache invalidation for `user → orders → order-items` where order items change independently.

**Model answer:** Identify which derived answers include each changed item. For a small dependency set, invalidate those answers after commit. For a large set, a user/entity version in composed keys can retire a namespace without enumerating it. The version must be coordinated with the source commit and the snapshot used to fill the result. Bumping a Redis counter separately does not ensure freshness; a delayed reader can put an old result in the new namespace.

**Probe:** "Why not delete the composed keys directly?" → "Fan-out deletes are not atomic — a concurrent read can repopulate a stale child mid-delete. A version bump avoids touching each old key, but the source write, version publication, and read snapshot still need coordination; an old-source read can otherwise fill the new namespace."

### Q4. The hot key: one product page gets 100k QPS and its cache entry expires. What physically happens, and what do you do?

**Model answer:** Requests that observe the expired key start overlapping source reads unless admission or coalescing stops them. The concurrent load depends on request rate and load duration, not just QPS. Coalesce within each process, bound fleet-wide origin concurrency and define waiting/failure behavior. A lease can reduce duplicate fills but can expire during work. Refresh-ahead or probabilistic refresh can reduce misses; TTL jitter spreads expiry across different keys. Serve an older value only if its age is allowed.

### Q5. Which Redis data structures did you actually use, and what did each cost you?

**Model answer:** Describe data structures from work you actually performed. Strings fit whole serialized values; hashes fit field access, but separate HGET/HSET decisions can still race. Sorted sets fit scores or timestamp ordering, with operation-specific cost and bounded range sizes. Streams fit retained messages under a stated persistence and retention policy. Avoid unbounded results and large blocking scans. SCAN supports incremental iteration but is not a snapshot or a substitute for tenant authorization.

### Q6. Your cache hit ratio drops from 94% to 60% after a feature launch. Investigate.

**Model answer:** Segment hits, misses, key count, entry size and load cost by key family. Compare the feature's traffic, key identity, TTLs and cold-start behavior with the previous workload. Increased cardinality, shorter lifetimes, larger entries, changed lookup routing or eviction can explain the drop. Preserve tenant/user inputs that affect results when redesigning keys. Increase memory only when measured capacity pressure justifies it; also check whether the new misses increased origin latency or errors.

### Q7. When is Redis persistence worth it, and when is a pure cache (no persistence) the right call?

**Model answer:** A disposable cache can omit persistence when every value is reconstructible and the origin can survive recovery load. Persistence may still shorten warm-up. Sessions, quotas, deduplication records and acknowledged writes need a declared loss/recovery contract because their loss changes behavior. Evaluate snapshots, append-only persistence, replication and restoration against that contract. Persistence alone does not make lease failover safe or ensure a duplicate business effect is rejected.

### Q8. How do you keep cache and database consistent under concurrent writes?

**Model answer:** First specify the consistency requirement. Source-first deletion reduces ordinary stale hits but can race a delayed fill. TTL is an expiry backstop, not proof of maximum source age. Source-coordinated versions or validation can enforce stronger selection rules; the read must use the corresponding version and snapshot. For read-your-writes, route a later read to an authority or minimum version that includes the accepted write. Returning the committed object helps that caller's immediate display but does not fix other cached reads.

### Q9. Compare cache-aside with read-through, write-through, and write-behind. What does each cost you operationally?

**Model answer:** Cache-aside makes the application own miss loading; read-through hides loading behind a cache interface. Both need the same freshness and fallback policy. Write-through puts the required source/cache work in the foreground path, increasing latency and exposing partial failure between stores. Write-behind acknowledges before the final source update: define durable intent, ordering, replay and the allowed loss window. Lower foreground latency is useful only if the resulting acknowledgment contract is acceptable.

### Q10. How do you choose a TTL? Give the actual methodology, not a number.

**Model answer:** Start with the operation's allowed data age, then account for source/replica lag, delayed fills, lower cache layers, refresh and stale-serving paths. Choose an entry TTL within that complete budget where a finite bound can be enforced. Measure hit rate, saved origin cost, miss latency and update frequency. Add jitter to spread batch expiration and coalesce hot-key loads. Expensive recomputation cannot justify exceeding a correctness requirement; change the loading or validation design instead.

### Q11. What is negative caching and when does it matter more than positive caching?

**Model answer:** Negative caching stores an allowed not-found or empty result, with a distinct representation and expiry. It reduces repeated loads for the same absent key, but high-cardinality probes can still overwhelm capacity and the source. Do not conflate absence with timeout, unavailable cache or another caller's authorization failure. Define how a newly created record becomes visible, include all result-changing key inputs, and combine caching with admission controls when probing traffic is the threat.

### Q12. Walk me through a correct distributed lock in Redis. What goes wrong with the naive version?

**Model answer:** SET with NX and expiry can acquire a lease atomically. Use a unique owner token and an atomic compare-and-delete release so an old holder cannot delete a successor's lease. Expiry still allows overlap: a paused holder can resume after another holder acquires. Protect the actual business effect with an invariant, atomic deduplication or an ordered fencing token checked by the resource. Renewal reduces expiry risk but does not prove exclusive authority after uncertainty or failover.

### Q13. How does Redis Cluster actually shard, and what breaks because of it?

**Model answer:** Redis Cluster maps keys to 16,384 hash slots using CRC16 modulo the slot count; hash tags select the hashed substring. Slot ownership can move between primaries without changing that mapping. Multi-key transactions and scripts require compatible same-slot keys. Co-locating related keys helps atomic operations but can create hotspots. A cluster-aware client handles MOVED/ASK redirects; migration, large keys, replica promotion and partial failures still need tested operational behavior.

### Q14. Your Redis is at memory capacity. Walk me through the eviction-policy decision.

**Model answer:** Inspect used memory, resident memory, allocator metrics and their byte differences together. A high fragmentation ratio alone can reflect a small dataset or non-dataset overhead; it is not proof that active defragmentation is the fix. Inspect large keys, buffers and the working set. Choose allkeys LRU/LFU for disposable values, volatile policies only when expiring values may be evicted, or noeviction when rejection is preferable to state loss. Separate authoritative state from a cache with incompatible eviction needs.

### Q15. Beyond single-flight: what else do you do when one key is 30% of your traffic?

**Model answer:** Measure the key's throughput, size, update rate and serving node first. An L1 copy can reduce network reads, at a memory/freshness cost per process. Multiple copied keys can spread reads across primaries only if their placement actually differs; avoid a shared hash tag that puts them back in one slot. Replica reads require explicit routing and a lag policy. A short L1 TTL bounds its entry lifetime, not the age of the value loaded from L2.

### Q16. Pipelining, MULTI/EXEC, and Lua scripts — what problem does each actually solve?

**Model answer:** Pipelining reduces network round trips; it does not make a read/decide/write sequence atomic. MULTI/EXEC prevents other clients interleaving during queued command execution, but a runtime command error does not roll back earlier successful commands. WATCH makes EXEC conditional on watched keys remaining unchanged. Lua can make a bounded read/branch/write decision atomic. Script errors also do not roll back earlier writes, so validate before mutation. Long transactions or scripts delay other clients.

### Q17. Redis Streams versus Pub/Sub — when does each win, and when is the answer Kafka?

**Model answer:** Pub/Sub is at-most-once live delivery with no retained replay; use it only when missed notifications have an acceptable repair policy. Streams retain entries under configured persistence/replication/retention and track pending deliveries in consumer groups. A dead consumer's pending work needs explicit claim/recovery, and duplicate effects need protection. Compare Kafka when retention, fan-out, throughput, partition ordering or ecosystem requirements warrant it. Neither system automatically gives exactly-once effects in an external database or API.

### Q18. How do you warm a cache, and when is warming the wrong answer?

**Model answer:** Warm the measured working set with bounded source concurrency before a predictable peak or rollout. Use the same identity, version and freshness rules as ordinary fills. Warming the whole dataset wastes capacity, and a warm-up racing source writes can still install old results. Measure the recovery curve and retain miss admission/coalescing because unexpected cold starts still happen. A durable event log can rebuild a projection only when retained history and processing capacity support that recovery.

### Q19. Compare invalidation strategies: TTL-only, pub/sub invalidation, and CDC-driven invalidation.

**Model answer:** TTL expires installed entries but needs a complete source-age contract. Pub/Sub can promptly invalidate connected processes; missed messages need expiry, validation or recovery. Change data capture (CDC) derives changes from the database's commit stream, avoiding application paths that forget publication, but it adds lag, replay and operational dependencies. Both notification approaches still race delayed fills unless versions or ordering handle that boundary. Select from the allowed stale window and tested recovery behavior.

### Q20. What changes when the cache itself is geo-distributed?

**Model answer:** Specify whether each key family uses one authoritative primary with remote reads, independent regional caches, or globally coordinated state. Replica lag affects remote freshness; region-independent copies need rules for shared entities and movement. Global quotas or locks may require a cross-region authoritative operation and its latency/partition tradeoff. Region-local quotas with periodic aggregation provide a different, approximate contract. Test promotion and stale-read recovery rather than treating the topology name as a guarantee.

### Q21. What metrics actually tell you a cache is healthy? What would you alert on?

**Model answer:** Track hit/miss rate by key family, load volume and latency, cache latency percentiles, rejected connections, evictions, bytes, allocator overhead and command outliers. Correlate them with user errors and origin saturation: a lower hit ratio need not mean memory pressure, and a higher hit ratio can still serve wrong data. Alert on the service's availability/latency objectives and required state-loss boundaries; investigate trends using workload-based thresholds rather than a universal memory percentage.

### Q22. How do you secure a Redis that production depends on?

**Model answer:** Use private network access, TLS where required, per-service ACL users, minimum command/key permissions and managed secrets. Restrict administrative/destructive commands and unneeded key enumeration; key patterns alone do not filter SCAN output. Derive tenant scope from trusted application context, pass Lua inputs as arguments and bound payloads. Run Redis with restricted filesystem/process privileges, patch supported versions, limit resource use and test backup access. Network isolation complements authentication rather than replacing it.

### Q23. What is client-side caching and when does the complexity pay off?

**Model answer:** Client-side caching retains local copies of Redis results and uses tracking invalidations under the selected mode. Handle disconnects, flush uncertainty and read/invalidation races before claiming coherence. It helps when repeated small reads are expensive relative to local access; measure actual latency and memory. Frequent updates can create costly fan-out. A simpler TTL-only L1 trades coordination for allowed older reads, but its TTL cannot by itself bound lower-layer source age or guarantee permission revocation.

### Q24. When does a cache quietly become the source of truth — and how do you pull it back?

**Model answer:** Classify what would be lost if Redis vanished. Unflushed accepted writes, non-reconstructible sessions or sole retained results are authoritative state even if they were called a cache. Either operate that state with a tested durability/recovery contract or migrate ownership. For migration, establish a consistent cutover, preserve concurrent changes, backfill a durable owner, verify reads and recovery, then retire the old write path. A blind copy during active writes can lose the very state being recovered.

### Q25. Tell me about the worst cache incident you have run. What did it teach you?

**Model answer:** Use your own verified incident and distinguish measurements from estimates. Describe the triggering change, the retained cache state, the user-visible failure, diagnosis and safe mitigation. In a hypothetical serializer rollout, old objects can fail under new code; compare backward-compatible reads, versioned namespaces and targeted invalidation, including miss-load and rollback risks. Explain the evidence that validates recovery and the prevention added. Do not present invented percentages or a sample story as personal production experience.

- Every answer above maps to a production mechanism detailed in [Caching Deep-Dive](20.8.01-caching-deep-dive.md), [Redis Fundamentals](20.8.02-redis-fundamentals.md), and [Advanced Redis Patterns](20.8.03-advanced-redis-patterns.md).
- For scheduling data, define stale-read tolerance per field and enforce booking availability in the authoritative write transaction; a cached display is not booking authority.

## Common Mistakes

- Answering pattern names without invalidation semantics — knowledge without operation.
- Treating Redis as one homogeneous system instead of latency-layer vs stateful.
- Treating a lease as authority after expiry or uncertain failover; explain how the protected resource rejects an unsafe effect.

## Best Practices

- Lead with the contract (what staleness is acceptable), then the mechanism — that is the senior order.
- Every design answer ends with its failure mode named unprompted.

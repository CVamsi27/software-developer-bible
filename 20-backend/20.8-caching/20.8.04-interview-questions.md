# Caching & Redis Interview Questions

> **TL;DR:** Senior-level caching interview questions with model answers, follow-up probes, and tradeoffs — drawn from the three caching chapters in this stack. The senior test is not "cache aside is read-through plus a cache" — it is naming invalidation order, stampede mechanics, and the failure modes you have personally operated through.

## Definition

This set covers the caching surface interviewers actually probe at senior level: strategy selection, invalidation correctness, stampede prevention, Redis data-structure choice, and consistency under failure. Each question includes the answer shape, the follow-up the interviewer fires next, and the tradeoff that separates senior from mid-level.

### Q1. Walk me through your default caching strategy for a read-heavy API and when you would NOT use it.

**Model answer:** "Default is cache-aside: check cache, miss → read DB, populate with TTL. It's my default because the application owns the cache contract — no infrastructure coupling, and a cache outage degrades to the database instead of failing reads. I would *not* use it when writes invalidate constantly (invalidation traffic exceeds the caching win — then read-through with short TTLs), or when the data is authorization-dependent per request, because per-user cache keys explode cardinality and a shared-key mistake is a data leak."

**Follow-up probe:** "How do you prevent the cache being down from melting the database?" → "Timeouts + bounded concurrency on the DB path, serve-stale-on-error, and load-shedding priorities so authenticated traffic wins over crawlers."

**Tradeoff to name unprompted:** cache-aside's first read after invalidation is always a miss — if that latency is contractual, use read-through with async warmup.

### Q2. A deploy changes the shape of a cached object. Users see old fields. Diagnose.

**Model answer:** "Three suspects in order. First, application-level object caches with long TTLs that no deploy invalidates — fixed by versioning the cache key namespace on deploy (`v2:{id}`), which invalidates lazily without a flush. Second, a CDN/Full-Route-Cache layer serving pre-rendered responses — fixed by deploy-time `revalidateTag`/purge. Third, the client Router Cache on already-open sessions — fixed by `router.refresh()` or accepting the revalidate window. Naming all three layers — server object cache, edge, client — is the senior signal; stopping at 'clear Redis' is the mid-level signal."

### Q3. Design cache invalidation for `user → orders → order-items` where order items change independently.

**Model answer:** "Never try to invalidate the composed view precisely. I cache each level with its own key and short TTL, and version the *edge* that composes them: a monotonically bumped `user-data-version` per user (stored in Redis) is part of every composed key. Bumping one number invalidates every derived view of that user atomically — O(1) write instead of O(dependencies) deletes. This is the write-or-bump pattern; precise per-entity invalidation only pays when dependency count is small and stable."

**Probe:** "Why not delete the composed keys directly?" → "Fan-out deletes are not atomic — a concurrent read can repopulate a stale child mid-delete. A version bump makes stale entries unreachable without touching them."

### Q4. The hot key: one product page gets 100k QPS and its cache entry expires. What physically happens, and what do you do?

**Model answer:** "Every request misses simultaneously → 100k concurrent DB reads for the same row → connection pool exhaustion, DB CPU spike, cascading timeouts. Prevention is layered: request coalescing (single-flight: one leader recomputes while followers wait on a short lock — per key, with a lock TTL and safe fallback on lock loss), probabilistic early expiry (each reader refreshes slightly before TTL with probability p·t, so the stampede never fully forms), and jittered TTLs so identical batch-populated keys don't die together. If it's already happening: serve last-known-good from a durable layer and let the coalescer absorb the rebuild."

### Q5. Which Redis data structures did you actually use, and what did each cost you?

**Model answer:** "Strings for serialized objects — simple, whole-value TTL, but no partial updates. Hashes for mutable field-level state (session objects) — HSET single fields without read-modify-write races. Sorted sets for anything ranked or time-windowed (rate limiter buckets, leaderboards, delayed-job queues by score = timestamp) — with the cost that ZSET operations are O(log N) and big sets need shard-aware keys. Streams for event logs with consumer groups. The mistakes I warn about: using KEYS in production (O(N) — SCAN instead), unbounded ZSETs without trimming policy, and storing serialized blobs in hashes field-by-field so an entity migration touches millions of field names."

### Q6. Your cache hit ratio drops from 94% to 60% after a feature launch. Investigate.

**Model answer:** "First segment the ratio by key family, not globally — the launch almost certainly shifted the *distribution*, not the cache. Usual causes: new per-user key cardinality explosion (feature keys by user+context), a new low-TTL key family competing for memory (evictions of hot families — check evicted_keys, not just hit ratio), and key-size bloat pushing the working set out of memory. The fix follows the diagnosis: raise maxmemory only after confirming eviction pressure, re-shape the new family's keys to shared prefixes, or accept and isolate the new family on its own pool so it can't evict the hot path."

### Q7. When is Redis persistence worth it, and when is a pure cache (no persistence) the right call?

**Model answer:** "If the cache is *only* a latency layer — every value recomputable from the source of truth — run it with no persistence: RDB/AOF costs memory bandwidth and restart latency and buys nothing, since cold-start repopulation is just traffic. Persistence becomes mandatory when Redis holds data with no cheap recompute: rate-limit counters (losing them resets quotas), distributed locks (losing them breaks mutual exclusion), or dedup/idempotency keys. The interview trap is treating Redis as one thing — 'a cache' — instead of separating latency-layer Redis from stateful Redis, which have opposite availability requirements."

### Q8. How do you keep cache and database consistent under concurrent writes?

**Model answer:** "Accept bounded staleness; do not chase linearizability through a cache. The workable contract: write DB first, then invalidate (never update the cache in-line — last-writer races produce stale-forever entries), TTL as the consistency backstop, and version-bumped keys for anything where stale-reads window matters. For read-your-own-writes on hot objects: per-user version bump at write time makes the user's next read miss while everyone else rides the cache. Where the window is truly unacceptable, the write path returns the fresh object and the client uses it — bypassing the cache for one read is cheaper than distributed transactions."

## Common Mistakes

- Answering pattern names without invalidation semantics — knowledge without operation.
- Treating Redis as one homogeneous system instead of latency-layer vs stateful.
- Reaching for Redlock in a single-instance question — naming the heavyweight tool when the question is about mechanics reads as pattern-matching, not experience.

## Best Practices

- Lead with the contract (what staleness is acceptable), then the mechanism — that is the senior order.
- Every design answer ends with its failure mode named unprompted.

## Summary

Eight questions covering strategy choice, invalidation design, stampede physics, data-structure tradeoffs, hit-ratio forensics, persistence decisions, and consistency contracts. The ladder is deliberate: each question assumes the previous one's answer.

| -------------------- | -------------------------------------------------------------------------------------- |

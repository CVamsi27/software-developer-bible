# Message Brokers

During a worker deployment, a downstream service may be unavailable for twenty minutes. Producers can keep publishing only if the broker's acceptance and retention settings cover that outage; when the consumer returns, it still has to process the backlog and tolerate duplicates. Broker choice defines that trade between availability, recovery and operational cost.

## Definition

A **message broker** accepts messages from publishers and makes them available to consumers; persistence and acknowledgment guarantees depend on the chosen mode/configuration, decoupling the two in time, rate, and topology.

> **Textbook Definition:** A message broker mediates message exchange through routing, buffering and delivery contracts. Log-based and queue-based systems assign retention and consumption state differently, which changes replay, ordering and failure recovery.

Two common systems illustrate different broker contracts:

|  | **Kafka** (log-based) | **RabbitMQ** (queue-first) |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model | Append-only, partitioned, replicated **log**; classic consumer groups track offsets, while Kafka 4.2+ Share Groups acknowledge records individually | Broker routes through **exchanges → bindings → queues**; the broker tracks delivery and awaits **acks** |
| Replay | Re-read retained offsets; a new group can replay available history | Classic/quorum queue messages are removed after ack; RabbitMQ Streams retain entries for replay |
| Routing | Producer selects topic and partition; key-based partitioning is common | Rich: direct/topic/fanout/headers exchanges, per-message routing |
| Ordering | Per partition; stable key mapping and serial handling are needed for per-entity effects. Share Groups distribute records independently and do not provide the same per-partition processing order. | Queue order is strongest with a single active consumer and no requeue or priority effects; multiple consumers and redelivery can change completion order |
| Backpressure | Consumer pulls at its own pace; lag is visible | Prefetch/credit-flow; unacked messages block delivery windows |
| Retention | Time/size-based, independent of consumption; **compaction** keeps latest per key | Classic/quorum queue delivery removed on ack; Streams retain by policy |
| Sweet spot | Event streaming, change data capture, analytics pipelines, audit logs | Task queues, RPC-over-AMQP, complex routing, per-job work distribution |

Version snapshot checked 2026-10-13: Kafka 4.3.1 is the newest supported Kafka release listed, and RabbitMQ 4.3.6 is the latest release. Kafka Share Groups became production-ready in 4.2 for queue-like per-record work; use classic consumer groups when partition ownership, offset commits and ordered stream processing are the required contract. These examples use Confluent's maintained `@confluentinc/kafka-javascript` 1.11.0 promisified API, exported through its `KafkaJS` namespace.
They pass native librdkafka configuration keys rather than the `kafkaJS` migration-compatibility block. The package exposes the Kafka 4.x `group.protocol` setting; its 1.11.0 public Node.js types do not expose a Share Consumer API.

**Delivery semantics** (both systems):

- **At-most-once** — fire and forget, or ack-before-process. Loses work on failure.
- **At-least-once** — process, *then* ack; redelivery on failure. Duplicates possible → consumers must be **idempotent** (→ 30.3.2.03 idempotency keys; → 20.6.3.06 outbox).
- **Effectively-once effects** — deduplication/transactional handling makes repeated deliveries harmless at a stated boundary. Kafka transactions can provide exactly-once semantics for a configured Kafka read-process-write pipeline; external effects require their own atomicity/idempotency contract.

## First Principles

1. **Networks and processes fail independently, so coupling in time is a liability.** A synchronous call succeeds only while both ends are up. A broker removes the requirement for the producer to wait for the consumer's business effect: publication completes under the configured broker acceptance contract, while the consumer may process the message concurrently or later. A successful local socket write alone is not durable acceptance. Retention, replay and buffering then define how the system recovers.
2. **An append-only log can buffer bursts efficiently.** Disk append is sequential I/O; the log absorbs bursts so producers and consumers scale (and fail) at independent rates. Consumer lag is not an error state — it is the buffer doing its job — until it isn't, which is why lag is a first-class SLI (→ 20.9.02).
3. **Ordering and parallelism are in tension; partitioning is the truce.** A single log is totally ordered but not parallel. Partitioning buys parallelism at the price of ordering only *within* a partition — which is exactly enough when records carry an entity key (order-id, user-id). A globally ordered stream still needs a serial ordering point; partitioning usually trades that global order for parallelism.
4. **Delivery semantics are a contract between two fallible parties.** At-least-once plus idempotent consumers is the production default; "exactly-once" is a property of a *narrowly configured pipeline* (→ 20.9.02), not a broker feature you switch on. Design the consumer for duplicates and the system is honest.

## How It Works


### 1. Trace a message through processing and recovery

The following sketch uses Confluent's promisified API, exported through the package's `KafkaJS` namespace. It assumes the `orders` topic is provisioned, this group has no committed offset yet, broker addresses are valid, and an injected `handler` validates the schema and makes effects idempotent. Shutdown and authentication are omitted to keep the delivery boundary visible:

```ts
import { KafkaJS } from '@confluentinc/kafka-javascript';

const kafka = new KafkaJS.Kafka({
  'bootstrap.servers': 'localhost:9092',
  'client.id': 'orders-projection',
});
const producer = kafka.producer({ 'allow.auto.create.topics': false });
const consumer = kafka.consumer({
  'group.id': 'orders-projection',
  'auto.offset.reset': 'earliest',
  'enable.auto.commit': false,
});
await producer.connect();
await consumer.connect();

// A stable partitioner and partition count map the same key to one partition.
await producer.send({
  topic: 'orders',
  messages: [{ key: order.id, value: JSON.stringify(order) }],
});

// In a classic group, partitions spread across group members.
// The new example group reads the event sent above. Existing committed offsets
// take precedence; auto.offset.reset applies only when no valid position exists.
await consumer.subscribe({ topics: ['orders'] });
await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    if (message.value === null) {
      throw new Error('orders events do not allow tombstones');
    }
    await handler(JSON.parse(message.value.toString())); // validate schema inside handler
    await consumer.commitOffsets([{
      topic,
      partition,
      offset: (BigInt(message.offset) + 1n).toString(),
    }]); // commit the next offset only after the effect succeeds
  },
});
```

If the effect succeeds but the offset commit fails, the record is delivered again; the handler's idempotency contract makes that retry safe. Do not process records concurrently within one partition and commit a later offset past unfinished work.

RabbitMQ's equivalent shape: publish to an **exchange**; bindings route messages to matching queues according to the exchange type; workers **ack** after processing; unacked work is redelivered to a live consumer.

Both reduce to the same production checklist: *keyed messages for ordering, idempotent handlers for redelivery, dead-letter policy for poison, lag/queue-depth monitoring for truth* (→ 20.9.03).

#### Trace the crash between the effect and acknowledgment

```text
1. Producer receives the required broker acknowledgment for event E.
2. Consumer charges the provider using stable idempotency key E:charge.
3. Consumer crashes before acknowledging E or committing its next offset.
4. Recovery delivers E again; the provider returns the original charge result.
5. Consumer records completion and acknowledges progress.
```

There were two deliveries and one charge under the provider's idempotency contract. A fresh key on step 4 would charge twice. A database-only effect can instead commit its dedup marker and mutation in one transaction; writing the marker first and crashing before the mutation loses work.
A marker in process memory disappears on restart. The [idempotency chapter](../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md) owns the complete effect protocol.

Ordering has another boundary: a partition orders stored records, while concurrent handlers may complete them out of order. Keep per-entity processing serial or enforce entity versions. Changing the topic's partition count or producer partitioner can move a key and split its old/new history across partitions.

### 2. Decide whether temporal decoupling is worth the operational cost

When *not* to reach for a broker — the senior call:

- **You need a synchronous answer to continue** (a checkout that must confirm stock before charging): use a request/response path; async cannot invent an answer.
- **Small N, low rate, same process** — an in-process queue or a simple DB-backed job table beats a new stateful system. A broker is an operational commitment (clusters, partitions, rebalances, upgrades), not a design decoration.
- **You wanted a database** — "store it for later querying" is retention/compaction territory at best; more often it's a table.

### 3. Match the delivery contract to the workload

- **Illustrative order lifecycle**: `orders.created` keyed by order-id → fulfillment and notification consumers each own their partitions; replaying retained records can rebuild a compatible read model; external effects must be disabled or deduplicated during a rebuild.
- **Audit/compliance feeds**: An uncompacted Kafka topic or an external archive can retain event history. Compaction removes superseded values; it is not a complete compliance archive. Set retention and access controls from the actual audit requirement.
- **Fan-out work distribution**: a RabbitMQ fanout exchange hands each deposited document to OCR, antivirus, and indexing workers independently. Give each purpose its own queue; workers competing on one queue divide work rather than each receiving a copy.

### 4. Failures that change the delivery guarantee

- **Treating "exactly-once" as a checkbox.** It is a pipeline property (transactional producers, log-compacted state stores, idempotent sinks); enabling one flag and calling it done produces exactly-once *theater* with at-least-once bugs.
- **Keyless publishing.** Unkeyed records use the producer's partition-selection strategy (often sticky/batched or round-robin), silently destroying per-entity ordering. Key by entity id, or document why order doesn't matter.
- **Unbounded prefetch / unhandled rejections in consumers.** In RabbitMQ, a slow live consumer can hold its prefetch window; a closed channel/connection requeues unacked deliveries. In the Confluent promisified Kafka client, an `eachMessage` failure stops forward progress until recovery handling intervenes. Poison messages need a *policy*, not a crash.
- **Browsing the queue to learn the state of the world.** Queues/log topics are transport, not a query surface; the queryable truth belongs in a read model (→ 20.6.3.04 CQRS).

### 5. Operate around explicit delivery and recovery contracts

- Key messages by the entity whose order you care about; state the invariant ("per order-id, strictly ordered") in the topic's README.
- Make each effect safe under redelivery. An upsert is insufficient if an older event can overwrite newer state; include a version condition and the supported replay horizon.
- Alert on event-to-effect delay and backlog relative to the service objective. Retry and quarantine rates help explain failures; a normal single redelivery need not page.
- Version your event schemas from day one (→ 20.9.03); producers and consumers deploy independently by definition here.
- Capacity-plan partitions for *consumer parallelism*, not throughput today — partitions are the unit of scaling (→ 20.9.02).

## Summary

Brokers buy temporal decoupling with a buffer; persistence and acknowledgment settings decide what survives failure. Kafka provides a replayable partitioned log, while RabbitMQ provides routed queues and replayable Streams. Classic Kafka groups preserve partition ownership and offsets; Share Groups offer per-record queue-like acknowledgment.
RabbitMQ ordering depends on queue type, consumer count, priority and redelivery. Across both, at-least-once delivery is common, so idempotent effects and backlog visibility are central operational concerns. The senior move is knowing when *not* to add one.

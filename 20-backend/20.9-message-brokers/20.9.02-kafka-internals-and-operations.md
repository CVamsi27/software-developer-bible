# Kafka Internals & Operations


---

## Definition

Kafka stores records in a distributed, replicated log that only appends new records. A producer writes to the end of a partition; classic consumers track their positions (**offsets**) and read at their own pace. Ordering is defined within a partition. Producer `acks` settings and the broker's `min.insync.replicas` setting affect when a write is acknowledged and which failures it can survive. Classic consumer groups divide partitions among consumers so processing can scale; Share Groups acknowledge individual records. The following terms describe these parts of the mechanism.

> **Textbook Definition:** Kafka partitions replicated append-only logs among brokers. Classic consumer groups assign partitions and commit offsets; Share Groups distribute records and track per-record acknowledgments. Producer acknowledgments, replica availability and consumer progress define separate durability and recovery boundaries.

| Concept | Meaning |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Partition** | The unit of ordering and parallelism; append-only, replicated |
| **ISR** | In-sync replicas: leader plus followers meeting the in-sync criterion; leader eligibility also depends on version/features |
| `acks` | `0` (fire-and-forget), `1` (leader only), `all` (all current ISR members) — producer durability dial |
| `min.insync.replicas` | Floor on live ISR for `acks=all` writes to be accepted — pairs with `acks=all`, never with `acks=1` |
| **Classic consumer group** | Consumers share a `group.id`; partitions divide among members and progress is committed as offsets |
| **Share Group** | Kafka 4.2+ queue-like mode; members process records individually and acknowledge each record |
| **Rebalance** | Redistribution of partitions when group membership changes |
| **Classic-group lag** | `log-end-offset − committed-offset` per partition; offset distance, not elapsed time |
| **Compaction** | Retention mode keeping the *latest* record per key (state rebuilds, `__consumer_offsets`) |

## First Principles

1. **Acknowledgment must identify which replicas hold the record.** A partition has a leader and followers. Its ISR includes the leader and followers considered caught up. `acks=all` waits for the current ISR; `min.insync.replicas` is the minimum ISR size required to accept such writes. This is not a fixed majority of the replication factor. Newer Kafka versions can also track eligible leader replicas (ELR); inspect that feature before equating the entire eligible election set with the current ISR. With clean election, retaining one acknowledged in-sync copy preserves the record; losing every copy does not.

2. **The consumer, not the broker, owns progress.** For classic groups, committed offsets live in the compacted internal topic (`__consumer_offsets`). This enables replay, independent consumer velocity, and "new service, old history" within retention/access policy — and means a consumer can process ahead of its last commit, so committed lag may overstate unfinished work. Share Groups instead persist individual record acquisition and acknowledgment state.
3. **Rebalancing is the cost of classic-group elasticity.** When a member joins/leaves/hangs, the coordinator redistributes that group's partitions. During the settle, consumption stalls. Rebalance storms come from members that *look* dead (`max.poll.interval.ms` exceeded by slow handlers) — the fix is handler budgets, not bigger timeouts alone.
4. **Backlog and time-to-completion answer different questions.** Offset lag counts offset distance, not milliseconds, and compaction/gaps can make it differ from record count. Track lag trend alongside oldest-unprocessed age and measured event-to-effect latency; throughput alone can hide a growing backlog.

## Why It Matters

Most Kafka interview questions are secretly operations questions: "what happens when a broker dies", "why did p99 spike after deploy", "how do you rebuild a store" — each answers cleanly from the log/ISR/offset model, and each has burned real teams via misconfiguration (`acks=1` with RF=1; unbounded `max.poll.interval.ms`; alerts on throughput instead of lag).

## How It Works

### A durable produce, precisely

This example uses `@confluentinc/kafka-javascript` 1.11.0's promisified API. The client wraps librdkafka; examples use native librdkafka configuration keys. Idempotence and acknowledgments are producer configuration, not per-send options. The example assumes validated `payment` data and provisioned topic settings.

```ts
import { KafkaJS } from '@confluentinc/kafka-javascript';

const kafka = new KafkaJS.Kafka({
  'bootstrap.servers': 'localhost:9092',
  'client.id': 'payments-writer',
});
const producer = kafka.producer({
  'enable.idempotence': true, // broker deduplicates producer-session retries
  acks: -1,
  'allow.auto.create.topics': false,
});
await producer.connect();
await producer.send({
  topic: 'payments',
  messages: [{ key: payment.accountId, value: JSON.stringify(payment) }],
});
// Topic configuration: min.insync.replicas=2; producer: acks=-1 (all).
// ⇒ the ack means "replicated to all current ISR members", not "the leader has it"
```

`enable.idempotence: true` + `acks=all` is a common produce posture: the broker deduplicates retries within one producer session and preserves their order. Application-level repeat sends or external side effects still need their own idempotency.

### Lag as a first-class metric

A committed offset is the **next** offset the group will read after recovery. If the log end is 120 and the committed position is 115, the distance is five. Offsets can exceed JavaScript's safe integer range. This complete helper preserves that precision and marks missing/reset positions explicitly:

```js
function offsetLag(end, committed) {
  const decimal = value => typeof value === 'string' && /^\d+$/.test(value);
  if (!decimal(end) || committed === '-1') return { status: 'unknown', lag: null };
  if (!decimal(committed)) throw new TypeError('committed offset must be decimal or -1');
  const distance = BigInt(end) - BigInt(committed);
  return distance < 0n
    ? { status: 'reset-or-truncated', lag: null }
    : { status: 'known', lag: distance.toString() };
}
console.log(offsetLag('120', '115')); // { status: 'known', lag: '5' }
```

A connected Confluent JavaScript admin client obtains per-partition high offsets and committed positions with `fetchTopicOffsets(topic)` and `fetchOffsets({ groupId, topics: [topic] })`. The latter returns topics containing nested `partitions`. Join on topic and partition before calling the helper. Unknown is not zero. Log-end lag may include records not yet visible to a `read_committed` consumer; its readable end stops at the last stable offset while transactions remain open. This offset-lag calculation is for classic groups; Share Groups acknowledge records individually.

Alert when measured event-to-effect age or backlog recovery time threatens the topic's service objective. A short traffic burst can grow lag without an incident; sustained growth, retry spikes, or one stalled partition need investigation. Offset distance is neither elapsed time nor necessarily the exact count of retained records.

## Code Examples

### Surviving a rebalance storm

A long handler can miss the client's liveness obligations and leave in-flight work after reassignment. In the Confluent JavaScript client, classic groups use librdkafka settings such as `session.timeout.ms`, `heartbeat.interval.ms`, and `max.poll.interval.ms`; the promisified API also provides an `eachMessage` heartbeat helper. Kafka's Java client has its own settings such as `max.poll.records`. These are client settings, not broker settings.

This Confluent promisified-client sketch injects `splitWork` and `processChunkIdempotently`; it illustrates heartbeat placement, not a complete worker.

```ts
await consumer.run({
  eachMessage: async ({ message, heartbeat }) => {
    // Each chunk must finish within the configured session/heartbeat budget.
    for (const chunk of splitWork(message)) {
      await processChunkIdempotently(chunk);
      await heartbeat();
    }
  },
});
```

A Promise timeout alone does not cancel the underlying handler. Propagate an abort signal when supported, keep work idempotent, and bound each chunk; heartbeat calls cannot rescue a blocked JavaScript event loop.

### 2026 protocol reality: KRaft and KIP-848

Since Kafka 4.0, clusters use **KRaft**, the built-in Raft metadata quorum, rather than ZooKeeper. The new consumer rebalance protocol (**KIP-848**) is also generally available from 4.0. In Kafka 4.3, the broker supports the protocol, but a compatible client must explicitly select `group.protocol=consumer`; upgrading the broker does not automatically migrate every client. The Confluent JavaScript client 1.11.0 exposes this setting, while the examples above use the classic protocol:

```ts
const consumer = kafka.consumer({
  'group.id': 'payments-projector',
  'group.protocol': 'consumer',
});
```

The new protocol uses incremental assignments and server-controlled heartbeat/session settings (`group.consumer.*`). Client `heartbeat.interval.ms`, `session.timeout.ms`, and classic partition assignors no longer configure those groups. **`max.poll.interval.ms` still limits consumer poll progress**; moving heartbeat control to the server does not permit an indefinitely blocked handler. Check broker/client version compatibility and migration behavior before enabling this protocol.

Kafka 4.2 also made **Share Groups** production-ready. A share group assigns records individually and tracks per-record acknowledgments and delivery attempts, making it useful for queue-like parallel work. It does not replace classic groups when per-partition order and offset-based replay are core requirements. Kafka's Java client documents a Share Consumer API, but Confluent JavaScript 1.11.0 does not expose one in its public Node.js type declarations; do not infer Node.js Share Group support from the broker feature.

### Rebuilding state from the log

Compacted topic `users.current` (key = user-id, value = latest state). A new classic group uses `auto.offset.reset: earliest`, joins, and materializes retained state. Existing committed offsets take precedence over this setting; reset offsets deliberately for a rebuild. Tombstone retention and compaction/trimming must allow the rebuild to finish before required deletions disappear. This is the operational payoff of the log model (→ 20.9.01).

## Real-World Applications

- **Illustrative payment pipeline**: `acks=all`, 3 RF, `min.insync.replicas=2` on payment-adjacent topics; lag dashboard per consumer group; DLQ topic per consumer with a weekly poison-message review.
- **CDC pipelines**: Debezium writes row changes into compacted Kafka topics; downstream materialized views rebuild by replay — schema evolution handled at the envelope (→ 20.9.03).
- **Multi-region durability**: stretch clusters or MirrorMaker 2 with the same quorum reasoning — RF is per-cluster; asynchronous inter-region replication can lose the unreplicated tail on failover; zero loss is not guaranteed (→ 30.3.2 RPO/RTO drills).

## Common Mistakes

- **`acks=1` on money topics.** Leader dies before followers catch up: acked writes vanish. RF=3 with `acks=all` and minimum ISR 2 is a common availability/durability choice, not a guarantee against losing every retained copy. State the failure model, backup/recovery path, and tolerated unavailability.
- **Thousand-partition "headroom".** Each partition is files, fds, replication traffic, and rebalance surface. Size from measured per-partition throughput, target consumer parallelism, key skew, and recovery cost; grow by measurement; a topic's partition count can increase but cannot decrease in place. Reducing it requires a new topic and an explicit migration; increasing it can change key mapping.
- **Alerting on throughput.** A pipeline can move millions of messages *into a growing backlog*. The SLI is lag/queue depth and end-to-end latency, not messages/sec.
- **Manual partition assignment "to control things".** You lose group elasticity and rebalance safety for a benefit `assign`-based tooling should own. Use group assignment for normal worker elasticity; manual assignment is appropriate for deliberate replay/admin tools.
- **Schema changes as afterthoughts.** Consumers deserialize what producers serialize; unversioned field drops crash consumers overnight. Envelopes and registry checks belong in CI (→ 20.9.03).

## Best Practices

- Standard posture: RF=3, `min.insync.replicas=2`, `acks=all`, idempotent producers, keyed messages.
- `unclean.leader.election.enable=false` (the default since 0.11) — acknowledge *unavailability* rather than silently accept data loss; write the choice down per topic.
- One consumer group per distinct purpose; never share a group across unrelated services — otherwise services receive only assigned subsets instead of each purpose seeing the whole stream.
- Disable unintended topic creation at the applicable layer: client `allow.auto.create.topics` and broker `auto.create.topics.enable` are distinct settings. Provision reviewed topic configuration explicitly.
- Run the broker with JMX/Prometheus exporters; the four graphs that matter: ISR shrink events, under-replicated partitions, request handler idle, group rebalance count.

## Summary

Kafka operations combine ISR acknowledgment rules with consumer-group progress and recovery. Get the produce posture right once (`acks=all`, idempotent, keyed), make lag the SLI, budget handlers against the selected client's liveness/heartbeat contract, and treat partition count and topic creation as reviewed infra. Everything else is the log model paying rent (→ 20.9.01).

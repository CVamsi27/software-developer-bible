# Kafka Internals & Operations

> **TL;DR:** Kafka is a replicated, partitioned log whose operations story is four verbs: **replicate** (ISR shrinks and expands; `acks=all` waits for it), **rebalance** (group membership changes redistribute partitions — the classic latency cliff), **compact** (log cleanup for keyed topics), and **drain** (consumer lag is the SLI that says whether any of it is working). Tune brokers rarely; measure lag always.

---

## First Principles

1. **Replication is majority quorum over a log.** Each partition has one leader and N followers; in-sync replicas (ISR) are the followers caught up within `replica.lag.time.max.ms`. A write acknowledged with `acks=all` is durable against any `min.insync.replicas − 1` broker loss — durability is a *configurable quorum*, not a binary.
2. **The consumer, not the broker, owns progress.** Offsets live in a compacted internal topic (`__consumer_offsets`). This single decision is why replay, independent consumer velocity, and "new service, old history" all fall out for free — and why a consumer that never commits is invisible to the broker but visible in lag.
3. **Rebalancing is the cost of group elasticity.** When a member joins/leaves/hangs, the group coordinator redistributes that group's partitions. During the settle, consumption stalls. Rebalance storms come from members that *look* dead (`max.poll.interval.ms` exceeded by slow handlers) — the fix is handler budgets, not bigger timeouts alone.
4. **Lag is the one number that cannot lie.** Throughput graphs can be green while consumers silently fall behind. End-to-end latency through a Kafka pipeline is, to first order, `produce → visible` + **consumer lag** + `process time`.

## Definition

| Concept | Meaning |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| **Partition** | The unit of ordering and parallelism; append-only, replicated |
| **ISR** | In-sync replicas: followers current enough to be election-eligible |
| `acks` | `0` (fire-and-forget), `1` (leader only), `all` (ISR quorum) — producer durability dial |
| `min.insync.replicas` | Floor on live ISR for `acks=all` writes to be accepted — pairs with `acks=all`, never with `acks=1` |
| **Consumer group** | Set of consumers sharing a `group.id`; partitions divide among members |
| **Rebalance** | Redistribution of partitions when group membership changes |
| **Consumer lag** | `log-end-offset − committed-offset` per partition; the SLI |
| **Compaction** | Retention mode keeping the *latest* record per key (state rebuilds, `__consumer_offsets`) |

## Why It Matters

Most Kafka interview questions are secretly operations questions: "what happens when a broker dies", "why did p99 spike after deploy", "how do you rebuild a store" — each answers cleanly from the log/quorum/offset model, and each has burned real teams via misconfiguration (`acks=1` with RF=1; unbounded `max.poll.interval.ms`; alerts on throughput instead of lag).

## How It Works

### A durable produce, precisely

```ts
const producer = kafka.producer({
  idempotent: true, // broker dedups retries via PID + sequence
});
await producer.connect();
await producer.send({
  topic: 'payments',
  messages: [{ key: payment.accountId, value: JSON.stringify(payment) }],
});
// broker-side: topic config `min.insync.replicas: 2` + `acks: all` (default)
// ⇒ the ack means "replicated to the ISR quorum", not "the leader has it"
```

`idempotent: true` + `acks=all` is the standard produce posture: retries without duplicates, durability without a fencing token of your own.

### Lag as a first-class metric

```ts
// admin fetch: per-partition lag for the group
const offsets = await admin.fetchOffsets({ groupId, topics });
const ends = await admin.fetchTopicOffsets(topic);
const lag = offsets.flatMap(o => {
  const end = ends.find(e => e.partition === o.partition);
  return [{ partition: o.partition, lag: Number(end!.offset) - Number(o.offset) }];
});
// export to Prometheus; alert on TREND, not single spikes
```

Alert shape (→ 40.4.5.01): *page* on lag growing monotonically over N minutes for any partition; *ticket* on absolute lag above a per-topic SLO; never alert on a redelivery.

## Code Examples

### Surviving a rebalance storm

The failure: handlers take 40s, `max.poll.interval.ms` is 45s, a GC pause pushes one poll to 46s — the coordinator evicts the member, partitions move, the incoming consumer starts from the *committed* offset, and the evicted one's in-flight work double-processes. The repair:

```ts
consumer.run({
  eachMessage: async ({ message }) => {
    await withTimeout(handler(message), 5_000);   // handler budget < poll budget
  },
  // broker cooperates: max.poll.interval.ms: 60_000, max.poll.records: 100
});
```

Handler budgets strictly below the poll interval; batch sizes sized so the *worst* batch fits; consumers are idempotent (→ 20.9.01) so the race the eviction leaves behind is a non-event.

### Rebuilding state from the log

Compacted topic `users.current` (key = user-id, value = latest state). A new service starts at `fromBeginning`, materializes the state store, joins the group — replay is a *restart*, not a migration script. This is the operational payoff of the log model (→ 20.9.01).

## Real-World Applications

- **docita-shaped worker deployable**: `acks=all`, 3 RF, `min.insync.replicas=2` on payment-adjacent topics; lag dashboard per consumer group; DLQ topic per consumer with a weekly poison-message review.
- **CDC pipelines**: Debezium writes row changes into compacted Kafka topics; downstream materialized views rebuild by replay — schema evolution handled at the envelope (→ 20.9.03).
- **Multi-region durability**: stretch clusters or MirrorMaker 2 with the same quorum reasoning — RF is per-cluster; async replication between regions means accepting RPO > 0 (→ 30.3.2 RPO/RTO drills).

## Common Mistakes

- **`acks=1` on money topics.** Leader dies before followers catch up: acked writes vanish. `acks=all` + `min.insync.replicas=2` (RF≥3) is the floor for anything you can't afford to lose.
- **Thousand-partition "headroom".** Each partition is files, fds, replication traffic, and rebalance surface. Start at `consumers × 2`, grow by measurement; partition count is easy to raise, painful to lower.
- **Alerting on throughput.** A pipeline can move millions of messages *into a growing backlog*. The SLI is lag/queue depth and end-to-end latency, not messages/sec.
- **Manual partition assignment "to control things".** You lose group elasticity and rebalance safety for a benefit `assign`-based tooling should own. Prefer cooperative-sticky assignment and let the group work.
- **Schema changes as afterthoughts.** Consumers deserialize what producers serialize; unversioned field drops crash consumers overnight. Envelopes and registry checks belong in CI (→ 20.9.03).

## Best Practices

- Standard posture: RF=3, `min.insync.replicas=2`, `acks=all`, idempotent producers, keyed messages.
- `unclean.leader.election.enable=false` (the default since 0.11) — acknowledge *unavailability* rather than silently accept data loss; write the choice down per topic.
- One consumer group per distinct purpose; never share a group across unrelated services — one slow consumer starves the others' partitions.
- Pin `allow.auto.create.topics=false` in prod; topics are infra, created by reviewable config.
- Run the broker with JMX/Prometheus exporters; the four graphs that matter: ISR shrink events, under-replicated partitions, request handler idle, group rebalance count.

## Summary

Kafka operations is quorum math over logs plus group choreography over consumers. Get the produce posture right once (`acks=all`, idempotent, keyed), make lag the SLI, budget handlers under the poll interval, and treat partition count and topic creation as reviewed infra. Everything else is the log model paying rent (→ 20.9.01).

## Cheat Sheet

```text
Durability   = acks=all + min.insync.replicas=2 + RF=3 (+ idempotent producer)
Ordering     = per partition ⇒ key by entity id
The SLI      = consumer lag (trend), not throughput
Rebalances   = handler budget < max.poll.interval; idempotent consumers absorb overlaps
State rebuild= compacted topic + fromBeginning = replay-as-restart
Partitions   = unit of parallelism; start small, grow measured
```

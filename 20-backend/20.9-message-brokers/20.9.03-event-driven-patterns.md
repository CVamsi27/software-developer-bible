# Event-Driven Patterns on a Broker

An order row commits, then the service crashes before publishing `order.placed`. The order exists, but fulfillment has no event to process. The patterns below make that gap, duplicate delivery, poison work, and replay explicit.

## Definition

Event-driven systems fail at specific boundaries: publication competes with a database commit, a delivery repeats, poison work blocks progress, or a payload exceeds the transport budget. Each pattern here addresses one of those failures. Follow the boundary and its recovery path instead of memorizing a catalog.

> **Textbook Definition:** Event-driven reliability patterns address coordination failures such as dual writes, duplicate delivery and poison messages. Each pattern establishes a specific boundary for recorded intent, processing state or recovery rather than universal delivery guarantees.

| Pattern | Problem it solves | One-line shape |
| ------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Envelope** | Consumers need identity, causality, and version context | `{event_id, event_type, occurred_at, producer, schema_version, payload}` plus transport key/routing metadata |
| **Outbox** | Atomic business write and publication intent | Same-transaction `outbox` insert; relay/CDC publishes after commit (→ 20.6.3.06) |
| **Dead-letter queue** | Poison messages must not block the stream | Bounded retries → DLQ topic/queue → alert + review + reprocess/discard |
| **Claim check** | Payloads too big for the pipe | Store blob in object storage; event carries the reference |
| **Content-based routing** | Same event, different consumers care differently | An explicit router inspects payloads; exchanges route using supported keys/headers |
| **Compacted state topic** | Rebuildable read state from the log | Keyed latest-value retention; new consumers replay to state (→ 20.9.02) |

## First Principles

1. **An event is a fact, not a command — until you make it one.** Facts ("order was placed") let any number of consumers react independently; commands ("charge the card") assign work to exactly one consumer. Mixing the two on one topic couples producers to consumers' semantics. Decide per topic which contract it carries; the name should say which (`orders.events` vs `payments.commands`).
2. **Schema evolution is a compatibility problem, not a serialization problem.** Producers and consumers deploy independently — that is the entire point of the broker — so the contract must survive version skew: test changes against the required backward/forward compatibility direction and actual readers. Optional fields and ignored unknown fields help only when the format, defaults and consumer validation permit them. A registry (Confluent Schema Registry, JSON Schema, Avro/Protobuf) turns this from convention into check.
3. **Failure handling is a designed path, not an exception.** A consumer that retries forever can block its partition or queue; one that drops silently corrupts the business process. One defensible path uses bounded retries with backoff, then moves poison work to a **monitored dead-letter queue** for an owner to repair/replay or discard. Some ordering contracts require holding later events until the failed one is repaired.
4. **Idempotency lives in the consumer, not the broker.** At-least-once redelivery is a fact of distributed life (crash between process and ack); the dedup key, upsert, or version check that makes reprocessing a no-op is the consumer's contribution to the contract (→ 30.3.2.03).

## How It Works


### 1. Carry identity and processing outcomes across failures

#### The envelope, concretely

```jsonc
{
  "event_id": "d4542ffc-906c-4a93-bfce-f160491e8924", // stable identity across retries
  "event_type": "order.placed",           // past tense: a fact happened
  "occurred_at": "2026-09-19T10:12:33Z",
  "producer": "orders-svc@1.14.2",
  "schema_version": 3,
  "trace_id": "4bf92f35...",              // joins the distributed trace
  "payload": { "order_id": "order_8841", "total_minor": 12900 }
}
```

`event_id`, event type, time, producer and schema identity belong to the event contract. A Kafka key or RabbitMQ routing key is transport metadata: keep it consistent with the entity that needs ordering or routing, but do not treat it as a substitute for the payload's business identity. `event_id` enables consumer-side dedup; `trace_id` helps correlate work; propagating the full trace context, including parent/span metadata and flags, establishes trace relationships (→ 40.4.1); `schema_version` selects the decoding contract. Neither a trace ID nor tenant ID supplied in an event proves authorization; validate producer identity and tenant scope at the transport and handler boundaries.

The payload is also a public contract. Do not expose a producer's persistence shape or make consumers depend on private nested fields. Document defaults and enum changes, then test compatibility against the actual readers.

#### Bounded retry → DLQ, in the consumer

This JavaScript policy accepts transport adapters. `decode` validates bytes and classifies malformed data as permanent; `handle` owns effect idempotency; `quarantine` must durably accept the original record or reject. All adapters must honor their own bounded deadlines/cancellation. It does not configure a live broker or commit offsets.

```js
async function processOrQuarantine(record, {
  decode, handle, quarantine, sleep, isTransient, random = Math.random,
  maxAttempts = 3,
}) {
  if (!Number.isInteger(maxAttempts) || maxAttempts < 1 || maxAttempts > 10) {
    throw new RangeError('maxAttempts must be between 1 and 10');
  }
  let failure;
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      const event = decode(record.value);
      await handle(event);
      return 'processed';
    } catch (error) {
      failure = error;
      if (!isTransient(error) || attempt === maxAttempts) break;
      const capMs = Math.min(30_000, 100 * 2 ** (attempt - 1));
      await sleep(Math.floor(random() * capMs));
    }
  }
  await quarantine(record, failure); // redact error details; protect original payload
  return 'quarantined';
}
```

A source adapter may acknowledge/commit only after this function resolves. The quarantine adapter should store a safe error classification, not blindly export `String(error)` containing credentials or patient data. Preserve protected original bytes under a retention/access policy.
Rejecting a malformed event is different from retrying a temporary database outage.

This is a consumer retry/quarantine policy, not automatic broker behavior. Successful quarantine lets processing advance; a crash between DLQ publication and source-offset commit may publish it twice. Key quarantine by consumer purpose plus source topic/partition/offset (or use a Kafka transaction) and preserve the original bytes so invalid JSON can be investigated.
Moving a failed entity event to a DLQ changes ordering: later events may be processed without it; decide whether that is acceptable for this topic.

### 2. Evolve contracts and preserve replayability

#### Schema evolution that survives version skew

```jsonc
// v2 → v3: ADD optional field, bump version, never repurpose meaning
{
  "event_type": "order.placed",
  "schema_version": 3,
  "payload": { "order_id": "...", "total_minor": 12900,
               "currency": "EUR" }              // new in v3, optional
}
```

Consumer contract: read `schema_version` and apply documented defaults for missing optional fields. Whether unknown fields are ignored or rejected depends on the decoder and validation policy; make that choice explicit and test it. Registry compatibility checks catch format-level breakage in CI, while consumer contract tests check semantics such as currency units and enum assumptions (→ 20.9.02).

#### Claim check: the event names a protected blob

An imaging event can carry an immutable object ID, version, byte length and checksum instead of embedding a large scan. Store the object first, then publish its reference. A failed publication can leave an orphan, so cleanup needs a grace period and recorded ownership.
Do not publish a reference before its object becomes readable.

The consumer resolves the object through its authorized storage adapter, verifies tenant access, length and checksum, then processes it. Avoid arbitrary publisher-supplied URLs that can redirect fetches to private services. Retain the object for the entire allowed message retention/retry/replay window; deleting it after the first consumer acknowledgment breaks independent consumers and later replays.
Decide how missing or corrupt objects enter quarantine.

RabbitMQ direct/topic exchanges match routing keys, and headers exchanges match message headers. They do not inspect arbitrary JSON fields. Payload-based routing needs an explicit trusted router or a producer that derives a validated routing key.
Kafka consumers filtering a shared topic still fetch its records; that is different from broker-side filtering.

For RabbitMQ quorum queues, RabbitMQ 4.3 adds native delayed retries. Configure `delayed-retry-type` and minimum/maximum delay; the delay is bounded linear backoff based on `delivery-count`. The broker increments that count for specific failure paths, such as a session/channel crash or AMQP 1.0 `modified` with `delivery_failed=true`; a plain return may leave it unchanged.
Choose the retry type with that behavior in mind. Set the delivery limit and terminal dead-letter policy explicitly, and monitor retry backlog. Other queue types or older deployments need their own retry design.

#### Outbox → broker, commit intent before relaying

```text
1. BEGIN; UPDATE orders ...; INSERT INTO outbox(event_id, topic, key, payload, state='pending'); COMMIT;
2. Relay reads committed intents (polling or CDC), publishes with stable identity and checkpoints after required broker acceptance.
3. At-least-once between relay and broker ⇒ consumers dedup on event_id.
```

The outbox row preserves the event intent. A relay can recover after the writer exits; an uncertain publish acknowledgment can still cause duplicate delivery. Consumers need effect-aware deduplication, and external effects retain a provider boundary (→ 20.6.3.06 for the full pattern).
Keep deduplication state for the supported replay horizon, unless the effect is safe for older duplicates by construction.

### 3. Where these patterns fit

- **Illustrative async processing**: appointment events enter an outbox; workers deduplicate effects; quarantined work has an owner and a review/replay policy.
- **Multi-tenant fan-out**: a tenant-activity fanout exchange routes each event to analytics, email, and audit consumers; each owns its DLQ and its own schema-compat checks.
- **State materialization**: `users.current` compacted topic rebuilt by a new group from its earliest retained offset, with deletion retention long enough for the rebuild — the compacted-state pattern from 20.9.02 applied to a read model (→ 20.6.3.04 CQRS).

## Summary

Broker guarantees depend on configuration and the processing boundary. Envelopes provide identity, compatible schemas tolerate version skew, monitored retry and quarantine paths support recovery, and idempotent consumers handle redelivery. An outbox makes publication intent atomic with local state; relay delivery remains a separate operation.

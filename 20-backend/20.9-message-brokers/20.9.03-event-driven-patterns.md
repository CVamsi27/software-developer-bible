# Event-Driven Patterns on a Broker


---

## Definition

Event-driven systems fail in recurring ways — a publish that must be atomic with a database write, a duplicate delivery, a poison message, a payload too large for the pipe — and each pattern below is the field's named answer to one of those failures. Learn them as problem-response pairs rather than catalog entries; the interview question is never "name a pattern," it is "what happens when this breaks."

| Pattern | Problem it solves | One-line shape |
| ------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **Envelope** | Consumers need identity, causality, and version context | `{event_id, event_type, occurred_at, producer, schema_version, partition_key, payload}` |
| **Outbox** | Atomic "DB write + publish" | Same-transaction `outbox` insert; relay/CDC publishes after commit (→ 20.6.3.06) |
| **Dead-letter queue** | Poison messages must not block the stream | Bounded retries → DLQ topic/queue → alert + review + reprocess/discard |
| **Claim check** | Payloads too big for the pipe | Store blob in object storage; event carries the reference |
| **Content-based routing** | Same event, different consumers care differently | Exchange bindings / topic keys route by fields, not per-consumer topics |
| **Compacted state topic** | Rebuildable read state from the log | Keyed latest-value retention; new consumers replay to state (→ 20.9.02) |

## First Principles

1. **An event is a fact, not a command — until you make it one.** Facts ("order was placed") let any number of consumers react independently; commands ("charge the card") assign work to exactly one consumer. Mixing the two on one topic couples producers to consumers' semantics. Decide per topic which contract it carries; the name should say which (`orders.events` vs `payments.commands`).
2. **Schema evolution is a compatibility problem, not a serialization problem.** Producers and consumers deploy independently — that is the entire point of the broker — so the contract must survive version skew: add fields as optional, never repurpose, make consumers ignore unknown fields. A registry (Confluent Schema Registry, JSON Schema, Avro/Protobuf) turns this from convention into check.
3. **Failure handling is a designed path, not an exception.** A consumer that retries forever blocks its partition/queue; one that drops silently corrupts the business process. The only honest structure is bounded retries with backoff, then a **dead-letter queue** that is *monitored and reviewed*, then reprocess or discard as a recorded decision.
4. **Idempotency lives in the consumer, not the broker.** At-least-once redelivery is a fact of distributed life (crash between process and ack); the dedup key, upsert, or version check that makes reprocessing a no-op is the consumer's contribution to the contract (→ 30.3.2.03).

## Why It Matters

These are the patterns interview loops probe when they say "event-driven architecture": not the diagram, but the failure questions — what happens on duplicate, on poison, on schema skew, on a publish that must be atomic with a DB write. Each pattern below is one of those questions answered.

## How It Works

### The envelope, concretely

```jsonc
{
  "event_id": "01JAZX7W2C9F3N5Q6R7S8T9VWX",        // ULID: time-ordered, unique
  "event_type": "order.placed",           // past tense: a fact happened
  "occurred_at": "2026-09-19T10:12:33Z",
  "producer": "orders-svc@1.14.2",
  "schema_version": 3,
  "partition_key": "order_8841",          // ordering scope (→ 20.9.01)
  "trace_id": "4bf92f35...",              // joins the distributed trace
  "payload": { "order_id": "order_8841", "total_minor": 12900 }
}
```

Rules that pay for themselves: `event_id` enables consumer-side dedup; `trace_id` helps correlate work; propagating the full trace context (including parent/span metadata and flags) establishes trace relationships (→ 40.4.1); `schema_version` lets consumers route by contract, not guess.

### Bounded retry → DLQ, in the consumer

```ts
await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    let failure: unknown;
    for (let attempt = 1; attempt <= 3; attempt++) {
      try {
        // decodeAndValidate classifies malformed JSON/schema as non-transient.
        // Its topic contract explicitly handles/rejects null-valued tombstones.
        const evt = decodeAndValidate(message.value);
        await handler(evt); // idempotent effect
        return;
      } catch (error) {
        failure = error;
        if (!isTransient(error) || attempt === 3) break;
        await sleep(100 * 2 ** (attempt - 1)); // bounded backoff; budget heartbeats too
      }
    }
    await dlq.publish({
      topic, partition, offset: message.offset,
      valueBase64: message.value?.toString('base64') ?? null,
      error: String(failure), firstSeen: message.timestamp,
    }, { key: message.key });
    // A failed DLQ publish must reject: don't advance past unrecorded work.
  },
});
```

This is a consumer retry/quarantine policy, not automatic broker behavior. Successful quarantine lets processing advance; a crash between DLQ publication and source-offset commit may publish it twice. Key the quarantine record by source topic/partition/offset (or use a Kafka transaction) and preserve the original bytes so invalid JSON can be investigated. Moving a failed entity event to a DLQ changes ordering: later events may be processed without it; decide whether that is acceptable for this topic.



## Code Examples

### Schema evolution that survives version skew

```jsonc
// v2 → v3: ADD optional field, bump version, never repurpose meaning
{
  "event_type": "order.placed",
  "schema_version": 3,
  "payload": { "order_id": "...", "total_minor": 12900,
               "currency": "EUR" }              // new in v3, optional
}
```

Consumer contract: read `schema_version`, ignore unknown fields, apply defaults for missing ones. Registry-backed producers reject incompatible changes in CI — the check that makes "consumers deploy independently" true rather than hopeful (→ 20.9.02 mistake list).

### Outbox → broker, the atomic bridge

```text
1. BEGIN; UPDATE orders ...; INSERT INTO outbox(event_id, topic, key, payload, state='pending'); COMMIT;
2. Relay (poller or CDC/Debezium) reads pending rows, publishes to the broker, marks sent.
3. At-least-once between relay and broker ⇒ consumers dedup on event_id.
```

The outbox row *is* the event of record: crash between commit and publish is recovered by the relay, not by hope; duplicates are absorbed downstream by idempotency (→ 20.6.3.06 for the full pattern).

## Real-World Applications

- **Illustrative async processing**: appointment events enter an outbox; workers deduplicate effects; quarantined work has an owner and a review/replay policy.
- **Multi-tenant fan-out**: a tenant-activity fanout exchange routes each event to analytics, email, and audit consumers; each owns its DLQ and its own schema-compat checks.
- **State materialization**: `users.current` compacted topic rebuilt by every new service from offset 0 — the compacted-state pattern from 20.9.02 applied to a read model (→ 20.6.3.04 CQRS).

## Common Mistakes

- **Events named as commands on shared topics.** `charge-card` on `orders.events` assigns work to whoever listens — fan-out semantics with command semantics. Name the contract, split the topics.
- **DLQ as a graveyard.** Unmonitored DLQs are how teams "handle" poison: silently, forever. The DLQ has an alert, an owner, and a review cadence, or it doesn't exist.
- **Retrying inside the handler without idempotency.** Retry-after-partial-write is worse than no retry: it duplicates side effects. Idempotency first, then retries.
- **Payload-as-API.** Consumers reading nested producer internals couple to the producer's schema evolution forever. The envelope plus a *contracted* payload is the boundary.
- **Big payloads on the pipe.** 5 MB base64 blobs in every event waste broker memory and consumer time; claim-check the blob, ship the reference.

## Best Practices

- One topic per contract, named for the fact (`orders.placed`) or command (`payments.authorize`); partition key = the entity whose order matters.
- Registry or JSON-Schema check in CI; consumers ignore unknown fields by default; enforce the chosen backward/forward compatibility mode; optional additions are one common safe change.
- DLQs alert and get reviewed; reprocessing is a recorded decision with a reason.
- Dedup on `event_id` with an atomic effect+dedup transaction where possible (or an inherently idempotent write); keep dedup state for every permitted redelivery/replay window; treat redelivery as routine weather.
- Propagate trace context with events so async hops can be correlated or linked (→ 40.4.1.03 tracing).

## Summary

The broker gives you at-least-once and a pipe; the patterns give you a system: envelopes for identity and versioning, schemas that tolerate skew, retry-then-DLQ failure paths that stay monitored, idempotent consumers that make redelivery boring, and the outbox that makes publishing atomic with state. Master these five and every "event-driven" interview question becomes a design discussion.

# WebSockets — Connection Lifecycle, Scaling, Rooms, Namespaces

## WebSocket Protocol
- **HTTP upgrade:** Client sends `Upgrade: websocket` header
- **Full-duplex:** Both client and server can send messages at any time
- **Persistent connection:** Stays open until explicitly closed
- **Binary or text:** Supports both `ws.send("text")` and `ws.send(buffer)`

## Connection Lifecycle
1. Client connects: `new WebSocket("ws://server")`
2. Server handles upgrade: `wss.on("connection", (ws) => {...})`
3. Bidirectional messaging
4. Client or server closes: `ws.close()` or `ws.terminate()`

## Socket.IO (most common in NestJS)
```typescript
// Server
@WebSocketGateway({ cors: { origin: "*" } })
export class ClinicGateway implements OnGatewayConnection {
  @WebSocketServer() server: Server;

  handleConnection(client: Socket) {
    const token = client.handshake.auth.token;
    const user = verifyJwt(token);
    client.join(`clinic:${user.clinicId}`);
  }

  @SubscribeMessage("appointment:update")
  handleAppointmentUpdate(@MessageBody() data: AppointmentUpdate) {
    this.server.to(`clinic:${data.clinicId}`).emit("appointment:changed", data);
  }
}
```

## Scaling WebSockets
| Challenge | Solution |
|-----------|----------|
| Single server limit | Sticky sessions or Redis adapter |
| Room broadcast | Redis pub/sub between instances |
| Connection state | External store (Redis) |
| Load balancing | L4 (TCP) or L7 with session affinity |

### Redis Adapter (Socket.IO)
```typescript
// Server
import { createAdapter } from "@socket.io/redis-adapter";
import { createClient } from "redis";

const pubClient = createClient({ url: "redis://localhost:6379" });
const subClient = pubClient.duplicate();
io.adapter(createAdapter(pubClient, subClient));
```

## Failure Modes
| Failure | Handling |
|---------|----------|
| Client disconnect | Reconnect with exponential backoff |
| Server restart | Client reconnects, misses events → use event sourcing |
| Network partition | Fallback to polling |
| Message loss | Persist critical events in database |

## WebSocket vs SSE vs Polling

| Feature | WebSocket | SSE | Polling |
|---------|-----------|-----|----------|
| **Direction** | Bidirectional | Server → Client | Client → Server |
| **Protocol** | ws:// or wss:// | HTTP | HTTP |
| **Connection** | Persistent | Persistent | New per request |
| **Use case** | Chat, collaboration, real-time | Notifications, updates | Simple status checks |
| **NestJS support** | @WebSocketGateway | @Sse() decorator | N/A |

## Common Interview Questions

**Q: How do you scale WebSockets across multiple instances?**

```
Problem: Client connects to Server A, but another client is on Server B
  → How do they communicate?

Solution 1: Redis Pub/Sub
  - All instances subscribe to Redis channels
  - Message published to Redis → all instances receive it
  - Each instance forwards to relevant connected clients
  
Solution 2: Sticky Sessions
  - Load balancer routes same client to same server
  - Problem: server failure loses all connections
  
Solution 3: External State Store
  - Store connection metadata in Redis
  - Any instance can look up where a client is connected
```

**Q: What happens when a WebSocket connection drops?**

```
Client-side:
  1. Detect disconnect (onclose event)
  2. Wait with exponential backoff (1s, 2s, 4s, 8s, max 30s)
  3. Reconnect with last known state
  4. Request missed events since last known timestamp
  
Server-side:
  1. Detect disconnect (onDisconnect handler)
  2. Clean up room subscriptions
  3. Mark user as offline (if presence tracking)
  4. Buffer events for offline user (optional)
```

**Q: How do you handle message ordering?**

```
Problem: Messages arrive out of order due to network latency

Solution 1: Sequence numbers
  - Each message has a monotonically increasing sequence number
  - Client buffers out-of-order messages
  - Client requests missing sequences
  
Solution 2: Timestamp-based
  - Each message has a server timestamp
  - Client processes in timestamp order
  - Problem: clock skew between servers
  
Solution 3: Single-writer per entity
  - Only one client can edit a resource at a time
  - Prevents conflicts entirely
```

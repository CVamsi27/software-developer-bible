# Server-Sent Events (SSE)

> **Unidirectional real-time communication over HTTP — simpler than WebSockets for server→client streaming.**

---

## What Is SSE?

SSE is a standard for pushing data from server to client over HTTP. Unlike WebSockets (bidirectional), SSE is unidirectional: server sends, client listens. Built on plain HTTP — works through proxies, firewalls, and load balancers that often break WebSocket connections.

```
WebSocket (Bidirectional):
Client ←──→ Server  (full-duplex, custom protocol)

SSE (Server → Client):
Client ←──── Server  (unidirectional, plain HTTP)
```

---

## SSE vs WebSocket vs Polling

| Feature | SSE | WebSocket | HTTP Polling |
|---------|-----|-----------|--------------|
| **Direction** | Server → Client | Bidirectional | Client → Server |
| **Protocol** | HTTP/1.1 or HTTP/2 | ws:// or wss:// | HTTP |
| **Auto-reconnect** | ✅ Built-in | ❌ Manual | ❌ Manual |
| **Event IDs** | ✅ Built-in (Last-Event-ID) | ❌ Manual | ❌ Manual |
| **Binary data** | ❌ Text only | ✅ Yes | ✅ Yes |
| **Proxy support** | ✅ Excellent | ⚠️ Often blocked | ✅ Excellent |
| **Max connections** | 6 per domain (HTTP/1.1) | No limit | No limit |
| **Use case** | Notifications, feeds, updates | Chat, gaming, collaboration | Polling for changes |

## NestJS SSE Implementation

### Server

```typescript
// events.controller.ts
import { Controller, Sse, MessageEvent } from '@nestjs/common';
import { Observable, Subject } from 'rxjs';
import { map } from 'rxjs/operators';

@Controller('events')
export class EventsController {
  private appointmentSubject = new Subject<MessageEvent>();

  // SSE endpoint
  @Sse('appointments/:clinicId')
  streamAppointments(
    @Param('clinicId') clinicId: string,
  ): Observable<MessageEvent> {
    return this.appointmentSubject.pipe(
      filter((event) => event.data.clinicId === clinicId),
      map((event) => ({
        data: JSON.stringify(event.data),
        id: event.id,
        type: event.type,
      })),
    );
  }

  // Emit events from anywhere in the app
  emitAppointmentCreated(appointment: Appointment) {
    this.appointmentSubject.next({
      id: appointment.id,
      type: 'appointment-created',
      data: appointment,
    } as MessageEvent);
  }
}
```

### Client

```typescript
// useSSE.ts
import { useEffect, useState } from 'react';

function useSSE<T>(url: string): T | null {
  const [data, setData] = useState<T | null>(null);

  useEffect(() => {
    const eventSource = new EventSource(url);

    eventSource.onmessage = (event) => {
      setData(JSON.parse(event.data));
    };

    eventSource.onerror = () => {
      // EventSource auto-reconnects!
      console.log('SSE connection lost, reconnecting...');
    };

    return () => eventSource.close();
  }, [url]);

  return data;
}

// Usage
function ClinicDashboard({ clinicId }: { clinicId: string }) {
  const latestAppointment = useSSE<Appointment>(
    `/events/appointments/${clinicId}`
  );

  return (
    <div>
      {latestAppointment && (
        <div className="notification">
          New appointment: {latestAppointment.patientName}
        </div>
      )}
    </div>
  );
}
```

## Common Patterns

### Reconnection with Last-Event-ID

```typescript
// Server: include event ID
@Sse('events')
stream(): Observable<MessageEvent> {
  return this.eventSubject.pipe(
    map((event, index) => ({
      data: JSON.stringify(event),
      id: String(index), // Event ID for reconnection
    })),
  );
}

// Client: EventSource sends Last-Event-ID header on reconnect
const es = new EventSource('/events');
es.onmessage = (event) => {
  console.log('Event ID:', event.lastEventId);
  // Server can use this to replay missed events
};
```

### Heartbeat (Keep-Alive)

```typescript
// Server: send keep-alive every 30s to prevent proxy timeouts
@Sse('events')
stream(): Observable<MessageEvent> {
  return interval(30000).pipe(
    map(() => ({
      data: '', // Empty keep-alive
    })),
  );
}
```

## Interview Questions

**Q: "When would you choose SSE over WebSockets?"**

> SSE when: (1) communication is primarily server→client (notifications, feeds, real-time updates), (2) you need auto-reconnect (built-in), (3) you're behind proxies/load balancers that block WebSocket upgrades, (4) you want simpler implementation (plain HTTP). WebSocket when: (1) you need bidirectional communication (chat, gaming, collaborative editing), (2) you need binary data transfer, (3) you need sub-millisecond latency. For Docita: SSE for appointment notifications (server→client), WebSocket for real-time calendar collaboration (bidirectional).

---

## 30-Second Interview Version

> SSE is server→client streaming over plain HTTP. Simpler than WebSockets for unidirectional use cases (notifications, feeds). Built-in auto-reconnect and event IDs via Last-Event-ID header. Limitation: 6 concurrent connections per domain in HTTP/1.1 (solved with HTTP/2 or domain sharding). Use when you only need server→client push. Use WebSocket when you need bidirectional communication. For Docita: SSE for appointment notifications on dashboard, WebSocket for real-time calendar editing.

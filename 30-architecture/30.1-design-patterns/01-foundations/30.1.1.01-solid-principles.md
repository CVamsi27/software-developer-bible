# SOLID Principles

> **The 5 principles every object-oriented design should follow.** Robert C. Martin's foundational set. SOLID is the basis for most design patterns, and a senior engineer should be able to apply all 5 instinctively. Interviewers ask.

## TL;DR

- **S** — Single Responsibility: one class, one job
- **O** — Open/Closed: open for extension, closed for modification
- **L** — Liskov Substitution: subclasses must be substitutable for parent classes
- **I** — Interface Segregation: many specific interfaces > one general interface
- **D** — Dependency Inversion: depend on abstractions, not concretions

---

## Why it matters

SOLID is the foundation of maintainable OOP code. Without it:
- Classes get bloated (multiple responsibilities)
- Changes break unrelated things
- Subclasses surprise users
- Interfaces are too coarse
- Tight coupling makes testing hard

In an interview, you should be able to:
1. Name all 5
2. Give a code example of each violation
3. Refactor to fix the violation
4. Recognize when a pattern implements a principle

## S — Single Responsibility Principle (SRP)

**Rule:** A class should have only one reason to change. One class, one job.

**Violation:**

```typescript
// User class does too much: auth, persistence, email
class User {
  authenticate(password: string): boolean { /* ... */ }
  saveToDatabase(): void { /* ... */ }
  sendWelcomeEmail(): void { /* ... */ }
  generateReport(): string { /* ... */ }
}
```

**Fix:** Split into separate classes.

```typescript
class UserAuthenticator {
  authenticate(user: User, password: string): boolean { /* ... */ }
}

class UserRepository {
  save(user: User): void { /* ... */ }
  findById(id: string): User | null { /* ... */ }
}

class WelcomeEmailSender {
  send(user: User): void { /* ... */ }
}

class UserReportGenerator {
  generate(user: User): string { /* ... */ }
}
```

**How to recognize:** "I have to change this class for two unrelated reasons." If yes, split.

**In interviews:** Common LLD question: "Design a parking lot." If your class has methods for parking, payment, display, AND notification, that's a violation.

## O — Open/Closed Principle (OCP)

**Rule:** Software entities should be open for extension, but closed for modification.

**Meaning:** You should be able to add new functionality without changing existing code.

**Violation:**

```typescript
class DiscountCalculator {
  calculate(customerType: string, amount: number): number {
    if (customerType === 'regular') return amount;
    if (customerType === 'silver') return amount * 0.9;
    if (customerType === 'gold') return amount * 0.8;
    // Adding 'platinum' requires MODIFYING this class
    return amount;
  }
}
```

**Fix:** Use polymorphism / strategy pattern.

```typescript
interface DiscountStrategy {
  apply(amount: number): number;
}

class RegularDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount; }
}

class SilverDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount * 0.9; }
}

class GoldDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount * 0.8; }
}

// Adding PlatinumDiscount: create a new class, don't touch existing code
class PlatinumDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount * 0.7; }
}

class DiscountCalculator {
  constructor(private strategy: DiscountStrategy) {}
  calculate(amount: number): number {
    return this.strategy.apply(amount);
  }
}
```

**In interviews:** "We added a new payment provider without modifying the existing payment processing code. We just added a new PaymentProvider class." That's OCP.

## L — Liskov Substitution Principle (LSP)

**Rule:** Objects of a superclass should be replaceable with objects of a subclass without breaking the application.

**Meaning:** A subclass must honor the contract of the parent. If the parent says "this method returns X," the subclass shouldn't return Y.

**Violation (classic):**

```typescript
class Rectangle {
  constructor(protected width: number, protected height: number) {}

  setWidth(width: number): void { this.width = width; }
  setHeight(height: number): void { this.height = height; }
  area(): number { return this.width * this.height; }
}

class Square extends Rectangle {
  setWidth(width: number): void {
    this.width = width;
    this.height = width; // Square forces width == height
  }
  setHeight(height: number): void {
    this.width = height;
    this.height = height;
  }
}

// Test fails!
function test(r: Rectangle): void {
  r.setWidth(5);
  r.setHeight(4);
  console.log(r.area()); // Expects 20, gets 16 for Square
}
```

**Fix:** Don't make Square a subclass of Rectangle. They're not actually substitutable.

```typescript
interface Shape {
  area(): number;
}

class Rectangle implements Shape {
  constructor(private width: number, private height: number) {}
  area(): number { return this.width * this.height; }
}

class Square implements Shape {
  constructor(private side: number) {}
  area(): number { return this.side * this.side; }
}
```

**How to recognize:** "I have to check the type of this object to know how to use it." If yes, LSP violation.

**In interviews:** "If I pass this subclass to a function expecting the parent, does the function still work correctly?" If no, LSP violation.

## I — Interface Segregation Principle (ISP)

**Rule:** Many client-specific interfaces are better than one general-purpose interface.

**Meaning:** Don't force a class to implement methods it doesn't need.

**Violation:**

```typescript
interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
  code(): void;
  manage(): void;
  design(): void;
}

class Developer implements Worker {
  work(): void { /* ... */ }
  eat(): void { /* ... */ }
  sleep(): void { /* ... */ }
  code(): void { /* ... */ }
  manage(): void { throw new Error("Not a manager"); } // Forced to implement
  design(): void { throw new Error("Not a designer"); } // Forced to implement
}
```

**Fix:** Split into smaller interfaces.

```typescript
interface Workable {
  work(): void;
}

interface Eatable {
  eat(): void;
}

interface Sleepable {
  sleep(): void;
}

interface Codeable {
  code(): void;
}

class Developer implements Workable, Eatable, Sleepable, Codeable {
  work(): void { /* ... */ }
  eat(): void { /* ... */ }
  sleep(): void { /* ... */ }
  code(): void { /* ... */ }
}
```

**In interviews:** Common in TypeScript/Java: "The Repository interface has 15 methods but my use case only needs 3." That's ISP violation. Split.

## D — Dependency Inversion Principle (DIP)

**Rule:** High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details. Details should depend on abstractions.

**Meaning:** Depend on interfaces, not concrete classes.

**Violation:**

```typescript
// High-level NotificationService depends on low-level EmailSender
class EmailSender {
  send(to: string, subject: string, body: string): void {
    // Send via SendGrid
  }
}

class NotificationService {
  private emailSender = new EmailSender(); // Tight coupling!

  notifyUser(userId: string, message: string): void {
    // ...
    this.emailSender.send(user, "Alert", message);
    // What if we want to add SMS or push? Have to modify this class.
  }
}
```

**Fix:** Depend on abstraction.

```typescript
interface MessageSender {
  send(to: string, subject: string, body: string): Promise<void>;
}

class EmailSender implements MessageSender {
  async send(to: string, subject: string, body: string): Promise<void> {
    // Send via SendGrid
  }
}

class SmsSender implements MessageSender {
  async send(to: string, subject: string, body: string): Promise<void> {
    // Send via Twilio (subject becomes the SMS body)
  }
}

class NotificationService {
  constructor(private sender: MessageSender) {} // Injected dependency

  async notifyUser(userId: string, message: string): Promise<void> {
    // ...
    await this.sender.send(user, "Alert", message);
    // Add a new sender: just inject a different one
  }
}
```

**In interviews:** "We use constructor injection to depend on interfaces, not concrete implementations. Easy to mock for tests, easy to swap."

**Also known as:** Dependency Injection (DI). Inversion of Control (IoC).

## The 5 principles summary

| Letter | Name | Rule | Common violation |
| ------ | --------------------- | ------------------------------------------- | --------------------------------------- |
| **S** | Single Responsibility | One class, one job | God class with 20 methods |
| **O** | Open/Closed | Open for extension, closed for modification | Switch/if-else for each new variant |
| **L** | Liskov Substitution | Subclasses substitutable for parents | Subclass breaks parent's contract |
| **I** | Interface Segregation | Many specific > one general | Class implements methods it doesn't use |
| **D** | Dependency Inversion | Depend on abstractions | `new ConcreteClass()` everywhere |

## SOLID in the LLD interview

**Common LLD question:** "Design a parking lot."

**Without SOLID:**

```typescript
class ParkingLot {
  park(vehicle): void { /* ... */ }
  unpark(ticket): void { /* ... */ }
  calculateFee(ticket): number { /* ... */ }
  printTicket(vehicle): Ticket { /* ... */ }
  notifyOwner(vehicle): void { /* ... */ }
  // God class
}
```

**With SOLID:**

```typescript
// SRP: each class has one job
class ParkingLot {
  constructor(
    private lot: Level[],
    private feeCalculator: FeeCalculator,
    private notifier: OwnerNotifier
  ) {}
  park(vehicle): Ticket { /* ... */ }
  unpark(ticket): void { /* ... */ }
}

class FeeCalculator { // SRP: only calculates fees
  calculate(ticket: Ticket): number { /* ... */ }
}

class HourlyFeeStrategy implements FeeStrategy { /* ... */ }
class FlatFeeStrategy implements FeeStrategy { /* ... */ }
// OCP: add new strategies without modifying

class OwnerNotifier { /* ... */ }
class EmailNotifier implements OwnerNotifier { /* ... */ } // DIP
class SmsNotifier implements OwnerNotifier { /* ... */ } // DIP
```

The senior signal: name the principle as you apply it.

## Common interview questions on SOLID

**Q: "What's the difference between SRP and OCP?"**
- SRP: one class, one reason to change
- OCP: extend behavior without modifying existing code
- Different problems, complementary solutions

**Q: "When should I NOT use SOLID?"**
- Tiny scripts / one-off code
- Performance-critical code where abstractions add overhead
- Simple CRUD apps where the patterns add complexity without benefit
- Prototypes

**Q: "Does SOLID apply to functional programming?"**
- Some principles yes, others no. SRP, ISP, DIP translate. OCP is more about polymorphism which is less of a thing in FP. LSP doesn't really apply.

## SOLID + Design Patterns

Many GoF patterns implement SOLID principles:

- **Strategy** implements OCP
- **Decorator** implements OCP
- **Factory** implements DIP
- **Observer** implements SRP + DIP
- **Adapter** implements ISP (often)
- **Template Method** uses LSP

See the rest of the bible's design patterns for how each implements SOLID.

---

## Anti-patterns

- **Cargo cult SOLID.** "I'll add an interface for everything" → over-engineering.
- **Premature abstraction.** Adding layers before you need them.
- **Misapplying LSP.** Sometimes two things shouldn't be in a hierarchy. Don't force it.
- **SRP taken too literally.** "A class should have one method" is wrong. It should have one responsibility, which can be many methods.
- **ISP taken too far.** 50 interfaces of 1 method each = same complexity, more files.

## Summary

SOLID is the foundation of maintainable OOP design. The 5 principles — Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion — work together to produce code that is flexible, testable, and easy to modify. Most GoF design patterns are implementations of one or more SOLID principles. In interviews, name the principle, show a violation, and demonstrate the fix with code.

## Cheat Sheet
```text
SOLID CHEAT SHEET
═══════════════════════════════════════════════════════════════

S — Single Responsibility
  One class = one reason to change
  Fix: Split god classes into focused classes
  Red flag: "I have to change this for 2 unrelated reasons"

O — Open/Closed
  Open for extension, closed for modification
  Fix: Strategy pattern, polymorphism, plugins
  Red flag: Switch/if-else for each new variant

L — Liskov Substitution
  Subclass must work wherever parent works
  Fix: Don't force broken hierarchies
  Red flag: "I have to check the type to know how to use it"

I — Interface Segregation
  Many specific interfaces > one general
  Fix: Split fat interfaces into role interfaces
  Red flag: Class implements methods it throws errors on

D — Dependency Inversion
  Depend on abstractions, not concretions
  Fix: Constructor injection, interfaces
  Red flag: new ConcreteClass() everywhere

IN INTERVIEWS:
• Name the principle as you apply it
• Show the violation → show the fix
• Connect to GoF patterns (Strategy=OCP, Factory=DIP)
```

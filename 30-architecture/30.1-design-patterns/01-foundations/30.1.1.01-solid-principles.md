# SOLID Principles

> **A design changes safely when callers can keep their promises.** SOLID offers five ways to examine change boundaries. Use each principle to diagnose a concrete dependency; adding more classes or interfaces is not proof of a better design.

## Definition

**SOLID** comprises five design rules for keeping a codebase changeable, each of which answers a different question about a dependency:

> **Textbook Definition:** SOLID is a set of object-oriented design principles governing responsibility, extension, behavioral substitution, interface dependencies, and the direction of dependencies between policy and implementation.

| Principle | Question it answers | Evidence to investigate |
| ------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| **S**ingle Responsibility | *Which stakeholders require this module to change?* | Independent policy changes repeatedly affect the same implementation |
| **O**pen/Closed | *Which recurring variation should a stable boundary absorb?* | Each new variant requires changing callers that should be unaffected |
| **L**iskov Substitution | *Can this implementation honor its callers' contract?* | A required operation rejects previously valid inputs or weakens results |
| **I**nterface Segregation | *Which operations does this client actually depend on?* | Unrelated operations force client implementations or releases to change |
| **D**ependency Inversion | *Who owns the contract between policy and detail?* | A vendor's types and lifecycle rules determine the business interface |

These questions examine change cost and behavioral correctness. A large class, a switch statement or an exception is evidence to inspect, not proof of a violation. For example, a switch over a small stable set can be clearer than a strategy registry; an unsupported operation is a substitution defect only if the contract required it. Diagnose the actual dependency and propose the smallest change that preserves the promised behavior.

## First Principles

A feature request can change several things at once: a discount rule, a storage schema, and an email format. Those decisions often have different owners and release schedules. If one module embeds all three, changing one requires retesting the others.

A boundary helps only when a caller can rely on it. A new discount implementation that silently rejects an input accepted by the old one forces callers to branch again. A provider interface copied directly from one vendor's SDK can also carry that vendor's churn into business rules.

This gives three design questions: which decisions should change together, which behavior must remain true across implementations, and who owns the contract between them? The five principles examine those questions from different sides.

In a review or interview, start with a concrete change or failing caller. Explain which dependency caused it, how the proposed boundary helps, and what extra complexity it introduces. Naming the principle supports that reasoning; it does not replace it.

## S — Single Responsibility Principle (SRP)

**Rule:** A module should respond to one coherent source of change. A responsibility can include several methods that maintain the same rule.

In *Clean Architecture*, that source is an **actor**: a stakeholder or group with aligned requirements. It is not necessarily one person, one team, one method or one runtime action. Keep code that maintains the same invariant together; separate decisions whose owners need them to change independently.

**Violation:** These are structural sketches: omitted method bodies and domain types are not a runnable implementation.

```typescript
// User class does too much: auth, persistence, email
class User {
  authenticate(password: string): boolean { /* ... */ }
  saveToDatabase(): void { /* ... */ }
  sendWelcomeEmail(): void { /* ... */ }
  generateReport(): string { /* ... */ }
}
```

**Fix:** Separate the independent decisions. Authentication policy, database mapping, welcome-message content, and report layout can change independently; each gets a boundary. A registration service may still coordinate them without embedding their implementations.

```typescript
class UserAuthenticator {
  authenticate(user: User, password: string): boolean { /* ... */ }
}

class UserRepository {
  save(user: User): void { /* ... */ }
  findById(id: string): User | null { /* ... */ }
}

class WelcomeEmailSender {
  send(user: User): void { /* ... */ }
}

class UserReportGenerator {
  generate(user: User): string { /* ... */ }
}
```

**How to recognize:** Identify two independently requested changes, then trace the code each touches. If one change can alter the other's rule, consider a boundary. Several methods that enforce one account invariant can belong together; splitting each into a class can scatter that invariant and increase coupling.

**In interviews:** In a parking-lot design, ask whether a fee-rule change requires editing occupancy tracking. A coordinator can call parking, payment, and notification; the coupling arises when it owns all their rules, not merely because it has several methods.

## O — Open/Closed Principle (OCP)

**Rule:** Software entities should be open for extension, but closed for modification.

**Meaning:** Stable policy should support the anticipated variation through an extension boundary. New requirements can still require editing existing code; an abstraction does not make every future change additive.

**Violation:**

```typescript
class DiscountCalculator {
  calculate(customerType: string, amount: number): number {
    if (customerType === 'regular') return amount;
    if (customerType === 'silver') return amount * 0.9;
    if (customerType === 'gold') return amount * 0.8;
    // Adding 'platinum' requires MODIFYING this class
    return amount;
  }
}
```

**Fix:** Use polymorphism / strategy pattern.

```typescript
interface DiscountStrategy {
  apply(amount: number): number;
}

class RegularDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount; }
}

class SilverDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount * 0.9; }
}

class GoldDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount * 0.8; }
}

// Add a strategy for a new discount policy
class PlatinumDiscount implements DiscountStrategy {
  apply(amount: number): number { return amount * 0.7; }
}

class DiscountCalculator {
  constructor(private strategy: DiscountStrategy) {}
  calculate(amount: number): number {
    return this.strategy.apply(amount);
  }
}
```

```typescript
console.log(new DiscountCalculator(new SilverDiscount()).calculate(100)); // 90
console.log(new DiscountCalculator(new PlatinumDiscount()).calculate(100)); // 70
```

The caller invokes `calculate`; the calculator delegates to its injected strategy. Adding platinum leaves that delegation unchanged. The code that chooses or registers the strategy still changes. If discounts later need a customer's purchase history, this interface may need to change too: it protects one known axis of variation, not every future requirement. The arithmetic uses illustrative numbers, not a production currency/rounding policy.

## L — Liskov Substitution Principle (LSP)

**Rule:** Objects of a superclass should be replaceable with objects of a subclass without breaking the application.

**Meaning:** A subtype must preserve what callers were promised: it cannot demand stricter inputs, weaken promised results, or break state invariants. In contract terms, it must not strengthen preconditions or weaken postconditions. Matching method signatures alone do not establish substitutability.

**Violation (classic):**

```typescript
class Rectangle {
  constructor(protected width: number, protected height: number) {}

  setWidth(width: number): void { this.width = width; }
  setHeight(height: number): void { this.height = height; }
  area(): number { return this.width * this.height; }
}

class Square extends Rectangle {
  setWidth(width: number): void {
    this.width = width;
    this.height = width; // Square forces width == height
  }
  setHeight(height: number): void {
    this.width = height;
    this.height = height;
  }
}

// Caller relies on width and height being independently mutable
function test(r: Rectangle): void {
  r.setWidth(5);
  r.setHeight(4);
  console.log(r.area()); // Contract promises 20 after these two assignments
}
test(new Rectangle(1, 1)); // 20
test(new Square(1, 1));    // 16: setHeight also changed width
```

**Fix:** Don't make Square a subclass of Rectangle. They're not actually substitutable.

```typescript
interface Shape {
  area(): number;
}

class Rectangle implements Shape {
  constructor(private width: number, private height: number) {}
  area(): number { return this.width * this.height; }
}

class Square implements Shape {
  constructor(private side: number) {}
  area(): number { return this.side * this.side; }
}
```

This fix changes the contract to area-only shapes. It does not repair callers that require independently mutable dimensions; those callers should still require `Rectangle`. A mathematical square can be a rectangle while failing the particular mutable API shown here.

**How to recognize:** A caller must compensate for a subtype breaking the promised behavior. A legitimate type check alone does not prove an LSP violation.

## I — Interface Segregation Principle (ISP)

**Rule:** Clients should not be forced to depend on operations they do not use. Split a contract when it makes unrelated clients change or implement irrelevant behavior.

**Meaning:** Expose the operations each caller needs. A shift scheduler that only starts work should depend on `Workable`; it should not need management or design operations. Implementers forced to throw for unused methods are a symptom of that broad contract, but the design question starts with the clients.

**Violation:**

```typescript
interface Worker {
  work(): void;
  manage(): void;
  design(): void;
}

function startShift(worker: Worker): void {
  worker.work();
}

class Developer implements Worker {
  work(): void { /* ... */ }
  manage(): void { throw new Error("Not a manager"); }
  design(): void { throw new Error("Not a designer"); }
}
```

`startShift` only needs `work`, yet its type requires all three operations and forces `Developer` to provide behavior it does not own.

**Fix:** Define contracts around actual caller needs. One implementation can satisfy more than one small contract when that matches its role.

```typescript
interface Workable {
  work(): void;
}

interface Manageable {
  manage(): void;
}

interface Designable {
  design(): void;
}

function startShift(worker: Workable): void {
  worker.work();
}

class Developer implements Workable {
  work(): void { /* ... */ }
}
```

A reporting client can similarly depend on a read-only repository port while a command handler receives a write port. Split around real callers and change boundaries; a large implementation is not automatically a bad client contract.

## D — Dependency Inversion Principle (DIP)

**Rule:** High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details. Details should depend on abstractions.

**Meaning:** The notification policy owns a small contract. Transport adapters conform to that contract instead of making the policy import their SDKs.

Without the boundary, a service that creates its own email SDK client also owns its credentials, provider payload, and error handling. Replacing email requires editing that policy. Here is an independent, runnable TypeScript wiring example; the adapters log instead of contacting a provider:

```typescript
interface MessageSender {
  send(message: string): Promise<void>;
}

class ConsoleEmailSender implements MessageSender {
  constructor(private address: string) {}
  async send(message: string): Promise<void> {
    console.log(`email to ${this.address}: ${message}`);
  }
}

class ConsoleSmsSender implements MessageSender {
  constructor(private number: string) {}
  async send(message: string): Promise<void> {
    console.log(`sms to ${this.number}: ${message}`);
  }
}

class NotificationService {
  constructor(private sender: MessageSender) {}
  async notify(message: string): Promise<void> {
    await this.sender.send(message);
  }
}

async function main(): Promise<void> {
  // Application setup chooses a destination and transport.
  await new NotificationService(new ConsoleEmailSender('demo@example.test'))
    .notify('Appointment confirmed');
  await new NotificationService(new ConsoleSmsSender('+15550100000'))
    .notify('Appointment confirmed');
}
void main();
// email to demo@example.test: Appointment confirmed
// sms to +15550100000: Appointment confirmed
```

The policy only knows `MessageSender`. Application setup imports the concrete adapters and constructs them. In a real provider adapter, the contract must specify whether resolution means queued, accepted, or delivered; different transports must not silently promise different guarantees. Destination lookup, retries, and delivery tracking are outside this demonstration.

DIP is the direction of source dependencies: provider details implement a contract used by the policy. Dependency injection supplies an object to that policy; injection alone does not invert a dependency if the injected type still exposes a vendor SDK. Inversion of control is the broader idea of handing some control to another component.

## Apply the principles in an LLD

In a parking-lot design, begin with a change request rather than a class diagram. If occupancy rules and fee policy have different owners or release schedules, make that separation explicit:

| Change request | Boundary to examine | Principle in play |
| ------------------------------------------ | --------------------------------------------------------------------------- | -------------------------------------------------------- |
| Change how a space is assigned | Keep occupancy invariants in the lot model | SRP: state and allocation change together |
| Add a recurring fee variation | Add a `FeePolicy` only if it protects stable callers from expected variants | OCP: extension protects a known change axis |
| Add a read-only occupancy report | Give the report a query contract rather than a write-heavy lot service | ISP: the caller depends on only the operations it needs |
| Replace a payment or notification provider | Keep provider SDKs behind application-owned ports | DIP: policy owns the contract; adapters implement it |
| Add another fee implementation | Require the same inputs, rounding rules, errors and result guarantees | LSP: every implementation must honor the caller contract |

The boundaries still have costs: extra types, wiring, deployment configuration and tests. Strategy, factory and observer patterns can help implement a boundary, but using one does not prove the design is open, substitutable or loosely coupled. A single stable switch may be cheaper than a registry; a new provider adapter is useful only if it prevents provider details from leaking into policy.

In an interview, trace one concrete change: name who needs it, show the dependency it would touch, state the contract that must remain true, then explain the smallest boundary and its cost. Test the contract across implementations, especially invalid input, failure and state transitions. Naming SOLID after the reasoning is stronger than treating it as a checklist.

---

## Summary

SOLID examines responsibility, extension, substitution, client contracts, and dependency direction. Choose a boundary because it isolates a real source of change while preserving behavior. The discount and notification examples protect specific variation; the square example shows why a type-compatible replacement can still break a caller. Interfaces and patterns are useful when their reduction in change cost exceeds their added complexity.

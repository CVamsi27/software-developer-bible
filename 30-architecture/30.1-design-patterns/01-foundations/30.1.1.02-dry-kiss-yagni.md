# DRY, KISS, YAGNI & Other Design Principles

Two features contain the same calculation. One rule changes, and only one copy gets updated. Sharing the rule prevents drift — but sharing code that merely looks alike couples two things that should change independently. The design question is what must stay consistent, and what complexity the current requirement earns.

```typescript
// Same formula in two places: one rule change, two edits, one missed.
function checkoutSubtotal(items: readonly Item[]): number { /* rule A */ return 0; }
function invoiceSubtotal(items: readonly Item[]): number { /* rule A, copied */ return 0; }
```

## Definition

**DRY**, **KISS**, and **YAGNI** are design **heuristics** for deciding when to share a rule, how much structure a requirement needs, and when to defer a capability. They guide trade-offs; none is a rule to apply mechanically.

> **Textbook Definition:** DRY gives each piece of system knowledge one authoritative representation; KISS favors the least complex design that satisfies its requirements; YAGNI defers capabilities that have no demonstrated need. The three principles address duplication, complexity, and speculative work respectively.

## First Principles

A system represents facts that change. If separate components encode the same rule independently, one requirement update needs coordinated edits, and a missed edit leaves contradictory behavior. One authoritative representation removes that drift — but it also gives its callers a shared contract, so unrelated rules must not be forced together.

Every abstraction has a present cost in code, tests, wiring, and reader attention, while a future capability has uncertain value until its requirement is known. Choose the smallest design that preserves current invariants and known constraints, and keep it easy to change when evidence reveals a new need.

## How It Works

### 1. Share the rule that must stay true (DRY)

Suppose checkout and invoicing both calculate the same pre-tax item subtotal. If the rule changes, two independent implementations can drift:

```typescript
// Inputs are validated non-negative integer cents and quantities.
type Item = { unitPriceCents: number; quantity: number };

function checkoutSubtotal(items: readonly Item[]): number {
  return items.reduce((sum, item) => sum + item.unitPriceCents * item.quantity, 0);
}

function invoiceSubtotal(items: readonly Item[]): number {
  return items.reduce((sum, item) => sum + item.unitPriceCents * item.quantity, 0);
}
```

Give the shared rule one home when both callers are governed by the same business fact:

```typescript
function subtotalCents(items: readonly Item[]): number {
  return items.reduce((sum, item) => sum + item.unitPriceCents * item.quantity, 0);
}
```

Invoice tax or checkout discounts compose that subtotal without changing the shared rule. If the two calculations have different rounding, eligibility, or ownership rules, keep those parts separate even if current code looks alike. Production money code must also define currency, rounding, and numeric-range behavior; this example assumes inputs and total fit the chosen integer representation.

The useful test for DRY is whether one rule change requires coordinated edits in multiple places — duplicated wording alone is not enough. A shared helper creates a shared contract, so extraction is worthwhile only when that coupling matches the domain. A third example can reveal variation two examples hid (the **Rule of Three**), but it is evidence for uncertain abstractions, not a gate: two clients bound by the same legal rule can share it immediately.

### 2. Keep the design adequate and small (KISS)

KISS favors the least complex design that satisfies known requirements. For one report sorting an in-memory list, a copied list and a sort may be enough:

```typescript
const byNewest = [...orders].sort((a, b) => b.createdAt - a.createdAt);
```

A configurable query engine, plugin registry, and cache add concepts without answering a current need. If data volume, latency target, or sort options change, measure the constraint and choose the structure that addresses it. "Simple" never means ignoring input validation, security, errors, concurrency, or recovery when the system requires them.

Complexity is justified by a concrete constraint. A bounded retry policy addresses a known transient failure; idempotency prevents a repeated request from duplicating an effect; a transaction protects a state invariant shared by concurrent requests. State the constraint and the guarantee the mechanism provides — a large traffic estimate or a vague wish to be flexible establishes neither.

### 3. Defer imagined capabilities, preserve known constraints (YAGNI)

YAGNI delays a feature or abstraction supporting a presumed future need. A generic export framework for formats no customer can export yet costs build and test time, taxes every reader's mental model, and may encode the wrong variation. Add the capability when a real requirement makes its behavior clear.

YAGNI does not mean "never prepare for change." A public API version, required data-retention policy, security boundary, or committed migration plan is already a constraint, even if its consequences arrive later. Keep code easy to change with clear contracts and tests, but avoid unused extension points. When considering future-proofing, compare the cost of a later change against the ongoing cost of carrying the abstraction now.

Together: centralize a rule that must stay consistent, keep that shared boundary as small as it can be, and avoid variation points for capabilities nobody needs. Refactoring remains available when later evidence changes the design.

### 4. Reuse behavior without promising a subtype

**Composition** delegates work to a collaborator; **inheritance** says a subtype can stand in for its parent under the parent's behavioral contract. Use inheritance when that substitution is true and useful; use composition when behavior varies independently or reuse does not imply "is-a." A geometric label alone proves nothing: a square cannot preserve a rectangle caller's promise that width and height change independently. See [OOP concepts](30.1.1.03-oop-concepts.md) and [Liskov Substitution Principle](30.1.1.01-solid-principles.md#l--liskov-substitution-principle-lsp) for the full substitution argument.

Composition also costs: collaborators need contracts and wiring. A plain function is simpler when there is no meaningful runtime variation.

### 5. Make effects and responsibilities visible

A method's name and contract should tell callers which effects it performs. A low-level `saveUser` that also sends email and updates analytics hides independent failure points. A `registerUser` workflow may intentionally coordinate these steps, but naming them does not make them atomic — if persistence succeeds and notification fails, retry needs a defined identity and recovery policy; an outbox can coordinate durable delivery.

Separate concerns when their policies or owners change independently. In registration, the HTTP adapter parses requests and maps responses, the application service applies registration rules, a password hasher owns hashing, and a repository owns persistence mapping. The service stores the hash through the repository, then returns a public projection such as `{ id, email }`; the HTTP response never exposes the persistence record or password hash. These boundaries clarify ownership; they do not make the steps one transaction. See [Single Responsibility Principle](30.1.1.01-solid-principles.md#s--single-responsibility-principle-srp) for actor-driven reasons to change.

### 6. Related heuristics worth knowing

| Heuristic | Useful interpretation | Boundary to remember |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Principle of Least Astonishment (POLA)** | Make names, return values, and side effects match what callers expect. | A clear name exposes effects; it does not make partial success atomic. |
| **Law of Demeter** | Depend on collaborators' behavior, not their internal object layout. | A long chain is a warning to inspect, not proof of a violation; immutable data access can be intentional. |
| **Tell, Don't Ask** | Ask the object owning an invariant to perform the operation preserving it. | An in-memory method cannot serialize competing writes in a database. |
| **Convention over configuration** | Provide a discoverable default, with an explicit override when real cases differ. | An undocumented or impossible-to-override convention hides behavior. |
| **Robustness principle (Postel's Law)** | The historical slogan says be conservative when sending, liberal when receiving. | Broad acceptance can entrench ambiguity and security bugs. Follow the protocol spec, accept only defined compatibility variations, send canonical output. |

[RFC 9413](https://www.rfc-editor.org/rfc/rfc9413.html) revisits this: tolerance can preserve interoperability, but accepting unspecified input indefinitely makes errors part of the protocol and weakens security. Treat tolerance as a deliberate compatibility policy, not a blanket command.

## Apply the trade-off in an interview

When asked to design a feature, trace one real change rather than naming principles as a checklist:

1. State the rule or invariant and who owns it.
2. Identify which callers must follow the same rule and which have independent policies.
3. Choose the smallest design meeting present constraints; name any complexity the constraints require.
4. Defer speculative capabilities, but preserve known compatibility, security, and recovery requirements.
5. Explain what happens when a step fails or a request repeats, then name the test proving the guarantee.

For example, share a mandated subtotal between checkout and invoices, keep invoice tax in the invoice policy, and avoid a generic fee plug-in until a real fee variation needs one. If a repeated checkout request could charge twice, idempotency is a present correctness requirement, not speculative flexibility.

## Summary

DRY centralizes shared knowledge, not coincidentally similar code. KISS chooses the least complex design satisfying real constraints; YAGNI delays speculative capabilities while preserving requirements already known. Share only rules that should change together, keep invariants with their owners, and explain each abstraction by the change or failure it handles.

# DRY, KISS, YAGNI & Other Design Principles

> **A useful abstraction removes a real change cost.** These principles help decide what to share, how much machinery a requirement needs, and which future capabilities can wait.

## Definition

**DRY, KISS, and YAGNI** are three design heuristics that constrain *when to generalize* — they are usually invoked together, but each rules out a different mistake:

> **Textbook Definition:** DRY requires authoritative knowledge to have one representation; KISS favors the least complex adequate design; YAGNI postpones capabilities until a demonstrated requirement justifies them.

```text
DRY    Don't Repeat Yourself          ─▶ duplicate *knowledge*, not duplicated *text*
KISS   Keep It Simple                ─▶ the simplest design that meets today's requirement
YAGNI  You Aren't Gonna Need It      ─▶ don't build for a speculative future
```

They form a tension that defines their correct use, not a checklist that always agrees:

1. **DRY is about knowledge, not characters.** Two identical-looking functions that change for different reasons (one formats money for an invoice, one for a report) are *not* duplication — merging them couples unrelated change. The mark of real duplication is that the copies must be edited together.
2. **YAGNI bounds DRY.** The **Rule of Three** suggests waiting for more examples when the variation is uncertain. A third case can provide evidence; it is not a prerequisite for sharing a rule that is already clearly authoritative.
3. **KISS is the tie-breaker** when the other two conflict: if the DRY abstraction needs configuration, generics, and a factory, the simpler duplication may be cheaper to own — the cost of an abstraction is paid by every future reader.

The honest way to state them: **DRY decides what deserves a single home, KISS decides how simple that home should be, and YAGNI decides whether to build it at all yet.**

## First Principles

A business rule copied into three modules requires three coordinated edits. Missing one leaves inconsistent behavior. Moving it into one helper removes that coordination cost, but callers now share the helper's contract and release schedule.

Every abstraction therefore trades one cost for another. If its options must grow whenever unrelated clients change, shared code can become harder to own than separate code. Speculative flexibility also has a certain cost today and uncertain value later. Start from the actual rule and known constraints, then compare the coordination, reading, and maintenance costs of the alternatives.

## Why it matters

A request such as “make this flexible” is incomplete. Ask what varies, who controls it and how often it changes. A configurable tax rule may need a policy boundary; a fixed calculation may need only a function. Likewise, testability can require separating I/O, while correctness under retries can require durable state. Choose the mechanism from that constraint, then explain its cost.

## DRY — Don't Repeat Yourself

**Rule:** Every piece of knowledge should have a single, authoritative representation in the system.

**Violation:**

```typescript
// Assume all three totals mean the same pre-tax item subtotal.
// Item is { price: number; quantity: number }; examples are independent snippets.
function calculateOrderTotal(items: Item[]): number {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  return total;
}

function calculateInvoiceTotal(items: Item[]): number {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  return total;
}

function calculateCartTotal(items: Item[]): number {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  return total;
}
```

**Fix:** Extract.

```typescript
function calculateItemsTotal(items: Item[]): number {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
```

For items priced 10 with quantity 2 and 5 with quantity 1, the shared helper returns 25. Order, invoice, and cart code can reuse it only while they share that subtotal rule. If invoice totals later include a billing adjustment, keep the shared subtotal and compose the adjustment in invoice code; do not force cart callers to understand it. Production currency code also needs an explicit representation and rounding policy.

**When to apply:** When the copies represent knowledge that must change together. If that relationship is uncertain, more cases may reveal it.

**When NOT to apply:** Coincidental similarity. Two pieces of code that look the same but mean different things — extracting them creates coupling. Example: "both have a `name` field" doesn't mean they should share a `Nameable` interface.

**In interviews:** "These callers use the same mandated subtotal rule, so it has one authoritative implementation. Their distinct billing adjustments remain outside it."

## KISS — Keep It Simple, Stupid

**Rule:** Most systems work best if they're kept simple rather than made complicated.

**Violation:**

```typescript
// Over-engineered solution for a simple problem
abstract class AbstractDataProcessor<T extends BaseEntity>
  implements IDataProcessor<T>, IValidatable, ILoggable {

  private readonly strategyFactory: IStrategyFactory<T>;
  private readonly validatorChain: IValidator<T>[];
  private readonly logger: ILogger;
  private readonly metricsCollector: IMetricsCollector;
  private readonly cacheManager: ICacheManager;
  private readonly eventBus: IEventBus;
  private readonly retryPolicy: IRetryPolicy;

  constructor(
    strategyFactory: IStrategyFactory<T>,
    @Inject('validatorChain') validatorChain: IValidator<T>[],
    @Inject('logger') logger: ILogger,
    // ... 8 more dependencies
  ) { /* ... */ }

  async process(data: T): Promise<ProcessedResult<T>> {
    // 200 lines of orchestration
  }
}
```

**Fix:** Just do the thing.

```typescript
function processOrder(order: Order): ProcessedOrder {
  validate(order);
  const total = calculateTotal(order);
  return saveOrder({ ...order, total });
}
```

**When to apply:** Prefer the least complex design that satisfies the known requirements. Both snippets above are structural sketches: application types and persistence/validation implementations are omitted.

**When complexity is justified:** Name the constraint and mechanism. Retrying a transient storage failure may require a bounded retry policy; preserving a committed side effect may require durable coordination. A large traffic number alone does not justify every cache, framework, or dependency in the first sketch.

**In interviews:** "I went with the simple approach because we don't have the requirements that would justify the complexity. We can refactor when we do."

## YAGNI — You Aren't Gonna Need It

**Rule:** Don't add functionality until it's actually needed.

**Violation:**

```typescript
// Adding "future-proof" features that may never be used
class UserService {
  createUser(data: UserData): User { /* ... */ }

  // Just in case we need to export users to CSV someday
  exportUsersToCsv(users: User[]): string { /* ... */ }

  // Just in case we need to import users from XML
  importUsersFromXml(xml: string): User[] { /* ... */ }

  // Just in case we need a webhook when a user is created
  triggerUserCreatedWebhook(user: User): void { /* ... */ }

  // Just in case we need to sync with LDAP
  syncWithLdap(): void { /* ... */ }
}
```

**Fix:** Add features when needed.

```typescript
class UserService {
  createUser(data: UserData): User { /* ... */ }

  // That's it. Add more when actually needed.
}
```

**Why:** "Just in case" features:
- Add maintenance burden
- Make code harder to understand
- Often never get used (or get used in a way that requires rewriting)
- Block refactoring

**When to apply:** Treat speculative features as a cost to justify. Known compatibility, security, recovery and migration requirements are current design constraints even when their consequences appear later.

Plan expensive compatibility boundaries such as public APIs, migrations and persisted formats, while avoiding speculative features. YAGNI does not require ignoring known future compatibility costs.

**In interviews:** "I didn't add the cache layer because the database is fast enough at current scale. We'll add it when we measure the need."

## Rule of Three

**Heuristic:** A third example often reveals variation that two examples hid; it is not a mandatory threshold.

**Why:** 1 time = maybe a coincidence. 2 times = maybe related. 3 times = more evidence of a pattern, not proof that the cases should share one abstraction.

**Without the rule:**

```typescript
// First user validation function
function validateUserEmail(email: string): boolean {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
}

// Premature abstraction
interface Validator {
  validate(value: string): boolean;
}

class EmailValidator implements Validator { /* ... */ }
class PhoneValidator implements Validator { /* ... */ }
class NameValidator implements Validator { /* ... */ }

// 2 weeks later: "We don't actually need this abstraction"
```

**With the heuristic:** Keep a plain email validator until actual clients need a common validation contract. Three validators with different input and error semantics may still be better separate. Conversely, two clients using one mandated email rule can share it immediately. The regex above only demonstrates structure; it is not a complete email-address specification.

**In interviews:** "These cases look similar, but I cannot yet name a shared rule. I will keep them separate until the variation is clear."

## Composition over Inheritance

**Rule:** Favor "has-a" relationships over "is-a" relationships.

**Inheritance problem:** A subclass is tied to its superclass behavior and extension hooks. A change to those hooks can affect descendants even when they do not override the changed method.

**Composition solution:** Delegate a task through a collaborator contract. Different instances can receive different collaborators. Runtime replacement requires an explicit replacement operation; merely storing a constructor argument does not provide one.

**Violation (deep inheritance):**

```typescript
class Vehicle { /* ... */ }
class Car extends Vehicle { /* ... */ }
class SportsCar extends Car { /* ... */ }
class Ferrari extends SportsCar { /* ... */ }
// Changes to inherited behavior or extension hooks can affect Ferrari.
```

**Fix (composition):**

```typescript
class Car {
  constructor(
    private engine: Engine, // has-a
    private transmission: Transmission, // has-a
    private wheels: Wheel[] // has-a
  ) {}
}
```

**The Strategy pattern is composition:**

```typescript
class DiscountCalculator {
  constructor(private strategy: DiscountStrategy) {} // has-a
  calculate(amount: number): number { return this.strategy.apply(amount); }
}
```

**When to use inheritance:** When callers need a valid behavioral subtype and the shared implementation is worth the coupling. A geometric “is-a” relationship alone is insufficient: mutable rectangles promise independent dimension changes, which a square cannot honor. An immutable area-only contract can permit both.

**When to use composition:** When behavior can vary independently or reuse does not imply substitution. It also creates collaborator contracts and wiring; prefer a plain function when neither mechanism adds value.

**In interviews:** "I injected the strategy so each calculator can use a different policy and test it independently. This example has no setter, so an existing calculator cannot switch strategies through its public API."

## Principle of Least Astonishment (POLA)

**Rule:** A component should behave in a way that most users would expect.

**Violation:**

```typescript
// Function name says "save" but it sends an email
function saveUser(user: User): void {
  database.save(user);
  emailService.sendWelcomeEmail(user); // Surprise!
  analytics.track("user_created", user); // Surprise!
  cache.invalidate("users"); // Surprise!
}
```

**Fix:** Make effects part of the named contract. A low-level `saveUser` can persist only; a `registerUser` workflow may deliberately persist, notify, and update indexes. Splitting calls makes their order visible but does not make them atomic.

```typescript
function saveUser(user: User): void {
  database.save(user);
}

// Caller composes the side effects
saveUser(user);
emailService.sendWelcomeEmail(user);
analytics.track("user_created", user);
```

If persistence succeeds and email fails, a blind retry can create a duplicate user. Decide which effects are required for success and how retries identify the same operation; see [outbox and change-data capture](../../30.2-system-design/01-theory/30.2.1.18-outbox-and-cdc.md) for durable coordination. Naming alone cannot solve this failure boundary.

**Other surprises to check for:** These are independent interface sketches; define and document the actual effects before exposing them.

```typescript
// Negative-named function that returns positive
function isNotValid(value: string): boolean { return value.length > 0; }
// Returns true for a nonempty value despite its negative name.

// Method that mutates AND returns
function addItem(cart: Cart, item: Item): Cart { /* mutates cart, returns new cart */ }

// Parameter order that surprises
function copy(source, destination) { /* source then dest, like cp */ }
function copyTo(destination, source) { /* reversed convention; document it */ }
```

**In interviews:** "I named the method `sendNotification` and it just sends a notification. The user is created separately. So the call site reads clearly: `createUser`, then `sendNotification`."

## Separation of Concerns (SoC)

**Rule:** Different concerns should be in different modules.

**Concerns:** Different aspects of a system — UI, business logic, data access, logging, etc.

**Violation:**

```typescript
class UserController {
  // 5 concerns mixed: HTTP, validation, business logic, persistence, email
  async createUser(req: Request): Promise<Response> {
    const data = req.body;
    if (!data.email || !data.password) {
      return { status: 400, body: { error: "invalid" } };
    }
    const user = new User(data.email, data.password);
    const hashedPassword = await bcrypt.hash(user.password, 10);
    user.password = hashedPassword;
    await db.query("INSERT INTO users ...");
    await emailService.sendWelcomeEmail(user);
    return { status: 201, body: { user } };
  }
}
```

**Fix:** Give each module a clear contract. The controller translates HTTP input and errors; the registration service validates the business rule and coordinates persistence; the repository hides storage mapping; the hasher hides the password algorithm.

This structural sketch uses application-specific HTTP types, not browser `Request`/`Response`. Implementations of validation, hashing, storage, and error logging are omitted:

```typescript
interface RegistrationInput { email: string; password: string }
interface PublicUser { id: string; email: string }
interface StoredUser extends PublicUser { passwordHash: string }
interface HttpRequest { body: RegistrationInput }
interface HttpResponse { status: number; body: object }
class ValidationError extends Error {}

interface UserRepository {
  create(data: { email: string; passwordHash: string }): Promise<StoredUser>;
}
interface PasswordHasher { hash(password: string): Promise<string> }

class UserService {
  constructor(private users: UserRepository, private hasher: PasswordHasher) {}
  async createUser(data: RegistrationInput): Promise<PublicUser> {
    if (!data.email || !data.password) throw new ValidationError('invalid input');
    const passwordHash = await this.hasher.hash(data.password);
    const stored = await this.users.create({ email: data.email, passwordHash });
    return { id: stored.id, email: stored.email }; // Never expose the hash
  }
}

class UserController {
  constructor(private users: UserService) {}
  async createUser(req: HttpRequest): Promise<HttpResponse> {
    try {
      return { status: 201, body: { user: await this.users.createUser(req.body) } };
    } catch (error) {
      if (error instanceof ValidationError) {
        return { status: 400, body: { error: 'invalid input' } };
      }
      // Record a sanitized internal diagnostic in the real application.
      return { status: 500, body: { error: 'registration failed' } };
    }
  }
}
```

A request moves controller → service → hasher → repository → public response. Changing the stored column name belongs in the repository; changing the response shape belongs in HTTP mapping. This example deliberately has no notification requirement. Adding one requires a decision about persistence/email failure and retry behavior, as the preceding POLA example explains. Separating classes does not by itself make a workflow reliable or every concern independently deployable.

## Other principles worth knowing

### Law of Demeter (Principle of Least Knowledge)

**Rule:** Only talk to your immediate friends.

```typescript
// Violation: "train wreck"
const cityName = user.getAddress().getCity().getName();

// Better: each class exposes only what callers need
const cityName = user.getCityName();
```

The issue is dependence on another object's internal representation, not the number of dots. A fluent builder or access to an intentionally exposed immutable data value can legitimately have several dots.

### Tell, Don't Ask

**Rule:** Tell objects what to do, don't ask for their state and act on it.

```typescript
// Violation: asking
if (account.balance > amount) {
  account.balance -= amount;
}

// Better: telling
account.withdraw(amount); // Account knows its own rules
```

`withdraw` puts amount validation and balance mutation under one owner. In a persisted account, separate processes can still race; the owner needs a database transaction or concurrency control. Moving code into a method is not itself an atomicity guarantee.

### Convention over Configuration

**Rule:** Defaults should be sensible. Don't make users configure everything.

A framework might discover modules in a standard folder. The default reduces setup, but callers need a documented override when their layout differs; an invisible convention that cannot be inspected increases surprise.

### Postel's Law

**Rule:** Be liberal in what you accept, conservative in what you send.

For protocols, liberal acceptance can create ambiguity and security inconsistencies. Define accepted forms explicitly, reject invalid input and emit a canonical representation rather than applying the slogan blindly.

## When to apply which principle

| Situation | Principle |
| --------------------------------------------------------------- | ---------------------------------------------------- |
| Same authoritative rule in multiple places | DRY; use more cases if the relationship is uncertain |
| Complex code that's hard to follow | KISS |
| Speculative feature for "future need" | YAGNI |
| Reuse behavior without promising a subtype contract | Composition |
| Independent stakeholder changes affect the same module | SRP; separate the actual sources of change |
| Class implements unused methods | ISP |
| Code surprises the user | POLA |
| Caller depends on another object's hidden layout | Law of Demeter |
| Caller mutates state using rules its owner should enforce | Tell, Don't Ask |
| Caller repeats an invariant over another object's mutable state | Consider moving that rule behind its state owner |

## Anti-patterns

- **Cargo cult DRY.** Two coincidentally similar pieces of code abstracted into one brittle thing.
- **Cargo cult SOLID.** 20 interfaces for a 200-line app.
- **Cargo cult KISS.** Refusing to add necessary complexity. "We don't need error handling, the user will just retry."
- **Premature optimization (KISS taken to mean "ignore future needs entirely").** Some complexity is justified.
- **Composition for the sake of it.** Sometimes inheritance IS the right tool.
- **YAGNI taken to mean "never think about the future".** Architecture should be flexible where it needs to be.

## In the LLD interview

**Common question:** "Design a parking lot / URL shortener / chess game."

**Senior answer structure:**

1. **Clarify the behavior and constraints:** reservation lifetime, payment outcome, competing park requests and fee changes.
2. **Identify state ownership and invariants:** one spot cannot belong to two active reservations; a ticket identifies an accepted parking operation.
3. **Choose boundaries for demonstrated variation:** isolate fee policy if it changes independently; keep occupancy checks with the mutation they protect. Preserve caller contracts across implementations.
4. **Trace success and failure:** reserve a spot, create a ticket, handle a failed payment or lost response, and explain retry identity and concurrency protection.
5. **Compare a simpler alternative:** retain a straightforward implementation unless an interface, strategy or hierarchy removes a specific cost.

## Summary

DRY gives shared knowledge one authoritative home; it does not merge all similar text. KISS asks for the least complex adequate design, and YAGNI postpones speculative capabilities while preserving known compatibility boundaries. Composition, explicit effects, and behavior owned with state can reduce coupling. Judge each against a concrete change or failure: neither a third example nor a new interface proves the abstraction is useful.

# DRY, KISS, YAGNI & Other Design Principles

> Two features contain the same calculation. One rule changes, and only one copy gets updated. Sharing the rule prevents drift, but sharing code that merely looks alike can couple two things that should change independently. The design question is what must stay consistent and what complexity the current requirement earns.

## Definition

**Practical definition:** DRY, KISS, and YAGNI are design heuristics for deciding when to share a rule, how much structure a requirement needs, and when to defer a capability. They guide trade-offs; none is a rule to apply mechanically.

> **Textbook Definition:** DRY gives each piece of system knowledge one authoritative representation; KISS favors the least complex design that satisfies its requirements; YAGNI defers capabilities that have no demonstrated need. The three principles address duplication, complexity, and speculative work respectively.

| Heuristic | Ask | Avoid |
| ------------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------- |
| **DRY** — Don't Repeat Yourself | Is this the same rule that must change together? | Merging code because it looks similar |
| **KISS** — Keep It Simple, Stupid | What is the least complex design that meets the real constraints? | Both needless machinery and careless shortcuts |
| **YAGNI** — You Aren't Gonna Need It | Is this capability required now, or only imagined? | Paying for speculative behavior before it is needed |

The phrase “Keep It Simple, Stupid” is a slogan, not a measurable specification. Use the practical test in the table: simplicity means fewer concepts and dependencies while still meeting the actual constraints.

## First Principles

A system represents facts that change. If separate components encode the same rule independently, one requirement update needs coordinated edits; a missed edit leaves contradictory behavior. One authoritative representation removes that drift, but it also gives its callers a shared contract, so unrelated rules should not be forced together.

Every abstraction has a present cost in code, tests, wiring, and reader attention. A future capability has uncertain value until its requirement is known. Choose the smallest design that preserves current invariants and known constraints, and keep it easy to change when evidence reveals a new need.

## Start with the rule that must stay true

Suppose checkout and invoicing both calculate the same pre-tax item subtotal. If the rule changes, two independent implementations can drift:

```typescript
// Inputs are validated non-negative integer cents and quantities.
type Item = { unitPriceCents: number; quantity: number };

function checkoutSubtotal(items: readonly Item[]): number {
  return items.reduce((sum, item) => sum + item.unitPriceCents * item.quantity, 0);
}

function invoiceSubtotal(items: readonly Item[]): number {
  return items.reduce((sum, item) => sum + item.unitPriceCents * item.quantity, 0);
}
```

Give the shared rule one home when both callers are governed by the same business fact:

```typescript
function subtotalCents(items: readonly Item[]): number {
  return items.reduce((sum, item) => sum + item.unitPriceCents * item.quantity, 0);
}
```

Invoice tax or checkout discounts can compose that subtotal without changing the shared rule. If the two calculations have different rounding, eligibility, or ownership rules, keep those parts separate even if their current code looks alike. Production money code must also define currency, rounding, and numeric-range behavior; this example assumes the inputs and total fit the chosen integer representation.

The useful test for DRY is whether one change to a rule requires coordinated edits in multiple places. Duplicated wording or similar syntax alone is not enough. A shared helper also creates a shared contract, so extraction is worthwhile only when that coupling matches the domain.

### Use the Rule of Three as evidence, not a gate

A third example can reveal variation that two examples hid. It is a heuristic for uncertain abstractions, not a requirement to wait before sharing a rule that already has one known authority. Two clients that must follow the same legal or product rule can share it immediately; three validators with independent meanings may still deserve separate implementations.

## Keep the design adequate and small

KISS favors the least complex design that satisfies known requirements. For one report that sorts an in-memory list, a copied list and a sort may be enough:

```typescript
const byNewest = [...orders].sort((a, b) => b.createdAt - a.createdAt);
```

A configurable query engine, plugin registry, and cache would add concepts without answering a current need. If the data volume, latency target, or sort options change, measure the constraint and choose the structure that addresses it. “Simple” does not mean ignoring input validation, security, errors, concurrency, or recovery when the system requires them.

Complexity is justified by a concrete constraint. For example, a bounded retry policy can address a known transient failure; idempotency can prevent a repeated request from duplicating an effect; a transaction can protect a state invariant shared by concurrent requests. State the constraint and the guarantee the mechanism provides. A large traffic estimate or a vague wish to be flexible does not establish either.

## Defer imagined capabilities, preserve known constraints

YAGNI says to delay a feature or abstraction that supports a presumed future need. A generic export framework for formats no customer can export yet costs time to build and test, adds concepts to every reader's mental model, and may encode the wrong variation. Add the capability when a real requirement makes its behavior clear.

YAGNI does not mean “never prepare for change.” A public API version, required data-retention policy, security boundary, or committed migration plan is already a constraint, even if its consequences arrive later. Keep code easy to change with clear contracts and tests, but avoid adding unused extension points. When considering future-proofing, compare the cost of a later change with the ongoing cost of carrying the abstraction now.

DRY, KISS, and YAGNI reinforce one another: centralize a rule that must stay consistent, keep that shared boundary as small as it can be, and avoid adding variation points for capabilities no one needs. Refactoring remains available when later evidence changes the design.

## Reuse behavior without promising a subtype

Composition delegates work to a collaborator; inheritance says that a subtype can stand in for its parent under the parent's behavioral contract. Use inheritance when that substitution is true and useful. Use composition when behavior varies independently or reuse does not imply “is-a.” A geometric label alone does not prove a valid subtype: a square cannot preserve a rectangle caller's promise that width and height can change independently.

Composition also has a cost: collaborators need contracts and wiring. A plain function may be simpler when there is no meaningful runtime variation. See [OOP concepts](30.1.1.03-oop-concepts.md) and [Liskov Substitution Principle](30.1.1.01-solid-principles.md#l--liskov-substitution-principle-lsp) for the full substitution argument.

## Make effects and responsibilities visible

A method's name and contract should tell callers which effects it performs. A low-level `saveUser` that also sends email and updates analytics hides independent failure points. A `registerUser` workflow may intentionally coordinate these steps, but naming them does not make them atomic. If persistence succeeds and notification fails, a retry needs a defined identity and recovery policy; an outbox can coordinate durable notification delivery.

Separate concerns when their policies or owners change independently. In a registration flow, the HTTP adapter parses requests and maps responses, the application service applies registration rules, a password hasher owns the hashing operation, and a repository owns persistence mapping. The service stores the hash through the repository, then returns a public projection such as `{ id, email }`; the HTTP response never exposes the persistence record or password hash. These boundaries clarify who owns each decision; they do not guarantee that the steps form one transaction.

This is the useful form of separation of concerns: isolate independent decisions and keep each invariant with the state it protects. Splitting every operation into its own class adds indirection without necessarily reducing change cost. See [Single Responsibility Principle](30.1.1.01-solid-principles.md#s--single-responsibility-principle-srp) for actor-driven reasons to change.

## A few related heuristics

| Heuristic | Useful interpretation | Boundary to remember |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Principle of Least Astonishment (POLA)** | Make names, return values, and side effects match what callers expect. | A clear name exposes effects; it does not make partial success atomic. |
| **Law of Demeter** | Depend on the behavior of collaborators, not their internal object layout. | A long chain is a warning to inspect, not proof of a violation; immutable data access can be intentional. |
| **Tell, Don't Ask** | Ask the object that owns an invariant to perform the operation that preserves it. | An in-memory method cannot serialize competing writes in a database. |
| **Convention over configuration** | Provide a discoverable default for common use and an explicit override when real cases differ. | An undocumented or impossible-to-override convention hides behavior. |
| **Robustness principle (Postel's Law)** | The historical slogan says to be conservative when sending and liberal when receiving. | Broad acceptance can entrench ambiguity and security bugs. Follow the protocol specification, accept only defined compatibility variations, and send canonical output. |

RFC 9413 revisits the robustness principle: tolerance can preserve interoperability, but accepting unspecified input indefinitely can make errors part of the protocol and weaken security. Treat tolerance as a deliberate compatibility policy, not a blanket command to accept malformed data.

## Apply the trade-off in an interview

When asked to design a feature, trace one real change rather than naming principles as a checklist:

1. State the rule or invariant and who owns it.
2. Identify which callers must follow the same rule and which have independent policies.
3. Choose the smallest design that meets the present constraints; name any complexity the constraints require.
4. Defer speculative capabilities, but preserve known compatibility, security, and recovery requirements.
5. Explain what happens when a step fails or a request repeats, then name the test that proves the guarantee.

For example, share a mandated subtotal between checkout and invoices, keep invoice tax in the invoice policy, and avoid a generic fee plug-in until a real fee variation needs one. If a repeated checkout request could charge twice, idempotency is a present correctness requirement rather than speculative flexibility.

## Summary

DRY centralizes shared knowledge, not coincidentally similar code. KISS chooses the least complex design that satisfies real constraints; YAGNI delays speculative capabilities while preserving requirements already known. Share only rules that should change together, keep invariants with their owners, and explain each abstraction by the change or failure it handles.

# OOP Concepts — Encapsulation, Inheritance, Polymorphism, Abstraction

> **The 4 pillars of OOP, plus the supporting concepts.** Every LLD interview tests these. Most senior engineers use them every day but might not articulate them clearly. This file is the canonical reference.

## TL;DR

- **Encapsulation** — hide state, expose behavior. Data + methods together, access controlled.
- **Inheritance** — "is-a" relationship. Subclass inherits from parent.
- **Polymorphism** — same interface, different behavior. Method overriding / overloading.
- **Abstraction** — hide complexity, show essentials. Abstract classes, interfaces.

Plus:
- **Association, Aggregation, Composition** — "has-a" relationships
- **Cohesion & Coupling** — module quality metrics
- **Message passing** — how objects communicate
- **Open recursion** — `self`/`this` in OOP

---

## First Principles

OOP's four pillars are answers to managing mutable state at scale:

1. **Encapsulation is state-protection**: invariants hold only if every mutation goes through controlled paths — visibility modifiers are the enforcement.
2. **Inheritance is reuse-of-contract; composition is reuse-of-behavior.** Inheritance couples subclass to superclass implementation forever (fragile base class); composition substitutes at runtime. "Prefer composition" is this asymmetry, not dogma.
3. **Polymorphism is dispatch-by-type**: one call site, many implementations — the mechanism that makes OCP (→ 30.1.1.01) mechanically possible.

## Why it matters

LLD interviews start with "design X" and expect you to model entities and their relationships. You need to:
- Identify classes (nouns)
- Decide inheritance vs composition
- Apply encapsulation (what's public, what's private)
- Use polymorphism where appropriate

You also need to talk about it: "I made this class abstract because we never instantiate it directly, we use its subclasses."

## Definition

**Object-oriented programming** is a way of organizing a program as a set of objects that own state and expose behaviour, so that the *internal representation* of that state can change without changing every caller. Its four named pillars are consequences of that goal rather than separate features:

| Pillar | Mechanism | What it buys |
| ----------------- | -------------------------------------- | -------------------------------------------------- |
| **Encapsulation** | private state + public methods | callers depend on a contract, not a representation |
| **Abstraction** | interfaces / abstract types | callers depend on *what*, not *how* |
| **Inheritance** | subtype relationship (`is-a`) | shared behaviour reused along a taxonomy |
| **Polymorphism** | same message, different implementation | call-site code stops branching on type |

The composition vocabulary sits alongside them, and it is what most modern design favors:

```text
association  A knows B                          (weakest)
aggregation  A has B; B outlives A              (shared, e.g. team members)
composition  A owns B; B dies with A            (strongest, lifecycle-bound)
```

Two definitional points are the ones interviewers probe. **Encapsulation is not "private fields"** — it is the guarantee that invariants (an account's balance is never negative) are enforced in one place, which requires behaviour to live with the data rather than in callers. And **prefer composition over inheritance** because inheritance couples a subclass to its parent's implementation in both directions (the fragile base class problem), while composition couples only to an interface — which is why the practical guidance is *inherit for substitutability, compose for reuse*.

## The 4 Pillars

### 1. Encapsulation

**Definition:** Bundling data with the methods that operate on that data, and restricting direct access to some of the object's components.

**Key idea:** Hide state. Expose behavior.

**Violation (no encapsulation):**

```typescript
class BankAccount {
  balance: number = 0; // Public! Anyone can change it.
}

const account = new BankAccount();
account.balance = -1000000; // Oops, allowed.
account.balance = 999999999; // No validation.
```

**Fix (with encapsulation):**

```typescript
class BankAccount {
  private balance: number = 0; // Private, can only be modified via methods

  constructor(initialBalance: number) {
    if (initialBalance < 0) throw new Error("Initial balance cannot be negative");
    this.balance = initialBalance;
  }

  deposit(amount: number): void {
    if (amount <= 0) throw new Error("Deposit must be positive");
    this.balance += amount;
  }

  withdraw(amount: number): void {
    if (amount <= 0) throw new Error("Withdrawal must be positive");
    if (amount > this.balance) throw new Error("Insufficient funds");
    this.balance -= amount;
  }

  getBalance(): number {
    return this.balance;
  }
}
```

**Why it matters:** Direct state access allows invariants to be broken. Encapsulation enforces invariants.

**In interviews:** "I made the fields private and exposed getter/setter methods so the balance can't be set to an invalid value."

**Levels of access (TypeScript / Java):**
- `private` — only this class
- `protected` — this class + subclasses
- `public` — everyone
- `default` / `package-private` (Java) — same package
- `readonly` (TypeScript) / `final` (Java) — assignable once

### 2. Inheritance

**Definition:** A class can inherit attributes and methods from another class. "Is-a" relationship.

```typescript
class Animal {
  constructor(public name: string) {}
  speak(): string { return `${this.name} makes a sound.`; }
}

class Dog extends Animal {
  speak(): string { return `${this.name} barks.`; }
}

class Cat extends Animal {
  speak(): string { return `${this.name} meows.`; }
}

const dog = new Dog("Rex");
console.log(dog.speak()); // "Rex barks."
```

**Pros:**
- Code reuse (subclass gets parent's methods)
- Polymorphism (treat subclass as parent)
- Logical hierarchy

**Cons:**
- Tight coupling (changes to parent break subclasses)
- Fragile base class problem
- Inheritance is permanent (can't "uninherit")
- Often misused (composition is usually better)

**LSP (Liskov Substitution Principle):** Subclass must be substitutable for parent. If you have to check the type, LSP is violated.

See [Solid Principles](30.1.1.01-solid-principles.md) for the L (LSP) section.

**In interviews:** "I considered inheritance but used composition because the relationship is 'has-a' (a Car has-a Engine), not 'is-a' (a Car is-a Vehicle)."

**When to use:**
- True "is-a" relationship (Dog is-a Animal)
- You want polymorphism through base class
- Code reuse is significant

**When NOT to use:**
- "Has-a" relationship (use composition)
- Forced hierarchy (Square is-a Rectangle is famous anti-example)
- You want to mix features from different classes (use mixins or interfaces)

### 3. Polymorphism

**Definition:** The ability of different objects to respond to the same message (method call) in different ways.

**Two main forms:**

#### a. Subtype polymorphism (method overriding)

```typescript
abstract class Shape {
  abstract area(): number;
  abstract perimeter(): number;
}

class Circle extends Shape {
  constructor(public radius: number) { super(); }
  area(): number { return Math.PI * this.radius ** 2; }
  perimeter(): number { return 2 * Math.PI * this.radius; }
}

class Rectangle extends Shape {
  constructor(public width: number, public height: number) { super(); }
  area(): number { return this.width * this.height; }
  perimeter(): number { return 2 * (this.width + this.height); }
}

// Same method call, different behavior
function printArea(shapes: Shape[]): void {
  for (const shape of shapes) {
    console.log(`Area: ${shape.area()}`); // Calls the right one
  }
}

printArea([new Circle(5), new Rectangle(4, 6)]);
// "Area: 78.54"
// "Area: 24"
```

#### b. Parametric polymorphism (generics)

```typescript
function identity<T>(value: T): T { return value; }
const num = identity(42); // T = number
const str = identity("hello"); // T = string
```

#### c. Ad-hoc polymorphism (overloading — not in TypeScript by default)

```java
// Java supports overloading
public class Calculator {
  public int add(int a, int b) { return a + b; }
  public double add(double a, double b) { return a + b; }
  public String add(String a, String b) { return a + b; }
}
```

**In interviews:** "I used polymorphism so the same `area()` call works for circles, rectangles, and triangles. The caller doesn't need to know which shape."

**When to use:** When you have multiple types that share a common interface but have different behavior.

### 4. Abstraction

**Definition:** Hiding complex implementation details and exposing only the essential features.

**Mechanisms:**
- Abstract classes
- Interfaces
- Methods (signature without implementation)

**Abstract class:**

```typescript
abstract class PaymentProcessor {
  // Abstract method: subclasses must implement
  abstract processPayment(amount: number, currency: string): Promise<PaymentResult>;

  // Concrete method: shared by all subclasses
  validateAmount(amount: number): boolean {
    return amount > 0 && amount < 1000000;
  }
}

class StripeProcessor extends PaymentProcessor {
  async processPayment(amount: number, currency: string): Promise<PaymentResult> {
    if (!this.validateAmount(amount)) throw new Error("Invalid amount");
    // Stripe-specific logic
    return { success: true, transactionId: "..." };
  }
}

class PayPalProcessor extends PaymentProcessor {
  async processPayment(amount: number, currency: string): Promise<PaymentResult> {
    if (!this.validateAmount(amount)) throw new Error("Invalid amount");
    // PayPal-specific logic
    return { success: true, transactionId: "..." };
  }
}
```

**Interface (pure abstraction, no implementation):**

```typescript
interface PaymentProcessor {
  processPayment(amount: number, currency: string): Promise<PaymentResult>;
  refund(transactionId: string): Promise<RefundResult>;
}

interface Notifier {
  notify(userId: string, message: string): Promise<void>;
}

// A class can implement multiple interfaces
class CheckoutService implements PaymentProcessor, Notifier {
  async processPayment(amount: number, currency: string): Promise<PaymentResult> { /* ... */ }
  async refund(transactionId: string): Promise<RefundResult> { /* ... */ }
  async notify(userId: string, message: string): Promise<void> { /* ... */ }
}
```

**In interviews:** "I abstracted the payment processing into a PaymentProcessor interface. We have 3 implementations (Stripe, PayPal, Adyen) and the checkout service depends on the interface, not the concrete class."

## "Has-a" Relationships

### Association

**Definition:** A loose relationship where one class uses another. "Knows-about."

```typescript
class Professor {
  advise(student: Student): void { /* ... */ }
}

class Student {
  // Has a reference to advisor (or none)
}
```

**UML:** Solid line, often with arrow.

### Aggregation

**Definition:** A "whole-part" relationship where the part can exist without the whole. "Has-a," but loosely.

```typescript
class Department {
  professors: Professor[] = [];

  addProfessor(p: Professor): void { this.professors.push(p); }
}

class Professor {
  // Professor can exist without Department
}
```

**UML:** Hollow diamond on the whole's side.

**Real-world example:** A Department has-a Professor, but if the Department is deleted, the Professor still exists.

### Composition

**Definition:** A strong "whole-part" relationship where the part CANNOT exist without the whole. "Owns-a."

```typescript
class House {
  private rooms: Room[];

  constructor() {
    // Rooms are created with the house
    this.rooms = [new Room("kitchen"), new Room("bedroom")];
  }
}

class Room {
  constructor(public name: string) {}
}

// If House is destroyed, Rooms are destroyed too
```

**UML:** Filled diamond on the whole's side.

**Real-world example:** A House has-a Room. If the House is destroyed, the Rooms are destroyed too. Rooms don't exist independently.

**In interviews:** "A Car has-an Engine (composition, strong). A Car has-a Driver (association, weak — the driver exists without the car)."

## Cohesion & Coupling

### Cohesion

**Definition:** How closely related the responsibilities of a module are.

- **High cohesion** = module does one thing well. Good.
- **Low cohesion** = module does many unrelated things. Bad.

**High cohesion example:** A `UserRepository` class only does user persistence.
**Low cohesion example:** A `UserRepository` class that also sends emails, generates reports, and handles authentication.

### Coupling

**Definition:** How dependent modules are on each other.

- **Low coupling** = modules can change independently. Good.
- **High coupling** = modules are tightly connected. Bad.

**Low coupling example:** Two modules communicate through a stable interface.
**High coupling example:** Module A reaches into Module B's private state and changes it.

**The goal:** **High cohesion + Low coupling.** The two go together.

**In interviews:** "I aimed for high cohesion (each class has one responsibility) and low coupling (classes depend on interfaces, not concrete implementations)."

## Message Passing

**Definition:** Objects communicate by sending messages to each other (calling methods).

```typescript
const order = new Order(items);
const total = order.calculateTotal(); // Message: "calculate your total"
order.place(); // Message: "place yourself"
```

**vs. direct state access:**

```typescript
// Direct state access (procedural, not OOP)
const orderTotal = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
order.total = orderTotal;
order.status = 'placed';
```

**OOP style:** "Tell, don't ask." Tell the order to calculate its own total. Tell it to place itself.

```typescript
// Better: tell, don't ask
order.calculateTotal();
order.place();
```

**In interviews:** "The Order class encapsulates the total calculation logic. The caller just calls `order.place()` and trusts the order to do the right thing."

## Open Recursion

**Definition:** The `this`/`self` reference in OOP that lets methods call other methods on the same object polymorphically.

```typescript
class Animal {
  speak(): string { return this.makeSound(); }

  protected makeSound(): string { return "..."; }
}

class Dog extends Animal {
  protected makeSound(): string { return "woof"; }
}

const dog = new Dog();
console.log(dog.speak()); // "woof" — calls Dog's makeSound through this
```

**Why it matters:** This is how polymorphism works. `this.makeSound()` resolves to the subclass's version at runtime.

## Common interview questions

**Q: "What's the difference between abstraction and encapsulation?"**
- Abstraction: hiding complexity, showing essentials. Focus on the interface.
- Encapsulation: hiding state, exposing behavior. Focus on data access.
- Both are about hiding things, but abstraction is about WHAT to expose, encapsulation is about HOW to control access.

**Q: "What's the difference between inheritance and composition?"**
- Inheritance: "is-a." Car IS-A Vehicle. Subclass gets parent's interface + impl.
- Composition: "has-a." Car HAS-A Engine. Object holds reference to another.
- Default to composition. Use inheritance only for true is-a + polymorphism.

**Q: "What's polymorphism and why is it useful?"**
- Same method call, different behavior. Lets you write code that works on a type, not a specific class.
- Useful for: extensibility (add new types without changing existing code), testability (mock implementations), clean abstractions.

**Q: "When would you use an abstract class vs an interface?"**
- Abstract class: when subclasses share implementation (default methods, fields).
- Interface: when you only want to define a contract, no shared implementation.
- Java: only one abstract class per class, but multiple interfaces.
- TypeScript: no real difference (interfaces can have default methods now).

**Q: "Explain aggregation vs composition."**
- Aggregation: weak "has-a." Part can exist without whole. (Department, Professor)
- Composition: strong "has-a." Part is owned by whole. (House, Room)
- Choice affects: lifetime management, cascade-delete semantics.

## OOP vs other paradigms

**OOP strengths:** Modeling real-world entities, polymorphism, encapsulation.
**OOP weaknesses:** Sometimes over-engineered for simple problems, inheritance is fragile, state management is hard.

**Alternatives:**
- **Functional programming (FP):** No mutable state, pure functions, composition. Better for concurrency and reasoning about behavior.
- **Procedural:** Top-down functions. Good for scripts and small programs.
- **Reactive:** Event-driven, async streams. Good for UIs and real-time systems.

**In interviews:** "I used OOP for the domain entities (User, Order, Payment) and FP-style pure functions for the calculations (calculateTotal, calculateTax). Best of both."

---

## Anti-patterns

- **God class.** One class with 30 methods and 20 fields. Low cohesion.
- **Anemic domain model.** Class with only getters/setters, no behavior. Behavior lives in services. Just a data bag.
- **Inheritance for code reuse only.** "Car extends Engine to reuse Engine's methods." Wrong. Car HAS-A Engine.
- **Polymorphism abuse.** 5 levels of inheritance for a 3-class problem. KISS.
- **Public everything.** All fields public. No encapsulation.
- **Circular dependencies.** Class A depends on B depends on A. Refactor.

---

## Summary

OOP is built on four pillars: encapsulation (hide state, expose behavior), inheritance (is-a relationships, use sparingly), polymorphism (same interface, different behavior), and abstraction (hide complexity). The three relationship types — association, aggregation, and composition — describe how objects relate. High cohesion and low coupling are the goals. In LLD interviews, draw class diagrams showing these relationships and explain your design choices.

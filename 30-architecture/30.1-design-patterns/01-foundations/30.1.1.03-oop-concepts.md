# OOP Concepts — Encapsulation, Inheritance, Polymorphism, Abstraction

A balance turns negative because several callers write it directly. Object-oriented design starts by asking who owns that state, which changes are legal, and what callers may rely on.

```typescript
account.balanceCents = -100_000; // No operation checks the invariant.
```

## Definition

**Object-oriented programming** organizes software as interacting **objects** that own state and expose behavior through **contracts**. Its value comes from clear ownership and caller guarantees, not from turning every noun into a class.

> **Textbook Definition:** Object-oriented programming models computation as interactions among objects that encapsulate state and behavior. Abstraction and polymorphism let callers rely on contracts instead of concrete representations; inheritance is one optional mechanism for sharing behavior and defining subtypes.

## First Principles

State changes only through the paths a system provides. If every caller writes the same balance field, every caller must repeat the validity rule, and one missed check corrupts the state. Put the invariant and its legal transitions behind one owner.

Callers then need a stable way to request behavior without knowing how the owner stores data — that is the contract. Different objects satisfy the same contract only when they preserve its promised inputs, outputs, errors, and state effects. Inheritance can provide that subtype relationship; delegation reuses behavior without claiming it. Neither removes the need to define the contract.

## How It Works

### 1. Encapsulation: own state and legal transitions

Public mutable state lets callers bypass the rule protecting it. Move mutation behind operations that validate first and update only when valid:

```typescript
class BankAccount {
  private balanceCents: number;

  constructor(initialBalanceCents: number) {
    if (!Number.isSafeInteger(initialBalanceCents) || initialBalanceCents < 0) {
      throw new Error('Initial balance must be a nonnegative safe integer');
    }
    this.balanceCents = initialBalanceCents;
  }

  deposit(amountCents: number): void {
    this.validateAmount(amountCents);
    const next = this.balanceCents + amountCents;
    if (!Number.isSafeInteger(next)) throw new Error('Balance overflow');
    this.balanceCents = next;
  }

  withdraw(amountCents: number): void {
    this.validateAmount(amountCents);
    if (amountCents > this.balanceCents) throw new Error('Insufficient funds');
    this.balanceCents -= amountCents;
  }

  getBalanceCents(): number {
    return this.balanceCents;
  }

  private validateAmount(amountCents: number): void {
    if (!Number.isSafeInteger(amountCents) || amountCents <= 0) {
      throw new Error('Amount must be a positive safe integer');
    }
  }
}

const account = new BankAccount(100);
account.deposit(50);
account.withdraw(40);
console.log(account.getBalanceCents()); // 110
try { account.withdraw(200); } catch { console.log('rejected'); }
console.log(account.getBalanceCents()); // 110: rejection left state unchanged
```

The invariant is a nonnegative safe-integer balance: validation rejects `NaN`, infinity, fractions, and invalid amounts, and deposit rejects overflow before mutation. The example uses integer minor units and omits currency conversion and persistence. One in-memory mutation path does not serialize concurrent requests — a shared persisted account still needs a database transaction or other concurrency control.

A getter returning a primitive does not expose internal state. A getter returning a mutable array or object may, unless the owner copies it or explicitly promises shared mutation. A setter is safe only when it enforces the same invariant. Visibility modifiers differ by language (`private`, ECMAScript `#field`, Java package access), but encapsulation is a design boundary, never an authorization system: never rely on a compile-time modifier to protect secrets from untrusted code or another process.

### 2. Abstraction: expose a contract

A caller needs the operation and its guarantees, not the provider's identity. Checkout can depend on a payment contract:

```typescript
type PaymentRequest = {
  orderId: string;
  amountMinor: number; // validated safe integer in the currency's minor unit
  currency: string;
  idempotencyKey: string;
};

type PaymentResult =
  | { status: 'accepted'; paymentId: string }
  | { status: 'declined'; reason: string };

interface PaymentGateway {
  charge(request: PaymentRequest): Promise<PaymentResult>;
}
```

Checkout depends on this contract without knowing which provider adapter implements it. The interface alone promises nothing about idempotency, timeouts, retryable failures, or reversibility — those guarantees belong in the contract and implementation. If payment succeeds but a later notification fails, retrying the whole workflow can still charge twice.

TypeScript expresses contracts with erased structural interfaces; Java uses nominal runtime types that may declare abstract, `default`, and static methods. Use an interface when callers need a contract; use an abstract class when a real inheritance relationship plus shared implementation justifies the extra coupling. Neither makes remote effects atomic.

### 3. Polymorphism: one call, different behavior

With subtype polymorphism, the caller invokes a contract and runtime dispatch selects the implementation:

```typescript
abstract class Shape {
  abstract area(): number;
}

class Circle extends Shape {
  constructor(private readonly radius: number) { super(); }
  area(): number { return Math.PI * this.radius ** 2; }
}

class Rectangle extends Shape {
  constructor(private readonly width: number, private readonly height: number) { super(); }
  area(): number { return this.width * this.height; }
}

function totalArea(shapes: readonly Shape[]): number {
  return shapes.reduce((sum, shape) => sum + shape.area(), 0);
}
```

`totalArea` never branches on concrete class — `Circle.area` or `Rectangle.area` runs according to the object passed. This works only while each implementation honors `Shape`'s promised behavior; a matching signature alone is not enough. Dimensions are assumed valid so the example focuses on dispatch.

Two compile-time forms differ from runtime dispatch: **parametric** polymorphism (one generic implementation, e.g. `function identity<T>(value: T): T`) and **ad hoc** polymorphism (overloads selected from declared argument types, e.g. Java `add(int, int)` vs `add(double, double)`). TypeScript erases generic parameters at runtime, and its overload signatures share one implementation body handling the supported cases.

### 4. Inheritance and composition: choose the promise you need

**Inheritance** derives a class from a base, sharing implementation and exposing the derived instance through the base type — so callers may rely on the base contract, and derived behavior must preserve it. The [Liskov Substitution Principle](30.1.1.01-solid-principles.md) explains how to check that promise. Inheritance for reuse alone also exposes subclasses to unrelated base-class changes and extension hooks.

Watch **open recursion**: a method calling another method through `this` can reach a subclass override. Useful for explicit extension hooks, but a base constructor calling an overridable method runs subclass code before subclass fields initialize — avoid that pattern unless the initialization contract is deliberate.

**Composition** gives an object a collaborator and delegates without claiming subtyping:

```typescript
interface Engine {
  start(): void;
}

class Car {
  constructor(private readonly engine: Engine) {}
  drive(): void { this.engine.start(); }
}
```

Use inheritance when substitution is valid and shared implementation is useful; use composition when behavior varies independently or reuse needs no "is-a" promise. Composition still adds a collaborator contract and wiring — a plain function is simpler when neither is needed.

### 5. Relationships, cohesion, and coupling describe boundary quality

UML **association**, **aggregation**, and **composition** answer different relationship questions, but their symbols never enforce ownership in a runtime or database:

| Relationship | Notation | Meaning and example |
| --------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Association** | Solid line; arrow may show navigability. | Related objects, e.g. a professor advising students. No lifecycle ownership implied. |
| **Aggregation** | Hollow diamond at the whole. | Weak whole-part grouping, e.g. a team grouping independently existing members. No exclusive ownership or automatic deletion. |
| **Composition** | Filled diamond at the whole. | Strong ownership, e.g. an order owning line items. A part belongs to at most one composite; deleting the composite deletes its object parts unless first removed. |

The model must still state multiplicities, removal rules, and persistence behavior — a database cascade or cleanup action is an implementation choice the diamond does not perform. For notation details, see [UML Basics](30.1.1.04-uml-basics.md).

**Cohesion** asks whether a module's responsibilities serve a related purpose: an account's deposit, withdrawal, and validation are cohesive because together they preserve its balance invariant. Method count alone decides nothing. **Coupling** is how one module depends on another's representation, types, behavior, timing, shared state, or failure — an interface hides concrete representation, but callers still depend on semantics, errors, and availability. Keep related invariants together; isolate independently changing decisions. Splitting every operation into its own class scatters one rule and adds indirection.

Reading a public balance, checking it elsewhere, then mutating it splits the rule across callers — `account.withdraw(amount)` keeps the check and transition with the owner. A method call still does not serialize two processes writing the same persisted row.

### 6. Combine OOP with other styles deliberately

OOP fits stateful behavior needing one owner, or several implementations behind a shared contract. Other styles solve different problems, and real systems combine them:

| Style | Useful when | Watch for |
| ------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Object-oriented** | State transitions belong to stable owners; callers benefit from interchangeable implementations. | Mutable state, implicit inheritance hooks, and class scaffolding can obscure simple operations. |
| **Functional** | Transformations read best as explicit inputs and outputs, often without mutation. | Effects still need explicit boundaries; practical functional languages may allow controlled mutation. |
| **Procedural** | A sequence of operations over explicit data is the clearest model. | Large systems still need module boundaries and ownership for shared invariants. |
| **Reactive** | Behavior depends on change over time, events, or streams. | Backpressure, ordering, cancellation, and failure semantics need definition; reactive code still uses objects and pure functions. |

A data-transfer object may stay data-only. Introduce behavior-rich objects where they stop callers reimplementing one invariant inconsistently — not for every domain noun.

## Common Mistakes

- Several callers mutate the same invariant-bearing state through different paths.
- A subtype forces callers to inspect its concrete type or avoid valid base operations.
- A class or interface only forwards calls, adding no contract, state ownership, or change boundary.
- A UML composition diamond is mistaken for automatic memory cleanup or database cascading.

These are signals to inspect the contract and actual changes, not automatic proof of a defect.

## Summary

Organize objects around owned state, legal transitions, and caller-visible contracts. Encapsulation protects invariants; abstraction exposes needed operations; polymorphism lets compatible implementations serve one contract. Inheritance creates a subtype promise, while composition delegates behavior without that promise. UML relationships describe association and ownership, but code and storage must enforce the required lifecycle.

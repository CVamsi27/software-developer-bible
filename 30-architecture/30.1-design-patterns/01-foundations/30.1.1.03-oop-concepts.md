# OOP Concepts — Encapsulation, Inheritance, Polymorphism, Abstraction

> A balance becomes negative because several callers can write it directly. Object-oriented design starts by asking who owns that state, which changes are legal, and what callers may rely on.

## Definition

**Practical definition:** Object-oriented programming organizes software as interacting objects that own state and expose behavior through contracts. Its value comes from clear ownership and caller guarantees, not from turning every noun into a class.

> **Textbook Definition:** Object-oriented programming models computation as interactions among objects that encapsulate state and behavior. Abstraction and polymorphism let callers rely on contracts instead of concrete representations; inheritance is one optional mechanism for sharing behavior and defining subtypes.

| Concept | What it means for a caller |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Encapsulation** | State changes go through operations that preserve the object's invariants. |
| **Abstraction** | The caller sees the operations and guarantees it needs, not their implementation. |
| **Polymorphism** | Different implementations can serve one compatible contract. |
| **Inheritance** | A derived type inherits members and may be used through a base type when it honors that type's behavioral contract. |

A method call from one object to another is often described as **message passing**. In ordinary application code it is a method call, not automatically a network message or asynchronous event.

## First Principles

State can change only through the paths a system provides. If every caller writes the same balance field, every caller must repeat the validity rule, and one missed check can corrupt the state. Put the invariant and its legal transitions behind one owner.

Callers then need a stable way to request behavior without knowing how that owner stores data. A contract provides that boundary. Different objects can satisfy the same contract only when they preserve its promised inputs, outputs, errors, and state effects. Inheritance can provide that subtype relationship; delegation can reuse behavior without claiming it. Neither removes the need to define the contract.

## Encapsulation: own state and legal transitions

Public mutable state lets callers bypass the rule that protects it:

```typescript
class BankAccount {
  balanceCents = 0;
}

const account = new BankAccount();
account.balanceCents = -100_000; // No operation checks the invariant.
```

Move mutation behind operations that validate first and update only when the operation is valid:

```typescript
class BankAccount {
  private balanceCents: number;

  constructor(initialBalanceCents: number) {
    if (!Number.isSafeInteger(initialBalanceCents) || initialBalanceCents < 0) {
      throw new Error('Initial balance must be a nonnegative safe integer');
    }
    this.balanceCents = initialBalanceCents;
  }

  deposit(amountCents: number): void {
    this.validateAmount(amountCents);
    const next = this.balanceCents + amountCents;
    if (!Number.isSafeInteger(next)) throw new Error('Balance overflow');
    this.balanceCents = next;
  }

  withdraw(amountCents: number): void {
    this.validateAmount(amountCents);
    if (amountCents > this.balanceCents) throw new Error('Insufficient funds');
    this.balanceCents -= amountCents;
  }

  getBalanceCents(): number {
    return this.balanceCents;
  }

  private validateAmount(amountCents: number): void {
    if (!Number.isSafeInteger(amountCents) || amountCents <= 0) {
      throw new Error('Amount must be a positive safe integer');
    }
  }
}

const account = new BankAccount(100);
account.deposit(50);
account.withdraw(40);
console.log(account.getBalanceCents()); // 110
try { account.withdraw(200); } catch { console.log('rejected'); }
console.log(account.getBalanceCents()); // 110: rejection left state unchanged
```

The invariant here is a nonnegative safe-integer balance. Validation rejects `NaN`, infinity, fractions, and invalid amounts; the deposit also rejects overflow before mutation. The example uses integer minor units and omits currency conversion and persistence. The object provides one in-memory mutation path; concurrent requests to a shared persisted account still need a database transaction or other concurrency control.

A getter that returns a primitive number does not expose the internal state. A getter that returns a mutable array or object may expose it unless the owner copies it or explicitly promises shared mutation. A setter is safe only when it enforces the same invariant.

### Visibility differs by language

| Mechanism | TypeScript | Java |
| --------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `public` | Class members are public by default; exports control module visibility. | Public access is also subject to enclosing type and module accessibility. |
| `private` | Enforced by type checking; an ordinary property is not runtime-private. | Restricted by Java access rules, including nestmate access. |
| Runtime-private field | ECMAScript `#field` is checked by the JavaScript runtime. | `private` is enforced by the JVM's access rules. |
| `protected` | Available to the declaring class and derived classes under TypeScript's type rules. | Also permits same-package access; subclass access outside the package has receiver restrictions. |
| Package access | No Java-style package-private member modifier; modules control exports. | Omitting an access modifier permits package access. |
| `readonly` / `final` | Prevents reassignment under the language's rules, but does not deeply freeze an object. | Prevents reassignment of the variable or field; referenced objects may remain mutable. |

Encapsulation is a design boundary, not an authorization system. Never rely on a compile-time modifier to protect secrets from untrusted code or another process.

## Abstraction: expose a contract

A caller needs the operation and its guarantees; it should not need to know which provider implements them. For example, checkout can depend on a payment contract:

```typescript
type PaymentRequest = {
  orderId: string;
  amountMinor: number; // validated safe integer in the currency's minor unit
  currency: string;
  idempotencyKey: string;
};

type PaymentResult =
  | { status: 'accepted'; paymentId: string }
  | { status: 'declined'; reason: string };

interface PaymentGateway {
  charge(request: PaymentRequest): Promise<PaymentResult>;
}
```

Checkout can depend on this contract without knowing which provider adapter implements it. The request assumes a validated safe-integer minor-unit amount; a remote adapter must also map it to the provider's wire format. The interface does not by itself promise idempotency, timeout behavior, which failures are retryable, or whether a charge is reversible. Those guarantees belong in the contract and implementation. If payment succeeds but a later notification fails, retrying the whole workflow can still charge twice.

TypeScript and Java express contracts differently:

| Type | TypeScript | Java |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Interface** | Compile-time type that is erased; compatibility is generally structural. `implements` checks a class but adds no behavior or runtime identity. | Runtime nominal type; may declare abstract, `default`, and static methods. A class may implement several interfaces. |
| **Abstract class** | Runtime class that may contain fields, constructors, and implemented methods; cannot be instantiated directly. A class extends at most one class. | Runtime class that may contain state, constructors, and implemented methods; a class extends at most one class. |

Use an interface when callers need a contract. Use an abstract class when a real inheritance relationship and shared implementation justify the extra coupling. Neither one is automatically better or makes remote effects atomic.

## Polymorphism: one call, different behavior

With subtype polymorphism, a caller invokes a contract and runtime dispatch selects the implementation from the object:

```typescript
abstract class Shape {
  abstract area(): number;
}

class Circle extends Shape {
  constructor(private readonly radius: number) { super(); }
  area(): number { return Math.PI * this.radius ** 2; }
}

class Rectangle extends Shape {
  constructor(private readonly width: number, private readonly height: number) { super(); }
  area(): number { return this.width * this.height; }
}

function totalArea(shapes: readonly Shape[]): number {
  return shapes.reduce((sum, shape) => sum + shape.area(), 0);
}
```

`totalArea` does not branch on concrete class. `Circle.area` or `Rectangle.area` runs according to the object passed. This works only while each implementation satisfies the behavior promised by `Shape`; a matching method signature alone is not enough. The dimensions here are assumed valid so the example can focus on dispatch.

Three forms are commonly discussed:

| Form | How behavior is selected | Example |
| -------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **Subtype** | Runtime object dispatches an overridden method through a base contract. | `shape.area()` above |
| **Parametric** | One generic implementation preserves a type relationship without branching on the type parameter. | TypeScript `function identity<T>(value: T): T { return value; }` |
| **Ad hoc** | A finite set of operations is selected from declared overloads, usually using compile-time argument types. | Java `add(int, int)` and `add(double, double)` overloads |

TypeScript erases generic parameters at runtime. TypeScript overload signatures also share one implementation body, which must handle the supported input cases. These compile-time forms differ from subtype dispatch on a runtime object.

## Inheritance and composition: choose the promise you need

Inheritance derives a class from a base class, sharing implementation and exposing the derived instance through the base type. That means callers can rely on the base contract; the derived behavior must preserve it. The [Liskov Substitution Principle](30.1.1.01-solid-principles.md) explains how to check that promise. Inheritance for code reuse alone can also expose subclasses to unrelated base-class changes and extension hooks.

**Open recursion** is a consequence of virtual method dispatch: a method that calls another method through `this` can reach a subclass override. This is useful for explicit extension hooks, but a base constructor that calls an overridable method can run subclass code before subclass fields are initialized. Avoid that constructor pattern unless its initialization contract is deliberate.

Composition gives an object a collaborator and delegates a task without making the collaborator a subtype:

```typescript
interface Engine {
  start(): void;
}

class Car {
  constructor(private readonly engine: Engine) {}
  drive(): void { this.engine.start(); }
}
```

Use inheritance when substitution is valid and shared implementation is useful. Use composition when a behavior varies independently or reuse does not require an “is-a” promise. Composition still adds a collaborator contract and wiring; a plain function is simpler when neither is needed.

## Relationships describe references and ownership

In UML, association, aggregation, and composition answer different relationship questions. Their symbols describe the model; they do not cause a language runtime or database to enforce ownership.

| Relationship | UML notation | Meaning and example |
| --------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Association** | Solid line; an arrow may show navigability. | Objects are related, such as a professor advising students. No lifecycle ownership is implied. |
| **Aggregation** | Hollow diamond at the whole. | A weak whole-part grouping, such as a team grouping members who can exist independently. It does not imply exclusive ownership or automatic deletion. |
| **Composition** | Filled diamond at the whole. | A strong ownership relationship, such as an order owning its line items. A part belongs to at most one composite at a time; deleting the composite deletes its object parts unless they were first removed. |

The model must still state multiplicities, removal rules, and persistence behavior. A database cascade, garbage collection, or cleanup action is an implementation choice; the UML diamond does not perform it. For multiplicity and diagram notation, see [UML Basics](30.1.1.04-uml-basics.md).

## Cohesion and coupling explain boundary quality

**Cohesion** describes whether a module's responsibilities serve a related purpose. An account's deposit, withdrawal, and validation operations can be cohesive because together they preserve its balance invariant. Method count alone does not decide cohesion.

**Coupling** describes how one module depends on another's representation, types, behavior, timing, shared state, or failure. An interface hides a concrete representation, but callers still depend on its semantics, errors, and availability. Keep related invariants together and isolate decisions that change independently; splitting every operation into its own class can scatter one rule and add indirection.

A method call such as `account.withdraw(amount)` is useful because the account owns the balance invariant. Reading a public balance, checking it elsewhere, and then mutating it splits the rule across callers. A method call still does not serialize two processes writing the same persisted row.

## Use OOP alongside other styles

OOP is useful when stateful behavior needs one owner or several implementations must satisfy a shared contract. Other styles solve different problems, and real systems combine them:

| Style | Useful when | Watch for |
| ------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Object-oriented** | State transitions and behavior belong to stable owners; callers benefit from interchangeable implementations. | Mutable state, implicit inheritance hooks, and class scaffolding can obscure simple operations. |
| **Functional** | Transformations are easier to reason about as explicit inputs and outputs, often without mutation. | Effects still need explicit boundaries; practical functional languages may allow controlled mutation. |
| **Procedural** | A sequence of operations over explicit data is the clearest model. | Large systems still need module boundaries and clear ownership for shared invariants. |
| **Reactive** | Behavior depends on change over time, events, or streams. | Backpressure, ordering, cancellation, and failure semantics need definition; reactive code can still use objects and pure functions. |

A data-transfer object can remain data-only. Introduce behavior-rich objects where they prevent callers from implementing the same invariant inconsistently; do not create a class for every domain noun.

## Warning signs to investigate

- Several callers mutate the same invariant-bearing state through different paths.
- A subtype requires callers to inspect its concrete type or avoid valid base operations.
- A class or interface only forwards calls and adds no useful contract, state ownership, or change boundary.
- A UML composition diamond is mistaken for automatic memory cleanup or database cascading.

These are signals to inspect the contract and actual changes, not automatic proof of a design defect.

## Summary

Organize objects around owned state, legal transitions, and caller-visible contracts. Encapsulation protects invariants; abstraction exposes needed operations; polymorphism lets compatible implementations serve one contract. Inheritance creates a subtype promise, while composition delegates behavior without that promise. UML relationships describe association and ownership, but code and storage must enforce the required lifecycle.

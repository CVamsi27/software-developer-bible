# OOP Concepts — Encapsulation, Inheritance, Polymorphism, Abstraction

## Definition

**Object-oriented programming** is a way of organizing a program as a set of objects that own state and expose behavior, so that the *internal representation* of that state can change without changing every caller. Encapsulation, abstraction, inheritance and polymorphism are commonly taught together, but an object-oriented design does not need an inheritance hierarchy for every collaboration:

> **Textbook Definition:** Object-oriented programming models computation through interacting objects that encapsulate state and behavior, with abstraction and polymorphism defining contracts independently of concrete implementations.

| Pillar | Mechanism | What it buys |
| ----------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **Encapsulation** | private state + public methods | callers depend on a contract, not a representation |
| **Abstraction** | interfaces / abstract types | callers depend on *what*, not *how* |
| **Inheritance** | derives a class from a base class; behavioral substitution needs a compatible contract | shared implementation and, where valid, use through a base type |
| **Polymorphism** | same message, different implementation | call-site code stops branching on type |

The relationship vocabulary describes a different question: how objects are connected and who owns their lifecycle. UML composition also has a narrower meaning than the general programming advice to compose collaborators:

```text
association  A is related to B                 (e.g. advisor and student)
aggregation  A groups B as a shared part        (e.g. team members)
composition  A owns B as an exclusive part      (lifecycle responsibility in the model)
```

Encapsulation gives a representation and its mutation rules a controlled boundary. Private fields help, but a getter exposing a mutable collection or several callers updating the same persisted row can still bypass the intended rule. Specify the invariant and every path that can change it.

Inheritance reuses behavior through a base class; a valid behavioral subtype must preserve the base contract. Composition delegates behavior to a collaborator and can make independently changing behavior replaceable. Both create dependencies. Prefer the mechanism that fits the actual variation, ownership and substitution requirements; a physical “is-a” or “has-a” phrase cannot prove that fit.

## First Principles

Suppose callers can change an account's balance directly. Every caller must repeat the same validity checks, and one missed check breaks the rule. Giving an object ownership of that state creates one controlled mutation path.

Now suppose several account kinds support the same operation. A caller can use a shared contract only if each kind preserves its promises. It should not have to inspect the implementation to decide whether withdrawal is safe. Separating that contract from storage and calculation lets representations change without rewriting every caller.

These constraints lead to encapsulation, abstraction, and polymorphism. Inheritance is one mechanism for obtaining a subtype contract and shared implementation; delegation through a collaborator is another way to reuse behavior. Neither mechanism eliminates the need to specify and enforce the promises.

## Why it matters

A useful object model says which state each object owns, which transitions are legal, and what callers may rely on after an operation. Start with those rules rather than converting every noun into a class. A data-transfer object can remain data-only; a domain object is useful when it centralizes behavior that would otherwise diverge across callers.

An abstract class is justified when a shared implementation and inheritance contract are useful. An interface is justified by a caller's contract, even if only one implementation currently exists. Neither choice establishes transaction atomicity, thread safety or correct remote effects.

## The 4 Pillars

### 1. Encapsulation

**Definition:** Bundling data with the methods that operate on that data, and restricting direct access to some of the object's components.

**Key idea:** Hide state. Expose behavior.

**Violation (no encapsulation):**

```typescript
class BankAccount {
  balance: number = 0; // Public! Anyone can change it.
}

const account = new BankAccount();
account.balance = -1000000; // Oops, allowed.
account.balance = 999999999; // No validation.
```

**Fix (with encapsulation):**

```typescript
class BankAccount {
  // Integer minor units; TypeScript private is a compile-time boundary.
  private balance: number;

  constructor(initialBalance: number) {
    if (!Number.isSafeInteger(initialBalance) || initialBalance < 0) {
      throw new Error('Initial balance must be a nonnegative safe integer');
    }
    this.balance = initialBalance;
  }

  private validateAmount(amount: number): void {
    if (!Number.isSafeInteger(amount) || amount <= 0) {
      throw new Error('Amount must be a positive safe integer');
    }
  }

  deposit(amount: number): void {
    this.validateAmount(amount);
    const nextBalance = this.balance + amount;
    if (!Number.isSafeInteger(nextBalance)) throw new Error('Balance overflow');
    this.balance = nextBalance;
  }

  withdraw(amount: number): void {
    this.validateAmount(amount);
    if (amount > this.balance) throw new Error('Insufficient funds');
    this.balance -= amount;
  }

  getBalance(): number { return this.balance; }
}

const account = new BankAccount(100);
account.deposit(50);
account.withdraw(40);
console.log(account.getBalance()); // 110
try { account.withdraw(200); } catch { console.log('rejected'); }
console.log(account.getBalance()); // 110: rejection changed no state
```

The invariant is a nonnegative safe-integer balance. Validation happens before mutation, including `NaN`, infinity, fractional values, and overflow checks. A plain `amount <= 0` check misses `NaN`, which would otherwise poison the balance. The example demonstrates one in-memory object's contract; it does not implement currency conversion, persistence, or concurrent transfers.

A getter returning a number cannot expose mutable internals. A getter returning an internal array or object could, unless the owner copies it or intentionally defines a shared-reference contract. Setters are useful only when they enforce the same invariant; `setBalance(anyNumber)` would reopen the hole.

**Language boundaries differ:**

| Control | TypeScript | Java |
| -------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `private` | Checked by the type checker; ordinary emitted properties remain accessible JavaScript properties | Access restricted under Java's class/nest and runtime access rules |
| `protected` | Checked for the declaring class and allowed subclass access | Also permits same-package access; subclass access outside the package has additional receiver restrictions |
| `public` | Public member under the static type contract | Access also depends on the enclosing type/package/module being accessible |
| Package access | No Java-style package-private member keyword | Omitting an access modifier gives package access where applicable |
| `readonly` / `final` | `readonly` restricts reassignment during checking | `final` restricts field reassignment under Java rules |

Neither `readonly` nor `final` deeply freezes the referenced object. JavaScript `#private` fields provide a separate runtime-enforced private-field boundary. Static access controls are not authorization checks for untrusted input or another process.

### 2. Inheritance

**Definition:** Class inheritance derives a class from a base class under the language's member and dispatch rules. Using that derived object wherever the base is expected also requires a compatible behavioral contract.

```typescript
class Animal {
  constructor(public name: string) {}
  speak(): string { return `${this.name} makes a sound.`; }
}

class Dog extends Animal {
  speak(): string { return `${this.name} barks.`; }
}

class Cat extends Animal {
  speak(): string { return `${this.name} meows.`; }
}

const dog = new Dog("Rex");
console.log(dog.speak()); // "Rex barks."
```

The subclass inherits shared behavior and overrides selected operations. The caller can use a base-type reference, but type compatibility alone does not prove that each override preserves the base's promised results, errors and state transitions. The [SOLID chapter's Liskov substitution section](30.1.1.01-solid-principles.md) owns that behavioral test.

A base implementation calling overridable methods can couple its internal algorithm to subclass behavior. Changes to that algorithm can therefore affect subclasses even when public signatures stay the same. Inheritance can still fit a stable framework contract with explicit extension hooks. Use delegation when behavior must vary independently or reuse does not require substitutability; it avoids inheriting unrelated base obligations but still needs a collaborator contract.

### 3. Polymorphism

**Definition:** The ability of different objects to respond to the same message (method call) in different ways.

**Common forms:**

#### a. Subtype polymorphism (method overriding)

```typescript
abstract class Shape {
  abstract area(): number;
  abstract perimeter(): number;
}

class Circle extends Shape {
  constructor(public radius: number) { super(); }
  area(): number { return Math.PI * this.radius ** 2; }
  perimeter(): number { return 2 * Math.PI * this.radius; }
}

class Rectangle extends Shape {
  constructor(public width: number, public height: number) { super(); }
  area(): number { return this.width * this.height; }
  perimeter(): number { return 2 * (this.width + this.height); }
}

// Same method call, different behavior
function printArea(shapes: Shape[]): void {
  for (const shape of shapes) {
    console.log(`Area: ${shape.area().toFixed(2)}`); // Runtime dispatch, then formatting
  }
}

printArea([new Circle(5), new Rectangle(4, 6)]);
// "Area: 78.54"
// "Area: 24.00"
```

The loop calls the `Circle.area` implementation for the first object and `Rectangle.area` for the second. Dispatch selects behavior from the runtime object; the caller only needs the `Shape` contract. These independent geometry snippets omit dimension validation to focus on dispatch.

#### b. Parametric polymorphism (generics)

```typescript
function identity<T>(value: T): T { return value; }
const num = identity(42); // T = number
const str = identity("hello"); // T = string
```

`identity` has one implementation that works without inspecting `T`. TypeScript preserves the relationship between input and output types during checking, then erases the generic type; there is no separate number implementation selected at runtime.

#### c. Ad-hoc polymorphism (overloads and type-specific operations)

```java
// Java supports overloading
public class Calculator {
  public int add(int a, int b) { return a + b; }
  public double add(double a, double b) { return a + b; }
  public String add(String a, String b) { return a + b; }
}
```

In Java, `add(2, 3)` selects the integer overload and `add("2", "3")` selects string concatenation based on the compile-time argument types. Overload selection differs from an overridden method being dispatched on the runtime object. TypeScript overload signatures also share one implementation body, which must handle the supported inputs.

**When to use:** When you have multiple types that share a common interface but have different behavior.

### 4. Abstraction

**Definition:** Hiding complex implementation details and exposing only the essential features.

**Mechanisms:**
- Abstract classes
- Interfaces
- Methods (signature without implementation)

**Abstract class:** Structural sketch: `PaymentResult` and provider integrations are omitted. The success objects below are placeholders, not evidence that a payment was sent. `validateAmount` is a shared example rule, not a provider limit.

```typescript
abstract class PaymentProcessor {
  // Abstract method: subclasses must implement
  abstract processPayment(amount: number, currency: string): Promise<PaymentResult>;

  // Concrete method: shared by all subclasses
  validateAmount(amount: number): boolean {
    return Number.isFinite(amount) && amount > 0 && amount < 1000000;
  }
}

class StripeProcessor extends PaymentProcessor {
  async processPayment(amount: number, currency: string): Promise<PaymentResult> {
    if (!this.validateAmount(amount)) throw new Error("Invalid amount");
    // Stripe-specific logic
    return { success: true, transactionId: "..." };
  }
}

class PayPalProcessor extends PaymentProcessor {
  async processPayment(amount: number, currency: string): Promise<PaymentResult> {
    if (!this.validateAmount(amount)) throw new Error("Invalid amount");
    // PayPal-specific logic
    return { success: true, transactionId: "..." };
  }
}
```

**Interface (type contract, no runtime implementation in TypeScript):** This is a separate example, not a declaration to combine with the preceding abstract class.

```typescript
interface PaymentProcessor {
  processPayment(amount: number, currency: string): Promise<PaymentResult>;
  refund(transactionId: string): Promise<RefundResult>;
}

interface Notifier {
  notify(userId: string, message: string): Promise<void>;
}

// Checkout consumes both contracts; it need not be a processor or notifier.
class CheckoutService {
  constructor(private payments: PaymentProcessor, private notifier: Notifier) {}
  async checkout(userId: string, amount: number, currency: string): Promise<PaymentResult> {
    const result = await this.payments.processPayment(amount, currency);
    if (result.success) await this.notifier.notify(userId, 'Payment accepted');
    return result;
  }
}
```

The service receives collaborators, invokes payment, and only then notifies on success. A real contract must define what `success` means, which failures are retryable, and how the operation is identified across retries. If notification throws after payment succeeds, blindly rerunning checkout can duplicate the charge; abstraction alone does not resolve that workflow boundary.

## "Has-a" Relationships

### Association

**Definition:** A loose relationship where one class uses another. "Knows-about."

```typescript
class Professor {
  advise(student: Student): void { /* ... */ }
}

class Student {
  // Has a reference to advisor (or none)
}
```

**UML:** Solid line, often with arrow.

### Aggregation

**Definition:** A "whole-part" relationship where the part can exist without the whole. "Has-a," but loosely.

```typescript
class Department {
  professors: Professor[] = [];

  addProfessor(p: Professor): void { this.professors.push(p); }
}

class Professor {
  // Professor can exist without Department
}
```

**UML:** Hollow diamond on the whole's side.

**Real-world example:** A Department has-a Professor, but if the Department is deleted, the Professor still exists.

### Composition

**Definition:** A whole-part relationship with exclusive ownership and lifecycle responsibility in the model. A part belongs to at most one composite at a time; the model specifies what happens when the whole is deleted or the part is removed.

```typescript
class House {
  private rooms: Room[];

  constructor() {
    // Rooms are created with the house
    this.rooms = [new Room("kitchen"), new Room("bedroom")];
  }
}

class Room {
  constructor(public name: string) {}
}

// Model ownership explicitly; JavaScript does not automatically destroy Room
// objects when a House reference disappears.
```

**UML:** Filled diamond on the whole's side.

**Real-world example:** In a building model, rooms may be parts whose lifecycle is managed by the house. This is a domain decision. Holding references in JavaScript does not automatically enforce exclusive ownership, cascade deletion, or resource cleanup; those rules need implementation.

## Cohesion & Coupling

### Cohesion

**Cohesion** describes how strongly a module's elements serve related responsibilities. Account deposits, withdrawals and validation can form one cohesive module because they preserve the same balance rule. Method count does not decide cohesion. A repository that also owns unrelated email, reporting and login policy can mix independent reasons to change.

### Coupling

**Coupling** is dependency between modules: on representations, types, behavior, timing, shared state or failure. Reaching into another module's internal state creates a representation dependency. An interface can reduce that exposure, but callers still depend on its semantics and error behavior. A payment interface does not make a remote provider's outage disappear.

Choose boundaries that keep related rules together and limit unnecessary change propagation. Splitting every small operation into its own interface can add indirection while scattering one invariant. Evaluate a concrete change or failure: which modules must change, which assumptions remain stable, and what new coordination is required?

## Message Passing

**Definition:** Objects communicate by sending messages to each other (calling methods).

```typescript
const order = new Order(items);
const total = order.calculateTotal(); // Message: "calculate your total"
order.place(); // Message: "place yourself"
```

**vs. direct state access:**

```typescript
// Bypasses any order-owned transition checks
const orderTotal = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
order.total = orderTotal;
order.status = 'placed';
```

**OOP style:** Put the rules for transitioning from draft to placed under one owner. The calculation can still be a pure function. The problem in the direct-write sketch is that it can set `placed` without enforcing the transition contract, not that procedural code is inherently invalid.

```typescript
// Better: tell, don't ask
order.calculateTotal();
order.place();
```

## Open Recursion

**Definition:** The `this`/`self` reference in OOP that lets methods call other methods on the same object polymorphically.

```typescript
class Animal {
  speak(): string { return this.makeSound(); }

  protected makeSound(): string { return "..."; }
}

class Dog extends Animal {
  protected makeSound(): string { return "woof"; }
}

const dog = new Dog();
console.log(dog.speak()); // "woof" — calls Dog's makeSound through this
```

**Why it matters:** `Dog` inherits `speak`, but inside that method `this` is still the dog. The call to `makeSound` therefore reaches the override and produces `woof`. This dispatch also means a base constructor calling an overridable method can reach subclass behavior before subclass fields are initialized; avoid such constructor hooks unless their initialization contract is explicit.

## OOP vs other paradigms

**OOP strengths:** Modeling real-world entities, polymorphism, encapsulation.
**OOP costs:** Mutable state and hierarchies need explicit ownership, substitution and initialization rules. Excess classes or abstraction can obscure a simple operation.

**Alternatives:**
- **Functional programming (FP):** Emphasizes pure functions, immutable data and composition. Many practical functional languages also support controlled effects or mutable state.
- **Procedural:** Organizes operations into procedures; it can also support large systems with deliberate module boundaries.
- **Reactive:** Models change propagation or asynchronous streams; it can combine with objects and pure functions. These are compatible tools rather than mutually exclusive architectures.

---

## Anti-patterns

- **God class.** A class embeds unrelated change rules. Method and field counts alone do not establish low cohesion.
- **Scattered invariants.** Several services mutate the same state with inconsistent rules. Data-only transfer objects are useful; a behavior-rich object is valuable when it centralizes rules that otherwise diverge.
- **Inheritance for code reuse only.** "Car extends Engine to reuse Engine's methods." Wrong. Car HAS-A Engine.
- **Unjustified hierarchy.** Inherited obligations and extension hooks add complexity without a real substitution or variation need; depth alone is not the diagnostic.
- **Uncontrolled mutation.** Public mutable fields expose transitions that should preserve an invariant. Public immutable values or transfer objects can be deliberate contracts.
- **Unmanaged dependency cycles.** Cycles can complicate initialization, independent testing or change boundaries. Distinguish a harmful module cycle from a deliberate bidirectional relationship with controlled ownership.

---

## Summary

Organize objects around owned state, legal transitions and caller-visible contracts. Encapsulation controls representation and mutation; abstraction exposes the required operations; polymorphism lets compatible implementations serve one caller contract. Inheritance and delegation provide different reuse mechanisms, and UML relationships describe separate ownership choices. Evaluate cohesion, coupling and failure through a concrete change rather than counting classes or repeating a design slogan.

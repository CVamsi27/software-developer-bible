# Singleton Pattern

Two startup callers ask for a connection pool before its opening work finishes. Sharing requires a clear scope and one initialization owner — it never means every process in a deployment gets the same object.

```typescript
const first = Registry.getInstance();
const second = Registry.getInstance();
console.log(first === second); // true in this loaded class instance
```

## Definition

A **Singleton** controls construction so one instance is accessed within a defined **runtime scope**. Traditional implementations also provide a global access point. "One instance" means the class/module instance in that runtime, not automatically one across workers, processes, bundles, or deployed replicas.

> **Textbook Definition:** Singleton is a creational pattern that restricts a class to one instance within a defined runtime scope and provides a shared means of accessing that instance.

## First Principles

1. A resource may need one lifecycle owner, such as the pool managing many database connections.
2. Uncontrolled construction creates independent owners. Construction and ownership must be constrained when the resource contract requires one.
3. A global lookup hides a dependency. Passing the owner explicitly retains one shared instance while keeping callers and tests easy to inspect.

## 1. Trace two accesses to one stored instance

```typescript
class Registry {
  private static instance: Registry | undefined;
  private constructor() {}
  static getInstance(): Registry {
    return Registry.instance ??= new Registry();
  }
}
const first = Registry.getInstance();
const second = Registry.getInstance();
console.log(first === second); // true in this loaded class instance
```

The first call creates and stores an instance; the second returns the stored reference. TypeScript's `private` constructor blocks ordinary construction during type-checking, but the emitted JavaScript still has a callable constructor — treat the modifier as an API constraint, not a runtime security boundary.

```text
caller A ─┐
          ├─→ one loaded Registry class → stored instance
caller B ─┘
other worker/process → separate runtime → separate loaded class/instance
```

Synchronous JavaScript evaluation in one agent never interleaves two ordinary calls halfway through this construction. A boolean named `isInitializing` does not implement thread-safe double-checked locking. Shared-memory languages need their actual locking and publication rules; separate JS workers do not share this class static field by default.

## 2. Share one instance per module or container

A loaded module can export one object:

```typescript
// registry.ts
export const registry = new Map<string, unknown>();
```

Imports resolving to that same module instance share it. Multiple module copies, different resolutions, hot reload, or separate runtimes may produce different instances — modules cache one loaded module instance; they are not a distributed singleton mechanism.

A dependency-injection container can likewise create one pool or configuration service and pass it to callers. The caller's dependency becomes explicit while lifetime stays centrally owned. Container scopes and child containers determine what "singleton" means there.

## Share Asynchronous Initialization

If initialization awaits I/O, concurrent callers can both start it unless they share the in-flight operation. Cache its promise:

```typescript
function sharedAsyncResource<T>(open: () => Promise<T>) {
  let pending: Promise<T> | undefined;
  return function get(): Promise<T> {
    if (!pending) {
      pending = Promise.resolve().then(open).catch(error => {
        pending = undefined; // allow a later deliberate retry after failure
        throw error;
      });
    }
    return pending;
  };
}
```

All concurrent callers receive the same pending result. This is asynchronous single-flight in one runtime, not a cross-process lock. The owner must also define shutdown, reconnect, and disposal — clearing a reference never closes connections.

## 4. Decide whether one instance is appropriate

| Candidate | Question to settle |
| --------------- | -------------------------------------------------------------------- |
| Configuration | Is it immutable after startup or refreshed under an explicit policy? |
| Connection pool | What is the fleet-wide connection budget and shutdown owner? |
| Logger | How are request context, buffering and flushing scoped? |
| Cache | Who bounds retention and keeps tenant/private data separated? |
| Event bus | Who unregisters callbacks, and what runtime boundary does it reach? |

One instance never makes its mutable state race-free, tenant-safe, or durable. A shared user-service instance is valid when stateless; it must not store one request's identity in an unscoped field.

## Common Mistakes

- Claiming one module export coordinates every replica. Use the shared store's actual coordination contract for a distributed invariant.
- Using a global accessor to hide dependencies. Prefer an explicit constructor or function parameter when it clarifies ownership.
- Starting initialization twice because the cached object appears only after an await. Share the pending promise.
- Resetting global state in tests without disposing the old resource. Isolate owners and close their resources.
- Keeping an unbounded cache or listener registry alive for the application's lifetime. Give retained data a clear expiry and cleanup policy.

## Summary

State the scope of "one," constrain construction only when that scope requires it, and make the lifecycle owner visible. Module exports or DI can share an instance within one runtime; asynchronous initialization needs single-flight, and distributed ownership needs a separate coordination mechanism.

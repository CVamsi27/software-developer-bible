# Factory Method and Simple Factories

Notification code can repeatedly choose an email, SMS, or push constructor. A reusable vehicle-report workflow can also need a subclass to supply its vehicle. Both hide construction choices, but their extension mechanisms differ.

## Definition

**Factory Method** defines an overridable creation operation: a base creator uses a product interface while subclasses choose the concrete product. A function or switch that directly chooses a constructor is a **simple factory**, a useful technique with a different extension mechanism. Examples in this chapter distinguish the two rather than treating every factory function as the GoF pattern.

> **Textbook Definition:** Factory Method is a creational pattern in which a creator defines an object-creation operation whose subclasses determine the concrete product returned through a common product interface.

The pattern is particularly useful when the creation process is complex, involves multiple steps, or when the system needs to be independent from how its objects are created.

## First Principles

A use case must obtain an object before calling its behavior. If every use case chooses the concrete constructor and initialization options itself, those choices must change together when a provider changes. Moving that decision to one boundary removes repeated knowledge.

There are two distinct extension needs. A fixed configuration selector can choose a constructor centrally. A reusable base workflow can instead call an overridable creation operation, letting a subclass supply its product while the workflow stays stable. The first needs a simple factory; the second motivates Factory Method. A passed creation function can provide similar variation without an inheritance hierarchy.

## Why Do We Need It?

Without the Factory pattern, object creation logic is scattered throughout the codebase, leading to:

1. **Tight coupling**: Code depends on specific concrete classes

2. **Code duplication**: Object creation logic repeated everywhere

3. **Difficult maintenance**: Changing creation logic requires modifying multiple places

4. **Testing challenges**: Hard to mock or replace object creation

## How It Works

In a simple factory, the client asks a central selector for a product. In Factory Method, the base creator's workflow calls its creation operation; virtual dispatch reaches the concrete creator and returns a product that satisfies the workflow's contract.

```text
Simple factory:
client → selector(type) → concrete constructor → product

Factory Method:
client → base workflow on concrete creator
                   → overridden createProduct() → concrete product
                   → workflow uses product interface
```

The factory hides the creation choice from this client, not from the application entirely. Setup still selects a creator or registers a constructor. Resource products also need a clear owner for disposal; construction indirection does not close files or connections.

## Code Examples

### Simple Factory

This independent example logs messages; it does not contact an email, SMS, or push provider.

```typescript
// Product interface
interface NotificationProduct {
  send(message: string): void;
}

// Concrete products
class EmailNotification implements NotificationProduct {
  send(message: string): void {
    console.log(`Sending email: ${message}`);
  }
}

class SMSNotification implements NotificationProduct {
  send(message: string): void {
    console.log(`Sending SMS: ${message}`);
  }
}

class PushNotification implements NotificationProduct {
  send(message: string): void {
    console.log(`Sending push notification: ${message}`);
  }
}

// Simple Factory
class NotificationFactory {
  static create(type: 'email' | 'sms' | 'push'): NotificationProduct {
    switch (type) {
      case 'email':
        return new EmailNotification();
      case 'sms':
        return new SMSNotification();
      case 'push':
        return new PushNotification();
      default:
        throw new Error(`Unknown notification type: ${type}`);
    }
  }
}

// Usage
const emailNotifier = NotificationFactory.create('email');
emailNotifier.send('Hello World!'); // Sending email: Hello World!

```

### Factory Method Pattern

```typescript
// Abstract creator
abstract class VehicleFactory {
  abstract createVehicle(): Vehicle;

  // Template method that uses the factory method
  describeVehicle(): void {
    const vehicle = this.createVehicle();
    console.log(`Created ${vehicle.getType()} with ${vehicle.getWheels()} wheels`);
  }
}

// Product interface
interface Vehicle {
  getType(): string;
  getWheels(): number;
  accelerate(): void;
}

// Concrete products
class Car implements Vehicle {
  getType(): string {
    return 'Car';
  }

  getWheels(): number {
    return 4;
  }

  accelerate(): void {
    console.log('Car is accelerating');
  }
}

class Motorcycle implements Vehicle {
  getType(): string {
    return 'Motorcycle';
  }

  getWheels(): number {
    return 2;
  }

  accelerate(): void {
    console.log('Motorcycle is accelerating');
  }
}

class Truck implements Vehicle {
  getType(): string {
    return 'Truck';
  }

  getWheels(): number {
    return 6;
  }

  accelerate(): void {
    console.log('Truck is accelerating');
  }
}

// Concrete factories
class CarFactory extends VehicleFactory {
  createVehicle(): Vehicle {
    return new Car();
  }
}

class MotorcycleFactory extends VehicleFactory {
  createVehicle(): Vehicle {
    return new Motorcycle();
  }
}

class TruckFactory extends VehicleFactory {
  createVehicle(): Vehicle {
    return new Truck();
  }
}

// Usage
const carFactory = new CarFactory();
carFactory.describeVehicle(); // Created Car with 4 wheels

const truckFactory = new TruckFactory();
truckFactory.describeVehicle(); // Created Truck with 6 wheels

```

`create('email')` enters the email branch, creates an `EmailNotification`, and returns it as `NotificationProduct`; the client then calls `send`. A new channel adds a branch in this central selector. This is a valid simple factory when the selector is small and owns the configuration decision.

In the vehicle example, `carFactory.describeVehicle()` runs the inherited workflow. Its call to `this.createVehicle()` reaches `CarFactory`, then the workflow reads the returned product's type and wheels. `TruckFactory` follows the same workflow with another product. Adding a creator leaves that workflow unchanged, while setup still chooses the new creator. Classes and methods here describe toy vehicles, not physical vehicle control.

## Choose the Creation Boundary

| Variation | Mechanism |
| ----------------------------------------------------------------- | --------------------------------------------------- |
| One configuration chooses a constructor | Simple factory or registry |
| A creator subclass supplies the product used by its base workflow | Factory Method |
| Related products must come from a compatible family | [Abstract Factory](30.1.2.04-abstract-factory.md) |
| A service needs an externally supplied dependency | Dependency injection; a factory may be its provider |

Payment processors, document generators and response objects can all use factories, but their domain name does not determine the pattern. Keep construction separate from the product's business work. Validation and safe resource initialization can legitimately be part of construction.

## Keep selection and product behavior separate

| Mistake | Boundary to use instead |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Adding an empty factory wrapper around every constructor | Use direct construction when it has no variation or shared setup to hide |
| Executing checkout or sending mail while creating a product | Return a ready collaborator; the application invokes its business operation |
| Returning `any` and allowing unsupported selectors to return `undefined` | Return the product contract and reject unknown configuration explicitly |
| Demanding a registry for a small closed selector | Keep a switch until registration is a real extension requirement |
| Caching a stateful request product as if it were reusable | Decide lifetime, tenant/request scope, and disposal separately from selection |

Validation of constructor options and acquiring a required resource can belong to creation. Domain business work belongs to the product or coordinator. A factory performing validation is not automatically an SRP violation.

### A registry changes who supplies creation choices

Reuse the notification product classes from the simple-factory example:

```typescript
class ProductRegistry<T> {
  private creators = new Map<string, () => T>();
  register(name: string, creator: () => T): void {
    if (this.creators.has(name)) throw new Error(`Duplicate product: ${name}`);
    this.creators.set(name, creator);
  }
  create(name: string): T {
    const creator = this.creators.get(name);
    if (!creator) throw new Error(`Unknown product: ${name}`);
    return creator();
  }
}

const registry = new ProductRegistry<NotificationProduct>();
registry.register('email', () => new EmailNotification());
registry.register('sms', () => new SMSNotification());
registry.create('sms').send('Ready'); // Sending SMS: Ready
```

Setup supplies the constructors. The registry rejects duplicate names and missing names, while each successful `create` invokes the supplied function. This sample creates a fresh product each time; if a registered function returns a cached object, its lifetime is different. A registry does not unload plugins, validate untrusted modules, or enforce cross-product compatibility.

## Construction cost and resource lifetime

Measure the actual initialization and allocation cost. Caching can reduce creation work only when sharing is correct for the product. An asynchronous connection-opening factory should expose its pending/error contract and shutdown owner; see [Singleton](30.1.2.01-singleton.md) for sharing one in-flight initialization. TypeScript interfaces and generics are erased, while the factory function, registry lookup, constructors, and any adapters execute at runtime.

## Summary

A simple factory owns a central creation choice; Factory Method lets a subclass supply the product used by a stable base workflow. The client still depends on a product contract, and setup still chooses or registers concrete implementations. Introduce the boundary for actual variation or shared initialization, then define rejection, lifetime, and cleanup independently.

# Builder Pattern

A request needs a URL, method, headers, body, and execution settings that agree before a client can use it. Named construction steps can keep those temporary choices together until the product is ready.

## Definition

The Builder pattern is a creational design pattern that separates the construction of a complex object from its representation. It allows you to produce different types and representations of an object using the same construction code.

> **Textbook Definition:** Builder is a creational pattern that expresses complex object construction as a sequence of steps, separating the construction procedure from the representation produced.

The pattern is particularly useful when you need to create an object with many optional parameters or when the construction process involves multiple steps.

## First Principles

Construction may require several decisions before the result is valid. Exposing the half-built product lets a caller use it before required parts agree; packing every decision into positional arguments makes omissions difficult to see.

Keep temporary state with a construction owner, name the steps, and expose the product at a final boundary. At that boundary, required values and cross-field rules can be checked together. Different construction owners can interpret the same steps differently when a genuine shared sequence exists. For simple data, a named options object plus a validating function may already solve the problem without a builder.

## Why Do We Need It?

Without the Builder pattern, object creation can be problematic:

1. **Telescoping constructors**: Too many constructor parameters

2. **Complex initialization**: Multiple steps needed to create an object

3. **Immutable objects**: Difficult to create immutable objects with many fields

4. **Readability**: Constructor calls with many parameters are hard to read

## How It Works

```text
client ──steps──→ builder's temporary state ──build/getResult──→ product
   │
   └─ optional director stores a reusable sequence of those same steps
```

The client controls individual choices; a director can reuse a standard sequence; the builder owns intermediate state and the hand-off policy. These are roles, not a requirement for three classes. A returned product must be independent of later builder edits according to its contract. Mutable products and shared references are still possible unless deliberately prohibited.

## Code Examples

### Basic Builder Pattern

```typescript
// Product
class House {
  constructor(
    public foundation: string,
    public structure: string,
    public roof: string,
    public interior: string,
    public garden: string,
    public garage: string
  ) {}

  toString(): string {
    return `
House:
  Foundation: ${this.foundation}
  Structure: ${this.structure}
  Roof: ${this.roof}
  Interior: ${this.interior}
  Garden: ${this.garden}
  Garage: ${this.garage}
    `.trim();
  }
}

// Builder interface
interface HouseBuilder {
  buildFoundation(): HouseBuilder;
  buildStructure(): HouseBuilder;
  buildRoof(): HouseBuilder;
  buildInterior(): HouseBuilder;
  buildGarden(): HouseBuilder;
  buildGarage(): HouseBuilder;
  getResult(): House;
}

// Concrete builder
class ConcreteHouseBuilder implements HouseBuilder {
  private house: House;

  constructor() {
    this.house = new House('', '', '', '', '', '');
  }

  reset(): void {
    this.house = new House('', '', '', '', '', '');
  }

  buildFoundation(): HouseBuilder {
    this.house.foundation = 'Concrete foundation';
    return this;
  }

  buildStructure(): HouseBuilder {
    this.house.structure = 'Wooden structure';
    return this;
  }

  buildRoof(): HouseBuilder {
    this.house.roof = 'Tile roof';
    return this;
  }

  buildInterior(): HouseBuilder {
    this.house.interior = 'Modern interior';
    return this;
  }

  buildGarden(): HouseBuilder {
    this.house.garden = 'Landscaped garden';
    return this;
  }

  buildGarage(): HouseBuilder {
    this.house.garage = 'Two-car garage';
    return this;
  }

  getResult(): House {
    const result = this.house;
    this.reset();
    return result;
  }
}

// Director
class HouseDirector {
  private builder: HouseBuilder;

  constructor(builder: HouseBuilder) {
    this.builder = builder;
  }

  setBuilder(builder: HouseBuilder): void {
    this.builder = builder;
  }

  buildSimpleHouse(): House {
    return this.builder
      .buildFoundation()
      .buildStructure()
      .buildRoof()
      .getResult();
  }

  buildFullHouse(): House {
    return this.builder
      .buildFoundation()
      .buildStructure()
      .buildRoof()
      .buildInterior()
      .buildGarden()
      .buildGarage()
      .getResult();
  }
}

// Usage
const builder = new ConcreteHouseBuilder();
const director = new HouseDirector(builder);

const simpleHouse = director.buildSimpleHouse();
console.log(simpleHouse.toString());

const fullHouse = director.buildFullHouse();
console.log(fullHouse.toString());

// Without director
const customHouse = builder
  .buildFoundation()
  .buildStructure()
  .buildRoof()
  .buildInterior()
  .getResult();

console.log(customHouse.toString());

```

The simple-house director calls foundation → structure → roof → `getResult`. The returned house contains those three strings and empty optional fields. `getResult` switches the builder to a new house, so building a full house next does not modify the first result. This demonstrates assembly and reset, not physical construction or domain validation. The returned `House` is mutable.

### HTTP Request Builder

```typescript
interface HttpRequest {
  method: string;
  url: string;
  headers: Record<string, string>;
  body: any;
  timeout: number;
  retries: number;
}

class HttpRequestBuilder {
  private request: HttpRequest;

  constructor() {
    this.request = {
      method: 'GET',
      url: '',
      headers: {},
      body: null,
      timeout: 30000,
      retries: 0
    };
  }

  reset(): this {
    this.request = {
      method: 'GET',
      url: '',
      headers: {},
      body: null,
      timeout: 30000,
      retries: 0
    };
    return this;
  }

  method(method: 'GET' | 'POST' | 'PUT' | 'DELETE' | 'PATCH'): this {
    this.request.method = method;
    return this;
  }

  url(url: string): this {
    this.request.url = url;
    return this;
  }

  header(key: string, value: string): this {
    this.request.headers[key] = value;
    return this;
  }

  headers(headers: Record<string, string>): this {
    Object.assign(this.request.headers, headers);
    return this;
  }

  body(body: any): this {
    this.request.body = body;
    return this;
  }

  json(data: any): this {
    this.request.body = JSON.stringify(data);
    this.request.headers['Content-Type'] = 'application/json';
    return this;
  }

  timeout(timeout: number): this {
    this.request.timeout = timeout;
    return this;
  }

  retries(retries: number): this {
    this.request.retries = retries;
    return this;
  }

  bearerToken(token: string): this {
    this.request.headers['Authorization'] = `Bearer ${token}`;
    return this;
  }

  build(): HttpRequest {
    if (!this.request.url) throw new Error('URL is required');
    const parsed = new URL(this.request.url);
    if (parsed.protocol !== 'http:' && parsed.protocol !== 'https:') {
      throw new Error('Only HTTP(S) URLs are supported');
    }
    if (!Number.isSafeInteger(this.request.timeout) || this.request.timeout <= 0) {
      throw new Error('Timeout must be a positive integer in milliseconds');
    }
    if (!Number.isSafeInteger(this.request.retries) || this.request.retries < 0) {
      throw new Error('Retries must be a nonnegative integer');
    }
    return { ...this.request, headers: { ...this.request.headers } };
  }
}

// Usage
const request = new HttpRequestBuilder()
  .method('POST')
  .url('https://api.example.com/users')
  .header('Accept', 'application/json')
  .json({ name: 'John', email: 'john@example.com' })
  .bearerToken('my-token')
  .timeout(5000)
  .retries(3)
  .build();

console.log(request.method, request.timeout, request.retries); // POST 5000 3
console.log(request.body); // {"name":"John","email":"john@example.com"}
// No request has been sent. Pass this description to a compatible client.

```

## Copying, Validation and Reuse

A director stores a reusable construction sequence; it is optional when callers can state the steps clearly. `build()` or `getResult()` is the boundary where required fields and cross-field invariants must be enforced.

A fluent interface is method chaining; it is not proof of type safety or immutability. Builders commonly use mutable intermediate state. Define whether building resets that state, whether the builder is reusable and whether the result shares nested references. The House example demonstrates assembly rather than validating a physically complete house; a real domain constructor must enforce its own requirements.

The HTTP builder above creates a request description. Unlike the House builder, `build()` does not reset; call `reset()` or construct a fresh builder before an unrelated request. Rebuilding without reset retains headers, body, and retry settings. An object supplied to `body()` remains a shared reference; `json()` serializes immediately into a string. Its timeout/retry fields do not execute a timeout or make retries safe; the consumer must enforce those behaviors. Copying headers prevents later builder edits from changing an already built result. Object.freeze is shallow, so deep immutability needs a deliberate representation.

Test-data builders are useful when tests need small valid defaults plus selected overrides. For URLs prefer the platform URL/URLSearchParams APIs; for SQL use a parameterized query builder rather than concatenating unchecked strings.

## Keep invalid intermediate state inside the builder

A fluent chain only says methods return a builder; it does not prove steps were supplied in a valid order. The HTTP example rejects a missing or unsupported URL and invalid timeout/retry counts at `build`, when all settings are available. A type-state API can catch some missing steps during checking, but still needs runtime validation at external boundaries.

Defaults should fill optional policy choices, not invent required business data. Retrying a GET may be acceptable while repeating a POST can duplicate a side effect unless its consumer has a retry/idempotency contract. A retry count on a description does not establish that safety.

Do not invent one director interface for unrelated representations. A house and a car do not share meaningful `buildFoundation`/`buildRoof` steps merely because both are constructed. Use a shared builder contract only when one actual sequence can operate on all its implementations.

## Choose a builder or a named options object

Prefer a builder when ordered assembly, reusable recipes, or cross-field validation benefits from one construction owner. Prefer a plain options object and validating constructor/function when all values can be given clearly together. A large count of fields alone is not decisive.

Define whether `build` resets, whether results can mutate, which references are copied, and how failed builds affect reuse. Avoid sharing one mutable builder between concurrent requests. Measure intermediate allocation before pooling builders, because reuse can retain credentials, payloads, or old defaults.

## Summary

A builder keeps intermediate construction state behind named steps and exposes a product at a defined validation boundary. A director can reuse a meaningful sequence. State whether building resets and whether results share mutable references; chaining alone proves neither immutability nor validity. Use a named options object when it expresses the same requirement more simply.

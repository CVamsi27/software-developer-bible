# Abstract Factory Pattern

> **TL;DR:** Abstract Factory provides an interface for creating **families of related objects** without specifying their concrete classes. Use it when the system must be configured with one of several families of products that are designed to be used together.

## First Principles

Abstract Factory creates *families* of related objects:

1. **Consistency across a family is the invariant**: a MacButton with a WindowsScrollbar is a bug; the abstract factory makes "all widgets from one family" structural rather than remembered.
2. **It's factory-method raised to the family level**: one factory interface, N concrete factories, each producing a coherent set. Adding a family is one class; adding a *product kind* to every family is the pattern's known cost (interface change everywhere).
3. **In practice it's the theme/provider selection problem** — DB drivers, payment providers, UI kits: any "swap the whole stack" configuration.

## Definition

The Abstract Factory pattern is a creational design pattern that provides a way to encapsulate a group of individual factories that have a common theme. It is one of the 23 classic GoF patterns.

The pattern is particularly useful when:

- The system needs to be independent of how its products are created
- The system should be configured with one of multiple families of products
- A family of related product objects is designed to be used together
- You want to provide a class library of products, and you want to reveal just their interfaces, not their implementations

```text
┌────────────────────────────────┐
│ AbstractFactory                │
│ + createButton(): Button       │
│ + createCheckbox(): Checkbox   │
│ + createScrollbar(): Scrollbar │
└────────────────────────────────┘
                ▲ ▲ ▲
                │ │ │
    ┌───────────┴────────────────────────────────┐ ┌──────────┴───┐ ┌────────┴─────┐
    │ MacFactory │ │ WinFactory │ │ LinuxFactory │
    │ (concrete) │ │ (concrete) │ │ (concrete)   │
    └────────────────────────────────────────────┘ └──────────────┘ └───────────────┘
            │ │ │
            ▼ ▼ ▼
    MacButton, WinButton, LinuxButton,
    MacCheckbox, WinCheckbox, LinuxCheckbox,
    MacScrollbar WinScrollbar LinuxScrollbar
```

## Why Do We Need It?

Without Abstract Factory, code that needs to vary its UI components by platform becomes:

```typescript
// BAD: tight coupling, scattered platform checks
function renderButton(os: 'mac' | 'win' | 'linux') {
  if (os === 'mac') {
    return new MacButton();
  } else if (os === 'win') {
    return new WinButton();
  } else {
    return new LinuxButton();
  }
}

function renderCheckbox(os: 'mac' | 'win' | 'linux') {
  if (os === 'mac') {
    return new MacCheckbox();
  } // ... same switch again
}
```

**Problems:**

1. **Duplication** — every product has its own `if/else` on platform
2. **Inconsistency** — a Mac button could be paired with a Windows checkbox if you mix factories
3. **Hard to extend** — adding a new OS means editing every method
4. **Leaky abstraction** — the client knows about all concrete products

Abstract Factory fixes all four by giving the client **one factory object** that returns a coherent family of products.

## How It Works

The pattern works by:

1. **Declaring an abstract factory interface** with a creation method per product family
2. **Concrete factories** implement the interface, each producing a coherent family
3. **Abstract product interfaces** declare what each product does
4. **Concrete products** implement those interfaces
5. **The client** takes a factory in its constructor and uses it to create products — never `new` on concretes

```typescript
// Abstract products
interface Button {
  render(): string;
  onClick(): void;
}

interface Checkbox {
  render(): string;
  toggle(): void;
}

// Abstract factory
interface UIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

// Concrete products — Mac family
class MacButton implements Button {
  render() { return '[ Mac Button ]'; }
  onClick() { console.log('Mac click'); }
}

class MacCheckbox implements Checkbox {
  render() { return '[x] Mac Checkbox'; }
  toggle() { console.log('Mac toggle'); }
}

// Concrete products — Windows family
class WinButton implements Button {
  render() { return '< Win Button >'; }
  onClick() { console.log('Win click'); }
}

class WinCheckbox implements Checkbox {
  render() { return '[x] Win Checkbox'; }
  toggle() { console.log('Win toggle'); }
}

// Concrete factories
class MacFactory implements UIFactory {
  createButton() { return new MacButton(); }
  createCheckbox() { return new MacCheckbox(); }
}

class WinFactory implements UIFactory {
  createButton() { return new WinButton(); }
  createCheckbox() { return new WinCheckbox(); }
}

// Client code — takes a factory, doesn't know about concrete types
class Application {
  constructor(private factory: UIFactory) {}

  render() {
    const button = this.factory.createButton();
    const checkbox = this.factory.createCheckbox();
    return `${button.render()}\n${checkbox.render()}`;
  }
}

// Usage
const app = os === 'mac' ? new Application(new MacFactory())
                        : new Application(new WinFactory());
app.render();
```

## Real-World Examples

### 1. Cross-platform UI (the canonical example)

Qt, JavaFX, and React Native's `Platform` module all use Abstract Factory to provide platform-native widgets. `Platform.OS === 'ios' ? new IOSComponents() : new AndroidComponents()`.

### 2. Theme systems

A theme bundle returns matching colors, fonts, spacing, and components. You don't want a "dark mode button" with "light mode checkbox" — the theme factory enforces consistency.

```typescript
interface Theme {
  background: string;
  text: string;
  buttonColor: string;
}

interface ThemeFactory {
  createTheme(): Theme;
}

class LightThemeFactory implements ThemeFactory {
  createTheme() { return { background: '#fff', text: '#000', buttonColor: '#007bff' }; }
}

class DarkThemeFactory implements ThemeFactory {
  createTheme() { return { background: '#000', text: '#fff', buttonColor: '#0d6efd' }; }
}
```

### 3. Database drivers with matching connection + query + transaction

```typescript
interface DatabaseFactory {
  createConnection(): Connection;
  createQueryBuilder(): QueryBuilder;
  createMigrator(): Migrator;
}

class PostgresFactory implements DatabaseFactory { /* ... */ }
class MySQLFactory implements DatabaseFactory { /* ... */ }
```

### 4. Payment providers

Stripe, PayPal, Braintree each have a `PaymentProviderFactory` returning a `Customer`, `Charge`, `Refund` — but each implementation is consistent (Stripe customer + Stripe charge + Stripe refund).

### 5. Test fixtures

`TestDataFactory` returns matching User + Address + PaymentMethod — all stubbed. Production factories return real entities.

## When to Use

 **Use Abstract Factory when:**

- The system must be configured with one of several families of products
- A family of related product objects is designed to be used together (this is the key signal)
- You want to provide a class library of products and only reveal their interfaces
- The system should be independent of how its products are created, composed, and represented

 **Avoid Abstract Factory when:**

- You have a single product type (use Factory Method instead)
- The products don't have a "family" relationship (any button works with any checkbox)
- You have 1-2 product types (overhead > benefit)
- The family of products is unlikely to grow (adding a factory is real work)

## How It Works in Code

### Modern TypeScript with abstract classes

```typescript
abstract class UIFactory {
  abstract createButton(): Button;
  abstract createCheckbox(): Checkbox;

  // Optional: a helper that uses the products together
  renderForm(): string {
    const btn = this.createButton();
    const cb = this.createCheckbox();
    return `${cb.render()}\n${btn.render()}`;
  }
}

class MacFactory extends UIFactory {
  createButton() { return new MacButton(); }
  createCheckbox() { return new MacCheckbox(); }
}
```

### Combining with DI

In a NestJS app, you bind a factory implementation to a token, then inject the abstract factory:

```typescript
// tokens
export const UI_FACTORY = Symbol('UI_FACTORY');

// provider
{ provide: UI_FACTORY, useClass: process.env.PLATFORM === 'mac' ? MacFactory : WinFactory }

// consumer
constructor(@Inject(UI_FACTORY) private factory: UIFactory) {}
```

### Functional Abstract Factory (TypeScript)

If your "products" are simple data, a factory function is cleaner than classes:

```typescript
type ThemeName = 'light' | 'dark' | 'high-contrast';

const themeFactories: Record<ThemeName, () => Theme> = {
  light: () => ({ background: '#fff', text: '#000', buttonColor: '#007bff' }),
  dark: () => ({ background: '#000', text: '#fff', buttonColor: '#0d6efd' }),
  'high-contrast': () => ({ background: '#000', text: '#fff', buttonColor: '#ff0' }),
};

const theme = themeFactories[userPreference]();
```

## Comparisons

### Abstract Factory vs Factory Method

| Abstract Factory | Factory Method |  |
| -- | ------------------ | ---------------- |
| **Creates** | Family of related products | One product |
| **Number of methods** | Multiple (one per product type) | One (the factory method) |
| **Variation axis** | Which family | Which subtype of one product |
| **When to use** | Cross-platform, theme systems, OS bundles | Plugin system, multiple impls of one interface |

**Rule of thumb:** if you have 3+ factory methods that get used together, that's an Abstract Factory.

### Abstract Factory vs Builder

- **Abstract Factory** creates a family of products **immediately**, in one step each.
- **Builder** constructs a single complex object **step-by-step**.

If your "family" is a complex object with 5+ optional fields, prefer Builder.

### Abstract Factory vs Prototype

- **Abstract Factory** constructs new products from scratch (re-runs constructors).
- **Prototype** clones existing instances.

If construction is expensive, Prototype is faster.

## Code Example: Real-world Test Data Factory

```typescript
// Abstract products
interface User { id: string; name: string; email: string; }
interface Order { id: string; userId: string; total: number; items: OrderItem[]; }
interface Product { id: string; name: string; price: number; }

// Abstract factory
interface TestDataFactory {
  createUser(overrides?: Partial<User>): User;
  createOrder(overrides?: Partial<Order>): Order;
  createProduct(overrides?: Partial<Product>): Product;
}

// One implementation: minimal valid data
class MinimalFactory implements TestDataFactory {
  createUser(o: Partial<User> = {}) { return { id: 'u1', name: 'Test', email: 't@x.io', ...o }; }
  createOrder(o: Partial<Order> = {}) { return { id: 'o1', userId: 'u1', total: 0, items: [], ...o }; }
  createProduct(o: Partial<Product> = {}) { return { id: 'p1', name: 'Item', price: 0, ...o }; }
}

// Another: realistic data with relations
class RealisticFactory implements TestDataFactory {
  createUser(o: Partial<User> = {}) { /* ... */ }
  createOrder(o: Partial<Order> = {}) { /* links to a real user */ }
  createProduct(o: Partial<Product> = {}) { /* ... */ }
}

// Test
function testCheckout(factory: TestDataFactory) {
  const user = factory.createUser();
  const product = factory.createProduct({ price: 100 });
  const order = factory.createOrder({ userId: user.id, items: [{ productId: product.id, qty: 1 }], total: 100 });
  // ... test code
}

// Choose family based on test
testCheckout(new MinimalFactory()); // unit tests
testCheckout(new RealisticFactory()); // integration tests
```

## Common Pitfalls

### 1. **Adding a new product type is expensive**

Adding `createScrollbar()` to `UIFactory` means editing every concrete factory. This is the "open-closed principle" cost of Abstract Factory.

**Mitigation:** Make sure the family is stable before introducing the pattern.

### 2. **Mixing products from different factories**

If a client can call `macFactory.createButton()` and `winFactory.createCheckbox()`, you lose the family guarantee. Keep the factory injected as a unit, or use module-private constructors.

### 3. **Confusing with Dependency Injection**

DI is how you **deliver** the right factory to the right place. Abstract Factory is what the factory **does**. They compose: use DI to inject the Abstract Factory.

### 4. **Over-engineering for 2 products**

If you only have a button and a checkbox, and they're trivial, a single Factory Method is enough. Abstract Factory is for families of 3+.

## Best Practices

1. **One concrete factory per family** — never mix products from different factories.
2. **Inject the factory, don't `new` it** — use DI to provide the right implementation.
3. **Abstract products as interfaces** — TypeScript/JS doesn't have abstract classes enforced; use interfaces or `abstract` classes.
4. **Keep families stable** — adding a product means editing all factories. Don't use this if the family changes often.
5. **Combine with other patterns** — Abstract Factory often uses Factory Method internally; combine with DI for the cleanest setup.

## Summary

Abstract Factory is a **family-level creational pattern**. Use it when you need to ensure that a set of related products is used together, and you want to swap families at runtime or by configuration. It's heavyweight — only reach for it when the family is real (3+ products that must be used together) and stable.

**Interview-ready one-liner:** "Abstract Factory provides an interface for creating families of related objects without specifying their concrete classes — you swap the whole family by swapping the factory."

# Abstract Factory Pattern


## Definition

An **Abstract Factory** gives a client one creation contract for a related family of products. Selecting a Mac factory supplies Mac buttons and checkboxes together; selecting a Windows factory supplies the other family without making the client choose each concrete class.

> **Textbook Definition:** Abstract Factory is a creational pattern that exposes operations for constructing a compatible family of products through abstract interfaces without coupling clients to concrete product classes.

The pattern is particularly useful when:

- The system needs to be independent of how its products are created
- The system should be configured with one of multiple families of products
- A family of related product objects is designed to be used together
- You want to provide a class library of products, and you want to reveal just their interfaces, not their implementations

## First Principles

A client can choose a button implementation and checkbox implementation independently, but the requirement may say they must follow one selected platform contract. Independent decisions then repeat the same knowledge and can disagree.

Select the family once and expose a creation operation for each product kind. The client still uses the individual product contracts, while the chosen factory owns consistent construction. This protects the family-selection axis: adding a family adds its products, factory, and application selection. Adding a new product kind changes the shared contract and every existing family implementation.

```text
setup selects MacFactory
          │
          ▼
client uses UIFactory ──createButton──→ MacButton as Button
                     └─createCheckbox→ MacCheckbox as Checkbox
```

The interface does not itself prove family compatibility. A faulty `MacFactory` could return a Windows product through the same structural types. Factory implementation, restricted construction paths, and compatibility tests establish the promise.

## Why Do We Need It?

Without Abstract Factory, code that needs to vary its UI components by platform becomes:

```typescript
// BAD: tight coupling, scattered platform checks
function renderButton(os: 'mac' | 'win' | 'linux') {
  if (os === 'mac') {
    return new MacButton();
  } else if (os === 'win') {
    return new WinButton();
  } else {
    return new LinuxButton();
  }
}

function renderCheckbox(os: 'mac' | 'win' | 'linux') {
  if (os === 'mac') {
    return new MacCheckbox();
  } // ... same switch again
}
```

**Problems:**

1. **Duplication** — every product has its own `if/else` on platform
2. **Inconsistency** — a Mac button could be paired with a Windows checkbox if you mix factories
3. **Hard to extend** — adding a new OS means editing every method
4. **Leaky abstraction** — the client knows about all concrete products

Supplying one coherent factory removes the repeated selection from this client. It reduces inconsistent choices when the client obtains its products from that factory; it does not prevent other code from mixing independently created products.

## How It Works

The pattern works by:

1. **Declaring an abstract factory interface** with a creation method per product kind
2. **Concrete factories** implement the interface, each producing a coherent family
3. **Abstract product interfaces** declare what each product does
4. **Concrete products** implement those interfaces
5. **The client** takes a factory in its constructor and uses it to create products — never `new` on concretes

```typescript
// Abstract products
interface Button {
  render(): string;
  onClick(): void;
}

interface Checkbox {
  render(): string;
  toggle(): void;
}

// Abstract factory
interface UIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

// Concrete products — Mac family
class MacButton implements Button {
  render() { return '[ Mac Button ]'; }
  onClick() { console.log('Mac click'); }
}

class MacCheckbox implements Checkbox {
  render() { return '[x] Mac Checkbox'; }
  toggle() { console.log('Mac toggle'); }
}

// Concrete products — Windows family
class WinButton implements Button {
  render() { return '< Win Button >'; }
  onClick() { console.log('Win click'); }
}

class WinCheckbox implements Checkbox {
  render() { return '[x] Win Checkbox'; }
  toggle() { console.log('Win toggle'); }
}

// Concrete factories
class MacFactory implements UIFactory {
  createButton() { return new MacButton(); }
  createCheckbox() { return new MacCheckbox(); }
}

class WinFactory implements UIFactory {
  createButton() { return new WinButton(); }
  createCheckbox() { return new WinCheckbox(); }
}

// Client code — takes a factory, doesn't know about concrete types
class Application {
  constructor(private factory: UIFactory) {}

  render() {
    const button = this.factory.createButton();
    const checkbox = this.factory.createCheckbox();
    return `${button.render()}\n${checkbox.render()}`;
  }
}

// Usage: application setup supplies the platform, not the client.
const os: 'mac' | 'win' = 'mac';
const app = os === 'mac' ? new Application(new MacFactory())
                        : new Application(new WinFactory());
console.log(app.render()); // [ Mac Button ] followed by [x] Mac Checkbox
```

`Application.render` asks its selected factory for two products and calls each product's `render`. Switching setup to `WinFactory` changes both products without editing that client method. These strings demonstrate selection; they do not create native widgets or manage click/checked state.

## Real-World Examples

### 1. Cross-platform UI (the canonical example)

A UI toolkit can expose a factory that creates matching platform widgets. This is a design example; a Platform selector alone does not demonstrate that a framework implements the GoF pattern.

### 2. Theme systems

A family factory can create matching themed components. The following smaller example instead creates one `Theme` data object. It is a single-product factory alternative, not by itself a demonstration of GoF Abstract Factory. Mixing visual themes is an application choice, whereas protocol-incompatible provider objects may be a correctness failure.

```typescript
interface Theme {
  background: string;
  text: string;
  buttonColor: string;
}

interface ThemeFactory {
  createTheme(): Theme;
}

class LightThemeFactory implements ThemeFactory {
  createTheme() { return { background: '#fff', text: '#000', buttonColor: '#007bff' }; }
}

class DarkThemeFactory implements ThemeFactory {
  createTheme() { return { background: '#000', text: '#fff', buttonColor: '#0d6efd' }; }
}
```

### 3. Database capabilities selected together

This is a structural sketch: connection, query builder, migrator, and their implementations are omitted. Specify which dialect and resource lifetime must agree; returning three interfaces alone does not make them compatible.

```typescript
interface DatabaseFactory {
  createConnection(): Connection;
  createQueryBuilder(): QueryBuilder;
  createMigrator(): Migrator;
}

class PostgresFactory implements DatabaseFactory { /* ... */ }
class MySQLFactory implements DatabaseFactory { /* ... */ }
```

### 4. Payment providers

An application can define a provider family containing customer lookup, charging, and refund operations. Its factory must ensure those operations share the intended provider/account context. A matching identifier cannot generally be passed to another provider. This is an application design example, not a claim that each payment SDK implements this GoF pattern.

### 5. Test fixtures

`TestDataFactory` returns matching User + Address + PaymentMethod — all stubbed. Production factories return real entities.

## When to Use

 **Use Abstract Factory when:**

- The system must be configured with one of several families of products
- A family of related product objects is designed to be used together (this is the key signal)
- You want to provide a class library of products and only reveal their interfaces
- The system should be independent of how its products are created, composed, and represented

 **Avoid Abstract Factory when:**

- You have a single product type and direct construction, a function, or a simple factory already expresses the variation
- The products don't have a "family" relationship (any button works with any checkbox)
- A simple options object or direct constructor already expresses the required variation
- The family of products is unlikely to grow (adding a factory is real work)

## How It Works in Code

### An alternative abstract-class declaration

This excerpt replaces the earlier `UIFactory` declaration; do not append both declarations and duplicate `MacFactory` classes into one source file.

```typescript
abstract class UIFactory {
  abstract createButton(): Button;
  abstract createCheckbox(): Checkbox;

  // Optional: a helper that uses the products together
  renderForm(): string {
    const btn = this.createButton();
    const cb = this.createCheckbox();
    return `${cb.render()}\n${btn.render()}`;
  }
}

class MacFactory extends UIFactory {
  createButton() { return new MacButton(); }
  createCheckbox() { return new MacCheckbox(); }
}
```

### Combining with DI

In a NestJS app, you bind a factory implementation to a token, then inject the abstract factory:

```typescript
// tokens
export const UI_FACTORY = Symbol('UI_FACTORY');

// provider fragment inside a Nest module providers array
{ provide: UI_FACTORY, useClass: process.env.PLATFORM === 'mac' ? MacFactory : WinFactory }

// consumer
constructor(@Inject(UI_FACTORY) private factory: UIFactory) {}
```

### A functional alternative for one configuration value

If your "products" are simple data, a factory function is cleaner than classes:

```typescript
type ThemeName = 'light' | 'dark' | 'high-contrast';

const themeFactories: Record<ThemeName, () => Theme> = {
  light: () => ({ background: '#fff', text: '#000', buttonColor: '#007bff' }),
  dark: () => ({ background: '#000', text: '#fff', buttonColor: '#0d6efd' }),
  'high-contrast': () => ({ background: '#000', text: '#fff', buttonColor: '#ff0' }),
};

const userPreference: ThemeName = 'dark';
const theme = themeFactories[userPreference]();
```

## Comparisons

### Abstract Factory vs Factory Method

| Property | Abstract Factory | Factory Method |
| -- | ------------------ | ---------------- |
| **Creates** | Family of related products | One product |
| **Number of methods** | Multiple (one per product type) | One (the factory method) |
| **Variation axis** | Which family | Which subtype of one product |
| **When to use** | Cross-platform, theme systems, OS bundles | Plugin system, multiple impls of one interface |

**Signal:** related products are selected as a coherent family. There is no minimum of three product types.

### Abstract Factory vs Builder

- **Abstract Factory** creates a family of products **immediately**, in one step each.
- **Builder** constructs a single complex object **step-by-step**.

If the variation is how to assemble one object, examine Builder or a named options object. Field count alone does not turn a family requirement into an assembly requirement.

### Abstract Factory vs Prototype

- **Abstract Factory** exposes family creation operations; those operations may use constructors, cached values, or prototype copies.
- **Prototype** clones existing instances.

Cloning may avoid some construction work, but deep copies, validation and resource identity can cost more; measure the actual representation.

## Test fixtures need explicit relationship wiring

A fixture helper can create several record kinds without being a compatible-family abstraction. In this independent example, the caller connects records explicitly; the helper supplies defaults, not database persistence or integration-test setup:

```typescript
interface FixtureUser { id: string; email: string }
interface FixtureProduct { id: string; price: number }
interface FixtureItem { productId: string; qty: number }
interface FixtureOrder { userId: string; items: FixtureItem[]; total: number }

class FixtureFactory {
  createUser(overrides: Partial<FixtureUser> = {}): FixtureUser {
    return { id: 'u1', email: 'demo@example.test', ...overrides };
  }
  createProduct(overrides: Partial<FixtureProduct> = {}): FixtureProduct {
    return { id: 'p1', price: 0, ...overrides };
  }
  createOrder(overrides: Partial<FixtureOrder> = {}): FixtureOrder {
    return { userId: 'u1', items: [], total: 0, ...overrides };
  }
}

const fixtures = new FixtureFactory();
const user = fixtures.createUser({ id: 'u2' });
const product = fixtures.createProduct({ price: 100 });
const order = fixtures.createOrder({
  userId: user.id, items: [{ productId: product.id, qty: 1 }], total: 100
});
console.log(order.userId, order.items[0].productId, order.total); // u2 p1 100
```

Default identifiers can collide across records or tests. If a coherent fixture graph is required, make its owner allocate identifiers and link records under one contract. Do not assume optional override arguments preserve valid totals and relations automatically.

## Common Pitfalls

### 1. **Adding a new product type is expensive**

Adding `createScrollbar()` to `UIFactory` means editing every concrete factory. This is the "open-closed principle" cost of Abstract Factory.

**Mitigation:** Make sure the family is stable before introducing the pattern.

### 2. **Mixing products from different factories**

If a client can call `macFactory.createButton()` and `winFactory.createCheckbox()`, you lose the family guarantee. Keep the factory injected as a unit, or use module-private constructors.

### 3. **Confusing with Dependency Injection**

DI is how you **deliver** the right factory to the right place. Abstract Factory is what the factory **does**. They compose: use DI to inject the Abstract Factory.

### 4. **Over-engineering for 2 products**

Even two product kinds can form a meaningful family. If there is no compatibility requirement, direct constructors or an options object may suffice. Factory Method is a different variation mechanism, not a smaller family factory.

## Best Practices

1. **One concrete factory per family** — never mix products from different factories.
2. **Inject the factory, don't `new` it** — use DI to provide the right implementation.
3. **Separate checking from runtime enforcement** — TypeScript checks interfaces and abstract declarations, then erases type-only constraints. Their presence does not validate arbitrary JavaScript or external input.
4. **Keep families stable** — adding a product means editing all factories. Don't use this if the family changes often.
5. **Combine with other patterns** — Abstract Factory often uses Factory Method internally; combine with DI for the cleanest setup.

## Summary

Abstract Factory is a **family-level creational pattern**. Use it when you need to ensure that a set of related products is used together, and you want to swap families at runtime or by configuration. It's heavyweight — use it when the family is real and stable enough to justify the creation boundary.

**Interview-ready one-liner:** "Abstract Factory provides an interface for creating families of related objects without specifying their concrete classes — you swap the whole family by swapping the factory."

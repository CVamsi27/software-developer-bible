# Abstract Factory Pattern

A UI must render platform-matched controls. Choosing a Mac button with a Windows checkbox satisfies each product interface yet breaks that requirement:

```typescript
const factory: UIFactory = platform === 'mac' ? new MacFactory() : new WindowsFactory();
const app = new Application(factory); // family chosen once
```

## Definition

In practice, an **Abstract Factory** gives a client one interface with a creation operation for each related **product kind**. Selecting a concrete factory selects the **family**; the client works through product interfaces without choosing each concrete class.

> **Textbook Definition:** Abstract Factory is a creational pattern that provides an interface for creating families of related or dependent objects without specifying their concrete classes.

Two product kinds form a meaningful family when they share a compatibility requirement or must vary together. The method count never defines the pattern.

## First Principles

If every client independently chooses each concrete product, platform or provider rules spread across the application. One factory selection centralizes that variation:

```text
setup selects MacFactory
          │
          ▼
client uses UIFactory ──createButton──→ MacButton as Button
                     └─createCheckbox→ MacCheckbox as Checkbox
```

The factory interface describes the required product kinds, but it never proves one implementation returns a compatible family — a `MacFactory` could return a Windows checkbox and still satisfy the structural TypeScript interface. Keep concrete construction behind the factory and test that each factory returns the intended family.

## 1. Select the family once, use product interfaces

```typescript
interface Button {
  render(): string;
}

interface Checkbox {
  render(): string;
}

interface UIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

class MacFactory implements UIFactory {
  createButton(): Button { return { render: () => '[Mac button]' }; }
  createCheckbox(): Checkbox { return { render: () => '[Mac checkbox]' }; }
}

class WindowsFactory implements UIFactory {
  createButton(): Button { return { render: () => '[Windows button]' }; }
  createCheckbox(): Checkbox { return { render: () => '[Windows checkbox]' }; }
}

class Application {
  constructor(private factory: UIFactory) {}

  render(): string {
    const button = this.factory.createButton();
    const checkbox = this.factory.createCheckbox();
    return `${button.render()}\n${checkbox.render()}`;
  }
}

// Setup selects the family once; the application uses only product interfaces.
const platform: 'mac' | 'windows' = 'mac';
const factory: UIFactory = platform === 'mac' ? new MacFactory() : new WindowsFactory();
console.log(new Application(factory).render());
```

`Application.render()` asks the same selected factory for both products. Changing setup changes the family without changing the client workflow. The example renders labels; it creates no native widgets and implements no checked state.

## 2. Recognize where a family contract matters

- **Database dialect:** A connection, query builder, and migrator may need to agree on one SQL dialect and resource lifetime. Similar class names alone never make them a family.
- **Payment provider:** Customer lookup, charge, and refund operations may need to share one provider and merchant account. A provider-specific identifier must never cross into another provider's client.
- **Platform UI or theme:** Components may need matching platform behavior or design tokens. A factory returning only one `Theme` object is a single-product factory; it becomes an Abstract Factory when supplying multiple related component kinds.
- **Test fixtures:** A helper creating unrelated records is only a fixture factory. It acts as a family boundary when it must create a linked graph whose identifiers and totals satisfy shared invariants.

## 3. Choose the creation boundary from the variation

| Need | Suitable mechanism |
| -------------------------------------------------------------- | --------------------------------------------------------- |
| Choose one product from configuration | Direct function, simple factory, or registry |
| Let a subclass supply one product to a stable creator workflow | [Factory Method](30.1.2.02-factory-method.md) |
| Assemble one product through ordered steps | [Builder](30.1.2.03-builder.md) or a named options object |
| Select several related products that must remain compatible | Abstract Factory |

The pattern favors adding families over adding product kinds: a new family adds a factory and its products while clients keep the same contract, but a new product kind changes the factory interface and every concrete factory. A coherent two-product family can justify that cost; unrelated constructors cannot.

Dependency injection can select and deliver the factory at the composition root, but DI never establishes product compatibility by itself. TypeScript checks declared interfaces and erases type-only constraints, so runtime inputs and each concrete family's behavior still need validation and tests.

## 4. Compare the related patterns

- **Factory Method** varies one product through an overridable creation operation used by a creator workflow. Abstract Factory exposes operations for a family; it may use Factory Methods internally.
- **Builder** controls the steps and validation boundary for one product. An Abstract Factory operation may delegate construction to a builder.
- **Prototype** creates by copying an existing instance. An Abstract Factory chooses the family and may use prototypes internally.

## Summary

Abstract Factory gives a client one family selection and one creation operation per related product kind. Use it when compatibility across those products is a real invariant. Adding a family is straightforward; adding a product kind changes every factory, and the implementations and tests must enforce the family promise.

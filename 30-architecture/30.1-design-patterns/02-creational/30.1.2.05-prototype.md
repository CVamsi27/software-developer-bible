# Prototype Pattern


## Definition

The Prototype pattern is a creational design pattern that lets you copy existing objects without making your code dependent on their classes. It's one of the 23 GoF patterns.

The pattern is useful when:

- Object creation is expensive (database calls, network requests, complex calculations)
- You need many similar objects that differ only in a few fields
- Classes to instantiate are specified at runtime (e.g., dynamic loading)
- You want to avoid building a parallel class hierarchy of factories

```text
┌────────────────────────────┐ ┌─────────────────────────┐
│ Client │ │ Prototype (interface)              │
│ - operation() │ │ + clone(): Prototype        │
│ - prototype: Prototype                        │ └─────────────────────────┘
└────────────────────────────┘ ▲
        │ │
        │ calls clone() │ implements
        ▼ │
┌───────────────────────────────────────────────┐ ┌─────────────────────────┐
│ ConcretePrototypeA │ │ ConcretePrototypeB     │
│ - field1 │ │ - field3                         │
│ + clone(): Prototype │ │ + clone(): Prototype │
└───────────────────────────────────────────────┘ └─────────────────────────┘
```

## First Principles

Prototype creates by copying instead of constructing:

1. **When construction is expensive or configuration-heavy, cloning may reuse configured state; its cost and validity still depend on the copy contract** — the copy carries proven settings without re-specifying them.
2. **Deep vs shallow is the entire correctness question** (→ 10.1.4.03): shared children are the speed win and the aliasing bug in one decision.
3. **JavaScript's prototype delegation is related vocabulary, not object copying** (→ 10.1.2.02): `Object.create(proto)` makes a new object delegate lookup to proto; it does not copy that object's state. Distinguish this language feature from the GoF cloning pattern.

## Why Do We Need It?

Three scenarios where Prototype beats `new`:

### 1. Construction is expensive

```typescript
// BAD: every config instance triggers a DB roundtrip
class Config {
  constructor() {
    this.data = db.query('SELECT * FROM config'); // 50ms per instance
  }
}
const c1 = new Config();
const c2 = new Config();
const c3 = new Config(); // 150ms total
```

```typescript
// GOOD: clone the cached prototype
class Config implements Cloneable {
  private static cached: Config | null = null;

  static getInstance(): Config {
    if (!this.cached) {
      this.cached = new Config(); // 50ms once
    }
    return this.cached.clone();
  }

  clone(): Config {
    const copy = Object.create(this);
    // optionally deep-copy mutable fields
    return copy;
  }
}
```

### 2. Many similar objects

A game spawning 1000 enemies that all share base stats — clone a prototype and tweak a few fields per enemy instead of running the constructor 1000 times.

### 3. Runtime-determined classes

If the class to instantiate is decided at runtime (loaded from config, user input, plugin system), and you can't have a Factory Method for every possible class, Prototype lets you say "clone this one I have."

## How It Works

1. **Declare a prototype interface** with a `clone()` method.
2. **Each concrete class** implements `clone()` by creating a copy of itself.
3. **The client** holds a prototype instance and calls `clone()` instead of `new`.

```typescript
interface Prototype<T> {
  clone(): T;
}

// Concrete prototype
class Enemy implements Prototype<Enemy> {
  constructor(
    public name: string,
    public health: number,
    public damage: number,
    public position: { x: number; y: number },
    public inventory: string[]
  ) {}

  clone(): Enemy {
    // Shallow copy: new Enemy object, but position/inventory are shared
    return new Enemy(this.name, this.health, this.damage, this.position, this.inventory);
  }

  deepClone(): Enemy {
    // Deep copy: also clone nested objects
    return new Enemy(
      this.name,
      this.health,
      this.damage,
      { ...this.position },
      [...this.inventory]
    );
  }
}

// Usage
const baseEnemy = new Enemy('Goblin', 100, 10, { x: 0, y: 0 }, ['sword']);

const enemy1 = baseEnemy.deepClone();
enemy1.position = { x: 5, y: 5 };
enemy1.health = 80;

const enemy2 = baseEnemy.deepClone();
enemy2.position = { x: 10, y: 0 };
enemy2.inventory = ['bow', 'arrows'];
```

## Shallow vs Deep Clone

This is the most important detail in Prototype. A shallow clone copies the top-level fields but shares references to nested objects:

```typescript
const original = { name: 'x', nested: { count: 1 } };
const shallow = { ...original };
shallow.nested.count = 99;
console.log(original.nested.count); // 99 — the original was mutated!
```

A deep clone copies the supported nested graph according to the chosen algorithm; functions, resources and custom prototypes need explicit handling:

```typescript
const original = { name: 'x', nested: { count: 1 } };
const deep = structuredClone(original); // or JSON.parse(JSON.stringify(x)) for simple data
deep.nested.count = 99;
console.log(original.nested.count); // 1 — original is untouched
```

**Rule:** if your prototype contains mutable nested objects (arrays, objects, Maps, Dates), you almost always want deep clone. Otherwise cloning a "copy" with shared nested state is a bug waiting to happen.

### Modern JS clone options

```typescript
// 1. structuredClone — built-in, handles most types, no functions
const copy = structuredClone(original);

// 2. JSON — works for plain data only (loses Dates, Maps, Sets, undefined, functions, symbols)
const copy = JSON.parse(JSON.stringify(original));

// 3. Spread (shallow only)
const copy = { ...original };

// 4. Manual deep clone for custom classes
class Foo {
  constructor(public data: any) {}
  clone() { return new Foo(structuredClone(this.data)); }
}
```

## Real-World Examples

### 1. `structuredClone()` in browsers/Node

The native structuredClone global supplies a data-copying mechanism. It does not preserve arbitrary class prototypes, private fields or methods, so a custom clone contract may still be needed.

### 2. React component patterns

A "skeleton" component with default props, cloned and overridden per use:

```typescript
const BaseButton = { variant: 'primary', size: 'md', disabled: false };
const SubmitButton = { ...BaseButton, type: 'submit' };
const CancelButton = { ...BaseButton, variant: 'secondary' };
```

### 3. Document templates

Clone a "Invoice" template (with logo, footer, formatting) and fill in `customerName`, `items`, `total`. The formatting and structure come "for free" from the prototype.

### 4. Game enemy/object spawning

The Quake-style game engines clone a base "monster" object and tweak position/AI state for each spawn.

### 5. Redux default state

```typescript
const initialState = { user: null, cart: [], loading: false };
// In a reducer:
const newState = { ...state, cart: [...state.cart, newItem] };
// Effectively a prototype clone with one field overridden.
```

### 6. Test fixtures

A "valid user" fixture is the prototype. Each test clones it and overrides the field under test. This is faster than re-constructing and ensures every test starts from the same baseline.

## When to Use

 **Use Prototype when:**

- Object creation is expensive (DB, network, heavy computation)
- You need many similar objects that differ in a few fields
- The class to instantiate is determined at runtime (e.g., loaded from a config file)
- You want to avoid subclassing a Factory Method for every product variation
- You have a base "template" and many derivative instances

 **Avoid Prototype when:**

- Construction is cheap (just call `new`)
- Objects are simple value objects (no nested mutable state)
- You only need a handful of instances
- The class hierarchy is flat and stable (Factory Method is clearer)

## How It Works in Code

### Using a Prototype Registry

A common variant: a registry of named prototypes, with `clone(name)` returning a copy.

```typescript
class Shape {
  constructor(public x: number, public y: number, public color: string) {}
  clone(): Shape { return new Shape(this.x, this.y, this.color); }
}

class ShapeRegistry {
  private shapes: Map<string, Shape> = new Map();

  register(name: string, prototype: Shape) {
    this.shapes.set(name, prototype);
  }

  create(name: string): Shape {
    const proto = this.shapes.get(name);
    if (!proto) throw new Error(`No prototype '${name}'`);
    return proto.clone();
  }
}

// Usage
const registry = new ShapeRegistry();
registry.register('red-circle', new Shape(0, 0, 'red'));
registry.register('blue-square', new Shape(0, 0, 'blue'));

const c1 = registry.create('red-circle');
c1.x = 10; c1.y = 20;
```

This is sometimes called the "Prototype Registry" or "Prototype Manager" pattern.

### Prototype with TypeScript generics

```typescript
interface Cloneable<T> {
  clone(): T;
}

abstract class BaseEntity implements Cloneable<this> {
  id: string = crypto.randomUUID();
  createdAt: Date = new Date();

  abstract clone(): this;
}

class User extends BaseEntity {
  constructor(public name: string, public email: string) { super(); }
  clone(): User { return new User(this.name, this.email); }
}
```

## Comparisons

### Prototype vs Factory Method

| Property | Prototype | Factory Method |
| -- | ----------- | ---------------- |
| **Creates** | A copy of an existing object | A new object from a class |
| **Construction path** | Chosen by clone(); it may call a constructor | Chosen by the creation method |
| **Cost** | Copying, validation and identity handling | Construction and initialization |
| **Flexibility** | Clone any prototype you have | Must know the class to instantiate |
| **Use when** | Construction is expensive | Construction is cheap, class is variable |

### Prototype vs Abstract Factory

- **Prototype** clones existing instances.
- **Abstract Factory** creates new instances from classes.

Use Prototype when the family of objects is realized as a set of pre-built prototypes. Use Abstract Factory when the family is created on demand from class definitions.

### Prototype vs Builder

- **Prototype** copies and tweaks.
- **Builder** constructs step-by-step.

If you find yourself with a long Builder chain that always starts the same way, consider a Prototype (set up the "base" as a prototype, then clone + override).

### Prototype vs Memento

- **Prototype** creates a **new object** that's a copy. Both old and new are independently usable.
- **Memento** stores the **state snapshot** of an object so the object can be restored. The memento is read-only; the original object continues to exist and mutate.

Use Prototype for "give me a similar one". Use Memento for "remember this so I can go back".

## Code Example: Cloning a Configuration

```typescript
interface AppConfig {
  db: { host: string; port: number; pool: number };
  features: Record<string, boolean>;
  cache: { ttl: number; type: 'memory' | 'redis' };
}

class ConfigPrototype implements Cloneable<ConfigPrototype> {
  constructor(public config: AppConfig) {}

  clone(): ConfigPrototype {
    return new ConfigPrototype(structuredClone(this.config));
  }

  withOverrides(overrides: Partial<AppConfig>): ConfigPrototype {
    return new ConfigPrototype({ ...this.config, ...overrides });
  }
}

// Setup — build the base config once
const baseConfig = new ConfigPrototype({
  db: { host: 'localhost', port: 5432, pool: 10 },
  features: { newDashboard: false, darkMode: true },
  cache: { ttl: 300, type: 'memory' },
});

// Per-environment — clone + override
const stagingConfig = baseConfig.withOverrides({
  db: { host: 'localhost', port: 5432, pool: 10 },
  features: { newDashboard: true },
});

const devConfig = baseConfig.withOverrides({
  cache: { ttl: 0, type: 'memory' }, // disable cache
});
```

## Common Pitfalls

### 1. **Shallow clone leaks shared state**

Forgetting to deep-clone nested objects means "clones" share the nested state. Two clones that share an `inventory` array will see each other's mutations.

**Fix:** define which fields are independently owned and which are intentionally shared. Copy or freeze as that contract requires; structuredClone only handles supported values.

### 2. **Clone of "dead" prototypes**

A retained registry reference keeps an object reachable even after the binding that first created it leaves scope. Reject missing registry names and define the owner's retention policy; scope exit alone does not invalidate a live prototype.

### 3. **Confusing clone with copy-constructor**

A copy-constructor takes the same class as argument; Prototype uses an interface so any prototype works. Stick to the interface to maintain polymorphism.

### 4. **Cycle references break naive deep clone**

```typescript
const a = { name: 'a' };
const b = { name: 'b', ref: a };
a.ref = b; // cycle
// JSON.parse(JSON.stringify(a)) throws or produces broken output
// structuredClone(a) handles cycles
```

### 5. **Over-using Prototype for trivial objects**

For a `User { name, email }` data class, `new User(name, email)` is clearer than `prototype.clone().withName(name)`.

## Best Practices

1. **Prefer `structuredClone()`** for deep clones in modern JS/TS — handles cycles, Maps, Sets, Dates.
2. **Document shallow vs deep** — if your `clone()` is shallow, say so in the method name (`shallowClone()`).
3. **Combine with a registry** for "give me a clone of X" semantics.
4. **Use in tests** for independent fixture state; measure cost rather than assuming copying is faster.
5. **Avoid Prototype when `new` is cheap and clear.** It's a tool for when the construction cost is real.

## Summary

Prototype is a **cloning-based** creational pattern. Use it when construction is expensive or when you need many similar objects. The core challenges are getting the shallow/deep clone semantics right and managing the prototype registry properly.

**Interview-ready one-liner:** "Prototype creates new objects through the instance's clone contract rather than choosing its concrete construction at the call site — useful when construction is expensive or when you have many similar objects."

# Prototype Pattern

A worker needs a region-specific request configuration. The shared defaults are already validated, but rebuilding them in every worker repeats setup and risks inconsistent values. A prototype gives each worker a configured starting point plus a deliberate way to make an independent variant:

```typescript
const euWorker = template.clone(); // independent variant
euWorker.headers['x-region'] = 'eu'; // template untouched
```

## Definition

**In practice:** Prototype creates a new object from a configured instance through a **copy operation**, so callers can request a similar object without choosing its concrete constructor.

> **Textbook Definition:** "Specify the kinds of objects to create using a prototypical instance, and create new objects by copying this prototype."

The copy operation is part of the design: it must say which mutable values are copied, which are shared, and whether identity is retained or regenerated.

## First Principles

Direct construction starts with a class and its initialization data. When the concrete type or a valid configuration is already known at runtime, making every caller repeat that choice and setup spreads creation rules across the system. Supplying a configured instance moves that choice to the prototype: callers ask it for a sibling through a clone contract.

That saves duplicated selection or setup only when the template holds work worth reusing. It also moves responsibility to the copy boundary, which must distinguish owned state from shared resources and decide what a new object's identity means.

## 1. Clone a configured template

Each worker below receives its own settings objects, then changes its region header without affecting the template or another worker:

```typescript
interface Prototype<T> {
  clone(): T;
}

type RetryPolicy = { maxAttempts: number; delayMs: number };

class RequestConfig implements Prototype<RequestConfig> {
  constructor(
    public endpoint: string,
    public retry: RetryPolicy,
    public headers: Record<string, string>,
  ) {}

  clone(): RequestConfig {
    return new RequestConfig(
      this.endpoint,
      { ...this.retry },
      { ...this.headers },
    );
  }
}

const template = new RequestConfig(
  'https://api.example.test',
  { maxAttempts: 3, delayMs: 200 },
  { accept: 'application/json' },
);

// A caller that knows only the clone contract need not name a concrete class.
const prototype: Prototype<RequestConfig> = template;
const euWorker = prototype.clone();
euWorker.endpoint = 'https://eu.api.example.test';
euWorker.headers['x-region'] = 'eu';

console.log(template.endpoint, template.headers['x-region']); // base URL, undefined
console.log(euWorker.endpoint, euWorker.headers['x-region']); // EU URL, eu
console.log(euWorker.retry === template.retry); // false

if (
  template.endpoint !== 'https://api.example.test' ||
  template.headers['x-region'] !== undefined ||
  euWorker.retry === template.retry ||
  euWorker.headers === template.headers
) {
  throw new Error('clone did not preserve the copy contract');
}
```

This implementation copies the two mutable nested objects and passes through the endpoint's string value — enough for these fields. A nested array, object, or resource would need its own ownership rule. `clone()` calls `new RequestConfig`: the pattern hides the construction choice from the caller, not from the clone implementation. TypeScript checks the `Prototype<T>` call contract but cannot prove an implementation copies the right references or regenerates identity; values from a runtime registry also need runtime validation.

## 2. Decide what each field's copy means

A shallow copy creates a new outer object but keeps references to nested objects. A deep copy recursively duplicates a supported object graph. Neither phrase defines correct domain behavior alone: a clone may need independent mutable data, shared immutable values, a new identifier, or a deliberately shared service.

| State in the source | Typical clone decision |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Per-instance mutable data, such as headers or retry settings | Copy it when the new instance must change independently. |
| Immutable lookup data | Share it when sharing is safe and documented. |
| Resource handles, such as sockets or file descriptors | Reopen, inject, or deliberately share them; do not blindly duplicate them. |
| Entity identity, version, or creation time | Regenerate for a new entity; preserve only when the operation means "snapshot this same entity." |

For a runtime-selected family of variants, a registry can map a name to a prototype and call its `clone()` operation. The registry is optional — validate registrations, define its lifetime, and prevent callers from mutating the stored templates.

## 3. Respect JavaScript's copy boundaries

`structuredClone(value)` copies supported data graphs, including cycles and values such as `Map` and `Set`. It throws on non-structured-cloneable values, does not preserve arbitrary custom class prototypes, methods, or private fields, and cannot re-run class invariants or choose new domain identity. Its transfer option moves transferable resources and detaches them from the original — an ownership transfer, not an independent copy.

`Object.create(template)` is different: it creates an object whose property lookup delegates to `template`. It copies no properties and runs no class constructor. That JavaScript prototype-chain mechanism is not, by itself, the GoF Prototype pattern.

## 4. Choose the creation owner from the need

| Need | Clear starting point |
| ---------------------------------------------------------------------------- | ------------------------------ |
| The type and values are known and construction is simple | Call the constructor directly. |
| A subclass selects a product for a base workflow | Factory Method. |
| Several related product kinds must vary as one compatible family | Abstract Factory. |
| Construction has meaningful stages or a reusable recipe | Builder. |
| A configured instance is selected at runtime and its copy policy is explicit | Prototype. |

Use Prototype when repeated setup is real, a runtime-selected template is useful, or callers need independent variants of an existing configuration. Measure before claiming a performance win: cloning plus validation may cost as much as direct construction. Prefer a constructor or builder when it explains required invariants more clearly. Refresh or recreate templates when configuration, credentials, or other time-sensitive state changes.

## Summary

Treat the template as a creation boundary with a testable copy contract. Before relying on it, audit which fields are copied, shared, or regenerated and how the template stays current.

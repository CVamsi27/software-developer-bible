# Facade Pattern

A startup caller should not need to remember how disk data reaches memory before execution. One common operation can own that sequence while its subsystem components keep their individual jobs.

## Definition

The Facade pattern is a structural design pattern that provides a simplified interface to a library, a framework, or any other complex set of classes. It hides the complexity of the subsystem and provides a unified interface to the client.

> **Textbook Definition:** Facade is a structural pattern that presents a cohesive, simplified entry point to a subsystem while delegating operations to its existing components.

The pattern is particularly useful when you need to provide a simple interface to a complex subsystem, when you want to layer your subsystems, or when you need to define entry points to each level of a layered software.

## First Principles

A common operation may require several subsystem calls in a specific order. If every client assembles that sequence, each client must learn the subsystem's coordination rules and update when those rules change.

Give the common workflow one entry point and delegate specialized work to its owners. The simplified call moves coordination knowledge; it does not remove the underlying complexity or make side effects atomic. Advanced access can remain available when the public boundary permits it; access restrictions are a separate decision.

## How It Works

```text
client → facade's common workflow
                   ├─ calls subsystem A
                   ├─ passes A's result to subsystem B
                   └─ invokes subsystem C in the required order
```

The facade names the useful operation. Subsystems retain their individual behaviors. The facade's success result must reflect what those behaviors actually established, including any uncertain or partial outcome.

## Code Examples

### Basic Facade Pattern

```typescript
// Complex subsystem classes
class CPU {
  freeze(): void {
    console.log('CPU: Freezing processor');
  }

  jump(address: number): void {
    console.log(`CPU: Jumping to address ${address}`);
  }

  execute(): void {
    console.log('CPU: Executing instructions');
  }
}

class Memory {
  load(address: number, data: string): void {
    console.log(`Memory: Loading ${data} at address ${address}`);
  }

  free(address: number): void {
    console.log(`Memory: Freeing address ${address}`);
  }
}

class HardDrive {
  read(sector: number, size: number): string {
    console.log(`HardDrive: Reading ${size} bytes from sector ${sector}`);
    return 'data';
  }

  write(sector: number, data: string): void {
    console.log(`HardDrive: Writing data to sector ${sector}`);
  }
}

// Facade
class ComputerFacade {
  private cpu: CPU;
  private memory: Memory;
  private hardDrive: HardDrive;

  constructor() {
    this.cpu = new CPU();
    this.memory = new Memory();
    this.hardDrive = new HardDrive();
  }

  startComputer(): void {
    console.log('Starting computer...');

    // Complex startup sequence
    this.cpu.freeze();
    const bootData = this.hardDrive.read(0, 512);
    this.memory.load(0, bootData);
    this.cpu.jump(0);
    this.cpu.execute();

    console.log('Computer started successfully');
  }

  shutdownComputer(): void {
    console.log('Shutting down computer...');

    // Complex shutdown sequence
    this.cpu.freeze();
    this.memory.free(0);

    console.log('Computer shut down successfully');
  }
}

// Client code
const computer = new ComputerFacade();
computer.startComputer();
// No need to know about CPU, Memory, HardDrive details

```

The logged trace is start → freeze → read sector → load the returned data → jump → execute → success. The disk reply is now the input to memory; calling `read` and discarding its data would not express that dependency. These classes simulate the sequence with console output, not a real boot protocol.

## Ordering and Failure Still Matter

The computer example demonstrates one coordinated entry point. A real checkout facade does not make inventory, payment and order storage atomic merely by calling them in sequence. Define local transactions, reservation, idempotency and reconciliation at the services that own those effects.

For example: authenticate and authorize the caller, create a durable pending order, reserve inventory, submit a stable payment operation, reconcile any uncertain response, then finalize. A facade can expose that workflow simply while the underlying [saga contract](../05-architectural/30.1.5.04-saga.md) owns recovery.

Use Promise.all only for independent work whose failures and cancellation policy are understood. Starting dependent operations in parallel changes the workflow, and rejecting one promise does not roll back siblings' effects.

A facade should cover the common workflow, not mechanically expose every underlying CRUD operation. Access to the subsystem may remain available for advanced clients; a facade is not inherently a security wall. Keep its public contract stable and delegate domain invariants to their proper owners.

## Keep the entry point cohesive

A facade can legitimately orchestrate a business workflow. Keep the underlying invariants with their owners: fee calculation belongs to fee policy, stock reservation to inventory, and authorization to the authoritative boundary. Moving every rule into a class called `Facade` simply creates another oversized dependency.

A stable entry point exposes the required common operations, not every method of every subsystem. An advanced caller bypassing the facade is valid only when the API permits that route; if the facade is the required permission or consistency boundary, enforce the restriction rather than relying on a naming convention.

Constructor injection can let tests replace failing subsystems and make lifecycle ownership visible. Direct construction in the toy computer example keeps setup short, but also fixes those collaborators and provides no failure-injection seam.

## Optimize only independent work

Do not recommend `Promise.all` for calls whose inputs or correctness depend on earlier results. In the example, memory loading depends on the disk data. A real workflow must also define cancellation, cleanup, and partial completion. Batch calls, caching, and deferred initialization help only when they preserve the public contract; caching at the front door still requires authorization, freshness, and retention policies.

## Summary

Facade exposes a common subsystem workflow through one simpler entry point while retaining the component responsibilities underneath. Trace where results feed later calls and what success means. The front door reduces repeated coordination knowledge; failure recovery, permissions, and atomicity still need explicit mechanisms.

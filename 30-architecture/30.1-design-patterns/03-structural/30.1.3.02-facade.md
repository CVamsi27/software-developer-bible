# Facade Pattern

A startup caller should not need to remember how disk data reaches memory before execution. One common operation can own that sequence while its subsystem components keep their individual jobs.

## Definition

**In practice:** A Facade presents a client-focused interface to a subsystem and delegates work to its components. It can bundle a common sequence so clients do not have to coordinate those calls.

> **Textbook Definition:** “Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.”

## First Principles

A common operation may require calls to several components in a specific order, with one result feeding the next call. If every client assembles that sequence, each must learn the subsystem's coordination rules and can drift when they change.

Give the common workflow one entry point and delegate specialized work to its owners. The facade centralizes coordination; component behavior and invariants remain with their owners.

## How It Works

```text
client → facade's common workflow
                   ├─ calls subsystem A
                   ├─ passes A's result to subsystem B
                   └─ invokes subsystem C in the required order
```

For each operation, pass intermediate results along its dependency path and return an outcome that reflects what the calls established. Represent partial or uncertain outcomes explicitly; do not imply that every step completed.

## Code Examples

### Coordinate a dependent sequence

```typescript
// Complex subsystem classes
class CPU {
  freeze(): void {
    console.log('CPU: Freezing processor');
  }

  jump(address: number): void {
    console.log(`CPU: Jumping to address ${address}`);
  }

  execute(): void {
    console.log('CPU: Executing instructions');
  }
}
class Memory {
  load(address: number, data: string): void {
    console.log(`Memory: Loading ${data} at address ${address}`);
  }
}

class HardDrive {
  read(sector: number, size: number): string {
    console.log(`HardDrive: Reading ${size} bytes from sector ${sector}`);
    return 'data';
  }
}

// Facade
class ComputerFacade {
  constructor(
    private readonly cpu: CPU,
    private readonly memory: Memory,
    private readonly hardDrive: HardDrive
  ) {}

  startComputer(): void {
    console.log('Starting computer...');

    // Complex startup sequence
    this.cpu.freeze();
    const bootData = this.hardDrive.read(0, 512);
    this.memory.load(0, bootData);
    this.cpu.jump(0);
    this.cpu.execute();
  }
}

// Client code
const computer = new ComputerFacade(new CPU(), new Memory(), new HardDrive());
computer.startComputer();
// The client does not assemble the subsystem sequence.
```

The trace is freeze → read sector 0 → pass the returned `data` to memory → jump to address 0 → execute. Dropping the disk result would break the dependency. These methods log and return placeholder data; they do not model a real boot or device failures. Injected collaborators let tests replace a component or make it fail to check how the facade propagates that failure.

## A sequence is not a transaction

Consider a checkout that creates a pending order, reserves inventory, charges payment and then confirms the order. A facade can coordinate that call sequence, but it cannot make writes across those services atomic or undo a payment when confirmation fails. Model independently committed steps as a [Saga](../05-architectural/30.1.5.04-saga.md): persist progress and operation IDs, then define forward steps, compensation and reconciliation. A facade may initiate it; a durable orchestrator or the participating services own recovery.

Run dependent calls in order. Use `Promise.all` only for independent work with defined failure and cancellation behavior: a rejected promise does not cancel sibling operations or roll back their effects. For payment retries, follow the provider's idempotency contract with a stable key; query or reconcile an uncertain result before starting a new operation.

## Keep the entry point cohesive

Expose a few common operations, not pass-through methods for every subsystem call. Keep invariants with their owners: fee calculation belongs to fee policy, stock reservation to inventory, and authorization to the authoritative boundary. A facade can coordinate a workflow without becoming the place that reimplements each rule.

A facade is not an access-control wall. A gateway can enforce edge policy, but the service that owns a resource must authorize access. Enforce required paths in infrastructure or service boundaries instead of relying on clients to choose a wrapper.

A facade adds a boundary, not automatic speed. Split it when unrelated workflows accumulate, and add batching or caching only for a measured need with explicit freshness, retention and authorization rules.

## Summary

Facade gives a client one coherent operation over subsystem components. Trace how data and failures move through it; keep transactions, durable recovery and resource authorization with their actual owners.

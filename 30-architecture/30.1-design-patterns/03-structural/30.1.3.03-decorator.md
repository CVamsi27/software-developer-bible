# Decorator Pattern

A price can apply a fee and a discount in different combinations. Creating a subclass for every combination repeats policy; wrapping operations can compose it, but order changes the result.

## Definition

The Decorator pattern is a structural design pattern that allows you to attach new behaviors to objects by placing these objects inside special wrapper objects that contain the behaviors. It provides an alternative to subclassing for extending functionality.

> **Textbook Definition:** Decorator is a structural pattern that adds responsibilities by wrapping an object with another object implementing the same contract, allowing behavior to be composed without subclassing every combination.

The pattern is particularly useful when you need to add responsibilities to objects dynamically, when extending functionality through subclassing is impractical, or when you want to combine multiple behaviors.

## First Principles

A component may need logging for one caller, fees for another, and both for a third. A subclass for every combination duplicates the underlying operation and grows with each added responsibility.

Let a wrapper accept the same component contract it exposes. A caller can then place another wrapper around it without learning its concrete type. This structural compatibility makes composition possible, but every wrapper must also preserve the caller's input, result, error, and lifecycle promises. The sequence of wrappers remains part of the behavior.

## How It Works

```text
caller → outer component contract → wrapper → inner component contract → base
                    result returns outward through the wrappers
```

A wrapper can act before delegation, after the result, or on an error. Because its inner object can itself be a wrapper, the same contract supports recursive composition. A cache may short-circuit a call, but only if that is permitted by the component's promise.

## Trace a Wrapped Operation

```typescript
interface Price { amount(): number; }
class BasePrice implements Price {
  amount() { return 10; }
}
class AddFee implements Price {
  constructor(private inner: Price, private fee: number) {
    if (!Number.isFinite(fee) || fee < 0) throw new RangeError('fee');
  }
  amount() { return this.inner.amount() + this.fee; }
}
class ApplyDiscount implements Price {
  constructor(private inner: Price, private fraction: number) {
    if (!Number.isFinite(fraction) || fraction < 0 || fraction > 1) throw new RangeError('fraction');
  }
  amount() { return this.inner.amount() * (1 - this.fraction); }
}
const discountThenFee = new AddFee(new ApplyDiscount(new BasePrice(), 0.2), 2);
const feeThenDiscount = new ApplyDiscount(new AddFee(new BasePrice(), 2), 0.2);
console.log(discountThenFee.amount()); // 10
console.log(feeThenDiscount.amount()); // 9.6 (subject to floating-point representation)
```

The caller asks the outer object for an amount. Each wrapper delegates inward and applies its own responsibility on the returned value. Swapping wrappers changes the result: decorators compose, but their behavior is not generally commutative. This numeric example demonstrates composition; real money should use an appropriate decimal/minor-unit representation.

```text
calls:   caller → fee → discount → base
returns: caller ← +2  ← ×0.8     ← 10
```

## Preserve the Contract Across Layers

Logging, metrics, retry and caching can wrap the same service interface, but their failure policies and order matter. A retry wrapper can repeat an inner logging or payment operation; a cache can retain user-specific data unless its identity and authorization contract cover that scope. A wrapper that implements every method can still violate behavioral substitution.

A logging wrapper should decide whether logger failure changes the business result. A cache needs bounded retention. An async wrapper must propagate promises and errors correctly. Stream wrappers must preserve flow control and resource cleanup; reversing a string is not encryption or compression.

The GoF pattern is distinct from TypeScript's @decorator syntax. Language decorators can define metadata or transform declarations without constructing a same-interface wrapper. See [TypeScript Decorators](../../../10-frontend/10.2-typescript/04-advanced-patterns/10.2.4.03-decorators.md) for standard versus legacy signatures and compiler requirements. NestJS annotation syntax does not itself prove GoF Decorator behavior.

## Keep the promise visible at every layer

An async logging wrapper must await the inner operation before claiming completion, and decide whether a logger failure can change the business result. A retry wrapper outside it repeats logging and the inner operation; inside it, the logger may observe one overall call instead of each attempt. Neither arrangement makes repeating a committed payment safe.

Test the combinations that change semantics, not just that each class implements the methods. An outer cache may bypass an inner authorization check on a hit; an authorization check outside a cache can still need caller-scoped keys and fresh permissions. Deep stacks can also hide cleanup ownership and where a failure originated.

Use a few named wrappers for actual responsibilities. Configuration or a direct helper can be clearer when callers always use one fixed combination. Sharing mutable state between wrappers requires a scope and disposal policy; a map or counter is not forbidden merely because it is state.

## Evaluate runtime cost and lifecycle

Each wrapper adds calls and retained references; measure them against the wrapped work. Stream wrappers must preserve backpressure and close their resources. Cache wrappers need bounded state and invalidation. Do not claim a string transform implements encryption/compression or that annotation syntax automatically builds GoF wrappers.

## Summary

Decorator composes responsibilities by exposing the same contract around an inner component. Calls travel inward and results/errors travel outward; swapping wrappers can change outcomes. Matching method names enables the structure, while substitution, retries, authorization, and cleanup determine whether the composition is correct.

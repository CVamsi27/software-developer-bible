# Decorator Pattern

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

The Decorator pattern is a structural design pattern that allows you to attach new behaviors to objects by placing these objects inside special wrapper objects that contain the behaviors. It provides an alternative to subclassing for extending functionality.

The pattern is particularly useful when you need to add responsibilities to objects dynamically, when extending functionality through subclassing is impractical, or when you want to combine multiple behaviors.

## First Principles

Decorator layers behavior by wrapping the same interface:

1. **Cross-cutting behavior composes at runtime**: logging, retry, caching, metrics around *the same calls* — each wrapper does one thing, and stacking is configuration. The alternative (subclassing for every combination) explodes combinatorially.
2. **Same-interface wrapping is the load-bearing constraint**: the wrapped object is substitutable everywhere the original was (LSP, → 30.1.1.01) — which is why middleware chains (→ 20.1.4.03) and interceptors (→ 20.2.2.04) are this pattern with framework plumbing.
3. **The cost is layer count**: deep stacks are hard to debug (which layer threw?); discipline is keeping wrappers few and ordered.

## Why Do We Need It?

Without the Decorator pattern, extending object behavior leads to:

1. **Class explosion**: Many subclasses for each combination of behaviors

2. **Rigid hierarchy**: Static inheritance makes changes difficult

3. **Code duplication**: Common behaviors repeated across subclasses

4. **Violation of Open/Closed Principle**: Modifying existing classes for new behavior

## How It Works

The Decorator pattern works by:

1. Defining a common interface for components and decorators

2. Creating concrete components that implement the base behavior

3. Creating decorators that wrap components and add behavior

4. Decorators delegate to the wrapped component and add their behavior

## Trace a Wrapped Operation

```typescript
interface Price { amount(): number; }
class BasePrice implements Price {
  amount() { return 10; }
}
class AddFee implements Price {
  constructor(private inner: Price, private fee: number) {}
  amount() { return this.inner.amount() + this.fee; }
}
class ApplyDiscount implements Price {
  constructor(private inner: Price, private fraction: number) {
    if (fraction < 0 || fraction > 1) throw new RangeError('fraction');
  }
  amount() { return this.inner.amount() * (1 - this.fraction); }
}
const discountThenFee = new AddFee(new ApplyDiscount(new BasePrice(), 0.2), 2);
const feeThenDiscount = new ApplyDiscount(new AddFee(new BasePrice(), 2), 0.2);
console.log(discountThenFee.amount()); // 10
console.log(feeThenDiscount.amount()); // 9.6 (subject to floating-point representation)
```

The caller asks the outer object for an amount. Each wrapper delegates inward and applies its own responsibility on the returned value. Swapping wrappers changes the result: decorators compose, but their behavior is not generally commutative. This numeric example demonstrates composition; real money should use an appropriate decimal/minor-unit representation.

```text
caller → fee → discount → base
         +2     ×0.8       10
```

## Preserve the Contract Across Layers

Logging, metrics, retry and caching can wrap the same service interface, but their failure policies and order matter. A retry wrapper can repeat an inner logging or payment operation; a cache can retain user-specific data unless its identity and authorization contract cover that scope. A wrapper that implements every method can still violate behavioral substitution.

A logging wrapper should decide whether logger failure changes the business result. A cache needs bounded retention. An async wrapper must propagate promises and errors correctly. Stream wrappers must preserve flow control and resource cleanup; reversing a string is not encryption or compression.

The GoF pattern is distinct from TypeScript's @decorator syntax. Language decorators can define metadata or transform declarations without constructing a same-interface wrapper. See [TypeScript Decorators](../../../10-frontend/10.2-typescript/04-advanced-patterns/10.2.4.03-decorators.md) for standard versus legacy signatures and compiler requirements. NestJS annotation syntax does not itself prove GoF Decorator behavior.

## Common Mistakes

### 1. Too Many Decorators

```typescript
// BAD - Decorator chain too long
const decorated = new DecoratorA(
  new DecoratorB(
    new DecoratorC(
      new DecoratorD(
        new DecoratorE(
          new Component()
        )
      )
    )
  )
);

```

### 2. Uncontrolled Decorator State

```typescript
// Owned cache/state can be valid; specify sharing and lifecycle
class BadDecorator extends BaseDecorator {
  private state: any;
  private dependencies: any[];

  // Hard to reason about
}

```

### 3. Not Implementing Interface

```typescript
// BAD - Decorator doesn't implement interface
class BadDecorator {
  private wrapped: Component;

  // Missing interface methods
}

```

### 4. Violating the Delegation Contract

```typescript
// BAD - Decorator doesn't delegate properly
class BadDecorator extends BaseDecorator {
  process(data: any): any {
    // Deliberate short-circuiting (for example a cache hit) is valid only under the contract
    return 'modified';
  }
}

```

## Best Practices

### 1. Implement Component Interface

```typescript
// GOOD - Implements interface
class GoodDecorator implements Component {
  private wrapped: Component;

  process(data: any): any {
    return this.wrapped.process(data);
  }
}

```

### 2. Keep Decorators Focused

```typescript
// GOOD - Single responsibility
class LoggingDecorator implements Component {
  // Only adds logging
}

```

### 3. Use Dependency Injection

```typescript
// GOOD - Injectable decorators
class Decorator {
  constructor(private wrapped: Component) {}
}

```

### 4. Limit Decorator Chain

```typescript
// GOOD - Reasonable chain length
const decorated = new CachingDecorator(
  new LoggingDecorator(
    new Component()
  )
);

```

## Performance Considerations

1. **Chain Overhead**: Each decorator adds a layer of indirection.

2. **Memory Usage**: Decorators are usually lightweight; the wrapped object consumes memory.

3. **Lazy Evaluation**: Consider lazy evaluation in decorators for expensive operations.

4. **Caching**: Use caching decorators to avoid redundant computation.

5. **Batch Operations**: Implement batch operations in decorators for better performance.

## Summary

The Decorator pattern is essential for adding behavior to objects dynamically. It promotes the Open/Closed Principle, enables flexible composition, and avoids class explosion. Use it for cross-cutting concerns, middleware, and extending functionality without modifying existing code.

# Decorator Pattern

A price of 10 becomes 10 or 9.60 when the same 20% discount and fee of 2 apply in a different order. Wrappers let a caller choose the combination for one object — while the order stays part of its behavior:

```typescript
const price = new AddFee(new ApplyDiscount(new BasePrice(), 0.2), 2);
console.log(price.amount()); // 10 — order is behavior
```

## Definition

**In practice:** A **Decorator** wraps a component with another object implementing the same **contract**. Each layer delegates to the next and adds a responsibility, so callers compose behavior for one object without a subclass per combination.

> **Textbook Definition:** "Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality." — Gamma et al., *Design Patterns*, p. 315, reproduced in the publisher excerpt below.

## First Principles

A component may need logging for one caller and a fee for another. A subclass per combination duplicates the operation and grows with each added responsibility. If each wrapper accepts and exposes the same component contract, callers can nest wrappers without depending on concrete classes. That shape enables composition; preserving the contract makes it safe.

## 1. Delegate inward, return outward

```text
caller → outer component contract → wrapper → inner component contract → base
                    result returns outward through the wrappers
```

A wrapper can act before delegation, after a result, or when an error occurs. Its inner component may itself be a wrapper, so the same contract supports nested composition. A cache may skip delegation — but only when returning a cached result still satisfies the component's promise.

## 2. Trace a wrapped operation

```typescript
interface Price { amount(): number; }
class BasePrice implements Price {
  amount() { return 10; }
}
class AddFee implements Price {
  constructor(private inner: Price, private fee: number) {
    if (!Number.isFinite(fee) || fee < 0) throw new RangeError('fee');
  }
  amount() { return this.inner.amount() + this.fee; }
}
class ApplyDiscount implements Price {
  constructor(private inner: Price, private fraction: number) {
    if (!Number.isFinite(fraction) || fraction < 0 || fraction > 1) throw new RangeError('fraction');
  }
  amount() { return this.inner.amount() * (1 - this.fraction); }
}
const discountThenFee = new AddFee(new ApplyDiscount(new BasePrice(), 0.2), 2);
const feeThenDiscount = new ApplyDiscount(new AddFee(new BasePrice(), 2), 0.2);
console.log(discountThenFee.amount()); // 10
console.log(feeThenDiscount.amount()); // 9.600000000000001 (binary floating-point)
```

The two constructions prove wrapper order changes the outcome: 10 × 0.8 + 2 = 10, while (10 + 2) × 0.8 = 9.6. This is illustrative arithmetic; production money needs an explicit decimal or minor-unit rounding policy.

```text
calls:   caller → fee → discount → base
returns: caller ← +2  ← ×0.8     ← 10
```

## 3. Choose the order by its effect

Order decides which responsibilities see a call and which can short-circuit it. A cache outside authorization can return a hit without running the inner check. Put the permission check on every path returning protected data, scope cache keys to caller and data version, and define how permission changes invalidate entries.

Retries also change what an outer layer observes. A logger outside a retry records one logical request; a logger inside records every attempt. Decide whether logger failure may fail the business operation, and never retry a write unless its idempotency policy makes repetition safe. A wrapper may propagate, map, retry, or handle an error — but that choice must preserve the service contract.

## 4. Preserve asynchronous and resource behavior

For an asynchronous operation, return its promise or await it so callers observe completion and rejection. If the wrapper's own work must finish first, await the inner promise and settle the outer promise only after that work completes. A stream wrapper must preserve backpressure and close resources it owns. Stateful wrappers need an explicit scope, bounded retention, and invalidation where applicable. Each layer adds calls and references, so measure overhead against the wrapped work, and use an explicit helper or fixed configuration when it communicates the policy more clearly.

The GoF pattern is object composition under a shared contract. TypeScript's `@decorator` syntax instead applies a function to a class declaration or member; it does not by itself create a same-contract wrapper. TypeScript 5.0 added a newer decorator convention: with `experimentalDecorators` off the compiler uses it; with the flag on, the compiler uses legacy semantics. These are separate modes, and an implementation for one is not automatically compatible with the other. See [TypeScript Decorators](../../../10-frontend/10.2-typescript/04-advanced-patterns/10.2.4.03-decorators.md) for calling conventions. NestJS annotation syntax alone never establishes GoF Decorator behavior.

## Summary

Decorator composes responsibilities by wrapping a component with the same contract. Calls delegate inward; results return outward, while a wrapper may deliberately handle or transform errors. Order can change outcomes, so preserve the component's behavioral promises across retries, caching, authorization and cleanup.

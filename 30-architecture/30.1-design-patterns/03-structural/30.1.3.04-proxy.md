# Proxy Pattern

An image gallery can show a filename before loading the image bytes. A stand-in preserves the image interface and defers that cost until someone opens the image:

```typescript
const image = new ImageProxy('photo.jpg');
image.getInfo(); // metadata now, bytes only on display()
```

## Definition

**In practice:** A **Proxy** implements a subject's public **contract** and mediates access to the real subject. It can delay creation, check permission, route a remote call, or reuse a result — while keeping the caller on the same access path.

> **Textbook Definition:** "Provide a surrogate or placeholder for another object to control access to it." — Steven John Metsker, *Design Patterns in C#*, reproduced in the publisher excerpt below.

## First Principles

If every caller creates an expensive object or applies its own permission check, cost and policy vary per call path. Put one stand-in on the subject's path and make it own that decision. When the proxy delegates, the subject does the underlying work; a cache proxy may instead return a stored result without invoking it.

The shared method shape never makes every proxy transparent. Lazy creation changes timing, remote calls add latency and failure, protection can deny an operation. Those outcomes belong in the contract callers rely on.

## 1. Defer creation until first use

```text
caller → DisplayImage contract → ImageProxy → create on first display → RealImage
                                   └─ getInfo returns metadata without creating it
```

```typescript
interface DisplayImage {
  display(): void;
  getInfo(): string;
}

class RealImage implements DisplayImage {
  constructor(private readonly filename: string) {
    this.loadFromDisk();
  }

  private loadFromDisk(): void {
    console.log(`Loading image from disk: ${this.filename}`);
  }

  display(): void {
    console.log(`Displaying image: ${this.filename}`);
  }

  getInfo(): string {
    return `Image: ${this.filename}`;
  }
}

class ImageProxy implements DisplayImage {
  private realImage: RealImage | null = null;

  constructor(private readonly filename: string) {}

  display(): void {
    this.realImage ??= new RealImage(this.filename);
    this.realImage.display();
  }

  getInfo(): string {
    return `Image: ${this.filename}`;
  }
}

const image = new ImageProxy('photo.jpg');
console.log(image.getInfo()); // Image: photo.jpg; still not loaded
image.display(); // loads once, then displays
image.display(); // reuses the subject
```

Constructing the proxy stores the filename. `getInfo` preserves the subject's metadata format without creating it. The first `display` constructs `RealImage`; later calls reuse it. This demo logs the simulated load and display, but opens no image file.

If the subject constructor throws, assignment to `realImage` never completes, so the next display tries again. That is a retry policy, even implicit — decide whether retry is safe and how callers learn initialization failed.

## 2. Define the boundary each proxy owns

Different proxy purposes carry different promises. The wrapper shape alone provides none of these policies:

| Proxy purpose | Required contract |
| --------------- | ------------------------------------------------------------------------------------------------------------------ |
| Virtual or lazy | Define when the subject becomes ready, how concurrent initialization is shared, and who disposes it. |
| Protection | Check current identity and permission on every protected path; do not expose a bypass to the subject. |
| Caching | Define caller scope, freshness, invalidation and bounded retention; authorization must still cover cache hits. |
| Rate limiting | Define coordinated capacity and denial behavior; a local counter does not enforce a fleet-wide limit. |
| Remote | Bound deadlines and expose transport failure; retry writes only with an idempotency policy and operation identity. |

An asynchronous virtual proxy should share one pending initialization among concurrent callers rather than start duplicate connections. Expose readiness through an awaited operation or factory; do not start connection work in a constructor and imply the object is ready. Clear a failed pending attempt only when retry is deliberate, and coordinate shutdown with initialization and in-flight work. The [shared asynchronous initialization contract](../02-creational/30.1.2.01-singleton.md#share-asynchronous-initialization) shows the concurrency requirement.

Authorization must stay authoritative even when a proxy caches. If callers can reach the server operation directly, a local protection proxy is no security boundary. Check permission before returning protected data, scope cached results to principal and data version, and define how permission changes invalidate entries. Represent denial and remote failure in the advertised result/error contract instead of silently turning them into success-shaped fallbacks.

## 3. Keep language proxies distinct

JavaScript's built-in `Proxy` constructor lets a handler intercept operations on an object. Its receiver behavior and target invariants are language rules; they never make every handler a GoF Proxy. Use [Proxy & Reflect](../../../10-frontend/10.1-javascript/02-objects-prototypes-this/10.1.2.03-proxy-reflect.md) for those mechanics.

Indirection adds work and hidden state. Lazy loading moves cost to first use; caching trades repeated work for memory and freshness policy; a remote proxy adds network failure. Measure those trade-offs against the real workload, and keep direct access when no access or lifecycle boundary is needed.

## Summary

A Proxy stands on the subject's call path to control access or lifecycle while presenting its public contract. The image example delays creation until first display and reuses the subject afterward. Production proxies must define readiness, authority, failures, freshness, retries and disposal; those policies do not come from matching method names.

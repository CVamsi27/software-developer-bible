# Proxy Pattern

An image gallery may need filenames before it needs the expensive image content. A stand-in can answer metadata now and create the subject on first display, provided both preserve the same call contract.

## Definition

The Proxy pattern is a structural design pattern that provides a surrogate or placeholder for another object to control access to it. It creates a representative object that controls access to the original object, adding a layer of indirection.

> **Textbook Definition:** Proxy is a structural pattern that interposes an object implementing a subject's interface to control access to that subject, such as access checks, lazy initialization, or remote invocation.

The pattern is particularly useful for lazy loading, access control, logging, caching, and remote resource management.

## First Principles

A caller may want an operation before its expensive subject exists, or may be allowed to invoke it only under an access policy. If every caller handles creation or gating itself, the lifecycle and permission rules can diverge.

Place a stand-in on the subject's call path. It exposes the required subject contract while owning the access decision. The real subject still performs the underlying work. Sharing method signatures does not erase delayed loading, authorization denial, network latency, or failure; those must fit the advertised contract.

## Why Do We Need It?

Direct access is adequate when creation is cheap and no extra access boundary is required. A proxy is useful when one path must deliberately gate, initialize, route, or reuse the subject.

## How It Works

```text
caller → subject contract on proxy → access/lifecycle decision → real subject
                                      └─ delay, deny, or reuse under the contract
```

The stand-in is an object-pattern role. JavaScript's `Proxy` language primitive can intercept object operations, but its receiver and target invariants are separate implementation rules.



## Code Examples

### Basic Proxy Pattern

```typescript
// Subject interface
interface DisplayImage {
  display(): void;
  getInfo(): string;
}

// Real subject
class RealImage implements DisplayImage {
  private filename: string;

  constructor(filename: string) {
    this.filename = filename;
    this.loadFromDisk();
  }

  private loadFromDisk(): void {
    console.log(`Loading image from disk: ${this.filename}`);
  }

  display(): void {
    console.log(`Displaying image: ${this.filename}`);
  }

  getInfo(): string {
    return `Image: ${this.filename}`;
  }
}

// Proxy
class ImageProxy implements DisplayImage {
  private realImage: RealImage | null = null;
  private filename: string;

  constructor(filename: string) {
    this.filename = filename;
  }

  display(): void {
    if (!this.realImage) {
      this.realImage = new RealImage(this.filename);
    }
    this.realImage.display();
  }

  getInfo(): string {
    return `Image: ${this.filename}`; // same metadata contract, no loading needed
  }
}

// Client code
function renderImage(image: DisplayImage): void {
  console.log(image.getInfo());
  image.display();
}

// Usage
console.log('Creating proxy (no image loaded yet):');
const proxy = new ImageProxy('photo.jpg');

console.log('\nFirst display (loads image):');
proxy.display();

console.log('\nSecond display (uses cached image):');
proxy.display();

```

Constructing the proxy stores only a filename. The first `display` constructs a `RealImage`, whose simulated loader logs once, then displays it. The second display reuses that subject. `getInfo` returns the same metadata format as the real image, so a caller is not forced to interpret two incompatible result meanings. No image file is opened by this demo.

If synchronous initialization throws, the assignment to `realImage` does not complete; the next display attempts it again. Decide whether retry is appropriate in a real implementation. Async initialization needs a shared pending operation as described below, not this synchronous field check.

## State the Access Contract

A lazy image proxy can delay loading until display; it cannot make loading free. A remote proxy introduces latency, partial failure and uncertain mutation outcomes even if its method shape resembles a local object.

| Proxy purpose | Required mechanism beyond wrapping |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| Lazy asynchronous resource | Await actual readiness, share in-flight initialization, define failure retry and disposal |
| Protection | Verify current identity and permission at the authoritative boundary; prevent bypass |
| Cache | Scope keys by data/permission identity and define freshness, invalidation and retention |
| Rate limit | Define coordinated capacity and failure policy rather than counting local calls only |
| Remote object | Bound deadlines and retry safely with operation identity where needed |

Do not start async connection work in a constructor and return a supposedly ready object. Use an awaited factory and the [shared asynchronous initialization contract](../02-creational/30.1.2.01-singleton.md#share-asynchronous-initialization) when multiple calls must share one attempt. Reset a failed pending attempt only under a deliberate retry policy, and coordinate shutdown with initialization and in-flight operations.

JavaScript Proxy traps are a language feature that can implement interception. They have invariants, receiver semantics and behavior with native/private-field objects that a hand-written wrapper does not automatically inherit. Use [Proxy & Reflect](../../../10-frontend/10.1-javascript/02-objects-prototypes-this/10.1.2.03-proxy-reflect.md) for that implementation rather than treating a small watcher simulation as Vue's reactivity system.

A proxy can legitimately own state such as a cached subject or access policy. The risk is uncontrolled state lifetime and hidden behavior, not the existence of state itself. Specify who creates, closes and invalidates it.

## Enforce the intended boundary

A protection proxy works only if callers cannot obtain another path to the authoritative subject. Checking a permission in the wrapper while exposing an unguarded server method gives no complete authorization boundary. Cached permissions or results also need a freshness and caller-identity policy.

Do not silently return `null` after denying an operation whose contract promises a result; expose the denial category. Do not treat a self-reference as recursion unless a delegated operation actually calls itself. A wrapper chain that delegates back into the same operation can recurse indefinitely even when each class individually looks valid.

Document load timing, subject identity, errors, retry policy, and disposal. A resource owner should close the subject it creates; merely removing a cache entry does not close a connection already held elsewhere. Constructor injection can expose dependencies, while a virtual proxy may intentionally receive a creation function instead of an already-created subject.

## Separate delayed work from eliminated work

Lazy access moves creation cost to the first operation; it does not eliminate it. Caching avoids some repeated work but can retain stale state or return a shared mutable object. A remote proxy adds deadlines, transport failure, and uncertain mutation outcomes even if it resembles a local call. Measure those effects against the subject's real workload rather than assuming wrapper overhead is the bottleneck.

## Summary

Proxy places access and lifecycle policy on a subject's call path. The lazy image trace creates the subject on first display and reuses it later while preserving metadata meaning. Real protection, remote access, and caches require their own authoritative permissions, failure, freshness, and disposal contracts.

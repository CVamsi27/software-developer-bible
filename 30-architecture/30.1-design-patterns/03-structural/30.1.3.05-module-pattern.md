# Module Pattern

A caller should calculate a circle's area without knowing the value of π or how the calculation is implemented. A module gives callers a small contract that stays stable while internals change — controlling visibility, not automatically shared state or import reach:

```typescript
import { area } from './shapes/index.js';
console.log(area(5).toFixed(2)); // 78.54 — PI stays hidden
```

## Definition

**Practical definition:** A JavaScript **module** is a unit with its own scope and an explicit interface. The historical **Module pattern** creates that boundary with a closure and returns selected operations. Modern JavaScript usually expresses module boundaries with native ECMAScript module (`import`/`export`) syntax; that is the language's module system, not the historical closure pattern itself.

> **Textbook Definition:** A module is a reusable software component defined by an interface contract: it exposes a public API while hiding implementation details, so consumers depend on the contract rather than the implementation. (Elliott, [*Programming JavaScript Applications*, Chapter 4](https://www.oreilly.com/library/view/programming-javascript-applications/9781491950289/ch04.html))

## First Principles

If every part of a program can reach every binding, callers can depend on details that should be free to change. Give each unit a scope, then expose only the operations other units need. A module boundary makes that dependency visible and reviewable.

A hidden name is not the same as hidden data. An exported function can return a mutable object, and module-level state is shared by every caller of that module instance. Encapsulation, mutability, authorization, and per-request isolation are separate design decisions.

## How It Works

### 1. Follow one export through the boundary

`circle.ts` keeps the constant and helper local. The barrel deliberately re-exports only the supported operations, and the consumer imports through that boundary:

```typescript
// shapes/circle.ts
const PI = Math.PI;

function computeArea(radius: number): number {
  return PI * radius * radius;
}

export function area(radius: number): number {
  return computeArea(radius);
}

export function circumference(radius: number): number {
  return 2 * PI * radius;
}
```

```typescript
// shapes/index.ts
export { area, circumference } from './circle.js';
```

```typescript
// consumer.ts
import { area } from './shapes/index.js';

console.log(area(5).toFixed(2)); // 78.54
```

The consumer can name `area` but cannot import `PI` or `computeArea` through this interface. The call passes through the barrel, reaches `computeArea`, and returns a number for the consumer to format. The `.js` specifier is valid for a TypeScript project configured to emit Node-compatible ESM; bundlers and other runtimes may use different resolution rules.

The historical **Revealing Module** variation uses an immediately invoked function expression (IIFE): functions defined inside a closure, with references to the public operations returned. Useful to recognize in legacy code, but new code rarely needs the extra wrapper:

```javascript
const Circle = (() => {
  const pi = Math.PI;
  const area = (radius) => pi * radius * radius;

  return { area };
})();

Circle.area(5); // public operation; pi stays inside the closure
```

The returned object is the public interface; the variation's name never changes its privacy limits.

### 2. Give shared state an explicit owner

A top-level cache belongs to the loaded module instance. In a server process, requests importing and using that instance share the same map:

```typescript
const values = new Map<string, unknown>();

export function get(key: string): unknown {
  return values.get(key);
}

export function set(key: string, value: unknown): void {
  values.set(key, value);
}
```

That may suit process-wide metadata, but it is not per-user or per-request isolation. When callers need separate caches, create state per owner:

```typescript
export function createCache<T>() {
  const values = new Map<string, T>();

  return {
    get(key: string): T | undefined {
      return values.get(key);
    },
    set(key: string, value: T): void {
      values.set(key, value);
    },
  };
}
```

Each `createCache()` call owns a different map. If `T` is an object, `get` still returns the stored reference, so a caller can mutate it — copy, freeze, or deliberately share returned values per the API contract; hiding the map never makes its contents immutable. In one ESM loader graph, repeated imports of the same resolved module share its instance, so top-level initialization and state are shared. A dynamic `import()` defers loading and returns a promise; it creates no fresh instance per caller. For tenant or request state, pass an owner-scoped object or create one through a factory.

### 3. Keep entry points, resolution, and cycles explicit

A directory barrel curates exports, but nothing stops another file from importing a sibling path directly. For a published package, use `package.json` `exports` to define supported entry points; for internal source, enforce deep-import rules with project tooling when they matter.

TypeScript's `paths` option helps the compiler resolve an alias but rewrites nothing in emitted JavaScript. Configure the bundler or runtime to resolve the same alias, or use a `package.json` `imports` entry where the runtime supports it. Always check the module-resolution mode of the code that will actually run.

Static ESM imports make dependencies visible to loader and bundler. Static structure can help tree-shaking, but removal also depends on side effects, package metadata, and the production build — marking a package side-effect-free incorrectly can drop required initialization or CSS. A dynamic import defers loading until later, e.g. after navigation, at the cost of asynchrony.

Cycles need attention at the dependency boundary. ESM uses live bindings, so reading an imported lexical binding before initialization can throw a `ReferenceError`; CommonJS cycles can instead expose partially initialized exports. Reduce a cycle by moving shared contracts or responsibilities to a lower-level module, rather than relying on initialization order.

### 4. Choose the boundary by its contract

Keep a module cohesive around a contract that changes for one reason. Split when independent responsibilities or consumers need independent interfaces — never to hit an arbitrary file length or export count. Keep exports intentional, make import-time effects visible, and inspect the built package when bundle size or public entry points matter.

## Summary

A module gives related code a scope and a deliberate public interface; native ESM is the usual modern JavaScript mechanism. A private binding can still manage shared mutable state, and exported objects remain mutable by callers — so choose state ownership and value semantics explicitly. Runtime resolution, package entry points, import-time effects, and tree-shaking behavior all depend on the loader and build configuration in use.

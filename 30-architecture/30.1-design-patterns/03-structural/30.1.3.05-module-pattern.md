# Module Pattern

A caller needs an area function without depending on its calculation helper or constant names. A module can expose that operation while keeping its internal bindings in a separate scope.

## Definition

The **Module pattern** groups related code (state + behavior) behind a defined public interface, hiding internal implementation details. In modern JavaScript/TypeScript, **ES modules** (`import` / `export`) are the native form — each ES module has its own scope; a TypeScript file's module classification depends on syntax and compiler configuration, and only explicitly exported bindings are visible through the module interface. The historical variants are the **IIFE module** (Immediately Invoked Function Expression) and the **Revealing Module** pattern, both designed to produce privacy before ES2015. The senior design choice is using modules to enforce a clear public API and prevent accidental coupling.

> **Textbook Definition:** The Module pattern encapsulates related state and operations behind an explicit export boundary, controlling which implementation details other components can access.

## First Principles

Unrelated parts of a program can choose the same internal variable name or accidentally modify one another's state if all bindings occupy one shared scope. A caller also needs to know which operations are supported without relying on every implementation detail.

Create an isolated scope and expose a selected interface. Closure-based modules retain hidden bindings through their exported functions; ES modules provide a language-defined module scope and export bindings. Either mechanism hides names, but a returned mutable object can still expose state, and one loaded module's state can still be shared by several requests. Visibility, data isolation, and lifecycle are distinct decisions.

## Why Do We Need It?

1. **Encapsulation** — Private state stays private; only the exported surface is part of the contract.
2. **Namespacing** — Avoid global scope pollution; multiple modules can use the same internal name without collision.
3. **Static analysis** — ESM syntax helps bundlers identify unused code; side effects, usage and build configuration determine what is actually removed.
4. **Testability** — A module with a small public surface is easy to mock; private internals stay untouched.
5. **Evaluation ownership** — A loaded module instance evaluates once in its module graph. Static dependencies run as the graph is evaluated; dynamic import can defer loading. Side effects are not inherently bounded or idempotent.
6. **Dependency clarity** — `import` statements make dependencies explicit; the file is self-documenting.
7. **Refactor safety** — A module's internals can change freely; consumers only depend on the public API.

## How It Works

### Modern ES Module

```text
shapes/circle.ts
   ├── private: PI, computeArea()
   ├── exported: area(r), circumference(r)
   │
   ▼
shapes/index.ts (barrel — re-exports)
   ├── re-exports: area, circumference
   │
   ▼
main.ts
   └── import { area } from './shapes/index.js'
```

### Module Resolution

```text
import { foo } from './module' // relative path
import { foo } from '@/lib/module' // path alias (tsconfig / bundler)
import { foo } from 'lodash/foo' // package
import { foo } from 'lodash' // package main
```

### Tree-Shaking

```text
Full module exports: { a, b, c, d }
   │
   ▼
Consumer imports: { a }
   │
   ▼
Possible optimized output: a plus its dependencies; unused b/c/d removed
(subject to side effects, static usage and production build configuration)
```

## Code Examples

### Modern ES Module (TypeScript)

```typescript
// shapes/circle.ts
const PI = Math.PI; // private — not exported

function computeArea(r: number): number { // private
  return PI * r * r;
}

export function area(r: number): number { // public
  return computeArea(r);
}

export function circumference(r: number): number { // public
  return 2 * PI * r;
}
```

```typescript
// shapes/index.ts — barrel re-export
export { area, circumference } from './circle.js';
```

```typescript
// consumer
import { area } from './shapes/index.js';
console.log(area(5).toFixed(2)); // 78.54 through the barrel's public API
// PI is not accessible here — private to the module
```

The consumer resolves the barrel, whose re-export points to the circle module. `area(5)` invokes private `computeArea`, which reads private `PI`; the returned number becomes `78.54` after formatting. These `.js` specifiers describe emitted JavaScript files and work with an appropriate TypeScript/Node ESM setup; the original directory-only spelling is bundler-dependent.

### IIFE Module (Pre-ES6; still seen in legacy code)

```typescript
// shapes/circle.iife.ts
const Circle = (function () {
  const PI = Math.PI; // truly private
  function computeArea(r: number) {
    return PI * r * r;
  }
  return {
    area(r: number) { return computeArea(r); },
    circumference(r: number) { return 2 * PI * r; },
  };
})();

// usage
Circle.area(5); // public
// PI is not accessible — IIFE captured it
```

### Revealing Module Pattern

```typescript
// utils/cache.ts
const Cache = (function () {
  const store = new Map<string, unknown>(); // private
  const hits = { count: 0 }; // private

  function get(key: string): unknown {
    if (store.has(key)) hits.count++;
    return store.get(key); // caller must check the retrieved value
  }

  function set(key: string, value: unknown) {
    store.set(key, value);
  }

  function stats() { // public read-only view
    return { size: store.size, hits: hits.count };
  }

  return { get, set, stats }; // public API
})();
```

`stats()` returns a new object, so modifying its hit count does not change the internal counter. A cached object returned by `get`, however, remains the same mutable reference. Hiding `store` does not deep-freeze its values. A generic `get<T>` cast would only assert a caller-selected type, not verify that a stored value has it. For separate scopes, expose a `createCache` factory instead of one immediately created cache.

### Namespace Imports vs Named Imports

```typescript
// Named imports expose the particular dependency; removability depends on the tool
import { readFile } from 'fs/promises';

// Namespace import — static property usage may still be tree-shaken
import * as fs from 'fs/promises'; // static usage may optimize; this Node builtin is normally external
```

### Explicit one-time configuration

This is a separate two-file example. Importing defines the module state and operations; it does not call `configure`.

```typescript
// logger/index.ts
let level: 'info' | 'debug' | undefined;
export function configure(opts: { level: 'info' | 'debug' }): void {
  if (level !== undefined && level !== opts.level) {
    throw new Error('Logger already configured with another level');
  }
  level = opts.level;
}
export function log(message: string): void {
  if (level === undefined) throw new Error('Configure logger first');
  console.log(`[${level}] ${message}`);
}
```

```typescript
// consumer
import { configure, log } from './logger/index.js';
configure({ level: 'info' });
log('ready'); // [info] ready
```

Two consumers of the same module instance share `level`. Repeating the same configuration is allowed; a conflicting one is rejected. Another process has its own instance. This is a logging demonstration, not a complete logger with buffering, request context, or flushing.



### Path Aliases (`tsconfig.json` + bundler)

```jsonc
// tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "@/lib/*": ["src/lib/*"],
      "@/domain/*": ["src/domain/*"]
    }
  }
}
```

```typescript
// usage
import { User } from '@/domain/user';
```

TypeScript paths aids compiler resolution; it does not rewrite emitted import specifiers. Configure the runtime/bundler mapping too. Native browser ESM and Node ESM also have their own extension and directory-resolution rules.

## Real-World Use Cases

1. **Domain layer** — `domain/order.ts` exports `Order`, `place()`, `cancel()`; the internal state machine and validation stay private.
2. **Service layer** — `services/payment-service.ts` exports a small public surface; the SDK clients and retry logic are private.
3. **Utility libraries** — `lib/format-date.ts` exports `formatDate`, `parseDate`; the internal locale data is private.
4. **Barrel re-exports** — `index.ts` can curate a public API. Restricting deep imports also needs package exports or enforced repository rules; a barrel does not hide every sibling file.
5. **Plugin systems** — A module that exports `install(app)` and `uninstall(app)`; the framework wires it via the module's public surface.
6. **Tree-shakeable SDK** — Static usage, accurate side-effect metadata, and build configuration may remove unused implementations. Inspect the resulting bundle rather than inferring removal from export style.
7. **Feature flags as a module** — A single import gives you the typed `flags` object; the underlying source (LaunchDarkly, Statsig) is an internal implementation detail.

## Common Mistakes

| Mistake | Fix |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `export *` from a barrel | Re-export named symbols explicitly; wildcard re-exports can still be tree-shaken, but may obscure ownership, export conflicts and side effects |
| Re-exporting internals "just in case" | Public API is a contract; smaller is better |
| `import * as X from 'X'` when a named import works | Static namespace access can also be optimized; dynamic property access may retain more exports. Inspect the actual production bundle |
| Side effects in module top-level code | Side effects run on import; make them idempotent or move them into an exported function |
| Circular imports | Refactor to a shared module; or defer a dependency when that actually resolves initialization order; a dynamic import alone does not remove a conceptual cycle |
| Mixing default + named exports | Pick one style; mixing makes it hard to know which is canonical |
| `@ts-ignore` on a private cross-module access | If you need it private, the design is wrong — talk to the owner |
| Barrel re-exports that hide circular dependencies | Audit the import graph; barrels can mask cycles |

## Best Practices

1. **Default to ES modules** — Use ESM syntax deliberately; .ts files without module syntax may be scripts depending on moduleDetection.
2. **Small public surface** — Only `export` what consumers need; everything else is private.
3. **Curated package entry points** — Add a barrel where it owns a useful contract; one per directory is not mandatory and can hide cycles.
4. **Named exports over default** — `export function area()` is more refactor-friendly than `export default { area }`.
5. **Make import-time effects deliberate** — use explicit initialization when timing or cleanup needs a caller-owned lifecycle. Required registration and CSS imports can legitimately have effects; declare them accurately to the bundler.
6. **Path aliases for readability** — `@/lib/foo` over `../../../lib/foo`.
7. **Verify removal in your SDK** — Use statically analyzable exports and accurate sideEffects metadata; do not mark required CSS/initialization as side-effect-free.
8. **Cohesive responsibility** — Split independently changing rules; an export count alone does not diagnose coupling.
9. **Document the public API** — A `README.md` per package; or TSDoc on every export.
10. **Lock down barrel re-exports** — `export *` is a footgun; prefer explicit `export { a, b }`.

## Performance Considerations

- ES module imports are static; bundlers can analyze and tree-shake them.
- Top-level code runs once per loaded module instance; expensive initialization should be lazy.
- `import()` is dynamic and returns a promise; useful for code-splitting and lazy loading.
- ESM cycles use live bindings; reading a lexical export before initialization can throw a TDZ ReferenceError. CommonJS may expose partially initialized exports; do not conflate the two.
- Bundlers can split modules into chunks; use dynamic `import()` for route-level code splitting.

## Summary

- The Module pattern encapsulates private state behind a public API.
- ES modules provide module scope and export bindings; TypeScript script/module classification depends on syntax and compiler settings.
- Keep the public surface small; use barrel `index.ts` to curate it; prefer named exports.
- Keep evaluation effects and resource lifetime explicit. Verify tree-shaking on actual production output; module size alone does not establish cohesion.

# Composite Pattern

A directory’s size includes files nested several levels below it. The directory combines its children, while each file contributes its own size. If every caller must check whether a node is a file or directory and walk the tree, that knowledge spreads through the application.

## Definition

**Practical definition:** Composite represents a part-whole hierarchy as recursive objects. Leaves and containers share the operations clients need, and each container delegates those operations to its children.

> **Textbook Definition:** “Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.” — Gamma, Helm, Johnson and Vlissides, *Design Patterns* (1994).

## First Principles

A leaf knows how to contribute to an operation such as `size`; a container combines the contributions of its children. Give both the same `size()` contract and a container can recurse without the caller knowing how deep the tree goes.

That uniformity should apply only to operations both kinds of node can honor. A file has a size, but it cannot add a child. The example therefore shares `Component.size()` and gives child-management methods only to `Container`.

## Follow the size calculation

```typescript
interface Component {
  size(): number;
}

interface Container extends Component {
  add(child: Component): void;
  remove(child: Component): boolean;
}

class FileLeaf implements Component {
  constructor(private readonly bytes: number) {}

  size(): number {
    return this.bytes;
  }
}

class Directory implements Container {
  private readonly children: Component[] = [];

  constructor(readonly name: string) {}

  add(child: Component): void {
    if (child === this || (child instanceof Directory && child.contains(this))) {
      throw new Error('Adding this child would create a cycle');
    }
    if (this.children.includes(child)) {
      throw new Error('Child is already in this directory');
    }
    this.children.push(child);
  }

  remove(child: Component): boolean {
    const index = this.children.indexOf(child);
    if (index < 0) return false;
    this.children.splice(index, 1);
    return true;
  }

  private contains(target: Component): boolean {
    return this.children.some(child =>
      child === target || (child instanceof Directory && child.contains(target))
    );
  }

  size(): number {
    return this.children.reduce((total, child) => total + child.size(), 0);
  }
}

const root = new Directory('root');
const home = new Directory('home');
const user = new Directory('user');

home.add(user);
user.add(new FileLeaf(1_024));
user.add(new FileLeaf(500_000));
root.add(home);
root.add(new FileLeaf(256));

console.log(root.size()); // 501280
```

`root.size()` asks `home` for its size and adds the root config file’s 256 bytes. `home` delegates to `user`, which adds 1,024 and 500,000. The total returns up the same path: 501,280 bytes. Each container owns the aggregation step; the caller invokes one operation on the root. The example assumes nonnegative byte counts whose total fits within `Number.MAX_SAFE_INTEGER`; use `bigint` when larger exact totals are possible.

Syntax trees and nested menus can also fit when a shared operation combines child results. A hierarchy alone does not guarantee a good Composite: DOM nodes, filesystem links and UI elements have operations or relationships that differ by node kind. Actual file-size accounting must also define whether it follows links and how it handles hard links.

## Choose the child-management contract

This example uses the **safe Composite** form: `FileLeaf` implements `Component`, while only `Directory` implements `Container`. A caller can ask either node for its size, but can add children only through a container.

The **transparent Composite** form puts `add`, `remove` and child lookup on the common component interface. That makes more operations callable through one type, but leaves must reject or otherwise define operations that do not apply to them. Use it only when that uniform API is valuable and its unsupported-operation behavior is explicit.

## Decide whether the structure is a tree

`add` rejects a directory added to itself or one of its descendants, and prevents adding the same child twice to one directory. It does not prevent a node from being attached to two different directories. That creates a directed acyclic graph rather than a strict tree; this `size()` counts the shared node once for each path that reaches it.

The cycle guard walks the proposed child’s subtree on every attachment, so building a long chain this way can take O(n²) total time. For a large strict tree, enforce single-parent ownership and keep parent links or an ownership index so attachment can check ancestry in O(h). If shared nodes are intentional, specify whether an aggregate counts each placement or each unique node; a visited-identity set implements the latter, while cycles still need an explicit policy. A strict-tree traversal visits `n` nodes in O(n) time and uses O(h) call-stack space for height `h`. Very deep or untrusted structures may need iterative traversal and cycle validation.

## Choose objects or tagged data

An object-oriented Composite makes it easy to add a new node implementation, but a new operation such as `serialize()` may require changes to every node. A tagged union centralizes operations in functions and can be clearer when the node kinds form a small, controlled set:

```typescript
type Tree =
  | { kind: 'file'; bytes: number }
  | { kind: 'directory'; children: Tree[] };

function size(node: Tree): number {
  if (node.kind === 'file') return node.bytes;
  return node.children.reduce((total, child) => total + size(child), 0);
}
```

TypeScript narrows the union from the `kind` field. Adding a new variant means reviewing each operation that handles the tree. If the node set is stable but operations keep growing, [Visitor](../04-behavioral/30.1.4.10-visitor.md) is another option; it makes the operation set explicit while retaining the object structure.

## Compare nearby patterns

- **Iterator** defines how to traverse a collection; Composite defines the recursive part-whole structure. An iterator can traverse a Composite without exposing child storage.
- **Decorator** wraps one object to add behavior; Composite groups children and delegates an operation across them. Their recursive object shapes can look alike, but the intent differs.

Use Composite when a recursive hierarchy is real and a shared operation simplifies clients. A flat collection, a single parent-child level or a misleading common contract is usually better modeled directly.

## Summary

- Composite lets clients call shared operations on leaves and containers while containers delegate across child objects.
- Keep child-management operations on containers unless leaves can define meaningful behavior for them.
- Decide whether shared children are allowed, how cycles are prevented and whether aggregation counts placements or unique nodes.

# Composite Pattern

> **TL;DR:** Composite composes objects into **tree structures** to represent part-whole hierarchies. The client treats individual objects ("leaves") and compositions ("branches") uniformly through a common interface. Use it for any recursive structure: file systems, UI trees, org charts, ASTs.

<!-- section: Design Patterns | category: Architecture | subcategory: Structural | tags: concept, gof -->

## Definition

The Composite pattern is a structural design pattern that lets you build tree structures of objects and work with them as if they were individual objects.

It's one of the 23 classic GoF patterns. The key insight: **the same interface** is used for both the primitive (leaf) and the composite (branch). The composite holds a collection of children of the same interface — so it can contain leaves AND other composites, recursively.

```text
                ┌──────────────────────────────┐
                │ Component (interface)        │
                │ + operation(): string        │
                │ + add(c: Component)          │
                │ + remove(c: Component)       │
                │ + getChild(i: int): Component│
                └──────────────────────────────┘
                          ▲ ▲
                          │ │                            
              ┌───────────┘ └────────────┐
              │ │                                        
┌───────────────────────────────────────────────────────┐
│ Leaf                  │ │                            │
│ - name: string        │ │                            │
│ + operation(): string │ │                            │
│                       │ │                            │
│                       │ │                            │
└─────────────────────────┘ │ + getChild(i): Component │ 
                                    └──────────────────────────┘
                                              │
                                              │ contains
                                              ▼
                                    ┌──────────────────────────┐
                                    │ Leaf or Composite │
                                    │ (recursion)       │
                                    └──────────────────────────┘
```

## Why Do We Need It?

### Without Composite

```typescript
// BAD: client must distinguish leaf from composite
function print(node: File | Directory, indent: string) {
  if (node instanceof Directory) {
    console.log(indent + node.name + '/');
    for (const child of node.children) {
      // Type check: is it a File or another Directory?
      if (child instanceof Directory) {
        print(child, indent + ' ');
      } else {
        console.log(indent + ' ' + child.name);
      }
    }
  } else {
    console.log(indent + node.name);
  }
}
```

**Problems:**

1. **Type discrimination everywhere** — every operation needs an `instanceof` check
2. **Open-closed violation** — adding a new node type (e.g., Symlink) means editing every traversal
3. **Duplicated traversal** — the same `if/else` appears in `print`, `size`, `delete`, `search`...

### With Composite

```typescript
// GOOD: client doesn't know if node is leaf or composite
function print(node: FileSystemNode, indent: string) {
  console.log(indent + node.name);
  for (const child of node.children) {
    print(child, indent + ' ');
  }
}
```

**Composite makes the client simpler** and the code more extensible — add a `Symlink` class and `print` still works.

## How It Works

1. **Component interface** — declares the common operations (e.g., `operation()`, optionally `add`/`remove`/`getChild`).
2. **Leaf** — implements the interface for primitive objects. No children.
3. **Composite** — implements the interface for compositions. Holds children (a list of `Component`), and delegates operations to them.
4. **Client** — works with `Component` only. Doesn't care if it's a leaf or a composite.

```typescript
// Component interface
interface FileSystemNode {
  name: string;
  size(): number; // common operation
  print(indent?: string): void; // common operation
}

// Leaf
class File implements FileSystemNode {
  constructor(public name: string, private bytes: number) {}
  size() { return this.bytes; }
  print(indent = '') { console.log(`${indent}${this.name} (${this.bytes} bytes)`); }
}

// Composite
class Directory implements FileSystemNode {
  public children: FileSystemNode[] = [];

  constructor(public name: string) {}

  add(node: FileSystemNode) { this.children.push(node); }
  remove(node: FileSystemNode) {
    this.children = this.children.filter(c => c !== node);
  }

  size(): number {
    return this.children.reduce((sum, child) => sum + child.size(), 0);
  }

  print(indent = '') {
    console.log(`${indent}${this.name}/`);
    for (const child of this.children) {
      child.print(indent + ' ');
    }
  }
}

// Usage
const root = new Directory('root');
const home = new Directory('home');
const user = new Directory('user');
home.add(user);
user.add(new File('readme.md', 1024));
user.add(new File('photo.jpg', 500_000));
root.add(home);
root.add(new File('config.json', 256));

root.print();
// root/
// home/
// user/
// readme.md (1024 bytes)
// photo.jpg (500000 bytes)
// config.json (256 bytes)
console.log('Total size:', root.size()); // 501280
```

## Real-World Examples

### 1. File systems (the canonical example)

Every OS file system IS a Composite: files and directories share operations (`size()`, `delete()`, `move()`), and directories contain other files and directories.

### 2. UI component trees

React, Vue, Angular, and the DOM itself are Composites. A `<div>` contains text nodes, other elements, and components. Operations like `mount()`, `unmount()`, `render()` work uniformly.

```typescript
// React-like example
interface Component {
  props: any;
  children: Component[];
  render(): VNode;
}

class LeafComponent implements Component { /* renders itself, no children */ }
class ContainerComponent implements Component {
  children: Component[] = [];
  render() { return <div>{this.children.map(c => c.render())}</div>; }
}
```

### 3. ASTs (Abstract Syntax Trees)

Every parser/compiler builds a Composite. A `BinaryOp` node contains two `Expression` children, each of which might be a `Literal` or another `BinaryOp`. Operations: `evaluate()`, `typecheck()`, `compile()`.

### 4. Organization charts

A `Manager` has `reports` (which are other `Manager`s or `Individual`s). Operations: `totalReports()`, `salaryBudget()`, `findPerson(name)`.

### 5. HTML/XML/JSON DOM

The DOM is a Composite: `Element` has children that are also `Element` or `Text`. `appendChild()`, `removeChild()`, `querySelector()` work on both.

### 6. Menu systems

A `Menu` contains `MenuItem`s and other `Menu`s. Click on a submenu → expands; click on an item → executes action.

### 7. Kubernetes resource trees

A `Deployment` has `Pod`s; a `Pod` has `Container`s. The recursive structure of k8s objects is a Composite.

## When to Use

 **Use Composite when:**

- You need to represent **part-whole hierarchies** of objects
- You want clients to be able to **ignore the difference** between compositions of objects and individual objects
- The structure is **recursive** (a part can contain parts can contain parts)
- You find yourself writing `instanceof` checks to handle leaves vs branches

 **Avoid Composite when:**

- The structure is flat (no recursion)
- The leaf and composite have very different APIs (then inheritance is the wrong abstraction)
- You only have one level (no children, just leaves)
- The class hierarchy is unstable (adding types is expensive — see "Open-Closed Cost" below)

## How It Works in Code

### Component interface with child management

There are two schools of thought:

**1. Declare child operations in the interface (transparent Composite):**

```typescript
interface Graphic {
  draw(): void;
  add(g: Graphic): void; // leaf: throw "not supported"
  remove(g: Graphic): void; // leaf: throw
  getChild(i: number): Graphic; // leaf: throw
}
```

Pro: client is uniform.
Con: leaves have useless methods that throw.

**2. Declare child operations only in Composite (safe Composite):**

```typescript
interface Graphic {
  draw(): void;
}

interface CompositeGraphic extends Graphic {
  add(g: Graphic): void;
  remove(g: Graphic): void;
  getChild(i: number): Graphic;
}
```

Pro: leaves don't have dead methods.
Con: client must know to cast / use `CompositeGraphic` for child management.

Most modern code prefers the **safe Composite** with TypeScript interfaces.

### Functional Composite in TypeScript

```typescript
type FileNode =
  | { type: 'file'; name: string; size: number }
  | { type: 'dir'; name: string; children: FileNode[] };

function totalSize(node: FileNode): number {
  if (node.type === 'file') return node.size;
  return node.children.reduce((sum, child) => sum + totalSize(child), 0);
}
```

This is a tagged-union Composite — TypeScript's pattern matching makes it ergonomic.

### Composite + Visitor

Often, Composite structures are paired with Visitor (see [Visitor](../04-behavioral/30.1.4.10-visitor.md)):

```typescript
interface FileSystemNode {
  accept(visitor: NodeVisitor): void;
}

class File implements FileSystemNode {
  accept(visitor: NodeVisitor) { visitor.visitFile(this); }
}
class Directory implements FileSystemNode {
  accept(visitor: NodeVisitor) { visitor.visitDirectory(this); }
}

interface NodeVisitor {
  visitFile(file: File): void;
  visitDirectory(dir: Directory): void;
}

class SizeCalculator implements NodeVisitor {
  total = 0;
  visitFile(file: File) { this.total += file.bytes; }
  visitDirectory(dir: Directory) {
    for (const child of dir.children) child.accept(this);
  }
}
```

## Comparisons

### Composite vs Decorator

- **Composite** adds structure (recursive aggregation). Focus on "what is contained".
- **Decorator** adds behavior. Focus on "what is wrapped".

Both use recursive composition in code, but intent differs.

### Composite vs Iterator

- **Composite** is a **structure** (tree of objects).
- **Iterator** is a **way to traverse** any collection, including a Composite.

You often pair them: traverse a Composite with an Iterator.

### Composite vs Facade

- **Composite** is recursive and the same interface applies at every level.
- **Facade** is a single level — one simplified interface to a set of unrelated subsystems.

### Composite vs Abstract Factory

- **Abstract Factory** creates a family of products.
- **Composite** structures a family of objects into a tree.

They often appear together: an Abstract Factory creates nodes; a Composite arranges them.

## Code Example: Menu System

```typescript
interface MenuComponent {
  name: string;
  display(indent?: string): void;
}

class MenuItem implements MenuComponent {
  constructor(public name: string, private action: () => void) {}
  display(indent = '') {
    console.log(`${indent}→ ${this.name}`);
  }
}

class Menu implements MenuComponent {
  public items: MenuComponent[] = [];

  constructor(public name: string) {}

  add(item: MenuComponent) { this.items.push(item); }
  remove(item: MenuComponent) {
    this.items = this.items.filter(i => i !== item);
  }

  display(indent = '') {
    console.log(`${indent}▼ ${this.name}`);
    for (const item of this.items) {
      item.display(indent + ' ');
    }
  }
}

// Usage
const mainMenu = new Menu('Main');
const fileMenu = new Menu('File');
const editMenu = new Menu('Edit');

fileMenu.add(new MenuItem('New', () => {}));
fileMenu.add(new MenuItem('Open', () => {}));
fileMenu.add(new MenuItem('Save', () => {}));

editMenu.add(new MenuItem('Cut', () => {}));
editMenu.add(new MenuItem('Copy', () => {}));

mainMenu.add(fileMenu);
mainMenu.add(editMenu);
mainMenu.add(new MenuItem('Quit', () => {}));

mainMenu.display();
// ▼ Main
// ▼ File
// → New
// → Open
// → Save
// ▼ Edit
// → Cut
// → Copy
// → Quit
```

## Common Pitfalls

### 1. **Type-checking leaks**

If the client still has to do `instanceof Composite`, you've leaked the abstraction. Either:
- Add a generic `operation` on the Component interface that works for both
- Use a tagged union + pattern matching in TypeScript

### 2. **Mutual references / cycles**

A directory containing itself (or a chain) breaks traversal. Validate on `add()` or use weak references.

### 3. **Memory leaks from holding child references**

A Composite holding a large child prevents GC. Use weak references for child lists if children have independent lifecycles.

### 4. **Trying to make leaves support `add()`**

Don't. Either throw a clear "not supported" error (transparent Composite) or split the interface (safe Composite). Don't silently no-op.

### 5. **Over-engineering a 2-level hierarchy**

If you have `Department` with `Employee`s and no sub-departments, you don't need a Composite — a `Department[]` is enough.

## Best Practices

1. **Prefer safe Composite** in TypeScript — separate `Graphic` and `CompositeGraphic` interfaces.
2. **Combine with Iterator** for clean traversal of the tree.
3. **Combine with Visitor** for operations that depend on the concrete node type.
4. **Validate `add()`** to prevent cycles.
5. **Use the Composite interface** in client code, not the concrete classes.
6. **Document the recursion** — every Composite method that recurses on children should say so.

## Summary

Composite is the pattern for **recursive tree structures**. It's everywhere in software — file systems, UI trees, ASTs, organization charts, and DOM. The core idea is to make leaves and branches share an interface so the client can treat them uniformly. Modern code often expresses this as a tagged union + recursive function.

**Interview-ready one-liner:** "Composite composes objects into tree structures; the same interface applies to leaves and branches so clients can treat them uniformly — used for file systems, UI trees, and ASTs."

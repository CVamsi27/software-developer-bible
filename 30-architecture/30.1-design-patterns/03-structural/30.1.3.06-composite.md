# Composite Pattern


## Definition

The Composite pattern is a structural design pattern that lets you build tree structures of objects and work with them as if they were individual objects.

> **Textbook Definition:** Composite is a structural pattern that represents part-whole hierarchies as trees whose leaf and composite objects share a contract, enabling uniform operations over individual elements and groups.

It's one of the 23 classic GoF patterns. The key insight: **the same interface** is used for both the primitive (leaf) and the composite (branch). The composite holds a collection of children of the same interface — so it can contain leaves AND other composites, recursively.

```text
client uses Component.operation()
        ├─ leaf performs its own operation
        └─ container calls operation() on each child
                                    └─ child may be another container
```

## First Principles

A total over a hierarchy needs two behaviors: a primitive contributes its own amount, while a group combines the contributions of its children. If each client distinguishes every node kind and repeats traversal, adding a node kind affects those clients.

Give the common operation a contract that both primitive and group can satisfy. A group calls that operation on each child, allowing nested groups to recurse naturally. Child management is a different capability: a leaf can have a size without accepting another child. Separating those capabilities keeps callers from demanding an impossible operation from a leaf.

## Why Do We Need It?

### Without Composite

```typescript
// BAD: client must distinguish leaf from composite
function print(node: FileLeaf | Directory, indent: string) {
  if (node instanceof Directory) {
    console.log(indent + node.name + '/');
    for (const child of node.children) {
      // Type check: is it a FileLeaf or another Directory?
      if (child instanceof Directory) {
        print(child, indent + ' ');
      } else {
        console.log(indent + ' ' + child.name);
      }
    }
  } else {
    console.log(indent + node.name);
  }
}
```

**Problems:**

1. **Type discrimination everywhere** — every operation needs an `instanceof` check
2. **Open-closed violation** — adding a new node type (e.g., Symlink) means editing every traversal
3. **Duplicated traversal** — the same `if/else` appears in `print`, `size`, `delete`, `search`...

### With Composite

```typescript
// GOOD: client doesn't know if node is leaf or composite
function print(node: FileSystemNode, indent: string) {
  node.print(indent); // common operation delegates recursion to the container
}
```

**Composite makes this client simpler** when every node honors `print`. A symbolic link needs a policy about following its target, broken links, and cycles; adding its class alone does not settle those semantics. The preceding before/after snippets are structural sketches whose types are defined in the example below.

## How It Works

1. **Component interface** — declares the common operations (e.g., `operation()`, optionally `add`/`remove`/`getChild`).
2. **Leaf** — implements the interface for primitive objects. No children.
3. **Composite** — implements the interface for compositions. Holds children (a list of `Component`), and delegates operations to them.
4. **Client** — works with `Component` only. Doesn't care if it's a leaf or a composite.

```typescript
// Component interface
interface FileSystemNode {
  name: string;
  size(): number; // common operation
  print(indent?: string): void; // common operation
}

// Leaf
class FileLeaf implements FileSystemNode {
  constructor(public name: string, private bytes: number) {}
  size() { return this.bytes; }
  print(indent = '') { console.log(`${indent}${this.name} (${this.bytes} bytes)`); }
}

// Composite
class Directory implements FileSystemNode {
  private children: FileSystemNode[] = [];

  constructor(public name: string) {}

  add(node: FileSystemNode): void {
    if (node === this || (node instanceof Directory && node.contains(this))) {
      throw new Error('Cycle would be created');
    }
    if (this.children.includes(node)) throw new Error('Duplicate child');
    this.children.push(node);
  }
  private contains(target: FileSystemNode): boolean {
    return this.children.some(child => child === target ||
      (child instanceof Directory && child.contains(target)));
  }
  getChildren(): readonly FileSystemNode[] { return [...this.children]; }
  remove(node: FileSystemNode) {
    this.children = this.children.filter(c => c !== node);
  }

  size(): number {
    return this.children.reduce((sum, child) => sum + child.size(), 0);
  }

  print(indent = '') {
    console.log(`${indent}${this.name}/`);
    for (const child of this.children) {
      child.print(indent + ' ');
    }
  }
}

// Usage
const root = new Directory('root');
const home = new Directory('home');
const user = new Directory('user');
home.add(user);
user.add(new FileLeaf('readme.md', 1024));
user.add(new FileLeaf('photo.jpg', 500_000));
root.add(home);
root.add(new FileLeaf('config.json', 256));

root.print();
// root/
// home/
// user/
// readme.md (1024 bytes)
// photo.jpg (500000 bytes)
// config.json (256 bytes)
console.log('Total size:', root.size()); // 501280
```

`root.size` asks `home` and `config.json` for their sizes. `home` asks `user`; `user` adds 1,024 and 500,000; the result returns to root, which adds 256, yielding 501,280. `print` follows the same nested delegation while carrying indentation. The output contains one extra leading space at each depth.

`add` rejects self/ancestor cycles and duplicate children for these supplied classes. It does not enforce one parent across all containers, so a deliberately shared leaf can be counted once per placement. Decide whether that is allowed, or enforce exclusive parent ownership for a strict tree. Deep structures may also exceed a recursive call stack; an explicit traversal stack is an alternative. This model does not read an actual filesystem.

## Real-World Examples

### 1. File systems (the canonical example)

Files and directories provide a familiar hierarchy for a Composite example. Real filesystems have distinct APIs and links that can introduce graph edges; the analogy is not proof of one uniform GoF interface.

### 2. UI component trees

A custom UI group can expose the same `render` operation as a leaf and delegate to children. Real frameworks have differing element, component, lifecycle, and text-node APIs; a hierarchy alone is not evidence that every operation is uniformly valid. The DOM qualifications below are consequential.



### 3. ASTs (Abstract Syntax Trees)

An expression tree can illustrate recursive structure. A `BinaryOp` node contains two `Expression` children, each of which might be a `Literal` or another `BinaryOp`. Operations: `evaluate()`, `typecheck()`, `compile()`.

### 4. Organization charts

A `Manager` has `reports` (which are other `Manager`s or `Individual`s). Operations: `totalReports()`, `salaryBudget()`, `findPerson(name)`.

### 5. HTML/XML/JSON DOM

The DOM offers a node hierarchy and some shared Node operations. Text nodes cannot accept children and do not expose querySelector; Element/Document APIs differ. Shared structure does not make every operation uniformly valid.

### 6. Menu systems

A `Menu` contains `MenuItem`s and other `Menu`s. Click on a submenu → expands; click on an item → executes action.

### 7. Kubernetes resource trees

Kubernetes has ownership references such as Deployment → ReplicaSet → Pod and Pod specs describe containers. These resources have distinct APIs; this is an ownership analogy, not necessarily one recursive Component interface.

## When to Use

 **Use Composite when:**

- You need to represent **part-whole hierarchies** of objects
- You want clients to be able to **ignore the difference** between compositions of objects and individual objects
- The structure is **recursive** (a part can contain parts can contain parts)
- You find yourself writing `instanceof` checks to handle leaves vs branches

 **Avoid Composite when:**

- The structure is flat (no recursion)
- The leaf and composite have very different APIs (then inheritance is the wrong abstraction)
- You only have one level (no children, just leaves)
- The common contract would hide consequential differences between node kinds

## How It Works in Code

### Component interface with child management

There are two schools of thought:

**1. Declare child operations in the interface (transparent Composite):**

```typescript
interface Graphic {
  draw(): void;
  add(g: Graphic): void; // leaf: throw "not supported"
  remove(g: Graphic): void; // leaf: throw
  getChild(i: number): Graphic; // leaf: throw
}
```

Pro: client is uniform.
Con: leaves have useless methods that throw.

**2. Declare child operations only in Composite (safe Composite):**

```typescript
interface Graphic {
  draw(): void;
}

interface CompositeGraphic extends Graphic {
  add(g: Graphic): void;
  remove(g: Graphic): void;
  getChild(i: number): Graphic;
}
```

Pro: leaves don't have dead methods.
Con: client must know to cast / use `CompositeGraphic` for child management.

A safe Composite can let construction code accept `CompositeGraphic` while rendering accepts `Graphic`; no unsafe cast is required. In a transparent interface, unsupported leaf operations must be part of the documented contract rather than surprising callers.

### Functional Composite in TypeScript

```typescript
type FileNode =
  | { type: 'file'; name: string; size: number }
  | { type: 'dir'; name: string; children: FileNode[] };

function totalSize(node: FileNode): number {
  if (node.type === 'file') return node.size;
  return node.children.reduce((sum, child) => sum + totalSize(child), 0);
}
```

This is a recursive-data alternative using a discriminant field and TypeScript narrowing. Operations live in functions that handle variants rather than methods dispatched on objects. Adding a variant can require editing those functions; that tradeoff differs from the object-oriented example.

### Composite + Visitor

Visitor is useful when an operation depends on concrete node kinds. A node's `accept` operation dispatches to the corresponding visitor method, and a directory visitor chooses whether to traverse children. Keep one traversal owner so both node and visitor do not visit every child twice. See [Visitor](../04-behavioral/30.1.4.10-visitor.md) for the canonical implementation; it is a separate contract extension, not another set of duplicate class declarations to append to this example.



## Comparisons

### Composite vs Decorator

- **Composite** adds structure (recursive aggregation). Focus on "what is contained".
- **Decorator** adds behavior. Focus on "what is wrapped".

Both use recursive composition in code, but intent differs.

### Composite vs Iterator

- **Composite** is a **structure** (tree of objects).
- **Iterator** is a **way to traverse** any collection, including a Composite.

You often pair them: traverse a Composite with an Iterator.

### Composite vs Facade

- **Composite** is recursive and the same interface applies at every level.
- **Facade** is a single level — one simplified interface to a set of unrelated subsystems.

### Composite vs Abstract Factory

- **Abstract Factory** creates a family of products.
- **Composite** structures a family of objects into a tree.

They often appear together: an Abstract Factory creates nodes; a Composite arranges them.

## Code Example: Menu System

```typescript
interface MenuComponent {
  name: string;
  display(indent?: string): void;
}

class MenuItem implements MenuComponent {
  constructor(public name: string, private action: () => void) {}
  display(indent = '') {
    console.log(`${indent}→ ${this.name}`);
  }
  activate(): void { this.action(); }
}

class Menu implements MenuComponent {
  public items: MenuComponent[] = [];

  constructor(public name: string) {}

  add(item: MenuComponent) { this.items.push(item); }
  remove(item: MenuComponent) {
    this.items = this.items.filter(i => i !== item);
  }

  display(indent = '') {
    console.log(`${indent}▼ ${this.name}`);
    for (const item of this.items) {
      item.display(indent + ' ');
    }
  }
}

// Usage
const mainMenu = new Menu('Main');
const fileMenu = new Menu('File');
const editMenu = new Menu('Edit');

fileMenu.add(new MenuItem('New', () => {}));
fileMenu.add(new MenuItem('Open', () => {}));
fileMenu.add(new MenuItem('Save', () => {}));

editMenu.add(new MenuItem('Cut', () => {}));
editMenu.add(new MenuItem('Copy', () => {}));

mainMenu.add(fileMenu);
mainMenu.add(editMenu);
const quit = new MenuItem('Quit', () => console.log('Quit requested'));
mainMenu.add(quit);

mainMenu.display();
// ▼ Main
// ▼ File
// → New
// → Open
// → Save
// ▼ Edit
// → Cut
// → Copy
// → Quit
```

`display` traverses the menu but does not execute actions. Selection can call `quit.activate()` explicitly. Nested menus in this short example assume an acyclic construction; the earlier directory example demonstrates cycle validation.

## Common Pitfalls

### 1. **Type-checking leaks**

If every common operation needs repeated type tests, reconsider the shared contract. Child-management operations can legitimately require the composite-specific interface. Either:
- Add a generic `operation` on the Component interface that works for both
- Use a tagged union + pattern matching in TypeScript

### 2. **Mutual references / cycles**

A directory containing itself (or a chain) breaks traversal. Validate on add() or use a traversal policy with visited identities when graph edges are intentional. Weak references do not prevent cycles.

### 3. **Memory leaks from holding child references**

A reachable Composite retains its strongly referenced children; that is often required ownership, not a leak by itself. If the composite owns its children, strong references are intentional. Release removed subtrees when their ownership ends; weak child references would make the structure depend on garbage collection.

### 4. **Trying to make leaves support `add()`**

Don't. Either throw a clear "not supported" error (transparent Composite) or split the interface (safe Composite). Don't silently no-op.

### 5. **Over-engineering a 2-level hierarchy**

If you have `Department` with `Employee`s and no sub-departments, you don't need a Composite — a department with an employee collection can be enough.

## Best Practices

1. **Prefer safe Composite** in TypeScript — separate `Graphic` and `CompositeGraphic` interfaces.
2. **Combine with Iterator** for clean traversal of the tree.
3. **Combine with Visitor** for operations that depend on the concrete node type.
4. **Validate `add()`** to prevent cycles.
5. **Use the Composite interface** in client code, not the concrete classes.
6. **Document the recursion** — every Composite method that recurses on children should say so.

## Summary

Composite is the pattern for **recursive tree structures**. It's everywhere in software — file systems, UI trees, ASTs, organization charts, and DOM. The core idea is to make leaves and branches share an interface so the client can treat them uniformly. Modern code often expresses this as a tagged union + recursive function.

**Interview-ready one-liner:** "Composite composes objects into tree structures; the same interface applies to leaves and branches so clients can treat them uniformly — used for file systems, UI trees, and ASTs."

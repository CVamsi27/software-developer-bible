# Bridge Pattern

A drawing tool supports circles and squares, and it can render each as vector or raster output. If every shape class hardcodes a renderer, each new shape must be paired with every renderer. Bridge separates those two decisions and connects them through composition.

## Definition

**Practical definition:** Bridge separates a client-facing abstraction from the implementations that perform its lower-level work. The abstraction holds an implementation through a contract, so each side can gain variants without a subclass for every pairing.

> **Textbook Definition:** “Decouple an abstraction from its implementation so that the two can vary independently.” — Gamma, Helm, Johnson and Vlissides, *Design Patterns* (1994).

## First Principles

Let one hierarchy describe **what** the client asks for and another describe **how** that request is carried out. A shape owns its geometry and delegates drawing to a renderer. The client can combine a circle with a vector renderer or a raster renderer without defining `VectorCircle` and `RasterCircle` subclasses.

Bridge removes the need to model every combination as a class. It does not make both contracts immune to change: if the renderer interface has one method per shape, adding a new shape still changes that interface and every renderer.

## Follow one shape through its renderer

```typescript
interface Renderer {
  renderCircle(radius: number): string;
  renderSquare(side: number): string;
}

class VectorRenderer implements Renderer {
  renderCircle(radius: number): string {
    return `vector circle, radius=${radius}`;
  }
  renderSquare(side: number): string {
    return `vector square, side=${side}`;
  }
}

class RasterRenderer implements Renderer {
  renderCircle(radius: number): string {
    return `raster circle, radius=${radius}`;
  }
  renderSquare(side: number): string {
    return `raster square, side=${side}`;
  }
}

abstract class Shape {
  constructor(protected readonly renderer: Renderer) {}
  abstract draw(): string;
}

class Circle extends Shape {
  constructor(renderer: Renderer, private readonly radius: number) {
    super(renderer);
  }
  draw(): string {
    return this.renderer.renderCircle(this.radius);
  }
}

class Square extends Shape {
  constructor(renderer: Renderer, private readonly side: number) {
    super(renderer);
  }
  draw(): string {
    return this.renderer.renderSquare(this.side);
  }
}

const vectorCircle = new Circle(new VectorRenderer(), 10);
const rasterCircle = new Circle(new RasterRenderer(), 10);
console.log(vectorCircle.draw()); // vector circle, radius=10
console.log(rasterCircle.draw()); // raster circle, radius=10
```

`Circle` and `Square` are refined abstractions; `Renderer` is the implementation contract; `VectorRenderer` and `RasterRenderer` are concrete implementations. The strings stand in for drawing work. In a real renderer, the contract would carry geometry or drawing commands and define errors, resource lifetime and output ownership.

For two shapes and two renderers, pair-specific inheritance needs four concrete combination classes; Bridge also has four concrete variant classes (two shape subclasses and two renderers), so the small example does not reduce the count. With three shapes and three renderers, the combinations would need nine classes, while Bridge needs six concrete variants. The advantage appears as both independent axes grow and the combinations are meaningful.

Adding `Triangle` to this interface requires a `renderTriangle` operation and an implementation in every renderer. Passing a general path or geometry object could stabilize the method set, but then that geometry contract must express the shapes and features renderers need. Bridge moves the coupling to an explicit boundary; it does not erase it.

## Choose Bridge when both axes matter

Choose Bridge when the abstraction and implementation have separate reasons to change—for example, notification policy versus transport channel—and the supported combinations should be selected without subclassing every pair. A composition root or dependency-injection container can choose the implementation; a container is optional.

A repository with two storage backends or a payment service with several providers is not automatically Bridge. It may be Strategy, Adapter or ordinary dependency injection. Look for both sides: a varying abstraction hierarchy, a varying implementation hierarchy, and delegation between them.

| Pattern | The decision it separates | Typical signal |
| ------------ | ------------------------------------------------------------------ | -------------------------------------------------------------- |
| **Bridge** | Client-facing abstraction from a separately varying implementation | Two axes need independent extension |
| **Strategy** | One algorithm or policy from its context | The context stays the same while the selected behavior changes |
| **Adapter** | An existing interface from the interface a client requires | One side must be translated for compatibility |

Bridge and Abstract Factory can work together: the factory can create a compatible family of implementations for an abstraction. The factory creates objects; Bridge defines how the abstraction delegates to its implementation.

## Summary

- Bridge connects an abstraction hierarchy to an implementation hierarchy through composition.
- It avoids a subclass for every pairing when both axes vary independently; at small sizes, it may add structure without reducing class count.
- The shared implementation contract remains a coupling point, so choose its operations and payloads deliberately.

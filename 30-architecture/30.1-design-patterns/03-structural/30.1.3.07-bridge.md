# Bridge Pattern


## Definition

The Bridge pattern is a structural design pattern that lets you split a large class or a set of closely related classes into two separate hierarchies — **abstraction** and **implementation** — which can be developed independently of each other.

It's one of the 23 classic GoF patterns. The key insight: instead of inheritance binding abstraction to implementation, **composition** is used at runtime — the abstraction holds a reference to an implementation object.

```text
         Abstraction Implementor
       ┌──────────────────┐ ┌──────────────────┐
       │ - impl: Implementor│ ────────────►    │ + operationImpl() │
       │ + operation()                                          │ └──────────────────┘
       └──────────────────┘ ▲
                ▲ │
                │ extends ┌────────────┴────────────┐
                │ │ │
       ┌────────────────────────────────────────────────────────┐ ┌──────────────┐ ┌──────────────┐
       │ RefinedAbstraction│ │ ConcreteImplA│ │ ConcreteImplB   │
       └────────────────────────────────────────────────────────┘ └──────────────┘ └──────────────┘
```

## First Principles

Bridge splits one axis of variation from another:

1. **Inheritance multiplies**: Shapes × Renderers as class hierarchy = M×N classes; bridge composes them (Shape *has* Renderer) = M+N. The pattern is the answer to class explosion from two independent dimensions.
2. **The discipline is spotting the axes early** — "shape" and "how to draw" vary independently; coupling them makes every combination a permanent class.
3. **Two variation axes are the signal.** Dependency injection can supply the implementation, but not every injected interface is a Bridge; the intent is independent abstraction and implementation evolution.

## Why Do We Need It?

### The "Cartesian product" problem

Imagine a drawing app. You have:
- **Shapes**: Circle, Square, Triangle
- **Renderers**: Vector, Raster, SVG

If you use inheritance to combine them, you get:
- `VectorCircle`, `VectorSquare`, `VectorTriangle`
- `RasterCircle`, `RasterSquare`, `RasterTriangle`
- `SVGCircle`, `SVGSquare`, `SVGTriangle`

**9 classes** for a 3×3 problem. Add a 4th shape or 4th renderer → 12 or 16 classes. This is class explosion.

### The Bridge solution

Split into 2 hierarchies:

**Abstraction hierarchy** (the "what" — shape API):
- `Shape` (abstract)
- `Circle extends Shape`
- `Square extends Shape`

**Implementation hierarchy** (the "how" — actual rendering):
- `Renderer` (interface)
- `VectorRenderer`
- `RasterRenderer`
- `SVGRenderer`

`Shape` holds a reference to `Renderer`. The abstraction calls `impl.renderCircle(radius)`, etc.

The simplified count is three concrete shape choices plus three concrete renderer choices, excluding their shared bases/interfaces. In this particular API, adding a new shape operation also changes the Renderer contract and its implementations.

```typescript
// Implementation side
interface Renderer {
  renderCircle(radius: number): string;
  renderSquare(side: number): string;
}

class VectorRenderer implements Renderer {
  renderCircle(r: number) { return `Drawing circle as vectors, r=${r}`; }
  renderSquare(s: number) { return `Drawing square as vectors, side=${s}`; }
}

class RasterRenderer implements Renderer {
  renderCircle(r: number) { return `Drawing circle as pixels, r=${r}`; }
  renderSquare(s: number) { return `Drawing square as pixels, side=${s}`; }
}

// Abstraction side
abstract class Shape {
  constructor(protected renderer: Renderer) {}
  abstract draw(): string;
}

class Circle extends Shape {
  constructor(renderer: Renderer, private radius: number) { super(renderer); }
  draw() { return this.renderer.renderCircle(this.radius); }
}

class Square extends Shape {
  constructor(renderer: Renderer, private side: number) { super(renderer); }
  draw() { return this.renderer.renderSquare(this.side); }
}

// Usage
const vector = new VectorRenderer();
const raster = new RasterRenderer();

const c1 = new Circle(vector, 10);
const c2 = new Circle(raster, 10);
c1.draw(); // "Drawing circle as vectors, r=10"
c2.draw(); // "Drawing circle as pixels, r=10"
```

Adding a `Triangle` shape requires editing `Renderer` to add `renderTriangle` (one change in 4 files, not creating 3 new classes).

## How It Works

1. **Abstraction** — the high-level interface the client uses. Holds a reference to an Implementor.
2. **Refined Abstraction** — extends the Abstraction with more specific behavior.
3. **Implementor** — declares the interface for implementation classes (the "primitive operations").
4. **Concrete Implementor** — implements the Implementor interface for a specific platform/format/variant.

The Abstraction delegates work to the Implementor. Both can vary independently.

```text
Client
  │
  ▼
Abstraction ◄── extends ── RefinedAbstraction
  │ (holds)
  ▼
Implementor ◄── implements ── ConcreteImplementorA
                          └── ConcreteImplementorB
```

## Real-World Examples

### 1. JDBC (Java Database Connectivity)

JDBC illustrates separating an application-facing API from database-specific implementations:

- **Abstraction**: `java.sql.Connection`, `Statement`, `ResultSet` (the API Java code uses)
- **Implementor**: JDBC driver interface (`java.sql.Driver`)
- **Concrete Implementors**: PostgreSQL JDBC driver, MySQL JDBC driver, Oracle JDBC driver

Your app code uses `Connection` without knowing which DB. The driver is chosen at deploy time. A compatible driver can change the database implementation, but dialect, feature and transaction differences may still require application changes.

### 2. Cross-platform UI toolkits

A cross-platform toolkit can be modeled with these roles:

- **Abstraction**: `Button`, `Dialog`, `Window` (the API)
- **Implementor**: `WindowSystem` interface (`createButton`, `createDialog`)
- **Concrete Implementors**: `Win32WindowSystem`, `CocoaWindowSystem`, `X11WindowSystem`

The button code (`button.setText(...)`) is identical; the platform-specific rendering is in the WindowSystem.

### 3. Device drivers

- **Abstraction**: `Printer` (with `print()` method)
- **Implementor**: `PrinterDriver` (with `sendBytes()`)
- **Concrete Implementors**: `HPDriver`, `CanonDriver`, `EpsonDriver`

### 4. Payment processing (modern)

- **Abstraction**: `PaymentProcessor` (with `charge(amount)`, `refund(...)`)
- **Implementor**: `PaymentGateway` (with `submitTransaction(...)`)
- **Concrete Implementors**: `StripeGateway`, `PayPalGateway`, `BraintreeGateway`

### 5. Persistence layer (common in DDD)

- **Abstraction**: `UserRepository` (with `findById`, `save`, `delete`)
- **Implementor**: `UserStore` (with `query`, `persist`, `remove`)
- **Concrete Implementors**: `PostgresUserStore`, `MongoUserStore`, `InMemoryUserStore`

### 6. Logger abstractions

- **Abstraction**: `Logger` (with `log(message, level)`)
- **Implementor**: `LogAppender` (with `write(message)`)
- **Concrete Implementors**: `ConsoleAppender`, `FileAppender`, `ElasticsearchAppender`

## When to Use

 **Use Bridge when:**

- You want to **avoid a permanent binding** between an abstraction and its implementation (e.g., the implementation must be selected at runtime)
- Both the abstraction and the implementation should be **extensible by subclassing**
- Changes in the implementation should not impact clients (decoupling)
- You have a **Cartesian product** of concerns (3 shapes × 4 renderers = 12, but Bridge reduces to 7)
- You want to **share an implementation** among multiple objects (reference counting, etc.)

 **Avoid Bridge when:**

- You have only one implementation and no need for an independent boundary (a direct object or function may suffice)
- There is no second independent variation axis (a Strategy or simpler composition may suffice)
- The class hierarchy is flat (no parallel hierarchies)
- The 2 hierarchies are tightly coupled in design (Bridge won't help)

## How It Works in Code

### With abstract classes (TypeScript)

```typescript
abstract class Shape {
  constructor(protected renderer: Renderer) {}
  abstract draw(): string;
  // common ops use the renderer
  resize(factor: number): void {
    // could call renderer here
  }
}

class Circle extends Shape {
  constructor(renderer: Renderer, public radius: number) { super(renderer); }
  draw() { return this.renderer.renderCircle(this.radius); }
}
```

### Functional Bridge (less common, sometimes nicer)

```typescript
type Renderer = {
  renderCircle: (r: number) => string;
  renderSquare: (s: number) => string;
};

type Shape = (renderer: Renderer, ...args: any[]) => string;

const drawCircle = (renderer: Renderer, radius: number) =>
  renderer.renderCircle(radius);
```

### Bridge with DI (NestJS-style)

```typescript
// Abstraction
export class PaymentProcessor {
  constructor(private gateway: PaymentGateway) {}
  charge(amount: number) { return this.gateway.submit({ amount }); }
}

// Implementor
export abstract class PaymentGateway {
  abstract submit(payload: any): Promise<TransactionResult>;
}

// Concrete implementor
@Injectable()
export class StripeGateway extends PaymentGateway {
  async submit(payload: any) { /* Stripe API call */ }
}

// Module
@Module({
  providers: [
    { provide: PaymentGateway, useClass: StripeGateway },
    PaymentProcessor,
  ],
})
export class PaymentModule {}
```

## Comparisons

### Bridge vs Adapter

- **Bridge** is designed up-front to decouple abstraction from implementation. Both sides can vary independently.
- **Adapter** is a fix-up pattern — you have existing incompatible interfaces and you adapt one to the other.

Both use composition, but intent differs: Bridge separates variation axes; Adapter translates an existing interface. Either may be introduced during refactoring.

### Bridge vs Strategy

- **Strategy** changes behavior (one dimension). The client picks a strategy.
- **Bridge** decouples two parallel hierarchies (two dimensions). The abstraction is the API; the implementor is the "platform."

| Property | Strategy | Bridge |
| -- | ---------- | -------- |
| **Dimensions** | 1 | 2 |
| **Hierarchy on the impl side** | Usually no parallel hierarchy | Parallel hierarchy (Implementor has its own subclasses) |
| **When chosen** | Often runtime | Often at construction (DI) |

### Bridge vs Abstract Factory

- **Abstract Factory** creates a family of related objects.
- **Bridge** decouples one abstraction from its implementation.

They can compose: an Abstract Factory creates matching Bridge implementors.

### Bridge vs Decorator

- **Bridge** is structural — separates what from how.
- **Decorator** is another structural pattern — it adds responsibilities through wrapping rather than separating two variation axes.

## Code Example: Multi-Platform Notification System

```typescript
// Implementor
interface NotificationSender {
  send(to: string, message: string): Promise<boolean>;
}

class EmailSender implements NotificationSender {
  async send(to: string, message: string) {
    console.log(`Email to ${to}: ${message}`);
    return true;
  }
}

class SMSSender implements NotificationSender {
  async send(to: string, message: string) {
    console.log(`SMS to ${to}: ${message}`);
    return true;
  }
}

class PushSender implements NotificationSender {
  async send(to: string, message: string) {
    console.log(`Push to ${to}: ${message}`);
    return true;
  }
}

// Abstraction
abstract class Notification {
  constructor(protected sender: NotificationSender) {}
  abstract notify(to: string, message: string): Promise<boolean>;
}

class UrgentNotification extends Notification {
  async notify(to: string, message: string) {
    console.log('[URGENT]');
    return this.sender.send(to, `[URGENT] ${message}`);
  }
}

class MarketingNotification extends Notification {
  async notify(to: string, message: string) {
    console.log('[Marketing]');
    return this.sender.send(to, message);
  }
}

// Usage
const email = new EmailSender();
const sms = new SMSSender();
const push = new PushSender();

const urgentSms = new UrgentNotification(sms);
await urgentSms.notify('+1234', 'Server down!'); // [URGENT] SMS to +1234: [URGENT] Server down!

const marketingPush = new MarketingNotification(push);
await marketingPush.notify('user-123', 'New feature!'); // [Marketing] Push to user-123: New feature!
```

Total: 3 senders + 2 notification types = 5 classes. Without Bridge: 2 × 3 = 6 classes for each combination.

## Common Pitfalls

### 1. **Confusing Bridge with Strategy**

If you only have one dimension of variation, you want Strategy, not Bridge. Bridge requires two parallel hierarchies.

### 2. **Tightly coupled API**

If every method in the Abstraction maps 1:1 to a method in the Implementor, you might be over-bridging. The Implementor should expose **primitive** operations; the Abstraction composes them into **higher-level** operations.

### 3. **Underestimating the refactor cost**

If you have an existing class explosion, refactoring to Bridge is a major change. Do it at design time, or accept the cost.

### 4. **Not using DI**

Bridge works best with DI — bind the Implementor at composition root (or via DI container). Otherwise you hardcode the binding.

## Best Practices

1. **Identify the dimensions** — if you have 2 independent dimensions, Bridge is the answer.
2. **Keep the Implementor interface small** — primitive ops only; let the Abstraction compose.
3. **Use composition, not inheritance** — the Abstraction HAS-A Implementor.
4. **Inject via DI** — the Implementor choice should be configurable.
5. **Pair with Abstract Factory** when there are multiple coordinated Implementors.

## Summary

Bridge solves the **Cartesian product class explosion** by separating abstraction from implementation into two independent hierarchies. It can be designed initially or introduced by refactoring when independent variation becomes clear.

**Interview-ready one-liner:** "Bridge decouples an abstraction from its implementation so they can vary independently — instead of 3 shapes × 4 renderers = 12 classes, you get 3 + 4 = 7 with composition."

# Flyweight Pattern


## Definition

The Flyweight pattern is a structural design pattern that lets you fit more objects into the available amount of RAM by sharing **common parts** of state between multiple objects, instead of keeping all the data in each object.

It's one of the 23 GoF patterns. The core trick: **separate intrinsic state** (shared, stored in the flyweight) **from extrinsic state** (unique per object, passed in by the client).

```text
┌──────────────────────────────────────────────────────────┐
│ Flyweight                                                │
│ - intrinsicState: shared data (e.g., the glyph bitmap)   │
│ + operation(extrinsicState: per-call data): void         │
└──────────────────────────────────────────────────────────┘
            ▲ ▲
            │ │
┌────────────────────┐ ┌────────────────────────┐
│ ConcreteFlyweight │ │ UnsharedFlyweight │
│ - shared intrinsic                      │ │ - all unique │
│ + operation() │ │ + operation()         │
└────────────────────┘ └────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│ FlyweightFactory                                         │
│ - pool: Map<key, Flyweight>                              │
│ + getFlyweight(key): Flyweight (returns shared one)      │
└──────────────────────────────────────────────────────────┘
```

## First Principles

Flyweight is sharing as a data structure:

1. **When thousands of objects share most of their state, split intrinsic (shared) from extrinsic (per-context)** — store the shared part once, pass the rest as parameters. The memory math is the entire justification.
2. **Identity is the cost**: shared flyweights break object-identity assumptions — `a === b` for two "different" glyphs. Everything downstream (locking, mutation) must respect that sharing.
3. **Engine sharing does not replace payload sharing.** String representation and object-shape optimizations can reduce some costs, but do not deduplicate arbitrary textures or application state. Measure the actual repeated payload.

## Intrinsic vs Extrinsic State

The key concept:

- **Intrinsic state**: data that's **the same across many objects**, stored in the flyweight. Independent of context.
- **Extrinsic state**: data that's **unique per object** (position, color, size for THIS instance), passed in by the client.

```typescript
// Tree in a forest — naive approach
class Tree {
  constructor(
    public x: number, // unique per tree
    public y: number, // unique per tree
    public age: number, // unique per tree
    public color: string, // shared across same species
    public texture: ImageData, // shared across same species
  ) {}
}

const trees = Array(1_000_000).fill(0).map(() =>
  new Tree(/* ... each tree has its own color and texture object */)
);
// 1M trees × (color string + texture ImageData) = a LOT of memory
```

```typescript
// Flyweight approach
class TreeType { // The flyweight — shared per species
  constructor(
    public color: string,
    public texture: ImageData,
  ) {}
  draw(canvas: Canvas, x: number, y: number) { /* draws using intrinsic + extrinsic */ }
}

class Tree { // Lightweight — only unique data
  constructor(
    public x: number,
    public y: number,
    public age: number,
    public type: TreeType, // shared reference
  ) {}
}

const oakType = new TreeType('green', oakTexture);
const pineType = new TreeType('dark-green', pineTexture);

const trees = Array(1_000_000).fill(0).map((_, i) => {
  const type = i % 2 === 0 ? oakType : pineType;
  return new Tree(/* x, y, age */ i, i, 5, type);
});
// 1M trees share only 2 TreeType objects. Massive memory savings.
```

## How It Works

1. **Flyweight interface** — declares the operation that takes extrinsic state.
2. **Concrete Flyweight** — implements the interface; stores intrinsic state; immutable after construction.
3. **Flyweight Factory** — manages a pool of flyweights. `getFlyweight(key)` returns the shared one.
4. **Client** — computes/stores extrinsic state, calls `flyweight.operation(extrinsic)`.

```typescript
// Flyweight
interface Glyph {
  draw(x: number, y: number, fontSize: number): void;
}

// Concrete Flyweight — stores the bitmap of a character
class CharacterGlyph implements Glyph {
  constructor(public char: string, public bitmap: ImageData) {}
  draw(x: number, y: number, fontSize: number) {
    // Use this.bitmap + (x, y, fontSize) to render
  }
}

// Flyweight Factory
class GlyphFactory {
  private cache = new Map<string, CharacterGlyph>();

  getGlyph(char: string, font: Font): CharacterGlyph {
    const key = `${char}-${font.name}`;
    if (!this.cache.has(key)) {
      this.cache.set(key, new CharacterGlyph(char, this.loadBitmap(char, font)));
    }
    return this.cache.get(key)!;
  }
}

// Client
class TextDocument {
  constructor(private factory: GlyphFactory) {}
  render(text: string) {
    let x = 0;
    for (const char of text) {
      const glyph = this.factory.getGlyph(char, this.font);
      glyph.draw(x, 0, 12);
      x += 8;
    }
  }
}
```

## Real-World Examples

### 1. Text rendering and particles

For a simplified packed-data illustration, assume a repeated bitmap uses 2,048 bytes and each placement uses 12 bytes. One million independent copies would spend about 2 GB on the repeated bitmap payload alone. Sharing 100 bitmaps spends about 200 KB on that payload, plus about 12 MB for placements. These are arithmetic assumptions, not measured JavaScript object sizes or a guarantee for a text engine.

The useful question is which state genuinely repeats. Glyphs may differ by font, size, shaping and rasterization; particles may share a texture/type but keep position, velocity and lifetime per instance. Key the shared representation by every property that determines its intrinsic state.

### 2. Distinguish sharing from pooling

A connection pool lends mutable resources with controlled ownership. That is an Object Pool contract, not Flyweight's shared intrinsic state. The costs of a connection depend on the database and workload; no fixed millisecond or byte estimate establishes the choice.

### 3. Runtime optimizations are separate

Engines may intern some strings or share some internal representations. Neither JavaScript nor CSS promises that all equal strings or equal computed styles have one physical object. Use heap evidence for application decisions, not assumed engine layouts.

### 6. Icon libraries

A 1000-row table, each row with a status icon (, , ). An SVG symbol/use design or cached image asset can share source data; 1000 inline SVG elements still create distinct DOM instances.

## When to Use

 **Use Flyweight when:**

- An application uses a **large number of objects**
- Storage costs are high because of the sheer quantity of objects
- Most object state can be made **extrinsic** (moved out of the object)
- Many groups of objects can be replaced by **relatively few shared objects** once extrinsic state is removed
- The application doesn't depend on object identity (you don't care WHICH instance)

 **Avoid Flyweight when:**

- The number of objects is too small to justify measured savings — the bookkeeping outweighs the savings
- Objects are mostly unique (little to share)
- The intrinsic state is hard to factor out (objects are too varied)
- Identity matters (each object is treated as distinct)
- You need thread-safety guarantees — shared mutable state is a synchronization hazard

## How It Works in Code

### Modern TypeScript with Maps

```typescript
class FlyweightFactory<TKey, T extends { operation(extrinsic: any): void }> {
  private cache = new Map<TKey, T>();

  constructor(private creator: (key: TKey) => T) {}

  get(key: TKey): T {
    let fw = this.cache.get(key);
    if (!fw) {
      fw = this.creator(key);
      this.cache.set(key, fw);
    }
    return fw;
  }
}

// Usage
const treeFactory = new FlyweightFactory<string, TreeType>((species) =>
  new TreeType(species, loadTexture(species))
);

const oak1 = treeFactory.get('oak');
const oak2 = treeFactory.get('oak');
oak1 === oak2; // true — same instance
```

### Functional Flyweight (cache of pure functions)

```typescript
const cache = new Map<string, number>();

function expensiveComputation(input: string): number {
  if (cache.has(input)) return cache.get(input)!;
  const result = /* ... complex work ... */ 42;
  cache.set(input, result);
  return result;
}
```

This is Flyweight at the function level — share results instead of objects.

## Comparisons

### Flyweight vs Object Pool

- **Flyweight** shares **immutable intrinsic state** across many lightweight objects.
- **Object Pool** reuses **mutable objects** (connections, threads) — but each is owned by one client at a time.

Both reduce allocation; they differ on mutability and ownership.

### Flyweight vs Prototype

- **Flyweight** is about **sharing** one instance across many uses.
- **Prototype** is about **cloning** an instance to create a new one.

### Flyweight vs Singleton

- **Singleton** enforces exactly ONE instance.
- **Flyweight** allows multiple instances, each shared by many clients (e.g., one TreeType per species, not one TreeType total).

### Flyweight vs Cache

A cache is a generic term for storing computed results. Flyweight is a specific design pattern that **structures** the cache + object split. Most "caches" in code are not formal Flyweights (they don't separate intrinsic/extrinsic) — they're just caches.

## Code Example: Forest with Trees

```typescript
// Tree type (the flyweight — shared per species)
class TreeType {
  constructor(
    public name: string,
    public color: string,
    public texture: ImageData,
  ) {}
  draw(canvas: Canvas, x: number, y: number, age: number) {
    // Draw using intrinsic (color, texture) + extrinsic (x, y, age)
  }
}

// Tree (lightweight — only unique data)
class Tree {
  constructor(
    public x: number,
    public y: number,
    public age: number,
    public type: TreeType, // shared reference
  ) {}
  draw(canvas: Canvas) {
    this.type.draw(canvas, this.x, this.y, this.age);
  }
}

// Tree factory
class TreeFactory {
  private types = new Map<string, TreeType>();

  getTreeType(name: string, color: string, texture: ImageData): TreeType {
    const key = `${name}-${color}`;
    if (!this.types.has(key)) {
      this.types.set(key, new TreeType(name, color, texture));
    }
    return this.types.get(key)!;
  }
}

// Forest
class Forest {
  private trees: Tree[] = [];

  plantTree(x: number, y: number, age: number, type: TreeType) {
    this.trees.push(new Tree(x, y, age, type));
  }
  draw(canvas: Canvas) {
    for (const tree of this.trees) tree.draw(canvas);
  }
}

// Usage
const factory = new TreeFactory();
const oakType = factory.getTreeType('oak', 'green', oakTexture);
const pineType = factory.getTreeType('pine', 'dark-green', pineTexture);

const forest = new Forest();
for (let i = 0; i < 1_000_000; i++) {
  const type = i % 2 === 0 ? oakType : pineType;
  forest.plantTree(Math.random() * 1000, Math.random() * 1000, 5, type);
}
// 2 TreeType objects, 1M Tree objects
```

## Common Pitfalls

### 1. **Mutating shared state**

If you mutate intrinsic state on a flyweight, you affect all clients. Make flyweights **immutable** (or document carefully).

### 2. **Confusing intrinsic and extrinsic**

If you accidentally store unique data in the flyweight, the sharing breaks. Audit the data: "Is this the same across instances?" → intrinsic. "Does this vary?" → extrinsic.

### 3. **Over-using for small numbers**

For small workloads, the bookkeeping may cost more than it saves; compare against the measured payload.

### 4. **Thread-safety on shared state**

If your flyweight is mutable, you need synchronization. Immutable payloads simplify reading, but the factory cache and any external resource lifecycle still need appropriate coordination.

### 5. **Memory leaks from cache growth**

The factory's cache grows over time. If you generate many distinct keys (e.g., one per user ID), the cache becomes huge. Add eviction (LRU) or limit the cache size.

## Best Practices

1. **Make flyweights immutable** — simplifies shared read access; coordinate cache construction and lifecycle separately.
2. **Use a factory** to centralize the cache; clients should never `new` a flyweight directly.
3. **Document what is intrinsic vs extrinsic** — comments help future maintainers.
4. **Combine with Composite** — flyweights are often leaves in a Composite tree.
5. **Consider WeakMap** for the cache if the keys are objects that may be GC'd.
6. **Measure first** — profile memory before adding Flyweight; the overhead might not be worth it.

## Summary

Flyweight is a **memory-optimization** pattern. Use it when you have many similar objects and you've measured that memory is a real problem. The core idea: separate what's shared (intrinsic) from what's unique (extrinsic), and share the former.

**Interview-ready one-liner:** "Flyweight shares common state across many objects to fit more in memory — separate intrinsic (shared) from extrinsic (per-instance) state, and use a factory to manage the shared instances."

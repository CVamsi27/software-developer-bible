# Flyweight Pattern

A forest can have many tree positions but only a few repeated appearances. Storing the same large texture separately in each tree wastes space; sharing one mutable position among trees would move them all together. The distinction is which state repeats and which state belongs to each placement.

## Definition

A **Flyweight** factors repeated, context-independent state into objects that many logical uses can share. Each use keeps its own context separately and supplies it when invoking shared behavior.

> **Textbook Definition:** “Use sharing to support large numbers of fine-grained objects efficiently.” — Gamma, Helm, Johnson and Vlissides, *Design Patterns* (1994), Flyweight intent.

**Intrinsic state** belongs to the shared representation, such as a tree's texture version and color. **Extrinsic state** belongs to one use, such as its coordinates and age. These are modeling choices: color can be intrinsic when all trees of one type share it, or extrinsic when every placement has its own tint.

## First Principles

A million placements do not require a million distinct copies of the same appearance. Separate the repeated payload from the varying coordinates, then let each placement reference the repeated payload.

Sharing creates a new obligation: changing the shared state changes every use. Either make it immutable or deliberately coordinate a shared update. The lookup key must also cover every property that determines that state; a key that ignores texture version can return the wrong appearance even when sharing saves memory.

## Follow a placement through the shared type

```text
Tree at (0,0) ─┐
Tree at (5,2) ─┼─→ one immutable oak TreeType → repeated appearance
Tree at (9,3) ─┘
  each owns coordinates/age; draw supplies them to the shared type
```

This independent TypeScript example renders descriptions rather than loading textures or drawing on a canvas. The texture key represents an asset identity/version; a real renderer must also share the actual payload/resource under a compatible ownership contract.

```typescript
class TreeType {
  constructor(
    public readonly name: string,
    public readonly color: string,
    public readonly textureKey: string
  ) {
    Object.freeze(this); // fields are strings; no nested mutable payload here
  }
  draw(x: number, y: number, age: number): string {
    return `${this.name}/${this.color}/${this.textureKey} at ${x},${y}, age ${age}`;
  }
}

class TreeFactory {
  private types = new Map<string, TreeType>();
  constructor(private maxTypes = 100) {
    if (!Number.isSafeInteger(maxTypes) || maxTypes < 1) {
      throw new Error('maxTypes must be a positive integer');
    }
  }
  getType(name: string, color: string, textureKey: string): TreeType {
    const key = JSON.stringify([name, color, textureKey]);
    const known = this.types.get(key);
    if (known) return known;
    if (this.types.size >= this.maxTypes) throw new Error('Type limit reached');
    const created = new TreeType(name, color, textureKey);
    this.types.set(key, created);
    return created;
  }
  clear(): void { this.types.clear(); }
}

class Tree {
  constructor(
    public x: number, public y: number, public age: number,
    public readonly type: TreeType
  ) {}
  draw(): string { return this.type.draw(this.x, this.y, this.age); }
}

const factory = new TreeFactory();
const oak = factory.getType('oak', 'green', 'oak-texture-v1');
const sameOak = factory.getType('oak', 'green', 'oak-texture-v1');
const revisedOak = factory.getType('oak', 'green', 'oak-texture-v2');
const first = new Tree(0, 0, 5, oak);
const second = new Tree(5, 2, 8, sameOak);
console.log(oak === sameOak, oak === revisedOak); // true false
console.log(first.draw()); // oak/green/oak-texture-v1 at 0,0, age 5
console.log(second.draw()); // oak/green/oak-texture-v1 at 5,2, age 8
```

The first lookup creates and stores an oak type. The second lookup returns that exact type; both trees call it with their own coordinates. The third lookup changes the texture key and gets another type. Omitting the texture key from the cache key would incorrectly reuse version 1. Encoding a tuple also avoids ambiguous separator-based keys.

The logical trees remain distinct even though `first.type === second.type`. Use tree identity to identify one placement; use type identity to identify a shared appearance. Mutating `first.x` moves only the first tree. The shallow freeze is sufficient for these three string fields, but it would not freeze a mutable bitmap, nested object, or external GPU resource.

## Estimate the saving, then measure the representation

Suppose a packed representation repeats a 2,048-byte bitmap per placement and needs 12 bytes of placement data. These are illustrative payload assumptions, not measured JavaScript object sizes:

| Representation for one million placements | Bitmap payload | Placement payload |
| ----------------------------------------- | ------------------: | --------------------------------------------: |
| One bitmap copy per placement | 2,048,000,000 bytes | 12,000,000 bytes |
| One hundred shared bitmaps | 204,800 bytes | 12,000,000 bytes, plus references/cache costs |

The sharing benefit comes from the removed copies. If the original implementation already references the same image asset, wrapping those references in another factory may save little. Engines can share strings and internal layouts, but do not promise to deduplicate arbitrary application payloads. Use heap/resource measurements for the actual representation.

With `N` placements, `K` distinct shared types, `S` bytes of repeated state, `E` bytes of varying state, and `R` bytes per reference, the rough comparison is `N × (S + E)` against `K × S + N × (E + R)` plus factory bookkeeping. Sharing becomes less useful when nearly every key is distinct or the repeated payload is already small.

## Keep the key and lifetime coherent

A glyph may depend on character, font identity/version, rasterization size, and shaping parameters. A particle may share a texture and material but keep velocity and remaining lifetime per use. Include all determinants of the retained representation, not every property of the logical object.

The example rejects a new distinct type after its configured limit instead of growing without bound. A real owner can choose a scene-scoped cache, an eviction policy, or another bounded retention contract. `clear` drops factory references, but a live `Tree` still retains its type. It does not destroy that type or release an external texture. Evicting and re-creating the same key can also produce two equivalent type objects, so do not use their identity as a permanent logical-object identifier.

An object-keyed `WeakMap` lets entries become collectible with their keys, but it is not a deterministic size bound or a resource-disposal hook. Its keys must be objects or non-registered symbols, so the string tuple in this example needs a normal `Map` and an explicit policy. Asynchronous asset loading needs an in-flight/error contract, while other languages may need synchronization for factory publication. Immutability alone does not coordinate cache creation.

## Compare sharing with nearby mechanisms

| Mechanism | Ownership decision |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| Flyweight | Many uses share intrinsic state and supply per-use context |
| Object pool | A mutable resource is leased to a client and later returned; not ordinarily used concurrently by every client |
| Prototype | A clone operation creates another object under a copying/identity policy |
| Singleton | One instance within a defined runtime scope, rather than one shared instance per appearance key |
| Memoization/cache | Retains results for later lookup; does not necessarily split intrinsic and extrinsic object state |

A cache of `expensiveComputation(input)` results is memoization. It becomes a Flyweight design only when that retained representation participates in the shared-state/context split. A database connection pool has reset, lease, failure, and disposal rules; calling it a Flyweight would hide the ownership difference.

## Decide whether sharing earns its cost

Use Flyweight when measured repeated payload matters, many logical uses can share it safely, and per-use context can be supplied without depending on shared identity. Avoid it when values are mostly unique, lookup/lifetime machinery outweighs the saving, or the proposed shared object still contains mutable per-use data.

Useful applications include glyph/texture representations, repeated particle appearance, and SVG symbol source data. One shared SVG source still permits many distinct DOM placement elements. A physical rendering pipeline needs its own resource cleanup; a metadata-sharing demonstration does not prove GPU or browser memory savings.

## Summary

Flyweight separates repeated intrinsic state from each use's extrinsic context. The tree trace shares one appearance while keeping positions separate, and a changed texture version selects another appearance. Correctness depends on safe sharing, complete keys, logical identity, and bounded lifetime. Measure the payload saved before adding another cache or factory.

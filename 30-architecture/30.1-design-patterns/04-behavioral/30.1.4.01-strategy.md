# Strategy Pattern

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Strategy gives a client interchangeable implementations of one behavior through a common contract. The implementation can be a function or an object; switching it at runtime is optional.

## First Principles

A checkout needs a shipping price, but its pricing policy varies. If checkout owns every pricing rule, each new policy adds another reason to change checkout. Passing the policy into checkout separates the stable workflow from the anticipated variation. This only works while the policies agree on inputs, outputs and failure semantics; a new requirement outside that contract may still change the client.

## One checkout, two policies

```typescript
type Parcel = { weightKg: number; distanceKm: number };
type ShippingPolicy = (parcel: Parcel) => number;

const standard: ShippingPolicy = ({ weightKg, distanceKm }) =>
  5 + weightKg * 2 + distanceKm * 0.01;
const pickup: ShippingPolicy = () => 0;

function shippingQuote(parcel: Parcel, policy: ShippingPolicy): number {
  if (!Number.isFinite(parcel.weightKg) || parcel.weightKg <= 0 ||
      !Number.isFinite(parcel.distanceKm) || parcel.distanceKm < 0) {
    throw new RangeError('Invalid parcel');
  }
  const price = policy(parcel);
  if (!Number.isFinite(price) || price < 0) throw new RangeError('Invalid quote');
  return price;
}

const parcel = { weightKg: 2, distanceKm: 100 };
console.log(shippingQuote(parcel, standard)); // 10
console.log(shippingQuote(parcel, pickup));   // 0
```

Trace the first call: validate the parcel → invoke the injected `standard` function → validate its result → return 10. The second call follows the same workflow but invokes `pickup`. The example uses simple numeric amounts to explain dispatch; production money handling must define currency and precision.

```text
checkout ── calls policy(parcel) ──┬── standard calculation
                                 └── pickup calculation
```

Policy selection belongs at a boundary that knows the business choice. A closed union or validated registry can map user input to approved policies. An arbitrary client-supplied name must not instantiate arbitrary code. If an unsupported choice appears, reject it or use an explicitly agreed fallback.

## When the policy needs an object

Use an object when the algorithm also owns configuration, dependencies, preparation or cleanup. A carrier implementation might call an API and return `Promise<Quote>`; all interchangeable implementations then need a compatible asynchronous contract. Define deadlines, unavailable-service behavior and cancellation together with that contract.

State is allowed. A strategy may retain a model or connection, provided its lifetime, concurrency and isolation rules are clear. Avoid storing one customer's request data in a shared strategy instance. Sharing a stateless function avoids per-call construction, but stateless objects and their results still allocate memory.

## Compare the intention

| Approach | The decision it expresses |
| ------------------- | ---------------------------------------------------------------- |
| Strategy | Which interchangeable policy should perform this operation? |
| State | Which behavior is valid in the object's current lifecycle state? |
| Template Method | Which steps may vary inside a fixed inherited sequence? |
| A small conditional | Which simple branch should execute here? |

A two-branch conditional is often clearer than a new abstraction. Extract a strategy when policies evolve independently, appear in multiple workflows or need isolated tests. Functions avoid class ceremony without changing the contract.

## Common mistakes

- Extracting each parameter value into a class when one configurable algorithm is enough.
- Requiring every strategy to have a default. Some workflows must reject an unspecified policy.
- Accepting a common TypeScript signature as proof of equivalent behavior. Units, validation and failure rules must agree too.
- Assuming indirection has no cost. Measure the complete workload; runtime engines may optimize some calls, while TypeScript itself does not perform runtime inlining.

## Summary

Keep the stable workflow in the client and pass in the behavior that actually varies. Choose a function for a simple policy and an object for a policy with dependencies or lifecycle. The interchangeable contract includes meaning and failures, not just a method name.

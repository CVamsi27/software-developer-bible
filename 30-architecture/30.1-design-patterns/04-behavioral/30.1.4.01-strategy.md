# Strategy Pattern

Checkout needs a shipping quote while pickup and standard delivery use different rules. Keep the workflow stable while giving the selected pricing policy a defined contract.

## Definition

Strategy gives a client interchangeable implementations of one behavior through a common contract. The implementation can be a function or an object; switching it at runtime is optional.

> **Textbook Definition:** “Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from the clients that use it.” — Gamma, Helm, Johnson and Vlissides, *Design Patterns* (1994).

## First Principles

A checkout needs a shipping price, but its pricing policy varies. If checkout owns every pricing rule, each new policy adds another reason to change checkout. Passing the policy into checkout separates the stable workflow from the anticipated variation. This only works while the policies agree on inputs, outputs and what each failure means; a new requirement outside that agreement may still change the client.

## One checkout, two policies

```typescript
type Parcel = Readonly<{ weightKg: number; distanceKm: number }>;
type ShippingPolicy = (parcel: Parcel) => number;

const standard: ShippingPolicy = ({ weightKg, distanceKm }) =>
  5 + weightKg * 2 + distanceKm * 0.01;
const pickup: ShippingPolicy = () => 0;

function shippingQuote(parcel: Parcel, policy: ShippingPolicy): number {
  if (typeof parcel !== 'object' || parcel === null) {
    throw new TypeError('Parcel must be an object');
  }
  if (!Number.isFinite(parcel.weightKg) || parcel.weightKg <= 0 ||
      !Number.isFinite(parcel.distanceKm) || parcel.distanceKm < 0) {
    throw new RangeError('Invalid parcel');
  }
  const price = policy(parcel);
  if (!Number.isFinite(price) || price < 0) throw new RangeError('Invalid quote');
  return price;
}

const parcel = { weightKg: 2, distanceKm: 100 };
console.log(shippingQuote(parcel, standard)); // 10
console.log(shippingQuote(parcel, pickup));   // 0
```

Trace the first call: validate the parcel → invoke the injected `standard` function → validate its result → return 10. The second call follows the same workflow but invokes `pickup`. The example uses simple numeric amounts to explain dispatch; production money handling must define currency and precision.

```text
checkout ── calls policy(parcel) ──┬── standard calculation
                                 └── pickup calculation
```

The example assumes its `policy` is already selected from trusted code and its `parcel` has the declared shape; its runtime checks reject `null` and invalid numeric values. Raw request data still needs parsing at the API boundary. A closed union or validated registry can map a user's choice to approved policies; do not turn an arbitrary client-supplied name into executable code. If a policy throws, the exception propagates unchanged for the caller to handle.

Select a policy at the boundary that knows the business choice. That can happen during startup or for each operation; Strategy does not require runtime switching.

## When the policy needs an object

Use an object when the algorithm needs multiple related operations or an explicit lifecycle. A closure can capture configuration or dependencies without a class. A carrier implementation might call an API and return `Promise<Quote>`; all interchangeable implementations then need a compatible asynchronous contract. Define deadlines, unavailable-service behavior and cancellation together with that contract.

State is allowed. A strategy may retain a model or connection, provided its lifetime, concurrency and isolation rules are clear. Avoid storing one customer's request data in a shared strategy instance. Reuse a stateless policy when possible; create per-request strategy objects only when callers need isolated state.

## Compare the intention

| Approach | The decision it expresses |
| ------------------- | ---------------------------------------------------------------- |
| Strategy | Which interchangeable policy should perform this operation? |
| State | Which behavior is valid in the object's current lifecycle state? |
| Template Method | Which steps may vary inside a fixed inherited sequence? |
| A small conditional | Which simple branch should execute here? |

A two-branch conditional is often clearer than a new abstraction. Extract a strategy when policies evolve independently, appear in multiple workflows or need isolated tests. Functions avoid class ceremony without changing the contract.

## Common mistakes

- Extracting each parameter value into a class when one configurable algorithm is enough.
- Requiring every strategy to have a default. Some workflows must reject an unspecified policy.
- Accepting a common TypeScript signature as proof of equivalent behavior. Units, validation and failure rules must agree too; the type annotation does not validate raw input at runtime.
- Treating Strategy as a performance optimization. It separates policy from workflow; profile the real call path before claiming that dispatch makes it faster.

## Summary

Keep the stable workflow in the client and pass in the behavior that actually varies. Choose a function for a simple policy and an object for a policy with dependencies or lifecycle. The interchangeable contract includes meaning and failures, not just a method name.

# Observer Pattern

One price update can affect a display and an alert. Registered callbacks avoid repeated polling, but the order, cleanup, and failures of those callbacks remain part of the delivery contract.

## Definition

Observer lets a subject notify registered listeners when something happens or state changes. It separates the producer from concrete consumers while retaining an explicit subscription relationship.

> **Textbook Definition:** Observer is a behavioral pattern in which a subject maintains subscriptions and notifies dependent observers of events or state changes through a defined notification contract.

## First Principles

A price update may matter to a display, an alert and an audit trail. Polling makes every consumer decide when to ask. A subject can instead announce each update to its registered listeners. That removes knowledge of concrete consumers, but introduces delivery, ordering and lifetime decisions: who holds listeners, when they run and when they stop?

## Follow one price update

This Node.js example uses the standard `EventEmitter`, whose listeners run synchronously in registration order.

```javascript
import { EventEmitter } from 'node:events';

const prices = new EventEmitter();
const display = (price) => console.log(`display: ${price}`);

prices.on('price', display);
prices.once('price', (price) => {
  console.log(`first update: ${price}`);
  prices.emit('price', price + 1);
});
prices.emit('price', 100);
prices.off('price', display);
prices.emit('price', 200);
// display: 100
// first update: 100
// display: 101
```

The outer emission calls `display`, then the one-time listener. `once` removes that registration before invoking it, so the recursive emission calls only `display`. The final emission has no listeners. Removing a one-time listener only after its callback returns would incorrectly let recursion invoke it again.

```text
subject ── registration ── listener A
       └── registration ── listener B
emit(value) → A(value) → B(value)
unsubscribe → remove that registration
```

This diagram describes this synchronous example. A particular subject may choose queued delivery instead; that is an additional contract, not a guarantee of Observer.

## Own the subscription lifetime

Pair registration with cleanup in the owner that knows when the subscription ends: component teardown, request completion or service disposal. Use the same callback reference when removing a listener. Duplicate registration can produce duplicate calls; raising Node's listener warning threshold does not fix an unintended lifetime.

Weak references are unsuitable when a subscriber must keep receiving events. Garbage collection is nondeterministic, and a weakly held listener can disappear while the logical subscription is still needed. Use explicit cleanup for predictable delivery. Weak references can be appropriate for genuinely optional observations, with their weaker semantics documented.

## Decide what failure means

For Node `EventEmitter`, an ordinary listener throwing interrupts the synchronous emission; returned promises are not awaited by `emit`. An unhandled `'error'` event throws. Use the documented rejection-handling facilities or handle asynchronous work explicitly; an `async` listener does not make emission awaitable.

If a notification must finish independently of the caller, define a queue, error reporting, capacity and ordering. Moving work to a microtask changes timing but does not provide durability or backpressure. Coalesce state changes only when intermediate updates may safely be omitted.

For a custom subject, specify whether listeners added or removed during a notification affect that notification, whether duplicate registrations are distinct and whether one failure stops other listeners. Snapshot iteration and live iteration make different choices.

## Observer, events and a broker

| Mechanism | Important boundary |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| Local Observer / EventEmitter | Subject retains registrations; delivery usually stays within one runtime. |
| DOM EventTarget | Browser event propagation and listener options define a different event contract. |
| Brokered publish-subscribe | Topics, acknowledgements, retries and independent process lifetimes introduce distributed delivery rules. |
| Reactive stream | Values also have a composition, completion and error contract; backpressure depends on the system. |

These share notification ideas. A Kafka consumer is not equivalent to a synchronous callback list: recovery, duplicate delivery and ordering must be assessed separately.

## Summary

Observer replaces repeated polling with explicit registrations. Trace listener order and reentrancy, assign cleanup to a clear owner and decide how failures propagate. A local notification mechanism does not by itself make delivery asynchronous, durable or exactly once.

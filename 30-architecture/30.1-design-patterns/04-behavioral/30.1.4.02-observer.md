# Observer Pattern

One price update can affect a display and an alert. Registered callbacks avoid repeated polling — but the order, cleanup, and failures of those callbacks remain part of the delivery contract:

```javascript
prices.on('price', display);
prices.emit('price', 100); // display: 100
```

## Definition

**Observer** is a behavioral pattern in which a **subject** keeps a list of **subscribers** and notifies them when its state changes. It depends on a shared listener contract, not on each subscriber's concrete type.

> **Textbook Definition:** "Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically." — Gamma, Helm, Johnson and Vlissides, *Design Patterns* (1994).

## First Principles

A price update may matter to a display, an alert, and an audit trail. Polling makes every consumer decide when to ask. A subject can instead announce each update to its registered listeners. That removes knowledge of concrete consumers — but introduces delivery, ordering, and lifetime decisions: who holds listeners, when they run, and when they stop?

## 1. Notify registrations on one update

This Node.js example uses the standard `EventEmitter`, whose listeners run synchronously in registration order:

```javascript
import { EventEmitter } from 'node:events';

const prices = new EventEmitter();
const display = (price) => console.log(`display: ${price}`);

prices.on('price', display);
prices.once('price', (price) => {
  console.log(`first update: ${price}`);
  prices.emit('price', price + 1);
});
prices.emit('price', 100);
prices.off('price', display);
prices.emit('price', 200);
// display: 100
// first update: 100
// display: 101
```

The outer emission calls `display`, then the one-time listener. `once` removes that registration before invoking it, so the recursive emission calls only `display`. The final emission has no listeners. Removing a one-time listener only after its callback returns would incorrectly let recursion invoke it again.

```text
subject ── registration ── listener A
       └── registration ── listener B
emit(value) → A(value) → B(value)
unsubscribe → remove that registration
```

This diagram describes this synchronous example. A particular subject may choose queued delivery instead; that is an additional contract, not a guarantee of Observer.

## 2. Own the subscription lifetime

Pair registration with cleanup in the owner knowing when the subscription ends: component teardown, request completion, or service disposal. Use the same callback reference when removing a listener. Node allows duplicate registrations, and `off` removes only one matching registration, so repeated setup can leave callbacks behind. During an emission, removing a later listener affects future emissions; Node still invokes listeners from the current emission's snapshot. Raising the listener warning threshold never fixes an unintended lifetime.

Weak references are unsuitable when a subscriber must keep receiving events. Garbage collection is nondeterministic, and a weakly held listener can disappear while the logical subscription is still needed. Use explicit cleanup for predictable delivery. Weak references suit genuinely optional observations only, with their weaker semantics documented.

## 3. Decide what failure means

For Node `EventEmitter`, a listener throwing interrupts synchronous dispatch, and `emit` never awaits returned promises. `captureRejections` is off by default; when enabled, Node routes a returned promise's rejection asynchronously to `Symbol.for('nodejs.rejection')` or the `'error'` event. It still never makes `emit` await completion. An unhandled `'error'` event throws; if uncaught, the process exits.

If a notification must finish independently of the caller, define a queue, error reporting, capacity, and ordering. Moving work to a microtask changes timing but provides no durability or backpressure. Coalesce state changes only when intermediate updates may safely be omitted. For a custom subject, specify whether listeners added or removed during a notification affect that notification, whether duplicate registrations are distinct, and whether one failure stops other listeners. Snapshot iteration and live iteration make different choices.

## 4. Place Observer among event mechanisms

| Mechanism | Important boundary |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| Local Observer / EventEmitter | Subject retains registrations; delivery usually stays within one runtime. |
| DOM EventTarget | Browser event propagation and listener options define a different event contract. |
| Brokered publish-subscribe | Topics, acknowledgements, retries and independent process lifetimes introduce distributed delivery rules. |
| Reactive stream | Values also have a composition, completion and error contract; backpressure depends on the system. |

These share notification ideas. A Kafka consumer is not equivalent to a synchronous callback list: recovery, duplicate delivery, and ordering must be assessed separately.

## Summary

Observer can replace repeated polling with explicit registrations. Trace listener order and reentrancy, assign cleanup to a clear owner and decide how failures propagate. A local notification mechanism does not by itself make delivery asynchronous, durable or exactly once.

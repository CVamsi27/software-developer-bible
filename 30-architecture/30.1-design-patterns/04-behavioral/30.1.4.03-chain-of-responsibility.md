# Chain of Responsibility

An urgent billing ticket should reach on-call before the ordinary billing handler. The routing sequence and its fallback need one visible owner.

## Definition

Chain of Responsibility sends a request through ordered handlers so the sender does not depend on a concrete receiver. Each handler can process the request, decline it and pass it onward, or terminate the chain under its contract. Middleware is a related variant in which several handlers can contribute to one request.

> **Textbook Definition:** “Avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request.” The chain passes the request along until a handler accepts it or the chain ends. — Gamma, Helm, Johnson and Vlissides, *Design Patterns* (1994).

## First Principles

If multiple handlers can answer a request, choosing the receiver at every call site duplicates routing policy. Compose that policy once as an ordered chain. Order is observable: a general handler placed first can prevent a specialized handler from ever running. The chain therefore needs an explicit result for both handled requests and complete fall-through.

## Route one support ticket

```typescript
type Ticket = Readonly<{ category: 'billing' | 'technical' | 'other'; urgent: boolean }>;
type Assignment = Readonly<{ team: string }>;
type Handler = (ticket: Ticket) => Assignment | undefined;

const emergency: Handler = ticket =>
  ticket.urgent ? { team: 'on-call' } : undefined;
const billing: Handler = ticket =>
  ticket.category === 'billing' ? { team: 'billing' } : undefined;
const technical: Handler = ticket =>
  ticket.category === 'technical' ? { team: 'technical' } : undefined;

function route(ticket: Ticket, handlers: readonly Handler[]): Assignment {
  for (const handle of handlers) {
    const assignment = handle(ticket);
    if (assignment !== undefined) return assignment;
  }
  return { team: 'triage' };
}

console.log(route({ category: 'billing', urgent: true },
  [emergency, billing, technical])); // { team: 'on-call' }
console.log(route({ category: 'other', urgent: false },
  [emergency, billing, technical])); // { team: 'triage' }
```

For the urgent billing ticket, `emergency` returns an assignment and `route` stops before billing. For the ordinary unknown ticket, all handlers decline and the explicit fallback assigns triage. A thrown handler error propagates and stops traversal; this example does not turn failure into fall-through. The `Ticket` type checks code only at compile time, so parse untrusted input before calling `route`.

```text
request → emergency ─declines→ billing ─declines→ technical → fallback
             │                    │                  │
           handles              handles            handles
             └────────────────────┴──────────────────┘ → result
```

An array keeps order visible and cannot form forwarding cycles. Linked handlers are another implementation when each object owns its successor; that structure needs cycle protection.

## Middleware passes control, not a result

Express middleware either ends the response or calls `next()` to pass control. `next()` does not return a promise for downstream completion, so code after that call is not guaranteed to run after later handlers or after the response.

Error handling depends on the Express major version. Express 5 forwards rejections from promises returned by middleware to error handling; Express 4 requires asynchronous failures to reach `next(err)` explicitly. A promise started but not returned is outside Express 5's automatic handling too.

An asynchronous onion-style pipeline has a different contract: define `next(): Promise<void>`, await it and reject repeated calls. Decide whether handlers return a terminal result or mutate shared response state; dropping a handler's returned result loses it.

## Make order and failure explicit

- Test overlapping handlers and the no-match fallback. A generic handler placed before a higher-priority one can claim work prematurely.
- Decide whether an exception stops traversal or becomes a typed outcome. In an authorization chain, never treat a failed check as a decline and continue.
- Keep reusable handlers stateless or put mutable data in a per-request context. Shared request-specific fields can leak across concurrent requests.

## Compare nearby patterns

| Pattern | What the client delegates |
| ----------------------- | -------------------------------------------------------- |
| Chain of Responsibility | Receiver selection or ordered handling across candidates |
| Strategy | One already selected interchangeable policy |
| Pipeline | A sequence of transformations that normally all run |
| Decorator | Behavior around a wrapped object's interface |

Middleware may combine these ideas. Explain who forwards, who terminates and who owns errors instead of choosing a pattern from the class diagram alone.

## Summary

Move receiver selection into a visible ordered chain. Trace first-match and complete fall-through, assign a failure policy, and preserve the framework's continuation and async-error contract. Handler order and lifetime are part of correctness.

# Chain of Responsibility

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Chain of Responsibility passes a request through ordered handlers without coupling its sender to one concrete receiver. A handler may handle it, forward it or reject it. Middleware is a related variant in which several handlers can contribute to one request.

## First Principles

If multiple handlers can answer a request, choosing the receiver at every call site duplicates routing policy. Compose that policy once as an ordered chain. Order is observable: a general handler placed first can prevent a specialized handler from ever running. The chain therefore needs an explicit result for both handled requests and complete fall-through.

## Route one support ticket

```typescript
type Ticket = { category: 'billing' | 'technical' | 'other'; urgent: boolean };
type Assignment = { team: string };
type Handler = (ticket: Ticket) => Assignment | undefined;

const emergency: Handler = ticket =>
  ticket.urgent ? { team: 'on-call' } : undefined;
const billing: Handler = ticket =>
  ticket.category === 'billing' ? { team: 'billing' } : undefined;
const technical: Handler = ticket =>
  ticket.category === 'technical' ? { team: 'technical' } : undefined;

function route(ticket: Ticket, handlers: readonly Handler[]): Assignment {
  for (const handle of handlers) {
    const assignment = handle(ticket);
    if (assignment !== undefined) return assignment;
  }
  return { team: 'triage' };
}

console.log(route({ category: 'billing', urgent: true },
  [emergency, billing, technical])); // { team: 'on-call' }
console.log(route({ category: 'other', urgent: false },
  [emergency, billing, technical])); // { team: 'triage' }
```

For the urgent billing ticket, `emergency` handles it and stops traversal. The billing handler never runs. For the ordinary unknown ticket, all three decline and the explicit fallback assigns triage.

```text
request → emergency ─declines→ billing ─declines→ technical → fallback
             │                    │                  │
           handles              handles            handles
             └────────────────────┴──────────────────┘ → result
```

An array keeps this example's order and termination visible. Linked handler objects are another implementation, useful when individual handlers manage forwarding. They must prevent accidental cycles.

## A middleware chain has a different stopping rule

In Express, a middleware can finish the response or call `next()` to continue. Errors use the framework's error-routing rules. Calling `next()` is not an awaitable promise for downstream completion, so code immediately after `next()` must not be described as guaranteed post-response processing.

If implementing an asynchronous onion-style pipeline yourself, define `next(): Promise<void>`, await it and reject repeated `next()` calls. Also define whether downstream returns a result or mutates a response. Do not mix those models: ignoring a terminal handler's returned response loses its output.

Authentication must validate credentials; checking that a token string exists is insufficient. A rate limiter shared across requests must keep appropriately scoped state; constructing a fresh limiter for every request resets its counters. These production mechanisms belong in their dedicated chapters rather than simulated middleware here.

## Bound the chain's responsibilities

- Validate ordering through concrete cases: rejected credentials, invalid input, successful handling and no handler.
- Decide whether an exception stops traversal or maps to a result; silently catching and continuing can bypass a protection handler.
- Keep each handler's responsibility cohesive. Handlers can own state, but request-specific mutable state must not leak between concurrent calls.
- Parallelize only genuinely independent work. Authentication and protected business operations are not an unordered batch.
- Cache only with the full caller, tenant and input identity needed by the result's contract.

## Compare nearby patterns

| Pattern | What the client delegates |
| ----------------------- | -------------------------------------------------------- |
| Chain of Responsibility | Receiver selection or ordered handling across candidates |
| Strategy | One already selected interchangeable policy |
| Pipeline | A sequence of transformations that normally all run |
| Decorator | Behavior around a wrapped object's interface |

Middleware may combine these ideas. Explain who forwards, who terminates and who owns errors instead of choosing a pattern from the class diagram alone.

## Summary

Move receiver selection into a visible ordered chain. Trace a request through every possible stopping point, define fall-through and preserve the framework's continuation semantics. Ordering and lifetime are part of correctness.

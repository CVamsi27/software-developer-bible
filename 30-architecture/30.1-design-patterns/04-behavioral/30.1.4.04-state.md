# State Pattern & State Machines

A shipping request should succeed for a paid order and fail for a pending order. The rule belongs to the order's lifecycle, so callers must not decide it independently.

## Definition

The GoF State pattern delegates behavior to an object representing the current state. A state machine is broader: it defines states, events and allowed transitions. A TypeScript discriminated union with a transition function is one way to implement those rules, but it is not the GoF object's delegation structure.

> **Textbook Definition:** “Allow an object to alter its behavior when its internal state changes. The object will appear to change its class.” The GoF definition describes a context delegating state-dependent behavior to a replaceable state object. A state machine can model the same lifecycle without using this object structure.

## First Principles

An order cannot ship merely because a caller asks: shipping requires a valid preceding state. A status string alone does not enforce this rule. Put the transition rule at the boundary that changes the order, and make state-specific data explicit. Static types improve internal handling; untrusted input and persisted data still require runtime validation, and concurrent updates still require a database concurrency rule.

## Follow a paid order

```typescript
// domain/order-state.ts
export type OrderState =
  | { kind: 'pending' }
  | { kind: 'paid'; paidAt: Date }
  | { kind: 'shipped'; tracking: string; shippedAt: Date }
  | { kind: 'cancelled'; reason: string; cancelledAt: Date };

export type OrderEvent =
  | { type: 'PAY'; paidAt: Date }
  | { type: 'SHIP'; tracking: string; shippedAt: Date }
  | { type: 'CANCEL'; reason: string; cancelledAt: Date };

export class IllegalTransitionError extends Error {
  constructor(from: OrderState['kind'], event: OrderEvent['type']) {
    super(`Illegal transition: ${event} from ${from}`);
  }
}

export function transition(state: OrderState, event: OrderEvent): OrderState {
  switch (state.kind) {
    case 'pending':
      if (event.type === 'PAY') return { kind: 'paid', paidAt: event.paidAt };
      if (event.type === 'CANCEL') return { kind: 'cancelled', reason: event.reason, cancelledAt: event.cancelledAt };
      break;
    case 'paid':
      if (event.type === 'SHIP') return { kind: 'shipped', tracking: event.tracking, shippedAt: event.shippedAt };
      if (event.type === 'CANCEL') return { kind: 'cancelled', reason: event.reason, cancelledAt: event.cancelledAt };
      break;
    case 'shipped':
      // shipped is terminal — no transitions
      break;
    case 'cancelled':
      // cancelled is terminal — no transitions
      break;
  }
  throw new IllegalTransitionError(state.kind, event.type);
}
```

The rules above describe this particular workflow: `pending` accepts payment or cancellation; `paid` accepts shipment or cancellation; shipment and cancellation are terminal. Another business may allow returns after shipment, which needs a different model.

```text
pending ── PAY ──→ paid ── SHIP ──→ shipped
   │                  │
 CANCEL             CANCEL
   └────────→ cancelled ←─────────┘
```

Trace `PAY` from pending: select the pending branch → accept the payment event → return a paid variant containing `paidAt`. Trace `SHIP` from pending: no rule accepts it → throw `IllegalTransitionError`. A matching event type alone is insufficient; the current state matters.

### The object pattern delegates instead of selecting a union branch

In a GoF object implementation, `order.ship(tracking)` delegates to `currentState.ship(order, tracking)`. A pending-state object rejects it; a paid-state object validates the request and asks the order to replace its delegate with a shipped-state object. The union implementation above computes the next variant rather than dispatching through state objects. Both representations need the same legal-transition and persistence rules; the distinction is where state-specific behavior lives.

The example retains the event's `Date` reference in the result. `Date` is mutable, so a new variant is not automatically deeply immutable. If independent state ownership is required, copy or store a validated primitive timestamp under that contract.

## Persist the transition safely

A pure function can validate two concurrent requests against the same old state. Both may appear legal independently. Persist with a version check, a conditional update or an appropriate transaction lock. If the version changed, reload and reevaluate; do not overwrite the newer state.

Validate dates, identifiers and event payloads before entering the trusted domain model. Decide whether repeated events are idempotent successes, illegal transitions or explicit duplicates. Rejection is not always the right user experience; intentional no-op transitions are valid when defined.

An audit record is useful when the domain needs traceability. Persist it atomically with the state change. Event sourcing is a further choice about the authoritative record and replay; a transition audit log alone does not imply event sourcing.

## Side effects are another boundary

A state transition that says `paid` does not prove that a payment provider completed the charge. External effects need operation identity, retries and reconciliation. For a durable workflow, store the intended effect alongside the transition, for example through an outbox, and track its outcome. Calling an asynchronous refund inside an unawaited callback does not make cancellation complete.

Pure transitions are easy to test, but state-machine libraries may legitimately integrate actions and invoked actors. Test entry, exit, guard and error behavior under that library's contract.

## When a statechart library helps

Nested states, parallel regions, timers or invoked actors can justify a statechart library such as XState when a hand-written transition function becomes hard to reason about. Match versioned documentation to the library release you install. Its persisted actor snapshot is a library-specific structure; `{ kind: 'paid', paidAt }` from the union above is not automatically an XState snapshot. Restore a validated snapshot created by that release's persistence API, and plan migrations when the machine definition changes. Restoring in-memory state does not by itself guarantee external effects ran exactly once.

Use a small union and switch when the transition set is easy to inspect. Use state objects when behavior in each state is substantial. Select a library for the mechanisms needed, without invented per-event timing claims.

## Common mistakes

- Treating compile-time types as protection against arbitrary database writes.
- Confusing a chosen algorithm (Strategy) with lifecycle-dependent behavior (State).
- Persisting new state before an effect without a recovery record, or performing an effect before state without duplicate handling.
- Replaying effects while replaying history without distinguishing reconstruction from execution.
- Leaving additional states unhandled. Exhaustiveness checks can catch this internally; they do not validate external data.

## Summary

Model the legal transitions and state-specific data, then trace both an accepted and a rejected event. Protect persistence against concurrent changes and give external effects a recoverable lifecycle. State objects, unions and statecharts are alternative tools for those rules.

# Template Method Pattern

> **TL;DR:** Template Method defines the **skeleton of an algorithm** in a method, deferring some steps to subclasses. The skeleton calls abstract/hook methods that subclasses override. Use it to avoid code duplication when many classes share the same algorithm structure but differ in details.

## First Principles

Template Method fixes the skeleton, defers the steps:

1. **Frameworks live on this pattern**: "we call you" (IoC) — the base class owns the algorithm's shape (request lifecycle, test runner phases); subclasses fill named hooks (→ 20.2.4.03's lifecycle hooks).
2. **The contract is the hook set**: which steps are overridable, which are fixed — a stable design surface that survives internal refactoring of the fixed parts.
3. **Composition-over-inheritance tension applies**: hooks-as-interfaces (strategy per step) beat deep inheritance chains when variation is multi-dimensional — the pattern's inheritance form suits single-axis variation.

## Definition

The Template Method pattern is a behavioral design pattern that defines the skeleton of an algorithm in a method, deferring some steps to subclasses. The Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure.

It's one of the 23 GoF patterns. The key insight: the **invariant** parts of an algorithm live in the base class; the **variant** parts are abstract methods that subclasses implement.

```text
┌──────────────────────────────────────────────────┐
│ AbstractClass                                    │
│ + templateMethod()                               │
│ step1()                                          │
│ step2()                                          │
│ step3()                                          │
└──────────────────────────────────────────────────┘
        ▲
        │ extends
        │
┌──────────────────────────────────────────────────┐
│ ConcreteClass                                    │
│ + step2() // overrides the variant step          │
└──────────────────────────────────────────────────┘
```

## Why Do We Need It?

### Without Template Method

```typescript
// BAD: duplicated algorithm structure across classes
class CSVExporter {
  export(data: any[]) {
    this.openFile();
    this.writeHeader();
    for (const row of data) {
      this.writeRow(row);
    }
    this.closeFile();
  }
  // ... file ops
}

class JSONExporter {
  export(data: any[]) {
    this.openFile();
    this.writeHeader();
    for (const row of data) {
      this.writeRow(row);
    }
    this.closeFile();
  }
  // ... different writeRow/writeHeader implementations
}

class XMLExporter {
  // ... yet another copy of the same algorithm structure
}
```

**Problems:**
1. **Duplication** — the "open, write header, loop, close" structure is in 3 places
2. **Inconsistency** — if you add a "validate data" step to CSV, you must remember to do it for JSON and XML
3. **Hard to evolve** — adding a step means editing every class

### With Template Method

```typescript
// GOOD: the algorithm is in one place
abstract class DataExporter {
  // The template method — defines the algorithm skeleton
  export(data: any[]) {
    this.openFile();
    this.validateData(data); // optional hook
    this.writeHeader();
    for (const row of data) {
      this.writeRow(row);
    }
    this.closeFile();
  }

  protected abstract openFile(): void;
  protected abstract writeHeader(): void;
  protected abstract writeRow(row: any): void;
  protected abstract closeFile(): void;

  // Hook — subclasses CAN override, but don't have to
  protected validateData(data: any[]): void { /* default: no-op */ }
}

class CSVExporter extends DataExporter {
  protected openFile() { /* open .csv */ }
  protected writeHeader() { /* write column names */ }
  protected writeRow(row: any) { /* write comma-separated */ }
  protected closeFile() { /* close file */ }
}

class JSONExporter extends DataExporter {
  protected openFile() { /* open .json */ }
  protected writeHeader() { /* write [ */ }
  protected writeRow(row: any) { /* write { ... }, */ }
  protected closeFile() { /* write ] */ }
}
```

The structure is in one place. Adding a step (e.g., `compress()`) means editing `DataExporter` once, and every subclass gets it.

## How It Works

1. **AbstractClass** — declares the template method (concrete) and abstract primitive operations.
2. **templateMethod()** — calls primitive operations in a fixed order. Usually `final` (in TS, this is convention — see below).
3. **ConcreteClass** — implements the primitive operations.
4. **Hooks** (optional) — concrete methods with default behavior; subclasses MAY override to customize.

### TypeScript implementation

TypeScript doesn't have `final` for methods, but you can:
- Use a comment convention: `// template method — do not override`
- Use a class that doesn't export its template method
- Use composition (see "Modern TypeScript alternative" below)

```typescript
abstract class DataExporter {
  // Template method — subclasses should NOT override this
  export(data: any[]): void {
    this.openFile();
    this.writeHeader();
    for (const row of data) {
      this.writeRow(row);
    }
    this.closeFile();
  }

  // Abstract primitive operations
  protected abstract openFile(): void;
  protected abstract writeHeader(): void;
  protected abstract writeRow(row: any): void;
  protected abstract closeFile(): void;
}
```

## Real-World Examples

### 1. Test frameworks (Jest, Mocha, Vitest, JUnit)

The test lifecycle IS a template method:

```
beforeAll() → beforeEach() → test() → afterEach() → afterAll()
```

You override `test()` (and optionally the hooks); the framework calls them in order. The framework controls the order; you control the steps.

```typescript
describe('user service', () => {
  beforeAll(() => db.connect()); // hook
  beforeEach(() => db.truncate()); // hook
  it('creates a user', () => { // the "test" step
    // test body
  });
});
```

### 2. Express middleware

```typescript
app.use((req, res, next) => {
  // Pre-processing
  next();
  // Post-processing (asynchronous continuation)
});
```

The Express request lifecycle is a template: parse → match route → run middleware → respond.

### 3. NestJS request lifecycle

NestJS has a fixed request pipeline:

```
Middleware → Guards → Interceptors (before) → Pipes → Handler → Interceptors (after) → Exception filters
```

You implement pieces; the framework orchestrates.

### 4. React class component lifecycle

```typescript
class MyComponent extends React.Component {
  componentDidMount() { /* hook */ }
  componentDidUpdate() { /* hook */ }
  componentWillUnmount() { /* hook */ }
  render() { /* abstract method */ }
}
```

React calls them in a fixed order: `constructor → render → componentDidMount → ... → componentWillUnmount`.

### 5. Build tools

Webpack, Vite, esbuild all have a build pipeline:

```
init → load config → resolve modules → transform → bundle → write → finalize
```

Plugins hook into specific steps.

### 6. Data pipeline ETL

```typescript
abstract class ETLPipeline {
  async run() {
    this.connect();
    const data = await this.extract();
    const cleaned = this.transform(data);
    await this.load(cleaned);
    this.disconnect();
  }
  protected abstract connect(): Promise<void>;
  protected abstract extract(): Promise<RawData>;
  protected abstract transform(raw: RawData): CleanedData;
  protected abstract load(cleaned: CleanedData): Promise<void>;
  protected async disconnect() { /* default close */ }
}
```

### 7. Baking a cake (the classic example)

```typescript
abstract class CakeRecipe {
  bake() {
    this.preheatOven();
    this.mixIngredients();
    this.pourIntoPan();
    this.bake();
    this.decorate();
  }
  protected abstract mixIngredients(): void;
  protected abstract decorate(): void;
  // preheatOven, pourIntoPan, bake have default impls
}

class ChocolateCake extends CakeRecipe {
  protected mixIngredients() { /* flour, cocoa, sugar, eggs */ }
  protected decorate() { /* chocolate ganache */ }
}
```

## When to Use

 **Use Template Method when:**

- You want to implement the **invariant parts of an algorithm once** and leave the variant parts to subclasses
- Common behavior among subclasses should be **factored and localized** to avoid duplication
- Subclasses extend behavior by **overriding certain steps**, not the whole algorithm
- You control the class hierarchy (it's your own code, not 3rd-party)

 **Avoid Template Method when:**

- The algorithm is fully fixed (no variation) — just write the method
- You want to compose behaviors at runtime (use [Strategy](30.1.4.01-strategy.md) instead — Strategy swaps the whole algorithm; Template Method keeps the structure and swaps steps)
- The class hierarchy is unstable (adding steps = editing all subclasses)
- You're using inheritance to override for code reuse, not for "is-a" — use composition

## How It Works in Code

### Hook methods (optional overrides)

```typescript
abstract class DataMiner {
  mine(path: string) {
    this.openFile(path);
    const raw = this.extractData();
    const parsed = this.parseData(raw);
    const analyzed = this.analyze(parsed);
    this.sendReport(analyzed);
    this.closeFile();
  }

  protected abstract openFile(path: string): void;
  protected abstract extractData(): string;
  protected abstract parseData(raw: string): any[];
  protected abstract closeFile(): void;

  // Subclasses MUST implement these
  protected abstract analyze(data: any[]): any;

  // Subclasses MAY override (default impl is fine)
  protected sendReport(report: any) {
    console.log('Sending report to default endpoint');
  }
}
```

### Modern TypeScript alternative — composition

Template Method has a downside: it locks you into inheritance. In modern TypeScript, **composition** is often preferred:

```typescript
// Template Method via composition
class DataExporter {
  constructor(
    private fileOps: FileOps, // injected strategy
    private formatter: Formatter,
  ) {}

  export(data: any[]) {
    this.fileOps.open();
    this.fileOps.write(this.formatter.header());
    for (const row of data) {
      this.fileOps.write(this.formatter.row(row));
    }
    this.fileOps.close();
  }
}
```

This is essentially **Strategy + a coordinator** (which is itself a template). Use this when:
- The "algorithm" has too many steps to make inheritance pleasant
- You want to mix and match steps from different sources

Use Template Method (inheritance) when:
- The "is-a" relationship is natural (a `CSVExporter` IS-A `DataExporter`)
- The framework controls the flow (e.g., Jest's test lifecycle)

## Comparisons

### Template Method vs Strategy

| Template Method | Strategy |  |
| -- | ----------------- | ---------- |
| **How it varies** | Subclasses override steps | Client passes a different strategy object |
| **Mechanism** | Inheritance | Composition |
| **Algorithm structure** | Fixed (in base class) | Fixed (in context) but the algorithm itself can change |
| **Runtime change?** | No (locked at class creation) | Yes (swap the strategy object) |
| **Use when** | The skeleton is the invariant | The whole algorithm varies |

A common rule: **Strategy** = swap the entire algorithm. **Template Method** = keep the algorithm, swap some steps.

### Template Method vs Factory Method

- **Factory Method** is a special case of Template Method — the template method creates an object, and the factory method decides which class.
- They're complementary: a Template Method can use a Factory Method as one of its steps.

### Template Method vs Builder

- **Template Method** has a fixed sequence of steps (in the base class).
- **Builder** lets the client choose the order and which steps to call.

## Code Example: ETL Pipeline

```typescript
abstract class ETLPipeline<T, R> {
  async run(): Promise<R> {
    this.validateConfig();
    const connection = await this.connect();
    try {
      const raw = await this.extract(connection);
      const cleaned = this.transform(raw);
      const result = await this.load(cleaned);
      this.onSuccess(result);
      return result;
    } catch (err) {
      this.onError(err as Error);
      throw err;
    } finally {
      await this.disconnect(connection);
    }
  }

  // Abstract — must implement
  protected abstract connect(): Promise<Connection>;
  protected abstract extract(conn: Connection): Promise<T>;
  protected abstract transform(raw: T): any;
  protected abstract load(cleaned: any): Promise<R>;
  protected abstract disconnect(conn: Connection): Promise<void>;

  // Hooks — can override
  protected validateConfig(): void { /* default: no-op */ }
  protected onSuccess(result: R): void { /* default: log */ }
  protected onError(err: Error): void { /* default: log */ }
}

class PostgresToBigQueryETL extends ETLPipeline<Row[], BigQueryResult> {
  protected async connect() { /* connect to PG */ }
  protected async extract(conn) { /* SELECT * FROM ... */ }
  protected transform(rows) { /* clean, normalize */ }
  protected async load(cleaned) { /* batch insert to BQ */ }
  protected async disconnect(conn) { /* close */ }

  protected onSuccess(result) { console.log(`Loaded ${result.rowCount} rows`); }
  protected onError(err) { Sentry.captureException(err); }
}
```

## Common Pitfalls

### 1. **The Liskov Substitution trap**

If subclasses override steps in ways that break the base class's assumptions, you have an LSP violation. The base class trusts that `step1()` runs before `step2()`; if a subclass doesn't, the algorithm breaks.

**Fix:** Document the contract. Use abstract methods, not overridable defaults, for steps the algorithm depends on.

### 2. **Inheritance for code reuse, not for "is-a"**

Template Method forces inheritance. If your "subclass" isn't really an "is-a" of the parent, prefer composition + Strategy.

### 3. **Too many steps**

If the template has 10+ steps, the base class becomes hard to read. Consider a Pipeline / Chain of Responsibility instead.

### 4. **No way to skip a step**

If some subclasses need to skip a step, the base class needs hooks (default no-op) and the subclass overrides to opt out.

## Best Practices

1. **Name hook methods clearly** — `validateData`, `onSuccess`, `beforeWrite` — so subclasses know what they can override.
2. **Default implementations for hooks** — make hooks no-op or sensible defaults so subclasses only override what they need.
3. **Make template method non-overridable** — in TS, use a comment `// do not override` or move the template to a non-exported class.
4. **Keep the template method short and readable** — it should be obvious what the algorithm does.
5. **Prefer composition in modern code** — use Template Method only when inheritance is natural (framework, "is-a" domain).

## Summary

Template Method is the **Hollywood Principle** ("don't call us, we'll call you") in code form. The base class controls the algorithm; subclasses customize steps. Use it to avoid duplication in a stable class hierarchy with a shared algorithm structure.

**Interview-ready one-liner:** "Template Method defines an algorithm's skeleton in a base class, letting subclasses override specific steps without changing the structure — the base class calls the subclass, not the other way around."

## Cheat Sheet

| Aspect | Detail |
| ---------------------- | -------------------------------------------------------------------- |
| **Category** | Behavioral (GoF) |
| **Intent** | Skeleton + customizable steps |

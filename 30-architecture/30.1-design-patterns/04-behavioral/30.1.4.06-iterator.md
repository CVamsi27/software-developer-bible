# Iterator Pattern

A caller needing the next record should not care whether it comes from an array, a tree, or an API cursor. When every caller implements those storage details, changing the collection changes its consumers too. An iterator gives consumers one way to request the next value while the collection keeps control of traversal:

```javascript
for (const value of range(1, 3)) {
  if (value === 2) break; // 3 is never produced
}
```

## Definition

**Iterator** separates **traversal** — visiting a collection's items — from how the collection stores them. The collection creates or exposes an iterator, and that **iterator** tracks progress as consumers request successive results. JavaScript provides synchronous iteration for immediately available results and asynchronous iteration when obtaining the next result may require waiting; their consumers and timing rules differ.

> **Textbook Definition:** "Provide a way to access the elements of an aggregate object sequentially without exposing its underlying representation." — GoF intent, quoted in [*Java Design Patterns*](https://www.oreilly.com/library/view/java-design-patterns/9781484218020/9781484218013_Ch10.xhtml)

Here, an aggregate is the collection being traversed.

## First Principles

The collection chooses the traversal, while the iterator owns its current position. The consumer asks for one step at a time, so it can stop early or choose among named traversal orders without learning the storage layout. Laziness is a separate implementation choice: wrapping an already materialized array in an iterator never undoes the original allocation.

## 1. Produce values only as consumed

```javascript
function* range(start, end) {
  if (!Number.isSafeInteger(start) || !Number.isSafeInteger(end)) {
    throw new RangeError('Range bounds must be safe integers');
  }
  for (let value = start; value <= end; value++) {
    console.log(`produce ${value}`);
    yield value;
  }
}

for (const value of range(1, 3)) {
  console.log(`consume ${value}`);
  if (value === 2) break;
}
// produce 1
// consume 1
// produce 2
// consume 2
```

This example uses an inclusive end bound (`value <= end`). Creating the generator runs no body. The first `next()` begins execution and reaches `yield 1`; the second resumes and reaches `yield 2`. Breaking the loop closes this generator, so 3 is never produced.

```text
consumer requests next → generator runs to yield → { value, done: false }
consumer requests next → resume after yield     → next result
consumer stops         → iterator closing, when supported
```

An iterable's `[Symbol.iterator]()` must return a valid iterator with `next()`. Each result is an object whose `done` flag indicates completion; the completion value is optional. For repeatable traversal, return a fresh iterator each time — a generator instance is normally single-use.

## 2. Compose lazy traversals without intermediate arrays

ES2025 iterator helpers map, filter, and limit values without building an intermediate array. Materialize only when the caller needs an array:

```javascript
const firstThreeEvenSquares = Iterator.from(range(1, 1_000_000))
  .map((value) => value ** 2)
  .filter((square) => square % 2 === 0)
  .take(3)
  .toArray();
// [4, 16, 36]
```

`map`, `filter`, and `take` are lazy; `toArray()` consumes the remaining pipeline and stores its results. These helpers belong to iterator objects, not every iterable, so `Iterator.from()` adapts an iterable or iterator when needed. Check support in deployed runtimes, especially older browsers and Node versions.

## 3. Bound resources and asynchronous pages

A generator can use `try/finally` to release a resource when it completes or its iterator closes through an early `for...of` exit. Not every manual consumer calls `return()`, and abandoned iterators never guarantee prompt cleanup. Make resource ownership clear.

An async generator can fetch one page, yield its items, and fetch another when the consumer resumes. `for await...of` awaits each result and calls and awaits `return()` on early exit. That closes the iterator but aborts no network I/O by itself — pass an `AbortSignal` to the request and define who cancels it. Also define network failures, retries, repeated cursors, and a maximum-page safeguard. Cursor stability is a server contract: changes between pages can still cause missing or repeated records. A SQL cursor or database driver may buffer rows internally, so one-at-a-time consumption never proves constant server memory. Use the dedicated [generator chapter](../../../10-frontend/10.1-javascript/05-functional-patterns/10.1.5.03-generators.md) for composition and asynchronous protocol examples.

## 4. Document the mutation rule — it is collection-specific

JavaScript Array iterators read the current length while advancing, so an appended element may be visited; continuously appending can prevent termination. Map and Set iterators can visit entries added before traversal ends and skip entries deleted before they are reached. Deleting and re-adding an entry makes it eligible again at its new insertion position. By contrast, Array `map`, `filter`, and `forEach` capture the initial length for their callback traversal. A custom iterator may instead use a snapshot or reject mutation. Document the actual rule instead of assuming all collections behave alike.

Array `map`, `filter`, and `forEach` perform eager callback traversals; they are not iterator helpers. Observables usually push notifications rather than waiting for `next()` requests, so they carry different completion, cancellation, and pressure semantics.

## 5. Choose the traversal contract from the need

| Need | Suitable contract |
| ------------------------------------- | ---------------------------------------------------- |
| Visit an ordinary array | Its existing iterator and `for...of` |
| Traverse a tree in multiple orders | Named DFS/BFS iterables |
| Process I/O-backed items sequentially | An async iterable with cancellation and cleanup |
| Jump to an indexed item | Random-access collection API |
| Push live updates | Event or stream API with explicit delivery semantics |

## Summary

Let the collection own how traversal progresses, and give consumers a consistent stepping contract. Trace production, consumption and early exit; distinguish laziness from buffering and define mutation and resource lifetime explicitly.

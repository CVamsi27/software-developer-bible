# Iterator Pattern


## Definition

Iterator separates traversal from a collection's representation. Consumers request successive results through a common protocol rather than inspecting the collection's storage. JavaScript provides synchronous and asynchronous iteration protocols; their consumers and timing contracts differ.

## First Principles

A caller wants the next item, not a tree's child pointers or an API's pagination details. Let the collection own traversal state and expose one step at a time. This allows early exit and alternative traversal orders. Laziness is an implementation choice: wrapping an already materialized array in an iterator does not undo the original allocation.

## Follow a lazy range

```javascript
function* range(start, end) {
  if (!Number.isSafeInteger(start) || !Number.isSafeInteger(end)) {
    throw new RangeError('Range bounds must be safe integers');
  }
  for (let value = start; value <= end; value++) {
    console.log(`produce ${value}`);
    yield value;
  }
}

for (const value of range(1, 3)) {
  console.log(`consume ${value}`);
  if (value === 2) break;
}
// produce 1
// consume 1
// produce 2
// consume 2
```

Creating the generator does not run its body. The first `next()` begins execution and reaches `yield 1`; the second resumes and reaches `yield 2`. Breaking the loop closes this generator, so 3 is never produced.

```text
consumer requests next → generator runs to yield → { value, done: false }
consumer requests next → resume after yield     → next result
consumer stops         → iterator closing, when supported
```

An iterable's `[Symbol.iterator]()` must return a valid iterator with `next()`. Each result is an object whose `done` flag indicates completion. The completion value is optional. For repeatable traversal, return a fresh iterator each time; a generator instance is normally single-use.

## Resources and asynchronous pages

A generator can use `try/finally` to release a resource when it completes or its iterator is closed through an early `for...of` exit. Not every manual consumer calls `return()`, and abandoned iterators do not guarantee prompt cleanup. Make resource ownership clear.

An async generator can fetch one page, yield its items and fetch the next page only when needed. `for await...of` awaits iteration results. Define cancellation, network failures, repeated cursors and a maximum-page safeguard. Cursor stability is a server contract: changes between pages can still cause missing or repeated records. A SQL cursor or database driver may buffer rows internally, so one-at-a-time consumption does not prove constant server memory.

Use the dedicated [generator chapter](../../../10-frontend/10.1-javascript/05-functional-patterns/10.1.5.03-generators.md) for composition and asynchronous protocol examples.

## Mutation is collection-specific

JavaScript Array iterators read the current length while advancing, so an appended element may be visited; continuously appending can prevent termination. Map and Set also have specified mutation behavior. A custom iterator may instead use a snapshot or reject mutation. Document the actual rule instead of calling all mutation behavior implementation-defined.

Array `map`, `filter` and `forEach` perform their own eager traversals; they are not implementations of the JavaScript iterator protocol. Observables usually push notifications rather than waiting for `next()` requests, so they have different completion, cancellation and pressure semantics. React also accepts iterable children in supported render contexts; rendering is not an unrestricted generic iteration API.

## Choose the traversal contract

| Need | Suitable contract |
| ------------------------------------- | ---------------------------------------------------- |
| Visit an ordinary array | Its existing iterator and `for...of` |
| Traverse a tree in multiple orders | Named DFS/BFS iterables |
| Process I/O-backed items sequentially | An async iterable with cancellation and cleanup |
| Jump to an indexed item | Random-access collection API |
| Push live updates | Event or stream API with explicit delivery semantics |

## Summary

Let the collection own how traversal progresses, and give consumers a consistent stepping contract. Trace production, consumption and early exit; distinguish laziness from buffering and define mutation and resource lifetime explicitly.

# Iterator Pattern

> **TL;DR:** Iterator provides a way to access elements of a collection **sequentially without exposing its underlying representation** (array, tree, graph, lazy stream). Use it to support multiple traversal algorithms over a collection, or to provide a uniform interface across different collection types.

<!-- section: Design Patterns | category: Architecture | subcategory: Behavioral | tags: concept, gof -->

## Definition

The Iterator pattern is a behavioral design pattern that lets you traverse elements of a collection without exposing its underlying representation (list, stack, tree, etc.).

It's one of the 23 GoF patterns. In modern JavaScript/TypeScript, the language has built-in iterator support via `Symbol.iterator` and the iterator protocol — so the pattern is largely a **concept** you use rather than a class you write.

```text
┌──────────────────────────────────────────────┐
│ Iterator (interface) │
│ + hasNext(): boolean │
│ + next(): T │
│ + current(): T │
└──────────────────────────────────────────────┘
                    ▲
                    │ implements
                    │
┌──────────────────────────────────────────────┐
│ ConcreteIterator │
│ - collection: Aggregate │
```

## Why Do We Need It?

### Without Iterator

```typescript
// Client must know the collection's internal structure
function printAll(coll: any) {
  if (coll.type === 'array') {
    for (let i = 0; i < coll.items.length; i++) {
      console.log(coll.items[i]);
    }
  } else if (coll.type === 'linkedList') {
    let node = coll.head;
    while (node) {
      console.log(node.value);
      node = node.next;
    }
  } else if (coll.type === 'tree') {
    function walk(n: TreeNode) {
      console.log(n.value);
      n.children.forEach(walk);
    }
    walk(coll.root);
  }
}
```

**Problems:**
1. **Leaky abstraction** — the client knows the internal structure
2. **Code duplication** — every traversal repeats the loop logic
3. **Hard to extend** — adding a new collection type means editing every function
4. **Multiple traversal strategies** — adding a reverse or BFS iteration is intrusive

### With Iterator

```typescript
function printAll(iter: Iterator<Item>) {
  while (iter.hasNext()) {
    console.log(iter.next());
  }
}
```

The client just uses the iterator. Each collection provides its own iterator with the right traversal logic.

## How It Works

1. **Iterator interface** — declares `hasNext()`, `next()` (and optionally `current()`, `remove()`).
2. **ConcreteIterator** — implements traversal for a specific collection. Tracks the current position.
3. **Aggregate (collection) interface** — declares `createIterator()`.
4. **ConcreteAggregate** — implements `createIterator()` to return the right iterator.

```typescript
interface Iterator<T> {
  hasNext(): boolean;
  next(): T;
  current(): T;
}

interface Collection<T> {
  createIterator(): Iterator<T>;
}

// A simple list iterator
class ListIterator<T> implements Iterator<T> {
  private position = 0;
  constructor(private items: T[]) {}

  hasNext() { return this.position < this.items.length; }
  current() { return this.items[this.position]; }
  next() {
    const item = this.items[this.position];
    this.position++;
    return item;
  }
}

class NumberList implements Collection<number> {
  constructor(private items: number[]) {}
  createIterator() { return new ListIterator(this.items); }
}

// Usage
const list = new NumberList([1, 2, 3, 4, 5]);
const it = list.createIterator();
while (it.hasNext()) {
  console.log(it.next());
}
```

## Modern JavaScript/TypeScript: Built-in Iterators

In modern JS/TS, the pattern is built into the language. You don't write `hasNext`/`next` classes; you implement the **iterator protocol**:

```typescript
interface Iterable<T> {
  [Symbol.iterator](): Iterator<T>;
}

interface Iterator<T> {
  next(): { value: T; done: boolean };
  return?(value?: T): { value: T | undefined; done: true };
}
```

Any object with a `[Symbol.iterator]()` method is iterable — usable with `for...of`, spread, destructuring, etc.

```typescript
class NumberRange {
  constructor(public start: number, public end: number) {}

  [Symbol.iterator]() {
    let current = this.start;
    const end = this.end;
    return {
      next() {
        return current <= end
          ? { value: current++, done: false }
          : { value: undefined, done: true };
      }
    };
  }
}

const range = new NumberRange(1, 5);
for (const n of range) {
  console.log(n); // 1, 2, 3, 4, 5
}

[...range]; // [1, 2, 3, 4, 5]
const [first, second] = range; // 1, 2
```

### Generator functions (the cleanest iterator)

```typescript
class NumberRange {
  constructor(public start: number, public end: number) {}

  *[Symbol.iterator]() {
    for (let i = this.start; i <= this.end; i++) {
      yield i;
    }
  }
}
```

`yield` makes this a generator — the function pauses at each `yield` and resumes on the next call to `next()`. The runtime handles the iterator protocol for you.

### Async iterators

```typescript
interface AsyncIterable<T> {
  [Symbol.asyncIterator](): AsyncIterator<T>;
}

class PaginatedAPI {
  constructor(private fetchPage: (page: number) => Promise<Item[]>) {}

  async *[Symbol.asyncIterator]() {
    let page = 0;
    while (true) {
      const items = await this.fetchPage(page++);
      if (items.length === 0) return;
      yield* items; // yield each item from the array
    }
  }
}

// Usage
for await (const item of new PaginatedAPI(api.fetch)) {
  // process one item at a time, across pages
}
```

This is the **laziest** form of iteration — items are produced on demand.

## Real-World Examples

### 1. Database cursors

SQL `CURSOR` lets you fetch rows one at a time without materializing the entire result set. The iterator protocol is the same.

```typescript
async function* fetchRows(query: string): AsyncIterable<Row> {
  const conn = await pool.connect();
  try {
    const cursor = await conn.query(new Cursor(query));
    while (true) {
      const rows = await cursor.read(100); // batch of 100
      if (rows.length === 0) break;
      for (const row of rows) yield row;
    }
  } finally {
    conn.release();
  }
}

for await (const row of fetchRows('SELECT * FROM users')) {
  // process one row at a time
}
```

### 2. File system traversal

```typescript
import { promises as fs } from 'fs';
import * as path from 'path';

async function* walk(dir: string): AsyncIterable<string> {
  for await (const entry of await fs.opendir(dir)) {
    const fullPath = path.join(dir, entry.name);
    if (entry.isDirectory()) {
      yield* walk(fullPath);
    } else {
      yield fullPath;
    }
  }
}

for await (const file of walk('/some/dir')) {
  console.log(file);
}
```

### 3. Tree traversal (DFS / BFS)

```typescript
class TreeNode<T> {
  constructor(public value: T, public children: TreeNode<T>[] = []) {}

  // Pre-order DFS iterator
  *[Symbol.iterator]() {
    yield this.value;
    for (const child of this.children) {
      yield* child;
    }
  }
}

const tree = new TreeNode(1, [
  new TreeNode(2, [new TreeNode(4), new TreeNode(5)]),
  new TreeNode(3, [new TreeNode(6)]),
]);

[...tree]; // [1, 2, 4, 5, 3, 6]
```

### 4. RxJS observables

An Observable is an iterator over time — it pushes values as they arrive. The semantics differ (push vs pull), but the pattern is similar: a sequence of values with a way to consume them.

### 5. React component children

React doesn't directly use the iterator protocol for children, but the conceptual model is similar: a component receives a collection of children and iterates them.

### 6. Generators in Redux-Saga

```typescript
function* fetchUserSaga(action) {
  try {
    const user = yield call(api.fetchUser, action.payload);
    yield put({ type: 'USER_FETCHED', payload: user });
  } catch (e) {
    yield put({ type: 'USER_FETCH_FAILED', error: e });
  }
}
```

Each `yield` is a pause point; the saga runtime "iterates" the generator, calling `next()` to advance.

## When to Use

 **Use Iterator when:**

- You need to traverse a collection **without exposing its internal structure**
- You want to support **multiple traversal algorithms** (forward, reverse, BFS, DFS, filtered)
- You want a **uniform interface** for traversing different collection types
- You want **lazy iteration** (don't materialize the whole sequence at once)
- The collection might be huge and you want to process items one at a time

 **Avoid Iterator when:**

- The collection is a simple array (just use `for...of`)
- You only need one traversal strategy
- The collection is small and the overhead isn't worth it
- You need random access by index (use array indexing)

## How It Works in Code

### Custom iterators with different strategies

```typescript
class TreeNode<T> {
  constructor(public value: T, public children: TreeNode<T>[] = []) {}

  // Multiple iterator strategies
  *preOrder(): IterableIterator<T> {
    yield this.value;
    for (const child of this.children) yield* child.preOrder();
  }

  *postOrder(): IterableIterator<T> {
    for (const child of this.children) yield* child.postOrder();
    yield this.value;
  }

  *levelOrder(): IterableIterator<T> {
    const queue: TreeNode<T>[] = [this];
    while (queue.length > 0) {
      const node = queue.shift()!;
      yield node.value;
      queue.push(...node.children);
    }
  }
}

const tree = new TreeNode(1, [
  new TreeNode(2, [new TreeNode(4)]),
  new TreeNode(3, [new TreeNode(5)]),
]);

[...tree.preOrder()]; // [1, 2, 4, 3, 5]
[...tree.postOrder()]; // [4, 2, 5, 3, 1]
[...tree.levelOrder()]; // [1, 2, 3, 4, 5]
```

### Iterator with state (filtering, mapping)

```typescript
function* filter<T>(iter: Iterable<T>, pred: (x: T) => boolean): IterableIterator<T> {
  for (const item of iter) {
    if (pred(item)) yield item;
  }
}

function* map<T, U>(iter: Iterable<T>, fn: (x: T) => U): IterableIterator<U> {
  for (const item of iter) {
    yield fn(item);
  }
}

function* take<T>(iter: Iterable<T>, n: number): IterableIterator<T> {
  let i = 0;
  for (const item of iter) {
    if (i++ >= n) return;
    yield item;
  }
}

// Compose lazy operations
const numbers = new NumberRange(1, 1_000_000);
const evens = filter(numbers, n => n % 2 === 0);
const doubled = map(evens, n => n * 2);
const first10 = take(doubled, 10);

[...first10]; // [4, 8, 12, 16, 20, 24, 28, 32, 36, 40]
// Doesn't materialize the 1M numbers — just iterates until 10 are emitted.
```

This is essentially how LINQ (C#) and Python iterators work — composable lazy sequences.

## Comparisons

### Iterator vs Visitor

- **Iterator** is about **movement** through a structure (read-only traversal).
- **Visitor** is about **operations on elements** of a structure (potentially transforming them).

You often traverse with an Iterator, then perform operations via a Visitor at each step.

### Iterator vs Generator

- **Iterator** is the **concept** (sequential access).
- **Generator** is a **language feature** in JS/TS that makes writing iterators easy.

Generators are not a separate pattern — they're a way to implement the Iterator pattern.

### Iterator vs forEach / map / filter

These are **built-in iterators** on arrays. The Iterator pattern generalizes the concept to any collection. For arrays, use `for...of` or `forEach` directly. For custom collections, implement the iterator protocol.

### Iterator vs Composite

- **Composite** is a **structure** (tree of objects).
- **Iterator** is a way to **traverse** that structure.

You often pair them: a Composite class with an iterator that does DFS or BFS.

## Code Example: Lazy Pagination

```typescript
class PaginatedResource<T> {
  constructor(
    private baseUrl: string,
    private fetcher: typeof fetch,
  ) {}

  // Async iterator that yields each item across pages
  async *[Symbol.asyncIterator](): AsyncIterableIterator<T> {
    let page = 1;
    while (true) {
      const res = await this.fetcher(`${this.baseUrl}?page=${page}&size=100`);
      const data = await res.json();
      const items: T[] = data.items;
      if (items.length === 0) return;
      for (const item of items) yield item;
      if (items.length < 100) return;
      page++;
    }
  }
}

// Usage
const users = new PaginatedResource<User>('/api/users', fetch);
for await (const user of users) {
  console.log(user.name);
  if (user.name === 'stop') break; // can break early
}
```

## Common Pitfalls

### 1. **Mutating the collection during iteration**

```typescript
const list = [1, 2, 3];
for (const x of list) {
  if (x === 2) list.push(4); // Bad — iterator may skip or repeat
}
```

This is implementation-defined. Most iterators will see the new element; some won't. Don't mutate during iteration.

### 2. **Forgetting `done: true`**

When implementing the protocol manually, you must return `{ value: undefined, done: true }` when done. Otherwise `for...of` loops forever.

```typescript
// CORRECT
next() {
  return current <= end
    ? { value: current++, done: false }
    : { value: undefined, done: true };
}
```

### 3. **Materializing when you meant to be lazy**

```typescript
// BAD — materializes 1M items
const evens = [...filter(numbers, n => n % 2 === 0)].slice(0, 10);

// GOOD — lazy
const evens = take(filter(numbers, n => n % 2 === 0), 10);
```

### 4. **Reusing a generator after it's done**

Generators are single-use. Once exhausted, you can't restart. If you need multiple traversals, return a new generator from `[Symbol.iterator]()`.

## Best Practices

1. **Use generators** (`yield`) in modern JS/TS — the cleanest way to implement the protocol.
2. **Implement `[Symbol.iterator]`** for any custom collection.
3. **Prefer lazy over eager** — use `take`, `filter`, `map` generators for large sequences.
4. **Document mutation safety** — say "do not mutate during iteration".
5. **Provide multiple iterators** for collections with multiple traversal strategies (BFS, DFS, etc.).
6. **Use async iterators for I/O** — DB cursors, paginated APIs, file streams.

## Summary

Iterator is the **traversal pattern**. It's so fundamental in modern JS/TS that the language builds it in (`Symbol.iterator`, `for...of`, generators). Use it to provide uniform traversal over custom collections, support multiple traversal strategies, and enable lazy iteration over large or streaming data.

**Interview-ready one-liner:** "Iterator provides sequential access to a collection's elements without exposing its internal structure — in modern JS/TS, implement `Symbol.iterator` and you get `for...of` for free."

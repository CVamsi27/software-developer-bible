# Mediator Pattern

A form should enable Submit only after both its title and body contain text. If each field checks the other and toggles the button, the rule spreads across peer components and becomes harder to change. A mediator gives that interaction one explicit owner:

```typescript
form.changed('title', 'Proposal'); // submit enabled: false — body still empty
form.changed('body', 'Details');   // submit enabled: true
```

## Definition

**Mediator** places the rules for a group's interactions in a **coordinator**. Participants communicate through it instead of implementing every peer-to-peer interaction themselves. It fits when those interactions form a cohesive policy; a message bus merely forwarding messages never automatically provides that coordination.

> **Textbook Definition:** "Define an object that encapsulates how a set of objects interacts." — GoF intent, quoted in [*Java Design Patterns*](https://www.oreilly.com/library/view/java-design-patterns/9781484218020/9781484218013_Ch18.xhtml)

## First Principles

Each participant reports a change to the mediator. The mediator evaluates the shared rule and calls the affected collaborators. Peer references become references to the coordinator: coupling moves to one boundary, where the interaction policy can be tested and changed together. The mediator must stay cohesive — a coordinator owning unrelated policies becomes another source of coupling.

## How It Works

### 1. Route peer changes through one coordinator

```typescript
type FieldName = 'title' | 'body';
interface SubmitButton { setEnabled(enabled: boolean): void }

class FormMediator {
  private values: Record<FieldName, string> = { title: '', body: '' };

  constructor(private readonly submit: SubmitButton) {
    this.refresh();
  }

  changed(field: FieldName, value: string): void {
    this.values[field] = value;
    this.refresh();
  }

  private refresh(): void {
    this.submit.setEnabled(
      this.values.title.trim().length > 0 &&
      this.values.body.trim().length > 0
    );
  }
}

const form = new FormMediator({
  setEnabled: enabled => console.log(`submit enabled: ${enabled}`)
});
form.changed('title', 'Proposal');
form.changed('body', 'Details');
// submit enabled: false
// submit enabled: false
// submit enabled: true
```

The title change reaches the mediator, which sees an empty body and keeps submit disabled. The body change completes the combined condition. Neither field needs a reference to the other field or the button.

```text
title widget ── changed(title, value) ──┐
                                       ├→ form coordinator → submit button
body widget ── changed(body, value) ────┘
```

This coordinator holds a small UI interaction rule. Domain validation and authorization still belong at the authoritative business boundary — enabling a button never proves the server will accept the request.

### 2. Keep the boundary cohesive

A dialog, a workflow, or a device session can each have its own mediator. Never build a single global coordinator owning unrelated domain rules. Let participants expose focused operations, and let the mediator own ordering and interaction policy. A mediator may contain coordination logic; forbidding all logic would leave its purpose unclear.

Adding a participant never guarantees zero changes to existing code. The interaction rule and contracts may change. Test the coordinator's complete scenarios and each participant against its narrow contract. Prevent feedback loops: a mediator-driven update must not re-announce the identical change forever. Distinguish user intent from state synchronization, compare before writing, or use explicit event origin/version rules. Asynchronous participants additionally require cancellation, stale-result handling, and error policy.

### 3. Compare the boundary with neighbors

| Mechanism | Primary intention |
| ---------------- | ----------------------------------------------------- |
| Mediator | Coordinate interactions within a cohesive group |
| Observer | Notify registered consumers of a change |
| Facade | Give a subsystem's clients a simpler entry point |
| Command bus | Route an operation request to its handler |
| Brokered pub-sub | Distribute messages through topics and delivery rules |

A mediator may receive change notifications through Observer, but a generic bus never owns the group's interaction policy by itself. A command bus routes a request to a handler; that dispatch role alone never makes it the coordinator for a participant group. A message broker may define persistence, retries, or cross-process delivery. This example coordinates synchronous in-process calls and provides none of those broker guarantees. A Facade can expose mutations as well as reads, so one-way versus bidirectional traffic alone is an unreliable distinction.

## Summary

Move scattered interaction rules into one cohesive coordinator. Trace which participant announces a change, which rule runs and which participant receives the result. Keep the boundary small and make feedback, asynchronous results and failures explicit.

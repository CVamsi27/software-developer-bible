# Mediator Pattern

> **TL;DR:** Mediator centralizes complex communication between many objects into a single mediator object. Objects no longer communicate directly with each other — they go through the mediator. Use it when many objects interact in well-defined but complex ways, and you want to reduce coupling.

## First Principles

Mediator replaces N×N peer wiring with a hub:

1. **Direct references between components couple their lifecycles and knowledge** — every component knows every other. The mediator is the only acquaintance: components announce and listen, the hub routes.
2. **It's air-traffic-control logic**: complexity moves into the mediator, which must stay a dispatcher, not become a god object holding business logic (the pattern's classic failure mode).
3. **Event buses, message brokers (→ 20.6.2.05), and frontend stores (Redux) are mediators at scale** — the same hub-and-spoke decoupling with infrastructure guarantees.

## Definition

The Mediator pattern is a behavioral design pattern that lets you reduce chaotic dependencies between objects. The pattern restricts direct communications between the objects and forces them to collaborate only via a mediator object.

It's one of the 23 GoF patterns. The key insight: instead of **many-to-many** coupling (every object knows every other), you have **one-to-many** coupling (every object knows only the mediator).

```text
        ┌──────────────────┐
        │ Mediator         │
        │ - colleagues[]   │
        │ + notify()       │
        │ + send()         │
        └──────────────────┘
            ▲ ▲ ▲
            │ │ │
        ┌───┴──────────────┐ ┌──┴───┐ ┌─┴────┐
        │ C1 │ │ C2 │ │ C3 │
        └──────────────────┘ └──────┘ └──────┘

WITHOUT Mediator (chaotic):
   C1 ←→ C2 ←→ C3
   C1 ←→ C3
   C2 ←→ C3
   (every object knows every other)

WITH Mediator (centralized):
   C1 → Mediator → C2
   C1 → Mediator → C3
   (objects only know the mediator)
```

## Why Do We Need It?

### Without Mediator

```typescript
// BAD: tight coupling — every dialog widget knows every other
class SaveButton {
  constructor(
    private titleField: TitleField,
    private contentEditor: ContentEditor,
    private saveDialog: SaveDialog,
  ) {}

  onClick() {
    if (!this.titleField.isValid()) {
      this.titleField.showError('Title is required');
      return;
    }
    this.saveDialog.show();
    this.contentEditor.setReadOnly(true);
    // ... more cross-widget logic
  }
}

class TitleField {
  constructor(
    private saveButton: SaveButton,
    private contentEditor: ContentEditor,
  ) {}
  onTextChange() {
    this.saveButton.setEnabled(this.isValid());
    this.contentEditor.setTitle(this.getValue());
  }
}
```

**Problems:**
1. **Combinatorial coupling** — adding a new widget means editing every existing widget
2. **Hard to test** — every widget's test needs to set up all the others
3. **Reusability is zero** — `SaveButton` is bound to `TitleField` + `ContentEditor`; you can't drop it into a different dialog
4. **Spaghetti logic** — the interaction rules are scattered across all the widgets

### With Mediator

```typescript
// GOOD: widgets only know the dialog (mediator)
class SaveButton {
  constructor(private dialog: SaveDialogMediator) {}
  onClick() { this.dialog.saveClicked(); }
}

class TitleField {
  constructor(private dialog: SaveDialogMediator) {}
  onTextChange() { this.dialog.titleChanged(this.getValue()); }
}

class SaveDialogMediator {
  constructor(
    private titleField: TitleField,
    private contentEditor: ContentEditor,
    private saveButton: SaveButton,
  ) {}

  titleChanged(title: string) {
    this.saveButton.setEnabled(title.length > 0);
  }

  saveClicked() {
    if (this.titleField.isValid()) {
      this.contentEditor.setReadOnly(true);
      // ... save logic
    }
  }
}
```

**Benefits:**
1. **Linear coupling** — adding a new widget means adding a method to the mediator, not editing every widget
2. **Testable in isolation** — a widget's test just needs a mock mediator
3. **Reusable** — `SaveButton` doesn't know about `TitleField`; you can use it in any dialog with a mediator
4. **Centralized interaction rules** — the "save requires valid title" logic is in ONE place

## How It Works

1. **Mediator interface** — declares the notification method (e.g., `notify(event)`).
2. **Concrete Mediator** — implements the interface; coordinates colleagues; knows about all of them.
3. **Colleague classes** — each knows only the mediator. When something happens, it notifies the mediator. When it receives a notification, it acts on it.

```typescript
interface Mediator {
  notify(sender: object, event: string): void;
}

class ConcreteMediator implements Mediator {
  private components: Component[] = [];

  register(c: Component) { this.components.push(c); }

  notify(sender: object, event: string) {
    if (event === 'A') {
      // React to A happening somewhere
    } else if (event === 'B') {
      // React to B
    }
  }
}

abstract class Component {
  constructor(protected mediator: Mediator) {}
}

class ComponentA extends Component {
  doA() { this.mediator.notify(this, 'A'); }
}
class ComponentB extends Component {
  doB() { this.mediator.notify(this, 'B'); }
}
```

## Real-World Examples

### 1. Air traffic control tower

Aircraft don't talk to each other directly. They talk to the tower. The tower coordinates takeoffs, landings, and routing to prevent collisions.

- **Colleagues**: Aircraft
- **Mediator**: Control tower

### 2. Chat room (the canonical example)

Users don't send messages directly to other users. They send to the chat room, which broadcasts to all users.

- **Colleagues**: User
- **Mediator**: ChatRoom

```typescript
class ChatRoom implements Mediator {
  private users: User[] = [];
  register(user: User) { this.users.push(user); }
  notify(sender: User, event: string) {
    if (event === 'message') {
      const msg = sender.getLastMessage();
      for (const u of this.users) {
        if (u !== sender) u.receive(msg);
      }
    }
  }
}

class User {
  constructor(public name: string, private room: ChatRoom) {
    this.room.register(this);
  }
  send(msg: string) {
    console.log(`${this.name} sends: ${msg}`);
    this.room.notify(this, 'message: ' + msg);
  }
  receive(msg: string) {
    console.log(`${this.name} receives: ${msg}`);
  }
}

const room = new ChatRoom();
const alice = new User('Alice', room);
const bob = new User('Bob', room);
alice.send('Hi!'); // Alice sends: Hi! / Bob receives: Hi!
```

### 3. GUI dialog boxes

A dialog with multiple widgets (text fields, buttons, lists) — the dialog is the mediator. Widgets notify the dialog when something happens; the dialog coordinates responses.

### 4. Redux / Zustand store

A store is a mediator between components. Components don't call each other; they dispatch actions to the store, which updates state, which components read.

```typescript
// Components → dispatch → Store → state update → Components re-render
```

### 5. MediatR library (C# / .NET)

A popular library for implementing CQRS with a mediator. Commands and queries are sent to a mediator, which routes them to the appropriate handler.

### 6. NestJS EventEmitter

`EventEmitter2` is a global event bus — a mediator. Modules emit events; other modules listen via `@OnEvent('user.created')`.

### 7. Express request/response

Not a perfect fit, but loosely: the Express app coordinates between middleware, route handlers, and the response object. The "app" is a mediator.

## When to Use

 **Use Mediator when:**

- A set of objects communicate in well-defined but **complex ways** (many-to-many)
- **Reusing an object is difficult** because it refers to and communicates with many other objects
- A behavior that's distributed between several classes should be **customizable without a lot of subclassing**
- You want to **centralize** complex communication and control logic

 **Avoid Mediator when:**

- Objects have few collaborators (direct refs are clearer)
- The interaction is simple (a single event triggers a single response)
- The mediator becomes a "god object" (knows and does too much)
- The colleagues are stateless and don't need coordination

## How It Works in Code

### Event-driven Mediator

```typescript
type Event = { type: string; payload?: any };

class EventBus implements Mediator {
  private handlers: Map<string, Array<(e: Event) => void>> = new Map();

  on(type: string, handler: (e: Event) => void) {
    if (!this.handlers.has(type)) this.handlers.set(type, []);
    this.handlers.get(type)!.push(handler);
  }

  notify(sender: object, event: Event) {
    const handlers = this.handlers.get(event.type) || [];
    for (const h of handlers) h(event);
  }
}

// Usage
const bus = new EventBus();

bus.on('user.created', (e) => {
  console.log('Send welcome email to', e.payload.email);
});

bus.on('user.created', (e) => {
  console.log('Track signup in analytics');
});

class UserService {
  constructor(private bus: EventBus) {}
  createUser(data: any) {
    // ... create user
    this.bus.notify(this, { type: 'user.created', payload: { email: data.email } });
  }
}
```

This is essentially an **Observer pattern** on the mediator side — the mediator fans out events to interested parties.

### Mediator with explicit method names (stronger typing)

```typescript
interface SaveDialogMediator {
  titleChanged(title: string): void;
  contentChanged(content: string): void;
  saveClicked(): void;
  cancelClicked(): void;
}

class SaveDialogMediatorImpl implements SaveDialogMediator {
  constructor(
    private titleField: TitleField,
    private contentEditor: ContentEditor,
    private saveButton: SaveButton,
    private cancelButton: CancelButton,
  ) {
    this.titleField.setMediator(this);
    this.contentEditor.setMediator(this);
    this.saveButton.setMediator(this);
    this.cancelButton.setMediator(this);
  }

  titleChanged(title: string) {
    this.saveButton.setEnabled(title.length > 0 && this.contentEditor.hasChanges());
  }
  contentChanged(content: string) { /* ... */ }
  saveClicked() { /* ... */ }
  cancelClicked() { /* ... */ }
}
```

This is more verbose but strongly typed and self-documenting.

## Comparisons

### Mediator vs Observer

- **Observer** is a **one-to-many** notification: subject → observers. Subject doesn't know its observers.
- **Mediator** is a **many-to-many** coordination: colleagues → mediator → colleagues. The mediator knows everyone and routes messages.

| Observer | Mediator |  |
| -- | ---------- | ---------- |
| **Topology** | One subject, many observers | Many colleagues, one mediator |
| **Direction** | One-way (subject → observers) | Many-to-many |
| **Use when** | "Notify many of one change" | "Coordinate many interactions" |

A common rule: if you have an event bus that fans out to many listeners → Observer. If you have a central coordinator that routes messages between specific colleagues → Mediator.

### Mediator vs Facade

- **Facade** simplifies a complex subsystem (one-way: subsystem → simple API). Often read-only.
- **Mediator** coordinates bidirectional communication between peers.

| Facade | Mediator |  |
| -- | -------- | ---------- |
| **Direction** | One-way (subsystem to client) | Many-to-many |
| **Intent** | "Hide complexity" | "Coordinate peers" |
| **Subsystem** | Doesn't know about the facade | Colleagues know about the mediator |

### Mediator vs Command Bus (CQRS)

A command bus is a special case of Mediator. Commands are sent to the bus, which routes to the appropriate handler. Same idea, different framing.

### Mediator vs Pub/Sub

Pub/sub is a distributed Mediator. The "mediator" is the message broker (Kafka, RabbitMQ), and the "colleagues" are services. The pattern is the same; pub/sub adds cross-process communication.

## Code Example: Form Mediator

```typescript
interface FormMediator {
  fieldChanged(field: string, value: any): void;
  submitClicked(): void;
}

class SignupFormMediator implements FormMediator {
  constructor(
    private emailField: Input,
    private passwordField: Input,
    private confirmField: Input,
    private termsCheckbox: Checkbox,
    private submitButton: Button,
    private api: AuthAPI,
  ) {
    this.emailField.onChange((v) => this.fieldChanged('email', v));
    this.passwordField.onChange((v) => this.fieldChanged('password', v));
    this.confirmField.onChange((v) => this.fieldChanged('confirm', v));
    this.termsCheckbox.onChange((v) => this.fieldChanged('terms', v));
    this.submitButton.onClick(() => this.submitClicked());
  }

  fieldChanged(field: string, value: any) {
    // Update submit button enablement based on the full form state
    const valid =
      this.isValidEmail(this.emailField.value) &&
      this.passwordField.value.length >= 8 &&
      this.passwordField.value === this.confirmField.value &&
      this.termsCheckbox.value;
    this.submitButton.setEnabled(valid);
  }

  async submitClicked() {
    if (!this.submitButton.isEnabled()) return;
    try {
      await this.api.signup({
        email: this.emailField.value,
        password: this.passwordField.value,
      });
    } catch (e) {
      this.showError('Signup failed');
    }
  }

  private isValidEmail(email: string) { return /.+@.+\..+/.test(email); }
  private showError(msg: string) { /* ... */ }
}
```

## Common Pitfalls

### 1. **God object**

If the mediator knows about every colleague and handles every event, it becomes a god class. Keep it focused: one mediator per logical subsystem (one per dialog, one per form, etc.).

### 2. **Confusing Mediator with god class**

A mediator **coordinates**; it doesn't **do everything**. If you're putting business logic in the mediator, refactor: mediator coordinates, services do work.

### 3. **Tight coupling to the mediator's interface**

Colleagues shouldn't import every method of the mediator's interface. Use a small, stable interface — just `notify` or a few specific methods.

### 4. **Performance bottleneck**

Every communication goes through one object. In high-throughput systems, this can be a bottleneck. Use pub/sub or direct communication for hot paths.

## Best Practices

1. **One mediator per logical boundary** — one per dialog, form, workflow.
2. **Use events** for many listeners (Observer-style); use methods for specific coordination.
3. **Inject the mediator** via DI so colleagues can be tested in isolation.
4. **Don't make the mediator a god class** — keep it as a coordinator.
5. **Document the interaction rules** — what events trigger what responses.

## Summary

Mediator centralizes communication. It turns many-to-many coupling (chaotic, untestable) into one-to-many coupling (clean, testable). The tradeoff: the mediator can become a god class if you're not careful.

**Interview-ready one-liner:** "Mediator centralizes communication between many objects into a single coordinator — instead of every object knowing every other, they all know only the mediator, which routes messages between them."

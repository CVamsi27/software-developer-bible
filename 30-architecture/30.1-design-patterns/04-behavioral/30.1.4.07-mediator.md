# Mediator Pattern


## Definition

Mediator places interaction rules in a coordinator so collaborating objects do not each need to know all their peers. Its purpose is cohesive coordination, not merely putting a message bus in the middle.

## First Principles

A form's title field, body field and submit button all affect whether submission is possible. If each widget reaches into the others, a rule change is scattered across widgets. Move the combined decision into the form boundary. Widgets report changes; the coordinator evaluates the full rule and updates the relevant collaborators. Coupling moves to that boundary rather than disappearing.

## Trace a form interaction

```typescript
type FieldName = 'title' | 'body';
interface SubmitButton { setEnabled(enabled: boolean): void }

class FormMediator {
  private values: Record<FieldName, string> = { title: '', body: '' };

  constructor(private readonly submit: SubmitButton) {
    this.refresh();
  }

  changed(field: FieldName, value: string): void {
    this.values[field] = value;
    this.refresh();
  }

  private refresh(): void {
    this.submit.setEnabled(
      this.values.title.trim().length > 0 &&
      this.values.body.trim().length > 0
    );
  }
}

const form = new FormMediator({
  setEnabled: enabled => console.log(`submit enabled: ${enabled}`)
});
form.changed('title', 'Proposal');
form.changed('body', 'Details');
// submit enabled: false
// submit enabled: false
// submit enabled: true
```

The title change reaches the mediator, which sees an empty body and keeps submit disabled. The body change completes the combined condition. Neither field needs a reference to the other field or the button.

```text
title widget ── changed(title, value) ──┐
                                      ├→ form coordinator → submit button
body widget ── changed(body, value) ────┘
```

This coordinator contains a small UI interaction rule. Domain validation and authorization still belong at the authoritative business boundary; enabling a button does not prove the server will accept the request.

## Keep the boundary cohesive

A dialog, a workflow or a device session can each have its own mediator. Avoid a single global coordinator that owns unrelated domain rules. Let participants expose focused operations, and let the mediator own ordering and interaction policy. A mediator may contain coordination logic; forbidding all logic would leave its purpose unclear.

Adding a participant does not guarantee zero changes to existing code. The interaction rule and contracts may change. Test the coordinator's complete scenarios and each participant against its narrow contract.

Prevent feedback loops: a mediator-driven update should not automatically announce the identical change forever. Distinguish user intent from state synchronization, compare before writing or use explicit event origin/version rules. Asynchronous participants also require cancellation, stale-result handling and error policy.

## Compare the boundary

| Mechanism | Primary intention |
| ---------------- | ----------------------------------------------------- |
| Mediator | Coordinate interactions within a cohesive group |
| Observer | Notify registered consumers of a change |
| Facade | Give a subsystem's clients a simpler entry point |
| Command bus | Route an operation request to its handler |
| Brokered pub-sub | Distribute messages through topics and delivery rules |

A mediator may use Observer to receive changes. A command bus may be implemented as a mediator, but a generic event bus is not automatically a domain coordinator. A broker adds process, failure and delivery boundaries that this local example does not provide. A Facade can expose mutations as well as reads; one-way versus bidirectional traffic alone is an unreliable distinction.

## Summary

Move scattered interaction rules into one cohesive coordinator. Trace which participant announces a change, which rule runs and which participant receives the result. Keep the boundary small and make feedback, asynchronous results and failures explicit.

# Memento Pattern

> **TL;DR:** Memento captures an object's internal state and externalizes it so the object can be restored later — without violating encapsulation. Use it for undo/redo, snapshots, transactions, and state rollback.

<!-- section: Design Patterns | category: Architecture | subcategory: Behavioral | tags: concept, gof -->

## Definition

The Memento pattern is a behavioral design pattern that lets you save and restore the previous state of an object without revealing the details of its implementation.

It's one of the 23 GoF patterns. The key insight: a **Memento** object stores a snapshot of another object's state. The original object (the **Originator**) creates the memento and uses it to restore itself. A **Caretaker** holds the mementos (e.g., for undo history) but doesn't inspect or modify them.

```text
┌───────────────────────────────────────────┐
│ Originator                                │
│ - state: ...                              │
│ + save(): Memento // creates snapshot     │
│ + restore(m: Memento) // restores from it │
└───────────────────────────────────────────┘
                    ▲ ▲
                    │ creates │ uses                                
                    │         │                          
            ┌───────┴────────┐│
            │ Memento      │    │
            │ - state: ... │    │
            │ (opaque)     │    │
            └────────────────┘│
                    ▲ │                                    
                    │ holds         │
                    ├──────────────┤
            ┌───────┴────────────────┴──────┐
            │ Caretaker     │
            │ - mementos: Me│
            │ + push(m: Meme│
            │ + pop(): Memen│
            └───────────────────────────────┘
```

The Memento is **opaque** to the Caretaker — it can hold it, pass it back, but can't read or modify its contents. This preserves encapsulation.

## Why Do We Need It?

### Without Memento

```typescript
// BAD: external code directly accesses internal state
class Editor {
  private text: string = '';
  private cursorPos: number = 0;
  private selection: string = '';
  private formatting: FormatState = new FormatState();
}

class UndoManager {
  private snapshots: any[] = [];

  save(editor: Editor) {
    // Direct access to private state — breaks encapsulation
    this.snapshots.push({
      text: editor.text,
      cursorPos: editor.cursorPos,
      selection: editor.selection,
      formatting: editor.formatting,
    });
  }

  restore(editor: Editor, snapshot: any) {
    editor.text = snapshot.text;
    editor.cursorPos = snapshot.cursorPos;
    // ... more direct writes
  }
}
```

**Problems:**
1. **Encapsulation broken** — the snapshot logic knows all the editor's private fields
2. **Tight coupling** — if `Editor` adds a new field, `UndoManager` must be updated
3. **Hard to keep in sync** — manual `text: editor.text` lines are easy to miss
4. **No integrity** — the snapshot is just a plain object; nothing enforces completeness

### With Memento

```typescript
class Editor {
  private text: string = '';
  private cursorPos: number = 0;
  private formatting: FormatState = new FormatState();

  save(): EditorMemento {
    return new EditorMemento(
      structuredClone({ text: this.text, cursorPos: this.cursorPos, formatting: this.formatting })
    );
  }

  restore(m: EditorMemento) {
    const state = m.getState();
    this.text = state.text;
    this.cursorPos = state.cursorPos;
    this.formatting = state.formatting;
  }
}

class EditorMemento {
  constructor(private state: EditorState) {}
  getState(): EditorState { return this.state; }
}

class UndoManager {
  private history: EditorMemento[] = [];
  save(editor: Editor) { this.history.push(editor.save()); }
  undo(editor: Editor) {
    const m = this.history.pop();
    if (m) editor.restore(m);
  }
}
```

Now `Editor` controls its own snapshot logic, and `UndoManager` doesn't know about the editor's internals.

## How It Works

1. **Originator** — the object whose state needs to be saved. Has `save()` and `restore(m)` methods.
2. **Memento** — opaque object holding the state. Only the Originator can read/write its contents.
3. **Caretaker** — holds mementos (e.g., a history stack). Cannot inspect the memento's contents.

```typescript
class Originator {
  private state: string;

  setState(s: string) { this.state = s; }
  getState(): string { return this.state; }

  save(): Memento {
    return new Memento(this.state);
  }

  restore(m: Memento) {
    this.state = m.getState();
  }
}

class Memento {
  constructor(private state: string) {}
  getState(): string { return this.state; }
}

class Caretaker {
  private history: Memento[] = [];

  save(originator: Originator) {
    this.history.push(originator.save());
  }

  undo(originator: Originator) {
    const m = this.history.pop();
    if (m) originator.restore(m);
  }
}

// Usage
const editor = new Originator();
const history = new Caretaker();

editor.setState('Hello');
history.save(editor);

editor.setState('Hello, world!');
history.save(editor);

editor.setState('Hello, world!!!');

history.undo(editor);
console.log(editor.getState()); // "Hello, world!"

history.undo(editor);
console.log(editor.getState()); // "Hello"
```

## Real-World Examples

### 1. Undo/Redo in editors (the canonical example)

VS Code, Figma, Photoshop — every text/graphics editor uses Memento for undo. Each user action saves a memento; Ctrl+Z pops one.

### 2. Redux DevTools time-travel debugging

The Redux store serializes its state at every action. DevTools keeps a stack of mementos and lets you "jump" to any past state.

### 3. Jest snapshot testing

```typescript
expect(component).toMatchSnapshot();
```

Jest saves the rendered output as a "memento" (a file). On the next run, it restores the saved snapshot and diffs. The test code doesn't know what the snapshot contains — it's opaque.

### 4. Database transactions

A transaction log is a sequence of mementos. The database can roll back to any previous state by applying the inverse of the operations in the log.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- If something fails:
ROLLBACK; -- restore to the BEGIN state
```

### 5. Git commits

A git commit is a memento of the entire working tree. `git checkout <commit>` restores that state. The memento is content-addressable (hash-based) and opaque.

### 6. Game save files

A "save game" is a memento of the game's state. Loading the save restores the game.

### 7. Browser back button

The browser keeps a history of pages — each page is a memento. Pressing back restores the previous state.

### 8. State management libraries (MobX, Zustand with `temporal`)

Some state libraries support time-travel via mementos.

## When to Use

 **Use Memento when:**

- A snapshot of an object's state must be saved so it can be **restored later**
- A direct interface to obtaining the state would **expose implementation details** and break encapsulation
- You need **undo/redo** functionality
- You want **transactional** behavior (commit or rollback)
- You want **time-travel debugging** (jump to a past state)

 **Avoid Memento when:**

- The state is simple and you can just deep-clone it
- The object is immutable (no need to save state — it doesn't change)
- The state is huge (memory cost of saving full snapshots is too high)
- You have many small changes per second (use a command log, not full snapshots)
- The state contains non-serializable data (functions, refs to DOM nodes)

## How It Works in Code

### Editor with Memento

```typescript
interface EditorMemento {
  getText(): string;
  getCursor(): number;
  getSelectionStart(): number;
  getSelectionEnd(): number;
}

class TextEditor {
  private text: string = '';
  private cursor: number = 0;
  private selectionStart: number = 0;
  private selectionEnd: number = 0;

  insert(s: string) { this.text = this.text.slice(0, this.cursor) + s + this.text.slice(this.cursor); this.cursor += s.length; }
  setCursor(pos: number) { this.cursor = pos; }
  select(start: number, end: number) { this.selectionStart = start; this.selectionEnd = end; }

  save(): EditorMemento {
    return {
      getText: () => this.text,
      getCursor: () => this.cursor,
      getSelectionStart: () => this.selectionStart,
      getSelectionEnd: () => this.selectionEnd,
    };
  }

  restore(m: EditorMemento) {
    this.text = m.getText();
    this.cursor = m.getCursor();
    this.selectionStart = m.getSelectionStart();
    this.selectionEnd = m.getSelectionEnd();
  }
}

class UndoStack {
  private stack: EditorMemento[] = [];
  push(m: EditorMemento) { this.stack.push(m); }
  pop(): EditorMemento | undefined { return this.stack.pop(); }
}
```

### Functional Memento (using `structuredClone`)

```typescript
type State = { /* any serializable data */ };

class StateHistory<T extends State> {
  private history: T[] = [];

  save(state: T) {
    this.history.push(structuredClone(state));
  }

  restore(): T | undefined {
    return this.history.pop();
  }
}

// Usage
const history = new StateHistory<{ count: number; items: string[] }>();
let state = { count: 0, items: [] };

state = { count: 1, items: ['a'] };
history.save(state);

state = { count: 2, items: ['a', 'b'] };
history.save(state);

const previous = history.restore()!;
state = { ...state, ...previous }; // count: 1, items: ['a']
```

### Diff-based Memento (for large states)

For huge states, saving a full snapshot is expensive. A diff-based Memento stores only the changes:

```typescript
type Change<T> = { from: T; to: T; key: keyof T };

class DiffHistory<T> {
  private changes: Change<T>[] = [];

  save(prev: T, next: T) {
    const changes: Change<T>[] = [];
    for (const key of Object.keys(next) as (keyof T)[]) {
      if (prev[key] !== next[key]) {
        changes.push({ from: prev[key], to: next[key], key });
      }
    }
    this.changes.push(...changes);
  }

  undo(state: T): T {
    const last = this.changes.pop();
    if (!last) return state;
    return { ...state, [last.key]: last.from };
  }
}
```

This is a Command pattern (each change is a command) used as a Memento.

## Comparisons

### Memento vs Command

- **Command** encapsulates **an action** ("do this" / "undo this"). The state is the side effect.
- **Memento** encapsulates **a state snapshot** ("here's the state at time T").

Use Memento for "go back to this state". Use Command for "do this action; later, undo it".

### Memento vs Prototype

- **Prototype** creates a **new object** that's a copy. Both old and new are independently usable.
- **Memento** stores the **state snapshot** of an object. The original continues to exist; the memento is read-only.

### Memento vs Serialization

Serialization (JSON, structuredClone) is a way to implement Memento. The Memento pattern is the **design** of saving state for restore; the **mechanism** is serialization.

### Memento vs Event Sourcing

- **Memento** saves **the state** at points in time.
- **Event Sourcing** saves **the events** that led to the state. State is derived by replaying events.

| Memento     | Event Sourcing           |                            |
| --          | ---------                | ----------------           |
| **Stores**  | State                    | Events                     |
| **Size**    | Large (full state)       | Smaller (just the changes) |
| **Restore** | Direct                   | Replay events              |
| **Audit**   | Implicit (snapshot at T) | Explicit (full history)    |

## Code Example: Undo/Redo with Limits

```typescript
class TextEditor {
  private text: string = '';

  insert(s: string, pos: number) { this.text = this.text.slice(0, pos) + s + this.text.slice(pos); }
  delete(start: number, end: number) { this.text = this.text.slice(0, start) + this.text.slice(end); }

  save(): EditorMemento {
    return new EditorMemento(this.text);
  }

  restore(m: EditorMemento) {
    this.text = m.getState();
  }

  getText() { return this.text; }
}

class EditorMemento {
  constructor(private state: string) {}
  getState() { return this.state; }
}

class HistoryManager {
  private undoStack: EditorMemento[] = [];
  private redoStack: EditorMemento[] = [];

  constructor(private editor: TextEditor, private maxSize = 100) {}

  // Call this BEFORE a change
  checkpoint() {
    this.undoStack.push(this.editor.save());
    if (this.undoStack.length > this.maxSize) this.undoStack.shift();
    this.redoStack = []; // any new change clears redo
  }

  undo() {
    const m = this.undoStack.pop();
    if (!m) return;
    this.redoStack.push(this.editor.save());
    this.editor.restore(m);
  }

  redo() {
    const m = this.redoStack.pop();
    if (!m) return;
    this.undoStack.push(this.editor.save());
    this.editor.restore(m);
  }
}

// Usage
const editor = new TextEditor();
const history = new HistoryManager(editor);

editor.insert('Hello', 0);
history.checkpoint();

editor.insert(' World', 5);
history.checkpoint();

console.log(editor.getText()); // "Hello World"

history.undo();
console.log(editor.getText()); // "Hello"

history.redo();
console.log(editor.getText()); // "Hello World"
```

## Common Pitfalls

### 1. **Memory bloat from saving full state**

If the state is huge and you save every change, memory explodes. Use:
- Limits on the undo stack
- Diff-based mementos (store only changes)
- Periodic snapshots + diffs between snapshots

### 2. **Forgetting to deep-clone**

```typescript
// BAD: shared reference — undo doesn't work as expected
save(): Memento {
  return new Memento(this.text, this.items); // items is shared!
}
```

Always deep-clone mutable fields. Use `structuredClone()` or manual deep copy.

### 3. **Breaking encapsulation**

If the Memento is just `{ text, cursor, ... }` and the Caretaker reads these fields, you've broken encapsulation. Use a class with a private constructor or make the fields truly opaque.

### 4. **Storing non-serializable data**

DOM nodes, functions, class instances with private state — these may not survive `structuredClone` and could cause issues on restore.

### 5. **No integrity check**

If the memento's data is corrupted, restoring it could put the system in an invalid state. Add a version number or checksum.

## Best Practices

1. **Use `structuredClone()` for deep copies** — handles cycles, Maps, Sets, Dates.
2. **Keep the memento opaque** — only the Originator should be able to read its contents.
3. **Limit history size** — don't keep 10,000 snapshots of a 100MB object.
4. **Consider diff-based mementos** for large states (use a Command log instead).
5. **Add a version number** to detect incompatible mementos after upgrades.
6. **Combine with Command** — each Command can save a Memento; that's how complex undo works.

## Summary

Memento is the **snapshot pattern**. It captures an object's state in an opaque way so it can be restored later without breaking encapsulation. The most common use is undo/redo, but it also powers transactions, snapshot testing, and time-travel debugging.

**Interview-ready one-liner:** "Memento captures and externalizes an object's internal state so it can be restored later — without exposing the implementation. The Caretaker holds mementos but can't read them; only the Originator can."

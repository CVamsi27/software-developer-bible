# Command Pattern

> **TL;DR:** Command encapsulates a **request as an object**, decoupling the sender from the receiver. Use it to parameterize, queue, log, and undo operations — and to build transaction-like, macro, and undo/redo systems.

<!-- section: Design Patterns | category: Architecture | subcategory: Behavioral | tags: concept, gof -->

## Definition

The Command pattern is a behavioral design pattern that turns a request into a stand-alone object that contains all information about the request. This transformation lets you parameterize methods with different requests, delay or queue a request's execution, and support undo.

It's one of the 23 GoF patterns. The key insight: instead of the client calling a method directly on a receiver, it creates a **Command** object that represents the request. The command is then executed (now or later) by an **Invoker**.

```text
┌─────────────────────┐
│ Client              │
└─────────────────────┘
        │ creates
        ▼
┌─────────────────────┐ ┌──────────────────┐
│ Command (interface)│ │ Invoker              │
│ + execute() │ │ - history                   │
│ + undo()                                    │ │ + run(c) │
└─────────────────────────────────────────────┘ │ + undo()         │
        ▲ └──────────────────┘
        │                    │ calls
        │ implements │
        │ ▼
┌───────┴──────────┐ ┌──────────────────┐
│ ConcreteCommand │ ── receiver ── │ Receiver │
│ - receiver │ │ + action()                   │
│ - state │ └──────────────────┘
│ + execute()                                 │
│ + undo()                                    │
└──────────────────┘
```

## Why Do We Need It?

### Without Command

```typescript
// BAD: tightly coupled, no undo, no queuing
class RemoteControl {
  private light: Light;
  private tv: TV;
  private stereo: Stereo;

  onLightButton() { this.light.on(); }
  offLightButton() { this.light.off(); }
  onTVButton() { this.tv.on(); }
  offTVButton() { this.tv.off(); }
  // ... 6 more buttons × 2 = 12 more methods
}
```

**Problems:**
1. **Combinatorial explosion** — adding a new device means adding 2 more methods to the remote
2. **No undo** — once you call `light.on()`, you can't undo it
3. **No queuing** — you can't "do this later" or "do all of these in order"
4. **No history** — you can't see "what happened"

### With Command

```typescript
// GOOD: remote just holds commands; each device command is an object
interface Command {
  execute(): void;
  undo(): void;
}

class LightOnCommand implements Command {
  constructor(private light: Light) {}
  execute() { this.light.on(); }
  undo() { this.light.off(); }
}

class TVOnCommand implements Command {
  constructor(private tv: TV) {}
  execute() { this.tv.on(); }
  undo() { this.tv.off(); }
}

class RemoteControl {
  private slots: Command[] = []; // each button holds a command

  setCommand(slot: number, command: Command) { this.slots[slot] = command; }
  pressButton(slot: number) { this.slots[slot].execute(); }
  pressUndo() {
    // undo the last executed command
  }
}
```

Adding a new device is one new `Command` class — no changes to the remote.

## How It Works

1. **Command interface** — declares `execute()` (and optionally `undo()`).
2. **ConcreteCommand** — implements the interface; holds a reference to the receiver and the parameters.
3. **Receiver** — knows how to perform the work (e.g., `Light.on()`).
4. **Invoker** — holds commands and calls them.
5. **Client** — creates the concrete command and sets its receiver.

```typescript
interface Command {
  execute(): void;
  undo(): void;
}

class Light {
  on() { console.log('Light on'); }
  off() { console.log('Light off'); }
}

class LightOnCommand implements Command {
  constructor(private light: Light) {}
  execute() { this.light.on(); }
  undo() { this.light.off(); }
}

class RemoteControl {
  private history: Command[] = [];

  executeCommand(c: Command) {
    c.execute();
    this.history.push(c);
  }

  undo() {
    const c = this.history.pop();
    if (c) c.undo();
  }
}

const light = new Light();
const remote = new RemoteControl();

remote.executeCommand(new LightOnCommand(light)); // Light on
remote.undo(); // Light off
```

## Real-World Examples

### 1. Job queues (BullMQ, Sidekiq, Celery)

A job is a Command. The worker pulls jobs from the queue and executes them. Jobs can be retried, scheduled, and tracked.

```typescript
// BullMQ
const queue = new Queue('emails');
await queue.add('welcome', { userId: 123 }); // 'welcome' is the command
```

### 2. Redux actions

```typescript
dispatch({ type: 'INCREMENT', payload: 1 });
// The reducer is the receiver; the action is the command.
```

Redux is essentially a Command pattern: actions are commands, the store is the invoker, reducers are receivers.

### 3. CQRS (Command Query Responsibility Segregation)

In CQRS, every state change is a Command. Commands are objects, validated and dispatched to handlers.

```typescript
class CreateUserCommand {
  constructor(public email: string, public password: string) {}
}

class CreateUserHandler {
  async handle(cmd: CreateUserCommand) {
    // create user
  }
}

// Dispatcher
async function dispatch(cmd: CreateUserCommand) {
  const handler = container.resolve(CreateUserHandler);
  return handler.handle(cmd);
}
```

### 4. Git

Each git command (`git commit`, `git merge`) is a command object. Many commands have a corresponding undo (`git revert`, `git reset`).

### 5. Macro recording

A "macro" is a list of commands. You record user actions as commands, then play them back.

```typescript
class Macro implements Command {
  constructor(private commands: Command[]) {}
  execute() { for (const c of this.commands) c.execute(); }
  undo() { for (let i = this.commands.length - 1; i >= 0; i--) this.commands[i].undo(); }
}
```

### 6. Transactional operations

A transaction is a list of commands. If any fails, all previous commands are undone.

```typescript
class Transaction implements Command {
  private history: Command[] = [];
  async execute() {
    for (const c of this.commands) {
      try {
        await c.execute();
        this.history.push(c);
      } catch (e) {
        for (let i = this.history.length - 1; i >= 0; i--) {
          await this.history[i].undo();
        }
        throw e;
      }
    }
  }
}
```

### 7. Database migration tools

Each migration is a command with `up` and `down` methods.

```typescript
class AddUserTableMigration implements Migration {
  up(db) { db.exec(`CREATE TABLE users ...`); }
  down(db) { db.exec(`DROP TABLE users`); }
}
```

### 8. Editor commands (VS Code, IntelliJ)

Each editor action (`Ctrl+B` for bold, `Ctrl+I` for italic) is a command. They can be:
- Tied to keyboard shortcuts
- Recorded in macros
- Replayed by automation

## When to Use

 **Use Command when:**

- You want to **parameterize** objects by the action to perform
- You want to **specify, queue, and execute** requests at different times
- You need **undo/redo**
- You want to **log all changes** so they can be reapplied after a crash
- You want to **structure a system** around high-level operations built on primitive operations
- You want **macro recording** (record actions, replay them)

 **Avoid Command when:**

- The operation is one-shot with no undo/redo
- The command would be a thin wrapper around a single method call (just call the method)
- The state is too complex to undo (some operations can't be reversed — e.g., "send email")
- You don't need to queue or log operations

## How It Works in Code

### Command with state for undo

```typescript
class TextEditor {
  private text = '';
  insert(s: string, pos: number) { this.text = this.text.slice(0, pos) + s + this.text.slice(pos); }
  delete(start: number, end: number) { this.text = this.text.slice(0, start) + this.text.slice(end); }
  getText() { return this.text; }
}

class InsertCommand implements Command {
  constructor(
    private editor: TextEditor,
    private text: string,
    private pos: number,
  ) {}
  execute() { this.editor.insert(this.text, this.pos); }
  undo() { this.editor.delete(this.pos, this.pos + this.text.length); }
}

class DeleteCommand implements Command {
  private deletedText = '';
  constructor(
    private editor: TextEditor,
    private start: number,
    private end: number,
  ) {}
  execute() {
    this.deletedText = this.editor.getText().slice(this.start, this.end);
    this.editor.delete(this.start, this.end);
  }
  undo() { this.editor.insert(this.deletedText, this.start); }
}
```

### Functional Command in TypeScript

```typescript
type Command = {
  execute: () => void;
  undo: () => void;
};

const insertCommand = (editor: Editor, text: string, pos: number): Command => {
  const oldText = editor.getText();
  return {
    execute: () => editor.insert(text, pos),
    undo: () => editor.setText(oldText),
  };
};
```

### Command queue (background job processing)

```typescript
class CommandQueue {
  private queue: Command[] = [];
  private running = false;

  enqueue(c: Command) {
    this.queue.push(c);
    if (!this.running) this.run();
  }

  private async run() {
    this.running = true;
    while (this.queue.length > 0) {
      const c = this.queue.shift()!;
      try {
        await c.execute();
      } catch (e) {
        await c.undo?.();
        console.error('Command failed', e);
      }
    }
    this.running = false;
  }
}
```

## Comparisons

### Command vs Memento

- **Command** encapsulates **an action** ("do this, undo this").
- **Memento** encapsulates **a state** ("here's the state at time T").

Use Command for action-based undo. Use Memento for state-based undo.

| Command | Memento |  |
| -- | --------- | --------- |
| **What's saved** | The action to perform | The state at a point in time |
| **Size** | Small (just params + receiver) | Large (full state) |
| **When to use** | Operations can be parameterized and replayed | State is hard to capture via inverse operations |

### Command vs Strategy

- **Strategy** swaps the **algorithm** that runs in a context.
- **Command** turns a **request** into an object (which can be queued, logged, undone).

| Strategy | Command |  |
| -- | ---------- | --------- |
| **Encapsulates** | An algorithm | A request |
| **Used for** | Behavior selection | Action queuing, undo, logging |
| **The "thing" itself** | The algorithm | The request |

### Command vs Observer

- **Command** is a **one-to-one** request-response: client → invoker → receiver.
- **Observer** is a **one-to-many** notification: subject → observers.

Command is for "do this specific thing". Observer is for "tell anyone interested that this happened".

### Command vs CQRS

CQRS uses Command as its "C" — every state change is a command. But Command pattern is more general; you can use Command without CQRS.

## Code Example: Smart Home Remote

```typescript
interface Command {
  execute(): void;
  undo(): void;
  name: string;
}

class Light {
  isOn = false;
  on() { this.isOn = true; console.log('Light ON'); }
  off() { this.isOn = false; console.log('Light OFF'); }
}

class Thermostat {
  temperature = 20;
  setTemp(t: number) { this.temperature = t; console.log(`Temp set to ${t}`); }
}

class LightOnCommand implements Command {
  name = 'Light On';
  constructor(private light: Light) {}
  execute() { this.light.on(); }
  undo() { this.light.off(); }
}

class SetTempCommand implements Command {
  name = 'Set Temperature';
  private prevTemp: number = 0;
  constructor(private thermo: Thermostat, private target: number) {}
  execute() {
    this.prevTemp = this.thermo.temperature;
    this.thermo.setTemp(this.target);
  }
  undo() { this.thermo.setTemp(this.prevTemp); }
}

class RemoteControl {
  private slots: (Command | null)[] = [null, null, null, null, null, null, null];
  private history: Command[] = [];

  setSlot(slot: number, cmd: Command) { this.slots[slot] = cmd; }
  pressButton(slot: number) {
    const cmd = this.slots[slot];
    if (cmd) {
      cmd.execute();
      this.history.push(cmd);
    }
  }
  pressUndo() {
    const cmd = this.history.pop();
    if (cmd) cmd.undo();
  }
  listButtons() {
    return this.slots.map((c, i) => `${i}: ${c?.name || '(empty)'}`).join('\n');
  }
}

// Usage
const light = new Light();
const thermo = new Thermostat();
const remote = new RemoteControl();

remote.setSlot(0, new LightOnCommand(light));
remote.setSlot(1, new SetTempCommand(thermo, 22));
remote.setSlot(2, new SetTempCommand(thermo, 18));

console.log(remote.listButtons());
// 0: Light On
// 1: Set Temperature
// 2: Set Temperature

remote.pressButton(0); // Light ON
remote.pressButton(1); // Temp set to 22
remote.pressUndo(); // Temp set to 20 (undo)
remote.pressUndo(); // Light OFF
```

## Common Pitfalls

### 1. **Commands that can't undo**

`SendEmailCommand.execute()` runs. How do you undo it? You can't unsend an email. Either:
- Don't include such commands in the undo stack
- Implement a "compensating action" (send a follow-up "please ignore previous email")

Document what can and can't be undone.

### 2. **State leakage between commands**

If a command's undo relies on state captured at execute time, ensure it's captured (not assumed to be the current state). Use a Memento internally for the undo state if needed.

### 3. **Memory bloat from history**

A long-running session with many commands fills memory. Either:
- Limit history size
- Snapshot periodically + diff between snapshots
- Use weak references

### 4. **Threading / async issues**

If commands are async, undo also needs to be async. Make `execute()` and `undo()` return Promises.

### 5. **Over-wrapper for trivial operations**

`new IncrementCounterCommand(counter).execute()` is overkill for `counter.increment()`. Use Command only when the indirection adds value (undo, queue, log, macro).

## Best Practices

1. **Keep commands small and focused** — one command, one operation.
2. **Implement `undo()` for every command** — even if it just no-ops, document why.
3. **Use a Command queue for async work** — BullMQ, Sidekiq, custom.
4. **Combine with Memento** — when the state is hard to capture via inverse operations, save a Memento in the command.
5. **Document what's reversible** — `IUndoableCommand` vs `ICommand`.
6. **Test commands in isolation** — they're easy to test (just call execute, then undo, and assert state).

## Summary

Command is the **request-as-object** pattern. It decouples the sender from the receiver and unlocks powerful features: undo/redo, queuing, logging, macros, and CQRS. The cost is indirection — every operation becomes a class — so use it only when you need at least one of those features.

**Interview-ready one-liner:** "Command turns a request into an object so you can parameterize, queue, log, and undo it — like Redux actions, job queues, and editor undo systems."

## Cheat Sheet

| Aspect | Detail |
| -------------- | ------------------------------------------------------------- |
| **Category** | Behavioral (GoF) |
| **Intent** | Encapsulate a request as an object |
| **Motivation** | Undo/redo, queues, logging, macros, CQRS |
| **Key signal** | "I need to undo, queue, or log this operation" |
| **Cost** | Indirection, every operation becomes a class |
| **Pairs with** | Memento (for hard-to-reverse ops), Mediator (for dispatching) |

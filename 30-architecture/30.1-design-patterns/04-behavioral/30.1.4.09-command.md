# Command Pattern

A toolbar button and a keyboard shortcut may request the same save operation. If both reach into persistence code, each must know how saving works. A Command packages the request so either trigger can invoke it — and the same request can be recorded, queued, or undone when its design supports those steps:

```typescript
button.click();            // execute()
undoHistory.pop()!.undo(); // back to false
```

## Definition

**Command** represents a **request as an object** that a separate **invoker** can execute. The client creates and configures the request; the invoker decides when to run it; the command delegates the work to a receiver. This separates the trigger from the operation — without promising every command is queueable, durable, or reversible.

> **Textbook Definition:** "Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations." — GoF intent, quoted in [*Spring 5 Design Patterns*](https://www.oreilly.com/library/view/spring-5-design/9781788299459/e4192dd1-85f8-4eff-9a6d-839ed5e2e9a8.xhtml)

## First Principles

The client binds a request to its receiver and gives it to an invoker, such as a button. The invoker calls `execute()` without knowing the receiver's details. Because the request is represented independently, callers can swap it, retain it, or pass it to another execution boundary. A function is often simpler for a one-off local callback; use a Command when the request needs a shared invocation contract, metadata, history, or a defined path to delayed execution.

## How It Works

### 1. Separate the trigger from the operation

```typescript
interface Command { execute(): void }
interface UndoableCommand extends Command { undo(): void }

class Light {
  on = false;
}

class SetLight implements UndoableCommand {
  private previous: boolean | undefined;
  constructor(private readonly light: Light, private readonly desired: boolean) {}

  execute(): void {
    if (this.previous !== undefined) throw new Error('Command already executed');
    this.previous = this.light.on;
    this.light.on = this.desired;
  }

  undo(): void {
    if (this.previous === undefined) throw new Error('Command not executed');
    this.light.on = this.previous;
    this.previous = undefined;
  }
}

const light = new Light();
const turnOn = new SetLight(light, true);
const undoHistory: UndoableCommand[] = [];
class Button {
  constructor(private readonly command: Command) {}
  click(): void { this.command.execute(); }
}
const button = new Button(turnOn);
button.click();
undoHistory.push(turnOn);
console.log(light.on); // true
undoHistory.pop()!.undo();
console.log(light.on); // false
```

Here, `Light` is the receiver, `SetLight` the command, and `Button` the invoker. The client connects them. Execution captures the preceding value, then applies the change. Undo restores that captured value rather than assuming the inverse of "on" is always the original state. The guards allow execution again after undo but reject a second execution before undo.

```text
client configures command → invoker calls execute() → command changes receiver
                                                     → optional history retains command
                                                       and later calls undo()
```

This example assumes one owner changes the light and history undoes in order. If another actor changes it between execution and undo, blindly restoring an old value can erase their work. Concurrent systems require versions, conflict rules, or a domain compensation operation.

### 2. Make a queued command serializable data

A closure such as `() => light.on = true` can represent an in-process command. A class holding a live receiver reference is not automatically serializable either. For a durable job, store a versioned, validated request such as `{ id, actorId, type, targetId, desired }`; let a worker resolve the receiver through explicitly registered handlers rather than serializing an object reference or dispatching arbitrary method names.

Persist the request identity and outcome before relying on retries. Check the actor's applicable authorization when execution occurs, keep secrets out of job payloads, and define deadlines and retention. A durable queue may redeliver after a worker fails; the Command pattern supplies no idempotency or exactly-once effects.

Commands express intent; events describe accepted facts. A CQRS write request may use a command object, but CQRS itself requires no class per operation. Redux actions are data messages to state logic and may represent events rather than imperative commands.

### 3. Limit undo to reversible boundaries

Expose `undo` only when it is meaningful. A no-op undo method falsely suggests reversibility. An email cannot be unsent by restoring local state. A refund or follow-up message is a compensating business action with its own failures.

Running several commands and invoking inverses on failure is not equivalent to an atomic database transaction. Earlier effects may already be visible, compensation can fail, and irreversible effects may remain. Use a database transaction for local atomic changes and a recoverable saga when distributed compensation is the intended contract. Bound command history by entry count and retained size. For concurrent edits, attach a version or define a conflict policy before restoring old state; otherwise undo can overwrite a later actor's work.

## Summary

Capture a request so execution policy can be separated from its trigger. Trace what is captured, when it runs and what happens on repeat or failure. Add undo only for a defined reversible boundary, and give durable commands identity, validation and recovery rules.

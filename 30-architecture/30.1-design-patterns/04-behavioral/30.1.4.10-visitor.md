# Visitor Pattern

> **TL;DR:** Visitor separates algorithms from the objects they operate on. You define a new operation (the visitor) without changing the classes of the elements it visits. Use it when you have a complex object structure (e.g., an AST) and you need to perform many distinct operations on it.

<!-- section: Design Patterns | category: Architecture | subcategory: Behavioral | tags: concept, gof -->

## Definition

The Visitor pattern is a behavioral design pattern that lets you separate algorithms from the objects on which they operate. It allows you to add new operations to existing object structures without modifying those structures.

It's one of the 23 GoF patterns. The key insight: instead of putting the operation in each element class (`Circle.area()`, `Square.area()`, `Triangle.area()`), you create a **Visitor** that knows how to operate on each element type. Each element has an `accept(visitor)` method that calls `visitor.visit(this)`.

```text
┌──────────────────────────────────┐
│ Visitor (interface)              │
│ + visitElementA(e: ElementA)     │
│ + visitElementB(e: ElementB)     │
│ + visitElementC(e: ElementC)     │
└──────────────────────────────────┘
        ▲
        │ implements
        │
┌──────────────────────────────┐
│ ConcreteVisitor (e.g., Area) │
│ + visitElementA(e) { ... }   │
│ + visitElementB(e) { ... }   │
└──────────────────────────────┘

┌──────────────────────────────────┐
│ Element (interface)              │
│ + accept(v: Visitor): void       │
└──────────────────────────────────┘
        ▲
        │ implements
        │
┌─────────────────────────────────────────────┐ ┌──────────────┐ ┌──────────────┐
│ ElementA │ │ ElementB │ │ ElementC          │
│ + accept(v) │ │ + accept(v) │ │ + accept(v) │
└─────────────────────────────────────────────┘ └──────────────┘ └──────────────┘
       ▲ ▲ ▲
       │ │ │
       └────────────────┴────────────────┘
              visited by the visitor
```

## Why Do We Need It?

### Without Visitor

```typescript
// BAD: operations baked into the element classes
abstract class Shape {
  abstract area(): number;
  abstract perimeter(): number;
  // To add a new operation (e.g., boundingBox), edit every Shape subclass
  abstract boundingBox(): BoundingBox;
  abstract serialize(): string; // edit again
  abstract toSVG(): string; // edit again
  abstract toJSON(): string; // edit again
}

class Circle extends Shape {
  area() { return Math.PI * this.r ** 2; }
  perimeter() { return 2 * Math.PI * this.r; }
  boundingBox() { /* ... */ }
  serialize() { /* ... */ }
  toSVG() { /* ... */ }
  toJSON() { /* ... */ }
}

class Square extends Shape {
  // ... 6 methods, one per operation
}

class Triangle extends Shape {
  // ... 6 methods
}
```

**Problems:**
1. **Combinatorial class explosion** — N shapes × M operations = N×M methods
2. **Editing every class to add a feature** — open-closed violation
3. **Mixing concerns** — geometry + serialization + rendering in one class

### With Visitor

```typescript
// GOOD: shapes know about visitors; operations are separate
interface ShapeVisitor<T> {
  visitCircle(c: Circle): T;
  visitSquare(s: Square): T;
  visitTriangle(t: Triangle): T;
}

abstract class Shape {
  abstract accept<T>(v: ShapeVisitor<T>): T;
}

class Circle extends Shape {
  constructor(public r: number) { super(); }
  accept<T>(v: ShapeVisitor<T>): T { return v.visitCircle(this); }
}

class Square extends Shape {
  constructor(public side: number) { super(); }
  accept<T>(v: ShapeVisitor<T>): T { return v.visitSquare(this); }
}

// Operations as visitors — add new ops without touching Shape
class AreaCalculator implements ShapeVisitor<number> {
  visitCircle(c: Circle) { return Math.PI * c.r ** 2; }
  visitSquare(s: Square) { return s.side ** 2; }
  visitTriangle(t: Triangle) { return 0.5 * t.base * t.height; }
}

class SVGExporter implements ShapeVisitor<string> {
  visitCircle(c: Circle) { return `<circle r="${c.r}" />`; }
  visitSquare(s: Square) { return `<rect width="${s.side}" height="${s.side}" />`; }
  visitTriangle(t: Triangle) { return `<polygon points="..." />`; }
}

class JSONSerializer implements ShapeVisitor<string> {
  visitCircle(c: Circle) { return JSON.stringify({ type: 'circle', r: c.r }); }
  visitSquare(s: Square) { return JSON.stringify({ type: 'square', side: s.side }); }
  visitTriangle(t: Triangle) { return JSON.stringify({ type: 'triangle' }); }
}
```

Adding a new operation (`BoundingBoxCalculator`) is **one new class** — no edits to `Shape`, `Circle`, `Square`, or `Triangle`.

## How It Works

1. **Visitor interface** — declares a `visit` method for each element type.
2. **Element interface** — declares `accept(visitor)`.
3. **Concrete elements** — implement `accept` by calling `visitor.visit(this)`.
4. **Concrete visitors** — implement the operations for each element type.

The **double-dispatch** is the key trick: `element.accept(visitor)` calls `visitor.visit(element)`, and the visitor dispatches on the element's actual type. This is the only way to get runtime polymorphism on the visitor side in a statically-typed language.

```typescript
const shapes: Shape[] = [new Circle(5), new Square(10)];

const areaCalc = new AreaCalculator();
const totalArea = shapes.reduce((sum, s) => sum + s.accept(areaCalc), 0);

const svgExporter = new SVGExporter();
const svgs = shapes.map(s => s.accept(svgExporter));
```

## Real-World Examples

### 1. AST traversal in compilers

The classic example. An AST has many node types (`BinaryOp`, `UnaryOp`, `Literal`, `Variable`, `FunctionCall`). The compiler runs multiple visitors over it:

- **Type checker** — verifies types of each node
- **Evaluator** — computes the result
- **Code generator** — emits target code
- **Optimizer** — rewrites nodes
- **Pretty printer** — formats the AST as text

```typescript
interface ExprVisitor<T> {
  visitBinaryOp(e: BinaryOp): T;
  visitUnaryOp(e: UnaryOp): T;
  visitLiteral(e: Literal): T;
  visitVariable(e: Variable): T;
}

abstract class Expr {
  abstract accept<T>(v: ExprVisitor<T>): T;
}

class BinaryOp extends Expr {
  constructor(public op: string, public left: Expr, public right: Expr) { super(); }
  accept<T>(v: ExprVisitor<T>): T { return v.visitBinaryOp(this); }
}

class Evaluator implements ExprVisitor<number> {
  visitBinaryOp(e: BinaryOp) {
    const l = e.left.accept(this);
    const r = e.right.accept(this);
    return e.op === '+' ? l + r : e.op === '-' ? l - r : /* ... */ 0;
  }
  visitLiteral(e: Literal) { return e.value; }
  visitVariable(e: Variable) { return this.env[e.name]; }
  visitUnaryOp(e: UnaryOp) { /* ... */ }
}
```

### 2. File system operations

```typescript
interface FSVisitor<T> {
  visitFile(f: File): T;
  visitDirectory(d: Directory): T;
  visitSymlink(s: Symlink): T;
}

class SizeCalculator implements FSVisitor<number> {
  visitFile(f: File) { return f.size; }
  visitDirectory(d: Directory) {
    let total = 0;
    for (const child of d.children) total += child.accept(this);
    return total;
  }
  visitSymlink(s: Symlink) { return 0; } // or follow it
}

class SearchVisitor implements FSVisitor<boolean> {
  constructor(private target: string) {}
  visitFile(f: File) { return f.name === this.target; }
  visitDirectory(d: Directory) {
    if (d.name === this.target) return true;
    return d.children.some(c => c.accept(this));
  }
  visitSymlink(s: Symlink) { return s.name === this.target; }
}
```

### 3. Linting rules (ESLint)

Each ESLint rule is a Visitor that walks the AST and reports issues.

```typescript
const noConsoleLogRule: Rule = {
  create(context) {
    return {
      CallExpression(node) {
        if (node.callee.name === 'console') {
          context.report(node, 'Avoid console.log in production');
        }
      },
    };
  },
};
```

The ESLint runtime traverses the AST; the rule visits each node.

### 4. Object serialization (to JSON, XML, YAML, MessagePack)

Each format is a Visitor that knows how to serialize each type.

### 5. Tax calculation across product types

A product catalog has different product types (`Book`, `Food`, `Electronics`). Tax rates and rules differ per category and per jurisdiction. Each combination is a Visitor.

### 6. Schema validation

A JSON schema validator visits each node and applies constraints.

## When to Use

 **Use Visitor when:**

- An object structure contains many classes with **differing interfaces**, and you want to perform operations on them
- Many **distinct and unrelated operations** need to be performed on objects in a structure
- The classes defining the object structure **rarely change**, but you often want to define **new operations** over the structure
- The operations need to operate on **concrete types** (not just the interface)

 **Avoid Visitor when:**

- The element hierarchy is **unstable** (adding a new element type = editing every visitor)
- You only have **one or two operations** — direct methods on the elements are clearer
- The element classes shouldn't know about visitors (Visitor is intrusive)
- You're in a language with pattern matching (TypeScript discriminated unions often serve the same role)

## How It Works in Code

### Functional Visitor (less ceremony)

If your "elements" are a tagged union, you can use a `match` function:

```typescript
type Shape =
  | { type: 'circle'; r: number }
  | { type: 'square'; side: number }
  | { type: 'triangle'; base: number; height: number };

const visit = <T>(shape: Shape, fns: {
  circle: (s: { r: number }) => T;
  square: (s: { side: number }) => T;
  triangle: (s: { base: number; height: number }) => T;
}): T => fns[shape.type](shape as any);

const area = (s: Shape) => visit(s, {
  circle: ({ r }) => Math.PI * r ** 2,
  square: ({ side }) => side ** 2,
  triangle: ({ base, height }) => 0.5 * base * height,
});

const svg = (s: Shape) => visit(s, {
  circle: ({ r }) => `<circle r="${r}" />`,
  square: ({ side }) => `<rect width="${side}" height="${side}" />`,
  triangle: ({ base, height }) => `<polygon points="0,0 ${base},0 0,${height}" />`,
});
```

In TypeScript with discriminated unions, this is often **cleaner** than the classical Visitor.

### Hierarchical Visitor (with traversal)

A common pattern: the visitor traverses the structure itself.

```typescript
class FileSearchVisitor implements FSVisitor<boolean> {
  constructor(private pattern: RegExp) {}

  visitFile(f: File) {
    return this.pattern.test(f.name);
  }

  visitDirectory(d: Directory) {
    // Recursive traversal happens INSIDE the visitor
    return d.children.some(child => child.accept(this));
  }
}
```

The element delegates to the visitor; the visitor decides whether to recurse.

### Visitor with accumulation (collector)

```typescript
class FileCollector implements FSVisitor<void> {
  collected: File[] = [];

  visitFile(f: File) {
    this.collected.push(f);
  }

  visitDirectory(d: Directory) {
    for (const child of d.children) child.accept(this);
  }
}

const collector = new FileCollector();
root.accept(collector);
console.log(collector.collected);
```

## Comparisons

### Visitor vs Strategy

- **Strategy** swaps the **algorithm** that runs in a context.
- **Visitor** adds **operations on a structure** without modifying the structure.

| Strategy | Visitor |  |
| -- | ---------- | --------- |
| **Encapsulates** | An algorithm | An operation on a structure |
| **Applied to** | A single object | A structure of objects |
| **New "what"** | Add a new strategy | Add a new visitor |
| **Cost of new element type** | Low | High (edit every visitor) |

### Visitor vs Double Dispatch

Visitor is essentially a **double dispatch** pattern. The element dispatches on the visitor; the visitor dispatches on the element. Languages with multiple dispatch (CLOS, Julia) don't need this pattern.

### Visitor vs Iterator

- **Iterator** provides **sequential access** to a structure.
- **Visitor** performs **operations** on each element during traversal.

You often combine them: traverse with an Iterator, perform operations via a Visitor at each step.

### Visitor vs Interpreter

- **Visitor** operates on a structure (an existing AST, a tree of objects).
- **Interpreter** defines **the grammar of a language** and parses it into a structure.

Compiler pipeline: **Interpreter** builds the AST → **Visitor** walks the AST.

## Code Example: Document Object Model (DOM)

```typescript
interface NodeVisitor<T> {
  visitTextNode(n: TextNode): T;
  visitElementNode(n: ElementNode): T;
  visitCommentNode(n: CommentNode): T;
}

abstract class DOMNode {
  abstract accept<T>(v: NodeVisitor<T>): T;
}

class TextNode extends DOMNode {
  constructor(public text: string) { super(); }
  accept<T>(v: NodeVisitor<T>): T { return v.visitTextNode(this); }
}

class ElementNode extends DOMNode {
  constructor(public tag: string, public children: DOMNode[] = []) { super(); }
  accept<T>(v: NodeVisitor<T>): T { return v.visitElementNode(this); }
}

class CommentNode extends DOMNode {
  constructor(public text: string) { super(); }
  accept<T>(v: NodeVisitor<T>): T { return v.visitCommentNode(this); }
}

// Operations
class TextExtractor implements NodeVisitor<string> {
  visitTextNode(n: TextNode) { return n.text; }
  visitElementNode(n: ElementNode) {
    return n.children.map(c => c.accept(this)).join('');
  }
  visitCommentNode(n: CommentNode) { return ''; }
}

class ElementCounter implements NodeVisitor<number> {
  visitTextNode(n: TextNode) { return 0; }
  visitElementNode(n: ElementNode) {
    return 1 + n.children.reduce((sum, c) => sum + c.accept(this), 0);
  }
  visitCommentNode(n: CommentNode) { return 0; }
}

// Usage
const doc = new ElementNode('html', [
  new ElementNode('head', [new ElementNode('title', [new TextNode('My Page')])]),
  new ElementNode('body', [
    new ElementNode('h1', [new TextNode('Hello')]),
    new CommentNode(' TODO '),
    new ElementNode('p', [new TextNode('World')]),
  ]),
]);

doc.accept(new TextExtractor()); // "My PageHelloWorld"
doc.accept(new ElementCounter()); // 6 (html, head, title, body, h1, p)
```

## Common Pitfalls

### 1. **Visitor is intrusive**

Every element must have an `accept(visitor)` method. You can't add Visitor to a class hierarchy you don't own without modifying it.

**Workaround:** wrap the elements or use a tagged union + match.

### 2. **Adding a new element type is expensive**

Adding a `Trapezoid` shape means editing every visitor's interface (TypeScript will fail compilation). This is the classic Visitor tradeoff.

**Use Visitor only when elements rarely change.**

### 3. **Confusing intent with strategy**

Visitor is for "operate on a structure". Strategy is for "swap an algorithm". They look similar but differ in what varies.

### 4. **State leaks between visits**

A visitor that accumulates state (like a collector) — if you reuse the same instance, you'll get cross-contamination. Either create a new visitor per use or reset its state.

### 5. **Cycle handling**

If your structure has cycles (a file with a symlink to its parent), a naive visitor will infinite-loop. Add a "visited" set.

## Best Practices

1. **Use Visitor for stable structures** — the structure rarely changes; new operations are common.
2. **Use tagged unions + match** in TypeScript when elements change often (less ceremony).
3. **Make visitor methods pure** (no side effects on the elements) when possible — easier to reason about.
4. **Reset state** between visits if the visitor accumulates.
5. **Combine with Iterator** for traversal logic.
6. **Document the visitor's contract** — what does the visitor do on each element type?

## Summary

Visitor is the **operations-on-structures** pattern. It lets you add new operations to a class hierarchy without modifying it. The cost is that adding a new element type requires editing every visitor. In TypeScript, tagged unions with exhaustive matching often serve the same role with less ceremony.

**Interview-ready one-liner:** "Visitor lets you add new operations to an object structure without modifying the classes — the element dispatches to the visitor, and the visitor handles each element type. Great for AST traversal, file system operations, and complex object graphs."

## Cheat Sheet

| Aspect | Detail |
| ---------------------- | ------------------------------------------------------------------------ |
| **Category** | Behavioral (GoF) |
| **Intent** | Add operations without modifying the structure |
| **Motivation** | Compilers, file system ops, multiple serializers, schema validators |
| **Key signal** | "Many operations on a stable structure" |
| **Cost** | Intrusive (elements must have `accept`), new element = edit all visitors |
| **Modern alternative** | Tagged unions + pattern matching in TypeScript |

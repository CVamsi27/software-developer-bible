# Visitor Pattern

A document already has `Heading` and `Paragraph` nodes. Now it needs plain-text extraction and an outline. Adding each output operation to both node classes couples export behavior to the document model. Visitor moves each operation into its own object — best when node types change less often than operations:

```typescript
documentNodes.map(node => node.accept(plainText)); // ["Start", "Body"] — no node changes
```

## Definition

**Visitor** adds operations over a **stable family of element types** without placing each operation in every element class. Each element accepts a **visitor** and dispatches to the method for its concrete type; a concrete visitor supplies one operation across those types.

> **Textbook Definition:** "Represent an operation to be performed on the elements of an object structure." — GoF intent, quoted in [*Design Patterns in C#: A Hands-on Guide with Real-world Examples*](https://www.oreilly.com/library/view/design-patterns-in/9781484260623/html/463942_2_En_13_Chapter.xhtml)

## First Principles

When a caller holds only `DocumentNode`, it needs a way to reach behavior specific to `Heading` or `Paragraph`. The node's `accept` method makes that type choice and calls the matching method on the supplied visitor; the visitor provides the operation. This makes new operations easy to add — while a new node type expands the visitor contract and its implementations.

## 1. Dispatch twice: element first, then visitor

```typescript
interface DocumentVisitor<T> {
  paragraph(node: Paragraph): T;
  heading(node: Heading): T;
}
interface DocumentNode {
  accept<T>(visitor: DocumentVisitor<T>): T;
}
class Paragraph implements DocumentNode {
  constructor(readonly text: string) {}
  accept<T>(visitor: DocumentVisitor<T>): T { return visitor.paragraph(this); }
}
class Heading implements DocumentNode {
  constructor(readonly text: string, readonly level: number) {}
  accept<T>(visitor: DocumentVisitor<T>): T { return visitor.heading(this); }
}
const plainText: DocumentVisitor<string> = {
  paragraph: node => node.text,
  heading: node => node.text
};
const outline: DocumentVisitor<string> = {
  paragraph: () => '',
  heading: node => `${'  '.repeat(node.level - 1)}${node.text}`
};
const documentNodes: DocumentNode[] = [new Heading('Start', 1), new Paragraph('Body')];
console.log(documentNodes.map(node => node.accept(plainText)).join('\n'));
// Start
// Body
console.log(documentNodes.map(node => node.accept(outline)).filter(Boolean).join('\n'));
// Start
```

The caller holds only `DocumentNode`. A heading's `accept` selects `visitor.heading`; the supplied visitor determines what that operation does. `plainText` returns the text, while `outline` excludes paragraphs. Adding the outline operation changed neither node class.

```text
node.accept(visitor) → node chooses heading/paragraph method
                     → visitor supplies that operation's behavior
```

This two-step call is often called double dispatch: the element selects a visitor method, and the concrete visitor supplies that operation. JavaScript/TypeScript never selects overload implementations from runtime argument types, so explicitly named methods make the node choice visible. Tagged-union matching and other techniques are alternatives; Visitor is not the only way to get type-dependent behavior.

## 2. Assign traversal to one owner

This example traverses an array before visiting each element. For a tree, a traversal driver or a visitor can choose DFS/BFS and whether to descend. State which owns recursion to avoid visiting children twice or not at all. Graphs need a cycle/identity policy; a global visited set prevents repeat visits but can also suppress a shared node that should be counted once per path.

A visitor can return values, accumulate results, mutate nodes, or produce a transformed structure. Reuse a stateful visitor only when its reset and concurrency behavior are explicit. Untrusted node data still needs validation; the sample's heading level must be a supported positive integer before calling `repeat` in a production boundary.

## 3. Choose the axis that changes

| Approach | What stays stable | What is easy to add |
| -------------------------------- | ------------------------------------- | ---------------------------- |
| Methods on node classes | Operations | Node types |
| Classic Visitor | Node types and their visitor contract | Operations |
| Tagged union + exhaustive switch | Closed union of node types | Separate operation functions |

A union reduces ceremony but retains the same tradeoff: adding a union member requires updating exhaustive operations. Neither form makes both axes independently extensible without costs. Visitor can be adapted around third-party objects through wrappers or an external dispatch layer; it need not be inserted into objects you cannot edit.

## 4. Walk a language pipeline with visitors

A parser reads input and builds an AST (abstract syntax tree), whose nodes represent the input's structure — expressions, statements, and the like. An interpreter evaluates its meaning. Visitors may then implement type checking, formatting, optimization, or evaluation over that AST. Interpreter is not the parser; the same structure can support multiple operations.

ESLint's node-type callbacks are visitor-like operations driven by its AST traversal, not proof that every AST class exposes the exact GoF `accept` method. Explain the dispatch mechanism used by the actual framework.

## Summary

Keep a stable structure's operations separate when operations change more often than element types. Trace both dispatch choices, assign traversal to one owner and account for the cost of adding a new node type.

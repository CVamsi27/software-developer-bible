# Interpreter Pattern


## Definition

Interpreter represents a language's expressions and evaluates them according to defined meaning. In the classic Gang of Four (GoF) form, expression objects model grammar constructs—the allowed parts of the language—and implement their evaluation. Parsing input into those expressions is a separate task.

## First Principles

A configurable rule needs more structure than arbitrary strings passed to `eval`. Define a small set of allowed operations, represent an expression using those operations, then evaluate it against an explicit environment. That makes meaning inspectable and testable, but it also makes you responsible for grammar, type rules, errors and resource limits.

## Evaluate one expression tree

```typescript
type Expression =
  | { kind: 'number'; value: number }
  | { kind: 'variable'; name: string }
  | { kind: 'add'; left: Expression; right: Expression }
  | { kind: 'multiply'; left: Expression; right: Expression };

function evaluate(expression: Expression, variables: ReadonlyMap<string, number>): number {
  switch (expression.kind) {
    case 'number': return expression.value;
    case 'variable': {
      const value = variables.get(expression.name);
      if (value === undefined) throw new Error(`Unknown variable: ${expression.name}`);
      return value;
    }
    case 'add': return evaluate(expression.left, variables) + evaluate(expression.right, variables);
    case 'multiply': return evaluate(expression.left, variables) * evaluate(expression.right, variables);
  }
}

const expression: Expression = {
  kind: 'multiply',
  left: {
    kind: 'add',
    left: { kind: 'variable', name: 'x' },
    right: { kind: 'number', value: 5 }
  },
  right: { kind: 'number', value: 2 }
};
console.log(evaluate(expression, new Map([['x', 3]]))); // 16
```

Read the tree from the root: multiplication needs both operands → the left operand needs `x + 5` → resolve `x` to 3 → produce 8 → multiply by 2 → produce 16. The tree was constructed directly here; no string parser is implied.

```text
multiply
├── add
│   ├── variable: x
│   └── number: 5
└── number: 2
```

A class-per-expression implementation can put the corresponding evaluation in each class. This union makes the same evaluation rules visible in one function. Adding an operator changes the representation and evaluator; supporting its text syntax also changes the grammar/parser and precedence rules.

## Parsing and evaluation do different jobs

A parser answers which structure the input denotes. An evaluator answers what that structure means in an environment. For `1 + 2 * 3`, precedence must make multiplication a child of addition to obtain 7. Parentheses can request a different tree.

A parser generator helps produce a parser from a grammar. It does not replace evaluation, guarantee helpful diagnostics or remove the need for semantic validation. A well-written recursive-descent parser can also have explicit grammar and location-aware errors. Choose by ambiguity, language evolution and tooling needs rather than an arbitrary number of rules.

SQL databases often plan and execute queries; regex engines may compile automata; template engines may compile output functions. These are language-processing examples, not evidence that every implementation uses a class-per-rule tree-walking interpreter. Kubernetes admission configuration is not uniformly Rego; select the actual policy engine when discussing its mechanism.

## Bound what untrusted expressions can do

Validate an incoming AST (abstract syntax tree), which represents the expression as connected nodes. Check its shape, supported operators, variable names and finite numeric values. Apply size, depth and evaluation-work limits; the recursive illustration can overflow on a deeply nested tree. Define overflow and non-finite result behavior instead of silently accepting it.

Provide only approved variable bindings and callable capabilities. Do not expose arbitrary object traversal or host functions merely because parsing succeeded. Do not interpolate a rule into SQL or JavaScript source; parameterized boundaries and a deliberately restricted evaluator solve different problems. "Sanitize" alone is not a complete security mechanism.

Cache parsed expressions only under a key that includes language/version and relevant configuration. Tree walking, compilation and bytecode each have costs; parse once versus parse per request can matter more than the representation. Measure the actual workload rather than assuming all interpreters are slow.

## Related parts of the same system

| Part | Responsibility |
| ----------- | ------------------------------------------------ |
| Grammar | Allowed sentence structure and precedence |
| Parser | Input text → expression representation |
| Interpreter | Representation + environment → meaning/result |
| Visitor | Separate operations over the representation |
| Composite | Recursive expression structure, where applicable |

## Summary

Define the allowed language, separate parsing from meaning and trace one expression from its root to its result. A small evaluator can be clear; an exposed language also needs validation, diagnostics, capability limits and bounded work.

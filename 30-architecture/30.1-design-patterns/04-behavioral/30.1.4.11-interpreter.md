# Interpreter Pattern

A pricing rule says `(x + 5) × 2`. Running user-supplied text with JavaScript `eval` gives it the host language's capabilities, not just arithmetic. Interpreter lets the application define the permitted expressions and how each one is evaluated:

```typescript
evaluate(tree, new Map([['x', 3]])); // 16 — only arithmetic, no eval()
```

## Definition

**Interpreter** models a small language's **grammar** as **expression forms** and defines how each form **evaluates**. A class hierarchy, tagged union, or another representation can encode those forms. If input arrives as text, parsing is a separate step.

> **Textbook Definition:** "Given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language." — GoF intent, quoted in [*Java Design Patterns*](https://www.oreilly.com/library/view/java-design-patterns/9781484218020/9781484218013_Ch24.xhtml)

## First Principles

An expression node records syntax; `evaluate` gives that node meaning in an environment. A parser may turn text into nodes, but it never defines their meaning. With a closed set of node types, adding an operator changes both the representation and the evaluator.

## 1. Evaluate one expression tree

```typescript
type Expression =
  | { kind: 'number'; value: number }
  | { kind: 'variable'; name: string }
  | { kind: 'add'; left: Expression; right: Expression }
  | { kind: 'multiply'; left: Expression; right: Expression };

function evaluate(expression: Expression, variables: ReadonlyMap<string, number>): number {
  switch (expression.kind) {
    case 'number': return expression.value;
    case 'variable': {
      const value = variables.get(expression.name);
      if (value === undefined) throw new Error(`Unknown variable: ${expression.name}`);
      return value;
    }
    case 'add': return evaluate(expression.left, variables) + evaluate(expression.right, variables);
    case 'multiply': return evaluate(expression.left, variables) * evaluate(expression.right, variables);
  }
}

const expression: Expression = {
  kind: 'multiply',
  left: {
    kind: 'add',
    left: { kind: 'variable', name: 'x' },
    right: { kind: 'number', value: 5 }
  },
  right: { kind: 'number', value: 2 }
};
console.log(evaluate(expression, new Map([['x', 3]]))); // 16
```

Read the tree from the root: multiplication needs both operands → the left operand needs `x + 5` → resolve `x` to 3 → produce 8 → multiply by 2 → produce 16. The tree was constructed directly here; no string parser is implied.

```text
multiply
├── add
│   ├── variable: x
│   └── number: 5
└── number: 2
```

A class-per-expression implementation can put the corresponding evaluation in each class. This union makes the same evaluation rules visible in one function. Adding an operator changes the representation and evaluator; supporting its text syntax also changes the grammar/parser and precedence rules.

## 2. Separate parsing from meaning

For text such as `1 + 2 * 3`, a parser applies precedence and builds a tree with multiplication below addition; the evaluator then computes 7 from that tree. Parentheses can request a different structure. The example above constructs its tree directly so the evaluation stays visible without parser code.

A parser generator helps produce a parser from a grammar. It never replaces evaluation, guarantees useful diagnostics, or removes the need for semantic validation. A well-written recursive-descent parser can also make grammar and source locations explicit. Choose by ambiguity, language evolution, and tooling needs — never by an arbitrary rule count.

SQL query planners, regular-expression engines, and template engines process languages, but may plan or compile input rather than interpret a class-per-rule tree. Name the mechanism used by the specific system when describing it.

## 3. Bound what untrusted expressions can do

Validate an incoming AST (abstract syntax tree), which represents the expression as connected nodes. Check its shape, supported operators, variable names, and finite numeric values. Apply size, depth, and evaluation-work limits; the recursive illustration can overflow on a deeply nested tree. Define overflow and non-finite result behavior instead of silently accepting it.

Provide only approved variable bindings and callable capabilities. Never expose arbitrary object traversal or host functions merely because parsing succeeded. Never interpolate a rule into SQL or JavaScript source; parameterized boundaries and a deliberately restricted evaluator solve different problems. "Sanitize" alone is no complete security mechanism.

Cache parsed expressions only under a key including language/version and relevant configuration. Tree walking, compilation, and bytecode each have costs; parse-once versus parse-per-request can matter more than the representation. Measure the actual workload rather than assuming all interpreters are slow.

## 4. Place the parts of a language system

| Part | Responsibility |
| ----------- | ------------------------------------------------ |
| Grammar | Allowed sentence structure and precedence |
| Parser | Input text → expression representation |
| Interpreter | Representation + environment → meaning/result |
| Visitor | Separate operations over the representation |
| Composite | Recursive expression structure, where applicable |

## Summary

Define the allowed language, separate parsing from meaning and trace one expression from its root to its result. A small evaluator can be clear; an exposed language also needs validation, diagnostics, capability limits and bounded work.

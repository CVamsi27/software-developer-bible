# Null Object Pattern

> **TL;DR:** Null Object provides a **do-nothing object** in place of `null`. Callers call real methods on it — no `if (!x)` guards, no `TypeError: cannot read property` crashes. It is a *behavioral default*, not just a missing-value marker. Use it when absence has a sensible neutral behavior (anonymous user, no-op logger, empty iterator).

## Definition

The Null Object pattern is a behavioral pattern in which a special object implements the same interface as a real object but performs no action (or a neutral action). Instead of returning `null`, a function returns a Null Object. Client code treats every object uniformly — there is nothing special to check.

```text
        ┌────────────────────────────┐
        │      <<interface>>         │
        │          Logger            │
        │ + info(msg): void          │
        │ + error(msg): void         │
        └───────────┬────────────────┘
                    │ implements
        ┌───────────┴───────────┐
        │                       │
┌─────────────────────────────────────────┐
│ ConsoleLogger  │    │  NullLogger       │
│ (real)         │    │  (null object)    │
│ + info() {…}   │    │ + info() {}       │
│ + error() {…}  │    │ + error() {}      │
└─────────────────────────────────────────┘

Client: logger.info("hi")   // never checks for null
```

Key properties:

1. **Same interface** as the real object (that is the whole trick).
2. **No-op or neutral behavior** — log nowhere, iterate nothing, discount 0%.
3. **Stateless and usually a singleton** — there is nothing to configure.
4. Returned **instead of `null`**, so callers cannot crash on it.

## Why Do We Need It?

### Without Null Object

```typescript
// BAD: null checks scattered through every caller
const user = userRepository.findById(id);

if (user !== null) {
  if (user.getDiscount() !== null) {
    const d = user.getDiscount();
    if (d.apply(cart) !== null) {
      // ...
    }
  }
}
```

**Problems:**

1. **Guard-clause avalanche** — every consumer repeats the same `!== null` ritual.
2. **Runtime crashes** — miss one check, ship a `Cannot read properties of null` to production.
3. **Type-system lies** — TypeScript's `strictNullChecks` forces `T | null` everywhere, infecting every signature downstream.
4. **Behavior leaks out** — what "nothing found" means (log? ignore? default?) gets decided differently in every caller.

### With Null Object

```typescript
// GOOD: absence is just another object
const user = userRepository.findById(id); // returns AnonymousUser, never null

const price = user.getDiscount().apply(cart.total);
logger.info(`checkout for ${user.name}`, { userId: user.id });
```

No branches. `AnonymousUser.getDiscount()` returns a zero-discount object; its `id` might be `"guest"`; its `name` might be `"Guest"`. The meaning of "nobody logged in" lives in ONE place.

## How It Works

1. Define the **common interface** both real and null versions implement.
2. Implement the **real object** normally.
3. Implement the **null object** with neutral behavior: empty method bodies, identity values (`0`, `""`, `[]`), or self-returning fluent methods.
4. Change producers (repositories, factories, lookups) to **return the null object instead of `null`**.
5. Clients consume uniformly. If callers still need to know whether it was real, expose `isNull()` / `isGuest()` explicitly rather than making them type-check.

### Core TypeScript implementation

```typescript
interface Discount {
  apply(amountInCents: number): number;
}

class NoDiscount implements Discount {
  apply(amountInCents: number): number {
    return amountInCents; // neutral element of "apply a discount"
  }
}

class PercentageDiscount implements Discount {
  constructor(private readonly percentOff: number) {}
  apply(amountInCents: number): number {
    return Math.round(amountInCents * (1 - this.percentOff / 100));
  }
}

interface User {
  id: string;
  name: string;
  getDiscount(): Discount;
}

class RegisteredUser implements User {
  constructor(
    public readonly id: string,
    public readonly name: string,
    private readonly discount: Discount,
  ) {}
  getDiscount(): Discount {
    return this.discount;
  }
}

class GuestUser implements User {
  readonly id = 'guest';
  readonly name = 'Guest';
  private static instance: GuestUser | null = null;

  static getInstance(): GuestUser {
    if (!GuestUser.instance) GuestUser.instance = new GuestUser();
    return GuestUser.instance;
  }

  getDiscount(): Discount {
    return new NoDiscount(); // composes: another null object!
  }
}

class UserRepository {
  findById(id: string): User {
    const row = db.users.find(id);
    return row ? new RegisteredUser(row.id, row.name, toDiscount(row)) : GuestUser.getInstance();
  }
}
```

Notice the composition: `GuestUser.getDiscount()` returns `NoDiscount` — null objects frequently hand back other null objects. That is how chains stay branch-free.

### Fluent / chainable null object

For APIs where callers chain calls, make every method return the null object itself:

```typescript
interface NotificationSender {
  to(channel: string): NotificationSender;
  withTemplate(t: string, data?: Record<string, unknown>): NotificationSender;
  send(): Promise<void>;
}

class NullSender implements NotificationSender {
  to(): NotificationSender { return this; }
  withTemplate(): NotificationSender { return this; }
  async send(): Promise<void> { /* deliberate no-op */ }
}
```

Callers can always chain `.to('email').withTemplate('welcome').send()` safely even when notifications are disabled (e.g., in tests).

## Relationship to `Optional`

Null Object and `Optional`/`Maybe` solve overlapping problems differently:

| Null Object       | `Optional<T>` / `null` union              |                                                        |
| --                | -------------                             | ------------------------------                         |
| What it encodes   | **What to do** when absent                | **That** something may be absent                       |
| Where logic lives | Inside the null object                    | At the call site (`map`, `?? `, `match`)               |
| Caller awareness  | None — uniform interface                  | Forced — type system demands unwrapping                |
| Failure mode risk | Can silently mask bugs (see pitfalls)     | Compiler prevents forgotten cases                      |
| Best for          | Neutral defaults consumed polymorphically | Values where absence is meaningful and must be handled |

They compose well: a function may return `Optional<Discount>` internally, resolve it to either the real discount or `NoDiscount` at the boundary, and expose only `Discount` to the domain. Rule of thumb: **`Optional` at edges where absence must be decided; Null Object inside, where neutrality is the decision.**

## Real-World Examples

### 1. Logging

Every DI container ships a null/no-op logger. Services in tests or performance-critical paths get it instead of `console` stubs.

### 2. Anonymous / guest users

Auth systems return a guest principal with empty permissions instead of `null` — permission checks become uniform calls.

```typescript
interface Principal {
  id: string;
  roles: string[];
  has(role: string): boolean;
}

class GuestPrincipal implements Principal {
  readonly id = 'anonymous';
  readonly roles: string[] = [];
  has(): boolean { return false; } // neutral: deny everything
}

class AuthenticatedPrincipal implements Principal {
  constructor(public readonly id: string, public readonly roles: string[]) {}
  has(role: string): boolean { return this.roles.includes(role); }
}
```

### 3. Metrics / tracing clients

OpenTelemetry's no-op tracer and meter: instrument code always calls `tracer.startSpan(...)`, but in environments without a backend wired up, it returns spans you can safely ignore.

### 4. Strategy defaults

Payment flows with optional gift wrapping, tax calculators for tax-free regions, shipping strategies for digital goods — all naturally modeled as null-object strategies.

### 5. Test doubles

A stub that accepts every call and does nothing IS a null object. Hand-rolled stubs and null objects share DNA; mocking libraries generate them.

### 6. Event listeners

DOM's `addEventListener` pattern: a handler registry that falls back to a no-op handler avoids `undefined is not a function` when nothing subscribed.

## When to Use

**Use Null Object when:**

- Absence has a **predictable, neutral behavior** (zero discount, deny-all permissions, discard logs).
- Many callers would otherwise repeat the **same null check and same default**.
- You want **polymorphism** to replace conditionals (a stated GoF goal).
- Building **frameworks/libraries** where forcing null-handling on users is hostile ergonomics.

**Avoid Null Object when:**

- Absence is **exceptional and must surface** — silently continuing hides failures.
- There is **no sensible neutral behavior** (what is a null `PaymentRefunder`?).
- Callers genuinely need to **branch on existence** for business reasons (show "login" button only for guests). Then give the null object an inspectable flag, or use `Optional`.
- The team would stop asking **WHY** the value was missing — see next section.

## When It Hides Real Bugs (interview-critical)

This is the standard senior-level critique, and interviewers expect you to raise it unprompted:

```typescript
// Dangerous: is "no discount" correct here, or did loading fail?
const discount = discounts.for(couponCode); // returns NoDiscount on ANY miss
checkout.total(discount.apply(cart));
```

If `discounts.for()` returns `NoDiscount` because of a **database outage**, a **typo'd coupon key**, or a **serialization bug**, customers silently pay full price and nobody notices. The null object converted a loud crash into quiet wrong behavior.

Mitigations:

1. **Distinguish "known absent" from "failed to load"** — throw on infrastructure errors, return null object only for legitimate misses.
2. **Instrument the null path** — emit a metric/log inside null-object methods during bring-up (`metrics.increment('guest_discount_used')`).
3. **Make absence inspectable when it matters** — `user.isGuest()` lets UI branch intentionally while keeping the happy path clean.
4. **Never null-object across trust boundaries for money, auth, or compliance decisions** without explicit product sign-off.

Interview framing: "Null Object trades visibility for convenience. I reach for it where neutrality is provably safe, and I keep an escape hatch (`isGuest()`/`isNull()`) for the call sites where absence actually changes behavior."

## Comparisons

### Null Object vs `Optional`

Covered above: Optional forces handling of *presence*; Null Object bakes in the *response* to absence. Optional is safer by default; Null Object is cleaner for stable neutral defaults.

### Null Object vs sentinel values

```typescript
// Sentinel: shared magic value
const NOT_FOUND = Symbol('not-found');
function find(id: string): User | typeof NOT_FOUND { … }

// Still requires a check — just moved the special value
if (result === NOT_FOUND) { … }
```

Sentinels are just `null` with extra steps: callers still branch, and the type system still needs a union. A null object removes the branch entirely because it *behaves* correctly.

### Null Object vs Strategy

A Null Object **is** a degenerate Strategy: the strategy selected when the answer is "do nothing." Same interface, pluggable behavior — the difference is purely semantic (default vs alternative).

### Null Object vs default parameter values

```typescript
function notify(sender: NotificationSender = new NullSender()) {}
```

Defaults handle *callers who omit* the dependency; Null Objects handle *producers whose lookup legitimately finds nothing*. Different layers of the same hygiene.

## Common Pitfalls

### 1. Masking systemic failures

Covered above — returning a null object on infrastructure errors turns outages into silent data problems. Fail loudly on errors; null-object only on legitimate misses.

### 2. One null object, many meanings

A single `EmptyUser` serving guest checkout, deleted accounts, and banned users conflates three distinct business situations. Model separate null objects per meaning.

### 3. Stateful null objects

If a no-op object accumulates state (`sentCount++`), it stops being neutral and becomes a bug factory. Keep null objects immutable singletons.

### 4. Equality surprises

`guestUser === registeredUser` is obviously false, but teams forget `Map`/`Set` semantics: two structurally equal null objects may not dedupe. Prefer singleton instances over repeated construction.

### 5. Null-object-ing the whole API "just in case"

Adding 40 no-op methods nobody calls bloats interfaces. Null objects should mirror only the interface clients actually exercise; if the interface is huge, split it (Interface Segregation).

### 6. Forgetting serialization boundaries

`JSON.stringify(guestUser)` may serialize differently than real users, breaking snapshot tests or API contracts. Give null objects explicit, stable serialized shapes.

## Best Practices

1. Return null objects from **repositories and factories**, not from deep business logic — one production point, many consumption points.
2. Keep null objects **stateless, immutable, and shared** (singleton or module-level constant).
3. Compose them: null objects returning null objects keeps chains branch-free.
4. Provide an **inspectability hatch** (`isNull()`/`isGuest()`) for the minority of callers that must branch — document that it is intentional.
5. Pair with **strict TypeScript**: `User | null` in public APIs, resolved to `User` (real or null object) inside the domain.
6. In tests, assert against the null object explicitly (`expect(repo.findById('ghost')).toBe(GuestUser.getInstance())`) so refactors that accidentally reintroduce `null` fail loudly.
7. Log or metric the null path temporarily when introducing the pattern into a live system — prove neutrality before removing the old guards.

## Summary

Null Object replaces `null` with a benign object sharing the real interface. Conditionals collapse into polymorphism; the definition of "do nothing here" lives in exactly one class. Its power and its danger are the same property: callers stop noticing absence. Use it where neutrality is a genuine business rule (guests, disabled integrations, test doubles), and keep absence visible wherever silence would hide a bug.

**Interview-ready one-liner:** "Null Object encapsulates 'do nothing' behind the real interface so callers never null-check — a guest user denying all permissions, a no-op logger. The senior-level caveat is that it can mask real bugs, so I reserve it for provably-neutral defaults and keep absence inspectable where it matters."

## Cheat Sheet

| Aspect            | Detail                                                                                              |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| **Category**      | Behavioral (GoF, described in Pattern Languages of Program Design)                                  |
| **Intent**        | Replace `null` with a no-op object implementing the same interface                                  |
| **Motivation**    | Eliminate scattered null checks; centralize "absence behavior"                                      |
| **Key signal**    | "Everyone who gets this value immediately checks for null and does the same nothing"                |
| **vs `Optional`** | Optional forces handling of absence; Null Object decides the response for everyone                  |
| **Biggest risk**  | Silently masking load failures or unexpected misses                                                 |

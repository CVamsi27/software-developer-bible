# Null Object Pattern

An order service may be configured to run without logging. Passing `null` makes each call site branch; a no-op `Logger` keeps the normal call path, provided silence is an approved outcome.

## Definition

Null Object is a later object-design technique, not one of the original 23 GoF patterns. It represents an intentionally absent capability with an object that implements the normal contract and supplies agreed neutral behavior. It removes repeated absence checks only when callers really want the same response to absence.

> **Textbook Definition:** “Rather than using a null reference when an object is absent, create an object that implements the expected interface but whose methods have no behavior.” — [*The Design Patterns Companion*](https://www.oreilly.com/library/view/the-design-patterns/9781628256581/chapter28.xhtml)

## First Principles

Resolve intentional absence once at the composition boundary. A no-op is a valid dependency when configuration disables logging; if logger initialization fails, preserve that failure instead of silently selecting the no-op.

## Trace an intentionally disabled logger

```typescript
interface Logger { info(message: string): void }
const noLogging: Logger = Object.freeze({ info: (_message: string) => {} });
const consoleLogging: Logger = { info: message => console.log(message) };

function processOrder(orderId: string, logger: Logger): string {
  logger.info(`Processing ${orderId}`);
  return orderId;
}

processOrder('order-1', noLogging);       // deliberately silent
processOrder('order-2', consoleLogging); // Processing order-2
```

Both calls use the same operation. In the first, the boundary has chosen to discard logs; the method returns normally. In the second, the concrete logger writes the message. No lookup failure or authorization decision is hidden by this sample.

```text
configuration → real logger OR no-op logger → same logging contract
```

A default parameter can select `noLogging` for an omitted argument; `??` can resolve a nullish dependency into it. Neither operator is itself the object pattern: the important part is the implementation and the decision that its behavior is correct.

## Neutral depends on the operation

Zero is neutral for adding a discount amount, one for a multiplier and an empty collection for traversal. Choose by semantics rather than returning `0`, `''` or `[]` from every method. A missing required identifier has no useful neutral string. A permission implementation may deliberately deny everything, but must preserve the distinction between a guest, a banned account and a failed authentication lookup when that distinction matters.

A no-op notification sender is valid only if the caller's contract allows notification to be disabled. Returning successful delivery from a disabled sender is misleading. An optional refund provider must not claim that money was refunded when it performed no operation.

## Keep absence visible when callers need it

| Situation | Better contract |
| --------------------------------------- | ------------------------------------------------ |
| Deliberately disabled optional logging | Logger with agreed no-op behavior |
| Lookup may find no account | `Account \| null` or a result type |
| Lookup failed | An explicit failure result or exception |
| Distinct guest and registered workflows | A tagged principal or explicit guest property |
| Required integration missing | Initialization failure, not a silent placeholder |

`strictNullChecks` makes absence explicit in types; it cannot make an incomplete substitute safe. A Null Object must satisfy its complete interface. If callers need only part of that contract, split the interface instead of supplying an incomplete implementation.

## Lifetime and observation

A stateless immutable instance is often easy to share, but singleton identity is not a requirement. Two separately created neutral implementations can behave identically while remaining distinct Map/Set keys. Pick identity rules intentionally.

Counters or diagnostics do not automatically invalidate neutrality: they may leave the caller's result unchanged. Their costs and isolation still matter. Do not let one shared object accumulate customer-specific state. Instrument initialization or fallback selection when unexpected absence needs attention, and keep serialization a separate boundary with an explicit data shape.

An empty listener collection simply has no subscribers; it is not a Null Object. A no-op test stub can be one, while a mock that asserts calls serves a different purpose.

## Summary

Resolve intentional absence into a compatible neutral implementation when callers agree on that meaning. Preserve failures and meaningful absence as explicit outcomes. Trace what "doing nothing" promises before removing the checks that made absence visible.

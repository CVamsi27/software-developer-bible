# Repository Pattern

Marking an order paid looks like one assignment. The service must also distinguish a missing order, an invalid status, and a concurrent update. A repository gives that decision a domain-facing contract while the adapter handles storage:

```typescript
await markPaid(orderId, orders); // not-found, invalid status, conflict — all explicit
```

## Definition

**Repository** exposes a **domain-facing interface** for retrieving and persisting objects while keeping **storage details** behind that boundary. It is an enterprise application pattern, not one of the GoF structural patterns. In DDD, a repository commonly works with aggregate roots rather than exposing every table as a separate collection.

> **Textbook Definition:** "Mediates between the domain and data mapping layers using a collection-like interface for accessing domain objects." — [Martin Fowler's *Patterns of Enterprise Application Architecture* catalog](https://martinfowler.com/eaaCatalog/repository.html)

## First Principles

Keep the domain decision in the service or aggregate and row mapping, query execution, and conditional writes in the persistence adapter. The repository contract connects them. It never removes database semantics: transactions, uniqueness, concurrency, and missing records still affect the service's behavior.

## How It Works

### 1. Trace one domain write through the contract

```typescript
type Order = Readonly<{ id: string; status: 'pending' | 'paid'; version: number }>;
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order, expectedVersion: number): Promise<Order>;
}

async function markPaid(id: string, orders: OrderRepository): Promise<Order> {
  const order = await orders.findById(id);
  if (order === null) throw new Error('Order not found');
  if (order.status !== 'pending') throw new Error('Order is not pending');
  return orders.save({ ...order, status: 'paid' }, order.version);
}
```

This domain example records an already-authorized payment outcome; it charges no payment provider. The service loads the order, checks the transition, and asks the repository to save against the observed version. The implementation must atomically update only when that version still matches, increment the version, and report conflicts. A TypeScript interface cannot enforce those database guarantees by itself.

```text
service: find → validate domain change → save(expected version)
              repository: query/map  → conditional persistence
```

The service must distinguish not-found, storage failure, and version conflict. This interface uses `null` for a legitimate miss; an adapter can reject with a typed error or return a result for storage failure and conflict. Collapsing these outcomes into an empty entity makes business decisions unreliable.

### 2. Define the contract before the adapter

Use focused methods such as `findPendingByCustomer` when their domain meaning is useful. Never wrap every ORM method merely to hide its name. Equally, never claim all direct ORM access is wrong: a simple read endpoint can legitimately query through a dedicated query service.

An ORM maps rows and offers persistence APIs. A repository adds a chosen application/domain boundary. Moving from relational tables to a document store still requires evaluating joins, isolation, constraints, and query behavior; swapping an injected object never makes those differences disappear. Specifications can describe reusable predicates, but an in-memory `isSatisfiedBy` function is not automatically translatable to SQL. Keep the supported query language explicit and avoid filtering an unbounded database table after loading it into memory.

### 3. Share one transaction across related repositories

A Unit of Work coordinates changes that must commit together. Every repository operation must use the same active transaction handle. A `transactionActive` boolean with `commit`/`rollback` methods merely clearing a Map undoes no writes and must never be presented as a transaction implementation.

A practical composition root constructs repositories from the transaction-scoped database client. Perform database operations through those instances, commit on success, roll back on failure. External effects require a separate recovery mechanism; local rollback cannot retract a delivered message.

### 4. Bound queries, cache deliberately, test against the real store

Return bounded pages with deterministic ordering. If records can change during traversal, define whether pages use a snapshot or may contain duplicates or omissions. Plan joins and batches around actual access patterns; one repository call per row can still cause N+1 queries, and lazy loading may move queries rather than reduce them.

Caching belongs wherever its ownership and invalidation rules are clear. Include tenant and caller visibility in cache keys when necessary. A cached object must never let callers mutate data shared with later requests. Invalidate or update only after the authoritative write commits, and define acceptable stale reads.

An in-memory test repository verifies service behavior but can hide uniqueness, isolation, collation, and concurrency differences. Exercise the persistence adapter against the actual database for every guarantee the service relies on. Clone mutable stored values or expose immutable values deliberately.

## Summary

A repository gives business code a meaningful persistence contract. Trace misses, failures and version conflicts as well as successful saves. Preserve real transaction and database semantics, and add the boundary only where it earns its maintenance cost.

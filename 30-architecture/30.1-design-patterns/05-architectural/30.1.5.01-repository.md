# Repository Pattern

An order service needs to save a valid change while persistence owns row mapping and concurrent writes. A domain-facing contract makes that division visible without erasing database behavior.

## Definition

Repository exposes a domain-facing interface for retrieving and persisting objects while keeping storage details behind that boundary. It is an enterprise application pattern, not one of the GoF structural patterns. In DDD, a repository commonly works with aggregate roots rather than exposing every table as a separate collection.

> **Textbook Definition:** Repository is an application architecture pattern that mediates between a domain model and persistence through a domain-oriented collection interface, hiding storage and query implementation details.

## First Principles

A service needs to find an unpaid order and save a valid change. It should not need to know the table joins and driver calls used to reconstruct that order. Put those persistence decisions behind a contract expressed in domain terms. The contract does not remove database semantics: transactions, uniqueness, concurrency and missing records still affect the service's behavior.

## Follow an order lookup

```typescript
type Order = Readonly<{ id: string; status: 'pending' | 'paid'; version: number }>;
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order, expectedVersion: number): Promise<Order>;
}

async function markPaid(id: string, orders: OrderRepository): Promise<Order> {
  const order = await orders.findById(id);
  if (order === null) throw new Error('Order not found');
  if (order.status !== 'pending') throw new Error('Order is not pending');
  return orders.save({ ...order, status: 'paid' }, order.version);
}
```

This domain example records an already-authorized payment outcome; it does not charge a payment provider. The service loads the order, checks the transition and asks the repository to save against the observed version. The implementation must atomically update only when that version still matches, increment the version and report conflicts. A TypeScript interface cannot enforce those database guarantees by itself.

```text
service: find → validate domain change → save(expected version)
              repository: query/map  → conditional persistence
```

The caller gets `null` for a legitimate miss, an exception or result for infrastructure failure, and a conflict outcome for a concurrent change. Collapsing all three into an empty entity makes business decisions unreliable.

## Define the contract before the adapter

Use focused methods such as `findPendingByCustomer` when their domain meaning is useful. Do not wrap every ORM method merely to hide its name. Equally, avoid claiming all direct ORM access is wrong: a simple read endpoint can legitimately query through a dedicated query service.

An ORM maps rows and offers persistence APIs. A repository adds a chosen application/domain boundary. Moving from relational tables to a document store still requires evaluating joins, isolation, constraints and query behavior; swapping an injected object does not make those differences disappear.

Specifications can describe reusable predicates, but an in-memory `isSatisfiedBy` function is not automatically translatable to SQL. Keep the supported query language explicit and avoid filtering an unbounded database table after loading it into memory.

## Share one transaction across related repositories

A Unit of Work coordinates changes that must commit together. Every repository operation must use the same active transaction handle. A `transactionActive` boolean with `commit`/`rollback` methods that merely clear a Map does not undo writes and must not be presented as a transaction implementation.

A practical composition root can construct repositories from the transaction-scoped database client. Perform database operations through those instances, commit on success and rollback on failure. External effects require a separate recovery mechanism; local rollback cannot retract a delivered message.

## Queries, caching and test doubles

Return bounded pages and define ordering so repeated traversal is predictable. Plan joins and batches around actual access patterns; calling a repository method once per row can still cause N+1 queries. Lazy loading may move queries to surprising points rather than reduce them.

Caching belongs wherever its ownership and invalidation rules are clear. Include tenant and caller visibility in cache keys when necessary. A cached object must not let callers mutate data shared with later requests. Invalidate or update only after the authoritative write commits, and define acceptable stale reads.

An in-memory test repository verifies service behavior but can hide uniqueness, isolation, collation and concurrency differences. Exercise the persistence adapter against the actual database for guarantees the service relies on. Clone mutable stored values or expose immutable values deliberately.

## Summary

A repository gives business code a meaningful persistence contract. Trace misses, failures and version conflicts as well as successful saves. Preserve real transaction and database semantics, and add the boundary only where it earns its maintenance cost.

# CQRS & Dependency Injection

>
> **Why it matters:** This is an Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

CQRS separates the model or code used to change state from the model or code used to read it. Dependency Injection supplies a component's dependencies from outside rather than having that component construct them. They can be combined, but solve independent problems.

> **Textbook Definition:** Command Query Responsibility Segregation (CQRS) separates state-changing operations from read operations through distinct models or interfaces. Dependency Injection constructs collaborations by supplying dependencies externally rather than locating or creating them inside consumers.

## First Principles

A write must enforce business rules; a read may need a tailored view for a screen. When one representation becomes awkward for both, give them separate contracts. They may still share one database and transaction system.

A handler that constructs its own database client also chooses configuration, lifetime and implementation. Supplying that dependency at a composition boundary separates those decisions from the handler's work. This is useful in both CQRS and ordinary CRUD applications; neither pattern requires the other.

## Follow one write, then one read

```typescript
type Product = Readonly<{ id: string; name: string }>;
interface ProductWrites {
  rename(id: string, name: string): Promise<Product>;
}
interface ProductReads {
  details(id: string): Promise<Product | null>;
}

class RenameProduct {
  constructor(private readonly products: ProductWrites) {}
  execute(id: string, input: string): Promise<Product> {
    const name = input.trim();
    if (name.length === 0) throw new Error('Name is required');
    return this.products.rename(id, name);
  }
}
class ProductDetails {
  constructor(private readonly products: ProductReads) {}
  execute(id: string): Promise<Product | null> {
    return this.products.details(id);
  }
}
```

At the composition root, an application provides adapters implementing these contracts. The rename handler validates the proposed name and delegates the authoritative change. The details handler asks for a view. A command may return a result, identifier or version; the classical CQS rule about void-returning commands is not a mandatory CQRS API rule.

```text
write request → command handler → authoritative write model
read request  → query handler   → query model
                  ↑                   ↑
             dependencies supplied at composition boundary
```

These models can use the same store synchronously. Separating handlers alone is a modest organizational step; it does not automatically create independently scalable read infrastructure.

## A separate projection adds a synchronization contract

If reads use another store, propagate accepted writes through a durable outbox or equivalent atomic change record. The projector needs idempotent handling, ordering/version rules, replay/checkpoints and monitoring. Writing an entity, updating a read Map and appending an event in three separate steps is not a reliable synchronization mechanism.

Define what a client sees immediately after a write: return the accepted representation, read from the authoritative store, wait for a projection version or allow documented lag. Eventual consistency follows from asynchronous projection, not from every use of CQRS. CQRS does not require Event Sourcing or a message broker.

Read models need not always be denormalized, and write models need not always use normalized relational tables. Choose shapes based on invariants and access patterns. A single model can be entirely adequate for simple CRUD.

## Injection determines ownership and lifetime

Constructor parameters, function arguments and configured providers can all inject dependencies. A container is optional. Interfaces disappear at runtime, so containers need a concrete token, class or registration key; they cannot resolve an arbitrary TypeScript interface by reflection.

Choose whether a dependency lives for one operation, request, tenant or runtime. A singleton must not capture request-specific data. Resolve circular ownership by clarifying responsibilities rather than disguising it with arbitrary lazy lookups. Dispose resources through the owner that created their scope.

TypeScript parameter decorators and emitted design metadata belong to a particular legacy decorator toolchain; they are not universal behavior of modern language decorators. Use framework-specific documentation instead of a miniature reflection container in this chapter. See the linked NestJS chapter for runnable framework wiring.

## Choose the smallest useful split

| Need | Starting point |
| --------------------------------------------- | -------------------------------------------------- |
| Replace an external dependency in tests | Explicit injection; no CQRS required |
| Different read/write responsibilities | Separate handlers/contracts sharing one store |
| Expensive query shape | Tailored read query or projection |
| Independently provisioned read infrastructure | Separate read store with measured lag and recovery |
| Authoritative event history | Evaluate Event Sourcing separately |

## Summary

CQRS separates read and write responsibilities; DI separates use from construction. Trace the write-to-read path before adding infrastructure, and make synchronization and dependency lifetime explicit. One store with clear contracts is often enough.

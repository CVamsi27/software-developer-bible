# CQRS & Dependency Injection

Renaming a product must preserve its business rules; displaying its details may need a view shaped for a screen. Those are two separate decisions: whether reads and writes need different models, and who supplies each handler's storage dependency:

```typescript
await new RenameProduct(writeAdapter).execute(id, 'New name'); // write path
await new ProductDetails(readAdapter).execute(id);              // read path
```

## Definition

**CQRS** separates the model or code used to **change state** from the model or code used to **read it**. **Dependency Injection** supplies a component's dependencies **from outside** rather than having that component construct them. They can be combined, but solve independent problems.

> **Textbook Definition:** CQRS separates the model used to update information from the model used to read it. Dependency Injection assembles a component by supplying an implementation of its declared dependency from outside the component. [CQRS](https://martinfowler.com/bliki/CQRS.html) · [Dependency Injection](https://martinfowler.com/articles/injection.html)

## First Principles

A command asks the system to change state, so the authoritative write path must enforce its invariants. A query returns information without changing state and may shape it for a particular reader. When one representation becomes awkward for both jobs, separate their contracts; they can still share one database and transaction.

A handler creating its own database client also chooses configuration, lifetime, and implementation. Dependency Injection (DI) moves that choice to application startup, where concrete dependencies are assembled and passed to consumers. DI is useful in ordinary CRUD applications too; neither pattern requires the other.

## How It Works

### 1. Route one write and one read through separate contracts

```typescript
type RenameReceipt = Readonly<{ id: string; version: number }>;
type ProductDetailsView = Readonly<{ id: string; name: string; priceInCents: number }>;
interface ProductCommands {
  rename(id: string, name: string): Promise<RenameReceipt>;
}
interface ProductQueries {
  details(id: string): Promise<ProductDetailsView | null>;
}

class RenameProduct {
  constructor(private readonly products: ProductCommands) {}
  execute(id: string, input: string): Promise<RenameReceipt> {
    const name = input.trim();
    if (name.length === 0) throw new Error('Name is required');
    return this.products.rename(id, name);
  }
}
class ProductDetails {
  constructor(private readonly products: ProductQueries) {}
  execute(id: string): Promise<ProductDetailsView | null> {
    return this.products.details(id);
  }
}
```

At startup, the application passes a write adapter to `RenameProduct` and a read adapter to `ProductDetails`; this wiring boundary is the composition root. The command checks basic input, while the authoritative write model enforces domain invariants and returns a versioned receipt. The query returns a screen-shaped projection. A command may return a result, identifier, or version: the classical Command Query Separation rule that commands return `void` is no mandatory CQRS API rule.

```text
application startup
  ├─ supplies → command handler → write adapter → authoritative model
  └─ supplies → query handler   → read adapter  → query model
```

The adapters can share one store synchronously. Splitting handlers alone separates responsibilities; it creates no independently scalable read infrastructure.

### 2. Pay for a separate projection with a synchronization contract

If reads use another store, commit the business change and an outbox record in the same database transaction. A publisher can then retry delivery after a crash without losing the accepted change. The projector must handle duplicate messages idempotently, apply per-entity ordering or version rules, atomically persist projection changes with replay checkpoints, and expose lag and failure metrics. Writing to the entity store, read store, and event stream as three independent steps can leave them inconsistent.

Define what a client sees immediately after a write: return the accepted representation, read from the authoritative store, wait for a projection version, or allow documented lag. Eventual consistency follows from asynchronous projection, not from every use of CQRS. CQRS requires neither Event Sourcing nor a message broker. Read models need not always be denormalized, and write models need not always use normalized relational tables — choose shapes by invariants and access patterns. A single model can be entirely adequate for simple CRUD.

### 3. Let injection determine ownership and lifetime

Constructor parameters, function arguments, and configured providers can all inject dependencies. A container is optional; it should clarify assembly, never hide dependencies that could be wired directly.

Choose whether a dependency lives for one operation, request, tenant, or process. A singleton must never capture request-specific data. If two services require each other, clarify ownership before introducing a lookup hiding the cycle. Dispose scoped resources through the owner creating the scope.

TypeScript decorator-based injection depends on the framework's decorator model. Legacy `experimentalDecorators` can emit design-type metadata with `emitDecoratorMetadata`. Standard decorators cannot use that legacy output or decorate parameters; TypeScript 5.2 provides a separate `context.metadata` API exposed through `Symbol.metadata`. A TypeScript interface is erased at runtime, so container registration needs a runtime class or explicit token. See the NestJS chapter for framework wiring; this chapter keeps the example container-free. [TypeScript 5.0 decorator changes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#decorators) · [TypeScript 5.2 decorator metadata](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-2.html#decorator-metadata)

### 4. Choose the smallest useful split

| Need | Starting point |
| --------------------------------------------- | -------------------------------------------------- |
| Replace an external dependency in tests | Explicit injection; no CQRS required |
| Different read/write responsibilities | Separate handlers/contracts sharing one store |
| Expensive query shape | Tailored read query or projection |
| Independently provisioned read infrastructure | Separate read store with measured lag and recovery |
| Authoritative event history | Evaluate Event Sourcing separately |

## Summary

CQRS separates read and write responsibilities; DI separates use from construction. Trace the write-to-read path before adding infrastructure, and make synchronization and dependency lifetime explicit. One store with clear contracts is often enough.

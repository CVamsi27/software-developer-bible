# Event Sourcing Pattern

An account shows a balance of 70, but a customer disputes the withdrawal that produced it. A current-state row cannot explain the accepted changes behind that number. Event Sourcing keeps those changes as the authoritative history and derives the balance from them:

```typescript
accountEvents.reduce(apply, null); // { id: 'a1', balance: 70 } — history, not a row
```

## Definition

**Event Sourcing** stores **accepted domain events** as the **authoritative history** for an entity or aggregate stream. Applying that stream in order reconstructs its current state. Snapshots accelerate replay and projections serve queries; neither replaces the event log. An audit log beside authoritative current-state rows is a different design.

> **Textbook Definition:** "Capture all changes to an application state as a sequence of events." — [Martin Fowler, *Event Sourcing*](https://martinfowler.com/eaaDev/EventSourcing.html)

## First Principles

Overwriting a balance with 70 preserves the result but loses how the account reached it. Saving each accepted event lets the application rebuild current or historical state. An audit trail can answer some of the same questions without becoming authoritative; Event Sourcing chooses the event stream as the source of truth and accepts the cost of ordered appends, replay, and schema evolution.

## 1. Fold accepted events into state

`Opened`, `Deposited`, and `Withdrawn` are facts the system accepted, not raw requests. The `apply` function is a reducer: it takes the previous account state and one event, then returns the next state. Folding replays that reducer over the stream in order:

```typescript
type AccountEvent =
  | { type: 'Opened'; accountId: string }
  | { type: 'Deposited'; amount: number }
  | { type: 'Withdrawn'; amount: number };
type Account = { id: string; balance: number };

function apply(state: Account | null, event: AccountEvent): Account {
  if (event.type === 'Opened') {
    if (state !== null) throw new Error('Already opened');
    return { id: event.accountId, balance: 0 };
  }
  if (state === null) throw new Error('Account not opened');
  if (!Number.isSafeInteger(event.amount) || event.amount <= 0) {
    throw new Error('Invalid amount');
  }
  const balance = state.balance + (event.type === 'Deposited' ? event.amount : -event.amount);
  if (!Number.isSafeInteger(balance) || balance < 0) throw new Error('Invalid balance');
  return { ...state, balance };
}

const accountEvents: AccountEvent[] = [
  { type: 'Opened', accountId: 'a1' },
  { type: 'Deposited', amount: 100 },
  { type: 'Withdrawn', amount: 30 }
];
console.log(accountEvents.reduce<Account | null>(apply, null)); // { id: 'a1', balance: 70 }
```

The event store durably appends events per stream; each record's envelope carries stream identity and sequence/version. Validate the envelope and payload schema before applying events. The sample folds trusted `AccountEvent` payloads from one account stream; the TypeScript union disappears at runtime. It uses integer minor units in one assumed currency: opening creates balance 0, deposit produces 100, withdrawal produces 70. Given the same valid history and reducer, replay produces the same state. The reducer must never send emails or charge accounts during replay.

```text
accepted events: opened → deposited(100) → withdrawn(30)
folded state:       0   →      100       →      70
```

## 2. Accept commands with concurrency control

A command handler loads or reconstructs an aggregate at stream version N, checks the proposed operation, and appends its resulting events only if the stream still has version N. The expected-version check and append must be atomic. A conflict means another command won: reload and reevaluate the intent rather than blindly appending an obsolete decision. The store orders events within a stream; independent streams have no automatic global order.

Append-only never means coordination-free: concurrent appends to one stream still need conflict detection. Give each command a stable idempotency key and define whether a duplicate returns its prior outcome or conflicts. Message delivery guarantees never prevent duplicate business effects.

The log records accepted domain facts, not every submitted command. Rejected attempts, authentication activity, and other audit requirements may need separate records. Events in an aggregate stream are not automatically a public integration contract: publish explicit, versioned integration events, and make consumers safe to retry. Event Sourcing alone establishes no audit completeness, tamper resistance, or compliance.

## 3. Give snapshots and projections separate jobs

A snapshot stores state at a particular stream version. Load it, then fold later events instead of rebuilding a long aggregate from the beginning. Treat the snapshot as a rebuildable performance aid, verify its schema and version, and retain the history the domain requires.

A projection creates a query-friendly view. Handle duplicates and preserve the ordering its calculation requires. Persist projection updates and their checkpoints atomically when they share a store; otherwise make replaying a batch safe. An asynchronous projection can lag an accepted command. For critical reads, use authoritative stream state or wait for a defined projection version. Synchronous projections can provide a stronger visibility contract; eventual consistency is not inherent in every event-sourced read. Choose snapshot intervals and projection design from measured replay cost, event sizes, and latency needs — no universal 100-event threshold exists.

## 4. Evolve events without rewriting history

Treat appended events as immutable. Record a correction as a new corrective or compensating event rather than silently rewriting history. Version event meaning, not only field names: upcasters can adapt old representations but cannot invent missing facts. When business rules change, decide whether replay uses versioned logic or new logic. Distinguish event time, stream acceptance order, and effective business time in temporal queries.

Keep secrets out of events. Decide whether sensitive data belongs inline, in a separately governed reference, or in an encrypted representation with a lifecycle. Immutable facts and deletion/retention obligations need an explicit design; moving data behind a URL never automatically solves them. Event Sourcing needs a durable event store, not necessarily a message broker — a broker can distribute events, but its retention or compaction may remove history, so evaluate atomic per-stream append, recovery, backup, and the required reconstruction horizon separately.

## 5. Compare the storage choice

| Approach | Authoritative record |
| ----------------------- | ---------------------------------------------------------- |
| CRUD with audit history | Current records, with additional history for defined needs |
| Event Sourcing | Accepted domain events; state is derived |
| Memento | Selected recoverable snapshots |
| CDC | Changes observed from another authoritative database |
| CQRS | Separate read/write models; storage choice is independent |

## Summary

Make accepted events authoritative only when reconstruction and domain history justify the added contract. Trace one fold, then account for atomic versioned appends, replay-safe effects, projection lag, schema evolution and retention.

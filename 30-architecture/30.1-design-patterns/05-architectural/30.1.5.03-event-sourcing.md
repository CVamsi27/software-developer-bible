# Event Sourcing Pattern

> **TL;DR:** Event Sourcing stores **all changes as a sequence of events** rather than the current state. The current state is derived by replaying events. Use it when you need a complete audit trail, temporal queries, or the ability to derive multiple views from the same event stream.

<!-- section: Design Patterns | category: Architecture | subcategory: Architectural | tags: concept, advanced, ddd -->

## Definition

Event Sourcing is an architectural pattern where state changes are stored as a sequence of immutable events, rather than just the current state. The application's current state is derived by replaying (or folding) those events.

```text
Traditional: Event Sourcing:
┌─────────────────────┐ ┌─────────────────────┐
│ Account │ │ Account                 │
│ ───────────── │ │ ─────────────     │
│ balance: $100 │ │ events: [         │
│ (just the result) │ │ {Opened, $0}, │
│ │ │ {Deposited, $50},               │
└─────────────────────────────────────┘ │ {Deposited, $50},   │
                                          │ {Withdrew, $20}     │
                                          │ ]                   │
                                          │                     │
                                          │ currentBalance() =  │
                                          │ events.reduce()     │
                                          └─────────────────────┘
```

## Why Do We Need It?

### Traditional state storage

```typescript
// User table — only the current state
const user = { id: 1, name: 'Alice', email: 'alice@x.com', plan: 'pro', planChangedAt: '2024-01-15' };
```

**Lost information:**
- When did the user sign up?
- What was the previous email?
- What plans did they have before pro?
- How many times have they changed plans?
- Why did they downgrade?

### Event Sourcing

```typescript
// Events — full history
const events = [
  { type: 'UserSignedUp', at: '2023-06-01', email: 'alice@x.com' },
  { type: 'EmailChanged', at: '2023-08-12', from: 'alice@x.com', to: 'alice@gmail.com' },
  { type: 'PlanUpgraded', at: '2023-09-01', from: 'free', to: 'basic' },
  { type: 'PlanUpgraded', at: '2024-01-15', from: 'basic', to: 'pro' },
];
```

**You can answer:**
- When did the user sign up? → first event.
- What was the previous email? → second event.
- How many plan changes? → count of `PlanUpgraded` events.
- Why the downgrade (if event has reason)? → field in event.

Plus you can:
- Rebuild the state at any point in time.
- Derive multiple read models (e.g., total revenue per plan tier).
- Audit compliance is built-in.

## How It Works

```typescript
// Event types
type Event =
  | { type: 'AccountOpened'; accountId: string; owner: string; initialBalance: number; at: Date }
  | { type: 'Deposited'; accountId: string; amount: number; at: Date }
  | { type: 'Withdrew'; accountId: string; amount: number; at: Date }
  | { type: 'AccountClosed'; accountId: string; at: Date };

// State (current account) — derived from events
type Account = { id: string; owner: string; balance: number; isOpen: boolean };

// Reducer: apply one event to state
function apply(state: Account, event: Event): Account {
  switch (event.type) {
    case 'AccountOpened':
      return { id: event.accountId, owner: event.owner, balance: event.initialBalance, isOpen: true };
    case 'Deposited':
      return { ...state, balance: state.balance + event.amount };
    case 'Withdrew':
      return { ...state, balance: state.balance - event.amount };
    case 'AccountClosed':
      return { ...state, isOpen: false };
  }
}

// Fold all events to get current state
function buildAccount(events: Event[]): Account {
  return events.reduce(apply, { id: '', owner: '', balance: 0, isOpen: false });
}
```

## Real-World Examples

### 1. Banking / financial systems

Every transaction is an event. Account balance is derived. Audit trail is mandatory by regulation (SOX, GDPR).

### 2. Version control (Git)

A git repository stores commits (events). The working tree is derived by applying the commits to an empty tree. `git checkout <commit>` reconstructs the state at that commit.

### 3. E-commerce order systems

Order lifecycle as events:

```
OrderPlaced → OrderPaid → OrderShipped → OrderDelivered
   ↓
OrderCancelled (if user cancels)
```

The order state at any time is the fold of these events.

### 4. Audit log systems

Compliance (HIPAA, SOC 2, financial regulations) requires immutable logs of "who did what when". Event Sourcing gives you this for free.

### 5. Collaboration tools (Google Docs, Figma)

The document state is the result of applying all the operations (events) to the initial state. CRDTs and OT (Operational Transformation) work on similar principles.

### 6. Stripe

Stripe's API and dashboard show you the full event history of a payment (`charge.created`, `charge.succeeded`, `charge.refunded`). You can replay the events to reconstruct what happened.

### 7. Kafka as an event store

Kafka is a natural fit for Event Sourcing. Topics store events; consumers build projections by consuming from the topic.

## When to Use

 **Use Event Sourcing when:**

- You need a **complete audit trail** (finance, healthcare, legal, compliance)
- You need **temporal queries** ("what was the state at time T?")
- You want to **debug by replaying** events
- You want to **derive multiple read models** from the same event stream (e.g., total balance per customer + transaction history)
- The domain is **collaborative** (multiple actors mutate state — version control is event sourcing)
- You want to **decouple write and read models** for performance

 **Avoid Event Sourcing when:**

- State is ephemeral and audit isn't needed (chat messages, ephemeral sessions)
- The complexity cost is too high (you can't maintain snapshots, projections, and event store)
- Your domain is simple CRUD (over-engineering)
- The events are not natural to the domain (forcing events for a calculator is silly)
- You need **strong consistency** for all reads (eventual consistency via projections is hard)
- You can't pay the storage cost (events accumulate forever — unless you snapshot)

## How It Works in Code

### With snapshots (essential for performance)

For long-lived aggregates, replaying all events from the start is slow. Use **snapshots** — periodically save the current state, then replay only events after the snapshot.

```typescript
class Account {
  constructor(
    public id: string,
    public balance: number,
    public isOpen: boolean,
    public version: number, // event count applied
  ) {}

  static fromHistory(events: Event[], snapshot?: AccountSnapshot): Account {
    let state: Account = snapshot
      ? new Account(snapshot.id, snapshot.balance, snapshot.isOpen, snapshot.version)
      : new Account('', 0, false, 0);
    const start = snapshot ? snapshot.version : 0;
    for (let i = start; i < events.length; i++) {
      state = apply(state, events[i]);
    }
    return state;
  }
}

// Snapshot every 100 events
function maybeSnapshot(account: Account, events: Event[]): AccountSnapshot | null {
  if (events.length % 100 === 0) {
    return { id: account.id, balance: account.balance, isOpen: account.isOpen, version: events.length };
  }
  return null;
}
```

### With projections (read models)

A projection is a derived view optimized for reads. Multiple projections can be built from the same event stream.

```typescript
// Projection 1: account summary
class AccountSummaryProjection {
  summaries = new Map<string, { id: string; balance: number; transactionCount: number }>();

  apply(event: Event) {
    if (event.type === 'AccountOpened') {
      this.summaries.set(event.accountId, { id: event.accountId, balance: event.initialBalance, transactionCount: 0 });
    } else if (event.type === 'Deposited' || event.type === 'Withdrew') {
      const s = this.summaries.get(event.accountId);
      if (s) {
        s.balance = event.type === 'Deposited' ? s.balance + event.amount : s.balance - event.amount;
        s.transactionCount++;
      }
    }
  }
}

// Projection 2: daily total deposits
class DailyTotalProjection {
  totals = new Map<string, number>(); // date -> total

  apply(event: Event) {
    if (event.type === 'Deposited') {
      const date = event.at.toISOString().split('T')[0];
      this.totals.set(date, (this.totals.get(date) || 0) + event.amount);
    }
  }
}

// Same event stream feeds both projections
const events = await eventStore.getEvents();
const summary = new AccountSummaryProjection();
const dailyTotal = new DailyTotalProjection();
for (const e of events) {
  summary.apply(e);
  dailyTotal.apply(e);
}
```

### Event Store implementation (simplified)

```typescript
class EventStore {
  private streams = new Map<string, Event[]>();

  // Append events atomically (with optimistic concurrency check)
  async append(streamId: string, events: Event[], expectedVersion: number): Promise<void> {
    const current = this.streams.get(streamId) || [];
    if (current.length !== expectedVersion) {
      throw new Error(`Concurrency conflict: expected version ${expectedVersion}, got ${current.length}`);
    }
    this.streams.set(streamId, [...current, ...events]);
  }

  async getEvents(streamId: string): Promise<Event[]> {
    return [...(this.streams.get(streamId) || [])];
  }
}
```

In production, use a real event store (EventStoreDB, Axon Server, Kafka with compacted topics, Postgres with append-only tables).

## Comparisons

### Event Sourcing vs CRUD

| CRUD | Event Sourcing |  |
| -- | ------ | ---------------- |
| **Stores** | Current state | History of changes |
| **Lost data** | All intermediate states | None (every change is recorded) |
| **Temporal queries** | Hard | Free (replay to time T) |
| **Audit** | Manual (add a log table) | Built-in (events are the source) |
| **Complexity** | Low | High |
| **Storage** | Small (current state only) | Large (all events) |

### Event Sourcing vs Memento

- **Memento** saves **the state** at points in time.
- **Event Sourcing** saves **the events** that produced the state.

| Memento | Event Sourcing |  |
| -- | --------- | ---------------- |
| **Storage size** | Large (full state per snapshot) | Smaller (just the changes) |
| **Restore to T** | Find a snapshot ≤ T | Replay events from the start |
| **Audit** | Implicit (snapshot at T) | Explicit (full history) |

### Event Sourcing vs CQRS

- **Event Sourcing** is about how state is stored (events).
- **CQRS** is about how state is accessed (separate read/write models).

They often appear together: write side emits events → events are stored → read side projects events into a query model.

### Event Sourcing vs CDC (Change Data Capture)

- **CDC** captures changes from a database (binlog) and publishes them as events. It's a way to get events from a system that doesn't natively use Event Sourcing.
- **Event Sourcing** makes events the primary storage.

## Code Example: Order Management

```typescript
type OrderEvent =
  | { type: 'OrderPlaced'; orderId: string; items: { sku: string; qty: number; price: number }[]; at: Date }
  | { type: 'OrderPaid'; orderId: string; amount: number; at: Date }
  | { type: 'OrderShipped'; orderId: string; tracking: string; at: Date }
  | { type: 'OrderCancelled'; orderId: string; reason: string; at: Date };

type Order = { id: string; status: 'pending' | 'paid' | 'shipped' | 'cancelled'; total: number; tracking?: string };

function applyOrder(state: Order, event: OrderEvent): Order {
  switch (event.type) {
    case 'OrderPlaced':
      return {
        id: event.orderId,
        status: 'pending',
        total: event.items.reduce((s, i) => s + i.qty * i.price, 0),
      };
    case 'OrderPaid': return { ...state, status: 'paid' };
    case 'OrderShipped': return { ...state, status: 'shipped', tracking: event.tracking };
    case 'OrderCancelled': return { ...state, status: 'cancelled' };
  }
}

// Build current state from history
function currentOrder(events: OrderEvent[]): Order {
  return events.reduce(applyOrder, { id: '', status: 'pending', total: 0 });
}

// Replay to a point in time
function orderAt(events: OrderEvent[], at: Date): Order {
  return events.filter(e => e.at <= at).reduce(applyOrder, { id: '', status: 'pending', total: 0 });
}

const events: OrderEvent[] = [
  { type: 'OrderPlaced', orderId: 'o1', items: [{ sku: 'X', qty: 2, price: 50 }], at: new Date('2024-01-15T10:00:00Z') },
  { type: 'OrderPaid', orderId: 'o1', amount: 100, at: new Date('2024-01-15T10:05:00Z') },
  { type: 'OrderShipped', orderId: 'o1', tracking: 'TRK123', at: new Date('2024-01-15T14:00:00Z') },
];

currentOrder(events);
// { id: 'o1', status: 'shipped', total: 100, tracking: 'TRK123' }

orderAt(events, new Date('2024-01-15T10:01:00Z'));
// { id: 'o1', status: 'pending', total: 100 } // before payment
```

## Common Pitfalls

### 1. **Forgetting snapshots**

Without snapshots, long-lived aggregates get slow. Replaying 10,000 events every time is wasteful.

**Fix:** snapshot every N events (100-1000 depending on size).

### 2. **Mutating events**

Events are immutable. If you "fix" an event by updating it, you've broken the audit trail. Add a new corrective event instead.

```typescript
// BAD
{ type: 'Deposited', amount: 100 } → { type: 'Deposited', amount: 200 }

// GOOD
{ type: 'Deposited', amount: 100 },
{ type: 'Correction', depositId: '...', correctedAmount: 200 }
```

### 3. **Storing everything in events**

PII, large blobs, secrets — these shouldn't be in events. Store references (URLs, IDs) instead, and fetch the actual data.

### 4. **Eventual consistency surprises**

Reads from projections are eventually consistent. If you write and immediately read, you might not see your own write. Document this; use synchronous projections for critical reads.

### 5. **Schema evolution**

Old events might have a different schema than new code expects. Use event versioning (e.g., `v1`, `v2` in the event type) and upcasters to migrate.

### 6. **Storage growth**

Events accumulate forever. Add a snapshot + archive strategy. Or use a real event store with retention policies.

## Best Practices

1. **Snapshot every 100-1000 events** to keep replay fast.
2. **Use multiple projections** — each read model is a separate view of the same event stream.
3. **Version your events** for schema evolution.
4. **Keep events small** — store references to large data, not the data itself.
5. **Use a real event store** in production (EventStoreDB, Kafka, Axon) — don't roll your own on Postgres without care.
6. **Document the eventual consistency** — make sure callers know that reads from projections lag writes.
7. **Pair with CQRS** for the cleanest separation of write/read models.

## Summary

Event Sourcing stores **events as the source of truth** and derives state by replay. It's the most powerful pattern for audit, temporal queries, and complex domains — but it's also the most complex. Reach for it when you genuinely need the audit trail or the ability to derive multiple read models from the same history. For simple CRUD, it's overkill.

**Interview-ready one-liner:** "Event Sourcing stores state as a sequence of immutable events instead of just the current state — the current state is derived by replaying events. Gives you free audit, temporal queries, and the ability to derive multiple read models."

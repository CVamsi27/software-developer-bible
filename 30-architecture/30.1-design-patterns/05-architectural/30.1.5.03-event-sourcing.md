# Event Sourcing Pattern


## Definition

Event Sourcing makes accepted domain events the authoritative record of state changes. Current state is derived by folding those events in order, often assisted by snapshots and read projections. An audit log beside an authoritative current-state table is a different storage choice.

> **Textbook Definition:** Event Sourcing is a persistence pattern in which an ordered sequence of accepted domain events is the authoritative history, and current state is reconstructed by applying those events.

## First Principles

If the domain needs to reconstruct how a state was reached, overwriting a value alone loses that explanation. Keeping accepted changes as facts preserves a history from which state can be rebuilt. Other designs can also preserve history through audit tables or temporal storage; Event Sourcing specifically makes the event history authoritative. That choice brings ordering, concurrency and long-term schema responsibilities.

## Fold one account's history

```typescript
type AccountEvent =
  | { type: 'Opened'; accountId: string }
  | { type: 'Deposited'; amount: number }
  | { type: 'Withdrawn'; amount: number };
type Account = { id: string; balance: number };

function apply(state: Account | null, event: AccountEvent): Account {
  if (event.type === 'Opened') {
    if (state !== null) throw new Error('Already opened');
    return { id: event.accountId, balance: 0 };
  }
  if (state === null) throw new Error('Account not opened');
  if (!Number.isSafeInteger(event.amount) || event.amount <= 0) {
    throw new Error('Invalid amount');
  }
  const balance = state.balance + (event.type === 'Deposited' ? event.amount : -event.amount);
  if (!Number.isSafeInteger(balance) || balance < 0) throw new Error('Invalid balance');
  return { ...state, balance };
}

const history: AccountEvent[] = [
  { type: 'Opened', accountId: 'a1' },
  { type: 'Deposited', amount: 100 },
  { type: 'Withdrawn', amount: 30 }
];
console.log(history.reduce<Account | null>(apply, null)); // { id: 'a1', balance: 70 }
```

The sample folds already decoded, trusted `AccountEvent` values in one account stream. External bytes also need schema/type/stream-identity validation; the TypeScript union disappears at runtime. It uses integer minor units in one assumed currency. Opening creates balance 0, deposit produces 100 and withdrawal produces 70. Folding the same valid ordered history gives the same result. The reducer must not send emails or charge accounts during replay.

```text
accepted events: opened → deposited(100) → withdrawn(30)
folded state:       0   →      100       →      70
```

## Accept commands with concurrency control

A command handler loads an aggregate through version N, checks the proposed operation and appends new events only if that stream still has version N. The append and expected-version check must be atomic. Another writer changing the stream causes a conflict; reload and reevaluate the command rather than blindly appending an obsolete decision.

Append-only does not mean lock-free: ordering and stream uniqueness still require coordination. Give retried commands durable identities and define whether repeated delivery returns a prior outcome or conflicts. Broker delivery guarantees do not remove duplicate business effects.

The log records accepted facts, not every submitted command. Rejected attempts, authentication activity and other audit requirements may need additional records. Event Sourcing does not automatically establish completeness, tamper resistance or compliance.

## Snapshots and projections have separate jobs

A snapshot stores state at a particular stream version. Load that snapshot and fold subsequent events to avoid rebuilding a long aggregate from the beginning. Verify schema/version compatibility and never claim the snapshot itself removes the need for historical retention decisions.

A projection creates a query-friendly view. Record progress, handle duplicates and preserve the ordering needed by its calculation. A read from an asynchronous projection can lag the command's accepted event. For critical reads, use the authoritative stream state or a defined projection-version barrier. Synchronous projections can have a stronger visibility contract; eventual consistency is not unavoidable for every read.

Choose snapshot intervals and projection design from measured replay cost, event sizes and latency needs. There is no universal 100-event threshold.

## Evolution and retention remain part of the design

Version event meaning, not only field names. Upcasters can adapt old representations; they cannot invent missing facts reliably. Preserve deterministic reconstruction across code upgrades and distinguish event time, acceptance order and effective business time in temporal queries.

Keep secrets out of events. Decide whether sensitive data belongs inline, in a separately governed reference or in an encrypted representation with a lifecycle. Immutable facts and deletion/retention obligations need an explicit design; moving data behind a URL does not automatically solve them.

A broker with retention or compaction is not automatically a permanent complete event store. Compaction can remove intermediate records, and retention can remove old history. Evaluate atomic per-stream append, recovery, backup and required reconstruction horizon. Git primarily stores snapshots of committed trees; a visible API event feed does not prove an application's internal authoritative storage architecture.

## Compare the storage choice

| Approach | Authoritative record |
| ----------------------- | ---------------------------------------------------------- |
| CRUD with audit history | Current records, with additional history for defined needs |
| Event Sourcing | Accepted domain events; state is derived |
| Memento | Selected recoverable snapshots |
| CDC | Changes observed from another authoritative database |
| CQRS | Separate read/write models; storage choice is independent |

## Summary

Make accepted events authoritative only when reconstruction and domain history justify the added contract. Trace one fold, then account for atomic versioned appends, replay-safe effects, projection lag, schema evolution and retention.

# DDD Tactical Patterns — Aggregates & Value Objects


## Definition

Tactical DDD patterns describe domain objects by identity, value and consistency boundaries. An entity persists as the same thing when its attributes change. A value object is defined by its attributes. An aggregate groups objects whose invariants must be maintained together, with its root controlling changes through a deliberate API. A domain event describes an accepted fact.

## First Principles

An order's line quantities and prices determine its total. If arbitrary callers can edit lines independently, the order cannot reliably enforce its own rules. Put those rules behind a boundary that owns the relevant state, then make persistence protect concurrent changes to that boundary. A class alone cannot prevent another database writer from bypassing it.

## Give a monetary value its own rules

```typescript
class Money {
  private constructor(readonly amountCents: number, readonly currency: 'USD' | 'EUR') {
    Object.freeze(this);
  }

  static of(amountCents: number, currency: 'USD' | 'EUR'): Money {
    if (!Number.isSafeInteger(amountCents) || amountCents < 0 ||
        (currency !== 'USD' && currency !== 'EUR')) throw new Error('Invalid money');
    return new Money(amountCents, currency);
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error('Currency mismatch');
    return Money.of(this.amountCents + other.amountCents, this.currency);
  }

  multiply(quantity: number): Money {
    if (!Number.isSafeInteger(quantity) || quantity <= 0) throw new Error('Invalid quantity');
    return Money.of(this.amountCents * quantity, this.currency);
  }

  equals(other: Money): boolean {
    return this.amountCents === other.amountCents && this.currency === other.currency;
  }
}

console.log(Money.of(250, 'USD').multiply(2).equals(Money.of(500, 'USD'))); // true
```

Construction checks integer minor units and supported currency; multiplication validates quantity and routes the result through the same validation. Addition rejects mixed currencies. These rules describe a deliberately small nonnegative USD/EUR model, not every currency or a financial ledger. Fractional rates and rounding need an explicit policy.

TypeScript `private` constrains typed access rather than creating a security boundary. This value uses runtime checks and freezes its flat fields. A nested value object would also need an intentional policy for mutable descendants.

## Place the order boundary around its invariant

```text
Order root
├── customerId          reference to another aggregate
├── status              legal lifecycle state
└── order lines         owned quantities and Money values

caller → root.addLine / root.place → validate → persist whole invariant
```

Trace adding a line: require a draft order → validate product identity and positive safe-integer quantity → find the existing line → enforce a compatible unit price/currency → merge safely or add a new bounded line. Check a line limit only when adding a new distinct line; an order already at its line limit may still increase a permitted existing quantity.

Return copied immutable line views rather than the internal mutable array. `ReadonlyArray` alone disappears at runtime and does not prevent a caller from mutating exposed objects. Validate hydrated database state as well as new commands, and use a version check or appropriate transaction locking so two valid in-memory decisions do not overwrite each other.

The root controls mutations of its owned objects. External read views can expose child information without granting a separate child persistence path. Repositories are commonly organized by aggregate root, while reporting/query models may use other shapes.

## Across boundaries, choose consistency deliberately

Small aggregates and identity references reduce coupling and contention. "One aggregate per transaction" is a useful design default, not a universal prohibition against atomically updating two roots. If a cross-object invariant must hold immediately, evaluate the aggregate boundary and storage transaction capabilities. Do not assume eventual inventory reservation is acceptable for every ordering domain.

Domain events can communicate accepted changes across boundaries. Persist state and outgoing event intent together, then relay with retries and duplicate handling. Snapshot pending events before persistence and acknowledge/drain them only after successful commit; draining the object before a failed commit can lose them from a retried operation. An outbox makes intent durable, not guaranteed delivered exactly once.

A reservation object cannot alone guarantee that no other reservation overlaps: the shared resource/schedule boundary or database constraint must coordinate competing bookings. Similarly, expiration rules need a defined clock, persisted expiry and atomic decision; a class name does not enforce time.

## Choose the object by what makes it the same

| Question | Likely model |
| -------------------------------------------------------------- | ------------ |
| Is equal value interchangeable regardless of identity? | Value object |
| Is it the same thing after its attributes change? | Entity |
| Which objects must change together to preserve this invariant? | Aggregate |
| What accepted business fact should other boundaries learn? | Domain event |

Entities can be implemented with immutable representations; identity does not require in-place mutation. Domain-event equality and identity are explicit choices too. Simple transaction scripts can be appropriate for simple rules; rich object models are useful when they clarify substantial domain behavior.

## Summary

Start with identity and the invariant that must commit together. Put intention-revealing changes behind the root, make value rules explicit and protect both runtime exposure and persistence concurrency. Communicate across boundaries with the consistency and recovery policy the domain actually requires.

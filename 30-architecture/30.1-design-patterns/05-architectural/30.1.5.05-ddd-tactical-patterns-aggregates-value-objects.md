# DDD Tactical Patterns — Aggregates & Value Objects

> **TL;DR:** DDD's tactical building blocks — **Entities** (identity over time), **Value Objects** (defined by attributes, immutable), and **Aggregates** (consistency boundaries with a single root) — turn a database-shaped model into a domain-shaped one. The aggregate rules (small aggregates, reference other aggregates by ID, one transaction per aggregate, domain events for cross-aggregate consistency) are what senior interviewers probe hardest.

<!-- section: Design Patterns | category: Architecture | subcategory: Architectural | tags: concept, ddd -->

## Definition

Tactical DDD patterns classify domain objects by *what defines their identity*:

| Pattern          | Defined by              | Mutable?                                   | Equality                                      | Examples                                 |
| ---------------- | ----------------------- | ------------------------------------------ | --------------------------------------------- | ---------------------------------------- |
| **Value Object** | Its attributes          | No (immutable)                             | Structural — equal attributes = equal objects | `Money`, `Address`, `DateRange`, `Email` |
| **Entity**       | A persistent identity   | Yes (attributes change, identity persists) | Identity — same ID = same thing               | `Customer`, `Order`, `Reservation`       |
| **Aggregate**    | A consistency boundary  | Root is the only public entry point        | Root's identity names the cluster             | `Order` + its `OrderLine`s               |
| **Domain Event** | Something that happened | No (immutable fact)                        | Occurrence ID                                 | `OrderPlaced`, `InventoryReserved`       |

An **aggregate** is a cluster of entities and value objects whose invariants must hold *atomically at commit time*. The **aggregate root** is the only member outside code may hold; everything else inside is reachable only through it.

```text
            ┌─────────────────────────────────────┐
            │ Aggregate root: Order               │
            │  id: OrderId                        │
            │  status: OrderStatus                │
            │                                     │
            │  ┌──────────────┐  ┌─────────────┐  │
            │  │ OrderLine    │  │ OrderLine   │  │   <- entities inside
            │  │ productId ---+--+-> by ID     |  |      the boundary                                   
            │  │ qty          │  └─────────────┘  │
            │  │ unitPrice: Money (VO)           │  │
            │  └──────────────┘                   │
            │  shippingAddress: Address (VO)      │   <- value objects
            │  total(): Money                     │
            │  + addLine() / removeLine()         │   <- ONLY mutation paths
            └─────────────────────────────────────┘
                      │  references BY ID
                      ▼
            ┌────────────────────┐
            │ Customer aggregate │  <- different boundary,                 
            │  id: CustomerId    │     loaded/committed separately                 
            └────────────────────┘
```

## Why Do We Need It?

### Without aggregates

1. **Invariants enforced nowhere.** Any service can do `order.status = 'SHIPPED'; order.lines.push(...)` — nothing stops an invalid order from being persisted.
2. **Transaction sprawl.** Code loads half an object graph, mutates pieces, and races another writer doing the same.
3. **Anemic models.** Business rules drift into controllers ("transaction scripts"), duplicated per endpoint.
4. **A mirror of the database, not the business.** Every table becomes a class; nobody can say where consistency begins or ends.

### With aggregates

1. **One place to enforce invariants** — mutate only via root methods that guard the rules.
2. **A crisp transaction rule** — one aggregate instance per transaction.
3. **Explicit consistency boundaries** — strongly consistent inside, eventually consistent outside.
4. **Domain events** as the escape hatch for reacting to changes without coupling aggregates.

## How It Works

### Decide Entity vs Value Object by equality semantics

Ask: "If every attribute changed but 'it' continued, would I still mean the same thing?" Money that changed amount is a *different* money (value). An order whose address changed is still *the same* order (entity).

### Keep aggregates small

The smaller the boundary, the fewer write conflicts. Vaughn Vernon's rules: reference other aggregates **by ID**, keep child collections bounded (tens, not thousands), and design each aggregate around a single transactional invariant.

### One transaction = one aggregate

Cross-aggregate updates happen through **domain events** handled asynchronously (or a saga when orchestration is required). This trades immediate cross-object consistency for scalability while keeping invariants locally absolute.

### Repository per aggregate root

Exactly one repository per root. Repositories load/save the WHOLE aggregate behind a collection-like interface (`findById`, `save`). Child entities get no repository of their own.

## Code Examples

### Value Object base + Money

```typescript
abstract class ValueObject {
  equals(other: ValueObject): boolean {
    if (other === null || other.constructor !== this.constructor) return false;
    const a = this.getEqualityFields();
    const b = other.getEqualityFields();
    return a.every((v, i) => v === b[i]);
  }
  protected abstract getEqualityFields(): unknown[];
}

export class Money extends ValueObject {
  private constructor(
    readonly amountCents: number,
    readonly currency: 'USD' | 'EUR',
  ) {
    super();
    Object.freeze(this);
  }

  static of(amountCents: number, currency: 'USD' | 'EUR'): Money {
    if (amountCents < 0) throw new Error('Money cannot be negative');
    return new Money(amountCents, currency);
  }

  add(other: Money): Money {
    this.assertSameCurrency(other);
    return new Money(this.amountCents + other.amountCents, this.currency);
  }

  multiply(qty: number): Money {
    return new Money(this.amountCents * qty, this.currency);
  }

  protected getEqualityFields(): unknown[] {
    return [this.amountCents, this.currency];
  }

  private assertSameCurrency(other: Money): void {
    if (this.currency !== other.currency) throw new Error('Currency mismatch');
  }
}
```

Note the factory + private constructor: invalid money cannot exist. That is the value-object contract — construct once, valid forever.

### Aggregate root: Order with invariant enforcement

```typescript
type OrderStatus = 'DRAFT' | 'PLACED' | 'PAID' | 'SHIPPED' | 'CANCELLED';

interface OrderLineState { // entity INSIDE the aggregate: no identity outside it
  readonly productId: string;
  quantity: number;
  unitPrice: Money;
}

export interface DomainEvent {
  readonly occurredAt: Date;
  readonly name: string;
  readonly payload: unknown;
}

export class Order {
  private status: OrderStatus = 'DRAFT';
  private lines: OrderLineState[] = [];
  private events: DomainEvent[] = [];
  static readonly MAX_LINES = 50;

  constructor(
    public readonly id: string,
    public readonly customerId: string, // BY ID: not a Customer object!
  ) {}

  addLine(productId: string, qty: number, unitPrice: Money): void {
    this.assertNotModifiable();
    if (qty <= 0) throw new Error('Quantity must be positive');
    if (this.lines.length >= Order.MAX_LINES) {
      throw new Error(`Order line limit (${Order.MAX_LINES}) exceeded`);
    }
    const existing = this.lines.find((l) => l.productId === productId);
    if (existing && !existing.unitPrice.equals(unitPrice)) {
      // Invariant: one product = one price within an order
      throw new Error('Same product added with different unit prices');
    }
    if (existing) {
      existing.quantity += qty;
    } else {
      this.lines.push({ productId, quantity: qty, unitPrice });
    }
  }

  removeLine(productId: string): void {
    this.assertNotModifiable();
    this.lines = this.lines.filter((l) => l.productId !== productId);
  }

  place(): void {
    this.assertNotPlaced();
    if (this.lines.length === 0) throw new Error('Cannot place empty order');
    this.status = 'PLACED';
    this.record('OrderPlaced', { orderId: this.id, total: this.total() });
  }

  cancel(): void {
    if (this.status === 'SHIPPED') throw new Error('Shipped orders cannot be cancelled');
    if (this.status === 'CANCELLED') return;
    this.status = 'CANCELLED';
    this.record('OrderCancelled', { orderId: this.id });
  }

  total(): Money {
    if (this.lines.length === 0) return Money.of(0, 'USD');
    const firstCurrency = this.lines[0].unitPrice.currency;
    return this.lines.reduce(
      (sum, l) => sum.add(l.unitPrice.multiply(l.quantity)),
      Money.of(0, firstCurrency),
    );
  }

  pullDomainEvents(): DomainEvent[] {
    const drained = this.events;
    this.events = [];
    return drained;
  }

  get currentStatus(): OrderStatus {
    return this.status;
  }

  getLines(): ReadonlyArray<Readonly<OrderLineState>> {
    return this.lines;
  }

  private assertNotModifiable(): void {
    if (this.status !== 'DRAFT') throw new Error(`Order is ${this.status}; lines are frozen`);
  }

  private assertNotPlaced(): void {
    if (this.status !== 'DRAFT') throw new Error(`Cannot place an order in ${this.status}`);
  }

  private record(name: string, payload: unknown): void {
    this.events.push({ occurredAt: new Date(), name, payload });
  }
}
```

Every mutation path guards invariants: no edits after placement, positive quantities, bounded lines, consistent pricing, non-empty orders. Invalid states are unrepresentable-in-practice because nothing can bypass these methods.

### Repository per aggregate

```typescript
export interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>; // persists whole aggregate atomically
}

// Postgres-backed implementation sketch
export class PgOrderRepository implements OrderRepository {
  async findById(id: string): Promise<Order | null> {
    const [row, lineRows] = await Promise.all([
      this.db.query('SELECT * FROM orders WHERE id = $1', [id]),
      this.db.query('SELECT * FROM order_lines WHERE order_id = $1', [id]),
    ]);
    if (!row.rows[0]) return null;
    return OrderMapper.toDomain(row.rows[0], lineRows.rows);
  }

  async save(order: Order): Promise<void> {
    await this.db.transaction(async (tx) => {
      await tx.upsertOrder(OrderMapper.toRow(order));
      await tx.replaceLines(order.id, order.getLines());
      const events = order.pullDomainEvents(); // events leave WITH the commit
      await tx.insertOutbox(events);           // atomic state + event write
    });
  }
}
```

The outbox insert inside the same transaction guarantees "state changed implies event published" — see Event Sourcing and Outbox chapters for deeper treatment.

### Consuming domain events cross-aggregate

```typescript
async function handleOrderPlaced(event: DomainEvent) {
  const { orderId, total } = event.payload as { orderId: string; total: Money };
  // Different aggregate, different transaction:
  const inventory = await inventoryRepository.findByProductIds(idsOf(orderId));
  await inventory.reserve(orderId, idsOf(orderId));
  await inventoryRepository.save(inventory); // emits InventoryReserved / InventoryShort
}
```

Inventory reservation is eventually consistent with the placed order — acceptable for most domains, and exactly the trade the aggregate rule asks you to make consciously.

## Real-World Use Cases

1. **E-commerce orders** — the canonical example above; totals, line limits, status transitions.
2. **Banking** — `Account` aggregate enforces "balance never negative"; `Money` VO prevents float drift and mixed-currency math.
3. **Hotel booking** — `Reservation` aggregate guards overlap invariants; `DateRange` VO centralizes start-before-end logic.
4. **Healthcare** — `PatientRecord` aggregate with audit-required transitions; VOs for dosage and allergies.
5. **Ticketing** — seat-hold aggregates enforce "hold expires in N minutes" deterministically at the boundary.

## Common Mistakes

### 1. Giant aggregates referencing everything

```typescript
// BAD: Order holds Customer, Store, Warehouse objects directly
class Order {
  customer!: Customer;      // drags another aggregate into every load/save
  warehouse!: Warehouse;    // write lock contention across boundaries
}
```

Fix: store IDs (`customerId`, `warehouseId`) and fetch other aggregates through their own repositories when needed.

### 2. Anemic model with setters

```typescript
// BAD: invariants live in whatever service remembers them
order.setStatus('SHIPPED'); // who checked payment? nobody, that's who
```

Fix: intention-revealing methods (`order.ship()`) that own the transition rules.

### 3. Repositories for child entities

`orderLineRepository` breaks the boundary — children must be mutated via the root so invariants run.

### 4. Skipping Value Objects

Using primitives everywhere (`price: number`, `currency: string`) scatters validation and lets `addTotals` mix currencies silently. Wrap them.

### 5. Strongly consistent cross-aggregate updates in one transaction

Locking `Order` + `Inventory` rows together serializes unrelated business flows. Use events + eventual consistency, escalate to a saga only when compensation semantics demand it.

### 6. Domain events emitted but never persisted atomically

Publishing after commit risks silent loss on crash; publishing before commit publishes ghosts. Persist to an outbox table in the same transaction.

## Best Practices

1. Default to Value Objects; promote to Entity only when identity truly matters.
2. Name mutation methods after business verbs (`place`, `cancel`, `ship`), not CRUD verbs.
3. Validate fully at construction; then trust the object — no re-validation shotgun.
4. Keep one aggregate per transaction; use optimistic concurrency (version column) on the root.
5. Bound child collection sizes explicitly and enforce the bound in the model.
6. Emit domain events from the aggregate, drain them in the repository, publish via outbox.
7. Map persistence rows <-> domain objects explicitly (a small mapper layer beats ORM leakage into the domain).
8. Write unit tests against the aggregate alone — if you cannot test invariants without a DB, the boundary is wrong.

## Summary

Tactical DDD gives you a decision procedure, not just diagrams: Value Objects for attribute-defined equality, Entities for identity threads, Aggregates as the smallest strongly-consistent clusters, roots as sole mutators, IDs as cross-boundary references, and domain events as the consistency bridge between aggregates. The payoff is invariants that are enforced where they live instead of remembered by services.

**Interview-ready one-liner:** "I draw the aggregate boundary around a single transactional invariant — Order plus its lines, enforcing totals and status transitions internally. Other aggregates are referenced by ID, updated via domain events eventually, and each root gets exactly one repository. Small boundaries keep write contention low and correctness local."

## Cheat Sheet

| Aspect               | Detail                                                         |
| -------------------- | -------------------------------------------------------------- |
| **Entity**           | Identity-based equality, mutable, lifecycle                    |
| **Value Object**     | Attribute-based equality, immutable, side-effect-free          |
| **Aggregate**        | Consistency boundary; root-only access; atomic invariants      |
| **Reference rule**   | Other aggregates by ID, never by object reference              |
| **Transaction rule** | One aggregate instance per transaction                         |
| **Consistency rule** | Strong inside the boundary; eventual outside via domain events |
| **Repository rule**  | One repository per root; loads/saves whole aggregate           |
| **Event rule**       | Events recorded in aggregate, persisted atomically (outbox)    |

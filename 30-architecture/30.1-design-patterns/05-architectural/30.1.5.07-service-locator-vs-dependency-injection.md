# Service Locator vs Dependency Injection

> **TL;DR:** Both patterns invert control of dependency creation. **Dependency Injection** hands dependencies in (constructor parameters) — dependencies are visible, compile-checked, and trivially faked. A **Service Locator** makes code ASK a global registry for dependencies — dependencies become hidden, runtime-resolved, and painful to test. Default to constructor injection; reserve locators for the rare plugin-registry seam.

<!-- section: Design Patterns | category: Architecture | subcategory: Architectural | tags: concept, di -->

## First Principles

Both patterns answer "how do objects find dependencies?" — with opposite coupling directions:

1. **Service locator: the object asks a registry.** Dependencies are hidden (not in the signature), the locator is a global — testability requires setting up the registry, and required-vs-optional is invisible. Fast to start, expensive to reason about.
2. **DI: the container pushes.** Dependencies are explicit constructor parameters — the graph is visible, missing wiring fails at startup (→ 20.2.1.04), tests substitute directly. More ceremony, honest structure.
3. **The principle underneath: make dependencies visible.** Whatever mechanism, the design win is the same — call sites reveal what they need; invisibility is the defect both patterns exist to avoid (locator just avoids it less well).

## Definition

| Service Locator (SL) | Dependency Injection (DI) |  |
| -- | ---------------------- | --------------------------- |
| Who resolves dependencies? | The object asks a registry (`locator.get('db')`) | The caller supplies them (constructor/args) |
| Where are deps declared? | Inside method bodies — invisible in the signature | In the constructor signature — self-documenting |
| Resolution time | Runtime, per call | Composition time (startup), then fixed |
| Failure mode | Runtime error on missing service | Startup wiring error, fails fast |
| Testing | Requires resetting/mocking global state | `new Sut(fakeDep)` — done |

**Service Locator:** a known object (the locator) holds every service; consumers query it by key.

```text
   ┌─────────────────────────────────────────────────────┐  get('orderRepo')   ┌─────────────────┐
   │  OrderSvc  │ ──────────────────▶ │ ServiceLocator   │
   │            │ ◀────────────────── │ (global registry)│
   └─────────────────────────────────────────────────────┘    concrete repo    └────────▲────────┘
                                               │ registers
                                     ┌─────────┴─────────┐
                                     │ bootstrap/main.ts │
                                     └───────────────────┘
```

**Dependency Injection:** the object declares what it needs; something else (composition root / IoC container) constructs and passes it.

```text
   ┌─────────────────────────────────────────────┐  container builds & injects
   │   main.ts     │ ────────────────────────────┐
   └─────────────────────────────────────────────┘                             ▼
                                     ┌────────────────────┐
                                     │ new OrderSvc(repo, │
                                     │      mailer, clock)│
                                     └────────────────────┘
                                        deps visible here
```

## Why Do We Need It?

The underlying need is the same for both: **Inversion of Control**. Classes should not hard-code their collaborators' construction (`new PostgresOrderRepo()` inside `OrderService` welds business logic to infrastructure). The disagreement is only about *who does the lookup*:

1. **Testability** — swap real implementations for fakes.
2. **Configuration** — choose implementations per environment without editing classes.
3. **Decoupling** — depend on interfaces, not concretes (Dependency Inversion Principle).
4. **Lifecycle management** — singletons, scoped instances (per-request), transient.

DI achieves all four while keeping dependencies honest. The Service Locator achieves them while hiding them — which is exactly the criticism developed below.

## How It Works

### Service Locator mechanics

```typescript
class ServiceLocator {
  private static services = new Map<string, unknown>();

  static register<T>(name: string, factory: () => T): void {
    this.services.set(name, factory);
  }

  static get<T>(name: string): T {
    const factory = this.services.get(name);
    if (!factory) throw new Error(`Service not registered: ${name}`);
    return (factory as () => T)();
  }
}

// Bootstrap
ServiceLocator.register('orderRepo', () => new PgOrderRepo(pool));
ServiceLocator.register('mailer', () => new SesMailer(client));

// Consumer
class OrderService {
  place(order: Order): void {
    // Hidden dependency #1: 'orderRepo' — invisible in any signature above
    const repo = ServiceLocator.get<OrderRepository>('orderRepo');
    repo.save(order);
    // Hidden dependency #2: stringly-typed key that only breaks at runtime
    ServiceLocator.get<Mailer>('mailr').sendWelcome(order); // typo → production
  }
}
```

### Constructor injection contrast

```typescript
class OrderService {
  constructor(
    private readonly orderRepo: OrderRepository,
    private readonly mailer: Mailer,
  ) {}

  place(order: Order): void {
    this.orderRepo.save(order);
    this.mailer.sendWelcome(order);
  }
}

// Test — no framework, no global state:
const sut = new OrderService(inMemoryRepo(), recordingMailer());
sut.place(order); // deterministic, parallel-safe
```

### IoC containers (the industrial version)

Frameworks like NestJS/Angular automate construction via reflection:

```typescript
@Injectable()
export class OrderService {
  constructor(
    private readonly orderRepo: OrderRepository, // token-based resolution
    private readonly mailer: Mailer,
  ) {}
}

// module wiring — resolution happens ONCE at startup
@Module({
  providers: [
    OrderService,
    { provide: OrderRepository, useClass: PgOrderRepo },
    { provide: Mailer, useFactory: () => new SesMailer(sesClient) },
  ],
})
export class OrdersModule {}
```

Important nuance: an IoC container used via constructor injection is NOT a service locator. The class never sees the container. The anti-pattern is *injecting the container itself* and calling `container.get()` inside methods — that is a locator wearing a DI costume.

## Code Examples

### Why hidden dependencies hurt tests

```typescript
// Locator style: every test must know the secret keys AND reset state
beforeEach(() => {
  ServiceLocator.reset();
  ServiceLocator.register('orderRepo', () => fakeRepo);
  ServiceLocator.register('mailer', () => fakeMailer);
});
afterEach(() => ServiceLocator.reset()); // leak into next test if forgotten

// Constructor style: the signature IS the documentation
const sut = new OrderService(fakeRepo, fakeMailer);
```

With the locator, reading `place()` reveals nothing; grepping bodies is the only way to enumerate dependencies. With constructor injection, `tsc` fails the moment you forget one — the compiler enforces the design.

### The acceptable exception: plugin registries

```typescript
interface Command { name: string; run(args: string[]): Promise<void>; }

class CommandRegistry { // locator-shaped BY DESIGN
  private commands = new Map<string, Command>();
  register(cmd: Command): void { this.commands.set(cmd.name, cmd); }
  resolve(name: string): Command | undefined { return this.commands.get(name); }
}
```

A CLI resolving user-typed command names, a CMS resolving widget types by slug, an editor resolving language plugins — these are legitimately locator-flavored because the *key arrives at runtime from data*, not from code. Note the differences from the anti-pattern: registration is explicit per plugin instance (no global singleton), consumers receive the registry via injection, and absence is handled (`undefined`, not throw-deep-inside).

## Comparisons

| Dimension | Service Locator | Constructor Injection |
| --------------------- | ----------------------------------- | ------------------------------------------------------------------- |
| Dependency visibility | Hidden — must read method bodies | Signature-level, grep-free |
| Compile-time safety | None (string keys) | Full (type-checked params) |
| Failure timing | Runtime, possibly rare code path | Startup composition |
| Test setup | Global reset rituals, serial tests | Plain construction, parallel-safe |
| Coupling direction | Consumers coupled to locator + keys | Consumers coupled only to abstractions |
| Refactoring safety | Rename service = runtime hunt | Rename type = compiler finds all |
| Framework lock-in | Usually none | Container-specific decorators (mitigatable with plain constructors) |
| Onboarding cost | "Where does X come from?" forever | Read the constructor |

Mark Seemann's canonical summary: the locator hides dependencies, and hiding dependencies is the problem DI exists to solve. Fowler's counterpoint: locator vs injection matters less than keeping NEWING of services out of business logic — but modern practice has clearly sided with injection.

### When a locator is acceptable

1. **Runtime-keyed registries** (plugins, commands, strategies selected by data).
2. **Legacy seams** — introducing DI to untestable legacy code often starts by wrapping globals behind a locator, then migrating call sites incrementally.
3. **Static entry points** where no composition root can reach (some serverless handlers, cron scripts) — as a temporary shim at the edge only.
4. **Cross-cutting optional services** (telemetry sinks) where absence must be tolerated everywhere — though null-object defaults usually serve better.

## Real-World Use Cases

1. **NestJS/Angular/Fastify-di** — constructor injection end-to-end; request-scoped providers handle per-request state.
2. **VS Code extension host** — contribution-point registries are runtime-keyed locators by necessity.
3. **Express middleware ecosystems** — historically locator-ish via `app.set/get`; modern apps wrap this into typed request contexts.
4. **Testing harnesses** — pure constructor injection with hand-built fakes; containers only in e2e composition roots.

## Common Mistakes

### 1. Locator in library code

Libraries calling a global locator force every embedding app to register exact keys. Libraries should accept dependencies as parameters — let the application decide.

### 2. Property/setter injection everywhere

```typescript
class OrderService {
  orderRepo!: OrderRepository; // set by container magic after construction
}
```

Same invisibility as a locator plus temporal coupling (use-before-set). Prefer constructor injection unless the framework genuinely cannot (cyclic graphs, base-class constraints).

### 3. Injecting the container itself

```typescript
constructor(private readonly container: Container) {}
// later: this.container.get('anything')
```

Hidden dependencies with extra steps, plus the class now depends on the container library. Inject the actual abstraction.

### 4. Stringly-typed keys without tokens

If you must run a locator, at least use branded symbols/tokens so typos are compile errors rather than production incidents.

### 5. Service location inside domain entities

Entities reaching for repositories/locators corrupts the model (see DDD aggregates). Dependencies flow inward to services; entities stay pure.

## Best Practices

1. Default to constructor injection; make dependencies impossible to miss.
2. Keep ONE composition root (main.ts / module graph) — no scattered `new` or mid-app registrations.
3. Type your locator keys as unique symbols if you ever build a legitimate registry.
4. Never pass the container below the composition layer.
5. In libraries, expose plain constructors; leave container adapters to the consuming app.
6. When inheriting locator-style legacy code, strangle it: introduce constructor injection top-down, delete registry entries as call sites migrate.

## Summary

Both approaches centralize construction; they differ in honesty. Constructor injection puts dependencies in signatures where compilers, reviewers, and testers can see them. Service locators bury lookups in method bodies where only runtime failures reveal them. Use DI everywhere except the narrow, deliberate case of runtime-keyed plugin registries — and even there, inject the registry rather than reaching for a global.

**Interview-ready one-liner:** "Service locator says `give me the thing named X` inside a method — hidden, stringly-typed, late-failing. Constructor injection says `I need these things` in the signature — visible, typed, startup-verified, and one-liner mockable. I default to constructor injection and allow locator semantics only for genuine runtime-keyed plugin registries."

## Cheat Sheet

| Aspect | Detail |
| ------------- | ---------------------------------------------------- |
| Shared goal | Inversion of control over dependency construction |
| SL mechanics | Global registry, `get(key)` at call time |
| DI mechanics | Constructor parameters wired at composition root |
| SL core flaw | Hidden dependencies; runtime failures; hostile tests |
| DI core win | Signature = documentation; compiler-enforced wiring |
| Acceptable SL | Plugin/command registries keyed by runtime data |
| Anti-pattern | Injecting the container and locating inside classes |
| Pairs with | IoC containers, DIP, hexagonal ports/adapters |

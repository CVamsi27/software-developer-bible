# Service Locator vs Dependency Injection


## Definition

With Service Locator, a consumer asks a registry for dependencies. With Dependency Injection, a caller supplies the dependencies the consumer needs. A container can support either approach; the difference is whether the consumer performs service lookup itself.

> **Textbook Definition:** Service Locator resolves dependencies through a registry queried by consumers; Dependency Injection provides dependencies through a consumer's construction or invocation interface, making collaboration requirements explicit.

## First Principles

A service needs storage, but should not choose the database configuration and lifetime in the middle of its business operation. Move construction to a boundary. Then decide whether the service receives storage directly or discovers it through a registry. Direct injection makes a fixed required dependency easier to see; a runtime-selected capability may legitimately need a registry.

## Trace the same dependency two ways

```typescript
interface Orders { count(): Promise<number> }
interface Services { orders(): Orders }

class LocatedReport {
  constructor(private readonly services: Services) {}
  run(): Promise<number> { return this.services.orders().count(); }
}
class InjectedReport {
  constructor(private readonly orders: Orders) {}
  run(): Promise<number> { return this.orders.count(); }
}

async function main(): Promise<void> {
  const fakeOrders: Orders = { count: async () => 3 };
  console.log(await new LocatedReport({ orders: () => fakeOrders }).run()); // 3
  console.log(await new InjectedReport(fakeOrders).run());                 // 3
}
void main().catch(console.error);
```

The first report depends on a registry and asks it to resolve storage during `run`. The second receives storage at construction, so its constructor exposes the required dependency directly. Both can be tested without globals. A locator need not be global or use untyped string keys, though a global mutable locator creates additional isolation problems.

```text
locator: consumer → registry lookup → dependency
DI:      composition boundary → dependency → consumer constructor
```

## Wiring time is a separate choice

Constructor injection can fail early if the graph is eagerly built and validated at startup. Lazy providers, factories and request-scoped resolution may fail later. A typed locator can catch key/type mistakes at compile time, while both designs still need runtime registration and configuration checks. Neither guarantees that credentials work or that external services are available.

TypeScript interfaces disappear at runtime. A container needs supported classes, tokens or registrations. Constructor types help typed callers supply compatible values, but JavaScript calls and casts can bypass those checks. Do not describe injection as universally startup-verified or fully compile-time safe.

## Registries are useful when selection is data

A plugin host may receive a format or command name at runtime. Inject a narrow registry that resolves approved implementations, handles unknown names explicitly and validates configuration. That dynamic selection is part of the consumer's actual contract, rather than a hidden way to obtain every service in the application.

Avoid injecting a whole container merely to call `get` for unrelated dependencies later. It obscures ownership and expands the consumer's capabilities. Property injection is another legitimate framework mechanism, but needs a clear initialization phase so use-before-set cannot occur.

## Ownership matters more than ceremony

Choose runtime, request, tenant or operation scope for each dependency. Share only resources that are compatible with concurrent callers and dispose them through the owner of the scope. Plain constructors and functions can provide DI without framework decorators. An application can have several explicit composition boundaries, such as server startup, worker startup and test setup, rather than one literal file containing every `new`.

Resolve cycles by examining responsibilities. Deferred resolution sometimes supports legitimate cycles, but can conceal initialization order and disposal problems. Migrating legacy global lookup can proceed incrementally through a narrow seam, then direct injection where selection is fixed.

## Summary

Supply fixed required collaborators directly when that makes the contract clear. Use a narrow registry for genuine runtime selection. Trace resolution timing and ownership separately from the label, and validate the actual graph under the application's chosen scopes.

# Service Locator vs Dependency Injection

Two report objects can both return a count of three. One asks a registry for `Orders` when it runs; the other receives `Orders` in its constructor. Both can be tested, but only the second declares that collaborator directly. The distinction is about where lookup happens, not whether a container exists:

```typescript
new InjectedReport(fakeOrders).run(); // 3 — collaborator declared in constructor
```

## Definition

**Dependency Injection (DI)** supplies a component's dependencies from outside instead of having the component construct them. A **Service Locator** is a registry that a component queries to obtain a dependency when it needs one. The registry itself can be injected, so DI and Service Locator can be combined. The useful design comparison is direct injection of a required collaborator versus lookup through a registry.

> **Textbook Definition:** Fowler distinguishes the patterns by how a component obtains its implementation: with a Service Locator, the component explicitly requests it; with Dependency Injection, the dependency is supplied without that request. Both separate configuration from use. [Fowler — Service Locator vs Dependency Injection](https://martinfowler.com/articles/injection.html#ServiceLocatorVsDependencyInjection)

## First Principles

A report with one configured data source should state that requirement as an `Orders` dependency. A composition boundary chooses the implementation, configuration, and lifetime, then supplies it. When input data genuinely selects among approved capabilities — for example, a file format plugin — a narrow registry makes that runtime choice explicit. A general container lookup for fixed collaborators hides a decision belonging at composition time.

## 1. Trace the same dependency two ways

```typescript
interface Orders { count(): Promise<number> }
interface Services { orders(): Orders }

class LocatedReport {
  constructor(private readonly services: Services) {}
  run(): Promise<number> { return this.services.orders().count(); }
}
class InjectedReport {
  constructor(private readonly orders: Orders) {}
  run(): Promise<number> { return this.orders.count(); }
}

async function main(): Promise<void> {
  const fakeOrders: Orders = { count: async () => 3 };
  console.log(await new LocatedReport({ orders: () => fakeOrders }).run()); // 3
  console.log(await new InjectedReport(fakeOrders).run());                 // 3
}
void main().catch(console.error);
```

`LocatedReport` receives the `Services` registry through its constructor, so the registry itself is injected. During `run`, however, the report still looks up `Orders`; its constructor never shows that specific collaborator. `InjectedReport` receives `Orders` directly. Both can be tested without globals. A locator need not be global or use untyped string keys — though a global mutable locator creates additional isolation problems.

```text
locator: consumer → registry lookup → dependency
DI:      composition boundary → dependency → consumer constructor
```

## 2. Separate wiring time from the pattern

An eagerly built dependency graph can reveal missing registrations at startup. Lazy providers, factories, and request-scoped resolution may fail later. A typed locator API can catch key/type mistakes at compile time, but only container-based wiring needs container registrations; direct construction uses ordinary call sites. Neither types nor successful resolution prove credentials work or an external service is available.

TypeScript erases interfaces at runtime. A container therefore needs runtime values such as classes or explicit tokens to identify interface-backed dependencies. TypeScript checks compatible values at typed call sites, but JavaScript calls and type assertions can bypass those checks. [TypeScript Handbook — Erased Types](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types)

## 3. Use a registry when selection is data

A plugin host may receive a format or command name at runtime. Inject a narrow registry resolving approved implementations, handling unknown names explicitly, and validating configuration. That dynamic selection is part of the consumer's actual contract — not a hidden way to obtain every service in the application.

Never inject a whole container merely to call `get` for unrelated dependencies later. It obscures ownership and expands the consumer's capabilities. Property injection is another legitimate framework mechanism, but it needs a clear initialization phase so use-before-set cannot occur.

## 4. Let ownership matter more than ceremony

Choose application, request, tenant, or operation scope per dependency. A long-lived singleton must never retain request-specific state; share resources only when safe for concurrent callers and dispose them through the scope owner. Plain constructors and functions provide DI without framework decorators. An application can hold several composition boundaries — server startup, worker startup, test setup — rather than one literal file containing every `new`.

Resolve cycles by examining responsibilities. Deferred resolution sometimes supports legitimate cycles, but can conceal initialization-order and disposal problems. Migrating legacy global lookup can proceed incrementally through a narrow seam, then direct injection where selection is fixed.

## Summary

Supply fixed required collaborators directly when that makes the contract clear. Use a narrow registry for genuine runtime selection. Trace resolution timing and ownership separately from the label, and validate the actual graph under the application's chosen scopes.

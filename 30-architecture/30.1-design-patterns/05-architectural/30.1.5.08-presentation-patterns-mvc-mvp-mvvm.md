# Presentation Patterns — MVC, MVP, MVVM

The checkout total changes from USD 12.50 to USD 15.00, but the screen still shows USD 12.50. Who owns the screen state, and which component tells the view to render the new value? MVC, MVP and MVVM place that coordination in different roles.

## Definition

Model-View-Controller (MVC), Model-View-Presenter (MVP) and Model-View-ViewModel (MVVM) separate application state, screen-specific state, input handling and rendering through different collaboration rules. MVC routes user input through a controller and synchronizes views with the model. MVP gives a presenter responsibility for coordinating the model and view. MVVM exposes screen state and operations through a view-model that the view can bind to. Frameworks vary, so describe the actual flow before assigning a label.

> **Textbook Definition:** In classic MVC, a controller interprets user input and changes a UI-independent model; views render and may observe model changes. In passive-view MVP, a presenter coordinates the model and calls a view contract. In MVVM, a view-model holds presentation state and commands that a view can bind to. These are role contracts, not mandatory framework class names. [Fowler — GUI architectures](https://martinfowler.com/eaaDev/uiArchs.html) · [Microsoft — MVVM](https://learn.microsoft.com/en-us/dotnet/architecture/maui/mvvm)

## First Principles

The order total is application state; its currency label, pending indicator and unsaved edits are screen state. If one handler owns persistence, business rules, formatting and widget updates, a screen change can alter business behavior. Keep authoritative rules at their application boundary, then choose one owner for screen state and one explicit way to synchronize the view.

## Trace the same checkout through three arrangements

```text
MVC-style desktop interaction:
input → controller → model changes → view observes/pulls → display

MVP passive view:
input → presenter → model/service → presenter chooses output → view methods

MVVM:
input binding/command → view-model → model/service
                         └→ presentation state → binding → display
```

In the first arrangement, the model's change notification causes the view to read state again. In passive-view MVP, the presenter explicitly calls display operations. In MVVM, the view binds to the view-model's presentation state; the binding mechanism propagates a change. Two-way binding is optional: an explicit input event can call a view-model operation.

These are role relationships, not a ranking in which each later pattern makes the view "dumber." Views still own rendering and UI-specific behavior. Validation and authorization that must hold beyond one screen remain at their authoritative domain/server boundary.

## What a passive-view presenter does

```typescript
interface CheckoutView {
  showTotal(text: string): void;
  showError(message: string): void;
}
interface CheckoutModel { totalCents(): number }

class CheckoutPresenter {
  constructor(private readonly model: CheckoutModel, private readonly view: CheckoutView) {}
  refresh(): void {
    const total = this.model.totalCents();
    if (!Number.isSafeInteger(total) || total < 0) {
      this.view.showError('Total is unavailable');
      return;
    }
    this.view.showTotal(`USD ${(total / 100).toFixed(2)}`);
  }
}

new CheckoutPresenter(
  { totalCents: () => 1250 },
  { showTotal: console.log, showError: console.error }
).refresh(); // USD 12.50
```

The presenter reads the model, validates the small presentation contract and formats the result for the view. The view does not need to know how the total is computed. This example assumes USD and integer cents; it is not a general currency-formatting library. A fake view can record method calls for tests, while rendering tests still verify what users actually see.

A supervising-controller variation permits straightforward view bindings and reserves more complex coordination for the presenter. It trades a little view behavior for simpler mapping; passive view moves that coordination into the presenter. These are different balances within MVP, not contradictions.

## Web MVC is a request boundary

A typical server-rendered flow is router → controller → model/service → template → response. The server's template is executed for that response; a browser is not automatically a persistent observer of the server model. Live updates need an additional protocol and client mechanism. This differs from the familiar desktop observer-based MVC arrangement without making web MVC merely an incorrect name.

Controllers commonly handle request parsing, authentication context, invocation and response mapping. Keep domain rules in a reusable authoritative boundary. Rendering a view does not establish that every query is a pure function or that all server frameworks have identical architecture.

## Frameworks provide mechanisms, applications choose roles

React's component model uses explicit state ownership and one-way data flow. Derive display values from current props and state during rendering instead of copying them into additional state with an Effect (`useEffect`); use Effects to synchronize with external systems. A feature can extract presenter/view-model-like logic into hooks or other modules, but React does not require an MVC/MVP/MVVM layer. A hook is not automatically a pure presenter: it can depend on rendering, Effects and external state.

Vue and Angular provide reactive state and declarative bindings that can support view-model roles. Their entire architecture is not determined by that similarity. Next.js adds server/client boundaries and request handling without mandating one controller-model-view decomposition. Describe ownership, data flow and lifecycle in the actual feature.

```text
user intent → update boundary → authoritative state
                             → presentation state → rendered output
```

For asynchronous reads, make pending/error states explicit and decide which request owns the visible result; ignore or cancel obsolete work. Clean up subscriptions on teardown. Effects that copy derived state back into its source can create feedback loops and stale screens.

## Choose separation by the problem

| Problem | Useful boundary |
| ---------------------------------------------------- | ------------------------------------ |
| Repeated server request/response concerns | Controller/service/template roles |
| UI coordination needs tests independent of rendering | Presenter with focused view contract |
| A binding system consumes screen-specific state | View-model with explicit operations |
| A small component already has clear state ownership | Keep its direct component design |

A feature may use different arrangements at different boundaries. Document those boundaries rather than requiring one label for every screen. Test domain rules directly, integration behavior through the rendered UI and a representative set of complete workflows; a blanket "shallowly and sparingly" rule can miss meaningful failures.

## Summary

Follow input, authoritative change and presentation update before naming the pattern. MVC, MVP and MVVM provide different places for coordination and propagation; use the roles that clarify ownership, lifecycle and testable behavior in the actual framework.

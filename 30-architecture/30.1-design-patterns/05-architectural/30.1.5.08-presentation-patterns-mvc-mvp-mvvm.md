# Presentation Patterns — MVC, MVP, MVVM

> **TL;DR:** MVC, MVP, and MVVM are strategies for splitting UI code into **model** (state + business rules), **view** (rendering), and an intermediary (controller / presenter / view-model) — differing in *who talks to whom* and *how updates flow*. Web "MVC" frameworks repurposed the name for request/response routing; MVVM's data binding fits reactive frameworks; React is neither classic MVC nor classic MVVM — it is a unidirectional component model. Interviewers love asking which one your framework actually implements.

## Definition

All three patterns answer the same question — *how do we keep UI rendering decoupled from domain state?* — with different wiring:

| Pattern            | Intermediary                                  | View knows about              | Update mechanism                             | Origin                                              |
| ------------------ | --------------------------------------------- | ----------------------------- | -------------------------------------------- | --------------------------------------------------- |
| **MVC** (original) | Controller (input) + Observer link Model→View | Model directly                | Model notifies observers; view pulls state   | Smalltalk-80 (Reenskaug → GoF era)                  |
| **Web MVC**        | Controller (request handler)                  | Rendered output only          | Server renders new page/fragment per request | Rails/Django/Spring adaptation (~2004+)             |
| **MVP**            | Presenter                                     | View via interface            | Presenter pushes state into passive view     | 1990s Dolphin/Taligent; testability focus           |
| **MVVM**           | ViewModel (observable state)                  | Nothing — binds declaratively | Data binding syncs view <-> view-model       | Microsoft WPF (Gossman, 2005); Knockout/Vue lineage |

```text
MVC (original)                          MVP
┌────────────────────────────────────────────────────────────────────┐
│ View  │ ────────────▶ │Controller│   │ View  │ ─────▶  │           │
│   ▲   │               └────┬─────┘   │(passive)◀───────│           │
│   │pulls/notified          ▼         │        setState │           │
┌──┴──────────┐        ┌──────────┐     └───▲─────┐      └─────┬─────┘
│   Model     │◀───────│  Model   │         │ reads plain model      │
│ (notifies)  │        └──────────┘     ┌───┴────┐                   │
└────────────────────────────────────────────────────────────────────┘
                                        └────────┘

MVVM
┌────────────────────────────────────────────────────────────────┐
│ View  │ ◀─────────────────────▶ │ View-Model │ ──────▶ │ Model │
└────────────────────────────────────────────────────────────────┘
```

The intermediary's job grows progressively fatter and the view progressively dumber as you move MVC → MVP → MVVM.

## Why Do We Need It?

1. **Testability** — rendering cannot be unit-tested cheaply; presenters/view-models can be, if they hold no framework references.
2. **Parallel work** — designers touch templates/bindings while engineers evolve models.
3. **Change amplification control** — without separation, a styling tweak risks business logic edits.
4. **Multiple presentations** — same model feeding web, mobile, CLI views through shared intermediaries.
5. **Framework fluency signal** — senior frontend/backend interviews probe whether you know what React/Vue/Angular actually do versus what marketing calls them.

## How It Works

### Original MVC (Smalltalk)

1. Controller receives raw input, translates to model operations (`controller.addItem()`).
2. Model mutates itself, enforces rules, then **notifies observers**.
3. Views subscribed to the model re-query it and redraw.

The defining trait: views observe models directly. In server-rendered web this observer loop died — HTTP request/response has no persistent view objects — so **web MVC** kept only the naming: Router → Controller → Model → Template render. The "View" became a template executed once; there are no observers. That historical drift is interview trap #1.

### MVP — Passive View vs Supervising Controller

- **Passive view:** the view interface exposes only `setOrderTotal(text)`, `showError(msg)` — zero logic, maximally testable presenter, view dumb as a screen buffer.
- **Supervising controller:** presenter handles complex state logic but lets simple bindings read the model directly — a pragmatic middle ground.

```typescript
interface OrderView {
  setTotal(totalText: string): void;
  setItems(items: string[]): void;
  showError(message: string): void;
}

class OrderPresenter {
  constructor(private readonly view: OrderView, private readonly cart: Cart) {}

  onAddItem(productId: string, qty: number): void {
    try {
      this.cart.add(productId, qty);
      this.view.setItems(this.cart.descriptions());
      this.view.setTotal(this.cart.total().format('USD'));
    } catch (e) {
      this.view.showError((e as Error).message);
    }
  }
}

// Test — no DOM anywhere:
const fakeView: OrderView = { setTotal: vi.fn(), setItems: vi.fn(), showError: vi.fn() };
new OrderPresenter(fakeView, cartWithItems()).onAddItem('sku-1', 2);
expect(fakeView.setTotal).toHaveBeenCalledWith('$25.00');
```

### MVVM — the ViewModel as observable state

A view-model holds renderable state and commands, exposing observables/computed values; the view binds declaratively and the binding engine propagates changes.

```typescript
class CheckoutViewModel {
  constructor(private readonly cart: Cart) {}

  @observable items: string[] = [];
  @observable couponCode = '';

  @computed get total(): string {
    return this.cart.total().format('USD');
  }

  @computed get canSubmit(): boolean {
    return this.items.length > 0 && this.couponCode.length > 0;
  }

  async submit(): Promise<void> { /* command invoked by binding */ }
}
// View template: <button disabled="{{!vm.canSubmit}}">Checkout</button>
```

Knockout pioneered this in JS; Vue's `ref`/`computed` + template directives and Angular's component bindings are production-grade descendants. Two-way binding is optional flavor — modern implementations prefer one-way data down, explicit events up.

## Which Frameworks Actually Use What

| Framework                       | Honest classification                                           | Notes                                                                                                               |
| ------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Rails/Django/Laravel/Spring MVC | **Web MVC**                                                     | Router+controller+template; no observer loop                                                                        |
| Angular                         | Component architecture closest to **MVVM-ish**                  | Component class acts as view-model; change detection replaces manual observers                                      |
| Vue                             | **MVVM-flavored** reactivity                                    | Official docs historically said "inspired by MVVM"; `reactive`/`computed` are the view-model layer                  |
| React                           | **Neither** — unidirectional component model (Flux/MVU lineage) | No separate controller/presenter/view-model; components own render(state); state libraries add Flux/Redux semantics |
| Next.js (server components)     | Pushes **web-MVC shape back in**                                | Controllers/actions + server-rendered views; client components stay React-style                                     |
| WPF/Xamarin/Knockout            | Canonical **MVVM**                                              | The pattern's birthplace                                                                                            |
| SwiftUI/Compose                 | MVVM-friendly unidirectional hybrids                            | Observable state + declarative views                                                                                |

Interview traps this table defuses:

1. *"React follows MVC"* — no. It deliberately dropped controllers/two-way binding for unidirectional flow; Redux formalizes Flux, not MVC.
2. *"MVVM requires two-way binding"* — no. Binding direction is an implementation choice; the essence is an observable view-model separated from the view.
3. *"Server-side frameworks do original MVC"* — no observer relationship exists across an HTTP boundary; it is a renamed request-handling pipeline.
4. *"MVP is obsolete"* — its core idea (testable UI logic behind a view interface) survives in every `usePresenter()`/hook extraction and testing-library philosophy.

## Code Examples

### Minimal original-MVC sketch (observer intact)

```typescript
import { EventEmitter } from 'node:events';

class CartModel extends EventEmitter {
  private items: { sku: string; qty: number }[] = [];
  addItem(sku: string, qty: number): void {
    this.items.push({ sku, qty });
    this.emit('changed'); // model notifies views
  }
  snapshot() { return structuredClone(this.items); }
}

class CartView {
  constructor(private model: CartModel, private render: (s: object) => void) {
    this.model.on('changed', () => this.redraw()); // direct observation
  }
  redraw(): void { this.render(this.model.snapshot()); }
}

const model = new CartModel();
new CartView(model, (s) => console.log(s));
model.addItem('sku-1', 2); // view repaints without any controller involvement
```

This triangle — input through controller, propagation through model observers — is what "real" MVC means and what web MVC quietly discarded.

### Choosing between them (decision guide)

| Situation                                                  | Reach for                                                        |
| ---------------------------------------------------------- | ---------------------------------------------------------------- |
| Server-rendered pages, form posts                          | Web MVC (controllers + templates)                                |
| Rich widget UI, heavy unit-test demands, no binding engine | MVP (passive view)                                               |
| Reactive/binding framework available (Vue/Angular/WPF)     | MVVM (observables + computed)                                    |
| Component-based SPA with strict unidirectional flow        | React/Flux-style; borrow MVVM ideas via hooks/view-model classes |

## Real-World Use Cases

1. **Enterprise dashboards on Angular** — components as view-models with computed signals; classic MVVM reasoning about testability applies.
2. **Vue e-commerce frontends** — Pinia store + composables act as the view-model layer over API models.
3. **Rails monolith admin panels** — textbook web MVC; fat-controller cleanup mirrors MVP presenter extraction.
4. **WPF line-of-business apps** — canonical XAML + ViewModel + commands.
5. **React design systems** — headless hooks (logic) + dumb components (view) recreate passive-view testability inside React's model.

## Common Mistakes

### 1. Fat controllers in web MVC

Business rules crammed into controllers ("controller as model layer") duplicate logic across endpoints. Extract domain services/models; controllers orchestrate HTTP concerns only.

### 2. Model-ignoring views in original MVC

Views that never observe the model go stale; ad-hoc refresh timers replace the observer contract. Subscribe or re-render explicitly — pick one and document it.

### 3. God presenters

MVP presenters absorbing validation, formatting, navigation, AND persistence become untestable monoliths — the pattern's point was testable units, not relocation of spaghetti.

### 4. Two-way binding chaos

Bidirectional bindings between unrelated fields create update cascades nobody can trace. Default to one-way flow + explicit events; allow two-way only on genuinely symmetric form inputs.

### 5. Mislabeling frameworks in interviews

Calling React "MVVM" or Rails "Smalltalk MVC" signals memorized buzzwords. Describe the actual data flow instead: "React renders from immutable state snapshots with events flowing up."

### 6. Mixing patterns mid-view-layer

Half the views talk to presenters, half bind to view-models of the same feature. Pick per application (or at least per module) based on the framework's grain.

## Best Practices

1. Name the pattern you are using per app/module; write it in the README — prevents archaeological debates later.
2. Keep views dumb even when the framework permits smart ones; push logic down until tests stop needing DOM.
3. Treat view-model/presenter outputs as pure functions of inputs wherever possible.
4. Prefer unidirectional data flow by default regardless of pattern; bidirectionality is opt-in and local.
5. Unit-test presenters/view-models directly; integration-test views shallowly; e2e-test flows sparingly.
6. When migrating legacy jQuery screens, extract an MVP presenter first — it gives you seams before any rewrite.

### Composition with modern state management

The classic patterns did not die; they dissolved into state-management layers:

| Classic role           | React equivalent                                        | Vue equivalent                               |
| ---------------------- | ------------------------------------------------------- | -------------------------------------------- |
| Model                  | API client + domain types + store state (Zustand/Pinia) | Pinia store                                  |
| View-model / Presenter | Custom hooks (`useCheckout()`), selectors, thunks/sagas | Composables (`useCheckout()`) + computed     |
| View                   | Dumb function components                                | Single-file component templates              |
| Observer plumbing      | `useSyncExternalStore`, subscription libs               | Reactivity system (`ref`/`computed`/`watch`) |

Reading table: a well-factored React feature IS an MVP/MVP-flavored design — hooks hold the presenter's logic behind testable pure functions, components render the passive view. The same is true of Vue composables wearing MVVM clothes. This mapping is the strongest senior-interview answer to "which pattern does your stack use": describe the mapping rather than reciting labels.

## Summary

MVC, MVP, and MVVM are three answers to UI/state separation, distinguished by their intermediary and update plumbing: MVC couples views to observing models (original) or dissolves into request handling (web), MVP inserts a test-driven presenter pushing into a passive view, and MVVM exposes an observable view-model consumed by declarative bindings. Modern stacks blur the lines — Vue/Angular lean MVVM, React runs its own unidirectional model, and server frameworks practice renamed web MVC — so precision about data flow beats label loyalty.

**Interview-ready one-liner:** "They differ in who mediates: MVC has views observing models (or web-MVC's controller-render pipeline), MVP has a presenter pushing into a passive test-only view interface, and MVVM binds views to an observable view-model. React isn't any of them — it's unidirectional component rendering — so I'd describe actual data flow rather than reach for labels."

## Cheat Sheet

| Aspect           | MVC (original)       | Web MVC                | MVP                         | MVVM                        |
| ---------------- | -------------------- | ---------------------- | --------------------------- | --------------------------- |
| Intermediary     | Controller           | Controller/router      | Presenter                   | ViewModel                   |
| View coupling    | Observes model       | None (template)        | Interface, passive          | Bindings only               |
| Update flow      | Model notifies views | Full re-render/request | Presenter setState          | Binding engine sync         |
| Testability unit | Model                | Controller+model       | Presenter                   | ViewModel                   |
| Typical homes    | GUI toolkits         | Rails/Django/Spring    | WinForms-era, legacy rescue | WPF, Knockout, Vue, Angular |
| Key risk         | Stale views          | Fat controllers        | God presenters              | Binding tangles             |

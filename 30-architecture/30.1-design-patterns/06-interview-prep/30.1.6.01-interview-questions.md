# Design Patterns Interview Questions

Practice describing the contract and one observable outcome before choosing a pattern name. The later scenarios add storage, concurrency and failure decisions to local object relationships.

## First Principles

Answer the prompt before reading its answer. Name the problem, trace one call or state change, identify a failure boundary and compare a simpler alternative. Use the learning chapters for implementation examples; this bank rehearses explanation and applied decisions.

The scenario questions ask for system mechanisms as well as pattern names. A correct label alone does not establish persistence, concurrency, security or delivery behavior.

---

## Explain the contract

[Creational chapters](../02-creational/INDEX.md), [structural chapters](../03-structural/INDEX.md), and [behavioral chapters](../04-behavioral/INDEX.md) provide the worked mechanisms.

### 1. What is the Singleton pattern and when would you use it?

**Answer:**
Singleton controls one instance within a defined scope, usually one loaded module/runtime. Processes, workers and independently loaded module copies can have separate instances. It does not establish a distributed singleton.

**When to use:**

- Database connection pools
- Configuration managers
- Logging services
- Caching mechanisms

**Follow-up:** What are the problems with Singleton?

- Global state, tight coupling, testing difficulties, concurrency issues.

---

### 2. What is the Factory pattern and why is it useful?

**Answer:**
Factory techniques centralize creation. A Simple Factory selects a product; GoF Factory Method lets a subclass override creation; Abstract Factory creates a compatible family. Identify which mechanism the example actually uses.

**Why useful:**

- Loose coupling
- Easier maintenance
- Better testability
- Flexibility in object creation

---

### 3. What is the Observer pattern and where is it used?

**Answer:**
The Observer pattern defines a one-to-many dependency between objects so that when one object changes state, all dependents are notified.

**Where used:**

- Node.js EventEmitter registrations
- Explicit UI or store subscriptions
- Local change notifications

A React state update or a brokered event alone does not prove a GoF Observer implementation. Explain registration, callback timing, cleanup and delivery failure in the actual mechanism.

---

### 4. What is the Adapter pattern?

**Answer:**
The Adapter pattern allows objects with incompatible interfaces to collaborate by wrapping one interface to make it compatible with another.

---

### 5. What is the Builder pattern?

**Answer:**
The Builder pattern separates the construction of a complex object from its representation, allowing step-by-step construction.

---

### 6. What is the Facade pattern?

**Answer:**
The Facade pattern provides a simplified interface to a complex subsystem, hiding its complexity.

---

### 7. What is the difference between Creational, Structural, and Behavioral patterns?

**Answer:**

- **Creational**: Deal with object creation (Singleton, Factory, Builder)
- **Structural**: Deal with object composition (Adapter, Facade, Decorator)
- **Behavioral**: Deal with object communication (Observer, Strategy, Chain of Responsibility)

---

### 8. What is the Decorator pattern?

**Answer:**
The Decorator pattern allows adding behavior to objects dynamically by wrapping them in decorator objects.

---

### 9. What is the Proxy pattern?

**Answer:**
The Proxy pattern provides a surrogate or placeholder for another object to control access to it.

---

### 10. What is the Strategy pattern?

**Answer:**
The Strategy pattern defines a family of algorithms, encapsulates each one, and makes them interchangeable.

## Compare neighboring intentions

Use [foundations revision](../01-foundations/REVISION.md), [behavioral revision](../04-behavioral/REVISION.md), and [Repository](../05-architectural/30.1.5.01-repository.md) to check contracts after answering.

### 11. What are the SOLID principles and how do design patterns relate to them?

**Answer:**

- **S**ingle Responsibility: Each class has one reason to change
- **O**pen/Closed: Open for extension, closed for modification
- **L**iskov Substitution: Subtypes must be substitutable for base types
- **I**nterface Segregation: Clients depend only on operations they need
- **D**ependency Inversion: Depend on abstractions, not concretions

Patterns can support particular design principles when their contracts are applied well; their presence does not prove SOLID compliance:

- Strategy → Open/Closed
- Factory → Dependency Inversion
- Interface Segregation → Interfaces split around actual client needs

---

### 12. What is the difference between Strategy and State patterns?

**Answer:**

- **Strategy**: Delegates to a selected interchangeable policy; selection may remain fixed for the object lifetime
- **State**: Changes behavior based on internal state, state transitions

---

### 13. What is the difference between Decorator and Proxy patterns?

**Answer:**

- **Decorator**: Adds behavior, focuses on extending functionality
- **Proxy**: Controls access or location/lifecycle while representing the subject

Both wrap objects, but their intent differs.

---

### 14. What is the Repository pattern and when should you use it?

**Answer:**
Repository mediates between domain and data mapping layers, exposing a collection-like interface to domain objects.

**When to use:**

- Domain-driven design
- Need database abstraction
- Complex queries
- Testing requirements

---

### 15. What is the Chain of Responsibility pattern?

**Answer:**
Chain of Responsibility passes requests along a chain of handlers, each deciding to process or pass along.

---

### 16. What is the Template Method pattern?

**Answer:**
Template Method defines the skeleton of an algorithm in a base class, letting subclasses override specific steps.

---

### 17. What is the Command pattern?

**Answer:**
Command encapsulates a request as an object, allowing parameterization and queueing.

---

### 18. What is the Mediator pattern?

**Answer:**
Mediator gives one owner responsibility for a cohesive coordination protocol. Participants send relevant events to it rather than reaching into each other; it need not own every communication in the application.

---

### 19. What is the Composite pattern?

**Answer:**
Composite composes objects into tree structures and lets clients treat individual objects and compositions uniformly.

---

### 20. What is the Iterator pattern?

**Answer:**
Iterator provides a way to access elements of an aggregate object sequentially without exposing its underlying representation.

---

## Reason about consequences

Use the [category learning flows](../INDEX.md) to find the source of a disputed mechanism; architectural boundaries are compared in [architectural revision](../05-architectural/REVISION.md).

### 21. How do you decide which design pattern to use?

**Answer:**
Consider:

1. **Problem type**: What problem are you solving?

2. **Context**: What's the application context?

3. **Trade-offs**: What are the costs and benefits?

4. **Existing patterns**: What patterns are already in use?

5. **Team familiarity**: What does the team know?

**Decision framework:**

- Creating objects → Factory, Builder, Singleton
- Adding behavior → Decorator, Strategy
- Simplifying interface → Facade, Adapter
- Managing complexity → Composite, Chain of Responsibility

---

### 22. What is the relationship between Design Patterns and Architecture?

**Answer:**

- **Patterns**: Solutions to recurring design problems
- **Architecture**: High-level structure of the system

Local creation, policy and communication patterns can clarify responsibilities inside any of these architectures. They do not establish service boundaries, dependency direction or durable event delivery by themselves. For example, an event-driven service still needs persisted outgoing intent and consumer progress beyond a callback list.

---

### 23. How do you handle cross-cutting concerns with patterns?

**Answer:**
Cross-cutting concerns (logging, security, transactions) can be handled with:

1. **Decorator Pattern**: Add behavior dynamically

2. **Chain of Responsibility**: Middleware pipeline

3. **Proxy Pattern**: Control access

4. **AOP (Aspect-Oriented Programming)**: Separate concerns

---

### 24. What are anti-patterns related to design patterns?

**Answer:**

1. **Pattern Overuse**: Using patterns when simpler solutions exist

2. **Gold Plating**: Adding unnecessary complexity

3. **God Object**: Class doing too much

4. **Spaghetti Code**: Tangled control/data dependencies that make behavior hard to trace

5. **Resume Driven Development**: Using patterns just to show knowledge

---

### 25. How do you test code that uses design patterns?

**Answer:**
Test the contract that the pattern establishes: factory configuration and product compatibility; Strategy input/output/failure equivalence; Observer order, cleanup and reentrancy; Decorator composition order; Proxy bypass, lifetime and failure behavior. Test database and remote-adapter guarantees at those boundaries rather than relying only on mocks.

---

### 26. How do patterns affect performance?

**Answer:**
Indirection, allocations and retained state have costs, but the pattern name does not determine their size. Trace the dominant work, measure the workload and include cache invalidation, resource lifetime and contention. A lazy proxy may move latency to first use; a singleton may reduce construction while increasing shared-state contention.

---

### 27. What is the relationship between patterns and SOLID principles?

**Answer:**
Suppose a new shipping provider needs a different input from the existing Strategy contract. Do not claim OCP means the client can never change. Decide whether to extend the shared contract, add an adapter or model a separate operation, then check compatibility with existing providers. Naming the pattern does not prove substitution.

---

### 28. How do you handle design patterns in distributed systems?

**Answer:**
A local wrapper or callback becomes a network boundary only through additional mechanisms. A remote Proxy needs deadlines, cancellation, status/serialization mapping and duplicate-effect handling. A brokered notification needs durable progress, acknowledgment, retry and ordering rules. Process-local Singleton identity does not coordinate service replicas.

---

### 29. What are modern alternatives to classic design patterns?

**Answer:**
Language mechanisms often make the same intention simpler: functions can express Strategy or local Command; generators implement Iterator; modules or scoped providers can own shared services. A DI factory is not automatically GoF Factory Method, and a reactive stream has more delivery semantics than a local Observer list.

---

### 30. How do you refactor code to use design patterns?

**Answer:**

1. **Identify code smells**: Duplication, complex conditionals

2. **Extract common behavior**: Look for repeated code

3. **Apply appropriate pattern**: Match problem to pattern

4. **Refactor incrementally**: Small changes, test often

5. **Document decisions**: Why this pattern was chosen

---

### 31. What is the impact of design patterns on code maintainability?

**Answer:**
**Positive:**

- Clear structure and intent
- Reusable solutions
- Better testability
- Team communication

**Negative:**

- Over-engineering
- Added complexity
- Learning curve
- Potential misapplication

---

### 32. How do you handle design patterns in legacy code?

**Answer:**

1. **Identify refactoring opportunities**: Look for code smells

2. **Apply Strangler Fig pattern**: Gradually replace

3. **Use Adapter pattern**: Integrate with legacy

4. **Introduce patterns incrementally**: Start with low-risk areas

5. **Write tests first**: Ensure behavior preservation

---

### 33. What is the relationship between patterns and frameworks?

**Answer:**
Describe the actual mechanism in framework code: Express routes requests through middleware; a UI component tree composes rendering; provider registration constructs dependencies. A language `@decorator` can attach metadata without wrapping an object through a shared GoF interface. Framework lifecycle callbacks may use composition rather than Template Method inheritance.

---

### 34. How do you handle design patterns in microservices?

**Answer:**
Start with service boundaries, authoritative invariants and communication contracts. Apply local creation, policy and wrapper patterns inside a service where useful. Across services, account for durable intent, retries, idempotency, ordering and partial state. CQRS, sagas and event sourcing are optional choices solving different problems, not a mandatory package.

---

### 35. What are the trade-offs of using design patterns?

**Answer:**

| Benefit | Trade-off |
| --------------- | -------------------------- |
| Code reuse | Added complexity |
| Clear structure | Learning curve |
| Testability | More classes |
| Maintainability | Potential over-engineering |

---

### 36. How do you explain design patterns to non-technical stakeholders?

**Answer:**
Use analogies:

- **Factory**: Like a manufacturing assembly line
- **Strategy**: Like different routes to the same destination
- **Facade**: Like a hotel concierge
- **Decorator**: Like adding toppings to a pizza

Connect the analogy to a concrete consequence: a carrier adapter lets checkout use one shipping contract while provider-specific status mapping stays at the boundary. Explain the extra mapping and tests it requires; a pattern name does not promise faster development or better quality.

---

### 37. What is the role of design patterns in code reviews?

**Answer:**

- **Identify pattern usage**: Ensure correct application
- **Check for anti-patterns**: Spot over-engineering
- **Check contracts**: Identify the change owner, substitution rules and client needs; naming a pattern is not proof of SOLID compliance
- **Knowledge sharing**: Help team learn patterns
- **Consistency**: Ensure consistent pattern usage

---

### 38. How do design patterns evolve over time?

**Answer:**

- **Classic patterns**: GoF patterns still relevant
- **Modern adaptations**: React patterns, serverless patterns
- **Language-specific**: TypeScript decorators, async/await patterns
- **Architecture patterns**: Microservices, event-driven

---

### 39. What are the most overused design patterns?

**Answer:**

1. **Singleton**: Often when DI is better

2. **Factory**: When simple object creation works

3. **Observer**: When a direct call gives a clearer ownership and delivery contract

4. **Decorator**: When explicit configuration is easier to trace than interacting wrapper layers

**Rule of thumb**: Don't use a pattern if a simpler solution exists.

---

### 40. How do you stay updated with design pattern trends?

**Answer:**

- Read blogs and articles
- Study framework source code
- Attend conferences and meetups
- Practice with side projects
- Discuss with team members
- Review open-source projects

## Apply the ideas to concrete systems

Check [Saga](../05-architectural/30.1.5.04-saga.md), [Adapter](../03-structural/30.1.3.01-adapter.md), and [Proxy](../03-structural/30.1.3.04-proxy.md) for the local and remote boundaries used below.

### 41. Design a URL shortener using design patterns.

**Answer:**
Define link creation, durable short-code uniqueness, destination validation, expiry and redirect behavior first. A generator policy can be a Strategy and a cache can be a Proxy, but a factory does not make randomly generated codes collision-free. Persist a unique mapping atomically and retry collisions; scope cache keys and invalidate expired or changed links.

---

### 42. Design a real-time notification system.

**Answer:**
Define notification identity, recipient/channel choice, persisted outgoing intent, retries and delivery evidence. Strategies and adapters can isolate channel APIs. A local Observer may notify in-process consumers; durable cross-process delivery needs a queue and idempotent handling. Provider acceptance is not proof that a user received the notification.

---

### 43. Design a plugin system for an application.

**Answer:**
Use an explicit approved plugin registry, validate manifests and negotiate capability/version contracts. Factories can construct plugins and Strategy can select behavior. A Proxy wrapper is not a sandbox: untrusted code needs an actual isolation boundary and capability restrictions. Define startup, errors, resource limits and disposal.

---

### 44. Design a payment processing system.

**Answer:**
Separate payment intent from provider attempts. Adapters translate provider meaning, Strategies select supported providers and a facade can expose focused operations. Persist a stable operation key, fingerprint and status; authorize each operation and reconcile uncertain outcomes. A timeout does not prove failure, and switching providers during an unknown outcome can double-charge.

---

### 45. Design a caching layer for a web application.

**Answer:**
Start with cache identity, freshness, capacity and invalidation after authoritative commit. A Proxy can wrap access and Strategy can choose eviction. Include tenant/caller visibility where the result depends on them; deduplicate safe in-flight loads and define negative-cache behavior. Notification-based invalidation still needs recovery from missed or duplicate messages.

---

## Defend and refine a design

### 46. How would you refactor a codebase that doesn't use design patterns?

**Answer:**
Choose one concrete behavior that is hard to change or trace. Capture its observable contract, introduce a boundary incrementally and verify representative success/failure cases. Pattern-free code is not inherently defective; preserve a simpler direct design when it already communicates the behavior clearly.

---

### 47. How do you handle design pattern disagreements in a team?

**Answer:**

1. **Discuss trade-offs**: Benefits vs costs

2. **Consider context**: What works for the project

3. **Look at precedents**: What patterns are already used

4. **Prototype**: Try different approaches

5. **Make a decision**: Avoid analysis paralysis

---

### 48. What questions should you ask before applying a design pattern?

**Answer:**

1. What problem are we solving?

2. Is this the simplest solution?

3. What are the trade-offs?

4. Does this fit our architecture?

5. Will the team understand this?

6. How will this affect testing?

7. What are the performance implications?

---

### 49. How do you document design pattern usage?

**Answer:**

- **Code comments**: Explain why, not what
- **Architecture decision records**: Document decisions
- **README files**: Explain pattern usage
- **Diagrams**: Visual representation
- **Code reviews**: Discuss pattern application

---

### 50. What's the most important thing to remember about design patterns?

**Answer:**
**Patterns are tools, not goals.** Use them when they solve a real problem, not just because they exist. The best pattern is the one that makes your code simpler, more maintainable, and easier to understand.

---

## Summary

Explain each intention through a concrete trace and its boundary conditions. A strong answer states who owns creation, delivery, state and recovery, and when a simpler design is enough.

# DRY, KISS, YAGNI & Other Design Principles

> **Beyond SOLID, there are 6 more principles that show up in LLD interviews and code reviews.** DRY, KISS, YAGNI, the Rule of Three, Composition over Inheritance, Principle of Least Astonishment. Senior engineers apply these instinctively.

## TL;DR

- **DRY** — Don't Repeat Yourself. Extract repeated code.
- **KISS** — Keep It Simple, Stupid. Don't over-engineer.
- **YAGNI** — You Aren't Gonna Need It. Don't build for hypothetical futures.
- **Rule of Three** — Wait until you've done something 3 times before abstracting.
- **Composition over Inheritance** — "Has-a" > "Is-a".
- **Principle of Least Astonishment** — Code should do what its name says.
- **Separation of Concerns** — Different concerns in different modules.

---

## Why it matters

LLD interviews don't just ask "design X." They ask "design X with these constraints." The constraints test whether you apply these principles:

- "This needs to be flexible" → think Strategy pattern, OCP
- "This needs to be simple" → KISS, YAGNI
- "This needs to be testable" → DIP, composition
- "This needs to be maintainable" → SRP, separation of concerns

Knowing these names lets you communicate trade-offs in the interview.

## DRY — Don't Repeat Yourself

**Rule:** Every piece of knowledge should have a single, authoritative representation in the system.

**Violation:**

```typescript
// Same logic in 3 places
function calculateOrderTotal(items: Item[]): number {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  return total;
}

function calculateInvoiceTotal(items: Item[]): number {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  return total;
}

function calculateCartTotal(items: Item[]): number {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  return total;
}
```

**Fix:** Extract.

```typescript
function calculateItemsTotal(items: Item[]): number {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
```

**When to apply:** When you have the same logic in 2+ places. Use the **Rule of Three** to avoid premature abstraction.

**When NOT to apply:** Coincidental similarity. Two pieces of code that look the same but mean different things — extracting them creates coupling. Example: "both have a `name` field" doesn't mean they should share a `Nameable` interface.

**In interviews:** "We extracted the calculation logic to a shared utility because we had it in 3 places."

## KISS — Keep It Simple, Stupid

**Rule:** Most systems work best if they're kept simple rather than made complicated.

**Violation:**

```typescript
// Over-engineered solution for a simple problem
abstract class AbstractDataProcessor<T extends BaseEntity>
  implements IDataProcessor<T>, IValidatable, ILoggable {

  private readonly strategyFactory: IStrategyFactory<T>;
  private readonly validatorChain: IValidator<T>[];
  private readonly logger: ILogger;
  private readonly metricsCollector: IMetricsCollector;
  private readonly cacheManager: ICacheManager;
  private readonly eventBus: IEventBus;
  private readonly retryPolicy: IRetryPolicy;

  constructor(
    strategyFactory: IStrategyFactory<T>,
    @Inject('validatorChain') validatorChain: IValidator<T>[],
    @Inject('logger') logger: ILogger,
    // ... 8 more dependencies
  ) { /* ... */ }

  async process(data: T): Promise<ProcessedResult<T>> {
    // 200 lines of orchestration
  }
}
```

**Fix:** Just do the thing.

```typescript
function processOrder(order: Order): ProcessedOrder {
  validate(order);
  const total = calculateTotal(order);
  return saveOrder({ ...order, total });
}
```

**When to apply:** Always. The default. The senior engineer instinct.

**When NOT to apply:** When complexity is justified by requirements. "We need this complex because we're handling 10K transactions/sec across 50 microservices with strict SLAs." That's not over-engineering, that's needed complexity.

**In interviews:** "I went with the simple approach because we don't have the requirements that would justify the complexity. We can refactor when we do."

## YAGNI — You Aren't Gonna Need It

**Rule:** Don't add functionality until it's actually needed.

**Violation:**

```typescript
// Adding "future-proof" features that may never be used
class UserService {
  createUser(data: UserData): User { /* ... */ }

  // Just in case we need to export users to CSV someday
  exportUsersToCsv(users: User[]): string { /* ... */ }

  // Just in case we need to import users from XML
  importUsersFromXml(xml: string): User[] { /* ... */ }

  // Just in case we need a webhook when a user is created
  triggerUserCreatedWebhook(user: User): void { /* ... */ }

  // Just in case we need to sync with LDAP
  syncWithLdap(): void { /* ... */ }
}
```

**Fix:** Add features when needed.

```typescript
class UserService {
  createUser(data: UserData): User { /* ... */ }

  // That's it. Add more when actually needed.
}
```

**Why:** "Just in case" features:
- Add maintenance burden
- Make code harder to understand
- Often never get used (or get used in a way that requires rewriting)
- Block refactoring

**When to apply:** Always. The default.

**When NOT to apply:** Public APIs that need stability. Schema migrations. Data formats that are hard to change later.

**In interviews:** "I didn't add the cache layer because the database is fast enough at current scale. We'll add it when we measure the need."

## Rule of Three

**Rule:** Wait until you've done something 3 times before abstracting.

**Why:** 1 time = maybe a coincidence. 2 times = maybe related. 3 times = definitely a pattern.

**Without the rule:**

```typescript
// First user validation function
function validateUserEmail(email: string): boolean {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
}

// Premature abstraction
interface Validator {
  validate(value: string): boolean;
}

class EmailValidator implements Validator { /* ... */ }
class PhoneValidator implements Validator { /* ... */ }
class NameValidator implements Validator { /* ... */ }

// 2 weeks later: "We don't actually need this abstraction"
```

**With the rule:** Wait until you have 3+ validators or 3+ validation functions, then abstract.

**In interviews:** "I'm not abstracting yet because we only have 2 cases. I'll wait for a 3rd to be sure it's a pattern."

## Composition over Inheritance

**Rule:** Favor "has-a" relationships over "is-a" relationships.

**Inheritance problem:** Subclass inherits everything from parent, including what it doesn't need. Tight coupling. Can't change at runtime.

**Composition solution:** Object has a reference to another object. Loose coupling. Can change at runtime.

**Violation (deep inheritance):**

```typescript
class Vehicle { /* ... */ }
class Car extends Vehicle { /* ... */ }
class SportsCar extends Car { /* ... */ }
class Ferrari extends SportsCar { /* ... */ }
// Ferrari inherits from 3 levels. Changing Vehicle breaks Ferrari.
```

**Fix (composition):**

```typescript
class Car {
  constructor(
    private engine: Engine,        // has-a
    private transmission: Transmission,  // has-a
    private wheels: Wheel[]         // has-a
  ) {}
}
```

**The Strategy pattern is composition:**

```typescript
class DiscountCalculator {
  constructor(private strategy: DiscountStrategy) {}  // has-a
  calculate(amount: number): number { return this.strategy.apply(amount); }
}
```

**When to use inheritance:** When there's a real "is-a" relationship and you want polymorphism. "Square is-a Rectangle" is a famous counter-example (LSP violation).

**When to use composition:** Almost always. Default to composition.

**In interviews:** "I used composition here so we can swap strategies at runtime and test them independently."

## Principle of Least Astonishment (POLA)

**Rule:** A component should behave in a way that most users would expect.

**Violation:**

```typescript
// Function name says "save" but it sends an email
function saveUser(user: User): void {
  database.save(user);
  emailService.sendWelcomeEmail(user);  // Surprise!
  analytics.track("user_created", user);  // Surprise!
  cache.invalidate("users");  // Surprise!
}
```

**Fix:** Do one thing.

```typescript
function saveUser(user: User): void {
  database.save(user);
}

// Caller composes the side effects
saveUser(user);
emailService.sendWelcomeEmail(user);
analytics.track("user_created", user);
```

**More violations:**

```typescript
// Negative-named function that returns positive
function isNotValid(value: string): boolean { /* ... */ }

// Method that mutates AND returns
function addItem(cart: Cart, item: Item): Cart { /* mutates cart, returns new cart */ }

// Parameter order that surprises
function copy(source, destination) { /* source then dest, like cp */ }
function copyTo(source, dest) { /* but here dest is first */ }
```

**In interviews:** "I named the method `sendNotification` and it just sends a notification. The user is created separately. So the call site reads clearly: `createUser`, then `sendNotification`."

## Separation of Concerns (SoC)

**Rule:** Different concerns should be in different modules.

**Concerns:** Different aspects of a system — UI, business logic, data access, logging, etc.

**Violation:**

```typescript
class UserController {
  // 5 concerns mixed: HTTP, validation, business logic, persistence, email
  async createUser(req: Request): Promise<Response> {
    const data = req.body;
    if (!data.email || !data.password) {
      return { status: 400, body: { error: "invalid" } };
    }
    const user = new User(data.email, data.password);
    const hashedPassword = await bcrypt.hash(user.password, 10);
    user.password = hashedPassword;
    await db.query("INSERT INTO users ...");
    await emailService.sendWelcomeEmail(user);
    return { status: 201, body: { user } };
  }
}
```

**Fix:**

```typescript
// Controller: HTTP only
class UserController {
  constructor(private userService: UserService) {}
  async createUser(req: Request): Promise<Response> {
    try {
      const user = await this.userService.createUser(req.body);
      return { status: 201, body: { user } };
    } catch (e) {
      return { status: 400, body: { error: e.message } };
    }
  }
}

// Service: business logic
class UserService {
  constructor(
    private userRepo: UserRepository,
    private emailService: EmailService,
    private passwordHasher: PasswordHasher
  ) {}
  async createUser(data: UserData): Promise<User> {
    if (!data.email || !data.password) throw new Error("invalid");
    const hashedPassword = await this.passwordHasher.hash(data.password);
    const user = await this.userRepo.create({ ...data, password: hashedPassword });
    await this.emailService.sendWelcome(user);
    return user;
  }
}

// Repository: data access only
class UserRepository {
  async create(data: UserData): Promise<User> { /* ... */ }
}
```

**Each class has one concern.** SRP applied at the module level.

**In interviews:** "I separated the controller (HTTP) from the service (business logic) from the repository (data access). Each can be tested and changed independently."

## Other principles worth knowing

### Law of Demeter (Principle of Least Knowledge)

**Rule:** Only talk to your immediate friends.

```typescript
// Violation: "train wreck"
const cityName = user.getAddress().getCity().getName();

// Better: each class exposes only what callers need
const cityName = user.getCityName();
```

### Tell, Don't Ask

**Rule:** Tell objects what to do, don't ask for their state and act on it.

```typescript
// Violation: asking
if (account.balance > amount) {
  account.balance -= amount;
}

// Better: telling
account.withdraw(amount);  // Account knows its own rules
```

### Convention over Configuration

**Rule:** Defaults should be sensible. Don't make users configure everything.

Rails, NestJS, Next.js — they have conventions, you follow them unless you have a reason not to.

### Postel's Law

**Rule:** Be liberal in what you accept, conservative in what you send.

For APIs: accept various input formats, but always return the canonical format. (But also, validate everything — security.)

## When to apply which principle

| Situation | Principle |
|-----------|-----------|
| Same logic in multiple places | DRY (or Rule of Three) |
| Complex code that's hard to follow | KISS |
| Speculative feature for "future need" | YAGNI |
| Two things share most properties | Composition (not inheritance) |
| Function does too much | SRP / Separation of Concerns |
| Class implements unused methods | ISP |
| Code surprises the user | POLA |
| Deep `a.b.c.d` chains | Law of Demeter |
| Branching on object state | Tell, Don't Ask |
| Repeatedly accessing other objects' state | Move behavior to that object |

## Anti-patterns

- **Cargo cult DRY.** Two coincidentally similar pieces of code abstracted into one brittle thing.
- **Cargo cult SOLID.** 20 interfaces for a 200-line app.
- **Cargo cult KISS.** Refusing to add necessary complexity. "We don't need error handling, the user will just retry."
- **Premature optimization (KISS taken to mean "ignore future needs entirely").** Some complexity is justified.
- **Composition for the sake of it.** Sometimes inheritance IS the right tool.
- **YAGNI taken to mean "never think about the future".** Architecture should be flexible where it needs to be.

## In the LLD interview

**Common question:** "Design a parking lot / URL shortener / chess game."

**Senior answer structure:**

1. **Clarify** (3-5 questions)
2. **Identify key entities** (nouns: Car, ParkingSpot, Ticket)
3. **Apply SOLID:**
   - SRP: one class, one job
   - OCP: open for extension (e.g., new vehicle types)
   - LSP: real is-a relationships only
   - ISP: small interfaces
   - DIP: depend on abstractions (e.g., FeeStrategy interface)
4. **Apply other principles:**
   - Composition over inheritance (Vehicle HAS-A Engine, not IS-A Engine)
   - Tell, don't ask (car.park() not car.isAvailable() then park)
   - KISS: don't add complexity that isn't needed
5. **Walk through a use case** showing the design works

## Summary

DRY, KISS, YAGNI, and related principles are the practical counterpart to SOLID. DRY eliminates duplication (but apply the Rule of Three first). KISS keeps code simple and readable. YAGNI prevents premature feature building. Composition over inheritance produces more flexible designs. Together with SOLID, these principles form the foundation of clean code and are tested in every LLD interview.

## Cheat Sheet
```text
DESIGN PRINCIPLES CHEAT SHEET
═══════════════════════════════════════════════════════════════

DRY — Don't Repeat Yourself
  Extract after 3 occurrences (Rule of Three)
  Red flag: copy-pasting code blocks

KISS — Keep It Simple, Stupid
  Default to the simplest solution
  Red flag: 5 abstraction layers for a CRUD endpoint

YAGNI — You Aren't Gonna Need It
  Don't build for hypothetical futures
  Red flag: "What if we need..." before MVP

Composition > Inheritance
  Has-a > Is-a. Prefer composing behaviors.
  Red flag: deep inheritance chains (>2 levels)

POLA — Principle of Least Astonishment
  Code does what its name says
  Red flag: function named "process" that also sends emails

SoC — Separation of Concerns
  Different concerns → different modules
  Red flag: UI logic in database queries

IN INTERVIEWS:
• Apply YAGNI: "I won't add X until we need it"
• Apply KISS: "The simplest approach is..."
• Apply DRY: "I'd extract this into a shared utility"
```

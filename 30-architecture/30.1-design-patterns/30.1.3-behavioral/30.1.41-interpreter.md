# Interpreter Pattern

> **TL;DR:** Interpreter defines a **grammar** for a language and an **interpreter** that evaluates sentences in that language. Use it for small DSLs (config formats, search queries, business rules) where rolling a full parser generator is overkill.

<!-- section: Design Patterns | category: Architecture | subcategory: Behavioral | tags: concept, gof -->

## Definition

The Interpreter pattern is a behavioral design pattern that defines a representation for a language's grammar along with an interpreter that uses the representation to interpret sentences in the language.

It's one of the 23 GoF patterns. The key insight: each grammar rule becomes a class. The AST (built by a parser) is composed of these classes. The interpreter walks the AST and evaluates it.

```text
┌──────────────────────────────────┐
│ AbstractExpression (interface) │
│ + interpret(context): T │
└──────────────────────────────────┘
        ▲ ▲
        │ │
┌──────────────────┐ ┌────────────────────┐
│ TerminalExpr │ │ NonterminalExpr │
│ (e.g., Literal) │ │ (e.g., Add, Sub) │
│ + interpret() │ │ - left, right │
│ │ │ + interpret() │
└──────────────────┘ └────────────────────┘

         Context (state, symbol table)
```

The grammar:
```
expression ::= term ( ('+' | '-') term )*
term ::= factor ( ('*' | '/') factor )*
factor ::= number | '(' expression ')'
```

The class hierarchy:
- `NumberExpression` (terminal)
- `AddExpression` (nonterminal: left + right)
- `SubtractExpression` (nonterminal: left - right)
- `MultiplyExpression`
- `DivideExpression`

## Why Do We Need It?

### Without Interpreter

```typescript
// BAD: hand-rolled parser with hardcoded logic
function evaluate(expr: string): number {
  // recursive descent parser, hardcoded
  // fragile, hard to extend
}
```

**Problems:**
1. **Hard to extend** — adding `^` (exponent) means editing the parser logic
2. **No clear grammar** — the parser is implicit in the code
3. **Hard to test in parts** — the parser is one monolithic function
4. **No AST manipulation** — can't transform, optimize, or analyze

### With Interpreter

```typescript
// GOOD: grammar is explicit, each rule is a class
interface Expression { interpret(): number; }

class Number implements Expression {
  constructor(private value: number) {}
  interpret() { return this.value; }
}

class Add implements Expression {
  constructor(private left: Expression, private right: Expression) {}
  interpret() { return this.left.interpret() + this.right.interpret(); }
}

class Subtract implements Expression {
  constructor(private left: Expression, private right: Expression) {}
  interpret() { return this.left.interpret() - this.right.interpret(); }
}

// Parser turns "1 + 2 - 3" into:
// new Subtract(new Add(new Number(1), new Number(2)), new Number(3))
// Then:
const ast = parser.parse('1 + 2 - 3');
ast.interpret(); // 0
```

Adding `Multiply` is one new class. The grammar is in the class hierarchy.

## How It Works

1. **AbstractExpression** — interface with `interpret(context)`.
2. **TerminalExpression** — represents a literal/variable in the grammar.
3. **NonterminalExpression** — represents a rule (usually holds sub-expressions).
4. **Context** — shared state (symbol table, environment).
5. **Client** — builds the AST (usually via a parser), then calls `interpret()` on the root.

```typescript
// Grammar: expression ::= number (('+' | '-') number)*
// AST: Add(Number(1), Number(2))

interface Expr { interpret(): number; }

class Num implements Expr {
  constructor(private value: number) {}
  interpret() { return this.value; }
}

class Add implements Expr {
  constructor(private l: Expr, private r: Expr) {}
  interpret() { return this.l.interpret() + this.r.interpret(); }
}

// Parser (simple)
function parse(input: string): Expr {
  const tokens = input.split(/\s+/);
  let left = new Num(parseInt(tokens[0]));
  for (let i = 1; i < tokens.length; i += 2) {
    const op = tokens[i];
    const right = new Num(parseInt(tokens[i + 1]));
    left = op === '+' ? new Add(left, right) : new Sub(left, right);
  }
  return left;
}

class Sub implements Expr {
  constructor(private l: Expr, private r: Expr) {}
  interpret() { return this.l.interpret() - this.r.interpret(); }
}

parse('1 + 2 - 3').interpret(); // 0
```

## Real-World Examples

### 1. SQL parsers

SQL grammar (`SELECT ... FROM ... WHERE ...`) is interpreted. Each SQL clause becomes an expression. The interpreter runs the query.

### 2. Regex engines

A regex `^[a-z]+@[a-z]+\.[a-z]+$` is a grammar. The regex engine interprets it against a string.

### 3. Search query languages (Lucene, Elasticsearch DSL)

A query like `name:john AND age:>30` is a small DSL. Each operator (`AND`, `OR`, `>`, `<`) is an expression.

```typescript
interface Query { matches(doc: Document): boolean; }

class TermQuery implements Query {
  constructor(private field: string, private value: string) {}
  matches(doc: Document) { return doc[this.field] === this.value; }
}

class AndQuery implements Query {
  constructor(private left: Query, private right: Query) {}
  matches(doc: Document) { return this.left.matches(doc) && this.right.matches(doc); }
}
```

### 4. Boolean expression evaluators

A `Rule` like `(age > 18 AND country = 'US') OR isAdmin` is a grammar.

### 5. Math expression evaluators

`(1 + 2) * 3` — class hierarchy for `Number`, `+`, `*`, etc.

### 6. Configuration formats (HCL, TOML, custom DSLs)

Tools like Terraform (HCL) and Kubernetes admission policies (Rego) use the Interpreter pattern.

### 7. Workflow / business rules engines

A rule like `IF order.amount > 1000 AND customer.tier = 'gold' THEN approve` is a small DSL.

### 8. Template engines

A template `Hello, {{name}}!` is interpreted — `{{name}}` is a VariableExpression, the surrounding text is literal.

## When to Use

 **Use Interpreter when:**

- The grammar of the language is **simple** (otherwise use a parser generator)
- **Efficiency is not a critical concern** (interpreters are usually slower than compiled parsers)
- You want to express **domain-specific language rules in your code**
- The language is **stable** (you don't need to extend it dynamically)
- You want **easy extensibility** — adding a new rule is adding a new class

 **Avoid Interpreter when:**

- The grammar is **complex** (use a parser generator: PEG.js, ANTLR, nearley.js)
- **Performance matters** (interpreters are slow; compile to bytecode or AST once, then evaluate)
- You only have **2-3 rules** (just write a `switch`)
- The language is **highly dynamic** (rules change at runtime — a parser generator is better)
- The user community expects a **standard parser generator** (don't reinvent the wheel)

## How It Works in Code

### Math expression interpreter

```typescript
interface Expr { interpret(): number; }

class Number implements Expr {
  constructor(private value: number) {}
  interpret() { return this.value; }
}

class Variable implements Expr {
  constructor(private name: string, private env: Map<string, number>) {}
  interpret() { return this.env.get(this.name) || 0; }
}

class Add implements Expr {
  constructor(private left: Expr, private right: Expr) {}
  interpret() { return this.left.interpret() + this.right.interpret(); }
}

class Subtract implements Expr {
  constructor(private left: Expr, private right: Expr) {}
  interpret() { return this.left.interpret() - this.right.interpret(); }
}

class Multiply implements Expr {
  constructor(private left: Expr, private right: Expr) {}
  interpret() { return this.left.interpret() * this.right.interpret(); }
}

// AST for: (x + 5) * 2
const ast = new Multiply(
  new Add(new Variable('x', env), new Number(5)),
  new Number(2),
);

env.set('x', 10);
ast.interpret(); // (10 + 5) * 2 = 30
```

### Boolean expression interpreter

```typescript
interface BoolExpr { interpret(): boolean; }

class Literal implements BoolExpr {
  constructor(private value: boolean) {}
  interpret() { return this.value; }
}

class And implements BoolExpr {
  constructor(private left: BoolExpr, private right: BoolExpr) {}
  interpret() { return this.left.interpret() && this.right.interpret(); }
}

class Or implements BoolExpr {
  constructor(private left: BoolExpr, private right: BoolExpr) {}
  interpret() { return this.left.interpret() || this.right.interpret(); }
}

class Not implements BoolExpr {
  constructor(private expr: BoolExpr) {}
  interpret() { return !this.expr.interpret(); }
}

class GreaterThan implements BoolExpr {
  constructor(private left: number, private right: number) {}
  interpret() { return this.left > this.right; }
}

// Rule: (age > 18 AND country = 'US') OR isAdmin
const rule = new Or(
  new And(
    new GreaterThan(25, 18), // hardcoded values for example
    new Literal(true), // country = 'US'
  ),
  new Literal(true), // isAdmin
);

rule.interpret(); // true
```

### Search query interpreter

```typescript
interface SearchQuery { matches(doc: any): boolean; }

class TermQuery implements SearchQuery {
  constructor(private field: string, private value: string) {}
  matches(doc: any) { return doc[this.field] === this.value; }
}

class RangeQuery implements SearchQuery {
  constructor(private field: string, private min: number, private max: number) {}
  matches(doc: any) {
    const v = doc[this.field];
    return v >= this.min && v <= this.max;
  }
}

class AndQuery implements SearchQuery {
  constructor(private left: SearchQuery, private right: SearchQuery) {}
  matches(doc: any) { return this.left.matches(doc) && this.right.matches(doc); }
}

// Query: name = "john" AND age BETWEEN 18 AND 65
const query = new AndQuery(
  new TermQuery('name', 'john'),
  new RangeQuery('age', 18, 65),
);

query.matches({ name: 'john', age: 30 }); // true
```

## Comparisons

### Interpreter vs Parser Generator

- **Interpreter** is a hand-rolled pattern. You write the grammar in code.
- **Parser generator** (ANTLR, PEG.js, nearley.js) takes a grammar and generates a parser. You write the grammar in a DSL.

For complex grammars, use a parser generator. For simple ones (5-20 rules), hand-rolled is fine.

### Interpreter vs Visitor

- **Visitor** operates on **an existing AST** (built by some parser).
- **Interpreter** defines the **grammar** and the **interpretation**.

In a compiler pipeline: Parser → AST → Visitor walks AST. The Interpreter is the parser; the Visitor is one of the operations on the AST.

### Interpreter vs Strategy

- **Strategy** swaps an algorithm.
- **Interpreter** defines a language and runs sentences in it.

Different intent; not directly comparable.

### Interpreter vs Composite

- **Composite** is the **structure** (tree of expressions).
- **Interpreter** is the **operation** on that structure (evaluating the expression tree).

Interpreter almost always uses Composite — the AST is a Composite tree.

## Code Example: A Small Rules Engine

```typescript
// Business rules: "if order.total > 1000 AND customer.tier = 'gold' then discount = 10%"

interface Rule { evaluate(ctx: Context): boolean; }

class Context {
  constructor(public vars: Record<string, any>) {}
  get(name: string) { return this.vars[name]; }
}

class Comparison implements Rule {
  constructor(private varName: string, private op: '>' | '<' | '==', private value: number) {}
  evaluate(ctx: Context) {
    const v = ctx.get(this.varName);
    return this.op === '>' ? v > this.value : this.op === '<' ? v < this.value : v === this.value;
  }
}

class AndRule implements Rule {
  constructor(private left: Rule, private right: Rule) {}
  evaluate(ctx: Context) { return this.left.evaluate(ctx) && this.right.evaluate(ctx); }
}

class OrRule implements Rule {
  constructor(private left: Rule, private right: Rule) {}
  evaluate(ctx: Context) { return this.left.evaluate(ctx) || this.right.evaluate(ctx); }
}

class NotRule implements Rule {
  constructor(private rule: Rule) {}
  evaluate(ctx: Context) { return !this.rule.evaluate(ctx); }
}

// Build a rule: (order.total > 1000) AND (customer.tier == 'gold')
const goldDiscountRule = new AndRule(
  new Comparison('order.total', '>', 1000),
  new Comparison('customer.tier', '==', 'gold'), // simplified — string comparison
);

// Evaluate
const ctx = new Context({ 'order.total': 1500, 'customer.tier': 'gold' });
goldDiscountRule.evaluate(ctx); // true
```

## Common Pitfalls

### 1. **Performance is bad for complex grammars**

Walking the AST is slow. For repeated evaluation of the same expression, cache the AST or compile to bytecode.

### 2. **Reinventing parser generators**

If your grammar has 30+ rules, you're reinventing ANTLR. Use a parser generator.

### 3. **Untrusted input**

Interpreting untrusted input is a security risk (think SQL injection, eval injection). Sanitize, sandbox, or use a parser with proper error handling.

### 4. **No error reporting**

Hand-rolled interpreters often give poor error messages ("failed at root" instead of "expected `)` at line 3, col 12"). A parser generator handles this for you.

### 5. **Coupling grammar to code**

Adding a new rule means editing code. If the rules change often (user-defined rules), make the grammar itself data-driven.

## Best Practices

1. **Use parser generators for complex grammars** (PEG.js, nearley.js, ANTLR).
2. **Validate input** — interpreters are a security risk with untrusted data.
3. **Cache the AST** for repeated evaluation.
4. **Provide good error messages** — track position in the input.
5. **Document the grammar** — separate doc (BNF/EBNF) from code.
6. **Combine with Visitor** for operations on the AST (typecheck, optimize, compile).

## Summary

Interpreter is the **language-in-code** pattern. It defines a grammar and an evaluator. Use it for small DSLs (search queries, business rules, math expressions) where a parser generator is overkill. For complex grammars, use a real parser generator.

**Interview-ready one-liner:** "Interpreter defines a grammar as a class hierarchy, builds an AST from input, and walks the AST to evaluate the sentence — like a small DSL engine. For complex grammars, use a parser generator instead."

# Saga Pattern

> **TL;DR:** Saga manages **distributed transactions across multiple services** by breaking them into local transactions and **compensating actions**. Each service commits its local transaction independently; if one fails, the prior services run their compensation to undo. Use it when a business transaction spans multiple services and you can't use a single DB transaction.

## Definition

The Saga pattern is an architectural pattern for managing **distributed transactions** across multiple services. A saga is a sequence of **local transactions**; each local transaction updates the data within a single service. If a step fails, the saga executes **compensating transactions** to undo the prior steps.

It addresses the fact that 2-phase commit (XA transactions) doesn't scale across services — and even when it could, it's slow and brittle.

```text
Traditional distributed transaction (2PC):
  ┌─────────────────────────────────────────────┐
  │ Coordinator │
  │ "Everyone prepare? ... Committed." │
  │ (locks all participants until commit) │
  └─────────────────────────────────────────────┘
   Slow, locks resources, doesn't scale

Saga:
  T1 → T2 → T3 → T4 → (success) → Done
   │ │ │
   │ │ └─── fails → C3 (undo T3) → C2 (undo T2) → C1 (undo T1)
   │
   └─── fails → C1 (undo T1)
```

## Why Do We Need It?

### The problem: distributed transactions

Imagine a travel booking system:
1. Reserve a flight
2. Reserve a hotel
3. Charge the credit card

These are 3 different services, each with its own database. If step 1 succeeds but step 2 fails, what happens to the flight reservation?

With a single DB transaction, you could roll back. But across services, you can't.

### Without Saga

```typescript
// BAD: each service commits independently; no rollback if one fails
async function bookTrip(user: User, trip: Trip) {
  await flightService.reserve(trip.flightId); // 1. committed
  await hotelService.reserve(trip.hotelId); // 2. fails (no rooms)
  // Flight is now reserved, but the trip is incomplete!
  // No way to "undo" step 1 from here.
  await paymentService.charge(user.id, trip.total); // never runs
}
```

### With Saga

```typescript
// GOOD: each step has a compensation; failures trigger compensations
async function bookTrip(user: User, trip: Trip) {
  const saga = new Saga();

  saga.step({
    name: 'reserveFlight',
    action: () => flightService.reserve(trip.flightId),
    compensation: () => flightService.cancel(trip.flightId),
  });

  saga.step({
    name: 'reserveHotel',
    action: () => hotelService.reserve(trip.hotelId),
    compensation: () => hotelService.cancel(trip.hotelId),
  });

  saga.step({
    name: 'chargeCard',
    action: () => paymentService.charge(user.id, trip.total),
    compensation: () => paymentService.refund(/* ... */),
  });

  await saga.run();
}
```

If step 2 fails, step 1's compensation runs to release the flight reservation.

## How It Works

1. **Saga** — the orchestrator or chain of local transactions.
2. **Local transaction** (T) — a service's operation that updates its own data.
3. **Compensating transaction** (C) — a service's operation that **semantically undoes** a prior T (e.g., `cancel` undoes `reserve`).

There are two ways to coordinate a saga:

### 1. Orchestration (centralized)

A central orchestrator tells each service what to do next.

```text
            ┌──────────────┐
            │ Orchestrator │
            └──────┬───────┘
                   │ command
       ┌───────────┼───────────┐
       ▼ ▼ ▼
   Service A Service B Service C
       │ │ │
       └─── reply ─┴──── reply ┘
                   │
              Orchestrator
              decides next step
```

```typescript
class TripBookingOrchestrator {
  async bookTrip(user: User, trip: Trip) {
    const compensations: (() => Promise<void>)[] = [];
    try {
      // Step 1
      const flight = await flightService.reserve(trip.flightId);
      compensations.push(() => flightService.cancel(flight.id));

      // Step 2
      const hotel = await hotelService.reserve(trip.hotelId);
      compensations.push(() => hotelService.cancel(hotel.id));

      // Step 3
      await paymentService.charge(user.id, trip.total);
      // No compensation for the last step if it succeeds — but if a step 4 existed, it would
    } catch (err) {
      // Roll back: run compensations in reverse order
      for (const c of compensations.reverse()) {
        await c();
      }
      throw err;
    }
  }
}
```

### 2. Choreography (decentralized)

No central orchestrator. Each service emits events; other services listen and react.

```text
   Service A ── emits ──> Event Bus ──> Service B (listens, reacts)
                                   └──> Service C (listens, reacts)
```

```typescript
// Service A: after flight reservation, emit event
async function reserveFlight(flightId: string) {
  const flight = await db.flights.reserve(flightId);
  await eventBus.emit('flight.reserved', { flightId: flight.id, ...flight });
  return flight;
}

// Service B: listen for flight reserved, then reserve hotel
eventBus.on('flight.reserved', async (event) => {
  try {
    const hotel = await hotelService.reserve(/* ... */);
    await eventBus.emit('hotel.reserved', { ... });
  } catch (err) {
    // Compensate: release the flight
    await flightService.cancel(event.flightId);
    await eventBus.emit('flight.cancelled', { reason: 'hotel_failed' });
  }
});

// Service C: listen for hotel reserved, then charge
eventBus.on('hotel.reserved', async (event) => {
  try {
    await paymentService.charge(/* ... */);
    await eventBus.emit('payment.charged', { ... });
  } catch (err) {
    // Compensate: release hotel and flight
    await hotelService.cancel(/* ... */);
    await flightService.cancel(/* ... */);
  }
});
```

## Comparison: Orchestration vs Choreography

| | Orchestration | Choreography |
|--|---------------|--------------|
| **Coordination** | Central orchestrator | Decentralized (event bus) |
| **Coupling** | Orchestrator knows all services | Services know only the event bus |
| **Visibility** | Easy (orchestrator has the full flow) | Hard (must trace events) |
| **Failure handling** | Centralized (one place for retries, timeouts) | Distributed (each service handles its own) |
| **Best when** | Complex flows, many services | Simple flows, few services |
| **Tools** | NestJS, Camunda, Temporal, AWS Step Functions | Kafka, RabbitMQ, EventBridge |

A rule of thumb: **Orchestration** for complex business processes (4+ steps, conditional flows). **Choreography** for simple reactions (3 or fewer steps, no conditional logic).

## Real-World Examples

### 1. Travel booking (the canonical example)

```
Reserve Flight → Reserve Hotel → Charge Card → Send Confirmation
```

Each step is a separate service. Saga ensures consistency across all 4.

### 2. E-commerce order

```
Reserve Inventory → Charge Payment → Create Shipment → Send Email
```

If payment fails, release inventory. If shipment fails, refund + release inventory.

### 3. Banking transfers

```
Debit Account A → Credit Account B
```

If credit fails, debit must be reversed. (Real banks use 2PC for this, but in a microservices world, Saga is more common.)

### 4. AWS Step Functions / Azure Durable Functions

Cloud orchestrators built for Saga-style workflows. You define the steps + compensations; the runtime handles retries, persistence, and error handling.

### 5. Temporal / Camunda

Workflow engines that manage long-running sagas with built-in persistence, retries, and human-in-the-loop.

### 6. Netflix / Uber

Both use Saga patterns for their core business processes (subscription, ride dispatching, payment).

## When to Use

 **Use Saga when:**

- A business transaction spans **multiple services** with separate databases
- You need **eventual consistency** with **rollback capability**
- 2-phase commit is too slow, doesn't scale, or isn't available
- The business process is **multi-step** with defined compensations
- You can identify **compensating actions** for each step (e.g., cancel undoes reserve, refund undoes charge)

 **Avoid Saga when:**

- A single DB transaction works (use it instead — Saga is for cross-service)
- You can't define compensations (some actions are irreversible — sending a real letter)
- The business logic is simple and fits in one service
- You need strong consistency (Saga is eventually consistent)
- The team isn't ready for the operational complexity (debugging distributed sagas is hard)

## How It Works in Code

### Orchestration with retry and timeout

```typescript
class SagaStep {
  constructor(
    public name: string,
    public action: () => Promise<any>,
    public compensation: (result?: any) => Promise<void>,
    public retries = 3,
    public timeout = 5000,
  ) {}
}

class Saga {
  private steps: SagaStep[] = [];
  private completed: { step: SagaStep; result: any }[] = [];

  step(step: SagaStep) { this.steps.push(step); }

  async run() {
    for (const step of this.steps) {
      try {
        const result = await this.executeWithRetry(step);
        this.completed.push({ step, result });
      } catch (err) {
        await this.compensate();
        throw err;
      }
    }
  }

  private async executeWithRetry(step: SagaStep): Promise<any> {
    for (let attempt = 1; attempt <= step.retries; attempt++) {
      try {
        return await Promise.race([
          step.action(),
          new Promise((_, reject) => setTimeout(() => reject(new Error('timeout')), step.timeout)),
        ]);
      } catch (err) {
        if (attempt === step.retries) throw err;
        await new Promise(r => setTimeout(r, 100 * attempt)); // backoff
      }
    }
  }

  private async compensate() {
    for (const { step, result } of this.completed.reverse()) {
      try {
        await step.compensation(result);
      } catch (err) {
        // Log and continue — best-effort compensation
        console.error(`Compensation for ${step.name} failed`, err);
      }
    }
  }
}
```

### Choreography with a typed event bus

```typescript
type SagaEvent =
  | { type: 'flight.reserved'; flightId: string; tripId: string }
  | { type: 'flight.cancelled'; flightId: string; tripId: string; reason: string }
  | { type: 'hotel.reserved'; hotelId: string; tripId: string }
  | { type: 'hotel.cancelled'; hotelId: string; tripId: string }
  | { type: 'payment.charged'; amount: number; tripId: string }
  | { type: 'payment.refunded'; tripId: string; reason: string }
  | { type: 'trip.booked'; tripId: string };

class SagaCoordinator {
  private state = new Map<string, 'pending' | 'completed' | 'failed'>();

  constructor(private bus: EventBus) {
    this.bus.on('flight.reserved', this.onFlightReserved);
    this.bus.on('hotel.reserved', this.onHotelReserved);
    this.bus.on('payment.charged', this.onPaymentCharged);
  }

  async startTripBooking(tripId: string, flightId: string, hotelId: string) {
    this.state.set(tripId, 'pending');
    await this.bus.emit({ type: 'flight.reserved', flightId, tripId });
  }

  private onFlightReserved = async (event: Extract<SagaEvent, { type: 'flight.reserved' }>) => {
    try {
      await hotelService.reserve(/* ... */);
      await this.bus.emit({ type: 'hotel.reserved', hotelId: '...', tripId: event.tripId });
    } catch (err) {
      await this.bus.emit({ type: 'flight.cancelled', flightId: event.flightId, tripId: event.tripId, reason: 'hotel_failed' });
      this.state.set(event.tripId, 'failed');
    }
  };
  // ... other handlers
}
```

## Comparisons

### Saga vs 2-Phase Commit (XA)

| | 2PC | Saga |
|--|-----|------|
| **Consistency** | Strong (atomic) | Eventual (compensations run async) |
| **Speed** | Slow (locks until all commit) | Fast (no locks) |
| **Failure** | Atomic rollback | Compensating transactions |
| **Scalability** | Poor (locks) | Good (no locks) |
| **Use when** | Same DB, can lock | Distributed, no shared DB |

### Saga vs Process Manager

A Process Manager is a long-running orchestrator that tracks saga state, retries, and timeouts. It's essentially a Saga with persistence.

### Saga vs Event Sourcing

- **Saga** is a **coordination** pattern for multi-step business processes.
- **Event Sourcing** is a **storage** pattern (store events, derive state).

Saga often uses events (via choreography); the saga state can be event-sourced.

### Saga vs Workflow Engine

A workflow engine (Camunda, Temporal, Airflow) is a tool for executing sagas with persistence, retries, and observability. Saga is the pattern; the engine is the implementation.

## Code Example: E-commerce Checkout

```typescript
class CheckoutSaga {
  private compensations: (() => Promise<void>)[] = [];

  async checkout(userId: string, cart: Cart, paymentInfo: PaymentInfo) {
    try {
      // Step 1: Reserve inventory
      const reservation = await inventoryService.reserve(cart.items);
      this.compensations.push(() => inventoryService.release(reservation.id));

      // Step 2: Charge payment
      const charge = await paymentService.charge(paymentInfo, cart.total);
      this.compensations.push(() => paymentService.refund(charge.id));

      // Step 3: Create shipment
      const shipment = await shipmentService.create({ userId, items: cart.items });
      this.compensations.push(() => shipmentService.cancel(shipment.id));

      // Step 4: Send confirmation
      await notificationService.sendOrderConfirmation(userId, shipment);

      return { reservation, charge, shipment };
    } catch (err) {
      // Compensate in reverse order
      for (const c of this.compensations.reverse()) {
        try { await c(); } catch (e) { console.error('Compensation failed', e); }
      }
      throw err;
    }
  }
}
```

## Common Pitfalls

### 1. **Irreversible actions**

Some steps can't be compensated:
- Sending a real letter
- Charging a credit card and shipping physical goods (refund is partial compensation)
- Notifying an external system (e.g., the IRS)

**Mitigation:** design compensations to be "good enough" (refund + apology) or break the saga into smaller pieces.

### 2. **Compensation failures**

If a compensation fails, you're in an inconsistent state. Need:
- Idempotent compensations (safe to retry)
- Manual reconciliation process
- Dead-letter queue for failed compensations
- Alerting

### 3. **Distributed transactions that look atomic**

If two steps need to be atomic (both succeed or both fail), you can't use Saga — you need 2PC or a different design.

### 4. **Eventual consistency leaks**

Users might see partial state during the saga. E.g., they see "flight reserved" but "hotel not yet reserved" for a few seconds. Document and design around this.

### 5. **Saga becomes a god orchestrator**

If the orchestrator knows about every service, it becomes a monolith in the middle. Use choreography for simpler flows.

### 6. **No observability**

Debugging a saga that's stuck mid-way is hard. Add tracing (OpenTelemetry), saga state persistence, and dashboards.

## Best Practices

1. **Make compensations idempotent** — safe to retry.
2. **Add timeouts** — don't wait forever for a step.
3. **Use a workflow engine** for complex sagas (Temporal, Step Functions, Camunda).
4. **Persist saga state** — so you can resume after a crash.
5. **Add tracing** — see which step is running, which failed, where compensations are.
6. **Design for partial failure** — the system must handle "step 3 done, step 4 not yet" gracefully.
7. **Document eventual consistency** — make sure users and downstream services know.
8. **Test failure paths** — most sagas look fine in the happy path; the failures are where bugs hide.

## Summary

Saga is the **distributed transaction pattern** for microservices. It replaces 2PC with a sequence of local transactions + compensations. It trades strong consistency for scalability and speed. Use it when a business process spans multiple services and you can't use a single DB transaction. Use a workflow engine for complex sagas.

**Interview-ready one-liner:** "Saga manages distributed transactions by breaking them into local transactions and compensating actions — if step 3 fails, steps 1 and 2 run their compensations to undo. Use it when a business process spans multiple services."

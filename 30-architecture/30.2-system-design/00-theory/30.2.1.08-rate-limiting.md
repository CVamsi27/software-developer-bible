# Rate Limiting

> **Protect your service from being overwhelmed.** Whether by malicious actors, buggy clients, or sudden traffic spikes. Every public API needs rate limiting. Every "how do you handle 100x traffic" question ends with rate limiting somewhere.

## TL;DR

- **Rate limit** = cap the number of requests per unit time.
- **By what:** per user, per IP, per API key, per endpoint, globally.
- **Algorithms:** fixed window, sliding window, token bucket, leaky bucket.
- **Where to enforce:** API gateway, application, edge (CDN).
- **When exceeded:** reject (429), queue, throttle, degrade.
- **In interviews: name the algorithm, the limit, the key (user/IP/etc.), what happens on limit.**

---

## Why it matters

Without rate limiting:
- One bad client can take down your service
- A bug can cause infinite retry loops
- A DDoS attack works
- You can't enforce paid tiers ("Pro users get 10K requests/hour")

With rate limiting:
- Predictable load
- Fair access
- Paid tier enforcement
- DDoS mitigation (partial)

## The 4 Algorithms

### 1. Fixed Window

**Algorithm:** Count requests in fixed time windows. Reset at the window boundary.

```
Window 1 (00:00 - 00:59): 100 requests allowed
Window 2 (01:00 - 01:59): 100 requests allowed
```

**Pros:** Simple, easy to implement (just an integer counter).

**Cons:** **Burst at window boundary.** A user can do 100 requests in the last second of window 1 and 100 in the first second of window 2 = 200 in 2 seconds.

**When to use:** Low-stakes APIs, simple cases.

### 2. Sliding Window

**Algorithm:** Count requests in a sliding window (last 60 seconds, not aligned to clock).

**Implementation 1: Sliding log**
- Store every request timestamp
- Count those in the last 60s
- Memory-intensive (one entry per request)

**Implementation 2: Sliding window counter (hybrid)**
- Track count in current window and previous window
- Estimate sliding count using weighted average
- Approximate, less memory

```
current_window_count = 80
previous_window_count = 100
elapsed_in_current_window = 30s (out of 60s)

sliding_count = previous_window_count * (1 - 30/60) + current_window_count
             = 100 * 0.5 + 80
             = 50 + 80
             = 130
```

**Pros:** Avoids the boundary burst problem.

**Cons:** More complex, slight inaccuracy.

**When to use:** Default choice. Most production systems.

### 3. Token Bucket

**Algorithm:** A bucket holds N tokens. Each request consumes 1 token. Tokens refill at rate R per second. If no tokens, reject.

```
Bucket capacity: 100 tokens
Refill rate: 10 tokens/sec

t=0: bucket has 100 tokens
t=0: request → bucket has 99 tokens
...
t=10: bucket has 100 tokens (refilled from 90 to 100, capped)
```

**Pros:**
- Allows bursts (up to bucket capacity)
- Smooth refill
- Simple to implement

**Cons:** Need to track token count per key.

**When to use:** APIs that should allow occasional bursts. Most common choice.

**Used by:** AWS, Stripe, GitHub.

### 4. Leaky Bucket

**Algorithm:** Requests enter a queue (the bucket). They're processed at a fixed rate. If queue is full, reject.

```
Queue capacity: 100
Process rate: 10 req/sec

Requests come in → enqueue (up to 100)
Process loop: dequeue + process at 10/sec
If queue is full → reject new requests
```

**Pros:** Smooth output rate (no bursts).

**Cons:** Doesn't allow bursts. Less flexible than token bucket.

**When to use:** When you need strict rate smoothing. Less common than token bucket.

## Comparison

| Algorithm | Allows bursts? | Memory | Complexity | Best for |
|-----------|---------------|--------|------------|----------|
| Fixed window | Yes (boundary) | Low | Very low | Low-stakes APIs |
| Sliding window | Some | Medium | Medium | Default choice |
| Token bucket | Yes (up to capacity) | Low | Medium | Most APIs |
| Leaky bucket | No | Low | Medium | Strict rate smoothing |

**In interviews:** Default to **token bucket** unless you have a specific reason. Mention sliding window as the alternative.

## Rate Limit Keys

What you limit BY:

| Key | Use case | Pros | Cons |
|-----|----------|------|------|
| **IP** | Public APIs, anonymous traffic | Easy (no auth needed) | NAT/CGNAT means many users share an IP |
| **User ID** | Authenticated APIs | Fair per user | Need to be authenticated |
| **API key** | B2B APIs | Tracks partner usage | Partners share one key for many users |
| **Tenant ID** | B2B SaaS | Fair per tenant | One tenant can have many users |
| **Endpoint** | Protect specific expensive endpoints | Limits resource use | Doesn't limit per user |
| **Composite** (user + endpoint) | Most production systems | Granular | More state to track |

**In production:** Stack keys. e.g., "100 req/sec per user" AND "10000 req/sec per tenant" AND "1000 req/sec on /search endpoint globally."

## Where to Enforce

| Layer | Pros | Cons |
|-------|------|------|
| **Edge (CDN, WAF)** | Stops bad traffic before it hits your service | Doesn't see user-level context |
| **API Gateway** | Centralized policy, sees all traffic | One more thing to maintain |
| **Application** | Full context, can vary by business logic | Per-app logic, harder to enforce globally |
| **Database / service** | Last line of defense | Too late, already wasted compute |

**Best:** API gateway for global limits, application for per-user/per-endpoint. Defense in depth.

---

## What to Return When Limited

- **HTTP 429 Too Many Requests** — standard
- **Retry-After header** — when the client can try again
- **X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset headers** — for clients to track their usage

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 60
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1640995200

{
  "error": "rate_limited",
  "message": "Too many requests. Try again in 60 seconds."
}
```

## Distributed Rate Limiting

In a multi-server setup, each server can't have its own counter (a user could hit 100 on server A and 100 on server B = 200 total).

**Solutions:**

### 1. Centralized store (Redis)

All servers share a Redis counter. Increment on each request. Check against limit.

```
Server A: INCR rate:user:123 → 1
Server B: INCR rate:user:123 → 2
...
```

**Pros:** Accurate, simple.
**Cons:** Redis becomes a dependency, network call adds latency.

### 2. Sliding window in Redis with Lua

Atomic check-and-increment in Redis (single round trip).

```lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local current = redis.call('INCR', key)
if current == 1 then
  redis.call('EXPIRE', key, window)
end
if current > limit then
  return 0  -- denied
end
return 1  -- allowed
```

### 3. Token bucket in Redis

Same idea, but with refill logic.

### 4. Approximate (sliding window counter in memory)

Each server has a partial view. Approximate, but no Redis dependency.

## Common Patterns

### 1. Free tier limit

```
Free: 1000 requests/day per API key
Pro: 100,000 requests/day per API key
```

### 2. Per-endpoint protection

```
GET /search: 10 req/sec per user (expensive)
GET /user/profile: 100 req/sec per user (cheap)
POST /login: 5 req/min per IP (security)
```

### 3. Tiered limits

```
Per user: 100 req/min
Per tenant: 10,000 req/min
Global: 1,000,000 req/min
```

### 4. Burst + sustained

```
Burst: 1000 requests in 1 second (token bucket)
Sustained: 100 req/sec average
```

## Anti-patterns

- **Rate limiting AFTER doing the work.** The whole point is to skip the work.
- **In-memory only in a multi-server setup.** Counts don't add up correctly.
- **No retry-after.** Client retries immediately, hits limit again, infinite loop.
- **Hard-coding limits in 10 places.** Centralize the config.
- **No monitoring.** You need to see when limits are hit (is it a bug? an attack? growth?).
- **Rate limiting only the API.** Don't forget the auth endpoint (brute force), the password reset (email spam), the export (data exfil).
- **Aggressive limits for paying customers.** 429 to a Pro user = churn.

## When to discuss in interviews

| Scenario | Rate limit | Why |
|----------|-----------|-----|
| Public API | Per API key, 1000/hour | Prevent abuse |
| Login endpoint | Per IP, 5/minute | Prevent brute force |
| Search endpoint | Per user, 10/minute | Expensive query |
| Webhook receiver | Per source, 1000/minute | Don't let one source overwhelm |
| File upload | Per user, 100/hour | Storage cost |
| Password reset | Per email, 3/day | Prevent email spam |
| SMS sending | Per user, 10/day | Cost |

## Summary

Rate limiting protects systems from overload by controlling the rate of requests. Algorithms include token bucket (flexible burst), sliding window (accurate), fixed window (simple), and leaky bucket (smooth). Distributed rate limiting uses Redis + Lua. Return 429 with Retry-After header. In interviews, name the algorithm, the key, the limit, and what happens on limit.

## Cheat Sheet
```text
RATE LIMITING CHEAT SHEET
═══════════════════════════════════════════════════════════════

ALGORITHMS:
• Token Bucket — tokens refill at fixed rate, burst allowed
• Sliding Window — count requests in rolling window
• Fixed Window — count in fixed time period
• Leaky Bucket — smooth output rate

DISTRIBUTED:
• Redis + Lua for atomic operations
• Key: user_id, IP, API key, endpoint
• Window: per-second, per-minute, per-hour

RESPONSE:
• 429 Too Many Requests
• Retry-After header (seconds)
• X-RateLimit-Limit, X-RateLimit-Remaining

STRATEGIES:
• Per-user limits (fairness)
• Per-endpoint limits (protect expensive ops)
• Global limits (protect infrastructure)
• Adaptive (adjust based on load)

• Name the key (user, IP, endpoint)
```

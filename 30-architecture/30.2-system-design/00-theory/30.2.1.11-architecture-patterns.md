# Architecture Patterns — Monolith, Microservices, Event-Driven, Hexagonal

> **4 architecture patterns you need to know.** Every system design discussion touches one of these. Know the trade-offs. Know when to use which. Know what "modular monolith" means.

## TL;DR

- **Monolith** — one deployable unit. Simple, fast to start, gets messy at scale.
- **Modular Monolith** — monolith with strong module boundaries. Best of both worlds (often).
- **Microservices** — many small services. Scales teams, distributed complexity.
- **Event-Driven** — services communicate via events. Loose coupling, async.
- **Layered** — UI → Service → Repository → DB. Classic. Can become a "big ball of mud."
- **Hexagonal (Ports & Adapters)** — domain at center, adapters at edges. Testable, swappable.
- **Clean Architecture** — entities, use cases, interface adapters, frameworks. Uncle Bob's take.
- **Microkernel (Plugin)** — core + plugins. IDEs, Eclipse, browsers.

---

## Why it matters

Every "how would you architect this" question has an implicit assumption about which pattern. The interviewer wants to hear:

- "I chose modular monolith because we have 5 engineers and one team — microservices would slow us down"
- "We moved to microservices when we hit 30 engineers and the monolith deploy was taking 2 hours"
- "We use event-driven for cross-service workflows, but request-response for synchronous operations"

The senior signal: name the pattern, justify the choice, know the trade-offs.

## 1. Monolith

**Definition:** One deployable unit. All code in one process. One database.

```
┌─────────────────────────────┐
│       Monolith App          │
│  ┌─────────┐  ┌─────────┐  │
│  │   UI    │  │  API    │  │
│  └─────────┘  └─────────┘  │
│  ┌─────────┐  ┌─────────┐  │
│  │ Service │  │  Data   │  │
│  └─────────┘  └─────────┘  │
└─────────────────────────────┘
            │
            ▼
       ┌────────┐
       │   DB   │
       └────────┘
```

**Pros:**
- Simple. One codebase, one deploy, one process.
- Fast to start. No service boundaries to think about.
- Easy debugging. One process, one log.
- Easy transactions. Single DB.
- Easy refactoring. Find usages across the whole codebase.

**Cons:**
- **All changes require a full deploy.** Can't deploy the UI without the API.
- **One team blocks another.** 50 engineers trying to merge into one codebase.
- **Scaling is all-or-nothing.** Can't scale just the search service.
- **Tech stack lock-in.** All in one language/framework.
- **Becomes a "big ball of mud"** over time without discipline.

**When to use:**
- Small team (< 10 engineers)
- Early-stage product (PMF still being figured out)
- Simple domain (no clear service boundaries)
- Tight coupling is natural (e.g., a single business process)

**Used by:** Most early-stage startups. Shopify (still on Rails monolith, but modular). GitHub. Basecamp. Stack Overflow.

## 2. Modular Monolith

**Definition:** A monolith with strict module boundaries. Each module is independent internally, but they all deploy together.

```
┌─────────────────────────────────────────┐
│           Monolith (one deploy)         │
│                                         │
│  ┌──────────┐  ┌──────────┐  ┌──────┐  │
│  │  Orders  │  │  Users   │  │  Auth│  │
│  │  Module  │  │  Module  │  │ Mod  │  │
│  └──────────┘  └──────────┘  └──────┘  │
│       │              │           │      │
│       └──── internal APIs ─────────┘     │
│                                         │
└─────────────────────────────────────────┘
            │
            ▼
       ┌────────┐
       │   DB   │
       └────────┘
```

**Module rules:**
- Each module has its own folder, namespace, or package
- Modules can ONLY communicate through public APIs (not direct DB access)
- Each module has its own DB schema/tables (no cross-module queries)
- Modules can be extracted into microservices later if needed

**Pros:**
- Same simplicity as monolith
- Forces good architecture (boundaries are enforced)
- Can be split into microservices later (if needed)
- Single deploy, single transaction, simple debugging

**Cons:**
- Still one deploy (can't scale individual modules)
- Discipline required (someone will reach across module boundaries)
- Can't use different tech stacks per module

**When to use:**
- Medium team (10-50 engineers)
- Clear domain boundaries exist
- Microservices feel premature
- Most teams should START here

**Used by:** Shopify (Rails Engines), many large Rails/Django/Next.js apps, parts of GitHub.

**In interviews:** "We went with a modular monolith. Each module has its own folder, internal API, and DB schema. We can split into microservices if a module needs independent scaling."

## 3. Microservices

**Definition:** Many small services. Each service owns its data, deploys independently, communicates via network.

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│  Order   │  │  User    │  │  Auth    │
│ Service  │  │ Service  │  │ Service  │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │
     ▼             ▼             ▼
┌─────────┐  ┌─────────┐  ┌─────────┐
│ Order DB│  │ User DB │  │ Auth DB │
└─────────┘  └─────────┘  └─────────┘
     │             │             │
     └─────── message bus ───────┘
```

**Pros:**
- **Independent deploys.** Each service can ship on its own schedule.
- **Independent scaling.** Scale the order service 10x without scaling the user service.
- **Team autonomy.** Each team owns a service end-to-end.
- **Tech stack flexibility.** Python for ML, Go for performance, Node for the API.
- **Failure isolation.** One service crash doesn't take down the whole system.

**Cons:**
- **Distributed systems complexity.** Network failures, partial failures, eventual consistency.
- **Operational overhead.** Each service needs CI/CD, monitoring, logging, deploys.
- **Data consistency.** No ACID across services. Need saga, eventual consistency.
- **Latency.** Network calls add 1-10ms each.
- **Debugging is hard.** A request touches 5 services. Trace it across all of them.
- **Cost.** More services = more infrastructure = more $.

**When to use:**
- Large team (50+ engineers) where teams need independence
- Different scaling needs per service
- Need for independent deploys (CD at scale)
- Domain boundaries are clear and stable

**When NOT to use:**
- Small team (< 10 engineers). Operational overhead will kill you.
- Unclear domain. You don't know what the right service boundaries are.
- Tight coupling between components. Network will be the bottleneck.

**Used by:** Amazon, Netflix, Uber, Airbnb, Spotify. But also: many teams have moved back from microservices to monolith after the operational pain.

**In interviews:** "We have 60 engineers across 5 teams. We went microservices because each team needed to deploy independently. We have a service mesh (Istio) for cross-cutting concerns."

## 4. Event-Driven Architecture (EDA)

**Definition:** Services communicate by emitting and consuming events. Asynchronous. Loose coupling.

```
┌─────────┐                  ┌─────────┐
│ Order   │ ── order_created →│ Inventory│
│ Service │                  │ Service │
└─────────┘                  └─────────┘
     │                             │
     │ event:                      │ event:
     │ payment_processed           │ stock_reserved
     ▼                             ▼
┌─────────┐                  ┌─────────┐
│ Payment │                  │Shipping │
│ Service │                  │ Service │
└─────────┘                  └─────────┘
```

**Pros:**
- **Loose coupling.** Producers don't know consumers. Add a new consumer without changing producers.
- **Async.** Producer doesn't wait for consumer.
- **Resilience.** If a consumer is down, the event is queued.
- **Audit trail.** Events can be stored forever (event sourcing).
- **Multiple consumers.** Same event can drive multiple workflows.

**Cons:**
- **Eventual consistency.** Hard to reason about. Hard to debug.
- **No synchronous request-response.** Some flows need sync (user waits for confirmation).
- **Schema management.** Event schemas evolve. Backward compatibility is hard.
- **Eventual ordering.** Order of events matters but isn't guaranteed.
- **Testing is hard.** Async flows are harder to test than sync.

**When to use:**
- Cross-service workflows (saga)
- Event broadcasting (notify multiple systems)
- Audit trail / event sourcing needed
- Workflows that take minutes to days (order processing, claims)

**Used by:** LinkedIn (Kafka), Uber, most microservices at scale.

**In interviews:** "We use event-driven for cross-service workflows. Order service emits `order_created`, inventory consumes and reserves, payment consumes and charges, all async. If any step fails, we run compensating actions in reverse (saga)."

**See also:** [Queues And Async](30.2.1.06-queues-and-async.md), [../../2-Backend-Stack/12-Microservices/03-Saga-Pattern.md](../../../20-backend/20.6-microservices/20.6.03-saga-pattern.md), [../../2-Backend-Stack/12-Microservices/07-Event-Sourcing.md](../../../20-backend/20.6-microservices/20.6.07-event-sourcing.md)

## 5. Layered Architecture

**Definition:** Strict layers, each only depending on the one below. Classic "N-tier" architecture.

```
┌─────────────────┐
│ Presentation    │  ← UI, controllers, API endpoints
├─────────────────┤
│ Business Logic  │  ← Services, domain logic
├─────────────────┤
│ Data Access     │  ← Repositories, DAOs
├─────────────────┤
│ Database        │  ← Postgres, MySQL, etc.
└─────────────────┘
```

**Pros:**
- Familiar. Most frameworks enforce this.
- Clear separation.
- Easy to test each layer independently.

**Cons:**
- **Anemic domain model.** Business logic often ends up in services, not in domain objects.
- **Layers leak.** Lower layers often know about higher ones.
- **Becomes a procedural mess** if not careful.

**When to use:** Simple CRUD apps, when the domain isn't complex.

**In interviews:** Mostly used as a default for simple systems. Mention the limitation: "We have a layered architecture, but we made sure the business logic is in the domain layer, not just in services."

## 6. Hexagonal Architecture (Ports & Adapters)

**Definition:** The domain is at the center. Outside adapters (UI, DB, external APIs) connect to the domain through "ports" (interfaces).

```
            ┌─────────────────────────────┐
            │      Outside World          │
            │  ┌──────┐  ┌─────────────┐  │
            │  │  UI  │  │  Database   │  │
            │  └──────┘  └─────────────┘  │
            │       │            │         │
            │  ┌────▼────┐  ┌────▼────┐    │
            │  │  Port   │  │  Port   │    │
            │  └────┬────┘  └────┬────┘    │
            └──────┼────────────┼─────────┘
                   │            │
            ┌──────▼────────────▼─────────┐
            │        Domain (core)         │
            │   - Entities                 │
            │   - Use cases                │
            │   - Business rules           │
            └──────────────────────────────┘
```

**Key idea:** The domain doesn't know about the UI, DB, or external APIs. It defines ports (interfaces), and adapters implement them.

**Pros:**
- **Testable.** Mock the adapters, test the domain.
- **Swappable.** Switch from Postgres to MongoDB by changing the adapter.
- **Independent of frameworks.** Domain is pure business logic.
- **Clear boundaries.** Domain is the heart, everything else is replaceable.

**Cons:**
- **More files.** Each port has an interface + adapter.
- **Over-engineering for simple apps.**
- **Indirection.** You have to follow the layers to understand what's happening.

**When to use:**
- Complex business logic (the domain is the hard part)
- Long-lived systems (the adapters change, the domain doesn't)
- You want to test the domain without DB/UI

**Used by:** Many fintech, insurance, healthcare apps where the domain is the value.

**In interviews:** "We use hexagonal architecture. The domain layer has no dependencies on frameworks. The DB and UI are adapters that implement ports defined by the domain."

## 7. Clean Architecture (Uncle Bob)

**Similar to hexagonal.** Four layers:

```
┌──────────────────────────────────────┐
│  Frameworks & Drivers (outermost)   │  ← Web, DB, UI, external
├──────────────────────────────────────┤
│  Interface Adapters                 │  ← Controllers, gateways, presenters
├──────────────────────────────────────┤
│  Use Cases (Application Business)   │  ← Application-specific business rules
├──────────────────────────────────────┤
│  Entities (Enterprise Business)     │  ← Domain, business rules
└──────────────────────────────────────┘
```

**Dependency rule:** Source code dependencies point only inward. Inner layers know nothing about outer layers.

**vs Hexagonal:** Very similar. Clean Architecture is more prescriptive about the layer names. Hexagonal emphasizes "ports and adapters" terminology.

**In interviews:** Use whichever you're more familiar with. Both demonstrate the same idea: domain at the center, adapters at the edges.

## 8. Microkernel (Plugin) Architecture

**Definition:** A small core system. Plugins add features. Core and plugins communicate through well-defined APIs.

```
┌──────────────────────────┐
│       Core System         │
│  - Plugin manager         │
│  - Plugin API             │
│  - Shared services        │
└──────────────────────────┘
       │           │           │
       ▼           ▼           ▼
┌────────┐  ┌────────┐  ┌────────┐
│Plugin 1│  │Plugin 2│  │Plugin 3│
│  (X)   │  │  (Y)   │  │  (Z)   │
└────────┘  └────────┘  └────────┘
```

**Pros:**
- Extensibility without changing the core
- Plugins can be added/removed at runtime
- Clear separation between platform and features

**Cons:**
- Plugin API design is hard (you can't predict all future plugins)
- Plugins might conflict with each other
- Versioning nightmare (which plugin versions are compatible with which core?)

**When to use:**
- Platform that supports many features (IDEs, browsers, CMSs)
- Third-party extensibility is a goal
- Clear plugin API can be designed upfront

**Used by:** Eclipse, IntelliJ IDEA, Chrome, Firefox, VS Code, WordPress, Jenkins.

**In interviews:** "We have a microkernel architecture. The core handles auth, routing, and the plugin lifecycle. Each feature is a separate plugin that registers itself with the core."

## Comparison

| Pattern | Team size | Domain complexity | When to use |
|---------|-----------|-------------------|-------------|
| **Monolith** | < 10 | Simple | Starting out, prototype |
| **Modular Monolith** | 10-50 | Medium | Most teams should be here |
| **Microservices** | 50+ | Complex, clear boundaries | Scale teams, scale services |
| **Event-Driven** | Any with async needs | Workflows | Cross-service workflows, audit |
| **Layered** | Any | Simple CRUD | Default for simple systems |
| **Hexagonal** | Any | Complex domain | Domain is the hard part |
| **Clean** | Any | Complex domain | Same as hexagonal |
| **Microkernel** | Any | Platform | Plugin-style extensibility |

| Interviewer asks... | You say... |
|---------------------|------------|
| "How would you architect this?" | "I'd start with a modular monolith. We can split into microservices when the team grows and clear service boundaries emerge." |

| "How do services communicate?" | "Synchronous for queries (REST/gRPC). Asynchronous for workflows (Kafka events)." |
| "What's the domain layer?" | "Hexagonal architecture. The domain has no dependencies on frameworks. Adapters implement ports defined by the domain." |
| "How do you scale?" | "Horizontal scaling of the bottleneck service. Sharding the database. Caching. Async queues for slow operations." |

## Migration paths

### Monolith → Modular Monolith

- Add module boundaries
- Extract shared code into libraries
- Enforce module dependencies with build tools
- Time: weeks to months

### Modular Monolith → Microservices

- Pick the most independent module
- Extract it: own codebase, own DB, own deploy
- Add an API gateway or message bus for communication
- Repeat for other modules
- Time: months to years

### Monolith → Microservices (skip modular)

- Risky. Hard to know the right service boundaries without trying them.
- Usually ends in a "distributed monolith" (worst of both).
- Modular monolith first is the recommended path.

---

## Anti-patterns

- **Distributed monolith.** Microservices that are tightly coupled. Network calls everywhere. No independent deploys possible.
- **Microservices for a 5-person team.** Operational overhead kills velocity.
- **Premature event-driven.** Sync is often fine. Don't add Kafka for one workflow.
- **Anemic domain model.** All logic in services, domain is just data.
- **Big ball of mud.** No structure, just a mess. Refactor to modular monolith first.
- **Layered violation.** Controller talks directly to DB. Service layer skipped.
- **Microkernel without API design.** Plugins can't be built because the API keeps changing.

## When to bring up in system design

| Topic | Mention |
|-------|---------|
| New system, small team | Monolith (or modular monolith) |
| High scale, large team | Microservices |
| Cross-service workflows | Event-driven + saga |
| Complex domain | Hexagonal / Clean |
| Plugin-style extensibility | Microkernel |
| Real-time data pipelines | Event-driven (Kafka) |
| Audit trail / event sourcing | Event-driven + event sourcing |

## Summary

Architecture patterns provide proven solutions to common design problems. Layered (MVC) for simple CRUD, hexagonal/clean for complex domains, event-driven for async workflows, microkernel for platforms, CQRS for read/write optimization. The right pattern depends on complexity, team size, and scalability needs. In interviews, name the pattern, justify the choice, know the trade-offs.

## Cheat Sheet
```text
ARCHITECTURE PATTERNS CHEAT SHEET
═══════════════════════════════════════════════════════════════

LAYERED (MVC/MVVM):
• UI → Service → Repository → DB
• Simple, familiar, easy to test
• Use: CRUD apps, simple domains

HEXAGONAL (Ports & Adapters):
• Domain at center, adapters at edges
• Easy to swap DB, API, UI
• Use: complex domains, long-lived systems

EVENT-DRIVEN:
• Events trigger handlers async
• Loose coupling, audit trail
• Use: cross-service workflows, notifications

CQRS:
• Separate read and write models
• Optimize each independently
• Use: complex queries, analytics, event sourcing

MICROKERNEL:
• Core + plugins
• Extensible without modifying core
• Use: platforms, IDEs, CMS

IN INTERVIEWS:
• Name the pattern
• Justify based on requirements
• Know the trade-offs
• Suggest migration path if pattern changes
```

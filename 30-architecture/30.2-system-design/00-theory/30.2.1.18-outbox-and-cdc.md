# Outbox Pattern & Change Data Capture (CDC)

> **How do you publish a Kafka event for every database write — atomically, without two-phase commit, and without losing messages if the broker is down?** Two answers: the **Outbox pattern** (your service writes the event to a database table in the same transaction as the business write) and **Change Data Capture / CDC** (an external reader tails the database's transaction log and publishes everything to a broker). Together they are the production solution to the "dual-write problem" — and the most-cited reason real microservices eventually get their data flows right.

## TL;DR

- **Dual-write problem** — writing to a database *and* publishing to a message broker can't be atomic across two systems. One of the two will eventually fail and the other will succeed, leaving the system inconsistent.
- **Outbox pattern** — your service writes the event to an `outbox` table in the **same DB transaction** as the business write. A separate **relay** process reads the outbox and publishes to the broker. At-least-once, no message loss, no "phantom events" for failed business writes.
- **CDC (Change Data Capture)** — instead of an app-level outbox, a **log-based** reader (Debezium, Maxwell, Datastax CDC) tails the database's **write-ahead log (WAL)** / binlog / commit log and emits every row change as a message. Zero app code, decouples DB from event design.
- **Trade-off matrix** — Outbox = simpler, but extra table + relay; CDC = zero app changes, but requires a Debezium-class operator and a log you can tail (Postgres WAL, MySQL binlog, MongoDB oplog, Cassandra commitlog).
- **In interviews: name the dual-write problem, pick a pattern, name the failure mode, name the delivery guarantee.**

---

## Why it matters

The "obvious" approach is broken:

```typescript
// The dual-write trap. Looks atomic. Is not.
async function createOrder(order: Order) {
  await db.insertOrder(order); // (1) DB write
  await kafka.send("orders.created", order); // (2) Broker write
}
```

If the process crashes between (1) and (2), the order exists in the database but no `orders.created` event was published. Downstream services (inventory, payment, fulfillment) never hear about it. The "fix" — wrapping both in a transaction — doesn't work because Kafka is not a transaction-capable resource the database knows about. **X/Open XA across DB + broker is technically possible but kills throughput** and most production stacks disable it.

A second, more insidious problem: if the broker publishes but the DB transaction later rolls back (network blip, constraint violation, optimistic-lock conflict), you've published a phantom event for a write that never happened. Downstream services now think the order exists when it doesn't.

**The two correct production patterns solve this by funneling the event through the same atomic boundary as the business write** — either by writing it to the same database (outbox) or by reading the database's own atomic write log (CDC).

## How they work

### 1. Outbox Pattern

```text
SERVICE PROCESS DATABASE RELAY PROCESS KAFKA
───────────────── ──────── ────────────── ─────
  BEGIN TX
    INSERT INTO orders ... orders table updated
    INSERT INTO outbox ... outbox table updated
  COMMIT TX ──── atomic ────>
                                                                 poll outbox / LISTEN
                                                                 publish to Kafka
                                                                 mark dispatched
```

**The outbox table** (one per service / aggregate root):

```sql
CREATE TABLE outbox (
  id BIGSERIAL PRIMARY KEY,
  aggregate_id TEXT NOT NULL, -- e.g. order_id
  event_type TEXT NOT NULL, -- e.g. "order.created"
  payload JSONB NOT NULL, -- serialized event body
  headers JSONB, -- trace id, schema version, etc.
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  dispatched_at TIMESTAMPTZ -- NULL until the relay publishes
);

CREATE INDEX outbox_pending_idx ON outbox (created_at) WHERE dispatched_at IS NULL;
```

**The producer** (your service code):

```typescript
async function createOrder(order: Order) {
  // Same transaction — atomic by definition.
  await db.tx(async (tx) => {
    await tx.insert(orders).values(order);
    await tx.insert(outbox).values({
      aggregateId: order.id,
      eventType: "order.created",
      payload: order,
      headers: { traceId: trace.id(), schemaVersion: 1 },
    });
  });
  // No direct Kafka call. The relay does the publish.
}
```

**The relay** (a separate worker; in production often a library like Debezium Outbox Connector, Outboxkit, or a custom one):

```typescript
// Polling relay (simplest). For 10K+ events/sec, use LISTEN/NOTIFY or
// transaction-log-based CDC instead of polling.
async function relayOutbox() {
  while (true) {
    const batch = await db
      .select()
      .from(outbox)
      .where(isNull(outbox.dispatchedAt))
      .orderBy(outbox.createdAt)
      .limit(100);

    for (const evt of batch) {
      await kafka.send({
        topic: `orders.${evt.eventType}`,
        key: evt.aggregateId, // partition by aggregate for ordering
        value: evt.payload,
        headers: { "x-event-type": evt.eventType, ...evt.headers },
      });
      await db.update(outbox)
        .set({ dispatchedAt: new Date() })
        .where(eq(outbox.id, evt.id));
    }
    await sleep(50); // backoff
  }
}
```

**Properties:**

| Property | Value |
|----------|-------|
| Atomicity | Business write + event are one DB transaction |
| Delivery | **At-least-once** (relay may publish then crash before marking dispatched → consumer must be idempotent) |
| Ordering | Per-aggregate_id, **only if the relay partitions by aggregate_id**. Polling in `created_at` order across all rows mixes ordering. |
| Coupling | Producer couples to outbox table; relay is generic |
| Operational cost | One table, one worker. Trivial to operate. |
| Throughput | Limited by the relay's poll + publish loop. Postgres LISTEN/NOTIFY or `SKIP LOCKED` is much better than naive polling. |
| Backpressure | The outbox table grows. Monitor depth. Drain or slow the producer if it explodes. |

**Failure modes:**

| Failure | Outcome |
|---------|---------|
| Service crashes after `BEGIN` but before `COMMIT` | Nothing published. Correct. |
| Service crashes after `COMMIT` but before the relay picks it up | Event still published, just delayed. |
| Relay crashes after Kafka publish but before marking dispatched | Event published **twice** (next loop re-publishes). Consumers must be **idempotent** (use event id + dedup window). |
| Kafka is down for an hour | Outbox table grows. Producer keeps writing. Once Kafka is back, relay drains. |
| Outbox table is huge (millions of pending rows) | The `WHERE dispatched_at IS NULL ORDER BY created_at` becomes slow. Mitigate with partial index + `SKIP LOCKED` + multiple relay workers. |

### 2. Change Data Capture (CDC) — log-based

CDC reads the **database's own transaction log** (WAL in Postgres, binlog in MySQL, oplog in MongoDB, commitlog in Cassandra) and turns every committed row change into a message.

```text
DATABASE CDC CONNECTOR MESSAGE BROKER
───────── ────────────── ──────────────
  orders table Debezium Kafka topic
  │ (reads WAL) │
  ▼ │ ▼
INSERT/UPDATE/DELETE → tail -f of binlog → JSON event per row change
```

**Key idea:** the database has *already* solved the atomic-write problem — every change is durably logged before commit. CDC just hooks that log and ships it.

**Debezium** is the canonical implementation. It runs as a Kafka Connect source connector:

```json
{
  "name": "orders-postgres-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "orders-db",
    "database.port": "5432",
    "database.dbname": "orders",
    "table.include.list": "public.orders",
    "plugin.name": "pgoutput",
    "publication.autocreate.mode": "filtered",
    "topic.prefix": "cdc"
  }
}
```

Each row change becomes a Kafka message:

```json
{
  "before": null,
  "after": { "id": "ord_42", "status": "CREATED", "total": 99.00 },
  "op": "c", // c=create, u=update, d=delete, r=read(snapshot)
  "ts_ms": 1737158400000,
  "source": { "db": "orders", "table": "orders", "lsn": "0/1A2B3C4" }
}
```

**Properties:**

| Property | Value |
|----------|-------|
| Atomicity | Inherited from the DB's commit log — if a transaction commits, the events exist; if it rolls back, no event |
| Delivery | **At-least-once** (consumer-side idempotency still required) |
| Ordering | Per-transaction, then per-row. Same as commit order. |
| Coupling | **Zero app code** — no outbox table, no `INSERT INTO outbox` in your business transaction |
| Operational cost | One CDC connector per database. Requires `REPLICATION` privileges on Postgres. Adds a read replica. |
| Throughput | Very high. CDC reads the log, not the table. Postgres logical decoding can saturate NIC. |
| Schema evolution | Debezium publishes schema-change events to a separate topic. Avro / Protobuf schema registry recommended. |
| Cold start | On a brand-new connector, do an **initial snapshot** first, then switch to streaming. |

**Failure modes:**

| Failure | Outcome |
|---------|---------|
| Database crashes mid-transaction | Log entry never committed → no CDC event. Correct. |
| Debezium crashes mid-stream | On restart, resumes from last checkpoint in the log. May replay some events. |
| Kafka unavailable | Debezium buffers to local disk; replays when Kafka is back. |
| Long-running transaction holds WAL | CDC falls behind. Postgres `pg_replication_slots` will fill, then block writes. **Always set `wal_keep_size` and monitor replication lag.** |
| Schema change (ALTER TABLE) | CDC may stop, re-snapshot, or silently drop columns depending on config. Test schema changes against CDC. |

## Outbox vs CDC — when to use which

| Dimension | Outbox | CDC |
|-----------|--------|-----|
| **App code change** | Yes — `INSERT INTO outbox` in every business transaction | None — DB-side only |
| **Operational complexity** | Low — one table, one relay | High — connector, schema registry, log retention |
| **Granularity** | Per business event (you control the shape) | Per row (you derive the event from row state) |
| **Multiple tables per event** | Yes — easy to emit one event covering 3 tables | Hard — need to correlate across topics / use transactional outbox of CDC events |
| **Sensitive data** | You can pre-filter / hash PII in the outbox row | The whole row hits the broker; mask at source |
| **Cross-DB aggregation** | Each service owns its outbox | One connector per DB; cross-DB events need a downstream joiner |
| **Throughput ceiling** | Limited by relay | Limited by WAL bandwidth |
| **Order guarantees** | Per aggregate if you partition the relay | Per row in commit order |
| **Cost** | 1× outbox row per business event | 1× CDC event per row change (often more, due to noisy updates) |
| **Good fit** | Per-service business events, small-to-medium scale, ops-light teams | Many services reading the same DB, large scale, ops-heavy teams that already run Kafka Connect |

**A hybrid pattern is common and good:** use CDC for the "broadcast every change" use cases (search index, analytics, audit log), and use the outbox for the "I control the event shape and need exactly-once-ish semantics" use cases (saga orchestration, billing, notifications). The same DB, two readers, different consumers.

## Code Examples

### Outbox: full producer + relay (Postgres + Kafka, TypeScript)

```typescript
import { Kafka } from "kafkajs";
import { Client } from "pg";
import { trace } from "@opentelemetry/api";

// ── Producer (in your business service) ───────────────────────────────────
export async function createOrder(db: Client, order: Order) {
  await db.query("BEGIN");
  try {
    await db.query(
      "INSERT INTO orders (id, user_id, total, status) VALUES ($1, $2, $3, $4)",
      [order.id, order.userId, order.total, "CREATED"],
    );
    await db.query(
      `INSERT INTO outbox (aggregate_id, event_type, payload, headers)
       VALUES ($1, $2, $3, $4)`,
      [
        order.id,
        "order.created",
        JSON.stringify(order),
        JSON.stringify({ traceId: trace.getActiveSpan()?.spanContext().traceId }),
      ],
    );
    await db.query("COMMIT");
  } catch (err) {
    await db.query("ROLLBACK");
    throw err;
  }
}

// ── Relay: SKIP LOCKED + LISTEN/NOTIFY (production-grade) ────────────────
const kafka = new Kafka({ brokers: [process.env.KAFKA!] });
const producer = kafka.producer();

export async function relayLoop(db: Client) {
  await producer.connect();

  // Push notification when new rows arrive
  await db.query("LISTEN outbox_new");

  db.on("notification", () => {
    /* wake the loop */
  });

  while (true) {
    // SKIP LOCKED: many relay workers can run in parallel without conflict
    const { rows } = await db.query(`
      SELECT id, aggregate_id, event_type, payload, headers
      FROM outbox
      WHERE dispatched_at IS NULL
      ORDER BY created_at
      LIMIT 100
      FOR UPDATE SKIP LOCKED
    `);

    if (rows.length === 0) {
      await new Promise((r) => setTimeout(r, 1000));
      continue;
    }

    for (const row of rows) {
      await producer.send({
        topic: `orders.${row.event_type}`,
        messages: [
          {
            key: row.aggregate_id,
            value: row.payload,
            headers: { "x-event-type": row.event_type, ...JSON.parse(row.headers ?? "{}") },
          },
        ],
      });
      await db.query("UPDATE outbox SET dispatched_at = now() WHERE id = $1", [row.id]);
    }
  }
}

// ── Outbox table trigger to wake the relay immediately ───────────────────
/*
  CREATE OR REPLACE FUNCTION notify_outbox() RETURNS TRIGGER AS $$
  BEGIN
    PERFORM pg_notify('outbox_new', NEW.id::text);
    RETURN NEW;
  END;
  $$ LANGUAGE plpgsql;

  CREATE TRIGGER outbox_notify AFTER INSERT ON outbox
    FOR EACH ROW EXECUTE FUNCTION notify_outbox();
*/
```

### CDC: Debezium + Kafka Connect + downstream service

```bash
# Register the Postgres CDC connector
curl -X POST http://kafka-connect:8083/connectors \
  -H "Content-Type: application/json" \
  -d @cdc-orders.json
```

```typescript
// Downstream service: inventory reads the CDC stream
const consumer = kafka.consumer({ groupId: "inventory" });
await consumer.connect();
await consumer.subscribe({ topic: "cdc.public.orders", fromBeginning: false });

await consumer.run({
  eachMessage: async ({ message }) => {
    const change = JSON.parse(message.value!.toString());
    if (change.op === "c" || change.op === "u") {
      // Debezium has a "new image" by default; for old+new, set
      // `value.converter.schemas.enable=false` and `key.converter=...`
      await inventory.reserve(change.after.id, change.after.items);
    } else if (change.op === "d") {
      await inventory.release(change.before.id);
    }
  },
});
```

### A hybrid: outbox via CDC (best of both)

```sql
-- 1. Service writes to outbox in the same transaction (no Kafka call)
-- 2. Debezium CDC connector watches the outbox table ONLY
-- 3. CDC publishes to Kafka
-- → no app-level relay
-- → no app coupling to outbox shape (CDC serializes the whole row)
-- → ordering + at-least-once from CDC
```

This is the "transactional outbox via CDC" pattern. The outbox table is your business contract; CDC is just a transport. Powers Order Management at most large companies.

## Common Mistakes

- **Skipping the idempotency requirement.** Both outbox and CDC deliver at-least-once. Consumers that assume exactly-once will double-charge, double-fulfill, or double-reserve. Always set a `seen_event_ids` window on the consumer.
- **Polling the outbox with no `SKIP LOCKED`.** Two relay workers will publish the same event twice. Use `SELECT ... FOR UPDATE SKIP LOCKED` or partition the relay by aggregate_id.
- **Forgetting the backpressure plan.** If Kafka is down for 4 hours, the outbox table grows 4 hours' worth. The relay's `WHERE dispatched_at IS NULL` query gets slow. Add a partial index, alert on `pending_count > N`, and have a "drain mode" that temporarily stops accepting new business writes.
- **Using CDC for events you need to control the shape of.** CDC emits row changes, not business events. "Order shipped" is a *transition* across multiple row updates; CDC will publish each row change, not the transition. For state machines, use the outbox.
- **Exposing PII via CDC.** Every column in the table goes to Kafka. Mask PII at the source (hash, redact, or column-filter in Debezium).
- **Forgetting snapshot semantics.** When you first attach Debezium, do you want the current table contents? New events only? Set `snapshot.mode` correctly — `initial` (default), `initial_only`, `never`, `when_needed`, `schema_only`.
- **Not handling schema evolution.** Adding a NOT NULL column without DEFAULT will break the connector. Always use the **expand-and-contract** migration pattern: add nullable, backfill, then add NOT NULL.
- **Trying to do "exactly once" with two systems.** Kafka transactions + idempotent producer give you exactly-once into Kafka, but you still need idempotent consumers. End-to-end exactly-once across DB+Kafka+consumer is a marketing claim, not a free property.
- **Treating outbox as an event bus.** The outbox is a *queue inside the database*, not a public event catalog. Consumers should subscribe to the Kafka topic, not the outbox table.
- **Polling the outbox on a hot loop.** 1ms polling will load the DB. Use `LISTEN/NOTIFY` or poll at 50-200ms with batched reads.

## Best Practices

1. **Always emit event ID and aggregate ID.** `id` for dedup, `aggregate_id` for partitioning. Consumers need both.
2. **Partition the Kafka topic by aggregate_id.** Guarantees per-aggregate ordering. Out-of-order events between aggregates is fine.
3. **Add a trace ID header.** Wire it to the consumer's processing span. End-to-end tracing across the event is the killer feature.
4. **Run the relay in at least 2 replicas.** Single relay = single point of failure. With `SKIP LOCKED`, you can run N replicas in parallel and they'll never double-publish.
5. **Set up partial indexes and alert on outbox depth.** `pg_stat_user_tables` shows live row counts; pair with a Prometheus alert at > 10K pending.
6. **For CDC, use a separate replication slot per consumer.** Don't share one Debezium connector across 50 services — one schema change will break all 50.
7. **Version the event schema.** Use a registry (Confluent Schema Registry, Apicurio). The `headers["x-schema-version"]` field in outbox is the simplest way.
8. **Make events immutable.** Don't mutate the outbox table after publish. If you need to redact, send a follow-up `order.redacted` event.
9. **Test with chaos.** Kill the relay mid-publish. Kill Kafka. Restart the DB. Use Toxiproxy. Your dual-write is only as good as your failure tests.
10. **Document the delivery guarantee.** "At-least-once, consumer must be idempotent" is one sentence that saves every downstream team a week of debugging.

## Performance Considerations

| Concern | Outbox | CDC |
|---------|--------|-----|
| Latency to broker | 50-1000 ms (poll interval or LISTEN/NOTIFY wake) | 100-500 ms (Debezium commit + flush) |
| Throughput ceiling | ~10K-50K events/sec (one DB) | ~100K+ events/sec (per CDC slot) |
| DB cost | One INSERT per event (negligible if same tx) | Replication slot + WAL retention (can balloon disk) |
| Storage | Outbox rows; purges after `dispatched_at + 7 days` | WAL retention; bounded by `wal_keep_size` or replication slot size |
| Backpressure | Outbox table grows → alert + throttle producer | WAL slot grows → DB writes block → ALL writes fail. Set up `max_slot_wal_keep_size`. |
| Horizontal scale | N relay workers, each with `SKIP LOCKED` | N Debezium workers (one per partition); careful with shared offsets |
| Cold start | Replay from `WHERE dispatched_at IS NULL` (slow if huge) | Snapshot mode: full table read then switch to streaming |

## Summary

- **Outbox** = write the event to a database table in the same transaction as the business write. A relay process publishes from outbox to the broker. Simple, well-understood, ops-light. At-least-once. Requires `SKIP LOCKED` and idempotent consumers.
- **CDC** = let a log-based reader (Debezium) tail the database's own write-ahead log. Zero app code. Operationally heavier. Excellent throughput. Same at-least-once guarantee.
- **Hybrid (transactional outbox via CDC)** = business service writes to outbox table, Debezium reads the outbox table only, publishes to Kafka. Best of both, but two moving parts.
- **In interviews: name the dual-write problem, pick outbox OR CDC, name the delivery guarantee, and say "consumers must be idempotent."** That's the senior signal.

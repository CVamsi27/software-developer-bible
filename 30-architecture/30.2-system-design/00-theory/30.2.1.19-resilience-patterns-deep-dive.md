# Resilience Patterns Deep-Dive: Hedging, Load Shedding, Request Coalescing, Deadlines

> **The 5-9s conversation always comes back to the same question: what do you do when the dependency is slow?** Circuit breakers answer "what if it's down". Rate limiting answers "what if there are too many requests". But the senior-level questions are: **what if it's slow**, **what if the same request is in flight 1000 times**, **what if the upstream takes the whole deadline and leaves no time for the rest of the chain**, and **what if the load exceeds what we can do anything useful with**. This file covers the four techniques that get you from "the system works on the happy path" to "the system works when AWS us-east-1 has a bad day": request hedging, adaptive concurrency / load shedding, request coalescing (singleflight), and deadline propagation. Plus the connections between them.

## TL;DR

- **Request hedging** — when a request is taking longer than `p95` of that endpoint, fire a second copy to a different replica. First response wins, second is cancelled. Cuts long-tail latency at the cost of duplicate work. The "tied requests" pattern.
- **Load shedding** — when the system is at capacity, **reject new requests early with a fast 503** rather than letting them queue and time out. Two flavors: **coordinated** (an admission controller, e.g. Envoy, Nginx) and **random early detection (RED)**. Failure mode: over-shed and lose revenue; under-shed and melt the server.
- **Request coalescing (singleflight)** — when N concurrent requests for the **same key** arrive, only the first one calls the dependency. The other N-1 wait on the result. Used for "thundering herd against cache miss". Go's `singleflight`, Node's `p-memoize` / `node:worker_threads`, Redis `SETNX` lock.
- **Deadline propagation** — the parent request has a deadline (e.g. 500ms). Every downstream call must receive a **fraction** of that remaining budget. This stops the "all calls took 4.9s" pathology where every service eats the full timeout.
- **Adaptive concurrency limits** (covered briefly) — the in-process version: cap in-flight requests to the smallest of `replicas * capacity_per_replica` or what the system is currently healthy enough to handle. Coined by Netflix (Concurrency-limits library) and the Envoy `adaptive_concurrency` filter.
- **In interviews: pick the technique, name the metric it improves (p99, error rate, throughput), and say what it costs (duplicate work, lost requests, added complexity).**

---

## Why it matters

The textbook answers (caching, queues, replicas) get you to 99.9%. The 99.99% and beyond come from these patterns, because **the long tail dominates the user experience**:

- A service that is fast 99% of the time but slow 1% of the time will see ~7% of users hit the slow path per session (probability of ≥1 slow request in 7 calls = 1 − 0.99⁷ ≈ 0.068).
- An SLO of "p99 < 200ms" means 1% of requests can be slow — but if those 1% cluster around specific shards or specific user actions, the user experience is broken even though the metric is "green".
- A service that handles 10× normal load by queueing will run out of memory and die. **Shedding load at the front door is the only way to stay up.**

These patterns are the reason Google, Meta, Netflix, and Cloudflare stay online when their dependencies don't. If you can't talk about them, your senior system-design interview will be capped at "junior-mid".

## 1. Request Hedging (Tied Requests)

### Definition

When a request is taking longer than a threshold (typically the **p95 or p99** of that endpoint), fire a **second copy** of the same request to a different replica. The first response wins; the second is cancelled. Also called "tied requests" or "speculative execution at the RPC layer".

### Why it works

Long-tail latency is almost always caused by a **single slow server** in the pool: a noisy neighbor, a GC pause, a disk stall, a partial network degradation. **The other replicas are fast.** Hedging bets on this. The expected second response time is much smaller than the first (which is at the p99 tail), so the user's observed latency is dominated by the faster of the two.

### Math (for the interview)

Without hedging:
- p50 = 50 ms, p99 = 500 ms (10× spread — typical for a backend with a slow tail)

With hedging at the p95 threshold (say 100 ms):
- 95% of requests: no second request, latency = original.
- 5% of requests: second request fires. The second replica has a *fresh* tail distribution (independent), so its expected completion ≈ p50 of the second replica ≈ 50 ms. Combined observed latency ≈ 50 ms.

So **p99 drops from 500 ms to ~50 ms** at the cost of **5% extra work**. The "duplicate work" budget is bounded by `1 / (1 − threshold_quantile)`.

### Code Example

```typescript
// Generic "hedged call" — first response wins.
export async function hedgedCall<T>(
  primary: () => Promise<T>,
  hedge: () => Promise<T>,
  delayMs: number,
  timeoutMs: number,
): Promise<T> {
  let hedgeTimer: NodeJS.Timeout | null = null;
  let settled = false;

  const settle = (result: { ok: true; value: T } | { ok: false; error: unknown }) => {
    if (settled) return;
    settled = true;
    if (hedgeTimer) clearTimeout(hedgeTimer);
    if (result.ok) return result.value as T;
    throw result.error;
  };

  return await new Promise<T>((resolve, reject) => {
    const primaryPromise = primary()
      .then((v) => settle({ ok: true, value: v }))
      .catch((e) => settle({ ok: false, error: e }));

    hedgeTimer = setTimeout(() => {
      hedge()
        .then((v) => settle({ ok: true, value: v }))
        .catch((e) => settle({ ok: false, error: e }));
    }, delayMs);

    setTimeout(() => settle({ ok: false, error: new Error("hedged-call timeout") }), timeoutMs);
  });
}

// Usage: read user profile from the user-service. p99 is 800ms, so hedge at 300ms.
const profile = await hedgedCall(
  () => fetch("http://user-svc/profile/" + id, { signal: controller.signal }),
  () => fetch("http://user-svc-replica-b/profile/" + id, { signal: controller.signal }),
  300, // hedge delay
  2000, // hard ceiling
);
```

### Production Reality

- **Use a *different* replica, not the same one.** A noisy-neighbor or partition issue affects the same shard; hedging within the shard doesn't help. Use **load-balancer-side hedging** (Envoy's `hedging_policy`).
- **Don't hedge idempotent writes.** Two `POST /orders` may double-create. Hedge only GET / safe / read-only calls, or include an idempotency key and dedupe server-side.
- **Be careful with rate limits and billing.** Hedging multiplies outbound traffic by `1 + hedge_probability`. If you have an upstream rate limit, factor this in.
- **Cost of hedge is small only if downstream is cheap.** Hedging a `POST /charge-credit-card` is a 2× billing cost. Hedge reads only.

### When to use
- **Read-heavy services with a long tail** — search, recommendations, profile lookups, autocomplete.
- **Cross-region replication** — read from primary, hedge against the read-replica region.

### When NOT to use
- **Writes / mutations / non-idempotent calls** — double-charge is worse than slow.
- **Very expensive operations** — doubling ML inference or DB join cost is too much.
- **Upstream with hard rate limits** — your hedge breaches them.

## 2. Load Shedding (Drop at the Door)

### Definition

When the system is at capacity, **reject new requests early with a fast 503 / 429** rather than letting them queue. The key insight: **better to fail fast than to fail slow** (which is a cascading failure that takes down the whole system).

### Why it works

The textbook M/M/1 queue: as utilization → 100%, **queue length and latency → ∞**. At 70% utilization you're already seeing 3× the latency. At 90% you're in tail-amplification territory. Letting requests queue past saturation doesn't make them succeed — it makes them time out, and the user retries, making things worse.

Shedding breaks the vicious cycle. Failed-fast requests retry with backoff (or don't), the system stays responsive for the load it CAN handle, and recovery is faster.

### Two flavors

**1. Coordinated admission control (e.g. Envoy, Nginx, AWS ALB):**
- Compute `current_load / capacity` (CPU, queue depth, in-flight count).
- If above threshold, reject with `503` or `429` and a `Retry-After` header.
- Decision is **synchronous, fast, in front of the work**.

**2. Random Early Detection (RED):**
- Don't wait for overload. Start dropping probabilistically as load grows.
- At 50% load: 0% drop. At 80% load: 5% drop. At 100% load: 50% drop.
- This keeps average latency low by avoiding the queue cliff.

### Code Example (coordinated, with overload detection)

```typescript
// Per-process admission control with RED-style probabilistic shedding.
class AdmissionController {
  private inflight = 0;
  private capacity: number;
  private shedProb: number;

  constructor(capacity: number) {
    this.capacity = capacity;
  }

  /** Returns true if request can proceed, false if it should be shed. */
  tryAdmit(): boolean {
    if (this.inflight < this.capacity * 0.7) {
      this.inflight++;
      return true;
    }
    // Above 70% — start shedding probabilistically.
    // At 100% capacity, shed with probability proportional to (load - 0.7) / 0.3.
    const overload = (this.inflight - this.capacity * 0.7) / (this.capacity * 0.3);
    if (Math.random() < overload) {
      return false; // shed
    }
    this.inflight++;
    return true;
  }

  release(): void {
    this.inflight--;
  }
}

// Middleware:
app.use((req, res, next) => {
  if (!admission.tryAdmit()) {
    res.set("Retry-After", "1");
    res.status(503).json({ error: "overloaded", retryAfterMs: 1000 });
    return;
  }
  res.on("finish", () => admission.release());
  res.on("close", () => admission.release());
  next();
});
```

### Production Reality

- **Always send `Retry-After`** on the 503/429. Otherwise the client retries immediately and makes things worse.
- **Pick the right signal.** CPU is laggy (5s update). In-flight count is instant. Queue depth is also instant. **Prefer signals that lead the problem, not lag it.**
- **Differentiate by request cost.** Don't shed a cheap `GET /health` the same way you shed an expensive `POST /report`. Use **cost-aware admission control** — heavy requests count as 5 in-flight, light ones as 1.
- **Shed in priority order.** Sheds `bulk` traffic before `interactive` traffic. `feature X` before `core product`. Use a request header or route to signal priority.
- **Make it observable.** Every shed should emit a metric: `sheds_total{reason,route}`. Otherwise you'll never know if you're over-shedding.

### When to use
- **Always.** Every public-facing service should have a load-shedding policy. The question is only the threshold and the priority.
- **DDoS protection** — same mechanism, different threshold.

### When NOT to use
- **Hard real-time systems** that can't tolerate any dropped request (medical, aviation). Even then, you'd shed, not crash.

## 3. Request Coalescing (Singleflight)

### Definition

When N concurrent requests for the **same key** arrive, only the first one calls the dependency. The other N-1 **wait on the result** of the first. The dependency sees 1 call, not N.

### Why it matters: the thundering herd / cache stampede

Classic scenario: a popular key expires from cache at `t=0`. 1000 concurrent requests all miss, all hit the database simultaneously. The DB melts.

```text
t=0     key "user:42" expires from cache
t=0+    1000 concurrent requests all miss
t=0+    1000 simultaneous SELECT * FROM users WHERE id = 42
        → DB connection pool exhausted
        → p99 spikes from 10ms to 30 seconds
        → every other request to that DB also slows down
```

With coalescing: 1 request hits the DB, the other 999 await its result. **One DB call, 1000 fast responses.**

### Code Example

```typescript
// Node.js: use p-memoize or a singleflight library
import pMemoize from "p-memoize";

const fetchUser = async (id: string) => {
  // simulate slow DB
  await new Promise((r) => setTimeout(r, 100));
  return { id, name: "alice" };
};

const memoizedFetchUser = pMemoize(fetchUser, {
  // 1000 concurrent calls for id="42" within 100ms = 1 actual call
  cache: new Map(),
  maxAge: 60_000,
});

await Promise.all(
  Array.from({ length: 1000 }, () => memoizedFetchUser("42")),
);
// → 1 DB call, all 1000 see the same result.
```

For the **lock-based** version (more control, used in Go's `singleflight` and in databases):

```typescript
// TypeScript port of Go's singleflight pattern
class Singleflight<T> {
  private inflight = new Map<string, Promise<T>>();

  do(key: string, fn: () => Promise<T>): Promise<T> {
    const existing = this.inflight.get(key);
    if (existing) return existing;

    const promise = fn().finally(() => this.inflight.delete(key));
    this.inflight.set(key, promise);
    return promise;
  }
}

const sf = new Singleflight<User>();

async function getUser(id: string) {
  return sf.do(`user:${id}`, async () => {
    return db.users.findUnique({ where: { id } });
  });
}
```

### Production Reality

- **Cancel-on-leader pattern**: if the leader request is cancelled (client disconnects), the followers also lose their result. Most implementations don't propagate cancellation. For critical paths, add a "minimum 1 second" floor.
- **Error propagation**: if the leader fails, all followers see the same error. That's usually correct. To "retry individually", use a different pattern.
- **Lock vs. lock-free**: The simplest version uses a distributed lock (Redis `SETNX` + expiry). The downside is lock-acquisition latency. The advanced version uses **request-dedup at the load balancer** (Envoy's `single_flight` per-route).
- **Memory pressure**: every in-flight call holds state. Bound the in-flight map (LRU eviction of stale keys).

### When to use
- **Cache miss / stampede** — the textbook case.
- **Idempotent lookups** with high duplication — e.g. fetching the same config / feature flag / geo-IP lookup.
- **Single-writer pattern** — coalesce writes too, e.g. "set key, but only if not already in flight".

### When NOT to use
- **Per-request keys that don't repeat** — no coalescing to do, just overhead.
- **Slow operations that block too many followers** — the first request might take 10s; 999 followers wait 10s. Bound the wait with a timeout.

## 4. Deadline Propagation (Stop the Cascade)

### Definition

When a parent request has a deadline (e.g. 500ms), every downstream call must receive a **fraction** of the **remaining budget**, not the full timeout. The downstream's deadline is the parent's deadline minus the time elapsed so far.

### Why it matters: the timeout cascade

The classic pathology:

```text
t=0     API gateway receives request, sets timeout = 5s
t=0+10  API handler calls user-svc with timeout = 5s (bug: should be 4.99s)
t=0+50  user-svc calls auth-svc with timeout = 5s (bug: should be 4.95s)
t=0+100 auth-svc calls billing-svc with timeout = 5s (bug: should be 4.9s)
...
t=4.95  billing-svc finally responds
t=4.99  user-svc responds
t=5.00  API gateway times out and returns 504

User's request took 5s. They saw a timeout. The whole chain executed
needlessly. The deep call was the actual bottleneck, but we couldn't
tell because every layer had the full timeout.
```

With deadline propagation:

```text
t=0     API gateway sets deadline = 500ms
t=10    API handler calls user-svc with deadline = 490ms
t=50    user-svc calls auth-svc with deadline = 440ms
t=100   auth-svc calls billing-svc with deadline = 350ms
        billing-svc is slow → times out at t=450 (350ms after t=100)
        auth-svc returns DEADLINE_EXCEEDED to user-svc at t=450
        user-svc has 40ms left → returns fast-fail response
t=460   API handler returns cached fallback
t=500   API gateway has 40ms of slack; returns the fallback to user.

User's request took 460ms. They saw a graceful degraded response,
not a 504. The deep call was the bottleneck, and we cut the chain
when it was clear it wouldn't fit.
```

### Code Example (gRPC has first-class support)

```typescript
// gRPC client — pass the deadline as a Date or duration.
const client = new UserServiceClient(target);
const deadline = new Date(Date.now() + parentRemainingMs);
const user = await client.getUser({ id }, { deadline });
```

```typescript
// Generic HTTP fetch — use AbortController with a timeout.
async function fetchWithDeadline(url: string, remainingMs: number) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), remainingMs);
  try {
    const res = await fetch(url, { signal: controller.signal });
    return await res.json();
  } finally {
    clearTimeout(timer);
  }
}

// At the call site, pass the budget, not the full timeout.
const childBudget = parentDeadline - Date.now() - 20; // 20ms self-overhead
const result = await fetchWithDeadline(url, childBudget);
```

### Production Reality

- **Pass it as a value, not a flag.** A boolean "is_critical" is not a deadline. Use `deadline: Date` (gRPC) or `remaining_ms: number` (HTTP).
- **Set the deadline on the FIRST byte, not the request.** `Connection: keep-alive` and TCP handshakes eat into the budget. Account for them.
- **Make it observable.** Every span should record its remaining-budget-on-entry. You'll see a histogram of "how much time did this hop have to work with" — a powerful debugging tool.
- **Reserves are good.** Don't use 100% of the budget for the call. Reserve 10-20% for serialization, retries, and the response trip.
- **gRPC has it built in.** HTTP/REST: you're on your own. Pick a deadline-propagation lib (e.g. `async_hooks`-based) or hand-roll it.

### When to use
- **Always.** Every multi-hop call should propagate a deadline. The only exception is background jobs with no user-facing deadline.

### When NOT to use
- **Background jobs / batch / cron** — they have a wall-clock SLA, not a request deadline.
- **One-call-only systems** — no propagation needed.

## 5. Adaptive Concurrency Limits (Bonus)

### Definition

An in-process limit on in-flight requests that **adapts** to the system's current health, rather than a static limit. The classic example: Netflix's **Concurrency-Limits** library, which uses Little's Law + gradient-descent to find the concurrency limit that minimizes latency.

### Why it matters

A static limit (e.g. "max 200 in-flight per process") is wrong when:
- The downstream is fast → 200 is too low, you're leaving capacity on the table.
- The downstream is slow → 200 is too high, you're queuing and dying.
- A new release made the service slower → 200 is now too high.

An adaptive limit:
1. Measures `rtt_min` (the fastest observed RTT — your best-case latency).
2. Computes `rtt_current` (smoothed recent RTT).
3. If `rtt_current > rtt_min`, the system is queueing. **Reduce** the limit.
4. If `rtt_current ≈ rtt_min`, the system has headroom. **Increase** the limit.
5. Run a gradient-descent on the limit value.

The result: the limit hugs the knee of the latency-vs-concurrency curve automatically.

### When to use
- **Services that talk to many heterogenous downstreams** (e.g. an API gateway, a BFF).
- **When static limits require constant manual tuning.**

### When NOT to use
- **Pure CPU-bound work** where concurrency = cores + 1 is sufficient.
- **When you already have a load balancer doing this** (Envoy's `adaptive_concurrency` filter).

## Comparison: When to Use Which

| Pattern | Solves | Cost | Latency impact |
|---------|--------|------|----------------|
| **Hedging** | Long-tail p99 | 5-10% duplicate work | **p99 → ~p50** |
| **Load shedding** | Cascading failure under overload | Lost requests (5-30%) | **None for accepted; fast-fail for shed** |
| **Coalescing** | Thundering herd / cache stampede | Lock latency, follower wait | **Reduces p99 for the herd** |
| **Deadline propagation** | Timeout cascade / wasted work | Slightly more code | **Stops the slow-path tail from getting worse** |
| **Adaptive concurrency** | Static limit tuning | Library complexity, metric collection | **Hugs the knee of the latency curve** |

**They are not mutually exclusive.** A senior system has all four:

- API gateway: load shedding at the front door.
- API handler: coalesces `getUser(id)` lookups.
- Each downstream call: deadline propagation + hedging on reads.

## Common Mistakes

- **Hedging writes** — the duplicate "POST /orders" creates two orders. Always include an idempotency key.
- **Hedging to the same replica** — the noisy neighbor is on the same box. Hedge to a different replica. Configure your LB to do this.
- **Shedding without `Retry-After`** — clients retry immediately, making things worse.
- **Shedding based on CPU only** — CPU lags reality. Use **in-flight count** or **queue depth** as the leading signal.
- **Coalescing with no timeout on followers** — 1000 followers wait 30s for a slow leader. Set a max wait (e.g. 100ms) and fall through to the dependency.
- **Setting deadline = full timeout on every call** — the cascade pathology. Always pass remaining budget.
- **Forgetting to reserve overhead** — using 100% of the budget for the call leaves 0 for the response. Reserve 10-20%.
- **Not testing with chaos** — these patterns look great in code review and break under real failure. Use Toxiproxy to inject 500ms latency. Test what happens when a replica dies during a hedge.
- **Stacking patterns that fight each other** — coalescing + aggressive retry + shedding can oscillate. Add a circuit breaker to break the loop.
- **Treating p99 as the only metric** — p99.9, p99.99, and **request-stuck count** matter more for user-perceived latency. Use HDR histograms (HdrHistogram, t-digest).

## Best Practices

1. **Hedge on reads, never on writes.** Always. No exceptions.
2. **Hedge to a different replica** (LB-enforced), with a 95th-percentile delay.
3. **Shed with a budget.** Decide the maximum % of requests you'll shed (e.g. 5%) and tune the threshold to hit that. Alert when shed rate > budget.
4. **Send `Retry-After` and `Connection: close`** on shed responses. Avoids thundering herd.
5. **Coalesce at the closest level to the dependency.** Coalescing in your service is good; coalescing at the LB is better (Envoy single_flight).
6. **Always propagate deadlines.** Use gRPC's deadline, or a `deadline_ms` HTTP header convention.
7. **Instrument everything.** Metrics: `hedges_total`, `sheds_total{reason}`, `coalesced_total`, `deadline_remaining_ms` (histogram). Logs: every shed / hedge with trace id and remaining budget.
8. **Test with chaos.** Toxiproxy + a 5% packet loss + 500ms latency on the dependency. Does your hedge fire? Does your shed kick in? Does your coalesce work? Does your deadline propagate?
9. **Document the trade-off.** "We shed 5% of traffic at peak. The 5% see a 503 with `Retry-After`. They retry in 1s, succeed." This is one sentence; write it down.
10. **Add a circuit breaker between the layers.** Hedges on a failed dependency just multiply the failure. Breaker first, then hedge.

## Performance Considerations

| Pattern | Throughput cost | Latency cost | Memory cost | Operational cost |
|---------|-----------------|--------------|-------------|------------------|
| Hedging | +5-10% outbound traffic | None for fast path; +delay_ms for tail | Negligible | Per-endpoint tuning |
| Load shedding | Variable — under load, throughput = capacity (not more) | None for accepted; fast-fail for shed | Tiny (counters) | Threshold tuning |
| Coalescing | -99% duplicate calls in stampede | Lock latency (sub-ms); follower wait = leader's latency | Per-key state, bounded | TTL on in-flight map |
| Deadline propagation | None | None | None | Discipline (every call site) |
| Adaptive concurrency | +5% metric collection | None | Tiny | Library |

---

## Summary

- **Hedging** = "p99 is dominated by a slow replica; bet on a faster one and cancel the slow one." Reads only.
- **Load shedding** = "better to reject fast than fail slow." Every public service should have it.
- **Coalescing** = "thundering herd against the same key should hit the dependency once." Cache miss, config lookups, geo-IP.
- **Deadline propagation** = "every hop gets a fraction of the remaining budget." Stops the timeout cascade.
- **Adaptive concurrency** = "the limit should hug the latency curve, not be a static config." Bonus, advanced.
- **In interviews: pick one, name the metric, name the cost, name the failure mode.**

- [Envoy — Hedging policy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/http_routing#hedging) and [Request coalescing](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/http_routing#request-coalescing) — production-grade implementations.
- [AWS Builders' Library — Avoiding fallback in distributed systems](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) — deadlines, retries, and backoff.

- [gRPC — Deadlines](https://grpc.io/docs/guides/deadlines/) — first-class support in gRPC.
- [Node.js — p-memoize](https://github.com/sindresorhus/p-memoize) — request coalescing for Node.

- [Envoy — Adaptive Concurrency](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/http_routing#adaptive-concurrency) — auto-tuning concurrency limits.

# CAP Theorem & PACELC

Two clinic servers — Server A in Frankfurt and Server B in Berlin — both show Dr. Patel's `10:00` appointment slot as **Free**. The network link between them drops. A patient books `10:00` on Server A and gets `"Confirmed!"`. One second later, another patient asks Server B for that same `10:00` slot. Because Server B cannot reach Server A, it faces an unavoidable dilemma: answer immediately from its stale copy (risking a double booking) or refuse the request (giving up availability). That exact dilemma is the **CAP theorem**.

```text
1. Initial state:  Server A [10:00 = Free]  ◄── link OK ──►  Server B [10:00 = Free]
2. Link breaks:    Server A [10:00 = Booked]  ✕  PARTITION  ✕  Server B [10:00 = Free?]
3. Dilemma at B:   Return "Free" (stale / double-book!)  OR  Refuse / error (unavailable!)
```

## Definition

The **CAP theorem** states that when a network partition prevents replicated nodes from communicating, a distributed data store cannot simultaneously guarantee **linearizable consistency** and **100% availability**.

- **Consistency (C)** in CAP means **linearizability**: every operation behaves as if there were a single up-to-date copy of the data, respecting real-time order (a read started after an acknowledged write must never see the older value).
- **Availability (A)** in CAP means every request reaching a non-failing node eventually receives a valid response according to the operation's contract — it is **not** a monthly uptime percentage like 99.9%.
- **Partition Tolerance (P)** means the system must define its behavior even when network messages between nodes are delayed or dropped.

> **Textbook Definition:** The CAP theorem states that a distributed read/write system cannot guarantee both linearizability and completion of every request to a non-failing node during a network partition.

## First Principles

When the link between Server A and Server B breaks, Server B is trapped by a basic information limit: its local memory looks **100% identical** in two completely different realities:

- **Reality 1:** Nobody booked `10:00` on Server A.
- **Reality 2:** Someone already booked `10:00` on Server A and received a confirmation.

Server B has no physical way to tell which reality happened without communicating across the broken link. If Server B must answer every request immediately, it may hand out an already-booked slot (breaking consistency). If it must guarantee single-copy correctness, it must either wait until the link heals or reject the request (breaking CAP availability). No database brand, retry loop, or clever code can bypass this physics limit.

## 1. Read C, A, and P as Operation Contracts (Why "Pick Two" Misleads)

You often hear CAP summarized as *"pick any two of C, A, and P."* That slogan is misleading because **you cannot opt out of network partitions** in a multi-node system — switches fail, fiber cuts happen, and GC pauses drop heartbeats whether you want them to or not. (A single-node database avoids inter-replica partitions, but if that one machine goes down, the service is unavailable anyway.)

| Property | What CAP strictly means | Practical distinction seniors know |
| --------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **C — Consistency** | Linearizable reads and writes (one logical copy in real-time order) | Different from ACID "C" (schema/foreign-key constraints inside a database) |
| **A — Availability** | Every non-failing node eventually completes every request | Returning HTTP `503 Service Unavailable` or an error JSON is **not** CAP-available |
| **P — Partition tolerance** | The system survives arbitrary message loss/delay between nodes | A timeout tells you nothing about whether the remote write actually committed |

The real engineering question is never *"do we want P?"* It is: **when a partition happens, which operations should fail closed (CP) and which should keep serving stale or divergent state (AP)?**

## 2. Step-by-Step Trace: One Booking Across a Partition

Follow what happens at Server B when a read or booking arrives for `10:00` after Server A has already committed and acknowledged the booking:

| Server B's choice | Immediate effect | Trade-off |
| ------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------ |
| **Answer from local copy** (`"Free"` or accept booking) | Request succeeds fast locally | **AP:** breaks single-copy booking contract; causes double booking that must be reconciled later |
| **Wait until link heals** | Avoids wrong answer | Cannot guarantee completion if the partition lasts indefinitely (fails CAP availability) |
| **Reject the request** (`"Cannot confirm right now"`) | Clear application error | **CP:** protects the booking invariant by sacrificing availability on the isolated node |

### How majority quorums limit the blast radius

Choosing **CP** does **not** mean shutting down the whole cluster during a partition. In a 3-node or 5-node consensus group (such as Raft or Paxos), any operation requires agreement from a **majority quorum** (more than half the nodes — e.g., 2 of 3, or 3 of 5):

```text
5-node cluster splits into [3 nodes]  ✕  [2 nodes]
  • Majority side (3 nodes): has quorum (3 > 5/2) → keeps serving consistent reads & writes!
  • Minority side (2 nodes): lacks quorum         → refuses unsafe operations (unavailable)
```

Only the isolated minority stops serving unsafe operations; the connected majority keeps working safely. Failover rules must agree with write acknowledgments — promoting a lagging replica that missed an acknowledged write silently loses committed bookings. (This multi-node example illustrates distributed replication; within a single primary PostgreSQL instance, transaction isolation and unique constraints enforce booking uniqueness without cross-region consensus.)

## 3. Decide Consistency Per Operation, Not Per Database

Real production systems are rarely pure "CP" or pure "AP" across the board. Even inside one application — and often on the same database — different endpoints need different contracts:

| Operation | Business invariant | Recommended partition policy |
| -------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------- |
| **Confirm a scarce appointment slot** | Never double-book the same slot | **CP:** route to authoritative leader/quorum; refuse confirmation if unreachable |
| **View a clinic's address and bio** | Briefly stale text is harmless | **AP:** serve cached/local replica copy and display freshness if helpful |
| **Revoke a compromised session/token** | Stale permission leaks private data | **CP / fail closed:** deny sensitive access if revocation authority is unreachable |
| **Show a daily analytics chart** | Delayed totals are acceptable | **AP:** serve the last completed snapshot labeled with its timestamp |

**Rule for AP writes:** If you allow disconnected nodes to accept writes independently (for example, offline appointment drafts or shopping carts), you **must** design an explicit reconciliation policy (such as last-write-wins, CRDTs, or manual conflict resolution) for when the network heals.

## 4. PACELC: The Trade-Off That Runs Every Day

Network partitions are rare, yet distributed systems make a consistency trade-off on **every single normal request**. **PACELC** extends CAP to cover normal operation:

- **If there is a Partition (P):** choose between **Availability (A)** and **Consistency (C)**.
- **Else (E — network is healthy):** choose between **Latency (L)** and **Consistency (C)**.

Waiting for a remote replica across regions to confirm a write adds round-trip network latency. Returning immediately from a local node is faster, but a reader hitting another node may see stale data.

### Concrete PostgreSQL example: `flush` vs. `remote_apply`

In PostgreSQL streaming replication, the primary ships Write-Ahead Log (WAL) records to standby replicas. Watch how one config flag shifts the **E (Latency vs. Consistency)** trade-off:

- **`synchronous_commit = on` (remote flush):** The primary waits until the standby writes the WAL record to disk. The write is now **durable** if the primary dies, but the standby may not have *replayed* that WAL record into its queryable tables yet — so an immediate read on the standby can still return the old value.
- **`synchronous_commit = remote_apply`:** The primary waits until the standby both flushes **and** applies the WAL record so queries immediately see it. Reads on that standby are fresher, at the cost of higher write latency.

Before labeling any database "CP" or "AP," inspect its exact **write acknowledgment mode, read routing, replication topology, and failover policy**.

## Common Mistakes

- **Confusing CAP Consistency with ACID Consistency:** CAP "C" is linearizable read/write ordering across replicas; ACID "C" is preserving database constraints (like `CHECK` or `UNIQUE`) across a transaction.
- **Treating a timeout as proof of failure:** When a write times out across a partition, the remote node may have committed it right before the acknowledgment dropped. Always attach an idempotency key and reconcile state before blindly retrying.
- **Assuming "eventual consistency" means "consistent within 500ms":** Eventual consistency makes no wall-clock bound — convergence only happens after communication heals and conflicts resolve.
- **Labeling an entire database brand as permanently CP or AP:** The same database (e.g., Cassandra with `QUORUM` vs. `ONE`, or PostgreSQL with async vs. `remote_apply` standbys) exposes very different guarantees depending on configuration.
- **Equating HTTP `200`/`503` responses with CAP availability:** Answering with an error payload saying *"please retry later"* is graceful degradation, not CAP availability — the requested operation did not complete.

### How to test partition behavior honestly

Happy-path load tests cannot verify partition safety. To test it: inject a network split between replicas, acknowledge a write on side A, issue a read or conflicting write on side B, record exact responses and timestamps, heal the partition, and verify whether the final state matches your declared contract.

## Summary

When a network partition isolates replicas, an isolated node cannot tell whether a remote write succeeded — so it must either serve potentially stale data (AP) or refuse unsafe operations to protect single-copy linearizability (CP). In consensus clusters, majority quorums let the connected majority keep serving while only the isolated minority fails closed. Choose consistency contracts per operation rather than by database label, define conflict reconciliation for any AP write, and use PACELC to reason about the everyday latency-versus-consistency trade-off (such as PostgreSQL WAL flush versus `remote_apply`) when the network is healthy.

# CAP Theorem & PACELC

## Definition

**CAP explains why replicated data cannot guarantee both linearizable operations and availability when replicas cannot communicate.** Linearizability means operations behave like one copy of the data, with completed operations respected in real-time order. Availability here means every request to a non-failing node eventually completes according to the operation's contract; it is not a monthly uptime percentage.

Imagine two clinic locations both showing one appointment slot as free. Their connection fails. One location books the slot. The other receives a request for that same slot: how can it answer safely without knowing what happened elsewhere?

> **Textbook Definition:** The CAP theorem states that a distributed read/write system cannot guarantee both linearizability and completion of every request to a non-failing node during a network partition.

## First Principles

The isolated location cannot distinguish two histories: nobody booked the slot, or someone booked it on the other side of the broken connection. Its local state is identical in both histories.

If it must answer every request without communication, it may accept an already-booked slot or report an obsolete state. If it must preserve a single authoritative order, it must wait for coordination or reject operations it cannot safely serve. Waiting indefinitely does not satisfy availability. The network failure creates this conflict; choosing a database brand cannot remove it.

## What C, A and P mean together

| Property | Meaning in the CAP model | Practical boundary |
| ----------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| C — consistency | Operations are linearizable: one logical copy respecting real-time order | A read begun after an acknowledged booking cannot return the earlier free-slot state |
| A — availability | Requests at non-failing nodes eventually complete | A failure response or refusal cannot stand in for a successful data operation |
| P — partition tolerance | The guarantees must be considered even when communication between nodes is disrupted | Detecting a timeout does not reveal whether the remote operation committed |

The familiar “pick two” slogan hides the useful question: **which operations may stop or return weaker results during a partition?** Excluding partitions from the model avoids that question rather than solving it. A single database instance avoids inter-replica partitions, but can still fail or become unreachable.

## Trace one booking across a partition

```text
Initially: A and B know slot 10:00 is free
Connection between A and B breaks
A commits a booking and acknowledges it
B receives a read or booking request for 10:00
```

| B's response | Consequence |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Reports free or accepts a conflicting booking from its old state | Completes locally, but violates the required single-copy booking contract |
| Waits until it can verify authoritative state | Preserves that contract, but cannot guarantee completion throughout an indefinite partition |
| Rejects the unsafe operation | Gives a clear application failure, sacrificing CAP availability for that operation |

These policies are often described as **CP** (preserve consistency during partitions by withholding unsafe operations) or **AP** (complete operations during partitions with a weaker consistency contract). The shorthand describes the chosen operation and failure model, not a permanent label for the entire application.

A leader with a majority quorum—agreement from more than half the replicas—can often keep serving the connected majority while the minority refuses unsafe operations. Sacrificing availability does **not** require shutting down every node. Acknowledged writes, leader election and failover rules must agree; a stale replica promoted without safeguards can lose an acknowledged booking.

This is an illustrative distributed booking model, not a claim that Docita runs multi-region active-active writes. Within one PostgreSQL authority, transaction isolation and uniqueness constraints address a different part of booking correctness.

## Decide per operation and invariant

| Operation | Required invariant or tolerance | Useful partition policy |
| --------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Confirm a scarce appointment slot | One accepted booking for the slot | Use an authoritative write path; refuse confirmation without safe coordination |
| Browse a clinic description | Temporarily old descriptive text is acceptable | Serve a retained copy and identify its freshness |
| Revoke access | Old permission may disclose sensitive data | Define revocation visibility; deny sensitive access when its required authority is unavailable |
| Show an analytics chart | Delayed counts are acceptable | Serve the last complete snapshot with its collection time |

Choose from requirements rather than declaring all money “CP” and all caches “AP.” A catalog price may need validation again at checkout. An offline booking draft may be acceptable while an actual confirmation is not. Allowing independent writes also requires an explicit conflict/reconciliation rule after connectivity returns.

## PACELC adds the normal-operation question

**During a partition, availability competes with consistency. Else, latency can compete with consistency.** PACELC is a design lens for replication behavior outside the failure case as well.

Waiting for remote coordination increases latency compared with returning local state. That local state may not include the latest remote write. Ask what the acknowledgment means, where reads go, and what visibility the operation promises. Geography, quorum size and read/write protocol affect the cost; PACELC is not a universal database benchmark.

A replica can durably save a log entry before applying it to the state used by reads. PostgreSQL calls this the write-ahead log (WAL). Waiting for a standby replica to flush that log is different from waiting for it to replay the write. An arbitrary standby read can still lag. For any database, specify read mode, write acknowledgment, replication topology and failover policy before assigning a shorthand label.

## Mistakes and practical checks

- Confusing CAP consistency with ACID consistency: linearizable visibility and database integrity constraints are different guarantees.
- Calling a timeout proof of rollback: a remote write may have committed before its acknowledgment was lost. Use an operation identity and query/retry policy.
- Treating “eventual” as a fixed delay: convergence needs the stated recovery assumptions; test conflicts and interrupted reconciliation.
- Calling every database permanently CP or AP: configurations and individual operations can expose different contracts.
- Equating a successful HTTP response with CAP availability: an endpoint returning a failure payload has not completed the requested booking.

Test a small history: partition replicas, acknowledge a write on one side, read on the other, and record responses and ordering. Then reconnect and verify recovery. State which guarantee you checked; a happy-path load test cannot establish partition safety.

## Summary

During lost communication, an isolated replica cannot know whether a remote write occurred. Completing from local state can break linearizability; coordinating or refusing unsafe operations sacrifices availability. Choose the required contract per operation, explain recovery, and use PACELC to discuss coordination latency when communication works.

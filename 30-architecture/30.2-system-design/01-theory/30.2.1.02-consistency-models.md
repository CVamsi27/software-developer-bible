# Data Consistency Models

> **Linearizability, Eventual, Causal, Read-your-writes, Monotonic reads** — the 5 models you need to know. Pick the right one for each operation in your system design, not a blanket "we use strong consistency."

## Definition

A **consistency model** is a contract between a data store and its clients that says, for any history of reads and writes, **which values a read is allowed to return**. It is a specification of observable behavior, not an implementation: a system "satisfies linearizability" when no client can tell (by the values it reads) that the data is replicated at all.

The guarantees form a partial order, not one ladder. Read-your-writes and monotonic reads are independent session guarantees: a client can read its own write and later move to an older replica, or read monotonically while never observing its unpropagated write.

```text
linearizable → sequential → causal
                               ├→ read-your-writes
                               └→ monotonic reads

eventual convergence is a separate liveness condition; add it explicitly.
```

Two properties pin most designs down:

1. **What must be ordered** — all operations globally (linearizable), only causally-related ones (causal), or nothing (eventual).
2. **What a single client may observe** — never going backwards (`monotonic reads`), always seeing its own writes (`read-your-writes`), or no promise at all (`eventual`).

Choosing a model is choosing *where replication lag becomes visible*: stronger models hide it behind coordination (higher latency), weaker models expose it to the application (more application-level repair).

---

## First Principles

Consistency models are the menu of answers to one question: how stale may a read be?

1. **Strong/linearizable is the max contract**: every read sees the latest completed write, as if one machine — which costs coordination on every operation (→ 30.2.1.01's CP choice).
2. **Weaker models trade guarantees for speed**, and each has a precise definition: eventual (replicas converge, order unspecified), causal (effects follow their dependencies), read-your-writes (your own writes visible — the session-pinning requirement from replication, → 20.4.3.04), monotonic reads.
3. **The model is chosen per data type, not per database.** Comments tolerate eventual; bank balances don't. Modern systems expose per-operation consistency selection — the senior skill is mapping *business tolerance* to *model*, not memorizing the ladder.

## Why it matters

In any non-trivial system design, you have multiple data types with different consistency needs:

- A bank account balance? **Linearizability.**
- A like count? **Eventual.**
- A comment thread (replies to a comment)? **Causal.**
- The user's own profile (after they edit)? **Read-your-writes.**

If you say "we use strong consistency" in an interview, you're being lazy. The right answer is per-operation.

## The 5 Models (weakest to strongest)

### 1. Eventual Consistency

**Definition:** If no new writes happen, all replicas will eventually converge to the same value. Reads may return stale data in the meantime.

```
Time →
Write to Node A: x = 1
Read from Node B (50ms later): x = ? (could be 0 or 1)
Read from Node B (500ms later): x = 1 (eventually consistent)
```

**When to use:**
- Social media feeds, likes, comments
- Analytics counters
- DNS
- Caching layers
- Any read-heavy, write-light workload where stale is OK

**Examples:** Cassandra, DynamoDB (default), Riak, CouchDB

**Interview signal:** "We use eventual consistency for the comment count. If a user sees '999 comments' instead of '1,000' for 200ms, that's fine."

---

### 2. Read-Your-Writes Consistency

**Definition:** A client always sees their own writes. They might see stale data for other clients' writes, but never their own.

```
Time →
User A writes x = 1 on Node A
User A reads from Node B (10ms later): x = 1 (guaranteed)
User B reads from Node B: x = 0 (might be stale)
```

**When to use:**
- User profile updates (you just changed your name, refresh and see the new name)
- Posts/comments (you just posted, refresh and see it)
- Any "I just submitted, why doesn't it show?" scenario

**Implementation:**
- Read from a leader that still contains the acknowledged write, or wait until the chosen replica has applied its commit position
- Route to the same shard/region for the duration of a session
- Carry a minimum commit/version token across failover; HTTP server stickiness alone does not synchronize a database replica

**Examples:** Most modern systems provide this for the user's own data, even if they don't provide strong consistency globally.

---

### 3. Monotonic Reads

**Definition:** A client never sees a "regression" — once they see a value v at time t, they never see a value older than v at any later time.

```
Time →
Read 1: x = 5
[replica fails over to a stale one]
Read 2: x = 3 ← VIOLATION (older value)
```

**When to use:**
- News feeds, timelines (you don't want a new post to "disappear" from your feed)
- Any feed where a regression would be confusing

**Implementation:**
- Read from the same replica (sticky reads)
- Or use a token/vector clock to filter out older reads

---

### 4. Causal Consistency

**Definition:** If operation A causally precedes operation B, all clients see A before B. Concurrent operations can be seen in any order.

```
Time →
User A posts comment C1
User A replies to C1 with comment C2
All users must see C1 before C2 (causally related)
```

**When to use:**
- Comment threads (replies must come after the parent)
- Collaborative editing (Google Docs)
- Messaging (replies after the original)
- Any "threaded" or "nested" data

**Implementation:**
- Version vectors
- Vector clocks
- Lamport timestamps
- Causally delivered operations or dependency tracking; a convergent CRDT by itself does not guarantee causal visibility (Conflict-free Replicated Data Types)

**Examples:** Some NoSQL systems with vector clocks, eventually-consistent systems with causal guarantees.

---

### 5. Linearizability / Strong Consistency (strongest)

**Definition:** Once a write is acknowledged, all subsequent reads (from any client, any node) return the most recent value. Equivalent to a single-copy system.

```
Time →
Write to Node A: x = 1 (acknowledged)
Read from Node B: x = 1 (guaranteed, even if it hits a different node)
```

**When to use:**
- Bank account balances
- Inventory counts
- Payment status
- User authentication tokens
- Any read where stale data would cause user-visible bugs or financial loss

**Implementation:**
- A single ordered writer plus synchronized reads and safe failover; synchronous replication alone is not a complete read protocol with quorum
- Consensus algorithms (Paxos, Raft)
- Two-phase commit (rare in production, but the textbook answer)
- Spanner (TrueTime), CockroachDB (Hybrid Logical Clocks)

**Cost:** higher latency (must coordinate with majority), lower availability during partitions

**Examples:** Spanner, CockroachDB, etcd, ZooKeeper, HBase, MongoDB (with majority write concern), traditional RDBMS with synchronous replication

---

## The Consistency Spectrum

```
Eventual ←→ Read-your-writes ←→ Monotonic reads ←→ Causal ←→ Linearizable
   weak strong
   fast slow
   AP CP
```

**Each step stronger has a cost** — more coordination, more latency, less availability.

---

## Consistency in Practice: Most Systems Mix

Real systems don't pick "eventual" or "strong" globally. They pick per-operation:

**Example: Reddit**
- Vote count: **Eventual** (you don't care if you see "9,999" for 100ms instead of "10,000")
- Your own post appearing: **Read-your-writes** (you just posted, refresh and see it)
- Comment thread: **Causal** (replies after parent)
- User authentication: **Linearizable** (must be exact, can't show wrong user)
- Karma count: **Eventual** (same as votes)
- Moderator action: **Linearizable** (action must be exact, can't be reverted)

**In an interview:** "This system uses a mix. Account balance is linearizable (CP), but the like count is eventual (AP). The user's own profile is read-your-writes."

---

## How to talk about consistency in an interview

When you discuss a data store in a system design round, name the consistency model explicitly:

1. "We use Postgres for the account balance with synchronous replication — that's linearizable. We accept higher write latency in exchange for correctness."
2. "For the comment count, we use Redis with eventual consistency. If a user sees '1,000 comments' when there are actually '1,002', that's fine — it's the typical social-media UX."
3. "For the comment thread, we need causal consistency. We use Cassandra with vector clocks to ensure replies come after parent comments."

The senior signal: name the model, explain the trade-off, justify the choice.

---

## Common pitfalls

- **Saying "we use strong consistency" globally.** Doesn't make sense — you'll pay the latency cost everywhere. Pick per-operation.
- **Saying "we use eventual consistency" without specifying the read-your-writes / monotonic guarantees.** Those are often desired even in eventual systems.
- **Confusing "eventual consistency" with "no consistency".** Eventual is a guarantee, just a weak one.
- **Ignoring PACELC.** Even with eventual, you trade latency. There's no free lunch.
- **Not thinking about the read path.** The consistency model affects what reads can return. Different reads from different replicas may diverge.

## Interview patterns: which model to pick

| Use case | Model | Why |
| ------------------ | ---------------- | --------------------------------- |
| Bank balance | Linearizable | Wrong = lost money |
| Inventory count | Linearizable | Overselling = angry customer |
| Payment status | Linearizable | Must be exact |
| Auth tokens | Linearizable | Stale = security hole |
| User profile (own) | Read-your-writes | UX: you should see your own edits |
| Posts you made | Read-your-writes | Same |
| Comment thread | Causal | Replies after parent |
| Collaborative doc | Causal | Operations on same doc must order |
| News feed | Monotonic reads | New posts shouldn't disappear |
| Timeline | Monotonic reads | Same |
| Likes count | Eventual | Slightly wrong is fine |
| View count | Eventual | Same |
| Analytics | Eventual | Always slightly stale |
| Search index | Eventual | Slightly stale is fine |
| DNS | Eventual | Propagation is eventual anyway |
| CDN | Eventual | That's the point |

## Implementing each model

### Eventual consistency
- Async replication
- No coordination
- Just write to local, propagate eventually

### Read-your-writes
- "Read your own writes" routing: read from the same region/replica
- Or read from leader, write to leader

### Monotonic reads
- Sticky reads while replica state cannot regress; use a minimum observed-version token when routing changes
- Or vector clocks + filter

### Causal consistency
- Vector clocks
- Version vectors
- Causally delivered operations or dependency tracking; a convergent CRDT by itself does not guarantee causal visibility
- Or causal barriers (delay reads until causally preceding writes are visible)

### Linearizability
- Quorum overlap (`R + W > N`) is necessary for some protocols, but insufficient alone: concurrent writes, partial writes, version selection and read repair still matter
- Consensus (Paxos, Raft)
- A single ordered writer plus synchronized reads and safe failover; synchronous replication alone is not a complete read protocol
- Spanner (TrueTime) — wait for time to be sure

---

## Summary

Consistency models define the guarantees a distributed system provides for data visibility across replicas. Stronger models (linearizability) provide better correctness but cost latency and availability. Weaker models (eventual consistency) provide better performance but require conflict resolution. In interviews, name the specific model, explain the trade-off, and justify your choice based on the use case.

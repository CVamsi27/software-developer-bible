# Data Consistency Models

Different parts of an application can show different versions of the same data. A write completes on replica A while replica B still shows the old value — what is each read allowed to show, and how do you choose?

```text
Write x=1 completes on replica A → read on replica B may still see x=0.
Which reads must see the write, and which may lag?
```

## Definition

A **consistency model** describes what values a client may see when it reads data after writes. It is a promise about **observable behavior**, not a database implementation. For example, linearizability means clients cannot observe an order that contradicts the real-time order in which completed operations took effect.

> **Textbook Definition:** A consistency model specifies which histories of reads and writes are observable across concurrent clients and replicas, constraining operation ordering, visibility, or convergence under stated assumptions.

## First Principles

A write can complete at replica A before replica B receives it. A later reader at B has the same local state whether that write happened or not. To include the write, B must obtain new information or wait for a known version; returning immediately from its old state cannot establish freshness.

A client can carry what it already knows: the version it wrote or last read. That information can prevent one session from moving backward without making every client's reads globally current. Dependent changes require more still: a reply must identify the parent state it depends on. These different information requirements produce different consistency contracts. If the necessary information is unreachable, the operation must either wait/refuse or weaken its promised view — and the chosen read mode, session token, and failover rules determine which choice the reader actually gets.

## 1. Eventual consistency: replicas settle with no deadline

**Promise:** If updates stop and every accepted update is eventually delivered, replicas eventually converge on the same value. Until then, a read may return an older value. No deadline for catching up is promised. The implementation still needs a conflict/merge rule: delivery alone is insufficient if replicas resolve the same conflicts differently.

```text
Time →
Write to Node A: x = 1
Read from Node B (50ms later): x = ? (could be 0 or 1)
After Node B receives the update: x = 1 (no fixed delivery time promised)
```

**Use for:**

- Social media feeds, likes, comments.
- Analytics counters.
- DNS.
- Caching layers.
- Any operation where the product tolerates a possibly delayed update.

The exact behavior depends on the store and its settings — a database may let callers choose eventual or stronger reads for some tables but not every index or region. A comment count may update after the comment is saved: decide how much delay the interface tolerates, because eventual consistency never guarantees a 200 ms limit.

## 2. Read-your-writes: a client sees its own acknowledged update

**Promise:** After a client receives confirmation that its write succeeded, later reads in that session include that write. The client may still see older data written by other clients.

```text
Time →
User A writes x = 1 on Node A
User A reads later: x = 1 or a later update (session guarantee)
User B may still read x = 0 from a lagging replica
```

**Use for:** profile updates ("I just changed my name, refresh and see it"), posts/comments ("I just posted, why doesn't it show?"). **Implement by:** reading from an authority containing the acknowledged write, or waiting until the chosen replica has applied it; carrying a version token with the session and rejecting or delaying reads from replicas below that version. Routing every request to the same application server never by itself makes a database replica current — the application must implement this guarantee, and the chosen read path must honor its tokens.

## 3. Monotonic reads: a session never moves backward

**Promise:** After a client has seen a version of the data, later reads in that session never return an older version. This says nothing about whether the first read was the newest version.

```text
Time →
Read 1: version v5 has x = 5
[replica fails over to one still at version v3]
Read 2: version v3 has x = 3 ← VIOLATION (older version)
```

A newer legitimate write may decrease x from 5 to 3 without violating monotonic reads. The guarantee concerns observed history/version order, not increasing numeric values. Deletion, filtering, and feed pagination can also change displayed items without a consistency regression. **Use for:** reads where an older version would confuse the user, e.g. feeds after failover. **Implement by:** keeping reads on a replica at or past the observed version, or carrying a version token so another replica waits until caught up.

## 4. Causal consistency: dependent changes stay ordered

**Promise:** A client's observations respect causal dependencies: its own program order, writes it observed before acting, and the transitive dependencies of those writes. Independent changes need no common order across clients.

```text
Time →
A user posts comment C1
The user replies to C1 with C2
A client must see C1 before it displays C2
```

Here the reply refers to a separately stored parent, so the view must contain that parent before exposing the reply. This never means a reader must retrieve every intermediate value: if `x=1` is causally followed by `x=2`, a reader may first read `x=2`; the later version incorporates the earlier history. Nor does causality order two independent replies or guarantee the view holds the latest update.

**Use for:** comment threads, collaborative edits, messaging — any threaded or nested data.

**Implement by:** tracking which earlier updates a new update depends on and carrying that information with it; delivering or displaying a dependent update only after its earlier updates are visible.

A CRDT may make replicas converge, but convergence alone never guarantees a client sees dependent updates in order. Causal behavior depends on the database protocol and client session — never infer it from a product category or timestamps alone.

## 5. Sequential consistency: one order, no real-time promise

**Promise:** All completed operations fit one legal sequential order preserving each client's program order. That order need not preserve real-time order between different clients.

Assume `x` starts at zero and only A writes it. A finishes `write(x=1)`. B then starts `read(x)` and gets zero. Sequential consistency explains this as `B:read(0) → A:write(1)` because no program-order edge connects those clients. Linearizability rejects that explanation: A's response occurred before B's invocation. Sequential consistency is therefore more specific than "replicas eventually agree," but weaker than real-time single-copy behavior. Never infer this contract merely from using a leader — the read protocol and permitted operation histories must establish it.

## 6. Linearizability: real-time single-copy behavior

**Promise:** Once a write completes, a read starting afterward returns that value or a later one. Concurrent reads and writes must fit one order respecting this real-time rule, as though operations used one logical copy.

```text
Time →
Write to Node A: x = 1 (acknowledged)
Read from Node B after acknowledgment: x = 1 or a later write
```

**Consider for:**

- Confirming a scarce inventory item.
- Checking a payment or account operation where an old value could trigger a second charge.
- Checking an access change the product requires to take effect immediately.

The business invariant may also require a transaction — a linearizable read alone enforces no multi-record rule.

**Implement with:** a protocol ordering writes, serving reads from sufficiently current state, and preventing unsafe failover; consensus protocols such as Raft can help replicas agree on that order. Verify transaction isolation, read routing, and failover behavior — synchronous replication alone never describes the full read contract.

**Cost:** coordination can add latency. During a partition, an operation may have to wait or fail if the system cannot safely establish the required order.

A product may provide this guarantee only for specific operations or settings — never infer linearizability from a database name or a synchronous-replication option.

Trace the operation intervals: each operation must appear to take effect at some point between its invocation and response. For one register initially zero, with only one write of one:

| Observed history | Linearizable? | Reason |
| -------------------------------------------------------------- | ------------- | ----------------------------------------------------------------------------- |
| Read begins and finishes before the write begins; returns zero | Yes | Place the read before the write |
| Read overlaps the write; returns zero | Can be | Place that read before the write, provided the rest of the history agrees |
| Write finishes, then a read begins; returns zero | No | Real-time order requires the read to follow the write |
| One read returns one, finishes, then another returns zero | No | With no intervening write, no legal single-copy order explains the regression |

An overlapping operation need not see the newest in-flight write. A timeout leaves an operation's outcome unknown; it never proves that operation had no effect. Reason from invocation/response order and the whole history, not from unsynchronized server timestamps.

## Serializability is a separate transaction contract

**Serializability** concerns transactions: their combined reads and writes have the same observable effect as some serial execution of those transactions. It never requires that serial order to match real time. **Strict serializability** adds real-time order between non-overlapping transactions. Linearizability typically describes individual object operations; a linearizable read plus a separate write never becomes an atomic read-modify-write transaction.

For example, two clients can both read `stock=1` through individually linearizable reads, then each confirm a sale through a separate write. Every operation can hold a legal order while two customers receive the last item. Put the check and decrement inside an invariant-preserving transaction, or use one authoritative conditional operation such as "decrement only if stock is positive." Specify its isolation, conflict/retry behavior, and acknowledgment boundary. See [database transactions](../../../20-backend/20.4-database/03-transactions-and-replication/20.4.3.01-transactions.md) for the isolation mechanisms.

## How the guarantees relate — and why session guarantees are independent

Linearizability preserves real-time order. Causal consistency preserves the order of dependent changes. Read-your-writes and monotonic reads describe guarantees for one client session. Eventual convergence describes whether replicas settle after updates stop; it promises no ordering while they catch up. Stronger guarantees often need more coordination — which can add latency or force a request to wait or fail during a partition.

Suppose you read version 8 from someone else's update, then your next request reaches a replica at version 6. A read-your-writes policy alone has nothing to preserve if you have not written; monotonic reads would reject that regression. Conversely, you can write version 9, then first read from version 8. That first read moves backward from no previously read version, but it violates read-your-writes. A session carrying both its read and write barriers can request both guarantees. The same system can mix guarantees by operation. In an interview, name what each operation may return and what it does when the required version is unavailable; CP/AP labels from CAP never answer that question.

## Common Mistakes

- Saying "we use strong consistency" without describing it. State which operations need the guarantee and what reads return after writes.
- Saying "we use eventual consistency" without specifying read-your-writes / monotonic guarantees. Those are often desired even in eventual systems.
- Confusing "eventual consistency" with "no consistency". Eventual is a guarantee, just a weak one.
- Ignoring latency when replicas coordinate. PACELC asks about the latency-versus-consistency choice during normal operation (the "else" case outside a partition); see the CAP chapter.
- Not thinking about the read path. The consistency model affects what reads can return. Different reads from different replicas may diverge.

## Match a product need to a guarantee

To choose, ask: must every read include the latest completed write? Must dependent changes stay ordered? Can one client see an older value after a newer one? Can it read its own confirmed change? These questions reveal where replica lag can appear.

| Product need | Guarantee to consider | Question to answer |
| ----------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------- |
| Confirm a limited-inventory booking | An authoritative transaction; possibly a linearizable claim | Can two clients both confirm the final item? |
| Show a count or analytics total | Eventual update may be acceptable | How stale can it be, and how are duplicates handled? |
| Show a user's own saved edit | Read-your-writes | Does refresh show the acknowledged change? |
| Display a reply | Causal ordering | Can a client see the reply before the parent? |
| Load a feed after failover | Monotonic reads, if regressions matter | Could a later read use an older accepted history? |
| Apply an access revocation | Define the required freshness of permissions | Can a request still use the old permission, and for how long? |

## Summary

A consistency contract says what a client may see after writes, including which changes must be ordered. Linearizability respects real-time order; causal consistency preserves dependent changes; read-your-writes and monotonic reads protect a client session; eventual consistency allows lag while replicas catch up. State the read path, failure behavior and stale-data tolerance for each important operation.

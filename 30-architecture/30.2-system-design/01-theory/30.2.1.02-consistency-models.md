# Data Consistency Models

Different parts of an application can show different versions of the same data. This chapter explains what a read is allowed to show and how to choose that behavior.

## Definition

A **consistency model** describes what values a client may see when it reads data after writes. It is a promise about observable behavior, not a database implementation. For example, linearizability means clients cannot observe operations in an order that contradicts when completed operations happened.

These guarantees do not form one simple ladder. **Read-your-writes** means a client sees its own acknowledged update on later reads. **Monotonic reads** means a client does not later see an older version than one it has already seen. A system can provide either guarantee without providing the other. A causal guarantee usually includes both for that client, because it preserves the order of dependent operations.

Sequential consistency puts operations in one order but may ignore when they happened in real time. Linearizability also respects real-time order. Causal consistency preserves the order of operations that depend on one another. Read-your-writes and monotonic reads describe what one client may observe. Eventual convergence is a separate promise: replicas may settle on the same value after updates stop and are delivered; it does not set a deadline or fully specify reads before then.

To choose a guarantee, ask: must every read include the latest completed write? Must changes that depend on one another stay in order? Can one client see an older value after a newer one? Can it read its own confirmed change? These questions reveal where replica lag can appear.

> **Textbook Definition:** A consistency model is an architectural contract between a distributed data store and its processes that specifies the system-wide constraints and ordering guarantees governing read and write operations (Tanenbaum & Van Steen, *Distributed Systems: Principles and Paradigms* / Herlihy & Wing, *Linearizability: A Correctness Condition for Concurrent Objects*). It formally dictates whether concurrent operations must appear instantaneous at a global linearization point, preserve causal dependencies, or guarantee monotonic read/write progress across replicas.

## First Principles

A user may read from a replica that has not yet received a recent update. A consistency model states whether the application must wait, can return an older value, or must preserve some ordering.

1. **Linearizability preserves one real-time order.** A read that begins after a write has completed must see that write or a later one. Distributed systems often need coordination to provide this during failures (→ 30.2.1.01).
2. **Other models preserve selected guarantees.** Replicas may temporarily return older values; a client may still be promised that it sees its own updates or that its reads never move backward (→ 20.4.3.04). Causal consistency preserves the order of dependent changes.
3. **Choose guarantees for the operation.** A delayed count may be acceptable, while confirming a scarce booking may require a single accepted owner. A database name alone does not tell you the guarantees: read mode, transactions, replication and failover settings matter.

## Why it matters

One product can need different guarantees for different actions:

- Confirming a transfer? Define a transaction that prevents spending the same funds twice; specify the read and write guarantees it needs.
- Displaying a like count? A delayed count may be acceptable if updates eventually appear.
- Showing a reply? If it depends on a parent comment, do not show the reply before the parent.
- Showing a profile immediately after its owner edits it? The product may require read-your-writes behavior.

State the guarantee for each important operation. “Strong consistency” alone does not describe what the reader can observe.

## Five Common Consistency Contracts

### 1. Eventual Consistency

**Definition:** If updates stop and every accepted update is eventually delivered, replicas eventually settle on a consistent value. Until then, a read may return an older value. Eventual consistency does not promise when every replica catches up or how conflicting updates are resolved.

```
Time →
Write to Node A: x = 1
Read from Node B (50ms later): x = ? (could be 0 or 1)
After Node B receives the update: x = 1 (no fixed delivery time is promised)
```

**When to use:**
- Social media feeds, likes, comments
- Analytics counters
- DNS
- Caching layers
- Any operation where the product can tolerate a possibly delayed update

The exact behavior depends on the store and its settings. For example, a database may let callers choose eventual or stronger reads for some tables but not for every index or region.

For example, a comment count may update after the comment is saved. Decide how much delay the interface can tolerate; eventual consistency does not guarantee a 200 ms limit.

---

### 2. Read-Your-Writes Consistency

**Definition:** After a client receives confirmation that its write succeeded, later reads in that session should include that write. The client may still see older data written by other clients.

```
Time →
User A writes x = 1 on Node A
User A reads later: x = 1 (if the read path preserves the session guarantee)
User B may still read x = 0 from a lagging replica
```

**When to use:**
- User profile updates (you just changed your name, refresh and see the new name)
- Posts/comments (you just posted, refresh and see it)
- Any "I just submitted, why doesn't it show?" scenario

**Implementation:**
- Read from an authority that contains the acknowledged write, or wait until the chosen replica has applied it
- Carry a version token with the session and reject or delay reads from replicas that have not reached that version
- Routing every request to the same application server does not by itself make a database replica current

The application must implement this guarantee. Session routing or version tokens can help, but only if the chosen read path honors them.

---

### 3. Monotonic Reads

**Definition:** After a client has seen a version of the data, later reads in that session do not go back to an older version. This says nothing about whether the first read was the newest version.

```
Time →
Read 1: x = 5
[replica fails over to a stale one]
Read 2: x = 3 ← VIOLATION (older value)
```

**When to use:**
- News feeds, timelines (you don't want a new post to "disappear" from your feed)
- Any feed where a regression would be confusing

**Implementation:**
- Keep reads on a replica that has reached at least the version already observed
- Or carry a version token so another replica can wait until it has caught up

---

### 4. Causal Consistency

**Definition:** If one change depends on another, a client that sees the later change must also see the earlier one first. Changes made independently can be observed in either order.

```
Time →
A user posts comment C1
The user replies to C1 with C2
A client must see C1 before it displays C2
```

**When to use:**
- Comment threads (replies must come after the parent)
- Collaborative edits where later changes depend on earlier ones
- Messaging (replies after the original)
- Any "threaded" or "nested" data

**Implementation:**
- Track which earlier updates a new update depends on, and carry that information with it
- Deliver or display a dependent update only after its earlier updates are visible
- A conflict-free replicated data type (CRDT) may make replicas converge, but convergence alone does not guarantee that a client sees dependent updates in order

Causal behavior depends on the database protocol and the client session; do not infer it from a product category or the use of timestamps alone.

---

### 5. Linearizability (often called strong consistency)

**Definition:** Once a write completes, a read that starts afterward returns that value or a later one. Concurrent reads and writes must fit one order that respects this real-time rule, as though operations used one logical copy.

```
Time →
Write to Node A: x = 1 (acknowledged)
Read from Node B: x = 1 (guaranteed, even if it hits a different node)
```

**When to consider it:**
- Confirming a scarce inventory item
- Checking a payment or account operation when an old value could trigger a second charge or spend
- Checking an access change when the product requires it to take effect immediately

The business invariant may also require a transaction. A linearizable read alone does not enforce every multi-record rule.

**Implementation:**
- Use a protocol that orders writes, serves reads from a sufficiently current state, and prevents unsafe failover
- Consensus protocols such as Raft can help replicas agree on that order
- Verify the database transaction isolation, read routing and failover behavior; synchronous replication alone does not describe the full read contract

**Cost:** coordination can add latency. During a partition, an operation may have to wait or fail if the system cannot safely establish the required order.

A product may provide this guarantee only for specific operations or settings. Check its transaction, read and failover documentation; do not infer linearizability from a database name or a synchronous-replication option.

## How the Guarantees Relate

Linearizability preserves real-time order. Causal consistency preserves the order of dependent changes. Read-your-writes and monotonic reads describe guarantees for one client session. Eventual convergence describes whether replicas settle after updates stop; it does not promise any specific ordering while they are catching up.

Stronger guarantees often need more coordination. Depending on the operation and failure, that can add latency or mean a request must wait or fail during a partition.

## Consistency in Practice: One System Can Mix Guarantees

A discussion product might allow counts to update after a post is saved, while requiring a user to see their own new post after submission. A reply should not appear before its parent if clients rely on that order. Permission revocation needs an explicit freshness rule: decide how long a request may use an old permission.

In an interview, name the guarantee and failure behavior for each operation. Do not use CAP labels such as CP or AP as if they were consistency models.

## Common Pitfalls

- **Saying "we use strong consistency" without describing it.** State which operations need the guarantee and what reads return after writes.
- **Saying "we use eventual consistency" without specifying the read-your-writes / monotonic guarantees.** Those are often desired even in eventual systems.
- **Confusing "eventual consistency" with "no consistency".** Eventual is a guarantee, just a weak one.
- **Ignoring latency when replicas coordinate.** PACELC asks about the latency-versus-consistency choice during normal operation (the “else” case outside a partition); see the CAP chapter.
- **Not thinking about the read path.** The consistency model affects what reads can return. Different reads from different replicas may diverge.

## Match a product need to a guarantee

| Product need | Guarantee to consider | Question to answer |
| ----------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------- |
| Confirm a limited-inventory booking | An authoritative transaction; possibly a linearizable claim | Can two clients both confirm the final item? |
| Show a count or analytics total | Eventual update may be acceptable | How stale can it be, and how are duplicates handled? |
| Show a user's own saved edit | Read-your-writes | Does refresh show the acknowledged change? |
| Display a reply | Causal ordering | Can a client see the reply before the parent? |
| Load a feed after failover | Monotonic reads, if regressions matter | Could a previously seen item disappear? |
| Apply an access revocation | Define the required freshness of permissions | Can a request still use the old permission, and for how long? |

---

## Summary

A consistency contract says what a client may see after writes, including which changes must be ordered. Linearizability respects real-time order; causal consistency preserves dependent changes; read-your-writes and monotonic reads protect a client session; eventual consistency allows lag while replicas catch up. State the read path, failure behavior and stale-data tolerance for each important operation.

# Caching Patterns

A product catalog may serve the same product details thousands of times while those details change only occasionally. Reading the database for every request wastes work. A cache keeps a temporary copy near the application — but that copy can go stale or disappear:

```text
GET /user/123 → cache miss → DB → cache SET (TTL 1h) → return
POST /user/123 → DB update → cache DEL → next read repopulates
```

## Definition

A **caching pattern** describes how an application, cache, and **source of truth** handle reads and writes. It answers three questions: who fills the cache, how writes reach the source, and how an old cached value stops being served.

> **Textbook Definition:** A caching pattern specifies how a derived copy of data is populated, read, updated, and invalidated relative to its authoritative source, defining both performance behavior and permitted staleness.

## First Principles

A copy cannot know its source changed unless someone delivers new information, validates it, or stops using the copy after an expiry. Fetching the authoritative value on every read would remove much of the saved work. Caching therefore exchanges repeated reads for a defined period or condition under which older data is acceptable.

A source update and cache update are usually two independent operations. Either can succeed while the other fails, and a reader can run between them. The write path needs recovery and ordering rules, not just two commands. If the system acknowledges a cache write before persistence elsewhere, it must also decide which failures can lose that acknowledged data. Measure hit rate and source-read cost against cache-hop latency and invalidation work — a low-hit cache can add a network call without relieving the source.

## 1. Fill on read: cache-aside and read-through

These six common patterns organize the fill/write choices; they are not an exhaustive taxonomy:

```text
                 who fills?      write path                          main trade-off
cache-aside      application     app writes source, then invalidates  stale window or cache miss
read-through     cache layer     depends on write strategy            loader is coupled to source
write-through    cache layer/app source and cache updated in request  partial failure needs recovery
write-behind     cache layer/app source updated asynchronously        accepted writes may be lost
refresh-ahead    cache layer     refresh before expiry                extra refresh work
write-around     application     writes bypass cache                  later reads may miss
```

**Cache-aside (lazy loading):** the application checks the cache first. On a miss it reads the database, populates the cache, and returns:

```text
GET /user/123
  → Cache: GET user:123 → miss
  → DB: SELECT * FROM users WHERE id = 123
  → Cache: SET user:123 = result, TTL 1h
  → Return result
```

On a write, the application updates the database, then invalidates:

```text
POST /user/123 (update)
  → DB: UPDATE users SET ... WHERE id = 123
  → Cache: DEL user:123 (invalidate)
```

Cache-aside is simple and application-controlled: the cache holds only what is actually read, and it works with any cache (Redis, Memcached, in-process). Costs: a miss penalty (database read plus population delays the first request), possible stale data if a write skips invalidation, and cache logic mixed into application code. **Useful when** the application owns loading and can define its invalidation and fallback policy.

**Read-through:** the cache layer loads from the authoritative database on a miss and returns cached copies on later reads — the database stays the source of truth:

```text
GET /user/123
  → Cache: GET user:123 → cache knows to load from DB on miss
  → Cache: load from DB, store, return
```

Unlike cache-aside, the application never talks to the database; the cache does. Application code stays simpler and load logic lives in the cache layer — but the cache library must know about the database (coupling), and loading plus cache-outage policies hide behind the cache interface while still needing explicit configuration. **Used by** some ORM-integrated caches (e.g. Hibernate L2 cache) and custom caching layers.

## 2. Write through the request path — or behind it

**Write-through:** a write updates database and cache as part of the request path, with defined order and recovery:

```text
POST /user/123 (update)
  → DB: UPDATE users SET ...
  → Cache: update or invalidate user:123
  → Return success only after required steps complete
```

Write-through can reduce stale reads when database and cache updates succeed in the intended order, with simpler invalidation (just write the new value) — at the cost of higher write latency (two writes), complex error handling, and a stale-cache risk when the cache update fails after the database commits (define invalidation and retry behavior). **Use when** the request can afford both writes and the application holds a recovery plan for partial failure. This pattern alone never guarantees strong consistency.

**Write-behind (write-back):** write to the cache, return success, and let the cache persist to the database in the background:

```text
POST /user/123 (update)
  → Cache: SET user:123 = new_value
  → Return success under the accepted-write durability contract
  → [Background] Cache: persist to DB (eventually)
```

Write-behind removes synchronous database work from the request path (actual latency depends on cache durability and acknowledgment) and can batch database writes — at the cost of **data-loss risk** (a cache dying before persisting loses data), write-queue/retry complexity, and harder debugging (writes happen async). **Use for** counters, analytics, and anything where eventual persistence is acceptable and low write latency matters. **Decision:** a deliberately lossy analytics aggregate may tolerate unpersisted updates; financial records or authoritative votes generally need a durable accepted-write contract. A five-second flush interval never caps loss at five seconds if persistence stays unavailable.

## 3. Refresh before expiry; skip the cache on write

**Refresh-ahead:** the cache proactively refreshes entries before they expire:

```text
At t=55min (TTL is 60min): cache async refreshes from DB
At t=60min: refreshed data remains available if refresh succeeded and installed a new expiry
```

Refresh-ahead can avoid an expiry miss when refresh succeeds before the old entry expires, with lower read latency — at the cost of complexity, wasted refreshes for unread keys, and refresh races. **Use for** high-traffic constantly-read keys, e.g. a popular product page or homepage.

**Write-around:** writes go to the database only; the cache populates on read:

```text
POST /user/123 (update)
  → DB: UPDATE users SET ...
  → [No cache fill; invalidate an existing entry if the freshness contract requires it]

GET /user/123
  → Cache: miss
  → DB: SELECT ...
  → Cache: SET user:123 = result
```

Write-around is simple, but an existing cache hit stays stale until invalidation, expiry, or validation: reading again never forces a reload, and the first read after a write pays a latency penalty. **Useful when** many written values are never read, so filling on every write wastes capacity. Existing entries still need the chosen invalidation policy.

## 4. Bound memory and lifetime separately

Capacity **eviction** chooses removals when memory is full; **expiration** stops serving an entry after its lifetime even with free memory. The two controls answer different questions — a pattern alone never guarantees freshness.

- **LRU (least recently used):** remove the longest-unaccessed entry. Adapts to access patterns (recent ≈ needed again) — but a scan of one-off keys can evict a frequently used key not accessed recently. Used by configured LRU caches; Redis supports several eviction policies, so inspect the instance's `maxmemory-policy` rather than assuming a default.
- **LFU (least frequently used):** remove the fewest-accessed entry. Fits skewed access (some keys very hot) — but without aging, historical frequency can dominate recent demand; some implementations decay frequencies. Used by Redis (`allkeys-lfu`) and specialized caches.
- **FIFO:** remove the oldest entry. Simple and predictable — but ignores access pattern, so a constantly accessed new key can be evicted. Used by specialized caches.
- **TTL (time-to-live):** stop serving an entry after its lifetime, regardless of access; physical reclamation may happen later. Bounds how long an installed entry may be served — but frequent hot-key expiration causes repeated reloads, and TTL alone is no memory budget: an incoming key rate can outpace expiration. Combine with an explicit expiration policy; caches can also use capacity eviction without per-entry TTL.
- **Random:** remove a random entry. Surprisingly competitive in some workloads with no metadata overhead — but can evict hot keys. Used by some theoretical algorithms.

In practice, many systems combine an eviction policy with per-key TTLs.

Invalidation needs an ordering and recovery contract between the source write, existing copies, and concurrent fills.

**TTL** suits a bounded stale-read window — but a delayed loader can install an already-old value with a fresh TTL, and stale-while-revalidate extends serving time, so include both in the maximum-age contract; authorization or inventory decisions may need a different validation boundary.

**Explicit invalidation on write** (`DEL` the key after the database write) removes the cached value so later reads repopulate from the new value — but a concurrent miss can read the old database value before the write commits and populate it after invalidation; use versioning, ordered invalidation, short TTLs, or another strategy if that stale window is unacceptable.

**Pub/sub invalidation** (publish on change; all cache nodes subscribe and invalidate) fits multi-node local caches — but delayed or lost notifications leave stale entries, and an ephemeral subscription can miss changes while disconnected; add expiry, replay, or validation when recovery matters.

**Version-based invalidation** caches a version and refreshes when it is no longer current — but an old cached version number alone never establishes freshness; validation and replacement must handle concurrent source writes atomically or define the remaining stale window.

Choose invalidation by the property the system can enforce: a time bound (TTL), a write ordering (explicit invalidation), a propagation channel (pub/sub), or an atomic replacement check (versioning).

## 5. Survive stampedes, poisoning, hot keys, and bloat

**Cache stampede (thundering herd):** a key expires and 1000 concurrent requests all miss, all hitting the database at once.

**Answers:** lock around the cache load so one request loads while others wait; probabilistic early refresh; background refresh (refresh-ahead); stale-while-revalidate (serve stale while one request refreshes).

Related: a delayed reader can refill an invalidated key with the version it loaded before the writer committed. Request coalescing reduces duplicate work but never orders that fill against the write.

Follow the canonical [refill race](../../../20-backend/20.8-caching/20.8.01-caching-deep-dive.md#event-based-invalidation) before promising a freshness guarantee.

**Cache poisoning:** an untrusted caller influences a representation that another caller later receives. Wrong cache identity or trusted-origin assumptions can cross authorization boundaries. Validate representations and their trusted origin before storing; include required identity and authorization scope in keys — a schema-valid value can still belong to the wrong tenant. Control request fields that affect an HTTP cache's key or stored response. A short TTL limits how long the bad copy is served, but it never prevents the exposure.

**Hot key:** one key takes a disproportionate traffic share and overloads its cache node. Replicate or split reads across cache nodes (defining how updates reach each copy); add an in-process cache for that key when its freshness contract permits another copy; measure per-key traffic — adding cache nodes never splits one key automatically.

**Memory bloat:** the cache grows unbounded. Set a memory limit with a workload-fitting eviction policy; add TTL only where the freshness contract permits expiry (TTL is no memory budget by itself); monitor memory use and eviction rate.

**Cache as source of truth:** treating cache as the database means cache loss is data loss. A disposable read cache must be rebuildable from its authority. If Redis owns sessions or acknowledged writes, treat it as an authoritative store and define persistence, replication, and recovery — the product name never makes its contents disposable. For write-behind, define durable intent, acknowledgment, retries, and recovery: Redis AOF or snapshots have configuration-dependent loss windows and never make the cache-to-database transfer atomic.

## 6. Layer caches and choose by contract

One possible read path:

```text
application → in-process object cache (L1)
            → shared network cache (L2)
            → database query → database buffer cache → storage as needed
```

An L1 hit skips network and database. An L2 hit skips the database query but still uses the network. PostgreSQL `shared_buffers` caches database pages; it is no query-result cache and skips no query execution. Each layer has its own keys, capacity, expiry, and invalidation scope. Measure actual hit latency and memory cost instead of assuming universal timings or that every lower layer is larger. Libraries also differ: Caffeine uses frequency-aware admission and recency management, while Redis offers configurable policies. Read-through and write-behind are application/library integrations, not six built-in commands supplied by every cache server. HTTP caches such as CDNs and Varnish follow request/response freshness and validation rules; never classify all their behavior as write-around.

| Scenario | Pattern | Why |
| ---------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **User profile, read-heavy** | Cache-aside | Simple, fits the use case |
| **Product catalog, read-heavy** | Cache-aside, optionally refresh-ahead | Define allowed price/stock staleness; background refresh alone does not guarantee freshness |
| **Loss-tolerant view estimate** | Write-behind with declared durability | Accept only the documented loss and duplicate window |
| **Session storage** | Authoritative session store or derived cache with explicit revocation policy | A caching pattern alone does not establish strong consistency |
| **Auth token validation** | Define revocation delay, then choose caching/validation | Lost invalidation cannot silently authorize access past the promised boundary |
| **Search results** | Cache-aside with query, authorization and index-version scope | Derived results change when indexed content or permissions change |
| **CDN static content** | HTTP freshness/validation, with versioned asset URLs where suitable | A response's cache directives and validators govern reuse; an application write pattern does not replace the HTTP contract |
| **GraphQL response cache** | Scope by operation, variables, schema and required caller identity | Equivalent query text can still produce different authorized results; invalidate affected data or bound its staleness |

## Summary

First decide whether the cache is a disposable copy or owns accepted state. For a disposable copy, name its authoritative source and rebuild path. Define the fill and write path, allowed staleness, and a separate capacity policy; then test the refill race, miss stampede, hot key and authorization boundaries that can violate those choices.

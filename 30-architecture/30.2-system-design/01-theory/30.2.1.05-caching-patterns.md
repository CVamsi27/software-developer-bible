# Caching Patterns

A product catalog may serve the same product details thousands of times while those details change only occasionally. Reading the database for every request wastes work. A cache keeps a temporary copy near the application, but that copy can become stale or disappear. This chapter explains how data moves between the cache and its source, and what each choice means for freshness and failure.

## Definition

A **caching pattern** describes how an application, cache and source of truth handle reads and writes. It answers three questions: who fills the cache, how writes reach the source, and how an old cached value stops being served.

These six common patterns organize those choices; they are not an exhaustive taxonomy:

```text
                 who fills?      write path                         main trade-off
cache-aside      application     app writes source, then invalidates  stale window or cache miss
read-through     cache layer     depends on write strategy            loader is coupled to source
write-through    cache layer/app  source and cache updated in request  partial failure needs recovery
write-behind     cache layer/app  source updated asynchronously        accepted writes may be lost
refresh-ahead    cache layer      refresh before expiry                extra refresh work
write-around     application     writes bypass cache                   later reads may miss
```

Two related choices also matter: the **eviction policy** decides what to remove when memory is full; the **invalidation mechanism** decides when a value is too old to serve. A pattern alone does not guarantee freshness.

> **Textbook Definition:** A caching pattern specifies how a derived copy of data is populated, read, updated, and invalidated relative to its authoritative source, defining both performance behavior and permitted staleness.


---

## First Principles

A copy cannot know that its source changed unless someone delivers new information, validates it, or stops using the copy after an expiry. Fetching the authoritative value on every read would remove much of the saved work. Caching therefore exchanges repeated reads for a defined period or condition under which older data is acceptable.

A source update and cache update are usually two independent operations. Either can succeed while the other fails, and a reader can run between them. The write path needs recovery and ordering rules, not just two commands. If the system acknowledges a cache write before persistence elsewhere, it must also decide which failures can lose that acknowledged data.

## Why it matters

Caching can reduce repeated work and database load when requests reuse the same data. The benefit depends on the workload, cache hit rate, network, and data size; measure it rather than assuming a fixed speedup. A cache also adds failure cases: stale reads, a burst of misses after expiry, and possible loss of unpersisted write-behind data.

## The 6 Caching Patterns

### 1. Cache-Aside (Lazy Loading)

**Pattern:** Application checks cache first. If miss, reads from DB, populates cache, returns.

```
GET /user/123
  → Cache: GET user:123 → miss
  → DB: SELECT * FROM users WHERE id = 123
  → Cache: SET user:123 = result, TTL 1h
  → Return result
```

**Write:**
```
POST /user/123 (update)
  → DB: UPDATE users SET ... WHERE id = 123
  → Cache: DEL user:123 (invalidate)
```

**Pros:**
- Simple, application-controlled
- Cache only contains what's actually read
- Works with any cache (Redis, Memcached, in-process)

**Cons:**
- Cache miss penalty (read DB, then populate cache — adds latency to first request)
- Stale data possible (if write doesn't invalidate cache)
- Application code has cache logic mixed in

**Useful when:** The application owns loading and can define its invalidation and fallback policy.

---

### 2. Read-Through

**Pattern:** The cache layer loads a value from the authoritative database on a miss and returns a cached copy on later reads. The database remains the source of truth.

```
GET /user/123
  → Cache: GET user:123 → cache knows to load from DB on miss
  → Cache: load from DB, store, return
```

**Difference from cache-aside:** the application doesn't talk to the DB. The cache does.

**Pros:**
- Application code is simpler
- Cache layer encapsulates the load logic

**Cons:**
- Cache library must know about the DB (coupling)
- Loading and cache-outage policies are hidden behind the cache interface; they still need explicit configuration

**Used by:** Some ORM-integrated caches (e.g., Hibernate L2 cache), some custom caching layers.

---

### 3. Write-Through

**Pattern:** A write updates the database and the cache as part of the request path. The exact order and recovery behavior must be defined.

```
POST /user/123 (update)
  → DB: UPDATE users SET ...
  → Cache: update or invalidate user:123
  → Return success only after required steps complete
```

**Pros:**
- Can reduce stale reads when the database update and cache update succeed in the intended order
- Simpler invalidation (just write the new value)

**Cons:**
- Higher write latency (two writes instead of one)
- If cache update fails after the database commits, a stale cache entry can remain; define invalidation and retry behavior
- More complex error handling

**Used by:** When the request can afford both writes and the application has a recovery plan for partial failure. This pattern alone does not guarantee strong consistency.

---

### 4. Write-Behind (Write-Back)

**Pattern:** Write to cache, return success. Cache asynchronously writes to DB in the background.

```
POST /user/123 (update)
  → Cache: SET user:123 = new_value
  → Return success under the accepted-write durability contract
  → [Background] Cache: persist to DB (eventually)
```

**Pros:**
- Removes synchronous database work from the request path; actual latency depends on cache durability and acknowledgment
- Can batch writes to DB (more efficient)

**Cons:**
- **Data loss risk** — if cache dies before persisting, data is lost
- Complex (needs write queue, retry logic, durability)
- Hard to debug (writes happen async)

**Used by:** Counters, analytics, anything where eventual persistence is OK and you need low write latency.

**Decision:** A deliberately lossy analytics aggregate may tolerate unpersisted updates. Financial records or authoritative votes generally need a durable accepted-write contract. A five-second flush interval does not cap loss to five seconds if persistence stays unavailable.

---

### 5. Refresh-Ahead

**Pattern:** Cache proactively refreshes entries before they expire.

```
At t=55min (TTL is 60min): cache async refreshes from DB
At t=60min: refreshed data remains available if refresh succeeded and installed a new expiry
```

**Pros:**
- Can avoid an expiry miss when refresh succeeds before the old entry expires
- Lower latency for reads

**Cons:**
- More complex
- Wasted refreshes for keys that aren't read
- Race conditions on refresh

**Used by:** High-traffic keys that are read constantly. E.g., a popular product page, the homepage.

---

### 6. Write-Around

**Pattern:** Write goes to DB only. Cache is populated only on read.

```
POST /user/123 (update)
  → DB: UPDATE users SET ...
  → [No cache fill; invalidate an existing entry if the freshness contract requires it]

GET /user/123
  → Cache: miss
  → DB: SELECT ...
  → Cache: SET user:123 = result
```

**Pros:**
- Simple

**Cons:**
- An existing cache hit remains stale until invalidation, expiry or validation; simply reading again does not force a reload
- Read latency penalty on first read after write

**Useful when:** Many written values may never be read, so filling on every write would waste cache capacity. Existing entries still need the chosen invalidation policy.

---

## Capacity Eviction and Expiration

Capacity eviction chooses which entries to remove when the cache exceeds its memory budget. Expiration stops serving an entry after its lifetime ends, even when free memory remains. The two controls answer different questions.

### LRU (Least Recently Used)

**Algorithm:** Remove the entry that hasn't been accessed for the longest time.

**Pros:** Adapts to access patterns. Recent = likely to be needed again.

**Cons:** A scan of many one-off keys can evict a frequently used key that was not accessed recently.

**Used by:** A configured cache using an LRU eviction policy, for example. Redis supports several eviction policies; the active policy depends on its configuration.

### LFU (Least Frequently Used)

**Algorithm:** Remove the entry with the fewest accesses.

**Pros:** Good for skewed access (some keys are very hot).

**Cons:** Without aging, historical frequency can dominate recent demand. Some implementations decay frequencies.

**Used by:** Redis (`allkeys-lfu`), some specialized caches.

### FIFO (First In, First Out)

**Algorithm:** Remove the oldest entry.

**Pros:** Simple, predictable.

**Cons:** Doesn't account for access pattern. A new key that's accessed constantly could be evicted.

**Used by:** Some specialized caches.

### TTL (Time-To-Live)

**Algorithm:** Remove entries after a fixed time, regardless of access.

**Pros:** Bounds how long that installed entry may be served after insertion, under the stated expiry policy.

**Cons:** Frequent expiration of hot keys creates repeated reloads. TTL alone is not a memory budget: an incoming key rate can outpace expiration.

**Use with:** An explicit expiration policy; caches can also use capacity eviction without per-entry TTL.

### Random

**Algorithm:** Remove a random entry.

**Pros:** Surprisingly competitive in some workloads. No metadata overhead.

**Cons:** Can evict hot keys.

**Used by:** Some theoretical/paper algorithms.

**In practice:** Many systems combine an eviction policy with per-key TTLs. Redis supports several policies, so inspect the instance's configured `maxmemory-policy` rather than assuming one default.

## Cache Invalidation Strategies

Invalidation needs an ordering and recovery contract between the source write, existing copies and concurrent fills.

### 1. TTL (Time-to-Live)

**Pattern:** Each cache entry has an expiry. After expiry, cache miss, read from DB, populate.

**Pros:** Simple expiration of an installed entry. It bounds data age only if the loader, refresh and stale-serving policies also bound age.

**Cons:** A delayed loader can insert an already-old value with a fresh TTL; stale-while-revalidate can extend serving time. Account for those paths when defining maximum data age.

**Useful when:** The operation permits a stated stale-read window and the complete loading/serving path can meet it. Authorization or inventory decisions may require a different validation boundary.

### 2. Explicit invalidation on write

**Pattern:** When you write to the DB, also `DEL` the cache key.

**Pros:** Removes the cached value after the database write, so later reads usually repopulate from the new value.

**Cons:** A concurrent cache miss can read the old database value before the write commits and populate it after invalidation. Use versioning, ordered invalidation, short TTLs or another strategy if this stale window is unacceptable.

**When to use:** When stale data would be very bad (e.g., user just changed their email, must not see the old one).

### 3. Write-through

The request path updates the source and cache. If one update succeeds and the other fails, they can disagree. Define which write is authoritative, when to return success, and how to invalidate or repair a stale cache entry. “Write-through” alone does not make the two stores atomic.

### 4. Pub/Sub invalidation

**Pattern:** When data changes, publish to a topic. All cache nodes subscribe and invalidate their local copy.

**Pros:** Works for multi-node caches.

**Cons:** Delayed or lost notifications can leave stale entries; an ephemeral subscription can miss changes while disconnected. Add expiry, replay or validation when recovery matters.

**When to use:** Multiple application instances need to invalidate local cached copies after a change. Use a pub/sub system that all instances can consume; the cache itself may not provide this mechanism.

### 5. Version-based invalidation

**Pattern:** Cache entry includes a version. On read, check if version is still current. If not, refresh.

**Pros:** Can reject older entries when compared against an authoritative version under the required read contract.

**Cons:** An old cached version number cannot establish freshness by itself. Validation and replacement must handle concurrent source writes atomically or define the remaining stale window.

## Cache Anti-Patterns

### 1. Cache Stampede (Thundering Herd)

**Problem:** Cache key expires. 1000 concurrent requests all miss, all hit the DB.

```
t=0: cache key expires
t=1ms: 1000 requests arrive, all miss
t=2ms: 1000 requests hit the DB simultaneously
t=2ms: DB overloaded
```

**Solutions:**
- **Lock around the cache load:** only one request loads, others wait
- **Probabilistic early refresh:** some requests refresh before expiry
- **Background refresh:** cache refreshes before expiry (refresh-ahead pattern)
- **Stale-while-revalidate:** serve stale data while one request refreshes

### Why deletion after commit can still return old data

A delayed reader can refill an invalidated key with the version it loaded before the writer committed. Request coalescing reduces duplicate work but does not order that fill against the write. Follow the canonical [refill race](../../../20-backend/20.8-caching/20.8.01-caching-deep-dive.md#event-based-invalidation) before promising a freshness guarantee.

### 2. Stale data after write

**Problem:** Write to DB, but cache still has old value.

**Solutions:**
- Write-through with explicit partial-failure recovery
- Explicit invalidation on write (DEL the cache key)
- Shorter TTL (faster recovery, but more cache misses)

### 3. Cache Poisoning

**Problem:** An untrusted caller influences a representation that another caller later receives. Wrong cache identity or trusted-origin assumptions can cross authorization boundaries.

**Solutions:**
- Validate representations and their trusted origin before storing them
- Include the required identity and authorization scope in keys; a schema-valid value can still belong to the wrong tenant
- Control request fields that affect an HTTP cache's key or stored response; short TTL limits duration but does not prevent exposure

### 4. Hot Key

**Problem:** One cache key gets 90% of traffic. That one Redis node becomes the bottleneck.

**Solutions:**
- Replicate the key across multiple cache nodes
- Read from multiple replicas (load balance within the cache)
- In-process cache (L1) for that specific key

### 5. Memory bloat

**Problem:** Cache grows unbounded.

**Solutions:**
- Max memory policy (LRU, LFU)
- TTL on every key
- Monitor memory usage

### 6. Cache as source of truth

**Problem:** Treating cache as the DB. If cache loses data, you lose data.

**Solutions:**
- A disposable read cache must be rebuildable from its authority
- If Redis owns sessions or acknowledged writes, treat it as an authoritative store and define persistence, replication and recovery; the product name does not make its contents disposable
- For write-behind, define durable intent, acknowledgment, retries and recovery. Redis AOF or snapshots have configuration-dependent loss windows and do not make the cache-to-database transfer atomic.

## Multi-level Caching

One possible read path is:

```text
application → in-process object cache (L1)
            → shared network cache (L2)
            → database query → database buffer cache → storage as needed
```

An L1 hit skips the network and database. An L2 hit skips the database query but still uses the network. PostgreSQL `shared_buffers` caches database pages; it is not a query-result cache and does not skip query execution. Each layer has its own keys, capacity, expiry and invalidation scope. Measure the actual hit latency and memory cost instead of assuming universal timings or that every lower layer is larger.

Libraries also differ: Caffeine uses frequency-aware admission and recency management, while Redis offers configurable policies. Read-through and write-behind are application/library integrations, not six built-in commands supplied by every cache server. HTTP caches such as CDNs and Varnish follow request/response freshness and validation rules; do not classify all their behavior as write-around.

## Choose from the Required Read and Write Contract

| Scenario | Pattern | Why |
| ---------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **User profile, read-heavy** | Cache-aside | Simple, fits the use case |
| **Product catalog, read-heavy** | Cache-aside, optionally refresh-ahead | Define allowed price/stock staleness; background refresh alone does not guarantee freshness |
| **Loss-tolerant view estimate** | Write-behind with declared durability | Accept only the documented loss and duplicate window |
| **Session storage** | Authoritative session store or derived cache with explicit revocation policy | A caching pattern alone does not establish strong consistency |
| **Auth token validation** | Define revocation delay, then choose caching/validation | Lost invalidation cannot silently authorize access past the promised boundary |
| **Search results** | Cache-aside with query, authorization and index-version scope | Derived results change when indexed content or permissions change |
| **CDN static content** | HTTP freshness/validation, with versioned asset URLs where suitable | A response's cache directives and validators govern reuse; an application write pattern does not replace the HTTP contract |
| **GraphQL response cache** | Scope by operation, variables, schema and required caller identity | Equivalent query text can still produce different authorized results; invalidate affected data or bound its staleness |

---

## Summary

A cache keeps a copy of data for faster reads. Decide who fills it, what happens after a write, how long old values may be served, and how entries are removed when memory is full. Cached data can be stale, so the product must define which operations can tolerate that. Watch for many requests rebuilding the same missing value, one key receiving most traffic, and untrusted input poisoning entries.

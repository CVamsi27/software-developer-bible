# Message Queues & Async Patterns

Suppose an API saves a report request, but building the report takes longer than a user should wait. It can return a job ID and let a worker build the report afterward. A queue can hold that work between the API and worker; the design must still explain when the job is durable, how retries behave, and how the user learns the result.

## Definition

A **message queue** holds work between a producer and a consumer so they do not have to run at the same time. Whether a message survives a process or broker failure depends on the product and its configuration. Producers may wait for an acknowledgment, and consumers process messages at the rate the system can sustain.

Formally it is a buffer with three defining properties:

1. **Temporal decoupling** — a producer can hand off work for a consumer to process later, subject to the broker's retention and availability settings.
2. **A delivery contract** — at-most-once may lose work; at-least-once can repeat it. Some brokers offer exactly-once delivery or transactions within defined scopes. Those features do not automatically make an external database write, email, or payment occur once; consumers still need an effect-level recovery plan.
3. **A topology** — point-to-point distributes work among consumers; publish-subscribe makes a copy available to each subscription. Ordering, priority and delay are product-specific options, not properties every queue provides.

What a queue adds beyond a function call is **buffering** and, in many systems, **redelivery**. It can absorb a short burst only while storage and retention limits allow; sustained overload still needs more capacity, backpressure or load shedding. Failures surface later, and messages may be repeated or require a dead-letter policy.

> **Textbook Definition:** A message queue mediates asynchronous communication by buffering messages between producers and consumers under defined contracts for acknowledgment, durability, ordering, and redelivery.


---

## First Principles

Queues convert "must answer now" into "will process eventually" — the decoupling follows mechanically:

1. **Synchronous chains fail at the rate of their slowest link.** Checkout calling inventory calling email means email's latency *is* checkout's latency — and email's outage *is* checkout's outage. Inserting a queue cuts the dependency: producers finish when the broker accepts.
2. **The price is deferred truth.** The user's confirmation no longer proves the work happened — so the UI contract changes (pending states), and delivery semantics (at-least-once + idempotent consumers, → 20.6.2.05) become part of correctness, not ops hygiene.
3. **Queue depth is the system's pressure gauge.** Growing depth = producers outpace consumers = capacity signal (scale consumers or shed load); An empty queue can mean consumers keep up with demand; it does not prove over-provisioning. Age of the oldest job, arrival/service rates, retries and retention reveal whether buffering remains safe.

## Why it matters

When a task exceeds the request deadline or useful interactive wait, the application can:

1. **Acknowledge the user fast** (return "we got it, processing")
2. **Process asynchronously** (worker picks up the job, runs in the background)
3. **Notify on completion** (webhook, email, push notification, polling)

Asynchronous work can free a request from waiting for a slow task, but it adds queueing, retries and eventual-consistency behavior. Use it when the user experience, timeout limits or workload shape justify those costs; short predictable work can remain synchronous.

## Sync vs Async

### Synchronous

```
Client → API → Service → Response
         (client blocks the whole time)
```

**Latency:** includes the critical path of calls; parallel calls do not simply add
**Failure mode:** required dependencies can fail the request; optional branches can have a defined fallback
**Throughput:** limited by the slowest service
**Use when:** the user needs the response in the request (e.g., "GET /user/profile")

### Asynchronous

```
Client → API → Queue → Response (immediate: "we got it")
            │
            └──→ Worker (background) → Service → Done
                  (notify user via webhook/poll)
```

**Latency:** request is fast, processing happens later
**Failure mode:** worker failure is decoupled from the original request, but recovery depends on the broker's retry, acknowledgment and dead-letter configuration.
**Throughput:** queue absorbs spikes
**Use when:** deferred completion fits the product and durability contract (e.g., "send email", "process payment")

## Queue Types

### 1. Competing consumers (work queue)

**Pattern:** Each delivery goes to an eligible worker. Retries can deliver the same logical message again; FIFO ordering is a separate broker option.

```
Producer → Queue → Consumer 1
                    (only one gets the message)
```

**Used for:** task distribution (any worker can do it), load balancing across workers.

**Examples:** SQS queues, RabbitMQ queues, Kafka partitions shared by a consumer group

### 2. Pub/Sub (Topic)

**Pattern:** One producer publishes to a topic; each configured subscription can receive its own copy. How consumers share work within a subscription depends on the broker.

```
Producer → Topic → Consumer 1 (gets the message)
                → Consumer 2 (gets the message)
                → Consumer 3 (gets the message)
```

**Used for:** event broadcasting (notify multiple services), fan-out.

**Examples:** Kafka with separate consumer groups, RabbitMQ fanout exchanges, SNS subscriptions, Google Pub/Sub subscriptions

### 3. Priority Queue

**Pattern:** Higher-priority messages are processed first.

```
Queue:
  - High priority: [msg1, msg2]
  - Normal: [msg3, msg4, msg5, msg6]
  - Low: [msg7, msg8]
```

**Used for:** VIP users, urgent jobs, throttling by user tier.

### 4. Delay Queue

**Pattern:** Messages are not visible to consumers until a delay has passed.

**Used for:** scheduled tasks, retries with backoff, deferred notifications.

**Examples:** SQS delay queues, RabbitMQ TTL with a dead-letter exchange, or a scheduler that releases work at a chosen time

## Delivery Guarantees

The **at-least-once / at-most-once / exactly-once** spectrum.

### At-most-once

**Guarantee:** Message is delivered 0 or 1 times. May be lost.

**How:** One possible policy does not retry uncertain sends, or a consumer acknowledges/removes work before processing. A broker-specific acknowledgment can still exist; at-most-once does not mean every layer sends no acknowledgment.

**Pros:** Fast, simple.

**Cons:** Can lose messages. Not OK for most use cases.

**When to use:** Metrics, logs, anything where occasional loss is OK.

### At-least-once

**Guarantee:** Message is delivered 1 or more times. May be duplicated.

**How:** Producers can retry an uncertain send; consumers acknowledge only after successful processing so retained work can be redelivered. Both boundaries need a documented retry/retention policy.

**Pros:** Redelivery can recover from a missing acknowledgment when the broker retains the message and retries within its configured policy.

**Cons:** Can have duplicates. Consumer must be idempotent.

**When to use:** A common choice when losing work is unacceptable and consumers can handle duplicates. Whether it is the default depends on broker and acknowledgment configuration.

### Exactly-once

**Guarantee:** Some brokers offer exactly-once delivery within a defined scope and configuration. This does not generally guarantee that an arbitrary external side effect happens only once.

**How:** Often implemented as deduplicated processing within a broker or transaction boundary. For an external effect such as charging a payment provider, use an idempotency key or another application-level correctness mechanism.

**Pros:** Can prevent duplicate delivery within the documented scope.

**Cons:** Scope and configuration matter. It does not remove the need to plan for broker outages, retention limits, or duplicates at system boundaries.

**When to use:** When the documented broker/transaction scope matches the operation. External payment effects still need stable provider identity and reconciliation.

**In interviews:** say "at-least-once delivery with idempotent consumer (effectively-once semantics)".

## Idempotency

**Plan for duplicates.** Retries, lost acknowledgments and redelivery can cause the same logical message to be processed more than once, depending on the broker and failure boundary. Make effects idempotent where repeats would be harmful.

**Idempotency strategies:**

### 1. Idempotency Key

A stable message identity represents one logical effect across retries. For a local database effect, record that identity and the effect in the **same transaction**:

```text
BEGIN
  claim message ID using a unique processed-message key
  if the claim already exists: skip the already-committed effect
  otherwise: apply the local business change
COMMIT
acknowledge the broker delivery
```

If the worker crashes before commit, both changes roll back and redelivery can retry. If it crashes after commit but before acknowledgment, redelivery sees the committed identity and skips the effect. A separate `exists → effect → set` sequence has a crash window and permits concurrent workers to repeat the effect.

A payment provider is outside that local transaction. Persist the payment intent, send the provider's supported idempotency identity and reconcile uncertain outcomes before deciding whether to retry or compensate. A Redis marker written after charging cannot close the successful-charge-before-marker crash window.

### 2. Idempotent operation

An operation that replaces a value can be idempotent under repetition of the same command, whereas incrementing can repeat the effect. Replacement still needs a version/order rule so an old retry cannot overwrite a newer balance.

### 3. Database constraints

Use unique constraints to prevent duplicates. `INSERT ... ON CONFLICT DO NOTHING`.

### 4. Optimistic locking

A version check can reject a stale update. If zero rows are affected, determine whether the operation already happened or a competing update won; blindly retrying or skipping does not establish the intended effect.

## Ordering

Broker log/delivery order and effect-completion order are different. State the queue/partition contract; parallel tasks, retries and redelivery can change completion order.

**Per-partition ordering:** Kafka guarantees ordering within a partition. Partition by aggregate ID (e.g., user_id), all messages for one user go to one partition, processed by one consumer.

**Example:**
```
Topic with 4 partitions:
  Partition 0: [user_1_msg1, user_1_msg3, user_1_msg5]
  Partition 1: [user_2_msg2, user_2_msg4]
  Partition 2: [user_3_msg1, user_3_msg2]
  Partition 3: [user_4_msg1, user_4_msg2, user_4_msg3, user_4_msg4]

In one consumer group, a partition is assigned to one consumer at a time. That consumer must also control its own parallel tasks if effect order matters.
Within a partition: ordered.
Across partitions: no global order.
```

**When to use:** Per-key ordering when an aggregate needs it. Global ordering can be implemented, but concentrates sequencing and reduces available parallelism; require it only for an actual invariant.

## Dead Letter Queue (DLQ)

**What:** An optional recovery destination for messages that meet a configured failure condition, such as exhausting a retry limit. Some systems require application or broker configuration to create and route to one.

```
Main Queue → Consumer fails 3 times → DLQ
                                       ↓
                                  Manual investigation
```

**Why:** A poison message may repeatedly fail and delay later work. A DLQ can isolate it so processing continues, but the system still needs monitoring and a replay or discard policy.

**What to do with DLQ messages:**
- Log them for investigation
- Set up alerts (DLQ depth > 0 is a problem)
- Have a manual review process
- Possibly retry them later (after fixing the bug)

## Retry Strategies

When a consumer fails, what next?

### 1. Immediate retry

**Pattern:** Retry the same message N times in a tight loop.

**Pros:** Catches transient failures (network blip).

**Cons:** If the failure is persistent, you waste time.

### 2. Exponential backoff

**Pattern:** Retry after `delay = base * 2^attempt + jitter`.

**Pros:** Gives the system time to recover.

**Cons:** Can be slow (delays grow exponentially).

**Example:** 1s, 2s, 4s, 8s, 16s, 32s, give up.

### 3. Retry with jitter

**Pattern:** Like exponential backoff, but add random jitter to prevent thundering herd.

**Why:** if 1000 messages all fail at once, they all retry at the same time. Adding jitter spreads them out.

### 4. Retry queue

**Pattern:** Failed message goes to a "retry" queue with a delay. After delay, it goes back to the main queue.

**Pros:** Don't block the consumer.

**Cons:** More complex.

---

## Backpressure

When the queue grows faster than consumers can process:

**Solutions:**

- **Scale up consumers:** add more workers. Kafka consumer groups allow this.
- **Slow the producer:** rate-limit producers, or use a token bucket.
- **Drop messages:** for non-critical queues (metrics, logs), drop if queue is too long.
- **Alert:** if queue depth > threshold, page on-call.

## Common Patterns

### Saga (recoverable local transactions)

For multi-step business processes that span services:

```
Order Service → emits "order_created"
Inventory Service → consumes, reserves stock, emits "stock_reserved"
Payment Service → consumes, charges card, emits "payment_charged"
Order Service → consumes both, marks order as "confirmed"

If any step fails → compensating actions in reverse:
Inventory Service → consumes "payment_failed", releases stock
```

See [Microservices/03 Saga Pattern](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.01-saga-pattern.md).

### Event Sourcing

Store every state change as an event, not just the current state.

```
Account created → balance=0
Deposit $100 → balance=$100
Withdraw $30 → balance=$70
```

To get current state, replay all events. Auditable, time-travel debug.

See [Microservices/07 Event Sourcing](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.03-event-sourcing.md).

### CQRS (Command Query Responsibility Segregation)

Separate the read and write models.

```
Write model: optimized for writes (Postgres)
Read model: optimized for reads (Elasticsearch, Redis, denormalized)

Write → publish event → read model subscribes and updates
```

See [Microservices/13 Cqrs](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.04-cqrs.md).

## Anti-patterns

- **No duplicate protection for a non-idempotent effect.** A redelivery can repeat a charge or other business action unless the consumer or receiving provider recognizes the operation identity.
- **No recovery policy for poison messages.** A DLQ may help, but some workloads use bounded retries, quarantine tables, or explicit rejection instead.
- **Sync API for slow work.** User waits 30 seconds. Bad UX.
- **No retry strategy.** Transient failure = permanent loss.
- **No backpressure.** Queue grows unbounded, runs out of disk, dies.
- **Tight coupling between producer and consumer.** Use a contract (event schema, version).
- **Global ordering without an invariant.** It concentrates sequencing; prefer per-aggregate order when it supplies the required contract.
- **No monitoring.** Queue depth, processing time, error rate. Alert on anomalies.
- **Tight retry loops without backoff.** Causes thundering herd.

---

## Summary

A queue lets one part of a system accept work while another processes it later. Choose whether messages need replay, broadcast, per-key ordering or priority. Messages may be delivered again after failures, so handlers should safely recognize repeated work. Define retry limits, recovery for jobs that keep failing, and which updates must commit together.

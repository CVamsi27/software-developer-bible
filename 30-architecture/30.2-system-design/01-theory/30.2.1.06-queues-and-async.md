# Message Queues & Async Patterns

Suppose an API saves a report request, but building the report takes longer than a user should wait. It can return a job ID and let a worker build the report afterward. A queue holds that work between API and worker — but the design must still explain when the job is durable, how retries behave, and how the user learns the result:

```text
POST /reports → 202 + job ID (durable) → worker builds → user polls status.
```

## Definition

A **message queue** holds work between a producer and a consumer so they need not run at the same time. Whether a message survives a process or broker failure depends on the product and its configuration. Producers may wait for an acknowledgment, and consumers process messages at the rate the system can sustain.

> **Textbook Definition:** A message queue mediates asynchronous communication by buffering messages between producers and consumers under defined contracts for acknowledgment, durability, ordering, and redelivery.

## First Principles

The request and the deferred job have different completion boundaries:

1. **A required call extends the request's critical path.** If checkout waits for email, an email delay or failure can delay or fail checkout. A durable handoff moves that wait to a worker; the request still depends on successfully recording the handoff.
2. **Acceptance is weaker than completion.** Return a job identity, expose pending/success/terminal failure/expiration, and let the caller check or receive the outcome. Retention, retries, and available workers determine whether accepted work completes; a queue alone cannot promise it will.
3. **Buffering does not create processing capacity.** If accepted work persistently arrives faster than it completes, backlog and waiting time grow. Measure oldest-job age and arrival/completion rates, then bound admission, retention, and retries. Empty storage never proves over-provisioning; work may be in flight.

## How It Works

Specify three parts of the handoff contract. **Temporal decoupling** — a producer hands off work for later processing, subject to the broker's retention and availability. A **delivery contract** — at-most-once may lose work; at-least-once can repeat it; some brokers offer exactly-once delivery or transactions within defined scopes, which never automatically make an external database write, email, or payment occur once, so consumers still need an effect-level recovery plan. A **topology** — point-to-point distributes work among consumers; publish-subscribe makes a copy available to each subscription. Ordering, priority, and delay are product-specific options, never properties every queue provides.

What a queue adds beyond a function call is **buffering** and, in many systems, **redelivery**. It can absorb a short burst only while storage and retention limits allow; sustained overload still needs more capacity, backpressure, or load shedding. Failures surface later, and messages may repeat or require a dead-letter policy.

### 1. Separate acceptance from completion

**Synchronous:**

```text
Client → API → Service → Response
         (client blocks the whole time)
```

Latency includes the critical path of calls; parallel calls do not simply add. Required dependencies can fail the request; optional branches can carry a defined fallback. Throughput depends on each required service's capacity and how much work one request causes there; latency alone never determines capacity. **Use when** the user needs the response in the request (e.g. `GET /user/profile`).

**Asynchronous:**

```text
Client → API → Queue → Response (immediate: "we got it")
            │
            └──→ Worker (background) → Service → Done
                  (notify user via webhook/poll)
```

The request waits for the acceptance boundary; job latency also includes queueing, processing, and retries. Worker failure is decoupled from the original request, but recovery depends on the broker's retry, acknowledgment, and dead-letter configuration. Buffering absorbs bounded spikes; sustained completion rate stays limited by workers and their dependencies. **Use when** deferred completion fits the product and durability contract (e.g. "send email", "process payment").

Trace acceptance before processing: the API accepts report request R and returns its job ID after the handoff becomes durable. A worker receives R, creates the result, and commits completion before acknowledging delivery. If acknowledgment is lost, redelivery must recognize R's completed effect. If the worker never completes within the product deadline, the status must expose failure or expiration rather than staying pending indefinitely. If acceptance updates an application database and separately publishes to a broker, a crash between those actions leaves a saved request with no queued job — use the [transactional outbox](30.2.1.18-outbox-and-cdc.md) or another explicit recovery protocol for that boundary. Broker acknowledgment alone cannot atomically commit an unrelated application database.

### 2. Choose a topology: work queue, pub/sub, priority, delay

**Competing consumers (work queue):** each delivery goes to an eligible worker. Retries can deliver the same logical message again; FIFO ordering is a separate broker option.

```text
Producer → Queue → Consumer 1
                    (only one gets the message)
```

**Used for** task distribution (any worker can do it) and load balancing across workers. **Examples:** SQS and RabbitMQ queues; Kafka topic partitions shared by a consumer group (with retained-log semantics).

**Pub/sub (topic):** one producer publishes to a topic; each configured subscription receives its own copy. How consumers share work within a subscription depends on the broker:

```text
Producer → Topic → Consumer 1 (gets the message)
                → Consumer 2 (gets the message)
                → Consumer 3 (gets the message)
```

**Used for** event broadcasting (notify multiple services) and fan-out. **Examples:** Kafka with separate consumer groups, RabbitMQ fanout exchanges, SNS subscriptions, Google Pub/Sub subscriptions.

**Priority queue:** prefer eligible higher-priority messages when selecting new work, per the broker's policy. Priority normally never preempts an executing task; prefetched deliveries and retries can also affect observed order. Reserve capacity or limit high-priority traffic to avoid starving ordinary jobs.

```text
Queue:
  - High priority: [msg1, msg2]
  - Normal: [msg3, msg4, msg5, msg6]
  - Low: [msg7, msg8]
```

**Used for** VIP users, urgent jobs, throttling by user tier.

**Delay queue:** messages stay invisible to consumers until a delay passes. **Used for** scheduled tasks, retries with backoff, deferred notifications. **Examples:** SQS delay queues, RabbitMQ TTL with a dead-letter exchange, or a scheduler releasing work at a chosen time.

### 3. Name the delivery guarantee precisely

**At-most-once:** delivered 0 or 1 times; may be lost. One possible policy never retries uncertain sends, or a consumer acknowledges/removes work before processing. A broker-specific acknowledgment can still exist; at-most-once never means every layer sends no acknowledgment. Avoids redelivery and duplicate-tracking work when loss is acceptable — but can lose messages, so it never satisfies a requirement to recover every accepted job. **Use for** metrics, logs, anything where occasional loss is OK.

**At-least-once:** accepted, retained work is delivered one or more times under the protocol's availability and progress assumptions. Processing may duplicate; retention expiry or terminal retry policy still needs an explicit outcome. Producers can retry an uncertain send; consumers acknowledge only after successful processing so retained work can be redelivered — both boundaries need a documented retry/retention policy. Redelivery can recover from a missing acknowledgment when the broker retains the message and retries within its configured policy — but duplicates follow, so the consumer must be idempotent. **A common choice** when losing work is unacceptable and consumers handle duplicates. Whether it is the default depends on broker and acknowledgment configuration.

**Exactly-once:** some brokers offer exactly-once delivery within a defined scope and configuration. This never generally guarantees an arbitrary external side effect happens only once. Often implemented as deduplicated processing within a broker or transaction boundary. For an external effect such as charging a payment provider, use an idempotency key or another application-level correctness mechanism. Prevents duplicate delivery within the documented scope — but scope and configuration matter, and broker outages, retention limits, and boundary duplicates still need planning. **Use when** the documented broker/transaction scope matches the operation; external payment effects still need stable provider identity and reconciliation.

Name the boundary precisely: for example, "a redeliverable message, with one committed local database effect per stable message identity." The phrase "effectively once" is useful only after explaining the identity, atomic write, and recovery rules establishing it.

### 4. Make effects safe under redelivery

**Plan for duplicates.** Retries, lost acknowledgments, and redelivery can process the same logical message more than once, depending on broker and failure boundary. Make effects idempotent where repeats would harm.

**Idempotency key:** a stable message identity represents one logical effect across retries. For a local database effect, record that identity and the effect in the **same transaction**:

```text
BEGIN
  claim message ID using a unique processed-message key
  if the claim already exists: skip the already-committed effect
  otherwise: apply the local business change
COMMIT
acknowledge the broker delivery
```

If the worker crashes before commit, both changes roll back and redelivery retries. If it crashes after commit but before acknowledgment, redelivery sees the committed identity and skips the effect. A separate `exists → effect → set` sequence holds a crash window and lets concurrent workers repeat the effect. A payment provider sits outside that local transaction: persist the payment intent, send the provider's supported idempotency identity, and reconcile uncertain outcomes before deciding to retry or compensate. A Redis marker written after charging cannot close the successful-charge-before-marker crash window.

**Idempotent operation:** replacing a value can be idempotent under repetition of the same command, whereas incrementing repeats the effect. Replacement still needs a version/order rule so an old retry cannot overwrite a newer balance.

**Database constraints:** use unique constraints to prevent duplicates: `INSERT ... ON CONFLICT DO NOTHING`.

**Optimistic locking:** a version check can reject a stale update. If zero rows are affected, determine whether the operation already happened or a competing update won; blindly retrying or skipping never establishes the intended effect.

### 5. Order per key; recover poison with DLQ, retries, and backpressure

Broker log/delivery order and effect-completion order differ. State the queue/partition contract; parallel tasks, retries, and redelivery can change completion order. **Per-partition ordering:** Kafka orders records in each partition. A stable aggregate key and partitioning rule keeps one aggregate's records together. Changing the partition count or routing rule can move later records to another partition; plan the migration if cross-change ordering matters. Consumer assignment and ordered effect completion remain separate concerns:

```text
Topic with 4 partitions:
  Partition 0: [user_1_msg1, user_1_msg3, user_1_msg5]
  Partition 1: [user_2_msg2, user_2_msg4]
  Partition 2: [user_3_msg1, user_3_msg2]
  Partition 3: [user_4_msg1, user_4_msg2, user_4_msg3, user_4_msg4]

In one consumer group, a partition is assigned to one consumer at a time. That consumer must also control its own parallel tasks if effect order matters.
Within a partition: ordered.
Across partitions: no global order.
```

**Use** per-key ordering when an aggregate needs it. Global ordering can be implemented, but concentrates sequencing and reduces available parallelism; require it only for an actual invariant.

**Dead-letter queue (DLQ):** an optional recovery destination for messages meeting a configured failure condition, such as exhausting a retry limit. Some systems require application or broker configuration to create and route to one:

```text
Main Queue → Consumer fails 3 times → DLQ → Manual investigation
```

A poison message may repeatedly fail and delay later work. A DLQ can isolate it so processing continues — but the system still needs monitoring and a replay or discard policy. Log DLQ messages for investigation; alert on unexpected failures, aging unresolved jobs, and product deadlines (a recovery queue with deliberately quarantined work need not page on every item); keep a manual review process; possibly retry later after fixing the bug.

**Retry strategies:** immediate retry catches transient failures (network blip) in a tight loop — but wastes time on persistent failures. **Exponential backoff** increases the delay between eligible attempts, with a cap, maximum attempt count, and overall deadline; retry only recoverable failures, since malformed input or a permanently rejected operation needs a terminal outcome (e.g. 1s, 2s, 4s, 8s, 16s, 32s, give up). **Jitter** spreads correlated retries: if 1000 messages fail at once, identical backoff retries them all at once. A **retry queue** moves a failed message to a delayed queue that returns it to the main queue later — never blocking the consumer, at the cost of complexity.

**Backpressure:** when the queue grows faster than consumers process, add workers if the downstream dependency has headroom (a Kafka group's useful partition concurrency is bounded by available partitions — idle extra consumers add nothing); slow the producer with rate limits or a token bucket; drop messages for non-critical queues (metrics, logs) when the queue runs too long; alert on sustained backlog age and missed completion objectives with capacity/runbook context — queue depth alone never distinguishes a harmless burst from urgent failure.

### 6. Verify broker contracts before choosing one

Product names never establish delivery or ordering guarantees. Confirm the configured mode and failure boundary before choosing a broker:

| System | Contract to verify |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Kafka** | A consumer group shares topic partitions; records are ordered per partition, though concurrent consumer work can complete out of order. With transactions and `read_committed`, consumed offsets and produced Kafka records can commit together. An external database is outside that transaction. |
| **RabbitMQ** | Consumer acknowledgments control requeue after failure. Publisher confirms let a producer know the broker accepted a publish under the configured queue/durability contract. Multiple consumers, prefetch and requeue can change the order in which effects complete. |
| **Amazon SQS** | Standard queues can redeliver and reorder. FIFO queues order within a message group and suppress duplicate sends within a five-minute deduplication window; consumers still need safe effect handling. |
| **Amazon SNS** | Standard topics can duplicate or reorder. FIFO topics preserve order within a message group for compatible FIFO subscriptions; separate subscribers do not share a global processing order. |
| **Google Pub/Sub** | At-least-once delivery is the default. Exactly-once is limited to supported pull subscriptions within a region; ordered delivery needs an ordering key and subscription configuration. |
| **Redis Streams** | Consumer groups track delivered-but-unacknowledged entries. Acknowledgment clears a pending reference; stream retention and trimming are separate decisions. |
| **NATS** | Core NATS delivers only to currently connected subscribers and does not replay missed messages. JetStream can add persistence, replay and at-least-once delivery when configured with an acknowledging consumer. |
| **Apache Pulsar** | Subscription type determines whether consumers share work or receive independent subscriptions. Acknowledgment, retention, redelivery and ordering depend on the selected subscription and topic configuration. |

Related distributed patterns use queues without being queues: **Saga** spans services with recoverable local transactions — each step commits locally and records the next action, and a later failure may require business-defined compensation such as releasing reserved stock after payment fails (compensation can itself fail or need manual recovery; it is no cross-service database rollback). See [Microservices/03 Saga Pattern](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.01-saga-pattern.md). **Event Sourcing** persists domain changes as the authoritative event history from which state derives, possibly with snapshots plus later events — a broker message is not automatically that durable history, since acknowledgment, retention, and replay policies may discard it. See [Microservices/07 Event Sourcing](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.03-event-sourcing.md). **CQRS** separates command handling from query models — a queue can update a read projection asynchronously, creating lag and recovery work; separate databases, event sourcing, and a message broker are optional choices, never CQRS requirements. See [Microservices/13 Cqrs](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.04-cqrs.md).

## When to discuss in interviews

| Scenario | Decision to explain | Failure boundary |
| -------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Email or payment effect | Stable provider operation identity and outcome reconciliation | Local acknowledgment cannot prove an external effect occurred once |
| Long-running report or video job | Durable status, bounded admission and appropriate worker resources | Processing time can exceed visibility/lease or retention limits |
| Ordered aggregate changes | Stable per-key routing and serialized effects where required | Parallel handlers and partition changes can alter effect order |
| Multiple independent subscribers | Subscription retention and separate consumer progress | One subscriber's success does not imply another's completion |
| Cache invalidation | Whether missed notifications can recover through versioning or refresh | Ephemeral pub/sub can lose messages while a subscriber is absent |
| Cross-service business workflow | Local commits, durable next actions and compensation | A saga does not provide one atomic global commit |

## Common Mistakes

- No duplicate protection for a non-idempotent effect. A redelivery can repeat a charge or other business action unless the consumer or receiving provider recognizes the operation identity.
- No recovery policy for poison messages. A DLQ may help, but some workloads use bounded retries, quarantine tables, or explicit rejection instead.
- Keeping work synchronous beyond the product's useful wait or deadline. Use a pending-job flow when deferred completion fits the user's task.
- No bounded recovery policy. Retrying everything indefinitely consumes capacity; retrying nothing can abandon recoverable work.
- No backpressure. Queue grows unbounded, runs out of disk, dies.
- Tight coupling between producer and consumer. Use a contract (event schema, version).
- Global ordering without an invariant. It concentrates sequencing; prefer per-aggregate order when it supplies the required contract.
- No monitoring. Queue depth, processing time, error rate. Alert on anomalies.
- Tight retry loops without backoff. Causes thundering herd.

## Summary

A queue lets one part of a system accept work while another processes it later. Choose whether messages need replay, broadcast, per-key ordering or priority. Messages may be delivered again after failures, so handlers should safely recognize repeated work. Define retry limits, recovery for jobs that keep failing, and which updates must commit together.

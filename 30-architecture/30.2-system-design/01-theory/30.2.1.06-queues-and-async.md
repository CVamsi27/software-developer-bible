# Message Queues & Async Patterns

> **Asynchronous processing is the backbone of every scalable system.** When a request would take 30 seconds (send email, generate report, process video), you don't make the user wait. You queue it. Know the patterns: point-to-point, pub/sub, delivery guarantees, ordering, idempotency, DLQ.

## TL;DR

- **Synchronous** = caller waits for response. Simple but slow.
- **Asynchronous** = caller queues work, returns immediately. Fast but more complex.
- **Queue types:** FIFO (point-to-point), pub/sub (broadcast), priority, delay.
- **Delivery guarantees:** at-most-once, at-least-once, exactly-once (in practice, effectively-once).
- **Idempotency is mandatory.** Duplicate messages will happen. Handle them.
- **DLQ (dead-letter queue)** for poison messages.
- **In interviews: name the queue type, delivery guarantee, idempotency strategy.**

---

## First Principles

Queues convert "must answer now" into "will process eventually" — the decoupling follows mechanically:

1. **Synchronous chains fail at the rate of their slowest link.** Checkout calling inventory calling email means email's latency *is* checkout's latency — and email's outage *is* checkout's outage. Inserting a queue cuts the dependency: producers finish when the broker accepts.
2. **The price is deferred truth.** The user's confirmation no longer proves the work happened — so the UI contract changes (pending states), and delivery semantics (at-least-once + idempotent consumers, → 20.6.2.05) become part of correctness, not ops hygiene.
3. **Queue depth is the system's pressure gauge.** Growing depth = producers outpace consumers = capacity signal (scale consumers or shed load); drained-to-zero = over-provisioned. The queue makes overload *visible and survivable* instead of a latency cliff.

## Why it matters

A user request that takes 30 seconds is broken. You need to:

1. **Acknowledge the user fast** (return "we got it, processing")
2. **Process asynchronously** (worker picks up the job, runs in the background)
3. **Notify on completion** (webhook, email, push notification, polling)

Without async, you can't scale. Every "send email", "process payment", "generate PDF", "transcode video" is async. The user doesn't wait.

---

## Definition

A **message queue** is durable, addressable storage that sits between a producer and a consumer and *decouples their timing*: the producer enqueues a message and returns immediately, and the consumer takes messages at whatever rate it can sustain.

Formally it is a buffer with three defining properties:

1. **Temporal decoupling** — producer and consumer need not be running at the same time; the queue owns the message in between.
2. **A delivery contract** — *at-most-once* (may lose), *at-least-once* (may duplicate), or *effectively-once* (deduplicated downstream). No broker provides exactly-once end-to-end across a network, so the consumer owns idempotency.
3. **A topology** — *point-to-point* (FIFO, one consumer gets each message) or *publish-subscribe* (fan-out, every subscriber gets a copy), plus optional priority and delay.

What a queue adds beyond a function call is **buffering and retry**: bursts are absorbed instead of failing, and failed messages can be redelivered or parked in a **dead-letter queue** rather than lost. What it costs is ordering (only per-partition, not global), visibility (async failures surface later), and duplicate handling.

## Sync vs Async

### Synchronous

```
Client → API → Service → Response
         (client blocks the whole time)
```

**Latency:** sum of all downstream calls
**Failure mode:** if any service fails, the request fails
**Throughput:** limited by the slowest service
**Use when:** the user needs the response in the request (e.g., "GET /user/profile")

### Asynchronous

```
Client → API → Queue → Response (immediate: "we got it")
            │
            └──→ Worker (background) → Service → Done
                  (notify user via webhook/poll)
```

**Latency:** request is fast, processing happens later
**Failure mode:** failure in worker doesn't fail the request (job goes to DLQ)
**Throughput:** queue absorbs spikes
**Use when:** processing takes >1 second, doesn't need to be in the request path (e.g., "send email", "process payment")

## Queue Types

### 1. Point-to-Point (FIFO Queue)

**Pattern:** One producer, one consumer (per message). Message is consumed once.

```
Producer → Queue → Consumer 1
                    (only one gets the message)
```

**Used for:** task distribution (any worker can do it), load balancing across workers.

**Examples:** SQS (default), RabbitMQ (default queue), Kafka (with consumer group)

### 2. Pub/Sub (Topic)

**Pattern:** One producer, multiple consumers. All subscribers get a copy of the message.

```
Producer → Topic → Consumer 1 (gets the message)
                → Consumer 2 (gets the message)
                → Consumer 3 (gets the message)
```

**Used for:** event broadcasting (notify multiple services), fan-out.

**Examples:** Kafka topics, RabbitMQ fanout exchanges, SNS, Google Pub/Sub

### 3. Priority Queue

**Pattern:** Higher-priority messages are processed first.

```
Queue:
  - High priority: [msg1, msg2]
  - Normal: [msg3, msg4, msg5, msg6]
  - Low: [msg7, msg8]
```

**Used for:** VIP users, urgent jobs, throttling by user tier.

### 4. Delay Queue

**Pattern:** Messages are not visible to consumers until a delay has passed.

**Used for:** scheduled tasks, retries with backoff, deferred notifications.

**Examples:** SQS with delay seconds, RabbitMQ with TTL + DLX, AWS SNS with retry policy

## Delivery Guarantees

The **at-least-once / at-most-once / exactly-once** spectrum.

### At-most-once

**Guarantee:** Message is delivered 0 or 1 times. May be lost.

**How:** Producer sends and forgets. No acknowledgment.

**Pros:** Fast, simple.

**Cons:** Can lose messages. Not OK for most use cases.

**When to use:** Metrics, logs, anything where occasional loss is OK.

### At-least-once

**Guarantee:** Message is delivered 1 or more times. May be duplicated.

**How:** Producer waits for ack. If no ack, retry.

**Pros:** No message loss.

**Cons:** Can have duplicates. Consumer must be idempotent.

**When to use:** Most cases. **This is the default.** Duplicates are easier to handle than losses.

### Exactly-once

**Guarantee:** Message is delivered exactly 1 time.

**How:** Combines at-least-once delivery + idempotent consumer + deduplication. Hard in practice.

**Pros:** No duplicates, no loss.

**Cons:** Complex. Often "effectively once" (very rare duplicates, rare losses).

**When to use:** Money transfers (in theory). Often replaced with "at-least-once + idempotency".

**In interviews:** say "at-least-once delivery with idempotent consumer (effectively-once semantics)".

## Idempotency

**Critical.** Duplicate messages WILL happen (at-least-once delivery, retries, network blips). Your consumer must handle them.

**Idempotency strategies:**

### 1. Idempotency Key

Producer sends a unique `idempotency_key` per logical operation. Consumer tracks processed keys (in DB, Redis) and skips duplicates.

```python
def process_payment(message):
    if redis.exists(f"processed:{message.idempotency_key}"):
        return # already processed
    result = do_payment(message.amount, message.user_id)
    redis.set(f"processed:{message.idempotency_key}", "1", ex=86400)
    return result
```

### 2. Idempotent operation

Design the operation itself to be idempotent. `SET balance = X` is idempotent. `balance += X` is not.

### 3. Database constraints

Use unique constraints to prevent duplicates. `INSERT ... ON CONFLICT DO NOTHING`.

### 4. Optimistic locking

Update with version check. `UPDATE x SET v=2 WHERE v=1`. If 0 rows affected, retry or skip.

## Ordering

**Default:** no global ordering. Messages are processed in the order they arrive, but parallelism breaks this.

**Per-partition ordering:** Kafka guarantees ordering within a partition. Partition by aggregate ID (e.g., user_id), all messages for one user go to one partition, processed by one consumer.

**Example:**
```
Topic with 4 partitions:
  Partition 0: [user_1_msg1, user_1_msg3, user_1_msg5]
  Partition 1: [user_2_msg2, user_2_msg4]
  Partition 2: [user_3_msg1, user_3_msg2]
  Partition 3: [user_4_msg1, user_4_msg2, user_4_msg3, user_4_msg4]

Each partition is processed by ONE consumer at a time.
Within a partition: ordered.
Across partitions: no global order.
```

**When to use:** Per-key ordering (e.g., "all events for user X in order"). Don't try for global ordering — it doesn't scale.

## Dead Letter Queue (DLQ)

**What:** A separate queue for messages that fail processing after N retries.

```
Main Queue → Consumer fails 3 times → DLQ
                                       ↓
                                  Manual investigation
```

**Why:** Poison messages (malformed, always-failing) block the queue. Move them out so processing continues.

**What to do with DLQ messages:**
- Log them for investigation
- Set up alerts (DLQ depth > 0 is a problem)
- Have a manual review process
- Possibly retry them later (after fixing the bug)

## Retry Strategies

When a consumer fails, what next?

### 1. Immediate retry

**Pattern:** Retry the same message N times in a tight loop.

**Pros:** Catches transient failures (network blip).

**Cons:** If the failure is persistent, you waste time.

### 2. Exponential backoff

**Pattern:** Retry after `delay = base * 2^attempt + jitter`.

**Pros:** Gives the system time to recover.

**Cons:** Can be slow (delays grow exponentially).

**Example:** 1s, 2s, 4s, 8s, 16s, 32s, give up.

### 3. Retry with jitter

**Pattern:** Like exponential backoff, but add random jitter to prevent thundering herd.

**Why:** if 1000 messages all fail at once, they all retry at the same time. Adding jitter spreads them out.

### 4. Retry queue

**Pattern:** Failed message goes to a "retry" queue with a delay. After delay, it goes back to the main queue.

**Pros:** Don't block the consumer.

**Cons:** More complex.

## Backpressure

When the queue grows faster than consumers can process:

**Solutions:**

- **Scale up consumers:** add more workers. Kafka consumer groups allow this.
- **Slow the producer:** rate-limit producers, or use a token bucket.
- **Drop messages:** for non-critical queues (metrics, logs), drop if queue is too long.
- **Alert:** if queue depth > threshold, page on-call.

## Common Patterns

### Saga (distributed transaction via events)

For multi-step business processes that span services:

```
Order Service → emits "order_created"
Inventory Service → consumes, reserves stock, emits "stock_reserved"
Payment Service → consumes, charges card, emits "payment_charged"
Order Service → consumes both, marks order as "confirmed"

If any step fails → compensating actions in reverse:
Inventory Service → consumes "payment_failed", releases stock
```

See [Microservices/03 Saga Pattern](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.01-saga-pattern.md).

### Event Sourcing

Store every state change as an event, not just the current state.

```
Account created → balance=0
Deposit $100 → balance=$100
Withdraw $30 → balance=$70
```

To get current state, replay all events. Auditable, time-travel debug.

See [Microservices/07 Event Sourcing](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.03-event-sourcing.md).

### CQRS (Command Query Responsibility Segregation)

Separate the read and write models.

```
Write model: optimized for writes (Postgres)
Read model: optimized for reads (Elasticsearch, Redis, denormalized)

Write → publish event → read model subscribes and updates
```

See [Microservices/13 Cqrs](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.04-cqrs.md).

## Specific Technologies

| Tech | Type | Delivery | Ordering | Throughput |
| ------------------ | --------------- | --------------------------------------------------------- | ---------------------------------------- | -------------------------------- |
| **Kafka** | Distributed log | At-least-once (default), exactly-once (with transactions) | Per-partition | Very high (millions/sec) |
| **RabbitMQ** | Broker | At-least-once (default) | Per-queue | High (hundreds of thousands/sec) |
| **AWS SQS** | Managed queue | At-least-once | Best-effort (FIFO queues have per-group) | High |
| **AWS SNS** | Pub/Sub managed | At-least-once | No | Very high (fanout) |
| **Google Pub/Sub** | Managed | At-least-once (default), exactly-once (with ordering key) | Per ordering key | High |
| **Redis Streams** | Lightweight | At-least-once | Per-stream | Medium |
| **NATS** | Lightweight | At-most-once / at-least-once | Per-subject | Very high |
| **Pulsar** | Distributed log | At-least-once | Per-partition | Very high |

## Anti-patterns

- **No idempotency.** Duplicate message = double-charge. Always.
- **No DLQ.** Poison message blocks the queue forever.
- **Sync API for slow work.** User waits 30 seconds. Bad UX.
- **No retry strategy.** Transient failure = permanent loss.
- **No backpressure.** Queue grows unbounded, runs out of disk, dies.
- **Tight coupling between producer and consumer.** Use a contract (event schema, version).
- **Global ordering requirement.** Doesn't scale. Use per-aggregate ordering.
- **No monitoring.** Queue depth, processing time, error rate. Alert on anomalies.
- **Tight retry loops without backoff.** Causes thundering herd.

---

## Summary

Message queues decouple producers from consumers, enabling async processing, load leveling, and fault tolerance. Key decisions: queue type (Kafka for durability + ordering, RabbitMQ for flexibility), delivery guarantee (at-most-once, at-least-once, exactly-once), ordering (per-partition), and idempotency. DLQ handles poison messages. In interviews, name the queue type, delivery guarantee, idempotency strategy, and retry strategy.

## Cheat Sheet
```text
QUEUES & ASYNC CHEAT SHEET
═══════════════════════════════════════════════════════════════

KAFKA:
• Durable, ordered, replayable
• Topics → partitions → consumer groups
• Best for: event streaming, audit, analytics
• Ordering: per partition (key by aggregate ID)

RABBITMQ:
• Flexible routing, acknowledgments
• Exchanges → queues → consumers
• Best for: task queues, RPC, complex routing

DELIVERY GUARANTEES:
• At-most-once — fire and forget (fast, lossy)
• At-least-once — retry until ack (default, idempotent consumer)
• Exactly-once — Kafka transactional (complex, expensive)

IDEMPOTENCY:
• Idempotency key per request
• Deduplication at consumer
• DB unique constraint

RETRY:
• Exponential backoff + jitter
• Max retries with DLQ
• Circuit breaker for downstream
```

# Rate Limiting

> **Rate limits protect a shared resource when unbounded demand is a risk.** Use them where a caller can exhaust capacity, fairness or a downstream quota; a limit is not necessary on every endpoint.

## Definition

**Rate limiting** is admission control that bounds the request rate or weighted work admitted for a defined identity, and specifies what happens when the allowance is exhausted. It is a resource-protection or fairness policy, not a direct bound on simultaneous in-flight work.

Four elements define a limiter; changing any one changes the guarantee:

1. **Key** — per user, per IP, per API key, per tenant, per endpoint, or global. The key is the fairness unit: per-IP limits can group many users behind a NAT, while a user ID is unavailable until authentication succeeds. Trust forwarded client addresses only when a trusted proxy removes caller-supplied forwarding headers and supplies its own.
2. **Algorithm** — *fixed window* (simple, can admit nearly 2× the limit across a boundary), *sliding window* (tracks or estimates recent traffic), *token bucket* (allows stored burst credit and steady refill), *leaky bucket* (queues or rejects bursts to shape output).
3. **Limit and cost** — a limiter may count *weighted cost* rather than bare requests (a search costs 10, a read costs 1).
4. **Rejection behavior** — reject, queue within a bounded delay, or degrade. For HTTP, `429` may include `Retry-After` when the server can give a useful wait time.

For a fleet-wide limit, independent per-instance counters can multiply the allowance by the number of instances. Shared state can enforce one coordinated budget; allocated per-instance sub-budgets trade some utilization for fewer coordination calls. Apply a limit where it protects a constrained resource or enforces a real fairness policy; not every endpoint needs one.

> **Textbook Definition:** Rate limiting is admission control that bounds requests or resource consumption for a defined identity and interval, with specified burst allowances and behavior when the limit is exceeded.

## First Principles

(→ 20.3.4.01 covers the API view; the theory view is shared-state under concurrency.)

1. **Concurrent admissions consume one authority's budget.** A fixed-window counter must check/update atomically; a token bucket must update credit and refill time together. Strict fleet-wide limits require coordination or safely allocated sub-budgets. The enforcement point can be a gateway or application, not necessarily the network edge.
2. **The algorithms are burst-shaping policies**: fixed window (cheap, 2× boundary burst), sliding log (exact, memory-heavy), sliding window counter (approximate, balanced), token bucket (sustained rate + burst credit). A sliding log retains timestamps; a token bucket retains credit and refill time. Their state differs because their burst contracts differ.
3. **Loss of the budget authority forces an admission policy.** Rejecting preserves a strict protection bound at an availability cost; admitting can exceed it. Safely preallocated local budgets permit some admission without contacting the authority. This is an explicit failure contract; calling every limiter a CAP example obscures the actual consistency requirement.

## Why it matters

Without rate limiting:
- One bad client can take down your service
- A bug can cause infinite retry loops
- Application-level abuse can consume resources; volumetric attacks also require protection before the saturated network boundary
- You can't enforce paid tiers ("Pro users get 10K requests/hour")

With rate limiting:
- Bounded admitted demand under the selected keys, costs and coordinated budget
- Fair access
- Paid tier enforcement
- DDoS mitigation (partial)

## Four Common Algorithms and Windows

### 1. Fixed Window

**Algorithm:** Count requests in fixed time windows. Reset at the window boundary.

```
Window 1 (00:00 - 00:59): 100 requests allowed
Window 2 (01:00 - 01:59): 100 requests allowed
```

**Pros:** Simple, easy to implement (just an integer counter).

**Cons:** **Burst at the window boundary.** With a limit of 100 per minute, a caller can make nearly 100 requests just before the boundary and 100 just after it, approaching 200 requests in a short interval.

**When to use:** Low-stakes APIs, simple cases.

### 2. Sliding Window

**Algorithm:** Count requests in a sliding window (last 60 seconds, not aligned to clock).

**Implementation 1: Sliding log**
- Store every request timestamp
- Count those in the last 60s
- Memory-intensive (one entry per request)

**Implementation 2: Sliding window counter estimate**
- Track count in current window and previous window
- Estimate sliding count using weighted average
- Approximate, less memory

```
current_window_count = 80
previous_window_count = 100
elapsed_in_current_window = 30s (out of 60s)

sliding_count ≈ previous_window_count * (1 - 30/60) + current_window_count
             = 100 * 0.5 + 80
             = 50 + 80
             = 130
```

**Pros:** The exact log gives an exact rolling count. The two-counter estimate reduces the aligned-window discontinuity with constant per-key state.

**Cons:** The exact log stores one timestamp per counted event. The estimate assumes the previous window's events were spread evenly; a skewed arrival pattern can make its answer inaccurate, so it is not a strict rolling-window guarantee.

**When to use:** When a rolling-window contract matters; choose exact versus approximate state deliberately.

### 3. Token Bucket

**Algorithm:** A bucket holds N tokens. Each request consumes 1 token. Tokens refill at rate R per second. If no tokens, reject.

```
Bucket capacity: 100 tokens
Refill rate: 10 tokens/sec

t=0: bucket has 100 tokens
t=0: request → bucket has 99 tokens
...
t=1: bucket has 100 tokens (99 + 10 refill tokens, capped; no intervening requests)
```

**Pros:**
- Allows bursts (up to bucket capacity)
- Smooth refill
- Simple to implement

**Cons:** Need to track token count per key.

**When to use:** When the policy needs a sustained refill rate and an explicit maximum burst. A bucket with capacity `C` and refill rate `r` can admit at most the stored credit plus credit replenished over the interval; it does not promise a constant output rate.

**Check:** The actual provider may layer several throttles and quotas; do not infer its complete contract from one algorithm.

### 4. Leaky Bucket

**Algorithm:** In the queueing form, requests enter a bounded queue and drain at a fixed rate. When full, reject. A drop-based leaky bucket can reject excess traffic immediately instead of queueing it.

```
Queue capacity: 100
Process rate: 10 req/sec

Requests come in → enqueue (up to 100)
Process loop: dequeue + process at 10/sec
If queue is full → reject new requests
```

**Pros:** Smooth output rate (no bursts).

**Cons:** The queueing form accepts a bounded burst but adds wait time; the drop-based form sheds excess work. Neither guarantees a request completes within its deadline unless queue delay and service time are bounded.

**When to use:** When you need strict rate smoothing. Less common than token bucket.

## Comparison

| Algorithm | Allows bursts? | Memory | Complexity | Best for |
| ------------------------ | -------------------------------------------- | ---------------------------- | ---------- | -------------------------------------- |
| Fixed window | Yes (boundary) | Low | Very low | Low-stakes APIs |
| Exact sliding log | Up to the rolling-window allowance | O(admitted events in window) | Medium | Exact rolling count |
| Sliding counter estimate | Approximate rolling allowance | O(1) per key | Medium | Lower state cost with documented error |
| Token bucket | Yes (up to capacity) | Low | Medium | Sustained budget with bounded burst |
| Queued leaky bucket | Can enqueue a bounded burst; drains smoothly | O(queue capacity) | Medium | Bounded-delay output shaping |

**In interviews:** State the required sustained rate, burst and deadline first. A token bucket fits bounded burst credit; an exact sliding log fits a strict rolling-window count.

## Rate Limit Keys

What you limit BY:

| Key | Use case | Pros | Cons |
| ------------------------------- | ------------------------------------ | --------------------- | -------------------------------------- |
| **IP** | Public APIs, anonymous traffic | Easy (no auth needed) | NAT/CGNAT means many users share an IP |
| **User ID** | Authenticated APIs | Fair per user | Need to be authenticated |
| **API key** | B2B APIs | Tracks partner usage | Partners share one key for many users |
| **Tenant ID** | B2B SaaS | Fair per tenant | One tenant can have many users |
| **Endpoint** | Protect specific expensive endpoints | Limits resource use | Doesn't limit per user |
| **Composite** (user + endpoint) | Most production systems | Granular | More state to track |

**In production:** Stack keys. e.g., "100 req/sec per user" AND "10000 req/sec per tenant" AND "1000 req/sec on /search endpoint globally."

Derive authenticated identities from verified credentials. A caller-controlled API key can identify a credential, but does not prove that the caller is authorized to use every resource named by the request.

## Where to Enforce

| Layer | Pros | Cons |
| ---------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Edge (CDN, WAF)** | Can reject before origin work | Usually has network and token signals; business identity may require a trusted gateway or verified token |
| **API Gateway** | Centralized policy, sees all traffic | One more thing to maintain |
| **Application** | Full context, can vary by business logic | Per-app logic, harder to enforce globally |
| **Database / service** | Protects a specific downstream dependency or expensive operation | Work upstream of that point has already been spent; local limits may not represent the fleet total |

Choose enforcement where the needed identity and protected resource are visible. A gateway replicated across machines still needs coordinated state or allocated sub-budgets for a strict fleet allowance. Layer coarse early protection and precise application budgets when both address a real risk. Rate bounds do not directly bound in-flight concurrency: slow requests can occupy many workers at a low arrival rate.

## What to Return When Limited

- **HTTP 429 Too Many Requests** — standardized for rate limiting. The response may include `Retry-After`, either a delay in seconds or an HTTP date; a 429 response must not be stored by a cache.
- **Rate-limit metadata** — header names and meanings vary by API. The current IETF `RateLimit` header-field document is an active Internet-Draft, not a published RFC; check its Datatracker status and the server's contract before relying on it.

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 60

{
  "error": "rate_limited",
  "message": "Too many requests. Try again in 60 seconds."
}
```

## Distributed Rate Limiting

Independent counters can implement intentional per-instance protection, but not the same full fleet allowance (100 on A plus 100 on B permits 200). State whether the promised budget is local or global.

**Solutions:**

### 1. Centralized store (Redis)

All servers share a Redis counter. Increment on each request. Check against limit.

```
Server A: INCR rate:user:123 → 1
Server B: INCR rate:user:123 → 2
...
```

**Pros:** One atomic authority prevents two callers independently granting the same remaining allowance.
**Cons:** Redis becomes a dependency, network call adds latency.

### 2. First-arrival window in Redis with Lua

This illustrative script validates positive integer configuration before changing state, then counts attempts atomically on one Redis authority. The first attempt starts the TTL; it is a first-arrival window, not a sliding-window algorithm or a clock-aligned fixed window. Denied attempts also increment the count, but do not extend expiry. Concurrent access, replication/failover loss and unavailable-store behavior remain part of the system contract.

```lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local max_safe_integer = 9007199254740991
if not limit or not window or limit ~= math.floor(limit) or window ~= math.floor(window)
  or limit < 1 or window < 1 or limit > max_safe_integer or window > max_safe_integer then
  return redis.error_reply('limit and window must be positive safe integers')
end
local current = redis.call('INCR', key)
if current == 1 then
  redis.call('EXPIRE', key, window)
end
if current > limit then
  return 0 -- denied
end
return 1 -- allowed
```

### 3. Token bucket in Redis

Same idea, but with refill logic.

### 4. Per-instance approximation

Each server has a partial view. Two independent full allowances can permit up to twice the intended rate; calling local state a sliding counter does not synchronize it. Allocate per-instance budgets or explicitly accept the multiplied/approximate allowance.

## Common Patterns

### 1. Free tier limit

```
Free: 1000 requests/day per API key
Pro: 100,000 requests/day per API key
```

### 2. Per-endpoint protection

```
GET /search: 10 req/sec per user (expensive)
GET /user/profile: 100 req/sec per user (cheap)
POST /login: 5 req/min per IP (security)
```

### 3. Tiered limits

```
Per user: 100 req/min
Per tenant: 10,000 req/min
Global: 1,000,000 req/min
```

### 4. Burst + sustained

```
Burst: 1000 requests in 1 second (token bucket)
Sustained: 100 req/sec average
```

## Implementation Boundaries

| Implementation | Scope and behavior to verify |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **Redis + Lua** | One Redis primary can atomically update shared state; failover, eviction, latency and store outage still affect the guarantee. |
| **NGINX `limit_req`** | Uses a leaky-bucket method with configurable burst handling; the key is configurable, so it need not be an IP. |
| **Envoy local rate limit** | Uses a token bucket in each Envoy process; it protects locally and does not by itself create one fleet-wide allowance. |
| **Envoy global rate limit** | Calls an external gRPC rate-limit service for a shared decision; this adds a dependency and network hop. |
| **Amazon API Gateway REST API** | Throttling targets use token buckets; configured limits are best-effort targets rather than guaranteed ceilings. |

---

## Anti-patterns

- **Checking after the protected work.** Derive a trusted identity and cost, then admit before the expensive operation; protect earlier stages separately if they are also costly.
- **Calling local state a global quota.** Independent instance counters multiply the total allowance unless budgets are partitioned or coordinated.
- **Returning no useful wait information.** Include `Retry-After` when the retry time is known; clients should still use bounded backoff and jitter.
- **Hard-coding limits in 10 places.** Centralize the config.
- **No monitoring.** You need to see when limits are hit (is it a bug? an attack? growth?).
- **Rate limiting only the API.** Don't forget the auth endpoint (brute force), the password reset (email spam), the export (data exfil).
- **Limits disconnected from the contracted tier or resource budget.** Publish the allowance, observe legitimate rejection, and adjust capacity or policy; paid traffic still needs a protection boundary.

## When to discuss in interviews

| Scenario | Rate limit | Why |
| ---------------- | ----------------------- | ------------------------------ |
| Public API | Per API key, 1000/hour | Prevent abuse |
| Login endpoint | Per IP, 5/minute | Prevent brute force |
| Search endpoint | Per user, 10/minute | Expensive query |
| Webhook receiver | Per source, 1000/minute | Don't let one source overwhelm |
| File upload | Per user, 100/hour | Storage cost |
| Password reset | Per email, 3/day | Prevent email spam |
| SMS sending | Per user, 10/day | Cost |

## Summary

Rate limiting controls how many requests a caller may make in a period. Choose the caller identity, allowed rate, burst behavior and response after the limit is reached. Fixed windows are simple but allow bursts at a boundary; token buckets allow bounded bursts; sliding windows smooth the boundary more closely. Multiple servers need a shared or deliberately partitioned limit. A 429 response can include Retry-After when the client should wait.

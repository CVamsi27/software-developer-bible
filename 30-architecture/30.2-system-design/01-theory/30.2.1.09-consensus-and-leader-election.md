# Consensus & Leader Election

Three replicas track the last item in stock. Leader A loses contact with B and C but can still reach the inventory database; B and C elect a replacement. If the database accepts A's stale write after the replacement updates it, both orders may appear successful. Consensus protects the replicas' shared history; the database must enforce ownership or the inventory invariant at its own boundary.

## Definition

**Consensus** lets participating processes choose the same proposed value despite specified failures. One decision can choose a value for one log position; a replicated-log protocol orders a sequence of such decisions.

> **Textbook Definition:** Consensus requires agreement, validity and integrity for a decision, with termination under the protocol's progress assumptions. Leader election designates a coordinator; it does not alone establish an agreed log or prevent stale effects.

- **agreement** — no two correct processes decide differently,
- **validity** — the decided value was actually proposed,
- **integrity** — a process does not decide a second value for the same consensus instance,
- **termination** — correct processes eventually decide when the protocol's progress assumptions hold. A deterministic protocol cannot guarantee termination in a fully asynchronous model with even one possible crash; practical protocols need additional assumptions such as eventual timely communication.

Safety means the protocol does not decide conflicting results. Liveness means it can eventually decide. In a common crash-tolerant design with `2f+1` voters, a majority of `f+1` can make progress despite up to `f` unavailable voters. This is a common quorum design, not a rule for every consensus protocol. During a network partition, a majority-based group can make progress only on the side that can reach a majority.

The Paxos and Raft descriptions below assume protocol-following nodes that may crash, recover or lose communication. They do not tolerate a voter lying about its persisted state. Such **Byzantine faults** require a different protocol and fault budget. Consensus also does not validate business rules: every replica can consistently apply the same invalid command.

**Leader election** chooses which member may coordinate work for a term or epoch. In Raft, election is one part of the consensus protocol; other systems use different mechanisms. A lease can limit how long authority lasts, but it depends on carefully defined timing assumptions.

Networks do not tell a node whether its peer has crashed or is only slow. Terms or epochs let members recognize newer protocol state and reject stale protocol messages. They do not by themselves stop an old leader from writing to an external system; the resource may need to check a fencing token or another ownership condition.

## First Principles

Consensus is needed when independent replicas must apply the same commands in the same order:

1. **Replicated state machines need the same ordered commands.** If each replica applies a different order, or applies nondeterministic logic, their state can diverge.
2. **Messages can be delayed and machines can fail.** A protocol needs rules for deciding when a change is accepted and when a member must wait.
3. **Progress needs a protocol-specific quorum and failure model.** A majority-based group may continue when one of three voters is unreachable; without a quorum, it waits rather than create a competing history. A quorum protects only state governed by that protocol. A separate database, payment provider or storage system must enforce ownership itself, often with a fencing token.

## Paxos (Leslie Lamport's consensus protocol)

**Two phases:**

### Phase 1: Prepare

- Proposer picks a unique proposal number N
- Sends "prepare(N)" to all acceptors
- If N exceeds its recorded promise, an acceptor durably promises not to accept lower-numbered proposals and returns its highest-numbered accepted proposal, if any. Otherwise it refuses this prepare.
- If a majority responds, proposer goes to Phase 2

### Phase 2: Accept

- Proposer adopts the value attached to the highest-numbered accepted proposal returned by the prepare quorum; only if none was accepted may it choose a new value
- Proposer sends "accept(N, value)" to all acceptors
- An acceptor accepts N only if it has not promised a higher proposal number. If a majority accepts the value, it is chosen.
- Acceptors persist promises and accepted proposals before acknowledging; a quorum of accepts chooses the value, even before a learner knows it

These phases describe one Paxos decision. Multi-Paxos extends this to a log, commonly reusing an established leader to avoid repeating preparation for every entry. Production variants have additional recovery and membership rules; the two-phase outline is not an implementation specification.

## Raft (designed to be understandable, 2014)

Raft decomposes consensus into 3 sub-problems:

### 1. Leader election

- Each node is in one of 3 states: Follower, Candidate, Leader
- All nodes start as Followers
- If a Follower doesn't hear from a Leader within a timeout, it becomes a Candidate
- Candidate advances its term, votes for itself and asks others for votes. A voter grants at most one vote per term and checks that the candidate's log is at least as up-to-date as its own.
- If a Candidate gets votes from a majority, it becomes the Leader
- Leader sends heartbeats to prevent needless elections while communication works; heartbeats alone do not authorize a write without the commit quorum.

### 2. Log replication

- Client sends command to Leader
- Leader appends to its log
- Leader sends "AppendEntries" to Followers
- Followers check the preceding entry's index/term, repair conflicting uncommitted suffixes and durably append before replying
- The leader advances the commit index when a majority has replicated an entry from its current term; earlier-term entries become committed indirectly through that index
- Leader notifies Followers of commit, applies to state machine

### 3. Safety

- Voters compare last-log term, then index; a candidate needs an eligible majority, not necessarily the longest log on every isolated node.
- Committed entries are preserved across leader changes under Raft's protocol assumptions
- Properties: state machine safety, leader completeness, log matching

Raft was designed to make the protocol easier to understand. Like other consensus protocols, it still requires careful implementation and operational choices.

Majority reasoning assumes an agreed voter configuration. Adding or removing voters must follow the implementation's reconfiguration protocol; independently replacing each node's voter list can create incompatible quorums. Adding read-only replicas does not necessarily change the voting majority.

## Zab (ZooKeeper Atomic Broadcast)

Zab orders ZooKeeper's state changes. **Atomic broadcast** means committed messages are delivered in the same order, with delivery guarantees under the failure model; it does not mean all replicas apply them simultaneously or that every read sees the latest change.

ZooKeeper's implementation documentation describes **leader activation**, which establishes an epoch and synchronizes a quorum with the chosen history, followed by **active messaging**, which proposes, persists and commits ordered updates. Election alone does not finish activation. Read freshness is an additional API contract.

HBase uses ZooKeeper for coordination. Kafka 3.x deployments could use ZooKeeper for metadata; Kafka 4.0 and later support only KRaft. Its controller quorum orders cluster metadata, while topic-partition replication follows a separate protocol.

## Where authority can become stale

A timeout is suspicion, not proof: a slow or partitioned leader may continue running. A majority-based group can elect a newer leader and commit only with its quorum, while an isolated old leader cannot extend the protocol's committed history. When it later receives a higher term, it steps down.

That rule does not revoke credentials or stop an external resource from accepting an old owner's request. A **fencing token** is a monotonically increasing ownership value that the resource checks on every write; it rejects a request from an older owner. A lease can bound authority only if its clock and pause assumptions hold, so correctness-critical writes still need protection at the resource boundary.

Election timeouts expose a recovery trade-off: short values can cause unnecessary elections during ordinary delay; long values slow detection. Tune and measure them against real network and process pauses rather than promise a fixed failover time.

---

## When to use consensus

Use consensus when a business invariant requires replicas to agree on one order or one owner before accepting a change—for example, a replicated metadata log or exclusive ownership record. The cost is coordination: loss of a quorum pauses those writes, and cross-region latency can lengthen each commit.

If stale or duplicate outcomes are acceptable, or a local/asynchronous design can enforce the invariant, consensus may add cost without improving correctness. Evaluate the specific operation's consistency and availability contract; a product name or “distributed” label is not enough to justify it.

## Trace a leader change

A, B and C are three voters. In term 4, A sends command X to B; both persist it. A commits X and acknowledges the client. A then becomes isolated.

B and C can form a majority. A newer-term election cannot safely choose a candidate whose log omits X against the voting rules: B will reject that stale candidate. B can win, replicate missing entries to C and continue under the commit rules. A may still call itself leader, but it cannot commit a fresh command alone. When it receives a higher-term protocol message, it steps down.

A read also needs a freshness rule. The old isolated A cannot simply answer from its local state because it remembers being leader. Safe Raft read paths establish current authority and an applied-state barrier under their documented protocol; serving from an arbitrary follower or stale leader is a different contract.

Now change one condition: A commits X, but its response is lost. Retrying X can append another command even though the first is already committed. Keep a stable operation identity and its result in the replicated application state to deduplicate retries. Log agreement alone does not make client submissions or external effects exactly once.

For application locks and external stale-writer protection, use [Distributed Locks](30.2.1.14-distributed-locks.md). The consensus log orders ownership changes; a resource outside that log must enforce the ownership value itself.

## How to explain the design in an interview

Start with the invariant and the protocol's failure model. Then trace one acknowledged write through persistence, quorum commit and failover. Close with the boundary the protocol does not cover: read freshness, client retry deduplication, voter reconfiguration or fencing an external resource. For PostgreSQL, for example, streaming replication does not elect or fence a primary by itself; those responsibilities belong to the configured failover system.

---

## Anti-patterns

- **Implementing Paxos/Raft yourself.** Use a battle-tested library. The failure modes are subtle.
- **Two voting nodes.** Their majority is 2, so losing either prevents progress. Three voters tolerate one failure; five tolerate two.
- **Treating election as revocation.** A new leader does not stop an old process from affecting an external resource; enforce ownership there.
- **Promising a fixed election time.** Failover depends on configuration and conditions; define and measure a recovery objective for the actual cluster.

---

## Summary

Consensus protocols let replicas agree on an ordered set of changes despite specified failures. Raft is designed to make this process easier to follow; Paxos is another family of protocols. A leader is useful only while it has authority under the protocol. Quorums, terms and safe failover rules prevent two nodes from committing conflicting histories. Timeouts detect suspected failure; they do not prove a node is dead.

# Consensus & Leader Election

Three replicas track the last item in stock. Leader A loses contact with B and C but can still reach the inventory database; B and C elect a replacement. If the database accepts A's stale write after the replacement updates it, both orders may appear successful. Consensus protects the replicas' shared history; the database must enforce ownership or the inventory invariant at its own boundary:

```text
A isolated, B+C elect B → A's stale write must be rejected by the database.
```

## Definition

**Consensus** lets participating processes choose the **same proposed value** despite specified failures. One decision can choose a value for one log position; a replicated-log protocol orders a sequence of such decisions.

> **Textbook Definition:** Consensus requires agreement, validity and integrity for a decision, with termination under the protocol's progress assumptions. Leader election designates a coordinator; it does not alone establish an agreed log or prevent stale effects.

## First Principles

Consensus is needed when independent replicas must apply the same commands in the same order:

1. **Replicated state machines need the same ordered commands.** If each replica applies a different order, or applies nondeterministic logic, their state can diverge.
2. **Messages can be delayed and machines can fail.** A protocol needs rules for deciding when a change is accepted and when a member must wait.
3. **Progress needs a protocol-specific quorum and failure model.** A majority-based group may continue when one of three voters is unreachable; without a quorum, it waits rather than create a competing history. A quorum protects only state governed by that protocol. A separate database, payment provider, or storage system must enforce ownership itself, often with a fencing token.

## 1. Choose one value with Paxos phases

One decision must satisfy four properties: **agreement** (no two correct processes decide differently), **validity** (the decided value was actually proposed), **integrity** (no process decides a second value for the same consensus instance), and **termination** (correct processes eventually decide when the protocol's progress assumptions hold). A deterministic consensus protocol cannot guarantee termination in a fully asynchronous model with even one possible crash; practical protocols need additional assumptions such as eventual timely communication.

Safety means the protocol never decides conflicting results. Liveness means it can eventually decide. In a common crash-tolerant design with `2f+1` voters, a majority of `f+1` makes progress despite up to `f` unavailable voters — a common quorum design, not a rule for every consensus protocol. During a partition, a majority-based group makes progress only on the side reaching a majority. The Paxos and Raft descriptions below assume protocol-following nodes that may crash, recover, or lose communication. They never tolerate a voter lying about its persisted state — such **Byzantine faults** need a different protocol and fault budget. Consensus also never validates business rules: every replica can consistently apply the same invalid command.

**Phase 1 — Prepare:** the proposer picks a unique proposal number N and sends `prepare(N)` to all acceptors. If N exceeds its recorded promise, an acceptor durably promises never to accept lower-numbered proposals and returns its highest-numbered accepted proposal, if any. Otherwise it refuses. With a majority of responses, the proposer proceeds to Phase 2.

**Phase 2 — Accept:** the proposer adopts the value attached to the highest-numbered accepted proposal returned by the prepare quorum; only if none was accepted may it choose a new value. It sends `accept(N, value)` to all acceptors. An acceptor accepts N only if it has not promised a higher proposal number. If a majority accepts the value, it is chosen. Acceptors persist promises and accepted proposals before acknowledging; a quorum of accepts chooses the value even before a learner knows it.

These phases describe one Paxos decision. Multi-Paxos extends this to a log, commonly reusing an established leader to avoid repeating preparation for every entry. Production variants add recovery and membership rules; the two-phase outline is not an implementation specification.

## 2. Elect, replicate, and stay safe with Raft

Raft decomposes consensus into three sub-problems. **Leader election:** each node is Follower, Candidate, or Leader; all start as Followers. A Follower that receives no Leader heartbeat within a timeout becomes a Candidate, advances its term, votes for itself, and asks others for votes. A voter grants at most one vote per term and checks that the candidate's log is at least as up-to-date as its own. A majority of votes makes the Candidate the Leader. The Leader sends heartbeats to prevent needless elections while communication works — but heartbeats alone never authorize a write without the commit quorum.

**Log replication:** the client sends a command to the Leader, which appends it to its log and sends `AppendEntries` to Followers. Followers check the preceding entry's index/term, repair conflicting uncommitted suffixes, and durably append before replying. The leader advances the commit index when a majority has replicated an entry from its current term; earlier-term entries commit indirectly through that index. The leader notifies Followers of commit and applies to the state machine.

**Safety:** voters compare the last log term, then the index; a candidate needs an eligible majority, not necessarily the longest log on every isolated node. Committed entries survive leader changes under Raft's protocol assumptions (properties: state machine safety, leader completeness, log matching).

Raft was designed for understandability — but like every consensus protocol, it still demands careful implementation and operational choices. Majority reasoning assumes an agreed voter configuration: adding or removing voters must follow the implementation's reconfiguration protocol, since independently replacing each node's voter list can create incompatible quorums. Adding read-only replicas does not necessarily change the voting majority.

## 3. Order ZooKeeper state with Zab

Zab (ZooKeeper Atomic Broadcast) orders ZooKeeper's state changes. **Atomic broadcast** means committed messages are delivered in the same order, with delivery guarantees under the failure model; it never means all replicas apply them simultaneously or that every read sees the latest change.

ZooKeeper's implementation documentation describes **leader activation**, which establishes an epoch and synchronizes a quorum with the chosen history, followed by **active messaging**, which proposes, persists, and commits ordered updates. Election alone never finishes activation. Read freshness is an additional API contract.

HBase uses ZooKeeper for coordination. Kafka 3.x deployments could use ZooKeeper or KRaft (Kafka's Raft-based metadata mode) for metadata; Kafka 4.0 and later support only KRaft. Kafka's controller quorum orders cluster metadata, while topic-partition replication follows a separate protocol.

## 4. Fence stale authority at the resource boundary

A timeout is suspicion, not proof: a slow or partitioned leader may keep running. A majority-based group can elect a newer leader and commit only with its quorum, while an isolated old leader cannot extend the protocol's committed history. When it later receives a higher term, it steps down.

Protocol authority does not revoke credentials or stop an external resource from accepting an old owner's request.

A **fencing token** is a monotonically increasing ownership value the resource checks on every write; it rejects requests from older owners.

A **lease** bounds authority only if its clock and pause assumptions hold, so correctness-critical writes still need protection at the resource boundary.

**Leader election** chooses which member may coordinate work for a term or epoch — in Raft it is one part of the consensus protocol; other systems use different mechanisms.

Networks never tell a node whether its peer crashed or is merely slow. Terms or epochs let members recognize newer protocol state and reject stale protocol messages — but they never by themselves stop an old leader writing to an external system; the resource must check a fencing token or another ownership condition.

Election timeouts expose a recovery trade-off: short values cause needless elections during ordinary delay; long values slow detection. Tune and measure them against real network and process pauses rather than promising a fixed failover time.

## 5. Trace one leader change

A, B, and C are three voters. In term 4, A sends command X to B; both persist it. A commits X and acknowledges the client. A then becomes isolated.

B and C can form a majority. A newer-term election cannot safely choose a candidate whose log omits X against the voting rules: B will reject that stale candidate. B can win, replicate missing entries to C, and continue under the commit rules. A may still call itself leader, but it cannot commit a fresh command alone. When it receives a higher-term protocol message, it steps down.

A read also needs a freshness rule. The old isolated A cannot simply answer from local state because it remembers being leader. Safe Raft read paths establish current authority and an applied-state barrier under their documented protocol; serving from an arbitrary follower or stale leader is a different contract.

Now change one condition: A commits X, but its response is lost. Retrying X can append another command even though the first is already committed. Keep a stable operation identity and its result in the replicated application state to deduplicate retries. Log agreement alone never makes client submissions or external effects exactly once. For application locks and external stale-writer protection, use [Distributed Locks](30.2.1.14-distributed-locks.md). The consensus log orders ownership changes; a resource outside that log must enforce the ownership value itself.

## 6. Reach for consensus only when the invariant needs it

Use consensus when a business invariant requires replicas to agree on one order or one owner before accepting a change — e.g. a replicated metadata log or exclusive ownership record. The cost is coordination: losing a quorum pauses those writes, and cross-region latency can lengthen each commit. If stale or duplicate outcomes are acceptable, or a local/asynchronous design can enforce the invariant, consensus may add cost without improving correctness. Evaluate the specific operation's consistency and availability contract; a product name or "distributed" label never justifies it.

| Tech | Protocol | Use case |
| --------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **etcd** | Raft | Kubernetes, distributed locks, config |
| **Google Chubby / Spanner** | Paxos-family protocols | Coordination / distributed database replication |
| **Consul** | Raft | Service discovery, config, health checks |
| **ZooKeeper** | Zab | ZooKeeper coordination state; used by HBase and legacy Kafka |
| **CockroachDB** | Raft | Distributed SQL |
| **TiKV** | Raft | Distributed key-value store |
| **MongoDB replica set** | MongoDB replication protocol | MongoDB high availability (HA) |
| **Postgres** | Write-ahead log (WAL) replication; external election/fencing | PostgreSQL HA with a configured failover manager |
| **Kafka** | KRaft metadata quorum uses Raft | Cluster metadata coordination |
| **Redis Sentinel** | Sentinel monitoring and failover | Redis HA; separate from a replicated-log consensus system |

In an interview, start with the invariant and the protocol's failure model. Then trace one acknowledged write through persistence, quorum commit, and failover. Close with the boundary the protocol never covers: read freshness, client retry deduplication, voter reconfiguration, or fencing an external resource. For PostgreSQL, for example, streaming replication never elects or fences a primary by itself; those responsibilities belong to the configured failover system.

## Common Mistakes

- Implementing Paxos/Raft yourself. Use a battle-tested library. The failure modes are subtle.
- Two voting nodes. Their majority is 2, so losing either prevents progress. Three voters tolerate one failure; five tolerate two.
- Treating election as revocation. A new leader never stops an old process affecting an external resource; enforce ownership there.
- Promising a fixed election time. Failover depends on configuration and conditions; define and measure a recovery objective for the actual cluster.

## Summary

Consensus protocols let replicas agree on an ordered set of changes despite specified failures. Raft is designed to make this process easier to follow; Paxos is another family of protocols. A leader is useful only while it has authority under the protocol. Quorums, terms and safe failover rules prevent two nodes from committing conflicting histories. Timeouts detect suspected failure; they do not prove a node is dead. Fencing at the resource boundary is what stops an old leader's external writes.

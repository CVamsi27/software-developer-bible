# Consensus & Leader Election

When several machines keep copies of the same data, they need a safe way to agree on which changes count and in what order. Consensus protocols provide that agreement under stated failure assumptions.

## Definition

**Consensus** is the problem of getting a set of unreliable processes to agree on a single value (or a single ordering of values) such that:

> **Textbook Definition:** Consensus establishes agreement on a value or ordered log among participating processes under a stated failure model. Leader election selects a coordinator but does not, by itself, establish agreement or prevent stale writes.

- **agreement** — no two correct processes decide differently,
- **validity** — the decided value was actually proposed,
- **termination** — correct processes eventually decide when the protocol's progress assumptions hold. A deterministic protocol cannot guarantee termination in a fully asynchronous model with even one possible crash; practical protocols need additional assumptions such as eventual timely communication.

Safety means the protocol does not decide conflicting results. Liveness means it can eventually decide. In a common crash-tolerant design with `2f+1` voters, a majority of `f+1` can make progress despite up to `f` unavailable voters. This is a common quorum design, not a rule for every consensus protocol. During a network partition, a majority-based group can make progress only on the side that can reach a majority.

**Leader election** chooses which member may coordinate work for a term or epoch. In Raft, election is one part of the consensus protocol; other systems use different mechanisms. A lease can limit how long authority lasts, but it depends on carefully defined timing assumptions.

Networks do not tell a node whether its peer has crashed or is only slow. Terms or epochs let members recognize newer protocol state and reject stale protocol messages. They do not by themselves stop an old leader from writing to an external system; the resource may need to check a fencing token or another ownership condition.

---

## First Principles

Consensus exists because state machines need agreement to stay identical:

1. **Replicated state machines need the same ordered commands.** If each replica applies a different order, or applies nondeterministic logic, their state can diverge.
2. **Messages can be delayed and machines can fail.** A protocol needs rules for deciding when a change is accepted and when a member must wait.
3. **A quorum is one common way to make progress safely.** Its size and fault assumptions depend on the protocol. Systems that need to protect an external resource may also need fencing, which the resource itself must enforce.

**Example:** three replicas process account updates. One replica proposes a transfer command; the protocol records the command in a safe order before replicas apply it. If one replica is unreachable, a majority-based group may still commit with the other two. If the group cannot form a majority, it waits instead of letting isolated replicas create conflicting histories.

## Why it matters

Consensus is used by:
- Replicated databases and metadata controllers (for example, MongoDB replica sets and Kafka's KRaft controller quorum; PostgreSQL deployments commonly pair streaming replication with a separate failover manager)
- Coordination services (etcd, ZooKeeper, Consul)
- Distributed locks (etcd/ZooKeeper use consensus-backed state; Redlock is a timed quorum-lease algorithm, not Raft)
- Strongly-consistent systems (Spanner, CockroachDB)

These examples use different protocols and assumptions. Understanding the agreement problem helps explain their behavior, but the systems are not interchangeable implementations of one identical design.

## Paxos (Leslie Lamport's consensus protocol)

**Two phases:**

### Phase 1: Prepare

- Proposer picks a unique proposal number N
- Sends "prepare(N)" to all acceptors
- If N exceeds its recorded promise, an acceptor durably promises not to accept lower-numbered proposals and returns its highest-numbered accepted proposal, if any. Otherwise it refuses this prepare.
- If a majority responds, proposer goes to Phase 2

### Phase 2: Accept

- Proposer adopts the value attached to the highest-numbered accepted proposal returned by the prepare quorum; only if none was accepted may it choose a new value
- Proposer sends "accept(N, value)" to all acceptors
- An acceptor accepts N only if it has not promised a higher proposal number. If a majority accepts the value, it is chosen.
- Acceptors persist promises and accepted proposals before acknowledging; a quorum of accepts chooses the value, even before a learner knows it

Paxos safety has formal proofs under its protocol assumptions. Production systems use specific Paxos variants, which can differ in their roles and operation. Systems including Google Chubby use Paxos-family protocols.

## Raft (designed to be understandable, 2014)

Raft decomposes consensus into 3 sub-problems:

### 1. Leader election

- Each node is in one of 3 states: Follower, Candidate, Leader
- All nodes start as Followers
- If a Follower doesn't hear from a Leader within a timeout, it becomes a Candidate
- Candidate advances its term, votes for itself and asks others for votes. A voter grants at most one vote per term and checks that the candidate's log is at least as up-to-date as its own.
- If a Candidate gets votes from a majority, it becomes the Leader
- Leader sends heartbeats to prevent needless elections while communication works; heartbeats alone do not authorize a write without the commit quorum.

### 2. Log replication

- Client sends command to Leader
- Leader appends to its log
- Leader sends "AppendEntries" to Followers
- Followers append to their log and reply
- The leader advances the commit index when a majority has replicated an entry from its current term; earlier-term entries become committed indirectly through that index
- Leader notifies Followers of commit, applies to state machine

### 3. Safety

- Voters compare last-log term, then index; a candidate needs an eligible majority, not necessarily the longest log on every isolated node.
- Committed entries are preserved across leader changes under Raft's protocol assumptions
- Properties: state machine safety, leader completeness, log matching

**Visualization:**

```
    Client
       │
       ▼
   [Leader] ─── heartbeat ──→ [Follower 1]
       │ ─── heartbeat ──→ [Follower 2]
       │ ─── heartbeat ──→ [Follower 3]
       │
   (Leader has the log, replicates to Followers)
```

Raft was designed to make the protocol easier to understand. Like other consensus protocols, it still requires careful implementation and operational choices.

**Used by:** etcd, Consul, CockroachDB, TiKV, many modern systems.

## Zab (ZooKeeper Atomic Broadcast)

ZooKeeper's protocol, similar to Paxos but optimized for the use case of "atomic broadcast" (all nodes see the same sequence of updates).

**Phases:**
- **Discovery:** Followers sync with the Leader, learn the latest epoch
- **Synchronization:** Leader sends missing transactions to Followers
- **Broadcast:** Normal operation, Leader proposes, Followers ack

**Used by:** Apache ZooKeeper, Apache HBase, Apache Kafka (older versions used it for controller quorum)

| Paxos variants | Google Chubby, Spanner | Coordination or replicated state |
| Raft | etcd, Consul, CockroachDB, TiKV | Replicated logs or metadata |
| Zab | ZooKeeper, HBase | Ordered updates in ZooKeeper |

**In interviews:** use Raft when the question is about a replicated log and its leader-election flow. If discussing a real product, name the protocol and version that product uses rather than assuming it uses Raft.

## Failure and split-brain boundaries

- **Timeout:** followers suspect a leader after a configured timeout; it may only be slow or disconnected.
- **Network partition:** an isolated old leader may still believe it leads while a majority elects a newer-term leader. It cannot commit fresh entries without a quorum.
- **Long pause or network delay:** followers may elect a new leader while the old one is paused or isolated. When the old leader learns of the newer term, it steps down. The protocol protects its own log; external writes may require fencing.
- **Timeout sensitivity:** short timeouts can cause unnecessary elections; long timeouts delay recovery. Leases also require explicit clock assumptions.

### Preventing split brain

- **Quorum:** in a majority-based protocol, only a group that can form a majority can elect a leader and commit changes.
- **Fencing tokens:** a protected resource rejects operations carrying an older token. This works only when the resource checks the token.
- **Leases:** time-bounded authority can reduce overlap when timing assumptions hold. For correctness-critical external writes, also make the resource reject stale owners.

## When to use consensus

**Use when:**
- Your database or metadata service uses leader-based replication and needs coordinated failover
- You need a coordination service (etcd, ZooKeeper, Consul)
- You need distributed locks
- You need strong consistency (Spanner, CockroachDB)
- You need service discovery (Consul uses Raft)

**Don't use when:**
- You can tolerate eventual consistency (most caches, feeds, counters)
- You have a single-node system (just run it directly)
- A local or asynchronous design can meet the business invariant with less coordination; measure the trade-off instead of adding consensus by default

## Trace a leader change

A, B and C are three voters. In term 4, A sends command X to B; both persist it. A commits X and acknowledges the client. A then becomes isolated.

B and C can form a majority. A newer-term election cannot safely choose a candidate whose log omits X against the voting rules: B will reject that stale candidate. B can win, replicate missing entries to C and continue under the commit rules. A may still call itself leader, but it cannot commit a fresh command alone. When it receives a higher-term protocol message, it steps down.

A read also needs a freshness rule. The old isolated A cannot simply answer from its local state because it remembers being leader. Safe Raft read paths establish current authority and an applied-state barrier under their documented protocol; serving from an arbitrary follower or stale leader is a different contract.

For application locks and external stale-writer protection, use [Distributed Locks](30.2.1.14-distributed-locks.md). The consensus log orders ownership changes; a resource outside that log must enforce the ownership value itself.

## When to discuss in interviews

When a system has a single-leader database, mention the consensus protocol:

- "PostgreSQL streaming replication does not elect a primary. We configure an external failover manager, promote a sufficiently caught-up standby, and fence the old primary."
- "We use etcd for service discovery. etcd uses Raft to maintain consistency across nodes."
- "In KRaft mode, Kafka uses a Raft-based controller quorum for cluster metadata. Check the Kafka release documentation for the migration path supported by the deployment."

When asked "what if the leader dies?":

- "Followers suspect a leader after an election timeout and may start an election. In Raft, a candidate needs votes from a majority and must have an up-to-date log. Recovery time depends on timeout settings, failures and network conditions, so I would measure it rather than promise a fixed duration."

When asked "what if the network partitions?":

- "In a majority-based protocol, only a side that can form a quorum can elect a leader and commit changes. The isolated old leader cannot commit without a quorum; when it learns a higher term, it steps down."

## Anti-patterns

- **Adding consensus without a consistency requirement.** Coordination adds network work and can prevent a minority partition from committing; use it when the invariant needs that agreement.
- **Implementing Paxos/Raft yourself.** Use a battle-tested library. The failure modes are subtle.
- **Two voting nodes.** Their majority is 2, so losing either prevents progress. Three voters tolerate one failure; five tolerate two.
- **No fencing.** Old leader can still write if it doesn't know it was replaced.
- **Promising a fixed election time.** Failover time depends on configuration and conditions; define and measure a recovery objective for the actual cluster.

---

## Summary

Consensus protocols let replicas agree on an ordered set of changes despite specified failures. Raft is designed to make this process easier to follow; Paxos is another family of protocols. A leader is useful only while it has authority under the protocol. Quorums, terms and safe failover rules prevent two nodes from committing conflicting histories. Timeouts detect suspected failure; they do not prove a node is dead.

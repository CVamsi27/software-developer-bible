# Failure Modes

## Definition

A **failure mode** is the way a component stops meeting its contract. For example, a request timeout might mean the service is down, the network is slow, or the write succeeded but its response was lost. Those cases need different handling.

| Failure class | Example | Possible response |
| ----------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Crash or unavailable | Process exits or host loses power | Detect it, stop routing new work there, and fail over only if the replacement has safe state |
| Slow or missing response | Network delay, overloaded dependency | Apply a deadline; retry only when the failure is transient and repeating the operation is safe |
| Incorrect or corrupted result | Bug, bad input, damaged data | Validate invariants, preserve evidence and recover from a trusted source; checksums can detect some corruption but do not repair it |
| Saturation | Queue, memory, connection pool or CPU limit reached | Bound work, shed optional load or add capacity after finding the bottleneck |
| Correlated failure | Shared region, configuration or release affects many instances | Separate failure domains, stage changes and test restore procedures |
| Security compromise | Credentials or data are exposed | Contain access, preserve evidence, rotate affected credentials and follow incident procedures |

Failure assumptions matter. A replicated system may recover from one machine stopping, but replicas can share a bad release, mistaken deletion or compromised credential. Byzantine fault-tolerant protocols address specific incorrect-node behavior under strict assumptions; ordinary health checks, checksums and extra replicas do not provide that guarantee.

"Plan for failure" means naming what failed and which contract is affected before choosing a mitigation.

---

## First Principles

Failure handling begins with three practical constraints:

1. **A timeout is a suspicion, not proof.** A slow peer and a dead peer can look the same. Choose deadlines from the caller's remaining time and expect occasional false suspicions.
2. **Retries can repeat work.** A timed-out request may already have changed data. Retry only transient errors, cap attempts, add jitter, and use idempotency or reconciliation for mutations.
3. **One failure can create another.** Retries, queues and shared pools can turn a small outage into overload. Bound work and protect critical paths.

Redundancy helps only when the replacement does not share the same failure and can serve correct state.

## Why it matters

For each component, decide what callers observe, what data might be lost or stale, how recovery starts and how the team will know it worked.

---

## The "What if X fails?" Framework

For every component in your system, ask:

1. **What if it fails entirely?**
2. **What if it fails partially (degraded mode)?**
3. **What if it's slow (not failed, but bad)?**
4. **What if it's wrong (returns bad data)?**
5. **What if it's a security incident?**

Then design mitigations for each.

**Example: Database**

| Condition | Question to answer | Safe response to consider |
| -------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Primary unavailable | Can a standby be promoted without losing acknowledged writes? | Promote according to the replication contract; otherwise pause writes and report the interruption |
| Slow or saturated | Are reads allowed to be stale? Is the connection pool saturated? | Bound query and queue work; use a replica or cache only when the staleness contract permits it |
| Suspected corruption | Which backup and log position are trusted? | Contain writes, preserve evidence, restore and validate, then reconcile changes after the recovery point |
| Database compromised | Which identities or data may be affected? | Contain access, rotate credentials and follow the incident and notification process |

**Example: API server**

- If an instance exits, route new requests to healthy instances and let in-flight operations follow their timeout/idempotency contract.
- If all instances are saturated, shed optional work or limit admission rather than accepting an unbounded queue.
- If a release is faulty, disable the affected feature or roll back using the deployment plan.
- If credentials or user data may be exposed, treat it as an incident; a WAF or restart alone does not resolve it.

## Specific Patterns for Failure

### 1. Retries with exponential backoff

Use bounded exponential backoff with jitter for transient failures. Choose the cap and attempt budget so retries fit inside the caller's overall deadline. The values below are illustrative; a mutation also needs an idempotency or reconciliation contract.

```
attempt 1: try
attempt 2: wait for a short interval plus random jitter, then try
attempt 3: wait longer, up to the configured cap, then try
...
stop when the attempt or deadline budget is exhausted
```

### 2. Circuit breaker

If a dependency keeps failing, a circuit breaker can temporarily reject calls so they do not consume local resources. It is useful only when the caller has a safe fallback or can return a clear error.

```
CLOSED: normal operation, count failures
  if failures > threshold:
    → OPEN: reject calls for a configured interval
OPEN: reject all calls
  after the interval:
    → HALF_OPEN: allow a limited number of test calls
HALF_OPEN: allow limited test calls
  if success:
    → CLOSED
  if failure:
    → OPEN
```

Circuit breakers are available in application libraries and service proxies; check how the chosen implementation handles cancellation, half-open probes and metrics.

### 3. Bulkhead

Isolate resources so one failure doesn't take down everything.

```
Example: reserve separate bounded capacity for critical requests,
search and optional recommendations. Pick limits from measured load
and resource use.

If search stalls, it cannot consume every worker or connection needed by critical requests.
```

### 4. Bound waits on dependencies

Network and storage operations need bounded waits. Propagate the remaining request deadline so nested calls do not each consume the full original budget. Set limits from service behavior and user-facing latency objectives.

```
incoming request deadline
  dependency A consumes part of the remaining budget
  dependency B receives only the time still available
reserve time to combine the response and return it
```

### 5. Graceful degradation

When an optional component fails, a safe fallback may preserve part of the user experience. Do not hide failures that affect correctness or data safety.

```
Recommendation service down → show "Popular" instead of "Recommended for you"
Map service down → show list of locations instead of map
Search service down → show cached results only if they meet freshness and authorization requirements
```

### 6. Chaos engineering

Chaos engineering runs controlled experiments to check whether a system meets a reliability hypothesis. Start in a safe environment; production experiments need explicit scope, monitoring, abort conditions and an approved blast radius.

- Experiments may inject latency, stop a process or interrupt a dependency, depending on the tool and environment.

### 7. Backups and disaster recovery

- Set backup and restore-test schedules from the required recovery objectives and data-change rate.
- Test restoration and validate recovered data; a backup that cannot be restored is not a recovery plan.
- A second region helps only when it has independent failure modes and a tested failover path.
- **Recovery Time Objective (RTO):** the target time to restore the service after a disruption.
- **Recovery Point Objective (RPO):** the maximum acceptable data-loss window, usually stated as time before the disruption.

## Failure Mode Catalog

Here are common failure modes you should be able to discuss:

### 1. Network partition

**What:** Two parts of the system can't talk to each other.

**Effect:** Some nodes cannot reach others. Depending on the protocol and operation, the system may reject writes, serve stale reads or risk conflicting updates.

**Mitigation:** define which operations require a quorum and which may return stale or unavailable results; test the chosen failover and reconciliation behavior.

### 2. Split brain

**What:** Two nodes both think they're the leader.

**Effect:** Both accept writes. When partition heals, conflict.

**Mitigation:** protocol-specific quorum rules and fencing enforced by the protected resource. A lease or witness helps only under its documented failure and timing assumptions.

### 3. Cascading failure

**What:** Service A fails, which causes B to overload, which fails, which causes C to fail...

**Effect:** Whole system goes down even though only one component failed.

**Mitigation:** Circuit breakers, bulkheads, timeouts, rate limiting, load shedding, capacity planning.

### 4. Thundering herd

**What:** Many requests all hit at once (after a pause, after a cache miss, after a deploy).

**Effect:** Service overload.

**Mitigation:** Jitter on retries, cache stampede protection, rolling deploys, pre-warming.

### 5. Slow client

**What:** A client sends data very slowly, holding a connection open.

**Effect:** Connections, request handlers or other bounded resources can be held long enough to reduce capacity for other callers.

**Mitigation:** Bound read and idle times, cap request sizes, and consider per-client limits with awareness that many users may share one source IP.

### 6. Data corruption

**What:** Bad data ends up in the database (bug, hardware, manual mistake).

**Effect:** Wrong results, downstream errors.

**Mitigation:** constraints and validation can prevent some invalid writes; checksums and audits can help detect problems; use a tested restore and reconciliation plan for recovery.

### 7. Runaway process

**What:** A bug causes a process to consume 100% CPU/memory.

**Effect:** Service slow or down.

**Mitigation:** resource limits, bounded queues, monitoring and cancellation. Restart only when recovery is safe; a restart does not repair a leak or bad work pattern.

### 8. Deadlock

**What:** Two transactions each hold a lock needed by the other and cannot proceed.

**Effect:** Both wait until a lock manager detects the cycle or a timeout/error interrupts the work.

**Mitigation:** consistent lock ordering and database deadlock detection. Retry a rolled-back transaction only when the retry is safe and bounded; a timeout alone does not resolve every deadlock.

### 9. Cache poisoning

**What:** Bad data in the cache, served to all users.

**Effect:** Wrong results across the system.

**Mitigation:** validate cache payloads, include tenant and authorization scope in keys, and prevent untrusted input from writing shared entries. TTL limits duration but does not prevent poisoning.

### 10. DNS failure

**What:** DNS resolution fails or returns an incorrect answer (for example, a provider outage or compromised record).

**Effect:** Clients that need the affected DNS answer may be unable to reach that endpoint.

**Mitigation:** understand resolver caching and TTLs, monitor resolution from relevant networks, and plan an alternate endpoint where the architecture supports one. A hard-coded IP can become stale or bypass routing controls.

### 11. TLS certificate expiration

**What:** A certificate expires or renewal fails.

**Effect:** Clients may reject connections to the affected hostname or service until the certificate chain is fixed.

**Mitigation:** automate renewal where possible and alert early enough to detect and fix renewal failures before expiry.

### 12. Time skew

**What:** Servers' clocks drift.

**Effect:** Clock differences can make one service reject a still-valid token or accept a token another service considers expired. Leases and ordering rules can also fail if their clock assumptions are violated.

**Mitigation:** synchronize wall clocks, use monotonic clocks for elapsed durations, and follow each protocol's stated clock-skew assumptions. Clock synchronization does not make an unsafe lease safe.

### 13. Payment or other external-provider outage

**What:** A request times out or the provider is unavailable. The provider may have completed the action even though the caller did not receive its response.

**Effect:** Blind retry or switching providers can charge twice or create inconsistent records.

**Mitigation:** use the provider's idempotency contract, store the operation identity, retry only under that contract, and reconcile unknown outcomes. Queue non-urgent notifications with bounded retry and deduplication. Do not fall back to a weaker authentication method when an identity provider is unavailable.

### 14. Bad release or configuration

**What:** A code change or configuration affects many instances at once.

**Effect:** A healthy fleet can fail together or corrupt data.

**Mitigation:** validate configuration, roll out gradually, monitor user-facing signals and keep a tested rollback or disable path. A rollback cannot undo data already changed by a migration or release.

### 15. Region or provider-wide outage

**What:** Multiple services fail together because they share a region, account, control plane or provider dependency.

**Effect:** Local redundancy may not help; failover can overload the remaining region or expose stale data.

**Mitigation:** define which workloads must recover elsewhere, the permitted data loss and stale-read behavior, and rehearse the failover. Multi-cloud is one possible strategy with significant operational cost, not a default requirement.

## Observability for Failure

Use telemetry to detect symptoms, connect them to a request and understand what users experience.

### 1. Metrics

- Request rate, error rate and request duration; percentiles can show slow requests hidden by an average.
- Resource use such as CPU, memory, disk and network, plus saturation such as queue depth and connection-pool use.
- Business outcomes that show whether users can complete the important workflow.

### 2. Logs

- Structured events with a request or trace identifier, useful context and an appropriate severity.
- Avoid sensitive data and unbounded high-cardinality fields.

### 3. Traces

- A trace links timed spans across one request's services and dependencies.
- Parent-child relationships help locate where time was spent and where an error began.

### 4. Real-user signals

- Browser errors and page behavior can reveal failures that server metrics miss.
- Connect these signals to user workflows without collecting unnecessary personal data.

## How to answer a failure question

State the assumed failure, the user-visible behavior, the data-safety rule, the recovery path and how you would verify recovery. Avoid inventing replica counts, failover times or spare capacity when the design has not specified them.

**Example:** If a primary database becomes unreachable, first establish whether the replica has all acknowledged writes and whether the failover process fences the old primary. If that is not guaranteed, pause writes rather than promote blindly. Reads may continue from a replica only if the product accepts its possible staleness. Measure detection, promotion and recovery time in the actual deployment.

---

## Anti-patterns

- **Unexamined single points of failure.** Know which components have no redundant path and what service behavior follows if they stop.
- **Synchronous calls without timeouts.** A slow service can hang your threads.
- **Unbounded or blind retries.** They can repeat mutations and increase load during an outage.
- **Circuit breakers without a safe fallback.** Rejection may make behavior worse if callers cannot handle it.
- **Degrading a correctness-critical path.** A clear error is safer than returning stale or misleading data.
- **No observability.** When something breaks, you have no idea why.
- **Untested recovery.** A documented failover or backup is not evidence that it works; rehearse restoring data and serving traffic again.

---

## Summary

Networks, machines, software and operators can all fail. Identify how each failure affects the user and the data, then choose protections such as deadlines, bounded retries, isolation between workloads and degraded responses. Measure failures so the team can detect and respond to them. Test recovery paths as well as normal behavior.

# Failure Modes

A payment request times out, but the provider may already have charged the card. The same observation can mean a dead service, a slow network, or a completed write whose reply was lost. Recovery starts by finding out which contract and side effect are uncertain — not by retrying automatically:

```text
payment timeout → charged? not charged? → find out before retrying.
```

## Definition

A **failure mode** is a pattern in which a component violates its **service contract** — by omitting a response, exceeding its latency limit, returning an invalid result, or losing acknowledged state.

> **Textbook Definition:** A failure mode is a way a system's externally specified service deviates from its intended behavior under particular conditions. In dependability analysis, a fault is a cause, an error is an incorrect internal state, and a failure is the resulting externally observable contract violation.

## First Principles

Failure handling begins with three practical constraints:

1. **A timeout is a suspicion, not proof.** A slow peer and a dead peer can look the same. Choose deadlines from the caller's remaining time and expect occasional false suspicions.
2. **Retries can repeat work.** A timed-out request may already have changed data. Retry only transient errors, cap attempts, add jitter, and use idempotency or reconciliation for mutations.
3. **One failure can create another.** Retries, queues, and shared pools can turn a small outage into overload. Bound work and protect critical paths.

Redundancy helps only when the replacement shares neither the same failure nor the same bad state.

A **fault** is a cause, such as a severed cable; it can create an **error**, such as a replica missing a committed update. That error becomes a **failure** when a caller sees stale data or loses an acknowledged write. A timeout is an observation at one caller, not a complete diagnosis: another caller may still reach the service, and the timed-out write may already be durable. This **partial failure** is why a distributed system needs explicit uncertainty and recovery states.

A **crash-stop** model assumes a process stops permanently; **crash-recovery** lets it return with specified durable state. A **fail-stop** assumption additionally lets others reliably detect that stop. In an asynchronous network without bounded delays, a missed heartbeat cannot supply that certainty. State which model a protocol assumes before treating timeout detection as proof that a former owner can no longer act.

Failure assumptions matter: a replicated system may recover from one machine stopping, but replicas can share a bad release, mistaken deletion, or compromised credential. Byzantine fault-tolerant protocols address specific incorrect-node behavior under strict assumptions; ordinary health checks, checksums, and extra replicas never provide that guarantee.

## 1. Review each dependency's failure boundary

| Failure class | Example | Possible response |
| ----------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Crash or unavailable | Process exits or host loses power | Detect it, stop routing new work there, and fail over only if the replacement has safe state |
| Slow or missing response | Network delay, overloaded dependency | Apply a deadline; retry only when the failure is transient and repeating the operation is safe |
| Incorrect or corrupted result | Bug, bad input, damaged data | Validate invariants, preserve evidence and recover from a trusted source; checksums can detect some corruption but do not repair it |
| Saturation | Queue, memory, connection pool or CPU limit reached | Bound work, shed optional load or add capacity after finding the bottleneck |
| Correlated failure | Shared region, configuration or release affects many instances | Separate failure domains, stage changes and test restore procedures |
| Security compromise | Credentials or data are exposed | Contain access, preserve evidence, rotate affected credentials and follow incident procedures |

Name the fault, the internal error it can create, and the caller-visible contract at risk before choosing a mitigation.

For each dependency, ask these questions in order:

1. What fault can occur, and which requests or users can it affect?
2. What will callers observe, including stale or missing results?
3. Could the operation already have changed data or caused an external side effect?
4. How will the team contain the fault and recover safely?
5. What evidence will show the user workflow and data invariant are healthy again?

Consider total outage, partial failure, slowness, incorrect output, and compromise wherever they change the contract.

**Example: Database:**

| Condition | Question to answer | Safe response to consider |
| -------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Primary unavailable | Can the standby preserve acknowledged writes, and can the old primary be fenced? | Promote only under the replication contract and fence the former primary; otherwise pause writes and report the interruption |
| Slow or saturated | Are reads allowed to be stale? Is the connection pool saturated? | Bound query and queue work; use a replica or cache only when the staleness contract permits it |
| Suspected corruption | Which backup and log position are trusted? | Contain writes, preserve evidence, restore and validate, then reconcile changes after the recovery point |
| Database compromised | Which identities or data may be affected? | Contain access, rotate credentials and follow the incident and notification process |

**API server:** if one instance exits, route new work to healthy instances and let in-flight operations follow their deadline and idempotency contract. If all instances saturate, limit admission or shed optional work instead of accepting an unbounded queue. If a release is faulty, disable the affected feature or roll back — first checking whether a migration changed data that rollback cannot restore. If credentials or user data may be exposed, contain access and follow incident procedures; a restart or web application firewall (WAF) rule alone never resolves it.

## 2. Bound time, retry safely, stop feeding failure

Bound time and admitted work first. Then retry only operations safe to repeat, and use isolation or fallbacks to limit the impact on other requests.

**Propagate deadlines:** network and storage operations need bounded waits. Propagate the remaining request deadline so nested calls never each consume the full original budget. Set limits from service behavior and user-facing latency objectives:

```text
incoming request deadline
  dependency A consumes part of the remaining budget
  dependency B receives only the time still available
reserve time to combine the response and return it
```

**Retry within a safe budget:** use bounded exponential backoff with jitter for transient failures. Choose the cap and attempt budget so retries fit inside the caller's overall deadline. The values below are illustrative; a mutation also needs an idempotency or reconciliation contract. Treat overload separately: retry only when rejection is local and another destination may have capacity. If the service is broadly saturated, retries add work to the bottleneck; fail clearly or defer within a bounded queue:

```text
attempt 1: try
attempt 2: wait for a short interval plus random jitter, then try
attempt 3: wait longer, up to the configured cap, then try
...
stop when the attempt or deadline budget is exhausted
```

**Stop feeding a failing dependency:** if a dependency keeps failing, a circuit breaker can temporarily reject calls so they consume no local resources. It is useful only when the caller holds a safe fallback or can return a clear error:

```text
CLOSED: normal operation, count failures
  if failures > threshold:
    → OPEN: reject calls for a configured interval
OPEN: reject all calls
  after the interval:
    → HALF_OPEN: allow a limited number of test calls
HALF_OPEN: allow limited test calls
  if success:
    → CLOSED
  if failure:
    → OPEN
```

Circuit breakers live in application libraries and service proxies; check how the chosen implementation handles cancellation, half-open probes, and metrics.

## 3. Isolate pools, degrade optionally, plan recovery

**Isolate resource pools** so one failure cannot take down everything:

```text
Example: reserve separate bounded capacity for critical requests,
search and optional recommendations. Pick limits from measured load
and resource use.

If search stalls, it cannot consume every worker or connection needed by critical requests.
```

**Degrade only optional behavior:** when an optional component fails, a safe fallback may preserve part of the user experience. Never hide failures affecting correctness or data safety:

```text
Recommendation service down → show "Popular" instead of "Recommended for you"
Map service down → show list of locations instead of map
Search service down → show cached results only if they meet freshness and authorization requirements
```

**Test failure assumptions:** chaos engineering runs controlled experiments checking whether a system meets a reliability hypothesis. Start in a safe environment; production experiments need explicit scope, monitoring, abort conditions, and an approved blast radius. Experiments may inject latency, stop a process, or interrupt a dependency, depending on tool and environment.

**Plan data recovery:** set backup and restore-test schedules from the required recovery objectives and data-change rate. Test restoration and validate recovered data — a backup that cannot be restored is no recovery plan. A second region helps only with independent failure modes and a tested failover path. **Recovery Time Objective (RTO):** the target time to restore the service after a disruption. **Recovery Point Objective (RPO):** the maximum acceptable data-loss window, usually stated as time before the disruption.

## 4. Recognize the failure cases by domain

These cases differ in cause and recovery. Use the same review sequence, but choose mitigations for the actual failure domain.

**Communication and authority:**

- **Network partition** splits the system so parts cannot talk — some nodes become unreachable, and depending on protocol and operation the system may reject writes, serve stale reads, or risk conflicting updates. Define which operations require a quorum and which may return stale or unavailable results; test the chosen failover and reconciliation.
- **Split brain** leaves two nodes both believing they are leader, so both may attempt writes. A safe quorum protocol stops an isolated leader committing fresh log entries, but an unfenced external resource can still accept conflicting writes — combine protocol-specific quorum rules with resource-enforced fencing (a lease or witness helps only under its documented failure and timing assumptions).
- **DNS (Domain Name System) failure** (provider outage or compromised record) strands clients needing the affected answer: understand resolver caching and TTLs, monitor resolution from relevant networks, and plan an alternate endpoint where the architecture supports one — a hard-coded IP can go stale or bypass routing controls.
- **TLS (Transport Layer Security) certificate expiration** makes clients reject connections until the chain is fixed: automate renewal where possible and alert early enough to catch renewal failures before expiry.
- **Time skew** breaks token validity, leases, and ordering rules: synchronize wall clocks, use monotonic clocks for elapsed durations, and follow each protocol's stated clock-skew assumptions — synchronization never makes an unsafe lease safe.

**Capacity and process behavior:**

- **Cascading failure** (A fails → B overloads → B fails → C fails) can sink the whole system from one component: use circuit breakers, bulkheads, timeouts, rate limiting, load shedding, and capacity planning.
- **Thundering herd** (many requests at once after a pause, cache miss, or deploy) overloads the service: add jitter to retries, stampede protection, rolling deploys, pre-warming.
- **Slow client** trickling data holds connections and bounded resources open, starving other callers: bound read and idle times, cap request sizes, and consider per-client limits aware that many users may share one source IP.
- **Runaway process** (bug consuming 100% CPU/memory) slows or stops the service: apply resource limits, bounded queues, monitoring, and cancellation — restart only when recovery is safe, since restart repairs no leak or bad work pattern.
- **Deadlock** (two transactions each holding the other's needed lock) stalls both until a lock manager detects the cycle or a timeout/error interrupts: use consistent lock ordering and database deadlock detection, and retry a rolled-back transaction only when the retry is safe and bounded — a timeout alone never resolves every deadlock.

**Data and external dependencies:**

- **Data corruption** (bug, hardware, manual mistake) produces wrong results and downstream errors: constrain and validate writes to prevent some invalid data, use checksums and audits to help detect problems, and recover with a tested restore and reconciliation plan.
- **Cache poisoning** serves bad data to all users: validate cache payloads, include tenant and authorization scope in keys, and stop untrusted input writing shared entries — TTL limits duration but never prevents poisoning.
- **Payment or external-provider outage** may hide a completed action behind a timeout: a blind retry or provider switch can charge twice or create inconsistent records. Use the provider's idempotency contract, store the operation identity, retry only under that contract, and reconcile unknown outcomes.

For notifications, queue non-urgent work with bounded retry and deduplication. For authentication, never fall back to a weaker method when an identity provider is unavailable.

**Changes and disaster recovery:** a **bad release or configuration** can fail a healthy fleet together or corrupt data: validate configuration, roll out gradually, monitor user-facing signals, and keep a tested rollback or disable path — rollback cannot undo data already changed by a migration or release.

A **region or provider-wide outage** defeats local redundancy when services share a region, account, control plane, or provider dependency, and failover can overload the remaining region or expose stale data: define which workloads must recover elsewhere, the permitted data loss and stale-read behavior, and rehearse the failover. Multi-cloud is one possible strategy with significant operational cost, never a default requirement.

## 5. Detect symptoms and verify recovery

A dependency normally takes 100 ms, then slows to two seconds. At the same arrival rate, more requests stay in flight and occupy connections. If each timed-out caller retries twice, the dependency can receive three attempts per logical request precisely when it holds less spare capacity. First bound admitted work and propagate an overall deadline. Retry only a transient failure under a safe identity, with capped attempts and jitter. A separate pool can preserve critical work while optional calls wait or fail. After recovery, confirm queued retries create no second overload wave. A restart or additional replica helps only if it addresses the actual resource and failure domain.

One alert rarely proves the cause. Combine caller-visible outcomes with saturation, dependency health, and traces; after recovery, verify both the user workflow and the data invariant.

- **Metrics:** request rate, error rate, and duration — percentiles expose slow requests that an average hides; resource use (CPU, memory, disk, network) plus saturation (queue depth, connection-pool use); business outcomes showing whether users complete the important workflow.
- **Logs:** structured events with a request or trace identifier, useful context, and appropriate severity — without sensitive data or unbounded high-cardinality fields.
- **Traces:** a trace links timed spans across one request's services and dependencies; parent-child relationships locate where time went and where an error began.
- **Real-user signals:** browser errors and page behavior can reveal failures server metrics miss; connect these signals to user workflows without collecting unnecessary personal data.

## Summary

Networks, machines, software and operators can all fail. Identify how each failure affects the user and the data, then choose protections such as deadlines, bounded retries, isolation between workloads, and degraded responses. Measure failures so the team can detect and respond to them. Test recovery paths as well as normal behavior.

# Capacity Planning & Back-of-Envelope Estimation

> **"How many servers do I need?"** Resource-sensitive designs need this estimate. You need to estimate QPS, storage, bandwidth, and CPU from first principles. This is the skill that turns a vague answer into a concrete plan.

## Definition

**Capacity planning** is the arithmetic that converts product assumptions into infrastructure requirements: given *N* users doing *k* actions per day, how many requests per second, how many bytes, how many instances, and how much headroom does the system need?

> **Textbook Definition:** Capacity planning estimates and validates the compute, storage, network, and concurrency resources required to sustain a workload while meeting performance and recovery objectives with measured headroom.

It is a **dimensional analysis**, not a benchmark — each requirement comes from a rate multiplied by a cost:

| Requirement | Identity | Typical unit |
| ------------ | ------------------------------------------------------------------ | ------------------------------------------- |
| Request rate | `DAU × actions/day ÷ 86,400`; estimate the actual peak separately | QPS |
| Storage | `writes/s × bytes/write × seconds retained` | GB, TB |
| Bandwidth | `requests/second × bytes/response` | bytes/second; multiply by 8 for bits/second |
| Concurrency | **Little's Law**: `L = λ × W` (in-flight = arrival rate × latency) | connections |
| Node count | `peak QPS ÷ per-node QPS at target utilization` | instances |

Two constraints make it an interview skill rather than a spreadsheet: **you must state your assumptions** (the numbers are only as good as the inputs, so the reasoning is what is evaluated), and **you should use rounded estimates with appropriate units** — `1M`, `10M`, `100M` — because the goal is to find which term dominates and where the design breaks (e.g. does the estimated peak workload exceed measured database capacity?).

---

## First Principles

Capacity planning is arithmetic you owe the business, derived from demand:

1. **Everything starts as per-user math**: RPS = DAU × actions/day ÷ seconds-in-day (peaked by a concentration factor), storage = objects × size × retention, bandwidth = read/write ratio × object size. The interview skill *is* this arithmetic done calmly.
2. **Headroom is priced, not guessed**: peak-to-average ratio, growth runway (12–18 months), N+1 redundancy for failure (→ 50.4's error budgets). Every unit of headroom costs money continuously — sizing is a lease-vs-buy-style trade.
3. **Bottlenecks move.** Add CPUs and the DB pool saturates; add pool and the network saturates. Capacity planning is therefore a *chain* analysis (USE: utilization, saturation, errors at every hop), never a single-number estimate.

## Turn demand assumptions into a testable sizing hypothesis

A server count is useful only when its inputs are clear: peak demand, measured per-instance throughput at an acceptable latency, failure headroom and downstream limits. A precise-looking number without those inputs is still a guess.

Use rough arithmetic to identify likely pressure points, then test them. A particular user count does not by itself imply database sharding; workload shape, data size, query cost and operational constraints determine whether simpler scaling is sufficient.

## Estimate five resource demands

### 1. QPS (Queries Per Second)

**How many requests per second does your system handle?**

```
DAU = Daily Active Users
requests_per_user_per_day = typical user action count
QPS_avg = DAU × requests_per_user_per_day / 86,400
QPS_peak = QPS_avg × assumed_or_measured_peak_factor
```

**Example:**
```
DAU = 10M
requests_per_user_per_day = 100 (browse, search, click, etc.)
QPS_avg = 10M × 100 / 86,400 = ~11,500 QPS
QPS_peak = 11,500 × 3 = ~35,000 QPS
```

**Tip:** Use round numbers. 10K, 50K, 100K, 1M. Not 11,574.

### 2. Storage

**How much data does your system store?**

```
writes_per_day = write_QPS × 86,400
bytes_per_day = writes_per_day × bytes_per_record
retained_bytes = bytes_per_day × retention_days
physical_bytes = retained_bytes × replica_count + index/metadata overhead
```

**Example:**
```
DAU = 10M
actions_per_user_per_day = 100
fraction_written = 0.1 (only 10% of actions are writes, rest are reads)
writes_per_day = 10M × 100 × 0.1 = 100M writes/day
size_per_record = 1 KB
storage_per_day = 100M × 1 KB = 100 GB/day
retention = 365 days
total_storage = 100 GB × 365 = 36,500 GB = ~36 TB
```

**Example replication assumption:**
```
With 3x replication: 36 TB × 3 = 108 TB
```

### 3. Bandwidth

**How much network traffic?**

```
ingress_per_sec = QPS × request_size
egress_per_sec = QPS × response_size
total_per_sec = ingress + egress
```

**Illustrative example:**
```
QPS = 35,000
request_size = 1 KB (typical REST request)
response_size = 10 KB (typical REST response)
ingress = 35,000 × 1 KB = 35 MB/s
egress = 35,000 × 10 KB = 350 MB/s
total = ~400 MB/s
```

**Check:** A CDN offloads only eligible cached responses. Personalized or authorization-sensitive reads still require their defined origin/validation path.

### 4. Memory / Cache

**How much memory for in-memory cache?**

```
cache_size = distinct_cached_items × serialized_bytes_per_item + measured_overhead
```

**Example:**
```
DAU = 10M
DAU_peak_concurrent = 10M × 0.1 = 1M (10% concurrent at peak)
items_per_user = 50 (user profile, settings, recent activity, etc.)
size_per_item = 10 KB
cache_size = 1M × 50 × 10 KB = 500 GB
```

**Check:** Measure the working set and hit-rate curve; a universal 80/20 split does not determine the correct cache size.

### 5. CPU

**How many CPU cores?**

```
cpu_cores = (QPS × cpu_time_per_request) / cpu_utilization_target
```

**Example:**
```
QPS = 35,000
cpu_time_per_request = 10 ms = 0.01 sec
cpu_utilization_target = 0.5 (don't run at 100%)
cpu_cores = 35,000 × 0.01 / 0.5 = 700 cores
```

**Tip:** Spread across N machines. 700 cores / 8 cores per machine = ~90 machines.

## Little's Law

**L = λ × W**

- **L** = number of items in the system (concurrent requests)
- **λ** = arrival rate (items per second)
- **W** = average time an item spends in the system (seconds per item, including queueing and service)

**Example:** 1000 requests/sec arrive. Each request takes 100ms. How many are in the system at once?
- L = 1000 × 0.1 = 100 concurrent requests

**Useful for:** Estimating average occupied capacity within one defined stable system boundary. A database pool uses database arrival rate and connection-hold time, not necessarily whole-request latency. Unstable queues have no finite steady-state average; do not multiply peak rate by p99 latency and call that Little's Law.

**Example only:** 100 simultaneously busy workers completing one 100 ms task at a time would complete about 1,000 requests per second if the workload has no other bottleneck. Real throughput depends on CPU, downstream waits, contention, request mix and saturation; measure it under representative load.

## Common interview scenarios

### Scenario 1: Twitter (timeline + tweet)

**Assumptions:**
- 200M DAU
- Each user tweets 2x/day, browses timeline 100x/day
- Each tweet ~300 bytes
- Each timeline page ~50 tweets × 300 bytes = 15 KB
- 5 year retention

**QPS:**
- Tweets: 200M × 2 / 86,400 = ~4,600 writes/sec
- Timeline reads: 200M × 100 / 86,400 = ~230,000 reads/sec

**Storage:**
- Tweets: 200M × 2 × 300 bytes = 120 GB/day
- 5 years: 120 × 365 × 5 = 219 TB
- With replication: 657 TB

**Bandwidth:**
- Tweets in: 4,600 × 300 B = 1.4 MB/s
- Timeline out: 230,000 × 15 KB = 3.5 GB/s
- Decide which responses are publicly cacheable; personalized timeline delivery cannot simply be assigned to a CDN.

### Scenario 2: Uber (ride matching)

**Assumptions:**
- 50M DAU
- 1M drivers
- Each user requests 5 rides/day
- Each ride: 100 driver locations × 1 KB = 100 KB

**QPS:**
- Ride requests: 50M × 5 / 86,400 = ~2,900 QPS
- Driver location updates: 1M drivers × 1 update / 30 sec = ~33,000 QPS

**Storage:**
- Ride records: 50M × 5 × 1 KB = 250 GB/day
- 1 year: 91 TB
- Driver locations: 1M × 2,880 updates/day × 1 KB = 2.88 TB/day; 30-day retention = 86.4 TB

**Real-time:** Geo queries are the bottleneck. Need geospatial index.

### Scenario 3: WhatsApp (messaging)

**Assumptions:**
- 2B users
- Each user sends 50 messages/day
- Each message ~1 KB (text only)
- Group messages broadcast to N members

**QPS:**
- Messages: 2B × 50 / 86,400 = ~1.2M QPS
- With group broadcasting (avg group 10): 12M message deliveries/sec

**Storage:**
- Messages: 2B × 50 × 1 KB = 100 TB/day
- 30-day retention: 3 PB

**Real-time:** WebSocket connections, fan-out, presence.

### Scenario 4: Netflix (video streaming)

**Assumptions:**
- 200M subscribers
- Each watches 2 hours/day
- Average bitrate 5 Mbps
- 80% from CDN, 20% from origin

**Bandwidth:**
- 200M × (2 × 3,600 seconds/day) × 5 Mbps ÷ 86,400 seconds/day ≈ 83.3 Tbps average delivery bandwidth. With the assumed 80% CDN hit fraction, origin bandwidth averages about 16.7 Tbps; peak demand and bitrate distribution need separate estimates.

**Storage:**
- Catalog: 10,000 titles × 50 GB (4K) = 500 TB
- Per user data: viewing history, preferences = small

**Real-time:** Recommendations, encoding pipeline.

## Common numbers to memorize

```
Decimal units used here: 1 KB = 1,000 bytes
Binary units: 1 KiB = 1,024 bytes
1 MB = 1,000 KB
1 GB = 1,000 MB
1 TB = 1,000 GB
1 PB = 1,000 TB

1 day = 86,400 seconds
1 month = ~30 days = 2.6M seconds
1 year = ~365 days = 31.5M seconds

Powers of 2:
2^10 = 1,024
2^20 = ~1M
2^30 = ~1B
2^40 = ~1T
```

Hardware latency and throughput depend on access pattern, request size, contention, virtualization and the actual device or network. Use measured figures for the target deployment. The reliable dimensional conversion is `1 Gbit/s ÷ 8 = 125 MB/s` before protocol overhead; it is not a promise that the workload can saturate that link.

## Estimation framework for interviews

**Step 1: State your assumptions (10 sec)**
"Assuming 10M DAU, 100 actions per user per day, 10% writes..."

**Step 2: Estimate QPS (30 sec)**
"QPS_avg = 10M × 100 / 86,400 = ~12K. Peak = ~36K."

**Step 3: Estimate storage (30 sec)**
"100M writes/day × 1 KB = 100 GB/day. 1 year = 36 TB. With 3x replication: 108 TB."

**Step 4: Estimate bandwidth (30 sec)**
"12K QPS × 10 KB response = 120 MB/s."

**Step 5: Estimate infrastructure (30 sec)**
"12K QPS / 1K QPS per server = 12 servers. With redundancy: 20."

**Total: 2-3 minutes.**

---

## Sanity check the answer

- Keep decimal/binary units consistent; separate bytes from bits and days from seconds.
- Include indexes, metadata, replicas, backups, temporary migration space and retention rather than only logical payload.
- Compare each demand with measured capacity at the required latency, including degraded operation.
- Check skew and bursts: average traffic can conceal a hot tenant or synchronized work.
- State uncertain inputs as ranges and explain which measurement would narrow them. An order-of-magnitude mistake can change the design; do not dismiss a tenfold error as harmless.

## Common mistakes

- **No assumptions stated.** "How many servers?" — "I don't know, depends." Bad.
- **Off by 1000x.** 10K vs 10M. Sanity check.
- **Ignoring peak shape.** Use the peak window that your service-level objective requires; the daily maximum may not be the right design target for every workload.
- **Ignoring data copies and recovery.** Estimate replicas and backups from the actual topology and retention policy; neither a fixed threefold multiplier nor replicas alone defines high availability.
- **Forgetting the read/write ratio.** Different QPS for reads vs writes.
- **Not accounting for cache hit rate.** With 90% cache hit, you only hit the DB 10% of the time.

## Turn throughput into a failure-aware instance count

Suppose a load test supports **1,000 requests/s per instance at the target latency**, and the sizing demand is 35,000 requests/s. At least 35 instances meet that tested steady workload if downstream capacity and traffic distribution remain comparable. To retain that capacity after losing one instance, provision at least 36; if losing one of three equally sized zones is the requirement, the remaining two zones must together supply 35 instances' measured capacity. Autoscaling delay and larger bursts may require additional headroom.

This is a hypothetical sizing trace, not a benchmark of this repository. Raising CPU count does not prove linear scaling; remeasure database, pool and network limits.

## Estimate cost from the actual topology

Use the current provider quote for region, instance type, billing hours and purchase model. Add databases, storage/IOPS, replicas, backup retention, network transfer, load balancers, telemetry and managed-service charges. Compare normal and recovery topology. A fixed monthly compute subtotal or universal multi-region multiplier omits those workload-dependent terms.

## Present the estimate in an interview

State assumptions, show the dominant rates and resource costs, then tie the proposed topology to tested capacity and recovery needs. Use rounded values while keeping units explicit. Revisit the estimate when the access pattern, retention or failure requirement changes; not every conceptual design question requires an exhaustive server budget.

## Summary

Capacity planning estimates resources from workload assumptions. Start with request rate, storage, bandwidth and concurrency, then state the assumptions and check dimensions. Little's Law uses average time in the system, including time waiting and being served. Treat estimates as hypotheses and validate them against measured workload and capacity.

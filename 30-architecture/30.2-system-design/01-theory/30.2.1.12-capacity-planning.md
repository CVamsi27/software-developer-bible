# Capacity Planning and Back-of-the-Envelope Estimation

A system serving ten million daily users may average only twelve thousand requests per second, yet a busy hour can push the peak near thirty-five thousand. A server count based on the daily average misses that peak; one based on a guessed peak wastes money. Capacity planning turns explicit workload assumptions into a sizing hypothesis, then checks it against measured behavior:

```text
10M users × 100 req/day ÷ 86,400 ≈ 11,600 req/s avg → ×3 peak ≈ 35,000 req/s.
```

## Definition

**Capacity planning** estimates the compute, storage, network, and concurrency resources needed to serve a workload within its performance, availability, and recovery objectives. The estimate starts from measured per-request cost and peak concurrency, then adds headroom for failure and growth before any purchasing decision.

> **Textbook Definition:** Capacity planning is the process of forecasting resource demand, comparing it with available capacity, and provisioning or adjusting resources so that a system can meet defined service objectives under expected and failure workloads.

## First Principles

Capacity depends on four things: the shape of demand, the cost of each operation, the service objective, and the failure the system must survive. An average is not a peak, a logical data size is not physical storage, and a per-instance benchmark is useful only at the target latency and workload mix.

Keep the assumptions visible. Use observed traffic when available; otherwise label a peak factor, growth range, cache behavior, and failure target as assumptions to validate. Retries, hot tenants, scheduled jobs, and fan-out can make downstream demand much larger than incoming request rate.

## 1. Convert one workload into rates and bytes

A user action is not necessarily one unit of work at every tier. One API request may issue several database queries, read cache entries, and publish events. Estimate demand separately at each constrained boundary. The calculations below use decimal storage units: 1 KB = 1,000 bytes, 1 GB = 1,000,000,000 bytes, 1 TB = 1,000 GB. Use KiB, GiB, and TiB when the system or provider reports binary units.

| Demand | Starting relationship | Useful unit |
| -------------------- | -------------------------------------------------------------------------- | ---------------------------------- |
| Offered request rate | users × actions per user ÷ time window, when each action makes one request | requests/s |
| Stored data | writes/s × bytes/write × retention | bytes |
| Network traffic | operations/s × bytes/operation | bytes/s or bits/s |
| Concurrent work | Little's Law: L = λ × W | items in a defined system boundary |
| Compute | operations/s × CPU time/operation | CPU-seconds/s, then cores |

Assume a service has **10 million daily active users**, each making **100 application programming interface (API) requests per day**. Assume the peak rate is **three times the daily average rate**. These are scenario inputs, not universal values.

**Request rate:** 1 billion requests per day gives an average of 1,000,000,000 ÷ 86,400 ≈ **11,600 requests/s**, and a peak estimate of 11,600 × 3 ≈ **35,000 requests/s**. The peak factor must come from a measured traffic profile or a stated planning assumption. Also separate reads, writes, background work, and retry traffic when they carry different costs.

**Storage:** assume 10% of API requests create a 1 KB record — 1 billion × 10% = **100 million records/day**, i.e. 100 million × 1 KB = **100 GB/day** logical. One year retained: 100 GB × 365 = **36.5 TB logical**. Three stored copies: 36.5 TB × 3 = **109.5 TB**, before indexes, metadata, logs, or temporary migration space. The three-copy figure is only an example replication layout. Backups, snapshots, and disaster-recovery copies hold their own retention and placement rules; never assume a replication multiplier covers them.

**Network traffic:** at the estimated 35,000 requests/s peak, assume a 1 KB request and 10 KB response — ingress 35,000 × 1 KB ≈ **35 MB/s**, egress 35,000 × 10 KB ≈ **350 MB/s**, combined payload about **385 MB/s** or **3.08 Gbit/s** before protocol overhead. A content delivery network (CDN) reduces origin traffic only for responses that are cacheable and actually served from cache. Personalized responses, cache misses, validation requests, and uploads still use their defined origin path. Compression and request mix change byte counts, so use representative measurements for production sizing.

**Cache memory:** suppose one million concurrently active users with a working set of 50 items per user averaging 10 KB each: 1,000,000 × 50 × 10 KB = **500 GB of serialized values**. This is a lower bound. Keys, indexes, allocator overhead, replication, and eviction headroom consume additional memory. Measure the working set and hit-rate curve; a fixed cache-hit percentage never determines the right cache size.

**CPU and instance count:** suppose each request consumes an average of **4 ms of central processing unit (CPU) time**. At 35,000 requests/s, CPU demand is 35,000 × 0.004 CPU-seconds = **140 cores at 100% utilization**, i.e. 140 ÷ 0.5 = **280 provisioned cores** at a 50% planning target. For an 8-vCPU instance, 50% utilization leaves about 4 vCPUs for this workload — roughly 1,000 requests/s per instance. That arithmetic is only a first estimate: validate it with a representative load test meeting the latency objective and including downstream work. If the test confirms 1,000 peak requests/s per instance, 35 instances serve the stated peak. To preserve throughput after losing one instance, provision at least 36. To survive losing any one of three equal availability zones, each zone needs capacity for 18 instances; 54 total leave 36 after a zone loss. Autoscaling delay, uneven load, and extra failure load may require more. This is a sizing example, not a benchmark: CPU may not bottleneck first — connection pools, databases, locks, network limits, or a hot partition may saturate earlier.

## 2. Apply Little's Law inside a stated boundary

Little's Law relates average arrival rate, average time in the system, and average number of items in that system: **L = λ × W**, where **L** is the average number of items in the chosen boundary, **λ** the average arrival rate through it, and **W** the average time each item spends there, including queueing and service.

At 1,000 requests/s with 100 ms average end-to-end time, the system holds about 100 requests in flight on average: 1,000 × 0.1 = 100. Choose the boundary carefully: to estimate occupied database connections, use database-call arrival rate and connection hold time, not whole-request latency. For example, 250 calls/s holding a connection for 40 ms use about 10 connections on average.

Little's Law describes a stable system over a representative interval. It never says multiplying a peak rate by p99 latency yields a valid concurrency estimate. If work arrives faster than it completes for long enough, the queue grows and no finite steady-state average exists.

## 3. Adapt the arithmetic to the workload shape

Different systems amplify different resources. Never force every estimate into API requests per second:

| Workload shape | Back-of-the-envelope demand | Likely pressure to investigate |
| -------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Fan-out | 100,000 events/s × 10 recipients = 1 million deliveries/s | Broker partitions, consumer throughput, duplicate work and outbound bandwidth |
| Device updates | 1 million devices ÷ 30-second interval ≈ 33,000 updates/s when evenly staggered | Ingestion bursts, hot keys, write amplification and retention |
| Live video | 1 million streams × 5 Mbit/s = 5 Tbit/s delivery | CDN capacity, regional placement and origin fill; if 80% of bytes are served from cache, origin still needs about 1 Tbit/s |

These examples expose scale, not a complete design. Fan-out is downstream delivery work, not necessarily broker publish rate. Video bitrate and cache-hit rate vary over time, so use distributions and peak windows rather than treating averages as guarantees.

## 4. Validate the plan against objectives

A capacity estimate becomes useful when each number holds a test or operational signal behind it:

1. Define the peak interval, request mix, growth horizon, latency objective, retention period, and failure scenario.
2. Convert each action into work at every relevant tier, including retries, fan-out, and scheduled jobs.
3. Load-test representative traffic and data at the target latency. Record throughput, CPU, memory, queue depth, connection usage, storage I/O, and errors.
4. Repeat for the required degraded state: instance or zone loss, failover, rebalancing, or recovery traffic.
5. Include indexes, metadata, replicas, backups, temporary migration space, telemetry, network transfer, and autoscaling delay in cost and headroom.
6. Treat uncertain inputs as ranges. Measure the assumption with the largest effect before committing to an expensive topology.

A single server count can hide the real bottleneck. Check utilization, saturation, and errors at each hop, then revisit the estimate when workload shape or service objectives change. For a budget, price the measured normal and recovery topologies, including compute, storage and I/O, backups, network transfer, and observability; provider, region, and purchase terms change the result.

## 5. Explain the estimate in an interview

Start by clarifying active users, actions, read/write mix, peak window, retention, latency objective, and failure target. State which values are observed and which are assumptions. Convert them into rates and storage with units, identify the likely bottleneck, then compare demand with measured capacity at the required latency. Close with the degraded-capacity plan and the measurement that would most change your answer.

Keep arithmetic rounded, but keep units and assumptions exact enough to audit. A tenfold error can change the architecture; rounding 11,574 requests/s to 12,000 is useful, while silently treating 1 KB as 1 MB is not.

## Summary

Capacity planning converts workload shape into resource demand, then validates that demand against service objectives and measured capacity. Estimate each constrained tier separately; account for peak traffic, data copies, retries, retention and the failure mode the system must survive. Use Little's Law only with averages from a clearly defined stable boundary. Treat the result as a testable hypothesis, not a benchmark.

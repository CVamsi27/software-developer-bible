# Backpressure & Flow Control

> **What happens when a producer sends faster than the consumer can process?** Sustained excess work must wait, slow down, be rejected or be discarded under an explicit policy.

## Definition

**Backpressure** is a **feedback signal from a consumer to its producer** that reduces the incoming rate to what the consumer can actually absorb. It helps bound accumulation; memory, deadlines, accepted-work durability and overload policy still need explicit limits.

> **Textbook Definition:** Backpressure communicates downstream capacity constraints upstream so production can slow or stop. Flow control regulates transfer to prevent a receiver or intermediary from accepting more work than it can handle.

Backpressure means a producer or intermediary responds to downstream capacity, for example by slowing intake, limiting in-flight work or returning a rejection. Bounded buffers help contain overload, but dropping or rejecting work is load shedding; it is not the same as making the producer slow down.

Related overload controls, each with a different acceptance and loss contract:

1. **Block / bounded buffer** — the producer waits when the receiver or buffer is full. This can preserve work while converting overload into latency; TCP flow control uses a receive window to limit bytes in flight, not to block an application directly.
2. **Drop / sample** — discard newest (or oldest) messages. Can reduce queued work but loses information. Use only where the telemetry or product contract permits that loss; required audit events are different.
3. **Load shedding** — reject at admission with a fast `503` with a bounded retry policy; retrying elsewhere can overload the same shared dependency. Preserves the healthy requests' latency; the receiver never even queues the doomed work.
4. **Rate limiting / QoS** — shape the input to a known serviceable rate.

The pattern to notice is that backpressure is a **protocol**, not a component: it needs the producer's cooperation (a signal it will honour) or an intermediary that enforces it (a proxy that caps concurrency per route). Reactive-streams libraries define exactly that protocol as `request(n)`.

---

## First Principles

If arrivals exceed completed work, the difference remains somewhere: queued objects, pending network writes or callers waiting for acceptance. A bounded receiver does not remove this work; it must communicate a limit or refuse it:

1. **Unbounded buffering is deferred collapse.** Accepting unlimited work while slower downstream just moves the crash later and makes it bigger (memory exhaustion, latency cliff). The honest alternatives: refuse (load shedding), defer (queue with bounds), or slow the producer (flow control, → 20.1.2.01).
2. **Flow control is a signal-propagation design**: consumer capacity must reach the producer *before* buffers fill — TCP receive windows bound transport bytes; Reactive Streams demand bounds emitted items; HTTP rejection can tell a caller to wait. These signals control different boundaries and do not automatically limit one another.
3. **Shedding policy is product strategy**: which requests get dropped under load (analytics > free-tier > checkout)? Fair queuing and priority classes turn "system overloaded" into "least important work waits" — the difference between an outage and a degradation.

## Why it matters

Backpressure helps contain overload when a slow dependency causes work to accumulate. It is one resilience control; capacity planning, timeouts, concurrency limits, retries and load shedding may also be needed.

## Trace the accumulating work

Assume 10,000 messages/s arrive and 1,000 messages/s finish. With a constant workload, unfinished work grows by 9,000 messages/s:

```text
0 seconds:       0 queued
1 second:    9,000 queued
10 seconds: 90,000 queued
~111 seconds: about 1,000,000 queued
```

The memory limit depends on message size and overhead; one million messages does not imply one universal crash point. A 10,000-message queue fills in about 1.11 seconds under this assumption. After that, the design must reduce admitted arrivals to the completion rate or reject/drop the excess. Blocking moves pressure upstream, so waiting callers also need a bound and deadline.

## 3 strategies

### 1. Blocking (apply backpressure upstream)

**Pattern:** Queue has a bounded size. When full, the producer blocks (waits).

```
producer.send(msg)
  → queue buffer (max 10K)
  → if buffer full, producer waits
  → consumer pulls, processes
  → buffer has space, producer resumes
```

**Pros:**
- Accepted work need not be discarded by this capacity policy; process crashes still need a durability contract
- Simple to implement (just a bounded queue)
- Natural rate limiting

**Cons:**
- Producer slows down (or blocks)
- May not be possible (HTTP request can't block forever)
- Can cause head-of-line blocking

**When to use:** Async systems where the producer can wait (workers, batch jobs).

**Examples:**
- BlockingQueue in Java
- Channel in Go
- asyncio.Queue in Python
- bounded queue in any language

**Teaching example:** Run in one JavaScript event loop with a positive integer capacity and non-null items. This bounds stored items, but it does not bound waiting producers, provide cancellation, fairness, consumer waiting or persistence. A real intake path also needs a finite waiter/deadline policy.

```typescript
// Node.js example with bounded stored items
class BoundedQueue<T> {
  private items: T[] = [];
  private maxSize: number;
  private resolvers: (() => void)[] = [];

  constructor(maxSize: number) {
    if (!Number.isSafeInteger(maxSize) || maxSize < 1) {
      throw new RangeError('Capacity must be a positive integer');
    }
    this.maxSize = maxSize;
  }

  async enqueue(item: T): Promise<void> {
    while (this.items.length >= this.maxSize) {
      // A woken writer must recheck: another writer may fill the slot.
      await new Promise<void>((resolve) => {
        this.resolvers.push(() => resolve());
      });
    }
    this.items.push(item);
  }

  async dequeue(): Promise<T | null> {
    if (this.items.length === 0) return null;
    const item = this.items.shift()!;
    // Wake up a blocked enqueue
    const resolve = this.resolvers.shift();
    if (resolve) resolve();
    return item;
  }
}
```

### 2. Dropping under an explicit loss policy

A finite queue can refuse a new telemetry sample or evict an older sample when full. Record the loss and choose which information matters more: recent state, full history or statistical sampling. Returning immediately bounds receiver storage, but does not ensure the rest of the system has spare CPU or network capacity.

Do not silently discard accepted payments, orders or required audit records. If work was promised durable acceptance, losing it violates that contract; reject before acceptance or use a durable recovery path.

### 3. Load shedding (reject some, keep rest)

**Pattern:** When overloaded, reject some requests (e.g., low-priority) but accept high-priority ones.

```
request arrives
  → if at capacity, check priority
  → if high priority: queue
  → if low priority: reject (return 503)
  → consumer pulls, processes
```

**Pros:**
- Protects important traffic
- System stays up
- Graceful degradation

**Cons:**
- Need to define priorities
- Some requests fail
- Need to communicate to client (retry?)

**When to use:** Mixed-priority workloads. Payment system: process payments, drop analytics. Search system: process user queries, drop bot traffic.

A priority policy still needs a hard bound. Reserving separate capacity for critical requests is easier to reason about than accepting every high-priority request indefinitely. If a new request evicts a queued request, the old caller/work record must receive a defined rejection or recovery action; silently replacing it breaks any earlier acceptance promise.

## Where to apply backpressure

| Layer | Mechanism |
| --------------------- | --------------------------------------------------------- |
| **Producer → Queue** | Bounded queue, blocking or drop |
| **Queue → Consumer** | Bound polling/prefetch or push credits and in-flight jobs |
| **Service → Service** | Timeouts, circuit breakers, load shedding |
| **Client → Server** | HTTP 429 (rate limited), Retry-After header |
| **DB queries** | Connection pool limits, query timeouts |
| **Network (TCP)** | Built-in flow control window |
| **Reactive streams** | Explicit backpressure protocol (request N items) |

---

## TCP flow control (the original backpressure)

TCP has built-in backpressure:
- Receiver has a "receive window" (how much data it can buffer)
- Sender doesn't send more than the window size
- As receiver processes data, window slides, sender can send more

TCP bounds unacknowledged transport data under its flow/congestion rules. An application can still read bytes quickly into an unbounded job queue, disconnecting network pressure from actual processing. Add an application-level bound where work accumulates.

---

## Reactive streams (RxJava, Project Reactor, Akka Streams)

Reactive Streams defines how a subscriber requests a finite number of items from a publisher. The publisher must not emit beyond the available demand. A subscriber can request more when it finishes work; asynchronous processing must account for completion rather than requesting unlimited work at subscription time.

Library operators may prefetch and buffer, and a source may reject overflow rather than suspend. Select bounded operator settings and understand whether demand reaches the original producer. A `subscribe` call alone does not prove no overflow or out-of-memory failure can occur.

## Specific patterns

### 1. Circuit breaker (sync systems)

When a downstream service is slow or failing, stop calling it. Return immediately with an error or fallback.

```
[CLOSED: normal, count failures]
  if failures > threshold:
    [OPEN: reject all calls for 30s]
[OPEN: reject]
  after 30s:
    [HALF_OPEN: try one call]
[HALF_OPEN]
  if success: [CLOSED]
  if fail: [OPEN]
```

**Libraries:** Hystrix (deprecated), Resilience4j, Polly (.NET), Istio.

**See:** [Microservices/04 Circuit Breaker](../../../20-backend/20.6-microservices/04-resilience/20.6.4.01-circuit-breaker.md) for the full deep-dive.

### 2. Bulkhead (isolation)

One slow service shouldn't take down everything. Isolate resources per service.

```
Thread pool for /search: 50 threads
Thread pool for /recommendations: 20 threads
Thread pool for /user/profile: 100 threads

If /search hangs, only its 50 threads are exhausted. The separate 20- and 100-thread pools remain available if no shared resource is exhausted.
```

**See:** [Microservices/14 Bulkhead Pattern](../../../20-backend/20.6-microservices/04-resilience/20.6.4.02-bulkhead-pattern.md).

### 3. Timeout everywhere

Bound each external operation by the caller's useful deadline and cancellation contract. A timed-out caller may leave remote work running; propagate cancellation where supported and reconcile uncertain side effects. The numbers below illustrate different budgets, not production defaults.

```
DB query: 5s timeout
HTTP call: 10s timeout
Cache read: 100ms timeout
Queue send: 1s timeout
```

### 4. Rate limiting (per consumer)

Limit how much any one consumer can use.

```
User A: 1000 req/min
User B: 1000 req/min
User C: 1000 req/min

This bounds one identity under the stated key policy; many identities or expensive requests can still exhaust shared capacity.
```

**See:** [Rate Limiting](30.2.1.08-rate-limiting.md).

### 5. Health checks + auto-scaling

Route away from instances that fail the relevant readiness contract. Scale only when added instances can relieve the measured bottleneck; provisioning delay and saturated shared databases require admission control during recovery. These example thresholds are policy choices, not guarantees:

```
[Load balancer]
  → Health check every 5s
  → If server unhealthy, remove from rotation
  → If all servers at > 80% capacity, scale out
```

## Push vs Pull

**Push (consumer is told to process):**
- Hard to apply backpressure
- Consumer must be ready or process asynchronously
- Risk: buffer overflow, OOM

**Pull (consumer asks for work when ready):**
- Natural backpressure
- Consumer controls rate
- Risk: underutilization if consumer is slow

**In practice:** Pull lets a consumer control fetch rate, while push can work when the receiver has bounded buffers, acknowledgments, credits or another flow-control signal. Broker APIs vary: Kafka consumers poll, RabbitMQ commonly pushes deliveries to consumers, and SQS consumers poll.

---

## Anti-patterns

- **Unbounded queue.** Grows forever, OOM eventually.
- **Producer without backpressure awareness.** Doesn't know the consumer is slow.
- **Sync request without timeout.** Pins a thread for 30 seconds.
- **No circuit breaker.** Keeps calling a dead service.
- **All requests equal priority.** A bot can take down the payment system.
- **Assuming pull alone prevents overload.** Bound prefetch, buffers and in-flight work; a slow consumer can still accumulate too much data.
- **No monitoring.** You don't see the queue growing until it crashes.

## When to discuss in interviews

| Scenario | Backpressure strategy |
| ----------------- | -------------------------------------------------------------------------------- |
| Worker queue full | Block producer, drop new, or load shed |
| HTTP service slow | Timeout, circuit breaker, 503 to client |
| DB overloaded | Connection pool limit, query timeout, read replica |
| Cache miss storm | Rate limit, refresh-ahead, stale-while-revalidate |
| Real-time stream | TCP flow control, reactive streams |
| Webhook receiver | Durable acceptance or explicit rejection, bounded retries and duplicate identity |

**Senior signal:** name the backpressure strategy, justify the choice, name the failure mode if you didn't have it.

---

## Make the interview contract concrete

Name the unit of capacity (bytes, stored items, waiting callers or in-flight jobs), its limit, the accepted-work guarantee and the overload response. Then trace what happens when the downstream service stalls beyond the deadline. For critical webhooks, acknowledge only after durable acceptance; if capacity cannot safely accept more, return a retryable failure under the sender's documented policy. For optional telemetry, measured dropping may be appropriate.

## Summary

Backpressure propagates limited downstream capacity so production slows or pauses. Bounded queues contain waiting work; rejection and permitted dropping are complementary load-shedding policies, not proof that a producer honored feedback. Pull and push are both useful: choose the one that gives the system a clear bound and overload behavior. TCP flow control protects a network connection; application streams may need their own limits.

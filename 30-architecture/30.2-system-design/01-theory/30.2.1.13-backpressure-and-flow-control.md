# Backpressure and Flow Control

A webhook service accepts 10,000 events per second, but its workers finish only 1,000. With a 10,000-event queue, the buffer fills in a little over one second. A larger queue delays the failure; it never corrects the mismatch. The system needs a way to slow or limit new work, define how senders retry rejections, and state the durability guarantee for accepted events:

```text
10,000 events/s in, 1,000/s out, 10,000 buffer → full in ~1.1 s.
```

## Definition

**Backpressure** is feedback about downstream capacity that causes an upstream producer to reduce or pause its work. If the producer ignores the signal, the receiver still needs an admission limit or overload policy.

**Flow control** limits the amount of data or work sent or kept in flight across a boundary. It can be implemented through credits, demand, windows, or concurrency limits.

> **Textbook Definition:** Backpressure is a feedback control in which downstream capacity constrains upstream production; flow control regulates transfer or in-flight work so that a receiver or intermediary is not forced to accept more than its configured capacity.

A bounded queue contains work at one point; it never by itself slows the producer. Blocking, pull, credits, and a respected retry response can propagate a limit. Rejection, dropping, and rate limiting are related overload controls, but they are not backpressure unless they change future producer behavior.

## First Principles

When arrivals persistently exceed completions, the backlog grows without bound — no buffer size fixes a sustained rate mismatch. The system must either slow the producer, bound what it accepts, or define what happens to the excess. If the system already promised durable acceptance, silently dropping the excess breaks that promise. Every stage where work can accumulate therefore needs a bound, and each signal needs a response the upstream stage can actually perform.

## How It Works

### 1. Derive when the buffer fills

Let **λ** be the arrival rate, **μ** the completion rate, and **B** the queue's remaining capacity. Use the same work unit for both rates and the buffer size. If arrivals stay above completions, the backlog grows at approximately λ − μ, so **time to fill ≈ B ÷ (λ − μ)**.

For the webhook example, 10,000 arrivals/s − 1,000 completions/s = 9,000 new queued events/s. A 10,000-event buffer fills in about 1.11 seconds. This assumes constant rates and an initially empty queue; bursts or a partially full queue shorten the time. The capacity unit matters: 10,000 large payloads may consume far more memory or disk than 10,000 small ones.

When the buffer fills, choose deliberately:

- **Wait or send less:** useful when the producer can honor a bounded wait, pull rate, or credit window.
- **Reject before acceptance:** useful when an HTTP caller can retry under a bounded policy.
- **Drop or sample:** appropriate only when the product contract allows losing that data, such as selected telemetry.
- **Persist and defer:** appropriate when work has been durably accepted and must survive process failure; storage, retention, and backlog recovery still need limits.

If the system already promised durable acceptance, silently dropping the event breaks that promise. A full durable queue must stop accepting more, preserve accepted work, or apply a documented expiry or priority policy.

### 2. Design one feedback path per stage

Every stage where work can accumulate needs a bound, and each signal needs a response the upstream stage can actually perform:

| Boundary | Capacity signal or limit | Contract to make explicit |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Producer to service | Credits, pull, bounded wait or admission response | Bound waiting producers and request bodies; set a deadline |
| Service to broker | Bounded send queue or broker acceptance result | Say whether acceptance is durable and what a lost reply means |
| Broker to worker | Prefetch, pull batch or maximum in-flight work | Bound payload size, in-flight jobs, retry count and backlog age |
| Hypertext Transfer Protocol (HTTP) service to caller | 429 for rate limits, or 503 for temporary unavailability; optionally `Retry-After` | The caller must honor the response; cap retries and use backoff with jitter |
| Transmission Control Protocol (TCP) receiver to sender | Advertised receive window in bytes | This limits transport data on that connection, not the application's job queue |
| Stream subscriber to publisher | Explicit demand, such as `request(n)` items | Bound operator prefetch and account for the size of each item |

A response is no throttle by itself. An HTTP caller may retry immediately, and an unbounded retry policy can amplify the overload. Define which requests may retry, their maximum attempts and deadline, and how duplicate side effects are made safe. `Retry-After` communicates a suggested delay; the client still needs to follow it. Bounded exponential backoff with random jitter varies retry delays so clients never all retry at once. For multi-tenant or mixed-priority systems, decide who uses the remaining capacity. Per-tenant quotas, fair queues, or reserved capacity can protect critical work — but a priority class must hold a hard bound too.

### 3. Choose push or pull — then bound every buffer

With **push**, a producer sends work when available. Push is safe when the receiver advertises credits, limits in-flight messages, or holds a bounded buffer with a defined full-buffer response. Unbounded push can move pressure into memory, pending network writes, or blocked handler tasks.

With **pull**, a consumer requests work when it has capacity. This makes demand visible — but only if fetch batches, worker concurrency, and prefetch are bounded. A consumer fetching a large batch and queueing it internally has recreated the same overload problem.

The important choice is never the application programming interface (API) shape. It is whether every intermediate buffer and set of waiting callers holds a limit and a recovery policy.

### 4. Separate transport flow control from application capacity

**TCP flow control:** a TCP receiver advertises a receive window describing how much sequence space it is currently prepared to accept. The sender limits unacknowledged data using that receive window and its congestion window; the receive window protects the receiver, while congestion control responds to network-path capacity. This is transport-level flow control. An application can read socket bytes quickly and place parsed jobs into an unbounded in-memory queue, so the TCP window no longer represents the application's processing capacity. Bound the application queue separately.

**Reactive Streams:** a non-blocking protocol for asynchronous streams. A subscriber requests a finite number of items; the publisher must never send more than the outstanding demand. Demand is measured in items, not bytes, so a stream of variable-size records still needs payload-size and memory limits. Operators may prefetch and buffer. Configure those bounds and confirm demand reaches the source; a `subscribe` call alone never establishes bounded memory or prevents overflow.

### 5. Keep adjacent controls distinct — and watch the limit

| Control | What it limits | What it does not guarantee |
| ------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| Rate limit | Accepted requests over a time window or identity | That a slow downstream signals its current capacity |
| Concurrency limit | Active work at one resource boundary | That queued or waiting work is bounded |
| Load shedding | New work admitted during overload | That previously accepted work is durable |
| Timeout or deadline | How long a caller waits | That remote work stopped when the caller timed out |
| Circuit breaker | Calls made to a failing dependency | That existing queues or blocked callers are bounded |
| Bulkhead | Capacity shared by one class of work | That total demand fits the isolated capacity |
| Autoscaling | Available capacity after new instances start | Immediate relief; provisioning takes time and extra instances can increase load on a shared bottleneck |

These controls often work together. For example, a bounded in-flight limit can apply backpressure to workers, while admission control rejects excess HTTP requests and a circuit breaker avoids calls to an already failing dependency.

Track queue depth and oldest-item age, admitted and rejected rates, active and waiting work, retry volume, consumer lag, and completion rate. Depth alone is never enough: a stable count can still hide an aging backlog, and many small messages differ from a few large payloads. In a design interview, state the unit being bounded, the point where the system considers work accepted, the full-buffer response, and who reacts to feedback. Then follow one slow-consumer trace through the request deadline, retry policy, and durability guarantee.

## Summary

Backpressure propagates downstream capacity limits upstream; flow control bounds transfer or in-flight work at a boundary. A queue bound contains accumulation but does not fix excess demand. Every stage needs a limit, and overload handling must preserve the contract for accepted work while defining whether new work waits, retries, is rejected or may be dropped.

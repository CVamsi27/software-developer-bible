# Backpressure & Flow Control

> **What happens when a producer sends faster than the consumer can process?** Without backpressure, the consumer dies, the queue overflows, the system crashes. With backpressure, the producer slows down or the system degrades gracefully. Know the patterns.

## TL;DR

- **Backpressure** = a mechanism for a consumer to tell a producer "slow down, I'm overwhelmed."
- **Without it:** memory grows, latency spikes, eventually OOM.
- **Three strategies:** blocking (queue with bounded size), dropping (drop new), load shedding (reject some).
- **In async systems:** bounded queues are the simplest backpressure.
- **In sync systems:** timeouts, circuit breakers, load shedding.
- **TCP has built-in backpressure** (flow control window).
- **Reactive streams (Rx, Reactor, Akka Streams):** explicit backpressure protocol.

---

## Why it matters

Most outages are caused by cascading failures where one slow service overwhelms the next. The fix is backpressure.

Without backpressure:
- Producer pushes 10K msg/sec
- Consumer processes 1K msg/sec
- Queue grows from 0 → 1M in 17 minutes
- OOM, crash, data loss

With backpressure:
- Producer pushes 10K msg/sec
- Consumer processes 1K msg/sec
- Queue fills up to its limit (say 10K)
- Producer blocks (waits) or drops new messages
- Consumer keeps up

---

## The problem: producer faster than consumer

**Common scenarios:**
- API gateway receives traffic spike (Black Friday)
- Worker processes slow jobs (PDF generation, image processing)
- DB is slow (long query, lock contention)
- Downstream service is down (cascade failure)

**Without backpressure:**

```
Time 0: queue = 0
Time 1: queue = 9,000 (10K in, 1K out)
Time 2: queue = 18,000
Time 3: queue = 27,000
...
Time 17: queue = 162,000 → OOM, crash
```

**The system looks "fine" for a while, then dies suddenly.** Hard to debug, hard to alert on.

---

## 3 strategies

### 1. Blocking (apply backpressure upstream)

**Pattern:** Queue has a bounded size. When full, the producer blocks (waits).

```
producer.send(msg)
  → queue buffer (max 10K)
  → if buffer full, producer waits
  → consumer pulls, processes
  → buffer has space, producer resumes
```

**Pros:**
- No data loss
- Simple to implement (just a bounded queue)
- Natural rate limiting

**Cons:**
- Producer slows down (or blocks)
- May not be possible (HTTP request can't block forever)
- Can cause head-of-line blocking

**When to use:** Async systems where the producer can wait (workers, batch jobs).

**Examples:**
- BlockingQueue in Java
- Channel in Go
- asyncio.Queue in Python
- bounded queue in any language

**In code:**

```typescript
// Node.js example with bounded queue
class BoundedQueue<T> {
  private items: T[] = [];
  private maxSize: number;
  private resolvers: ((value: T | null) => void)[] = [];

  constructor(maxSize: number) {
    this.maxSize = maxSize;
  }

  async enqueue(item: T): Promise<void> {
    if (this.items.length >= this.maxSize) {
      // Queue full, wait until there's space
      await new Promise<void>((resolve) => {
        this.resolvers.push(() => resolve());
      });
    }
    this.items.push(item);
  }

  async dequeue(): Promise<T | null> {
    if (this.items.length === 0) return null;
    const item = this.items.shift()!;
    // Wake up a blocked enqueue
    const resolve = this.resolvers.shift();
    if (resolve) resolve();
    return item;
  }
}
```

### 2. Dropping (silently discard)

**Pattern:** Queue has a bounded size. When full, new messages are dropped.

```
producer.send(msg)
  → queue buffer (max 10K)
  → if buffer full, drop msg
  → consumer pulls, processes
```

**Pros:**
- Producer never blocks
- System stays up even under extreme load
- Predictable memory

**Cons:**
- Data loss
- Need to monitor drop rate
- Not OK for critical data (payments, orders)

**When to use:** Non-critical data (logs, metrics, telemetry, telemetry-like events).

**Examples:**
- UDP packets (no retransmit, no guarantee)
- Metrics (Prometheus, drop on overflow)
- Logs (log shipper drops on overflow)
- Some pub/sub systems

**In code:**

```typescript
class DropOnFullQueue<T> {
  private items: T[] = [];
  private maxSize: number;
  private dropped = 0;

  constructor(maxSize: number) {
    this.maxSize = maxSize;
  }

  enqueue(item: T): boolean {
    if (this.items.length >= this.maxSize) {
      this.dropped++;
      return false; // Dropped
    }
    this.items.push(item);
    return true; // Accepted
  }
}
```

### 3. Load shedding (reject some, keep rest)

**Pattern:** When overloaded, reject some requests (e.g., low-priority) but accept high-priority ones.

```
request arrives
  → if at capacity, check priority
  → if high priority: queue
  → if low priority: reject (return 503)
  → consumer pulls, processes
```

**Pros:**
- Protects important traffic
- System stays up
- Graceful degradation

**Cons:**
- Need to define priorities
- Some requests fail
- Need to communicate to client (retry?)

**When to use:** Mixed-priority workloads. Payment system: process payments, drop analytics. Search system: process user queries, drop bot traffic.

**Examples:**
- Hystrix (Netflix)
- Resilience4j
- AWS load balancers (cross-zone load balancing)
- nginx (with `limit_req`)

**In code:**

```typescript
class PriorityQueue<T extends { priority: number }> {
  private items: T[] = [];
  private maxSize: number;
  private rejected = 0;

  constructor(maxSize: number) {
    this.maxSize = maxSize;
  }

  enqueue(item: T): boolean {
    if (this.items.length < this.maxSize) {
      this.items.push(item);
      return true;
    }

    // Queue full. Try to evict a low-priority item.
    const lowestPriorityIdx = this.findLowestPriorityIndex();
    if (item.priority > this.items[lowestPriorityIdx].priority) {
      // Replace low-priority item
      this.items[lowestPriorityIdx] = item;
      return true;
    }

    // Reject this item (it's lower priority)
    this.rejected++;
    return false;
  }
}
```

## Where to apply backpressure

| Layer | Mechanism |
| --------------------- | --------------------------------------------------------- |
| **Producer → Queue** | Bounded queue, blocking or drop |
| **Queue → Consumer** | Consumer pulls at its own rate (never pushes to consumer) |
| **Service → Service** | Timeouts, circuit breakers, load shedding |
| **Client → Server** | HTTP 429 (rate limited), Retry-After header |
| **DB queries** | Connection pool limits, query timeouts |
| **Network (TCP)** | Built-in flow control window |
| **Reactive streams** | Explicit backpressure protocol (request N items) |

---

## TCP flow control (the original backpressure)

TCP has built-in backpressure:
- Receiver has a "receive window" (how much data it can buffer)
- Sender doesn't send more than the window size
- As receiver processes data, window slides, sender can send more

This is the foundation of all backpressure in distributed systems. Every time you use TCP, you have backpressure.

---

## Reactive streams (RxJava, Project Reactor, Akka Streams)

These libraries have explicit backpressure:

```java
// RxJava example
Flowable.fromIterable(data)
  .observeOn(Schedulers.io())
  .map(processItem)
  .subscribe(
    item -> save(item),
    error -> log(error),
    () -> done()
  );
```

The consumer signals to the producer how many items it can handle. The producer respects this. No buffer overflow, no OOM.

Used by Netflix, LinkedIn, and other high-scale systems.

## Specific patterns

### 1. Circuit breaker (sync systems)

When a downstream service is slow or failing, stop calling it. Return immediately with an error or fallback.

```
[CLOSED: normal, count failures]
  if failures > threshold:
    [OPEN: reject all calls for 30s]
[OPEN: reject]
  after 30s:
    [HALF_OPEN: try one call]
[HALF_OPEN]
  if success: [CLOSED]
  if fail: [OPEN]
```

**Libraries:** Hystrix (deprecated), Resilience4j, Polly (.NET), Istio.

**See:** [Microservices/04 Circuit Breaker](../../../20-backend/20.6-microservices/04-resilience/20.6.4.01-circuit-breaker.md) for the full deep-dive.

### 2. Bulkhead (isolation)

One slow service shouldn't take down everything. Isolate resources per service.

```
Thread pool for /search: 50 threads
Thread pool for /recommendations: 20 threads
Thread pool for /user/profile: 100 threads

If /search hangs, only its 50 threads are exhausted. The other 50 are safe.
```

**See:** [Microservices/14 Bulkhead Pattern](../../../20-backend/20.6-microservices/04-resilience/20.6.4.02-bulkhead-pattern.md).

### 3. Timeout everywhere

Every external call has a timeout. Otherwise a slow service can pin your threads forever.

```
DB query: 5s timeout
HTTP call: 10s timeout
Cache read: 100ms timeout
Queue send: 1s timeout
```

### 4. Rate limiting (per consumer)

Limit how much any one consumer can use.

```
User A: 1000 req/min
User B: 1000 req/min
User C: 1000 req/min

Even if User A is malicious, they can't use 100% of capacity.
```

**See:** [Rate Limiting](30.2.1.08-rate-limiting.md).

### 5. Health checks + auto-scaling

If a service is unhealthy, route around it. If all services are at capacity, add more.

```
[Load balancer]
  → Health check every 5s
  → If server unhealthy, remove from rotation
  → If all servers at > 80% capacity, scale out
```

## Push vs Pull

**Push (consumer is told to process):**
- Hard to apply backpressure
- Consumer must be ready or process asynchronously
- Risk: buffer overflow, OOM

**Pull (consumer asks for work when ready):**
- Natural backpressure
- Consumer controls rate
- Risk: underutilization if consumer is slow

**In practice:** Always use pull. The consumer decides when to fetch. The producer doesn't push.

Most message queues (Kafka, RabbitMQ, SQS) are pull-based. The consumer polls.

---

## Anti-patterns

- **Unbounded queue.** Grows forever, OOM eventually.
- **Producer without backpressure awareness.** Doesn't know the consumer is slow.
- **Sync request without timeout.** Pins a thread for 30 seconds.
- **No circuit breaker.** Keeps calling a dead service.
- **All requests equal priority.** A bot can take down the payment system.
- **Pull on a slow consumer.** It still OOMs if it can't process fast enough.
- **No monitoring.** You don't see the queue growing until it crashes.

---

## When to discuss in interviews

| Scenario | Backpressure strategy |
| ----------------- | --------------------------------------------------- |
| Worker queue full | Block producer, drop new, or load shed |
| HTTP service slow | Timeout, circuit breaker, 503 to client |
| DB overloaded | Connection pool limit, query timeout, read replica |
| Cache miss storm | Rate limit, refresh-ahead, stale-while-revalidate |
| Real-time stream | TCP flow control, reactive streams |
| Webhook receiver | Bounded queue, retry with backoff, drop on overflow |

**Senior signal:** name the backpressure strategy, justify the choice, name the failure mode if you didn't have it.

---

## When to bring up in system design

When you're designing any async system, queue, or pipeline:

- "We use a bounded queue (10K messages). When full, the producer blocks for up to 1 second, then drops the message. We monitor drop rate and alert if it's > 1%."

- "Our service has a 5s timeout on all downstream calls. If the DB is slow, we return a cached response. If the cache is also down, we return 503 with a Retry-After header."

- "We use a circuit breaker for the payment provider. If it fails 5 times in 10 seconds, we stop calling it for 30s and return 'payment temporarily unavailable.'"

## Summary

Backpressure prevents fast producers from overwhelming slow consumers. Three strategies: blocking (wait), dropping (discard low-priority), and load shedding (reject with 503). Always use bounded queues. Pull-based (consumer controls rate) is better than push-based. TCP has built-in flow control. Reactive streams add explicit backpressure. In interviews, name the strategy, justify the choice, and name the failure mode it prevents.

## Cheat Sheet
```text
BACKPRESSURE CHEAT SHEET
═══════════════════════════════════════════════════════════════

STRATEGIES:
• Blocking — producer waits (simple, can deadlock)
• Dropping — discard low-priority (fast, data loss)
• Load shedding — reject with 503 (explicit, client retries)

RULES:
• Always use bounded queues (unbounded = OOM)
• Pull > push (consumer controls rate)
• TCP has built-in flow control
• Reactive streams: Publisher → Subscriber with request(n)

IMPLEMENTATIONS:
• TCP flow control (sliding window)
• RabbitMQ: prefetch count
• Kafka: consumer polling rate
• RxJS: backpressure operators
• Project Reactor: request(n) pattern

IN INTERVIEWS:
• Name the strategy (block, drop, shed)
• Justify based on data criticality
• Use bounded queues
• Mention failure mode: OOM, cascading failure
```

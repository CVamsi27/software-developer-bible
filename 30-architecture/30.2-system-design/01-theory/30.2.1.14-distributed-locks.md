# Distributed Locks & Coordination

> **How do you make sure only one process does X at a time, across multiple machines?** Distributed locks are how. Used for: leader election, exclusive access to a resource, preventing duplicate work, coordinating across services.

## TL;DR

- **Distributed lock** = a lock that works across multiple machines/processes.
- **Use cases:** leader election, exclusive access, prevent duplicate work, distributed coordination.
- **Implementations:** Redis (Redlock), ZooKeeper, etcd, Postgres advisory locks, DynamoDB.
- **Critical properties:** mutual exclusion, no deadlock, fault tolerance, no spurious failures.
- **Redlock debate:** Martin Kleppmann vs Antirez. Be aware of the limitations.
- **In interviews: when to use, when NOT to use, and the fencing token problem.**

---

## Why it matters

You have a service running on 50 machines. You want to:
- Make sure only one of them runs the "send daily email" job
- Make sure only one of them processes each message
- Make sure two services don't write to the same row at the same time

A local lock doesn't work — the lock has to be visible across machines. That's a distributed lock.

---

## Use cases

1. **Leader election** — only one node is the leader. (See [Consensus And Leader Election](30.2.1.09-consensus-and-leader-election.md).)
2. **Exclusive access to a resource** — only one process can update a critical resource at a time.
3. **Prevent duplicate work** — only one cron job runs the "process pending records" task.
4. **Distributed coordination** — services need to coordinate on a shared state.
5. **Rate limiting** — limit a resource to N concurrent uses.
6. **Idempotent operations** — make sure a task is done only once across all retries.

---

## The properties of a good distributed lock

From the Redis Redlock paper:

1. **Safety (mutual exclusion):** At any moment, only one client can hold the lock.
2. **Liveness A (no deadlock):** Eventually it's possible to acquire a lock, even if the client holding it crashes.
3. **Liveness B (fault tolerance):** As long as a majority of Redis nodes are up, clients can acquire and release locks.

**Plus (from Kleppmann's critique):**
4. **Fencing tokens:** The lock should provide a monotonically increasing token, used to fence out stale clients.

## Implementations

### 1. Redis + Redlock

**Algorithm (simplified):**

```
To acquire:
  1. Get current time in ms (T1)
  2. Try to SET key with random value + TTL in N independent Redis instances
  3. Get current time in ms (T2)
  4. If (T2 - T1) < lock_ttl AND majority (N/2 + 1) succeeded: lock acquired
  5. The valid time of the lock = lock_ttl - (T2 - T1)

To release:
  1. Send DEL to all N instances
  2. Use Lua script to check the value before deleting (so you don't delete someone else's lock)
```

**Pros:**
- Fast
- Simple
- Widely used

**Cons:**
- **Clock skew issues.** Redlock relies on synchronized clocks.
- **GC pauses can cause problems.** Long GC pause, lock expires, another client acquires, original client thinks it still has lock → mutual exclusion violated.
- **Martin Kleppmann's critique:** Redlock is not safe for correctness-critical use cases. Use ZooKeeper or etcd instead.

**When to use:** Non-critical locks (e.g., "process this job once"). Not for correctness-critical (e.g., "don't double-charge").

### 2. ZooKeeper

**Algorithm:** Use sequential ephemeral znodes.

```
To acquire:
  1. Create a znode: /locks/myresource/guid- (sequential, ephemeral)
  2. List all children of /locks/myresource
  3. If my znode is the lowest-numbered, I have the lock
  4. Otherwise, set a watch on the next-lowest znode
  5. When that znode is deleted, I have the lock

To release:
  1. Delete my znode
  2. Session expiry also releases (ephemeral)
```

**Pros:**
- Strong consistency (Zab protocol)
- Ephemeral nodes handle session expiry
- Watchers are efficient (no polling)

**Cons:**
- More complex to set up
- Slower than Redis
- Operational overhead

**When to use:** Correctness-critical locks (financial, configuration).

### 3. etcd

**Algorithm:** Use leases + keys.

```
To acquire:
  1. Create a lease (TTL 30s)
  2. PUT a key with the lease ID
  3. To check if I have the lock: GET the key, see if it has my lease ID
  4. If not, wait (using watch) for the key to be deleted, then retry
  5. Refresh the lease periodically (keep alive)

To release:
  1. DELETE the key
  2. Or let the lease expire
```

**Pros:**
- Strong consistency (Raft)
- Built-in leader election (Kubernetes uses it)
- Watches for efficient waiting

**Cons:**
- More complex
- Need to manage lease keep-alive

**When to use:** Kubernetes-style coordination, configuration, leader election.

### 4. Postgres advisory locks

**Algorithm:** Use Postgres's built-in `pg_advisory_lock` / `pg_try_advisory_lock`.

```sql
-- Acquire
SELECT pg_try_advisory_lock(12345);
-- Returns true if acquired, false if not

-- Release
SELECT pg_advisory_unlock(12345);
```

**Pros:**
- Built into Postgres, no extra infrastructure
- Strong consistency (Postgres's MVCC)
- Session-level or transaction-level

**Cons:**
- Ties up a DB connection
- Slower than Redis (DB round-trip)
- Only available if you have Postgres

**When to use:** When you already have Postgres, for non-high-throughput locks.

### 5. DynamoDB

**Algorithm:** Use a conditional PUT on a "lock" item with TTL.

```
To acquire:
  1. PUT item with key "lock" and attribute "owner" = my_id
     ConditionExpression: attribute_not_exists(owner) OR owner = :my_id
  2. If succeeded, lock acquired
  3. TTL attribute ensures the lock expires

To release:
  1. DELETE item
     ConditionExpression: owner = :my_id
```

**Pros:**
- Strong consistency (DynamoDB conditional writes)
- No extra infrastructure (you have DynamoDB)
- TTL is built in

**Cons:**
- 1-second granularity for TTL (minimum)
- Network round trip

**When to use:** When you already have DynamoDB, for moderate-throughput locks.

## The Fencing Token Problem

**The killer problem with distributed locks:** clock skew + GC pauses + network delays can cause a client to think it still holds the lock when it doesn't.

**Scenario:**
```
1. Client A acquires lock with TTL 10s
2. Client A starts a long operation (20s)
3. At t=10s, lock expires
4. Client B acquires lock
5. Both A and B think they have the lock
6. Both write to the same resource
7. Conflict, data corruption
```

**The fix: fencing tokens.** The lock server returns a monotonically increasing token with each acquisition. The resource (e.g., database) rejects writes from older tokens.

```
1. Client A acquires lock → token 33
2. Client A starts operation
3. Lock expires
4. Client B acquires lock → token 34
5. Client A tries to write with token 33
6. Database sees token 33 < current max 34, REJECTS the write
```

**In practice:** Most storage systems don't have built-in fencing. Postgres has it for some operations. S3 has version IDs. Most others don't.

**The right answer in interviews:** "Distributed locks have a fencing token problem. For correctness-critical operations, prefer database-level locking (transactions, row-level locks) over distributed locks."

## Common patterns

### 1. Lock for cron-like jobs

Make sure only one of N machines runs the daily job.

```typescript
// In a service that runs on 10 machines
async function runDailyJob() {
  const lockKey = 'lock:daily-job';
  const acquired = await redis.set(lockKey, instanceId, 'NX', 'EX', 86400);

  if (!acquired) {
    log('Another instance is running the daily job');
    return;
  }

  try {
    await doDailyWork();
  } finally {
    await redis.del(lockKey);
  }
}
```

### 2. Lock for distributed work queue

Make sure each message is processed by exactly one worker.

```typescript
// Worker pulls a message, processes it, marks as done
async function processMessage(msg: Message) {
  const lockKey = `lock:msg:${msg.id}`;
  const acquired = await redis.set(lockKey, instanceId, 'NX', 'EX', 300);

  if (!acquired) {
    log('Another worker is processing this message');
    return;
  }

  try {
    await process(msg);
    await db.updateMessageStatus(msg.id, 'done');
  } finally {
    await redis.del(lockKey);
  }
}
```

### 3. Lock for distributed transactions

Use a lock to coordinate a 2-phase commit (rare; saga is preferred).

### 4. Lock for cache stampede prevention

When a cache key expires, only one process should regenerate it.

```typescript
async function getValue(key: string) {
  const value = await cache.get(key);
  if (value) return value;

  const lockKey = `lock:regen:${key}`;
  const acquired = await redis.set(lockKey, instanceId, 'NX', 'EX', 30);

  if (!acquired) {
    // Another process is regenerating. Wait and retry.
    await sleep(100);
    return getValue(key);
  }

  try {
    const fresh = await db.get(key);
    await cache.set(key, fresh, 3600);
    return fresh;
  } finally {
    await redis.del(lockKey);
  }
}
```

## When to use distributed locks

**Use when:**
- You need mutual exclusion across machines
- The operation is not super critical (some chance of double-processing is OK)
- You can tolerate some failure modes (fencing issues)
- The operation is idempotent (so even if processed twice, no harm)

**Don't use when:**
- You can use database-level locks instead (transactions, row-level locks, advisory locks)
- You can use optimistic concurrency control (version numbers)
- The operation is correctness-critical and you can't tolerate any double-processing
- You need strong fencing (most distributed lock implementations don't have it)

**Prefer:**
1. Database-level locking (transactions, row-level locks, advisory locks) — strongest
2. Optimistic concurrency control (version numbers) — no lock, but works
3. etcd/ZooKeeper — strong consistency for coordination
4. Redis Redlock — for non-critical locks
5. Custom solution — almost never, use a battle-tested one

## Common pitfalls

- **Lock without TTL.** If the holder crashes, the lock is held forever.
- **Lock with too-short TTL.** Lock expires while operation is in progress, another client acquires.
- **Lock without fencing.** Old client thinks it still holds the lock, writes anyway.
- **Lock with value = no ID.** Release can delete someone else's lock.
- **Lock without proper error handling.** If acquire fails, what do you do? Retry? Fail?
- **Lock per row.** If you have 1M rows, you don't need 1M distributed locks. Use database row-level locks.
- **Locking when not needed.** Sometimes a simple idempotency key is enough.

## When to discuss in interviews

| Scenario                              | Lock approach                              |
| ----------                              | --------------                               |
| Daily cron job                        | Redis SET NX with TTL (24h)                |
| Idempotent message processing         | Idempotency key (no lock needed)           |
| Bank transfer (must be atomic)        | Database transaction, NOT distributed lock |
| Leader election for service           | etcd lease                                 |
| Exclusive access to external resource | Redis or ZooKeeper                         |
| Cache stampede prevention             | Redis SET NX with short TTL                |
| Coordinating multi-step workflow      | Saga (no lock)                             |

**Senior signal:** know when NOT to use a distributed lock. Prefer database-level locks, optimistic concurrency, or just idempotency.

---

## When to bring up in system design

When discussing:
- "Make sure only one X runs" → distributed lock
- "Process each message once" → idempotency key, not lock
- "Coordinate multiple services" → saga, not lock
- "Atomic update of multiple rows" → database transaction, not lock

**The default answer in interviews:** "We use database-level locks (transactions) for correctness-critical operations. We use Redis distributed locks for non-critical coordination (cron jobs, deduplication). We avoid distributed locks for correctness because of the fencing problem."

## Summary

Distributed locks coordinate access to shared resources across nodes. Implementations: Redis (Redlock), ZooKeeper, etcd, Postgres advisory locks. Fencing tokens are critical for correctness — they prevent stale locks from causing corruption. Prefer database locks for correctness-critical operations. Use distributed locks for non-critical coordination (cron, dedup). In interviews, know when NOT to use locks, mention the fencing problem.

## Cheat Sheet
```text
DISTRIBUTED LOCKS CHEAT SHEET
═══════════════════════════════════════════════════════════════

IMPLEMENTATIONS:
• Redis (Redlock) — fast, eventual consistency
• ZooKeeper — strong consistency, slower
• etcd — strong consistency, Kubernetes uses it
• Postgres advisory locks — transactional
• DynamoDB — conditional writes

FENCING TOKENS (critical):
• Lock includes monotonically increasing token
• Resource checks token before accepting writes
• Prevents stale lock holder from corrupting data
• Without fencing, distributed locks are unsafe

WHEN TO USE:
• Cron job dedup (only one instance runs)
• Non-critical coordination
• Leader election (with fencing)

WHEN NOT TO USE:
• Critical correctness (use DB transactions)
• High-contention (use optimistic locking)
• When you can use a single database

IN INTERVIEWS:
• Know when NOT to use locks
• Mention the fencing problem
• Prefer DB locks for correctness
• Use locks for non-critical coordination
```

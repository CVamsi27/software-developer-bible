# Distributed Locks and Coordination

Two workers run the same scheduled job. Worker A acquires a 30-second lease, then pauses for longer than 30 seconds. The coordinator lets worker B acquire the expired lease and begin the job. When A resumes, it may still try to write. The coordinator knows B is the current owner; the database or other protected resource may not.

## Definition

A **distributed lock** is a coordination record that lets processes agree which one may attempt work on a named resource at a time. A lease-based lock expires after a configured interval so another process can take over after a crash or lost session. Expiry does not stop the old process.

A typical lease has an acquisition rule, a unique owner identity, an expiry or session, and a release rule that removes the lock only if the owner identity still matches.

> **Textbook Definition:** A distributed lock is a coordination mechanism for granting a time-bounded, mutually exclusive claim on a named resource across processes under a stated failure model. The claim protects the resource only when its writes enforce the ownership or fencing rule.

## First Principles

The lock service and the protected resource are usually different systems. A lease timeout tells the coordinator when it may grant a new claim; it cannot prove that the old worker has stopped. Correctness-sensitive writes therefore need an enforcement rule at the resource.

1. **A lease is not a process kill.** A worker can pause, lose network access or miss renewal, then continue after the coordinator expires its lease.
2. **A lock does not make work exactly once.** An operation may commit before the process crashes or its reply is lost. Make the operation idempotent (repeating the same request has the same effect), use a unique constraint or record completion in the same transaction.
3. **A lock is not always necessary.** A conditional update, database transaction, version check, single-writer partition or idempotent consumer may protect the invariant more simply.
4. **Unavailable coordination needs a policy.** Fail closed when duplicate work can corrupt state; choose a fallback only when its consistency risk is explicit.

A client may lose the response to a successful acquisition. It must not assume the lock was not granted and start a second attempt with a different identity. Resolve the result using an operation identity the coordination system can inspect, or wait for the possible lease to expire before proceeding.

## Fencing stale owners

A **fencing token** is a monotonically increasing generation assigned to each new owner. Each write carries its generation, and the protected resource atomically remembers the highest generation it has accepted, rejecting lower ones.

~~~text
Worker A receives token 33, then pauses past lease expiry.
Worker B receives token 34 and writes; the resource records 34.
Worker A resumes and writes with token 33.
The resource rejects 33 because it has already accepted 34.
~~~

The resource is the fence. Checking the token only in worker code or writing it to a log cannot stop a stale write.

There is an important limit: token 33 may still be accepted if it reaches the resource before the resource has seen token 34. Fencing rejects an old owner after a newer generation reaches the protected resource; it cannot revoke an earlier accepted write or atomically validate a lease held in another system. If each write must prove current ownership, the target must check authoritative ownership as part of the same transaction or conditional operation that applies the write. A separate ownership read followed by a write still races. Otherwise combine fencing with the resource's own version, uniqueness or idempotency rule.

A random owner token and a fencing token solve different problems. A random token lets a client release only the lock it acquired. It cannot order owners or fence writes. The fencing value must increase across acquisitions and the resource must enforce it atomically.

## Choose a primitive that owns the invariant

| Problem | Primitive to consider first | Why |
| ----------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Update rows in one database | Transaction, row lock, unique constraint or conditional update | The database can enforce the invariant with the data change |
| Reject an old version | Optimistic concurrency with a version column | The write is accepted only if the version still matches |
| Process a message safely | Idempotency key and acknowledgment after commit | Redelivery is normal; a lock does not guarantee one execution |
| Elect one leader | Consensus-backed election or lease API | Terms, ownership changes and recovery are explicit |
| Coordinate access to an external resource | Lease only if the resource can enforce fencing or an equivalent condition | A coordinator alone cannot stop an expired holder from acting |

A lock is not a semaphore. A semaphore grants up to N concurrent permits; use it for a capacity limit, while an exclusive lock admits only one holder. Neither primitive guarantees fair or FIFO access; set a bounded acquisition wait and observe contention.

## Common implementations

### Redis lease

Acquire with an atomic create-if-absent operation and an expiry, such as `SET resource token NX PX ttl`. Use a unique random owner token and release with compare-and-delete so an expired owner cannot delete a newer owner's key. Redis 8.4 adds `DELEX key IFEQ token`; older versions can perform the comparison and deletion atomically with a Lua script. A plain delete is unsafe.

A single Redis primary with asynchronous replication can lose a lock write during failover: a promoted replica may not contain the key and can grant the same lock to another client. Use that design only if the failure risk is acceptable. Redis's Redlock algorithm uses independent masters and depends on bounded clock drift and work completing within the lease's validity period; evaluate those assumptions against the protected resource and the consequences of overlap.

### ZooKeeper

The lock recipe creates an ephemeral sequential node. The client with the lowest sequence owns the lock; each waiter watches only its immediate predecessor, avoiding a wake-up storm. A client must handle a create that succeeds even when its response is lost, and it must stop treating the lock as valid when its ZooKeeper session ends. Ephemeral-node cleanup releases coordination state, but the protected resource still needs a stale-owner rule.

### etcd

The etcd v3 lock API associates the lock key with a lease and returns a unique ownership key. For writes inside etcd, compare the ownership key or its creation revision in the same etcd transaction as the protected update. This makes the transaction conditional on still holding the lock. An etcd lease does not by itself fence writes to a database or service outside etcd.

### PostgreSQL advisory locks

An advisory lock names an application-defined resource; PostgreSQL does not automatically make ordinary table writes obey it. Every writer must follow the convention. A transaction-level advisory lock is released when its transaction ends. A session-level lock stays until explicit release or session end, so pooled connections need care.

~~~sql
BEGIN;
SELECT `pg_try_advisory_xact_lock`(42);
-- Perform the protected database work only if the result is true.
COMMIT;
~~~

Perform protected work in the same transaction only when the call returns true. Prefer row locks or constraints when the lock protects data in the same database; they bind coordination more directly to the mutation.

### DynamoDB conditional claim

A conditional write can claim a lock item when no live owner is recorded, or replace it after the stored expiry. DynamoDB time to live (TTL) asynchronously deletes expired items, typically within a few days; an expired item can remain readable or be updated while awaiting deletion, so TTL is not a precise lease mechanism. Use a conditional takeover, account for clock error if clients supply the time, and advance an owner generation.

If protected data is also in DynamoDB, use a transaction or condition that checks the generation as part of the data update. If the data is in another system, that system must enforce fencing or an equivalent invariant itself.

## Match the pattern to the work

| Work | Usually safer approach |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Scheduled job claimed by several workers | Durable claim, owner identity, idempotent effect and fencing if a stale worker could overwrite newer state |
| Message delivery | Commit the effect and deduplication record together, then acknowledge; a lock may reduce overlap but does not replace idempotency |
| Cache regeneration | Request coalescing or a short lease; bound waiters and serve stale data when its freshness contract permits |
| Multi-service business workflow | Saga or durable workflow; do not hold a lock while waiting on slow network calls |

## Review the failure contract

Before relying on a lock, answer:

- What exact invariant and resource does it protect?
- Which writes enforce owner identity or fencing, and are those checks atomic with the mutation?
- What does the client do when acquisition or renewal returns an uncertain result?
- If the coordinator is unavailable, does the operation fail closed or follow a documented fallback?
- Can a completed effect be retried safely after a lost reply?
- How are contention, lease loss, wait time and rejected stale writes observed?

In an interview, start with the invariant and choose the primitive closest to the data. For work across workers, explain the lease and recovery rule. If an expired worker might still write, show how the resource rejects it; do not claim that a lock alone provides exactly-once execution.

## Summary

A distributed lock coordinates a temporary claim; it does not stop a paused worker when its lease expires. A random owner token protects release, while a monotonically increasing fencing generation protects writes only after the resource has observed the newer generation. Prefer a database transaction, conditional update, version or idempotency rule when it directly enforces the invariant.

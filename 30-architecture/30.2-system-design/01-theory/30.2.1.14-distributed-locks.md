# Distributed Locks & Coordination

Several application instances may try to update the same resource at once. A **distributed lock** coordinates those processes through a shared service, such as a database or coordination system. The lock decides who may proceed; the protected resource still has to enforce the correctness rule.

## Definition

A lock grants one owner temporary permission to perform work on a named resource. A common lease-based design stores an owner token and an expiration time:

```text
acquire(resource, owner, lease)  → succeed only if no live owner exists
release(resource, owner)         → remove only if the stored owner still matches
```

The lease lets another worker proceed after the holder crashes. It also means the lease can expire while the old holder is paused or disconnected. A lock is therefore not proof that the old process has stopped.

| Need | What to establish |
| ------------------------------ | ------------------------------------------------------------------------------- |
| Exclusive ownership | The coordination service serializes acquisition for the resource |
| Recovery after a crash | The lease/session expires or an operator releases the claim |
| Safe release | The release operation checks that the caller still owns the lock |
| Safe writes after lease expiry | The protected resource rejects stale owners, or the operation is safe to repeat |

> **Textbook Definition:** A distributed lock is a coordination mechanism that grants exclusive ownership of a named resource across processes under a defined failure model; lease expiration requires protection against stale holders continuing to act.

## First Principles


1. **The lock service and the protected resource are separate.** The lock can expire while a process is paused. The database, file store or external service must still reject an invalid or stale write when correctness depends on exclusive ownership.
2. **A lease is time-bounded permission.** A timeout detects that the holder may be gone; it cannot prove the holder has stopped. Lease renewal can also fail during a partition.
3. **A lock does not make an operation exactly once.** Work can complete before the process crashes but before it records completion. Use idempotency, a unique constraint or transactional state as well.
4. **Avoid coordination when a simpler invariant works.** A conditional update, database transaction, unique key, single-writer partition or idempotent consumer may solve the problem without a distributed lock.

## Why it matters

A scheduled worker may acquire a lease, pause for a long time, and resume after another worker has acquired the same lease. Both processes can then attempt the work. The system must define what happens to the old worker's write, not only how the new worker acquired the lock.

## Fencing tokens

A **fencing token** is an increasing number issued for each new owner. The owner includes it with writes to the protected resource. The resource atomically remembers the newest token it has accepted and rejects lower tokens after a newer token has arrived.

```text
Worker A gets token 33, then pauses.
Worker B gets token 34 and writes it to the database.
Worker A resumes and tries to write with token 33.
The database rejects 33 because it has already accepted 34.
```

Fencing works only when the protected resource checks the token as part of the write. Storing the token in a log or checking it only in the worker does not fence anything. It also does not undo a write already accepted before the resource has seen the newer token; pair it with the data invariant, such as a version check or uniqueness constraint.

## Choose the right primitive

| Need | Usually consider first | Why |
| -------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------- |
| Update rows in one database | Transaction, row lock, constraint or conditional update | The database can protect the data change atomically |
| Reject stale updates | Optimistic concurrency with a version column | No lease is needed; the database rejects an old version |
| Process a message safely | Idempotency key and acknowledgement after commit | Redelivery is expected; a lock does not guarantee one execution |
| Coordinate one leader | A consensus-backed election or lease API | Election terms and failover rules are explicit |
| Coordinate access across systems | A lock service only if the protected systems can enforce ownership | A lock alone cannot stop an expired holder from acting |

A lock is not a semaphore: limiting a resource to *N* concurrent users requires a semaphore or capacity-control mechanism, not an exclusive lock.

## Common implementations

### Redis lease

A single Redis primary can grant a short lease with an atomic “create only if absent” operation and an expiration. Use a random owner token. Release with a compare-and-delete operation so an expired owner cannot delete a newer owner's key. Redis replication and failover settings affect the failure guarantees; a successful command on one primary is not, by itself, proof of a durable global lock.

Redis documents Redlock as an algorithm over independent Redis masters. Its guarantees depend on timing and failure assumptions. Martin Kleppmann's critique explains why a lease without resource-side fencing is insufficient for correctness-critical writes. Treat Redlock as a design to evaluate against a stated failure model, not as a universal guarantee.

### ZooKeeper

ZooKeeper's lock recipe creates a sequential ephemeral node. The client with the lowest sequence owns the lock; each waiting client watches only its immediate predecessor to avoid waking every waiter on every release. The client must handle session loss and uncertain create responses. Ephemeral-node cleanup ends the coordination claim, but an old process still needs protection at the resource if it might continue after losing its session.

### etcd

Use etcd's lock API, which associates a lock key with a lease and uses the key's creation revision to coordinate waiters. If the lease expires, etcd removes the key. The application should stop work when it loses ownership and use revision or fencing checks at the protected resource when stale writes would be harmful.

### PostgreSQL advisory locks

Advisory locks coordinate application-defined resources through the PostgreSQL server. They are not enforced automatically by table writes; every code path that can change the resource must follow the same convention. Transaction-level advisory locks release at transaction end. Session-level locks remain until explicitly released or the session ends, so pooled connections need particular care.

```sql
-- True only if this transaction acquires the application-defined lock.
SELECT pg_try_advisory_xact_lock(42);
```

If the result is false, do not perform the protected work. Prefer a row lock or constraint when the lock is about protecting particular database data.

### DynamoDB conditional claim

A conditional write can create or update a lock item. The condition must check the current owner and expiration; a TTL attribute alone is not a lock lease. DynamoDB deletes expired TTL items asynchronously, so an expired item may still exist in reads and writes. To take over safely, use a conditional update that checks expiry and advances an owner generation or fencing value.

## Safe use patterns

### Scheduled work

Prefer a scheduler with a durable claim or a database row that records the job's owner, lease expiry and attempt identity. Each job should be idempotent. Renew the lease only while the worker is healthy, stop when renewal fails, and condition release on the same owner token. An expired lease may let another worker begin while the first is still running, so protect the job's writes too.

### Message processing

Assume a message can be delivered more than once. Commit the local effect and deduplication record together, then acknowledge the message. A distributed lock may reduce concurrent attempts, but it does not replace idempotency or the broker's acknowledgment contract.

### Cache regeneration

Use request coalescing or a short-lived lease to reduce duplicate regeneration. Bound how long other callers wait. If stale data is acceptable, serve it while one worker refreshes; otherwise return a clear loading or retry response. Do not recurse or poll without a deadline.

### Cross-service workflows

A saga or durable workflow usually fits multi-step business work better than holding a lock across network calls. Locks held during slow requests are vulnerable to lease expiry and make recovery harder.

## Failure checklist

Before using a distributed lock, answer these questions:

1. What resource does the lock protect, and which writes check ownership?
2. What happens if the holder pauses beyond the lease or loses its connection?
3. How does a new owner distinguish itself from an old owner? Is a fencing token enforced atomically?
4. What happens when acquisition succeeds on the server but the response is lost?
5. What happens when the lock service is unavailable: wait, fail the operation or use a documented fallback?
6. Can work be retried safely, and how is completion recorded?

## Interview answer

Start with the invariant, then name the primitive that enforces it. For example: “For rows in one database, I would use a transaction and a constraint or row lock. For work across workers, I would use a durable claim with an owner token and make the job idempotent. If an expired owner could still write, the resource must reject stale fencing values. I would not promise exactly-once execution from a lock.”

## Summary

A distributed lock coordinates temporary ownership across processes, but it cannot stop an expired or paused worker from running. Release must verify the current owner, and correctness-critical writes need enforcement at the protected resource, such as a fencing token or version condition. Prefer a transaction, constraint or idempotency when it directly protects the invariant.

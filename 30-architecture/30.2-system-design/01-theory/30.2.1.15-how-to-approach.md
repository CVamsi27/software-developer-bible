# How to Approach Any System Design Problem

A request to “design a URL shortener” sounds concrete until you ask what a redirect must guarantee. Can a user choose an alias? When does a new link become visible? Can old links expire? Those answers change the data model, write path and cache behavior. Good system design starts by finding the few unknowns that change the design.

## Definition

**System design** is the process of deciding how software components, data and communication fit together to meet a product’s needs. In an interview, you clarify an open-ended problem, propose an architecture and explain why its trade-offs fit the stated constraints.

> **Textbook Definition:** System design specifies components, interfaces, data placement and operating policies to satisfy functional requirements and measurable quality constraints under stated workload and failure assumptions.

A **functional requirement** describes what a user or another system can do. A **non-functional requirement (NFR)** sets a quality target or constraint, such as latency, availability, capacity or cost. A **service-level objective (SLO)** is a measurable target for a service-level indicator, such as the fraction of valid requests that finish within a latency threshold. Treat early numbers as assumptions until evidence replaces them.

## First Principles

1. **Behavior sets the shape of the system.** A link service that promises unique custom aliases has a different write invariant from one that accepts generated links only.
2. **Workload and quality targets expose bottlenecks.** Estimate the traffic, data and latency that could change a component or consistency choice.
3. **Every design choice buys one property and costs another.** Explain the cost that matters here, then state what evidence would make you revisit the choice.

## A 45-minute conversation

Use this as a starting allocation, not a script. Follow the interviewer’s signals and leave time to summarize.

| Time | Move | What the interviewer should be able to see |
| --------- | ----------------------------------- | ------------------------------------------------------------------- |
| 0–5 min | Clarify behavior and constraints | Agreed scope, invariants and assumptions |
| 5–10 min | Estimate the decision-changing load | A few checked calculations, including peak assumptions |
| 10–18 min | Sketch the end-to-end paths | Components and labeled reads, writes and asynchronous work |
| 18–40 min | Deep-dive the highest-risk decision | Alternatives, failure behavior, chosen trade-off and operating plan |
| 40–45 min | Close and invite correction | Main decisions, limits and the next measurement |

### Clarify what must be true

Start with the most important user flows and explicitly defer features that do not affect the core problem. For a URL shortener, ask whether users can choose aliases, whether aliases must be globally unique, whether links expire, and what redirect behavior is required.

Then identify the constraints that can change your design:

- **Load:** average and peak reads/writes, growth, payload size and geographic distribution.
- **Latency and availability:** which operations have targets, how success is counted, and over what measurement window. An SLO needs a defined indicator and eligible request population.
- **Data behavior:** which writes must be durable, whether users need read-your-writes, and how stale other reads may be.
- **Boundaries:** cost, data residency, privacy, security and existing systems the design must use.

Ask only questions that affect a decision. If the interviewer does not know a value, state a reasonable assumption and keep moving.

### Estimate only what can change a decision

Use order-of-magnitude arithmetic to reveal pressure on storage, network, partitions or service limits. For example, if the service receives 1 billion redirects per day, dividing by roughly 100,000 seconds gives about 10,000 average redirects per second. The peak may be much higher; state the peak factor as an assumption rather than presenting the average as capacity.

If that estimate does not change the first design, do not spend interview time refining it. Show the units, assumptions and one next measurement you would collect. Calculations are prompts for validation, not proof that a particular database or cache is necessary.

### Draw the smallest complete design

Sketch one request path at a time. For the shortener, show a client calling an application service, the service creating an alias and storing its mapping, and a redirect reading that mapping. Add a cache only if the read volume or latency target justifies it; add a queue only if secondary work such as analytics can happen after the redirect response.

Label which store is authoritative, what each component owns, and where data crosses a boundary. A box is useful only when it performs a distinct responsibility or enforces a requirement. If reads and writes differ, draw both paths. Do not begin with a catalog of technologies.

### Deep-dive where the design can fail

Choose the decision with the greatest correctness, scale or operational risk, then compare realistic alternatives. For the alias write, a uniqueness constraint in the authoritative store can arbitrate concurrent requests; a prior cache lookup cannot, because two writers can race. For redirect reads, a cache can reduce repeated lookups, but the design must state its expiry, invalidation and database-failure behavior.

Keep asking what happens when a dependency times out, a retry repeats a write, traffic becomes skewed, or a region is unavailable. Connect each failure to a user-visible result and recovery action. For example, if a cache is unavailable, send reads to the database only if its remaining capacity can absorb them; otherwise use a deliberate degraded response.

For every major choice, explain the alternative and the condition that would change your mind. “Use a relational database because alias uniqueness is transactional” is stronger than naming a database without tying it to the invariant.

### Close with operation and evidence

Summarize the scope, key decisions, main trade-off and known limit. Name the signals that would show whether the design meets its targets: request success, latency percentiles, saturation, storage growth, queue lag and cache behavior, as applicable. State how you would test the riskiest failure and which measurement would trigger a redesign.

A senior-level answer stays collaborative: make assumptions visible, invite correction, and adapt when the interviewer changes a requirement. Depth comes from tracing consequences through the system, not from drawing the largest architecture.

## Summary

Clarify the behavior and invariants first. Estimate only the workload that can change a decision, draw complete read and write paths, then examine the riskiest trade-off and its failure behavior. Close with operations, evidence and the assumptions that remain.

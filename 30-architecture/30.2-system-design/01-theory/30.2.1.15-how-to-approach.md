# How to Approach Any System Design Problem

## Definition

**System design** is deciding how software parts, data stores and communication fit together to meet a product’s needs. In an interview, you clarify an open-ended request, state assumptions, outline a design and explain its trade-offs with the interviewer.

The diagram helps explain the proposal. The important part is the decisions and the reasons behind them:

```text
requirements (features and measurable quality targets)
        ↓
traffic, data size and simultaneous users  ← estimates guide later choices
        ↓
API and data model                          ← requests, responses and stored information
        ↓
architecture                                ← parts of the system and their connections
        ↓
one important risk examined closely         ← often where follow-up questions go
        ↓
decisions explained with costs and benefits
```

A **functional requirement** describes what users can do. A **non-functional requirement (NFR)** describes a quality or limit, such as response time, capacity, availability or cost. A **service-level objective (SLO)** is a measurable target for a service, such as the fraction of requests completed within a stated time. Write down only the numbers that affect the design. They can be estimates with explicit assumptions. For important choices, explain the alternative and why it fits the stated needs.

## First Principles

The problem begins with missing details. You need to ask which details affect the design, make assumptions visible, and revise the proposal when new constraints appear.

1. **Clarify what the system must do and what matters most.** A booking system has different needs from a public catalog. Its traffic, correctness, latency and cost limits shape later choices.
2. **Estimate the workload before choosing capacity.** Requests, stored data and payload sizes give a rough sense of what the system must handle. Show the calculation and its assumptions so another person can check it.
3. **A design choice has a cost as well as a benefit.** For example, keyset pagination can work well for a stable sort order, but it does not support every arbitrary page jump. Explain the cost that matters for this system.

## Requirements

### Functional Requirements (clarify first)

Start with a few important user-visible features. State the related features that are outside the interview problem so you do not design for them accidentally.

### Non-Functional Requirements (clarify second)

Clarify measurable targets where they affect later choices. A percentile describes how requests are distributed: p95 latency is the time at or below which 95% of measured requests finish; p50 and p99 use 50% and 99%.

- Workload: requests per second, stored data, bandwidth and number of simultaneous users
- Latency: p50, p95 and p99 percentiles for important operations
- Availability: the target fraction of time the service meets its contract; translate it into an allowed failure budget for the reporting period
- Data visibility: must each read show the latest accepted write, or can some views update later?
- Durability: which accepted writes must survive which failures?
- Location: must the service work across regions, and how fresh must remote copies be?
- Legal or security constraints: identify which regulations or standards apply; naming one does not by itself make a design compliant

## How It Works

### A 4-Phase Framework

```text
┌──────────────────────────────────────────────────────────────┐
│ SYSTEM DESIGN INTERVIEW FRAMEWORK                            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│ Phase 1: CLARIFY (about 5 min)                               │
│ ├── List functional requirements (3-7)                       │
│ ├── Pin down NFRs (scale, latency, availability)             │
│ └── State explicit out-of-scope items                        │
│                                                              │
│ Phase 2: ESTIMATE (about 5 min)                              │
│ ├── Estimate requests per second from daily usage            │
│ ├── Estimate storage = records × size × retention            │
│ ├── Estimate bandwidth = requests × payload                  │
│ └── Pick the right shape (cache? queue? sharding?)           │
│                                                              │
│ Phase 3: HIGH-LEVEL (about 5-10 min)                         │
│ ├── Draw: client, traffic distributor, app, cache, database  │
│ ├── Mark data flow with arrows                               │
│ ├── Identify read/write paths                                │
│ └── Mark where identity is checked and requests are limited  │
│                                                              │
│ Phase 4: DEEP-DIVE (about 20-25 min)                         │
│ ├── Drill the bottleneck the interviewer cares about         │
│ ├── Discuss trade-offs, not "best practices"                 │
│ └── End with monitoring/operational concerns                 │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### Phase 1: Clarify (about 5 minutes)

Start by clarifying the requirements before choosing a database. In a short interview, reserve enough time to agree on scope, important quality targets and assumptions. Possible questions include:

- "What's the most important feature here — the one we must not get wrong?"
- "Is this for global users or one region?"
- "After someone changes something, must they immediately see their own change? Can other pages show older data for a while?"
- "What's the budget? Is this a 3-person team or 30?"
- "Should I optimize for latency or for cost?"

Then summarize the agreed scope and assumptions. This gives both people a chance to correct a misunderstanding before you draw the design.

### Phase 2: Capacity Estimation (about 5 minutes)

Use rough arithmetic (see the table below) to estimate workload size. The result is an order-of-magnitude estimate, not a performance claim. State assumptions and identify which part needs measurement.

These are rough starting points for interview arithmetic, not capacity guarantees. Replace them with measurements or service limits when available.

| Quantity | Starting estimate | What to check |
| ---------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------ |
| Seconds per day | About 86,000 (often rounded to 100,000) | State the rounding used in your calculation |
| Decimal storage units | 1 KB ≈ 1,000 bytes; 1 MB ≈ 1,000,000 bytes | Storage products may report binary units instead |
| Read-to-write ratio | Depends on the product and endpoint | Estimate from the workload; social feeds and messaging vary widely |
| Peak traffic | Often higher than the daily average | Derive peak from busy periods or state it as an assumption |
| Database or cache throughput | Varies with hardware, schema, queries, consistency and payload | Benchmark the actual workload and check provider limits |
| Network latency | Depends on region, routing and service path | Measure between the systems you plan to connect |

Worked example (URL shortener):

- 100M URLs/day created → using 100,000 seconds/day gives about 1,000 writes/sec average; assume 2,000/sec peak for this example
- 1B redirects/day → about 10,000 reads/sec average; assume 30,000/sec peak for this example
- 5-year retention × 500 bytes/URL × 100M/day × 365 ≈ 90 TB of base record data; indexes, replicas and backups add storage

### Phase 3: High-Level Architecture (about 5–10 minutes)

Draw the main parts and show how requests and data move between them. A load balancer (LB) can distribute requests across application instances; a cache can keep frequently read data closer to the application; a database (DB) stores authoritative records. Add other components only when a requirement calls for them:

| Problem needs | Add |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| Work that can finish later (email, video encoding) | A queue, such as Kafka or SQS, plus worker processes |
| Search / ranking | Search index (Elasticsearch / OpenSearch) |
| Full-text + facets | Same as above, but discuss indexing pipeline |
| Large files (images, videos) | Object storage, such as Amazon S3, Google Cloud Storage (GCS) or MinIO |
| Time-series measurements | A time-series database (TSDB), such as Prometheus, InfluxDB or TimescaleDB |
| Frequently read data | A cache such as Redis or Memcached |
| Users across distant locations | Multiple regions, a content delivery network (CDN), or location-aware DNS |
| Long-running jobs | Job queue (Sidekiq, Temporal, Airflow) |
| Machine-learning inference | A feature store plus a model-serving system, if the product needs them |

When a system has different read and write behavior, label both paths. This makes data flow easier to discuss.

### Phase 4: Deep-Dive (about 20–25 minutes)

Use the remaining time to examine the highest-risk parts of the proposal. Common areas include:

1. **Data and competing changes** — What records must be stored? Which queries need indexes? If data is split across partitions (shards), how are related records found and concurrent updates handled?
2. **The busiest operation** — Which request runs most often or takes the longest? How does it behave during a flash sale or a large traffic spike?

For each, compare a few realistic options and explain which one fits the current assumptions. Mention the main cost of the option you choose.

## Real-World Use Cases

- **Short design interview:** practice outlining a URL shortener, news feed, chat service or video platform. Use the interviewer's time limit and prompts to decide how much detail to include.
- **Longer design interview:** the problem may cover a broad product, such as a hospital system. Agree on scope, then spend time on the risks the interviewer wants to explore.
- **Take-home design document:** use the same reasoning, but include diagrams, alternatives and unresolved questions that do not fit in a live interview.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Jumping to "let's use Cassandra" | First derive the access pattern, then justify the store |
| Drawing every microservice in 5 minutes | Start with 3–5 boxes; split only when the interview asks |
| Using every tech buzzword | Pick a stack and explain it; don't name 12 databases |
| Skipping relevant estimates | Estimate the traffic or storage that changes a design choice, and state your assumptions |
| Ignoring writes | Trace how updates are checked, stored and made visible, as well as how reads work |
| Leaving operation unclear | For a production design, describe how the team would measure behavior, detect failures and respond |
| "It depends" without follow-up | Name what the answer depends on, then choose under the current assumptions |
| Forgetting cost | Flag bandwidth, storage, and compute as a constraint |

## Best Practices

1. **Drive the conversation** — Senior candidates use phrases like "Let me start with the requirements" and "The riskiest part of this design is X, so I'll deep-dive there next."
2. **State trade-offs out loud** — "If writes grow beyond what one database can handle, we could partition the data. First I would measure the workload and check which queries and transactions the application needs."
3. **Start simple, then iterate** — A 3-box design that the interviewer can challenge is better than a 15-box design that no one can read.
4. **Use estimates when they change a decision** — For example, an assumed 30,000 reads per second may justify testing a read replica. The estimate alone does not prove that a particular database needs one.
5. **Name the failure modes** — "If Redis is down, do we send more reads to the database, serve older cached data, or fail some requests? Choose and test the fallback against database capacity."
6. **Close with operations** — "How do we know this is healthy?" — name the measurements, alerts and response steps the team needs.
7. **Listen for hints** — When the interviewer says "what about X?" they are giving you the next deep-dive topic. Take it.

## Performance Considerations

| Factor | Impact | Mitigation |
| ----------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| One frequently requested key | Requests can overload the machine holding that key | Cache replicas or split the key where semantics allow; measure first |
| Uneven traffic | One account or product can receive a disproportionate share of requests | Measure the skew; isolate hot keys or limit abusive traffic where appropriate |
| Remote round trips | A request that waits on several sequential remote calls can accumulate their delays | Place data closer, reduce sequential calls or run independent calls in parallel |
| Too many database connections | Application instances can collectively exceed the database's connection limit | Size pools across all instances and bound retries |
| Garbage collection pauses | Runtime memory cleanup can delay some requests | Profile allocation and pauses; tune the runtime only when measurements show a benefit |

## Summary

- **Frame**: 4-phase loop — Clarify → Estimate → High-Level → Deep-Dive.
- **Time-box**: use the four phases, then adjust their length to the interview format.
- **Style**: State trade-offs out loud, name what you didn't pick and why.
- **Anchor**: show estimates when they affect a choice; finish by explaining how the system would be operated.
- **Collaboration**: lead the explanation while responding to new constraints from the interviewer.

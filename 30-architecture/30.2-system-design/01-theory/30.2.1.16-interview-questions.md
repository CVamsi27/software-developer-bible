# System Design Interview Questions

## First Principles

Start with the behavior the system must guarantee and the failures it must handle. Those requirements determine the data model and boundaries; choose technologies only after the constraints are clear.

## How to use these prompts

These 30 prompts are practice exercises, not a ranking of what interviewers ask most often. The difficulty labels are approximate. Any traffic, latency, or capacity number inside a prompt is an exercise assumption, not a benchmark or a claim about a real service.

For each prompt, state the product requirements and important invariants first. Estimate load only when the prompt provides enough information, then draw the simplest design that meets those requirements. Explain what can fail, how the system recovers, and what evidence would change your choices. Treat the sample answers as starting points, not scripts to memorize.

## Easy Level (1-10)

### 1. Design a URL Shortener

**Start by clarifying:** Is the short link public or private? Can users choose a code? Do links expire? Can a destination be edited or deleted? What redirect behavior and analytics are required? If the interviewer supplies traffic numbers, use those assumptions; do not invent production capacity from this example.

**A basic design:** The API validates the destination URL, creates a unique short code, and stores `code → destination` in a database with a uniqueness constraint. A redirect handler looks up the code and returns the configured redirect. Add a cache only after measuring database load and cache effectiveness. Send click events to an asynchronous analytics path if reporting must not slow redirects.

```text
Create: client → API → code generator → database
Redirect: client → redirect handler → cache (optional) → database
                                      └→ click event → analytics worker
```

**Code generation:** A sequence or allocated numeric ID encoded with Base62 can produce compact codes, but workers must allocate IDs without collisions. Random codes also work when the system checks the unique constraint and retries on collision. A truncated hash needs collision handling too; MD5 is not required for this problem and should not be presented as the default.

**Storage:** Keep the code unique. Store the destination, creation time, optional expiration, and owner or access policy if needed. A relational database is a reasonable starting point. Add partitioning only when measured size or throughput requires it; the partition key must preserve efficient lookup by short code.

**Redirect and analytics:** A permanent redirect may be cached by browsers and intermediaries, making destination changes and per-click measurement harder. A temporary redirect gives the service more control but adds a lookup on later visits. Choose based on whether links are editable, how analytics are defined, and what cache behavior is acceptable. HTTP status alone does not guarantee complete analytics.

**Failure cases to cover:** code collision, invalid or unsafe destination, expired link, database/cache outage, hot links, abuse and malicious redirects. State whether a cache outage falls back to the database or fails closed, and how that choice affects the service.

### 2. Design a Rate Limiter

**Start by clarifying:** What is limited (requests, writes, or another cost)? What is the key (account, API key, IP, tenant, or a combination)? Is the policy a steady rate, a burst allowance, or a strict quota? What should happen if the limiter store is unavailable?

**A basic design:** Each request derives a policy key, checks and updates its counter atomically, then either continues or receives `429 Too Many Requests` with an optional `Retry-After`. The state must be shared or coordinated when requests can reach multiple application instances. Local counters alone enforce only per-process limits.

**Choose an algorithm from the policy:**

- **Fixed window:** simple counter per interval; requests at the boundary can create nearly twice the intended short-term rate.
- **Sliding log:** accurate per-request history for a window; stores more state.
- **Sliding counter:** estimates a rolling window with less state; the estimate is approximate.
- **Token bucket:** accumulates tokens up to a capacity and spends one per request; permits a defined burst while limiting the long-term rate.

For a distributed token bucket, the read, refill, and consume operation must be atomic in the shared store. Use the store's server time or otherwise handle clock differences deliberately. The in-memory class below is only a single-process teaching example; it is neither thread-safe nor distributed.

```python
class TokenBucket:
    def __init__(self, capacity, refill_per_second, now):
        self.capacity = capacity
        self.refill_per_second = refill_per_second
        self.tokens = capacity
        self.updated_at = now

    def allow_request(self, now):
        elapsed = max(0, now - self.updated_at)
        self.tokens = min(
            self.capacity,
            self.tokens + elapsed * self.refill_per_second,
        )
        self.updated_at = now
        if self.tokens < 1:
            return False
        self.tokens -= 1
        return True
```

**Distributed storage:** A Redis implementation must perform the whole decision atomically, for example in a script that reads state, refills, checks, and writes it. A pipeline containing `INCR` and `EXPIRE` is not an atomic rate-limit decision: concurrent requests can race, and a failure between commands can leave incorrect expiry behavior.

**Failure behavior:** Decide whether limiter-store failures fail open, fail closed, or use a bounded local fallback. This is a product and abuse-risk decision. A local fallback changes the effective limit across instances; it does not preserve the distributed quota.

**Operations:** Monitor allowed and rejected requests, store latency/errors, key cardinality, and policy changes. Avoid unbounded keys from attacker-controlled values. For a service-capacity overload, use load shedding (often `503`) rather than pretending that every capacity failure is a client's rate-limit violation.

### 3. Design a Notification System

**Start by clarifying:** Which channels are required? Which notifications are urgent or optional? How do user preferences, quiet hours, retries, and delivery reports work? What does “delivered” mean for each provider?

**A basic design:** The product service records the business change and a notification intent. A worker reads pending intents, applies preferences, renders a template, and sends through a channel-specific provider. Provider callbacks update the delivery record. Keep provider-specific logic behind an adapter so that retry and error behavior can differ by channel.

```text
business transaction → durable notification intent → channel workers → providers
                                                    ← provider callbacks ←
```

**Protect the business transaction:** If a notification must follow a committed change, persist the intent in the same database transaction (for example, with an outbox). Otherwise a crash between saving the change and publishing the event can lose the notification. Workers should be safe to retry; use a stable notification ID and provider idempotency support where available.

**Delivery is not one state:** `queued`, `submitted`, `accepted`, `delivered`, `failed`, and `unknown` mean different things. A provider accepting a request does not prove that a person received or read it. Do not retry an ambiguous send blindly if it could create duplicates.

**Failure and abuse cases:** provider timeouts, rate limits, invalid addresses, delayed callbacks, duplicate callbacks, consent changes, and queue growth. Apply bounded retries with backoff, a dead-letter or review path, per-user and per-provider limits, and clear retention rules for message content.

**Trade-offs:** A queue isolates user requests from slow providers but adds delay and recovery work. Push, email, and SMS have different cost, urgency, consent, and delivery semantics. Choose fallback channels only when user preference and product policy allow them.

See [Queues & Async](30.2.1.06-queues-and-async.md), [Outbox & CDC](30.2.1.18-outbox-and-cdc.md), and [Transactional Email and Notifications](../../../20-backend/20.3-rest-apis/03-payloads-errors-integration/20.3.3.07-transactional-email-and-notifications.md).

### 4. Design a Chat System

**Start by clarifying:** Is this one-to-one, group chat, or both? What do users expect for message history, ordering, edits, delivery state, offline use, and search? Which scale and retention assumptions does the prompt provide?

**A basic design:** Authenticate a connection, authorize each conversation action, accept a client message with a stable ID, persist it, then publish it to connected recipients. A WebSocket can carry live updates, while durable storage remains the source for reconnect and history. A message broker can fan out work, but it does not replace message storage or access checks.

```text
sender → connection/API → authorize + persist → conversation event
                                                   ├→ connected recipients
                                                   └→ offline notification
```

**Ordering:** Define the scope. If messages need order within one conversation, assign a sequence or ordering key there. Do not promise global ordering across all conversations. Retries can duplicate a send, so deduplicate by the client message ID and conversation.

**Reconnect and offline delivery:** The client supplies its last received cursor; the server returns missing messages from durable storage, then resumes live delivery without a gap. Presence is approximate and should not decide whether a message is stored. Push notifications are hints to reconnect, not the message itself.

**Scaling and storage:** Partition events and message history by conversation when that preserves the required ordering and access pattern. Keep group membership and authorization checks available to the send and read paths. Add caches for measured hot reads; choose replication and retention based on durability and regional requirements.

**Failure cases:** connection loss during send, persistence success but lost acknowledgment, duplicate publish, unavailable broker, stale membership, hot group, and storage outage. State when the sender may safely retry and how clients reconcile uncertain outcomes.

See [WebSockets Overview](../../../60-realtime/60.1-websockets/01-transports/60.1.1.01-websockets-overview.md), [Consistency Models](30.2.1.02-consistency-models.md), and [Queues & Async](30.2.1.06-queues-and-async.md).

### 5. Design a Key-Value Store

**Start by clarifying:** Is this a single-node service or a distributed database? What are key/value size limits, read/write volume, durability, consistency, transactions, and availability requirements? What may a read return after a concurrent write or node failure?

**A basic distributed design:** Hash each key to a partition, route the request to its current owner, and replicate the partition according to a chosen protocol. Keep partition metadata or a deterministic routing scheme so clients and coordinators agree where a key belongs. Rebalancing must move data without losing writes.

```text
client → router/metadata → partition owner → replicas
                 key → partition → current replica set
```

**Partitioning:** A hash scheme spreads keys but does not preserve range queries. Consistent hashing or a partition map can reduce remapping when membership changes, but production systems also need virtual partitions, metadata updates, and controlled data movement. A short ring implementation is not enough to explain those guarantees.

**Replication and reads:** Define how writes are acknowledged, what happens when replicas disagree, and how stale reads are detected or repaired. A quorum intersection such as `R + W > N` is useful only under specific assumptions about the replica set and protocol; it does not by itself guarantee linearizable reads or resolve concurrent writes.

**Failure and recovery:** Discuss node loss, network partitions, replica repair, backup/restore, hot keys, disk-full behavior, and rolling membership changes. Choose consistency and availability from the application's contract rather than calling three replicas or a particular quorum a universal default.

See [Sharding & Replication](30.2.1.03-sharding-and-replication.md), [Consistency Models](30.2.1.02-consistency-models.md), and [CAP Theorem & PACELC](30.2.1.01-cap-theorem.md).

### 6. Design a Web Crawler

**Start by clarifying:** What pages are in scope? How fresh must they be? Are pages rendered with JavaScript? What limits apply to storage, bandwidth, domains, and legal or policy requirements?

**A basic design:** Start URLs enter a durable frontier. Fetch workers lease URLs, check domain policy and crawl delay, fetch with bounded timeouts, parse content and links, normalize discovered URLs, and enqueue eligible unseen pages. Store fetch metadata separately from page content so failures and recrawls can be managed.

```text
seeds → durable frontier → policy/scheduler → fetchers → parser
              ↑                                  ├→ page store
              └──── normalized discovered links ─┘
```

**Politeness and safety:** Read and apply `robots.txt` according to the crawler's policy; the protocol communicates crawl rules but is not access authorization. Limit concurrency and request rate per host, identify the crawler, honor response signals, and avoid repeatedly fetching failures. Resolve and validate destinations safely to prevent server-side request forgery and access to private network addresses.

**Deduplication:** Normalize URLs carefully (scheme/host case, default ports, fragments, and selected query parameters) without merging URLs that the site treats as different. Exact deduplication costs storage; a Bloom filter saves memory but false positives can skip pages. Use it only if that loss is acceptable or confirm positives against exact state.

**Failure cases:** redirect loops, traps from calendars or faceted URLs, oversized responses, decompression bombs, slow hosts, DNS changes, robots fetch failures, duplicate workers, and frontier growth. Bound depth and response size, lease work with recovery, and make page writes idempotent.

See [RFC 9309 — Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html) and [Probabilistic Data Structures](30.2.1.17-probabilistic-data-structures.md).

### 7. Design Search Autocomplete

**Start by clarifying:** What data is searched? How fresh must suggestions be? Is ranking global, personalized, or both? What latency and privacy constraints apply? Can a user delete or opt out of their history?

**A basic design:** Normalize the query, retrieve a bounded set of prefix matches from an index, rank them, and return a small result set. A trie is one option for prefix lookup; a sorted term index or search engine may fit better when updates, ranking, and distribution matter. Do not choose a data structure before defining update and ranking needs.

```text
query prefix → prefix index → candidate suggestions → rank/filter → response
                                     ↑
                         offline or streaming updates
```

**Ranking:** Combine signals such as query frequency, recency, locale, and policy filters. Personalization may improve relevance but requires a clear data boundary, retention policy, and opt-out behavior. Filter unsafe, private, or disallowed suggestions before returning them.

**Freshness and scale:** Update the index in batches or incrementally according to the freshness target. Precomputing top suggestions for every prefix can speed reads but uses more memory and complicates updates. Measure query latency, index size, update delay, and ranking quality against the chosen workload rather than assuming a cache-hit rate.

**Failure cases:** stale index, hot prefixes, abusive queries, cache or ranking-service outage, and deletion requests not reaching derived indexes. Keep a bounded fallback and define how quickly deletions must affect suggestions.

### 8. Design a Web Analytics System

**Start by clarifying:** Which events and reports are needed? How fresh must dashboards be? What duplicate or missing-event rate is acceptable? What consent, retention, deletion, and access rules apply?

**A basic design:** Clients or servers send validated events to a collector. The collector authenticates the source, applies size and rate limits, and writes to a durable stream. Consumers update near-real-time aggregates and a historical analytics store. Keep the raw event path separate from query-serving so a dashboard spike does not block ingestion.

```text
event producer → collector → durable stream → validation/deduplication
                                               ├→ live aggregates
                                               └→ retained event store → reports
```

**Event contract:** Include an event ID, event type, schema version, event time, ingestion time, and only the identifiers and properties needed for the analysis. Validate schemas at the boundary. Client clocks can be wrong, events can arrive late, and retries can duplicate them; define which timestamp controls each report and how duplicate IDs are handled.

**Partitioning and queries:** Choose partition keys and retention from the expected query patterns. Time partitioning can help bounded time-range queries; a high-cardinality user key may create skew or many small partitions. Pre-aggregate common reports, but preserve enough source data for the corrections and retention policy you support.

**Failure and privacy:** Provide bounded buffering and retry, isolate malformed events, and monitor ingestion lag and dropped data. Define how consent changes and deletion requests reach raw events, aggregates, exports, and backups. Do not include sensitive fields just because the event schema permits arbitrary properties.

See [Queues & Async](30.2.1.06-queues-and-async.md) and [Capacity Planning](30.2.1.12-capacity-planning.md).

### 9. Design a Content Delivery Network (CDN)

**Start by clarifying:** Which content is cacheable? How fresh must it be? Are responses personalized or authenticated? Which regions and failure scenarios matter? What are the origin's capacity limits?

**A basic design:** Route a client request to an edge location, check for a valid cached response, and fetch from the origin on a miss. An edge may use an upstream cache tier, but the number of tiers and locations depends on the provider and workload. Protect the origin with request coalescing, rate limits, and controlled retries where supported.

```text
client → edge cache → (optional parent cache) → origin
             └─ hit: return response
```

**Cache correctness:** Define the cache key and the response rules together. Include the host, path, and any request variation that changes the response. Do not share-cache private or user-specific data unless the key and policy safely isolate it. Respect cache directives, freshness, stale-serving policy, and authorization boundaries.

**Invalidation and rollout:** Versioned asset names make immutable static files easy to cache. For mutable content, use TTLs or purge APIs and understand propagation behavior. Keep the origin able to serve uncached traffic during a cold start or purge, and test failures rather than assuming every edge refreshes at once.

**Routing and measurement:** DNS may select an entry point, while anycast or provider routing can direct packets to an edge. Resolver location is not always the same as end-user location. Measure cache hit rate, origin load, stale responses, error rates, and user latency by region; do not assume fixed edge counts or latency numbers.

See [CDN Architecture](../../../40-platform/40.10-cdn/40.10.01-cdn-architecture.md), [HTTP Caching](../../../20-backend/20.3-rest-apis/02-http-mechanics/20.3.2.04-http-caching.md), and [DNS & Name Resolution](30.2.1.22-dns-and-name-resolution.md).

### 10. Design a Unique ID Generator

**Start by clarifying:** Must IDs be unique only within one database or across independent regions? Must they be numeric, compact, hard to guess, sortable by approximate creation time, or strictly increasing? What happens if a generator restarts or its clock moves backward?

**Choose a scheme from those requirements:**

- **Database sequence:** simple and ordered at its authority, but generation depends on that database or a coordinated sequence service. Gaps can occur; do not promise gap-free IDs unless the design specifically guarantees it.
- **Random UUID (such as version 4):** generated without a central allocator and has a very low collision probability when generated correctly, but it is not time-sortable and can have different index-locality costs.
- **Time-ordered UUID (version 7):** places a timestamp in the UUID layout to improve time ordering, but does not establish a strict global order across machines or solve clock and same-time generation behavior by itself.
- **Snowflake-style ID:** combines a timestamp with worker identity and a per-time-unit sequence. It needs unique worker assignment and an explicit clock rollback/sequence-exhaustion policy.

**System shape:** Put a stable API in front of one or more generators only if clients need centralized policy or metrics. If workers generate IDs independently, state how worker identities are allocated and recovered. If an ID is used as a credential, add a separate authorization or unguessability mechanism; uniqueness is not access control.

**Trade-offs to explain:** sortability versus coordination, identifier size versus index behavior, timestamp leakage, worker registration, and behavior during clock or network faults. Test uniqueness over the actual generator lifecycle, including restarts and failover, rather than claiming a scheme is collision-proof.

See [RFC 9562 — UUIDs](https://www.rfc-editor.org/rfc/rfc9562.html) for the UUID formats and generation considerations.

## Medium Level (11-20)

### 11. Design a Ride-Sharing Service

**Start by clarifying:** Is the task dispatch, the entire trip lifecycle, or both? What are the location freshness and pickup constraints? How are drivers matched, and can a driver accept more than one offer? Which payment, cancellation, and safety flows are in scope?

**A basic design:** Driver devices send authenticated location updates. A location service stores the latest position with a freshness time and indexes eligible drivers by area. A dispatch service searches nearby candidates, applies product rules and estimated travel time, then sends an offer. The durable trip service owns the state transition from requested to accepted, picked up, completed, or cancelled.

```text
driver locations → geo index → candidate search → offer/accept
rider request → trip state machine ─────────────→ confirmed driver
```

**Correctness before proximity:** Nearby search produces candidates, not a reservation. Two dispatch workers can select the same driver, so acceptance must use an atomic trip/driver state transition with an idempotent request identity. Location records should expire or be marked stale; stale coordinates must not make an offline driver look available.

**Tradeoffs and failure cases:** A larger search radius can improve match probability but increase pickup time. Mapping and location services can be delayed or unavailable. Handle duplicate location updates, offer timeouts, driver disconnects, rider cancellation, and payment uncertainty without losing the trip's durable state. Keep high-frequency location telemetry separate from the authoritative trip record.

Avoid claiming a fixed Redis capacity or sharding scheme without workload and freshness requirements. See [Capacity Planning](30.2.1.12-capacity-planning.md), [Consistency Models](30.2.1.02-consistency-models.md), and [WebSockets Overview](../../../60-realtime/60.1-websockets/01-transports/60.1.1.01-websockets-overview.md).

### 12. Design a Social Media Feed

**Start by clarifying:** Is the feed chronological or ranked? Are posts public, private, or both? How fresh must new posts appear? How are follows, blocks, deletions, and muted users applied?

**A basic design:** Persist a post once in the author's post store. Build each reader's timeline as a projection of eligible post IDs, then fetch post content and apply current visibility rules when serving the feed. A queue can update projections asynchronously, so the API must define whether a new post appears immediately or after a short delay.

```text
new post → durable post store → fan-out workers → reader timeline projections
reader request → candidate posts → visibility/ranking → page response
```

**Push and pull:** Fan-out-on-write copies a post reference to readers' timelines, making reads simpler but making high-follower posts expensive. Fan-out-on-read gathers recent posts from followed authors, reducing write work but making reads depend on follow-graph size. A hybrid can use both; choose based on measured distribution and freshness requirements, not a fixed follower-count threshold.

**Correctness and privacy:** Make projection updates idempotent and deduplicate post IDs when merging sources. Apply blocks, private-account rules, and deletions even if a cached projection is stale. Use a cursor stable enough for pagination while new posts arrive; avoid relying on offset pagination over a moving feed.

**Failure cases:** delayed fan-out, duplicated events, hot authors, stale caches, deleted posts, and ranking-service outage. Keep the post store authoritative and define a simpler fallback feed if ranking is unavailable.

See [Queues & Async](30.2.1.06-queues-and-async.md), [Outbox & CDC](30.2.1.18-outbox-and-cdc.md), and [Pagination](../../../20-backend/20.3-rest-apis/03-payloads-errors-integration/20.3.3.01-pagination.md).

### 13. Design a Video Streaming Service

**Start by clarifying:** What upload sizes and formats are supported? Must playback begin before the full video is processed? Which devices, access rules, latency, and availability targets matter? Are recommendations in scope or a separate product system?

**A basic design:** The API authorizes an upload and issues a bounded upload session. The client sends the file to object storage, often in resumable parts. When the upload is complete, a durable job starts validation and transcoding. The system publishes a video only after required renditions and manifests are ready; playback requests use a CDN that retrieves authorized content from storage.

```text
client → upload session → object storage → validate/transcode/package
                                             ↓
client ← manifest/segments ← CDN ← published renditions
```

**Playback:** Package renditions and segments for adaptive streaming so the player can change quality as bandwidth changes. Cache public segments with clear versioning. For private videos, use authorization and short-lived access mechanisms that do not accidentally turn a shared cache into a data leak.

**Processing and failure:** Track each video through explicit states such as uploading, processing, ready, and failed. Make jobs retryable and idempotent; record which rendition failed and allow targeted recovery. Validate media type and size, scan or moderate as required, and keep the original according to retention policy. A recommendation system is a separate read path and should not block upload or playback.

**Capacity:** Estimate from actual assumptions supplied in the prompt: upload volume, average source size, rendition count, retention, watch traffic, and cache hit rate. Do not present example resolutions, edge counts, or bandwidth as universal requirements.

See [CDN Architecture](../../../40-platform/40.10-cdn/40.10.01-cdn-architecture.md) and [Queues & Async](30.2.1.06-queues-and-async.md).

### 14. Design a Payment System

**Start by clarifying:** Which payment methods and lifecycle states are needed? Does the system authorize then capture, or charge immediately? How are refunds, disputes, currencies, and reconciliation handled? What must a retry guarantee after a timeout?

**A basic design:** Authenticate the merchant, validate the request, and create a durable payment operation with a stable idempotency key and parameter fingerprint. Record state transitions in a database. A worker or request handler calls the processor with the same idempotency key where supported, stores the result, and exposes a status that can be queried after a lost response.

```text
merchant → payment API → durable operation → processor
               ↑                ↓                ↓
           status query ← state/outbox ← webhook/reconciliation
```

**Idempotency and uncertainty:** Enforce uniqueness of the key within the correct merchant/operation scope and reject reuse with different parameters. A timeout does not prove that the processor failed; query or retry using the processor's supported idempotency mechanism before attempting a new operation. A local Redis check followed by a charge and a later cache write is unsafe: concurrent requests can both charge, and a crash can lose the stored result.

**Webhooks and reconciliation:** Verify webhook signatures, persist event IDs before acknowledging, and process duplicates safely. Events may arrive late or out of order, so fetch the canonical processor object when needed and validate allowed state transitions. Reconciliation compares internal records with processor reports and settlement data to find unresolved differences.

**Failure and safety:** Handle duplicate submissions, processor timeouts, partial refunds, webhook outages, key misuse, ledger imbalance, and sensitive-data boundaries. Keep an append-only financial record or ledger model appropriate to the product. Do not automatically route a payment to another processor after an ambiguous result; resolve the first attempt first.

Stripe documents its own [idempotency behavior](https://docs.stripe.com/api/idempotent_requests) and [webhook practices](https://docs.stripe.com/webhooks); provider contracts vary. Also see [Webhooks](../../../20-backend/20.3-rest-apis/03-payloads-errors-integration/20.3.3.05-webhooks.md) and [Outbox & CDC](30.2.1.18-outbox-and-cdc.md).

### 15. Design a Ticket Booking System

**Start by clarifying:** Are seats assigned or general admission? How long may a reservation last? Can a user reserve multiple seats? What happens if payment succeeds but the confirmation response is lost? What traffic bursts does the prompt specify?

**A basic design:** Read availability from a query model, but reserve through an authoritative transaction. Create a hold with an owner and expiry using a conditional update or uniqueness constraint so concurrent buyers cannot both hold the same seat. Record the booking state durably before starting payment.

```text
browse availability → request hold → atomic durable reservation
                                      ↓
                            payment operation → confirm or release
```

**Hold lifecycle:** A hold moves through pending, confirmed, expired, or cancelled states. A worker can release expired holds, but every transition must check the current owner and expiry; a delayed worker must not release a newer hold. Redis TTL can accelerate temporary coordination, but it should not be the only record that determines whether a seat was sold.

**Payment and retries:** Give the payment operation a stable idempotency identity. If payment times out, reconcile its status before releasing the seat or charging again. If payment succeeds after a hold expires, define whether to reacquire the seat, refund, or send the case for resolution.

**Failure and scale:** Handle oversold inventory, duplicate client submissions, queue backlogs, partial multi-seat holds, and flash-sale load. Use a waiting room or admission control when needed, and measure it against the stated demand. Generate a ticket only after the booking reaches its confirmed state.

See [Transactions](../../../20-backend/20.4-database/03-transactions-and-replication/20.4.3.01-transactions.md), [Idempotency Keys](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md), and [Capacity Planning](30.2.1.12-capacity-planning.md).

### 16. Design a Search Engine

**Start by clarifying:** Is this web-wide search or search over one product's documents? Which fields and languages matter? How fresh must changes be? What ranking, filtering, access-control, and latency behavior is required?

**A basic design:** Ingest documents from their source, normalize and tokenize text, and build an inverted index mapping terms to documents and positions. A query service parses the request, retrieves candidate documents, applies filters and access rules, ranks candidates, and returns a stable page of results. Keep the source documents authoritative; the search index is a derived view that may lag.

```text
source changes → ingestion → analysis/indexing → searchable index
query → parse/analyze → retrieve candidates → filter/rank → results
```

**Ranking and updates:** BM25 is a common lexical ranking method; other signals depend on the product. Spell out freshness and deletion behavior, including how updates propagate to replicas and caches. If the prompt requires vector or semantic retrieval, describe how that path combines with exact filters and lexical results rather than adding it by default.

**Scale from the workload:** Estimate document count, average indexed size, update rate, query concurrency, and retention only from stated assumptions. Partition the index according to search and update patterns. Replicas can improve availability and query capacity but add storage and update work. Cache only queries whose results remain correct under the chosen personalization and freshness rules.

**Failure and security:** Handle partial indexing, malformed documents, unavailable shards, expensive queries, tenant isolation, and deletion requests. Apply authorization before returning results, not only when the document is first indexed.

See [PostgreSQL Search Infrastructure](../../../20-backend/20.4-database/05-operations-and-scaling/20.4.5.05-search-infrastructure-at-scale.md) and [Pagination](../../../20-backend/20.3-rest-apis/03-payloads-errors-integration/20.3.3.01-pagination.md).

### 17. Design a Distributed Cache

**Start by clarifying:** What data is cached and where is the source of truth? Is the cache-aside, write-through, or another pattern? How stale may a value be? What should happen when the cache is unavailable or loses its contents?

**A basic design:** The application routes a key to a cache node, reads a hit, and fetches from the source on a miss. Writes update the source and then invalidate or refresh cache entries according to a defined policy. A distributed cache reduces repeated source work; it does not make cached data authoritative unless the application explicitly designs it that way.

```text
read: app → cache ─ hit → response
                └ miss → source → populate cache → response
write: app → source commit → invalidate or refresh cache
```

**Placement and eviction:** Consistent hashing or a partition map can assign keys to nodes, but membership changes need controlled remapping and clients must learn the new topology. Eviction policy (for example, LRU or LFU) answers which entries to remove under memory pressure; TTL answers how long an entry may remain valid. They are separate choices.

**Consistency and resilience:** Invalidation can race with an in-flight stale fill. Use versions, write ordering, or a bounded-staleness policy where stale values would cause harm. Replication can improve availability but introduces stale copies and repair work. Plan for hot keys, cache stampedes, cold starts, and partial network partitions. Avoid retries that multiply load on an already failing source.

**Measure:** hit and miss rates, source load, evictions, memory pressure, request latency, stale responses, and recovery time after a flush. Choose these from the service's actual objectives rather than assuming a fixed replica count or cache-hit percentage.

See [Caching Patterns](30.2.1.05-caching-patterns.md) and [Sharding & Replication](30.2.1.03-sharding-and-replication.md).

### 18. Design a Task Scheduler

**Start by clarifying:** Are tasks one-time or recurring? What do schedule expressions and time zones mean? What should happen after downtime or a missed run? Are duplicate executions acceptable, and how are task versions or cancellations handled?

**A basic design:** Store each schedule durably, compute due occurrences, and atomically lease each occurrence to a worker. The worker records an attempt, runs the task, and stores the outcome. A lease lets another worker recover work after a crash, so the task handler must be safe to retry or use an idempotency key.

```text
schedule store → due-occurrence planner → leased queue → workers
       ↑                    └→ run history/status ←┘
```

**Recurrence and time:** Define daylight-saving transitions, time-zone changes, missed-run policy (skip, run once, or catch up), and whether changing a schedule affects already-created occurrences. Use a stable identity for each schedule occurrence so multiple scheduler instances do not enqueue the same logical run.

**Execution semantics:** A scheduler can provide at-least-once attempts with retry and recovery; it cannot guarantee exactly-once side effects in an external system without cooperation from that system. Separate schedule state from attempt state. Bound retries, use backoff, and send exhausted work to a reviewable failure path.

**Operations:** Monitor scheduling lag, queue age, running and stuck leases, success/failure counts, and retry volume. Allow cancellation and pause to take effect at a defined boundary. Scale workers from queue pressure while protecting downstream dependencies with concurrency limits.

See [Queues & Async](30.2.1.06-queues-and-async.md), [Distributed Locks](30.2.1.14-distributed-locks.md), and [Idempotency Keys](../../../30-architecture/30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md).

### 19. Design a File Storage and Sync System

**Start by clarifying:** What are the file size and type limits? Is sync one-way or across devices? How should simultaneous edits, renames, deletes, sharing, version history, and offline devices behave?

**A basic design:** The API authenticates the user and creates an upload session. File bytes go to durable object storage; metadata records ownership, path, version, size, and content identity. After upload completion and validation, the service commits a new version and publishes a change for other devices. Clients use a cursor to discover changes and fetch content they are authorized to read.

```text
client → upload session → object storage → validate/commit metadata
other device ← change feed/cursor ← committed version
```

**Sync model:** Treat content, metadata, and notifications as separate concerns. A WebSocket can announce that something changed, but clients must recover from disconnects by querying a durable change feed. Define conflict behavior for concurrent edits; silently overwriting one device's work is not a sync strategy. Deletions need tombstones or another durable signal so offline clients do not resurrect removed files.

**Chunking and deduplication:** Chunking can support resumable uploads or transfer only changed portions. Fixed-size chunks are simple; content-defined chunking can preserve boundaries after insertions but adds complexity. Content hashes help identify duplicate blocks, but global deduplication can leak whether another user has a file and requires strict authorization. It is optional, not the starting design.

**Failure and security:** Handle interrupted uploads, checksum mismatch, malware scanning, quota exhaustion, partial metadata commits, stale cursors, link revocation, and version recovery. Keep object-store access scoped and short-lived; never expose a shared content hash as authorization.

See [Outbox & CDC](30.2.1.18-outbox-and-cdc.md) and [WebSockets Overview](../../../60-realtime/60.1-websockets/01-transports/60.1.1.01-websockets-overview.md).

### 20. Design a Metrics Monitoring System

**Start by clarifying:** Which decisions should operators make from these metrics? What freshness and retention are required? How many services and dimensions are expected? Which alerts need paging, and what response should they trigger?

**A basic design:** Services expose or emit measurements. Collectors scrape or receive them, validate names and labels, and write to a time-series store. Query and dashboard systems aggregate data for humans; an alert evaluator checks defined conditions and routes actionable notifications. Preserve the monitoring path independently enough that an application incident does not hide all telemetry.

```text
services → scrape/receive → validate/aggregate → time-series store
                                                    ├→ dashboards/queries
                                                    └→ alert rules → responders
```

**Metric design:** Choose counters, gauges, and histograms from the question being answered. Labels create separate time series; unbounded values such as request IDs or raw URLs can cause uncontrolled cardinality and storage use. Keep identifiers in logs or traces instead. Define units, labels, and aggregation semantics consistently across services.

**Alerts:** Alert on user-visible symptoms and SLO/error-budget conditions where possible, not every metric threshold. A useful alert names the impact, includes context, and links to a runbook. Group duplicate notifications, handle missing telemetry explicitly, and distinguish warning dashboards from pages that require immediate action.

**Retention and failure:** Set retention and downsampling from investigation and cost needs. Bound ingestion and protect against a single tenant or label explosion. Monitor scrape gaps, ingest lag, query load, storage capacity, and alert delivery itself. A monitoring system can be healthy while one target is missing; show that gap clearly.

See [Monitoring](../../../40-platform/40.4-observability/01-pillars/40.4.1.02-monitoring.md), [SLI/SLO/SLA](../../../40-platform/40.4-observability/03-sre-targets/40.4.3.01-sli-slo-sla.md), and [Alerting](../../../40-platform/40.4-observability/03-sre-targets/40.4.3.02-alerting.md).

## Hard Level (21-30)

### 21. Coordinate a Business Operation Across Services

**Start by clarifying:** Which invariants must hold? Do all participants share one database? Is temporary inconsistency acceptable? What should users see while a step is pending, and how are failures compensated?

**Choose the smallest transaction boundary:** If the state fits in one database, use a local transaction. For independent services, a distributed transaction coordinator (such as two-phase commit) can provide atomic commit only when participants support the protocol; participants may block while the coordinator recovers. A saga instead commits local steps and records progress, then runs compensating business actions when a later step fails. Compensation is not always a perfect rollback.

```text
single store: validate + update → one local commit
multiple services: step A → durable progress → step B → complete
                                       └ failure → compensate/reconcile
```

**Make each step recoverable:** Persist operation identity and state, use an outbox for publication intent, and make consumers and external calls idempotent where possible. Define how retries, timeouts, duplicate messages, and human review affect each state transition. Do not report success until the required invariant is actually established.

**Separate related patterns:** Event sourcing stores state changes as an event history; it is not itself a distributed transaction protocol. CQRS separates read and write models; it does not create atomicity. Use either only when its distinct requirements justify the additional model and operations.

**Tradeoff:** Choose between waiting for coordinated atomicity and allowing a visible, recoverable workflow. Explain the user's experience during pending state, what data can disagree temporarily, and how reconciliation detects unfinished work.

See [Distributed Transactions](30.2.1.07-distributed-transactions.md), [Outbox & CDC](30.2.1.18-outbox-and-cdc.md), and [Queues & Async](30.2.1.06-queues-and-async.md).

### 22. Design a Streaming Analytics System

**Start by clarifying:** What events are processed, at what assumed rate, and how fresh must results be? Are reports based on event time or arrival time? How should duplicates and late events affect results? What historical queries must remain possible?

**A basic design:** Validate events at ingestion, write them to a durable log, and process partitions with stateful workers. Workers produce windowed aggregates to a query store and retain or archive source events according to the replay and retention policy. Keep the query path separate from ingestion.

```text
producers → durable event log → stateful stream workers → aggregates/query store
                                      └ checkpoint/replay ─→ recovery
```

**Time and correctness:** Event time is when an event occurred; processing time is when the system handled it. Watermarks let a processor decide when a window is likely complete, but very late events still need a policy: update results, route for correction, or drop with accounting. Deduplication needs a stable event identity and a defined retention window.

**Recovery and output:** Checkpoints restore processor state, while replay rebuilds results from retained input. A sink may still receive duplicate writes after a crash; use idempotent writes, transactional integration, or reconciliation as appropriate. Do not claim end-to-end exactly-once behavior from the stream processor alone.

**Scale from assumptions:** Estimate event size, partition count, state size, retention, processing cost, and query needs from the prompt. Monitor consumer lag, late-event rates, checkpoint failures, state growth, and freshness of published aggregates. A named product or “millions per second” target is not a design unless the workload is specified.

See [Queues & Async](30.2.1.06-queues-and-async.md), [Capacity Planning](30.2.1.12-capacity-planning.md), and [Outbox & CDC](30.2.1.18-outbox-and-cdc.md).

### 23. Design a Multi-Region Database

**Start by clarifying:** Which reads and writes must be local? What consistency is required per operation? What are the recovery point and recovery time objectives? What data-location rules, traffic patterns, and partition behavior matter?

**Choose write authority per data:** A single write region with replicas elsewhere simplifies conflict handling but adds cross-region latency for remote writes and can lose acknowledged data if replication is asynchronous. Partitioning write ownership by tenant or key can keep most writes local. Allowing concurrent writes in multiple regions requires an explicit conflict policy and may weaken what reads can promise.

```text
option A: clients → home-region writer → async replicas → regional reads
option B: clients → key owner → replicated partitions → policy-based reads
```

**Consistency and recovery:** Synchronous coordination can preserve stronger write guarantees for a stated failure model but adds network coordination and may reduce availability during partitions. Asynchronous replication lowers write coordination but creates lag and possible loss on failover. Before promotion, fence the old writer, verify recovery state against the RPO, and prevent split brain; test the process to measure actual RTO.

**Conflicts and residency:** Last-write-wins can discard meaningful updates and depends on timestamp behavior. Vector clocks can expose concurrent versions but require application resolution. CRDTs fit only operations with a merge rule that preserves the domain invariant. Data residency depends on the applicable rules and data flows, including backups and operational access; it is not solved by adding a region.

**Measure and rehearse:** Track replication lag, regional read/write latency, failover duration, and data loss in exercises. Do not call the design active-active and assume that all records can be safely written anywhere.

See [Multi-Region Deployment](30.2.1.20-multi-region-deployment.md), [Consistency Models](30.2.1.02-consistency-models.md), and [Sharding & Replication](30.2.1.03-sharding-and-replication.md).

### 24. Design a Recommendation System

**Start by clarifying:** What items are recommended, where do they appear, and what outcome should improve? What user and item data may be used? How fresh must behavior affect results? What latency, privacy, and opt-out requirements apply?

**A basic design:** Generate a candidate set, filter items the user cannot or should not see, score the remaining candidates, and return a bounded result with a fallback for missing or stale features. Candidate generation may use item similarity, co-occurrence, or collaborative signals; ranking can combine relevance with product constraints. Keep eligibility and policy filters separate from model scores.

```text
user/context → candidates → eligibility filters → ranker → bounded results
                                  ↑                  ↑
                           catalog/policy       model/features
```

**Data and serving:** An offline job can train or refresh models from retained interactions. An online feature path supplies fresh context for serving. Version models and features together enough to reproduce decisions, and define behavior when the online feature store or model is unavailable. Do not put recommendation computation on a critical path that must remain available for the core product action.

**Evaluation and safety:** Separate offline ranking metrics from online experiments. Use guardrails for latency, user harm, exposure balance, privacy, and business outcomes; randomization needs a clear assignment unit and experiment record. Handle cold-start users/items, feedback loops, deleted data, and abusive manipulation of engagement signals.

**Scale from measured needs:** Estimate candidate volume, feature size, update frequency, and serving concurrency from the prompt. A specific ML framework is an implementation choice, not an architecture requirement.

### 25. Design a Graph Data Store

**Start by clarifying:** Which relationship queries must be fast? How large are nodes and edges? Are writes frequent? Is the graph mostly read-only or changing? Do queries need shortest paths, bounded traversals, or analytics across the whole graph?

**A basic design:** Store vertices, edges, and properties with indexes for the starting points used by queries. A traversal follows adjacent edges while enforcing depth, authorization, and resource limits. Choose a storage layout from the access pattern: adjacency-oriented layouts help local traversals, while relational tables or specialized graph stores may be simpler for other workloads.

```text
start vertex → indexed lookup → bounded edge traversal → filtered result
```

**Query costs:** A breadth-first search can find an unweighted shortest path, but work grows with the explored graph. Weighted paths require a different algorithm; community detection is a separate graph-analysis workload. Set depth and result limits so a broad or cyclic graph cannot consume unbounded resources.

**Partitioning:** Keeping connected vertices together can reduce traversal hops but may create hotspots and make rebalancing difficult. Partitioning only by vertex ID can send each edge traversal across the network. Replicas help availability or reads but require update consistency. Explain which queries cross partitions and how the design handles skew.

**Failure and security:** Define edge updates, deletion, consistency during traversals, tenant isolation, and recovery. Enforce authorization during traversal so a connected path cannot reveal restricted vertices or relationships.

### 26. Design a Service Mesh

**Start by clarifying:** Which problems should the mesh solve: service identity, encrypted transport, traffic policy, retries, or telemetry? What platform and operational capacity already exist? A mesh adds another layer to deploy and debug, so first compare it with library, gateway, and platform-native options.

**A basic model:** The data plane handles service traffic and applies configured policies. A control plane distributes identity material and policy to data-plane components; it usually is not on the request path. Deployments may use sidecars, node-level proxies, or other forms, so “one sidecar per service” is not a universal requirement.

```text
workload A → local data-plane proxy → workload B
                    ↑
            policy and identity
                    ↑
               control plane
```

**Policy boundaries:** Service identity can support mutual TLS and workload-level authorization, but encrypted transport alone does not prove that a caller may access a resource. Retries, timeouts, load balancing, and circuit breaking need limits that fit the request deadline and operation semantics. Automatically retrying a non-idempotent write can duplicate its effect.

**Operations and tradeoffs:** Measure proxy CPU and memory, added latency, configuration propagation, and failure behavior. Decide what existing connections do if the control plane is unavailable, how invalid policy is rejected or rolled back, and how operators distinguish application failure from proxy failure. A mesh centralizes common traffic controls; it does not remove the need for application authorization, sensible timeouts, or end-to-end tracing.

### 27. Design a Multi-Tenant SaaS

**Start by clarifying:** What must be isolated—rows, encryption keys, compute, backups, or all of them? Are there contractual or regulatory reasons to dedicate infrastructure to some customers? What onboarding, tenant migration, customization, and noisy-neighbor limits are required?

**Choose an isolation model:** A shared database and schema with a `tenant_id` is operationally simple and cost-efficient, but every access path must preserve tenant scope. Separate schemas or databases can improve isolation and simplify some customer-specific operations, at the cost of more provisioning, migrations, and fleet management. Many products use a shared default and offer dedicated environments where requirements justify them.

**Enforce the boundary:** Derive tenant identity from the authenticated principal and its authorized memberships; do not trust a client-supplied tenant ID by itself. Carry that identity through API authorization, database queries, background jobs, caches, object storage, search indexes, exports, and audit records. Add tenant-aware uniqueness constraints and indexes where appropriate. Database row-level security can provide defense in depth, but application authorization is still needed for resource-level rules.

For PostgreSQL connection pools, set tenant context transaction-locally and ensure every query runs within that transaction. A session-level setting that survives pool reuse can leak context between requests. Test missing context, cross-tenant identifiers, worker jobs, and rollback paths.

**Growth and operations:** Measure tenant-specific load and enforce fair-use limits without letting one tenant exhaust shared capacity. Plan how to move a tenant between shared and dedicated storage, and how migrations, backups, deletion, and restore preserve isolation. Billing and feature flags are product concerns built on reliable tenant identity; they do not replace data-access controls.

### 28. Design an Event-Driven Architecture

**Start by clarifying:** Which services need to react to a change, how quickly, and what ordering or delivery guarantees matter? Do consumers need a durable history for replay, or is a queue of work enough? Event-driven communication can reduce direct coupling, but adds delivery, ordering, and debugging work.

**A basic flow:** A service commits its business change and an event intent durably. A publisher delivers the event to a broker; consumers process it and record progress. Consumers should expect duplicate delivery and make effects idempotent. A transactional outbox is one way to avoid committing a database change while losing its corresponding event.

```text
command → service transaction (state + outbox)
                              ↓
                         publisher → broker → consumer → its state
```

**Keep the patterns distinct:** Event-driven architecture means components communicate through events or messages. Event sourcing stores events as the authoritative record of state and rebuilds state by applying them; it changes how data is modeled and corrected. Command-query responsibility segregation (CQRS) separates write and read models, which can be useful independently of event sourcing. A saga coordinates a multi-service workflow through steps and compensating actions; it is not a database transaction across services.

**Delivery and evolution:** Define event identity, schema compatibility, partition key, ordering scope, retry and dead-letter handling, and replay policy. An acknowledgment should follow durable processing; otherwise a crash can lose work. If a consumer calls another system, a retry may repeat that side effect, so use that system's idempotency mechanism or reconcile outcomes. Monitor consumer lag and poison messages. Add event sourcing or CQRS only when their audit, replay, or read-model benefits justify their storage and operational costs.

### 29. Design a Chaos Engineering Platform

**Start by clarifying:** What resilience assumption should an experiment test, and where can it run safely? Begin with a staging environment or a narrowly scoped, reversible fault. Production experiments require explicit ownership, observability, a defined abort condition, and an agreed operating process.

**A safe experiment loop:** Record the hypothesis and expected user-visible behavior. Check system health and target scope before starting. Apply one bounded fault, observe the agreed signals, stop or roll back when a guardrail is crossed, and verify recovery. Save the configuration and result so the team can repeat the experiment.

```text
hypothesis → pre-check → scoped fault → observe → abort or finish
     ↑                                      ↓
     └──────────── review and follow-up ← recovery check
```

**Safety controls:** Authenticate and authorize experiment operators; restrict targets and fault types; cap duration and blast radius; prevent conflicting experiments; and provide a reliable stop path. Automatic rollback is useful, but the platform must also handle runner crashes and lost control-plane connectivity. Do not assume that a timed command will always restore a network rule after the process dies.

**Evidence and tradeoffs:** Compare the observed behavior with the hypothesis, including alerting, customer impact, and recovery time. Keep experiments small enough that a failed safety mechanism has a limited effect. The platform coordinates faults and records evidence; teams still need understandable failure objectives, service ownership, and follow-up fixes.

### 30. Design a Global Payment Network

**Start by clarifying:** Is this a payment processor, a bank-to-bank network, or a product integrating existing payment providers? Which currencies, payment rails, regions, and participants are in scope? Clearing and settlement rules, compliance duties, and finality depend on that scope; do not assume one universal global flow.

**Model the lifecycle:** Accept a payment request with a durable idempotency key, validate the payer and instructions, run required risk and compliance checks, and submit to the chosen rail or provider. Track explicit states such as accepted, pending, succeeded, failed, and reversed. A timeout after submission is ambiguous: query or reconcile the provider before retrying in a way that could charge twice.

```text
client → payment API → durable payment record → rail/provider
                              ↑                    ↓
                        ledger entries ← status updates/reconciliation
```

**Money and correctness:** Record value as integer minor units or an exact decimal representation with an explicit currency; currencies do not all share the same decimal scale. Use an auditable ledger with balanced debit and credit entries, and treat provider callbacks as duplicate or out-of-order inputs. Keep authorization/holds, capture, refund, reversal, clearing, and settlement distinct. A successful API response does not necessarily mean final settlement.

**Operations and boundaries:** Protect payment data, restrict access, retain an audit trail, and apply the legal and scheme requirements relevant to each operating region. Exchange rates need a source, timestamp, and explicit quote/expiry policy; “real time” is not a sufficient contract. Reconcile internal records against provider or rail reports, monitor stuck states, and define recovery ownership. Scale regional processing only after deciding where each payment record and ledger entry is authoritative and how outages affect acceptance and settlement.

## Summary

Use these prompts to practice explaining requirements, invariants, a minimal design, and the failure and recovery paths. Difficulty labels are only rough guides; a familiar prompt can become difficult when its consistency, privacy, or operational requirements change.

Across the set, distinguish authoritative records from caches and projections, define what a successful operation means, and make retries safe. Choose queues, partitioning, replicas, or specialized patterns only to meet a stated requirement. For every design, identify what can fail, what evidence reveals it, and how the system returns to a correct state.

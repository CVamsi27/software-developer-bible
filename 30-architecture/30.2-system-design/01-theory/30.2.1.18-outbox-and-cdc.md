# Outbox Pattern & Change Data Capture (CDC)

An order API must save an order and tell another service that it exists. Saving to PostgreSQL and publishing to a broker are separate operations: a crash between them can leave an order without its event, or an event for an order that rolled back. The design needs durable publication intent, not just another retry loop:

```text
order + event commit together → relay publishes → crash → republish → consumer dedups by ID.
```

## Definition

A **transactional outbox** stores the business change and its event intent in one database transaction. A **relay** later publishes that intent. **Change data capture (CDC)** reads database changes for downstream processing; log-based CDC follows a database change-log position rather than repeatedly comparing whole tables.

> **Textbook Definition:** The transactional outbox records business changes and publication intent in one local atomic transaction. Change data capture exposes database changes to downstream systems under explicit snapshot, position-retention and delivery contracts.

These choices compose. A polling relay can read an outbox, or a CDC connector can transport its rows. CDC over business tables produces row-change records; an outbox carries an application-defined event such as `order.created`.

## First Principles

One local transaction can commit an order and an event row together. It cannot automatically commit an independent broker send. Moving publication intent inside that transaction removes the first crash window, but publishing and recording "sent" remain separate operations.

If a relay publishes before marking sent, a crash can cause duplicate publication. If it marks sent before publishing, a crash can lose publication. Choose recoverable duplicates, retain stable event identity, and make downstream effects safe under replay. Retention and eventual dependency recovery are necessary for progress; "outbox" is no unconditional delivery promise.

The API can also lose its connection while the database is committing. The transaction may have succeeded even though the caller saw a timeout. Persist a stable command idempotency key with the business change, then resolve a retry against that key instead of creating a second order and event.

## 1. Trace one event across a crash

```text
API transaction: order + event E commit together
relay: read E → broker accepts E → relay crashes before marking sent
recovery: E is still pending → broker accepts E again
consumer: same event identity E → skip its already-committed local effect
```

The consumer must record the identity and its local effect in the same transaction when that effect is not naturally idempotent. A Kafka transaction coordinates Kafka records; it never includes the source database commit or an external provider. Email and payment effects therefore need the provider's own idempotency or reconciliation contract. A probabilistic membership filter cannot authoritatively decide that a required event was already processed.

| Failure boundary | What recovery needs |
| ----------------------------------------------- | ----------------------------------------------------------------------------- |
| Before order/outbox commit | Both changes roll back; no committed event intent |
| Client loses connection during commit | Query by the same idempotency key; the transaction may already have committed |
| After commit, before publication | Retained pending row and a recovering relay |
| After broker acceptance, before dispatched mark | Stable event ID and duplicate-safe consumer |
| Broker unavailable | Bounded retry, backlog/disk monitoring and admission policy |
| Consumer receives older event after newer one | An explicit aggregate version/order contract |

## 2. Store the event contract in the outbox

This PostgreSQL schema is an illustrative single-service outbox. `aggregate_id` names the business object; `aggregate_version` orders that object's accepted transitions. Assign that version in the same authoritative transaction changing the object:

```sql
CREATE TABLE outbox (
  id BIGSERIAL PRIMARY KEY,
  aggregate_id TEXT NOT NULL,
  aggregate_version BIGINT NOT NULL,
  event_ordinal SMALLINT NOT NULL DEFAULT 0 CHECK (event_ordinal >= 0),
  event_type TEXT NOT NULL,
  payload JSONB NOT NULL,
  headers JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  dispatched_at TIMESTAMPTZ,
  UNIQUE (aggregate_id, aggregate_version, event_ordinal)
);
CREATE INDEX outbox_pending_idx
  ON outbox (id) WHERE dispatched_at IS NULL;
```

Use the stable `id` in the published envelope, together with event type, aggregate identity/version, event ordinal, and schema version. The ordinal allows one state transition to emit more than one ordered event; if the domain emits exactly one event per transition, it can be omitted. Assign the aggregate version in the same authoritative transaction changing the object. The sequence ID is an identity, not proof of commit order: one transaction can allocate an earlier ID and commit after another. A timestamp also supplies no unique total order.

## 3. Claim rows with a real lock boundary

The following SQL shows **one claim transaction**, not a complete relay program. Use a dedicated database connection for the whole transaction. `FOR UPDATE` locks hold until that transaction ends; running the select in autocommit releases them before later publication:

```sql
BEGIN;
SELECT id, aggregate_id, aggregate_version, event_ordinal, event_type, payload, headers
FROM outbox
WHERE dispatched_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
-- Publish each selected row with its stable event ID.
-- After the required broker acknowledgment, mark only that row:
UPDATE outbox SET dispatched_at = now() WHERE id = 42;
COMMIT;
```

Here `42` stands for an ID actually selected and acknowledged by the relay; never mark unrelated pending rows. If publication fails, roll back or retain the unacknowledged rows for recovery. A lost response can still mean the broker accepted the event.

Holding database locks while waiting for a broker can increase transaction age and contention. An alternative is a short transactional lease/claim followed by publication outside that transaction. That design needs owner identity, claim expiry, and recovery rules. Both designs can republish after a crash; neither makes the database and broker one atomic system.

`SKIP LOCKED` lets another worker claim different unlocked rows. It never preserves aggregate order: worker A can stall on version 1 while worker B publishes version 2. A shared Kafka partition key preserves broker append order, not the order these competing relays should have published. Serialize dispatch per aggregate, partition relay ownership, or have consumers enforce a durable version/gap policy.

PostgreSQL `LISTEN/NOTIFY` can wake a relay after commit. The notification is a hint to check the outbox, not durable event storage: disconnected listeners need a table scan on recovery. Combine wakeups with bounded periodic polling; no fixed event-rate threshold proves one approach faster.

## 4. Follow CDC from a retained position

For PostgreSQL, a logical-decoding connector uses a replication slot and tracks a log sequence number (LSN), a location in the write-ahead log. A snapshot establishes initial table state; streaming follows changes from the appropriate position. Consumers must distinguish snapshot/read records from new business transitions.

Debezium's PostgreSQL connector supports configured snapshots and streams committed row changes to Kafka. Its records describe creates, updates, deletes, and snapshot reads. An update record may lack the full previous row: PostgreSQL's replica-identity setting and connector configuration control which old values are available. The record's JSON envelope is a separate serialization choice. Snapshot mode, authentication, publication/slot setup, and supported versions must match the deployed connector. Read the [connector documentation](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) before applying configuration:

```text
source rows/log → snapshot + retained log position → connector → broker
                                                        ↓
                                               recorded recovery offset
```

A connector restart may replay records after its last durable offset. Never assume it can spool an outage indefinitely: connector buffers, retained database WAL, broker durability, and committed offsets define recovery. If required WAL is removed or the slot becomes invalid, recovery may need a new snapshot and reconciliation rather than resuming without a gap.

A PostgreSQL slot can retain WAL as a reader falls behind. Monitor retained bytes, lag, and available disk. `max_slot_wal_keep_size` can cap slot retention, but a lagging slot may lose the WAL it needs and become unusable. `wal_keep_size` sets a minimum for standby recovery; it is no cap on logical-slot retention. Source failover also needs a compatible slot/offset/topology recovery plan.

CDC never inherently adds a read replica or creates a separate transaction per business event. A PostgreSQL connector's ordered source stream can split across Kafka topics/partitions; consumers never automatically obtain one globally atomic or ordered view of every affected table. Use transaction metadata and a deliberate reconstruction contract when needed.

## 5. Choose business events or row changes

| Need | Prefer or evaluate | Boundary |
| ---------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------- |
| Publish `order.shipped` with a stable business schema | Outbox event recorded by the state transition | Producer must maintain that contract |
| Maintain a search projection from row updates | CDC over eligible source tables | Projection must handle snapshot, replay and schema evolution |
| Transport outbox rows without an application polling relay | Outbox plus CDC/event routing | Connector and source-log operations remain |
| One event spans several local table changes | Explicit outbox event in the same transaction | Row CDC alone needs reconstruction |
| Minimize exposure of sensitive columns | Deliberately limited event payload and source filtering | Broker, exports and retained copies still need access/retention rules |

The Debezium [Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) maps configured outbox fields to event identity, key, payload, and routing. It never removes the application's dependency on its outbox schema or business-event semantics.

## 6. Decide recovery and evolution up front

- **Keep** event identity through publication and consumer replay. Deduplication retention must cover the permitted replay window; deleting identities too early re-enables old effects.
- **Define** schema compatibility and snapshot behavior before changing columns. A snapshot row representing a completed order is no permission to charge it again.
- **Bound** relay batches, dependency waits, and retries. Monitor oldest pending age as well as row count, publication errors, and disk use.
- **Retain or delete** dispatched rows per retry, audit, privacy, and recovery requirements. Replication never replaces backups or a restore test.
- **Test** commit-before-publication and publish-before-mark crashes, duplicate delivery, reordered aggregate events, and connector recovery after retention loss.
- **Treat** notifications, timestamps, and partition keys as their actual mechanisms; none supplies end-to-end atomicity by itself.

## Summary

An outbox commits publication intent with the business change, then recovers publication independently. CDC transports changes using a snapshot and retained position. They can compose, but both need stable command/event identity, duplicate-safe effects, ordering rules, schema evolution and recoverable retention. Explain the crash boundary before selecting the transport.

# Resilience Patterns Deep-Dive: Hedging, Load Shedding, Request Coalescing, Deadlines

A product request calls two services. One replica stalls, the caller retries, and the queue grows until healthy requests wait behind work whose users have already left. The controls here answer different questions: can a slow attempt be raced safely, should new work be admitted, are concurrent calls identical, and how much time does the request have left?

## Definition

A **resilience pattern** limits how a system behaves when a dependency is slow, failing, or overloaded. It sets a bound on waiting, duplicate work, admitted load, or degraded behavior so one failure is less likely to consume the resources needed by other requests.

> **Textbook Definition:** A resilience pattern is a design mechanism that contains the impact of component failure or overload through bounded execution, controlled admission, isolation, recovery or explicitly limited degradation.

## First Principles

Every request consumes capacity while it waits or runs. If arrival rate exceeds service capacity for long enough, a queue grows; if callers time out while the work continues, the system spends resources on results nobody will use. A useful control therefore names its unit, bound, owner, and failure behavior: attempts per operation, requests in flight, one operation per key, or remaining time per request.

The controls interact. A retry policy can multiply attempts, a hedge deliberately starts another attempt, and coalescing can keep many callers waiting on one slow operation. Give each operation one time budget, cap extra work, and measure both user outcomes and resource cost.

## 1. Race a slow attempt only when paths are independent

These patterns spend different resources. Hedging spends extra attempts to reduce some tail waits. Load shedding declines work to protect admitted requests. Coalescing shares one in-flight operation among equivalent callers. Deadline propagation limits how long downstream work should continue. Adaptive concurrency adjusts an admission limit from observed conditions. Circuit breakers and bulkheads address related problems and are covered in [the resilience-pattern chapter](../../30.3-infra-patterns/02-failure-and-recovery/30.3.2.01-resilience-patterns.md).

**Hedging** starts a second attempt after the first has exceeded a measured delay. It can shorten a tail when the attempts take sufficiently independent paths; it can worsen an incident when both hit the same saturated database, region, or rate limit.

```text
request starts
  ├─ primary attempt starts now
  └─ if no acceptable result by hedge delay, start one alternate attempt
       └─ return the first acceptable result before the caller's deadline
```

Choose the delay from observed latency and set a duplicate-work budget. Cancel losing work when client and dependency support cancellation, but never assume cancellation undoes work already accepted downstream. Prefer reads. For a mutation, retries and hedges require a tested idempotency contract; an idempotency key can prevent duplicate effects but never removes extra load, fees, or every external side effect.

The benefit depends on correlation, not just replica count. If the primary fails before the hedge delay, a separate retry policy may start the alternate immediately; state that behavior and count it in the same attempt budget. If both attempts share a bottleneck, the second request adds load without creating an independent chance of a fast result. Measure latency, accepted-result rate, attempt count, and cancellation under realistic load before enabling hedging. See [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) for the original motivation.

## 2. Refuse work the system cannot serve

**Load shedding** rejects or defers work once the protected resource reaches a bound. A queue limit protects memory and waiting time; a concurrency limit protects active workers or downstream connections. Choose the signal reflecting the actual bottleneck rather than using CPU as a universal proxy:

```typescript
import type { NextFunction, Response } from 'express';

let inFlight = 0;
const limit = 200; // illustrative; derive and load-test the real limit

function tryAdmit(): (() => void) | null {
  if (inFlight >= limit) return null;
  inFlight++;
  let released = false;
  return () => {
    if (released) return;
    released = true;
    inFlight--;
  };
}

// Invoke before starting work. work must settle only after its resources are released.
export async function serveBounded<T>(
  res: Response,
  next: NextFunction,
  work: (signal: AbortSignal) => Promise<T>,
): Promise<void> {
  const release = tryAdmit();
  if (!release) {
    res.status(503).json({ error: 'temporarily overloaded' });
    return;
  }

  const cancellation = new AbortController();
  const onClose = () => {
    if (!res.writableFinished) cancellation.abort();
  };
  res.once('close', onClose);

  try {
    if (res.destroyed) cancellation.abort();
    cancellation.signal.throwIfAborted();
    const result = await work(cancellation.signal);
    if (!res.destroyed) res.json(result);
  } catch (error) {
    if (!res.destroyed) next(error);
  } finally {
    res.off('close', onClose);
    release();
  }
}
```

The operation owns its permit until `work` settles and cleanup has released the protected resources. A prematurely closed response requests cooperative cancellation; it never releases the permit by itself. If a database call ignores that signal, it keeps occupying capacity until it finishes. Releasing on `finish` or `close` would instead count open responses: clients could disconnect repeatedly while their expensive operations continue, bypassing the work limit. Node's [`ServerResponse` lifecycle](https://nodejs.org/api/http.html#event-close_2) explicitly allows `close` before response completion.

Pass the signal to clients that support cancellation and retain the permit through their cleanup. A `Promise.race` timeout that rejects while the protected operation continues breaks `work`'s settlement contract. Record failed and late outcomes even after the client disconnects; an aborted local call still cannot undo a remote effect. If a dependency continues processing after local cancellation, its own admission policy must protect its capacity.

This in-memory counter limits operations represented by `work` in one process. It does not bound request bodies, waiting callers, response buffers, detached tasks, or another process's operations. Bound those separately, keep underlying work deadlines explicit, and coordinate elsewhere only when a shared resource's contract requires it.

Return a status matching the policy: `503 Service Unavailable` for temporary service capacity, or `429 Too Many Requests` when a caller exceeded a rate policy. Add `Retry-After` only when the service can give a useful retry time. A retry hint without bounded client retries and jitter (randomized delay) can recreate the same queue. Priority shedding suits explicit product traffic classes; derive priority from trusted route or identity data, never an arbitrary request header.

## 3. Share one in-flight operation per key

**Request coalescing**, often called singleflight, lets callers with the same key await one in-flight computation. It fits a popular cache key expiring while many requests would otherwise issue the same database read. Each process needs its own in-flight map, so this never deduplicates across a fleet:

```typescript
class Singleflight<T> {
  private readonly inFlight = new Map<string, Promise<T>>();

  do(key: string, load: () => Promise<T>): Promise<T> {
    const existing = this.inFlight.get(key);
    if (existing) return existing;

    const operation = Promise.resolve()
      .then(load)
      .finally(() => this.inFlight.delete(key));
    this.inFlight.set(key, operation);
    return operation;
  }
}
```

The first caller starts the load; later callers with that key receive the same promise. If the leader fails, all waiters see that failure.

One caller disconnecting must never cancel work still needed by the others. Bound operation duration and the number of keys or waiters, and define cancellation ownership.

Include every result-changing input, such as tenant or authorization scope, in the key; otherwise coalescing can return one caller's data to another.

A loader must never recursively await its own key, because it would wait on the operation waiting for it.

Use a distributed lock only when the requirement is cross-process coordination; a lock alone never shares the completed result with waiters.

## 4. Spend the remaining budget downstream

A **deadline** is the latest time a caller will wait. Each downstream call should receive the remaining budget, never a fresh full timeout. Otherwise, three sequential services each given a new 500 ms timeout can continue long after the original caller's 500 ms budget expired:

```text
caller starts with 500 ms
  API spends 120 ms       → profile receives about 380 ms
  profile spends 180 ms   → preferences receives about 200 ms
  deadline expires        → cancel work where the downstream supports it
```

Within one process, use a monotonic clock to measure elapsed time. Across machines, monotonic clock values never compare directly; transmit a remaining timeout or use an absolute deadline with an explicit clock-skew policy. gRPC supports deadline propagation in many language implementations; verify the binding in use. HTTP services need an agreed, validated header or request context for the remaining budget.

Cancellation must reach the actual operation to save downstream work. Timing out a local promise only stops the caller from waiting. Reserve response or cleanup time only when that policy is deliberate and measured; never silently subtract a universal margin.

## 5. Adapt the limit only within bounds

**Adaptive concurrency** changes the in-flight limit from observed signals such as request latency. A controller can raise the limit while the dependency stays responsive and reduce it when queueing appears — but the signal can also change because the request mix changed. Keep minimum and maximum bounds, expose the current limit and controller decisions, and validate behavior with load tests. Envoy's [adaptive concurrency filter](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/adaptive_concurrency_filter.html) is one implementation, not a universal algorithm.

For stable CPU-bound work, a measured fixed worker limit may be easier to operate. Adaptive control is most useful when downstream capacity varies and a static limit requires repeated manual tuning.

## 6. Put the controls around one request

```text
caller deadline
      ↓
admission bound ── reject or admit
      ↓
coalesce equivalent work ── one operation per key in this process
      ↓
downstream calls use remaining time
      └─ hedge only a measured, safe, sufficiently independent attempt
```

This is a reasoning order, not a universal middleware order. A service may place admission control at the edge or near a specific constrained resource. A hedge creates physical attempts even when there is one logical request, so account for both in concurrency, rate, and cost budgets. Retries must fit inside the same deadline and attempt budget. A circuit breaker, bulkhead, or stale fallback can add another control when its own failure contract is explicit.

## Summary

Use one deadline as the outer time budget, admission control to protect a measured bottleneck, and coalescing for equivalent in-flight work. Hedge only when independent, safe attempts can improve the tail; adaptive concurrency may adjust the admission bound when capacity varies. Every control needs an operational owner, a limit, resource-cost metrics and a defined failure behavior.

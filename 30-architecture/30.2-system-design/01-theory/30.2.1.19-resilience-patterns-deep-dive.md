# Resilience Patterns Deep-Dive: Hedging, Load Shedding, Request Coalescing, Deadlines

When a dependency slows down, waiting longer or retrying blindly can make an outage spread. This chapter explains four ways to bound that damage: request hedging, load shedding, request coalescing, and deadline propagation. Adaptive concurrency is an optional way to adjust an admission limit from observed latency.

## Definition

A **resilience pattern** limits the effect of a slow, failed, or overloaded component. Some patterns spend extra work to reduce waiting; others reject or simplify work to protect the service. The right trade depends on what the request is allowed to lose.

> **Textbook Definition:** Resilience patterns constrain how a system handles dependency failure and overload through bounded waiting, controlled retries, isolation, admission control, and explicitly defined degraded behavior.

The deep-dive patterns each give up something different:

| Pattern | What it does | What it gives up |
| ------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------- |
| **Hedging** | starts a duplicate request after a chosen delay; an acceptable response wins | extra compute and downstream load |
| **Load shedding** | rejects work when a bounded queue or concurrency limit is full | requests that might have succeeded if admitted |
| **Request coalescing (singleflight)** | within one process, callers for the same key await one in-flight call | independence — one failure affects its waiters |
| **Circuit breaker** | stops calling a failing dependency for a cooldown | that feature's availability |
| **Bulkhead** | isolates thread/connection pools per dependency | total capacity |
| **Fallback / stale-while-error** | serves cached or degraded results | freshness and exact correctness |

These patterns bound different costs: queue growth, duplicate work, and time spent waiting. They are not interchangeable, and each needs an explicit limit and fallback behavior. Retries need a budget, backoff with jitter, and an operation that is safe to repeat.

---

## First Principles

Circuit breakers and bulkheads are covered in the resilience-pattern chapter; here the focus is how controls compose around a request.

1. Bound each wait and each queue. A timeout limits how long one caller waits; admission control limits how much work the service accepts.
2. Bound retries across the whole request. A retry policy should fit within the caller's deadline and must not multiply without limit at every layer.
3. Compose policies around their contracts. A circuit breaker may count attempts or logical operations depending on the library. There is no universal wrapper order; document what metrics count and test the combined behavior.

## Why it matters

These patterns matter when normal load tests hide slow or overloaded paths:

- If each of seven calls independently has a 1% chance of being slow, the chance of at least one slow call is about 6.8%. Real request latencies may be correlated, so use observed data for a service's actual user journeys.
- An SLO of "p99 < 200ms" means 1% of requests can be slow — but if those 1% cluster around specific shards or specific user actions, the user experience is broken even though the metric is "green".
- An unbounded queue can consume memory and make useful responses arrive after callers have timed out. A bounded queue or concurrency limit makes overload visible and limits wasted work.

## 1. Request Hedging (Tied Requests)

### Definition

When a request exceeds a chosen delay, start a duplicate against another replica. Return the first acceptable response and cancel work that is no longer needed when cancellation is supported. Hedging is a form of speculative execution; it trades extra load for a chance to reduce tail latency.

### Why it works

Hedging helps when the delay is unusually slow for one request and the second attempt is likely to see an independent, faster path. It helps less when replicas share a bottleneck, such as a saturated database, network link, or downstream service. Measure the latency benefit and added work under realistic load before enabling it.

### Math (for the interview)

Choose the delay from measured latency and a duplicate-work budget. If hedging starts after threshold `t`, only requests still unfinished at `t` create a hedge (assuming one hedge per request). That fraction depends on the observed latency distribution; it is not a universal constant. The resulting p99 depends on attempt independence, cancellation behavior, and shared bottlenecks. Do not promise a particular improvement without measuring it.

### Code Example

```typescript
// Pseudocode: a production implementation must propagate cancellation,
// enforce one overall deadline, and define how failed attempts are handled.
start(primary);
after(hedgeDelay, () => {
  if (!primary.hasAcceptableResponse()) start(hedgeOnAnotherReplica);
});
return firstAcceptableResponseBefore(deadline);
```

### Production Reality

- **Select another healthy host where possible.** Another replica may still share the same database, region, or network bottleneck.
- **Treat mutation hedging cautiously.** An idempotency key can prevent duplicate effects, but does not remove extra load, billing, or every external side effect. Prefer reads unless safety and cost are explicit.
- **Be careful with rate limits and billing.** Hedging multiplies outbound traffic by `1 + hedge_probability`. If you have an upstream rate limit, factor this in.
- **Separate attempts from effects.** A duplicate payment attempt can repeat a charge without provider cooperation; even a safely deduplicated attempt consumes resources or request quota.

### When to use
- **Read-heavy paths with measured tail latency** — when another replica can serve independently and the extra work is affordable.

### When NOT to use
- **Mutations without a tested idempotency contract** — duplicate effects can be worse than a slow response.
- **Very expensive operations** — doubling ML inference or DB join cost is too much.
- **Upstream with hard rate limits** — your hedge breaches them.

## 2. Load Shedding (Drop at the Door)

### Definition

When a service reaches a configured concurrency or queue bound, it can reject or defer new work instead of allowing an unbounded queue. Use `503 Service Unavailable` for temporary service capacity problems. Use `429 Too Many Requests` when a client or caller exceeded a rate policy. A `Retry-After` header is useful when the service can give a meaningful retry time.

### Why it works

In a queue, waiting time rises as arrivals approach service capacity. The exact curve depends on arrival and service-time distributions, number of workers, and queue policy. A bounded queue makes overload explicit instead of letting waiting work consume resources after its caller has given up.

Shedding can break that cycle by keeping admitted work within a bound. Rejected requests should follow an explicit client retry policy; immediate retries can recreate the overload.

### Two flavors

**1. Admission control:**
- Compute `current_load / capacity` (CPU, queue depth, in-flight count).
- If the limit is reached, reject with the status that matches the policy; provide `Retry-After` only when a retry time is meaningful.
- Decision is **synchronous, fast, in front of the work**.

**2. Probabilistic admission:**
- Don't wait for overload. Start dropping probabilistically as load grows.
- The drop probability is configured from observed queueing or service signals; there are no generally correct load percentages.
- This keeps average latency low by avoiding the queue cliff.

### Code Example (local admission with an illustrative threshold)

```typescript
// Teaching example: positive integer capacity, one event loop, and exactly
// one release for each admitted request. 70% is illustrative, not tuned.
class AdmissionController {
  private inflight = 0;
  private capacity: number;

  constructor(capacity: number) {
    this.capacity = capacity;
  }

  /** Returns true if request can proceed, false if it should be shed. */
  tryAdmit(): boolean {
    if (this.inflight < this.capacity * 0.7) {
      this.inflight++;
      return true;
    }
    // Above 70% — start shedding probabilistically.
    // At 100% capacity, shed with probability proportional to (load - 0.7) / 0.3.
    const overload = (this.inflight - this.capacity * 0.7) / (this.capacity * 0.3);
    if (Math.random() < overload) {
      return false; // shed
    }
    this.inflight++;
    return true;
  }

  release(): void {
    this.inflight--;
  }
}

// Middleware:
app.use((req, res, next) => {
  if (!admission.tryAdmit()) {
    res.status(503).json({ error: "overloaded" });
    return;
  }
  // Both events may fire; release the slot exactly once.
  let released = false;
  const releaseOnce = () => {
    if (released) return;
    released = true;
    admission.release();
  };
  res.once("finish", releaseOnce);
  res.once("close", releaseOnce);
  next();
});
```

### Production Reality

- **Make retry behavior explicit.** A retry hint helps only if its value is meaningful and clients respect it; pair it with bounded retries and jitter.
- **Pick a signal that matches the bottleneck.** In-flight count and queue depth are direct admission signals. CPU, memory, or dependency latency can also matter, depending on the service.
- **Differentiate by request cost.** Don't shed a cheap `GET /health` the same way you shed an expensive `POST /report`. Use **cost-aware admission control** — heavy requests count as 5 in-flight, light ones as 1.
- **Shed in priority order.** Sheds `bulk` traffic before `interactive` traffic. `feature X` before `core product`. Derive priority from an authorized route or principal; do not trust an arbitrary caller header to bypass capacity policy.
- **Make it observable.** Every shed should emit a metric: `sheds_total{reason,route}`. Otherwise you'll never know if you're over-shedding.

### When to use
- **Bound queues and concurrency when overload could exhaust resources.** Choose rejection, queueing, or degradation based on the endpoint contract.
- **DDoS protection** — same mechanism, different threshold.

### When NOT to use
- **Hard real-time systems** that can't tolerate any dropped request (medical, aviation). Even then, you'd shed, not crash.

## 3. Request Coalescing (Singleflight)

### Definition

Within one process, when concurrent requests for the **same key** arrive, one call can run while the others await its result. This is often called singleflight. Separate processes do not share an in-memory flight map; cross-process coordination adds a different distributed-systems problem.

### Why it matters: the thundering herd / cache stampede

Classic scenario: a popular key expires from cache and concurrent requests all miss, then hit the database at once. The resulting burst can exhaust the connection pool or slow unrelated work.

```text
t=0 key "user:42" expires from cache
t=0+ concurrent requests all miss
t=0+ many identical SELECTs reach the database
        → the connection pool fills
        → other database work waits too
```

With coalescing in one process, one request hits the DB and the others await it. The requests still consume memory and remain subject to their own deadlines.

### Code Example

```typescript
// Node.js: use p-memoize or a singleflight library
import pMemoize from "p-memoize";

const fetchUser = async (id: string) => {
  // simulate slow DB
  await new Promise((r) => setTimeout(r, 100));
  return { id, name: "alice" };
};

const memoizedFetchUser = pMemoize(fetchUser, {
  // Concurrent calls for the same key can share in-flight work.
  cache: false, // Share concurrent calls; do not retain settled results.
});

await Promise.all(
  Array.from({ length: 1000 }, () => memoizedFetchUser("42")),
);
// → one in-flight DB call for this key in this process.
```

For a focused local in-flight map:

```typescript
// TypeScript port of Go's singleflight pattern
class Singleflight<T> {
  private inflight = new Map<string, Promise<T>>();

  do(key: string, fn: () => Promise<T>): Promise<T> {
    const existing = this.inflight.get(key);
    if (existing) return existing;

    const promise = fn().finally(() => this.inflight.delete(key));
    this.inflight.set(key, promise);
    return promise;
  }
}

const sf = new Singleflight<User>();

async function getUser(id: string) {
  return sf.do(`user:${id}`, async () => {
    return db.users.findUnique({ where: { id } });
  });
}
```

### Production Reality

- **Cancellation ownership**: one caller disconnecting should not automatically cancel work still needed by other waiters. Use a shared operation context or reference-count waiters; bound the operation with a service deadline.
- **Error propagation**: if the leader fails, all followers see the same error. That's usually correct. To "retry individually", use a different pattern.
- **Do not add a distributed lock by default.** A per-process map is enough when duplicate calls only need collapsing inside that process. Cross-process coalescing needs explicit coordination and failure handling.
- **Bound in-flight work and clean up only after it settles.** Evicting a live key can start a second copy and defeat coalescing.

### When to use
- **Cache miss / stampede** — the textbook case.
- **Idempotent lookups** with high duplication — e.g. fetching the same config / feature flag / geo-IP lookup.
- **Identical read or refresh work** — only when callers truly request the same computation and can share its result.

### When NOT to use
- **Per-request keys that don't repeat** — no coalescing to do, just overhead.
- **Slow operations that block too many followers** — the first request might take 10s; 999 followers wait 10s. Bound the wait with a timeout.

## 4. Deadline Propagation (Stop the Cascade)

### Definition

When a request has a deadline, downstream work should use the remaining time rather than restarting the full timeout at each hop. A propagated absolute deadline or remaining duration carries the same budget; it is not a fixed fraction of that budget.

### Why it matters: the timeout cascade

The classic pathology:

```text
t=0 API receives request with a 500 ms deadline
t=120 API calls profile service with a fresh 500 ms timeout
t=300 profile calls preferences service with a fresh 500 ms timeout
t=500 caller gives up, but downstream work may continue until t=800

The caller stops at 500 ms, while a downstream timeout can extend to
800 ms. Cancellation must reach the remote operation to stop its work.
```

With the original deadline propagated:

```text
t=0 API sets deadline = 500 ms from now
t=120 profile receives the remaining budget (about 380 ms)
t=300 preferences receives the remaining budget (about 200 ms)
t=500 all work should stop unless it has a separate, justified lifecycle
```

### Code Example (gRPC has first-class support)

```typescript
// gRPC client — pass the deadline as a Date or duration.
const client = new UserServiceClient(target);
const deadline = new Date(Date.now() + parentRemainingMs);
const user = await client.getUser({ id }, { deadline });
```

```typescript
// Generic HTTP fetch — use AbortController with a timeout.
async function fetchWithDeadline(url: string, remainingMs: number) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), remainingMs);
  try {
    const res = await fetch(url, { signal: controller.signal });
    return await res.json();
  } finally {
    clearTimeout(timer);
  }
}

// At the call site, pass the budget, not the full timeout.
const childBudget = parentDeadline - Date.now() - 20; // illustrative response reserve
if (!(childBudget > 0 && Number.isFinite(childBudget))) {
  throw new Error("deadline exhausted before child request");
}
const result = await fetchWithDeadline(url, childBudget);
```

### Production Reality

- **Pass it as a value, not a flag.** A boolean "is_critical" is not a deadline. Use `deadline: Date` (gRPC) or `remaining_ms: number` (HTTP).
- **Propagate the caller's deadline, not a new full timeout.** If a downstream needs cleanup or response time, reserve it deliberately and measure the trade-off.
- **Make it observable.** Every span should record its remaining-budget-on-entry. You'll see a histogram of "how much time did this hop have to work with" — a powerful debugging tool.
- **Stop work after cancellation where possible.** A client timing out does not necessarily stop server-side work.
- **gRPC supports deadline propagation in many language implementations.** Check the behavior of the language API in use. HTTP services need an agreed, validated way to carry the deadline or remaining budget.

### When to use
- **Request/response chains with a bounded caller wait** — propagate that budget through the work. Background jobs usually need a separate job deadline or execution policy.

### When NOT to use
- **Background jobs / batch / cron** — they have a wall-clock SLA, not a request deadline.
- **One-call-only systems** — no propagation needed.

## 5. Adaptive Concurrency Limits (Bonus)

### Definition

An in-flight request limit that adjusts from observed signals such as latency. Implementations use different algorithms and safeguards; for example, Envoy documents a gradient controller based on measured round-trip time.

### Why it matters

A static limit (e.g. "max 200 in-flight per process") is wrong when:
- The downstream is fast → 200 is too low, you're leaving capacity on the table.
- The downstream is slow → 200 is too high, you're queuing and dying.
- A new release made the service slower → 200 is now too high.

An adaptive limit:
1. Measures `rtt_min` (the fastest observed RTT — your best-case latency).
2. Computes `rtt_current` (smoothed recent RTT).
3. If `rtt_current` rises above the expected baseline, that can indicate queueing. The controller may **reduce** the limit.
4. If `rtt_current ≈ rtt_min`, the system has headroom. **Increase** the limit.
5. Apply the implementation's controller, bounds, and sampling rules.

A lower RTT can reflect a cheaper request mix rather than spare capacity. Controller sampling must distinguish that change from reduced queueing. Adaptive limits can reduce manual tuning, but they still need safe minimums, observability, and load tests. They do not automatically find a globally optimal limit.

### When to use
- **Services that talk to many heterogenous downstreams** (e.g. an API gateway, a BFF).
- **When static limits require constant manual tuning.**

### When NOT to use
- **Pure CPU-bound work** when a measured static worker limit is simpler and effective.
- **When you already have a load balancer doing this** (Envoy's `adaptive_concurrency` filter).

## Comparison: When to Use Which

| Pattern | Solves | Cost | Latency impact |
| ------------------------ | ------------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------ |
| **Hedging** | Some independent slow attempts | Duplicate work depends on delay and latency distribution | Outcome depends on attempt independence and cancellation |
| **Load shedding** | Excess work beyond a bound | Rejected or deferred work | Protects admitted work when the limit matches the bottleneck |
| **Coalescing** | Duplicate in-flight work for one key | Waiters share the leader's duration | Can reduce duplicate load; wait time remains |
| **Deadline propagation** | Timeout cascade / wasted work | Deadline handling and cancellation | Bounds how long downstream work should continue |
| **Adaptive concurrency** | Static limit tuning | Controller complexity and metric collection | Depends on the signal and controller |

They can be combined when each solves a measured problem:

- The service bounds admitted work.
- Identical reads may share one in-flight result within a process.
- Downstream calls use the caller's remaining deadline; hedging is considered only for an independent, safe attempt.

## Common Mistakes

- **Assuming hedging always improves p99** — correlated slowdowns and duplicate load can make latency worse.
- **Hedging to the same failing path** — another host may still share the bottleneck; understand the dependency topology.
- **Returning a retry hint clients cannot honor** — retry timing must be compatible with the status and caller policy.
- **Shedding from a signal unrelated to the bottleneck** — choose and validate the admission signal against the constrained resource.
- **Coalescing with no bound on waiters or duration** — the shared call can retain many callers. Bound it with admission control and deadlines.
- **Setting deadline = full timeout on every call** — the cascade pathology. Always pass remaining budget.
- **Assuming cancellation stops remote work** — verify cancellation reaches the operation and observe work that outlives its caller.
- **Testing only the happy path** — test slow and failed dependencies, shared bottlenecks, cancellation, and overload with limits appropriate to the service.
- **Stacking patterns without checking their interaction** — retries, shedding, and breakers can change each other's behavior. Test the combined policy and make attempt counts observable.
- **Treating p99 as the only metric** — choose percentiles, timeout counts, and queue metrics that reflect the service contract; avoid optimizing a percentile without checking the accepted-request rate.

---

## Best Practices

1. **Set a duplicate-work budget before hedging.** Tune the delay from measured distributions, cap attempts, and watch added load.
2. **Define overload behavior.** Bound queues and in-flight work; choose rejection, deferral, or degradation based on the API contract.
3. **Keep singleflight local unless distributed coordination is justified.** Share only equivalent work and bound callers and duration.
4. **Carry one deadline through the request chain.** Verify the implementation stops work when the deadline expires.
5. **Measure outcomes and costs.** Track attempt count, rejected work, queue depth, coalesced waiters, deadline exhaustion, and work continuing after cancellation.
6. **Test the combinations.** Include slow dependencies, shared bottlenecks, client disconnects, and retry behavior.

## Performance Considerations

| Pattern | Throughput cost | Latency cost | Memory cost | Operational cost |
| -------------------- | ------------------------------------------------------- | ------------------------------------------------------- | -------------------------- | ------------------------------------- |
| Hedging | Depends on fraction of calls that trigger a hedge | May reduce some tails; can add load | Attempt state | Per-endpoint measurement and budgets |
| Load shedding | Rejects work beyond the configured limit | Fast failure for rejected calls | Queue or concurrency state | Limit and status-code policy |
| Coalescing | Reduces duplicate in-flight calls for the same key | Waiters share leader duration | Per-key in-flight state | Cancellation and waiter limits |
| Deadline propagation | Deadline metadata and cancellation checks | Can stop work that would outlive the caller | Request context | Propagation and cancellation coverage |
| Adaptive concurrency | Controller-specific sampling | Depends on controller behavior | Controller state | Bounds, tuning, and validation |

---

## Summary

- **Hedging** starts another attempt after a delay; its benefit depends on independent paths and costs extra work.
- **Load shedding** bounds admitted work and makes overload explicit.
- **Coalescing** lets concurrent callers in one process share identical in-flight work.
- **Deadline propagation** carries one caller budget through downstream calls.
- **Adaptive concurrency** adjusts a concurrency limit from observed signals; it still needs bounds and testing.
- In a design discussion, state the trigger, limit, cost, and failure behavior.

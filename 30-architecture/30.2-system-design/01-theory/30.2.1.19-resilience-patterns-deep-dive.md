# Resilience Patterns Deep-Dive: Hedging, Load Shedding, Request Coalescing, Deadlines

A product request calls two services. One replica stalls, the caller retries, and the queue grows until healthy requests wait behind work whose users have already left. The controls in this chapter answer different questions: can a slow attempt be raced safely, should new work be admitted, are concurrent calls identical, and how much time does the request have left?

## Definition

A **resilience pattern** limits how a system behaves when a dependency is slow, failing or overloaded. It sets a bound on waiting, duplicate work, admitted load or degraded behavior so that one failure is less likely to consume the resources needed by other requests.

> **Textbook Definition:** A resilience pattern is a design mechanism that contains the impact of component failure or overload through bounded execution, controlled admission, isolation, recovery or explicitly limited degradation.

These patterns spend different resources. Hedging spends extra attempts to reduce some tail waits. Load shedding declines work to protect admitted requests. Coalescing shares one in-flight operation among equivalent callers. Deadline propagation limits how long downstream work should continue. Adaptive concurrency adjusts an admission limit from observed conditions. Circuit breakers and bulkheads address related problems and are covered in [the resilience-pattern chapter](../../30.3-infra-patterns/02-failure-and-recovery/30.3.2.01-resilience-patterns.md).

## First Principles

Every request consumes capacity while it waits or runs. If arrival rate exceeds service capacity for long enough, a queue grows; if callers time out while the work continues, the system spends resources on results nobody will use. A useful control therefore names its unit, bound, owner and failure behavior: attempts per operation, requests in flight, one operation per key, or remaining time per request.

The controls interact. A retry policy can multiply attempts, a hedge deliberately starts another attempt, and coalescing can keep many callers waiting on one slow operation. Give each operation one time budget, cap extra work, and measure both user outcomes and resource cost.

## Is one replica slow, or is the dependency slow?

**Hedging** starts a second attempt after the first has exceeded a measured delay. It can shorten a tail when the attempts take sufficiently independent paths; it can worsen an incident when both hit the same saturated database, region or rate limit.

```text
request starts
  ├─ primary attempt starts now
  └─ if no acceptable result by hedge delay, start one alternate attempt
       └─ return the first acceptable result before the caller's deadline
```

Choose the delay from observed latency and set a duplicate-work budget. Cancel losing work when the client and dependency support cancellation, but do not assume cancellation undoes work already accepted downstream. Prefer reads. For a mutation, retries and hedges require a tested idempotency contract; an idempotency key can prevent duplicate effects but does not remove extra load, fees or every external side effect.

The benefit depends on correlation, not just the number of replicas. If the primary fails before the hedge delay, a separate retry policy may start the alternate immediately; state that behavior and count it in the same attempt budget. If both attempts share a bottleneck, the second request adds load without creating an independent chance of a fast result. Measure latency, accepted-result rate, attempt count and cancellation under realistic load before enabling hedging. See [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) for the original motivation.

## Should this request enter the queue?

**Load shedding** rejects or defers work once the resource being protected reaches a bound. A queue limit protects memory and waiting time; a concurrency limit protects active workers or downstream connections. Choose the signal that reflects the actual bottleneck rather than using CPU as a universal proxy.

```typescript
let inFlight = 0;
const limit = 200; // illustrative; derive and load-test the real limit

function tryAdmit(): (() => void) | null {
  if (inFlight >= limit) return null;
  inFlight++;
  let released = false;
  return () => {
    if (released) return;
    released = true;
    inFlight--;
  };
}

// Express-shaped example: finish and close can both fire, so release is idempotent.
const release = tryAdmit();
if (!release) {
  res.status(503).json({ error: 'temporarily overloaded' });
  return;
}
res.once('finish', release);
res.once('close', release);
next();
```

The request handler should acquire before starting expensive work and release exactly once on completion or disconnect. In a multi-process service, this in-memory counter limits only one process; coordinate elsewhere only if the protected resource is shared and the extra coordination is justified.

Return a status that matches the policy: `503 Service Unavailable` for temporary service capacity, or `429 Too Many Requests` when a caller exceeded a rate policy. Add `Retry-After` only when the service can give a useful retry time. A retry hint without bounded client retries and jitter can recreate the same queue. Priority shedding is useful when the product has explicit traffic classes; derive priority from trusted route or identity data, not an arbitrary request header.

## Are concurrent callers asking for the same work?

**Request coalescing**, often called singleflight, lets callers with the same key await one in-flight computation. It is useful when a popular cache key expires and many requests would otherwise issue the same database read. Each process needs its own in-flight map, so this does not deduplicate across a fleet.

```typescript
class Singleflight<T> {
  private readonly inFlight = new Map<string, Promise<T>>();

  do(key: string, load: () => Promise<T>): Promise<T> {
    const existing = this.inFlight.get(key);
    if (existing) return existing;

    const operation = Promise.resolve()
      .then(load)
      .finally(() => this.inFlight.delete(key));
    this.inFlight.set(key, operation);
    return operation;
  }
}
```

The first caller starts the load; later callers with that key receive the same promise. If the leader fails, all waiters see that failure. One caller disconnecting should not cancel work still needed by the others. Bound operation duration and the number of keys or waiters, and define cancellation ownership. Include every result-changing input, such as tenant or authorization scope, in the key; otherwise coalescing can return one caller's data to another. A loader must not recursively await its own key, because it would wait on the operation that is waiting for it. Use a distributed lock only when the requirement is cross-process coordination; a lock alone does not share the completed result with waiters.

## How much time does the request have left?

A **deadline** is the latest time a caller is willing to wait. Each downstream call should receive the remaining budget, not a fresh full timeout. Otherwise, three sequential services each given a new 500 ms timeout can continue long after the original caller's 500 ms budget has expired.

```text
caller starts with 500 ms
  API spends 120 ms       → profile receives about 380 ms
  profile spends 180 ms   → preferences receives about 200 ms
  deadline expires        → cancel work where the downstream supports it
```

Within one process, use a monotonic clock to measure elapsed time. Across machines, monotonic clock values cannot be compared directly; transmit a remaining timeout or use an absolute deadline with an explicit clock-skew policy. gRPC supports deadline propagation in many language implementations; verify the behavior of the binding in use. HTTP services need an agreed, validated header or request context for the remaining budget.

Cancellation must reach the actual operation to save downstream work. Timing out a local promise only stops the caller from waiting. Reserve response or cleanup time only when that policy is deliberate and measured; do not silently subtract a universal margin.

## What if the safe limit changes with the workload?

**Adaptive concurrency** changes the in-flight limit using observed signals such as request latency. A controller can raise the limit while the dependency remains responsive and reduce it when queueing appears, but the signal can also change because the request mix changed. Keep minimum and maximum bounds, expose the current limit and controller decisions, and validate behavior with load tests. Envoy's [adaptive concurrency filter](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/adaptive_concurrency_filter.html) is one implementation, not a universal algorithm.

For stable CPU-bound work, a measured fixed worker limit may be easier to operate. Adaptive control is most useful when downstream capacity varies and a static limit requires repeated manual tuning.

## Put the controls around one request

```text
caller deadline
      ↓
admission bound ── reject or admit
      ↓
coalesce equivalent work ── one operation per key in this process
      ↓
downstream calls use remaining time
      └─ hedge only a measured, safe, sufficiently independent attempt
```

This is a reasoning order, not a universal middleware order. A service may place admission control at the edge or near a specific constrained resource. A hedge creates physical attempts even when there is one logical request, so account for both in concurrency, rate and cost budgets. Retries must fit inside the same deadline and attempt budget. A circuit breaker, bulkhead or stale fallback can add another control when its own failure contract is explicit.

| If the observed problem is… | Consider… | State the cost or limit |
| ------------------------------------------------- | -------------------- | ------------------------------------------------------------ |
| An occasional slow, independent read attempt | Hedging | Extra attempts and downstream load |
| Queue or active work exceeds safe capacity | Load shedding | Which callers or work classes can be rejected |
| Many simultaneous requests repeat one computation | Coalescing | Shared failure and local process scope |
| Downstream work outlives its caller | Deadline propagation | Remaining-time transport and cancellation support |
| Safe capacity varies with dependency latency | Adaptive concurrency | Controller bounds, signal and behavior under changed traffic |

## Summary

Choose a control from the failure you measured. Hedging trades extra work for a chance to avoid an independent slow tail; shedding bounds admitted load; coalescing shares identical in-flight work within one process; deadlines carry one time budget through the call chain; adaptive concurrency adjusts a limit but still needs bounds and evidence. For each, explain the trigger, owner, limit, resource cost and behavior when the control itself cannot help.

# Multi-Region Deployment

> **Your service is live in `us-east-1`. It's 3 AM. AWS is having a bad day. What do your users in Berlin see?** If the answer is "a 503", you're single-region. The senior-level follow-up question is: **how do you design for global users, with regional failures, with state?** This file covers the patterns: active-passive, active-active, geo-routing, cross-region replication, multi-region writes, conflict resolution, data residency, and disaster recovery. Every global product — Netflix, Stripe, GitHub, Notion, Cloudflare, WhatsApp — runs some variant of these.

## TL;DR

- **Three deployment topologies** — single-region, **active-passive** (one writes, others standby), **active-active** (every region writes, every region serves).
- **Routing layers** — **GeoDNS**, **Anycast**, **HTTP load balancers** (ALB/GLB), **CDN edge**. Each makes a different trade-off.
- **Replication modes** — **synchronous** (RPO=0, latency cost) vs **asynchronous** (RPO>0, fast) vs **quorum-based** (Cassandra-style, tunable).
- **Multi-region writes** are hard. Conflict resolution: **last-writer-wins (LWW)**, **vector clocks**, **CRDTs**, or **avoid altogether by sharding users to their home region**.
- **Data residency / GDPR** — EU users' data must stay in EU. Plan for **regional data sovereignty** early.
- **Disaster recovery (DR)** — RPO (how much data you can lose) and RTO (how long you can be down) define the design. Pick the numbers first, then the architecture.
- **In interviews: pick a topology, name the RPO/RTO, name the cost, name the failure mode.**

---

## Why it matters

Single-region is fine for most startups. The moment you have:
- Users in multiple continents (latency > 200ms kills interactive UX)
- Regulatory requirements (GDPR, data sovereignty, financial data residency)
- Customers asking "what's your DR story?"
- An SLA above 99.9% (single-region AWS = 99.9% baseline)

…you need to think multi-region. The bad news: every cross-region decision has a sharp trade-off. **There is no "right" multi-region architecture; there are 5 common ones and you must pick.**

## 1. Deployment Topologies

### Single-Region (no DR)

```text
        users
         │
    GeoDNS / LB
         │
    ┌────┴────┐
    │ us-east-1 │
    │ (active) │
    └─────────────┘
```

- **RPO** = whatever you lose when the region dies (everything in volatile state).
- **RTO** = the time to bring up a new region from backups (hours).
- **Use when**: startup with users in one continent, no SLA, no DR requirement.

### Active-Passive (hot standby)

```text
   EU users US users
     │ │
   GeoDNS GeoDNS
     │ │
     ▼ ▼
  eu-west-1 us-east-1
  (active) (active)
     │
     │ async replication
     ▼
  us-west-2
  (passive / warm standby)
```

- **Reads** served from the active region. **Writes** go to the active region's primary, replicate async to the passive.
- **Failover** is manual or DNS-automated. Active goes down, passive is promoted.
- **RPO** = seconds to minutes (depends on replication lag).
- **RTO** = minutes to hours (DNS TTL + promotion).
- **Use when**: most production systems with global users but not real-time state-sharing. Stripe's primary is multi-region active-active, but their payments write path is single-region per currency.

### Active-Active (multi-region writes)

```text
   EU users US users APAC users
     │ │ │
   GeoDNS GeoDNS GeoDNS
     │ │ │
     ▼ ▼ ▼
  eu-west-1 us-east-1 ap-southeast-1
  (active) (active) (active)
     │ ↘ async/quorum replication ↙ │
     ▼ ▼ ▼ ▼ ▼ ▼ ▼
   every region sees writes from every other region
```

- **Reads and writes** served from the user's home region (or the closest).
- **Writes** propagate to other regions asynchronously or via a quorum.
- **Multi-region writes = conflict potential.** See section 4.
- **RPO** = ~0 if quorum, seconds if async.
- **RTO** = seconds (any region down, traffic shifts to others; no manual failover).
- **Use when**: global product, real-time collaboration (Figma, Notion), social (Twitter, Instagram), or hard SLA targets.

### Hybrid (regional active-active + global read-only)

The most common production setup. Most teams claim "active-active" but actually run:
- **Per-region primary for writes** (e.g. each user has a home region; writes go there)
- **Cross-region reads** served from local replicas
- **Replication** is async, conflict-free because writes are sharded by user/region

This is what most "active-active" SaaS products actually run. It has the **latency of active-active without the conflict-resolution problem**.

## 2. Routing: How Traffic Gets to a Region

| Mechanism                             | Resolution                        | Latency to redirect | Best for                 |
| -----------                             | -----------                         | --------------------- | ----------                 |
| **GeoDNS** (Route 53, Cloudflare)     | Country / continent → IP          | DNS TTL (60-300s)   | Most web traffic         |
| **Anycast** (BGP)                     | Same IP, nearest PoP wins         | None — automatic    | UDP, DDoS-resistant, CDN |
| **HTTP load balancer** (ALB, GLB)     | `Host` header, path, geo headers  | None (per request)  | Inside AWS/GCP           |
| **CDN edge** (Cloudflare, CloudFront) | Geo + cache                       | None for cached     | Static + dynamic edge    |
| **Client-side SDK**                   | User's locale → hard-coded region | None                | Mobile apps, B2B         |

**Production pattern: layered.**
1. **GeoDNS** maps `example.com` → region IP based on client country.
2. **Anycast / CDN edge** fronts the regional load balancer for DDoS + TLS termination.
3. **HTTP LB** routes inside the region to the right service.

**The DNS-TTL problem:** if a region dies, users keep hitting the dead IP for up to TTL seconds. Mitigations:
- **Low TTL (60s)** for production — 60s of "wrong" traffic, but recovers fast.
- **Health-check based DNS** — Route 53 health checks the region, removes from DNS on failure. Recovery: 30-60s.
- **Anycast** — automatic failover in BGP, no TTL issue.
- **CDN with origin failover** — Cloudflare can detect origin down and route elsewhere.

## 3. Cross-Region Replication

### Synchronous

- **Writes** go to the local region's primary, which **synchronously** writes to at least one other region before acking.
- **RPO = 0** — if a region dies, no data lost.
- **Latency cost** = RTT between regions (~70-100ms cross-continent). Every write pays this.
- **Used by**: CockroachDB, Google Spanner, FoundationDB.
- **Use when**: you cannot lose data and your writes can tolerate 100ms latency.

### Asynchronous

- **Writes** go to local region's primary, ack immediately, replicate to other regions in the background.
- **RPO = N seconds** (whatever your replication lag is). 1-5s typical.
- **Latency cost** = 0 (single-region write latency).
- **Used by**: every "active-active" SaaS, DynamoDB Global Tables (with caveats), most Postgres setups.
- **Use when**: most production workloads. Accept a small window of data loss.

### Quorum-based

- **Writes** go to `W` of `N` replicas before acking.
- **Reads** go to `R` of `N` replicas.
- **Consistency** is configurable: `R + W > N` = strong reads; otherwise eventual.
- **Used by**: Cassandra, DynamoDB (tunable), Cosmos DB.
- **Use when**: you want configurable consistency per query.

### Replication topology

```text
         ┌─────── All-to-all (full mesh) ───────┐
         │ │
       R1 ←──→ R2 ←──→ R3 │
       │ ↑ │ │
       └──────┴────────┘ │
                                               │
         ┌─── Hub-and-spoke (primary + replicas) ───┐
         │ │
              R1 (primary) │
              ↙ ↓ ↘ │
           R2 R3 R4 │
```

- **All-to-all**: any region can replicate to any other. Simple, but N² connections. Used when N=3-5 regions.
- **Hub-and-spoke**: one region is the hub. Avoids N², but the hub is a SPOF. Used for "primary + read replicas" topology.
- **Cascading / chain**: each region replicates to the next. Used for read-replica chains in legacy setups.

## 4. Multi-Region Writes: The Hard Part

When two regions write the **same row** at the **same time**, you have a conflict. Single-region writes are conflict-free. Multi-region writes are not.

### Strategies

**1. Avoid conflicts by sharding**
- **Hash user_id → home region.** All writes for user X go to region Y. No conflict possible.
- **Used by**: most production "active-active" systems in practice. Instagram, WhatsApp, etc.
- **Cost**: uneven load. Some regions hotter than others.

**2. Last-Writer-Wins (LWW)**
- Each write has a timestamp. Latest timestamp wins.
- **Simple, but lossy**: if two regions write at the same ms, one is silently dropped.
- **Used by**: DynamoDB Global Tables (with vector clocks as a refinement), Cassandra default.

**3. Vector clocks**
- Each version carries the causal history. On conflict, you can detect "true concurrent" writes.
- **More honest than LWW** — you know there was a conflict, you can surface it.
- **Rare in production** — too complex for most use cases.

**4. CRDTs (Conflict-free Replicated Data Types)**
- Data structures designed so concurrent edits always converge to the same state.
- **Examples**: counters (sum of all region counts), sets (union), text (Yjs, Automerge).
- **Used by**: Figma (multiplayer), Notion, Linear, Redis Enterprise, collaborative editing.
- **Cost**: limited data model; some operations are not CRDT-friendly (e.g. "if X then Y").

**5. Operational Transform (OT)**
- The CRDT ancestor. Used by Google Docs.
- **Cost**: complex; needs a central ordering authority in practice.

### Decision framework

| Use case                       | Strategy                                      |
| ----------                       | ----------                                      |
| User profile, account settings | LWW (acceptable to drop a stale write)        |
| Counters (likes, views)        | CRDT counter (additive, converges)            |
| Collaborative document         | OT or CRDT (Yjs)                              |
| Money / ledger                 | **Single-region writes** (no conflicts, ever) |
| Inventory                      | **Single-region writes** with reservations    |
| Cart                           | Per-user home region (sharded)                |
| Search index                   | Append-only, last writer wins per doc         |

**The cardinal rule**: if it touches money, **don't multi-region write it**. Use a single-region ledger, replicated synchronously to a second region for DR. Money is too important to be eventually consistent.

## 5. Data Residency & Sovereignty

GDPR (EU), LGPD (Brazil), PIPL (China), Russia's data laws, India's DPDP Act: all require **certain data to stay within national borders**.

**Patterns:**
- **Regional data partitioning** — EU user data is in `eu-west-1`, US user data in `us-east-1`. Never replicated across borders.
- **Sovereign cloud** — AWS GovCloud, Azure Germany, OVH EU. Physical infrastructure in-region.
- **Tokenization** — replace PII with a non-reversible token before cross-border replication.
- **Customer-managed keys (CMK)** — encrypt with region-specific KMS keys, never export.

**Architectural impact:**
- EU users may have **higher latency to global services** (since their data can't leave EU).
- **Auth tokens may need to be region-specific** (no global session that touches EU PII).
- **Logs, analytics, and metrics** also need residency treatment. Many companies route EU logs to an EU-only observability stack.

**In interviews**: if the question says "EU users" or "GDPR", volunteer the data-residency angle. That's a senior signal.

## 6. Disaster Recovery (RPO / RTO)

| Tier                             | RPO           | RTO             | Cost  | Architecture                                         |
| ------                             | -----           | -----             | ------  | --------------                                         |
| 0 — No DR                        | Hours-to-days | Days            | $     | Backup only                                          |
| 1 — Backup & restore             | Hours         | Hours           | $     | Cross-region backups, restore on failure             |
| 2 — Pilot light                  | Minutes       | 10s of minutes  | $$    | Core services pre-built, data replicated, no traffic |
| 3 — Warm standby                 | Seconds       | Minutes         | $$$   | Scaled-down passive region always running            |
| 4 — Hot standby (active-passive) | Seconds       | Seconds-minutes | $$$$  | Full passive region, async replication               |
| 5 — Multi-region active-active   | ~0            | Seconds         | $$$$$ | All regions active, sync or quorum                   |

**AWS defines these tiers as "DR Tiers 0-5". The minimum for a B2B SaaS with paying customers is Tier 3.**

**Recovery time math:**
- DNS TTL: 60-300s (the floor for DNS-based failover)
- Health check interval: 10-30s (how fast you detect failure)
- Promotion: 30-300s (database promotion, cache warmup)
- App boot: 30-60s

So an automated DR failover from "region dies" to "other region takes traffic" is **~2-5 minutes** in a well-designed Tier 3 system. Tier 5 (active-active) is sub-30s because traffic just shifts.

---

## 7. Cost

Multi-region is expensive. Order-of-magnitude estimates per TB/month (rough, 2026):

| Resource      | Single-region         | Multi-region (active-active)                           |
| ----------      | --------------          | ------------------------------                           |
| Compute       | 1×                    | 3× (1 per region + headroom for failover)              |
| Data transfer | $0 in-region          | **$0.02-0.09/GB cross-region** (often the surprise)    |
| Database      | 1× primary + replicas | 3× primary + 3× replicas (or 3× replicas w/ consensus) |
| Storage       | 1×                    | 3× (full copy in each region)                          |
| **Total**     | **1×**                | **~3-5×**                                              |

The killer line item is **data transfer**. A 1 TB/day cross-region replication = $700-3000/month. 100 TB/day = $70-300K/month. Always estimate this.

### Multi-region read replica promotion (Postgres)

```typescript
// In production, use a tool like PgBouncer + Patroni or AWS RDS Multi-Region Clusters.
// This is a sketch of the read-replica promotion step.

async function promoteReplicaToPrimary(region: string) {
  // 1. Stop accepting writes on the dead region's primary.
  // 2. Wait for the new region's replica to catch up.
  const replica = await pgClient(`postgres://replica-${region}/mydb`);
  await sql`SELECT pg_wal_replay_pause()`.execute(replica);
  // 3. Verify no in-flight writes from the old primary.
  const lagBytes = await sql`SELECT pg_last_wal_replay_lsn() - pg_last_wal_receive_lsn() AS lag`
    .execute(replica);
  if (lagBytes > 1024 * 1024) throw new Error("replica too far behind");
  // 4. Promote.
  await sql`SELECT pg_promote()`.execute(replica);
  // 5. Update DNS / LB to point at the new primary.
  await route53.changeResourceRecordSets(/* new primary */);
  // 6. Reconfigure the rest of the region to read from the new primary.
}
```

### CRDT counter (G-Counter)

```typescript
// Grow-only counter: each region has its own count. Total = sum of all regions.
// Convergent by design. Used for like counts, view counts, page visits.
class GCounter {
  private counts: Map<string, number> = new Map();

  inc(region: string, by = 1) {
    this.counts.set(region, (this.counts.get(region) ?? 0) + by);
  }

  value(): number {
    return [...this.counts.values()].reduce((a, b) => a + b, 0);
  }

  merge(other: GCounter): GCounter {
    const merged = new GCounter();
    const keys = new Set([...this.counts.keys(), ...other.counts.keys()]);
    for (const k of keys) {
      merged.counts.set(k, Math.max(this.counts.get(k) ?? 0, other.counts.get(k) ?? 0));
    }
    return merged;
  }
}

// On replication: ship the map. On receive: merge.
// Total count always converges to the sum of all per-region counts.
```

### Region-aware user routing (TypeScript)

```typescript
// Pin users to their home region on signup; route all writes there.
// Reads can come from any region (cross-region read replicas).
function homeRegionFor(userId: string): Region {
  const hash = parseInt(userId.slice(0, 8), 16);
  const regions: Region[] = ["us-east-1", "eu-west-1", "ap-southeast-1"];
  return regions[hash % regions.length];
}

// Write path: always go to home region.
async function writeUserProfile(userId: string, profile: Profile) {
  const region = homeRegionFor(userId);
  return primaryDb(region).users.update(userId, profile);
  // Async replication carries the write to other regions' read replicas.
}

// Read path: closest region.
async function readUserProfile(userId: string, clientRegion: Region) {
  return replicaDb(clientRegion).users.findById(userId);
  // May be a few seconds behind home region; acceptable for reads.
}
```

## Common Mistakes

- **Confusing "active-active" with "no conflict".** They are not the same. If two regions write the same row, you have a conflict. Plan for it.
- **Forgetting data-transfer costs.** Cross-region replication at scale can dwarf compute. Estimate the bandwidth first.
- **GeoDNS with 24h TTL.** DNS TTL is the floor for failover recovery. 60-300s for production.
- **Replicating PII across borders for "convenience".** GDPR fine is 4% of global revenue. Not worth it.
- **Multi-region writes for money.** Don't. Use a single-region ledger, replicated synchronously to one DR region.
- **Treating "active-active" as a marketing checkbox.** Most "active-active" SaaS is actually "per-user-region-pinned writes + cross-region reads". Say what you actually run.
- **Health checks that pass for a dead region.** Health check the actual data path, not just `/health`. The bug: a service returns 200 but the database is unreachable.
- **No game day for failover.** A DR plan you've never tested isn't a plan, it's a hope. Quarterly game day.
- **Promoting a stale replica.** A replica that fell behind 10 minutes and you promote it: you lose 10 minutes of writes. Always check `pg_last_wal_replay_lsn` or equivalent before promotion.
- **Skipping the cost model.** Three regions of compute + storage + cross-region traffic is 3-5× single-region. The CFO will ask.
- **Confusing "global" with "everyone sees the same data".** Global ≠ consistent. Global = available in every region. They can be eventually consistent.

---

## Best Practices

1. **Pick the topology to match the requirement.** Most apps don't need active-active. Active-passive is 80% of the value at 30% of the cost.
2. **Pin writes to a home region** for any user-data write that doesn't need real-time global visibility. Default pattern.
3. **Use CRDTs for counters and append-only data.** They converge by design.
4. **Treat money as a single-region problem.** Ledger in one region, sync-replicated to one DR region. Period.
5. **Test failover in production (game days).** Quarterly. You will find issues you never imagined.
6. **GeoDNS at 60-300s TTL.** Anything higher is a liability.
7. **Health-check the data path**, not just `/health`. The "I'm alive but my DB is gone" failure is the most common DR bug.
8. **Estimate the bandwidth first.** Cross-region transfer is the surprise cost line. Surface it in the design doc.
9. **Document RPO and RTO.** Numbers, not vibes. "Tier 3: RPO < 1 min, RTO < 5 min" beats "we have DR".
10. **One DR plan, not three.** Pick a tier. Build for it. Don't half-build four.

## Performance Considerations

| Concern                     | Single-region     | Active-passive                             | Active-active (sharded writes) | Active-active (multi-region writes) |
| ---------                     | ---------------     | ----------------                             | -------------------------------- | -------------------------------------- |
| Write latency               | Local             | Local + replication lag (writes are local) | Local                          | Local + conflict resolution cost    |
| Read latency (home region)  | Local             | Local                                      | Local                          | Local                               |
| Read latency (other region) | N/A               | Cross-region (~100ms)                      | Local (replica)                | Local (replica)                     |
| Availability                | 99.9% (single AZ) | 99.95% (region + DR)                       | 99.99%                         | 99.99%+                             |
| RPO                         | Hours (backup)    | Seconds                                    | ~0 (sync) or seconds (async)   | ~0 (quorum) or seconds (async)      |
| RTO                         | Hours             | Minutes                                    | Seconds                        | Seconds                             |
| Cost (relative)             | 1×                | ~1.5×                                      | ~2-3×                          | ~3-5×                               |
| Operational complexity      | Low               | Medium                                     | High                           | Very high                           |

## Summary

- **Pick a topology**: single-region for prototypes, active-passive for most B2B, active-active for global real-time products.
- **Routing**: GeoDNS at 60-300s TTL, layered with Anycast / CDN / HTTP LB.
- **Replication**: synchronous for RPO=0, async for speed, quorum for tunable consistency.
- **Conflicts**: avoid by sharding (home region per user), LWW for trivial cases, CRDTs for counters/sets, never multi-region write money.
- **GDPR / data residency**: regional partitioning, sovereign cloud, tokenization.
- **DR**: pick RPO/RTO first, then architecture. Test quarterly.
- **Cost**: 3-5× for full active-active; bandwidth is the surprise.
- **In interviews: pick the topology, name the RPO/RTO, name the conflict strategy, name the cost.**

## Cheat Sheet

```text
MULTI-REGION DEPLOYMENT CHEAT SHEET
═══════════════════════════════════════════════════════════════════

TOPOLOGIES
  • Single-region: 1× cost, hours RTO, no DR story
  • Active-passive: 1.5× cost, minutes RTO, async replication
  • Active-active: 3-5× cost, seconds RTO, conflict resolution

ROUTING
  • GeoDNS (60-300s TTL): most production web
  • Anycast: DDoS + UDP + global CDN
  • HTTP LB: inside a region
  • CDN edge: cached + dynamic content

REPLICATION
  • Sync: RPO=0, +100ms latency, CockroachDB / Spanner
  • Async: RPO=seconds, fast, most production
  • Quorum: tunable, R+W>N for strong

CONFLICT RESOLUTION
  • Avoid: pin writes to home region (default pattern)
  • LWW: simple, lossy, OK for profile
  • Vector clocks: more honest, rare
  • CRDTs: counters, sets, text (Yjs, Automerge)
  • Never: money, inventory, anything financial

DATA RESIDENCY
  • Regional partitioning (EU data in EU)
  • Sovereign cloud (AWS GovCloud, Azure Germany)
  • Tokenization (replace PII before cross-border)
  • GDPR fine: 4% of global revenue

DR TIERS (AWS)
  • 0: backup only
  • 1: backup + restore
  • 2: pilot light
  • 3: warm standby (B2B SaaS minimum)
  • 4: hot standby / active-passive
  • 5: multi-region active-active

INTERVIEW FORMULA
  • Pick topology (active-passive vs active-active)
  • Name RPO and RTO
  • Name replication mode (sync/async/quorum)
  • Name conflict resolution (shard / LWW / CRDT)
  • Name the cost (3-5× for true active-active)
  • Name the failure mode (replica lag, DNS TTL, PII)
```

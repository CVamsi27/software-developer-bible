# Multi-Region Deployment

A global order service wants fast reads near customers and recovery after a regional outage. It also must not let two regions reserve the same last item. Adding a second region solves neither problem by itself: the design must choose where writes are authoritative, what a remote read can observe, and how failover changes ownership:

```text
EU reads fast, US writes authoritative → what does an EU read observe?
```

## Definition

**Multi-region deployment** runs application or data components in geographically separate regions to improve regional latency, recovery, or data placement. It defines how traffic is routed, which region holds **write authority**, how replicas change, and what happens when regions cannot communicate.

> **Textbook Definition:** Multi-region deployment distributes application and data components across geographic regions under explicit policies for traffic routing, write authority, replication consistency, data location and recovery from regional failure.

## First Principles

1. **Distance trades latency for freshness.** A nearby replica can answer sooner, but may not include a recent remote write.
2. **Every write needs an authority.** It may be one region, one owner per key, or a protocol coordinating regions. "Active-active" alone never says which.
3. **Recovery changes ownership and traffic.** Replication lag, fencing the old writer (rejecting its stale ownership generation at the data boundary), dependencies, surviving capacity, and routing all determine what users experience.
4. **Regions are not wholly independent failure domains.** Identity systems, provider control planes, quotas, and network paths can still be shared.

## 1. Start from the user contract, then pick a topology

Write down which operations need local latency, which may see stale data, and which invariants must remain true during a partition. Then choose a topology per data type:

| Topology | Serving and write model | Main cost or limit |
| --------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Single region | One region serves and owns writes. | A regional outage requires restore or a separate recovery design. |
| Active-passive | One region serves normal traffic and owns writes; a standby is promoted after recovery checks. | Failover time and possible lost writes depend on replication, fencing and routing. |
| Active-active, single write owner | Multiple regions serve traffic, while each key or tenant has one write owner or home region. | Remote writes and ownership changes add latency and require a transfer protocol. |
| Active-active, multi-writer | Multiple regions serve and accept writes for the same data. | Concurrent updates require a conflict rule or cross-region coordination. |

**Active-active means multiple regions serve traffic; it does not necessarily mean every region can write the same record.** Keep the serving topology separate from the per-key write policy. A region must never start accepting writes merely because traffic was routed there.

## 2. Route requests to a useful region

| Mechanism | What it selects | What affects failover |
| -------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Domain Name System (DNS) routing | A region based on geography or health policy. | Resolver and client caches, connection reuse and health-detection delay. |
| Anycast | An advertised network address reached through routing policy. | Route convergence and the network operator's policy. |
| HTTP proxy or load balancer | A backend per request using application or health information. | Proxy availability, health-check meaning and connection state. |
| Content delivery network (CDN) | Cached content or an origin for supported paths. | Cache freshness and origin failover policy; it does not define database write authority. |
| Client routing | An endpoint selected by the application. | Client refresh, endpoint discovery and fallback behavior. |

Health should indicate whether the region can serve useful work, not merely whether its process responds. Routing is only one part of recovery: open connections, data promotion, identity dependencies, capacity, and service quotas can dominate observed recovery time. DNS time-to-live is never the full failover time.

## 3. Define what a successful write means

With **asynchronous replication**, the source acknowledges a write before remote copies receive it. This lowers write latency, but a remote read can be stale and a regional failure can lose writes still in transit. Track replication lag and define the allowed recovery point.

With **synchronous replication**, the write waits for acknowledgments required by the database's protocol. Acknowledged-write survival depends on where those replicas are and the protocol's failure assumptions. Cross-region round trips raise latency, and a partition may prevent writes if the required quorum is unreachable. Synchronous replication does not automatically mean every replica holds the latest value or every transaction is globally atomic.

A **quorum** is the minimum set of replicas whose acknowledgments the protocol needs to proceed. In a simple fixed-membership model, a read set and write set intersect when R + W > N, where R is the read-quorum size, W the write-quorum size, and N the replica count. That arithmetic alone never proves **linearizability** (each completed operation appears to take effect atomically in an order consistent with real time) or safe membership changes; the database's complete read, write, version, and recovery protocol defines the guarantee.

One product-specific example: DynamoDB global tables documents two different consistency modes; their behavior must never be generalized to other databases.

**Multi-Region eventual consistency (MREC)** replicates item changes asynchronously. Concurrent writes to one item resolve by an internal-timestamp last-writer-wins rule. A transaction is atomic in its source region, but its item changes replicate individually, so a remote region can temporarily see only part of it. Its RPO depends on replication delay.

**Multi-Region strong consistency (MRSC)** synchronously replicates writes to another region before success and supports strong reads and an RPO of zero under its documented service contract. It requires exactly three supported Regions: three replicas, or two replicas and a witness. AWS permits any combination of three supported Regions, including Regions on different continents. A witness serves no reads or writes.

Cross-region communication increases write and strong-read latency; same-item conflicts can fail with **ReplicatedWriteConflictException**. MRSC does not support transactions, time-to-live (TTL) deletion, or local secondary indexes.

Check AWS's current supported-Region list and constraints before choosing MRSC, then measure latency across the intended locations. Product availability changes over time, and these limits describe DynamoDB rather than a universal synchronous-replication model.

## 4. Decide how concurrent writes resolve

A single authority avoids conflicts only while every writer respects its ownership rule. A failover must fence the old owner before another region accepts writes; otherwise both may believe they are authoritative.

| Strategy | What it does | What the application must accept |
| ----------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| One owner per key or tenant | Routes each write to one authority; ownership can be home-region or partitioned. | Remote access may add latency. Ownership changes need fencing and data migration. |
| Last-writer-wins | Selects one version using a defined timestamp or version rule. | A concurrent update can be discarded; clock and tie-breaking behavior matter. |
| Version vectors | Tracks causal history to distinguish ordered updates from concurrent ones. | Detecting a conflict never decides how the product should resolve it. |
| Conflict-free replicated data type (CRDT) | Merges supported operations so replicas converge after receiving the same updates. | The data type constrains operations; convergence alone never preserves every business invariant. |
| Operational transformation (OT) | Transforms concurrent collaboration operations under a defined ordering protocol. | Requires a tested protocol for that document model; OT and CRDTs are distinct approaches. |

A state-based grow-only counter shows both the benefit and the boundary of a CRDT. If region A owns component A and region B owns component B, their states {A:3, B:0} and {A:0, B:2} merge by per-component maximum, producing {A:3, B:2} and total 5. Replaying the same state changes nothing. But if two writers both change A from 3 to 4, the merge still returns 4: one increment is lost. A unique, durable owner per component is part of the protocol.

Never use an eventually convergent counter or last-writer-wins field to protect a ledger, inventory reservation, or other invariant requiring atomic coordination. Use one authority or a database protocol explicitly providing the required guarantee.

## 5. Place data under its legal constraints

**Data residency** concerns where data is stored or processed; **data sovereignty** concerns the laws and control applying to the data. They are related, but never interchangeable. Requirements depend on the data, parties, jurisdiction, and transfer mechanism; never infer that a regulation requires every record to stay within one country's borders.

Map the full data path: primary records, replicas, backups, logs, analytics, support access, and subprocessors. Where personal data moves outside the European Union, the European Data Protection Board describes transfer mechanisms such as an adequacy decision or safeguards including Standard Contractual Clauses or Binding Corporate Rules. Confirm the current rules and the specific organization's obligations with qualified counsel. Location constraints can change routing, key management, backup placement, telemetry, and incident access. Encryption and pseudonymization reduce some risks but never by themselves settle data-transfer requirements.

## 6. Make RPO, RTO, and capacity testable

A **recovery point objective (RPO)** is the maximum acceptable recent data loss, expressed as time. A **recovery time objective (RTO)** is the target time to restore a service after disruption. They are objectives to test, never properties guaranteed by a topology name.

Disaster-recovery options differ in readiness, not in guaranteed recovery times:

| Recovery design | What is ready before failure | Typical trade-off |
| ------------------------ | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Backup and restore | Backups and infrastructure definitions. | Lowest always-on footprint; restoration and provisioning can take longest. |
| Pilot light | Data and core infrastructure are present; application capacity must be started or scaled. | Less standby compute, with additional failover steps. |
| Warm standby | A reduced but functional environment is already running. | Faster service than pilot light, but steady standby cost. |
| Multi-site active-active | Multiple sites already serve traffic. | High operating and data-coordination complexity; does not imply multi-writer data. |

Set RPO and RTO from business impact, then exercise the whole path: detect and declare the failure, fence the previous writer, inspect lag or restore point, promote the new authority, verify dependencies and capacity, route traffic, and reconcile the recovered region. Test both regional loss and data corruption. Live replication can copy an accidental delete or corrupt update; it never replaces point-in-time backups and restore tests.

Model peak normal traffic and single-region failure traffic separately. Check database throughput, application capacity, network transfer, service quotas, and backup retention in the surviving regions. Replicated compute and storage, cross-region traffic, observability, and operational effort all add cost. Use current provider prices and workload estimates rather than assuming a second region doubles every bill by the same amount.

## Summary

Choose regions from user latency, data-location and recovery requirements. For each data type, state the write authority, remote-read freshness, replication contract and conflict rule. Treat traffic routing, fencing, capacity and data restoration as one tested recovery procedure. RPO and RTO are demonstrated by exercises, not topology labels.

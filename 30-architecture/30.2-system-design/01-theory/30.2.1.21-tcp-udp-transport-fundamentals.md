# TCP & UDP Transport Fundamentals

A request times out, and someone suggests replacing TCP with UDP to make it faster. Before changing transports, ask what the application needs: a stream whose bytes arrive in order, independent datagrams, or multiple reliable streams with less cross-stream blocking? The answer determines which guarantees the application gets from the transport and which it must implement itself:

```text
timeout over TCP → bytes delivered ≠ operation committed. Retry needs an operation ID.
```

## Definition

The **transport layer** moves data between application endpoints. IP routes packets between hosts; transport protocols use **port numbers** to deliver that data to the right process and define how the endpoints exchange it.

> **Textbook Definition:** Transmission Control Protocol (TCP) provides a reliable, ordered byte stream between endpoints. User Datagram Protocol (UDP) sends independent datagrams without transport-level guarantees of delivery, ordering, or duplicate suppression.

## First Principles

1. **Transport reliability is not business success.** TCP can deliver request bytes to the peer's TCP stack, but it cannot tell the caller whether the application processed or committed an operation. A timeout can leave that outcome unknown; operation IDs and idempotency are application-level tools for safe retries.
2. **A stream has no message boundaries.** One write can arrive in several reads, and several writes can arrive in one read. The application protocol must frame messages, for example with a length prefix or delimiter.
3. **UDP trades built-in guarantees for independent datagrams.** A later datagram can be delivered even if an earlier one was lost, but the application must decide whether loss, duplication, reordering, pacing, congestion control, or security need handling.
4. **Choose by contract, not by protocol name.** QUIC uses UDP packets but adds reliable streams, flow control, congestion control, loss recovery, encryption, and connection migration. UDP itself does not make an application faster or reliable.

## How It Works

```text
┌───────────────────────────────────────────────────────────┐
│  Application protocols HTTP · SSH · DNS · SMTP · gRPC     │
├───────────────────────────────────────────────────────────┤
│  Transport layer      TCP (reliable stream)               │
│                       UDP (datagram transport)            │
├───────────────────────────────────────────────────────────┤
│  Network layer        IP — best-effort packet delivery    │
├───────────────────────────────────────────────────────────┤
│  Link layer           Ethernet · Wi-Fi · fiber · cellular │
└───────────────────────────────────────────────────────────┘
```

TCP and UDP are common Internet transports, not the only ones. Their contracts differ:

| Property | TCP | UDP |
| ------------------------------------ | ---------------------------------------------------------------- | --------------------------------- |
| Data delivered to the application as | Ordered byte stream | Separate datagrams |
| Connection setup | Handshake | None |
| Delivery and ordering | Retransmits and orders bytes while the connection remains viable | No delivery or ordering guarantee |
| Receiver flow control | Yes | No |
| Congestion control | Yes; algorithm depends on the implementation | No built-in mechanism |
| Header size | 20–60 bytes, including options | 8 bytes |

### 1. Establish, deliver, and protect a TCP connection

In the ordinary three-way handshake, each endpoint chooses an initial sequence number. The SYN-ACK acknowledges the client's initial sequence number and introduces the server's; the final ACK confirms the client received it. TCP can then track each direction independently:

```text
CLIENT                                   SERVER
  │                                         │
  │── SYN, seq=x ─────────────────────────►│   client opens
  │                                         │
  │◄─ SYN-ACK, seq=y, ack=x+1 ─────────────│   server replies
  │                                         │
  │── ACK, ack=y+1 ────────────────────────►│   client confirms
  │                                         │
  │═══════ connection established ═════════│
  │── application bytes ──────────────────►│
```

A round-trip time (RTT) is the time for a signal to travel to the peer and back. With this ordinary handshake, TCP setup normally costs about 1 RTT before application data can proceed. A full TLS 1.2 handshake commonly adds 2 RTTs; a full TLS 1.3 handshake commonly adds 1. Session resumption and early data change what can be sent and when. TLS 1.3 0-RTT data can be replayed, so applications must restrict it to operations designed to tolerate replay. At a 70 ms RTT, a new TCP connection plus a full TLS 1.3 handshake takes about 140 ms before ordinary application data can be sent. DNS lookup, the request/response exchange, server processing, and queueing add time. Reusing a connection avoids repeating these setup handshakes for every request.

TCP numbers bytes, acknowledges received ranges, and retransmits data when loss is detected. If a segment is missing, the receiver may buffer later bytes but cannot deliver bytes past the gap to the application:

```text
Sender sends:   [1-100] [101-200] [201-300] [301-400] [401-500]
Receiver gets:     ok       ok       LOST      held      held
Receiver acks:             ack=201  ack=201   ack=201   ack=201
                                      │
                           missing range is recovered
```

This is transport-level head-of-line (HOL) blocking: one missing range delays later bytes on the same TCP stream. TCP delivery also ends at the transport boundary. Even after the remote stack acknowledges bytes, the application might fail before committing the requested operation.

TCP holds two separate controls. **Flow control protects the receiver:** the receiver advertises a receive window (`rwnd`) from available buffer space, and the sender limits unacknowledged data to that window. If the application stops reading, the window can shrink or reach zero; this is backpressure, not necessarily a network fault. The actual data in flight is also bounded by the congestion window below. See [Backpressure & Flow Control](30.2.1.13-backpressure-and-flow-control.md). **Congestion control protects the network:** the sender limits data in flight with a congestion window (`cwnd`). It probes for available capacity and reduces sending when congestion is inferred. Classic TCP Reno illustrates additive increase and multiplicative decrease (AIMD); modern algorithms and growth rules vary by implementation. At any moment, outstanding data is bounded by the smaller of rwnd and cwnd. The distinction matters in production: receiver saturation calls for application or capacity changes, while network congestion calls for examining the path and traffic behavior. Reusing a connection can also preserve useful congestion state instead of repeatedly restarting with new connections.

### 2. Implement guarantees yourself over UDP

UDP adds an 8-byte header with source port, destination port, length, and checksum. It establishes no connection and provides no retransmission, ordering, duplicate suppression, flow control, or congestion control. A successful local send call never proves a peer received the datagram.

This model works when messages are independently useful and the application can make timely decisions under loss. Real-time media may prefer a recent frame to a delayed retransmission; a game may discard state superseded by a newer update. The application or a higher-level protocol still needs an appropriate congestion-control and pacing strategy. If it needs reliability, it must also define acknowledgments, retries, duplicate handling, and message framing. Recreating these mechanisms casually can be less safe and efficient than using a maintained protocol such as QUIC.

### 3. Reduce cross-stream blocking with QUIC

HTTP/2 multiplexes many request streams over one TCP connection. Because TCP delivers one ordered byte stream, loss in that connection can delay data for all HTTP/2 streams, even when some later data is intact.

HTTP/3 uses QUIC over UDP. QUIC gives streams independent ordering and loss recovery: loss affecting one stream never automatically blocks delivery on other streams. The streams still share connection-level congestion control, and missing data still blocks later data within the affected ordered stream. QUIC connection IDs can let a connection survive some client address changes after the new path is validated, such as when switching networks.

A QUIC handshake integrates TLS 1.3. A full handshake commonly takes 1 RTT; eligible resumed connections can send 0-RTT early data, with replay risk. HTTP/3 therefore gets no reliability from UDP; it gets its transport guarantees from QUIC.

### 4. Choose the transport from the workload

| Workload | Common transport | Reason and boundary |
| ----------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| HTTP/1.1 and HTTP/2 | TCP | Reliable ordered stream; HTTP defines message framing, and HTTP/2 multiplexing still shares TCP's loss blocking |
| HTTP/3 | QUIC over UDP | Reliable streams with less cross-stream blocking; streams still share congestion control |
| PostgreSQL and MySQL connections | TCP | Ordered stream; database protocols frame queries and replies, while transactions define commit behavior |
| SSH and SMTP | TCP | Commands and responses depend on reliable ordered delivery |
| DNS | Often UDP; TCP is also required and used | Small queries commonly fit in datagrams; DNS transport rules cover truncation and other cases |
| Real-time media and some game state | Often UDP-based protocols | Timeliness may matter more than retransmitting stale data; the application stack still handles congestion and any needed recovery |
| File transfer or on-demand video | TCP or QUIC | Reliable delivery is useful; buffering and the application protocol determine playback behavior |

### 5. Reuse connections, size pools, and terminate TLS deliberately

Persistent HTTP connections and outbound pools avoid paying handshake cost per request. A pool also limits sockets, so requests may wait when the pool is full. Monitor pool wait time as well as request latency and errors; distinguish pool saturation from a slow upstream. For example, Node's HTTP/1.1 `Agent` can cap active sockets per upstream host and across all hosts. These settings are limits, not universally correct values; choose them with upstream capacity and workload concurrency in mind:

```typescript
import { Agent, request } from "node:http";

const agent = new Agent({
  keepAlive: true,
  maxSockets: 50,        // active sockets per host
  maxTotalSockets: 100,  // active sockets across hosts
  maxFreeSockets: 10,    // idle sockets retained per host
});

const req = request(
  { host: "upstream.internal", path: "/api", agent },
  (res) => res.resume(),
);
req.end();
// Handle timeouts, request errors, and response status in production code.
```

HTTP/1.1 connections persist by default unless closed. Pooling never removes the need to handle timeouts or uncertain operation outcomes. Frequent active closes can also leave sockets in `TIME_WAIT` for an implementation-dependent interval; investigate connection churn before tuning platform timers.

For HTTPS over TCP, TLS runs above TCP and below HTTP. It authenticates the server and can authenticate the client when configured; it protects application data but never changes TCP's stream semantics. A TLS-terminating proxy is a secure endpoint for the client connection and typically establishes a separate upstream connection, which may or may not use TLS. QUIC integrates TLS 1.3 into its transport handshake:

```text
┌──────────────────────────────────┐
│ HTTP (request/response)          │  application
├──────────────────────────────────┤
│ TLS (records, keys, certificates)│
├──────────────────────────────────┤
│ TCP (reliability, ordering)      │  transport
├──────────────────────────────────┤
│ IP                               │  network
└──────────────────────────────────┘
```

A TCP flow is commonly identified by its source and destination IP addresses and ports (the 4-tuple). A layer-4 balancer routes with network and transport metadata such as these addresses and ports. It cannot decide from encrypted HTTP paths, cookies, or headers. An HTTP-aware proxy can route on those fields after it has access to HTTP, which for HTTPS generally means terminating TLS. Server Name Indication (SNI) can support routing without decrypting HTTP when the hostname is visible in the TLS handshake; Encrypted Client Hello (ECH) can conceal the inner server name. Choose the layer from the routing information and security boundary needed. See [Load Balancing](30.2.1.04-load-balancing.md).

Measure the boundary actually cared about. This Node.js example measures the time until a TCP socket connects. When `host` is a name rather than an IP address, name resolution can be included; it never measures TLS, an HTTP request, or server processing:

```typescript
import net from "node:net";

function measureConnect(host: string, port: number, timeoutMs = 5000): Promise<number> {
  const start = process.hrtime.bigint();
  return new Promise((resolve, reject) => {
    const socket = net.connect({ host, port });
    const timer = setTimeout(
      () => socket.destroy(new Error("connect deadline exceeded")),
      timeoutMs,
    );

    socket.once("connect", () => {
      clearTimeout(timer);
      const elapsedMs = Number(process.hrtime.bigint() - start) / 1e6;
      socket.destroy();
      resolve(elapsedMs);
    });
    socket.once("error", (error) => {
      clearTimeout(timer);
      reject(error);
    });
  });
}

measureConnect("example.com", 443).then((ms) => {
  console.log("TCP connect, possibly including DNS: " + ms.toFixed(1) + " ms");
});
```

To observe UDP's local-send boundary, run the receiver and sender in separate processes. A message event shows that this receiver got a datagram; the sender's callback alone cannot confirm peer delivery. Receiver:

```typescript
import dgram from "node:dgram";

const receiver = dgram.createSocket("udp4");
receiver.on("message", (message, remote) => {
  console.log(
    "received " + message.length + " bytes from " + remote.address + ":" + remote.port,
  );
});
receiver.bind(9999, "127.0.0.1");
```

Sender:

```typescript
import dgram from "node:dgram";

const sender = dgram.createSocket("udp4");
sender.send(Buffer.from("example datagram"), 9999, "127.0.0.1", (error) => {
  if (error) console.error("local send error:", error);
  else console.log("local send completed; peer receipt is unknown");
  sender.close();
});
```

## Summary

TCP supplies a reliable ordered byte stream, receiver flow control, and network congestion control, but not application message boundaries or business-operation success. Its ordered delivery can block later bytes behind loss. UDP supplies independent datagrams without built-in delivery, ordering, flow, or congestion guarantees. QUIC builds reliable streams and congestion control over UDP, reducing cross-stream blocking while retaining shared connection congestion. Connection reuse reduces setup work; choose transport and load-balancing layers from the application's delivery, timing, and routing contracts.

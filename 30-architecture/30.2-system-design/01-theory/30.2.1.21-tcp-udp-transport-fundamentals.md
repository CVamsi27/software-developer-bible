# TCP & UDP Transport Fundamentals

> **The two doors every byte of internet traffic walks through.** TCP gives you a reliable ordered byte stream and pays for it with handshakes, retransmissions, and head-of-line blocking. UDP gives you a fire-and-forget datagram and makes you build (or skip) everything else. Every latency number, load balancer choice, and "why does QUIC exist" question bottoms out here.

## TL;DR

- **Transport sits between IP (below) and application protocols (above).** IP moves packets best-effort; TCP/UDP decide whether you get reliability, ordering, and flow control.
- **TCP = connection + reliability:** three-way handshake (1 RTT before data), sequence/ack numbers, retransmission on loss, receive-window flow control, slow-start/AIMD congestion control.
- **UDP = connectionless datagrams:** no handshake, no ordering, no retry, no congestion control. The application owns all of it.
- **Rule of thumb:** correctness-critical request/response (HTTP, DB, SSH) → TCP; latency-tolerant-to-loss media/realtime (DNS, video, gaming) → UDP; modern fix → QUIC, which rebuilds TCP semantics on top of UDP.
- **Connection reuse is not optional:** a fresh TCP+TLS connection can cost 2–4 RTTs; keep-alive/pooling turns that into amortized zero.
- **In interviews: know the handshake cold, know why HTTP/3 moved off TCP, and nail the transport leg of "what happens when you type a URL".**

## Definition

The transport layer provides host-to-host (really process-to-process, via port numbers) communication on top of the network layer. IP below it delivers packets but guarantees nothing — packets are lost, duplicated, reordered, throttled. The transport protocol is where you choose your guarantees:

```text
┌─────────────────────────────────────────────────────────────┐
│  Application layer    HTTP · SSH · DNS · SMTP · QUIC · gRPC │
├─────────────────────────────────────────────────────────────┤
│  Transport layer      TCP (reliable stream)                 │
│                       UDP (unreliable datagram)             │
├─────────────────────────────────────────────────────────────┤
│  Network layer        IP — best-effort packet delivery      │
├─────────────────────────────────────────────────────────────┤
│  Link layer           Ethernet · Wi-Fi · fiber · cellular   │
└─────────────────────────────────────────────────────────────┘
```

| TCP | UDP |  |
| ------------------ | ---------------------- | ------------ |
| Unit | Byte stream (segments) | Datagram |
| Connection | Handshake required | None |
| Reliability | Retransmits lost data | Lost is lost |
| Ordering | In-order delivery | None |
| Flow control | Receive window | None |
| Congestion control | Slow start / AIMD | None |
| Header size | 20–60 bytes | 8 bytes |

## Why It Matters

1. **Every performance number you quote depends on transport.** Time-to-first-byte, TLS overhead, retry storms — all shaped by handshakes and RTT.
2. **Protocol choice is an architecture decision.** Picking TCP for a game loop or UDP for a payment API is a design failure visible in round one of any system design interview.
3. **L4 vs L7 load balancing only makes sense if you know what each layer can see** — which requires knowing what TCP exposes versus what lives in the payload.
4. **Backpressure was invented here.** TCP's flow-control window is the original producer-slow-down signal; every queue/backpressure discussion inherits from it.
5. **QUIC/HTTP-3 is the biggest transport shift in 20 years** — and explaining *why* it exists requires exactly this chapter's mechanics (handshakes, HOL blocking, ossification).

## How It Works

### Where transport sits

IP routes packets between hosts; port numbers multiplex them to processes. TCP connection = `(src IP, src port, dst IP, dst port)` 4-tuple. That tuple is also exactly what an L4 load balancer sees — remember this for later.

### The TCP three-way handshake

Before any application byte moves, both sides agree on initial sequence numbers:

```text
CLIENT                                   SERVER
  │                                         │
  │── SYN, seq=x ─────────────────────────►│   ① client wants to talk
  │                                         │
  │◄─ SYN-ACK, seq=y, ack=x+1 ─────────────│   ② server agrees + picks its seq
  │                                         │
  │── ACK, ack=y+1 ────────────────────────►│   ③ client confirms server's seq
  │                                         │
  │═══════ connection ESTABLISHED ═════════│
  │── [PSH, ACK] GET / HTTP/1.1 ───────────►│   now app data may flow
```

Why three ways? The exchange synchronizes **two independent sequence numbers** (x for client→server, y for server→client). Two segments would leave the server unsure the client received its SYN-ACK.

**Cost accounting (the interview-relevant part):**

- Handshake itself = **1 full RTT** before any data.
- TLS 1.2 on top = **+2 RTT** (ClientHello/ServerHello... then key exchange); TLS 1.3 = **+1 RTT**.
- A first HTTPS request to a far region at 70 ms RTT: ~70 ms connect + ~70 ms TLS + request/response ≈ **210+ ms before useful work completes**. This is the number that motivates keep-alive, connection pooling, TLS session resumption, and QUIC's 0-RTT.

### Reliability mechanics

**Sequence numbers & acknowledgments.** Every byte is numbered. The receiver acks the next byte it expects (cumulative ack). Missing range → sender retransmits:

```text
Sender sends:      [1-100] [101-200] [201-300] [301-400]
Receiver gets:      ok      ok        LOST      held*
Receiver acks:              ack=201   ack=201   ack=201
                                     ▲
Sender: after 3 duplicate acks → FAST RETRANSMIT of [201-300]
        (or waits for the RTO timer if dup-acks don't arrive)
```

*Bytes beyond a gap are usually buffered but cannot be delivered to the app until the hole fills — this is the seed of transport-level head-of-line blocking.

**Flow control (protect the receiver).** The receiver advertises a window (`rwnd`) = free buffer space. Sender may have at most `rwnd` unacknowledged bytes in flight. As the app reads data, the window slides open. Zero-window = hard stop: the original backpressure mechanism (see [Backpressure & Flow Control](30.2.1.13-backpressure-and-flow-control.md)).

**Congestion control (protect the network).** Independent of rwnd, the sender keeps a congestion window (`cwnd`):

- **Slow start:** cwnd starts small (~10 segments), doubles every RTT (exponential) until reaching `ssthresh` or loss.
- **Congestion avoidance (AIMD):** additive increase (+1 segment per RTT), multiplicative decrease (halve cwnd on loss).

```text
cwnd
 │                    ／﹨            ／
 │                 ／﹨   ﹨halve   ／  ← AIMD sawtooth
 │             ／﹨        ﹨     ／
 │        ／﹨              ﹨＿／
 │   ／﹨  ← loss event
 │／   ssthresh ──────────────────────────────
 └──────────────────────── time (RTTs) ─────►
   slow start (×2/RTT)   congestion avoidance (+1/RTT)
```

Consequence: **long-lived connections "warm up" and short-lived ones never do** — one more reason to reuse connections instead of paying slow start per request.

### The UDP datagram model

UDP is nearly a pass-through: an 8-byte header (source port, dest port, length, checksum) over IP. No handshake, no seq/acks, no ordering, no retransmission, no congestion control, no receiver window.

What you gain: **no setup latency, no HOL coupling between datagrams, predictable per-packet cost**, and freedom to design your own reliability (which is precisely what QUIC, WebRTC, and game netcode do).

What you accept: loss, duplication, reordering, and — because there is no congestion control — the social contract that your app paces itself or contributes to collapse.

### TCP vs UDP decision table

| Workload | Protocol | Why |
| -------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| HTTP/1.1, HTTP/2 | **TCP** | Correctness > latency; streams benefit from reliability |
| Database connections (Postgres, MySQL) | **TCP** | Never acceptable to lose a query mid-flight |
| SSH | **TCP** | Interactive bytes must arrive, in order |
| Email (SMTP) | **TCP** | Delivery guarantees required |
| DNS lookups | **UDP** (port 53) + TCP fallback | Single tiny query/response; retry cheaply by re-asking; TCP for truncation/zone transfers |
| Video streaming / calls (RTP/WebRTC) | **UDP** | Late frame ≈ lost frame; prefer newest data over complete history |
| Online gaming | **UDP** | State updates stale in ms; TCP retransmit would deliver yesterday's position |
| QUIC / HTTP/3 | **UDP** (transport rebuilt in userspace) | TCP's in-kernel design couldn't evolve: HOL blocking + handshake cost + middlebox ossification |

**QUIC in one line:** a TCP successor tunneled over UDP — user-space retransmission, per-stream independence (no cross-stream HOL), crypto integrated into the handshake (1-RTT, 0-RTT resumption), and connection IDs that survive network changes (Wi-Fi → LTE).

### Head-of-line blocking at the transport level

TCP is a single ordered byte stream. One lost segment stalls **everything** behind it, even data the app could perfectly use now:

```text
HTTP/2 multiplexes requests into streams over ONE TCP connection:

streams:   A1  B1  A2  B2  A3  B3 ...
TCP seq:   [ok][ok][LOST·····][held][held]
                         │
app sees:  A1  B1  ✗ all streams stall until retransmit lands
                        (A3/B3 were fine — blocked anyway)
```

This is why HTTP/2's multiplexing gains evaporate on lossy links, and it is the single most-cited technical reason QUIC exists: QUIC tracks offsets **per stream**, so a lost packet only blocks its own stream.

Note the sibling problem inside HTTP/1.1: requests on one connection are strictly serial, so one slow response head-of-line-blocks the queue too. Keep-alive fixes connection cost, not queuing order — hence browsers open parallel connections and proxies matter.

### Connection economics: reuse, keep-alive, pooling

Handshake costs compound. At 50 ms RTT to a typical cloud peer:

| Scenario | Cost before first useful byte |
| ---------------------------- | ----------------------------- |
| Fresh TCP only | 1 RTT = 50 ms |
| Fresh TCP + TLS 1.2 | 3 RTT = 150 ms |
| Fresh TCP + TLS 1.3 | 2 RTT = 100 ms |
| Reused keep-alive connection | 0 RTT (already established) |

Multiply by QPS and the case closes itself:

- **Keep-alive** (`Connection: keep-alive`, HTTP/1.1 default): hold connections open across requests.
- **Pooling** on the server side: outbound connection pools (HTTP agents, DB pools) cap concurrency AND amortize handshakes. Pool exhaustion is backpressure made visible.
- **Server-side residue:** every closed TCP connection lingers ~2 minutes in `TIME_WAIT` on the closer's side; connection-per-request under load exhausts ephemeral ports — the classic "cannot assign requested address" outage.

### TLS rides on TCP

TLS is an application-layer protocol sitting **on top of** the transport, not inside it:

```text
┌─────────────────────────────┐
│ HTTP (request/response)     │  application
├─────────────────────────────┤
│ TLS (records, cipher, certs)│ ← rides on TCP like any other payload
├─────────────────────────────┤
│ TCP (reliability, ordering) │  transport
├─────────────────────────────┤
│ IP                          │  network
└─────────────────────────────┘
```

Practical implications: TLS inherits TCP's handshake latency (why TLS 1.3 collapsed rounds and QUIC fused crypto with transport handshake), and terminating TLS early at a proxy is possible without losing TCP reachability. For ciphers, certificates, and key exchange mechanics, see [Encryption](../../../20-backend/20.5-security/03-hardening-and-operations/20.5.3.01-encryption.md).

### L4 vs L7 load balancing implication

A load balancer can only route on what its layer can read:

- **L4 balancer** sees the TCP/UDP 4-tuple only — it can hash/spread connections but cannot route by URL, cookie, or header, and it need not terminate TCP (it can NAT packets straight through).
- **L7 balancer/proxy** must fully terminate TCP (and usually TLS) to parse HTTP — buying smart routing at the price of connection handling CPU and added latency.

So the LB-type decision is literally a transport-knowledge decision: high-throughput raw TCP/WebSocket fan-out → L4; content-based routing, retries, buffering, rate limiting → L7. Full treatment in [Load Balancing](30.2.1.04-load-balancing.md).

## Code Examples

Measuring what a fresh connection actually costs (Node.js):

```typescript
import net from "node:net";

function measureConnect(host: string, port: number): Promise<number> {
  const start = process.hrtime.bigint();
  return new Promise((resolve, reject) => {
    const socket = net.connect({ host, port });
    socket.once("connect", () => {
      // elapsed = SYN → SYN-ACK → ACK: roughly 1 RTT
      resolve(Number(process.hrtime.bigint() - start) / 1e6);
      socket.destroy();
    });
    socket.once("error", reject);
  });
}

// Run twice against the same host:
// first ≈ full handshake RTT, second ≈ same (no reuse — net.connect
// opens a NEW socket each time; this is exactly the waste pooling removes)
measureConnect("example.com", 443).then((ms) => console.log(`connect #1: ${ms.toFixed(1)} ms`));
measureConnect("example.com", 443).then((ms) => console.log(`connect #2: ${ms.toFixed(1)} ms`));
```

Keep-alive + pooling for outbound HTTP (the fix):

```typescript
import http from "node:http";
import { Agent } from "node:http";

// One pool per upstream; sockets are reused across requests.
const agent = new Agent({
  keepAlive: true,
  maxSockets: 50,        // cap concurrency → natural backpressure
  maxFreeSockets: 10,    // idle pool kept warm
  scheduling: "lifo",    // reuse hottest sockets, let extras die
});

const req = http.request(
  { host: "upstream.internal", path: "/api", agent },
  (res) => res.resume(),
);
req.end();
// Every request after the first skips SYN + TLS entirely.
```

Raw UDP datagrams — everything TCP does for free is now your job:

```typescript
import dgram from "node:dgram";

const socket = dgram.createSocket("udp4");

socket.on("message", (msg, rinfo) => {
  console.log(`got ${msg.length}B from ${rinfo.address}:${rinfo.port}`);
  // No ack needed — but did the peer get OUR reply? Unknown.
  // No ordering — datagram 2 may land before datagram 1.
});

socket.bind(53, () => {
  const query = Buffer.from("a dns-shaped query");
  socket.send(query, 53, "8.8.8.8", (err) => {
    if (err) console.error("send failed:", err);
  });
});
```

A tiny application-level retry wrapper (what "reliability over UDP" means in practice):

```typescript
async function sendReliable(
  send: (payload: Buffer) => void,
  makePayload: (seq: number) => Buffer,
  awaitAck: (seq: number, timeoutMs: number) => Promise<void>,
  seq: number,
): Promise<void> {
  let delay = 100;
  for (let attempt = 0; attempt < 5; attempt++) {
    send(makePayload(seq));
    try {
      await awaitAck(seq, 500);   // UDP gave us nothing — we built:
      return;                     // acks + timeout + exponential backoff,
    } catch {                     // i.e., a worse TCP
      await new Promise((r) => setTimeout(r, delay));
      delay *= 2;
    }
  }
  throw new Error(`datagram ${seq} unconfirmed after 5 attempts`);
}
```

## Real-World Use Cases

### 1. Database connection pooling (PgBouncer)

Postgres connections are expensive TCP sessions (process per connection + auth + slow-start warmup). PgBouncer sits in front, holds a warm pool, and multiplexes thousands of client connections onto dozens of server connections — converting per-request handshake cost into amortized zero.

### 2. DNS resolvers choosing UDP

A lookup is one small question deserving one small answer; a fresh TCP handshake would triple latency for the world's most-issued query. Resolvers use UDP and treat loss as "ask again"; they escalate to TCP when responses truncate or payloads exceed legacy size limits.

### 3. Video conferencing over WebRTC

A 200 ms-old video frame is worthless. WebRTC runs RTP over UDP, drops late frames, and lets encoders react to loss signals — accepting visible glitches rather than TCP-style pauses that would desync audio/video.

### 4. Multiplayer game state sync

Servers broadcast position ticks at 20–60 Hz over UDP. A dropped tick is simply superseded by the next; retransmitting it would deliver stale state. Client-side prediction + server reconciliation replace TCP's guarantees with domain-specific ones.

### 5. The CDN/edge migration to HTTP/3

Large CDNs enable QUIC because mobile users lose packets constantly: per-stream independence removes HOL stalls, 0-RTT resumption shaves a full RTT off repeat visits, and connection IDs survive Wi-Fi↔cellular switches mid-transfer.

## Interview Traps

| Trap | What they're testing | Strong answer spine |
| ---------------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Walk me through what happens when you type a URL" — the transport leg | Do you know where the network ends and the app begins? | DNS (usually UDP) → TCP 3-way handshake (1 RTT) → TLS handshake (TLS 1.3: +1 RTT) → HTTP request on the warm connection. Quote RTTs, not vibes. |
| "Why does HTTP/3 use UDP?" | Do you understand WHY, not just THAT? | Not "UDP is faster" — UDP is just a carrier. Real reasons: TCP HOL blocking vs multiplexing, handshake+TLS round trips, kernel/middlebox ossification blocking TCP evolution. QUIC reimplements reliable ordered streams per-stream, in userspace. |
| "Is UDP always faster than TCP?" | Precision | No — for large reliable transfers, well-tuned TCP matches or beats naive UDP+custom-retry. UDP wins when loss tolerance or custom reliability beats generic TCP behavior. |
| "Your API has 300 ms TTFB to a far region. Fix it." | Connection economics | Keep-alive/pooling, TLS session resumption, edge PoP to cut RTT, HTTP/3 0-RTT — in that order of bang/buck. |
| "Why do we see TIME_WAIT alerts during traffic spikes?" | Lifecycle details | Connection-per-request burns ephemeral ports; each closed connection parks ~2 min in TIME_WAIT. Fix: reuse (agents/pools), not aggressive tuning. |

## Common Mistakes

| Mistake | Consequence | Fix |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Opening a new connection per request | +2–3 RTT per call, slow start every time, TIME_WAIT/port exhaustion | Keep-alive agents + bounded pools |
| "It works locally" assumptions in prod | localhost RTT ≈ 0.05 ms hides 100× latency cliffs | Budget RTT explicitly in designs |
| Assuming TCP preserves *message* boundaries | `recv()` returns arbitrary chunks; framing bugs | Length-prefix or delimiter-frame the stream yourself |
| Choosing UDP "for speed" then rebuilding TCP badly | Worse-than-TCP reliability with more bugs (your retry logic vs decades of kernel tuning) | Choose UDP only when loss-tolerance or custom control is real; otherwise use QUIC libraries |
| Ignoring congestion control on UDP floods | Self-inflicted packet collapse, ISP throttling | Pace sends; borrow CC algorithms (e.g., via QUIC stacks) |
| Treating zero-window/rwnd as a bug | Fighting the transport's backpressure causes OOM upstream | Read it as the receiver saying "slow down" — same lesson as [Backpressure & Flow Control](30.2.1.13-backpressure-and-flow-control.md) |
| Nagle + delayed-ACK interaction on chatty protocols | Mysterious 40–200 ms latency spikes | `TCP_NODELAY` for latency-sensitive small writes |

## Best Practices

1. **Reuse connections everywhere**: HTTP agents with keep-alive, DB pools, sticky upstream sessions at the proxy.
2. **Quote RTT arithmetic in interviews** — "fresh TCP+TLS 1.3 = 2 RTT, so at 60 ms that's 120 ms before the first byte" instantly separates senior from junior.
3. **Default to TCP for anything that must be correct; default to UDP only when staleness beats completeness.**
4. **Prefer QUIC libraries over DIY UDP reliability** — retransmission and congestion control are deceptively deep problems.
5. **Set `TCP_NODELAY` on latency-sensitive request/response paths**; batch deliberately instead of letting Nagle batch accidentally.
6. **Size pools deliberately**: pool limit = concurrency limit = backpressure point; monitor wait-time-on-pool, not just errors.
7. **When designing protocols over UDP, plan for MTU** — keep datagrams under ~1200 bytes to avoid fragmentation across tunnels (this constraint shaped QUIC's packet design).

## Summary

The transport layer chooses your guarantees above IP's best-effort delivery. TCP buys a reliable ordered byte stream with a 1-RTT handshake, seq/ack retransmission, receive-window flow control (the original backpressure), and slow-start/AIMD congestion control — paying in latency, head-of-line blocking, and connection-management overhead that keep-alive and pooling amortize. UDP buys near-nothing — an 8-byte-header datagram with no handshake, ordering, or retry — which is exactly right for loss-tolerant realtime traffic and as substrate for QUIC, which rebuilds TCP semantics per-stream in userspace to kill HOL blocking and fuse TLS into a 1-RTT handshake. Load balancer layers map directly onto this knowledge: L4 routes blind tuples, L7 must terminate the connection to think. Master the handshake arithmetic and the QUIC rationale, and the transport leg of any system design answer is yours.

• 8-byte header · no handshake/ordering/retry/congestion ctrl

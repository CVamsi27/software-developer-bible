# TCP & UDP Transport Fundamentals

TCP and UDP are the main transport protocols used by Internet applications. TCP provides a reliable, ordered byte stream. UDP sends independent datagrams without built-in delivery, ordering, or congestion control. QUIC uses UDP as its network carrier and adds its own streams, reliability, flow control, and congestion control.

## Definition

The transport layer carries data between application endpoints, using addresses and port numbers to identify transport endpoints. IP provides best-effort packet delivery. Transport protocols add different guarantees and controls:

> **Textbook Definition:** Transmission Control Protocol (TCP) provides a reliable, ordered byte stream between endpoints. User Datagram Protocol (UDP) provides independent datagrams without transport-level guarantees of delivery, ordering, or duplicate suppression.

```text
┌───────────────────────────────────────────────────────────┐
│  Application protocols HTTP · SSH · DNS · SMTP · gRPC     │
├───────────────────────────────────────────────────────────┤
│  Transport layer      TCP (reliable stream)               │
│                       UDP (datagram transport)            │
├───────────────────────────────────────────────────────────┤
│  Network layer        IP — best-effort packet delivery    │
├───────────────────────────────────────────────────────────┤
│  Link layer           Ethernet · Wi-Fi · fiber · cellular │
└───────────────────────────────────────────────────────────┘
```

| Property | TCP | UDP |
| ------------------ | --------------------------------- | ------------ |
| Unit | Byte stream (segments) | Datagram |
| Connection | Handshake required | None |
| Reliability | Retransmits lost data | Lost is lost |
| Ordering | In-order delivery | None |
| Flow control | Receive window | None |
| Congestion control | Slow start / AIMD | None |
| Header size | 20–60 bytes, depending on options | 8 bytes |

## First Principles

Transport choice follows from what each protocol promises:

1. **TCP adds a reliable, ordered stream.** Sequence numbers, acknowledgments, retransmission, flow control, and congestion control make a byte stream useful to applications. The application still needs message framing and operation-level error handling.
2. **UDP leaves these choices to the application protocol.** This suits some real-time traffic that can discard stale updates. Applications using UDP still need congestion control and may add reliability, ordering, or security.
3. **The design question is which transport contract fits the application.** QUIC uses UDP packets but defines reliable, flow-controlled streams and congestion control; HTTP/3 uses QUIC to avoid TCP's cross-stream head-of-line blocking and to integrate TLS 1.3.

## Why It Matters

1. **Handshakes add round trips.** Their cost depends on connection reuse, TLS version, resumption, and where the endpoints are.
2. **TCP does not preserve application messages.** The receiver sees a stream of bytes; the application defines message boundaries.
3. **A load balancer's layer limits what it can inspect.** A transport-level balancer can use IP and port information; HTTP-aware routing needs access to HTTP metadata.
4. **Flow control and congestion control protect different resources.** TCP's receive window protects the receiver; its congestion window limits pressure on the network.
5. **QUIC changes stream and connection behavior.** Understanding its differences from TCP helps explain HTTP/3 without claiming UDP itself is more reliable or faster.

## How It Works

### Where transport sits

IP routes packets between hosts; port numbers direct transport data to processes. A TCP connection is commonly identified by its source and destination IP addresses and ports (the 4-tuple). A transport-level load balancer can route using network and transport metadata; it cannot read encrypted HTTP paths or headers.

### The TCP three-way handshake

In the ordinary handshake without TCP Fast Open, both sides synchronize initial sequence numbers before the established byte stream carries application data:

```text
CLIENT                                   SERVER
  │                                         │
  │── SYN, seq=x ─────────────────────────►│   ① client wants to talk
  │                                         │
  │◄─ SYN-ACK, seq=y, ack=x+1 ─────────────│   ② server agrees + picks its seq
  │                                         │
  │── ACK, ack=y+1 ────────────────────────►│   ③ client confirms server's seq
  │                                         │
  │═══════ connection ESTABLISHED ═════════│
  │── [PSH, ACK] GET / HTTP/1.1 ───────────►│   now app data may flow
```

Why three ways? The exchange synchronizes **two independent sequence numbers** (x for client→server, y for server→client). Two segments would leave the server unsure the client received its SYN-ACK.

**Cost accounting (the interview-relevant part):**

- The TCP handshake normally takes **1 RTT** before application protocols can proceed.
- A full TLS 1.2 handshake typically adds **2 RTTs**; a full TLS 1.3 handshake typically adds **1 RTT**. Resumption and early data change the exchange; TLS 1.3 0-RTT data has replay risks.
- At an illustrative 70 ms RTT, a new TCP + full TLS 1.3 connection takes about 140 ms in handshakes before the HTTP request/response round trip. DNS, processing, and queueing add more. Reuse and pooling avoid paying a fresh handshake for each request.

### Reliability mechanics

**Sequence numbers & acknowledgments.** Every byte is numbered. The receiver acks the next byte it expects (cumulative ack). Missing range → sender retransmits:

```text
Sender sends:      [1-100] [101-200] [201-300] [301-400] [401-500] [501-600]
Receiver gets:      ok      ok        LOST      held*      held*      held*
Receiver acks:              ack=201   ack=201   ack=201    ack=201    ack=201
                                     ▲
The sender may infer loss from duplicate acknowledgements or other signals,
then retransmit the missing range; recovery depends on TCP mechanisms.
```

*Bytes beyond a gap are usually buffered but cannot be delivered to the app until the hole fills — this is the seed of transport-level head-of-line blocking.

**Flow control (protect the receiver).** The receiver advertises a window (`rwnd`) = free buffer space. Sender may have at most `rwnd` unacknowledged bytes in flight. As the app reads data, the window slides open. A zero window pauses ordinary new data; bounded window probes can check whether the receiver reopened it. This is transport backpressure (see [Backpressure & Flow Control](30.2.1.13-backpressure-and-flow-control.md)).

**Congestion control (protect the network).** Independent of rwnd, the sender keeps a congestion window (`cwnd`):

- **Slow start:** `cwnd` grows quickly while the sender probes available capacity; the initial value and growth rules depend on implementation and standards.
- **Congestion avoidance:** classic TCP Reno uses additive increase and multiplicative decrease. Modern congestion-control algorithms can behave differently.

```text
cwnd
 │                    ／﹨            ／
 │                 ／﹨   ﹨halve   ／  ← AIMD sawtooth
 │             ／﹨        ﹨     ／
 │        ／﹨              ﹨＿／
 │   ／﹨  ← loss event
 │／   ssthresh ──────────────────────────────
 └──────────────────────── time (RTTs) ─────►
   classic idealized slow start (~×2/RTT); Reno avoidance (~+1 MSS/RTT)
```

Consequence: **connection reuse can avoid repeatedly restarting congestion-control state** — one more reason to reuse connections instead of paying slow start per request.

### The UDP datagram model

UDP has an 8-byte header (source port, destination port, length, checksum) over IP. It does not provide a connection handshake, ordering, retransmission, flow control, or congestion control. Checksum rules differ between IPv4 and IPv6.

What you gain: no transport handshake and independent datagrams. A lost datagram does not block delivery of a later datagram at the UDP layer. The application protocol chooses what additional behavior is needed.

What you accept: datagrams can be lost, duplicated, or reordered. Any application that sends at scale must use an appropriate congestion-control and pacing strategy.

### TCP vs UDP decision table

| Workload | Protocol | Why |
| -------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| HTTP/1.1, HTTP/2 | **TCP** | Correctness > latency; streams benefit from reliability |
| Database connections (Postgres, MySQL) | **TCP** | Ordered reliable stream; the database protocol handles query framing and responses |
| SSH | **TCP** | Interactive bytes must arrive, in order |
| Email (SMTP) | **TCP** | SMTP uses a reliable ordered stream for commands and replies |
| DNS lookups | Often **UDP**; TCP is also required and used for cases such as truncation | Small queries commonly fit in a datagram; clients follow DNS retry and transport rules |
| Real-time media (RTP/WebRTC) | Often **UDP** | Applications can prioritize timely media and adapt to loss; deployment details vary |
| Video file or on-demand streaming | **TCP or QUIC** are common | Reliable delivery is useful; transport and application buffering shape playback |
| Online gaming | Often **UDP** for time-sensitive state | Some updates can be superseded, but the game protocol defines reliability and congestion behavior |
| QUIC / HTTP/3 | **QUIC over UDP** | QUIC defines streams, reliability, flow control, congestion control, and connection migration |

**QUIC in one line:** a secure transport over UDP with independently ordered streams, flow control, loss recovery, congestion control, and connection migration. A typical handshake can complete in 1 RTT; 0-RTT early data can be replayed, so use it only for operations safe under replay.

### Head-of-line blocking at the transport level

TCP is a single ordered byte stream. One lost segment stalls **everything** behind it, even data the app could perfectly use now:

```text
HTTP/2 multiplexes requests into streams over ONE TCP connection:

streams:   A1  B1  A2  B2  A3  B3 ...
TCP seq:   [ok][ok][LOST·····][held][held]
                         │
app sees:  A1  B1  ✗ all streams stall until retransmit lands
                        (A3/B3 were fine — blocked anyway)
```

This is one reason HTTP/3 uses QUIC: a lost packet carrying data for one stream does not block delivery of data for every other stream. The connection still has shared congestion control, and loss can affect overall throughput.

HTTP/1.1 pipelining can also cause response-order head-of-line blocking. Keep-alive avoids reconnecting but does not remove every ordering or queueing delay.

### Connection economics: reuse, keep-alive, pooling

For an illustrative 50 ms RTT, ignoring DNS, processing, loss, and TLS resumption:

| Scenario | Connection setup before application data |
| ---------------------------- | ---------------------------------------- |
| Fresh TCP only | 1 RTT = 50 ms |
| Fresh TCP + full TLS 1.2 | Typically 3 RTT = 150 ms |
| Fresh TCP + full TLS 1.3 | Typically 2 RTT = 100 ms |
| Reused keep-alive connection | 0 RTT (already established) |

- **Keep-alive**: reuse a persistent HTTP/1.1 connection across requests; HTTP/1.1 connections are persistent by default unless closed.
- **Pooling** on the server side: outbound connection pools reuse connections and bound open sockets. Callers may queue when the pool is full, so monitor pool wait time as well as errors.
- **Connection churn:** the endpoint that performs the active close can retain a connection in `TIME_WAIT` for an implementation-dependent interval. High churn can contribute to port and resource pressure; reuse connections and inspect the platform before tuning timers.

### TLS rides on TCP

For common HTTPS-over-TCP, TLS runs above TCP and below HTTP. Network-stack diagrams do not always map exactly to OSI layers:

```text
┌──────────────────────────────────┐
│ HTTP (request/response)          │  application
├──────────────────────────────────┤
│ TLS (records, keys, certificates)│
├──────────────────────────────────┤
│ TCP (reliability, ordering)      │  transport
├──────────────────────────────────┤
│ IP                               │  network
└──────────────────────────────────┘
```

TLS handshake messages travel over TCP and add round trips on a fresh connection. QUIC integrates TLS 1.3 key negotiation with its transport handshake. A proxy that terminates TLS becomes a separate secure endpoint for each connection it handles. For certificates and key exchange, see [Encryption](../../../20-backend/20.5-security/03-hardening-and-operations/20.5.3.01-encryption.md) and [TLS, HTTPS & the Certificate Lifecycle](30.2.1.23-tls-https-and-certificates.md).

### L4 vs L7 load balancing implication

A load balancer can only route on what its layer can read:

- **Transport-level balancer** routes using IP and transport metadata. It cannot inspect HTTP paths, cookies, or headers inside encrypted traffic.
- **HTTP-aware proxy** needs access to HTTP metadata. For HTTPS path/header routing, it generally terminates TLS and becomes a separate secure endpoint; SNI-based routing can work without decrypting HTTP.

Choose a transport-level balancer when network/transport metadata is sufficient. Use an HTTP-aware proxy when paths, headers, cookies or HTTP policy affect routing. WebSocket deployments can use either: the required upgrade routing and session policy determine the choice. Full treatment in [Load Balancing](30.2.1.04-load-balancing.md).

## Code Examples

Measuring connection establishment time (Node.js):

```typescript
import net from "node:net";

function measureConnect(host: string, port: number, timeoutMs = 5000): Promise<number> {
  const start = process.hrtime.bigint();
  return new Promise((resolve, reject) => {
    const socket = net.connect({ host, port });
    const timer = setTimeout(() => socket.destroy(new Error("connect deadline exceeded")), timeoutMs);
    socket.once("close", () => clearTimeout(timer));
    socket.once("connect", () => {
      // elapsed = SYN → SYN-ACK → ACK: roughly 1 RTT
      resolve(Number(process.hrtime.bigint() - start) / 1e6);
      socket.destroy();
    });
    socket.once("error", reject);
  });
}

// This measures socket connection establishment, not TLS or an HTTP request.
// Name resolution may be included when the host needs resolving.
measureConnect("example.com", 443).then((ms) => console.log(`TCP connect: ${ms.toFixed(1)} ms`));
```

Keep-alive and a finite pool for outbound HTTP:

```typescript
import http from "node:http";
import { Agent } from "node:http";

// Illustrative Node HTTP/1.1 agent configuration; check your Node version
// and the upstream's connection limits before choosing these values.
const agent = new Agent({
  keepAlive: true,
  maxSockets: 50,        // caps sockets; excess requests may wait for one
  maxFreeSockets: 10,    // idle pool kept warm
  scheduling: "lifo",    // reuse hottest sockets, let extras die
});

const req = http.request(
  { host: "upstream.internal", path: "/api", agent },
  (res) => res.resume(),
);
req.end();
// This plain-http example reuses TCP only. An HTTPS agent additionally
// reuses its established TLS connection; both still need timeout/error handling.
```

Raw UDP preserves datagram boundaries. Run a peer listening on localhost port9999 to receive this illustrative payload; the sender alone supplies no receiver or delivery confirmation. Stop the open socket after the experiment. This is not a DNS client:

```typescript
import dgram from "node:dgram";

const socket = dgram.createSocket("udp4");

socket.on("message", (msg, rinfo) => {
  console.log(`got ${msg.length}B from ${rinfo.address}:${rinfo.port}`);
  // No ack needed — but did the peer get OUR reply? Unknown.
  // No ordering — datagram 2 may land before datagram 1.
});

socket.bind(() => {
  const payload = Buffer.from("example datagram");
  socket.send(payload, 9999, "127.0.0.1", (err) => {
    if (err) console.error("send failed:", err);
    // No error means the local send completed; it does not prove the peer received it.
  });
});
```

If an application needs reliable messages over UDP, it must define message IDs, acknowledgments, duplicate suppression, timeouts, bounded retries, congestion control, and security. This is complex; use a maintained protocol such as QUIC unless a different datagram behavior is a real requirement.

## Real-World Use Cases

### 1. Database connection pooling (PgBouncer)

PostgreSQL clients use TCP connections. PgBouncer can pool server connections and reduce direct database sessions, depending on pooling mode and application behavior. Pooling does not make database work free; understand transaction and session-state compatibility.

### 2. DNS resolvers choosing UDP

DNS commonly uses UDP for queries that fit in a datagram. DNS also uses TCP, including for truncated responses and zone transfers. Resolver behavior follows DNS protocol rules and configuration; it is not simply “UDP, then retry the same query.” The naming system itself — hierarchy, TTL, and why DNS failover is slow — is covered in [DNS & Name Resolution](30.2.1.22-dns-and-name-resolution.md).

### 3. Video conferencing over WebRTC

Real-time media can prefer a newer frame over retransmitting an obsolete one. RTP is commonly carried over UDP in WebRTC, while congestion control, encryption, packet recovery, and media adaptation are handled by the broader WebRTC stack.

### 4. Multiplayer game state sync

Some games send time-sensitive state over UDP because a later update can replace an older one. Update frequency and recovery rules depend on the game; client prediction and server reconciliation are application techniques, not UDP guarantees.

### 5. The CDN/edge migration to HTTP/3

CDNs and browsers support QUIC for HTTP/3's stream-level loss isolation and connection migration. 0-RTT can reduce setup delay for eligible resumed connections, but early data may be replayed and should be restricted to safe operations.

## Common Mistakes

| Mistake | Consequence | Fix |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Opening a new connection per request | Repeats connection setup and increases socket churn | Reuse connections where the protocol and workload allow it |
| Treating local timing as a production estimate | Local and remote paths have different latency, loss, and queueing | Measure from representative locations and include the full request path |
| Assuming TCP preserves *message* boundaries | `recv()` returns arbitrary chunks; framing bugs | Length-prefix or delimiter-frame the stream yourself |
| Choosing UDP "for speed" then rebuilding TCP badly | Worse-than-TCP reliability with more bugs (your retry logic vs decades of kernel tuning) | Choose UDP only when loss-tolerance or custom control is real; otherwise use QUIC libraries |
| Ignoring congestion control on UDP floods | Self-inflicted packet collapse, ISP throttling | Pace sends; borrow CC algorithms (e.g., via QUIC stacks) |
| Treating zero-window/rwnd as a bug | Fighting the transport's backpressure causes OOM upstream | Read it as the receiver saying "slow down" — same lesson as [Backpressure & Flow Control](30.2.1.13-backpressure-and-flow-control.md) |
| Disabling Nagle without measuring | More small packets and overhead; latency may not improve | Measure the application path; use `TCP_NODELAY` only when small-write delay is a demonstrated problem |

---

## Best Practices

1. **Reuse connections when useful**, and bound pools so they do not overwhelm the upstream.
2. **Show the assumptions in RTT arithmetic.** Distinguish TCP setup, TLS setup, request/response, DNS, and server processing; resumption changes the handshake.
3. **Choose a transport from the application contract.** UDP alone does not provide reliability or congestion control.
4. **Use a maintained QUIC implementation** when QUIC behavior is needed; do not recreate it casually.
5. **Measure before tuning socket options** such as `TCP_NODELAY`.
6. **Monitor pool wait time and connection churn** in addition to request errors.
7. **Respect path MTU and QUIC's packetization rules.** A universal payload size is not safe across all network paths.

## Summary

TCP provides a reliable ordered byte stream with retransmission, receiver flow control, and network congestion control. It costs connection setup and can block delivery of later bytes behind a lost segment. UDP provides datagrams with no built-in delivery, ordering, flow control, or congestion control. QUIC runs over UDP and supplies secure, reliable streams with transport-level flow and congestion control. Connection reuse and TLS resumption can reduce setup work. A network-level load balancer can route on network and transport metadata; HTTP-aware routing needs access to HTTP data.

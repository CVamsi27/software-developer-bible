# DNS & Name Resolution

When an application connects to `api.example.com`, it needs an IP address. DNS (the Domain Name System) looks up that name and returns typed records. Caching makes repeat lookups faster, but it also means a change may take time to reach every client.

## Definition

DNS is a distributed naming system. A **zone** is a part of the namespace served by an authority. A **record** stores one kind of information about a name. A **stub resolver** sends a lookup to a **recursive resolver**; that resolver finds the answer and may cache it.

> **Textbook Definition:** The Domain Name System (DNS) is a hierarchical, distributed naming system that resolves names to typed resource records through authoritative servers and caching resolvers.

```text
┌──────────────────────────────────────────────────────────────────────┐
│  STUB RESOLVER        the OS/library on your machine (no brain)      │
│  e.g. getaddrinfo() → sends ONE question to a configured resolver    │
├──────────────────────────────────────────────────────────────────────┤
│  RECURSIVE RESOLVER   does the walking + caches (ISP, 8.8.8.8,       │
│                       Cloudflare 1.1.1.1, your VPC resolver)         │
├──────────────────────────────────────────────────────────────────────┤
│  ROOT SERVERS         know where each TLD lives (.com, .io, .de)     │
│        └── TLD SERVERS        know the authoritative NS for example  │
│               └── AUTHORITATIVE  holds YOUR zone's records — the     │
│                   NAMESERVERS    only source of truth for the zone   │
└──────────────────────────────────────────────────────────────────────┘
```

| Component | What it does |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Stub resolver | Sends the application's lookup to a configured recursive resolver. The OS or runtime may also consult local sources such as a hosts file. |
| Recursive resolver | Finds the answer, following referrals when needed, and caches records according to their TTLs. |
| Root nameserver | Refers the resolver to the nameservers for a top-level domain such as `.com`. |
| TLD nameserver | Refers the resolver to the authoritative nameservers for a domain. |
| Authoritative nameserver | Returns the records configured for the zones it serves. |

On a cache miss, the recursive resolver follows referrals until it reaches an authoritative answer. On a cache hit, it can answer without repeating that walk. The operating system or application may also reuse answers, depending on its resolver.

## First Principles

DNS handles four practical needs:

1. **Names can stay stable while infrastructure changes.** Clients use a name; DNS lets operators change which addresses that name returns.
2. **The namespace is delegated.** Root, top-level-domain, and authoritative servers each handle different parts of the lookup.
3. **Repeated lookups should be cheap.** Resolvers cache answers for a limited time, called the **TTL (time to live)**.
4. **A cached answer can be old.** A record change affects authoritative data first. Caches that already hold the old answer may keep using it until it expires; active connections can last longer still.

## Why It Matters

1. **Deploys and failovers:** TTLs and client connection behavior affect how quickly traffic moves.
2. **Latency:** a cache miss can add DNS lookup time before a connection begins ([TCP & UDP Transport Fundamentals](30.2.1.21-tcp-udp-transport-fundamentals.md)).
3. **Traffic steering:** DNS can return different addresses, but caching and resolver location limit how precisely it steers.
4. **Security:** DNSSEC lets resolvers validate signed DNS data; it does not encrypt lookups. DoH and DoT encrypt the resolver connection but do not prove that the returned address is a safe application.

## How It Works

### The resolution walk

A cold lookup for `api.example.com` from a laptop:

```text
STUB           RECURSIVE (1.1.1.1)        ROOT            TLD (.com)      AUTHORITATIVE
 │                    │                    │                 │                 │
 │─ api.example.com ─►│                    │                 │                 │
 │                    │─ .com? ───────────►│                 │                 │
 │                    │◄─ NS for .com ─────│                 │                 │
 │                    │─ example.com? ─────────────────────►│                 │
 │                    │◄─ NS ns1.example.com ───────────────│                 │
 │                    │─ api.example.com? ───────────────────────────────────►│
 │                    │◄─ A 203.0.113.10 (TTL 60) ─────────────────────────────│
 │◄─ 203.0.113.10 ────│   (caches for 60 s, plus NS glue)     │                 │
 │  (OS caches too)   │                    │                 │                 │
```

Warm lookup: stub → recursive → cached answer. The recursive resolver does not need to contact other DNS servers; the stub still needs to reach it unless the local system already has the answer.

Two practical consequences:

- **Cache locality is a real performance feature.** Run a resolver near your workloads (VPC resolver, node-local DNS cache) or every cold lookup pays the walk.
- **A recursive resolver can reuse cached records** for many clients until their TTLs expire.

### Record types you must know

| Record | Maps | Use it for | Notes |
| ------------------- | ----------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| `A` | name → IPv4 | The main address record | Can appear many times (round-robin) |
| `AAAA` | name → IPv6 | Dual-stack | Absent `AAAA` means IPv4-only, not "broken" |
| `CNAME` | name → another **name** | Aliases, pointer to a cloud provider hostname | Illegal at the zone apex (must not coexist with `NS`/`SOA`) |
| `NS` | zone → nameservers | Delegation and subzone handoff | The mechanism that makes DNS a hierarchy |
| `MX` | domain → mail hosts | Email delivery routing | Takes priority numbers |
| `TXT` | name → arbitrary strings | Verification, `SPF`, `DKIM`, `DMARC`, app config | Free-form; abused as a poor DB |
| `SRV` | `_service._proto` → host:port | Service discovery (older systems) | Port + priority + weight |
| `SOA` | zone → authority metadata | Zone identity; sets **negative-cache TTL** | The TTL here governs NXDOMAIN caching |
| `CAA` | domain → allowed CAs | Restrict who may issue your certs | Enforced by CAs, not by DNS |
| `PTR` | IP → name | Reverse DNS (logs, mail reputation) | Lives under `in-addr.arpa` / `ip6.arpa` |

**Try it yourself:** `dig api.example.com +noall +answer` shows the record and its remaining TTL; repeating the command shows the TTL counting down from *your* resolver's cache, not from the authoritative server.

### TTL controls how long a cached answer can be reused

TTL is the number of seconds a resolver may cache a record. A shorter TTL can reduce the time clients use an old answer after expiry, while increasing lookup traffic. It does not guarantee that every client refreshes at that exact time.

| Choice | Effect | Considerations |
| ----------- | -------------------------------------- | --------------------------------------------------- |
| Shorter TTL | Caches can refresh sooner after expiry | More queries; existing connections may remain open |
| Longer TTL | Fewer repeat lookups | Old answers may remain cached longer after a change |

For a planned migration, lower the TTL well before the cutover and wait at least the previous TTL before switching. Confirm that the new target works, keep the old target available while clients may still use it, and define how to roll back. A TTL change does not shorten answers already cached under the previous TTL.

### Negative caching and the NXDOMAIN trap

Resolvers can cache negative answers such as NXDOMAIN (the name does not exist). The response's SOA information supplies the negative-cache lifetime under DNS rules. Two practical consequences:

- Create the record *before* pointing clients at it, or a client's cached NXDOMAIN will keep failing even once the record exists.
- Some resolvers ignore very low negative TTLs and apply their own floor, so an outage can outlive your intent.

### DNS as a load balancer

Because one name may return many answers, DNS can distribute traffic:

| Strategy | How it works | Honest limitation |
| -------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Round-robin | Return all `A` records rotated | No health awareness; clients may get a dead one |
| Weighted | Return subsets by configured weight | Coarse; cached for the TTL, so reweighting is slow |
| Latency / geo | Resolver's region steers to the nearest entry point | Depends on resolver location being a proxy for user location (EDNS Client Subnet improves this, and privacy-minded resolvers may ignore it) |
| Failover | Health checks influence which answers are returned | Detection, caching, client behavior, and open connections all affect when traffic moves |
| Anycast | Many servers announce the *same* IP | Routing magic, not records — the basis of CDN and root-server resilience |

**Why DNS-based failover is not instant:** cached answers may remain in use until expiry, clients do not all refresh at the same time, and open connections keep using their existing destination. Pair DNS changes with health checks and retry behavior; test actual recovery time instead of assuming a fixed propagation time.

### Anycast, DoH, and the security layer

- **Anycast** — the same IP announced from many locations, so BGP delivers each client to a nearby instance. This is how root servers, public resolvers, and CDNs get both latency and crude DDoS absorption. It is invisible at the record level.
- **DNS over HTTPS (DoH) / DNS over TLS (DoT)** — encrypts the connection to a resolver. This can prevent local network observers from reading or changing queries, but may conflict with network-managed filtering. Connection reuse means the TLS cost is not necessarily paid for every lookup.
- **DNSSEC** — cryptographic signatures on answers, proving they came from the zone. It provides *integrity*, not *confidentiality*, and is deployed unevenly; validation failures are a classic silent outage.
- **Spoofing and poisoning** — DNSSEC validation can detect forged answers for signed zones. It does not encrypt queries, and unsigned zones do not gain that validation.

### Kubernetes, registries, and the ndots gotcha

Kubernetes configures DNS search domains and options in pod resolver settings. For example, `ndots` controls how many dots a name needs before it is tried as absolute first. With `ndots:5`, some external names may be tried against search suffixes before the absolute name. Check the pod's actual `/etc/resolv.conf`; behavior also depends on the resolver library.

For a frequently queried external name, compare a fully qualified name and a trailing dot in the specific runtime. Do not assume every language resolver applies search domains in the same way.

## Code Examples

Inspecting what your system actually resolves, including the records behind a CDN hostname:

```bash
# Answer + TTL as your resolver sees it
dig api.github.com +noall +answer

# Walk the hierarchy explicitly — root, TLD, then authoritative
dig +trace www.example.com

# Ask a specific authoritative server (bypass every cache)
dig @ns1.example.com www.example.com

# Which resolver am I even using?
scutil --dns 2>/dev/null | head -20 || cat /etc/resolv.conf

# Mail/verification records
dig TXT example.com +short
```

Resolving from application code, distinguishing the resolver path from the hosts-file path:

```typescript
import dns from "node:dns/promises";

// resolve* sends a DNS query and does not use the OS hosts-file lookup path.
const a = await dns.resolve4("api.github.com", { ttl: true });
console.log(a); // [{ address: "140.82.121.6", ttl: 47 }]  ← TTL is remaining, not original

// lookup uses OS name-resolution facilities, including configured sources.
// Use it when you want behavior similar to other programs on this machine.
console.log(await dns.lookup("api.github.com", { all: true }));

// Distinguish a missing name from a name that lacks this record type.
try {
  await dns.resolve4("does-not-exist-xyz.example");
} catch (err) {
  const code = (err as NodeJS.ErrnoException).code;
  console.log(code); // ENOTFOUND (NXDOMAIN) or ENODATA (name exists, no A)
}
```

Measure lookup time in your environment. Repeating a query does not guarantee a cache hit because this Resolver sends DNS queries and caching depends on the resolver it contacts.

```typescript
import { Resolver } from "node:dns/promises";

const resolver = new Resolver({ timeout: 2000, tries: 2 });

async function timeLookup(name: string, label: string) {
  const start = process.hrtime.bigint();
  await resolver.resolve4(name);
  const ms = Number(process.hrtime.bigint() - start) / 1e6;
  console.log(`${label.padEnd(8)} ${name.padEnd(24)} ${ms.toFixed(1)} ms`);
}

await timeLookup("api.github.com", "lookup #1");
await timeLookup("api.github.com", "lookup #2");
```

A TTL-aware in-process cache — the pattern for "I must not re-resolve on every request, but I must also not pin an address forever":

```typescript
type Entry = { address: string; expiresAt: number };

const cache = new Map<string, Entry>();

async function resolveCached(
  hostname: string,
  capMs = 30_000, // never trust a record longer than this, however big its TTL
): Promise<string> {
  const hit = cache.get(hostname);
  if (hit && hit.expiresAt > Date.now()) return hit.address;

  const [record] = await dns.resolve4(hostname, { ttl: true });
  const ttlMs = Math.min(record.ttl * 1000, capMs);
  cache.set(hostname, { address: record.address, expiresAt: Date.now() + ttlMs });
  return record.address;
}
```

Health-checked failover at the DNS layer, expressed as the declarative config teams actually write:

```yaml
# Route 53-style failover: primary answers only while its health check passes.
PrimaryRecord:
  Name: api.example.com
  Type: A
  TTL: 30                    # low TTL: this record is expected to change under pressure
  Failover: PRIMARY
  HealthCheckId: !Ref ApiHealthCheck   # fails over after detection × threshold

SecondaryRecord:
  Name: api.example.com
  Type: A
  TTL: 30
  Failover: SECONDARY
# Cost of this mechanism = health-check interval × failure threshold + TTL drain.
# Design the client to retry, because clients will hold the old address meanwhile.
```

## Real-World Use Cases

### 1. Blue-green and region cutovers

A team migrating between regions can change a DNS answer or shift a weighted share of traffic. Before the change, it verifies both targets and lowers the TTL early enough for existing cached answers to age out. It keeps the old target available during the transition and tests rollback.

### 2. Global entry points and CDNs

CDNs publish their edge under anycast addresses and use latency/geo steering to choose a nearby PoP. The client resolves one name and is served by a machine near it; DNS is the first, cheapest layer of that optimisation ([CDN Architecture](../../../40-platform/40.10-cdn/40.10.01-cdn-architecture.md)).

### 3. Service discovery in Kubernetes

`my-service.my-namespace.svc.cluster.local` resolves to the Service's virtual IP or the pod endpoints. This is DNS used as the service registry — convenient and universal, at the cost of the `ndots`/`resolv.conf` behaviors above ([Service Discovery](../../../20-backend/20.6-microservices/01-service-topology/20.6.1.01-service-discovery.md)).

### 4. Certificate issuance depends on DNS

ACME's `DNS-01` challenge proves domain control by asking you to publish a specific `TXT` record; `CAA` records restrict which CAs are permitted to issue for your domain. Your certificate lifecycle is therefore partially a DNS workflow — see [TLS, HTTPS & the Certificate Lifecycle](30.2.1.23-tls-https-and-certificates.md).

### 5. Email deliverability as a naming problem

`MX` routes mail; `SPF`/`DKIM`/`DMARC` live as `TXT` records and decide whether your transactional mail lands or is rejected. "We can't send email from the new domain" is frequently a missing record, not an application bug.

### 6. Outage forensics

A "we deployed and traffic vanished" incident often traces to a record that expired because its TTL was shorter than the deploy, or to a resolver's negative cache holding an NXDOMAIN from a momentary misconfiguration ([Failure Modes](30.2.1.10-failure-modes.md)).

## Common Mistakes

| Mistake | Consequence | Fix |
| -------------------------------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Editing a record with a long TTL and immediately testing | "It's not propagated" confusion on the operator's own laptop | Lower TTL **before** the change window; verify with `dig +trace` and against authoritative servers |
| Assuming every client honours your TTL | Some resolvers enforce minimums or cache longer | Design for the worst case; do not rely on sub-minute cutovers for correctness |
| `CNAME` at the zone apex | Records silently rejected / apex breaks | Use `A`/`AAAA` (or provider "alias"/flattening records) at the apex |
| Creating the record after pointing clients at it | Cached NXDOMAIN keeps failing after the fix | Create first, then cut over; be aware of negative-cache TTL |
| Using DNS as the only failover mechanism | Failover is slow and partially outside your control | Health checks at the load balancer + client retries/backoff + DNS as an outer layer |
| Assuming the resolver's location equals the user's | Geo-steering sends users to the wrong region | Use EDNS Client Subnet-aware routing where available, or steer with anycast/LB instead |
| Ignoring `ndots` and search domains in containers | Extra failed lookups → measurable latency and DNS-server load | Set `ndots` deliberately; use FQDNs (trailing dot) for external names in hot paths |
| Leaving a wildcard `A`/`CNAME` in place | Typos resolve to a live host, hiding misconfiguration; broad TLS exposure | Avoid wildcards except for deliberate multi-tenant subdomains |
| No `CAA` and no expiry monitoring | Any CA may issue for your domain; expired cert takes you down | Publish `CAA`; automate issuance and expiry alerts |
| Treating plain DNS as private | Lookups (and thus behaviour) are observable and spoofable on-path | Use DoH/DoT where appropriate and DNSSEC for integrity |

## Best Practices

1. **Choose TTLs from your change and query patterns.** Lower them in advance of planned migrations, and test the behavior clients actually use.
2. **Do not rely on DNS alone for failover.** Include health checks, client retry behavior, and a recovery plan for existing connections.
3. **Measure resolution in the target runtime.** Its cache and resolver behavior may differ from `dig` or another runtime.
4. **Review important zone changes.** Infrastructure as code can make record changes auditable ([IaC Fundamentals](../../../40-platform/40.12-iac/40.12.01-iac-fundamentals-terraform.md)).
5. **Own your certificate prerequisites**: `CAA` published, `DNS-01` automation working, expiry monitored.
6. **Check search-domain behavior** for external names in containers; use a fully qualified name when the runtime requires it.
7. **Monitor DNS as an availability dependency**: query latency, SERVFAIL/NXDOMAIN rates, and change history. A resolver outage looks like an application outage.
8. **Document the zone's archaeology** — which records are load-bearing (mail, verification, CAA, ACME) and which are leftovers waiting to bite.

## Summary

DNS maps stable names to changing records. A stub resolver asks a recursive resolver, which follows referrals when it does not already have a cached answer. TTL controls how long a record may be reused, so a DNS change does not instantly reach every client. DNS can steer traffic, but reliable failover also depends on health checks, application retries, and open connections. Check actual resolver behavior and test recovery rather than assuming a fixed propagation time.

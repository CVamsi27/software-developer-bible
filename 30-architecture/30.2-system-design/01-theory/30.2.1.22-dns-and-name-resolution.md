# DNS & Name Resolution

> **The internet's naming layer — and its most abused control plane.** DNS turns a name humans can remember into an address machines can route to, using a globally distributed, delegated, aggressively cached database. Because almost every migration, failover, and multi-region strategy ultimately flips a DNS record, DNS is where architecture decisions and downtime both become visible.

## Definition

The Domain Name System is a hierarchical, distributed naming system that maps names to records. A **zone** is a slice of the namespace owned by one authority; a **record** is one typed entry in that zone; a **resolver** is the client-side component that turns a name into an answer, walking the hierarchy and caching as it goes.

```text
┌──────────────────────────────────────────────────────────────────────┐
│  STUB RESOLVER        the OS/library on your machine (no brain)      │
│  e.g. getaddrinfo() → sends ONE question to a configured resolver    │
├──────────────────────────────────────────────────────────────────────┤
│  RECURSIVE RESOLVER   does the walking + caches (ISP, 8.8.8.8,       │
│                       Cloudflare 1.1.1.1, your VPC resolver)         │
├──────────────────────────────────────────────────────────────────────┤
│  ROOT SERVERS         know where each TLD lives (.com, .io, .de)     │
│        └── TLD SERVERS        know the authoritative NS for example  │
│               └── AUTHORITATIVE  holds YOUR zone's records — the     │
│                   NAMESERVERS    only source of truth for the zone   │
└──────────────────────────────────────────────────────────────────────┘
```

| Term | Who operates it | What it does | Caches? |
| ----------------------- | --------------------------------- | -------------------------------------------------- | ------------------------------- |
| Stub resolver | The OS / language runtime | Asks a resolver; applies local hosts file + ndots | Yes (OS/libc, per-process) |
| Recursive resolver | ISP, cloud VPC, public (1.1.1.1) | Walks the hierarchy, caches, returns final answer | Yes — the big cache you wait on |
| Root nameserver | ICANN-root operators (13 anycast) | Delegates to TLD nameservers only | Yes |
| TLD nameserver | Registry (.com, .io, .dev) | Delegates to your zone's `NS` records | Yes |
| Authoritative NS | You (or Route 53, Cloudflare) | Answers with your records; no upstream caching | No |

**The resolution walk is only paid on a cache miss.** On a hit, the whole hierarchy above is irrelevant — which is why DNS feels instant in benchmarks and mysteriously slow in a fresh container.

## First Principles

DNS exists because of four unavoidable constraints. Read them as a chain — each one forces the next:

1. **Names must be stable; addresses must not.** A human or a client config points at `api.example.com` for years, while the machine behind it is replaced, moved between clouds, or scaled out. Anything that hardcodes an address breaks on the first migration. So the indirection layer is not optional — it is the only way to change infrastructure without changing every caller.
2. **No single server can hold every name.** Billions of names, billions of queries per second. The only structure that scales is a **hierarchy with delegation**: each zone hands authority for its children to someone else, and each server answers only for its own slice. This is why resolution is a *walk* (root → TLD → authoritative) rather than one lookup — and why each level can be operated by a different organization.
3. **Latency budgets cannot absorb a walk per request.** A cold 3–4 level walk costs real RTTs. So the design is forced into **caching**: resolvers and stub clients store answers for a TTL the zone owner chooses. Caching is what makes DNS cheap, and it is simultaneously why DNS changes are slow — you are not updating state, you are waiting for other people's caches to forget.
4. **Because answers are cached by unaccountable third parties, consistency must be traded away.** You cannot both "answer fast from a nearby cache" and "change the answer for everyone immediately." That single trade-off explains TTL tuning, the propagation myth, negative caching, and why blue-green cutovers are planned in hours rather than seconds.

Corollary that interviewers are really testing: **DNS is an eventually-consistent, multiply-cached distributed system you do not control end to end.** Design accordingly.

## Why It Matters

1. **Every deploy, failover, and multi-region story ends in a DNS change.** If you cannot reason about TTL, you cannot plan a cutover or a rollback.
2. **DNS is a first-class latency contributor.** A cold lookup can add 1–3 RTTs *before* TCP even starts — on top of the handshake ([TCP & UDP Transport Fundamentals](30.2.1.21-tcp-udp-transport-fundamentals.md)).
3. **It is the cheapest load-balancing and geographic-routing lever you have** — no code, no proxy, no client change.
4. **It fails in a distinctive way:** cached answers keep old traffic flowing while new regions look "empty", and negative answers can pin an outage in place for minutes.
5. **Security lives here too:** DNS is unauthenticated by default (spoofable/poisonable without DNSSEC), a favourite exfiltration and C2 channel with resolvers, and the enforcement point for `CAA` (who may issue your certificates).
6. **It is a favourite senior interview topic** precisely because it spans transport (UDP/TCP), caching, distributed consistency, and operations at once.

## How It Works

### The resolution walk

A cold lookup for `api.example.com` from a laptop:

```text
STUB           RECURSIVE (1.1.1.1)        ROOT            TLD (.com)      AUTHORITATIVE
 │                    │                    │                 │                 │
 │─ api.example.com ─►│                    │                 │                 │
 │                    │─ .com? ───────────►│                 │                 │
 │                    │◄─ NS for .com ─────│                 │                 │
 │                    │─ example.com? ─────────────────────►│                 │
 │                    │◄─ NS ns1.example.com ───────────────│                 │
 │                    │─ api.example.com? ───────────────────────────────────►│
 │                    │◄─ A 203.0.113.10 (TTL 60) ─────────────────────────────│
 │◄─ 203.0.113.10 ────│   (caches for 60 s, plus NS glue)     │                 │
 │  (OS caches too)   │                    │                 │                 │
```

Warm lookup: stub → recursive → cached answer. **Zero upstream traffic**, one short RTT (or none, if the OS already has it).

Two consequences seniors quote:

- **Cache locality is a real performance feature.** Run a resolver near your workloads (VPC resolver, node-local DNS cache) or every cold lookup pays the walk.
- **The walk cost is amortised across everyone using that resolver**, which is why public resolvers are fast even for names you have never visited.

### Record types you must know

| Record | Maps | Use it for | Notes |
| ------------------- | ----------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| `A` | name → IPv4 | The main address record | Can appear many times (round-robin) |
| `AAAA` | name → IPv6 | Dual-stack | Absent `AAAA` means IPv4-only, not "broken" |
| `CNAME` | name → another **name** | Aliases, pointer to a cloud provider hostname | Illegal at the zone apex (must not coexist with `NS`/`SOA`) |
| `NS` | zone → nameservers | Delegation and subzone handoff | The mechanism that makes DNS a hierarchy |
| `MX` | domain → mail hosts | Email delivery routing | Takes priority numbers |
| `TXT` | name → arbitrary strings | Verification, `SPF`, `DKIM`, `DMARC`, app config | Free-form; abused as a poor DB |
| `SRV` | `_service._proto` → host:port | Service discovery (older systems) | Port + priority + weight |
| `SOA` | zone → authority metadata | Zone identity; sets **negative-cache TTL** | The TTL here governs NXDOMAIN caching |
| `CAA` | domain → allowed CAs | Restrict who may issue your certs | Enforced by CAs, not by DNS |
| `PTR` | IP → name | Reverse DNS (logs, mail reputation) | Lives under `in-addr.arpa` / `ip6.arpa` |

**Try it yourself:** `dig api.example.com +noall +answer` shows the record and its remaining TTL; repeating the command shows the TTL counting down from *your* resolver's cache, not from the authoritative server.

### TTL: the one knob that matters

TTL is the number of seconds a caching resolver may reuse an answer. It is a direct trade between **agility** and **load + latency**:

| TTL | Cutover visibility | Resolver load | When it's right |
| --------------- | ------------------ | ------------- | ------------------------------------------------------------- |
| 30–60 s | ~1–2 minutes | High | Active failover, blue-green, anything you may need to reverse |
| 300 s (5 min) | ~5 minutes | Moderate | Default for most production API records |
| 3600 s (1 h) | Up to an hour | Low | Stable infrastructure you rarely move |
| 86400 s (1 day) | Up to a day | Minimal | Apex/static records; never during a migration |

**The migration ritual** (know this — it is a classic interview follow-up): lower the TTL to 60 s *at least one old-TTL window before* the change, wait for caches to drain, make the switch, verify, then raise the TTL back. Skipping the "pre-lower" step is why teams discover too late that their rollback takes six hours.

### Negative caching and the NXDOMAIN trap

The `SOA` record's minimum TTL governs how long "this name does not exist" is cached. Two practical consequences:

- Create the record *before* pointing clients at it, or a client's cached NXDOMAIN will keep failing even once the record exists.
- Some resolvers ignore very low negative TTLs and apply their own floor, so an outage can outlive your intent.

### DNS as a load balancer

Because one name may return many answers, DNS can distribute traffic:

| Strategy | How it works | Honest limitation |
| -------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Round-robin | Return all `A` records rotated | No health awareness; clients may get a dead one |
| Weighted | Return subsets by configured weight | Coarse; cached for the TTL, so reweighting is slow |
| Latency / geo | Resolver's region steers to the nearest entry point | Depends on resolver location being a proxy for user location (EDNS Client Subnet improves this, and privacy-minded resolvers may ignore it) |
| Failover | Health checks remove unhealthy answers | Detection + TTL delay ⇒ minutes, not seconds |
| Anycast | Many servers announce the *same* IP | Routing magic, not records — the basis of CDN and root-server resilience |

**Why DNS-based failover is blunt:** the answer lives in caches you do not own. Even with a 30 s TTL, some resolvers apply a minimum TTL, clients re-resolve lazily, and long-lived TCP connections keep talking to the old address until they close. DNS failover is therefore a *coarse, minutes-scale* control, and should be the outer layer of a defense that also includes load-balancer health checks and client retries.

### Anycast, DoH, and the security layer

- **Anycast** — the same IP announced from many locations, so BGP delivers each client to a nearby instance. This is how root servers, public resolvers, and CDNs get both latency and crude DDoS absorption. It is invisible at the record level.
- **DNS over HTTPS (DoH) / DNS over TLS (DoT)** — encrypts the lookup so networks cannot read or tamper with it. Cost: it bypasses enterprise DNS-based filtering, and it adds a TLS handshake for a query that used to be a single UDP datagram.
- **DNSSEC** — cryptographic signatures on answers, proving they came from the zone. It provides *integrity*, not *confidentiality*, and is deployed unevenly; validation failures are a classic silent outage.
- **Spoofing and poisoning** — plain DNS is unauthenticated UDP; source-port randomisation and DNSSEC are the mitigations.

### Kubernetes, registries, and the ndots gotcha

In-cluster DNS is a normal hierarchy (`cluster.local` → services → endpoints), and it exposes two very common production bugs:

- **`ndots` + search domains:** a name with fewer dots than `ndots` (default 5) is *first* tried as `name.namespace.svc.cluster.local`, then with other search paths, then absolutely. A single-dot external name can therefore trigger several failed lookups before succeeding — measurable latency on every cold call.
- **`resolv.conf` concurrency limits:** classic resolver libraries serialize lookups (and cap outstanding queries at ~2), so one slow DNS server stalls unrelated application calls. Node-local DNS caches exist to fix exactly this.

## Code Examples

Inspecting what your system actually resolves, including the records behind a CDN hostname:

```bash
# Answer + TTL as your resolver sees it
dig api.github.com +noall +answer

# Walk the hierarchy explicitly — root, TLD, then authoritative
dig +trace www.example.com

# Ask a specific authoritative server (bypass every cache)
dig @ns1.example.com www.example.com

# Which resolver am I even using?
scutil --dns 2>/dev/null | head -20 || cat /etc/resolv.conf

# Mail/verification records
dig TXT example.com +short
```

Resolving from application code, distinguishing the resolver path from the hosts-file path:

```typescript
import dns from "node:dns/promises";

// resolve* = ALWAYS asks DNS (ignores /etc/hosts)
const a = await dns.resolve4("api.github.com", { ttl: true });
console.log(a); // [{ address: "140.82.121.6", ttl: 47 }]  ← TTL is remaining, not original

// lookup = the OS path (honours /etc/hosts, respects ndots/search domains).
// Use this when you want the same answer the rest of the machine gets.
console.log(await dns.lookup("api.github.com", { all: true }));

// NXDOMAIN vs NODATA matters for caching strategy
try {
  await dns.resolve4("does-not-exist-xyz.example");
} catch (err) {
  const code = (err as NodeJS.ErrnoException).code;
  console.log(code); // ENOTFOUND (NXDOMAIN) or ENODATA (name exists, no A)
}
```

Measuring the cold-vs-warm cost, which is the number worth quoting in a design review:

```typescript
import { Resolver } from "node:dns/promises";

const resolver = new Resolver({ timeout: 2000, tries: 2 });

async function timeLookup(name: string, label: string) {
  const start = process.hrtime.bigint();
  await resolver.resolve4(name);
  const ms = Number(process.hrtime.bigint() - start) / 1e6;
  console.log(`${label.padEnd(8)} ${name.padEnd(24)} ${ms.toFixed(1)} ms`);
}

await timeLookup("api.github.com", "cold #1");
await timeLookup("api.github.com", "warm #2"); // resolver cache hit: drops sharply
```

A TTL-aware in-process cache — the pattern for "I must not re-resolve on every request, but I must also not pin an address forever":

```typescript
type Entry = { address: string; expiresAt: number };

const cache = new Map<string, Entry>();

async function resolveCached(
  hostname: string,
  capMs = 30_000, // never trust a record longer than this, however big its TTL
): Promise<string> {
  const hit = cache.get(hostname);
  if (hit && hit.expiresAt > Date.now()) return hit.address;

  const [record] = await dns.resolve4(hostname, { ttl: true });
  const ttlMs = Math.min(record.ttl * 1000, capMs);
  cache.set(hostname, { address: record.address, expiresAt: Date.now() + ttlMs });
  return record.address;
}
```

Health-checked failover at the DNS layer, expressed as the declarative config teams actually write:

```yaml
# Route 53-style failover: primary answers only while its health check passes.
PrimaryRecord:
  Name: api.example.com
  Type: A
  TTL: 30                    # low TTL: this record is expected to change under pressure
  Failover: PRIMARY
  HealthCheckId: !Ref ApiHealthCheck   # fails over after detection × threshold

SecondaryRecord:
  Name: api.example.com
  Type: A
  TTL: 30
  Failover: SECONDARY
# Cost of this mechanism = health-check interval × failure threshold + TTL drain.
# Design the client to retry, because clients will hold the old address meanwhile.
```

## Real-World Use Cases

### 1. Blue-green and region cutovers

A team migrating from a single region to multi-region changes one `A` record (or flips a weighted split 10 % → 50 % → 100 %). The skill is not the change — it is having pre-lowered the TTL an hour earlier, and having verified both environments independently so the rollback is a one-line revert rather than an incident.

### 2. Global entry points and CDNs

CDNs publish their edge under anycast addresses and use latency/geo steering to choose a nearby PoP. The client resolves one name and is served by a machine near it; DNS is the first, cheapest layer of that optimisation ([CDN Architecture](../../../40-platform/40.10-cdn/40.10.01-cdn-architecture.md)).

### 3. Service discovery in Kubernetes

`my-service.my-namespace.svc.cluster.local` resolves to the Service's virtual IP or the pod endpoints. This is DNS used as the service registry — convenient and universal, at the cost of the `ndots`/`resolv.conf` behaviors above ([Service Discovery](../../../20-backend/20.6-microservices/01-service-topology/20.6.1.01-service-discovery.md)).

### 4. Certificate issuance depends on DNS

ACME's `DNS-01` challenge proves domain control by asking you to publish a specific `TXT` record; `CAA` records restrict which CAs are permitted to issue for your domain. Your certificate lifecycle is therefore partially a DNS workflow — see [TLS, HTTPS & the Certificate Lifecycle](30.2.1.23-tls-https-and-certificates.md).

### 5. Email deliverability as a naming problem

`MX` routes mail; `SPF`/`DKIM`/`DMARC` live as `TXT` records and decide whether your transactional mail lands or is rejected. "We can't send email from the new domain" is frequently a missing record, not an application bug.

### 6. Outage forensics

A "we deployed and traffic vanished" incident often traces to a record that expired because its TTL was shorter than the deploy, or to a resolver's negative cache holding an NXDOMAIN from a momentary misconfiguration ([Failure Modes](30.2.1.10-failure-modes.md)).

## Interview Traps

| Trap | What they're testing | Strong answer spine |
| -------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "What happens when you type a URL?" — the DNS leg | Do you know the walk, or just the word "DNS"? | OS cache/hosts file → configured recursive resolver → (on miss) root → TLD → authoritative → answer + TTL, cached at every level. Then TCP and TLS begin. Say "cached means zero extra RTT". |
| "We'll fail over with DNS in 30 seconds." | Do you understand who holds the answer? | Push back: you control the authoritative answer, not the caches. Add health checks, load-balancer-level failover, and client retries; be honest that failover is minutes-scale even with a short TTL. |
| "DNS propagation takes 24–48 hours." | Myth-detection | Nothing propagates. Caches expire, unevenly, and some resolvers apply TTL floors. Plan around the old TTL rather than waiting for a mystical clock. |
| "How do you do zero-downtime migration between clouds?" | Sequencing under TTL | Pre-lower TTL → stand up and verify target → shift weight in stages → drain connections → raise TTL. Include rollback, and note long-lived connections may need explicit draining. |
| "Why is our service slow in a new container but fine in prod?" | Cold-cache awareness | Fresh container = cold resolver, cold node-local cache, and possibly `ndots` search-path failures before the real answer. Run a local cache / set `ndots` deliberately. |
| "Does DNS give you high availability for the database?" | Layer confusion | No — DNS gives you an address, not a failover protocol. Replicated state, leader election, and connection handling must exist underneath ([Consensus & Leader Election](30.2.1.09-consensus-and-leader-election.md)). |
| "Why not point everything at IPs and skip DNS?" | Trade-off articulation | You would lose indirection, TLS certificate names, geo/anycast routing, and multi-tenancy on shared infrastructure. Every migration would become a client-configuration project. |

## Common Mistakes

| Mistake | Consequence | Fix |
| -------------------------------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Editing a record with a long TTL and immediately testing | "It's not propagated" confusion on the operator's own laptop | Lower TTL **before** the change window; verify with `dig +trace` and against authoritative servers |
| Assuming every client honours your TTL | Some resolvers enforce minimums or cache longer | Design for the worst case; do not rely on sub-minute cutovers for correctness |
| `CNAME` at the zone apex | Records silently rejected / apex breaks | Use `A`/`AAAA` (or provider "alias"/flattening records) at the apex |
| Creating the record after pointing clients at it | Cached NXDOMAIN keeps failing after the fix | Create first, then cut over; be aware of negative-cache TTL |
| Using DNS as the only failover mechanism | Failover is slow and partially outside your control | Health checks at the load balancer + client retries/backoff + DNS as an outer layer |
| Assuming the resolver's location equals the user's | Geo-steering sends users to the wrong region | Use EDNS Client Subnet-aware routing where available, or steer with anycast/LB instead |
| Ignoring `ndots` and search domains in containers | Extra failed lookups → measurable latency and DNS-server load | Set `ndots` deliberately; use FQDNs (trailing dot) for external names in hot paths |
| Leaving a wildcard `A`/`CNAME` in place | Typos resolve to a live host, hiding misconfiguration; broad TLS exposure | Avoid wildcards except for deliberate multi-tenant subdomains |
| No `CAA` and no expiry monitoring | Any CA may issue for your domain; expired cert takes you down | Publish `CAA`; automate issuance and expiry alerts |
| Treating plain DNS as private | Lookups (and thus behaviour) are observable and spoofable on-path | Use DoH/DoT where appropriate and DNSSEC for integrity |

## Best Practices

1. **Decide TTL from an operational invariant**: "how fast must I be able to reverse this?" — then pre-lower before every planned change.
2. **Never plan a DNS-only failover.** Layer it: health-checked records (minutes) + load balancer failover (seconds) + client retries with backoff (instant).
3. **Make resolution a measured cost.** Cache in-process with a capped TTL, run a resolver near your workloads, and avoid resolving inside hot request paths when an address can be reused safely.
4. **Automate the whole zone.** Record changes belong in code with review (IaC), not in a console at 3 a.m. — see [IaC Fundamentals](../../../40-platform/40.12-iac/40.12.01-iac-fundamentals-terraform.md).
5. **Own your certificate prerequisites**: `CAA` published, `DNS-01` automation working, expiry monitored.
6. **Use the trailing dot for external names in hot paths** (`api.stripe.com.`) so search domains can never intercept them.
7. **Monitor DNS as an availability dependency**: query latency, SERVFAIL/NXDOMAIN rates, and change history. A resolver outage looks like an application outage.
8. **Document the zone's archaeology** — which records are load-bearing (mail, verification, CAA, ACME) and which are leftovers waiting to bite.

## Summary

DNS is a hierarchical, delegated, cacheable database whose job is to keep names stable while the addresses behind them change. A stub resolver asks a recursive resolver, which walks root → TLD → authoritative only on a cache miss and then caches the answer for the zone's TTL. That caching is what makes DNS fast and what makes DNS changes slow: caches expire unevenly and no amount of waiting makes "propagation" real, so TTL — not propagation — is the knob you tune before a migration. Record types encode intent (`A`/`AAAA` address, `CNAME` alias, `NS` delegation, `MX`/`TXT` mail and verification, `SOA` authority and negative caching, `CAA` cert control). DNS can also balance and fail over traffic, but bluntly, because the answer lives in caches you do not own — which is why it belongs as the outer layer of a resilience design rather than the whole of it. Master the walk, the TTL trade, and the failover honesty, and you can answer the DNS leg of any system design question with numbers instead of vibes.

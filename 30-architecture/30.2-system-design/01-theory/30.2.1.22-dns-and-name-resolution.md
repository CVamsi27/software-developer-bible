# DNS & Name Resolution

You deploy a new service address, but some clients still reach the old region. DNS does not push a change to every client. To predict the cutover, follow the lookup from the application through its resolver caches, then account for connections already open:

```bash
dig api.github.com A +noall +answer  # answer + remaining TTL from your resolver
```

## Definition

The **Domain Name System (DNS)** is a distributed naming system. An application asks for records about a name; a **stub resolver** passes the lookup to a **recursive resolver**, which can answer from cache or follow referrals to an **authoritative nameserver**. A zone is the part of the namespace for which an authority serves records.

> **Textbook Definition:** DNS is a hierarchical, distributed naming system that maps names to typed resource records through authoritative servers and caching resolvers.

## First Principles

Names separate a service identity from the machine address currently serving it. Delegation lets each authority manage a smaller zone instead of requiring one global server to hold every record. Caching avoids repeating the full lookup, but it trades freshness for fewer queries and lower latency.

That trade-off explains DNS behavior during a deployment: an authoritative change affects future answers, while cached answers and existing network connections can continue pointing at the old target.

## How It Works

```text
APPLICATION
    │ asks for a name and record type
    ▼
STUB RESOLVER ── query ──► RECURSIVE RESOLVER
(OS or runtime)             (checks cache; follows referrals)
                                  │ cache miss
                                  ▼
                         ROOT → TOP-LEVEL DOMAIN (TLD) → AUTHORITATIVE
                                  │ answer or referral
                                  └──────────────► recursive cache → application
```

### 1. Follow one lookup from stub to authoritative

For a cold lookup of `api.example.com`, the application normally asks its configured recursive resolver. If that resolver holds no usable cached answer, it starts at a root server, follows the referral to the `.com` nameservers, then follows the `example.com` delegation to an authoritative server:

```text
STUB          RECURSIVE          ROOT             TLD (.com)       AUTHORITATIVE
 │                 │               │                  │                  │
 │─ A api.example.com? ───────────►│                  │                  │
 │                 │─ .com? ──────►│                  │                  │
 │                 │◄─ referral ───│                  │                  │
 │                 │─ example.com? ──────────────────►│                  │
 │                 │◄─ referral ──────────────────────│                  │
 │                 │─ api.example.com? ────────────────────────────────►│
 │                 │◄─ A 203.0.113.10, TTL 60 ─────────────────────────│
 │◄─ answer ───────│  caches records and referrals                     │
```

The trace shows the logical walk, not necessarily one packet per step. Resolvers cache delegations and other records, so a later lookup may skip the root or TLD. A warm cache can answer without contacting an authoritative server. The operating system or application may also keep its own cache.

When a delegated nameserver sits inside the zone being delegated, its address would otherwise depend on resolving that same delegation. The parent includes **glue** (A or AAAA address data) so a resolver can reach the nameserver. Glue is bootstrap data in the referral; the child zone's authoritative address records remain the source of truth. Most conventional DNS lookups use UDP. Resolvers and authoritative servers must also support TCP: a client retries over TCP when a UDP response is truncated, and full zone transfers use TCP. See [TCP & UDP Transport Fundamentals](30.2.1.21-tcp-udp-transport-fundamentals.md).

### 2. Choose the record type by its consumer

DNS returns typed records, not a universal "IP for name" value. The record type determines what the answer means and which protocol consumes it.

Name-to-address and delegation records:

| Record | Meaning | Practical boundary |
| --------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `A` / `AAAA` | IPv4 / IPv6 address for a name | Multiple records publish multiple addresses; answer order is not a reliable load-balancing contract. |
| Canonical Name (`CNAME`) | Alias from one name to another name | The owner cannot also hold ordinary record data. Because a zone apex needs SOA and NS records, it cannot be an ordinary CNAME; some providers offer alias or flattening features. |
| Name Server (`NS`) | Nameservers for a zone or delegation | Parent and child delegations must agree; in-domain targets may need glue. |
| `SOA` | Start of Authority metadata for a zone | Includes the serial and timers; its TTL and MINIMUM field bound ordinary negative caching. |
| Pointer (`PTR`) | Reverse mapping from an address to a name | A reverse name is not proof that the named host owns the address. |

Service, mail, and policy records:

| Record | Meaning | Practical boundary |
| --------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mail Exchanger (`MX`) | Mail exchanger and preference | Lower preference values are tried first; mail delivery has additional policy and reputation checks. |
| Text (`TXT`) | Text associated with a name | Used by domain verification and mail policies such as Sender Policy Framework (SPF), DomainKeys Identified Mail (DKIM), and Domain-based Message Authentication, Reporting, and Conformance (DMARC). |
| Service (`SRV`) | Service target, port, priority, and weight | The client must know to query and interpret the service record; DNS does not make every client service-discovery aware. |
| Certification Authority Authorization (`CAA`) | Certificate authorities allowed to issue for a domain | Constrains certificate issuance; it does not itself issue or validate a certificate. |
| `DS` / `DNSKEY` / `RRSIG` / `NSEC` / `NSEC3` | DNSSEC delegation and signatures | A parent `DS` links to a child `DNSKEY`; `RRSIG` signs record sets, while `NSEC` or `NSEC3` can prove authenticated absence. A resolver must validate the chain. |
| Service Binding (`SVCB`) / `HTTPS` | Service target and connection parameters | Can advertise a port, Application-Layer Protocol Negotiation (ALPN) values, or Encrypted Client Hello (ECH) configuration. Client support and fallback matter; the record is not a certificate or endpoint identity. |

The Automatic Certificate Management Environment (ACME) DNS-01 challenge, for example, asks the domain owner to publish a specific TXT value to prove control. HTTPS/SVCB records can help clients discover connection parameters, but the client still validates the service identity during TLS.

### 3. Treat TTL as reuse, not failover

A record's time to live (TTL) tells caches how long the answer may ordinarily be reused. Each cached copy counts down independently. A shorter TTL lets a resolver refresh sooner after expiry, at the cost of more queries; it never pushes a new answer to clients or closes existing connections.

A TTL is no exact failover timer. Recursive resolvers and runtimes may apply local limits, applications may cache independently, and open connections keep using their current peer. Some recursive resolvers can also serve stale data after expiry when they cannot reach an authority, improving availability at the cost of freshness ([RFC 8767](https://www.rfc-editor.org/rfc/rfc8767.html)).

Negative answers behave separately:

- **NXDOMAIN** says the queried name does not exist.
- **NODATA** means the name exists but holds no record of the requested type.
- An authoritative negative answer's ordinary cache lifetime is the smaller of the SOA record TTL and the SOA MINIMUM value. With values 300 and 60 seconds, caches may reuse the negative answer for 60 seconds.
- **SERVFAIL** means resolution failed; it never says the name is absent. Failure caching follows separate rules under [RFC 9520](https://www.rfc-editor.org/rfc/rfc9520.html).

A cached NXDOMAIN can therefore outlive the moment an operator creates the missing record. Lowering a positive A-record TTL never clears a previous negative answer.

DNS can influence which endpoint a client discovers, but recursive-resolver location is only a proxy for user location, and caches smooth out changes:

| Strategy | What DNS does | Limitation |
| ----------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Multiple A/AAAA answers | Publishes several addresses | Client and resolver selection vary; answer order alone does not guarantee even distribution. |
| Weighted answers | Returns addresses according to configured weights | Cached answers and client reuse delay the effect of a weight change. |
| Geographic or latency answers | Chooses based on resolver location or available client subnet data | The recursive resolver may be far from the user; EDNS Client Subnet (ECS) support and privacy policy vary. |
| Health-based failover | Stops returning an endpoint after health checks fail | Detection time, cache lifetime, stale serving, client retry, and existing connections all affect recovery. |
| Anycast | Routes one shared IP from multiple sites | Border Gateway Protocol (BGP) routing policy selects a path; it does not guarantee the geographically nearest site. Anycast is a routing technique, not a DNS record. |

A safe planned cutover accounts for the whole path:

1. Lower the authoritative TTL far enough ahead for the change to reach every authority, then wait at least the old TTL before cutover.
2. Publish and verify the new target at the authoritative servers before sending production traffic to it.
3. Shift traffic gradually where the provider supports weights or health checks. Check answers through representative recursive resolvers, not only the operator's local cache.
4. Keep the old endpoint healthy during the overlap. Cached or serve-stale answers and long-lived connections may still use it.
5. Measure actual requests reaching each target and rehearse rollback. Never equate a DNS answer changing with traffic having moved.

### 4. Verify authenticity, privacy, and resolver behavior

**DNS Security Extensions (DNSSEC)** let a validating resolver verify signed DNS data through a chain of trust. This protects integrity and origin authentication for signed records; it never encrypts the query. At each zone cut, the parent's `DS` digest links to the child's `DNSKEY`; `RRSIG` covers record sets, and `NSEC` or `NSEC3` can prove a name or type is absent. The resolver validates down from a trusted root key. A broken chain can make a validating resolver return `SERVFAIL`. A signature alone is never enough if the client or resolver skips chain validation.

Transport Layer Security (TLS) protects **DNS over HTTPS (DoH)** and **DNS over TLS (DoT)**; **DNS over QUIC (DoQ)** uses QUIC's encrypted transport. This encryption protects the client-to-resolver channel from observers on that network path, but the selected resolver still sees the queries. Encrypted DNS changes which resolver and network policy the client uses; manage that choice deliberately in split-horizon or filtered networks.

Kubernetes configures pod search domains and resolver options through `/etc/resolv.conf`. A common setting is `ndots:5`. With libc-style resolver behavior, a name with fewer than five dots may be tried with search suffixes before the absolute name. For example, `api.github.com` may trigger cluster-suffix queries before its public lookup. Resolver libraries differ, so inspect the pod's actual file and measure from the runtime used by the application. A trailing dot marks an absolute fully qualified domain name (FQDN) for many resolver paths, but test the exact language/runtime behavior before relying on it.

### 5. Inspect the answer the client receives

Use `dig` to compare a recursive answer, the delegation path, and an authoritative response. The final commands select a nameserver from `example.com`'s NS records, then query it directly:

```bash
# Answer and remaining TTL from the configured resolver
dig api.github.com A +noall +answer

# Follow referrals from the root
dig +trace www.example.com

# Discover an authoritative server, then query it directly
AUTH_NS=$(dig NS example.com +short | head -1)
dig @"$AUTH_NS" example.com A +norecurse

# Inspect the machine's configured resolver
if command -v scutil >/dev/null 2>&1; then
  scutil --dns | head -20
else
  cat /etc/resolv.conf
fi
```

In Node.js, `dns.resolve4` sends a DNS query through the configured resolver. `dns.lookup` uses operating-system name-resolution facilities, which may consult a hosts file and need never send a DNS packet. It runs `getaddrinfo` in libuv's threadpool; `dns.resolve*` performs asynchronous network queries outside that pool. Under load, the distinction affects both lookup results and threadpool contention. These APIs answer different questions:

```javascript
import dns from "node:dns/promises";

const name = "api.github.com";

async function timed(label, lookup) {
  const start = process.hrtime.bigint();
  const answer = await lookup();
  const elapsedMs = Number(process.hrtime.bigint() - start) / 1e6;
  console.log(label + ": " + elapsedMs.toFixed(1) + " ms");
  return answer;
}

const dnsRecords = await timed(
  "DNS A query via configured resolver",
  () => dns.resolve4(name, { ttl: true }),
);
console.log(dnsRecords); // TTL is in seconds; addresses and values vary

const systemAddresses = await timed(
  "OS name lookup",
  () => dns.lookup(name, { all: true }),
);
console.log(systemAddresses);
```

A successful DNS query never proves the service is reachable or healthy. Test the returned endpoint and the application request separately.

## Summary

DNS delegates ownership of typed records and uses caches to make name resolution scalable. A cache miss follows referrals; a hit avoids that walk. TTLs govern ordinary cache reuse, but negative answers, serve-stale policy, runtime caches, and existing connections all affect a cutover. DNS can steer new connections, while reliable failover requires health checks, application retries, endpoint overlap, and measured recovery.

# TLS, HTTPS & the Certificate Lifecycle

When a browser opens an HTTPS connection, it must check the server identity and agree on encryption keys before sending private data. TLS (Transport Layer Security) handles this setup and protects data sent over the connection. A certificate helps the client check the server name; the handshake establishes keys; the record layer protects application data.

## Definition

**TLS (Transport Layer Security)** protects data sent between two endpoints. HTTP/1.1 and HTTP/2 commonly use TLS over TCP. HTTP/3 uses QUIC, which incorporates TLS 1.3 into its connection setup. A **handshake** negotiates connection settings, checks the server certificate, and establishes traffic keys. For TLS over TCP, a **record layer** uses those keys to protect application data. QUIC uses TLS handshake/key derivation but protects its own packets instead of carrying TLS application-data records. Client certificates can also be used when both sides need to authenticate.

> **Textbook Definition:** Transport Layer Security (TLS) negotiates cryptographic keys and authenticates the server, then protects application data with confidentiality and integrity. For TLS over TCP, the TLS record protocol carries that data; QUIC reuses the TLS handshake and key schedule but protects QUIC packets itself. Certificate validation binds a public key to the expected service identity.

**HTTPS** is HTTP protected by TLS.

**Elliptic-curve Diffie–Hellman ephemeral (ECDHE)** agrees a temporary shared secret. **HKDF**, an HMAC-based key derivation function, derives distinct traffic keys from secret and transcript inputs. **Authenticated encryption with associated data (AEAD)** encrypts records and detects tampering while authenticating selected unencrypted metadata. **Application-Layer Protocol Negotiation (ALPN)** selects a supported protocol such as HTTP/2; it does not implement that protocol.

```text
HTTP/1.1 or HTTP/2:  HTTP → TLS record layer → TCP → IP
                          (TLS handshake derives traffic keys)

HTTP/3:              HTTP/3 → QUIC streams and packet protection → UDP → IP
                               (TLS 1.3 handshake derives QUIC keys)

QUIC uses the TLS handshake and key schedule, but protects QUIC packets
instead of carrying TLS application-data records.
```

| Concept | What it actually is | What people wrongly assume |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| Certificate | A CA's signed statement binding a public key to a name | "A guarantee the site is safe" |
| Root store | Pre-installed trusted CAs shipped by OS/browser | "Something the server sends" |
| Chain of trust | Leaf ← intermediate ← root, each signed by the next | "The server's cert is signed directly by the root" |
| Server Name Indication (SNI) | Ordinary `ClientHello` exposes the requested name; deployed ECH can encrypt the inner name while leaving a public name visible | "Everything is encrypted from byte one" |
| Forward secrecy | Later long-term-key compromise cannot recover past session secrets under the chosen key exchange | "Rotating certs gives me forward secrecy" |
| Mutual TLS (mTLS) | Client also presents a certificate | "TLS always authenticates the client too" |

## First Principles

TLS addresses several problems on an untrusted network:

1. **The network is hostile, and the two parties have no prior relationship.** An attacker may observe or modify network traffic. Key agreement lets both endpoints derive matching keys without sending those keys across the network. Diffie–Hellman is one way to do this.
2. **Public-key operations and bulk symmetric encryption solve different problems and have different costs.** TLS uses public-key agreement/authentication rather than applying that machinery to every payload byte. This forces the **hybrid** design: use the expensive primitive minimally (to agree a key, and to prove identity), then switch to a fast symmetric cipher for all the actual bytes.
3. **Encryption alone does not establish the peer identity.** If you cannot be sure *whose* key you agreed with, a man in the middle performs the same handshake twice and reads everything. Since clients have no out-of-band relationship with servers, a browser commonly relies on trusted certificate authorities (CAs) installed in advance; private protocols can use other explicitly provisioned trust anchors — hence certificate authorities and the root trust stores baked into operating systems.
4. **Compromising today's long-term key must not decrypt yesterday's traffic.** If the session key were derived solely from a static private key, stealing that key would unlock recorded history. Ephemeral Diffie–Hellman key exchange can provide **forward secrecy**: later theft of the certificate private key alone does not reveal past traffic protected by those ephemeral session keys. The property depends on the negotiated key exchange and key handling.
5. **Servers host many names on one address, and clients need to negotiate versions and protocols.** The client may include the target hostname using **SNI** and offer an application protocol using **ALPN**. In standard TLS these fields are generally visible in the ClientHello; Encrypted Client Hello can protect some ClientHello fields when supported and configured.

Consequence worth stating plainly: **When correctly configured and certificate validation succeeds, TLS provides confidentiality, integrity, and server authentication. It does not give you availability, authorization, or protection from a compromised endpoint.** Everything after the handshake is still your application's problem.

## Why It Matters

1. **Everything sensitive you build is behind it.** Passwords, tokens, cookies, and payment data are only as safe as the channel — and a bearer token over plaintext HTTP is a credential handed to the network.
2. **TLS adds connection setup work.** A full TLS 1.2 handshake commonly takes two round trips; TLS 1.3 commonly takes one after the transport connection. Resumption and connection reuse change the cost ([TCP & UDP Transport Fundamentals](30.2.1.21-tcp-udp-transport-fundamentals.md)).
3. **Termination point is an architecture decision** with consequences for trust boundaries, certificate management surface, and what your load balancer can inspect.
4. **Certificate lifecycle affects availability.** An expired or misconfigured certificate can prevent clients from connecting. Automated renewal, deployment, and monitoring reduce manual failure risk.
5. **It is where service-to-service identity lives**, in the shape of mTLS — the foundation of zero-trust and service mesh designs ([Service Mesh](../../../20-backend/20.6-microservices/01-service-topology/20.6.1.03-service-mesh.md)).
6. **Interviewers probe the reasoning, not the acronym.** "Why is a certificate enough?" and "why ephemeral keys?" separate candidates who memorised the handshake from those who understand the constraints.

## How It Works

### The full handshake, TLS 1.2 vs 1.3

```text
Common certificate handshake over an established TCP connection:

TLS1.2:
client → ClientHello
server → ServerHello, certificate, key exchange, ServerHelloDone
client → ClientKeyExchange, ChangeCipherSpec, Finished
server → ChangeCipherSpec, Finished

TLS1.3:
client → ClientHello with key_share
server → ServerHello with key_share,
         encrypted EncryptedExtensions, Certificate, CertificateVerify, Finished
client → encrypted Finished (and application data as permitted)
```

This is the normal full certificate-authenticated flow, omitting optional client authentication and retry messages. In TLS1.3, the server's Finished is in its first flight; it does not wait for the client's Finished and then send a second server Finished.

What changed in 1.3, and why it matters:

- **One round trip.** The client guesses the key-exchange group and sends its half immediately, so the server can compute keys without waiting.
- **Encryption starts earlier.** The certificate itself is encrypted in 1.3, removing an on-path metadata leak.
- **Ephemeral key exchange is the normal full-handshake path.** TLS 1.3 also supports PSK modes; 0-RTT early data does not provide full forward secrecy.
- **A deliberately short cipher list.** Modes with known weaknesses (CBC, RC4, static RSA key transport, renegotiation) were removed rather than deprecated — less to misconfigure.
- **Resumption is built in.** A session ticket lets a returning client send a pre-shared key (PSK) and skip the certificate round, and can enable 0-RTT.

### Hybrid crypto: agree, then switch


```text
HANDSHAKE (asymmetric — expensive, used minimally)
  ECDHE: client and server each send a public ephemeral value;
         both derive the same shared secret S. An eavesdropper sees
         both public values and still cannot compute S (discrete log).
  AUTHENTICATION: server signs the handshake transcript with the private
         key matching its certificate → client verifies with the cert's
         public key → proves the server owns that key, and that the
         handshake was not tampered with.
                    ↓ derive (HKDF)
SESSION KEYS (symmetric — fast, used for all bulk data)
  AEAD record layer: AES-128/256-GCM or ChaCha20-Poly1305
         → confidentiality + integrity in one pass, per record
```

Why the signature is not redundant: Diffie–Hellman alone is unauthenticated — it protects against a passive eavesdropper but not an active one. The CA signature authenticates the certificate's public key and names under the trust chain. The server's **CertificateVerify** signature proves possession of that key and authenticates the handshake transcript, including the ephemeral exchange. Both checks are needed in this certificate-authenticated flow.

### Certificates and the chain of trust

A certificate is a signed assertion: `{name(s), public key, validity window, issuer} + CA signature`. The client verifies a **chain** up to a root it already trusts:

```text
ROOT CA (usually in the OS/browser trust store; servers commonly omit it)
  └─ signs ─► INTERMEDIATE CA (sent by the server)
                └─ signs ─► LEAF CERT (your domain, sent by the server)

Before accepting the connection, the client checks that the chain reaches a trusted root and that the identity matches the one it intended to reach. Checks include:
  1. A valid signature chain to a trusted root
  2. A matching subjectAltName identifier: DNS names use `dNSName`, IP addresses use `iPAddress`, and a DNS alias does not replace the original expected name
  3. The certificate's validity period and applicable client revocation policy
  4. Certificate constraints such as path length, extended key usage, and key usage
  ⟶ a fatal validation failure aborts the handshake; it is not a warning to click through.
```

Validation levels differ in *how much identity* the CA verified — degree of assurance, not cryptographic strength:

| Type | CA verifies | Typical use | Browser signal |
| -------------- | ------------------------------------------------ | --------------------------------------- | ------------------------------------------- |
| DV (Domain) | Control of the domain only (file/DNS/HTTP) | Most APIs and modern sites | Browser security indicator varies |
| OV (Org) | Domain + organisation existence | Enterprise, some commerce | Details on inspection |
| EV (Extended) | Stricter organisational vetting | Specialized business and legal contexts | UI varies; no universal stronger encryption |

The current service-identity rules require names in the certificate's `subjectAltName`; a `Common Name` fallback is not valid. Wildcards match only as the complete left-most DNS label (for example, `*.example.com` can match `api.example.com`, not `v2.api.example.com`).

Many publicly trusted DV certificates are issued through **ACME** (Automatic Certificate Management Environment). A `DNS-01` challenge proves domain control by publishing a `TXT` record, which makes DNS part of that issuance workflow ([DNS & Name Resolution](30.2.1.22-dns-and-name-resolution.md)). Let's Encrypt is one certificate authority that supports ACME.

### Forward secrecy, resumption, and 0-RTT

- **Forward secrecy** means later theft of the server's certificate private key alone does not reveal previously recorded sessions that used ephemeral key exchange. It depends on the negotiated mode and correct handling of ephemeral secrets.
- **Resumption** uses a pre-shared secret established from an earlier session to authenticate a later handshake without a fresh certificate exchange. Tickets identify or encode resumption state; their lifetime and protection are implementation choices. Protect resumption secrets and rotate keys used to encrypt stateless tickets. A normal full TLS 1.3 handshake and resumed handshake both commonly take one RTT; the main savings are certificate bytes and authentication work unless early data is used.
- **0-RTT** lets a returning client send application data with the first flight — sending eligible application data before that resumed handshake completes. The cost is **replay risk**: early data may be delivered more than once. The application must be safe under replay; HTTP method names alone do not establish that. Do not accept early data for an operation that can cause harmful duplicate effects ([Idempotency Keys](../../30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md)).

### Revocation, HSTS, and cleartext metadata

- **Revocation** mechanisms include certificate revocation lists (CRLs), OCSP, and OCSP stapling (the server attaches a signed OCSP response). Client support and checking behavior vary, so operators should not assume every client performs a live revocation check or that stapling is universally required.
- **HSTS** (`Strict-Transport-Security`) tells a browser that has received the header over HTTPS to use HTTPS for the stated period. It cannot protect a first visit unless the domain is preloaded or another secure starting point exists. Preloading is a separate, deliberate commitment; check domain and subdomain readiness before enabling it ([Web Security](../../../20-backend/20.5-security/03-hardening-and-operations/20.5.3.02-web-security.md)).
- **What TLS still exposes:** the destination IP, the port, traffic volumes and timings. Without negotiated ECH, the **SNI hostname** is also visible. ECH protects selected ClientHello fields but does not hide the server IP, all traffic patterns, or the DNS query from the chosen resolver.

### Where you terminate TLS

| Termination point | What you get | What you give up |
| ------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Load balancer / edge / CDN** | Central cert management, cheap handshake offload, L7 routing, WAF | Payload is plaintext inside your network — trust boundary must be real |
| **Application** | End-to-end encryption to the process that owns the data | Handshake CPU on app hosts, per-service cert sprawl |
| **Both (re-encrypt)** | Edge routing + encryption on the internal hop | Two cert lifecycles, more moving parts |
| **mTLS end-to-end** | Cryptographic client identity for the connection | Still needs authorization policy and certificate lifecycle management |

Choose the termination point from the trust boundary and operational needs. If TLS ends at a load balancer, the next hop is a separate connection and needs its own protection decision. mTLS is useful when services need cryptographic client identity; it also requires certificate issuance, rotation, and authorization policy.

## Code Examples

This diagnostic raw TLS server selects a certificate by SNI and logs negotiation; it does not implement HTTP/2 or HTTP/1.1. Production HTTP serving needs the matching protocol handler, an explicit unknown/no-SNI certificate policy, managed key loading and connection limits.

```typescript
import tls from "node:tls";
import fs from "node:fs";

const byHost: Record<string, { key: Buffer; cert: Buffer }> = {
  "api.example.com": {
    key: fs.readFileSync("/etc/tls/api.example.com.key"),
    cert: fs.readFileSync("/etc/tls/api.example.com.fullchain.pem"), // leaf + intermediates
  },
};

const server = tls.createServer(
  {
    // Ordinary SNI lets this server choose a certificate before HTTP.
    // Encrypted Client Hello is a separate supported-configuration question.
    // The default identity is api.example.com. Unknown SNI names are rejected;
    // clients without SNI receive this default certificate and must validate it.
    key: byHost["api.example.com"].key,
    cert: byHost["api.example.com"].cert,
    SNICallback: (servername, cb) => {
      const credentials = byHost[servername.toLowerCase()];
      if (!credentials) return cb(new Error(`unrecognized SNI name: ${servername}`));
      cb(null, tls.createSecureContext(credentials));
    },
    minVersion: "TLSv1.2", // 1.3 preferred; 1.0/1.1 are not acceptable
    // Add ALPN only when the selected application protocol is implemented.
  },
  (socket) => {
    const cipher = socket.getCipher();
    console.log(`${socket.servername} ${cipher?.name} ${cipher?.version}`);
  },
);

server.listen(8443); // local illustrative port; public port 443 needs deployment routing
```

Inspecting a live endpoint — chain, expiry, and negotiated protocol:

```bash
# Inspect the presented leaf certificate; this pipeline does not show the full chain.
# Use s_client -showcerts directly when inspecting all certificates sent by the server.
openssl s_client -connect api.github.com:443 -servername api.github.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# Negotiated protocol/version in one line
openssl s_client -connect api.github.com:443 -servername api.github.com </dev/null 2>/dev/null \
  | grep -E 'New,|Protocol|Cipher'

# When does it expire? (the number your monitor must watch)
echo | openssl s_client -connect api.github.com:443 -servername api.github.com 2>/dev/null \
  | openssl x509 -noout -enddate
```

Expiry monitoring in application code — the guard that prevents the classic outage:

```typescript
import tls from "node:tls";

function certDaysRemaining(host: string, port = 443): Promise<number> {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => socket.destroy(new Error("TLS probe deadline exceeded")), 5000);
    const socket = tls.connect({ host, port, servername: host }, () => {
      const cert = socket.getPeerCertificate();
      if (!cert || !cert.valid_to) {
        socket.destroy();
        return reject(new Error(`no certificate presented by ${host}`));
      }
      const expires = new Date(cert.valid_to).getTime();
      const days = (expires - Date.now()) / 86_400_000;
      socket.destroy();
      resolve(days);
    });
    socket.once("close", () => clearTimeout(timer));
    socket.once("error", reject);
  });
}

// This checks the certificate presented by this endpoint; it does not check every certificate in the chain.
certDaysRemaining("api.example.com").then((d) =>
  console.log(`${Math.floor(d)} days remaining ${d < 30 ? "⚠ renew now" : ""}`),
);
```

A client that verifies properly — and the one line you must never ship:

```typescript
import https from "node:https";
import fs from "node:fs";

const agent = new https.Agent({
  keepAlive: true,
  minVersion: "TLSv1.2",
  // NEVER in production:
  // rejectUnauthorized: false   ← disables the authentication half of TLS,
  //                               allowing an active attacker to impersonate the server.
});

// Verifying a private CA properly: trust it explicitly rather than disabling checks.
const internal = new https.Agent({
  ca: fs.readFileSync("/etc/tls/internal-root-ca.pem"), // explicitly trust this private CA
  keepAlive: true,
});
```

mTLS: the client also presents a certificate, so the server authenticates the *caller*:

```typescript
import tls from "node:tls";
import fs from "node:fs";

const socket = tls.connect({
  host: "internal-service.svc",
  port: 8443,
  servername: "internal-service.svc",
  key: fs.readFileSync("/etc/tls/client.key"),
  cert: fs.readFileSync("/etc/tls/client.pem"),
  ca: fs.readFileSync("/etc/tls/ca.pem"),
  // rejectUnauthorized stays true — we verify the SERVER as well.
});

class ServerSideCheck {
  // Server side: requestCert + rejectUnauthorized reject an absent or untrusted client certificate.
  static readonly options = {
    requestCert: true,
    rejectUnauthorized: true, // ← a client without a valid cert cannot connect
    ca: fs.readFileSync("/etc/tls/ca.pem"),
  } as const;
}
```

TLS termination at the proxy:

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem; # leaf + chain
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    ssl_protocols       TLSv1.2 TLSv1.3;

    # This example leaves ssl_ciphers unset; choose a TLS 1.2 suite list from
    # current BCP 195 guidance for the installed TLS library. ssl_ciphers does
    # not select TLS 1.3 suites, and HIGH may include legacy choices.
    ssl_prefer_server_ciphers off;                 # client suite ordering; policy still limits allowed suites

    ssl_session_cache   shared:SSL:10m;            # supports resumption, not removal of every handshake
    ssl_session_timeout 1d;
    ssl_session_tickets off;                       # only if you cannot rotate ticket keys

    # This example uses Let's Encrypt, which no longer provides OCSP.
    # Configure revocation/stapling only for a CA that supports the mechanism.

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location / {
        proxy_pass http://app_upstream;            # plaintext inside a trusted network
        proxy_set_header X-Forwarded-Proto https;  # apps need to know the real scheme
        proxy_set_header Host $host;
    }
}
```

The `app_upstream` group, installed Nginx modules, certificate files and deploy permissions must exist. TLS1.3 cipher configuration is distinct from `ssl_ciphers`; use the current Nginx/TLS-library documentation. HSTS `includeSubDomains` is appropriate only after every covered subdomain supports HTTPS. Let's Encrypt [ended OCSP on 6 August 2025](https://letsencrypt.org/2025/08/06/ocsp-service-has-reached-end-of-life) and publishes revocation information through CRLs.

Certificate issuance with a manually completed DNS challenge, followed by renewal through the configured Certbot authenticator:

```bash
# Manual DNS challenge. This command is not unattended automation.
certbot certonly --manual --preferred-challenges dns -d "*.example.com"

# For unattended renewal, configure an automated authenticator such as a DNS provider plugin.
# Then renew before expiry and deploy/reload the new certificate on success.
certbot renew --deploy-hook "systemctl reload nginx"
```

## Real-World Use Cases

### 1. Terminating at the edge for a public API

A load balancer holds one certificate for `api.example.com`, offloads the handshake (saving app CPU), routes by path, and forwards plaintext to app hosts inside a private network. The design's correctness depends on that internal network actually being trusted; if it is not, add re-encryption or mTLS.

### 2. mTLS for service-to-service identity in a mesh

In a service mesh, every sidecar holds a short-lived certificate issued by an internal CA, so service identity is cryptographic rather than "the request came from an IP in our subnet". Rotation happens automatically, and policy can be expressed as "service A may call service B" ([Service Mesh](../../../20-backend/20.6-microservices/01-service-topology/20.6.1.03-service-mesh.md)).

### 3. An expired-certificate outage

If a certificate expires or a renewed certificate is not deployed, clients that validate it will reject the connection. Renewal automation must include deployment or reload, and monitoring should check the certificate that clients actually receive ([Incident Response](../../../50-quality/50.4-production-engineering/50.4.01-incident-response.md)).

### 4. HSTS and cookie protection

A site that serves a login page over plain HTTP once can have its session cookie or redirect stolen. HSTS forces HTTPS for a period after the first secure visit, and enrollment in a browser preload list can protect the first request. Adding the `preload` token alone does not enroll the domain. Cookie flags (`Secure`, `HttpOnly`, `SameSite`) close the adjacent gaps ([Sessions & Cookies](../../../20-backend/20.5-security/01-auth/20.5.1.04-sessions-cookies.md)).

### 5. 0-RTT for repeat visitors, selectively

A CDN may enable 0-RTT to send eligible early data before the resumed handshake completes. The application allows it only for operations designed to tolerate replay. A `GET` is not automatically safe if the application attaches side effects to it ([Idempotency Keys](../../30.3-infra-patterns/02-failure-and-recovery/30.3.2.03-idempotency-keys.md)).

### 6. Certificate pinning in mobile and machine clients

A mobile app that pins the expected public key or CA can resist a compromised or mis-issued certificate from a trusted-but-wrong CA. The cost is operational: pin rotation must be planned, and pinning only a leaf certificate can break clients when that certificate changes.

## Common Mistakes

| Mistake | Consequence | Fix |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `rejectUnauthorized: false` / `NODE_TLS_REJECT_UNAUTHORIZED=0` | Encryption without authentication — trivially MITM-able; usually shipped to "fix" a CA issue | Trust the private CA explicitly (`ca:` option) instead of disabling verification |
| Certificate expires in production | Validating clients reject the affected endpoint | Automate issuance + reload (ACME), monitor at 30/14/7 days |
| Pin a leaf certificate in a mobile app | Pin mismatch can reject renewed certificates | Pin the CA or a set of public keys, and plan rotation |
| Long-lived internal certificates for services | Compromise window measured in years; identity rot | Short-lived certs with automatic rotation (mesh-style) |
| Wildcard certificate for everything | One key leak enables impersonation of names covered by that wildcard; broad exposure | Scope certs per service/domain where practical |
| Plaintext internal hop while assuming the network is safe | Any internal foothold reads all traffic | Re-encrypt or mTLS once the network is multi-tenant/multi-cloud |
| Certificate validation errors suppressed in CI | Tests pass against broken TLS; the failure surfaces in production | Fix the trust (mount the CA into the runner), never weaken the check |
| Treating SNI as secret | Assuming the hostname is hidden by TLS | It is cleartext (unless ECH); treat DNS + SNI as observable metadata |
| Serving HTTP and redirecting to HTTPS with no HSTS | First request is hijackable; cookie theft on downgrade | Enable HSTS (short `max-age` first), then `preload` deliberately |
| Not setting `X-Forwarded-Proto` at the terminator | App generates `http://` links and cookie `secure` logic misfires | Set forwarding headers and trust them only from the proxy |
| Enabling 0-RTT for state-changing endpoints | Replay produces duplicate side effects | Restrict 0-RTT to operations proven safe under replay across their processing path |

## Best Practices

1. **Use current TLS versions and deployment guidance.** Prefer TLS 1.3; keep TLS 1.2 only for clients that require it and configure it using the current BCP 195 guidance. New protocols using TLS are required to support TLS 1.3.
2. **Automate the certificate lifecycle end to end**: ACME issuance, reload hook, expiry monitoring. A manual path still requires an owned renewal and deployment process.
3. **Never disable verification.** If you need to trust a private CA, configure the trust anchor explicitly; if you need mutual identity, use mTLS.
4. **Decide the termination point deliberately** and document the trust boundary it implies — "terminated at edge, plaintext inside the VPC" is a sentence a reviewer must be able to find.
5. **Enable resumption** (session cache/tickets) to reduce handshake work for returning clients — and protect/rotate ticket keys, since they are key material.
6. **Accept 0-RTT only when the application can safely handle replay.** Idempotency keys may help for mutations, but must be implemented across the actual processing path.
7. **Roll out HSTS in stages**: short `max-age`, verify, then lengthen and consider `preload`.
8. **Alert on expiry and on negotiation regressions** (unexpected protocol version, cipher, or issuer change) — a sudden issuer change is a useful mis-issuance signal.
9. **Keep certificates and keys out of the image and out of git**: mount them, or inject from a secret manager ([Secrets Management](../../../20-backend/20.5-security/03-hardening-and-operations/20.5.3.04-secrets-management.md), [ConfigMaps & Secrets](../../../40-platform/40.2-kubernetes/02-networking-and-config/40.2.2.02-configmaps-secrets.md)).

## Summary

TLS checks server identity and establishes keys before protecting application data. A certificate binds a public key to names under a certificate authority; the client validates the chain and the requested hostname. The handshake uses public-key cryptography to establish shared keys, then symmetric cryptography protects the data. TLS 1.3 usually needs one round trip after TCP setup, while TLS 1.2 commonly needs two. Resumption can reduce setup time; 0-RTT has replay and forward-secrecy limitations. In production, choose where TLS ends, automate certificate renewal and deployment, and never disable certificate verification to hide a trust problem.

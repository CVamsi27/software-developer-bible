# TLS, HTTPS & the Certificate Lifecycle

When a browser opens an HTTPS connection, it must check the server identity and agree on encryption keys before sending private data. TLS (Transport Layer Security) handles this setup and protects data sent over the connection. A certificate helps the client check the server name; the handshake establishes keys; the record layer protects application data:

```text
browser → ClientHello → certificate check → keys → protected data. Skip a step, lose the guarantee.
```

## Definition

**TLS (Transport Layer Security)** protects data sent between two endpoints. A **handshake** negotiates connection settings, checks the server **certificate**, and establishes traffic keys. HTTP/1.1 and HTTP/2 commonly use TLS over TCP; HTTP/3 uses QUIC, which incorporates TLS 1.3 into its connection setup.

> **Textbook Definition:** Transport Layer Security (TLS) negotiates cryptographic keys and authenticates the server, then protects application data with confidentiality and integrity. For TLS over TCP, the TLS record protocol carries that data; QUIC reuses the TLS handshake and key schedule but protects QUIC packets itself. Certificate validation binds a public key to the expected service identity.

## First Principles

TLS addresses several problems on an untrusted network:

1. **The network is hostile, and the two parties have no prior relationship.** An attacker may observe or modify network traffic. Key agreement lets both endpoints derive matching keys without sending those keys across the network. Diffie–Hellman is one way to do this.
2. **Public-key operations and bulk symmetric encryption solve different problems and have different costs.** TLS uses public-key agreement/authentication rather than applying that machinery to every payload byte. This forces the **hybrid** design: use the expensive primitive minimally (to agree a key, and to prove identity), then switch to a fast symmetric cipher for all the actual bytes.
3. **Encryption alone does not establish the peer identity.** If you cannot be sure *whose* key you agreed with, a man-in-the-middle performs the same handshake twice and reads everything. Since clients have no out-of-band relationship with servers, a browser commonly relies on trusted certificate authorities (CAs) installed in advance; private protocols can use other explicitly provisioned trust anchors — hence certificate authorities and the root trust stores baked into operating systems.
4. **Compromising today's long-term key must not decrypt yesterday's traffic.** If the session key were derived solely from a static private key, stealing that key would unlock recorded history. Ephemeral Diffie–Hellman key exchange can provide **forward secrecy**: later theft of the certificate private key alone does not reveal past traffic protected by those ephemeral session keys. The property depends on the negotiated key exchange and key handling.
5. **Servers host many names on one address, and clients need to negotiate versions and protocols.** The client may include the target hostname using **Server Name Indication (SNI)** and offer an application protocol using **Application-Layer Protocol Negotiation (ALPN)**. In standard TLS these fields are generally visible in the ClientHello; Encrypted Client Hello (ECH) can protect some ClientHello fields when supported and configured.

The boundary is plain: **when correctly configured and certificate validation succeeds, TLS provides confidentiality, integrity, and server authentication. It does not give you availability, authorization, or protection from a compromised endpoint.** Everything after the handshake is still your application's problem.

## 1. Complete a full handshake before sending data

**HTTPS** is HTTP protected by TLS. **Elliptic-curve Diffie–Hellman ephemeral (ECDHE)** agrees a temporary shared secret. **HKDF**, an HMAC-based key derivation function, derives distinct traffic keys from secret and transcript inputs. **Authenticated encryption with associated data (AEAD)** encrypts records and detects tampering while authenticating selected unencrypted metadata. **ALPN** selects a supported protocol such as HTTP/2; it never implements that protocol.

For TLS over TCP, a **record layer** uses those keys to protect application data. QUIC uses TLS handshake/key derivation but protects its own packets instead of carrying TLS application-data records. Client certificates can also be used when both sides need to authenticate.

```text
HTTP/1.1 or HTTP/2:  HTTP → TLS record layer → TCP → IP
                           (TLS handshake derives traffic keys)

HTTP/3:              HTTP/3 → QUIC streams and packet protection → UDP → IP
                                (TLS 1.3 handshake derives QUIC keys)

QUIC uses the TLS handshake and key schedule, but protects QUIC packets
instead of carrying TLS application-data records.
```

| Concept | What it actually is | What people wrongly assume |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| Certificate | A CA's signed statement binding a public key to a name | "A guarantee the site is safe" |
| Root store | Pre-installed trusted CAs shipped by OS/browser | "Something the server sends" |
| Chain of trust | Leaf ← intermediate ← root, each signed by the next | "The server's cert is signed directly by the root" |
| Server Name Indication (SNI) | Ordinary `ClientHello` exposes the requested name; deployed ECH can encrypt the inner name while leaving a public name visible | "Everything is encrypted from byte one" |
| Forward secrecy | Later long-term-key compromise cannot recover past session secrets under the chosen key exchange | "Rotating certs gives me forward secrecy" |
| Mutual TLS (mTLS) | Client also presents a certificate | "TLS always authenticates the client too" |

```text
Common certificate handshake over an established TCP connection:

TLS 1.2 (representative ECDHE exchange; exact messages vary by suite):
client → ClientHello
server → ServerHello, Certificate, ServerKeyExchange, ServerHelloDone
client → ClientKeyExchange, ChangeCipherSpec, Finished
server → ChangeCipherSpec, Finished

TLS 1.3:
client → ClientHello with key_share
server → ServerHello with key_share,
         encrypted EncryptedExtensions, Certificate, CertificateVerify, Finished
client → encrypted Finished (and application data as permitted)
```

This is the normal full certificate-authenticated flow, omitting optional client authentication and retry messages. In TLS 1.3, the server sends its Finished in its first flight; it never waits for the client's Finished and then sends a second server Finished.

A common full TLS 1.3 handshake takes one round trip after TCP setup: the client sends a key share in its first flight, so the server derives handshake keys immediately.

A HelloRetryRequest can add a round trip if the server needs a different key-share group. Most of the server flight after ServerHello is encrypted, including its certificate.

TLS 1.3 also removes legacy record ciphers such as RC4 and CBC, static RSA key exchange, and renegotiation.

A full TLS 1.2 handshake commonly takes two round trips after TCP setup; TLS 1.2 resumption commonly takes one. TLS 1.3 resumption also commonly takes one round trip, while 0-RTT allows eligible application data before that handshake finishes. Reusing an existing connection avoids another handshake altogether.

For TLS 1.2 deployments, follow BCP 195 (Best Current Practice 195): RFC 10015 deprecates RSA and finite-field DH key-exchange suites and discourages static ECDH. This is about key exchange; it never means RSA certificate signatures are forbidden. New protocols using TLS must require TLS 1.3, while an existing service may retain TLS 1.2 for compatibility if configured to current guidance.

## 2. Agree asymmetrically, then switch to symmetric

```text
HANDSHAKE (asymmetric — expensive, used minimally)
  ECDHE: client and server each send a public ephemeral value;
         both derive the same shared secret S. An eavesdropper sees
         both public values and still cannot compute S (discrete log).
  AUTHENTICATION: TLS 1.3 CertificateVerify (or the signed
         ServerKeyExchange in a TLS 1.2 ECDHE handshake) proves possession
         of the private key matching the certificate and binds it to this
         exchange. Finished verifies the transcript with the derived keys.
                    ↓ derive (HKDF)
SESSION KEYS (symmetric — fast, used for all bulk data)
  AEAD record layer: AES-128/256-GCM or ChaCha20-Poly1305
         → confidentiality + integrity in one pass, per record
```

These checks solve different problems: the CA signature authenticates the certificate; the protocol proves the peer holds its private key for this handshake (CertificateVerify in TLS 1.3, or signed ServerKeyExchange in a TLS 1.2 ECDHE exchange); Finished confirms the peer derived the same keys and transcript. Diffie–Hellman without those checks would stop passive eavesdropping but never an active man-in-the-middle.

## 3. Validate the chain to the intended identity

A certificate is a signed assertion: `{name(s), public key, validity window, issuer} + CA signature`. The client verifies a **chain** up to a root it already trusts:

```text
ROOT CA (usually in the OS/browser trust store; servers commonly omit it)
  └─ signs ─► INTERMEDIATE CA (sent by the server)
                └─ signs ─► LEAF CERT (your domain, sent by the server)

Before accepting the connection, the client checks that the chain reaches a trusted root and that the identity matches the one it intended to reach. Checks include:
  1. A valid signature chain to a trusted root
  2. A matching subjectAltName (SAN) identifier: DNS names use `dNSName`, IP addresses use `iPAddress`, and a DNS alias does not replace the original expected name
  3. The certificate's validity period and applicable client revocation policy
  4. Certificate constraints such as path length, extended key usage, and key usage
  ⟶ a fatal validation failure aborts the handshake; it is not a warning to click through.
```

Validation levels differ in *how much identity* the CA verified — degree of assurance, not cryptographic strength:

| Type | CA verifies | Typical use | Browser signal |
| -------------- | ------------------------------------------------ | --------------------------------------- | ------------------------------------------- |
| DV (Domain) | Control of the domain only (file/DNS/HTTP) | Most APIs and modern sites | Browser security indicator varies |
| OV (Org) | Domain + organisation existence | Enterprise, some commerce | Details on inspection |
| EV (Extended) | Stricter organisational vetting | Specialized business and legal contexts | UI varies; no universal stronger encryption |

The current service-identity rules require names in the certificate's `subjectAltName`; a `Common Name` fallback is not valid. Wildcards match only as the complete left-most DNS label (for example, `*.example.com` can match `api.example.com`, not `v2.api.example.com`).

Many publicly trusted DV certificates are issued through **ACME** (Automatic Certificate Management Environment). A `DNS-01` challenge proves domain control by publishing a `TXT` record, which makes DNS part of that issuance workflow ([DNS & Name Resolution](30.2.1.22-dns-and-name-resolution.md)). Let's Encrypt is one certificate authority supporting ACME.

## 4. Bound resumption, 0-RTT, revocation, and exposure

Forward secrecy means later theft of a server's long-term certificate key alone never reveals recorded sessions using fresh ephemeral key exchange. It depends on the negotiated mode and correct handling of ephemeral secrets.

Resumption lets a returning client and server authenticate with a pre-shared key (PSK) derived from an earlier session, so the server omits a new certificate and CertificateVerify signature. In TLS 1.3, PSK-only resumption adds no fresh forward secrecy; PSK-DHE resumption combines the PSK with new ephemeral Diffie–Hellman. Both full and resumed TLS 1.3 handshakes commonly take one round trip, so resumption mainly saves certificate bytes and some authentication work. Ticket keys protect reusable session state and need a defined rotation and sharing policy.

TLS 1.3 0-RTT lets a returning client send early application data in its first flight, before the handshake completes. A server can receive that data more than once because early data is replayable, and it holds no full forward secrecy. Accept it only for operations whose complete processing path tolerates replay; an HTTP method name or an idempotency key by itself never guarantees that.

- **Revocation** mechanisms include certificate revocation lists (CRLs), OCSP, and OCSP stapling (the server attaches a signed OCSP response). Client support and checking behavior vary, so never assume every client performs a live revocation check. Match the mechanism to the issuer: Let's Encrypt ended OCSP on 6 August 2025 and now publishes revocation information through CRLs.
- **HSTS** (`Strict-Transport-Security`) tells a browser that received the header over HTTPS to use HTTPS for the stated period. It cannot protect a first visit unless the domain is preloaded or another secure starting point exists. Roll it out with a short `max-age` first; add `includeSubDomains` or pursue preload only after every covered host is HTTPS-ready. Preloading is a separate commitment ([Web Security](../../../20-backend/20.5-security/03-hardening-and-operations/20.5.3.02-web-security.md)).
- **What TLS still exposes:** the destination IP, the port, traffic volumes and timings. Without negotiated ECH, the **SNI hostname** is also visible. ECH protects selected ClientHello fields but never hides the server IP, all traffic patterns, or the DNS query from the chosen resolver.

## 5. Terminate where the trust boundary is real

| Termination point | What you get | What you give up |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| **Load balancer / edge / CDN** | Central cert management, cheap handshake offload, Layer 7 (L7) routing, web application firewall (WAF) | Payload is plaintext inside your network — trust boundary must be real |
| **Application** | End-to-end encryption to the process that owns the data | Handshake CPU on app hosts, per-service cert sprawl |
| **Both (re-encrypt)** | Edge routing + encryption on the internal hop | Two cert lifecycles, more moving parts |
| **mTLS end-to-end** | Cryptographic client identity for the connection | Still needs authorization policy and certificate lifecycle management |

Choose the termination point from the trust boundary and operational needs. If TLS ends at a load balancer, the next hop is a separate connection: re-encryption creates a new authenticated connection to the backend, not end-to-end TLS from the original client. mTLS authenticates a client certificate at the connection; the application must still map that identity to a principal and authorize each operation. For service-to-service mTLS, the server requests a client certificate and validates it against a private CA. The example below shows the TLS boundary only; map the verified certificate identity to an application principal and apply authorization separately:

```nginx
server {
    listen 8443 ssl;
    server_name orders.internal.example;

    ssl_certificate     /etc/tls/orders.fullchain.pem;
    ssl_certificate_key /etc/tls/orders.key;
    ssl_client_certificate /etc/tls/service-ca.pem;
    ssl_verify_client on;
}
```

TLS termination at a reverse proxy is safe only when the backend hop holds an explicit trust decision. This illustrative Nginx configuration terminates public TLS and forwards plain HTTP to a trusted upstream; it is no universal cipher policy or complete production configuration:

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:TLS:10m;
    ssl_session_timeout 10m;

    # Choose TLS 1.2 policy for the installed Nginx/OpenSSL build.
    # ssl_ciphers does not configure TLS 1.3 cipher suites.

    # Begin with a short policy while validating every browser-facing hostname.
    add_header Strict-Transport-Security "max-age=300" always;

    location / {
        proxy_pass http://app_upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

A shared Nginx session cache supports reuse and, since Nginx 1.23.2, also manages local session-ticket keys. A multi-node deployment explicitly sharing ticket keys must protect and rotate those keys; disabling tickets is a valid choice when that lifecycle is unmanaged, with a resumption-cost trade-off. Nginx directives and behavior depend on the installed version and TLS library, so validate the configuration against their current documentation.

## 6. Probe the served certificate after every renewal

Inspect a live endpoint with hostname and chain verification enabled. The server name is sent as SNI, while `-verify_hostname` checks it against the certificate identity:

```bash
openssl s_client -connect api.example.com:443 \
  -servername api.example.com \
  -verify_hostname api.example.com -verify_return_error -showcerts </dev/null
```

The output includes the certificates presented by the endpoint, the negotiated TLS version and cipher, and the verification result. Inspect the certificate actually served after every renewal or load-balancer change.

A Node.js probe can alert before the endpoint's leaf certificate expires. Pass a DNS hostname; `tls.connect` validates the chain and hostname by default. Keep verification enabled and treat errors as failed probes:

```typescript
import tls from "node:tls";

function daysUntilExpiry(host: string, timeoutMs = 5_000): Promise<number> {
  return new Promise((resolve, reject) => {
    let settled = false;
    let timer: ReturnType<typeof setTimeout> | undefined;
    const socket = tls.connect({
      host,
      port: 443,
      servername: host,
      rejectUnauthorized: true,
      minVersion: "TLSv1.2",
    });

    const finish = (error?: Error, days?: number) => {
      if (settled) return;
      settled = true;
      if (timer) clearTimeout(timer);
      socket.destroy();
      if (error) reject(error);
      else resolve(days!);
    };

    timer = setTimeout(() => finish(new Error("TLS probe deadline exceeded")), timeoutMs);
    socket.once("error", finish);
    socket.once("close", () => {
      if (!settled) finish(new Error("TLS probe closed before the handshake completed"));
    });
    socket.once("secureConnect", () => {
      if (!socket.authorized) {
        return finish(new Error(String(socket.authorizationError ?? "certificate not authorized")));
      }
      const validTo = socket.getPeerCertificate().valid_to;
      const expiresAt = Date.parse(validTo ?? "");
      if (!Number.isFinite(expiresAt)) return finish(new Error("peer certificate has no valid expiry"));
      finish(undefined, (expiresAt - Date.now()) / 86_400_000);
    });
  });
}

// This monitors the leaf certificate presented by one endpoint, not every chain certificate.
daysUntilExpiry("api.example.com").then((days) => {
  console.log(Math.floor(days) + " days remaining");
});
```

A TLS client must authenticate the server as well as encrypt traffic. In Node.js, leave `rejectUnauthorized` enabled. For a private service CA, add that CA as a trust anchor with `ca`; never set `rejectUnauthorized: false` or `NODE_TLS_REJECT_UNAUTHORIZED=0` to silence a trust error. A validation failure should be fixed by correcting the chain, hostname, or configured trust store.

Issuance is only one part of renewal. ACME proves control of a name — for example, DNS-01 publishes a TXT record and suits wildcard certificates — but obtaining a new certificate never puts it on every serving endpoint. Treat renewal as a deployment:

1. Automate the ACME challenge with narrowly scoped DNS or web-server credentials; check CAA policy and protect the challenge credentials.
2. Install the leaf certificate and required intermediate chain, and keep the private key in a secret store or protected mount rather than source control or a container image.
3. Reload or roll each serving instance only after the new files are present. Keep the previous working certificate available until the new deployment is healthy.
4. Probe the public hostname after rollout. Verify the served chain, SAN, expiry, and negotiated protocol; alert early enough to repair a failed renewal or reload.

For Let's Encrypt certificates, never configure OCSP stapling: its OCSP service ended on 6 August 2025. Follow the issuer's current revocation mechanism and the behavior of the clients supported.

## Summary

TLS authenticates the intended service and agrees on keys before application data is protected. The certificate chain establishes trust in the server's public key; SAN matching checks that it is the service the client requested. Ephemeral key exchange, HKDF and AEAD protect the session, while protocol version and resumption mode determine setup cost and forward-secrecy properties.

TLS 1.3 is the required baseline for new protocols; TLS 1.2 remains a compatibility option only with current guidance. In a deployed system, the security boundary is the termination point, and the certificate lifecycle is complete only after renewal reaches and passes a probe of every serving endpoint.

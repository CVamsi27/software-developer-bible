# WhatsApp System Design

## Definition

A WhatsApp-like service lets participants send private messages across several devices, including devices that are temporarily offline. The hard part is deciding what “sent,” “delivered” and “read” mean when a connection disappears between a durable write and its acknowledgment.

> **Textbook Definition:** A large-scale messaging service routes conversation messages among authenticated participants and their devices, with explicit contracts for ordering, offline delivery, encryption, and acknowledgments.

This is a proposed interview design, not a description of WhatsApp's internal deployment or measured production capacity. The generic [chat system](30.2.2.15-chat-system.md) owns transport and shared chat mechanics; this case emphasizes encrypted multi-device delivery and receipts.

## First Principles

A sender cannot distinguish a lost request from a lost acknowledgment. Retrying is necessary, so the message must retain the same identity across attempts. A durable uniqueness constraint turns retries into the same accepted message rather than another displayed copy.

The service cannot know that a recipient received a message merely because a socket write succeeded. The recipient must acknowledge receipt after its own durable storage. Reading is a separate client action. Several devices can acknowledge at different times, so define whether a user's receipt means one device, every active device or a particular device.

End-to-end encryption means only intended participant devices possess the keys that decrypt content. The routing service still sees metadata needed to deliver ciphertext. A server-held shared key, or a key derived from a public conversation ID, does not provide that boundary.

## Requirements and boundaries

Support direct/group messages, media attachments, multi-device synchronization, bounded history retrieval, optional receipts and presence. Choose explicit group-size and retention limits for the exercise. A strict server arrival sequence is one possible conversation order; concurrent sends do not have an objectively observable global order.

Text search over plaintext belongs on authorized clients when the server cannot decrypt content. Voice/video needs a separate media transport, signaling and relay design; a WebSocket message path does not carry a complete calling system. Presence is an expiring hint and can be hidden by privacy settings, not proof that a user is available.

Specify latency from durable acceptance to a particular recipient acknowledgment under a stated network condition. Availability, connection counts and maximum group size are targets to validate, not consequences of choosing a broker.

## Capacity follows a stated workload

Use these hypothetical assumptions consistently:

| Quantity | Calculation | Meaning |
| ------------------------------ | ---------------------------- | ------------------------------------------------------- |
| Messages/day | 500 million active users ×40 | 20 billion accepted sends |
| Average sends/second | 20 billion /86,400 | ≈231,481; peak factor is separate |
| Text bytes/day | 20 billion ×100 bytes | 2 TB before metadata, replication and fan-out |
| Text/year | 2 TB ×365 | 730 TB with one retained copy |
| Media/year at 10× text bytes | 730 TB ×10 | 7.3 PB/year, or 20 TB/day |
| Mean payload transfer | 22 TB/day /86,400 | ≈255 MB/s before recipient copies and protocol overhead |
| Connections | 500 million ×30% concurrent | 150 million connections |
| Connection state at 10 KB each | 150 million ×10 KB | 1.5 TB aggregate memory before runtime overhead |

For one recipient with three devices, one send can generate three envelope deliveries plus retries. Group fan-out and attachment download dominate different resources. A claimed 100,000 connections per host requires measured file-descriptor, TLS, queue, bandwidth and reconnect behavior; dividing the target by that number is only an initial estimate.

## How the components fit

```text
Sender device: stable ID + encrypted envelopes
  → authenticated connection gateway
  → conversation authority: membership + unique accepted message + sequence
  → durable dispatch record, committed with acceptance
  → workers route ciphertext to authorized recipient devices
  → recipient durable receipt → delivery status
  → recipient read action → optional read status

Media: client encryption → authorized object upload → opaque reference
Reconnect: device cursor → bounded replay → apply → persist cursor
```

The conversation authority serializes accepted writes for that conversation. A broker key can preserve a partition's order, but does not automatically establish one order across multiple producers, migrations and databases. Bind sequence allocation and message acceptance to the authoritative write. Fence an old owner before a failover accepts competing writes.

## Example: acceptance survives a lost response

The following PostgreSQL schema is a small relational teaching model. It does not implement encryption, sharding, transport or delivery workers.

```sql
CREATE TABLE conversations (
  id BIGINT PRIMARY KEY,
  next_sequence BIGINT NOT NULL DEFAULT 0 CHECK (next_sequence >= 0)
);
CREATE TABLE participants (
  conversation_id BIGINT REFERENCES conversations(id),
  user_id BIGINT NOT NULL,
  PRIMARY KEY (conversation_id, user_id)
);
CREATE TABLE messages (
  conversation_id BIGINT NOT NULL REFERENCES conversations(id),
  sequence BIGINT NOT NULL CHECK (sequence > 0),
  sender_id BIGINT NOT NULL,
  client_message_id UUID NOT NULL,
  ciphertext BYTEA NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (conversation_id, sequence),
  UNIQUE (conversation_id, sender_id, client_message_id),
  FOREIGN KEY (conversation_id, sender_id)
    REFERENCES participants(conversation_id, user_id)
);
CREATE TABLE dispatch_outbox (
  conversation_id BIGINT NOT NULL,
  sequence BIGINT NOT NULL,
  dispatched_at TIMESTAMPTZ,
  PRIMARY KEY (conversation_id, sequence),
  FOREIGN KEY (conversation_id, sequence)
    REFERENCES messages(conversation_id, sequence)
);
```

For an authenticated sender, perform the following steps in one transaction:

1. Lock the conversation row. Verify current membership and permissions; coordinate removals through the same authority so a stale membership read cannot bypass revocation.
2. Look up `(conversation, sender, client_message_id)`. If it exists, verify the request matches the accepted payload and return its existing sequence. A reused ID with different content is a conflict.
3. Increment the conversation's sequence and insert the ciphertext message and outbox row. Commit before returning durable acceptance.
4. Dispatch workers retry pending outbox rows. Recipient devices deduplicate the message identity and acknowledge after their own storage succeeds.

Suppose message `m 1` commits at sequence 42, but the HTTP/socket response is lost. The sender retries `m 1`, and receives 42; the service must not allocate 43 for a second displayed copy. If a worker delivers 42 and crashes before marking its outbox row, it may redeliver 42. Device deduplication handles that second failure independently of server acceptance deduplication.

The composite primary key also makes a future conversation-partitioned table possible: PostgreSQL partitioned uniqueness must include its partition key. A single-column message ID primary key on a table partitioned by conversation would not enforce that schema contract. Keep partition creation, routing and migration as explicit implementation work.

## Encryption changes the whole design

Do not hand-build a messaging cryptosystem from a password KDF and conversation ID. A production protocol needs reviewed device identity keys, authenticated key agreement, message-key evolution, replay handling and membership-change behavior. Verify device keys through a suitable trust/verification mechanism. Server-controlled key substitution remains a threat if participants never verify identities.

For multi-device accounts, encrypt or distribute envelopes according to the chosen reviewed protocol and device registry. A newly linked device must not silently receive all past plaintext without an explicit history-transfer/backup policy. Removing a device must stop future authorized envelope delivery and rotate relevant keys as the protocol requires; it cannot erase copies already decrypted.

Encrypt media on the client before upload, keep decryption material with authorized recipients, and use bounded authorized references to ciphertext objects. Do not place plaintext message snippets in provider push notifications when the service cannot read those messages; use a minimal “new message” hint and fetch authorized ciphertext. Server logs and analytics should avoid message contents and unnecessary relationship metadata.

Encryption protects content under its threat model. It does not prevent abusive authenticated participants, conceal every traffic pattern or enforce deletion on a recipient's independent copy.

## Receipts, presence and replay

| Signal | What establishes it | What it does not prove |
| ------------------- | ------------------------------------------ | ------------------------------------------------ |
| Accepted | Authoritative durable message commit | Recipient delivery |
| Delivered to device | Authenticated device receipt after storage | User read the content |
| Read | Explicit authorized client read marker | Attention, comprehension or every device reading |
| Online | Recent connection lease/heartbeat | Delivery capacity or consent to reveal presence |

Maintain monotonic per-device receive cursors, bounded queues and a reconnect replay contract. Persist the cursor after applying messages; persisting it first can permanently skip data after a crash. A cursor older than retention needs an explicit gap/resynchronization response, not a fabricated complete history.

Use a lease per connection/device instead of one user-wide TTL that another device continually renews. Distinguish current connection generations so a delayed disconnect from an old socket cannot mark a new connection offline. Slow consumers need bounded buffering and controlled reconnect, rather than unlimited gateway memory.

## Real-world decisions

**Retention and offline access.** Decide whether the service retains encrypted history, only undelivered envelopes, or an optional encrypted backup. Retention affects long-offline devices, deletion, storage and recovery; “persist forever” conflicts with an undefined privacy policy.

**Groups.** Check membership at send, history access and event delivery. Define whether a joining member can read past messages and when a removed member loses future access. Avoid materializing unlimited per-message/per-user receipts for huge groups; cumulative cursors and aggregate receipt semantics can bound state.

**Storage and regions.** Choose from required query patterns, write volume and authoritative transactions. Cassandra does not replace the message identity/order contract, and PostgreSQL does not supply unlimited shard capacity. Regional routing must define one active conversation authority and failover fencing; asynchronous mirroring alone does not provide zero-loss failover.

**Cache boundaries.** Cache ciphertext/history under membership-aware access checks. A cache hit must not bypass revoked access. Presence cache loss means “unknown” or reduced functionality; querying the database does not reconstruct which sockets remain alive.

**Push and connection routing.** Provider acceptance is not delivery. A push is a hint to synchronize, not the durable message itself. Reconnects need backoff with jitter; mass reconnect can saturate authentication, routing and storage even when steady-state connections fit in memory.

## Mistakes

- Deriving secret keys from public identifiers or storing decrypting keys on the routing server while calling the result end-to-end encryption.
- Generating a fresh message ID on each retry or equating a UUID with exactly-once delivery.
- Marking a message delivered after writing to a socket, before a recipient acknowledgment.
- Searching plaintext or sending plaintext push snippets without reconciling the encryption boundary.
- Treating broker partitioning, automatic failover or a successful cache lookup as sufficient ordering and permission guarantees.

## Best practices

Test the two distinct duplicate windows: acceptance followed by lost response, and recipient delivery followed by lost receipt. Test concurrent sends, membership revocation, cursor gaps, slow devices and connection-generation races. Measure accepted-to-device latency and replay backlog separately from gateway availability. Use reviewed cryptographic protocols and independent security assessment before handling real private messages.

## Summary

An encrypted messaging design separates durable acceptance, device delivery and user read receipts. Stable IDs and authoritative sequence allocation handle retries and ordering; bounded replay handles offline devices. End-to-end encryption moves plaintext processing and key ownership to participant devices, changing search, media, backups and push behavior. Capacity estimates must account for fan-out and failure recovery rather than treating a connection count as a deployment plan.

# Uber System Design

A map shows a driver near the rider, but that position may already be stale and the driver may have accepted another trip. Even a fresh nearby dot is only a candidate: roads, availability and a competing booking determine whether the driver can actually take this ride.

## Definition

An Uber-like marketplace connects riders to eligible nearby drivers, then coordinates pickup, the trip and its financial outcome. The map gives a changing estimate of supply; only the trip authority can decide whether a driver has actually accepted an assignment.

> **Textbook Definition:** A ride-hailing service matches passenger requests with available drivers using location and trip state, then coordinates acceptance, journey tracking, pricing, and payment under concurrent updates.

This is a proposed interview design. Its workload and objectives are hypothetical, not statements about Uber's current deployment. The [Lyft case](30.2.2.19-lyft.md) owns the complete driver-and-ride assignment invariant and transaction trace; this chapter focuses on fresh location discovery, marketplace decisions and the trip's boundaries.

## First Principles

Positions change faster than durable trip state. Keeping every latest position in one transactional row can create contention, while trusting a cache to allocate a ride can double-book a driver. Separate approximate discovery from authoritative booking.

Nearness is not travel time. A driver across a river may be physically closer and take longer to reach the pickup. Candidate search should cheaply reduce the set before spending a bounded routing budget on road estimates. No ranking formula can create supply when there are no eligible drivers.

Network failure also differs from driver abandonment. A moving trip may continue during a brief disconnection. Automatically replacing a driver after a missed location update can create conflicting real-world journeys.

## Requirements and consistent assumptions

Support authenticated quotes and booking, eligible-driver discovery, expiring offers, cancellation, trip-state transitions, live positions, receipts, payment recovery and ratings. Separate objectives for request-to-offer, offer acceptance, location freshness and completed payments. GPS accuracy and arrival latency depend on devices, road conditions and supply; a backend design cannot promise ten-meter accuracy everywhere.

For one hypothetical workload, 20 million active riders taking two trips/day means 40 million trips/day, approximately 463 trips/second on average. A peak of one million requests/hour is only 278/second and therefore inconsistent with that average. Choose a peak factor, such as 5×, giving about 2,315 requests/second; validate it against the actual arrival mix.

At 5 KB/trip, metadata adds 200 GB/day before indexes and replication. One million simultaneously reporting drivers, each every four seconds, produces 250,000 position updates/second. At 200 bytes/report, this is 50 MB/s **during that concurrency level**, or 4.32 TB/day if sustained. Retaining every position needs a justified purpose and retention policy. A server-count estimate requires measured per-host ingestion, fan-out and failover capacity.

## How the components fit

```text
Driver → identity/sequence validation → latest position index
                                         ↓
Rider → quote → booking → dispatch → eligible shortlist
                                         ↓
                                  bounded road ETA
                                         ↓
                           authoritative offer acceptance
                                         ↓
                          trip transaction + event outbox
                                         ↓
                          tracking / payment / receipts
```

Keep location ingest and trip decisions independent enough that a tracking backlog cannot exhaust booking capacity. Partition location streams by driver identity for ordering, and use explicit regional/cell routing for queries. A city-wide partition can become a hotspot; region ownership and border moves need a handoff contract.

## Location records must carry freshness and generation

A location report should include coordinates, observation time, session generation and a sequence that increases within that generation. The server records receive time separately. Reject invalid ranges and old reports from a superseded session, and treat suspicious speed/accuracy signals as evidence for review rather than proof of physical truth.

A spatial index maps position to nearby candidates. Redis GEO or a PostGIS spatial index can serve this role at different measured workloads. Modern Redis `GEOSEARCH` expresses radius or box discovery; PostGIS `ST_DWithin` can filter radius queries through an available GiST spatial index when the query and column types support it. The result still needs current availability, vehicle class, access policy and freshness checks.

Expiring a driver's metadata hash does not remove its member from a separate geo sorted set. Query-time stale filtering and explicit member cleanup are necessary. A user-wide TTL also cannot distinguish several device sessions. Coordinate keys atomically where required, and include the latest generation so delayed disconnects do not remove new sessions.

Do not use process-randomized Python `hash()` as a cross-host shard contract. Choose a documented stable hash/routing version and plan migrations; changing a modulus moves ownership. Latitude/longitude degree cells do not have one fixed physical width at all latitudes.

## Example: distance is only a shortlist signal

The following complete Python function returns a great-circle distance in kilometers. It is a coarse geographic filter, not a road route, arrival guarantee or dispatcher.

```python
import math

def straight_line_km(lat1, lon1, lat2, lon2):
    values = (lat1, lon1, lat2, lon2)
    if not all(math.isfinite(v) for v in values):
        raise ValueError("Coordinates must be finite")
    if not (-90 <= lat1 <= 90 and -90 <= lat2 <= 90
            and -180 <= lon1 <= 180 and -180 <= lon2 <= 180):
        raise ValueError("Coordinates out of range")
    phi1, phi2 = map(math.radians, (lat1, lat2))
    delta_phi = phi2 - phi1
    delta_lon = math.radians(lon2 - lon1)
    a = (math.sin(delta_phi / 2) ** 2
         + math.cos(phi1) * math.cos(phi2)
         * math.sin(delta_lon / 2) ** 2)
    return 6371.0088 * 2 * math.asin(math.sqrt(min(1.0, max(0.0, a))))

print(round(straight_line_km(0, 0, 0, 1), 3))  # 111.195 km
```

Trace a rider beside a bridge. Candidate A is 0.5 km away across the river; candidate B is 1 km away on the same bank. Straight-line ranking chooses A. A road-routing lookup may choose B because A must travel several kilometers to cross. Expanding the first nonempty search ring therefore does not prove the globally best pickup ETA.

Limit radius, candidates, routing calls and total dispatch time. Exclude incompatible vehicles before scoring, rather than allowing an incorrect vehicle to win with a lower score. If scoring combines distance, acceptance history and ratings, normalize their units, justify weights and inspect fairness and manipulation; arbitrary 40/30/20/10 weights are a proposal, not an optimal policy.

## An offer is not an assignment

The offer names driver, ride, offer ID, expiry and expected version. Identity comes from the authenticated session rather than a body-provided rider/driver ID. Acceptance must claim both scarce resources in one authoritative transaction: one active ride per driver and one active driver per ride. See the [Lyft assignment model](30.2.2.19-lyft.md) for schema and the two-ride race.

A cache flag set after a ride update leaves a double-booking window. A successful push only means a notification provider or gateway accepted work; the driver must explicitly accept, and the transaction must recheck expiry and current state. Repeated acceptance of the same accepted offer should return the existing result; a late different offer must not overwrite it.

Publish trip events through an outbox committed beside state, then deduplicate downstream events. A Kafka event alone does not atomically update trip and driver state across unrelated stores.

## Quotes and transitions have independent rules

A quote records currency, precise monetary amount, pricing version, applicable product and expiry. Derive charges from server-approved rules and authoritative trip facts; do not trust a client-provided final fare. Dynamic pricing must handle stale demand/supply, zero supply and oscillation. A maximum multiplier is a product/legal policy to verify for the market, not a universal constant.

Use explicit permitted state transitions and expected versions for requested, matched, arrived, in-progress, completed and cancelled. Cancellation racing trip start must have one recorded authoritative outcome. Release driver availability exactly with the winning transition and do not let a delayed completion event release a driver assigned to a newer ride.

A completed trip and paid trip are distinct states. Payment needs stable command identity, provider outcome reconciliation, ledger records and retry rules. Do not silently switch a card booking to cash when a provider fails. Authorization, capture, refund and disputes follow their own lifecycle; [payment gateway](30.2.2.06-payment-gateway.md) owns that mechanism. Using a provider does not automatically establish the application's PCI compliance.

## Recovery and privacy

| Failure | Controlled response |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Stale location index | Exclude stale drivers; label tracking unavailable and reduce new matching if safe supply cannot be established. |
| Routing unavailable | Use a clearly labeled bounded estimate or reject unsupported quotes; never invent precision. |
| Driver connection disappears | Check trip phase, timeout policy and contact/recovery path before reassignment; an ongoing journey cannot simply be replaced. |
| Dispatch overload | Bound waiting/queued requests, expire them and expose busy/no-driver outcomes; an unlimited queue hides failure. |
| Payment response lost | Reconcile the existing command/provider identity before charging again. |
| Region ownership changes | Fence old dispatch/assignment ownership and reject stale generations. |

Authorize live positions to the current trip participants and minimum operational roles. Public nearby-driver views can be approximate; avoid revealing exact independent driver histories. Retain telemetry only for a defined safety/product purpose, restrict access and audit sensitive access. Buffering old GPS reports must not overwrite current location on reconnect.

## Real-world decisions

Start with one region and a well-defined authoritative store if it satisfies measured demand. Introduce a distributed geo index when ingest/query evidence justifies the added consistency boundary. Use regional sharding to limit latency and failure scope, with explicit cross-border ownership; global read replicas cannot make remote primary writes locally fast.

Prefer bounded candidate selection with observable outcomes before proposing complex learned matching. Measure request-to-offer latency, no-driver rate, offer expiry, location age, conflict rejections, pickup ETA error and payment pending duration. A low API response time can coexist with poor pickup outcomes or broken assignment.

## Test the failure boundaries

Send old and out-of-order reports after a driver reconnects, move drivers across cell and region boundaries, and verify stale candidates cannot overwrite current state. Race two acceptances for one driver, cancellation against trip start, and a delayed completion against a newer assignment. Inject routing timeouts and payment responses lost after provider acceptance. Measure location age, request-to-offer latency, no-driver rate, offer expiry, pickup ETA error, assignment conflicts and payment-pending duration under skewed city demand. Keep location privacy and access audits in the same release evidence.

## Summary

A ride-hailing marketplace uses fresh approximate positions to find candidates, bounded road estimates to compare them and an authoritative transaction to assign both driver and ride. Quotes, trip transitions and payment have separate contracts. Correct recovery prevents stale telemetry, late events and disconnected drivers from creating conflicting real-world actions.

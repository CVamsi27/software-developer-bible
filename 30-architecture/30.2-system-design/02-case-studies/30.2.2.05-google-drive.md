# Google Drive System Design

## Definition

A Drive-like service lets users organize, share and version files while several devices maintain local copies. Uploading bytes is only one step: permissions, folder moves, edit conflicts and replay must remain understandable after devices reconnect.

> **Textbook Definition:** A collaborative file service stores versioned content and metadata, synchronizes replicas across devices, and resolves concurrent edits under explicit sharing and consistency policies.

This is an interview proposal, not a verified account of Google Drive internals. The [Dropbox case](30.2.2.18-dropbox.md) owns block hashing, upload-version conflicts and device replay. This chapter adds folder permissions, quota and the distinction between opaque-file synchronization and collaborative document operations.

## First Principles

A file has stable identity even when its name or folder changes. Treating the pathname as identity makes rename look like delete-and-recreate and loses references. Store immutable byte versions separately from mutable identity, placement and permissions.

An offline edit was authorized under a past view of the world. On reconnect, another editor may have changed the content or the owner may have revoked permission. The service must recheck current permission and the expected base version; it cannot silently accept every queued operation.

Changing a folder can affect many descendants. Evaluating inherited access avoids eagerly copying every permission, but requires bounded traversal, cycle prevention and a defined cache-invalidation boundary. A one-row share update does not imply constant-time authorization for the whole tree.

## Requirements and coherent estimates

Support upload/download, bounded listings, version history with an explicit retention policy, restore, device replay, sharing, folders, trash and quotas. A published version's bytes are immutable, but retention may later remove old versions. Collaboration is an additional document protocol, not automatic merging of arbitrary binary files. Choose which metadata writes are authoritative and which offline observations are provisional.

Illustrative assumptions: one billion files at 1 MB average occupy 1 PB of current bytes. Ten equally sized retained versions imply 10 PB; one billion metadata rows at 1 KB add 1 TB, so total is about 10.001 PB before replication, indexes and previews, not 11 PB. Actual history storage depends on churn, delta encoding and retention.

At 100 million active users transferring 10 MB/day, daily bytes are 1 PB and average throughput is about 11.6 GB/s. A 5× peak is about 57.9 GB/s; it is not 11.6 TB/s. Ten million concurrent sync operations at 100,000 completions/second imply an average 100-second residence time under steady state. State whether those are long polls, byte transfers or metadata operations before using the number for capacity.

Object durability percentages are provider- and configuration-specific and differ from application availability and restore correctness. Replication without tested backups and metadata recovery is not sufficient evidence for end-to-end durability.

## How the components fit

```text
Client → authenticated metadata authority → folder/version/quota/permissions
                      ↓                             ↓
              scoped upload intent           transaction + change log/outbox
                      ↓                             ↓
              immutable object bytes          device replay / search / preview
                      ↓                             ↓
              verified completion             notifications are sync hints

Document editor → separate reviewed operation protocol → checkpoints/history
```

An upload becomes visible through a metadata commit, not when a client finishes sending bytes:

1. Authorize the caller, reserve the expected quota, and issue a short-lived upload target scoped to one intent and object key.
2. After upload, verify the completed object and its actual size/checksum at the storage boundary. Do not treat client-reported metadata as proof that all bytes arrived.
3. In one metadata transaction, recheck current permission and expected file version, append the version, move `current_version`, finalize quota usage, and record the change through an outbox or equivalent durable log.
4. If publication fails, keep the bytes invisible and retry the same intent or reclaim the unreferenced object after a safe retention period. Garbage collection must recheck that no retained version or live upload references it.

## Example: folder identity and a current version

The following executable PostgreSQL DDL is a **single-store teaching model**. It covers identities, file versions and direct user grants; group/domain sharing, inheritance evaluation, changelog, upload intents and distributed routing are separate implementation work.

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  storage_quota BIGINT NOT NULL CHECK (storage_quota >= 0),
  storage_used BIGINT NOT NULL DEFAULT 0 CHECK (storage_used >= 0),
  CHECK (storage_used <= storage_quota)
);
CREATE TABLE files (
  id BIGINT PRIMARY KEY,
  owner_id BIGINT NOT NULL REFERENCES users(id),
  parent_id BIGINT REFERENCES files(id),
  name TEXT NOT NULL CHECK (length(name) > 0),
  is_folder BOOLEAN NOT NULL DEFAULT false,
  current_version BIGINT CHECK (current_version IS NULL OR current_version > 0),
  trashed_at TIMESTAMPTZ,
  CHECK (parent_id IS NULL OR parent_id <> id),
  CHECK (NOT is_folder OR current_version IS NULL)
);
CREATE UNIQUE INDEX live_root_name ON files(owner_id, name)
  WHERE parent_id IS NULL AND trashed_at IS NULL;
CREATE UNIQUE INDEX live_child_name ON files(parent_id, name)
  WHERE parent_id IS NOT NULL AND trashed_at IS NULL;
CREATE TABLE file_versions (
  file_id BIGINT NOT NULL REFERENCES files(id),
  version BIGINT NOT NULL CHECK (version > 0),
  byte_size BIGINT NOT NULL CHECK (byte_size >= 0),
  object_key TEXT NOT NULL,
  created_by BIGINT NOT NULL REFERENCES users(id),
  PRIMARY KEY (file_id, version)
);
ALTER TABLE files
  ADD CONSTRAINT files_current_version_fk
  FOREIGN KEY (id, current_version)
  REFERENCES file_versions(file_id, version)
  DEFERRABLE INITIALLY DEFERRED;
CREATE TABLE direct_grants (
  file_id BIGINT REFERENCES files(id),
  user_id BIGINT REFERENCES users(id),
  role TEXT NOT NULL CHECK (role IN ('reader','commenter','writer')),
  PRIMARY KEY (file_id, user_id)
);
```

The deferred composite foreign key keeps a non-folder's current-version pointer attached to a version of that same file. It lets one transaction insert a new version and update the pointer before the constraint is checked at commit; folders can leave the pointer null. The two name indexes explicitly handle root files: ordinary SQL uniqueness on `(owner,parent,name)` does not make null parents compare equal. Product semantics may instead allow duplicate display names; choose that contract rather than claiming every file service requires uniqueness.

The `storage_used <= storage_quota` check models a hard quota that cannot be lowered below current usage. If a product lets an account become over quota after a plan change, remove that check and reject only new publishes that exceed the updated allowance.

A foreign key proves that the parent exists, not that it is a folder, shares the appropriate ownership scope or has no deeper ancestry cycle. A move transaction must validate these conditions, permissions and expected metadata version. Coordinate concurrent moves through an appropriate lock/serializable design so two individually checked moves cannot form a cycle.

Trace an edit based on version 7. After bytes are uploaded, the metadata transaction checks current write permission, expected version 7 and quota. It atomically publishes version 8, adjusts accounted usage and appends its change record. A second writer still based on 7 receives a conflict. It may retain a separate conflict copy or explicitly merge through a supported document protocol; it must not overwrite 8 based on an untrusted device clock.

Restore is another new version referencing an authorized retained object, preserving history. It must recheck current permission, quota and the current version; a system-user shortcut is not permission to restore arbitrary private content.

## Sharing and inherited access

Define how owner privileges, direct grants, inherited grants, restrictions and share links combine. A reader cannot add a writer merely because the request contains `role: writer`. Resolve caller identity from the session, validate the requested target and enforce permission to grant/revoke.

For inherited grants, traverse a bounded cycle-free ancestry path or maintain a reviewed closure model. Cache effective permissions only with scope and invalidation/version rules. Moving a file can change access; authorization must use the current ancestry, not the old folder's cached grant. Search, previews, downloads, retained versions and collaboration events need the same authoritative policy.

A share link is a capability with explicit scope, expiry, revocation and optional authentication requirements. Store sensitive capability material appropriately and avoid exposing it in unrelated logs. A revoked link must stop new access even if a preview or CDN object is cached; already downloaded copies cannot be recalled.

## Quota belongs beside publication

Choose whether quota counts current bytes, retained versions, trash, shared ownership and deduplicated storage. Logical user quota and physical provider bytes are different quantities. Reserve bounded upload capacity where needed, expire abandoned reservations and finalize it in the authoritative publish transaction.

A read-then-increment outside a transaction lets two uploads independently consume the same remaining quota. Use locking or an atomic conditional update, and abort the entire publication if the quota claim fails. Counter reconciliation should be possible from authoritative version/reservation records.

Global deduplication based only on a client-supplied checksum can disclose whether another user holds a file, and a hash does not authorize access to it. Use verified bytes, appropriately scoped deduplication and authoritative references before cleanup. Client-side encryption changes deduplication and prevents ordinary server plaintext search/preview unless another explicit trust design is introduced.

## Synchronization and collaboration are different protocols

Opaque-file sync uses stable operation IDs, expected base versions and a durable authorized change cursor. Timestamps alone can miss equal-time changes, late commits and permission removals. Apply replay records before persisting a cursor; deduplicate repeated records and return an explicit reset when history is no longer retained. Notifications wake synchronization, but are not its authoritative history.

Fixed chunks permit resumable transfer but do not automatically implement rsync's rolling-block matching. Inserting a byte can shift all fixed chunk boundaries. A delta needs an identified base, ordered operations with precise insert/delete/replace semantics and a verified final checksum; the old example that inserted changed chunks into the base would duplicate bytes and fail truncation.

A collaborative text protocol requires reviewed operational transformation (**OT**) or a conflict-free replicated data type (**CRDT**), with operation identity, causality/order, convergence, persistence and resynchronization. Choosing “OT for documents, last writer wins for spreadsheets” is not a complete algorithm. Binary files normally need explicit conflict copies unless the application supplies a format-aware merge. Do not fabricate a generic transform function and present it as verified convergence.

Folder deletion racing a child addition needs a stated policy and authoritative transaction boundary. Preserve rejected offline work locally so the user can choose a new destination. Two concurrent renames cannot both define one final name; surface the selected result or conflict instead of saying “apply both.”

## Recovery and retention

| Failure | Controlled response |
| -------------------------------- | ----------------------------------------------------------------------------------------------- |
| Upload completes, metadata fails | Retry the stable publication command or reclaim the orphan after a safe retention period. |
| Permission revoked while offline | Reject new unauthorized writes; retain local unsynced work and clearly explain the boundary. |
| Cursor falls behind retention | Return reset/resnapshot instructions; never claim an incomplete replay is complete. |
| Preview/search unavailable | Continue authorized file operations with bounded missing-preview/search behavior. |
| Metadata authority unavailable | Do not accept conflicting writes against an arbitrary stale replica. |
| Byte object unavailable | Retry/fail the specific download; replication configuration must actually supply a usable copy. |

Offline availability requires locally downloaded bytes, capacity and key availability before connectivity is lost. Marking every file “offline available” does not download it. Track partial downloads and encrypted local storage according to the device threat model.

Trash hides access under the chosen policy while preserving restore metadata. Define retention, legal holds, backup aging and cleanup evidence. Reference-aware garbage collection must preserve retained versions and active uploads, and recheck live references before deleting objects; deleting a file row is not proof that every distributed copy vanished. Do not imply that the product name promises permanent history: Google's public Drive API notes that revision listings can omit older edits for frequently edited Workspace files and that older blob revisions may be purged under its retention rules.

## Real-world decisions

Use relational metadata and object bytes when their transaction, query and size profiles fit; neither object storage nor relational storage is infinitely scalable. Dedicated search may help fuzzy/content queries, but no fixed file-count threshold proves PostgreSQL inadequate. Measure the intended queries and indexes first.

Shard around an explicit metadata authority and cross-owner sharing model. Independent user/file modulo routes do not automatically preserve folder transactions or grants. Regional latency, ownership transfer and data residency require their own routing/recovery decisions, not a three-region diagram.

Measure publish latency, rejected version/quota checks, oldest unsynced cursor, reconciliation drift, preview backlog and permission-revocation delay. Separate byte throughput from metadata operations and observed sync delay from user edit latency.

## Mistakes

- Treating pathname or device time as authoritative file identity/version.
- Publishing unverified bytes or adjusting quota after a separate metadata commit.
- Using root-name uniqueness with nullable parents without its intended semantics.
- Claiming generic chunk insertion implements delta synchronization.
- Assuming encryption permits ordinary server plaintext search or deduplication is an access check.
- Calling a one-row share update constant-time authorization for all descendants.

## Best practices

Test concurrent edits, quota exhaustion races, folder-move cycles, revoke-during-download and deletion/addition conflicts. Execute the actual document convergence protocol separately from opaque-file version tests. Verify restore and byte integrity, and retain clear local conflict UX so rejection does not silently discard the user's work.

## Summary

A collaborative file service separates immutable byte versions from stable metadata identity, current permissions and quota. Expected versions and durable replay preserve offline edits without silently overwriting newer work. Folder inheritance, moves and sharing have authoritative transaction boundaries; real-time document collaboration requires its own verified convergence protocol.

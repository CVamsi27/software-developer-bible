# Google Drive System Design

Edit a file offline on one laptop. Meanwhile, another editor publishes version 8, and the owner revokes your write access. When the laptop reconnects, its bytes might reach storage successfully, but they must not replace version 8 or become visible without a fresh permission check. Separating transfer from publication is the core design problem:

```text
offline edit v7 + remote publish v8 + revoked access → transfer ≠ publication.
```

## Definition

A Drive-like service gives each file a **stable identity**, stores **immutable versions** of its bytes, and updates mutable **metadata** such as its name, folder, permissions, and current version. It lets users organize and share files while multiple devices maintain local copies.

> **Textbook Definition:** A collaborative file service stores versioned content and metadata, synchronizes replicas across devices, and resolves concurrent edits under explicit sharing and consistency policies.

This is an interview proposal, not a verified account of Google Drive internals. The [Dropbox case](30.2.2.18-dropbox.md) owns block hashing, upload-version conflicts, and device replay. This chapter adds folder permissions, quota, and the distinction between opaque-file synchronization and collaborative document operations.

## First Principles

1. A file has stable identity even when its name or folder changes. Treating the pathname as identity makes rename look like delete-and-recreate and loses references. Store immutable byte versions separately from mutable identity, placement, and permissions.
2. An offline edit was authorized under a past view of the world. On reconnect, another editor may have changed the content or the owner may have revoked permission. The service must recheck current permission and the expected base version; it cannot silently accept every queued operation.
3. Changing a folder can affect many descendants. Evaluating inherited access avoids eagerly copying every permission, but requires bounded traversal, cycle prevention, and a defined cache-invalidation boundary. A one-row share update never implies constant-time authorization for the whole tree.

## Requirements and coherent estimates

Support upload/download, bounded listings, version history with an explicit retention policy, restore, device replay, sharing, folders, trash, and quotas. A published version's bytes are immutable, but retention may later remove old versions. Collaboration is an additional document protocol, not automatic merging of arbitrary binary files. Choose which metadata writes are authoritative and which offline observations are provisional.

Using decimal units, one billion files at 1 MB each occupy 1 PB of current bytes. If each has ten equally sized retained versions, content occupies 10 PB; one 1 KB metadata row per file adds 1 TB, for about 10.001 PB before replicas, indexes, and previews. Actual history storage depends on changed bytes, edit frequency, and retention.

At 100 million active users transferring 10 MB/day, daily transfer is 1 PB and average throughput is about 11.6 GB/s; a 5× peak is about 57.9 GB/s. By Little's law, ten million concurrent sync operations completing at 100,000 per second hold a 100-second average residence time under steady state. State whether these operations are long polls, byte transfers, or metadata requests before using the estimate for capacity.

Object durability percentages are provider- and configuration-specific and differ from application availability and restore correctness. Replication without tested backups and metadata recovery is never sufficient evidence for end-to-end durability.

## Make an upload visible safely

```text
Client → authenticated metadata authority → folder/version/quota/permissions
                      ↓                             ↓
              scoped upload intent           transaction + change log/outbox
                      ↓                             ↓
              immutable object bytes          device replay / search / preview
                      ↓                             ↓
              verified completion             notifications are sync hints

Document editor → separate reviewed operation protocol → checkpoints/history
```

The object store holds file bytes; the metadata store decides which verified object is the current version and who may access it. The upload becomes visible through a metadata commit:

1. Authorize the caller, reserve the expected quota, and issue a short-lived upload target scoped to one intent and object key.
2. After upload, verify the completed object and its actual size/checksum at the storage boundary. Never treat client-reported metadata as proof that all bytes arrived.
3. In one metadata transaction, recheck current permission and expected file version, append the version, move `current_version`, finalize quota usage, and record the change through an outbox or equivalent durable log.
4. If publication fails, keep the bytes invisible and retry the same intent or reclaim the unreferenced object after a safe retention period. Garbage collection must recheck that no retained version or live upload references it.

## Model file identity and versions

The following executable PostgreSQL DDL is a **single-store teaching model**. A file ID remains stable across renames; each version points to an immutable stored object. The `object_key` names that object and grants no access by itself. This model covers file identities, versions, and direct user grants; group/domain sharing, inherited-access evaluation, change feeds, upload intents, and distributed routing require additional design:

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  storage_quota BIGINT NOT NULL CHECK (storage_quota >= 0),
  storage_used BIGINT NOT NULL DEFAULT 0 CHECK (storage_used >= 0),
  CHECK (storage_used <= storage_quota)
);
CREATE TABLE files (
  id BIGINT PRIMARY KEY,
  owner_id BIGINT NOT NULL REFERENCES users(id),
  parent_id BIGINT REFERENCES files(id),
  name TEXT NOT NULL CHECK (length(name) > 0),
  is_folder BOOLEAN NOT NULL DEFAULT false,
  current_version BIGINT CHECK (current_version IS NULL OR current_version > 0),
  trashed_at TIMESTAMPTZ,
  CHECK (parent_id IS NULL OR parent_id <> id),
  CHECK (NOT is_folder OR current_version IS NULL)
);
CREATE UNIQUE INDEX live_root_name ON files(owner_id, name)
  WHERE parent_id IS NULL AND trashed_at IS NULL;
CREATE UNIQUE INDEX live_child_name ON files(parent_id, name)
  WHERE parent_id IS NOT NULL AND trashed_at IS NULL;
CREATE TABLE file_versions (
  file_id BIGINT NOT NULL REFERENCES files(id),
  version BIGINT NOT NULL CHECK (version > 0),
  byte_size BIGINT NOT NULL CHECK (byte_size >= 0),
  object_key TEXT NOT NULL,
  created_by BIGINT NOT NULL REFERENCES users(id),
  PRIMARY KEY (file_id, version)
);
ALTER TABLE files
  ADD CONSTRAINT files_current_version_fk
  FOREIGN KEY (id, current_version)
  REFERENCES file_versions(file_id, version)
  DEFERRABLE INITIALLY DEFERRED;
CREATE TABLE direct_grants (
  file_id BIGINT REFERENCES files(id),
  user_id BIGINT REFERENCES users(id),
  role TEXT NOT NULL CHECK (role IN ('reader','commenter','writer')),
  PRIMARY KEY (file_id, user_id)
);
```

The deferred composite foreign key keeps a non-folder's current-version pointer attached to a version of that same file. It lets one transaction insert a new version and update the pointer before the constraint is checked at commit; folders can leave the pointer null. The two name indexes explicitly handle root files: ordinary SQL uniqueness on `(owner,parent,name)` never makes null parents compare equal. Product semantics may instead allow duplicate display names; choose that contract rather than claiming every file service requires uniqueness.

The `storage_used <= storage_quota` check models a hard quota that cannot be lowered below current usage. If a product lets an account become over quota after a plan change, remove that check and reject only new publishes exceeding the updated allowance.

A foreign key proves the parent exists, not that it is a folder, shares the appropriate ownership scope, or holds no deeper ancestry cycle. A move transaction must validate these conditions, permissions, and expected metadata version. Coordinate concurrent moves through an appropriate lock/serializable design so two individually checked moves cannot form a cycle.

### Follow two edits from the same base

Suppose two editors start from version 7. After one uploads its bytes, the metadata transaction checks current write permission, expected version 7, and quota. It atomically publishes version 8, adjusts accounted usage, and appends its change record. The other editor, still based on version 7, receives a conflict. Preserve its work as a conflict copy or merge it through a supported document protocol; never overwrite version 8 from an untrusted device clock.

Restore is another new version referencing an authorized retained object, preserving history. It must recheck current permission, quota, and the current version; a system-user shortcut is no permission to restore arbitrary private content.

## Sharing and inherited access

Define how owner privileges, direct grants, inherited grants, restrictions, and share links combine. A reader cannot add a writer merely because the request contains `role: writer`. Resolve caller identity from the session, validate the requested target, and enforce permission to grant/revoke.

For inherited grants, traverse a bounded cycle-free ancestry path or maintain a reviewed closure model. Cache effective permissions only with scope and invalidation/version rules. Moving a file can change access; authorization must use the current ancestry, not the old folder's cached grant. Search, previews, downloads, retained versions, and collaboration events need the same authoritative policy.

A share link is a capability with explicit scope, expiry, revocation, and optional authentication requirements. Store sensitive capability material appropriately and avoid exposing it in unrelated logs. A revoked link must stop new access even if a preview or CDN object is cached; already downloaded copies cannot be recalled.

## Quota belongs beside publication

Choose whether quota counts current bytes, retained versions, trash, shared ownership, and deduplicated storage. Logical user quota and physical provider bytes are different quantities. Reserve bounded upload capacity where needed, expire abandoned reservations, and finalize it in the authoritative publish transaction.

A read-then-increment outside a transaction lets two uploads independently consume the same remaining quota. Use locking or an atomic conditional update, and abort the entire publication if the quota claim fails. Counter reconciliation should be possible from authoritative version/reservation records.

Global deduplication from a client-supplied checksum alone can disclose whether another user holds a file, and a hash never authorizes access to it. Use verified bytes, appropriately scoped deduplication, and authoritative references before cleanup. Client-side encryption changes deduplication and prevents ordinary server plaintext search/preview unless another explicit trust design is introduced.

## Synchronization and collaboration are different protocols

Opaque-file sync uses stable operation IDs, expected base versions, and an authorized change cursor. Timestamps alone can miss equal-time changes, late commits, and permission removals. Apply replay records before persisting a cursor, and deduplicate repeated records. Notifications wake synchronization; they are not the authoritative history.

The published Drive API holds a separate change feed per user and shared drive. A change record provides an item's current state, not a byte-level delta; tracking all visible items may require replaying the relevant feeds. Its `changes.list` reference documents page tokens as non-expiring. A new service compacting its own change log must instead return an explicit reset and resnapshot path when it can no longer honor a cursor.

Fixed chunks permit resumable transfer but never implement rsync's rolling-block matching: inserting a byte can shift all later chunk boundaries. A list of changed chunks cannot be appended to the base because that duplicates content and cannot express deletion or truncation. A correct delta identifies its base, orders precise insert/delete/replace operations, and verifies the final size and checksum.

A collaborative text protocol requires reviewed operational transformation (**OT**) or a conflict-free replicated data type (**CRDT**), with operation identity, causality/order, convergence, persistence, and resynchronization. Choosing "OT for documents, last writer wins for spreadsheets" is no complete algorithm. Binary files normally need explicit conflict copies unless the application supplies a format-aware merge. Never fabricate a generic transform function and present it as verified convergence.

Folder deletion racing a child addition needs a stated policy and authoritative transaction boundary. Preserve rejected offline work locally so the user can choose a new destination. Two concurrent renames cannot both define one final name; surface the selected result or conflict instead of saying "apply both."

## Recovery and retention

| Failure | Controlled response |
| -------------------------------- | ----------------------------------------------------------------------------------------------- |
| Upload completes, metadata fails | Retry the stable publication command or reclaim the orphan after a safe retention period. |
| Permission revoked while offline | Reject new unauthorized writes; retain local unsynced work and clearly explain the boundary. |
| Cursor falls behind retention | Return reset/resnapshot instructions; never claim an incomplete replay is complete. |
| Preview/search unavailable | Continue authorized file operations with bounded missing-preview/search behavior. |
| Metadata authority unavailable | Do not accept conflicting writes against an arbitrary stale replica. |
| Byte object unavailable | Retry/fail the specific download; replication configuration must actually supply a usable copy. |

Offline availability requires locally downloaded bytes, capacity, and key availability before connectivity is lost. Marking every file "offline available" never downloads it. Track partial downloads and encrypted local storage per the device threat model.

Trash hides access under the chosen policy while preserving restore metadata. Define retention, legal holds, backup aging, and cleanup evidence. Reference-aware garbage collection must preserve retained versions and active uploads, and recheck live references before deleting objects; deleting a file row is no proof that every distributed copy vanished. Never imply that the product name promises permanent history: Google's public Drive API notes that revision listings can omit older edits for frequently edited Workspace files and that older blob revisions may be purged under its retention rules.

## Real-world decisions

Use relational metadata and object bytes when their transaction, query, and size profiles fit; neither object storage nor relational storage is infinitely scalable. Dedicated search may help fuzzy/content queries, but no fixed file-count threshold proves PostgreSQL inadequate. Measure the intended queries and indexes first. Shard around an explicit metadata authority and cross-owner sharing model. Independent user/file modulo routes never automatically preserve folder transactions or grants. Regional latency, ownership transfer, and data residency require their own routing/recovery decisions, not a three-region diagram. Measure publish latency, rejected version/quota checks, oldest unsynced cursor, reconciliation drift, preview backlog, and permission-revocation delay. Separate byte throughput from metadata operations and observed sync delay from user edit latency.

## Test the synchronization contract

Have two devices edit from version 7 while one is offline; verify that only one update becomes current and the rejected work remains recoverable. Race two uploads for the remaining quota, revoke access before publication, move folders concurrently, and add a child while its parent is deleted. Replay the same change page twice and verify that content, cursor, and permissions remain consistent. Test document convergence separately from opaque-file sync, then verify restored bytes and access under current grants and retention rules.

## Summary

A collaborative file service separates immutable byte versions from stable metadata identity, current permissions and quota. Expected versions and durable replay preserve offline edits without silently overwriting newer work. Folder inheritance, moves and sharing have authoritative transaction boundaries; real-time document collaboration requires its own verified convergence protocol.

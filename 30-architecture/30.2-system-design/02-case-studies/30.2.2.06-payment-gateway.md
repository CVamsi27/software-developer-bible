# Payment Gateway System Design

An online store sends a $50 charge to its processor. The processor accepts it, but the response is lost in a network timeout. If the store retries as a new purchase, the customer may be charged twice; if the gateway reports failure, the merchant may show a false decline. The gateway must preserve one command identity and resolve the unknown outcome:

```text
charge $50 → response lost → retry same key → same command, no second charge.
```

## Definition

A **payment gateway** accepts a merchant's **payment command**, communicates with a provider, and records the outcome so retries never create another charge. Its hardest result is **unknown**: the provider may have charged the customer even though the response never reached the gateway.

> **Textbook Definition:** A payment gateway mediates payment requests between merchants and payment providers, maintaining operation identity, authorization state, and reconciliation records across independently failing systems.

This is an interview design, not a certified payment product. Availability, throughput, and card-security compliance require evidence from the complete implementation and operating controls. Prefer provider tokenization/hosted capture for card details where appropriate; never log or retain card verification codes.

## First Principles

1. A database commit and an external charge cannot share an ordinary local transaction. Therefore persist the command identity before attempting the provider call, and keep ambiguous outcomes recoverable. Calling another provider after a timeout can charge twice because independent providers share no idempotency namespace.
2. Two legitimate purchases can share identical customer, currency, and amount. Deduplicating by those fields merges distinct business actions. Use an explicit stable command key, scoped to the authenticated merchant and operation; separately bind that key to a normalized request fingerprint and reject changed payloads.
3. A payment status describes operational progress; a ledger describes financial obligations and movements. They are related but different. Accounting needs balanced postings per currency, immutable committed entries, and compensating entries for corrections, rather than silently rewriting the past.

## Requirements and coherent estimates

Support intents, confirmation, authorization/capture where applicable, refunds, disputes, recurring commands, merchant notifications, and reconciliation. Currency semantics must specify permitted currency codes and each currency's minor-unit rules; not every currency uses cents. Fraud assessment, onboarding, and settlement are explicit surrounding workflows.

Ten million transactions/day is about 116/second on average. A 100,000/second peak is about 864× that mean: justify burst duration and provider capacity before using it. At 1 KB/transaction, base records add 10 GB/day or 3.65 TB/year; seven equally sized years imply 25.55 TB before indexes, ledger entries, events, replication, and backups. Volume at an assumed 50 USD/transaction is 500 million USD/day; never aggregate unrelated currencies as dollars.

Five-nines annual availability permits about 5.26 minutes downtime in a 365-day year, but an active-active diagram never establishes that objective. Define whether availability means command acceptance, confirmed payment, or query access, and include provider dependencies and ambiguous outcomes in the user-visible measure.

## How the components fit

```text
Authenticated merchant → validate intent / permission / amount
             ↓
 durable command identity + request fingerprint + pending state
             ↓
 bounded provider worker → stable provider idempotency/reference
             ↓
 response / verified webhook / provider status reconciliation
             ↓
 authorized state transition + balanced ledger postings + outbox
             ↓
 merchant notification retries and settlement reconciliation
```

The database owns command identity and payment state. A Redis cache can speed reads or coordinate optional work, but expiry/eviction must never authorize a second charge. Worker leases need ownership/generation checks and never replace the durable command or provider identity.

## Example: durable commands distinguish repeats from purchases

This PostgreSQL DDL illustrates merchant command identity and provider correlation. The merchant's idempotency key identifies the intended purchase across merchant retries. A provider idempotency key deduplicates attempts within a provider account; the provider reference correlates a returned result. Persist these separately. This is no provider client, complete ledger, or permission implementation:

```sql
CREATE TABLE merchants (merchant_id BIGINT PRIMARY KEY);
CREATE TABLE payment_commands (
  command_id UUID PRIMARY KEY,
  merchant_id BIGINT NOT NULL REFERENCES merchants(merchant_id),
  operation TEXT NOT NULL CHECK (operation IN ('charge','refund','capture')),
  idempotency_key TEXT NOT NULL CHECK (length(idempotency_key) > 0),
  request_fingerprint TEXT NOT NULL CHECK (length(request_fingerprint) > 0),
  amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
  currency TEXT NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
  state TEXT NOT NULL CHECK (state IN
    ('pending','processing','unknown','succeeded','failed')),
  version BIGINT NOT NULL DEFAULT 0 CHECK (version >= 0),
  provider TEXT,
  provider_account_id TEXT,
  provider_idempotency_key TEXT,
  provider_reference TEXT,
  CHECK ((provider IS NULL) = (provider_account_id IS NULL)),
  CHECK (provider_idempotency_key IS NULL OR provider IS NOT NULL),
  CHECK (provider_reference IS NULL OR provider IS NOT NULL),
  UNIQUE (merchant_id, operation, idempotency_key)
);
CREATE UNIQUE INDEX provider_request_identity
  ON payment_commands(provider, provider_account_id, provider_idempotency_key)
  WHERE provider_idempotency_key IS NOT NULL;
CREATE UNIQUE INDEX provider_result_identity
  ON payment_commands(provider, provider_account_id, provider_reference)
  WHERE provider_reference IS NOT NULL;
CREATE TABLE provider_events (
  provider TEXT NOT NULL,
  provider_account_id TEXT NOT NULL,
  event_id TEXT NOT NULL,
  received_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (provider, provider_account_id, event_id)
);
```

The provider account column scopes request keys, references, and event IDs to the account owning them. Use the provider's actual uniqueness scope if it differs. The currency check verifies shape, not that a code is supported. Normalize and validate currency/amount against the business contract before acceptance. A fingerprint should cover meaningful normalized inputs, token/customer identity, and target charge, excluding unstable transport fields. On a merchant-key uniqueness conflict, compare it with the stored fingerprint: a match returns the existing command; a mismatch is a conflict. The constraint reserves one row but never performs that semantic comparison. Never place raw card secrets in the fingerprint's source logs.

Trace command `checkout-17`:

1. The merchant submits 5,000 minor units with key `checkout-17`. The gateway commits the command and a stable provider idempotency key in the selected provider-account scope before making the request.
2. The provider charges successfully, but the response is lost. Record unknown/reconciling instead of asserting failure.
3. A client retry uses the same key and payload. It retrieves the same command; it creates no new charge.
4. A verified webhook or authenticated provider lookup confirms the existing result. The state transition, ledger posting identity, and merchant outbox event commit together.
5. Replaying that event sees the same provider event/posting identity and never posts twice.

A retry with `checkout-17` but a different amount is a conflict, not another operation. A separate legitimate purchase uses a new merchant key even if its amount is also 5,000. Provider idempotency is separately scoped and time-bounded. Stripe documents that it may prune a key after it is at least 24 hours old, after which reusing that key can start a new request. Keep the gateway command for the full retry/reconciliation horizon. If the provider's guarantee has expired, resolve an old unknown outcome through an authoritative lookup or reconciliation before sending another charge.

## The ledger needs a posting authority

For a simplified 50 USD confirmed receivable, post a 50 USD debit to the processor receivable asset and a 50 USD credit to merchant payable liability. Fees, settlement, and refunds require additional explicitly identified postings. Debits and credits balance within each currency; a 50 USD debit and 50 EUR credit never balance merely because the numbers match.

A journal header and lines are necessary but never sufficient. Reject an unbalanced journal at the posting boundary, commit all its lines atomically, enforce unique source/operation identity, and restrict mutation of posted records. Ordinary row CHECK constraints cannot enforce a sum across arbitrary journal lines by themselves. Use a transactionally verified posting function or a properly designed deferred validation mechanism, with concurrent/negative tests.

Cached balances are derived and reconcile against entries; operational state may update as a command progresses, while posted financial history remains immutable under the chosen controls. Correction uses reversal/adjustment entries with audit linkage. Retaining rows alone is no adequate audit policy: permissions, retention, tamper detection, and controlled administrative changes matter.

## Payment phases and refunds have different invariants

Authorization reserves permission/funds under the provider's contract; capture, settlement, and payout occur later and can fail independently. A succeeded capture is no proof of merchant settlement. Customer authentication may require an interactive step and cannot be reduced to "sub-second charge."

A refund references the authorized merchant's charge, uses its own stable command identity, and checks refundable balance. Concurrent partial refunds need authoritative reservation/conditional accounting so both cannot independently consume the same remaining amount. Provider acceptance can leave a refund pending; expose that outcome and reconcile it. Disputes are not simply a negative refund and follow their own evidence/state policy.

Recurring billing creates one stable command identity per intended billing cycle/action. Retrying a failed attempt must never create another cycle. Fraud results can be approve, reject, or review; a review outcome needs a workflow and must never be silently treated as approval. Sliding velocity metrics need actual time windows and scoped identities; resetting one TTL after each increment never counts "last hour" correctly.

## Webhooks are durable, verified and replay-safe

Follow each provider's signature contract. For Stripe, verify the signature and timestamp over the exact, unmodified request body with its official library before parsing or trusting payload fields. Support controlled secret rotation. Deduplicate event identity within its provider-account scope and use state/version rules because events can arrive out of order. Durably accept the event before returning the provider's documented successful response, then process expensive work asynchronously.

Outbound merchant notifications need stable event IDs, signed exact transmitted bytes, timestamp/replay policy, bounded retries with jitter, attempt history, and a dead-letter/manual replay path. A JSON object independently reserialized for signing and transmission can produce different bytes. Use the agreed receiver contract for successful 2xx acknowledgments, rather than assuming only 200 is valid. Delivery acknowledgment is no proof that the merchant applied the business effect exactly once.

Merchant webhook URLs are untrusted destinations. Validate scheme/ports, enforce an egress policy, handle DNS rebinding and redirects, and block internal/metadata targets to prevent server-side request forgery. Bound response bodies, connections, and timeouts; never let slow recipients exhaust payment workers.

## Reconcile both sides of the boundary

Compare local command/ledger records with provider operations and settlement reports in both directions: missing local records, missing provider records, duplicate references, currency/amount differences, fees, and timing windows. Account for pending/cutoff states before declaring a discrepancy. A loop over only local successful transactions misses charges existing solely at the provider. Never silently "auto-resolve anything below one dollar." Record the discrepancy, explain its cause, and post an authorized adjustment when warranted. Keep the source report/version and reconciliation action auditable. Reconciliation frequency follows risk and provider visibility; daily batch alone may leave urgent unknown charges unresolved too long.

## Recovery preserves command ownership

| Failure | Controlled response |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Provider timeout after request | Keep unknown; query/retry the same provider identity under its contract before any alternate route. |
| Database unavailable | Reject/defer commands when durable identity cannot be established; a stale replica is not a safe write authority. |
| Redis lost | Use durable command state; eviction cannot reset the business operation. |
| Broker unavailable | Retain committed outbox events and bound backlog; local process memory is not durable recovery. |
| Worker lease expires | A new owner rechecks durable state; stale workers cannot overwrite newer transitions. |
| Region partition | Preserve one authority per command/financial account scope; asynchronous mirroring cannot prevent competing charges. |

Circuit breakers protect provider capacity and user latency, but never decide whether a timed-out charge happened. Bounded retries require the same identity and a known retryable contract. Never route every SQL SELECT to a read replica: lock reads, permission checks, and current command decisions may require the authority's consistent view.

## Real-world decisions

Choose stores by transaction, conditional-write, and recovery requirements, not "DynamoDB cannot provide transactions." Keep payment command, journal, and financial account ownership explicit before sharding or multi-region writes. A database may support transactions while the end-to-end provider operation still remains distributed. Limit card-data exposure through provider integrations appropriate to the product, then assess the full system's PCI obligations and operating controls. Tokenization can reduce scope but never establishes certification. Keep API key verification material, provider credentials, and webhook secrets out of plaintext schemas/logs; encrypt or hash per how each credential is used. Measure pending/unknown age, duplicate/conflicting command attempts, provider latency, authorization versus capture success, webhook backlog, unbalanced/rejected postings, and reconciliation differences by currency. A fast HTTP 200 response is no evidence of completed payment or correct books.

## Test the payment contract

Race two requests with the same merchant key and payload, then reuse that key with a different amount; only the first command should exist and the changed request should conflict. Simulate a provider success with a lost response, an expired provider idempotency window, a duplicate or out-of-order webhook, and a worker lease takeover. Separately race partial refunds, reject an unbalanced or cross-currency journal, and reconcile a provider charge missing from local records. Verify every recovery against provider references and immutable posting identities.

## Summary

A payment gateway keeps one durable identity for each intended financial command while external outcomes may remain unknown. Provider reconciliation, verified replay-safe events and authoritative state transitions close that gap. Balanced immutable postings describe financial effects; caches, breakers and active-active diagrams do not replace that authority.

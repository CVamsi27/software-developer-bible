# Notification Service System Design

One order-shipped event creates an email and an in-app item. The email provider accepts the message, but its response is lost; before a retry, the recipient disables that email channel. Replaying the whole event could duplicate the inbox item or ignore the new preference. One event therefore needs independent delivery identities, outcomes, and policy checks:

```text
1 event → email + inbox; email ack lost + opt-out → retry only the email, recheck policy.
```

## Definition

A **notification service** converts a **domain event** — a fact the business has recorded, such as an order shipment — into one or more **authorized deliveries** by email, push, short message service (SMS), or an in-app inbox. It decides whether, when, and where to send. Provider acceptance and recipient delivery are separate outcomes.

> **Textbook Definition:** A notification service converts domain events into recipient-specific deliveries across channels, applying consent, preference, scheduling, deduplication, and provider-response policies.

This is an interview proposal. Traffic, latency, and retention are exercise assumptions; a service architecture never establishes consent, legal compliance, or universal delivery guarantees.

## First Principles

1. One event can create several deliveries, and each can fail independently. Therefore retain event identity separately from recipient/channel delivery identity. Retrying an email must never repeat an already confirmed SMS or create another in-app item.
2. Preferences can change after scheduling. Checking them only when accepting the event lets a queued marketing message bypass a later opt-out. Recheck the current authorized policy at dispatch and define any exception explicitly by notification purpose.
3. A lost provider response is ambiguous. A retry can send another notification even though the first was accepted. Stable delivery identity, provider-supported idempotency, and reconciliation reduce duplicates, but an at-least-once queue alone cannot guarantee one human-visible message.
4. A consent check and an external send cannot share one ordinary database transaction. Rechecking immediately before dispatch narrows the stale-policy window, but an opt-out may race with an already-authorized request. Define the policy cutoff: a later opt-out blocks new attempts, while an in-flight or provider-accepted message can only be canceled if that channel/provider supports cancellation.

## Requirements and capacity assumptions

Support versioned templates/locales, preferences by category/channel, bounded bulk jobs, scheduling, expiry, quiet hours, per-recipient quotas, and observable status. Authenticate event producers and authorize their recipient scope; a public user ID is no permission to notify that user. Keep inbox history access scoped to its recipient.

A hypothetical 100 million users receiving 10 delivery attempts/day means one billion attempts/day, or about 11,574/second average. At 5× peak, plan for about 57,870/second. If "notification" instead means a domain event expanding into multiple devices/channels, multiply that fan-out before sizing providers and queues.

Using decimal units, 1 KB per delivery-attempt record adds 1 TB/day, or 30 TB over 30 days before retries, indexes, replication, and retained bodies. SMS segment counts depend on encoding and multipart rules, so a fixed character count is no universal byte or cost limit; measure the segments the selected provider will bill for. Provider payload limits and quotas also vary. A latency objective must name its endpoint, such as durable job acceptance to provider acceptance; it cannot promise recipient attention within five seconds.

## How the components fit

```text
Authorized domain event + stable event ID
        ↓
 durable acceptance / intent records / outbox
        ↓
 recipient/category/channel policy → bounded delivery plans
        ↓
 scheduler → fresh preference check → template version → channel queue
        ↓
 provider adapter → accepted / unknown / rejected
        ↓
 verified status callback / reconciliation → channel-specific outcome

In-app inbox: durable recipient item → socket hint → authorized read
```

Isolate queues, concurrency, and retry budgets by channel/provider so an email outage cannot starve urgent in-app work. Priorities need fairness and expiry; unlimited "urgent" producers can starve other traffic. Backlog age and provider rate limit matter as much as queue length.

## Example: one event, two independent deliveries

The following PostgreSQL schema is a single-store teaching model for durable identity and scheduled state, not a complete notification database. It omits preference storage, audience snapshots, versioned payload storage, worker claims, encryption, and provider callbacks; each needs an explicit retention, authorization, and recovery contract:

```sql
CREATE TABLE notification_intents (
  intent_id UUID PRIMARY KEY,
  producer_id TEXT NOT NULL,
  source_event_id TEXT NOT NULL,
  request_fingerprint TEXT NOT NULL,
  category TEXT NOT NULL,
  template_version TEXT NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL,
  UNIQUE (producer_id, source_event_id)
);
CREATE TABLE delivery_jobs (
  delivery_id UUID PRIMARY KEY,
  intent_id UUID NOT NULL REFERENCES notification_intents(intent_id),
  recipient_id BIGINT NOT NULL,
  channel TEXT NOT NULL CHECK (channel IN ('push','email','sms','in_app')),
  target_identity TEXT NOT NULL,
  scheduled_at TIMESTAMPTZ NOT NULL,
  state TEXT NOT NULL CHECK (state IN
    ('scheduled','processing','accepted','unknown','delivered',
     'failed','suppressed','expired')),
  attempt_count INT NOT NULL DEFAULT 0 CHECK (attempt_count >= 0),
  version BIGINT NOT NULL DEFAULT 0 CHECK (version >= 0),
  provider_message_id TEXT,
  UNIQUE (intent_id, recipient_id, channel, target_identity)
);
CREATE INDEX scheduled_delivery_lookup
  ON delivery_jobs(scheduled_at, delivery_id) WHERE state='scheduled';
```

Scope `target_identity` to a device/address identity under the recipient's verified registry; avoid logging raw tokens or addresses. The producer/event unique key identifies one intent, while its fingerprint binds that key to the normalized event meaning. Compute it from canonical immutable fields such as event type, recipient scope, category, and payload version; exclude attempt timestamps and transport-only fields. A replay with the same key and fingerprint returns the existing intent; a changed fingerprint is a conflict. Store only the event payload needed for delivery, with a defined privacy and retention policy. For a dynamic group or campaign audience, freeze the intended recipient set or record an immutable audience version before expansion; resolving a segment again during replay could notify people added after the event. The delivery unique key prevents repeated expansion of the same intent and recipient from creating another logical delivery. It never by itself prevents duplicate external sends after a worker crash.

When the producer retries, the event key returns the existing intent. The email and in-app deliveries retain separate identities, so committing the inbox item never depends on the email result. If the email provider accepted the send but the response was lost, mark only that delivery unknown and reconcile its existing provider identity where possible. Before another attempt, recheck the email preference; if it is now disabled, suppress the attempt. If the provider offers no reliable idempotency or lookup, explain the duplicate risk instead of claiming exactly-once delivery.

A worker claims a due job with a bounded lease/generation, rechecks category consent, current target, expiry, and quota, then durably authorizes its attempt before provider work. Where preference and job state share an authority, condition the claim on the preference version so revocation and dispatch authorization serialize. The committed authorization is the service cutoff: a later opt-out blocks new attempts, but an already-authorized request may still be in flight and cannot be recalled after provider acceptance. A stale worker must never overwrite a newer state after lease expiry. Use a durable schedule for deferral; returning `scheduled` from a function without updating a due time never makes quiet-hour delivery happen later.

## Quiet hours follow the recipient's local clock

Store a validated Internet Assigned Numbers Authority (IANA) time-zone name, such as `Asia/Kolkata`, separately from the absolute scheduled instant. The following complete standard-library Python example answers whether an aware instant falls inside local quiet hours. It handles windows crossing midnight; equal start and end explicitly mean no quiet window in this example:

```python
from datetime import datetime, time
from zoneinfo import ZoneInfo

def in_quiet_hours(instant, zone_name, start, end):
    if instant.tzinfo is None or instant.utcoffset() is None:
        raise ValueError("An aware instant is required")
    local = instant.astimezone(ZoneInfo(zone_name)).time().replace(tzinfo=None)
    if start == end:
        return False
    if start < end:
        return start <= local < end
    return local >= start or local < end

sample = datetime.fromisoformat("2026-10-10T18:00:00+00:00")
print(in_quiet_hours(sample, "Asia/Kolkata", time(22), time(8)))  # True
```

This membership check never computes the next allowed instant. `ZoneInfo` uses the system IANA database and raises `ZoneInfoNotFoundError` if neither system data nor the `tzdata` package is available; include timezone data in runtimes lacking it. A scheduler must resolve daylight-saving skipped/repeated local times under an explicit policy, recompute after timezone/preference changes, and respect notification expiry. Never add a fixed number of UTC hours and assume it means the next local morning.

Critical security/transactional notices may hold a documented quiet-hour policy different from marketing. Such policy is no blanket bypass of consent or a reason to deliver every failure by SMS. Channel fallback must be authorized for that category and recipient, with cost and deduplication policy rechecked.

## Templates need channel-specific safety

Identify a template by name, channel, locale, and immutable revision. Validate required variables and lengths before enqueue/dispatch. Choose explicit locale fallback, and prevent fallback from silently switching channel or revealing content unsuitable for a lock screen.

Configure HTML templates with Jinja's `select_autoescape`; its `Environment` never enables autoescaping by default. Also validate link schemes and keep header values free of injection because HTML escaping never addresses those boundaries. Never accept arbitrary executable template source from untrusted producers; use a constrained rendering model and resource limits when needed. Cache by immutable revision or invalidate every applicable variant on change.

Push payloads need provider-specific limits and string-valued metadata where required. Never block an async event loop with synchronous SDK calls; use a compatible client or bounded worker pool. Reuse suitable connection pools, handle the provider's actual successful response shape, and redact tokens from failures. A missing device is a suppressed/no-target outcome, not a successful send.

## Delivery status is evidence, not a guess

| State | Evidence | Limitation |
| ------------------ | ------------------------------------------------- | ------------------------------------------------------------ |
| Accepted job | Durable local acceptance | No provider request yet |
| Provider accepted | Provider acknowledged the attempt | Device/mailbox/carrier delivery may still fail |
| Delivered | Provider/device evidence defined for that channel | Does not prove reading or comprehension |
| Opened/clicked | Client or tracking event under its policy | Privacy features, image fetchers and scanners can distort it |
| Unknown | Attempt may have succeeded, response absent | Retrying can duplicate without provider support |
| Suppressed/expired | Current policy or expiry blocks dispatch | Must not be counted as provider failure or success |

Authenticate provider callbacks, correlate provider message identity, deduplicate event IDs, and accept out-of-order statuses through reviewed transitions. Never downgrade a confirmed terminal result because an earlier queued callback arrives late. Not every channel provides the same delivery/open receipt; absence of receipt is no proof of failure.

## Quotas and retries require actual atomic boundaries

A separate read of count followed by increment lets parallel jobs exceed the quota. Use an atomic policy operation with clearly chosen fixed/sliding/token-bucket semantics; the [rate limiter](30.2.2.13-rate-limiter.md) owns that mechanism. Define whether suppressed jobs, retries, and multi-device fan-out consume quota. Provider quota is separate from user fatigue limits. Retry transient failures with jitter, deadlines, and bounded attempts. Never retry invalid tokens, permanent address failures, or policy suppression as though they were temporary provider outages. Remove/refresh invalid device targets under verified provider evidence. Expired order alerts must never emerge hours later just because the queue recovered.

## Recovery and privacy

| Failure | Controlled response |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Provider outage | Retain bounded retryable jobs; respect expiry and consent before a later attempt. |
| Ambiguous response | Recover stable attempt/provider identity; do not blindly switch providers. |
| Metadata authority unavailable | Reject/defer acceptance when durable identity/policy cannot be established; Redis is not automatically a substitute. |
| Event broker unavailable | Retain committed outbox work and bound backlog; process-local buffering is not durable. |
| Preference cache stale | Recheck the required policy/version; opt-out cannot wait indefinitely for an arbitrary TTL. |
| In-app socket unavailable | Durable inbox remains readable after reconnect; socket send is only a hint. |

Minimize sensitive data in payloads, logs, and lock-screen previews. Separate operational retention from marketing analytics and confirm required consent/opt-out rules for the market. A template engine and deletion job never establish GDPR compliance. Use controlled access, deletion/retention evidence, and provider-data handling appropriate to the actual product.

## Real-world decisions

Choose a task queue when due-time scheduling/retry ownership is primary, an event log when durable replay/multiple independent consumers justify it, or a deliberate combination. Naming Kafka as "scalable" never defines retry queues or scheduled delivery. Partitioning by recipient helps serialize some fatigue decisions, but never replaces distributed quota consistency or isolates provider hotspots. For A/B tests, assign a stable variant before dispatch and record its template/policy version. Repeated jobs must never switch variants or count duplicate sends as new participants. Measure accepted-to-provider latency, oldest eligible backlog, suppression reasons, unknown outcomes, retries/cost, and channel-specific confirmed delivery separately.

## Test the delivery contract

Replay one producer event and verify it creates one intent and only the intended recipient/channel jobs. Simulate an accepted email with a lost response, a preference change before retry, a duplicate inbox event, and an out-of-order provider callback. Race quota claims and worker-lease expiry, test quiet-hour windows across daylight-saving transitions, and confirm an expired job is never sent after recovery. Every operator replay must recheck current policy and must never resend obsolete sensitive content.

## Summary

A notification service owns recipient policy, durable delivery identity and scheduling, while channel providers supply different outcome evidence. Fresh consent checks, scoped templates, atomic quotas and retry-aware status transitions prevent queue retries from becoming unauthorized or misleading sends. Accepted, delivered and opened remain distinct observations.

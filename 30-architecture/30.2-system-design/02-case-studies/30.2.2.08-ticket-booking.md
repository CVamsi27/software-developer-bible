# Ticket Booking System Design

During a flash sale, thousands of buyers can see seat 10 as available at once. The seat map helps them choose; it cannot grant ownership. The difficult race appears when payment succeeds after a buyer's hold expires and another buyer now owns the seat:

```text
10,000 buyers see seat 10 free → one atomic claim wins; payment after expiry compensates.
```

## Definition

A ticket-booking service lets a buyer **temporarily hold seats** and convert that hold into a confirmed purchase. The seat map is a recent view of inventory; only the **booking authority** can decide whether the buyer still owns those seats when payment completes.

> **Textbook Definition:** A ticket-booking service allocates finite inventory through temporary holds and confirmed reservations, preserving exclusive ownership while payment and expiration proceed asynchronously.

This is an interview design. Capacity, hold duration, and latency are exercise assumptions, not verified deployment behavior. Browsing, seat ownership, payment, and venue admission hold different availability and correctness boundaries.

## First Principles

1. Both buyers can observe the same old availability. A cache read followed by a later write is no ownership decision: one authority must claim each event/seat pair atomically, and a multi-seat request must either claim every requested seat or fail.
2. Payment occurs outside that transaction and may outlast the hold. Holding database locks during a provider call creates long contention and still cannot make the provider atomic with the database. Keep a bounded durable hold, use stable payment identity, and define what happens if success arrives after inventory ownership was lost.
3. Expiration is a policy checked at use time, not merely a cleanup job. A delayed cleanup worker must never release a newer owner's hold. Bind every transition to the exact hold identity/generation and current state.

## Requirements and consistent estimates

Support event discovery, seating charts, bounded seat-group holds, quoted prices/currency, purchase confirmation, ticket retrieval, cancellation/refund, and admission validation. Derive the buyer from authentication; never trust a body-selected user ID or seat price. Define all-or-none group selection versus explicitly accepted partial allocation.

For a hypothetical flash sale, 100,000 concurrent browsers and 10,000 bookings/minute imply about 167 bookings/second. At 1 KB/booking request, payload is about 167 KB/s, not 10 MB/s. One million bookings/day averages about 11.6/second. At two tickets/booking, daily tickets are two million; model how many attempts and availability polls precede each success.

If each of 100,000 browsers polls once every five seconds with 100 bytes of response, that is 20,000 polls/second and 2 MB/s before protocol overhead. Without a polling interval, concurrent users never determine bandwidth. Ten-minute holds consume inventory per admitted hold rate and abandonments, not merely completed bookings.

## How the components fit

```text
Browse/search → cached event metadata / approximate seat map
                           ↓
Authenticated buyer → admission / quote → seat authority
                                             ↓
                                    durable temporary hold
                                             ↓
                            payment command / pending outcome
                                             ↓
                          ownership recheck + booking transaction
                                             ↓
                             durable tickets + event outbox
                                             ↓
                           retrieval / notification / admission scan
```

A waiting room limits attempts reaching the hot event. Signed admission tokens need expiry, replay/account policy, and fair queue semantics; they are no proof of seat ownership. Event partitioning limits failure scope but never removes competition for the last seat of one event.

## Example: the authority claims a seat group atomically

This executable PostgreSQL example demonstrates the hold boundary. It omits authentication, request idempotency, prices, booking, and payment tables; its owner argument represents an already authorized caller:

```sql
CREATE TABLE holds (
  hold_id UUID PRIMARY KEY,
  event_id BIGINT NOT NULL,
  owner_id BIGINT NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL,
  UNIQUE (event_id, hold_id),
  UNIQUE (hold_id, expires_at)
);
CREATE TABLE seats (
  event_id BIGINT NOT NULL,
  seat_id BIGINT NOT NULL,
  state TEXT NOT NULL CHECK (state IN ('available','held','booked')),
  hold_id UUID,
  hold_until TIMESTAMPTZ,
  PRIMARY KEY (event_id, seat_id),
  CHECK ((state='available' AND hold_id IS NULL AND hold_until IS NULL)
      OR (state='held' AND hold_id IS NOT NULL AND hold_until IS NOT NULL)
      OR (state='booked' AND hold_id IS NOT NULL AND hold_until IS NULL)),
  FOREIGN KEY (event_id, hold_id) REFERENCES holds(event_id, hold_id),
  FOREIGN KEY (hold_id, hold_until) REFERENCES holds(hold_id, expires_at)
    DEFERRABLE INITIALLY DEFERRED
);
CREATE FUNCTION claim_seats(
  p_event BIGINT, p_seats BIGINT[], p_owner BIGINT,
  p_hold UUID, p_until TIMESTAMPTZ
) RETURNS INTEGER LANGUAGE plpgsql AS $$
DECLARE wanted INTEGER; changed INTEGER;
BEGIN
  wanted := cardinality(p_seats);
  IF p_seats IS NULL OR wanted IS NULL OR wanted < 1 OR wanted > 8
     OR array_ndims(p_seats) <> 1 THEN
    RAISE EXCEPTION 'Seat group must contain 1 to 8 one-dimensional entries';
  END IF;
  IF array_position(p_seats, NULL) IS NOT NULL
     OR wanted <> (SELECT count(DISTINCT requested_seat_id)
                   FROM unnest(p_seats) AS requested(requested_seat_id)) THEN
    RAISE EXCEPTION 'Seat group contains null or duplicate IDs';
  END IF;
  IF p_event IS NULL OR p_owner IS NULL OR p_hold IS NULL
     OR p_until IS NULL OR p_until <= clock_timestamp() THEN
    RAISE EXCEPTION 'Invalid seat group or expiry';
  END IF;
  -- All competing group paths acquire seat locks in the same order.
  PERFORM seat_id FROM seats
    WHERE event_id=p_event AND seat_id=ANY(p_seats)
    ORDER BY seat_id FOR UPDATE;
  IF p_until <= clock_timestamp() THEN
    RAISE EXCEPTION 'Hold deadline elapsed while waiting';
  END IF;
  INSERT INTO holds VALUES(p_hold,p_event,p_owner,p_until);
  UPDATE seats SET state='held',hold_id=p_hold,hold_until=p_until
    WHERE event_id=p_event AND seat_id=ANY(p_seats)
      AND (state='available'
           OR (state='held' AND hold_until <= clock_timestamp()));
  GET DIAGNOSTICS changed = ROW_COUNT;
  IF changed <> wanted THEN
    RAISE EXCEPTION 'Seat group unavailable';
  END IF;
  RETURN changed;
END;
$$;
```

For held seats, the deferred composite foreign key keeps the seat's copied `hold_until` equal to that hold's `expires_at`; the other composite key prevents attaching a hold to a seat from another event. Renew both values in one transaction. An exception aborts the function's statement effects, including its newly inserted hold and any partial updates. Missing seats and booked seats therefore cannot yield a partially held group. A caller's surrounding transaction must handle the error correctly; never catch it and claim purchase success. A service also imposes a server-selected maximum hold duration, event status, buyer limits, and quote validation.

Trace buyers A and B claiming seat 10. A acquires its row lock, writes holdA, and commits. B sees the current held state after waiting and fails while it is unexpired. When holdA expires, another authoritative claim may replace it with holdB. A delayed cleanup for holdA must use `hold_id=holdA` and current state/expiry, so it cannot release holdB.

The function is not a complete retry API: a repeated p_hold currently conflicts with the primary key. Wrap requests in a durable scoped idempotency contract verifying the same event/seat group and returning its prior outcome rather than allocating another hold. Client retries after a lost response must never consume another set of seats.

## Confirmation and payment must recheck ownership

Persist a pending purchase and a stable payment command tied to the intended purchase before calling the provider. Never keep a database transaction open across that network call. All workflows touching both seats and a hold must lock seat rows in the same event/seat order as the claim path, then lock and recheck the hold and purchase. Verify current owner, event, quoted price/currency, expiry policy, and that every seat still belongs to that hold. Commit booking, seat state, ticket identity, and the outbox event together.

If the provider separates authorization from capture, model them as distinct durable steps and decide whether capture follows seat confirmation. A timeout leaves the current payment step unknown until reconciled; a captured payment whose hold was lost follows compensation instead of taking another buyer's seats.

Choose a clear policy for payments in progress: extend/reserve under a bounded authorized rule, or allow expiry and compensate a late successful charge. A provider success for an expired hold cannot steal seats from a newer buyer. Mark the purchase outcome honestly and reconcile/cancel/refund through the [payment gateway](30.2.2.06-payment-gateway.md) contract. A timeout is unknown, not automatically declined. A cleanup job improves storage/availability but never defines whether the hold remains usable. Use authoritative time and current state at confirmation. Queue delay must never give an old request permission to book after its deadline.

## Redis can accelerate views without becoming a second authority

Cache event details and approximate availability; stale seat maps are acceptable if the hold API clearly rejects changed inventory. A Redis pipeline with individual SET NX operations never provides all-or-none acquisition with conditional rollback. A hash field already containing available also makes HSETNX fail rather than transition it to reserved. Never switch between unrelated Redis and database ownership during failure: one path can accept a seat the other already claimed. If Redis is deliberately the authoritative allocation store, its persistence/failover, atomic multi-seat logic, ownership tokens, and reconciliation contract require a separate reviewed design. Expiring a lock never fences a paused old worker; deletion must verify the exact owner token. Socket seat updates are freshness hints. Reconnect needs a current snapshot or versioned replay; losing a hint cannot change authoritative seat ownership. Bound subscriptions and hide buyer identity from public seat maps.

## Tickets and admission are separate from QR rendering

A ticket is a durable entitlement associated with an event, booking, and seat. A QR image is one representation of its identifier or signed claim, not the entitlement itself. Use enough unpredictable identity and verify authorization on ticket retrieval; eight hex characters offer only 32 bits and are inappropriate as the sole guessable access credential at large scale.

Admission scans need an authoritative single-use transition or a defined multi-entry policy. Two gates can scan the same copied code concurrently. A conditional valid-to-used transition can permit one admission; a signed code alone cannot establish that it was not already used. Offline gates require explicit duplicate-risk and reconciliation policy.

Cancellation invalidates the ticket and updates inventory per resale/event rules, while refund may remain pending. Delayed notification or QR generation must never revive a cancelled entitlement. Persist ticket identity before asynchronous image generation so retries render the same ticket.

## Recovery and fair admission

| Failure | Controlled response |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Inventory authority unavailable | Continue safe browsing but reject/defer new claims; stale replicas cannot allocate seats. |
| Payment response lost | Reconcile the existing payment command before charging again. |
| Payment succeeds after hold lost | Follow compensation policy without taking the new owner's seats. |
| Cleanup delayed | Confirmation checks expiry; a stale cleaner cannot release a new hold. |
| Notification or QR renderer fails | Confirmed tickets remain retrievable; retry the derived artifact/delivery. |
| Traffic surge | Bound admission and per-account holds, protect authoritative capacity and report queue/busy outcomes. |

Bots and fairness need a stated product policy. Database arrival order is not necessarily fair user arrival order. Define queue ordering, token expiry, reconnect behavior, abandoned positions, and abusive multiple-account handling. Avoid holding seats for everyone in a 100,000-person waiting room before they reach checkout.

## Real-world decisions

Start with transactional seat ownership and measured contention. Optimistic conditional updates can prevent oversell when their predicates and affected-row checks are correct; pessimistic locks are not uniquely capable of correctness. Compare waiting-room throughput, lock duration, multi-seat group frequency, and event skew before distributing allocation. Track oversell/conflict outcomes, oldest holds, confirmation/expiry races, payment unknown age, late-payment compensation, and gate duplicate attempts. Separate admitted attempts from confirmed bookings and ticket-render latency from booking latency. A low database conflict rate can merely indicate that buyers never reached the authority.

## Test the ownership transitions

- Race overlapping one-seat and group requests. Each contested seat has one owner, and a failed group leaves no partial hold.
- Lose a hold response and retry with the same idempotency key and request fingerprint; the retry returns the same outcome. Reuse the key with changed seats and expect a conflict.
- Reassign an expired seat, then run the old cleanup task; it must leave the new hold untouched.
- Inject payment timeouts, late success, duplicate webhooks, and lost confirmation responses. Reconcile the same payment command and confirm only seats still bound to the unexpired hold; otherwise follow the compensation policy.
- Race two admission scans for one ticket. Only one valid-to-used transition succeeds unless the event explicitly allows re-entry.

## Summary

Ticket booking separates approximate browsing from authoritative seat ownership. Atomic bounded holds, exact owner checks and current expiry protect inventory while payment proceeds independently. Confirmation, compensation and admission each need their own durable transition; cache locks, QR images and queued notifications cannot supply those guarantees.

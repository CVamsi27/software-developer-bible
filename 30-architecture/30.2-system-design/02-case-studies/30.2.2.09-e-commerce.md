# E-Commerce System Design

## Definition

An e-commerce platform lets a buyer discover products, prepare a cart and place an order that coordinates inventory, payment and fulfillment. A search result can be stale; checkout cannot treat that stale price or stock count as the authoritative purchase contract.

> **Textbook Definition:** An e-commerce platform coordinates product discovery, order creation, inventory allocation, and payment, with distinct freshness and correctness requirements for browsing and checkout.

This is a proposed interview design. Traffic estimates and objectives are assumptions to test. Using a card provider, queue and catalog cache does not establish PCI compliance, correct taxes or reliable fulfillment.

## First Principles

A cart expresses intent, not inventory ownership. Several carts can contain the same final unit. Only an authoritative reservation can allocate it; browse caches are insufficient even when very fresh.

Inventory and an external charge fail independently. An order must exist durably before its external payment attempt so the system can explain and recover a lost response. A payment timeout means the charge may have happened, not permission to release everything and start again.

An order is historical evidence. If a customer edits an address or a product price changes tomorrow, yesterday's order must retain the accepted address and priced items. Snapshot the purchase contract rather than reconstructing it from mutable catalog/profile rows.

## Requirements and capacity assumptions

Support catalog/search, cart, authorized checkout, warehouse/SKU inventory, order tracking, payment/refund, fulfillment, promotions, reviews and wishlist. Define product variants, units and seller/warehouse scope before identifying stock. Separate browse/search objectives from admitted checkout and completed fulfillment.

Illustrative daily workload: 100,000 orders ×3 items means 300,000 sold item units. At 2 KB/order, base order records add 200 MB/day. Ten million products ×5 KB is 50 GB; one million 500 KB images is 500 GB, but that image count does not provide one image per product. State the intended coverage and actual image downloads separately.

One million browse interactions at 50 KB is 50 GB/day, about 579 KB/s average. Ten million 500 KB image downloads is 5 TB/day, about 57.9 MB/s average. Those daily divisions do not establish peak bandwidth; a peak factor and request mix are required. Ten thousand orders/minute is about 167/second compared with about 1.16/second average for 100,000/day, so justify burst duration and dependency throughput.

## How the components fit

```text
Catalog authority → derived search/cache/media → product discovery
                                                   ↓
Buyer identity → cart version → server-priced checkout quote
                                                   ↓
                         durable order + inventory reservations
                                                   ↓
                         stable payment command / unknown recovery
                                                   ↓
                         confirmed order + event outbox
                                                   ↓
                         fulfillment / shipment / notifications
```

Begin with a modular transactional core where it meets the workload. Separate services only when ownership or measured scaling/failure isolation justifies the additional distributed consistency boundaries. A list of services and modulo shard functions is not a transaction design.

## Cart mutations and checkout snapshots

Authorize cart ownership from the session and use a version or atomic item updates so two concurrent read-modify-write requests do not lose one another's changes. Define guest-to-account merge semantics, positive bounded quantities and stock/price notices. Cart TTL loss is a product decision; Redis is not automatically a durable cart store.

An add-to-cart stock check can provide useful feedback but must not promise reservation. Checkout revalidates active products, quantities, current prices, promotions, taxes, shipping and address/serviceability. If the displayed quote changed, follow an explicit confirmation policy before charging.

Keep amounts as exact decimal or validated minor units with explicit currency and rounding rules. Country-only hard-coded tax percentages are not a tax engine: jurisdiction, product, buyer status, exemptions and effective dates can change the result. Use reviewed market-specific rules or a suitable service, and record the calculation version/evidence. Promotions need atomic usage limits, per-buyer eligibility and bounds preventing invalid negative totals.

Snapshot item description/SKU, quantity, unit price, discounts, taxes, shipping and accepted addresses in the order. A mutable user-address foreign key can help reference the source, but cannot replace its accepted snapshot. Minimize access and retention for personal delivery data.

## Example: reserve one SKU without overselling

This complete PostgreSQL example shows a single-SKU reservation boundary. It does not implement order authentication, multi-item atomicity, expiry or price calculation.

```sql
CREATE TABLE inventory (
  sku TEXT PRIMARY KEY,
  available BIGINT NOT NULL CHECK (available >= 0)
);
CREATE TABLE inventory_reservations (
  reservation_id UUID PRIMARY KEY,
  order_id UUID NOT NULL,
  sku TEXT NOT NULL REFERENCES inventory(sku),
  quantity BIGINT NOT NULL CHECK (quantity > 0),
  state TEXT NOT NULL CHECK (state IN ('active','consumed','released')),
  UNIQUE (order_id, sku)
);
CREATE FUNCTION reserve_sku(
  p_reservation UUID, p_order UUID, p_sku TEXT, p_quantity BIGINT
) RETURNS VOID LANGUAGE plpgsql AS $$
DECLARE changed INTEGER;
BEGIN
  IF p_quantity IS NULL OR p_quantity <= 0 THEN
    RAISE EXCEPTION 'Quantity must be positive';
  END IF;
  INSERT INTO inventory_reservations
    VALUES(p_reservation,p_order,p_sku,p_quantity,'active');
  UPDATE inventory SET available=available-p_quantity
    WHERE sku=p_sku AND available>=p_quantity;
  GET DIAGNOSTICS changed=ROW_COUNT;
  IF changed<>1 THEN
    RAISE EXCEPTION 'Insufficient inventory';
  END IF;
END;
$$;
```

The conditional update tests and consumes available stock under the database's row concurrency rules. If it matches no row, the exception rolls back the inserted reservation as part of the statement. A negative quantity cannot increase stock. The unique order/SKU record distinguishes a retry from another reservation; the API must compare payload and return the recorded result instead of treating a duplicate exception as success for changed inputs.

Trace two orders requesting the final unit. One statement reduces available from 1 to 0 and commits. The other observes no remaining available unit, raises and leaves no reservation. A stale product cache may still display stock 1, but cannot authorize that second purchase.

For several SKU lines, sort/lock consistently and reserve every line in one transaction when they share an authority. Abort all lines if any fails. Across independent inventory authorities, use a durable orchestrated workflow with reservation expiry and compensation; do not ignore a false return halfway through the cart.

## Release and consume are one-time transitions

A reservation owns quantity until consumed or released. Release must first claim active-to-released under a row lock/conditional transition, then restore that exact quantity in the same transaction. Repeated release returns the existing result and must not increment stock again. Consumption claims active-to-consumed and does not decrement available a second time if reservation already did so.

Restocking, adjustments, cancellation and returns need identified inventory movements and reconciliation. Model physical on-hand, reserved and available consistently; a sold order, returned damaged item and immediately resalable return are different movements. Record warehouse identity when allocation can vary by location.

Expiry workers use reservation identity/state/version. A delayed release must not undo an already consumed or renewed reservation. Payment success after reservation loss needs compensation or new allocation under a stated customer policy, never silent fulfillment of nonexistent inventory. The [ticket-booking case](30.2.2.08-ticket-booking.md) owns the detailed hold/expiry race.

## The order workflow survives partial outcomes

1. Accept a stable checkout command scoped to the authenticated buyer. Freeze its cart/quote version and create the durable pending order.
2. Reserve inventory and promotion use under their authorities. Publish durable work through an outbox or equivalent change capture.
3. Attempt payment with the order's stable provider command identity. Persist unknown/processing outcomes when response is ambiguous.
4. Confirm only after the required allocation and payment policy is satisfied. Commit the order transition and downstream fulfillment event together.
5. Fulfillment workers deduplicate commands and record provider shipment identities. Reconcile ambiguous label/carrier calls before creating another shipment.

A **saga** is a durable workflow coordinating independently committed steps and defined recovery actions. It does not roll back time. Releasing a reservation or refunding a charge can compensate some effects; a parcel already shipped requires a return/interception policy and may not be recoverable automatically. Include stuck-state detection, operator escalation and audit history rather than a generic retry-all loop.

The [payment gateway](30.2.2.06-payment-gateway.md) owns duplicate-charge and unknown-provider recovery. Keying checkout only by user identity merges all that user's future purchases. Use one identity per intended purchase, preserving it through retries; another valid purchase uses another command key.

## Catalog, search and caches are derived views

Cache public catalog/media with defined version and freshness policy. Personal prices, private seller data, cart and order responses require appropriate identity partitioning. Recheck authoritative price/inventory/promotion at checkout; a cache hit does not settle a purchase.

Search indexing uses committed changes with idempotent document versions so an old event cannot restore a withdrawn product. Rebuild into a new index, catch up changes, verify and switch readers; uncoordinated dual writes create missing/divergent records. Bound search inputs and deep pagination; use a stable search-after/snapshot policy where necessary rather than unbounded offsets.

Popularity and counters are derived, while verified-purchase reviews need authoritative order evidence. Do not accept a client-supplied verified flag. Wishlist/review mutations need ownership, uniqueness and moderation rules independent of their UI route.

## Recovery and safe degradation

| Failure | Controlled response |
| ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Search unavailable | Offer bounded catalog/category browsing without changing checkout policy. |
| Inventory authority unavailable | Reject/defer allocation; stale cache or local queue cannot promise ownership. |
| Payment response lost | Keep order recoverable and reconcile its existing command before release/retry decisions. |
| Broker unavailable | Retain committed outbox records and bound backlog; local memory is not durable. |
| Cache lost | Bound database fallback and preserve private access policy instead of stampeding the authority. |
| Shipment outcome unknown | Query/reconcile the existing fulfillment identity; another label can create duplicate shipment work. |

Order queries authorize buyer/seller/operations visibility. Delivery addresses, order totals and payment references must not leak through guessed IDs, logs or shared caches. Provider status callbacks require signature/identity checks and deduplication before changing fulfillment state.

## Real-world decisions

Compare conditional inventory updates with short row locks using measured contention and multi-item transactions. An expiring Redis lock cannot replace the database predicate and may let a paused worker delete a new owner's lock. Avoid recursive unbounded retries for busy inventory.

Choose search, cart and storage systems from query patterns, durability and ownership; Elasticsearch, Redis and async workers are tools, not universal requirements. Sharding product, buyer and order tables independently introduces cross-shard operations that a same-database schema did not have.

Measure reserved/available reconciliation, prevented oversell, oldest pending/unknown order, payment compensation, fulfillment duplicates and checkout abandonment by failure stage. Separate cart abandonment from failed checkout and successful HTTP response from confirmed order. Alert on correctness violations as well as latency and saturation.

## Mistakes

- Trusting cart prices, negative quantities or cached stock at checkout.
- Ignoring a failed reservation or double-restoring quantity on retries.
- Creating an order only after an external charge succeeds.
- Using one payment reference for every purchase by the same user.
- Treating a saga as an atomic rollback of shipments and charges.
- Reconstructing old orders from mutable addresses/catalog or hard-coding broad tax rules as legal fact.

## Best practices

Test concurrent final-unit reservations, multi-item rollback, duplicate checkout, changed payload, reservation expiry and repeated compensation. Exercise lost provider/fulfillment responses and old event versions. Validate historical order snapshots and access policy independently from the browse cache, and load-test hot SKUs instead of only uniform catalog traffic.

## Summary

E-commerce separates tolerant discovery from authoritative checkout. A durable order snapshots the accepted purchase, identity-safe reservations allocate stock and payment/fulfillment progress through recoverable states. Derived caches and search can lag, but cannot determine ownership, price acceptance or financial outcomes.

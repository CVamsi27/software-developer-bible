# Live Betting System Design

## Definition

A bettor sees decimal odds of 1.50 and submits a stake of 20. Before the request reaches the service, the market may close or the price may change. A live-betting system must decide whether to accept that exact request against current authoritative state, then preserve the accepted price and money movement for later settlement. Displaying a price is separate from committing a wager.

**In practice:** A live-betting system publishes changing prices and accepts a wager only when its outcome, price version, account eligibility and available funds are valid at the transaction boundary.

This is a hypothetical interview design, not a claim about a real operator or permission to operate in any jurisdiction. Product eligibility, retention, licensing and responsible-gambling rules require jurisdiction-specific review.

> **Textbook Definition:** A live-betting service publishes changing odds and accepts wagers against authoritative price and account state, preserving transaction identity and settlement rules despite delayed events.


## First Principles

A network delay creates two different views of the same market. A fast display cannot prove a price is still available. Acceptance therefore needs an explicit price version and a serialized decision against market state.

Money introduces a second constraint: checking a balance and subtracting a stake must be one transaction. Otherwise two concurrent bets can spend the same funds. A timeout creates a third constraint: the caller needs a stable command identity to discover whether the transaction committed before retrying.

## Requirements and boundaries

Support live event tracking, changing odds, single wagers, wallets, cash-out offers and settlement. A **market** is a question about an event, such as who wins; an **outcome** is one possible answer; a **leg** is one selected outcome in a multi-market wager. An accumulator combines all selected legs, while a system bet combines defined subsets. Introduce these products after single-wager acceptance works, because void legs, correlated outcomes, rounding and partial settlement add rules beyond one market. A bet slip is the client's unaccepted draft; a wager is the durable accepted transaction.

Separate the optional live video stream from the price and wager paths. Multi-sport adapters normalize event identifiers, timestamps and result states without pretending every sport has identical settlement rules. Eligibility, including age and location, self-exclusion, deposit/stake limits and fraud checks belong on the command path; the frontend alone cannot enforce them.

Use exercise targets of 100,000 connected users, odds propagation below 100 ms and 10,000 accepted commands/s during a short burst. Define the measurement boundaries and percentile before designing for these values. A 99.99% availability target needs a dependency and recovery budget; it is not established by choosing Redis and WebSockets.

## Capacity follows the event and fan-out rates

Assume one million wagers/day averaging 20 currency units: 20 million units/day, with a mean of 11.6 wagers/s. A 10,000/s peak is about 864 times that mean, so state its duration and event concentration; a sustained peak contradicts this daily volume.

At 500 bytes per wager, raw wager records add 500 MB/day before indexes, journals and replicas. At 100,000 odds updates/minute and 100 bytes/update, the source stream is 10 MB/minute, about 0.167 MB/s or 14.4 GB/day. This is **before fan-out**. If each update reaches 1,000 subscribers, delivery traffic is about 167 MB/s before protocol overhead. Partition and load-test the hottest market, not only the aggregate rate.

## Architecture separates display from acceptance

```text
sport feeds -> ordered market processor -> authoritative market state
                                      -> odds events -> gateways -> displays
client command -> eligibility + market/wallet transaction -> wager + journal
                                                        -> committed outbox
verified final result -> settlement transaction -> payout + committed outbox
```

A market processor accepts feed sequence numbers, rejects duplicates and detects gaps. A suspended or unresolved market stays closed to new wagers while the feed is reconciled. A single active writer or fenced ownership prevents an old processor from overwriting newer state after failover. Source event time helps diagnose delay; the acceptance policy specifies which authoritative processing state governs a request.

WebSocket messages carry a market identifier and version. A client receiving version 43 after 41 knows it missed an update and requests a snapshot. Gateways bound each client's output queue and coalesce obsolete prices; a slow subscriber must not block other subscribers. Neither a socket write nor a cached odds value proves that a wager was accepted.

## One acceptance transaction preserves the price and funds

The request contains a stable client command ID, outcome ID, expected odds version, stake and currency. Derive account identity from authentication. Validate positive integer minor units, supported currency, bounds and permissions before accepting the operation.

This interview baseline assumes the current market version, wallet, wager, command record and journal can participate in one transactional authority. If market and wallet services own separate databases, a local transaction cannot make the numbered steps atomic. Keep acceptance in a shared authority or introduce explicit price/funds reservations, expiry, compensation and recovery before splitting it; an outbox alone does not make a distributed debit atomic.

1. Claim `(account_id, command_id)` durably and compare its request fingerprint. Return the recorded result for the same request; reject reuse with different terms.
2. Lock or conditionally update the authoritative market/outcome state and verify the outcome belongs to that market, is open, has the expected version and has not expired. Define a consistent lock order across acceptance and market updates.
3. Lock the wallet and any applicable spending-limit counters. Recheck eligibility and remaining limits at the decision boundary; a concurrent self-exclusion or limit change needs a defined serialization policy.
4. Debit the stake, record the wager's accepted odds/version, post the corresponding journal movement and write an outbox event **in the same commit**. Represent odds with the market's exact fixed-point or scaled-integer precision, not binary floating point; apply a versioned currency rounding rule when calculating a payout. Roll back all of them on failure.
5. Return the durable acceptance ID. If the response disappears, the same command ID retrieves this result without another debit.

A changed price returns a new quote requiring explicit consent according to product policy. Do not silently replace the displayed price with a worse price. A Redis lock with a timeout cannot substitute for the durable command and wallet invariants. Two intentional wagers with identical terms use two command IDs; a ten-second deduplication rule based on account/outcome would reject legitimate work.

The [payment case](30.2.2.06-payment-gateway.md) explains command identity, provider-unknown outcomes and balanced journals. Here the critical addition is serializing price acceptance with money movement. A cached balance or read replica can serve a dashboard but cannot authorize a debit.

## Cash-out prices the remaining claim

Decimal odds represent the total winning return divided by the stake. A stake of 20 at accepted odds of 1.50 creates a potential winning return of 30. If current odds fall to 1.25, the implied chance of winning has increased. An idealized, margin-free present value is `30 / 1.25 = 24`; reversing the ratio would incorrectly reduce the value as that chance improves.

This complete Python example illustrates that arithmetic with decimal strings and assumes a two-decimal currency for display. Production uses the currency's minor-unit precision and an explicit rounding policy. The function does not generate an operator's cash-out quote: spreads, correlated exposure, fees, liability limits and suspension policy are separate inputs.

```python
from decimal import Decimal, ROUND_DOWN

def idealized_claim_value(stake: str, accepted: str, current: str) -> Decimal:
    amount, old_odds, new_odds = map(Decimal, (stake, accepted, current))
    if not all(x.is_finite() for x in (amount, old_odds, new_odds)):
        raise ValueError("finite decimal inputs required")
    if amount <= 0 or old_odds <= 1 or new_odds <= 1:
        raise ValueError("positive stake and decimal odds above one required")
    return (amount * old_odds / new_odds).quantize(
        Decimal("0.01"), rounding=ROUND_DOWN
    )
```

A real offer has an immutable quote ID, amount, currency, wager version and expiration. The server computes it; the client cannot choose the credited amount. Acceptance compares the wager's open state and offer version, records one cash-out movement and transitions it to closed atomically. Cash-out and settlement compete for the **same terminal-state transition**, so only one can credit the wallet. Expired or suspended offers require a new decision, never an unconditional wallet credit.

## Settlement needs an authoritative result and a correction path

An event ending is not necessarily a verified final result. Store the result source, version, applicable rule version and whether an outcome won, lost or was voided. Unknown results must remain pending; treating a missing winner flag as a loss creates an irreversible accounting error.

For each open wager, a settlement command claims a durable identity, computes the return from **accepted** terms, posts the journal and closes the wager in one transaction. Worker retries return the existing settlement. A later official correction uses an auditable reversal/adjustment tied to the prior posting; it does not edit history or blindly repeat the payout. Reconcile wager state, journal postings and external funding/withdrawal records in both directions.

Accumulator payouts require every leg's final/void state and the precise combination rule. Publish partial progress without calling the wager settled. Explain currency rounding at the posting boundary rather than accumulating binary floating-point error.

## Recovery, decisions and operational evidence

| Failure or decision | Required behavior |
| ------------------------------------- | --------------------------------------------------------------------------------------------- |
| Feed gap or processor split ownership | Suspend affected markets; reconcile source sequence and fence stale writers. |
| Acceptance response timeout | Retrieve by command ID; do not create another wager. |
| Wallet authority unavailable | Reject or report unavailable acceptance; retain cached prices as clearly non-binding display. |
| Settlement worker crash | Retry the durable settlement identity and inspect terminal state. |
| Gateway overload | Drop superseded price updates, bound queues and resynchronize versions. |
| Regional partition | Keep an explicit market/wallet authority; avoid independent conflicting debit writers. |

Measure feed age, market suspension time, price-rejection rate, command latency, lock contention, duplicate retry results, unsettled wager age and reconciliation discrepancies. Do not log sensitive account data or turn a fraud signal into an unexplained money adjustment.

## Test the acceptance and settlement boundaries

- Race two different wagers against the last available balance; the accepted debits must never exceed it, and each intent has its own command identity.
- Change or suspend a market while a request uses the previous version. The request either commits against the exact still-open version or receives a changed-price response requiring renewed consent.
- Commit a wager but drop the response. A same-key retry returns that wager without another debit; a changed fingerprint conflicts.
- Race cash-out against settlement for one wager. Exactly one terminal transition and one wallet credit commit.
- Redeliver a settlement result and then apply an official correction. The duplicate does not pay twice; the correction is a linked reversal/adjustment that preserves the original journal history.
- Inject an odds-feed sequence gap and overload one hot market's subscribers. Affected markets suspend until reconciled, while bounded/coalesced display queues do not block wager processing.

## Summary

Live betting separates fast, replaceable price display from authoritative wager acceptance. Durable command identity, current market versions and atomic wallet/journal transitions preserve accepted terms. Cash-out and settlement share one terminal-state boundary, while source gaps and unresolved results stop decisions until they can be reconciled.

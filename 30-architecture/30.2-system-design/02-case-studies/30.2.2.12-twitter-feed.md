# Twitter Feed System Design

## Definition

A user follows hundreds of accounts but expects the next twenty posts immediately. Constructing that feed from every account on every request is expensive; copying a celebrity's post into millions of feeds is expensive in a different way. A feed service chooses where to do this work while checking which posts the requesting user may still see.

**In practice:** A home feed is a bounded, ordered page of posts selected for one viewer from followed authors and other eligible sources. The feed service assembles candidates, checks current visibility and applies the page's ordering or ranking contract.

The workload below is hypothetical. “Twitter feed” names the interview problem; it does not establish current product limits or the architecture of today's service.

> **Textbook Definition:** A social feed service assembles and ranks authorized posts for a user from a changing follow graph, balancing precomputed fan-out with request-time retrieval and freshness.


## First Principles

One post can have many readers. Precomputing their candidates moves work to publication time; collecting candidates when readers arrive moves work to read time. The cheaper choice depends on the author's posting rate, follower activity and required freshness, not follower count alone.

A feed entry is a derived pointer to a post, not an access grant. Unfollow, blocking, deletion and protected-account changes can invalidate a pointer after it was copied. Serving therefore needs current authorization even when candidate storage is eventually consistent.

Pagination introduces a third constraint: equal timestamps and concurrent publications need a stable ordering boundary. An offset into a changing list can repeat or skip content, so the cursor must represent the same ordering used by the query.

## Requirements and workload

Support posting, following/unfollowing, profiles, replies, reposts, likes, media, hashtags, search, interaction notifications, trends, blocking, protected accounts and content moderation. Start with a reverse-chronological home feed; introduce personalized ranking explicitly because ranked pagination needs a snapshot/session policy rather than only a time cursor. Choose a text-length rule for the exercise and specify whether it counts bytes, code points or grapheme clusters.

Assume 500 million daily users, half creating one post/day: 250 million posts/day, about 2,894/s on average and an exercise peak of 10,000/s. At 1.28 KB/post, raw records add 320 GB/day or 116.8 TB/year. A UTF-8 post's character count does not guarantee its byte size; this is a measured average assumption.

If 10% attach an average 200 KB image, uploads add **5 TB/day**, not 50 TB/day. Replication, videos and transformations need separate estimates. Five billion feed reads/day average 57,870/s. A twenty-post response of roughly 1 KB/post gives 100 TB/day, about 1.16 GB/s, before media downloads. Media upload volume does not equal CDN playback/download volume.

At 200 recipients per pushed post, the upper-bound exercise fan-out is 50 billion candidate inserts/day, about 578,704/s. A hybrid policy reduces it; calculate the actual distribution and hottest account. Treat sub-200-ms feed latency and 99.99% availability as targets requiring measurement.

## The durable post precedes its derived views

```text
publish request -> post + idempotent command + outbox (one commit)
                  -> relay -> fan-out / search / trends / notifications
feed request -> pushed candidates + selected author histories
             -> current visibility checks -> merge/rank -> bounded page
media upload -> ownership + processing verification -> ready attachment
```

The posting command uses authenticated identity and a stable client operation ID. Validate media ownership/readiness and reply/repost visibility. Commit the post and its outbox event together; a broker outage leaves a durable backlog, not an in-memory promise. Workers retry stable post/event identities and acknowledge after durable effects. An author-sharded post store supplies profile history and pull candidates independently of a user's cached home feed.

A reply points to a conversation thread; a repost points to an original post plus the reposter. Deleting or hiding the original must affect both. Likes have unique `(user_id, post_id)` identity; counters are derived and may lag. Their uniqueness and counter latency are different guarantees.

## Push ordinary authors; pull expensive ones

**Push:** a worker enumerates followers in bounded pages and inserts `(recipient_id, post_id)` candidates idempotently. Persist progress or task identities so a crash resumes without losing later follower pages. A deduplicated sorted candidate store avoids duplicate list entries on retry.

**Pull:** keep the author's ordered recent history and fetch bounded ranges when an active follower reads. A prolific high-fan-out account may favor pull; an author followed by mostly active readers may justify more push work. Measure candidate writes, active-reader ratio, read amplification and cache miss costs before setting a threshold.

When an author changes strategies, readers temporarily consult both sources and deduplicate by post ID. Preserve a transition watermark so old posts are not lost. Following someone may require bounded history backfill; unfollowing changes authorization immediately, even while stale candidate pointers remain. A social-graph cache must have a defined revocation policy, not an hour-long implicit permission window.

## Trace one chronological page

Suppose the pushed store contains posts `(12:00, 70)` and `(11:59, 65)`, while a pulled author supplies `(12:00, 71)` and `(11:58, 60)`. After visibility checks and deduplication, order by `(created_at, post_id)` descending: 71, 70, 65, 60. A cursor after 70 uses the complete tuple; comparing only time would incorrectly skip or repeat one of the noon posts.

This complete Python example merges already hydrated and authorized candidate records. It deliberately omits network calls, cursor signing, ranking and source fetching. Timestamp values must use one comparable UTC representation, and IDs must have the same type.

```python
def chronological_page(sources, limit, before=None):
    if not isinstance(limit, int) or isinstance(limit, bool) or not 1 <= limit <= 100:
        raise ValueError("limit must be an integer from 1 to 100")
    unique = {}
    for source in sources:
        for post in source:
            key = (post["created_at"], post["id"])
            if before is None or key < before:
                old = unique.get(post["id"])
                if old is not None and old != post:
                    raise ValueError("conflicting versions must be resolved before merging")
                unique[post["id"]] = post
    ordered = sorted(unique.values(),
                     key=lambda p: (p["created_at"], p["id"]), reverse=True)
    page = ordered[:limit]
    cursor = (page[-1]["created_at"], page[-1]["id"]) if page else None
    return page, cursor
```

In a service, fetch more candidates when filtering removes entries, subject to a total scan/deadline budget. Query every chronological source below the same cursor and use an index supporting `(author_id, created_at DESC, post_id DESC)`. Fetch enough from each source to form the page, then determine `has_more` from additional eligible candidates or bounded continuation state; an exactly full page alone is not proof.

The cursor is opaque, validated and bound to the requesting user/feed context. A timestamp/ID cursor avoids shifts caused by newer inserts, but does not freeze membership or ranking. For a ranked feed, preserve a session candidate/ranking snapshot or accept and explain controlled refresh behavior. Ranking changes between pages otherwise cause repeats and omissions even with unique post IDs.

## Hydration checks what the user may see now

Hydration means replacing candidate IDs with post text, author/media metadata and viewer context. Batch cache/database reads instead of one request per candidate. Verify current deletion, blocking and protected-account permissions before returning text or media URLs. A cached author count or candidate pointer cannot establish access.

Use object versions for edits and monotonic deletion tombstones for derived views. A delayed create event must not resurrect a deleted post. Search applies the same visibility rules to results, previews and total counts where disclosure matters. Rebuild indexes from a snapshot plus a replay watermark, then switch the serving alias after catch-up; concurrent best-effort dual writes cannot prove completeness.

For media, keep uploads private until ownership, checksum/type/size and processing checks pass. Publish immutable ready variants with the post; revoke access at the serving boundary before background deletion finishes. Public CDN caching and protected media need distinct cache/access policies.

## Trends count recent activity, not lifetime totals

A trend is activity in a defined time window, usually interpreted relative to a baseline. Deduplicate events, normalize tags with a documented Unicode policy and decide whether repeated tags in one post count once. Count unique participating accounts or apply abuse controls so one account cannot dominate solely by repetition.

Time buckets allow expired activity to leave the window. Late events need an event-time/lateness policy. Subtracting a fixed 0.05 from every score every fifteen minutes is neither a sliding-window count nor a 5% multiplicative decay. Keep location scope, minimum support and moderation separate from raw velocity.

## Failures and design decisions

| Situation | Response |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Fan-out delayed | Merge bounded author-history candidates or serve an authorized stale page with a freshness indicator. |
| Timeline cache lost | Rebuild from durable candidates/history with admission control; avoid an unrestricted database stampede. |
| Hot celebrity post | Partition follower tasks or use pull; do not put all followers into one broker payload. |
| Search unavailable | Report search unavailable or use a documented bounded text-search fallback; unrelated recent posts are not equivalent results. |
| Author changes privacy | Enforce current visibility before serving, then purge/rebuild derived pointers. |
| Region loses write authority | Fence the old writer before promotion; preserve the command/replay contract. |

An ID's format does not guarantee authoritative publication order: generated timestamps can skew across nodes. Keep an explicit stable ordering contract. Modulo routing is not consistent hashing; increasing its shard count remaps keys and needs a migration strategy.

Measure authorized page latency, scanned-to-returned candidate ratio, fan-out lag by author class, graph revocation delay, replay duplicates, cache miss load and trend abuse. Notifications use the [notification case](30.2.2.07-notification-service.md)'s durable intent and consent rules. WebSockets can deliver refresh hints; HTTP still retrieves a recoverable page.

## Test feed consistency and access

- Merge pushed and pulled posts with identical timestamps; verify the `(created_at, post_id)` cursor returns every item once and in the same order.
- Revoke access after a post ID is copied to a candidate cache. Block, unfollow, protect or delete the author, then verify text and media are withheld on cache hits.
- Deliver a deletion tombstone before replaying an older create event; the post must remain deleted in feed, search and media access.
- Crash fan-out midway through a large follower set, restart from its persisted progress, and verify idempotent candidate writes without skipping later pages.
- Move an author from push to pull with the transition watermark active; verify dual reads neither lose nor repeat posts.
- Filter the first candidate batch down to zero visible posts. Refill within the scan/deadline budget and set `has_more` only when an eligible continuation exists.

## Summary

A social feed balances publication work against read work through measured hybrid fan-out. Stable chronological cursors, idempotent candidate insertion and current visibility checks make the derived timeline recoverable. Ranking, search and trends need their own version, pagination and event-time contracts rather than inheriting correctness from a cache.

# Web Crawler System Design

## Definition

A search index needs to discover a page, fetch it without overwhelming its host, extract links and revisit it when it changes. A crawler performs that loop over URLs supplied by untrusted pages. Its **frontier** is the durable set of URLs waiting for a first visit or a scheduled revisit.

> **Textbook Definition:** A web crawler traverses discovered URLs, retrieves permitted resources, and schedules future visits while controlling duplication, resource consumption, and per-origin request behavior.

## First Principles

Links can create an unlimited amount of work, while memory, bandwidth and remote-server capacity are finite. Admission needs a crawl scope and budgets; fetching needs coordinated limits for each origin. An origin is the combination of scheme, host and port, such as `https://example.com:443`.

A worker can crash after claiming a URL. Removing work before storing its result loses progress; never removing it repeats work. Persist a claim with an expiry and generation, then commit completion only for the current claim. Retrying a fetch may repeat a remote request even when local completion is deduplicated.

Two URLs may return the same bytes, while one URL may change tomorrow. URL identity, content deduplication and revisit scheduling therefore solve three different problems.

## Scope and capacity come before worker count

Support seed submission, link discovery, HTML extraction, content storage, status/error reporting, pause/resume and freshness-driven recrawls. PDF/image processing uses separate bounded parsers when the crawl's purpose requires it. Avoid fetching every script, image and video merely because HTML references it. Browser rendering is an optional expensive tier with isolated execution and stricter budgets.

A crawl job specifies permitted origins, depth, maximum accepted URLs, duration, bytes and per-origin demand. Seeds and discovered links pass the same policy. An API must not let an arbitrary caller disable destination safety or crawling policy. Open-ended discovery has no stable percentage-complete denominator; report discovered, queued, active and completed counts, with estimates labeled as estimates.

For a hypothetical ten billion visits in thirty days, the mean is about **3,858 visits/s**. At an assumed 500 KB downloaded per visit, that is 5 PB/month, about 166.7 TB/day and 1.93 GB/s. Fifty extracted links per visit yield about 192,901 discovery candidates/s before deduplication. A measured 5:1 compression ratio would reduce stored bodies to 1 PB/month; it does not reduce inbound download traffic.

Two ideal 10-Gbps network interfaces do not establish a two-node crawler. DNS, remote latency, per-origin limits, decompression, parsing, storage and failure reserve constrain it. At two seconds of mean fetch occupancy, roughly 7,716 requests must be in flight to sustain that mean rate. Retention and storage capacity are product and budget policies; worker count alone does not determine them.

## Follow a URL through the whole system

```text
seeds / extracted links -> scope + URL identity -> durable frontier
frontier -> origin scheduler -> leased fetch -> bounded parser
                                   |                |
                                   v                v
                             response storage   discovered links
                                   -> completion + revisit + outbox
```

The scheduler chooses an eligible origin and claims one due URL. The fetcher applies destination and robots policy, performs a bounded request, and stores response bytes under an immutable content key. The parser resolves links against the final response URL and a validated HTML base URL, then applies admission again. Completion records the fetched version, error or next visit and durable discovery/publication intent.

A broker may distribute tasks and analytics, but its acceptance is not frontier completion. Keep a durable authority for claims, revisit timestamps and policy versions. Store large bodies in object storage; store metadata, checksums, source URLs and scheduling state in a database or purpose-built frontier store. A cached queue can accelerate selection without becoming the only recovery record.

## Coordinate politeness across workers

A local sleep only slows one worker. Several workers can all read the same last-fetch timestamp and start together. The origin authority must atomically reserve the next permitted start time and enforce a concurrent-request cap. Record that reservation with the claim; use a consistent lock order and release capacity on completion or lease recovery.

For example, origin A allows one active request and a one-second start interval. Worker 1 reserves A at 10:00:00; worker 2 must choose another origin or wait. If worker 1 hangs, a bounded timeout ends its request before another claim is admitted under the recovery policy. A lease expiry alone cannot prove the old network request stopped; account for that overlap when selecting limits.

Shard by origin so one scheduler owns its coordinated demand, and fence stale ownership during movement. Fair scheduling prevents an enormous site from starving smaller eligible origins. Respect `Retry-After` where applicable, reduce demand after overload, and include jitter without allowing early starts. Reduce concurrency when a host is distressed; shortening timeouts and immediately retrying can make distress worse.

## Robots rules and destination safety are separate checks

`robots.txt` describes crawler access policy, not user authentication. Select the crawler's matching user-agent rules and evaluate allowed/disallowed paths with a compliant parser. Fetch/cache rules with their status and expiry. Under RFC 9309, unavailable 4xx responses may permit access; an unreachable file from network/server failure initially requires complete disallow. Normal cached rules should not be used beyond 24 hours unless the file is unreachable. `crawl-delay` is an extension, so support it explicitly where required rather than presenting it as universal RFC syntax. [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html).

Fetching user-supplied URLs can cause **server-side request forgery (SSRF)**: the crawler reaches an internal service on the caller's behalf. Permit only intended schemes and ports; reject embedded credentials, private/loopback/link-local destinations and cloud metadata routes. Resolve and validate every address, ensure the actual connection uses the approved destination, and reapply policy at each redirect. DNS rebinding defeats a separate one-time hostname check. Egress enforcement supplies a boundary even when a URL parser or application check fails.

Apply destination safety to robots files, sitemaps, callbacks and browser subresources too. Disable automatic redirects until each hop is checked; bound redirect count and total time. A public page redirecting to an internal address is still unsafe. Crawl policy cannot grant access to an otherwise forbidden destination.

## Preserve URL meaning when deduplicating

Lowercase the scheme and hostname, remove the fragment and normalize the scheme's default port. Preserve case-sensitive paths, trailing slashes, query order, repeated parameters and non-default ports unless the target's semantics establish equivalence. `/products` and `/products/` can be different resources. Removing port 80 from HTTPS changes the destination. Do not treat a page's canonical-link hint as permission to drop another URL or cross a trust boundary.

This complete Python helper demonstrates a deliberately narrow policy for absolute, ASCII HTTP(S) URLs. It preserves path/query meaning and rejects controls or credentials. It is **not a fetch permission check**: it performs no DNS, IP-range, redirect or egress validation. International hostnames require an explicit IDNA policy before this helper.

```python
from urllib.parse import urlsplit, urlunsplit
from ipaddress import IPv4Address
import re

def url_identity(raw: str) -> str:
    if not isinstance(raw, str) or not raw or len(raw) > 2048:
        raise ValueError("bounded absolute URL required")
    if any(ord(c) <= 32 or ord(c) >= 127 for c in raw) or "\\" in raw:
        raise ValueError("ASCII URL without spaces, controls or backslashes required")
    p = urlsplit(raw)
    scheme, host = p.scheme.lower(), p.hostname
    if scheme not in ("http", "https") or not host:
        raise ValueError("HTTP(S) host required")
    if p.username is not None or p.password is not None:
        raise ValueError("credentials forbidden")
    if host.endswith("."):
        host = host[:-1]  # Rooted and unrooted DNS spellings share one identity.
    if not host or host.endswith(".") or len(host) > 253:
        raise ValueError("invalid or overlong host")
    labels = host.split(".")
    if all(label.isdigit() for label in labels):
        if len(labels) != 4:
            raise ValueError("numeric host must be a four-part IPv4 address")
        try:
            host = str(IPv4Address(host))
        except ValueError as error:
            raise ValueError("invalid IPv4 address") from error
    elif any(
        not 1 <= len(label) <= 63
        or not re.fullmatch(r"[A-Za-z0-9](?:[A-Za-z0-9-]*[A-Za-z0-9])?", label)
        for label in labels
    ):
        raise ValueError("invalid ASCII DNS name")
    port = p.port  # raises for invalid or out-of-range ports
    if port == 0:
        raise ValueError("port zero forbidden")
    authority = host.lower()
    if port is not None and port != (443 if scheme == "https" else 80):
        authority += f":{port}"
    return urlunsplit((scheme, authority, p.path or "/", p.query, ""))
```

Python's URL parsing functions separate components but do not validate a destination's trustworthiness. The helper's narrow syntax and the network safety layer remain separate. [Python URL parsing documentation](https://docs.python.org/3/library/urllib.parse.html).

## Persist claims and results without losing work

An illustrative PostgreSQL frontier stores one identity and a revisitable state. This executable schema omits origin coordination and result tables so it does not pretend one table is the whole scheduler.

```sql
CREATE TABLE crawl_frontier (
    url TEXT PRIMARY KEY,
    origin TEXT NOT NULL,
    depth integer NOT NULL CHECK (depth >= 0),
    priority integer NOT NULL CHECK (priority BETWEEN 1 AND 10),
    due_at timestamptz NOT NULL,
    state text NOT NULL CHECK (state IN ('ready', 'leased', 'blocked', 'retired')),
    generation bigint NOT NULL DEFAULT 0 CHECK (generation >= 0),
    leased_by text,
    lease_until timestamptz,
    CHECK ((state = 'leased') = (leased_by IS NOT NULL AND lease_until IS NOT NULL)),
    CHECK (state = 'leased' OR (leased_by IS NULL AND lease_until IS NULL))
);
CREATE INDEX crawl_due ON crawl_frontier (origin, due_at, priority DESC)
    WHERE state = 'ready';
```

Within one transaction, reserve the origin's eligible slot, select a due ready row with a lock, transition it to leased and increment its generation. Commit before downloading; do not hold a database transaction across remote HTTP. The worker completes only if URL, owner, generation and unexpired lease still match. A reaper clears expired ownership under the same authority and reschedules bounded recovery. A late old worker cannot overwrite the newer result.

Write fetched-result metadata, the next visit and outbox/discovery intents together where one database owns them. An object upload can finish before that commit; treat its immutable key as staged and garbage-collect unreferenced objects later. Never mark content seen before retaining the result needed for recovery. If link discovery is paged, persist page progress; a crash after storing a page must not silently omit all its outgoing links.

## Deduplication saves work without hiding coverage

An exact URL set prevents duplicate frontier admission; it must not prevent a due revisit. A Redis set is an exact set of its stored members, not a Bloom filter. A Bloom filter can answer “definitely absent” or “possibly present.” Confirm positive matches against exact storage when skipping a never-seen URL would violate coverage. An intentionally approximate crawl may tolerate omissions, but it must say so.

A cryptographic content checksum identifies equal stored bytes. Near-duplicate techniques such as SimHash compare compact fingerprints of chosen textual features; a small Hamming distance is a similarity signal, not proof of equal content. Define tokenization, weighting and the candidate-search index before claiming useful near-duplicate detection. HTML templates can make unrelated pages look similar.

Keep URL-to-content associations even for duplicate bodies. Resolve each page's relative links against its own effective base before deciding whether extraction can be reused; identical HTML at different paths may discover different URLs. Deduplicating body storage must not erase visit provenance, freshness or outgoing-link coverage.

## Bound hostile input and revisit useful pages

Reuse bounded HTTP connection pools. Cap response bytes **during** streaming, plus decompressed bytes, parsing time, link count and metadata sizes. A `Content-Length` header can be absent or false; decompression bombs and endless responses need independent limits. Classify HTTP outcomes explicitly rather than marking every received response successful.

Keep the final URL, status, selected headers, checksum, timing and parser version. Conditional requests using ETag or Last-Modified can reduce transfer on revisits; a 304 needs an existing compatible retained representation. Schedule changes from observed update frequency and crawl purpose, with upper/lower bounds and starvation prevention. Retry transient errors within a budget; distinguish permanent exclusion, temporary failure and a successful empty page.

Protect extractors and optional browser workers from active content. Pause stops new claims while current claims drain or expire under policy. Content may contain personal or protected information: define retention, access controls, deletion and the purpose of the crawl instead of retaining everything indefinitely.

## Decisions, failures and evidence

| Decision or failure | What to establish |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Breadth-first versus priority scheduling | Coverage/depth fairness versus freshness; prevent unbounded priority starvation. |
| Worker dies after fetch | Expired claim is recoverable; immutable result references and discovery progress avoid lost work. |
| Origin rules change | Refresh policy and recheck before dispatch; a cached permit is not permanent. |
| Frontier cache fails | Recover from durable authority with admission control, not an uncoordinated local queue. |
| Storage is full | Stop or delay acceptance/completion; do not record success for an unretained body. |
| Region loses ownership | Fence old completions and coordinate origin limits before promoting another scheduler. |

Measure origin demand, rule age, blocked destinations, oldest eligible frontier item, claim expiry/recovery, fetched and decompressed bytes, parser errors, duplicate-body ratio and discovery coverage. A low page rate can be deliberate politeness; alert on violated service contracts rather than a universal throughput threshold.

## Mistakes and best practices

Avoid check-then-remove queue claims, permissive robots behavior for every exception, unbounded response reads, and aggressive URL normalization. Test redirects to forbidden destinations, DNS changes, two workers claiming one origin, completion after lease replacement, duplicate-body links with different bases and revisits after a successful crawl. The local helper/schema checks do not establish a safe deployed crawler or the exercise's throughput.

## Summary

A crawler is a bounded, recoverable discovery loop over untrusted destinations. Coordinate origin demand, preserve URL meaning, separate exact/approximate deduplication, and complete leased work only under current ownership. Destination safety, robots policy, retained results and scheduled revisits each need their own explicit boundary.

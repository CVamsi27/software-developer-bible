# Web Crawler System Design

A calendar page can generate a different URL for every date, so one seed can create an endless queue. Fetch too quickly and the crawler can overload the site; lose a worker mid-fetch and it can lose or duplicate work. The design must bound discovery, coordinate requests per origin, and recover each visit safely:

```text
calendar trap → ∞ URLs → scope + per-origin limits + leased claims.
```

## Definition

A search index needs to discover a page, fetch it without overwhelming its host, extract links, and revisit it when it changes. A crawler performs that loop over URLs supplied by untrusted pages. Its **frontier** is the durable set of URLs waiting for a first visit or a **scheduled revisit**.

> **Textbook Definition:** A web crawler traverses discovered URLs, retrieves permitted resources, and schedules future visits while controlling duplication, resource consumption, and per-origin request behavior.

## First Principles

1. Links can create an unlimited amount of work, while memory, bandwidth, and remote-server capacity are finite. Admission needs a crawl scope and budgets; fetching needs coordinated limits for each origin. An origin is the combination of scheme, host, and port, such as `https://example.com:443`.
2. A worker can crash after claiming a URL. Removing work before storing its result loses progress; never removing it repeats work. Persist a claim with an expiry and generation, then commit completion only for the current claim. Retrying a fetch may repeat a remote request even when local completion is deduplicated.
3. Two URLs may return the same bytes, while one URL may change tomorrow. URL identity, content deduplication, and revisit scheduling therefore solve three different problems.

## Scope and capacity come before worker count

Support seed submission, link discovery, HTML extraction, content storage, status/error reporting, pause/resume, and freshness-driven recrawls. PDF/image processing uses separate bounded parsers when the crawl's purpose requires it. Avoid fetching every script, image, and video merely because HTML references it. Browser rendering is an optional expensive tier with isolated execution and stricter budgets.

A crawl job specifies permitted origins, depth, maximum accepted URLs, duration, bytes, and per-origin demand. Seeds and discovered links pass the same policy. An API must never let an arbitrary caller disable destination safety or crawling policy. Open-ended discovery holds no stable percentage-complete denominator; report discovered, queued, active, and completed counts, with estimates labeled as estimates.

For a hypothetical ten billion visits in thirty days, the mean is about **3,858 visits/s**. At an assumed 500 kB downloaded per visit (decimal units), that is 5 PB/month, about 166.7 TB/day and 1.93 GB/s inbound. Fifty extracted links per visit yield about 192,901 discovery candidates/s before deduplication. A measured 5:1 compression ratio would reduce stored bodies to 1 PB/month; it never reduces inbound traffic.

Two 10-Gbps links provide at most 2.5 GB/s of theoretical aggregate throughput, only modestly above the 1.93 GB/s mean inbound estimate and before protocol overhead or failure reserve. That arithmetic never establishes a two-node crawler: DNS, remote latency, per-origin limits, decompression, parsing, and storage can each become the bottleneck. At two seconds of mean fetch occupancy, roughly 7,716 requests must be in flight to sustain that mean rate. Retention and storage capacity are product and budget policies; worker count alone never determines them.

## Follow a URL through the whole system

```text
seeds / extracted links -> scope + URL identity -> durable frontier
frontier -> origin scheduler -> leased fetch -> bounded parser
                                   |                |
                                   v                v
                             response storage   discovered links
                                   -> completion + revisit + outbox
```

The scheduler chooses an eligible origin and claims one due URL. The fetcher applies destination and robots policy, performs a bounded request, and stores response bytes under an immutable content key. The parser resolves links against the final response URL and a validated HTML base URL, then applies admission again. Completion records the fetched version, error or next visit, and durable discovery/publication intent.

A broker may distribute tasks and analytics, but its acceptance is no frontier completion. Keep a durable authority for claims, revisit timestamps, and policy versions. Store large bodies in object storage; store metadata, checksums, source URLs, and scheduling state in a database or purpose-built frontier store. A cached queue can accelerate selection without becoming the only recovery record.

## Coordinate politeness across workers

A local sleep only slows one worker. Several workers can all read the same last-fetch timestamp and start together. The origin authority must atomically reserve the next permitted start time and enforce a concurrent-request cap. Record that reservation with the claim; use a consistent lock order and release capacity on completion or lease recovery.

For example, origin A allows one active request and a one-second start interval. Worker 1 reserves A at 10:00:00; worker 2 must choose another origin or wait. If worker 1 hangs, a bounded timeout ends its request before another claim is admitted under the recovery policy. A lease expiry alone cannot prove the old network request stopped; account for that overlap when selecting limits.

Shard by origin so one scheduler owns its coordinated demand, and fence stale ownership during movement. Fair scheduling prevents an enormous site from starving smaller eligible origins. Respect `Retry-After` where applicable, reduce demand after overload, and include jitter without allowing early starts. Reduce concurrency when a host is distressed; shortening timeouts and immediately retrying can make distress worse.

## Robots rules and destination safety are separate checks

`robots.txt` describes crawler access policy, not user authentication. A compliant parser merges matching user-agent groups, applies the most specific path rule (the longest match), and favors `Allow` when an `Allow` and `Disallow` rule are equivalent. Fetch and cache rules with their status and expiry.

Under RFC 9309, a robots response in the 4xx range may be treated as unavailable, while a network or 5xx failure initially requires complete disallow. Treat HTTP 429 as an overload signal and back off using `Retry-After`, even though it is a 4xx response.

Follow at least five consecutive robots redirects when possible, applying destination safety at every hop and interpreting the final rules for the original origin. Never use cached rules beyond 24 hours unless the file is unreachable. `crawl-delay` is an extension, so support it explicitly where required rather than presenting it as universal RFC syntax. [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html); [RFC 6585](https://datatracker.ietf.org/doc/html/rfc6585#section-4).

Fetching user-supplied URLs can cause **server-side request forgery (SSRF)**: the crawler reaches an internal service on the caller's behalf. Permit only intended schemes and ports; reject embedded credentials, private/loopback/link-local destinations, and cloud metadata routes. Validate all resolved IPv4 and IPv6 addresses, reject unsafe answers, then connect to an approved address without a second unchecked lookup.

Preserve the original hostname for the HTTP `Host` header, Transport Layer Security (TLS) Server Name Indication (SNI), and certificate verification. Reapply destination policy at every redirect and retry; DNS rebinding defeats a one-time hostname check. Egress enforcement supplies a boundary even when a URL parser or application check fails.

Apply destination safety to robots files, sitemaps, callbacks, and browser subresources too. Disable automatic redirects until each hop is checked; bound redirect count and total time. A public page redirecting to an internal address is still unsafe. Crawl policy cannot grant access to an otherwise forbidden destination.

## Preserve URL meaning when deduplicating

Lowercase the scheme and hostname, remove the fragment, and normalize the scheme's default port. Preserve case-sensitive paths, trailing slashes, query order, repeated parameters, and non-default ports unless the target's semantics establish equivalence. `/products` and `/products/` can be different resources. Removing port 80 from HTTPS changes the destination. Never treat a page's canonical-link hint as permission to drop another URL or cross a trust boundary.

This complete Python helper demonstrates a deliberately narrow policy for absolute, ASCII HTTP(S) URLs. It preserves path/query meaning and rejects controls or credentials. It is **not a fetch permission check**: it performs no DNS, IP-range, redirect, or egress validation. International hostnames require an explicit Internationalized Domain Names in Applications (IDNA) policy before this helper:

```python
from urllib.parse import urlsplit, urlunsplit
from ipaddress import IPv4Address, IPv6Address
import re

def url_identity(raw: str) -> str:
    if not isinstance(raw, str) or not raw or len(raw) > 2048:
        raise ValueError("bounded absolute URL required")
    if any(ord(c) <= 32 or ord(c) >= 127 for c in raw) or "\\" in raw:
        raise ValueError("ASCII URL without spaces, controls or backslashes required")
    if re.search(r"%(?![0-9A-Fa-f]{2})", raw):
        raise ValueError("percent escapes must contain two hexadecimal digits")
    p = urlsplit(raw)
    scheme, host = p.scheme.lower(), p.hostname
    if scheme not in ("http", "https") or not host:
        raise ValueError("HTTP(S) host required")
    if p.username is not None or p.password is not None:
        raise ValueError("credentials forbidden")
    if host.endswith("."):
        host = host[:-1]  # Rooted and unrooted DNS spellings share one identity.
    if not host or host.endswith(".") or len(host) > 253:
        raise ValueError("invalid or overlong host")
    if ":" in host:
        if "%" in host:
            raise ValueError("scoped IPv6 addresses are not supported")
        try:
            host = f"[{IPv6Address(host).compressed}]"
        except ValueError as error:
            raise ValueError("invalid or scoped IPv6 address") from error
    else:
        labels = host.split(".")
        if all(label.isdigit() for label in labels):
            if len(labels) != 4:
                raise ValueError("numeric host must be a four-part IPv4 address")
            try:
                host = str(IPv4Address(host))
            except ValueError as error:
                raise ValueError("invalid IPv4 address") from error
        elif any(
            not 1 <= len(label) <= 63
            or not re.fullmatch(r"[A-Za-z0-9](?:[A-Za-z0-9-]*[A-Za-z0-9])?", label)
            for label in labels
        ):
            raise ValueError("invalid ASCII DNS name")
    port = p.port  # raises for invalid or out-of-range ports
    if port == 0:
        raise ValueError("port zero forbidden")
    authority = host.lower()
    if port is not None and port != (443 if scheme == "https" else 80):
        authority += f":{port}"
    return urlunsplit((scheme, authority, p.path or "/", p.query, ""))
```

Python's URL parsing functions separate components but never validate URL syntax or destination trustworthiness, so the helper applies its own narrow checks. It accepts ASCII DNS names, IPv4, and bracketed IPv6 literals; internationalized domain names (IDNs) require a separately defined IDNA policy. This is still not a fetch permission check: DNS resolution, address policy, redirects, and egress enforcement belong to the network safety layer. [Python URL parsing documentation](https://docs.python.org/3/library/urllib.parse.html); [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

## Persist claims and results without losing work

An illustrative PostgreSQL frontier stores one identity and a revisitable state. This executable schema omits origin coordination and result tables so it never pretends one table is the whole scheduler:

```sql
CREATE TABLE crawl_frontier (
    url TEXT PRIMARY KEY,
    origin TEXT NOT NULL,
    depth integer NOT NULL CHECK (depth >= 0),
    priority integer NOT NULL CHECK (priority BETWEEN 1 AND 10),
    due_at timestamptz NOT NULL,
    state text NOT NULL CHECK (state IN ('ready', 'leased', 'blocked', 'retired')),
    generation bigint NOT NULL DEFAULT 0 CHECK (generation >= 0),
    leased_by text,
    lease_until timestamptz,
    CHECK ((state = 'leased') = (leased_by IS NOT NULL AND lease_until IS NOT NULL)),
    CHECK (state = 'leased' OR (leased_by IS NULL AND lease_until IS NULL))
);
CREATE INDEX crawl_due ON crawl_frontier (origin, due_at, priority DESC)
    WHERE state = 'ready';
```

Within one transaction, reserve the origin's eligible slot, select a due ready row with a lock, transition it to leased, and increment its generation. Commit before downloading; never hold a database transaction across remote HTTP. The worker completes only if URL, owner, generation, and unexpired lease still match. A reaper clears expired ownership under the same authority and reschedules bounded recovery. A late old worker cannot overwrite the newer result.

Write fetched-result metadata, the next visit, and outbox/discovery intents together where one database owns them. An object upload can finish before that commit; treat its immutable key as staged and garbage-collect unreferenced objects later. Never mark content seen before retaining the result needed for recovery. If link discovery is paged, persist page progress; a crash after storing a page must never silently omit all its outgoing links.

## Deduplication saves work without hiding coverage

An exact URL set prevents duplicate frontier admission; it must never prevent a due revisit. A Redis set is an exact set of its stored members, not a Bloom filter. A Bloom filter can answer "definitely absent" or "possibly present." Confirm positive matches against exact storage when skipping a never-seen URL would violate coverage. An intentionally approximate crawl may tolerate omissions, but it must say so.

A cryptographic content checksum identifies equal stored bytes. Near-duplicate techniques such as SimHash compare compact fingerprints of chosen textual features; a small Hamming distance is a similarity signal, not proof of equal content. Define tokenization, weighting, and the candidate-search index before claiming useful near-duplicate detection. HTML templates can make unrelated pages look similar.

Keep URL-to-content associations even for duplicate bodies. Resolve each page's relative links against its own effective base before deciding whether extraction can be reused; identical HTML at different paths may discover different URLs. Deduplicating body storage must never erase visit provenance, freshness, or outgoing-link coverage.

## Bound hostile input and revisit useful pages

Reuse bounded HTTP connection pools. Cap response bytes **during** streaming, plus decompressed bytes, parsing time, link count, and metadata sizes. A `Content-Length` header can be absent or false; decompression bombs and endless responses need independent limits. Classify HTTP outcomes explicitly rather than marking every received response successful.

Keep the final URL, status, selected headers, checksum, timing, and parser version. Conditional requests using entity tags (ETags) or Last-Modified can reduce transfer on revisits; a 304 needs an existing compatible retained representation. Schedule changes from observed update frequency and crawl purpose, with upper/lower bounds and starvation prevention. Retry transient errors within a budget; distinguish permanent exclusion, temporary failure, and a successful empty page.

Protect extractors and optional browser workers from active content. Pause stops new claims while current claims drain or expire under policy. Content may contain personal or protected information: define retention, access controls, deletion, and the purpose of the crawl instead of retaining everything indefinitely.

## Decisions, metrics and tests

| Decision or failure | What to establish |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Breadth-first versus priority scheduling | Coverage/depth fairness versus freshness; prevent unbounded priority starvation. |
| Worker dies after fetch | Expired claim is recoverable; immutable result references and discovery progress avoid lost work. |
| Origin rules change | Refresh policy and recheck before dispatch; a cached permit is not permanent. |
| Frontier cache fails | Recover from durable authority with admission control, not an uncoordinated local queue. |
| Storage is full | Stop or delay acceptance/completion; do not record success for an unretained body. |
| Region loses ownership | Fence old completions and coordinate origin limits before promoting another scheduler. |

Measure origin demand, rule age, blocked destinations, oldest eligible frontier item, claim expiry/recovery, fetched and decompressed bytes, parser errors, duplicate-body ratio, and discovery coverage. A low page rate can be deliberate politeness; alert on violated service contracts rather than a universal throughput threshold.

Test the promised boundaries before increasing worker count:

| Test | Expected result |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Equivalent hosts, IPv6 literals and paths | Default ports/fragments and IPv6 spellings normalize; meaningful path/query differences remain distinct. |
| Malformed escapes or credentials | URL admission rejects them before they enter the frontier. |
| Redirect or DNS answer reaches private IP | The fetch is blocked after re-resolving and validating the actual destination. |
| `robots.txt` returns 429 or 5xx | The crawler backs off on 429 and follows its conservative unreachable-file policy for 5xx/network failure. |
| Two workers race for one origin | The origin concurrency and start interval hold across workers. |
| Lease expires before old worker completes | The new generation wins; the stale completion cannot overwrite it. |
| Same bytes at different page bases | Body storage deduplicates while both pages retain correct link coverage. |
| Revisit after a prior success | The same URL can be scheduled when due and its new response becomes the current version. |

These fixtures verify local policy and state transitions; measured origin behavior, network enforcement, and production throughput require deployment-level tests.

## Summary

A crawler is a bounded, recoverable discovery loop over untrusted destinations. Coordinate origin demand, preserve URL meaning, separate exact/approximate deduplication, and complete leased work only under current ownership. Destination safety, robots policy, retained results and scheduled revisits each need their own explicit boundary.

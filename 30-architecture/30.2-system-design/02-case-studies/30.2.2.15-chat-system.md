# Chat System Design

Alice sends a message from her phone, loses the connection, and retries from the same device. Bob reads it on a laptop, then opens his phone later. A chat service must retain one accepted message, recover each device's missing history, and distinguish "stored by the service" from "stored or read by Bob":

```text
send → commit seq 42 → reply lost → retry same op ID → 42; laptop ack ≠ phone delivery.
```

## Definition

A **chat service** maintains conversations, participant membership, message history, and online delivery, distinguishing **durable message acceptance** from **device delivery** and **read acknowledgment**.

> **Textbook Definition:** A chat service maintains conversations, participant membership, message history, and online delivery, distinguishing durable message acceptance from device delivery and read acknowledgment.

This hypothetical case extends the [WhatsApp case](30.2.2.02-whatsapp.md) with conversation membership, large-group history, edits, reactions, presence, and search. That chapter owns the basic durable messaging and device-delivery model; this one develops the additional boundaries rather than implementing a second transport stack.

## First Principles

1. An intermittent connection makes a lost reply indistinguishable from a rejected send at the client. Retain a stable client operation ID and resolve retries against durable acceptance. A socket write cannot prove recipient storage, and recipient storage cannot prove human reading.
2. Conversation membership changes while messages and devices remain offline. Define which historical range each participant may access, then authorize sends, history, subscriptions, and attachments under that rule. Copying a message into a cache cannot grant permission.
3. A user may hold several active devices. Closing one connection cannot make all devices offline; an old connection's cleanup cannot delete a replacement. Connection identities and expiry belong to the routing layer, while durable history belongs to the conversation authority.

## Define the product contract before the transport

Support direct and group conversations, text/media, replies, history pagination, delivery/read receipts, edits/deletions, reactions, typing, presence, device sync, and notification hints. Define maximum group size, retention, edit window, administrator powers, and the visibility of messages before joining or after leaving. "Infinite scroll" is a navigation behavior within retention, not infinite storage.

Choose encryption policy explicitly. Transport encryption protects network traffic; end-to-end encryption (E2EE) keeps message plaintext from the service under its key/device protocol. Service-side full-text search over plaintext cannot simultaneously claim the server never receives plaintext. Use on-device search for that contract, or explain a different, reviewed disclosure model. Group membership changes also need key rotation and authorized-device distribution. Never put private encryption keys inside chat messages; provision device keys through the reviewed protocol. Use established protocols rather than a homemade "Signal-like" algorithm. [Signal protocol documentation](https://signal.org/docs/).

A hypothetical workload of one billion daily users sending fifty messages each produces 50 billion messages/day, about 578,704/s on average. At 1 KB per accepted record, text/metadata adds 50 TB/day and 18.25 PB/year before replicas/indexes. If 10% carry a 500-KB attachment, source uploads add **2.5 PB/day**; a CDN offloads origin delivery but never magically compresses this into 250 TB/day. Downloads and group fan-out need separate recipient-rate estimates.

At 500 million simultaneous connections and an assumed 10 KB per connection, baseline connection memory is 5 TB before runtime, queues, and transport overhead. A measured 100,000 connections/node would require 5,000 nodes before redundancy. These are arithmetic assumptions, not benchmarked limits. Specify whether a sub-100-ms target measures service acceptance or online device delivery and from which region; disconnected devices cannot meet an immediate-delivery deadline.

## Store authoritative history before deriving delivery

```text
client command -> membership + command identity + conversation transaction
               -> message/version + outbox (durable acceptance)
outbox -> delivery routing -> current device connection -> device receipt
history request -> current membership/history policy -> ordered message range
device reconnect -> authenticated cursor -> retained changes -> local durable apply
```

The conversation owner serializes accepted messages and membership changes. A transaction assigns a conversation-local sequence, retains the stable command identity and payload fingerprint, inserts the message, and appends delivery intent. Return acceptance only after the authority's durable commit. A lost reply with the same command returns the same sequence; a changed payload under that command is a conflict.

The outbox relay can send the same intent more than once. Device storage deduplicates by conversation/message identity before acknowledging. A routing outage leaves messages available through history/reconnect; Redis's offline queue must never be their only copy. If a broker is chosen as the authoritative log instead of the database, specify its durable acceptance, projection lag, and replay contract. Never alternate between "database-first" prose and an unacknowledged broker-only implementation.

## Conversation sequences provide an ordering boundary

A UUID identifies a message but never proves chronological order. Use an authority-assigned sequence for the conversation's accepted order. Timestamps help display time; they may tie or skew. For large deployments, route the conversation to its owner and fence old writers during movement. Partitioning by conversation alone never serializes concurrent application handlers or external effects.

This executable PostgreSQL schema illustrates the identity constraints for one shard. It is no complete membership/retention service or a claim that one PostgreSQL instance meets the workload. Public APIs serialize large sequence values safely, for example as decimal strings:

```sql
CREATE TABLE chat_conversations (
    id bigint PRIMARY KEY,
    next_sequence bigint NOT NULL DEFAULT 1 CHECK (next_sequence > 0)
);
CREATE TABLE chat_members (
    conversation_id bigint NOT NULL REFERENCES chat_conversations(id),
    user_id bigint NOT NULL,
    active boolean NOT NULL,
    PRIMARY KEY (conversation_id, user_id)
);
CREATE TABLE chat_messages (
    conversation_id bigint NOT NULL REFERENCES chat_conversations(id),
    sequence bigint NOT NULL CHECK (sequence > 0),
    sender_id bigint NOT NULL,
    client_operation_id uuid NOT NULL,
    payload_fingerprint text NOT NULL,
    content bytea NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (conversation_id, sequence),
    UNIQUE (conversation_id, sender_id, client_operation_id)
);
CREATE TABLE chat_outbox (
    conversation_id bigint NOT NULL,
    sequence bigint NOT NULL,
    PRIMARY KEY (conversation_id, sequence),
    FOREIGN KEY (conversation_id, sequence)
        REFERENCES chat_messages(conversation_id, sequence)
);
```

Lock the conversation row in one transaction. Recheck active membership under the same serialization contract used by membership changes, then inspect the scoped client operation. For new work, treat `next_sequence` as the next unallocated value, reserve it while holding the row lock, insert the message, and insert its outbox row before commit. For an existing command, compare the fingerprint and return its retained result without allocating another sequence. Retain operation IDs and fingerprints through at least the client retry window, even if message content expires; a tombstone or separate command ledger can preserve that identity. Rollback restores the counter and all local writes. The schema alone enforces neither these transaction steps nor active membership.

The following is a parameterized SQL fragment (`$1` is a bound conversation ID). Run it after locking the conversation row, checking active membership, and resolving any retry:

```sql
UPDATE chat_conversations
   SET next_sequence = next_sequence + 1
 WHERE id = $1
 RETURNING next_sequence - 1 AS allocated_sequence;
```

For history, authorize first, then query `(conversation_id, sequence)` below a validated cursor in descending sequence order. Fetch `limit + 1` eligible records to establish another page rather than returning `has_more: true` on every cache hit. Include historical membership ranges where product policy requires them. A deleted record may remain a tombstone for sync; the UI can hide its content without pretending the sequence never existed.

## Trace acceptance, device delivery and reading separately

Suppose Alice's command `C7` commits as conversation sequence 42, but the acceptance reply is lost. Retrying `C7` returns 42. Delivery worker W1 sends 42 to Bob's laptop and crashes before recording its receipt. W2 sends it again; Bob's laptop finds its already stored identity and acknowledges 42 without another displayed bubble.

Bob's phone remains disconnected. A laptop receipt never establishes phone delivery. Decide whether the user-facing delivered badge means at least one authorized device or every required device, and retain the evidence matching that policy. A read receipt is another authenticated application event under user privacy settings, not a WebSocket control frame or proof that a person understood the content.

Receipts may arrive out of order. Advance a contiguous device-delivery cursor only after all required prior items are applied or explicitly accounted for; receiving 44 never proves 43 was received. Reading history can hold a different cursor contract because the UI may legitimately jump to newer content. Validate receipt scope, membership, and upper bounds; an arbitrary client cannot advance another user's cursor. Store monotonic progress atomically so a delayed receipt cannot move it backwards.

## Reconnect uses retained changes, not a destructive offline pop

Each device retains its applied cursor durably. After reconnect and authentication, request the missing range, apply it idempotently to local storage, then advance the cursor. Popping a Redis list before socket delivery creates a crash/loss gap. A local client queue retains unsent commands until durable service acceptance, using the same operation ID on reconnect.

A history sequence tracks new messages, but edits, deletion, and reaction changes can occur on older sequences. Reconnect therefore needs a retained **change stream** or versioned delta cursor in addition to the original-message cursor. Pair snapshots with their change watermark. If retention removed required changes, return a resynchronization response and a fresh authorized snapshot; never silently claim complete replay.

Subscription and history operations recheck authority on reconnect. A removed group member must never receive a fresh page through a stale cache or restored socket room. Previously downloaded content may remain on an offline device; distinguish server-side revocation from deletion guarantees on someone else's device.

## Large groups change fan-out and receipt costs

Store one ordered message history per conversation, then deliver pointers or ciphertext to currently eligible devices. Large groups can fetch from a shared log rather than persisting a full message copy per recipient. Small groups may benefit from inbox fan-out for quick navigation; measure active-reader ratio, write amplification, and retention before choosing.

For a 10,000-member group, one post can require tens of thousands of device deliveries and receipt updates. Bound subscriber queues, page membership enumeration, and shard delivery tasks. Persist task progress and deduplicate by message/device identity. Never serialize all recipient network writes behind the sender's acceptance response.

Per-member read positions are usually more compact than a full read row per message/member pair. Product policy can show aggregate counts or a bounded participant list instead of rendering 10,000 receipts. A very hot conversation's serialization point remains a limit; changing the contract to thread/subchannel order may help, but it is no longer one total conversation order.

## Presence and typing are disposable hints

Route by `(user, device, connection_generation)` with heartbeat expiry. Cleanup compares the generation before removing a mapping. Online presence aggregates valid devices across gateways, so one device closing never marks the user offline. Gateway death makes entries expire; a heartbeat is recent evidence, not a guarantee the next send will arrive.

Bound and coalesce typing events, expire them, and authorize membership before broadcasting. A cache-key existence check cannot distinguish stored `offline` state from online state. Avoid scanning all Redis keys for typing on every request; retain bounded conversation-local membership. Privacy controls govern who can see presence and last-seen time.

Presence never decides whether to retain a message. Push notifications are best-effort wake-up hints under consent/device-token policy. Provider acceptance never proves device delivery. Suppress sensitive previews for the chosen encryption/privacy contract and reconcile invalid tokens without affecting durable chat history.

## Edits, deletions, reactions and search retain authority

An edit holds a message owner, allowed window, and expected version. Atomically update the current version and append a change; reject stale concurrent edits or provide an explicit merge policy. A deletion writes a monotonic tombstone and revokes future content/media access under policy; a delayed original event must never resurrect it.

Replies retain a conversation-scoped reference and handle deleted targets. Reactions use a unique scoped `(message, user, reaction)` identity or a defined single-reaction rule, with idempotent add/remove commands. Never trust a caller-supplied reaction array containing other users' identities.

A plaintext searchable deployment indexes committed authorized content as a derived view. Recheck current access and deletion before returning hits, snippets, and attachments; a stale conversation-ID list is insufficient. Versioned index events prevent older edits from overwriting newer state. An E2EE deployment keeps plaintext search on authorized clients under its separate device/history contract.

Attachments start as scoped private uploads. Verify ownership, permitted size/type, checksum, and processing readiness before publication. Ready immutable variants still need authorized retrieval and retention. The [notification](30.2.2.07-notification-service.md) and [file-sync](30.2.2.18-dropbox.md) cases own detailed provider and change-cursor mechanisms.

## Prove recovery at the failure boundary

A design is incomplete until a test crosses the crash point that could violate its contract. Assert durable state after retry or recovery, not only the immediate HTTP or socket response.

| Failure boundary | Required behavior | Focused test |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reply lost after message commit | Resolve the same scoped operation ID; do not allocate another message. | Commit a send, drop its response, retry the same command, then assert one history item, one sequence and the original acceptance result. |
| Gateway crashes | Reconnect elsewhere, renew authority and resume retained changes. Sticky routing is an optimization, not recovery. | Accept a message, terminate the gateway before live delivery, reconnect through another gateway and verify cursor replay has no gap or duplicate. |
| Routing cache unavailable | Preserve accepted history; bound delivery/rebuild work and expose delay. | Disable the routing cache, accept a message and read history; confirm acceptance survives and delivery backlog stays bounded and observable. |
| Slow device | Bound its queue, disconnect/resync under policy; retain durable cursor recovery. | Stop one device's acknowledgments while another remains online; verify the healthy device progresses and the slow device catches up from its cursor. |
| Conversation owner fails | Fence old writers, recover committed sequence and command state, then promote. | Crash after commit but before reply; verify the new owner returns the accepted result and a fenced old owner cannot allocate a competing sequence. |
| Search index delayed | Report lag or use a documented authorized fallback; history acceptance remains separate. | Delay an edit or deletion event; verify search does not expose content that current authorization or deletion policy disallows. |

Measure acceptance latency, device-delivery latency for online eligible devices, replay age/gaps, duplicate commands, outbox lag, revocation delay, connection churn, queue bytes, and authorization failures. Regional proximity never justifies independent conflicting writers; select explicit ownership and replication/recovery objectives. Validate actual failover timing instead of promising a universal thirty seconds. These tests establish recovery behavior at their tested boundaries, not production throughput or the security of an encryption protocol.

## Summary

Chat keeps durable conversation history separate from online routing and device evidence. Stable command identities prevent duplicate acceptance, conversation sequences define order, and retained change cursors recover offline devices. Membership, versioned edits, encryption policy and bounded group fan-out remain explicit authority boundaries even when cached delivery is fast.

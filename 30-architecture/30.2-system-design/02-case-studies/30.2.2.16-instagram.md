# Instagram System Design

An upload can finish while its thumbnail job fails, and a follower's cached feed can still point to a post after the author changes its visibility. The system must answer three different questions: did the bytes arrive, is the post ready to publish, and may this viewer see it now? Keeping those decisions separate prevents broken posts and stale-feed leaks:

```text
bytes arrived ≠ post ready ≠ viewer may see it. Three separate decisions.
```

## Definition

A **photo-sharing service** stores users' media and social relationships, then builds a visible, **ranked feed** from those sources. A cached feed is a shortlist of post IDs; it must still respect current privacy, blocking, and deletion when displayed.

> **Textbook Definition:** A photo-sharing service combines a media-processing pipeline with a social graph and ranked feeds, enforcing visibility and deletion across both metadata and distributed media copies.

This is a proposed interview design, not a description of Instagram's current internal architecture. The traffic and service targets below are exercise assumptions.

## First Principles

1. An upload acknowledgment proves that bytes reached storage. It never proves that the object belongs to the caller, matches its declared size, decodes safely, or holds the renditions required for display. Publish only after those checks pass.
2. A feed cache is a list of candidates, not an authorization grant. Follows, blocks, visibility, and deletion can change after that list is written, so the read path must check current policy before returning post data or signing a media URL.
3. A post belongs to one author but may appear in many feeds. Pushing each post to every follower makes writes expensive for high-follower accounts; merging all followed authors on every read makes reads expensive. A hybrid chooses between those paths from measured fan-out cost. Likes and comments hold authoritative unique records; displayed totals are rebuildable projections.

## Product contract and scope

The core exercise covers upload and publication, follow relationships, a paginated home feed, likes, and comments. A story may be modeled as a post with a 24-hour expiry policy. The active follow edge represents an approved relationship; a private-account follow-request workflow is outside this design.

Ranking starts with a bounded candidate set, then applies product policy; recency and engagement are reasonable interview signals, not a universal ranking formula. A production recommendation system is a separate component. Explore, search, notifications, and direct messages consume derived events or use their own designs; they never block the core publish path. See Meta's [multi-stage ranking discussion](https://engineering.fb.com/2025/05/21/production-engineering/journey-to-1000-models-scaling-instagrams-recommendation-system/) for a production example, not a specification for this design.

Treat all numbers below as interviewer-provided targets for this exercise. Replace them when the prompt supplies different constraints.

| Contract | Exercise target |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scale | 2 billion monthly active users, 500 million daily active users, 100 million media objects uploaded per day and 50 billion retained source objects. |
| Feed | p99 page latency below 300 ms in the selected serving region; 99.99% read availability at the stated load. |
| Publication | 99.9% post-creation API availability; success means a durable commit after media is ready. The author sees the committed post immediately through an own-post overlay while follower feeds catch up within 1–5 minutes. |
| Correctness | A post and like are unique under retry; displayed counts may lag, but must be rebuildable from authoritative records. |
| Access | Current visibility, block and deletion policy applies to feed hydration and media retrieval; define retention and deletion evidence for the target market. |

## Capacity Estimation

Assume decimal units, 200 KB per source object, three source copies, 20 feed loads per daily user, 20 thumbnails at 50 KB each, 2 KB of metadata per object, and 100 KB of recent candidate IDs per active user. These assumptions exclude rendition growth, database indexes, and most runtime overhead; measure those separately.

| Estimate | Calculation | Result |
| ------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------- |
| Average uploads | 100 million / 86,400 seconds | ≈1,157 objects/s; at an assumed 3× peak, ≈3,472/s |
| Source storage | 50 billion × 200 KB | 10 PB raw; 30 PB for three copies |
| Recent source objects | 100 million/day × 30 days × 200 KB | 600 TB raw; the remaining 47 billion objects are 9.4 PB raw |
| Feed reads | 500 million × 20/day / 86,400 | ≈115,741 page requests/s average; ≈347,222 at 3× peak |
| Thumbnail payload | 20 × 50 KB per page | 1 MB/page; ≈116 GB/s average client/CDN delivery, before protocol overhead |
| Metadata | 50 billion × 2 KB | 100 TB raw under the assumed row size, before indexes and replicas |
| Candidate cache | 500 million × 100 KB | 50 TB before Redis overhead and replication |

The write path receives about 20 TB/day, or 231 MB/s, at the assumed source-object size. Feed bandwidth is mostly a delivery/CDN question; it is not the same as origin bandwidth. Use the arithmetic to identify likely bottlenecks, then validate peak shape, cache hit rate, video size distribution, and replication cost with measured workloads.

## System boundary

Keep the upload and feed paths distinct. Media bytes go directly to a scoped object-store target; feed reads return authorized metadata and a separate media grant:

```text
Publish: client -> API -> PostgreSQL [consume ready upload + post + outbox]
             |                                  |
             +-> scoped upload -> private object store -> media workers
                                                      -> immutable renditions
Outbox relay -> event log -> feed fan-out / counters / search / notifications

Read: client -> feed API -> cached IDs + pull-side author posts -> hydrate
                       -> current access check -> response + media grant
                       -> CDN -> authorized object origin
```

The CDN never turns a cached candidate into permission: check current access before returning post metadata or issuing a media grant.

## API Design

```yaml
# Request a short-lived upload target. The server chooses the object key.
POST /v1/media/upload-intents
  Headers: Authorization: Bearer <token>, Idempotency-Key: <uuid>
  Body: { "content_type": "image/jpeg", "size_bytes": 2048000, "checksum": "sha256:..." }
  Response: 201 {
    "upload_id": "upl_abc123",
    "upload_target": "https://storage.example.com/scoped-short-lived-target",
    "expires_at": "<UTC timestamp>",
    "status": "uploading"
  }
  Idempotency: same owner/key/fingerprint returns the same intent; changed input returns 409.

# Upload bytes to the scoped target, then ask the service to verify the transfer.
PUT {upload_target}
  Body: binary media bytes

POST /v1/media/upload-intents/upl_abc123/complete
  Headers: Authorization: Bearer <token>
  Response: 202 { "upload_id": "upl_abc123", "status": "processing" }

# Poll or subscribe until validation and rendition generation finish.
GET /v1/media/uploads/upl_abc123
  Response: 200 { "upload_id": "upl_abc123", "status": "ready" }

# Publish only a ready upload. Reusing this key with a different request is a conflict.
POST /v1/posts
  Headers: Authorization: Bearer <token>, Idempotency-Key: <uuid>
  Body: { "upload_id": "upl_abc123", "caption": "Sunset", "visibility": "followers" }
  Response: 201 { "post_id": "post_abc123", "status": "published", "created_at": "<UTC timestamp>" }
  Idempotency: scope key by owner; same fingerprint returns the original post, a different fingerprint returns 409.

# Home feed
GET /v1/feed?cursor=...&limit=20
  The opaque cursor binds ordering and ranking-policy version; the server enforces a maximum page size.
  Response:
    {
      "items": [
        {
          "post_id": "post_abc123",
          "user": { "id": "u_42", "username": "alice", "avatar": "..." },
          "media_url": "authorized delivery URL or short-lived signed URL",
          "caption": "Sunset ",
          "likes": 1234,
          "liked_by_me": true,
          "comments_count": 12,
          "created_at": "<UTC timestamp>"
        }
      ],
      "next_cursor": "..."
    }

# Like
POST /v1/posts/{post_id}/likes
  Response: 204
  Idempotency: the unique (user, post) relation makes repeats a no-op; emit an event only on insertion.
  Note: the unique like relation is authoritative; the displayed count may lag.

# Unlike
DELETE /v1/posts/{post_id}/likes
  Response: 204
  Idempotency: repeat deletion is a no-op; emit an event only when a relation is removed.

# Comment
POST /v1/posts/{post_id}/comments
  Headers: Authorization: Bearer <token>, Idempotency-Key: <uuid>
  Body: { "body": "A useful explanation" }
  Response: 201 { "comment_id": "cmt_abc123" }
  Idempotency: scope by owner and post; same key/fingerprint returns the original comment, changed input returns 409.

# Follow
POST /v1/users/{user_id}/follow
  Response: 204
  Idempotency: the unique follower/followee relation makes retries safe; emit only on a state change.

DELETE /v1/users/{user_id}/follow
  Response: 204
  Idempotency: deleting an absent relation is a no-op; emit only when a relation is removed.
```

## Database Design

### Schema (single PostgreSQL teaching model)

This DDL makes the ownership and uniqueness rules concrete on one relational authority. At very large scale, physical shards may not support these cross-table constraints globally; preserve the same invariants by including the owner/shard key in relationships and routing each command to the authority that can enforce them:

```sql
-- Users
CREATE TABLE users (
    user_id BIGINT PRIMARY KEY,
    username VARCHAR(30) UNIQUE NOT NULL,
    display_name VARCHAR(100),
    avatar_url TEXT,
    follower_count BIGINT NOT NULL DEFAULT 0 CHECK (follower_count >= 0), -- derived
    following_count BIGINT NOT NULL DEFAULT 0 CHECK (following_count >= 0), -- derived
    post_count BIGINT NOT NULL DEFAULT 0 CHECK (post_count >= 0), -- derived
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- One upload intent belongs to one owner and one server-chosen object key.
CREATE TABLE media_uploads (
    upload_id UUID PRIMARY KEY,
    owner_id BIGINT NOT NULL REFERENCES users(user_id),
    request_operation_id UUID NOT NULL,
    request_fingerprint BYTEA NOT NULL CHECK (octet_length(request_fingerprint) = 32),
    object_key TEXT NOT NULL UNIQUE,
    declared_content_type TEXT NOT NULL,
    validated_content_type TEXT,
    status TEXT NOT NULL CHECK (status IN (
        'issued', 'uploaded', 'processing', 'ready', 'consumed', 'failed', 'expired'
    )),
    expected_size_bytes BIGINT NOT NULL CHECK (expected_size_bytes > 0),
    verified_size_bytes BIGINT CHECK (verified_size_bytes >= 0),
    expected_sha256 BYTEA NOT NULL CHECK (octet_length(expected_sha256) = 32),
    verified_sha256 BYTEA CHECK (verified_sha256 IS NULL OR octet_length(verified_sha256) = 32),
    processing_generation INTEGER NOT NULL DEFAULT 0 CHECK (processing_generation >= 0),
    processing_lease_until TIMESTAMPTZ,
    expires_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (expires_at > created_at),
    CHECK ((status = 'processing') = (processing_lease_until IS NOT NULL)),
    CHECK (status NOT IN ('ready', 'consumed') OR (
        verified_size_bytes IS NOT NULL AND verified_sha256 IS NOT NULL
        AND validated_content_type IS NOT NULL
        AND verified_size_bytes = expected_size_bytes
        AND verified_sha256 = expected_sha256
    )),
    UNIQUE (upload_id, owner_id),
    UNIQUE (owner_id, request_operation_id)
);

-- The upload's object key points to immutable validated bytes, not an access grant.
CREATE TABLE posts (
    post_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(user_id),
    media_upload_id UUID NOT NULL UNIQUE,
    create_operation_id UUID NOT NULL,
    request_fingerprint BYTEA NOT NULL CHECK (octet_length(request_fingerprint) = 32),
    rendition_manifest JSONB NOT NULL,
    media_type TEXT NOT NULL CHECK (media_type IN ('photo', 'video', 'story')),
    visibility TEXT NOT NULL CHECK (visibility IN ('public', 'followers', 'private')),
    caption TEXT,
    location_id BIGINT,
    like_count BIGINT NOT NULL DEFAULT 0 CHECK (like_count >= 0), -- derived, eventually consistent
    comment_count BIGINT NOT NULL DEFAULT 0 CHECK (comment_count >= 0), -- derived, eventually consistent
    view_count BIGINT NOT NULL DEFAULT 0 CHECK (view_count >= 0), -- derived, eventually consistent
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at TIMESTAMPTZ,
    deleted_at TIMESTAMPTZ,
    UNIQUE (user_id, create_operation_id),
    FOREIGN KEY (media_upload_id, user_id)
        REFERENCES media_uploads(upload_id, owner_id),
    CHECK ((media_type = 'story') = (expires_at IS NOT NULL)),
    CHECK (expires_at IS NULL OR expires_at = created_at + INTERVAL '24 hours')
);
CREATE INDEX idx_user_created ON posts(user_id, created_at DESC, post_id DESC);
CREATE INDEX idx_live_story_expiry ON posts(expires_at)
    WHERE media_type = 'story' AND deleted_at IS NULL;

-- Follows; one canonical relationship per pair
CREATE TABLE follows (
    follower_id BIGINT NOT NULL REFERENCES users(user_id),
    followee_id BIGINT NOT NULL REFERENCES users(user_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (follower_id, followee_id),
    CHECK (follower_id <> followee_id)
);
CREATE INDEX idx_follows_followee ON follows(followee_id, follower_id);

-- Block checks are part of current visibility authorization.
CREATE TABLE user_blocks (
    blocker_id BIGINT NOT NULL REFERENCES users(user_id),
    blocked_id BIGINT NOT NULL REFERENCES users(user_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (blocker_id, blocked_id),
    CHECK (blocker_id <> blocked_id)
);
CREATE INDEX idx_blocks_reverse ON user_blocks(blocked_id, blocker_id);

-- Likes; unique user/post pair makes retries duplicate-safe
CREATE TABLE likes (
    user_id BIGINT NOT NULL REFERENCES users(user_id),
    post_id BIGINT NOT NULL REFERENCES posts(post_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (user_id, post_id)
);
CREATE INDEX idx_likes_post ON likes(post_id, user_id);

-- Comments (sharded by post_id)
CREATE TABLE comments (
    comment_id BIGINT PRIMARY KEY,
    post_id BIGINT NOT NULL REFERENCES posts(post_id),
    user_id BIGINT NOT NULL REFERENCES users(user_id),
    client_operation_id UUID NOT NULL,
    request_fingerprint BYTEA NOT NULL CHECK (octet_length(request_fingerprint) = 32),
    body TEXT NOT NULL,
    parent_comment_id BIGINT,
    like_count BIGINT NOT NULL DEFAULT 0 CHECK (like_count >= 0), -- derived
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (post_id, comment_id),
    UNIQUE (post_id, user_id, client_operation_id),
    FOREIGN KEY (post_id, parent_comment_id)
        REFERENCES comments(post_id, comment_id)
);
CREATE INDEX idx_comments_post_created ON comments(post_id, created_at, comment_id);

-- Insert this event in the same transaction as the post or relationship change.
CREATE TABLE outbox_events (
    event_id UUID PRIMARY KEY,
    aggregate_type TEXT NOT NULL,
    aggregate_key TEXT NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    published_at TIMESTAMPTZ
);
CREATE INDEX idx_outbox_unpublished ON outbox_events(created_at, event_id)
    WHERE published_at IS NULL;
```

## Follow the publish and read paths

The schema is a single-authority teaching model. A sharded deployment must route each command to an authority that can enforce the same uniqueness rules.

### Validate media before publication

An upload intent binds the owner to a server-chosen object key, expected size, checksum, permitted type, and expiry. The client uploads directly to that scoped target. Completion verifies the stored object, then records `processing` plus a generation and lease. A bounded worker decodes the bytes, validates the actual format, strips sensitive metadata when policy requires it, and writes immutable renditions. Only after every required rendition exists may the same generation mark the upload `ready`.

Technical readiness is not content approval. If the product requires moderation or abuse review, publication must also wait for that policy decision; a file decoding successfully is no moderation result.

The state path is `issued → uploaded → processing → ready → consumed`, with failure and expiry terminal for that intent. Provider acceptance is not validation. A stale worker may finish writing objects, but its generation check must prevent it from publishing after a newer worker has reclaimed the lease. Delete abandoned temporary objects after expiry. Meta's [video-processing example](https://engineering.fb.com/2025/11/17/ios/enhancing-hdr-on-instagram-for-ios-with-dolby-vision/) describes distinct client, server, and playback stages; it is an implementation example, not a required architecture.

Claim a processing lease with a fencing generation:

```sql
UPDATE media_uploads
SET status = 'processing',
    processing_generation = processing_generation + 1,
    processing_lease_until = clock_timestamp() + INTERVAL '2 minutes'
WHERE upload_id = $1
  AND expires_at > clock_timestamp()
  AND (status = 'uploaded'
       OR (status = 'processing' AND processing_lease_until < clock_timestamp()))
RETURNING processing_generation;
```

After verifying the immutable renditions, mark the upload `ready` only where the upload ID and claimed generation still match; require verified size and checksum to match the intent. Publish only if that update affects one row. Post creation then consumes the ready upload and writes the post, idempotency result, and outbox event in one transaction. The relay may deliver events more than once, so projections deduplicate stable event IDs; a broker never makes external side effects exactly once.

### Build a feed without coupling it to post acceptance

The post transaction commits before follower-feed work begins. Its outbox relay emits `post.published`; a worker handles that event idempotently. For an author whose measured follower fan-out fits the write budget, push the post ID into follower candidate lists. For an author whose fan-out exceeds that budget, keep recent authored posts and merge them at read time. There is no universal follower-count threshold: measure write amplification, active followers, and read cost. During a strategy change, use a watermark and deduplicate both paths so a post is neither skipped nor repeated:

```text
Publish: ready upload + post + outbox commit -> idempotent relay -> fan-out worker
Read: bounded pushed candidates + pull-side authors -> deduplicate -> hydrate
      -> current visibility/block/expiry/deletion check -> rank -> stable page
```

The reader merges bounded candidates from both paths, hydrates post metadata, rechecks current authorization, then ranks eligible results. Fetch another bounded batch when filtering removes too many candidates; if the budget is exhausted, return a shorter page rather than scanning without limit. The creator sees a committed post immediately through an own-post overlay while follower projections catch up. Production ranking models remain separate from this feed-storage design.

The opaque cursor carries a stable ordering tuple and the feed/ranking snapshot version. Define whether posts arriving after a page session begins appear only after refresh; a changing score cannot by itself define a stable next page. Recheck current visibility on every page. The [Twitter feed case](30.2.2.12-twitter-feed.md) develops timeline pagination and push/pull mechanics further.

## Keep caches and events disposable

| Derived view | Canonical source | Recovery and access rule |
| ---------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Feed candidate IDs | Posts plus follow graph | Rebuild or refill from bounded queries; recheck current visibility after every cache hit. |
| Post metadata cache | Canonical post row | Version or invalidate edits/deletions; cache presence never grants read access. |
| Like/comment totals | Unique relationship rows | Deduplicate stable events and reconcile projections from canonical relations. |
| CDN renditions | Immutable validated objects | Public objects may be cached long; private grants are bearer credentials until expiry. |

Write the post or relationship and its outbox event in the same database transaction. The relay publishes committed events such as `post.published`, `follow.changed`, `like.added`, `like.removed`, `comment.added`, and `media.processing.requested`. Create interaction events only when the authoritative relation actually changes. Consumers use stable event IDs, tolerate redelivery, and can rebuild from durable source records. Kafka is one possible event log when measured throughput and replay needs justify its operational cost; choosing Kafka alone never defines durability, ordering, or consumer idempotency. AWS's [transactional outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) explains the dual-write failure this boundary prevents.

## Scale by the resource that is hot

| Pressure | Starting decision | Cost or boundary |
| ------------------------------------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| High-follower author | Pull-merge recent authored posts at read time. | More read work; bound and cache the per-author query. |
| Large feed cache | Shard candidate lists by viewer and cap each list. | Inactive users may need a bounded refill on return. |
| Slow media processing | Bound workers and prioritize required renditions. | Less-used variants can be generated later if the product contract permits it. |
| Hot post interactions | Keep unique like/comment rows canonical; aggregate stable events into sharded counters. | Displayed counts lag and must be reconciled. |
| Search rebuild | Build a versioned index, replay changes, verify, then switch. | Search remains a derived view and must recheck current access. |
| Regional failure | Define the write owner, replicas and failover fencing per data class. | Failover objectives depend on what was replicated; never promise copies that do not exist. |

Stories expire at read time when their deadline passes; cleanup is asynchronous and never defines access. Feed, search, metadata, and media authorization must all reject expired stories. Never issue a media grant whose expiry outlasts the story; a grant already issued remains usable until expiry unless the origin checks authorization on each request. Soft deletion first blocks new access in authoritative reads, then a retry-safe outbox event removes feed candidates, search records, and renditions. A presigned object URL is a bearer credential until expiry, as [S3's documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) describes; use short grants or an authorization-aware origin when faster revocation is required. Purge CDN objects, define browser-cache and backup retention separately, and record deletion evidence. No server-side deletion can retract media already downloaded to another device.

## Test the failures that can break the contract

| Failure boundary | Required result | Focused test |
| -------------------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Upload worker is retried | Only the current generation may publish `ready`. | Let a worker lease expire, reclaim with a new generation, then assert the old worker's ready update affects zero rows. |
| Post commit succeeds but response is lost | Retry returns the same post and event identity. | Drop the response after commit; retry the same owner/key/fingerprint and assert one post, one consumed upload and one logical outbox event. |
| Event broker is unavailable | Accepted posts remain durable and projections catch up later. | Stop the relay/broker, publish within the configured backlog budget, restore it and assert idempotent replay with no lost post. |
| Feed cache is unavailable | Reads use a bounded fallback or fail predictably without stampeding storage. | Disable Redis under load and assert database concurrency stays within the admission limit. |
| Visibility or deletion changes after caching | No newly authorized response exposes protected post data. | Cache a candidate, block or delete the post, then check feed hydration and media retrieval both deny it. |
| Like event is delivered twice | The unique relationship and projected total do not double-count. | Replay the same event ID and assert one like row and one logical counter increment. |
| Story expires while still cached | Expired content and fresh media grants are denied. | Keep its ID in the feed cache past expiry; assert feed hydration and media authorization both deny it and any prior grant expires within the policy window. |

Measure feed and upload latency against the agreed SLOs, upload-to-ready time, fan-out lag, replay gaps, outbox age, projection drift, cache fallback rate, authorization denials, storage growth, and shard skew. Alert thresholds should follow the service's error budget and backlog capacity rather than arbitrary global defaults.

## Summary

Validate media before consuming it into a post, then commit the post with an outbox event. Use a hybrid feed for write/read skew, but treat cached IDs and counters as rebuildable projections. Stable pagination, current authorization and retry-safe deletion preserve the contract when relationships or media change.

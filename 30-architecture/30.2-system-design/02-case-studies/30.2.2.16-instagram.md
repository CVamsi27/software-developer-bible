# Instagram System Design

## Definition

A photo-sharing service stores users' media and social relationships, then builds a visible, ranked feed from those sources. A cached feed is a shortlist of post IDs; it must still respect current privacy, blocking and deletion when displayed.

> **Textbook Definition:** A photo-sharing service combines a media-processing pipeline with a social graph and ranked feeds, enforcing visibility and deletion across both metadata and distributed media copies.

This is a proposed interview design. Product limits and traffic figures below are exercise assumptions, not verified current Instagram facts.

## First Principles

A large media upload can finish before its contents are safe or ready to display. Separate upload acceptance, validated processing and publication, so a broken thumbnail or rejected object does not become a public post.

A post belongs to an author, but its feed copies belong to many viewers. Creating every copy eagerly makes posting expensive for high-follower accounts; merging everything at read time makes each feed expensive. A hybrid policy trades those costs using measured follower activity and posting frequency.

Privacy changes faster than some distributed copies. Therefore a cached ID cannot prove that a viewer may see a post. Current visibility and deletion checks must survive hydration, search and media delivery, including cache hits.

## Requirements

### Functional Requirements

- Users can upload photos and short videos (with a chosen duration limit for this exercise)
- Follow / unfollow other users
- Home feed: see posts from people you follow, ranked by recency + engagement
- Like and comment on posts
- Stories (24-hour ephemeral content)
- Explore tab: discovery of new content based on interests
- Direct messages (out of scope — see chat-system design)
- Search by username, hashtag, location
- Notifications for likes, comments, follows, mentions

### Non-Functional Requirements

- 2 B+ monthly active users
- 100 M photos/videos uploaded per day
- 50 B+ photos stored
- Feed-load latency below 300 ms at p99
- 99.99% availability for reads; 99.9% for writes
- Read-your-writes for the user posting (they should see their own post immediately)
- Eventual consistency for everyone else (1–5 min skew is acceptable)
- Authoritative unique likes/comments; displayed aggregate counts may be eventually consistent
- Define deletion, retention and access policies; implementation alone does not establish legal compliance

## Capacity Estimation

```text
User & Media:
- 2B MAU, 500M DAU
- 100M media uploads/day = ~1,160 uploads/sec average, ~3,500 peak
- 50B photos × 200 KB avg = 10 PB raw storage
- 3 replicas: 30 PB total

Feed Read Path:
- 500M DAU × 20 feed loads/day = 10B feed reads/day
- 10B / 86,400 ≈115,741 reads/sec average, ≈347,222 at 3× peak
- Each feed load: 20 posts × 50 KB (thumbnails) = 1 MB payload

Storage Mix:
- Hot (last 30 days) in object storage, delivered through a CDN: 100M × 30 × 200 KB = 600 TB of source objects
- Cold (the other 47B of the 50B total) in a lower-cost object-storage tier: 47B × 200 KB = 9.4 PB raw
- Metadata (PostgreSQL sharded): 50B rows × 2 KB = 100 TB
- Feed cache (Redis): 500M users × 100 KB of recent posts = 50 TB

Bandwidth:
- Write: 1,160 × 200 KB = 230 MB/s
- Read: ≈115,741 ×1 MB ≈116 GB/s average payload demand; CDN hit rate determines origin demand

```

## Database Design

### Schema (single PostgreSQL teaching model)

This DDL makes the ownership and uniqueness rules concrete on one relational authority. At very large scale, physical shards may not support these cross-table constraints globally; preserve the same invariants by including the owner/shard key in relationships and routing each command to the authority that can enforce them.

```sql
-- Users
CREATE TABLE users (
    user_id BIGINT PRIMARY KEY,
    username VARCHAR(30) UNIQUE NOT NULL,
    display_name VARCHAR(100),
    avatar_url TEXT,
    follower_count BIGINT NOT NULL DEFAULT 0 CHECK (follower_count >= 0), -- derived
    following_count BIGINT NOT NULL DEFAULT 0 CHECK (following_count >= 0), -- derived
    post_count BIGINT NOT NULL DEFAULT 0 CHECK (post_count >= 0), -- derived
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- One upload intent belongs to one owner and one server-chosen object key.
CREATE TABLE media_uploads (
    upload_id UUID PRIMARY KEY,
    owner_id BIGINT NOT NULL REFERENCES users(user_id),
    request_operation_id UUID NOT NULL,
    request_fingerprint BYTEA NOT NULL CHECK (octet_length(request_fingerprint) = 32),
    object_key TEXT NOT NULL UNIQUE,
    declared_content_type TEXT NOT NULL,
    validated_content_type TEXT,
    status TEXT NOT NULL CHECK (status IN (
        'issued', 'uploaded', 'processing', 'ready', 'consumed', 'failed', 'expired'
    )),
    expected_size_bytes BIGINT NOT NULL CHECK (expected_size_bytes > 0),
    verified_size_bytes BIGINT CHECK (verified_size_bytes >= 0),
    expected_sha256 BYTEA NOT NULL CHECK (octet_length(expected_sha256) = 32),
    verified_sha256 BYTEA CHECK (verified_sha256 IS NULL OR octet_length(verified_sha256) = 32),
    processing_generation INTEGER NOT NULL DEFAULT 0 CHECK (processing_generation >= 0),
    processing_lease_until TIMESTAMPTZ,
    expires_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (expires_at > created_at),
    CHECK ((status = 'processing') = (processing_lease_until IS NOT NULL)),
    CHECK (status NOT IN ('ready', 'consumed') OR (
        verified_size_bytes IS NOT NULL AND verified_sha256 IS NOT NULL
        AND validated_content_type IS NOT NULL
        AND verified_size_bytes = expected_size_bytes
        AND verified_sha256 = expected_sha256
    )),
    UNIQUE (upload_id, owner_id),
    UNIQUE (owner_id, request_operation_id)
);

-- The upload's object key points to immutable validated bytes, not an access grant.
CREATE TABLE posts (
    post_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(user_id),
    media_upload_id UUID NOT NULL UNIQUE,
    create_operation_id UUID NOT NULL,
    request_fingerprint BYTEA NOT NULL CHECK (octet_length(request_fingerprint) = 32),
    rendition_manifest JSONB NOT NULL,
    media_type TEXT NOT NULL CHECK (media_type IN ('photo', 'video', 'reel', 'story')),
    visibility TEXT NOT NULL CHECK (visibility IN ('public', 'followers', 'private')),
    caption TEXT,
    location_id BIGINT,
    like_count BIGINT NOT NULL DEFAULT 0 CHECK (like_count >= 0), -- derived, eventually consistent
    comment_count BIGINT NOT NULL DEFAULT 0 CHECK (comment_count >= 0), -- derived, eventually consistent
    view_count BIGINT NOT NULL DEFAULT 0 CHECK (view_count >= 0), -- derived, eventually consistent
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at TIMESTAMPTZ,
    deleted_at TIMESTAMPTZ,
    UNIQUE (user_id, create_operation_id),
    FOREIGN KEY (media_upload_id, user_id)
        REFERENCES media_uploads(upload_id, owner_id),
    CHECK ((media_type = 'story') = (expires_at IS NOT NULL)),
    CHECK (expires_at IS NULL OR expires_at = created_at + INTERVAL '24 hours')
);
CREATE INDEX idx_user_created ON posts(user_id, created_at DESC, post_id DESC);
CREATE INDEX idx_live_story_expiry ON posts(expires_at)
    WHERE media_type = 'story' AND deleted_at IS NULL;

-- Follows; one canonical relationship per pair
CREATE TABLE follows (
    follower_id BIGINT NOT NULL REFERENCES users(user_id),
    followee_id BIGINT NOT NULL REFERENCES users(user_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (follower_id, followee_id),
    CHECK (follower_id <> followee_id)
);
CREATE INDEX idx_follows_followee ON follows(followee_id, follower_id);

-- Likes; unique user/post pair makes retries duplicate-safe
CREATE TABLE likes (
    user_id BIGINT NOT NULL REFERENCES users(user_id),
    post_id BIGINT NOT NULL REFERENCES posts(post_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (user_id, post_id)
);
CREATE INDEX idx_likes_post ON likes(post_id, user_id);

-- Feed cache (separate Redis cluster, not SQL)

-- Comments (sharded by post_id)
CREATE TABLE comments (
    comment_id BIGINT PRIMARY KEY,
    post_id BIGINT NOT NULL REFERENCES posts(post_id),
    user_id BIGINT NOT NULL REFERENCES users(user_id),
    body TEXT NOT NULL,
    parent_comment_id BIGINT,
    like_count BIGINT NOT NULL DEFAULT 0 CHECK (like_count >= 0), -- derived
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (post_id, comment_id),
    FOREIGN KEY (post_id, parent_comment_id)
        REFERENCES comments(post_id, comment_id)
);
CREATE INDEX idx_comments_post_created ON comments(post_id, created_at, comment_id);

-- Insert this event in the same transaction as the post or relationship change.
CREATE TABLE outbox_events (
    event_id UUID PRIMARY KEY,
    aggregate_type TEXT NOT NULL,
    aggregate_key TEXT NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    published_at TIMESTAMPTZ
);
CREATE INDEX idx_outbox_unpublished ON outbox_events(created_at, event_id)
    WHERE published_at IS NULL;
```

## Architecture

The diagram groups responsibilities; it does not imply that every request traverses the media CDN or that naming a store establishes its consistency contract.

### ASCII Architecture Diagram

```text
┌────────────────────────────────────────────────────────────────────┐
│ INSTAGRAM-TYPE STACK                                               │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│ Client ── JSON/API ──▶ Load Balancer → API Gateway                 │
│   │                    (auth, rate limits, routing)                │
│   └──── media bytes ─▶ CDN ──▶ authorized media origin             │
│                                                                    │
│ ├──▶ Feed Service ──▶ Redis (candidate post IDs)                   │
│ ├──▶ Post/Graph Services ──▶ PostgreSQL (canonical state)          │
│ ├──▶ Media Service ──▶ object store ──▶ rendition workers          │
│ ├──▶ Like/Comment Service ──▶ unique relationship records          │
│ ├──▶ Transactional outbox ──▶ Kafka ──▶ fan-out/search/notify      │
│ └──▶ Counter projection ──▶ sharded derived-counter buckets        │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

The PostgreSQL model is the teaching authority for unique follows, likes and comments. A production system may partition those records, but it still needs an equivalent uniqueness or conditional-write contract. Kafka events update rebuildable counters and indexes; retries must not create a second relationship or count the same event twice. The CDN serves bytes only after the access policy has authorized the request.

## Key Components

### Media Upload Pipeline

1. An authenticated owner requests an upload intent. The server chooses the object key and records the permitted size/type, expected checksum and expiry. Select a storage upload mechanism that actually enforces its advertised limits.
2. The client uploads to the intent's scoped object target. A provider acknowledgment proves transfer acceptance, not that the media is safe or publishable.
3. Completion verifies owner, object identity, actual size, checksum and storage outcome. Record a processing version and outbox event in the same metadata transaction.
4. A bounded worker decodes under resource limits, validates formats, strips unnecessary sensitive EXIF/location metadata and creates immutable rendition objects. A client MIME label is not validation.
5. Mark the upload ready only after required outputs exist and the processing generation still matches. A retried or superseded worker cannot publish stale outputs. Return processing/failed status until ready; read-your-writes does not require showing unprocessed media.

The lifecycle is `issued → uploaded → processing → ready → consumed`; failure and expiry are terminal states for that upload intent. The service owns each transition, binds the intent to its owner and server-generated object key, and deletes abandoned temporary objects after expiry. Treat the declared MIME type as a hint; the worker validates the bytes and records the detected format. Claim work by incrementing a fencing generation and setting a short lease:

```sql
UPDATE media_uploads
SET status = 'processing',
    processing_generation = processing_generation + 1,
    processing_lease_until = clock_timestamp() + INTERVAL '2 minutes'
WHERE upload_id = $1
  AND expires_at > clock_timestamp()
  AND (status = 'uploaded'
       OR (status = 'processing' AND processing_lease_until < clock_timestamp()))
RETURNING processing_generation;
```

After writing and verifying immutable rendition objects, update `status` to `ready`, clear the lease and store the verified size, checksum and detected format only where both the upload ID and returned generation still match. Require the verified size and checksum to equal the intent's expected values. Publish only if that update affects one row; an expired worker cannot publish after another worker reclaims the upload. Only ready media can be consumed by one post-creation transaction; that transaction changes the upload to consumed and stores the post, its idempotency result and an outbox event together. Consumers may receive events more than once. Use stable event IDs with idempotent writes, durable deduplication or replayable projections; a broker's delivery mode does not make an external side effect exactly once.

### Feed Generation (Hybrid Push/Pull)

- **Push (fan-out on write)**: When an ordinary author posts, we enqueue a fan-out job that pushes the post ID into the feed cache (Redis) of each follower.
- **Pull (for celebrities)**: For sufficiently expensive fan-out authors, do not fan out. Instead, merge at read time by querying the celebrity's recent posts and considering them in the same ranking policy.

```text
Read path:
  1. Read a bounded precomputed candidate page from Redis (for example, up to 500 post IDs)
  2. Hydrate candidates from the post cache or authoritative metadata store
  3. For each followed celebrity, fetch their latest N posts and merge
  4. Recheck current visibility, blocking, expiry and deletion; rank eligible candidates
  5. Return top 20

Write path:
  1. Lock and consume a ready upload; commit its state change, the post and outbox record in one PostgreSQL transaction
  2. Publish committed outbox records as `post.published`; retry delivery safely
  3. Fan-out worker:
     a. If measured fan-out cost is within the push budget → push post ID to each follower's feed cache
     b. If measured fan-out cost exceeds the budget → mark as "celebrity" in their profile; read path merges
  4. Update derived post counters from the committed event; reconcile against canonical post rows
```

## Caching Strategy

| Cache | Stores | TTL | Invalidation |
| ---------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Redis feed cache | `user_id → [post_id, ...]` | 7 days, LRU on overflow | New post event-driven push |
| Memcached post cache | `post_id → post object` | 24 hours | Delete on post update/delete |
| CDN | Authorized media + thumbnails | Long TTL for public immutable objects; short grants for private media | Check access before signing/delivery; bound signed-URL revocation delay and purge deleted objects |
| Local in-process (LRU) | Hottest 1 K posts per app server | 60 s | Time-based |
| Browser cache | Content-hashed UI assets; media follows visibility policy | Long TTL for public immutable assets; private media is non-storable or short-lived | A content hash provides freshness, not authorization or revocation |

## Message Queue

Kafka is one possible event-log choice when its operational costs and retention model fit:

- Measured throughput sufficient for the actual event mix
- Replay for backfill (e.g., when feed ranking model changes, replay `post.published`)
- Multi-consumer (fan-out, search indexer, analytics, notifications)

Topics:
- `post.published` → fan-out, search, notification
- `user.followed` → timeline generation, notification
- `post.liked` → counter update and notification, written to the outbox only when a unique relation is inserted
- `post.commented` → counter update and notification, committed with the canonical comment
- `media.processing.requested` → image pipeline

## Scaling Strategy

| Bottleneck | Solution |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| Hot user (celebrity with 1 B followers) | Pull-side merge instead of push |
| Feed cache too large | Shard by user_id; LRU eviction for inactive users |
| Image processing latency | Parallel pipeline workers; precompute on upload |
| Database write contention on `posts` table | Shard by user_id; consider Cassandra for the timeline side |
| Counter updates (likes) on hot posts | Keep unique like rows authoritative; aggregate stable outbox event IDs into sharded counter buckets |
| Search index rebuild on schema change | Build a versioned index from durable history, catch up changes and verify before switching |

## Failure Handling

| Failure | Mitigation |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Feed cache Redis down | Serve a still-authorized bounded stale page when policy allows; otherwise rebuild with strict query limits and admission control to prevent a database stampede |
| Kafka down | Keep events in the committed metadata outbox; bound backlog and reject/degrade before capacity exhaustion |
| Image pipeline worker dies | Retry the same upload ID and processing generation; publish `ready` only if that generation is still current |
| Celebrity user posts | Detect on write; do NOT push to followers; read-time merge |
| Hot post (1 M likes/sec) | Async counter updates batched; counter reconciled nightly |
| S3 region outage | Planned replication/failover for permitted media; do not promise unavailable copies exist |

## Monitoring

- **Business metrics**: posts/sec, likes/sec, DAU/MAU ratio, feed CTR
- **Latency**: feed load p50/p95/p99, upload acknowledgment, image processing duration
- **Cache hit rate**: feed cache, post cache, CDN cache
- **Queue health**: Kafka consumer lag per topic, DLQ size
- **Storage**: S3 object count, PG row counts, shard skew
- **Errors**: 5xx rate, partial-failure rate from image pipeline

Alerts: warn when feed p99 exceeds the 300 ms target for five minutes and page when it exceeds 1 s; alert on image-pipeline lag above 5 minutes, fan-out lag above 1 minute, or Redis memory above 80%.

## Trade-offs

| Decision | Option A | Option B | Choice |
| ------------------ | ---------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------- |
| Feed generation | Push (write-heavy) | Pull (read-heavy) | Hybrid (push for normal users, pull for celebrities) |
| Counter projection | Update one exact post row on every interaction | Aggregate into replayable, sharded buckets | Keep unique relation records canonical; derive and reconcile counts asynchronously |
| Media metadata | PostgreSQL | DynamoDB | PostgreSQL (joins + transactions needed) |
| Search | Elasticsearch (own infra) | Algolia (managed) | Elasticsearch (cost + control at scale) |
| Direct messages | Dedicated protocol/service | Managed service | Separate design; excluded from this chapter's first scope |
| Story expiry | Scheduled cleanup | Read-time expiry plus cleanup | Enforce expiry at every access path; PostgreSQL has no automatic row TTL |

## Deletion and pagination need visible contracts

Use a stable candidate order with a unique tie-breaker, a bounded cursor and a ranking snapshot/version policy. Deduplicate overlapping pages; a changing relevance score alone is not a stable cursor. The [Twitter feed case](30.2.2.12-twitter-feed.md) owns the full push/pull timeline mechanism.

A story becomes inaccessible when its expiry is reached, even if cleanup has not run. Soft deletion must immediately prevent new authorized access, then drive retry-safe removal from feeds, search and media copies. A signed URL is a bearer grant until expiry; use short lifetimes for private media, or authorization-aware edge/origin checks when revocation must take effect sooner. Purge CDN copies after deletion, define browser-cache and backup retention separately, and record completion evidence. Never promise deletion from recipient copies already downloaded. This policy needs legal review for the intended market rather than a generic compliance label.

## Mistakes

- Publishing metadata before processing completes or trusting a user-provided object key/MIME type.
- Separately committing a post and broker event without recovery.
- Treating hydrated feed or CDN cache hits as authorization.
- Incrementing a like counter for every retry instead of authoritative unique relation changes.
- Claiming PostgreSQL inline INDEX or automatic row TTL behavior.

## Best practices

Test retried upload completion and post creation, stale processing versions, duplicate likes, cross-post comment parents, visibility changes during page requests, revoked media grants and expired stories still present in caches. Reconcile derived counters from authoritative relationships. Bound fan-out, hydration and cache-failure fallback so losing Redis does not overload every database shard. Measure access-policy denials and publication failures separately from feed latency.

## Summary

The media pipeline owns validated publication; the social graph and post state own visibility; feeds and counters are rebuildable derived views. Hybrid fan-out handles skew when guided by measured cost. Stable pagination, current access checks and retry-safe deletion must hold across metadata, search and cached media.

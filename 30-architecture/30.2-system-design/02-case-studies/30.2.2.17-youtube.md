# YouTube System Design

A creator's upload finishes, but the video is not yet playable: validation, transcoding, and manifest publication still lie ahead. Meanwhile a viewer request must never serve a half-written rendition, and a private video's cached segments must never become public. Acceptance, preparation, and authorized delivery are three different states:

```text
upload accepted ≠ playable: verify → transcode → versioned manifest → publish atomically.
```

## Definition

A user-generated video platform accepts **uploads**, prepares **playable versions**, and serves those versions to **authorized viewers**. Its upload, processing, playback, and discovery paths hold different workloads and failure behavior.

> **Textbook Definition:** A user-generated video platform ingests uploads, produces playback representations, and distributes authorized media, coordinating asynchronous processing with discovery, moderation, and delivery.

This is a YouTube-style interview design, not a description of YouTube's current internal architecture. Product limits, traffic, and service targets must come from the exercise or current evidence; the numbers below are explicitly hypothetical.

## First Principles

1. An uploaded file may be incomplete, unsafe, or unsuitable for a viewer's decoder and connection. Preparation takes longer than an ordinary API request, so upload acceptance and playback readiness must be different states. Viewers request many small media pieces; those bytes need a delivery path that never forces every play through application servers.
2. Metadata, access policy, and bytes must also agree. A processing retry must never publish an incomplete manifest, and a private or removed video must never become public because its segments are cached. These constraints derive the asynchronous pipeline, immutable output versions, and authorized delivery boundary.

## Requirements

Clarify accepted formats and maximum size/duration, supported devices, public/unlisted/private visibility, moderation, deletion, and resume behavior. Define whether live streaming, licensed-content protection, search, comments, and recommendations are in scope. Video-on-demand preparation and live ingestion hold different latency/recovery contracts; derive the core design for one before adding the other.

Choose measurable service goals for upload completion, time to playable, playback startup, rebuffering, and authorization changes. **Time to first byte (TTFB)** measures one request's first response bytes; it never measures the time until a video starts playing. Define each metric and workload rather than borrowing an unverified "YouTube bar."

## Separate Control and Media Paths

```text
uploader → upload-session API → authorized multipart parts → raw object
                                                    ↓ verified completion
metadata transaction + durable processing intent → worker queue
    → validated/transcoded outputs → versioned playlists + segments
    → atomic publication of ready-version metadata

viewer → metadata/authorization API → playable manifest reference
viewer → authorized CDN → cached segments or object-store origin

committed metadata/events → search index, discovery and bounded analytics
```

The API controls identity, ownership, and state transitions. The object store retains media bytes. Workers encode a source into compatible **variants** with selected dimensions, bitrates, and codecs. A content delivery network (CDN) caches delivery objects near viewers. A queue coordinates work; it never itself makes database and object-store updates one transaction.

## Trace One Upload into Playback

1. An authenticated creator requests an upload session. The service creates a unique raw-object key and binds the session to owner, quota, expiry, and accepted upload policy.
2. For Amazon S3 multipart upload, initiate the upload, send numbered parts with that upload ID and retain their returned ETags, then explicitly complete the multipart upload. Retrying one failed part need never resend every other part. A generic `Content-Range` request is not S3's multipart protocol.
3. Verify completed object identity, size, and checksum policy. Persist a processing state and durable intent; reconcile completion events because notification delivery can repeat or fail. A final part alone never establishes a completed playable object.
4. A worker validates the media and produces required outputs under a processing-version key. It uses a bounded lease/retry policy and records each variant's identity and completion. Abandoned upload parts and failed outputs need cleanup.
5. A publisher confirms that every required playlist and segment is available, then atomically selects that manifest as the ready version in metadata. Optional expensive variants may finish later if the product permits it. Never advertise a manifest whose referenced files are not ready.
6. A viewer requests metadata and an access decision. The player retrieves the manifest and media through the CDN policy, choosing a compatible variant and changing its bitrate as connection and buffer conditions change.

Suppose worker A prepares version1, but a replacement upload starts version2 before A finishes. A's completion must never mark version2 ready or replace its selected manifest. Compare the source/processing version during publication. A retried job may reuse verified version1 outputs, while partial files remain unpublished. This is stronger than merely giving both jobs the same filename.

## Store State and Bytes with Different Responsibilities

The following PostgreSQL DDL is a focused metadata example. It is not also Cassandra syntax and implements no accounts, search, moderation, or job leasing:

```sql
CREATE TABLE videos (
  video_id uuid PRIMARY KEY,
  owner_id uuid NOT NULL,
  title text NOT NULL CHECK (char_length(title) BETWEEN 1 AND 200),
  tags text[] NOT NULL DEFAULT '{}',
  visibility text NOT NULL CHECK (visibility IN ('public','unlisted','private')),
  status text NOT NULL CHECK (status IN ('uploading','processing','ready','failed','removed')),
  source_version bigint NOT NULL CHECK (source_version > 0),
  ready_version bigint CHECK (ready_version IS NULL OR ready_version > 0),
  manifest_key text,
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK (ready_version IS NULL OR ready_version <= source_version),
  CHECK ((ready_version IS NULL) = (manifest_key IS NULL)),
  CHECK (status <> 'ready' OR (ready_version IS NOT NULL AND ready_version = source_version))
);

CREATE TABLE video_variants (
  video_id uuid NOT NULL REFERENCES videos(video_id),
  source_version bigint NOT NULL CHECK (source_version > 0),
  variant_key text NOT NULL,
  storage_key text NOT NULL,
  PRIMARY KEY (video_id, source_version, variant_key)
);
```

The primary key identifies a video; the variant key identifies one versioned encoding output. The `ready` check prevents one invalid metadata state, but cannot prove object-store files exist. It explicitly tests `ready_version IS NOT NULL` because PostgreSQL accepts a `CHECK` expression evaluating to `NULL`; the [constraint documentation](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS) explains this behavior. The publication service owns the cross-store file check and recovery.

When a replacement upload starts, increment `source_version` and set the processing state. Keep the previous `ready_version` and `manifest_key` only if policy permits viewers to continue watching the old version while the replacement is prepared. The player serves the selected ready manifest, never a partly written output. Initial uploads hold no ready version.

Publication fences the worker against a replacement source:

```sql
UPDATE videos
SET status = 'ready',
    ready_version = source_version,
    manifest_key = $3
WHERE video_id = $1
  AND status = 'processing'
  AND source_version = $2
RETURNING ready_version;
```

Commit this pointer with the publication event only after verifying every required object. Zero returned rows means the source changed or left processing; keep the outputs unreferenced and never publish them. Versioned object keys keep a stale worker from overwriting files selected by a newer manifest.

Keep likes, comments, view events, and search projections out of a single hot video row when their workload warrants separate ownership. A like can need a unique user/video record so repeated requests never inflate the count. A displayed view total can tolerate delayed aggregation, while ad billing or fraud investigation may require different durable evidence. "Never write a record per view" is no universal rule; define retention, sampling, and accuracy for the actual purpose.

## Understand Adaptive Playback Before Listing Protocols

**Adaptive bitrate (ABR)** playback offers several compatible video variants. The player chooses segments per measured throughput, buffer health, and device support. A higher bitrate can improve quality but drain the buffer if downloads cannot keep pace.

In HTTP Live Streaming (HLS), a multivariant playlist (called a master playlist in RFC 8216) lists variant streams whose media playlists point to segments; it can also associate alternate audio and subtitle renditions. MPEG-DASH organizes its MPD as Periods, AdaptationSets, and Representations; a Representation describes one compatible encoding, and segment-addressing elements identify its media pieces. Video variants must support safe switching, such as compatible keyframe and segment boundaries. Merely listing several complete MP4 files never builds an ABR pipeline.

RFC 8216 remains the [published HLS document](https://www.rfc-editor.org/rfc/rfc8216.html). The newer [HLS 2nd Edition draft](https://datatracker.ietf.org/doc/draft-pantos-hls-rfc8216bis/22/) has been sent to the RFC Editor but remains work in progress; verify player and device support before depending on draft-only behavior.

### Produce one local HLS variant

In an empty disposable directory, this FFmpeg command generates six seconds of synthetic video and one video-only 360p HLS variant. It requires an FFmpeg build with `libx264`. It is a packaging demonstration, not a complete multi-variant production encoder:

```bash
ffmpeg -hide_banner -loglevel error \
  -f lavfi -i testsrc=size=640x360:rate=24 -t 6 \
  -c:v libx264 -pix_fmt yuv420p -g 48 -sc_threshold 0 \
  -f hls -hls_time 2 -hls_playlist_type vod \
  -hls_segment_filename '360-%03d.ts' 360.m3u8
```

The 48-frame keyframe interval at 24 frames/second creates two-second boundaries. The output playlist references three segment files and ends with `#EXT-X-ENDLIST`, identifying completed video-on-demand content. Inspect the referenced files before treating the variant as ready. A real pipeline also validates input, audio, timestamps, device compatibility, and multiple aligned outputs; bitrate labels must reflect the generated media.

## Estimate Capacity with Consistent Units

For illustration, assume 720,000 source hours uploaded per day at an average 8 megabits/second, and one billion viewing hours per day at 5 megabits/second. These are design inputs, not current YouTube measurements. Use decimal storage/bandwidth units:

```text
source seconds/day = 720,000 × 3,600 = 2,592,000,000
raw bytes/day      = source seconds/day × 8,000,000 ÷ 8
                   = 2.592 PB/day
average upload     = raw bytes/day × 8 ÷ 86,400 = 240 Gbit/s
five-year raw copy = 2.592 PB × 365 × 5 ≈ 4.73 EB

average playback   = 1,000,000,000 × 3,600 × 5,000,000 ÷ 86,400
                   ≈ 208.33 Tbit/s
hypothetical 4× peak ≈ 833.33 Tbit/s
```

At 8 megabits/second, one source hour is 3.6 GB; combining that bitrate with 1 GB/hour would contradict the same storage model. Output variants, replicas, temporary uploads, and retention add separate costs. Tiering media into archival storage must account for restore latency: a video needing immediate playback cannot rely solely on an offline cold copy.

Transcoding capacity comes from measured compute-seconds per source-second for each codec/resolution, multiplied by incoming source rate and divided by target utilization. Six resolutions across four codecs create 24 possible outputs only if every combination is actually supported and required. Never infer a core count from "faster than realtime" without defining that factor, parallelism, and per-variant cost.

## Discovery and Event Processing Follow Committed State

Search indexes can lag metadata. Publish an event/outbox intent with the committed state and update the index idempotently; a blind database-plus-search dual write holds a failure gap. Visibility/removal enforcement must still apply when a stale index returns a video.

Recommendations can begin with subscriptions, recent history, and bounded popularity candidates. A larger system can separate candidate generation from ranking, with freshness and fallback policies. A vector store is one possible tool, not the entire recommendation service, and no fixed watch-time percentage justifies machine learning by itself.

Partitioning processing events by video ID can keep their broker ordering within a partition. It never ensures that asynchronously processed jobs finish in order, removes duplicate delivery, or prevents a stale version from publishing. Enforce those contracts at state transitions.

## Delivery, Privacy and Failure Decisions

| Condition | Mechanism and boundary |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Popular segments generate many reads | CDN caching and origin shielding reduce origin work; misses, purges and cold content still reach bounded origin capacity |
| A private/removed video is cached | Authorize manifests and segment delivery as required; token lifetime, edge enforcement and invalidation determine revocation delay |
| Worker dies after writing some files | Lease/retry and versioned output identity allow recovery; publish only verified required outputs |
| Origin region is unavailable | Replication can support failover only for available replicated objects and usable metadata/access dependencies; account for replication lag |
| Search is unavailable | Degrade to known catalog/history views or a bounded fallback; unrestricted database wildcard search can overload another dependency |
| Recommendations are unavailable | Serve a bounded fallback using currently visible content and retained preferences |
| Queue backlog grows | Scale from measured job cost, queue age and resource limits; queue depth alone hides jobs of different duration |
| Content requires studio protection | Signed delivery controls access; digital rights management (DRM) adds licensed decryption/usage controls where required |

Signed URLs are bearer credentials with a lifetime. An unlisted link is discoverable by anyone receiving it, so it never equals private ownership authorization. Codec savings depend on content, bitrate/quality targets, and device compatibility; compare measured output rather than claiming a universal percentage.

Moderation and malware/media validation need clear gates and appeals/removal behavior. Keep watch history and analytics under deliberate access, retention, and consent policies. Live streaming would add continuous ingestion, short-latency packaging, redundant source behavior, and its own reconnect policy; it never follows from the video-on-demand example.

## Observe User Outcomes and Pipeline State

Measure upload completion, time to first playable version, oldest queued job, failed/stale publication attempts, and storage cleanup. During playback, measure startup, stalls/rebuffer duration, and delivered quality by device/network cohort. CDN hit ratios and egress help diagnose costs, but never alone prove a good viewing experience.

Derive alerts from service objectives and workload baselines. An arbitrary universal five-minute queue threshold can be too slow for a short clip and unrealistic for a large archival upload. Use operation/version identifiers to follow one upload without logging signed credentials or private viewing payloads.

## Trade-offs

A managed transcoder reduces encoder operations but adds provider cost and limits; a self-managed fleet gives control while requiring scheduling, codecs, and failure recovery. Additional codecs can reduce delivery cost for compatible clients at the cost of preparation/storage. Multi-CDN delivery can improve coverage and supplier flexibility while making routing, authorization, and incident analysis more complex. Choose these from measured workload and team capacity.

## Summary

Separate upload acceptance, durable processing and playable publication. Version preparation outputs, verify complete manifests, and keep authorized media delivery distinct from the control API. Use consistent workload units, measured codec/compute costs and explicit cache/revocation boundaries; discovery and analytics should follow committed state without becoming playback's unbounded dependencies.

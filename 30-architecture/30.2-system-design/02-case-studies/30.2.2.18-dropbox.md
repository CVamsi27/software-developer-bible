# Dropbox System Design

## Definition

A file-sync service moves committed file versions among devices, including devices that edit while offline. It must reconcile content, paths, permissions and deletion without silently discarding a competing edit.

> **Textbook Definition:** A file-synchronization service propagates versioned file changes among devices using content transfer and metadata reconciliation, preserving an explicit policy for concurrent edits and deletion.

This is a Dropbox-style design exercise. Its proposed architecture is distinct from documented Dropbox API behavior and dated engineering reports. Confirm current product limits and retention from the exercise; there is no assumed universal file-size or paid-plan policy here.

## First Principles

Devices can lose connectivity after sending bytes but before learning whether a version committed. Two devices can edit the same base independently. Notifications can disappear, and one filename can refer to different versions over time. A reliable design therefore needs stable identity, version-conditioned commits, a retained change position and durable local progress.

Large files add another constraint: retrying a small change should not always transfer the whole file. Chunking can reuse unchanged bytes, but the metadata that selects a complete version must agree with the available chunks. Access permission remains separate from knowing a content hash.

## Requirements

Clarify file-size/types, expected edit rate, path normalization, moves, selective/on-demand sync, offline duration, deleted-file recovery and version retention. Define a **namespace**, the user/team-owned logical tree with its own authorization and change ordering. Sharing can change membership without changing file bytes, so permission changes need their own enforcement path.

Choose whether arbitrary binary files get conflict copies, whether any text formats support a safe three-way merge, and whether live collaborative documents are a separate product. Operational transformation (OT) or conflict-free replicated data types (CRDTs) are specialized collaboration models; neither automatically merges arbitrary binary files.

## Keep Bytes, Metadata and Recovery Separate

```text
local durable journal + local file/index state
  → inspect base revision and changed chunks
  → authorized content upload → immutable chunk/object storage
  → conditional metadata/version commit + retained namespace change
  → notification hint → other device reads changes from its cursor
  → apply content/metadata locally → persist the new cursor
```

The byte store holds content. Metadata selects a current file version and its path; a version manifest lists chunks in order. The change log tells another device what committed. Notifications reduce waiting but are not the only record of truth. A local database/journal retains operations and last-applied progress across a client crash.

## Trace Two Offline Editors

Device A and device B both start from file revision 7. A uploads its changed chunks and commits with the condition “current revision must still be 7.” The server accepts revision 8. B later uploads its different chunks with the same base condition; the metadata commit detects that 7 is stale.

For a conflict-copy policy, preserve B's content under a new conflict identity/path and return an explicit conflict outcome. For a supported text format, a service might compare base 7, current 8 and B's candidate to attempt a three-way merge. File timestamps do not prove which edit should win, and an unconditional overwrite silently loses one contribution.

A retry after a lost successful response should find the outcome associated with its operation identity. It must not create revision 9 or a second conflict copy simply because the caller cannot distinguish success from timeout. The metadata transaction and idempotency record belong to the operation's durable boundary.

## Chunking Reuses Bytes Within a Defined Protocol

For fixed four-MiB chunks, changing bytes in one chunk requires retransferring that chunk, not just the one changed byte:

```text
base: [A][B][C][D][E]
edit: [A][B][X][D][E] → reuse A,B,D,E; transfer X
```

An insertion near the beginning can shift fixed boundaries and change many later hashes. Content-defined chunking chooses boundaries from content to reduce that effect, at extra CPU/protocol complexity. The rsync rolling-checksum method is another delta-transfer design; it is not synonymous with a fixed-chunk hash list.

A content-addressed store keys an immutable chunk by a digest of its bytes. Verify supplied bytes against the digest, handle concurrent uploads through the store's supported conditional/integrity contract and keep ownership authorization separate. A missing object is a failed integrity check, not permission to publish a manifest that references it.

### Compute the documented Dropbox content hash

Dropbox's API `content_hash` hashes each four-MiB block, concatenates the binary 32-byte digests and hashes that concatenation. It is not an ordinary whole-file SHA-256 or a recursively paired Merkle-tree root. The following Python standard-library function implements that documented checksum:

```python
from hashlib import sha256
from pathlib import Path

BLOCK_SIZE = 4 * 1024 * 1024

def dropbox_content_hash(file_path: str | Path) -> str:
    combined = sha256()
    with open(file_path, 'rb') as source:
        while block := source.read(BLOCK_SIZE):
            combined.update(sha256(block).digest())
    return combined.hexdigest()
```

For an empty file, the result is SHA-256 of empty bytes because there are no block digests. Using hexadecimal text instead of each digest's binary bytes changes the result. This checksum verifies content identity; it does not expose an API for arbitrary cross-user deduplication or grant access to matching content.

## Commit a Complete Version Through Valid Metadata

The following PostgreSQL DDL is a focused model for current file identity and version manifests. The service supplies validated owner/namespace access and normalized paths. A path can change while file identity remains stable.

```sql
CREATE TABLE file_metadata (
  file_id uuid PRIMARY KEY,
  namespace_id uuid NOT NULL,
  normalized_path text NOT NULL,
  revision bigint NOT NULL CHECK (revision > 0),
  deleted_at timestamptz,
  UNIQUE (namespace_id, file_id)
);
CREATE UNIQUE INDEX live_file_path
  ON file_metadata(namespace_id, normalized_path)
  WHERE deleted_at IS NULL;

CREATE TABLE file_versions (
  namespace_id uuid NOT NULL,
  file_id uuid NOT NULL,
  revision bigint NOT NULL CHECK (revision > 0),
  manifest_key text NOT NULL,
  size_bytes bigint NOT NULL CHECK (size_bytes >= 0),
  committed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (file_id, revision),
  UNIQUE (namespace_id, file_id, revision),
  FOREIGN KEY (namespace_id, file_id)
    REFERENCES file_metadata(namespace_id, file_id)
);

-- The pointer must name an existing version. Deferral permits a new pointer
-- and its file_versions row to be written in the same transaction.
ALTER TABLE file_metadata
  ADD CONSTRAINT current_version_exists
  FOREIGN KEY (namespace_id, file_id, revision)
  REFERENCES file_versions(namespace_id, file_id, revision)
  DEFERRABLE INITIALLY DEFERRED;

-- Store the result with the mutation so a retry after an unknown response
-- returns the same outcome rather than applying it again.
CREATE TABLE sync_operations (
  namespace_id uuid NOT NULL,
  operation_id uuid NOT NULL,
  request_fingerprint bytea NOT NULL CHECK (octet_length(request_fingerprint) = 32),
  outcome jsonb NOT NULL,
  committed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (namespace_id, operation_id)
);

-- One head row serializes cursors within a namespace in this teaching model.
CREATE TABLE namespace_heads (
  namespace_id uuid PRIMARY KEY,
  last_sequence bigint NOT NULL DEFAULT 0 CHECK (last_sequence >= 0)
);

CREATE TABLE namespace_changes (
  namespace_id uuid NOT NULL,
  sequence bigint NOT NULL CHECK (sequence > 0),
  change_id uuid NOT NULL,
  operation_id uuid NOT NULL,
  file_id uuid NOT NULL,
  revision bigint NOT NULL CHECK (revision > 0),
  change_kind text NOT NULL CHECK (change_kind IN ('created', 'updated', 'moved', 'deleted')),
  committed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (namespace_id, sequence),
  UNIQUE (namespace_id, change_id),
  FOREIGN KEY (namespace_id, operation_id)
    REFERENCES sync_operations(namespace_id, operation_id),
  FOREIGN KEY (namespace_id, file_id, revision)
    REFERENCES file_versions(namespace_id, file_id, revision)
);
```

A content write first stages and verifies immutable chunks. In one metadata transaction, insert an uncommitted operation claim with a placeholder outcome and compare `(namespace_id, operation_id)` plus the canonical request fingerprint; a matching retry returns the committed outcome, while changed input under the same key is rejected. Replace the placeholder before commit. For an edit, increment the revision only if the current value still equals the caller's base revision, then use the returned revision for the version and change rows:

```sql
UPDATE file_metadata
SET revision = revision + 1
WHERE namespace_id = $1
  AND file_id = $2
  AND revision = $3
  AND deleted_at IS NULL
RETURNING revision;
```

No returned row means the file was deleted or the base is stale; return a conflict or create one explicit conflict copy under a new file identity, never overwrite the competing revision. Insert the complete version, advance that namespace's head, and append the matching change and operation outcome in the same transaction. Because the current-version and change-row foreign keys point at the new version, the complete manifest record must exist by commit. The `namespace_heads` row is created with the namespace and incremented in the same transaction:

```sql
UPDATE namespace_heads
SET last_sequence = last_sequence + 1
WHERE namespace_id = $1
RETURNING last_sequence;
```

Use the returned sequence for the change row and cursor; do not substitute wall-clock timestamps. This one-head model serializes writes in a hot namespace; partitioning it requires a cursor that can represent the chosen partition order.

Moves and deletions also advance revision and produce durable changes; a delete is a retained tombstone, not physical removal of the metadata row. Sharing and membership changes require their own policy and change stream. The schema cannot prove that object-store bytes exist: verify the manifest before the metadata commit, and let a grace-period collector remove only unreachable staged objects.

Keep file manifests immutable so an old revision remains reconstructible. Deleting a live path can release the partial unique constraint, but restoring its previous occupant may conflict with a newly created file at the same path. Define recovery behavior instead of assuming that soft deletion makes every restore possible.

## A Notification Wakes Sync; a Cursor Recovers It

For a proposed sync service, retain ordered namespace changes and issue a scoped cursor. A client reads a page, applies it safely, then persists its latest cursor. Repeated pages must be harmless, and retained tombstones prevent deletion from being forgotten and later resurrected by an offline device.

If a client crashes after applying changes but before saving its cursor, it may apply the page again. If it saves the cursor before applying changes, it may skip required work after a crash. Use local transactional progress or staged apply/recovery appropriate to the filesystem operations. A notification without a durable cursor/change source cannot establish replay.

For the actual Dropbox API, `/files/list_folder` and its continuation enumerate entries and later changes. `/files/list_folder/longpoll` waits for a change indication; it does not return the changed entries. After that indication, call the continuation to read them, following `has_more` until exhausted. An expired cursor can require a fresh listing after a reset error. File-change cursors do not necessarily report sharing-setting changes; fetch the relevant permission information through its own supported contract.

A WebSocket, long poll or webhook is a notification transport choice. Apply bounded reconnect/backoff and provider-directed delays; immediately retrying every timeout across the fleet can create a request storm. Offline duration beyond retained history needs a full reconciliation procedure, not an unlimited replay promise.

## Deduplication and Garbage Collection Need Safety Rules

A global “does this digest exist?” oracle can disclose whether another user stores known content. Compare per-tenant deduplication with global deduplication under encryption, ownership proof and privacy requirements. Client-side encryption can also prevent the server from reusing plaintext identities unless a separate deliberate scheme is used.

Garbage collection (GC) must account for current manifests, retained versions, pending uploads and recovery windows. Asynchronously incrementing a reference count after commit can let GC delete a live block first. A zero cached count does not prove that an object is unreachable. Use authoritative reachability/reference state, protected publication and a grace period with revalidation before deletion; reconcile failed or interrupted GC operations.

LAN sync can transfer authorized content from a nearby trusted device under a defined authentication/integrity protocol. It is an optional optimization, not a guarantee that most bytes never reach the service. Measure reuse and bandwidth savings rather than treating cross-user deduplication as free storage.

## Estimate the Chosen Workload Consistently

Use hypothetical registered/active users, storage distribution, versions and edit rate from the exercise. If 700 million users each store 50 GB, their logical current data totals 35 EB before history or replicas. A smaller physical total requires a supported occupancy, deduplication or compression model; it does not follow from those inputs automatically.

```text
average syncs/second = syncs/day ÷ 86,400
transferred bytes   = missing chunks + protocol/metadata overhead
metadata rows       = current files + retained versions/change entries
physical storage    = unique retained objects × replication/encoding cost
```

File-size distribution, boundary-shifting edits, hot namespaces and inactive users affect the estimate. Capacity planning must include local-disk space, watcher/indexing work and reconciliation after long outages, not only server requests.

## Failure and Scaling Decisions

| Condition | Behavior to define |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| File changes during a local read | Snapshot/stage or detect the change and retry; avoid publishing hashes of mixed versions |
| Client or upload connection disappears | Retain bounded operation/session progress and safely resume or expire it |
| Notification is lost | Fetch retained changes from the cursor; do not rely solely on an ephemeral pub/sub event |
| Metadata commit fails after bytes upload | Unreferenced bytes remain for bounded cleanup; do not advertise the candidate as current |
| Content is missing after metadata publication | Detect integrity failure, recover a verified replica/version and retain an explicit failure state |
| A namespace becomes hot | Bound per-namespace work and evaluate partitioning; replica reads must satisfy the cursor/current-state contract |
| A share link is revoked | Enforce current access and chosen signed-token lifetime/cache policy; expiration is not automatic CDN purge |
| An object-store region fails | Fail over only to available replicated content with usable metadata/access dependencies; lag can make recent files unavailable |

Selective/on-demand sync saves device storage but still needs accurate placeholder, hydration and access behavior. Cold-tiering old versions saves storage cost while changing recovery time; state that latency in the product contract.

## Monitor and Choose Trade-offs

Measure committed-to-applied sync delay, stale-base conflicts, retries after unknown outcomes, cursor resets, stalled clients, missing content and GC backlog. Separate metadata visibility from completed local hydration. Define service goals and alerts from cohorts and expected workload, rather than universal thresholds borrowed from a product name.

Smaller chunks can reduce retransferred bytes while increasing metadata and request work. Strongly coordinated namespace commits simplify ordering while constraining partitioning. Conflict copies preserve arbitrary binary edits without claiming a semantic merge. Version retention and deduplication scope determine cost, privacy and recovery; justify each choice from the requirements.

## Summary

A dependable sync design combines immutable content, conditional version commits, durable local progress and cursor-based recovery. Notifications speed detection, while retained state handles loss and offline devices. Bound content reuse by privacy/authority, preserve competing edits and protect live/retained objects during garbage collection.

# Lyft / Ride-Sharing System Design

## Definition

A ride-sharing system finds an available driver for a rider, offers the trip, and coordinates pickup, travel, and payment. A nearby dot on the map is only a candidate: the driver may have moved, gone offline, or accepted another ride.

> **Textbook Definition:** A ride-sharing service coordinates geographically distributed supply and demand through driver discovery, trip assignment, and state transitions, with matching policy adapted to local density and availability.

This is an interview design exercise, not a description of Lyft's current implementation. The [Uber case](30.2.2.03-uber.md) covers the related marketplace problem. Here the focus is matching under uneven city density and preserving assignment correctness when offers race.

## First Principles

A location report describes the recent past. Messages arrive late or out of order, and two dispatch workers can see the same available driver. Fast discovery therefore needs an approximate location index, while the final assignment needs an authoritative check. Putting both responsibilities in the map cache would let an expired observation create a real booking.

A ride and a driver are separate scarce resources. Locking one ride prevents two drivers from taking that ride; it does **not** stop one driver taking two different rides. Assignment must protect both resources together.

## Requirements and capacity assumptions

Support quotes, immediate ride requests, offers with acceptance deadlines, cancellation, trip progress, live positions, receipts, and payment recovery. Exclude pooled rides, scheduled pickup, and driver onboarding from this first design; they introduce different allocation and safety rules.

For an illustrative peak, assume one million online drivers sending once every three seconds. That is about 333,333 location reports per second. If that load lasted all day, it would produce 28.8 billion reports, or 2.88 TB at 100 bytes per report before envelopes, indexes, and replication. Peak concurrency alone does not establish daily volume.

Assume 200,000 simultaneous trips with a 20-minute average duration at steady state. Completion throughput is about 167 trips per second; five lifecycle events per trip give about 833 events per second. This estimate excludes cancellations and retries. Multiplying concurrent trips by five without dividing by duration produces an event count, not an event rate.

Choose separate objectives for request-to-offer, offer-to-acceptance, and successful pickup. For this exercise, target request-to-offer p99 below five seconds and bounded 30-second offers. Measure each city separately: a global average can hide a city with no available drivers.

## How the components fit together

```text
Driver app → authenticated location ingest → driver-keyed stream → geo index
                                                                   ↓
Rider app → quote / booking API → dispatch → bounded road-ETA lookup
                                    ↓
                         authoritative assignment transaction
                                    ↓
                     outbox → notifications / trip events
                                    ↓
                       trip lifecycle → payment workflow
```

The **geo index** groups recent driver positions into map cells so dispatch can shortlist candidates. S2 uses hierarchical spherical cells; H3 uses a hexagonal global grid. Redis may store each cell's members, but it is a storage choice rather than a geometry library. Start with a simpler spatial database if measured workload permits it.

The trip store owns booking state. A transactional **outbox** records events beside the state change in the same database transaction; a publisher later delivers them. Delivery can repeat, so consumers deduplicate event IDs. This avoids committing a trip while losing its notification because a separate broker write failed.

## Find candidates without promising a global optimum

Accept location reports only from the authenticated driver. Validate latitude, longitude, payload size, and an increasing session sequence. Store server receive time and the device observation time separately: a device timestamp alone cannot establish freshness. Partition position events by driver ID to preserve that driver's order without forcing an entire busy city into one broker partition.

For example, a Redis sorted set uses receive time as the score and driver ID as the member:

```text
ZADD geo:cell:example 1791532800 driver_99
ZRANGEBYSCORE geo:cell:example 1791532790 1791532800 LIMIT 0 100
```

The numbers are illustrative epoch seconds. The member and score order matters. Query nearby cells, load candidate metadata, exclude stale or unavailable drivers, and cap the number of expensive route estimates. Moving between cells must remove old membership or deduplicate candidates and recheck their latest position. Expiring a cell key is insufficient when a busy cell is continually refreshed: individual stale members still need removal or filtering.

An expanding search ring is a **bounded approximation**. The first nonempty ring need not contain the driver with the lowest road travel time: a nearby driver across a river may be slower than a farther driver beside a bridge. Choose an explicit time/radius/candidate budget and compare eligible candidates within it. Larger budgets improve selection at a cost in latency and routing load.

Straight-line distance divided by an assumed speed yields a rough time; multiplying distance by speed does not. A road-routing service accounts for bridges, one-way streets, and traffic. Cache estimates briefly with their observation time, and label degraded estimates when the routing dependency fails. Do not silently report a precise arrival time from an old matrix.

## Offer acceptance must claim both resources

An offer names a ride, driver, offer ID, expiry, and expected booking version. Several offers may be outstanding if policy allows it, but an acceptance is a request to assign, not proof of ownership. Authorize the driver from their session, then check the offer, expiry, and both current resources in one transaction.

A minimal PostgreSQL model illustrates the invariant:

```sql
CREATE TABLE rides (
    ride_id bigint PRIMARY KEY,
    rider_id bigint NOT NULL,
    status text NOT NULL CHECK (status IN
        ('requested', 'matched', 'arrived', 'in_progress', 'completed', 'cancelled')),
    version bigint NOT NULL DEFAULT 0 CHECK (version >= 0)
);
CREATE TABLE drivers (
    driver_id bigint PRIMARY KEY,
    available boolean NOT NULL DEFAULT false
);
CREATE TABLE active_assignments (
    driver_id bigint PRIMARY KEY REFERENCES drivers(driver_id),
    ride_id bigint NOT NULL UNIQUE REFERENCES rides(ride_id),
    offer_id uuid NOT NULL UNIQUE
);
```

The assignment primary key prevents two active rides for one driver. The unique ride key prevents two active drivers for one ride. This is a focused model, omitting coordinates, offer storage, quotes, audit events, and the outbox.

Here, `drivers.available` means eligible to receive another offer; it is not proof that no assignment exists. The unique assignment constraints remain the final double-booking guard. Recheck both the flag and current assignment state inside the transaction rather than trusting a cached map result.

Acceptance uses the following **transaction pseudocode**, not a complete API implementation:

```text
begin
lock the driver row, then the ride row (every competing path uses this order)
check authenticated driver, unexpired offer, driver availability,
      ride status=requested, and expected ride version
insert active assignment; a uniqueness conflict rejects the acceptance
mark driver unavailable
update ride to matched and increment its version
append event and outbox record
commit
```

Abort the entire transaction if any check or write fails. A retry for the same accepted offer returns its existing assignment; an expired or different offer cannot reuse that success. A rides-only conditional update protects just the ride and leaves the driver invariant broken.

Trace two acceptances: driver 99 accepts ride 10 and ride 11 at nearly the same time. The first transaction locks driver 99, assigns ride 10, and commits. The second obtains that lock afterward, sees the driver unavailable, and rejects ride 11. If the first transaction fails after inserting the assignment, rollback restores **both** availability and booking state.

A notification may arrive after expiry or after the ride is cancelled. The acceptance transaction must recheck current state rather than trust the displayed offer. Regional ownership transfer also needs an explicit handoff: two regional databases cannot each authoritatively declare the same driver available.

## Trip progress and payment are separate lifecycles

```text
requested → matched → arrived → in_progress → completed
     ↘          ↘         ↘
                 cancelled (only where policy permits)

payment: pending → processing → succeeded
                         ↘ failed → recovery / reconciliation
```

Enforce allowed transitions, authorized actors, and expected versions. For a cancellation/start race at version 7, only one transition may change version 7 to 8; the loser rereads and applies the appropriate policy. An event ID or per-ride sequence identifies audit records more safely than a timestamp-only primary key.

Completing physical travel does not prove payment succeeded. Preserve the completed trip while tracking payment independently. Use a stable provider idempotency key for a charge attempt and reconcile unknown outcomes before issuing another charge. Retry limits depend on provider semantics and recovery policy, not an arbitrary promise that every charge resolves within 24 hours.

Release an assignment through an authorized, version-checked trip transition. Removing it merely because a worker lease expired could free a driver who is still carrying a passenger. Worker ownership and trip ownership are different facts.

## Quotes, identity, and privacy boundaries

Derive rider and driver IDs from authentication. A request body cannot impersonate another account. Check ownership for cancellation and access to positions, and restrict live location visibility to the participants who currently need it.

A quote records its currency, amount in minor units, pricing policy version, and expiry. The rider confirms that quote before booking. Demand-based pricing reads aggregated supply and demand, but smoothing, maximum changes, fallback age, and disclosure depend on product policy and applicable rules. A universal four-times cap is not an architectural or legal guarantee.

If pricing fails, honor an already valid quote under its terms or ask for a new quote. Do not substitute an expired cached multiplier after the rider agreed to a different price. Retain precise location history only as required for the stated operational and safety purpose, with scoped access and deletion rules.

## Real-world decisions and failure recovery

| Condition | Decision and boundary |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dense event venue | Cap per-cell candidate work and queue length; reject or estimate a bounded wait when overloaded. More candidates do not automatically mean better latency. |
| Sparse suburb | Expand search within a time/distance budget; report no availability when the budget ends. |
| Stalled location stream | Exclude positions beyond the freshness limit. Reusing stale locations indefinitely fabricates available supply. |
| Lost booking response | Retry with a rider-scoped idempotency key and return the existing request. A retry must not create a second ride. |
| Notification outage | Replay outbox events with deduplication and deadlines; do not treat delivery as driver acceptance. |
| GPS anomalies | Flag implausible movement for additional checks. Plausibility filtering is a signal, not proof against spoofing. |
| Region outage | Preserve assignment ownership during recovery. Availability loss is safer than assigning a still-busy driver twice. |

Track request-to-offer and acceptance latency, expired offers, unassigned requests, assignment conflicts, per-city available supply, location age, route-estimate error, broker lag, outbox age, and unresolved payments. Alert against explicit service objectives and freshness budgets rather than unexplained universal thresholds.

## Mistakes and best practices

- Treat the map as candidate discovery; recheck authoritative state when accepting.
- Protect both the driver and the ride, including cancellation and release paths.
- Separate peak rate, daily volume, concurrency, and average trip duration in capacity arithmetic.
- Bound search, retries, and queues so an outage cannot accumulate unlimited work.
- Distinguish an offered ride, accepted assignment, completed journey, and successful charge.

## Summary

Ride sharing joins an approximate, time-sensitive map with a strict resource-allocation workflow. A bounded spatial search finds plausible drivers; an atomic acceptance claims both driver and ride. Versioned transitions, expiring offers, durable event publication, and independent payment recovery keep delayed messages and retries from creating conflicting journeys.

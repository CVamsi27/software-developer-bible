# Distributed Counter / Metrics Aggregation System Design

Two processes read 10 and both write 11: one increment is lost. An atomic update fixes that race at one record, but retrying a committed increment after a lost response counts twice. Arithmetic safety and duplicate safety are different contracts:

```text
2 processes read 10, write 11 → one increment lost. Atomic update or event identity?
```

## Definition

A **distributed counter** combines increments from several processes into a value clients can read. Counting video views can tolerate a delayed display; counting remaining tickets must prevent overselling. Both use numbers, but they need **different guarantees**.

> **Textbook Definition:** A distributed counter aggregates updates from multiple processes under a specified merge and read contract, trading coordination, freshness, and exactness according to the counter's business use.

## First Principles

1. Two processes separately reading 10 and writing 11 lose one increment. An atomic update avoids that race at one authoritative record, but concurrent writes to a hot record still serialize. Splitting the record spreads work while making a consistent total harder to read.
2. Delivery creates another problem: a sender cannot always tell whether an increment committed before its response was lost. Retrying without identifying the original operation can count twice. Atomic arithmetic and duplicate suppression solve different failures.

## Choose a counting contract before the storage

| Business use | Contract | Consequence |
| ---------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Approximate popularity | Bounded delay or explicit error/loss budget | Local aggregation may be acceptable; disclose freshness. |
| Eventually exact event count | Every accepted unique event eventually contributes once | Durable acceptance, replay, and deduplication must share a defined boundary. |
| Remaining inventory | Atomically admit only if capacity remains | A stale distributed sum cannot authorize a sale. |
| Unique visitors | Count distinct identities under a defined identity/window rule | An ordinary increment counts visits, not people; sketches estimate distinctness. |

For this exercise, use eventually exact event counts with a maximum normal display lag, plus a separate approximate mode when loss is explicitly acceptable. Never promise strong per-key reads while choosing asynchronously summed shards.

## Capacity assumptions

Assume one million events per second at a **sustained** rate. At 100 bytes per event, raw ingestion is 100 MB/s or 8.64 TB/day before indexes and replication. If one million is only the peak, daily volume requires the traffic profile.

One billion 64-bit counter values need 8 GB (decimal) of raw storage. If each counter also stores one 64-bit timestamp or generation, that pair needs 16 GB. If every counter retains 60 equally populated buckets, those buckets need 480 GB for values alone, or 960 GB for value-plus-metadata pairs. Keys, indexes, replicas, and storage-engine overhead add to either estimate. Often only recently active keys hold all buckets; measure that distribution rather than allocating every bucket for every historical key.

A workload in which one key receives 100,000 updates per second needs a hot-key strategy. There is no universal PostgreSQL or Redis operations-per-second ceiling: row contention, persistence, batching, hardware, and network behavior need representative measurements.

## Start with one correct authoritative update

For moderate traffic, a PostgreSQL transaction can claim an event and update its counter together:

```sql
CREATE TABLE counter_values (
    tenant_id bigint NOT NULL,
    counter_key text NOT NULL,
    value bigint NOT NULL DEFAULT 0,
    PRIMARY KEY (tenant_id, counter_key)
);
CREATE TABLE counter_events (
    tenant_id bigint NOT NULL,
    event_id uuid NOT NULL,
    counter_key text NOT NULL,
    delta bigint NOT NULL,
    PRIMARY KEY (tenant_id, event_id)
);

-- $1 tenant, $2 stable event ID, $3 authorized counter key, $4 delta
WITH accepted AS (
    INSERT INTO counter_events(tenant_id, event_id, counter_key, delta)
    VALUES ($1, $2, $3, $4)
    ON CONFLICT (tenant_id, event_id) DO NOTHING
    RETURNING tenant_id, counter_key, delta
)
INSERT INTO counter_values(tenant_id, counter_key, value)
SELECT tenant_id, counter_key, delta FROM accepted
ON CONFLICT (tenant_id, counter_key) DO UPDATE
SET value = counter_values.value + EXCLUDED.value;
```

This is a parameterized PostgreSQL statement; create the tables first and supply bound parameters through a driver. A duplicate event contributes nothing. After a conflict, compare the stored `counter_key` and `delta` with the request: return the prior outcome only for an exact match, and reject reuse of the same event ID with a different payload. The statement suppresses a second addition, but never performs that payload comparison itself. The enclosing transaction rolls back both event insertion and arithmetic if the addition overflows or another write fails.

Authorize writes, bound batch size, and validate numeric ranges. The toy schema omits namespace policy and stored response metadata.

Trace event E adding 3: value 10 becomes 13. The response is lost. The client retries **E**, not a new UUID; the event uniqueness check suppresses the second addition. A later distinct event F adding 2 yields 15. Retain deduplication records at least as long as accepted retry/replay history; expiry must never turn an old replay into a fresh count.

## Scale with a durable log and a rebuildable projection

```text
Producer → authorized ingest → durable event log → shard aggregators
                                                     ↓
                                            counter projection
                                                     ↓
                                     total / time-window read API
```

A **projection** is stored state derived from the event log, such as the latest count for a key. Return acceptance only after the chosen durable-log acknowledgment; specify replication and retention assumptions. Consumers update a projection and record consumed event IDs or offsets in a consistent commit boundary. Crash after updating but before checkpointing must never add the same event again on replay.

A Redis-first update followed by a fire-and-forget log write holds no such boundary: a crash between them creates an unlogged increment, and the reverse order can leave the visible value behind. Make one durable source authoritative and let the other state be rebuildable. Redis atomic commands never imply lossless failover; [Redis replication documentation](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/) describes acknowledged-write loss boundaries.

Never evict the only authoritative counter as if it were a cache. If Redis stores a projection, cache misses load a known checkpoint and replay or read the authoritative projection. Track its generation so an older restoration cannot overwrite a newer total.

## Spread a hot key across shards

Route an event to one of N shards, preferably by a stable hash of its event ID. Randomly selecting another shard on a retry breaks shard-local deduplication. Include the routing generation when changing N so replay follows the original ownership rule:

```text
Logical counter views:video7
  shard 0 = 120
  shard 1 = 90
  shard 2 = 110
Displayed total = 320
```

Writes to separate shards can proceed independently. A sequential read across shards is no single atomic snapshot: updates can arrive between reads. Return a freshness/checkpoint description, or maintain a periodic aggregate for cheaper reads. A globally linearizable total requires additional coordination; sharding alone never provides it.

Signed deltas can be stored per shard, but independently decrementing shards cannot enforce a global lower bound. Inventory and quotas need an authoritative conditional allocation or a proved reservation protocol. Counting likes also needs a unique user–post relationship if one like per user is the rule; accepting arbitrary repeated increments is insufficient.

## Batch locally only with an explicit recovery story

Local pre-aggregation sums many events before writing a batch. If 1,000 servers each combine 100 updates to one key into one batch per second, that key sees 1,000 batch writes rather than 100,000 individual writes. Idle keys still need a timer-driven flush; flushing only on the next incoming increment can leave the last update pending indefinitely.

Volatile buffers lose unflushed work on process death. Durable batches carry a stable batch ID and are retained until acknowledged. If acknowledgment is lost, retry the **same batch**; clearing a buffer before confirmation loses work, while blindly resending its delta can count twice. Bound buffer memory, batch size, retry age, and producer backpressure. A local flush interval is only one part of end-to-end freshness, which also includes broker and consumer lag.

## A grow-only counter merges state, not repeated deltas

A conflict-free replicated data type (**CRDT**) is a replicated structure with a merge rule converging despite repeated or reordered state exchange. A grow-only counter (**G-Counter**) gives each writer a monotonic slot and merges slots by maximum:

```python
def merge(left: dict[str, int], right: dict[str, int]) -> dict[str, int]:
    nodes = left.keys() | right.keys()
    return {node: max(left.get(node, 0), right.get(node, 0)) for node in nodes}

left = {"A": 3, "B": 2}
right = {"A": 1, "B": 5}
third = {"A": 2, "C": 4}
combined = merge(left, right)  # {"A": 3, "B": 5}; total = 8
assert merge(left, left) == left  # idempotent
assert merge(left, right) == merge(right, left)  # commutative
assert merge(merge(left, right), third) == merge(left, merge(right, third))  # associative
assert merge(combined, right) == combined  # repeated state does not add again
```

For valid G-Counter state, the **merge**, not summing arbitrary received totals, is idempotent, commutative, and associative. Total equals the sum of the merged slots. Writers must never share a slot concurrently or reset a durable slot to zero after restart. Use durable identity/state or a new unique writer epoch; old epochs still contribute, so safe compaction needs a protocol.

A positive/negative counter (**PN-Counter**) keeps two grow-only structures and subtracts their totals. It converges for signed changes, but never by itself enforces a nonnegative inventory or deduplicates repeated business events. Its state can converge perfectly to a value that counted a client retry twice.

## Time windows and operational boundaries

Choose event time or ingestion time explicitly. Event time reflects when something happened but requires late-arrival handling; ingestion time is simpler but shifts delayed events into later buckets. Specify bucket width, timezone, window boundary inclusion, and correction policy. A watermark is an estimate of event-time progress, not proof that no older event will ever arrive.

Expose projection age and consumer checkpoint alongside window totals. Rebuilding must never publish partial results as complete: construct a new generation, catch up to a known boundary, then switch readers. Reprocessing changed business rules also needs a versioned projection rather than silently mixing two definitions of a view.

## Verify the counting contract

| Test | Expected result |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Retry one accepted event ID with the same key and delta | The count changes once and the original outcome is returned. |
| Reuse an event ID with a different key or delta | Reject the request and leave both counters unchanged. |
| Lose the response after commit, then retry the same event | Replay returns the committed result without adding again. |
| Crash after projection write but before consumer checkpoint | Replay is idempotent or the write and checkpoint share a transaction; the count is not doubled. |
| Read shards while updates are in flight | Return a documented freshness/checkpoint boundary; do not label a sequential sum a linearizable snapshot. |
| Rebuild a projection while new events arrive | Publish the new generation only after it catches up to a known log boundary. |

## Summary

A counter's business meaning determines its architecture. Atomic updates prevent lost arithmetic; stable event identities prevent duplicate application. Durable logs make projections rebuildable, sharding spreads hot writes while weakening snapshot reads, and CRDT slot-wise maximum merges repeated state safely. None of these mechanisms alone authorizes an inventory decision or guarantees a lossless end-to-end count.

# Workflow Engine — System Design Case Study

An order workflow reserves stock, charges payment, then requests shipping. The worker crashes after the charge but before recording it. Recovery must resume from durable progress — never charge again just because the shipping step is unfinished:

```text
charge OK, worker dies before shipping step → resume from durable state, never recharge.
```

## Definition

A **workflow engine** remembers which steps of a **multi-step job** have finished and decides what can run next. For an order, it might reserve stock, charge payment, and request shipping. If a worker crashes after the charge, recovery must never charge again just because the shipping step remains unfinished.

> **Textbook Definition:** A workflow engine executes declared steps and transitions while persisting progress, scheduling work, and governing retries, timeouts, and compensation across process failures.

This exercise designs user-defined automation with webhook, schedule, and manual triggers. It is relevant to products such as n8n; it never asserts their internal architecture or guarantees a particular interview format.

## First Principles

1. A process's memory disappears when it dies, so progress needed for recovery must be durable. An external action and a local progress write usually cannot share a transaction: the action may succeed before the worker records its result. Retrying must therefore preserve the identity of the intended action and resolve uncertain outcomes.
2. A queue tells a worker that work may be ready; it cannot alone prove dependencies are complete, ownership is current, or an execution is still permitted. The persisted execution state decides those questions. For long-running work, the definition and credentials may also change while an old execution is paused.

## Requirements and scope

Support immutable published workflow versions, authenticated triggers, conditional branches, retry policies, durable waits, cancellation requests, and an auditable step history. Use a directed acyclic graph (**DAG**) for this first version: arrows represent dependencies, and cycles are rejected before publication. Loops and repeated subworkflows require explicit iteration identities and limits rather than accidental graph cycles.

Assume 100,000 executions per day with 5–20 steps each: about 1.16 executions and 5.8–23.1 step starts per second on average before retries. Burst rate, external latency, and fan-out determine actual worker demand. A one-second average step at 100 starts/second needs roughly 100 concurrently occupied slots; CPU-heavy work requires a different capacity model.

Set objectives for scheduling delay and engine recovery separately from downstream business success. An invalid email address is not an engine availability failure. Bound execution duration, payload sizes, fan-out, waiting history, per-tenant concurrency, and retention.

## How the engine fits together

```text
Builder → validate / publish immutable definition version
Trigger → deduplicate → create execution pinned to version
                              ↓
                        state + outbox
                              ↓
                  ready-step queue → worker
                              ↓
                      external action
                              ↓
                    result + next-step outbox

Timer / human signal → durable wait record → eligibility check
```

Store ready-work publication in the same transaction as the state transition. The outbox publisher can resend queue messages, so workers claim steps atomically and tolerate duplicate delivery. Lost notifications are recoverable from persisted ready steps; no queue message is the sole record of business progress.

## Persist the definition, step identity, and ownership

A minimal PostgreSQL teaching schema:

```sql
CREATE TABLE workflow_versions (
    workflow_id uuid NOT NULL,
    version integer NOT NULL CHECK (version > 0),
    tenant_id uuid NOT NULL,
    definition jsonb NOT NULL,
    PRIMARY KEY (workflow_id, version)
);
CREATE TABLE executions (
    execution_id uuid PRIMARY KEY,
    workflow_id uuid NOT NULL,
    workflow_version integer NOT NULL,
    status text NOT NULL CHECK (status IN
        ('queued', 'running', 'waiting', 'cancelling', 'completed', 'failed', 'cancelled')),
    FOREIGN KEY (workflow_id, workflow_version)
        REFERENCES workflow_versions(workflow_id, version)
);
CREATE TABLE execution_steps (
    execution_id uuid NOT NULL REFERENCES executions(execution_id),
    node_id text NOT NULL,
    status text NOT NULL CHECK (status IN
        ('pending', 'ready', 'running', 'waiting', 'completed', 'failed', 'skipped')),
    attempt integer NOT NULL DEFAULT 0 CHECK (attempt >= 0),
    lease_token uuid,
    lease_until timestamptz,
    output jsonb,
    PRIMARY KEY (execution_id, node_id)
);
```

The step primary key provides the uniqueness a per-step upsert requires. A published definition is immutable by application policy and restricted write access; the schema alone never enforces that policy. Check tenant ownership when starting or reading an execution. This model omits attempt-history, timer, credential, signal, and outbox tables.

An attempt claims a ready step and stores a fresh ownership token plus deadline. Its result update must match the current token and valid state. If the lease expires and a replacement worker claims it, the old worker cannot overwrite the replacement's result. The token protects database progress; external systems also need an idempotency or fencing contract.

## Trace a dependency and a failed action

Consider this graph:

```text
validate order → reserve stock → charge → request shipping
                      ↘ out of stock → notify unavailable
```

After stock reservation succeeds, persist its result and make the charge step ready in one transaction. If the worker crashes before enqueueing, the outbox republishes the charge. If the worker crashes after a provider accepts the charge but before progress is stored, retry uses the same business-action key and checks the provider's known outcome.

A topological ordering is a possible ordering of a graph; it is not a durable execution algorithm. A step whose parent is still running is **pending**, not automatically skipped. Skipping suits only the case where the selected branch or failure policy establishes that the step will never run. At a join, define whether all selected parents, any successful parent, or some explicit subset must complete.

Execution completion requires every required reachable step to hold a permitted terminal outcome. Breaking out of a loop because a step failed or cancellation was requested must never subsequently mark the whole execution completed.

## A focused state-transition example

This complete TypeScript function models execution-level transitions; step results are persisted separately. It leaves persistence, ownership, graph evaluation, and external actions to the surrounding engine:

```typescript
type Status = 'queued' | 'running' | 'waiting' | 'cancelling' |
  'completed' | 'failed' | 'cancelled';
type WorkflowEvent = 'start' | 'wait' | 'resume' | 'complete' | 'fail' |
  'request_cancel' | 'finish_cancel';

const next: Record<Status, Partial<Record<WorkflowEvent, Status>>> = {
  queued: { start: 'running', request_cancel: 'cancelled' },
  running: { wait: 'waiting', complete: 'completed',
    fail: 'failed', request_cancel: 'cancelling' },
  waiting: { resume: 'running', request_cancel: 'cancelled' },
  cancelling: { request_cancel: 'cancelling', finish_cancel: 'cancelled' },
  completed: {}, failed: {}, cancelled: {}
};

function transition(status: Status, event: WorkflowEvent): Status {
  const target = next[status][event];
  if (target === undefined) {
    throw new Error(`Invalid transition: ${status} + ${event}`);
  }
  return target;
}

const failed = transition(transition('queued', 'start'), 'fail');
const cancelling = transition(transition('queued', 'start'), 'request_cancel');
const cancelled = transition(cancelling, 'finish_cancel');
if (failed !== 'failed' || cancelling !== 'cancelling' || cancelled !== 'cancelled') {
  throw new Error('Workflow transition contract failed');
}
```

The engine emits `complete` only after checking graph completion, not whenever a worker function returns. A running execution enters `cancelling` when cancellation is requested; never mark it terminal until active actions are settled or reconciled. A failed execution is terminal here; a user-initiated retry creates a linked recovery execution under explicit policy rather than clearing history and pretending the original never failed.

## Retries cannot manufacture exactly-once side effects

Checking a completed-step row before making an HTTP call is useful, but leaves two gaps: competing workers can both pass the check, and an action can succeed before the completion write. Use a stable key such as `(execution ID, node ID, action version)` for the logical action, independent of attempt number. Require downstream support or record a reconciliation process for unknown outcomes.

Retry transient failures with bounded exponential backoff and jitter. Respect provider rate limits and response guidance; validation errors usually need correction, not automatic retries. A timeout can mean the remote operation completed. Classifying it as transient never establishes that replay is safe.

For SQL serialization failures, retry the whole transaction rather than just its last statement. For email or providers without suitable idempotency, state the possible duplicate/loss boundary and offer recovery instead of claiming a local upsert solves it.

BullMQ dispatches work; it is not itself the full workflow engine. Current BullMQ no longer requires the old `QueueScheduler` helper for stalled-job handling. A stalled job can run again, and a queue failure event may describe an attempt rather than the final business outcome. Derive execution status from persistent policy/state, never blindly from each queue callback.

## Durable waits, cancellation, and compensation

A long wait stores a deadline or correlation key and releases the worker slot. A timer service later rechecks readiness. Signals are authenticated, scoped to the execution, deduplicated, and recorded durably. Define behavior when a signal arrives before the wait record, after expiry, or concurrently with cancellation.

Cancellation requests stop scheduling new actions and ask running actions to cooperate. A remote provider may ignore the request or finish after it; reconcile the outcome before compensation or a terminal cancellation state. Cancellation cannot undo an email already sent or prove that a remote call stopped. Forced termination is different: it closes execution without cleanup and can leave reservations or external effects unresolved, so reserve it for an explicit emergency policy.

**Compensation** is a new business action counteracting an earlier one, such as refunding a successful charge. It is not a database rollback and may itself fail. Persist its progress and identity; expose unresolved compensation for an operator. Pause means stop future scheduling while preserving progress, not kill the process and erase work.

## Versioning and security choices

A custom state-machine engine resumes persisted states under a pinned definition and compatible action implementations. A deterministic replay engine, such as Temporal, instead reconstructs workflow decisions from recorded history under replay-compatible code. They are different recovery approaches; storing JSON step outputs never automatically implements deterministic replay.

Keep external effects in activities/connectors, preserve compatible code for in-flight versions, and use explicit migrations or version routing. Never reload today's edited workflow for a months-old execution without a migration policy.

User-configured HTTP and database actions create a security boundary. Restrict outbound destinations to prevent server-side request forgery, scope credentials per tenant/action, prevent arbitrary privileged queries or unsafe code execution, and redact secrets from inputs/outputs. Limit response size and execution time; isolation and authorization are part of the engine, not optional connector details.

## Real-world decisions and best practices

| Situation | Decision |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Short simple job | A queue plus explicit transactional state may suffice. |
| Long waits and complex recovery | Compare an established durable engine with the cost of building timers, history, versioning, and repair tooling. |
| Duplicate trigger | Reuse a stable trigger identity within its documented scope; create one execution. |
| Stale worker completion | Reject a result with the wrong ownership token; investigate any external effect separately. |
| Huge fan-out | Enforce per-tenant budgets and fair scheduling, not unlimited child jobs. |
| Workflow repair | Record who changed what and why; preserve original attempts and external-action identities. |

Observe ready-to-start delay, oldest pending outbox record, running lease age, retry exhaustion, wait deadlines, downstream latency, tenant fairness, unknown action outcomes, and outstanding compensation. Test crashes before and after remote effects as well as successful happy paths.

## Summary

A workflow engine makes progress durable and schedules only eligible steps. Stable action identity handles retries, ownership tokens reject stale results, and completion checks distinguish success from failure or cancellation. Long waits, immutable versions, external-effect uncertainty, compensation, and tenant isolation determine whether recovery works beyond the happy path.

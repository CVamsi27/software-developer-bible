# Real-Time Collaboration — System Design Case Study

## Definition

A collaborative editor lets several people change one shared document while seeing their own edits immediately. It must reconcile changes made without knowledge of each other and recover missing updates after reconnecting. Sending text over a WebSocket is only the transport part of that problem.

> **Textbook Definition:** A collaborative editor applies concurrent document operations from multiple users and reconciles replicas through an explicit ordering or merge algorithm, with persistence and authorization as separate contracts.

## First Principles

If Alice and Bob both insert at position zero of the same text, applying raw numeric positions in different orders can produce different documents. The editor needs a rule for relating edits to shared history, not merely a reliable connection.

Local display, peer visibility, and durable storage occur at different moments. Alice can see a change before Bob receives it and before the server stores it. The interface and acknowledgment protocol must identify which boundary has been reached. Reconnection must repair gaps rather than assume a live broadcast reached everyone.

## Scope and capacity assumptions

Support concurrent text editing, offline changes, reconnect synchronization, per-user undo, version history, and ephemeral cursors/presence. Begin with text and an explicit shared-data schema; rich text, attachments, comments, and granular permissions introduce additional operation semantics.

Illustrative capacity: 500,000 simultaneous editors and 100,000 updates per second globally. This implies one update per five seconds per connected editor on average, not a typing-rate guarantee. One billion 100 KB documents occupy about 100 TB of raw content before CRDT metadata, update history, replicas, and backups. Fan-out depends on editors and viewers per document; one update delivered to 1,000 viewers is 1,000 deliveries.

Target fast local feedback and define a separate peer propagation objective by region/network condition. A universal sub-100ms end-to-end promise does not follow from choosing WebSockets.

## Choose a reconciliation algorithm

**Operational transformation (OT)** adjusts an operation against other edits so it still refers to the intended content. Many practical systems use a server ordering and retained history. Correctness depends on transformation rules and the protocol; a unique sequence number alone does not implement OT.

A **conflict-free replicated data type (CRDT)** uses identifiers and merge rules that converge under stated update-delivery assumptions. Text CRDTs preserve relationships between inserted items rather than treating the current numeric index as a globally stable reference. Exact identifier, deletion, and compaction rules depend on the library.

Neither choice guarantees user intent, access control, durability, or bounded memory. CRDTs have not universally replaced OT, and named companies' internals are not a substitute for explaining the protocol. For this exercise choose Yjs because its shared text and update APIs let us demonstrate concurrent edits and repair explicitly. Measure its metadata, history, and editor-binding costs with representative documents.

## Trace concurrent changes with a complete example

Install `yjs` and save this as an ES module, such as `example.mjs`. It uses two in-memory replicas and explicitly transfers updates; it does not create a network server:

```javascript
import * as Y from 'yjs';

const alice = new Y.Doc();
const bob = new Y.Doc();
alice.getText('body').insert(0, 'cat');
Y.applyUpdate(bob, Y.encodeStateAsUpdate(alice));

// Both start from "cat" and edit while disconnected.
alice.getText('body').insert(0, 'A');
bob.getText('body').delete(0, 1); // remove the original c
const aliceUpdate = Y.encodeStateAsUpdate(alice);
const bobUpdate = Y.encodeStateAsUpdate(bob);
Y.applyUpdate(alice, bobUpdate);
Y.applyUpdate(bob, aliceUpdate);

console.assert(alice.getText('body').toString() === 'Aat');
console.assert(bob.getText('body').toString() === 'Aat');
Y.applyUpdate(bob, aliceUpdate); // duplicate delivery
console.assert(bob.getText('body').toString() === 'Aat');

// Carol recovers from a snapshot, then asks for later missing updates.
const carol = new Y.Doc();
Y.applyUpdate(carol, Y.encodeStateAsUpdate(alice));
alice.getText('body').insert(3, '!');
const missing = Y.encodeStateAsUpdate(alice, Y.encodeStateVector(carol));
Y.applyUpdate(carol, missing);
console.assert(carol.getText('body').toString() === 'Aat!');

alice.destroy(); bob.destroy(); carol.destroy();
```

Bob's deletion refers to the original `c`; it does not delete Alice's unseen new `A`. A **state vector** describes received CRDT state so another replica can compute missing updates. It is not a database transaction version or an authorization token. Yjs binary updates tolerate duplicate application and reordered delivery when all required updates eventually arrive.

## Separate transport, persistence, and presence

```text
Editor binding ↔ local Yjs document ↔ authenticated sync gateway
                                              ↓
                               durable document update store
                                              ↓
                                    cross-node relay

Presence/cursors ↔ ephemeral awareness channel (expires on disconnect)
Snapshots       ← reconstruct durable CRDT state at a known checkpoint
```

WebSocket connections still have local state even when gateways share a relay. A Redis Pub/Sub backplane can broadcast to connected peers but is not durable replay. A disconnected gateway or client must recover from persisted state, not depend on messages it missed. Document affinity can simplify per-document state and batching; hot documents may need a dedicated fan-out layer. Choose according to measured memory and delivery load rather than assuming either topology eliminates hotspots.

A cursor needs a position representation compatible with concurrent edits, such as the library's relative-position mechanism. Raw character offset 5 becomes stale when someone inserts before it. Awareness expires and is separate from document persistence; throttle/coalesce it and drop stale updates under pressure. Do not persist every cursor merely because durable document updates are stored.

## Persist before claiming an edit is saved

A minimal PostgreSQL log stores binary Yjs updates:

```sql
CREATE TABLE documents (
    document_id uuid PRIMARY KEY,
    tenant_id uuid NOT NULL,
    title text NOT NULL
);
CREATE TABLE document_updates (
    document_id uuid NOT NULL REFERENCES documents(document_id),
    update_id uuid NOT NULL,
    payload bytea NOT NULL,
    accepted_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (document_id, update_id)
);
CREATE TABLE document_snapshots (
    document_id uuid NOT NULL REFERENCES documents(document_id),
    snapshot_id uuid NOT NULL,
    payload bytea NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (document_id, snapshot_id)
);
```

The application checks document permissions and payload limits before writing. A stable update ID suppresses duplicate log rows; CRDT duplicate tolerance separately protects document state. A duplicate ID carrying different bytes is a protocol error, not an identical retry. Timestamps alone do not define a reliable total order or compaction checkpoint.

Acknowledge **saved** only after the selected durable commit. Broadcasting optimistically may improve peer latency, but peers then see work that can still fail persistence; distinguish that state and retain pending local updates for retry. Batching is acceptable if the acknowledgment waits for commit. An in-memory one-second buffer is not a durable write-ahead log, and calling Redis a WAL does not define its persistence or recovery boundary.

Snapshots must contain CRDT state, not just rendered plain text. Recreating a text document from its displayed string discards identifiers needed to merge an offline client's history. Record exactly which durable updates a snapshot includes. Build it from a known checkpoint, publish it atomically, then delete only covered history under a supported compaction/recovery policy. An update arriving during snapshot creation must remain recoverable.

## Offline recovery and authorization changes

Persist unacknowledged local changes where policy permits. On reconnect, authenticate again, recheck current document membership, exchange state, and resend pending changes with stable identities. Use backoff with jitter and bounded payloads to avoid reconnect storms.

A user revoked while offline must not automatically upload edits on return. Decide whether to reject, quarantine, or export their local work; keep rejected local edits visibly separate from saved shared state. Convergence cannot override authorization. Sensitive cached documents also need a retention/logout policy; offline support expands the places data lives.

For large synchronization gaps, send an authorized snapshot plus missing updates. Protect private snapshots at the origin and cache layer rather than exposing a predictable CDN URL. Detect corrupt/incompatible payloads and define a repair path without silently replacing the shared document with one client's string.

## Undo, history, and schema evolution

Undo should generally reverse the current user's intended action while preserving other users' contributions. A global rewind to an earlier snapshot would erase intervening collaborator edits. Use the library's undo facilities with scoped transaction origins and test remote edits interleaved with local undo/redo. An append-only log alone does not establish these semantics.

Version history is a product feature distinct from CRDT merge metadata and per-user undo. Define named revisions and permissions for restoration. Restoring a historical document is a new shared action with its own conflict and audit policy.

Pin compatible shared-data schemas and editor bindings. Renaming a root shared type, changing rich-text attributes, or mixing incompatible binary formats can break clients even when transport succeeds. Gate migrations and test old/offline clients before compacting away compatibility information.

## Decisions, failure cases, and best practices

| Risk | Required boundary |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Relay loses a message | Repair from durable update state; Pub/Sub does not prove delivery. |
| Server dies after commit but before acknowledgement | Client resends the same update; storage and merge tolerate replay. |
| Slow client | Bound send buffers and disconnect for resync rather than accumulate unlimited updates. |
| Hot document | Batch compatible updates and separate viewers from active editors; measure fan-out and state memory. |
| Malformed or hostile update | Enforce size/rate/time budgets, isolate processing, and validate supported schema and permissions. |
| Presence overload | Coalesce or drop presence; preserve durable edit acceptance priority. |

Measure local pending age, persistence latency, peer propagation delay, reconnect repair size, gateway memory, per-document fan-out, slow-client disconnections, snapshot reconstruction time, and rejected updates. Test concurrent insert/delete, duplicate and reordered delivery, save failure, snapshot races, revoked offline users, and per-user undo.

## Summary

Collaborative editing requires a proved reconciliation protocol plus durable synchronization. Yjs can merge concurrent text updates and repair missing state, but the application still owns saved acknowledgments, access control, offline revocation, snapshots, and memory limits. Presence is ephemeral; durable edits and per-user undo need their own explicit contracts.

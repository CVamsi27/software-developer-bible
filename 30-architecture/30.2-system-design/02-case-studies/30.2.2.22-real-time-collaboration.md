# Real-Time Collaboration — System Design Case Study

> **Company-adjacent:** Pitch, Contentful, n8n. Design a real-time collaborative editor where multiple users edit the same document simultaneously.

---

## First Principles

Collaborative editing is conflict resolution with typing latency:

1. **Two editors offline must converge without a server deciding** — CRDTs (merge math) or OT (server-sequenced transforms) are the two resolution theories; the choice defines the whole architecture.
2. **The illusion of simultaneity is engineered**: local-first application (edit now, sync later), with the sync layer guaranteeing convergence — latency hides in the UI, not the protocol.
3. **Presence and awareness are ephemeral by design** — transient channels separate from the durable document log.

## Requirements

**Functional:**
- Multiple users edit the same document simultaneously with <100ms latency.
- Conflict resolution ensures all users converge to the same final state.
- Show ephemeral state: cursors, selections, and presence (who is online).
- Version history, undo/redo, and offline support with sync on reconnect.

**Non-Functional:**
- **Traffic:** 10M DAU, 500K concurrent editors at peak.
- **Scale:** 100K edits/sec globally.
- **Storage:** 1B documents, avg 100KB per document. 100TB base storage + operational logs.
- **Reliability:** 99.99% availability, graceful degradation of presence when under load.

## Data Model

The data model relies on PostgreSQL for durable document state and Redis for ephemeral presence.

```sql
-- Documents metadata
CREATE TABLE documents (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL,
  title VARCHAR(255) NOT NULL,
  latest_version INT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_docs_tenant ON documents(tenant_id);

-- Operational log (The source of truth for changes and undo/redo)
CREATE TABLE document_operations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  document_id UUID NOT NULL REFERENCES documents(id),
  version INT NOT NULL,
  user_id UUID NOT NULL,
  operation_data JSONB NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(document_id, version) -- Concurrency control via unique constraint
);

-- Snapshots (Performance optimization for fast loading)
CREATE TABLE document_snapshots (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  document_id UUID NOT NULL REFERENCES documents(id),
  version INT NOT NULL,
  content JSONB NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(document_id, version)
);
```

## Critical Design Decisions

### 1. Conflict Resolution: OT vs CRDT
- **Option A (OT):** Operational Transformation requires a central server to sequence operations. Smaller payload size but incredibly complex to implement correctly (Google Docs uses this).
- **Option B (CRDT):** Conflict-free Replicated Data Types attach metadata to every character, making operations commutative. No central sequencer needed, but higher memory overhead (Figma, Notion use this).
- **Decision:** **CRDT (Yjs/Automerge)**. Modern libraries have solved the memory bloat problem, and the ease of implementation, peer-to-peer potential, and decentralized nature make it the standard for new collaboration tools.

### 2. WebSocket Connection Management
- **Option A:** Sticky sessions (route all users for Document A to Server A).
- **Option B:** Stateless WebSockets with Redis Pub/Sub backplane.
- **Decision:** **Redis Pub/Sub per document**. Sticky sessions create hot spots and complex rebalancing when a server dies. By having any WebSocket server subscribe to a Redis channel (`doc:<id>`), we decouple the transport layer from the document processing layer.

### 3. Presence and Cursor State
- **Option A:** Store cursor positions and online status in the database alongside document edits.
- **Option B:** Treat presence as purely ephemeral data.
- **Decision:** **Ephemeral State (Redis + WebSockets)**. Cursor updates happen 10x more frequently than document edits. Writing them to PostgreSQL would crush the database. Cursors and selections are broadcast via WebSockets and temporarily held in Redis with a TTL.

### 4. Operational Log for Undo/Redo
- **Option A:** Store full document snapshots on every edit.
- **Option B:** Store an append-only log of operations.
- **Decision:** **Append-only log**. Undo/redo requires knowing exactly what changed. The operational log acts as the source of truth, while periodic snapshots (e.g., every 100 versions) are used to speed up initial document load.

## The Hard Problem: Convergence via CRDTs

The single toughest technical challenge is ensuring that when User A inserts "X" at position 5, and User B concurrently deletes position 5, the document does not permanently diverge. If we rely on simple index positions, latency will corrupt the document.

CRDTs solve this by giving every character a unique, globally sortable identifier (usually a combination of a Lamport timestamp and client ID). Instead of saying "insert at index 5", a CRDT operation says "insert after character ID 12345". Because the operations are mathematically commutative, they can arrive in any order and still result in the exact same final state across all clients. The trade-off is garbage collection: deleted characters leave "tombstones" so future concurrent operations still have a reference point.

## Scaling Bottlenecks

1. **The Thundering Herd on Reconnect:** When a brief network blip disconnects 10,000 users, they all try to reconnect and download missed operations simultaneously.
   *Fix:* Implement exponential backoff with jitter on the client, and serve read-heavy snapshot requests from a CDN or Redis cache.
2. **Hot Documents:** A popular public document with 1,000 concurrent viewers will overwhelm a single Redis Pub/Sub channel or WebSocket node.
   *Fix:* Introduce a fan-out layer where WebSocket servers aggregate operations from local clients before broadcasting to the central pub/sub, reducing message volume (batching).
3. **Database Write Contention:** Inserting every single keystroke into PostgreSQL will exhaust connection pools and write IOPS.
   *Fix:* Batch operations in memory on the WebSocket server and flush them to PostgreSQL asynchronously every second, using a write-ahead log (WAL) in Redis for durability.

## Interview Tips

- **It's a state machine problem:** The interviewer is testing if you understand that collaborative editing is just distributed state synchronization.
- **CRDTs > OT:** Mentioning CRDTs (like Yjs) and explaining *why* they replaced OT for new builds shows modern industry knowledge.
- **Separate durable from ephemeral:** Explicitly split the architecture between durable state (PostgreSQL, document text) and ephemeral state (Redis, cursors, presence).
- **Handling offline:** Explain that offline support isn't just caching; it's queuing operations and doing a CRDT merge upon reconnect.
- **Snapshots are necessary:** Acknowledge that an append-only log of 50,000 keystrokes is too slow to load on a fresh refresh; periodic snapshots are required.

## Summary

1. **The OT vs CRDT decision is the interview's center of gravity** — OT needs a central server to order operations; CRDTs converge without one — Yjs made CRDTs the default for new builds
2. **Concurrent edits must converge to the same document on every replica** — demonstrate the transform function, not just name the algorithm
3. **Presence is a separate lightweight channel** — cursors and avatars ride ephemeral signals (WebSocket + Redis pub/sub), never the durable document log
4. **Snapshots bound history compaction** — periodic checkpointing keeps replay cost flat for long-lived documents
5. **Offline is queued operations replayed on reconnect** — the sync protocol must tolerate reordering and dedupe

# Typeahead / Autocomplete System Design

Autocomplete offers useful completions while someone types. For `net`, it might suggest `network security` or `netflix`. It must return quickly, keep suggestions relevant, and never expose another person's private searches. An old response for `ne` arriving after the response for `net` must never overwrite the newer suggestions:

```text
type "net" → cancel "ne" response → serve "net" candidates only.
```

## Definition

An **autocomplete service** retrieves and ranks **candidate completions** for a partial input using indexed data, with explicit latency, normalization, freshness, and visibility requirements. Each keystroke cancels the in-flight request and issues a narrower lookup, so the client only ever renders candidates for the latest prefix.

> **Textbook Definition:** An autocomplete service retrieves and ranks candidate completions for a partial input using indexed data, with explicit latency, normalization, freshness, and visibility requirements.

## First Principles

1. Many users repeatedly ask about the same short prefixes. Computing every candidate from the full corpus on every keystroke repeats work. A precomputed index can make candidate retrieval cheap, but a tiny fixed list may omit candidates needed for a different region, personal history, or a typo.
2. Typing also creates overlapping requests: an old response for `ne` can arrive after the response for `net`. Backend speed alone cannot prevent the interface showing stale suggestions. Retrieval, ranking, privacy, and response ordering need separate rules.

## Requirements and capacity assumptions

Return a bounded list of public query/entity completions, support selected languages, and record authorized selection signals. Add typo tolerance and personal-history suggestions only with explicit budgets and permissions. Search must still work when autocomplete fails.

Assume 100 million daily users making five searches each, with three suggestion requests per search after client scheduling. That is 1.5 billion requests/day, averaging about 17,361 requests/second; a three-times peak is about 52,083. This is an exercise assumption, not measured capacity. Payload size includes text encoding and protocol metadata, not only visible characters.

For 150 million indexed prefixes, a 12-byte prefix plus ten `(8-byte ID, 2-byte score)` entries gives **112 bytes**, or 16.8 GB of raw entries. Actual memory depends on representation, shared prefix paths, strings, alignment, and runtime overhead. A trie never automatically holds `prefix count × average length` distinct nodes: shared paths reduce that total.

Budget end-to-end latency across client debounce, network, retrieval, optional personalization, and rendering. A 120ms debounce already exceeds a 50ms end-to-end objective before the request begins; distinguish server response time from perceived interaction time.

## The serving path and learning loop

```text
Typing → bounded/debounced request → public candidate index
                                           ↓
                         optional authorized private candidates
                                           ↓
                              bounded ranking / filtering
                                           ↓
                                  current-query UI

Selections / public signals → aggregate / filter → versioned index artifact
                                                     ↓
                                           validate / publish / swap
```

An offline builder produces a versioned index. Online requests retrieve a bounded candidate set, filter visibility, and may rerank it cheaply. Precomputing public candidates avoids expensive full-corpus searches; it never requires every ranking decision to happen offline.

Build statistics for **candidate completions**, not merely the typed prefix. A single count for `net` cannot decide whether `netflix` or `network security` should rank first. Keep locale, corpus/policy version, candidate identity, score inputs, and eligibility boundaries explicit.

## A complete exact-prefix index

This strict TypeScript example stores precomputed top lists at indexed prefixes. It supports exact normalized-prefix lookup only; it makes no fuzzy-search or latency guarantee:

```typescript
interface Suggestion { id: string; text: string; score: number }
function compareCodeUnits(a: string, b: string): number {
  if (a < b) return -1;
  if (a > b) return 1;
  return 0;
}
class PrefixNode {
  children = new Map<string, PrefixNode>();
  suggestions: Suggestion[] = [];
}
function normalizePrefix(value: string): string {
  return value.normalize('NFKC').toLowerCase();
}
class TypeaheadIndex {
  private root = new PrefixNode();

  constructor(entries: ReadonlyMap<string, readonly Suggestion[]>) {
    const indexedPrefixes = new Set<string>();
    for (const [prefix, candidates] of entries) {
      const normalizedPrefix = normalizePrefix(prefix);
      if (indexedPrefixes.has(normalizedPrefix)) {
        throw new Error(`Duplicate normalized prefix: ${prefix}`);
      }
      indexedPrefixes.add(normalizedPrefix);
      const candidateIds = new Set<string>();
      for (const item of candidates) {
        if (!item.id.trim() || !item.text.trim() || !Number.isFinite(item.score)) {
          throw new Error(`Invalid suggestion under prefix: ${prefix}`);
        }
        if (candidateIds.has(item.id)) {
          throw new Error(`Duplicate candidate ID under prefix: ${item.id}`);
        }
        candidateIds.add(item.id);
      }
      let node = this.root;
      for (const character of normalizedPrefix) {
        let child = node.children.get(character);
        if (child === undefined) {
          child = new PrefixNode();
          node.children.set(character, child);
        }
        node = child;
      }
      node.suggestions = candidates.map(item => ({ ...item }))
        .sort((a, b) => b.score - a.score ||
          compareCodeUnits(a.text, b.text) || compareCodeUnits(a.id, b.id))
        .slice(0, 10);
    }
  }

  complete(prefix: string, limit = 8): Suggestion[] {
    if (!Number.isInteger(limit) || limit < 1 || limit > 10) {
      throw new RangeError('limit must be an integer from 1 to 10');
    }
    let node = this.root;
    for (const character of normalizePrefix(prefix)) {
      const child = node.children.get(character);
      if (child === undefined) return [];
      node = child;
    }
    return node.suggestions.slice(0, limit).map(item => ({ ...item }));
  }
}
const index = new TypeaheadIndex(new Map([
  ['ne', [{ id: 'netflix', text: 'netflix', score: 9 }]],
  ['net', [{ id: 'network-security', text: 'network security', score: 8 },
    { id: 'netflix', text: 'netflix', score: 9 }]]
]));
if (index.complete('ＮＥＴ', 1)[0]?.id !== 'netflix') {
  throw new Error('NFKC normalization or score ordering failed');
}
if (index.complete('n').length !== 0) {
  throw new Error('A prefix without a stored list must return no suggestions');
}
const ties = new TypeaheadIndex(new Map([['x', [
  { id: 'entity-b', text: 'Shared name', score: 1 },
  { id: 'entity-a', text: 'Shared name', score: 1 }
]]]));
if (ties.complete('x')[0]?.id !== 'entity-a') {
  throw new Error('Equal scores must use a stable text-and-ID tie-break');
}
const invalidLists = [
  [{ id: '', text: 'candidate', score: 1 }],
  [{ id: 'bad-score', text: 'candidate', score: Number.NaN }],
  [{ id: 'duplicate', text: 'one', score: 1 },
    { id: 'duplicate', text: 'two', score: 2 }]
];
for (const candidates of invalidLists) {
  let rejected = false;
  try {
    new TypeaheadIndex(new Map([['q', candidates]]));
  } catch {
    rejected = true;
  }
  if (!rejected) throw new Error('Invalid candidate data must be rejected');
}
```

Unicode Normalization Form KC (**NFKC**) unifies some compatibility forms, including these full-width Latin letters. Lowercasing is not complete multilingual case folding or a security check; locale-specific rules, accent handling, transliteration, and grapheme boundaries need a consistent policy at build and query time. Reject or merge duplicate normalized prefix entries during building rather than silently publishing colliding definitions.

The example rejects normalization-colliding prefix keys but only demonstrates the serving structure. A production pipeline must bound source and artifact sizes, pin the normalization version used to build the index, and validate visibility policy before publication.

Each candidate holds a stable ID because selection events and authorization refer to an entity, not just its display text. The builder rejects blank IDs or text, non-finite scores, and duplicate IDs within one prefix list. Equal scores use code-unit ordering by text and then ID so two builders never reorder the artifact because their host locales differ. If product ranking requires natural-language ordering, pin the locale and collation version in the artifact metadata.

Traversal visits prefix characters, then copies up to k results. It never searches every descendant at request time. The builder must populate each prefix the service promises to answer; merely storing lists at complete-word terminals leaves shorter prefixes empty.

## Choose retrieval and typo tolerance deliberately

| Structure | Useful property | Boundary |
| ------------------------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Trie / compressed radix tree | Follows shared prefixes and supports precomputed lists | Object overhead and stored top lists can dominate memory. |
| Sorted dictionary | Binary search locates a prefix range | Scanning/ranking a large matching range still costs work. |
| Finite-state transducer (FST) | Compact representation with weighted lookup capabilities | Build/update cost and supported matching depend on the implementation. |
| Search-engine completion index | Engine-managed prefix lookup with implementation-specific fuzzy matching and filters/contexts | Elasticsearch keeps its completion structure in memory; measure per-shard footprint, context coverage, and build/refresh cost. |

A function choosing one child whose grandchild matches a letter is **not** edit-distance search. Substitution, insertion, and deletion affect the remaining prefix differently. Use a supported fuzzy index or a bounded edit-distance traversal with explicit distance, minimum prefix length, candidate count, and time limits. Never let broad fuzzy expansion for a one-character prefix exhaust the service.

For `newtork`, retrieve eligible candidates within the configured typo policy and rank them; never silently claim every edit-distance-two candidate was searched. Separate exact, fuzzy, and fallback results so quality can be measured by path.

## Ranking, private history, and cache keys

Public scores may combine popularity, freshness, entity quality, and abuse signals. A candidate pool larger than the final display list leaves room for regional and personal reranking. Fixed global top-ten truncation can eliminate a relevant candidate before reranking sees it. For tenant-scoped data, retrieve within a visibility context derived from the authenticated caller; filtering only after a global top list is selected can suppress authorized results and expose cross-tenant presence through observable result counts or timing.

Personal history is a separate private source. Derive the user from authenticated credentials, not an `X-User-Id` header or selection payload. Check tenant/entity visibility before returning candidates. Opt-out, retention, deletion, and consent rules are product/policy decisions; a universal 90-day TTL is no privacy guarantee.

Cache **public** candidate lists by normalized prefix, locale/region, corpus version, ranking/policy version, and any other dimension changing eligibility. Personalized responses should bypass shared public caches or use a correctly isolated private cache. A flag saying `personalized=true` is no user-specific key: two users with that flag can otherwise receive each other's results.

A policy removal may need an immediate blocklist/filter while the next full index is built. An hour-old versioned artifact is never allowed to keep serving a revoked private entity merely because cache expiry has not arrived.

## Keep the interface aligned with current input

Debounce or throttle per measured interaction needs; support input-method composition rather than sending half-composed characters. Give each request a generation, and render a response only if its generation still matches the current query. Cancelling the previous request helps reduce work but never replaces that check: cancellation can race with response arrival.

Use an accessible combobox interaction with keyboard navigation, an announced option count, predictable focus, and safe text rendering. Keep ordinary search submission available. For no results or service failure, close or show the appropriate empty state without erasing the user's query. Avoid a new error toast on every keystroke.

A selection event identifies the displayed candidate and index/ranking version. Validate it against the authenticated session or a signed display context where needed, rate-limit ingestion, and deduplicate a stable event ID. Raw prefixes can contain personal information: minimize logging and separate authorized private history from public training signals.

## Freshness, rollout, and failure recovery

Validate each artifact's format, checksum, normalization version, coverage, eligibility, representative results, and memory requirements before publication. A serving process loads a complete new version and swaps one reference so a request sees one consistent index. Account for old and new copies coexisting during the swap; a nominally fitting index may exceed memory during rollout.

Retain a known-good version and pin caches to version identity. Rollback restores an earlier artifact, but still apply current safety/visibility removals. Trend overlays can update sooner than a full rebuild, with their own expiry, abuse checks, and merge rules. Freshness is more than a timer: upstream signal lag, moderation, build, distribution, and cache age all contribute.

| Failure | Recovery |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| Builder produces a bad artifact | Reject before activation; keep the current version and alert on growing age. |
| Personalization dependency fails | Serve authorized generic candidates within the remaining request budget. |
| Popular prefix overwhelms a cold cache | Coalesce builds/loads, bound concurrency, and provision for cache-cold load. |
| Signal pipeline lags | Continue serving with a measured freshness indicator; do not fabricate trends. |
| Out-of-order response | Current-query generation check prevents stale suggestions from replacing newer ones. |

## Best practices and measurement

Track server latency by exact/fuzzy/personalized path, cache-cold behavior, no-result rates by locale, corpus publish age, candidate removal delay, memory during swaps, stale-response suppression, and selection quality. Click-through rate holds position and selection bias; a higher rate alone never proves relevance or user satisfaction. Compare suitable cohorts and include harmful/private suggestion checks.

Load-test the stated traffic and corpus before claiming 52,000 requests/second or p99 below 50ms. The arithmetic establishes a target, not benchmark evidence.

## Summary

Autocomplete separates candidate preparation from a bounded serving path. Exact prefix retrieval, controlled fuzzy search, authorized private history, correct cache dimensions, and current-query response ordering solve different problems. Versioned indexes make publication recoverable, while explicit freshness and visibility policies keep fast suggestions useful and safe.

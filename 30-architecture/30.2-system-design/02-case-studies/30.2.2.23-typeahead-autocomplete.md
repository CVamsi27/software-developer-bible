# Typeahead / Autocomplete System Design

## TL;DR

Design a system that returns top-k relevant suggestions for any prefix in under 100ms — the box that completes your query on Google, YouTube, Amazon, and GitHub.

**Why it matters:** Tests prefix indexing (trie vs sorted arrays vs search-engine completion), offline aggregation of popularity signals into per-prefix top-k lists, geo-sharding, cache-first serving, and the freshness-vs-latency tradeoff. It looks easy and separates candidates who hand-wave ranking from those who can size a trie.

## First Principles

Autocomplete is a latency-bound read with a precomputed soul:

1. **Everything expensive happens offline**: n-gram/trie indexes built from logs and refreshed periodically — the online path is pure lookup, O(prefix), sub-10ms.
2. **Ranking is frequency × recency × personalization** — and must be *precomputed per prefix*, because scoring candidates at query time blows the budget.
3. **Top-k truncation is the memory lever**: only the top ~10 completions per node are served; the tail is worthless at UI scale (→ 30.2.1.17's economics).

## Requirements
### Functional Requirements

- Given a partial query prefix, return k ranked suggestions (default k=8-10)
- Suggestions include completed queries, entities, and trending terms
- Handle typos with fuzzy matching (edit distance ≤ 1-2)
- Personalize results using the user's recent queries/history
- Support multiple languages and scripts
- Trending/breaking topics should surface within minutes
- Log user selections to improve future rankings

### Non-Functional Requirements

- Suggestion latency < 50ms p99 (perceived as instant)
- High availability (99.99%) — typeahead appears on every page; failure must degrade silently
- Scale: 100M+ DAU, ~50K suggestions served per second at peak
- Freshness: popular new terms visible within minutes-to-hours, not days
- No suggestion leakage across users' private data (personalization is opt-out)
- Read-heavy: reads outnumber writes ~1000:1

## Capacity Estimation

```text
Traffic Estimates:

- 100M DAU × ~5 searches/day = 500M searches/day
- Each search fires ~3 typeahead keystroke requests = 1.5B requests/day
- Peak QPS: 1.5B / 86,400s × 3 (peak factor) ≈ ~52K QPS
- Response payload: ~10 suggestions × 30 bytes ≈ 300 bytes

Storage Estimates (offline index):

- Unique prefixes worth indexing: ~150M (after pruning long-tail)
- Each prefix entry: prefix (avg 12B) + 10 suggestions × (8B id + 2B score)
  ≈ 100 bytes → ~15 GB raw index
- Fits in RAM across shards; trie node overhead ~3-5x → ~50-75 GB total
  → trivially sharded across ~10 nodes or kept per-region

Signal Pipeline Estimates:

- Query logs: 1.5B events/day × 200 bytes ≈ 300 GB/day raw
- Aggregated daily: distinct prefixes ≈ tens of millions → few GB

Cache Estimates:

- Top prefixes follow Zipf: top 10% of prefixes serve ~80% of traffic
- Cache top ~1M prefix→suggestions entries (~100 MB) per region in Redis
- Per-user recent-query list: 10 items × 30 B × 100M users ≈ 30 GB (separate store, lazy-loaded)
```

## Database Design
### Schema

The serving index is NOT a relational database — it is an in-memory structure rebuilt by an offline pipeline. The durable stores are:

```sql
-- Aggregated prefix statistics (the ranking source of truth)
CREATE TABLE prefix_stats (
    prefix           VARCHAR(100) NOT NULL,
    region           VARCHAR(16)  NOT NULL,
    query_count_1d   BIGINT DEFAULT 0,
    query_count_7d   BIGINT DEFAULT 0,
    query_count_30d  BIGINT DEFAULT 0,
    last_queried_at  TIMESTAMPTZ,
    updated_at       TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (prefix, region)
);

-- Entity dictionary (products, places, people eligible for completion)
CREATE TABLE entities (
    id          BIGSERIAL PRIMARY KEY,
    text        VARCHAR(200) NOT NULL,
    type        VARCHAR(32) NOT NULL,      -- product | place | person | org
    popularity  FLOAT DEFAULT 0,
    region_whitelist TEXT[],
    active      BOOLEAN DEFAULT TRUE
);
CREATE INDEX idx_entities_text ON entities USING gin (to_tsvector('simple', text));

-- User history for personalization (TTL'd)
CREATE TABLE user_recent_queries (
    user_id     BIGINT NOT NULL,
    query       VARCHAR(200) NOT NULL,
    queried_at  TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (user_id, query)
);
-- TTL via scheduled cleanup: keep last 10 per user, expire after 90 days
```

### Serving Index (in-memory, not SQL)

```text
TRIE over normalized prefixes:

              (root)
             /      \
           n         s
           |         |
           e         h
           |         |
           t* ──┬─── w*
                |
                f*
                |
                l*
                |
                i*
                |
                x*   ← terminal: [netflix:0.97, netflix series:0.71, …]

Each terminal node stores: top-k (text, score) pairs precomputed offline.
Node count ≈ total characters across unique prefixes ≈ 150M × 6 ≈ 900M nodes.
Compressed trie (radix/patricia) collapses chains → ~10x fewer nodes.
```

Alternative serving structures worth naming in an interview:

| Structure | Lookup | Memory | Fuzzy | Notes |
| ----------------------------- | --------------- | ------ | ------------------------- | ------------------------------------------------------------------ |
| Trie / radix tree | O(len) | High | Manual edit-distance walk | Classic answer; supports incremental traversal per keystroke |
| Sorted array + binary search | O(log n + scan) | Low | Prefix range scan only | How Lucene/Elasticsearch Completion suggester works under the hood |
| FST (finite state transducer) | O(len) | Lowest | Limited | Lucene's choice; shares suffixes too |

## Key Components

### In-Memory Trie with Precomputed Top-k

```typescript
interface Suggestion {
  text: string;
  score: number;
}

class TrieNode {
  children = new Map<string, TrieNode>();
  suggestions: Suggestion[] | null = null; // only on terminal-ish nodes
}

export class TypeaheadIndex {
  private root = new TrieNode();

  static build(entries: Map<string, Suggestion[]>): TypeaheadIndex {
    const idx = new TypeaheadIndex();
    for (const [prefix, suggestions] of entries) idx.insert(prefix, suggestions);
    return idx;
  }

  insert(prefix: string, topK: Suggestion[]): void {
    let node = this.root;
    for (const ch of prefix.normalize('NFKC').toLowerCase()) {
      let child = node.children.get(ch);
      if (!child) {
        child = new TrieNode();
        node.children.set(ch, child);
      }
      node = child;
    }
    node.suggestions = topK.slice(0, 10); // precomputed offline
  }

  complete(queryPrefix: string, limit: number): Suggestion[] {
    const norm = queryPrefix.normalize('NFKC').toLowerCase();
    let node = this.root;
    for (const ch of norm) {
      node = node.children.get(ch) ?? this.fuzzyStep(node, ch);
      if (!node) return [];
    }
    return (node.suggestions ?? []).slice(0, limit);
  }

  // One edit-distance step: substitution, insertion, deletion
  private fuzzyStep(node: TrieNode, expected: string): TrieNode {
    const candidates: TrieNode[] = [...node.children.values()];
    return candidates.find((c) => c.children.has(expected)) ?? null;
  }
}
```

The crucial design point: **ranking happens offline**. The online path does zero scoring beyond slicing a precomputed list — that is how you hit sub-millisecond lookups.

### Offline Top-k Aggregation

```typescript
// Stream job: consume clicks/searches -> maintain counts -> emit top-k per prefix
import { MinHeap } from './heap';

function topKForPrefix(counts: Map<string, number>, k: number): Suggestion[] {
  const heap = new MinHeap<Suggestion>((a, b) => a.score - b.score);
  for (const [text, count] of counts) {
    const score = Math.log(1 + count); // dampen mega-popular terms
    if (heap.size() < k) {
      heap.push({ text, score });
    } else if (score > heap.peek().score) {
      heap.pop();
      heap.push({ text, score });
    }
  }
  return heap.drainSorted().reverse();
}
```

Score blending (what makes results feel smart):

```text
final_score =
    w1 * log(queries_7d)          # popularity
  + w2 * recency_decay(last_seen) # freshness
  + w3 * entity_quality(popularity)
  + w4 * trend_zscore_24h         # breaking-topic boost
  − penalty(low_quality_source)   # spam/gibberish suppression
```

### Geo-Sharded Indexes

Popularity is regional ("football" means different things in Manchester and São Paulo). Options compared:

| Approach | Consistency of ops | Latency | Complexity |
| ------------------------------- | ----------------------- | ------------------------- | ---------- |
| Single global index | Simple deploys | Ignores locale | Low |
| **Per-region indexes (chosen)** | N parallel pipelines | Best relevance | Medium |
| Per-country fine sharding | Very high pipeline cost | Marginal gain over region | High |

Region-level granularity captures most relevance gains at manageable operational cost. A small global overlay serves cross-regional trends.

### Personalization Layer

Two-phase re-ranking keeps the hot path fast:

```typescript
async function suggest(req: SuggestRequest): Promise<Suggestion[]> {
  const base = index.complete(req.q, req.limit + 5); // cheap: in-memory
  if (!req.userId || !personalizationEnabled(req)) return base.slice(0, req.limit);

  // Phase 2 (only when personalized): blend in user's own vocabulary
  const history = await userHistory.topTerms(req.userId, 10); // Redis, ~2ms
  const boosted = base.map((s) => ({
    ...s,
    score: s.score * (history.matches(s.text) ? 1.35 : 1),
  }));
  return boosted.sort((a, b) => b.score - a.score).slice(0, req.limit);
}
```

Privacy rules: personalization must be opt-out-able, history TTL'd aggressively (90d), and never used to leak one account's queries into another's session.

## Caching Strategy

Three tiers, hottest first:

```text
L0  Browser/CDN:      full response cached 60s keyed by (q, geo, anon-personalization)
L1  Local in-process: prefix→topk map, 5-min refresh, ~50 MB per pod
L2  Redis cluster:    shared prefix→topk + user-history hashes

Hit path target: >90% served by L0+L1 without touching the trie walk
Invalidation: none needed per-request — indexes swap wholesale on publish;
              Redis entries carry index-version tags and age out naturally
```

Debouncing on the client (fire after 100-120ms idle) cuts request volume ~60% and matters more than any backend tweak for perceived latency.

## Message Queue

Kafka topics feeding the learning loop:

```text
Topics:
├── suggest.query.logged     (every served request: prefix, geo, latency)
├── suggest.selected         (which suggestion won — the strongest signal)
├── suggest.noresult         (zero-hit prefixes → coverage gap alerts)

Consumers:
├── stats-aggregator   → rolling counts into prefix_stats
├── quality-monitor    → no-result rate per locale; CTR per position
├── abuse-filter       → injection attempts, gibberish flooding
```

Selection events are weighted far above impressions: a click says "this completion was right," an impression says nothing.

## Scaling Strategy

```text
Read scaling:
• Stateless suggest services behind LB — scale horizontally on CPU
• Zipf distribution means L1 caches absorb most load; provision for cache-cold bursts
• Shard the INDEX by first character(s) if it outgrows one box:
    shard("a".."m") -> node pool A ; shard("n".."z") -> pool B
  (rarely needed below ~1B prefixes)

Freshness scaling:
• Hourly incremental index publishes for top prefixes (streaming updates)
• Daily full rebuild for the long tail
• Breaking news path: manual/automated "trending injection" API writes
  directly into next artifact version (minutes, not hours)

Write path (logging):
• Fire-and-forget beacon ingestion; Kafka partitions by region
• Backpressure acceptable: losing some analytics beats slowing search
```

## Failure Handling

| Failure | Mitigation |
| ------------------------------------ | ---------------------------------------------------------------------------------- |
| Index build fails | Keep previous artifact version serving (blue/green artifacts) |
| Redis down | L1 local cache still serves top prefixes; skip personalization |
| Suggest service down | Client hides the dropdown; search box still works — silent degradation |
| Corrupt/ranked-gamed index | Canary region validates CTR/no-result metrics before global promote; auto-rollback |
| Hot prefix stampede (celebrity name) | CDN absorbs; request coalescing at edge; static fallback list |

Graceful degradation ladder: personalized → generic → cached-generic → nothing. Every rung still leaves the site functional.

## Trade-offs

| Decision | Option A | Option B | Choice |
| --------------------- | --------------------------- | ------------------------------------- | ----------------------------------------------------------------------- |
| Serving structure | Trie in memory | Elasticsearch completion | Trie (predictable p99, no cluster ops); ES wins if fuzzy needs dominate |
| Ranking time | Online scoring | **Offline precomputed top-k** | Offline — online path stays O(prefix length) |
| Index update cadence | Real-time streaming updates | **Hourly incremental + daily full** | Hybrid — real-time ranking consistency is a research project |
| Geo strategy | Global index | **Per-region indexes** | Regional — relevance gain justifies pipeline duplication |
| Fuzzy matching | Full Levenshtein automaton | **One-edit trie steps + client-side** | Cheap fuzzy now, upgrade when data demands |
| Personalization scope | Deep ML ranker | **Lightweight history boost** | Start light; measure lift before ML investment |

## Summary

Typeahead design reduces to three insights: (1) separate the **learning loop** (log signals, aggregate popularity offline) from the **serving path** (precomputed top-k behind O(prefix-length) lookups); (2) exploit Zipf — cache aggressively because a sliver of prefixes carries most traffic; (3) treat the index as a versioned artifact published atomically, which makes rollbacks trivial and freshness a scheduling problem rather than a consistency problem. Regional indexes buy localization; personalization layers on top without touching the core.

Key takeaways:

1. Offline ranking + online lookup = the latency story

2. Trie (or FST) holds the prefix space; top-k lives on nodes, not computed live

3. Kafka selection events are the ranking fuel; CTR collapse alarms guard bad publishes

4. Geo-sharding at region granularity balances relevance vs pipeline cost

5. Degrade silently: no-result beats error toast on every keystroke

This design sustains ~50K QPS with p99 under 50ms while refreshing trends within an hour.

## Cheat Sheet
```text
TYPEAHEAD SYSTEM DESIGN CHEAT SHEET
===========================================================

CORE ARCHITECTURE:
  - Offline pipeline aggregates query/click signals into
    per-prefix top-k lists (score = log(count) + recency + trend)
  - Online service = read-only in-memory trie + L1/L2 caches
  - Index published as immutable versioned artifact; atomic swap

SCALE NUMBERS:
  - 100M DAU, 3 keystroke reqs/search -> ~50K QPS peak
  - Index ~15GB raw (compressed trie), fits RAM, shard by char
  - Top 10% prefixes = 80% traffic (Zipf) -> cache-first design

KEY DECISIONS:
  - Rank OFFLINE, slice ONLINE (sub-ms lookups)
  - Region-level geo shards for localization
  - Sticky caching: CDN 60s + local 5min + Redis
  - Debounce client 100-120ms (cuts volume ~60%)

FRESHNESS:
  - hourly incrementals (top prefixes), daily full rebuild
  - trending-injection API for breaking topics (minutes)

INTERVIEW TIPS:
  - Name the alternatives: FST/Lucene completion, sorted array
  - Explain why not real-time ranking (consistency cost)
  - Mention privacy: opt-out personalization, TTL'd history
  - Guard rails: canary CTR check before index promote
```

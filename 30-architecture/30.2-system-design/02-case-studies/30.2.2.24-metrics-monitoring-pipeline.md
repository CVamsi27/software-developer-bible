# Metrics & Monitoring Pipeline System Design

Fifty thousand targets emit samples every 15 seconds: 1.67 million samples per second across 25 million series. One request-ID label would multiply that into a series per request and exhaust a system handling the sample rate comfortably. Cardinality is the first design constraint:

```text
1.67M samples/s, 25M series → a request-ID label would explode cardinality.
```

## Definition

A **metrics pipeline** collects **measurements** such as request counts, queue depth, and response time, then makes them available for dashboards and alerts. A graph is useful only when the reader knows what its values measure, how fresh they are, and which samples are missing.

> **Textbook Definition:** A metrics pipeline ingests time-stamped measurements, groups them into series, and supports aggregation and retention under bounded cardinality, lateness, and query-cost policies.

## First Principles

1. A metric name plus its labels identifies a time series. Adding a label value creates another series, so memory and index costs grow with distinct combinations, not just the number of metric names. A request-ID label can create one series per request and exhaust a system handling the sample rate comfortably.
2. Collection, durable acceptance, query visibility, and alert evaluation happen at different times. Buffering absorbs a temporary overload but also delays detection. Retention and downsampling reduce cost by discarding detail, which limits what future queries can reconstruct.

## Requirements and capacity assumptions

Collect through authenticated push protocols and discovered scrape targets. Support counters, gauges, and histograms; preserve metric units and temporality. Provide tenant-isolated range queries, bounded query cost, retention, and alert routing. Treat application latency and missing telemetry as different signals.

Assume 50,000 targets with 500 active series each, sampled every 15 seconds. That is 25 million active series and about 1.67 million samples/second. Timestamp plus numeric value at 16 bytes each gives 26.7 MB/s, **excluding** labels, transport envelopes, and batch encoding. If every point carried another 200 bytes of identity metadata, raw bandwidth would instead approach 360 MB/s. Chunk encoding can amortize identity and compress samples; it never removes metadata and index costs.

Assume all 25 million series persist and the system retains three representations concurrently: seven days of 15-second samples, 30 days of one-minute rollups, and 390 days of five-minute rollups. At an illustrative 1.5 compressed bytes/sample, those tiers occupy about 1.512 TB, 1.620 TB, and 4.212 TB, respectively. Their value-only total is 7.344 TB before indexes, active-head memory, replication, rollup fields, and object-store overhead; the total counts each resolution tier even where their time ranges overlap. A rollup with count/sum/min/max stores more than one number per bucket.

Five hundred dashboards with ten panels refreshing every 30 seconds generate about 167 panel queries/second. Query cost also depends on selected series, time span, resolution, and aggregation. A single unrestricted label matcher can cost more than thousands of narrow queries.

## How collection becomes an alert

```text
Scrape targets / push agents → validation + tenant limits
                                      ↓
                           durable acceptance / buffer
                                      ↓
                           time-series writers
                             ↓                 ↓
                     query frontend       sealed blocks
                             ↓                 ↓
                     rule evaluator       compaction / rollups
                             ↓
                    alert routing / grouping / notification

Independent synthetic probe → separate notification route
```

Pull collection discovers targets and observes scrape success. It still requires reachable networks, timeouts, and synchronized load control; it never inherently eliminates request bursts. Push works across suitable outbound network paths but needs buffering/backpressure and liveness signals. Prometheus remote write, the OpenTelemetry Protocol (OTLP), and StatsD hold different transport and acknowledgment semantics; one generic JSON endpoint is no implementation of all three.

Start with an established time-series system when it fits. A broker-based custom ingestion layer is a choice for decoupling and replay, not a prerequisite for every monitoring deployment.

## Preserve metric meaning

| Type | Meaning | Aggregation boundary |
| ---------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Counter | A cumulative event total in Prometheus; an OpenTelemetry Sum may be delta or cumulative | Interpret resets and temporality per series before summing rates. |
| Gauge | A current level, such as queue depth | Min/max/mean/last answer different questions; averaging can hide spikes. |
| Histogram | A distribution represented by classic buckets or a native histogram | Interpret temporality and bucket schema before merging; aggregate compatible rates before quantiles. |
| Summary quantile | Quantile computed by an instrumented process | Averaging instance 99th percentiles (p99s) never gives the population p99. |

Cumulative histogram samples are not independent interval observations. Summing every scraped cumulative bucket repeatedly counts the same events. Calculate compatible deltas/rates with reset handling, or retain an encoding supporting the desired query. Native histogram layouts and classic bucket boundaries require their own compatibility rules.

OpenTelemetry sums and histograms declare **delta** or **cumulative** aggregation temporality. Delta points describe non-overlapping intervals; cumulative points describe an accumulated interval from a start time. Converting between them is stateful: preserve start times, gaps, and resets rather than treating a delta as a cumulative sample. The current OpenTelemetry data model defines these stream boundaries explicitly.

Where the instrumentation library and backend support them, Prometheus recommends native histograms for distribution metrics. They keep a histogram in one composite series and avoid classic histograms' separate time series per bucket. The alert example below deliberately shows the widely supported classic-bucket form; native-histogram queries omit the `le` label and aggregate the histogram sample directly.

A gauge rollup can retain `(count, sum, min, max, last)` rather than only a mean. The mean of means is wrong when bucket sample counts differ: two samples averaging 10 and one sample averaging 100 produce a combined mean of 40, not 55. Irregular sampling may require a time-weighted average instead of an arithmetic sample mean.

Keeping only the last counter value in a large bucket can hide a reset inside it. Preserve enough reset/delta information for the promised rates. Downsample only after defining the queries it must support.

## Cardinality limits need an exact admission boundary

In Prometheus, a series is identified by its metric name and complete normalized label set; a multi-tenant backend adds tenant scope. An OpenTelemetry stream also carries resource attributes and instrumentation scope, while point attributes further distinguish its time series. Preserve these fields in the mapped identity or deliberately merge them through an aggregation view. Validate metric type, unit, temporality, and histogram schema as compatible metadata; version intentional schema changes. A hash speeds indexing, but collision handling and the full identity remain necessary. Never silently remove meaningful dimensions to make quota counts smaller.

A Bloom filter can say **definitely absent** or **possibly present**. A possible match is no proof that a series was already admitted: a false positive can otherwise bypass the quota. Use the filter as a lookup optimization and confirm admission in an exact registry.

In transaction pseudocode:

```text
validate tenant, metric name, labels, sample semantics, and batch limits
canonicalize series identity
look up exact tenant-scoped registry
if new: atomically claim identity and reserve one quota unit
record durable sample acceptance according to the storage contract
return explicit accepted/rejected results
```

The claim and quota reservation must avoid two gateways counting the same new series twice or admitting different series past the limit. Define active-series expiry and churn limits; an attacker can create and expire identities repeatedly while staying below the instantaneous limit. Reserving a quota unit before rejecting an invalid sample leaks capacity unless rolled back or released.

Validate numeric semantics by protocol and metric type. Prometheus text samples and OpenMetrics permit `NaN`, `+Inf`, and `-Inf`, but OpenMetrics never uses `NaN` to mean missing data. Prometheus marks staleness internally with a special NaN bit pattern distinct from an ordinary NaN value. Never apply one finite-number check to every protocol; enforce type-specific rules, such as rejecting NaN counter totals and negative histogram bucket counts. Bound label bytes, labels per series, payload size, new-series rate, sample rate, and tenant retention independently.

## Durable acceptance, ordering, and replay

An accepted response states a durability boundary, not merely that a local send function was called. Await the selected broker/store acknowledgment and report partial rejection explicitly. Stable producer/sample identity and storage rules distinguish identical retries from conflicting values at the same timestamp.

Keep source sample time and collector receive time separate: the first says when the measurement applies, while their difference measures ingestion lag. Use sample time for event-time queries and receive time to detect delayed arrivals. Partitioning by tenant-plus-series identity can preserve broker order for one series, but never sorts sample timestamps or prevents a producer sending old samples. Specify late/out-of-order policy, clock-skew handling, replay deduplication, and maximum backlog age.

A writer commits its durable state before advancing the recovery checkpoint under a consistent protocol. A broker replication factor of three alone never guarantees lossless acceptance; producer acknowledgment, in-sync replica policy, persistence, consumer checkpointing, and replay retention all matter. Size partitions from bytes and processing cost: 26.7 MB/s divided by 256 is about 104 KB/s each before overhead, not 7 KB/s.

## Query isolation and truthful freshness

Authenticate queries and restrict tenant scope outside user-controlled query text. Cache keys include tenant, permissions/policy version, expression, time range, step, and relevant data generation. Omitting tenant from an otherwise correct range-query key can expose another team's metrics.

Bound selected series, regex cost, time span, result points, concurrent work, and memory. Use fair queues and separate alert evaluation budgets from interactive dashboards. Cache-coalescing reduces identical concurrent work; it cannot turn different queries into one or guarantee that a cache never misses during an incident.

Mark stale or incomplete results. No sample differs from zero: zero traffic, a failed scraper, and a disconnected agent can look similar without separate collection-health signals. Never clear an incident merely because its input disappeared.

## Evaluate rules and route alerts separately

A rule evaluator calculates conditions and tracks pending/firing state. An Alertmanager-style component groups, deduplicates, silences, and routes those alerts; it is not the PromQL evaluation engine.

For example, this Prometheus Query Language (PromQL) alert-rule group flags a classic histogram's p99 above half a second for five minutes:

```yaml
groups:
  - name: api-latency
    rules:
      - alert: HighApiLatency
        expr: histogram_quantile(0.99, sum by (service, le) (rate(http_request_duration_seconds_bucket{service="api"}[5m]))) > 0.5
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: API p99 latency has remained above 0.5 seconds
```

It assumes compatible bucket boundaries and suitable sample volume; the quantile is an estimate. It needs a separate missing-data rule. Never average per-instance p99 values to replace the histogram aggregation.

For native histograms, remove the `le` label from the aggregation: `histogram_quantile(0.99, sum by (service) (rate(http_request_duration_seconds[5m]))) > 0.5`.

Prometheus tracks an alert for each label set returned by its expression. A `for` duration requires that alert identity to remain present at each evaluation; an empty result is not a zero value, and a disappearing result normally clears the alert unless `keep_firing_for` is configured. A query error or skipped evaluation is an evaluator-health problem, not evidence that the service recovered. Define restart restoration and rule-version behavior. Multiple evaluators can be legitimate high-availability replicas if notification identity and deduplication are correct; a blanket rule that two evaluators must never process one group is unnecessary.

End-to-end detection includes scrape interval, ingestion lag, evaluation interval, `for` duration, and notification delay. A five-minute pending duration cannot meet a 30-second total detection promise, even when processing after data arrival takes less than 30 seconds.

## Retention, rollups, and recovery choices

Compaction publishes a complete replacement block before retiring source blocks and records which generation/checkpoint it covers. Rebuilding after a bug requires retained inputs; deleting raw history before the correction closes that recovery path. Keep rollup definitions versioned and distinguish partial buckets at window edges.

| Failure | Recovery boundary |
| ------------------- | ------------------------------------------------------------------------------------------------- |
| Writer loses a node | Replay durable accepted input within retention and deduplicate; measure backlog catch-up. |
| Cardinality surge | Reject new series under exact per-tenant limits while preserving already admitted traffic fairly. |
| Query overload | Enforce budgets and prioritize rule evaluation; dashboards may show honest stale data. |
| Alert route fails | Retry/deduplicate notifications and probe the full route independently. |
| Storage fills | Apply backpressure or declared loss policy; an in-memory head is finite. |

Self-hosted versus managed systems depends on operating cost, team capability, query/cardinality needs, and retention. A universal cutoff at 5,000 series or a fixed 24 TB total is no valid decision rule.

## Best practices and measurement

Monitor accepted/rejected points, active series and churn, backlog age, newest query-visible timestamp, late-sample rejection, compaction failures, query cost, evaluation gaps, and notification delivery. A `/health` probe alone cannot establish that a sample travels through ingestion, evaluation, and paging; use a synthetic end-to-end signal and an independent escalation path.

Test counter resets, unequal gauge bucket weights, cumulative histogram handling, duplicate replay, quota races, missing data, tenant cache isolation, and rule failover. Load-test representative label distributions and queries before claiming throughput or availability.

## Summary

Metrics pipelines preserve measurement meaning across collection, durable storage, aggregation, and alerting. Exact series admission limits cardinality; type-aware rollups retain the information promised to queries. Tenant-isolated caches, explicit missing-data behavior, separate rule evaluation and routing, and independent end-to-end probes keep monitoring useful during the failures it must reveal.

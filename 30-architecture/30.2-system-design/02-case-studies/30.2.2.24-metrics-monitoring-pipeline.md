# Metrics & Monitoring Pipeline System Design

## TL;DR

Design the telemetry backbone that ingests millions of metric points per second, stores them in a time-series database with tiered retention, downsamples aggressively, and evaluates alert rules at scale without melting — the system behind every dashboard and pager you have ever received.

**Why it matters:** Combines high-throughput ingestion (Kafka), cardinality management (the #1 operational killer of TSDBs), storage economics (downsampling + retention tiers), and alert evaluation (sharded rule engines). Interviewers use it to test whether you understand that monitoring systems themselves must survive the outage they are diagnosing.

## Requirements
### Functional Requirements

- Accept metrics via push (agents, OTLP, StatsD) and scrape targets (Prometheus pull model)
- Support counter, gauge, histogram, and summary metric types
- Query API: range queries, aggregation (sum/avg/percentile), grouping by labels
- Evaluate alert rules continuously; fire notifications with deduplication
- Downsample raw data over time; expire per retention policy
- Multi-tenancy: team namespaces with quotas
- Dashboards render < 2s for typical 1h windows

### Non-Functional Requirements

- Ingestion: 1M+ unique series updates/sec sustained, 5x burst headroom
- Query latency: p95 < 500ms for 1h window, < 3s for 30d rollups
- Ingestion availability > 99.99% (monitoring must not be the thing that's down)
- Alert evaluation delay < 30s from data arrival
- Retention: 15s raw for 7d, 1m for 30d, 5m for 13 months
- Durability: buffered writes survive broker restarts; acceptable to lose < 10s of tail data in catastrophic failure (it is telemetry, not payments)

## Capacity Estimation

```text
Ingestion Estimates:

- 50K hosts/pods × 500 series each = 25M active series
- Average sample rate: 1 per 15s → 25M / 15 ≈ 1.7M points/sec
- Each point: metric name+labels (~200B) + timestamp (8B) + value (8B)
  → compressed typically ~1-2 bytes/value with chunking (Gorilla-style)
- Raw ingest bandwidth: ~1.7M × 16B ≈ 27 MB/s uncompressed,
  ~3-6 MB/s after compression

Storage Estimates:

- Raw (7d @15s):   25M series × 40,320 samples × 1.5B ≈ 1.4 TB
- 1m rollup (30d): 25M series × 43,200 samples × 1.5B ≈ 1.6 TB
- 5m rollup (13mo):25M series × 112K samples  × 1.5B ≈ 4.2 TB
- Total steady-state ≈ 8 TB (+ replication factor 3 → ~24 TB) — very manageable;
  cardinality mistakes are what blow this up (see below)

Cardinality Reality Check:

- One unbounded label (user_id on every metric!) → +100M series/day = disaster
- Budget: unique series count is THE capacity metric, not bytes

Query Load:

- 500 concurrent dashboards × refresh 30s × 10 panels = ~170 QPS query path
- Alert engine: 5K rules × eval every 30s = ~170 QPS steady + range reads
```

## Database Design
### Schema

Time-series databases invert relational assumptions: index on (series identity + time), append-only writes, no cross-row transactions.

```text
Logical layout inside a TSDB (e.g., Prometheus/VictoriaMetrics/M3 style):

Series identity (hashed):
┌───────────────────────────────────────────────────────┐
│ __name__="http_requests_total"                        │
│ service="api", method="POST", status="500", pod="…"   │
│                    → seriesID = hash(all labels)      │
└───────────────────────────────────────────────────────┘

Time-partitioned chunks per series:
┌───────────────────────────────────────────┐
│ chunk    │ chunk    │ chunk    │ chunk    │
│ t0..t2h  │ t2h..t4h │ ...      │ head     │
│ (immutable)         │          │(writable)│
└───────────────────────────────────────────┘
        │ sealed chunks → object storage blocks (Thanos/M3 style)
        ▼
   [block 2026-08-18] [block 2026-08-19] …  ← compaction + downsampling jobs
```

```sql
-- Metadata side tables (control plane stays relational)
CREATE TABLE tenants (
    id              BIGSERIAL PRIMARY KEY,
    name            VARCHAR(64) UNIQUE NOT NULL,
    max_series      BIGINT DEFAULT 1000000,     -- cardinality quota
    max_ingest_rps  BIGINT DEFAULT 50000,
    raw_retention   INTERVAL DEFAULT '7 days',
    rollup_retention INTERVAL DEFAULT '13 months'
);

CREATE TABLE alert_rules (
    id           BIGSERIAL PRIMARY KEY,
    tenant_id    BIGINT REFERENCES tenants(id),
    name         VARCHAR(128) NOT NULL,
    expr         TEXT NOT NULL,               -- PromQL-ish
    for_duration INTERVAL NOT NULL DEFAULT '5 minutes',
    severity     VARCHAR(16),
    enabled      BOOLEAN DEFAULT TRUE,
    updated_at   TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (tenant_id, name)
);
```

Push vs pull deserves its own verdict: **pull** (Prometheus-style) gives free service-discovery-based health checks and avoids thundering herds, but struggles across network boundaries; **push** (OTLP/cloud agents) traverses NAT/K8s boundaries naturally but needs backpressure discipline. Production platforms run both paths into one buffer.

## Key Components

### Ingestion Gateway with Cardinality Guard

```typescript
const MAX_SERIES_PER_TENANT = 1_000_000;

async function ingest(batch: MetricBatch): Promise<IngestResult> {
  const tenant = await tenants.resolve(batch.apiKey);
  let accepted = 0, rejected = 0;

  for (const sample of batch.samples) {
    const normalized = normalizeLabels(sample); // sort labels, drop empties
    const seriesId = hashSeries(normalized.labels);

    // Cardinality explosion protection — reject BEFORE Kafka
    if (!(await cardinalityCache.mightContain(tenant.id, seriesId))) {
      if (!(await tenantStore.reserveSeries(tenant.id))) {
        rejected++;
        metrics.increment('ingest.rejected', { reason: 'cardinality_quota' });
        continue;
      }
      await cardinalityCache.add(tenant.id, seriesId); // bloom-filter style
    }
    validateValueRange(sample.value); // NaN/Inf guards
    producer.send({ key: seriesId, value: sample }); // partition by series hash
    accepted++;
  }
  return { accepted, rejected };
}
```

Key decisions: reject at the edge (bad series must never reach storage), partition by series hash so one series lands on one writer (per-series ordering + writer-local compression), and make the gateway stateless so it scales horizontally.

### Downsampler

```typescript
// Runs as a periodic compactor over sealed blocks
async function downsample(block: Block, target: Resolution): Promise<Block> {
  const out = new BlockWriter(target);
  for (const series of block.series()) {
    const buckets = groupByWindow(series.points(), target.intervalMs);
    for (const [, points] of buckets) {
      switch (series.type) {
        case 'counter':
        case 'cumulative':                      // keep last (monotonic)
          out.append(series.id, last(points));
          break;
        case 'gauge':                           // avg preserves level info
          out.append(series.id, average(points));
          break;
        case 'histogram':                       // merge bucket counts
          out.append(series.id, mergeHistograms(points));
          break;
      }
    }
  }
  return out.seal();
}
```

Aggregation-type awareness matters: averaging counters or summing gauges produces silently wrong graphs — a classic senior-level gotcha.

### Alert Evaluation Engine

```typescript
class RuleGroupEvaluator {
  constructor(private group: RuleGroup, private queryEngine: QueryEngine) {}

  async tick(): Promise<void> {
    const results = await this.queryEngine.evalRange(this.group.expr, lookback(this.group));

    for (const rule of this.group.rules) {
      for (const [labels, value] of results.series()) {
        const key = `${rule.name}:${hash(labels)}`;
        const state = this.pending.get(key);

        if (!rule.condition(value)) {            // condition cleared
          if (state?.firing) notifier.resolve(rule, labels);
          this.pending.delete(key);
          continue;
        }
        const since = state?.since ?? Date.now();
        this.pending.set(key, { since });

        if (Date.now() - since >= rule.forMs && !state?.notified) {
          notifier.fire(rule, labels, value);    // dedup handled downstream
          this.pending.set(key, { since, notified: true });
        }
      }
    }
  }
}

// Sharding: hash(ruleGroup.name) % numEvaluators, with leader election
// per shard-group for HA — two evaluators must never own one group.
```

The `for` duration prevents flapping; the pending-state map survives evaluator restarts via a small state snapshot; Alertmanager-style routing then deduplicates, silences, and routes by label (`team=payments` → their PagerDuty).

## Caching Strategy

```text
Query cache layers:
L1  Frontend result cache: full query_range responses, TTL 30-90s
    keyed by (query, start, end, step) — absorbs dashboard stampedes
L2  Chunk cache (Redis/memcached): decompressed chunks by (series, timerange)
Negative caching: empty results cached briefly too — most label combos are empty!

Write-path buffering:
• Head block in writer memory (2h) — absorb write bursts
• WAL on local NVMe before Kafka ack consideration for replay
```

Dashboard refresh storms are the read-path's worst enemy: 500 engineers opening the same board after an incident multiplies one query by hundreds. The frontend result cache converts that into ~1 backend query.

## Message Queue

Kafka is the shock absorber between collection and storage:

```text
Topic design:
├── metrics.raw        partitions=256, key=seriesHash, RF=3, retention 72h
├── metrics.dlq        malformed/unparseable batches for forensics
└── alerts.events      fired/resolved notifications (audit trail)

Why Kafka here:
• Writers can restart/deploy without losing in-flight telemetry
• Replay: re-run downsampling after fixing an aggregation bug
• Backpressure: ingestion slows gracefully rather than dropping blindly
• Partition-by-series keeps per-series ordering + even load

Sizing note: 256 partitions × ~7 KB/s each ≈ comfortable consumer units;
more partitions = more file handles & leader elections, not free parallelism.
```

## Scaling Strategy

```text
Horizontal levers, in order of application:
1. Gateways: trivially stateless — scale on CPU/connection count
2. Kafka partitions: sized for peak ingest, rarely touched later
3. Writers: scale with ACTIVE SERIES (cardinality), not just points/sec
4. Query frontends: scale on dashboard concurrency; add result-cache hit ratio first
5. Compactors: scheduled, idempotent — run sharded by time-block

Vertical/federation patterns:
• Hierarchical federation: regional aggregators push rollups to global cluster
  (global views query aggregates, never raw cross-region)
• Cell architecture: independent stacks per business unit; blast-radius isolation
  for both cardinality accidents and bad deploys
```

## Failure Handling

| Failure                     | Mitigation                                                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------------- |
| Writer node loss            | Kafka replays unacked partitions to surviving writers; blocks replicated to S3                 |
| Kafka broker loss           | RF=3 + min.insync.replicas=2; producers retry; brief duplication filtered by idempotent writes |
| Cardinality bomb deployed   | Per-tenant quotas reject at gateway; alert on series-count growth slope (>5%/hour)             |
| Alert evaluator dies        | Shard leadership re-elected; pending-state snapshot restores `for` timers                      |
| Query storm (runaway regex) | Per-query timeouts + label-match limits; query queue with fairness per tenant                  |
| Storage layer slow          | Head block buffers; dashboards degrade to stale-cached results with "stale" badge              |

Monitoring-the-monitor: a tiny always-on external probe checks `/health` of the whole pipeline and alerts through an INDEPENDENT channel (SMS provider ≠ pipeline being monitored).

## Trade-offs

| Decision         | Option A                 | Option B                     | Choice                                                                              |
| ---------------- | ------------------------ | ---------------------------- | ----------------------------------------------------------------------------------- |
| Collection model | Pull (Prometheus)        | Push (agents/OTLP)           | Both — pull for infra health, push for app/custom + boundary crossing               |
| Storage          | Self-hosted TSDB cluster | Managed (Datadog/CloudWatch) | Self-host for cost/cardinality control at this scale; managed wins under ~5K series |
| HA strategy      | Replicate raw (RF=3)     | Dual-scrape pairs            | RF=3 through Kafka — cheaper than double-scraping everything                        |
| Downsampling     | On-write (write both)    | On-compaction (later)        | On-compaction — raw disk freed early, single write path                             |
| Alert placement  | Central rule engine      | Edge/local evaluators        | Central with sharding — consistent state, simpler dedupe                            |

## Summary

A metrics pipeline is four subsystems wearing one name: collection (pull+push gateways), transport (Kafka absorbing bursts and enabling replay), storage (TSDB with cardinality-guarded ingestion, time-partitioned blocks, and type-aware downsampling), and reaction (sharded alert evaluation with deduped routing). The two numbers that decide success are active-series count (capacity) and alert-eval delay (freshness). Design monitoring to survive its own outage: independent meta-alerts, buffered transport, and degraded-but-honest dashboards.

Key takeaways:

1. Cardinality is the capacity currency — budget and enforce it per tenant at the gateway

2. Partition by series hash: ordering, compression, and load balance fall out for free

3. Downsample with metric-type awareness; wrong aggregation silently lies in graphs

4. Cache query results — dashboard stampedes are the read-path DDoS

5. Meta-monitor through an independent channel; the watchdog cannot live in the kennel

This design sustains 1.7M points/sec within ~24 TB replicated storage and keeps alerts flowing within 30 seconds of data arrival.

## Cheat Sheet
```text
METRICS PIPELINE SYSTEM DESIGN CHEAT SHEET
===========================================================

INGESTION PATH:
  agents/scrapers -> stateless gateway -> Kafka(series-hash parts)
  -> TSDB writers -> S3 blocks -> compactors/downsamplers

CARDINALITY CONTROL:
  - active_series_count is THE capacity metric
  - per-tenant quotas enforced AT GATEWAY (reject early)
  - alarm on growth slope >5%/hr; unbounded labels banned
    (no user_id/request_id as metric label)

STORAGE MATH:
  - 25M series @15s ~= 1.4TB raw/7d (XOR-compressed ~1.5B/pt)
  - tiers: 15s x 7d -> 1m x 30d -> 5m x 13mo
  - counter=last, gauge=avg, histogram=merge when rolling up

ALERT EVALUATION:
  - rule groups sharded by hash + leader election per shard
  - 'for' duration + pending-state map = no flapping
  - alertmanager dedupe/silence/route by labels

RESILIENCE:
  - Kafka RF=3 buffers bursts; replay fixes bad rollups
  - result cache for dashboard stampedes
  - meta-alerts via INDEPENDENT channel

INTERVIEW TIPS:
  - push vs pull: say "both, for different reasons"
  - know Gorilla/XOR compression exists (2 bytes/sample)
  - mention federation/cells for multi-region
```

# Distributed Job Scheduler System Design

## Definition

A distributed job scheduler decides when work becomes eligible, assigns it to an available worker, and records its outcome. For a weekly digest, scheduling determines the intended Monday occurrence; a queue delivers it; a worker sends it. Those are different responsibilities with different retry boundaries.

> **Textbook Definition:** A distributed job scheduler assigns executable work to workers and tracks ownership, timing, and completion under resource constraints and a defined retry and duplicate-execution contract.

## First Principles

A worker may stop responding while still executing. Giving another worker the job restores progress but creates overlapping attempts. A lease establishes temporary ownership in the scheduler; it does not stop the old process or undo an external action.

Recurring schedules add a second identity problem: a retry of Monday's occurrence must remain Monday's run, while next Monday is new work. Persisting occurrence identity separately from attempt identity prevents both duplicate triggering and accidental suppression of future runs.

## Requirements and capacity assumptions

Support one-off delayed jobs, recurring schedules, bounded payloads, priorities, per-tenant budgets, retries, cancellation, and inspectable history. Define schedule timezone, missed-occurrence policy, overlap policy, and maximum execution/retry age.

Assume 50 million runs/day: about 579 starts/second on average, with a 3,000/second design peak. At a measured 500ms mean duration, the peak needs about 1,500 occupied slots before retries and spare capacity. Two hundred workers with 16 slots provide 3,200 logical slots, but CPU, connection limits, provider quotas, and long-tail duration can reduce usable concurrency.

At 500 bytes per run, history grows by 25 GB/day and 750 GB over 30 days before indexes and replicas. A fleet of 500,000 recurring definitions does not establish how many become due per minute: every-second, daily, and synchronized-hourly schedules have very different distributions.

Define trigger delay separately from queue wait and execution duration. A 15-second leader failover cannot preserve a one-second trigger objective during that outage. State the recovery objective instead of promising universal sub-second execution.

## Three cooperating planes

```text
Schedule API → definitions / next occurrence
                          ↓
                  trigger transactions
                          ↓
              durable runs + publication outbox
                          ↓
                  queue / ready-work signal
                          ↓
                  worker claim + heartbeat
                          ↓
                   result / retry / dead
```

The database owns run identity and attempt state in this design. The broker signals ready work; duplicate or lost signals are repaired from durable runnable state. This choice means a database write outage pauses new authoritative claims and completions. Continuing to drain broker messages does not grant permission to execute work without the required ownership check.

A single elected trigger leader simplifies coordination, but is not mandatory: multiple scanners can claim disjoint rows transactionally with `SKIP LOCKED` and unique occurrence identities. Leader election alone does not prevent a stale leader writing after expiry; authoritative transactions still need protection.

## A minimal occurrence and claim-state schema

```sql
CREATE TABLE job_definitions (
    job_id bigint PRIMARY KEY,
    tenant_id bigint NOT NULL,
    schedule_version integer NOT NULL CHECK (schedule_version > 0),
    enabled boolean NOT NULL DEFAULT true,
    next_fire_at timestamptz NOT NULL
);
CREATE TABLE job_runs (
    run_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    job_id bigint NOT NULL REFERENCES job_definitions(job_id),
    schedule_version integer NOT NULL,
    scheduled_at timestamptz NOT NULL,
    status text NOT NULL DEFAULT 'pending' CHECK (status IN
        ('pending', 'leased', 'succeeded', 'failed', 'dead', 'cancelled')),
    attempts integer NOT NULL DEFAULT 0 CHECK (attempts >= 0),
    max_attempts integer NOT NULL DEFAULT 5 CHECK (max_attempts > 0),
    run_after timestamptz NOT NULL,
    leased_by text,
    lease_until timestamptz,
    fence_token bigint NOT NULL DEFAULT 0 CHECK (fence_token >= 0),
    CHECK (
        (status = 'leased' AND leased_by IS NOT NULL AND lease_until IS NOT NULL)
        OR (status <> 'leased' AND leased_by IS NULL AND lease_until IS NULL)
    ),
    UNIQUE (job_id, schedule_version, scheduled_at)
);
CREATE INDEX job_runs_due ON job_runs(run_after, run_id)
    WHERE status = 'pending';
```

The occurrence key remains unique after success. A partial unique index covering only live runs would allow a completed occurrence to be inserted again during late replay. Archive policies must preserve the deduplication boundary for the supported replay horizon.

This is the occurrence and claim-state core, not a complete production schema. It omits recurring-expression/time-zone policy, queue payloads, outbox records, tenant fairness, attempt history, and one-off submission keys. Every transition out of `leased` must clear both lease columns in the same update. If partitioning history, create partitioned tables deliberately and include required partition keys in unique constraints or keep a separate dedup registry. PostgreSQL does not convert this ordinary table with `ALTER TABLE ... PARTITION BY`.

## Create an occurrence and advance the cursor together

Within one database transaction, lock a due definition, check its current version/enabled state, insert the unique `(job, version, scheduled time)` run, advance `next_fire_at`, and append its publication outbox record. The lock must remain in the transaction that does those writes; selecting `FOR UPDATE` in an earlier autocommitted query releases it too soon.

A crash before commit creates neither the occurrence nor the advanced cursor. A crash after commit leaves both plus the outbox, which can resend. Decide what to do after an outage: catch up every missed occurrence, coalesce to one, or skip old occurrences. Bound catch-up to avoid millions of overdue jobs flooding recovery.

Store an IANA timezone and use a tested recurrence parser. For a nonexistent local time during a daylight-saving jump, define whether to skip or shift it; for a repeated time, define whether to fire once or twice. Distinguish fixed delay, which schedules from completion, from fixed rate, which follows the clock even when a run is still active. If a run exceeds the interval, fixed rate can overlap or accumulate work, so the overlap/misfire policy is part of the schedule contract.

## Claim one eligible run atomically

This parameterized PostgreSQL statement returns the claimed row:

```sql
WITH candidate AS (
    SELECT run_id FROM job_runs
    WHERE status = 'pending' AND run_after <= statement_timestamp()
      AND attempts < max_attempts
    ORDER BY run_after, run_id
    LIMIT 1 FOR UPDATE SKIP LOCKED
)
UPDATE job_runs AS run
SET status = 'leased', leased_by = $1,
    lease_until = clock_timestamp() + interval '30 seconds',
    fence_token = run.fence_token + 1,
    attempts = run.attempts + 1
FROM candidate
WHERE run.run_id = candidate.run_id
RETURNING run.*;
```

Bind `$1` to an authenticated worker identity. No returned row means no eligible claim. The eligibility cutoff is fixed at statement start; the lease deadline uses the database clock when the update is applied. Keep the transaction short and require `lease_until > clock_timestamp()` on heartbeat and completion. The ordering is intentionally simple; tenant/queue eligibility and fairness must be incorporated before using this as a multi-tenant allocator.

Heartbeat and completion updates require the same worker, fence token, leased state, and an unexpired lease. A heartbeat after success must not reopen ownership, and an expired worker cannot resurrect its lease. Use the authoritative database clock and a renewal interval with room for expected pauses; `now()` is transaction-start time, so keep ownership transactions short or choose time semantics deliberately.

## Trace lease expiry without promising exactly-once effects

Worker A claims run 10 with token 7. It pauses beyond the deadline. Recovery releases the expired claim, and worker B claims with token 8. When A later submits success under token 7, the database rejects it. B can commit only while its token/state/deadline still match.

The rejection protects scheduler state. If A already sent an email or charged a provider, that external effect still exists. Use a stable action key tied to the logical run, not token or attempt number, where downstream idempotency is supported. This schema's token orders attempts of one run. If different runs can mutate the same downstream resource, allocate fencing tokens in that resource's ownership scope; the resource must atomically record the highest accepted token and reject lower ones with the mutation. A per-run counter cannot order separate runs. Otherwise reconcile uncertain outcomes and document possible duplicate/loss behavior.

Inserting `digest_sent` **before** sending email can lose the email if the process crashes after the insert. Inserting it afterward can duplicate email when sending succeeds before the insert. A local marker alone cannot make an unrelated email provider atomic with the database. The [workflow case](30.2.2.21-workflow-engine.md) owns the detailed external-effect recovery and compensation discussion.

A reaper must handle every expired leased state and atomically choose retry or terminal exhaustion. An exhausted run must not remain pending forever because the claim query rejects it. Preserve each attempt's history separately from the logical run.

## Retry, cancellation, and fairness policies

Use bounded exponential backoff with jitter for retryable failures and respect provider limits. Cap attempts and total retry age; put poison work in an inspectable terminal/dead-letter state. A timeout is an unknown outcome, not automatic proof that retrying a side effect is safe.

Cancelling a future occurrence prevents a new claim under authoritative state. Cancelling an active run requests cooperative stop and defines what happens to already started effects. Editing a recurring definition increments its schedule version; document whether old pending occurrences remain valid or are cancelled.

Strict priority can starve lower-priority tenants. Deficit round-robin (**DRR**) maintains a persistent per-queue credit balance: add a weighted quantum each round, serve work affordable by that credit, then subtract its cost and retain unused credit. Sorting by a `deficit` field without updating it is not DRR. Decide whether cost means jobs, estimated work, or measured duration; one slow job and one quick job consume different resources.

Enforce per-tenant active-work limits and bounded waiting, with explicit aging/priority policy. Aging should not silently bypass safety/provider quotas. Consider separate worker pools for CPU-heavy jobs and slow network operations.

## Broker and deployment decisions

| Choice | Boundary |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Redis Streams | Consumer recovery and persistence settings matter; reclaiming a pending message does not stop its old worker. |
| Kafka | Replay and partition order are useful; dispatch priority/fairness are additional application policies. |
| Managed visibility-timeout queue | Visibility delays redelivery but does not fence the side effect or guarantee exactly-once processing. |
| Database-only queue | Can be adequate at measured moderate traffic; avoids a separate publication boundary but shares database capacity. |

Broker-specific timeout limits must come from the selected service's documentation; do not infer a universal 15-minute limit from delayed-message settings. Timing wheels or due-set caches can reduce scan work, but durable definitions remain authoritative and schedule changes must invalidate cached candidates.

Shard scanning when measurements justify it. Treat region failover as an ownership/deduplication transfer; independent regional stores cannot each create the same global occurrence without a defined conflict protocol.

## Observe and test the scheduling contract

Track oldest due time and trigger delay separately from queue age, execution duration, lease expiry, stale-result rejection, exhausted attempts, per-tenant service share, outbox backlog, and unresolved external outcomes.

Exercise two claimers on one due run, an expired lease followed by a late heartbeat/completion, duplicate occurrence creation after success, a crash between transaction commit and outbox publication, daylight-saving gaps/repeats, exhausted retries, and DRR with unequal job costs. Assert that only one logical occurrence is created, stale owners cannot update protected state, exhausted work reaches a terminal state, and recovery stays within the declared backlog and trigger objectives.

## Summary

A scheduler combines durable occurrence creation, temporary worker ownership, and allocation policy. Unique occurrence identities prevent repeat triggering; atomic claims and fenced updates protect run state. External effects still need their own retry contract, while bounded catch-up, fair scheduling, and honest trigger/recovery objectives make the system operable during outages.

# Distributed Job Scheduler System Design

## TL;DR

Design cron-at-scale: a system that reliably triggers millions of scheduled and delayed jobs per day across a fleet, with leader-elected triggering, lease-based dispatch, at-least-once execution with deduplication, and fairness across tenants — the machinery behind Sidekiq/BullMQ/Celery clusters, Temporal workers, and every "run this nightly" feature ever shipped.

**Why it matters:** Tests the intersection of coordination (leader election), delivery guarantees (leases, visibility timeouts, dedup), and multi-tenancy (fairness/starvation). Almost every candidate can draw a queue; senior candidates can explain what happens when a worker dies mid-job or when one tenant floods the system.

## Requirements
### Functional Requirements

- Schedule jobs by cron expression, fixed delay, or absolute time (delayed jobs)
- Jobs carry payloads/queues/priorities; idempotency keys supported natively
- Dispatch to worker pools over multiple queues with per-queue concurrency
- Retries with configurable backoff; dead-letter queues after max attempts
- Delayed/cron jobs can be cancelled before execution
- Full run history: started_at, finished_at, attempts, result/error
- Multi-tenant: quotas and fairness between teams/customers

### Non-Functional Requirements

- Scale: 50M job executions/day (~580/sec average, ~3K/sec peak)
- Trigger precision: cron jobs fire within 1s of schedule
- Delivery: at-least-once; duplicate execution window minimized via leases + dedup
- Availability: scheduler keeps firing during partial failures (no single-node cron)
- Job payload up to 64KB (larger via blob reference)
- Run-history retention 30 days hot, 1 year archived

## Capacity Estimation

```text
Execution Estimates:

- 50M runs/day ≈ 580/sec average, design for 3K/sec peak
- Average job duration: 500ms → concurrent in-flight ≈ 3K × 0.5s = 1.5K active jobs
- Worker fleet: 200 nodes × 16 slots = 3.2K slots ✓

Metadata Store Estimates:

- Job definitions: ~500K recurring schedules × 2KB = 1 GB
- Run history: 50M rows/day × 500B ≈ 25 GB/day hot → partitioned daily,
  archived after 30d (750 GB hot, rest cold)

Trigger Ring Estimates:

- Next-fire computation for 500K crons: precompute next fire time per job,
  keep sorted structure; only jobs due within lookahead horizon need scanning
- With 60s horizons: scan touches ~7K jobs/min — trivial

Queue Throughput:

- Redis Streams / Kafka partitioned by queue name:
  3K msg/sec × 1KB avg ≈ 3 MB/s — comfortably single-digit partitions
```

## Database Design
### Schema

```sql
-- Recurring schedules (cron definitions)
CREATE TABLE job_definitions (
    id              BIGSERIAL PRIMARY KEY,
    owner_tenant    BIGINT NOT NULL REFERENCES tenants(id),
    name            VARCHAR(128) NOT NULL,
    cron_expr       VARCHAR(64),
    queue           VARCHAR(64) NOT NULL,
    payload         JSONB NOT NULL DEFAULT '{}',
    idempotency_key VARCHAR(191) UNIQUE,      -- natural dedup on definition
    enabled         BOOLEAN DEFAULT TRUE,
    last_fired_at   TIMESTAMPTZ,
    next_fire_at    TIMESTAMPTZ NOT NULL,     -- materialized for trigger ring
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_defs_next_fire ON job_definitions (next_fire_at)
    WHERE enabled;

-- One row per actual execution attempt
CREATE TABLE job_runs (
    id             BIGSERIAL PRIMARY KEY,
    def_id         BIGINT REFERENCES job_definitions(id), -- null for ad-hoc
    idempotency_key VARCHAR(191),             -- UNIQUE per pending run (partial)
    queue          VARCHAR(64) NOT NULL,
    priority       SMALLINT DEFAULT 5,
    status         VARCHAR(16) NOT NULL DEFAULT 'pending',
                   -- pending|leased|running|succeeded|failed|dead|cancelled
    attempts       SMALLINT DEFAULT 0,
    max_attempts   SMALLINT DEFAULT 5,
    run_after      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    leased_by      VARCHAR(64),
    lease_expires  TIMESTAMPTZ,
    fence_token    BIGINT DEFAULT 0,
    payload        JSONB,
    result         JSONB,
    error          TEXT,
    created_at     TIMESTAMPTZ DEFAULT NOW(),
    started_at     TIMESTAMPTZ,
    finished_at    TIMESTAMPTZ
);
CREATE INDEX idx_runs_due ON job_runs (queue, priority DESC, run_after)
    WHERE status IN ('pending', 'leased');
CREATE UNIQUE INDEX idx_runs_dedup ON job_runs (idempotency_key)
    WHERE status IN ('pending','leased','running');   -- partial unique!

-- Daily partitions for finished history
ALTER TABLE job_runs PARTITION BY RANGE (created_at);
```

Two planes matter here: the **control plane** decides WHEN jobs become runnable (leader-elected, DB-backed); the **dispatch plane** moves them to workers fast. Conflating them is the classic monolith-cron mistake.

## Key Components

### Trigger Ring (leader-elected cron evaluation)

The leader scans `job_definitions` for due entries and enqueues runs. Leader election uses the primitives from consensus theory — see [Theory: Consensus & Leader Election](../01-theory/30.2.1.09-consensus-and-leader-election.md):

```typescript
async function triggerLoop(): Promise<void> {
  while (true) {
    const lease = await coordinator.tryAcquire('trigger-leader', ttlMs = 15_000);
    if (!lease.ok) { await sleep(jitter(5_000)); continue; } // follower idle

    await renewLoop(lease, async () => {
      const due = await db.query(
        `SELECT * FROM job_definitions
         WHERE enabled AND next_fire_at <= now() + interval '1 second'
         ORDER BY next_fire_at LIMIT 1000 FOR UPDATE SKIP LOCKED`
      );
      for (const def of due.rows) {
        await db.transaction(async (tx) => {
          const nextAt = cron.next(def.cron_expr, def.next_fire_at);
          await tx.insertRun({ defId: def.id, runAfter: def.next_fire_at,
                               idempotencyKey: `${def.id}:${fireSlot(def.next_fire_at)}` });
          await tx.updateNextFire(def.id, nextAt);
        }); // atomic: create run + advance cursor together
      }
    });
  }
}
```

Details that separate working schedulers from toy ones:

- **Fire-slot idempotency**: key = `defId:scheduledTimestamp`, so if leadership flaps and re-scans, the unique index blocks double-firing.
- **SKIP LOCKED** lets multiple helper replicas drain large due-batches without blocking each other even while one holds leadership.
- **Clock discipline**: all comparisons use DB time (`now()`), not app-server clocks.

### Task Leases & Visibility Timeouts

Workers never own jobs — they borrow them:

```typescript
async function claim(worker: Worker): Promise<Lease | null> {
  return db.transaction(async (tx) => {
    const job = await tx.query(
      `UPDATE job_runs SET status='leased', leased_by=$1,
              lease_expires = now() + interval '30 seconds',
              fence_token = fence_token + 1, attempts = attempts + 1
       WHERE id = (
         SELECT id FROM job_runs
         WHERE status='pending' AND run_after <= now()
           AND queue = ANY($2)
         ORDER BY priority DESC, run_after ASC
         LIMIT 1 FOR UPDATE SKIP LOCKED)`
    );
    return job ? { job, fence: job.fence_token } : null;
  });
}

// Heartbeat extends the lease while work continues
setInterval(() => db.query(
  `UPDATE job_runs SET lease_expires = now() + interval '30 seconds'
   WHERE id=$1 AND leased_by=$2 AND fence_token=$3`,
  [run.id, worker.id, fence]), 10_000);

// Reaper converts expired leases back to pending (crashed workers)
await db.query(`UPDATE job_runs SET status='pending'
                WHERE status='leased' AND lease_expires < now()`);
```

Fence tokens (monotonic per-run counters) guard against zombie workers: a stale worker's late `complete()` is rejected because its token no longer matches. This is Kleppmann's fencing pattern applied to queues.

### At-Least-Once Dispatch + Deduplication

Delivery is at-least-once BY DESIGN (exactly-once transport is a lie at this scale). Exactly-once EFFECTS come from:

1. **Structural dedup** — partial unique index on `(idempotency_key) WHERE status IN ('pending','leased','running')`: resubmits and crash-replays collapse into one live run.
2. **Handler-side idempotency** — jobs write results keyed by run-idempotency key (upsert semantics), so a rare post-success replay is a no-op:

```typescript
export async function handleWeeklyDigest(job: Job): Promise<void> {
  const done = await db.query(
    'INSERT INTO digest_sends (key, sent_at) VALUES ($1, now()) ON CONFLICT DO NOTHING',
    [job.idempotencyKey]);
  if (done.rowCount === 0) return; // already sent — replay absorbed
  await mailer.send(buildDigest(job.payload.user_id));
}
```

### Delayed Jobs & Retry Backoff

Both reduce to the same primitive: a `run_after` timestamp plus the due-index. Retry scheduling is just `run_after = now() + backoff(attempt)`:

```typescript
const backoff = (attempt: number) =>
  Math.min(2 ** attempt * 1_000 * (1 + Math.random() * 0.2), 6 * 3_600_000);
// exponential + jitter, capped at 6h
```

For very high volumes of far-future delayed jobs (billions), add a timing-wheel layer in front of the DB: hold coarse buckets in memory/Redis sorted sets, spill into the due-index only within the final hour.

### Fairness Across Tenants

Naive `ORDER BY priority, run_after` lets Tenant A's 100K backlog starve everyone else. Weighted fair queueing fixes it:

```typescript
function pickQueues(queues: QueueStats[], workerCapacity: number): string[] {
  // Deficit round-robin: each tenant accumulates deficit proportional
  // to its configured weight; serve tenant whose deficit is largest.
  const order = [...queues].sort((a, b) => b.deficit - a.deficit);
  const picks: string[] = [];
  let remaining = workerCapacity;
  for (const q of order) {
    const take = Math.min(q.backlog, Math.ceil(q.weight * workerCapacity), remaining);
    if (take > 0) { picks.push(...Array(take).fill(q.name)); remaining -= take; }
  }
  return picks;
}
```

Plus starvation guards: an aging boost raises effective priority of any job waiting > 15 min regardless of tenant quota.

## Caching Strategy

Scheduling metadata is small but hot:

```text
• Cron parse cache: expression → compiled matcher (pure function memoization)
• Due-set cache: leader holds next N minutes of fires in memory;
  DB consulted only for writes (advance cursor + insert run)
• Queue depth metrics: sampled, not exact — fairness math tolerates staleness
• Definition lookups (payload fetch): Redis, 60s TTL, invalidated on update
```

Deliberately NOT cached: lease state. Lease correctness depends on a single authoritative store; caching it would resurrect zombie executions.

## Message Queue

Broker choice shapes the failure model:

| Broker             | Strengths                                                      | Watch-outs                                        |
| --------             | -----------                                                      | ------------                                        |
| Redis Streams      | Sub-ms latency, consumer groups, XAUTOCLAIM for lease recovery | Persistence tuning (AOF); memory-bound            |
| Kafka              | Replay, huge throughput, compacted topics for state            | Per-partition ordering only; higher latency floor |
| SQS / cloud queues | Managed, built-in visibility timeout = free leases             | Pricing at billions of ops; 15-min max VT         |

This design treats the broker as replaceable plumbing: the DB owns correctness (dedup, fences, history); the broker owns speed.

## Scaling Strategy

```text
Control plane:
• Single leader for triggering (correctness needs serialization),
  N read replicas for API/history queries
• Shard trigger scanning if definitions > millions: hash(def_id) → shard leaders

Dispatch plane:
• Partition queues by name; scale brokers on throughput
• Workers: stateless fleets per queue class; autoscale on queue depth + age
  (depth alone lies during bursts — age of OLDEST pending job is truth)

Failure domains:
• Cell isolation: per-region or per-tier stacks (free vs paid customers)
  so one runaway tenant cannot exhaust global capacity
• Metadata DB: primary + sync replica; run-writes tolerate brief
  unavailability via broker-side buffering (jobs enqueue, rows catch up)
```

## Failure Handling

| Failure                                | Mitigation                                                                                            |
| ---------                                | ------------                                                                                            |
| Worker crashes mid-job                 | Lease expires (30s) → reaper returns run to pending; fence token invalidates zombie writes            |
| Leader crashes                         | Election completes < 15s; followers were idle; fire-slot dedup prevents double-triggering during flap |
| Metadata DB down (write)               | Triggering pauses (safe); dispatch plane drains existing queue; alerts fire                           |
| Poison job (always throws)             | Max attempts → DLQ with full error context; quarantine dashboard                                      |
| Clock skew across nodes                | All scheduling compares DB time; NTP-maintained hosts assumed                                         |
| Thundering herd at :00                 | Jittered cron option; staggered scan batches; rate-limited enqueue per tenant                         |
| Duplicate execution despite everything | Handler idempotency keyed off idempotency_key (the final safety net)                                  |

## Trade-offs

| Decision          | Option A                      | Option B                                | Choice                                                            |
| ----------          | ----------                      | ----------                                | --------                                                            |
| Correctness owner | DB (metadata authoritative)   | Broker-only (visibility timeouts)       | DB-owned dedup/fences — brokers are plumbing, replaceable         |
| Triggering        | Multi-master (any node fires) | **Single elected leader**               | Leader + fire-slot dedup — simpler reasoning about duplicates     |
| Delivery          | Exactly-once transport        | **At-least-once + idempotent handlers** | Honest engineering; exactly-once effects via dedup keys           |
| Fairness          | Strict priority queues        | **Weighted fair queueing + aging**      | Priorities alone starve; DRR gives predictable shares             |
| Delayed jobs      | Poll DB due-index             | Timing wheel in front                   | Hybrid — wheel for far-future bulk, index for near-term precision |

## Summary

A distributed scheduler separates three concerns most systems blur: **deciding when** (leader-elected trigger ring writing fire-slot-deduped runs), **moving fast** (broker + lease-based claiming with heartbeats, fences, and a reaper), and **being fair** (weighted deficits, aging boosts, tenant quotas). Reliability comes from embracing at-least-once delivery and making duplicates harmless through structural (unique indexes) and behavioral (handler idempotency) dedup rather than chasing exactly-once transport myths.

Key takeaways:

1. Fire-slot idempotency keys make cron double-fires structurally impossible

2. Leases + heartbeats + fence tokens = crash-safe dispatch; visibility timeout is the same idea rented from SQS

3. The reaper is a first-class component, not an afterthought

4. Fairness needs weights AND starvation alarms — priorities alone are a footgun

5. Cells and per-tenant rate limits contain the blast radius of noisy neighbors

This design sustains 3K executions/sec with sub-second trigger precision and survives any single-component death without losing or duplicating work beyond handler-level absorption.

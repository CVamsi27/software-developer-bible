# Distributed ID Generator System Design

## TL;DR

Design a service that mints billions of unique, roughly time-ordered 64-bit IDs per day across a globally distributed fleet without coordinating in the hot path — the Snowflake problem that underlies every primary key ever generated at scale, and a direct comparison point for UUIDv7.

**Why it matters:** Tests bit-level layout reasoning, clock-skew handling (the part most candidates forget), coordination tradeoffs (node-ID assignment), and k-orderability's effect on database index locality. The UUIDv7 comparison is now standard senior-loop follow-up material.

## Requirements
### Functional Requirements

- Generate unique IDs at ~10K/sec per node, horizontally scalable across nodes
- IDs are 64-bit integers (fit BIGINT primary keys)
- IDs are roughly sortable by creation time (k-ordered) for index locality
- No network calls in the minting hot path (after startup)
- Support embedding coarse metadata (timestamp, generator) recoverable from the ID
- Tolerate node restarts without reissuing past IDs

### Non-Functional Requirements

- Latency: < 1ms p99 per mint (in-process, no RPC)
- Availability: generation survives coordinator (etcd/ZK) outages entirely
- Uniqueness: guaranteed across fleet, including across restarts and clock adjustments
- Span: timestamps must not overflow for decades (69-year horizon typical)
- Skew tolerance: handle NTP steps of ±seconds without duplicate emission

## Capacity Estimation

```text
Throughput Estimates:

- Per node: 12 sequence bits = 4096 IDs/ms = 4.096M IDs/sec theoretical,
  ~10K/sec realistic — headroom is enormous by design
- Fleet: 100 nodes × 10K/sec = 1M IDs/sec sustained
- Daily volume: 50M events/day needs 0.6 IDs/ms average — one node suffices;
  we deploy many for HA and domain separation, not raw throughput

Bit Budget (Snowflake layout):

| 1 bit | 41 bits        | 10 bits     | 12 bits  |
| sign  | timestamp (ms) | node/worker | sequence |

- 41 bits ms since custom epoch: 2^41 ms ≈ 69.7 years
- 10 node bits: 1024 distinct generators (or split 5 datacenter + 5 node)
- 12 sequence bits: 4096 IDs per millisecond per node

Epoch choice: e.g., 2020-01-01T00:00:00Z → overflow in ~2089.
Custom epochs buy decades vs Unix epoch (1970) if starting late.
```

## Database Design
### Schema

ID generation itself uses no database. Durable state lives only for node-identity assignment:

```sql
-- Node identity registry (coordination plane; etcd/ZK in many designs)
CREATE TABLE id_generators (
    node_id       SMALLINT PRIMARY KEY,      -- 0..1023
    hostname      VARCHAR(128) NOT NULL,
    datacenter    VARCHAR(32),
    leased_until  TIMESTAMPTZ NOT NULL,      -- ephemeral lease semantics
    max_ts_ever   BIGINT NOT NULL DEFAULT 0, -- last emitted ts (restart guard)
    created_at    TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (hostname)
);

-- Optional audit of issued RANGES for HiLo/range-based alternatives
CREATE TABLE id_ranges (
    domain       VARCHAR(32) NOT NULL,
    start_id     BIGINT NOT NULL,
    end_id       BIGINT NOT NULL,
    owner_node   SMALLINT REFERENCES id_generators(node_id),
    allocated_at TIMESTAMPTZ DEFAULT NOW(),
    CHECK (end_id > start_id)
);
```

```text
SNOWFLAKE 64-bit layout:

 63 62─────────────────22 21────────12 11──────────0
┌──────────────────────────────────────────────────┐
│ 0│   timestamp (41)   │ node (10)  │sequence (12)│
└──────────────────────────────────────────────────┘

Decoded example: 726204563838636032
  ts  = (id >> 22) + epoch        → 2026-08-25T10:00:00.123Z
  node= (id >> 12) & 0x3FF        → 7
  seq =  id         & 0xFFF       → 0

UUIDv7 layout (for comparison):

┌──────────────────────────────────────────────────────┐
│ ver(4)=7 │ unix_ts_ms │var │ rand_a   │ rand_b (62b) │
│ 48 bits time                                         │
└──────────────────────────────────────────────────────┘
128 bits total; time-sortable to ms; tail random (no node info)
```


## Key Components

### Core Minting Loop with Clock-Skew Handling

```typescript
const NODE_ID_BITS = 10;
const SEQUENCE_BITS = 12;
const MAX_SEQUENCE = (1 << SEQUENCE_BITS) - 1;           // 4095
const TIMESTAMP_SHIFT = NODE_ID_BITS + SEQUENCE_BITS;    // 22
const NODE_SHIFT = SEQUENCE_BITS;                        // 12
const MAX_BACKWARD_DRIFT_MS = 1_000;                      // tolerate ≤1s regression

export class SnowflakeGenerator {
  private lastTimestamp = -1;
  private sequence = 0;

  constructor(
    readonly nodeId: number,               // 0..1023, leased at startup
    private epoch: number,                 // custom epoch ms
    private clock: Clock,
    private onSkew?: (info: SkewInfo) => void,
  ) {}

  next(): bigint {
    let ts = this.clock.nowMillis();

    // CASE 1: clock stepped BACKWARD (NTP correction, VM migration)
    if (ts < this.lastTimestamp) {
      const drift = this.lastTimestamp - ts;
      if (drift <= MAX_BACKWARD_DRIFT_MS) {
        // Small drift: refuse to issue until wall clock catches up.
        // Guarantees no duplicates; latency hit bounded by drift size.
        while ((ts = this.clock.nowMillis()) < this.lastTimestamp) {
          this.onSkew?.({ type: 'wait', driftMs: drift });
          busySpinOrSleep(1);
        }
      } else {
        // Large drift: fail loudly rather than silently fork the timeline
        this.onSkew?.({ type: 'refuse', driftMs: drift });
        throw new Error(`Clock moved back ${drift}ms; refusing to mint`);
      }
    }

    // CASE 2: same millisecond — consume sequence space
    if (ts === this.lastTimestamp) {
      this.sequence = (this.sequence + 1) & MAX_SEQUENCE;
      if (this.sequence === 0) {
        // Sequence exhausted: spin into the NEXT millisecond
        while ((ts = this.clock.nowMillis()) <= this.lastTimestamp) {
          /* bounded spin */
        }
      }
    } else {
      this.sequence = 0;
    }

    this.lastTimestamp = ts;

    return (BigInt(ts - this.epoch) << BigInt(TIMESTAMP_SHIFT)) |
           (BigInt(this.nodeId) << BigInt(NODE_SHIFT)) |
           BigInt(this.sequence);
  }
}
```

Three skew policies exist — knowing all three IS the interview answer:

| Policy     | Mechanism                                             | Tradeoff                                                                                                       |
| ---------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **Wait**   | Spin until wall clock passes last emitted ts          | Zero duplicates; adds latency proportional to drift                                                            |
| **Bump**   | Advance logical clock beyond wall clock; keep minting | No latency spike; future-dated IDs until reality catches up; must persist bumped value or restarts can collide |
| **Refuse** | Error when drift exceeds threshold                    | Safest; converts infra problem into visible outage (usually correct above ~1s)                                 |

Production systems combine them: wait below 250ms, bump to 500ms, alarm-and-refuse beyond 1s.

### Node-ID Assignment Strategies

| Strategy                          | How                                               | Pros                      | Cons                                                                     |
| --------------------------------- | ------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------ |
| **Coordination service** (chosen) | Ephemeral sequential znodes / etcd lease → number | Automatic, collision-free | Startup dependency; ZK/etcd ops burden                                   |
| Operator-assigned static          | Config/env per instance                           | Dead simple               | Human error scales badly past ~20 nodes                                  |
| DB row with lease                 | Row per node, heartbeat extends lease             | Reuses existing DB        | DB outage blocks NEW starts only                                         |
| Derived from infra                | K8s StatefulSet ordinal, IP suffix                | Zero coordination         | Ordinals reused after scale-down → MUST pair with persisted max_ts guard |
| MAC/IP hash                       | hash(low bits of ip)                              | Automatic                 | Collisions possible; needs dedup verification                            |

Whichever strategy is chosen, pair it with the **restart monotonicity guard**: persist each node's `max(lastTimestamp)` (file, DB row, or coordinator) and initialize `lastTimestamp` from it at boot. Without it, a node whose clock regressed across restart will re-mint old territory.

### K-Orderability & Its Limits

```text
Within one node: STRICTLY increasing (ts, seq lexicographic).
Across fleet:    k-ordered — IDs sort within ~clock-sync window (tens of ms),
                 but node A at 10:00:00.000 may emit AFTER node B's .999.

Why k-orderability matters:
• B-tree inserts land near the right edge → cache-friendly, low page splits
• Range scans ("orders created after X") mostly follow ID order
• Cursor pagination stays stable-ish without a separate sort key

What it does NOT give you:
• Exact ordering guarantees between concurrent writers (never derive
  business causality from ID comparison alone — keep a real timestamp column)
```

### UUIDv7 Comparison

| Dimension         | Snowflake                                          | UUIDv7                                                                               |
| ----------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Size              | 64-bit (BIGINT-native)                             | 128-bit                                                                              |
| Time source       | Custom epoch, ms                                   | Unix epoch, ms                                                                       |
| Coordination      | Node-ID registry required                          | NONE — randomness replaces identity                                                  |
| Uniqueness basis  | ts + node + seq (deterministic)                    | ts + 74 random bits (probabilistic but effectively certain)                          |
| Embedded metadata | Node + sequence recoverable                        | None (opaque random tail)                                                            |
| Collision risk    | Zero (by construction)                             | ~0 practically; rises with same-ms same-node volume only via counter bits exhaustion |
| Index locality    | Excellent (same as v7)                             | Good; random tail shuffles within-ms ties                                            |
| Best fit          | Internal PKs where BIGINT matters, multi-DC fleets | Public-facing identifiers, cross-org systems, no registry to operate                 |

Rule of thumb: UUIDv7 when you cannot/will not run coordination and 16 bytes is fine; Snowflake when 8-byte keys and operational metadata earn their keep. Both beat UUIDv4 catastrophically for index locality — v4's full randomness fragments B-trees and wrecks page-cache hit rates at scale.

### Per-Shard Range Alternative (HiLo)

When neither bit-packing nor UUIDs fit (e.g., numeric IDs per tenant), hand out ranges:

```typescript
// Each shard reserves a block once per N ids — amortized coordination
async function reserveRange(domain: string): Promise<Range> {
  return db.transaction(async (tx) => {
    const [row] = await tx.query(
      `INSERT INTO id_ranges (domain, start_id, end_id, owner_node)
       VALUES ($1,
               (SELECT COALESCE(MAX(end_id),0)+1 FROM id_ranges WHERE domain=$1),
               (SELECT COALESCE(MAX(end_id),0)+1 FROM id_ranges WHERE domain=$1) + $2,
               current_node())
       RETURNING start_id, end_id`, [domain, RANGE_SIZE]);
    return { next: Number(row.start_id), remaining: RANGE_SIZE };
  });
}
// Minting = local counter decrement; coordination cost = 1 insert per 10K ids
```

Tradeoff vs Snowflake: IDs ordered per-shard but NOT globally time-ordered; gaps appear on crashes (abandoned ranges) — usually acceptable.

## Caching Strategy

Nothing to cache in the hot path — that is the entire point. The coordination plane benefits though:

```text
• Cron-parse... rather, compiled cron equivalents do not apply here;
  relevant caches are:
• Node-identity cache: lease state cached locally; refreshed lazily
• Clock-state cache: last-known NTP offset sampled every 30s by chrony;
  generator consults local kernel clock which NTP disciplines
• max_ts persistence: write-behind to durable store every few seconds
  (bounded loss window accepted because bump policy covers recovery)
```

## Message Queue

Not applicable to minting itself — generation is synchronous, allocation-free arithmetic. Where queues DO appear in this system's orbit:

```text
• Telemetry: each node streams (node_id, ts_range, count) heartbeats to the
  metrics pipeline for uniqueness auditing
• Audit replay: optional event log of range allocations (HiLo variant)
```

If your design reaches for a queue inside ID minting, stop — you have built a slow ID generator.

## Scaling Strategy

```text
Vertical limits first:
• One node handles 4.096M IDs/sec theoretical — throughput almost never
  drives scaling; AVAILABILITY does

Horizontal scaling axes:
• More nodes (each unique node_id) — trivially parallel
• Domain separation: orders-gen, users-gen fleets (blast-radius isolation)
• Datacenter-split node bits (5 DC + 5 node = 32×32) when fleets exceed
  1024 total or need strict DC ownership of ranges

Exhaustion planning:
• Timestamp overflow (~69y): documented migration deadline; version bit
  reserved in some layouts for future re-basing
• Sequence exhaustion (4096/ms/node): spin-to-next-ms already handles bursts;
  sustained saturation means add nodes, not bits
```

## Failure Handling

| Failure                            | Mitigation                                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| NTP step backward (< 1s)           | Wait policy: hold issuance until wall clock passes last ts                                                |
| Large backward jump (VM restore)   | Refuse + alarm; requires operator/persisted-max-ts reconciliation                                         |
| Forward jump (leap smearing aside) | Harmless — creates a gap in timeline, never duplicates                                                    |
| Coordinator down at startup        | Existing nodes unaffected (no hot-path dependency); new nodes use cached/assigned identities or fail fast |
| Node crash mid-ms                  | On reboot, init from persisted max_ts (or bump); abandoned sequence values simply never used              |
| Duplicate node_id (misconfig)      | Detectable via telemetry audit comparing (ts,node) density; fence by refusing two live leases on same ID  |
| Leap second                        | Use clocks smeared by NTP (chrony default) — monotonic-ish minutes avoid the 23:59:60 pathology           |

## Trade-offs

| Decision         | Option A                   | Option B                         | Choice                                                                    |
| ---------------- | -------------------------- | -------------------------------- | ------------------------------------------------------------------------- |
| ID scheme        | Snowflake (64-bit)         | UUIDv7 (128-bit)                 | Snowflake for internal PKs; expose UUIDv7 externally if opaque IDs wanted |
| Coordination     | Registry-assigned node IDs | Coordination-free (UUIDv7 style) | Accept startup-only coordination to keep 64-bit width + metadata          |
| Skew policy      | Always wait                | Wait→bump→refuse ladder          | Ladder — matches drift severity to disruption                             |
| Ordering promise | Claim global ordering      | Document k-orderability          | Honest docs prevent downstream causality bugs                             |
| Range allocation | Per-request DB increment   | HiLo blocks                      | Blocks — 1 coordination per 10K ids                                       |

## Summary

Distributed ID generation is a negotiation between three goods: uniqueness (absolute), ordering (statistical), and independence (hot-path coordination-free). Snowflake buys all three with 64 bits: 41 of timestamp, 10 of rented identity, 12 of per-ms burst room. The engineering lives in the edges — clock steps met with a wait/bump/refuse ladder, node identities leased not configured, restarts guarded by persisted maxima. UUIDv7 trades those edges away (no registry, no metadata, probabilistic uniqueness) for 128 bits and zero infrastructure.

Key takeaways:

1. Layout is a contract: encode what you will need to decode later (ts, node, seq)

2. Clock skew handling is the senior-level differentiator — name all three policies

3. Node-ID assignment needs leases plus a restart monotonicity guard

4. k-ordered ≠ ordered; never infer causality from ID comparison

5. UUIDv4 is the anti-pattern here — pure randomness murders index locality

This design mints 64-bit IDs at sub-millisecond latency, survives any single failure without duplicates, and overflows comfortably after everyone reading this has retired.

## Cheat Sheet
```text
DISTRIBUTED ID GENERATOR CHEAT SHEET
===========================================================

SNOWFLAKE LAYOUT (64 bits):
  1 sign | 41 ts(ms, ~69y) | 10 node | 12 seq (4096/ms)

CLOCK SKEW LADDER:
  drift <= 250ms -> WAIT (spin till caught up)
  drift <= 1s    -> BUMP logical clock (persist it!)
  drift >  1s    -> REFUSE + alarm
  always: persist max_ts; init from it on restart

NODE IDENTITY:
  lease from ZK/etcd/DB (startup only, never hot path)
  alternatives: StatefulSet ordinal (needs max-ts guard),
  IP-hash (needs collision check)

ORDERING:
  strict within node; k-ordered fleet-wide (~NTP window)
  never derive business causality from ID compare

VS UUIDv7:
  v7 = 48b unix-ms + random, NO coordination, 128 bits
  snowflake wins: width(8B), metadata, deterministic
  v7 wins: zero infra, cross-org friendliness
  both >> uuidv4 (index locality!)

INTERVIEW TIPS:
  - draw the bit layout FIRST, unprompted
  - mention leap-smear + why DB-time isn't usable here
  - HiLo/range blocks as the third alternative family
```

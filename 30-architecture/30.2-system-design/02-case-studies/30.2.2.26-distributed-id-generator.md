# Distributed ID Generator System Design

## Definition

A distributed ID generator creates identifiers at several machines without giving two records the same ID. It may also make IDs roughly time-sortable. An ID identifies a record; it does not establish permission to read it or prove which business event happened first.

> **Textbook Definition:** A distributed identifier generator assigns identifiers across independent producers according to stated uniqueness, ordering, coordination, and clock-failure assumptions.

## First Principles

Independent generators need some way to avoid selecting the same value. They can coordinate through an authoritative sequence, reserve disjoint ranges/identities, or choose from a large random space with a quantified collision risk.

Adding time bits narrows where values sort, but clocks can repeat or move backward. If uniqueness depends on time and local sequence, a restart must preserve enough state to avoid reusing a previously issued combination. A lease protects an identity only while the generator obeys its ownership boundary.

## Choose the identifier contract

| Approach | Useful property | Cost or boundary |
| ------------------------------ | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| Database sequence | Simple authoritative allocation | Network/database dependency, gaps, and allocation order distinct from commit order. |
| Reserved numeric ranges | Amortized coordination and local minting | Abandoned gaps and durable non-overlapping allocation. |
| Snowflake-style packed integer | 64-bit width and approximate time locality | Exclusive worker identity, timestamp horizon, and restart/clock discipline. |
| UUIDv4 | Large random namespace without worker registry | Probabilistic uniqueness and scattered index insertion. |
| UUIDv7 | 128-bit UUID with Unix-millisecond prefix | Within-millisecond generation/ordering behavior depends on implementation. |

Choose Snowflake-style integers here to explore the operational boundaries. Use a maintained library when it satisfies the required contract. Index locality improvements depend on database workload; random IDs do not universally make a system unusable. Time-bearing identifiers expose approximate creation time, and worker-bearing IDs expose topology. Use separate public identifiers when that disclosure matters.

## The bit layout and capacity

```text
signed 64-bit positive integer
| unused sign:1 | milliseconds since epoch:41 | worker:10 | sequence:12 |
```

The 41-bit time field spans `2^41` milliseconds, about 69.7 years. Ten worker bits allow 1,024 identities, and 12 sequence bits allow 4,096 IDs in one timestamp millisecond per worker. Splitting ten bits into five region and five worker bits still permits only 1,024 combinations; it does not increase fleet capacity.

The 4.096 million IDs/second figure is a **per-worker bit-budget ceiling** if every millisecond's sequence space is used. At most 1,024 worker identities make the theoretical aggregate ceiling about 4.19 billion/second, but neither number is a runtime benchmark. One hundred generators measured at 10,000 IDs/second each would provide one million/second under those test conditions. Fifty million/day averages about 579/second across the system, or 0.579/millisecond.

Use an explicitly versioned epoch and plan migration before the timestamp field expires. Reject pre-epoch timestamps, invalid worker IDs, and field overflow instead of packing overlapping bits.

## A complete single-process teaching generator

This strict TypeScript example deliberately refuses clock regression and sequence exhaustion rather than blocking the event loop. It assumes one live process exclusively owns its worker ID and does not implement durable restart safety:

```typescript
class SnowflakeGenerator {
  private lastMs = -1;
  private sequence = 0;

  constructor(private readonly workerId: number,
    private readonly epochMs: number,
    private readonly clock: () => number) {
    if (!Number.isInteger(workerId) || workerId < 0 || workerId >= 1024) {
      throw new RangeError('workerId must be 0..1023');
    }
    if (!Number.isSafeInteger(epochMs)) throw new RangeError('invalid epoch');
  }

  next(): bigint {
    const now = this.clock();
    if (!Number.isSafeInteger(now)) throw new RangeError('invalid clock');
    const elapsed = now - this.epochMs;
    if (elapsed < 0 || elapsed >= 2 ** 41) {
      throw new RangeError('timestamp outside 41-bit horizon');
    }
    if (now < this.lastMs) throw new Error('clock moved backward');
    const nextSequence = now === this.lastMs ? this.sequence + 1 : 0;
    if (nextSequence >= 4096) throw new Error('millisecond sequence exhausted');
    this.lastMs = now;
    this.sequence = nextSequence;
    return (BigInt(elapsed) << 22n) |
      (BigInt(this.workerId) << 12n) | BigInt(nextSequence);
  }
}
const epoch = Date.UTC(2020, 0, 1);
let now = epoch + 123;
const generator = new SnowflakeGenerator(7, epoch, () => now);
const first = generator.next();
const second = generator.next();
console.assert(first === 515928064n);
console.assert(second === first + 1n);
console.assert(Number(first >> 22n) + epoch === now);
console.assert(Number((first >> 12n) & 1023n) === 7);
```

The first value packs elapsed time 123, worker 7, and sequence 0. Native JavaScript numbers cannot exactly represent every 64-bit ID; use `bigint` internally and decimal **strings** in JSON. Keep database-driver conversion explicit, and never pass a large ID through `Number` merely to serialize it.

This example is synchronous and intended for one JavaScript event loop. Multiple threads/processes sharing a worker ID require synchronized state or separate identities. A mutex in one process cannot coordinate a second process with the same configuration.

## Clock handling and restart safety

| Policy | Mechanism | Required boundary |
| --------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| Refuse | Reject a timestamp below the last issued timestamp | Preserves safety at the cost of availability. |
| Wait | Resume once a clock/retry condition is satisfied | Bound the wait; asynchronous waiting avoids a frozen event loop. |
| Logical advance | Keep time at/above a durable logical high-water mark | Bound future drift and preserve state across restart. |

A forward jump is not harmless: it can push the generator near overflow and make a later correction look like a large backward jump. Clock synchronization reduces risk but does not prove monotonic wall time. Leap handling depends on configured clock services; do not assume every chrony installation uses smearing by default.

Persisting `last timestamp` every few seconds leaves a window of previously issued IDs absent from durable state. Restarting at the old timestamp with sequence zero can duplicate IDs. Even an exact last timestamp must preserve the sequence or start **strictly after** the durable timestamp before reusing the identity.

One safe design reserves an issuance high-water boundary durably **before** using values beneath it, then skips to beyond that reserved boundary after restart. Another changes to a never-reused identity/epoch namespace under a defined protocol. State the durability and ownership assumptions explicitly; merely adding a `max_ts` column that the generator never updates does not implement recovery.

## Leased worker identities must stop at expiry

If worker 7 loses contact with its coordinator, the coordinator may reassign 7 after its lease expires. Continuing indefinitely with a cached identity can then create duplicates with the new owner. Stop before the lease's safe local expiry, or use a non-reassignable static allocation with its own operational guarantees.

There need not be a network call for **each** ID, but leased identity generally needs renewal and a conservative deadline check. Cached ownership is not ownership forever. Coordinator outage may leave existing generators usable only until their lease safety boundary; new owners must not reuse cached expired assignments.

An etcd/ZooKeeper registration number is not automatically a valid ten-bit identity: map allocations into the bounded namespace and define safe reuse. IP/MAC hashes can collide. StatefulSet ordinals can be reused during replacement or cloning. Audit detection of duplicate IDs is useful, but detects damage after generation rather than preventing it.

## Range allocation without a MAX race

A numeric range alternative stores one authoritative cursor per domain. This PostgreSQL statement reserves a half-open range `[start_id, end_id)` of `$2` IDs:

```sql
CREATE TABLE id_allocators (
    domain text PRIMARY KEY,
    next_id bigint NOT NULL CHECK (next_id > 0)
);
-- Initialize the domain once with its first unallocated value.
INSERT INTO id_allocators VALUES ('orders', 1);

-- Bind $1 = domain, $2 = positive block size (validated by the API).
UPDATE id_allocators
SET next_id = next_id + $2
WHERE domain = $1 AND $2 > 0
RETURNING next_id - $2 AS start_id, next_id AS end_id;
```

Concurrent updates serialize on the cursor row and reserve disjoint ranges. Separate `SELECT MAX(end_id)` queries can both observe the same maximum and allocate overlapping ranges. Store the allocation durably before issuing from it; on crash, abandon uncertain remainder rather than reconstructing the cursor from an old local cache. Overflow aborts allocation.

The local allocator emits only within its reserved half-open interval. Gaps are expected. Range order is allocation order, not necessarily event or commit order; two owners consume their ranges at different speeds.

## UUIDv7 and ordering boundaries

RFC 9562 places a 48-bit Unix-millisecond timestamp first, followed by the version, 12 `rand_a` bits, the variant, and 62 `rand_b` bits. The remaining space can include specified monotonicity techniques, not always 74 independently random bits. A library's implementation determines its within-millisecond/restart behavior.

Random UUID collision risk is probabilistic across all issuers selecting within the relevant space, not only one node. UUIDv7 removes a Snowflake worker-ID registry but does not prove globally causal order or make timestamps private. UUIDv4/v7 still need uniqueness constraints and a collision/retry policy where appropriate.

Within a correctly owned running Snowflake generator, emitted values increase as `(timestamp, sequence)` increases. Across workers, clock differences and worker bits affect order. Database insertion/commit order and business causality can differ from ID order. Stable pagination needs an explicit sort/tie-break contract, not a promise that IDs are "stable-ish."

## Decisions, failure cases, and best practices

- Reject invalid layout fields, exhausted sequences, unsafe clock state, and expired ownership before emission.
- Test fixed milliseconds, the 4,096 boundary, backward/forward jumps, horizon overflow, reused identity, crash recovery, and serialization through every client.
- Document epoch, layout, version, allocation domain, and migration deadline.
- Measure actual latency/throughput and watch lease renewal age, refused issuance, clock drift, durable reservation age, and duplicate constraint failures.
- Treat identifiers as public inputs to authorization checks, not secrets or bearer credentials.

## Summary

Distributed IDs trade coordination, width, ordering, and collision assumptions. A packed 64-bit format works only with exclusive identities, validated fields, and a real clock/restart protocol. Durable range cursors avoid overlapping allocation, while UUIDv7 offers time locality without a worker registry. None of these formats establishes business causality or access rights by itself.

# Ad Click Aggregator System Design

## TL;DR

Design the pipeline that turns billions of raw ad-click events per day into accurate, fraud-filtered, per-ad/per-campaign aggregates available within minutes — streaming ingestion, windowed aggregation with watermarks for late data, exactly-once sinks into an OLAP store, and rollups that make dashboards and billing queries instant.

**Why it matters:** The canonical streaming-aggregation interview. Tests windowing semantics (tumbling vs sliding), watermark reasoning for late/out-of-order events, dedup strategy (exact vs probabilistic), exactly-once sink design, and where fraud filtering hooks in. Billing money flows through this system — correctness arguments matter as much as scale.

## Requirements
### Functional Requirements

- Ingest click events (click_id, ad_id, campaign_id, user_id, cost_cents, timestamp, ip, ua) from edge gateways
- Deduplicate repeated clicks (retries, double-taps, replays)
- Aggregate clicks/revenue per ad per time window; roll up to campaign/advertiser
- Handle late-arriving events (minutes-to-hours delay) with corrections
- Fraud/invalid-click filtering before aggregation (bot signatures, impossible velocity)
- Serve aggregate queries: dashboards (seconds-fresh), advertiser reports (hourly), billing (daily, exact)
- Support ad-hoc drill-downs by dimensions (country, platform, placement)

### Non-Functional Requirements

- Scale: 2B clicks/day (~23K/sec avg, ~100K/sec peak during events)
- End-to-end freshness: p95 < 5 min from click to queryable aggregate
- Correctness tiers: billing numbers must be EXACT (replayable); dashboards may be approximate (< 1% error tolerated)
- Availability > 99.95% for ingestion (dropped clicks = lost revenue attribution)
- Late-data tolerance up to 24h; older arrivals routed to batch reconciliation
- Multi-region ingestion with global merge

## Capacity Estimation

```text
Ingestion Estimates:

- 2B clicks/day ≈ 23K/sec average; 100K/sec peak (Super-Bowl-style spikes ×4)
- Click event ~500 bytes JSON → 150B avro/protobuf after schema compression
- Bandwidth: 100K × 150B ≈ 15 MB/s peak — modest; the hard parts are
  cardinality and correctness, not bandwidth

Dedup State Estimates:

- Dedup window 1h at peak: 100K/sec × 3600 = 360M keys/hour
- Exact set infeasible on one node → partitioned keyed stores + probabilistic
  pre-filter:
    Bloom filter (fpr 1%): 360M × ~10 bits ≈ 450 MB per hour-window shard
    Exact fallback: only for "maybe-seen" positives (~1%) → 3.6M lookups/hr

Aggregation Cardinality:

- Active ads: ~50M; windows/day: 86,400 hourly or 1440 ten-minute
- Live state: hot ads (top ~1M) × current windows × dimension combos
  ≈ tens of GB keyed state across aggregators — partitioned by ad_id

OLAP Storage:

- Hourly fact rows: 50M ads × 24h × avg dims(8) — but sparse: actual rows/day
  ≈ 300M × 40B columnar ≈ 12 GB/day compressed — trivial for ClickHouse-class
```

## Database Design
### Schema

```sql
-- OLAP star schema (ClickHouse/Doris/BigQuery class)
CREATE TABLE click_stats_hourly (
    window_start   DateTime,
    ad_id          LowCardinality(String),
    campaign_id    LowCardinality(String),
    country        LowCardinality(String),
    platform       LowCardinality(String),
    clicks         UInt64,
    invalid_clicks UInt64,          -- filtered by fraud layer, kept for audit
    spend_cents    UInt64,
    unique_users   UInt64,          -- HLL state or precomputed estimate
    quality        Enum8('provisional'=1, 'final'=2),
    _ingested_at   DateTime DEFAULT now()
)
ENGINE = ReplacingMergeTree(_ingested_at)   -- idempotent upserts by key
PARTITION BY toYYYYMM(window_start)
ORDER BY (campaign_id, window_start, ad_id, country, platform);

-- Daily billing rollup (EXACT tier, built from replayable log)
CREATE TABLE click_stats_daily (
    day            Date,
    campaign_id    LowCardinality(String),
    clicks         UInt64,
    spend_cents    UInt64,           -- reconciled against invoicing
    adjusted_at    DateTime
)
ENGINE = ReplacingMergeTree(adjusted_at)
ORDER BY (day, campaign_id);

-- Raw replayable log (the source of truth for recompute)
-- Kafka topic clicks.raw retained 14 days + archived to object storage 90d
```

## Key Components

### Windowed Aggregation (tumbling + sliding)

```typescript
interface WindowId { startMs: number; }

class TumblingWindowAggregator {
  // key = (ad_id, dim-hash, window_start)
  private state = new Map<string, Aggregate>();

  add(evt: ValidClick): void {
    const winStart = Math.floor(evt.ts / this.sizeMs) * this.sizeMs;
    const key = `${evt.ad_id}:${evt.dimHash}:${winStart}`;
    const agg = this.state.get(key) ?? emptyAggregate();
    agg.clicks += 1;
    agg.spendCents += evt.costCents;
    agg.userHll.add(evt.userIdHash);       // HLL: ~1.5% err, fixed memory
    this.state.set(key, agg);
  }

  // Watermark fires a window when we believe late data is done arriving
  maybeEmit(watermarkMs: number): EmitResult[] {
    const ready: EmitResult[] = [];
    for (const [key, agg] of this.state) {
      const winEnd = parseWindowEnd(key);
      if (watermarkMs >= winEnd + this.allowedLatenessMs) {
        ready.push({ key, aggregate: agg, final: true });
        this.state.delete(key);              // state reclaimed
      } else if (watermarkMs >= winEnd) {
        ready.push({ key, aggregate: agg, final: false }); // provisional push
      }
    }
    return ready;
  }
}
```

Window semantics cheat table:

| Window type | Definition | Use here |
|-------------|------------|----------|
| Tumbling | Fixed non-overlapping slices (10m/1h) | Primary aggregation |
| Sliding | Overlapping windows (e.g., last 1h, slide 5m) | Fraud velocity checks ("clicks in past hour") |
| Session | Gap-based dynamic windows | User-behavior analytics, not core accounting |

### Deduplication (layered: probabilistic then exact)

```typescript
class LayeredDedup {
  constructor(private bloomPerWindow: RollingBloom, private kv: KeyedStore) {}

  async isDuplicate(click: Click): Promise<boolean> {
    const key = `${click.click_id}:${windowOf(click.ts)}`;

    // L1: Bloom says "definitely NOT seen" for ~99% of traffic -> zero I/O
    if (!this.bloomPerWindow.mightContain(key)) {
      this.bloomPerWindow.add(key);
      return false;
    }
    // L2: Only bloom-positives pay an exact check (SETNX semantics)
    return !(await this.kv.putIfAbsent(key, '1', ttlHours(2)));
  }
}
```

Why layered: an exact Redis SETNX for all 100K/sec costs real capacity; the bloom absorbs ~99% at ~450 MB/hour of RAM. False positives from the bloom merely escalate to the cheap exact path — never cause wrong answers. This pattern generalizes far beyond ads.

### Exactly-Once Sink

Two accepted mechanisms; production systems pick one and can prove it:

1. **Idempotent upserts (chosen)** — every emitted partial writes `ReplacingMergeTree` rows keyed by (window, ad, dims). Replays overwrite identical values; a final emit replaces provisional ones. Uniqueness lives in the KEY, so at-least-once delivery collapses into exactly-once state.
2. **Transactional two-phase commit** — Flink 2PC sinks hold commits until checkpoint completes; stronger guarantee, more moving parts, ties latency to checkpoint interval.

```typescript
async function sink(emitted: EmitResult[]): Promise<void> {
  await olap.insert(
    'click_stats_hourly',
    emitted.map((e) => ({
      window_start: new Date(e.windowStart),
      ...dimsOf(e.key),
      clicks: e.aggregate.clicks,
      spend_cents: e.aggregate.spendCents,
      unique_users: e.aggregate.userHll.estimate(),
      quality: e.final ? 'final' : 'provisional',
    })),
  ); // ReplacingMergeTree keeps latest _ingested_at per ORDER BY key
}
```

### Late Events & Watermarks

```text
Watermark = max(event_time_seen) - bounded_out_of_orderness (e.g., 2 min)

Timeline example (10-min tumbling windows):
  events arrive: 10:04, 10:06, 10:03(late), 10:11...
  watermark hits 10:10+2min slack -> window [10:00,10:10) emits FINAL
  event ts 10:07 arrives at 10:13 -> ALLOWED LATENESS (say 24h) applies:
      aggregator recomputes window from checkpointed state,
      emits corrected row (ReplacingMergeTree supersedes old one)
  event arrives AFTER allowed lateness -> side output ->
      nightly BATCH RECONCILIATION recomputes affected windows from raw log

Billing safety net: daily exact job recomputes yesterday from clicks.raw,
overwriting streamed numbers. Streaming provides freshness; the batch
recompute provides the audit-grade number.
```

### Fraud Filtering Hook

Runs post-dedup, pre-aggregation, as a pure enrichment step so it can evolve independently:

```typescript
function fraudVerdict(click: ValidClick, ctx: FraudContext): Verdict {
  if (ctx.velocityFor(click.userId) > LIMITS.clicksPerHourUser) return 'invalid';
  if (ctx.knownBotRanges.has(click.ip))                      return 'invalid';
  if (click.ua && DATA_CENTER_UA_RE.test(click.ua))          return 'invalid';
  if (ctx.impossibleTravel(click.userId, click.geo, click.ts)) return 'review';
  return 'valid';
}
// Invalid clicks still count INTO invalid_clicks metric (auditability)
// but are excluded from billable spend_cents aggregation.
```

Velocity checks use sliding windows over keyed state — the same machinery the aggregation itself uses, which is why fraud sits inside the stream engine rather than as a separate service.

## Caching Strategy

```text
• Dashboard queries hit OLAP materialized views (pre-grouped hot campaigns);
  result cache at API tier, 30-60s TTL — matches dashboard refresh cadence
• Live endpoint reads aggregator-local state snapshots (sub-second numbers,
  explicitly provisional)
• Dimension dictionaries (LowCardinality) live in-memory per OLAP node —
  massive compression + faster group-bys
• Gateway-level negative caching: malformed/blocked senders throttled at edge
```

## Message Queue

```text
Topic layout:
├── clicks.raw        key=ad_id hash, partitions=192, RF=3, retention 14d
│                     (partition-by-ad gives per-key order + even spread;
│                      retention IS the replay budget for recomputes)
├── clicks.dlq        schema-invalid/unverifiable batches (forensics)
├── fraud.rules       compacted topic: bot ranges, thresholds distribution
└── agg.audit         window emissions log (provisional/final) for tracing

Backpressure story: gateways buffer briefly and shed via 429 + retry-after;
Kafka absorbs multi-minute surges; aggregators throttle emission not intake.
```

## Scaling Strategy

```text
Ingestion: GW horizontally behind LB; signing+validation ~µs — CPU-bound only
Kafka:     partition count sized for PEAK (100K/s ÷ ~2K/s-per-partition ≈ 64+)
Aggregators: parallelism == partitions; state partitioned by ad_id;
             hot-ad skew handled by two-phase aggregation (pre-combine local,
             shuffle, combine global — standard map-reduce shape)
OLAP:      sharded + replicated MergeTree tables; coordinator-less queries;
             scale-out on scan throughput, keep hot partitions on NVMe
Multi-region: regional ingest + aggregation; GLOBAL numbers merged from
             regional partials (associative adds make this safe); cross-region
             only carries compacted partial aggregates, not raw clicks
```

## Failure Handling

| Failure | Mitigation |
|---------|------------|
| Aggregator crash | Checkpointed keyed state restored; replay unacked Kafka offsets; idempotent sink absorbs duplicates |
| Kafka broker loss | RF=3/min.insync=2; producers failover; no data loss under single-broker death |
| Late data beyond lateness | Side-output -> nightly batch recompute from raw log; billing job is authoritative anyway |
| Hot ad (celebrity campaign) | Two-phase agg spreads load; partition skew alarms; optional salting of extreme keys |
| OLAP node loss | Replicated tables serve from peers; rebuild via fetch from other replica |
| Fraud rule regression | Shadow-mode evaluation first; rules versioned; invalid_clicks kept separately so reversals are computable |
| Clock skew at gateways | Event-time semantics everywhere — processing time irrelevant to windowing |

## Trade-offs

| Decision | Option A | Option B | Choice |
|----------|----------|----------|--------|
| Processing paradigm | Lambda (stream + batch layers) | Kappa (stream-only, replayable log) | Kappa-shaped: one stream codepath + batch recompute FROM THE SAME LOG for billing audit |
| Dedup | Exact everywhere | Probabilistic front + exact tail | Layered — bloom absorbs 99%, exactness preserved |
| Sink guarantee | Transactional 2PC | Idempotent keyed upserts | Upserts — simpler ops, provably correct with ReplacingMergeTree keys |
| Freshness model | Single "truth" number | Provisional + final quality flags | Flags — honest about epistemics, lets consumers opt in |
| Fraud placement | Separate service pre-Kafka | Stage inside stream engine | Inside engine — shares windowed state (velocity) with aggregation |

## Summary

Ad click aggregation is streaming correctness engineering: signed ingestion feeds a replayable log; layered dedup (bloom-then-exact) kills retries; fraud verdicts ride the same windowed state as the math; tumbling windows with watermarks emit provisional then final numbers while absorbing hours of lateness; and idempotent keyed upserts turn at-least-once delivery into exactly-once aggregates. The billing tier closes the loop — nightly exact recomputation from the raw log makes the whole streaming apparatus auditable rather than trusted.

Key takeaways:

1. Event-time windows + watermarks; processing time plays no role in correctness

2. Provisional-vs-final quality flags beat pretending there is one truth mid-stream

3. Dedup: probabilistic pre-filter + exact confirmation = cheap AND right

4. Exactly-once comes from idempotent sinks keyed by window identity, not from magic transports

5. Always build the batch reconciliation path — money demands it

This design handles 100K clicks/sec peaks with sub-5-minute freshness and billing-grade accuracy through replayable recompute.

## Cheat Sheet
```text
AD CLICK AGGREGATOR CHEAT SHEET
===========================================================

PIPELINE:
  signed ingest -> Kafka(raw, by ad_id) -> stream aggregator
  [dedup -> fraud -> tumbling windows] -> OLAP upserts
  -> hourly facts -> daily EXACT rollup (billing)

WINDOWS & WATERMARKS:
  watermark = max_event_ts - allowed_disorder
  emit provisional at win_end, FINAL at win_end+lateness
  beyond-lateness -> side output -> batch reconcile

DEDUP (layered):
  bloom (99%, ~450MB/hr) -> SETNX exact only on positives
  key = click_id + event-time window

EXACTLY-ONCE SINK:
  idempotent upsert keyed (window,ad,dims)
  ReplacingMergeTree keeps newest row
  (alt: Flink 2PC checkpoints)

FRAUD HOOK:
  post-dedup pre-agg, INSIDE stream (shares velocity state)
  sliding windows for velocity; DC-ip/bot-UA/impossible-travel

GUARANTEES TIERS:
  dashboards: provisional <1% err, <5min fresh
  billing:    nightly exact recompute from raw log

INTERVIEW TIPS:
  - explain tumbling vs sliding vs session in one breath each
  - know WHY partition by ad_id (order + skew story)
  - say "event-time, not processing-time" early
```

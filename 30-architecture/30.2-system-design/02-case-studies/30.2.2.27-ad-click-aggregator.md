# Ad Click Aggregator System Design

## Definition

An ad-click aggregator turns individual click events into reports such as clicks and spend per campaign per hour. It must distinguish a new click from a retry, track late events and fraud decisions, and make billing corrections auditable. A fast dashboard total is not automatically an invoice-ready total.

> **Textbook Definition:** An ad-click aggregator validates and summarizes click events for reporting and billing, reconciling duplicates, late arrivals, and corrections under explicit event-identity and accounting rules.

## First Principles

The same physical event can arrive more than once, while a second legitimate click may look similar to the first. Mint an immutable event ID at the trusted producer: a retry keeps that ID, while a separate click gets a new one even if its campaign, time, and price match. If IDs are only unique within a producer or tenant, include that stable namespace in the deduplication key and preserve it across regions. Do not infer identity from fields shared by valid clicks.

Event time and arrival time differ. A watermark estimates progress through event time; it cannot prove no older event will ever arrive. Fraud rules and campaign attribution can also change after initial ingestion. Exact accounting therefore needs durable inputs, versioned decisions, and correction policy, not merely a nightly sum.

## Requirements and capacity assumptions

Accept authenticated gateway events, deduplicate stable identities, validate campaign attribution, aggregate by authorized dimensions, and support late-data corrections. Separate provisional reporting from settled billing revisions. Do not accept client-supplied `cost_cents` as authoritative: resolve price, currency, and billability under the campaign contract.

Assume two billion events/day: about 23,148 events/second on average. At a 100,000/second peak and 150-byte encoded event, traffic is 15 MB/s before transport, replication, and indexing. Event size/compression are measurements to obtain, not universal properties of protobuf or Avro.

A one-hour peak-rate dedup horizon contains up to 360 million identities. A Bloom filter sized at roughly 9.6 bits per item with about seven probes targets a one-percent false-positive rate; that is about 432 MB for this **whole** population before overhead, not per shard unless each shard stores that whole population. Every accepted event still needs authoritative exact dedup state. The one-percent rate applies to genuinely unseen lookups; real repeats can make positive lookups much more frequent.

One day contains 24 hourly windows or 144 ten-minute windows. Under a deliberately dense assumption of 50 million active ads and eight dimension tuples per ad in each hourly window, the upper bound is 9.6 billion hourly rows/day. Real combinations are sparse, so measure active tuples and the cost of raw-event retention, exact identities, rule history, and reconciliation alongside compressed fact rows.

## The durable event and decision pipeline

```text
Signed gateway batch → validate / durable raw log
                                  ↓
                       stable identity + attribution
                                  ↓
                      versioned fraud / billability
                                  ↓
                       window aggregation checkpoint
                                  ↓
                 revisioned reporting snapshots → queries
                                  ↓
             reconciliation / settlement → billing ledger
```

Authenticate sender identity, validate schema/signature scope, bound batches, and reject impossible timestamp ranges under policy. Signing an event proves which trusted sender signed it, not that a human clicked or the price is correct. Minimize IP, user-agent, and user identifiers; pseudonymization alone does not make data anonymous.

Return acceptance after the chosen durable log acknowledgment and state partial failures explicitly. Partitioning by ad spreads many campaigns but can leave a hot ad on one partition. Global dedup requires a stable ownership rule for event identity even when the same event is forwarded through two regions; summing regional totals is safe only when their accepted event populations are disjoint or globally reconciled.

## Atomic deduplication and aggregation

Claiming an event as seen and adding it to a window must share a recoverable commit boundary. Otherwise a crash after the claim loses its contribution, while a crash after the addition but before the claim can double-count replay.

This Python teaching model accepts an immutable event whose sender, campaign attribution, price, currency, and billability have already been validated by trusted services. A later policy correction is a versioned adjustment, not a replay with changed event contents. The function copies state and returns the next state only for a new accepted event; it demonstrates the transition, not distributed persistence:

```python
from dataclasses import dataclass
from types import MappingProxyType
from typing import Mapping

@dataclass(frozen=True)
class AcceptedClick:
    event_id: str
    campaign: str
    event_ms: int
    price_minor: int
    currency: str
    billable: bool

@dataclass(frozen=True)
class State:
    seen: Mapping[str, AcceptedClick]
    totals: Mapping[tuple[str, str, int], tuple[int, int]]

    def __post_init__(self) -> None:
        # frozen=True is shallow; copy and wrap the mappings as well.
        object.__setattr__(self, 'seen', MappingProxyType(dict(self.seen)))
        object.__setattr__(self, 'totals', MappingProxyType(dict(self.totals)))

def apply(state: State, click: AcceptedClick, window_ms: int = 3_600_000) -> State:
    if (type(window_ms) is not int or window_ms <= 0
            or type(click.event_ms) is not int or click.event_ms < 0
            or type(click.price_minor) is not int or click.price_minor < 0):
        raise ValueError('invalid window, time, or price')
    previous = state.seen.get(click.event_id)
    if previous is not None:
        if previous != click:
            raise ValueError('event ID reused with different contents')
        return state
    seen = dict(state.seen)
    totals = dict(state.totals)
    seen[click.event_id] = click
    if click.billable:
        start = click.event_ms // window_ms * window_ms
        key = (click.campaign, click.currency, start)
        count, spend = totals.get(key, (0, 0))
        totals[key] = (count + 1, spend + click.price_minor)
    return State(seen, totals)

initial = State({}, {})
click = AcceptedClick('e1', 'campaign7', 3_599_999, 42, 'USD', True)
accepted = apply(initial, click)
assert apply(accepted, click) is accepted
assert accepted.totals[('campaign7', 'USD', 0)] == (1, 42)
assert initial.totals == {}  # no mutation before state replacement
another_click = AcceptedClick('e2', 'campaign7', 3_599_999, 42, 'USD', True)
twice = apply(accepted, another_click)
assert twice.totals[('campaign7', 'USD', 0)] == (2, 84)
assert isinstance(initial.seen, MappingProxyType)
filtered = AcceptedClick('e3', 'campaign7', 3_599_999, 42, 'USD', False)
after_filter = apply(twice, filtered)
assert after_filter.totals == twice.totals and after_filter.seen['e3'] == filtered
next_hour = AcceptedClick('e4', 'campaign7', 3_600_000, 42, 'USD', True)
after_boundary = apply(after_filter, next_hour)
assert after_boundary.totals[('campaign7', 'USD', 3_600_000)] == (1, 42)
try:
    apply(accepted, AcceptedClick('e1', 'campaign7', 3_599_999, 43, 'USD', True))
except ValueError as error:
    assert 'reused with different contents' in str(error)
else:
    raise AssertionError('reused event ID with changed contents was accepted')
```

A real processor persists dedup state, aggregate state, and recovery position consistently with its selected engine. Memory copies do not implement that protocol. Scope event identities by sender/tenant where required, bound state retention, and reject payload mismatch. Expiring exact identities before replay history can make an old event count again.

A Bloom filter may avoid an extra exact lookup; it cannot replace the authoritative claim. Unique-user sketches estimate distinct users under a chosen identity rule. They must remain separate from exact click/spend fields, with error bounds and precision stated. Never use an approximate distinct count as an exact invoice quantity by accident.

## Event-time windows and corrections

A tumbling hourly window is `[10:00, 11:00)`: an event exactly at 11:00 belongs to the next window. Processing time drives retries, retention, and operational freshness even when grouping uses event time.

Suppose the watermark passes 11:00 and a policy allows 24 more hours of late updates. The initial window emission is provisional. A 10:55 event arriving at 11:20 changes that window and emits a new revision. Only after the allowed-lateness boundary does the processor retire its active window under policy. An older event arriving afterward goes to an explicit reconciliation path; the watermark was an estimate, not proof that the event was invalid.

For several input partitions, progress generally depends on the slowest relevant watermark, with an explicit idle-partition policy. Using the global maximum observed timestamp can prematurely close windows when one source runs ahead or has a bad clock. Validate timestamp skew and retain arrival time for diagnosis.

Do not delete window state at the first "final" emission then claim later corrections can be made without retained state or recomputation. Name status according to its scope, such as `provisional`, `closed_for_stream`, or `settled_revision`; billing settlement may still allow contractual adjustments.

## Publish replay-safe reporting revisions

A snapshot contains the **complete** current total for a key such as `(tenant, campaign, currency, hour, dimensions)`, plus an authoritative increasing revision. Retry the same revision with identical contents. A late old snapshot cannot replace a newer one.

In ClickHouse, `ReplacingMergeTree(revision)` removes obsolete rows during merges; it is not an immediate uniqueness constraint. Queries must collapse revisions using an appropriate latest-row query such as `FINAL` or `argMax` **before** summing. Include all identity dimensions in the sorting key and keep the key's partition placement stable, because background merges are partition-local.

A stable stream checkpoint/revision protocol and correct reads can make snapshot replay harmless. This is a scoped projection guarantee, not a claim that any sink automatically offers exactly-once end-to-end accounting. Two-phase commit is an alternative only when the selected connector/storage actually supports it and recovery is proved.

## Fraud, attribution, and billing are versioned decisions

Retain the raw accepted event and the decision's rule/model version, reason, effective time, and attribution/price inputs needed for review. Some fraud signals are available at ingestion; others arrive days later. A reversal is a new recorded decision and adjustment, not silent deletion of evidence.

Reconciliation recomputes under a specified policy version and compares event sets and monetary totals with the provisional projection. A replayable log cannot correct missing source events, a forged business signal, a buggy shared rule, or an expired retention window on its own.

Billing commits a reviewed settlement revision to an accounting boundary with currency-specific integer amounts, invoice identity, and adjustment entries. Do not silently overwrite an already issued invoice from a changed dashboard table. The [payment case](30.2.2.06-payment-gateway.md) owns the detailed ledger and provider-outcome contract.

## Query, failure, and scaling boundaries

Authorize advertiser/tenant access outside caller-controlled query text. Result-cache keys include tenant, permission scope, window, dimensions, policy/revision visibility, and currency. Expose provisional status and freshness; a cached number must not masquerade as the newest settlement.

| Failure or bottleneck | Response |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Processor dies mid-checkpoint | Restore consistent dedup/aggregate/offset state and replay under the selected engine protocol. |
| Hot campaign | Two-stage aggregation with stable contribution identity; avoid adding repeated partial snapshots as fresh deltas. |
| Sink unavailable | Bound buffering and backpressure; preserve accepted input within retention. |
| Late event beyond stream horizon | Reconcile retained evidence and issue a documented correction. |
| Fraud-rule regression | Shadow/compare versioned decisions and make reversals auditable. |
| Region duplicate forwarding | Enforce global event ownership or reconcile exact identity before adding regional totals. |

Broker replication/acknowledgment settings, storage durability, checkpoint retention, and sink read behavior jointly define recovery. A replication factor alone does not establish zero data loss. Backpressure cannot be deferred forever by "throttling emission but not intake"; state and buffers are finite.

## Operational signals and acceptance tests

Measure acceptance failures, duplicate/payload mismatch rates, new identities, watermark lag, event/arrival skew, checkpoint age, sink revision lag, reconciliation deltas, rule-version reversals, and settlement backlog. Track exact money and approximate analytics separately.

Test boundary timestamps, duplicate replay across regions, payload mismatch, checkpoint crash points, old snapshot arrival, currency separation, post-close corrections, and fraud reversal. Validate traffic/freshness targets with actual representative workloads before asserting 100,000 clicks/second or a universal less-than-one-percent error bound.

## Summary

Click aggregation joins stable event identity, consistent deduplication/state recovery, event-time windows, and versioned business decisions. Replay-safe reporting needs authoritative revisions and deduplicating reads; invoice-grade results additionally need retained evidence, reconciliation, settlement, and auditable adjustments. Fast provisional numbers and exact accounting serve different contracts.

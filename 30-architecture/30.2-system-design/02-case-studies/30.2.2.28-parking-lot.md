# Parking Lot System Design

## Definition

A parking-management system admits vehicles, assigns compatible spaces, records parking sessions, calculates fees, and coordinates exit. A reservation in software is not proof that a vehicle physically reached a space; sensors and terminal events provide additional evidence.

> **Textbook Definition:** A parking-management system tracks finite spaces, vehicle admission, ticket state, and payment, coordinating physical observations with authoritative reservation and exit decisions.

## First Principles

Two terminals can observe the same free space before either assigns it. A display or cache cannot authorize both: allocation needs one authoritative transaction. Vehicles then move through a physical world that does not roll back with the database, so allocation, actual occupancy, payment, and barrier movement are separate states.

A sensor can miss an event and a command can be delivered twice. Reliable operation therefore needs stable event/command identities, reconciliation, and an explicit manual recovery policy rather than assuming every database update exactly reflects reality.

## Requirements and scope

Support multiple floors, compatible vehicle/spot sizes, accessible-space eligibility, optional EV charging, ticket/session tracking, transparent pricing, and availability displays. Separate ordinary parking from charging billing and monthly-pass entitlement. Begin with on-site admission; online reservations require additional hold/no-show policies.

Assume roughly 1,000 spaces and several entry/exit lanes. A transactional relational database may be entirely adequate; measure terminal latency and peak admission rate before adding a separate authoritative store. A cached count can make the display faster, but show its freshness and let the allocation transaction decide who gets a space.

## Components and state boundaries

```text
Entry terminal → allocation + session transaction → entry command outbox
                                                        ↓
                                                barrier controller
                                                        ↓
                                              observed vehicle passage

Spot sensors → observed occupancy → reconciliation → availability display

Exit terminal → versioned fee quote → payment → exit authorization
                                                    ↓
                                         barrier command + passage event
```

A local controller owns safety interlocks and physical command execution under its specified hardware contract. The backend must not equate "command sent" with "barrier opened" or "vehicle exited." Define operator and offline policies for power/network/payment failure; safe behavior depends on the facility's physical and operational requirements.

## An authoritative minimal schema

```sql
CREATE TABLE parking_spots (
    spot_id bigint PRIMARY KEY,
    floor_number integer NOT NULL,
    spot_number integer NOT NULL,
    size_rank integer NOT NULL CHECK (size_rank BETWEEN 1 AND 3),
    accessible_only boolean NOT NULL DEFAULT false,
    in_service boolean NOT NULL DEFAULT true,
    UNIQUE (floor_number, spot_number)
);
CREATE TABLE parking_sessions (
    session_id uuid PRIMARY KEY,
    spot_id bigint NOT NULL REFERENCES parking_spots(spot_id),
    entry_event_id uuid NOT NULL UNIQUE,
    assigned_at timestamptz NOT NULL,
    entered_at timestamptz,
    exited_at timestamptz,
    state text NOT NULL CHECK (state IN
        ('assigned', 'parked', 'exit_authorized', 'closed', 'cancelled')),
    CHECK (entered_at IS NULL OR entered_at >= assigned_at),
    CHECK (exited_at IS NULL OR (entered_at IS NOT NULL AND exited_at >= entered_at)),
    CHECK (state <> 'assigned' OR entered_at IS NULL),
    CHECK (state NOT IN ('parked', 'exit_authorized', 'closed') OR entered_at IS NOT NULL),
    CHECK (state <> 'cancelled' OR entered_at IS NULL),
    CHECK ((state = 'closed') = (exited_at IS NOT NULL))
);
CREATE UNIQUE INDEX one_live_session_per_spot
ON parking_sessions(spot_id)
WHERE state IN ('assigned', 'parked', 'exit_authorized');
```

The unique live-session index protects a space even when two terminals selected it. `assigned` is a temporary hold, `parked` requires observed entry, and `exit_authorized` allows an exit attempt while the session still owns the space. Mark the session `closed` only after exit evidence; cancel an `assigned` session only after controller or passage evidence confirms that no vehicle entered. Apply transitions conditionally against the current state so delayed retries cannot move a session backward.

Record `assigned_at`, `entered_at`, and `exited_at` using the database clock when evidence is accepted. Keep a controller's own `observed_at` and sequence separately for diagnosis; a device clock can be skewed or its event delayed. Create the session and entry-command intent together; a conflict chooses another eligible space or reports no capacity. Retries of one entry event reuse its session rather than creating another ticket. The schema omits pricing/payment records, vehicle identity, holds, sensor history, and the outbox.

For a separate reservation-hold model, use explicit expiry and owner/version checks. A one-hour Redis key expiration must not free a space occupied by a car still parked there. `SET NX` protects one Redis key operation; it does not make allocation plus a database ticket plus physical entry atomic or guarantee safe failover.

## Choose a compatible space before optimizing preference

Filter for spots whose configured fit class accommodates the vehicle, then check service status, accessible eligibility, reservations, and charging requirements. Rank only the compatible candidates by a stated policy: smallest suitable space preserves larger spaces; nearest suitable space reduces walking; first-fit is simple.

Define `size_rank` as a site-specific compatibility class; do not assume an enum's ordinal is a physical dimension. A floor/spot number is not measured walking distance. Treat accessible and EV requirements as constraints rather than points in one universal size ordering. Candidate ranking does not reserve the space; the authoritative transaction still decides who wins.

Trace two cars selecting space 3. Both see it free. Terminal A inserts an assigned session and commits; terminal B's live-session insertion conflicts and tries space 4. If A's response is lost, retrying its entry event returns A's existing session. Do not reallocate A to space 4 merely because the response timed out.

## Define fee arithmetic precisely

A pricing policy states currency, hourly rate in minor units, grace handling, rounding, cap boundaries, taxes, and version. The following complete Python example charges each started hour of the **whole stay** once a total-duration grace is exceeded, and caps each rolling 24-hour block. It does not implement calendar-day caps or subtract grace minutes from billable duration:

```python
def parking_fee(duration_seconds: int, hourly_minor: int,
                daily_cap_minor: int | None, grace_seconds: int = 900) -> int:
    if (type(duration_seconds) is not int or duration_seconds < 0
            or type(hourly_minor) is not int or hourly_minor < 0
            or type(grace_seconds) is not int or grace_seconds < 0):
        raise ValueError('duration, rate, and grace must be non-negative integers')
    if (daily_cap_minor is not None
            and (type(daily_cap_minor) is not int or daily_cap_minor < 0)):
        raise ValueError('cap must be a non-negative integer')
    if duration_seconds <= grace_seconds:
        return 0
    full_days, remainder = divmod(duration_seconds, 86_400)
    full_day_fee = hourly_minor * 24
    if daily_cap_minor is not None:
        full_day_fee = min(full_day_fee, daily_cap_minor)
    partial_fee = ((remainder + 3_599) // 3_600) * hourly_minor
    if daily_cap_minor is not None:
        partial_fee = min(partial_fee, daily_cap_minor)
    return full_days * full_day_fee + partial_fee

assert parking_fee(900, 200, 2_000) == 0
assert parking_fee(901, 200, 2_000) == 200
assert parking_fee(4_500, 200, 2_000) == 400
assert parking_fee(86_400, 200, 2_000) == 2_000
assert parking_fee(86_401, 200, 2_000) == 2_200
assert parking_fee(172_800, 200, 2_000) == 4_000
try:
    parking_fee(901, 200.0, 2_000)
except ValueError:
    pass
else:
    raise AssertionError('fractional minor-unit rate was accepted')
```

Use actual instants for elapsed duration; local calendar days have daylight-saving boundaries and need timezone-aware rules if that is the intended tariff. Do not truncate seconds to minutes before deciding whether a grace or started-hour boundary was crossed. Integer minor units avoid binary floating-point rounding, but currencies and legal rounding policies still need explicit handling.

Pin a quote to a policy version and expiry so a repeated payment request does not unexpectedly use a changed tariff. Define what happens if a driver pays and waits long enough for an exit grace period to expire.

## Payment, exit, and occupancy reconciliation

Record a stable payment attempt identity and verified provider outcome. A lost response is not proof of failure; reconcile before another charge. Monthly entitlement or manual override can authorize exit under documented policy without pretending a payment succeeded.

Exit authorization, barrier command, observed passage, and spot-vacated evidence are distinct. A car can leave its parking space before reaching the exit lane, so a space sensor may report it free while its session is still active. Conversely, payment alone does not prove it left the space. Decide whether authoritative reassignment requires a verified sensor transition, staff confirmation, or another facility-specific rule; close/release the session accordingly.

Persist command IDs and controller acknowledgments and detect replay. If the barrier opens but the network fails before acknowledgment, recover from controller/passage evidence rather than blindly issuing unlimited opens. Camera plate recognition is fallible and plate uniqueness depends on jurisdiction; retain ticket/manual alternatives without inventing a universal accuracy percentage.

## Failure and operating decisions

| Condition | Decision |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Spot sensor says occupied but software says free | Quarantine/reconcile the space; do not keep admitting cars from a stale count. |
| Payment provider unavailable | Apply a documented operator/offline/exit policy and record unresolved balance; do not fabricate success. |
| Allocation database unavailable | Limit automatic admission under a designed local-capacity policy or pause it; disconnected terminals cannot each allocate the full lot. |
| Display cache stale | Show freshness/degraded availability; actual admission still uses authoritative state. |
| Reservation no-show | Release only its expired hold under owner/version checks; occupied sessions follow a separate lifecycle. |

Protect tickets, payment details, plate data, and camera retention with scoped access. Authenticate terminal/controller messages. Track live assignments, observed occupancy discrepancies, entry/exit command age, quote/payment uncertainty, full-lot rejections, and manual overrides.

## Validate the operating boundaries

Test simultaneous space claims, lost entry responses, duplicate sensor events, expired holds, grace/hour/day boundaries, payment response loss, and passage without acknowledgment. Isolate a tariff or compatibility policy when it varies independently; leave one-off rules as direct conditions.

## Summary

Parking combines finite-resource allocation with physical observations and money. Atomic live-session ownership prevents conflicting assignments; sensors and barrier evidence reconcile what actually happened. Explicit tariff arithmetic, stable payment/command identities, and documented degraded operation keep a software state change from being mistaken for physical or financial completion.

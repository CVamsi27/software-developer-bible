# Parking Lot System Design

## TL;DR

Design a multi-floor parking lot system that handles vehicle entry/exit, spot assignment, payment calculation, and real-time availability tracking.

**Why it matters:** Tests OOP modeling (vehicle types, spot types, strategy pattern for pricing), real-time state management, concurrent access control, and payment integration. Classic LLD + system design hybrid interview question.

## Requirements

### Functional Requirements

- Multiple floors with different spot types (compact, regular, handicapped, EV charging)
- Vehicle types: motorcycle, car, truck/SUV
- Entry/exit terminal with ticket generation
- Automatic spot assignment based on vehicle type
- Real-time availability display boards
- Payment calculation (duration-based, tiered pricing)
- Support multiple payment methods (cash, card, app)
- Monthly pass / subscription support
- Reservation system (optional, advanced)

### Non-Functional Requirements

- Handle 1000+ vehicles across multiple floors
- Real-time availability updates (< 100ms)
- 99.9% uptime for entry/exit terminals
- Concurrent access: multiple vehicles entering/exiting simultaneously
- Fault tolerance: system must work even if payment is down (manual mode)

## Data Model

```sql
-- Floors and spots
CREATE TABLE floors (
    id          SERIAL PRIMARY KEY,
    floor_num   INT UNIQUE NOT NULL,
    total_spots INT NOT NULL
);

CREATE TABLE parking_spots (
    id          SERIAL PRIMARY KEY,
    floor_id    INT REFERENCES floors(id),
    spot_num    INT NOT NULL,
    spot_type   VARCHAR(20) NOT NULL,  -- COMPACT, REGULAR, HANDICAPPED, EV
    status      VARCHAR(20) DEFAULT 'AVAILABLE',  -- AVAILABLE, OCCUPIED, RESERVED
    vehicle_type_capable VARCHAR(20) NOT NULL,  -- MOTORCYCLE, CAR, TRUCK
    UNIQUE(floor_id, spot_num)
);

-- Vehicles and tickets
CREATE TABLE vehicles (
    id            SERIAL PRIMARY KEY,
    license_plate VARCHAR(20) UNIQUE NOT NULL,
    vehicle_type  VARCHAR(20) NOT NULL,  -- MOTORCYCLE, CAR, TRUCK
    color         VARCHAR(20),
    owner_id      INT
);

CREATE TABLE parking_tickets (
    id            SERIAL PRIMARY KEY,
    ticket_code   VARCHAR(20) UNIQUE NOT NULL,
    vehicle_id    INT REFERENCES vehicles(id),
    spot_id       INT REFERENCES parking_spots(id),
    entry_time    TIMESTAMP NOT NULL,
    exit_time     TIMESTAMP,
    status        VARCHAR(20) DEFAULT 'ACTIVE',  -- ACTIVE, COMPLETED
    payment_amt   DECIMAL(10,2),
    payment_time  TIMESTAMP
);

-- Pricing rules
CREATE TABLE pricing_rules (
    id              SERIAL PRIMARY KEY,
    vehicle_type    VARCHAR(20) NOT NULL,
    spot_type       VARCHAR(20) NOT NULL,
    base_rate       DECIMAL(10,2) NOT NULL,  -- per hour
    max_daily       DECIMAL(10,2),            -- daily cap
    grace_minutes   INT DEFAULT 15            -- free grace period
);
```

## Core Components

### 1. Spot Assignment Strategy

```java
// Strategy pattern for spot assignment
interface SpotAssignmentStrategy {
    ParkingSpot assignSpot(Vehicle vehicle, List<ParkingSpot> available);
}

// First-fit: assign the first available spot of correct type
class FirstFitStrategy implements SpotAssignmentStrategy {
    public ParkingSpot assignSpot(Vehicle vehicle, List<ParkingSpot> available) {
        return available.stream()
            .filter(s -> s.vehicleTypeCapable == vehicle.type)
            .findFirst()
            .orElse(null);
    }
}

// Best-fit: assign the smallest spot that fits (save larger spots for trucks)
class BestFitStrategy implements SpotAssignmentStrategy {
    public ParkingSpot assignSpot(Vehicle vehicle, List<ParkingSpot> available) {
        return available.stream()
            .filter(s -> s.vehicleTypeCapable == vehicle.type)
            .min(Comparator.comparingInt(s -> s.spotType.ordinal()))
            .orElse(null);
    }
}

// Nearest-to-entry: minimize walking distance
class NearestEntryStrategy implements SpotAssignmentStrategy {
    public ParkingSpot assignSpot(Vehicle vehicle, List<ParkingSpot> available) {
        return available.stream()
            .filter(s -> s.vehicleTypeCapable == vehicle.type)
            .min(Comparator.comparingInt(s -> s.floor_id * 100 + s.spot_num))
            .orElse(null);
    }
}
```

### 2. Entry/Exit Flow

```text
ENTRY FLOW:
1. Vehicle arrives at entry terminal
2. Camera reads license plate (ALPR)
3. System creates vehicle record (if new)
4. Strategy assigns spot
5. Ticket generated (QR code + barcode)
6. Barrier opens
7. Spot status → OCCUPIED
8. Display board updated

EXIT FLOW:
1. Vehicle arrives at exit terminal
2. Ticket scanned (QR/barcode) or plate read
3. System calculates duration
4. Pricing engine applies rules
5. Payment processed
6. Ticket status → COMPLETED
7. Spot status → AVAILABLE
8. Barrier opens
9. Display board updated
```

### 3. Pricing Engine

```java
class PricingEngine {
    public Money calculate(ParkingTicket ticket, List<PricingRule> rules) {
        PricingRule rule = findRule(ticket.vehicleType, ticket.spotType);
        long minutes = Duration.between(ticket.entryTime, ticket.exitTime).toMinutes();

        if (minutes <= rule.graceMinutes) {
            return Money.zero(); // free grace period
        }

        double hours = Math.ceil(minutes / 60.0);
        Money amount = rule.baseRate.multiply(hours);

        // Apply daily cap
        if (rule.maxDaily != null) {
            long days = minutes / (24 * 60);
            Money dailyTotal = rule.maxDaily.multiply(days);
            double remainingHours = (minutes % (24 * 60)) / 60.0;
            Money partialDay = rule.baseRate.multiply(Math.ceil(remainingHours));
            amount = dailyTotal.add(partialDay).min(rule.maxDaily.multiply(days + 1));
        }

        return amount;
    }
}
```

## Concurrency Handling

```text
CRITICAL: Multiple vehicles may try to park in the same spot simultaneously.

Solutions:
1. Redis atomic operations: SETNX on spot key
   - SET spot:3:status OCCUPIED NX EX 3600
   - If NX fails → spot taken, try another

2. Database optimistic locking:
   - UPDATE parking_spots SET status='OCCUPIED'
     WHERE id=3 AND status='AVAILABLE'
   - If 0 rows affected → spot taken

3. Distributed lock (Redis RedLock):
   - Lock on spot_id before assignment
   - Unlock after vehicle confirms parked
```

## Trade-offs

| Decision | Choice | Why | Alternative |
|----------|--------|-----|-------------|
| Spot tracking | Redis (real-time) + Postgres (持久化) | Redis for < 1ms reads, Postgres for audit | All-Postgres (slower display updates) |
| Pricing | Strategy pattern | Different pricing per vehicle/floor/peak hours | Hardcoded (simpler but inflexible) |
| Payment | Sync at exit | Simple, user sees total immediately | Async (app payment, pay-on-phone) |
| Plate recognition | ALPR camera + manual fallback | Real-world accuracy ~95%, fallback needed | Manual ticket only (slower) |

## What Could Be Better

- **Reservation system:** Pre-book spots online, reduces arrival uncertainty
- **EV charging integration:** Track charge level, auto-stop billing when full
- **Dynamic pricing:** Surge pricing during peak hours (like Uber)
- **Analytics dashboard:** Occupancy heatmaps, revenue forecasting
- **Valet mode:** Drop car at entrance, system parks it

## Interview Script

> "I'd model this as a multi-floor parking lot with Redis for real-time spot tracking and Postgres for durable logs. Entry uses ALPR + strategy pattern for spot assignment — first-fit for simplicity, best-fit to preserve large spots. Pricing is a strategy with per-vehicle-type rates and daily caps. Concurrency is handled with Redis SETNX atomic operations. Payment is synchronous at exit with grace period. Display boards poll Redis every 2 seconds for availability."

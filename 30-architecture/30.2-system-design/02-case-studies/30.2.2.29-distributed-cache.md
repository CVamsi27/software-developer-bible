# Distributed Cache System Design

## First Principles

(→ 30.2.1.05's patterns; the case study is the cluster design.)

1. **Consistent hashing is the clustering mechanism** — nodes join/leave moving only their share of keys (→ 30.2.1.03); without it, every resize is a cache flush.
2. **Replication vs reconstruction is the availability trade for a cache**: replicating hot keys (memory cost) vs re-fetching from origin on node loss (stampede risk) — protection layers (→ 20.8.01 axiom 3) become mandatory at cluster scale.
3. **The cluster is itself a dependency to be resilient about**: cache-cluster failure must degrade to origin (which must survive it — the cold-start axiom), never to outage.

## Requirements

### Functional Requirements

- `put(key, value, ttl)` — store a key-value pair with optional TTL
- `get(key)` — retrieve value by key
- `delete(key)` — remove a key
- Support millions of keys across multiple nodes
- Automatic failover when a node dies

### Non-Functional Requirements

- Sub-millisecond latency for reads (< 1ms p99)
- 99.99% availability
- Horizontal scaling (add/remove nodes without downtime)
- Data durability (optional, configurable per key)
- Consistent hashing for even data distribution

## Capacity Estimation

```text
Assumptions:
- 10M keys, average key 64 bytes, value 1KB
- Total data: ~10GB
- 100K reads/sec, 20K writes/sec
- 5 cache nodes, each with 4GB RAM

Storage:
- 10GB across 5 nodes = 2GB per node (fits in memory)
- Replication factor 2: 20GB total, 4GB per node

Network:
- 120K ops/sec × 2KB avg = 240MB/sec cluster-wide
- Per node: ~48MB/sec (well within 1Gbps)
```

## Core Concepts

### 1. Consistent Hashing (Data Partitioning)

```text
Problem: Where does key K live?
Bad approach: hash(K) % N nodes → adding a node remaps ALL keys

Consistent Hashing:
- Hash both keys AND nodes onto a ring (0 to 2^32)
- Key K → walk clockwise until you hit a node
- Adding/removing a node only affects keys in that node's range

Virtual Nodes:
- Each physical node gets 150 virtual positions on the ring
- Prevents hotspots when nodes have different capacities
- More vnodes = better distribution

Ring visualization:
        Node A (v1)
           ╱
     ●────●────● Node B (v2)
    ╱              ╲
   ●                ●
    ╲              ╱
     ●────●────●
           ╲
        Node C (v1)

Key "user:123" → hash to position 42 → walk clockwise → lands on Node B
```

### 2. Replication

```text
Strategy: Leader-Follower per partition

Partition 1: Node A (leader) → Node B (follower)
Partition 2: Node B (leader) → Node C (follower)
Partition 3: Node C (leader) → Node A (follower)

Writes: go to leader, async replicate to follower
Reads:  can read from any replica (eventual consistency)

Failover: if leader dies, promote follower to leader
- Detect via heartbeat (miss 3 heartbeats = dead)
- Promote follower, update routing table
- Client SDK refreshes hash ring
```

### 3. Eviction Policies

```text
When cache is full, what do we evict?

LRU (Least Recently Used):
- Track access order (doubly-linked list + hashmap)
- Evict least recently accessed
- Most common default (Redis: allkeys-lru)

LFU (Least Frequently Used):
- Track access frequency (counter per key)
- Evict least frequently accessed
- Good for skewed workloads (viral content stays)

FIFO (First In First Out):
- Evict oldest entry
- Simple, predictable
- Rarely used in practice

TTL (Time To Live):
- Expire after fixed time
- Always combined with another policy
- Bounded staleness

Redis configuration:
  maxmemory 4gb
  maxmemory-policy allkeys-lru
```

### 4. Cache Invalidation

```text
The hardest problem. Strategies:

1. TTL-based (simplest):
   - Every key has expiry
   - Pros: bounded staleness, simple
   - Cons: stale data up to TTL

2. Write-through:
   - Write to cache + DB synchronously
   - Pros: always consistent
   - Cons: write latency = cache + DB

3. Write-behind (write-back):
   - Write to cache, async flush to DB
   - Pros: fastest writes
   - Cons: data loss risk if cache dies

4. Pub/Sub invalidation:
   - When data changes, publish invalidation event
   - All cache nodes subscribe and delete local copy
   - Works for multi-node caches

5. Explicit DEL on write:
   - App writes to DB, then DEL cache key
   - Pros: simple, effective
   - Cons: race condition (write + DEL can reorder)
```

## Anti-Patterns

```text
1. CACHE STAMPEDE (Thundering Herd):
   - Cache key expires, 1000 requests all miss, all hit DB
   - Fix: distributed lock (only 1 request populates cache)
   - Fix: probabilistic early refresh (random requests refresh before TTL)

2. HOT KEY:
   - One key gets 90% of traffic → one node becomes bottleneck
   - Fix: replicate hot key across multiple nodes
   - Fix: in-process L1 cache for that specific key
   - Fix: key sharding (user:123:a, user:123:b, round-robin reads)

3. CACHE POISONING:
   - Bad data enters cache, served until TTL
   - Fix: validate cache values on read
   - Fix: short TTL for high-risk keys

4. THUNDERING HERD ON RESTART:
   - All cache nodes restart simultaneously, all cold
   - Fix: stagger restarts, pre-warm cache before traffic

5. BIG KEY:
   - One key with 10MB value blocks the node
   - Fix: shard large values, set max value size
```

## Monitoring

```text
Key Metrics:
- Hit ratio: hits / (hits + misses) → target > 90%
- Eviction rate: evictions/sec → high means cache is too small
- Memory usage: used / maxmemory → alert at 80%
- Latency: p50, p99, p999 of get/set operations
- Replication lag: leader-follower lag in ms
- Connection count: active client connections per node
```

## Trade-offs

| Decision | Choice | Why | Alternative |
| ------------ | ---------------------------------- | -------------------------------------------- | -------------------------------------------- |
| Partitioning | Consistent hashing + virtual nodes | Even distribution, minimal reshuffling | Modulo hashing (remaps all on node change) |
| Replication | Leader-follower async | Read scaling, acceptable lag | Sync replication (slower writes) |
| Eviction | LRU + TTL | Adapts to access patterns, bounded staleness | LFU (slower adaptation to new hot keys) |
| Consistency | Eventual (read from any replica) | Better availability | Strong (read from leader only, slower) |
| Persistence | Optional AOF/RDB | Durability for critical data | Pure in-memory (fastest, data loss on crash) |

## What Could Be Better

- **Multi-level caching:** L1 (in-process Caffeine) + L2 (Redis) + DB — reduces network hops
- **Cache warming:** pre-populate cache from DB snapshots on deploy
- **Adaptive TTL:** automatically adjust TTL based on access frequency
- **Cross-region replication:** geo-distributed cache for global low latency
- **Cache-as-database:** Redis with AOF for small datasets (sessions, feature flags)

## Interview Script

> "I'd design this with consistent hashing for partitioning — each key hashes onto a ring and maps to the nearest clockwise node. 150 virtual nodes per physical server prevent hotspots. Replication is leader-follower per partition; writes go to leader, async replicate to follower. Reads can come from any replica. Eviction is LRU + TTL as default. Cache stampede is handled with a distributed lock — only one request populates on miss, others wait. Hot keys get replicated across nodes or sharded with suffix."

## Summary

1. **Consistent hashing is the sharding story** — the ring + 150 virtual nodes keeps the keyspace balanced through node joins and departures
2. **Leader-follower replication trades freshness for availability** — async replication means reads may be stale; the design must tolerate that
3. **Eviction is policy, not accident** — LRU + TTL as the default pair, tuned per workload
4. **Stampede protection is non-negotiable at scale** — a distributed lock (or single-flight) ensures one population per miss; hot keys get replication or suffix-sharding
5. **Every answer names the failure mode it prevents** — stampede, hotspot, staleness — that's what separates a design from a wish list

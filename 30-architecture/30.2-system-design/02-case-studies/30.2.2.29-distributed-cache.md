# Distributed Cache System Design

A reader misses the cache and loads version 7 from the origin. Meanwhile a writer commits version 8 and deletes the cached value. The reader finishes late and caches its stale version 7 — and later readers keep hitting it. Deleting after the write never stopped the older in-flight fill:

```text
R reads v7 → W writes v8 + deletes cache → R caches stale v7. Versions or tombstones fix it.
```

## Definition

A **distributed cache** stores **derived values** across several machines so repeated reads avoid an expensive origin lookup. For example, a product description may be cached near its readers. A cache hit is useful only if the value belongs to the right caller and is fresh enough for the operation.

> **Textbook Definition:** A distributed cache places derived key-value data across multiple nodes with explicit policies for partitioning, replication, eviction, and acceptable staleness relative to the source of truth.

## First Principles

1. Memory is finite and nodes fail, so the system must decide where keys live, which copies exist, and how values are removed or rebuilt. Distribution spreads different keys, but one extremely popular key still concentrates work on its owners.
2. The origin and cache usually share no transaction. A write, invalidation, and concurrent cache fill can race. Correctness therefore depends on explicit version/freshness policy, not simply writing to both places synchronously.

## Requirements and capacity assumptions

Support bounded key/value sizes, get/put/delete, expiry, partition routing, eviction, and observable recovery. Decide which data is safely reconstructible and which operations require the authoritative origin. This chapter designs a **derived-data cache**; using Redis as a session or primary state store needs a different durability and failover contract.

Ten million keys at 64 bytes each plus 1,024-byte values occupy 10.88 GB of raw decimal storage. Two copies require 21.76 GB before metadata, allocator overhead, replication buffers, and spare capacity. Five nodes with 4 GB each provide only 20 GB, so that proposal never fits even the raw replicated data.

At 120,000 operations/second and an assumed 2,000 bytes of combined request/response payload per operation, the cluster carries 240 MB/s of payload in aggregate. Equal division over five nodes gives 48 MB/s, but response size, replication, hot keys, protocol overhead, and traffic direction change the distribution. A 1ms p99 objective across a network needs measurement; arithmetic never proves it.

## Separate routing from value policy

```text
Caller → scoped key + serializer → client routing OR proxy routing
                                               ↓
                                 partition owner / replicas
                                               ↓ miss
                             bounded coalesced origin load
                                               ↓
                                 versioned cache population
```

Choose who owns routing. Client-side routing avoids a proxy hop but requires clients to handle topology updates and migration. Proxy routing centralizes that logic but adds another capacity/failure boundary. Drawing both never explains which decision each makes.

Keys include tenant, authorization/visibility scope, resource, representation, and relevant policy/version dimensions. A product's public description and an account's private price cannot share an unscoped `product:7` response key. Validate codec/schema version and payload size, and authenticate network access to cache nodes.

## Partitioning and topology changes

Modulo routing `hash(key) % N` changes many assignments when N changes, not literally every key. Consistent hashing maps keys to a ring and chooses an owner; adding a ring position moves the interval assigned to it. Virtual positions can reduce placement imbalance and can be weighted by capacity, but they never guarantee balance or split one hot key. Measure skew with the actual key distribution.

Other systems use fixed hash slots or rendezvous hashing. Redis Cluster uses **16,384 hash slots**, not a generic clockwise virtual-node ring. Hash tags force selected keys into one slot, which can enable multi-key commands but can also create a hotspot. A client must handle redirects during topology change.

Rebalancing needs a protocol for owner generations, reads, writes, expiry, and in-flight fills. During a move, copying an older value after a newer write can resurrect stale data. Carry value versions and publish topology changes deliberately; routing theory alone never implements online migration.

## Replication and failover assumptions

Replicas can reduce rebuild pressure and provide additional read capacity. Asynchronous replication permits lag and may lose an acknowledged cache write during failover. Reading the primary avoids a replica-lag path, but never by itself makes origin/cache state globally linearizable.

Missed heartbeats indicate suspicion, not proof the old primary stopped. Promotion requires an ownership/election protocol preventing conflicting writers, or the cache must explicitly tolerate divergent derived values and rebuild them. A cache can sacrifice availability and return misses/errors while ownership is uncertain.

Replication is optional for cheaply reconstructible values, but loss of a whole shard can overwhelm the origin. Choose copies and failure domains using the origin's recovery capacity, not only the cache's hit rate.

## Expiry, eviction, and invalidation solve different problems

**Expiry** removes values after a deadline. **Eviction** removes values under memory pressure. **Invalidation** removes or supersedes values because their source changed. A value can be evicted long before its TTL, and a value without TTL can still be evicted under an applicable policy.

Least-recently-used (**LRU**) favors recently read values; least-frequently-used (**LFU**) favors repeated use under its aging policy. Redis implements approximate policies and requires explicit `maxmemory-policy` configuration; `allkeys-lru` is no universal default. Reserve memory for overhead/buffers and test the configured policy under pressure.

A TTL bounds time since **cache insertion** under the implemented expiry semantics. It never guarantees source age when a loader read an already stale replica, spent a long time computing, or repeatedly refreshed the same old value. Store source version/observation time when that distinction matters.

Synchronous write-through is not automatically atomic across database and cache. Write-behind makes the cache part of the write-durability path and cannot retain this chapter's assumption that every lost value is harmless. Pub/Sub invalidation can be missed during disconnect; pair it with expiry, version checks, or a durable recovery mechanism where required.

## Trace the stale-fill race

```text
Reader R misses and reads origin version 7.
Writer W commits version 8 and deletes the cached value.
Reader R finishes late and caches its old version 7.
Later readers hit version 7 until another correction occurs.
```

Deleting after the write never stopped the older in-flight fill. A version check works only when the writer's newer version or invalidation generation is visible before the old loader publishes. Other options are a generation/tombstone barrier, serialized per-key loading/writing, or an explicitly accepted staleness window. A "double delete after a delay" can reduce probability but never proves safety for arbitrarily slow readers.

For immediate revocation or inventory authorization, read/check the authoritative state or use a mechanism with the required consistency contract. Short TTLs cannot replace that decision.

## Coalesce misses without creating an unlimited wait queue

A local single-flight loader shares one pending origin request per key in one process. Across processes, there can still be several loads. A distributed lease reduces that work only while its owner is current; a stalled old loader must never publish stale results after a replacement load without a version/ownership check.

Bound origin concurrency, waiting callers, loader timeout, retry age, and per-key result size. Add expiry jitter or refresh-ahead for suitable data. Serve stale data only where policy permits it, with a maximum source age; never use that fallback for revoked permissions or authoritative payments.

A complete cache outage can be an application outage if the origin cannot handle full demand. Recovery may require request shedding, a circuit breaker, bounded stale fallback, warm-up, and reduced features. "Always fall through to the database" is no complete resilience plan.

## Hot keys and large values

Adding nodes spreads many keys but never divides reads to one owner of one key. Replicate immutable or versioned hot values, use short-lived local caches, or fan out through an appropriate read layer. Suffix copies require coordinated updates and invalidation; they are no independent shards of one mutable value.

Limit large values and serialization work. Splitting a value into chunks adds multi-key read consistency and missing-chunk handling; carry a manifest/version and never combine chunks from different generations. Negative cache entries also need authorization scope and an appropriate short lifetime, since "not found" can change or differ by caller.

## Real-world choices and failure checks

| Condition | Decision |
| ------------------------------- | ------------------------------------------------------------------------------------- |
| Cheap origin and modest traffic | One cache or no cache may suffice; avoid cluster complexity without measured need. |
| Cache-cold rollout | Stagger, warm representative keys, limit origin loads, and watch readiness/freshness. |
| Replica lag | Route freshness-sensitive reads appropriately or treat the result as a miss. |
| Topology split | Reject uncertain writes or accept/rebuild under a stated derived-data policy. |
| Private cached response | Require scoped keys and current authorization, including revocation behavior. |

Monitor hit/miss/error rates separately, origin load and queueing, oldest loader, eviction/expiry rate, value size, memory overhead, per-node skew, replication lag, stale-version detection, and cold-start recovery. A high hit rate can hide wrong or obsolete results.

## Questions to settle before rollout

Test stale-fill races, missed invalidation, tenant isolation, expiry/eviction interaction, failed loaders, hot-key bursts, topology migration, and complete cache loss. Document which operations tolerate stale responses and which bypass the cache. Keep the origin recovery budget explicit and benchmark actual network/codec latency before claiming sub-millisecond reads.

## Summary

A distributed cache combines routing, replication, finite-memory policy, and origin-relative correctness. Consistent hashing or slots distribute keys; they do not solve hot keys, stale fills, or failover ownership. Scoped keys, versioned population, bounded miss coalescing, and an origin-safe outage plan determine whether the cache improves the system reliably.

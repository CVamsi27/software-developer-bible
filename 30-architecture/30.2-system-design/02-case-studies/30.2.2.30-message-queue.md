# Message Queue System Design

## Definition

A message broker accepts work or events so producers and consumers do not have to act at the same time. An order service can publish an order event while billing and notifications process it independently. The broker's acceptance, a consumer's acknowledgment, and the business action's success are different facts.

> **Textbook Definition:** A message broker accepts and stores messages for later consumption, defining acknowledgments, persistence, routing, ordering, and redelivery independently of consumer business effects.

This case designs a partitioned replayable log. The [broker stack](../../../20-backend/20.9-message-brokers/INDEX.md) and canonical [Kafka](../../../20-backend/20.6-microservices/02-communication-and-messaging/20.6.2.03-kafka.md) and [RabbitMQ](../../../20-backend/20.6-microservices/02-communication-and-messaging/20.6.2.04-rabbitmq.md) chapters own their implementation examples.

## First Principles

A producer can lose its response after the broker accepted a message. A consumer can crash after performing work but before acknowledging it. Both gaps create retries, so durable storage and stable message identity are needed in addition to transport.

One ordered log serializes append order. Several logs provide parallelism but only local order. Replication improves failure recovery, while requiring multiple copies to accept writes can reduce availability when replicas are unreachable. The acknowledgment rule defines which trade is actually made.

## Scope and capacity assumptions

Support topics, partitions, authenticated producers, consumer groups, retention, replay, partition leadership, quotas, and inspectable errors. Specify maximum record/batch size and producer/consumer buffer limits. Begin with append-only retained logs; delayed work, priority queues, and complex routing require additional policies.

Assume 100,000 messages/second averaging 1 KB: about 100 MB/s or 8.64 TB/day of logical payload. With three copies and seven-day retention, raw payload copies alone approach 181.44 TB, before indexes, protocol, compression, and headroom. A million/second increases that by ten times. Choose partitions from measured bytes, append/replication cost, and consumer processing throughput, not a universal messages-per-second table.

Set latency objectives separately for accepted append and useful consumer completion. A broker cannot promise sub-10ms business completion when the handler takes a second.

## How the log fits together

```text
Producer → partition leader → replicated append → acceptance response
                                ↓
                     partitioned retained logs
                                ↓
               group A readers       group B readers
                 billing                notifications
                    ↓                        ↓
               group offsets            group offsets

Metadata controller → partition ownership / membership / failover
```

A **topic** is a logical stream. A **partition** is one ordered append log. An **offset** identifies a position within that partition, not a global sequence across the topic. A consumer group tracks its own progress, so billing and notifications can read the same records independently without deleting them from each other's view.

Each partition has segments and sparse indexes to locate offsets. Sealed segments can be retained or removed under policy. Disk/page-cache behavior, flush settings, replication, and the failure model determine persistence; an acceptance does not universally imply an `fsync` for every record. A batch can amortize I/O while changing its latency and crash boundary.

## Route keys and preserve the required ordering

Partitioning by aggregate ID, such as order ID, keeps related events on a partition under a fixed compatible routing rule. Changing partition count or partitioner can move a key, so migration must address old/new streams if per-key ordering remains required.

Log order is broker append order, not necessarily event time or intended business sequence. Several producers racing to send events for one order need an authoritative version/sequence rule if causal ordering matters. Parallel handlers, retries, and multiple in-flight external calls can finish out of order even when the records were read in order.

Within a conventional partition-assigned consumer group, one active owner reads a partition at a time under the group protocol. On reassignment, an old worker can still be running. Generation/ownership checks protect commits, but external effects need their own fencing/idempotency boundary. A consumer should finish/cancel or transfer work deliberately during rebalance rather than keep processing an unowned partition indefinitely.

## Define acceptance and leader recovery

In a Kafka-like design, the leader appends and followers replicate. **In-sync replicas (ISR)** are copies meeting the protocol's progress criteria. `acks=all` waits according to the current ISR acknowledgment rule, while `min.insync.replicas` can reject writes when too few copies are available. The two settings cooperate; `acks=all` alone is not a universal three-copy guarantee.

`acks=0` provides no broker acceptance result; `acks=1` waits for the leader boundary. Client defaults vary by implementation/version; modern Kafka producers commonly default to `all`, so do not teach leader-only acknowledgment as a timeless default. Producer idempotence constrains broker-level retry duplication under its session/protocol rules; it does not deduplicate every arbitrary business event submitted with a new identity.

Leadership recovery needs a metadata/election protocol, current log boundaries, and rules about promoting out-of-sync copies. Unclean promotion can favor availability while losing accepted data. A network timeout or missed heartbeat is not proof that the previous leader stopped, so ownership epochs and rejection of stale operations matter.

## Trace the consumer commit boundary

```text
Record offset 41: reserve stock for order7
Consumer performs the reservation.
Consumer crashes before committing progress.
Replacement reads offset 41 again.
```

If the reservation has a stable event/action key, the second application returns the previous result. If it blindly decrements stock again, broker replay duplicates the business effect. Commit the next resume offset only after the chosen processing boundary, and avoid numeric precision loss in large offsets.

Committing before processing can skip work after a crash (**at-most-once** processing under that boundary). Committing after processing permits repeats (**at-least-once**). Offset commits and external database writes need a joint protocol: a local transaction can atomically apply an event and record its ID/checkpoint, or downstream APIs may provide idempotency.

For Kafka-to-Kafka processing, a supported transaction can atomically commit produced records and consumed offsets; consumers must use the appropriate isolation/read protocol. It does not include an unrelated payment provider, email server, or database. Explain the protected boundary instead of declaring all exactly-once claims impossible or all transactions globally exact.

## Retention, replay, and schema evolution

Retention is independent of consumer progress. A slow group can fall behind deleted history; restoring an offset then needs an explicit out-of-range/recovery policy. Monitor oldest unread age relative to retention, not only record-count lag.

Compaction retains later values/tombstones according to key and policy; it is not a full event-history archive and does not immediately leave one row per key. Replay after compaction may not recreate every original business event. An audit log and a latest-state topic serve different purposes.

Enforce envelope/schema compatibility and bound payloads. A schema registry checks supported structural rules; semantic changes to units, event meaning, authorization, or ordering still need migrations. Include tenant/event identity, event time, schema version, and relevant aggregate version without placing secrets in broadly readable topics.

## Poison messages, backpressure, and fairness

Malformed input can be rejected at ingestion; a valid message may still fail permanently in a handler. Define retry count/age, backoff, and a dead-letter or quarantine path with stable source identity. Moving a poison record aside lets later work advance but can break per-entity sequence; the business policy must say whether to block, compensate, or continue.

Replaying a dead-letter item is a controlled recovery action, not a new business event with a random ID. Authenticate operators, preserve provenance, and avoid exposing sensitive payloads in logs or unprotected dashboards.

Bound producer buffers, broker disk, consumer in-flight work, and retry queues. Scaling consumers helps only up to useful partition parallelism and downstream capacity. One hot partition remains hot when more idle consumers join. Reject, defer, or apply declared loss policy when durable acceptance cannot be supported; memory buffering cannot promise unlimited availability.

## Compare broker models using conditions

| Model | Strength | Important boundary |
| ------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Kafka-style retained log | Independent groups and replay by position | Per-partition order, retention/checkpoint discipline, routing migration. |
| RabbitMQ queues | Delivery/routing and explicit acknowledgements | Multiple consumers and redelivery can change observed processing order; durable/persistent/confirm settings matter. |
| RabbitMQ streams | Retained log-style consumption | Different model from a queue that removes acknowledged messages. |
| SQS standard | Managed work distribution | Duplicates and best-effort ordering; external effects still need retry safety. |
| SQS FIFO | Order within a message group; producer deduplication is scoped to its documented five-minute window | No global ordering across groups and no automatic exactly-once external action. |

Benchmark the selected deployment and message sizes. Fixed claims such as "RabbitMQ100K/s" or "SQS300K/s" omit queue types, batching, regional limits, and processing cost.

## Operations and best practices

Observe acceptance latency/errors, ISR shrinkage, leader elections, replica lag, disk growth, oldest consumer backlog, rebalance frequency, poisoned records, retry age, and downstream saturation. Keep control-plane metadata recovery, partition data recovery, and client recovery as separate runbooks.

Test response loss, producer retries, replica outage, unsafe promotion policy, rebalance with in-flight work, consumer crash before/after side effect, retention overrun, schema incompatibility, and hot-key overload. A durable log is useful only when recovery and application idempotency are also tested.

## Summary

A broker separates durable acceptance from later consumption. Partition logs provide local append order and replay, while groups track independent progress. Replication/acknowledgment policy determines accepted-write recovery; consumer commits and stable business identities determine retry safety. Explicit retention, schema, ownership, and backpressure boundaries turn transport guarantees into reliable application behavior.

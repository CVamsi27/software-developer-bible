# Message Queue System Design

## TL;DR

Design a distributed message queue (like Kafka/RabbitMQ) that supports pub/sub and point-to-point messaging, with durability, ordering guarantees, and horizontal scaling.

**Why it matters:** Message queues are the backbone of every async system. Tests understanding of write-ahead logs, consumer groups, delivery guarantees, ordering, and backpressure — concepts that appear in almost every system design interview.

## Requirements

### Functional Requirements

- `produce(topic, message)` — publish a message to a topic
- `consume(topic, consumer_group, callback)` — subscribe to messages
- Support multiple topics and consumer groups
- Message ordering within a partition
- Message replay (re-process from any offset)
- At-least-once delivery guarantee

### Non-Functional Requirements

- High throughput: millions of messages/sec
- Low latency: < 10ms end-to-end
- Durability: messages persist to disk
- Horizontal scaling: add brokers without downtime
- Fault tolerance: no message loss on broker failure

## Core Concepts

### 1. Topics and Partitions

```text
Topic: Logical channel for messages (e.g., "orders", "payments")
Partition: Physical division of a topic for parallelism

Topic "orders" with 4 partitions:
  Partition 0: [msg1, msg5, msg9, ...]   → Broker 1
  Partition 1: [msg2, msg6, msg10, ...]  → Broker 1
  Partition 2: [msg3, msg7, msg11, ...]  → Broker 2
  Partition 3: [msg4, msg8, msg12, ...]  → Broker 2

Key guarantees:
- Messages in SAME partition are ORDERED
- Messages ACROSS partitions have NO ordering guarantee
- Partition assignment: hash(message_key) % num_partitions
```

### 2. Consumer Groups

```text
Consumer Group: Set of consumers that process messages together

Rules:
- Each partition is consumed by exactly ONE consumer in a group
- If 4 partitions and 3 consumers: one consumer gets 2 partitions
- If 4 partitions and 6 consumers: 2 consumers are idle
- Multiple groups can read the same topic independently

Example:
  Topic: orders (4 partitions)
  Group "billing":
    Consumer 1 → Partition 0, Partition 1
    Consumer 2 → Partition 2, Partition 3
  Group "notifications":
    Consumer 1 → Partition 0, Partition 1
    Consumer 2 → Partition 2, Partition 3
  → Both groups get ALL messages, independently
```

### 3. Write-Ahead Log (WAL)

```text
Messages are appended to an immutable, ordered log on disk.

Partition 0 log:
  [offset=0] {key: "order-1", value: {...}, timestamp: T1}
  [offset=1] {key: "order-2", value: {...}, timestamp: T2}
  [offset=2] {key: "order-3", value: {...}, timestamp: T3}

Properties:
- Append-only (sequential I/O, very fast)
- Messages immutable after write
- Offset = position in log (monotonically increasing)
- Retention: configurable (7 days, infinite, size-based)
- Compaction: optional (keep only latest value per key)
```

### 4. Replication (ISR - In-Sync Replicas)

```text
Each partition has:
- 1 Leader broker (handles all reads and writes)
- N Follower brokers (replicate from leader)

Write path:
1. Producer sends message to partition leader
2. Leader appends to local log
3. Leader sends to followers (ISR)
4. Wait for acks from N followers (configurable: acks=1, all)
5. Acknowledge producer

ISR (In-Sync Replicas):
- Followers that are caught up with leader (within threshold)
- If a follower falls behind, it's removed from ISR
- If leader dies, a new leader is elected from ISR

acks configuration:
- acks=0: fire and forget (fastest, may lose messages)
- acks=1: leader ack only (default, some loss risk)
- acks=all: all ISR ack (safest, highest latency)
```

## Delivery Guarantees

```text
AT-MOST-ONCE:
  - Producer fires and forgets (acks=0)
  - Consumer commits offset BEFORE processing
  - If consumer crashes → message lost
  - Use case: metrics, logs (loss OK)

AT-LEAST-ONCE (default):
  - Producer waits for ack
  - Consumer commits offset AFTER processing
  - If consumer crashes → message reprocessed
  - Consumer MUST be idempotent
  - Use case: most systems (payments, orders)

EFFECTIVELY-ONCE:
  - Combine at-least-once + idempotent consumer
  - Deduplication via message ID or idempotency key
  - Or use Kafka transactions (read-process-write atomic)
  - Use case: financial systems

EXACTLY-ONCE (theoretical):
  - Requires distributed transactions across all systems
  - Almost impossible in practice
  - Settle for effectively-once
```

## Ordering Guarantees

```text
Per-partition ordering:
  - Messages with same key go to same partition
  - hash("user-123") % 4 → always partition 2
  - All events for user-123 are processed in order

Global ordering:
  - Only 1 partition (no parallelism)
  - Throughput limited to single broker
  - Almost never worth it

In practice:
  - Partition by aggregate ID (user_id, order_id)
  - Guarantees per-entity ordering
  - Enables parallel processing across entities
```

## Backpressure and Flow Control

```text
Problem: Producers faster than consumers → queue grows unbounded

Solutions:
1. Rate limiting at producer:
   - Token bucket per producer
   - Reject or buffer excess messages

2. Scale consumers:
   - Add more consumers to consumer group
   - Kafka: rebalance partitions across consumers

3. Slow the producer:
   - Producer blocks when queue depth > threshold
   - Bounded buffer with back-pressure

4. Drop messages (non-critical):
   - For metrics/logs: drop oldest if queue > 1M
   - Alert on high drop rate

5. Alert and auto-scale:
   - Monitor consumer lag (latest offset - committed offset)
   - Auto-scale consumers when lag > threshold
```

## Comparison: Kafka vs RabbitMQ vs SQS

| Feature | Kafka | RabbitMQ | SQS |
| ---------- | ---------------------------- | ------------------------ | ------------------ |
| Model | Distributed log | Broker (AMQP) | Managed queue |
| Ordering | Per-partition | Per-queue | Per-queue (FIFO) |
| Throughput | Millions/sec | 100K/sec | 300K/sec |
| Retention | Configurable (days) | Until consumed | 14 days max |
| Replay | Yes (offset-based) | No (once consumed, gone) | No |
| Delivery | At-least-once, transactional | At-least-once, ack-based | At-least-once |
| Use case | Event streaming, audit | Task queues, RPC | Simple async tasks |

## Trade-offs

| Decision | Choice | Why | Alternative |
| ------------ | -------------------------- | ----------------------------------- | ----------------------------------- |
| Storage | WAL (append-only log) | Sequential I/O, replay capability | Random-access DB (slower) |
| Partitioning | Hash-based | Even distribution, per-key ordering | Range-based (hotspots) |
| Ordering | Per-partition | Parallelism + per-entity order | Global (single partition, no scale) |
| Delivery | At-least-once + idempotent | Simplest correct guarantee | Exactly-once (complex, expensive) |
| Replication | ISR with configurable acks | Balance durability vs latency | Sync all (slow writes) |

## What Could Be Better

- **Schema registry:** enforce message schemas (Avro/Protobuf) to prevent breaking changes
- **Dead letter queue (DLQ):** separate queue for poison messages that always fail
- **Exactly-once transactions:** Kafka transactions for read-process-write atomicity
- **Cross-datacenter replication:** MirrorMaker for geo-distributed queues
- **Message-level TTL:** auto-expire old messages instead of retention-based

## Interview Script

> "I'd design this with topics partitioned by aggregate ID — hash(order_id) % num_partitions ensures per-order ordering. Each partition is a WAL on disk with append-only writes. Consumer groups allow multiple systems to independently process the same events. Replication uses ISR with acks=all for durability. Delivery is at-least-once; consumers are idempotent via message ID deduplication. Backpressure is handled by monitoring consumer lag and auto-scaling consumers. We'd use Kafka for event streaming and audit, RabbitMQ for task queues with complex routing."

## Summary

1. **Partitioning by aggregate ID buys ordering where it matters** — per-key order without serializing the whole topic
2. **The partition log is a WAL** — append-only, fsync-backed, replicated via ISR with `acks=all` for durability
3. **Delivery is at-least-once, so consumers own idempotency** — message-ID dedup turns redelivery into a no-op
4. **Backpressure is consumer lag made visible** — monitor lag, auto-scale consumers, shed or buffer upstream
5. **Kafka and RabbitMQ are complements, not rivals** — event streaming + audit vs task queues with complex routing

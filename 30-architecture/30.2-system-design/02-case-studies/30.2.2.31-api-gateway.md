# API Gateway System Design

## Definition

An API gateway receives client requests and forwards them to selected backend services under shared edge policies. For `/orders/7`, it may validate the caller, apply admission limits, select an orders-service instance, and forward the request. The orders service still decides whether that caller may read order 7.

> **Textbook Definition:** An API gateway is a client-facing routing and policy boundary that forwards requests to backend services while applying configured authentication, admission, transformation, and observability controls.

This case studies the design and failure boundaries. The canonical [REST gateway chapter](../../../20-backend/20.3-rest-apis/04-edge-and-scale/20.3.4.02-api-gateway.md) owns HTTP forwarding examples; the [microservices gateway chapter](../../../20-backend/20.6-microservices/01-service-topology/20.6.1.02-api-gateway.md) owns service-boundary choices. Do not turn a short routing snippet into a claimed production proxy.

## First Principles

Every forwarded request passes through another shared dependency. The gateway can reject abusive work early, but a slow identity provider, unbounded buffering, or bad route configuration can now affect many services at once.

Caller-supplied headers are untrusted. If a backend accepts identity headers without checking who set them, a direct caller can impersonate another user. Central authentication therefore needs a protected downstream trust boundary, while resource-specific authorization remains with the service that knows the resource.

## Requirements and capacity assumptions

Support route/method matching, authentication, scoped admission, upstream selection, bounded forwarding, and route-level observability. Add response caching, aggregation, or protocol translation only for routes needing them. Decide streaming, upload, WebSocket, and long-running-request behavior explicitly.

Estimate requests, simultaneous connections, bytes/second, upload sizes, upstream latency, and retry amplification. With 10,000 requests/second and 200ms mean upstream time, roughly 2,000 requests are in flight before queueing and retries. At 100 KB per buffered request, payload buffers alone could consume about 200 MB. Streaming reduces some buffering but still needs backpressure and connection budgets.

Benchmark added latency and end-to-end availability by route class. More gateway replicas remove one process bottleneck; shared dependencies, configuration, quotas, and regional failure can still affect all replicas.

## A deliberate policy pipeline

```text
Client → TLS / coarse edge abuse limits → request framing and route match
                                       ↓
                       authentication + route admission
                                       ↓
                          authorized upstream selection
                                       ↓
                    bounded forwarding / cancellation
                                       ↓
                    response policy / safe observability
```

Coarse unauthenticated limits protect expensive token verification; caller-scoped quotas require authenticated identity. Route-specific validation and body limits must run before expensive buffering/forwarding. The exact order is a documented policy, not one universal list.

Terminate each rejection with a defined status and bounded response: invalid credentials commonly produce 401, denied access 403, exceeded limits 429, and upstream failure/timeout an appropriate 5xx. Preserve a useful request ID without logging tokens or raw private bodies.

## Route configuration is an executable contract

The following is **illustrative configuration**, not syntax promised to work unchanged in Kong, Nginx, or AWS:

```yaml
routes:
  - id: orders-read-v1
    path_prefix: /api/v1/orders
    methods: [GET]
    upstream_id: orders-v1
    authentication: required
    max_request_bytes: 16384
    upstream_timeout_ms: 1000
    retry_policy: read-only-bounded
```

Define whether a prefix matches the exact path and descendants. `/api/v1/orders-extra` must not accidentally match `/api/v1/orders`. Test percent encoding, duplicate slashes, normalization, host/method matching, route precedence, and query preservation. The proxy and backend must agree on framing/normalization or attackers may exploit their disagreement.

Upstreams come from validated configuration/discovery, not arbitrary caller URLs; otherwise forwarding becomes a server-side request-forgery capability. Restrict schemes and destinations, and do not follow an upstream redirect outside that policy. Define how discovery handles readiness, stale endpoints, and rollout versions.

Validate a complete configuration before publishing it. Each request pins one configuration generation so routing, authentication, and cache policy do not mix old/new versions midway. Roll out with canaries and retain a known-good rollback. A checksum proves artifact identity, not that its routing or policy is correct.

## Authentication and downstream identity

For JWT authentication, validate signatures with an allowlisted algorithm and trusted keys, then check the expected issuer, audience, token purpose/type, required expiry/time claims, and applicable scopes. A valid signature for another audience or token purpose is not permission to call this API. Pin trusted key-set locations; do not fetch attacker-controlled key URLs from token headers.

Cache signing keys with bounded refresh and rotation rules. An unknown key ID can trigger a rate-limited/coalesced refresh, not an unlimited fetch for every invalid signature. Define behavior during key-provider failure, retired-key grace, and emergency revocation. Key caching alone does not prove seamless rotation or immediate token revocation.

Strip inbound identity/role/forwarded headers that the gateway owns, then supply verified identity over a protected service channel or signed context. Backends authenticate that channel/context and enforce resource/tenant policy. Network isolation reduces direct access but does not replace authorization or protect every internal compromised caller.

Trust forwarded client-IP information only from known upstream proxies. Per-IP limits are coarse and can group many legitimate users behind one address. Cross-origin resource sharing (**CORS**) governs browser access to responses; it is not authentication or network access control.

## Admission, retries, and forwarding correctness

Token buckets permit a configured burst and refill over time; implement an atomic state transition under the selected store. The [rate-limiter case](30.2.2.13-rate-limiter.md) owns algorithm examples. A Lua script touching multiple undeclared/different-slot Redis keys or updating only one key's expiry does not implement a safe clustered bucket.

Separate caller quota from upstream concurrency and gateway queue limits. Decide fail-open/closed behavior by route when the limiter is unavailable; neither policy is universally correct. Use bounded waits and a clear overloaded response rather than accepting unlimited work.

Forward methods, bodies, queries, status, and permitted headers correctly. Remove hop-by-hop headers as required, handle streaming/backpressure, and propagate client cancellation and deadlines. A timeout does not prove an upstream write failed. Automatically retrying a POST may duplicate an order even if the first response was lost.

Permit retries only under the route's idempotency/side-effect contract, with a total request deadline, bounded attempts, jitter, and retry budget. Retry amplification across client, gateway, and service layers can turn three attempts at each layer into 27 upstream attempts. Prefer one intentional owner for each retry policy.

## Cache only representations with the right scope

Cache keys include route/config generation, normalized resource/query, method where relevant, tenant/caller visibility, representation negotiation, and authorization/policy dimensions. Respect the actual response's cache controls and varying headers; a URL-only cache can expose personalized order data.

Do not cache authorization failures or private responses under a public key. Invalidation and revocation behavior must match the data's requirements. Public cache hits may still need a current policy check for removed content. TTL does not convert stale permissions into current authorization.

## Aggregation and protocol translation

A backend for frontend (**BFF**) shapes data for a particular client experience. It can be separate from the general forwarding gateway. Several BFFs are useful when needs differ materially, not mandatory for every web/mobile/partner application.

For a profile view, fan out to user, recent-orders, and notification services with separate bounded work under one parent deadline. Parallel time is roughly the slowest required branch **plus** gateway/network/merge work, not precisely their maximum. Decide which branches are required, which can return a labeled partial result, and how cancellation/error budgets work. `Promise.all` rejects early but does not cancel the other requests.

Business transactions and compensation belong in an owning service/workflow, not hidden inside an aggregation handler. Protocol translation also requires schema/error/deadline/streaming mapping; HTTP-to-gRPC is not automatically faster, and GraphQL federation is not a generic improvement to every gateway.

## Circuit breaking and failure decisions

A circuit breaker stops selected upstream calls after a measured failure condition and permits bounded recovery probes. Scope it appropriately so one route or tenant does not unnecessarily block healthy traffic. Distinguish upstream capacity/network failures from ordinary client validation errors.

| Condition | Required decision |
| ---------------------------------- | -------------------------------------------------------------------------------------------- |
| No ready upstream | Fail or serve a permitted fallback; do not route to arbitrary/unready instances. |
| Identity/key dependency outage | Apply the documented cached-key/expiry policy; do not accept unverifiable tokens by default. |
| Response lost after an order write | Reconcile/retry by stable business identity, not automatic fresh POST. |
| Slow upload/client | Enforce time/size/connection budgets and streaming cancellation. |
| Bad shared configuration | Revert a validated generation and verify route/policy behavior after rollback. |

Gateway instances hold connections, pools, circuit state, and sometimes local caches even if they store no durable session data. Horizontal scalability requires coordinating the relevant shared limits and accepting/documenting local-state differences. Autoscale using concurrency, bandwidth, queueing, CPU/memory, and latency; request rate alone can miss a small number of huge uploads.

## Verify trust and failure boundaries

Use a maintained proxy/gateway for transport machinery unless building it has a justified purpose. Keep policy plugins small, versioned, and tested. Log bounded route templates and outcome codes, not raw unmatched URLs or credential-bearing query strings. Trace downstream timing with trusted propagation and redact sensitive context.

Test path boundaries, spoofed identity headers, issuer/audience mismatch, key-refresh storms, tenant cache isolation, upstream framing, body/stream limits, client cancellation, timeout-after-write, retry amplification, and configuration rollback. Load-test the full policy pipeline, including cold keys/caches and failing dependencies.

## Summary

A gateway is a routing and policy dependency with a precise downstream trust boundary. Safe configuration, authenticated identity propagation, bounded forwarding, route-specific retry contracts, and scoped caches matter more than a long feature list. Resource authorization and business recovery remain with their owning services, while the gateway makes admission and transport behavior explicit.

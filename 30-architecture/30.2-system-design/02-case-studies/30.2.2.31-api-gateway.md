# API Gateway System Design

## TL;DR

Design an API Gateway that serves as the single entry point for all client requests, handling routing, authentication, rate limiting, load balancing, and request transformation.

**Why it matters:** The API Gateway is the front door of every microservices architecture. Tests understanding of cross-cutting concerns, service mesh vs gateway trade-offs, protocol translation, and the BFF (Backend for Frontend) pattern.

## Requirements

### Functional Requirements

- Route requests to appropriate microservices
- Authentication and authorization (JWT validation, API keys)
- Rate limiting (per-user, per-IP, per-API-key)
- Request/response transformation (header injection, body mapping)
- Load balancing across service instances
- Request aggregation (fan-out to multiple services, merge response)
- API versioning (URL path, header, content negotiation)
- Caching of frequent responses
- Logging and monitoring of all requests

### Non-Functional Requirements

- Handle 100K+ requests per second
- Sub-10ms added latency for pass-through requests
- 99.99% availability (higher than any downstream service)
- Horizontal scaling (stateless design)
- Graceful degradation (circuit breaker for unhealthy services)

## Core Components

### 1. Request Routing

```yaml
# Route configuration (like Kong/Nginx routes)
routes:
  - path: /api/v1/users/**
    service: user-service
    methods: [GET, POST, PUT, DELETE]
    strip_prefix: /api/v1

  - path: /api/v1/orders/**
    service: order-service
    methods: [GET, POST]
    rate_limit: 100/min

  - path: /api/v2/products/**
    service: product-service-v2
    methods: [GET]
    header_rewrite:
      X-API-Version: "2"
```

### 2. Rate Limiting (Token Bucket)

```java
class TokenBucketRateLimiter {
    private final Redis redis;
    private final int capacity;
    private final int refillRate; // tokens per second

    public boolean allowRequest(String key) {
        String script = """
            local tokens = redis.call('GET', KEYS[1]) or ARGV[1]
            local last_refill = redis.call('GET', KEYS[1] .. ':ts') or ARGV[2]
            local now = tonumber(ARGV[3])

            -- Refill tokens
            local elapsed = now - tonumber(last_refill)
            tokens = math.min(ARGV[1], tonumber(tokens) + elapsed * tonumber(ARGV[4]))

            if tokens >= 1 then
                tokens = tokens - 1
                redis.call('SET', KEYS[1], tokens)
                redis.call('SET', KEYS[1] .. ':ts', now)
                redis.call('EXPIRE', KEYS[1], 3600)
                return 1
            else
                return 0
            end
            """;
        return (long) redis.eval(script, List.of(key),
            List.of(capacity, "0", System.currentTimeMillis()/1000, refillRate)) == 1;
    }
}
```

### 3. Authentication Pipeline

```text
Request arrives at gateway:

1. Extract token from header: Authorization: Bearer <JWT>
2. Validate JWT signature against JWK endpoint
3. Check expiry (exp claim)
4. Extract claims (user_id, roles, scopes)
5. Inject claims as headers for downstream services:
   X-User-Id: 123
   X-User-Roles: admin,editor
   X-Request-Id: uuid (traceability)
6. If invalid → 401 Unauthorized (never forward to service)

JWK rotation:
- Cache JWKS endpoint response (refresh every 5 min)
- If signature fails with cached keys → force refresh
- Supports key rotation without downtime
```

### 4. Request Aggregation (BFF Pattern)

```text
Client requests: GET /api/profile
Gateway fans out to 3 services simultaneously:

  ┌─→ user-service    → { name, email }
  ├─→ order-service   → { recent_orders: [...] }
  └─→ notification-service → { unread_count: 5 }

Gateway merges:
  {
    "name": "Alice",
    "email": "alice@example.com",
    "recent_orders": [...],
    "unread_count": 5
  }

Latency = max(service_latencies) instead of sum
```

### 5. Circuit Breaker

```text
States:
  CLOSED (normal): requests pass through
    → if failures > threshold → OPEN

  OPEN (broken): requests fail immediately (no forwarding)
    → after timeout → HALF-OPEN

  HALF-OPEN (testing): allow one probe request
    → if success → CLOSED
    → if failure → OPEN

Configuration:
  failure_threshold: 5 failures in 30s
  timeout: 30s
  half_open_requests: 1

Benefits:
- Prevents cascade failures
- Gives failing service time to recover
- Fails fast for clients (no waiting for timeout)
```

## API Gateway vs Direct Service Calls

```text
| Feature          | API Gateway       | Direct Calls      |
| ---------------- | ----------------- | ----------------- |
| Single entry     | Yes               | No                |
| Cross-cutting    | Centralized       | Distributed       |
| Client coupling  | Loose             | Tight             |
| Protocol support | Multiple          | Service-specific  |
| Complexity       | Additional layer  | Simpler           |
| Auth             | One place         | Every service     |
| Rate limiting    | One place         | Per-service       |
| Monitoring       | Centralized       | Distributed       |
```

## Common Patterns

### 1. Backend for Frontend (BFF)

```text
Problem: Web, Mobile, IoT have different data needs

Solution: Separate gateway per client type

Web BFF:     Full API, field-heavy responses
Mobile BFF:   Reduced payload, offline support
IoT BFF:      Binary protocol, small payloads
Partner BFF:  Limited API, strict rate limits

Each BFF is a thin service that talks to backend services.
```

### 2. Edge Service

```text
Gateway handles all security at the edge:
- Authentication (JWT validation)
- Authorization (role-based, scope-based)
- TLS termination
- DDoS protection (WAF + rate limiting)
- Request validation (schema, content-type)

Services focus purely on business logic.
Services can be internal (no public endpoint).
```

### 3. Protocol Translation

```text
Client speaks HTTP/JSON → Gateway translates to:
- gRPC for internal service-to-service
- GraphQL for flexible queries
- WebSocket for real-time
- Thrift for high-performance RPC

Example:
  Client: GET /api/users/123 (HTTP/JSON)
  Gateway → gRPC: UserService.GetProfile(userId=123)
  Gateway ← gRPC: { name: "Alice", ... }
  Gateway → Client: { "name": "Alice", ... } (HTTP/JSON)
```

## Anti-Patterns

```text
1. GOD GATEWAY:
   - Gateway contains business logic
   - Fix: Gateway is pure infrastructure (routing, auth, rate limit)
   - Business logic belongs in services

2. SINGLE GATEWAY FAILURE:
   - One gateway handles everything → SPOF
   - Fix: Multiple gateway instances behind load balancer
   - Fix: DNS failover, health checks

3. TIGHT COUPLING:
   - Gateway knows about every service's internal API
   - Fix: Service discovery (Consul, Eureka, K8s services)
   - Fix: Gateway routes by path prefix, not service details

4. NO OBSERVABILITY:
   - Requests disappear into gateway black box
   - Fix: Structured logging, distributed tracing (OpenTelemetry)
   - Fix: Metrics per route, per service, per client

5. SKIPING GATEWAY:
   - Services call each other directly for some requests
   - Fix: Enforce all external traffic through gateway
   - Fix: Internal service mesh for service-to-service
```

## Trade-offs

| Decision | Choice | Why | Alternative |
| ------------- | --------------------------------- | -------------------------------------- | ------------------------------------------------ |
| Routing | Path-based + service discovery | Simple, flexible | Hardcoded service URLs (brittle) |
| Auth | JWT validation at gateway | One auth check, services trust headers | Auth at every service (redundant) |
| Rate limiting | Token bucket in Redis | Distributed, accurate | Local rate limiting (per-instance, inexact) |
| Aggregation | Gateway-level fan-out | Fewer round-trips for clients | Client-side aggregation (more client complexity) |
| Protocol | HTTP/JSON external, gRPC internal | Client compatibility + performance | All HTTP (slower internal) |

## What Could Be Better

- **GraphQL Gateway:** single endpoint, client specifies exact data needs (Apollo Federation)
- **WebSocket support:** real-time push for chat, notifications, live updates
- **Request validation:** JSON Schema validation at gateway (reject bad requests early)
- **Chaos testing:** inject failures to test circuit breaker and degradation
- **Auto-scaling:** scale gateway based on request rate, not CPU (requests are fast)

## Interview Script

> "I'd put an API Gateway as the single entry point. It handles cross-cutting concerns — JWT validation, rate limiting (token bucket in Redis), circuit breakers for unhealthy services, and request logging. Routing is path-based with service discovery. For BFF, I'd have separate gateways per client type (web, mobile, IoT) with different payload shapes. Internal communication uses gRPC for performance. The gateway is stateless and horizontally scalable behind a load balancer."

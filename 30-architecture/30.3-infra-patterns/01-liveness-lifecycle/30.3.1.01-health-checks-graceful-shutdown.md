# Health Checks & Graceful Shutdown — Liveness, Readiness, SIGTERM

A database outage does not necessarily mean the application process is broken. Restarting every instance may add connection storms while the database recovers. Health checks tell the platform which action is useful; shutdown tells it how an instance leaves service without depending on unlimited cleanup time.

## Definition

**Health checks** expose selected lifecycle signals to the platform that starts, stops and routes traffic to instances. **Graceful shutdown** stops admitting work and finishes or safely transfers accepted work within a termination budget.

> **Textbook Definition:** Lifecycle probes report startup completion, restart eligibility or traffic eligibility. Graceful shutdown coordinates withdrawal, in-flight completion and resource cleanup before a bounded termination deadline.

A **liveness** failure can trigger restart after the configured threshold. A **readiness** failure withdraws normal serving eligibility without necessarily restarting. A **startup** probe gates the other probes during initialization; persistent startup failure can trigger restart. The configured controller determines the actual action, not the endpoint name alone.

## First Principles

A platform cannot infer the complete application contract from a running PID. A responsive endpoint is one observation; readiness must represent the work the instance can safely accept, while liveness should identify failures a restart can repair.

A request can already be admitted when routing changes. Withdrawal, routing propagation and process termination are distinct events, so shutting down needs an admission boundary plus a bounded drain. Closing a Node.js HTTP listener stops new connections; it does not inherently reset every active response.

The process can also die without running a handler. Accepted durable work must therefore recover after abrupt death, independently of graceful completion. A lost response can leave a committed mutation uncertain even when the server shut down correctly.

## How the Three Signals Differ

| Signal | Question | Suitable action/condition |
| --------- | ------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Liveness | Can this instance recover usefully by restarting? | Stuck process or an unrecoverable local failure; avoid coupling every shared dependency |
| Readiness | Can this instance accept its intended work now? | Initialization, required serving capability, deliberate withdrawal or admission state |
| Startup | Has the required boot phase completed? | Allow realistic initialization time before ordinary liveness/readiness enforcement |

A cheap liveness response proves the handler answered, not that a database is up. Labeling that response `database: up` is false evidence. A database `SELECT 1` tests a selected connection/query path; it does not prove schema compatibility, write permissions or every business transaction.

Readiness should reflect critical capability, not blindly ping every dependency. If Redis is optional and a safe degraded path exists, removing the whole fleet for Redis failure may be worse than serving that path. If all instances depend on a failed database, decide what routing/admission response is useful; readiness cannot conjure a healthy backend.

A table named `appointments` does not prove migrations completed. A startup gate can check the supported schema/version contract, while migration ownership and execution remain controlled separately. Do not run the same destructive migration independently during every replica's boot.

## Example: Trace Withdrawal Around One Request

```text
request R admitted → uses database → response completes
                             ↑
termination begins → withdraw readiness / stop new work
                   → routing may still have stale observations
                   → drain R while required dependencies remain usable
                   → close dependencies → exit
deadline exceeded  → force termination; R's outcome may need reconciliation
```

New work can be rejected with the defined response contract while admitted work drains. Long-lived WebSockets, streams and background jobs need their own reconnect, completion or transfer protocol. A fixed sleep only spends time; it does not prove that a load balancer stopped routing.

### Await the HTTP drain before closing its dependencies

This Node.js helper demonstrates the ordering for an already-listening ordinary HTTP server. `closeDependencies` is application-owned; the caller must choose one shutdown owner and handle the returned failure under its process/platform policy. The helper does not terminate the process or drain upgraded sockets/background workers.

```typescript
import type { Server } from 'node:http';

export function drainHttp(
  server: Server, closeDependencies: () => Promise<void>, graceMs: number,
): Promise<void> {
  if (!Number.isSafeInteger(graceMs) || graceMs <= 0) throw new RangeError('graceMs');
  return new Promise((resolve, reject) => {
    let settled = false;
    const finish = (error?: Error) => {
      if (settled) return;
      settled = true;
      clearTimeout(deadline);
      clearInterval(reapIdle);
      if (error) reject(error); else resolve();
    };
    const deadline = setTimeout(() => {
      server.closeAllConnections(); // ordinary HTTP connections, not upgraded sockets
      finish(new Error('Shutdown deadline exceeded'));
    }, graceMs);
    // Reap connections that become idle after shutdown begins.
    const reapIdle = setInterval(() => server.closeIdleConnections(), 25);
    server.close(error => {
      if (settled) return;
      if (error) { finish(error); return; }
      Promise.resolve().then(closeDependencies).then(() => finish(), error => finish(error));
    });
  });
}
```

The illustrative 25 ms sweep closes only idle ordinary HTTP connections, including ones that become idle after shutdown begins; it does not destroy R while its response is active. Verify this behavior on the deployed Node version. With R still active, the close callback waits; dependencies remain open. After R ends, cleanup starts. If the total drain/cleanup exceeds the deadline, the returned promise rejects. Forcibly closed responses can fail; work already committed is not undone. A timeout cannot cancel arbitrary dependency cleanup code, so the caller still needs the platform's final termination policy.

For NestJS, choose the framework lifecycle/shutdown integration or a coordinated custom signal handler. Enabling automatic shutdown hooks and independently running another `app.close()` handler can create competing cleanup owners. Verify the HTTP adapter and lifecycle-hook ordering; do not assume `app.close()` supplies every worker/socket/drain contract. See [NestJS lifecycle](../../../20-backend/20.2-nestjs/04-quality-and-operations/20.2.4.03-lifecycle-hooks-graceful-shutdown.md) for its implementation home.

## Kubernetes Owns Another Part of the Protocol

Configure probe timing/thresholds from actual boot/serving behavior. A startup probe suppresses the ordinary probes until it succeeds. Failure thresholds and scheduling mean `period × threshold` is an approximate budget, not exact proof of a wall-clock deadline.

Pod termination changes endpoint information and begins local shutdown; propagation to every routing path is not instantaneous. The termination grace countdown includes a configured `preStop` hook. A long sleep in that hook leaves less time after the termination signal for drain and cleanup. Ensure the actual application receives its signal rather than relying on a shell wrapper to forward it accidentally.

```yaml
# Pod-spec fragment, not a complete Deployment manifest.
terminationGracePeriodSeconds: 45
containers:
  - name: api
    image: example-api:release-id
    ports:
      - containerPort: 3000
    startupProbe:
      httpGet: { path: /health/startup, port: 3000 }
      periodSeconds: 5
      failureThreshold: 30
    livenessProbe:
      httpGet: { path: /health/liveness, port: 3000 }
      periodSeconds: 15
      timeoutSeconds: 2
      failureThreshold: 3
    readinessProbe:
      httpGet: { path: /health/readiness, port: 3000 }
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2
```

The endpoints and their stated contracts must exist; these illustrative values are not workload validation. Reserve time for routing, accepted work, cleanup and a margin before forced termination. Thirty seconds is a common default, not a required universal maximum. See [Kubernetes health checks](../../../40-platform/40.2-kubernetes/04-production-hardening/40.2.4.01-health-checks.md) for the complete platform configuration.

## Real-World Decisions

Choose whether a degraded instance can serve a useful subset, whether an admitted mutation has an outcome identity, and which work can be resumed or redelivered. A worker should stop claiming jobs; commit/acknowledge finished effects or leave recoverable work for another worker under its queue policy. SIGTERM handling alone does not provide exactly-once effects.

A process with a long warm-up may need startup allowance and ready spare capacity. Lazy initialization can shift delay to the first request, so measure the resulting path rather than always treating it as a fix.

## Mistakes

- Reporting fictitious dependency health from a cheap liveness handler.
- Restarting the fleet for a shared dependency failure that restarts cannot repair.
- Closing database/queue resources before accepted work completes.
- Treating a listener close as either an instant drain or an automatic reset of every active request.
- Registering competing shutdown handlers or depending on cleanup after SIGKILL.
- Spending the termination budget on a sleep while ignoring real routing and work durations.

## Best Practices

Measure startup, withdrawal, accepted-work completion and cleanup separately. Test a dependency outage, one slow request during SIGTERM, lost mutation replies and forced termination. Keep lifecycle observation separate from business-path checks and accepted-work recovery; neither a green endpoint nor a successful close callback proves all user operations survived.

## Summary

Liveness selects useful restart, readiness controls admission eligibility and startup bounds initialization. Graceful shutdown withdraws, drains accepted work and closes resources under a deadline. Correct durable effects must also survive abrupt death and uncertain replies.

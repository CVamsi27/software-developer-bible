# Health Checks & Graceful Shutdown — Liveness, Readiness, SIGTERM


---

## Definition

**Health checks** and **graceful shutdown** let a process coordinate with its orchestrator—the platform that starts, stops and routes traffic to application instances. Health checks let the platform *ask* whether an instance should receive traffic. Graceful shutdown lets the instance *announce* that it is leaving and finish ongoing work.

```text
process starts ──▶ liveness:  "am I wedged?"      → fail ⇒ restart
               ──▶ readiness: "should I get traffic?" → fail ⇒ remove from LB, keep process
               ──▶ startup:   "have I finished booting?" → gates the other two
SIGTERM ──▶ stop accepting new work ──▶ drain in-flight ──▶ close pools ──▶ exit 0
```

The distinction that defines them is **restart versus reroute**: a failed *liveness* probe causes the orchestrator to kill and replace the process, so a liveness check that depends on a downstream (database, cache) will restart a healthy instance during a downstream outage — a self-inflicted outage amplifier. A failed *readiness* probe only removes the instance from load-balancer rotation, which is the correct response to "dependency unavailable, cannot serve". Graceful shutdown is the same contract in reverse: on `SIGTERM` the process must give the load balancer time to stop sending traffic before it stops listening, which is why the sequence is *drain, then close* — closing the listener first turns every in-flight request into a connection reset.

## First Principles

Liveness design follows from what an orchestrator can and cannot see:

1. **The platform can only act on what you report.** Health endpoints are the contract: liveness ("should this process be restarted?") vs readiness ("should traffic be routed here?") — conflating them causes restart storms during dependency outages (a DB blip must fail *readiness*, not *liveness*).
2. **Graceful shutdown is the drain sequence** (→ 20.2.4.03): stop accepting → finish in-flight → close resources, within the orchestrator's grace period. The sequence exists because SIGKILL is always next.
3. **Startup ordering is the third phase**: readiness must stay false until warmup completes (caches, connections) — otherwise the first traffic after deploy hits a cold service and times out.

## Health Check Types

### 1. Liveness Probe

**Purpose:** Is the service running?

```
If liveness fails → Restart the container
Use case: Deadlock detection, infinite loops
```

```typescript
// NestJS health check
import { HealthCheck, HealthCheckService } from '@nestjs/terminus';

@Controller('health')
export class HealthController {
  constructor(private health: HealthCheckService) {}

  @Get('liveness')
  @HealthCheck()
  check() {
    return this.health.check([
      // Just check if the service is responsive
      () => ({ database: { status: 'up' } }),
    ]);
  }
}
```

### 2. Readiness Probe

**Purpose:** Is the service ready to accept traffic?

```
If readiness fails → Remove from load balancer
Use case: Database not connected, dependencies not ready
```

```typescript
@Get('readiness')
@HealthCheck()
async checkReadiness() {
  return this.health.check([
    // Check database connection
    async () => {
      await this.prisma.$queryRaw`SELECT 1`;
      return { database: { status: 'up' } };
    },
    // Check Redis connection
    async () => {
      await this.redis.ping();
      return { redis: { status: 'up' } };
    },
  ]);
}
```

### 3. Startup Probe

**Purpose:** Has the service finished starting?

```
If startup fails → Restart the container
Use case: Slow startup, initialization timeout
```

```typescript
@Get('startup')
@HealthCheck()
async checkStartup() {
  return this.health.check([
    async () => {
      // Check if migrations are complete
      const migrated = await this.prisma.$queryRaw`
        SELECT EXISTS (
          SELECT 1 FROM information_schema.tables
          WHERE table_name = 'appointments'
        ) as exists
      `;
      return { migrations: { status: migrated[0].exists ? 'up' : 'down' } };
    },
  ]);
}
```

## Kubernetes Probes Configuration

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: docita-api
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: api
          image: docita-api:latest
          ports:
            - containerPort: 3000

          # Liveness: is the container alive?
          livenessProbe:
            httpGet:
              path: /health/liveness
              port: 3000
            initialDelaySeconds: 10
            periodSeconds: 15
            timeoutSeconds: 5
            failureThreshold: 3

          # Readiness: can it accept traffic?
          readinessProbe:
            httpGet:
              path: /health/readiness
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 3

          # Startup: has it finished initializing?
          startupProbe:
            httpGet:
              path: /health/startup
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 5
            failureThreshold: 30 # 30 × 5s = 150s max startup time
```

## Graceful Shutdown

### The Problem

```
Without graceful shutdown:
  1. SIGTERM received
  2. Process killed immediately
  3. In-flight requests dropped
  4. Database connections abruptly closed
  5. Users see 500 errors
```

### The Solution

```
With graceful shutdown:
  1. SIGTERM received
  2. Stop accepting new requests
  3. Wait for in-flight requests to complete
  4. Close database connections gracefully
  5. Exit cleanly
```

### Implementation

```typescript
// NestJS graceful shutdown
async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // Enable graceful shutdown
  app.enableShutdownHooks();

  await app.listen(3000);

  // Handle SIGTERM
  process.on('SIGTERM', async () => {
    console.log('SIGTERM received. Starting graceful shutdown...');

    // 1. Stop accepting new connections
    await app.close();

    // 2. Wait for in-flight requests (already handled by app.close())

    // 3. Close database connections
    await prisma.$disconnect();

    // 4. Close Redis connections
    await redis.quit();

    // 5. Exit
    console.log('Graceful shutdown complete.');
    process.exit(0);
  });
}
```

### With HTTP Server (Keep-Alive)

```typescript
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import { ExpressAdapter } from '@nestjs/platform-express';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  const server = app.getHttpServer();

  await app.listen(3000);

  // Graceful shutdown with connection draining
  const shutdown = async () => {
    console.log('Shutting down gracefully...');

    // Stop accepting new connections
    server.close(() => {
      console.log('HTTP server closed.');
    });

    // Wait for existing connections to finish (max 30s)
    const forceCloseTimeout = setTimeout(() => {
      console.log('Force closing connections.');
      process.exit(1);
    }, 30000);

    // Close dependencies
    await prisma.$disconnect();
    await redis.quit();

    clearTimeout(forceCloseTimeout);
    process.exit(0);
  };

  process.on('SIGTERM', shutdown);
  process.on('SIGINT', shutdown);
}
```

## Connection Draining

### Load Balancer Drain

```
When deploying new version:
  1. New pods start (readiness probe passes)
  2. Old pods marked for drain
  3. Load balancer stops sending new traffic to old pods
  4. Existing connections continue until timeout (30s)
  5. Old pods terminate
```

### Kubernetes Configuration

```yaml
spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: api
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"] # Wait for LB to deregister
```

## Interview Tips

- **Q: What's the difference between liveness and readiness probes?**
  - Liveness: Is the container alive? (restart if fails)
  - Readiness: Can it accept traffic? (remove from LB if fails)

- **Q: How do you handle graceful shutdown in Node.js?**
  - Listen for SIGTERM
  - Stop accepting new connections
  - Wait for in-flight requests
  - Close database/Redis connections
  - Exit cleanly

- **Q: What happens if you don't have graceful shutdown?**
  - In-flight requests dropped
  - Database connections abruptly closed
  - Users see 500 errors
  - Potential data corruption

## Summary

1. **Liveness ≠ readiness** — liveness says "restart me", readiness says "send traffic elsewhere"; conflating them causes restart storms
2. **Health checks must check dependencies at the right depth** — a DB ping belongs in readiness, not liveness
3. **Graceful shutdown is a protocol**: stop accepting → drain in-flight → close connections → exit within the SIGTERM window
4. **Kubernetes wires this via `terminationGracePeriodSeconds` + `preStop`** — the default 30s window is a budget you design against
5. **Startup probes prevent slow-boot services from being killed** before they're ready

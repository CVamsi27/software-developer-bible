# Resilience Patterns — Circuit Breaker, Bulkhead, Retry, Idempotency


---

A dependency slows down and every request waits. The wait fills the worker pool, then retries add load just as the dependency is struggling. Resilience design decides where to reject, wait, retry or degrade so one failure does not consume the whole service.

## Definition

**Resilience patterns** keep a service useful when a dependency fails or capacity runs out. Each policy answers two questions: which resource or outcome is bounded, and what happens to work that cannot complete?

> **Textbook Definition:** Resilience patterns are reusable policies that preserve defined service behavior during failures or overload by limiting waiting, repeated work, resource contention and failure propagation.

## First Principles

A request holds memory, a connection or another finite resource while waiting. If arrivals continue faster than completions, outstanding work grows. Repeating a failed request adds more arrivals; timing out locally does not establish that its remote effect failed. These constraints require separate controls for admission, waiting and repeated effects.

No single policy solves all three. A breaker that rejects future calls does not cancel calls already running. A timeout releases a caller's wait only if cleanup actually releases its resources. Idempotency prevents repeated business effects but still consumes capacity for duplicate attempts.

## Choose the Bound Before the Pattern

| Problem | Policy | Boundary that remains |
| --------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------- |
| Too much in-flight work for one dependency | Bulkhead: reserve a bounded pool or admission limit | A shared database or CPU can still couple pools |
| Caller waits beyond its useful time | Deadline and cooperative cancellation | Remote work may already have committed |
| A repeatable request encounters a transient failure | Classified retry with delay and budget | Retries add load; classification can be wrong |
| Repeated calls are unlikely to help | Circuit breaker rejects calls until recovery probes | Observed failure is suspicion, not proof of death |
| Arrivals exceed available service capacity | Load shedding rejects work before costly allocation | Caller needs a useful retry/degradation contract |
| A less fresh result is still acceptable | Fallback serves a bounded, authorized alternative | Stale data can violate the business rule |

A **bulkhead** borrows its name from compartments in a ship: one flooded compartment should not consume every compartment's capacity. Partition by dependency, tenant or work class according to the failure you want to contain. Bound both active work and queued/waiting work; a concurrency limit with an unlimited queue only moves the overload.

## What a Circuit Breaker Actually Observes

```text
CLOSED: admit calls and measure selected failures
   threshold reached → OPEN: reject calls without contacting dependency
   cooldown elapsed  → HALF-OPEN: admit a bounded number of probes
   probe success     → CLOSED (under the chosen recovery rule)
   probe failure     → OPEN again
```

Choose a consecutive-failure or rolling-window policy explicitly. A rolling failure rate needs a minimum sample count, window and treatment of slow calls. An invalid customer request should not normally count as dependency failure. In HALF-OPEN, limit probes atomically; opening the gate to every waiting caller recreates the outage.

Late responses need a defined policy too. A success from a call admitted before the breaker opened must not automatically reset a newer OPEN/HALF-OPEN state. Libraries often associate results with a state generation or use equivalent synchronization. Verify this behavior instead of implementing an untested counter.

## Trace One Slow Catalog Request

Suppose a storefront allows 800 ms for a catalog read, including local processing. Its dependency allowance is 600 ms; an illustrative attempt cap is 250 ms.

1. Admission rejects immediately if the catalog bulkhead is full. A waiting queue, if allowed, also consumes the 600 ms allowance.
2. The breaker either rejects or permits an attempt. The client bounds connection, headers **and body consumption**, rather than stopping its timer at headers.
3. A transient failure may permit another attempt only if a retry token and useful remaining time exist. All attempts and backoff share the same end-to-end allowance.
4. If the policy permits stale public prices, the fallback checks their freshness and authorization. A checkout requiring current prices must instead fail or use an authoritative price path.
5. Cancellation and resource cleanup release admission. A caller timeout alone cannot prove the remote server stopped work.

These values illustrate the arithmetic; they are not production defaults. Derive them from the user deadline, dependency latency, request sizes, queue behavior and acceptable false-timeout rate.

## Composition Changes What Gets Counted

There is no universal fixed wrapper order:

| Placement | Consequence |
| --------------------------------------------- | --------------------------------------------------------------------------- |
| Breaker observes each attempt | Failed attempts contribute individually; it may stop later retries |
| Breaker observes one whole retrying operation | Final outcome contributes once; retries can hide partial dependency failure |
| Bulkhead permit held through backoff | Caps whole operations but sleeping attempts occupy permits |
| Permit acquired per attempt | Frees capacity during sleep, but the retry population needs its own bound |
| Timeout around only the network call | Does not bound queue time, backoff or fallback |
| Overall deadline around everything | Bounds useful caller time; cancellation/cleanup still needs implementation |

Choose the signals and scope deliberately. Exhausting a retry budget does not by itself prove the dependency failed and should not automatically trip an unrelated breaker.

## Fallback and Health Are Product Contracts

Fallback is useful when the alternative meets a weaker **declared** contract: a cached public catalog can be acceptable; a stale account balance used to approve a transfer may not be. Another dependency used for fallback also needs capacity and time bounds. A cheap, independent fallback reduces coupling; an unbounded cascade of alternatives increases it.

Health endpoints serve a different controller. Liveness should not restart every instance because a shared dependency is down. Readiness depends on which requests the instance can serve or reject usefully. Deep diagnostics can examine more dependencies without becoming a restart or admission decision. Their implementation lives in [Health Checks & Graceful Shutdown](../01-liveness-lifecycle/30.3.1.01-health-checks-graceful-shutdown.md).

## Real-World Decisions

- Choose one retry owner across application, SDK, proxy and queue layers. Three attempts at three layers can produce 27 downstream attempts for one logical request.
- Measure original requests, retry attempts, queue wait, admission rejection, breaker state/probes, timeout stage and fallback quality separately.
- Test recovery, not just opening: pause the dependency, saturate the pool, lose a response after commit and recover while many callers are waiting.
- Use a maintained implementation where available, configured for the selected failure contract. A library name does not establish correct thresholds, cancellation or isolation.

## Common Mistakes

| Mistake | Why it fails | Repair |
| ------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------- |
| Redis check → appointment creation → SETEX | Concurrent calls and crashes can repeat the appointment | Atomic local effect/replay transaction; see idempotency chapter |
| Request hash used as the operation identity | Two intentionally identical purchases collapse | Stable identity per logical operation plus a separate fingerprint |
| `Promise.race` described as cancellation | Underlying work can continue after rejection | Propagate cancellation and verify resource release |
| Unlimited HALF-OPEN traffic | Recovery probes become another load burst | Bound probes and handle late results |
| A fulfilled fetch marks health success | Fetch can fulfill for HTTP 503 | Classify status and validate the required response |
| Universal wrapper order | Changes accounting and capacity without acknowledging it | State which layer observes each attempt/operation |

## Summary

Resilience comes from explicit bounds and useful failure behavior. Admission controls capacity; deadlines bound waiting; retries handle selected transient outcomes; idempotency protects repeated effects. Breakers and fallbacks change future work, while cleanup and recovery tests establish whether the chosen policies preserve service behavior.

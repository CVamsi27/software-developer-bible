# Retry Patterns


---

## Definition

A **retry** repeats a logical operation after a failed or uncertain attempt. It helps only when another attempt can succeed, repeating the operation is safe, and the added work fits a capacity and time budget.

> **Textbook Definition:** A retry policy specifies which failed or uncertain operations may be attempted again, their attempt and time budgets, and the delay strategy, while preserving the operation's side-effect contract.

## First Principles

A missing response cannot distinguish a rejected request from a committed request whose response was lost. Retrying a mutation therefore needs operation identity or a naturally repeatable state transition. A failing dependency also has less capacity to absorb additional requests, so attempts and delay must be controlled separately.

Exponential backoff spreads attempts over increasing intervals; it **does not limit their number**. Jitter prevents many callers using the same intervals from returning together. An attempt cap, deadline and shared retry budget supply distinct bounds.

## Classify the Operation Before the Error

| Outcome | Decision |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Invalid payload or unchanged unauthorized request | Fix the request/authentication; do not blindly repeat it |
| 429 or 503 with Retry-After | Retry only if safe, budgeted and the requested delay fits the deadline |
| 500, 502, 504 or connection reset | Possibly transient; a status alone does not prove safe repetition or eventual recovery |
| Timeout after submitting a payment | Outcome is unknown; use the same provider identity and reconcile |
| 404 immediately after an asynchronous create | May reflect documented propagation delay; otherwise repeating an absent resource does not help |
| Deadline/budget exhausted or breaker rejects admission | Stop; report failure/degradation according to the caller contract |

Credential refresh can justify a new authorized attempt; it is not endless retry of the same bad credentials. Read the API's documented retry and idempotency behavior rather than treating all 4xx or 5xx alike. `fetch` resolves for HTTP error statuses, so classification must inspect the response.

## Delay and Budget Are Independent

For retry number `r` starting at zero, **full jitter** chooses a delay uniformly from zero to `min(maxDelay, baseDelay × 2^r)`. A fixed delay is simpler but can synchronize callers. Equal/decorrelated jitter are other policies with different delay distributions; “30% randomness” is not a universal optimum.

`Retry-After` can be seconds or an HTTP date. Convert a date using wall-clock time, then use monotonic elapsed time for the operation's local deadline. Do not silently shorten the server's requested wait to fit the caller deadline: decline the retry instead.

A **retry budget** caps additional attempts across logical calls to a dependency. Originals can still be admitted under their own capacity policy. A per-process budget multiplies across instances; decide whether that is acceptable or allocate a fleet budget. Reserve tokens with one operation, not an asynchronous check followed by a separate increment.

## A Bounded Read-Only HTTP Example

This complete Node.js helper demonstrates one safe scope: an endpoint whose GET contract is read-only. The chosen retry statuses and failure handling are illustrative policy. It reads text and assumes the selected endpoint has an acceptable bounded response size; the helper itself does not impose a byte limit or validate the application's response schema. Configure the URL/credentials under the application's trust policy; this is not a general proxy for user-supplied URLs.

```typescript
export class HttpFailure extends Error {
  constructor(public status: number, public retryAfterMs: number) {
    super(`HTTP ${status}`);
  }
}
export function retryAfterMs(value: string | null, now = Date.now()): number {
  if (value === null) return 0;
  if (/^\d+$/.test(value)) return Number(value) * 1000;
  const date = Date.parse(value);
  return Number.isFinite(date) ? Math.max(0, date - now) : 0;
}
export class RetryBudget {
  private tokens: number;
  constructor(tokens: number) {
    if (!Number.isSafeInteger(tokens) || tokens < 0) throw new RangeError('tokens');
    this.tokens = tokens;
  }
  take(): boolean {
    if (this.tokens === 0) return false;
    this.tokens--; return true;
  }
}
interface ReadPolicy {
  maxAttempts: number; totalMs: number; attemptMs: number;
  baseDelayMs: number; maxDelayMs: number; budget: RetryBudget;
}
export async function retryRead(url: string, p: ReadPolicy): Promise<string> {
  for (const n of [p.maxAttempts, p.totalMs, p.attemptMs, p.baseDelayMs, p.maxDelayMs]) {
    if (!Number.isSafeInteger(n) || n <= 0 || n > 2_147_483_647) {
      throw new RangeError('positive bounded policy values required');
    }
  }
  const end = performance.now() + p.totalMs;
  const statuses = new Set([429, 502, 503, 504]);
  for (let attempt = 0; attempt < p.maxAttempts; attempt++) {
    const remaining = end - performance.now();
    if (remaining <= 0) throw new Error('Read deadline exceeded');
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), Math.min(p.attemptMs, remaining));
    let failure: unknown;
    try {
      const response = await fetch(url, { method: 'GET', signal: controller.signal });
      if (!response.ok) {
        void response.body?.cancel().catch(() => {});
        throw new HttpFailure(response.status, retryAfterMs(response.headers.get('retry-after')));
      }
      return await response.text(); // timer includes body consumption
    } catch (error) { failure = error; }
    finally { clearTimeout(timer); }
    // Read timeouts/network failures are repeatable here; a mutation needs another contract.
    const transient = failure instanceof HttpFailure
      ? statuses.has(failure.status)
      : controller.signal.aborted || failure instanceof TypeError;
    if (!transient || attempt + 1 === p.maxAttempts) throw failure;
    const cap = Math.min(p.maxDelayMs, p.baseDelayMs * 2 ** attempt);
    const serverWait = failure instanceof HttpFailure ? failure.retryAfterMs : 0;
    const delay = Math.max(serverWait, Math.random() * cap);
    if (!Number.isFinite(delay) || delay >= end - performance.now()) throw failure;
    if (!p.budget.take()) throw failure;
    await new Promise(resolve => setTimeout(resolve, delay));
  }
  throw new Error('Unreachable');
}
```

The finite token allocation is deliberately simple: its owner creates/replenishes budgets according to the chosen window or token-bucket policy. It is local to one process and cannot cap a whole fleet. A token reserved before sleeping is conservatively spent even if no time remains to start the attempt.

Node fetch reports several network failures as TypeError; a malformed URL can also produce TypeError. Validate known endpoint configuration before using this policy, classify transport errors more narrowly in production, and do not promise every TypeError is transient. This helper aborts local fetch waiting; it cannot prove the remote server stopped work. Add caller cancellation and transport-specific telemetry in the integration rather than hiding them behind a generic promise retry.

## Trace the Shared Deadline

An illustrative 700 ms operation has a 250 ms attempt cap. Attempt A fails after 220 ms; a 100 ms backoff leaves about 380 ms. Attempt B then has at most 250 ms. If B asks for a one-second Retry-After, attempt C is declined: the requested delay exceeds remaining useful time.

Increasing the retry count does not enlarge the 700 ms budget. Queue wait, authentication refresh and local processing also consume the caller's overall deadline; this helper's total budget begins only when it is invoked.

## Integration Decisions

- Use one retry owner. A proxy, SDK and application each doing three attempts can produce 27 downstream attempts. Queue redelivery adds another horizon.
- Return a documented failure or defer durable work when interactive time expires. A background job needs its own deadline, retention and poison-message policy.
- Use maintained SDK retry behavior when it matches the contract; inspect attempt counting, Retry-After, body cancellation, defaults and mutation exclusions for the installed version.
- Keep health-check controllers separate. Terminus health configuration is not a retry mechanism; its implementation belongs in the lifecycle chapter.

## Common Mistakes

| Mistake | Repair |
| ------------------------------------------------ | ---------------------------------------------------------------------------- |
| Retrying every exception or every 5xx | Classify the endpoint, outcome, identity and budget |
| New idempotency key on each attempt | Generate once per logical mutation and persist across supported retries |
| Per-attempt timeouts with unlimited total time | Share a deadline across attempts and sleeps |
| Jitter added after applying a hard cap | Cap the intended distribution; added jitter can exceed an advertised maximum |
| Returning headers and clearing the timer | Keep the timer through body consumption |
| Saying “three retries means the service is down” | A few samples show failure under a policy, not proven process death |

## Summary

Retry repeats one logical operation under explicit safety, error, attempt, time and capacity conditions. Backoff changes spacing; jitter spreads callers; neither replaces a cap or deadline. Stop when another attempt cannot be safe and useful, and preserve the same mutation identity after an uncertain outcome.

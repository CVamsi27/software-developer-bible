# Idempotency Keys

An appointment request commits, but its response is lost. When the browser retries, the server must recognize the same operation and replay its result instead of creating a second appointment:

```typescript
fetch('/api/appointments', { headers: { 'Idempotency-Key': operationKey } }); // same key, same body.
```

## Definition

An **idempotency key** identifies one logical operation across retries. The server scopes it to the authorized caller and operation, associates it with a request **fingerprint**, and replays the committed result when that same operation is retried.

> **Textbook Definition:** An idempotency key is a caller-scoped identifier for a logical operation that lets a service detect repeat submissions and reuse an established outcome under a defined retention and concurrency contract.

Idempotent effects need not return identical HTTP responses: a repeated DELETE may return a different status while leaving the resource absent. A replayable API contract may additionally promise to return the original status and body.

## First Principles

1. A timeout never reveals whether the effect committed. The caller must reuse an identity for the uncertain operation.
2. Two retries can arrive together. A check followed by a separate write cannot choose one winner atomically.
3. A worker can fail between an effect and recording its completion. The record must commit with the effect, or the receiving system must independently deduplicate it.

## How It Works

### 1. Define the contract first

Use a scope such as `(tenant, operation, key)`, with the tenant derived from verified authorization. Keep the key stable across retries; mint a new one for a genuinely new operation. Store a fingerprint of normalized, validated business input and reject key reuse with a different fingerprint.

Serialize expiry cleanup with active claims/replays under the chosen database protocol; deleting a record while a supported operation is still in flight can reopen its identity. Choose a retention horizon at least as long as supported retries and replay. Once a record expires, the same key may execute again. Some business operations need permanent uniqueness independently of this temporary response cache.

### 2. Commit claim, effect, and replay record together

The following PostgreSQL model puts an appointment and its replay record in the same database. The payload fingerprint is computed by the application from canonical validated fields; the SQL below is a transaction outline, with parameters bound by the driver:

```sql
CREATE TABLE operation_results (
  tenant_id UUID NOT NULL,
  operation TEXT NOT NULL,
  operation_key TEXT NOT NULL,
  request_fingerprint TEXT NOT NULL,
  status_code INTEGER,
  response_body JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, operation, operation_key),
  CHECK ((status_code IS NULL) = (response_body IS NULL))
);
CREATE TABLE appointments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL,
  patient_id UUID NOT NULL,
  appointment_time TIMESTAMPTZ NOT NULL
);
```

```sql
BEGIN;
INSERT INTO operation_results
  (tenant_id, operation, operation_key, request_fingerprint)
VALUES ($1, 'create-appointment', $2, $3)
ON CONFLICT DO NOTHING
RETURNING operation_key;
-- Driver checks whether RETURNING produced a row.
-- If it did: create appointment, then store its response below.
-- If it did not: SELECT the existing row in this transaction, compare
-- fingerprint, and replay the result. Never create another appointment.
```

For the winner, bind the same appointment ID into both writes:

```sql
INSERT INTO appointments (id, tenant_id, patient_id, appointment_time)
VALUES ($4, $1, $5, $6);
UPDATE operation_results
SET status_code = 201, response_body = jsonb_build_object('id', $4::text)
WHERE tenant_id = $1 AND operation = 'create-appointment'
  AND operation_key = $2;
COMMIT;
```

At PostgreSQL's default READ COMMITTED isolation, a conflicting insert waits for the competing transaction. After a committed conflict, the loser's next statement obtains a fresh snapshot and can read the completed result. If the first transaction aborts, its claim and effect roll back together. Retry serialization/deadlock failures per the chosen isolation level.

Never commit the placeholder alone in this model: that would introduce a separate pending-operation state machine. A production handler must always roll back on failure, check the fingerprint before replay, and enforce a deadline while waiting for another attempt.

### 3. Carry identity across external boundaries

A database transaction cannot roll back a payment accepted by an external provider. Write an outbox intent with the business change, then send a stable provider idempotency key on every delivery attempt. After a timeout, reconcile against the provider's operation identity before deciding to repeat or compensate.

If the provider offers no way to recognize repeated requests or look up the result of an earlier request, deduplication in your database alone cannot guarantee one remote effect. State the remaining duplicate risk explicitly and choose a business recovery policy.

For queue consumers, insert an inbox/message ID and apply the database mutation in one transaction; acknowledge delivery after commit. Kafka's idempotent producer suppresses certain producer retries in Kafka. Kafka transactions can atomically publish records and consumed offsets within Kafka; neither automatically includes an unrelated PostgreSQL write or email send.

### 4. Make the client reuse one key

```typescript
const operationKey = crypto.randomUUID(); // once per logical operation
const body = JSON.stringify(appointmentData);
async function attempt() {
  return fetch('/api/appointments', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Idempotency-Key': operationKey,
    },
    body,
  });
}
// Retry attempt() with this same key and body after an uncertain failure.
```

The header's spelling and value syntax belong to the API contract. This example defines an opaque UUID value; clients must follow the receiving API's documented format. As of 2026-10-14, the IETF Datatracker lists draft-07 as expired on 2026-04-18, with no intended RFC status. It is no current standard, so never assume its proposed Structured Field syntax is interoperable.

Persist the operation key if the retry must survive a page reload or process restart. A request hash is useful for detecting changed payloads, but using it as the operation identity may collapse two intentionally identical purchases.

## Common Mistakes

| Mistake | Repair |
| --------------------------------------------------------- | --------------------------------------------------------------------- |
| Redis GET followed by SETEX | Use an atomic claim, and separately solve the effect/record crash gap |
| Returning a placeholder with status code 0 | Wait within a deadline, or expose a documented pending response |
| Changing the record ID on conflict | Replay the original object; do not mutate it to the retry's ID |
| Recording a processed marker after sending a notification | Use receiver idempotency or reconciliation for the remote effect |
| Dual-writing Redis and the database | Make one durable transactional source authoritative |
| Hardcoding a 24-hour TTL for every operation | Match retention to the documented retry horizon |

## Summary

A stable key identifies the operation; scope and fingerprint prevent unrelated requests from sharing it. Commit the claim, business write and replay result together when one database owns the effect. At external boundaries, carry the identity to the receiver and reconcile uncertain outcomes. Retention limits the guarantee and must be part of the API contract.

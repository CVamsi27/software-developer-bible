# Feature Flags & Kill Switches

A new checkout path reaches every instance, then begins returning incorrect totals. A kill switch can stop new requests from entering that path; it cannot undo writes already committed or work already submitted.

## Definition

A **feature flag** selects behavior while the application runs, so deploying code and exposing its behavior can happen separately. A **kill switch** is an operational control used to disable a capability during an incident. Flags can select booleans, variants or configuration values; a switch needs an unambiguous allowed/disabled meaning.

> **Textbook Definition:** A feature flag selects runtime behavior through an evaluated rule independently of deployment. A kill switch disables a capability to contain an incident under a defined propagation and failure contract.

## First Principles

Installed code can contain two paths even when only one is exposed. Selecting a path requires rules, a subject and a value available at the decision point. Rule distribution can fail or lag, so application instances may temporarily choose differently. A flag flip cannot undo an already committed write or stop work that never checks the decision again.

Every additional path adds states to test. Temporary release flags therefore need removal ownership, while long-lived operational controls need continuing drills. Neither hiding a button nor assigning a flag grants authorization to the protected operation.

## Decide What the Flag Controls

| Type | Purpose | Lifecycle and boundary |
| ------------------- | ----------------------------------- | ------------------------------------------------------------------ |
| Release | Expose new behavior gradually | Remove old path/flag after compatibility and rollback window close |
| Experiment | Assign measured variants | Stable assignment, exposure measurement and experiment design |
| Operational control | Disable expensive or dangerous work | Retain only with an owner and tested incident behavior |
| Entitlement | Select a paid/allowed capability | Durable product rule; enforce authorization at the server |

A deployment can already use staged traffic or canaries without feature flags. Flags add behavior selection inside deployed code. They are not automatically safer: turning on incompatible writes can make the old path unusable even after the flag turns off.

## Put Evaluation and Distribution in the Whole System

```text
operator changes versioned rules → distribution/refresh → local rule snapshot
request + trusted subject/context → evaluate snapshot → choose application path
```

Server-side local evaluation avoids a remote call on each request and can continue using known rules during an outage. Its price is propagation delay and stale state. Remote evaluation can centralize rules and attributes, but adds a network dependency and needs its own deadline, capacity and fallback. Select it from the application contract rather than a universal “admin only” rule.

Client-side SDKs may use different evaluation/privacy models. Do not ship secret targeting rules or authorization decisions into a browser just because the UI uses the same flag name. Collect only the evaluation attributes needed; identifiers and telemetry need the application's data policy.

Snapshots should have a revision and freshness metadata. Define whether freshness means a successful control-plane contact or an actual rule change: rules can remain unchanged for months while the control plane is healthy. A failed refresh must not advance the contact timestamp. Reject out-of-order revisions and retain valid state atomically; avoid partially updating a rule set during evaluation.

## A Sticky Audience Without Anonymous Guessing

This complete Node.js primitive demonstrates a release percentage, not a vendor SDK or a full experiment system. Context IDs must use the same canonical encoding everywhere. The tuple encoding prevents ambiguous colon concatenations, and the flag-specific salt controls deliberate reassignment.

```typescript
import { createHash } from 'node:crypto';
interface Rollout {
  key: string; salt: string; percent: number; anonymous: boolean;
}
export function releaseEnabled(rule: Rollout, subject?: string): boolean {
  if (!Number.isFinite(rule.percent) || rule.percent < 0 || rule.percent > 100) {
    throw new RangeError('percent');
  }
  if (subject === undefined) return rule.anonymous;
  const bytes = createHash('sha256')
    .update(JSON.stringify([rule.key, rule.salt, subject])).digest();
  const fraction = bytes.readUInt32BE(0) / 2 ** 32;
  return fraction < rule.percent / 100;
}
```

Holding the subject, salt and algorithm fixed makes a 5% audience a subset of a 10% audience. It does not guarantee exactly 5% of a small sample, equal traffic volume, or a statistically sound experiment. Exclude or assign anonymous traffic explicitly; mapping every unidentified request to “on when percentage ≥ 50” is not percentage allocation. A stable pseudonymous session identifier can support assignment when the data policy permits it; an IP address is neither a stable person nor a free privacy solution.

## Give the Kill Switch One Polarity

Name an allow control `paymentsAllowed`: `true` permits new submissions; `false` prevents them. Choose a failure default for that capability. Turning off a risky optional integration can be safe; turning off a security check would be unsafe. “False is always safe” has no meaning without the controlled path.

For example, stop **new** payment submissions when `paymentsAllowed` becomes false. Already submitted payments remain unknown or accepted until reconciled; the switch must not mark them failed merely because it was flipped. Workers check at an appropriate bounded work boundary. Disabling a task also needs a policy for queued jobs, retries and customer-visible pending work.

Measure change-to-effect from the operator action to observed behavior on every relevant instance and worker. A successful control-plane API response proves acceptance, not fleet convergence. Record revision/decision telemetry, test offline and stale instances, and provide an authenticated emergency path when the usual administration interface is unavailable.

## Trace a Checkout Rollout

1. Deploy code that can read both the old and new data shape, with the new path disabled.
2. Assign a stable small audience and emit actual exposure events. Verify errors, latency and business outcomes for comparable traffic, including users who could not reach the feature.
3. Increase the audience only after enough relevant observations and expected workload cycles. Example percentages and 30-minute holds are not statistical evidence by themselves.
4. Flip off after a regression and measure where new admissions stop. Reconcile already submitted orders; a flag cannot reverse them.
5. Remove the old path/flag only after old clients, in-flight work and the rollback window are accounted for. Archive metadata and audit history according to policy.

Changing a percentage during an experiment can affect cohort/time comparisons. Treat rollout and experiment analysis as separate decisions rather than assuming sticky hashing alone makes metrics interpretable.

## Best Practices and Mistakes

| Mistake | Repair |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| “Flag provider outage has no effect” | Define stale/default behavior and test clients that never initialized |
| Default false disables an authorization check | Model permission enforcement separately and fail according to the protected contract |
| A rule-update timestamp treated as contact freshness | Record successful contact/refresh independently when freshness matters |
| Random choice per request | Use stable assignment for the intended subject and lifetime |
| Read the flag repeatedly inside one mutation | Take a coherent decision at the appropriate boundary; separately define long-job rechecks |
| Global override from untrusted request attributes | Derive identities/privileged context from verified authorization |
| Automatic archive based only on lack of source matches | Check active versions/clients and operational ownership before deletion |

Temporary flags need owner, purpose, rollout/removal criteria and a deadline for review. Permanent controls need owner, default, audit, propagation objective and drill evidence. Removing a branch reduces future test combinations; keeping an incident control requires maintaining them.

## Summary

Flags select behavior; their reliability depends on subject identity, rule distribution and failure defaults. Stable assignment helps coherent rollout but does not supply authorization or experiment validity. Kill switches need clear polarity, measured propagation and a policy for already-started work. Remove temporary paths deliberately and continue testing retained controls.

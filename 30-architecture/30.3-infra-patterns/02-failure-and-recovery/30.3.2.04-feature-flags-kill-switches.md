# Feature Flags & Kill Switches

> **TL;DR:** Decoupling deploy from release: flag types, targeting rules, kill-switch SLAs, and the cleanup discipline that keeps flags from rotting into debt.

---

## First Principles

Feature flags decouple deploy from release — the axioms follow:

1. **Shipping code ≠ enabling code.** Dark launches, canary percentage, kill switches for a misbehaving feature — all one mechanism: a runtime decision layer between deploy and exposure.
2. **Flags are debt with a TTL.** Every flag adds a code path that must be tested in both states; flags without removal dates accumulate into combinatorial test matrices. Lifecycle (create → ramp → 100% → remove) is part of the pattern, not housekeeping.
3. **Kill switches are incident response**: the ability to disable a feature *without a deploy* is the difference between a 5-minute mitigation and a rollback at 3am. That requires the flag check to be on the hot path and the flag store to be more available than the feature.

---

## Definition

A **feature flag** is a runtime-evaluated conditional that decouples *deploying* code from *releasing* behaviour; a **kill switch** is a flag whose only job is to disable a path during an incident. Both are the same mechanism — a named boolean/rule set read at request time — differing only in **lifespan and who may flip them**.

```text
flag type       lifespan        owner          removal
release flag    days–weeks      feature team   after 100% rollout
experiment flag weeks           growth/data    after the test concludes
ops/kill switch indefinite      on-call        kept (part of the safety story)
permission flag indefinite       product (as entitlements — usually not a "flag")
```

Three properties make a flag system trustworthy, and each maps to a failure mode:

1. **Fail-safe default** — if the flag service is unreachable, the client must fall back to a cached value or a declared default, never throw; a flag SDK that can take the app down is worse than the feature it gates.
2. **Consistent evaluation** — the same user must get the same answer across instances (stable hashing of user id, not per-node randomness), or a rollout produces incoherent UX and skewed metrics.
3. **Bounded debt** — flags are temporary by nature, so each carries an owner and an expiry; the "flag debt" cleanup is part of the pattern, because a system with thousands of stale flags can no longer reason about which code is live.

A kill switch adds one more requirement: its **change-to-effect SLA** must be measured and short (seconds, not a deploy cycle), because it exists to be the fastest remedy available in an incident.

## The Problem

You want to merge a half-finished feature without shipping it. Or ship to 1% of users before committing. Or turn off a flaky dependency at 3 AM without redeploying. Deploys are slow, risky, all-or-nothing events; configuration is fast, reversible, and per-audience.

Feature flags solve this by making behavior a **runtime decision**:

```
Deploy (slow, risky):        code reaches everyone at once
Flag   (fast, targeted):     code ships dark, releases progressively
```

Without flags, every release is a big bang; with undisciplined flags, you get a config swamp nobody dares delete. This chapter covers both halves.

## Flag Types (know your lifespans)

| Type | Purpose | Typical lifespan | Owner |
| --------------------------------------- | ----------------------------------------------- | ----------------------------- | ------------ |
| **Release** | Ship incomplete work dark; progressive rollout | Days to weeks | Engineering |
| **Experiment** (A/B) | Measure variants statistically | Fixed test window | Product/Data |
| **Ops** (kill switch / circuit-breaker) | Disable a dependency or heavy path under stress | Long-lived but rarely flipped | SRE/Platform |
| **Permission** (entitlement) | Gate features per customer tier | Permanent-ish; product data | Product |

The types fail differently: release flags rot if forgotten, experiment flags lie if not cleaned up after measurement, ops flags must work during outages (when your admin UI may be down), permission flags are really business data and belong in durable storage with an audit trail.

---

## Flag Store Landscape

| Store | Model | Evaluation | Notes |
| ------------------------------ | ------------------------------- | ------------------------- | ------------------------------------------------- |
| **LaunchDarkly** | SaaS SDK + edge eval | Local (SDK streams rules) | Gold standard DX; cost scales with MAU |
| **Unleash** | Open source, self-host or cloud | Local SDK or server API | Popular OSS choice; proxy for edge eval |
| **Flagsmith** | OSS + hosted | Remote or local | Simple targeting model |
| **DB-backed (Postgres/Redis)** | Homegrown rows + cache endpoint | Poll + local memoize | Fine for small scale; you own consistency + audit |
| **Config files** | YAML in image | At boot | Not dynamic — only for boot-time defaults |

Key architectural decision — **where evaluation happens**:

```text
Local evaluation (preferred):
  SDK subscribes to rule updates ──▶ in-process cache ──▶ nanosecond lookups
  Works during vendor outage; network only for rule updates

Remote evaluation:
  App calls vendor API per request ──▶ adds 10-100ms + availability coupling
  Only acceptable for low-QPS admin paths
```

Rule of thumb: production hot paths evaluate **locally from a streamed/pushed snapshot**; nothing on the request path should block on the flag store being reachable.

## Targeting Rules

Typical rule hierarchy evaluated top-down until a match:

```text
if user in explicit allow-list      → true        (dogfooding)
else if user attribute matches      → rule value  (region=eu AND tier=pro)
else if hash(userId) % 100 < rollout→ true        (percentage)
else default                        → false
```

Percentage rollouts must be **sticky** — the same user sees the same variant across requests and restarts. Hash a stable key, not randomness:

```typescript
function bucketFor(userId: string, flagKey: string, salt = 'v1'): number {
  const hash = createHash('sha256').update(`${flagKey}:${salt}:${userId}`).digest();
  return hash.readUInt32BE(0) % 100; // deterministic 0-99
}

function isEnabled(flag: FlagConfig, userId?: string): boolean {
  if (flag.allowList?.length && userId && flag.allowList.includes(userId)) return true;
  if (flag.rolloutPercent >= 100) return true;
  if (!userId) return flag.rolloutPercent >= 50; // define anonymous traffic explicitly!
  return bucketFor(userId, flag.key) < flag.rolloutPercent;
}
```

Stickiness also gives you clean ramp math: moving 5% → 10% keeps the original 5% users in treatment, so experiment deltas stay interpretable.

## Implementation: minimal resilient client

```typescript
type FlagValue = boolean | string | number;

interface FlagSnapshot {
  readonly revision: number;
  readonly fetchedAt: number;
  get(key: string, ctx: { userId?: string; attrs?: Record<string, string> }): FlagValue;
}

class FeatureFlagClient {
  private snapshot: FlagSnapshot;
  private readonly fallback: Map<string, FlagValue>; // last-known-good

  constructor(private store: FlagStore, private logger: Logger) {
    this.snapshot = store.initial();
    this.fallback = new Map();
    // Push/stream updates; never block callers on refresh
    store.subscribe((next) => {
      this.snapshot = next;
      for (const [k, v] of store.lastKnownGood()) this.fallback.set(k, v);
    });
  }

  enabled(key: string, ctx: { userId?: string } = {}): boolean {
    try {
      const v = this.snapshot.get(key, ctx);
      if (typeof v === 'boolean') return v;
    } catch (err) {
      // Evaluation must never take down the request path
      this.logger.error({ err }, 'flag eval failed');
    }
    return false; // safe default: feature off
  }

  killSwitch(key: string): boolean {
    // Ops flags invert: absence of fresh data means OFF
    const staleMs = Date.now() - this.snapshot.fetchedAt;
    if (staleMs > 120_000) return false;
    return this.enabled(key, {});
  }
}
```

Two non-negotiables visible above: evaluation failures degrade to **off**, and kill switches treat staleness as **disabled** — the switch exists precisely for moments when infrastructure is unhappy.

## Kill Switches & Their SLA

A kill switch is an ops flag whose job is to make a bad thing stop **faster than a rollback would**. Treat it as an SLO-backed component:

| Property | Target |
| ----------------------------------------- | ------------------------------------------------ |
| Propagation latency (decision → all pods) | < 60s |
| Evaluation overhead per request | < 1ms (local cache) |
| Availability independent of admin UI | Yes — control plane separate from serving plane |
| Behavior when store unreachable | Fail-safe default (feature OFF for risky paths) |
| Auditability | Every toggle logged: who, when, why, ticket link |

Operational drill: flip each critical kill switch in staging monthly. An untested kill switch is Schrödinger's rollback.

## Safe Rollout Recipe

```text
1. Wrap new code path in flag (default OFF), merge, deploy dark
2. Dogfood: allow-list team accounts; verify metrics/logs locally
3. Internal users: expand list; watch error rate + latency dashboards
4. Canary: 1% → 5% → 25% → 50% → 100%, gated on:
     - error rate delta < baseline + 0.5%
     - p99 latency delta < 10%
     - no new Sentry issues at severity >= warning
   Hold each step ≥ 30 min (or one full traffic cycle)
5. Announce; keep flag at 100% for one full week (rollback window)
6. CLEAN UP: remove branch + flag from code; close ticket
```

Step 6 is where most teams leak. Institutionalize it:

- Every flag carries metadata: owner, created-date, linked issue, intended expiry.
- CI job greps for flags older than N days still referenced → opens cleanup PR / pings owner.
- Registry audit: flags defined in store but absent from codebase for 2 weeks → auto-archive.

## Flag Debt Management

Undeleted flags compound like unindexed queries:

| Symptom | Cause | Fix |
| ------------------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------- |
| `isEnabled('newCheckout')` always true since 2023 | Cleanup skipped | Delete branch; keep only the old path removal commit |
| Combinatorial test explosion | Many long-lived release flags | Time-box release flags; permanent behavior goes behind permissions/config instead |
| Nobody knows what flag X does | Missing metadata | Require owner+description+expiry at creation |
| Stale flag flips cause surprise | No audit trail | Log toggles to central audit stream; alert on prod flips of aged flags |

Budget: if more than ~10% of your flags outlive their intended lifespan, cleanup is under-resourced — make it part of the feature's definition-of-done, not a someday task.

## Common Mistakes

| Mistake | Problem | Fix |
| --------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------- |
| Flag checks deep in domain logic | Untestable tangle; flags live forever | Evaluate once at edge/composition layer; pass plain values inward |
| Random per-request percentage | Users flip variants mid-session; experiments unreadable | Sticky hashing on stable user key |
| Remote-evaluating flags on hot path | Vendor outage = site outage | Local snapshot evaluation |
| Kill switch default ON when store down | Broken feature stays broken during outage | Fail toward disabled for risky paths |
| One flag reused for different audiences | Semantics drift; cleanup impossible | New purpose = new flag |
| No anonymous-traffic policy | Bots/crawlers skew rollouts unpredictably | Decide explicitly (bucket by IP hash / exclude / full-on) |

## Interview Questions

**Q: "How do you ship a feature to 1% of users safely?"**

> Merge dark behind a release flag, dogfood via allow-list, then sticky-hash percentage rollout 1→5→25→50→100 gated on error-rate and latency deltas. Keep the flag at 100% through a rollback window, then delete the flag and dead code as part of the same ticket. Rollback is a flag flip (< 60s propagation), not a redeploy.

**Q: "What happens when your flag service goes down?"**

> Nothing, by design: clients hold a last-known-good snapshot locally and evaluate in-process. For kill switches I additionally treat stale snapshots (> 2 min) as disabled for risky paths, so an outage fails toward safety rather than keeping a burning feature lit.

---

## 30-Second Interview Version

> Feature flags decouple deploy from release. Four types — release (short-lived), experiment (measured windows), ops/kill-switches (fast disable), permissions (product data). Serve them from a store with local SDK evaluation so the request path never depends on the flag service. Rollouts use sticky hashing for consistent audience assignment and step-wise gates on error/latency metrics. The discipline that matters most is cleanup: every flag gets an owner and expiry, and CI nags until the flag and its dead branch are deleted.

---

## Summary

- Flags convert risky deploys into reversible runtime decisions; four types have very different lifespans and failure modes.
- Evaluate locally from pushed snapshots; remote evaluation only for admin paths.
- Sticky percentage hashing makes rollouts coherent and experiments measurable.
- Kill switches need an SLA and monthly drills; they fail toward disabled.
- Flag debt is real debt: owner, expiry, CI enforcement, deletion in the same ticket as the rollout completion.

## Cheat Sheet

```text
FEATURE FLAGS CHEAT SHEET
═══════════════════════════════════════
TYPES:
• Release    - ship dark, short-lived, eng-owned
• Experiment - measured A/B, fixed window
• Ops        - kill switches, fail-safe defaults
• Permission - entitlements, durable + audited

ROLLOUT RECIPE:
• dark deploy -> allow-list -> internal -> 1/5/25/50/100%
• gate each step: errors, latency, sentry
• rollback = flag flip, not redeploy

HARD RULES:
• evaluate locally (snapshot), never block on store
• sticky hash for percentages
• kill switch + stale data = OFF
• every flag: owner, expiry, ticket
• cleanup is part of done

DEBT SIGNALS:
• flag older than expiry -> nag/delete
• flag unused 2 weeks -> archive
• >10% overdue -> fix the process
```

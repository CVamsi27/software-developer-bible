# Backup Strategy & Restore Drills

A primary database replicates an accidental `DELETE` to every live replica. Recovery needs a protected historical copy, a complete log chain and a tested way to restore service from the selected point.

## Definition

A **backup strategy** specifies recoverable historical copies, their protection and retention, and how the service will be restored. A **restore drill** exercises that procedure with checks and timing rather than inferring recoverability from a successful upload.

> **Textbook Definition:** A backup strategy defines recoverable copies, retention, integrity checks and restoration procedures against recovery objectives. A restore drill measures whether those procedures recover usable state within the chosen objectives.

**Recovery Point Objective (RPO)** is the maximum acceptable loss window; **Recovery Time Objective (RTO)** is the maximum acceptable time to restore service. They are business targets. Actual recovery measurements may miss them.

## First Principles

A replica normally copies valid and invalid writes alike. Deleting a table can therefore reach every live replica; recovery needs a historical state before that event. A historical copy is useful only with readable keys, a complete change chain and compatible restore tools. Retrieval and replay take time, and the application must be able to use the recovered state.

A second copy controlled by the same compromised credentials may also be deleted. Independence requires access and failure boundaries, not just a second bucket name. Retention also makes sensitive data survive after its deletion from the live service, so restore and deletion policy must be designed together.

## Trace an Accidental Deletion

```text
10:00 base backup + uninterrupted archived changes
10:31 valid order commits
10:32 destructive transaction commits and reaches replicas
10:40 incident discovered
       restore clean target → replay to just before destructive commit
       verify business state → reconcile effects → fence/cut over writers
```

The target is a point before the destructive change, not simply “the latest artifact.” Transactions after that target may be lost from the restored database. A payment provider, outgoing email or object store can still contain later effects: rolling back database time does not roll back the world. Inventory and reconcile these identities before replaying jobs or admitting new writes.

## What the Backup Contains

| Representation | Useful property | Conditions |
| -------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Logical dump | Database objects/data can be loaded and sometimes selected individually | Roles/extensions and surrounding configuration may be separate; compatibility and load time must be tested |
| Physical base backup | Starting state for a matching database recovery procedure | Requires compatible server/tool versions and complete needed log history for point-in-time recovery |
| Storage snapshot | Fast copy of a storage state under its consistency contract | Independent volumes/process state can require coordination; snapshot existence does not prove database consistency |

**Point-in-time recovery (PITR)** restores a base and replays a continuous sequence of database change records to the chosen target. PostgreSQL calls these records write-ahead log (WAL). An archived WAL segment alone is not a complete database backup. Database-specific commands live in [Backups, PITR & Recovery](../../../20-backend/20.4-database/05-operations-and-scaling/20.4.5.04-backups-pitr-recovery.md).

Full backups copy the selected whole state. Incrementals contain changes since the prior backup; differentials contain changes since a full baseline. The restore chain depends on the tool's format and guarantees. Neither “physical is always fastest” nor “logical is portable across every version” is a safe design rule.

## Derive the Schedule From Recoverable Evidence

A hourly job does not automatically establish a one-hour RPO. Include job duration, failures, transfer/archival delay and the last verified recovery point. For continuous archival, monitor whether the complete required history actually reached protected storage, not merely whether a primary replica is caught up.

RTO includes declaration/detection under the chosen measurement convention, credentials, provisioning, retrieval, restore/replay, verification, writer fencing, routing and application recovery. Agree on the start/end of the clock so teams compare the same objective.

For an illustrative decimal 500 GB restore with a four-hour target and 30 minutes reserved for other work:

```text
available bulk-restore time = 3.5 × 3600 = 12,600 seconds
required average throughput = 500,000 MB / 12,600 ≈ 39.7 MB/s
```

That is only a throughput floor. WAL replay, index work, storage limits and semantic verification can dominate. Measure a representative dataset and target; do not infer a four-hour full recovery from a fast download.

A derived dataset can be rebuildable yet still require retained source data, compatible processing code and time inside the service recovery objective. “Derived” alone is not a reason to omit recovery planning.

## Protect the Copies and Their Keys

The **3-2-1** heuristic asks for three copies, two different media types and one offsite copy. Common extensions add an offline/immutable copy and verified restores. These are prompts to examine shared failure modes, not proof from counting objects. Cross-region storage can still share one administrator or encryption key.

S3 Object Lock applies retention/legal holds to object versions under its documented modes. Compliance mode and governance mode have different bypass contracts. Protect versioning, encryption keys, backup catalogs and restore credentials too; locking bytes while allowing key deletion can still destroy recoverability. A cross-account copy needs independently controlled restore access.

Choose retention from documented business, legal and deletion requirements for the actual jurisdiction/data. There is no universal seven-year payment-backup rule. Operational recovery history and long-term audit records often need different shapes and access policies.

## Verify From Bytes to Service Behavior

| Check | Evidence it supplies | What it does not prove |
| -------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Manifest checksum | Bytes match the trusted recorded digest | Logical correctness, recoverability or authenticity of a compromised manifest |
| Decompress/list/load | Format/tool can read the artifact | Required data completeness and business meaning |
| Recovered-state assertions | Expected rows, invariants and time boundary hold | All application paths or recovery duration |
| Application smoke test | Selected service behavior works against recovered data | Production cutover, external side effects or whole fleet capacity |
| Timed recovery drill | Selected scenario has measured end-to-end result | Untested incidents, larger datasets or lost credentials |

An object-store ETag is not universally a whole-file checksum, especially with multipart/encrypted uploads. Use the backup tool or storage API's documented checksums and a trusted manifest.

This complete **GNU coreutils/Linux** fragment verifies one local artifact against a sibling manifest containing only its SHA-256 hex digest. It does not restore a database, check semantic freshness or authenticate the manifest. Do not run untrusted restored code/SQL against production; use an isolated recovery environment.

```bash
#!/usr/bin/env bash
set -euo pipefail
backup=${1:?usage: verify-artifact /path/to/backup}
expected=$(cat -- "${backup}.sha256")
[[ "$expected" =~ ^[0-9a-f]{64}$ ]] || { echo 'invalid manifest' >&2; exit 1; }
# Hash stdin so filename characters cannot alter checksum-manifest syntax.
actual=$(sha256sum < "$backup")
actual=${actual%% *}
[[ "$actual" == "$expected" ]] || { echo 'checksum mismatch' >&2; exit 1; }
echo 'artifact checksum verified; restore validation still required'
```

Do not use the file's local modification time as the recovery point: copying an old artifact can give it a new timestamp. Record the source snapshot/log position, creation and verification evidence in the catalog. Semantic freshness assertions must be relative to the selected recovery target; an intentionally old PITR target should not fail merely because its rows are older than today.

## A Runbook an Unfamiliar On-Call Can Execute

1. State the scenario, chosen target time/log position, acceptable lost work and authority to cut over.
2. Find the catalog, full chain, tools/versions, keys and break-glass access without depending on the failed primary environment.
3. Provision an isolated target with outbound side effects disabled. Restore and replay to the selected point under the database's documented target semantics.
4. Check schemas, business totals, identities, required objects and application behavior against expected target state. Keep record of what was checked and what was omitted.
5. Reconcile external effects and queued jobs; fence the old writer before enabling the recovered authority. Routing propagation alone does not prevent dual writers.
6. Measure actual RPO/RTO, enable traffic under observation and record a recovery/fallback decision if the new target fails checks.
7. Repair the runbook and missing controls, then repeat changed portions. Select drill frequency from risk and changing infrastructure rather than a universal monthly/quarterly rule.

Keep offline-accessible instructions and securely available credentials when the identity provider/wiki may also be unavailable. Restore environments contain real sensitive data unless deliberately sanitized; their access, retention and deletion matter too.

## Common Mistakes

| Mistake | Repair |
| ----------------------------------------------- | ----------------------------------------------------------------------------------- |
| Replication described as historical recovery | Retain protected points and required change chains |
| Latest upload treated as last recoverable point | Check complete, verified source position/history |
| Restored jobs resend old external effects | Disable dispatch and reconcile stable operation identities |
| Restore only data | Include roles, configuration, keys, extensions and compatible application artifacts |
| Matching row count treated as correctness | Check business invariants and selected application behavior |
| Unmeasured “warm replica restores in minutes” | Time failover, fencing, verification and cutover for the selected failure |

## Summary

Backups preserve historical recovery options; drills establish what can actually be recovered. Derive copy/log schedules and restore capacity from RPO/RTO, protect both artifacts and keys, and verify meaning as well as bytes. A database rewind also needs external-effect reconciliation and one writable authority before traffic returns.

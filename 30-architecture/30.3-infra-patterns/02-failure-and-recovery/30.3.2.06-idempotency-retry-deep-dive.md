# Idempotency & Retry Patterns — Deep Dive

> Stage 7 of the [Failure & Recovery](INDEX.md) — prev: [Idempotency Keys](30.3.2.03-idempotency-keys.md)
>
> **TL;DR:** In production distributed systems, retries are mandatory (networks fail) but retries without idempotency cause duplicates (double charges, double emails). The deep-dive patterns: idempotency keys with TTL, deduplication windows, idempotent database operations, retry budgets with circuit breakers, and the full chain from API → outbox → consumer. The senior test is designing the complete retry+idempotency chain, not just one piece.
>
> **Why it matters:** This is a Backend / Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## First Principles

(→ 30.3.2.02 + → 30.3.2.03 combined; the deep-dive axioms:)

1. **Idempotency is a property of the operation's *state transition*, not its syntax.** `PUT /settings` (full replace) is naturally idempotent; `POST /increment` is not — until a key makes it replay-safe. Classify operations first; add keys where transitions aren't naturally repeatable.
2. **The interaction matrix matters**: retry × idempotency × ordering. At-least-once + unordered delivery requires dedupe by key; at-least-once + ordered per-key requires per-key sequencing — the delivery semantics (→ 20.6.2.05) determine which combination you must build.
3. **The end state is convergence**: what matters is that after all retries and duplicates settle, the state equals the single-application outcome — the same convergence criterion as CRDTs (→ 30.2.2.22), applied to workflows.

## Definition

**Idempotency** is the property that an operation produces the same result whether executed once or multiple times. **Retry patterns** handle transient failures by re-executing operations. Together, they form the reliability foundation of distributed systems: retries handle failure, idempotency makes retries safe.

**The equation:**
```
Reliable distributed system = Retries (handle transient failure)
                            + Idempotency (make retries safe)
                            + Circuit breaker (stop retrying when downstream is down)
                            + DLQ (capture what can't be retried)
```

## Why Do We Need It?

1. **Networks are unreliable** — TCP retries, load balancer reroutes, DNS TTL changes
2. **HTTP is not at-most-once** — servers may receive a request, process it, and crash before responding
3. **Message queues redeliver** — if a consumer crashes mid-processing, the message is redelivered
4. **User behavior** — users double-click submit, refresh during slow responses
5. **Microservices** — every network call is a potential failure point

## How It Works

### The Complete Reliability Chain

```text
┌────────────────────────────────────────────────────────────────────────┐
│ Complete Retry + Idempotency Chain                                     │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  Client                                                                │
│  ├── Generate idempotency key (UUID or client-generated)               │
│  ├── POST /payments with header: Idempotency-Key: abc-123              │
│  └── Retry on 5xx/timeout (up to 3 times, same key)                    │
│                                                                        │
│  API Gateway / Load Balancer                                           │
│  ├── May retry on backend timeout (connection reset)                   │
│  └── Same idempotency key reaches server again                         │
│                                                                        │
│  Server                                                                │
│  ├── Idempotency guard: check if key exists                            │
│  │   ├── Found → return cached response (no duplicate)                 │
│  │   └── Not found → process, store response with key                  │
│  ├── Business logic: create payment                                    │
│  ├── Write to outbox: same transaction as business data                │
│  └── Return response                                                   │
│                                                                        │
│  Consumer (async)                                                      │
│  ├── Read event from outbox/broker                                     │
│  ├── Deduplication: check if event ID already processed                │
│  │   ├── Already processed → ack (skip)                                │
│  │   └── Not processed → process + mark as processed                   │
│  ├── On failure: retry with exponential backoff                        │
│  └── After max retries: move to DLQ                                    │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

## Code Examples

### Idempotency Key at API Layer

```typescript
// idempotency.guard.ts — NestJS guard for idempotent POST endpoints
@Injectable()
export class IdempotencyGuard implements CanActivate {
  constructor(private cache: TenantCacheService) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest();
    const response = context.switchToHttp().getResponse();

    if (!['POST', 'PUT', 'PATCH'].includes(request.method)) return true;

    const key = request.headers['idempotency-key'];
    if (!key) return true; // optional — some endpoints require it

    const cacheKey = `idempotency:${key}`;
    const existing = await this.cache.get(cacheKey);

    if (existing) {
      // Return the cached response — no duplicate processing
      const parsed = JSON.parse(existing);
      response.status(parsed.statusCode).json(parsed.body);
      return false; // short-circuit the handler
    }

    // Store a placeholder to prevent concurrent duplicate processing
    await this.cache.set(cacheKey, JSON.stringify({ statusCode: 202, body: 'processing' }), 'EX', 86400);

    // Monkey-patch response to capture and cache the result
    const originalJson = response.json.bind(response);
    response.json = (body: any) => {
      this.cache.set(cacheKey, JSON.stringify({ statusCode: response.statusCode, body }), 'EX', 86400);
      return originalJson(body);
    };

    return true;
  }
}
```

### Retry with Exponential Backoff + Jitter

```typescript
// retry.util.ts
interface RetryOptions {
  maxRetries: number;        // e.g., 3
  baseDelayMs: number;       // e.g., 1000
  maxDelayMs: number;        // e.g., 30000
  jitter: boolean;           // true — add randomness to prevent thundering herd
  retryableErrors: string[]; // e.g., ['ECONNRESET', 'ETIMEDOUT', '502', '503']
}

async function withRetry<T>(
  fn: () => Promise<T>,
  options: RetryOptions,
): Promise<T> {
  let lastError: Error;

  for (let attempt = 0; attempt <= options.maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error as Error;

      // Check if error is retryable
      const isRetryable = options.retryableErrors.some(
        (e) => error.message.includes(e) || error.code === e
      );
      if (!isRetryable) throw error; // non-retryable → fail immediately

      if (attempt === options.maxRetries) break; // exhausted

      // Exponential backoff with jitter
      const delay = Math.min(
        options.baseDelayMs * Math.pow(2, attempt),
        options.maxDelayMs
      );
      const jitterMs = options.jitter ? Math.random() * delay * 0.5 : 0;
      await sleep(delay + jitterMs);
    }
  }

  throw lastError;
}
```

### Idempotent Database Operations

```typescript
// payment.service.ts — idempotent payment creation
async function createPayment(tenantId: string, dto: CreatePaymentDto) {
  return prisma.$transaction(async (tx) => {
    // 1. Check if payment with this idempotency key already exists
    const existing = await tx.payment.findUnique({
      where: { idempotencyKey: dto.idempotencyKey },
    });
    if (existing) return existing; // already processed — return cached result

    // 2. Create the payment (unique constraint on idempotencyKey prevents duplicates)
    const payment = await tx.payment.create({
      data: {
        tenantId,
        idempotencyKey: dto.idempotencyKey,
        amount: dto.amount,
        patientId: dto.patientId,
        status: 'PENDING',
      },
    });

    // 3. Write outbox event (same transaction)
    await tx.outboxEvent.create({
      data: {
        tenantId,
        eventType: 'payment.created',
        aggregateId: payment.id,
        payload: { paymentId: payment.id, amount: dto.amount },
      },
    });

    return payment;
  });
}
```

### Consumer-Side Deduplication

```typescript
// payment-consumer.ts — idempotent event handler
async function handlePaymentCreated(event: PaymentCreatedEvent) {
  const dedupKey = `payment-processed:${event.paymentId}`;

  // 1. Check if already processed
  const alreadyProcessed = await redis.get(dedupKey);
  if (alreadyProcessed) {
    console.log(`Skipping duplicate event for payment ${event.paymentId}`);
    return; // already handled
  }

  try {
    // 2. Process the event
    await sendPaymentConfirmation(event.patientId, event.amount);

    // 3. Mark as processed (with TTL for eventual cleanup)
    await redis.set(dedupKey, '1', 'EX', 7 * 86400); // 7 days
  } catch (error) {
    // 4. Retry logic — rethrow to trigger message queue retry
    throw error;
  }
}
```

### Retry Budget with Circuit Breaker

```typescript
// retry-budget.ts — prevents retry storms
class RetryBudget {
  private retryCount = 0;
  private windowStart = Date.now();
  private readonly windowMs = 10000; // 10 second window
  private readonly maxRetriesPerWindow = 10;

  canRetry(): boolean {
    const now = Date.now();
    if (now - this.windowStart > this.windowMs) {
      // Reset window
      this.retryCount = 0;
      this.windowStart = now;
    }
    return this.retryCount < this.maxRetriesPerWindow;
  }

  recordRetry(): void {
    this.retryCount++;
  }
}

// Usage with circuit breaker
const retryBudget = new RetryBudget();
const circuitBreaker = new CircuitBreaker({
  failureThreshold: 5,
  resetTimeoutMs: 30000,
});

async function callExternalService(request: Request) {
  if (!retryBudget.canRetry()) {
    throw new Error('Retry budget exhausted — circuit breaker should trip');
  }

  return circuitBreaker.execute(async () => {
    return withRetry(
      () => httpClient.post('/api/payments', request),
      { maxRetries: 3, baseDelayMs: 1000, jitter: true, retryableErrors: ['ECONNRESET', '503'] }
    );
  });
}
```

## Real-World Use Cases

| Pattern | Where Used | Why |
| --------------------------- | -------------------------------- | -------------------------------------- |
| **Idempotency keys** | Payment APIs (Stripe, Razorpay) | Prevent double charges on retry |
| **Deduplication windows** | Webhook receivers | Webhooks retry on failure |
| **Retry budgets** | Service-to-service calls | Prevent thundering herd on recovery |
| **Idempotent consumers** | Message queue processors | Messages redelivered on consumer crash |
| **Circuit breaker + retry** | External API calls (AI, payment) | Stop retrying when downstream is down |
| **DLQ** | All async processing | Capture failures for manual review |

## Common Mistakes

### 1. Retries Without Idempotency

```typescript
// BAD: Retrying a non-idempotent operation
await httpClient.post('/api/payments', paymentData); // retried → double charge!

// GOOD: Idempotency key makes retry safe
await httpClient.post('/api/payments', paymentData, {
  headers: { 'Idempotency-Key': uuid() },
});
```

### 2. Infinite Retries

```typescript
// BAD: No retry budget — retry storm
while (true) {
  try {
    await callService();
    break;
  } catch (e) {
    await sleep(1000); // retries forever if service is down
  }
}

// GOOD: Retry budget + circuit breaker
const budget = new RetryBudget();
while (budget.canRetry()) {
  try {
    await callService();
    break;
  } catch (e) {
    budget.recordRetry();
    await sleep(Math.min(1000 * Math.pow(2, budget.retryCount), 30000));
  }
}
```

### 3. No Jitter → Thundering Herd

```typescript
// BAD: All clients retry at the same interval
await sleep(1000); // all 1000 clients retry at exactly 1000ms

// GOOD: Add jitter
await sleep(1000 + Math.random() * 500); // spread across 1000-1500ms
```

### 4. Deduplication Window Too Short

```typescript
// BAD: 1-minute dedup window — late retries bypass it
await cache.set(key, '1', 'EX', 60); // 1 minute

// GOOD: Match the retry window — 24 hours for safety
await cache.set(key, '1', 'EX', 86400); // 24 hours
```

## Best Practices

1. **Idempotency keys on all POST endpoints** — client-generated UUID, stored with response.
2. **Retry budgets** — limit retries per time window to prevent storms.
3. **Exponential backoff + jitter** — prevent thundering herd on recovery.
4. **Idempotent consumers** — deduplicate with event ID + TTL cache.
5. **Circuit breaker** — stop retrying when downstream is consistently failing.
6. **DLQ for failures** — after max retries, move to DLQ for inspection.
7. **Unique constraints** — database unique constraint on idempotency key as last resort.
8. **Retryable error classification** — only retry on transient errors (5xx, timeout, connection reset).
9. **Monitoring** — track retry rate, idempotency cache hit rate, DLQ size.
10. **Test idempotency** — verify that calling the same endpoint twice produces the same result.

## Summary

Idempotency and retry patterns form the reliability foundation of distributed systems. The complete chain: client generates idempotency key → API guard checks for duplicates → business logic writes to outbox in same transaction → consumer deduplicates with event ID → DLQ captures failures. Exponential backoff with jitter prevents thundering herd; retry budgets prevent storms; circuit breakers stop retrying when downstream is down. The senior test is designing this complete chain, not just one piece.

## Cheat Sheet

```text
Complete Reliability Chain:
├── Client: generate idempotency key (UUID)
├── API: idempotency guard (check cache/DB)
├── Business: idempotent DB operation (unique constraint)
├── Outbox: event in same transaction as business data
├── Consumer: deduplicate with event ID + TTL
├── Retry: exponential backoff + jitter + budget
├── Circuit breaker: stop when downstream is down
└── DLQ: capture what can't be retried

Retry Decision Tree:
├── Is error transient? (5xx, timeout, connection reset) → retry
├── Is error permanent? (4xx, validation) → don't retry
├── Retry budget exhausted? → circuit breaker should trip
├── Dedup window expired? → reprocess (risk of late duplicate)
└── DLQ size growing? → investigate root cause

Idempotency Key Storage:
├── Short-lived: Redis with TTL (24h) — fast, ephemeral
├── Persistent: Database unique constraint — audit trail
├── Hybrid: Redis cache + DB fallback — fast + durable
└── Consumer: event ID + processed set — exactly-once semantics
```

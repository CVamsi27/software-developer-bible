# Idempotency & Retry Patterns — Deep Dive

## Definition

**Idempotency** means repeating an operation has the same intended effect as applying it once. A retry repeats one logical operation after a failed or uncertain attempt. The combined design must preserve identity and durable evidence across each system boundary; identical response replay is a separate API promise.

> **Textbook Definition:** Safe retry combines repeatable effects or operation deduplication with classified failures, bounded attempts and recovery of uncertain outcomes. End-to-end reliability requires each participating authority to preserve those contracts at its own commit boundary.

## First Principles

One database cannot atomically commit an unrelated broker, payment gateway and email provider. A process can crash between any two external operations. After a timeout, another participant may have completed its effect even when the caller lacks evidence.

Consequently, one deduplication cache or API guard cannot guarantee the whole workflow. Each boundary needs a stable identity, an atomic local effect or receiver contract, and a way to recover uncertain results. Duplicate suppression also differs from ordering: applying event 2 once before event 1 can still produce the wrong state.

## Trace an Order Through the Authorities

```text
client operation K → API database: claim K + order + replay result + outbox intent
                         │ one commit
                         ▼
relay event E → broker (may accept before relay records publication)
                         │ E can be redelivered
                         ▼
consumer database: inbox E + local change + notification intent
                         │ one commit, then delivery acknowledgment
                         ▼
notification sender → provider identity N → accepted / rejected / unknown
```

The database transaction ensures the order cannot commit without its delivery intent. It does not establish that the broker or provider received the intent. A timeout after publication can cause duplicate E; a timeout after a send can leave N unknown. Stable identities let the receiving authorities distinguish repeated attempts **if their documented contract supports it**.

## API: Commit the Claim and Effect Together

The [Idempotency Keys](30.3.2.03-idempotency-keys.md) chapter owns the PostgreSQL claim/effect/replay SQL. The API derives tenant scope from verified authorization, validates business input, and compares its fingerprint before returning an existing result.

Trace concurrent requests A and B with `(tenant, operation, K)`:

1. A inserts the unique claim in its transaction. B's competing insert waits on that uniqueness boundary.
2. A creates the order, its response and outbox intent, then commits.
3. At READ COMMITTED, B's next statement reads the committed claim/result with a fresh snapshot, checks the fingerprint and replays it.
4. If A aborts, its claim/effect roll back and another attempt can become the winner. If the connection fails around commit, the caller reuses K to discover which outcome became durable.

A Redis GET followed by SET is not a claim. Even an atomic Redis claim leaves a gap if its business effect commits in another database. A NestJS guard that returns false may invoke the framework's forbidden-response behavior; monkey-patching an Express response also ties the mechanism to one adapter and can lose asynchronous cache writes. Use a defined endpoint/interceptor/service transaction contract instead of treating those hooks as durable execution control.

## Relay: Publication Is Not a Database Flag

Commit an outbox intent with the order. The relay claims pending intents, submits them and records progress. If the broker accepted E but the acknowledgment or progress update is lost, resubmission is required and can repeat delivery. Claim recovery must account for a paused previous claimant; do not erase pending work merely because a timer expired.

Preserve per-aggregate ordering where required. `SKIP LOCKED` can let one relay skip E1 and publish E2 first. Partitioned broker ordering begins only after records enter the relevant ordered partition and does not repair earlier publication reordering. The [Transactional Outbox & CDC](../../30.2-system-design/01-theory/30.2.1.18-outbox-and-cdc.md) chapter owns the SQL and relay mechanism.

## Consumer: Acknowledge After Its Local Commit

For an effect in one database, insert `(consumer, event ID)` into an inbox/processed table and apply the business mutation **in the same transaction**. Then acknowledge the broker. If that acknowledgment is lost, the repeat sees the committed inbox identity and does not reapply the mutation.

The identity must represent the event/operation being deduplicated. Deduplicating every event by payment ID can drop a later legitimate `payment.refunded` event. Payload conflicts under the same event identity should be detected, not silently treated as harmless repeats.

For notifications, record a durable notification intent locally. The sender carries stable N to a provider that supports that identity and retention contract. Sending email and only afterward writing `processed` in Redis leaves a crash gap; setting the marker first instead can permanently skip the email. Without receiver deduplication or lookup, exactly one remote send cannot be guaranteed by local marking alone.

## Retry Budgets Belong to the Call They Bound

The [Retry Patterns](30.3.2.02-retry-patterns.md) chapter owns the complete bounded read helper. Mutations add the stable operation identity and provider-specific reconciliation policy. Do not generate a new UUID inside each repeated call.

Separate original admission from additional attempts. An exhausted retry budget can stop repeats while still allowing useful originals; a breaker uses selected dependency outcomes to decide whether to call at all. Placing the breaker outside retries counts whole-operation outcomes; placing it around attempts counts attempts. Choose what it observes rather than assuming one universal wrapper order.

Transport retransmission is not the same as application-operation repetition. TCP repeats bytes within a connection; application clients, proxies, SDKs and queue consumers can independently repeat logical work. Inspect and bound every configured retry owner.

## Poison Events and Recovery

A **dead-letter queue (DLQ)** holds messages a configured delivery policy could not process. It is an operational workflow, not a guarantee that a failed business effect never occurred. Preserve event identity, attempts, error classification and unknown-effect evidence.

Before replaying, fix the cause, decide whether the old schema/authorization context is still valid, and check receiver retention horizons. A seven-day queue replay with a one-day deduplication record can execute a forgotten operation again. Some permanent business uniqueness constraints must outlive temporary retry/response caches.

A corrective replay may need a new event identity because it represents a new intended transition; repeating a still-uncertain original must keep the original identity. Document that distinction instead of generating fresh IDs for all replays.

## Prove the Failure Boundaries

| Injected failure | Expected evidence |
| ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| Two simultaneous API submissions with same K | One local effect and consistent replay; different fingerprint rejected |
| API loses response after commit | Repeat K discovers durable original outcome |
| API crashes before commit | No partial local claim/effect/outbox |
| Relay loses publication acknowledgment | E may repeat; consumer local effect remains single |
| Consumer crashes after local commit before ack | Redelivery finds inbox E and skips effect |
| Provider accepts N but caller times out | Receiver lookup/retry under same N or explicit unknown-effect recovery |
| Old event arrives after dedup record expiry | Documented re-execution boundary or permanent uniqueness prevents it |
| E2 arrives before E1 | Sequence/version policy rejects, waits or applies a defined commutative transition |

Calling the same endpoint twice sequentially tests only a narrow happy path. Crash, concurrency, retention, tenant isolation and delayed-event tests establish the important boundaries.

## Common Mistakes

- Request hash replaces logical identity and collapses intentionally identical purchases.
- A global unique key leaks or replays another tenant's outcome.
- A processed marker is committed separately from its local effect.
- A DLQ replay is assumed safe because the original worker threw an error.
- “Reliable = retries + breaker + DLQ” is treated as a proof. These components still need authority, recovery and capacity contracts.
- At-most-once delivery is achieved by discarding uncertain work without acknowledging the possible lost effect.

## Summary

Reliability is established at each authority's commit boundary. Keep one identity for an uncertain operation, commit local claims/effects/intents together, and carry deduplication or reconciliation to remote receivers. Budgets bound amplification; inbox/outbox mechanisms preserve local evidence; recovery must account for ordering, retention and effects that may already have happened.

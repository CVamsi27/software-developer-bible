# Leader Election & Consensus — Raft, Paxos, Practical Patterns


---

## Definition

**Leader election** selects a process to coordinate work. Consensus-backed services make ownership changes durable and ordered; application leaders then need a way to stop stale work from mutating the protected resource. A Raft **term** is a logical epoch, not a wall-clock lease. A ZooKeeper session, an etcd lease, a PostgreSQL advisory lock and a database lease have different expiry and failure contracts.

> **Textbook Definition:** Leader election designates a process to coordinate work; consensus establishes an agreed value or log across participants. Safe leadership also requires an ownership-transfer contract and enforcement against stale coordinators.

## First Principles

1. **Timeouts detect suspicion, not death.** A paused old leader can resume after a replacement starts. Choosing a replacement does not stop the old process.
2. **The authority must be checked where the effect occurs.** A database can reject an old fencing token atomically; an email provider cannot be fenced by a local flag, so repeated sends need a provider idempotency contract or an explicitly tolerated duplicate.
3. **The coordination store is part of the failure model.** Losing a quorum should prevent new ownership, while recovery must preserve the ordering state that gives fencing tokens meaning.

## How It Works

```text
acquire ownership → receive epoch → start work → renew/check ownership
                                │
                                └→ write(resource, epoch)
                                   resource rejects epoch older than stored epoch

old holder pauses → ownership expires → replacement gets higher epoch
old holder resumes → its older-epoch write is rejected
```

Use [Consensus & Leader Election](../../30.2-system-design/01-theory/30.2.1.09-consensus-and-leader-election.md) for Raft/Paxos voting and log rules. Handwritten vote-counting classes omit durable terms, log freshness and stale RPC handling; they are not practical election implementations.

## Choosing a Primitive

| Primitive | Ownership ends when | Operational boundary |
| ----------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------- |
| etcd lease-backed election | Lease expires or holder resigns | Raft-backed ownership; use the election revision as a fencing value where supported |
| ZooKeeper ephemeral sequential node | Session expires or node is deleted | Lowest sequence wins; watch the predecessor and fence external writes |
| PostgreSQL advisory lock | Session/transaction ends, depending on API | One database connection holds it; failover still needs old-primary fencing |
| Database lease row | Database-clock expiry or explicit release | Conditional renewals and a durable increasing epoch |
| Redis single-instance lease | TTL expires or matching token is released | Advisory coordination; asynchronous failover can lose the key |

A cluster with `n` voters needs `floor(n/2)+1` reachable voters for majority decisions. Three tolerate one unavailable voter; four also tolerate only one; five tolerate two. An isolated leader may still believe it leads, but cannot commit fresh Raft entries without a majority. A controller election and the database's own replication election are separate layers.

## Code Examples

### Database lease with an epoch

The coordinator uses the database clock. Run this against one authoritative PostgreSQL primary, and treat losing that primary as a separate failover problem.

```sql
CREATE TABLE leader_leases (
  name text PRIMARY KEY,
  owner text NOT NULL,
  epoch bigint NOT NULL,
  expires_at timestamptz NOT NULL
);

-- Claim only an expired lease. Each successful replacement increments epoch.
-- No returned row means another owner still holds the lease.
INSERT INTO leader_leases (name, owner, epoch, expires_at)
VALUES ('scheduler', 'node-a', 1, clock_timestamp() + interval '30 seconds')
ON CONFLICT (name) DO UPDATE
SET owner = EXCLUDED.owner,
    epoch = leader_leases.epoch + 1,
    expires_at = EXCLUDED.expires_at
WHERE leader_leases.expires_at <= clock_timestamp()
RETURNING owner, epoch, expires_at;

-- Renew only this acquisition, and never resurrect an expired lease.
UPDATE leader_leases
SET expires_at = clock_timestamp() + interval '30 seconds'
WHERE name = 'scheduler' AND owner = 'node-a' AND epoch = 1
  AND expires_at > clock_timestamp()
RETURNING epoch;
```

Keep the returned epoch with the acquisition. A process identifier alone is insufficient: the same process may lose and reacquire ownership. No renewal row, an RPC timeout, or a coordination error means stop scheduling new work until authority is confirmed. Serialize renewals rather than running overlapping async `setInterval` callbacks.

### Fence the protected write

```sql
CREATE TABLE scheduled_resources (
  id text PRIMARY KEY,
  value text NOT NULL,
  last_epoch bigint NOT NULL DEFAULT 0
);

-- Accept the active epoch, including repeated writes in the same term.
-- Bind :epoch, :value and :id as query parameters in application code.
UPDATE scheduled_resources
SET value = :value, last_epoch = :epoch
WHERE id = :id AND last_epoch <= :epoch
RETURNING id;
```

This is a stale-writer fence once the higher epoch has reached the resource; it does not prove the caller currently holds a lease. Where every write must prove *current* authority, validate the owner, epoch and expiry against the lease row in the same transaction/locking protocol as the mutation. Keep the epoch issuer durable across restarts and restores. A counter on each worker starts at one repeatedly and provides no distributed ordering.

The `<=` comparison lets one holder make several writes; a strict `<` comparison would reject its second write. Business-operation deduplication remains a separate key/unique constraint. Never let caller-supplied payload overwrite the trusted epoch.

### Atomic Redis renewal for advisory work

```typescript
// ioredis syntax. ownerToken is unique for this acquisition, not just nodeId.
async function renewLease(
  redis: Redis, key: string, ownerToken: string, ttlMs: number,
): Promise<boolean> {
  if (!Number.isSafeInteger(ttlMs) || ttlMs <= 0) throw new RangeError('ttlMs');
  const renewed = await redis.eval(`
    if redis.call('get', KEYS[1]) == ARGV[1] then
      return redis.call('pexpire', KEYS[1], ARGV[2])
    end
    return 0
  `, 1, key, ownerToken, ttlMs);
  return renewed === 1;
}
```

A separate `GET` then `PEXPIRE` has a race: the old token can expire between the calls, so the old holder extends the new holder's key. Compare-and-renew in one Lua execution prevents that race. Acquisition uses `SET ... NX PX`, and release likewise compares the token and deletes atomically. This is a single-Redis lease, **not Redlock**; see [Distributed Locks](../../30.2-system-design/01-theory/30.2.1.14-distributed-locks.md) for the timed multi-instance algorithm and its assumptions.

## Failure Handling

| Failure | Response |
| --------------------------------------- | ----------------------------------------------------------------------------------- |
| Holder pauses longer than lease | Replacement may start; reject stale effects at the resource |
| Renewal response is lost | Ownership is uncertain; stop new work and reacquire/check safely |
| Coordination quorum unavailable | Stop new ownership changes; do not invent an election in the minority |
| Primary database fails over | Fence the old primary; a lease table alone does not prevent dual writable databases |
| Restore resets epochs | Preserve a monotonic issuer or rotate the resource namespace before allowing writes |
| External side effect has no fencing API | Use stable business idempotency keys and reconcile unknown outcomes |

## Best Practices

1. Choose the coordination service already operated reliably by the team.
2. Separate election correctness from job delivery: a leader can enqueue the same job twice around failover.
3. Put ownership loss, renewal latency, election count and rejected stale writes on dashboards.
4. Test a live-but-paused holder, a partition and a lost renewal response, not only process termination.
5. Set lease duration from measured pauses and latency; shorter leases trade failover speed for false suspicion.

## Summary

An election changes authority; it cannot stop a paused old process. Use a durable coordination primitive, renew only the current acquisition, and fence effects where they commit. Terms are logical epochs, leases expire in time, and idempotency handles repeated business work. The failure drill that proves the design is a stale holder resuming after its replacement has already written.

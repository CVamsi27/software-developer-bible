# Leader Election & Consensus — Raft, Paxos, Practical Patterns

## First Principles

(→ 30.2.1.09 covers the theory; this chapter is the practice:)

1. **Use off-the-shelf consensus; never write your own.** etcd/ZooKeeper/Postgres advisory locks implement Raft/Zab with years of bug fixes — the pattern is *choosing* the right primitive, not deriving it.
2. **Every leader needs fencing** (→ 30.2.1.09 axiom 3): the epoch token storage checks — because the alternative (trusting the leader's self-report) fails under GC pauses and clock skew, guaranteed.
3. **Advisory locks are the lightweight tier**: Postgres `pg_advisory_lock` for single-DB coordination, Redis leases for advisory-only work (dedupe, cleanup) — matching primitive strength to blast radius is the engineering judgment.

---

## Definition

**Leader election** is the operational form of consensus: a cluster agrees which single member owns a *lease* for a period of time, and only that member performs serialized work (writing the primary, running the singleton job, issuing claims).

The mechanism is always a **lease with a term**, never a vote in the abstract:

```text
etcd/ZooKeeper: create ephemeral node ──▶ session dies ⇒ node vanishes ⇒ others campaign
                                        ──▶ lowest sequence number wins
Raft (used by etcd): candidate bumps term, requests votes,
                      wins with majority ⇒ leader until heartbeat fails
Heartbeat must complete in ≪ lease duration, or a slow node loses its lease.
```

Four properties define a usable implementation, and each has an operational consequence:

1. **Majority quorum** — progress requires `⌊n/2⌋+1` nodes reachable, so an even-sized cluster is worse than the odd size below it, and losing a majority means *no* leader rather than two.
2. **Monotonic terms/epochs** — every leadership carries a higher number, so a resumed or partitioned old leader's writes are rejected by peers (prevents **split brain**).
3. **Fencing at the resource** — a paused leader can wake up believing it still leads; the protected resource must reject writes carrying an older term/fencing token.
4. **Bounded failover** — lease time is the trade: shorter means faster failover but more spurious elections under GC pauses and network jitter.

The design question in an interview is therefore almost never "which protocol?" but **"what happens to work if the leader is alive-but-frozen, and where is the fence?"**

## Why Leader Election?

| Problem | Solution |
| ----------------------- | ----------------------------------- |
| Single point of failure | Leader election with failover |
| Write conflicts | Single leader for writes |
| Coordinated tasks | Leader coordinates distributed jobs |
| Distributed locks | Leader-based or lock-based |

## Consensus Algorithms

## Raft (Practical, Understandable)

**What is leader election?** In a distributed system with multiple servers, you need exactly one server to be "in charge" (the leader) for certain tasks — like accepting writes, running cron jobs, or coordinating distributed locks. If the leader crashes, another server must take over. Leader election algorithms ensure exactly one leader at a time, even during network partitions. Raft is the most practical consensus algorithm — it's designed to be understandable and is used by etcd, Consul, and CockroachDB.

```typescript
// Raft states
enum RaftState {
  FOLLOWER = 'FOLLOWER',
  CANDIDATE = 'CANDIDATE',
  LEADER = 'LEADER'
}

// Raft node implementation (simplified)
class RaftNode {
  private state: RaftState = RaftState.FOLLOWER;
  private currentTerm: number = 0;
  private votedFor: string | null = null;
  private log: LogEntry[] = [];
  private commitIndex: number = 0;
  private lastApplied: number = 0;

  // Election timeout (150-300ms random)
  private electionTimeout: number = this.randomTimeout();
  private lastHeartbeat: number = Date.now();

  // Candidate: Request votes
  async requestVotes(): Promise<void> {
    this.state = RaftState.CANDIDATE;
    this.currentTerm++;
    this.votedFor = this.id;

    const votes = await Promise.all(
      this.peers.map(peer => peer.requestVote({
        term: this.currentTerm,
        candidateId: this.id,
        lastLogIndex: this.log.length - 1,
        lastLogTerm: this.log[this.log.length - 1]?.term || 0
      }))
    );

    const majority = Math.floor(this.peers.length / 2) + 1;
    if (votes.filter(v => v.granted).length >= majority) {
      this.state = RaftState.LEADER;
      this.startHeartbeat();
    }
  }

  // Leader: Send heartbeats
  private startHeartbeat(): void {
    setInterval(() => {
      this.peers.forEach(peer => {
        peer.appendEntries({
          term: this.currentTerm,
          leaderId: this.id,
          prevLogIndex: this.commitIndex,
          prevLogTerm: this.log[this.commitIndex]?.term || 0,
          entries: [],
          leaderCommit: this.commitIndex
        });
      });
    }, 50); // Heartbeat interval
  }

  // Handle incoming requests
  async handleRequestVote(request: VoteRequest): Promise<VoteResponse> {
    if (request.term < this.currentTerm) {
      return { term: this.currentTerm, voteGranted: false };
    }

    if (request.term > this.currentTerm) {
      this.currentTerm = request.term;
      this.state = RaftState.FOLLOWER;
      this.votedFor = null;
    }

    if (!this.votedFor || this.votedFor === request.candidateId) {
      this.votedFor = request.candidateId;
      return { term: this.currentTerm, voteGranted: true };
    }

    return { term: this.currentTerm, voteGranted: false };
  }
}
```

### Paxos (Theoretical Foundation)
```typescript
// Two-Phase Paxos (simplified)
class PaxosNode {
  // Phase 1: Prepare
  async prepare(proposalNumber: number): Promise<PrepareResponse> {
    if (proposalNumber > this.promisedNumber) {
      this.promisedNumber = proposalNumber;
      return {
        accepted: true,
        promisedNumber: proposalNumber,
        acceptedValue: this.acceptedValue,
        acceptedNumber: this.acceptedNumber
      };
    }
    return { accepted: false };
  }

  // Phase 2: Accept
  async accept(proposalNumber: number, value: any): Promise<boolean> {
    if (proposalNumber >= this.promisedNumber) {
      this.promisedNumber = proposalNumber;
      this.acceptedNumber = proposalNumber;
      this.acceptedValue = value;
      return true;
    }
    return false;
  }
}
```

## Practical Leader Election Patterns

### Database-Based Leader Election
```sql
-- Leader election table
CREATE TABLE leader_election (
  id VARCHAR(50) PRIMARY KEY,
  leader_id VARCHAR(100) NOT NULL,
  elected_at TIMESTAMPTZ DEFAULT NOW(),
  expires_at TIMESTAMPTZ NOT NULL,
  heartbeat_interval INTERVAL DEFAULT '10 seconds'
);

-- Acquire leadership
BEGIN;
SELECT * FROM leader_election
WHERE id = 'scheduler'
AND expires_at > NOW()
FOR UPDATE;

-- If no leader or expired, become leader
INSERT INTO leader_election (id, leader_id, expires_at)
VALUES ('scheduler', 'node-1', NOW() + '30 seconds')
ON CONFLICT (id) DO UPDATE
SET leader_id = 'node-1',
    elected_at = NOW(),
    expires_at = NOW() + '30 seconds'
WHERE leader_election.expires_at < NOW();
COMMIT;

-- Heartbeat (extend leadership)
UPDATE leader_election
SET expires_at = NOW() + '30 seconds'
WHERE id = 'scheduler' AND leader_id = 'node-1';
```

## Redis-Based Leader Election

**How it works:** Redis `SET key value NX EX ttl` is an atomic operation: set a key only if it doesn't exist, with a time-to-live. The first server to run this command becomes the leader. The key expires after `ttl` seconds, so the leader must periodically "renew" its leadership by setting the key again. If the leader crashes, the key expires and another server can claim leadership. This is simpler than Raft/Paxos and works well for single-responsibility tasks like cron job coordination.

```typescript
// Using Redis for leader election
async function tryBecomeLeader(
  key: string,
  nodeId: string,
  ttlMs: number
): Promise<boolean> {
  const result = await redis.set(
    key,
    nodeId,
    'NX',
    'PX',
    ttlMs
  );
  return result === 'OK';
}

async function extendLeadership(
  key: string,
  nodeId: string,
  ttlMs: number
): Promise<boolean> {
  // Only extend if we're still the leader
  const currentLeader = await redis.get(key);
  if (currentLeader !== nodeId) return false;

  await redis.pexpire(key, ttlMs);
  return true;
}

// Leadership loop
class LeaderElection {
  private isLeader: boolean = false;
  private interval: NodeJS.Timeout | null = null;

  async start(nodeId: string): Promise<void> {
    this.interval = setInterval(async () => {
      if (!this.isLeader) {
        // Try to become leader
        this.isLeader = await tryBecomeLeader('scheduler:leader', nodeId, 30000);
        if (this.isLeader) {
          console.log(`${nodeId} became leader`);
          this.onBecomeLeader();
        }
      } else {
        // Extend leadership
        const stillLeader = await extendLeadership('scheduler:leader', nodeId, 30000);
        if (!stillLeader) {
          console.log(`${nodeId} lost leadership`);
          this.isLeader = false;
          this.onLoseLeadership();
        }
      }
    }, 10000); // Check every 10 seconds
  }

  private onBecomeLeader(): void {
    // Start leader-only tasks
    this.startScheduledJobs();
  }

  private onLoseLeadership(): void {
    // Stop leader-only tasks
    this.stopScheduledJobs();
  }
}
```

## Distributed Locks

### Redis Distributed Lock (Redlock)
```typescript
class RedisLock {
  constructor(private redis: Redis) {}

  async acquire(
    lockKey: string,
    ttlMs: number
  ): Promise<string | null> {
    const lockValue = uuid();

    const acquired = await this.redis.set(
      lockKey,
      lockValue,
      'NX',
      'PX',
      ttlMs
    );

    return acquired ? lockValue : null;
  }

  async release(lockKey: string, lockValue: string): Promise<boolean> {
    // Lua script for atomic check-and-delete
    const script = `
      if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
      else
        return 0
      end
    `;

    const result = await this.redis.eval(script, 1, lockKey, lockValue);
    return result === 1;
  }

  async extend(lockKey: string, lockValue: string, ttlMs: number): Promise<boolean> {
    const script = `
      if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("pexpire", KEYS[1], ARGV[2])
      else
        return 0
      end
    `;

    const result = await this.redis.eval(script, 1, lockKey, lockValue, ttlMs);
    return result === 1;
  }
}

// Usage
const lock = new RedisLock(redis);
const lockValue = await lock.acquire('appointment:lock:123', 30000);

if (lockValue) {
  try {
    // Critical section
    await updateAppointment(appointmentId, data);
  } finally {
    await lock.release('appointment:lock:123', lockValue);
  }
} else {
  throw new ConflictError('Could not acquire lock');
}
```

### Fencing Tokens
```typescript
// Prevent stale locks from causing issues
class FencedLock {
  private fencingToken: number = 0;

  async withLock<T>(key: string, fn: (token: number) => Promise<T>): Promise<T> {
    const lockValue = await this.acquireLock(key);
    if (!lockValue) throw new LockError('Could not acquire lock');

    this.fencingToken++;

    try {
      return await fn(this.fencingToken);
    } finally {
      await this.releaseLock(key, lockValue);
    }
  }
}

// Server-side validation
async function updateWithFencing(
  appointmentId: string,
  data: any,
  fencingToken: number
): Promise<void> {
  // Only update if fencing token is newer
  const result = await prisma.appointment.updateMany({
    where: {
      id: appointmentId,
      lastFencingToken: { lt: fencingToken }
    },
    data: {
      ...data,
      lastFencingToken: fencingToken
    }
  });

  if (result.count === 0) {
    throw new ConflictError('Stale lock or concurrent modification');
  }
}
```

## Failure Modes

### Split-Brain
```typescript
// Prevention: Use quorum-based decisions
class QuorumDecision {
  private votes: Map<string, boolean> = new Map();

  async vote(nodeId: string, decision: boolean): Promise<boolean> {
    this.votes.set(nodeId, decision);

    const totalNodes = this.nodes.length;
    const requiredVotes = Math.floor(totalNodes / 2) + 1;

    const positiveVotes = Array.from(this.votes.values()).filter(v => v).length;

    if (positiveVotes >= requiredVotes) {
      return true;
    }

    return false;
  }
}
```

### Follower Failure
```typescript
// Raft handles this automatically
// If follower doesn't respond, leader continues with majority
async function handleFollowerFailure(failedNode: string): Promise<void> {
  console.log(`Follower ${failedNode} failed`);

  // Raft continues if majority is available
  const healthyNodes = this.nodes.filter(n => n.id !== failedNode);
  const majority = Math.floor(this.nodes.length / 2) + 1;

  if (healthyNodes.length >= majority) {
    console.log('Majority available, system continues');
  } else {
    console.log('Majority lost, system unavailable');
    this.systemUnavailable();
  }
}
```

## Summary

1. **Many distributed components need exactly one leader** — schedulers, partition assigners, cron runners
2. **Leases beat raw locks** — a time-bounded lease survives a crashed holder without operator intervention
3. **Fencing tokens prevent zombie leaders** — a storage layer that rejects stale epochs is the only true protection
4. **Consensus (Raft) is the correct-but-expensive path** — etcd/Consul/ZooKeeper give it to you off the shelf
5. **Know your split-brain tolerance** — most systems accept brief dual-leadership and use fencing to contain it

# Leader Election & Consensus — Raft, Paxos, Practical Patterns

At 02:00, worker A claims a scheduled settlement and pauses longer than its lease. Worker B takes over. When A resumes, its local `isLeader` flag still says yes, so both may try to write the same charge. The election can be correct while the application repeats an effect.

## Definition

**Leader election** chooses one process to coordinate work. **Consensus** lets replicated nodes agree on a value or ordered log despite failures, within the algorithm's quorum and timing assumptions. A **lease** is a time-bounded ownership grant: expiration lets another process contend, but it does not stop the old process from running.

> **Textbook Definition:** Distributed consensus is the process by which participants agree on one value or a consistent sequence of values despite a defined set of failures. Leader election selects a coordinator; a safe application must also transfer authority durably and prevent an old coordinator from committing effects.

## First Principles

1. **A timeout detects suspicion, not death.** A pause or network partition can hide a live process from the coordinator. The old process may continue using authority it no longer has.
2. **Check authority where the effect commits.** A local leadership flag can be stale. A database can reject an old fencing epoch in the same transaction as a write; an email provider needs its own idempotency or reconciliation contract.
3. **Preserve the ordering authority.** A quorum-backed store must stop granting new leaders when it cannot form a quorum. Recovery must not reuse an old fencing epoch while a protected resource still remembers it.

## Follow the paused leader

```text
worker A acquires lease, epoch 41
worker A pauses ── lease expires ── worker B acquires epoch 42
                                      │
                                      └─ B writes 42; resource records 42
worker A resumes and writes 41 ────────→ resource rejects stale epoch
```

The resource rejects A only after it has observed B's higher epoch. If B has acquired epoch 42 but has not yet written to the resource, an epoch-only check may still accept A's 41. When the invariant requires an expired owner to be rejected immediately, validate the current lease and apply the protected mutation atomically at the resource.

A Raft term is a logical election epoch, not a wall-clock lease. Raft elects a log leader using terms and log freshness, then commits current-term entries through a majority. Paxos uses numbered proposals and intersecting majorities to choose one value. Both preserve agreement within their assumptions; neither stops a stale process from calling a separate database or provider. Keep consensus-service leadership, application job ownership and the database's replication election as separate boundaries. See [Consensus & Leader Election](../../30.2-system-design/01-theory/30.2.1.09-consensus-and-leader-election.md) for vote, term and log rules; handwritten vote-counting classes omit durable terms, log freshness and stale RPC handling.

## Choose a coordination primitive

| Primitive | Store permits another owner when | Operational boundary |
| ----------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| etcd lease-backed election | Lease expires or holder resigns | `LeaderKey.rev` can verify ownership inside etcd transactions; a downstream resource still needs fencing |
| ZooKeeper ephemeral sequential node | Session expires or node is deleted | Lowest sequence wins; watch the predecessor and fence external writes |
| PostgreSQL advisory lock | Owning transaction or session ends | Keep effects on the same primary; failover must fence the old primary, and the lock provides no epoch by itself |
| Database lease row | Database-clock expiry or explicit release | Conditional renewal plus a durable increasing epoch; fence the old primary on failover |
| Redis single-instance lease | TTL expires or matching token is released | Advisory coordination; failover or wall-clock shifts can allow overlapping owners |

For a fixed membership of `n` voters, a majority is `floor(n/2)+1`: three voters tolerate one unavailable voter, four still tolerate only one, and five tolerate two. A Raft leader isolated from a majority cannot commit new entries. A consensus service should therefore stop progress rather than grant ownership from a minority. Choose an already operated coordination service when possible; custom election code must implement its full durable protocol, not just count votes.

## A database lease and its fencing epoch

When the protected state already lives in PostgreSQL, a lease row can keep acquisition, renewal and the protected write under one authority. Keep one row per resource: deleting and recreating this example row would reset its epoch to 1. If rows must be removed, store the fencing sequence separately or rotate the resource namespace before work resumes.

`clock_timestamp()` makes contenders compare against the database server's current clock rather than their different local clocks. It is still wall-clock time, not a monotonic distributed clock; expiry controls when another owner may contend, while fencing protects the write. Run this against one authoritative primary and ensure the old primary cannot remain writable after failover.

```sql
CREATE TABLE leader_leases (
  name text PRIMARY KEY,
  owner text NOT NULL,
  epoch bigint NOT NULL,
  expires_at timestamptz NOT NULL
);

-- Claim only an expired lease. Each successful replacement increments epoch.
-- No returned row means another owner still holds the lease.
INSERT INTO leader_leases (name, owner, epoch, expires_at)
VALUES ('scheduler', 'node-a', 1, clock_timestamp() + interval '30 seconds')
ON CONFLICT (name) DO UPDATE
SET owner = EXCLUDED.owner,
    epoch = leader_leases.epoch + 1,
    expires_at = clock_timestamp() + interval '30 seconds'
WHERE leader_leases.expires_at <= clock_timestamp()
RETURNING owner, epoch, expires_at;

-- Renew only this acquisition, and never resurrect an expired lease.
UPDATE leader_leases
SET expires_at = clock_timestamp() + interval '30 seconds'
WHERE name = 'scheduler' AND owner = 'node-a' AND epoch = 1
  AND expires_at > clock_timestamp()
RETURNING epoch;
```

Compute replacement expiry after any conflict-row lock wait. The candidate INSERT timestamp can be old when `ON CONFLICT` obtains the existing row; reusing `EXCLUDED.expires_at` can grant a lease that has already expired. The update above starts a new interval from the database clock after the wait.

Keep the returned epoch with the acquisition. A process identifier alone is insufficient because the same process may lose and reacquire ownership. If renewal returns no row, or times out, stop starting work until authority is confirmed. Serialize renewals rather than running overlapping asynchronous `setInterval` callbacks.

### Reject stale writes at the resource

Store the highest accepted epoch beside the protected state. The write below allows repeated writes during epoch 42 but rejects an epoch below the value already observed.

```sql
CREATE TABLE scheduled_resources (
  id text PRIMARY KEY,
  value text NOT NULL,
  last_epoch bigint NOT NULL DEFAULT 0
);

-- Accept the active epoch, including repeated writes in the same term.
-- Bind :epoch, :value and :id as query parameters in application code.
INSERT INTO scheduled_resources (id, value, last_epoch)
VALUES (:id, :value, :epoch)
ON CONFLICT (id) DO UPDATE
SET value = EXCLUDED.value,
    last_epoch = EXCLUDED.last_epoch
WHERE scheduled_resources.last_epoch <= EXCLUDED.last_epoch
RETURNING id;
```

This fence rejects epoch 41 only after a write with 42 has advanced the resource. For an immediate current-owner check, lock the lease row, verify owner, epoch and expiry, and mutate the resource in the same short transaction. Acquisition and renewal must use that same row so a replacement cannot pass the check mid-write. Do not extend the transaction across a remote call: the database lock cannot fence an external provider. Keep the epoch issuer durable across restarts and restores; a worker-local counter starts over and provides no distributed ordering. A fencing epoch orders owners, not jobs within one owner's epoch.

The `<=` comparison lets one holder make several writes; a strict `<` comparison would reject its second write. Business-operation deduplication remains a separate key or uniqueness constraint. Never let caller-supplied payload overwrite the trusted epoch.

## Renew an advisory Redis lease atomically

For best-effort work coordinated by one Redis instance, acquire with `SET key token NX PX ttl`. Renew and release only if the stored token still matches. On Redis 8.4 or later, `DELEX key IFEQ token` releases conditionally; on older versions, use compare-and-delete Lua rather than bare `DEL`. A separate `GET` then `PEXPIRE` has a race: the old holder can extend a successor's key after its own token expires.

```typescript
import type Redis from 'ioredis';

// ioredis syntax. ownerToken is unique for this acquisition, not just nodeId.
async function renewLease(
  redis: Redis, key: string, ownerToken: string, ttlMs: number,
): Promise<boolean> {
  if (!Number.isSafeInteger(ttlMs) || ttlMs <= 0) throw new RangeError('ttlMs');
  const renewed = await redis.eval(`
    if redis.call('get', KEYS[1]) == ARGV[1] then
      return redis.call('pexpire', KEYS[1], ARGV[2])
    end
    return 0
  `, 1, key, ownerToken, ttlMs);
  return renewed === 1;
}
```

The Lua script makes renewal atomic for that Redis key; it does not make the lease a consensus-backed fence for another database. Redis documents that its TTL uses a wall clock and can be affected by clock shifts. Treat the single-instance pattern as advisory unless the protected resource independently enforces fencing or idempotency. This is not Redlock; see [Distributed Locks](../../30.2-system-design/01-theory/30.2.1.14-distributed-locks.md) for the multi-instance algorithm and its assumptions.

## Test the failure boundary

Test a stale holder, not only a dead process:

- Pause A past expiry, let B acquire a higher epoch, write with B, then resume A and assert that the resource rejects A.
- Repeat before B's first write. If A can still write, use a current-lease check serialized with the mutation when that violates the invariant.
- Lose a renewal response or the coordination quorum. The uncertain worker must stop starting work, and a minority must not grant a new owner.
- Restore the coordinator or fail over the database. Assert that the fencing sequence does not move backward and the old primary cannot accept writes.
- Lose the reply after an external provider accepts a job. Retry with a stable idempotency key or reconcile the outcome rather than trusting election state to prevent a duplicate.

Track renewal latency, ownership changes and rejected stale writes. They show whether short leases are causing false suspicion or whether stale work is reaching the resource.

## Summary

An election changes authority; it cannot stop a paused old process. Use a durable coordination primitive, renew only the current acquisition, and enforce authority where effects commit. Raft terms and Paxos proposal numbers order consensus decisions; leases expire by time; idempotency handles repeated business work. A fencing token works after the resource observes a newer token, so test both sides of that boundary.

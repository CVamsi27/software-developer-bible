# Database Scaling — Partitioning, Replication, Connection Pooling, Query Optimization

## First Principles

DB scaling follows a fixed order because each step buys different headroom:

1. **Vertical → read replicas → cache → shard, in that order.** Each earlier step is cheaper and less risky: replicas scale reads (→ 20.4.3.04), caching absorbs hot reads (→ 30.2.1.05), and sharding — the irreversible, cross-shard-transaction-creating step — comes only when the first three are exhausted.
2. **The shard key decision is the point of no return** (→ 30.2.1.03 axiom 3): everything before sharding is reversible; after, the data model is committed to the key's geometry.
3. **Scaling the DB is usually the wrong first move**: most "DB is slow" is N+1, missing indexes (→ 20.4.2.01), or cache-absent hot paths — application-level fixes precede infrastructure-level ones.

---

## Definition

**Database scaling** is the ordered ladder of techniques for making a database handle more load, where each rung buys capacity at a specific cost and the ladder is climbed **in order** because the cheap rungs are prerequisites for the expensive ones:

```text
rung                buys                 costs                         try first when
1 index + query    10–1000× on reads    write overhead, disk          any slow query exists
2 cache (read)     10–100× on reads     staleness, invalidation       read-heavy, hot keys
3 read replicas    read scale           replica lag, no write help    read:write ≫ 1
4 pooling/partition r/w throughput      ops complexity                connection saturation
5 sharding         write scale          cross-shard joins, rebalancing  single node maxed, writes
6 specialized store per access pattern  fit-for-purpose engine         one engine hurting both OLTP and search
```

Two constraints define the discipline. **Writes cannot be scaled by replicas** — replication multiplies read capacity and durability only, so a write-bound system must shard, partition, or move writes off the critical path (queues, batching). And **sharding is a one-way door for your data model**: the shard key becomes embedded in every query, and a bad key produces hot shards that no amount of hardware fixes. That is why the ladder is climbed in order — most "we need to shard" conclusions are really unfixed query plans, missing indexes, or an unpooled connection storm.

## Horizontal Scaling Strategies

### Vertical vs Horizontal
| Strategy | Pros | Cons | Use Case |
| -------------------------- | ----------------------- | -------------------------------------------- | ------------------- |
| **Vertical (Scale Up)** | Simple, no code changes | Limited by hardware, single point of failure | Small-medium apps |
| **Horizontal (Scale Out)** | Elastic, fault-tolerant | Complex, distributed systems challenges | Large-scale systems |

## PostgreSQL Partitioning

**Why partition?** When a table grows beyond millions of rows, queries slow down because PostgreSQL scans the entire table. Partitioning splits one logical table into smaller physical tables. Queries that filter by the partition key (e.g., date range) only scan the relevant partition, not the whole table. This is critical for time-series data like appointments — you almost always query by date range, so range partitioning on `scheduled_at` gives you 10-100x speedup on those queries.


### Range Partitioning (Time-Series Data)
```sql
-- Partition appointments by month
CREATE TABLE appointments (
  id UUID DEFAULT gen_random_uuid(),
  patient_id UUID NOT NULL,
  clinic_id UUID NOT NULL,
  scheduled_at TIMESTAMPTZ NOT NULL,
  status VARCHAR(20) DEFAULT 'scheduled',
  created_at TIMESTAMPTZ DEFAULT NOW()
) PARTITION BY RANGE (scheduled_at);

-- Create monthly partitions
CREATE TABLE appointments_2024_01 PARTITION OF appointments
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE appointments_2024_02 PARTITION OF appointments
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Auto-create partitions (using pg_partman)
CREATE EXTENSION pg_partman;
SELECT partman.create_parent('public.appointments', 'scheduled_at', 'native', 'monthly');
```

### Hash Partitioning (Distributed Data)
```sql
-- Partition by clinic_id for multi-tenant isolation
CREATE TABLE patient_records (
  id UUID DEFAULT gen_random_uuid(),
  clinic_id UUID NOT NULL,
  patient_id UUID NOT NULL,
  data JSONB NOT NULL
) PARTITION BY HASH (clinic_id);

-- Create 8 hash partitions
CREATE TABLE patient_records_p0 PARTITION OF patient_records
  FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE patient_records_p1 PARTITION OF patient_records
  FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ... up to p7
```

### List Partitioning (Categorical Data)
```sql
-- Partition by region for compliance
CREATE TABLE audit_logs (
  id UUID DEFAULT gen_random_uuid(),
  region VARCHAR(10) NOT NULL,
  event_type VARCHAR(50) NOT NULL,
  payload JSONB NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
) PARTITION BY LIST (region);

CREATE TABLE audit_logs_eu PARTITION OF audit_logs
  FOR VALUES IN ('EU', 'DE', 'FR', 'NL');
CREATE TABLE audit_logs_us PARTITION OF audit_logs
  FOR VALUES IN ('US', 'CA');
CREATE TABLE audit_logs_global PARTITION OF audit_logs
  FOR VALUES IN ('APAC', 'LATAM');
```

## Replication

**Why replicate?** Replication creates copies of your database on other servers. The primary handles writes, replicas handle reads. This gives you two benefits: (1) read scaling — distribute read queries across multiple replicas instead of hammering one server, and (2) fault tolerance — if the primary dies, a replica can be promoted to primary. For healthcare apps like Docita, replication also enables geographic distribution — EU patient data stays in EU replicas for GDPR compliance.


### Streaming Replication (Read Replicas)
```sql
-- Primary: Enable WAL replication
ALTER SYSTEM SET wal_level = 'replica';
ALTER SYSTEM SET max_wal_senders = 10;
ALTER SYSTEM SET wal_keep_size = '1GB';
SELECT pg_reload_conf();

-- Create replication user
CREATE USER replicator WITH REPLICATION LOGIN PASSWORD 'secure_password';

-- Replica: Configure recovery
primary_conninfo = 'host=primary port=5432 user=replicator password=secure_password'
```

### Logical Replication (Selective Replication)
```sql
-- Publisher (Primary)
ALTER SYSTEM SET wal_level = 'logical';
ALTER SYSTEM SET max_replication_slots = 10;
ALTER SYSTEM SET max_wal_senders = 10;

-- Create publication
CREATE PUBLICATION clinic_data FOR TABLE appointments, patients;

-- Subscriber (Replica)
CREATE SUBSCRIPTION clinic_data_sub
  CONNECTION 'host=primary dbname=docita user=replicator'
  PUBLICATION clinic_data;
```

## Connection Pooling

**Why pool connections?** Every PostgreSQL connection spawns a backend process using ~5-10MB of memory. With 500 app connections, that's 2.5-5GB just for connection overhead. PgBouncer sits between your app and PostgreSQL, maintaining a small pool of database connections (e.g., 20) that are shared across 1000+ app connections. The app thinks it has its own connection, but PgBouncer multiplexes them. This is essential — without pooling, you'll hit "too many connections" errors under load.


### PgBouncer Configuration
```ini
[databases]
docita = host=primary port=5432 dbname=docita

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt

# Pool settings
pool_mode = transaction # or session, statement
default_pool_size = 20
max_client_conn = 1000
min_pool_size = 5

# Timeouts
server_idle_timeout = 600
client_idle_timeout = 0
```

### Connection Pool in NestJS
```typescript
// Prisma with connection pooling
const prisma = new PrismaClient({
  datasources: {
    db: {
      url: process.env.DATABASE_URL + '?connection_limit=20&pool_timeout=10'
    }
  }
});

// Monitor connection pool
const poolMetrics = {
  active: await prisma.$queryRaw`SELECT count(*) FROM pg_stat_activity WHERE state = 'active'`,
  idle: await prisma.$queryRaw`SELECT count(*) FROM pg_stat_activity WHERE state = 'idle'`,
  waiting: await prisma.$queryRaw`SELECT count(*) FROM pg_stat_activity WHERE wait_event IS NOT NULL`
};
```

## Query Optimization

### Query Analysis
```sql
-- Enable query analysis
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT * FROM appointments
WHERE clinic_id = '123'
AND scheduled_at > NOW()
ORDER BY scheduled_at;

-- Identify slow queries
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;
```

### Index Optimization
```typescript
// Composite index for common query pattern
CREATE INDEX idx_appointments_clinic_scheduled
ON appointments (clinic_id, scheduled_at DESC);

// Partial index for active records
CREATE INDEX idx_appointments_active
ON appointments (clinic_id, scheduled_at)
WHERE status = 'scheduled';

// GIN index for JSONB queries
CREATE INDEX idx_patient_metadata_gin
ON patients USING GIN (metadata jsonb_path_ops);

// Covering index (INCLUDE)
CREATE INDEX idx_appointments_covering
ON appointments (clinic_id, scheduled_at)
INCLUDE (patient_id, status);
```

### Query Rewriting
```sql
-- Bad: Using OR prevents index usage
SELECT * FROM appointments
WHERE clinic_id = '123' OR patient_id = '456';

-- Good: Use UNION ALL with separate index scans
SELECT * FROM appointments WHERE clinic_id = '123'
UNION ALL
SELECT * FROM appointments WHERE patient_id = '456'
AND clinic_id != '123';

-- Bad: Using NOT IN with subquery
SELECT * FROM patients
WHERE id NOT IN (SELECT patient_id FROM appointments);

-- Good: Use NOT EXISTS or LEFT JOIN
SELECT p.* FROM patients p
WHERE NOT EXISTS (
  SELECT 1 FROM appointments a WHERE a.patient_id = p.id
);
```

## Performance Monitoring

### Key Metrics
```typescript
const dbMetrics = {
  // Connection pool
  connectionPool: {
    active: 'pg_stat_activity count WHERE state = \'active\'',
    idle: 'pg_stat_activity count WHERE state = \'idle\'',
    waiting: 'pg_stat_activity count WHERE wait_event IS NOT NULL'
  },

  // Query performance
  queryPerformance: {
    avgDuration: 'mean_exec_time from pg_stat_statements',
    slowQueries: 'queries with mean_exec_time > 1000ms',
    cacheHitRatio: 'sum(blks_hit) / (sum(blks_hit) + sum(blks_read))'
  },

  // Replication lag
  replicationLag: 'pg_stat_replication lag in seconds',

  // Disk usage
  diskUsage: 'pg_database_size(current_database())',
  tableBloat: 'pg_stat_user_tables n_dead_tup'
};
```

## Summary

1. **Scale in order: indexes → caching → read replicas → sharding** — each step is 10x the operational cost of the previous
2. **Vertical scaling is underrated** — a bigger box delays sharding by years and buys nothing but money
3. **Read replicas give read throughput, not failover safety** — replication lag is a product decision (stale reads)
4. **Shard by tenant or entity, not by hash-of-random** — co-location of related data is the whole game
5. **Resharding is the project you must design for before you need it** — consistent hashing + dual-write backfills

# Data Pipelines — ETL, Stream Processing, Data Lake

A change-data-capture worker writes an appointment projection, then crashes before acknowledging the source event. On restart, the event arrives again. A versioned upsert can make that retry safe when the event carries a complete after-image; an additive event needs a different rule. That crash boundary is part of the pipeline's delivery contract:

```text
crash after write, before ack → replay; versioned upsert absorbs it, blind counters don't.
```

## Definition

A **data pipeline** moves data through ingestion, transformation, and delivery stages so another system can use it. The destination might serve reports, search, alerts, or operational integration. The **contract** includes schema, latency, ordering, loss/duplicates, and supported reprocessing.

> **Textbook Definition:** A data pipeline is a sequence of ingestion, transformation and delivery stages that transfers data between systems under specified schema, ordering, latency and recovery contracts.

## First Principles

Every handoff creates a failure boundary. If output commits before source progress, a crash can repeat work; if progress advances first, output can be lost. Replaying later can also produce different results if the input snapshot or transformation version changed.

Latency requirements determine how soon work must become useful; ordering and correction requirements determine which state is meaningful. A watermark or retained log helps only under a chosen contract. Not every pipeline needs streaming, immutable history, or identical deterministic replay, and deletion or privacy policy can limit how long inputs are retained.

## How It Works

### 1. Place stages around retained input and committed output

```text
transactional source → snapshot/log ingestion → validated transform
                            │                        │
                            └→ retained/quarantined input
                                                     ▼
                                 committed destination + progress evidence
                                                     ▼
                                            search/report/alert consumer
```

**Extract, Transform, Load (ETL)** transforms records before writing them to the destination. **Extract, Load, Transform (ELT)** loads them first and transforms them there. These names describe where compute runs, not a required cadence or schema policy; either approach can validate data and run in batches or continuously. **Change data capture (CDC)** captures changes made to source data and publishes them downstream. Log-based CDC reads a source transaction log; polling-based CDC detects changes with queries. A consistent snapshot plus CDC from the same change-log boundary captures existing rows and later updates, but extraction queries and log capture still consume source resources and must be measured. Monitor retained log positions: a PostgreSQL replication slot can retain WAL until its consumer catches up and fill disk; a retention cap bounds growth but can invalidate an overdue slot, requiring a new snapshot ([slot monitoring details](https://www.postgresql.org/docs/current/view-pg-replication-slots.html)).

### 2. Choose processing from the consumer's contract

| Choice | What it buys | Cost or boundary |
| ---------------------------- | ---------------------------------------- | ----------------------------------------------------------- |
| Periodic batch | Bounded dataset/run, efficient bulk work | Freshness waits for scheduling and completion |
| Continuous/stream processing | React to arriving records quickly | Checkpoints, state, ordering and late corrections need care |
| Lambda design | Separate batch history and stream view | Duplicate logic and reconciling their answers |
| Kappa design | One log/stream path including replay | Input retention, replay capacity and state rebuild must fit |

These are design choices; no rule says most production systems must use a Lambda-style dual path or that batch must take hours. A small frequent batch can meet a modest freshness target without a streaming platform. In Kafka-like logs, records are ordered within a partition, not across the whole topic. Key by entity and preserve sequential application at the consumer when that entity needs ordered processing.

### 3. Project versioned after-images, aggregate deltas differently

Suppose source appointments emit **complete after-images**: each event contains the full current state and a monotonically increasing version for that appointment. An update at version 8 supersedes version 7. A deletion becomes a versioned tombstone, a retained deletion marker preventing an older replay from recreating the row. The destination retains the highest accepted version rather than incrementing a count per arrival.

The following complete PostgreSQL upsert model demonstrates that projection rule. It assumes trusted tenant/source identity and a producer never reusing a version for conflicting contents. It implements no broker checkpoints or source extraction job:

```sql
CREATE TABLE appointment_projection (
  tenant_id uuid NOT NULL,
  appointment_id uuid NOT NULL,
  source_version bigint NOT NULL CHECK (source_version >= 0),
  status text NOT NULL,
  deleted boolean NOT NULL,
  PRIMARY KEY (tenant_id, appointment_id)
);

-- Driver binds validated tenant, appointment, version, status and deletion values.
INSERT INTO appointment_projection
  (tenant_id, appointment_id, source_version, status, deleted)
VALUES ($1::uuid, $2::uuid, $3::bigint, $4::text, $5::boolean)
ON CONFLICT (tenant_id, appointment_id) DO UPDATE
SET source_version = EXCLUDED.source_version,
    status = EXCLUDED.status, deleted = EXCLUDED.deleted
WHERE appointment_projection.source_version < EXCLUDED.source_version;
```

Repeated version 8 never applies again; delayed version 7 cannot overwrite 8. Version 9 can mark the appointment deleted. Removing the tombstone while old version 7 is still replayable would permit resurrection. Equal-version conflicting payloads need a validation/quarantine policy; this upsert alone ignores them rather than proving they agree.

This rule fits full state images. A delta such as "add one appointment" cannot discard older arrivals with the same rule: it needs event deduplication and an aggregation or ordering contract. Joins also need the corresponding versions of referenced data, not an assumption that replay sees the current reference table.

### 4. Commit progress with the output it describes

For a database destination, one transaction can apply output and update the authoritative checkpoint for a source partition, an independently ordered slice of the input log. On restart, resume from the next input position corresponding to that committed output. A crash before commit repeats the input; a crash after commit can consult the durable checkpoint.

When output and source progress use separate systems, their commit order determines the failure mode. Commit output first and a crash can cause the source to redeliver it: this is at-least-once delivery, so make the effect idempotent. Advance source progress first and a crash can lose the output: this is at-most-once. "Exactly once" is scoped to an atomic boundary; deduplication can make repeated deliveries produce one logical effect, but the label alone never makes unrelated systems atomic.

The checkpoint needs a single owner or generation fence so an old worker cannot overwrite a newer worker's progress. "Store the maximum offset" never makes skipped work safe: all earlier records required by that checkpoint must have reached the committed boundary.

Kafka transactions can atomically cover consumed offsets and produced Kafka records within Kafka. They never include a PostgreSQL mutation, object upload, or email. For a database sink, commit the projection and checkpoint together in the database, then allow source redelivery until its offset catches up; the sink must tolerate that replay. If retained broker history expires before recovery, a checkpoint alone cannot reconstruct missing input. See [Kafka Streams' transaction boundary](https://kafka.apache.org/43/streams/core-concepts/) for the guarantee within Kafka. See [Transactional Outbox & Change Data Capture (CDC)](../../30.2-system-design/01-theory/30.2.1.18-outbox-and-cdc.md) for source transaction/publication boundaries and [Idempotency Keys](../02-failure-and-recovery/30.3.2.03-idempotency-keys.md) for atomic local claim/effect handling.

### 5. Extract windows and handle late data explicitly

A daily extraction normally uses a half-open interval `[dayStart, nextDayStart)` in an explicitly selected business timezone. "Today at 2 AM" is not yesterday's complete data, and daylight-saving days need not last 24 hours.

Page using a stable cursor/order with a snapshot or change boundary. Offset pagination against changing rows can skip/repeat records; fetching the entire day and slicing the resulting array never bounds memory. Bound batch size, concurrent writes, and pending work, and record failed batches instead of announcing full success after swallowing their errors.

A scheduled job can overlap its next run or execute on multiple instances. Use the scheduler/coordination contract and a run identity; a cron expression is no distributed exclusion. Source corrections may require a later rerun of the same business interval.

**Event time** is when the represented event occurred; **processing time** is when the pipeline handles it. A five-minute tumbling window groups events into fixed, non-overlapping intervals. A sliding window overlaps, so one event can contribute to several windows.

A **watermark** is the pipeline's estimate of how complete event time is for a window; it is no proof that no older event can arrive. Define allowed lateness, idle-partition handling, and what happens to later arrivals: update or retract an answer, write a correction, quarantine, or drop under an explicit policy. The [Apache Beam programming guide](https://beam.apache.org/documentation/programming-guide/#watermarks-and-late-data) describes watermarks and late-data handling in a concrete runner model.

For example, an event for 10:04 reaches the pipeline at 10:12 after the 10:00–10:05 result was published. If corrections are supported, issue a versioned corrected result and have downstream consumers replace the prior result. Adding it to an unrelated current window hides the late event rather than fixing history.

Checkpoint window state and progress consistently; bound retained state after the allowed correction horizon. A map collecting events indefinitely until undefined `isWindowComplete()` succeeds supplies neither a memory bound nor a recovery contract.

### 6. Layer storage, measure quality, and backfill safely

Bronze/raw, silver/validated, and gold/serving name responsibilities, not mandatory formats or retention periods. Parquet is a columnar file format. A transaction-log table format such as Delta adds a commit protocol and snapshot metadata so readers can identify a consistent table version; capabilities depend on that format's protocol. Writing files under a folder named `_delta_log` never implements that protocol.

Retain original input and transformation/schema versions when recovery policy permits it. Validate types and cross-field/business constraints, quarantine failures with safe diagnostics, and avoid dumping entire patient records into error logs. A schema registry stores schema versions and can check configured compatibility rules; it never proves business meaning or fixes every old consumer.

Measure different dimensions separately:

| Dimension | Useful evidence |
| ------------ | ------------------------------------------------------------------------------------- |
| Completeness | Expected required fields/records and reconciled source totals |
| Validity | Values match schema/ranges/business constraints |
| Accuracy | Values match authoritative reality, beyond merely passing a range check |
| Freshness | Consumer-relevant source positions/time coverage, including quiet or stuck partitions |
| Uniqueness | Duplicate identity rate under the event/entity contract |
| Reliability | Failed/quarantined runs, backlog age, replay capacity and recoverable checkpoints |

One recent record never proves all partitions are fresh. Use dimension-specific units, denominators, and objectives; comparing every metric to 0.95 is meaningless when one is seconds or a count. Distinguish a successful scheduler invocation from complete delivered data.

Pin the input period, transformation version, and destination namespace for a backfill. For a live source, record a snapshot/change-log boundary, copy a consistent snapshot, then replay changes after that boundary until the new destination catches up. This closes the gap where a row changes during the initial copy. Bound replay so it never starves the source or live path; compare counts and business invariants before publishing through a defined version or ownership boundary.

A new transformation may intentionally change output for an old event. Permanent "already processed" markers keyed only by original ID would suppress that correction. Include run or transform identity where needed and use a controlled replacement strategy.

## Summary

A pipeline makes useful copies under a latency, ordering and recovery contract. Define input identity, transformation version and committed progress together; apply snapshot images differently from deltas. Bound extraction/state/backfill work, handle late corrections explicitly, and measure complete source coverage rather than only job success or one recent record.

# Data Pipelines — ETL, Stream Processing, Data Lake


---

## Definition

A **data pipeline** moves data through ingestion, transformation and delivery stages so another system can use it. The destination might serve reports, search, alerts or operational integration. The contract includes schema, latency, ordering, loss/duplicates and supported reprocessing.

> **Textbook Definition:** A data pipeline is a sequence of ingestion, transformation and delivery stages that transfers data between systems under specified schema, ordering, latency and recovery contracts.

## First Principles

Sources change while copies are being read. A destination may commit output before the source position is recorded, or record a position before output commits. The first crash gap repeats work; the second loses work. Source data and transformation rules also change over time, so repeating a run needs an explicit input snapshot and rule version.

Latency requirements determine how soon work must become useful; ordering and correction requirements determine which state is meaningful. A watermark or log is useful under a chosen contract, but not every pipeline needs streaming, immutable history or identical deterministic replay. Required deletion and privacy policies can limit retained inputs.

## Put the Stages in the Whole System

```text
transactional source → snapshot/log ingestion → validated transform
                            │                        │
                            └→ retained/quarantined input
                                                     ▼
                                 committed destination + progress evidence
                                                     ▼
                                            search/report/alert consumer
```

**ETL** means extract, transform, then load into the destination; **ELT** loads first and transforms there. This describes compute placement, not a mandatory cadence or schema policy. Either can use validation and batch/continuous execution. Extracting analytics work can protect a transactional database, but extraction queries/CDC still impose source work that must be measured.

## Choose Processing From the Consumer's Contract

| Choice | What it buys | Cost or boundary |
| ---------------------------- | ---------------------------------------- | ----------------------------------------------------------- |
| Periodic batch | Bounded dataset/run, efficient bulk work | Freshness waits for scheduling and completion |
| Continuous/stream processing | React to arriving records quickly | Checkpoints, state, ordering and late corrections need care |
| Lambda design | Separate batch history and stream view | Duplicate logic and reconciling their answers |
| Kappa design | One log/stream path including replay | Input retention, replay capacity and state rebuild must fit |

These are design choices; there is no established rule that most production systems are lambda-like or that batch must take hours. A small frequent batch can meet a modest freshness target without a streaming platform.

## Trace a Replayable Appointment Projection

Suppose source appointments emit **complete after-images** with a monotonically increasing version per appointment. An update at version 8 supersedes version 7; a deletion becomes a versioned tombstone. The destination retains the highest accepted version, rather than incrementing a count for every arrival.

The following complete PostgreSQL upsert model demonstrates that projection rule. It assumes trusted tenant/source identity and a producer that never reuses a version for conflicting contents. It does not implement broker checkpoints or a source extraction job.

```sql
CREATE TABLE appointment_projection (
  tenant_id uuid NOT NULL,
  appointment_id uuid NOT NULL,
  source_version bigint NOT NULL CHECK (source_version >= 0),
  status text NOT NULL,
  deleted boolean NOT NULL,
  PRIMARY KEY (tenant_id, appointment_id)
);

-- Example after-image at source version 8; driver binds real validated values.
INSERT INTO appointment_projection
  (tenant_id, appointment_id, source_version, status, deleted)
VALUES ('00000000-0000-0000-0000-000000000001',
        '00000000-0000-0000-0000-000000000002', 8, 'confirmed', false)
ON CONFLICT (tenant_id, appointment_id) DO UPDATE
SET source_version = EXCLUDED.source_version,
    status = EXCLUDED.status, deleted = EXCLUDED.deleted
WHERE appointment_projection.source_version < EXCLUDED.source_version;
```

Repeated version 8 does not apply again; delayed version 7 cannot overwrite 8. Version 9 can mark the appointment deleted. Removing the tombstone while old version 7 is still replayable would permit resurrection. Equal-version conflicting payloads need a validation/quarantine policy; this upsert alone ignores them rather than proving they agree.

This rule fits full state images. A delta such as “add one appointment” cannot discard older arrivals using the same rule: it needs event deduplication and an aggregation/ordering contract. Joins also need the corresponding versions of referenced data, not an assumption that replay sees the current reference table.

## Commit Progress With the Output It Describes

For a database destination, one transaction can apply selected output and update that pipeline partition's authoritative checkpoint. On restart, resume from the next input position corresponding to that committed output. A crash before commit repeats the input; a crash after commit can consult the durable checkpoint.

The checkpoint needs a single owner or generation fence so an old worker cannot overwrite a newer worker's progress. “Store the maximum offset” does not make skipped work safe: all earlier records required by that checkpoint must have reached the committed boundary.

Kafka transactions can cover consumed offsets and produced Kafka records. They do not automatically include a PostgreSQL mutation, object upload or email. If a database is authoritative, broker acknowledgments may lag its local checkpoint; redelivery must be harmless. If retained broker history expires before recovery/replay, that checkpoint alone cannot reconstruct missing input.

See [Transactional Outbox & CDC](../../30.2-system-design/01-theory/30.2.1.18-outbox-and-cdc.md) for source transaction/publication boundaries and [Idempotency Keys](../02-failure-and-recovery/30.3.2.03-idempotency-keys.md) for atomic local claim/effect handling.

## Extract a Window Without Loading Everything

A daily extraction normally uses a half-open interval `[dayStart, nextDayStart)` in an explicitly selected business timezone. “Today at 2 AM” is not yesterday's complete data, and daylight-saving days need not last 24 hours.

Page using a stable cursor/order with a snapshot or change boundary. Offset pagination against changing rows can skip/repeat records; fetching the entire day and slicing the resulting array does not bound memory. Bound batch size, concurrent writes and pending work, and record failed batches instead of announcing full success after swallowing their errors.

A scheduled job can overlap its next run or execute on multiple instances. Use the scheduler/coordination contract and a run identity; a cron expression is not distributed exclusion. Source corrections may require a later rerun of the same business interval.

## Event Time, Windows and Late Data

**Event time** is when the represented event occurred; **processing time** is when the pipeline handles it. A five-minute bucket keyed by `floor(timestamp / fiveMinutes)` is a tumbling window, not a sliding window. A sliding window overlaps and can assign one record to several windows.

A **watermark** expresses the pipeline's estimate/progress boundary for event time under its source policy. It is not proof that no older event can arrive. Define allowed lateness, idle-partition handling and what happens to later arrivals: update/retract an answer, write a correction, quarantine, or drop under an explicit policy.

For example, an event for 10:04 reaches the pipeline at 10:12 after the 10:00–10:05 result was published. If corrections are supported, issue a versioned corrected result and have downstream consumers replace the prior result. Adding it to an unrelated current window hides the late event rather than fixing history.

Checkpoint window state and progress consistently; bound retained state after the allowed correction horizon. A map that collects events indefinitely until undefined `isWindowComplete()` succeeds supplies neither a memory bound nor a recovery contract.

## Storage Layers and Data Quality

Bronze/raw, silver/validated and gold/serving are names for responsibilities, not mandatory formats or retention periods. Parquet is a file format; a transaction-log table format adds different metadata/commit semantics. Writing files under a folder named `_delta_log` does not create a valid transactional table.

Retain original input and transformation/schema versions when recovery policy permits it. Validate types and cross-field/business constraints, quarantine failures with safe diagnostics, and avoid dumping entire patient records into error logs. A schema registry can check configured compatibility; it does not prove business meaning or fix all old consumers.

Measure different dimensions separately:

| Dimension | Useful evidence |
| ------------ | ------------------------------------------------------------------------------------- |
| Completeness | Expected required fields/records and reconciled source totals |
| Validity | Values match schema/ranges/business constraints |
| Accuracy | Values match authoritative reality, beyond merely passing a range check |
| Freshness | Consumer-relevant source positions/time coverage, including quiet or stuck partitions |
| Uniqueness | Duplicate identity rate under the event/entity contract |
| Reliability | Failed/quarantined runs, backlog age, replay capacity and recoverable checkpoints |

One recent record does not prove all partitions are fresh. Use dimension-specific units, denominators and objectives; comparing every metric to 0.95 is meaningless when one is seconds or a count. Distinguish a successful scheduler invocation from complete delivered data.

## Backfill Without Racing Live Processing

Pin the input period, transformation version and destination namespace. Bound extraction/replay so it does not starve the source or live path. Compare counts/business totals, then publish or merge the new result through a defined version/ownership boundary.

A new transformation may intentionally change output for an old event. Permanent “already processed” markers keyed only by original ID would suppress that correction. Include run/transform identity where needed and use a controlled replacement strategy. Snapshot/high-watermark capture must also close the gap between initial copy and concurrent changes.

## Summary

A pipeline makes useful copies under a latency, ordering and recovery contract. Define input identity, transformation version and committed progress together; apply snapshot images differently from deltas. Bound extraction/state/backfill work, handle late corrections explicitly, and measure complete source coverage rather than only job success or one recent record.

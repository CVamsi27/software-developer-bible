# CDN Architecture — Edge Caching, Geographic Distribution, Cache Invalidation


---

## Definition

A **content delivery network (CDN)** places a delivery layer between clients and the origin. Eligible shared responses can be served from distributed caches; other requests are forwarded or processed under edge routing and security policy. An edge location is a serving site, often called a point of presence (PoP).

> **Textbook Definition:** A CDN is a distributed delivery layer that serves eligible content from edge locations and forwards misses or dynamic requests to origins according to routing, authorization and cache policies.

## First Principles

Distance limits round-trip time, and a finite origin cannot repeatedly generate every popular response without capacity cost. Copies reduce that repeated work only when they represent the same authorized response for multiple callers. Copies also outlive origin changes, so their identity, freshness and access boundaries must be explicit.

Routing chooses which path reaches the response; authorization decides who may receive it; storage identity decides which bytes can be reused. Treating these as one path-prefix rule creates leaks and stale decisions. A cache key cannot establish authorization by itself.

## Place the CDN in the Request Path

```text
client → selected edge → access/routing policy → shared cache lookup
                                                  │ hit → response
                                                  │ miss
                                                  ▼
                                      optional cache tier/shield → origin
```

The network-selected edge is not guaranteed to be geographically nearest or fastest for a particular user. A cache hit still involves connection, edge and transfer work; it is not universally a microsecond response. Tiering can satisfy an edge miss from another cache, so not every PoP miss becomes an origin request.

**Origin shielding** consolidates traffic through an intermediate cache; **request coalescing** lets concurrent compatible misses share one fill. These mechanisms can reduce origin bursts when correctly configured, but different keys, tiers, regions and failures still generate multiple requests. They need bounds for waiters, timeouts and errors.

## Design the Cache Contract From Response Classes

| Response class | Typical architectural decision | Required condition |
| -------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------- |
| Content-hashed application asset | Long-lived immutable copy | Publish asset before referencing it; retain assets for old clients |
| Deployment HTML/bootstrap | Short freshness or validation | Old and new HTML/assets/API combinations remain compatible |
| Public catalog | Shared key and declared stale allowance | No caller-private fields or authorization decision hidden in “public” route |
| Patient/account response | Bypass shared storage under the chosen data policy | Correct response headers plus provider rules/edge code/telemetry controls |
| Protected media | Verify access for every delivery, including cache hits | Internal byte reuse cannot bypass current access checks |
| Health/readiness endpoint | Fresh controller-specific response | Caching a formerly healthy response must not conceal current readiness |

Do not infer these classes only from URL prefixes. `/api/config` can contain secrets or user-specific entitlements; a public clinic URL can return a personalized field. Cookies, authorization, locale, compression and negotiated media variants need either bypass or matching key/response policy.

A key with **too many** irrelevant variations fragments reuse; a key with **too few** required variations merges different responses. Cache poisoning occurs when attacker-controlled input changes a cached response without a corresponding key/trust boundary. It is different from ordinary sharing of a user-private response, although both can leak or corrupt content.

## Freshness Is Independent of Removing a Copy

`no-cache` permits storage but requires validation before reuse under the protocol. `no-store` requests no storage in relevant caches; it does not encrypt the request, erase earlier copies or control logs. Provider configuration and custom cache APIs can change effective behavior and need verification.

A time-to-live bounds reuse under the selected freshness policy; it does not ensure the origin's own data was current at fill time. `stale-while-revalidate` permits specified stale reuse during refresh; it does not make a mutable price or permission current. Provider support, stale windows and error policies determine what a client sees.

A content-hashed URL names new bytes. It does not purge old bytes, change cached HTML or force old tabs to update. Cache tags/surrogate keys identify groups to invalidate under provider APIs; they are **not** versioned URLs and do not make invalidation an instant global transaction.

## Trace Deployment A to B

1. Upload B assets under new content identities. Verify they are available before publishing B HTML.
2. Publish B HTML under its freshness/validation policy. Cached A HTML can still reference A assets.
3. Retain A assets and an API compatible with active A clients for the declared support window.
4. A submitted purge is tracked through provider completion and observed responses. Browser copies and another CDN remain independent.
5. Rollback must select compatible HTML/assets/API/data together; deleting B assets immediately can break a B tab that already opened.

## Routing and Edge Compute Add Trust Boundaries

An origin sees traffic from the edge, so define which forwarded identity/host/scheme headers it trusts. Shared CDN source addresses alone do not establish that a request belongs to your distribution or tenant. Prevent direct-origin bypass where the access contract requires edge enforcement.

Edge logic can select variants or upstreams, but must preserve intended path/query/body/header semantics and allowed origin destinations. IP-based random assignment is not a stable user experiment. Geolocation is not proof of a person's identity, tenant authority or permitted data residency.

Client-routing geography also does not constrain storage in the origin, backups, logs, analytics or provider control plane. Sensitive data can transit an edge even when it is not cached. Determine the actual processing, contractual and legal obligations instead of inferring compliance from `no-store`, a POST method or a private header.

## Prove Both Warm and Cold Paths

| Evidence | Why it matters |
| ------------------------------------------ | ----------------------------------------------------------------------------- |
| Request hit ratio by route/class | Identifies reuse, while overall ratio can hide an unsafe route |
| Byte hit ratio and transfer volume | Large objects dominate cost/bandwidth differently from tiny requests |
| Miss rate, coalescing and origin load | Tests capacity when caches expire, evict or are cold |
| Client-visible latency/errors by geography | Includes network and transfer, not only server timing |
| Key/authorization probes | Two identities, variants and credential states must receive the correct bytes |
| Purge/deploy propagation observations | Acceptance and convergence are separate evidence |

Hit ratio does not directly compute cost savings: include provider request, delivery, storage, origin transfer/compute and plan terms. A high ratio can still be wrong if private content was shared. A warm-cache load test cannot establish survival during cold failover or a global invalidation.

## Summary

A CDN reduces distance and repeated origin work when response identity and access contracts permit reuse. Separate routing, authorization, storage and freshness; versioned names and purge APIs solve different problems. Validate both cached and forwarded paths, including old clients, cold origins, provider rules and sensitive-data processing boundaries.

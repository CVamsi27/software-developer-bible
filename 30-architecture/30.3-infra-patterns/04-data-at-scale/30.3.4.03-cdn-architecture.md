# CDN Architecture — Edge Caching, Geographic Distribution, Cache Invalidation

Two signed-in patients request `/profile`. If a cache keys only on the path, the second request can receive the first patient's data. A content-hashed JavaScript file can safely be reused by both. Whether two requests may share a response is the central decision in CDN architecture.

---

## Definition

A **content delivery network (CDN)** places a delivery layer between clients and the origin. It can serve an eligible stored response from an edge location, a provider site that receives requests along a network-selected path. Edge locations are often called points of presence (PoPs). Requests that cannot use a stored response continue through the configured route to the origin.

> **Textbook Definition:** A CDN is a distributed request-routing and caching system that serves reusable representations from edge locations and forwards cache misses or non-cacheable requests to origins under defined access and freshness policies.

## First Principles

Reusing a response can reduce transfer distance and repeated origin work, but it is safe only when the next request selects the same representation and its caller is allowed to receive it. A stored copy can outlive an origin change, so identity, authorization and freshness are separate decisions.

Routing chooses the path, authorization grants access, and the cache key selects a stored representation. One rule cannot stand in for the others: a key can separate variants, but it cannot prove that a caller is authorized.

## Follow a Request Through the CDN

```text
client → provider-selected edge → routing and access policy
                                      │
                              eligible shared cache lookup
                                ├─ hit → response
                                └─ miss or bypass → optional shield → origin
```

The provider-selected edge is not guaranteed to be the geographically nearest or fastest one. Even a hit still requires network, lookup and transfer work. A cache tier can satisfy an edge miss before it reaches the origin, so not every point-of-presence miss becomes an origin request.

An **origin shield** is an intermediate cache that consolidates eligible misses before they reach the origin. **Request coalescing** lets concurrent misses for the same reusable response share one fill. Both can reduce origin bursts, but different keys, regions, cache tiers, retries and failures still generate requests. Bound waiting requests and define timeout and error behavior.

## Decide Which Requests Can Share a Response

A **cache key** is the request identity a cache uses to select a stored response. HTTP caching uses at least the request method and target URI; a CDN can add selected query values, headers or cookies. If any input changes the response, include it in the identity or bypass shared caching. Too few key fields merge different responses; too many irrelevant fields fragment reuse.

For `/profile`, a path-only key ignores the signed-in identity. For a versioned public asset, the URL can identify the same immutable bytes for every caller. Keep authorization separate. For revocable content, evaluate access on every delivery, including a hit. Enforce it at the edge with credentials and policy state whose revocation delay meets the product requirement, or consult an authorization service before releasing cached bytes. If a required check is unavailable, deny delivery by default. An explicit bounded offline-access policy is a deliberate exception; a cached object or stale authorization result alone never grants access.

| Response class | Typical architectural decision | Required condition |
| -------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Content-hashed application asset | Long-lived immutable copy | Publish asset before referencing it; retain assets for old clients |
| Deployment HTML/bootstrap | Short freshness or validation | Old and new HTML/assets/API combinations remain compatible |
| Public catalog | Shared key and declared stale allowance | No caller-private fields or authorization decision hidden in “public” route |
| Patient/account response | Bypass shared storage under the chosen data policy | Verify response headers, provider rules, edge code and telemetry paths |
| Protected media | Enforce authorization for every delivery, including cache hits | Define credential validation, revocation delay and authorization-service failure behavior |
| Health/readiness endpoint | Bypass caching and evaluate current state | A formerly healthy response must not conceal current readiness |

Do not infer these classes from URL prefixes. `/api/config` can contain secrets or user-specific entitlements; a public clinic route can still return a personalized field. Cookies, authorization, locale, content encoding and media negotiation need either bypass or a matching key and response policy.

Cache poisoning occurs when untrusted input changes a response that is stored without a matching key or trust boundary. That is different from correctly caching a private response under the wrong sharing policy, although both can leak or corrupt content.

## Set Freshness and Recovery Separately

Freshness answers when a stored response may be reused; invalidation removes a stored copy. A **time-to-live (TTL)** sets how long the response may be considered fresh under the selected policy. `no-cache` permits storage but requires revalidation with the origin before reuse under HTTP rules. `no-store` directs compliant caches not to store the response; it does not encrypt the request, erase earlier copies or control logs. Provider rules and custom cache APIs can change effective behavior, so verify the deployed configuration.

A fresh copy does not prove the origin data was current when the cache filled it. `stale-while-revalidate` permits configured stale reuse while the cache revalidates with the origin in the background; `stale-if-error` can permit it after defined upstream errors such as 500, 502, 503 or 504. These separate extensions do not guarantee current data or permission. Ordinary stale-content behavior cannot replace an access decision; any offline-access exception needs its own bounded authorization policy. Price and reservation outcomes need their authoritative transaction. Provider support, stale windows and error behavior determine what a client sees. See [RFC 5861](https://www.rfc-editor.org/rfc/rfc5861.html) for the extension contract.

A content-hashed URL names new bytes; it does not purge old bytes, update cached HTML or force open tabs to refresh. Cache tags or surrogate keys identify groups to invalidate through provider APIs. They are not versioned URLs and do not make invalidation an instant global transaction.

### Release a new version without breaking old clients

1. Upload B assets under new content identities. Verify they are available before publishing B HTML.
2. Publish B HTML under its freshness/validation policy. Cached A HTML can still reference A assets.
3. Retain A assets and an API compatible with active A clients for the declared support window.
4. Track purge completion and observe responses. Browser copies and another CDN remain independent.
5. Rollback must select compatible HTML/assets/API/data together; deleting B assets immediately can break a B tab that already opened.

## Keep Edge Routing Inside the Trust Boundary

The origin sees the edge's connection, so define which forwarded identity, host and scheme headers it trusts. Shared CDN source addresses alone do not prove that a request belongs to your distribution or tenant. Prevent direct-origin bypass when the security design depends on edge enforcement.

Edge logic can select variants or upstreams, but must preserve path, query, body and header semantics and restrict allowed origin destinations. An IP-address hash is not a stable user identity across shared networks or changing addresses; assignment and cache identity must agree for an experiment. Geolocation does not prove identity, tenant authority or permitted data residency.

Routing users through a region does not constrain where the origin, backups, logs, analytics or provider control plane process or store data. Sensitive data can transit an edge even when it is not cached. Determine the actual data flow and applicable contractual or legal obligations; `no-store`, POST and a private header do not establish compliance or residency.

## Measure Warm and Cold Behavior

| Evidence | Why it matters |
| ------------------------------------------ | ----------------------------------------------------------------------------- |
| Request hit ratio by route/class | Identifies reuse, while overall ratio can hide an unsafe route |
| Byte hit ratio and transfer volume | Large objects dominate cost/bandwidth differently from tiny requests |
| Miss rate, coalescing and origin load | Tests capacity when caches expire, evict or are cold |
| Client-visible latency/errors by geography | Includes network and transfer, not only server timing |
| Key/authorization probes | Two identities, variants and credential states must receive the correct bytes |
| Purge/deploy propagation observations | Acceptance and convergence are separate evidence |

Hit ratio does not directly calculate savings. Include provider requests, delivery, storage, origin transfer and compute, plus plan terms. A high ratio can still be wrong if private content was shared. A warm-cache load test cannot establish behavior during cold failover or broad invalidation.

## Summary

A CDN reduces distance and repeated origin work when response identity and access contracts permit reuse. Separate routing, authorization, storage and freshness; versioned names and purge APIs solve different problems. Validate both cached and forwarded paths, including old clients, cold origins, provider rules and sensitive-data processing boundaries.

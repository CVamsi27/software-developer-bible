# Multi-Tenant SaaS Architecture

> **TL;DR:** Multi-tenancy is how one deployment serves many customers (tenants) with isolated data and configurable behavior. The three models — shared database/shared schema, shared database/separate schemas, and separate databases — trade isolation for cost. The senior test is tenant context propagation: every query, job, and cache entry must carry the tenant ID, and every access decision must check it.
>
> **Why it matters:** This is a Backend / Architecture interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Multi-tenancy is an architecture where a single instance of an application serves multiple tenants (customers, organizations, clinics), each with their own data that is logically isolated from other tenants. Unlike single-tenant deployments where each customer gets their own infrastructure, multi-tenant SaaS shares compute and often database resources while guaranteeing data isolation.

**Key terms:**
- **Tenant** — a customer organization (e.g., a clinic, a company)
- **Tenant context** — the request-scoped identity carrying `tenantId` through every layer
- **Data isolation** — guaranteeing tenant A never sees tenant B's data
- **Noise neighbors** — one tenant's load degrading another's experience

## Why Do We Need It?

1. **Cost efficiency** — shared infrastructure amortizes cost across tenants
2. **Operational simplicity** — one deployment, one schema, one set of migrations
3. **Scalability** — horizontal scaling serves all tenants automatically
4. **Feature velocity** — ship once, every tenant gets it
5. **Compliance** — healthcare (HIPAA), finance (SOC2) require provable data isolation

## How It Works

### The Three Tenancy Models

```text
┌──────────────────────────────────────────────────────────────────────┐
│ MODEL 1: Shared DB, Shared Schema (Row-Level)                        │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  Tenant A ──┐                                                        │
│  Tenant B ──┼──> Single Database ──> Single Schema ──> tenant_id     │
│  Tenant C ──┘    (PostgreSQL)         (one set of tables)  column    │
│                                                                      │
│  Isolation: WHERE tenant_id = ? (application-level or RLS)           │
│  Cost:      Lowest  |  Complexity: Medium  |  Isolation: Logical     │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│ MODEL 2: Shared DB, Separate Schemas                                 │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  Tenant A ──> schema_tenant_a.users                                  │
│  Tenant B ──> schema_tenant_b.users    (same DB, different schemas)  │
│  Tenant C ──> schema_tenant_c.users                                  │
│                                                                      │
│  Isolation: Schema-level (SET search_path)                           │
│  Cost:      Medium   |  Complexity: High  |  Isolation: Stronger     │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│ MODEL 3: Separate Databases                                          │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  Tenant A ──> DB_tenant_a                                            │
│  Tenant B ──> DB_tenant_b    (isolated databases per tenant)         │
│  Tenant C ──> DB_tenant_c                                            │
│                                                                      │
│  Isolation: Database-level (physical)                                │
│  Cost:      Highest |  Complexity: Highest |  Isolation: Strongest   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### Decision Matrix

| Dimension | Shared Schema | Separate Schemas | Separate DBs |
| ----------------------- | ------------------------- | ------------------------------------ | ---------------------------- |
| **Data isolation** | Application-enforced | Schema-level | Database-level |
| **Cost** | Lowest | Medium | Highest |
| **Schema migrations** | One set, one deploy | Per-schema or global | Per-tenant |
| **Connection pooling** | Shared pool | Shared pool | Per-tenant pool |
| **Backup/restore** | Per-tenant via query | Per-schema | Per-database |
| **Noise neighbor risk** | High | Medium | Low |
| **Custom schema** | No (shared columns) | Yes (per-schema) | Yes (per-DB) |
| **Best for** | <100 tenants, same schema | 10-500 tenants, slight customization | Enterprise, compliance-heavy |

### Tenant Context Propagation

The critical pattern: **every layer must carry and enforce tenant context**.

```text
┌────────────────────────────────────────────────────────────────────┐
│ Tenant Context Propagation Stack                                   │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  Request                                                           │
│  ├── 1. Extract tenant from JWT / session / API key                │
│  ├── 2. Set tenant context (AsyncLocalStorage / request object)    │
│  ├── 3. ORM middleware injects tenant_id into every query          │
│  ├── 4. RLS policies enforce at database level (defense-in-depth)  │
│  ├── 5. Cache keys are tenant-scoped: `tenant:{id}:resource`       │
│  ├── 6. Background jobs carry tenant_id in payload                 │
│  └── 7. Audit logs record tenant context                           │
│                                                                    │
│  If ANY layer skips tenant isolation → data leak                   │
└────────────────────────────────────────────────────────────────────┘
```

## Code Examples

### Tenant Context with AsyncLocalStorage (Node.js)

```typescript
// tenant-context.ts — request-scoped tenant identity
import { AsyncLocalStorage } from 'node:async_hooks';

interface TenantContext {
  tenantId: string;
  userId: string;
  role: string;
}

export const tenantStorage = new AsyncLocalStorage<TenantContext>();

export function getTenant(): TenantContext {
  const ctx = tenantStorage.getStore();
  if (!ctx) throw new Error('No tenant context — are you inside a request?');
  return ctx;
}

// NestJS guard — extracts tenant from JWT and runs every handler in context
@Injectable()
export class TenantContextGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const tenantId = request.user?.tenantId;
    const userId = request.user?.sub;
    const role = request.user?.role;

    if (!tenantId) throw new UnauthorizedException('Missing tenant context');

    return new Promise<boolean>((resolve) => {
      tenantStorage.run({ tenantId, userId, role }, () => resolve(true));
    });
  }
}
```

### Prisma Multi-Tenant Middleware

```typescript
// prisma-tenant.middleware.ts — auto-inject tenant_id into every query
import { Prisma } from '@prisma/client';
import { getTenant } from './tenant-context';

export const tenantMiddleware: Prisma.Middleware = async (params, next) => {
  const { tenantId } = getTenant();

  // Inject tenant_id into create operations
  if (params.action === 'create') {
    params.args.data.tenantId = tenantId;
  }

  // Inject tenant filter into findMany, updateMany, deleteMany
  if (['findMany', 'findFirst', 'count', 'aggregate'].includes(params.action)) {
    params.args.where = { ...params.args.where, tenantId };
  }

  if (['updateMany', 'deleteMany'].includes(params.action)) {
    params.args.where = { ...params.args.where, tenantId };
  }

  return next(params);
};
```

### PostgreSQL Row-Level Security (Defense in Depth)

```sql
-- Enable RLS on the patients table
ALTER TABLE patients ENABLE ROW LEVEL SECURITY;

-- Policy: tenants can only see their own patients
CREATE POLICY tenant_isolation ON patients
  USING (tenant_id = current_setting('app.current_tenant')::uuid);

-- Application sets the tenant before each transaction:
SET LOCAL app.current_tenant = 'clinic-abc-123';
SELECT * FROM patients; -- only returns clinic-abc's patients
```

### Tenant-Scoped Cache Keys

```typescript
// cache.service.ts — always scope cache to tenant
import { getTenant } from './tenant-context';

class TenantCacheService {
  private prefix(tenantId: string, key: string): string {
    return `tenant:${tenantId}:${key}`;
  }

  async get(key: string): Promise<string | null> {
    const { tenantId } = getTenant();
    return redis.get(this.prefix(tenantId, key));
  }

  async set(key: string, value: string, ttl: number): Promise<void> {
    const { tenantId } = getTenant();
    await redis.set(this.prefix(tenantId, key), value, 'EX', ttl);
  }
}
```

### Background Job Tenant Propagation

```typescript
// appointment-reminder.job.ts — jobs carry tenant context
interface AppointmentReminderJob {
  tenantId: string;    // must be present
  appointmentId: string;
  patientId: string;
}

// Producer: enqueue with tenant context
async function scheduleReminder(appointment: Appointment) {
  await queue.add('appointment-reminder', {
    tenantId: appointment.tenantId,  // ← propagated
    appointmentId: appointment.id,
    patientId: appointment.patientId,
  });
}

// Consumer: restore tenant context before processing
async function handleReminder(job: Job<AppointmentReminderJob>) {
  // Restore tenant context for all DB/cache operations
  await tenantStorage.run({ tenantId: job.data.tenantId, userId: 'system', role: 'worker' }, async () => {
    const patient = await prisma.patient.findUnique({ where: { id: job.data.patientId } });
    await sendReminder(patient, job.data.appointmentId);
  });
}
```

## Real-World Use Cases

| Use Case | Tenant Model | Why |
| ------------------------------------ | ------------------- | ----------------------------------------------------- |
| **Clinic SaaS** (Docita) | Shared schema + RLS | 25+ clinics, same data model, legal isolation via RLS |
| **Enterprise SaaS** (Salesforce) | Separate schemas | Large customers need custom fields, strong isolation |
| **Multi-region** (AWS Organizations) | Separate databases | Compliance (data residency), maximum isolation |
| **Freemium** (Notion, Linear) | Shared schema | Millions of workspaces, cost-sensitive, same features |
| **Healthcare** (Epic, Cerner) | Separate databases | HIPAA requires provable per-org data isolation |

## Common Mistakes

### 1. Forgetting Tenant Context in Background Jobs

```typescript
// BAD: Job doesn't carry tenant — DB queries will fail or leak data
await queue.add('send-email', { patientId: '123' });

// GOOD: Always include tenant context
await queue.add('send-email', { tenantId: 'clinic-abc', patientId: '123' });
```

### 2. Tenant ID in URL Path Without Server-Side Enforcement

```typescript
// BAD: Client-sourced tenant ID — trust nothing from the client
app.get('/api/:tenantId/patients', (req, res) => {
  const patients = await prisma.patient.findMany({ where: { tenantId: req.params.tenantId } });
});

// GOOD: Tenant from server-side session/JWT only
app.get('/api/patients', (req, res) => {
  const { tenantId } = getTenant(); // from JWT, not URL
  const patients = await prisma.patient.findMany({ where: { tenantId } });
});
```

### 3. Shared Cache Without Tenant Scoping

```typescript
// BAD: Tenant A's cached data leaks to Tenant B
await cache.set('patients:list', JSON.stringify(data)); // global key

// GOOD: Tenant-scoped cache key
await cache.set(`tenant:${tenantId}:patients:list`, JSON.stringify(data));
```

### 4. Migration Without Tenant Awareness

```typescript
// BAD: Data migration ignores tenant boundaries
await prisma.$executeRaw`UPDATE patients SET status = 'active'`;

// GOOD: Tenant-aware migration
const tenants = await prisma.tenant.findMany();
for (const tenant of tenants) {
  await prisma.$executeRaw`UPDATE patients SET status = 'active' WHERE tenant_id = ${tenant.id}`;
}
```

## Best Practices

1. **Defense in depth** — application-level filtering + database RLS + ORM middleware. Never rely on a single layer.
2. **Tenant context via AsyncLocalStorage** — request-scoped, implicit propagation, no manual passing.
3. **ORM middleware for tenant injection** — centralizes the WHERE clause, prevents missed queries.
4. **Tenant-scoped cache keys** — `tenant:{id}:{resource}:{key}` pattern.
5. **Jobs carry tenant context** — every async task must restore tenant context before execution.
6. **Audit every access** — log tenant ID in every write operation for compliance.
7. **Test tenant isolation** — cross-tenant access tests in your test suite.
8. **Schema migrations must be tenant-aware** — always filter by tenant_id in data migrations.
9. **Connection pooling per tier** — free tenants share a pool, enterprise tenants get dedicated connections.
10. **Monitor per-tenant metrics** — query latency, error rate, cache hit ratio per tenant.

## Summary

Multi-tenant SaaS architecture balances cost efficiency against data isolation. The shared-schema model (with RLS) is the most cost-effective for <100 tenants with a uniform data model; separate schemas or databases provide stronger isolation for enterprise or compliance-heavy use cases. The critical pattern is **tenant context propagation**: every layer — HTTP handler, ORM, cache, background job, audit log — must carry and enforce the tenant ID. Defense in depth (application + ORM + RLS) is the production standard.

## Cheat Sheet

```text
Multi-Tenancy Decision Tree:
├── Same data model for all tenants? ──→ Shared schema + RLS
├── Some tenants need custom fields? ──→ Separate schemas
├── Compliance / data residency? ──→ Separate databases
└── < 10 tenants, high-value? ──→ Separate databases (simpler ops)

Tenant Context Propagation:
├── Extract from JWT/session (server-side only)
├── Store in AsyncLocalStorage (request-scoped)
├── ORM middleware injects tenant_id
├── RLS policies enforce at DB level
├── Cache keys: tenant:{id}:{resource}
├── Jobs: carry tenant_id in payload
└── Audit logs: record tenant context

Common Pitfalls:
├── Forgetting tenant context in background jobs
├── Client-sourced tenant ID (trust nothing from client)
├── Shared cache without tenant scoping
├── Data migrations without tenant filter
└── Missing RLS policies on new tables
```

# Multi-Tenant SaaS Architecture

A service authenticates a user from tenant A, but a background export later loads a document by its identifier without checking the tenant. Authentication succeeded; the data path still exposed another customer's information. Multi-tenant software-as-a-service (SaaS) must carry and enforce the tenant boundary across requests, data stores, caches, jobs, and operations:

```text
auth OK as tenant A → background export loads doc by ID, no tenant check → leak.
```

## Definition

A **multi-tenant application** serves multiple customer organizations or other independent customer groups through one product. Tenants may share or receive dedicated infrastructure, but each operation must be scoped to the **tenant** after the caller's membership and authority are verified.

> **Textbook Definition:** Multi-tenant architecture serves independent customer tenants on pooled, dedicated or mixed resources while enforcing tenant-specific authorization, data isolation, capacity allocation and lifecycle operations.

## First Principles

A tenant identifier names the requested boundary; it never proves that a caller belongs to it. Verify identity and membership before creating tenant context. Sharing infrastructure also creates shared failure and capacity domains, so data isolation alone cannot prevent one tenant exhausting another's resources. Finally, every asynchronous path must establish its own scope: request-local state never automatically authorizes a job, export, or scheduled task.

## 1. Choose an isolation model per resource

| Model | Typical layout | Main trade-off |
| --------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **Pool** — shared tables | Tenants share processes, schema and tables; rows carry a tenant key | Low operating cost, but every query and restore path must preserve tenant scope |
| **Bridge** — schema per tenant | Tenants share a database server but have separate schemas | Separate namespaces and grants, but migrations fan out and the server remains shared |
| **Silo** — database or stack per tenant | A tenant receives a separate database or broader resource set | Stronger operational boundary, with more pools, migrations, monitoring and capacity to manage |
| **Hybrid** | Different services or tenant tiers use pool, bridge or silo | Fits different workload and isolation needs, but routing and operations become more complex |

Pool, bridge, and silo are common pattern names; products may use different labels. A separate database on one server is no physical isolation. A schema's `search_path` selects names; it never authorizes access. Choose per service and resource using isolation promises, restore granularity, workload variance, data-location commitments, and operating cost. In many pooled systems, point-in-time restore rewinds every tenant together; restoring one tenant needs a tested tenant-scoped export or isolated copy plus write reconciliation. Tenant count alone is no useful threshold. The [AWS SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/general-design-principles.html) likewise treats pooling and siloing as choices differing by service and tenant profile.

## 2. Verify membership before carrying context

A tenant name in a route or request body is a selection, not a permission. Authenticate the actor, verify membership and role for the selected tenant, then create a context for the downstream work. A signed token can contain a tenant claim, but membership removal may make it stale; set a revocation or revalidation policy matching the product's access requirements.

In Node.js, `AsyncLocalStorage` can carry that verified context through asynchronous work created inside its callback. It propagates context; it never performs authorization. The callback must wrap the actual downstream handler:

```typescript
import { AsyncLocalStorage } from 'node:async_hooks';
type TenantContext = { tenantId: string; actorId: string };
export const tenantStorage = new AsyncLocalStorage<TenantContext>();

export function getTenant(): TenantContext {
  const context = tenantStorage.getStore();
  if (!context) throw new Error('Missing authorized tenant context');
  return context;
}

export async function withTenantRequest<T>(
  resolveAuthorizedContext: () => Promise<TenantContext>,
  work: () => Promise<T>,
): Promise<T> {
  const context = await resolveAuthorizedContext();
  return tenantStorage.run(context, work);
}
```

Framework hooks differ in when authentication runs. If a guard only returns an authorization result and the framework invokes the handler later, that handler must still execute inside the context callback. Never pass request context to a worker as proof of authority; give the job its own trusted producer, actor, or service identity, then establish its scope when it runs. See the [Node.js async context documentation](https://nodejs.org/api/async_context.html) for `run()` semantics.

## 3. Enforce tenant scope in the database

With a connection pool, tenant A and tenant B can use the same physical connection at different times. Begin a transaction, install the verified tenant locally on that transaction's connection, and send every protected query through the transaction client. Commit or rollback ends the local setting before the connection returns to the pool:

```text
verified tenant context → BEGIN on one checked-out connection
                            ↓
              transaction-local tenant setting
                            ↓
       scoped repository queries + database policy
                            ↓
             COMMIT / ROLLBACK → release connection
```

Keep explicit tenant predicates in repositories so query intent stays visible. Where supported, database row-level security (RLS) can backstop an omitted predicate on tables with applicable policies. This protects against an application bug under trusted execution; it never protects against SQL injection or a compromised application role running arbitrary statements and changing its tenant setting. Run with a non-owner role lacking `BYPASSRLS` and constrain cross-tenant relationships with tenant-scoped keys. The [PostgreSQL RLS chapter](../../../20-backend/20.4-database/01-postgresql-foundations/20.4.1.06-row-level-security.md) owns exact policy syntax, role behavior, and runnable examples.

Object-relational mapper (ORM) filters and middleware are no isolation proofs. Confirm coverage for raw structured query language (SQL), unique reads, nested writes, and relationship connects against the pinned version. Prisma ORM 7 removed the legacy client `$use` middleware hook. Prisma ORM 8 holds a different middleware configuration and remains a release candidate as of 2026-10-14; check its [release status](https://www.prisma.io/docs/orm/release-status) before adoption. Neither middleware hook replaces database constraints and policies.

## 4. Carry the boundary into every resource

| Resource | Required boundary |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Relational data | Scope reads and writes; constrain tenant-owned relationships; test the runtime role and transaction path |
| Cache and object storage | Include tenant and permission scope in cache keys; authorize each delivery; treat object keys and prefixes as organization, not access control; bound signed-link lifetime to revocation needs |
| Jobs and events | Carry tenant plus actor or service identity from a trusted producer; recheck tenant status and operation authority when the worker executes |
| Search and exports | Apply tenant scope when indexing, querying and producing exports; object IDs and storage prefixes are not authorization |
| Administration | Make cross-tenant actions explicit, narrowly scoped and auditable; don't grant routine application paths a global bypass |

## 5. Budget shared work and manage the lifecycle

Per-tenant quotas, concurrency limits, and fair queue scheduling prevent a bulk import monopolizing a shared worker pool. Measure requests, storage, database connections, job time, and cost by tenant. A dedicated connection pool per tenant can multiply connection counts; use bounded shared pools or a small set of service tiers when that meets the isolation contract.

Provision tenants through an idempotent workflow: create the chosen resource boundary, apply the current schema and grants, set quotas, verify access, then mark the tenant active. Offboarding first revokes new access, then cancels or drains jobs, removes cache and search copies, and applies the data-retention and backup-expiry policy. Test tenant-specific restore and migration paths before enabling traffic; restoring only the database may leave object storage, indexes, or queues inconsistent.

## 6. Test the real isolation boundary

| Probe | Expected result |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Caller selects a tenant without membership | Denied before tenant data is read or changed |
| Context is missing or a pooled connection is reused | No prior tenant setting or data becomes visible |
| Raw, nested or relationship query crosses tenant identifiers | Policy or tenant-scoped constraint rejects the access |
| Cache hit follows a tenant or permission change | No cross-tenant response; revocation follows the declared bound |
| Job uses forged, stale or disabled-tenant context | Worker rejects or safely cancels the operation |
| Tenant is offboarded or restored | Access, jobs, cache, indexes, objects and retained backups match the lifecycle policy |

Run tests as the deployed non-owner database role and through the actual pool and worker paths. A unit test injecting a tenant identifier directly cannot prove the membership check or connection behavior.

## Summary

Choose pool, bridge or silo boundaries for each resource using isolation, recovery, workload and operating constraints. Verify tenant membership before creating context, bind database context and queries to one transaction, and carry a separately authorized scope through caches, storage and jobs. Test provisioning, offboarding and restore alongside ordinary reads and writes.

# Zero-Downtime Deployments — Blue-Green, Canary, Rolling, Feature Flags


---

## Definition

A **zero-downtime deployment** is a release process in which no client request fails and no version is served from a partially-updated state. It is a *compatibility* property, not a rollout speed: the mechanical parts (load balancer, rolling update, health checks) are easy, and what actually defines the discipline is that **the old and new versions run simultaneously** and must interoperate.

The constraint that shapes every choice:

```text
schema:  expand ──▶ migrate ──▶ contract          (never rename/drop in one step)
          add nullable column   backfill   make NOT NULL   drop old column
          └──────── new code writes both; old code still works ────────┘

rollout: canary 1% → 10% → 50% → 100%   with automatic rollback on SLO breach
         blue-green (two fleets, switch at LB) — fast rollback, 2× cost during cutover
         rolling (replace in batches, drain before kill) — cheapest, slowest rollback
```

Three rules define a deploy that cannot take traffic down: **drain before terminate** (stop routing, wait for in-flight requests, then exit); **decouple schema from code** via expand/contract so both versions' queries are valid during the overlap; and **make the change backward-compatible at the API boundary** (add fields, never repurpose; tolerate unknown fields). Where a change genuinely cannot be made compatible — a mandatory field, a changed enum meaning — the pattern is to deploy it as two releases, which is what "expand/contract" means in practice.

## First Principles

Zero-downtime deploys are possible because of one discipline: N and N+1 coexist.

1. **Rolling/blue-green/canary are all the same requirement**: two versions live simultaneously — which forces backward-compatible migrations (→ 20.4.5.02's expand-migrate-contract) and stateless services (→ 20.3.1.02).
2. **Traffic shifting is the risk control**: canary routes 1% → watch error/latency signals → ramp or rollback. The metrics gate must be automated — humans watching dashboards don't catch a 0.5% error regression at 3am.
3. **The database is the shared hazard**: schema changes must serve both versions for the whole rollout window — which is why DB migrations, not app code, are the long pole of zero-downtime.

## Deployment Strategies

| Strategy | Downtime | Risk | Rollback Speed | Cost |
| ----------------- | -------- | -------- | -------------- | ------ |
| **Rolling** | None | Medium | Medium | Low |
| **Blue-Green** | None | Low | Instant | High |
| **Canary** | None | Very Low | Instant | Medium |
| **Feature Flags** | None | Minimal | Instant | Low |

## Rolling Deployment

### Kubernetes Rolling Update
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # Max pods above desired count
      maxUnavailable: 0 # Never have fewer than desired
  template:
    spec:
      containers:
      - name: api
        image: api:v2
        readinessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 10
          periodSeconds: 5
```

### Rolling with Pre-Stop Hook
```yaml
spec:
  containers:
  - name: api
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 15"] # Drain connections
```

## Blue-Green Deployment

**How it works:** You run two identical environments — "blue" (current version) and "green" (new version). Both are fully deployed and ready. To deploy, you switch the load balancer from blue to green. If something goes wrong, you switch back instantly. The key advantage: rollback is instant (just flip the switch back) because blue is still running. The downside: you need double the infrastructure resources during deployment.
 Deployment

### Infrastructure Setup
```typescript
// Blue-Green configuration
const blueGreenConfig = {
  blue: {
    name: 'api-blue',
    version: 'v1',
    replicas: 4,
    service: 'api-blue-service'
  },
  green: {
    name: 'api-green',
    version: 'v2',
    replicas: 4,
    service: 'api-green-service'
  },
  loadBalancer: {
    name: 'api-lb',
    activeTarget: 'api-blue-service' // or 'api-green-service'
  }
};
```

### Kubernetes Implementation
```yaml
# Blue deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-blue
spec:
  replicas: 4
  selector:
    matchLabels:
      app: api
      version: blue
  template:
    metadata:
      labels:
        app: api
        version: blue
    spec:
      containers:
      - name: api
        image: api:v1
---
# Green deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-green
spec:
  replicas: 4
  selector:
    matchLabels:
      app: api
      version: green
  template:
    metadata:
      labels:
        app: api
        version: green
    spec:
      containers:
      - name: api
        image: api:v2
---
# Service (switch target)
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
    version: blue # Switch to green for new version
  ports:
  - port: 80
    targetPort: 3000
```

### Switch Traffic
```bash
# Switch from blue to green
kubectl patch service api -p '{"spec":{"selector":{"version":"green"}}}'

# Switch back (rollback)
kubectl patch service api -p '{"spec":{"selector":{"version":"blue"}}}'
```

## Canary Deployment

**How it works:** You route a small percentage of traffic (e.g., 10%) to the new version while the rest stays on the old version. If the canary shows elevated error rates or slow response times, you automatically roll back by routing 100% back to the old version. This is safer than blue-green for production because you test with real traffic but only affect a small fraction of users. Kubernetes + Istio makes this straightforward with VirtualService weight-based routing.
 Deployment

### Istio Traffic Splitting
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api
spec:
  hosts:
  - api
  http:
  - route:
    - destination:
        host: api
        subset: stable
      weight: 90
    - destination:
        host: api
        subset: canary
      weight: 10
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api
spec:
  host: api
  subsets:
  - name: stable
    labels:
      version: v1
  - name: canary
    labels:
      version: v2
```

### Nginx Canary
```nginx
# Canary configuration
upstream backend {
    server api-stable:3000 weight=90;
    server api-canary:3000 weight=10;
}

# Or use split_clients for percentage-based routing
split_clients "${remote_addr}" $backend_pool {
    10% canary;
    * stable;
}

server {
    location / {
        proxy_pass http://$backend_pool;
    }
}
```

## Feature Flags

### Implementation
```typescript
interface FeatureFlag {
  name: string;
  enabled: boolean;
  rolloutPercentage: number;
  allowedUsers: string[];
  allowedClinics: string[];
  startDate?: Date;
  endDate?: Date;
}

class FeatureFlags {
  private flags: Map<string, FeatureFlag> = new Map();

  constructor(private redis: Redis) {}

  async isEnabled(flagName: string, context: UserContext): Promise<boolean> {
    const flag = await this.getFlag(flagName);
    if (!flag) return false;

    // Check if flag is enabled
    if (!flag.enabled) return false;

    // Check date range
    if (flag.startDate && new Date() < flag.startDate) return false;
    if (flag.endDate && new Date() > flag.endDate) return false;

    // Check allowed users
    if (flag.allowedUsers.length > 0) {
      return flag.allowedUsers.includes(context.userId);
    }

    // Check allowed clinics
    if (flag.allowedClinics.length > 0) {
      return flag.allowedClinics.includes(context.clinicId);
    }

    // Percentage rollout
    if (flag.rolloutPercentage < 100) {
      const hash = this.hashUserId(context.userId, flagName);
      return hash < flag.rolloutPercentage;
    }

    return true;
  }

  private hashUserId(userId: string, flagName: string): number {
    const hash = crypto.createHash('md5')
      .update(`${userId}:${flagName}`)
      .digest('hex');
    return parseInt(hash.substring(0, 8), 16) % 100;
  }
}
```

### Usage in Code
```typescript
// Instead of
if (featureFlags.isEnabled('new-booking-flow', user)) {
  return newBookingFlow(data);
} else {
  return legacyBookingFlow(data);
}

// Better: Abstract behind interface
interface BookingFlow {
  create(data: BookingData): Promise<Booking>;
}

class BookingFlowFactory {
  constructor(private flags: FeatureFlags) {}

  async getFlow(user: UserContext): Promise<BookingFlow> {
    if (await this.flags.isEnabled('new-booking-flow', user)) {
      return new NewBookingFlow();
    }
    return new LegacyBookingFlow();
  }
}
```

## Database Migrations (Zero-Downtime)

### Expand-Contract Pattern
```sql
-- Step 1: Expand (add new column)
ALTER TABLE appointments ADD COLUMN scheduled_date DATE;
UPDATE appointments SET scheduled_date = scheduled_at::date;

-- Step 2: Migrate (dual write)
-- Application writes to both columns
-- Backfill existing data

-- Step 3: Contract (remove old column)
-- After verifying new column works
ALTER TABLE appointments DROP COLUMN scheduled_at;
ALTER TABLE appointments RENAME COLUMN scheduled_date TO scheduled_at;
```

### Backward-Compatible Migrations
```sql
-- Add column with default
ALTER TABLE users ADD COLUMN full_name VARCHAR(200) DEFAULT '';

-- Add NOT NULL after backfill
ALTER TABLE users ALTER COLUMN full_name SET NOT NULL;

-- Add index concurrently (no lock)
CREATE INDEX CONCURRENTLY idx_users_email ON users (email);
```

## Rollback Strategies

### Application Rollback
```typescript
// Quick rollback via deployment
const rollback = {
  rolling: 'kubectl rollout undo deployment/api',
  blueGreen: 'kubectl patch service api -p \'{"spec":{"selector":{"version":"blue"}}}\'',
  canary: 'Update Istio weight to 0% for canary'
};
```

### Database Rollback
```typescript
// Never drop columns in rollback
const safeRollback = {
  // Instead of: DROP COLUMN
  use: 'SET DEFAULT + stop using',

  // Instead of: ALTER COLUMN TYPE
  use: 'Add new column, migrate data, swap',

  // Instead of: DELETE data
  use: 'Soft delete with flag'
};
```

## Summary

1. **Rolling, blue-green, and canary are the three shapes** — pick by blast-radius appetite and rollback speed requirement
2. **The database is the constraint** — expand/contract (backward-compatible) schema migrations unlock everything else
3. **Health-gated rollout** — deployments that ignore readiness checks are just fast outages
4. **Feature flags decouple deploy from release** — ship dark, flip when ready, kill instantly
5. **Practise the rollback until it's boring** — an untested rollback is a theory

# Zero-Downtime Deployments — Blue-Green, Canary, Rolling, Feature Flags

Traffic moves back to release A, and its latency recovers. Then an old worker reads a queued message written by release B and cannot parse the new payload. The route switch restored the old code; it never restored compatibility. A safe rollout must account for what versions share while requests and work remain in flight:

```text
route back to A → old worker can't parse B's queued message. Compatibility ≠ routing.
```

## Definition

A **zero-downtime deployment** aims to replace a version while preserving the service's declared **availability and latency objectives**. Traffic transfer, readiness, and cleanup matter, but so does compatibility between old/new servers, clients, workers, and data.

> **Textbook Definition:** A zero-downtime deployment is a release procedure designed to preserve service availability during version replacement through compatible interfaces and data, controlled traffic transfer and bounded lifecycle transitions.

## First Principles

Replacement is never instantaneous across a fleet. Old requests, open connections, queued jobs, and browser tabs can outlive a traffic switch. Both versions can therefore observe or write shared data during the overlap, and reverting a binary never reverts committed data or external effects.

To maintain service, reserve enough useful capacity while replacement boots and drains. A readiness check establishes one instance's ability to serve its intended contract; it cannot prove a migration is reversible or that a new business path is correct. Stateful services can also roll safely, but need their own ownership/replication transition instead of an assumption that every service must be stateless.

## 1. Choose what the rollout controls

| Strategy | Mechanism | Boundary |
| ------------ | -------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Rolling | Replace selected instances progressively | Mixed versions, available surge capacity and safe drain |
| Blue-green | Prepare another fleet and change routing | New/old fleets may share data; routing convergence and old connections remain |
| Canary | Expose a limited audience/traffic portion, then evaluate | Enough representative evidence and a safe stop/rollback path |
| Feature flag | Select behavior within deployed code | Rule propagation and already-started effects; not itself a fleet replacement |

One useful distinction is that deployment puts a version into the fleet while release exposes its behavior to users. A flag separates those steps only while both code paths and the flag state remain supported. None of these strategies guarantees zero downtime or instant rollback by itself. Cost depends on retained capacity, shared infrastructure, traffic, and observation time; blue-green need never double every resource. A small canary can still corrupt shared data used by all users. Build one immutable artifact and promote those same bits through test, canary, and full release; supply environment-specific configuration separately.

For example, a blue-green rollout prepares green, verifies it against shared dependencies, routes new requests to green, drains blue, then retires blue. Both fleets can overlap, so the data and queue contracts still have to support both versions.

## 2. Trace a rolling replacement

```text
start B → initialize → readiness succeeds → route new work to B
stop routing to A → finish or reject in-flight work by deadline → close A
```

Kubernetes `maxSurge: 1` permits one extra Pod above desired count. With `maxUnavailable: 0`, the controller never intentionally reduces available replicas below the desired count under its readiness rules. Terminating Pods can still consume resources beyond `replicas + maxSurge` until their grace periods expire. These settings manufacture no spare compute, make no load balancer converge instantly, and guarantee no request success. Image startup, quotas, and unschedulable Pods can stall the rollout; set `progressDeadlineSeconds` and alert on `ProgressDeadlineExceeded`. Kubernetes reports a stalled Deployment and keeps reconciling it; it never automatically rolls back. An operator or higher-level controller must choose whether to pause, roll back, or repair forward.

A `preStop` sleep may allow routing propagation in a measured setup; it never drains an application by itself. Kubernetes starts the termination-grace countdown before the hook and sends the stop signal after the hook completes, so the hook and shutdown share one deadline. The process must stop new admission appropriately, complete useful in-flight work, and close dependencies afterward. Upgraded sockets/workers need explicit policies. [Health Checks & Graceful Shutdown](../01-liveness-lifecycle/30.3.1.01-health-checks-graceful-shutdown.md) owns that implementation; the [Kubernetes deployment stack](../../../40-platform/40.2-kubernetes/INDEX.md) owns complete manifest patterns.

## 3. Demand canary evidence from the changed path

Compare stable and candidate using release/cohort labels, request outcomes, latency distributions, saturation, and business results. A health probe returning 200 is no order/payment correctness probe. A raw error count is no error ratio; a Prometheus `up` metric establishes scrape availability rather than customer-visible service availability.

Account for cohort bias: a 1% population can exclude a rare large tenant, long transaction, or nightly workload. Choose minimum samples and observation coverage, not a universal percentage/time hold. Weighted request routing, subject assignment, and connection-level routing expose different populations; persistent connections can distort nominal traffic weights.

Define automated gates where appropriate, plus an operational pause/override and a responsible decision owner. A canary gate can stop further exposure, but a payment or email already accepted by a provider needs reconciliation; routing back cannot undo it.

## 4. Expand, migrate, then contract without losing meaning

Consider renaming an order reference while retaining its text meaning. Old code reads/writes `reference`; new code eventually uses `external_reference`. The following local database fixture illustrates schema/data compatibility, not a production-sized backfill scheduler or rollout controller.

The safe transition is: add the nullable field → deploy writers maintaining both fields → backfill and verify → switch readers → retire old writers and clients → remove the old field:

```sql
CREATE TABLE release_orders (
  id bigint PRIMARY KEY, reference text NOT NULL
);
INSERT INTO release_orders VALUES (1, 'order-A'), (2, 'order-B');

-- EXPAND: old readers remain valid; new field is initially optional.
ALTER TABLE release_orders ADD COLUMN external_reference text;

-- Deploy compatible writers that maintain both fields before relying on the new one.
-- Example of one dual-written new order:
INSERT INTO release_orders (id, reference, external_reference)
VALUES (3, 'order-C', 'order-C');

-- MIGRATE: small fixture only. Production backfill uses bounded batches,
-- stable progress and a concurrency policy for updates from old writers.
UPDATE release_orders SET external_reference = reference
WHERE external_reference IS NULL;

-- Verify equality/completeness under the established writer contract.
SELECT count(*) AS mismatches FROM release_orders
WHERE external_reference IS DISTINCT FROM reference;
```

Old writers updating only `reference` after backfill can make the new field stale. Upgrade or bridge every writer, handle concurrent changes, and revalidate before making new reads authoritative. A trigger or change capture is another bridge with its own tested contract; a one-time copy alone is insufficient.

Switch readers only after coverage/meaning checks, then retain both fields through the rollback and old-client/job support window. Contract removes the old field only when no supported version uses it. Constraint changes, locks, and indexes need their own bounded migration plan. A rename or converting a timestamp to a date in one release can break readers **and discard information**.

PostgreSQL `CREATE INDEX CONCURRENTLY` reduces blocking of writes; it is not "no lock." It performs multiple phases, cannot run inside a normal transaction block, and failed builds can leave an invalid index needing recovery. Use the canonical [database operations stack](../../../20-backend/20.4-database/05-operations-and-scaling/INDEX.md) for migration commands and boundaries.

## 5. Know rollback's states and test transitions

| State to assess | Why reverting code may fail |
| ------------------------ | --------------------------------------------------------------------------------- |
| Schema and stored values | Old binary may not understand contracted columns/enums/format |
| Queue/event payloads | New producer may have emitted work still consumed by old workers |
| Assets and clients | A browser already running B may continue requesting B's assets or response fields |
| Provider effects | Accepted payment/email cannot be undone by routing back to A |
| Configuration/flags | Old binary may interpret the same value differently |

Retain the compatible artifact/configuration set and practice recovery while new work is in flight. "Soft delete" or "stop using the column" never reconstructs lost values. Prefer a forward repair when rollback would violate the current data contract.

Exercise a stalled boot, a request outliving the drain window, a migration waiting on a lock, and a provider committing an effect before its response is lost. Then attempt rollback after new data and work have been written; verify whether the system can stop, reconcile, or needs a forward repair. Readiness alone never covers these transitions.

## Summary

Safe replacement requires useful capacity and compatible versions through boot, overlap and drain. Rolling, blue-green, canary and flags change exposure in different ways; none makes rollback instant or undoes committed effects. Expand/migrate/contract preserves meaning only when every writer and supported reader participates in the transition.

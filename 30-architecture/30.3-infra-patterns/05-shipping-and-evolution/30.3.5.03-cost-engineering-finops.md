# Cost Engineering & FinOps

> **TL;DR:** **Cloud spend is engineering output, so the metric to manage is unit economics (cost per request, per customer, per tenant) — not the total bill.** The loop is visibility (tagging and allocation) → optimization (rightsizing from percentile utilization, storage tiering, spot, autoscaling traps) → operation (budgets, anomaly alerts, cost-regression checks in CI), the same shape as latency discipline: measure, attribute, gate.

---

> **Cloud bills are engineering output.** Rightsizing, storage tiering, spot strategy, autoscaling traps, tagging for allocation, unit economics (cost per request/customer), and cost regression checks in CI — FinOps is the practice of making money a first-class engineering metric alongside latency and errors.

---

## First Principles

Cost engineering exists because cloud pricing converts architecture decisions into monthly invoices:

1. **Cost is an architecture output**: chatty service calls, over-provisioned instances, and unpartitioned tables are design decisions with price tags — FinOps makes the feedback loop visible (per-team, per-feature attribution).
2. **The levers are few and ordered**: rightsize (utilization), commit (reserved/spot), eliminate waste (zombie resources, → 50.4's hygiene), then architectural (caching, storage tiers, → 20.8.01). Most savings are in the first three, which are operational, not architectural.
3. **Unit economics is the language**: cost per request/user/transaction turns infrastructure spend into product margin — the number that lets engineering and business argue about the same fact.

---

## Definition

**FinOps** is the practice of treating cloud spend as an engineering metric with the same discipline as latency: attribution, unit economics, and regression gates. It exists because in a variable-cost model, architecture *is* the bill — and without accounting, cost becomes an invisible second consequence of every design choice.

```text
attribution     ─▶ allocation (mandatory tags: service/team/env) ─▶ showback/chargeback
unit economics  ─▶ cost per request / per tenant / per active user  ← the only number that
                                                                      explains a growing bill
levers, ranked  ─▶ rightsizing (idle CPU) > storage tiering > spot/preemptible >
                   autoscaling policy > architecture (egress, per-call pricing)
guardrail       ─▶ cost regression check in CI (cost per 1k requests vs. baseline)
```

Three definitional points separate FinOps from "turn things off". First, **total spend is not actionable; unit cost is** — a bill that doubles while users quadruple is a *success*, so the tracked metric must be normalized (per request, per tenant). Second, the biggest waste is usually **structural, not operational**: over-provisioned instances are visible on day one, whereas cross-AZ chatter, egress, per-call serverless pricing, and duplicated telemetry scale invisibly with traffic. Third, **cost must be attributed before it can be optimized** — untagged resources are unowned, and unowned spend is never reduced, which is why tagging policy is the first thing to implement.

## The Problem

```
Month 1:  $12k bill, nobody looks
Month 6:  $140k bill, CFO asks questions
Cause:    no allocation (who spends?), no unit model (what should it cost?),
          no feedback loop (did this PR change the bill?)
```

Engineering optimizes what it can see. Latency has dashboards; dollars historically had a monthly invoice PDF. FinOps closes that gap: allocate every dollar to an owner, express spend as unit economics, and gate regressions in CI the same way you gate performance.

## Rightsizing

Match provisioned capacity to *observed* need, using percentiles not averages:

```text
Rightsizing loop (run quarterly per service):
1. Pull p95 CPU / memory utilization over 30 days
2. Flag instances where p95 < 40% of provisioned -> downsize one step
3. Flag instances where p95 > 80%                 -> upsize BEFORE incidents
4. Prefer burstable families for spiky, low-average workloads
5. Re-check after two weeks (utilization often shifts)
```

| Signal | Typical finding | Action |
| ------------------------------------ | -------------------------------- | -------------------------------------------------- |
| p95 memory < 30% on all app pods | Requests sized from dev machines | Halve requests/limits; watch OOM kills |
| DB instance at 8% CPU but IOPS maxed | Wrong dimension optimized | Move to IOPS-optimized family instead of more vCPU |
| Nightly batch on 24/7 nodes | Time-shapeable workload | Scheduled scaling or spot batch queue |
| Dozens of idle dev/staging envs | Always-on environments | Auto-sleep off-hours (70%+ savings typical) |

Rightsizing is the highest-yield first move because it requires zero architecture change.

## Storage Tiering

Storage is the stealth budget line: data only grows, and hot-access pricing is 10-100x cold-access pricing.

| Tier (AWS naming) | Access pattern | Relative cost | Retrieval |
| ------------------------------------ | -------------------- | ---------------------------------- | --------- |
| Hot (S3 Standard / NVMe) | Frequent, ms latency | 1x (baseline) | immediate |
| Warm (S3 Standard-IA / Int.-Tiering) | Monthly-ish | ~40% storage, per-GB retrieval fee | immediate |
| Cold (Glacier Instant/Flexible) | Quarterly-yearly | ~10-20%, minutes retrieval | minutes |
| Deep archive (Glacier Deep Archive) | Compliance/rare | ~2-4%, hours retrieval | up to 48h |

Practices:

1. Default new buckets to **lifecycle rules**: 30d hot → 90d IA → 365d Glacier → expire.
2. Partition append-only data (logs, events) by date so tiering = moving whole partitions.
3. Watch retrieval fees: IA/Glacier charge per GB fetched — a dashboard querying "cold" daily erases the savings.
4. Delete snapshots of deleted volumes; orphaned EBS snapshots are classic silent spend.

## Spot & Preemptible Strategy

Spot capacity runs 60-90% cheaper but can be reclaimed with ~30 seconds notice.

```text
Good fit                          Bad fit
─────────────────────             ─────────────────────
batch jobs / map-reduce           stateful primaries
CI runners                        latency-critical request paths
stateless workers with queues     single-instance anything
model training with checkpoints   long transactions without retry
render farms                      etcd/consensus quorum members (mixed!)
```

Make workloads spot-safe:

```typescript
// Worker loop tolerant of 30s eviction warnings
async function runJob(job: Job): Promise<void> {
  const checkpoint = await store.loadCheckpoint(job.id);
  try {
    await process(job, {
      startFrom: checkpoint,
      onProgress: (p) => store.saveCheckpoint(job.id, p), // resume point
      deadlineMs: remainingSpotLifetime(), // drain before eviction
    });
    await queue.ack(job);
  } catch (err) {
    if ((err as EvictionError).isEviction) {
      await queue.nack(job, { delayMs: 0 }); // another node re-runs from checkpoint
      return;
    }
    throw err;
  }
}
```

Pair spot with on-demand fallback pools via ASG/MIG mixed policies so evictions degrade throughput, not availability.

## Autoscaling Cost Traps

Autoscaling promises pay-per-use; misconfigured, it multiplies waste:

| Trap | What happens | Fix |
| ----------------------------- | ---------------------------------------------------- | --------------------------------------------------------------- |
| Scale-out storms | Flappy metric (e.g., CPU) thrashes instances up/down | Longer stabilization windows; scale-in protection; step scaling |
| Min replicas too high | 20 idle pods 24/7 "for safety" | Schedule min by traffic curve (cron scaler) |
| Cross-AZ chatter | Chatty services pay inter-AZ egress both ways | Topology-aware routing; co-locate hot paths |
| Per-pod sidecar overhead | Mesh proxy doubles small pods' footprint | Rightsize sidecars; share meshes selectively |
| NAT gateway + private subnets | Every outbound byte costs NAT processing | VPC endpoints for S3/ECR/etc.; audit egress paths |
| Overprovisioned HPA targets | Requests/limits set for peak-of-peaks | Base on p95, not max; use VPA recommendations |

The pattern: autoscaling amplifies whatever policy you wrote — including a wrong one, at machine speed.

## Tagging & Allocation

Unallocated spend cannot be optimized, only lamented.

```yaml
# Mandatory tags (enforced by policy-as-code at deploy time)
tags:
  service: checkout-api       # maps to owning team's dashboard
  team: payments              # showback recipient
  environment: production     # enables env-level comparisons
  cost-center: cc-4411        # finance mapping
  managed-by: terraform       # detects unmanaged resources
```

Allocation maturity ladder:

1. **None** — one giant invoice line ("cloud").
2. **Showback** — tagged report per team; no chargeback pressure yet.
3. **Chargeback** — teams own their line item in departmental budgets.
4. **Unit-economics-driven** — teams see cost per request/customer and act on it.

Enforce with guardrails, not memos: CI rejects untagged Terraform plans; a nightly job flags untagged resources older than 24h; untagged = unowned = deletable after warning period.

## Unit Economics

Absolute dollars mean nothing without scale context. Express cost as a ratio:

```text
Cost per request   = monthly infra cost attributable to service
                     ÷ successful requests served

Cost per customer  = total COGS (infra + third-party APIs + support tooling)
                     ÷ active customers          (gross-margin view)

Gross margin check = revenue per customer − cost per customer
```

Worked example:

```text
checkout-api:        $9,600/month
successful orders:   3,000,000/month
→ cost per order     = $0.0032

If product wants free shipping threshold feature tripling recommendation calls:
  projected cost/order = $0.0047 (+47%)
  → visible BEFORE launch, not on next month's invoice
```

Uses:

- Anomaly detection: alert when cost/request jumps >20% week-over-week (often a perf bug wearing a billing costume).
- Prioritization: optimize the endpoint that is 40% of spend, not the 15th microservice.
- Pricing input: sales asks "can we do unlimited plan?" — now you can answer with math.

## Cost Regression Checks in CI

Treat the bill like a benchmark suite:

```yaml
# .github/workflows/cost.yml
name: cost-regression
on: [pull_request]
jobs:
  infracost:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Estimate infra cost delta
        uses: infracost/infracost-gh-action@master
        with:
          path: infra/
          # posts table to the PR:
          # + aws_instance.worker  (x12)  +$486/mo
          # ~ aws_db.instance       gp3->io2 +$210/mo
      - name: Fail on big deltas
        run: infracost diff --path infra/ --threshold "10%" --format diff | \
             check-delta --max-monthly-increase 250
```

Layered checks:

1. **IaC diff** (Infracost/OpenCost): estimated monthly delta posted per PR; hard-fail above threshold or require `cost-review` label.
2. **Budget alerts**: provider budgets at 50/80/100% with owner routing.
3. **Unit-economy monitors**: cost-per-request SLO breach pages like any other regression.
4. **Anomaly detection**: provider anomaly alerts or homegrown EWMA on daily spend.

Culture rules that make it stick:

- Cost reviews are part of architecture reviews — same RFC template gets a "cost impact" section.
- Efficiency KPIs (cost per 1k requests, $/customer) appear on the same dashboards as golden signals.
- Savings wins get celebrated like performance wins; engineers optimize what leadership notices.
- FinOps is a loop, not a project: inform (visibility) → opt (targets) → operate (automation), repeating as scale changes the picture.

## Common Mistakes

| Mistake | Problem | Fix |
| --------------------------------------- | ------------------------------------------------ | ------------------------------------ |
| Optimizing absolute $ before allocation | Wrong teams optimize wrong things | Tag/allocation first |
| Averages for rightsizing | Peaks hidden; averages lie | Percentiles (p95/p99) |
| Treating spot as free | Evictions corrupt naive stateful jobs | Checkpointing + mixed pools |
| Query-heavy dashboards on cold tiers | Retrieval fees exceed storage savings | Tier by access evidence, not hope |
| One-off cleanup sprints | Bill regrows in weeks | Continuous loops + CI gates |
| Ignoring egress/NAT/data-transfer | Often 20-30% of bill, invisible in compute views | Dedicated transfer review line |
| No cost section in RFCs | Architecture bakes in spend silently | Cost impact mandatory in design docs |

## Interview Tips

- Frame cost as an engineering SLO: "I treat $/request exactly like p99 — monitored, alerted, gated in CI."
- Know rough magnitudes: egress and NAT surprise people most; storage grows forever; idle dev environments are the fastest win.
- Tell an ownership story: tagging → showback → unit economics → chargeback, enforced by policy-as-code not meetings.
- Mention concrete tooling once (Infracost/OpenCost/provider budgets) — signals practice, not theory.

## 30-Second Interview Version

> I run cost like performance: first allocate everything via enforced tagging so every dollar has an owner; then rightsize from p95 utilization and tier storage by access evidence; use spot with checkpointing for interruptible work; and watch autoscaling traps — flap, min-replica waste, cross-AZ traffic. Spend becomes unit economics — cost per request and per customer — and CI posts a cost diff on every infra PR, failing large regressions like a benchmark test.

---

## Summary

- FinOps = visibility → optimization → operation, owned jointly by finance and engineering.
- Rightsizing from percentile utilization is the highest-leverage first pass.
- Storage tiering needs lifecycle automation and retrieval-fee awareness.
- Spot saves 60-90% only for checkpointable, stateless-shaped work.
- Allocation (tags → showback → chargeback) precedes meaningful optimization.
- Unit economics turn invoices into engineering metrics; CI cost diffs prevent regressions like any other test.

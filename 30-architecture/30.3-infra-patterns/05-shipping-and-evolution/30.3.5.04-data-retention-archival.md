# Data Retention & Archival

A deletion job reports success, but a restore later brings the same customer's data back. The live row was removed; a backup or replay path was never part of the deletion boundary:

```text
DELETE succeeds → restore brings the row back. The backup wasn't in the deletion boundary.
```

## Definition

**Retention** defines how long each class of information is kept and when it may or must be deleted. **Archival** moves retained information into a store chosen for its access, integrity, and retrieval requirements. Moving bytes never shortens their retention or removes their protection obligations.

> **Textbook Definition:** Data retention defines how long information is kept and when it is deleted; archival moves retained information to storage with explicit retrieval, integrity and access requirements.

## First Principles

Data is copied into indexes, logs, exports, analytics, backups, and downstream processors or recipients. Removing one live row never removes these copies. A source event can also be replayed after deletion and recreate the data unless the ingestion/recovery path respects its lifecycle.

Some information must remain available while other information must expire. Those requirements attach to purpose, data class, subject, and applicable obligations, not one global table age. Deletion, legal holds, archival, and restores therefore need a shared authority and evidence protocol.

## 1. Write the policy before the schedule

For each data class, record its owner and purpose, every storage location and copy, governing policy, clock origin, retention and hold rules, access controls, deletion method, retrieval objective, and verification evidence. A clock can start at creation, account closure, or another defined event; "90 days" is ambiguous without it.

Retention rules for telemetry, financial records, clinical records, and raw customer uploads require separate analysis. For example, the Health Insurance Portability and Accountability Act (HIPAA) requires six-year retention for specified Security Rule documentation; its Privacy Rule sets no general medical-record retention period, which may be governed by state law. The actual record, jurisdiction, and obligation matter.

Choose telemetry retention from incident-response and trend-analysis needs, balanced against data risk. Raw high-resolution signals, downsampled metrics, and selected exemplars serve different purposes; sampling/downsampling never automatically anonymizes identifiers. Example retention durations are policy inputs to review, not universal standards.

## 2. Separate storage class from data lifecycle

```text
source/derived copies → approved retained archive → permitted expiry/deletion
                              │                         │
                              └→ catalog/restore path  └→ hold + deletion evidence
```

Hot/warm/cold describe expected access, not a precise price ratio or fixed delay. In Amazon Simple Storage Service (Amazon S3), Glacier Instant Retrieval supports real-time, millisecond reads; Glacier Flexible Retrieval and Deep Archive require a restore request, and retrieval time depends on the selected tier. Model retrieval, request, transition, and minimum-duration charges against the actual retrieval objective.

This valid Amazon S3 lifecycle **configuration example** transitions and expires current objects under one prefix. It is no complete deletion/hold protocol: versioned buckets need expiration rules for noncurrent versions and delete markers, and current size-eligibility and minimum-duration charges may affect transitions. Locked versions can remain protected. Confirm policy before applying it:

```json
{
  "Rules": [{
    "ID": "click-events-lifecycle",
    "Status": "Enabled",
    "Filter": { "Prefix": "events/clicks/" },
    "Transitions": [
      { "Days": 30, "StorageClass": "STANDARD_IA" },
      { "Days": 180, "StorageClass": "GLACIER_IR" }
    ],
    "Expiration": { "Days": 1095 }
  }]
}
```

In a versioned bucket, Amazon S3 current-version expiration can create a delete marker while older bytes remain. A successful configuration or elapsed policy age never proves every object was physically removed. Inspect relevant versions and hold status, and verify that asynchronous actions completed.

## 3. Treat database expiry as cleanup, not authorization

| Mechanism | Boundary |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL scheduled `DELETE` | Batch to bound locks and write-ahead log (WAL) volume; vacuum later reclaims dead tuples, but neither covers other copies |
| Time partition removal | Efficient whole-range operation; locks, dependencies and held rows still matter |
| MongoDB time-to-live (TTL) index | Background deletion, not exact expiry at every document's timestamp |
| DynamoDB TTL | Eventual removal; application must exclude expired data when immediate visibility/access expiry matters |
| Redis expiry | Cache-key lifetime under server/persistence behavior; not a durable all-system deletion certificate |

An automatic sweeper can lag. If data must stop being accessible at a deadline, enforce that deadline at the request boundary; never wait for asynchronous physical removal.

Dropping an old partition is useful only when **all** its rows may be removed. A single held row may require a different physical organization or an authorized copy/hold protocol. Partition data definition language (DDL) can wait on locks; it is never universally instant or lock-free. Date partitioning also holds routing, uniqueness, and query tradeoffs; see [Database Scaling](../04-data-at-scale/30.3.4.01-database-scaling.md).

## 4. Serialize holds with deletion

A deletion worker can read "no hold," then a hold arrives before its destructive action. A check without a shared serialization boundary leaves a race. Define an authority ordering hold/release and deletion claims; revalidate at commit/action boundaries and stop or reconcile remote work already submitted.

Object Lock retention and legal holds, storage lifecycle rules, and database hold metadata use different application programming interfaces (APIs). Amazon S3 Object Lock protects specific versions; a lifecycle rule can still add a delete marker, and it can expire other eligible, unprotected versions or copies. Record hold scope and authorized release, test held items across every store, and account for changes made by administrators outside the ordinary worker.

Transactions can serialize local metadata but cannot include a remote lifecycle engine. Amazon S3 documents that a new or updated lifecycle configuration can take a few minutes to propagate; eligible transitions and expirations are then processed asynchronously and can take days or weeks. Inspect the effective configuration and reconcile actions submitted during that window. Use a storage-native hold where possible.

An audit log can be append-only while current hold state changes under authorized events. Calling the entire mutable hold table "immutable" obscures that transition. Removing a hold should resume the applicable policy, not mean "delete everything immediately."

## 5. Run erasure as a request-and-recovery workflow

For an applicable privacy request, recognize the request even if the person never uses legal phrasing; confirm identity when necessary and ask only for proportionate evidence. Then have the policy owner determine scope, lawful retention exceptions, and deadlines.

In the United Kingdom (UK), the Information Commissioner's Office (ICO) says to respond without undue delay and within **one calendar month**; this is a response deadline, not a universal deadline to physically erase every copy. A complex request or several requests from one person may extend the response period by up to two months if the person is told within the first month.

The ICO flags this guidance for review after the Data (Use and Access) Act, so check its current applicability before encoding a deadline. This UK guidance is no universal General Data Protection Regulation (GDPR) or California Consumer Privacy Act (CCPA) "delete all copies within 30 days" rule:

```text
verified request → scoped policy decision → durable work per store and recipient
                                                   │
              live data / indexes / exports / analytics / backups / processors
                                                   ▼
                  outcome + exceptions / retry / verification for each boundary
```

Where an applicable rule requires contacting recipients or other controllers, track that notice and its outcome alongside each deletion action.

Redacting a name while retaining identifiers, relationships, and rare attributes may still leave identifiable data. A keyed hash using a hash-based message authentication code (HMAC) may create a stable **pseudonym**; it is pseudonymization, not automatic erasure or anonymization, and can remain linkable. In k-anonymity, each combination of quasi-identifiers — attributes identifying when combined, such as age band and postal district — appears in at least *k* records. This limits uniqueness in the release but never rules out re-identification using other data or context.

Backups need their own approved lifecycle and beyond-use/restore handling where applicable. ICO guidance allows inaccessible backup copies to await overwrite under an established schedule when they are kept beyond use; never reuse them for another purpose. Restore pipelines must reapply still-active deletion and hold decisions before exposing or dispatching recovered data.

**Cryptographic erasure** removes the ability to decrypt selected ciphertext by destroying required keys. It works only if encryption was appropriate, every relevant plaintext/key copy is covered, and no retained or recoverable key still permits decryption. Per-subject data-encryption keys (DEKs) can enable finer scope; a shared key can also erase unrelated users. The scheduled deletion and recovery path of each cloud key-management service (KMS), its backed-up wrapped keys, and cached copies must all be included. Key destruction is no universal legal answer or proof that all derived plaintext vanished.

## 6. Trace one archived dataset end to end

1. Select a closed source range and freeze/capture changes under the archive consistency contract.
2. Export required fields with schema/version and safe access controls. Record source position, count, business invariants, and trusted checksums.
3. Store the archive/catalog/key references under the approved retention/hold policy. A folder name and successful upload never prove its readability.
4. Read/load the archive into an isolated environment and check meaning, not only a few bytes. Prove the retrieval time required by consumers.
5. Remove source data only after verified coverage and a serialized permitted-deletion decision. Partial export must never authorize dropping the whole source partition.
6. Retain compatible readers or a format-migration plan; archives can outlive application code and key infrastructure.
7. Expire all eligible versions/copies under the policy, track failed actions, and verify bounded residual data. Reconcile restored/backfilled copies so deletion is never undone.

A completion ledger records what action and verification occurred, along with pending work/exceptions. It is useful evidence but never proves full legal compliance by itself. Protect the ledger's identifiers and retain only what its own policy requires.

## Common Mistakes

| Mistake | Repair |
| ---------------------------------------------- | ---------------------------------------------------------------------------- |
| Soft delete described as erasure | Follow the documented physical/logical/key lifecycle across copies |
| HMAC identifiers called anonymous | Assess retained linkability and data context |
| Expire current object only | Include relevant versions/markers/locked copies |
| Checking hold once before a long task | Order hold/deletion through an authority and revalidate at action boundaries |
| Restore recreates previously deleted records | Apply the active deletion/hold ledger before reuse |
| Backup key copy survives cryptographic erasure | Inventory and validate all decryption paths and plaintext copies |

## Summary

Retention is a per-class policy across every copy and recovery path. Archival needs readable, verified history; expiry mechanisms have different timing and version behavior. Serialize holds with destructive actions, distinguish pseudonymization from erasure, and verify deletion/key/restore outcomes under the applicable policy rather than treating one database DELETE as completion.

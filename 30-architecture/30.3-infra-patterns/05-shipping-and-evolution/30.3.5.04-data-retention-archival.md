# Data Retention & Archival

## Definition

**Retention** defines how long each class of information is kept and when it may or must be deleted. **Archival** moves retained information into a store chosen for its access, integrity and retrieval requirements. Moving bytes does not shorten their retention or remove their protection obligations.

> **Textbook Definition:** Data retention defines how long information is kept and when it is deleted; archival moves retained information to storage with explicit retrieval, integrity and access requirements.

## First Principles

Data is copied into indexes, logs, exports, analytics and backups. Removing one live row does not remove these copies. A source event can also be replayed after deletion and recreate the data unless the ingestion/recovery path respects its lifecycle.

Some information must remain available while other information must expire. Those requirements are attached to purpose, data class, subject and applicable obligations, not one global table age. Deletion, legal holds, archival and restores therefore need a shared authority and evidence protocol.

## Write the Policy Before the Schedule

For each data class record owner, purpose, location/copies, applicable policy, clock origin, retention/hold rules, access and deletion method, retrieval objective and verification. A clock can start at creation, account closure or another defined event; “90 days” is ambiguous without it.

Telemetry, financial records, clinical records and raw customer uploads need different analysis. Do not reuse shorthand such as “HIPAA six years” or “all financial data seven years” as a general row-retention rule. The actual record, jurisdiction and obligation matter.

Choose observability history from incident/trend needs and data risk. Raw high-resolution signals, downsampled metrics and selected exemplars serve different purposes; sampling/downsampling does not automatically anonymize identifiers. Example retention durations are policy inputs to review, not universal standards.

## Separate Storage Class From Data Lifecycle

```text
source/derived copies → approved retained archive → permitted expiry/deletion
                              │                         │
                              └→ catalog/restore path  └→ hold + deletion evidence
```

Hot/warm/cold describe expected access, not a precise price ratio or fixed delay. S3 Glacier Instant Retrieval permits immediate reads; Flexible Retrieval and Deep Archive use restore workflows under their selected retrieval tiers. Model retrieval/request/transition/minimum-duration charges and the actual recovery objective.

This valid S3 lifecycle **configuration example** transitions and expires current objects under one prefix. It is not a complete deletion/hold protocol: versioned buckets need noncurrent-version/delete-marker policy, eligible object sizes/minimum charging apply, and locked versions can remain protected. Confirm policy before applying it.

```json
{
  "Rules": [{
    "ID": "click-events-lifecycle",
    "Status": "Enabled",
    "Filter": { "Prefix": "events/clicks/" },
    "Transitions": [
      { "Days": 30, "StorageClass": "STANDARD_IA" },
      { "Days": 180, "StorageClass": "GLACIER_IR" }
    ],
    "Expiration": { "Days": 1095 }
  }]
}
```

S3 current-version expiration in a versioned bucket can create a delete marker while older bytes remain. Submission and policy age do not prove every object has physically disappeared. List/verification evidence must include relevant versions, holds and asynchronous execution.

## Database Expiry Is Not an Authorization Clock

| Mechanism | Boundary |
| --------------------------- | ------------------------------------------------------------------------------------------------------- |
| PostgreSQL scheduled DELETE | Batch/lock/vacuum/WAL work; deleting a row is not all-copy sanitization |
| Time partition removal | Efficient whole-range operation; locks, dependencies and held rows still matter |
| MongoDB TTL index | Background deletion, not exact expiry at every document's timestamp |
| DynamoDB TTL | Eventual removal; application must exclude expired data when immediate visibility/access expiry matters |
| Redis expiry | Cache-key lifetime under server/persistence behavior; not a durable all-system deletion certificate |

An automatic sweeper can lag. Enforce credential/access expiry at the request boundary using the trusted authorization clock/policy, rather than assuming physical removal happens exactly then.

Dropping an old partition is useful only when **all** its rows may be removed. A single held row may require a different physical organization or an authorized copy/hold protocol. Partition DDL can wait on locks; it is not universally instant/no-lock. Date partitioning also has routing, uniqueness and query tradeoffs; see [Database Scaling](../04-data-at-scale/30.3.4.01-database-scaling.md).

## Serialize a Hold With Deletion

A deletion worker can read “no hold,” then a hold arrives before its destructive action. A check without a shared serialization boundary leaves a race. Define an authority that orders hold/release and deletion claims; revalidate at commit/action boundaries and stop or reconcile remote work that was already submitted.

Object-lock retention/legal hold, storage lifecycle and database hold metadata have different APIs. A lifecycle filter that does not encode the hold contract can continue deleting eligible unprotected copies. Record scope and authorized release, test held items across every store, and account for changes made by administrators outside the ordinary worker.

An audit log can be append-only while current hold state changes under authorized events. Calling the entire mutable hold table “immutable” obscures that transition. Removing a hold should resume the applicable policy, not mean “delete everything immediately.”

## Erasure Is a Request-and-Recovery Workflow

For applicable privacy rights, verify the request/identity and have the responsible policy owner determine scope, lawful retention exceptions and deadlines. UK ICO guidance describes response without undue delay and ordinarily within **one month**, with documented conditions/extensions; that is not a universal GDPR/CCPA “delete all copies within 30 days” rule.

```text
verified request → scoped policy decision → durable deletion work per store
                                                │
                     live data / indexes / exports / analytics / backup lifecycle
                                                ▼
                     per-store outcome + remaining exceptions/retry/verification
```

Redacting a name while retaining identifiers, relationships and rare attributes may still leave identifiable data. A keyed pseudonym/HMAC is **pseudonymization**, not automatic erasure or anonymization; it can remain linkable. Aggregation and k-anonymity labels also do not prove re-identification is impossible under the actual data/context.

Backups need their own approved lifecycle and beyond-use/restore handling where applicable. ICO guidance permits context-dependent handling while inaccessible backup copies await scheduled overwrite; do not reuse them for another purpose. Restore pipelines must apply still-valid deletion/hold decisions before exposing or dispatching recovered data.

**Cryptographic erasure** removes the ability to decrypt selected ciphertext by destroying required keys. It works only if encryption was appropriate, every relevant plaintext/key copy is covered, and no retained/recoverable key still permits decryption. Per-subject data-encryption keys can enable finer scope; a shared key can also erase unrelated users. KMS scheduling, backed-up wrapped keys and cache copies must be included. Key destruction is not a universal legal answer or proof that all derived plaintext vanished.

## Trace One Archived Dataset

1. Select a closed source range and freeze/capture changes under the archive consistency contract.
2. Export required fields with schema/version and safe access controls. Record source position, count, business invariants and trusted checksums.
3. Store the archive/catalog/key references under the approved retention/hold policy. A folder name and successful upload do not prove its readability.
4. Read/load the archive into an isolated environment and check meaning, not only a few bytes. Prove the retrieval time required by consumers.
5. Remove source data only after verified coverage and a serialized permitted-deletion decision. Partial export must never authorize dropping the whole source partition.
6. Retain compatible readers or a format-migration plan; archives can outlive application code and key infrastructure.
7. Expire all eligible versions/copies under the policy, track failed actions and verify bounded residual data. Reconcile restored/backfilled copies so deletion is not undone.

A completion ledger records what action and verification occurred, along with pending work/exceptions. It is useful evidence but does not prove full legal compliance by itself. Protect the ledger's identifiers and retain only what its own policy requires.

## Common Mistakes

| Mistake | Repair |
| ---------------------------------------------- | ---------------------------------------------------------------------------- |
| Soft delete described as erasure | Follow the documented physical/logical/key lifecycle across copies |
| HMAC identifiers called anonymous | Assess retained linkability and data context |
| Expire current object only | Include relevant versions/markers/locked copies |
| Checking hold once before a long task | Order hold/deletion through an authority and revalidate at action boundaries |
| Restore recreates previously deleted records | Apply the active deletion/hold ledger before reuse |
| Backup key copy survives cryptographic erasure | Inventory and validate all decryption paths and plaintext copies |

## Summary

Retention is a per-class policy across every copy and recovery path. Archival needs readable, verified history; expiry mechanisms have different timing and version behavior. Serialize holds with destructive actions, distinguish pseudonymization from erasure, and verify deletion/key/restore outcomes under the applicable policy rather than treating one database DELETE as completion.

# Data Retention & Archival


---

> **Data that lives forever costs forever — and leaks forever.** Retention tiers for logs/metrics/traces, hot-warm-cold storage, TTL strategies in databases, legal hold, deletion pipelines for right-to-erasure, and archival runbooks: the operational half of data lifecycle management.

---

## Definition

**Data retention and archival** is the set of policies and mechanisms that decide how long each class of data lives in its fast store, where it goes when it leaves, and when it is destroyed — a **legal requirement** (GDPR erasure, sector retention mandates) that is simultaneously a **cost** and **performance** decision.

```text
hot      (queryable in ms, transactional)  ─▶ weeks–months
warm     (queryable in seconds, analytical) ─▶ months–1 year
cold     (restore in hours, object storage) ─▶ years (compressed, immutable)
purge    (crypto-shredded / deleted)        ─▶ per policy or erasure request
```

Three constraints define a correct design. First, **retention is per data class, not global** — access logs, financial records, and user-generated content have different legal clocks, so the policy must be expressed per table/stream. Second, **archival must preserve reconstructability**: moving rows to cold storage is only safe if a restore path exists (a partition-pruned table, a documented schema) and the archive is format-stable for years. Third, and most often missed: **deletion is an obligation, not a table scan** — a `DELETE` on the primary leaves copies in backups, caches, search indexes, and analytics warehouses, so an erasure request must be implemented as a *path through every store*, and where the data cannot be selectively deleted (immutable backups), the industry answer is **crypto-shredding**: encrypt per-user, destroy the key.

## First Principles

Retention follows from storage growth being unbounded without policy:

1. **Data has a lifecycle, and every stage has different access patterns** — hot (query often), warm (occasional), cold (audit only). Tiering to cheaper storage as access decays is the economics; keeping everything hot is the default failure.
2. **Retention is legal + product policy, not engineering preference**: GDPR deletion, financial record-keeping, and product needs (recovery, analytics) set the windows — engineering implements and *automates* them.
3. **Deletion must be real**: soft-delete (→ 20.4.5.03) keeps rows; retention policy must eventually *purge* — including backups and replicas (the hard part everyone discovers late). Tombstones (→ 20.4.5.03) interact with this directly.

## The Problem

```
Year 1:  200 GB of events. Queries fast, storage cheap.
Year 3:  40 TB. Slow queries, $30k/month storage, GDPR erasure request
         arrives for a user whose data is spread across 14 systems,
         and legal needs ONE table frozen for litigation.
```

Without explicit retention policy, every system defaults to "keep everything" — which fails three ways simultaneously: unbounded cost, degraded query performance, and compliance exposure (data you cannot find or delete is data you still owe protection for).

## Policy Drivers

| Driver | What it demands | Typical shape |
| -------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------- |
| **Legal/compliance** | Minimum AND maximum retention (GDPR storage limitation; SOX 7y financial records; HIPAA 6y) | Per-data-class schedule, auditable |
| **Cost** | Pay only for access you actually use | Tiering + expiry |
| **Debuggability** | Enough history to diagnose incidents and trends | Hot: days-weeks; warm: months |
| **Security** | Minimize breach blast surface; old PII = old liability | Aggressive PII expiry, crypto-shredding |

Design tension to name out loud: debuggability wants MORE history, security wants LESS. Resolve by keeping long-lived data **aggregated/pseudonymized** and short-lived data raw.

## Observability Retention Tiers

| Signal | Hot (queryable, full res) | Warm (queryable, downsampled) | Cold (archive) |
| ----------------- | ----------------------------- | ----------------------------- | ------------------------- |
| Application logs | 7-14 days | 90 days (error+warn only) | 1 year compressed |
| Access/audit logs | 30 days | 1 year | Per regulation (often 7y) |
| Metrics | 15-30d raw (e.g., 10s scrape) | 13 months at 5m rollup | rarely needed |
| Traces | 3-7 days sampled | none | exemplars only |
| Security events | 90 days | 2 years | per policy (1-7y) |

Rationale: incident diagnosis needs minutes-to-days of high resolution; trend analysis needs months of coarse resolution; almost nothing legitimately queries a random trace from last spring.

## Hot / Warm / Cold Storage

Object-storage classes make tiering concrete:

| Class (S3 naming) | Latency | Storage $/GB-mo (relative) | Retrieval fee |
| --------------------------- | ------------- | -------------------------- | ------------------- |
| Standard (hot) | ms | 1x | none |
| Standard-IA (warm) | ms | ~0.4x | per-GB retrieved |
| Glacier Instant | ms | ~0.25x | per-GB retrieved |
| Glacier Flexible | minutes-hours | ~0.05x | higher, per-request |
| Glacier Deep Archive (cold) | up to 48h | ~0.02x | highest |

Lifecycle automation does the work:

```json
{
  "Rules": [{
    "id": "click-events-lifecycle",
    "filter": { "prefix": "events/clicks/" },
    "transitions": [
      { "days": 30,  "storage_class": "STANDARD_IA" },
      { "days": 180, "storage_class": "GLACIER_IR" }
    ],
    "expiration": { "days": 1095 }
  }]
}
```

Two rules of hard experience:

1. Partition append-only data by date so tier/expiry moves whole partitions, never row-hunts.
2. Compute the retrieval math before tiering anything queried by dashboards — warm-tier fees on daily queries erase savings instantly.

## TTL Strategies in Databases

| Store | Mechanism | Notes |
| ---------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------- |
| PostgreSQL | `pg_cron` delete jobs; DROP PARTITION by range | Partition drop is O(1)-ish metadata op — design tables partitioned-by-time from day one |
| MongoDB | TTL index `expireAfterSeconds` | Background sweeper (~60s granularity); not exact timing |
| DynamoDB | TTL attribute | Free, but deletion is *eventual* (may take days); do not treat as authorization |
| Cassandra | Per-row/column TTL | First-class; beware tombstone accumulation on mass expiry |
| Redis | `EXPIRE` / lazy+active eviction | Exact enough for sessions/cache; persistence choices affect durability of "expired" semantics |

PostgreSQL pattern — partition + scheduled drop:

```sql
CREATE TABLE events (
  id BIGINT GENERATED ALWAYS AS IDENTITY,
  occurred_at TIMESTAMPTZ NOT NULL,
  payload JSONB
) PARTITION BY RANGE (occurred_at);

-- retention = 90 days: dropping a partition is instant vs DELETE's vacuum storm
DROP TABLE IF EXISTS events_2026_05;  -- run monthly by pg_cron/scheduler

SELECT cron.schedule('drop-old-events', '0 3 1 * *', $$
  SELECT drop_partitions_before('events', now() - interval '90 days')
$$);
```

Deleting rows with `DELETE` at scale bloats tables and floods WAL; time-partitioning converts retention into cheap DDL.

## Legal Hold

When litigation or investigation lands, normal retention must freeze for identified data:

1. **Hold flag** per matter: `legal_hold` markers on custodians/accounts/data ranges, stored with audit trail.
2. Deletion pipelines check holds BEFORE expiring anything: `if (holds.matches(record)) skipAndLog();`
3. Suspends apply across the estate — object-store lifecycle rules need exceptions too (separate prefix/bucket under hold, or lifecycle rule gated on tag).
4. Release process mirrors imposition: documented, authorized, dated — releasing early is spoliation; never deleting after release is the old cost problem back.

Practical shape: an immutable `legal_holds` table (matter_id, scope, imposed_at, released_at) consulted by every deletion job; plus quarterly reconciliation proving held items still exist.

## Deletion Pipelines & Right-to-Erasure

GDPR Art. 17 / CCPA make "delete user X everywhere within 30 days" an engineering requirement:

```text
Erasure request flow:
request verified ──▶ enqueue ErasureRequest(userId)
                        │
             ┌──────────┼─────────────┬──────────────┐
             ▼          ▼             ▼              ▼
        orders svc   logs pipeline   metrics     backups(!)
        anonymize    rewrite/expire  hash-salt   key destruction
             │          │             │              │
             └──────────┴─────────────┴──────────────┘
                        ▼
            completion ledger + receipt to requester
```

Techniques per store type:

1. **Transactional stores** — anonymize rather than delete where foreign keys demand it (`name='REDACTED'`, keep invoice totals for accounting law). Document that legal basis.
2. **Logs** — store a keyed pseudonym (HMAC(userId, secret)) instead of raw IDs; erasure becomes impossible-by-design for hot logs, and key rotation handles old ones.
3. **Derived/aggregated stores** — aggregates that cannot be inverted are generally exempt; ensure aggregation really destroys individual values (k-anonymity thresholds).
4. **Backups** — you cannot surgically edit a backup image. Accepted answers:
   - **Crypto-shredding**: encrypt per-user fields with per-user DEKs stored in KMS; erasure = destroy the DEK. Backups remain encrypted blobs without plaintext.
   - Restore-and-purge before any reuse beyond the erasure SLA window; document the bounded lifetime.
5. **Completion tracking** — a ledger of (requestId, system, status, completed_at) proves compliance when regulators ask.

Idempotency note: deletion workers must tolerate replays — same dedupe-key discipline as any other event processor.

## Archiving Runbook Template

```text
ARCHIVE RUNBOOK — <dataset>           Owner: <team>   Last verified: <date>

SCOPE
  Source:            <db/table or bucket/prefix>
  Volume estimate:   <rows / GB per month>
  Retention class:   <regulation / internal policy ref>
  Hot duration:      <N days>   Cold until: <date-rule>   Then: DELETE

PROCEDURE
  1. Export partition range to Parquet/CSV (schema versioned!)   [cmd]
  2. Checksum + write manifest {range, count, sha256, schema_v}  [cmd]
  3. Upload to cold bucket with lock mode + retention until date  [cmd]
  4. Verify round-trip: byte count, spot-read sample rows         [cmd]
  5. Record archive entry in catalog                              [link]
  6. Drop source partition                                        [cmd]
  7. Update data map (what lives where, until when)

RESTORE PATH
  Request template -> ticket -> thaw (eta ___h) -> load into <sandbox>
  Owner sign-off required: <role>

VERIFICATION CADENCE
  Quarterly: read 3 random archives fully (bit rot / format drift check)
```

The schema-version field matters more than people expect: archives outlive services, and Parquet from 2031 must be readable by tooling that has never heard of your 2026 service.

## Common Mistakes

| Mistake | Problem | Fix |
| ---------------------------------------- | ------------------------------------------------- | ------------------------------------------ |
| "Keep everything" default | Cost + breach surface + can't-comply-with-erasure | Explicit per-class schedules |
| Row-level DELETE for big tables | Vacuum storms, WAL flood, slow sweeps | Time-partitioned DROP |
| Dashboards reading warm/cold tiers | Retrieval fees exceed storage savings | Keep hot rollups for queries |
| Treating DB TTL as exact/deletion-proof | DynamoDB TTL is eventual days | Not for compliance-critical timing |
| Erasure ignores derived data | Regulator finds user in aggregates/export buckets | Map ALL copies incl. exports & caches |
| Backups exempt from privacy thinking | Deleted user resurrected by restore | Crypto-shredding or bounded restore policy |
| Archives without schema/version metadata | Unreadable in five years | Manifest with schema version + checksums |
| No legal-hold plumbing | Litigation meets auto-expiry | Holds checked before every deletion path |

## Interview Tips

- Lead with drivers: retention is set by legal minimums, security maximums, and cost curves — engineering implements the intersection.
- For erasure questions, show you know backups: crypto-shredding (per-user encryption keys destroyed) is the senior answer; "we re-delete after each restore" is the honest fallback.
- Quantify: observability tiers (raw days → rollup months), S3 class ratios (~50x hot-to-deep-archive), partition-drop vs DELETE tradeoff.
- Mention the completion ledger — proof-of-deletion is what auditors actually request.

## 30-Second Interview Version

> I define per-data-class schedules balancing legal minimums, security maximums, and cost; implement them with time-partitioned drops and object-store lifecycles across hot/warm/cold classes; keep observability in tiers — days of raw signal, months of downsampling. For right-to-erasure I prefer pseudonymized IDs plus crypto-shredding so backups comply by key destruction, with a completion ledger proving each request finished. Legal hold hooks sit in front of every deletion path.

## Summary

- Retention policy = legal floor ∧ security ceiling ∩ debuggability ∩ cost curve — written per data class, enforced automatically.
- Observability lives in tiers: raw for days, downsampled for months, archived per regulation.
- Storage tiering pays only with lifecycle automation and retrieval-aware query placement.
- In databases, partition-drop beats row-delete for scale; TTL features differ wildly in exactness.
- Right-to-erasure is a distributed-systems problem: transactional redaction, log pseudonymization, aggregate exemption, crypto-shredded backups, and a provable completion ledger.
- Legal hold suspends everything above — build the hook before the subpoena.

# Saga Pattern — Orchestration vs Choreography, Compensating Transactions

## What is a Saga?

A Saga is a sequence of local transactions where each step publishes events that trigger the next step. If any step fails, compensating transactions undo the previous steps.

### Why Sagas?

```
Problem: Distributed transactions (2PC) are:
  - Slow (two-phase commit)
  - Blocking (locks held during commit)
  - Fragile (coordinator is SPOF)
  
Solution: Saga
  - Each step is a local transaction
  - Steps communicate via events
  - Failures trigger compensating transactions
  - No distributed locks
```

## Two Saga Patterns

### 1. Choreography (Event-Driven)

Each service publishes events and listens for events. No central coordinator.

```
┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐
│ Service  │────▶│ Service  │────▶│ Service  │────▶│ Service  │
│    A     │     │    B     │     │    C     │     │    D     │
└─────────┘     └─────────┘     └─────────┘     └─────────┘
     │               │               │               │
     ▼               ▼               ▼               ▼
  Event A         Event B         Event C         Event D
  published       published       published       published
```

**Example: Appointment Booking**

```
1. API: Create appointment → Publish APPOINTMENT_CREATED
2. Notification Service: Listen → Send confirmation email → Publish NOTIFICATION_SENT
3. Billing Service: Listen → Create invoice → Publish INVOICE_CREATED
4. Analytics Service: Listen → Track booking → Publish EVENT_TRACKED

If any step fails:
  - Notification fails → Compensate: cancel appointment
  - Billing fails → Compensate: cancel notification, cancel appointment
```

### 2. Orchestration (Central Coordinator)

A central orchestrator controls the sequence of steps.

```
┌─────────────────────────────────────┐
│           Orchestrator              │
│  ┌─────────────────────────────┐   │
│  │ 1. Call Service A           │   │
│  │ 2. Call Service B           │   │
│  │ 3. Call Service C           │   │
│  │ 4. If any fails → Compensate│   │
│  └─────────────────────────────┘   │
└─────────────────────────────────────┘
         │       │       │
         ▼       ▼       ▼
      ┌─────┐ ┌─────┐ ┌─────┐
      │  A  │ │  B  │ │  C  │
      └─────┘ └─────┘ └─────┘
```

**Example: Appointment Booking**

```typescript
class AppointmentSaga {
  async execute(dto: BookAppointmentDto): Promise<void> {
    const steps: SagaStep[] = [
      {
        name: 'createAppointment',
        execute: async () => {
          const apt = await this.appointmentService.create(dto);
          return { appointmentId: apt.id };
        },
        compensate: async (ctx) => {
          await this.appointmentService.cancel(ctx.appointmentId);
        },
      },
      {
        name: 'sendNotification',
        execute: async (ctx) => {
          await this.notificationService.send(ctx.appointmentId);
        },
        compensate: async (ctx) => {
          await this.notificationService.cancel(ctx.appointmentId);
        },
      },
      {
        name: 'createInvoice',
        execute: async (ctx) => {
          await this.billingService.createInvoice(ctx.appointmentId);
        },
        compensate: async (ctx) => {
          await this.billingService.cancelInvoice(ctx.appointmentId);
        },
      },
    ];
    
    const context: SagaContext = {};
    
    for (let i = 0; i < steps.length; i++) {
      try {
        const result = await steps[i].execute(context);
        Object.assign(context, result);
      } catch (error) {
        // Compensate previous steps in reverse order
        for (let j = i - 1; j >= 0; j--) {
          await steps[j].compensate(context);
        }
        throw error;
      }
    }
  }
}
```

## Choreography vs Orchestration

| Aspect | Choreography | Orchestration |
|--------|-------------|---------------|
| **Coupling** | Loose (event-based) | Tight (knows all services) |
| **Complexity** | Distributed | Centralized |
| **Visibility** | Hard to trace | Easy to trace |
| **Failure handling** | Each service compensates | Orchestrator compensates |
| **Scalability** | Good (independent services) | Good (orchestrator scales) |
| **Use case** | Simple workflows | Complex, multi-step workflows |

## Compensating Transactions

Compensating transactions undo the effects of previous steps. They don't literally reverse the database changes — they bring the system to an equivalent state.

### Examples

| Step | Compensating Transaction |
|------|-------------------------|
| **Create appointment** | Cancel appointment |
| **Send email** | Send cancellation email |
| **Charge credit card** | Issue refund |
| **Reserve inventory** | Release inventory |

### Implementation

```typescript
// Saga step with compensation
interface SagaStep {
  name: string;
  execute: (context: SagaContext) => Promise<any>;
  compensate: (context: SagaContext) => Promise<void>;
}

// Saga executor
class SagaExecutor {
  async execute(steps: SagaStep[]): Promise<void> {
    const completedSteps: SagaStep[] = [];
    const context: SagaContext = {};
    
    for (const step of steps) {
      try {
        const result = await step.execute(context);
        Object.assign(context, result);
        completedSteps.push(step);
      } catch (error) {
        // Compensate in reverse order
        for (const completedStep of completedSteps.reverse()) {
          try {
            await completedStep.compensate(context);
          } catch (compensationError) {
            // Log compensation failure (manual intervention needed)
            console.error(`Compensation failed for ${completedStep.name}:`, compensationError);
          }
        }
        throw error;
      }
    }
  }
}
```

## Saga vs 2PC (Two-Phase Commit)

| Aspect | Saga | 2PC |
|--------|------|-----|
| **Consistency** | Eventual | Strong |
| **Performance** | Better (no locks) | Worse (locks held) |
| **Complexity** | Higher (compensation) | Lower (coordinator) |
| **Availability** | Higher | Lower (coordinator SPOF) |
| **Use case** | Long-running workflows | Short, atomic transactions |

## Interview Tips

- **Q: When would you use choreography vs orchestration?**
  - Choreography: simple workflows, few services, loose coupling needed
  - Orchestration: complex workflows, many services, visibility needed

- **Q: How do you handle compensation failures?**
  - Log the failure
  - Alert on-call engineer
  - Manual intervention may be needed
  - Design compensations to be idempotent

- **Q: How do you ensure idempotency in sagas?**
  - Use idempotency keys per step
  - Check if step already completed before executing
  - Make compensations idempotent too

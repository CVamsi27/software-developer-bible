# API Gateway Patterns — Kong, Rate Limiting, Authentication, Routing

## What is an API Gateway?

An API Gateway is a single entry point for all client requests. It handles cross-cutting concerns like authentication, rate limiting, routing, and SSL termination.

### Why an API Gateway?

```
Without API Gateway:
  Client → API Service (auth, rate limit, routing)
  Client → Worker Service (auth, rate limit, routing)
  Client → Notification Service (auth, rate limit, routing)
  
  Problem: Each service duplicates auth, rate limiting, routing

With API Gateway:
  Client → Gateway (auth, rate limit, routing) → Services
  
  Solution: Cross-cutting concerns handled once
```

### Architecture

```
                    ┌─────────────────┐
                    │   API Gateway   │
                    │  (Kong / nginx) │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
         ┌────────┐    ┌────────┐    ┌────────┐
         │  API   │    │ Worker │    │  Notif │
         │Service │    │Service │    │Service │
         └────────┘    └────────┘    └────────┘
```

## Kong Configuration

### Route Configuration

```yaml
# Kong service
services:
  - name: docita-api
    url: http://api:3000
    routes:
      - name: api-v1
        paths:
          - /api/v1
        strip_path: false
        preserve_host: true
        protocols:
          - http
          - https

# Rate limiting plugin
plugins:
  - name: rate-limiting
    config:
      minute: 100
      policy: redis
      redis_host: redis
      redis_port: 6379

# Authentication plugin
  - name: jwt
    config:
      key_claim_name: iss
      secret_is_base64: false

# CORS plugin
  - name: cors
    config:
      origins:
        - "*"
      methods:
        - GET
        - POST
        - PUT
        - DELETE
      headers:
        - Authorization
        - Content-Type
```

### Rate Limiting Strategies

| Strategy | Description | Use Case |
|----------|-------------|----------|
| **Local** | Per-instance counter | Simple, not distributed |
| **Cluster** | Shared counter in DB | Accurate, slower |
| **Redis** | Shared counter in Redis | Fast, distributed |

### Authentication Flow

```
1. Client sends request with JWT
2. Gateway validates JWT signature
3. Gateway extracts user claims
4. Gateway forwards request to service with claims in headers:
   X-User-Id: abc
   X-Clinic-Id: 123
   X-User-Role: CLINICIAN
5. Service trusts gateway (no duplicate validation)
```

## Rate Limiting Implementation

### Redis Token Bucket

```typescript
// Kong custom plugin for rate limiting
const rateLimitPlugin: KongPlugin = {
  name: 'rate-limiting',
  handler: {
    async access(ctx) {
      const clientId = ctx.request.headers['x-client-id'];
      const key = `ratelimit:${clientId}`;
      
      const allowed = await redis.eval(TOKEN_BUCKET_SCRIPT, [key], [100, 1.67, Date.now()]);
      
      if (!allowed) {
        ctx.response = {
          status: 429,
          body: { error: 'Rate limit exceeded' },
          headers: { 'Retry-After': '60' },
        };
      }
    },
  },
};
```

### Rate Limit Headers

```typescript
// Always include rate limit headers
ctx.response.headers['X-RateLimit-Limit'] = '100';
ctx.response.headers['X-RateLimit-Remaining'] = '42';
ctx.response.headers['X-RateLimit-Reset'] = '1724300400';
```

## Routing Patterns

### Path-Based Routing

```yaml
routes:
  - paths:
      - /api/v1/patients
    service: patient-service
  - paths:
      - /api/v1/appointments
    service: appointment-service
  - paths:
      - /api/v1/notifications
    service: notification-service
```

### Header-Based Routing

```yaml
routes:
  - headers:
      - name: X-API-Version
        values:
          - "2"
    service: api-v2-service
  - headers:
      - name: X-API-Version
        values:
          - "1"
    service: api-v1-service
```

### Canary Deployment

```yaml
# 90% traffic to v1, 10% to v2
routes:
  - paths:
      - /api/v1
    service: api-v1-service
    plugins:
      - name: rate-limiting
        config:
          minute: 90
  
  - paths:
      - /api/v2
    service: api-v2-service
    plugins:
      - name: rate-limiting
        config:
          minute: 10
```

## Trade-offs

| Aspect | API Gateway | Direct Service Access |
|--------|-------------|----------------------|
| **Latency** | +1-5ms (gateway overhead) | Direct (no overhead) |
| **Complexity** | More infrastructure | Simpler |
| **Security** | Centralized auth | Distributed auth |
| **Rate Limiting** | Centralized | Per-service |
| **Routing** | Flexible | Hardcoded |
| **Monitoring** | Centralized | Distributed |

## Interview Tips

- **Q: When would you use an API Gateway?**
  - Multiple services with shared auth/rate limiting
  - Need for centralized monitoring/logging
  - Complex routing rules
  - SSL termination at edge

- **Q: What's the difference between API Gateway and Service Mesh?**
  - API Gateway: north-south traffic (client → service)
  - Service Mesh: east-west traffic (service → service)

- **Q: How do you handle gateway failures?**
  - Health checks on gateway
  - Fallback to direct service access
  - Circuit breaker on gateway

# Distributed Transactions — 2PC, Saga, TCC, Trade-offs

## What are Distributed Transactions?

A distributed transaction spans multiple services or databases. The challenge: how do you ensure all participants commit or all rollback?

### The Problem

```
Service A: Create appointment (PostgreSQL)
Service B: Send notification (SendGrid)
Service C: Create invoice (Stripe)

Problem: What if B succeeds but C fails?
  - Appointment created ✅
  - Notification sent ✅
  - Invoice NOT created ❌
  
  System is in inconsistent state
```

---

## Patterns

### 1. Two-Phase Commit (2PC)

Two-phase commit is a blocking protocol that ensures atomicity across distributed participants.

```
Phase 1: Prepare
  Coordinator asks all participants: "Can you commit?"
  Participants: "Yes, I can commit" (but don't commit yet)
  
Phase 2: Commit
  Coordinator: "Everyone said yes → COMMIT"
  Participants: Actually commit
  
If any participant says "No":
  Coordinator: "Someone said no → ROLLBACK"
  Participants: Rollback
```

**Implementation:**

```sql
-- PostgreSQL 2PC (distributed transaction)
BEGIN;
  -- Phase 1: Prepare
  PREPARE TRANSACTION 'appointment-123';
  
  -- Phase 2: Commit (after all participants prepare)
  COMMIT PREPARED 'appointment-123';
  
  -- Or rollback
  ROLLBACK PREPARED 'appointment-123';
```

**Trade-offs:**

| Aspect | 2PC | Saga |
|--------|-----|------|
| **Consistency** | Strong (ACID) | Eventual |
| **Performance** | Slow (blocking) | Fast (non-blocking) |
| **Availability** | Low (coordinator SPOF) | High |
| **Complexity** | Low (protocol handles it) | High (compensation) |
| **Use case** | Short, atomic transactions | Long-running workflows |

### 2. Saga Pattern

Saga breaks the distributed transaction into local transactions with compensating actions.

```
Step 1: Create appointment → Success
Step 2: Send notification → Success
Step 3: Create invoice → FAILS

Compensation:
  Step 2: Cancel notification → Success
  Step 1: Cancel appointment → Success

System is back to consistent state
```

**See 30.3.09-saga-pattern.md for detailed implementation.**

### 3. TCC (Try-Confirm-Cancel)

TCC is a three-phase pattern that separates reservation from confirmation.

```
Phase 1: Try (Reserve resources)
  - Reserve appointment slot
  - Reserve notification queue space
  - Reserve invoice amount
  
Phase 2: Confirm (Commit if all succeed)
  - Confirm appointment
  - Send notification
  - Create invoice
  
Phase 3: Cancel (Rollback if any fail)
  - Release appointment slot
  - Release notification queue space
  - Release invoice amount
```

**Implementation:**

```typescript
class AppointmentTCC {
  // Phase 1: Try (reserve resources)
  async try(dto: BookAppointmentDto): Promise<TCCContext> {
    // Reserve slot (pessimistic lock)
    const slot = await prisma.$transaction(async (tx) => {
      const slot = await tx.slot.findUnique({
        where: { id: dto.slotId },
        lock: { mode: 'pessimistic_write' },
      });
      
      if (slot.booked) {
        throw new ConflictException('Slot already booked');
      }
      
      return slot;
    });
    
    return { slotId: slot.id, reservationId: generateId() };
  }
  
  // Phase 2: Confirm (commit)
  async confirm(context: TCCContext): Promise<void> {
    await prisma.$transaction(async (tx) => {
      // Create appointment
      await tx.appointment.create({ data: { slotId: context.slotId } });
      
      // Mark slot as booked
      await tx.slot.update({
        where: { id: context.slotId },
        data: { booked: true },
      });
    });
  }
  
  // Phase 3: Cancel (rollback)
  async cancel(context: TCCContext): Promise<void> {
    // Release slot (remove pessimistic lock)
    // Lock is released automatically when transaction ends
  }
}
```

## Comparison

| Pattern | Consistency | Performance | Complexity | Use Case |
|---------|-------------|-------------|------------|----------|
| **2PC** | Strong | Slow | Low | Short, atomic transactions |
| **Saga** | Eventual | Fast | Medium | Long-running workflows |
| **TCC** | Strong | Medium | High | Resource reservation |

---

## When to Use Each

| Scenario | Pattern | Why |
|----------|---------|-----|
| **Bank transfer** | 2PC | Strong consistency required |
| **Appointment booking** | Saga | Long-running, compensation needed |
| **Hotel reservation** | TCC | Resource reservation needed |
| **E-commerce checkout** | Saga | Multiple services, eventual consistency OK |
| **Payment processing** | 2PC | Strong consistency required |

## Interview Tips

- **Q: What's the difference between 2PC and Saga?**
  - 2PC: Strong consistency, blocking, coordinator SPOF
  - Saga: Eventual consistency, non-blocking, compensation-based

- **Q: How do you handle compensation failures?**
  - Log the failure
  - Alert on-call engineer
  - Manual intervention may be needed
  - Design compensations to be idempotent

- **Q: What is TCC?**
  - Try: Reserve resources
  - Confirm: Commit if all succeed
  - Cancel: Rollback if any fail
  - Used for resource reservation scenarios

# Service Discovery

> **How services find each other in distributed systems — DNS, Consul, etcd, and Kubernetes patterns.**

---

## The Problem

In a microservice architecture, services scale independently. A service that needs to call another service can't hardcode an IP address — it changes every time a container restarts. Service discovery solves this: services register themselves and find each other dynamically.

```
Without Service Discovery:
Service A → hardcoded IP 10.0.1.5:3000 → Service B
If Service B moves to 10.0.1.6:3000 → Service A breaks ❌

With Service Discovery:
Service A → "Where is Service B?" → Registry → "10.0.1.6:3000" → Service A connects ✅
```

---

## Discovery Patterns

| Pattern | Description | Pros | Cons |
|---------|-------------|------|------|
| **Client-Side** | Client queries registry, picks instance | Simple, no extra hop | Client logic complexity |
| **Server-Side** | Load balancer queries registry, routes traffic | Client unaware | Extra infrastructure |
| **DNS-Based** | Service names resolve to IPs via DNS | Universal, no extra tools | Slow TTL propagation |
| **Mesh-Based** | Sidecar proxy handles discovery | Transparent to app | Resource overhead |

## Client-Side Discovery (Consul)

```
┌─────────────────────────────────────────────┐
│                  Consul Registry             │
│  ┌──────────────┐  ┌──────────────┐         │
│  │ user-service  │  │ appt-service │  ...    │
│  │ 10.0.1.5:3000│  │ 10.0.1.6:4000│         │
│  │ 10.0.1.7:3000│  │ 10.0.1.8:4000│         │
│  └──────────────┘  └──────────────┘         │
└──────────────────┬──────────────────────────┘
                   │
         ┌─────────┴─────────┐
         │                   │
   ┌─────┴─────┐       ┌────┴─────┐
   │  Service A │       │ Service B │
   │ (queries   │       │ (registers│
   │  Consul)   │       │  itself)  │
   └───────────┘       └──────────┘
```

```typescript
// Consul client-side discovery in NestJS
import { Consul } from 'consul';

const consul = new Consul({ host: 'consul.internal', port: 8500 });

// Register service
await consul.agent.service.register({
  name: 'appointment-service',
  id: 'appointment-service-1',
  address: '10.0.1.6',
  port: 4000,
  check: {
    http: 'http://10.0.1.6:4000/health',
    interval: '10s',
    timeout: '5s',
  },
  meta: {
    version: '1.2.0',
  },
});

// Discover other services
const services = await consul.health.service('user-service', {
  passing: true, // Only healthy instances
});

// Pick an instance (round-robin or random)
const instance = services[Math.floor(Math.random() * services.length)];
const url = `http://${instance.Service.Address}:${instance.Service.Port}`;
```

## DNS-Based Discovery

### Kubernetes Services

```yaml
# Kubernetes Service (auto-discovers pods)
apiVersion: v1
kind: Service
metadata:
  name: appointment-service  # DNS name
spec:
  selector:
    app: appointment-service
  ports:
    - port: 4000
  type: ClusterIP
```

```typescript
// In Kubernetes, services are discoverable via DNS
// From another pod:
const response = await fetch('http://appointment-service:4000/appointments');
// Kubernetes DNS resolves "appointment-service" to the service's ClusterIP
// kube-proxy load-balances across healthy pods
```

### Consul DNS Interface

```bash
# Consul also provides DNS interface
dig @127.0.0.1 -p 8600 user-service.service.consul SRV
# Returns: user-service.service.consul. 10 IN SRV 1 100 3000 user-1.node.dc1.consul.

# Use in app
const response = await fetch('http://user-service.service.consul:3000/users');
```

## etcd for Service Discovery

etcd is a distributed key-value store used by Kubernetes internally.

```typescript
import { Etcd3 } from 'etcd3';

const client = new Etcd3({ hosts: 'etcd.internal:2379' });

// Register service
await client.put('services/appointment-service/instance-1')
  .value(JSON.stringify({
    address: '10.0.1.6',
    port: 4000,
    healthy: true,
  }));

// Watch for changes
const watcher = await client.watch()
  .key('services/appointment-service/')
  .create();

watcher.on('put', (kv) => {
  console.log('Service updated:', kv.key.toString(), kv.value.toString());
});

watcher.on('delete', (kv) => {
  console.log('Service removed:', kv.key.toString());
});
```

## Health Checks

Every registered service must provide health checks. Registry removes unhealthy instances.

| Health Check Type | Description | Use Case |
|-------------------|-------------|----------|
| **HTTP** | GET /health returns 200 | Web services |
| **TCP** | Port is open | Databases, Redis |
| **gRPC** | gRPC health protocol | gRPC services |
| **TTL** | Service sends periodic heartbeats | Legacy services |
| **Script** | Run custom script | Complex checks |

```typescript
// NestJS Health Check
import { Controller, Get } from '@nestjs/common';
import { HealthCheck, HealthCheckService, PrismaHealthIndicator } from '@nestjs/terminus';

@Controller('health')
export class HealthController {
  constructor(
    private health: HealthCheckService,
    private prisma: PrismaHealthIndicator,
  ) {}

  @Get()
  @HealthCheck()
  check() {
    return this.health.check([
      () => this.prisma.pingCheck('database'),
    ]);
  }
}
```

## Interview Questions

**Q: "How do services find each other in Kubernetes?"**

> Kubernetes provides built-in service discovery: each Service gets a DNS name (e.g., `appointment-service.default.svc.cluster.local`). Pods can call `http://appointment-service:4000/appointments` and Kubernetes DNS resolves it to the Service's ClusterIP. kube-proxy then load-balances across healthy pods matching the Service's selector labels. No external tool needed — it's native to Kubernetes. For more advanced discovery (cross-cluster, multi-datacenter), use Consul or Istio service mesh.

---

## 30-Second Interview Version

> Service discovery lets services find each other dynamically without hardcoded IPs. In Kubernetes, Services provide DNS-based discovery — call `http://service-name:port` and DNS + kube-proxy handle routing. For non-Kubernetes, use Consul or etcd for client-side discovery: services register themselves, clients query the registry. Always include health checks (HTTP, TCP, gRPC) so the registry removes unhealthy instances. For Docita in Kubernetes: use native Service discovery for most cases, add Consul only for multi-cluster or external service discovery.

# Strangler Fig Migration

> **Incrementally replacing a monolith with microservices without a risky big-bang rewrite.**

---

## The Metaphor

The strangler fig tree grows around a host tree, gradually replacing it. Eventually the host tree dies and the fig stands on its own — without ever having to cut down the host.

```
Day 1:          Month 3:         Month 6:         Month 12:
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│Monolith │    │Proxy     │    │Proxy     │    │Microservices│
│  (100%) │    │┌───────┐│    │┌───────┐│    │┌───────┐│
│         │    ││Mono   ││    ││Mono   ││    ││  (0%) ││
│         │    ││(80%)  ││    ││(30%)  ││    ││Removed││
│         │    │└───────┘│    │└───────┘│    │└───────┘│
└─────────┘    └─────────┘    └─────────┘    └─────────┘
                 ↑ New svc       ↑ More new     ↑ Monolith
                 handles 20%     handles 70%    fully replaced
```

---

## The Proxy Layer

The key architectural element is a **proxy/router** that sits in front of both the monolith and new services, routing traffic based on rules.

```
┌──────────────────────────────────────────────────┐
│                 Proxy / Router                     │
│                                                    │
│  /api/v2/patients/*  → New Patient Service         │
│  /api/v2/prescriptions/* → New Prescription Service│
│  /* → Monolith (everything else)                   │
│                                                    │
└────────────────────┬─────────────────────────────┘
                     │
         ┌───────────┴───────────┐
         │                       │
   ┌─────┴─────┐           ┌─────┴─────┐
   │  Monolith  │           │ New Service│
   │  (legacy)  │           │ (NestJS)  │
   └───────────┘           └───────────┘
```

## Migration Steps

### Step 1: Identify the Strangle Target

```typescript
// Analyze monolith — find the most painful module
// Criteria: high bug rate, frequent changes, clear boundaries

// Example: Appointments module in monolith
// - 40% of all bugs are in appointment code
// - Changes every week (new features)
// - Clear API boundary (CRUD + booking logic)
// - This is our strangling target!
```

### Step 2: Build the New Service

```typescript
// appointment-service (new NestJS service)
@Controller('appointments')
export class AppointmentsController {
  @Post()
  async create(@Body() dto: CreateAppointmentDto) {
    // New implementation with Prisma, multi-tenant isolation, etc.
    return this.appointmentsService.create(dto);
  }

  @Get(':id')
  async findOne(@Param('id') id: string) {
    return this.appointmentsService.findById(id);
  }
}
```

### Step 3: Configure the Proxy

```nginx
# nginx.conf — Strangler proxy
upstream monolith {
    server monolith.internal:3000;
}

upstream appointment_service {
    server appointment-service.internal:4000;
}

server {
    listen 443 ssl;

    # New service handles appointment routes
    location /api/v2/appointments {
        proxy_pass http://appointment_service;
    }

    # Everything else goes to monolith
    location / {
        proxy_pass http://monolith;
    }
}
```

### Step 4: Migrate Data

```typescript
// Dual-write during migration
async function createAppointment(dto: CreateAppointmentDto) {
  // Write to new service's database
  const newAppointment = await newDb.appointment.create({ data: dto });

  // Also write to monolith's database (for backward compatibility)
  await monolithDb.query(
    'INSERT INTO appointments (id, patient_id, time) VALUES ($1, $2, $3)',
    [newAppointment.id, dto.patientId, dto.time]
  );

  return newAppointment;
}

// Data sync job (migrate historical data)
async function syncHistoricalData() {
  const oldAppointments = await monolithDb.query('SELECT * FROM appointments');
  for (const apt of oldAppointments.rows) {
    await newDb.appointment.upsert({
      where: { id: apt.id },
      create: apt,
      update: apt,
    });
  }
}
```

### Step 5: Traffic Migration

```typescript
// Feature flag controls traffic routing
async function routeRequest(req: Request) {
  const percentage = await getFeatureFlag('appointments-migration-percentage');

  if (Math.random() * 100 < percentage) {
    // Route to new service
    return proxyTo('appointment-service', req);
  } else {
    // Route to monolith
    return proxyTo('monolith', req);
  }
}

// Gradually increase: 1% → 5% → 25% → 50% → 100%
```

### Step 6: Remove from Monolith

```sql
-- After 100% traffic on new service, remove from monolith
-- Step 1: Stop writes to monolith database
-- Step 2: Verify data consistency
-- Step 3: Remove appointment code from monolith
-- Step 4: Remove appointment tables (after retention period)
```

## Data Consistency During Migration

| Challenge | Solution |
|-----------|----------|
| **Dual writes** | Write to both DBs, async sync |
| **Read consistency** | Read from new service if migrated, monolith otherwise |
| **Data conflicts** | New service is source of truth after cutover |
| **Historical data** | One-time migration job + ongoing sync |

---

## When to Use Strangler Fig

| Scenario | Recommendation |
|----------|---------------|
| **Monolith → microservices** | ✅ Perfect use case |
| **Framework migration** (Express → NestJS) | ✅ Route by endpoint |
| **Database migration** (MongoDB → PostgreSQL) | ✅ Dual-write + sync |
| **Cloud migration** (on-prem → AWS) | ✅ Gradual traffic shift |
| **Small app (< 10K LOC)** | ❌ Just rewrite — too much proxy overhead |
| **Rewriting everything at once** | ❌ Use strangler instead of big-bang |

## Interview Questions

**Q: "How do you migrate from a monolith to microservices?"**

> Strangler fig pattern: (1) Put a proxy in front of the monolith, (2) Identify the most painful module (high bugs, frequent changes, clear boundaries), (3) Build a new service for that module, (4) Route traffic via feature flag (start at 1%), (5) Gradually increase to 100%, (6) Remove module from monolith, (7) Repeat for next module. Key challenge: data consistency during dual-write phase — use outbox pattern for eventual consistency, verify with checksums before cutover. Never do big-bang rewrites — they have >70% failure rate.

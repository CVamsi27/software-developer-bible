# Docker Images & Containers

## Definition

A **Docker image** is a read-only template containing instructions for creating a container. It consists of layered filesystem changes. A **Docker container** is a runnable instance of an image—lightweight, isolated, and ephemeral. Images are built from a **Dockerfile**, a declarative script of build instructions.

> **Textbook Definition:** A container image is a versioned filesystem and execution configuration packaged as layers and metadata. A container is an isolated running process environment instantiated from that image by a container runtime.

Key terms:

- **Image**: Immutable blueprint (e.g., `nginx:1.25`)
- **Container**: Running process with isolated CPU, memory, filesystem, network
- **Layer**: Filesystem-changing build steps produce layers; configuration instructions record runtime/build settings
- **Registry**: Central repository for images (Docker Hub, ECR, GCR, ACR)
- **Tag**: Mutable named pointer appended to image name (`node:22-alpine`)

## First Principles

Containers are isolating *processes*, not machines:

1. **A container is a process with walls**: namespaces (what it can see: PID, net, mount) + cgroups (what it can use: CPU, memory) (→ 40.1.07). A Linux container shares its host Linux kernel. Docker Desktop on macOS/Windows normally supplies that host through a Linux VM. Startup depends on image availability and application initialization; kernel vulnerabilities can cross container boundaries.
2. **The image combines filesystem layers with configuration**: filesystem-changing instructions such as `RUN`, `COPY` and `ADD` add filesystem changes. Instructions such as `WORKDIR`, `ENV`, `EXPOSE` and `CMD` set image configuration or build behavior. Docker can reuse unchanged filesystem layers and share base layers.
3. **The tag is a pointer, not a version** — `latest` moves. Reproducibility demands digests (`image@sha256:...`), the only immutable reference.

## Why Do We Need It?

| Problem | Solution |
| --------------------- | ------------------------------------- |
| "Works on my machine" | Consistent environment via images |
| Manual server setup | Declarative Dockerfile |
| Dependency conflicts | Per-container isolation |
| Slow deployments | Lightweight containers vs VMs |
| Difficult rollbacks | Immutable image digests |
| Resource waste | Shared kernel, no hypervisor overhead |

## How It Works

### Image Layering

Filesystem-changing instructions create image layers. Instructions such as `EXPOSE` and `CMD` primarily update image configuration. `WORKDIR` also creates a missing directory; do not infer layer contents only from the instruction name. Docker can reuse a cached filesystem layer when its inputs and preceding build state have not changed.

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

```

### Container Lifecycle

`docker build` produces an image. `docker run` creates a container with a writable layer and starts its configured process. `docker stop` requests graceful termination, then forces termination after its timeout. The stopped container and writable layer remain until `docker rm`; removing the container does not remove its image or named volumes.

`docker pause` suspends processes; it does not stop or remove the container. A restart starts the same container again, so its writable-layer files remain. Use a named volume for data that must survive replacement by a newly created container.

## Code Examples

These examples assume a Linux target, committed lockfiles, and an application listening on `0.0.0.0` at the stated port. `/health` must exist for a health check to pass. A tag pinned to a major or patch can still move; select an approved digest for reproducible release artifacts. The first Node example runs existing JavaScript; compiled applications need development dependencies during the build stage.


### Basic Dockerfile

```dockerfile
# Use specific version, never 'latest'
FROM node:22-alpine AS builder

# Set working directory
WORKDIR /app

# Copy dependency manifests first (layer caching)
COPY package*.json ./

# Install dependencies
RUN npm ci --omit=dev

# Copy application code
COPY . .

# Expose port
EXPOSE 3000

# Health check
HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1

# Run as non-root user
USER node

# Start application
CMD ["node", "server.js"]

```

### Building and Running

```bash
# Build image with tag
docker build -t myapp:1.0.0 .

# The Dockerfile must declare ARG before a build argument changes behavior.
# Use -e NODE_ENV=production on docker run for runtime configuration.

# Run container
docker run -d -p 3000:3000 --name myapp myapp:1.0.0

# Run with environment variables
docker run -d -p 3000:3000 \
  -e DATABASE_URL="postgres://db:5432/mydb" \
  -e REDIS_URL="redis://cache:6379" \
  --name myapp myapp:1.0.0

# Run interactively
docker run --rm -it --entrypoint sh myapp:1.0.0

```

### Multi-Stage Build

```dockerfile
# Stage 1: Build
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:22-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY package*.json ./
RUN npm ci --omit=dev

USER node
CMD ["node", "dist/server.js"]

```

### Inspecting Images and Containers

```bash
# Inspect image layers
docker history myapp:1.0.0

# Inspect image details
docker inspect myapp:1.0.0

# List running containers
docker ps

# List all containers (including stopped)
docker ps -a

# View container logs
docker logs myapp

# Execute command in running container
docker exec -it myapp sh

# Copy files from container
docker cp myapp:/app/logs ./logs

# Remove stopped containers
docker rm myapp

# Remove image
docker rmi myapp:1.0.0

```

## Real-World Use Cases

### 1. Node.js Microservice

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY dist/ ./dist/
USER node
EXPOSE 8080
CMD ["node", "dist/index.js"]

```

### 2. Python Django App

```dockerfile
FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /usr/local /usr/local
COPY . .
RUN python manage.py collectstatic --noinput
EXPOSE 8000
CMD ["gunicorn", "myproject.wsgi:application", "--bind", "0.0.0.0:8000"]

```

### 3. Go Binary (Distroless)

```dockerfile
FROM golang:1.26-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /server ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=builder /server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]

```

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Using `latest` tag | Pin a supported Node.js major and, where reproducibility requires it, an image digest |
| Copying everything before `npm install` | Copy `package*.json` first for layer caching |
| Running as root | Use `USER node` or create custom user |
| No `.dockerignore` | Exclude `node_modules`, `.git`, etc. |
| No multi-stage builds | Separate build deps from production |
| Leaving package lists or temporary files in an image layer | Remove them in the same `RUN` that creates them |
| Not using `HEALTHCHECK` | Configure the orchestrator's health probes; Kubernetes does not execute Dockerfile HEALTHCHECK |
| Large image size | Use Alpine, distroless, or slim variants |

## Best Practices

```dockerfile
# GOOD: Pinned versions, Alpine, multi-stage, non-root, health check
FROM node:22.23.3-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --omit=dev && npm cache clean --force

FROM node:22.23.3-alpine
RUN apk add --no-cache dumb-init
WORKDIR /app
COPY --from=builder --chown=node:node /app/dist ./dist
COPY --from=builder --chown=node:node /app/node_modules ./node_modules
COPY --from=builder --chown=node:node /app/package*.json ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD node -e "require('http').get('http://localhost:3000/health', r => { process.exit(r.statusCode === 200 ? 0 : 1) })"
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/server.js"]

```

1. **Pin base image versions** — avoid `:latest`

2. **Use multi-stage builds** — minimize final image size

3. **Order instructions by change frequency** — deps before source

4. **Run as non-root** — security best practice

5. **Use `.dockerignore`** — exclude unnecessary files

6. **Leverage layer caching** — copy dependency files first

7. **Add HEALTHCHECK** — records Docker health; configure Kubernetes probes separately

8. **Use specific distroless/alpine images** — smaller attack surface

9. **Keep transient files out of image layers** — clean them in the same `RUN`, or use a multi-stage build
10. **Scan images** — use `docker scout` or Trivy

## Performance Considerations

| Factor | Impact | Mitigation |
| ------------------------ | -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Image size | Pull time, storage | Alpine, multi-stage, `.dockerignore` |
| Layer contents and order | Image size and cache reuse | Remove temporary files in the same `RUN`; copy stable dependency manifests before frequently changed source |
| Build context size | Upload time to daemon | `.dockerignore`, minimize context |
| Cache invalidation | Full rebuild | Order Dockerfile instructions carefully |
| Registry latency | CI/CD speed | Use local cache or mirror registry |
| Container startup | Deployment speed | Use `dumb-init`, minimal base |

```bash
# Build with the context restricted by .dockerignore
docker build -t myapp . -f Dockerfile

# Use buildkit for parallel builds
DOCKER_BUILDKIT=1 docker build -t myapp .

# Check image size
docker images myapp

# Scan image for vulnerabilities
docker scout cves myapp:1.0.0

```

## Summary

Docker images are immutable, layered templates. Containers are ephemeral runtime instances. Mastering Dockerfiles, layer caching, multi-stage builds, and security practices is essential for any senior engineer. Images should be minimal, scanned, non-root, and reproducible.

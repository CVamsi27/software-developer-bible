# Docker Images & Containers

Two machines can run the same application commit and still behave differently if their files, dependencies or startup commands differ. A Docker image packages those filesystem and startup defaults together. The running process still depends on its host kernel, runtime configuration and external services, so the image is a repeatable starting point—not a whole virtual machine.

## Definition

A **Docker image** is a content-addressed package of filesystem layers and execution metadata. A **container** is a process started from an image, with configured isolation and a writable layer for changes made while it runs. A **Dockerfile** describes how to build the image; a **registry** stores and distributes images.

> **Textbook Definition:** A container image is an immutable, content-addressed artifact composed of a layered root filesystem and runtime configuration. A container is a running instance of that artifact whose processes use operating-system isolation and resource controls.

A **tag** such as `orders-api:1.4` is a mutable name that can point to a different image later. The image digest identifies exact content. Use a reviewed digest when a deployment must be reproducible.

## First Principles

An image must preserve enough files and defaults to start the application consistently. A container must isolate a process from other workloads without carrying a separate kernel. Those needs lead to two useful boundaries: the image is the build artifact; the container is the runtime instance. Configuration, persistent data and resource limits each have their own lifecycle and must be provided deliberately.

## Build an image, then run its process

This example expects the application to be compiled into `dist/` before the image is built. If compilation belongs in the Docker build, use the separate [multi-stage build chapter](40.1.04-multi-stage-builds.md).

```dockerfile
FROM node:24-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY dist/ ./dist/
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

Build and start the image:

```bash
docker build -t orders-api:dev .
docker run --rm --name orders-api -p 3000:3000 orders-api:dev
```

Docker stores filesystem changes from instructions such as `RUN` and `COPY` in image layers. It can reuse an earlier result when that instruction's inputs have not changed, which is why dependency manifests are copied before frequently changing source files. `WORKDIR` sets the working directory and creates it when needed. `ENV` records a default environment value. `EXPOSE` documents a container port; `-p 3000:3000` is what publishes a host-to-container port mapping.

The JSON-array form of `CMD` starts the application directly, so it can receive termination signals as the container's main process. `ENTRYPOINT` fixes the executable; `CMD` supplies its default command or arguments. Choose the combination that makes the intended process and its shutdown behavior explicit.

Use a `.dockerignore` file to keep local dependencies, credentials and repository history out of the build context:

```text
node_modules
.git
.env
.env.*
coverage
```

A smaller context avoids uploading irrelevant files to the builder. Excluding a secret from the image does not make it safe to commit; provide runtime secrets through the deployment platform.

## What survives when a container stops?

`docker run` creates a container and starts its configured process. The writable layer records changes made by that container. `docker stop` asks the process to terminate gracefully and then forces it to stop after the timeout. The stopped container and its writable layer remain until `docker rm`; removing the container does not remove its image.

The writable layer is disposable runtime state. Replacing a container creates a new writable layer, so application data that must survive replacement belongs in a named volume or external data service. A bind mount instead uses a path owned by the host. The [volumes and networks chapter](40.1.02-volumes-networks.md) explains those storage and connection lifecycles.

A moved tag does not update a container that is already running: that container was created from the image content available at its start. Pull or build the desired image, then create a new container from that image. For a release, record and deploy the digest so each environment receives the same artifact.

## Where the isolation boundary ends

On Linux, a container shares the host kernel. Namespaces limit what a process can see; cgroups account for and can limit its resource use when configured. A container has no CPU or memory limit merely because it is a container. Docker Desktop on macOS and Windows normally runs Linux containers inside a Linux virtual machine.

These boundaries are useful for packaging and process isolation, but they are not equivalent to a separate guest kernel. Host mounts, privileges, kernel exposure and resource settings affect the actual risk. See [container runtime internals](40.1.07-container-runtime-internals-namespaces-cgroups.md) for the mechanism and [Dockerfile security practices](40.1.05-dockerfile-best-practices.md) for release hardening.

## Common misreadings

- `EXPOSE` records image metadata; it does not publish a port. Use `-p` or a platform network rule.
- A tag is a name, not an immutable release identity. Pin a digest for deployment.
- A container is a process plus isolation, not a small virtual machine with its own Linux kernel.
- Container-local files are not durable application storage. Persist data outside the writable layer.
- An image health check does not replace orchestration probes. Kubernetes uses its own startup, readiness and liveness probes.
- A smaller image is not automatically safer or faster. Check compatibility, startup behavior, vulnerability findings and the actual pull/build bottleneck.

## Summary

An image packages filesystem layers and startup defaults; a container runs a process from that image with a disposable writable layer. Treat the image digest, runtime configuration, persistent state and isolation limits as separate parts of a deployment. Build once, then replace containers deliberately when promoting a new image.

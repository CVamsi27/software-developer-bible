# Docker Volumes & Networks

A replacement API container starts cleanly, but its database is empty and it cannot reach Redis at `localhost`. These are two separate lifecycle mistakes: the database wrote to disposable container storage, and `localhost` points back to the API container itself.

## Definition

A **volume** mounts storage into a container at a path. A **Docker network** connects container network namespaces and controls which peers can communicate. Both are external to the container's writable layer, but they have different owners and lifetimes.

> **Textbook Definition:** Container storage mounts connect container paths to Docker-managed, host-backed, or memory-backed data. Container networks define addressability and traffic paths among containers, the host, and external endpoints.

## First Principles

A container can be replaced independently of its data and its network peers. Choose storage by the required persistence and recovery boundary; choose networking by the required reachability and name-resolution boundary. Docker's default behavior is not a backup plan or an authorization policy.

## Choose where the data lives

| Mount | Backing and lifetime | Use it when |
| ------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Named volume | Docker-managed; survives ordinary container removal, but a local volume stays on that Docker host | Application data needs a managed path |
| Bind mount | An explicit host path with host ownership and permissions | Development files or deliberately managed host configuration |
| `tmpfs` | Memory-backed and temporary; host swap policy may still write pages to disk | Short-lived scratch data |

Writes to a mounted path go to that mount. They do not go to the container's writable layer. A mount hides the image's files at its destination; Docker may initialize a new empty volume from image contents, but a bind mount exposes the host directory instead. On Docker Desktop, the Linux daemon and its managed volume storage live inside the Desktop VM.

For PostgreSQL 18 and later, the official image stores its versioned `PGDATA` below `/var/lib/postgresql` and declares that parent as the volume target. Earlier major images use a different layout. Follow the official image's migration procedure before changing the major image tag.

```bash
docker volume create orders-data
docker run -d --name orders-db \
  --mount source=orders-data,target=/var/lib/postgresql \
  -e POSTGRES_PASSWORD="${DB_PASSWORD:?Set a disposable local password}" \
  postgres:18
```

Removing the `orders-db` container leaves the `orders-data` volume behind; removing the volume deletes that data. A volume is persistent storage, not a backup: use a database-consistent backup method and test restoration. For a named bind mount or a local-driver option, the host path must already exist and its permissions must match the process inside the container.

## Choose who can reach the service

A container normally has its own network namespace. On a user-defined bridge, containers resolve each other by name and use the destination's **container port**. A published port connects a host address and port to a container port:

```text
API container ── DNS "postgres":5432 ──► database container:5432
host browser  ── 127.0.0.1:8080 ───────► API container:3000
```

```bash
docker network create orders-net
docker run -d --name orders-web --network orders-net nginx:alpine
docker run --rm --network orders-net busybox:1.37 \
  sh -c 'i=0; while [ "$i" -lt 20 ]; do wget -qO- http://orders-web:80 >/dev/null && exit 0; sleep 1; i=$((i + 1)); done; exit 1'
```

The example waits because creating a container does not prove that its process is ready. Publish a port with `-p 127.0.0.1:8080:3000` when only local host access is required; omitting the host address normally publishes it on host interfaces more broadly. `EXPOSE` documents a container port but does not publish it.

The default bridge lacks the automatic container-name DNS of a user-defined bridge; `--link` is a legacy exception. Host networking shares the host network namespace and is a different isolation choice. An overlay network can connect services across Docker hosts in Swarm. A Compose `internal` network restricts external routing, but a service attached to both internal and external networks can still relay at the application layer.

A network controls reachability, not application authorization. Keep databases off published ports, authenticate service calls, and treat shared network membership as a trust boundary.

## Summary

Mounts determine where container paths store data; networks determine how workloads find and reach one another. Named volumes survive container replacement but remain host-local unless another storage system is configured. User-defined bridges provide service-name DNS; published ports define host access. Plan backups, migration, permissions, and authorization separately from these primitives.

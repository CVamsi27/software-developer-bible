# Docker Volumes & Networks

## Definition

**Volumes** are mechanisms for persisting data generated by containers and for sharing data between them. **Docker networks** provide container-to-container and container-to-host communication. Together, they solve the statefulness and connectivity challenges of ephemeral containers.

Key concepts:

- **Volume**: Managed by Docker, stored in Docker's storage directory, persists beyond container lifecycle
- **Bind Mount**: Maps host path directly into container, depends on host filesystem
- **tmpfs Mount**: Stored in memory; tmpfs pages can reach swap unless the host policy prevents it
- **Bridge Network**: Default; containers on same bridge can communicate
- **Host Network**: Container shares host's network stack directly
- **Overlay Network**: Spans multiple Docker hosts (Swarm)

> **Textbook Definition:** Container storage mounts attach persistent, host-backed, or memory-backed data to a container's filesystem. Container networks define addressability and connectivity among containers, hosts, and external endpoints.

## First Principles


Persistence and networking are *provided* to containers because their writable layer and network namespace have container lifetimes:

1. **Container layers are ephemeral by design** — writes remain after stop/restart but are lost when the container is removed. Volumes exist to put state somewhere with a lifetime you choose (named volume: Docker-managed; bind mount: host path — host perms/semantics included).
2. **A normal bridge-network container gets its own network namespace** — so "localhost" inside ≠ host. The bridge network + port publishing is the default topology; service discovery on user-defined networks is built-in DNS by container name.
3. **Volumes and networks are explicit runtime dependencies** — choose their lifetime, reachability and recovery behavior rather than relying on a container's writable layer or a hard-coded address.

## Why Do We Need It?

| Problem | Solution |
| ----------------------------------- | ------------------------------------------------------------------------------------- |
| Data lost when container is removed | Volumes persist data |
| Containers can't communicate | Networks enable discovery |
| Hardcoded IPs are fragile | DNS-based service discovery |
| Secrets need secure passing | Secret files or a configured secret manager; a volume alone does not protect a secret |
| Multi-host networking | Overlay networks |
| Performance-sensitive I/O | Volume mounts for DBs |

## How It Works

### Mount Lifetime: Replacing a Container

```text
container A /data ──mount──► named volume orders
container A removed         volume orders remains
container B /data ──mount──► same named volume orders
```

Writes under `/data` reach the mounted volume, while writes elsewhere normally reach the container's writable layer. Restarting A preserves both; removing A discards its writable layer. B sees `/data` again only when explicitly attached to the same volume. Mounting over a directory hides the image's files at that path; a fresh empty volume may be populated from image contents, whereas a bind mount exposes the host directory directly.

A local named volume is local to the Docker host. Moving the container to another host does not move its data. On Docker Desktop, the managed storage is normally inside its Linux VM, not the macOS host's `/var/lib/docker`. Back up through a database-consistent method and test restore; copying a live database directory is not a consistency guarantee.

### Network Paths: Container Port and Published Port

```text
API on user-defined network ──DNS postgres──► database container:5432
host client ──published host port──► API container:3000
```

Containers sharing a user-defined bridge resolve service/container names. The built-in default bridge does not offer the same automatic name resolution. Publishing `127.0.0.1:3000:3000` makes the API reachable through the host's loopback interface; `3000:3000` normally binds host interfaces more broadly. Containers on the same network use the destination's container port, regardless of its host publication.

`localhost` refers to the caller's network namespace, so an API container cannot reach a separate database at `localhost:5432`. The API needs `postgres:5432`. A host-network container is an exception because it shares host networking; Docker Desktop host networking has separate support/configuration requirements. An internal backend network restricts external routing, but an app attached to both backend and external networks can still act as a bridge at the application layer.

## Code Examples

The commands below are isolated examples. Set any password variables to disposable local values; they are not production secret-management recipes. Create referenced bind-mount paths before starting the container.

### Volumes

```bash
# Create named volume
docker volume create mydata

# Use named volume
docker run -d \
  -v mydata:/var/lib/mysql \
  --name db \
  -e MYSQL_ROOT_PASSWORD="${MYSQL_ROOT_PASSWORD:?Set a disposable local value}" \
  mysql:8

# Bind mount
docker run -d \
  --mount "type=bind,src=$(pwd)/src,dst=/app/src" \
  --name dev \
  node:24-alpine node -e "setInterval(() => {}, 1000)"

# Read-only mount
# Requires ./config/nginx.conf to exist.
docker run -d \
  -v "$(pwd)/config/nginx.conf:/etc/nginx/nginx.conf:ro" \
  nginx:alpine

# tmpfs mount (memory-backed; host swap policy still matters)
docker run -d \
  --tmpfs /tmp:rw,size=100m \
  nginx:alpine

# Volume with specific driver options
docker volume create \
  --driver local \
  --opt type=none \
  --opt device=/data/mysql \
  --opt o=bind \
  mysql-data

```

### Volume Management

```bash
# List volumes
docker volume ls

# Inspect volume
docker volume inspect mydata

# Remove volume
docker volume rm mydata

# Remove all unused volumes
docker volume prune

# Copy from volume
# Assumes the container has already exported this file.
docker cp db:/var/lib/mysql/data.sql ./data.sql

```

### Networks

```bash
# Create bridge network
docker network create mynetwork

# Create with subnet
docker network create \
  --driver bridge \
  --subnet 172.20.0.0/16 \
  --ip-range 172.20.240.0/20 \
  isolated-subnet

# Connect container to network
docker network connect mynetwork mycontainer

# Disconnect
docker network disconnect mynetwork mycontainer

# Run on specific network
docker run -d --network mynetwork --name api nginx

# Inspect network
docker network inspect mynetwork

# List networks
docker network ls

```

### Docker Compose Volumes & Networks

```yaml
# docker-compose.yml

services:
  app:
    build: .
    ports:

      - "3000:3000"
    volumes:

      - ./src:/app/src # bind mount
      - app_data:/app/data # named volume
    networks:

      - frontend
      - backend
    environment:

      - DB_HOST=postgres
      - REDIS_HOST=redis

  postgres:
    image: postgres:18
    volumes:

      - pg_data:/var/lib/postgresql
    networks:

      - backend
    environment:

      - POSTGRES_PASSWORD=secret

  redis:
    image: redis:8-alpine
    volumes:

      - redis_data:/data
    networks:

      - backend

volumes:
  app_data:
  pg_data:
  redis_data:

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true # no external access

```

### DNS-Based Service Discovery

```bash
docker network create study-net
docker run -d --name study-web --network study-net nginx:alpine
docker run --rm --network study-net node:24-alpine \
  node -e "fetch('http://study-web:80').then(r => console.log(r.status))"
# Expected: 200. The request runs inside the client container, not the host.
docker rm -f study-web
docker network rm study-net
```

Do not use the legacy `--link` mechanism for new bridge networking.

## Real-World Use Cases

### 1. Database with Persistent Storage

```yaml
services:
  postgres:
    image: postgres:18
    volumes:

      - pg_data:/var/lib/postgresql
      - ./init-scripts:/docker-entrypoint-initdb.d
    environment:
      POSTGRES_DB: myapp
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    deploy:
      resources:
        limits:
          memory: 1G

volumes:
  pg_data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /mnt/persistent/pg_data

```

### 2. Development Environment with Hot Reload

```bash
docker run -d \
  --name dev \
  -p 3000:3000 \
  --mount "type=bind,src=$(pwd),dst=/app" \
  -w /app \
  -v /app/node_modules \
  -e NODE_ENV=development \
  node:24-alpine \
  sh -c "npm install && npm run dev"

```

### 3. Multi-Host Overlay Network (Swarm)

```bash
# Initialize swarm
docker swarm init

# Create overlay network
docker network create \
  --driver overlay \
  --attachable \
  --subnet 10.0.9.0/24 \
  app-net

# Deploy service
docker service create \
  --name api \
  --network app-net \
  --replicas 3 \
  myapp:approved-release

```

## Common Mistakes

| Mistake | Fix |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Using bind mounts in production | Choose explicit managed storage or an intentional host path with ownership, backup and restore policies |
| Hardcoding IPs in configs | Use DNS names (container names) |
| Storing DB data in container filesystem | Mount volumes for all stateful services |
| Not backing up named volumes | Use database-consistent backup and test restore |
| Using `--net=host` carelessly | Only for performance-sensitive cases |
| Mixing volume types across environments | Use Compose profiles for dev vs prod |
| Not cleaning up unused volumes | Review ownership and retention before deleting unused volumes |

## Best Practices

```yaml
# Local Compose storage and secret-file example (requires backup and restore planning)
services:
  postgres:
    image: postgres:18-alpine
    volumes:

      - type: volume
        source: pg_data
        target: /var/lib/postgresql
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:

      - db_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  pg_data:
    driver: local

secrets:
  db_password:
    file: ./secrets/db_password.txt

```

1. **Use named volumes for all persistent data** — survives container removal

2. **Use `internal: true` when a network needs no external routing** — a multi-homed service can still bridge traffic at the application layer

3. **Use secrets for credentials** — avoid embedding credentials in images; choose supported runtime injection

4. **Set resource limits** — limit compute resources; monitor disk and connection capacity separately

5. **Use health checks** — ensure service readiness before traffic

6. **Label volumes** — track ownership (`docker volume create --label app=myapp`)

7. **Test volume backups** — verify database-consistent backups can restore

8. **Use bind mounts deliberately** — for code hot reload or managed host configuration

9. **Monitor disk usage** — volumes grow unmonitored
10. **Use `:ro` for read-only mounts** — defense in depth

## Performance Considerations

| Mount Type | Performance | Use Case |
| -------------------- | -------------------------------------------- | -------------------------- |
| Named volume (local) | Host filesystem/driver dependent | Databases, persistent data |
| Bind mount | Good (native) | Development, config files |
| tmpfs | Memory-backed; capacity and swap constraints | Secrets, temp data, caches |
| NFS volume | Network/server dependent | Shared across hosts |
| CIFS/SMB | Network/server dependent | Windows file sharing |

```bash
# Benchmark volume performance
docker run --rm -v mydata:/data alpine \
  sh -c "dd if=/dev/zero of=/data/test bs=1M count=64 && rm /data/test"

# Network performance test
docker network create study-net
docker run -d --name study-iperf --network study-net alpine \
  sh -c "apk add --no-cache iperf3 && iperf3 -s"
sleep 2
docker run --rm --network study-net alpine \
  sh -c "apk add --no-cache iperf3 && iperf3 -c study-iperf"
docker rm -f study-iperf
docker network rm study-net

```

## Summary

Volumes provide persistent storage for containers. Networks enable service discovery and isolation. Named volumes with health checks, internal networks with proper DNS, and secrets management are essential for production Docker deployments.

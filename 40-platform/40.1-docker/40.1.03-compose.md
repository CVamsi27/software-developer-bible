# Docker Compose

An API container can start before its database accepts connections. Starting the database first helps, but it does not fix later outages or establish that a schema migration succeeded. Compose gives the services a shared, reviewable model; the application and deployment still need to handle runtime failure.

## Definition

**Docker Compose** defines the services, networks, volumes, secrets, and build settings for an application, then creates or updates those resources on a Docker environment. It suits development, tests, and deliberately operated single-host deployments — but provides no multi-host scheduling, automatic failover, or rolling-update controller by itself.

> **Textbook Definition:** Docker Compose is a declarative specification and CLI for creating and managing related container services and their network, storage, and configuration resources.

## First Principles

Compose describes a dependency graph and reconciles containers to that graph. Its dependency conditions gate startup but are not ongoing service supervision. Volumes, secrets, and environment values also have lifetimes and exposure rules separate from the YAML that references them.

## 1. Order Startup with Health and Completion Conditions

This example assumes the API reads `DATABASE_PASSWORD_FILE`, and the app image provides a `migrate` command. The local secret file is a development fixture; Compose does not encrypt the source file on the host.

```yaml
name: orders-local

services:
  api:
    build: .
    image: orders-api:local
    ports:
      - "127.0.0.1:${APP_PORT:-3000}:3000"
    environment:
      DATABASE_HOST: db
      DATABASE_PORT: "5432"
      DATABASE_NAME: orders
      DATABASE_USER: orders
      DATABASE_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    depends_on:
      db:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully
    networks:
      - backend
    healthcheck:
      test: ["CMD", "node", "-e", "require('http').get('http://localhost:3000/health', r => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"]
      interval: 20s
      timeout: 3s
      retries: 3
      start_period: 10s

  migrate:
    build: .
    image: orders-api:local
    command: ["node", "dist/migrate.js"]
    environment:
      DATABASE_HOST: db
      DATABASE_PORT: "5432"
      DATABASE_NAME: orders
      DATABASE_USER: orders
      DATABASE_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    depends_on:
      db:
        condition: service_healthy
    networks:
      - backend
    restart: "no"

  db:
    image: postgres:18
    environment:
      POSTGRES_DB: orders
      POSTGRES_USER: orders
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - orders_data:/var/lib/postgresql
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U orders -d orders"]
      interval: 5s
      timeout: 3s
      retries: 12
      start_period: 10s

volumes:
  orders_data:

networks:
  backend:
    internal: true

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

The database starts first and must pass its health check; the migration service must then exit successfully before the API starts. That is a startup condition, not a continuing guarantee: if the database fails later, the API needs bounded retries, connection-pool recovery, and user-safe error handling. An `unhealthy` status does not itself restart a container; restart policies act on process exit. Compose's long `depends_on` form also supports `restart: true` for an explicit Compose-controlled dependency restart, not arbitrary runtime restarts.

The API publishes only on host loopback. The database is unpublished, and both services share the `backend` network. `internal: true` restricts external routing; if the API needs outbound access, add and review a separate network path. A service on both networks can relay traffic at the application layer.

PostgreSQL 18 declares `/var/lib/postgresql` as its volume target and stores its version-specific data directory below it. Earlier major images use a different layout — follow the official image's migration procedure before promoting a major version; changing the tag is not a database upgrade.

## 2. Resolve Configuration Without Confusing It for Secrets

Compose interpolation reads values while it builds the model, commonly from the shell or a project `.env` file. A service's `env_file` passes variables into the container; it does not supply every `${...}` expression in the Compose model. Explicit `environment` entries override matching `env_file` values. The `secrets` block grants a selected service access to a mounted file or, in Docker Compose, a host environment value — not a cloud secret manager or encrypted Swarm secret.

Use `docker compose config` to inspect the merged model and `docker compose config --environment` to inspect interpolation inputs. Both can reveal sensitive values; keep the output local and out of logs.

Optional services use profiles. Unprofiled services start by default; a profiled service starts when its profile is enabled or explicitly targeted:

```yaml
services:
  debug-shell:
    image: busybox:1.37
    command: ["sleep", "3600"]
    profiles: ["debug"]
```

```bash
docker compose --profile debug up
```

For file synchronization during development, Compose Watch requires Compose 2.22 or later. Declare watch rules only for services that benefit from syncing or rebuilding; `.dockerignore` rules also apply.

## 3. Use the Model in Tests, Then Set Production Limits

A CI test job can run its dependencies and report the test service's exit status:

```bash
docker compose up --build --abort-on-container-exit --exit-code-from tests
```

The `tests` service must be defined in the model and complete with the test command's actual exit code. For one-off commands, `docker compose run --rm SERVICE COMMAND` creates a temporary service container; `docker compose up` instead reconciles selected services and their dependencies. `docker compose down` removes project containers and networks but keeps named volumes by default — adding `-v` removes project-managed volumes and can erase database contents.

Compose can operate a single-host deployment when an owner supplies TLS, host patching, backup/restore, resource enforcement, monitoring, and recovery procedures. `deploy` resource fields are implemented by current Compose versions, but verify enforcement on the target engine. A fixed published host port also prevents multiple replicas from binding that same port without a proxy or another load-balancing design. Use an orchestrator when you need multi-host scheduling, controller-managed rollouts, or automated failover.

## Summary

Compose keeps a multi-container environment in one declarative model. Health and completion conditions can order startup; they do not replace reconnection or recovery logic. Environment interpolation, container variables, local secrets, volumes, and network access each have separate contracts. Use Compose for a transparent local/test graph and single-host operation with explicit owners, and choose a cluster orchestrator for cluster-level control.

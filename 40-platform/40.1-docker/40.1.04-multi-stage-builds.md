# Docker Multi-Stage Builds

A TypeScript service needs compilers, test tools, and development packages to build, but none of those should be required just to serve a request. Multi-stage builds let the Dockerfile use one environment to produce the release files and a separate environment to run them.

## Definition

A **multi-stage build** uses multiple `FROM` instructions in one Dockerfile. Each instruction starts a new stage, and `COPY --from` transfers selected files from an earlier stage into a later one. The final stage contains only the runtime image and artifacts deliberately included in it.

> **Textbook Definition:** A multi-stage container build can separate build and runtime environments by copying selected artifacts into a separate base instead of inheriting every build-stage file and tool.

## First Principles

The builder and runtime solve different problems. The builder needs compilers and development dependencies; the runtime needs the executable, runtime libraries, and configuration required to start it. `COPY --from` controls which files cross between them; it does not copy `ENV`, `USER`, `WORKDIR`, or command settings. A stage inherits the configuration of its own `FROM` base; `FROM earlier-stage` deliberately reuses that stage, including its files and configuration. The example below starts the runtime from a fresh base and defines its settings explicitly.

## 1. Separate the Build Environment from the Runtime

```dockerfile
# syntax=docker/dockerfile:1

FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:24-alpine AS runtime-dependencies
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

FROM node:24-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=runtime-dependencies --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/package.json ./package.json
COPY --from=build --chown=node:node /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

The build stage installs development dependencies and compiles `dist/`. A separate dependency stage installs production packages from the same lockfile. The final stage copies only those packages, the module manifest, and compiled output. If the application needs templates, certificates, migrations, or static assets at runtime, copy those deliberately too. Keep `package.json` when runtime behavior depends on it, such as Node's ESM `"type": "module"` setting.

BuildKit follows dependencies between stages. It reuses unchanged steps and skips stages the requested target does not depend on:

```bash
docker buildx build --target build -t orders-api:build .
docker buildx build --target runtime -t orders-api:release .
```

Order stable inputs before changing source to reuse dependency-install layers. A BuildKit cache mount speeds package downloads but is only a performance cache: the build must stay correct if that cache is empty or evicted. Use a secret mount for private package credentials; never pass them through `ARG` or `ENV`, and never let build commands print or persist the secret.

## 2. Match the Artifact to Its Runtime

A file crossing the stage boundary still has platform requirements. Native modules need a compatible CPU architecture, C library, and runtime ABI. Alpine uses musl while Debian-based images use glibc; building a native dependency on one and copying it to the other can fail at startup. Distroless removes the shell and package manager, not the libraries the program needs.

This Go example cross-compiles for the target platform and uses the currently supported Debian 13 static distroless base:

```dockerfile
FROM --platform=$BUILDPLATFORM golang:1.27-alpine AS build
ARG TARGETOS
ARG TARGETARCH
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=build /out/server /server
ENTRYPOINT ["/server"]
```

This assumes the program is statically linked and needs no additional runtime files. A CGO build may require a libc-containing base such as `gcr.io/distroless/base-debian13:nonroot`; HTTPS clients also need CA certificates. Test the final image on the target architecture. If a runtime image has no shell, use its debug variant or an external debugging method rather than assuming `docker exec ... sh` will work.

## 3. Select Build Targets Deliberately

Development, test, and production stages can live in one Dockerfile, but each target must define its own runtime behavior. `docker buildx build --target test` runs the test stage's dependencies; building the production target does not automatically run tests from an unrelated stage. Make CI run tests explicitly and fail the release if they fail.

Build once for the target platforms, inspect the final image, and verify a clean start. Image size, build duration, and vulnerability count depend on the application and base — compare measured artifacts instead of assuming a fixed reduction.

## Summary

Multi-stage builds separate the tools that produce an artifact from the files that run it. `COPY --from` transfers only selected files, while `FROM` selects the inherited base; runtime configuration and native-library compatibility remain explicit. Keep lockfile-driven dependency installation cacheable, target tests deliberately, and validate the final image on the platforms where it will run.

# Docker Multi-Stage Builds

## Definition

**Multi-stage builds** allow you to use multiple `FROM` statements in a single Dockerfile. Each `FROM` begins a new stage. Artifacts from earlier stages can be selectively copied to later stages using `COPY --from=<stage>`. A final stage contains its own base image plus files deliberately installed or copied into it. This enables a smaller runtime image; it does not automatically remove unnecessary dependencies.

Key concepts:

- **Build Stage**: Contains compilers, build tools, dev dependencies
- **Production Stage**: Contains only runtime and application artifacts
- **AS alias**: Names a stage for later reference
- **COPY --from**: Copies files from a specific stage
- **Target build**: Build up to a specific stage (`docker build --target`)

> **Textbook Definition:** A multi-stage container build uses multiple build stages with explicit artifact transfers so the final image includes selected outputs independently of the toolchains and files used to produce them.

## First Principles


Multi-stage builds exist because build tools and runtime needs are disjoint:

1. **The build environment is not the artifact**: compilers, dev deps, and toolchains make images huge and attack-surface wide. Stages copy *only the artifact* (compiled binary, node_modules pruned to prod) into a clean minimal runtime.
2. **Caching is the second product**: cache entries belong to build steps and their inputs — dependency installation before source copy allows source-only changes to reuse the install step. Changed source still rebuilds compilation and affected downstream copy steps. The Dockerfile is ordered by change frequency for exactly this reason.
3. **The distroless endgame**: when the artifact is static (Go, Rust) or self-contained (Node with bundled deps), the runtime stage has no shell, no package manager — minimal by construction (→ 40.1.05).

## Why Do We Need It?

| Problem | Solution |
| ------------------------------- | -------------------------------------------------------- |
| Build tools in production image | Multi-stage: build in one, run in another |
| Large image sizes | Final image has only production deps |
| Security vulnerabilities | Exclude unnecessary tools; scan the actual runtime image |
| Slow CI/CD pipelines | Smaller images = faster pulls |
| Dev/prod parity issues | Same Dockerfile, different targets |
| Dependency on build cache | Isolated stages with clear boundaries |

## How It Works

### Files Cross the Boundary; Build Configuration Does Not

```text
builder: manifests + development tools + source → compile → /app/dist
runtime: clean base + production dependencies + copied dist → node dist/server.js
```

`COPY --from=build /app/dist ./dist` transfers files, not the builder's `ENV`, `USER`, `WORKDIR` or entry point. The runtime inherits settings from its own `FROM` image and must define the remaining configuration. For a Node ESM application, its `package.json` can still be required to interpret `.js` files as modules. Native modules also need a compatible CPU architecture, C library and runtime version; Alpine-built native dependencies cannot be assumed compatible with a Debian runtime.

BuildKit follows stage dependencies. `--target production` builds what that target requires, not necessarily every earlier stage in textual order. Independent stages can execute concurrently; a `COPY --from` adds a dependency.

### What multi-stage builds remove

```text
Single-stage image                 Multi-stage runtime image
--------------------               --------------------------
base image                          base image
production dependencies             production dependencies
development dependencies            compiled output only
compiler and build tools             runtime configuration
source files

```

The runtime image is often smaller because it omits build-only files and tools. There is no reliable fixed size ratio: measure both built images for the target platform and dependency set.

## Code Examples

### Node.js TypeScript Application

```dockerfile
# Stage 1: Dependencies
FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

# Stage 2: Build
FROM deps AS build
COPY . .
RUN npm run build

# Stage 3: Production
FROM node:22-alpine AS production
RUN apk add --no-cache dumb-init
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY package*.json ./
RUN npm ci --omit=dev
USER node
EXPOSE 3000
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/server.js"]

```

### Go Application with Distroless

This builds for the architecture of the Linux build image. Use a platform-aware build with explicit target architecture when cross-compiling; a hardcoded amd64 binary will not run in an arm64 runtime image. Static linking still needs runtime data such as CA certificates when HTTPS is used.


```dockerfile
# Stage 1: Build
FROM golang:1.26-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux \
    go build -ldflags="-s -w" -o /server ./cmd/server

# Stage 2: Production (distroless - no shell, no package manager)
FROM gcr.io/distroless/static-debian12
COPY --from=builder /server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]

```

### Python Flask Application

```dockerfile
# Stage 1: Build wheels
FROM python:3.11-slim AS builder
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt

# Stage 2: Production
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /wheels /wheels
RUN pip install --no-cache-dir /wheels/* && rm -rf /wheels
COPY . .
RUN addgroup --system appgroup && adduser --system --ingroup appgroup appuser
USER appuser
EXPOSE 5000
CMD ["gunicorn", "app:app", "--bind", "0.0.0.0:5000"]

```

### Rust Application with Scratch

A default Rust release build can dynamically link to glibc. Copying that binary into `scratch` leaves its loader and libraries missing. Either build a genuinely static target (with a configured musl toolchain and compatible dependencies) or use a runtime containing the required libraries. Inspect the binary dependencies and run the resulting image; `cargo build --release` alone is not proof of static linking. `scratch` also has no shell or CA bundle unless explicitly copied.

### Angular/Frontend Application

```dockerfile
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build -- --configuration production

FROM nginx:alpine
COPY --from=build /app/dist/myapp/browser /usr/share/nginx/html
COPY nginx.conf /etc/nginx/nginx.conf
EXPOSE 80

```

### Custom Build Targets

```bash
# Build the named build stage from the Node example
docker build --target build -t myapp:debug .

# Build the production stage
docker build --target production -t myapp:approved-release .

# Build the default final target and its dependencies
docker build -t myapp:approved-release .

```

## Real-World Use Cases

### 1. Monorepo with Shared Libraries

A workspace install needs the root lockfile plus each package manifest. A runtime import can also rely on hoisted dependencies and workspace symlinks; copying only an API's local `node_modules` omits part of that resolution graph. Build shared libraries before consumers, then use the package manager's deployment/packing workflow or bundle a self-contained runtime. Install the resulting artifact in a clean container and check an import from the shared library. See [Turborepo packaging boundaries](../40.8-monorepo/40.8.02-turborepo.md).

### 2. Full-Stack Application

```dockerfile
# Frontend build
FROM node:22-alpine AS frontend-build
WORKDIR /frontend
COPY frontend/package*.json ./
RUN npm ci
COPY frontend/ .
RUN npm run build

# Backend build
FROM node:22-alpine AS backend-build
WORKDIR /backend
COPY backend/package*.json ./
RUN npm ci
COPY backend/ .
RUN npm run build

# Production
FROM node:22-alpine
WORKDIR /app
COPY --from=backend-build /backend/dist ./backend/dist
COPY backend/package*.json ./backend/
RUN cd backend && npm ci --omit=dev
COPY --from=frontend-build /frontend/dist ./frontend/dist
USER node
CMD ["node", "backend/dist/server.js"]

```

### 3. Java Spring Boot with GraalVM

The builder must provide both the native-image compiler and the project's build tool (often a committed Maven wrapper). A native executable may still depend on libc and shared libraries. Use a runtime matching those dependencies; `scratch` requires an explicitly static build and necessary runtime data. Verify the executable inside the final image before treating a native-image build as a deployment success.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Not naming stages | Always use `AS` for clarity |
| Copying entire node_modules | Copy package.json first, install, then copy source |
| Not using `--target` for dev builds | Use `--target` for debug/development stages |
| Forgetting `npm prune --omit=dev` | Remove dev deps in final stage |
| Using wrong base image for build vs runtime | Match CPU, libc and runtime ABI; distroless is a packaging choice, not an ABI conversion |
| Deleting build files in a later layer | Remove temporary files in the same `RUN`, or omit them from the final stage |
| Not using BuildKit | Enable BuildKit for parallel stage builds |

## Best Practices

The Node example above provides the dependency/build/runtime split. Use a separate production install or prune before copying runtime dependencies; deleting copied development dependencies in a later layer does not remove their bytes from earlier layers.

1. **Name all stages** — improves readability and caching

2. **Use distroless for final stage** — minimal attack surface

3. **Separate dependency installation from source copy** — better caching

4. **Use `npm ci` not `npm install`** — deterministic builds

5. **Prune dev dependencies** — reduce final image size

6. **Use `--target` for dev/debug** — build specific stages

7. **Leverage BuildKit** — parallel stage execution

8. **Pin base image versions** — reproducible builds

9. **Order dependency inputs before changing source** — BuildKit schedules by dependencies, not the longest textual stage
10. **Scan each stage** — catch vulnerabilities early

## Performance Considerations

| Factor | Impact | Mitigation |
| ------------------ | ---------------- | ----------------------------- |
| Number of stages | Build time | Minimize stages, use BuildKit |
| Stage dependencies | Cache efficiency | Order by change frequency |
| Base image size | Pull time | Use Alpine or distroless |
| Build context | Upload time | `.dockerignore` |
| Parallel builds | Build speed | BuildKit auto-parallelizes |
| Layer size | Push/pull time | Combine small layers |

```bash
# BuildKit parallel build
DOCKER_BUILDKIT=1 docker build -t myapp .

# Build specific target
docker build --target builder -t myapp:debug .

# Build with no cache
docker build --no-cache -t myapp .

# Check image size
docker images myapp

```

## Summary

Multi-stage builds separate build-time and run-time concerns, allowing smaller runtime images with explicit artifact and dependency boundaries. They improve caching, reduce image sizes, and enable consistent dev/prod environments using a single Dockerfile with different target stages.

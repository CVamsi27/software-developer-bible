# Dockerfile Best Practices & Security

## Definition

**Dockerfile Best Practices** encompass the patterns, optimizations, and security measures for creating efficient, secure, and maintainable container images. Key principles include minimizing image size, leveraging layer caching, running with least privilege, and eliminating vulnerabilities.

## First Principles

Dockerfile best practices are cache economics + image physics:

1. **Layer order = cache strategy**: least-frequently-changing first (package installs), most-volatile last (source, → 40.1.04). Every best-practice list is this rule applied.
2. **Every layer persists forever in the image**: `rm` in a *later* layer doesn't shrink earlier ones — hence `apt clean && rm` in the *same* RUN, and multi-stage for real slimming.
3. **The image is a supply-chain artifact**: pin bases by digest, non-root USER, one process per container (PID 1 semantics), .dockerignore — each is attack-surface or reproducibility, not style (→ 40.1.08).

## Why Do We Need It?

1. **Smaller images**: Faster deployments, less storage, lower bandwidth
2. **Faster builds**: Proper layer ordering maximizes cache utilization
3. **Security**: Fewer attack vectors with minimal dependencies and non-root users
4. **Compliance**: Meeting security standards (PCI-DSS, SOC2) for containerized apps
5. **Reproducibility**: Deterministic builds with pinned versions

## How It Works

### Why layer physics make `rm` useless across layers

Each Dockerfile instruction creates an immutable layer; the final image is a **union mount** — a lower layer's files remain in the image even when an upper layer deletes or overwrites them (whiteout files hide them from view, not from storage). This is why `apt-get clean` in a *later* RUN saves nothing: the apt lists live forever in the layer that created them. Every size rule derives from this: combine update/install/clean in **one RUN** (one layer, transient state never persisted), multi-stage builds (build toolchain layers never reach the final image at all — `COPY --from` copies *files*, not layers), and `--no-install-recommends` for apt (recommends pull tens of packages into a layer that cannot shed them).

### BuildKit changed the rules worth knowing

Modern builds run on **BuildKit**, which turns the layer model into a content-addressed DAG: unchanged subtrees skip entirely, *and* stages without dependents never execute (a test stage in the same Dockerfile runs only when targeted — `docker build --target` or `docker buildx bake`). Frontend features matter in practice: cache mounts (`RUN --mount=type=cache,target=/root/.npm`) persist package caches *across* builds without baking them into layers — the correct fix for "npm ci is slow," versus the anti-pattern of moving `COPY . .` before `npm ci` to "help" caching; secrets (`RUN --mount=type=secret,id=npmrc`) keep tokens out of image history entirely (`--build-arg` values are inspectable in image metadata forever); and SSH mounts forward agent access without copying keys. Order rules still apply — BuildKit parallelizes and skips, but a change to an early layer still invalidates everything downstream of it.

### The runtime contract: PID 1 and signal handling

`CMD ["node", "main.js"]` (exec form) makes your process **PID 1** in the container — the kernel routes SIGTERM to it, and Node/Go handle signals fine; but `CMD npm start` (shell form) or a shell wrapper makes the *shell* PID 1, which by default does not forward signals to children — the container ignores `docker stop`'s SIGTERM and dies at the SIGKILL grace timeout, losing graceful shutdown (→ 30.3.1). Distroless images sidestep the class entirely (no shell to wrap); for shell-wrapped apps, `tini` or `docker run --init` provides a signal-forwarding PID 1. `HEALTHCHECK` failures pair with orchestrator probes: Docker's own health status matters under plain `docker run`, but under Kubernetes the `livenessProbe`/`readinessProbe` replace it (K8s ignores Docker HEALTHCHECK) — knowing which layer owns health in your runtime is the senior tell.

## Real-World Usage

- **The 1 GB → 80 MB image is a five-move story**: multi-stage (drop toolchain), alpine/distroless base (drop libc and package manager), one-RUN apt with clean (drop layer ghosts), `npm ci --omit=dev` (drop dev deps from the runtime layer), `.dockerignore` (keep build context small — context upload is often the *build* bottleneck, not compute). Each move is observable: `docker history` shows per-layer sizes, `dive` shows wasted bytes.
- **Base-image updates are a rebuild, not a re-release**: with digest-pinned bases and a CI job that rebuilds on base digest change (Renovate pinning `node:22-alpine@sha256:...`), the app image picks up OpenSSL/libc CVE fixes by merge — the supply-chain discipline that makes scanning actionable instead of a quarterly fire drill. Scan in CI (`trivy image --exit-code 1 --severity HIGH,CRITICAL`) and gate; a scanner nobody reads is decoration.
- **Non-root is also a Kubernetes prerequisite**: `USER app` + a read-only root filesystem (`securityContext.runAsNonRoot: true`, `readOnlyRootFilesystem: true`) is what lets a pod run without privileged escape vectors — and the image must actually work that way (writable `/tmp` via emptyDir, not the root fs), which is why the Dockerfile is the contract the pod spec depends on.
- **The cache-order mistake that survives code review**: copying source before the dependency install still builds and still works — until the day you need a fast CI, at which point every commit rebuilds the dependency layer. The pattern is invisible in correctness and only shows in lead time, which is why it belongs in review checklists rather than "works on my machine."

### 1. Leverage Multi-Stage Builds

```dockerfile
# Stage 1: Build
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:22-alpine
RUN addgroup -g 1001 app && adduser -u 1001 -G app -s /bin/sh -D app
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
USER app
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

### 2. Optimize Layer Caching

```dockerfile
# BAD: Cache invalidated on every code change
COPY . .
RUN npm ci
RUN npm run build

# GOOD: Copy only what's needed, layer strategically
COPY package*.json ./
RUN npm ci # Cached unless package.json changes
COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build # Cached unless src/ changes
COPY public/ ./public/ # Static files rarely change
```

### 3. Use Distroless or Slim Base Images

```dockerfile
# BAD: Full OS with unnecessary tools
FROM node:22

# GOOD: Slim variant
FROM node:22-slim

# BEST: Distroless (no shell, no package manager)
FROM gcr.io/distroless/nodejs20-debian12
COPY --from=builder /app /app
CMD ["/app/dist/main.js"]
```

### 4. Run as Non-Root User

```dockerfile
# Add user and group
RUN addgroup -g 1001 app && \
    adduser -u 1001 -G app -s /bin/sh -D app

# Set ownership
COPY --chown=app:app . /app

# Switch to non-root
USER app
```

### 5. Pin Base Image Versions

```dockerfile
# BAD: Unpinned version
FROM node:22

# BAD: 'latest' tag
FROM node:latest

# GOOD: Pinned digest
FROM node:22-alpine@sha256:1234abcd...

# GOOD: Specific minor version
FROM node:22.14.0-alpine
```

### 6. Minimize Layers

```dockerfile
# BAD: Many separate RUN commands
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git
RUN apt-get clean

# GOOD: Combine related commands
RUN apt-get update && \
    apt-get install -y curl git && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*
```

### 7. Use .dockerignore

```
# .dockerignore
.git
node_modules
dist
.env
*.md
Dockerfile
docker-compose.yml
.gitignore
coverage
test
```

### 8. Add Healthcheck

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1
```

### 9. Set Metadata Labels

```dockerfile
LABEL org.opencontainers.image.title="My App"
LABEL org.opencontainers.image.description="Production application"
LABEL org.opencontainers.image.version="1.2.3"
LABEL org.opencontainers.image.created="2025-01-15T10:00:00Z"
LABEL org.opencontainers.image.source="https://github.com/org/repo"
```

### 10. Security Scanning

```bash
# Scan with Trivy
trivy image myapp:latest

# Scan with Docker Scout
docker scout cves myapp:latest

# Scan with Snyk
snyk container test myapp:latest
```

## Summary

Dockerfile best practices reduce image size, improve build speed, and enhance security. Use multi-stage builds, optimize layer order, run as non-root, pin versions, and scan for vulnerabilities in CI/CD.

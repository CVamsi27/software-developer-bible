# Dockerfile Best Practices & Security

A Dockerfile can build successfully while putting credentials in an image layer, rebuilding dependencies on every code change, or starting the service with privileges it does not need. A good review follows the artifact from build inputs to the process that runs in production.

## Definition

**Dockerfile best practices** are build and runtime choices that make an image understandable, repeatable, efficient to produce, and appropriately constrained when it runs. They specify the artifact inputs and process contract.

> **Textbook Definition:** Dockerfile engineering specifies build inputs, layer dependencies, runtime contents and execution privileges so an image can be rebuilt, inspected and operated under an explicit artifact contract.

## First Principles

A Docker build receives a context, evaluates instructions into reusable results, and assembles a final image. The Dockerfile should make each boundary visible: keep irrelevant files and credentials out of the build context, order stable inputs before frequently changing source so the cache can be reused, keep build secrets out of layers and logs, and include only the files and privileges the runtime process requires. A smaller image can reduce transfer and scanning work, but size alone establishes neither security nor compatibility — measure the result and test the final image.

## 1. Keep the Context and Cache Deliberate

The build context is the set of files available to `COPY` and `ADD`. A `.dockerignore` file prevents local dependencies, credentials, and repository history from being sent unnecessarily:

```text
.git
node_modules
.env
.env.*
coverage
.nyc_output
```

Do not exclude files a build stage needs. If tests are in the context and the Dockerfile uses `COPY . .`, excluding the tests also removes them from that stage.

Copy dependency manifests before source that changes often. BuildKit reuses the dependency-install step while those manifests stay unchanged:

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine AS build
WORKDIR /app

COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build
```

This assumes the lockfile describes the full build dependency set and that `src/` plus `tsconfig.json` are sufficient build inputs — copy any additional required files explicitly. A cache mount speeds package downloads but is disposable; the build must still succeed when it is empty or evicted.

A later instruction cannot remove bytes committed by an earlier filesystem layer. If a package manager creates temporary lists, clean them in the same `RUN` instruction that installs packages. Do not combine unrelated commands only to chase fewer layers; preserve useful cache boundaries and readable intent. For a separate runtime image, use a multi-stage build and copy only selected artifacts; see [Multi-Stage Builds](40.1.04-multi-stage-builds.md).

## 2. Keep Credentials Out of the Artifact

Never pass credentials through Dockerfile `ARG` or `ENV`: build metadata, command output, or a later layer can expose them. BuildKit secret mounts provide temporary access to a file for one instruction:

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
```

Supply the secret from a protected path in the build environment, and ensure the command neither prints it nor copies it into an artifact. Runtime credentials have a separate lifecycle — inject them through the deployment platform or a supported secret mechanism rather than baking them into the image.

## 3. Make the Runtime Contract Explicit

Choose a maintained base image containing the libraries the application needs. Alpine uses musl rather than glibc, so native modules built for one C library may not run on the other. Distroless removes shell and package manager but still needs compatible libraries, certificates, and runtime files. Test the actual final image instead of assuming the smallest base is the best fit.

Use a reviewed digest when a release requires exact base-image bytes. A tag such as `node:24-alpine` is a convenient update channel but can move; a digest pins a particular artifact and should be refreshed through an owned update process. Pinning does not make an image vulnerability-free, so rebuild and roll out approved base updates.

Run the application as a non-root user when the image supports it. A read-only root filesystem can further constrain writes, but the app may need explicit writable mounts for temporary files, sockets, or state. Drop capabilities and configure seccomp or other policy at the runtime boundary according to the threat model — these controls reduce privilege, but none alone proves the container cannot escape its host boundary.

Use exec-form startup so the intended process receives termination signals directly:

```dockerfile
USER node
CMD ["node", "dist/server.js"]
```

The application still needs a graceful shutdown path: stop accepting work, drain in-flight requests, and exit before the runtime's stop deadline. A Docker `HEALTHCHECK` records container health; it does not restart an unhealthy process. Kubernetes uses its own startup, readiness, and liveness probes rather than the image's Docker health check.

Labels such as `org.opencontainers.image.source` and `org.opencontainers.image.version` help identify an artifact, but they are claims from the build. Generate provenance and verify the expected identity and digest in the release process; see [Image Signing, SBOM & Supply Chain Security](40.1.08-image-signing-sbom-supply-chain.md).

## 4. Review the Image That Will Ship

Scan the immutable image digest produced by CI, not a mutable tag that may later resolve to different content. Review findings against the application's reachability and deployment context, set a clear release policy, and rebuild when the approved base or dependencies change. A scanner reports known issues in the data it has; it does not establish that the artifact is safe.

During review, ask:

1. Which files and build inputs enter the context?
2. Which changes invalidate expensive steps, and can the cache be discarded safely?
3. Could a credential appear in an image layer, metadata, artifact, or log?
4. What user, writable paths, and signals does the runtime require?
5. Which exact image digest is tested, scanned, approved, and deployed?

## Summary

Treat a Dockerfile as the contract between build inputs and the production process. Control the context, order stable dependencies for cache reuse, use temporary secret mounts, and make the final image's files, user, and shutdown behavior explicit. Verify and scan the exact artifact that will be deployed; no single optimization or scanner replaces runtime testing and release policy.

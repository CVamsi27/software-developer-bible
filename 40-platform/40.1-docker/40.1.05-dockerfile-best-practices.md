# Dockerfile Best Practices & Security

## Definition

Dockerfile best practices help produce images that are smaller, easier to maintain, and safer to run. Reuse unchanged build layers, include only the runtime files the application needs, run with the fewest required privileges, and check dependencies for known vulnerabilities.

> **Textbook Definition:** Dockerfile engineering specifies reproducible build inputs, layer dependencies, runtime contents, and execution privileges so an image can be rebuilt, inspected, and operated under an explicit artifact contract.

## First Principles

Dockerfile best practices are cache economics + image physics:

1. **Layer order = cache strategy**: least-frequently-changing first (package installs), most-volatile last (source, → 40.1.04). Separate concerns still matter: runtime privileges, secret handling and dependency compatibility are independent of cache ordering.
2. **Bytes committed in an earlier image layer remain in that image**: `rm` in a *later* layer doesn't shrink earlier ones — hence `apt clean && rm` in the *same* RUN, and multi-stage for real slimming.
3. **The image is a supply-chain artifact**: pin bases by digest, non-root USER, one process per container (PID 1 semantics), .dockerignore — each is attack-surface or reproducibility, not style (→ 40.1.08).

## Why Do We Need It?

1. **Smaller images**: Faster deployments, less storage, lower bandwidth
2. **Faster builds**: Proper layer ordering maximizes cache utilization
3. **Security**: Fewer attack vectors with minimal dependencies and non-root users
4. **Compliance**: Meeting security standards (PCI-DSS, SOC2) for containerized apps
5. **Reproducibility**: Deterministic builds with pinned versions

## How It Works

### Why layer physics make `rm` useless across layers

Filesystem-changing instructions such as `RUN`, `COPY` and `ADD` create filesystem layers; configuration instructions such as `ENV` and `CMD` update image configuration; `WORKDIR` can also create a directory. The final filesystem presents a **union** of its layers. If a later layer deletes a file, an earlier layer still contains its bytes; a whiteout hides the file from the merged view but does not reclaim that storage. Therefore, remove temporary package lists in the same `RUN` that creates them. Multi-stage builds keep build-only files out of the final stage: `COPY --from` copies selected files, not the builder's layers. Combining `apt-get update`, installation and cleanup in one `RUN` is useful for removing transient package lists, not as a general goal to minimize the number of instructions.

### BuildKit changed the rules worth knowing

Modern builds run on **BuildKit**, which turns the layer model into a content-addressed DAG: unchanged subtrees skip entirely, *and* stages without dependents never execute (a test stage in the same Dockerfile runs only when targeted — `docker build --target` or `docker buildx bake`). Frontend features matter in practice: cache mounts (`RUN --mount=type=cache,target=/root/.npm`) persist package caches *across* builds without baking them into layers — the correct fix for "npm ci is slow," versus the anti-pattern of moving `COPY . .` before `npm ci` to "help" caching; secrets (`RUN --mount=type=secret,id=npmrc`) avoid embedding the mounted secret itself in layers; the invoked command can still leak it to logs or write it into artifacts. Do not pass secrets through build arguments or ENV metadata; and SSH mounts forward agent access without copying keys. Order rules still apply — BuildKit parallelizes and skips, but a change to an early layer still invalidates everything downstream of it.

### The runtime contract: PID 1 and signal handling

`CMD ["node", "main.js"]` (exec form) starts Node directly as the container's main process. Docker sends the configured stop signal to that process; the application must handle it, drain work and exit before the stop deadline. With `CMD npm start` (shell form), the shell becomes PID 1 and may not forward signals to its child. A small init such as `tini` or `docker run --init` can forward signals and reap orphaned children, but application shutdown still needs explicit handling (→ 30.3.1). A Docker `HEALTHCHECK` records Docker health state; it does not restart an unhealthy process. Kubernetes ignores the image's Docker `HEALTHCHECK` and requires its own startup, readiness and liveness probes.

## Real-World Usage

- **Inspect what each change actually removes**: multi-stage excludes build tools; runtime-only dependencies omit development tools; `.dockerignore` restricts build context. Alpine replaces glibc with musl, while distroless still contains the runtime libraries its application needs. Measure the built image and `docker history`; there is no universal size-reduction ratio.
- **Base-image updates are a rebuild, not a re-release**: with digest-pinned bases and a CI job that rebuilds on base digest change (Renovate pinning `node:24-alpine@sha256:...`), the app image picks up OpenSSL/libc CVE fixes after a new build and rollout — the supply-chain discipline that makes scanning actionable instead of a quarterly fire drill. Scan in CI (`trivy image --exit-code 1 --severity HIGH,CRITICAL`) and gate; a scanner nobody reads is decoration.
- **Non-root is a Kubernetes security control**: `USER app` plus a read-only root filesystem (`securityContext.runAsNonRoot: true`, `readOnlyRootFilesystem: true`) reduces process privileges and prevents ordinary writes to the root filesystem, but does not eliminate container-escape risks. The image must work with that setting; mount a writable path such as `/tmp` with `emptyDir` when required.
- **The cache-order mistake that survives code review**: copying source before the dependency install still builds and still works — until the day you need a fast CI, at which point every commit rebuilds the dependency layer. The pattern is invisible in correctness and only shows in lead time, which is why it belongs in review checklists rather than "works on my machine."

### 1. Leverage Multi-Stage Builds

This example assumes build tools are development dependencies and runtime dependencies remain in `dependencies`. Install both for compilation, then prune development packages before copying the runtime tree. Verify native dependencies and the chosen runtime base are compatible.

```dockerfile
# Stage 1: Build
FROM node:24-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --omit=dev

# Stage 2: Production
FROM node:24-alpine
RUN addgroup -g 1001 app && adduser -u 1001 -G app -s /bin/sh -D app
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/package*.json ./
USER app
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

### 2. Optimize Layer Caching

```dockerfile
# BAD: Cache invalidated on every code change
COPY . .
RUN npm ci
RUN npm run build

# GOOD: Copy only what's needed, layer strategically
COPY package*.json ./
RUN npm ci # Cached unless package.json changes
COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build # Cached unless src/ changes
COPY public/ ./public/ # Static files rarely change
```

### 3. Use Distroless or Slim Base Images

A full Node base can be appropriate when runtime libraries or operational tools are required. Slim reduces packaged tools; Alpine uses musl, which changes native-module compatibility. Distroless removes the shell/package manager but still needs compatible compiled dependencies, explicit user settings and a debugging plan. Choose by required runtime files and measured risk, rather than ranking every smaller image as automatically better.

### 4. Run as Non-Root User

```dockerfile
# Add user and group
RUN addgroup -g 1001 app && \
    adduser -u 1001 -G app -s /bin/sh -D app

# Set ownership
COPY --chown=app:app . /app

# Switch to non-root
USER app
```

### 5. Pin Base Image Versions

The digest below is a placeholder, not a valid build input. Resolve the approved image's full digest for the intended platform, record it, and automate reviewed updates. A digest pins bytes; it does not guarantee vulnerability-free contents.


```dockerfile
# BAD: Mutable major tag when reproducible release inputs are required
FROM node:24

# BAD: 'latest' tag
FROM node:latest

# GOOD: Pinned approved digest (replace the placeholder with a real digest)
FROM node:24-alpine@sha256:<verified-full-digest>

# Patch tag narrows updates but remains a mutable registry pointer
FROM node:24-alpine
```

### 6. Keep Temporary Files Out of Committed Layers

```dockerfile
# GOOD: remove package lists in the same filesystem layer that installed packages
RUN apt-get update && \
    apt-get install -y curl git && \
    rm -rf /var/lib/apt/lists/*
```

Combining unrelated commands only to chase a smaller layer count can make builds harder to read and reduce cache reuse. Combine operations when doing so keeps temporary files out of the committed filesystem layer; otherwise, optimize cache ordering and build contents.

### 7. Use .dockerignore

```
# .dockerignore
.git
node_modules
dist
.env
.env.*
.gitignore
coverage
.nyc_output
```

Do not exclude a path that a build or test stage needs. The Dockerfile and `.dockerignore` are still sent to the builder as control files, but excluding the tests directory from the context would make `COPY . .` omit those tests.

### 8. Add Healthcheck

This Node image must expose `/health`. A distroless image cannot run a shell-form probe with wget; configure a supported exec probe or orchestrator-native HTTP check instead.


```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/health', r => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"
```

### 9. Set Metadata Labels

```dockerfile
LABEL org.opencontainers.image.title="My App"
LABEL org.opencontainers.image.description="Production application"
LABEL org.opencontainers.image.version="1.2.3"
ARG BUILD_DATE
LABEL org.opencontainers.image.created=$BUILD_DATE
LABEL org.opencontainers.image.source="https://github.com/org/repo"
```

### 10. Security Scanning

```bash
# Scan with Trivy
trivy image myapp@sha256:<verified-full-digest>

# Scan with Docker Scout
docker scout cves myapp@sha256:<verified-full-digest>

# Scan with Snyk
snyk container test myapp@sha256:<verified-full-digest>
```

## Summary

Dockerfile best practices reduce image size, improve build speed, and enhance security. Use multi-stage builds, optimize layer order, run as non-root, pin versions, and scan for vulnerabilities in CI/CD.

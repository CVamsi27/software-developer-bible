# Docker Production Patterns — Security, Optimization, Multi-Stage

A container passes a local smoke test, then fails in production because it cannot write to the root filesystem, exceeds its memory limit, or receives SIGTERM without draining work. The image is only one part of the production contract: the release also needs bounded privileges, configuration, health, state, and recovery.

## Definition

A **production container pattern** is a repeatable choice for building, configuring, starting, observing, and replacing containers under real workload and failure conditions. It ties image behavior to an operational service contract.

> **Textbook Definition:** Production container engineering defines the artifact identity, runtime permissions and resources, lifecycle behavior, external state, and recovery controls required to operate a containerized service.

## First Principles

Treat the image as an immutable release artifact and the running container as a replaceable process. Inject environment-specific configuration at runtime, keep durable state outside the writable container layer, and define what happens when health, capacity, or dependencies fail. Each control needs an owner and a test.

## How It Works

### 1. Promote One Artifact

Build and test the image once, then promote its immutable digest through environments. A tag is a movable reference; if deployment resolves the same tag later, it may select different bytes. Record the digest and the prior approved digest so rollback restores a known artifact.

A locked dependency file and digest-pinned base constrain inputs, but they do not prove the build is reproducible. Network downloads, lifecycle scripts, platform-specific dependencies, and generated timestamps can still vary. Rebuild and compare when reproducibility is part of the release requirement.

Keep credentials out of build `ARG`s, image `ENV`s, and committed image layers. Use a build secret mount when a build needs private package access; inject runtime credentials from the deployment secret manager or a tightly scoped mounted file. A local Compose secret file is not encrypted storage.

### 2. Run Under the Permissions and Limits the Service Needs

Start with a non-root image user. Then test the application under a read-only root filesystem, dropped capabilities, a memory/CPU budget, and only the writable mounts it needs:

```bash
docker run --rm --read-only --tmpfs /tmp:rw,size=64m \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --memory=512m --cpus=1 --pids-limit=128 \
  -p 127.0.0.1:3000:3000 myapp@sha256:<approved-digest>
```

This is a starting policy, not a universal configuration. The app must fit within the memory limit, write only to mounted paths, and listen on `0.0.0.0:3000` inside the container; the published host side is limited to loopback. Validate the actual cgroup behavior and runtime support — Compose and orchestrator resource declarations are enforced by their target engine, not by YAML alone. A non-root user and a smaller base reduce some risks but do not remove the shared-kernel boundary.

### 3. Make Startup and Shutdown Observable

A health check reports whether its probe succeeds; Docker does not restart a container solely because it becomes unhealthy. Restart policies react to process exit. An orchestrator may use its own readiness and liveness probes to remove traffic or restart a workload. Use the probe that matches the platform and keep health endpoints bounded.

On stop, Docker sends the configured stop signal, normally SIGTERM, then SIGKILL when the grace period expires. The application must stop accepting new work, finish or safely abandon in-flight work, close its resources, and exit before that deadline. Exec-form commands or a small init improve signal forwarding and child reaping; neither supplies application-level draining.

### 4. Keep State and Rollback Compatible

Treat container-local writes as disposable. Put database state in persistent storage or an external service, choose a consistent backup method, and prove restore against a recovery objective. Promote schema changes with an expand/contract sequence when old and new application versions may overlap. Rolling back an image does not reverse a migration or make an incompatible schema usable.

For a single-host service, Compose can declare the app, storage, and dependencies, but the operator still owns host patching, TLS, backups, rollout, and failure recovery. For multi-host scheduling, controller-managed rollouts, or automatic failover, select an orchestrator and validate its storage and health contracts.

### 5. Verify What Is Actually Running

Scan the built image digest using a current vulnerability database and a documented exception policy. A clean scan covers known findings at that time; it is not proof the image is defect-free. For higher-assurance releases, verify the signed digest, expected builder/source provenance, and required SBOM at deployment admission; see [image signing and supply-chain security](40.1.08-image-signing-sbom-supply-chain.md).

During an incident, correlate the running digest and configuration with application logs and user-facing metrics. Check restart count, memory events, CPU throttling, probe failures, and dependency status before choosing a mitigation. A green container status cannot establish that users received correct responses.

## Summary

Reliable container operation comes from a verified image digest plus an explicit runtime contract. Limit privileges and resources to what the process needs, inject secrets safely, externalize state, and test startup, shutdown, health, migration, and rollback behavior on the target engine. An image scan, health check, or non-root user is one piece of evidence, not a release guarantee.

# Docker Production Patterns — Security, Optimization, Multi-Stage

## Definition

**Docker production patterns** are the conventions that make a container image *safe and reproducible* as a deployable artifact rather than a hand-built environment. The definition is a contract on three axes:

> **Textbook Definition:** Production container patterns define build provenance, runtime privileges, lifecycle behavior, configuration injection, and recovery controls needed to operate a deployable image reliably.

```text
reproducible     deterministic inputs      pinned base digest, lockfile, no :latest
                 multi-stage build          build toolchain absent from the final image
least privilege  non-root user (UID fixed) no write to the filesystem (read-only rootfs)
                 no secrets in layers       (build args/ENV are visible in image history)
minimal          slim/distroless base      fewer packages ⇒ smaller attack surface
                 .dockerignore              no .git, node_modules, or local env files
```

A runtime contract needs evidence: identify the exact image digest, check its contents, define required permissions and writable paths, and verify startup/shutdown under the deployment's limits. A lockfile and pinned base narrow build inputs; network downloads, lifecycle scripts and generated timestamps can still change outputs. Reproducibility must be checked rather than inferred from two configuration settings.

Non-root users, read-only filesystems and restricted capabilities reduce what an exploited process can do. They do not guarantee that an exploit stays inside the container: mounted credentials, shared kernels, accessible services and host mounts remain part of the threat model. Measure build and pull costs for the actual image instead of assuming a fixed cache or size improvement.

## First Principles

Containers in production obey the same physics as any process, plus orchestration:

1. **PID 1 must reap zombies and forward signals** — the shell-form CMD breaks both; exec-form + a real init (tini) is the fix. Signal handling is graceful shutdown (→ 30.3.1.01) at container granularity.
2. **Resource limits are the interface to neighbors**: exceeding a memory limit can cause an OOM kill, subject to cgroup and swap policy; CPU limits can throttle. Sizing them is capacity planning (→ 30.2.1.12), and JVM/Node runtimes need explicit awareness of cgroup limits.
3. **Logs to stdout, config via env, state via volumes** — the 12-factor mapping (→ 40.9) is what makes a container schedulable by anything.

## Multi-Stage Build (Production)

```dockerfile
# Stage 1: Build
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --omit=dev

# Stage 2: Production
FROM node:22-alpine AS production
WORKDIR /app

# Security: run as non-root user
RUN addgroup -g 1001 -S appgroup
RUN adduser -S appuser -u 1001 -G appgroup

# Copy only production dependencies
COPY --from=builder --chown=appuser:appgroup /app/dist ./dist
COPY --from=builder --chown=appuser:appgroup /app/node_modules ./node_modules
COPY --from=builder --chown=appuser:appgroup /app/package.json ./

# Security: no root access
USER appuser

# Health check
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/health', r => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"

EXPOSE 3000
CMD ["node", "dist/main.js"]
```

## Security Best Practices

Build checks and runtime controls have different owners. Keep scanners in CI rather than installing them into the final image. Scan the built digest and apply an explicit vulnerability policy, including justified exceptions and reviewed base updates. A clean scan covers known findings from its database; it is not proof of no vulnerabilities.

At runtime, request the permissions the process actually needs:

```bash
# The app must work without root writes or Linux capabilities.
docker run --rm --read-only --tmpfs /tmp:rw,size=64m \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --memory=512m --cpus=1 \
  -p 127.0.0.1:3000:3000 myapp:approved-release
```

The example assumes port 3000 does not need a privileged bind and `/tmp` is the only required writable path. Explicitly mount other required state; do not make the whole root filesystem writable just to hide a missing path.

## Docker Compose (Single-Host Deployment Sketch)

This is an illustrative local topology, not a report of Docita's deployed configuration. Replace placeholder credentials through the application's supported secret injection, configure TLS and backup/restore, and test migrations and shutdown before using it in production. A fixed host port supports one API replica; multiple replicas need an entry point with a deliberate load-balancing/port strategy.


```yaml
# docker-compose.prod.yml

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
      target: production
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgresql://user:pass@db:5432/appdb
      - REDIS_URL=redis://redis:6379
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    deploy:
      replicas: 1
      resources:
        limits:
          cpus: '2'
          memory: 2G
        reservations:
          cpus: '1'
          memory: 1G
    healthcheck:
      test: ["CMD", "node", "-e", "require('http').get('http://localhost:3000/health', r => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"]
      interval: 30s
      timeout: 10s
      retries: 3
    restart: unless-stopped

  db:
    image: postgres:15-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d appdb"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources:
        limits:
          cpus: '4'
          memory: 8G

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
  redis_data:
```

## Image Contents and Release Recovery

Choose a base compatible with the application's native dependencies. Slim, Alpine and distroless have different libc/tool/debugging contracts; smaller bytes alone do not establish a safer deployment. Record image size for the selected platform and identify which runtime files account for it.

Promote the tested digest through environments instead of rebuilding per environment. Inject runtime configuration at deployment, record the previous approved digest, and verify rollback against database compatibility. A base-image security fix requires rebuilding and redeploying; moving a tag does not patch an already running container.

## Container Security Checklist

```markdown
## Pre-Deployment
- [ ] Base image digest and scan timestamp satisfy the reviewed vulnerability policy
- [ ] Running as non-root user
- [ ] No secrets in image layers
- [ ] .dockerignore excludes sensitive files
- [ ] Health check configured
- [ ] Resource limits set

## Runtime
- [ ] Read-only filesystem (where possible)
- [ ] Dropped capabilities
- [ ] No privileged mode
- [ ] Network isolation
- [ ] Logging configured

## Monitoring
- [ ] Container metrics (CPU, memory, network)
- [ ] Application metrics (errors, latency)
- [ ] Log aggregation
- [ ] Alerting on anomalies
```

## Summary

1. **Multi-stage builds are the default, not an optimization** — build toolchain in one stage, runtime artifacts in another; explicitly verify excluded tools and required runtime libraries
2. **The production container is unprivileged and contains no embedded secrets** — non-root USER, secrets via orchestration or mounted files, never baked into layers
3. **Health checks and graceful shutdown make containers orchestratable** — a container that lies about health breaks rolling deploys and self-healing
4. **Compose can deploy a production single-host application** — multi-host scheduling, policy, and failover require an appropriate orchestrator and operational design
5. **Images are a supply-chain surface** — pin digests, scan continuously, rebuild on base-image CVEs

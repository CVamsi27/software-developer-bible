# Docker Production Patterns — Security, Optimization, Multi-Stage

## TL;DR

**A production image is a reproducible artifact, not a hand-built environment** — multi-stage builds are the default rather than an optimization, so the runtime layer carries the compiled output and no toolchain. The properties that make it safe: unprivileged `USER`, secrets injected at runtime (never baked into a layer, which is forever), pinned base images by digest with a slim or distroless runtime, a `.dockerignore` that keeps build context small, and explicit resource limits and health checks. Smaller images are not just tidy — they are a smaller attack surface, a faster cold start and a cheaper registry.

---

## First Principles

Containers in production obey the same physics as any process, plus orchestration:

1. **PID 1 must reap zombies and forward signals** — the shell-form CMD breaks both; exec-form + a real init (tini) is the fix. Signal handling is graceful shutdown (→ 30.3.1.01) at container granularity.
2. **Resource limits are the interface to neighbors**: memory limits cause OOM-kill (not swapping); CPU limits throttle. Sizing them is capacity planning (→ 30.2.1.12), and JVM/Node runtimes need explicit awareness of cgroup limits.
3. **Logs to stdout, config via env, state via volumes** — the 12-factor mapping (→ 40.9) is what makes a container schedulable by anything.

---

## Definition

**Docker production patterns** are the conventions that make a container image *safe and reproducible* as a deployable artifact rather than a hand-built environment. The definition is a contract on three axes:

```text
reproducible     deterministic inputs      pinned base digest, lockfile, no :latest
                 multi-stage build          build toolchain absent from the final image
least privilege  non-root user (UID fixed) no write to the filesystem (read-only rootfs)
                 no secrets in layers       (build args/ENV are visible in image history)
minimal          slim/distroless base      fewer packages ⇒ smaller attack surface
                 .dockerignore              no .git, node_modules, or local env files
```

Three properties define a production-grade image, and each has a failure mode it prevents:

1. **Determinism** — the same commit must produce the same image, which requires pinning the base image by digest and installing from a lockfile; `RUN npm install` (instead of `npm ci`) and a floating `node:latest` are how "it worked yesterday" becomes unexplainable.
2. **Least privilege at runtime** — a container that is not a root user, cannot write outside its declared volumes, and carries no credentials can be exploited without becoming a cluster-wide incident. Secrets belong in the orchestrator's secret store injected at runtime, never baked into a layer (layers are readable by anyone who can pull the image).
3. **Layer-cache discipline** — the build order encodes what can be cached, so dependency manifests are copied and installed *before* application source: copying the whole repo first invalidates the dependency layer on every source change and turns a 20-second build into a 5-minute one.

The clustering question that usually follows is deliberate placement of each instruction — build toolchain and dev dependencies in an early stage, the runtime artifact and nothing else in the final stage — because "small and non-root" is not an aesthetic preference but a reduction of both attack surface and cold-start time.

## Multi-Stage Build (Production)

```dockerfile
# Stage 1: Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:20-alpine AS production
WORKDIR /app

# Security: run as non-root user
RUN addgroup -g 1001 -S appgroup
RUN adduser -S appuser -u 1001 -G appgroup

# Copy only production dependencies
COPY --from=builder --chown=appuser:appgroup /app/dist ./dist
COPY --from=builder --chown=appuser:appgroup /app/node_modules ./node_modules
COPY --from=builder --chown=appuser:appgroup /app/package.json ./

# Security: no root access
USER appuser

# Health check
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1

EXPOSE 3000
CMD ["node", "dist/main.js"]
```

## Security Best Practices

```dockerfile
# 1. Use specific base image version
FROM node:20.11-alpine # Not node:latest

# 2. Run as non-root user
RUN addgroup -g 1001 -S appgroup && \
    adduser -S appuser -u 1001 -G appgroup
USER appuser

# 3. Don't store secrets in image
# Bad: ENV DB_PASSWORD=secret
# Good: Use Docker secrets or runtime environment

# 4. Scan for vulnerabilities
RUN apk add --no-cache trivy && \
    trivy fs --severity HIGH,CRITICAL .

# 5. Use .dockerignore
# node_modules
# .git
# .env
# *.md

# 6. Set read-only filesystem
# docker run --read-only --tmpfs /tmp

# 7. Drop capabilities
# docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE
```

## Docker Compose (Production)

```yaml
# docker-compose.prod.yml
version: '3.8'

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
      target: production
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgresql://user:pass@db:5432/docita
      - REDIS_URL=redis://redis:6379
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    deploy:
      replicas: 3
      resources:
        limits:
          cpus: '2'
          memory: 2G
        reservations:
          cpus: '1'
          memory: 1G
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
    restart: unless-stopped

  db:
    image: postgres:15-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data
    environment:
      POSTGRES_DB: docita
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d docita"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources:
        limits:
          cpus: '4'
          memory: 8G

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
  redis_data:
```

## Image Optimization

```bash
# 1. Use Alpine base images (smaller)
FROM node:20-alpine # ~170MB
FROM node:20-slim # ~200MB
FROM node:20 # ~1GB

# 2. Multi-stage builds (copy only what's needed)
COPY --from=builder /app/dist ./dist

# 3. Clean up in same layer
RUN apk add --no-cache curl && \
    rm -rf /var/cache/apk/*

# 4. Use .dockerignore
echo "node_modules" >> .dockerignore
echo ".git" >> .dockerignore
echo "*.md" >> .dockerignore

# 5. Check image size
docker images | grep api
# Target: < 200MB for Node.js apps
```

## Container Security Checklist

```markdown
## Pre-Deployment
- [ ] Base image is up-to-date (no known CVEs)
- [ ] Running as non-root user
- [ ] No secrets in image layers
- [ ] .dockerignore excludes sensitive files
- [ ] Health check configured
- [ ] Resource limits set

## Runtime
- [ ] Read-only filesystem (where possible)
- [ ] Dropped capabilities
- [ ] No privileged mode
- [ ] Network isolation
- [ ] Logging configured

## Monitoring
- [ ] Container metrics (CPU, memory, network)
- [ ] Application metrics (errors, latency)
- [ ] Log aggregation
- [ ] Alerting on anomalies
```

## Summary

1. **Multi-stage builds are the default, not an optimization** — build toolchain in one stage, runtime artifact in another; the runtime image never carries compilers
2. **The production container is unprivileged and secret-free** — non-root USER, secrets via orchestration or mounted files, never baked into layers
3. **Health checks and graceful shutdown make containers orchestratable** — a container that lies about health breaks rolling deploys and self-healing
4. **Compose is for local parity, not production** — same images, different runtime policy; production policy lives with the orchestrator
5. **Images are a supply-chain surface** — pin digests, scan continuously, rebuild on base-image CVEs

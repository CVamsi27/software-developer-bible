# Container Runtime Internals — Namespaces, cgroups and OverlayFS

A pod exits with code 137, but that number alone does not tell you why it stopped. To diagnose it, you need to know which kernel view the process had, which resource limits applied, and how the container's filesystem was assembled. Those are the mechanisms behind container isolation — and its limits.

## Definition

A **Linux container** is a process running on the host kernel with a configured filesystem, namespaces, resource controls, and security policy. It does not boot a separate kernel.

> **Textbook Definition:** A Linux container runtime creates a process environment using kernel namespaces for scoped system views and control groups for resource accounting and configured limits, with a filesystem prepared from an image.

**Namespaces** control what system resources look like to a process. **Control groups (cgroups)** account for resource use and can enforce limits. A layered filesystem such as **OverlayFS** combines image layers with a writable container layer. An OCI-compatible runtime such as runc applies the process configuration; a supervisor such as containerd tracks the running task.

## First Principles

Starting a container assembles a process with three properties: a **scoped view** of processes, networking, mounts, and hostname; a **place in the host's resource-accounting hierarchy**, with limits only where configured and supported; and a **root filesystem** assembled from image layers plus a writable layer. The process still uses the host kernel. Namespaces impose no CPU or memory limits, and cgroups filter no system calls — capabilities, seccomp, Linux security modules, and user-namespace mappings are separate security controls.

## How It Works

### 1. Give the Process Its Own System Views

A namespace changes what a process sees; it does not create a separate machine.

| Namespace | Scoped view | Operational consequence |
| --------- | ------------------------------- | ----------------------------------------------------------------------- |
| pid | Process IDs | The container's init process appears as PID 1 inside its PID namespace. |
| net | Interfaces, routes and sockets | localhost refers to this network namespace. |
| mnt | Mount points | The process sees the container's assembled root filesystem. |
| uts | Hostname and domain name | Its hostname can differ from the host's. |
| ipc | System V and POSIX IPC objects | IPC identifiers can be isolated from other workloads. |
| user | UID and GID mappings | UID 0 inside may map to an unprivileged host UID. |
| cgroup | Cgroup path view | /proc/self/cgroup can show a namespace-relative path. |
| time | Monotonic and boot-time offsets | Used for controlled time-shift environments. |

On Linux, `unshare` makes selected namespaces visible without Docker. This small experiment needs a Linux host and sufficient permission; it is not a complete container or security sandbox:

```bash
sudo unshare --pid --uts --fork --mount-proc sh -c '
  hostname isolated-name
  printf "hostname: "; hostname
  printf "processes in this PID namespace:\n"
  ps -o pid,comm
'
```

The command creates a PID and UTS namespace, then mounts a `/proc` view for that PID namespace. It configures no cgroup limits, prepares no image, and applies no complete container security policy. macOS cannot create Linux namespaces directly; Docker Desktop runs its Linux daemon inside a VM.

### 2. Account for and Bound Resources with cgroups

On cgroup v2 systems, controllers appear in a unified hierarchy, commonly mounted at `/sys/fs/cgroup`. The exact path for a container depends on the engine's cgroup driver, systemd layout, rootless mode, and host. On Docker Desktop, the Linux host is its VM.

| File | What it tells you |
| -------------- | -------------------------------------------------------------- |
| cpu.max | CPU quota and period; a ceiling, not reserved CPU capacity |
| cpu.weight | Relative CPU share when groups contend |
| memory.current | Current accounted memory, including file cache |
| memory.high | Reclaim/throttling boundary, not a hard allocation limit |
| memory.max | Maximum accounted memory before reclaim or cgroup OOM handling |
| memory.events | Counters such as oom and oom_kill |
| pids.max | Maximum number of tasks in the group |

For example, `cpu.max` containing `200000 100000` permits up to 200,000 microseconds of CPU time during each 100,000-microsecond period — a two-CPU quota across the group, not a reservation of two physical cores. A parallel workload can spend the period's budget quickly and then be throttled until the next period.

Memory limits include anonymous memory and file cache. Reclaimable clean cache can be dropped; memory pressure can reclaim or throttle at `memory.high`; an unrecoverable limit breach can trigger a cgroup OOM kill. Check `memory.events` before attributing a restart to OOM.

Docker exposes configured limits inside a cgroup v2 container:

```bash
docker run --rm --memory=256m --cpus=1 --pids-limit=64 node:24-alpine sh -c '
  cat /sys/fs/cgroup/memory.max
  cat /sys/fs/cgroup/cpu.max
  cat /sys/fs/cgroup/memory.events
'
```

A process exit code of 137 usually means it received SIGKILL; OOM is one possible cause, not the only one. Compare the container's state, orchestration events, and cgroup counters:

```bash
docker inspect orders-api --format \
  'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
docker exec orders-api cat /sys/fs/cgroup/memory.events
docker exec orders-api cat /sys/fs/cgroup/cpu.stat
```

`OOMKilled=true` or a rising `oom_kill` counter supports an OOM diagnosis. A rising `nr_throttled` counter in `cpu.stat` shows quota throttling occurred; correlate it with request latency and workload before changing the limit.

### 3. Trace the Filesystem and the Runtime Stack

Filesystem-changing Dockerfile instructions such as `RUN` and `COPY` produce image layers. At runtime, the engine presents their merged view and adds a writable layer for the container:

```text
container view
┌─────────────────────────────┐
│ writable layer for this run │
├─────────────────────────────┤
│ read-only image layer 2     │
├─────────────────────────────┤
│ read-only image layer 1     │
├─────────────────────────────┤
│ base image layer            │
└─────────────────────────────┘
```

A read uses the topmost layer containing a file. Writing to a file that exists only in a lower layer first copies that file into the writable layer, then changes the copy. Deleting a lower-layer file creates a whiteout marker in the upper layer; its bytes remain in the image. That is why deleting a large file in a later Dockerfile instruction does not shrink the earlier layer. A volume mount supplies storage outside the container's writable layer.

The image's default command, environment, and user are configuration metadata, not filesystem layers. Docker's classic overlay2 driver exposes one implementation layout; newer containerd image stores can use different snapshotters. Use `docker history` to inspect build layers and `docker diff CONTAINER` to inspect changes to a container, rather than assuming a host storage path.

The runtime stack explains who performs each step:

```text
Docker CLI / Compose
        │ Docker Engine API
        ▼
dockerd ── delegates lifecycle ──► containerd
                                       │
                                       ▼
                                containerd shim
                                       │ invokes
                                       ▼
                         runc applies OCI configuration
                                       │
                                       ▼
                                  Linux kernel
```

runc creates the configured process environment and starts the workload; it is not the long-lived service supervisor. containerd and its shim track task state and I/O. Docker's daemon and live-restore configuration affect what happens during daemon restarts. Kubernetes talks to a CRI-compatible runtime such as containerd or CRI-O; it does not require Docker Engine's former dockershim.

### 4. Decide Whether the Shared Kernel Fits

| Requirement | Container | Virtual machine |
| -------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Process delivery and image-based rollout | Shares the host kernel and packages the application filesystem | Boots a guest operating system and kernel |
| Different guest kernels or operating systems | Not provided by a standard Linux container | Supported subject to hypervisor and platform constraints |
| Isolation from a hostile tenant | Depends on kernel, runtime, privileges and policy | Adds a guest-kernel boundary, which still needs hypervisor and host hardening |
| Startup and resource overhead | Measure image setup and workload startup | Measure guest boot and workload startup |

A shared kernel fits trusted workloads with a strong host boundary and controlled privileges. When tenants are hostile or policy requires a guest-kernel boundary, evaluate hardened VMs or sandboxed container runtimes such as gVisor and Kata. Compare the complete system, including host, hypervisor, runtime, and management plane.

## Summary

Namespaces scope what a container process sees; configured cgroups account for and limit resources; image layers form its root filesystem with a per-container writable layer. The OCI runtime applies the requested setup, while a supervisor tracks the task. These mechanisms help diagnose OOM kills, CPU throttling, and filesystem growth — but a Linux container still shares its host kernel.

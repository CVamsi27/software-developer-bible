# Container Runtime Internals — Namespaces, cgroups, OverlayFS

## Definition

A **container** is a process (or group of processes) running on the host kernel, isolated via kernel primitives instead of hardware virtualization:

> **Textbook Definition:** A Linux container runtime creates a process environment using kernel namespaces for scoped resource views and control groups for accounting and limits, with a filesystem prepared from the image.

- **Namespaces**: Virtualize the view of the system — each container gets its own process tree, network stack, mounts, hostname, IPC segments, and (optionally) UID space.
- **cgroups (control groups v2)**: Account for resource use and enforce configured controls — CPU quota/weight, memory limits, process-count limits and I/O controls.
- **OverlayFS**: Stacks read-only image layers with a writable layer using copy-on-write, so unchanged image data can be shared rather than copied into each writable layer.
- **OCI runtimes**: `runc` performs the actual namespace/cgroup setup from an OCI bundle; `containerd` supervises containers above it; Docker/Podman are UX layers on top.

```text
                    shared Linux host kernel
             ┌──────────────┴──────────────┐
             │                             │
      container A                   container B
      PID/net/mount views            PID/net/mount views
      configured cgroup              configured cgroup
      writable overlay               writable overlay

Containers have separate configured views and limits, but use the host kernel.
Without explicit cgroup limits, workloads still compete for host resources.
```

## First Principles

Runtime internals combine kernel mechanisms with a runtime protocol:

1. **Namespaces isolate *views***: pid (own init), net (own stack), mnt (own fs), uts, ipc, user — isolation is perspective, not hardware.
2. **Cgroups account for and can bound resources**: CPU, memory, process count and I/O controls apply only when supported and configured; they do not reserve capacity by default.
3. **OCI defines interoperable formats and runtime configuration**: Docker builds and manages containers; an OCI runtime such as `runc` applies the requested setup. Kubernetes uses a CRI-compatible runtime such as `containerd` or CRI-O.

## Why Do We Need It?

| Problem | Solution |
| -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| "What am I actually debugging inside a container?" | Namespaces explain why `ps`, `ip`, and mounts look different inside |
| One container starves others on a shared host | configured cgroups v2 controls can bound CPU, memory, pids and I/O |
| Images must start fast without copying GBs | OverlayFS copy-on-write shares read-only layers across containers |
| Interview question "container vs VM" | You can answer at the kernel-primitive level, not hand-waving |
| Security boundaries need to be reasoned about | Knowing which isolation exists (and what does NOT exist) informs hardening choices |
| OOM-killed pods / throttled latency in prod | cgroup semantics (limits vs requests, page-cache reclaim) explain the behavior |

## How It Works

### The Six Core Namespaces

| Namespace | Isolates | Flag | What the container sees |
| --------- | ------------------ | --------------- | ----------------------------------------------------------- |
| `pid` | Process IDs | `CLONE_NEWPID` | Its own tree; app runs as PID 1 |
| `net` | Network stack | `CLONE_NEWNET` | Own interfaces, routes, iptables, socket table |
| `mnt` | Mount points | `CLONE_NEWNS` | Own filesystem view (`/` is the container rootfs) |
| `uts` | Hostname/domain | `CLONE_NEWUTS` | Own `hostname` (defaults to container ID) |
| `ipc` | System V/POSIX IPC | `CLONE_NEWIPC` | Own semaphore/shm/message-queue space |
| `user` | UID/GID mappings | `CLONE_NEWUSER` | Mapping determines which host UID represents container root |

Two more matter operationally:

- **`cgroup` namespace**: hides the host cgroup paths so `/proc/self/cgroup` looks uniform inside the container.
- **`time` namespace** (newer): lets containers have offset boottime/monotonic clocks (used for testing time-shift scenarios).

### Namespace Demo Without Docker

You can build a mini-container with Linux util-linux tools to observe selected isolation primitives. This omits image preparation, network setup, resource controls and security policy; it is not equivalent to Docker:

```bash
# Create a new PID + UTS + mount namespace, fork into it,
# remount /proc so ps sees only the new namespace
sudo unshare --pid --uts --mount --fork --mount-proc bash

# Inside the new namespace:
hostname sandbox-demo          # UTS namespace: change hostname here only
ps aux                         # PID namespace: you are PID 1
readlink /proc/self/ns/pid     # identity of THIS pid namespace
```

```bash
# From the host: enumerate all namespaces on the machine
lsns                            # every namespace type, all processes
lsns -t net                     # only network namespaces
lsns -p $$                      # namespaces of your current shell

# Enter another process's namespaces (replace this with its host PID):
CONTAINER_PID=1234
sudo nsenter --target "$CONTAINER_PID" --pid --net --mount -- bash
```

### cgroups v2 — The Unified Hierarchy

cgroups v2 replaces separate per-controller hierarchies of v1 with a single tree under `/sys/fs/cgroup`. Containers get one directory per cgroup; limits are plain files:

```text
/sys/fs/cgroup/system.slice/docker-<id>.scope/
├── cgroup.controllers      # cpu io memory pids ...
├── cpu.max                 # "200000 100000" = max 2 CPUs per 100ms period
├── cpu.weight              # share-based weighting (replaces cpu.shares)
├── memory.max              # hard limit; reclaim and possible cgroup OOM
├── memory.high             # reclaim/throttling boundary; not a hard allocation cap
├── memory.current          # current usage incl. page cache
├── memory.events           # oom_kill counter — check when debugging!
└── pids.max                # prevents fork-bomb style PID exhaustion
```

The exact host cgroup path depends on the engine's cgroup driver, systemd layout and rootless mode. On Docker Desktop the Linux host is its VM. In a cgroup-v2 container, inspect the mounted controller files directly:

```bash
CID=$(docker run -d --memory=256m --cpus=1 --pids-limit=64 node:24-alpine \
  node -e "setInterval(() => {}, 1000)")
docker exec "$CID" cat /sys/fs/cgroup/memory.max
docker exec "$CID" cat /sys/fs/cgroup/cpu.max
docker exec "$CID" cat /sys/fs/cgroup/memory.events
docker rm -f "$CID"
```

Expected limits are 268435456 bytes and, with a 100000-microsecond CPU period, `100000 100000`. The CPU quota is a ceiling across the group, not ownership of one physical core. A runnable group may use multiple cores briefly and then be throttled when its period budget is exhausted. Verify the actual period rather than hardcoding a host directory layout.

Key cgroup v2 behaviors seniors must know:

1. **memory.max includes page cache.** Clean cache is reclaimed before OOM, but dirty pages count toward the limit.
2. **cpu.max is quota over a period**, not reservation — bursting above the quota within one 100ms period produces latency spikes ("CFS throttling").
3. **pids.max is the forgotten limit** — many production outages are fork-bombs or runaway thread pools that a pids cap would have contained.
4. **memory.events** exposes `oom` and `oom_kill` counters — first place to look for unexplained container deaths.

### OverlayFS — Copy-on-Write Image Layers

Filesystem-changing Dockerfile instructions such as `RUN` and `COPY` produce read-only filesystem layers. Configuration instructions such as `CMD` are stored in image metadata. At `run` time, Docker adds one writable upper layer:

```text
        ┌──────────────────────────────────┐
        │  Container view (merged mount)   │
        │  /  = union of all layers below  │
        └───────────────▲──────────────────┘
                        │ merge
        ┌───────────────┴──────────────────┐
        │  upperdir (writable, per-run)    │ ← writes land here
        ├──────────────────────────────────┤
        │  lowerdir L3: COPY dist ./dist   │
        ├──────────────────────────────────┤
        │  lowerdir L2: RUN npm ci         │ ← shared read-only layers
        ├──────────────────────────────────┤
        │  lowerdir L1: COPY package*.json │
        ├──────────────────────────────────┤
        │  lowerdir L0: FROM node:24-slim  │
        └──────────────────────────────────┘
```

The image configuration (including its default `CMD`) describes how to start the container; it is not a filesystem layer.

Copy-on-write rules that interviewers expect you to know:

- **Read** of a file hits the topmost layer containing it — no copying happens.
- **Write** to a file from a lower layer copies the whole file up first (`copy_up`), then modifies the copy. Large files edited in place pay a full-copy penalty on first write.
- **Delete** of a lower-layer file creates a whiteout entry in the upper layer; the bytes stay in the lower layer (why `rm` never shrinks images).
- **Same-layer cleanup** (`RUN curl big.tgz && tar ... && rm big.tgz`) removes the temporary archive before the layer snapshot is committed. Deleting it in a later `RUN` leaves its bytes in the earlier layer and adds a whiteout in the later one.

Storage paths are implementation details. Docker's classic overlay2 driver exposes directories in `GraphDriver.Data`; newer containerd image stores can use snapshotters and a different layout. Inspect the engine's configured store before following host paths. Use `docker diff <container>` to observe writable filesystem changes without assuming an overlay2 directory structure. A mounted volume is outside that writable-layer mechanism.

### The Runtime Stack — Where runc and containerd Sit

```text
┌───────────────────────────────────────────────────────────────────────┐
│  docker CLI / docker compose        (UX, API client)                  │
├───────────────────────────────────────────────────────────────────────┤
│  dockerd                            (Docker engine API)               │
│    └─ delegates container lifecycle                                   │
├───────────────────────────────────────────────────────────────────────┤
│  containerd                         (supervisor daemon)               │
│    ├─ image pull/store/snapshot management                            │
│    ├─ supports lifecycle decoupling; live-restore policy matters      │
│    └─ shim per container (containerd-shim-runc-v2)                    │
├───────────────────────────────────────────────────────────────────────┤
│  runc                               (OCI runtime program)             │
│    1. read OCI bundle (config.json + rootfs)                          │
│    2. create requested namespaces and mount layout                    │
│    3. apply configured cgroup controls                                │
│    4. start the container process                                     │
├───────────────────────────────────────────────────────────────────────┤
│  Linux kernel                       (the actual runtime)              │
└───────────────────────────────────────────────────────────────────────┘
```

Why the split matters:

- **runc applies the OCI configuration.** It creates the process environment and starts the workload; the containerd shim supervises task I/O and exit state. Do not assume daemon restart behavior: Docker live-restore and runtime configuration determine what remains running.
- **Kubernetes talks through CRI.** The kubelet uses a CRI-compatible runtime such as containerd or CRI-O. Dockershim was removed; Kubernetes did not remove containerd or OCI runtimes.
- **A shim separates task lifetime from the client command.** It can preserve task supervision across some daemon events, but process survival depends on the configured runtime and live-restore behavior.

## Code Examples

### Linux Namespace Demo Prerequisites

The earlier `unshare` demonstration requires a Linux host and sufficient namespace permissions. A prepared root filesystem must contain an executable shell plus its loader/libraries or an approved statically linked binary. `chroot` changes path resolution; it does not impose CPU/memory limits or create every namespace. Adding only a few namespaces does not create a complete security sandbox.

Do not download an unverified architecture-specific shell and execute it as root. Select an approved image/rootfs for the host architecture, isolate the experiment, and inspect its contents first. macOS host commands cannot directly create Linux namespaces; Docker Desktop provides a separate Linux host.

### Reading Container Isolation State From Inside

```bash
# Compare namespace identities: same value = same namespace
for ns in pid net mnt uts ipc user cgroup; do
  printf "%-8s %s\n" "$ns" "$(readlink /proc/self/ns/$ns)"
done

# Which capabilities does PID 1 really have? (containers drop most)
grep CapEff /proc/1/status
capsh --decode=$(grep CapEff /proc/1/status | awk '{print $2}')

# Inspect UID mapping (user namespaces are not by themselves proof of a rootless daemon)
cat /proc/self/uid_map
#         0          0      4294967295   ← rootful: direct mapping
# Example mappings depend on daemon/user configuration; rootless often maps UID 0
# separately to the invoking host user, then maps remaining IDs to subordinate ranges.
```

### Demonstrating cgroup Limits Causing Real Failures

```bash
# An isolated allocation experiment; inspect state instead of assuming exit137 means OOM.
docker run -m 64m --name study-oom python:3.14-alpine \
  python -c "x = ' ' * 200_000_000"
docker inspect study-oom --format '{{.State.ExitCode}} {{.State.OOMKilled}}'
docker rm study-oom

# A runnable task under a half-CPU quota can accumulate throttling events.
CID=$(docker run -d --cpus=0.5 node:24-alpine node -e 'while (true) {}')
docker exec "$CID" cat /sys/fs/cgroup/cpu.stat
# Repeat after load has run; compare nr_periods, nr_throttled and throttled_usec.
# The quota is CPU-time capacity, not "half the periods throttle".
docker rm -f "$CID"
```

### Layer Forensics With diff

```bash
# What did each Dockerfile step change?
docker history --no-trunc myapp:latest
docker history myapp:latest --format "{{.Size}}\t{{.CreatedBy}}" | head

# Total waste from deleted-in-later-layer files (needs dive or manual diff):
docker system df -v
# For per-layer file contents, use a layer-inspection tool such as dive against the image.
```

## Real-World Use Cases

### 1. Debugging a Pod That Keeps Dying With Exit 137

Exit code 137 conventionally indicates termination by SIGKILL. OOM is one cause; a forced stop or another kill can produce the same exit code. Check runtime state and memory events before diagnosing OOM. The namespace/cgroup model tells you exactly where to look:

```bash
kubectl describe pod crashy | grep -E 'OOMKilled|Last State'
# On the Linux node, resolve the process's cgroup from /proc/<host-pid>/cgroup,
# then inspect memory.events in that cgroup; paths depend on the cgroup driver.
kubectl top pod crashy                                 # usage vs limit
# Fix: raise memory.max equivalent (limits.memory) or fix the leak
```

### 2. Explaining Latency Spikes Under Load

CPU throttling artifacts: a container with `--cpus=1` (quota 100000us/period 100000us) with enough concurrently running threads to burn its 100ms CPU-time quota in the first 20ms of wall time of each period stalls for the remaining 80ms. P99 latency degrades even though average CPU utilization looks low. Fix: raise quota, spread work, or reduce single-period bursts.

### 3. Slimming a Bloated CI-Built Image

Understanding layers explains why `rm -rf /var/cache` in a later instruction saves nothing — the data persists in the earlier layer. Correct pattern: clean within the same `RUN`, or use multi-stage builds so the artifact layer is all that survives.

### 4. Choosing Runtime Configuration for a Multi-Tenant Cluster

Knowing that containers share the kernel tells you when plain runc is insufficient (hostile tenants, kernel CVE exposure window) and pushes you toward gVisor/Kata — covered in [Rootless & Sandboxed Runtimes](40.1.09-rootless-sandboxed-runtimes.md).

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Treating containers as lightweight VMs with their own kernel | They share the host kernel; kernel version/modules affect every container |
| Setting memory limits without checking page-cache semantics | Remember `memory.max` counts cache; verify with `memory.events`, not guesswork |
| Assuming `rm` in a later layer shrinks the image | Delete within the same `RUN` layer or use multi-stage builds |
| Ignoring process-count growth until a fork-bomb outage | Set and monitor a pids limit when the workload's process model permits a meaningful bound |
| Believing `ps aux` inside a container shows host processes | That is the `pid` namespace; use `nsenter` or `lsns` from the host |
| Running everything as root because "it is a container" | Root in the container usually means root-shaped access to the host kernel surface; use USER + dropped caps |

## Best Practices

1. **Set resource controls against a capacity and failure model** — configure CPU, memory, process and I/O limits where the runtime supports them, then validate throttling, reclaim and OOM behavior under load.
2. **Alert on `memory.events.oom_kill` and `cpu.stat.nr_throttled`** — they are leading indicators users feel before dashboards show saturation.
3. **Keep layers immutable-minded**: one concern per `RUN`, clean caches in the same instruction, order rarely-changing steps first.
4. **Use `nsenter`/`lsns` for host-side debugging** instead of installing debug toolchains into slim images (or use ephemeral debug containers).
5. **Prefer rootless/user-namespace execution** when the threat model allows; the uid_map is your tell.
6. **Know your runtime stack** — when `docker` CLI misbehaves, containerd/shim state is often the ground truth (`ctr`, `crictl`).

## Performance Considerations

| Aspect | Cost | Notes |
| ----------------------------- | ---------------------- | ---------------------------------------------------------------------------- |
| Container start | Workload dependent | Image pull, filesystem setup and application initialization also contribute |
| Copy-up on first write | File-size proportional | Big DB files written in place suffer; use volumes |
| Many tiny reads across layers | Lookup overhead | Overlay lookup walks lowerdirs top-down; deep stacks add slight cost |
| CFS throttling | Tail latency | Quota granularity (100ms default) shapes burstiness |
| Memory limit proximity | Reclaim pressure | Reclaim pressure depends on active working set and cache/dirty-page behavior |

## Interview Framing: Container vs VM

Compare the kernel boundary, the risks that boundary changes, and the requirements of the workload. Containers and VMs provide different isolation models; neither is automatically secure or faster.

```text
Q: "What is the difference between a container and a VM?"

1. ISOLATION MECHANISM
   VM: a hypervisor presents virtual hardware to a guest OS, which runs
       its own kernel. Implementations use hardware virtualization support
       where available, but details depend on the platform.
   Container: processes share the host kernel. Namespaces scope system
       views; configured cgroups account for or limit resources. A standard
       Linux container does not boot a guest kernel.

2. CONSEQUENCES
   Startup: compare VM boot with image pull/setup and application startup;
       measure the deployed workload rather than assuming a fixed winner.
   Density: guest-kernel and host overhead differ, but workload and platform
       determine actual resource use.
   Security: a separate guest kernel changes the boundary, but VM security
       still depends on the hypervisor, host, management plane and device
       configuration. Containers share the host kernel; privileges, mounts
       and kernel vulnerabilities can weaken their isolation.

3. WHEN EACH FITS
   Containers: useful for image-based delivery and higher density when
       sharing a patched host kernel fits the trust model.
   VMs: useful when workloads need separate guest kernels, different OSes,
       or a policy-defined VM boundary; that boundary still needs hardening.
   Hybrid: a cluster can run container workloads inside VM worker nodes.
       Assess both layers instead of treating one as a complete security plan.
```

## Summary

A Linux container uses namespaces to scope system views, configured cgroups to account for or limit resources, and a layered filesystem such as OverlayFS for copy-on-write storage. The runtime applies OCI configuration; a supervisor such as containerd tracks the task. These boundaries explain symptoms such as OOM kills, CPU throttling and unexpected image size, while preserving the key limit: an ordinary Linux container shares its host kernel.

# Container Runtime Internals — Namespaces, cgroups, OverlayFS

## TL;DR

A container is not a virtual machine — it is an ordinary Linux process wrapped in **namespaces** (isolation of what it can see) and constrained by **cgroups** (limits on what it can use), with an image assembled from **OverlayFS layers** and launched by **runc** under the supervision of a container runtime daemon like containerd.

**Why it matters:** Senior interviews probe whether you understand *what a container actually is* beneath `docker run`. Explaining namespaces, cgroups v2, copy-on-write layers, and where runc/containerd sit lets you debug real problems (OOM kills, PID exhaustion, layer bloat) that surface-level Docker knowledge cannot.

## First Principles

Runtime internals are two kernel mechanisms and a protocol:

1. **Namespaces isolate *views***: pid (own init), net (own stack), mnt (own fs), uts, ipc, user — isolation is perspective, not hardware.
2. **Cgroups bound *resources***: cpu, memory, pids, io — the enforcement that makes "one noisy container" survivable and multi-tenancy honest.
3. **OCI is the contract**: image format + runtime spec — Docker builds it, runc/containerd/CRI-O run it. Knowing the layers (engine → containerd → runc → kernel) tells you where "Docker issues" actually live (usually not Docker).

## Definition

A **container** is a process (or group of processes) running on the host kernel, isolated via kernel primitives instead of hardware virtualization:

- **Namespaces**: Virtualize the view of the system — each container gets its own process tree, network stack, mounts, hostname, IPC segments, and (optionally) UID space.
- **cgroups (control groups v2)**: Enforce resource accounting and limits — CPU shares/quota, memory ceilings, pids limits, I/O weight.
- **OverlayFS**: Stacks read-only image layers with a writable layer using copy-on-write, so containers start in milliseconds without duplicating image data.
- **OCI runtimes**: `runc` performs the actual namespace/cgroup setup from an OCI bundle; `containerd` supervises containers above it; Docker/Podman are UX layers on top.

```text
┌───────────────────────────────────────────────────────────────────────────────────┐
│                        HOST KERNEL                                                │
├───────────────────────┬───────────────────────────────────────────────────────────┤
│  Container A          │  Container B                                              │
│  ┌─────────────────────────────────────────┐  │  ┌─────────────────┐                                      │
│  │ pid ns: PID 1   │  │                    │ pid ns: PID 1   │  ← isolated views  │
│  │ net ns: eth0    │  │                    │ net ns: eth0    │                    │
│  │ mnt ns: /       │  │                    │ mnt ns: /       │                    │
│  └─────────────────────────────────────────┘  │  └─────────────────┘                                      │
│  cgroup: cpu.max=2    │  cgroup: memory.high=512M                                 │
│  overlay: upper_a     │  overlay: upper_b                                         │
├───────────────────────┴───────────────────────────────────────────────────────────┤
│  Same kernel, same physical RAM/CPU — just partitioned views                      │
└───────────────────────────────────────────────────────────────────────────────────┘
```

## Why Do We Need It?

| Problem | Solution |
| -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| "What am I actually debugging inside a container?" | Namespaces explain why `ps`, `ip`, and mounts look different inside |
| One container starves others on a shared host | cgroups v2 enforce CPU/memory/pids/I/O limits per container |
| Images must start fast without copying GBs | OverlayFS copy-on-write shares read-only layers across containers |
| Interview question "container vs VM" | You can answer at the kernel-primitive level, not hand-waving |
| Security boundaries need to be reasoned about | Knowing which isolation exists (and what does NOT exist) informs hardening choices |
| OOM-killed pods / throttled latency in prod | cgroup semantics (limits vs requests, page-cache reclaim) explain the behavior |

## How It Works

### The Six Core Namespaces

| Namespace | Isolates | Flag | What the container sees |
| --------- | ------------------ | --------------- | ------------------------------------------------- |
| `pid` | Process IDs | `CLONE_NEWPID` | Its own tree; app runs as PID 1 |
| `net` | Network stack | `CLONE_NEWNET` | Own interfaces, routes, iptables, socket table |
| `mnt` | Mount points | `CLONE_NEWNS` | Own filesystem view (`/` is the container rootfs) |
| `uts` | Hostname/domain | `CLONE_NEWUTS` | Own `hostname` (defaults to container ID) |
| `ipc` | System V/POSIX IPC | `CLONE_NEWIPC` | Own semaphore/shm/message-queue space |
| `user` | UID/GID mappings | `CLONE_NEWUSER` | Root inside maps to unprivileged host UID |

Two more matter operationally:

- **`cgroup` namespace**: hides the host cgroup paths so `/proc/self/cgroup` looks uniform inside the container.
- **`time` namespace** (newer): lets containers have offset boottime/monotonic clocks (used for testing time-shift scenarios).

### Namespace Demo Without Docker

You can build a mini-container with coreutils alone — this is exactly what `docker run` does under the hood:

```bash
# Create a new PID + UTS + mount namespace, fork into it,
# remount /proc so ps sees only the new namespace
sudo unshare --pid --uts --mount --fork --mount-proc bash

# Inside the new namespace:
hostname sandbox-demo          # UTS namespace: change hostname here only
ps aux                         # PID namespace: you are PID 1
readlink /proc/self/ns/pid     # identity of THIS pid namespace
```

```bash
# From the host: enumerate all namespaces on the machine
lsns                            # every namespace type, all processes
lsns -t net                     # only network namespaces
lsns -p $$                      # namespaces of your current shell

# Enter another process's namespaces (like `docker exec`):
nsenter --target <container_pid> --pid --net --mount bash
```

### cgroups v2 — The Unified Hierarchy

cgroups v2 replaces the ten per-controller hierarchies of v1 with a single tree under `/sys/fs/cgroup`. Containers get one directory per cgroup; limits are plain files:

```text
/sys/fs/cgroup/system.slice/docker-<id>.scope/
├── cgroup.controllers      # cpu io memory pids ...
├── cpu.max                 # "200000 100000" = max 2 CPUs per 100ms period
├── cpu.weight              # share-based weighting (replaces cpu.shares)
├── memory.max              # hard limit; exceeding → OOM kill
├── memory.high             # soft limit; exceeding → reclaim + throttle
├── memory.current          # current usage incl. page cache
├── memory.events           # oom_kill counter — check when debugging!
└── pids.max                # prevents fork-bomb style PID exhaustion
```

```bash
# Inspect the live cgroup of a running container
CID=$(docker run -d --memory=256m --cpus=1 nginx)
CGROUP=$(docker inspect -f '{{.Id}}' $CID)

cat /sys/fs/cgroup/system.slice/docker-$CGROUP.scope/memory.max   # 268435456
cat /sys/fs/cgroup/system.slice/docker-$CGROUP.scope/cpu.max      # 100000 100000
cat /sys/fs/cgroup/system.slice/docker-$CGROUP.scope/memory.events

# Ad-hoc cgroup by hand (no Docker involved):
sudo cgcreate -g memory,pids:demo
echo 100M | sudo tee /sys/fs/cgroup/demo/memory.max
echo 50   | sudo tee /sys/fs/cgroup/demo/pids.max
cgexec -g memory,pids:demo bash    # shell now limited to 100MB and 50 PIDs
```

Key cgroup v2 behaviors seniors must know:

1. **memory.max includes page cache.** Clean cache is reclaimed before OOM, but dirty pages count toward the limit.
2. **cpu.max is quota over a period**, not reservation — bursting above the quota within one 100ms period produces latency spikes ("CFS throttling").
3. **pids.max is the forgotten limit** — many production outages are fork-bombs or runaway thread pools that a pids cap would have contained.
4. **memory.events** exposes `oom` and `oom_kill` counters — first place to look for unexplained container deaths.

### OverlayFS — Copy-on-Write Image Layers

Each Dockerfile instruction produces a read-only layer (a directory + metadata under the storage driver). At `run` time, Docker adds one writable upper layer:

```text
        ┌──────────────────────────────────┐
        │  Container view (merged mount)   │
        │  /  = union of all layers below  │
        └───────────────▲──────────────────┘
                        │ merge
        ┌───────────────┴──────────────────┐
        │  upperdir (writable, per-run)    │ ← writes land here
        ├──────────────────────────────────┤
        │  lowerdir L5: CMD ["node", ...]  │
        ├──────────────────────────────────┤
        │  lowerdir L4: COPY dist ./dist   │
        ├──────────────────────────────────┤
        │  lowerdir L3: RUN npm ci         │ ← shared read-only layers
        ├──────────────────────────────────┤
        │  lowerdir L2: COPY package*.json │
        ├──────────────────────────────────┤
        │  lowerdir L1: FROM node:22-slim  │
        └──────────────────────────────────┘
```

Copy-on-write rules that interviewers expect you to know:

- **Read** of a file hits the topmost layer containing it — no copying happens.
- **Write** to a file from a lower layer copies the whole file up first (`copy_up`), then modifies the copy. Large files edited in place pay a full-copy penalty on first write.
- **Delete** of a lower-layer file creates a whiteout entry in the upper layer; the bytes stay in the lower layer (why `rm` never shrinks images).
- **Same-layer churn** (`RUN curl big.tgz && rm big.tgz`) still bakes both states into the layer — classic image-size trap.

```bash
# See the merged mount of a running container
docker inspect -f '{{json .GraphDriver.Data}}' $CID | python3 -m json.tool
# → LowerDir, UpperDir, MergedDir, WorkDir paths under /var/lib/docker/overlay2/

mount | grep overlay
# overlay on /var/lib/docker/overlay2/<id>/merged type overlay (lowerdir=...,upperdir=...,workdir=...)

# Prove copy-on-write: write inside container, find it in upperdir
docker exec $CID sh -c 'echo hello > /tmp/x'
ls /var/lib/docker/overlay2/*/diff/tmp/x   # appears in the writable diff dir
```

### The Runtime Stack — Where runc and containerd Sit

```text
┌───────────────────────────────────────────────────────────┐
│  docker CLI / docker compose        (UX, API client)      │
├───────────────────────────────────────────────────────────┤
│  dockerd                            (Docker engine API)   │
│    └─ delegates container lifecycle                       │
├───────────────────────────────────────────────────────────┤
│  containerd                         (supervisor daemon)   │
│    ├─ image pull/store/snapshot management                │
│    ├─ keeps containers RUNNING after dockerd restarts     │
│    └─ shim per container (containerd-shim-runc-v2)        │
├───────────────────────────────────────────────────────────┤
│  runc                               (OCI runtime, exits)  │
│    1. read OCI bundle (config.json + rootfs)              │
│    2. clone() with CLONE_NEW* flags → new namespaces      │
│    3. write cgroup limits                                 │
│    4. pivot_root into the rootfs                          │
│    5. exec the entrypoint → then runc EXITS               │
├───────────────────────────────────────────────────────────┤
│  Linux kernel                       (the actual runtime)  │
└───────────────────────────────────────────────────────────┘
```

Why the split matters:

- **runc is short-lived.** After setting up namespaces/cgroups/rootfs it execs the payload and goes away; the shim owns stdio and signals afterwards. This is why `systemctl restart docker` does not stop your containers (with live-restore/containerd-managed workloads).
- **containerd is the stable substrate.** Kubernetes' kubelet speaks CRI to containerd directly — Docker-the-engine was removed from K8s runtimes, but containerd (and thus OCI/runc) remained.
- **shims decouple lifecycle.** Each container gets a shim so daemon upgrades/restarts do not kill workloads.

## Code Examples

### Building a Toy Container From Scratch (Linux)

```bash
#!/usr/bin/env bash
# mini-container.sh — the primitive Docker reimplements
set -euo pipefail

ROOTFS=/tmp/toy-rootfs
mkdir -p "$ROOTFS"

# A minimal rootfs: busybox gives us a shell + coreutils
mkdir -p "$ROOTFS"/{bin,proc,sys,dev,etc}
wget -qO- https://busybox.net/downloads/binaries/1.35.0-x86_64-linux-musl/busybox \
  > "$ROOTFS/bin/busybox"
chmod +x "$ROOTFS/bin/busybox"
"$ROOTFS/bin/busybox" --install "$ROOTFS/bin"

# Clone into new pid/mnt/uts/ipc namespaces, chroot-style pivot, remount proc
unshare --pid --fork --mount --uts --ipc --mount-proc="$ROOTFS/proc" \
  chroot "$ROOTFS" /bin/sh -c '
    hostname toy-container
    echo "== ps ==" && ps
    echo "== hostname ==" && hostname
    echo "== /proc/self/cgroup ==" && cat /proc/self/cgroup
    exec sleep infinity
  '
```

### Reading Container Isolation State From Inside

```bash
# Compare namespace identities: same value = same namespace
for ns in pid net mnt uts ipc user cgroup; do
  printf "%-8s %s\n" "$ns" "$(readlink /proc/self/ns/$ns)"
done

# Which capabilities does PID 1 really have? (containers drop most)
grep CapEff /proc/1/status
capsh --decode=$(grep CapEff /proc/1/status | awk '{print $2}')

# Am I in a user namespace? (rootless mode indicator)
cat /proc/self/uid_map
#         0          0      4294967295   ← rootful: direct mapping
#         0     165536      65536        ← rootless: mapped range
```

### Demonstrating cgroup Limits Causing Real Failures

```bash
# Memory limit → OOM kill, observable in memory.events
docker run -m 64m --name oom-demo python:3-alpine \
  python -c "x = ' ' * 200_000_000"
docker inspect oom-demo --format '{{.State.OOMKilled}}'    # true

# CPU quota → throttling, visible as nr_throttled
docker run -d --cpus=0.5 --name thrash-demo busybox \
  sh -c 'while :; do :; done'
CG=/sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' thrash-demo).scope
sleep 5
cat $CG/cpu.stat    # nr_periods vs nr_throttled ≈ half the periods
```

### Layer Forensics With diff

```bash
# What did each Dockerfile step change?
docker history --no-trunc myapp:latest
docker history myapp:latest --format "{{.Size}}\t{{.CreatedBy}}" | head

# Total waste from deleted-in-later-layer files (needs dive or manual diff):
find /var/lib/docker/overlay2 -maxdepth 3 -name diff -type d \
  -exec du -sh {} \; | sort -rh | head
```

## Real-World Use Cases

### 1. Debugging a Pod That Keeps Dying With Exit 137

Exit code 137 = SIGKILL, typically the cgroup OOM killer. The namespace/cgroup model tells you exactly where to look:

```bash
kubectl describe pod crashy | grep -E 'OOMKilled|Last State'
# On the node: confirm the kernel agrees
cat /sys/fs/cgroup/kubepods.slice/.../memory.events   # oom_kill 14
kubectl top pod crashy                                 # usage vs limit
# Fix: raise memory.max equivalent (limits.memory) or fix the leak
```

### 2. Explaining Latency Spikes Under Load

CPU throttling artifacts: a container with `--cpus=1` (quota 100000us/period 100000us) that burns its quota in the first 20ms of each period stalls for the remaining 80ms. P99 latency degrades even though average CPU utilization looks low. Fix: raise quota, spread work, or reduce single-period bursts.

### 3. Slimming a Bloated CI-Built Image

Understanding layers explains why `rm -rf /var/cache` in a later instruction saves nothing — the data persists in the earlier layer. Correct pattern: clean within the same `RUN`, or use multi-stage builds so the artifact layer is all that survives.

### 4. Choosing Runtime Configuration for a Multi-Tenant Cluster

Knowing that containers share the kernel tells you when plain runc is insufficient (hostile tenants, kernel CVE exposure window) and pushes you toward gVisor/Kata — covered in [Rootless & Sandboxed Runtimes](40.1.09-rootless-sandboxed-runtimes.md).

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Treating containers as lightweight VMs with their own kernel | They share the host kernel; kernel version/modules affect every container |
| Setting memory limits without checking page-cache semantics | Remember `memory.max` counts cache; verify with `memory.events`, not guesswork |
| Assuming `rm` in a later layer shrinks the image | Delete within the same `RUN` layer or use multi-stage builds |
| Ignoring `pids.max` until a fork-bomb outage | Always set a pids limit alongside memory/CPU |
| Believing `ps aux` inside a container shows host processes | That is the `pid` namespace; use `nsenter` or `lsns` from the host |
| Running everything as root because "it is a container" | Root in the container usually means root-shaped access to the host kernel surface; use USER + dropped caps |

## Best Practices

1. **Set all three limits** — memory.max, cpu.max (or weight), pids.max — on every production workload.
2. **Alert on `memory.events.oom_kill` and `cpu.stat.nr_throttled`** — they are leading indicators users feel before dashboards show saturation.
3. **Keep layers immutable-minded**: one concern per `RUN`, clean caches in the same instruction, order rarely-changing steps first.
4. **Use `nsenter`/`lsns` for host-side debugging** instead of installing debug toolchains into slim images (or use ephemeral debug containers).
5. **Prefer rootless/user-namespace execution** when the threat model allows; the uid_map is your tell.
6. **Know your runtime stack** — when `docker` CLI misbehaves, containerd/shim state is often the ground truth (`ctr`, `crictl`).

## Performance Considerations

| Aspect | Cost | Notes |
| ----------------------------- | ---------------------- | -------------------------------------------------------------------- |
| Container start | ~ms | No boot: namespaces + cgroups + pivot_root only |
| Copy-up on first write | File-size proportional | Big DB files written in place suffer; use volumes |
| Many tiny reads across layers | Lookup overhead | Overlay lookup walks lowerdirs top-down; deep stacks add slight cost |
| CFS throttling | Tail latency | Quota granularity (100ms default) shapes burstiness |
| Memory limit proximity | Reclaim pressure | Running at >90% of memory.max causes cache eviction storms |

## Interview Framing: Container vs VM

The senior-level answer has three beats:

```text
Q: "What is the difference between a container and a VM?"

1. ISOLATION MECHANISM
   VM: hypervisor emulates hardware; guest OS boots per VM;
       hardware-assisted virtualization (VT-x/AMD-V).
   Container: kernel-enforced partitions (namespaces = visibility,
       cgroups = resources); zero guest kernel.

2. CONSEQUENCES
   Start time: seconds+ (boot) vs milliseconds (clone+exec).
   Density: GBs + OS overhead vs MBs + shared kernel pages.
   Boundary strength: VM isolates kernels (stronger against
       kernel exploits); container isolates views (weaker — hence
       gVisor/Kata/microVMs when tenants are hostile).

3. WHEN EACH WINS
   Containers: high-density services, fast deploys, same-trust workloads.
   VMs: hard multi-tenancy, mixed OS/kernel needs, compliance boundaries.
   Hybrid reality: cloud K8s runs containers INSIDE VM nodes —
       belt-and-suspenders boundary placement.
```

## Summary

Containers are processes wearing six disguises: namespaces give each one a private view (pid, net, mnt, uts, ipc, user), cgroups v2 give them budgets (cpu.max, memory.max/high, pids.max), and OverlayFS gives them a cheap layered filesystem with copy-on-write writes. runc performs the setup from an OCI bundle and exits; containerd and its shims supervise; Docker is the friendly front door. Mastering these primitives converts mysterious production symptoms — exit 137s, tail-latency cliffs, inexplicably fat images — into readable kernel state.

## Cheat Sheet

```text
CONTAINER RUNTIME INTERNALS CHEAT SHEET
═══════════════════════════════════════

NAMESPACES (what you SEE):
• pid  — own process tree, PID 1 reaping duty
• net  — own NICs/routes/iptables/socket tables
• mnt  — own mount table, / is the rootfs
• uts  — own hostname
• ipc  — own SysV shm/semaphores
• user — uid/gid mapping (rootless foundation)

CGROUPS V2 (what you GET):
• cpu.max      "quota period"  e.g. 200000 100000 = 2 CPUs
• memory.max   hard cap → OOM kill; watch memory.events
• memory.high  soft cap → reclaim/throttle
• pids.max     fork-bomb guard
• Path: /sys/fs/cgroup/system.slice/docker-<id>.scope/

OVERLAYFS:
• lowerdir(s) read-only, upperdir writable, merged view
• Write → copy_up whole file; Delete → whiteout
• rm in a later layer NEVER frees space

RUNTIME STACK:
• docker → containerd → shim → runc → kernel
• runc: namespaces + cgroups + pivot_root, then exec + exit
• kubelet speaks CRI to containerd (Docker engine removed)

DEBUG COMMANDS:
• lsns [-p <pid>]            list namespaces
• nsenter -t <pid> -n -m -p  enter a container's namespaces
• cat /proc/self/uid_map     detect rootless mode
• cat .../memory.events      oom_kill counter
• cat .../cpu.stat           nr_throttled counter
• docker history             per-layer size forensics

INTERVIEW ONE-LINER:
"A container is an isolated VIEW (namespaces) with a BUDGET
(cgroups) on the HOST KERNEL — a VM is a separate kernel."
```

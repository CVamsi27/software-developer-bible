# Image Signing, SBOM & Supply Chain Security

## Definition

**Container supply chain security** is the set of controls that lets a cluster answer three questions before running an image:

> **Textbook Definition:** Container supply-chain security verifies artifact identity and integrity, inventories components through a software bill of materials (SBOM), and evaluates build provenance before permitting an image to run.

- **Integrity/authenticity** — Who built and published this digest, and has anything changed since? → cryptographic signatures (**cosign/Sigstore**).
- **Composition** — What exactly is in this image (packages, libraries, licenses)? → **SBOM** (Software Bill of Materials) via **syft**, **Trivy**, or BuildKit **attestations**.
- **Process** — Was it built by a trustworthy pipeline from the declared source at the declared commit? → **provenance** attestations graded by **SLSA levels**.

```text
THREAT MODEL: WHERE IMAGES GET COMPROMISED
═══════════════════════════════════════════
 [source repo]──build CI──push──registry──pull/admit──runtime
      │            │         │        │          │
   malicious     runner    stolen   tag       unsigned/
   PR or dep     hijack    creds    mutated /  spoofed
   injected      or dirty  or weak  reference  image pulled
                 cache     ACLs     rewritten  by cluster
```

## First Principles

Supply-chain security follows from one fact: the image is the unit of trust.

1. **You run what you pull — so provenance must be verifiable**: a cosign signature authenticates a digest under the trusted signing identity. A verified provenance statement separately describes the builder and source. Trust moves from tags (mutable) to signatures over digests.
2. **SBOM makes the dependency inventory queryable**: when the next openssl CVE lands, "which of my images contain it?" must be a query, not an archaeology project (→ 20.5.3.05's SCA at image granularity).
3. **Admission is the last policy gate**: verify signatures, provenance and the exact digest before pod creation; use CI and registry policy as earlier checks too. Registry-side checks alone do not stop a later tag from resolving to different bytes.

## Why Do We Need It?

| Problem | Solution |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Attacker pushes a backdoored tag to your registry | Sign at build; verify signature before admission |
| `latest` mutable tags make "what is running?" unanswerable | Deploy by immutable digest; sign the digest |
| Compromised CI produces a valid-looking image | Provenance attestation ties image to source commit + builder identity |
| Zero-day drops; you must find every service using log4j/xz | SBOM query answers "where is X?" in minutes, not weeks |
| A procurement or control program requires software evidence | Supply the SBOM, signed digest and provenance required by that program; map each requirement to its actual scope |
| Developers pull random public images | Registry allowlist + pull-through cache + signature verification |

## How It Works

### Sigstore Keyless Signing Model

Cosign's keyless mode removes long-lived keys from developers/CI:

```text
┌──────┐ 1. OIDC token (ci@org) ──▶ ┌─────────┐
│ CI                                           │                            │ Fulcio  │ issues short-lived cert,
│ job  │ ◀────────────────────────── │ (CA)    │ binding authenticated identity→ephemeral key
└──┬───┘                            └─────────┘
   │ 2. push signature + cert to OCI registry (attached to digest)
   ▼
┌───────────────────────────────────────────────┐ 3. transparency log      ┌─────────┐
│ Rekor    │ ◀──record signed entry── │ cosign  │
│ (log)    │                          │ sign    │
└───────────────────────────────────────────────┘                          └─────────┘

Verify = check sig against cert + cert against OIDC identity +
         entry exists in tamper-evident Rekor log.
```

### What Gets Signed — Digests, Not Tags

Signing a tag makes the tool resolve that tag to a digest. The resulting signature does not transfer to unrelated bytes when the tag later moves. The danger is resolving the tag again during deployment and selecting a different digest. Resolve once, then sign, verify and deploy that exact reference:

```text
approved tag → resolved sha256 digest → signed/verified digest → deployment digest
```

### SBOM Generation Paths

```text
Option A: post-build scan (works with any existing image)
   syft myregistry/myapp:1.4.2 -o spdx-json > sbom.spdx.json

Option B: build-time attestation (BuildKit with Docker Buildx)
   docker buildx build --sbom=true --provenance=mode=max \
     --push -t myregistry/myapp:1.4.2 .
   → SBOM + provenance stored IN the registry as OCI artifacts,
     attached to the image manifest — retention and registry access policy still apply.

Formats: SPDX (ISO standard, ecosystem-wide) vs CycloneDX
         (security-tooling friendly). Both readable by Grype/Trivy.
```

### SLSA Provenance Levels

SLSA Build track v1.1 defines three levels. Level claims apply only when the platform satisfies the corresponding requirements and the verifier checks the provenance:

| Build level | Guarantee | Main risk addressed |
| ------------------ | --------------------------------------------------------------- | ----------------------------------------------------------- |
| L1 | Provenance records how the artifact was built | Mistakes and missing build documentation |
| L2 | A hosted build platform generates signed provenance | Provenance or artifact tampering after the build |
| L3 | The build platform is hardened against tampering during a build | A malicious build step influencing other builds or evidence |

There is no SLSA Build L0 level. Choose a target from the threat model, then verify both the platform controls and the provenance against the specification. An attestation signed by an arbitrary key does not establish L2; ephemeral runners alone do not establish L3.

### Enforcement Points

```text
1. ADMISSION (cluster): Kyverno/Gatekeeper verify signature +
   provenance issuer + SBOM present BEFORE pod creation.

2. REGISTRY POLICY: Harbor/ECR/GAR rules — immutable tags,
   deny unsigned pushes, allowlisted upstream mirrors only.

3. CI GATE: verify base-image signature + scan SBOM against
   policy (fail on critical CVEs / banned licenses) pre-push.

4. RUNTIME DRIFT CHECK: periodic re-verify of what actually runs
   vs what was admitted (detects out-of-band changes).
```

## Code Examples

### Signing and Verifying With Cosign

The shortened digests below are placeholders; replace them with approved full digests. Keyless signing needs a supported authenticated identity, and registry writes need authorization. Use a pinned cosign version and matching predicate types. Verifying an attestation authenticates its statement; separately check the fields required by your policy.


```bash
# Install cosign, then sign keyless (CI identity via OIDC)
cosign sign --yes \
  myregistry.io/team/myapp@sha256:9f86d081884c7d65...

# Verify: expected exact identity and issuer, plus required trust/log evidence
cosign verify \
  --certificate-identity 'https://github.com/org/myapp/.github/workflows/release.yml@refs/tags/v1.4.2' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  myregistry.io/team/myapp@sha256:9f86d081884c7d65...

# Attach an SBOM as an attestation
syft myregistry.io/team/myapp@sha256:9f86... -o cyclonedx-json > sbom.json
cosign attest --yes --predicate sbom.json --type cyclonedx \
  myregistry.io/team/myapp@sha256:9f86...

# Verify the attestation too
cosign verify-attestation --type cyclonedx \
  --certificate-identity 'https://github.com/org/myapp/.github/workflows/release.yml@refs/tags/v1.4.2' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  myregistry.io/team/myapp@sha256:9f86...
```

### Generating SBOMs

```bash
# Syft: catalog any image, dir, or lockfile set
syft myregistry.io/team/myapp:1.4.2 -o spdx-json > app.sbom.json
syft dir:. -o cyclonedx-json > src.sbom.json   # even without Docker

# Query it: are we exposed to a specific component?
jq '.packages[] | select(.name | test("xz|log4j")) | {name, versionInfo}' app.sbom.json

# Vulnerability-match the SBOM with Grype
grype sbom:app.sbom.json --fail-on high
```

### BuildKit Attestations at Build Time

```bash
docker buildx create --use --name secure-builder
docker buildx build \
  --provenance=mode=max \
  --sbom=true \
  --push -t myregistry.io/team/myapp:1.4.2 .

# Inspect attestations attached in-registry
docker buildx imagetools inspect myregistry.io/team/myapp:1.4.2
# → attestation-manifest entries: provenance, sbom
```

The provenance predicate records builder identity, build type and parameters, source configuration, and resolved dependencies according to its predicate version and mode. Inspect the emitted statement instead of assuming a fixed field layout; unrecorded network or host inputs are not made trustworthy by an attestation.

Build arguments can appear in maximum-detail provenance. Never pass credentials through `ARG` or `ENV`; use a secret mount, and ensure commands do not print or persist the mounted value.

The classic Docker image store cannot retain attestations attached to an image index. A Buildx builder using a supported containerd image store or a registry output is required; the `--push` example preserves registry attestations.

### Verify Before Deployment and Enforce at Admission

An admission verifier needs more than a signature-present check:

1. Match the intended registry/repository and resolve the exact digest.
2. Verify a signature under the approved issuer and narrowly scoped signing identity.
3. Verify separately required attestations and evaluate their contents: expected builder, source, commit and policy version.
4. Apply the component/vulnerability policy to the SBOM and the released artifact.
5. Admit the pinned digest and record the decision; reject missing or mismatched evidence.

Kyverno image-verification rules can implement these checks, but use the installed version's schema. A policy matching any workflow under an organization grants every matching workflow signing authority. Wildcards require an explicit reason; prefer the expected release workflow/ref. Confirm a valid release is admitted and a wrong signer, unsigned image, changed digest and missing attestation are rejected. A YAML excerpt or a CI cosign command alone does not prove the cluster enforces admission.

For CI, install pinned verifier/scanner versions, provide registry access, and verify the exact immutable reference with the same identity/issuer expectations. Verification normally does not require minting a new signing OIDC token. Deploy only after these checks succeed; scanner database unavailability and admission timeout behavior need an explicit fail-open/fail-closed policy.

### Registry-Side Policy (Harbor Example)

```bash
# Harbor project settings enforced server-side:
#   Content trust: require signed images for pull
#   Tag immutability: v* patterns immutable once pushed
#   Quota + vulnerability policy: block pull when severity >= High
# AWS ECR equivalent: ECR basic scanning + enhanced scanning,
#   plus immutable tags per repository configuration.
aws ecr put-image-tag-mutability \
  --repository-name team/myapp \
  --image-tag-mutability IMMUTABLE
```

## Real-World Use Cases

### 1. The xz-Style Backdoor Scenario

A compromised dependency ships subtly malicious code. Without SBOMs you audit by memory and grep. With them:

```bash
for ns in prod staging; do
  kubectl get pods -n $ns -o json | jq -r '..|.image? // empty' | sort -u
done > deployed-images.txt
while read -r img; do syft "$img" -o json | jq -r '.artifacts[].name'; done \
  < deployed-images.txt | sort -u | grep -n xz
```

### 2. Multi-Team Platform With a Private Registry

Platform team configures Harbor: pulls from Docker Hub only via an allowlisted pull-through mirror, can apply content-trust/vulnerability restrictions on supported pulls. Application teams inherit enforcement without touching their pipelines — the registry becomes the choke point.

### 3. Auditable Releases for Regulated Workloads

Each release produces: signed digest + provenance attestation (builder, commit, base image digests) + SPDX SBOM archived with the release. An auditor can reconstruct exactly what shipped and how, months later, without trusting anyone's memory.

### 4. Blocking a Stolen CI Credential From Shipping Malware

If admission checks the expected builder, source and artifact digest, a stolen registry credential alone should not authorize deployment of an untrusted image. This defense depends on the verifier's policy and the build platform's guarantees; SLSA L3 requires controls that prevent runs from influencing one another and keep signing secrets away from build steps.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------- | ----------------------------------------------------------------------- |
| Signing a mutable tag (`:latest`) | Sign digests; resolve tag→digest once and pin everywhere |
| Verifying only locally/manually ("we ran cosign once") | Enforce at admission (Kyverno/Gatekeeper) — humans forget |
| SBOM generated but never queried or gated | Wire SBOM into CI gates (grype --fail-on) and incident playbooks |
| Treating CVE scanning as supply-chain security complete | Scanning covers known vulns only; signatures/provenance cover tampering |
| Long-lived cosign keys pasted into CI secrets | Use keyless OIDC signing or KMS-backed keys with rotation |
| Allowing arbitrary public bases (`FROM anything`) | Allowlist base images through a curated internal mirror |

## Best Practices

1. **Pin and deploy by digest** — tags are pointers, not identities; make admission rewrite tags to digests.
2. **Sign in the same trusted pipeline that builds** — validate the expected signing identity and build evidence; a signing service can be trusted when its authorization policy and attested inputs are explicit.
3. **Emit both SBOM and provenance as registry attestations** — retain and verify their association with the digest; registry garbage collection/access policy can affect availability.
4. **Start enforcement in audit mode** — run Kyverno policy as `Audit`, review violations, then flip to `Enforce`.
5. **Curate the bottom of the stack** — approved base images with automated rebuilds matter more than scanning your own code.
6. **Practice the recall drill** — given component X at version Y, produce the list of affected workloads within the incident response target; time the drill and record missing inventory.

## Performance Considerations

| Aspect | Cost | Mitigation |
| ------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| Admission webhook verifying signatures | Measure under actual rollout/concurrency | Cache verification results per digest; batch rollouts |
| SBOM cataloging large images | Seconds-minutes per image | Build-time attestations amortize into the build |
| Registry storing attestations | Additional manifests and blobs | Measure retention and transfer; select the provenance detail level required by policy |
| Keyless verification requiring Rekor lookup | Network round-trip | Verify complete trusted bundles offline where supported; do not disable required verification |
| Policy complexity | Webhook latency under load | Scope match rules narrowly (namespace/image prefixes) |

## Summary

Supply-chain controls add verifiable evidence to each release. Sign production images with cosign (keyless where possible), attach SBOM and provenance as BuildKit attestations, assess the build platform against SLSA requirements, and verify the expected identity and immutable digest in CI and at admission. Scanners report known weaknesses in image contents; signatures and provenance help verify who built a specific digest and from which declared inputs, but neither proves the software is free of defects.

# Image Signing, SBOM & Supply Chain Security

A release tag can move after it was tested, and a signed image can still contain a vulnerable dependency. To decide whether to run an image, first bind the release to its digest, then verify who produced it, what it contains, and whether that evidence meets deployment policy.

## Definition

Container supply-chain security is the set of controls used to identify an image, inventory its contents, evaluate how it was built, and decide whether to deploy it.

> **Textbook Definition:** Container supply-chain security verifies artifact identity and integrity, inventories included components with a software bill of materials (SBOM), and evaluates build provenance against a defined trust policy.

A signature, SBOM, and provenance answer different questions:

- A **signature** binds a signer identity to an artifact digest.
- An **SBOM** lists software components identified by a scanner or build process.
- **Provenance** describes the source and process that produced an artifact.

None proves that the application is free of defects.

## First Principles

The deployment target is the immutable image digest, not its tag. Evidence must refer to that digest and be checked against a policy that names the expected signer, builder, source, and contents. Signing proves an identity/integrity claim; the verifier decides whether that identity is trusted.

## Bind the release to a digest

Resolve the approved tag once, then sign, verify, and deploy the same digest. If a tag later points at different bytes, the old signature does not authorize the new digest.

```text
approved tag → resolved sha256 digest → signed and verified digest → deployment digest
```

Sigstore keyless signing uses an authenticated OIDC identity to create a short-lived certificate and signature. Cosign can verify both the artifact digest and the certificate's expected identity and issuer. A transparency-log bundle supports later verification; keep the verifier's trust and availability policy explicit.

```bash
IMAGE='registry.example.com/orders/api@sha256:<full-approved-digest>'

cosign verify \
  --certificate-identity 'https://github.com/example/orders/.github/workflows/release.yml@refs/tags/v1.4.2' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  "$IMAGE"
```

The repository, workflow identity, tag, and digest are placeholders. Replace them with the exact approved release values. A valid signature authenticates that digest under the matched signer; it does not establish that the image is safe, that its source was reviewed, or that a deployment policy approved it.

## Produce inventory and build evidence

An SBOM lets responders query which images include a component when a vulnerability is disclosed. It may come from scanning an existing image or from an attestation attached during the build:

```bash
IMAGE='registry.example.com/orders/api@sha256:<full-approved-digest>'
syft --from registry "$IMAGE" -o spdx-json > image.sbom.json
grype sbom:image.sbom.json --fail-on high
```

The scanner's database and the SBOM's coverage both affect the result. A clean scan means no findings crossed the configured policy at that time; it is not a guarantee that no vulnerable or malicious code is present.

BuildKit can create provenance and an SBOM while building:

```bash
docker buildx build \
  --provenance=mode=max \
  --sbom=true \
  --push \
  --tag registry.example.com/orders/api:1.4.2 .
```

Capture the digest returned by the push and use that reference for signature verification, SBOM queries, policy checks, and deployment. Do not resolve the tag independently at each step.

BuildKit attaches attestation manifests to the image index and associates them with the built artifact. Provenance records fields according to its predicate version and generation mode; inspect the emitted statement instead of assuming every source input or network download was captured. The classic Docker image store cannot retain attestations attached to an image index. Use a supported containerd image store or a Buildx driver that exports to a registry. Registry retention and access controls also apply to the evidence.

Never pass credentials in build arguments or environment metadata. Maximum-detail provenance can expose build arguments; use a secret mount and ensure the command does not print or persist the secret.

## Interpret SLSA levels as requirements

SLSA 1.2 has separate **Build** and **Source** tracks. The Build track levels describe evidence and controls for producing a package; they are not a quality score for the image. BuildKit emitting provenance does not by itself establish a SLSA level.

| Build level | Minimum claim | What the consumer must check |
| ----------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| L0 | No SLSA requirements are met | Treat as no SLSA guarantee |
| L1 | Provenance describes how the package was built; it may be incomplete or unsigned | Inspect whether it identifies useful source and build inputs |
| L2 | A hosted build platform generates signed provenance | Verify the signature and provenance authenticity |
| L3 | A hardened platform prevents runs from influencing one another and protects signing material from user-defined build steps | Verify the platform and provenance satisfy the specified controls |

Source-track requirements are assessed separately. An ephemeral runner alone does not establish Build L3; the platform must meet the track's isolation and signing-key requirements, and the consumer must verify the relevant evidence.

## Enforce the policy at the deployment boundary

An admission policy should require a digest reference, match the expected registry and repository, verify the signer identity and issuer, and validate required provenance and SBOM claims. It should admit that exact digest and record the decision. A signature-present check is insufficient if it accepts any identity. Test both a valid release and rejected cases: an unsigned image, wrong signer, changed digest, missing attestation, or unexpected source.

CI and registry checks can catch errors earlier, but the deployment boundary must still enforce the final policy. Scanner outages, missing attestations, registry retention, and admission timeouts need explicit fail-open or fail-closed behavior. Start policy in audit mode when existing releases have gaps, then enforce after the owner has reviewed the violations.

## Summary

Follow one image digest from the trusted build to deployment. Verify signer identity, inspect provenance and SBOM contents, and enforce their required claims at admission. Signatures establish an identity and integrity relationship; SBOMs provide component inventory; provenance describes how an artifact was made. Each answers a different question, and none alone proves the release is safe.

# Rootless Mode & Sandboxed Runtimes (gVisor, Kata)

A container launched by an untrusted build job reaches the host kernel through the same syscall interface as other processes. Rootless mode reduces the host privilege available to the engine; sandboxed runtimes add another boundary. They solve different problems, so select them from the workload threat model.

## Definition

Three isolation approaches address different parts of a workload's threat model: **rootless containers**, where the daemon runs as a non-root user and user namespaces map container-UID-0 to an unprivileged host UID; **gVisor (runsc)**, a userspace kernel ("Sentry") that mediates application system calls; and **Kata Containers**, a real microVM per pod with its own guest kernel behind the OCI interface.

> **Textbook Definition:** Rootless runtimes reduce host privileges through user-namespace mappings; sandboxed runtimes introduce a mediated system-call interface or virtual-machine boundary to strengthen workload isolation under a defined threat model.

```text
rootful/rootless runc: application → shared host kernel, different host privileges
gVisor:               application → Sentry's Linux interface → restricted host interfaces
Kata:                 application → guest kernel → hypervisor → host
```

Rootless limits host privilege; gVisor mediates the app's kernel interface; Kata gives a guest-kernel boundary. They are not a universal performance/security ranking, and each still depends on mounts, credentials, network policy, and patched runtime code.

## First Principles

Choose the boundary by identifying what an attacker could reach after compromising the workload: rootless execution reduces the host privilege held by the engine and mapped container identities; a syscall-mediating runtime narrows the host-kernel interface available to application code; a VM-backed runtime adds a hypervisor boundary. These controls complement capabilities, seccomp, AppArmor or SELinux, resource limits, and network policy — each addresses a different risk and none replaces the others.

## 1. Rootless Mechanics: User Namespaces, Networking, cgroups

Rootless mode leans on three cooperating pieces. First, **user namespaces**: `/etc/subuid` and `/etc/subgid` allocate ranges, and a common rootless mapping gives container UID 0 the invoking user's host UID, with additional IDs drawn from the subordinate range:

```text
/etc/subuid:            developer:165536:65536
                        └──user └start   └count

Container view          Host reality
uid 0 (root in ctr) →   invoking host user UID (for example 1000)
uid 1..65536       →    subordinate UIDs 165536..231071
```

Second, **networking without root**: rootless engines avoid privileged host network setup and normally relay container traffic through a user-space backend. The implementation and default vary by engine and version — Docker Engine 29 uses `gvisor-tap-vsock` by default, while `slirp4netns` and `pasta` are available in supported configurations. Port publishing is mediated by RootlessKit; measure throughput and source-address behavior on the target host.

Third, **cgroup delegation**: Docker requires cgroup v2 and systemd for its rootless cgroup flags. The relevant controller must also be delegated: many hosts delegate only `memory` and `pids` by default, so CPU enforcement needs an administrator-provided delegation policy. Check the user subtree's `cgroup.controllers` and `docker info`; if its cgroup driver is `none`, those resource flags are ignored. A YAML/CLI limit without an available controller is not evidence of enforcement.

```bash
# Enable and inspect rootless Docker
dockerd-rootless-setuptool.sh install      # requires configured subuid/subgid and supporting tools; installs user daemon/unit
export DOCKER_HOST=unix:///run/user/$UID/docker.sock
docker info | grep -E 'rootless|cgroup'
#  rootless: true

# Inspect the container's mapping, not the host shell's mapping.
# User-namespace mappings alone do not establish that the daemon is rootless.
docker run --rm node:24-alpine cat /proc/self/uid_map

# Networking topology
#   container ──tap──▶ rootless user-mode network backend ──host sockets──▶ internet
#   port publishing needs rootlesskit to bind low ports on the host
```

Docker Engine versions before 29.5 also placed rootless host networking inside RootlessKit's namespace, so `--network host` did not bind in the real host namespace. Engine 29.5 and later changed that behavior; sharing the host network namespace still weakens isolation, so prefer explicit port publishing unless the workload requires host networking.

## 2. gVisor: A Syscall Firewall in Userspace

The application sees a Linux-like interface implemented by **Sentry**, gVisor's userspace kernel. Sentry validates and implements calls using its own filesystem and network views, and a separate **gofer** can broker filesystem access. This narrows the host-kernel interface exposed to application calls, but the runtime still needs host services and can have vulnerabilities.

Current gVisor platforms include **systrap**, which intercepts application system calls through seccomp-based mechanisms, and **KVM**, which uses virtualization to provide the application execution boundary. Platform choice depends on host capabilities — do not assume an old ptrace diagram describes the current default.

Compatibility is interface-specific: test required ioctls, debugging, filesystem operations, networking, and performance tooling. Counting implemented system calls is not proof that an arbitrary image works. Workloads requiring unsupported interfaces need a deliberate alternative boundary, not an automatic security-policy bypass.

## 3. Kata: A MicroVM Behind the OCI Interface

```text
pod sandbox
┌────────────────────────────────────────────┐
│  VM (QEMU / Firecracker / cloud-hypervisor)│
│  ┌──────────────────────────────────────┐  │
│  │ GUEST KERNEL (dedicated, minimal)    │  │
│  │  ┌─────────┐ ┌─────────┐             │  │
│  │  │ ctr 1   │ │ ctr 2   │  namespaces │  │
│  │  └─────────┘ └─────────┘  inside VM  │  │
│  └──────────────────────────────────────┘  │
│   virtio-fs: rootfs/image shares           │
│   vsock:     control channel to shim       │
└────────────────────────────────────────────┘
        ▲ host shim → control channel → kata-agent inside guest
```

Hardware virtualization gives near-native compute and guest Linux system-call behavior, subject to guest configuration, device, and platform support. Each sandbox needs guest-kernel and virtualization resources — measure the overhead on the selected hypervisor and guest configuration. Startup includes VM and guest initialization; pooling/templating changes that cost and needs its own lifecycle and isolation checks.

## 4. Select Runtimes per Pod with RuntimeClasses

Nodes register supported runtimes, and workloads opt in per pod:

```yaml
# Nodes register their supported runtimes:
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata                      # passed to the CRI runtime
scheduling:
  nodeSelector:                    # only these nodes carry the handler
    kata-runtime: "true"
---
# Workloads opt in per pod:
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-ci-job
spec:
  runtimeClassName: kata            # matches the RuntimeClass defined above
  containers:
    - name: build
      image: myregistry.io/ci-runner:1.9
```

The kubelet forwards the handler to containerd (`runsc` or `kata`), which launches that shim instead of plain runc — one cluster, multiple isolation tiers selected by manifest.

## 5. Register the Runtime Before Selecting It

Installing `runsc` does not register it automatically with every Docker/containerd installation. Follow the installed engine version's runtime registration instructions, then verify the handler exists before using `--runtime=runsc` or `runtimeClassName: gvisor`. A containerd handler and Docker runtime name are separate configuration surfaces.

Run a small compatibility smoke test, then the application's tests. For a workload comparison, pin the same image digest, pre-pull it, repeat cold/warm starts, and measure actual CPU, network, and filesystem paths. Tools such as `bc` or GNU time are not guaranteed to exist in a minimal Alpine image — do not present a shell timing snippet as a validated cross-runtime benchmark.

## Code Examples

On Linux, Podman runs rootless without a long-lived privileged daemon:

```bash
podman run -d --name web -p 8080:80 docker.io/nginx:alpine

# Inspect only this container: user is inside, huser is the host identity.
podman exec web sh -c 'id -u'          # default exec user is 0
podman top web user huser pid hpid

# Optional socket-activated REST API; this does not supervise the web container.
systemctl --user enable --now podman.socket
# Keeping user services running after logout may require administrator authorization.
loginctl enable-linger "$USER"         # keep user services after logout
```

With the default mapping, the container's UID 0 maps to the invoking host user; an Nginx worker running as another container UID can map to a subordinate host UID. A host-wide `ps | grep nginx` does not establish which processes belong to this container. The `podman.socket` unit starts an API service on demand; a [Quadlet user unit](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html) supplies container startup/supervision. Lingering keeps the user manager available after logout; it does not create that container unit.

A hardened CI runner pool combines the sandbox with least-privilege pod settings:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ci-runner-untrusted
  namespace: ci
spec:
  replicas: 10
  selector: { matchLabels: { app: ci-runner } }
  template:
    metadata:
      labels: { app: ci-runner }
    spec:
      runtimeClassName: gvisor            # every job lands in the sandbox
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: runner
          image: myregistry.io/ci/runner:2.1
          resources:
            limits: { cpu: "2", memory: 4Gi }
          securityContext:
            allowPrivilegeEscalation: false
            capabilities: { drop: ["ALL"] }
      nodeSelector:
        sandbox.gvisor.org/pool: untrusted
      tolerations:
        - key: sandbox
          operator: Equal
          value: untrusted
          effect: NoSchedule
```

## Real-World Use Cases

- **Public CI with arbitrary pull requests.** A SaaS build platform runs customer PRs in disposable Kata sandboxes. A build job receives an OIDC token only after the trust policy permits it; untrusted fork code must not receive release credentials. The microVM adds a guest-kernel boundary, but guest-kernel, hypervisor, and host-runtime vulnerabilities remain in the threat model.
- **Multi-tenant platform with compliance boundaries.** If a contract or threat model requires a guest-kernel boundary for selected workloads, label eligible nodes, select Kata through a RuntimeClass, and document the configured boundary. Regulatory obligations do not universally mandate Kata — verify the applicable control and runtime evidence.
- **Developer laptop without sudo.** Engineers use rootless Podman daily: no daemon holding root, no sudo prompts, test compatibility with the selected Compose provider. Port publishing above 1024 plus the engine's configured networking provider handles connectivity; `podman machine` covers macOS.
- **Defense-in-depth for edge clusters.** Compare gVisor and Kata against the device's memory, startup, syscall, and I/O budget. Overhead and compatibility vary by platform — benchmark the workload and choose a boundary the operator can patch.

## Summary

Rootless mode reduces host privileges while retaining a shared kernel. gVisor mediates the application system-call interface through a userspace kernel; its runtime still uses restricted host interfaces. Kata adds a guest kernel and hypervisor boundary. Each approach changes compatibility, resource use, and the remaining attack surface. Kubernetes RuntimeClasses select configured runtimes per Pod. Choose against the workload threat model, test required interfaces, and keep the host and runtime patched.

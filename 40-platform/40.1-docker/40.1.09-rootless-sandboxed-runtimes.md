# Rootless Mode & Sandboxed Runtimes (gVisor, Kata)

## Definition

Three escalating isolation strategies beyond default Docker:

> **Textbook Definition:** Rootless runtimes reduce host privileges through user-namespace mappings; sandboxed runtimes introduce a mediated system-call interface or virtual-machine boundary to strengthen workload isolation under a defined threat model.

- **Rootless containers** — The Docker daemon (or Podman) runs as a non-root user; `user` namespaces map container-UID-0 to an unprivileged host UID. This limits the host privilege available to a compromised daemon; it does not eliminate kernel or application vulnerabilities.
- **gVisor (runsc)** — A **userspace kernel** ("Sentry") implements the Linux syscall ABI in Go; application system calls are mediated by Sentry; runtime components still call the host kernel. Syscall interception + reimplementation.
- **Kata Containers** — A real **microVM** (QEMU/Firecracker/Cloud Hypervisor) per pod with its own guest kernel; hardware virtualization does the isolating, OCI tooling hides it.

```text
rootful/rootless runc: application → shared host kernel, different host privileges
gVisor:               application → Sentry's Linux interface → restricted host interfaces
Kata:                 application → guest kernel → hypervisor → host
```

Rootless and sandboxing address different risks. Rootless limits host privilege; gVisor mediates the app's kernel interface; Kata gives a guest-kernel boundary. They are not a universal performance/security ranking, and each still depends on mounts, credentials, network policy and patched runtime code.

## First Principles

Sandboxing depth follows from the trust level of what you run:

1. **Root-in-container is still root-in-kernel-namespace** — user namespaces map container-root to an unprivileged host identity. This reduces the impact of runtime compromise but still shares the host kernel; assess required devices, networking, and cgroup support.
2. **Defense in depth stacks**: seccomp (syscall allowlist), AppArmor/SELinux (mandatory access), gVisor (userspace kernel — syscall interception), Kata (micro-VMs). Each layer assumes the previous one failed; untrusted code (CI, multi-tenant) needs the deeper stack.
3. **The threat model picks the runtime**: my own app → default runtime; user-submitted code → gVisor/Kata. The question "what if the container is malicious?" is the selector.

## Why Do We Need It?

| Problem | Solution |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| CI runners execute untrusted PR code in containers | gVisor or Kata: additional isolation boundaries reduce host exposure |
| Multi-tenant PaaS: customers run arbitrary images side by side | Stronger runtime class per tenant namespace |
| Daemon running as root is the biggest single attack surface on hosts | Rootless mode reduces daemon and container host privileges |
| Compliance mandates VM-level boundaries for regulated workloads | Kata provides hypervisor isolation with container UX |
| Kernel CVEs require emergency patching of every host | gVisor/Kata reduce exposed kernel surface; Kata fully separates kernels |
| "Noisy neighbor" or fork-bomb style abuse | cgroups still apply; sandbox adds crash-domain separation |

## How It Works

### Rootless Mechanics

Rootless mode leans on three cooperating pieces:

1. **User namespaces** — `/etc/subuid` and `/etc/subgid` allocate ranges (e.g., user `vamsi`: 165536-231071). A common rootless mapping gives container UID0 the invoking user's host UID, with additional IDs allocated from the subordinate range:

```text
/etc/subuid:            vamsi:165536:65536
                        └──user └start   └count

Container view          Host reality
uid 0 (root in ctr) →   invoking host user UID (for example 1000)
uid 1..65536       →    subordinate UIDs 165536..231071
```

2. **Network without root** — No host bridge/iptables manipulation allowed. Two user-space options:
   - **slirp4netns**: a user-space TCP/IP stack; the container's tap device is relayed through sockets. Universal but slower.
   - **pasta (passt)**: newer; copies address/route config into the namespace and avoids extra translation where possible. Lower overhead, becoming the Podman default.

3. **cgroup delegation** — With systemd, the user session receives a delegated cgroup subtree (`Delegate=yes`) so rootless engines can still set memory/CPU limits (cgroup v2 required).

```bash
# Enable and inspect rootless Docker
dockerd-rootless-setuptool.sh install      # requires configured subuid/subgid and supporting tools; installs user daemon/unit
export DOCKER_HOST=unix:///run/user/$UID/docker.sock
docker info | grep -E 'rootless|cgroup'
#  rootless: true

# Inspect the container's mapping, not the host shell's mapping.
# User-namespace mappings alone do not establish that the daemon is rootless.
docker run --rm node:22-alpine cat /proc/self/uid_map

# Networking topology
#   container ──tap──▶ slirp4netns/pasta ──host sockets──▶ internet
#   port publishing needs rootlesskit to bind low ports on the host
```

### gVisor: A Syscall Firewall in Userspace

The application sees a Linux-like interface implemented by **Sentry**, gVisor's userspace kernel. Sentry validates and implements calls using its own filesystem and network views. A separate **gofer** can broker filesystem access. This narrows the host-kernel interface exposed to application calls, but the runtime still needs host services and can have vulnerabilities.

Current gVisor platforms include **systrap**, which intercepts application system calls through seccomp-based mechanisms, and **KVM**, which uses virtualization to provide the application execution boundary. Platform choice depends on host capabilities. Do not assume an old ptrace diagram describes the current default.

Compatibility is interface-specific: test required ioctls, debugging, filesystem operations, networking and performance tooling. Counting implemented system calls is not proof that an arbitrary image works. Workloads requiring unsupported interfaces need a deliberate alternative boundary, not an automatic security-policy bypass.

### Kata: A MicroVM Behind the OCI Interface

```text
pod sandbox
┌────────────────────────────────────────────┐
│  VM (QEMU / Firecracker / cloud-hypervisor)│
│  ┌──────────────────────────────────────┐  │
│  │ GUEST KERNEL (dedicated, minimal)    │  │
│  │  ┌─────────┐ ┌─────────┐             │  │
│  │  │ ctr 1   │ │ ctr 2   │  namespaces │  │
│  │  └─────────┘ └─────────┘  inside VM  │  │
│  └──────────────────────────────────────┘  │
│   virtio-fs: rootfs/image shares           │
│   vsock:     control channel to shim       │
└────────────────────────────────────────────┘
        ▲ host shim → control channel → kata-agent inside guest
```

- Hardware virtualization (VT-x/AMD-V/ARM virt) → near-native compute, guest Linux system-call behavior, subject to guest configuration, device and platform support.
- Each sandbox needs guest-kernel and virtualization resources; measure the overhead on the selected hypervisor and guest configuration.
- Startup includes VM and guest initialization. Pooling/templating changes that cost and needs its own lifecycle and isolation checks.

### Kubernetes Runtime Classes

```yaml
# Nodes register their supported runtimes:
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata                      # passed to the CRI runtime
scheduling:
  nodeSelector:                    # only these nodes carry the handler
    kata-runtime: "true"
---
# Workloads opt in per pod:
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-ci-job
spec:
  runtimeClassName: kata            # matches the RuntimeClass defined above
  containers:
    - name: build
      image: myregistry.io/ci-runner:1.9
```

The kubelet forwards the handler to containerd (`runsc` or `kata`), which launches that shim instead of plain runc — one cluster, multiple isolation tiers selected by manifest.

## Code Examples

### Running Rootless With Podman (No Daemon At All)

```bash
# Podman is rootless-first: no daemon, forks per command
podman run -d --name web -p 8080:80 docker.io/nginx:alpine

# Prove the mapping: "root" inside is you outside
podman exec web sh -c 'id -u'          # 0
ps aux | grep nginx | head -2          # owned by your username (mapped UIDs)

# systemd integration WITHOUT root: quadlet/user units
systemctl --user enable --now podman.socket
loginctl enable-linger "$USER"         # keep user services after logout
```

### Configure the Engine Before Selecting a Runtime

Installing `runsc` does not register it automatically with every Docker/containerd installation. Follow the installed engine version's runtime registration instructions, then verify the handler exists before using `--runtime=runsc` or `runtimeClassName: gvisor`. A containerd handler and Docker runtime name are separate configuration surfaces.

Run a small compatibility smoke test, then the application's tests. For a workload comparison, pin the same image digest, pre-pull it, repeat cold/warm starts, and measure actual CPU, network and filesystem paths. Tools such as `bc` or GNU time are not guaranteed to exist in a minimal Alpine image. Do not present a shell timing snippet as a validated cross-runtime benchmark.

### Hardened CI Runner Pool (Kubernetes)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ci-runner-untrusted
  namespace: ci
spec:
  replicas: 10
  selector: { matchLabels: { app: ci-runner } }
  template:
    metadata:
      labels: { app: ci-runner }
    spec:
      runtimeClassName: gvisor            # every job lands in the sandbox
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: runner
          image: myregistry.io/ci/runner:2.1
          resources:
            limits: { cpu: "2", memory: 4Gi }
          securityContext:
            allowPrivilegeEscalation: false
            capabilities: { drop: ["ALL"] }
      nodeSelector:
        sandbox.gvisor.org/pool: untrusted
      tolerations:
        - key: sandbox
          operator: Equal
          value: untrusted
          effect: NoSchedule
```

## Real-World Use Cases

### 1. Public CI With Arbitrary Pull Requests

A SaaS build platform runs customer PRs. Every runner pod uses `runtimeClassName: kata`; secrets are injected via short-lived OIDC tokens instead of long-lived env vars. Even a malicious `npm postinstall` that attempts a Dirty-COW-class exploit hits a disposable guest kernel.

### 2. Multi-Tenant Data Platform With Compliance Boundaries

Regulated workloads (payment processing) must be hypervisor-isolated from neighbors. Platform team labels nodes `isolation=kata`, pins those pods by RuntimeClass + nodeSelector, and documents the VM boundary for auditors — while everything still deploys as ordinary YAML/images.

### 3. Developer Laptop Without sudo

Engineers use rootless Podman daily: no daemon holding root, no sudo prompts, test compatibility with the selected Compose provider. Port publishing above 1024 plus the engine's configured networking provider handles connectivity; `podman machine` covers macOS.

### 4. Defense-in-Depth for Edge Clusters

Small-footprint edge nodes run vendor-provided images nobody audited. gVisor's low memory tax (vs Kata's per-VM kernel) fits constrained hardware while still cutting the exploitable kernel surface dramatically.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assuming rootless means "no root inside container ever" | It maps UID 0→unprivileged host range; host permission checks and namespace policy still apply; not every privileged-looking operation has a universal outcome |
| Expecting gVisor to run anything (DinD, custom modules, perf/eBPF tooling) | Test compatibility first; keep an escape hatch runtimeClass |
| Treating Kata pods as cheap as runc pods for capacity math | Measure guest/runtime overhead and configure RuntimeClass overhead and workload requests accordingly |
| Publishing low ports (<1024) from rootless engines and failing mysteriously | Use rootlesskit port driver or sysctl net.ipv4.ip_unprivileged_port_start |
| Skipping cgroup v2/systemd delegation, then blaming rootless for OOM | Verify `docker info` shows cgroup v2 and limits actually apply |
| One runtime for everything because tiering seems complex | Tier deliberately: trusted internal services on runc, untrusted on sandbox |

## Best Practices

1. **Default to rootless everywhere you can** — it costs little and removes the most-exploited daemon privilege.
2. **Tier isolation by trust level**: first-party code → runc; third-party/untrusted → gVisor; regulated/hostile → Kata.
3. **Pin RuntimeClasses in platform policy** (Kyverno: reject pods referencing undefined classes; force `ci-*` namespaces onto sandbox classes).
4. **Benchmark your own workloads**, not folklore: measure startup p99, syscall-heavy paths, and network throughput per runtime before committing.
5. **Keep sandbox node pools separate** (taints + tolerations) so a runaway sandbox cannot starve trusted workloads.
6. **Update sandboxes like kernels** — gVisor and Kata ship security fixes independently of the host; automate their upgrade cadence too.

## Performance Considerations

| Boundary | Costs to measure | Compatibility checks |
| ------------- | ------------------------------------------------------------------ | ------------------------------------------------------------ |
| Rootless runc | Network forwarding, storage driver and delegated resource controls | Host port binding, mounts, devices and enforced limits |
| gVisor | Interception, filesystem brokering and virtual network paths | Required syscalls/ioctls, debugging and I/O behavior |
| Kata | Guest memory, VM startup and virtualized device paths | Guest kernel, CPU architecture and hypervisor/device support |

Measure startup p50/p99, steady-state resource use and the workload's slowest operation under representative load. Image size is disk content, not a runtime's memory overhead. There is no universal ratio that replaces these measurements.

## Summary

Rootless mode reduces host privileges while retaining a shared kernel. gVisor mediates the application system-call interface through a userspace kernel; its runtime still uses restricted host interfaces. Kata adds a guest kernel and hypervisor boundary. Each approach changes compatibility, resource use, and the remaining attack surface. Kubernetes RuntimeClasses select configured runtimes per Pod. Choose against the workload threat model, test required interfaces, and keep the host and runtime patched.

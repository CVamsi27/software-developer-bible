# Rootless Mode & Sandboxed Runtimes (gVisor, Kata)

## TL;DR

Standard runc containers share the host kernel — fine for trusted workloads, risky for multi-tenant platforms. **Rootless mode** runs the whole engine as an unprivileged user via user namespaces; **gVisor** intercepts syscalls behind a userspace kernel; **Kata** wraps each workload in a lightweight hardware-virtualized microVM. Each trades performance and compatibility for a stronger boundary.

**Why it matters:** "How do you isolate untrusted tenants on shared infrastructure?" separates seniors from juniors. You should know what each layer buys, what it costs, and when Kubernetes' `runtimeClassName` selects between them.

## Definition

Three escalating isolation strategies beyond default Docker:

- **Rootless containers** — The Docker daemon (or Podman) runs as a non-root user; `user` namespaces map container-UID-0 to an unprivileged host UID. No daemon root = no daemon-root escape.
- **gVisor (runsc)** — A **userspace kernel** ("Sentry") implements the Linux syscall ABI in Go; container processes never invoke the host kernel directly. Syscall interception + reimplementation.
- **Kata Containers** — A real **microVM** (QEMU/Firecracker/Cloud Hypervisor) per pod with its own guest kernel; hardware virtualization does the isolating, OCI tooling hides it.

```text
ISOLATION SPECTRUM (weaker → stronger boundary)

runc (default)      rootless runc         gVisor                Kata
┌───────────┐      ┌───────────┐        ┌───────────┐       ┌───────────┐
│ app        │      │ app       │        │ app       │       │ app       │
│            │ syscalls│     │  │ syscalls│        │  │ syscalls│       │ guest krl │
│  ▼         │      │  ▼        │        │  ▼        │       │           │ traps   │
│ HOST KERNEL│     │ HOST KERNEL│       │ Sentry     │       │  ▼        │
│ (direct)   │      │ (via user │        │ (Go impl) │       │ host KVM  │
│            │      │  ns only) │        │  ▼ filtered│      │  ▼        │
│            │      │           │        │ HOST KERNEL│      │ HOST KERNEL│
└───────────┘      └───────────┘        └───────────┘       └───────────┘
 kernel attack      limits root          syscall surface    separate kernel
 surface full       privileges           mostly gone        entirely gone
```

## Why Do We Need It?

| Problem | Solution |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| CI runners execute untrusted PR code in containers | gVisor or Kata: kernel exploits in the payload stay contained |
| Multi-tenant PaaS: customers run arbitrary images side by side | Stronger runtime class per tenant namespace |
| Daemon running as root is the biggest single attack surface on hosts | Rootless mode removes root from the equation entirely |
| Compliance mandates VM-level boundaries for regulated workloads | Kata provides hypervisor isolation with container UX |
| Kernel CVEs require emergency patching of every host | gVisor/Kata reduce exposed kernel surface; Kata fully separates kernels |
| "Noisy neighbor" or fork-bomb style abuse | cgroups still apply; sandbox adds crash-domain separation |

## How It Works

### Rootless Mechanics

Rootless mode leans on three cooperating pieces:

1. **User namespaces** — `/etc/subuid` and `/etc/subgid` allocate ranges (e.g., user `vamsi`: 165536-231071). Container root maps to host UID 165536:

```text
/etc/subuid:            vamsi:165536:65536
                        └──user └start   └count

Container view          Host reality
uid 0 (root in ctr) →   uid 165536 (plain user)
uid 1..65535       →    uid 165537..231071
```

2. **Network without root** — No host bridge/iptables manipulation allowed. Two user-space options:
   - **slirp4netns**: a user-space TCP/IP stack; the container's tap device is relayed through sockets. Universal but slower.
   - **pasta (passt)**: newer; copies address/route config into the namespace and avoids extra translation where possible. Lower overhead, becoming the Podman default.

3. **cgroup delegation** — With systemd, the user session receives a delegated cgroup subtree (`Delegate=yes`) so rootless engines can still set memory/CPU limits (cgroup v2 required).

```bash
# Enable and inspect rootless Docker
dockerd-rootless-setuptool.sh install      # sets up subuid/subgid + systemd unit
export DOCKER_HOST=unix:///run/user/$UID/docker.sock
docker info | grep -E 'rootless|cgroup'
#  rootless: true

# The uid_map tells the truth about privilege:
cat /proc/self/uid_map
# 0     165536      65536     ← mapped: this is rootless

# Networking topology
#   container ──tap──▶ slirp4netns/pasta ──host sockets──▶ internet
#   port publishing needs rootlesskit to bind low ports on the host
```

### gVisor: A Syscall Firewall in Userspace

```text
container process                    host
┌──────────────┐
│ open("/x")   │──ptrace stop──▶ Sentry (Go userspace kernel)
│              │                 ├─ validate fd/path against VFS view
│              │◀─result──────── ├─ implement in Go (gofer for files)
└──────────────┘                 └─ only ~70 safe host calls escape
                                    to the real kernel

Two platforms:
• ptrace platform : tracer stops tracee per syscall (portable, slower)
• KVM platform    : Sentry runs in ring 0 of a light VM (faster,
                    still no direct host-kernel syscalls from app)
```

- Implements a large subset of Linux syscalls (~200+); most Go/JVM/Python/Node apps run unmodified.
- File access goes through a **gofer** process — the app never gets a host fd directly.
- FUSE-style /dev/fuse, overlayfs-backed rootfs, its own network stack (netstack).
- Incompatible-ish cases: exotic ioctls, some ptrace-based debuggers, certain eBPF tools.

### Kata: A MicroVM Behind the OCI Interface

```text
pod sandbox
┌────────────────────────────────────────────┐
│  VM (QEMU / Firecracker / cloud-hypervisor)│
│  ┌──────────────────────────────────────┐  │
│  │ GUEST KERNEL (dedicated, minimal)    │  │
│  │  ┌─────────┐ ┌─────────┐             │  │
│  │  │ ctr 1   │ │ ctr 2   │  namespaces │  │
│  │  └─────────┘ └─────────┘  inside VM  │  │
│  └──────────────────────────────────────┘  │
│   virtio-fs: rootfs/image shares           │
│   vsock:     control channel to shim       │
└────────────────────────────────────────────┘
        ▲ agent (kata-agent) speaks CRI-O/containerd shim API
```

- Hardware virtualization (VT-x/AMD-V/ARM virt) → near-native compute, full syscall compatibility (it IS Linux).
- Memory overhead: each VM carries a guest kernel (~100-160MB before tuning; less with Firecracker/CH + overcommit tricks like virtio-mem/nydus image service).
- Boot latency: hundreds of ms to a few seconds per sandbox — mitigated by VM templating and pre-boot pools.

### Kubernetes Runtime Classes

```yaml
# Nodes register their supported runtimes:
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata                      # passed to the CRI runtime
scheduling:
  nodeSelector:                    # only these nodes carry the handler
    kata-runtime: "true"
---
# Workloads opt in per pod:
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-ci-job
spec:
  runtimeClassName: gvisor          # or: kata
  containers:
    - name: build
      image: myregistry.io/ci-runner:1.9
```

The kubelet forwards the handler to containerd (`runsc` or `kata`), which launches that shim instead of plain runc — one cluster, multiple isolation tiers selected by manifest.

## Code Examples

### Running Rootless With Podman (No Daemon At All)

```bash
# Podman is rootless-first: no daemon, forks per command
podman run -d --name web -p 8080:80 docker.io/nginx:alpine

# Prove the mapping: "root" inside is you outside
podman exec web sh -c 'id -u'          # 0
ps aux | grep nginx | head -2          # owned by your username (mapped UIDs)

# systemd integration WITHOUT root: quadlet/user units
systemctl --user enable --now podman.socket
loginctl enable-linger "$USER"         # keep user services after logout
```

### Selecting gVisor for Specific Workloads

```bash
# Install runsc alongside containerd
runsc --version
# containerd config: [plugins."io.containerd.runtime.v1.linux"]
#   runtime_type = "io.containerd.runc.v2"
# [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.gvisor]
#   runtime_type = "io.containerd.runsc.v1"

docker run --rm --runtime=runsc hello-world

# Compare syscall exposure: strace under both runtimes
docker run --rm --runtime=runc   alpine sh -c 'wget -O- https://example.com >/dev/null'
docker run --rm --runtime=runsc  alpine sh -c 'wget -O- https://example.com >/dev/null'
# Under runc: raw syscalls hit host kernel. Under runsc: intercepted by Sentry.
```

### Benchmarking the Isolation Tax

```bash
#!/usr/bin/env bash
# quick-sandbox-bench.sh — compare startup + CPU throughput
IMAGE=alpine:3.19

for RT in runc runsc kata; do
  echo "== $RT =="
  /usr/bin/time -f "start %e s" docker run --rm --runtime=$RT $IMAGE true 2>&1 | tail -1
  docker run --rm --runtime=$RT $IMAGE sh -c \
    'time (echo "scale=2000; 4*a(1)" | bc -l > /dev/null)' 2>&1 | grep real
done

# Typical shape of results (hardware-dependent):
#   start:  runc ~0.3s · runsc ~0.5-1s · kata ~1-4s
#   cpu:    runc 1.00x · runsc ~0.85-0.95x · kata ~0.90-0.98x
#   syscall-heavy I/O: runsc can drop to 0.5x or worse
```yaml

### Hardened CI Runner Pool (Kubernetes)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ci-runner-untrusted
  namespace: ci
spec:
  replicas: 10
  selector: { matchLabels: { app: ci-runner } }
  template:
    metadata:
      labels: { app: ci-runner }
    spec:
      runtimeClassName: gvisor            # every job lands in the sandbox
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: runner
          image: myregistry.io/ci/runner:2.1
          resources:
            limits: { cpu: "2", memory: 4Gi }
          securityContext:
            allowPrivilegeEscalation: false
            capabilities: { drop: ["ALL"] }
      nodeSelector:
        sandbox.gvisor.org/pool: untrusted
      tolerations:
        - key: sandbox
          operator: Equal
          value: untrusted
          effect: NoSchedule
```

## Real-World Use Cases

### 1. Public CI With Arbitrary Pull Requests

A SaaS build platform runs customer PRs. Every runner pod uses `runtimeClassName: kata`; secrets are injected via short-lived OIDC tokens instead of long-lived env vars. Even a malicious `npm postinstall` that attempts a Dirty-COW-class exploit hits a disposable guest kernel.

### 2. Multi-Tenant Data Platform With Compliance Boundaries

Regulated workloads (payment processing) must be hypervisor-isolated from neighbors. Platform team labels nodes `isolation=kata`, pins those pods by RuntimeClass + nodeSelector, and documents the VM boundary for auditors — while everything still deploys as ordinary YAML/images.

### 3. Developer Laptop Without sudo

Engineers use rootless Podman daily: no daemon holding root, no sudo prompts, identical compose workflows. Port publishing above 1024 plus rootlesskit handles the rest; `podman machine` covers macOS.

### 4. Defense-in-Depth for Edge Clusters

Small-footprint edge nodes run vendor-provided images nobody audited. gVisor's low memory tax (vs Kata's per-VM kernel) fits constrained hardware while still cutting the exploitable kernel surface dramatically.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Assuming rootless means "no root inside container ever" | It maps UID 0→unprivileged host range; privileged-looking ops inside still fail safely |
| Expecting gVisor to run anything (DinD, custom modules, perf/eBPF tooling) | Test compatibility first; keep an escape hatch runtimeClass |
| Treating Kata pods as cheap as runc pods for capacity math | Reserve ~150-300MB extra per sandbox; adjust requests/limits accordingly |
| Publishing low ports (<1024) from rootless engines and failing mysteriously | Use rootlesskit port driver or sysctl net.ipv4.ip_unprivileged_port_start |
| Skipping cgroup v2/systemd delegation, then blaming rootless for OOM | Verify `docker info` shows cgroup v2 and limits actually apply |
| One runtime for everything because tiering seems complex | Tier deliberately: trusted internal services on runc, untrusted on sandbox |

## Best Practices

1. **Default to rootless everywhere you can** — it costs little and removes the most-exploited daemon privilege.
2. **Tier isolation by trust level**: first-party code → runc; third-party/untrusted → gVisor; regulated/hostile → Kata.
3. **Pin RuntimeClasses in platform policy** (Kyverno: reject pods referencing undefined classes; force `ci-*` namespaces onto sandbox classes).
4. **Benchmark your own workloads**, not folklore: measure startup p99, syscall-heavy paths, and network throughput per runtime before committing.
5. **Keep sandbox node pools separate** (taints + tolerations) so a runaway sandbox cannot starve trusted workloads.
6. **Update sandboxes like kernels** — gVisor and Kata ship security fixes independently of the host; automate their upgrade cadence too.

## Performance Considerations

| Dimension | runc baseline | gVisor | Kata |
| ------------------------------------ | ------------- | ----------------------------------- | ------------------------ |
| Sandbox start | ~100-300ms | ~300ms-1s | ~1-4s (templating helps) |
| CPU-bound compute | 1.00x | ~0.85-0.95x | ~0.90-0.98x |
| Syscall-dense I/O (many small files) | 1.00x | often 0.3-0.6x | near-native (guest fs) |
| Network throughput | native | netstack: reduced; gofer paths vary | virtio: near-native |
| Memory per sandbox | image size | +~15-50MB | +~130MB+ guest kernel |
| Compatibility | everything | large-but-partial syscall set | full Linux ABI |

Rule of thumb: gVisor taxes syscall-heavy patterns hardest (databases on local disks, builds touching millions of files); Kata taxes memory footprint and startup; rootless taxes essentially nothing except low-port binding and initial setup friction.

## Summary

Isolation is a dial, not a switch. Rootless mode removes root from the daemon and confines even container-root to a mapped unprivileged range — nearly free, always worth doing. gVisor inserts a userspace kernel so hostile syscalls never reach yours — cheap on memory, expensive on syscall-dense I/O, partial compatibility. Kata gives every pod a private guest kernel via microVMs — strongest boundary, full compatibility, highest footprint. Kubernetes RuntimeClasses make the choice declarative per pod. Choose per trust level, benchmark honestly, and remember the interview framing: stronger isolation always trades something measurable away.

## Cheat Sheet

```text
ROOTLESS & SANDBOXED RUNTIMES CHEAT SHEET
═════════════════════════════════════════

ROOTLESS:
• /etc/subuid: user:start:count   → uid_map check: /proc/self/uid_map
• Network: slirp4netns (universal) vs pasta (faster, newer)
• Needs: cgroup v2 + systemd Delegate=yes for limits
• Low ports <1024: rootlesskit or ip_unprivileged_port_start
• Podman: daemon-less rootless-first; systemctl --user + linger

GVISOR (runsc):
• Sentry = userspace kernel; ptrace or KVM platform
• App syscalls NEVER hit host kernel; gofer fronts the filesystem
• Cost: syscall-heavy I/O down to ~0.3-0.6x; +15-50MB RAM
• Watch out: DinD, eBPF/perf tooling, exotic ioctls

KATA:
• One microVM (QEMU/FC/CLH) per pod; own guest kernel
• Full Linux ABI; hardware-virt boundary
• Cost: ~1-4s boot, +130MB+ memory per sandbox
• Mitigations: VM templating, pre-boot pools, virtio-fs/nydus

KUBERNETES:
• kind: RuntimeClass {name, handler, scheduling.nodeSelector}
• pod.spec.runtimeClassName selects isolation per workload
• Taint sandbox pools: sandbox=true:NoSchedule

DECISION LINE:
trusted code → runc · semi-trusted → gVisor · hostile/regulated
or full-compat strong isolation → Kata · everyone → rootless anyway
```

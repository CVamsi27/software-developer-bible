# Docker Interview Questions

## First Principles

This set probes the container axioms (→ 40.1.01): images as immutable artifacts, layers, and isolation.

1. **The senior tells are trade-off statements**: "X when Y, Z when not-Y" — juniors memorize answers; seniors recite the *conditions* under which each answer is right.
2. **Every question here maps to an axiom chain, not a fact** — if you can derive the answer from the linked chapters, you can answer the variant questions too (that's the point of → First Principles sections).

## 30 Most Asked Docker Interview Questions with Detailed Answers

---

### Question 1: What is Docker and how does it differ from a virtual machine?

**Answer:** Docker builds, distributes and runs container images. A normal Linux container shares its host kernel and uses namespaces for system views; cgroups account for resources and enforce limits when configured. A VM runs a guest kernel behind a hypervisor. Neither model is automatically secure: compare the threat model, privileges, mounts, host or hypervisor management, required kernel/device access, and measured startup and resource use. Docker Desktop can run Linux containers inside a Linux VM on macOS/Windows.

---

### Question 2: What is a Docker image and how is it structured?

**Answer:** An image combines content-addressed filesystem layers and execution metadata. A running container adds a writable layer and executes the configured process. RUN/COPY normally change filesystem contents; CMD/ENV mainly configure behavior, while WORKDIR can create a directory. Tags are mutable names; digests identify content. A tag moving does not modify an existing container.

---

### Question 3: What is the difference between COPY and ADD in Dockerfile?

**Answer:** COPY copies selected files from the build context or another stage. ADD can additionally retrieve supported remote sources and unpack local tar archives. Use COPY when its simpler contract is sufficient. Remote ADD has cache/checksum behavior governed by its options; it does not universally bypass caching. Pin/check remote inputs rather than assuming a URL identifies stable bytes.

---

### Question 4: Explain Docker layer caching and how to optimize it.

**Answer:** Build steps depend on their inputs and preceding state. Copy manifests/lockfile and install dependencies before copying changing source, so a source edit can reuse installation. The compile step and dependent copies still rebuild. BuildKit can reuse independent graph branches; it is inaccurate to say only one changed layer ever rebuilds. Check warm/cold builds and restored outputs on the actual project.

---

### Question 5: What is a multi-stage build and why use it?

**Answer:** Each FROM starts a stage. COPY --from transfers selected files, not the previous stage's ENV, USER or command. Keep compilers in a build stage and install or copy runtime-only dependencies into a compatible final base. An ESM package may need its manifest; a native module also needs a matching CPU/libc/runtime ABI. A smaller final image is possible, not automatic.

---

### Question 6: How do you handle secrets in Docker?

**Answer:** Keep credentials out of image layers. BuildKit secret/SSH mounts provide temporary build access; commands can still leak mounted values into logs or output files. Inject runtime credentials through supported mounted files, environment or a secret manager with scoped identity. Restrict inspection access and define rotation. Swarm secrets, local Compose secret files and an external secret service have different storage/authorization contracts.

---

### Question 7: What is Docker Compose and when would you use it?

**Answer:** Compose declares services, networks and volumes for a Docker environment. It suits local development, integration fixtures and deliberately operated single-host deployments. `depends_on` with `service_healthy` waits during startup; long syntax `restart: true` can restart a dependent after an explicit Compose-controlled dependency restart, but neither feature repairs arbitrary later connection failures. Restart policies can restart exited processes; Compose does not supply multi-host scheduling or rolling-update controllers. Configuration alone does not prove dev/CI behavior is identical.

---

### Question 8: What are Docker networks and their types?

**Answer:** A user-defined bridge supplies container-name DNS for containers sharing that network. The default bridge has different discovery behavior. Host networking shares the host network namespace and needs platform support. Overlay networks support configured multi-host Docker networking such as Swarm; Kubernetes network implementations are separately configured. macvlan assigns LAN-facing identities; none removes ordinary external networking. A database connection uses its database protocol at db:5432, not an HTTP curl request.

---

### Question 9: How do you reduce Docker image size?

**Answer:** Inspect final contents and size for the actual platform. Separate build tools from runtime artifacts, omit development dependencies after compilation, exclude irrelevant context files and remove temporary files in the same step that created them. Deleting an earlier-layer file merely hides its bytes. Alpine uses musl; slim/distroless have other runtime/debugging contracts. Size and security require evidence, not a base-image ranking.

---

### Question 10: What is the difference between CMD and ENTRYPOINT?

**Answer:** ENTRYPOINT defines the executable or fixed command prefix; CMD supplies the default command when no entry point exists, or default arguments when one does. With ENTRYPOINT ["node"] and CMD ["server.js"], passing app.js runs node app.js. Override the entry point using docker run --entrypoint node IMAGE app.js. Exec form avoids an intermediate shell, but the application still needs shutdown handlers and child reaping where applicable.

---

### Question 11: Explain Docker volume types.

**Answer:** Named volumes are Docker-managed storage retained across ordinary container removal. Bind mounts expose an explicit host path and its permissions; they can suit development or intentionally managed production configuration. tmpfs is memory-backed and transient, but host swap policy can allow pages to reach disk. A local named volume does not automatically move to another host. Define capacity, consistent backup and restore procedures.

---

### Question 12: How do you debug a container that keeps crashing?

**Answer:** Inspect logs, exit code, runtime errors, OOMKilled and restart/health state. Exit137 conventionally indicates SIGKILL; it alone does not prove OOM. Reproduce with the same limits and configuration. A shell override is useful only if the image contains a shell; distroless needs an appropriate debugging method. Check whether an app failed during startup, was force-stopped, exceeded a resource limit, or lost a dependency before choosing a fix.

---

### Question 13: What is a .dockerignore file?

**Answer:** .dockerignore removes matching paths from the build context, including files that COPY . . could otherwise package. It differs from .gitignore; track both policies. Exclude secrets, dependency/build output and irrelevant metadata. BuildKit can transfer context incrementally rather than tarring every byte on every build. Measure actual transfer/cache behavior and inspect the final image instead of assuming ignored files or a claimed MB reduction prove safety.

---

### Question 14: How do you handle database migrations in Docker?

**Answer:** Give each database migration an explicit owner and deployment step. A Compose migration service can gate startup on service_completed_successfully; a Kubernetes Job can be orchestrated before rollout. These are not universal exactly-once guarantees: retries and concurrent deployments need schema locks, migration history and idempotent/resumable behavior. Use expand/contract so old and new app versions can coexist, and verify rollback compatibility. Running migration independently in every app replica can race.

---

### Question 15: What is Docker BuildKit?

**Answer:** BuildKit executes a dependency graph of build actions, reuses cached results and supports cache, secret and SSH mounts. A cache mount persists package downloads separately from the image; a secret mount gives a build command temporary credentials. Those mechanisms do not by themselves make a build hermetic: undeclared network and host inputs still matter. Target a test stage explicitly; unrelated stages need not execute when building production. There is no generic --mount=type=lock Dockerfile mount.

---

### Question 16: Explain Docker health checks.

**Answer:** A Docker HEALTHCHECK command returns success or failure, producing starting/healthy/unhealthy state. Configure interval, timeout, startup grace and consecutive failure threshold; make the probe available in the image and fail on an invalid HTTP status. Docker health status alone does not restart the container. Restart policies respond to process exit. Kubernetes does not run Dockerfile HEALTHCHECK; configure its startup/readiness/liveness probes explicitly.

---

### Question 17: How do you manage Docker in production?

**Answer:** Promote a tested image digest, supply authorized runtime configuration, restrict privileges and verify startup/shutdown under resource limits. Operate logs, metrics, alerting and a rollout/rollback plan. Stateful services need consistent backups and tested restore; migrations need compatibility. Keep scan/signature/provenance policy explicit. A scanner passing or a non-root USER is one control, not a guarantee against compromise or a complete production release gate.

---

### Question 18: What is the difference between docker stop and docker kill?

**Answer:** docker stop sends the configured stop signal, normally SIGTERM, and forces SIGKILL after the allowed timeout. Defaults depend on the container/platform configuration. docker kill sends SIGKILL by default or an explicitly requested signal. The process must drain work and exit before the deadline; exec form or an init helps signal delivery but cannot supply app cleanup. Target the intended container rather than stopping every running container on a shared host.

---

### Question 19: How do you copy files between host and container?

**Answer:** docker cp transfers files between a host and running or stopped container. Dockerfile COPY transfers build inputs; bind mounts/volumes expose runtime storage. Choose according to the lifetime and owner of the file. Check permissions and user-namespace mapping rather than assuming ownership survives unchanged. A copied live database directory is not automatically a consistent backup.

---

### Question 20: What is the difference between docker compose up and docker compose run?

**Answer:** docker compose up reconciles selected services and dependencies from the model. docker compose run creates a one-off instance with the service's configuration and an overridden command; ports are not published by default unless requested. Profiles affect selection. For a test harness, combine appropriate exit/abort options with --exit-code-from so the intended test result determines CI success. Stopping on any container exit is not by itself the same as reporting its failure.

---

### Question 21: How do you handle different environments (dev/staging/prod)?

**Answer:** Promote one tested immutable release artifact and inject environment-specific runtime configuration. Compose override files merge models; profiles enable service groups. Model interpolation uses the shell/.env inputs, whereas env_file supplies container variables; environment entries can override them. Some frontend values are baked at build time, so decide that contract explicitly rather than assuming every env change affects an already built asset. Inspect the merged model without exposing secrets.

---

### Question 22: What is the difference between an image and a container?

**Answer:** An image is the filesystem/configuration artifact; a container is an instance with process state and a writable layer. Stopping/restarting the same container normally retains that layer. Removing the container discards it, while mounted data follows its separate lifecycle. Images also occupy local storage, not only registries, and can be garbage-collected; neither image nor container has an automatic permanent lifetime.

---

### Question 23: How do you implement logging in Docker containers?

**Answer:** Write structured application logs to stdout/stderr and configure the engine/collector for retention, rotation and transport. The process command does not itself guarantee logging behavior. json-file defaults can grow without bounds unless configured. File logging requires an intentional persistent/collector contract. Decide blocking/nonblocking delivery, buffering, dropped-log detection, multiline handling and sensitive-field redaction. Test an unavailable log collector so logging cannot silently stall the service.

---

### Question 24: What is Docker context?

**Answer:** A Docker context selects a daemon endpoint and its connection metadata. Registry credentials are configured separately in the Docker CLI credential store. Use `docker context ls` to inspect targets and `docker --context NAME ps` for an explicit operation; `DOCKER_HOST` and flags can also affect endpoint selection. Remote daemon access is powerful host control, so restrict SSH/TLS access and confirm the target before a mutation. An unauthenticated TCP 2375 endpoint exposes the daemon API.

---

### Question 25: How do you handle resource limits in Docker?

**Answer:** Memory limits bound cgroup-accounted usage, including relevant cache; reclaim and OOM behavior depend on cgroup/swap configuration. CPU quota bounds total CPU time per period and can throttle; relative CPU shares/weights matter under contention and are not a hard cap. Set PID limits as well. Inspect actual controller files/runtime metrics, and test heap sizing and limit behavior. Compose single-host resource declarations and Kubernetes scheduling requests are different contracts.

---

### Question 26: What is a Docker registry and how does it work?

**Answer:** A registry distributes manifests, configuration and filesystem blobs, typically addressed by content digest and mutable tags. Push a versioned artifact, record the resolved digest, verify it, and deploy that digest. Restrict writer/pull credentials, retention, immutability and scanning policy. Current Google managed workflows use Artifact Registry; legacy GCR references require migration/context. A registry access policy is not automatically a cluster admission policy.

---

### Question 27: How do you secure Docker containers?

**Answer:** Use compatible maintained bases, least-privilege users, restricted capabilities, read-only root where possible, no-new-privileges and explicit writable mounts. Limit resources and network access; keep credentials scoped and rotatable. Verify image identity/provenance and scan known weaknesses. These controls address different threats and do not remove shared-kernel risk. Sandboxed runtimes can add boundaries for untrusted code; test interfaces and overhead against the threat model.

---

### Question 28: What is the difference between docker-compose and Kubernetes?

**Answer:** Compose can operate a single-host application; Kubernetes adds cluster scheduling, controllers, configurable rollouts and optional autoscaling. Neither provides automatic end-to-end availability without correct probes, capacity, storage, policies and app behavior. Choose based on required failure recovery and operational capability. Kubernetes need not use Docker Engine to run OCI images; containerd/CRI-O are separate runtime integrations.

---

### Question 29: How do you handle persistent data in Docker?

**Answer:** Mount data with a deliberate storage lifetime and owner. Named local volumes survive normal container removal but remain host-local; bind mounts couple to host paths, and remote drivers add another failure model. For a stopped/disposable filesystem, tar can be a file-copy backup; for a live database, use its consistency-aware backup mechanism. Test restore, encryption/access, retention and recovery objectives. Review ownership before deleting unused volumes.

---

### Question 30: What are the best practices for writing Dockerfiles?

**Answer:** Order stable install inputs before changing source, build with required development tools, and create a final stage with compatible runtime dependencies, manifest and entry point. Avoid embedded secrets and unnecessary privileges. Pin approved digests with reviewed updates, scan actual artifacts, and implement health/shutdown through the correct runtime layer. Use [multi-stage builds](40.1.04-multi-stage-builds.md) and [production patterns](40.1.06-production-patterns.md) as the canonical recipes rather than copying a second divergent Dockerfile into the drill.

---

## Summary

Docker interview questions typically cover:

- Core concepts (images, containers, Dockerfile)
- Best practices (multi-stage builds, security, optimization)
- Production concerns (logging, monitoring, orchestration)
- Debugging and troubleshooting
- Compose and multi-container applications

Focus on understanding the **why** behind each concept, not just the **how**.

### Question 1: What is Docker and how does it differ from a virtual machine?

**Answer:**

Docker is a containerization platform that packages applications with their dependencies into lightweight, portable containers. Containers share the host OS kernel, unlike VMs which each run a full guest OS.

**Key Differences:**

| Aspect | Docker Container | Virtual Machine |
| ----------- | ------------------ | ------------------- |
| OS | Shares host kernel | Full guest OS |
| Size | MBs | GBs |
| Startup | Seconds | Minutes |
| Isolation | Process-level | Hardware-level |
| Performance | Near-native | Hypervisor overhead |
| Density | 100s per host | 10s per host |

**Architecture:**

```text
VM Architecture:
+------------------+ +------------------+

| App B     |     | App A     |
| Bins/Libs |     | Bins/Libs |
| Guest OS  |     | Guest OS  |

+------------------+ +------------------+

| Hypervisor |

+-------------------------------------+

+-------------------------------------+

| Hardware |

+-------------------------------------+

+------------------+ +------------------+

| App B     |     | App A     |
| Bins/Libs |     | Bins/Libs |

+------------------+ +------------------+
```

### Question 2: What is a Docker image and how is it structured?

**Answer:**

A Docker image is a read-only template with instructions for creating a container. It uses a union filesystem with layers, each representing a Dockerfile instruction.

**Layer Structure:**

```text
+-------------------------------+

| Layer N: CMD ["app"] | <-- ~0 bytes (metadata)
+-------------------------------+

| Layer N-1: COPY dist/ | <-- varies
+-------------------------------+

| Layer N-2: RUN npm ci | <-- ~150 MB
+-------------------------------+

| Layer N-3: COPY package.json | <-- ~0.05 MB
+-------------------------------+

| Layer N-4: WORKDIR /app | <-- ~0 bytes
+-------------------------------+

| Layer 0: node:18-alpine | <-- ~130 MB
+-------------------------------+

```

Each layer is content-addressable (SHA256 hash). Layers are cached and shared across images.

### Question 3: What is the difference between COPY and ADD in Dockerfile?

**Answer:**

| Feature | COPY | ADD |
| ---------------- | ----------- | ---------------- |
| Basic copy | Yes | Yes |
| URL download | No | Yes |
| Auto-extract tar | No | Yes |
| Control | Predictable | Less predictable |

**Best Practice:** Use `COPY` unless you specifically need tar extraction or URL downloading. `COPY` is explicit and easier to understand.


The mechanism behind the rule: `ADD`'s URL download bypasses build cache validation (the file isn't checksum-pinned, so a changed remote silently changes the build) and its auto-extract is non-obvious to readers. Explicit `COPY` makes layer content auditable from the Dockerfile alone — a real cost when debugging why an image changed. Reserve `ADD` for local tar archives you genuinely want unpacked.
```dockerfile
# Preferred
COPY package*.json ./
COPY dist/ ./dist/

# Only use ADD when needed
ADD archive.tar.gz /app/
ADD https://example.com/file.txt /app/

```

### Question 4: Explain Docker layer caching and how to optimize it.

**Answer:**

Docker caches each layer. If a layer and its context haven't changed, Docker reuses the cached version. Only changed layers rebuild.

**Optimization Strategy:**

```dockerfile
# BAD: Changes to source code invalidate dependency cache
COPY . .
RUN npm ci

# GOOD: Dependencies cached separately
COPY package*.json ./
RUN npm ci
COPY . .

```

**Cache Hierarchy (least to most changeable):**

1. Base image (rarely changes)

2. System dependencies (occasionally)

3. Application dependencies (weekly)

4. Application code (daily)

### Question 5: What is a multi-stage build and why use it?

**Answer:**

Multi-stage builds use multiple `FROM` statements to build in stages. Only artifacts from later stages are included in the final image.

**Benefits:**

- Smaller production images (no build tools)
- Better security (no compilers/shells)
- Faster CI/CD (smaller images)
- Single Dockerfile for dev/prod

```dockerfile
FROM node:22 AS builder
WORKDIR /app
COPY . .
RUN npm ci && npm run build

FROM node:22-alpine
COPY --from=builder /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]

```

### Question 6: How do you handle secrets in Docker?

**Answer:**

Never hardcode secrets in Dockerfiles or images.

**Methods:**

```bash
# 1. Environment variables (runtime only)
docker run -e DB_PASSWORD=secret myapp

# 2. Docker secrets (Swarm mode)
docker secret create db_pass password.txt

# 3. BuildKit secrets (build time)
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci

# 4. External secrets (Vault, AWS SSM)
# Use entrypoint scripts to fetch secrets

```

**Never:**

```dockerfile
# BAD: Secrets baked into image
ENV API_KEY=sk_live_abc123
COPY secrets.json /app/

```

The taxonomy matters because each layer has different blast radius: build-time secrets (BuildKit `--mount=type=secret`) never enter image layers at all — the mount is ephemeral and absent from history, unlike `ENV` which is readable by anyone with image access, forever. Runtime secrets (Swarm secrets, mounted files, Vault agent injecting at startup) keep values out of the image entirely. The senior default: fetch at runtime from a secrets manager via identity (IAM role, workload identity), so the image is environment-agnostic and rotation doesn't require a rebuild. Never bake them in — registry access is a smaller boundary than people assume.

### Question 7: What is Docker Compose and when would you use it?

**Answer:**

Docker Compose is a tool for defining and running multi-container applications using YAML configuration.

**Use Cases:**

- Local development environments
- Multi-service applications
- Integration testing
- CI/CD pipelines

```yaml
services:
  app:
    build: .
    ports: ["3000:3000"]
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:15
    volumes: ["pg_data:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD", "pg_isready"]

volumes:
  pg_data:

```

The honest scope: Compose is a developer-experience tool, not an orchestrator — single host, no self-healing, no rolling updates. That boundary is the interview answer. Depth where seniors go: `depends_on` with `condition: service_healthy` fixes the startup-order race (plain depends_on only orders *starts*, not readiness); the `version:` top-level key is deprecated — services at the root is the current schema. Compose in CI runs the *same* compose file the developer used, which is exactly what kills the 'works on my machine' class of integration-test failures.

### Question 8: What are Docker networks and their types?

**Answer:**

Docker networks enable container-to-container communication.

| Network | Description | Use Case |
| ------- | -------------------- | -------------------- |
| bridge | Default, single host | Most common |
| host | Shares host network | Performance-critical |
| overlay | Multi-host (Swarm) | Clusters |
| macvlan | Assigns MAC address | Legacy apps |
| none | No networking | Isolated workloads |


The reason user-defined bridges beat the default `bridge` is DNS: containers on it resolve each other by name, while the default bridge only offers the legacy `--link`. `host` removes the NAT hop for latency-sensitive workloads at the cost of losing port isolation; `overlay` implements VXLAN encapsulation so Swarm/K8s clusters span hosts; `macvlan` exists for legacy apps that need a real LAN identity.
```bash
# Create custom bridge network
docker network create --driver bridge mynet

# Run containers on network
docker run --network mynet --name api myapp
docker run --network mynet --name db postgres

# Containers communicate via name
# Inside api: curl http://db:5432

```

### Question 9: How do you reduce Docker image size?

**Answer:**

| Technique | Impact |
| ------------------------ | ------------------------- |
| Use Alpine base | ~130MB vs ~900MB |
| Multi-stage builds | Remove build tools |
| .dockerignore | Exclude unnecessary files |
| npm ci --only=production | No devDependencies |
| Combine RUN commands | Fewer layers |
| Use distroless | Minimal runtime |
| Remove caches | Clean npm/pip cache |

**Example:**


The underlying mechanism is layer immutability: every `RUN` persists in the image forever, so deleting files in a *later* layer doesn't shrink it — only not creating them does. That's why dependency manifests are copied before source (cache hits on `npm ci`) and multi-stage builds exist: the final stage starts fresh and copies only runtime artifacts, leaving compilers and caches in discarded layers. Alpine trades glibc for musl — verify native modules before committing.
```dockerfile
# ~900MB
FROM node:22
COPY . .
RUN npm install

# ~150MB
FROM node:22-alpine
COPY package*.json ./
RUN npm ci --only=production
COPY dist/ ./dist
USER node

```

### Question 10: What is the difference between CMD and ENTRYPOINT?

**Answer:**

| Aspect | CMD | ENTRYPOINT |
| -------- | ---------------------- | ------------------------------- |
| Purpose | Default arguments | Main executable |
| Override | `docker run myapp arg` | `docker run myapp --entrypoint` |
| Multiple | Last one wins | Can be combined with CMD |


The practical consequence is signal handling: exec-form (JSON array) runs the process as PID 1 so SIGTERM reaches it; shell-form wraps it in `/bin/sh -c`, which doesn't forward signals — containers hang for the full stop timeout. The combination pattern is the standard idiom: `ENTRYPOINT` pins the binary, `CMD` supplies arguments that `docker run myapp args` overrides — the same separation as a Kubernetes command/args pair.
```dockerfile
# ENTRYPOINT defines the executable
ENTRYPOINT ["node"]

# CMD provides default arguments
CMD ["server.js"]

# Result: node server.js
# Override args: docker run myapp app.js --> node app.js

```

### Question 11: Explain Docker volume types.

**Answer:**

| Type | Description | Persistence |
| ------------ | ----------------- | ----------- |
| Named volume | Docker-managed | Yes |
| Bind mount | Host path mapping | Yes |
| tmpfs | Memory only | No |


The choice is portability versus coupling. Named volumes live in Docker's storage area and move safely between environments — the default for stateful data. Bind mounts point at a host path: ideal for dev hot-reload, risky in production (the Docker socket bind-mount is the classic container-escape vector). `tmpfs` never touches disk, which is exactly what you want for session secrets or temp credentials that must not persist.
```bash
# Named volume
docker run -v mydata:/data myapp

# Bind mount
docker run -v /host/path:/container/path myapp

# tmpfs
docker run --tmpfs /tmp:rw,size=100m myapp

# Read-only
docker run -v /data:/app/data:ro myapp

```

### Question 12: How do you debug a container that keeps crashing?

**Answer:**

```bash
# 1. Check logs
docker logs <container>
docker logs --tail 100 <container>

# 2. Inspect container
docker inspect <container>

# 3. Check exit code
docker inspect --format='{{.State.ExitCode}}' <container>

# 4. Run with shell override
docker run --entrypoint sh -it myapp

# 5. Check health status
docker inspect --format='{{.State.Health.Status}}' <container>

# 6. View resource usage
docker stats <container>

```

The loop mirrors K8s triage but with direct process access: exit code first — 137 is OOMKill or SIGKILL, 126/127 are entrypoint/command problems, 1 is an app error whose stack trace is in `docker logs`. `--entrypoint sh` is the escape hatch: run the image with a shell to inspect the environment it actually has (env vars, file presence, DNS) — but note it tests the *image*, not the crash. `docker inspect` .State gives restart count, OOMKilled flag, and error message. The senior habit: reproduce locally with the same limits (`-m`) — most 'works locally, crashes in prod' container stories are memory limits never replicated on the laptop.

### Question 13: What is a .dockerignore file?

**Answer:**

`.dockerignore` excludes files from the build context, reducing build time and preventing sensitive files from entering the image.

```text
node_modules
npm-debug.log
.git
.gitignore
.env
.env.*
Dockerfile
docker-compose.yml
*.md
coverage
.nyc_output
.vscode
.idea

```

**Impact:** A project with `node_modules` (200MB) vs without (2MB) significantly affects build context upload time.

The mechanism juniors miss: the entire build context is tarred and streamed to the daemon on *every* build — .dockerignore shrinks that transfer and, critically, keeps `.env`, `.git`, and credentials out of `COPY . .` reach. Layer-cache interaction matters too: context changes touching files a COPY layer depends on invalidate that layer — ignoring volatile files preserves cache. The senior line: treat .dockerignore as a security control, not an optimization; .gitignore semantics but with a different failure mode — one missing pattern and the secret ships inside the image.

### Question 14: How do you handle database migrations in Docker?

**Answer:**

**Option 1: Init Container Pattern**

```yaml
services:
  migrations:
    image: myapp
    command: npm run migrate
    depends_on:
      db:
        condition: service_healthy
    restart: "no"

  app:
    image: myapp
    command: npm start
    depends_on:
      migrations:
        condition: service_completed_successfully

```

**Option 2: Entrypoint Script**

```bash
#!/bin/sh
set -e
npm run migrate
exec node server.js

```

**Option 3: Kubernetes Jobs**
Use a Job resource that runs migrations before the Deployment.

The principle: migrations must run exactly once, before the new version serves — which is why the entrypoint script pattern (migrate then exec app) is dangerous at scale: every replica races the migration, and rollback runs old code on a new schema. The correct patterns isolate migration as a step: init/service container gated on `service_completed_successfully`, K8s Job or init container before the Deployment rolls, or a pipeline stage. The senior architecture answer: forward-compatible, expand/contract migrations — additive first, old code runs on new schema during the rollout window, destructive changes in a later release.

### Question 15: What is Docker BuildKit?

**Answer:**

BuildKit is the modern build engine for Docker, providing:

- Parallel stage builds
- Cache mount support
- Secret mounts
- SSH forwarding
- Better output formatting

```bash
# Enable BuildKit
DOCKER_BUILDKIT=1 docker build -t myapp .

# Use cache mounts
RUN --mount=type=cache,target=/root/.npm npm ci

# Use secret mounts
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci

# Use SSH mounts
RUN --mount=type=ssh ssh git@github.com

```

BuildKit is not just faster — it changes what builds can *do*. The senior specifics: cache mounts persist package-manager caches across builds without baking them into layers; secret mounts pass credentials at build time without leaving them in history (the classic npm-token problem); SSH forwarding lets a build clone private repos without copying keys into any layer; and `--mount=type=lock` plus frontend directives enable hermetic builds. Parallel-stage execution comes free via the dependency DAG. It's default in modern Docker — knowing it's *the* engine, not an opt-in, is the current-answer tell.

### Question 16: Explain Docker health checks.

**Answer:**

Health checks verify container health status.


The exit-code contract is the whole design: the command's success or failure *is* the health signal, so any check must fail fast and cheap — an endpoint hit beats a script. `start-period` exists because slow-booting apps otherwise crash-loop before they're ready. Note Docker has no readiness concept: an unhealthy container is restarted, not just removed from load-balancing — that distinction is Kubernetes' addition.
```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1

```

| Parameter | Description |
| ------------ | ------------------------------ |
| interval | Time between checks |
| timeout | Max time per check |
| start-period | Grace period for startup |
| retries | Failed checks before unhealthy |

**Status:** `healthy`, `unhealthy`, `starting`

**Answer:**

| Aspect | Solution |
| ------------- | ---------------------------------- |
| Orchestration | Kubernetes, Docker Swarm |
| Registry | ECR, GCR, ACR, Docker Hub |
| Monitoring | Prometheus, cAdvisor, Datadog |

| Security | Trivy, Clair, Docker Scout |

**Production Checklist:**

- Non-root user

- Log rotation
- Image scanning
- Secrets management

The checklist encodes the deployment pillars: non-root limits the blast radius of a container escape; health checks give the orchestrator something to act on; log rotation matters because the container logging driver tails stdout — writing logs to files inside the container instead silently fills the writable layer. Secrets belong in a manager, not env vars, which any `docker inspect` (or image-layer archaeology) exposes.

### Question 18: What is the difference between docker stop and docker kill?

**Answer:**

| Command | Signal | Behavior |
| ------------- | --------------------- | ------------------------------- |
| `docker stop` | SIGTERM, then SIGKILL | Graceful shutdown (10s default) |
| `docker kill` | SIGKILL (default) | Immediate termination |

```bash
# Graceful stop with timeout
docker stop --time=30 mycontainer

# Kill with specific signal
docker kill --signal=SIGTERM mycontainer

# Stop all running containers
docker stop $(docker ps -q)

```

The mechanism: `stop` sends SIGTERM and waits (default 10s, `--time` to extend) before SIGKILL — grace period for connection draining and in-flight request completion; `kill` sends SIGKILL immediately (unless `--signal` overrides) — data corruption risk for anything mid-write. The senior trap: the PID-1 problem — many images run shell wrappers that don't forward signals, so the app never sees SIGTERM and every stop is really a kill after timeout. Fix with exec-form ENTRYPOINT and tini or explicit signal handling. The `stop --time` value should match the app's actual shutdown duration, measured not guessed.

### Question 19: How do you copy files between host and container?

**Answer:**

```bash
# Copy from host to container
docker cp ./config.json mycontainer:/app/config.json

# Copy from container to host
docker cp mycontainer:/app/logs ./logs

# During build (better approach)
COPY ./config.json /app/config.json

# Using volumes (best for development)
docker run -v $(pwd)/config:/app/config myapp

```

The layered answer: `docker cp` is the debugging tool (pull logs, artifacts out of a running container); COPY is the build-time answer; volumes/bind-mounts are the runtime answer — and for development, bind-mounting source beats rebuilding on every change. Senior nuance: `docker cp` preserves the file but not ownership semantics across user namespaces — chown inside if the container runs non-root; and `docker compose cp` extends the same to compose services. The real interview signal: knowing when each layer applies rather than listing commands.

### Question 20: What is the difference between docker-compose up and docker-compose run?

**Answer:**

| Command | Purpose |
| ------- | --------------------------------------------- |
| `up` | Start all services defined in compose file |
| `run` | Start a specific service for one-off commands |

```bash
# Start entire application
docker compose up -d

# Run one-off command
docker compose run --rm app npm test

# Run with service overrides
docker compose run --rm -e DEBUG=true app sh

```

The distinction that matters: `up` runs the *declared* application — all services, the compose file as contract; `run` executes a one-off in a service's environment (same image, networks, env) with overrides, `--rm` for cleanup — the CI/test workhorse. Senior details: `run` does not publish ports by default (deliberate — one-off commands shouldn't collide with the running stack) and replaces the service's command; `up -d` is the detached production-ish flow, `up --abort-on-container-exit` for test harnesses that must fail when any container fails.

### Question 21: How do you handle different environments (dev/staging/prod)?

**Answer:**

**Option 1: Multiple Compose Files**

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

```

**Option 2: Profiles**

```yaml
services:
  app:
    profiles: ["dev", "prod"]

  debug:
    profiles: ["dev"]

```

**Option 3: Environment Variables**

```bash
# .env.dev
NODE_ENV=development
DATABASE_URL=postgres://localhost/dev

# .env.prod
NODE_ENV=production
DATABASE_URL=postgres://prod-db/prod

```

The senior principle: one immutable image promoted through environments — differences live in configuration, not in builds. Compose files override per environment (`-f base.yml -f prod.yml` merges), profiles toggle which services exist where, env-files supply per-env values — but if you find yourself building a different image per environment, that's the drift factory CI exists to prevent. Depth: `env_file` vs `environment` precedence, secrets via mounted files rather than env (env vars leak via `docker inspect`, child processes, and crash dumps).

### Question 22: What is the difference between an image and a container?

**Answer:**

| Concept | Image | Container |
| ----------- | -------------- | ---------------- |
| State | Immutable | Mutable |
| Storage | Registry | Local filesystem |
| Creation | `docker build` | `docker run` |
| Analogy | Class | Instance |
| Persistence | Permanent | Ephemeral |

An image is a template. A container is a running instance of that image with added writable layers.

The image/container split mirrors class/instance but the mechanism underneath is layers plus copy-on-write: containers add one thin writable layer on top of the image's read-only layers, so starting a container is cheap and ten containers share one image's disk. The writable layer is ephemeral by design — anything that must survive belongs in a volume, which is why 'pets' inside containers is the anti-pattern.

### Question 23: How do you implement logging in Docker containers?

**Answer:**

**Option 1: stdout/stderr (Recommended)**

```dockerfile
# Application logs to stdout
CMD ["node", "server.js"]
# In app: console.log("Request processed")

```

**Option 2: Docker Logging Drivers**

```bash
# JSON file (default)
docker run --log-driver=json-file --log-opt max-size=10m myapp

# syslog
docker run --log-driver=syslog myapp

# fluentd
docker run --log-driver=fluentd myapp

```

**Option 3: Compose Configuration**

```yaml
services:
  app:
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"

```

The 12-factor answer with teeth: containers log to stdout/stderr and the *host's* log driver decides where it goes — json-file (default, with rotation options or the disk fills), or a shipping driver (fluentd, syslog, gelf) straight to an aggregator. The senior additions: multi-line logs (stack traces) break naive line-oriented shippers — log as JSON from the app or configure a merging driver; never log to files inside the container (they vanish with the container and rot the layer); and set rotation explicitly — the default json-file driver without max-size is a disk-full incident on a schedule.

### Question 24: What is Docker context?

**Answer:**

Docker contexts allow managing multiple Docker hosts.

```bash
# List contexts
docker context ls

# Create context for remote host
docker context create remote --docker "host=ssh://user@remote-host"

# Use remote context
docker context use remote

# Run commands on remote host
docker ps

```

Contexts answer 'which daemon am I talking to' — local socket, remote SSH host, or a cloud endpoint — and every docker command runs against the active one. The senior use: managing a remote dev/staging daemon over SSH without exposing it, or DOCKER_HOST-style switching in CI. The security note worth adding: remote contexts mean your local CLI holds remote control — scope SSH keys accordingly, and the older DOCKER_TLS_VERIFY/tcp:2375 pattern should never appear in modern setups (unauthenticated daemon access was always the footgun).

### Question 25: How do you handle resource limits in Docker?

**Answer:**

```bash
# Memory limit
docker run -m 512m myapp

# CPU limit
docker run --cpus=1.5 myapp

# CPU shares (relative weight)
docker run --cpu-shares=512 myapp

# GPU access
docker run --gpus all myapp

```

**Compose:**

```yaml
services:
  app:
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: "1.5"
        reservations:
          memory: 256M
          cpus: "0.5"

```

The mechanism: limits are cgroup controls — `-m` caps memory where exceeding it means OOMKill (exit 137), `--cpus` caps CPU quota where exceeding it means *throttling* (latency spikes, no crash — the sneakier failure). Senior depth: always set memory limits and requests separately (reservation vs limit in compose terms); watch for JVM/python runtimes that size heaps from host memory rather than cgroups (need explicit flags or modern defaults); cpu-shares is the relative-weight tool for fair sharing under contention, not a hard cap. Unbounded containers are how one noisy service takes down a node.

### Question 26: What is a Docker registry and how does it work?

**Answer:**

A registry stores and distributes Docker images.

| Registry | Description |
| ---------- | --------------- |
| Docker Hub | Public, default |
| AWS ECR | AWS managed |
| Google GCR | GCP managed |
| Azure ACR | Azure managed |
| Harbor | Self-hosted |


The registry is the distribution layer that makes images actually shareable, and its main operational trap is tag mutability: `myapp:latest` can silently point somewhere else tomorrow, so production pull policies pin digests (`@sha256:...`). Self-hosted registries exist for compliance and air-gapped clusters; pull-through caches mitigate Docker Hub rate limits, which is usually the first production incident a registry causes.
```bash
# Tag and push to registry
docker tag myapp:latest registry.example.com/myapp:1.0.0
docker push registry.example.com/myapp:1.0.0

# Pull from registry
docker pull registry.example.com/myapp:1.0.0

```

### Question 27: How do you secure Docker containers?

**Answer:**

**Image Security:**

- Use minimal base images (Alpine, distroless)
- Scan for vulnerabilities (Trivy, Clair)
- Sign images (Docker Content Trust)
- Don't run as root

**Runtime Security:**

- Read-only filesystem
- Drop capabilities
- No new privileges
- Resource limits

**Network Security:**

- Internal networks for backend services
- TLS for all connections
- Network policies

```bash
# Security best practices
docker run \
  --read-only \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges \
  --user 1000:1000 \
  myapp

```

### Question 28: What is the difference between docker-compose and Kubernetes?

**Answer:**

| Aspect | Docker Compose | Kubernetes |
| -------------- | -------------- | ---------- |
| Scale | Single host | Multi-host |
| Complexity | Simple | Complex |
| Use case | Development | Production |
| Self-healing | Limited | Full |
| Auto-scaling | No | Yes |
| Learning curve | Low | High |

**When to use Compose:** Local dev, testing, simple deployments
**When to use K8s:** Production, large scale, microservices, multi-tenant

The framing that resolves the 'which one?' question: they're different lifecycle stages, not competitors. Compose models a single host's dev/test topology in one file and stays out of your way; Kubernetes trades operational complexity (scheduling, self-healing, rollouts, autoscaling) for multi-host production guarantees. The common path is Compose locally, K8s in staging onward — with migration tooling bridging the gap.

### Question 29: How do you handle persistent data in Docker?

**Answer:**

```bash
# Named volume (recommended for production)
docker volume create mydata
docker run -v mydata:/app/data myapp

# Bind mount (development only)
docker run -v $(pwd)/src:/app/src myapp

# Backup volume
docker run --rm -v mydata:/data -v $(pwd):/backup \
  alpine tar czf /backup/backup.tar.gz -C /data .

# Restore volume
docker run --rm -v mydata:/data -v $(pwd):/backup \
  alpine tar xzf /backup/backup.tar.gz -C /data

```

The decision the question wants: named volumes (docker-managed, survive container removal, the production answer for stateful data) vs bind mounts (host-path mapped, the development answer for live-reload source) vs tmpfs (ephemeral, secrets/scratch). Senior depth: volume drivers let volumes live on network storage; the backup pattern shown (alpine tar over the volume) is the standard trick worth knowing cold; and anonymous volumes from image VOLUME instructions are a leak class — `docker system prune --volumes` policy matters because 'the database was in a volume that got pruned' is a real postmortem genre.

### Question 30: What are the best practices for writing Dockerfiles?

**Answer:**

1. **Use specific image versions** — `node:18.17.0-alpine`

2. **Use multi-stage builds** — separate build and runtime

3. **Order instructions by change frequency** — deps before source

4. **Use .dockerignore** — exclude unnecessary files

5. **Run as non-root** — `USER node`

6. **Add health checks** — enable orchestration monitoring

7. **Minimize layers** — combine RUN commands

8. **Use BuildKit** — better caching and security

9. **Scan images** — check for vulnerabilities
10. **Document with LABELs** — metadata for maintainability

```dockerfile
# GOOD Dockerfile example
FROM node:22.14.0-alpine AS builder
LABEL maintainer="team@example.com"
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production && npm cache clean --force
COPY . .
RUN npm run build

FROM node:22.14.0-alpine
RUN apk add --no-cache dumb-init
WORKDIR /app
COPY --from=builder --chown=node:node /app/dist ./dist
COPY --from=builder --chown=node:node /app/node_modules ./node_modules
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD node -e "require('http').get('http://localhost:3000/health')"
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/server.js"]

```

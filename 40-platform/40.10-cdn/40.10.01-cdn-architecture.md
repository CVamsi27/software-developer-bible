# CDN Architecture

A public asset can be reused by many clients. A patient record cannot be reused across those clients merely because its URL matches. A content delivery network (CDN) adds delivery locations and policies between users and origins; decide which responses may be reused before choosing its topology.

## Definition

A **CDN deployment architecture** is the arrangement of edge locations, origin shields and origin access/configuration used by a product. An **edge location**, often called a point of presence (PoP), receives requests near a network path selected by the provider. An **origin** supplies the source response. An **origin shield** is an optional intermediate cache that reduces eligible miss traffic reaching that origin.

> **Textbook Definition:** A content delivery network is a distributed delivery layer that serves eligible representations from edge locations and forwards misses or dynamic requests to origins according to routing, cache and access policies.

```text
client → selected edge → optional shield → origin
          eligible hit: reuse response
          miss/bypass: follow the configured origin path
```

The selected edge is not necessarily the geographically closest one. Network routing, provider policy, capacity and failures affect selection. Edge code and transforms may run under additional runtime limits.

## First Principles

Every uncached response requires work at its serving source and transfers bytes toward the user. Reusing an equivalent response can reduce that work and shorten part of the network path. Reuse is safe only if the next request is entitled to the same representation.

Copies introduce delay: changing the origin does not contact every browser or edge copy. A deployment therefore needs representation identity, permitted staleness and a recovery/invalidation policy. More cache layers create more ownership boundaries, not a single global freshness guarantee.

A miss still reaches an origin. A traffic spike or cache flush can expose origin capacity that a high average hit ratio concealed. Shielding/coalescing can reduce eligible repeated fetches, but not arbitrary personalized traffic, all unique keys or every retry.

## Why It Matters

Measure latency and origin offload separately for hits, misses and bypassed requests. A high overall hit ratio can hide a hot uncacheable route. TLS termination, request inspection and edge logs also make the provider part of the data-processing boundary even when a response is never cached.

## How It Works

### Define a policy for each response class

| Content | Example policy | Conditions |
| ------------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| Versioned public JS/image | `public, max-age=31536000, immutable` | URL identifies bytes that will never change; old assets remain available while referenced |
| Public HTML shell | Revalidate or use a stated short freshness period | Old tabs/service workers and old API clients still need a compatibility policy |
| Public catalog response | Shared freshness plus required representation variants | Query, language and other output-changing inputs participate in identity |
| Personalized/sensitive response | `no-store` and explicit CDN bypass policy | Verify actual edge rules, custom code and every response/error path; logs are separate |

These are illustrative choices. `no-cache` permits storage but requires validation before ordinary reuse; `no-store` directs compliant caches not to store the response. Neither method choice nor a header is an access-control system. See [HTTP caching](../../20-backend/20.3-rest-apis/02-http-mechanics/20.3.2.04-http-caching.md) for the canonical directive semantics.

### Follow one public asset across a deployment

1. Release A's HTML references `/assets/app.a1b2.js`; the edge stores the eligible bytes under that identity.
2. Release B publishes `/assets/app.c3d4.js` before its HTML references it. The new URL misses once along each applicable cache path, then can be reused.
3. A user with an old tab can still run A. Keep its referenced assets and supported API behavior for the chosen transition period.
4. If `/assets/app.a1b2.js` is overwritten, the immutable policy is now false. A new filename only helps when the HTML/client actually obtains the new reference.

Versioned URLs avoid replacing an existing asset's bytes; they do not update every open client or reverse a breaking API rollout.

### Protect and test the origin path

Choose reachable origins, verified TLS per hop, permitted Host/forwarding headers and an access policy. Prevent unapproved direct-origin access where the security design depends on the CDN. A source-IP allowlist may accept shared provider infrastructure; authenticated origin requests can establish a narrower boundary when supported. Validate the deployed contract rather than assuming a CDN address alone proves the requesting tenant.

An origin shield and miss coalescing share eligible same-object work. They still need capacity, error/retry handling and cache-key agreement. Cache warm-up is an optimization, not assurance that every PoP retains an object.

### Treat purge as an observed operation

A provider may invalidate by URL, tag or another supported identity. Submit the right variants, check HTTP and API-result errors, handle quotas, and track completion/verification according to that API. API acceptance is not universal proof that every client copy is gone. A CDN purge does not delete browser caches or already-downloaded files.

For an emergency correction, balance stale-copy risk against the origin load caused by invalidation. `stale-while-revalidate` explicitly permits old data while refresh runs; it is not a promise of an immediately fresh response. Retire invalidated objects and allowed stale behavior under the actual product contract.

## Real-World Decisions

### Edge code needs a complete request contract

Routing, token verification or image negotiation can run near users, but checking that an Authorization header exists does not verify its credential. Validate identity/scope and authorize before every protected cache hit. A random response header also does not implement a stable A/B experiment: assignment, variant selection and cache identity must agree.

Choose edge placement from runtime support, data dependency latency, consistency and operation cost. A nearby function that synchronously calls a distant database can retain most of that distance cost. Durable services can support edge writes under an explicit authority protocol; proximity alone does not supply one.

### Sensitive data includes transit and telemetry

Protected health information (PHI) can appear in bodies, URLs, headers, logs, analytics and diagnostics. Avoid placing sensitive identifiers in casually retained URLs/logs; a POST body can still be processed or recorded by intermediaries. Opaque identifiers can remain personal data when linkable to a person.

For a HIPAA-covered workflow, determine the actual provider/service data flow, applicable safeguards and business-associate obligations. HHS cloud guidance explains that providers maintaining or processing electronic PHI can be business associates, including in some encrypted-data cases. A `no-store` header is one cache control, not proof of compliance. Data-location requirements must cover processing, storage and logs; steering users to an EU-looking hostname does not establish them.

### Compare providers with current evidence

Evaluate audience-path measurements, origin security, cache/routing features, runtime limits, purge operations, logging, contract terms and quoted cost. Distinguish request hit ratio from byte offload and account for request/transform/security fees and origin egress. Free tiers, supported services and compliance offerings change; verify the intended account and service rather than relying on a static vendor table.

## Mistakes

- Treating POST, `no-store`, a cache key or an opaque token as complete privacy/access protection.
- Overwriting an immutable URL or deleting old assets still referenced by clients.
- Claiming a purge is immediate everywhere or expecting it to remove browser copies.
- Assuming request coalescing works for every response or a warm secondary cannot become cold.
- Caching error/personalized responses because a broad rule overrides the origin policy.

## Best Practices

Maintain a response-class policy matrix, test hit/miss/bypass paths and measure recovery after invalidation or origin failure. Keep sensitive processing/logging and origin trust explicit. Use current provider documentation and actual probes for account-specific behavior; a diagram is not deployment evidence.

## Summary

A CDN distributes delivery work under representation, cache, routing and trust policies. Equivalent authorized responses can be reused; misses still expose origin work and copies still need a freshness/recovery contract. Verify cache behavior, origin access and data processing as separate boundaries.

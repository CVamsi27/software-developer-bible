# CDN Architecture

> **Content Delivery Networks, edge caching, cache invalidation, and healthcare PHI considerations.**

---

## First Principles

(→ 30.3.4.03 covers the architecture axioms; the operations view:)

1. **The CDN's value is proximity + offload**: latency for users, requests absorbed before origin — both scale with hit ratio, which is the metric everything else serves.
2. **You configure behavior through cache rules**: origins, TTLs, keys, bypass conditions — the discipline is knowing *per content class* what staleness is acceptable (→ 20.8.01's per-field question at CDN scale).

## What Is a CDN?

A CDN caches content at edge locations worldwide. Users request content from the nearest edge server instead of the origin server, reducing latency.

```
Without CDN:
User (Berlin) ──── 150ms ────→ Origin Server (Virginia)
                               ← 150ms
Total: 300ms

With CDN:
User (Berlin) ──── 10ms ────→ Edge Server (Frankfurt)
                               ← 10ms
Total: 20ms (cached) or 170ms (cache miss → origin)
```

## CDN Caching Strategies

| Strategy | How It Works | Use Case |
| ------------------- | -------------------------------------------- | -------------------- |
| **Static Assets** | CSS, JS, images cached aggressively (1 year) | Bundle files, fonts |
| **API Responses** | Cache-Control headers control caching | Public API responses |
| **HTML Pages** | Edge-side rendering or static HTML | Marketing pages |
| **Purge on Deploy** | Clear cache on each deployment | SPA shell |

### Cache-Control Headers

```typescript
// NestJS — set cache headers per route
@Get('assets/:filename')
@Header('Cache-Control', 'public, max-age=31536000, immutable')
serveAsset(@Param('filename') filename: string) {
  return.sendFile(filename);
}

// No caching for API responses
@Get('api/appointments')
@Header('Cache-Control', 'no-store, no-cache, must-revalidate')
async getAppointments() {
  return this.appointmentsService.findAll();
}
```

## Cache Invalidation

The hardest problem in caching: how to ensure stale content is replaced.

| Strategy | How It Works | Pros | Cons |
| -------------------------- | -------------------------------- | ------------ | ----------------------- |
| **TTL-based** | Content expires after time | Simple | Stale during TTL |
| **Versioned URLs** | Hash in filename (app.abc123.js) | Never stale | Build complexity |
| **Purge API** | Explicitly clear cache | Immediate | Requires infrastructure |
| **Stale-while-revalidate** | Serve stale, fetch fresh in bg | Fast + fresh | Complexity |

```typescript
// Versioned URLs (Vite/Vercel automatic)
// Output: app.abc123.js → cached forever, new hash on deploy

// Cache purge API (Cloudflare)
async function purgeCache(urls: string[]) {
  await fetch(`https://api.cloudflare.com/client/v4/zones/${ZONE_ID}/purge_cache`, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${CF_API_TOKEN}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ files: urls }),
  });
}
```

## Edge Computing

Edge functions run code at CDN edge locations — closer to users than traditional servers.

| Platform | Function Type | Cold Start | Use Case |
| ---------------------- | -------------- | ---------- | -------------------------------------- |
| **Cloudflare Workers** | V8 isolates | < 1ms | API proxy, auth, A/B testing |
| **Vercel Edge** | V8 isolates | < 1ms | Middleware, redirects, personalization |
| **AWS Lambda@Edge** | Node.js/Python | 50-200ms | Image transformation, headers |
| **Deno Deploy** | V8 isolates | < 1ms | API routes, SSR |

```typescript
// Cloudflare Worker — edge middleware
addEventListener('fetch', (event) => {
  event.respondWith(handleRequest(event.request));
});

async function handleRequest(request: Request): Promise<Response> {
  const url = new URL(request.url);

  // Edge auth check
  const token = request.headers.get('Authorization');
  if (url.pathname.startsWith('/api/') && !token) {
    return new Response('Unauthorized', { status: 401 });
  }

  // A/B testing at edge
  const variant = Math.random() > 0.5 ? 'A' : 'B';
  const response = await fetch(request);
  const newResponse = new Response(response.body, response);
  newResponse.headers.set('X-AB-Variant', variant);

  return newResponse;
}
```

## Healthcare PHI Considerations

| Concern | Rule | Implementation |
| -------------------- | ------------------------------------------- | ------------------------ |
| **PHI in URLs** | Never cache URLs containing patient data | Use POST for PHI queries |
| **PHI in headers** | Never put patient IDs in cache keys | Use opaque tokens |
| **PHI in responses** | Cache-Control: no-store for PHI endpoints | Server-side caching only |
| **Audit logging** | Log all PHI access, including edge requests | Edge function logs |

```typescript
// BAD: PHI in URL (will be cached by CDN)
@Get('patients/:patientId/records')
async getRecords(@Param('patientId') patientId: string) { ... }

// GOOD: PHI via POST (not cached by CDN)
@Post('patients/records')
async getRecords(@Body() dto: GetRecordsDto) { ... }
```

## Interview Questions

**Q: "How do you handle cache invalidation for a SPA?"**

> Use versioned URLs (Vite generates `app.abc123.js`) — each deploy gets a new hash, so the browser always loads the new version. Set `Cache-Control: public, max-age=31536000, immutable` for hashed assets. For the HTML shell, set `Cache-Control: no-cache` so the browser always checks for updates. For API responses, use `no-store` for PHI and `stale-while-revalidate` for non-sensitive data.

**Q: "How do you prevent PHI from being cached at the CDN edge?"**

> Never put patient identifiers in URLs (CDN caches by URL). Use POST requests for PHI queries (CDN doesn't cache POST). Set `Cache-Control: no-store` on all PHI endpoints. Use opaque session tokens instead of patient IDs in cache keys. For Docita: appointment and patient data always goes through POST with no-store headers — only static assets (CSS, JS, images) are CDN-cached.

## 30-Second Interview Version

> CDNs cache content at edge locations worldwide. Static assets: cache forever with versioned URLs (`app.abc123.js`). HTML: no-cache to always check for updates. API: no-store for PHI, stale-while-revalidate for non-sensitive data. Edge computing (Cloudflare Workers, Vercel Edge) runs code at the edge for auth, A/B testing, personalization. For healthcare: never cache PHI in URLs or response bodies — use POST + no-store headers.

## Summary

1. **A CDN is a distributed reverse proxy with a cache-control contract** — edge POPs serve content based on origin-set headers; the origin's `Cache-Control` is the whole policy surface
2. **Tiering is deliberate** — browser → edge POP → origin shield → origin; shield POPs collapse fetch storms for popular objects
3. **Purge is the escape hatch, and it varies by vendor** — soft TTLs, surrogate keys, and purge APIs are the operational difference between providers
4. **Edge compute moves request logic to the user** — auth rewrites, A/B assignment, and personalization run at POPs, subject to runtime limits
5. **Security and compliance are edge concerns** — WAF/DDoS at the edge, but PHI-like payloads demand no-store discipline end to end

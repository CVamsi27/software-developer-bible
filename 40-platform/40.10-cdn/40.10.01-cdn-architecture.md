# CDN Architecture

A public image can be reused by many clients. A patient record cannot be shared merely because its uniform resource locator (URL) matches. A content delivery network (CDN) adds delivery locations and policies between users and origins; decide which responses may be reused before choosing its topology.

## Definition

A **CDN deployment architecture** is the arrangement of edge locations, optional intermediate caches and origin access/configuration used by a product. An **edge location**, often called a point of presence (PoP), receives requests near a network path selected by the provider. An **origin** supplies the source response. An **origin shield** is an optional cache layer between edge caches and the origin; it can improve reuse across edge locations and reduce eligible origin requests.

> **Textbook Definition:** A content delivery network is a distributed delivery layer that serves eligible representations from edge locations and forwards misses or dynamic requests to origins according to routing, cache and access policies.

```text
client → selected edge → optional shield → origin
          eligible hit: reuse response
          miss/bypass: follow the configured origin path
```

The selected edge is not necessarily the geographically closest one. Network routing, provider policy, capacity and failures affect selection. Edge code and transforms may run under additional runtime limits.

## First Principles

Every uncached response requires work at its serving source and transfers bytes toward the user. Reusing an equivalent response can reduce that work and shorten part of the network path. Reuse is safe only when the next request is entitled to the same representation and every input that changes its bytes is represented in the cache identity.

Copies introduce delay: changing the origin does not contact every browser or edge copy. A deployment therefore needs representation identity, permitted staleness and a recovery/invalidation policy. More cache layers create more ownership boundaries, not a single global freshness guarantee.

A miss or bypass still follows the configured origin path. A traffic spike or cache flush can expose origin capacity that a high average hit ratio concealed. Measure hit latency, miss latency, bypass traffic and bytes offloaded separately; one aggregate hit ratio can hide a hot route that cannot be shared. Transport Layer Security (TLS) termination, request inspection and edge logs also put the provider inside the data-processing boundary even when no response is cached.

## How It Works

### Define a policy for each response class

| Content | Example policy | Conditions |
| --------------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Versioned public JavaScript/image | `public, max-age=31536000, immutable` | The content stays unchanged for its freshness lifetime; retain old assets while supported clients can reference them |
| Public Hypertext Markup Language (HTML) shell | Revalidate with validators or set a short freshness period | Old tabs, service workers and API clients still need a compatibility policy |
| Public catalog response | Shared freshness plus explicit representation variants | Every output-changing input, such as language or negotiated format, must affect `Vary` or the provider cache key |
| Personalized/sensitive response | `no-store`; explicitly bypass protected routes if CDN rules can override origin headers | Test actual edge rules, custom code, errors and redirects; response headers do not control logs |

These are starting policies, not universal defaults. Under the Hypertext Transfer Protocol (HTTP) caching rules, unqualified `no-cache` permits storage but requires successful validation before reuse; `no-store` tells compliant caches not to store the request or response. A provider rule or edge function can change deployed behavior, so test the path users actually take. Neither a request method nor a cache directive is an authorization system. See [HTTP caching](../../20-backend/20.3-rest-apis/02-http-mechanics/20.3.2.04-http-caching.md) for the canonical directive semantics.

### Follow one public asset across a deployment

1. Release A's HTML references `/assets/app.a1b2.js`; the edge stores eligible bytes under that versioned identity.
2. Release B publishes `/assets/app.c3d4.js` before its HTML references it. The new URL misses along each cold cache path, then can be reused.
3. A user with an old tab can still run A. Keep its referenced assets and supported API behavior for the chosen transition period.
4. If `/assets/app.a1b2.js` is overwritten, the immutable policy is now false. A new filename only helps when the HTML/client actually obtains the new reference.

Versioned URLs avoid replacing an existing asset's bytes; they do not update every open client or reverse a breaking application programming interface (API) rollout. Publish new assets before publishing HTML that references them, and retain old assets for the client overlap and rollback period your product supports.

### Protect and test the origin path

Choose reachable origins, verified TLS on each hop, permitted `Host`/forwarding headers and an access policy. Prevent unapproved direct-origin access where the security design depends on the CDN. A source-IP allowlist may include shared provider infrastructure; authenticated origin requests can establish a narrower boundary when supported. Validate the deployed contract rather than assuming a CDN address alone proves the requesting tenant.

An origin shield is another cache tier: when several edge regions request the same cacheable object, the shield may satisfy later requests from its copy and reduce duplicate origin fetches. Request collapsing is a separate behavior: a cache node may combine simultaneous misses for the same cache key into one in-flight fetch. The exact scope and eligibility depend on the provider; unique keys, uncacheable requests and retries can still reach the origin. Account for shield latency and cost, and test origin load under cold-cache conditions. Cache warm-up is an optimization, not assurance that every PoP retains an object.

### Treat purge as an observed operation

A provider may purge by URL, tag or another supported selector. Follow its exact matching rules, include distinct cache-key variants, check HTTP and API-result errors, handle quotas, and track completion according to that provider's contract. Provider completion does not clear browser caches or bytes already downloaded by clients.

For an emergency correction, balance stale-copy risk against the origin load caused by a purge. The `stale-while-revalidate` extension permits a cache to serve a stale response while it revalidates within a configured window; it does not promise immediate freshness. `stale-if-error` is a separate extension for eligible error cases. Use stale responses only where the product's consistency contract allows them, and test the provider's behavior during origin failures.

## Decisions at the Edge

### Edge code needs a complete request contract

Routing, credential verification or image negotiation can run near users, but checking that an `Authorization` header exists does not verify its credential. Authenticate and authorize each protected request before serving a cache hit; if the edge cannot check current permission, bypass shared caching. A user-specific cache key prevents one caller's representation from being served to another, but it does not detect an expired token, revoked grant or changed entitlement. Any cached authorization grant needs an explicit lifetime and revocation policy. A random response header also does not implement a stable experiment: assignment, variant selection and cache identity must agree.

Choose edge placement from runtime support, data dependency latency, consistency and operation cost. A nearby function that synchronously calls a distant database can retain most of that distance cost. Do not move writes to the edge for proximity alone; the data model still needs an explicit write authority, conflict policy and consistency contract.

### Sensitive data includes transit and telemetry

Protected health information (PHI) can appear in bodies, URLs, headers, logs, analytics and diagnostics. Avoid placing sensitive identifiers in casually retained URLs or logs; an HTTP `POST` body can still be processed or recorded by intermediaries. Opaque identifiers remain personal data when they can be linked back to a person.

For a workflow covered by the Health Insurance Portability and Accountability Act (HIPAA), map the provider's actual service and data flow, then establish applicable safeguards and business-associate obligations. The U.S. Department of Health and Human Services (HHS) says a cloud provider that creates, receives, maintains or transmits electronic PHI on behalf of a covered entity or business associate can be a business associate even when it cannot decrypt the data. HIPAA does not impose a blanket U.S.-only storage or processing rule for ePHI; overseas processing can still change the risks that belong in the required analysis. If another law, contract or organizational policy imposes a residency limit, verify it for processing, storage, logs, support and backups—a regional-looking hostname does not establish it. A `no-store` header is one cache control, not proof of compliance.

### Compare providers with current evidence

Evaluate audience-path measurements, origin security, cache/routing features, runtime limits, purge operations, logging, contract terms and quoted cost. Distinguish request hit ratio from byte offload; include request, transform, security and origin-egress costs. Free tiers, supported services and compliance offerings change, so verify the intended account and service with current documentation and traffic probes rather than a static vendor table.

## Summary

A CDN distributes delivery work under representation, cache, routing and trust policies. Equivalent authorized responses can be reused; misses still expose origin work and copies still need a freshness/recovery contract. Verify cache behavior, origin access and data processing as separate boundaries.

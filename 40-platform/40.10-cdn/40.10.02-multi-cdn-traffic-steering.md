# Multi-CDN Traffic Steering

At 03:00, content delivery network (CDN) A fails for users in one region. The authoritative Domain Name System (DNS) record changes to CDN B, but some clients still use cached answers. B's cache is cold, so its misses surge against the origin both providers share. Multi-CDN helps only when the alternate path can serve the same authorized content and the switch reaches real requests without overwhelming shared dependencies.

## Definition

**Multi-CDN traffic steering** is the policy and mechanism that selects among two or more content delivery providers for a product's requests. The practical architecture includes the signal that detects a change, the control plane that chooses a route, and the delivery path that must honor the same content, access, and freshness contract.

> **Textbook Definition:** Multi-CDN traffic steering selects among delivery providers using availability, performance, cost and policy constraints while coordinating cache, origin, identity and failover behavior across providers.

Real-user monitoring (RUM), synthetic probes, and provider health checks are evidence for the decision; they are not, by themselves, a steering mechanism.

## First Principles

A second provider removes only the failures it does not share. If both CDNs depend on the same authoritative DNS, origin, identity service, or application database, that dependency remains a common failure domain. Changing a control-plane setting is not the same as moving user traffic: DNS answers can remain cached, clients can keep connections open, and players may retry on their own schedule. A steering policy must be evaluated by observed requests, not by a successful configuration update. The alternate path must return the intended representation under the same authorization and freshness rules. Provider-specific cache keys, header forwarding, TLS certificates, web application firewall rules, redirects, or cookie scope can turn a successful switch into wrong content or a broken session.

## 1. Choose Where the Decision Happens

| Mechanism | Decision point | What it can control | Main limit |
| ------------------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Authoritative DNS / global server load balancing (GSLB) | A DNS lookup | Broad routing by health, geography or relative weight | Resolvers cache answers; geography may describe a resolver or network, not the individual user |
| Client or media player | A page, session or next media request | A client can choose a provider-specific URL or retry path | Requires compatible clients and a tested session, hostname, retry and security contract |
| Managed traffic director | The provider's documented control or request path | Health, policy and provider-specific performance selection | Decision granularity, signals, propagation and fallback behavior vary by product |

RUM can help compare similar users across providers, but it is sampled and often misses users whose page never loads far enough to send a beacon. Synthetic probes can test an unselected or failed path; they do not reproduce every user's network. Use both, and confirm what a managed steering product actually measures. For example, Cloudflare documents dynamic steering from regional health-monitor round-trip-time profiles; that is a provider-specific signal, not a universal RUM contract.

## 2. Treat DNS Weights and TTLs as Inputs, Not Guarantees

If a weighted DNS policy assigns records 80 and 20, the ratio describes eligible DNS-answer selection under that provider's policy. It does not promise that exactly 80% of people, requests, or bytes use A: recursive resolvers cache answers, clients reuse connections, and retries change the observed mix. Route 53 documents weights as relative shares; other providers have their own rules.

An authoritative update affects later lookups. Recursive resolvers normally cache an answer for its time-to-live (TTL), and some may serve stale data beyond expiry when they cannot refresh the authoritative answer. A live connection can also continue after a new lookup would select B. Lowering the TTL before a planned migration can reduce one source of delay; it does not create a universal failover deadline. Measure detection, answer changes, and actual request movement separately.

## 3. Prove the Alternate Path Before Relying on It

For each provider, test the production hostname or the exact provider-specific hostname used by clients, with representative requests from multiple regions. Check both a cacheable asset and a route that must reach the origin. A cached `200` can show that one edge copy works while saying nothing about current origin health; an origin probe alone does not prove the full CDN path works. Keep delivery-path and origin checks separate.

Before shifting traffic, compare the contracts that commonly drift: TLS and host routing, cache-key dimensions, response headers, compression and range behavior, web application firewall rules, signed access, cookies, redirects, and direct-origin protections. If sessions are tied to a CDN hostname or cookie, test what happens when the path changes. A geographic steering answer is not proof of data residency; enforce any required processing or storage boundary as an eligibility rule that also applies during failover.

If both CDNs use one origin, that origin is still shared. A cold secondary can add miss traffic precisely when the system is degraded. Keep enough origin capacity for the miss path, test with cold caches, and warm important eligible objects only where the provider supports it. Shielding can reduce repeated eligible fetches; it does not guarantee that every request is coalesced or every location has a warm copy.

Set health thresholds and recovery behavior to match the failure being detected. Use multiple observation regions, require enough consecutive signals to avoid flapping, and test the fallback when all pools appear unhealthy. A provider's health-check state, configured traffic shift, and customer-visible success are three different observations.

## 4. Use Measurements That Answer the Decision

Compare providers on equivalent cohorts: same region and network type, content class, client version, and time window. Record latency percentiles and successful-request rate together; a percentile calculated only from successful page loads can make a failing provider look fast. Include synthetic failures and the provider's request logs to reduce that blind spot.

Keep at least two separate measures of cache efficiency. Request hit ratio counts how many requests avoid the origin; byte offload estimates how many response bytes do. Small-file hits can produce a high request ratio with little egress savings. Compare both with origin load, user outcomes, and the complete bill: request, transfer, transform, security, shield, logging, and traffic-management charges, plus commitments and duplicate operational work.

RUM needs its own data contract. Minimize identifiers, define retention and access, and follow the applicable privacy requirements. `Server-Timing` can expose request metrics to browser code; expose only deliberate, low-cardinality information and use the required cross-origin permissions. Do not assume all browsers, providers, or failed requests produce comparable beacons.

For a planned experiment, define the eligible traffic, success and error guardrails, sample sufficiency, observation window, and rollback condition before changing weights. Keep other release changes stable during the comparison. Do not use a fixed ramp percentage or calendar duration without relating it to traffic volume and failure impact.

## 5. Coordinate Purges as Independent Provider Operations

Each provider has its own cache-key normalization, purge selectors, quotas, and completion contract. A path or tag accepted by A may not identify the same variants on B. Keep a durable per-provider status, retry failed submissions idempotently, and verify completion when the provider exposes it; there is no atomic transaction across separate APIs.

Versioned URLs reduce the need to replace existing asset bytes, but HTML and active clients can still refer to old versions. For corrections, purge the affected identities on every provider and continue serving compatible old assets for the supported client overlap. See [CDN Architecture](40.10.01-cdn-architecture.md) for the single-provider cache and release contract.

## 6. Walk Through a Regional Incident

Suppose RUM shows higher tail latency and errors for A in one region. First compare those observations with synthetic probes and provider health data; verify that B can serve the same content and that the problem is not a shared origin. If B is eligible, shift only the affected traffic at the control point the product supports. Watch B's successful-request rate, tail latency, cache misses, and origin load while the shift propagates. Roll back if the user outcome or shared dependency crosses its guardrail, then reconcile cache and routing state on both providers.

For cost steering, use the same evidence discipline. Compare current contracts and effective regional charges with user outcomes and the cost of operating a second path. A cheaper provider is not a win if it misses the service objective, causes origin overload, or violates a processing restriction.

## Summary

Multi-CDN creates alternate delivery paths, but its value depends on independent failure coverage and a switch that reaches real traffic. Treat RUM and probes as evidence, DNS weights and TTLs as approximate controls, and each provider's cache, authorization, origin, and purge behavior as a separate contract. Test the cold path and shared dependencies before relying on failover, then justify the added cost with comparable user and origin measurements.

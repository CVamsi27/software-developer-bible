# Multi-CDN Traffic Steering

> One CDN means one vendor's outages, price sheet, and peering quality decide your user experience. **Multi-CDN** spreads traffic across providers and steers it dynamically — trading operational complexity for resilience, cost leverage, and regional performance.

## Definition

Multi-CDN architecture serves the same content through two or more CDNs (e.g., Cloudflare + Fastly + CloudFront), with a **steering layer** deciding which provider answers each user request or region:

| Steering mode                      | Decides via                                                                                              | Switch speed                         |
| ---------------                      | -------------                                                                                              | --------------                         |
| **DNS / GSLB**                     | Authoritative DNS answers different CNAMEs/A records per health/geo/policy                               | Bounded by record TTLs (30s-minutes) |
| **RUM-based**                      | Real-user telemetry (beacons) ranks CDNs per region/ISP                                                  | Continuous, statistical              |
| **Edge orchestrator / CDN broker** | Dedicated service (commercial "traffic optimizers", anycast fabrics) rewrites mappings in near-real-time | Seconds                              |

```text
                        ┌────────────────────┐
 users ──► resolver ──► │ steering decision  │ ◄── health probes
           (DNS/GSLB)   │ (policy + RUM data)│ ◄── RUM beacons
                        └─────┬────────┬─────┘
                              │        │
                    70% CNAME ▼        ▼ 30% CNAME
                   ┌─────────┐    ┌─────────┐
                   │ CDN A   │    │ CDN B   │──► origin (+ shields)
                   └─────────┘    └─────────┘
```

## Why Do We Need It?

1. **CDN outages happen to everyone** — major providers have had global incidents lasting hours; single-CDN sites inherit them fully.
2. **No CDN wins everywhere** — last-mile peering differs by ISP and city; provider A may beat B in Berlin while losing in São Paulo.
3. **Cost arbitration** — commit-tier discounts expire mid-quarter; shifting even 15% of egress between vendors is real money at petabyte scale.
4. **Negotiating leverage** — credible multi-CDN posture changes renewal conversations measurably.
5. **Capacity headroom** — flash events (launches, live streams) exceed one vendor's comfortable margin; overflow routing absorbs spikes.
6. **Compliance routing** — some regions must be served from specific PoPs/providers; steering encodes that policy.

## How It Works

### DNS/GSLB Steering

The oldest mechanism: authoritative DNS returns provider CNAMEs based on policy.

```text
Zone apex: www.example.com
  ├── geo policy:      EU → cdn-a.net ; Americas → cdn-b.net
  ├── weighted split:  80% A / 20% B (ramp or arbitrage)
  ├── health failover: A probes fail ≥3x → answer B
  └── TTL trap:        cached answers keep flowing until TTL expiry
```

Characteristics: simple, universal, but coarse (per-resolver, not per-user) and slow to converge because resolvers cache.

### RUM-Based Steering

Real-user monitoring closes the loop with ground truth:

```javascript
// Navigation Timing beacon sent per page load
const nav = performance.getEntriesByType('navigation')[0];
beacon('/rum', {
  cdnHint: nav.serverTiming?.find((t) => t.name === 'cdn')?.description,
  region: geo.country,
  asn: clientAsn,
  ttfb: nav.responseStart - nav.startTime,
  cacheStatus: nav.serverTiming?.find((t) => t.name === 'cache')?.description,
});
```

A steering service aggregates TTFB/error percentiles per `(region, ISP, CDN)` cell and adjusts weights. Synthetic probes complement RUM where traffic is thin.

### Edge Orchestrators

Commercial optimizers (and anycast fabrics like some managed multi-CDN products) ingest RUM + probe data and push mapping updates to DNS or their own edge layer within seconds — effectively automating what GSLB+RUM setups do manually.

### Failover Health Checks and Consistency Hazards

```text
HEALTH CHECK DESIGN
  • probe real URLs (/healthz AND a hot cached asset path)
  • multiple geographies per CDN — regional failure ≠ global
  • distinguish origin-down from CDN-down (origin failures hit BOTH CDNs)

CONSISTENCY HAZARDS AFTER FAILOVER
  • stale DNS: users on long-TTL answers stay on sick CDN for minutes-hours
  • cold cache: failover CDN misses everything → origin stampede without shields
  • config drift: TLS certs/WAF rules differ → failover breaks things that worked
  • sticky sessions: tokens bound to CDN hostnames/cookies invalidate mid-session
```

Mitigations: low TTLs (30-60s) on steerable records, pre-warming scripts that periodically fill the backup CDN for top assets, config-as-code deployed identically to all providers, and connection-drain awareness during weight shifts.

### Cache Invalidation Across CDNs

Each provider has its own purge API, propagation speed, and cache-key normalization:

```typescript
const purgers = [
  cloudflare.purge(zoneId, { files }),          // instant-ish, URL/tag based
  fastly.purgeService(serviceId, { surrogateKeys }),  // key-based, seconds
  cloudfront.createInvalidation(distroId, paths),     // path globs, slower quota
];

// Versioned URLs make cross-CDN purges rare:
// deploy ships app.a1b2c3.js; old hashes simply age out everywhere identically.
```

Hazards: different query-string handling (`?v=1` keyed by one, ignored by another) produces mixed old/new content mid-rollout. Normalize keys via origin headers (`Cache-Key` policies) so all providers agree on identity.

### Cost Arbitration

| Lever                   | Mechanism                                                                          |
| -------                   | -----------                                                                          |
| Commit tiers            | negotiate volume discounts; steer overflow above commit to cheaper second vendor   |
| Egress deltas           | per-GB rates vary 2-4x between providers/regions; shift heavy regions              |
| Origin-shield economics | shield hits reduce origin egress; configure shields on whichever CDN fronts origin |
| Offload ratio           | higher hit ratio = less origin spend; tune each CDN independently                  |

Arbitration logic belongs in the steering policy: `weight = f(perf_score, unit_cost, remaining_commit_burn_down)`.

### Measurement Infrastructure to Prove Which CDN Wins Where

1. **RUM pipeline**: beacons → collector → warehouse; dashboards of p75 TTFB & error rate per `(country, ASN, CDN)` from `server-timing`.
2. **Synthetic fleet**: scheduled probes from vantage points hitting identical URLs on both CDNs (cache-warm and cache-cold runs).
3. **Log unification**: pull CDN raw logs into one schema (`cdn_vendor` column); reconcile against billing GB.
4. **Experiment discipline**: shift weights gradually (5% steps), hold regions constant, watch week-over-week — CDN differences are smaller than day-of-week noise.
5. **Verdict artifacts**: quarterly scorecards naming the winning CDN per region, feeding both steering weights and vendor negotiations.

## Code Examples

### Weighted DNS Steering With Health Failover (Route53-style pseudo-config)

```yaml
# Terraform-flavored sketch of dual-CDN weighted routing
resource "aws_route53_record" "www_multi_cdn" {
  zone_id = aws_route53_zone.main.id
  name    = "www.example.com"
  type    = "CNAME"
  ttl     = 60                       # short TTL: failover convergence vs resolver load

  weighted_routing_policy {
    weight = 800                     # 80% → primary
  }
  set_identifier = "cdn-a"
  alias {                       # CNAME to CDN A edge hostname
    name = "dxxxx.cloudflare.net"
    zone_id = "Z0abcdef"
    evaluate_target_health = true
  }
}

resource "aws_route53_record" "www_multi_cdn_b" {
  # ... same block, weight = 200, set_identifier = "cdn-b",
  #     alias to fastly domain, health_check = aws_route53_health_check.eu
}
```

### RUM Aggregation Job (TypeScript, warehouse-side)

```typescript
interface RumEvent {
  country: string;
  asn: number;
  cdn: 'cloudflare' | 'fastly';
  ttfbMs: number;
  failed: boolean;
}

export function scoreCdns(events: RumEvent[]): Record<string, number> {
  const cells = new Map<string, { p75: number[]; errors: number; n: number }>();

  for (const e of events) {
    const key = `${e.country}:${e.asn}:${e.cdn}`;
    const c = cells.get(key) ?? { p75: [], errors: 0, n: 0 };
    c.p75.push(e.ttfbMs);
    if (e.failed) c.errors += 1;
    c.n += 1;
    cells.set(key, c);
  }

  const scores: Record<string, number> = {};
  for (const [key, { p75, errors, n }] of cells) {
    if (n < 200) continue;                          // statistical floor
    p75.sort((a, b) => a - b);
    const latency = p75[Math.floor(p75.length * 0.75)];
    scores[key] = latency + 500 * (errors / n);      // ms penalty per error rate
  }
  return scores;                                     // lower wins per cell
}
```

### Coordinated Purge Across Providers

```typescript
export async function purgeEverywhere(paths: string[]): Promise<void> {
  const results = await Promise.allSettled([
    cfPurge(paths),
    fastlyPurgeBySurrogateKey(paths.map(pathToSurrogate)),
    cfInvalidate(paths.map(toDistributionPath)),
  ]);

  results.forEach((r, i) => {
    if (r.status === 'rejected') {
      // Partial invalidation is worse than none — alert loudly
      throw new Error(`Provider ${i} purge failed; content divergence risk`);
    }
  });
}

const pathToSurrogate = (p: string) => `key-${p.replace(/[^a-z0-9]/gi, '-')}`;
```

## Real-World Use Cases

### 1. Global News Site Surviving a Provider Outage

Primary CDN fails globally during election-night traffic. GSLB health checks flip weights within one TTL; the backup CDN serves from pre-warmed cache plus shielded origin; postmortem credits multi-CDN with avoiding a front-page blackout.

### 2. Streaming Platform Cost Program

Finance targets 20% egress reduction. Team builds the RUM scoreboard, discovers vendor B is 30% cheaper in LATAM at equal p75, shifts LATAM weighting over a quarter while keeping vendor A in EMEA where it measurably wins.

### 3. Live Event Overflow

Product launches route baseline traffic to the committed vendor; orchestrator pushes overflow beyond commit thresholds to the second CDN, avoiding both overage pricing and capacity cliffs.

### 4. Data-Residency Routing

Policy table pins EU users to the provider with in-region processing guarantees regardless of performance scoring — compliance overrides optimization.

### 5. Vendor Renegotiation

Quarterly scorecards showing per-region win rates convert anecdotes into negotiating evidence; procurement cites measured parity to justify competitive pricing.

## Common Mistakes

### 1. Failover Without Pre-Warmed Secondary Cache

Flipping 100% of traffic to an empty CDN turns a CDN outage into an origin outage. Keep secondary shields warm for top objects; ramp weights instead of hard flips.

### 2. Long TTLs on Steerable Records

A 3600s TTL means up to an hour of users pinned to a dead provider. Steerable hostnames get 30-60s TTLs; put stability in separate static hostnames if needed.

### 3. Divergent Configuration Between CDNs

WAF rules, header rewrites, and compression settings drift until failover serves broken pages. Manage provider configs as code from one source and test both paths in staging.

### 4. Trusting Synthetic Latency Alone

Lab probes miss last-mile realities (CGNAT, mobile radios). RUM data must anchor decisions; synthetic fills coverage gaps only.

### 5. Purging One CDN During Incidents

Rolling an urgent fix through a single provider's API leaves others stale — always use the coordinated purge path with all-or-alert semantics.

### 6. Steering on Averages

Mean TTFB hides tail disasters; a CDN winning on average while tripling p95 error rates is a bad bet. Score percentiles and error budgets, never averages alone.

## Best Practices

1. **Standardize observability headers first** (`Server-Timing: cdn;desc=..., cache`) so every provider reports comparably.
2. **Keep origin behind shields on every CDN** — failover must never mean direct-to-origin stampedes.
3. **Version URLs religiously** (see [CDN Architecture](40.10.01-cdn-architecture.md)) so cross-provider consistency does not depend on purge races.
4. **Automate config deployment to all providers together**, tested as a unit.
5. **Shift traffic in small steps** with automated rollback triggers on error-rate deltas.
6. **Reconcile logs vs bills monthly** — steering bugs show up as invoice surprises before user pain.
7. **Document the runbook**: who flips weights, in what console/API, with what verification checklist.
8. **Treat measurement as the product**: without the RUM/probe/log pipeline you cannot prove anything — including whether multi-CDN was worth it.

## Performance Considerations

| Factor                               | Effect                         | Tuning                                        |
| --------                               | --------                         | --------                                        |
| DNS resolution chain                 | extra hop through steering DNS | keep delegation shallow; anycast steering DNS |
| Cold-cache windows after shifts      | elevated origin load + latency | pre-warm, gradual ramps, shields              |
| RUM sample sparsity in small markets | unstable scores                | widen cells (country-level), longer windows   |
| Double caching layers                | stale-mix risk on deploys      | uniform cache-key policy; versioned assets    |

Multi-CDN adds moving parts; the payoff is optionality — measure that it exceeds the overhead in your traffic profile.

## Summary

- Multi-CDN exists for resilience, regional performance, cost leverage, and compliance — not fashion.
- DNS/GSLB steering is coarse and TTL-bound; RUM-based steering uses real-user truth; edge orchestrators automate the loop in seconds.
- Failover correctness depends on health-check design, warm secondary caches, short TTLs, and identical configs across providers.
- Cross-CDN invalidation is inconsistent by nature; versioned URLs and coordinated purge jobs neutralize most divergence.
- Cost arbitration combines commit burn-down, per-region rates, and offload ratios inside steering policy.
- The decisive investment is measurement infrastructure: RUM + synthetic + unified logs proving which CDN wins where.

## Cheat Sheet

```text
MULTI-CDN STEERING CHEAT SHEET
════════════════════════════════════════════════════

WHY MULTI-CDN:
  • survive provider outages       • per-region performance wins
  • egress cost arbitrage          • vendor leverage / compliance routing

STEERING MODES:
  DNS/GSLB         geo + weighted + health answers; TTL-bound (use 30-60s)
  RUM-based        beacon TTFB/errors per (region, ISP, CDN) drive weights
  edge orchestrator near-real-time optimizer pushing mappings

FAILOVER CHECKLIST:
  • probe real URLs from multiple geos
  • distinguish origin-down vs CDN-down
  • secondary cache pre-warmed (shields!)
  • configs identical across providers (as-code)
  • expect stale-DNS stragglers until TTL expiry

INVALIDATION:
  versioned URLs > purge races
  purge EVERY provider atomically (all-or-alert)
  normalize cache keys (?v= handling differs!)

COST LEVERS:
  commit burn-down vs overflow vendor
  per-region rate deltas
  offload ratio tuning per CDN
  shield placement economics

MEASUREMENT STACK:
  Server-Timing headers → RUM beacons → warehouse
  synthetic probes (warm+cold) per region
  unified CDN logs w/ vendor column; logs vs bill reconciliation
  score percentiles + errors, NEVER averages

INTERVIEW TIPS:
  • Draw DNS-steer diagram with TTL caveat
  • Name cold-cache stampede as THE failover hazard
  • Say "prove it with RUM per (region, ISP)" — senior signal
```

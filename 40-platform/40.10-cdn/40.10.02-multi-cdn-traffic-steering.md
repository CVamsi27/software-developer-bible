# Multi-CDN Traffic Steering

## Definition

Multi-CDN architecture serves the same content through two or more CDNs (e.g., Cloudflare + Fastly + CloudFront), with a **steering layer** assigning a delivery path at its supported granularity (for example a DNS lookup or player request):

> **Textbook Definition:** Multi-CDN traffic steering selects among delivery providers using availability, performance, cost, and routing constraints, while coordinating cache, origin, and failover policies across providers.

| Steering mode | Decides via | Switch speed |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **DNS / GSLB** | Authoritative DNS answers different CNAMEs/A records per health/geo/policy | Health detection, cached answers and connection reuse affect convergence |
| **RUM-based** | Real-user telemetry (beacons) ranks CDNs per region/ISP | Continuous, statistical |
| **Edge orchestrator / CDN broker** | Dedicated service (commercial "traffic optimizers", anycast fabrics) rewrites mappings in near-real-time | Depends on the actual control/data plane |

```text
health probes + real-user measurements → steering policy
DNS response or client decision → CDN A or CDN B → permitted origin path
```


## First Principles

A second provider creates another delivery path, but both can still depend on the same DNS, origin or identity system. Redundancy only reduces failures that the alternate path can survive.

Changing an authoritative DNS answer cannot recall copies already held by resolvers or close live connections. The steering decision and observed request movement are therefore separate events. A client/player can choose again at a different granularity, with its own retry and session rules.

Every alternate path must also return the intended bytes under the same access/freshness contract. Different cache keys, certificates or authorization behavior can turn an availability recovery into a correctness failure. Match the policy and test observable behavior; vendor configuration syntax need not be identical.

## Why Do We Need It?

Consider multiple providers when measurements or required failure coverage justify the added ownership: a regional path performs poorly, an alternate can meet a stated delivery objective, or current contract/cost constraints favor another allocation. Include shared-dependency risk, configuration work, purge coordination and origin capacity in that decision. More providers do not automatically guarantee availability or lower cost.

## How It Works

### DNS/GSLB Steering

The oldest mechanism: authoritative DNS returns provider CNAMEs based on policy.

```text
Steerable subdomain: www.example.com
  ├── geo policy:      EU → cdn-a.net ; Americas → cdn-b.net
  ├── weighted split:  80% A / 20% B (ramp or arbitrage)
  ├── health failover: A probes fail ≥3x → answer B
  └── TTL trap:        cached answers keep flowing until TTL expiry
```

Characteristics: simple, universal, but coarse (per-resolver, not per-user) and slow to converge because resolvers cache.

### RUM-Based Steering

Real-user monitoring (RUM) observes sampled user paths; it is affected by traffic assignment, device/network mix, missing beacons and successful-page bias.

```javascript
// Partial browser measurement sketch: beacon/geo/ASN collection are supplied
const nav = performance.getEntriesByType('navigation')[0];
beacon('/rum', {
  cdnHint: nav.serverTiming?.find((t) => t.name === 'cdn')?.description,
  region: geo.country,
  asn: clientAsn,
  ttfb: nav.responseStart - nav.startTime,
  cacheStatus: nav.serverTiming?.find((t) => t.name === 'cache')?.description,
});
```

A steering service aggregates TTFB/error percentiles per `(region, ISP, CDN)` cell and adjusts weights. Synthetic probes complement RUM where traffic is thin.

### Edge Orchestrators

Commercial optimizers (and anycast fabrics like some managed multi-CDN products) ingest RUM + probe data and push mapping updates to DNS or their own edge layer under the product's measured update/propagation contract — automating what GSLB+RUM setups do manually.

### Failover Health Checks and Consistency Hazards

```text
HEALTH CHECK DESIGN
  • probe real URLs (/healthz AND a hot cached asset path)
  • multiple geographies per CDN — regional failure ≠ global
  • distinguish origin-down from CDN-down (origin failures hit BOTH CDNs)

CONSISTENCY HAZARDS AFTER FAILOVER
  • stale DNS: users on long-TTL answers stay on sick CDN for minutes-hours
  • cold cache: failover CDN misses everything → origin stampede without shields
  • config drift: TLS certs/WAF rules differ → failover breaks things that worked
  • sticky sessions: tokens bound to CDN hostnames/cookies invalidate mid-session
```

Choose TTLs from measured lookup behavior and resolver load. Warm important eligible objects when supported, retain miss-path origin headroom, reconcile policy across providers and test active-connection behavior. A warm cache can evict data; a short TTL does not set a total failover deadline.

### Cache Invalidation Across CDNs

Each provider has its own purge API, propagation speed, and cache-key normalization:

A purge job needs an operation identity, a provider-specific mapping and a status for each target. API acceptance and propagation completion can differ. Retry failed targets and verify the affected representations; there is no atomic transaction across providers.


Hazards: different query-string handling (`?v=1` keyed by one, ignored by another) produces mixed old/new content mid-rollout. Configure each provider's supported cache-key policy and test the same representation matrix; there is no universal `Cache-Key` response header that makes every provider agree.

### Cost Arbitration

| Lever | Mechanism |
| ----------------------- | --------------------------------------------------------------------------------------- |
| Commit tiers | negotiate volume discounts; steer overflow above commit to cheaper second vendor |
| Egress deltas | compare current effective region/contract costs, including commitments and request fees |
| Origin-shield economics | shield hits reduce origin egress; configure shields on whichever CDN fronts origin |
| Offload ratio | higher hit ratio = less origin spend; tune each CDN independently |

Arbitration logic belongs in the steering policy: `weight = f(perf_score, unit_cost, remaining_commit_burn_down)`.

### Measurement Infrastructure to Prove Which CDN Wins Where

1. **RUM pipeline**: beacons → collector → warehouse; dashboards of p75 TTFB & error rate per `(country, ASN, CDN)` from `server-timing`.
2. **Synthetic fleet**: scheduled probes from vantage points hitting identical URLs on both CDNs (cache-warm and cache-cold runs).
3. **Log unification**: pull CDN raw logs into one schema (`cdn_vendor` column); reconcile against billing GB.
4. **Experiment discipline**: shift weights gradually (5% steps), hold regions constant, watch week-over-week — CDN differences are smaller than day-of-week noise.
5. **Verdict artifacts**: quarterly scorecards naming the winning CDN per region, feeding both steering weights and vendor negotiations.

## Code Examples

### Trace weighted DNS selection without a false configuration

For a subdomain, two ordinary weighted CNAME records can conceptually target provider A and provider B:

| Name/type | Identifier | Target | Relative weight |
| ----------------------- | ---------- | --------------------- | --------------- |
| www.example.com / CNAME | cdn-a | configured A hostname | 80 |
| www.example.com / CNAME | cdn-b | configured B hostname | 20 |

This is a policy illustration, not deployable Terraform. Route53 weights are in the supported 0–255 range; weighted selection concerns DNS answers, not exactly eighty percent of users or bytes. A CNAME is not a zone-apex record. Alias targets/health evaluation have separate supported-resource rules and are not interchangeable with arbitrary provider hostnames.

If A becomes unhealthy, the authority may stop selecting A under its configured health policy. A resolver already holding A's answer can keep returning it, and a live connection can continue using it. Measure detection, answer changes and actual request movement separately; also check that B's miss path and access policy work.

### RUM Aggregation Job (TypeScript, warehouse-side)

```typescript
interface RumEvent {
  country: string;
  asn: number;
  cdn: 'cloudflare' | 'fastly';
  ttfbMs: number;
  failed: boolean;
}

export function scoreCdns(events: RumEvent[]): Record<string, number> {
  // Illustrative heuristic: not a confidence interval or automatic steering controller.
  const cells = new Map<string, { p75: number[]; errors: number; n: number }>();

  for (const e of events) {
    const key = `${e.country}:${e.asn}:${e.cdn}`;
    const c = cells.get(key) ?? { p75: [], errors: 0, n: 0 };
    if (!e.failed && Number.isFinite(e.ttfbMs) && e.ttfbMs >= 0) c.p75.push(e.ttfbMs);
    if (e.failed) c.errors += 1;
    c.n += 1;
    cells.set(key, c);
  }

  const scores: Record<string, number> = {};
  for (const [key, { p75, errors, n }] of cells) {
    if (n < 200 || p75.length === 0) continue;       // example evidence floor, not proof of confidence
    p75.sort((a, b) => a - b);
    const latency = p75[Math.ceil(p75.length * 0.75) - 1];
    scores[key] = latency + 500 * (errors / n);      // chosen policy penalty, not a measured retry cost
  }
  return scores;                                     // lower wins per cell
}
```

### Coordinated Purge Across Providers

```typescript
interface PurgeTarget {
  name: string;
  // Adapter resolves only after its documented success check; may mean acceptance.
  submit(paths: readonly string[]): Promise<void>;
}

export async function purgeEverywhere(
  paths: readonly string[], targets: readonly PurgeTarget[],
): Promise<{ provider: string; submitted: boolean }[]> {
  const results = await Promise.allSettled(
    targets.map(target => Promise.resolve().then(() => target.submit(paths))),
  );
  return results.map((result, i) => ({
    provider: targets[i].name,
    submitted: result.status === 'fulfilled',
  }));
}

// Caller persists every result, retries failed targets and verifies completion.
// Provider adapters/key mappings are integration dependencies, not implemented here.
```

## Real-World Use Cases

### An outage plan must survive its own switch

For a hypothetical news launch, provision both delivery paths and test the same asset, authorization, TLS, error and purge cases. During an A failure, measure the authority/client steering change and B's hit/miss/origin load. If both depend on a failed shared origin, B cannot restore fresh uncacheable responses merely by becoming selected.

For cost steering, use current contract costs and comparable audience/content observations. A cheaper measured path may be appropriate; a geographic/legal processing requirement can override the score. Define that requirement over actual processing/storage/logging, not just the requesting user's IP location.

## Common Mistakes

### 1. Failover Without Pre-Warmed Secondary Cache

Flipping 100% of traffic to an empty CDN turns a CDN outage into an origin outage. Warm important eligible objects where useful, retain origin miss-path capacity and choose ramp or emergency switch from the observed failure. A deliberately cold standby can be viable when its miss path is provisioned.

### 2. Long TTLs on Steerable Records

A one-hour cached answer can delay new lookup changes, while active connections/client behavior add their own lifetime. Lower TTL ahead of a planned change if appropriate and verify user-path convergence; there is no universally correct TTL.

### 3. Divergent Configuration Between CDNs

WAF rules, header rewrites, and compression settings drift until failover serves broken pages. Manage provider configs as code from one source and test both paths in staging.

### 4. Trusting Synthetic Latency Alone

Lab probes miss last-mile realities (CGNAT, mobile radios). Use complementary observations: synthetic probes can test failed/unselected paths, while RUM reveals sampled user behavior. Account for both measurement biases.

### 5. Purging One CDN During Incidents

Rolling an urgent fix through a single provider's API leaves others stale — use a coordinated purge path for affected providers with durable per-provider status and recovery.

### 6. Steering on Averages

Mean TTFB hides tail disasters; a CDN winning on average while tripling errors or worsening p95 latency is a bad bet. Score percentiles and error budgets, never averages alone.

## Best Practices

1. **Standardize observability headers first** (`Server-Timing: cdn;desc=..., cache`) so every provider reports comparably.
2. **Keep origin behind shields on every CDN** — failover must never mean direct-to-origin stampedes.
3. **Version URLs religiously** (see [CDN Architecture](40.10.01-cdn-architecture.md)) so cross-provider consistency does not depend on purge races.
4. **Automate equivalent policy deployment across providers**, tested as a unit.
5. **Shift traffic in small steps** with automated rollback triggers on error-rate deltas.
6. **Reconcile logs vs bills monthly** — steering bugs show up as invoice surprises before user pain.
7. **Document the runbook**: who flips weights, in what console/API, with what verification checklist.
8. **Treat measurement as the product**: without the RUM/probe/log pipeline you cannot prove anything — including whether multi-CDN was worth it.

## Performance Considerations

| Factor | Effect | Tuning |
| ------------------------------------ | ------------------------------ | --------------------------------------------- |
| DNS resolution chain | extra hop through steering DNS | keep delegation shallow; anycast steering DNS |
| Cold-cache windows after shifts | elevated origin load + latency | pre-warm, gradual ramps, shields |
| RUM sample sparsity in small markets | unstable scores | widen cells (country-level), longer windows |
| Double caching layers | stale-mix risk on deploys | uniform cache-key policy; versioned assets |

Multi-CDN adds moving parts; the payoff is optionality — measure that it exceeds the overhead in your traffic profile.

## Summary

Multi-CDN supplies alternate delivery paths under a shared representation/access contract. Steering changes do not instantly move cached or connected clients. Measure both providers' successful and failure paths, retain origin miss capacity, coordinate partial purge outcomes and justify the overhead with current performance, cost and required failure coverage.

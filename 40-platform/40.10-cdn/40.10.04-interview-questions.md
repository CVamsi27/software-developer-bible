# CDN & Edge Interview Questions


## Definition

This set covers the edge layer as production actually uses it: what the cache key contains, when invalidation is safe, how shielding protects origin, and what changes when the payload is media instead of JSON. Each question includes the answer shape and the probe that separates memorized answers from operated systems.

## First Principles

This set probes cache economics (→ 40.10.01): keys, TTLs, hit ratio, and steering.:

1. **The senior tells are trade-off statements**: "X when Y, Z when not-Y" — juniors memorize answers; seniors recite the *conditions* under which each answer is right.
2. **Every question here maps to an axiom chain, not a fact** — if you can derive the answer from the linked chapters, you can answer the variant questions too (that's the point of → First Principles sections).

### Q1. What goes into a CDN cache key, and what is the cost of getting it wrong?

**Model answer:** "Minimum: host + path + query allowlist. The decisions are in what you *add*: `Accept-Encoding` (always — else you serve brotli to agents that cannot read it), selected device or image-format headers for transform pipelines, and cookies — never. Adding cookies to the key fragments the cache per user and destroys the hit ratio; excluding cookies while caching personalized responses leaks one user's data to another. The senior framing: the cache key is a security boundary — everything that changes the response must be in the key, everything that would fragment it must not reach the key, and that tradeoff is decided per path."

**Probe:** "A page depends on a logged-in flag only — do you put the session cookie in the key?" → "No. Cache the anonymous variant publicly and gate the personalized shell client-side or via a separate `Cache-Control: private` path — one bit of state does not justify per-user keys."

### Q2. You deployed a JS bundle with a breaking API change. Old HTML references old bundles. What purges, what waits?

**Model answer:** "Nothing needs to purge if the pipeline is right: content-hashed filenames (`app.a1b2c3.js`) mean every deploy is a *new URL* — old entries age out on their own TTL while new HTML references new URLs. The only correctness-critical TTL is on the HTML itself: short (seconds) or no-cache with ETag revalidation. The failing pattern is stable filenames (`app.js`) with long TTLs — then you are purging a whole distribution on every deploy, which is slow and eventually consistent in the worst way. Versioned URLs convert invalidation from an operational event into a non-event."

**Probe:** "When *is* an immediate purge the right tool?" → "Correction of published wrong content — legal, pricing errors — where you must remove stale copies everywhere now, and you accept the origin spike."

### Q3. What does an origin shield buy, and what does it cost?

**Model answer:** "Without shielding, a cache miss at any of 200 POPs means 200 requests to origin — the 'miss amplification' problem. A shield designates one mid-tier location: POPs miss to the shield, the shield misses to origin once, so origin sees one concurrent fetch per object instead of N. Cost: one extra hop of latency on shield misses (usually milliseconds versus origin round-trips — a win), a hot spot that needs its own capacity planning, and a second layer whose headers (`Via`, shield `X-Cache` states) you must read correctly when debugging. For the same reason, request coalescing at the shield collapses concurrent misses for the same object into one origin fetch — the CDN analog of a single-flight lock."

### Q4. Which parts of a 'dynamic' app can actually ride the CDN, and how?

**Model answer:** "More than people expect. Static shells and versioned assets obviously. Beyond that: semi-personalized pages where the shared body is edge-cached and the personalized fragments load client-side or via edge-includes; API GETs that are cacheable by design (public catalog endpoints with allowlisted query params and short TTLs); and full HTML where personalization is cookie-gated into `private` responses. The discipline that makes it safe: per-path cache policy as code — reviewed like the routing table — because one `Cache-Control` typo on a personalized path is a data-leak incident, not a performance bug."

### Q5. Design delivery for video at 4K to a global audience with DRM.

**Model answer:** "ABR ladder: content transcoded into resolution/bitrate renditions, packaged as HLS and DASH so players adapt per bandwidth — the ladder is generated once per title, cached forever by content hash. Storage in object storage, origin shield in front, POPs at the edge. Access control via short-lived signed URLs or token cookies (the CDN validates the token at the edge; origin never serves unsigned requests) — and DRM license servers are separate endpoints because licenses are small, personal, and uncacheable. The edge question that matters for cost: byte-range caching for seek-heavy playback, because a full-object cache miss on a 4 GB asset is a origin-transit disaster."

**Probe:** "Where does latency actually come from in playback start?" → "Manifest fetch + first segment; both must be edge-cached. Pre-warming popular manifests matters more than any codec choice."

### Q6. Multi-CDN: when is it worth it and how do you steer?

**Model answer:** "Worth it when one provider's footprint measurably misses your audience, when you need pricing leverage, or when availability SLOs exceed a single provider's history. Steering options in order of sophistication: DNS-level (coarse, cache-timing-lagged), per-request via a steering service using real-user measurements (RUM) feeding health/score data, and client-side failover for assets via loader logic. The operational cost is real: doubled purge surface, per-CDN cache-key behavior differences, and analytics you must normalize. I would not run multi-CDN for a product whose traffic fits one provider at acceptable SLOs — the complexity needs a reason."

### Q7. A marketing campaign doubles traffic in one region and origin CPU spikes. Walk me through the diagnosis.

**Model answer:** "First question: what is the *hit ratio on the campaign paths*? A spike that lands on uncached paths (new URLs with query strings — tracking params fragmenting keys) bypasses the CDN entirely; that is a cache-key problem, not a capacity problem. Fix: normalize/allowlist query params in the key, pre-warm the campaign's known assets, raise the HTML TTL for the campaign pages since they are effectively static. Only after key hygiene do I look at origin autoscaling — because if the CDN is configured right, origin should see a rounding error of the traffic."

### Q8. When do you serve stale content on purpose, and how do you configure it?

**Model answer:** "Three directives, three different jobs. `stale-while-revalidate` is a latency optimization: serve the cached copy immediately and refresh in the background — the user gets instant responses while the origin load stays smooth instead of spiky. `stale-if-error` is an availability control: origin 5xx or timeout → serve the stale copy rather than an error page, which converts origin outages into content that is minutes staler than usual. And plain long TTL with revalidation is the correctness wrapper: `must-revalidate` for anything where stale serving would be wrong. The senior framing: staleness is a *policy* you set per path with eyes open — a pricing page and a blog post should not share one. The failure mode to name: `stale-while-revalidate` on personalized content is a data-leak vector, because 'stale' was computed for whoever requested it first."

### Q9. You need to purge 10,000 URLs across a site without flushing the whole cache. What is the mechanism?

**Model answer:** "Surrogate keys (Fastly's term; tag-based purge elsewhere): the origin sends a `Surrogate-Key` header listing logical tags — `product-42 category-shoes homepage` — the CDN indexes every cached object by its tags, and a purge API invalidates everything tagged `product-42` in one call. That converts invalidation from a URL-listing problem into a data-modeling problem: tags should match your domain's invalidation units (entity id, section, dependency), not URL patterns. The design discipline: tag taxonomy is reviewed like schema — a tag that mixes 'everything on the homepage' with 'one product' turns a surgical purge into a site flush. This is also the answer to 'purge is slow and eventually consistent': with surrogate keys plus versioned URLs for assets, the residual need for full-zone purges should be approximately never."

### Q10. Cache-Control has a dozen directives. Which actually matter in production, and who respects what?

**Model answer:** "Split by audience. For the CDN: `s-maxage` (shared-cache TTL), `max-age` (everyone), `private` (shared caches must not store — the security directive), and `Vary` (key extension; the footgun is `Vary: *` which disables caching entirely). For the browser: `max-age`, `no-cache` (store but revalidate — misnamed, it is *not* no-store), `no-store` (the real don't-save), and `immutable` on versioned assets, which eliminates revalidation requests entirely. The classic production bug: setting only `max-age` and assuming the CDN respects browser semantics — most CDNs default to honoring `s-maxage` over `max-age`, but some strip directives; the fix is testing per path, not reading docs once. And the senior habit: a one-page cache-policy matrix (path → directives → who caches how long) that ships with the service, because tribal knowledge of six directives across thirty routes is how personalization leaks happen."

### Q11. What belongs on edge compute versus in a cache, versus left at origin?

**Model answer:** "The decision axis is: does the logic need *consistency* with state, or only *proximity*? Cache: static and semi-static responses — the CDN's core competence, zero code. Edge compute: logic that benefits from being near users but touches no source-of-truth writes — request transformation, A/B bucketing, auth-token validation, personalization assembled from cached fragments, bot scoring. Those run on cached data or cheap lookups and tolerate edge replicas. Origin: anything transactional — writes, inventory decrements, anything where two edge nodes racing would corrupt state. The cost dimension is real: edge compute is more expensive per request than cache and has colder ecosystems — moving logic to the edge to save 30ms on a path that then calls the origin twice is negative arbitrage. My rule: the edge is for decisions that must be made *per request near the user*; everything else is a TTL question."

### Q12. Design signed-URL access control for premium media.

**Model answer:** "Components: a token containing the resource path, expiry, and scope — HMAC-signed with a key the CDN can validate at the edge (so unsigned requests never transit to origin), or a cookie for multi-file sessions. Expiry tuned to playback length plus clock skew — minutes for a download, longer for a streaming session, with renewal via an authenticated endpoint. Replay protection: expiry is the main control; for higher assurance, bind the token to session or IP (knowing IP binding breaks on mobile networks — a support-cost trade you make deliberately). Key rotation designed in: versioned keys so rotation doesn't invalidate every live URL, because a key-rotation incident during a launch is a classic. The senior tell: origin *never* trusts its own judgment — it serves only edge-validated requests, because the edge is the policy enforcement point and split-brain access control is how premium content leaks."

### Q13. A product launch makes one asset go viral; origin is melting. What happened and what do you do now?

**Model answer:** "Diagnosis: a cache-miss stampede — the asset's first requests all miss (key mismatch from a query param, a purge that ran mid-launch, or simply cold cache), so thousands of concurrent origin fetches for the same object, and origin capacity sized for the *hit* profile dies on the miss profile. Immediate: request coalescing should collapse concurrent misses for one object into a single origin fetch — verify it is on and that the key actually normalizes; if origin is dying anyway, serve-stale or a maintenance fallback buys time. Prepared: pre-warm known launch assets (push them into POPs before traffic arrives — every CDN has a prefetch API), and capacity-test the origin path for the miss case, not just the hit case. The postmortem framing: launch playbooks include cache hygiene — normalize keys, pre-warm, and confirm coalescing — because 'it worked in the load test' tested the wrong path."

### Q14. How do CDN choices intersect with data residency and geo-compliance?

**Model answer:** "Three layers of the problem. *Storage*: some regimes (GDPR-adjacent interpretations, sectoral rules, China) require user data to be stored in-region — that constrains origin architecture more than the CDN, but edge-compute logs and analytics are data too, and they land wherever the POP is. *Caching policy*: per-geo cache rules — EU users' personalized responses cached only in EU POPs — are a per-path policy configuration on serious CDNs, and getting it wrong is a compliance finding, not a perf bug. *Steering*: geo-DNS and latency steering must respect the residency envelope — you cannot 'fail over' EU traffic to a US POP for a regulated path even during an outage; the SLO policy and the compliance policy can conflict, and that conflict needs a pre-made decision, not an incident-room improvisation. The senior habit: treat residency as a cache-key dimension — if a response is residency-bound, that fact belongs in the cache policy document, next to `private`."

### Q15. How do you prove the CDN is worth what it costs?

**Model answer:** "Three measurements, because each answers a different question. Offload ratio: percentage of requests (and better, bytes) served from cache — the capacity story, since every offloaded request is origin cost and failure surface you don't pay. Latency improvement: TTFB and LCP with CDN versus direct — measured via RUM segmented by region, because synthetic tests from three cities are marketing numbers; the honest version shows per-POP variance and the regions where the CDN *doesn't* help (your audience concentrated where its footprint is thin). Resilience contribution: incidents where stale-serving or shielding absorbed what would have been an origin outage — invisible in dashboards, visible in postmortems. The cost side: egress plus request fees plus transform costs versus origin scaling avoided. The senior artifact is the before/after segmented by region and content type — 'the CDN improved p75 LCP 40% in APAC and 8% in the US' funds the next decision; 'it made things faster' funds nothing."

### Q16. What does a CDN do with WebSockets and server-sent events, and where are the pitfalls?

**Model answer:** "Modern CDNs proxy WebSockets at the edge, but the contract differs from HTTP caching: no cache semantics, so you are paying for a long-lived reverse proxy — the pitfalls are timeout management (idle connections reaped on both edge and origin side; application-level keepalives are mandatory, not optional), buffering (a proxy that buffers SSE turns streaming into chunked bursts — confirm `X-Accel-Buffering`-style disable headers or CDN-specific passthrough settings), and connection limits per plan tier that surface as random disconnects at scale. SSE is simpler — plain HTTP — but the same buffering and timeout rules apply, plus HTTP/2 multiplexing limits on some intermediaries. The design consequence: fan-out messaging that actually needs presence, channels, and delivery guarantees belongs in a real system (Redis pub/sub at origin or a dedicated service); the edge proxy is transport, not a messaging platform. Knowing that boundary is the answer — 'we ran our notification system on CDN-proxied sockets and spent a quarter learning why it dropped connections' is the cautionary tale interviewers have heard."

### Q17. Where does image optimization belong — build time, origin, or edge?

**Model answer:** "A decision table by content volatility. Build-time: known assets in a repo — variants generated in CI, content-hashed, cached forever; zero runtime cost, the default for app shells. Origin/on-demand: user-uploaded media — generate variants on ingest (store the ladder of sizes), serve from storage through the CDN; generating per-request at origin couples your compute to traffic spikes. Edge transforms: the CDN resizes/reformats on the fly keyed by transform parameters — powerful for the long tail of sizes, and the cost is cache-key discipline: every distinct `(format, width, quality)` tuple is a distinct cache entry, so an unconstrained `?w=` parameter is an origin-cost bomb via cache fragmentation. The senior constraint: cap the transform matrix — an allowlist of widths, format negotiation via `Accept`, and transform results cached as long as the source. The edge is for the tail, not the head."

### Q18. What does rate limiting at the edge buy that origin rate limiting doesn't?

**Model answer:** "Placement economics: a request dropped at the edge costs the CDN's margin; a request that transits to origin costs origin compute, database load, and fan-out amplification — so abuse filtering belongs at the edge where the cost asymmetry is maximal. The edge sees *global* per-client behavior across POPs (via shared counters or the CDN's bot-management tier), which origin-local rate limiting cannot — a attacker rotating across edge IPs looks like normal traffic to any single origin node. The design discipline is in the policy: limit by identity (API key, token) not just IP (NAT breaks IP limits for legitimate users — one university behind a NAT is your false-positive generator); return `429` with `Retry-After` so well-behaved clients back off; and stage rules in monitor-mode first, because the cost of a false positive on a checkout endpoint is measured in revenue, not requests. Bot scoring complements, not replaces, explicit limits — opaque ML verdicts without a rules layer you control are a vendor-incident waiting to happen."

### Q19. Explain cache poisoning at the CDN layer and the key-hygiene defenses.

**Model answer:** "Cache poisoning is getting the CDN to store a response computed from attacker-controlled input, then serving it to everyone — the cache turns one crafted request into persistent distribution. The classic vectors: unkeyed headers influencing the response (`X-Forwarded-Host` used to build absolute URLs but not part of the key — attacker poisons the stored page's links), and normalization mismatches where the CDN's path normalization differs from origin's (path confusion, semicolon params, encoding). Defenses are key hygiene as a security discipline: every input that influences the response is either in the key or stripped before it reaches logic; normalize consistently (one owner of path parsing); `Vary` for genuinely content-negotiated dimensions; and framework-level — never build URLs from unkeyed headers without validation. The audit habit: pen-test the *cache*, not just the app — request the same URL with attacker-varying unkeyed headers and diff the stored response. 'We discovered our cache could be poisoned from a header nobody knew affected output' is a real postmortem genre, and the fix is always key policy, not heroics."

### Q20. How do you cache an API — and what changes for GraphQL?

**Model answer:** "REST caching works when the API is shaped for it: GET resources, allowlisted query params in the key, `s-maxage` per resource family, ETags for revalidation — the API contract and the cache policy are designed together, which is why 'cache the API' is a design phase decision, not an ops afterthought. GraphQL breaks the model: the endpoint is one URL with a POST body, so the URL key carries zero query information, and responses differ per field selection. The workable patterns: Automatic Persisted Queries (the query hash becomes a GET parameter — hot queries become cacheable GETs), edge caching per normalized object with a gateway that reassembles (the Apollo/GraphOS model — expensive and worth it only at real scale), and the honest fallback: don't cache GraphQL at the CDN; cache the *expensive resolved subtrees* in the origin layers where you control keys. The senior tell: proposing to cache GraphQL responses by URL — that answer has leaked someone's data in production somewhere, because the cache key cannot express 'who is asking.'"

### Q21. Your origin is multi-region. How does that interact with the CDN tier?

**Model answer:** "The CDN decouples user proximity from origin geography — POPs are everywhere, origins are few — so the questions are about the origin-facing side: which origin does each POP fetch from (latency-based origin selection so a Frankfurt POP misses to the EU origin, not Virginia), how shield layers map to origin regions (shield-in-region, so misses stay within the residency and latency envelope), and failover — an unhealthy origin region routed around at the CDN steering layer, which is often faster than DNS-level failover and doesn't wait on TTLs. The consistency dimension is the trap: an object cached in two regions from two origins with different replication lag means users in different geos see different content versions — acceptable for most content, unacceptable for the paths where you set short TTLs precisely because consistency matters. The senior framing: origin topology is part of the cache-correctness design — write-region, replication lag, and TTL policy are one conversation, not three teams' defaults."

### Q22. Edge logs: what do you keep, what do you sample, and what does it cost?

**Model answer:** "Edge log volume is the stealth cost center — every request logged with 30 fields at full retention costs more than the compute it documents. The policy: classify logs by decision value. Security and audit logs (WAF verdicts, auth failures) — full retention, they are the incident record. Steering and performance telemetry — sampled hard (1% is usually plenty for aggregate decisions; RUM data from real users often makes edge logs redundant for latency analysis). Debug-level — time-boxed: enabled for an investigation, auto-expiring after the window, because permanent debug logging is the bill that grows 40% quarterly unnoticed. Drain cost matters too: log-push to object storage with a separate analytics pipeline usually beats streaming everything into a SIEM-grade tool at edge volume. And the senior discipline: per-property log budgets reviewed like SLOs — a log policy nobody owns is a cost center nobody limits."

### Q23. Model the cost of a CDN commitment. When does the bill exceed the value?

**Model answer:** "The bill has four components: egress per GB (tiered, cheaper at volume — model your real distribution, not averages), request fees (HTTPS requests priced separately — high request-to-byte ratios like API traffic and small-file sites cost far more than the GB number suggests), add-on services (WAF, bot management, image optimization — each priced per-request or per-policy), and commitment structure (committed-use discounts versus pay-as-you-go's 2-5x premium). The value side: origin scaling avoided (compute plus the database load that traffic would have caused), and the resilience value that never shows in a pricing table. The crossover to watch: *small objects and API traffic* — where request fees dominate and origin is cheap — and *uncacheable traffic* you are still routing through the CDN: paying CDN margins for dynamic requests that bypass cache entirely is often just reverse-proxy rent, and sometimes the right answer is routing those paths direct. The senior artifact: cost per effective-offloaded-GB, trended — it catches both the traffic-mix drift and the vendor price change that a raw bill graph hides."

### Q24. You are migrating CDNs. What is the runbook?

**Model answer:** "The risk inventory first: cache-key behavior differences (header and query handling vary by vendor — the same policy produces different hit ratios), purge API differences, TLS and header quirks, and the analytics gap during dual-run. The runbook: dual-run with both CDNs provisioned and warmed — pre-populate the new CDN's cache via its prefetch API before any traffic moves, because a cold-cache cutover on launch day is a self-inflicted origin stampede. Cutover in stages: low-risk subdomain first, then percentage-based steering if the platform supports it, then the main domain — each stage with a defined rollback (DNS TTL pre-lowered, because you cannot roll back fast through a 24-hour TTL). Parity tests: purge latency, failover behavior, and the header set origin receives — the integration tests that would have caught the key-semantics difference. And the success metric defined before cutover: hit ratio, error rate, p95 TTFB per region on the *new* CDN meeting the old one's numbers, or you are not done."

### Q25. Tell me about a CDN incident you led. What made it hard?

**Model answer:** "The shape to score with: a cache-related incident is *silent* before it is loud — content that is wrong rather than content that is down, so detection lag is the first hard part (the config change that silently raised an HTML TTL showed up as users reporting stale prices hours later, not as an alert). Structure the story as: detection gap and what closed it (a synthetic check that diffs rendered content against expected — content-correctness monitoring, not just availability), mitigation and its blast radius (emergency purge plus the origin spike the purge itself caused — purging a hot cache is its own mini-incident), root cause in the system not the person (TTL policy lived in one person's head; per-path policy existed but wasn't reviewed as code), and the class fix — cache policy as reviewed configuration, a content-freshness synthetic, and TTL ceilings enforced by the deploy pipeline. The interviewer is listening for whether you understand that edge incidents have a different physics than origin incidents: broader blast radius, silent onset, and purge-as-mitigation being a double-edged tool."

## Common Mistakes

- Answering "the CDN caches static files" — that is the 2010 model; the question is about cache keys and invalidation semantics.
- Forgetting that the cache key is a security boundary (cookie fragmentation vs personalization leaks).
- Proposing multi-CDN without naming its operational cost.

## Best Practices

- Per-path cache policy as code, reviewed — never per-request pragmatism.
- Versioned URLs as the default invalidation story; purges for corrections only.

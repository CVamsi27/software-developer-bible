# CDN & Edge Interview Questions


## Definition

This set covers the edge layer as production actually uses it: what the cache key contains, when invalidation is safe, how shielding protects origin, and what changes when the payload is media instead of JSON. Each question includes the answer shape and the probe that separates memorized answers from operated systems.

## First Principles

This set probes cache economics (→ 40.10.01): keys, TTLs, hit ratio, and steering.

1. **The senior tells are trade-off statements**: "X when Y, Z when not-Y" — juniors memorize answers; seniors recite the *conditions* under which each answer is right.
2. **Every question here maps to an axiom chain, not a fact** — if you can derive the answer from the linked chapters, you can answer the variant questions too (that's the point of → First Principles sections).

### Q1. What goes into a CDN cache key, and what is the cost of getting it wrong?

**Model answer:** Include representation-changing inputs or remove/reject their influence: target identity, allowed query values and resolved negotiated variants. Cookie-dependent responses may bypass shared caching or use a deliberately authorized finite variant model; neither always-key-cookies nor never-key-cookies is universal. Test hit-path authorization, key normalization and downstream Vary behavior.

**Probe:** "A page depends on a logged-in flag only — do you put the session cookie in the key?" → "No. Cache the anonymous variant publicly and keep access-protected data behind server-enforced authorization and choose a separate personalized shell or via a separate `Cache-Control: private` path — one bit of state does not justify per-user keys."

### Q2. You deployed a JS bundle with a breaking API change. Old HTML references old bundles. What purges, what waits?

**Model answer:** Publish new content-hashed assets before referencing them and retain old assets while clients can use them. New HTML does not update every open tab/service worker or make a breaking API compatible. Revalidation/purge can update eligible stored responses, but plan old-client support and rollback. Purge cannot recall downloaded browser bytes.

**Probe:** "When *is* an immediate purge the right tool?" → "Correction of published wrong content — legal, pricing errors — where stale copies need urgent correction under the verified purge/recovery contract, and you accept the origin spike."

### Q3. What does an origin shield buy, and what does it cost?

**Model answer:** A shield can reuse eligible objects and coalesce concurrent same-key misses before origin. It needs its own capacity, retry/error policy and key agreement. It does not reduce every set of N edge misses to exactly one fetch, or make uncacheable/unique traffic cheap; measure the miss path and extra hop.

### Q4. Which parts of a 'dynamic' app can actually ride the CDN, and how?

**Model answer:** Public shells/assets and deliberately equivalent public GET representations can be shared. Private personalized responses need separate policy and access enforcement, including fragments. Provider rules/custom code can override defaults, so test success/error/hit/miss paths instead of treating an origin header as the complete policy.

### Q5. Design delivery for video at 4K to a global audience with DRM.

**Model answer:** Create supported ABR renditions, HLS/DASH packaging and eligible segment caching, with compatible codec/encryption/player behavior. Live manifests differ from versioned on-demand segments. Verify signed access before hits and secure origin access; licenses/entitlements/DRM are separate. Measure manifest, license, initialization and segment startup dependencies rather than promising one codec-independent bottleneck.

**Probe:** "Where does latency actually come from in playback start?" → "Trace manifest, license/entitlement, initialization and first segments on the actual player path. Eligible caching/warm-up can help; live/personalized manifests and codec/decode cost have separate conditions."

### Q6. Multi-CDN: when is it worth it and how do you steer?

**Model answer:** Use another provider only when measured user outcomes, required failure coverage or contract constraints justify the coordination cost. DNS weights affect eligible answers, not exact user or byte shares; client/player and managed steering have different control points. Treat RUM and probes as separate evidence, then test cold-cache load, shared dependencies, access/key parity and partial purge recovery. More providers do not automatically meet an availability target.

### Q7. A marketing campaign doubles traffic in one region and origin CPU spikes. Walk me through the diagnosis.

**Model answer:** Split the campaign paths by hit/miss/bypass, request and byte offload, query variants, stale/error behavior and origin work. Normalize only inputs that do not affect output. Cache eligible public responses under an acceptable freshness policy; personalized or unique traffic may still need capacity/admission changes. A configured CDN does not guarantee negligible origin traffic.

### Q8. When do you serve stale content on purpose, and how do you configure it?

**Model answer:** Choose allowed stale windows per representation and path. stale-while-revalidate can return old eligible data while refreshing; stale-if-error can allow an old response during supported failures. must-revalidate constrains stale reuse. None supplies identity isolation or a universal freshness/availability promise; test deployed extension/rule interactions.

### Q9. You need to purge 10,000 URLs across a site without flushing the whole cache. What is the mechanism?

**Model answer:** Use supported tags/surrogate keys aligned with actual content dependencies, or mapped URL/variant invalidations under quotas. Track API acceptance, completion and failed targets. Versioned assets reduce replacement needs but do not make every correction immediate or eliminate a purge runbook.

### Q10. Cache-Control has a dozen directives. Which actually matter in production, and who respects what?

**Model answer:** Distinguish storage from reuse: no-store disallows compliant storage; no-cache requires validation before ordinary reuse; private restricts shared storage; s-maxage targets shared freshness; max-age defines freshness; immutable avoids unnecessary fresh-response revalidation. Vary names request variants; Vary:* prevents ordinary reuse rather than literally every storage. Verify provider overrides and every response class.

### Q11. What belongs on edge compute versus in a cache, versus left at origin?

**Model answer:** Choose placement from data dependencies, runtime limits, latency, consistency, authorization and cost. Edge code can make local decisions or call durable services under explicit authority; transactional writes are not categorically forbidden at the edge. Proximity does not supply a shared invariant, and extra remote calls can erase the latency benefit.

### Q12. Design signed-URL access control for premium media.

**Model answer:** Issue a signed canonical resource/scope/expiry only after entitlement checks; verify before every protected cache hit and miss. Expiry limits bearer replay time but does not prevent sharing. Bind additional grant-changing fields, protect/rotate keys and URLs, and secure direct-origin access. Internal content keys can omit grants only when enforcement still happens for each caller.

### Q13. A product launch makes one asset go viral; origin is melting. What happened and what do you do now?

**Model answer:** Check cache identity, eligible misses, purge events, coalescing and origin capacity. Serve stale/fallback only under the content contract; reduce overload while fixing the cause. Warm important objects through supported requests/APIs but do not assume every provider has universal prefetch or every PoP retains the result. Test miss load before a launch.

### Q14. How do CDN choices intersect with data residency and geo-compliance?

**Model answer:** Start from the specific processing/storage/logging and access requirements, including provider contracts. A user's location, geo-DNS answer or cache-key field does not guarantee where data is processed. Verify supported restrictions and pre-decide permitted failover. Do not infer an EU-only rule from GDPR as a universal statement.

### Q15. How do you prove the CDN is worth what it costs?

**Model answer:** Compare request and byte offload, latency/user outcomes by content/audience, and required failure behavior with actual egress/request/transform/security/logging/origin costs. Use comparable experimental traffic and account for RUM/synthetic bias. Report observed numbers and limitations; an example percentage is not deployment evidence.

### Q16. What does a CDN do with WebSockets and server-sent events, and where are the pitfalls?

**Model answer:** Verify the provider's actual WebSocket/SSE protocol, buffering, idle timeout, connection and reconnect contract. Heartbeats may keep allowed idle paths alive but must fit policy. Edge transport does not itself supply presence, replay or delivery semantics; choose a suitable messaging service for those guarantees.

### Q17. Where does image optimization belong — build time, origin, or edge?

**Model answer:** Pre-generate known assets, transform on ingest for predictable variants, or use bounded on-demand generation for a measured long tail. Normalize inputs before both rendering and key construction; include source revision, transform-policy version and negotiated format. Reject failed output, constrain dimensions/quality and measure cache reuse, decode, visual quality and user latency. No placement is universally best.

### Q18. What does rate limiting at the edge buy that origin rate limiting doesn't?

**Model answer:** Early admission can save downstream resources, but edge limits may be local, approximate or coordinated depending on the service. Verify shared-counter semantics and failure policy. Choose trusted identities/budgets, test NAT and false positives, and return the defined rejection/backoff contract. Origin resource admission can still be necessary.

### Q19. Explain cache poisoning at the CDN layer and the key-hygiene defenses.

**Model answer:** An attacker-influenced response reused for other callers is a cache-poisoning risk. Verify keyed variants, validated forwarding inputs and consistent parsing/normalization; reject or remove unrepresented influence. Test stored responses after hostile variants in an isolated authorized environment, including hit-path access and provider overrides.

### Q20. How do you cache an API — and what changes for GraphQL?

**Model answer:** Cache only equivalent authorized responses under a complete key and freshness policy. A GraphQL POST body is not represented by a URL-only key. Persisted-query GETs still need variables/identity/scope treatment; operation caches and origin subtree caches have separate boundaries. REST GET alone is no proof of public reuse.

### Q21. Your origin is multi-region. How does that interact with the CDN tier?

**Model answer:** Specify each origin's write/read authority, version/lag contract, selected fetch path, shield and permitted failover. A recent TTL can wrap already-lagging origin data; short freshness does not give linearizable reads. CDN-level routing can avoid some DNS changes but has its own detection/propagation and active-connection behavior.

### Q22. Edge logs: what do you keep, what do you sample, and what does it cost?

**Model answer:** Classify telemetry by incident value, sensitive content, required retention and cost. Measure volume/drop/sampling behavior and protect access. One-percent sampling is not universally sufficient, and security/audit categories do not imply indefinite full retention. RUM can miss failed loads and does not replace every edge observation.

### Q23. Model the cost of a CDN commitment. When does the bill exceed the value?

**Model answer:** Model current contracted egress/request/add-on/logging/transform charges, commitment floors and origin effects by real traffic mix. Dynamic traffic may still buy useful routing/security, not just cache offload. Compare required behavior and total ownership cost; no universal pay-as-you-go premium or direct-origin answer is implied.

### Q24. You are migrating CDNs. What is the runbook?

**Model answer:** Provision and test both paths: TLS/access, key variants, headers, stale behavior, purge recovery and miss load. Shift under measured guardrails, preserve old paths/assets and define rollback. Lower applicable DNS TTL in advance but measure actual request convergence. Supported warm-up can help; it does not prove every cache is populated.

### Q25. Tell me about a CDN incident you led. What made it hard?

**Model answer:** Use your actual incident, with detection, affected content/identity boundary, mitigation cost, root cause, measured recovery and prevention evidence. An illustrative story about TTL drift or a purge-induced load surge is a practice case, not personal experience. Distinguish silent wrong content from availability symptoms.

## Common Mistakes

- Answering "the CDN caches static files" — that is the 2010 model; the question is about cache keys and invalidation semantics.
- Forgetting that the cache key is a security boundary (cookie fragmentation vs personalization leaks).
- Proposing multi-CDN without naming its operational cost.

## Best Practices

- Per-path cache policy as code, reviewed — never per-request pragmatism.
- Versioned URLs as the default invalidation story; purges for corrections only.

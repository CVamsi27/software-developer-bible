# Nginx Reverse Proxy Internals

> **One process, a handful of workers, tens of thousands of connections.** Nginx won the web by refusing the thread-per-connection model: an event loop per worker plus non-blocking I/O turns a commodity box into a TLS-terminating, buffering, rate-limiting, load-balancing front door. Understand the master–worker split, the config context hierarchy, and where requests actually get held — and nginx stops being magic incantations in `/etc/nginx`.

## TL;DR

- **Forward proxy protects clients; reverse proxy protects servers.** Nginx in reverse-proxy mode fronts your app pool with TLS termination, caching, compression, rate limiting, and L7 routing.
- **Nginx exists because of C10K**: Apache's thread-per-connection collapsed at 10K concurrent connections; nginx's event-driven workers handle thousands of connections each on a fixed memory budget.
- **Master reads config and manages workers; workers accept connections and run event loops** (epoll on Linux, kqueue on BSD/macOS) — never one OS thread per connection.
- **Blocking is poison.** One blocking call freezes an entire worker's event loop; disk I/O goes to thread pools (`aio threads`), CPU-heavy work gets offloaded or proxied elsewhere.
- **Config is a context hierarchy:** `main` → `events` → `http` → `server` → `location`. Directives inherit downward unless overridden.
- **Static files ride `sendfile` (zero-copy kernel path); dynamic traffic rides `proxy_pass` to `upstream` pools** — with round-robin, `least_conn`, `ip_hash`, and weights.
- **Reload without downtime:** `nginx -t` first, then SIGHUP — old workers drain in-flight connections while new workers serve new config.

## First Principles

A reverse proxy is the network's front door — its internals are event-loop economics:

1. **Nginx's model: async event loop per worker** (not thread-per-connection) — C10K by architecture; the config language maps locations → upstreams with buffering, TLS, and limits as knobs.
2. **It's the TLS terminator, the static file server, and the load balancer** (→ 30.2.1.04) in one — which is why it sits everywhere, and why its timeout/buffer settings are the source of classic 502/413 incidents (the defaults are conservative; your upload sizes are not).
3. **The proxy is also the trust boundary**: header sanitization, rate limits (→ 20.3.4.01), and access control happen here once — the edge policy point before (→ 20.6.1.02) or instead of a gateway.

## Definition

A **reverse proxy** is a server that sits in front of backend application servers and forwards client requests to them, returning responses as if it were the origin. Clients see only the proxy; topology, scaling, and hardening live behind it.

The mirror concept, so you never mix them up:

```text
FORWARD PROXY — protects CLIENTS
┌──────────────────────────────────────────────┐     ┌───────────────┐     ┌─────────┐
│ Laptop │────►│ Forward proxy │────►│   Web   │
│ (user) │     │ corp egress,  │◄────│ (any)   │
└──────────────────────────────────────────────┘     │ filtering,    │     └─────────┘
               │ anonymity     │
               └───────────────┘
Server has NO idea which real client is behind it.

REVERSE PROXY — protects SERVERS
┌────────────────────────────────────────────────────────────────────────┐     ┌───────────────┐     ┌──────────────┐
│ Browser│────►│ Reverse proxy                      │────►│ App server 1 │
│ (user) │     │ nginx: TLS,                        │     │ App server 2 │
└────────────────────────────────────────────────────────────────────────┘     │ cache, limits │     │ App server 3 │
               └───────────────┘     └──────────────┘
Client has NO idea how many servers are behind it.
```

Same word "proxy," opposite beneficiaries. A forward proxy hides *who's asking*; a reverse proxy hides *who's answering*.

## Why It Matters

1. **C10K was the founding problem.** In 1999, 10K concurrent connections on one box was impossible with thread-per-connection stacks (each thread = ~MB of stack + scheduler overhead). Nginx's event model made C10K trivial and C10M plausible — that design is why Node.js, Go netpollers, and Envoy all look the same inside.
2. **It is the default edge of real deployments.** Kubernetes ingress-nginx, most Docker setups, every "put a proxy in front" tutorial — nginx is the vocabulary.
3. **Senior interviews probe internals, not syntax.** "Why does one slow disk read stall thousands of connections?" separates people who memorized directives from people who understand the loop.
4. **Every frontend concern concentrates here:** TLS certificates, gzip/brotli, caching, rate limiting, slow-client absorption — done once at the proxy instead of in every app instance.
5. **It is the reference point for alternatives.** You can't choose HAProxy/Envoy/cloud ALB intelligently without knowing what nginx does and where it strains.

## How It Works

### Master–worker process model

```text
                 nginx binary start
                        │
                ┌───────▼─────────────┐
                │     MASTER          │  runs as root (bind :80/:443)
                │ • reads config      │  then drops privileges for workers
                │ • binds ports       │
                │ • spawns N          │
                │   workers           │
                │ • handles           │
                │   SIGHUP/reload     │
                └───┬───┬───┬─────────┘
                    │   │             │  fork
              ┌─────▼┐ ┌▼─────┬▼──────┐
              │WORKER│ │WORKER│WORKER │  unprivileged user
              │event │ │event │event  │  worker_processes auto
              │loop  │ │loop  │loop   │  (= # cores)
              └──────┘ └──────┴───────┘
                share listening sockets;
                kernel wakes one on arrival
```

Division of labor:

| Master | Worker |  |
| ----------------------- | ------------------------------------- | ---------------------------- |
| Reads config | Yes (validates, then signals workers) | Inherits parsed config |
| Binds :80/:443 | Yes (privileged) | Uses inherited fds |
| Accepts connections | No | Yes (shared listen socket) |
| Handles reloads/signals | Yes | Drains gracefully on request |
| Runs your app code | Never | Per-connection, event-driven |

Rule: **one master, `worker_processes auto` workers** (one per CPU core). More workers than cores just adds contention.

### The event loop: epoll/kqueue multiplexing

Each worker runs a single-threaded event loop over an OS readiness API:

```text
WORKER EVENT LOOP (single thread)
┌──────────────────────────────────────────────────────┐
│ epoll_wait(kqueue) ← register ALL sockets once       │
│      │                                               │
│      ▼ "fd 17 readable, fd 92 writable"              │
│ dispatch ready events:                               │
│   • fd 17: read request bytes → parse HTTP           │
│   • fd 92: write response chunk (socket buffer room) │
│   • upstream fd: proxy_pass response arriving        │
│ never wait on ANY single connection                  │
└──────────────────────────────────────────────────────┘

Memory math: thread-per-conn ≈ 8 MB stack × 10,000 conns = 80 GB ✗
             event loop    ≈ few KB per conn state  = ~100 MB ✓
```

Contrast with Apache's classic prefork/worker MPMs:

| Apache (thread/process per conn) | Nginx (event loop per worker) |  |
| -------------------------------- | ------------------------------------------------ | ----------------------------------------------------- |
| Cost per idle connection | Thread stack + scheduler slot (~MBs) | One socket entry in epoll set (~KBs) |
| 10K concurrent conns | Needs tuning heroics (C10K problem) | Default behavior |
| Best-case workload | CPU-bound dynamic modules, .htaccess flexibility | Massive concurrency of mostly-idle or I/O-bound conns |
| Blocking call damage | Blocks ONE thread | Blocks the WHOLE worker |

This is also exactly why nginx is a great WebSocket/long-polling proxy: idle connections are nearly free.

### Blocking is poison

The event loop contract: **never block the thread.** One synchronous 200 ms disk read inside a worker stalls every connection that worker owns:

```text
Worker handling 5,000 conns hits a blocking read():
  t=0     ── worker asleep in read() ── 4,999 conns frozen
  t=200ms ── wake, flush everything   ── latency spike for everyone

Fixes:
• aio threads;        → disk I/O handed to kernel thread pool,
  aio on                event loop keeps spinning
• sendfile            → static file serving stays in-kernel
• proxy offload       → heavy work belongs to app servers anyway
```

Practical rule: if a directive or plugin would block (slow disk, DNS sync lookup, embedded scripting doing IO), it must be async/threaded — otherwise it's a self-inflicted outage amplifier.

### Config model: contexts and inheritance

Directives live in nested contexts; children inherit unset values from parents:

```text
main      (global: user, worker_processes, error_log)
└── events        (connection model: worker_connections, use epoll)
    └── http      (all web: mime types, logging, gzip, proxies)
        ├── upstream   (named backend pools)
        ├── server     (one virtual host: listen + server_name)
        │   └── location (per-path routing: /static/, /api/)
        └── server ...
```

Annotated production-flavored snippet (annotated line by line):

```nginx
# ── main context: process-level ──────────────────────────────
user www-data;                 # workers drop root after binding
worker_processes auto;         # one worker per core
error_log /var/log/nginx/error.log warn;

# ── events context: connection model ─────────────────────────
events {
    worker_connections 4096;   # per worker; ×cores = total ceiling
}

# ── http context: shared web plumbing ────────────────────────
http {
    include       /etc/nginx/mime.types;
    log_format main '$remote_addr - $request_time '
                    'upstream:$upstream_response_time "$request"';
    access_log    /var/log/nginx/access.log main;

    gzip              on;
    gzip_types        text/css application/javascript application/json;

    limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

    # named backend pool — referenced by proxy_pass below
    upstream app_pool {
        least_conn;                                  # algorithm
        server 10.0.0.11:3000 weight=2 max_fails=3 fail_timeout=15s;
        server 10.0.0.12:3000           max_fails=3 fail_timeout=15s;
        server 10.0.0.13:3000 backup;                # spare
        keepalive 32;                   # reuse upstream conns!
    }

    # ── server context: one virtual host ─────────────────────
    server {
        listen 443 ssl http2;
        server_name api.example.com;

        ssl_certificate     /etc/ssl/example.com.fullchain.pem;
        ssl_certificate_key /etc/ssl/example.com.key;
        ssl_protocols       TLSv1.2 TLSv1.3;   # termination HERE

        # ── location contexts: routing table ────────────────
        location /static/ {          # cold files → kernel path
            alias /srv/app/assets/;
            expires 1y;
            add_header Cache-Control "public, immutable";
            sendfile on;
            tcp_nopush on;
        }

        location /api/ {             # dynamic → upstream pool
            limit_req zone=api burst=20 nodelay;
            proxy_pass http://app_pool;
            proxy_http_version 1.1;
            proxy_set_header Connection "";        # enable keepalive
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_read_timeout 30s;
            proxy_buffering on;      # absorb slow clients here
        }
    }
}
```

### Static files vs proxy_pass: two very different paths

```text
STATIC REQUEST (/static/app.js):
client ──► nginx ──► open file ──► SENDFILE (zero-copy):
                     page cache → NIC without touching userspace
                     (no copy to worker buffer, no user/kernel ping-pong)

DYNAMIC REQUEST (/api/users):
client ──► nginx ──► PROXY_PASS:
                     parse request → pick upstream → open/reuse conn
                     → forward → buffer response → stream back
```

`sendfile on` matters because static serving becomes almost free CPU-wise. `proxy_pass` is where nginx earns its keep as a *reverse proxy* rather than a web server.

### Upstream blocks and load-balancing algorithms

| Directive | Behavior | Use when |
| ---------------------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| *(default round robin)* | Sequential even spread | Homogeneous stateless pool |
| `least_conn` | Fewest active connections wins | Long-lived/mixed-duration requests |
| `ip_hash` | hash(client IP) → fixed server | Session affinity without shared store (crude — NAT makes offices one client) |
| `weight=N` | Proportional share | Heterogeneous hardware, canary-by-ratio |
| `backup` | Only used when others fail | Warm spare |
| `max_fails` / `fail_timeout` | Passive health check | Marking flaky servers down |

Theory and algorithms beyond these (consistent hashing, least-response-time): [Load Balancing](../../30-architecture/30.2-system-design/01-theory/30.2.1.04-load-balancing.md).

### Health checks: passive vs active

- **Passive (open source, built-in):** nginx watches real traffic — `max_fails=3 fail_timeout=15s` means 3 failures within the window pulls the server from rotation for 15 s. Zero extra traffic; reacts only to actual failures.
- **Active:** nginx probes `/health` on a schedule and ejects before real users hit a dead node. This ships with **NGINX Plus**, while open-source nginx needs third-party modules or an external checker. HAProxy and Envoy include native active checks out of the box — a genuine selection criterion between them.
- Either way, pair with `keepalive N` in the upstream so healthy-server checks don't churn handshakes (see transport economics in [TCP & UDP Transport Fundamentals](../../30-architecture/30.2-system-design/01-theory/30.2.1.21-tcp-udp-transport-fundamentals.md)).

### TLS termination at the proxy

Terminate HTTPS at nginx; speak plain HTTP (or mTLS) to the internal network:

- Certificates renew in ONE place instead of every app instance.
- TLS handshakes (CPU-heavy asymmetric crypto) stop hitting app workers.
- HTTP/2 to clients, HTTP/1.1 to upstreams — protocols may differ per hop.
- Trade-off: plaintext on the internal segment — re-encrypt inside zero-trust estates (or use SSL passthrough when end-to-end TLS is mandatory, losing L7 visibility).

Cipher suites and certificate mechanics: [Encryption](../../20-backend/20.5-security/03-hardening-and-operations/20.5.3.01-encryption.md); header/CSP hardening at the edge: [Web Security](../../20-backend/20.5-security/03-hardening-and-operations/20.5.3.02-web-security.md).

### Compression: gzip and brotli

```nginx
gzip              on;
gzip_min_length   1024;              # don't compress tiny bodies
gzip_comp_level   5;                 # diminishing returns past ~6
gzip_vary         on;                # caches key on Accept-Encoding
gzip_proxied      any;
```

Brotli (`ngx_brotli` module) beats gzip ~15–20% on text at comparable CPU, but is CPU-costlier at max levels — common pattern: brotli level 4-5 for dynamic responses, pre-brotli'd (level 11) static assets on disk served as-is.

### Proxy buffering and slow-client protection

By default nginx buffers upstream responses to disk/memory (`proxy_buffering on`). Why care:

```text
WITHOUT buffering: upstream writes directly to client socket
  → client on 2G network reading 10 MB at 50 KB/s pins the
    upstream worker/connection for 3+ minutes  ✗

WITH buffering: upstream dumps to nginx in milliseconds, frees
  itself; nginx dribbles bytes to the slow client at its leisure ✓
```

Tuning knobs: `proxy_buffers`, `proxy_max_temp_file_size`, `proxy_buffer_size` (first-chunk/headers). Turn buffering OFF only for streaming (SSE, long-poll) endpoints. Same protective logic applies inbound via `client_max_body_size` and `proxy_request_buffering`.

### Rate limiting: limit_req

```nginx
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
# 10 MB zone ≈ ~160K IP states

location /api/ {
    limit_req zone=api burst=20 nodelay;
    # burst=20   → queue depth of 20 above the rate
    # nodelay    → serve burst immediately (no artificial spacing),
    #              reject beyond it with 503 (default status code
    #              configurable via limit_req_status 429)
}
```

Algorithm is leaky-bucket: requests drip at `rate`; `burst` absorbs spikes; `nodelay` chooses instant-serve-then-reject over smooth throttling. Without `burst`, every millisecond jitter over the rate returns errors — the classic misconfiguration. Full taxonomy (token bucket, sliding window, distributed): [Rate Limiting theory](../../30-architecture/30.2-system-design/01-theory/30.2.1.08-rate-limiting.md).

### Caching at the proxy: proxy_cache

```nginx
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=pages:50m
                 max_size=1g inactive=60m;

server {
    location /public/ {
        proxy_cache pages;
        proxy_cache_valid 200 60s;         # TTL per status
        proxy_cache_use_stale error timeout updating;
                                           # serve stale on upstream pain
        add_header X-Cache-Status $upstream_cache_status;
        proxy_pass http://app_pool;
    }
}
```

`$upstream_cache_status` (HIT/MISS/BYPASS) is your hit-ratio metric. For the cache-pattern theory this implements (cache-aside vs read-through, invalidation strategy): [Caching Patterns](../../30-architecture/30.2-system-design/01-theory/30.2.1.05-caching-patterns.md); for doing it globally across regions: [CDN Architecture](../40.10-cdn/40.10.01-cdn-architecture.md).

### Zero-downtime reload: SIGHUP semantics

```bash
sudo nginx -t                 # ① validate BEFORE touching anything
sudo nginx -s reload          # ② sends SIGHUP to master
```

What SIGHUP actually does:

```text
SIGHUP arrives at MASTER
  ├─ re-reads + validates nginx.conf (fails → old config kept!)
  ├─ spawns NEW workers with the new config
  ├─ tells OLD workers: finish in-flight, then exit
  │    (listen sockets stay shared the whole time)
  └─ result: ZERO refused connections during deploys
```

Notes that matter operationally: `systemctl reload nginx` wraps the same signal; long-lived connections (WebSockets) need `worker_shutdown_timeout` so draining workers eventually let go; config *syntax* validity ≠ semantic validity — `-t` catches typos, not "wrong upstream port."

## Code Examples

Full minimal production setup — browser → CDN → nginx (TLS termination) → app pool:

```nginx
user www-data;
worker_processes auto;
events { worker_connections 4096; }

http {
    include      mime.types;
    sendfile     on;

    limit_req_zone $binary_remote_addr zone=all:10m rate=20r/s;

    upstream app_pool {
        least_conn;
        server 10.0.0.11:3000 max_fails=3 fail_timeout=10s;
        server 10.0.0.12:3000 max_fails=3 fail_timeout=10s;
        keepalive 64;
    }

    server {
        listen 80;
        server_name example.com;
        return 301 https://$host$request_uri;      # force TLS
    }

    server {
        listen 443 ssl http2;
        server_name example.com;

        ssl_certificate     /etc/ssl/example.com.fullchain.pem;
        ssl_certificate_key /etc/ssl/example.com.key;
        ssl_protocols       TLSv1.2 TLSv1.3;

        add_header Strict-Transport-Security "max-age=31536000" always;

        location /assets/ {
            alias /srv/app/public/;
            expires 1y;
            add_header Cache-Control "public, immutable";
        }

        location / {
            limit_req zone=all burst=40 nodelay;
            proxy_pass http://app_pool;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto https;
        }
    }
}
```

Operations workflow — the safe deploy loop:

```bash
# edit config, then ALWAYS:
sudo nginx -t                                   # syntax check
# ok: configuration file /etc/nginx/nginx.conf test is successful

sudo nginx -s reload                            # graceful SIGHUP swap

# watch the swap happen:
tail -f /var/log/nginx/error.log
# ...gracefully shutting down, exiting...

# verify workers picked up new config:
ps aux | grep '[n]ginx'
```

WebSocket proxying — the two headers everyone forgets:

```nginx
location /ws/ {
    proxy_pass http://app_pool;
    proxy_http_version 1.1;                       # required
    proxy_set_header Upgrade $http_upgrade;       # WS handshake
    proxy_set_header Connection "upgrade";        # (not "" here!)
    proxy_read_timeout 3600s;                     # idle conns die at 60s default
}
```

Verifying what nginx is actually doing, from outside:

```bash
curl -sI https://example.com/ \
  | grep -Ei 'server|x-cache|content-encoding'
# Server: nginx
# Content-Encoding: br        ← compression active
# X-Cache-Status: HIT         ← proxy_cache working

ab -n 10000 -c 500 https://example.com/api/health   # soak test the edge
```

## Real-World Use Cases

### 1. The canonical production edge

Browser → CDN (Cloudflare caches static, absorbs DDoS) → origin nginx (TLS termination, WAF-ish header rules, rate limiting, gzip) → upstream app pool (Node/NestJS). Each layer does the one thing it's best at; apps stay boring and stateless.

```text
┌─────────────────────────────────────────────────────────────────────────┐  HTTPS   ┌─────────┐  HTTPS   ┌───────────┐  HTTP   ┌──────────┐
│Browser │─────────►│   CDN   │─────────►│   nginx   │────────►│ app pool │
└─────────────────────────────────────────────────────────────────────────┘ (cached)│  edge   │(miss)    │ TLS term  │keepalive│ 3x Node  │
                   └─────────────────────────────────────────────────────┘          │ limits    │         └──────────┘
                                        └───────────┘
```

### 2. Kubernetes ingress

ingress-nginx IS nginx: ingress controllers translate Kubernetes `Ingress` resources into the same `server`/`location` blocks above. Knowing raw nginx means debugging ingress annotations stops being folklore.

### 3. Canary releases without new infrastructure

Weighted upstreams give percentage splits with zero app changes: `server app_v2 weight=1; server app_v1 weight=9;` → 10% to v2, watch error rates, raise the weight, remove v1. (Envoy/Istio do richer matching — see decision table below.)

### 4. Slow-client armor for APIs

Mobile clients on bad networks request big exports. With `proxy_buffering on`, upstream workers finish writing in ms and move on; nginx babysits the trickle. Without it, a handful of subway riders exhausts the app's connection pool.

### 5. Legacy modernization façade

Migrating a monolith to services incrementally: nginx routes `/api/v2/*` to new microservices while everything else falls through to the monolith — path-based strangulation at the edge, no client changes.

### Choosing: nginx vs HAProxy vs Envoy vs cloud ALB

| Dimension | nginx | HAProxy | Envoy | Cloud ALB (AWS ALB/NLB) |
| ------------------------ | --------------------------------------------------------- | ---------------------------------- | ------------------------------------------- | ------------------------------ |
| Sweet spot | Web edge: static + reverse proxy + cache | Raw LB throughput, TCP/UDP mastery | Service mesh / dynamic microservice routing | Zero-ops managed LB |
| Active health checks | Plus/third-party only | Built-in | Built-in | Managed |
| Dynamic config (API/SDS) | Weak (reload-centric) | Runtime map updates | First-class xDS, hot-reconfig | Fully managed |
| Config model | Files, declarative | Files + runtime API | YAML + gRPC xDS | Console/IaC |
| Observability depth | Logs + basic stats | Rich stats, stick tables | Tracing/metrics richest | CloudWatch integration |
| Learning curve | Low | Medium | High | Lowest |
| Pick it when... | You want one box to serve, cache, and protect web traffic | TCP-heavy LB or extreme PPS | Mesh, canary-by-header, dynamic fleets | You'd rather not run LB at all |

Common mature answer: several at once — cloud NLB at the perimeter, nginx/HAProxy in the VPC, Envoy sidecars in the mesh.

## Common Mistakes

| Mistake | Consequence | Fix |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Reload without `nginx -t` first | Broken config rejected mid-deploy confusion — or worse, semantic breakage with valid syntax | Script `nginx -t && nginx -s reload` always |
| Missing `proxy_set_header Host/X-Forwarded-*` | Apps generate wrong absolute URLs, lose real client IPs, break auth callbacks | Set them once per location; log `$http_x_forwarded_for` |
| `limit_req` without `burst` | Legitimate bursts get 503s at perfectly normal load | Add `burst=N nodelay`; return 429 via `limit_req_status` |
| Blocking module/sync DNS inside worker | Whole worker (thousands of conns) stalls per call | Keep workers async-only; resolve upstream names out-of-band |
| `ip_hash` for session affinity behind corporate NAT | Entire office = one "client" → hot server; scale-out broken | Shared session store (Redis) + true LB algorithms |
| Buffering disabled everywhere "for simplicity" | Slow clients pin upstream connections; pool exhaustion | Buffer by default; disable only for streaming endpoints |
| No `keepalive` in upstream block | New TCP handshake per request to app servers | `proxy_http_version 1.1` + `Connection ""` + `keepalive N` |
| `worker_processes` hardcoded on scaled VMs | Under-utilized or oversubscribed CPUs after resize | `auto` |
| Forgetting `worker_shutdown_timeout` | WebSocket-holding workers never drain on reload | Set explicit timeout; plan reconnect logic |

## Best Practices

1. **`nginx -t` before every reload; automate it in CI/deploy hooks.**
2. **`worker_processes auto` + tune `worker_connections` deliberately** — multiply by core count for the real ceiling.
3. **Keep upstream connections alive** (`keepalive` + `proxy_http_version 1.1` + empty `Connection`) — free latency win per request.
4. **Terminate TLS at the edge, centralize cert renewal**, and set HSTS while you're there.
5. **Buffer responses by default; make streaming opt-out per location.**
6. **Rate-limit with explicit burst semantics and 429s,** and monitor rejections as a first-class metric.
7. **Prefer passive health checks in OSS nginx; demand active checks when evaluating HAProxy/Envoy/Plus.**
8. **Log `$request_time` and `$upstream_response_time`** — the gap isolates proxy-side vs app-side latency instantly.
9. **Test config changes against staging traffic shapes** (WebSockets, uploads > `client_max_body_size`, SSE) — syntax-valid configs still route wrong.
10. **Know your escape hatch:** when requirements outgrow nginx (dynamic service discovery, per-request routing logic, mesh telemetry), the decision table says Envoy — migrate consciously, not reactively.

## Summary

Nginx is a reverse proxy born to solve C10K: a privileged master manages lifecycle and config, while a fixed number of unprivileged workers each run an epoll/kqueue event loop that multiplexes thousands of cheap connections — the anti-Apache. Its cardinal law is never block the worker (disk I/O to threads/sendfile, heavy work downstream). Configuration nests through `main → events → http → server → location` contexts with downward inheritance; static paths ride kernel zero-copy `sendfile`, dynamic ones flow through `proxy_pass` into `upstream` pools balanced by round-robin, `least_conn`, `ip_hash`, or weights, guarded by passive health checks (`max_fails`) — active checks require Plus or another product. Around those bones: TLS termination, gzip/brotli, response buffering as slow-client armor, leaky-bucket `limit_req`, `proxy_cache`, and genuinely zero-downtime SIGHUP reloads validated by `nginx -t`. Choose nginx for the web edge, HAProxy for raw LB throughput, Envoy for dynamic mesh routing, and managed ALBs when operating a proxy isn't your job.

## Cheat Sheet
```text
NGINX REVERSE PROXY CHEAT SHEET
════════════════════════════════════════════════════════════════

PROXY DIRECTION:
• Forward proxy  = protects/hides CLIENTS (egress, filtering)
• Reverse proxy  = protects/hides SERVERS (TLS, cache, LB, limits)

PROCESS MODEL:
• Master: config, ports, signals, forks workers
• Workers: worker_processes auto · event loop each
• epoll (Linux) / kqueue (BSD·macOS) — KBs per conn, not MBs
• BLOCKING = POISON: aio threads/sendfile for disk, nothing else

CONFIG CONTEXTS (inherit ↓):
main → events → http → upstream/server → location

ROUTING:
• Static:  sendfile on (zero-copy, near-free CPU)
• Dynamic: proxy_pass http://upstream_name

UPSTREAMS:
• round-robin (default) · least_conn · ip_hash · weight=N · backup
• Passive health: max_fails=3 fail_timeout=15s (active = Plus/OSS mods)
• keepalive N + proxy_http_version 1.1 + Connection "" = reuse

EDGE DUTIES:
• TLS termination: certs in one place, crypto off app servers
• gzip/brotli: gzip_vary on, min_length, comp_level ≤ 6
• proxy_buffering on = slow-client armor (off ONLY for SSE/streaming)
• limit_req zone=X burst=N nodelay  (leaky bucket; no burst = 503 storm)
• proxy_cache_path + proxy_cache_valid + X-Cache-Status header

ZERO-DOWNTIME RELOAD:
• nginx -t  THEN  nginx -s reload (SIGHUP)
• new workers spawn, old ones drain in-flight, no dropped conns

VS ALTERNATIVES:
• nginx = web edge · HAProxy = raw LB · Envoy = mesh/dynamic
• cloud ALB = managed, zero ops

IN INTERVIEWS:
• C10K story + why event loops win
• "one blocked disk read stalls 1000s of conns" — the poison rule
• SIGHUP drain semantics = zero-downtime deploys
```

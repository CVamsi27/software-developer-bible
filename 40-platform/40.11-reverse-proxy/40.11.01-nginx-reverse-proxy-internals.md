# Nginx Reverse Proxy Internals

A client requests an export that takes 40 seconds to generate. Another client uploads a large file, and a third opens a WebSocket. The proxy must route each request, manage two network connections for ordinary proxied traffic, and decide where waiting, buffering, and failure recovery belong. Understanding that path makes NGINX configuration easier to reason about than memorizing directives.

## Definition

A **reverse proxy** accepts requests on behalf of one or more backend services. The client connects to the proxy; the proxy applies routing and connection policy, forwards the request to a selected backend, and returns the backend response.

> **Textbook Definition:** A reverse proxy is an intermediary server on the origin side of a client–server communication. It terminates or relays client connections, selects an origin server, and forwards requests and responses according to configured routing, transport, security, and availability policies.

A forward proxy represents a client reaching external origins. A reverse proxy represents an origin reaching its backend services. Neither role alone guarantees security or hides the original address: network policy, authentication, and trusted-header handling establish those boundaries.

## First Principles

Most network connections spend more time waiting than using CPU. An event-driven server can let a worker process many connections by responding when sockets become ready, instead of assigning a waiting thread to each connection. This saves waiting threads; it does not make a worker's CPU, file descriptors, memory, or disk unlimited. When a client reads slowly, something must retain the response bytes. NGINX can buffer them in memory and temporary files, moving pressure away from the application connection and onto proxy resources. Every reliability setting therefore chooses where work waits, what is bounded, and which failure the system accepts.

## 1. Follow One Request Through Master, Worker, and Location

The master process reads configuration, opens listening sockets, and manages worker lifecycles. A worker accepts a client connection, processes TLS and HTTP, selects a virtual server and location, then either serves a local file or opens an upstream connection. For a typical proxied request, NGINX is managing both the client-side and upstream-side sockets.

    client ──TLS/HTTP──> worker ──location──> upstream service
                           │                       │
                           └── local file           └── response
                                   response <── buffers or streams

The configuration is organized into nested **contexts**. The main context contains process settings; `events` configures connection handling; `http` contains web settings, upstream groups, virtual `server` blocks, and per-path `location` blocks. A directive is legal only in supported contexts, and inheritance depends on that directive. For example, a child location that defines any `add_header` directive stops inheriting the parent's `add_header` set by default; NGINX 1.29.3 added `add_header_inherit` to change this behavior.

Here is a routing fragment, not a complete deployment file. It assumes TLS certificates, an appropriate trusted-proxy policy, and two reachable application instances are configured for the environment:

    worker_processes auto;

    events {
        worker_connections 2048;
    }

    http {
        upstream app_pool {
            least_conn;
            server 10.0.0.11:3000 max_fails=3 fail_timeout=15s;
            server 10.0.0.12:3000 max_fails=3 fail_timeout=15s;
        }

        server {
            listen 443 ssl;
            server_name api.example.test;

            location /api/ {
                proxy_pass http://app_pool;
                proxy_set_header Host $host;
                proxy_set_header X-Real-IP $remote_addr;
                proxy_set_header X-Forwarded-For $remote_addr;
                proxy_set_header X-Forwarded-Proto $scheme;
                proxy_read_timeout 30s;
            }
        }
    }

`worker_processes auto` is a starting point based on detected CPUs, not a universal sizing rule. Tune it against the container or host's actual CPU allocation and workload. `worker_connections` is a per-worker ceiling for all open connections, including upstream sockets; a proxied request often uses one client socket and one upstream socket. File-descriptor limits also constrain the real ceiling. HTTP/2 can carry multiple request streams over one client connection, so neither connection count nor worker count directly states request throughput.

Each worker runs an event loop using the operating system's available readiness mechanism, such as epoll on Linux or kqueue on BSD systems. A slow socket does not require the worker to sleep in a dedicated thread; the worker can process other ready events and return to it later. A blocking operation is different: a long CPU-bound filter, synchronous plugin call, or blocking file read occupies that worker and delays other connections assigned to it. This is not automatically a stall across every worker, but it can cause a large latency spike on one worker. `aio threads` can offload supported file operations when NGINX is built and configured for thread pools. `sendfile` can reduce data copying, but it does not guarantee that cold-file reads never wait. Heavy business logic belongs in the application tier, not in a worker callback.

## 2. Route, Balance, and Reuse Upstream Connections

`location` selection and `proxy_pass` determine the path the application receives. In `location /api/`, `proxy_pass http://app_pool;` preserves `/api/users`. Adding a URI slash — `proxy_pass http://app_pool/;` — normally replaces the matched `/api/` prefix and sends `/users`. Rewrites, regular-expression or named locations, and variables add special cases, so test the exact route when changing it.

The upstream group chooses a backend. The default is weighted round robin; `least_conn` can fit pools where request durations differ; `ip_hash` offers address-based affinity but can skew traffic behind NAT or change assignments as the pool changes. Weights express a share of selection, not an exact share of users or completed work. Pick a method from observed traffic and failure behavior, not its name.

Open-source NGINX uses **passive health checks**: it notices failures while handling real requests. `max_fails` and `fail_timeout` influence when a server is treated as unavailable, with behavior affected by the retry policy and special cases such as a single-server group. Active probes that check a server before routing user traffic are available in NGINX Plus; otherwise use a supported external checker or a proxy that meets this requirement.

Upstream connection reuse depends on NGINX version. Starting with **1.29.7**, NGINX uses HTTP/1.1 and keeps an idle upstream connection cache by default, with a default limit of 32 idle connections per worker. The cache can be sized explicitly; `keepalive N` limits cached idle connections, not all active connections. Before 1.29.7, explicit HTTP/1.1, an empty `Connection` header, and an upstream `keepalive` setting were commonly required. Check the deployed version before copying an older recipe. Reuse avoids repeated connection setup; the backend can still close a socket, and too many idle sockets can consume backend capacity.

A retry is not proof that the first attempt had no effect. An application may commit a mutation and lose its response before NGINX sees it. By default, NGINX does not send a non-idempotent request to another upstream after it has already sent that request; enabling the `non_idempotent` retry option accepts that risk. Safe mutation retries require application-level idempotency keys and a way to look up or reconcile the original operation.

## 3. Place Waiting and Backpressure Deliberately

Timeout directives named for an I/O operation usually bound inactivity **between successive operations**, not the total request duration. `proxy_connect_timeout` governs establishing the upstream connection; `proxy_send_timeout` and `proxy_read_timeout` govern gaps while sending to or reading from the upstream. An upstream that sends a byte often enough may run much longer than `proxy_read_timeout`. Define an end-to-end deadline in the application or request orchestration layer, and give each hop a compatible budget.

Response buffering is on by default. NGINX reads from the upstream as capacity allows, keeping data in memory and, for large responses, possibly in temporary files. This can let an application release its upstream connection before a slow client finishes downloading. Buffering does not remove resource cost: configure disk capacity, memory, temporary-file limits, and concurrent downloads. Disable it on paths such as server-sent events when prompt flushing is part of the contract. Long polling alone does not necessarily require streaming.

Request buffering is also on by default. NGINX can read a client upload before forwarding it; disabling it streams the body upstream and changes when upstream work begins and whether a request can be retried. Set `client_max_body_size` and upload/read timeouts to the application contract, and test large, slow, interrupted, and resumed uploads separately from downloads.

For a public cache, `proxy_cache_bypass` decides whether NGINX may serve an existing entry, while `proxy_no_cache` decides whether it may store the new response. Authenticated and cookie-bearing requests often need both controls, but the cache key, upstream `Cache-Control`, `Set-Cookie`, and `Vary` behavior must also be checked. A cache is safe only when every request dimension that changes the representation is either in the key or excluded from shared caching. Stale serving improves availability only when the tolerated staleness is explicit.

## 4. Enforce Trust and Policy at the Edge

When NGINX is directly reachable, `$remote_addr` is the network peer and is a safer starting point than a client-supplied `X-Forwarded-For`. When a CDN or load balancer sits in front, configure the Real IP module with that proxy's exact CIDRs and its documented address header before using the normalized `$remote_addr`. Otherwise, rate limits may group all users under the CDN address — or forged headers may influence application security decisions. Restrict direct-origin access when the design depends on traffic passing through the trusted proxy.

`limit_req` implements leaky-bucket rate accounting in a shared memory zone on one NGINX instance. `burst` controls excess requests; without `nodelay`, allowed excess is delayed, while `nodelay` admits the burst immediately and rejects requests beyond it. The default rejection is 503; set a status such as 429 when that is the API contract. A per-instance zone is not a coordinated fleet-wide quota, and its key is only meaningful when client identity has been established correctly.

TLS has two separate hops: client-to-proxy and proxy-to-upstream. Terminating public TLS at NGINX centralizes that hop's certificate and HTTP policy, but internal traffic is plaintext unless re-encrypted. For HTTPS upstreams, verification and SNI are off by default. Configure the expected certificate name and trusted CA explicitly:

    location /private-api/ {
        proxy_pass https://private_api;
        proxy_ssl_server_name on;
        proxy_ssl_name api.internal.example;
        proxy_ssl_verify on;
        proxy_ssl_trusted_certificate /etc/ssl/internal-ca.pem;
    }

The certificate must be valid for `api.internal.example`; use a client certificate too when the upstream requires mutual TLS. Merely writing `https://` encrypts the connection but does not authenticate the upstream under NGINX's defaults.

Compression also belongs to an explicit edge policy. Gzip may save bandwidth for text responses while using CPU. Measure representative content and latency, avoid recompressing already-compressed formats, and emit `Vary: Accept-Encoding` when caches may store compressed variants. Brotli requires a build/module or another serving layer that supports it.

## 5. Reload Safely and Read Operational Evidence

A safe configuration update starts with `nginx -t`, followed by a reload. On SIGHUP the master validates and attempts to apply the new configuration; if that fails, it keeps the old configuration. On success, it starts new workers and asks old workers to stop accepting new work and drain existing connections.

    sudo nginx -t
    sudo nginx -s reload

A successful syntax check cannot catch a valid route to the wrong service, an incorrect trust list, or a broken application contract. Probe important routes and response headers after reload. Long-lived WebSockets can keep old workers alive; `worker_shutdown_timeout` bounds graceful draining, after which NGINX closes remaining connections. Clients need a reconnect policy, and a reload is not an unconditional zero-downtime guarantee.

Use access logs and metrics that separate proxy time from upstream time, such as `$request_time`, `$upstream_response_time`, upstream address/status, and cache status. Interpret them with retries, upload time, buffering, and client download speed in mind: a timing difference is evidence about the request path, not by itself proof of which component is at fault.

In Kubernetes, do not assume the Ingress API means NGINX. The community ingress-nginx controller retired in March 2026; this does not retire the Kubernetes Ingress API, NGINX itself, or separately maintained NGINX products. Select a maintained controller and test how its routing and security policies map during migration.

## Summary

NGINX routes a request through a worker, location, and upstream, then decides where its response waits. Event-driven workers handle many ready connections, but CPU, file descriptors, and buffers remain finite. At senior level, explain the exact version, trust boundary, timeout interval, retry effect, buffering cost, and recovery behavior behind each configuration choice; then verify those choices with representative traffic and observable evidence.

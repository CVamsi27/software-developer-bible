# 40.11.02 — Nginx Reverse Proxy Interview Questions

> Senior-depth reverse-proxy questions — grouped by difficulty, each with a short answer, the deeper senior reasoning, and the follow-up interviewers actually ask. Covers the full surface: the event-loop process model, config contexts and inheritance, zero-downtime reloads, buffering, health checks, rate limiting, and the nginx-vs-alternatives decision.

## TL;DR

Senior-level nginx/reverse-proxy questions with model answers and follow-ups — the master–worker split, why one blocking call stalls thousands of connections, SIGHUP reload semantics, upstream keepalive economics, and the proxy as trust boundary. The senior signal is reasoning about the **event loop's failure modes** (what blocks it, what drains it, what it holds), not reciting directives — every answer here is derivable from → 40.11.01's internals.

## First Principles

This set probes event-loop economics and edge responsibilities (→ 40.11.01):

1. **The senior tells are mechanism statements**: "old workers drain in-flight while new workers serve" beats "reload is zero-downtime" — juniors memorize directives; seniors narrate what the process actually does.
2. **Every question here maps to an axiom chain** — the loop must never block, connections are cheap but worker time is not, and the proxy is the one place cross-cutting concerns (TLS, limits, headers) happen once. Derive from those and the variant questions answer themselves.

## Beginner

**Q1: What's the difference between a forward proxy and a reverse proxy?**

**Short answer:** A forward proxy protects *clients* — it sits in front of users (corporate egress, filtering, anonymity) and the server doesn't know the real client. A reverse proxy protects *servers* — it sits in front of your app pool (TLS, caching, limits, load balancing) and the client doesn't know how many servers are behind it.

**Go deeper (senior):** "Same word, opposite beneficiaries. The interview variant is: which side does TLS termination belong on, and why? Reverse proxy — certificates renew in one place and the CPU-heavy handshakes stop hitting app workers."

**Q2: Why did nginx beat thread-per-connection servers at scale?**

**Answer:** C10K. A thread per connection costs ~MBs of stack plus scheduler overhead — 10K connections is ~80 GB and scheduler collapse. Nginx runs an event loop per worker over epoll/kqueue: connection state is KBs, so one worker multiplexes thousands of mostly-idle connections on a fixed memory budget.

**Follow-up they ask:** "So what's the cost of that model?" — One blocking call freezes the *entire worker's* connection set. That's the next question.

**Q3: What do the master and worker processes each do?**

**Answer:** The master runs as root to bind :80/:443, reads and validates config, spawns workers, and handles signals (reload, shutdown). Workers run unprivileged, share the listening sockets, and each runs the event loop that accepts connections and serves requests. `worker_processes auto` = one worker per core; more than cores just adds contention.

**Q4: What is TLS termination, and what do you gain and lose at the proxy?**

**Answer:** Terminate HTTPS at the proxy, speak plain HTTP (or mTLS) internally. Gain: certificates renew in one place, handshake CPU off app servers, HTTP/2 to clients while upstreams stay HTTP/1.1. Lose: plaintext on the internal segment — re-encrypt in zero-trust estates, or use SSL passthrough when end-to-end TLS is mandatory (and lose L7 visibility).

**Q5: How does nginx serve a static file differently from a dynamic request?**

**Answer:** Static rides `sendfile on` — the kernel copies page cache to the NIC without touching userspace, so serving files is nearly free CPU-wise. Dynamic rides `proxy_pass` to an upstream pool: parse the request, pick a server, forward, buffer the response, stream it back.

## Intermediate

**Q6: Explain nginx's config context hierarchy and how inheritance works.**

**Answer:** `main → events → http → server → location`. Directives inherit downward unless overridden — so `gzip on` at `http` level applies to every server unless a server turns it off. The practical test: a directive belongs at the highest level where it's uniformly true; per-path overrides belong in `location` blocks.

**Q7: What actually happens on `nginx -s reload`, and why run `nginx -t` first?**

**Answer:** Reload sends SIGHUP to the master: it re-reads and validates config — if validation fails the old config stays — then spawns new workers with the new config and tells old workers to finish in-flight connections and exit, while listen sockets stay shared the whole time. Result: zero refused connections. `nginx -t` first because a syntax error mid-deploy is a pager event, and because `-t` catches typos but *not* semantic errors — a valid config can still point at the wrong upstream port.

**Q8: A mobile client on a bad network downloads a 10 MB export. What does nginx do for you?**

**Answer:** `proxy_buffering on` (the default) is slow-client armor: nginx reads the upstream response into memory/disk buffers in milliseconds, freeing the upstream connection, then dribbles bytes to the slow client at its own pace. Without it, the client's 50 KB/s pins the upstream connection for minutes and exhausts the pool. Turn buffering *off* only for streaming endpoints (SSE, long-poll).

**Q9: How do health checks work in open-source nginx vs HAProxy/Envoy?**

**Answer:** Open-source nginx has passive checks only: `max_fails=3 fail_timeout=15s` ejects a server after 3 real failures within the window, for 15 s. Active checks — probing `/health` before real traffic hits a dead node — ship with NGINX Plus; HAProxy and Envoy include them natively. That's a genuine selection criterion when the pool is small and failures must be caught pre-traffic.

**Q10: How do you rate-limit correctly with `limit_req`?**

**Answer:** `limit_req_zone` defines a leaky-bucket zone (rate per client IP); `limit_req zone=api burst=20 nodelay` allows a queue depth of 20 above the rate, served immediately, rejected beyond that. Without `burst`, millisecond jitter over the rate returns errors at perfectly normal load — the classic misconfiguration. Set `limit_req_status 429` (the default rejection is 503, which lies about the cause) and monitor rejections as a first-class metric.

## Advanced

**Q11: Why is one blocking call in a worker catastrophic, and what are the escapes?**

**Answer:** The worker is single-threaded over thousands of connections — a 200 ms synchronous disk read freezes every connection that worker owns; multiply by workers and you have a site-wide latency spike from one slow disk. Escapes: `aio threads` for disk I/O (kernel thread pool, loop keeps spinning), `sendfile` for static (stays in-kernel), and architectural offloading — heavy work belongs to app servers, not the proxy. Same rule for sync DNS lookups and blocking embedded scripting.

**Q12: WebSocket proxying — what breaks and what do you set?**

**Answer:** Three things: `proxy_http_version 1.1` (WS handshake is HTTP/1.1), `proxy_set_header Upgrade $http_upgrade` and `Connection "upgrade"` (note: *not* the empty `Connection ""` you set for upstream keepalive), and `proxy_read_timeout` above 60 s — idle WebSocket connections die at the default timeout. Reloads also need `worker_shutdown_timeout`, or draining workers holding WebSockets never exit.

**Q13: Why does upstream keepalive need three settings together?**

**Answer:** `keepalive N` in the upstream block creates the connection *cache*, but two defaults silently defeat it: HTTP/1.0 closes per request, so `proxy_http_version 1.1`; and nginx forwards `Connection: close`, so `proxy_set_header Connection ""`. All three or the handshake happens per request anyway — a free latency win most configs forfeit.

**Q14: Why is `ip_hash` session affinity usually the wrong answer?**

**Answer:** It hashes the client IP to pin a user to one server — but behind corporate NAT an entire office is one "client", so the hash hot-spots one server and scale-out breaks. The senior answer: sessions belong in a shared store (Redis), the app stays stateless (→ factor VI of twelve-factor), and the LB picks servers on load, not identity.

**Q15: nginx vs HAProxy vs Envoy vs a cloud ALB — how do you choose?**

**Answer:** nginx for the web edge — one box serving static, caching, and proxying. HAProxy for raw L4/L7 throughput and TCP mastery. Envoy when routing must be dynamic (xDS, mesh, canary-by-header) — nginx is reload-centric and weak at runtime API-driven config. Cloud ALB when operating a proxy isn't your job. The mature answer is often several: managed NLB at the perimeter, nginx in the VPC, Envoy sidecars in the mesh.

## Behavioral & Scenario Drills

**Q16 (scenario): After a deploy, 502s spike. Walk your diagnosis.**

**Answer:** 502 means the proxy couldn't get a valid response from upstream — the proxy is the witness, not the culprit. Check: are app processes up (crash loop on boot?), do health checks show the pool ejection (`max_fails`), is it all upstreams or one, and did the deploy change startup time past `proxy_connect_timeout`. Then split blame with logs: `$request_time` vs `$upstream_response_time` — a gap isolates proxy-side stalls from app-side slowness instantly.

**Q17 (behavioral): Tell me about a config change that caused an outage despite testing.**

**Story to tell (situation → task → action → result):** A rate-limit change passed `nginx -t` and reload — but the new `location` block shadowed an existing one, sending `/api/` to the wrong upstream; syntax was valid, semantics were wrong. The fix: staged config testing against production traffic shapes (WebSockets, uploads, streaming), a weighted canary on the upstream for risky routing changes, and scripted `nginx -t && nginx -s reload` so validation is never skipped. Result: reloads became boring.

**Q18 (follow-up trap): "Kubernetes ingress and CDNs exist — is nginx still relevant?"**

**Answer (the nuanced answer they want):** ingress-nginx *is* nginx — controllers compile Ingress resources into the same `server`/`location` blocks, so raw nginx knowledge is how you debug annotations instead of folklore. CDNs push caching one layer out, but origin TLS termination, rate limiting, and header policy still live at a proxy you own. The layers compose; knowing what each does makes the boundary a decision instead of a default.

## Summary

1. **The event loop is the interview's center of gravity** — C10K economics on one side, blocking-is-poison on the other
2. **Reload semantics are a senior tell** — validate, spawn, drain, zero refused connections; `-t` catches syntax, not semantics
3. **Buffering, keepalive, and burst are the three defaults that bite** — each has a one-line fix and a story
4. **The proxy is the trust boundary** — TLS, limits, and header policy happen once at the edge
5. **Tool choice is a trade-off answer** — nginx edge / HAProxy throughput / Envoy dynamic / ALB managed, often layered

## Cheat Sheet

```text
MODEL:     master (config/ports/signals) + workers (event loop, epoll/kqueue)
COST:      KBs per connection, not MBs · worker_connections × cores = ceiling
POISON:    one blocking call stalls the worker's whole conn set → aio/sendfile/offload
CONTEXTS:  main → events → http → server → location (inherit ↓)
RELOAD:    nginx -t THEN nginx -s reload → new workers spawn, old drain, zero refused
TLS:       terminate at edge · one cert home · per-hop protocol freedom
BUFFERING: proxy_buffering on = slow-client armor · off ONLY for SSE/streaming
UPSTREAM:  keepalive N + proxy_http_version 1.1 + Connection "" (all three)
HEALTH:    passive max_fails/fail_timeout (OSS) · active = Plus/HAProxy/Envoy
LIMITS:    limit_req burst=N nodelay · limit_req_status 429 · watch rejections
WEBSOCKET: http/1.1 + Upgrade + Connection "upgrade" + read_timeout ↑
CHOICE:    nginx edge · HAProxy throughput · Envoy dynamic · ALB managed
```

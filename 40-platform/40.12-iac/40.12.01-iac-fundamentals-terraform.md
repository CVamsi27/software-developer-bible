# 40.12.01 — Infrastructure as Code & Terraform Fundamentals

A console change can make a service work today while leaving nobody able to reproduce it tomorrow. Infrastructure as code (IaC) records intended resources so changes can be reviewed and compared with observed infrastructure. The difficult part is preserving resource identity and controlling partial changes, not writing a long configuration file.

## Definition

**Infrastructure as code** manages infrastructure through machine-readable, versioned definitions. **Terraform** evaluates configuration written in HashiCorp Configuration Language (HCL), obtains resource information through provider plugins, and plans changes to managed resources.

> **Textbook Definition:** Infrastructure as code expresses infrastructure configuration as versioned, machine-readable specifications. Terraform uses desired configuration, recorded resource identities and provider observations to construct and execute a dependency-ordered change plan.

The three inputs are distinct:

| Input | Meaning | What it cannot prove |
| -------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Configuration | Desired resources and their relationships | That they already exist or serve traffic correctly |
| State | Terraform's recorded mapping from resource addresses to remote identities and attributes | That the remote system has not changed since observation |
| Provider observation | Values returned by a resource API during planning/refresh | Every application-level property or all changes after that read |

A **provider** implements resource operations against an API. A **backend** stores state and may supply locking. A **module** groups configuration with inputs and outputs. A **resource address**, such as `aws_s3_bucket.uploads`, identifies a managed declaration; its remote ID identifies the actual bucket.

## First Principles

An API object does not know which declaration created it. Terraform needs a persistent identity mapping to distinguish updating an existing object from creating a new one. Losing that mapping does not delete the remote object; it makes safe adoption/reconciliation necessary.

Two operators can read the same mapping and propose conflicting actions. Supported backend locks serialize Terraform operations on that state. They do not stop console edits, another state managing the same object, or later resource changes.

Resource APIs can fail after some operations succeed. Infrastructure changes are therefore not one all-or-nothing transaction. A plan makes intent reviewable, while post-failure observation and re-planning determine the next safe action.

## Why It Matters

A reviewed plan makes replacements and destructive actions visible before execution. Shared modules reduce repeated configuration, and recorded history helps explain intended changes. Rebuilding a database still requires its data backups; rolling source code back can itself plan destructive actions. Git history and provider/audit logs answer different questions.

## How Planning and Applying Work

1. **Initialize:** select the backend and install declared providers/modules. Commit the provider dependency lockfile and use explicit version constraints.
2. **Validate:** check configuration consistency. This does not establish account permissions, real availability or application readiness.
3. **Plan:** normally read remote resource values and compare them with configuration and recorded state. Review creates, updates and replacements, including dependent effects.
4. **Apply:** execute the selected plan and record reported results. A saved plan binds its planned actions and prior state; it is not a guarantee that external conditions remain unchanged.
5. **Verify:** inspect resource/API outcomes and service behavior. On failure, inspect what succeeded, recover state if needed and produce a new plan before retrying.

Terraform is invoked for a run; it is not automatically a continuously running reconciler. Scheduled drift plans or a managed run service add that behavior. Ordinary planning does not intentionally execute proposed resource changes, but uses credentials/APIs, backend locking and configured data evaluation. Do not call every configuration's planning behavior side-effect-free or cost-free.

## Example: Follow an Identity Without Creating Cloud Resources

This isolated teaching configuration uses Terraform's built-in `terraform_data` resource. It stores a value in local state and exercises the lifecycle; it does not create a server, call a cloud API or establish cloud-backend behavior. Use a new temporary directory with Terraform 1.4 or later.

```hcl
terraform {
  required_version = ">= 1.4, < 2.0"
}

variable "release" {
  type    = string
  default = "v1"
}

resource "terraform_data" "release" {
  input = var.release
}

output "recorded_release" {
  value = terraform_data.release.output
}
```

```bash
terraform init
terraform validate
terraform plan -out=plan.tfplan
terraform apply plan.tfplan
terraform plan -detailed-exitcode
# Exit 0: no planned difference. Exit 2: a difference. Exit 1: an error.
terraform plan -var='release=v2' -out=next.tfplan
terraform apply next.tfplan
```

The first plan creates one recorded resource. With unchanged inputs, the next plan has no difference. Changing `release` updates its stored input/output. Renaming `terraform_data.release` without an identity migration can propose removing the old address and adding a new one. For remote resources, that identity mistake can cause real destruction.

For a supported address refactor, declare a `moved` block and update references, then inspect the plan. For an existing unmanaged remote object, write matching configuration and import its ID; import alone does not establish the intended settings or a zero-change plan.

## Real-World Decisions

### Protect state and saved plans

Ordinary state and saved plans can contain credentials and sensitive values. A `sensitive` mark controls presentation; it does not generally remove stored values. A secret-manager lookup can also place its returned value into state. Use least privilege, encryption, protected backups and restricted artifact retention. Supported ephemeral values/write-only provider arguments can avoid some persistence, but verify the specific version and resource contract.

### Choose locking and isolation deliberately

For a current Terraform S3 backend, `use_lockfile = true` enables native state locking; it is not enabled merely by selecting S3. The documented DynamoDB lock mechanism is deprecated. Backend credentials, existing bucket/versioning, state and lockfile permissions must be supplied separately.

Separate state narrows the managed resource set, not the account permissions. A development run with production-capable credentials can still affect production. CLI workspaces select separate states under shared configuration/backend access; they are not strong access-isolation boundaries. Separate root configurations/backends and restricted roles may be appropriate. Reuse modules without concealing environment topology.

### Promote code, not an unrelated environment's saved plan

Use the same reviewed module version where compatible, but generate a plan against each target's state, inputs and permissions. Protect saved plans as sensitive artifacts; verify the target and reviewed revision before applying. Plan credentials often need backend lockfile writes, even when resource permissions are read-only. Do not execute untrusted pull-request configuration with privileged credentials.

`-target` restricts planning to a resource and its necessary dependencies. It does not inherently corrupt state, but can omit other desired changes and leave an incomplete overall reconciliation. Reserve it for a justified recovery case and follow it with a full plan. Force-unlock only after establishing that the original operation is no longer running.

### Compare tools by their model and support

Terraform and OpenTofu have related origins; check current language, backend, provider and state compatibility before migration. HCP Terraform supplies hosted run/state capabilities. Pulumi uses programming languages to declare managed resources; AWS CDK synthesizes CloudFormation templates. A general-purpose language does not make the resulting deployment imperative. Ansible mixes orchestration with declarative resource modules.

CDK for Terraform (CDKTF) was deprecated on 10 December 2025; HashiCorp no longer maintains it. Treat it as a migration concern for existing projects rather than a supported new-project choice. Choose tools from required resources, support, policy, licensing and team operation, not an assumed universal default.

## Mistakes

- Treating state as current remote truth or assuming a second apply must always be a no-op.
- Thinking a saved plan, import or successful apply proves the deployed service works.
- Using `sensitive = true` as evidence that state contains no secret.
- Sharing one object's ownership across independent states or controllers.
- Assuming state separation implies permission separation.
- Applying an old plan after a partial failure or unreviewed external change.

## Best Practices

Give each managed object a clear owner. Commit configuration and dependency locks, protect state/plans, review replacements, and test recovery as well as provisioning. Record the applied revision/target and verify actual service outcomes. Keep module compatibility promises tied to supported callers and meaningful plans, not only syntax checks.

## Summary

Terraform plans from desired configuration, recorded identities and provider observations. State preserves ownership; locks serialize supported state operations; neither removes external changes or partial failure. Safe operation needs reviewed intent, protected artifacts, target-specific permissions and observed results.

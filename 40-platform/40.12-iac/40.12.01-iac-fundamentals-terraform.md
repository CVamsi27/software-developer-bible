# 40.12.01 — Infrastructure as Code & Terraform Fundamentals

## Definition

**Infrastructure as Code:** managing infrastructure (networks, databases, compute, DNS, IAM) through machine-readable definition files instead of interactive configuration.

**Terraform** (HashiCorp, HCL — HashiCorp Configuration Language):

- **Providers** — plugins that translate Terraform's generic resource model into one cloud's API (AWS, GCP, Azure, Cloudflare, Kubernetes, and hundreds more).
- **Resources** — the atomic units of desired state: `aws_instance.web`, `aws_s3_bucket.data`, `cloudflare_dns_record.x`.
- **State** — a JSON record of what *currently exists*, mapping config to real resource IDs. Without state, Terraform cannot compute a diff.
- **Plan** — reads config + state, queries providers, and prints the exact changes (add/change/destroy) **without touching anything**.
- **Apply** — executes the plan. `terraform apply` shows the plan and asks for confirmation (or applies with `-auto-approve` in CI).
- **Backends** — where state lives: local file (dev only) or remote (S3 + DynamoDB lock, GCS, Terraform Cloud).

```hcl
# minimal example — an S3 bucket + Cloudflare DNS record
terraform {
  backend "s3" {
    bucket = "my-state-bucket"
    key    = "prod/network.tfstate"
    region = "ap-south-1"
  }
}

provider "aws" { region = "ap-south-1" }

resource "aws_s3_bucket" "data" {
  bucket = "my-app-data"
}

resource "cloudflare_dns_record" "app" {
  zone_id = var.zone_id
  name    = "api"
  content = aws_instance.app.public_ip
  type    = "A"
}
```

## First Principles

IaC applies software discipline to infrastructure: declarative state + plan/apply.

1. **The state file is the source of truth about *what exists*** — Terraform plans a diff between config and state; `apply` reconciles. The state's sensitivity (secrets inside!) and locking (concurrent applies) are the operational realities.
2. **Idempotence is the contract**: apply twice = second is a no-op — the same reconciliation loop (→ 40.2.1.01) with terraform as the controller.
3. **Modules are the reuse unit**; remote state + locking (S3+DynamoDB pattern) make it team-safe — infrastructure gets the same review/CI lifecycle as code (→ 40.3), which is the entire point.

## Why It Matters

| Without IaC | With IaC |
| ------------------------------------------- | ---------------------------------------------------------------- |
| Click-configured, undocumented environments | Every resource is code-reviewed in the same PR as the app change |
| \"It works on the staging box\" drift | Staging and prod are the same module with different variables |
| Rebuilding after an outage is archaeology | `terraform apply` recreates the environment from the repo |
| No one can say who changed what | Git history is the audit log |

**The interview one-liner:** \"IaC moves infrastructure from tribal knowledge to versioned code — same review, rollback, and reproducibility discipline as application code.\"

## How It Works

### 1. Declarative desired state

You describe the **end state**, not the steps. Terraform figures out the ordering (dependency graph), parallelism, and what to leave alone. Compare with imperative tools (older Ansible playbooks, shell scripts, CloudFormation's procedural cousin CDK) where you script *how*.

### 2. State and drift

State is the ground truth Terraform compares against. If someone edits a resource in the AWS console, `terraform plan` shows **drift** — the config wants X, reality is Y — and offers to revert it. This is both the superpower (self-healing) and the danger (state must never be edited by hand or lost; a lost state file orphans real resources).

### 3. Plan/apply as a safe gate

`plan` is free and read-only — CI runs it on every PR and posts the diff as a review artifact. A human (or policy engine like Sentinel/OPA) approves before `apply` mutates anything.

### 4. Modules = functions for infrastructure

A module is a reusable folder of resources with inputs (`variables`) and outputs. `modules/postgres` used five times = five databases with consistent settings.

### 5. Terraform Cloud / OpenTofu ecosystem

- **Terraform Cloud** — hosted state, locking, policy as code, run history.
- **OpenTofu** — open-source fork (2023) after HashiCorp's license change; API-compatible.
- **CDKTF** — write Terraform in TypeScript/Python instead of HCL.
- **Pulumi** — the main *non-Terraform* competitor: real programming languages + per-resource state; same declarative model.

## Code — The Core Commands

```bash
terraform init          # download providers, set up backend
terraform fmt           # canonical HCL formatting
terraform validate      # syntax + internal consistency
terraform plan -out=plan.tfplan   # compute diff, save it
terraform apply plan.tfplan        # apply the exact reviewed plan
terraform apply -auto-approve      # CI convenience (use with policy gates)
terraform destroy      # tear down (careful: removes real resources)
terraform state list   # what state knows exists
terraform import aws_instance.web i-123456  # adopt a console-created resource
terraform output db_endpoint   # read declared outputs
```

### CI/CD pattern (the senior answer)

```yaml
# every PR: read-only plan posted as a comment
- run: terraform plan -out=plan.tfplan
# on merge to main: apply with approval + Slack notify
- run: terraform apply plan.tfplan
```

**Key safety practices:** remote state + **state locking** (two applies must not race); `-target` only for emergencies (it breaks the dependency graph's guarantees); never store secrets in state (use variables + a secret manager; note state may contain them — restrict access); pin provider versions in `versions.tf`.

## Real-World Patterns

- **Environment promotion:** one module, three workspaces (`dev`/`staging`/`prod`) or three backend keys — prod gets the identical config that was reviewed on staging.
- **GitOps adjacency:** ArgoCD/Terraform Cloud runs apply from Git on merge — the repo remains the single source of truth (see the [40.3 CI/CD](../40.3-ci-cd/INDEX.md) and [40.2 Kubernetes](../40.2-kubernetes/INDEX.md) stacks for the K8s side).
- **Drift detection on a schedule:** periodic `plan` in CI catches console edits before they bite.
- **Brownfield adoption:** start with `terraform import` of the resources you already clicked together, then manage forward — never rebuild production to \"do IaC properly.\"

---

## Mistakes (that interviews love to hear you name)

1. **Storing state locally or in Git** — lost state = orphaned resources; concurrent applies = corruption. Always a remote backend with locking.
2. **Secrets in config or state** — `password = \"hunter2\"` in `main.tf` is now in Git history forever.
3. **Blind `apply` in production** — no plan review, no policy gate; a typo in a CIDR block takes down the network.
4. **Recreating instead of importing** — deleting a prod database \"because Terraform didn't know it\" is the cardinal sin.
5. **One giant monolith `main.tf`** — a 3,000-line file nobody reviews; split into modules and environments early.
6. **Drift blindness** — no scheduled plan; console edits silently diverge until an apply stomps them.
7. **`-target` as a habit** — targeted applies bypass Terraform's ordering guarantees and corrupt the state's consistency.

---

## Best Practices

- Remote state + locking from day one (S3 + DynamoDB, GCS, or Terraform Cloud).
- Modules with narrow surface: inputs validated, outputs minimal, no hidden side effects.
- Pin provider + Terraform versions; upgrade deliberately (`terraform providers lock`).
- Plan on every PR; apply on merge with approval; post the diff to the PR.
- Treat `terraform plan` output as the review artifact — require it for infra PRs.
- Separate state per environment (dev/staging/prod) so a bad dev apply can't touch prod.
- Use workspaces or backend keys for environments, not copy-pasted directories.

---

## Summary

- IaC = infrastructure declared as reviewable, versioned code.
- Terraform = declarative desired state + **state file** + **plan/apply** diff loop.
- The three interview pillars: *state & drift*, *declarative vs imperative*, *safe change (plan before apply)*.
- Alternatives to name-drop: OpenTofu (OSS fork), Pulumi (real languages), CDKTF, Ansible (config mgmt, imperative), CloudFormation (AWS-only).

# 40.12.01 — Infrastructure as Code & Terraform Fundamentals

A Terraform plan proposes replacing a database after someone renames a resource block. The database still exists, but Terraform no longer sees its old address in the configuration. To decide whether the plan is safe, you need to know how configuration, state, and remote observations establish resource identity — and why an apply is not one all-or-nothing transaction.

## Definition

**Infrastructure as code (IaC)** manages infrastructure through versioned, machine-readable definitions and operations. Tools may declare a desired outcome or sequence imperative steps. **Terraform** usually uses HashiCorp Configuration Language (HCL) to declare desired resources, then uses provider plugins to observe and manage them through service application programming interfaces (APIs).

> **Textbook Definition:** Infrastructure as code is the practice of managing infrastructure through version-controlled, machine-readable definitions. Declarative tools specify desired resources; Terraform combines its configuration with state bindings and provider observations to build a dependency graph and plan resource creation, updates, and destruction.

A **resource address**, such as `aws_s3_bucket.uploads`, names a managed declaration in configuration. Its remote identifier (ID) identifies the actual bucket in the provider's system. A **provider** implements reads and writes for a service's API; a **backend** stores state and may support locking; a **module** is a reusable collection of configuration with inputs and outputs.

## First Principles

A provider API identifies a cloud object by its remote ID; Terraform configuration identifies it by a resource address. Without a saved binding between the two, Terraform cannot reliably know whether the next declaration updates an existing object or asks to create another. State preserves that identity across runs. Identity alone does not make changes safe: resource references establish operation order, a backend lock serializes supported Terraform runs, and a reviewed plan makes intended actions visible. Remote APIs can still partially succeed, so none of these turns an apply into an atomic transaction.

## How It Works

### 1. Reconcile Three Inputs: Configuration, State, Observations

Terraform cannot infer which declaration owns a remote object from that object alone. It records a binding between the resource address and the remote ID, then compares the recorded view with the configuration and provider observations:

| Input | What it contributes | Its limit |
| --------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Configuration | Desired resources, arguments, and relationships | Does not prove an object exists or that a service is ready |
| State | Resource-address-to-remote-ID bindings and recorded attributes | Can lag behind an out-of-band change or a failed operation |
| Provider observations | Values the provider reads from the remote API during planning | Cover only what was read; they do not prove every application behavior or later change |

Terraform builds a dependency graph from references between resources and explicit ordering constraints. It uses that graph to order operations; independent work can run concurrently. The graph is an execution order, not a transaction. A cloud API can accept some operations and reject a later one, leaving a partial result that must be inspected.

### 2. Move Configuration to a Reviewed Change

A normal workflow follows the same sequence locally and in automation:

1. **Initialize:** `terraform init` configures the selected backend and installs provider and module dependencies. Commit `.terraform.lock.hcl` to record selected provider versions and checksums. It does not lock module versions, so constrain module sources separately.
2. **Validate:** `terraform validate` checks internal configuration consistency. It does not prove cloud permissions, quota, resource availability, network reachability, or application readiness.
3. **Plan:** Terraform reads state, normally refreshes managed resources through providers, compares observations with configuration, and calculates proposed actions. A provider may require replacement when a field cannot be changed in place. A plan can show values as known only after apply when they depend on an operation that has not run. Planning does not execute proposed resource changes, but it does make API/data-source reads and backend operations; cost and side effects depend on those integrations.
4. **Review:** inspect creates, updates, deletions, replacements, unknown values, target account, region, state, and input revision. A saved plan file contains the configuration and planned values, including potentially sensitive data. Treat it as a secret-bearing deployment artifact.
5. **Apply:** applying a saved plan executes those reviewed actions without prompting again. If the recorded state has changed, Terraform can reject the plan as stale. An external change that occurs after planning may not be detected before execution, so protect the interval between review and apply and regenerate the final plan when its assumptions no longer hold.
6. **Verify:** inspect provider results and the service itself. An API reporting success does not establish that routes, permissions, data, or readiness work for users.

Running `terraform apply` without a saved plan first creates a fresh plan and asks for approval interactively. Automation commonly separates planning and applying so people or policy checks can review the exact artifact. `terraform plan -detailed-exitcode` returns 0 for no changes, 2 for a proposed difference, and 1 for an error; account for these values explicitly in CI.

Terraform's command-line interface (CLI) runs when invoked or when a run service schedules it; it is not a continuously running reconciler. GitOps controllers such as Argo CD or Flux do reconcile continuously. Define one owner for each resource or field so Terraform and a controller do not continually overwrite one another.

### 3. Trace One Resource Without Creating Cloud Infrastructure

This example uses Terraform's built-in `terraform_data` resource. It exercises the normal resource lifecycle using local state; it does not create a server, call a cloud provider, or demonstrate remote backend locking. Run it in a new temporary directory with Terraform 1.4 or later:

    terraform {
      required_version = ">= 1.4, < 2.0"
    }

    variable "release" {
      type    = string
      default = "v1"
    }

    resource "terraform_data" "release" {
      input = var.release
    }

    output "recorded_release" {
      value = terraform_data.release.output
    }

Run the lifecycle and then change the variable:

    terraform init
    terraform validate
    terraform plan -out=plan.tfplan
    terraform apply plan.tfplan
    terraform plan -detailed-exitcode
    terraform plan -var='release=v2' -out=next.tfplan
    terraform apply next.tfplan

The first plan proposes one resource; apply creates its state binding. With no configuration changes, the next plan returns 0. Changing `release` updates the stored input and output. Renaming `terraform_data.release` changes its resource address; Terraform can interpret that as removing one instance and creating another. In cloud configuration, the same address mistake can propose a destructive replacement.

For an intentional rename, a `moved` block declares the old and new addresses so Terraform can preserve the binding. For an unmanaged remote object, import its existing ID, write configuration that matches the intended settings, then review the resulting plan. Import records identity; it does not establish that the object already matches the declaration.

### 4. Protect Identity, State, and Access

State is operational data, not disposable cache. It may contain resource attributes and secret values, and Terraform expects one managed address to correspond to one remote object. Do not edit the serialized state file by hand or let independent states and controllers claim the same object. Use Terraform's state commands or supported `moved` and `import` blocks for ownership changes, and preserve secure backups for recovery.

For team work, store state in a remote backend or HCP Terraform, and configure encryption, access controls, versioned recovery, and supported locking. A lock serializes Terraform operations using that state; it does not block console edits, a second state managing the same object, or an operator with direct provider credentials. Force-unlock only after proving that the original operation has ended and that the lock is genuinely stale.

Amazon Simple Storage Service (S3) backend locking is opt-in: configure `use_lockfile = true`, plus the required permissions on the state object and lock file. DynamoDB-based S3 locking is deprecated. Selecting S3 alone does not turn locking on. Local state can be appropriate for an isolated exercise, but it is not a sound shared-team collaboration model.

Environment separation needs both state boundaries and permission boundaries. CLI workspaces select distinct state instances under shared configuration and backend access; they are not a strong security boundary. Separate root configurations/backends and restricted roles when production needs different approvals, permissions, or topology. A development job holding production-capable credentials can still change production even when it selects a development workspace. Continuous Integration (CI) jobs should run privileged plans only for trusted revisions, use short-lived credentials where available, and bind approval to the target and exact plan being applied.

A saved plan is also sensitive. The `sensitive` flag redacts values in command output and the hosted UI, but values can remain in state and plan files. Ephemeral variables/outputs and provider write-only arguments can omit supported values from those files, subject to version and context restrictions. Use them where available, but still protect state and plans and keep credentials short-lived and least-privileged.

### 5. Reuse Modules Without Hiding the Environment

A module packages resources and configuration behind a deliberate input/output interface. Reuse it when environments share a real contract; keep environment-specific account, region, network, and data decisions visible in the root configuration. Declare and review module version constraints; use an exact version or immutable source revision when reproducible dependency selection is required. Provider lockfiles do not pin module sources.

Use `-target` only for a justified recovery or exceptional operation. It deliberately narrows planning to selected resources and dependencies, so it can leave unrelated desired changes unapplied. Follow a targeted operation with a complete plan. For critical modules, test input/output contracts, validate supported caller configurations, review meaningful plan changes, and exercise integration and recovery in an isolated account.

Compare tools against their actual operating model. Terraform and OpenTofu have related origins, but language, provider, licensing, backend, and state compatibility still need verification before migration. Pulumi declares managed resources through programming languages; the Amazon Web Services (AWS) Cloud Development Kit (CDK) synthesizes CloudFormation templates. HashiCorp Cloud Platform (HCP) Terraform adds hosted state and run workflows. CDK for Terraform (CDKTF) was deprecated on 10 December 2025 and is no longer maintained; treat existing use as a migration/support decision, not a new-project recommendation.

## Summary

Terraform compares desired configuration with state bindings and provider observations, then builds a dependency-ordered plan. State preserves identity; locks serialize supported operations; neither makes infrastructure changes atomic or prevents out-of-band edits. Review the target and destructive actions, protect state and saved plans, recover from partial results deliberately, and verify the running service after apply.

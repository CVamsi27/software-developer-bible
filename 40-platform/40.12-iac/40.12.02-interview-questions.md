# 40.12.02 — IaC & Terraform Interview Questions

> Practice state, plan/apply, locking, module contracts, environment separation, drift, adoption and tool choice. Trace each operation and its failure boundary; the prompts do not predict a particular interview.

## First Principles

This set probes state/reconciliation (→ 40.12.01): plan/apply, drift, and module design.

1. **The senior tells are trade-off statements**: "X when Y, Z when not-Y" — juniors memorize answers; seniors recite the *conditions* under which each answer is right.
2. **Every question here maps to an axiom chain, not a fact** — if you can derive the answer from the linked chapters, you can answer the variant questions too (that's the point of → First Principles sections).

## Answer Framework

```text
ANSWER STRUCTURE:
  1. The principle (declarative desired-state vs imperative steps)
  2. The mechanism (state → plan → apply loop, where the diff comes from)
  3. The failure mode you're guarding (drift, locking, secrets, blast radius)
  4. The operational answer (backends, CI gates, review, rollback)
  5. The trade-off (when NOT to use it / what it doesn't solve)
```

## Beginner

**Q1: What is Infrastructure as Code, and why does it matter?**

**Answer:** Infrastructure as code (IaC) records intended infrastructure as versioned, reviewable configuration and operations. Reproduction depends on providers, credentials, available resources and data recovery; replaying configuration alone does not restore database contents. Declarative reconciliation is one IaC approach, not the definition of every IaC tool.

**Q2: Declarative vs imperative provisioning — what's the difference, and when would you use each?**

**Answer:** Declarative tools derive actions from desired resources and observations; imperative scripts specify steps. The Amazon Web Services Cloud Development Kit (AWS CDK) uses programming languages to synthesize declarative CloudFormation templates. Ansible modules can declare desired state inside ordered playbooks. Choose by resource support and operational contract rather than the language syntax.

**Q3: What is Terraform state? Why is it needed, and what can go wrong?**

**Answer:** State maps Terraform addresses to remote identities and recorded attributes. It is not current remote truth; normal planning refreshes through providers. Lost state does not delete objects but can cause unsafe duplicate creation or replacement assumptions. Protect backups/access, lock supported operations and recover/import ownership before applying.

**Q4: What does `terraform plan` actually do?**

**Answer:** A normal `terraform plan` evaluates configuration, refreshes provider observations and proposes creates, updates, deletes and replacements. It does not execute those proposed resource actions, but can make provider reads and backend writes. Saved plans contain configuration and planned values, including sensitive data, and can be rejected if the state changed; an external edit after planning may still affect execution.

## Intermediate

**Q5: Walk through a safe Terraform workflow in continuous integration and delivery (CI/CD).**

**Answer:** Use a trusted configuration revision, target-specific credentials and protected state/plan artifacts. Plan and review replacements, then apply the reviewed plan under a supported lock and approval gate. Resource-read-only planning may still need backend lock writes. An untrusted pull-request configuration must not receive privileged credentials. Verify provider and service outcomes after execution.

**Q6: How do you manage multiple environments (dev/staging/prod) with Terraform?**

**Answer:** Reuse versioned modules while selecting each environment's own inputs, state and restricted role. CLI workspaces share configuration/backend access and are not strong security isolation. Separate root configurations/backends can make divergent topology and permissions explicit. Generate a target-specific plan; never apply a staging state plan to production.

**Q7: What are Terraform modules, and what makes a good one?**

**Answer:** A module is a collection of resource configuration with a caller-facing input/output contract. Keep that interface small and validated, expose the values callers actually need, and make environment-specific account/region choices visible in the root module. Version shared modules and test their callers; avoid a single module that hides unrelated lifecycle ownership.

**Q8: What is drift, and how do you handle it?**

**Answer:** Drift is a difference between intended configuration and provider-observed attributes. Some attributes are ignored/computed, and planning does not prove every service behavior. Decide whether a change is temporary or intended; update configuration or apply a reviewed correction. Import is for adopting a remote identity, not simply recording every attribute change.

**Q9: How does IaC fit with Kubernetes manifests and GitOps (ArgoCD/Flux)?**

**Answer:** GitOps means reconciling deployed resources from version-controlled desired configuration. Define one owner per object or field. Terraform may provision clusters and shared dependencies while GitOps manages application objects, but either tool can own objects on either side of that line. Avoid Terraform and a continuously reconciling controller fighting over the same fields.

## Advanced

**Q10: How would you adopt Terraform on an existing environment that was built by hand?**

**Answer (brownfield):** Preserve existing resources and define the matching Terraform resource configuration before adopting them. Use reviewed `import` blocks or the CLI import command, one ownership boundary at a time. The first plan may propose updates if configuration does not match observed attributes; inspect and reconcile those before applying. Freeze or coordinate concurrent changes during adoption, and verify each subsystem before moving on. Import does not make all future changes flow through code unless permissions and operating policy enforce that boundary.

**Q11: Terraform vs Pulumi vs CloudFormation vs OpenTofu — how do you choose?**

**Answer:** Compare required resources, provider/support lifecycle, licensing, state compatibility, policy, team skills and operating costs. Terraform/OpenTofu have related origins, not a universal future compatibility guarantee. Pulumi and AWS CDK use languages to describe managed resources; CDK produces CloudFormation. Current CDKTF is deprecated, so existing use needs a support/migration decision.

**Q12: A teammate hand-edits a resource in the console, then a `plan` wants to destroy it. What do you do?**

**Answer:** Stop and identify the intended change and affected dependencies, especially replacements of durable resources. An emergency change may need to remain until a reviewed compatible fix exists. Update intended configuration or plan a deliberate correction; do not assume reverting the console change is safe merely because it was temporary.

**Q13: How do you handle secrets and blast radius in Terraform?**

**Answer:** Ordinary state and saved plans can contain sensitive values, including values read from a secret manager. The `sensitive` mark redacts presentation, not storage. Restrict access, encrypt and back up the files; use supported ephemeral/write-only paths when their restrictions fit. Separate state narrows managed resources, but only credentials and policy constrain cross-environment access.

## Behavioral & Scenario Drills

**Q14 (behavioral): Tell me about a time infrastructure broke because it wasn't code.**

**Answer:** Use your actual incident and observed outcome. An illustrative outline: find a relevant staging/production mismatch, record intended configuration, add a targeted drift/integration check and measure recurrence. Sharing a module does not make every environment identical or eliminate every drift source.

**Q15 (scenario): An apply fails halfway — a virtual private cloud (VPC) was created, but its subnets were not. What now?**

**Answer:** Inspect the returned failure, remote objects and persisted state. Terraform records reported successes where it can, but a crash after remote creation and before recording can leave an uncertain orphan. Fix the cause, recover/import any missing identity, re-plan and review before retrying. Apply is not an atomic transaction or an automatic rollback.

**Q16 (follow-up trap): "So IaC means no one ever touches the console again?"**

**Answer (the nuanced answer they want):** The goal is that *durable, versioned infrastructure* only changes through code. But there are legitimate console uses: emergency mitigation while a fix ships through review (then reconciled via code), read-only debugging, and throwaway environments. The discipline is classifying console actions as temporary and always converging back to the declared state — the console is for inspecting and emergency-braking, not for permanent configuration.

## Senior: Scale & Discipline

**Q17: What does state locking actually prevent, and what is the force-unlock discipline?**

**Answer:** A supported lock serializes Terraform operations against one state. It does not block console changes or another state managing the same object. Current S3 native use_lockfile locking is opt-in; DynamoDB locking is deprecated. For force-unlock, establish that the owner has stopped, then inspect interrupted effects/state and produce a fresh plan.

**Q18: Workspaces, directories per environment, or Terragrunt — how do you lay out multi-environment Terraform?**

**Answer:** Workspaces keep one configuration and backend with separate state instances; they are simplest when environments genuinely share topology and access policy. Separate root directories with shared modules make divergent permissions and topology explicit, at the cost of more configuration. Terragrunt or another wrapper can reduce repeated backend/dependency wiring, but adds another tool and abstraction. Choose from environment differences, team size and review requirements. DRY means “Don't Repeat Yourself.”

**Q19: How do you pin provider versions, and when do you upgrade?**

**Answer:** Declare provider constraints and commit `.terraform.lock.hcl` to record selected provider versions/checksums. `~> 5.0` allows 5.x minor updates; `~> 5.0.0` permits 5.0 patch updates. The lockfile does not pin remote modules, so constrain their versions or revisions separately. Upgrade dependencies intentionally, inspect plans and test target behavior; a provider constraint alone does not select a reproducible version.

**Q20: How do you refactor Terraform resources without destroying them?**

**Answer:** Resource addresses are state identities. Rename or move through supported moved blocks, then inspect the full plan and references. state mv is a controlled state operation when a declarative migration is unsuitable. Import adopts an unmanaged identity. A zero-destroy plan helps review the identity refactor but does not prove every provider/API behavior.

**Q21: count vs for_each — what is the identity trap?**

**Answer:** count identifies by index; for_each identifies by stable map/set key. Inserting into a positional list can change attributes at later indexes and cause updates or replacements according to the resource schema, not necessarily destruction in every case. Choose stable keys when identity follows a member and plan explicit moves during migration.

**Q22: How do you test infrastructure code?**

**Answer:** Use static validation/lint/policy, plan assertions for supported callers, and isolated integration with real APIs and cleanup for critical behavior. Terraform test can exercise module contracts. A plan count is useful evidence, not complete correctness; permissions, propagation, readiness and destructive recovery need appropriate checks.

**Q23: How do you structure Terraform across many accounts and regions?**

**Answer:** Separate states and roles by real ownership/blast-radius boundaries; define dependency direction and avoid cycles. Publishing necessary outputs explicitly can restrict access better than broad remote-state access, which may permit reading the entire state snapshot. State separation does not by itself prevent an account-authorized apply affecting other resources.

**Q24: What is the versioning contract for a shared Terraform module?**

**Answer:** Specify a module's supported inputs, outputs and resource behavior, then use semantic versions with migration notes. A compatible additive input is optional/defaulted; a breaking behavior/address change needs explicit migration even if syntax compiles. Patch changes can alter plans while fixing a bug, so do not promise that all patch diffs are empty. Pin module releases and test supported caller configurations.

**Q25 (behavioral): Tell me about a plan that almost destroyed something — how was it caught?**

**Answer:** Use a real near-miss: identify a replacement in the plan, explain its provider cause, compare intended state/data recovery and record the check that prevented unsafe execution. A renamed input may alter behavior but does not automatically replace a database. A protected-resource policy/approval exception must inspect the actual planned actions and authorized owner.

## Summary

1. **State is Terraform's identity mapping** — protect it, lock supported operations, and keep one owner per remote object
2. **Plan/apply is a review boundary** — apply the reviewed target-specific actions and verify the service outcome
3. **Modules make infrastructure composable** — versioned, reusable abstractions over provider resources
4. **Drift detection has limits** — normal plans reveal provider-readable differences; update configuration or deliberately reconcile the remote object
5. **Interviews test the workflow, not syntax** — change → plan → review → apply → verify, and what breaks at each step

# 40.12.02 — IaC & Terraform Interview Questions

> Senior-depth IaC & Terraform questions — grouped by difficulty, each with a short answer, the deeper senior reasoning, and the follow-up interviewers actually ask. Covers the full surface: state, plan/apply, backends & locking, modules, workspaces, drift, brownfield, policy-as-code, GitOps, and tool choice.

## Answer Framework

```text
ANSWER STRUCTURE:
  1. The principle (declarative desired-state vs imperative steps)
  2. The mechanism (state → plan → apply loop, where the diff comes from)
  3. The failure mode you're guarding (drift, locking, secrets, blast radius)
  4. The operational answer (backends, CI gates, review, rollback)
  5. The trade-off (when NOT to use it / what it doesn't solve)
```

## Beginner

**Q1: What is Infrastructure as Code, and why does it matter?**

**Short answer:** Infrastructure as Code is managing infrastructure through versioned, reviewable definition files instead of interactive consoles. It matters because environments become reproducible (same code → same infra), reviewable (Git PRs instead of clicks), and recoverable (rebuild from the repo, not from memory).

**Go deeper (senior):** "The shift is from *procedures* to *declarations*. The old model was a runbook — step 1 click this, step 2 edit that. IaC is a specification — this is the desired state — and the tool reconciles reality to it. That turns infrastructure changes into the same code-review, rollback, and audit workflow as application changes."

**Q2: Declarative vs imperative provisioning — what's the difference, and when would you use each?**

**Answer:** Declarative (Terraform, CloudFormation, Kubernetes manifests) states *what* you want; the tool derives the steps and handles ordering and idempotency. Imperative (shell scripts, most Ansible playbooks, CDK code with explicit steps) states *how* — precise control, but you own ordering, idempotency, and cleanup. Use declarative for long-lived infrastructure where drift and repeatability matter; imperative for one-off bootstrap steps or things declarative tools model poorly.

**Q3: What is Terraform state? Why is it needed, and what can go wrong?**

**Answer:** State is Terraform's record of what currently exists — it maps config declarations to real resource IDs and attributes. It's needed because Terraform computes a diff: it can't know what to change without knowing what's already there. If state is lost or stale, Terraform either tries to recreate existing resources or misses real ones.

**Dangers to name:** local-only state (lost or corrupted), no locking (two concurrent applies race), state containing secrets, state out of sync with reality (drift). **Mitigations:** remote backend with locking, per-environment state, secrets out of state, scheduled plans to detect drift.

**Q4: What does `terraform plan` actually do?**

**Answer:** Plan reads the current state, builds a graph of the resources your config declares, and computes the set of create/update/delete actions needed to move reality to the declared state — *without applying anything*. It's Terraform's dry-run: you review the diff (additions, changes, and especially **destructions**) before any mutation. `-destroy` shows what a full teardown would do; `-out` pins the exact plan for a later `apply`.

## Intermediate

**Q5: Walk through a safe Terraform workflow in CI/CD.**

**Answer:** Pull requests run `terraform plan` and post the diff as a review comment — read-only, with credentials that can't mutate. Merge to main triggers apply with an approval step, policy-as-code gates (Sentinel/OPA) layered on top of human review, state locked so applies serialize, and a Slack/audit notification on every apply. Secrets come from a secret manager at apply time, never from config or plan output.

**Q6: How do you manage multiple environments (dev/staging/prod) with Terraform?**

**Answer:** One module set, instantiated per environment — either workspaces (one backend, multiple states) or separate backend keys per environment. Same reviewed code promoted up; variables (`env`, region, sizes) are the only difference. Prod should use a stricter apply gate (approval + policy) than dev. Never copy-paste directories per environment — that recreates the drift problem inside IaC.

**Q7: What are Terraform modules, and what makes a good one?**

**Answer:** A module is a reusable, parameterized folder of resources — functions for infrastructure. Good modules: small surface (clear inputs with validation, minimal outputs), no hardcoded environment values, versioned and reused across environments, compose into larger modules. Bad modules: 400 lines doing everything, hidden side effects, inputs that bypass defaults silently.

**Q8: What is drift, and how do you handle it?**

**Answer:** Drift is the difference between declared config and actual infrastructure — usually from console edits, manual hotfixes, or failed applies. Terraform surfaces it on the next `plan`. Handling: scheduled plan jobs in CI as a canary, decide per resource whether to reconcile (apply reverts the drift) or import the change (update config to match reality). The cardinal rule: never let drift accumulate silently until an unrelated apply stomps it.

**Q9: How does IaC fit with Kubernetes manifests and GitOps (ArgoCD/Flux)?**

**Answer:** They're the same philosophy at different layers. Terraform provisions the *cluster and its dependencies* (VPC, node pools, DNS, IAM). Inside the cluster, Kubernetes YAML is declarative desired state reconciled by controllers, and GitOps (ArgoCD/Flux) makes Git the source of truth that the cluster continuously reconciles to. The pattern is: *Terraform owns what's outside the cluster; GitOps owns what's inside; both are code-reviewed manifests.*

## Advanced

**Q10: How would you adopt Terraform on an existing environment that was built by hand?**

**Answer (brownfield):** "The wrong move is deleting and recreating to 'be clean.' The right move is `terraform import` — adopt each existing resource into state with its real ID, wrap them in modules as the config grows, and run a first `plan` that should show zero changes. From that point, all changes flow through code. I'd do it incrementally by subsystem and keep a parallel console-freeze during the transition so state doesn't drift mid-adoption."

**Q11: Terraform vs Pulumi vs CloudFormation vs OpenTofu — how do you choose?**

**Answer:** Terraform is the default: broadest provider ecosystem and team familiarity. Pulumi wins when your team wants real languages (typed, testable, loops/conditionals without HCL gymnastics) and per-resource state. CloudFormation only if you're all-in on AWS (native drift detection, StackSets). OpenTofu for license-policy reasons — it's API-compatible with Terraform. The honest answer for most teams: Terraform or OpenTofu unless you have a specific reason for Pulumi's programmability.

**Q12: A teammate hand-edits a resource in the console, then a `plan` wants to destroy it. What do you do?**

**Answer (scenario):** Don't apply blindly. Decide intent first: if the console edit was a *temporary hotfix*, let the plan reconcile it away (apply reverts). If it was a *legitimate change that should persist*, update the config to match reality first, then plan again — the diff disappears and the change is now owned by code. The interview signal is refusing to either "just apply" or "just revert" without classifying the drift, and putting the fix in place (scheduled drift plans + console-freeze policy) so it doesn't recur.

**Q13: How do you handle secrets and blast radius in Terraform?**

**Answer:** Never store secrets in state or config — state is plaintext by default, so use a remote backend with encryption at rest, keep state access locked down (state holds resource metadata and any values passed as variables), and reference secrets from a secret manager (Vault, AWS SSM/Secrets Manager) at plan/apply time. Blast radius: per-environment backends and state files (a prod apply can never touch dev state), `moved`/`import` blocks over delete-recreate, and plan review that flags any `-/+` replace on stateful resources (databases, disks) before apply.

## Behavioral & Scenario Drills

**Q14 (behavioral): Tell me about a time infrastructure broke because it wasn't code.**

**Story to tell (structure: situation → task → action → result):** A staging environment that was click-configured drifted from production; a "quick console change" made staging behave differently and a bug shipped. The fix: move both environments under Terraform with the same module, add a scheduled drift plan, and make infra changes reviewable PRs. Result: staging and prod converged and the class of bug disappeared.

**Q15 (scenario): An apply fails halfway — the VPC is created but the subnets aren't. What now?**

**Answer:** Terraform's behavior here is the point of the question: it persists whatever succeeded into state, so a retry after fixing the error *continues from where it stopped* rather than restarting — that's the idempotency that declarative tools buy you. What you don't do is hand-create the missing pieces in the console (that re-introduces drift). Fix the root cause (often a transient provider error, an IAM permission, or a race), re-plan to confirm only the remaining resources are in the diff, and re-apply.

**Q16 (follow-up trap): "So IaC means no one ever touches the console again?"**

**Answer (the nuanced answer they want):** The goal is that *durable, versioned infrastructure* only changes through code. But there are legitimate console uses: emergency mitigation while a fix ships through review (then reconciled via code), read-only debugging, and throwaway environments. The discipline is classifying console actions as temporary and always converging back to the declared state — the console is for inspecting and emergency-braking, not for permanent configuration.

## Cheat Sheet

```text
STATE:     map of declarations → real resource IDs; remote backend + locking + encryption
LOOP:      init → validate → plan (review diff, watch for -/+ destroys) → apply → state update
DRIFT:     console edit or failed apply → next plan shows it → reconcile (revert) or import (adopt)
ENVS:      one module set, per-env backend keys or workspaces, stricter prod apply gate
MODULES:   small surface, validated inputs, minimal outputs, versioned, no hardcoded env
BROWNFIELD: terraform import existing resources first → zero-change plan → code-owned after
CI SAFETY: plan in PR (read-only), apply on merge with approval + policy gate + lock + audit
LAYERS:    Terraform owns outside the cluster; GitOps (ArgoCD/Flux) owns inside
CHOICE:    Terraform/OpenTofu default; Pulumi for real-language teams; CFN only all-in AWS
SECRETS:   never in state/config → secret manager at apply time; state encrypted + access-locked
```

# Kubernetes Pods & ReplicaSets

## Definition

A **Pod** is the smallest unit Kubernetes schedules. Its containers run together and share a network identity and any configured volumes. A **ReplicaSet** maintains the desired number of matching Pods by creating replacements when needed. A Pod can disappear; the ReplicaSet keeps trying to restore the requested count.

> **Textbook Definition:** A Kubernetes Pod is a scheduling unit of colocated containers sharing a network namespace and configured storage. A ReplicaSet reconciles a label-selected Pod population to a desired replica count.

Key concepts:

- **Pod**: Co-scheduled containers sharing a network namespace and only the volumes mounted into them
- **ReplicaSet**: Maintains stable set of replica Pods
- **Labels**: Key-value pairs attached to Pods for selection
- **Selectors**: Query mechanism to filter Pods by labels
- **Namespace**: Scope for names and selected policies on namespaced objects; it is not a security boundary by itself

## First Principles

A container's process can crash, and an entire machine can disappear. Restarting a process on the same machine addresses one failure; requesting a replacement on another machine addresses a different failure. Kubernetes therefore separates node-local container recovery from a workload controller's responsibility to maintain a population.

Containers that need localhost communication or a tightly coordinated lifecycle can share a Pod. Sharing files still requires a volume mounted into both containers. Independent replicas instead need separate Pods so the scheduler can place them on different nodes. An existing Pod is assigned to one node; replacement creates a new Pod, rather than moving the same object between nodes.

Labels give controllers a way to identify the population they own. A ReplicaSet combines a selector, a template for missing members, and a desired count. The Deployment above it owns template revisions and rollout, while the ReplicaSet owns population reconciliation.

## Why Do We Need It?

| Problem | Solution |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| Tightly coupled helper processes | Containers in one Pod share networking, explicitly mounted volumes, and a lifecycle boundary |
| Manual scaling | ReplicaSet maintains replica count |
| Restoring a replica count | A ReplicaSet creates replacement Pods for its managed population |
| Changing replica addresses | Services/DNS provide discovery over eligible Pod endpoints |
| Resource management | Container requests guide scheduling; container limits constrain runtime use |
| Deployment strategy | Deployment coordinates old/new ReplicaSets |

By default, set resource requests and limits on each container. The scheduler uses the Pod's effective requests when placing it, while the kubelet enforces configured limits: a CPU limit can throttle execution, and a memory limit can lead to OOM termination. Kubernetes 1.37 also supports beta Pod-level requests and limits for CPU, memory, and hugepages; `PodLevelResources` has been beta and enabled by default since 1.34, though a cluster can disable the feature gate. The examples use per-container resources for broader compatibility.

## How It Works

### A Pod shares one placement and selected resources

```text
one chosen node
  Pod (one network namespace / Pod address)
    app:8080 <-> localhost <-> helper:9090
       |                           |
       +------ mounted volume -----+
```

Both containers run on that one node and must avoid binding the same address/port. Each has its own filesystem unless a volume is explicitly mounted into both. A shared Pod does not automatically share every file or the process namespace; process sharing is separately configurable. `emptyDir` survives container restarts within the Pod but disappears when that Pod is removed.

### Reconciliation replaces members, not process memory

```text
ReplicaSet: desired=3, selector app=myapp
  observed matching population=2
    -> API request for a third Pod from the template
    -> admission -> scheduler chooses node -> kubelet starts containers
    -> readiness may eventually add useful service capacity
```

If a container exits and the Pod's restart policy allows it, the kubelet can restart that container in the same Pod. If the Pod is deleted or becomes a terminal failed member, a ReplicaSet can create a new Pod with a new object identity/address. It does not restore the old process's memory or guarantee replacement readiness. A running but unhealthy member can still count toward population while readiness/liveness handle different decisions.

A selector can also match an existing unowned Pod, which the ReplicaSet may adopt. Keep controller selectors distinct and avoid overlapping owners. Run the recipes below separately in a test namespace; applying a bare `app=myapp` Pod beside the ReplicaSet is an adoption experiment, not an extra guaranteed fourth replica.

## Code Examples

Replace application images with ones that implement the stated ports, commands, and endpoints. `containerPort` documents a port in the Pod spec; it does not make the process listen or publish the port outside the Pod. Secret, ConfigMap, and claim references must exist in the same namespace. These manifests describe different scenarios; they are not cumulative steps to apply together. For reproducible production releases, pin images by digest and update them through an explicit process.


### Basic Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: myapp
    environment: production
spec:
  containers:

    - name: myapp
      image: myapp:1.0.0
      ports:

        - containerPort: 8080
      resources:
        requests:
          memory: "128Mi"
          cpu: "250m"
        limits:
          memory: "256Mi"
          cpu: "500m"

```

### Multi-Container Pod (Sidecar Pattern)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-with-sidecar
spec:
  containers:

    - name: app
      image: myapp:1.0.0
      ports:

        - containerPort: 8080
      volumeMounts:
        - name: app-logs
          mountPath: /var/log/app

    - name: log-shipper
      image: fluent/fluentd:v1.19.3-debian
      volumeMounts:

        - name: app-logs
          mountPath: /var/log/app

    - name: metrics
      image: prom/prometheus:v3.15.0
      ports:

        - containerPort: 9090

  volumes:

    - name: app-logs
      emptyDir: {}

```

The application must actually write logs into the mounted directory, and Fluentd needs a configuration that tails them and exports them to the chosen sink. The Prometheus container also needs scrape configuration; adding its image does not automatically expose application metrics. Sidecars share the Pod lifecycle, so choose this placement only for helpers that must accompany each application instance.

### ReplicaSet

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-rs
  labels:
    app: myapp
    environment: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        environment: production
    spec:
      containers:

        - name: myapp
          image: myapp:1.0.0
          ports:

            - containerPort: 8080
          resources:
            requests:
              memory: "128Mi"
              cpu: "250m"
            limits:
              memory: "256Mi"
              cpu: "500m"

```

After applying the ReplicaSet, deleting one of its managed Pods asks the controller to recreate a member from this template. Editing the template alone does not roll existing Pods to the new image; use a Deployment for revision transitions.

### Pod Lifecycle

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-lifecycle
spec:
  initContainers:

    - name: init-db
      image: busybox
      command: ['sh', '-c', 'until nslookup mydb; do echo waiting for mydb; sleep 2; done']

  containers:

    - name: myapp
      image: myapp:1.0.0

      lifecycle:
        postStart:
          exec:
            command: ["/bin/sh", "-c", "echo started > /tmp/started"]
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 5"]

  terminationGracePeriodSeconds: 30

```

The init command waits for DNS resolution of `mydb`, not an authenticated database query; the application still needs runtime connection recovery. `postStart` is not guaranteed to finish before the container entrypoint runs. `preStop` runs before the termination signal and consumes the same grace-period budget. A sleep can allow traffic changes to propagate, but the process must handle its stop signal and drain work itself.

### Pod with Probes

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-probes
spec:
  containers:

    - name: myapp
      image: myapp:1.0.0

      startupProbe:
        httpGet:
          path: /health
          port: 8080
        failureThreshold: 30
        periodSeconds: 10

      livenessProbe:
        httpGet:
          path: /health
          port: 8080
        initialDelaySeconds: 10
        periodSeconds: 15
        timeoutSeconds: 3
        failureThreshold: 3

      readinessProbe:
        httpGet:
          path: /ready
          port: 8080
        initialDelaySeconds: 5
        periodSeconds: 10
        timeoutSeconds: 3

```

This probe configuration assumes distinct application contracts; change liveness to `/alive` when `/health` represents startup initialization. The full probe action and failure trace belongs in [Health Checks](../04-production-hardening/40.2.4.01-health-checks.md).

### Managing Pods and ReplicaSets

```bash
# Create resources
kubectl apply -f pod.yaml
kubectl apply -f replicaset.yaml

# List pods
kubectl get pods
kubectl get pods -l app=myapp
kubectl get pods --all-namespaces

# Describe pod
kubectl describe pod myapp-pod

# View logs
kubectl logs myapp-pod
kubectl logs myapp-with-sidecar -c log-shipper # named example container
kubectl logs -f myapp-pod # follow

# Execute in pod
kubectl exec -it myapp-pod -- sh

# Delete
kubectl delete pod myapp-pod
kubectl delete replicaset myapp-rs

```

## Real-World Use Cases

### 1. Web Application Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app
  labels:
    app: web
    tier: frontend
spec:
  containers:

    - name: nginx
      image: nginx:stable-alpine
      ports:

        - containerPort: 80
      volumeMounts:

        - name: nginx-config
          mountPath: /etc/nginx/nginx.conf
          subPath: nginx.conf

  volumes:

    - name: nginx-config
      configMap:
        name: nginx-config

```

The `nginx-config` object must contain a valid `nginx.conf`; this `subPath` mount does not refresh automatically when the ConfigMap changes. A bare Pod is suitable for an experiment, not a durable web service population.

### 2. Database Pod with Persistent Storage

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: postgres-rs
spec:
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:

        - name: postgres
          image: postgres:18-alpine
          env:

            - name: POSTGRES_DB
              value: mydb

            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
          volumeMounts:

            - name: pg-data
              mountPath: /var/lib/postgresql

      volumes:

        - name: pg-data
          persistentVolumeClaim:
            claimName: pg-pvc

```

This single-replica database example needs a usable `pg-pvc` and `db-credentials` Secret. Do not scale it to multiple independent writers against one data directory. A ReplicaSet is not a database replication/failover mechanism; production database ownership belongs to a suitable StatefulSet/operator and storage design.

### 3. Batch Job Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: data-processor
  labels:
    app: batch
    job: data-process
spec:
  restartPolicy: Never
  containers:

    - name: processor
      image: myapp/data-processor:1.0
      command: ["python", "process.py"]
      env:

        - name: INPUT_PATH
          value: "s3://bucket/input/"

        - name: OUTPUT_PATH
          value: "s3://bucket/output/"

```

This bare finite task can complete or fail once under `Never`; it lacks a Job controller to record a target completion and launch retries. The image must contain `process.py` and its cloud credentials/output handling. Use the [Jobs chapter](40.2.1.04-jobs-cronjobs.md) for controlled batch execution.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| Using bare Pods | Use ReplicaSets or Deployments |
| Hardcoding Pod labels | Use consistent label strategy |
| Omitting requests or choosing limits without measuring | Set requests from observed demand; choose limits deliberately because CPU throttling and memory OOM have different effects |
| Missing health checks | Add startup/liveness/readiness probes |
| Assuming init is mandatory | Use it only for bounded pre-start setup; keep runtime recovery in the app |
| Running as root | Set securityContext |
| No pod disruption budgets | Set PDB for critical workloads |

## Best Practices

```yaml
# Illustrative workload: verify image user, endpoints, DNS, and Secret prerequisites
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-rs
  labels:
    app: myapp
    version: v1
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        version: v1
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000

      initContainers:

        - name: init-db
          image: busybox:1.36
          command: ['sh', '-c', 'until nslookup db; do sleep 2; done']

      containers:

        - name: myapp
          image: myapp:1.0.0
          ports:

            - containerPort: 8080

          resources:
            requests:
              memory: "256Mi"
              cpu: "500m"
            limits:
              memory: "512Mi"
              cpu: "1000m"

          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 20

          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10

          env:

            - name: DB_HOST
              value: "db"

            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password

      terminationGracePeriodSeconds: 60

```

1. **Use a workload controller for persistent service populations** — bare Pods still have valid debugging/experimental uses

2. **Set realistic resource requests** — requests inform placement; set limits according to workload behavior and the cost of throttling or OOM termination

3. **Add health checks** — enable self-healing

4. **Use labels consistently** — enable service discovery and monitoring

5. **Run as non-root** — security best practice

6. **Use init containers deliberately** — DNS resolution is not ongoing dependency health

7. **Set terminationGracePeriodSeconds** — allow graceful shutdown

8. **Use PodDisruptionBudgets** — protect during voluntary disruptions

9. **Limit pod size** — smaller pods enable better scheduling
10. **Use namespaces deliberately** — they scope names and selected policies; use RBAC, NetworkPolicy and admission controls for security boundaries

## Performance Considerations

| Factor | Impact | Mitigation |
| ----------------- | ------------------- | ---------------------- |
| Pod size | Scheduling speed | Keep pods small |
| Resource requests | Scheduling accuracy | Set realistic requests |
| Init containers | Startup time | Minimize init logic |
| Container count | Resource overhead | Use sidecars sparingly |
| Node affinity | Distribution | Use pod anti-affinity |

```bash
# View pod resource usage
kubectl top pods
kubectl top pods --sort-by=memory

# Check scheduling
kubectl describe pod myapp-pod | grep -A 5 "Events"

# View pod density on nodes
kubectl get pods --all-namespaces -o custom-columns=NODE:.spec.nodeName --no-headers | sort | uniq -c

```

## Summary

Pods are Kubernetes' scheduling unit: their containers share placement and a network namespace, while a controller such as a ReplicaSet replaces missing replicas. Probe status, resource requests, network exposure, and application health have separate contracts; none is a substitute for the others.

# Kubernetes Pods & ReplicaSets

Deleting a Pod does not move its process to another machine. It removes one API object; if a controller owns that Pod, the controller notices the missing replica and asks Kubernetes to create a replacement from its template. Understanding that boundary explains why a container restart, Pod replacement, and application rollout are three different events.

## Definition

A **Pod** is Kubernetes' smallest schedulable workload unit. Its containers are placed on one node and share a network identity; they share files only through volumes mounted into each of them. A **ReplicaSet** keeps a selected Pod population near a desired count by creating or deleting Pods.

> **Textbook Definition:** A Pod is an API object representing one or more co-scheduled containers with shared network configuration and declared storage. A ReplicaSet is a controller that reconciles Pods selected by labels toward a desired replica count.

## First Principles

A container runtime can restart a failed process on its current node. That does not recover a node that is gone, and it does not create a missing application replica. Kubernetes splits these jobs: the kubelet manages containers for a Pod assigned to its node, while a workload controller manages the population of Pod objects.

### What one Pod shares

Containers in a Pod use the same Pod IP and can reach each other over `localhost`. They must avoid binding the same port. Their root filesystems are separate; a shared file requires a volume mounted into both containers. The Pod's process namespace is also not shared by default. Containers have individual restart behavior, but Pod deletion ends the whole Pod and its `emptyDir` data.

Use this boundary for tightly coupled helpers that must be placed and managed with the application, such as a local proxy or a log reader for a shared directory. Ordinary init containers run in sequence and must finish before application containers start. A native sidecar is declared as an init container with `restartPolicy: Always`; it starts before the application and keeps running beside it. Native sidecars are stable from Kubernetes 1.33. Do not combine independent application replicas into one Pod: the scheduler places a Pod as a unit, so replicas in separate Pods can be distributed independently.

### What a ReplicaSet replaces

A ReplicaSet compares its selector and desired replica count with the Pods it owns. If a managed Pod disappears, it creates a new Pod from the template. The replacement has a new object identity and may have a new IP; its process memory is not restored. If only a container exits and the Pod remains, the kubelet follows the Pod's restart policy and can restart that container in place.

The selector is the ownership boundary. A ReplicaSet can adopt an otherwise unowned Pod whose labels match, so avoid overlapping selectors and do not treat a matching hand-created Pod as a guaranteed extra replica. A ReplicaSet does not update existing Pods when its template changes. A Deployment manages ReplicaSets and their revisions, so use a Deployment for application releases.

## Follow a replacement Pod through the control plane

This small example asks for three interchangeable copies. The image must actually listen on port 8080; `containerPort` documents the port but does not publish it or create a listener.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: catalog
spec:
  replicas: 3
  selector:
    matchLabels:
      app: catalog
  template:
    metadata:
      labels:
        app: catalog
    spec:
      containers:
        - name: app
          image: registry.example.com/catalog:1.4.2
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
```

When one managed Pod is deleted, a replacement follows this path:

```text
kubectl writes ReplicaSet intent
  -> API server authenticates, authorizes, admits and stores the object in etcd
  -> ReplicaSet controller observes the change and creates a Pod object
  -> API server admits and stores the Pod
  -> scheduler selects a feasible node and records the binding
  -> that node's kubelet asks its container runtime to start the containers
  -> kubelet reports status; readiness determines whether the Pod is published as a Service endpoint
```

The **API server** is the control plane's API and validation boundary; **etcd** stores the cluster's API state. Controllers and the scheduler are API clients that watch state and write their decisions back through the API server. The scheduler chooses placement; it does not start containers. The **kubelet** on the selected node observes its assigned Pod and works with the container runtime through the Container Runtime Interface (CRI). It reports observed status, but the application must still become ready.

This is an asynchronous control loop, not one transaction or a command that runs from top to bottom. A missing Pod object can mean admission or controller trouble; an existing Pod stuck in `Pending` points toward scheduling or image/storage setup; a running but unready Pod points toward startup or readiness. The ReplicaSet restores the desired object count, not immediate serving capacity. A Service provides stable discovery over eligible endpoints; it does not preserve a vanished Pod's in-memory state.

Resource requests inform scheduling, and limits configure runtime enforcement. CPU limits can throttle; exceeding a memory limit can cause a container to be terminated. The scheduler evaluates the Pod's effective requests, which depend on its complete container specification, not just the application container. Set requests from workload needs and account for sidecars and initialization when planning capacity. The `PodLevelResources` feature for Pod-level CPU, memory, and hugepage requests and limits is beta and enabled by default since Kubernetes 1.34. Kubernetes 1.37 adds a separate beta, disabled-by-default `PodLevelResourceManagers` feature gate that lets kubelet's topology, CPU, and memory managers use those Pod-level declarations for allocation decisions. Check both gates and the target cluster's support before relying on those behaviors. Namespace quotas can reject creation even when a node appears to have room.

## Inspect the controller boundary

```bash
kubectl get rs catalog
kubectl get pods -l app=catalog -o wide
kubectl describe rs catalog
kubectl describe pod <pod-name>
kubectl logs <pod-name> -c app
```

If a Pod is missing, inspect ReplicaSet events and ownership. If it exists but is not serving, inspect scheduling, container state, readiness and Service endpoints. Probe design and graceful termination have their own contracts in [Health Checks](../04-production-hardening/40.2.4.01-health-checks.md); a restart policy cannot substitute for a probe or application recovery logic.

A bare Pod is useful for debugging or a short experiment, but Kubernetes does not recreate it after deletion. Finite work needs a Job controller, and a version change needs a Deployment. A database may need stable identity and a storage design, but a StatefulSet alone still does not implement replication, backup or failover.

## Summary

A Pod groups containers that need one placement and network identity. The kubelet handles container restarts on that Pod; a ReplicaSet maintains a population by creating replacement Pod objects; a Deployment owns version transitions. None of those controllers restores process memory or proves that a replacement is ready to serve.

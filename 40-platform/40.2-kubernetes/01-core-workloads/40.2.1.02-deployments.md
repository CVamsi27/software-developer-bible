# Kubernetes Deployments

A release changes the application while users are still sending requests. If every old Pod disappears before a new one can serve, traffic has nowhere to go. If a new Pod starts but cannot actually serve, Kubernetes needs a signal before it removes healthy capacity. A Deployment coordinates that version change through ReplicaSets and Pods.

## Definition

A **Deployment** is a Kubernetes controller for a replicated, usually stateless application. You declare a Pod template and desired replica count; the Deployment manages ReplicaSets that create, replace and retain those Pods during updates.

> **Textbook Definition:** A Deployment is a declarative workload controller that reconciles a desired Pod template and replica count through ReplicaSets, recording template revisions and applying a configured rollout strategy.

## First Principles

A controller repeatedly compares actual state with desired state and acts to reduce the difference. A ReplicaSet can maintain a number of matching Pods, but it does not own a version transition. A Deployment does: it creates a ReplicaSet for a changed Pod template, adjusts old and new ReplicaSets, and records revisions that can be selected for a later rollout.

During a rolling update, old and new application versions may serve at the same time. Database schemas, APIs and queued messages must tolerate that overlap. Restoring an older Pod template does not reverse writes or schema changes already made by the newer version.

## Follow one rollout from template to ready Pod

This Deployment asks for three replicas. It permits one surge Pod and no unavailable Pod during a rolling update. The exact capacity still depends on namespace quota, node capacity, image availability and the application's startup behavior.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog
  labels:
    app: catalog
spec:
  replicas: 3
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: catalog
  template:
    metadata:
      labels:
        app: catalog
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: app
          image: registry.example.com/catalog:v1.4.2
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 512Mi
          startupProbe:
            httpGet:
              path: /startup
              port: http
            periodSeconds: 5
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /ready
              port: http
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /alive
              port: http
            periodSeconds: 15
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: catalog-db
                  key: password
```

When the image changes, the controllers work through this chain:

```text
Deployment template changes
  → Deployment creates a new ReplicaSet revision
  → new ReplicaSet asks for a Pod
  → scheduler places it; kubelet starts its containers
  → startup probe gates readiness and liveness until initialization succeeds
  → readiness marks the Pod eligible for Service traffic
  → after the availability policy is satisfied, old ReplicaSet capacity decreases
```

A release tag such as `v1.4.2` is only a name; the registry can still move it. For reproducible promotion, record and deploy the image digest produced by the build, then promote that same artifact between environments.

For three desired replicas, `maxSurge: 1` permits one extra non-terminated Pod above the desired count during the rollout, while `maxUnavailable: 0` prevents the controller from reducing the number considered available below the desired count. A terminating Pod can continue using CPU and memory, so plan for its cleanup time too. `minReadySeconds`, when configured, requires a Pod to remain ready for that duration before the Deployment counts it as available.

The probes answer different questions. A **startup probe** protects a slow initialization period; while it has not succeeded, Kubernetes does not run that container's liveness or readiness probes. A **readiness probe** controls whether the Pod receives Service traffic. A **liveness probe** restarts a container after repeated failure. Keep liveness local to a condition a restart can repair: making it fail whenever a database is briefly unavailable can restart every replica and amplify the outage. The [probe guide](https://kubernetes.io/docs/concepts/workloads/pods/probes/) explains the probe contract.

Readiness is not a zero-error promise. It only reports the condition your probe checks, and a Pod may fail after receiving traffic. Likewise, `maxUnavailable: 0` is a controller policy, not proof that clients observe no failed requests. Test the full release path and measure errors and latency.

## Diagnose a rollout that stops

Apply a reviewed manifest and wait for the controller's outcome:

```bash
kubectl apply -f catalog-deployment.yaml
kubectl rollout status deployment/catalog --timeout=5m
kubectl get deployment,replicaset,pods -l app=catalog
kubectl describe deployment/catalog
kubectl rollout history deployment/catalog
```

A new Pod may remain `Pending` because of insufficient schedulable capacity or quota, or fail to start because its image or configuration is invalid. A Pod that starts but never becomes ready keeps old capacity in place when `maxUnavailable` is zero. A `ProgressDeadlineExceeded` condition reports stalled progress; Kubernetes continues reconciliation and does not automatically roll back. Inspect events, ReplicaSets, probe results, quota and capacity to find the failed step.

`kubectl rollout undo deployment/catalog` selects an earlier Pod template and begins another rollout. Before using it, check that the old application can read the current database schema and interact with already-updated services. Rollback changes the template, not committed business data. Use `kubectl rollout pause` and `resume` only when a release process owns the pause and has a clear decision to continue or recover.

## Choose how traffic changes between versions

| Strategy | What changes | Use it when | Boundary to plan |
| -------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rolling update | One Deployment gradually replaces old Pods with new Pods. | Mixed versions can coexist and gradual capacity change is acceptable. | Surge capacity, readiness, application compatibility and termination behavior. |
| Recreate | The Deployment terminates old Pods before creating new ones. | The application cannot safely run both versions and the outage is acceptable. | It does not guarantee single-writer behavior across failures or external storage; use a StatefulSet or operator when stable identity and ownership are required. |
| Canary | Separate stable and candidate Deployments receive traffic through a routing layer. | You need to compare a candidate with a small cohort before promotion. | Replica ratios alone do not guarantee an exact request percentage; connection reuse, affinity and the data plane affect distribution. Use weighted routing for a controlled share. |
| Blue-green | Two full versions run separately; a Service or routing layer switches new traffic. | You need a fast traffic reversal and can afford both environments. | Existing connections may persist, and switching traffic does not undo writes made by green. |

For canary traffic, a Service selecting both stable and candidate Pods can approximate a share from their eligible endpoints, but it does not enforce a precise percentage of requests. For blue-green, verify green readiness and data compatibility before changing the selector; retain blue long enough to support a deliberate reversal.

## Let the HPA own replica count when demand varies

A Horizontal Pod Autoscaler (HPA) changes the target's replica count from observed metrics. With CPU utilization targets, container resource **requests** provide the denominator. If the HPA owns scaling, do not routinely reapply a manifest that pins a competing `spec.replicas` value; the two writers can overwrite one another. The HPA adjusts desired scale, while scheduling capacity and readiness determine how many Pods actually become available. See the [HPA controller documentation](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/).

Use manual scaling for an intentional one-off change when no autoscaler owns that field. Record the field owner in the release process so a GitOps reconciler, command-line operation and HPA do not fight over the same value.

## Keep rollout, eviction and application guarantees separate

`maxUnavailable` and `maxSurge` govern a Deployment's update. A PodDisruptionBudget (PDB) constrains supported voluntary disruptions such as some node drains; it does not replace the Deployment's rollout strategy or guarantee availability during crashes. Neither controller makes two application versions compatible, drains in-flight work automatically, or preserves Pod memory.

Requests guide scheduling and, for CPU utilization metrics, HPA calculations. CPU limits can throttle a process; a memory-limit breach can lead to termination. A `preStop` hook consumes the Pod's termination grace period and does not drain requests by itself. The application must stop accepting work and handle termination within the remaining time. A shell-based hook also assumes the image contains that shell.

## Summary

A Deployment moves an application between Pod templates by reconciling ReplicaSets. Readiness and rollout budgets control when old capacity can leave, while startup and liveness probes govern different container conditions. Capacity, mixed-version compatibility, request draining and data rollback remain application and release responsibilities. Explain which controller owns replicas, how traffic reaches a new version, and what evidence triggers recovery.

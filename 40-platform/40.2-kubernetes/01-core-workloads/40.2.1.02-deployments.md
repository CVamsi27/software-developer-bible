# Kubernetes Deployments

## Definition

A **Deployment** provides declarative updates for Pods and ReplicaSets. It manages the desired state of your application, enabling rolling updates, rollbacks, scaling, and self-healing. Deployments are the most common way to run stateless applications in Kubernetes.

> **Textbook Definition:** A Kubernetes Deployment reconciles a desired Pod template and replica count through ReplicaSets, governing replacement, rollout strategy, and recorded revisions for compatible workload updates.

Key concepts:

- **Deployment**: Manages ReplicaSets and Pods
- **Rolling Update**: Gradual replacement of Pods
- **Rollback**: Revert to previous Deployment revision
- **Strategy**: How updates are performed
- **Revision History**: Track of all Deployment changes

## First Principles

A service must change version while requests continue arriving. Replacing every process at once loses serving capacity; replacing individual replicas requires an owner that knows both the old and new templates and can retain a fallback. A ReplicaSet maintains a population but does not coordinate that version transition.

A Deployment records the desired template and manages old/new ReplicaSets. Availability and extra-capacity budgets constrain their counts while both versions can exist. That coexistence creates an application constraint: database schemas, APIs, and queued messages must remain compatible during the overlap. Restoring an older template cannot undo effects already committed by the newer one.

## Why Do We Need It?

| Problem | Solution |
| ----------------------- | ------------------------- |
| Manual Pod management | Declarative desired state |
| Downtime during updates | Rolling updates |
| No rollback capability | Revision history |
| Manual scaling | `kubectl scale` |
| No self-healing | Automatic Pod replacement |
| No deployment history | Revision tracking |

## How It Works

### Each controller owns one part of the transition

```text
Deployment template changes v1 -> v2
  -> new ReplicaSet uses v2 template
  -> Deployment adjusts old/new ReplicaSet desired counts
  -> each ReplicaSet creates/removes its Pod members
  -> scheduler and kubelets turn requests into running containers
  -> readiness and minReadySeconds establish rollout availability
```

The Deployment does not launch containers directly. Template changes create rollout revisions; a replica-count change alone does not create a new template revision. The old ReplicaSet can remain at zero within revision-history limits. A rollback restores an earlier template and starts another reconciliation; it is not a snapshot of the database or application memory.

### Rolling Update Process

```text
Step 1: Initial State
+--------+ +--------+ +--------+

| v1 Pod | | v1 Pod | | v1 Pod |

+--------+ +--------+ +--------+

Step 2: Create new Pod
+--------+ +--------+ +--------+ +--------+

| v1 Pod | | v1 Pod | | v1 Pod | | v2 Pod |

+--------+ +--------+ +--------+ +--------+

Step 3: Terminate old Pod
+--------+ +--------+ +--------+

| v1 Pod | | v1 Pod | | v2 Pod |

+--------+ +--------+ +--------+

Step 4: Create another new Pod
+--------+ +--------+ +--------+ +--------+

| v1 Pod | | v1 Pod | | v2 Pod | | v2 Pod |

+--------+ +--------+ +--------+ +--------+

Step 5: Terminate another old Pod
+--------+ +--------+ +--------+

| v1 Pod | | v2 Pod | | v2 Pod |

+--------+ +--------+ +--------+

Step 6: Complete
+--------+ +--------+ +--------+

| v2 Pod | | v2 Pod | | v2 Pod |

+--------+ +--------+ +--------+

```

The illustrated sequence assumes three replicas, `maxSurge: 1`, `maxUnavailable: 0`, and successful readiness/availability of each new member before reducing old capacity. `minReadySeconds` can require continuous readiness before a Pod is available. Pending or unhealthy surge Pods stall this trace; absent readiness probes can falsely admit a version that cannot serve. Terminating Pods may still consume resources beyond the apparent active rollout count.

## Code Examples

Each recipe is an alternative configuration. Use an image implementing its ports/endpoints, create referenced Secrets/ConfigMaps first, and run it in an intended test namespace. Commands require a reachable authorized cluster.

### Basic Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:

        - name: myapp
          image: myapp:1.0.0
          ports:

            - containerPort: 8080
          resources:
            requests:
              memory: "128Mi"
              cpu: "250m"
            limits:
              memory: "256Mi"
              cpu: "500m"

```

### Rolling Update Strategy

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # Max pods above desired count
      maxUnavailable: 0 # Permit no rollout reduction below desired available count
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:

        - name: myapp
          image: myapp:2.0.0

```

The five-replica strategy can request one additional active member; it needs admission quota and feasible node capacity for that member. Zero allowed unavailability is a rollout policy, not proof of zero failed user requests.

### Recreate Strategy

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  strategy:
    type: Recreate # Kill all old pods before creating new
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:

        - name: myapp
          image: myapp:2.0.0

```

Recreate removes old version Pods before creating new version Pods during an update, so it trades coexistence for interruption. It is not a universal single-writer guarantee: failures, manual deletion, and external storage still need application fencing/ownership. Use StatefulSet/operator semantics when stable identity and data handling matter.

### Deployment with Probes and Lifecycle

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      terminationGracePeriodSeconds: 60
      containers:

        - name: myapp
          image: myapp:2.0.0

          startupProbe:
            httpGet:
              path: /health
              port: 8080
            failureThreshold: 30
            periodSeconds: 10

          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            periodSeconds: 15
            timeoutSeconds: 3

          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 3

          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 15"]

          resources:
            requests:
              memory: "256Mi"
              cpu: "500m"
            limits:
              memory: "512Mi"
              cpu: "1000m"

          env:

            - name: DB_HOST
              value: "db-service"

            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password

```

### Managing Deployments

```bash
# Create deployment
kubectl apply -f deployment.yaml

# Check status
kubectl get deployments
kubectl rollout status deployment/myapp

# Scale
kubectl scale deployment/myapp --replicas=5

# Update image
kubectl set image deployment/myapp myapp=myapp:2.0.0

# Rollback
kubectl rollout undo deployment/myapp
kubectl rollout undo deployment/myapp --to-revision=2

# View history
kubectl rollout history deployment/myapp

# Pause/resume
kubectl rollout pause deployment/myapp
kubectl rollout resume deployment/myapp

```

The sleep hook consumes 15 seconds of the 60-second termination budget and may allow endpoint withdrawal to propagate. It does not drain work by itself; the application must stop intake and handle its termination signal within the remaining budget. Choose liveness `/alive` when `/health` owns only startup.

### Deployment with HPA

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:

        - name: myapp
          image: myapp:2.0.0
          resources:
            requests:
              memory: "256Mi"
              cpu: "500m"
            limits:
              memory: "512Mi"
              cpu: "1000m"

---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 3
  maxReplicas: 20
  metrics:

    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

```

Once HPA owns scale, reapplying a fixed `spec.replicas` can reset its decision. Keep the declarative replica field out of routine updates under an intentional ownership/migration procedure. CPU requests supply HPA utilization denominators; actual readiness and node capacity remain separate.

## Real-World Use Cases

### 1. Maintain serving capacity during replacement

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:

        - name: web
          image: web:2.0
          ports:

            - containerPort: 80

          readinessProbe:
            httpGet:
              path: /ready
              port: 80
            periodSeconds: 5

          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 15"]

```

This pattern needs surge capacity, honest readiness, compatible versions, and application draining. Test observed errors/latency; `maxUnavailable: 0` alone cannot establish a no-interruption release.

### 2. Canary Deployment

```yaml
# Stable version
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-stable
spec:
  replicas: 9
  selector:
    matchLabels:
      app: myapp
      track: stable
  template:
    metadata:
      labels:
        app: myapp
        track: stable
    spec:
      containers:

        - name: myapp
          image: myapp:1.0.0

---
# Canary version
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-canary
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
      track: canary
  template:
    metadata:
      labels:
        app: myapp
        track: canary
    spec:
      containers:

        - name: myapp
          image: myapp:2.0.0

```

These Deployments alone do not route any traffic. A Service selecting `app: myapp` can include both tracks; with equally eligible backends, nine stable and one canary replicas can approximate a small share across many connections, not enforce exactly 10% of requests. Connection reuse and session affinity change the share. Use a routing controller with explicit weights/cohorts when precise allocation matters. Both versions still need compatibility and observation before promotion.

### 3. Blue-Green Deployment

```yaml
# Blue (current)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
      version: blue
  template:
    metadata:
      labels:
        app: myapp
        version: blue
    spec:
      containers:

        - name: myapp
          image: myapp:1.0.0

---
# Green (new)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-green
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
      version: green
  template:
    metadata:
      labels:
        app: myapp
        version: green
    spec:
      containers:

        - name: myapp
          image: myapp:2.0.0

---
# Service (switch selector between blue/green)
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    app: myapp
    version: blue # Change to green for new version
  ports:

    - port: 80
      targetPort: 8080

```

The Service initially selects only blue; changing its selector to green changes new eligible backend selection after propagation. It does not migrate existing sessions or roll back green's data writes. Verify green readiness and compatible data before switching, and retain enough capacity for a recoverable traffic reversal. These example images must listen on target port 8080.

### Detecting and recovering a stalled rollout

Set `progressDeadlineSeconds` to expose a rollout that stops making progress. `ProgressDeadlineExceeded` is a status condition: Kubernetes continues reconciliation and does not automatically restore the previous release. A pipeline or release controller must choose rollback or repair. Before `kubectl rollout undo`, verify that the earlier Pod template can still read current data and communicate with already updated dependencies. Rollback restores application configuration, not committed business effects.

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Readiness probe treated as a zero-downtime guarantee | Make readiness reflect ability to serve; also plan rollout capacity, compatibility and routing |
| Availability budget chosen without capacity planning | Match permitted loss/surge to SLO and schedulable headroom |
| Limits copied without workload evidence | Set realistic requests; choose CPU and memory limits based on their distinct throttling and OOM effects |
| Liveness probe checks a dependency | Use liveness only for a process-local failure that a restart can repair; use readiness for traffic eligibility |
| Using `latest` tag | Pin specific image versions |
| PDB treated as a rollout or crash guarantee | Use a PDB for supported voluntary evictions; configure Deployment rollout availability separately |
| No revision history limit | Set revisionHistoryLimit |

## Best Practices

```yaml
# GOOD: Production Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp
    version: v1
spec:
  replicas: 3
  revisionHistoryLimit: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        version: v1
    spec:
      terminationGracePeriodSeconds: 60
      containers:

        - name: myapp
          image: myapp:1.0.0

          startupProbe:
            httpGet:
              path: /health
              port: 8080
            failureThreshold: 30
            periodSeconds: 10

          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            periodSeconds: 15
            timeoutSeconds: 3
            failureThreshold: 3

          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 3

          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 15"]

          resources:
            requests:
              memory: "256Mi"
              cpu: "500m"
            limits:
              memory: "512Mi"
              cpu: "1000m"

          env:

            - name: DB_HOST
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: db-host

      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:

            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:

                    - key: app
                      operator: In
                      values:

                        - myapp
                topologyKey: kubernetes.io/hostname

```

1. **Use a deliberate availability budget** — `maxUnavailable=0` can retain ready capacity during replacement when surge capacity and application compatibility permit

2. **Choose probes from required actions** — protect slow startup, withdraw unready traffic, restart recoverable local failure

3. **Set realistic resource requests** — requests guide placement; choose CPU and memory limits deliberately because throttling and OOM termination have different consequences

4. **Use pod anti-affinity** — distribute across nodes

5. **Set revisionHistoryLimit** — manage revision history

6. **Test termination** — hooks consume the grace budget and application signal handling must drain work

7. **Pin image versions** — never use `latest`

8. **Use a PodDisruptionBudget where its eviction contract helps** — it constrains supported voluntary disruptions, while Deployment strategy governs rollout availability

9. **Use namespaces deliberately** — scope names and selected policies; add RBAC, NetworkPolicy and admission controls for security
10. **Monitor rollout status** — `kubectl rollout status`

## Performance Considerations

| Factor | Impact | Mitigation |
| --------------------- | ----------------------------- | ------------------------------------------------------------------------------------ |
| maxSurge | Resource overhead | Set appropriate value |
| maxUnavailable | Availability during a rollout | Set against SLO and surge capacity; zero still cannot guarantee zero failed requests |
| Startup probe timeout | Deployment speed | Tune failureThreshold |
| PreStop sleep time | Grace period | Balance with terminationGracePeriod |
| Anti-affinity rules | Scheduling speed | Use preferredDuringScheduling |

```bash
# Monitor deployment
kubectl rollout status deployment/myapp
kubectl get events -w

# Check resource usage
kubectl top pods -l app=myapp

# View rollout history
kubectl rollout history deployment/myapp

```

## Summary

Deployments are the standard way to manage stateless applications in Kubernetes. They provide rolling updates, rollbacks, and self-healing. Proper probe configuration, resource limits, and update strategies are essential for production reliability.

# StatefulSets & DaemonSets

## Definition

**StatefulSets** manage stateful applications with unique network identities, stable persistent storage, and ordered deployment/scaling (e.g., databases, message queues). **DaemonSets** ensure all (or select) nodes run a copy of a pod — used for cluster-wide services like log collectors, monitoring agents, and network plugins.

> **Textbook Definition:** A StatefulSet reconciles Pods with stable ordinal identities and associated storage. A DaemonSet reconciles one workload Pod on each eligible node according to its scheduling constraints.

## First Principles

Interchangeable service replicas can return under a new name without changing the service protocol. A database member or broker may instead need its replacement to recover the same member's data and identity. That requirement calls for a stable ordinal and claim association beyond the lifetime of one Pod.

A node-local agent has a different requirement: each eligible machine needs its own collector, driver, or network process, regardless of the application replica count. Its population must follow node eligibility rather than a fixed number. StatefulSet solves identity; DaemonSet solves this per-node coverage. Neither controller implements application replication or guarantees a process is always ready.

## Why Do We Need It?

1. **StatefulSets**: Stable Pod identities (DNS), ordered graceful deployment, persistent storage per Pod, useful when the selected database deployment requires stable member identities; operators still own replication/failover
2. **DaemonSets**: Node-level agents (Fluentd for logs, Prometheus Node Exporter, Calico/Cilium networking, kube-proxy)

## How It Works

### StatefulSet mechanics: identity is the whole design

The controller pairs each replica with an **ordinal identity** (`postgres-0`, `postgres-1`, `postgres-2`) and — via the required **headless Service** (`serviceName`) — a stable DNS name (`postgres-0.postgres.default.svc.cluster.local`). Three consequences define the workload class:

- **Storage follows identity, not the pod.** `volumeClaimTemplates` creates one PVC per ordinal (`data-postgres-0`, `data-postgres-1`…). When a replacement Pod is assigned to another compatible node, it can reattach its own volume if the storage implementation and topology permit it — the data survives, the network identity survives, the pod is still recognizable.
- **Scaling down is asymmetric with scaling up.** By default, scaling down retains the PVC. `persistentVolumeClaimRetentionPolicy` can explicitly change scale-down/deletion retention when supported — a deliberate data-safety choice that surprises people: scale 3→5→3 and two orphaned PVCs remain, still billing, and still holding data that a future scale-up will silently reattach. Orphaned-PVC hygiene is a real operational task (`kubectl get pvc` after every scale-down).
- **With the default `OrderedReady` management policy, order applies to scaling at both ends.** Pods start in ascending order (N must be Ready before N+1 launches) and terminate in descending order — the contract quorum systems (etcd, Kafka, ZooKeeper-era systems) rely on when a member must be replaced cleanly.

Update strategy is where the senior answers live: `RollingUpdate` with `partition` is a built-in canary (set partition=3 to update only pod-3+; walk it down as confidence grows — the pattern operators use for stateful rollouts), `OnDelete` gives full manual control, and `podManagementPolicy: Parallel` removes readiness/termination sequencing for scaling; it does not change RollingUpdate's separate update strategy. A quorum protocol must still manage membership and replication before a restart or scale change. Kubernetes readiness alone is not proof that a member has caught up.

### DaemonSet mechanics: coverage is the contract

The controller watches nodes, not replicas: a desired Pod per eligible node, subject to placement and startup, new nodes get pods automatically, nodes removed have their pods garbage-collected. Scheduling is intentional about being *un*-selective — the controller automatically tolerates `node.kubernetes.io/unschedulable:NoSchedule` and several node-condition taints, and reaching control-plane nodes requires tolerations for `node-role.kubernetes.io/control-plane` (declare it in the example when those nodes should be included). Updates roll per-node (`RollingUpdate` with `maxSurge`/`maxUnavailable`, or `OnDelete` for agents you must coordinate — many CNI daemons use OnDelete because restarting the pod that owns the node's networking is not a background event). DaemonSets can also target a subset via `nodeSelector`/`affinity` — GPU drivers via the NVIDIA device plugin targeting only `gpu=true` nodes is the canonical case.

## Code Examples

### StatefulSet

This identity/storage demonstration assumes a `standard` StorageClass with dynamic provisioning, a `db-credentials` Secret with a password, and supported volume attachment. It launches **three independent PostgreSQL instances**, not a replicated database cluster. Use a database operator or application-specific replication setup for high availability. Create the headless Service as well as the StatefulSet:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: postgres
spec:
  clusterIP: None
  selector: {app: postgres}
  ports:
    - {name: postgres, port: 5432, targetPort: 5432}
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:15
        env:
          - name: POSTGRES_PASSWORD
            valueFrom:
              secretKeyRef: {name: db-credentials, key: password}
        ports:
          - {name: postgres, containerPort: 5432}
        readinessProbe:
          exec:
            command: [pg_isready, -U, postgres]
          periodSeconds: 5
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      storageClassName: standard
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
```

A replacement `postgres-1` uses `data-postgres-1` again rather than adopting `postgres-0`'s data. The Pod object/IP can change even while its DNS identity remains stable. The readiness command observes connection acceptance only; it does not establish replication consistency. Headless DNS normally includes ready endpoints, so a bootstrapping protocol may need a deliberate different discovery contract.

### DaemonSet

This log-agent example requires an image/configuration that can read the actual node log layout and forward it to your sink. Decide whether host filesystem access is permitted by cluster security policy; existence of the DaemonSet does not prove log export.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  selector:
    matchLabels:
      name: fluentd
  template:
    metadata:
      labels:
        name: fluentd
    spec:
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: fluentd
        image: fluent/fluentd:v1.16
        volumeMounts:
        - name: varlog
          mountPath: /var/log
          readOnly: true
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
          type: Directory
```

DaemonSet uses node eligibility to choose the desired population, then the scheduler assigns each Pod to its intended node. A new eligible node adds demand; a resource or image failure can still leave that node uncovered. Rolling updates with surge can temporarily place two versions on a node, while a non-surge transition can temporarily leave no ready agent. Verify coverage during updates.

## Key Differences

| Feature | StatefulSet | DaemonSet | Deployment |
| ------------------- | :----------------------------------------: | :-------------------------------------: | :---------------------------------------: |
| Pod identity | Stable ordinal | Per-node | Random |
| Storage association | Can create claims per ordinal | Can use host or other supported volumes | Can use any appropriate Pod volume design |
| Scaling | OrderedReady by default; Parallel optional | Follows eligible node count | Interchangeable replica count |
| Update strategy | Rolling/Custom | RollingOnDelete | Rolling/Rollback |

## Real-World Usage

- **Kafka via Strimzi, PostgreSQL via operators, etcd, ZooKeeper** — these are common stable-member workloads; individual operators may choose other controllers. Stable identity alone does not establish quorum membership. The operators layer reconciliation logic (backup, failover, reconfiguration) on top of the StatefulSet primitives.
- **The observability layer is DaemonSets end to end**: Fluentd/Fluent Bit or the Grafana Alloy agents tail node logs, Node Exporter scrapes hardware metrics, and CNI daemons (Cilium, Calico) are DaemonSets that *are* the node's networking — the desired coverage the controller maintains still needs scheduling, resources, startup, and health.
- **The scale-down surprise in production**: an operator scales a 5-replica Kafka StatefulSet to 3, weeks later notices storage cost hasn't dropped — the two PVCs outlived their pods. The lesson is institutional: StatefulSet scale-down is a *data* decision (was there data on those ordinals?), not a capacity one.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Scaling a StatefulSet down and assuming storage follows | Default retention keeps PVCs; inspect explicit retention and reclaim policies before cleanup |
| Omitting `serviceName` (headless Service) | Pod DNS doesn't resolve; clients that address replicas break |
| Using a normal Service for StatefulSet DNS | Only headless (`clusterIP: None`) creates per-pod A records |
| DaemonSet missing control-plane tolerations | Agents silently absent from masters — logs and CNI gaps there |
| Leaving `partition` set after a canary rollout | Most replicas keep running the old version indefinitely |
| `hostPath` volumes without a plan | DaemonSets need node access, but pin paths and use `type: Directory` |
| Choosing StatefulSet "to be safe" for stateless work | You pay ordered, slower operations for identity you don't use |

## Best Practices

1. **Ask the identity question first** — "if a pod comes back as someone else, does the system break?" Only a yes earns a StatefulSet; otherwise a Deployment is faster to operate.
2. **Pair every StatefulSet with its headless Service and name the DNS contract** for clients (`pod-0.svc` is an API, not an implementation detail).
3. **Use `partition` canaries for stateful rollouts** — update one ordinal, verify, walk the partition down; `OnDelete` when the workload must own its restart timing.
4. **Monitor orphaned PVCs** — a scheduled check for claims with no matching pod catches the billing-and-surprise drift.
5. **For DaemonSets, decide node coverage explicitly** — tolerations, `nodeSelector`, and tainted-node behavior are the spec, not afterthoughts.
6. **Budget StatefulSet operations in time** — ordered replacement of a 10-replica quorum takes ten Ready-waits; say so in the runbook before the incident.

## Summary

- StatefulSets manage stateful applications with stable network identities and persistent storage
- DaemonSets reconcile desired coverage per eligible node; failures and update overlap affect the observed population, ideal for logging, monitoring, and networking agents
- StatefulSets provide ordered deployment, scaling, and rolling updates for databases and message queues
- DaemonSets automatically schedule pods on new nodes as they join the cluster
- Headless Services are typically used with StatefulSets for stable DNS names per pod

# StatefulSets & DaemonSets

## TL;DR

StatefulSets give Pods stable network IDs and persistent storage per replica. DaemonSets run one Pod per node (logging, agents, CNI).

**Why it matters:** Tests the difference between stateless and stateful workloads, headless services, PVC templates, and node-level workloads (Fluentd, Node Exporter).

## First Principles

StatefulSet and DaemonSet exist where Deployments' assumptions break:

1. **StatefulSet promises *identity***: stable names, stable PVCs, ordered start/stop — because databases and quorum systems need "pod-0 is the one that was pod-0." The cost: slower, more fragile operations — use only when identity is truly required.
2. **DaemonSet promises *coverage***: exactly one Pod per (matching) node — the shape of log collectors, node monitors, CNI plugins. It's the "per-host agent" primitive.
3. **Both exist because Pods are cattle — except when they're pets**; knowing which your workload is, is the design decision.

## Definition

**StatefulSets** manage stateful applications with unique network identities, stable persistent storage, and ordered deployment/scaling (e.g., databases, message queues). **DaemonSets** ensure all (or select) nodes run a copy of a pod — used for cluster-wide services like log collectors, monitoring agents, and network plugins.

## Why Do We Need It?

1. **StatefulSets**: Stable Pod identities (DNS), ordered graceful deployment, persistent storage per Pod, required for databases (PostgreSQL, Cassandra, Kafka)
2. **DaemonSets**: Node-level agents (Fluentd for logs, Prometheus Node Exporter, Calico/Cilium networking, kube-proxy)

## How It Works

### StatefulSet mechanics: identity is the whole design

The controller pairs each replica with an **ordinal identity** (`postgres-0`, `postgres-1`, `postgres-2`) and — via the required **headless Service** (`serviceName`) — a stable DNS name (`postgres-0.postgres.default.svc.cluster.local`). Three consequences define the workload class:

- **Storage follows identity, not the pod.** `volumeClaimTemplates` creates one PVC per ordinal (`data-postgres-0`, `data-postgres-1`…). When a pod reschedules to another node, it reattaches its *own* volume — the data survives, the network identity survives, the pod is still recognizable.
- **Scaling down is asymmetric with scaling up.** Deleting a replica removes the pod but **never its PVC** — a deliberate safety choice that surprises people: scale 3→5→3 and two orphaned PVCs remain, still billing, and still holding data that a future scale-up will silently reattach. Orphaned-PVC hygiene is a real operational task (`kubectl get pvc` after every scale-down).
- **Order is enforced at both ends.** Pods start in ascending order (N must be Ready before N+1 launches) and terminate in descending order — the contract quorum systems (etcd, Kafka, ZooKeeper-era systems) rely on when a member must be replaced cleanly.

Update strategy is where the senior answers live: `RollingUpdate` with `partition` is a built-in canary (set partition=3 to update only pod-3+; walk it down as confidence grows — the pattern operators use for stateful rollouts), `OnDelete` gives full manual control, and `podManagementPolicy: Parallel` trades the ordering guarantee for speed when identity matters but order doesn't.

### DaemonSet mechanics: coverage is the contract

The controller watches nodes, not replicas: one pod per matching node, new nodes get pods automatically, nodes removed have their pods garbage-collected. Scheduling is intentional about being *un*-selective — DaemonSets ignore `unschedulable` taints unless you say otherwise, and reaching control-plane nodes requires tolerations for `node-role.kubernetes.io/control-plane` (the fluentd example above carries one). Updates roll per-node (`RollingUpdate` with `maxSurge`/`maxUnavailable`, or `OnDelete` for agents you must coordinate — many CNI daemons use OnDelete because restarting the pod that owns the node's networking is not a background event). DaemonSets can also target a subset via `nodeSelector`/`affinity` — GPU drivers via the NVIDIA device plugin targeting only `gpu=true` nodes is the canonical case.

## Code Examples

### StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:15
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      storageClassName: standard
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
```

### DaemonSet

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  selector:
    matchLabels:
      name: fluentd
  template:
    metadata:
      labels:
        name: fluentd
    spec:
      tolerations:
      - key: node-role.kubernetes.io/master
        effect: NoSchedule
      containers:
      - name: fluentd
        image: fluent/fluentd:v1.16
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
```

## Key Differences

| Feature | StatefulSet | DaemonSet | Deployment |
| --------------- | :----------------: | :---------------: | :--------------: |
| Pod identity | Stable ordinal | Per-node | Random |
| Storage | Persistent per Pod | HostPath/emptyDir | Shared PVC |
| Scaling | Ordered | By node count | Arbitrary |
| Update strategy | Rolling/Custom | RollingOnDelete | Rolling/Rollback |

## Real-World Usage

- **Kafka via Strimzi, PostgreSQL via operators, etcd, ZooKeeper** — every quorum system on Kubernetes is a StatefulSet, because quorum membership is exactly the stable-identity problem. The operators layer reconciliation logic (backup, failover, reconfiguration) on top of the StatefulSet primitives.
- **The observability layer is DaemonSets end to end**: Fluentd/Fluent Bit or the Grafana Alloy/Promtail agents tail node logs, Node Exporter scrapes hardware metrics, and CNI daemons (Cilium, Calico) are DaemonSets that *are* the node's networking — the pods the cluster cannot function without are the ones the DaemonSet guarantees.
- **The scale-down surprise in production**: an operator scales a 5-replica Kafka StatefulSet to 3, weeks later notices storage cost hasn't dropped — the two PVCs outlived their pods. The lesson is institutional: StatefulSet scale-down is a *data* decision (was there data on those ordinals?), not a capacity one.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------- | ------------------------------------------------------------------------ |
| Scaling a StatefulSet down and assuming storage follows | PVCs outlive their pods by design — clean up or reattach deliberately |
| Omitting `serviceName` (headless Service) | Pod DNS doesn't resolve; clients that address replicas break |
| Using a normal Service for StatefulSet DNS | Only headless (`clusterIP: None`) creates per-pod A records |
| DaemonSet missing control-plane tolerations | Agents silently absent from masters — logs and CNI gaps there |
| Leaving `partition` set after a canary rollout | Most replicas keep running the old version indefinitely |
| `hostPath` volumes without a plan | DaemonSets need node access, but pin paths and use `type: Directory` |
| Choosing StatefulSet "to be safe" for stateless work | You pay ordered, slower operations for identity you don't use |

## Best Practices

1. **Ask the identity question first** — "if a pod comes back as someone else, does the system break?" Only a yes earns a StatefulSet; otherwise a Deployment is faster to operate.
2. **Pair every StatefulSet with its headless Service and name the DNS contract** for clients (`pod-0.svc` is an API, not an implementation detail).
3. **Use `partition` canaries for stateful rollouts** — update one ordinal, verify, walk the partition down; `OnDelete` when the workload must own its restart timing.
4. **Monitor orphaned PVCs** — a scheduled check for claims with no matching pod catches the billing-and-surprise drift.
5. **For DaemonSets, decide node coverage explicitly** — tolerations, `nodeSelector`, and tainted-node behavior are the spec, not afterthoughts.
6. **Budget StatefulSet operations in time** — ordered replacement of a 10-replica quorum takes ten Ready-waits; say so in the runbook before the incident.

## Summary

- StatefulSets manage stateful applications with stable network identities and persistent storage
- DaemonSets ensure exactly one pod runs on each node, ideal for logging, monitoring, and networking agents
- StatefulSets provide ordered deployment, scaling, and rolling updates for databases and message queues
- DaemonSets automatically schedule pods on new nodes as they join the cluster
- Headless Services are typically used with StatefulSets for stable DNS names per pod

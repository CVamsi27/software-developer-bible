# StatefulSets & DaemonSets

A replacement API Pod can use a different name and a different disk. A database member or node-level agent may not be interchangeable in that way. StatefulSets and DaemonSets solve those two placement problems: stable member identity and per-node coverage.

## Definition

A **StatefulSet** manages Pods with stable ordinal names and a corresponding storage identity. A **DaemonSet** requests one Pod on each node that matches its scheduling rules.

> **Textbook Definition:** A StatefulSet is a workload controller that maintains an ordered or parallel set of Pods with stable identities and persistent-volume claims. A DaemonSet is a controller that maintains a Pod on each eligible node.

Neither controller implements the application protocol. A StatefulSet does not replicate a database or elect a leader; a DaemonSet does not prove every node's agent is healthy.

## First Principles

A Deployment is the right default when replicas are interchangeable. Use a StatefulSet only when the application needs to recognize a particular member after replacement, such as a broker that rejoins with its own data. Use a DaemonSet when the desired population follows eligible machines rather than a fixed replica number, such as a network plugin or node log collector.

## How It Works

### 1. Preserve a Member's Identity Across Pod Replacement

A StatefulSet names Pods with stable ordinals such as `ledger-0` and `ledger-1`. The Pod object and IP can change; the ordinal remains the member's identity. Its `volumeClaimTemplates` create a separate claim for each ordinal, so a replacement `ledger-1` can request its prior claim when storage topology and attachment rules allow it.

Pair the StatefulSet with a governing Service. A headless Service (`clusterIP: None`) provides per-Pod DNS records when clients or a peer-discovery protocol need them. DNS identity is not database membership: the application or operator must still manage replication, quorum, backup, failover, and recovery.

This example demonstrates three separate PostgreSQL data directories. It is **not** a replicated cluster — use an application-specific operator or documented replication design when replicas must coordinate. A default or suitably configured StorageClass, the `db-credentials` Secret, and a compatible volume provisioner must already exist.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ledger
spec:
  clusterIP: None
  selector:
    app: ledger
  ports:
    - name: postgres
      port: 5432
      targetPort: postgres
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: ledger
spec:
  serviceName: ledger
  replicas: 3
  selector:
    matchLabels:
      app: ledger
  template:
    metadata:
      labels:
        app: ledger
    spec:
      containers:
        - name: postgres
          image: postgres:18
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
          ports:
            - name: postgres
              containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 10Gi
```

### 2. Roll Members Out in a Controlled Order

By default, `OrderedReady` starts Pods in ascending order and terminates them in descending order, waiting on readiness between operations. This can protect ordered initialization, but one Pod that never becomes Ready can block later scaling or rollout steps. `podManagementPolicy: Parallel` changes scaling order; it does not remove the separate update strategy.

For `RollingUpdate`, `partition` lets an operator hold lower ordinals on the old template while higher ordinals receive the new one. Lower the partition after checking the canary member. `OnDelete` leaves existing Pods on their old template until an operator deletes them. Neither policy knows whether a database replica has caught up; readiness must reflect the application's required condition, and the rollout owner must verify membership before continuing.

### 3. Retain Claims as a Data-Lifecycle Decision

Claims are retained by default when the StatefulSet scales down or is deleted. `persistentVolumeClaimRetentionPolicy` can change retention on supported clusters. Treat a change to that policy as a data-lifecycle decision: deleting a claim can trigger the storage class's reclaim behavior, while retaining claims preserves data and can preserve ongoing storage cost. Inspect the claims as well as the Pods after scale-down — a deleted Pod does not imply its claim or stored data was deleted.

### 4. Follow Node Eligibility with a DaemonSet

A DaemonSet asks for a Pod on each node selected by its node selector, affinity, and tolerations. A newly eligible node adds another desired Pod; removing or excluding a node removes it from the desired population. The DaemonSet controller accounts for node scheduling and creates node-bound Pods, but a resource shortage, image-pull failure, or broken agent can leave a node without a working copy.

Updates normally replace each node's Pod according to the DaemonSet update strategy. `maxUnavailable` trades rollout speed against temporary coverage; `maxSurge`, when supported and configured, permits overlap. An agent that provides the node's networking or storage has a special failure domain: follow the plugin's supported upgrade order rather than assuming a generic rolling update is safe.

A DaemonSet shape for a node-local agent looks like this. Replace the image and selector with the cluster's supported agent and node policy; host filesystem mounts and privileges require an explicit security review.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      nodeSelector:
        kubernetes.io/os: linux
      containers:
        - name: agent
          image: registry.example.com/node-agent:1.2.3
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
```

Check the number of desired, current, ready, and available Pods per node during rollout. Desired coverage is a controller target, not an availability measurement.

### 5. Choose the Controller from the Identity Requirement

| Requirement | Choose | Verify |
| ---------------------------------------- | ----------- | ------------------------------------------------------- |
| Interchangeable application replicas | Deployment | Readiness, rollout capacity and compatible versions |
| Stable member name and per-member claim | StatefulSet | Storage attachment, member health and retention policy |
| One node-local process on selected nodes | DaemonSet | Node eligibility, actual readiness and upgrade coverage |

## Summary

StatefulSets preserve ordinal identity and claim association; DaemonSets make desired workload placement follow eligible nodes. Choose between them from the application's identity or placement requirement. Storage, quorum, node-agent health, and safe upgrades remain explicit operational responsibilities.

# Jobs & CronJobs

## Definition

**Jobs** manage short-lived, batch workloads that run to completion. **CronJobs** create Jobs on a time-based schedule. Both are essential for ETL pipelines, database migrations, backups, report generation, and cleanup tasks in Kubernetes.

> **Textbook Definition:** A Kubernetes Job reconciles a batch workload toward defined completion criteria. A CronJob creates Jobs according to a schedule, with explicit concurrency and missed-run policies rather than an exactly-once execution guarantee.

## First Principles

Batch work in a reconciled world has different guarantees than servers:

1. **A Job is "run to completion, retry on failure"** — the reconciler's answer to tasks (vs services). completions/parallelism shape the fan-out; backoffLimit bounds the churn.
2. **CronJob = schedule → Job** — with the distributed-cron hazard (→ 20.2.4.04): startingDeadlineSeconds and concurrencyPolicy (Allow/Forbid/Replace) are the levers that make the schedule honest under missed ticks.
3. **Batch jobs are the classic cluster-abuser** — resource requests/limits and quotas (→ 40.2.4.04) keep them from starving serving traffic.

## Why Do We Need It?

1. **Jobs**: Run-to-completion tasks, parallel processing, bounded retries with backoff and completion tracking; application effects still need idempotency
2. **CronJobs**: Scheduled jobs (backups @daily, report generation @weekly), timezone-aware, concurrency policies

## How It Works

### Job mechanics: completion is a first-class state

A Job's reconciler counts *successful completions* against `completions`, launching pods until the count is met. Job Pod templates allow `Never` or `OnFailure`, not `Always`. Duplicate execution is possible even with one completion: retries or controller recovery can start the same logical work more than once. The three fields interact precisely: `backoffLimit` bounds *failed* pod attempts (exceeded → the Job fails and stops launching), `activeDeadlineSeconds` bounds *wall-clock time* for the whole Job (exceeded → everything is terminated and the Job fails — even mid-retry), and `parallelism` sets how many pods run at once. Completion modes matter at scale: `NonIndexed` (default) treats all pods as interchangeable workers pulling from shared work; `Indexed` assigns each pod a unique index (`completion-index=N` annotation + hostname) — the contract that lets N pods partition an N-way task (shard N of the dataset, segment N of the export).

The cleanup lever people miss: completed Job *objects* (and their pods) linger forever unless `ttlSecondsAfterFinished` is set — a cluster that runs many batch jobs accumulates thousands of Completed pods that break listing tools and clutter scheduler caches. TTL-based cleanup (or the older cron-based cleanup pattern) is part of the Job spec, not an ops afterthought. And `suspend: true` gives Jobs a stopped state — the pattern for deferred or manually gated batch work.

### CronJob mechanics: the schedule is a promise the controller tries to keep

The CronJob controller wakes every ~10 seconds, evaluates each schedule, and creates a Job when a tick is due. The honest-cron problems all live in how it handles *missed* ticks: `startingDeadlineSeconds` defines how late a Job may still start (a tick missed beyond the deadline is skipped and counted); with no deadline set, missed runs beyond a controller-level limit (~100 consecutive misses) cause the controller to decline creation for that reconciliation and emit a warning — a deliberate circuit-breaker against e.g. a suspended cluster silently queueing a year of backups. `concurrencyPolicy` is the race-condition lever: `Allow` (default — overlap, correct for independent work), `Forbid` (skip if the previous Job is active — correct for backups), `Replace` (kill the old, start new — correct when only the freshest run matters). `timeZone` (stable since 1.27) pins schedule interpretation to a civil timezone. DST can skip or repeat a local clock time; the schedule is not an exactly-once guarantee.

## Code Examples

### Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 3
  activeDeadlineSeconds: 300
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migration
        image: myapp:latest
        command: ["npm", "run", "migrate"]
```

### CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
spec:
  schedule: "0 2 * * *"
  timeZone: "America/New_York"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: postgres:15
            command: ["sh", "-c"]
            args:
              - 'pg_dump -h database -U admin mydb > /backup/backup-$(date -u +%Y%m%dT%H%M%SZ).sql'
            env:
              - name: PGPASSWORD
                valueFrom:
                  secretKeyRef:
                    name: database-backup-auth
                    key: password
            volumeMounts:
              - name: backup-storage
                mountPath: /backup
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backups
          restartPolicy: Never
```

The CronJob assumes a reachable `database` Service, a provisioned `backups` PVC, and a narrowly scoped backup credential Secret. It writes a file rather than merely printing a dump to logs. Protect and retain that storage, copy it off-cluster where required, and verify restores.

## Real-World Usage

- **Database migrations as a release step** — the expand/contract discipline (→ 30.3.5) runs each migration as a Job gated in the deploy pipeline, never as boot logic: one completion, bounded retries, and the Job's success is the pipeline's go/no-go signal. Running migrations-on-boot from N replicas is the replica-race hazard twelve-factor flags (→ 40.9.02 Q14).
- **The nightly backup is the canonical `Forbid` CronJob** — `pg_dump` to object storage at 02:00 local time, `concurrencyPolicy: Forbid` so a slow night can't stack a second dump, `successfulJobsHistoryLimit` low because history is not backup. The backup-is-a-drill lesson applies: a Job that completes is not a backup until a restore has consumed it.
- **Fan-out batch processing with `Indexed` completion** — report generation across N shards: one Job, `completions: N`, `parallelism: M < N`, each pod reads its index and processes its slice. The map-reduce shape without a framework, and the reason `Indexed` exists.
- **Finite queue-drain work fits Jobs** — a nightly reconciliation that consumes a backlog until empty: run to completion, `OnFailure` restart for transient errors, and the Job's Completion is the monitoring signal An ongoing queue consumer is appropriately a Deployment; use a Job when there is a meaningful finite completion condition.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| Using Deployment for one-shot tasks | Use Job — it tracks completion |
| Omitting an explicit retry budget | Default backoffLimit is 6; choose and monitor a suitable budget |
| No activeDeadlineSeconds | Job runs indefinitely |
| CronJob without concurrencyPolicy | Overlapping runs cause data corruption |
| Choosing restart policy accidentally | Never preserves separate failed Pods; OnFailure restarts containers in the same Pod |
| No resource limits | Job pods can consume unlimited resources |

## Best Practices

1. **Set backoffLimit** — choose a bounded retry budget for the task
2. **Set activeDeadlineSeconds** — kill stuck jobs after timeout
3. **Choose concurrencyPolicy** — Forbid prevents overlap between Jobs of this CronJob; independent CronJobs can still overlap
4. **Set successfulJobsHistoryLimit** — clean up completed Jobs
5. **Use separate ServiceAccounts** — least privilege for Job pods
6. **Monitor Job status** — `kubectl get jobs -w` for live updates

## Summary

- Jobs manage batch processing tasks that run to completion, with retry and parallelism controls
- CronJobs schedule Jobs on a time-based schedule using standard cron syntax
- Jobs support parallel execution via completions and parallelism parameters for distributed processing
- Failed Jobs automatically retry based on the backoffLimit and restartPolicy configuration
- CronJob concurrency policies (Allow, Forbid, Replace) control overlapping execution behavior

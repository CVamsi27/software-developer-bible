# Jobs & CronJobs

## TL;DR

Jobs run a workload to completion. CronJobs schedule Jobs on a cron expression. Both support parallelism, backoff, and history limits.

**Why it matters:** Tests completion semantics, retries with exponential backoff, concurrency policies, and the common mistake of using a Deployment for a one-shot task.

## First Principles

Batch work in a reconciled world has different guarantees than servers:

1. **A Job is "run to completion, retry on failure"** — the reconciler's answer to tasks (vs services). completions/parallelism shape the fan-out; backoffLimit bounds the churn.
2. **CronJob = schedule → Job** — with the distributed-cron hazard (→ 20.2.4.04): startingDeadlineSeconds and concurrencyPolicy (Allow/Forbid/Replace) are the levers that make the schedule honest under missed ticks.
3. **Batch jobs are the classic cluster-abuser** — resource requests/limits and quotas (→ 40.2.4.04) keep them from starving serving traffic.

## Definition

**Jobs** manage short-lived, batch workloads that run to completion. **CronJobs** create Jobs on a time-based schedule. Both are essential for ETL pipelines, database migrations, backups, report generation, and cleanup tasks in Kubernetes.

## Why Do We Need It?

1. **Jobs**: Run-to-completion tasks, parallel processing, retry with backoff, guaranteed execution
2. **CronJobs**: Scheduled jobs (backups @daily, report generation @weekly), timezone-aware, concurrency policies

## How It Works

### Job mechanics: completion is a first-class state

A Job's reconciler counts *successful completions* against `completions`, launching pods until the count is met — which is why a Job pod's `restartPolicy` can never be `Always`: a pod that restarts forever can never report "done." The three fields interact precisely: `backoffLimit` bounds *failed* pod attempts (exceeded → the Job fails and stops launching), `activeDeadlineSeconds` bounds *wall-clock time* for the whole Job (exceeded → everything is terminated and the Job fails — even mid-retry), and `parallelism` sets how many pods run at once. Completion modes matter at scale: `NonIndexed` (default) treats all pods as interchangeable workers pulling from shared work; `Indexed` assigns each pod a unique index (`completion-index=N` annotation + hostname) — the contract that lets N pods partition an N-way task (shard N of the dataset, segment N of the export).

The cleanup lever people miss: completed Job *objects* (and their pods) linger forever unless `ttlSecondsAfterFinished` is set — a cluster that runs many batch jobs accumulates thousands of Completed pods that break listing tools and clutter scheduler caches. TTL-based cleanup (or the older cron-based cleanup pattern) is part of the Job spec, not an ops afterthought. And `suspend: true` gives Jobs a stopped state — the pattern for deferred or manually gated batch work.

### CronJob mechanics: the schedule is a promise the controller tries to keep

The CronJob controller wakes every ~10 seconds, evaluates each schedule, and creates a Job when a tick is due. The honest-cron problems all live in how it handles *missed* ticks: `startingDeadlineSeconds` defines how late a Job may still start (a tick missed beyond the deadline is skipped and counted); with no deadline set, missed runs beyond a controller-level limit (~100 consecutive misses) cause the CronJob to stop scheduling entirely and emit a warning — a deliberate circuit-breaker against e.g. a suspended cluster silently queueing a year of backups. `concurrencyPolicy` is the race-condition lever: `Allow` (default — overlap, correct for independent work), `Forbid` (skip if the previous Job is active — correct for backups), `Replace` (kill the old, start new — correct when only the freshest run matters). `timeZone` (stable since 1.27) pins schedules to a civil timezone so a 02:00 backup stays 02:00 across DST shifts.

## Code Examples

### Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 3
  activeDeadlineSeconds: 300
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migration
        image: myapp:latest
        command: ["npm", "run", "migrate"]
```

### CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
spec:
  schedule: "0 2 * * *"
  timeZone: "America/New_York"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: postgres:15
            command: ["pg_dump", "-U", "admin", "mydb"]
          restartPolicy: Never
```

## Real-World Usage

- **Database migrations as a release step** — the expand/contract discipline (→ 30.3.5) runs each migration as a Job gated in the deploy pipeline, never as boot logic: one completion, bounded retries, and the Job's success is the pipeline's go/no-go signal. Running migrations-on-boot from N replicas is the replica-race hazard twelve-factor flags (→ 40.9.02 Q14).
- **The nightly backup is the canonical `Forbid` CronJob** — `pg_dump` to object storage at 02:00 local time, `concurrencyPolicy: Forbid` so a slow night can't stack a second dump, `successfulJobsHistoryLimit` low because history is not backup. The backup-is-a-drill lesson applies: a Job that completes is not a backup until a restore has consumed it.
- **Fan-out batch processing with `Indexed` completion** — report generation across N shards: one Job, `completions: N`, `parallelism: M < N`, each pod reads its index and processes its slice. The map-reduce shape without a framework, and the reason `Indexed` exists.
- **Queue-drain workers are Jobs, not Deployments** — a nightly reconciliation that consumes a backlog until empty: run to completion, `OnFailure` restart for transient errors, and the Job's Completion is the monitoring signal (a Deployment worker that idles forever is the misuse this workload class exists to prevent).

## Common Mistakes

| Mistake | Fix |
| ----------------------------------- | ---------------------------------------- |
| Using Deployment for one-shot tasks | Use Job — it tracks completion |
| No backoffLimit | Job retries forever on failure |
| No activeDeadlineSeconds | Job runs indefinitely |
| CronJob without concurrencyPolicy | Overlapping runs cause data corruption |
| Missing restartPolicy: Never | OnFailure is better for debugging |
| No resource limits | Job pods can consume unlimited resources |

## Best Practices

1. **Set backoffLimit** — prevent infinite retries (3 is typical)
2. **Set activeDeadlineSeconds** — kill stuck jobs after timeout
3. **Use concurrencyPolicy: Forbid** for CronJobs — prevent overlapping runs
4. **Set successfulJobsHistoryLimit** — clean up completed Jobs
5. **Use separate ServiceAccounts** — least privilege for Job pods
6. **Monitor Job status** — `kubectl get jobs -w` for live updates

## Summary

- Jobs manage batch processing tasks that run to completion, with retry and parallelism controls
- CronJobs schedule Jobs on a time-based schedule using standard cron syntax
- Jobs support parallel execution via completions and parallelism parameters for distributed processing
- Failed Jobs automatically retry based on the backoffLimit and restartPolicy configuration
- CronJob concurrency policies (Allow, Forbid, Replace) control overlapping execution behavior

## Cheat Sheet
```text
JOBS & CRONJOBS CHEAT SHEET
═══════════════════════════════════════════════════════════════

JOB:
• Runs to completion (batch workloads)
• Key fields: completions, parallelism, backoffLimit
• restartPolicy: Never (debug) or OnFailure (retry)
• activeDeadlineSeconds: kill stuck jobs

CRONJOB:
• Creates Jobs on schedule (cron syntax)
• schedule: "0 2 * * *" (daily at 2am)
• timeZone: "America/New_York" (timezone-aware)
• concurrencyPolicy: Allow|Forbid|Replace
• successfulJobsHistoryLimit: 3
• failedJobsHistoryLimit: 1

PARALLEL JOBS:
• completions: N (total pods to complete)
• parallelism: M (concurrent pods)
• indexed: true (give each pod an index)
• Use for: map-reduce, batch processing

CONCURRENCY POLICIES:
• Allow — multiple Jobs run simultaneously
• Forbid — skip new if previous still running
• Replace — cancel running, start new

WHEN TO USE:
• Database migrations (Job)
• Daily backups (CronJob)
• Report generation (CronJob)
• Data pipeline (Job with parallelism)
• Cleanup tasks (CronJob)

IN INTERVIEWS:
• Job vs Deployment (completion semantics)
• backoffLimit + activeDeadlineSeconds
• concurrencyPolicy trade-offs
• restartPolicy: Never vs OnFailure
```

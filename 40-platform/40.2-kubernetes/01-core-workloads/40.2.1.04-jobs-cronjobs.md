# Jobs & CronJobs

## Definition

**Jobs** manage short-lived, batch workloads that run to completion. **CronJobs** create Jobs on a time-based schedule. Both are essential for ETL pipelines, database migrations, backups, report generation, and cleanup tasks in Kubernetes.

> **Textbook Definition:** A Kubernetes Job reconciles a batch workload toward defined completion criteria. A CronJob creates Jobs according to a schedule, with explicit concurrency and missed-run policies rather than an exactly-once execution guarantee.

## First Principles

Batch work in a reconciled world has different guarantees than servers:

1. A Job controller reconciles finite work toward completion; `completions` and `parallelism` shape its work, while retry and deadline policies bound attempts.
2. A CronJob creates Jobs from a schedule. Missed ticks, overlapping work, and controller delays mean the schedule is not an exactly-once timer; `startingDeadlineSeconds` and `concurrencyPolicy` define the intended response.
3. Batch work shares cluster capacity with services. Set realistic requests, choose limits deliberately, and use quotas where needed to keep batch demand within the cluster's budget.

## Why Do We Need It?

1. **Jobs**: Run-to-completion tasks, parallel processing, bounded retries with backoff and completion tracking; application effects still need idempotency
2. **CronJobs**: Scheduled jobs (backups @daily, report generation @weekly), timezone-aware, concurrency policies

## How It Works

### Job mechanics: completion is a first-class state

A Job controller counts successful completions against `completions` and creates Pods until the target is met. Job Pod templates allow `Never` or `OnFailure`, not `Always`. Duplicate execution is possible even for one completion: retries or controller recovery can repeat the same logical work. `backoffLimit` bounds counted failures under the configured restart and failure policies; `activeDeadlineSeconds` bounds the Job's wall-clock runtime and terminates active work when exceeded; `parallelism` caps concurrent Pods. `NonIndexed` (the default) treats workers as interchangeable. `Indexed` assigns each Pod a completion index, exposed through the `batch.kubernetes.io/job-completion-index` label and hostname, so work can be partitioned by stable index.

Completed Job objects and Pods can remain until a cleanup policy removes them. `ttlSecondsAfterFinished` enables cleanup after terminal completion or failure; CronJob history limits are a separate retention mechanism. Large histories add API objects and complicate inspection. `suspend: true` stops a Job; suspending an active Job terminates its active Pods and does not checkpoint their process memory.

### CronJob mechanics: the schedule is a promise the controller tries to keep

The controller checks schedules periodically (the default check interval is about 10 seconds), so a CronJob is not a precise timer. `startingDeadlineSeconds` bounds how late a missed run may start; when it is unset and more than about 100 schedules are missed, the controller declines catch-up creation for that reconciliation and records a warning. `concurrencyPolicy` applies only to Jobs created by that CronJob: `Allow` permits overlap, `Forbid` skips a tick while its prior Job is active, and `Replace` terminates that Job before starting another. The stable `timeZone` field (Kubernetes 1.27+) makes the schedule's civil timezone explicit. Daylight-saving transitions can skip or repeat a local clock time, so choose UTC when the workload requires a uniform interval.

### Trace completions independently from attempts

For an Indexed Job with four completions and parallelism two, the controller runs at most two Pods concurrently. A successful index counts toward completion; a failed attempt can be retried for that index. Two attempts can execute the same logical index, so persist output or idempotency under the index rather than the Pod name. The Job finishes when its completion criteria are met or enters terminal failure when its deadline or failure policy is met. An application write committed just before a crash survives even when Kubernetes records that attempt as failed.

Forbid coordinates Jobs belonging to one CronJob; it is not a lock shared by other CronJobs or manual commands. Replace can stop an active run and start a new one, but cannot undo the interrupted run's external effects. Choose skip, overlap, or replace from that business meaning before picking a schedule.

## Code Examples

### Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 3
  activeDeadlineSeconds: 300
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migration
        image: myapp:1.0.0
        command: ["npm", "run", "migrate"]
```

The image must include the migration command, database connectivity, and credentials. The example sets retry/deadline bounds but cannot make a non-idempotent migration safe to repeat. Observe Job status and logs; a terminal failed Job does not keep retrying automatically.

### CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
spec:
  schedule: "0 2 * * *"
  timeZone: "Etc/UTC"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: postgres:18
            command: ["sh", "-c"]
            args:
              - 'pg_dump -h database -U admin mydb > /backup/backup-$(date -u +%Y%m%dT%H%M%SZ).sql'
            env:
              - name: PGPASSWORD
                valueFrom:
                  secretKeyRef:
                    name: database-backup-auth
                    key: password
            volumeMounts:
              - name: backup-storage
                mountPath: /backup
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backups
          restartPolicy: Never
```

The CronJob assumes a reachable PostgreSQL 18 `database` Service, a provisioned `backups` PVC, and a narrowly scoped backup credential Secret. Its `pg_dump` client major matches the server. It writes a file rather than merely printing a dump to logs. This example runs at 02:00 UTC to avoid daylight-saving ambiguity. Protect and retain that storage, copy it off-cluster where required, and verify restores.

## Real-World Usage

- **Database migrations as a release step** — the expand/contract discipline (→ 30.3.5) runs each migration as a Job gated in the deploy pipeline, never as boot logic: one completion, bounded retries, and the Job's success is the pipeline's go/no-go signal. Running migrations-on-boot from N replicas is the replica-race hazard twelve-factor flags (→ 40.9.02 Q14).
- **A nightly backup can use a `Forbid` CronJob** — `pg_dump` to persistent backup storage at 02:00 UTC, with a separate off-cluster copy policy. `concurrencyPolicy: Forbid` skips a tick while the previous dump runs; `successfulJobsHistoryLimit` controls Job history, not backup retention. A completed dump is not a verified backup until a restore succeeds.
- **Fan-out batch processing with `Indexed` completion** — report generation across N shards: one Job, `completions: N`, `parallelism: M < N`, each pod reads its index and processes its slice. The map-reduce shape without a framework, and the reason `Indexed` exists.
- **Finite queue-drain work fits Jobs** — a nightly reconciliation that consumes a backlog until empty: run to completion, `OnFailure` restart for transient errors, and the Job's Completion is the monitoring signal. An ongoing queue consumer is appropriately a Deployment; use a Job when there is a meaningful finite completion condition.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Using Deployment for one-shot tasks | Use Job — it tracks completion |
| Relying on an implicit retry budget | Set and monitor a retry budget that fits the side effects and recovery cost |
| No activeDeadlineSeconds | A stuck process can continue running indefinitely |
| Overlap policy chosen accidentally | Overlap is safe only when the task's effects permit it |
| Choosing restart policy accidentally | Never preserves separate failed Pods; OnFailure restarts containers in the same Pod |
| Requests and limits left to defaults | Requests affect placement; configured limits affect runtime use, so set each from workload needs and apply namespace quotas where appropriate |

## Best Practices

1. **Set backoffLimit** — choose a bounded retry budget for the task
2. **Set activeDeadlineSeconds** — kill stuck jobs after timeout
3. **Choose concurrencyPolicy** — Forbid prevents overlap between Jobs of this CronJob; independent CronJobs can still overlap
4. **Set successfulJobsHistoryLimit** — clean up completed Jobs
5. **Use separate ServiceAccounts** — least privilege for Job pods
6. **Monitor Job status** — `kubectl get jobs -w` for live updates

## Summary

- Jobs manage batch processing tasks that run to completion, with retry and parallelism controls
- CronJobs schedule Jobs on a time-based schedule using standard cron syntax
- Jobs support parallel execution via completions and parallelism parameters for distributed processing
- Failed attempts can retry within configured budgets; terminal failed Jobs require a deliberate new run or repair
- CronJob concurrency policies (Allow, Forbid, Replace) control overlapping execution behavior

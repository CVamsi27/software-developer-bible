# Jobs & CronJobs

A scheduled backup is not a timer that runs code exactly once. The control plane can miss a schedule, retry a failed Pod, or create a replacement while earlier work is still terminating. Design the work so that the same logical run can be attempted again without corrupting its result.

## Definition

A **Job** manages finite work until its completion criteria are met or its failure policy is reached. A **CronJob** creates Jobs on a schedule and defines how missed or overlapping runs are handled.

> **Textbook Definition:** A Kubernetes Job controller reconciles Pods toward a specified number of successful completions under retry and deadline policies. A CronJob controller creates Jobs from a time-based schedule with bounded catch-up and concurrency behavior.

## First Principles

A Deployment keeps service Pods running; a Job stops when finite work completes. `completions` describes how many successful units are required, and `parallelism` caps the intended concurrent workers. The application must make progress, record its result durably and tolerate retries: Kubernetes status tracks Pod attempts, not a transaction with the database or external API the worker changes.

## Let a Job account for finite work

With `completionMode: NonIndexed` (the default), workers are interchangeable. An Indexed Job assigns each completion a stable index so the application can map it to a shard or partition. `backoffLimit` bounds failed attempts, and `activeDeadlineSeconds` bounds the Job's elapsed runtime. They protect against different failure modes: repeated exits versus work that never finishes.

The Pod template must use `restartPolicy: Never` or `OnFailure`. With `Never`, a failed Pod remains available for diagnosis while the Job controller creates another attempt. With `OnFailure`, the kubelet can restart a failed container inside the same Pod; those restarts also count toward Job failure handling. Completed Job objects remain until cleanup; `ttlSecondsAfterFinished` can remove a finished Job and its Pods after a delay.

Even one completion with parallelism one can start the program more than once. An attempt may commit a database write and then fail before Kubernetes records success. Key durable output by a business idempotency key or completion index, and make retries safe. For Indexed Jobs, `backoffLimitPerIndex` (stable since Kubernetes 1.33) bounds failures independently for each index; `maxFailedIndexes` can stop a run after too many shards fail. The stable `podFailurePolicy` (since 1.31) can count, ignore, fail an index, or fail the Job based on Pod failure conditions. It requires `restartPolicy: Never`.

A terminating Pod can overlap with its replacement depending on the configured replacement policy. `parallelism` is a target, not an exactly-one-process guarantee. Check the current Pod lifecycle and failure policy when duplicate concurrency would be unsafe.

This example runs one bounded migration attempt. The image must include the migration command and credentials, and the migration itself must tolerate the retry policy or detect that it already completed.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: schema-migration
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 2
  activeDeadlineSeconds: 300
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/catalog:1.4.2
          command: ["npm", "run", "migrate"]
```

## Let a CronJob create scheduled attempts

A CronJob controller checks schedules periodically, so a run is approximate rather than a precise alarm. `startingDeadlineSeconds` limits how late a missed run may start. More than 100 missed schedules can prevent catch-up; when a deadline is set, the controller counts missed schedules within that deadline window. `timeZone` makes the schedule's civil timezone explicit. Use UTC for uniform operational intervals, and account for daylight-saving changes if the business schedule is local time.

Choose `concurrencyPolicy` from the effect of overlap:

- `Allow` (default) permits Jobs from this CronJob to overlap.
- `Forbid` skips a scheduled time while a prior Job from this CronJob is active; other CronJobs and manual invocations remain independent.
- `Replace` requests cancellation of the prior Job and starts the new scheduled Job. Cancellation does not undo writes already made or prove that the old process stopped before new work begins.

A CronJob update changes the template for Jobs created later. It does not change a Job that is already running. Since Kubernetes 1.32, created Jobs carry an annotation with their originally scheduled timestamp, which helps distinguish scheduled time from actual start time during diagnosis.

This backup example assumes a reachable PostgreSQL 18 Service, a `backups` PVC, and a narrowly scoped Secret. It writes a named dump file to the mounted volume. Protect that storage, copy backups off-cluster as required, and verify recovery by restoring them.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"
  timeZone: "Etc/UTC"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 900
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 2
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 1800
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: backup
              image: postgres:18
              command: ["sh", "-c"]
              args:
                - 'pg_dump -h database -U backup mydb > /backup/mydb-$(date -u +%Y%m%dT%H%M%SZ).sql'
              env:
                - name: PGPASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: database-backup-auth
                      key: password
              volumeMounts:
                - name: backup-storage
                  mountPath: /backup
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backups
```

A skipped tick under `Forbid` is not queued as a durable work item. The application must record which business interval has been completed if missing one is unacceptable. A successful Job condition means the command exited successfully; it does not prove the file is complete, retained, restorable or replicated off-cluster.

## Diagnose the difference between attempts and effects

```bash
kubectl get cronjob,job,pods
kubectl describe cronjob nightly-backup
kubectl describe job <job-name>
kubectl logs job/<job-name>
```

Check the CronJob's scheduled timestamp, Job status, Pod exit reason and application-level run identifier. A terminally failed Job does not retry forever; repair the cause and create or schedule another run intentionally. Use `kubectl create job --from=cronjob/nightly-backup manual-backup` only when the manual execution's effects and overlap are safe.

## Summary

Jobs account for finite successful completions under retry and deadline policies. CronJobs create those Jobs approximately on schedule and apply a per-CronJob overlap policy. Both can repeat or miss logical work; idempotency, durable run identity, output verification and recovery remain application responsibilities.

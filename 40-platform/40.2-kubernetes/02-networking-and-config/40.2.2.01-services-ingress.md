# Kubernetes Services & Ingress

## Definition

A **Service** gives clients a stable way to reach changing backend endpoints. A normal ClusterIP Service has a virtual IP and DNS name; a headless Service returns endpoint addresses without that virtual IP. An **Ingress** declares HTTP host/path routing. A matching **ingress controller** reads those declarations and configures a proxy or load balancer to carry traffic.

## First Principles

A Pod can disappear and return at a different address. A caller therefore needs discovery separate from the Pod's lifetime. Discovery alone does not forward packets: a Service data plane must route connections to eligible endpoints. HTTP routing adds another decision — which backend owns this hostname and path — so it needs both a declaration and an implementation.

## Follow One Request Before Choosing an Exposure Type

Suppose a browser calls `https://api.example.com/orders` while the `api` Deployment replaces a Pod:

1. DNS directs the browser to the published edge address.
2. The configured edge controller terminates TLS and matches the host/path.
3. The route identifies the `api` Service and its **Service port**.
4. The controller resolves the Service's endpoints; some implementations proxy directly to endpoint addresses rather than traversing the ClusterIP.
5. An eligible backend receives the request at its **target port**. EndpointSlice updates allow replacement Pods to enter the backend set when ready.

```text
route declaration ──watched by──> controller config
                                      │
browser ──> published edge ──> HTTP proxy ──> api endpoint:8080
                                      │
                         Service api:80 identifies backends
```

An Ingress object is configuration, not an extra network hop. A Service does not preserve an in-memory session when its backend disappears, and readiness does not guarantee that every request during shutdown succeeds. Draining, retry policy, and application state still matter.

## Why These Objects Are Separate

| Role | Object or implementation | Responsibility |
| ---------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------- |
| Stable backend discovery | Service + EndpointSlices | Map a service name to eligible backends |
| Connection forwarding | kube-proxy or another Service implementation | Implement virtual-IP forwarding where used |
| HTTP routing | Ingress + matching controller | Select a backend by host/path and implement TLS policy |
| More explicit edge ownership | Gateway API + compatible implementation | Separate infrastructure class, listener, and application route responsibilities |

Service data planes vary: kube-proxy has multiple modes, and some CNIs provide an alternative implementation. Diagnose the implementation actually installed rather than assuming every packet crosses an iptables or IPVS rule.

## Choose Who Can Reach the Service

| Service type | What changes | Boundary to verify |
| ---------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| ClusterIP | Allocates a virtual IP, normally for internal access | Routing and network policies determine reachability; “internal” is not authorization |
| NodePort | Exposes a port through reachable node addresses | NodePort range, node address selection, firewall and routing policy |
| LoadBalancer | Requests an external load balancer from an installed implementation | Cloud or on-prem integration, internal/external placement, health checks and cost |
| ExternalName | Returns a DNS CNAME for an external name | No proxying or automatic rewriting of HTTP Host/TLS names |
| Headless (`clusterIP: None`) | Returns endpoint addresses without a Service virtual IP | The client chooses/connects to backends; common for stateful discovery |

A LoadBalancer Service is not inherently cloud-only. NodePort is not inherently unsuitable for production; it can be part of an intentional edge design. There is no universal latency ordering across these types.

## Code Examples

### Map a Service Port to the Container's Port

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  type: ClusterIP
  selector:
    app: api
  ports:
    - name: http
      port: 80
      targetPort: 8080
      protocol: TCP
```

This assumes Pods labeled `app: api` listen on port 8080. An Ingress backend refers to port **80**, not 8080. A matching selector alone is insufficient: inspect readiness and the EndpointSlices. A Service without a selector requires a separately managed endpoint arrangement; Kubernetes cannot discover its backends from Pod labels.

### Declare HTTP Routing Without Controller-Specific Annotations

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
spec:
  ingressClassName: edge
  tls:
    - hosts:
        - api.example.com
      secretName: api-tls
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 80
```

Prerequisites: an `IngressClass` named `edge`, its supported controller, a published address, DNS, the `api` Service in the same namespace, and a suitable TLS Secret. The `/api` prefix is forwarded as part of the path unless the chosen implementation explicitly rewrites it. Prefix matching follows path elements (`/api` does not match `/apiculture`). `tls:` supplies certificate configuration; redirect behavior and backend TLS require separate implementation-specific configuration.

Ingress annotations are not a portable API for rate limits, rewrites, or timeouts. Choose the controller first, then use its supported policy fields or annotations. For rate limiting, verify the identity being limited, replica aggregation, forwarded-client-IP trust, and failure behavior. Putting a plausible annotation in YAML does not ensure the controller implements it.

### The Retired Controller and the Supported API Are Different

The community **ingress-nginx** controller retired in March 2026. Its existing deployments and artifacts remain available, but there are no further releases, bug fixes, or security updates. This retirement does not remove the Kubernetes Ingress API or imply that every NGINX-based product has the same lifecycle.

Inventory an existing installation, then plan migration to a maintained ingress implementation or Gateway API implementation. Compare path rewrites, TLS/certificate handling, authentication, rate limits, timeouts, source-IP behavior and observability before moving traffic. Copying old `nginx.ingress.kubernetes.io/*` annotations into a new controller does not transfer those policies.

Gateway API expresses the relationship as **GatewayClass → Gateway → HTTPRoute → Service**: the class chooses an implementation, the Gateway configures listeners, and an attached route owns HTTP matches/backends. Installing CRDs alone does not provide a data plane; follow the selected implementation's installation and conformance guidance.

## Real-World Use Cases

### Publish Several Applications Through One Edge

Host/path routing can share an edge across multiple Services. Whether it shares one load balancer, how isolation works, and what it costs depend on the controller configuration. Keep internal admin backends private by deliberate listener/routing/access policy rather than treating a hard-to-guess hostname as protection.

### Let a Stateful Client Discover Individual Members

A headless Service can expose member addresses while StatefulSets supply stable Pod identities. The application protocol still decides leader discovery, failover and replication. Headless DNS is not itself an application load balancer.

### Preserve Client IP Deliberately

`externalTrafficPolicy: Local` can avoid cross-node forwarding and preserve source addresses for eligible external traffic, but it can leave a node without local ready endpoints. Coordinate the external load balancer's health checks and topology. Do not select it solely as a latency shortcut.

## Diagnose the Missing Boundary

```bash
kubectl get service api
kubectl describe service api
kubectl get endpointslices -l kubernetes.io/service-name=api
kubectl get pods -l app=api -o wide
kubectl get ingressclass
kubectl describe ingress api
# For an existing legacy installation: inventory before migration.
kubectl get pods --all-namespaces --selector app.kubernetes.io/name=ingress-nginx
```

Work from backend to edge: confirm the application listens, the Service selector/targetPort match, ready endpoints exist, in-cluster access succeeds, and the controller accepts the route. Then inspect edge address, DNS, TLS and firewall policy. Use the installed controller's logs and status conditions rather than assuming its namespace or labels.

## Common Mistakes

| Symptom or assumption | Mechanism to check |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Service exists but no requests arrive | Selector, readiness, EndpointSlices, application port and network policy |
| Ingress exists but has no effect | Matching IngressClass and running controller; accepted rules and published address |
| TLS certificate configured, HTTP still allowed | Controller listener/redirect policy; certificate fields alone are not a universal redirect |
| All replicas have a separate rate limit | Whether the controller's policy shares counters and which identity it trusts |
| Healthy endpoints vanish during rollout | Readiness, termination/draining, rollout policy and application capacity |
| Reusing ingress-nginx annotations after migration | Translate each policy to the replacement implementation and test behavior |

## Best Practices

Start with a private Service and expose it only when a caller needs that boundary. Make route ownership, class selection, certificate management and network access explicit. Test readiness transitions and draining under traffic. Use maintained controller implementations, pin deployment artifacts, and rehearse the traffic cutover with a recoverable configuration.

## Summary

A Service stabilizes backend discovery; its implementation forwards connections. An Ingress declares HTTP routing; a controller supplies the working edge. Trace the request across those separate roles before debugging a type, annotation or load balancer. Keep the Ingress API's lifecycle separate from the retired ingress-nginx controller, and verify the replacement's behavior before migrating traffic.

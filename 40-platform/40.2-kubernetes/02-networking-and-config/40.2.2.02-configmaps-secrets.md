# Kubernetes ConfigMaps & Secrets

A Secret can be rotated in the API while a running process keeps the old value in memory. To know when the new credential actually takes effect, follow it from the object through kubelet delivery to the application's reload behavior.

## Definition

A **ConfigMap** stores non-sensitive configuration, such as log level or a configuration file. A **Secret** stores values intended to be confidential, such as credentials or private keys. Both are namespaced API objects that a Pod can reference as environment values or mounted files.

> **Textbook Definition:** ConfigMaps and Secrets are namespaced Kubernetes API objects that provide configuration to workloads through environment variables or files. Secret values are base64-encoded and, unless configured otherwise, stored unencrypted in etcd.

Secret `data` uses base64 representation, which anyone can decode. By default, Secret objects are stored unencrypted in etcd — configure and verify encryption at rest, protect its keys and backups, and verify that existing objects have been rewritten after enabling it. Encryption at rest does not stop an authorized API reader from retrieving a Secret.

## First Principles

The API stores a configuration value, the kubelet delivers it to a container, and the application reads it — three different owners with different lifetimes. A process environment is constructed at startup; a mounted file can change later; application memory changes only when the process rereads or reloads it. An API edit cannot skip the last step.

Confidential values need a separate access policy, because a caller allowed to inspect ordinary configuration should not automatically obtain credentials. A principal who can create a Pod that mounts a Secret may be able to expose its value even without direct permission to read the Secret object. Treat Pod creation, `get`, `list`, and `watch` permissions as part of the Secret access boundary. Namespaces scope names and policy; they do not isolate workloads from principals allowed to create Pods in that namespace.

## 1. Keep Configuration Outside the Image

Two environments can run the same application image but need different database addresses. Baking each address into a separate image couples release code to operational values. Kubernetes can supply the values separately, but the application still needs a deliberate way to consume and refresh them.

```text
ConfigMap/Secret in namespace
  -> Pod template references object/key in that namespace
  -> kubelet obtains required data
      -> environment constructed at container startup
      -> or volume files materialized and eventually refreshed
  -> application reads value
      -> startup-only consumer retains old in-memory value
      -> reload-aware consumer can validate and adopt new file contents
```

A missing non-optional object or key can prevent the container from starting. A file update does not trigger a Deployment template revision. During a mutable ConfigMap change, new Pods can start with new environment values while old Pods retain old ones — a mixed-configuration population even though every Pod uses the same object name.

## 2. Choose the Consumption Method by Its Refresh Contract

| Consumption method | When the delivered value changes | What the application must do |
| -------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------ |
| Explicit `env` key reference | When the container starts | Restart/replace to refresh the process environment |
| `envFrom` object reference | When the container starts | Know every imported key and resolve naming/precedence deliberately |
| Normal ConfigMap/Secret volume | Eventually after mutable object updates | Reread/reload files; retained open descriptors or parsed caches may stay stale |
| `subPath` file mount | Does not receive object updates | Replace the Pod or use a different mounting design |
| Direct Kubernetes API read/watch | According to application request/watch logic | Own credentials, retries, version handling, and reload behavior |

Projected volumes can combine sources into one mounted directory, but they do not eliminate propagation delay or implement application reload. Treat a credential's source update, delivery update, and successful new authenticated connection as separate milestones.

## 3. Configure One Application with Versioned References

Create `production` first and use an image that reads the declared inputs. This ConfigMap uses text keys; structured JSON remains one file-valued string rather than becoming individual environment variables.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v1
  namespace: production
immutable: true
data:
  DATABASE_HOST: "postgres.production.svc.cluster.local"
  LOG_LEVEL: "info"
  config.json: |
    {"features": {"darkMode": true}}
```

`immutable: true` rejects changes to the object's data. To release changed values, create `app-config-v2` and change the Pod template's reference; that template change initiates a Deployment rollout. Keep older configuration names available for rollback until no retained revision needs them. Immutability does not prevent deletion or make an old template compatible with a new database schema.

For a Secret, use your approved secret provisioning procedure. This demonstration reads a protected local file without putting its value into command arguments. The file must contain the intended bytes; a trailing newline is also data.

```bash
kubectl create secret generic app-secrets -n production \
  --from-file=DATABASE_PASSWORD=./database-password.txt
```

Do not commit the source file or emitted Secret manifests. A declarative Secret can use `data` with base64 values or `stringData` with unencoded values; both expose the original secret to anyone reading the source. `stringData` is a write convenience and has server-side-apply limitations, not an encryption feature.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels: {app: myapp}
  template:
    metadata:
      labels: {app: myapp}
    spec:
      containers:
        - name: myapp
          image: myapp:1.0.0
          env:
            - name: DATABASE_HOST
              valueFrom:
                configMapKeyRef: {name: app-config-v1, key: DATABASE_HOST}
            - name: DATABASE_PASSWORD
              valueFrom:
                secretKeyRef: {name: app-secrets, key: DATABASE_PASSWORD}
          volumeMounts:
            - name: config
              mountPath: /etc/app-config
              readOnly: true
      volumes:
        - name: config
          configMap:
            name: app-config-v1
            items:
              - {key: config.json, path: config.json}
```

For each container start, the kubelet resolves `DATABASE_HOST` and `DATABASE_PASSWORD` from same-namespace objects and mounts `/etc/app-config/config.json` from the selected key. The application must parse that path and use the environment values; Kubernetes does not infer database-client settings from their names. This immutable example changes only through a new reference/rollout. For mutable objects, ordinary volume updates can arrive without changing already injected environment variables.

## 4. Import and Mount with Least Privilege

An alternative container fragment imports every eligible key from an object:

```yaml
envFrom:
  - configMapRef: {name: app-env}
```

Create `app-env` with only the intended environment keys. Unlike an explicit key reference, this broadens the inputs whenever someone adds a key — do not indiscriminately import a file-oriented ConfigMap or every credential from a large Secret. Explicit `env` values take precedence over matching `envFrom` values; with multiple `envFrom` sources, later matching entries win. Check variable-name support and events for your Kubernetes version rather than silently assuming every file key is a suitable process setting.

Mount confidential files with usable permissions. This fragment belongs under Pod `spec`; add a read-only container mount for `credentials`:

```yaml
volumes:
  - name: credentials
    secret:
      secretName: app-secrets
      defaultMode: 0400
```

The mode is octal in YAML; JSON needs its decimal equivalent. A non-root process still needs permission to read the resulting owner/group. Pod security settings such as `fsGroup` can affect ownership and mode bits. Verify access as the application's actual user; a restrictive number that prevents startup is not a working confidentiality policy. Prefer mounting only needed keys, and keep values out of logs, debug endpoints, and crash artifacts.

## 5. Match Secret Types to Their Consumers

An **Opaque** Secret stores application-defined keys. A `kubernetes.io/tls` Secret expects `tls.crt` and `tls.key`; create it from a suitable certificate/key and reference it from the intended same-namespace route:

```bash
kubectl create secret tls api-tls -n production \
  --cert=./api.crt --key=./api.key
```

This does not issue or renew a certificate, publish a listener, or configure an HTTP redirect. The edge controller must consume it; renewal must propagate and be observed at the actual endpoint.

An image-pull credential is a different contract, commonly `kubernetes.io/dockerconfigjson`. Provision it through the approved registry credential procedure and reference it with `imagePullSecrets` in the Pod spec (or a deliberately configured ServiceAccount). The kubelet uses it to pull the image; placing registry credentials in application environment variables does not satisfy that role. Avoid long-lived broad registry credentials and verify that rotation reaches future pulls.

External secret stores can mount values directly or synchronize Kubernetes Secret objects, depending on the integration. If copied into a Secret, normal Kubernetes access/storage controls still apply. Source rotation alone does not prove a running connection pool or TLS listener adopted the new value.

## 6. Observe Delivery and Reload Separately

```bash
kubectl get configmap app-config-v1 -n production -o yaml
kubectl get deployment myapp -n production -o yaml
kubectl describe pod <pod-name> -n production
kubectl rollout status deployment/myapp -n production
```

Inspect referenced names, missing-key events, rollout state, and application-reported configuration version. Avoid decoding a Secret merely to show it in a shared terminal. For a mutable file-based test, edit a non-sensitive ConfigMap in a test namespace, observe when the mounted file changes, then separately verify the application's effective setting. Repeat with an environment reference and a `subPath` mount to demonstrate their different contracts.

ConfigMaps and individual Secrets have size limits around 1 MiB; they are unsuitable for large artifacts. Many watched mutable objects also add API/kubelet work. Choose immutable versioned objects when coordinated release/rollback matters, and mutable mounted configuration only when the application's reload contract is designed and tested. Neither choice makes several object updates a transaction over all replicas.

## Summary

ConfigMaps and Secrets separate operational values from application images. Kubelet delivery, file/environment lifetime, and application reload determine when a value actually takes effect. Base64 does not protect credentials; access, storage, mount, and rotation policies do. Versioned immutable references support deliberate rollout, while mutable mounted data needs a tested refresh contract and does not update process environments or subPath mounts automatically.

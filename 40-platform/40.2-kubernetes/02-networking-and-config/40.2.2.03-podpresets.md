# PodPresets

An older manifest may still define a PodPreset even though a current cluster rejects that resource. The API was removed, but the shared-configuration problem remains: decide whether each workload or the platform owns the injected values.

## Definition

**PodPreset is a removed Kubernetes API**, retained here to explain older manifests and the problem of shared Pod configuration. Kubernetes 1.20 removed both its `settings.k8s.io/v1alpha1` resource and admission plugin. Enabling an API-server flag does not restore it in current clusters.

> **Textbook Definition:** PodPreset was an alpha Kubernetes API for injecting selected environment variables and volume configuration into matching Pods; it was removed and must be replaced with supported configuration or admission mechanisms.

The former API added environment variables, volumes, and mounts to selected Pods. It did **not** provide general sidecar injection or arbitrary Pod mutation. Current choices are explicit workload templates, Helm/Kustomize transformations, or admission-time mutation.

## First Principles

A controller creates Pods from a template, so reusable defaults can be applied to that template before submission — the rendered manifest then shows what the application asks to run. A cluster may also need rules for workloads it does not own, so admission can inspect or modify incoming objects before they are persisted; that moves configuration ownership into cluster infrastructure and adds another dependency to Pod creation. Mutation and validation answer different questions: adding a default changes an object, while rejecting an unsafe configuration enforces a condition. A mutator alone never ensures every admitted Pod satisfies the intended policy.

Suppose several services need an outbound proxy and a shared CA bundle. Copying environment variables and mounts into every Deployment invites drift. First decide who owns those defaults: the application release, the deployment platform, or a cluster policy. That ownership determines the mechanism.

## How It Works

### 1. Assign Each Default an Owner

| Owner and requirement | Mechanism | What to inspect |
| ------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------- |
| Application-specific configuration | Deployment Pod template with ConfigMap/Secret references | Source manifest and rendered values |
| Shared release defaults | Helm values or Kustomize patches | Rendered manifests before deployment |
| Cluster-wide injection, including third-party workloads | Mutating admission webhook or policy engine | Admission configuration and the admitted Pod |
| Mandatory security constraints | Validation, including Pod Security Admission where applicable | Rejection policy and audit events |

Build-time transformations and admission mutation can both affect the same field. Define precedence and ownership instead of assuming that the last writer produces a sensible result.

### 2. Keep Application Configuration in the Workload Template

This fragment belongs under `spec.template.spec` in a Deployment. The referenced ConfigMap and Secret must exist in the same namespace. Environment variables are read when the container starts; changing a ConfigMap does not refresh already running process environments.

```yaml
containers:
  - name: api
    image: example/api:1.0.0
    envFrom:
      - configMapRef:
          name: api-network-config
    volumeMounts:
      - name: trusted-ca
        mountPath: /etc/company-ca
        readOnly: true
volumes:
  - name: trusted-ca
    secret:
      secretName: company-ca
```

For the full workload, follow [Deployments](../01-core-workloads/40.2.1.02-deployments.md). For variants across environments, use the [Kustomize chapter](../05-packaging-and-extensibility/40.2.5.02-kustomize-overlays-packaging-tradeoffs.md).

### 3. Diagnose Admission Mutation Against the Admitted Pod

```bash
# Compare source configuration with the actual admitted Pod.
kubectl get deployment api -o yaml
kubectl get pods -l app=api -o yaml
kubectl get mutatingwebhookconfigurations
kubectl describe pod <pod-name>
```

A server-side dry run can show supported admission mutations without persisting the object. Webhooks must declare compatible side effects for dry-run requests. It still requires access to the API server and is not a replacement for testing a real rollout.

### 4. Migrate Old Repositories Deliberately

Service meshes often inject a proxy through admission. An application-owned ConfigMap is usually simpler for a single service's proxy settings — use admission when centralized ownership is intentional and the platform can operate the webhook reliably.

When migrating an old repository, search for `kind: PodPreset` and obsolete API-server plugin flags. Translate each injected field into an owned template or policy, render the result, and compare a newly admitted Pod. Do not assume a modern policy engine reproduces historical merge/conflict behavior.

## Common Mistakes

- **Treating PodPreset as a current alpha option.** Remove the obsolete resource and use a supported mechanism.
- **Using mutation as proof of compliance.** Validate required invariants separately.
- **Overlapping mutators.** Scope selectors carefully and test repeated admission so patches are idempotent.
- **Ignoring webhook outages.** Choose failure policy, timeout, availability, and rollout order deliberately. A fail-closed unavailable webhook can block matching Pod creation.
- **Assuming injected Secrets make them public defaults.** Restrict Secret access and mount only what the workload needs.

## Best Practices

Prefer explicit rendered configuration where possible. If admission owns a setting, document that ownership in the application's runbook, constrain which Pods it matches, and observe rejection/latency rates. Test both injection and failure behavior before applying a policy to an entire namespace.

## Summary

PodPreset was removed in Kubernetes 1.20. The lasting design choice is where shared Pod configuration belongs: in application manifests, deployment-time transformations, or cluster admission. Make that owner explicit, inspect the resulting Pod, and validate requirements independently of mutation.

# Kubernetes HPA & Scaling

A web service has three replicas. Each is busy, requests are queueing, and a fixed replica count no longer matches demand. Adding a Pod can distribute that work, but only if a node can run it and the application becomes ready. Autoscaling coordinates those separate decisions.

## Definition

The **Horizontal Pod Autoscaler (HPA)** changes how many Pod replicas an application requests, based on metrics such as CPU, memory, or a custom load measurement. The **Vertical Pod Autoscaler (VPA)** recommends or adjusts resource requests for individual Pods. Horizontal scaling changes the number of Pods; vertical scaling changes the resources assigned to each Pod.

> **Textbook Definition:** Horizontal Pod Autoscaling is a feedback controller that adjusts workload replica count from observed metrics and target values, constrained by configured replica bounds, stabilization windows, and scaling policies.

A **node** is a machine that runs Pods. A node autoscaler adds or removes those machines. HPA can ask for five replicas while only three can schedule: desired application capacity and available cluster capacity are different states.

## First Principles

Traffic arrives at a rate, each request consumes resources, and each running replica has finite capacity. When incoming work exceeds what the ready replicas can serve, queues and latency grow. A controller needs an observable signal related to that bottleneck before it can choose a useful response.

Measurements arrive after the work occurs. Starting a replacement also takes time. Acting on every small fluctuation can repeatedly add and remove replicas before earlier changes become useful. Tolerance, stabilization, and rate limits make this delayed feedback loop less erratic; warm headroom covers demand that arrives faster than it can react.

## Why It Matters

Autoscaling can replace routine replica adjustments and recover idle capacity. It cannot create unlimited throughput. A saturated database, serialized critical section, or exhausted provider quota may remain the bottleneck after adding application Pods. Choose a metric whose value can improve when the selected workload gains useful replicas.

## From measured CPU to ready replicas

```text
container resource use -> kubelet -> Metrics Server -> resource metrics API
                                                           |
                                                           v
                                                  HPA controller
                                               chooses desired replicas
                                                           |
                                                           v
                                                Deployment scale field
                                                           |
                                             Deployment -> ReplicaSet
                                                           |
                                                    creates Pods
                                                           |
                                      scheduler chooses a feasible node
                                              /                     \
                                        capacity exists         no capacity
                                              |                     |
                                    kubelet starts container   Pod remains Pending
                                              |                     |
                                    readiness allows serving   node autoscaler may
                                                               provision capacity
```

The first arrows carry measurements. Metrics Server obtains resource measurements from kubelets and exposes them through Kubernetes' resource metrics API. The HPA controller reads that API and writes the target workload's **scale subresource**, the interface for reading and changing its requested replica count. It does not directly launch containers.

The next arrows are reconciliation: the Deployment and its ReplicaSet request the needed Pods, the scheduler assigns them to feasible nodes, and each selected node's kubelet starts containers. A Pod may be scheduled but still pulling its image or warming up. Readiness determines normal Service endpoint eligibility, so “five desired” does not yet mean “five serving.”

Custom and external metrics use their own metric APIs and adapters. Declaring a metric name in YAML does not install that adapter or make an application export it. [Node Autoscaling](40.2.3.02-node-autoscaling-cluster-capacity.md) owns provisioning and drain mechanics.

### The CPU percentage uses requests as its denominator

A resource **request** tells the scheduler how much capacity to account for when placing a container. A **limit** configures resource enforcement: CPU is throttled, while memory pressure can trigger an out-of-memory kill. It is not a promise that every memory overage is stopped immediately. For CPU, `500m` means half a CPU core; `1000m` means one core. A request is not the CPU's physical utilization ceiling.

Assume each of three Pods contains one application container, each requesting `500m`, and each averages `400m` CPU use. Its CPU utilization for HPA is:

```text
observed CPU / requested CPU = 400m / 500m = 80%
```

A `50%` target therefore asks each replica to average about `250m` under this request configuration. The basic recommendation is:

```text
desiredReplicas = ceil(currentReplicas × currentMetricValue / desiredMetricValue)
                = ceil(3 × 80 / 50)
                = 5
```

If total work remains roughly constant and distributes evenly, five replicas share the previous `1200m`, about `240m` each, or `48%` of the request. This explains the direction of the formula: work above the target increases replicas. The calculation is a prediction, not a cluster benchmark or a guarantee that a database-bound service will improve.

If the request doubles to `1000m` while use remains `400m`, measured utilization becomes `40%`. The denominator changed even though the physical workload did not. Resource utilization requires suitable requests on the relevant containers; missing requests can make that utilization unavailable. A `ContainerResource` metric can select one container when sidecar use should not drive application scaling.

### Why the applied count can differ from the ratio

The ratio above is the starting calculation with usable samples. The controller also accounts for conditions that make a naive reaction unsafe:

- **Tolerance:** a small deviation near the target can leave replicas unchanged. With a configured tolerance of 10%, a ratio of `1.05` does not justify a scale action.
- **Missing samples:** the controller uses conservative assumptions when recalculating. For scale-down, it can treat missing Pods as using the target amount; for scale-up, as using zero. This reduces the proposed change. Not-yet-ready Pods also dampen CPU scale-up under the controller's initialization rules.
- **Multiple metrics:** each usable metric proposes a count and the largest is selected. If one metric cannot be read and another suggests scale-down, the controller skips that downscale; a valid scale-up recommendation can still proceed.
- **Bounds:** `minReplicas` and `maxReplicas` limit the final request. A maximum of ten can leave demand unsatisfied when the ratio asks for seventeen.
- **Stabilization and policies:** recent recommendations and allowed changes per period constrain how quickly capacity changes. They smooth an unstable signal; they do not replace enough capacity or accurate metrics.

Inspect `kubectl describe hpa` for conditions, events, current metrics, and desired count. Separately inspect Pod events for quota rejection, scheduling failure, image pull, or readiness problems. The HPA synchronization interval and the metric sampling interval are different clocks; neither proves an immediate response to a new request.

## Configure one controller, then follow its result

These examples assume an existing Deployment named `myapp`, a working resource metrics API, and an image containing a correctly configured application. Use your own image and health endpoints. The container's resources belong in the Deployment template:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

The CPU request supplies the denominator in the worked trace; the CPU limit is a separate cap. The memory values govern scheduling and container resource behavior, not the CPU utilization calculation.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Pods
          value: 4
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
```

`scaleTargetRef` names the workload whose count changes. This policy permits up to four added Pods in a 60-second period; scale-down considers a five-minute recommendation window and permits a limited percentage reduction per period. A recommendation of five from three can fit that scale-up allowance, but missing metrics and other controller rules may still alter it.

Let HPA own the Deployment's replica count. Reapplying a manifest with a fixed `spec.replicas` can reset that count, and manual scaling can be overwritten by the next controller decision. To pause HPA control deliberately, remove or change the controller under an explicit operational procedure.

### Scale by work when CPU is the wrong signal

For an application limited by request processing rather than CPU, a per-Pod request-rate metric can target useful throughput. This is an alternative `metrics` entry, not an additional HPA controlling the same Deployment:

```yaml
metrics:
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "1000"
```

An application/exporter and custom metrics adapter must expose that name per Pod. If four Pods average `1500` requests per second, the basic recommendation is `ceil(4 × 1500 / 1000) = 6`. Validate that adding replicas actually shares incoming work and that the selected request count captures expensive operations adequately.

For workers consuming a shared queue, an external metric can represent total backlog:

```yaml
metrics:
  - type: External
    external:
      metric:
        name: sqs_queue_length
        selector:
          matchLabels:
            queue: "my-queue"
      target:
        type: AverageValue
        averageValue: "10"
```

The adapter must translate the selector into the intended queue. A backlog of 100 and a target of ten queued messages per replica gives a basic recommendation of ten replicas before bounds and policies. Queue depth alone ignores processing cost and age: ten long jobs may need more attention than a hundred cheap jobs. Check oldest-message age and downstream concurrency before increasing workers.

### Scale queue workers to zero (Kubernetes v1.37 beta)

As of Kubernetes v1.37, an HPA can scale to zero when it uses at least one object or external metric. This feature is beta and enabled by default in v1.37. The feature gate must be enabled on both the API server and controller manager; during a control-plane upgrade, verify both components support it before applying `minReplicas: 0`. CPU and memory resource metrics cannot wake a workload from zero because no Pods remain to produce those measurements.

For a durable queue, a metric that exists independently of the workers can keep detecting new work:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: queue-worker
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: queue-worker
  minReplicas: 0
  maxReplicas: 10
  metrics:
    - type: External
      external:
        metric:
          name: sqs_queue_length
          selector:
            matchLabels:
              queue: "my-queue"
        target:
          type: AverageValue
          averageValue: "10"
```

This example still requires a functioning external-metrics adapter and a metric query that returns the intended queue. At zero, the HPA records `ScaledToZero=True`; that condition distinguishes an autoscaled worker from a workload deliberately paused by setting its replicas to zero. Inspect the HPA condition and metric before treating zero replicas as a failed scale-up. Cold starts add metric, scheduling, image, and application-startup delay. A Kubernetes Service does not buffer HTTP requests while no Pods are ready, so use this pattern for work that can wait in durable storage or put an explicit buffering layer in front of request-driven work.

Memory utilization is another resource metric, calculated relative to memory requests. Adding replicas helps only if the relevant memory load can be redistributed. It does not repair a leak or guarantee that warmed caches shrink after scale-out.

## HPA, VPA, and nodes make different changes

HPA changes **how many** application replicas exist. VPA changes or recommends **how much resource each replica requests**. Node autoscaling changes **where those requested resources can fit**. For example, raising a request from `500m` to `1000m` can reduce CPU utilization seen by HPA and simultaneously make the same Pod harder to schedule.

Start VPA in recommendation mode when learning a workload's shape:

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: myapp-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  updatePolicy:
    updateMode: "Off"
```

VPA is an installed add-on, not implied by this YAML or by an HPA installation. In `Off` mode it produces recommendations without changing Pods; inspect `.status.recommendation`. Update modes and in-place/eviction behavior depend on installed VPA and cluster capabilities. If both controllers adjust or measure the same resource, one controller changes the other's denominator. Coordinate their policies or use a separate work-based HPA metric, rather than treating two automatic loops as independent optimizations.

If HPA adds replicas and Pods remain unschedulable, node provisioning may help. It cannot fix a namespace quota that prevents Pod creation or a selector that excludes every permitted node. Do not install an old, isolated Cluster Autoscaler Deployment recipe: its version, provider permissions, discovery, and node groups must match the actual cluster. Follow the node-capacity chapter and provider installation guidance.

## Observe a scaling exercise

```bash
kubectl apply -f hpa.yaml
kubectl get hpa myapp-hpa -w
kubectl describe hpa myapp-hpa
kubectl top pods -l app=myapp
kubectl get pods -l app=myapp -o wide
kubectl describe deployment myapp
```

Generate controlled load against a Service that routes to the selected Pods, using an application-specific test plan. Compare the measured metric, requested count, scheduled count, and ready count over time. Expect delay between those states. Record latency, errors, dependency connections, and scale-in termination behavior alongside replica count. `kubectl top` displays current resource observations; it does not by itself show why every controller adjustment occurred.

A PodDisruptionBudget limits cooperating eviction paths, such as a node drain. HPA downscale and Deployment replacement follow their own controllers and can remove Pods without PDB eviction admission. Preserve graceful shutdown, spare capacity, and workload-specific availability checks; a PDB does not make application scale-in safe by itself.

## Decisions and common mistakes

| Observation | Reason to investigate | Useful decision |
| -------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------- |
| HPA shows unknown utilization | Relevant requests or resource metrics may be missing | Repair the denominator/API before tuning thresholds |
| CPU is low while queue age rises | Waiting or an external dependency may dominate | Choose a work signal and bound dependency concurrency |
| Desired replicas rise but useful capacity does not | Quota, scheduling, startup, or readiness may block progress | Trace the next controller state instead of raising maxReplicas blindly |
| Replicas oscillate | Delayed noisy feedback can react to previous changes | Tune stabilization and change rate from observed response time |
| VPA changes requests while HPA reacts | Utilization's denominator moved | Coordinate resource ownership or use a separate demand metric |
| Downscale interrupts work despite a PDB | Replica reduction did not use eviction admission | Test termination and workload availability separately |

Choose lower and upper counts from the minimum useful service population and the affordable, schedulable, downstream-safe maximum. Keep warm capacity for bursts that cannot wait for measurement and startup. Retest when request cost, image startup, or dependencies change: a previous scaling test does not establish the new workload's response.

## Summary

HPA converts observed workload metrics into a requested replica count. CPU utilization divides use by requests; limits serve a different purpose. Deployment reconciliation, scheduling, node capacity, and readiness determine whether that request becomes serving capacity. Missing metrics, tolerance, bounds, and scaling behavior constrain the basic ratio. VPA and node autoscaling own different resource decisions and need coordinated policies; verify the full request-to-ready trace and its failure boundaries.

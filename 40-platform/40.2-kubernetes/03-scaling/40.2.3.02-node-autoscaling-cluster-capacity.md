# Node Autoscaling & Cluster Capacity (Cluster Autoscaler, Karpenter)

A Deployment can have the right number of replicas and still have too few running Pods. If the scheduler cannot place a Pod on any permitted node, the missing resource is cluster capacity. A node autoscaler can add a suitable machine, but the Pod must still pass scheduling, startup, and readiness before it becomes useful.

## Definition

**Node autoscaling** changes the number or type of worker nodes in response to workload demand. The **Cluster Autoscaler (CA)** changes the size of configured node groups. **Karpenter** chooses individual capacity that satisfies a workload and a `NodePool`; in the AWS provider, an `EC2NodeClass` supplies the launch configuration.

> **Textbook Definition:** Node autoscaling reconciles available cluster compute capacity with unschedulable workload demand and safe scale-in conditions, subject to placement constraints, provider limits and disruption policy.

## First Principles

The scheduler places admitted Pods using their effective resource requests and placement requirements — not a cluster-wide sum of idle CPU. If two allowed nodes each have `1` CPU available, a Pod requesting `1500m` cannot fit either one. A third, larger node may solve that shape mismatch; a node in the wrong zone or without the required device will not.

The full path is asynchronous:

```text
HPA changes desired replicas
  -> workload controller creates Pod objects
  -> scheduler cannot find a feasible node; Pod remains Pending
  -> autoscaler simulates candidate capacity and requests provider launch
  -> machine joins and registers as a usable Kubernetes node
  -> scheduler assigns the waiting Pod
  -> kubelet starts it; readiness makes it eligible to serve
```

These are separate control loops, not one transaction or a fixed latency guarantee. A Pod may be Pending because of quota, an unbound volume, an image issue, or impossible affinity rather than lack of nodes. Inspect its events before changing autoscaler settings. Quota rejection can happen before a Pending Pod exists.

## How It Works

### 1. Choose the Capacity Owner

CA compares configured node-group templates with unschedulable Pods. If a group could fit the work and remains within its bounds, it asks the provider to increase that group's size. The provider and bootstrap process determine how quickly a node becomes usable.

Karpenter evaluates Pod requirements against its `NodePool` constraints and provider offerings, then requests individual machines. Its `NodeClass` supplies provider-specific launch details such as image, networking, and identity. A `NodeClaim` records a requested node lifecycle; it is not proof that the node joined or the application became ready.

| Question | Cluster Autoscaler | Karpenter |
| ------------------------------ | --------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| What can it add? | Nodes from configured groups | Individual offerings within a NodePool and provider configuration |
| What must operations maintain? | Group templates, discovery, minimums and maximums | NodePool constraints, NodeClass, permissions and offerings |
| How does it remove capacity? | Removes nodes considered unneeded after placement and eviction checks | Disrupts empty or underused nodes when replacement or relocation is feasible |
| Main boundary | Group shape can leave a workload without a fitting option | Provider limits, launch failures and constraints can still prevent a usable node |

Do not let both controllers manage the same node group. Provider quotas, exhausted offerings, bootstrap errors, and scale-up backoff can prevent requested capacity from becoming schedulable.

### 2. Make the Intended Pool Schedulable

A **label** describes a node; a Pod's **node selector** or affinity requires a matching label. A **taint** repels Pods unless they tolerate it. A toleration allows placement but does not select or reserve a node. For GPU work, the Pod must also request the device resource exposed by the installed device plugin.

This fragment belongs under the workload's `spec.template.spec`; it selects and permits placement on a dedicated pool, but does not itself request a GPU:

```yaml
nodeSelector:
  pool: gpu-training
tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule
containers:
  - name: trainer
    image: registry.example.com/trainer:1.2.3
    resources:
      requests:
        nvidia.com/gpu: 1
```

The provider's node image, accelerator driver, and device plugin must agree. Spread, affinity, volume topology, and taints are all part of the autoscaler's feasibility calculation. A new node that fails any one of them does not unblock the Pod.

### 3. Pay for Warm Capacity Only Where Delay Matters

Cloud launch, node initialization, image pull, and application startup all contribute to time-to-ready. Measure that path under real load; a controller's reconciliation interval is not a service-level deadline. If a burst cannot wait, a low-priority placeholder workload can reserve requests on existing nodes. Higher-priority Pods may preempt it and use the released space while autoscaling replenishes the buffer.

A buffer trades continuous cost for lower scheduling delay. It does not skip image startup, readiness, or dependency limits. CA can ignore placeholder Pods below its configured expendable-priority threshold, so verify that evicted placeholders still trigger the intended refill behavior. Size the buffer from measured burst demand and revisit it when startup time changes.

Scale-from-zero also needs a way to infer the shape of a nonexistent node group. CA requires provider-specific node-template/discovery configuration for a zero-sized group. Karpenter can evaluate a NodePool without existing nodes, but the provider still needs a matching offering and launch configuration. GPU cold starts, image size, zone-bound volumes, and spot availability can make zero-to-ready latency unsuitable for interactive traffic. Stateful workloads require special care: local persistent data cannot be recreated by launching a different node.

### 4. Reclaim Nodes Without Losing Work

Scale-in first needs a feasible destination for movable Pods, then a safe way to evict them. CA checks whether Pods can move and whether eviction is allowed. Karpenter considers whether it can remove or replace capacity while satisfying scheduling constraints. Both can be blocked by a full PodDisruptionBudget, local storage, zone affinity, restrictive selectors, or a workload that cannot tolerate interruption.

A voluntary disruption policy does not prevent every failure. Spot interruption, node loss, provider repair, forced termination, and manual deletion may bypass the normal eviction path or impose a deadline. Make applications checkpoint, retry, or drain work as appropriate; do not treat a disruption annotation or PDB as a physical availability guarantee.

For Karpenter, `WhenEmptyOrUnderutilized` can consolidate a node when workloads can be placed elsewhere or on a cheaper feasible node. Consolidation trades cost against churn. A `karpenter.sh/do-not-disrupt` annotation blocks some voluntary disruption such as consolidation, but not forceful interruption, expiration, node repair, or manual deletion. The CA node annotation `cluster-autoscaler.kubernetes.io/scale-down-disabled=true` excludes that node from CA scale-down. Remove protections after the controlled operation; they are operational switches, not permanent safety mechanisms.

### 5. Inspect the Next Blocked Step

```bash
kubectl get pods -A --field-selector status.phase=Pending -o wide
kubectl describe pod <pending-pod>
kubectl get nodes -o wide
kubectl describe node <node>
kubectl get nodeclaims,nodepools
kubectl get events -A --sort-by=.lastTimestamp
```

Use the installed autoscaler's status and logs as well; its resource names and namespace depend on the provider installation. `FailedScheduling: Insufficient cpu` points toward request shape or capacity. A node-affinity mismatch points toward placement policy. A Pod with an unbound volume may need storage or zone resolution, not another general-purpose machine. After launch, verify node readiness, Pod scheduling, container startup, and application readiness separately.

An AWS-provider `NodePool` has this general shape. It assumes the Karpenter CRDs and controller, provider permissions, and a ready `EC2NodeClass` named `general-purpose`. Workloads must select `pool=general` and tolerate its taint.

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-purpose
spec:
  template:
    metadata:
      labels:
        pool: general
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: general-purpose
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: [on-demand, spot]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: [m, c]
        - key: kubernetes.io/arch
          operator: In
          values: [amd64]
      taints:
        - key: pool
          value: general
          effect: NoSchedule
  limits:
    cpu: "200"
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
```

The NodePool limits the choices Karpenter can consider; the EC2NodeClass provides the cloud launch details. Aggregate limits guide provisioning and should not be treated as a precise billing cap under concurrent reconciliation. Validate rendered manifests and the actual launched node before relying on a policy.

## Summary

Node autoscaling supplies machines when workload Pods cannot be placed, then reclaims them when work can move safely. Diagnose the scheduler's actual constraint first. CA works from configured node groups; Karpenter selects from provider-backed NodePools. Requests, placement, startup delay, disruption policy, and application recovery determine whether added or removed capacity is useful.

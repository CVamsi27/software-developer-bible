# Node Autoscaling & Cluster Capacity (Cluster Autoscaler, Karpenter)

## TL;DR

Pod autoscaling is useless without node capacity behind it. **Cluster Autoscaler** reacts to unschedulable pods by adding nodes from pre-defined node groups, and removes underutilized ones — slowly and conservatively. **Karpenter** watches pending pods directly and provisions exactly-fitting EC2 instances in seconds, then consolidates. Seniors are expected to know scale-down safety rules, taint-based pool strategy, overprovisioning buffers, and why GPU/stateful scale-from-zero is hard.

**Why it matters:** "HPA wants 10 replicas but pods stay Pending" is a classic production incident. Interviews probe the full capacity stack: requests → scheduler → node provisioning → cost.

## Definition

**Node autoscaling** adjusts the number of worker nodes to match aggregate pod demand:

- **Cluster Autoscaler (CA)** — Reacts to *scheduling failures*: pods stuck `Pending` with reason `TriggeredScaleUp` cause CA to add a node from a configured node group; long-underutilized nodes are drained and removed.
- **Karpenter** — Watches *pending pods* directly through the scheduler queue and provisions instances from the full EC2 fleet (no pre-baked ASGs), choosing type/size that bin-packs best; later consolidates by rescheduling pods onto fewer nodes.
- **Node pools/groups** — Labeled+tainted node sets dedicated to workload classes (general, memory-heavy, GPU, spot) so autoscaling decisions stay predictable.
- **Overprovisioning buffer** — Headroom pause-pods that get evicted instantly when real pods arrive, hiding node-provisioning latency behind already-warm capacity.

```text
CAPACITY DECISION FLOW

HPA scales replicas ──▶ pods created
                              │
                 scheduler: feasible node?
                    │yes                │no
                    ▼                   ▼
               pods Running      Pending (Insufficient cpu/memory)
                                        │
              ┌─────────────────────────┴──────────────┐
              ▼                                        ▼
     Cluster Autoscaler                        Karpenter
     "which NODE GROUP fits?"                  "which INSTANCE fits?"
     group templates, fixed sizes              whole EC2 fleet, exact fit
     ~minutes to Ready                         ~seconds-minutes to Ready
```

## Why Do We Need It?

| Problem                                       | Solution                                                           |
| --------------------------------------------- | ------------------------------------------------------------------ |
| HPA adds replicas but nothing schedules       | Node autoscaler creates capacity for Pending pods                  |
| Paying for idle nodes at 3am                  | Scale-down (CA) or consolidation (Karpenter)                       |
| Black-Friday spikes need +40 nodes in minutes | Karpenter direct provisioning; warm/pinned buffers otherwise       |
| Mixed fleets: CPU jobs vs GPU training        | Node pools with taints keep accelerators reserved                  |
| Spot interruptions                            | Diversified instance selection (Karpenter) / multi-ASG groups (CA) |
| Node churn hurting latency-sensitive apps     | Overprovisioning buffer; scale-down stabilization windows          |

## How It Works

### Cluster Autoscaler Behavior

Scale-up triggers and rules:

1. Every loop (~10s), CA inspects pods marked unschedulable by the scheduler (`PodFitsResources` style failures).
2. It simulates whether any node-group template would make them schedulable; if yes, it bumps that group's desired size (respecting max).
3. `expander` strategies pick among viable groups: `random`, `most-pods`, `least-waste`, `price`, `gpu`, or `priority` (custom expander).

Scale-down safety rules — ALL must hold before a node drains:

```text
Node removable iff:
• utilization < scale-down-utilization-threshold (default 0.5)
  = sum(requests of pods) / allocatable on the node
• ALL pods on it can move elsewhere:
    - no DaemonSet-only-node situation
    - no restrictive PDB blocking eviction
    - no pods with emptyDir-local data unless allowed
• No annotation: cluster-autoscaler.kubernetes.io/scale-down-disabled: "true"
• Not within --scale-down-unneeded-time (default 10 min) since last add/activity
• Not a newly added node inside --scale-down-delay-after-add (default 10 min)
```

Limits seniors should quote:

- One update per node group per `--max-node-provision-time` cycle pacing; CA is deliberately slow.
- CA does NOT look inside your cloud console; it manages groups it was told about via `--nodes`/auto-discovery tags.
- Cluster-wide: it will not remove the last node of a group if pods would become unschedulable anywhere.

### Karpenter Model

```text
                     ┌───────────────────────────┐
 kube events ───────▶│ Karpenter controller       │
 pending pods        │  ├─ scheduling simulation  │
                     │  ├─ NodePool specs         │
                     │  └─ disruption/consolidation│
                     └──────────┬────────────────┘
                                │ chooses instance type/size/AZ/spot
                                ▼
                  raw EC2/Fleet API (NO ASG in the path)
                                │
                                ▼
                  NodeClaim → Node joins → kubelet registers

NodePool (declarative): constraints + limits + disruption budgets
  • labels/taints applied to provisioned nodes
  • instance categories/families/sizes/architectures allowlist
  • consolidation policy: WhenEmpty vs WhenUnderutilized
  • do-not-disrupt annotations protect sensitive pods
```

Key differences worth memorizing:

| Aspect            | Cluster Autoscaler                    | Karpenter                                     |
| ----------------- | ------------------------------------- | --------------------------------------------- |
| Input signal      | Unschedulable pods (scheduler output) | Pending pods (scheduling simulation itself)   |
| Provisioning unit | Pre-defined node groups/ASGs/MIGs     | Individual instances via cloud Fleet API      |
| Instance choice   | Whatever the group template says      | Best-fit per batch of pods; flexible families |
| Bin-packing       | Indirect (group granularity)          | Native (per-provisioning + consolidation)     |
| Speed             | Minutes (ASG + group updates)         | Seconds to low minutes                        |
| Consolidation     | None (scale-down only)                | Continuous reschedule-and-remove              |
| Spot handling     | Per-group config                      | Automatic diversification across types        |
| Scope             | Multi-cloud, many providers           | AWS first-class (GCP/Azure variants emerging) |

### Node Pools, Labels, Taints Strategy

```yaml
# Pattern: dedicate capacity classes so autoscaling stays sane
apiVersion: v1
kind: Node
metadata:
  labels:
    pool: gpu-training          # selector target
spec: {}
---
# Taint keeps general workloads OFF expensive machines:
#   kubectl taint nodes <node> nvidia.com/gpu=true:NoSchedule
# Workload tolerates + selects:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: trainer
spec:
  template:
    spec:
      nodeSelector: { pool: gpu-training }
      tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
```

Rules of thumb:

- Taint every special pool (GPU, high-memory, spot, sandbox) — untainted special nodes silently attract unrelated pods.
- Give each pool its own CA `--nodes min:max:size` entry (or its own Karpenter `NodePool`) so scaling one class never starves another.
- Prefer `preferredDuringScheduling` soft spread across zones; combine topology-spread with autoscaling carefully (spreads can force extra nodes).

### Overprovisioning Buffer (Headroom Pods)

Provisioning a node takes 1-5 minutes; bursty traffic cannot wait. The trick: deploy lower-priority pause pods whose eviction makes room instantly.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: overprovisioning
value: -1                          # below everything real
globalDefault: false
description: "Headroom placeholder, evicted first"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: overprovisioning-buffer
spec:
  replicas: 4                      # ≈ expected burst size
  selector: { matchLabels: { app: reserve } }
  template:
    metadata: { labels: { app: reserve } }
    spec:
      priorityClassName: overprovisioning
      containers:
        - name: reserve
          image: registry.k8s.io/pause:3.9
          resources:
            requests: { cpu: 500m, memory: 512Mi }   # the reserved amount
```

Mechanics: real pods preempt negative-priority placeholders immediately → no wait for new nodes; the now-Pending placeholders trigger CA/Karpenter to refill the buffer. Size it as (p95 burst replicas − steady replicas) × per-replica requests.

### Scale-From-Zero and Its Caveats

- **Stateless CPU pools**: fine. Karpenter provisions from zero naturally; CA needs an ASG min=0 plus discovery annotations so it knows what a zero-sized group would look like.
- **GPU pools**: images are huge (multi-GB CUDA layers) and driver init takes time; cold-start to Ready can be 5-15 minutes. Keep a warm minimum, or use pre-pulled images/EFS-cached layers. Also: GPU nodes are expensive — scale-to-zero overnight often beats warm buffers economically; measure both.
- **Stateful workloads**: zone-bound volumes (EBS/PDs) constrain which nodes can host the pod; scale-from-zero must land in the volume's zone. Local PVs make nodes effectively unremovable — expect scale-down to skip them entirely. Quorum systems (etcd-style) dislike rapid member churn: pin StatefulSets to stable pools and disable their scale-down.
- **Spot pools**: never scale-from-zero during peak demand for critical services — spot availability fluctuates; hold a small on-demand floor.

## Code Examples

### Reading Autoscaling State

```bash
# What does CA think right now?
kubectl describe configmap cluster-autoscaler-status -n kube-system | head -30
kubectl get events -A | grep -iE 'TriggeredScaleUp|ScaleDown'

# Which pods are waiting on capacity?
kubectl get pods -A --field-selector status.phase=Pending -o wide
kubectl describe pod $POD | grep -A4 Events | tail -6
#   FailedScheduling ... Insufficient cpu  ← capacity problem
#   FailedScheduling ... node(s) didn't match Pod's node affinity/selector ← config problem

# Karpenter view
kubectl get nodeclaims,karpenter/nodepools
kubectl logs -n karpenter deploy/karpenter | grep -i provisioned
```

### Protecting Nodes From Premature Removal

```bash
# Pin a node doing something slow and precious (batch export):
kubectl annotate node $NODE \
  cluster-autoscaler.kubernetes.io/scale-down-disabled=true

# Protect individual pods from consolidation (Karpenter):
#   kubectl annotate pod $POD karpenter.sh/do-not-disrupt=true
```

### Sizing Check Before Blaming Autoscaling

```bash
#!/usr/bin/env bash
# capacity-check.sh — is this really a node-capacity gap?
NS=${1:-default}
echo "== allocatable vs requested per node =="
kubectl get nodes -o custom-columns=\
'NODE:.metadata.name,CPU_ALLOC:.status.allocatable.cpu,MEM_ALLOC:.status.allocatable.memory'

echo "== total requests vs allocatable ($NS) =="
kubectl -n $NS describe resourcequotas 2>/dev/null | sed -n '/Resource/,+3p'
kubectl top nodes
echo "== pending reason breakdown =="
for p in $(kubectl -n $NS get po --field-selector=status.phase=Pending -o name); do
  kubectl -n $NS describe $p | grep -m1 'FailedScheduling' 
done
```

### Karpenter NodePool (Declarative Capacity Tier)

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-purpose
spec:
  template:
    metadata:
      labels: { pool: general }
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand", "spot"]
        - key: node.kubernetes.io/instance-family
          operator: In
          values: ["m", "c"]           # diverse but bounded
        - key: node.kubernetes.io/architecture
          operator: In
          values: ["amd64"]
      taints:
        - key: pool
          value: general
          effect: NoSchedule            # only matching workloads land here
  limits:
    cpu: "200"                          # hard ceiling per tier
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
---
apiVersion: v1
kind: LimitRange                      # guardrail: honest requests
metadata:
  name: default-requests
spec:
  limits:
    - type: Container
      defaultRequest: { cpu: 250m, memory: 256Mi }
```

## Real-World Use Cases

### 1. Burst Traffic With HPA + Buffer

Media API: baseline 12 replicas, campaigns triple traffic in minutes. A 4-replica overprovisioning buffer absorbs the first wave; placeholders go Pending; Karpenter adds two c7g.2xlarge in ~40s; HPA settles at 36 replicas. Without the buffer, p99 doubles for ~3 minutes while nodes boot.

### 2. Overnight Cost Shrink With Consolidation

Analytics workspace: daytime 60 nodes, nights ~15% utilization. Karpenter `WhenEmptyOrUnderutilized` consolidates to 22 nodes nightly; PDBs keep each service above quorum during reschedules. Monthly bill drops ~35% with zero SLO breaches after tuning `consolidateAfter`.

### 3. GPU Training Farm With Dedicated Pool

Training jobs tolerate queueing but not sharing GPUs. A tainted `gpu-training` pool scales 0→16 g5.12xlarge on job arrival, back to 0 after 20 minutes idle (CA `--scale-down-unneeded-time` tuned down). Warm AMI with drivers + pre-pulled CUDA images cut Ready time from 11 to 4 minutes.

### 4. Spot Diversification for Stateless Services

Image thumbnailer runs on spot. Karpenter spreads replacements across three instance families; interruption handler drains pods gracefully; PDB allows one unavailable replica per deployment. Effective compute cost: 68% of on-demand.

## Common Mistakes

| Mistake                                                              | Fix                                                                                                      |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Pods Pending forever, team blames autoscaler                         | First check *why*: `FailedScheduling` reason — affinity/selectors and quotas masquerade as capacity gaps |
| Honest-but-tiny requests causing massive fragmentation               | Right-size requests (VPA recommendation mode); enable consolidation/bin-packing                          |
| Untainted GPU/memory nodes absorbing random pods                     | Taint special pools; require explicit tolerations                                                        |
| Expecting instant scale-up from CA                                   | CA waits on node-group mechanics (minutes). Use buffers or Karpenter for burst sensitivity               |
| Letting scale-down evict cache-warmed or session-local nodes mid-job | `scale-down-disabled` annotation per node; `do-not-disrupt` per pod; tune unneeded-time                  |
| StatefulSets with local PVs on autoscaled nodes                      | Move to network-attached volumes; exclude those nodes from scale-down                                    |

## Best Practices

1. **Fix requests before buying capacity** — most "autoscaling problems" are request-shape problems; audit with VPA recommendation mode quarterly.
2. **One pool per trust/performance class**, all tainted except the default; document min/max per pool like you document quota.
3. **Buffer only the tiers that feel latency**: overprovisioning costs money continuously — apply to user-facing services, not batch.
4. **Set PDBs before enabling aggressive consolidation**; disruption controllers respect them, but only where they exist.
5. **Alert on signals, not symptoms**: pending-pod age > X, buffer exhaustion, scale-up failures hitting provider limits, spot-interruption rate.
6. **Prefer Karpenter on AWS for elastic fleets**; keep CA for multi-cloud uniformity or deeply ASG-integrated estates — both are valid, mixing both on one cluster is not.

## Performance Considerations

| Lever                        | Effect                      | Watch out                                                               |
| ---------------------------- | --------------------------- | ----------------------------------------------------------------------- |
| Overprovisioning buffer size | Hides 1-5min node latency   | Idle cost = buffer × requests × price; revisit monthly                  |
| `--scale-down-unneeded-time` | Stability vs cost           | Too low → thrash during rolling deploys; too high → paying for ghosts   |
| Karpenter `consolidateAfter` | Packing efficiency vs churn | Aggressive settings increase reschedules; protect stateful pods         |
| Zone-balanced expansion      | Failure-domain resilience   | Spreads can force +N nodes for N-zone balance                           |
| Image pull on fresh nodes    | Time-to-ready               | Pre-pull via DaemonSet or use image caching (nydus/SOCI) for big images |
| Provider API limits          | Ceiling on burst speed      | Request quota increases ahead of known events                           |

## Summary

Capacity is a pipeline: honest requests feed the scheduler; the scheduler's leftovers (Pending pods) feed node autoscalers; autoscalers trade money against latency under safety constraints. Cluster Autoscaler is conservative and group-shaped — know its scale-down checklist cold. Karpenter is reactive and instance-exact, with consolidation as the killer economic feature. Structure clusters into tainted node pools, hide provisioning latency with priority-class buffers where bursts matter, and treat GPU and stateful scale-from-zero as special cases requiring warm pools or zone-aware design. In interviews, walk the full chain: metric → HPA → Pending → provisioner → Ready → scheduled.

## Cheat Sheet

```text
NODE AUTOSCALING CHEAT SHEET
════════════════════════════

CLUSTER AUTOSCALER:
• Up: pods Pending + group template could fit them
• Down requires ALL: util < 0.5 · pods movable · PDB ok
  · no scale-down-disabled · past unneeded-time (10m)
• Slow by design: group-level, minutes
• Expander picks group: most-pods | least-waste | price | priority

KARPENTER:
• Watches pending pods; provisions raw instances (no ASG)
• Chooses exact type/size/AZ/spot per batch
• Consolidation: WhenEmptyOrUnderutilized + do-not-disrupt
• Fast: seconds→Ready; declarative NodePool CRDs

POOL STRATEGY:
• Taint every special pool (gpu/mem/spot/sandbox)
• nodeSelector + tolerations pair per workload class
• Separate min/max ceilings per pool

BUFFER (hide provisioning latency):
• PriorityClass value: -1 → pause-pod Deployment sized to burst
• Real pod preempts placeholder instantly; refills trigger CA

SCALE-FROM-ZERO CAVEATS:
• GPU: 5-15min cold (image+driver) → warm pool or accept queue
• Stateful+zone volumes: must land in volume AZ
• local-PV nodes never scale down; quorum sets: pin them

DEBUG ORDER:
1 kubectl describe pod → FailedScheduling reason
2 requests/limits sane? quota? affinity?
3 then: CA status CM / karpenter logs & nodeclaims
```

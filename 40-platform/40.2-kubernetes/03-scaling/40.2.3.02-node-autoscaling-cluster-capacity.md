# Node Autoscaling & Cluster Capacity (Cluster Autoscaler, Karpenter)

A Deployment asks for more Pods, but the scheduler cannot find a node with enough available requested CPU. The workload count is already correct; the missing part is somewhere to run it. Node autoscaling supplies that capacity, then removes capacity that can be reclaimed safely.

## Definition

**Node autoscaling** adjusts the number of worker nodes to match aggregate pod demand:

> **Textbook Definition:** Node autoscaling reconciles cluster compute capacity with workload scheduling demand, provisioning or removing nodes subject to resource requests, placement constraints, disruption policies, and provider limits.

The Kubernetes scheduler assigns each admitted Pod to a feasible node. A node autoscaler observes Pods that cannot be placed and asks a cloud provider for capacity. It does not assign the Pod itself: the new machine must join the cluster, become usable, and pass the scheduler's constraints before its kubelet starts the workload.

**Cluster Autoscaler (CA)** grows predefined node groups, such as an AWS Auto Scaling Group (ASG). Each group provides a template of what another node would offer. **Karpenter**, using its AWS provider in this chapter, chooses individual instances within declared **NodePool** constraints. A NodePool describes acceptable capacity; a provider **NodeClass** describes how that capacity launches, including images, networking, and identity. Other providers have their own implementation and capabilities.

```text
HPA requests replicas -> Deployment creates Pods -> scheduler tries placement
                                                        |
                                         no feasible existing node
                                                        |
                         autoscaler simulates acceptable new capacity
                                      /                         \
                         CA grows a node group       Karpenter creates NodeClaim
                                      \                         /
                                        provider launches machine
                                                    |
                                    node joins and becomes usable
                                                    |
                                    scheduler assigns waiting Pod
                                                    |
                                  kubelet starts it -> readiness passes
```

These arrows describe separate controllers, not one atomic operation. A **NodeClaim** tracks Karpenter's requested instance lifecycle. Provider launch success is not application readiness. A Pending Pod may also be waiting for a volume or image rather than node capacity; inspect its scheduling events before diagnosing it. A namespace quota can reject Pod creation before there is any Pending Pod to observe.

## First Principles

A node has finite CPU, memory, storage, and device capacity. Some is reserved for node services; the remainder is **allocatable**, the amount Kubernetes can offer to workloads. Scheduling accounts for declared resource requests and placement rules. Plenty of idle CPU across several nodes does not help a Pod that needs more contiguous capacity than any permitted node has.

Suppose two permitted nodes each have `1` CPU left, but a new Pod requests `1500m` (1.5 CPUs). Neither fits, even though the aggregate free amount is two CPUs. A suitable new node can solve that shape mismatch. A new node in the wrong zone or without the required GPU cannot. Autoscaling must simulate a feasible placement rather than merely divide total demand by total cluster capacity.

Removing a node reverses that reasoning: its workloads need feasible destinations and a safe interruption window. Packing tightly saves money but leaves less room for a burst or failed node. Warm headroom is a deliberate cost and latency decision, not wasted capacity by definition.

## Why Do We Need It?

| Problem | Solution |
| --------------------------------------------- | ------------------------------------------------------------------ |
| HPA adds replicas but nothing schedules | Node autoscaler creates capacity for Pending pods |
| Paying for idle nodes at 3am | Scale-down (CA) or consolidation (Karpenter) |
| Black-Friday spikes need +40 nodes in minutes | Karpenter direct provisioning; warm/pinned buffers otherwise |
| Mixed fleets: CPU jobs vs GPU training | Node pools with taints keep accelerators reserved |
| Spot interruptions | Diversified instance selection (Karpenter) / multi-ASG groups (CA) |
| Node churn hurting latency-sensitive apps | Overprovisioning buffer; scale-down stabilization windows |

## How It Works

### Cluster Autoscaler Behavior

CA examines Pods reported as unschedulable and simulates them against configured node-group templates. If a group could accommodate waiting work and has room under its bounds, CA requests a larger group size. An **expander** chooses among feasible groups according to the installed strategy. Provider quotas, instance availability, bootstrap failures, and scale-up backoff can prevent that request from becoming usable capacity; a reconciliation interval is not a provisioning deadline.

For scale-down, CA first identifies nodes whose requested load is low enough under its configuration. It then checks whether their movable workloads can run elsewhere and whether eviction is allowed. PodDisruptionBudgets (PDBs), local storage, placement rules, unmanaged workloads, and protective annotations can prevent removal. DaemonSet Pods normally follow their nodes and are treated differently from application Pods; their presence alone does not make a node unremovable.

A request-based utilization of `0.3` does not prove a node is removable: moving a zone-bound volume or a Pod protected by a fully consumed PDB may still be impossible. The unneeded-time setting requires a node to remain unnecessary long enough; a separate delay-after-add setting postpones scale-down after expansion. Consult the installed version's configuration rather than treating an abbreviated checklist as an exhaustive removal algorithm.

CA discovers only the groups its provider configuration allows it to manage. It can scale an eligible group to zero when supported and when its workloads remain schedulable; there is no universal rule requiring every group to retain its last node.

### Karpenter Model

```text
                     ┌─────────────────────────────┐
 kube events ───────▶│ Karpenter controller        │
 pending pods        │  ├─ scheduling simulation   │
                     │  ├─ NodePool specs          │
                     │  └─ disruption/consolidation│
                     └──────────┬──────────────────┘
                                │ chooses instance type/size/AZ/spot
                                ▼
                  raw EC2/Fleet API (NO ASG in the path)
                                │
                                ▼
                  NodeClaim → Node joins → kubelet registers

NodePool (declarative): constraints + limits + disruption budgets
  • labels/taints applied to provisioned nodes
  • instance categories/families/sizes/architectures allowlist
  • consolidation policy: WhenEmpty vs WhenEmptyOrUnderutilized
  • do-not-disrupt annotations protect sensitive pods
```

The provisioner changes the choice being simulated: CA compares group templates; Karpenter intersects Pod requirements with NodePool and provider offerings. Both still depend on actual launch availability and Kubernetes scheduling. Compare that ownership before comparing speed:

| Aspect | Cluster Autoscaler | Karpenter |
| ------------------- | --------------------------------------------------------- | ------------------------------------------------------------------- |
| Input signal | Unschedulable pods (scheduler output) | Pending pods (scheduling simulation itself) |
| Provisioning unit | Pre-defined node groups/ASGs/MIGs | Individual instances via cloud Fleet API |
| Instance choice | Whatever the group template says | Best-fit per batch of pods; flexible families |
| Bin-packing | Indirect (group granularity) | Native (per-provisioning + consolidation) |
| Provisioning delay | Group update, launch, and bootstrap determine it | Instance launch and bootstrap determine it; measure the full path |
| Reclaiming capacity | Remove an unneeded node after placement and safety checks | Remove or replace nodes when a feasible cheaper placement exists |
| Spot handling | Per-group config | Automatic diversification across types |
| Provider scope | Capabilities vary by cloud provider integration | This example uses the AWS provider; check the chosen implementation |

### Node Pools, Labels, Taints Strategy

A **label** describes a node, a **selector** requires a matching label, and a **taint** repels Pods unless they have a matching **toleration**. Tolerating a taint permits placement; it does not force it. To dedicate GPU nodes, label and taint capacity through the node group or NodePool configuration. Do not create a fake Node object to provision a machine.

This fragment belongs inside an existing workload's `spec.template.spec`; the Deployment still needs its usual selector, matching Pod labels, containers, and GPU resource request:

```yaml
nodeSelector:
  pool: gpu-training
tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule
```

The selector chooses the pool; the toleration permits its taint. A real training container also requests `nvidia.com/gpu` after the provider's device plugin exposes that resource. Otherwise this fragment only selects GPU-capable machines and does not allocate an accelerator.

Rules of thumb:

- Taint every special pool (GPU, high-memory, spot, sandbox) — untainted special nodes silently attract unrelated pods.
- Give each pool its own CA `--nodes min:max:group-name` entry (or its own Karpenter `NodePool`) so scaling one class never starves another.
- Prefer `preferredDuringScheduling` soft spread across zones; combine topology-spread with autoscaling carefully (spreads can force extra nodes).

### Overprovisioning Buffer (Headroom Pods)

Provisioning and bootstrapping take time that must be measured for the actual fleet. A headroom buffer runs low-priority placeholder Pods on already usable nodes. Higher-priority application Pods can preempt them and reuse that requested capacity. Preemption, image pull, and readiness still take time; the buffer primarily avoids waiting for another machine.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: overprovisioning
value: -1                          # below everything real
globalDefault: false
description: "Headroom placeholder, evicted first"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: overprovisioning-buffer
spec:
  replicas: 4                      # ≈ expected burst size
  selector: { matchLabels: { app: reserve } }
  template:
    metadata: { labels: { app: reserve } }
    spec:
      priorityClassName: overprovisioning
      containers:
        - name: reserve
          image: registry.k8s.io/pause:3.9
          resources:
            requests: { cpu: 500m, memory: 512Mi }   # the reserved amount
```

When a higher-priority Pod cannot fit, the scheduler may nominate a node and remove suitable lower-priority placeholders. Replacement placeholders then become unschedulable, potentially prompting more capacity. CA can ignore Pods below its configured expendable-priority cutoff, so choose a placeholder priority that still triggers the intended refill behavior. Verify that refill, rather than assuming every negative-priority Pod does it. Size the reserved requests against observed burst size and startup time; a percentile-based estimate leaves larger bursts uncovered.

### Scale-From-Zero and Its Caveats

- **Stateless CPU pools**: fine. Karpenter provisions from zero naturally; CA needs a zero-minimum group plus provider-specific template/discovery information so it knows what a zero-sized group would look like.
- **GPU pools**: images are huge (multi-GB CUDA layers) and driver init takes time; cold-start to Ready can be 5-15 minutes. Keep a warm minimum, or use pre-pulled images/EFS-cached layers. Also: GPU nodes are expensive — scale-to-zero overnight often beats warm buffers economically; measure both.
- **Stateful workloads**: zone-bound volumes (EBS/PDs) constrain which nodes can host the pod; scale-from-zero must land in the volume's zone. Local persistent volumes tie data to a particular node; a spare cloud machine cannot recreate that data. Safe relocation requires a separate data migration or replication design. Quorum systems (etcd-style) dislike rapid member churn: pin StatefulSets to stable pools and disable their scale-down.
- **Spot pools**: never scale-from-zero during peak demand for critical services — spot availability fluctuates; hold a small on-demand floor.

## Code Examples

### Reading Autoscaling State

```bash
# What does CA think right now?
kubectl describe configmap cluster-autoscaler-status -n kube-system | head -30
kubectl get events -A | grep -iE 'TriggeredScaleUp|ScaleDown'

# Which pods are waiting on capacity?
kubectl get pods -A --field-selector status.phase=Pending -o wide
kubectl describe pod $POD | grep -A4 Events | tail -6
#   FailedScheduling ... Insufficient cpu  ← capacity problem
#   FailedScheduling ... node(s) didn't match Pod's node affinity/selector ← config problem

# Karpenter view
kubectl get nodeclaims,nodepools
kubectl logs -n karpenter deploy/karpenter | grep -i provisioned
```

### Protecting Nodes From Premature Removal

```bash
# Pin a node doing something slow and precious (batch export):
kubectl annotate node $NODE \
  cluster-autoscaler.kubernetes.io/scale-down-disabled=true

# Protect individual pods from consolidation (Karpenter):
#   kubectl annotate pod $POD karpenter.sh/do-not-disrupt=true
```

### Sizing Check Before Blaming Autoscaling

Run this in an authorized cluster context. It shows allocatable node capacity, namespace quotas, live usage, and Pending events; it does not calculate total per-node requests. Use `kubectl describe node <node>` for allocated requests. `kubectl top` additionally requires a working resource metrics API. Set `POD`/`NODE` and the namespace before commands referring to those placeholders. Controller names and namespaces vary by installation.


```bash
#!/usr/bin/env bash
# capacity-check.sh — is this really a node-capacity gap?
NS=${1:-default}
echo "== allocatable vs requested per node =="
kubectl get nodes -o custom-columns=\
'NODE:.metadata.name,CPU_ALLOC:.status.allocatable.cpu,MEM_ALLOC:.status.allocatable.memory'

echo "== namespace quota and observed usage ($NS) =="
kubectl -n $NS describe resourcequotas 2>/dev/null | sed -n '/Resource/,+3p'
kubectl top nodes
echo "== pending reason breakdown =="
for p in $(kubectl -n $NS get po --field-selector=status.phase=Pending -o name); do
  kubectl -n $NS describe $p | grep -m1 'FailedScheduling'
done
```

### Karpenter NodePool (Declarative Capacity Tier)

This AWS-provider example assumes installed Karpenter CRDs/controllers, provider permissions, and a ready `EC2NodeClass` named `general-purpose` that selects your subnets, security groups, image, and node identity. The NodePool references that launch configuration; it cannot provision with constraints alone. Workloads need a matching `pool=general` toleration for this example.


```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-purpose
spec:
  template:
    metadata:
      labels: { pool: general }
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: general-purpose
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand", "spot"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["m", "c"]           # diverse but bounded
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]
      taints:
        - key: pool
          value: general
          effect: NoSchedule            # only matching workloads land here
  limits:
    cpu: "200"                          # aggregate pool provisioning limit
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
---
apiVersion: v1
kind: LimitRange                      # guardrail: honest requests
metadata:
  name: default-requests
spec:
  limits:
    - type: Container
      defaultRequest: { cpu: 250m, memory: 256Mi }
```

The NodePool restricts architecture and instance categories before Karpenter chooses an available offering. Its aggregate CPU limit bounds provisioning decisions; concurrent reconciliation can temporarily exceed it, so it is not a precise billing cap. The separate LimitRange supplies default requests to admitted containers in its namespace. Defaults are guardrails, not workload measurements.

## Real-World Use Cases

The following are illustrative scenarios and candidate measurements, not reported production results. Numbers describe example workloads; measure your own time-to-ready, latency, disruption, and cost before accepting a policy.


### 1. Burst Traffic With HPA + Buffer

Media API: baseline 12 replicas, campaigns triple traffic in minutes. A 4-replica overprovisioning buffer absorbs the first wave; placeholders go Pending; an ARM-compatible Karpenter pool might add suitable nodes; HPA settles at 36 replicas. Without the buffer, p99 doubles for ~3 minutes while nodes boot.

### 2. Overnight Cost Shrink With Consolidation

Analytics workspace: daytime 60 nodes, nights ~15% utilization. Karpenter `WhenEmptyOrUnderutilized` consolidates to 22 nodes nightly; PDBs keep each service above quorum during reschedules. Compare the monthly bill and SLO results after tuning `consolidateAfter`; fewer nodes alone does not establish safe savings.

### 3. GPU Training Farm With Dedicated Pool

Training jobs tolerate queueing but not sharing GPUs. A tainted `gpu-training` pool scales 0→16 g5.12xlarge on job arrival, back to 0 after 20 minutes idle (CA `--scale-down-unneeded-time` tuned down). Warm AMI with drivers + pre-pulled CUDA images cut Ready time from 11 to 4 minutes.

### 4. Spot Diversification for Stateless Services

Image thumbnailer runs on spot. Karpenter spreads replacements across three instance families; interruption handler drains pods gracefully; PDB allows one unavailable replica per deployment. Measure effective cost including interruptions, repeated work, and on-demand fallback.

## Common Mistakes

| Mistake | Fix |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Pods Pending forever, team blames autoscaler | First check *why*: `FailedScheduling` reason — affinity/selectors and quotas masquerade as capacity gaps |
| Honest-but-tiny requests causing massive fragmentation | Right-size requests (VPA recommendation mode); enable consolidation/bin-packing |
| Untainted GPU/memory nodes absorbing random pods | Taint special pools; require explicit tolerations |
| Expecting instant scale-up from CA | CA waits on node-group mechanics (minutes). Use buffers or Karpenter for burst sensitivity |
| Letting scale-down evict cache-warmed or session-local nodes mid-job | `scale-down-disabled` annotation per node; `do-not-disrupt` per pod; tune unneeded-time |
| StatefulSets with local PVs on autoscaled nodes | Move to network-attached volumes; exclude those nodes from scale-down |

## Best Practices

1. **Fix requests before buying capacity** — most "autoscaling problems" are request-shape problems; audit with VPA recommendation mode quarterly.
2. **One pool per trust/performance class**, all tainted except the default; document min/max per pool like you document quota.
3. **Buffer only the tiers that feel latency**: overprovisioning costs money continuously — apply to user-facing services, not batch.
4. **Set PDBs before enabling aggressive consolidation**; cooperating voluntary eviction paths respect them. Provider interruption or a forced termination deadline can still remove capacity; a budget is not a physical availability guarantee.
5. **Alert on signals, not symptoms**: pending-pod age > X, buffer exhaustion, scale-up failures hitting provider limits, spot-interruption rate.
6. **Prefer Karpenter on AWS for elastic fleets**; keep CA for multi-cloud uniformity or deeply ASG-integrated estates — both can coexist when capacity ownership is separate. Do not let two controllers independently manage the same node groups or assume every Pod belongs to both provisioning paths.

## Performance Considerations

| Lever | Effect | Watch out |
| ---------------------------- | --------------------------- | ----------------------------------------------------------------------- |
| Overprovisioning buffer size | Hides 1-5min node latency | Idle cost = buffer × requests × price; revisit monthly |
| `--scale-down-unneeded-time` | Stability vs cost | Too low → thrash during rolling deploys; too high → paying for ghosts |
| Karpenter `consolidateAfter` | Packing efficiency vs churn | Aggressive settings increase reschedules; protect stateful pods |
| Zone-balanced expansion | Failure-domain resilience | Spreads can force +N nodes for N-zone balance |
| Image pull on fresh nodes | Time-to-ready | Pre-pull via DaemonSet or use image caching (nydus/SOCI) for big images |
| Provider API limits | Ceiling on burst speed | Request quota increases ahead of known events |

## Summary

Capacity is a pipeline: honest requests feed the scheduler; the scheduler's leftovers (Pending pods) feed node autoscalers; autoscalers trade money against latency under safety constraints. Cluster Autoscaler is conservative and group-shaped — know its scale-down checklist cold. Karpenter chooses individual allowed instances and can consolidate by removing or replacing capacity. Structure clusters into tainted node pools, hide provisioning latency with priority-class buffers where bursts matter, and treat GPU and stateful scale-from-zero as special cases requiring warm pools or zone-aware design. In interviews, walk the full chain: metric → HPA → Pod creation → scheduling failure → capacity request → usable node → Pod assignment → application readiness.

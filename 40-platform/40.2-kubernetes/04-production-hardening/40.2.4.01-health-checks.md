# Kubernetes Health Checks

A process can be running while still loading configuration, unable to reach a required database, or stuck forever. These states need different responses. Sending it traffic, removing it from rotation, and restarting it are separate decisions.

## Definition

Kubernetes **probes** let the node's **kubelet** observe a container and act on the result. A **startup probe** asks whether initialization has completed. A **readiness probe** asks whether the container can serve normal traffic. A **liveness probe** asks whether restarting this container is a useful recovery action.

> **Textbook Definition:** Kubernetes probes are container health observations: startup probes gate initialization, liveness probes trigger restart after failure, and readiness probes determine normal traffic eligibility through Service endpoints.

A successful observation is evidence for the chosen check, not proof that every application operation works. A TCP connection can succeed while an HTTP route returns errors. Design the check around the action Kubernetes will take.

## First Principles

Starting a process takes time, and a supervisor cannot infer its internal progress from the existence of a PID. Restarting a healthy but initializing process destroys that progress. Initialization therefore needs a bounded waiting period separate from the ordinary stuck-process test.

After startup, some failures are temporary and external. Restarting every API replica during a shared database outage cannot repair the database and can add reconnection load. Traffic withdrawal may be useful, but restart requires evidence of a local failure that a fresh process can recover from. Conversely, an unrecoverable deadlock needs a restart even if no clients are currently calling the service.

## How the kubelet turns observations into actions

```text
container starts -> startup probe repeats until success
                          |                    |
                  threshold failures          success once
                          |                    |
                 stop container;       enable two independent checks
                 restart policy                |
                 governs next start      +-----+----------------+
                                         |                      |
                                   liveness fails         readiness fails
                                   past threshold         past threshold
                                         |                      |
                                   stop/restart          mark not ready;
                                   container             withdraw ordinary
                                                         Service eligibility
```

Startup is not one attempt: it repeats until it succeeds or exhausts its failure threshold. Once successful, it stops for that container instance. Liveness and readiness then run independently; readiness does not wait for liveness success. A container restart starts the startup check again.

A failed readiness check keeps the process running so it can recover. Endpoint changes propagate through controllers and the network; they do not instantly cancel an existing request or prevent direct Pod access. Graceful shutdown must separately finish or reject in-flight work. Services using `publishNotReadyAddresses` intentionally have different endpoint behavior.

Without a readiness probe, a running container is ordinarily considered ready. Without liveness, the runtime still notices a process exit, but Kubernetes has no application-specific probe for a live yet stuck process. Use a startup probe when initialization needs protection; installing all three types mechanically is not always useful.

### Each handler observes a different property

| Handler | What succeeds | What it cannot establish by itself |
| ----------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| `httpGet` | Response status from 200 through 399 on the configured path | A shallow route does not exercise every dependency or business operation |
| `exec` | Command in the container exits with status zero | A stale file may outlive the healthy state it once represented |
| `tcpSocket` | Kubelet establishes a connection to the container's port | A listener may accept connections while application work is broken |
| `grpc` | The configured numeric port answers the gRPC health-check protocol | An arbitrary gRPC method is not a health protocol; native probes have protocol/authentication limitations |

For an exec check, the image must contain the command. For gRPC, the server must implement the standard health service; use its optional service name to distinguish check meanings. The kubelet performs network probes from the node, so probe reachability is a separate condition from a client reaching a Service.

## Configure one workload and trace its behavior

This complete Deployment assumes an image serving `/health`, `/alive`, and `/ready` on port 8080. Replace the image with your own. The image must already implement those endpoints; YAML does not create them.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: myapp
          image: myapp:1.0.0
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet: {path: /health, port: 8080}
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 30
          livenessProbe:
            httpGet: {path: /alive, port: 8080}
            periodSeconds: 15
            timeoutSeconds: 3
            failureThreshold: 3
          readinessProbe:
            httpGet: {path: /ready, port: 8080}
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
            successThreshold: 1
```

The startup configuration provides a nominal `30 × 10 = 300` second attempt window; actual timing also depends on when probes run and their duration. Once startup succeeds, three consecutive failed liveness attempts stop the container. Three failed readiness attempts instead make it unready; one later success restores readiness. Period and timeout settings are detection budgets, not precise end-to-end outage deadlines.

This local Node.js example needs no packages. Save it as `probe-demo.cjs` and run `node probe-demo.cjs`; it serves on port 8080. Its timer simulates initialization only. A real application must set dependency health from bounded connection checks or reliable client state, rather than leave this demo flag permanently true.

```javascript
const http = require('node:http');
let initialized = false;
let dependencyAvailable = true; // Demo assumption, not a real database check.
setTimeout(() => { initialized = true; }, 2000);

http.createServer((req, res) => {
  const checks = {
    '/health': initialized,
    '/alive': true, // If this event loop answers, this shallow local check passes.
    '/ready': initialized && dependencyAvailable,
  };
  if (!(req.url in checks)) {
    res.writeHead(404).end();
    return;
  }
  const ok = checks[req.url];
  res.writeHead(ok ? 200 : 503, {'content-type': 'application/json'});
  res.end(JSON.stringify({ok}));
}).listen(8080);
```

Initially `/health` and `/ready` return 503 while `/alive` returns 200. After two seconds, all return 200 under the demo assumptions. If a real dependency monitor sets `dependencyAvailable` false after initialization, `/ready` returns 503 while `/health` and `/alive` stay 200. Kubernetes withdraws ordinary Service eligibility without restarting an otherwise responsive process. If the event loop cannot answer probes, the network check times out and the threshold determines the next action.

## Workload-specific decisions

A database's `pg_isready` check reports connection acceptance; it does not prove replication freshness, query correctness, or that restarting will help. Use it only for a decision that needs that signal. A database deployment also needs credentials, persistent storage, and its controller configuration; a probe fragment alone is not a working StatefulSet.

A queue worker may not receive Service traffic at all. Its readiness flag does not automatically pause queue consumption. The application must coordinate job intake, checkpoints, and termination. A file-based liveness check such as `cat /tmp/healthy` works only if the process reliably creates and removes that marker according to current health; an indefinitely retained file hides a stuck worker.

Readiness can include dependencies essential to every served request. For optional dependencies, withdrawal of every replica may be worse than degraded service. Choose the contract deliberately. Keep liveness cheap and local when a shared dependency outage would otherwise create a restart storm.

## Observe and tune the response

```bash
kubectl get pods -l app=myapp
kubectl describe pod <pod-name>
kubectl get events --field-selector reason=Unhealthy
kubectl get pod <pod-name> -o jsonpath='{.spec.containers[*].livenessProbe}'
```

Run these against the intended namespace and cluster. Compare container restart count, readiness, and probe events after controlled startup delay, local failure, and dependency failure. A passing shallow check can coexist with a business-route failure; compare service errors and latency as well.

Probe frequency consumes resources, especially when exec spawns a process or HTTP performs expensive work. Short timeouts and thresholds find failures faster but can restart a busy healthy replica. Measure startup duration and overloaded behavior before choosing settings, and verify recovery after traffic withdrawal rather than only observing the failure transition.

## Summary

Startup protects bounded initialization; liveness can stop and restart a failed container; readiness withdraws ordinary Service traffic while leaving the process alive. Each probe's meaning must justify its resulting action. Trace thresholds, endpoint propagation, dependency behavior, and in-flight work separately; a probe result is evidence for its check, not a complete application availability guarantee.

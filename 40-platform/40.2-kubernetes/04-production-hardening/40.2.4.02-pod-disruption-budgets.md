# Pod Disruption Budgets

A node drain wants to evict a healthy Pod, while the service still needs enough replicas to handle traffic. A PodDisruptionBudget lets the eviction API admit or reject that maintenance request based on the workload's current healthy count.

## Definition

A **PodDisruptionBudget (PDB)** constrains voluntary Pod **evictions through the Kubernetes eviction API**. It expresses a minimum healthy population (`minAvailable`) or a maximum unavailable population (`maxUnavailable`) for selected Pods.

> **Textbook Definition:** A PodDisruptionBudget limits voluntary evictions through the Kubernetes eviction API by specifying an allowed unavailable population or required healthy population among selected Pods.

A PDB does not guarantee uptime. Direct deletion, node failure, and workload-controller actions can bypass its eviction constraint; an involuntary failure can still reduce the healthy count and leave less disruption allowance. Deployment rolling updates and HPA replica reductions are governed by their own controllers, not blocked by a PDB.

## First Principles

Maintenance may need to remove a healthy process while the service still needs a minimum serving population — a budget turns that competing requirement into an explicit admission decision. A replacement Pod is not useful until it is healthy, so the calculation must count healthy availability rather than assume a desired or merely running replica serves traffic. And only a cooperating disruption path can enforce the policy: eviction admission can reject a request, but a failed node cannot ask permission before failing.

## 1. Admit or Reject Each Eviction Against Current Health

```text
maintenance requests eviction
  -> eviction API evaluates relevant budget/status
  -> enough healthy capacity: accept eviction, account for pending disruption
  -> insufficient healthy capacity: reject/retry
  -> workload controller creates replacement; readiness restores capacity
```

For an ordinary healthy population, `disruptionsAllowed` reflects the positive difference between current healthy Pods and the desired healthy threshold, including in-progress disruption accounting. The controller-calculated status can lag the current Pods; inspect it after reconciliation, and treat the eviction API response as the actual admission decision.

For **three desired replicas and `maxUnavailable: 1`**, desired healthy is two. With three healthy Pods, one eviction is permitted. After one accepted eviction leaves two healthy Pods, a second eviction is **not** permitted until enough health returns. The first eviction does not grant another one merely because the Deployment intends to replace it.

Percentage values round up under Kubernetes rules. For one replica, `maxUnavailable: "30%"` can therefore allow one unavailable Pod and complete loss of service. Quorum, topology, and the consequences of partial failure must determine the policy.

With the stable `policy/v1` API, `selector: {}` matches every Pod in the namespace; use explicit labels and inspect the resulting `expectedPods` and `disruptionsAllowed`. `maxUnavailable` also needs the selected Pods to have the same managing controller. For bare Pods or workloads without a supported scale subresource, use an integer `minAvailable` instead.

## 2. Declare the Budget for a Stateless Service and a Quorum

A stateless three-replica service:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-maintenance
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: api
```

`AlwaysAllow` allows unhealthy running Pods to be evicted during drain even when the normal healthy budget is not met; it does not permit extra healthy Pods to be evicted. The field is stable from Kubernetes 1.31 — check support before applying it to an older cluster. The default `IfHealthyBudget` can leave drain blocked by unhealthy Pods.

A quorum-oriented workload:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: quorum-maintenance
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: quorum-service
```

This assumes a five-member application whose actual protocol needs three healthy members. A PDB counts Pod readiness; it does not verify database membership or replication lag. StatefulSet identity and ordered behavior come from the StatefulSet controller and application, not this PDB.

## 3. Observe Before Draining

```bash
kubectl get pdb -n production
kubectl describe pdb api-maintenance -n production
kubectl get pods -n production -l app=api
kubectl drain worker-1 --ignore-daemonsets --timeout=10m
```

Verify replacement capacity and scheduling constraints first. Do not bypass blocked eviction or force deletion without diagnosing the availability and data consequences.

## Real-World Use Cases

Node upgrades and autoscaler consolidation can respect eviction budgets while relocating workloads. Pair budgets with accurate readiness, distributed placement, surge/replacement capacity, and graceful shutdown. For a Deployment release, configure and test its `maxSurge`/`maxUnavailable` strategy separately.

Choose the healthy threshold from the application's actual failure tolerance, then test a node drain and verify replacement Pods can schedule. A blocked drain is a reason to inspect readiness, `disruptionsAllowed`, selector scope, and capacity. Do not weaken the budget until you understand which protection it is enforcing.

## Summary

A PDB limits voluntary eviction through the eviction API. It does not control HPA replica changes, workload rollouts, direct deletion, or involuntary failure. Healthy accounting, rounding, replacement capacity, and application quorum determine whether its policy is safe and usable.

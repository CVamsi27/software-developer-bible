# RBAC & Network Policies

## Definition

**Role-Based Access Control (RBAC)** authorizes requests to the Kubernetes API through rules and bindings. A **NetworkPolicy** declares permitted Pod ingress and egress; an installed network implementation must enforce those rules.

> **Textbook Definition:** Role-Based Access Control (RBAC) authorizes Kubernetes API operations through role bindings. NetworkPolicy declares permitted Pod network traffic, whose enforcement depends on a supporting network implementation.

## First Principles

A workload has two different ways to affect its surroundings: it can call the Kubernetes API to read or change objects, and it can connect to other processes over the network. Preventing one does not prevent the other. A Pod allowed to contact the API server still needs authorization to read a Secret; a Pod denied Secret reads may still be able to reach the database with credentials it already holds.

RBAC grants an API operation when a rule matches. When no RBAC rule matches, the RBAC authorizer returns no opinion rather than a negative deny. The API server follows its configured authorizer chain: a conclusive allow or deny decides the request; if every authorizer returns no opinion, the request is denied. RBAC grants are additive, so a narrower role does not cancel a broader grant already bound to the subject. NetworkPolicy rules are also additive: a narrower policy cannot subtract a path allowed by another matching policy.

## Why Do We Need It?

RBAC separates API permissions for people, teams, and workloads. NetworkPolicy reduces permitted Pod-to-Pod and egress paths. These controls address different boundaries; validate effective API permissions and actual network behavior instead of treating either manifest as proof of containment.

## How It Works

### RBAC mechanics: the verbs are the API

Authentication first establishes a subject such as a user, group, or ServiceAccount. Authorization then checks the operation: API group, resource/subresource, verb, and namespace where applicable. A **Role** stores permissions in one namespace. A **RoleBinding** grants a Role, or a reusable ClusterRole, within its namespace. A **ClusterRoleBinding** grants its ClusterRole across the cluster, including namespaced resources wherever that rule applies.

These objects are complementary: a Role without a binding grants nobody access; a binding without a matching rule does not allow the operation. `pods` and `pods/log` are distinct resources. Reading Pod metadata does not automatically permit reading its logs or starting a shell through `pods/exec`.

Secret access is powerful because stored credentials may unlock other systems or identities. Its actual reach depends on which Secrets and permissions exist; it is not universally equivalent to cluster-admin. Pod creation in a namespace can also expose credentials through mounted Secrets or ServiceAccount selection, so restricting direct Secret reads alone is incomplete.

A **ServiceAccount** is a namespaced workload identity. Since Kubernetes v1.22, a Pod normally receives a short-lived projected token that the kubelet rotates. Kubernetes v1.24 stopped automatically creating a long-lived token Secret for each ServiceAccount; that change became stable in v1.27. An administrator can still create a legacy token Secret manually, but the Kubernetes project recommends short-lived tokens. Set `automountServiceAccountToken: false` when a workload does not call the API, and check for explicit token projections as well.

### NetworkPolicy mechanics: additive and connection-oriented

A NetworkPolicy selects destination Pods for ingress and source Pods for egress. Once any matching policy isolates a direction, only that direction's permitted connections remain allowed under the supported model. All matching policies contribute a union of allows. A source-to-destination connection needs both the source's egress permission and the destination's ingress permission when those directions are isolated. Replies on an allowed connection are implicitly permitted.

A **Container Network Interface (CNI)** plugin supplies Pod networking; policy enforcement requires a supporting network implementation. The API can accept a policy object even when the data plane does not enforce it. Test an allowed connection and a denied new connection in the real cluster; object creation alone proves only configuration acceptance.

A `podSelector` peer matches Pods in the policy's own namespace. A `namespaceSelector` matches namespace labels. Both inside one peer entry mean their conditions must match together; separate peer entries mean either can match. An `ipBlock` expresses address ranges, commonly for external peers; Service address translation can make the observed address implementation-dependent. Standard NetworkPolicy primarily controls IP/transport traffic, not HTTP routes; vendor layer-seven extensions are separate APIs.

Policy propagation is not necessarily instant or globally atomic: a network implementation may take time to apply a new policy across nodes. Do not treat a newly created policy as immediate quarantine; use the cluster's incident-isolation controls when time matters, then verify the data plane.

## Code Examples

### RBAC: Role & RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: default
  name: read-pods
subjects:
- kind: User
  name: alice@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

The binding above assumes authentication already identifies the user as `alice@example.com`. It grants get/list/watch on Pods and `get` on their log subresource in `default`, not Secret reads or access in another namespace. Use `kubectl auth can-i get pods -n default --as=alice@example.com` from an administrator allowed to impersonate that user; without impersonation rights the command cannot establish the result.

### Network Policy

This namespace-wide policy makes both directions isolated for every Pod in the namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

An empty selector deliberately matches all Pods in this NetworkPolicy's namespace. This policy has no allow rules, so it blocks DNS and application egress and can disrupt health, telemetry, or control-plane integrations that rely on Pod network paths. Apply it in a test namespace with the required allow policies, then verify both permitted and denied connections before using the pattern in production.

The next policy assumes appropriately labeled workloads and an enforcing network implementation. It selects API Pods, permits frontend ingress on TCP 3000, and permits database egress on TCP 5432. It intentionally omits DNS to show why an otherwise correct data path can still fail. It does not define the frontend's egress policy or the database's ingress policy; those are separate sides of the connection.


```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 3000
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

If the API calls its database by a DNS name, it also needs a DNS egress allow. Inspect the cluster's DNS topology and labels first; node-local DNS deployments can need different rules. This additional policy is an example for a cluster whose DNS Pods carry `k8s-app: kube-dns` in `kube-system`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-dns
spec:
  podSelector:
    matchLabels: {app: api}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: kube-system}
          podSelector:
            matchLabels: {k8s-app: kube-dns}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}
```

The two selectors are in one peer entry, so this permits those labeled Pods **in that namespace**, not every Pod in kube-system or every locally labeled DNS Pod. Its allows combine with the database rule. The database's own ingress policy and the frontend's own egress policy must also permit their halves of the connection. Adding a select-all default-deny policy does not subtract these existing allows; it isolates otherwise unselected Pods.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Using default ServiceAccount | Create dedicated ServiceAccount per workload |
| ClusterRoleBinding used where one namespace was intended | Use a RoleBinding to a Role or reusable ClusterRole |
| No default-deny NetworkPolicy | The NetworkPolicy layer allows ingress and egress by default for non-isolated Pods; other network controls may still block traffic |
| NetworkPolicy without a supporting network implementation | The API can store the object without enforcing it; kube-proxy alone does not provide NetworkPolicy enforcement |
| Overly broad verbs ("*") | Use minimum verbs needed |
| Treating API audit logs as network-flow evidence | Audit logs record Kubernetes API requests, not every Pod packet; pair them with data-plane telemetry and tests |

## Real-World Usage

- **Network-policy rollout**: apply a namespace-scoped default-deny ingress/egress policy, then explicit workload and DNS allows. A reusable Kustomize base must be composed and applied for each namespace; Kustomize does not automatically protect namespaces created later. Route external egress through an approved proxy when the design requires domain-level controls, because standard NetworkPolicy filters IP/transport traffic rather than HTTP hostnames.
- **RBAC through the platform layer**: bind team groups to namespace-scoped roles and give each workload a dedicated ServiceAccount with only the required verbs. Give CI deployers access only to the namespaces they operate. `kubectl auth can-i --list --as=system:serviceaccount:ns:sa` checks the effective permissions when the caller is authorized to impersonate that ServiceAccount; inspect bindings as well as the decision result.
- **A compromised application**: an attacker inherits the workload's credentials and reachable services. The default ServiceAccount does not normally grant cluster-wide Secret access; overbroad bindings can create that exposure. Scoped API grants and tested network allows reduce reachable targets, but the service's own data and permitted dependencies remain exposed. These controls do not prove complete containment or record every network action in Kubernetes audit logs.

## Best Practices

1. **Least privilege** — grant only the API permissions each subject needs
2. **Default-deny NetworkPolicy** — where the network implementation enforces policy, isolate ingress and egress first, then allow required paths explicitly
3. **Namespace scope** — use RoleBinding for a namespaced grant, including reusable ClusterRoles
4. **ServiceAccount per workload** — don't share ServiceAccounts
5. **Audit logging** — use API audit logs to investigate Kubernetes API activity; assess compliance requirements across the full system rather than treating logs as sufficient evidence
6. **Test NetworkPolicy after applying in staging** — verify required traffic succeeds and a representative forbidden connection fails

## Summary

RBAC rules and bindings authorize API requests; NetworkPolicy limits IP and transport flows only when a supporting network implementation enforces them. The controls are additive and protect different paths. Use scoped workload identities, explicit network policy, and tests that verify both allowed and denied behavior.

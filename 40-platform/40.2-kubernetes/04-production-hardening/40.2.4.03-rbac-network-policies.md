# RBAC & Network Policies

An API Pod can have permission to read a Secret and a network path to a database for separate reasons. Removing its API grant does not close the network path; a NetworkPolicy does not revoke credentials already mounted in the Pod. Secure the two paths independently.

## Definition

**Role-Based Access Control (RBAC)** authorizes requests to the Kubernetes API through rules and bindings. A **NetworkPolicy** declares permitted Pod ingress and egress; an installed network implementation must enforce those rules.

> **Textbook Definition:** Role-Based Access Control (RBAC) authorizes Kubernetes API operations through role bindings. NetworkPolicy declares permitted Pod network traffic, whose enforcement depends on a supporting network implementation.

## First Principles

A workload has two different ways to affect its surroundings: it can call the Kubernetes API to read or change objects, and it can connect to other processes over the network. Preventing one does not prevent the other — a Pod allowed to contact the API server still needs authorization to read a Secret, and a Pod denied Secret reads may still reach the database with credentials it already holds.

RBAC grants an API operation when a rule matches; when no rule matches, the RBAC authorizer returns no opinion rather than a negative deny, and the API server's authorizer chain decides — a conclusive allow or deny wins, and if every authorizer has no opinion, the request is denied.

RBAC grants are additive, so a narrower role never cancels a broader grant already bound to the subject. NetworkPolicy rules are likewise additive: a narrower policy cannot subtract a path another matching policy allows.

## 1. Authorize API Operations with Roles and Bindings

Authentication first establishes a subject such as a user, group, or ServiceAccount. Authorization then checks the operation: API group, resource/subresource, verb, and namespace where applicable. A **Role** stores permissions in one namespace. A **RoleBinding** grants a Role, or a reusable ClusterRole, within its namespace. A **ClusterRoleBinding** grants its ClusterRole across the cluster, including namespaced resources wherever that rule applies.

These objects are complementary: a Role without a binding grants nobody access; a binding without a matching rule does not allow the operation. `pods` and `pods/log` are distinct resources — reading Pod metadata does not automatically permit reading its logs or starting a shell through `pods/exec`.

Secret access is powerful because stored credentials may unlock other systems or identities. Its actual reach depends on which Secrets and permissions exist; it is not universally equivalent to cluster-admin. Pod creation in a namespace can also expose credentials through mounted Secrets or ServiceAccount selection, so restricting direct Secret reads alone is incomplete.

A **ServiceAccount** is a namespaced workload identity. Since Kubernetes v1.22, a Pod normally receives a short-lived projected token that the kubelet rotates. Kubernetes v1.24 stopped automatically creating a long-lived token Secret for each ServiceAccount; that change became stable in v1.27. An administrator can still create a legacy token Secret manually, but the Kubernetes project recommends short-lived tokens. Set `automountServiceAccountToken: false` when a workload does not call the API, and check for explicit token projections as well.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: default
  name: read-pods
subjects:
- kind: User
  name: alice@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

The binding assumes authentication already identifies the user as `alice@example.com`. It grants get/list/watch on Pods and `get` on their log subresource in `default` — not Secret reads or access in another namespace. Check it with `kubectl auth can-i get pods -n default --as=alice@example.com` from an administrator allowed to impersonate that user; without impersonation rights the command cannot establish the result.

## 2. Isolate Pod Traffic with Additive NetworkPolicy

A NetworkPolicy selects destination Pods for ingress and source Pods for egress. By default, Pods are not isolated for either direction; a selected Pod becomes isolated separately for each direction included in a matching policy's effective `policyTypes` (which the API can default from the policy spec). Once isolated, only that direction's permitted connections remain allowed under the supported model. All matching policies contribute a union of allows. A source-to-destination connection needs both the source's egress permission and the destination's ingress permission when those directions are isolated. Replies on an allowed connection are implicitly permitted.

A **Container Network Interface (CNI)** plugin supplies Pod networking; policy enforcement requires a supporting network implementation. The API can accept a policy object even when the data plane does not enforce it — test an allowed connection and a denied new connection in the real cluster; object creation alone proves only configuration acceptance.

A `podSelector` peer matches Pods in the policy's own namespace. A `namespaceSelector` matches namespace labels. Both inside one peer entry mean their conditions must match together; separate peer entries mean either can match. An `ipBlock` expresses address ranges, commonly for external peers; Service address translation can make the observed address implementation-dependent.

Standard NetworkPolicy primarily controls IP/transport traffic, not HTTP routes; vendor layer-seven extensions are separate APIs. Kubernetes API audit logs show API requests, not every packet sent by a Pod.

Policy propagation is not necessarily instant or globally atomic: a network implementation may take time to apply a new policy across nodes. Do not treat a newly created policy as immediate quarantine; use the cluster's incident-isolation controls when time matters, then verify the data plane.

## 3. Deny by Default, Then Allow Explicit Paths

This namespace-wide policy makes both directions isolated for every Pod in the namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

An empty selector deliberately matches all Pods in this NetworkPolicy's namespace. This policy has no allow rules, so it blocks DNS and application egress and can disrupt health, telemetry, or control-plane integrations that rely on Pod network paths. Apply it in a test namespace with the required allow policies, then verify both permitted and denied connections before using the pattern in production.

The next policy assumes appropriately labeled workloads and an enforcing network implementation. It selects API Pods, permits frontend ingress on TCP 3000, and permits database egress on TCP 5432. It intentionally omits DNS to show why an otherwise correct data path can still fail. It does not define the frontend's egress policy or the database's ingress policy; those are separate sides of the connection.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 3000
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

If the API calls its database by a DNS name, it also needs a DNS egress allow. Inspect the cluster's DNS topology and labels first; node-local DNS deployments can need different rules. This additional policy is an example for a cluster whose DNS Pods carry `k8s-app: kube-dns` in `kube-system`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-dns
spec:
  podSelector:
    matchLabels: {app: api}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: kube-system}
          podSelector:
            matchLabels: {k8s-app: kube-dns}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}
```

The two selectors sit in one peer entry, so this permits those labeled Pods **in that namespace** — not every Pod in kube-system or every locally labeled DNS Pod. Its allows combine with the database rule. The database's own ingress policy and the frontend's own egress policy must also permit their halves of the connection. Adding a select-all default-deny policy does not subtract these existing allows; it isolates otherwise unselected Pods.

## 4. Verify Both Boundaries in the Real Cluster

Before rollout, check the effective API permission with `kubectl auth can-i` under the intended identity; the caller must be authorized to impersonate it. Then test a required network connection and a representative forbidden connection from the real workload namespace. Verify after policy propagation, and observe the installed network implementation's flow telemetry if you need evidence about packet paths. A stored Role, RoleBinding, or NetworkPolicy proves configuration was accepted, not that the runtime boundary behaves as intended.

## Summary

RBAC rules and bindings authorize API requests; NetworkPolicy limits IP and transport flows only when a supporting network implementation enforces them. The controls are additive and protect different paths. Use scoped workload identities, explicit network policy, and tests that verify both allowed and denied behavior.

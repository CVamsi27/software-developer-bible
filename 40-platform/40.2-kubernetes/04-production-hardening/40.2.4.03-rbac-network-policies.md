# RBAC & Network Policies

## Definition

**RBAC (Role-Based Access Control)** controls who can access the Kubernetes API and what actions they can perform. **Network Policies** control how pods communicate with each other and external services. Both are fundamental to Kubernetes security.

## First Principles

Cluster security is two allow-by-default systems turned restrictive:

1. **RBAC governs the API**: who (ServiceAccount) may do what (verbs) to which (resources) — default-deny is manual; least-privilege service accounts per workload is the discipline (→ 20.5.1.09's model, cluster-shaped).
2. **NetworkPolicy governs the wire**: by default every Pod reaches every Pod; policies are additive allowlists — "default deny" requires a select-all-deny policy first. The CNI must enforce them (many silently don't) — verify, don't assume.
3. **Both exist because blast radius is the metric**: a compromised Pod with cluster-admin + flat network is a cluster breach; the same Pod with scoped SA + deny-by-default egress is contained.

## Why Do We Need It?

1. **RBAC**: Principle of least privilege, multi-team clusters, audit compliance (SOC2, PCI-DSS)
2. **Network Policies**: Micro-segmentation, zero-trust networking, prevent lateral movement

## How It Works

### RBAC mechanics: the verbs are the API

Every API request is a tuple — **user, verb, resource** — checked against the union of all Roles bound to the subject; there is no deny rule in RBAC, only the absence of allow. The subtleties that separate working RBAC from paper RBAC: `resources: ["pods"]` and `resources: ["pods/log"]` are *different* resources (pod read access does not include logs, and vice versa); subresources (`pods/exec`, `pods/attach`) are what `kubectl exec` actually needs — which is why debuggers hold more power than they appear to; and `verbs: ["*"]` on `secrets` is effectively cluster admin, because Secrets carry every other credential. `Role` is namespaced; `ClusterRole` can be cluster-wide *or* namespaced-resource-affecting depending on its binding — a `ClusterRoleBinding` to a `Role`-shaped ClusterRole grants it everywhere, which is the pattern for reusable platform roles (bind per-namespace with `RoleBinding` to scope it).

ServiceAccounts are the workload identity: a Pod's token is mounted automatically (projected, expiring — the 1.24+ change that killed the eternal tokens), and `automountServiceAccountToken: false` on workloads that don't call the API removes the credential from the pod entirely — the cheapest hardening win in the chapter.

### NetworkPolicy mechanics: additive and connection-oriented

Policies select pods by label; a pod selected by **any** policy becomes isolated for that direction (`policyTypes`) — all traffic not explicitly allowed drops. Two properties produce most misunderstandings: policies are **additive** (union of all matching policies' allows — you cannot subtract with a second policy), and they are **connection-stateful** (a pod that can receive on 5379 can reply on the same connection; you don't open return-path ports). Egress DNS is the classic outage: `egress` rules that forget `kube-system`/DNS (UDP/TCP 53 to the cluster DNS pods, selected by `k8s-app: kube-dns`-style labels) break *name resolution* for every selected pod — the rule looks right and everything fails. `ipBlock` with `except` handles external CIDRs; and Cilium's L7 policies (HTTP paths, Kafka topics) extend the model beyond L3/L4 where the CNI supports it.

Enforcement is the CNI's job: kube-router/Calico/Cilium enforce; a cluster without a policy-capable CNI accepts NetworkPolicy objects **and ignores them silently** — `kubectl apply` succeeding proves nothing, which is why the test (two pods, deny, expect timeout) belongs in cluster bring-up.

## Code Examples

### RBAC: Role & RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "watch", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: default
  name: read-pods
subjects:
- kind: User
  name: alice@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### Network Policy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 3000
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

## Common Mistakes

| Mistake | Fix |
| --------------------------------------- | -------------------------------------------- |
| Using default ServiceAccount | Create dedicated ServiceAccount per workload |
| ClusterRole for namespace-scoped access | Use Role instead |
| No default-deny NetworkPolicy | All pods can talk to all pods |
| NetworkPolicy without CNI support | kube-proxy doesn't enforce NetworkPolicy |
| Overly broad verbs ("*") | Use minimum verbs needed |
| No audit logging | Enable audit logs for compliance |

## Real-World Usage

- **The production baseline in order**: default-deny ingress+egress per namespace → per-workload allowlists (frontend→api:3000, api→db:5432, everything→DNS) → egress to the internet only via the proxy allowlist. Applied as a Kustomize base so every new namespace inherits the deny posture; the audit question "can pod A reach pod B?" becomes a diff instead of a quest.
- **RBAC via the platform layer**: namespace-per-team with a namespace-admin ClusterRole bound to the team's group (OIDC groups via RBAC-through-SSO), workloads running dedicated SAs with verb-scoped Roles, and CI deployers holding only the namespaces they deploy to. `kubectl auth can-i --list --as=system:serviceaccount:ns:sa` is the verification command — reading someone's effective permissions beats reading their bindings.
- **The blast-radius argument in one incident shape**: a compromised dependency in one service, RCE in its pod. Flat network + default SA: attacker reads Secrets cluster-wide, moves laterally, exfiltrates. Scoped SA + default-deny egress: the pod can reach its DB and nothing else; the breach is one service's data, visible in audit logs. Same CVE, different disaster — the chapter's entire point.

## Best Practices

1. **Least privilege** — give minimum RBAC permissions needed
2. **Default-deny NetworkPolicy** — block all traffic, then allow explicitly
3. **Namespace isolation** — use Role (not ClusterRole) for namespace-scoped access
4. **ServiceAccount per workload** — don't share ServiceAccounts
5. **Audit logging** — enable Kubernetes audit logs for SOC2/PCI-DSS
6. **Test NetworkPolicy** — verify with `kubectl exec` before deploying

## Summary

- RBAC controls access to Kubernetes API resources through Roles, ClusterRoles, RoleBindings, and ClusterRoleBindings
- Network Policies define firewall rules at the pod level using label selectors and namespace selectors
- RBAC follows least-privilege principles with verbs (get, list, create, update, delete) on API resources
- Network Policies are enforced by CNI plugins like Calico, Cilium, and Weave Net
- ServiceAccounts should use dedicated RBAC permissions rather than the default namespace token

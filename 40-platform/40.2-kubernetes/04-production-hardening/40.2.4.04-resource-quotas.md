# Resource Quotas

## Definition

**ResourceQuota** sets an aggregate admission budget for a namespace: declared CPU/memory requests and limits, storage requests and supported object counts. Its usage accounting is not a meter of live CPU or memory consumption. **LimitRange** constrains individual Pod, container or persistent-volume-claim allocations and can default container requests/limits. Tenant isolation also requires appropriate access, network and workload security boundaries.

> **Textbook Definition:** ResourceQuota is a namespaced admission policy that rejects resource creation or updates exceeding specified aggregate accounting limits. LimitRange applies allocation bounds, ratios and supported defaults to individual resources within a namespace.

## First Principles

Several teams share finite cluster capacity. Per-container resource requests express schedulable demand, but they do not limit how many containers a team can create. A namespace therefore needs an aggregate admission budget as well as per-container bounds.

Admission and scheduling happen at different stages. A quota can reject a new Pod before it exists. An accepted Pod can still remain unschedulable because no feasible node has room. Conversely, a namespace with plenty of quota cannot consume resources already committed elsewhere; quota is permission to request capacity, not a reservation of physical nodes.

Requests and limits also serve different purposes. CPU requests guide placement and relative CPU allocation; CPU limits cause throttling. Memory limits can trigger out-of-memory termination. The Guaranteed, Burstable, and BestEffort quality-of-service (QoS) classes describe resource configurations; pressure eviction considers additional factors such as priority and usage relative to requests. None proves business-level performance or uptime.

## Why Do We Need It?

Use quotas to stop one namespace admitting more declared demand or objects than its budget allows. For example, a runaway controller can be prevented from creating its thousandth Pod even while its existing Pods use little CPU.

Capacity and billing need separate evidence. A quota of ten requested CPUs does not reserve ten CPUs on nodes, cap cloud spend, or stop already admitted containers from bursting above their requests when their limits permit it. Combine admission budgets with measured workload sizing, runtime limits, placement and cluster capacity. Priority-scoped quotas can protect admission headroom for important work; they do not prove that work can be scheduled or meet its latency objective.

## How It Works

### Resource Quota Flow

```text
ResourceQuota Enforcement:
═══════════════════════════════════════════════════════════════

┌─────────────────────────────────────────────────────────────┐
│ QUOTA ENFORCEMENT FLOW                                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ Before Pod Creation:                                        │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ 1. User creates Pod with requests: CPU=1, Memory=1Gi    │ │
│ │                                                         │ │
│ │ 2. API Server checks ResourceQuota:                     │ │
│ │ ├── Quota: requests.cpu: 10 total                       │ │
│ │ ├── Used: 9.5                                           │ │
│ │ ├── Available: 0.5                                      │ │
│ │ ├── Requested: 1.0 (exceeds available!)                 │ │
│ │ └── REJECTED: "exceeded quota"                          │ │
│ │                                                         │ │
│ └─────────────────────────────────────────────────────────┘ │
│                                                             │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ 3. User adjusts Pod: requests: CPU=500m, Memory=512Mi   │ │
│ │                                                         │ │
│ │ 4. API Server checks ResourceQuota:                     │ │
│ │ ├── Available: 0.5 CPU, 2Gi Memory                      │ │
│ │ ├── Requested: 0.5 CPU, 512Mi Memory                    │ │
│ │ └── ACCEPTED                                            │ │
│ │                                                         │ │
│ └─────────────────────────────────────────────────────────┘ │
│                                                             │
└─────────────────────────────────────────────────────────────┘

```

### Defaults apply before aggregate accounting

LimitRange can supply missing container requests/limits and reject values outside its allowed range. ResourceQuota then checks the resulting object's accounted requests, limits, storage, or count against the namespace budget. LimitRange also supports Pod and persistent-volume-claim constraints; it is not restricted to containers.

For example, a default request of `200m` and default limit of `500m` makes an otherwise unspecified container request 0.2 CPU and declare a 0.5 CPU limit. Ten such containers account for two requested CPUs and five CPUs of declared limits. These totals are configuration commitments, not a live CPU-usage reading.

If a quota requires CPU/memory requests or limits and no valid values are supplied or defaulted, admission can reject the Pod. Omitting LimitRange does **not** let requestless containers silently bypass those quotas. Object-count quotas still count applicable objects, regardless of their resource fields. Quotas for other resource kinds have their own accounting rules.

## Code Examples

Each numbered configuration is an alternative policy example, not a recipe to apply all quotas together. Create the named namespaces first. Multiple matching ResourceQuotas are all enforced; a second quota does not override the first. Use a test namespace to observe admission before adopting a policy in production.


### 1. Basic ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: team-a
spec:
  hard:
    # Compute resources
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"

    # Storage resources
    requests.storage: "100Gi"
    persistentvolumeclaims: "10"

    # Object counts
    pods: "50"
    services: "10"
    configmaps: "20"
    secrets: "20"
    services.loadbalancers: "2"
    services.nodeports: "5"
    replicationcontrollers: "20"
```

### 2. ResourceQuota with Scopes

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: production
spec:
  hard:
    requests.cpu: "20"
    requests.memory: "40Gi"
    limits.cpu: "40"
    limits.memory: "80Gi"
  scopes:
  - NotTerminating # Excludes pods with activeDeadlineSeconds set
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: best-effort-quota
  namespace: production
spec:
  hard:
    pods: "10"
  scopes:
  - BestEffort # Only applies to BestEffort QoS pods
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: non-best-effort-quota
  namespace: production
spec:
  hard:
    pods: "30"
  scopes:
  - NotTerminating # Includes Burstable and Guaranteed QoS
  - NotBestEffort
```

### 3. LimitRange with Defaults

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: container-limits
  namespace: team-a
spec:
  limits:
  - type: Container
    default:
      cpu: "500m"
      memory: "512Mi"
    defaultRequest:
      cpu: "200m"
      memory: "256Mi"
    max:
      cpu: "4"
      memory: "8Gi"
    min:
      cpu: "50m"
      memory: "64Mi"
    maxLimitRequestRatio:
      cpu: "4"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: pvc-limits
  namespace: team-a
spec:
  limits:
  - type: PersistentVolumeClaim
    max:
      storage: "100Gi"
    min:
      storage: "1Gi"
```

The CPU defaults have a limit/request ratio of `500m / 200m = 2.5`, within the configured maximum of four. A ratio limit of four with a `100m` request and `500m` default limit would reject the otherwise defaulted container; defaults must satisfy their own validation rules. The PVC range checks an individual storage request, while the storage quota caps the aggregate.

### 5. Priority Class Quotas

```yaml
# Priority classes for workload differentiation
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000
globalDefault: false
description: "High priority workloads (critical production)"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 100
globalDefault: false
description: "Low priority workloads (batch, non-critical)"
---
# Quota scoped by priority class
apiVersion: v1
kind: ResourceQuota
metadata:
  name: high-priority-quota
  namespace: production
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    pods: "10"
  scopeSelector:
    matchExpressions:
    - operator: In
      scopeName: PriorityClass
      values:
      - high-priority
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: low-priority-quota
  namespace: production
spec:
  hard:
    requests.cpu: "20"
    requests.memory: "40Gi"
    pods: "40"
  scopeSelector:
    matchExpressions:
    - operator: In
      scopeName: PriorityClass
      values:
      - low-priority
```

PriorityClass sets scheduling priority, not a physical resource reservation. The scope selector makes each quota apply only to matching Pods; a namespace-wide quota can additionally constrain both classes together. Declare `priorityClassName` in the Pod template and check all matching budgets.

### 6. Viewing Quota Usage

```bash
# View quotas in a namespace
kubectl get resourcequota -n team-a

# Illustrative populated-cluster output; a fresh namespace has different Used values
# Detailed view
kubectl describe resourcequota team-quota -n team-a
# Name: team-quota
# Namespace: team-a
# Resource Used Hard
# -------- --- ----
# requests.cpu 8.5 10
# requests.memory 15Gi 20Gi
# limits.cpu 16 20
# limits.memory 30Gi 40Gi
# pods 35 50
# services 5 10

# View limit ranges
kubectl get limitrange -n team-a
kubectl describe limitrange container-limits -n team-a

# Check quota usage across all namespaces
kubectl get resourcequota --all-namespaces

# Custom columns
kubectl get quota -n team-a -o custom-columns=\
  NAME:.metadata.name,\
  CPU-REQ:.status.hard.'requests\.cpu',\
  CPU-REQ-USED:.status.used.'requests\.cpu',\
  MEM-REQ:.status.hard.'requests\.memory',\
  MEM-REQ-USED:.status.used.'requests\.memory'
```

### 7. Pod Requesting Resources

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: quota-aware-pod
  namespace: team-a
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "200m"
        memory: "512Mi"
      limits:
        cpu: "500m"
        memory: "1Gi"
  # Without these resource requests:
  # - LimitRange injects defaults
  # - ResourceQuota tracks them
```

The sample Pod requests `200m`/`512Mi` and declares `500m`/`1Gi` limits. With the basic team quota, admission must fit both request totals and limit totals. Passing admission does not establish node placement, successful image startup, or readiness.

### 8. Quota Enforcement Error

```bash
# Attempt to create a pod that exceeds quota
kubectl apply -f big-pod.yaml
# Error:
# Error from server (Forbidden): error when creating "big-pod.yaml":
# pods "big-pod" is forbidden: exceeded quota:
# team-quota, requested: requests.cpu=4,
# used: requests.cpu=9.5, limited: requests.cpu=10
```

## Real-World Use Cases

| Scenario | ResourceQuota | LimitRange |
| -------------------------- | ----------------------------------------------- | -------------------------------------------------------- |
| **Multi-team cluster** | Per-team aggregate request/limit budgets | Bounds and defaults for individual allocations |
| **Production vs staging** | Different admission ceilings based on demand | Different measured default sizes |
| **CI/CD pipelines** | Namespace object and resource budgets for jobs | Container allocation bounds |
| **Free tier vs paid tier** | Tier-specific admission budgets | Minimum permitted requests, not reserved capacity |
| **Batch vs real-time** | Separate admission accounting by priority class | Defaults that influence QoS classification, not priority |

## Common Mistakes

### 1. Missing resource defaults

A CPU-request quota with no compatible defaulting policy can reject a Pod that omits the required request. The failure occurs at API admission, not as a Pending scheduling state. Supply explicit resources or a valid LimitRange; inspect Deployment/ReplicaSet events if a controller's requested replica count is larger than the number of Pods that exist.

### 2. Overly Restrictive Limits

```yaml
# Fits only workloads whose aggregate demand stays within these values
spec:
  hard:
    requests.cpu: "1"
    pods: "2"

# An illustrative larger budget; choose it from measured demand and headroom
spec:
  hard:
    requests.cpu: "10"
    pods: "30"
    requests.memory: "20Gi"
```

### 3. Not Planning for Quota Headroom

```yaml
# BAD: No headroom — rolling update fails
spec:
  hard:
    pods: "3"
# With maxUnavailable=0 and surge creation required, quota blocks progress.
# A rollout that permits reducing old replicas can progress with a different trade-off.

# GOOD: Account for deployment strategy
spec:
  hard:
    pods: "6"
# Can do rolling updates with 3 replicas + surge
```

### 4. Different Quotas for Different Priorities

```yaml
# BAD: Single quota — low-priority can starve high-priority
spec:
  hard:
    requests.cpu: "20"
    # All pods share 20 CPUs regardless of priority

# One scoped budget; add a batch budget if batch must not exhaust shared admission
apiVersion: v1
kind: ResourceQuota
metadata:
  name: high-priority
spec:
  hard:
    requests.cpu: "10"
  scopeSelector:
    matchExpressions:
    - operator: In
      scopeName: PriorityClass
      values: ["high"]
```

## Best Practices

1. **Pair quotas with intentional defaulting or explicit resources** — missing required CPU/memory fields can cause admission rejection

2. **Size defaults from actual workloads** — defaults fill omitted fields; they do not resize existing Pods or prove safe performance

3. **Protect admission headroom where needed** — scoped quotas separate accounting; scheduling priority and node capacity remain separate

4. **Monitor admission headroom and actual saturation** — choose alerts from rollout/scaling needs; quota usage and runtime usage answer different questions

5. **Plan headroom for deployments** — Account for surge during rolling updates

6. **Document quota decisions** — Why each namespace gets its specific limits

7. **Use namespace budgets deliberately** — multiple quotas may apply; access and network isolation remain separate

8. **Review and adjust regularly** — Quotas need tuning as workloads evolve

## Summary

- ResourceQuota checks namespace admission against aggregate allocations and object counts, independently of available node capacity
- LimitRange sets supported defaults and per-object allocation constraints, including Pod, container and persistent-volume-claim bounds
- Required CPU/memory values must be explicit or defaulted; absence can cause admission rejection
- Use priority classes to differentiate critical vs best-effort workloads within the same namespace
- Monitor utilization and plan for headroom, especially for rolling updates

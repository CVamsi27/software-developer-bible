# Resource Quotas

A Deployment asks for four replicas, but only three Pod objects exist. The fourth may have been rejected at API admission because its namespace reached a quota; the node autoscaler cannot help because there is no Pending Pod to schedule. ResourceQuota and LimitRange govern namespace admission and individual allocations, while the scheduler and node autoscaler govern physical placement.

## Definition

A **ResourceQuota** sets an aggregate admission budget for a namespace, such as requested CPU and memory, storage, or supported object counts. A **LimitRange** sets bounds and defaults for individual containers, Pods, or persistent-volume claims.

> **Textbook Definition:** ResourceQuota is a namespaced admission policy that rejects resource creation or updates exceeding specified aggregate accounting limits. LimitRange applies per-object bounds, ratios and supported defaults within a namespace.

Neither object isolates tenants or reserves physical capacity. Use access control, network policy, workload security, and cluster capacity planning for those separate boundaries.

## First Principles

A quota accounts for declared resources, not live CPU or memory usage. CPU and memory **requests** inform placement; **limits** configure runtime enforcement. CPU limits can throttle, and memory limits can lead to out-of-memory termination. Quality-of-Service (QoS) classes describe Pod resource configurations; they do not guarantee business performance.

Admission happens before scheduling. A quota can reject Pod creation before an object exists; an admitted Pod can still remain Pending when no feasible node has room. A namespace quota grants permission to request resources — not a reservation of cluster nodes or a cap on cloud spending.

When a quota requires CPU or memory requests or limits, each container must provide those fields or receive valid defaults. A LimitRange can default and bound individual containers; ResourceQuota then checks aggregate usage. Multiple matching quotas all apply, so a new quota does not override an existing one.

## 1. Cap the Namespace Aggregate with ResourceQuota

This quota limits requested resources, declared limits, storage, and selected object counts. All quantities are example budgets; size them from measured workloads and required rollout headroom.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-budget
  namespace: team-a
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"
    requests.storage: "100Gi"
    persistentvolumeclaims: "10"
    pods: "50"
    services: "10"
    configmaps: "20"
    secrets: "20"
```

Quotas can also scope accounting by Pod properties such as QoS class, termination status, or PriorityClass. A priority-scoped quota separates admission budgets, but scheduling priority is not a resource reservation: nodes still need feasible capacity. Use a namespace-wide quota as a total ceiling when several scoped quotas must not collectively exceed the team's full budget.

## 2. Bound and Default Each Container with LimitRange

A LimitRange applies defaults and bounds to each container in the namespace. Its defaults must satisfy their own minimum, maximum, and limit-to-request ratio constraints.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: container-bounds
  namespace: team-a
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 200m
        memory: 256Mi
      default:
        cpu: 500m
        memory: 512Mi
      min:
        cpu: 50m
        memory: 64Mi
      max:
        cpu: "4"
        memory: 8Gi
      maxLimitRequestRatio:
        cpu: "4"
```

Here, each container without explicit values receives a request of `200m` CPU and `256Mi` memory, plus limits of `500m` and `512Mi`. Ten such containers account for two requested CPUs and five CPUs of declared limits. That is quota accounting, not a live usage measurement. The LimitRange constrains one container; the ResourceQuota caps the namespace aggregate.

## 3. Diagnose Rejection Before Capacity

Inspect the namespace policies and their current `Used` and `Hard` values:

```bash
kubectl get resourcequota,limitrange -n team-a
kubectl describe resourcequota team-budget -n team-a
kubectl describe limitrange container-bounds -n team-a
kubectl get events -n team-a --sort-by=.lastTimestamp
```

An API response such as `exceeded quota` means admission rejected the object. If a Deployment requests more replicas than there are Pods, inspect controller events; quota may prevent creation. If a Pod object exists and has `FailedScheduling`, inspect node allocatable resources, requests, affinity, taints, and storage topology. These are different failure stages with different remedies.

A successful quota check proves only that the request fits the namespace budget. It does not prove a node can run it, the image can start, the workload is ready, or a rolling update has enough surge capacity. If a Deployment uses `maxUnavailable: 0`, account for surge Pods and terminating Pods in the namespace budget — otherwise admission can block progress while the old version is correctly kept alive.

ResourceQuota can count supported objects such as Pods, Services, ConfigMaps, Secrets, and PVCs. It can also limit requested storage and supported extended resources. Inspect the resource names supported by the cluster API and the quota documentation rather than assuming every object or provider bill is included.

## Summary

ResourceQuota limits aggregate namespace admission; LimitRange defaults or bounds individual allocations. Neither reserves node capacity, measures live consumption, or creates tenant isolation. Follow the request from admission through scheduling to readiness, and budget for controller-created surge and termination overlap when defining limits.

# Kubernetes Helm

A team deploys the same API to development and production, but needs different replica counts, resources, and hostnames. Copying two full manifests invites drift; a chart turns supported differences into values while keeping the workload structure shared.

## Definition

**Helm** packages Kubernetes resources into reusable **charts** and manages named **releases** by rendering and submitting their manifests. The examples use Helm 4 syntax: prefer `--rollback-on-failure`, since `--atomic` remains only as a deprecated alias. A rollback restores Kubernetes configuration where possible; it does not reverse data changes or external side effects.

> **Textbook Definition:** Helm packages Kubernetes resources as configurable charts and manages named releases by rendering and applying manifests, with recorded revision metadata supporting upgrade and rollback operations.

Key concepts:

- A **Chart** is a package of Kubernetes resources.
- A **Release** is a named installation record containing a chart revision, configuration, and status (Helm records it but does not continuously reconcile live resources).
- **Values** are configuration parameters for a chart.
- Charts ship through a traditional HTTP chart repository or an OCI registry — choose a trusted source and pin the chart version.
- **Templates** use the Go templating engine for dynamic manifest generation.

## First Principles

Helm is templating plus packaging over YAML that the API server can't parameterize: Kubernetes manifests are static while deployments need variation (environment, region, size), so Helm templates parameterize — values per environment, chart as the unit of reuse. The price is that YAML-in-templates has its own language and debugging surface. A release record is not a transaction: `helm install/upgrade/rollback` tracks manifest revisions and status with a configurable storage driver, resources update separately, hooks can have side effects, and reverting manifests never reverses data migrations or external operations. Charts are dependencies too — subcharts and the umbrella pattern mirror package management, with the same version-pin discipline.

## 1. Render Values into Manifests, Record the Release

```text
Chart + ordered values files → Helm renders manifests → API server applies resources
                                     ↓
                              Release revision/history
```

The chart is input, not a running service. Helm combines defaults with ordered values files and command-line overrides, evaluates templates, and submits the resulting objects. Kubernetes admission and workload controllers then own resource validity, scheduling, and readiness. The configured release-storage driver records the manifest revision and status; Helm does not continuously reconcile drift between commands or guarantee application health. Later values files override earlier matching values, so inspect the final render rather than only one environment file. In Helm 4, new releases use server-side apply by default; upgrades and rollbacks follow the release's previous apply method unless overridden. Server-side field ownership can conflict with another manager, so test upgrades where operators or GitOps tools also write these resources.

## 2. Organize the Chart's Files

```text
mychart/
+-- Chart.yaml # Chart metadata
+-- Chart.lock # Dependency lock file
+-- values.yaml # Default configuration values
+-- values.schema.json # JSON Schema for values
+-- templates/ # Kubernetes manifest templates

| +-- deployment.yaml
| +-- service.yaml
| +-- ingress.yaml
| +-- hpa.yaml
| +-- _helpers.tpl # Template helpers
| +-- NOTES.txt # Post-install notes
+-- charts/ # Sub-charts (dependencies)
+-- crds/ # Custom Resource Definitions

```

## 3. Render, Validate, and Release Deliberately

```bash
helm lint ./mychart
helm template myrelease ./mychart -f values-prod.yaml
helm upgrade --install myrelease ./mychart \\
  --namespace production --create-namespace \\
  -f values-prod.yaml --set image.tag=2.0.0 \\
  --wait --timeout 5m --rollback-on-failure
helm history myrelease -n production
helm rollback myrelease 1 -n production
```

Local rendering shows generated YAML but does not exercise API admission. A server-side dry run uses the cluster's validation and admission path; keep Secrets out of captured output. `--wait` observes supported Kubernetes readiness conditions, not business operations. Helm 4 uses server-side apply for a new release by default; it latches the prior apply mode when upgrading or rolling back an existing release. Test field ownership and chart behavior against the exact Helm and Kubernetes versions used by the pipeline.

`--rollback-on-failure` attempts to restore the previous release configuration; the older `--atomic` spelling is deprecated in Helm 4. Rollback cannot reverse a database migration, a hook's external effect, or an already processed message. Review the rendered diff and make data changes backward-compatible before applying the chart.

Charts in `crds/` install as plain, non-templated resources. Helm does not upgrade or delete them as part of normal release operations, and a dry run cannot fully validate custom resources whose CRDs are not installed. Manage CRD schema, conversion, and storage-version migrations as a separate lifecycle. A dependency should be pinned and reviewed like application code; a release record does not guarantee the upstream chart is maintained or safe.

## Code Examples

### Basic Chart

```yaml
# Chart.yaml
apiVersion: v2
name: myapp
description: Example API chart
type: application
version: 1.0.0
appVersion: "1.0.0"
```

`version` identifies the chart package; `appVersion` is descriptive metadata and does not select the image. The `edge` IngressClass, certificate issuer, TLS Secret, and resource metrics API used below are separate cluster prerequisites.

### Values File

```yaml
# values.yaml
replicaCount: 3
image:
  repository: registry.example.com/myapp
  tag: "1.0.0"
  pullPolicy: IfNotPresent
service:
  type: ClusterIP
  port: 80
  targetPort: 8080
ingress:
  enabled: true
  className: edge
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
  hosts:
    - host: myapp.example.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: myapp-tls
      hosts: [myapp.example.com]
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi
autoscaling:
  enabled: true
  minReplicas: 3
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70
```

The `image` must implement the configured probe paths and listen on the target port. CPU requests are required for the HPA utilization target. Values expose the supported variations; they do not create cluster prerequisites such as an Ingress controller or metrics adapter.

### Deployment Template

```yaml
# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "mychart.fullname" . }}
  labels:
    {{- include "mychart.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  selector:
    matchLabels:
      {{- include "mychart.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "mychart.selectorLabels" . | nindent 8 }}
    spec:
      containers:

        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:

            - name: http
              containerPort: {{ .Values.service.targetPort }}
              protocol: TCP
          livenessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 15
          readinessProbe:
            httpGet:
              path: /ready
              port: http
            periodSeconds: 10
          resources:
            {{- toYaml .Values.resources | nindent 12 }}

```

The helper names below resolve release-specific object names and selectors. The selector helper deliberately excludes image/chart version so a version update does not mutate the Deployment's immutable selector. `nindent` formats inserted maps at the YAML depth; Go-template correctness and YAML validity are separate checks. Probe paths require implementation in the image; use `/alive` for a local liveness contract when `/health` represents startup.

### Service Template

```yaml
# templates/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ include "mychart.fullname" . }}
  labels:
    {{- include "mychart.labels" . | nindent 4 }}
spec:
  type: {{ .Values.service.type }}
  ports:

    - port: {{ .Values.service.port }}
      targetPort: {{ .Values.service.targetPort }}
      protocol: TCP
      name: http
  selector:
    {{- include "mychart.selectorLabels" . | nindent 4 }}

```

### Optional HPA Template

The Deployment omits `spec.replicas` when autoscaling is enabled. This matching template creates the controller that then owns the scale field:

```yaml
# templates/hpa.yaml
{{- if .Values.autoscaling.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ include "mychart.fullname" . }}
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ include "mychart.fullname" . }}
  minReplicas: {{ .Values.autoscaling.minReplicas }}
  maxReplicas: {{ .Values.autoscaling.maxReplicas }}
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.autoscaling.targetCPUUtilizationPercentage }}
{{- end }}
```

### Ingress Template

```yaml
# templates/ingress.yaml
{{- if .Values.ingress.enabled -}}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ include "mychart.fullname" . }}
  labels:
    {{- include "mychart.labels" . | nindent 4 }}
  {{- with .Values.ingress.annotations }}
  annotations:
    {{- toYaml . | nindent 4 }}
  {{- end }}
spec:
  ingressClassName: {{ .Values.ingress.className }}
  {{- if .Values.ingress.tls }}
  tls:
    {{- range .Values.ingress.tls }}

    - hosts:
        {{- range .hosts }}

        - {{ . | quote }}
        {{- end }}
      secretName: {{ .secretName }}
    {{- end }}
  {{- end }}
  rules:
    {{- range .Values.ingress.hosts }}

    - host: {{ .host | quote }}
      http:
        paths:
          {{- range .paths }}

          - path: {{ .path }}
            pathType: {{ .pathType }}
            backend:
              service:
                name: {{ include "mychart.fullname" $ }}
                port:
                  number: {{ $.Values.service.port }}
          {{- end }}
    {{- end }}
{{- end }}

```

`range` changes the template's current context to each host/path entry. `$` retains the root context, which is why the nested backend reads `$.Values.service.port` and passes `$` to the fullname helper. Otherwise a lookup tries to find chart-level values on one path item. The rendered backend uses the Service port, not the container targetPort.

### Helper Templates

```yaml
# templates/_helpers.tpl
{{- define "mychart.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}

{{- define "mychart.fullname" -}}
{{- if .Values.fullnameOverride }}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- $name := default .Chart.Name .Values.nameOverride }}
{{- if contains $name .Release.Name }}
{{- .Release.Name | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" }}
{{- end }}
{{- end }}
{{- end }}

{{- define "mychart.chart" -}}
{{- printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" | trunc 63 | trimSuffix "-" }}
{{- end }}

{{- define "mychart.labels" -}}
helm.sh/chart: {{ include "mychart.chart" . }}
{{ include "mychart.selectorLabels" . }}
app.kubernetes.io/version: {{ .Values.image.tag | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}

{{- define "mychart.selectorLabels" -}}
app.kubernetes.io/name: {{ include "mychart.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}

```

### Helm Commands

```bash
# Install chart
helm install myrelease ./mychart -f values-prod.yaml

# Upgrade release; attempt to restore the previous successful revision on failure
helm upgrade myrelease ./mychart -f values-prod.yaml --rollback-on-failure

# Rollback release
helm rollback myrelease 1

# List releases
helm list -A

# Uninstall release
helm uninstall myrelease

# Add a trusted HTTP chart repository (replace the reserved example URL)
helm repo add example https://charts.example.com/

# Update repositories
helm repo update

# Search a configured HTTP chart repository
helm search repo example/nginx

# Show chart info
helm show chart ./mychart
helm show values ./mychart

# Pull a versioned chart from an OCI registry (replace the example coordinate)
helm pull oci://registry.example.com/charts/mychart --version 1.2.3

```

`helm rollback myrelease 1` requires revision 1 to remain available. Hooks, persistent data, and external operations need their own recovery plans. CRDs in `crds/` are installed as plain, non-templated resources; Helm does not upgrade or delete them. Install-time dry runs also cannot fully validate custom resources whose CRDs are not installed. Manage schema and storage-version migrations deliberately, and review conversion, existing custom resources, and controller compatibility before changing them.

### Environment-Specific Values

Each environment file is a separate YAML document. Production enables the HPA template; development keeps a fixed replica count.

```yaml
# values-dev.yaml
replicaCount: 1
autoscaling:
  enabled: false
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 250m
    memory: 256Mi
```

```yaml
# values-prod.yaml
replicaCount: 3
autoscaling:
  enabled: true
  minReplicas: 3
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: "1"
    memory: 1Gi
```

## Summary

A Helm chart turns supported configuration into rendered Kubernetes objects; a release records the submitted revision. Helm 4 defaults new releases to server-side apply, but apply ownership and rollback still have operational boundaries. Use a chart when shared packaging and release history justify its template surface; use plain manifests or Kustomize when those abstractions add no value.

# Kustomize Overlays & Packaging Trade-offs

## Definition

**Kustomize** is a template-free customization engine built into `kubectl apply -k`. A **kustomization.yaml** declares:

- **resources** — the manifests being customized (the *base*)
- **patches** — surgical modifications (strategic merge or JSON6902)
- **generators** — create ConfigMaps/Secrets from files/literals (`configMapGenerator`)
- **transformers** — cross-cutting rewrites (namespace prefixing, label injection, image tag overrides, name suffixes)
- **components** — reusable partial kustomizations composed into overlays

```text
repo/
├── base/                        # the app, environment-neutral
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   ├── service.yaml
│   └── hpa.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml   # resources: ../../base
    │   ├── replica-count.yaml   # strategic merge patch
    │   └── image-tag.yaml
    └── prod/
        ├── kustomization.yaml
        ├── patches/
        │   ├── replicas.yaml
        │   └── resources.json       # JSON6902 patch
        └── secrets/                 # SOPS-encrypted, never plain!
```

## First Principles

Copied manifests drift because each copy becomes another place to maintain shared policy. A base keeps shared resource declarations together; an overlay expresses a deployment's differences. The final object still has to satisfy Kubernetes field and selector rules, regardless of how readable the patch looks.

## Follow a Configuration Change to a Pod Rollout

A Deployment refers to `api-config`. Kustomize generates that ConfigMap with a content hash in its name and rewrites the Deployment reference. Changing the generator input therefore changes the Pod template; applying that rendered Deployment starts a rollout. The generator does not restart Pods itself.

```text
base resources + overlay patches + generator inputs
                         ↓ build with pinned tool versions
                 final Kubernetes manifests
                         ↓ diff / review / apply
              API validation and workload reconciliation
```

**Resources** are the starting objects. **Patches** change selected fields. **Generators** construct objects from inputs. **Transformers** apply shared name, namespace, label or image changes. **Components** bundle optional shared changes. Learn those roles before choosing a particular patch syntax.

## Why Do We Need It?

| Problem | Solution |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Copy-pasted YAML per env drifts silently | One base; env deltas live only in overlays |
| Need to inspect final composed objects | `kubectl kustomize` renders the result; validate the output against the target APIs |
| Third-party charts need org-wide tweaks (labels, proxy env) | Post-render with Kustomize instead of forking the chart |
| Image tags updated by CI in N files | `images:` transformer — one line per env |
| Config change must restart pods reliably | Generated ConfigMap name hash changes → Deployment ref changes → rollout |
| Reviewing PRs that touch 40 templated lines | Patches show ONLY the delta — small, reviewable diffs |

## How It Works

### Strategic Merge vs JSON6902

Strategic merge patches understand Kubernetes field semantics (lists merge by key where supported):

```yaml
# overlays/dev/replica-count.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 1                    # overrides base value
  template:
    spec:
      containers:
        - name: api              # merge key: name
          resources:
            requests: { cpu: 100m, memory: 128Mi }
```

JSON6902 applies explicit JSON Patch operations. Existing paths and list indices matter: adding to `/tolerations/-` requires the parent list to exist in the base. For a missing list, first add `/tolerations` with the full desired array. Strategic merge needs schema merge semantics; do not assume arbitrary CRD lists merge like built-in container lists:

```yaml
# overlays/prod/patches/resources.json
[
  {"op": "replace", "path": "/spec/replicas", "value": 12},
  {"op": "add",
   "path": "/spec/template/spec/tolerations/-",
   "value": {"key": "dedicated", "operator": "Exists", "effect": "NoSchedule"}}
]
```

Wiring both into an overlay:

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payments-prod
resources:
  - ../../base
patches:
  - path: patches/replicas.yaml        # strategic merge
    target:
      kind: Deployment
      name: api
  - path: patches/resources.json       # JSON6902
    target:
      kind: Deployment
      name: api
labels:
  - pairs:
      env: prod
    includeSelectors: false
```

### Generators Drive Rollouts

```yaml
# base/kustomization.yaml
configMapGenerator:
  - name: api-config
    files:
      - app.properties
    literals:
      - LOG_LEVEL=info
```

Generated names get a content hash suffix: `api-config-6f9h27m5t8`. The Deployment's `envFrom` reference is rewritten to match. A content change normally changes the hash and rewritten Pod-template reference; applying that changed Deployment triggers a rollout. This requires hash suffixes to remain enabled and references to be recognized by Kustomize. Editing a manually named ConfigMap does not change the Pod template: mounted data may update, but environment values require restart and application reload behavior must be designed.

### Transformers — Cross-Cutting Rewrites

| Transformer | Effect | Typical use |
| ------------------------------- | ---------------------------------------------------------------- | -------------------------------- |
| `namespace:` | Sets namespace on namespaced resources and recognized references | Env isolation |
| `namePrefix:` / `nameSuffix:` | Renames objects + rewrites recognized references | Multi-instance installs |
| `labels:` | Adds labels; selector/template propagation is explicit | Org tagging policy |
| `images:` | Rewrites name/tag/digest | CI-driven releases |
| `replacements:` | Copies selected source fields to selected targets | Wire service DNS into client env |
| `replicas:` (transf.) | Sets replica count per resource | Simple scale overrides |

```yaml
images:
  - name: myregistry/api
    newTag: sha256-9f86d081884c   # CI rewrites this one line
```

### Make Rendering Reproducible

Pin the Kustomize/Helm versions, chart versions and remote inputs. Identical local inputs with a fixed toolchain should render repeatably; mutable remote bases, chart repositories and plugins can break that assumption. `kubectl kustomize` renders; `kubectl apply -k` also mutates the cluster. GitOps reconciles the rendered desired objects, while admission mutation, runtime status, secrets and controller state still affect the running system.

## Code Examples

### Complete Base

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
configMapGenerator:
  - name: api-config
    literals:
      - PORT=3000
labels:
  - pairs:
      app.kubernetes.io/part-of: payments
    includeSelectors: false
```

### Overlay With Component Reuse

```yaml
# components/mtls-sidecar/kustomization.yaml   (a component)
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
patches:
  - path: sidecar.yaml
    target: { kind: Deployment, name: ".*" }
---
# overlays/prod/kustomization.yaml
components:
  - ../../components/mtls-sidecar
```

Components are composable feature flags for manifests — enable mesh injection, PDBs, or monitoring per overlay without duplicating patches.

### Render a Chart, Then Patch Its Output

Use a maintained chart whose API and deployment policy you have reviewed. The community ingress-nginx chart is a historical artifact: its controller retired in March 2026, so it is no longer a new-installation recommendation.

This local-file example keeps the two stages explicit. It assumes a reviewed chart at `../../charts/api`, a values file, and a patch that targets the actual rendered Deployment name:

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - chart-rendered.yaml
patches:
  - path: patch-api-resources.yaml
    target:
      kind: Deployment
      name: api
```

```bash
helm template api ../../charts/api -f values-prod.yaml > chart-rendered.yaml
kubectl kustomize . > rendered.yaml
kubectl diff -f rendered.yaml
# After reviewing the diff:
kubectl apply -f rendered.yaml
```

Kustomize reads declared resources from the directory; piping Helm's YAML into `kustomize build .` does not make it an input resource. Also, `kubectl diff` exits 1 when it finds differences, so chaining apply with `&&` would skip precisely the changed deployment.

The alternative `helmCharts:` generator invokes Helm and requires `--enable-helm` in the renderer. In Argo CD, configure `kustomize.buildOptions` globally or use an approved config-management plugin; there is no per-Application native `--enable-helm` toggle. Rendered charts can contain Secrets, so protect generated output and avoid checking sensitive generated files into Git.

### Secrets Handling Caveat

`secretGenerator` only base64-encodes — it provides zero confidentiality, and committing generated plaintext Secrets is a leak waiting to happen:

```yaml
secretGenerator:
  - name: db-password
    literals:
      - password=hunter2     # NEVER commit the source of this in plaintext
    type: Opaque
```

Choose a pattern for the threat model and operational ownership; there is no universal ranking:

```text
1. External Secrets Operator / vault-injected Secret resources
   → cluster pulls from Vault/ASM at runtime; git holds only references.
2. SealedSecrets (Bitnami) → commit ciphertext only; controller holds key.
3. SOPS + age/KMS → an explicitly installed/configured plugin such as
   KSOPS decrypts inputs; control its execution and key access.
4. CI-only: generate at deploy time from pipeline secrets,
   apply out-of-band from the kustomize build.
```

### Verifying What Will Apply

```bash
kustomize build overlays/prod | less          # read the truth
kustomize build overlays/prod | kubeconform -strict -
diff <(kustomize build overlays/dev) <(kustomize build overlays/staging)  # env delta review
kustomize edit set image myregistry/api=myregistry/api@sha256:abc123
```

## Real-World Use Cases

### 1. Three-Environment GitOps Repo

ArgoCD watches `overlays/{dev,staging,prod}`. PRs to prod overlay require CODEOWNERS approval; the rendered diff in the PR shows exactly which fields change between staging and prod. Enable the GitOps controller's self-heal/prune policies deliberately; merely watching the repository does not imply those behaviors.

### 2. Adopting Upstream Charts Without Forking

Platform team installs cert-manager via `helmCharts`, then adds a Kustomize patch pinning resource requests and injecting a corporate proxy env block. Upstream upgrades become version bumps, not merge conflicts across a vendored fork.

### 3. Multi-Tenant Namespaced Install

One base app installed per tenant: overlay sets `namespace: tenant-a`, `namePrefix: t-a-`; replacements wire the prefixed Service DNS name into client ConfigMaps. This separates object names and namespaces; actual tenant isolation also requires network, access, quota and workload security policy.

### 4. CI Release Promotion

Merge to main runs `kustomize edit set image ...@sha256:<digest>` on `overlays/staging`, commits, Argo syncs; promotion to prod updates its overlay to the same image digest after canary sign-off — auditable, revertible, digest-pinned.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Committing plaintext values feeding `secretGenerator` | Use ESO/SealedSecrets/SOPS; git must hold ciphertext or references only |
| Editing generated ConfigMaps directly | Edit generator inputs; hashes keep rollouts correct |
| Strategic-merge patch on a list expecting element merge | Lists merge by key only where API semantics allow; else use JSON6902 |
| Deep overlay-on-overlay hierarchies nobody can trace | Keep the dependency graph traceable; extract shared changes into components when they clarify ownership |
| Duplicating whole resources into overlays "just to tweak" | Patch shared resources; an overlay can also deliberately introduce environment-specific resources |
| Forgetting `--enable-helm` (or v5 flag) for helmCharts builds | Configure the build invocation and Argo CD global build options or an approved plugin |
| Assuming `commonLabels` rewrites selectors safely | Legacy `commonLabels` mutates selectors; prefer `labels:` with `includeSelectors` chosen deliberately |

## Best Practices

1. **Base stays boring and complete** — make shared resources understandable; document any inputs an overlay must supply and any resources it adds.
2. **Review rendered output in CI** — fail the build if `kustomize build` errors, schema-invalidates (kubeconform), or produces unexpected namespace/image drift.
3. **Digest-pin images in prod overlays**, tags elsewhere — the images transformer makes this one-line cheap.
4. **Prefer components over copy-paste for shared features** (mesh, monitoring, PDBs).
5. **Decide Helm-vs-Kustomize per artifact**: third-party chart → consume as chart; first-party manifests → Kustomize; complex conditional logic → Helm authoring may still win.
6. **Protect decrypted secrets during rendering** — plaintext must exist at some trusted boundary to apply a Secret. Restrict access, logs, temporary files and generated output; prefer references when possible.

## Performance Considerations

| Aspect | Impact | Mitigation |
| ------------------------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Build cost depends on resource count, transforms and plugins | Large monorepo bases slow CI seconds-minutes | Split bases per service; avoid global replacements |
| Hash-suffix ConfigMaps churn etcd objects | Many regenerations accumulate old maps | Configure GitOps pruning or scoped cleanup; ordinary generated ConfigMaps have no automatic owner-based garbage collection guarantee |
| helmCharts builds invoke Helm each render | Adds ~seconds | Cache chart downloads; pin versions |
| Massive single base shared by many overlays | Any base change re-renders every overlay | Stabilize base contracts; version bases like libraries |

## Summary

Kustomize composes starting resources with explicit changes. Inspect the rendered result to verify selectors, references, namespaces and API validity. Generated-name changes can drive rollouts through Pod-template changes; Helm can supply upstream manifests before local patches. Reproducibility, pruning and secret handling depend on the configured toolchain and deployment controller.

# Kustomize Overlays & Packaging Trade-offs

Development and production usually share an application's resources but differ in image digest, replicas, and capacity limits. Copying complete manifests makes those common fields drift. Kustomize keeps one base and describes each environment as a small set of patches and generators.

## Definition

**Kustomize** composes and customizes Kubernetes resources without embedding template expressions in the resource files. `kubectl kustomize` renders a directory; `kubectl apply -k` builds and applies it.

> **Textbook Definition:** Kustomize derives customized Kubernetes resource configurations from reusable manifests through patches, generators and transformations, composing environment-specific overlays without template expressions in resource files.

## First Principles

The API server receives complete objects, not an instruction such as "use three replicas in production." Keep a canonical set of resources, apply the environment's explicit changes during a reproducible build, and inspect the rendered objects before submission. A `kustomization.yaml` names the source resources; patches change selected fields, generators create ConfigMaps or Secrets from declared inputs, transformers rewrite supported names, labels, namespaces, or image references, and components package optional reusable changes.

Suppose a Deployment reads `api-config` from an environment variable. A `configMapGenerator` builds a name that includes a content hash, and Kustomize rewrites the Deployment reference to that generated name. When the input changes, the name and Pod template change. Applying the rendered Deployment starts a rollout; the generator itself does not restart Pods.

```text
base resources + overlay patches + generator inputs
                       ↓ build with pinned tool versions
               rendered Kubernetes objects
                       ↓ review / validate / apply
              admission and workload controllers
```

A manually named ConfigMap has no generated hash. Mounted files may update according to Kubernetes' delivery behavior, but environment variables do not change in an already running process. Use a generated name when a configuration change should deliberately alter the Pod template, and keep pruning/retention behavior explicit so obsolete generated objects do not accumulate indefinitely.

## 1. Patch Only the Fields That Differ

A strategic-merge patch identifies a resource by kind/name and merges supported fields according to Kubernetes schema semantics. Built-in container lists merge by their `name` key, but do not assume arbitrary lists or custom-resource fields have the same merge behavior.

```yaml
# overlays/dev/replicas.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 1
  template:
    spec:
      containers:
        - name: api
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
```

JSON Patch (RFC 6902), often serialized as YAML in a patch file, applies explicit operations to exact paths. Paths must exist for `replace`; appending to `/tolerations/-` requires the `tolerations` array to exist first. Use this when a precise operation is clearer or when strategic-merge schema behavior is unsuitable.

```yaml
# overlays/prod/patches/replicas-patch.yaml
- op: replace
  path: /spec/replicas
  value: 5
```

A production overlay can apply the patches to a base:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payments-prod
resources:
  - ../../base
patches:
  - path: patches/replicas-patch.yaml
    target:
      group: apps
      version: v1
      kind: Deployment
      name: api
labels:
  - pairs:
      environment: production
    includeSelectors: false
```

The `labels` transformer makes the label addition explicit. Legacy `commonLabels` can also rewrite selectors; choose selector propagation deliberately, because changing a workload selector can violate its immutability or alter which Pods it owns.

## 2. Use Generators and Transformers for Recurring Changes

A base may generate a ConfigMap from files or literals:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
configMapGenerator:
  - name: api-config
    files:
      - app.properties
    literals:
      - LOG_LEVEL=info
images:
  - name: registry.example.com/api
    # Illustrative 64-hex digest; substitute the published image digest.
    digest: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

The Deployment must reference the generated ConfigMap name for Kustomize's reference rewrite to change its Pod template. Image transformation changes recognized image fields, so promote the same published digest from staging to production rather than rebuilding under a mutable tag.

Other transformers provide `namespace`, `namePrefix`/`nameSuffix`, `labels`, `images`, and `replacements`. They rewrite supported object fields and references, not arbitrary strings inside every resource. Inspect the final build to confirm names, selectors, namespaces, and references. Components can bundle optional patches or generators when multiple overlays need the same feature; use them only when they clarify shared ownership rather than hiding another layer of composition.

## 3. Combine Kustomize with Helm Without Losing the Input Boundary

A chart can generate upstream resources and Kustomize can patch the rendered objects, but the build stages must be explicit. For a local chart, one workflow is:

```bash
helm template api ../charts/api -f values-prod.yaml > overlays/prod/chart-rendered.yaml
kubectl kustomize overlays/prod > rendered.yaml
kubectl diff -f rendered.yaml
```

The overlay's `resources` must name `chart-rendered.yaml`; piping Helm output into a command that builds `.` does not make that output a Kustomize input. The `helmCharts` generator is another option, but it requires `--enable-helm` in the renderer. Argo CD needs this configured through `kustomize.buildOptions` or an approved config-management plugin. Pin the chart, renderer, and remote inputs so the same source produces a reviewable build.

## 4. Keep Secret Values Out of Rendered Source

`secretGenerator` creates a Kubernetes Secret, but base64 is encoding, not confidentiality. A plaintext source file or generated manifest in Git still exposes the credential. Use an external-secret reference, an encrypted-at-rest workflow such as SOPS, or a trusted deployment-time secret injection path. Protect decrypted files and rendered output in temporary storage, logs, and CI artifacts.

```yaml
secretGenerator:
  - name: db-password
    files:
      - password=./secrets/db-password.txt
    type: Opaque
```

Keep the source file out of Git and ensure the chosen renderer and deployment controller have the required secret decryption or synchronization capability. The generated object still needs Kubernetes access controls and storage protection.

## 5. Validate the Exact Output Before Applying

Use the same Kustomize version as CI or the deployment controller. Strict schema validation needs schemas for the target Kubernetes and custom resource APIs; skipped resources or missing schemas limit what the validator proves.

```bash
kubectl kustomize overlays/prod > rendered.yaml
kubeconform -strict rendered.yaml
kubectl diff -f rendered.yaml
```

`kubectl diff` returns status 1 when it finds differences, so CI should distinguish an expected diff from a command failure instead of blindly chaining `apply` with `&&`. Review the actual rendered objects, then apply that same artifact:

```bash
kubectl apply -f rendered.yaml
```

Rendering proves what the tool produced, not that the API server accepts it or the application becomes healthy. Admission mutation, cluster policy, secrets, scheduling, and runtime state are separate. GitOps pruning and self-healing are also explicit controller settings; watching a repository alone does not enable them.

## Summary

Kustomize composes a shared base with explicit environment changes. Generators can change Pod templates through hashed references; patches and transformers have schema and reference boundaries. Pin the build inputs, protect Secret data, and review the exact rendered output before applying it.

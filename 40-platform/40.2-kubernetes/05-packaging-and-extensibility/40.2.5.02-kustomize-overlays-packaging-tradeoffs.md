# Kustomize Overlays & Packaging Trade-offs

## TL;DR

Kustomize customizes raw Kubernetes YAML **without templating**: a `base` defines the app; `overlays` patch it per environment using strategic-merge/JSON6902 patches, generators, and transformers. Choose Kustomize for diff-friendly, template-free variance; Helm for ecosystem charts and complex parameterization. They combine cleanly: render a chart with `helm template`, then overlay org-specific patches.

**Why it matters:** Packaging choices shape every deployment and GitOps repo. Interviews test when you reach for each tool, how configMapGenerator hash-rollouts work, and why secrets need more than base64.

## First Principles

Kustomize answers Helm's templating with pure patching:

1. **Base + overlays = variation without a template language**: the base is valid YAML; overlays are strategic-merge patches. No `{{ }}` means no template-debugging — the cost is expressiveness for real conditionality.
2. **The choice is logic-vs-patching**: heavy variation with conditionals → Helm; layered deltas over a shared base → Kustomize. Both reify the same need: one source, many environments (→ 30.3.5's config discipline).
3. **Generate-then-patch composes**: Kustomize can *use* Helm (render charts, then patch) — the tools layer rather than compete.

## Definition

**Kustomize** is a template-free customization engine built into `kubectl apply -k`. A **kustomization.yaml** declares:

- **resources** — the manifests being customized (the *base*)
- **patches** — surgical modifications (strategic merge or JSON6902)
- **generators** — create ConfigMaps/Secrets from files/literals (`configMapGenerator`)
- **transformers** — cross-cutting rewrites (namespace prefixing, label injection, image tag overrides, name suffixes)
- **components** — reusable partial kustomizations composed into overlays

```text
repo/
├── base/                        # the app, environment-neutral
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   ├── service.yaml
│   └── hpa.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml   # resources: ../../base
    │   ├── replica-count.yaml   # strategic merge patch
    │   └── image-tag.yaml
    └── prod/
        ├── kustomization.yaml
        ├── patches/
        │   ├── replicas.yaml
        │   └── resources.json       # JSON6902 patch
        └── secrets/                 # SOPS-encrypted, never plain!
```

## Why Do We Need It?

| Problem | Solution |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Copy-pasted YAML per env drifts silently | One base; env deltas live only in overlays |
| Go templates hide what will actually be applied | Kustomize output = valid input YAML at every step; `kubectl kustomize` shows final state |
| Third-party charts need org-wide tweaks (labels, proxy env) | Post-render with Kustomize instead of forking the chart |
| Image tags updated by CI in N files | `images:` transformer — one line per env |
| Config change must restart pods reliably | Generated ConfigMap name hash changes → Deployment ref changes → rollout |
| Reviewing PRs that touch 40 templated lines | Patches show ONLY the delta — small, reviewable diffs |

## How It Works

### Strategic Merge vs JSON6902

Strategic merge patches understand Kubernetes field semantics (lists merge by key where supported):

```yaml
# overlays/dev/replica-count.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 1                    # overrides base value
  template:
    spec:
      containers:
        - name: api              # merge key: name
          resources:
            requests: { cpu: 100m, memory: 128Mi }
```

JSON6902 is precise positional editing — needed when strategic merge cannot express intent (insert list item, replace array element by index):

```yaml
# overlays/prod/patches/resources.json
[
  {"op": "replace", "path": "/spec/replicas", "value": 12},
  {"op": "add",
   "path": "/spec/template/spec/tolerations/-",
   "value": {"key": "dedicated", "operator": "Exists", "effect": "NoSchedule"}}
]
```

Wiring both into an overlay:

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payments-prod
resources:
  - ../../base
patches:
  - path: patches/replicas.yaml        # strategic merge
    target:
      kind: Deployment
      name: api
  - path: patches/resources.json       # JSON6902
    target:
      kind: Deployment
      name: api
commonLabels:
  env: prod
```

### Generators Drive Rollouts

```yaml
# base/kustomization.yaml
configMapGenerator:
  - name: api-config
    files:
      - app.properties
    literals:
      - LOG_LEVEL=info
```

Generated names get a content hash suffix: `api-config-6f9h27m5t8`. The Deployment's `envFrom` reference is rewritten to match. Change one byte of `app.properties` → new hash → new ConfigMap + Deployment ref → automatic rolling restart. This is the single most-loved Kustomize behavior; hand-written ConfigMaps silently never roll pods.

### Transformers — Cross-Cutting Rewrites

| Transformer | Effect | Typical use |
| ------------------------------- | ----------------------------------------- | -------------------------------- |
| `namespace:` | Sets namespace on all resources | Env isolation |
| `namePrefix:` / `nameSuffix:` | Renames objects + rewrites refs | Multi-instance installs |
| `commonLabels:` (now `labels:`) | Injects labels everywhere incl. selectors | Org tagging policy |
| `images:` | Rewrites name/tag/digest | CI-driven releases |
| `replacements:` | Copies any field to any other | Wire service DNS into client env |
| `replicas:` (transf.) | Sets replica count per resource | Simple scale overrides |

```yaml
images:
  - name: myregistry/api
    newTag: sha256-9f86d081884c   # CI rewrites this one line
```

### The Build Is Purely Functional

`kustomize build overlays/prod` (or `kubectl apply -k`) is deterministic: same inputs → byte-identical output. That property makes GitOps trivial — the repo IS the rendered truth, and ArgoCD/Flux run the builder server-side. No Tiller-equivalent lives in your cluster, no release state to corrupt.

## Code Examples

### Complete Base

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
configMapGenerator:
  - name: api-config
    literals:
      - PORT=3000
labels:
  - pairs:
      app.kubernetes.io/part-of: payments
    includeSelectors: false
```

### Overlay With Component Reuse

```yaml
# components/mtls-sidecar/kustomization.yaml   (a component)
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
patches:
  - path: sidecar.yaml
    target: { kind: Deployment, name: ".*" }
---
# overlays/prod/kustomization.yaml
components:
  - ../../components/mtls-sidecar
```

Components are composable feature flags for manifests — enable mesh injection, PDBs, or monitoring per overlay without duplicating patches.

### Combining Helm + Kustomize

```yaml
# overlays/prod/kustomization.yaml
helmCharts:                          # native helm-chart support (v5+)
  - name: ingress-nginx
    repo: https://kubernetes.github.io/ingress-nginx
    version: 4.10.1
    releaseName: edge
    valuesFile: values-prod.yaml     # chart knobs stay Helm-y
patches:                             # org policy stays Kustomize-y
  - path: patch-controller-resources.yaml
    target:
      kind: Deployment
      name: edge-ingress-nginx-controller
```

Or the classic pipe when you want explicit stages in CI:

```bash
helm template edge ingress-nginx/ingress-nginx \
  --version 4.10.1 -f values-prod.yaml \
  | kustomize build --enable-helm . \
  > rendered.yaml
kubectl diff -f rendered.yaml && kubectl apply -f rendered.yaml
```

The pattern: **upstream complexity stays upstream (Helm), local divergence stays declarative (Kustomize)**. You stop maintaining chart forks while keeping full control of the final manifest.

### Secrets Handling Caveat

`secretGenerator` only base64-encodes — it provides zero confidentiality, and committing generated plaintext Secrets is a leak waiting to happen:

```yaml
secretGenerator:
  - name: db-password
    literals:
      - password=hunter2     # NEVER commit the source of this in plaintext
    type: Opaque
```

Acceptable patterns, best first:

```text
1. External Secrets Operator / vault-injected Secret resources
   → cluster pulls from Vault/ASM at runtime; git holds only references.
2. SealedSecrets (Bitnami) → commit ciphertext only; controller holds key.
3. SOPS + age/KMS → kustomize supports .enc.yaml decryption via
   ksops plugin; keys stay in cloud KMS, git holds encrypted bytes.
4. CI-only: generate at deploy time from pipeline secrets,
   apply out-of-band from the kustomize build.
```

### Verifying What Will Apply

```bash
kustomize build overlays/prod | less          # read the truth
kustomize build overlays/prod | kubeconform -strict -
diff <(kustomize build overlays/dev) <(kustomize build overlays/staging)  # env delta review
kustomize edit set image myregistry/api=myregistry/api@sha256:abc123
```

## Real-World Use Cases

### 1. Three-Environment GitOps Repo

ArgoCD watches `overlays/{dev,staging,prod}`. PRs to prod overlay require CODEOWNERS approval; the rendered diff in the PR shows exactly which fields change between staging and prod. Drift self-heals because the cluster reconciles toward `kustomize build` output.

### 2. Adopting Upstream Charts Without Forking

Platform team installs cert-manager via `helmCharts`, then adds a Kustomize patch pinning resource requests and injecting a corporate proxy env block. Upstream upgrades become version bumps, not merge conflicts across a vendored fork.

### 3. Multi-Tenant Namespaced Install

One base app installed per tenant: overlay sets `namespace: tenant-a`, `namePrefix: t-a-`; replacements wire the prefixed Service DNS name into client ConfigMaps. Tenants stay isolated without per-tenant forks.

### 4. CI Release Promotion

Merge to main runs `kustomize edit set image ...@sha256:<digest>` on `overlays/staging`, commits, Argo syncs; promotion to prod is the identical commit against `overlays/prod` after canary sign-off — auditable, revertible, digest-pinned.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Committing plaintext values feeding `secretGenerator` | Use ESO/SealedSecrets/SOPS; git must hold ciphertext or references only |
| Editing generated ConfigMaps directly | Edit generator inputs; hashes keep rollouts correct |
| Strategic-merge patch on a list expecting element merge | Lists merge by key only where API semantics allow; else use JSON6902 |
| Deep overlay-on-overlay hierarchies nobody can trace | Keep depth ≤ 2 (base → overlay); extract shared bits into components |
| Duplicating whole resources into overlays "just to tweak" | If you copy a resource into an overlay, the base reference broke — patch instead |
| Forgetting `--enable-helm` (or v5 flag) for helmCharts builds | Set it in CI + ArgoCD spec (`configManagementPlugins` handles natively in newer Argo) |
| Assuming `commonLabels` rewrites selectors safely | Legacy `commonLabels` mutates selectors; prefer `labels:` with `includeSelectors` chosen deliberately |

## Best Practices

1. **Base stays boring and complete** — every resource must be validly deployable from base alone; overlays should shrink diffs, not invent resources.
2. **Review rendered output in CI** — fail the build if `kustomize build` errors, schema-invalidates (kubeconform), or produces unexpected namespace/image drift.
3. **Digest-pin images in prod overlays**, tags elsewhere — the images transformer makes this one-line cheap.
4. **Prefer components over copy-paste for shared features** (mesh, monitoring, PDBs).
5. **Decide Helm-vs-Kustomize per artifact**: third-party chart → consume as chart; first-party manifests → Kustomize; complex conditional logic → Helm authoring may still win.
6. **Never let secrets touch the renderer in plaintext** — encrypt at rest, decrypt at apply, audit both paths.

## Performance Considerations

| Aspect | Impact | Mitigation |
| ------------------------------------------------------------------------ | -------------------------------------------- | -------------------------------------------------------------------------------------- |
| Render time grows with resources² in worst cases (replacements scanning) | Large monorepo bases slow CI seconds-minutes | Split bases per service; avoid global replacements |
| Hash-suffix ConfigMaps churn etcd objects | Many regenerations accumulate old maps | Prune old generated maps (GarbageCollector handles via Argo; manual cleanup otherwise) |
| helmCharts builds invoke Helm each render | Adds ~seconds | Cache chart downloads; pin versions |
| Massive single base shared by many overlays | Any base change re-renders every overlay | Stabilize base contracts; version bases like libraries |

## Summary

Kustomize treats packaging as pure function application: a valid base, deterministic transforms, readable per-env deltas. Its strengths — template-free diffs, hash-triggered rollouts, native integration with kubectl and GitOps — make it the default choice for first-party manifests and post-rendering third-party charts. Helm wins where ecosystem reuse or heavy conditional logic dominates. The senior move is fluency in both plus the judgment table to choose per situation, and an ironclad rule that secrets never exist in plaintext anywhere near the rendering pipeline.

## Cheat Sheet

```text
KUSTOMIZE CHEAT SHEET
═════════════════════

STRUCTURE:
base/ (complete, neutral) ← overlays/{dev,staging,prod}
kustomization.yaml fields:
• resources · patches · configMapGenerator · secretGenerator
• labels/namePrefix/namespace · images · replacements · components

PATCHES:
• strategic merge: normal yaml, merges by field semantics
• JSON6902: op/path/value — add/replace/remove, list-index precise
• target: kind/name/labelSelector narrows scope

GENERATORS:
• configMapGenerator → name-<hash>; ref rewritten → auto rollout
• secretGenerator = base64 ONLY — not encryption!

COMMANDS:
• kustomize build overlays/prod         render (pure function)
• kubectl apply -k overlays/prod        direct apply
• kustomize edit set image X=Y          CI promotion
• diff <(build dev) <(build prod)       env delta review

HELM VS KUSTOMIZE:
need ecosystem charts / heavy logic  → HELM (values + templates)
first-party manifests / tiny diffs   → KUSTOMIZE
third-party chart + org tweaks       → helm template | kustomize
                                       (or helmCharts: field)

SECRETS RULE:
git stores ciphertext/references ONLY:
ESO (vault pull) > SealedSecrets > SOPS+ksops > CI-time inject

GOTCHAS:
• lists don't deep-merge → JSON6902
• commonLabels touches selectors → use labels: includeSelectors:false
• overlays must not redefine base resources wholesale
```

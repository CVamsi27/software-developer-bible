# CRDs, Operators & Controller Patterns

## Definition

A **CustomResourceDefinition (CRD)** adds a resource type to the Kubernetes API. A **custom resource (CR)** is one object of that type, such as `PostgresCluster/payments-db`. The API server validates and stores it, but installing a schema does not create the database.

A **controller** supplies behavior by repeatedly comparing the declared intent with observed state and making changes toward that intent. An **operator** applies this controller approach to application-specific operations such as backup, upgrade, or failover. The operational capability comes from its code, permissions, and tests, not the name of its CRD.

> **Textbook Definition:** A CustomResourceDefinition extends the Kubernetes API with a resource schema. A controller reconciles observed state toward declared intent; an operator applies that control-loop approach to application-specific operational procedures.

## First Principles

Objects and processes can disappear independently. A notification can be delayed or repeated, and an API write can succeed even when the controller loses its response. Logic that means “on this event, create another database” therefore risks duplicates or lost recovery steps.

Reconciliation instead asks “given the current intent and observed resources, what is still missing?” That is **level-triggered** behavior: an event is a hint to inspect the current state, not an exactly-once instruction to execute a remembered transition. Watches, relists, retries, and explicit requeues provide opportunities to inspect it again. Each action needs to be safe to repeat; an external effect may need a durable operation identity and recovery state beyond a Kubernetes helper.

```text
API objects -> informer watch/cache -> workqueue key (namespace/name)
                                               |
                                      reconcile latest state
                                      /       |        \
                             read children  act       record status
                                      \       |        /
                                      writes through API server
                                               |
                                  new events / retry / later requeue
```

An **informer** watches and caches API objects; a **workqueue** schedules keys for workers. The queue is not a log of guaranteed business operations. The controller can observe an older cached resource, encounter an update conflict, and retry. Distinguish spec intent from status observation, and associate status with the generation it actually observed.

## Why Do We Need It?

| Problem | Solution |
| --------------------------------------------------------------- | ------------------------------------------------------------------------- |
| App needs `kubectl`-native lifecycle beyond Deployment/Job | CRD gives it first-class API semantics (RBAC, validation, kubectl get) |
| Day-2 operations are tribal knowledge (runbooks) | Operator encodes runbooks as code — consistent at 3am |
| Stateful failover logic too complex for init containers/scripts | Controller reacts to topology changes continuously |
| Team wants declarative multi-cluster rollouts | CRD + GitOps: commit the CR, controllers converge everywhere |
| Manual steps drift between environments | Desired-state reconciliation makes drift visible and self-correcting |
| Ecosystem extensibility (cert-manager, Istio, Prometheus) | They ARE CRDs + operators — understanding the pattern unlocks all of them |

## How It Works

### CRD Anatomy

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: postgresclusters.db.example.com     # <plural>.<group>
spec:
  group: db.example.com                     # API group
  scope: Namespaced                         # or Cluster
  names:
    plural: postgresclusters
    singular: postgrescluster
    kind: PostgresCluster                   # CamelCase singular
    shortNames: [pgc]
    categories: [database]                  # kubectl groups
  versions:
    - name: v1alpha1                        # maturity-tagged versions
      served: true
      storage: true                         # exactly ONE per definition
      schema:
        openAPIV3Schema:
          type: object
          required: ["spec"]
          properties:
            spec:
              type: object
              required: ["version", "replicas"]
              properties:
                version: { type: string }
                replicas: { type: integer, minimum: 1 }
                storage:
                  type: object
                  properties:
                    size: { type: string }        # e.g. "100Gi"
            status:
              type: object
              x-kubernetes-preserve-unknown-fields: true
      subresources:
        status: {}               # enables /status subresource writes
        scale:
          specReplicasPath: .spec.replicas
          statusReplicasPath: .status.replicas
      additionalPrinterColumns:
        - name: Replicas
          type: integer
          jsonPath: .spec.replicas
```

The schema requires a spec, version, and a positive replica count. It validates those declared types/bounds; it does not prove a database version is supported or a storage quantity is usable. Declare additional constraints intentionally. The scale interface needs the controller to report actual replica count separately from ready count; utilization-based HPA also needs the appropriate selector/status contract before this becomes an HPA-ready resource.

The remaining fields have separate owners:

- **Schema enforcement**: structural schemas enforce the declared admission constraints; unspecified business constraints still need schema rules or validation.
- **status subresource**: separates user intent (`spec`) from controller observations (`status`) — writes to `/status` need separate RBAC.
- **Versions**: serve multiple, store one; configure conversion when served representations differ; changing the storage version does not automatically rewrite all old stored objects.

### Desired vs Observed — The Core Discipline

```text
spec: replicas=5, version=16.2
status: replicas=4, readyReplicas=3, observedGeneration=7
```

This is a progress observation, not a contradiction. The user requested five; only four exist and three satisfy the controller's readiness contract. If the resource is now generation eight, status for generation seven is stale. Conditions should explain whether the controller is creating, waiting, failing, or ready for the current request. Pod readiness does not prove replication consistency or completed database migration.

Reconcile must tolerate missing optional fields, deleted children, retryable API errors, and ownership conflicts. Idempotency reduces duplicate effects but does not prevent races; resource versions, optimistic conflict handling, leader/ownership design, and external fencing can matter as well. A controller should report an error or condition instead of declaring success after a failed observation.

### Operator Capability Levels

The community shorthand (OperatorHub / OperatorSDK levels):

| Level | Capability | Example behavior |
| ----- | -------------- | -------------------------------------------------- |
| 1 | Basic install | Create DB pods + service from CR |
| 2 | Upgrades | Rolling version bump with data-dir migration |
| 3 | Full lifecycle | Backup, restore, resize storage online |
| 4 | Insights | Metrics, alerts, topology exported to status |
| 5 | Auto-pilot | Self-healing quorum, auto-tuning, planned failover |

Levels 1-2 are common and valuable; higher levels describe broader automation goals, not certification that a controller safely performs them.

### ownerReferences & Garbage Collection

For children whose lifecycle should follow the CR, set an appropriate controlling owner reference. Shared or retained data resources may deliberately have different ownership. This is a fragment; copy the actual parent UID, not the abbreviated demonstration value:

```yaml
metadata:
  ownerReferences:
    - apiVersion: db.example.com/v1alpha1
      kind: PostgresCluster
      name: payments-db
      uid: 0f3c...-...            # copied from the parent CR
      controller: true            # exactly one controlling owner
      blockOwnerDeletion: false
```

Consequences worth quoting in interviews:

- Deleting the CR can initiate garbage collection of valid owned children under the chosen propagation policy. PVC retention and intentionally shared/retained resources need separate policies; garbage collection is asynchronous.
- Foreground vs background deletion changes whether children vanish before or after the parent disappears.
- A recreated CR with the same name has a new UID. Do not silently adopt unrelated children or recreate persistent data blindly; verify identity, ownership, and recovery policy before either action.

### Finalizers cover cleanup outside Kubernetes ownership

A cloud database or bucket is not a Kubernetes child for garbage collection. A controller can add a **finalizer**, a metadata key that keeps the CR present after deletion is requested. On a CR with a deletion timestamp, the controller performs its idempotent cleanup and removes that finalizer only after the cleanup is complete. Deletion then proceeds.

Install the finalizer before creating the external resource, persist its operation/identity, and handle a successful provider deletion whose response was lost. If the controller or provider is unavailable, the CR can remain terminating. The runbook must recover cleanup safely; removing the finalizer manually skips that contract and can leak a resource or abandon data. An owner reference does not replace this external lifecycle.

## Code Examples

### Go Skeleton With controller-runtime

This is an excerpt inside a Kubebuilder/controller-runtime project, not a standalone compiling database operator. Generated CR types, imports/RBAC, the pure `desiredStatefulSet` builder, and application upgrade/replication procedures are omitted. The builder must produce stable names/selectors and fields this controller owns. The example reconciles a child workload and its observed ready count only; add the finalizer path before introducing external resources.

```go
// Reconcile moves the world one step toward spec. Idempotent, level-triggered.
func (r *PostgresClusterReconciler) Reconcile(
    ctx context.Context, req ctrl.Request) (ctrl.Result, error) {

    var cluster dbv1alpha1.PostgresCluster
    if err := r.Get(ctx, req.NamespacedName, &cluster); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err) // absent: valid owned Kubernetes children may be GC'd
    }

    // 1. Ensure the child StatefulSet exists and matches spec
    want := desiredStatefulSet(&cluster) // pure function: CR -> object
    op, err := controllerutil.CreateOrUpdate(ctx, r.Client, want,
        func() error {
            // CreateOrUpdate fetches live state; establish ownership inside mutation.
            if err := ctrl.SetControllerReference(&cluster, want, r.Scheme); err != nil {
                return err // an unrelated controlling owner is a conflict
            }
            mergeSpecInto(want, &cluster) // change only deliberately owned fields
            return nil
        })
    if err != nil {
        return ctrl.Result{}, err // requeued with backoff automatically
    }
    _ = op // Created / Updated / Unchanged — useful for logs/metrics

    // 2. Failed observation is not success; propagate it for retry.
    sts := &appsv1.StatefulSet{}
    if err := r.Get(ctx, types.NamespacedName{
        Name: want.Name, Namespace: want.Namespace}, sts); err != nil {
        return ctrl.Result{}, err
    }
    before := cluster.DeepCopy()
    cluster.Status.ReadyReplicas = sts.Status.ReadyReplicas
    // Status structs/imports must be defined in the surrounding project.
    if !reflect.DeepEqual(before.Status, cluster.Status) {
        if err := r.Status().Patch(ctx, &cluster, client.MergeFrom(before)); err != nil {
            return ctrl.Result{}, err
        }
    }

    // 3. Wait for the child to observe its own desired generation.
    if sts.Status.ObservedGeneration < sts.Generation ||
        sts.Status.ReadyReplicas < cluster.Spec.Replicas ||
        sts.Status.UpdatedReplicas < cluster.Spec.Replicas ||
        sts.Status.CurrentRevision != sts.Status.UpdateRevision {
        return ctrl.Result{RequeueAfter: 15 * time.Second}, nil
    }
    return ctrl.Result{}, nil
}

func (r *PostgresClusterReconciler) SetupWithManager(m ctrl.Manager) error {
    return ctrl.NewControllerManagedBy(m).
        For(&dbv1alpha1.PostgresCluster{}).                 // primary watch
        Owns(&appsv1.StatefulSet{}).                        // child events requeue us
        Complete(r)
}
```

What this excerpt demonstrates, and where it stops:

- `For(...)` + `Owns(...)`: owned-child watch events enqueue the parent CR when relevant; filters, cache scope, and event delivery need intentional configuration.
- `CreateOrUpdate` chooses create versus update; its mutation function must still be repeatable, ownership-safe, and compatible with API defaults.
- Returning an error requeues with exponential backoff — errors are still failures to observe and report; automatic retry does not guarantee eventual recovery.

### TypeScript Pseudocode Equivalent

```typescript
async function reconcile(req: Request): Promise<Result> {
  const cr = await api.get("postgresclusters", req.ns, req.name);
  if (!cr) return {};                       // absence is not proof cleanup finished

  const want = buildStatefulSet(cr.spec);   // deterministic desired object
  want.metadata.ownerReferences = [ownerRefTo(cr)];

  const have = await api.get("statefulsets", req.ns, want.metadata.name);

  if (!have) {
    await api.create(want);
  } else if (!matchesDesired(have, want)) { // compare fields this controller owns
    await api.patchOwnedFields(have, want, have.metadata.resourceVersion);
  }

  const live = await api.get("statefulsets", req.ns, want.metadata.name);
  await api.patchStatus({
    kind: "PostgresCluster",
    namespace: req.ns,
    name: req.name,
    observedGeneration: cr.metadata.generation,
    readyReplicas: live?.status?.readyReplicas ?? 0,
    phase: childMatchesDesiredAndIsReady(live, want) ? "Ready" : "Provisioning",
  });

  return !childMatchesDesiredAndIsReady(live, want)
    ? { requeueAfterSeconds: 15 }
    : {};
}

setInterval(() => listAll().forEach(enqueue), RESYNC_PERIOD_MS); // level-trigger safety net
```

All TypeScript API helpers above are pseudocode, not an SDK. Conditional owned-field updates must handle conflicts and avoid overwriting other owners; status comparison must include current child generation/template, not only a ready-count coincidence. Neither excerpt performs a database upgrade or validates its data.

### Using It From the Outside

Install the example CRD and a controller implementing the promised spec before these commands. With only the CRD installed, the API may accept and list the object, but no database will be provisioned. The example has no working complete operator behind it.

```bash
kubectl apply -f - <<'YAML'
apiVersion: db.example.com/v1alpha1
kind: PostgresCluster
metadata:
  name: payments-db
spec:
  version: "16.2"
  replicas: 3
  storage: { size: 200Gi }
YAML

kubectl get pgc payments-db -w        # printer column shows requested count; inspect status for actual progress
kubectl describe pgc payments-db      # events from our controller
kubectl delete pgc payments-db        # owned-child deletion follows policy; verify retention/finalizer effects first
```

## Real-World Use Cases

### 1. cert-manager (Ecosystem Operator)

You declare `Certificate` CRs; the operator orders from ACME providers, renews before expiry, stores results in Secrets, and updates the issued Secret; consumers need their own observed reload/rollout contract. Studying its CRDs (`Issuer`, `CertificateRequest`, order chains) is a masterclass in status machines.

### 2. In-House Kafka Topic Provisioner (Level 1-2)

Platform team exposes `KafkaTopic` CRs. A small controller validates config against org policy (retention limits, replication >= 3), creates topics via admin API, and mirrors status back. Developers stop opening tickets; RBAC replaces shared admin creds. This is the sweet spot where operators pay off immediately.

### 3. Database Failover Automation (Level 3-5)

PostgresOperator watches pod liveness and replica roles; on primary loss it runs the promotion runbook ( fencing → promote newest replica → update Service selector → resync old primary as standby). Measure recovery and verify fencing/data consistency before claiming an availability improvement; automation can also repeat a flawed failover procedure faster.

### 4. Multi-Cluster Rollout via GitOps

Each fleet cluster runs the same operator; a single committed `RolloutPolicy` CR (canary weights, region gates) drives divergent local actions everywhere. The CR is the interface; operators are the execution layer.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Edge-triggered logic assuming events arrive exactly once | Level-triggered reconcile + periodic resync; treat events as hints |
| Non-idempotent reconcile (append-only side effects) | Every action derived from full desired state; use CreateOrUpdate-style helpers |
| Writing status without the status subresource | Enable `subresources.status`; split RBAC so users cannot fake health |
| Children created without ownerReferences | Always SetControllerReference — else leaks and broken cascades |
| Blocking reconcile on slow external calls (API timeouts inline) | Return `Result{RequeueAfter}` or move long work to jobs; keep loops fast |
| Building an operator for a 3-command workflow | Scripts/CronJobs/plain Deployments first — see decision table below |

## Best Practices

1. **Model intent in spec, truth in status** — never let users write status, never let controllers rewrite spec.
2. **Make the desired-object builder a pure function** (`CR -> Object`) — trivially unit-testable without a cluster (envtest optional).
3. **Watch relevant dependencies** — owned children are common; explicitly map referenced Secrets or other required resources when needed; use predicates/filters to keep queues clean.
4. **Version your CRD API from day one** (`v1alpha1`), design conversions early — retrofitting versions onto deployed users hurts.
5. **Ship metrics + events from the controller** — reconcile counts, error rates, and Kubernetes Events are your UX.
6. **Prefer upstream operators over homegrown ones** — cert-manager/Prometheus/Postgres operators are battle-tested; contribute fixes instead of forking.

## When To Write an Operator (vs Scripts)

| Signal | Verdict |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| One-off setup, rarely changes | Shell script / Terraform |
| Periodic maintenance task | CronJob |
| Needs to react to cluster state changes continuously | Controller |
| Runbook steps humans execute repeatedly under stress | Operator (levels 1-3) |
| Multiple teams consume the capability via API | Operator + CRD is the product |
| Logic fits in Helm values + hooks already | Stay with packaging (Helm/Kustomize) — do not add a controller |

Litmus test: if the answer must remain correct *while nobody watches*, across restarts, races, and partial failures, you need a controller; otherwise you need documentation and cron.

## Performance Considerations

| Aspect | Impact | Mitigation |
| ---------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Requeue storms after API outages | Queue floods on recovery | Rate-limiting workqueues (default); cap concurrency per controller |
| Large informer caches (thousands of CRs) | Memory + startup time | Field/label selectors on caches; partition by namespace |
| Slow external systems inside reconcile | Worker starvation | Async job pattern + status conditions; RequeueAfter pacing |
| Webhook conversion latency | API slowness for all clients of the CRD | Keep conversion cheap; cache certificates |
| Aggressive resync period | Wasted API traffic | Choose watches, relist/requeue, and resync from dependency/recovery requirements; resync is not a guaranteed external-health check |

## Summary

CRDs turn Kubernetes into a platform for building platforms: schema-validated resources served by the apiserver you already operate. Controllers implement the universal loop — observe, diff, act idempotently, record status, repeat — and operators encode application-specific runbooks into that loop. Owner references wire child lifetimes to parents; garbage collection makes deletion declarative. Choose the pattern deliberately: scripts for one-offs, CronJobs for schedules, controllers for continuous correctness, operators when day-2 automation justifies building and maintaining a piece of software. OLM and OperatorHub exist because the industry converged on this being the right way to ship operational software into clusters.

# CRDs, Operators & Controller Patterns

Applying a `PostgresCluster` object can succeed even when no database is created. The object tells the API server how to validate and store intent; a controller must still observe it and perform the work. That separation is the central design boundary between extending the Kubernetes API and implementing application behavior.

## Definition

A **CustomResourceDefinition (CRD)** adds a resource type to the Kubernetes API. A **custom resource (CR)** is one object of that type, such as `PostgresCluster/payments-db`. A **controller** repeatedly compares declared intent with observed state and makes changes toward that intent. An **operator** uses this controller pattern for application-specific lifecycle work such as upgrades, backups or failover.

> **Textbook Definition:** A CRD extends the Kubernetes API with a schema for a new resource type. A controller reconciles observed state toward declared intent; an operator applies that loop to application-specific operational procedures.

## First Principles

The API server can validate and store a custom object, but it does not execute the application's lifecycle. The CRD defines the resource contract; a controller observes the object and acts on it. Use this extension when a Kubernetes-native declarative API, validation, RBAC and status justify owning a controller. A CRD is not a database for high-volume end-user records; behavior that needs custom API-server logic may require an aggregated API.

## Start with the resource contract

A CRD's OpenAPI schema validates shape and declared constraints; it cannot prove that an external database version is supported or a storage request can be fulfilled. Define which fields users own, which values are defaulted, what status means, and which versions the controller serves before releasing the type.

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: postgresclusters.db.example.com
spec:
  group: db.example.com
  scope: Namespaced
  names:
    plural: postgresclusters
    singular: postgrescluster
    kind: PostgresCluster
    shortNames: [pgc]
  versions:
    - name: v1alpha1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          required: [spec]
          properties:
            spec:
              type: object
              required: [version, replicas]
              properties:
                version: {type: string}
                replicas: {type: integer, minimum: 1}
                storage:
                  type: object
                  properties:
                    size: {type: string}
            status:
              type: object
              properties:
                replicas: {type: integer}
                readyReplicas: {type: integer}
                selector: {type: string}
                observedGeneration: {type: integer, format: int64}
      subresources:
        status: {}
        scale:
          specReplicasPath: .spec.replicas
          statusReplicasPath: .status.replicas
          labelSelectorPath: .status.selector
```

Exactly one served version is the storage version. Multiple served versions need a conversion strategy when their representations differ; changing which version stores new writes does not rewrite already stored objects. Plan a storage migration when old objects must be converted. The status subresource separates controller observations from user-written spec and needs appropriate RBAC. Exposing the scale subresource also requires the resource to report its selector and replica count consistently; an HPA still needs a compatible metric and target.

## Reconciliation treats events as hints

Controllers receive notifications, but events can be delayed, repeated or observed after newer state exists. A watch event should enqueue a resource key; reconciliation then reads current state and asks what remains to be done. This is **level-triggered** behavior: the controller converges from today's intent instead of treating each event as an exactly-once command.

```text
CR event -> informer cache -> workqueue key (namespace/name)
                                     |
                              read latest intent
                              /       |        \
                        inspect child  act   update status
                              \       |        /
                               API writes and later events
```

An informer watches and caches API objects; a workqueue schedules keys for workers. Cache state can be stale, API updates can conflict, and external calls can succeed even when the controller loses the response. Reconcile must therefore be safe to retry and should change only fields it owns. Persist an operation identity when an external action cannot be inferred from current Kubernetes state alone.

Keep user intent in `spec` and observations in `status`. Report status for the generation actually processed; otherwise readers may mistake an old Ready condition for success on a new request. A ready Pod count does not prove database replication, migration completion or application-level consistency.

## Give children and external resources different cleanup contracts

Use a controlling `ownerReference` for a child whose lifetime should follow the CR. Garbage collection is asynchronous and follows the deletion propagation policy. PVCs, backups and shared resources may need deliberate retention rather than automatic deletion. A new CR with the same name has a different UID; do not adopt old children or data by name alone without checking identity and recovery policy.

A cloud database or bucket is not a Kubernetes child, so garbage collection cannot remove it. A **finalizer** keeps the CR present after deletion is requested while the controller performs external cleanup. Add the finalizer before creating the resource, make cleanup idempotent, and remove it only after cleanup is confirmed. If the provider completed deletion but its response was lost, the next reconcile must safely discover that state. A stuck finalizer needs a recovery procedure; removing it manually bypasses cleanup and can leak resources or abandon data.

## Reconcile owned Kubernetes state

This controller-runtime excerpt shows the shape of a reconcile loop, not a complete operator. It assumes the generated `Spec.Replicas` field is `*int32`; generated API types, imports, RBAC, error conditions and database procedures are omitted. `desiredStatefulSet` must return a deterministic object, and `mergeOwnedFields` must preserve fields managed by Kubernetes or another controller.

```go
func (r *PostgresClusterReconciler) Reconcile(
    ctx context.Context, req ctrl.Request,
) (ctrl.Result, error) {
    var cluster dbv1alpha1.PostgresCluster
    if err := r.Get(ctx, req.NamespacedName, &cluster); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    desiredReplicas := int32(1)
    if cluster.Spec.Replicas != nil {
        desiredReplicas = *cluster.Spec.Replicas
    }

    want := desiredStatefulSet(&cluster)
    _, err := controllerutil.CreateOrUpdate(ctx, r.Client, want, func() error {
        if err := controllerutil.SetControllerReference(&cluster, want, r.Scheme); err != nil {
            return err // do not take over an unrelated controlling owner
        }
        mergeOwnedFields(want, &cluster)
        return nil
    })
    if err != nil {
        return ctrl.Result{}, err
    }

    live := &appsv1.StatefulSet{}
    key := types.NamespacedName{Name: want.Name, Namespace: want.Namespace}
    if err := r.Get(ctx, key, live); err != nil {
        return ctrl.Result{}, err
    }

    before := cluster.DeepCopy()
    cluster.Status.Replicas = live.Status.Replicas
    cluster.Status.ReadyReplicas = live.Status.ReadyReplicas
    cluster.Status.Selector = selectorString(live.Spec.Selector) // helper serializes the live label selector
    cluster.Status.ObservedGeneration = cluster.Generation
    if !reflect.DeepEqual(before.Status, cluster.Status) {
        if err := r.Status().Patch(ctx, &cluster, client.MergeFrom(before)); err != nil {
            return ctrl.Result{}, err
        }
    }

    if live.Status.ObservedGeneration < live.Generation ||
        live.Status.ReadyReplicas < desiredReplicas ||
        live.Status.UpdatedReplicas < desiredReplicas ||
        live.Status.CurrentRevision != live.Status.UpdateRevision {
        return ctrl.Result{RequeueAfter: 15 * time.Second}, nil
    }
    return ctrl.Result{}, nil
}

func (r *PostgresClusterReconciler) SetupWithManager(m ctrl.Manager) error {
    return ctrl.NewControllerManagedBy(m).
        For(&dbv1alpha1.PostgresCluster{}).
        Owns(&appsv1.StatefulSet{}).
        Complete(r)
}
```

`For` watches the custom resource and `Owns` enqueues its parent when a child changes. Production controllers also need status conditions, conflict handling, tests, least-privilege RBAC, metrics and bounded external calls. Use rate-limited retries for transient errors; avoid blocking every reconcile worker on a slow provider API.

## Decide whether the controller is worth owning

A one-off setup is usually a script or infrastructure tool. A scheduled cleanup is usually a CronJob. A fixed install may fit Helm or Kustomize. A controller is justified when desired state must keep converging across restarts, retries and partial failures. An operator pays off when users need that convergence to encode a meaningful application lifecycle; it also creates a long-lived API, security boundary and operational service that the team must maintain.

For example, a `KafkaTopic` controller can validate retention and replication settings, create the topic through an administrative API, and report observed configuration. It must still handle duplicate requests, ownership conflicts and provider outages. Calling it an operator does not establish safe upgrades or data recovery; test those behaviors directly.

## Summary

CRDs define schema-backed API intent; controllers implement reconciliation; operators apply that loop to application operations. Reconciliation must tolerate repeated events and partial failures. Owner references govern Kubernetes children, while finalizers coordinate external cleanup. Choose the pattern from the lifecycle guarantee users need and account for the controller's ongoing security and operational ownership.

# CRDs, Operators & Controller Patterns

## TL;DR

CRDs extend the Kubernetes API with your own resource types; **controllers** watch those resources and continuously drive the cluster from *observed* state toward *desired* state in a **reconcile loop**. An **operator** is a controller that encodes operational knowledge (backup, failover, upgrades) for a specific application. Write one only when day-2 lifecycle logic is real — otherwise scripts and plain controllers suffice.

**Why it matters:** "How does Kubernetes itself work?" is the answer's backbone: every built-in object (Deployment, Job) runs the same pattern you would build. Interviews test level-triggered thinking, idempotency, ownerReferences/GC, and the judgment of when NOT to write an operator.

## First Principles

CRDs + operators are Kubernetes's extension mechanism — the API as a platform:

1. **A CRD adds a resource type; a controller gives it behavior.** "Desired state + reconcile" (→ 40.2.1.01's axiom) applied to *your* domain: a Postgres CR whose operator provisions, scales, and backs up databases. The operator pattern is domain expertise encoded as a control loop.
2. **The level distinction matters**: level 1 (install) through level 5 (auto-scale, version-upgrade) — declaring which level your operator reaches is the honest scoping.
3. **Controllers are loops — idempotent, level-triggered, watch-driven** — the same reconciliation discipline whether the loop ships with k8s or you wrote it.

## Definition

- **CRD (CustomResourceDefinition)** — API extension that teaches the apiserver about a new kind (`PostgresCluster`, `Certificate`), including its schema, scope, versions, and subresources. The apiserver then stores/serves it like any native object.
- **Controller** — A control loop: *observe* actual state, compare to spec, act to converge, repeat forever. Kubernetes ships dozens; you can add yours.
- **Operator pattern** — A controller for an app that captures human operational procedures as code (provision → scale → backup → failover → version-upgrade), typically via CRDs + custom controller.
- **Level-triggered vs edge-triggered** — Controllers re-declare full desired state each loop (level-triggered) instead of reacting to discrete events (edge). Missed events self-heal on next resync.

```text
THE RECONCILE LOOP (every controller, ever)

        ┌────────────────────────────────────────────┐
        │                                            │
        ▼                                            │
  ┌───────────┐   watch    ┌─────────────────────┐             │
  │ apiserver │──────────▶│ Informer           │             │
  │ (desired  │  + events │ + cache            │             │
  │  = CR     │           └─────┬─────┘             │
  └────▲──────┘                 │ key (ns/name)      │
       │                        ▼                    │
       │                  ┌────────────────────┐              │
       │   write status   │ Workqueue          │              │
       │   create/update  └─────┬─────┘              │
       │                        ▼                    │
       │                  ┌────────────────────┐     │
       └─────────────────────────────────────────────┤ Reconcile(req)      │────┘
          observed state   │ 1. load desired CR  │ requeue if
          converges        │ 2. read live state  │ not done
                           │ 3. diff             │
                           │ 4. act (idempotent) │
                           │ 5. update status    │
                           └─────────────────────┘
```

## Why Do We Need It?

| Problem | Solution |
| --------------------------------------------------------------- | ------------------------------------------------------------------------- |
| App needs `kubectl`-native lifecycle beyond Deployment/Job | CRD gives it first-class API semantics (RBAC, validation, kubectl get) |
| Day-2 operations are tribal knowledge (runbooks) | Operator encodes runbooks as code — consistent at 3am |
| Stateful failover logic too complex for init containers/scripts | Controller reacts to topology changes continuously |
| Team wants declarative multi-cluster rollouts | CRD + GitOps: commit the CR, controllers converge everywhere |
| Manual steps drift between environments | Desired-state reconciliation makes drift visible and self-correcting |
| Ecosystem extensibility (cert-manager, Istio, Prometheus) | They ARE CRDs + operators — understanding the pattern unlocks all of them |

## How It Works

### CRD Anatomy

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: postgresclusters.db.example.com     # <plural>.<group>
spec:
  group: db.example.com                     # API group
  scope: Namespaced                         # or Cluster
  names:
    plural: postgresclusters
    singular: postgrescluster
    kind: PostgresCluster                   # CamelCase singular
    shortNames: [pgc]
    categories: [database]                  # kubectl groups
  versions:
    - name: v1alpha1                        # maturity-tagged versions
      served: true
      storage: true                         # exactly ONE per definition
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: ["version", "replicas"]
              properties:
                version: { type: string }
                replicas: { type: integer, minimum: 1 }
                storage:
                  type: object
                  properties:
                    size: { type: string }        # e.g. "100Gi"
            status:
              type: object
              x-kubernetes-preserve-unknown-fields: true
      subresources:
        status: {}               # enables /status subresource writes
        scale:
          specReplicasPath: .spec.replicas
          statusReplicasPath: .status.readyReplicas
      additionalPrinterColumns:
        - name: Replicas
          type: integer
          jsonPath: .spec.replicas
```

Key anatomy points seniors mention:

- **Schema enforcement**: structural schemas give you admission-time validation for free.
- **status subresource**: separates user intent (`spec`) from controller observations (`status`) — writes to `/status` need separate RBAC.
- **Versions**: serve multiple, store one; conversion webhooks translate between them.

### Desired vs Observed — The Core Discipline

```text
spec (user intent)      status (controller truth)
┌──────────────────────────────────────────────┐    ┌──────────────────────┐
│ replicas: 5      │    │ readyReplicas: 3     │
│ version: "16.2"  │    │ currentVersion: 16.1 │
│ storage: 200Gi   │    │ phase: Upgrading     │
└──────────────────────────────────────────────┘    └──────────────────────┘

Reconcile NEVER panics and NEVER assumes ordering:
• any field may be missing (fresh cluster mid-boot)
• children may be deleted by anyone, anytime
• two reconciles may race → everything must be idempotent
• external APIs may fail → return error, retry with backoff
```

### Operator Capability Levels

The community shorthand (OperatorHub / OperatorSDK levels):

| Level | Capability | Example behavior |
| ----- | -------------- | -------------------------------------------------- |
| 1 | Basic install | Create DB pods + service from CR |
| 2 | Upgrades | Rolling version bump with data-dir migration |
| 3 | Full lifecycle | Backup, restore, resize storage online |
| 4 | Insights | Metrics, alerts, topology exported to status |
| 5 | Auto-pilot | Self-healing quorum, auto-tuning, planned failover |

Levels 1-2 are common and valuable; 3+ is where operators genuinely replace senior humans on call.

### ownerReferences & Garbage Collection

Child objects should always point at their owning CR:

```yaml
metadata:
  ownerReferences:
    - apiVersion: db.example.com/v1alpha1
      kind: PostgresCluster
      name: payments-db
      uid: 0f3c...-...            # copied from the parent CR
      controller: true            # exactly one controlling owner
      blockOwnerDeletion: false
```

Consequences worth quoting in interviews:

- Delete the CR → kube garbage collector cascades deletion of all owned children (StatefulSet, PVCs if configured, Services).
- Foreground vs background deletion changes whether children vanish before or after the parent disappears.
- Orphaned children (missing/wrong uid) are the classic bug: recreate children with correct ownership rather than adopting silently.

## Code Examples

### Go Skeleton With controller-runtime

```go
// Reconcile moves the world one step toward spec. Idempotent, level-triggered.
func (r *PostgresClusterReconciler) Reconcile(
    ctx context.Context, req ctrl.Request) (ctrl.Result, error) {

    var cluster dbv1alpha1.PostgresCluster
    if err := r.Get(ctx, req.NamespacedName, &cluster); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err) // deleted: GC handles kids
    }

    // 1. Ensure the child StatefulSet exists and matches spec
    want := desiredStatefulSet(&cluster) // pure function: CR -> object
    if err := ctrl.SetControllerReference(&cluster, want, r.Scheme); err != nil {
        return ctrl.Result{}, err
    }

    op, err := controllerutil.CreateOrUpdate(ctx, r.Client, want,
        func() error { mergeSpecInto(want, &cluster); return nil })
    if err != nil {
        return ctrl.Result{}, err // requeued with backoff automatically
    }
    _ = op // Created / Updated / Unchanged — useful for logs/metrics

    // 2. Mirror observation into status (subresource write)
    sts := &appsv1.StatefulSet{}
    if err := r.Get(ctx, types.NamespacedName{
        Name: want.Name, Namespace: want.Namespace}, sts); err == nil {
        cluster.Status.ReadyReplicas = sts.Status.ReadyReplicas
        if err := r.Status().Update(ctx, &cluster); err != nil {
            return ctrl.Result{}, err
        }
    }

    // 3. Version upgrade gate: block until rollout finishes
    if cluster.Status.CurrentVersion != cluster.Spec.Version {
        return ctrl.Result{RequeueAfter: 15 * time.Second}, nil
    }
    return ctrl.Result{}, nil
}

func (r *PostgresClusterReconciler) SetupWithManager(m ctrl.Manager) error {
    return ctrl.NewControllerManagedBy(m).
        For(&dbv1alpha1.PostgresCluster{}).                 // primary watch
        Owns(&appsv1.StatefulSet{}).                        // child events requeue us
        Complete(r)
}
```

Details that make this production-grade:

- `For(...)` + `Owns(...)`: any change to owned StatefulSets enqueues the parent CR — the loop self-heals after tampering.
- `CreateOrUpdate` centralizes the idempotent create-or-patch decision.
- Returning an error requeues with exponential backoff — errors are control flow, not failures.

### TypeScript Pseudocode Equivalent

```typescript
async function reconcile(req: Request): Promise<Result> {
  const cr = await api.get("postgresclusters", req.ns, req.name);
  if (!cr) return {};                       // gone; GC cleaned children

  const want = buildStatefulSet(cr.spec);   // deterministic desired object
  want.metadata.ownerReferences = [ownerRefTo(cr)];

  const have = await api.get("statefulsets", req.ns, want.metadata.name);

  if (!have) {
    await api.create(want);
  } else if (!matchesDesired(have, want)) { // compare generation/status
    await api.patch(have, strategicMergePatch(want));
  }

  const live = await api.get("statefulsets", req.ns, want.metadata.name);
  await api.patchStatus({
    kind: "PostgresCluster",
    readyReplicas: live?.status?.readyReplicas ?? 0,
    phase: live?.status?.readyReplicas === cr.spec.replicas ? "Ready" : "Provisioning",
  });

  return cr.status.currentVersion !== cr.spec.version
    ? { requeueAfterSeconds: 15 }
    : {};
}

setInterval(() => listAll().forEach(enqueue), RESYNC_PERIOD_MS); // level-trigger safety net
```

## Real-World Use Cases

### 1. cert-manager (Ecosystem Operator)

You declare `Certificate` CRs; the operator orders from ACME providers, renews before expiry, stores results in Secrets, and rotates consumers. Studying its CRDs (`Issuer`, `CertificateRequest`, order chains) is a masterclass in status machines.

### 2. In-House Kafka Topic Provisioner (Level 1-2)

Platform team exposes `KafkaTopic` CRs. A small controller validates config against org policy (retention limits, replication >= 3), creates topics via admin API, and mirrors status back. Developers stop opening tickets; RBAC replaces shared admin creds. This is the sweet spot where operators pay off immediately.

### 3. Database Failover Automation (Level 3-5)

PostgresOperator watches pod liveness and replica roles; on primary loss it runs the promotion runbook ( fencing → promote newest replica → update Service selector → resync old primary as standby). What was a 20-minute page becomes a 60-second automated recovery with an audit trail in events.

### 4. Multi-Cluster Rollout via GitOps

Each fleet cluster runs the same operator; a single committed `RolloutPolicy` CR (canary weights, region gates) drives divergent local actions everywhere. The CR is the interface; operators are the execution layer.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Edge-triggered logic assuming events arrive exactly once | Level-triggered reconcile + periodic resync; treat events as hints |
| Non-idempotent reconcile (append-only side effects) | Every action derived from full desired state; use CreateOrUpdate-style helpers |
| Writing status without the status subresource | Enable `subresources.status`; split RBAC so users cannot fake health |
| Children created without ownerReferences | Always SetControllerReference — else leaks and broken cascades |
| Blocking reconcile on slow external calls (API timeouts inline) | Return `Result{RequeueAfter}` or move long work to jobs; keep loops fast |
| Building an operator for a 3-command workflow | Scripts/CronJobs/plain Deployments first — see decision table below |

## Best Practices

1. **Model intent in spec, truth in status** — never let users write status, never let controllers rewrite spec.
2. **Make the desired-object builder a pure function** (`CR -> Object`) — trivially unit-testable without a cluster (envtest optional).
3. **Watch what you own** (`Owns`) and nothing more; use predicates/filters to keep queues clean.
4. **Version your CRD API from day one** (`v1alpha1`), design conversions early — retrofitting versions onto deployed users hurts.
5. **Ship metrics + events from the controller** — reconcile counts, error rates, and Kubernetes Events are your UX.
6. **Prefer upstream operators over homegrown ones** — cert-manager/Prometheus/Postgres operators are battle-tested; contribute fixes instead of forking.

## When To Write an Operator (vs Scripts)

| Signal | Verdict |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| One-off setup, rarely changes | Shell script / Terraform |
| Periodic maintenance task | CronJob |
| Needs to react to cluster state changes continuously | Controller |
| Runbook steps humans execute repeatedly under stress | Operator (levels 1-3) |
| Multiple teams consume the capability via API | Operator + CRD is the product |
| Logic fits in Helm values + hooks already | Stay with packaging (Helm/Kustomize) — do not add a controller |

Litmus test: if the answer must remain correct *while nobody watches*, across restarts, races, and partial failures, you need a controller; otherwise you need documentation and cron.

## Performance Considerations

| Aspect | Impact | Mitigation |
| ---------------------------------------- | --------------------------------------- | ------------------------------------------------------------------ |
| Requeue storms after API outages | Queue floods on recovery | Rate-limiting workqueues (default); cap concurrency per controller |
| Large informer caches (thousands of CRs) | Memory + startup time | Field/label selectors on caches; partition by namespace |
| Slow external systems inside reconcile | Worker starvation | Async job pattern + status conditions; RequeueAfter pacing |
| Webhook conversion latency | API slowness for all clients of the CRD | Keep conversion cheap; cache certificates |
| Aggressive resync period | Wasted API traffic | Default 10h resync is fine when Owns-watches cover churn |

## Summary

CRDs turn Kubernetes into a platform for building platforms: schema-validated resources served by the apiserver you already operate. Controllers implement the universal loop — observe, diff, act idempotently, record status, repeat — and operators encode application-specific runbooks into that loop. Owner references wire child lifetimes to parents; garbage collection makes deletion declarative. Choose the pattern deliberately: scripts for one-offs, CronJobs for schedules, controllers for continuous correctness, operators when day-2 automation justifies building and maintaining a piece of software. OLM and OperatorHub exist because the industry converged on this being the right way to ship operational software into clusters.

```text
CRDS / OPERATORS CHEAT SHEET
════════════════════════════

CRD ANATOMY:
names.plural.kind · group · scope(Namespaced|Cluster)
versions[]: served/storage(one!) + openAPIV3Schema
subresources: status (split RBAC) · scale
printer columns → kubectl get output

RECONCILE DISCIPLINE:
• observe spec vs live → act idempotently → update status
• level-triggered: events are HINTS, resync is the net
• errors = requeue w/ backoff (control flow, not failure)
• desired-builder = pure function (unit-test offline)

OWNERSHIP:
child.ownerReferences = [{kind,name,uid,controller:true}]
delete parent → GC cascade · wrong uid → orphaned leak

OPERATOR LEVELS:
1 install · 2 upgrade · 3 full lifecycle (backup/restore)
4 insights · 5 autopilot (self-heal/tune)

SKELETON (controller-runtime):
For(CR).Owns(StatefulSet).Complete(r)
CreateOrUpdate(ctx, client, want, mutateFn)
SetControllerReference(parent, child, scheme)

WHEN TO BUILD:
continuous reaction needed → controller
stress-tested runbook repeated → operator (L1-3)
multi-team API surface → CRD as product
one-off / scheduled / helm-enough → script/cron/chart
```

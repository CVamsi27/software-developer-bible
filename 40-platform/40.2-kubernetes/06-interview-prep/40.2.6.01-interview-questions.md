### Question 1: What is Kubernetes and why is it used?

**Answer:**

Kubernetes (K8s) is an open-source container orchestration platform that automates deployment, scaling, and management of containerized applications.

**Key Benefits:**

- **Self-healing**: Restarts failed containers, replaces and reschedules containers
- **Horizontal scaling**: Scale up/down automatically based on metrics
- **Service discovery**: DNS-based service discovery and load balancing
- **Automated rollouts**: Availability-controlled rolling updates when capacity, readiness, and application compatibility permit
- **Storage orchestration**: Mount storage systems automatically
- **Secret management**: Manage sensitive configuration

---

### Question 2: What is a Pod in Kubernetes?

**Answer:**

A Pod is the smallest deployable unit in Kubernetes. It represents a single instance of a running process and can contain one or more containers that share:

- Network namespace (same IP address)
- Storage volumes
- Optional process-namespace sharing when `shareProcessNamespace` is enabled

**When to use multi-container Pods:**

- Sidecar pattern (log shipping, proxies)
- Ambassador pattern (service proxies)
- Adapter pattern (output formatting)

### Question 3: Explain the difference between a Deployment and a StatefulSet.

**Answer:**

| Aspect | Deployment | StatefulSet |
| ---------- | -------------- | ---------------------- |
| Use case | Stateless apps | Stateful apps |
| Pod naming | Random | Ordered (pod-0, pod-1) |
| Scaling | Unordered | Ordered |
| Network | Any order | Stable DNS |
| Storage | Shared | Per-Pod persistent |
| Updates | Rolling | Ordered |

The naming is the contract: StatefulSet gives each pod a stable identity — a replacement for pod-0 keeps its ordinal identity and claim association when the configured storage and headless Service support that contract — which is exactly what replication primaries, quorum databases, and clustered brokers require. Deployments treat pods as interchangeable: cheaper to scale and roll, but any state must live outside the pod, which is why stateless services default there.

### Question 4: What are Kubernetes Services and their types?

**Answer:**

Services provide stable networking for Pods.

| Type | Description | Use Case |
| ------------ | ----------------- | -------------------------- |
| ClusterIP | Internal only | Default, internal services |
| NodePort | Expose on node IP | Development, testing |
| LoadBalancer | Cloud LB | Production external access |
| ExternalName | CNAME alias | External service reference |

The types form a discovery ladder: ClusterIP gives a stable virtual IP implemented by the cluster networking data plane. NodePort exposes a configured port on permitted node addresses. LoadBalancer asks a supporting provider/controller for external connectivity; some implementations use NodePorts while others route directly to Pods. ExternalName is the odd one — a pure DNS CNAME with no proxying — used to alias external services behind a stable in-cluster name.

### Question 5: How does Kubernetes handle service discovery?

**Answer:**

Kubernetes uses DNS for service discovery:

```text
Service Name: myservice
Namespace: production
FQDN: myservice.production.svc.cluster.local

```

**Methods:**

1. **DNS**: CoreDNS resolves service names to Cluster IPs

2. **Environment variables**: Injected into Pods at creation

3. **Headless Services**: Return Pod IPs directly

The mechanism: CoreDNS watches the API server and programs DNS records for every Service (and pod-ready headless Service). The FQDN encodes hierarchy — `service.namespace.svc.cluster-domain` — the example assumes the default `cluster.local` domain; resolver search paths make a bare Service name usually refer to the current namespace. Senior gotchas: the `ndots:5` default in pod resolv.conf causes external lookups to try cluster suffixes first (lookup storms under load — set ndots or use FQDNs for external calls), and env-var discovery is create-time only — it goes stale and is legacy, not a mechanism to design on.

### Question 6: What is the difference between a ConfigMap and a Secret?

**Answer:**

| Aspect | ConfigMap | Secret |
| --------------- | -------------------------- | ------------------------------------------------------------------ |
| Data type | Non-sensitive | Sensitive |
| Encoding | Plain text | Base64 |
| Confidentiality | Not a secret-data boundary | Base64 is encoding; encryption at rest must be configured/verified |
| Use case | App config | Passwords, tokens |

The operational reality behind the table: Secrets are only base64-*encoded*, not encrypted — anyone who can read the object (or an etcd backup) gets the value, so real sensitivity needs etcd encryption-at-rest, tight RBAC, and usually an external secret manager. The honest distinction is intent and access control: a Secret is the signal to lock down, rotate, and audit differently.

### Question 7: Explain HPA (Horizontal Pod Autoscaler).

**Answer:**

HPA writes a workload's requested replica count based on metrics. This manifest assumes an existing `myapp` Deployment with appropriate CPU requests and a working resource metrics API:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:

    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

```

**Metrics used:**

- CPU utilization
- Memory utilization
- Custom metrics (requests/second)
- External metrics (queue length)

Mechanically the HPA is a control loop reading metrics (resource metrics from metrics-server, custom via the metrics APIs) and computing `desiredReplicas = ceil(currentReplicas * currentMetricValue / desiredMetricValue)`. Senior depth: stabilization windows and scaling policies prevent thrash — without them traffic oscillation makes replicas flap; Replica bounds apply; scale-to-zero support depends on metric type, feature gates, and controller configuration. KEDA is a common choice for event-driven activation. Know the division of labor: HPA scales pods, VPA right-sizes requests, Cluster Autoscaler adds nodes — they compose, but VPA changing requests also changes resource-utilization denominators seen by HPA. Coordinate resource ownership or choose an independent work metric. For three replicas at 80% against a 50% target, the basic count is five; scheduling and readiness still determine useful capacity. Missing metric errors can prevent downscale even when another metric suggests it.

### Question 8: What are liveness and readiness probes?

**Answer:**

| Probe | Purpose | On Failure |
| --------- | ------------------------------ | ------------------------------------------------------------ |
| Liveness | Is container alive? | Restart container |
| Readiness | Can container receive traffic? | Remove from Service |
| Startup | Is initialization complete? | Repeats until success; threshold failure stops the container |

**Probe Handlers:**

- `exec`: Run command
- `httpGet`: HTTP request
- `tcpSocket`: TCP connection
- `gRPC`: gRPC health check

The failure actions are the design: a liveness failure kills the container (the restart policy owns recovery), while a readiness failure only withdraws the pod from Service endpoints — crucial during deploys, so a slow-warming pod stops receiving traffic without being killed mid-startup. The startup probe gates the other two, preventing slow-booting apps from being liveness-killed before they finish initializing.

### Question 9: How do you manage secrets in Kubernetes?

**Answer:**

Assume `./db-password.txt` is a protected local file created by your secret-handling procedure. The command reads it without putting the value in command arguments; do not commit the file.

```bash
kubectl create secret generic db-creds --from-file=password=./db-password.txt
```

This fragment belongs in the application's container definition in the same namespace:

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-creds
        key: password
```

**Best Practices:**

- Use external secret stores (Vault)
- Enable encryption at rest
- Use RBAC to restrict access
- Rotate secrets regularly

The critical fact: base64 is encoding, not encryption — without `EncryptionConfiguration` on kube-apiserver, secrets sit in etcd plaintext on the control-plane disks. Senior posture: enable etcd encryption at rest, restrict with RBAC on the secrets resource (not cluster-wide read), avoid env vars where the values leak into crash dumps and logs, and treat external stores (Vault, cloud secret managers) synced via External Secrets Operator or CSI drivers as the real answer — the chosen integration may mount data directly or copy it into Kubernetes Secrets. Rotation at the source does not prove running applications refreshed their credentials; verify synchronization, consumption, and access boundaries.

### Question 10: What is an Ingress in Kubernetes?

**Answer:**

Ingress manages external HTTP/HTTPS access to Services:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
spec:
  tls:

    - hosts:
        - myapp.example.com
      secretName: tls-secret
  rules:

    - host: myapp.example.com
      http:
        paths:

          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80

```

**Features:**

- TLS termination
- Host-based routing
- Path-based routing
- Controller-specific rate limiting where supported

Ingress is a specification, not infrastructure — an Ingress controller (NGINX, Traefik, cloud) must implement it, which is why annotations differ per controller. Depth: TLS termination with cert-manager automating issuance/renewal is the day-one setup; the controller-specific canary annotations are powerful but non-portable. The forward-looking answer is Gateway API: role-separated (platform team owns Gateways, teams own HTTPRoutes), expressive (header matching, weighting are core, not annotations), and vendor-portable — name it and you sound current.

### Question 11: What is the difference between `kubectl apply` and `kubectl create`?

**Answer:**

| Command | Behavior |
| -------- | --------------------------------------- |
| `create` | Creates a new resource; fails if exists |
| `apply` | Creates or updates idempotently |

```bash
# Creates new resource
kubectl create -f pod.yaml

# Creates or updates
kubectl apply -f pod.yaml

```

Client-side apply compares the submitted manifest, its last-applied annotation, and live state. It can remove fields previously managed in that annotation when omitted from the new manifest; fields outside that ownership can remain. Server-side apply tracks field managers and can report ownership conflicts. Choose a consistent management path and investigate conflicts rather than treating every manual edit or omitted field identically. Creation, defaulting, admission mutation, and controller reconciliation can all change the eventual object; repeating apply does not guarantee the application has reached readiness.

### Question 12: Explain the Kubernetes control plane components.

**Answer:**


Each component owns one decision: the API server is the only writer (validation and authz; everything else watches it), etcd is the source of truth (quorum buys consistency), the scheduler *chooses* nodes but never starts anything, and controller managers drive current state toward desired state in reconciliation loops. That separation — decide, store, act — is what makes the control plane restartable and auditable.
```text
clients/controllers -> API server <-> etcd
                              |
                  watch objects and submit changes
                     /                    \
                 scheduler            controller managers
                chooses node          reconcile desired state
                     \                    /
                       API updates observed by kubelet
                                starts containers
```

| Component | Responsibility |
| ------------------------ | --------------------------------------------- |
| API Server | RESTful API, authentication, authorization |
| etcd | Distributed key-value store for cluster state |
| Scheduler | Assigns Pods to nodes |
| Controller Manager | Maintains desired state |
| Cloud Controller Manager | Cloud provider integration |

### Question 13: What are Persistent Volumes and PVCs?

**Answer:**

**PersistentVolume (PV):** Cluster-level storage resource.

**PersistentVolumeClaim (PVC):** Request for storage by a Pod.

```yaml
# PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:

    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi

```

This fragment belongs under an existing Pod's `spec`; add a matching `volumeMounts` entry to the container. The claim must bind to usable storage before the workload can run.

```yaml
volumes:

  - name: data
    persistentVolumeClaim:
      claimName: my-pvc

```

The architecture point: PVCs decouple 'how much storage a workload needs' from 'which disk provides it' — pods claim via PVC, the cluster binds claims to PVs, a configured StorageClass and provisioner can automate dynamic provisioning; static PVs still have valid uses. Depth: access modes are about node attachment semantics — RWO is writable from one node at a time, potentially by multiple Pods on that node; ReadWriteOncePod is a different single-Pod restriction (why stateful replicas on different nodes can't share one RWO volume), RWX needs a shared filesystem backend; reclaim policy Retain vs Delete decides whether data survives the claim — a deletion-protection decision, not a default to click past.

### Question 14: How do you perform rolling updates in Kubernetes?

**Answer:**

This strategy fragment belongs in an existing Deployment; it is not a complete Deployment manifest.

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

```

**Commands:**

```bash
# Update image
kubectl set image deployment/myapp myapp=myapp:2.0

# Monitor rollout
kubectl rollout status deployment/myapp

# Rollback
kubectl rollout undo deployment/myapp

```

Mechanism ties back to the Deployment model: a template change creates a new ReplicaSet; maxSurge/maxUnavailable bound how fast old scales down and new up, and readiness probes govern normal Service endpoint eligibility. Direct Pod traffic, special Service settings, and in-flight connections still need separate handling. Senior details: `progressDeadlineSeconds` reports `ProgressDeadlineExceeded` for a stalled rollout (default 600s); the Deployment controller keeps reconciling and does not automatically roll back, `kubectl rollout undo` scales the previous RS back, and database migrations must be backward-compatible because both versions serve simultaneously during the window.

### Question 15: What is a DaemonSet?

**Answer:**

A DaemonSet ensures a Pod runs on all (or specific) nodes.

**Use Cases:**

- Log collectors (Fluentd, Filebeat)
- Monitoring agents (Prometheus Node Exporter)
- Network plugins (Calico, Weave)

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
spec:
  selector:
    matchLabels:
      app: log-collector
  template:
    metadata:
      labels:
        app: log-collector
    spec:
      containers:

        - name: fluentd
          image: fluentd:latest

```

DaemonSet is the answer to 'run one pod per node' — node agents, log shippers, CNI plugins — the DaemonSet controller creates a Pod per eligible node and the scheduler still assigns those Pods under their placement rules. Depth: taints matter — nodes need tolerations matched or the agent misses nodes (the classic 'why is this node unmonitored' incident); RollingUpdate can configure `maxUnavailable` and `maxSurge`; OnDelete leaves replacement until manual Pod deletion. Whether two versions may overlap is an application constraint. The interview follow-up: DaemonSet vs hostNetwork/hostPort tradeoffs for network-critical agents, and why these pods usually get PriorityClass so eviction doesn't kill observability first.

### Question 16: What is the difference between a Job and a CronJob?

**Answer:**

| Aspect | Job | CronJob |
| --------- | --------------------------------------- | --------------------------------------------------------------- |
| Execution | One-time | Scheduled |
| Retry | Job/Pod policies govern failed attempts | Created Jobs use those same policies; schedule creates new Jobs |
| Use case | Batch processing | Recurring tasks |


The semantics that matter operationally: a Job's pods must *complete* (restartPolicy OnFailure or Never — never Always), and `completions` plus `parallelism` scale the batch. CronJobs create Jobs from a template on a schedule; schedules and retries do not guarantee exactly-once execution. Make external side effects idempotent. They can miss ticks — `startingDeadlineSeconds` decides whether a missed window runs late or is skipped, the classic surprise after a controller-manager outage.
```yaml
# CronJob
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:

            - name: backup
              image: backup:latest
          restartPolicy: OnFailure

```

### Question 18: What is a Namespace in Kubernetes?

**Answer:**

Namespaces provide virtual cluster partitioning within a physical cluster.

```bash
# Create namespace
kubectl create namespace production

# Set context
kubectl config set-context --current --namespace=production

# List resources in namespace
kubectl get pods -n production

```

**Use Cases:**

- Environment isolation (dev, staging, prod)
- Resource quotas per team
- RBAC boundaries

Namespaces scope names and policies; creating one does not establish tenant isolation. RBAC controls API permissions, an enforcing network implementation applies NetworkPolicy, and quotas constrain admitted allocations/counts. Runtime workload privileges and shared-node risks need separate controls. Choose namespace ownership so those policies are reviewable. Reserve elevated PriorityClasses for the workloads that require them and restrict who can use them; priority influences scheduling/preemption but does not guarantee protection from node failure, pressure eviction or insufficient capacity.

### Question 19: What are Taints and Tolerations?

**Answer:**

**Taints** repel Pods from nodes.
**Tolerations** allow Pods to be scheduled on tainted nodes.

```bash
# Add taint to node
kubectl taint nodes node1 key=value:NoSchedule

# Toleration in Pod
tolerations:

  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"

```

The mental model: taints mark nodes as 'keep out unless you tolerate this' — the opposite of affinity, which attracts. Effects matter: NoSchedule blocks new pods, PreferNoSchedule is best-effort, NoExecute can evict running Pods that do not tolerate the taint; tolerationSeconds controls how long they tolerate it, while graceful termination is a separate contract. Senior use: dedicated node pools via taints (GPU, compliance-isolated, spot workloads), plus node-condition taints such as not-ready and unreachable explaining why pods suddenly reschedule during node trouble.

### Question 20: How do you troubleshoot a CrashLoopBackOff?

**Answer:**

```bash
# Check pod status
kubectl get pods
kubectl describe pod <pod-name>

# Check logs
kubectl logs <pod-name>
kubectl logs --previous <pod-name>

# Common causes:
# 1. Application crash
# 2. Missing environment variables
# 3. Failed health checks
# 4. Insufficient resources
# 5. Incorrect command/args

```

The systematic loop: `describe pod` first — Events show the restart reason and backoff timer; `logs --previous` shows the *dying* instance's output, which is where the actual error lives. Then classify: exit 137 means termination by SIGKILL; check the container's reason and node events before attributing it to an out-of-memory kill, exit 1 with a stack trace is an app bug, and a pod that runs then gets killed on schedule is a liveness probe misfire — probe too aggressive or wrong port. Restart backoff depends on kubelet configuration and feature gates. CrashLoopBackOff describes repeated restarts; previous logs, termination state, events, and node pressure provide the evidence for a diagnosis.

### Question 21: What is the difference between `docker-compose` and Kubernetes?

**Answer:**

| Aspect | Docker Compose | Kubernetes |
| ------------ | -------------- | ---------- |
| Scale | Single host | Multi-host |
| Complexity | Simple | Complex |
| Self-healing | Limited | Full |
| Auto-scaling | No | Yes |
| Use case | Development | Production |

The accurate mental model: Compose declares a host's containers and can use restart policies for process recovery. ### Question 22: What is Helm and why use it?

**Answer:**

Helm is the package manager for Kubernetes.

**Benefits:**

- Packages multiple manifests into charts
- Manages releases and rollbacks
- Configurable via values files
- Version control for deployments

```bash
# Install chart
helm install myrelease ./mychart -f values.yaml

# Upgrade
helm upgrade myrelease ./mychart -f new-values.yaml

# Rollback
helm rollback myrelease 1

```

Beyond 'package manager': a Helm release is a tracked installation instance stored as a secret in-cluster — that release record is what makes upgrade, rollback, and `helm diff` possible, and what makes two installs of one chart two independent releases. Senior depth: hooks and `helm test` encode post-install health checks; `helm lint` + `helm template` and an installed diff plugin in CI catch render breakage before the cluster does; and the honest tradeoff — template logic in YAML has a maintenance cliff, which is why Kustomize-style patching appeals to teams that don't need parameterized charts.

### Question 23: How do you implement network policies?

**Answer:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:

    - Ingress
  ingress:

    - from:
        - podSelector:
            matchLabels:
              app: api
      ports:

        - port: 8080

```

A policy selecting web Pods isolates their ingress and permits only matching API Pods on the stated port, together with any other matching policies' allows. A select-all default-deny also isolates otherwise unselected Pods; order does not subtract prior grants. The source's egress and destination's ingress must both permit the connection. Two production gotchas: the CNI must implement NetworkPolicy (Flannel silently ignores them — verify with a two-pod denial test), and egress policies break DNS immediately unless you allow UDP/TCP 53 to CoreDNS — every 'my policy locked the whole namespace' story is that story.

### Question 24: What is RBAC in Kubernetes?

**Answer:**

Role-Based Access Control controls who can do what.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader
  namespace: production
subjects:
  - kind: User
    name: jane
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

The model: a Role grants verbs on resources within one namespace; ClusterRole spans the cluster (or is bound per-namespace via RoleBinding — the reusable-role pattern). Depth: grant to ServiceAccounts, not users, in automation (least privilege per workload — this is what OIDC-federated CI assumes); `kubectl auth can-i get pods -n ns --as=system:serviceaccount:ns:sa` answers 'can it actually do this' without guessing; and aggregated ClusterRoles let platform teams compose permissions without duplicating rules. Watch the wildcard verbs — `*` on resources is a standing audit finding.

### Question 25: How do you handle multi-cluster management?

**Answer:**

Begin with requirements: independent failure domains, regulatory location, or separate trust/operations ownership. A central configuration source should produce per-cluster desired state; it does not create cross-cluster networking or recover a failed cluster's data by itself.

**Strategies:**

- GitOps with Argo CD
- Service mesh (Istio, Linkerd)
- Centralized monitoring

The senior answer starts with *why* — most orgs need fewer clusters than they think: one cluster with namespace discipline is operationally cheaper than three. Real drivers for multi-cluster: blast-radius isolation, data residency, and cloud/vendor hedging. Then the design: GitOps (Argo CD app-of-apps or Flux) makes one Git source deploy to N clusters with per-cluster overlays — config drift between clusters becomes a PR, not a divergence; a service mesh with multi-cluster federation handles cross-cluster mTLS/traffic if services must talk. Choose maintained tooling after deciding which configuration, identity, traffic, and state are shared. A second cluster is not automatically a failover plan.

### Question 26: What are init containers?

**Answer:**

Init containers run before main containers and must complete successfully.

```yaml
spec:
  initContainers:

    - name: init-db
      image: busybox
      command: ['sh', '-c', 'until nslookup db; do sleep 2; done']
  containers:

    - name: app
      image: myapp:1.0

```

**Use Cases:**

- Wait for dependencies
- Database migrations
- Configuration setup

Init containers run to completion *before* app containers start, sequentially — the mechanism for bounded setup before application start. This command checks DNS resolution of `db`, not database connection readiness, and it can wait indefinitely. The application still needs runtime dependency recovery. Depth: for ordinary init containers, scheduling accounts for the larger of the peak init request and the app-container sum, plus Pod overhead when configured; restartable sidecars also consume resources while later containers run; a failing init container restarts with backoff and blocks app start (visible as Init:CrashLoopBackOff). The modern twist: native sidecars (stable in Kubernetes 1.33; check older cluster support) — an init container with `restartPolicy: Always` runs for the pod's whole lifetime, making the sidecar pattern first-class instead of the old ambassador hacks.

### Question 27: How do you monitor Kubernetes?

**Answer:**

**Components:**

- **Metrics Server**: Basic CPU/memory metrics
- **Prometheus**: Metrics collection
- **Grafana**: Visualization
- **Jaeger**: Distributed tracing
- **ELK Stack**: Log aggregation

```bash
# Check resource usage
kubectl top pods
kubectl top nodes

# View events
kubectl get events --sort-by=.metadata.creationTimestamp

```

The useful structure is what to measure per layer: kubelet/cAdvisor gives per-pod resource signals, kube-state-metrics gives object state (desired vs available replicas, pending pods), and the node agent completes the picture — Prometheus scrapes all three. Senior points: alert on symptoms (latency, error rate) not causes (CPU) — CPU alarms page people on healthy-but-busy systems; `kubectl get events` sorted by timestamp is the first triage tool and too many people don't know it; and the USE/RED methods (utilization-saturation-errors per resource, rate-errors-duration per service) structure dashboards so they answer questions.

### Question 28: What is a Pod Disruption Budget?

**Answer:**

PDB limits voluntary disruptions during node maintenance.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp

```

The precise scope is voluntary eviction through the eviction API. With three healthy selected replicas and `minAvailable: 2`, one healthy eviction can proceed; another waits for health to return. A node failure cannot be prevented, and HPA replica reductions, direct deletes, and workload rolling updates follow other paths. Percentage thresholds round up and need careful small-population checks. `kubectl drain` uses eviction admission by default when supported; there is no `--respect-pdbs` flag. If drain stalls, inspect budget status and whether replacements can schedule rather than bypassing the policy.

### Question 29: How do you implement GitOps with Kubernetes?

**Answer:**

**Tools:**

- **Argo CD**: GitOps continuous delivery
- **Flux**: GitOps toolkit

**Workflow:**

1. Store manifests in Git

2. Argo CD watches repository

3. Automatically syncs changes

4. Provides rollback via Git

The cluster-side mechanics: an operator (Argo CD or Flux) watches Git, applies manifests, and *continuously reconciles* — drift from a hand-edit can be detected; automatic reversion requires the controller's self-heal/reconciliation policy, which is the property that separates GitOps from 'CI that runs kubectl'. Depth: app-of-apps scales the pattern (one root Application owns per-team/per-env Applications — platform teams onboard a service by merging a directory); sync waves order databases before apps; promotion between environments is a PR changing an image tag in a per-env overlay — the PR is the audit trail, and a Git revert changes desired configuration; it does not reverse data migrations or external side effects.

### Question 30: What are the best practices for Kubernetes security?

**Answer:**

1. **RBAC**: Restrict access with roles

2. **Network Policies**: Limit pod-to-pod communication

3. **Pod Security Standards**: Run as non-root

4. **Image scanning**: Use Trivy/Clair

5. **Secrets management**: External secret stores

6. **Audit logging**: Monitor API access

7. **Resource quotas**: Bound admitted namespace allocations and object counts; also plan runtime limits and physical capacity

8. **Regular updates**: Keep K8s and images updated

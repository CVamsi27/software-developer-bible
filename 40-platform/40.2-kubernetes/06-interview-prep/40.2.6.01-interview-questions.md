# Kubernetes Interview Questions

## First Principles

Use the links to reconstruct the answer, not memorize a slogan. For each question, state the assumptions, explain the mechanism, name a failure mode and describe how you would verify the behavior.

## 30 Kubernetes Questions: Mechanisms and Trade-offs

---

### Question 1: What is Kubernetes and why is it used?

**Answer:**

Kubernetes is an open-source system for declaring, scheduling and reconciling containerized workloads across a cluster. Controllers maintain declared state, while the scheduler places Pods and kubelets run them on nodes.

**Key Benefits:**

- **Workload recovery**: Controllers can replace failed Pods, and kubelets restart containers according to each Pod's restart policy
- **Horizontal scaling**: Scale up and down automatically based on metrics
- **Service discovery**: Domain Name System (DNS)-based service discovery and load balancing
- **Automated rollouts**: Availability-controlled rolling updates when capacity, readiness, and application compatibility permit
- **Storage orchestration**: Mount storage systems automatically
- **Secret management**: Manage sensitive configuration

---

### Question 2: What is a Pod in Kubernetes?

**Answer:**

A Pod is the smallest unit Kubernetes schedules. Its containers share one placement and network identity; they share files only through volumes mounted into each container. Process-namespace sharing is separately configured.

Use multiple containers when a helper must be colocated and share the Pod lifecycle, such as a proxy or a log reader. Independent application replicas belong in separate Pods so the scheduler can place them independently.

### Question 3: Explain the difference between a Deployment and a StatefulSet.

**Answer:**

| Aspect | Deployment | StatefulSet |
| ------------ | -------------------------------- | -------------------------------------------------------------------------------------------- |
| Use case | Stateless apps | Stateful apps |
| Pod identity | Names change with replacement | Stable ordinal names (for example, `db-0`) |
| Scaling | Interchangeable replica count | `OrderedReady` by default; `Parallel` changes scale-operation ordering, not update strategy |
| Network | Pod identity can change | Stable ordinal names; a governing headless Service exposes per-Pod DNS |
| Storage | Can mount persistent volumes | Per-ordinal claims when `volumeClaimTemplates` is configured; claims are retained by default |
| Updates | Deployment rollout strategy | StatefulSet `RollingUpdate` or `OnDelete`; readiness does not prove quorum or replication |

StatefulSet gives each Pod a stable ordinal and network identity; a replacement can reuse its ordinal's claim when `volumeClaimTemplates` and retention policy are configured. The controller does not make an application stateful or provide database replication. Deployments treat replicas as interchangeable and are usually simpler when persistent identity belongs in an external data service.

### Question 4: What are Kubernetes Services and their types?

**Answer:**

Services provide stable networking for Pods.

| Type | Description | Use Case |
| -------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `ClusterIP` | Internal only | Default, internal services |
| `NodePort` | Exposes a configured port through permitted node addresses | Intentional edge exposure or an implementation building on NodePorts |
| `LoadBalancer` | Requests an external load balancer from a supporting provider or controller | External connectivity when that implementation is installed |
| `ExternalName` | CNAME alias | External service reference |

The types form a discovery ladder: `ClusterIP` gives a stable virtual Internet Protocol (IP) implemented by the cluster networking data plane. `NodePort` exposes a configured port on permitted node addresses. `LoadBalancer` asks a supporting provider or controller for external connectivity; some implementations use NodePorts while others route directly to Pods.

`ExternalName` is the odd one — a pure DNS `CNAME` with no proxying — used to alias external services behind a stable in-cluster name.

### Question 5: How does Kubernetes handle service discovery?

**Answer:**

Kubernetes uses DNS for service discovery:

```text
Service Name: myservice
Namespace: production
FQDN: myservice.production.svc.cluster.local
```

**Methods:**

1. **DNS**: CoreDNS resolves service names to Cluster IPs

2. **Environment variables**: Injected into Pods at creation

3. **Headless Services**: Return Pod IPs directly

The Kubernetes DNS plugin answers from Service and Endpoint data; exact records depend on the Service type and readiness policy. The Fully Qualified Domain Name (FQDN) is `service.namespace.svc.<cluster-domain>`; `cluster.local` is a common default, not a guarantee.

Resolver search paths make a short Service name resolve within the Pod's namespace. `ndots:5` is a common Pod resolver setting, but cluster and Pod DNS configuration can change it; high-`ndots` search expansion can multiply external lookups. Service environment variables are fixed when a Pod is created, so DNS is generally the better choice for dynamic discovery.

### Question 6: What is the difference between a ConfigMap and a Secret?

**Answer:**

| Aspect | ConfigMap | Secret |
| --------------- | -------------------------- | ---------------------------------------------------------------------- |
| Data type | Non-sensitive | Sensitive |
| Encoding | Plain text | Base64 |
| Confidentiality | Not a secret-data boundary | Base64 is encoding; encryption at rest must be configured and verified |
| Use case | App config | Passwords, tokens |

The operational reality behind the table: Secrets are only base64-*encoded*, not encrypted — anyone who can read the object (or an `etcd` backup) gets the value, so real sensitivity needs `etcd` encryption-at-rest, tight Role-Based Access Control (RBAC), and usually an external secret manager. The honest distinction is intent and access control: a Secret is the signal to lock down, rotate, and audit differently.

### Question 7: Explain HPA (Horizontal Pod Autoscaler).

**Answer:**

HPA writes a workload's requested replica count based on metrics. This manifest assumes an existing `myapp` Deployment with appropriate Central Processing Unit (CPU) requests and a working resource metrics Application Programming Interface (API):

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

**Metrics used:**

- CPU utilization
- Memory utilization
- Custom metrics (requests per second)
- External metrics (queue length)

Mechanically, the HPA is a control loop reading metrics (resource metrics from Metrics Server, custom metrics via the metrics APIs) and computing `desiredReplicas = ceil(currentReplicas * currentMetricValue / desiredMetricValue)`. Stabilization windows and scaling policies prevent thrashing — without them, traffic oscillation makes replicas flap. Replica bounds still apply, and scale-to-zero support depends on metric type, feature gates, and controller configuration.

Kubernetes Event-driven Autoscaling (KEDA) is a common choice for event-driven activation. Know the division of labor: HPA scales Pods, Vertical Pod Autoscaler (VPA) right-sizes requests, and Cluster Autoscaler adds nodes. They compose, but VPA changing requests also changes the resource-utilization denominators seen by HPA, so coordinate resource ownership or choose an independent work metric.

For three replicas at 80% against a 50% target, the basic count is five; scheduling and readiness still determine useful capacity. Missing metric errors can prevent downscaling even when another metric suggests it. In Kubernetes 1.37, scale-to-zero is beta and enabled by default, requiring an object or external metric plus the `HPAScaleToZero` gate on both the API server and controller manager; CPU and memory cannot wake a zero-replica workload. The `ScaledToZero` condition distinguishes an HPA-owned zero state from a manual pause.

### Question 8: What are liveness and readiness probes?

**Answer:**

| Probe | Purpose | On Failure |
| --------- | -------------------------------- | -------------------------------------------------------------------------------------------- |
| Liveness | Can the container make progress? | Kubelet terminates it; the Pod restart policy governs what happens next |
| Readiness | Can container receive traffic? | Remove from Service |
| Startup | Has initialization completed? | Repeats until success; threshold failure terminates the container and restart policy applies |

**Probe Handlers:**

- `exec`: Run command
- `httpGet`: HTTP request
- `tcpSocket`: TCP connection
- `gRPC`: gRPC health check

The failure actions are the design: a liveness failure kills the container (the restart policy owns recovery), while a readiness failure only withdraws the Pod from Service endpoints — crucial during deploys, so a slow-warming Pod stops receiving traffic without being killed mid-startup.

The startup probe repeats until success or its failure threshold, then stops for that container instance and enables liveness and readiness checks. Readiness failure removes normal Service eligibility but does not stop the process or cancel in-flight requests; a liveness check should target a fault that a restart can repair.

### Question 9: How do you manage secrets in Kubernetes?

**Answer:**

Assume `./db-password.txt` is a protected local file created by your secret-handling procedure. The command reads it without putting the value in command arguments; do not commit the file.

```bash
kubectl create secret generic db-creds --from-file=password=./db-password.txt
```

This fragment belongs in the application's container definition in the same namespace:

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-creds
        key: password
```

**Best Practices:**

- Use external secret stores (Vault)
- Enable encryption at rest
- Use RBAC to restrict access
- Rotate secrets regularly

The critical fact: base64 is encoding, not encryption — without `EncryptionConfiguration` on `kube-apiserver`, secrets sit in `etcd` plaintext on the control-plane disks. Senior posture: enable `etcd` encryption at rest, restrict with RBAC on the `secrets` resource (not cluster-wide read), avoid environment variables where values leak into crash dumps and logs, and treat external stores (Vault, cloud secret managers) synced via External Secrets Operator or Container Storage Interface (CSI) drivers as the real answer — the chosen integration may mount data directly or copy it into Kubernetes Secrets.

Rotation at the source does not prove running applications refreshed their credentials; verify synchronization, consumption, and access boundaries.

### Question 10: What is an Ingress in Kubernetes?

**Answer:**

Ingress manages external Hypertext Transfer Protocol (HTTP) and HTTPS access to Services:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
spec:
  tls:
    - hosts:
        - myapp.example.com
      secretName: tls-secret
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
```

**Features:**

- Transport Layer Security (TLS) termination
- Host-based routing
- Path-based routing
- Controller-specific rate limiting where supported

Ingress is an API object, not a data plane; an installed controller must implement it, and annotations remain implementation-specific. The community `ingress-nginx` controller is retired, so check the support status of any controller before a new deployment. Gateway API provides role-oriented resources such as `Gateway` and `HTTPRoute` and standardizes more routing features; implementation support still varies. Choose a maintained controller and verify its conformance and feature support.

### Question 11: What is the difference between `kubectl apply` and `kubectl create`?

**Answer:**

| Command | Behavior |
| -------- | --------------------------------------- |
| `create` | Creates a new resource; fails if exists |
| `apply` | Creates or updates idempotently |

```bash
# Creates new resource
kubectl create -f pod.yaml

# Creates or updates
kubectl apply -f pod.yaml
```

Client-side apply compares the submitted manifest, its last-applied annotation, and live state. It can remove fields previously managed in that annotation when omitted from the new manifest; fields outside that ownership can remain. Server-side apply tracks field managers and can report ownership conflicts.

Choose a consistent management path and investigate conflicts rather than treating every manual edit or omitted field identically. Creation, defaulting, admission mutation, and controller reconciliation can all change the eventual object; repeating `apply` does not guarantee the application has reached readiness.

### Question 12: Explain the Kubernetes control plane components.

**Answer:**

Normal Kubernetes API writes pass through the API server, which authenticates, authorizes, and validates requests before persisting state in `etcd`. `etcd` uses quorum consensus; loss of quorum impairs writes. The scheduler assigns eligible nodes to Pods but does not start containers. Controllers watch API objects and submit changes toward desired state, while kubelets on nodes start containers for assigned Pods.

```text
clients/controllers -> API server <-> etcd
                              |
                  watch objects and submit changes
                     /                    \
                 scheduler            controller managers
                chooses node          reconcile desired state
                     \                    /
                       API updates observed by kubelet
                                starts containers
```

| Component | Responsibility |
| ------------------------ | --------------------------------------------- |
| API Server | RESTful API, authentication, authorization |
| `etcd` | Distributed key-value store for cluster state |
| Scheduler | Assigns Pods to nodes |
| Controller Manager | Maintains desired state |
| Cloud Controller Manager | Cloud provider integration |

### Question 13: What are Persistent Volumes and PVCs?

**Answer:**

**PersistentVolume (PV):** Cluster-level storage resource.

**PersistentVolumeClaim (PVC):** Request for storage by a Pod.

```yaml
# PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

This fragment belongs under an existing Pod's `spec`; add a matching `volumeMounts` entry to the container. The claim must bind to usable storage before the workload can run.

```yaml
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc
```

The architecture point: PVCs decouple "how much storage a workload needs" from "which disk provides it" — Pods claim storage via a PVC, the cluster binds claims to PVs, and a configured `StorageClass` and provisioner can automate dynamic provisioning, while static PVs still have valid uses.

Access modes govern node attachment semantics: `ReadWriteOnce` (`RWO`) is writable from one node at a time, potentially by multiple Pods on that node. `ReadWriteOncePod` is a stricter single-Pod restriction (which is why stateful replicas on different nodes cannot share one `RWO` volume), and `ReadWriteMany` (`RWX`) needs a shared filesystem backend. Reclaim policy (`Retain` versus `Delete`) decides whether data survives claim deletion — a data-protection decision, not a default to overlook.

### Question 14: How do you perform rolling updates in Kubernetes?

**Answer:**

This strategy fragment belongs in an existing Deployment; it is not a complete Deployment manifest.

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
```

**Commands:**

```bash
# Update image
kubectl set image deployment/myapp myapp=myapp:2.0

# Monitor rollout
kubectl rollout status deployment/myapp

# Rollback
kubectl rollout undo deployment/myapp
```

The mechanism ties back to the Deployment model: a template change creates a new ReplicaSet, `maxSurge` and `maxUnavailable` bound how fast old replicas scale down and new ones scale up, and readiness probes govern normal Service endpoint eligibility. Direct Pod traffic, special Service settings, and in-flight connections still need separate handling.

`progressDeadlineSeconds` reports `ProgressDeadlineExceeded` for a stalled rollout (default `600s`). The Deployment controller keeps reconciling and does not automatically roll back; `kubectl rollout undo` scales the previous ReplicaSet back, and database migrations must be backward-compatible because both versions serve simultaneously during the window.

### Question 15: What is a DaemonSet?

**Answer:**

A DaemonSet ensures a Pod runs on all (or specific) nodes.

**Use Cases:**

- Log collectors (Fluentd, Filebeat)
- Monitoring agents (Prometheus Node Exporter)
- Network plugins (Calico, Cilium)

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
spec:
  selector:
    matchLabels: {app: node-agent}
  template:
    metadata:
      labels: {app: node-agent}
    spec:
      nodeSelector:
        kubernetes.io/os: linux
      containers:
        - name: agent
          image: registry.example.com/node-agent:1.2.3
```

Replace the example image with a configured agent. The controller requests one Pod per eligible node; scheduling, image startup, and readiness can still leave a node uncovered. Taints require matching tolerations. `RollingUpdate` supports availability and surge limits; `OnDelete` waits for manual deletion. Host networking and host ports change the node-level conflict and exposure model, so enable them only when the agent needs them.

### Question 16: What is the difference between a Job and a CronJob?

**Answer:**

| Aspect | Job | CronJob |
| --------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| Execution | Tracks finite work toward successful completions | Creates Jobs from a time-based schedule |
| Retry | Bounded by Job failure and deadline policies | Each created Job uses those same policies |
| Boundary | Attempts may repeat; effects need idempotency | Schedules may be missed or duplicated; no exactly-once guarantee |

`completions` defines the successful work count, while `parallelism` caps intended concurrent workers. CronJob `concurrencyPolicy` applies only to Jobs from that CronJob: `Forbid` skips a tick while its prior Job is active; it is not a lock shared with manual runs or other CronJobs. `Replace` requests cancellation but cannot undo external writes.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"
  timeZone: "Etc/UTC"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 900
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 1800
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: backup
              image: registry.example.com/backup:1.0.0
              command: ["/app/backup"]
```

The image must contain the backup command and credentials. Verify the output and restore path; a successful Job condition is not proof that a backup is recoverable. See the [Jobs and CronJobs chapter](../01-core-workloads/40.2.1.04-jobs-cronjobs.md) for retries, Indexed Jobs, and missed-schedule behavior.

### Question 17: How does Kubernetes handle networking?

**Answer:**

**Key Principles:**

1. Ordinary Pods have their own IP address (or addresses in a dual-stack cluster); containers in one Pod share that network identity. `hostNetwork` Pods instead use the node network namespace.

2. The network implementation supplies Pod-to-Pod addressability without address translation between Pod addresses. Enforced network policy can still deny a connection.

3. Node agents such as the kubelet can reach Pods on their own node; this is not a promise that every node process has unrestricted access to every Pod in the cluster.

**Network Plugins (Container Network Interface, CNI):**

- Calico: Network policy
- Flannel: Pod networking; policy enforcement depends on the installed implementation
- Cilium: Extended Berkeley Packet Filter (eBPF)-based networking

### Question 18: What is a Namespace in Kubernetes?

**Answer:**

Namespaces provide virtual cluster partitioning within a physical cluster.

```bash
# Create namespace
kubectl create namespace production

# Set context
kubectl config set-context --current --namespace=production

# List resources in namespace
kubectl get pods -n production
```

**Use Cases:**

- Environment isolation (dev, staging, prod)
- Resource quotas per team
- RBAC boundaries

Namespaces scope names and policies; creating one does not establish tenant isolation. RBAC controls API permissions, an enforcing network implementation applies NetworkPolicy, and quotas constrain admitted allocations and counts. Runtime workload privileges and shared-node risks need separate controls.

Choose namespace ownership so those policies are reviewable. Reserve elevated `PriorityClass` resources for the workloads that require them and restrict who can use them; priority influences scheduling and preemption but does not guarantee protection from node failure, pressure eviction, or insufficient capacity.

### Question 19: What are Taints and Tolerations?

**Answer:**

**Taints** repel Pods from nodes.
**Tolerations** allow Pods to be scheduled on tainted nodes.

```bash
# Add taint to node
kubectl taint nodes node1 key=value:NoSchedule

# Toleration in Pod
tolerations:
  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"
```

The mental model: taints mark nodes as "keep out unless you tolerate this" — the opposite of affinity, which attracts. Effects matter: `NoSchedule` blocks new Pods, `PreferNoSchedule` is best-effort, and `NoExecute` can evict running Pods that do not tolerate the taint; `tolerationSeconds` controls how long they tolerate it, while graceful termination is a separate contract.

Dedicated node pools use taints (Graphics Processing Unit (GPU), compliance-isolated, or spot workloads), while node-condition taints such as `not-ready` and `unreachable` explain why Pods suddenly reschedule during node trouble.

### Question 20: How do you troubleshoot a CrashLoopBackOff?

**Answer:**

```bash
# Check pod status
kubectl get pods
kubectl describe pod <pod-name>

# Check logs
kubectl logs <pod-name>
kubectl logs --previous <pod-name>

# Common causes:
# 1. Application crash
# 2. Missing environment variables
# 3. Failed health checks
# 4. Insufficient resources
# 5. Incorrect command/args
```

The systematic loop: run `describe pod` first — events show the restart reason and backoff timer, while `logs --previous` shows the *dying* instance's output, which is where the actual error lives.

Then classify exit states: exit `137` means termination by `SIGKILL` — check the container's reason and node events before attributing it to an out-of-memory kill. Exit `1` with a stack trace indicates an application bug, and a Pod that runs then gets killed on schedule suggests a liveness probe misfire from an aggressive timeout or wrong port. Restart backoff depends on kubelet configuration and feature gates; `CrashLoopBackOff` describes repeated restarts, so previous logs, termination state, events, and node pressure provide the evidence for diagnosis.

### Question 21: What is the difference between `docker-compose` and Kubernetes?

**Answer:**

| Aspect | Docker Compose | Kubernetes |
| ------------ | ------------------------------------- | --------------------------------------------------------------------------- |
| Scheduling | Services run on one host | Scheduler places Pods across eligible nodes |
| Complexity | Simple | Complex |
| Recovery | Host-level restart policies | Workload controllers replace Pods and kubelets restart containers by policy |
| Scaling | Manual replica changes | Autoscaling controllers can scale when configured with metrics and bounds |
| Typical fit | Single-host development or deployment | Workloads needing cluster scheduling and reconciliation |

The accurate mental model: Compose declares a host's containers and can use restart policies for process recovery. It does not provide Kubernetes' cross-node scheduling and workload controllers; Kubernetes adds that control plane and its operational cost.

Some Compose services can be translated into Kubernetes Deployments and Services, and tools such as Kompose can create a starting point. The mapping is not one-to-one: storage, health checks, networking, and operational ownership need review. Teams often keep Compose for local development and use Kubernetes where cluster scheduling and reconciliation justify its cost.

### Question 22: What is Helm and why use it?

**Answer:**

Helm packages Kubernetes manifests into charts, renders them from values, and records named releases. With Helm 4, a new release uses server-side apply by default; an upgrade or rollback follows that release's previous apply mode unless explicitly changed.

```bash
helm lint ./mychart
helm template myrelease ./mychart -f values.yaml
helm install myrelease ./mychart -f values.yaml
helm upgrade myrelease ./mychart -f new-values.yaml --rollback-on-failure
helm history myrelease
helm rollback myrelease 1
```

Release history records configuration, not a transaction over application data. `--rollback-on-failure` attempts to restore Kubernetes configuration; it cannot reverse migrations or hook side effects. Server-side apply tracks field ownership, so test for conflicts when another controller or GitOps tool writes the same objects. Use Kustomize when explicit patches are easier to review than conditional templates.

### Question 23: How do you implement network policies?

**Answer:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: api
      ports:
        - port: 8080
```

A policy selecting `web` Pods isolates their ingress and permits matching `api` Pods on the stated port, together with allows from other matching policies. A select-all default-deny isolates otherwise unselected Pods; policies are additive, so order does not subtract an existing allow. When both directions are isolated, the source egress and destination ingress must allow the connection.

Enforcement depends on the installed network implementation; verify a denied connection in the actual cluster. Egress isolation also needs an explicit DNS path when workloads resolve service names. Standard NetworkPolicy permits traffic to and from a Pod's own node and cannot block a Pod reaching itself; `hostNetwork` handling also varies by implementation, so default deny is not host isolation.

### Question 24: What is RBAC in Kubernetes?

**Answer:**

Role-Based Access Control controls who can do what.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader
  namespace: production
subjects:
  - kind: User
    name: jane
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

The model: a Role defines namespaced permissions. A ClusterRole defines reusable permissions; a ClusterRoleBinding grants them across the cluster, while a RoleBinding grants its namespaced permissions only in that binding's namespace.

Give automation a dedicated identity with least privilege. This can be a ServiceAccount or an explicitly mapped federated subject; OpenID Connect (OIDC) authentication does not imply a ServiceAccount. For verification, `kubectl auth can-i get pods -n ns --as=system:serviceaccount:ns:sa` answers "can it actually do this" without guessing, and aggregated ClusterRoles let platform teams compose permissions without duplicating rules. Watch wildcard verbs — `*` on resources is a standing audit finding.

### Question 25: How do you handle multi-cluster management?

**Answer:**

Begin with requirements: independent failure domains, regulatory location, or separate trust or operations ownership. A central configuration source should produce per-cluster desired state; it does not create cross-cluster networking or recover a failed cluster's data by itself.

**Strategies:**

- GitOps with Argo CD
- Service mesh (Istio, Linkerd)
- Centralized monitoring

Start with *why* — most organizations need fewer clusters than they expect: one cluster with namespace discipline is operationally cheaper than three. Real drivers for multi-cluster architectures are blast-radius isolation, data residency, and cloud or vendor hedging.

GitOps (Argo CD app-of-apps or Flux) deploys one Git source to multiple clusters with per-cluster overlays so configuration drift becomes a Pull Request (PR), not silent divergence. A service mesh with multi-cluster federation handles cross-cluster mutual Transport Layer Security (mTLS) and traffic when services must communicate across clusters. Choose maintained tooling after deciding which configuration, identity, traffic, and state are shared; a second cluster is not automatically a failover plan.

### Question 26: What are init containers?

**Answer:**

Ordinary init containers run sequentially to completion before application containers start. They are useful for bounded setup, such as preparing files or checking local configuration. A command that waits forever for a dependency can hold the application from starting; the application still needs runtime retry and recovery.

A native sidecar is declared as an init container with `restartPolicy: Always`. It starts before application containers and continues running beside them. Native sidecars are stable since Kubernetes 1.33. Unlike a short-lived init container, this helper consumes resources throughout the Pod lifetime.

When diagnosing startup, `Init:CrashLoopBackOff` means an init container is repeatedly failing and the application containers have not completed initialization. Init requests, application requests, and sidecars also affect the Pod's effective resource request and scheduling fit.

### Question 27: How do you monitor Kubernetes?

**Answer:**

**Components:**

- **Metrics Server**: Short-term CPU and memory resource metrics for `kubectl top` and common HPA inputs
- **Metrics backend**: Time-series retention and alert evaluation, such as Prometheus or a managed service
- **kube-state-metrics**: Kubernetes object state such as desired and available replicas
- **OpenTelemetry Collector**: Receives, processes, and exports telemetry to configured backends
- **Logs and traces**: Use backends that fit retention, query, and operational needs

```bash
# Check resource usage
kubectl top pods
kubectl top nodes

# View events
kubectl get events --sort-by=.metadata.creationTimestamp
```

Separate short-term resource metrics from monitoring history: Metrics Server supplies CPU and memory metrics for `kubectl top` and common HPA inputs, while a metrics backend stores time series. `kube-state-metrics` exposes Kubernetes object state; node and application instrumentation add resource and service signals. Use Rate, Errors, Duration (RED) for services and Utilization, Saturation, Errors (USE) for resources. Alert on user impact and actionable saturation, then use events, logs, metrics, and traces to find causes.

### Question 28: What is a Pod Disruption Budget?

**Answer:**

A Pod Disruption Budget (PDB) limits voluntary disruptions during node maintenance.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp
```

The precise scope is voluntary eviction through the eviction API. With three healthy selected replicas and `minAvailable: 2`, one healthy eviction can proceed; another waits for health to return. A node failure cannot be prevented, and HPA replica reductions, direct deletes, and workload rolling updates follow other paths.

Percentage thresholds round up and need careful small-population checks. `kubectl drain` uses eviction admission by default when supported; there is no `--respect-pdbs` flag. If a drain stalls, inspect budget status and whether replacements can schedule rather than bypassing the policy. Since Kubernetes 1.31, `unhealthyPodEvictionPolicy: AlwaysAllow` can let drains remove unhealthy running Pods without permitting extra healthy evictions; verify cluster support and the workload's recovery behavior.

### Question 29: How do you implement GitOps with Kubernetes?

**Answer:**

**Tools:**

- **Argo CD**: GitOps continuous delivery
- **Flux**: GitOps toolkit

**Workflow:**

1. Store manifests in Git

2. Argo CD watches the repository

3. Syncs changes automatically when automated sync is enabled

4. Provides rollback via Git

The cluster-side mechanics: an operator (Argo CD or Flux) watches Git, applies manifests, and *continuously reconciles* — drift from a hand-edit can be detected, while automatic reversion requires the controller's self-heal and reconciliation policy, which separates GitOps from Continuous Integration (CI) that runs `kubectl`.

An app-of-apps structure scales the pattern (one root Application owns per-team and per-environment Applications so platform teams onboard a service by merging a directory). Sync waves order databases before applications, and promotion between environments is a PR changing an image tag in a per-environment overlay — the PR is the audit trail, and a Git revert changes desired configuration without reversing data migrations or external side effects.

### Question 30: What are the best practices for Kubernetes security?

**Answer:**

1. **RBAC**: Restrict access with roles

2. **Network Policies**: Limit Pod-to-Pod communication

3. **Pod Security Standards**: Enforce an appropriate admission profile; the Restricted profile includes non-root and other workload controls

4. **Image scanning**: Use Trivy or Clair

5. **Secrets management**: External secret stores

6. **Audit logging**: Monitor API access

7. **Resource quotas**: Bound admitted namespace allocations and object counts; also plan runtime limits and physical capacity

8. **Regular updates**: Keep Kubernetes patches and base images updated

### Question 1: What is Kubernetes and why is it used?

**Answer:**

Kubernetes (K8s) is an open-source container orchestration platform that automates deployment, scaling, and management of containerized applications.

**Key Benefits:**

- **Self-healing**: Restarts failed containers, replaces and reschedules containers
- **Horizontal scaling**: Scale up/down automatically based on metrics
- **Service discovery**: DNS-based service discovery and load balancing
- **Automated rollouts**: Rolling updates with zero downtime
- **Storage orchestration**: Mount storage systems automatically
- **Secret management**: Manage sensitive configuration

---

### Question 2: What is a Pod in Kubernetes?

**Answer:**

A Pod is the smallest deployable unit in Kubernetes. It represents a single instance of a running process and can contain one or more containers that share:

- Network namespace (same IP address)
- Storage volumes
- Process namespace

**When to use multi-container Pods:**

- Sidecar pattern (log shipping, proxies)
- Ambassador pattern (service proxies)
- Adapter pattern (output formatting)

### Question 5: How does Kubernetes handle service discovery?

**Answer:**

Kubernetes uses DNS for service discovery:

```text
Service Name: myservice
Namespace: production
FQDN: myservice.production.svc.cluster.local

```

**Methods:**

1. **DNS**: CoreDNS resolves service names to Cluster IPs

2. **Environment variables**: Injected into Pods at creation

3. **Headless Services**: Return Pod IPs directly

The mechanism: CoreDNS watches the API server and programs DNS records for every Service (and pod-ready headless Service). The FQDN encodes hierarchy — `svc.namespace.cluster.local` — which is why short names only resolve within the same namespace. Senior gotchas: the `ndots:5` default in pod resolv.conf causes external lookups to try cluster suffixes first (lookup storms under load — set ndots or use FQDNs for external calls), and env-var discovery is create-time only — it goes stale and is legacy, not a mechanism to design on.

### Question 7: Explain HPA (Horizontal Pod Autoscaler).

**Answer:**

HPA automatically scales Pod replicas based on metrics:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 2
  maxReplicas: 10
  metrics:

    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

```

**Metrics used:**

- CPU utilization
- Memory utilization
- Custom metrics (requests/second)
- External metrics (queue length)

Mechanically the HPA is a control loop reading metrics (resource metrics from metrics-server, custom via the metrics APIs) and computing `desiredReplicas = ceil(current * targetMetric / actualMetric)`. Senior depth: stabilization windows and scaling policies prevent thrash — without them traffic oscillation makes replicas flap; HPA never scales below minReplicas and standard HPA cannot scale to zero (KEDA fills that gap for queue-driven workloads). Know the division of labor: HPA scales pods, VPA right-sizes requests, Cluster Autoscaler adds nodes — they compose, but VPA+HPA on the same resource conflict.

### Question 8: What are liveness and readiness probes?

**Answer:**

| Probe | Purpose | On Failure |
| --------- | ------------------------------ | ------------------- |
| Liveness | Is container alive? | Restart container |
| Readiness | Can container receive traffic? | Remove from Service |
| Startup | Is initialization complete? | Delay other probes |

**Probe Handlers:**

- `exec`: Run command
- `httpGet`: HTTP request
- `tcpSocket`: TCP connection
- `gRPC`: gRPC health check

### Question 9: How do you manage secrets in Kubernetes?

**Answer:**

```bash
# Create secret
kubectl create secret generic db-creds \
  --from-literal=password=secret123

# Use in Pod
env:

  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-creds
        key: password

```

**Best Practices:**

- Use external secret stores (Vault)
- Enable encryption at rest
- Use RBAC to restrict access
- Rotate secrets regularly

The critical fact: base64 is encoding, not encryption — without `EncryptionConfiguration` on kube-apiserver, secrets sit in etcd plaintext on the control-plane disks. Senior posture: enable etcd encryption at rest, restrict with RBAC on the secrets resource (not cluster-wide read), avoid env vars where the values leak into crash dumps and logs, and treat external stores (Vault, cloud secret managers) synced via External Secrets Operator or CSI drivers as the real answer — Kubernetes then holds only short-lived projections, rotation happens at the source, and `kubectl get secret` stops being a treasure map.

### Question 10: What is an Ingress in Kubernetes?

**Answer:**

Ingress manages external HTTP/HTTPS access to Services:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
spec:
  tls:

    - hosts:
        - myapp.example.com
      secretName: tls-secret
  rules:

    - host: myapp.example.com
      http:
        paths:

          - path: /api
            backend:
              service:
                name: api-service
                port:
                  number: 80

```

**Features:**

- TLS termination
- Host-based routing
- Path-based routing
- Rate limiting

Ingress is a specification, not infrastructure — an Ingress controller (NGINX, Traefik, cloud) must implement it, which is why annotations differ per controller. Depth: TLS termination with cert-manager automating issuance/renewal is the day-one setup; the controller-specific canary annotations are powerful but non-portable. The forward-looking answer is Gateway API: role-separated (platform team owns Gateways, teams own HTTPRoutes), expressive (header matching, weighting are core, not annotations), and vendor-portable — name it and you sound current.

### Question 11: What is the difference between `kubectl apply` and `kubectl create`?

**Answer:**

| Command | Behavior |
| -------- | --------------------------------------- |
| `create` | Creates a new resource; fails if exists |
| `apply` | Creates or updates idempotently |

```bash
# Creates new resource
kubectl create -f pod.yaml

# Creates or updates
kubectl apply -f pod.yaml

```

The deeper cut: `create` is imperative (here's a new object), `apply` is declarative (converge live state to this file) — and apply does a three-way merge against the `last-applied-configuration` annotation, which is exactly why hand-edits and apply fight each other. Senior rule: in any GitOps or even Git-reviewed world, apply is the only write path; create/replace are debugging tools. Follow-up worth anticipating: 'what breaks three-way merge?' — removed fields survive (the classic deleted-strategy surprise), which is why server-side apply with field ownership exists.

### Question 13: What are Persistent Volumes and PVCs?

**Answer:**

**PersistentVolume (PV):** Cluster-level storage resource.

**PersistentVolumeClaim (PVC):** Request for storage by a Pod.

```yaml
# PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:

    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi

# Use in Pod
volumes:

  - name: data
    persistentVolumeClaim:
      claimName: my-pvc

```

The architecture point: PVCs decouple 'how much storage a workload needs' from 'which disk provides it' — pods claim via PVC, the cluster binds claims to PVs, StorageClass automates provisioning (dynamic provisioning is why nobody hand-creates PVs anymore). Depth: access modes are about node attachment semantics — RWO is one node at a time (why stateful replicas on different nodes can't share one RWO volume), RWX needs a shared filesystem backend; reclaim policy Retain vs Delete decides whether data survives the claim — a deletion-protection decision, not a default to click past.

### Question 14: How do you perform rolling updates in Kubernetes?

**Answer:**

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

```

**Commands:**

```bash
# Update image
kubectl set image deployment/myapp myapp=myapp:2.0

# Monitor rollout
kubectl rollout status deployment/myapp

# Rollback
kubectl rollout undo deployment/myapp

```

Mechanism ties back to the Deployment model: a template change creates a new ReplicaSet; maxSurge/maxUnavailable bound how fast old scales down and new up, and readiness probes gate membership — an unready pod never takes traffic, which is what makes the rollout safe. Senior details: `progressDeadlineSeconds` turns a stuck rollout into a failed one (default 600s) rather than a silent hang, `kubectl rollout undo` scales the previous RS back, and database migrations must be backward-compatible because both versions serve simultaneously during the window.

### Question 15: What is a DaemonSet?

**Answer:**

A DaemonSet ensures a Pod runs on all (or specific) nodes.

**Use Cases:**

- Log collectors (Fluentd, Filebeat)
- Monitoring agents (Prometheus Node Exporter)
- Network plugins (Calico, Weave)

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
spec:
  selector:
    matchLabels:
      app: log-collector
  template:
    spec:
      containers:

        - name: fluentd
          image: fluentd:latest

```

DaemonSet is the answer to 'run one pod per node' — node agents, log shippers, CNI plugins — bypassing the scheduler's replica math entirely. Depth: taints matter — nodes need tolerations matched or the agent misses nodes (the classic 'why is this node unmonitored' incident); rolling updates support surge/unordered strategies, or manual cordon-and-delete for agents that must not run two versions. The interview follow-up: DaemonSet vs hostNetwork/hostPort tradeoffs for network-critical agents, and why these pods usually get PriorityClass so eviction doesn't kill observability first.

### Question 18: What is a Namespace in Kubernetes?

**Answer:**

Namespaces provide virtual cluster partitioning within a physical cluster.

```bash
# Create namespace
kubectl create namespace production

# Set context
kubectl config set-context --current --namespace=production

# List resources in namespace
kubectl get pods -n production

```

**Use Cases:**

- Environment isolation (dev, staging, prod)
- Resource quotas per team
- RBAC boundaries

The trap: namespaces are a naming and scoping partition, not a security boundary — isolation comes from RBAC (who sees the namespace), NetworkPolicy (what traffic crosses), and ResourceQuota/LimitRange (what it may consume) layered together. Senior practice: namespace per team-app-environment, not one giant shared namespace — quotas and access control become per-team rather than global; system namespaces (kube-system) get node-critical PriorityClass so nothing user-created can evict them. The `default` namespace is where discipline goes to die.

### Question 19: What are Taints and Tolerations?

**Answer:**

**Taints** repel Pods from nodes.
**Tolerations** allow Pods to be scheduled on tainted nodes.

```bash
# Add taint to node
kubectl taint nodes node1 key=value:NoSchedule

# Toleration in Pod
tolerations:

  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"

```

The mental model: taints mark nodes as 'keep out unless you tolerate this' — the opposite of affinity, which attracts. Effects matter: NoSchedule blocks new pods, PreferNoSchedule is best-effort, NoExecute evicts *running* pods (the maintenance tool — combined with tolerationSeconds for graceful drain). Senior use: dedicated node pools via taints (GPU, compliance-isolated, spot workloads), plus the kubelet's automatic taints (not-ready, unreachable) explaining why pods suddenly reschedule during node trouble.

### Question 20: How do you troubleshoot a CrashLoopBackOff?

**Answer:**

```bash
# Check pod status
kubectl get pods
kubectl describe pod <pod-name>

# Check logs
kubectl logs <pod-name>
kubectl logs --previous <pod-name>

# Common causes:
# 1. Application crash
# 2. Missing environment variables
# 3. Failed health checks
# 4. Insufficient resources
# 5. Incorrect command/args

```

The systematic loop: `describe pod` first — Events show the restart reason and backoff timer; `logs --previous` shows the *dying* instance's output, which is where the actual error lives. Then classify: exit 137 usually means OOMKill (raise requests/limits or fix a leak), exit 1 with a stack trace is an app bug, and a pod that runs then gets killed on schedule is a liveness probe misfire — probe too aggressive or wrong port. Backoff is exponential to 5 minutes by design; CrashLoopBackOff is a symptom collector, not a diagnosis — the diagnosis is always in the previous container's logs or the probe config.

### Question 22: What is Helm and why use it?

**Answer:**

Helm is the package manager for Kubernetes.

**Benefits:**

- Packages multiple manifests into charts
- Manages releases and rollbacks
- Configurable via values files
- Version control for deployments

```bash
# Install chart
helm install myrelease ./mychart -f values.yaml

# Upgrade
helm upgrade myrelease ./mychart -f new-values.yaml

# Rollback
helm rollback myrelease 1

```

Beyond 'package manager': a Helm release is a tracked installation instance stored as a secret in-cluster — that release record is what makes upgrade, rollback, and `helm diff` possible, and what makes two installs of one chart two independent releases. Senior depth: hooks and `helm test` encode post-install health checks; `helm lint` + `helm template` + `helm diff upgrade` in CI catch render breakage before the cluster does; and the honest tradeoff — template logic in YAML has a maintenance cliff, which is why Kustomize-style patching appeals to teams that don't need parameterized charts.

### Question 23: How do you implement network policies?

**Answer:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:

    - Ingress
  ingress:

    - from:
        - podSelector:
            matchLabels:
              app: api
      ports:

        - port: 8080

```

The foundation that juniors miss: policies are allow-lists on top of a default-allow world — the first rule of any real deployment is a default-deny (empty podSelector selecting all pods, denying both ingress and egress), then allow just what's needed. Two production gotchas: the CNI must implement NetworkPolicy (Flannel silently ignores them — verify with a two-pod denial test), and egress policies break DNS immediately unless you allow UDP/TCP 53 to CoreDNS — every 'my policy locked the whole namespace' story is that story.

### Question 24: What is RBAC in Kubernetes?

**Answer:**

Role-Based Access Control controls who can do what.

```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
rules:

  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]

# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader
subjects:

  - kind: User
    name: jane
roleRef:
  kind: Role
  name: pod-reader

```

The model: a Role grants verbs on resources within one namespace; ClusterRole spans the cluster (or is bound per-namespace via RoleBinding — the reusable-role pattern). Depth: grant to ServiceAccounts, not users, in automation (least privilege per workload — this is what OIDC-federated CI assumes); `kubectl auth can-i --as=system:serviceaccount:ns:sa` answers 'can it actually do this' without guessing; and aggregated ClusterRoles let platform teams compose permissions without duplicating rules. Watch the wildcard verbs — `*` on resources is a standing audit finding.

### Question 25: How do you handle multi-cluster management?

**Answer:**

**Tools:**

- **KubeFed**: Kubernetes-native federation
- **Rancher**: Multi-cluster management UI
- **Anthos**: Google's hybrid/multi-cloud platform
- **Azure Arc**: Azure's hybrid platform

**Strategies:**

- GitOps with Argo CD
- Service mesh (Istio, Linkerd)
- Centralized monitoring

The senior answer starts with *why* — most orgs need fewer clusters than they think: one cluster with namespace discipline is operationally cheaper than three. Real drivers for multi-cluster: blast-radius isolation, data residency, and cloud/vendor hedging. Then the design: GitOps (Argo CD app-of-apps or Flux) makes one Git source deploy to N clusters with per-cluster overlays — config drift between clusters becomes a PR, not a divergence; a service mesh with multi-cluster federation handles cross-cluster mTLS/traffic if services must talk. KubeFed itself is effectively dead — name the GitOps pattern instead.

### Question 26: What are init containers?

**Answer:**

Init containers run before main containers and must complete successfully.

```yaml
spec:
  initContainers:

    - name: init-db
      image: busybox
      command: ['sh', '-c', 'until nslookup db; do sleep 2; done']
  containers:

    - name: app
      image: myapp:1.0

```

**Use Cases:**

- Wait for dependencies
- Database migrations
- Configuration setup

Init containers run to completion *before* app containers start, sequentially — the mechanism for 'database must be reachable before the app boots' without retry hacks in app code. Depth: resource scheduling uses the *max* of init and sum of app containers (a fat init container raises the pod's cost); a failing init container restarts with backoff and blocks app start (visible as Init:CrashLoopBackOff). The modern twist: native sidecars (1.28+) — an init container with `restartPolicy: Always` runs for the pod's whole lifetime, making the sidecar pattern first-class instead of the old ambassador hacks.

### Question 27: How do you monitor Kubernetes?

**Answer:**

**Components:**

- **Metrics Server**: Basic CPU/memory metrics
- **Prometheus**: Metrics collection
- **Grafana**: Visualization
- **Jaeger**: Distributed tracing
- **ELK Stack**: Log aggregation

```bash
# Check resource usage
kubectl top pods
kubectl top nodes

# View events
kubectl get events --sort-by=.metadata.creationTimestamp

```

The useful structure is what to measure per layer: kubelet/cAdvisor gives per-pod resource signals, kube-state-metrics gives object state (desired vs available replicas, pending pods), and the node agent completes the picture — Prometheus scrapes all three. Senior points: alert on symptoms (latency, error rate) not causes (CPU) — CPU alarms page people on healthy-but-busy systems; `kubectl get events` sorted by timestamp is the first triage tool and too many people don't know it; and the USE/RED methods (utilization-saturation-errors per resource, rate-errors-duration per service) structure dashboards so they answer questions.

### Question 28: What is a Pod Disruption Budget?

**Answer:**

PDB limits voluntary disruptions during node maintenance.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp

```

The precise scope: PDB constrains *voluntary* disruptions — node drains, cluster upgrades — by keeping minAvailable (or maxUnavailable) replicas serving; it does nothing against crashes or OOM (that's the Deployment's replica reconciliation). Senior gotchas: percentage minAvailable rounds *up* on eviction but the math with tiny deployments (2 replicas, 50% = 1) can stall drains entirely — drained nodes wait forever, upgrades hang; use maxUnavailable with absolute values for small deployments. The pairing question: PDB + `kubectl drain --respect-pdbs` is how maintenance stays graceful.

### Question 29: How do you implement GitOps with Kubernetes?

**Answer:**

**Tools:**

- **Argo CD**: GitOps continuous delivery
- **Flux**: GitOps toolkit

**Workflow:**

1. Store manifests in Git

2. Argo CD watches repository

3. Automatically syncs changes

4. Provides rollback via Git

The cluster-side mechanics: an operator (Argo CD or Flux) watches Git, applies manifests, and *continuously reconciles* — drift from a hand-edit is detected and reverted, which is the property that separates GitOps from 'CI that runs kubectl'. Depth: app-of-apps scales the pattern (one root Application owns per-team/per-env Applications — platform teams onboard a service by merging a directory); sync waves order databases before apps; promotion between environments is a PR changing an image tag in a per-env overlay — the PR is the audit trail, and rollback is `git revert`.

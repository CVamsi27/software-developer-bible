# GitHub Actions

## Definition

**GitHub Actions** schedules repository workflows in response to events. A workflow declares jobs; each job runs ordered steps on a runner. A step invokes a shell command or an action. Jobs can depend on other jobs, but they do not automatically share a checkout, installed packages or build output.

## First Principles

Testing a commit requires executable code and dependencies. Promoting it additionally requires release authority and an identified artifact. Untrusted changes must be testable without receiving that authority, and the deployed bytes must correspond to the checks you approved. Model the workflow as a dependency graph with explicit data and credential boundaries.

## Trace a Change From PR to a Protected Deployment

1. A pull request starts verification with minimal repository access and no cloud deployment credentials.
2. The runner checks out the event's code, installs locked dependencies, checks types/tests and builds.
3. A trusted push to main runs verification again and uploads that run's build artifact.
4. A deployment job waits for successful verification and the production environment's configured protection rules.
5. It downloads the identified artifact and obtains narrowly scoped, short-lived cloud credentials.
6. The deployment command publishes those bytes and checks the application's readiness.

```text
PR / merge queue ──> verify only
trusted main push ──> verify + identified artifact ──> protected deploy
                           no cloud role                  scoped cloud role
```

A YAML environment name does not itself configure reviewers or branch restrictions. Set those rules in the repository's environment settings and account for plan/repository feature availability. [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) defines the event, dependency and permission semantics used here.

## How the Parts Fit Together

| Component | Role in the flow | Important boundary |
| ---------------- | ------------------------------------------- | --------------------------------------------------------- |
| Event | Select the run and its ref/payload | A PR's ref/SHA is not necessarily its head commit |
| Workflow | Declare jobs and policy | Config is executable repository content |
| Job + needs | Schedule a dependency node | Files and environment do not transfer automatically |
| Runner | Execute checked-out code/actions | Self-hosted machines can retain state and network access |
| Action | Reusable step implementation | It executes with the job's accessible inputs/permissions |
| Cache | Reuse reconstructible inputs | It is not an approved release artifact |
| Artifact | Transfer named run output | Validate producer, run and integrity before promotion |
| Environment/OIDC | Gate access and obtain deployment authority | Cloud trust and role policy must be configured separately |

GitHub-hosted runner isolation differs by runner type; self-hosted runners need explicit lifecycle and trust controls. An ephemeral runner alone does not make privileged execution of untrusted code safe.

## Code Examples

### Keep Verification and Deployment Authority in Different Jobs

This is a workflow template for a project whose scripts provide lint, typecheck, test:ci, build and deploy:production, with build output in dist/. The deployment script must consume the downloaded artifact, perform the project's actual provider deployment and verify readiness; the name does not supply that implementation. This template targets GitHub.com; current artifact actions have separate GHES compatibility constraints. Use compatible current hosted runners or updated self-hosted runners for the pinned Node 24 action runtime.

Action release commits below were resolved from their official repositories on 2026-10-02. Review changes and update pins deliberately. Full commit pins give immutable action references; they do not establish that the pinned code is safe. [GitHub's secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) explains the trust boundary.

```yaml
# .github/workflows/verify-and-deploy.yml
name: Verify and deploy
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
  merge_group:
    types: [checks_requested]

permissions:
  contents: read

# Cancel obsolete PR verification, but avoid interrupting production promotion.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    outputs:
      artifact-id: ${{ steps.bundle.outputs.artifact-id }}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0
        with:
          node-version: '24'
          cache: npm
          cache-dependency-path: package-lock.json
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test:ci
      - run: npm run build
      - uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1
        id: bundle
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        with:
          name: application-${{ github.sha }}
          path: dist/
          if-no-files-found: error
          retention-days: 7

  deploy:
    needs: verify
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    environment: production
    concurrency:
      group: production-deployment
      cancel-in-progress: false
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0
        with:
          node-version: '24'
          # Credentialed job does not restore a dependency cache.
          package-manager-cache: false
      - run: npm ci --ignore-scripts
      - uses: actions/download-artifact@3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c # v8.0.1
        with:
          artifact-ids: ${{ needs.verify.outputs.artifact-id }}
          path: release/
          merge-multiple: true
          digest-mismatch: error
      - uses: aws-actions/configure-aws-credentials@e1253824e5c10ff9df46874f81ed3ec929e19cfd # v6.3.0
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}
          role-session-name: deploy-${{ github.run_id }}
      - name: Deploy the downloaded build and verify readiness
        env:
          RELEASE_DIRECTORY: release
        run: npm run deploy:production -- --artifact "$RELEASE_DIRECTORY"
```

The example assumes deployment tooling can install without lifecycle scripts. If it requires generated/native components, build that tooling in a reviewed trusted stage or narrowly allow required setup; blindly removing ignore-scripts changes the credentialed job's attack surface. Verify that the deploy command does not quietly rebuild dist or resolve an unapproved release tag. Test its error exit, timeout, rollback and backward-compatible database behavior.

OIDC id-token: write permits requesting a token; it does not grant AWS access by itself. Configure the identity provider, intended audience, subject conditions such as the exact repository/environment, and a least-privilege role. Environment-based subjects differ from branch-based subjects. [GitHub's AWS OIDC instructions](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws) describe the required external trust setup. Do not broaden the role trust to every repository or PR.

### Pass Untrusted Text as Data

A PR title is caller-controlled. Do not expand it directly into generated shell source. Pass it through an environment variable and quote it when treating it as text:

```yaml
# An additional verify-job step; no privileged operation.
- name: Check title length
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: |
    if [ "${#PR_TITLE}" -gt 120 ]; then
      printf '%s\n' 'PR title is too long'
      exit 1
    fi
```

Never print a secret as a demonstration of deployment. Inject necessary credentials through the intended input/environment, avoid shell tracing and verify logs/artifacts for transformed leaks. Automatic log masking is useful but does not promise to redact every derived value.

## Match Required Checks to Events and Shared Inputs

A path-filtered workflow can be skipped while its required check remains pending. Monorepo app changes can also depend on shared packages, root lockfiles, build config or workflow changes. Keep the required dispatcher/check available and compute affected work from the dependency graph. Test changes to shared inputs and deletion/rename cases rather than watching only apps/web/**.

If using a merge queue, required Actions checks must handle merge_group in addition to the PR event. Keep stable unique job/check names and distinguish skipped work from evidence that the code was tested. Fork PRs ordinarily lack repository secrets and have restricted token permissions; repository settings/event types can change the trust context. Do not “fix” that restriction by moving tests to a privileged trigger.

pull_request_target and workflow_run can execute in a privileged context. Do not check out and run untrusted PR code there or blindly execute its artifacts. Current checkout includes safer fork-checkout handling, but do not override it as a shortcut; trust separation remains a workflow responsibility. See [GitHub's event reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

## Use a Cache to Save Work, an Artifact to Identify a Release

setup-node's npm cache restores package-manager download data; it does not replace npm ci or install node_modules. Cache keys should account for lockfile, runtime/platform and relevant inputs. A fallback restore key may return an older cache, so installation still resolves the locked dependency set. Do not cache credentials or use a cache as the authoritative dist to deploy. [GitHub's caching model](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching) distinguishes this purpose from transferring build output.

Upload immutable run artifacts with unique names; do not assume parallel matrix jobs can append to one artifact. Release promotion should identify the producer/run, expected commit and artifact or container digest. For container pipelines, build and scan the identified image, then promote its digest rather than deploying latest. A Git SHA tag is a label, not automatic proof that the image was built, pushed and tested.

Reports, traces and auth files can contain sensitive data. Upload only reviewed evidence, set access/retention policy, and exclude secrets/auth state. if: always() is useful for failure diagnostics; publishing a partial build as a release artifact after a failed check is a different decision.

## Reuse the Right Unit

| Mechanism | Invocation | Useful scope |
| ----------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| Reusable workflow | Job uses workflow_call file | A complete job/pipeline with declared inputs, secrets and outputs |
| Composite action | Step uses action.yml with composite steps | Repeated setup inside the calling job's runner/context |
| Matrix | One job definition expanded over axes | Required runtime/OS/application variants |

Reusable workflows do not grant extra permissions or automatically receive every secret. Pass the intended contract, account for environment-secret behavior and pin external reusable workflows too. Composite run steps must declare a shell. Prefer explicit inputs over a reusable setup that silently grants deployment access. [GitHub's reuse documentation](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) covers these distinctions.

Choose matrix axes from actual supported configurations, not a desire for more green boxes. fail-fast can cancel remaining matrix jobs; collect all required results before claiming platform coverage. Configure concurrency to match environment capacity; a concurrency group limits overlap but is not a transactional deployment lock or a general FIFO queue guarantee. Reject superseded releases through an explicit desired-revision policy rather than assuming approval or serialization will establish deployment freshness.

## Real-World Decisions

### Build a Monorepo From Its Dependency Graph

Run the canonical [Turborepo](../../40.8-monorepo/40.8.02-turborepo.md) flow against shared-package/config changes and locked inputs. Verify that every affected test/build participates and that remote cache credentials are scoped. Treat restored output as untrusted if its producer can run untrusted code; do not give a PR cache writer an indirect path into a privileged release job.

### Diagnose a Failure Before Retrying It

Use gh run list, gh run view and the job's logs to identify setup, test, artifact or deployment failure. A rerun cannot fix a missing cloud trust rule or a nonexistent image. Scheduled workflows are useful for periodic checks but can be delayed; they are not a hard real-time scheduler. Release changelogs need a defined previous release and graceful first-release behavior, not git describe called on the current tag as if it always finds the prior one.

## Common Mistakes

| Mistake | Why it breaks the flow | Better boundary |
| --------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| Deploy on an ordinary PR run | Untrusted code gains release authority | Verify-only PR, trusted protected promotion |
| Print/interpolate secrets into shell source | Logs or generated scripts leak credentials | Scoped injection and log inspection |
| Pin an action to master or assume a major tag is immutable | Dependency content can change unnoticed | Reviewed full commit pin and deliberate updates |
| Build a SHA-tagged image but deploy a different/unpublished tag | Deployed bytes lack the asserted evidence | Publish and promote the identified digest |
| Apply kubectl without context/credentials | Runner lacks a valid trusted cluster connection | Explicit role, context, namespace and readiness checks |
| Switch to a self-hosted runner only to save cost | Persistence/network access can expose trusted systems | Measured capacity and a deliberate runner trust model |

## Best Practices

Keep the event/ref, real checks, artifact identity and release authority visible in one trace. Validate required-check behavior, dependency paths and credential trust before adding parallelism or caching. Use immutable reviewed actions, scoped cloud roles, restricted telemetry artifacts and a tested promotion/rollback procedure.

## Summary

GitHub Actions schedules jobs; correct CI/CD comes from the contracts between those jobs. Test untrusted changes without deployment authority, carry an identified checked artifact into a protected release job, and make credentials, required events and readiness explicit. Caches accelerate reconstructible work; they do not certify a release.

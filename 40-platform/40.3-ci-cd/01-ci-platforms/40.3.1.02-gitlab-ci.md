# GitLab CI/CD

## Definition

**GitLab CI/CD** is GitLab's built-in continuous integration and continuous delivery platform. Pipelines are defined in a `.gitlab-ci.yml` file in the repository root. It features auto-scaling runners, container registry, built-in container scanning, and integrated deployment environments with review apps.

## First Principles

GitLab CI's single-file, single-platform model trades flexibility for coherence:

1. **One `.gitlab-ci.yml` per repo, stages shared globally** — the pipeline is first-class in the same platform as the code, which is why review/MR integration is frictionless. The cost: monolithic config as pipelines grow (hence `include`).
2. **The DAG is explicit**: stages sequence; `needs` breaks out of linear stages into a graph — parallelism where the dependency structure allows (→ 40.3.2.02's shape choice).
3. **Runners carry the same trust calculus** (→ 40.3.1.01): shared runners for public repos are isolation-by-ephemeral; self-hosted runners for protected branches only.

## Why Do We Need It?

1. **Single platform**: SCM, CI/CD, registry, and monitoring in one tool
2. **Auto DevOps**: Automated pipeline setup for common stacks
3. **Review Apps**: Auto-deploy feature branches as ephemeral environments
4. **Built-in security**: SAST, DAST, container scanning, dependency scanning
5. **Scale**: Auto-scaling runners for parallel job execution

## How It Works

### Pipeline types and the rules engine

GitLab builds different pipelines for the same YAML depending on context: **branch pipelines** (push), **merge request pipelines** (a merged-result ref that tests what the MR *would become* — the honest pre-merge signal), **scheduled pipelines**, and **parent-child pipelines** (a parent job dynamically generating child YAML for per-path jobs in a monorepo). Which one runs is decided by `rules` — an evaluated-in-order list of `if`/`changes`/`exists` clauses with `when: on_success|manual|never`. The `only`/`except` syntax in the examples above still works but is the legacy form; `rules` composes (and is where `changes:` paths make monorepo per-component pipelines tractable: `changes:
  - "frontend/**/*"`).

### The execution model: stages, needs, runners

Stages sequence; jobs within a stage default to parallel; `needs` breaks the stage wall into a true DAG — `needs: []` (as the lint job above shows) detaches a job from the stage chain so it starts immediately, and `needs:` with an artifacts declaration makes artifact-passing explicit instead of implicit-per-stage. Runners execute each job in an ephemeral environment: the **Docker executor** (one container per job — the default trust boundary), the **Kubernetes executor** (pods per job, autoscaled), or **shell** (stateful and trust-heavy — reserved for runners locked to protected branches). The dind example above shows the Docker-in-Docker service pattern with its TLS dir disabled — and its known alternative: kaniko/buildkit for building images *inside* the Kubernetes executor without privileged dind containers.

### The cache/artifacts distinction (the classic confusion)

**Cache** is per-runner archived directories restored to speed up *your* next run (`node_modules` keyed by `${CI_COMMIT_REF_SLUG}`) — best-effort, may miss, never your delivery mechanism. **Artifacts** are job outputs passed to dependent jobs and downloadable from the UI — the delivery mechanism (build outputs, test reports: `junit`, `cobertura`, `dotenv` for job-to-job variables). Getting this wrong one way makes pipelines slow (delivering builds via cache), the other way makes them subtly wrong (relying on cache presence as if it were guaranteed). Cache keys are also the hygiene story: an unkeyed or branch-blind cache shares artifacts between feature branches — a build-poisoning vector as well as a correctness bug.

## Code Examples

### Basic Pipeline

```yaml
# .gitlab-ci.yml
stages:
  - build
  - test
  - deploy

variables:
  NODE_VERSION: "20-alpine"
  DOCKER_DRIVER: overlay2

cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

before_script:
  - node --version
  - npm --version

build:
  stage: build
  image: node:${NODE_VERSION}
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 hour

lint:
  stage: test
  image: node:${NODE_VERSION}
  script:
    - npm ci
    - npm run lint
  needs: []

unit-test:
  stage: test
  image: node:${NODE_VERSION}
  script:
    - npm ci
    - npm run test:unit
  coverage: '/Statements\s+:\s([\d.]+)%/'
  artifacts:
    reports:
      junit: reports/junit.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage/cobertura-coverage.xml

integration-test:
  stage: test
  image: node:${NODE_VERSION}
  services:
    - postgres:15-alpine
    - redis:7-alpine
  variables:
    DATABASE_URL: "postgres://postgres:password@postgres:5432/test"
  script:
    - npm ci
    - npm run test:integration

deploy-dev:
  stage: deploy
  image: alpine:latest
  script:
    - apk add --no-cache curl
    - curl -X POST ${DEPLOY_WEBHOOK}
  environment:
    name: development
  only:
    - main

deploy-production:
  stage: deploy
  image: alpine:latest
  script:
    - apk add --no-cache kubectl
    - kubectl set image deployment/my-app app=${CI_REGISTRY_IMAGE}:${CI_COMMIT_SHORT_SHA}
  environment:
    name: production
    url: https://example.com
  when: manual
  only:
    - tags
```

### Multi-Project Pipeline

```yaml
# Trigger downstream pipeline
trigger-frontend:
  stage: deploy
  trigger:
    project: myorg/frontend
    branch: main
    strategy: depend

# Multi-project pipeline with artifacts
deploy:
  stage: deploy
  variables:
    UPSTREAM_COMMIT: ${CI_COMMIT_SHA}
  trigger:
    project: myorg/deployment
    branch: main
    strategy: depend
```

### Docker & Registry

```yaml
docker-build:
  stage: build
  image: docker:20
  services:
    - docker:20-dind
  variables:
    DOCKER_HOST: tcp://docker:2375
    DOCKER_TLS_CERTDIR: ""
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  only:
    - main
```

## Real-World Usage

- **Monorepo per-path pipelines** — parent-child with `rules:changes:` keeps a 50-service repo from running 50 pipelines per push: the parent triggers only children whose paths changed, and `strategy: depend` (as in the multi-project example) keeps MR status honest across repos.
- **Review Apps per merge request** — `environment: name: review/$CI_COMMIT_REF_SLUG` plus `rules: if: $CI_PIPELINE_SOURCE == "merge_request_event"` deploys every MR to an ephemeral URL; paired with `environment: on_stop:` and a scheduled cleanup job, the environments list becomes the source of truth for what's currently deployed where.
- **Compliance via central templates** — organizations `include:` from a central pipeline-template repo (with `include` pinned to a ref), so SAST/dependency-scanning and deploy-gate jobs are mandated once and updated everywhere in one commit — the GitLab-shaped answer to pipeline drift across a hundred repos.
- **The security stage is opt-in-looking but config-light** — SAST, secret detection, dependency and container scanning attach as jobs (often via the included templates) and surface findings in the MR security widget; the senior move is wiring them as MR-blocking gates, not advisory dashboards.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------- | ----------------------------------------------------------------------------- |
| `only`/`except` in new pipelines | `rules` — composable, MR-aware, and the only non-deprecated form |
| Cache as the delivery mechanism | Artifacts pass outputs between jobs; cache is best-effort speed |
| Branch-blind cache keys | Key by commit or lockfile hash; shared caches leak between branches |
| No `needs` in a large pipeline | Every job waits for its whole stage — the DAG is the speed lever |
| Long-lived credentials in CI variables | `CI_JOB_TOKEN` / short-lived tokens; protected variables + protected branches |
| dind on Kubernetes runners | Privileged containers for what kaniko/buildkit do rootless |
| Deploy jobs without `environment:` | Environments carry protection rules, approvals, and deploy history |

## Best Practices

1. **Use `needs`** to run jobs in parallel and reduce pipeline time
2. **Cache dependencies** between runs (node_modules, gems)
3. **Use `rules`** instead of deprecated `only`/`except`
4. **Include templates** for reusable pipeline configuration
5. **Set job timeouts** to prevent runaway pipelines
6. **Use GitLab Container Registry** for storing Docker images
7. **Implement protected environments** for production deployments

## Summary

- GitLab CI/CD is integrated directly into GitLab for a unified DevOps lifecycle
- Pipelines are defined in .gitlab-ci.yml with stages, jobs, and parallel execution
- GitLab Runners execute jobs and can be shared, specific, or auto-scaled on cloud providers
- Built-in container registry, artifact management, and environment management simplify deployments
- Auto DevOps provides automated CI/CD pipelines with review apps and continuous deployment

# GitLab CI/CD

A merge request can pass its tests while the release job receives an artifact from the wrong producer or credentials from an untrusted branch. GitLab's pipeline graph is useful only when event rules, artifacts, and protected resources preserve the intended boundary.

## Definition

**GitLab CI/CD** is GitLab's continuous integration and delivery platform. A pipeline is usually defined in `.gitlab-ci.yml`; its jobs run on configured GitLab Runners and exchange data through artifacts, caches, and downstream pipelines. Registry, security-scanning, and deployment integrations depend on the GitLab edition and project configuration.

> **Textbook Definition:** GitLab CI/CD executes repository-defined pipelines through runners, using job dependencies, artifacts, variables, and environment controls to automate integration and delivery under specified permissions.

## First Principles

A merge request can change the code, build instructions, and test commands. It must receive enough authority to run verification without receiving production credentials. Different jobs also need an explicit way to pass outputs: runner-local files and caches are not an approved release. Separate verification, artifact identity, and deployment authorization before optimizing parallelism.

## 1. Select Pipelines and Jobs from Events and Rules

GitLab reads the pipeline configuration for an event and evaluates `workflow: rules` to decide whether a pipeline exists. Job `rules` decide which jobs enter it. Rules are evaluated in order; the first matching rule determines behavior.

By default, stages sequence and jobs within a stage can run concurrently. `needs` declares a dependency graph and can let a job start before unrelated earlier-stage work finishes. With `needs`, request artifacts from the intended producer explicitly. A dependency on a job that rules exclude needs matching selection or a deliberate optional relationship.

An ordinary merge-request pipeline tests source-branch content. A **merged-results pipeline** separately tests a temporary result incorporating the target branch. Do not present one as evidence of the other. Changes to shared packages, lockfiles, and pipeline configuration can affect more than the directly edited app directory.

Runners execute the jobs according to their executor. Docker/Kubernetes executors provide job containers or Pods, but their host resources, mounts, and credentials still define trust boundaries. Shell executors reuse a host environment. Tagging a job `protected` does not automatically make its runner ephemeral or safe for untrusted code; configure runner eligibility and protected resources explicitly.

## 2. Verify First, Promote an Identified Artifact

This template assumes committed `package-lock.json`, scripts `lint`, `typecheck`, `test:ci`, `build`, and `deploy:production`, with build output in `dist/`. The deploy script must consume `release/dist`, publish it to the intended provider, check readiness, and fail on errors. Production protection/approval rules and scoped credentials must be configured in GitLab separately.

```yaml
# .gitlab-ci.yml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
    - when: never

stages: [verify, deploy]

default:
  image: node:24-alpine

verify:
  stage: verify
  timeout: 20m
  cache:
    key:
      files: [package-lock.json]
    paths: [.npm/]
  script:
    - npm ci --cache .npm --prefer-offline
    - npm run lint
    - npm run typecheck
    - npm run test:ci
    - npm run build
    - mkdir -p release
    - cp -R dist release/dist
    - printf '%s\n' "$CI_COMMIT_SHA" > release/commit.txt
  artifacts:
    paths: [release/]
    expire_in: 7 days

deploy-production:
  stage: deploy
  timeout: 20m
  needs:
    - job: verify
      artifacts: true
  cache: []
  resource_group: production
  environment:
    name: production
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
      when: manual
      allow_failure: false
    - when: never
  script:
    - test "$(cat release/commit.txt)" = "$CI_COMMIT_SHA"
    - npm ci --ignore-scripts
    - npm run deploy:production -- --artifact release/dist
```

Trace a merge request: verification runs, uploads its output, and no production job is selected. Trace a trusted default-branch push: verification succeeds, the release job downloads that producer's output and waits for an authorized manual action plus configured environment protections. The checked SHA marker narrows accidental mixups; it is not cryptographic provenance. Record and verify the artifact/image digest when that is the release identity.

The deployment example assumes tooling can install without lifecycle scripts. If that is false, prepare reviewed tooling in a trusted job rather than silently allowing arbitrary installation scripts next to production credentials. `resource_group` limits overlap; configure deployment freshness and ordering policy separately so an approved old pipeline cannot overwrite a newer release.

## 3. Cache Speeds Work; Artifacts Carry Outputs

The npm cache stores reconstructible downloads. `npm ci` still installs the locked dependency set; a cache miss must not prevent a correct build. Cache sharing depends on runner storage and project/protected-resource settings, so treat it as best-effort and keep privileged jobs away from untrusted cache writers.

Artifacts identify a producing job's output and can carry test reports, coverage, or build files. Set retention and access deliberately. Do not upload secrets, browser auth state, or sensitive traces. A report file missing from disk is not a passed report gate; configure the test runner to produce the declared format before adding `reports:` entries.

## 4. Authenticate to Cloud Services with Job Identity

Prefer GitLab ID tokens with a narrowly scoped cloud trust policy over long-lived cloud keys stored as CI variables. Set an explicit audience for the intended provider, then have that provider verify the issuer, audience, project, and protected-ref or environment claims before issuing short-lived credentials. A token is only as safe as the pipeline code allowed to request and use it; do not grant production trust to unreviewed merge-request code.

## 5. Treat Services as Real Dependencies with Startup Contracts

A PostgreSQL service must receive the database/user/password expected by the test. Its service alias determines the hostname from a job container. Define those values explicitly and wait for a meaningful database readiness check before running integration tests; starting a service is not proof it accepts queries. Keep disposable test data and credentials isolated. Do not put Node-only `before_script` commands on a deploy job using a plain Alpine image.

## 6. Build and Publish Images with an Explicit Trust Boundary

Docker-in-Docker commonly requires privileged runner configuration; an unencrypted daemon endpoint is not a harmless convenience. Current GitLab documents rootless BuildKit as an alternative, with explicit registry authentication and runner security prerequisites. Kaniko's former upstream project is archived; do not teach it as the unqualified current default.

Use a maintained pinned builder, install registry auth through the supported secret mechanism, build/push the intended image, and capture its digest. Verification and promotion must use that digest. The fact that a command uses `$CI_COMMIT_SHORT_SHA` as a tag does not establish that this image was tested or even pushed. Never put a password in `docker login -p`; use the tool's supported stdin or credential configuration and restrict logs.

## 7. Coordinate Parent/Child and Multi-Project Pipelines

A child pipeline can split a large repository's configuration; a multi-project trigger can coordinate another repository. A trigger starts a downstream run, not an automatic artifact transfer. `strategy: mirror` mirrors downstream status and was introduced in GitLab 18.2 — check the installed version before using it. Existing `depend` semantics can differ around manual jobs.

Pin included templates/components to reviewed versions and declare intended inputs and token scopes. Forwarding a commit variable does not make the downstream repository check out that commit. Verify ref selection and artifact origin explicitly. Path selection must include shared inputs and deletions, and periodic wider integration checks can catch dependency relationships not inferred by the graph.

## Real-World Use Cases

- **Review apps.** Use a deliberately isolated environment with a cleanup/stop job and TTL. Untrusted branches should not receive production secrets merely because their preview is convenient. Bound database cost, external calls, and access to internal networks.
- **Protected releases.** Restrict deploy credentials, eligible runners, and environment permissions. A masked variable can still be leaked in transformed output; pipeline code executes with accessible secrets. Review fork-origin changes before running them in a parent project's resource context.
- **Central policy.** Includes reduce duplication, but a configuration include by itself does not prevent projects from removing a mandated gate. Match enforcement to the organization's actual configuration/security-policy features and subscription.

## Common Mistakes

| Mistake | Failure mechanism | Better boundary |
| --------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------ |
| Call an ordinary MR run a merged-result test | Target changes are absent | Configure and identify merged-results coverage |
| Deploy an image that no job built/pushed | A tag label is mistaken for an artifact | Verify producer and resolved digest |
| Pass dist through a dependency cache | Restoration is optional and may select stale content | Request artifacts from the intended job |
| Give every branch deploy variables | Repository code can read them | Protected resources and explicit trust selection |
| Select only app paths | Shared contracts/lockfiles can change behavior | Dependency-aware selection with tested cases |
| Treat runner containers as complete isolation | Host mounts/network/credentials remain | Explicit executor lifecycle and threat model |

## Best Practices

Show the event, selected jobs, output producer, and deploy authority in one trace. Use ordered rules, explicit artifact relationships, and tested runtime prerequisites. Keep cache misses harmless, credentials scoped, protection rules configured, and rollout/restore evidence separate from YAML syntax validation.

## Summary

GitLab selects pipelines and jobs from events and rules. Stages and needs define ordering, artifacts carry identified outputs, and protected resources define release authority. Trace the producer and deployment target explicitly; caching, a manual button, and a SHA tag do not certify a release.

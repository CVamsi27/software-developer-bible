# Jenkins CI/CD

## Definition

**Jenkins** is an open-source automation server for building, testing, and deploying software. It supports declarative and scripted pipelines, distributed builds, extensive plugin ecosystem, and integration with virtually all DevOps tools. Jenkins pipelines are defined in a `Jenkinsfile` using Groovy-based DSL.

## First Principles

Jenkins is self-hosted automation freedom with self-hosted automation costs:

1. **Plugins are the power and the liability**: every integration exists, and every plugin is supply-chain surface plus upgrade risk (→ 20.5.3.05's dependency problem, in a server).
2. **The controller must not run builds**: agents execute, controller orchestrates — the controller is state (config, plugins, history) and its loss is the real disaster; backup + IaC-reproducible controller (→ 40.12) is the discipline.
3. **Pipelines-as-code (Jenkinsfile) was the reformation**: from UI-configured jobs (unversionable) to repo-committed pipelines — the same config-as-code migration every platform eventually makes.

## Why Do We Need It?

1. **Pipeline as Code**: Define entire CI/CD pipeline in version-controlled `Jenkinsfile`
2. **Extensibility**: 1,800+ plugins for every tool in the DevOps ecosystem
3. **Distributed builds**: Master/agent architecture for scaling build capacity
4. **Mature ecosystem**: Battle-tested in enterprise environments for decades
5. **Flexibility**: Support for any SCM, build tool, or deployment target

## Code Examples

### Declarative Pipeline

```groovy
// Jenkinsfile (Declarative Pipeline)
pipeline {
    agent any

    parameters {
        choice(name: 'ENV', choices: ['dev', 'staging', 'prod'], description: 'Deploy environment')
        string(name: 'VERSION', defaultValue: '1.0.0', description: 'Release version')
    }

    environment {
        DOCKER_REGISTRY = 'registry.example.com'
        APP_NAME = 'my-app'
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Install Dependencies') {
            steps {
                sh 'npm ci'
            }
        }

        stage('Lint') {
            steps {
                sh 'npm run lint'
            }
        }

        stage('Test') {
            steps {
                sh 'npm run test:ci'
            }
            post {
                always {
                    junit 'reports/**/*.xml'
                }
            }
        }

        stage('Build') {
            steps {
                sh 'npm run build'
            }
        }

        stage('Docker Build & Push') {
            when {
                branch 'main'
            }
            steps {
                sh """
                    docker build -t ${DOCKER_REGISTRY}/${APP_NAME}:${VERSION} .
                    docker push ${DOCKER_REGISTRY}/${APP_NAME}:${VERSION}
                """
            }
        }

        stage('Deploy') {
            when {
                branch 'main'
            }
            steps {
                script {
                    if (params.ENV == 'prod') {
                        input message: 'Deploy to production?', ok: 'Deploy'
                    }
                }
                sh "kubectl set image deployment/${APP_NAME} app=${DOCKER_REGISTRY}/${APP_NAME}:${VERSION}"
            }
        }
    }

    post {
        always {
            cleanWs()
        }
        failure {
            slackSend(
                channel: '#deployments',
                message: "Build failed: ${env.BUILD_URL}"
            )
        }
        success {
            slackSend(
                channel: '#deployments',
                message: "Build succeeded: ${env.BUILD_URL}"
            )
        }
    }
}
```

### Scripted Pipeline

```groovy
// Jenkinsfile (Scripted Pipeline)
node('linux') {
    stage('Checkout') {
        checkout scm
    }

    stage('Build') {
        docker.image('node:20-alpine').inside {
            sh 'npm ci'
            sh 'npm run build'
        }
    }

    stage('Test') {
        parallel(
            unit: {
                sh 'npm run test:unit'
            },
            integration: {
                sh 'npm run test:integration'
            }
        )
    }

    stage('Deploy') {
        if (env.BRANCH_NAME == 'main') {
            build job: 'deploy-to-prod', parameters: [
                string(name: 'BUILD_TAG', value: env.BUILD_TAG)
            ]
        }
    }
}
```

### Shared Library

```groovy
// vars/buildNodeApp.groovy
def call(Map config = [:]) {
    pipeline {
        agent any
        environment {
            NODE_VERSION = config.nodeVersion ?: '20'
        }
        stages {
            stage('Setup') {
                steps {
                    sh "node --version"
                    sh "npm ci"
                }
            }
            stage('Quality') {
                parallel {
                    stage('Lint') {
                        steps { sh 'npm run lint' }
                    }
                    stage('Test') {
                        steps {
                            sh 'npm run test:ci'
                            junit 'reports/**/*.xml'
                        }
                    }
                }
            }
            stage('Build') {
                steps { sh 'npm run build' }
            }
        }
    }
}

// Jenkinsfile using shared library
@Library('my-shared-library') _

buildNodeApp(nodeVersion: '20')
```

## Real-World Usage

- **The controller/agent split is the architecture interview answer**: the controller stores state (config, plugins, job history) and orchestrates; **agents execute** — statically provisioned VMs, or the Kubernetes plugin spinning ephemeral pods per build. Builds on the controller are the classic self-inflicted outage: a runaway `sh` step OOMs the process that holds every job's history and credentials. `agent any` in the examples above is fine for a demo; production pins labels (`agent { label 'docker && linux' }`) so work lands on capable agents.
- **Shared libraries are the scaling mechanism — and the trust boundary**: `vars/*.groovy` with a `call(Map)` turns a 200-line Jenkinsfile into `buildNodeApp(...)` across hundreds of repos, but the library executes *inside* every consuming pipeline with full credentials — so it lives in a separate, locked-down repo (`@Library` with a pinned version, not `main`), or pipeline integrity silently becomes whoever-can-push-to-the-library's problem.
- **Plugin discipline is the operational tax**: plugins updated ad hoc drift the controller; a Weekly-update cadence with a staging controller (or `pluginInstallationMonitor`) catches breakage before production. Every plugin is also supply-chain surface — the 2024 `view-job-filters` incident (malicious post-compromise releases) is the canonical argument for minimizing plugins and pinning versions in Configuration-as-Code (JCasC exports the entire controller config as YAML — the reproducible-controller discipline the First Principles name).
- **Why new teams choose hosted CI instead**: the cost is not the Jenkins license (free) but the operations — controller upgrades, plugin compatibility matrices, agent capacity, security patches — a standing platform-team obligation. Jenkins remains the right answer where self-hosting is mandated, ecosystems (mainframes, exotic hardware agents) demand it, or a decade of pipeline investment would be rewritten; greenfield teams inherit that cost for nothing.
- **Scripted vs declarative in practice**: declarative's structure (stages, `post`, `when`, `input` gates) is lintable and legible; scripted Groovy is full programming power with zero guardrails — arbitrary code in a privileged context, which is how credential leakage and infinite loops happen. The house rule: declarative + shared-library steps; scripted only inside a library function with a reason.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------- | ------------------------------------------------------------------------------ |
| Running builds on the controller | Agents execute; controller orchestrates — an OOM there loses state and history |
| `agent any` everywhere | Pin labels for toolchain requirements; capacity planning is per-label |
| Shared library from `main`, unversioned | Pin versions; the library runs with full credentials in every pipeline |
| Ad-hoc plugin updates on prod controller | Cadenced updates via a staging controller; JCasC to make config reproducible |
| Secrets as env vars echoed in logs | Credentials Store + `wrap([$class: ...])` masking; audit `sh` steps for echoes |
| Groovy scripting in Jenkinsfiles | Declarative + library steps; arbitrary Groovy in-pipeline is a security hole |
| No `cleanWs()` in `post` | Disk fills with workspace leftovers; flaky builds from stale artifacts |

## Best Practices

1. **Use Declarative Pipeline** over Scripted for readability
2. **Store credentials** in Jenkins Credentials Store, never in code
3. **Use Shared Libraries** for reusable pipeline code
4. **Clean workspace** in `post { always { cleanWs() } }` block
5. **Parallelize stages** for faster feedback
6. **Use when conditions** to skip unnecessary stages
7. **Implement approval gates** for production deployments

## Summary

- Jenkins is a self-hosted automation server for building, testing, and deploying software
- Pipeline as Code (Jenkinsfile) defines CI/CD workflows using Declarative or Scripted pipeline syntax
- Master-agent architecture distributes build workloads across multiple worker nodes
- Extensive plugin ecosystem integrates with SCM, build tools, test frameworks, and cloud providers
- Blue Ocean provides a modern UI for pipeline visualization and monitoring

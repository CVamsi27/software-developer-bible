# Jenkins CI/CD

## Definition

**Jenkins** is an open-source automation server for building, testing, and deploying software. It supports declarative and scripted pipelines, distributed builds, extensive plugin ecosystem, and integration with virtually all DevOps tools. Jenkins pipelines are defined in a `Jenkinsfile` using Groovy-based DSL.

> **Textbook Definition:** Jenkins is an extensible automation server that schedules and executes build and delivery jobs, distributing work to agents and defining pipeline behavior through configuration or versioned pipeline code.

## First Principles

A build executes repository code, while the automation server owns job configuration, history and credentials. A test must not acquire server or deployment authority just because it needs a runner. Keep the controller's scheduling/state responsibility separate from agents that execute build steps, and define how an approved artifact crosses into a release job.

## Controller, Agent and Workspace

The **controller** schedules work and stores configuration/history. An **agent** supplies an executor and tools. A **workspace** is the filesystem allocated for a job's checkout/output; it can retain files unless deliberately isolated or cleaned. Labels select eligible agents, not a particular tool version or security boundary.

```text
repository event → controller schedules pipeline → eligible agent executes steps
                                               → identified test/build output
trusted release job ← explicit artifact transfer + authorization
```

A Jenkinsfile is executable Groovy-based pipeline code. Declarative syntax supplies structured stages, conditions and post actions; scripted syntax supplies flexible program flow. Neither syntax alone prevents credential exposure or makes untrusted repository code safe.

## Example: Verify on a Prepared Agent

This example assumes a `node24-linux` agent has the intended Node/npm toolchain, a committed lockfile, project scripts and the Pipeline/JUnit/workspace-cleanup plugins. The test script must create the declared XML reports. Multibranch source discovery and credential policy must be configured outside this file.

```groovy
pipeline {
    agent { label 'node24-linux' }
    options {
        skipDefaultCheckout(true)
        timeout(time: 20, unit: 'MINUTES')
        disableConcurrentBuilds()
    }
    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Verify') {
            steps {
                sh 'node --version && npm --version'
                sh 'npm ci'
                sh 'npm run lint'
                sh 'npm run typecheck'
                sh 'npm run test:ci'
                sh 'npm run build'
            }
            post {
                always { junit 'reports/**/*.xml' }
            }
        }
        stage('Archive') {
            steps {
                archiveArtifacts artifacts: 'dist/**', fingerprint: true
            }
        }
    }
    post {
        always { cleanWs() }
    }
}
```

A failing command prevents the normal archive stage. `post always` publishes diagnostics even on failure; it must not silently certify a missing test report. `fingerprint` supports artifact tracking, but a release still needs the intended job/build, commit and integrity evidence. Workspace cleanup reduces stale-file reuse; it does not undo code that compromised the agent or stole accessible credentials.

## Deploy in a Separate Trusted Job

A main-branch condition is useful selection, not a complete authorization policy. Give a release job only the approved immutable artifact and intended environment. Configure credentials, authorized approvers, target cluster/context, namespace and rollout checks there. Do not let a free-form `ENV` parameter decide whether approval is required while the command always uses the same default cluster.

Avoid Groovy interpolation of caller-controlled parameters into `sh` source. Validate parameter values, pass them as environment data and quote shell expansions. Credentials-binding masking reduces accidental logging; anyone able to modify the credentialed pipeline can intentionally exfiltrate secrets. Keep untrusted jobs off credentialed agents and avoid sharing workspaces/process access with them.

Approval and serialization do not ensure release freshness. Compare the desired revision before promotion and define rollback against database/schema compatibility. Passing a `BUILD_TAG` to another job does not automatically make that job retrieve or verify the producer's artifact.

## Scripted Pipelines Must Keep Tool and File Ownership Clear

When `docker.image(...).inside` exits, subsequent steps run in the surrounding agent environment. Building in a Node container and then testing on an unspecified host silently changes the runtime. Keep the required steps in the intended container or prepare the host toolchain explicitly. Native dependencies installed inside Alpine may not work on a glibc host.

Parallel tasks can also race when writing the same workspace, report directory or build output. Isolate their work directories and dependencies, then collect distinct reports. A Groovy `parallel` block changes scheduling; it does not establish independent files or make a side-effecting deployment safe.

## Shared Libraries Reuse a Reviewed Contract

A `vars/buildNodeApp.groovy` step with `call(Map)` can standardize checkout, tooling, verification and artifact handling. Pin the library revision and control who can publish it. A configuration value named `NODE_VERSION` does not install Node or select a Docker image; the library must actually provision/select that toolchain.

Libraries may be trusted or sandboxed according to Jenkins configuration. Trusted library code can use privileges beyond ordinary sandboxed pipeline code; both can interact with credentials actually made available to their job. Avoid the blanket assumption that every library automatically has every server credential. Declare expected plugins, labels, scripts, outputs and permissions so consumers understand the contract.

## Operate the Automation Server as a Production Service

Keep build execution off the controller, minimize plugin/API exposure and test controller/plugin upgrades in staging. Configuration as Code can reproduce supported configuration, but it is not a complete backup of credentials, build history or every plugin state. Inventory those separately and test recovery. Agent capacity, queue time and controller availability are distinct metrics.

Ephemeral agents reduce retained build state; host sockets, privileged containers, network access and mounted secrets still define their blast radius. Docker socket access grants powerful control of the Docker host and is not an ordinary build-cache mount.

Evaluate a hosted alternative against required integrations, hardware, data boundaries and operational cost. Jenkins supports environments hosted CI may not, but its free license does not eliminate controller/security/agent operations.

## Common Mistakes

| Mistake | Why it fails | Better contract |
| -------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| Run arbitrary builds on controller | Build code gains access to critical server resources | Separate restricted agents |
| Use agent any as tool installation | A label/executor is not a pinned runtime | Prepared toolchain or declared container agent |
| Test outside the build container | Runtime/native dependency environment changes | Keep steps in the intended environment |
| Interpolate parameters/secrets into Groovy shell strings | Generated shell can execute unintended text or expose values | Validate and pass quoted environment data |
| Share output directories across parallel branches | Report/build files race | Isolated workspaces and artifact names |
| Treat input approval as full deployment policy | Target identity/artifact freshness remain unchecked | Authorized release job with explicit desired revision |
| Assume JCasC is a full recovery backup | History/secrets/plugin state can remain outside exports | Tested configuration and state restore |

## Best Practices

Make controller/agent/toolchain ownership, executable repository trust and artifact transfer explicit. Keep credentialed release operations separate, pin reviewed library/plugin inputs, collect real report evidence and test failure, timeout, cleanup and restore behavior. Pipeline syntax validation is separate from a successful Jenkins integration run.

## Summary

Jenkins separates controller scheduling from agent execution. A Jenkinsfile relies on prepared tools, plugins and credential policy; its syntax alone cannot reproduce or secure a release. Verify on restricted agents, transfer an identified artifact into authorized promotion and operate controller state and recovery deliberately.

# Argo CD (GitOps)

A deploy command may return successfully while the cluster has drifted, Pods are not ready, or a database migration has already changed state. GitOps gives the team a durable desired state and a controller that repeatedly compares it with the cluster.

## Definition

**Argo CD** is a declarative GitOps continuous-delivery controller for Kubernetes. It renders manifests from configured sources, compares them with tracked live resources, and applies changes according to each application's synchronization policy. Git provides the reviewed desired state; the controller repeatedly reconciles it with the cluster.

> **Textbook Definition:** Argo CD is a Kubernetes delivery controller that compares rendered desired configuration from versioned sources with cluster state and applies changes according to configured synchronization and reconciliation policies.

## First Principles

A release changes several resources at different times. A deployment client can disappear halfway through, and operators can change live resources afterward. Keep a durable desired configuration and compare it with observed state repeatedly. The controller can retry convergence; it cannot reverse arbitrary database writes or guarantee that a healthy-looking workload satisfies its business contract. Use reconciliation when teams need reviewed deployment intent, drift visibility, and a repeatable route from configuration to cluster state. CI still builds and checks the artifact; Argo CD consumes its reference. A manifest-writing credential can influence production even without direct cluster access, so protect that repository, allowed sources, target namespaces, and controller permissions.

## 1. Reconcile Rendered Desire Against Live State

```text
reviewed source revision → repo server renders manifests
                         → application controller compares/apply resources
                         → Kubernetes controllers create workloads
API server → UI/CLI, authentication and authorization
```

The **repo server** prepares desired manifests using the configured Helm, Kustomize, or plugin tooling. The **application controller** compares them with live resources and applies synchronization policy. The **API server** exposes UI/CLI operations. Rendering repository-controlled configuration is executable work; plugin, repository, and controller permissions remain security boundaries.

**Sync status** answers whether desired and live configuration agree. **Health status** answers whether resource-specific observations meet configured health criteria. A Deployment can be Synced while its Pods are failing, and a Healthy Deployment can still return incorrect prices. Polling/webhooks trigger refresh according to controller configuration; a fixed three-minute interval is not a universal contract.

Synchronization orders resources by phase, wave, and resource ordering. `PreSync` hooks run before the main apply; ordinary resources use the Sync phase; `PostSync` hooks run after successful synchronization and healthy resources. `SyncFail` is a failure hook, not a transactional undo. Hooks do not run during selective sync. A stuck resource in an earlier wave can prevent later work; inspect that resource instead of increasing retries blindly.

## 2. Trace Drift and a Failed Release

Suppose Git requests image B while the cluster runs A. Rendering must succeed before a meaningful diff exists. Sync then updates the Deployment; Kubernetes begins the rollout. If B fails readiness, inspect the workload, events, and sync result. Agreement on image B does not mean B serves traffic successfully.

A manual edit to an Argo-tracked resource can be overwritten when self-heal is enabled. An incident policy must establish who controls desired state, pause the relevant automation deliberately, and record the repair in Git. Prefer a reviewed forward change to a compatible known-good digest; a rollback command cannot restore deleted rows or undo payments.

## 3. Keep Hooks, Progressive Delivery, and Deletion Separate

A migration hook must be idempotent or safely repeatable and compatible with both old and new application versions during overlap. Successful hook deletion cleans its Job object; it does not remove the migration's effects. Selective sync skips hooks, so use a complete synchronization when the release depends on them.

Argo CD does not itself implement metric-driven canary rollback. Argo Rollouts is a separate controller with its own analysis and traffic-routing configuration. Sync waves arrange application, while health checks observe resources; neither establishes an automatic rollback policy by itself.

`prune` permits removal of managed resources no longer declared. `PruneLast=true` changes ordering, not data-loss protection. Assess persistent resources, finalizers, and deletion policy before enabling it. `selfHeal` handles drift according to policy; it is not an authorization rule for who may change Git.

## 4. Operate Sources and Secrets

Pin or identify the rendered source and image digest, control who can alter production intent, and use narrow AppProjects/controller access. Helm/Kustomize/tool versions affect rendering. Hard refresh can help diagnose cached generation, but invalid values, permissions, and nondeterministic generators can also produce unexpected manifests.

Keep plaintext secrets out of Git. Secret operators and sealed ciphertext introduce key-management, access, and recovery requirements; they do not remove those requirements. Separate applications by meaningful ownership/release boundaries and test ordering between them explicitly.

## Code Examples

### Application Definition

This template requires installed Argo CD CRDs, an authorized source repository, registered destination, and existing manifests. Replace the sample source with a reviewed repository and promote an immutable image digest inside its manifests. The built-in `default` AppProject is permissive; production projects should explicitly restrict source repositories, destination clusters/namespaces, and permitted resource kinds.

```yaml
# application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/org/my-app.git
    targetRevision: main
    path: k8s/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      allowEmpty: false
    syncOptions:
      - CreateNamespace=true
      - PruneLast=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
```

### ApplicationSet (Multi-Environment)

An ApplicationSet generates Applications. This example lives in the Argo CD control-plane namespace, `argocd`; observing ApplicationSets in other namespaces requires explicit controller configuration. Register the named cluster and repositories first; generation does not create cluster credentials. Its controller owns generated fields, so changing a child directly may be overwritten.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: my-app-environments
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - env: dev
            namespace: dev
            cluster: https://kubernetes.default.svc
          - env: staging
            namespace: staging
            cluster: https://kubernetes.default.svc
          - env: prod
            namespace: prod
            cluster: https://prod-cluster.example.com
  template:
    metadata:
      name: 'my-app-{{env}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/org/my-app.git
        targetRevision: main
        path: 'k8s/overlays/{{env}}'
      destination:
        server: '{{cluster}}'
        namespace: '{{namespace}}'
      syncPolicy:
        automated:
          selfHeal: true
```

### Sync Waves and Lifecycle Hooks

```yaml
# 1. PreSync Hook: Database Migration Job (Wave -1)
apiVersion: batch/v1
kind: Job
metadata:
  name: db-schema-migration
  namespace: production
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
    argocd.argoproj.io/sync-wave: "-1"
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: my-registry.example.com/db-migrator:v2.4.0 # illustrative tag; production should use a reviewed digest or enforced immutable tag
          command: ["./migrate", "up"]
---
# 2. Main Service Deployment (Wave 0)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "0"
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
        - name: app
          image: my-registry.example.com/order-service:v2.4.0 # illustrative tag; production should use a reviewed digest or enforced immutable tag
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
```

### Rollback and Operational CLI Commands

```bash
# Check app status, sync status, and active drift
argocd app get my-app

# Inspect live diff between Git desired state and K8s live state
argocd app diff my-app

# Manually trigger a sync with pruning enabled
argocd app sync my-app --prune

# Inspect deployment history and revisions
argocd app history my-app

# After following the incident policy and disabling automated sync,
# select a known compatible history ID (example: 3). --prune permits
# removal of unexpected resources during the rollback.
argocd app rollback my-app 3 --prune

# Configure automated self-heal and auto-prune directly via CLI
argocd app set my-app --sync-policy automated --auto-prune --self-heal
```

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auto-sync with `prune` before the team understands it | Deleted manifests disappear live resources; enable prune deliberately, per app |
| Trusting the `status` without reading sync conditions | `OutOfSync` + error conditions carry the actual reason; the UI dot hides it |
| Expect self-heal to remove every manually created resource | Self-heal reconciles tracked resources; unrelated objects may remain orphaned, so manage them through the application or monitor scoped namespaces |
| Plaintext secrets in Git | External Secrets/Sealed Secrets; the repo must remain safely clonable |
| One giant Application for a whole system | Per-service Applications; blast radius and rollback granularity are per-app |
| Treating unexpected output as a cache diagnosis | Confirm source revision, values/parameters and renderer first; hard refresh tests cached generation but cannot repair invalid inputs |

## Best Practices

Choose automatic sync, self-heal, and pruning deliberately for each environment. Restrict source and destination access, promote identified artifacts, and distinguish sync status from health and user-visible behavior. Rehearse hotfix, failed-hook, deletion, and compatible-revert procedures. Retry limits/backoff bound attempts; they are not Pod CPU or memory limits.

## Summary

Argo CD repeatedly reconciles rendered desired configuration with Kubernetes state. Trace rendering, comparison, application, and workload health separately. Automatic sync, self-heal, and pruning are explicit policies; hooks and waves order work, while database recovery and metric-driven progressive delivery need their own mechanisms.

# Docker Build & Deploy Pipeline

Two deployments from the same source commit can contain different base images or dependencies. A reliable pipeline records the tested image identity and promotes those exact bytes through each environment.

## Definition

A **container build-and-deploy pipeline** turns versioned source and declared build inputs into an image, validates and publishes it, then deploys the identified artifact to a target environment. Repeatable steps help consistency, but reproducibility requires controlling every relevant input.

> **Textbook Definition:** A container build-and-deploy pipeline converts versioned source and declared dependencies into an identified image, validates that artifact, publishes it to a registry, and deploys the validated digest.

## First Principles

A source commit does not identify the bytes a builder produces: base images, dependency downloads, tool versions, and configuration also contribute. A second build can differ. Preserve a tested image identity, then make every release gate and deployment refer to that identity. Separate build authority from registry publication and production authority.

## 1. Follow One Candidate Through the Pipeline

```text
source + locked inputs → build candidate → runtime tests + image scan
                       → publish identified digest → staging checks
                       → production promotion of that digest
```

A **tag** is a name that may move. A **manifest digest** identifies registry content; a local Docker image ID identifies image configuration and is not interchangeable with a registry manifest digest. For multi-platform images, an index digest selects platform-specific manifests. Record which platforms were actually tested and scanned.

A vulnerability scan examines the selected image against a database/policy. It cannot establish that an application works or that the builder was trustworthy. Record the image identity, scanner/database time, policy, and reviewed exceptions. Scanning source files alone is a different check.

## 2. Build a Candidate with a Real Runtime Contract

Save these two files in an empty directory. This demonstration has no npm dependencies; a real application must install from its lockfile and test its actual production dependencies.

```javascript
// server.mjs
import { createServer } from 'node:http';
createServer((request, response) => {
  if (request.url !== '/health') {
    response.writeHead(404); response.end('Not found'); return;
  }
  response.writeHead(200, { 'content-type': 'application/json' });
  response.end(JSON.stringify({ status: 'ok' }));
}).listen(3000, '0.0.0.0');
```

```dockerfile
FROM node:24-alpine
WORKDIR /app
COPY --chown=node:node server.mjs ./
USER node
EXPOSE 3000
CMD ["node", "server.mjs"]
```

The base tag keeps the example readable but can move. A release should use a reviewed base digest and deliberate update process. Build once and test the local candidate:

```bash
docker build -t bible-pipeline-demo:candidate .
docker run -d --name bible-pipeline-demo   --read-only --cap-drop=ALL --security-opt=no-new-privileges   -p 127.0.0.1:4301:3000 bible-pipeline-demo:candidate
curl --fail --retry 10 --retry-connrefused --retry-delay 1   http://127.0.0.1:4301/health
docker inspect --format '{{.Image}}' bible-pipeline-demo
docker image inspect --format '{{.Id}}' bible-pipeline-demo:candidate
docker rm -f bible-pipeline-demo
```

The two inspection values should agree: the container runs the candidate's local image configuration. The health endpoint checks this tiny process, not database readiness, integration correctness, or production capacity. Keep a separate test that fails on wrong content and unexpected status, rather than relying only on successful connection.

## 3. Publish, Resolve, and Promote the Same Digest

After tests and the required image scan pass, an authenticated registry job publishes the candidate. Configure registry permissions and scanner tooling first; commands below are a template for your registry, not a claim that the public example has been published.

```bash
# Set IMAGE to your authorized lowercase registry/repository and TAG to a candidate ID.
: "${IMAGE:?required}" "${TAG:?required}"
docker tag bible-pipeline-demo:candidate "$IMAGE:$TAG"
docker push "$IMAGE:$TAG"
# With an installed reviewed crane CLI:
DIGEST=$(crane digest "$IMAGE:$TAG")
case "$DIGEST" in sha256:*) ;; *) exit 1 ;; esac
printf '%s@%s\n' "$IMAGE" "$DIGEST" > candidate-reference.txt
```

Validate the complete digest format and expected repository in the promotion service. Carry that reference and its evidence across jobs explicitly; jobs do not share local images automatically. Use registry candidates or exported image artifacts with verified producer/integrity. A later job that rebuilds from the same Git SHA has not necessarily retrieved the tested image.

A Kubernetes release also requires an authenticated, intended cluster context, namespace, existing Deployment/container, and timeout:

```bash
: "${CONTEXT:?required}" "${NAMESPACE:?required}" "${IMAGE_REFERENCE:?required}"
kubectl --context "$CONTEXT" -n "$NAMESPACE" set image   deployment/api "api=$IMAGE_REFERENCE"
kubectl --context "$CONTEXT" -n "$NAMESPACE" rollout status   deployment/api --timeout=180s
```

This is an ordinary Deployment rollout, not automatically a canary. It must run only after artifact/trust/environment checks; readiness and a user-path smoke test remain separate. For ECS, register a task-definition revision containing the intended digest and update the service to that revision. `--force-new-deployment` alone reuses the configured task definition and does not select the newly built image.

## 4. Choose the Builder and Target Deliberately

A Docker socket gives powerful host control. Rootless BuildKit, remote builders, and in-cluster builders have different host, network, secret, and isolation requirements; location alone does not make one safe. Keep untrusted builds away from publication/deployment credentials. Use maintained builders and explicitly installed tools; do not recommend archived Kaniko as a default.

A Compose command on a GitHub-hosted runner starts a temporary runner-local application. It is useful as an integration test, but it does not deploy to your production VM. A real VM release needs an authenticated target, stored image reference, compatible configuration, health checks, and a recovery procedure.

## 5. Bound Rebuilds and Recovery

Keep the context small with `.dockerignore`, cache reconstructible build inputs, and arrange stable dependency layers before frequently changing source. BuildKit registry-cache configuration belongs to `docker buildx build --cache-from type=registry,...`; do not mix it with legacy `docker build` cache syntax. A cache miss should cost time, not correctness.

A multi-stage build removes build-only tools from the runtime, so running `npm test` inside a minimal production image may be impossible. Test build-stage code separately and test the final image's actual startup, user, filesystem, dependencies, and application endpoints. Do not re-add a full development toolchain solely to make a release image run unit tests.

Retain previously deployed digests and compatible configuration. Rolling back an image cannot reverse incompatible schema changes or external writes. Test overlap and recovery before calling the release automated or safe.

## Common Mistakes

| Mistake | Consequence | Better boundary |
| -------------------------------------------- | ------------------------------------- | -------------------------------------------- |
| Build once in each environment | Different bytes can pass and ship | Promote identified content |
| Deploy latest or an unverified SHA tag | Name may select different content | Resolve and verify expected digest |
| Scan filesystem, claim image scan | Runtime image contents are unobserved | Name the scan target precisely |
| Push a different image after scanning | Evidence does not bind deployment | Carry the tested identity |
| Run Compose on CI, claim VM deploy | Application dies with runner | Explicit authenticated deployment target |
| Force ECS redeploy without new task revision | Old image selection remains | Register and select intended task definition |

## Best Practices

Keep one trace from source and builder inputs to candidate tests, scan, published digest, and authorized target. Distinguish local image IDs, registry digests, and tags. Pin reviewed tooling, bound execution, verify readiness/application behavior, and preserve compatible recovery artifacts.

## Summary

A container pipeline builds and validates a candidate, publishes identified content, and promotes that content through explicit gates. Correct deployment depends on artifact identity, target authority, and runtime evidence; a YAML action, SHA tag, or successful push supplies only part of that contract.

# CI/CD Pipeline Patterns — GitHub Actions, GitLab CI, Deployment Strategies

## Definition

A **CI/CD pipeline** automates the path from a commit to a deployed application. Each stage can check the change, produce a build artifact, or deploy that artifact. A required check is a **gate**: failure stops the change from progressing. Run cheap checks early, and keep the identity of the tested artifact through deployment so the version shipped is the version that passed.

> **Textbook Definition:** A CI/CD pipeline is an ordered dependency graph of automated validation, artifact creation, and delivery stages whose gates govern whether a change may progress to a target environment.

```text
commit ─▶ [validate]  ─▶ [build once]  ─▶ [test]  ─▶ [scan]  ─▶ [deploy]
          lint/type      immutable        unit →      deps/       staging →
          unit smoke     artifact +       integration secrets     canary/prod
                         digest          e2e         SBOM        (same digest)

invariants: retain candidate identity · required failures block promotion
            credentials scoped to the trusted job and target environment
```

This is one possible dependency graph. Some checks need the built artifact; others can run directly against source. Optional diagnostics and post-deployment checks have different blocking points from merge gates. Keep each required result tied to the exact candidate.

Build once and promote the same artifact when its configuration can be supplied safely at runtime. If the target requires a different compiled artifact, treat it as a separate candidate and repeat its required checks; do not transfer test evidence by assuming equivalence.

A deployment job can have powerful credentials, so control its inputs and permissions. Scans and a software bill of materials (SBOM) provide evidence; they do not replace restricted execution, event/ref trust or scoped credentials.

Choose recovery from the release's failure modes. Automatic rollback can help when its signals and compatibility conditions are reliable. An incompatible data change may need forward repair, and a controlled manual decision can be appropriate. In either case, rehearse recovery and retain evidence for the candidate being deployed.

## First Principles

Each check needs inputs and produces evidence. Some checks can run independently; others require a built artifact or deployed environment. Model those dependencies before adding parallelism. A failed required check must stop promotion, while optional diagnostics must never be mistaken for a passed gate.

## Trace a Failure Through a Dependency Graph

```text
commit → lint ───────────────┐
       → typecheck ──────────┼→ build candidate → artifact tests + scan
       → unit tests ────────┘                 → staging → promotion
```

If typecheck fails, the candidate is not eligible even when unit tests pass. If staging smoke tests fail, production must not start. A `needs` relationship schedules dependencies; configured required checks, failure handling and authorization establish policy. Distinguish an absent/skipped check from a successful one.

Run inexpensive useful checks early, but measure feedback cost rather than requiring a universal ten-minute limit. Security/integration checks may need to be required before promotion even when costly. Conditional selection must cover shared dependencies, lockfiles, renames and deletions.

## Separate Execution, Data and Authority

| Relationship | Required contract | Example failure |
| ------------------------ | -------------------------------------------- | ------------------------------------------------------ |
| Check executes code | Runtime, scripts and service readiness | A test starts before PostgreSQL accepts queries |
| Job consumes output | Producer/run, artifact identity and transfer | New job cannot see a previous job's local Docker image |
| Job receives credentials | Event/ref trust, scope and target | PR cache output is executed beside production secrets |
| Job deploys | Intended cluster/environment and readiness | Successful kubectl targets the wrong default context |

Use the canonical [GitHub Actions](../01-ci-platforms/40.3.1.01-github-actions.md) and [GitLab](../01-ci-platforms/40.3.1.02-gitlab-ci.md) examples for complete provider syntax. Their event/artifact/permission contracts belong there; duplicating partial workflows here obscures those contracts.

## Prepare Integration Dependencies Explicitly

For a test running on the runner host, mapped service ports can use localhost. A test inside a job container normally connects through a service hostname. Provide consistent credentials and URLs, then wait for a meaningful readiness check. A container marked running is not necessarily ready.

Apply committed test migrations to a disposable database before integration tests, generate required ORM clients using the project's actual scripts and isolate test state. Do not run test setup against production or let a missing service silently switch the suite to mocked mode. Coverage output needs a configured reporter and an existing file; uploading a report is not proof that the expected tests ran.

## Cache Only Reconstructible Work

Package-manager downloads and build caches save repeated work. `setup-node` npm caching does not restore `node_modules`; `npm ci` still installs the locked tree. Native outputs depend on OS, architecture and ABI, while generated clients depend on schema and generator version. Include relevant inputs in cache keys and run a clean-cache build periodically.

A release artifact needs producer identity and integrity evidence. Cache fallback keys deliberately permit older content, so they cannot substitute for an approved release. Restrict cache writers when privileged jobs consume restored content.

## Parallelize Independent Work, Join Required Evidence

Fan out supported runtime/platform variants and join all required results before promotion. Give each shard independent ports, test data, outputs and report names. A fail-fast matrix may cancel unfinished jobs: report cancellation as incomplete coverage, not success.

Keep side-effecting deploys serialized per environment, then check desired release freshness. A queue or approval can still deploy an older candidate after a newer one. Retries need idempotent operations, bounded attempts and a distinction between known failure and unknown outcome.

## Deployment and Exposure Are Different Decisions

| Strategy | What changes | Boundary to explain |
| ------------ | -------------------------------------------- | ----------------------------------------------------------- |
| Rolling | Old and new instances overlap | API/schema compatibility and capacity during replacement |
| Blue-green | Traffic target switches between environments | Existing sessions, writes and database state do not rewind |
| Canary | A measured cohort receives new behavior | Routing/cohort policy, sample size and stop criteria |
| Feature flag | Already deployed code changes exposure | Old/new paths, flag evaluation failure and eventual cleanup |

`kubectl set image` on one Deployment normally performs its configured rollout; it does not establish ten-percent traffic routing. Pod count and request share can differ. A canary needs a real routing/cohort mechanism and analysis policy, taught in [releases](../03-releases-and-metrics/40.3.3.01-blue-green-canary.md).

Automatic stop/rollback is useful only with valid signals and compatible recovery. Missing telemetry, zero traffic or a query error should not quietly pass. Reverting an image cannot undo payments or incompatible database changes; define forward repair when rollback is unsafe.

## Common Mistakes

| Mistake | Why it fails | Better decision |
| --------------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------- |
| Every failure is retried | Deterministic defects waste capacity; unknown effects duplicate | Classify failure and make retries bounded/idempotent |
| Deploy workflow starts independently of build | It may reference unpublished/unapproved content | Carry verified candidate and gate on its evidence |
| Compare an error-count rate to a percentage | Units and denominator differ | Bad-request rate divided by eligible-request rate |
| Sample only first Prometheus result | One instance can hide aggregate failures | Define aggregation and cohort labels |
| Generate many green jobs | They may skip real work | Require meaningful evidence for supported cases |

## Best Practices

Design the graph around observable failure classes and actual artifact dependencies. Keep clean-cache correctness, complete required evidence, service readiness and release authority explicit. Optimize feedback after establishing those contracts; choose exposure and recovery from user impact and state compatibility.

## Summary

Pipeline patterns organize dependency, artifact and authority relationships. Independent checks can run together, but promotion needs complete evidence for the exact candidate. Caches save time, retries handle chosen transient failures and release strategies control exposure only when their routing and recovery mechanisms actually exist.

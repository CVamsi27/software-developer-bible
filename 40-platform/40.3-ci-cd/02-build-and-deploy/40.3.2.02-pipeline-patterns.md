# CI/CD Pipeline Patterns — GitHub Actions, GitLab CI, Deployment Strategies

## First Principles

Pipeline shape follows from feedback-latency economics:

1. **The fast path must be truly fast**: lint + unit on every push (<10 min); the expensive stages (e2e, security scans) trigger conditionally — a pipeline that's slow gets bypassed, and a bypassed pipeline is worse than none.
2. **The DAG encodes dependency honesty**: parallelize what's independent, gate what's truly sequential (build → test → promote). Fan-out/fan-in is the shape for matrix testing.
3. **Every stage exists to catch a failure class as early as possible** — shift-left is just "cheapest place to find the bug." The pipeline is a sorted list of detection mechanisms by cost.

---

## Definition

A **CI/CD pipeline** is the ordered, automated path from a commit to a running version, where each stage is a **gate**: it either produces a verified artifact or stops the line. Its definition is not "the steps" but the **fail-fast ordering** and the artifact identity they share.

```text
commit ─▶ [validate]  ─▶ [build once]  ─▶ [test]  ─▶ [scan]  ─▶ [deploy]
          lint/type      immutable        unit →      deps/       staging →
          unit smoke     artifact +       integration secrets     canary/prod
                         digest          e2e         SBOM        (same digest)

invariants: build once, promote the same artifact · every stage's failure blocks
            the merge · secrets injected per-environment, never in the repo
```

Four properties define a pipeline that is trusted rather than tolerated:

1. **Build once, promote the same artifact** — rebuilding per environment means the thing you tested is not the thing you shipped; the artifact digest must be the identity carried through staging to production.
2. **Fail-fast ordering by cost** — cheap deterministic checks (lint, typecheck, unit) run before expensive ones (integration, e2e), so a typo costs 30 seconds instead of 20 minutes of CI capacity.
3. **A pipeline is a security boundary** — dependency and container scanning, an SBOM, protected branches, and OIDC-based short-lived cloud credentials replace long-lived secrets in the repository, because the pipeline is the highest-privilege actor in the system.
4. **Rollback is part of the pipeline, not a manual act** — the deploy stage must be able to revert a release automatically on SLO breach (canary with automatic rollback) and must be idempotent/re-runnable, otherwise "deploy" and "fix" are the same risky manual operation.

The design question in an interview is therefore about **gates and identity** — what blocks a merge, what proves an artifact, and how a bad release is detected and reverted — rather than which YAML runner is used.

## GitHub Actions (NestJS + Prisma)

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB: test_db
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_pass
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

      redis:
        image: redis:7
        ports:
          - 6379:6379

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run Prisma migrations
        run: npx prisma migrate deploy
        env:
          DATABASE_URL: postgresql://test_user:test_pass@localhost:5432/test_db

      - name: Run linting
        run: npm run lint

      - name: Run type checking
        run: npm run typecheck

      - name: Run unit tests
        run: npm run test

      - name: Run integration tests
        run: npm run test:e2e
        env:
          DATABASE_URL: postgresql://test_user:test_pass@localhost:5432/test_db
          REDIS_URL: redis://localhost:6379

      - name: Upload coverage
        uses: codecov/codecov-action@v3
        with:
          token: ${{ secrets.CODECOV_TOKEN }}

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build

      - name: Build Docker image
        run: docker build -t api:${{ github.sha }} .

      - name: Push to registry
        run: |
          echo ${{ secrets.DOCKER_PASSWORD }} | docker login -u ${{ secrets.DOCKER_USERNAME }} --password-stdin
          docker tag api:${{ github.sha }} registry.example.com/api:${{ github.sha }}
          docker push registry.example.com/api:${{ github.sha }}
```

## Deployment Pipeline

```yaml
# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy to staging
        run: |
          kubectl set image deployment/api api=registry.example.com/api:${{ github.sha }} -n staging
          kubectl rollout status deployment/api -n staging

      - name: Run smoke tests
        run: |
          curl -f https://staging.api.example.com/health
          npm run test:smoke -- --base-url=https://staging.api.example.com

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to production (canary)
        run: |
          # Deploy to 10% of pods
          kubectl set image deployment/api api=registry.example.com/api:${{ github.sha }} -n production
          kubectl rollout status deployment/api -n production

      - name: Monitor error rate
        run: |
          # Wait 5 minutes, check error rate
          sleep 300
          ERROR_RATE=$(curl -s "http://prometheus:9090/api/v1/query?query=rate(http_requests_total{status=~'5..'}[5m])" | jq '.data.result[0].value[1]')
          if (( $(echo "$ERROR_RATE > 0.01" | bc -l) )); then
            echo "Error rate too high, rolling back"
            kubectl rollout undo deployment/api -n production
            exit 1
          fi

      - name: Complete rollout
        run: |
          # If monitoring passed, continue rollout
          kubectl rollout status deployment/api -n production
```

## GitLab CI (NestJS)

```yaml
# .gitlab-ci.yml
stages:
  - test
  - build
  - deploy

variables:
  POSTGRES_DB: test_db
  POSTGRES_USER: test_user
  POSTGRES_PASSWORD: test_pass

test:
  stage: test
  image: node:20-alpine
  services:
    - postgres:15
    - redis:7
  script:
    - npm ci
    - npx prisma migrate deploy
    - npm run lint
    - npm run typecheck
    - npm run test
    - npm run test:e2e
  coverage: '/Lines\s*:\s*(\d+\.?\d*)%/'

build:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  only:
    - main

deploy-staging:
  stage: deploy
  script:
    - kubectl set image deployment/api api=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -n staging
  environment:
    name: staging
  only:
    - main

deploy-production:
  stage: deploy
  script:
    - kubectl set image deployment/api api=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -n production
  environment:
    name: production
  when: manual
  only:
    - main
```

## Deployment Strategies

```typescript
const deploymentStrategies = {
  // Rolling update
  rolling: {
    description: 'Gradually replace old pods with new ones',
    pros: ['Simple', 'No extra infrastructure'],
    cons: ['Slow rollback', 'Mixed versions during deploy'],

  blueGreen: {
```

## Interview Tips
- Explain CI/CD pipeline stages (lint → test → build → deploy)
- Know deployment strategies (rolling, blue-green, canary)
- Discuss caching strategies for faster builds
- Explain security scanning in pipelines- Know rollback strategies (automatic on error rate spike)

## Summary

1. **The pipeline is a quality gate sequence** — lint → test → build → deploy, and every stage exists to stop a defect class from moving right
2. **Deployment strategy is a risk decision** — rolling for cost, blue-green for instant rollback, canary for data-driven safety
3. **Build caching is the highest-leverage speedup** — dependency and layer caches turn 20-minute pipelines into 3-minute ones
4. **Security scanning belongs in the pipeline, not after it** — SCA, SAST, and image scans fail the build before deployment
5. **Rollback must be automatic and measured** — error-rate spikes trigger reversion faster than a human can; the strategy you chose in (2) determines whether that's possible

# Artifact Registries & Release Promotion

> **The registry is the contract between CI and CD.** Everything you deploy is a byte-exact artifact that was built exactly once, stored under an immutable digest, and *promoted* — never rebuilt — from dev through staging to production. This file covers the registry landscape (GHCR, ECR, Artifactory, NPM), why tags lie and digests do not, the build-once/promote-everywhere flow, changelog automation with release-please and changesets, retention policies that do not shoot you in the foot, and pull-through caches that make upstream outages irrelevant.

## TL;DR

- **Registry = source of truth** for deployable artifacts. If it is not in the registry, it does not exist.
- **Tags are mutable pointers; digests (`sha256:...`) are immutable content addresses.** Deploy by digest, tag for humans.
- **Promotion = moving the SAME digest through environments** (dev -> staging -> prod). Rebuilding per environment means you ship untested bytes to prod.
- **Changelog automation**: release-please (conventional commits -> version PR -> CHANGELOG + tag + GitHub Release) or changesets (intent files merged per PR -> aggregated version PR -> npm publish).
- **Retention policies** keep the last N promoted digests and prune the rest — never delete a digest a running workload references.
- **Pull-through caches** proxy Docker Hub/npm upstreams through your own registry: rate-limit immunity, audit trail, survives upstream outages.
- **In interviews: "how do you guarantee staging tested exactly what prod runs?" Answer: one digest, promoted — never rebuilt.**

## Definition

An **artifact registry** is a versioned, access-controlled store for build outputs: OCI container images, npm packages, language wheels/jars, Terraform modules, Helm charts. A **release promotion flow** takes one artifact version and moves it through environments by *reference* (re-tagging or re-pointing manifests at the same digest), applying human or automated gates along the way — not by re-running the build per environment.

Key concepts:

- **Tag**: a human-friendly, *mutable* pointer (`v1.2.3`, `main`, `latest`). Anyone with push rights can move it.
- **Digest**: `sha256:<hex>` of the image manifest. Content-addressed: identical bytes -> identical digest. Immutable until garbage-collected.
- **Promotion**: `dev-current` -> `staging-current` -> `prod-current` all pointing at one digest, or (better) every environment pinning the digest itself.
- **Changelog automation**: tooling that derives versions and release notes from merged PRs/conventional commits, so the CHANGELOG is generated, not authored.
- **Pull-through cache**: a read-through proxy repository that stores upstream artifacts on first pull.

## Why Do We Need It?

| Problem | Solution |
| -------------------------------------------------------------------------- | ------------------------------------------------------- |
| "Works in staging, breaks in prod" — because prod runs a *different build* | Promote one digest; staging tests byte-exact prod bits |
| `myapp:latest` means something different on every machine | Immutable digests + immutable release tags |
| Hand-written CHANGELOG rots immediately | release-please / changesets generate it from merged PRs |
| Docker Hub rate limits break 6 AM deploys | Pull-through cache in your own registry |
| Registry bill explodes with 50k untagged images | Lifecycle/retention policies with safe keep-rules |
| "Which build is in prod?" is a Slack question | Digest recorded in the deploy manifest is the answer |

## How It Works

### 1. The registry landscape

| Registry | Best for | Notes |
| ------------------------------------ | ------------------------------- | ---------------------------------------------------------------------- |
| **GHCR** (GitHub Container Registry) | GitHub-native teams, OSS images | `ghcr.io/org/app`, GITHUB_TOKEN auth, OCI-compliant |
| **ECR / ECR Public** | AWS shops | IAM auth, lifecycle policies, pull-through cache rules |
| **Google Artifact Registry** | GCP shops | Regional repos, vulnerability scanning |
| **JFrog Artifactory** | Enterprise polyglot | Virtual/federated repos, one URL for npm+Docker+Maven, air-gap support |
| **npm registry + private mirror** | JS packages | Verdaccio/Nexus/Artifactory npm repos for private packages and caching |
| **Harbor** | Self-hosted OCI | CNCF project: scanning, signing, replication built in |

All container registries speak **OCI distribution spec** — `crane`, `skopeo`, `oras`, and `docker` work against all of them. Lock-in is low; choose by ecosystem.

### 2. Tags lie, digests do not

```text
TAG vs DIGEST
═══════════════════════════════════════════════════════════
ghcr.io/acme/api:prod        <- anyone can re-point this. Today.
ghcr.io/acme/api:v1.4.2      <- SHOULD be immutable, but nothing enforces it
ghcr.io/acme/api@sha256:9a4f…<- content address. Identical bytes forever.

Rules:
• Humans read tags. Machines deploy digests.
• One push = one digest. Pushing again produces a NEW digest,
  even if a Dockerfile did not change (timestamps, base image drift).
• Kubernetes manifests, Helm values, ECS task defs: pin @sha256:...
```

Verify immutability yourself:

```bash
crane digest ghcr.io/acme/api:v1.4.2
# sha256:9a4fb1d0…  <- deploy THIS string, not the tag
```

### 3. Build once, promote everywhere

```text
             BUILD EXACTLY ONCE
┌──────────────────────────────────────────────────────────┐  test+scan+sign  ┌──────────────────────────────┐
│   CI   │ ───────────────► │ REGISTRY                     │
└──────────────────────────────────────────────────────────┘                  │ api@sha256:9a4f… (immutable) │
                            └──────────────────────────────┘
                                  │           │           │
                     tag dev-cur  │ tag stg-  │ tag prd-  │
                                  ▼           ▼           ▼
                             ┌──────────────────────────────────┐  ┌─────────┐ ┌──────────┐
                             │  DEV   │  │ STAGING │ │   PROD   │
                             │ digest │─►│ digest  │►│  digest  │
                             └──────────────────────────────────┘  └─────────┘ └──────────┘
                              same sha256:9a4f… everywhere

Gates between hops: smoke tests, QA sign-off, change approval,
canary analysis — applied to the PROMOTION, never to a rebuild.
```

Environment differences (DB URLs, feature flags, replicas) belong in **config**, not in the image: Helm values per environment, Kustomize overlays, or runtime env vars. If someone asks for a "prod image", the answer is "there is one image; here is prod config".

### 4. Changelog automation

| Tool | Model | Best for |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| **release-please** | Scans conventional commits on main; opens a "Release PR" that bumps the version and writes CHANGELOG; merging it tags + creates a GitHub Release | Apps and libraries on GitHub; low ceremony |
| **changesets** | Every meaningful PR ships a `.changeset/*.md` intent file (patch/minor/major + note); a Version PR accumulates them; merging publishes | Monorepos, npm packages, explicit per-PR intent |
| **semantic-release** | Fully automatic publish on conventional commits, no human gate | Fast-moving internal libs |

The CI/CD hook point is the same for all: **the merge of the release PR is the trigger** that builds/pushes the tagged artifact (`:v1.5.0`) and records its digest. Version-first means the registry tag and the changelog entry can never disagree.

### 5. Retention and cleanup

Registries grow forever unless you delete. Policy shape that works:

- **Keep**: every digest currently deployed anywhere, the last 20-30 release digests, all `vX.Y.Z` semver tags for 90+ days (rollback depth).
- **Delete**: untagged layers older than N days (build cache), stale `sha-<commit>` tags past their PR lifetime, preview-env images older than 7 days.
- **Never**: bulk-delete by date across release tags while old workloads still run — a pod restart pulls layers that no longer exist and the rollout dies.

ECR expresses this as JSON lifecycle rules; GHCR via package retention settings; Artifactory via scheduled repo policies.

### 6. Pull-through caches

First pull of an upstream image goes through your registry, which stores it; later pulls are served locally.

```text
Cluster pod ──pull──► YOUR REGISTRY (cache miss? fetch upstream, store, serve)
                                                   │                        ▲
                          └── cache hit ───────────┘
Benefits: Docker Hub rate limits gone • upstream outage irrelevant •
audit of every third-party image • one egress path to whitelist
```

## Code Examples

### Build and push once, capture the digest, sign it

```yaml
# .github/workflows/build.yml
name: build
on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write
  id-token: write # for keyless signing

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: push
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/acme/api:sha-${{ github.sha }}
          provenance: true

      # Sign BY DIGEST. Signing a tag is signing whatever it points at
      # tomorrow, which is nothing.
      - name: Sign image
        run: |
          cosign sign --yes \
            ghcr.io/acme/api@${{ steps.push.outputs.digest }}

      - name: Export digest for downstream promotion
        run: echo "${{ steps.push.outputs.digest }}" > digest.txt
```

### Promotion gate: same digest, verified, redeployed

```typescript
// scripts/promote.ts — move ONE digest dev -> staging -> prod.
// Never rebuilds. Refuses anything that is not a digest.
import { execSync } from "node:child_process";

const IMAGE = "ghcr.io/acme/api";

const ALLOWED_PROMOTIONS: Record<string, string[]> = {
  staging: ["dev"],
  prod: ["staging"],
};

function assertDigest(ref: string): void {
  if (!/^sha256:[0-9a-f]{64}$/.test(ref)) {
    throw new Error(`refusing non-digest ref "${ref}" — tags are mutable`);
  }
}

export async function promote(digest: string, from: string, to: string): Promise<string> {
  assertDigest(digest);
  const legalSources = ALLOWED_PROMOTIONS[to] ?? [];
  if (!legalSources.includes(from)) {
    throw new Error(`${to} may only be promoted from ${legalSources.join(" | ")}, saw ${from}`);
  }

  // 1. Verify the signature made at build time (keyless, via OIDC).
  execSync(
    `cosign verify ${IMAGE}@${digest} ` +
      `--certificate-identity-regexp '^https://github.com/acme/' ` +
      `--certificate-oidc-issuer https://token.actions.githubusercontent.com`,
    { stdio: "inherit" },
  );

  // 2. Move the human-readable tag onto this digest (digest unchanged).
  execSync(`crane tag ${IMAGE}@${digest} ${to}-current`, { stdio: "inherit" });

  // 3. Deploy by digest so the cluster state references immutable bytes.
  execSync(`kubectl -n ${to} set image deploy/api api=${IMAGE}@${digest}`, { stdio: "inherit" });
  execSync(`kubectl -n ${to} rollout status deploy/api --timeout=180s`, { stdio: "inherit" });

  return digest;
}
```

### ECR lifecycle policy: prune the cache, keep the releases

```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Expire untagged build-cache images after 14 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 14
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Keep only the 30 most recent sha-* commit tags",
      "selection": {
        "tagStatus": "tagged",
        "tagPatternList": ["sha-*"],
        "countType": "imageCountMoreThan",
        "countNumber": 30
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 3,
      "description": "Keep the 50 most recent release tags, expire older ones",
      "selection": {
        "tagStatus": "tagged",
        "tagPatternList": ["release-*", "staging-*", "prod-*"],
        "countType": "imageCountMoreThan",
        "countNumber": 50
      },
      "action": { "type": "expire" }
    }
  ]
}
```

Rules evaluate in priority order; a rule that expires a `prod-*` image still respects the "keep last 50" floor. Tune the floor to (deploy frequency x rollback window).

```yaml
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

### release-please: conventional commits to tagged release

```yaml
# .github/workflows/release-please.yml
name: release-please
on:
  push:
    branches: [main]

permissions:
  contents: write
  pull-requests: write

jobs:
  release-please:
    runs-on: ubuntu-latest
    steps:
      - uses: googleapis/release-please-action@v4
        with:
          release-type: node
          # feat: -> minor, fix: -> patch, feat!: / BREAKING CHANGE: -> major
    outputs:
      tag_name: ${{ steps.release.outputs.tag_name }}
    # Downstream job: build + push ghcr.io/acme/api:${tag_name}
    # then record its digest as the promoted candidate.
```

### ECR pull-through cache for Docker Hub

```bash
aws ecr create-pull-through-cache-rule \
  --ecr-repository-prefix docker-hub \
  --upstream-registry-url registry-1.docker.io \
  --region eu-central-1

# Pods (or FROM lines) now reference your registry, not Docker Hub:
# 123456789012.dkr.ecr.eu-central-1.amazonaws.com/docker-hub/library/postgres:16
```

## Real-World Use Cases

### 1. Microservices on ECR, one account per environment

Build once into the shared build account's ECR; cross-account resource policies let staging/prod accounts *pull* the digest. Promotion = updating each account's deploy manifest to the digest that QA certified. No cross-account push ever happens.

### 2. npm design system published with changesets

Every consumer-facing PR carries a changeset file. The bot aggregates them into one Version PR per cycle; merging publishes to npm with provenance and a generated CHANGELOG, so app teams upgrade against accurate notes instead of `git log`.

### 3. Enterprise Artifactory as the single door

Virtual repositories stack `libs-release` + a Maven Central cache + an internal snapshot repo. Builds resolve everything from one URL; a firewall rule whitelists exactly one egress host; compliance gets a complete log of which artifact versions entered the company.

### 4. GHCR-backed open-source image with release-please

Conventional commits drive the version. Merging the Release PR tags `v2.3.0`, publishes the GitHub Release with generated notes, and the follow-on job pushes the signed `:v2.3.0` image whose digest lands in the release body — users can pin `@sha256:...` straight from the notes.

### 5. Preview environments with aggressive retention

Every PR pushes `pr-<num>` images; the environment dies on close and a lifecycle rule expires those tags after 7 days. Registry stays flat despite hundreds of PRs a week.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Deploying `:latest` or a mutable `:prod` tag | Pin `@sha256:...` in manifests; tags are for humans only |
| Rebuilding the image per environment | Build once; promote the digest; vary config, not bytes |
| Signing/tagging before the image is scanned and gated | Scan and sign the candidate digest, then promote through gates |
| Deleting tags to "clean up" while workloads still reference layers | Retention floors sized to rollback window; GC only below the floor |
| Hand-editing CHANGELOG.md | Generate it: conventional commits + release-please, or changesets |
| One giant registry with no repo separation | Separate repos/projects per team and maturity (stable vs snapshot/cache) |
| Pulling base images straight from Docker Hub in CI | Pull-through cache or pre-synced golden bases |

## Best Practices

1. **Treat the registry as the interface between CI and CD.** CI's deliverable is a digest; CD consumes digests. Nothing else crosses the boundary.
2. **Deploy by digest everywhere** — Kubernetes, ECS task definitions, Helm values. Record the digest in the deployment event for auditability.
3. **Make release tags append-only** (registry permission or bot-only credentials). A moved `v1.4.2` is worse than no tag at all.
4. **Promote through an explicit state machine** (dev -> staging -> prod) enforced in code, not tribal knowledge.
5. **Sign at build time, verify at deploy time** (cosign/Sigstore). Verification belongs in the admission controller or promotion gate, not in a wiki page.
6. **Automate the changelog from day one.** Retro-fitting release notes is archaeology; generating them is a habit.
7. **Size retention to rollback needs:** keep enough history to roll back three releases and to reproduce any build from the last quarter (via digest + lockfiles).
8. **Cache upstreams behind your registry.** Rate limits, outages, and audits all get cheaper at once.
9. **Separate cache repos from release repos.** Untagged churn belongs somewhere it can be deleted wholesale.
10. **Monitor registry health:** pull latency, storage growth, failed auth spikes — the registry failing silently stalls every deploy at once.

## Performance Considerations

| Concern | Reality | Mitigation |
| ------------------------------------------- | ------------------------------ | ----------------------------------------------------------- |
| Pull latency dominates cold starts | First pod on a node pulls GBs | Regional replication, smaller images, zonal cache |
| Layer dedupe saves most storage | Shared bases cost once | Standardize base images across services |
| Manifest HEAD requests are cheap but chatty | Digest verification per deploy | Cache verification results per digest+signature |
| Cross-region pulls bill egress | Global fleets pay twice | Replicate release digests to each region at promotion |
| Retention scans are IO heavy | Nightly full sweeps | Incremental policies (ECR lifecycle, Artifactory scheduled) |

## Summary

- The registry is the **single source of truth**: CI produces digests, CD consumes digests.
- **Tags are mutable; digests are immutable.** Human-facing tags ride on top of content-addressed digests.
- **Promotion means re-pointing environments at the same digest** — testing staging bytes equals shipping prod bytes.
- **Changelog automation** (release-please, changesets) makes versions and notes derived artifacts, so the registry tag always matches the story.
- **Retention is a safety feature**: keep rollback depth, delete churn, never evict a digest a running workload references.
- **Pull-through caches** neutralize upstream rate limits and outages while giving you an audit trail of third-party artifacts.
- **In interviews: build once, promote by digest, sign at build, verify at deploy.**

## Cheat Sheet

```text
ARTIFACT REGISTRIES & PROMOTION CHEAT SHEET
════════════════════════════════════════════════════════════════

REGISTRIES
  • GHCR: GitHub-native, OCI • ECR: AWS, IAM + lifecycle rules
  • Artifactory: enterprise polyglot, virtual repos
  • Harbor: self-hosted OCI + scanning • NPM: packages (+ private mirror)

IMMUTABILITY
  • Tag     = mutable pointer (humans read)
  • Digest  = sha256 of manifest (machines deploy)
  • crane digest img:tag  ->  deploy THAT
  • Pin @sha256:... in K8s/ECS/Helm manifests

PROMOTION FLOW
  build ONCE -> scan -> sign(by digest) -> push :sha-<gitsha>
      -> dev -> staging -> prod   (SAME digest, gates between hops)
  • Config varies per env (values/overlays), never image bytes
  • Enforce the state machine in code (allowed transitions only)

CHANGELOG AUTOMATION
  • release-please: conventional commits -> Release PR -> tag + notes
  • changesets: per-PR intent files -> Version PR -> npm publish
  • Merge of release PR triggers the registry push of :vX.Y.Z

RETENTION
  • Keep: deployed digests, last N releases, semver tags >= 90d
  • Delete: untagged > 14d, pr-* previews > 7d, sha-* beyond top 30
  • NEVER delete a digest a running workload can still pull

PULL-THROUGH CACHE
  • Your registry proxies Docker Hub/npm -> rate limits + outages gone
  • ECR: create-pull-through-cache-rule • Artifactory: remote repos

INTERVIEW FORMULA
  • "Staging == prod?" -> one digest, promoted
  • "Rollback?" -> kubectl set image back to previous digest
  • "Audit?" -> signed digest + deploy event records
```

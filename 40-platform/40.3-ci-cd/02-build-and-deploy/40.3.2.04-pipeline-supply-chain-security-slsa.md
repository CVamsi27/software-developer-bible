# Pipeline Supply-Chain Security & SLSA

> **Your CI pipeline is part of your attack surface.** It holds cloud credentials, pushes to production registries, and executes third-party code on every push. This file covers the threat model (what SolarWinds, Codecov, and xz actually teach), SLSA build levels in plain terms, SHA-pinning actions plus Dependabot to keep pins alive, OIDC federation that deletes long-lived keys, provenance attestations you can verify at deploy time, and branch protection for the workflows themselves — because the pipeline is the one repo directory where a typo is a breach.

## Definition

**Software supply-chain security** protects the path from source code to running artifact: dependencies, build tooling, CI infrastructure, and distribution. **SLSA** (Supply-chain Levels for Software Artifacts, pronounced "salsa") is a graded framework — originated at Google, now an OpenSSF project — describing how much of that path is tamper-resistant. Its core output is **provenance**: signed metadata stating *what* was built, *from which sources*, *by which builder*.

Key concepts:

- **Attack surface**: every system that can change code or artifacts without review.
- **Pinned action reference**: `owner/repo@<full-commit-SHA>` — immutable; annotated with the version tag for humans.
- **OIDC federation**: CI exchanges its identity token with a cloud provider's STS for short-lived credentials; nothing secret is stored.
- **Attestation**: a signed statement about an artifact (provenance, SBOM, scan result) following the **in-toto** attestation format.
- **TUF (The Update Framework)**: metadata standard that makes software update systems resilient to key compromise and rollback attacks — the pattern behind secure metadata rotation.

---

## First Principles

Pipeline security follows from the pipeline being where untrusted input meets production trust:

1. **PRs are untrusted code execution** — `pull_request_target` misconfigurations, workflow injection through titles/branch names: the pipeline itself is an attack surface. Isolate untrusted builds from secrets.
2. **Provenance closes the loop**: SLSA levels attest how the artifact was built (hermetic? isolated? signed?) — the consumer's verification (→ 40.1.08's admission) is only as good as the builder's attestation.
3. **Dependencies enter here too**: lockfiles, pinned actions by SHA, and SBOM generation make the pipeline the *checkpoint* where supply-chain policy is enforced (→ 20.5.3.05).

## Why Do We Need It?

| Threat shown by real incidents | What happened | Pipeline defense |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Compromised build server (**SolarWinds**, 2020) | Attackers lived in the build network and injected a backdoor into the official, *signed* Orion installer | Isolated/hermetic builders; provenance proving what sources produced what bytes |
| Leaky CI helper (**Codecov**, 2021) | Tampered bash uploader exported CI environment variables — including cloud keys — for months | No long-lived secrets in env; OIDC federation; pin/verify third-party scripts |
| Social-engineered dependency (**xz**, 2024) | New maintainer gained commit/release rights; backdoor hidden in release tarballs, not git; targeted SSH auth in builds/servers | Reviewer integrity on critical deps; provenance tying tarball to public commits; SBOM awareness |
| Movable action tag (`@v3` re-pointed) | A hijacked or compromised action repo silently changes behavior for everyone who pinned only a major tag | SHA-pinning + Dependabot-driven, reviewable bumps |
| Stolen AWS key from CI logs | Long-lived `AWS_SECRET_ACCESS_KEY` scraped from logs/cache | OIDC federation: zero stored cloud keys |

The pattern across all three headline incidents: **the artifact was trusted because the pipeline was trusted.** Hardening the pipeline is cheaper than explaining the breach.

## How It Works

### 1. The pipeline as attack surface

```text
                 WHAT AN ATTACKER CAN TOUCH
┌───────────────────────────────────────────────────────────────────────────┐   ┌────────────────┐   ┌───────────────────┐
│ REPO │──►│ WORKFLOW YAML                          │──►│ THIRD-PARTY CODE  │
└───────────────────────────────────────────────────────────────────────────┘   │ • pull_request │   │ • actions (@v3 ?) │
     ▲     │   _target trap │   │ • npm install     │
     │     │ • secrets ctx  │   │ • curl | bash     │
  social  └────────────────┘   └─────────┬─────────┘
 engineering                             ▼
     │     ┌────────────────┐   ┌───────────────────┐
  runners ◄─│ RUNNERS        │   │ SECRETS           │
  (shared,  │ • cache poison │   │ • env vars        │
   PR code) └────────────────┘   │ • long-lived keys │
                                 └─────────┬─────────┘
                                           ▼
                            ┌───────────────────────────────────┐    ┌──────────┐
                            │ REGISTRY          │───►│   PROD   │
                            │ • mutable tags    │    └──────────┘
                            └───────────────────────────────────┘
```

Every arrow is a control point. The rest of this chapter hardens each one.

### 2. SLSA build levels, plainly

| Level | Meaning | Typical evidence |
| ------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **L0** | No guarantees | Local laptop builds, `docker push` from dev machines |
| **L1** | Provenance exists (may be unverified/host-generated) | Script writes a JSON provenance file |
| **L2** | Hosted build platform; provenance **signed** by the platform | GitHub Actions + artifact attestations; GitLab CI signed provenance |
| **L3** | Hardened, isolated builds; provenance effectively unfalsifiable | Ephemeral isolated runners, separate build accounts, verified builder identity |

SLSA v1.x focuses on **Build** levels L0-L3 (source and dependency tracks exist as guidance). Practical reading for interviews:

```text
L1: we can SAY what was built      (a file exists)
L2: we can PROVE who said it       (platform-signed provenance)
L3: nobody else COULD have built   (hardened, single-use builders)
```

Most GitHub-based teams can reach L2 quickly (hosted Actions + attestations). L3 requires isolation discipline (ephemeral VMs, dedicated build projects).

### 3. SHA-pinning actions (+ Dependabot)

`uses: actions/checkout@v6` resolves to whatever the maintainers move `v4` to. Pinning to a full commit SHA freezes behavior; Dependabot then proposes version bumps as normal, reviewable PRs.

### 4. OIDC federation instead of long-lived keys

The workflow requests an ID token bound to claims like `repo`, `ref`, `workflow`; your cloud IAM policy trusts exactly those claims and returns temporary credentials valid for minutes.

```text
GitHub job ──OIDC ID token──► Cloud STS (trust policy checks subject)
                │                       │
                │                       ▼
                └────────────► temp creds (15-60 min TTL)
No AWS_SECRET_ACCESS_KEY exists anywhere in GitHub settings.
Leaked logs leak nothing. Key rotation stops being a chore.
```

### 5. Provenance attestations

An attestation is signed JSON (in-toto format) answering: builder, source commit/ref, build config, materials digest. Generate with the native GitHub `attest-build-provenance` action or the SLSA generator; verify with `gh attestation verify` or cosign before deploying.

### 6. Protecting the workflows themselves

- **CODEOWNERS entry for `.github/workflows/**`** so workflow edits require security/team review even from admins-with-PRs.
- **Branch protection**: required reviews, required status checks, disallow force-pushes on protected branches.
- **Least-privilege token**: default `permissions: contents: read` at workflow level; grant per-job extras explicitly.
- **Avoid `pull_request_target` with checkout of the PR head** — it runs untrusted code with repository secrets. Use plain `pull_request` or isolate the untrusted part in a workflow with no secret access.
- **Pin runner images / use ephemeral self-hosted runners** for sensitive repos; never reuse stateful runners across PR authors.

## Code Examples

### Hardened workflow skeleton

```yaml
# .github/workflows/build.yml
name: build

on:
  push:
    branches: [main]

# Least privilege first; jobs escalate below if needed.
permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write       # push to GHCR
      id-token: write       # OIDC federation + keyless signing
      attestations: write   # record build attestations
    steps:
      # Tag for humans, SHA for machines. Dependabot updates both together.
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

      # Placeholder form shown deliberately: ALWAYS resolve the real
      # 40-char SHA (Dependabot does this for you when it opens the PR).
      - uses: actions/setup-node@<commit-sha> # v4

      - run: npm ci
      - run: npm test

      - name: Build and push image
        id: push
        uses: docker/build-push-action@<commit-sha> # v6
        with:
          push: true
          tags: ghcr.io/acme/api:${{ github.sha }}

      - name: Generate build provenance (SLSA L2)
        uses: actions/attest-build-provenance@<commit-sha> # v1+
        with:
          subject-name: ghcr.io/acme/api
          subject-digest: ${{ steps.push.outputs.digest }}
```

### OIDC federation: AWS trust policy + workflow usage

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": [
            "repo:acme/api:ref:refs/heads/main",
            "repo:acme/api:environment:production"
          ]
        }
      }
    }
  ]
}
```

```yaml
- uses: aws-actions/configure-aws-credentials@<commit-sha> # v4
  with:
    role-to-assume: arn:aws:iam::123456789012:role/ci-deploy-api
    aws-region: eu-central-1
  # No secrets.AWS_* involved. Token lives for the job only.
```

### Dependabot keeps SHA pins alive

```yaml
# .github/dependabot.yml
version: 2

updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
    groups:
      github-actions-minor:
        update-types: ["minor", "patch"]

  - package-ecosystem: npm
    directory: /
    schedule:
      interval: daily
    groups:
      npm-dev:
        dependency-type: development
```

Each Dependabot PR swaps the old pinned SHA for the new one and updates the `# vX.Y.Z` comment — a reviewable diff instead of silent tag drift.

### Verify provenance at deploy time

```bash
# One-time per artifact family: list known attestations for an image
gh attestation list \
  --repo acme/api \
  ghcr.io/acme/api@sha256:9a4fb1d0c6e5b1f8e2d3a4b5c6d7e8f90123456789abcdef0123456789abcd

# Gate: fail the promotion unless the platform signed this exact digest,
# built from THIS repo's main branch.
gh attestation verify \
  ghcr.io/acme/api@sha256:9a4fb1d0c6e5b1f8e2d3a4b5c6d7e8f90123456789abcdef0123456789abcd \
  --repo acme/api
```

### Policy check: no unpinned actions in CI itself

```typescript
// scripts/check-action-pinning.ts
// Fails the repo-audit job if any step references an action by tag.
// Run nightly AND in a workflow that validates workflow changes.
import { readdirSync, readFileSync } from "node:fs";
import { join } from "node:path";

const WORKFLOW_DIR = ".github/workflows";
const USES_RE = /^\s*-?\s*uses:\s*(\S+)@(\S+)/gm;
const SHA_RE = /^[0-9a-f]{40}$/;
const offenders: string[] = [];

for (const file of readdirSync(WORKFLOW_DIR)) {
  if (!(file.endsWith(".yml") || file.endsWith(".yaml"))) continue;
  const source = readFileSync(join(WORKFLOW_DIR, file), "utf-8");
  let match: RegExpExecArray | null;
  while ((match = USES_RE.exec(source)) !== null) {
    const [, action, ref] = match;
    const local = action.startsWith("./");
    if (!local && !SHA_RE.test(ref)) {
      offenders.push(`${file}: ${action}@${ref} (not SHA-pinned)`);
    }
  }
}

if (offenders.length > 0) {
  console.error("Unpinned actions found:");
  for (const line of offenders) console.error(`  - ${line}`);
  process.exit(1);
}
console.log("All actions SHA-pinned.");
```

> Note the deliberate simplicity: a regex over YAML is fine here because the check is advisory-shaped and workflows are small. For monorepos with hundreds of workflows, use a proper YAML parser.

### CODEOWNERS protecting the pipelines

```text
# .github/CODEOWNERS
# Workflow changes always need platform-security review.
/.github/workflows/   @acme/platform-security
/.github/dependabot.yml @acme/platform-security
/Dockerfile           @acme/platform-security @acme/api-team
```

## Real-World Use Cases

### 1. Fintech reaching SLSA L2 in a quarter

Hosted GitHub Actions everywhere, all actions SHA-pinned via Dependabot, `attest-build-provenance` on every image, ArgoCD admission hook runs `gh attestation verify` against each new digest. Audit finding closed without changing application code.

### 2. Deleting 200 stored cloud keys

A platform team inventories `AWS_ACCESS_KEY_ID`-style org secrets, maps each to a role, and migrates workflows to `configure-aws-credentials` with OIDC one repo at a time. Secret-rotation runbooks shrink to zero; leaked-log blast radius drops to nothing.

### 3. OSS maintainer defending against xz-style drift

Release tarballs are built by CI from git alone (no hand-uploaded artifacts), so every byte traces to a reviewed commit; `release.tar.gz.sha256` published alongside matches CI output; consumers can diff-check provenance before building.

### 4. Self-hosted runner farm for regulated workloads

Ephemeral VM runners boot per job from a golden image, assume a scoped build role, and burn down after the job — the L3-style isolation that lets one org host untrusted PR builds and privileged deploys in the same account safely.

### 5. Nightly supply-chain audit job

A scheduled workflow runs the pinning checker above, `npm audit --omit=dev`, SBOM diffing (syft) against last week, and posts a single digest issue. Drift becomes a Monday-morning PR queue, not an incident.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------------------- | -------------------------------------------------------------------- |
| Pinning actions by major tag (`@v4`) only | Pin full commit SHAs; Dependabot maintains them |
| Storing cloud keys as repo/org secrets | OIDC federation with strict `sub` conditions |
| Broad OIDC trust (`"sub": "repo:*"`) | Trust exact `repo:path`/`ref`/`environment` subjects |
| `pull_request_target` checking out PR head with secrets | Use `pull_request`; split privileged steps into a separate gated job |
| Default GITHUB_TOKEN with wide write scopes | `permissions: contents: read` globally, escalate per job |
| Generating provenance but never verifying it | Verify in the promotion gate/admission controller |
| Reviewing app code but not workflow diffs | CODEOWNERS on `.github/workflows/**` + required reviews |
| Treating SBOM generation as compliance theater | Diff SBOMs per release; alert on unexpected new packages |

---

## Best Practices

1. **Default-deny the token.** Start every workflow with `permissions: contents: read`; add write scopes only where a step needs them.
2. **Pin everything you execute**: actions by SHA, base images by digest, toolchains by lockfile. Reproducibility is a side effect of pinning.
3. **Let bots do the bumping.** Dependabot/Renovate PRs make supply-chain upgrades visible and revertible.
4. **Federate all cloud auth.** If a static credential still exists after migration, treat that as an exception with an owner and expiry date.
5. **Attest, then verify elsewhere.** An attestation nobody verifies is decoration; wire verification into CD.
6. **Guard the guardrails:** required reviews + CODEOWNERS on workflow paths; audit log alerts on workflow file changes outside PRs.
7. **Assume dependency compromise:** limit what CI credentials can do (scoped roles, separate build/deploy identities) so a poisoned build cannot pivot to prod data.
8. **Know your critical few.** Apply xz lessons where they matter: extra reviewer scrutiny on crypto/auth/parsing dependencies and on maintainer-trust changes.
9. **Rehearse revocation:** practice rotating an OIDC trust policy and re-running the gate; recovery speed is the metric auditors actually probe.
10. **Track your level honestly.** Map today's pipeline to SLSA L0-L3, pick the next cheapest control, and put the target in the roadmap.

## Performance Considerations

| Concern | Reality | Mitigation |
| ----------------------------------- | ------------------------ | ---------------------------------------------------- |
| Attestation steps add ~seconds | Negligible vs build time | Keep them; batch subjects per workflow |
| OIDC adds a token exchange (~100ms) | Invisible | None needed |
| SHA-pinning slows upgrades? | Only without automation | Dependabot weekly cadence |
| Verification at deploy adds latency | One API call per digest | Cache verification results per digest+attestation ID |
| Ephemeral runners cost more compute | True but bounded | Scope hardened runners to sensitive repos only |

## Summary

- The CI pipeline is production infrastructure holding production credentials; treat its files like prod config.
- **SolarWinds/Codecov/xz** map cleanly to defenses: hermetic builds + provenance, no long-lived secrets + verified helpers, source-tied releases + dependency scrutiny.
- **SLSA L1-L3** is a maturity ladder: say -> prove -> make unfalsifiable. Hosted Actions + attestations gets most teams to L2.
- **SHA-pin actions** and automate bumps; **federate cloud auth** with OIDC so no keys exist to steal.
- **Provenance attestations** close the loop only when something at deploy time verifies them.
- **Branch protection applies to `.github/workflows/**`** — the highest-leverage directory in the repo.
- **In interviews: pin, federate, attest, verify, protect the workflows themselves.**

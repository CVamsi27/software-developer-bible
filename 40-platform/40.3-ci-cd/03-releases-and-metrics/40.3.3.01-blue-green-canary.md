# Blue-Green & Canary Deployments

## Definition

**Blue-Green Deployment** maintains two identical environments (blue and green). One serves production traffic while the other is updated. The routing policy switches after validation; propagation and connection draining determine when clients fully move. **Canary Deployment** gradually rolls out changes to a small subset of users before full deployment.

> **Textbook Definition:** Blue-green deployment replaces traffic between independently deployable environments. Canary deployment exposes a bounded portion of production traffic to a candidate release and uses observed outcomes to govern promotion or rollback.

Key concepts:

- **Blue-Green**: Two deployable environments, controlled traffic switch
- **Canary**: Gradual rollout to small user subset
- **Rolling Update**: Gradual replacement of instances
- **Feature Flags**: Control feature visibility without deployment
- **Rollback**: Revert to previous version

## First Principles

A new version may fail only under real traffic, while an old version remains a useful recovery target. Separate creating capacity from deciding who receives it. Then bound exposure, observe meaningful outcomes and retain a compatible path back. Shared data, background jobs and long-lived connections can outlive a routing change.

## Choose What the Router Changes

```text
blue-green:  router → blue       prepare green → validate → route to green
canary:      router → stable + bounded candidate cohort → observe → ramp/stop
rolling:     one workload replaces instances while old/new overlap
```

Blue-green keeps independently deployable environments; it need not duplicate the database. A shared database requires compatible application/schema behavior. Separate databases require a deliberate data synchronization/cutover plan. Reversing traffic does not reverse writes.

A canary uses a limited cohort to evaluate release risk. Nine stable Pods and one candidate Pod do not guarantee ten percent of requests: connections, endpoint choice, sticky routing and unequal load affect the split. Weighted routing or explicit user cohorts can provide a defined policy, with observed actual exposure checked separately.

## Trace a Blue-Green Switch

The following Service fragment chooses only blue Pods with matching labels. It assumes an intended cluster/namespace, complete ready Deployments for both versions, correct container ports, authorization and identified image digests.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: checkout
spec:
  selector:
    app: checkout
    release: blue
  ports:
    - port: 80
      targetPort: 8080
```

1. Deploy green without changing this selector; verify readiness and direct green smoke tests.
2. Check old/new API and schema compatibility, plus sufficient green capacity.
3. Update the selector to `release: green` through the authorized desired-state mechanism.
4. Observe EndpointSlice propagation, new connections and user outcomes. Existing connections may keep using blue until drained.
5. Retain blue for the agreed recovery window, then remove it only after compatibility and stability checks.

A shell script that toggles whichever color is active is unsafe to retry: a second invocation can switch back. Request an explicit desired release and verify current/expected state. Check green **before** directing users to it. If GitOps owns the Service, commit the intended selector instead of making an unrecorded hotfix that reconciliation reverses.

## Evaluate a Canary Before Increasing Exposure

Define candidate and stable labels, comparable request cohorts, eligible traffic, observation windows and minimum samples before launching. Error fraction is bad eligible requests divided by eligible requests; an error-count rate has different units. Aggregate counters across instances after per-series rates, and keep candidate/stable separated.

Example hypothetical window: candidate serves 1,000 eligible requests with 20 failures; stable serves 9,000 with 45 failures. Candidate error fraction is 2%, stable is 0.5%, a 1.5 percentage-point difference. An overall 65/10,000 = 0.65% hides the candidate's regression. These are exercise values, not universal release thresholds.

```javascript
// canary-decision.mjs: local policy demonstration, not a telemetry collector
import assert from 'node:assert/strict';
function decide({ requests, errors, minimumRequests, maximumErrorFraction }) {
  if (!Number.isInteger(requests) || !Number.isInteger(errors) ||
      requests < 0 || errors < 0 || errors > requests) throw new Error('Invalid counts');
  if (!Number.isInteger(minimumRequests) || minimumRequests < 1 ||
      !Number.isFinite(maximumErrorFraction) || maximumErrorFraction < 0 ||
      maximumErrorFraction > 1) throw new Error('Invalid policy');
  if (requests < minimumRequests) return 'hold';
  return errors / requests > maximumErrorFraction ? 'abort' : 'eligible';
}
const policy = { minimumRequests: 1000, maximumErrorFraction: 0.01 };
assert.equal(decide({ ...policy, requests: 1000, errors: 20 }), 'abort');
assert.equal(decide({ ...policy, requests: 0, errors: 0 }), 'hold');
assert.equal(decide({ ...policy, requests: 1000, errors: 10 }), 'eligible');
assert.throws(() => decide({ ...policy, requests: 1000, errors: 1001 }));
```

The production analysis also needs latency distributions, business correctness, comparison to baseline and trusted telemetry completeness. `eligible` here means only this illustrative count rule passed, not that promotion is authorized. Missing series, query errors, too little traffic or incomplete candidate labeling should hold/abort under an explicit policy, rather than becoming zero failures.

For example, Argo Rollouts can apply explicit traffic weights and run an `AnalysisTemplate` against a metrics provider between rollout steps. Successful analysis allows progression; a failed analysis aborts the rollout, while an inconclusive result pauses for human judgment. Define metric windows, sample minimums and provider-error behavior in that policy. The controller can restore routing to the stable ReplicaSet, but this does not undo writes or other external effects.

## Implement the Strategy With the Actual Controller

Kubernetes Deployments manage rolling replacement; they do not supply a metric-driven canary policy. [Argo Rollouts](https://argoproj.github.io/argo-rollouts/features/canary/) is a separate controller that supports steps, analysis and integrations with traffic routers. It needs its CRDs/controller, stable/canary Services, an actual routing provider and analysis configuration.

A service mesh can weight requests through route subsets only when its data plane, resources, labels and Services exist. An isolated VirtualService fragment does not provision those prerequisites. Choose the smallest supported routing mechanism that meets the cohort and operational requirements; a mesh is not compulsory.

Community ingress-nginx was retired in March 2026. Its old canary annotations describe a legacy controller, not a maintained default for a new deployment. Select a maintained controller/Gateway implementation and verify its supported traffic policy. [Kubernetes retirement notice](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/).

## Keep Release Exposure and State Recovery Separate

Feature flags alter exposure within already deployed code. Define targeted cohorts, default/failure behavior, configuration freshness and cleanup ownership. An environment boolean is a process-start setting, not automatically a dynamic flag service. Both paths must remain compatible while active.

A background worker canary needs job-level success, lag, duplicate-effect and retry signals, not an HTTP traffic percentage. Scope which jobs it receives and ensure old/new workers honor idempotency and payload versions. A process remaining started is necessary operational evidence but does not prove jobs succeeded.

On abort, stop new candidate exposure, preserve incident evidence and verify restored user behavior. Image rollback cannot remove incompatible schema changes, reverse external payments or erase candidate writes. Use expand/contract migrations and forward repair when state cannot safely be rewound.

## Common Mistakes

| Mistake | Failure mechanism | Better boundary |
| -------------------------------------- | ---------------------------------------------- | -------------------------------------------------------- |
| Switch then test green | All users observe a known-bad target | Validate before routing |
| Treat Pod ratio as request ratio | Persistent/unequal connections distort traffic | Real cohort/routing policy and measured exposure |
| Check only global error rate | Stable traffic hides candidate failures | Candidate-specific and baseline signals |
| Promote after a fixed sleep | Sparse or missing telemetry looks successful | Minimum samples and completeness policy |
| Call traffic reversal instant recovery | Connections and shared state persist | Observe propagation, draining and compatible restoration |
| Retry a toggle script | Retry reverses the intended selection | Explicit idempotent desired release |

## Best Practices

Define artifact/configuration identity, exposure mechanism, valid analysis and recovery together. Rehearse low-traffic, missing-metric, incompatible-migration and long-lived-connection cases. Retain sufficient stable capacity and verify actual recovery rather than equating a completed command with restored service.

## Summary

Blue-green prepares replacement capacity before a controlled routing switch. Canary bounds exposure and uses defined evidence to govern expansion. Both require real routing, compatible state and observed restoration; readiness, a Pod count or a fixed waiting period cannot establish release safety.

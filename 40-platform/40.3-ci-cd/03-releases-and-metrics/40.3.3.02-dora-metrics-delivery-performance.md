# DORA Metrics & Delivery Performance

## Definition

**DORA's software delivery metrics** describe delivery outcomes at the application or service level. The four historical measures were deployment frequency, change lead time, failed-deployment recovery time, and change failure rate. Current guidance also tracks **deployment rework rate**: the share of deployments that are unplanned work responding to a production incident. Use current definitions and do not treat an older benchmark table as a timeless scorecard.

> **Textbook Definition:** DORA delivery metrics measure software delivery throughput and instability at the service or application level, relating deployment activity and change lead time to failure, recovery, and rework outcomes.

| Metric | Question it answers | Formula (operational) |
| ----------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| Deployment Frequency | How often do changes reach users? | count(production deployments) / period |
| Change Lead Time (historically Lead Time for Changes) | How long does one change take? | median(deployed_at - committed_at) per change |
| Failed Deployment Recovery Time | How fast do we fix bad changes? | median(restored_at - failed_deploy_at) |
| Change Failure Rate | What fraction of deployments require remediation? | failed_deployments / total_deployments |
| Deployment Rework Rate | How much deployment work responds to incidents? | incident-driven_unplanned_deployments / total_deployments |

Definitions that matter more than formulas:

- **Deployment** = a release of code or configuration to production users. Staging syncs do not count. A feature-flagged dark launch counts if it ships executable code to production.
- **Failure** = a production deployment that causes degraded service and requires immediate intervention, such as rollback, hotfix or fix-forward. Link remediation to the originating deployment; timing overlap alone does not establish causation.
- **Recovery** ends when user-facing service is restored. Choose and document the start event—such as the failed deployment or confirmed detection—and use that same clock across the report.

## First Principles

Delivery crosses several queues: commit, review, verification, approval and release. A deployed change can then require remediation. Measure those transitions with consistent identities and clocks so the team can locate delay and failure, rather than rewarding more deployment events. Pair throughput with instability and user-facing reliability; the numbers describe a system, not an individual engineer.

## Why Do We Need It?

1. **You cannot improve what you cannot see.** Delivery friction hides in handoffs; consistent event evidence helps investigate it; slow lead time and high failure rate are symptoms with several possible causes.
2. **They are validated, not vibes.** DORA research supports examining delivery and organizational outcomes together; it does not prove that a numeric target or one intervention causes every reported benefit.
3. **They force system-of-record instrumentation.** To compute LT you must join git to CD; that join exposes broken tagging, missing environments, and manual deploy steps.
4. **Benchmarks calibrate ambition.** "We want to deploy daily" becomes concrete when compared against published performance clusters.
5. **They pair with reliability targets.** DF/LT describe velocity; error budgets describe safety. Together they answer "can we ship faster?" with data instead of opinion.

## How It Works

### 1. The measurement pipeline

```text
Git commits + identified production deploy events + attributed failures/restoration
                             → consistent service/window dataset
                             → throughput, instability and unresolved-work views
```

Every arrow is a real integration:

- **Deploy events** come from the CD system's API/webhook (Argo CD app sync, GitHub `deployment_status`, Spinnaker pipeline completion). A green CI run is not a deployment.
- **Commit times** come from git (`authored/committed date` of the deployed SHA).
- **Failure attributions** normalize evidence such as explicit rollbacks, hotfixes linked to the affected component and incident/SLO records that identify the originating deployment. A hotfix is repair work, not proof that the repair deployment failed; timing overlap alone is not causal attribution.

### 2. Interpret a defined measurement window

Compare a service with its own baseline under a consistent definition and period. Research clusters and benchmark thresholds change across report years; they are context for improvement, not universal goals or individual performance rankings. The current [DORA metric guide](https://dora.dev/guides/dora-metrics/) defines five delivery measures, including deployment rework rate.

### 3. Instrumentation choices that determine honesty

| Decision | Honest choice | Dishonest drift |
| --------------------- | ------------------------- | ---------------------------------- |
| What counts as deploy | Prod-facing deploy events | Counting staging, cron restarts |
| Failure definition | Remediation required | Only Sev-1 incidents |
| Aggregation | Median per service | Mean across org (hides bimodality) |
| Window | Rolling 30-90 days | Cherry-picked sprints |
| Attribution | Per service/team | One number for 200 services |

### 4. Linking to error budgets

DORA answers throughput; **SLOs/error budgets gate it**:

An error-budget policy is a team agreement tied to user-facing reliability, remaining budget and burn rate. It may limit ordinary changes while preserving emergency repair/security work. Fixed percentages do not automatically authorize faster delivery, and DORA outcomes are not a release-control signal by themselves.

Discuss delivery trends alongside reliability evidence; neither table alone establishes safe release authority.

## Code Examples

### Emitting a structured deploy event from GitHub Actions

```yaml
# Excerpt: build produces a verified image digest; cluster access is configured.
jobs:
  deploy-production:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Roll out image by digest
        env:
          IMAGE_DIGEST: ${{ needs.build.outputs.digest }}
        run: |
          kubectl -n prod set image deploy/api "api=ghcr.io/acme/api@$IMAGE_DIGEST"
          kubectl -n prod rollout status deploy/api --timeout=5m
      - name: Emit deployment evidence
        env:
          COMMIT_SHA: ${{ github.sha }}
          DEPLOY_ACTOR: ${{ github.actor }}
          METRICS_TOKEN: ${{ secrets.METRICS_TOKEN }}
        run: |
          committed_at=$(git log -1 --format=%cI "$COMMIT_SHA")
          deployed_at=$(date -u +%Y-%m-%dT%H:%M:%SZ)
          jq -n --arg sha "$COMMIT_SHA" --arg actor "$DEPLOY_ACTOR" \
            --arg committed "$committed_at" --arg deployed "$deployed_at" \
            '{service:"api", environment:"production", sha:$sha, actor:$actor,
              committed_at:$committed, deployed_at:$deployed, kind:"standard"}' > deploy-event.json
          curl -fsS -X POST https://metrics.internal/api/v1/deployments \
            -H "Authorization: Bearer $METRICS_TOKEN" -H 'content-type: application/json' \
            --data-binary @deploy-event.json
```

Rollout readiness is one checkpoint; the deployment's definition of completion may also require a user-path smoke check. A failing rollout must not emit a successful-deployment event.


### Computing delivery measures from attributed events

```typescript
// scripts/dora.ts — pure functions over deployment and normalized evidence records.
export interface DeployEvent {
  id: string; // deployment identity, not merely a source SHA
  service: string;
  environment: "production" | "staging";
  sha: string;
  committedAt: Date;
  deployedAt: Date;
  kind: "standard" | "rollback" | "hotfix";
  triggeredByIncident?: boolean;
}

export interface FailureAttribution {
  service: string;
  failedDeploymentId: string; // normalized rollback, hotfix or incident evidence
}

export interface Incident {
  service: string;
  failedDeploymentId: string; // explicitly attributed originating deployment
  resolvedAt: Date | null; // null means recovery is still pending
}

export interface MeasurementWindow {
  startAt: Date;
  endAt: Date; // exclusive
}

const production = (ds: DeployEvent[]) => ds.filter(d => d.environment === "production");
const inWindow = (deploys: DeployEvent[], window: MeasurementWindow): DeployEvent[] => {
  const start = window.startAt.getTime();
  const end = window.endAt.getTime();
  if (!Number.isFinite(start) || !Number.isFinite(end) || start >= end) {
    throw new RangeError("invalid window");
  }
  return production(deploys).filter(d => {
    const deployed = d.deployedAt.getTime();
    if (!Number.isFinite(deployed)) throw new RangeError("invalid deployment time");
    return deployed >= start && deployed < end;
  });
};
const median = (values: number[]): number => {
  const xs = [...values].sort((a, b) => a - b);
  if (xs.length === 0) return NaN; // unavailable, not an observed zero
  const mid = Math.floor(xs.length / 2);
  return xs.length % 2 ? xs[mid] : (xs[mid - 1] + xs[mid]) / 2;
};

// Filter all measures to the same service and half-open time window.
export function deploymentFrequency(deploys: DeployEvent[], window: MeasurementWindow): number {
  const days = (window.endAt.getTime() - window.startAt.getTime()) / 86_400_000;
  return inWindow(deploys, window).length / days;
}

export function leadTimeMinutes(deploys: DeployEvent[], window: MeasurementWindow): number {
  return median(inWindow(deploys, window).map(d => {
    const minutes = (d.deployedAt.getTime() - d.committedAt.getTime()) / 60_000;
    if (!Number.isFinite(minutes) || minutes < 0) throw new RangeError("invalid timestamps");
    return minutes;
  }));
}

// A repair deploy is not itself a failed change merely because it is a hotfix.
export function changeFailureRate(deploys: DeployEvent[], failures: FailureAttribution[], window: MeasurementWindow): number {
  const prod = inWindow(deploys, window);
  if (prod.length === 0) return NaN;
  const failedIds = new Set(failures.map(f => `${f.service}\u0000${f.failedDeploymentId}`));
  const failed = prod.filter(d => failedIds.has(
    `${d.service}\u0000${d.id}`
  ));
  return failed.length / prod.length;
}

export function deploymentReworkRate(deploys: DeployEvent[], window: MeasurementWindow): number {
  const prod = inWindow(deploys, window);
  return prod.length ? prod.filter(d => d.triggeredByIncident === true).length / prod.length : NaN;
}

// Here the declared clock runs from originating deployment to confirmed restoration.
// If several incidents reference one deployment, use its latest confirmed restoration.
export function recoveryTimeMinutes(deploys: DeployEvent[], incidents: Incident[], window: MeasurementWindow): number {
  const durations: number[] = [];
  for (const d of inWindow(deploys, window)) {
    const linked = incidents.filter(i => i.service === d.service && i.failedDeploymentId === d.id);
    if (!linked.length || linked.some(i => i.resolvedAt === null)) continue;
    const restored = Math.max(...linked.map(i => i.resolvedAt!.getTime()));
    const minutes = (restored - d.deployedAt.getTime()) / 60_000;
    if (!Number.isFinite(minutes) || minutes < 0) throw new RangeError("invalid recovery timeline");
    durations.push(minutes);
  }
  return median(durations);
}
```

Each helper applies the same half-open interval (`startAt` included, `endAt` excluded) to production deployments. Filter to one service and deduplicate deployment IDs before calling them. Unresolved incidents are excluded from the completed-recovery median; report their count/age alongside it to avoid survivor bias. Define the failure-attribution policy before computing rates.

### Warehouse query joining deployments to attributed failures

```sql
-- BigQuery-style: weekly DORA view for one service
WITH prod_deploys AS (
  SELECT
    deployment_id,
    service,
    sha,
    committed_at,
    deployed_at,
    kind,
    triggered_by_incident,
    DATE_TRUNC(DATE(deployed_at), WEEK(MONDAY)) AS week
  FROM deploys
  WHERE environment = 'production' AND service = 'api'
),

failures AS (
  SELECT DISTINCT d.deployment_id
  FROM prod_deploys d
  JOIN deployment_failures f
    ON f.service = d.service
   AND f.failed_deployment_id = d.deployment_id
)

SELECT
  week,
  COUNT(*)                                        AS deploys_per_week,
  APPROX_QUANTILES(TIMESTAMP_DIFF(d.deployed_at, d.committed_at, MINUTE), 50)[OFFSET(25)] AS lead_time_p50_min,
  SAFE_DIVIDE(COUNTIF(f.deployment_id IS NOT NULL), COUNT(*)) AS change_failure_rate,
  SAFE_DIVIDE(COUNTIF(d.triggered_by_incident), COUNT(*)) AS deployment_rework_rate
FROM prod_deploys d
LEFT JOIN failures f USING (deployment_id)
GROUP BY week
ORDER BY week DESC;
```

### Report What the Dataset Cannot Establish

This example assigns one commit timestamp per deployment. Batched changes need an explicit per-change lead-time policy; measuring only the final commit can hide earlier commits waiting in the batch. Distinguish authored and committed timestamps and avoid mixing clocks across reports.

The SQL excerpt is BigQuery syntax, not portable PostgreSQL. `deployment_failures` is a normalized table of attributed production failures; raw rollbacks, hotfixes and incidents must be linked to the failed deployment before they enter it. The pure functions require selected-service data and deduplicated deployment IDs. Report absent data, unresolved recoveries and attribution quality; a median excluding unresolved incidents can look better precisely when severe failures remain open.

A dashboard should show the current observation window, event count, p50/p90 where relevant, failure/rework denominators, unresolved count/age and prior service baseline. Published performance clusters vary by research year; do not label illustrative numbers ELITE without a cited matching report and definitions.

## Real-World Use Cases

The numbers below are hypothetical diagnostic examples, not measured outcomes for named organizations.

### 1. Monolith-to-services baseline before a platform investment

A 40-team org instruments deploy webhooks into BigQuery for one quarter. Lead time p50 turns out to be 6 days, dominated by a manual QA sign-off queue — turning a "we need better CI runners" instinct into a "we need to automate the acceptance gate" decision.

### 2. Post-incident recovery loop

Incidents link to deployment IDs via the alert payload; after every Sev-2, the retro reviews detection, decision, deployment and restoration delays. In this hypothetical example, the team observes recovery time fall from 90 to 25 minutes after adding automated rollback, then checks incident mix and rollback safety before attributing the change to that intervention.

### 3. CFR-driven test investment

CFR rises from 6% to 14% over two months. Joining failure SHAs to changed paths shows 70% of failures touch the payments module; regression coverage concentrates there and CFR returns to baseline — metrics directing engineering effort, not dashboards for their own sake.

### 4. Error-budget-gated release train

A SaaS ties its weekly release train to budget state: full train above 30% budget, reduced train below, freeze below 10%. DF becomes an emergent property of reliability rather than a target argued over in planning.

## Common Mistakes

| Mistake | Fix |
| --------------------------------------------- | --------------------------------------------------------------- |
| Counting CI runs or staging syncs as deploys | Only production-facing deploy events count |
| Measuring lead time from PR merge | Start the clock at commit; merge hides review latency |
| Reporting means instead of medians | Means explode on outliers; medians reflect typical work |
| Defining failure as "Sev-1 only" | Failure = any deploy needing rollback/hotfix/incident |
| Team-wide averages across 100 services | Aggregate per service; org-wide means hide the distribution |
| Setting numeric targets ("DF >= 10/day") | Targets invite gaming; publish bands and investigate outliers |
| Vanity deploys: config-only pushes padding DF | Tag deploy kinds; report standard-code deploys separately |
| Weaponizing metrics in perf reviews | Metrics diagnose systems, not individuals — keep them blameless |

Gaming patterns deserve names because they will appear once leadership watches the dashboard:

```text
VANITY DEPLOY   : trivial pushes counted as shipping
BATCHING        : stacking a week of changes -> DF falls, blast radius grows,
                  CFR gets hidden inside big risky releases
SPLITTING       : slicing one logical release into five deploys to inflate DF
FAILURE HIDING  : calling a rollback a "revert refactor"
```

## Best Practices

1. **Automate collection end-to-end.** If a human updates the numbers, they stop being metrics and start being narratives.
2. **Record deployment and artifact identities alongside SHA.** One commit can be deployed repeatedly or to several services; attribute failure to the particular deployment.
3. **Use medians and distributions.** Publish p50/p90; a bimodal lead time (most fast, some ancient) is itself a finding.
4. **Define vocabulary in writing**: deployment, failure, restoration. Re-litigating definitions quarterly destroys trend lines.
5. **Review trends with the teams who own the numbers**, in the same forum as error-budget reviews — throughput and stability are one conversation.
6. **Compare against your own history first**, published bands second. Cross-org comparisons ignore domain context.
7. **Pair every throughput push with a stability check**: raising DF while CFR climbs means the gating was load-bearing.
8. **Keep dashboards blameless and boring.** The moment metrics enter individual reviews, Goodhart takes over.
9. **Distinguish remediation from the failed change.** Record the original failed deployment, confirmed restoration, and whether a later deploy is incident-driven rework. A rollback is not automatically a new failure.
10. **Start ugly, then refine.** A webhook + warehouse script this quarter beats a perfect taxonomy next year.

## Performance Considerations

| Concern | Reality | Guidance |
| ------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Data volume | Usually lower than trace volume, but varies with service count and deployment frequency | Size storage, retention, event cardinality and query costs from the actual dataset |
| Incident linking accuracy | The weakest joint | Require SHA fields in incident templates; accept some misses |
| Small-sample noise | Low-volume services swing wildly | Report rolling 30-90d windows; suppress tiny cohorts |
| Timezone/clock skew | Commit vs deploy clocks differ | Normalize to UTC; use server-side event timestamps |
| Privacy | Team-level data can feel surveillant | Keep granularity at service level; no individual leaderboards |

## Summary

- Current guidance defines five delivery measures, adding **deployment rework rate** to the historical four keys.
- Throughput and stability should be improved together; a single faster number does not establish better user outcomes.
- **Instrument from systems of record**: CD deploy events + git + incident tooling, joined by deployment and artifact identities with source SHA retained; distributions per service.
- Benchmarks vary by report year; compare consistent service-level measurements against their own baseline.
- Expect gaming and design against it: define deploy/failure precisely, tag deploy kinds, never tie metrics to individual evaluation.
- **Use error-budget policy with delivery evidence**: DORA describes delivery outcomes; a team may use current SLO risk and remaining budget to decide whether to proceed, limit or pause ordinary changes.
- **In interviews:** define the metric and its data source, state its limits, compare it with a service's own baseline, and explain how incentives can distort it.

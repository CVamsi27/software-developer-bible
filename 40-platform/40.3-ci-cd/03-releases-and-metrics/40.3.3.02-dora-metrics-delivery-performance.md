# DORA Metrics & Delivery Performance

> **Four numbers describe software delivery performance.** Deployment frequency, lead time for changes, failed-deployment recovery time, and change failure rate — the "four keys" from the DORA research program (the team behind *Accelerate*). They are the closest thing our industry has to a validated performance model: measured from systems of record, not spreadsheets; correlated with organizational outcomes; and stable across company sizes. This file defines each metric precisely, shows how to instrument them honestly from CI + incident tooling, gives the published benchmark bands, catalogs the ways teams accidentally (and deliberately) game them, and connects them to SLOs and error budgets.

## TL;DR

- **The four keys**:
  - **Deployment Frequency (DF)** — how often you deploy to production.
  - **Lead Time for Changes (LT)** — median time from commit to running in production.
  - **Failed Deployment Recovery Time (MTTR)** — median time to restore service after a bad change.
  - **Change Failure Rate (CFR)** — fraction of deployments that degrade service and need remediation.
- **Collect from systems of record**: CD events + git timestamps + incident tooling joined by git SHA. Never survey, never spreadsheet.
- **Benchmarks** come from annual DORA reports; thresholds were revised over the years (2021 elite: on-demand deploys, <1h lead, <1h recovery, 0-15% CFR). Treat bands as conversation anchors, not targets.
- **Honesty rules**: count production deploys only, define "failure" as remediation-required, use medians not means, measure per service.
- **Pitfalls**: vanity deploys (config churn), batching to hide failures, splitting releases to inflate DF, Goodhart's law when metrics become targets.
- **Error budgets close the loop**: DORA measures how fast you can change; SLOs/error budgets decide how much change is safe right now.
- **In interviews: name all four, give the formula, say where each data point comes from, and warn about gaming.**

## Definition

The **DORA metrics** (DevOps Research and Assessment, acquired by Google) quantify delivery performance along two axes — **throughput** (deployment frequency, lead time) and **stability** (recovery time, change failure rate). Research across tens of thousands of teams found these four measures cluster together: high performers score well on both speed AND stability, refuting the speed-vs-safety trade-off.

| Metric                          | Question it answers             | Formula (operational)                             |
| ------------------------------- | ------------------------------- | ------------------------------------------------- |
| Deployment Frequency            | How fast do we ship value?      | count(deployments to prod) / period               |
| Lead Time for Changes           | How long does one change take?  | median(deployed_at - committed_at) per deployment |
| Failed Deployment Recovery Time | How fast do we fix bad changes? | median(restored_at - failed_deploy_at)            |
| Change Failure Rate             | What fraction of changes hurt?  | failed_deployments / total_deployments            |

Definitions that matter more than formulas:

- **Deployment** = a release of code to PRODUCTION users. Staging syncs do not count. A feature-flagged dark launch counts if it ships executable code to prod.
- **Failure** = a deployment requiring remediation: rollback, emergency fix ("roll forward"), hotfix outside cadence, or an associated incident/SLO breach.
- **Recovery** starts at the failed deployment (or detection, whichever the report uses) and ends when user-facing service is restored — not when the fix PR merges.

---

## Why Do We Need It?

1. **You cannot improve what you cannot see.** Delivery friction hides in handoffs; four numbers localize it (slow lead time = process friction, high CFR = weak testing/gating).
2. **They are validated, not vibes.** DORA's multi-year research links the four keys to organizational performance, burnout reduction, and profitability — giving engineers evidence in roadmap arguments.
3. **They force system-of-record instrumentation.** To compute LT you must join git to CD; that join exposes broken tagging, missing environments, and manual deploy steps.
4. **Benchmarks calibrate ambition.** "We want to deploy daily" becomes concrete when compared against published performance clusters.
5. **They pair with reliability targets.** DF/LT describe velocity; error budgets describe safety. Together they answer "can we ship faster?" with data instead of opinion.

## How It Works

### 1. The measurement pipeline

```text
┌────────────────────────────────────────────────────────┐
│   GIT   │─────────►│ CI PIPELINE  │──────────►│ CD SYSTEM        │
│ sha,ts  │          │ build+test   │           │ argocd / actions │
└────────────────────────────────────────────────────────┘
     │                                                   │ deploy event
     │ sha                                               │ {sha, env, ts}
     │            ┌────────────────────┐                 │
     └───────────►│  EVENT STORE       │◄────────────────┘                  
                  │  (warehouse / BQ)  │      deploy records                  
     ┌────────────┤  join key: git SHA │
     │            └─────────▲──────────┘
     │                      │ incident {started_at, resolved_at,                             
     │                      │            linked_sha}                             
┌────────────────────────────────────────────────────────┐
│ METRIC COMPUTE                  │                       
│ DF, LT(median), MTTR(median),   │                       
│ CFR = failed / total            │                       
└────────────────────────────────────────────────────────┘
```

Every arrow is a real integration:

- **Deploy events** come from the CD system's API/webhook (ArgoCD app sync, GitHub `deployment_status`, Spinnaker pipeline complete). A green CI run is NOT a deployment.
- **Commit times** come from git (`authored/committed date` of the deployed SHA).
- **Failures** come from three signals, unioned: explicit rollbacks (deploy event type), hotfix deploys within N hours targeting the same component, and incidents in PagerDuty/Opsgenie whose timeline overlaps the deploy window and whose ticket references the SHA.

### 2. Benchmark bands (published)

From the DORA reports (2021 canonical table; note the reports revise buckets year to year):

| Metric                      | Elite                    | High         | Medium         | Low       |
| --------------------------- | ------------------------ | ------------ | -------------- | --------- |
| Deployment Frequency        | On-demand (multiple/day) | Daily-weekly | Weekly-monthly | Monthly+  |
| Lead Time for Changes       | < 1 hour                 | < 1 week     | 1 wk - 1 mo    | > 1 month |
| Failed Deploy Recovery Time | < 1 hour                 | < 1 day      | < 1 day        | > 1 week  |
| Change Failure Rate         | 0-15%                    | ~16-30%      | ~16-30%        | 16-60%    |

The 2023 report re-clustered: the "medium" band effectively dissolved into high/low, elite CFR tightened (~5%), and recovery-time bands merged downward. Use the shape (elite = daily+, hours-level lead/recovery, single-digit CFR), not the exact cells.

### 3. Instrumentation choices that determine honesty

| Decision              | Honest choice             | Dishonest drift                    |
| --------------------- | ------------------------- | ---------------------------------- |
| What counts as deploy | Prod-facing deploy events | Counting staging, cron restarts    |
| Failure definition    | Remediation required      | Only Sev-1 incidents               |
| Aggregation           | Median per service        | Mean across org (hides bimodality) |
| Window                | Rolling 30-90 days        | Cherry-picked sprints              |
| Attribution           | Per service/team          | One number for 200 services        |

### 4. Linking to error budgets

DORA answers throughput; **SLOs/error budgets gate it**:

```text
Error budget remaining?          DORA signal
────────────────────────────────────────────────────
> 50% budget left             -> increase DF, shorten LT gates
10-50%                        -> normal cadence, watch CFR
< 10% or burning fast         -> freeze non-essential deploys;
                                 invest in reliability work
CFR rising                    -> tighten pre-prod gates before DF drops
MTTR rising                   -> invest in observability/rollback tooling
```

This is the practical resolution of "speed vs stability": the four keys tell you how fast you CAN move; the budget tells you how fast you SHOULD move today.

## Code Examples

### Emitting a structured deploy event from GitHub Actions

```yaml
# .github/workflows/deploy.yml (excerpt)
jobs:
  deploy-production:
    runs-on: ubuntu-latest
    environment: production # approval gate lives here
    steps:
      - name: Roll out image by digest
        run: kubectl -n prod set image deploy/api api=ghcr.io/acme/api@${{ needs.build.outputs.digest }}

      - name: Emit deploy event (system of record)
        run: |
          curl -fsS -X POST https://metrics.internal/api/v1/deployments \
            -H "Authorization: Bearer ${{ secrets.METRICS_TOKEN }}" \
            -H 'content-type: application/json' \
            -d '{
              "service": "api",
              "environment": "production",
              "sha": "${{ github.sha }}",
              "committed_at": "$(git log -1 --format=%cI ${{ github.sha }})",
              "deployed_at": "'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'",
              "actor": "${{ github.actor }}",
              "kind": "standard"
            }'
```

### Computing the four keys from raw events

```typescript
// scripts/dora.ts — pure functions over deploy + incident records.
export interface DeployEvent {
  service: string;
  environment: "production" | "staging";
  sha: string;
  committedAt: Date;
  deployedAt: Date;
  kind: "standard" | "rollback" | "hotfix";
}

export interface Incident {
  service: string;
  startedAt: Date;
  resolvedAt: Date;
  linkedSha?: string;
}

const isProdDeploy = (d: DeployEvent) => d.environment === "production";

/** DF: production deployments per day, per service. */
export function deploymentFrequency(deploys: DeployEvent[], days = 30): number {
  const prod = deploys.filter(isProdDeploy);
  return prod.length / days;
}

/** LT: median minutes from commit to production deploy. */
export function leadTimeMinutes(deploys: DeployEvent[]): number {
  const sorted = deploys
    .filter(isProdDeploy)
    .map((d) => (d.deployedAt.getTime() - d.committedAt.getTime()) / 60_000)
    .sort((a, b) => a - b);
  if (sorted.length === 0) return NaN;
  const mid = Math.floor(sorted.length / 2);
  return sorted.length % 2 ? sorted[mid] : (sorted[mid - 1] + sorted[mid]) / 2;
}

/**
 * CFR: share of prod deploys requiring remediation.
 * A deploy fails if it was rolled back, is a hotfix, or an incident
 * references its SHA within the observation window.
 */
export function changeFailureRate(
  deploys: DeployEvent[],
  incidents: Incident[],
): number {
  const prod = deploys.filter(isProdDeploy);
  if (prod.length === 0) return 0;
  const incidentShas = new Set(incidents.map((i) => i.linkedSha).filter(Boolean));
  const failed = prod.filter(
    (d) => d.kind === "rollback" || d.kind === "hotfix" || incidentShas.has(d.sha),
  );
  return failed.length / prod.length;
}

/** MTTR: median minutes from a failed deploy to restoration. */
export function recoveryTimeMinutes(
  deploys: DeployEvent[],
  incidents: Incident[],
): number {
  const restoreDurations: number[] = [];

  const nextSuccessByService = new Map<string, Date>();
  for (const d of [...deploys].filter(isProdDeploy).sort(
    (a, b) => a.deployedAt.getTime() - b.deployedAt.getTime(),
  )) {
    // A later healthy deploy restores service after a rollback/hotfix chain.
    if (d.kind === "standard") {
      nextSuccessByService.set(d.service, d.deployedAt);
    } else {
      const restored = nextSuccessByService.get(d.service);
      if (restored) {
        restoreDurations.push((restored.getTime() - d.deployedAt.getTime()) / 60_000);
      }
    }
  }

  for (const i of incidents) {
    if (i.linkedSha && i.resolvedAt > i.startedAt) {
      restoreDurations.push((i.resolvedAt.getTime() - i.startedAt.getTime()) / 60_000);
    }
  }

  const sorted = restoreDurations.sort((a, b) => a - b);
  if (sorted.length === 0) return NaN;
  const mid = Math.floor(sorted.length / 2);
  return sorted.length % 2 ? sorted[mid] : (sorted[mid - 1] + sorted[mid]) / 2;
}
```

### Warehouse query joining deploys to incidents

```sql
-- BigQuery-style: weekly DORA view for one service
WITH prod_deploys AS (
  SELECT
    service,
    sha,
    committed_at,
    deployed_at,
    kind,
    DATE_TRUNC(deployed_at, WEEK) AS week
  FROM deploys
  WHERE environment = 'production' AND service = 'api'
),

failures AS (
  SELECT DISTINCT d.sha
  FROM prod_deploys d
  LEFT JOIN incidents i
    ON i.service = d.service
   AND i.started_at BETWEEN d.deployed_at AND TIMESTAMP_ADD(d.deployed_at, INTERVAL 48 HOUR)
  WHERE d.kind IN ('rollback', 'hotfix')
     OR i.id IS NOT NULL
)

SELECT
  week,
  COUNT(*)                                        AS deploys_per_week,
  APPROX_QUANTILES(TIMESTAMP_DIFF(d.deployed_at, d.committed_at, MINUTE), 50)[OFFSET(0)] AS lead_time_p50_min,
  COUNTIF(f.sha IS NOT NULL) / COUNT(*)           AS change_failure_rate
FROM prod_deploys d
LEFT JOIN failures f USING (sha)
GROUP BY week
ORDER BY week DESC;
```

## Real-World Use Cases

### 1. Monolith-to-services baseline before a platform investment

A 40-team org instruments deploy webhooks into BigQuery for one quarter. Lead time p50 turns out to be 6 days, dominated by a manual QA sign-off queue — turning a "we need better CI runners" instinct into a "we need to automate the acceptance gate" decision.

### 2. Post-incident MTTR loop

Incidents auto-link SHAs via the alert payload; after every Sev-2 the retro reviews MTTR decomposition (detect -> decide -> deploy). Adding automated rollback cut p50 MTTR from 90m to 25m without changing deploy frequency.

### 3. CFR-driven test investment

CFR rises from 6% to 14% over two months. Joining failure SHAs to changed paths shows 70% of failures touch the payments module; regression coverage concentrates there and CFR returns to baseline — metrics directing engineering effort, not dashboards for their own sake.

### 4. Error-budget-gated release train

A SaaS ties its weekly release train to budget state: full train above 30% budget, reduced train below, freeze below 10%. DF becomes an emergent property of reliability rather than a target argued over in planning.

## Common Mistakes

| Mistake                                       | Fix                                                             |
| --------------------------------------------- | --------------------------------------------------------------- |
| Counting CI runs or staging syncs as deploys  | Only production-facing deploy events count                      |
| Measuring lead time from PR merge             | Start the clock at commit; merge hides review latency           |
| Reporting means instead of medians            | Means explode on outliers; medians reflect typical work         |
| Defining failure as "Sev-1 only"              | Failure = any deploy needing rollback/hotfix/incident           |
| Team-wide averages across 100 services        | Aggregate per service; org-wide means hide the distribution     |
| Setting numeric targets ("DF >= 10/day")      | Targets invite gaming; publish bands and investigate outliers   |
| Vanity deploys: config-only pushes padding DF | Tag deploy kinds; report standard-code deploys separately       |
| Weaponizing metrics in perf reviews           | Metrics diagnose systems, not individuals — keep them blameless |

Gaming patterns deserve names because they will appear once leadership watches the dashboard:

```text
VANITY DEPLOY   : trivial pushes counted as shipping
BATCHING        : stacking a week of changes -> DF falls, blast radius grows,
                  CFR gets hidden inside big risky releases
SPLITTING       : slicing one logical release into five deploys to inflate DF
FAILURE HIDING  : calling a rollback a "revert refactor"
```

## Best Practices

1. **Automate collection end-to-end.** If a human updates the numbers, they stop being metrics and start being narratives.
2. **Join on git SHA.** It is the only key that unambiguously connects source, build, deploy, and incident.
3. **Use medians and distributions.** Publish p50/p90; a bimodal lead time (most fast, some ancient) is itself a finding.
4. **Define vocabulary in writing**: deployment, failure, restoration. Re-litigating definitions quarterly destroys trend lines.
5. **Review trends with the teams who own the numbers**, in the same forum as error-budget reviews — throughput and stability are one conversation.
6. **Compare against your own history first**, published bands second. Cross-org comparisons ignore domain context.
7. **Pair every throughput push with a stability check**: raising DF while CFR climbs means the gating was load-bearing.
8. **Keep dashboards blameless and boring.** The moment metrics enter individual reviews, Goodhart takes over.
9. **Instrument rollbacks explicitly** as a deploy kind — they are simultaneously your best MTTR signal and your honest CFR numerator.
10. **Start ugly, then refine.** A webhook + warehouse script this quarter beats a perfect taxonomy next year.

## Performance Considerations

| Concern                   | Reality                              | Guidance                                                      |
| ------------------------- | ------------------------------------ | ------------------------------------------------------------- |
| Data volume               | Trivial (events, not traces)         | A warehouse free tier handles org-scale easily                |
| Incident linking accuracy | The weakest joint                    | Require SHA fields in incident templates; accept some misses  |
| Small-sample noise        | Low-volume services swing wildly     | Report rolling 30-90d windows; suppress tiny cohorts          |
| Timezone/clock skew       | Commit vs deploy clocks differ       | Normalize to UTC; use server-side event timestamps            |
| Privacy                   | Team-level data can feel surveillant | Keep granularity at service level; no individual leaderboards |

## Summary

- Four metrics cover delivery: **deployment frequency** and **lead time** (throughput), **recovery time** and **change failure rate** (stability).
- High performers win on BOTH axes — the speed-vs-safety trade-off is largely a myth the research dismantled.
- **Instrument from systems of record**: CD deploy events + git + incident tooling, joined by SHA; medians over means; per-service over org-wide.
- Benchmarks are **anchors, not targets**: elite ≈ daily deploys, sub-hour lead/recovery, single-digit CFR.
- Expect gaming and design against it: define deploy/failure precisely, tag deploy kinds, never tie metrics to individual evaluation.
- **Error budgets operationalize the balance**: DORA says how fast you can move; the budget says how fast you should move today.
- **In interviews: formula + data source + benchmark + one gaming anecdote = senior-level answer.**

## Cheat Sheet

```text
DORA METRICS CHEAT SHEET
════════════════════════════════════════════════════════════════

THE FOUR KEYS
  • Deployment Frequency : prod deploys / period        (throughput)
  • Lead Time            : median(commit -> prod)       (throughput)
  • Recovery (MTTR)      : median(fail -> restored)     (stability)
  • Change Failure Rate  : failed deploys / total       (stability)

DATA SOURCES (join on git SHA)
  • Deploys  : CD webhooks/API (ArgoCD sync, GH deployment_status)
  • Commits  : git timestamps
  • Failures : rollback/hotfix deploy kinds + incident tool links

BENCHMARK ANCHORS (2021 table, revised yearly)
  Elite : on-demand DF | <1h lead | <1h recovery | 0-15% CFR
  High  : daily-weekly | <1w lead  | <1d recovery  | 16-30%
  2023+: medium band dissolved; elite CFR ~5%

HONESTY RULES
  • Production only • medians only • per-service only
  • Failure = needed remediation (rollback/hotfix/incident link)
  • No numeric targets -> bands + outlier investigation

GAMING WATCHLIST
  vanity deploys | batching | splitting | failure relabeling

ERROR-BUDGET LINK
  budget > 30%  -> ship faster (raise DF, trim gates)
  budget < 10%  -> freeze features, fund reliability
  CFR rising    -> strengthen gates BEFORE pushing DF

INTERVIEW FORMULA
  name all four -> formula -> data source -> benchmark ->
  gaming caveat -> error-budget tie-in
```

# CI/CD Interview Questions

## First Principles

This set probes pipeline economics (→ 40.3.2.02) and supply-chain trust (→ 40.3.2.04).:

1. **The senior tells are trade-off statements**: "X when Y, Z when not-Y" — juniors memorize answers; seniors recite the *conditions* under which each answer is right.
2. **Every question here maps to an axiom chain, not a fact** — if you can derive the answer from the linked chapters, you can answer the variant questions too (that's the point of → First Principles sections).

## 30 Most Asked CI/CD Interview Questions with Detailed Answers

---

### Question 1: What is CI/CD and why is it important?

**Answer:**

**CI (Continuous Integration)**: Automatically build and test code changes when pushed to a repository.

**CD (Continuous Delivery/Deployment)**: Automatically deploy code changes to production.

**Importance:**

- Faster release cycles
- Reduced manual errors
- Early bug detection
- Consistent deployments
- Improved developer productivity

---

### Question 2: What is the difference between Continuous Delivery and Continuous Deployment?

**Answer:**

| Aspect | Continuous Delivery | Continuous Deployment |
| ---------- | ------------------- | --------------------- |
| Deployment | Manual approval | Automatic |
| Release | On-demand | Every change |
| Risk | Lower (manual gate) | Higher (automated) |
| Speed | Slower | Faster |

The distinction is a single gate: both automate everything up to production, but Continuous Delivery stops at a manual approval while Continuous Deployment removes it entirely. The trade-off is blast radius versus lead time — the manual gate buys a human checkpoint at the cost of batched, riskier releases, which is why feature flags (not the approval step) are how mature teams de-risk full continuous deployment.

---

### Question 3: What are the stages of a CI/CD pipeline?

**Answer:**

```text

1. Source --> Code commit triggers pipeline

2. Build --> Compile code, build artifacts

3. Test --> Unit tests, integration tests

4. Security --> Vulnerability scanning

5. Package --> Create Docker image/artifacts

6. Deploy --> Deploy to staging/production

7. Monitor --> Verify deployment health

```

The senior signal is not reciting the stages — it is the properties between them. Fail-fast ordering: test before package, package once and promote the *same artifact* through staging to production rather than rebuilding per environment (rebuilds reintroduce drift). Security scanning belongs left (dependencies and container layers at build time), not as a release-eve gate. Parallelize independent stages and cache aggressively — a pipeline over ten minutes gets bypassed, and a bypassed pipeline is worse than a slow one.

### Question 4: What is a Dockerfile and why use it?

**Answer:**

A Dockerfile is a text file with instructions to build a Docker image.

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

```

**Benefits:**

- Reproducible builds
- Environment consistency
- Version control for infrastructure
- Easy deployment

The mechanism interviewers probe is the layered build cache: each instruction is a layer invalidated from the first changed line down. That is why the example copies `package*.json` before the source — dependency layers stay cached while code churns. Senior additions: multi-stage builds so build toolchains never ship in the final image, base images pinned by digest for reproducibility, and the tradeoff between alpine (small, musl quirks) and slim variants. A Dockerfile is code: it gets reviewed, linted (hadolint), and versioned like code.


---

### Question 5: What is the difference between a Docker image and a container?

**Answer:**

| Aspect | Image | Container |
| -------- | -------------- | ---------------- |
| State | Immutable | Mutable |
| Storage | Registry | Local filesystem |
| Creation | `docker build` | `docker run` |
| Analogy | Class | Instance |

The mechanism is layered filesystems: an image is an immutable stack of layers in the registry; a container is that stack plus one writable layer, created in seconds because nothing is copied. The consequence interviewers probe: a container's writes die with it — state belongs in volumes, and 'rebuild the image' versus 'restart the container' is a different operation precisely because of this split.

---

### Question 6: What is Kubernetes and why use it?

**Answer:**

Kubernetes is a container orchestration platform that automates deployment, scaling, and management of containerized applications.

**Key Features:**

- Self-healing
- Horizontal scaling
- Service discovery
- Automated rollouts
- Secret management

What Kubernetes actually is: a declarative reconciliation loop — you state desired state, controllers continuously converge actual state toward it. That model is what enables self-healing, rollouts, and GitOps; anything built on top inherits it. The senior tradeoff: orchestration has real operational and cognitive cost, so small static workloads on a single VM or a PaaS can be the right answer — reach for K8s when you need multi-service scheduling, autoscaling, and rollouts across a fleet, and prefer managed control planes (EKS/GKE/AKS) over operating one.

### Question 7: What is a Kubernetes Deployment?

**Answer:**

A Deployment manages ReplicaSets and Pods, providing:

- Rolling updates
- Rollbacks
- Scaling
- Self-healing

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    spec:
      containers:

        - name: myapp
          image: myapp:1.0.0

```

Mechanically, a Deployment owns ReplicaSets; each pod-template change creates a *new* ReplicaSet and the rollout is just scaling old down and new up — which is why rollback is trivial (scale the previous RS back). Senior details: `maxSurge`/`maxUnavailable` control blast radius and speed; `revisionHistoryLimit` bounds rollback depth. Know when Deployment is the wrong controller: stateful identity needs StatefulSet, node-level agents need DaemonSet, finite work needs Job/CronJob.

### Question 8: What is Infrastructure as Code (IaC)?

**Answer:**

Managing infrastructure through code instead of manual processes.

**Tools:**

- Terraform
- AWS CloudFormation
- Pulumi
- Ansible

**Benefits:**

- Version control
- Reproducibility
- Automation
- Documentation

The defining property is declarative state with a persistent state file — the file records what Terraform *believes* exists, which is why plan/apply exists: plan diffs desired vs. recorded reality before anything touches cloud APIs. Senior depth: state locking prevents concurrent applies, remote state with locking (S3+DynamoDB or Terraform Cloud) is mandatory for teams, and drift detection catches out-of-band console changes. The review gate for infrastructure is the plan output, reviewed like a diff — because it is one.

### Question 9: What is a CI/CD pipeline?

**Answer:**

An automated workflow that builds, tests, and deploys code changes.

```yaml
# Example GitHub Actions workflow
name: CI/CD
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:

      - uses: actions/checkout@v7
      - run: npm ci
      - run: npm test
      - run: docker build -t myapp .
      - run: docker push myapp:latest

```

What separates this from the stages question: a pipeline is a sequence of *quality gates* ending in a single promoted artifact. Build once — the image tested in CI is byte-identical to the one deployed — otherwise testing proved nothing about production. Practical senior concerns: keep p95 pipeline time low enough that developers trust it, run independent jobs in parallel, cache dependencies keyed on lockfiles, and fail the pipeline on flaky tests rather than retrying them silently — a pipeline that lies trains people to ignore red.

### Question 10: What is version control and why is it important?

**Answer:**

Version control tracks changes to code over time.

**Benefits:**

- Collaboration
- History tracking
- Branching/merging
- Rollback capability
- Audit trail

**Tools:**

- Git
- GitHub
- GitLab
- Bitbucket

The CI connection is the part juniors miss: CI *is* an automation triggered by version-control events, so branch strategy and pipeline design are one decision. Trunk-based development with short-lived branches keeps integration pain low and makes rollforward the default recovery; long-lived feature branches demand merge debt and break continuous integration's premise. Protected branches plus required PR checks make the main branch always releasable — that invariant is what the whole deployment pipeline stands on.


---

### Question 11: What is a microservices architecture?

**Answer:**

An architecture style where applications are built as small, independent services.

**Benefits:**

- Independent deployment
- Technology flexibility
- Scalability
- Fault isolation

**Challenges:**

- Distributed system complexity
- Network latency
- Data consistency

The interview angle is the CI/CD consequence: independent deployability is the whole point, and it is only real with per-service pipelines plus consumer-driven contract tests — otherwise one team's release breaks another's and you have a distributed monolith. Senior honesty: microservices trade code complexity for operational complexity, so they require CI/CD maturity, observability, and on-call capacity first. Start modular-monolith and extract services when team topology demands independent deploys — Conway's law is the actual driver.


---

### Question 12: What is a container registry?

**Answer:**

A storage system for Docker images.

**Examples:**

- Docker Hub
- AWS ECR
- Google GCR
- Azure ACR
- Harbor (self-hosted)

What matters beyond the list: registries are the trust boundary of deployment. Tag discipline — deploy by immutable digest, never `:latest` — makes rollbacks exact; vulnerability scanning on push (Trivy, ECR scanning) catches CVEs before deploy; retention policies bound cost; and promotion means the same artifact moving across registries/environments, not rebuilds. Self-hosted Harbor shows up when data-residency or air-gapped environments rule out managed registries.

### Question 13: What is the difference between `docker build` and `docker compose`?

**Answer:**

| Aspect | docker build | docker compose |
| ------------- | ------------------ | --------------------------- |
| Purpose | Build single image | Manage multi-container apps |
| Configuration | Dockerfile | docker-compose.yml |
| Use case | Image creation | Application stack |

The confusion comes from compose *also* building images (when a `build:` key is present), but its real job is orchestration of a stack: networks, volumes, and multiple services from one file. `docker build` produces exactly one image and knows nothing about runtime topology. In pipelines they compose: build/push per service image, then compose (or K8s manifests) to stand up the full stack for integration tests.

### Question 14: What is a Kubernetes Service?

**Answer:**

A Service provides stable networking for Pods.

**Types:**

- ClusterIP: Internal only
- NodePort: Expose on node IP
- LoadBalancer: Cloud load balancer

Mechanism: ClusterIP is a virtual IP with stable DNS; kube-proxy programs iptables/IPVS (or eBPF in modern setups) to load-balance to ready pod IPs — pods come and go, the VIP does not. That is why readiness gates membership. Senior tradeoffs: NodePort burns ports and exposes node addresses; LoadBalancer costs one cloud LB per service, which is why Ingress (or Gateway API) fronts many services with one entry point. Headless Services (`clusterIP: None`) matter when clients need direct pod DNS — StatefulSets.


---

### Question 15: What is Helm?

**Answer:**

The package manager for Kubernetes.

**Benefits:**

- Packages multiple manifests
- Manages releases
- Configurable via values
- Rollback capability

Helm's model: charts are Go templates over `values.yaml`, and a release is a tracked installation instance stored in-cluster — which is what makes `helm rollback` and `helm diff` possible. Senior depth: template rendering errors are runtime-not-parse-time, so CI runs `helm lint`, `helm template`, and `helm diff upgrade --dry-run` before any apply; pin chart versions; secrets do not belong in plain values (SOPS/Sealed Secrets). The honest alternative: Kustomize — patches over base manifests, no templating language; teams pick per tolerance for logic-in-YAML.


---

### Question 16: What is a webhook in CI/CD?

**Answer:**

A webhook triggers a CI/CD pipeline when an event occurs (e.g., code push, PR creation).

Mechanism: the forge HTTP-POSTs an event payload to your CI's webhook URL, which enqueues a run — push-to-deploy rather than poll. The senior details are the failure modes: validate the shared secret (HMAC signature) so anyone cannot trigger builds, handle delivery retries with idempotency (dedupe by delivery ID), and know the failure mode when CI is down — GitHub retries with backoff then drops, so missed webhooks need a reconciliation path (API-triggered runs, scheduled catch-up).

### Question 17: What is the difference between a build and a release?

**Answer:**

| Aspect | Build | Release |
| ------- | -------------------- | -------------------- |
| Purpose | Create artifacts | Distribute artifacts |
| Trigger | Code change | Manual/automated |
| Output | Docker image, binary | Deployed application |

The distinction is artifact versus act: a build produces an immutable, versioned artifact (image, binary) from source; a release is the decision and mechanics of putting that artifact into an environment. Keeping them separate is the whole point of modern pipelines — the *same* promoted artifact moves dev → staging → prod, so what you tested is bit-for-bit what you ship; rebuilding per environment is the anti-pattern this separation exists to kill.

---

### Question 18: What is a staging environment?

**Answer:**

A production-like environment used for testing before deployment.

**Purpose:**

- Integration testing
- Performance testing
- User acceptance testing
- Validation

The real topic is environment parity: staging drifts from production in data shape, scale, and integrations, which is why 'it passed staging' is weak evidence. Senior directions: ephemeral preview environments per PR (each PR gets a fresh namespace with seeded data) give parity *per change* rather than a shared long-lived environment everyone dirties; sensitive data gets masked or synthesized (GDPR); and cost is the constraint that decides between a permanent staging fleet and on-demand namespaces.


---

### Question 19: What is a canary deployment?

**Answer:**

Gradually rolling out changes to a small subset of users.

**Benefits:**

- Reduced risk
- Real-world testing
- Easy rollback

What makes canary real is automated metric comparison: route a small percentage, compare error rate and latency against the stable version, promote or roll back on thresholds — Argo Rollouts and Flagger encode exactly this. Without measurement it is just a slow rollout. Senior details: canaries need enough traffic for statistical signal (low-traffic services need longer windows), database migrations must be backward-compatible because two versions run simultaneously, and session affinity can bias the sample.


---

### Question 20: What is blue-green deployment?

**Answer:**

Maintaining two identical environments and switching traffic between them.

**Benefits:**

- Zero downtime
- Instant rollback
- Easy testing

The tradeoffs: instant rollback (flip traffic back) but 2x infrastructure cost during releases, and the hard part is state — databases cannot be blue-green naively, so migrations must be expand/contract (additive first, contract later) to keep both versions correct. Docker-era nuance: blue-green at the LB/target-group level is routine; the senior variation is doing it at the *cluster* level or with feature flags to decouple deploy from release entirely.


---

### Question 21: What is feature flagging?

**Answer:**

A technique to enable/disable features without deployment.

```javascript
if (featureFlags.newCheckout) {
  return newCheckoutFlow();
}

```

**Benefits:**

- Decouple deployment from release
- A/B testing
- Gradual rollout

The principle this encodes: decouple deployment from release — code ships dark, exposure is a runtime decision. Senior depth: percentage rollouts, kill switches that beat rollback speed in incidents, and A/B assignment keyed on stable user attributes. The costs that show up in interviews: flag debt (flags outliving their experiment — retire them on a schedule or the codebase fills with dead branches), testing both paths (every flag doubles test matrices), and the failure mode when the flag service is down — default to safe and fail closed on consequential paths.


---

### Question 22: What is observability in CI/CD?

**Answer:**

Monitoring and understanding system state through logs, metrics, and traces.

**Components:**

- Logging (ELK, Loki)
- Metrics (Prometheus, Grafana)
- Tracing (Jaeger, Zipkin)

The CI/CD-specific layer: pipeline health is measured with DORA metrics — deployment frequency, lead time for changes, change failure rate, MTTR — because they predict delivery performance better than stage timings. Practical depth: build logs and test results are artifacts (kept, linked from the deploy record), flaky tests get quarantined and tracked as bugs not retried into silence, and deployment events get annotated on production dashboards so an SRE can correlate an incident with a release instantly.


---

### Question 23: What is GitOps?

**Answer:**

A Git-centric approach to infrastructure and deployment.

**Principles:**

- Git as single source of truth
- Automated deployment
- Version control for infrastructure
- Pull-based model

**Tools:**

- Argo CD
- Flux

The differentiator vs. push-based CI/CD: a controller *inside* the cluster pulls from Git and reconciles — the cluster never accepts pushes, credentials for CI are eliminated, and drift (someone kubectl-edited prod) is detected and reverted. The PR process becomes the deployment approval. Senior gotchas: secrets cannot be plain Git (Sealed Secrets, SOPS, or External Secrets Operator referencing a vault), and sync waves/ordering matter for databases-before-apps. Argo CD and Flux are the standard implementations.


---

### Question 24: What is a pipeline as code?

**Answer:**

Defining CI/CD pipelines in version-controlled files.

**Examples:**

- GitHub Actions (YAML)
- GitLab CI (.gitlab-ci.yml)
- Jenkins (Jenkinsfile)

The why: pipelines versioned beside the app get the same review, history, and revert as code — a deploy change is a PR, not a console edit. Senior depth: YAML sprawl is the known failure mode, cured by reusable workflows/templates/composites shared across repos; pipeline changes get validated on a branch before touching main (CI for CI); and the Jenkinsfile caveat — Groovy scripting power is exactly what makes Jenkinsfiles unmaintainable without discipline.


---

### Question 25: What is artifact management?

**Answer:**

Storing and versioning build artifacts.

**Examples:**

- Docker images (registry)
- npm packages (npm registry)
- Maven artifacts (Nexus)
- Helm charts (chart museum)

The senior framing: artifacts are the unit of promotion — build once, store once, promote by reference through environments; never rebuild on the way to prod. Depth: immutability (digests, never overwrite released tags), retention policies because registries grow unbounded and cost real money, and provenance as the emerging signal — SBOMs and signed attestations (SLSA levels, cosign) so a deployed image can be traced to the exact commit and build that produced it.

### Question 26: What is the difference between a build agent and a runner?

**Answer:**

| Aspect | Build Agent | Runner |
| ------------- | --------------- | ---------------------------- |
| Usage | Jenkins, Bamboo | GitHub Actions, GitLab CI |
| Configuration | Manual | YAML-based |
| Management | Self-hosted | GitHub-hosted or self-hosted |

The real difference is who owns the lifecycle: Jenkins agents are long-lived self-managed hosts — you patch them, drain them, and debug their snowflake state. Runners (GitHub/GitLab) invert that: ephemeral, declared in YAML, thrown away per job, which is why hosted runners have no config drift. The trade-off is control versus maintenance — self-hosted runners exist for private networks, custom hardware, and cost, carrying the old agent-management burden with them.

### Question 27: What is a secrets manager?

**Answer:**

A tool for securely storing and accessing secrets.

**Examples:**

- HashiCorp Vault
- AWS Secrets Manager
- Azure Key Vault
- GitHub Secrets

The architecture question hiding here: *when* do secrets enter the process. Never build-time (they live forever in image layers and CI logs) — runtime injection from the manager via mounted volumes or CSI drivers, or an operator like External Secrets syncing into K8s Secrets. Senior depth: prefer short-lived credentials — OIDC federation lets CI assume a cloud role per-run with no stored cloud keys at all, which removes the biggest breach class. Rotation is a property of the design, not a calendar reminder.


---

### Question 28: What is a Kubernetes Ingress?

**Answer:**

Manages external HTTP/HTTPS access to Services.

**Features:**

- TLS termination
- Host-based routing
- Path-based routing

Mechanism: Ingress is just a resource — an *Ingress controller* (NGINX, Traefik, cloud LB) implements it, reading Ingress objects and programming the actual routing; no controller, no effect. Depth: TLS termination plus cert-manager automating issuance/renewal from Let's Encrypt or private CAs is the day-one setup; canary-weight annotations exist but are controller-specific. The forward-looking answer: Gateway API is the successor — role-separated (platform team owns Gateway, teams own HTTPRoutes), extensible, and portable.


---

### Question 29: What is a service mesh?

**Answer:**

An infrastructure layer for service communication.

**Examples:**

- Istio
- Linkerd
- Consul Connect

**Features:**

- Traffic management
- Security (mTLS)
- Observability

The honest answer includes the cost: sidecar proxies add a hop (latency), heavy memory footprint, and real operational complexity, so the value — uniform mTLS, retries, circuit breaking, golden metrics without touching app code — only pays at fleet scale with many teams and compliance demands. Smaller systems get mTLS from the ingress plus app-level retries. Cilium's eBPF sidecar-less model is the current counter-trend, trading kernel-level efficiency for the same features.

### Question 30: What are the best practices for CI/CD?

**Answer:**

1. **Automate everything** - Build, test, deploy

2. **Version control** - All configuration and code

3. **Fast feedback** - Short pipeline duration

4. **Security scanning** - Integrate in pipeline

5. **Monitoring** - Track pipeline health

6. **Rollback strategy** - Automated rollback on failure

7. **Environment parity** - Same across environments

8. **Secrets management** - Never hardcode

9. **Documentation** - Maintain runbooks
10. **Continuous improvement** - Regular pipeline reviews

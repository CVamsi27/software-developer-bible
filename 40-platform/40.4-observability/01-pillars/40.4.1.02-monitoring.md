# Monitoring

## Definition

Monitoring is the process of collecting, analyzing, and acting on metrics (numeric measurements) to understand system health, performance, and behavior over time. While logging tells you *what happened*, monitoring tells you *how your system is performing* right now and whether it has deviated from expected behavior.

> **Textbook Definition:** Monitoring observes system behavior over time by collecting and evaluating signals against expected conditions, supporting detection, diagnosis, capacity decisions, and response.

A **monitoring system** scrapes or receives metrics at regular intervals, stores them in a time-series database, visualizes them on dashboards, and fires alerts when predefined thresholds are breached.

## First Principles

One request cannot establish system health. Aggregate repeated observations over defined intervals, retaining enough dimensions to distinguish important workloads without recording every identity. Then separate application failure from failures in collection itself; a missing measurement is not an observed healthy value.

## Choose the Measurement Type Before Its Query

| Type | Meaning | Example |
| --------- | -------------------------------------------------- | --------------------------------- |
| Counter | Cumulative events, normally increasing until reset | Completed requests |
| Gauge | Current value that can rise/fall | In-flight requests or queue depth |
| Histogram | Count/sum and a distribution representation | Request duration |
| Summary | Client-computed quantiles plus count/sum | Local instance latency quantile |

Counters need rate/increase over a window, with resets handled per series before aggregation. Classic histogram buckets are cumulative (`le` bounds) rather than disjoint bars. Quantiles estimated from aggregated histogram buckets depend on bucket resolution; averaging instance p99 values does not produce fleet p99. Summary quantiles generally cannot be merged across instances, while their count/sum can be aggregated for a mean.

```text
application instrumentation → private metrics endpoint → scraper/collector
                             → time-series store → queries/dashboards/alert rules
```

Collection interval, labels, retention and scrape health determine evidence resolution/cost. RED means Rate, Errors, Duration for requests; USE means Utilization, Saturation, Errors for resources. The golden signals add traffic, latency, errors and saturation as useful investigation dimensions; they do not automatically define a contractual SLO.

## Instrument a Complete Tiny Application

Install a reviewed `@prometheus-io/client` version and save this Node ES module. A separate private endpoint/access policy is preferable for real deployments; this localhost demonstration keeps one server for clarity.

```javascript
// monitoring.mjs
import { createServer } from 'node:http';
import { performance } from 'node:perf_hooks';
import { Registry, Counter, Gauge, Histogram } from '@prometheus-io/client';
export const registry = new Registry();
const requests = new Counter({ name: 'demo_requests_total', help: 'Completed writes',
  labelNames: ['route', 'status'], registers: [registry] });
const duration = new Histogram({ name: 'demo_duration_seconds', help: 'Completed write duration',
  labelNames: ['route'], buckets: [0.01, 0.1, 0.5, 1], registers: [registry] });
const inFlight = new Gauge({ name: 'demo_in_flight', help: 'In-flight requests', registers: [registry] });
const aborted = new Counter({ name: 'demo_aborted_total', help: 'Premature connection closes', registers: [registry] });
export const server = createServer(async (req, res) => {
  const route = req.url === '/health' ? '/health' : req.url === '/metrics' ? '/metrics' : 'unmatched';
  if (route !== '/metrics') {
    const started = performance.now(); inFlight.inc(); let settled = false;
    const settle = completed => {
      if (settled) return; settled = true; inFlight.dec();
      if (!completed) { aborted.inc(); return; }
      requests.inc({ route, status: String(res.statusCode) });
      duration.observe({ route }, (performance.now() - started) / 1000);
    };
    res.once('finish', () => settle(true));
    res.once('close', () => settle(res.writableFinished));
  }
  if (route === '/metrics') {
    try { res.writeHead(200, { 'content-type': registry.contentType }); res.end(await registry.metrics()); }
    catch { res.writeHead(500); res.end('Metrics unavailable'); }
    return;
  }
  res.writeHead(route === '/health' ? 200 : 404); res.end(route === '/health' ? 'ok' : 'Not found');
});
if (process.env.RUN_DEMO === 'true') server.listen(4302, '127.0.0.1');
```

Run `RUN_DEMO=true node monitoring.mjs`, request `/health` and several unknown paths, then inspect `/metrics`. All unknown paths share `unmatched`, so random IDs cannot create a new series per URL. The gauge settles once for both normal finish and premature close. This demo observes response-write completion, not authenticated business success; define eligible requests and failures for the real user contract.

## Query With Matching Units and Labels

For this classic histogram/counter shape, PromQL examples are:

```promql
# Request rate across instances, keeping route.
sum by (route) (rate(demo_requests_total[5m]))

# Failure fraction per route: drop status before dividing.
sum by (route) (rate(demo_requests_total{status=~"5.."}[5m]))
/
sum by (route) (rate(demo_requests_total[5m]))

# Approximate p99 per route, preserving le during bucket aggregation.
histogram_quantile(0.99,
  sum by (route, le) (rate(demo_duration_seconds_bucket[5m])))
```

A fresh series needs enough samples for rate. The numerator may be absent when no matching error series exists; zero eligible traffic can produce an undefined ratio. Handle these cases deliberately in dashboards/recording rules and use separate completeness/scrape-health checks. Do not silently convert missing instrumentation or failed scrapes into zero user errors. A threshold rule and `for` duration do not supply this policy automatically.

## Control Series Growth and Collection Failure

A label combination produces a time series, and histogram buckets multiply that cost. Two routes × five status values × ten instances already produce 100 counter series, before duration buckets. Keep route templates and bounded status/operation categories; put individual identities in protected logs/traces when needed.

Avoid public `/metrics` exposure that leaks topology, tenant labels or business information. Bound cardinality, collection time and exporter failure. Monitor scraper/collector health, queue losses and stale series; `up == 0` detects selected failed scrapes, but an entirely removed target may need absence/inventory checks.

Synthetic checks need a defined endpoint/body contract, timeout, response consumption and cleanup in `finally`. Prevent overlapping runs from accumulating. External HTTP success is one observation point; it may not cover authenticated journeys, queues or every region.

## Real-World Decisions

For a request service, begin with eligible traffic, user success and latency, then resource/queue signals that explain saturation. For background work, include oldest-item age and successful completion; a small queue can still contain one stuck critical job. Infrastructure thresholds support diagnosis, while paging policy should reflect actionable user impact or imminent failure.

Choose histogram boundaries near the SLO and measure storage/scrape costs. There is no universal metric-count or scrape-interval rule that proves low overhead. Record query/dashboards in version control and test label/reset/missing-data scenarios before using them as release gates.

## Common Mistakes

| Mistake | Failure mechanism | Better boundary |
| ----------------------------- | ----------------------------------------- | -------------------------------------- |
| Raw URL fallback labels | Attackers create unbounded series | Bounded route template/unmatched label |
| Divide while retaining status | Numerator/denominator label sets mismatch | Aggregate to matching dimensions |
| Average instance p99 | Quantiles are not composable that way | Aggregate histogram distribution |
| Decrement only on finish | Aborts leak in-flight gauge | Once-only finish/close cleanup |
| Treat absent data as healthy | Collection failure masks impact | Completeness and failure policy |

## Best Practices

Define the question, population, measurement and units before the dashboard. Use correct counter/distribution aggregation, bounded labels, private collection and explicit missing-data policy. Alert from meaningful user/resource signals with an owner and runbook; test the query's actual failure cases.

## Summary

Monitoring evaluates repeated observations against a defined contract. Instrument types and labels determine valid queries; distribution aggregation, bounded cardinality and collection health determine whether those queries are credible. Missing data and zero traffic require explicit interpretation.

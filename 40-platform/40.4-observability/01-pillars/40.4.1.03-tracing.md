# Distributed Tracing

A checkout request takes 900 ms, while the API handler records only 80 ms. The missing time may be in inventory, payment, a queue, or an uninstrumented wait; a trace connects the observed operations so the team can inspect that path.

## Definition

Distributed tracing is a method of tracking the flow of a request as it travels through multiple services in a distributed system. Each unit of work is recorded as a **span**, and all spans from a single request form a **trace**. Tracing answers the question: *"Where did time go for this request?"*

> **Textbook Definition:** Distributed tracing records causally related operations as spans with propagated context, enabling reconstruction of a request's path, timing, and dependency interactions across process boundaries.

A **trace** is a directed acyclic graph (DAG) of spans representing the causal relationships between operations. A **span** is a named, timed operation with metadata (attributes), events, and a parent-child relationship to other spans.

## First Principles

A request may wait on work in several processes, so no local timer can identify the entire path. Carry a correlation context across boundaries and record the operations it connects. Instrumentation and sampling can omit work, clocks can differ, and parallel spans overlap; interpret a trace as observed evidence rather than a complete proof of causation.

## 1. Understand the Trace Before Installing a Collector

A **span** represents a timed operation with an ID, attributes/events, and status. Spans usually share a trace ID and parent relationships; **links** can connect other contexts for asynchronous or batched work. A simple request forms a tree, while links and asynchronous work make the wider causal graph richer.

```text
checkout request
  ├─ inventory call ── database operation
  └─ pricing call
       then payment call
```

If inventory and pricing run concurrently, their durations cannot simply be added to derive request duration. Inspect overlap and the critical dependency path. A large parent span may contain waiting, uninstrumented work, or CPU; the longest child is not always the complete bottleneck.

## 2. Propagate Valid Context Without Trusting It as Identity

W3C `traceparent` carries version, a 32-hex-digit trace ID, 16-hex-digit parent ID, and flags. For example:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

The sampled flag is a sampling signal, not an authorization claim. Use a propagator to validate/extract/inject context rather than inventing malformed IDs. At an untrusted boundary, decide which context to accept, restart, or link and what baggage to forward. A supplied trace ID does not identify an authenticated user.

## 3. Record a Runnable Parent/Child and Failure Trace

Install compatible reviewed OpenTelemetry API, trace-node, trace-base, and core packages. This local example exports to memory so the relationships are checkable; network export/collectors are taught in the [OpenTelemetry chapter](../04-advanced-telemetry/40.4.4.01-opentelemetry.md).

```javascript
// tracing.mjs
import assert from 'node:assert/strict';
import { trace, propagation, context, SpanStatusCode, ROOT_CONTEXT } from '@opentelemetry/api';
import { NodeTracerProvider } from '@opentelemetry/sdk-trace-node';
import { SimpleSpanProcessor, InMemorySpanExporter } from '@opentelemetry/sdk-trace-base';
import { W3CTraceContextPropagator } from '@opentelemetry/core';
const exporter = new InMemorySpanExporter();
const provider = new NodeTracerProvider({ spanProcessors: [new SimpleSpanProcessor(exporter)] });
provider.register({ propagator: new W3CTraceContextPropagator() });
const tracer = trace.getTracer('checkout-demo');
await tracer.startActiveSpan('checkout', async parent => {
  try {
    const headers = {}; propagation.inject(context.active(), headers);
    assert.match(headers.traceparent, /^00-[0-9a-f]{32}-[0-9a-f]{16}-01$/);
    const extracted = propagation.extract(ROOT_CONTEXT, headers);
    await context.with(extracted, () => tracer.startActiveSpan('remote-inventory', async child => {
      try { await Promise.resolve(); throw new Error('Synthetic inventory failure'); }
      catch (error) { child.recordException(error); child.setStatus({ code: SpanStatusCode.ERROR }); }
      finally { child.end(); }
    }));
  } finally { parent.end(); }
});
await provider.forceFlush();
const spans = exporter.getFinishedSpans();
assert.equal(spans.length, 2);
const child = spans.find(s => s.name === 'remote-inventory');
const parent = spans.find(s => s.name === 'checkout');
assert.equal(child.spanContext().traceId, parent.spanContext().traceId);
assert.equal(child.parentSpanContext.spanId, parent.spanContext().spanId);
assert.equal(child.status.code, SpanStatusCode.ERROR);
assert.equal(child.events[0].name, 'exception');
await provider.shutdown();
```

Extraction alone does not create a server span; the example explicitly starts one under the extracted context. The memory carrier simulates a process boundary but is not an HTTP/network integration test. Automatic instrumentation may create client/server spans for supported libraries; initialize it before those libraries load and avoid duplicating already-created spans.

A `startActiveSpan` callback does not automatically end the span. Use `finally`, including rejection/cancellation paths. Recording an exception and setting error status are separate operations. Error messages can contain sensitive data, so apply the event/attribute privacy policy.

## 4. Keep Baggage Separate from Authorization

**Baggage** carries key/value metadata between services; it is not automatically a span attribute and is not inherently authenticated. Do not grant a premium tier or tenant access from caller-provided baggage. Derive permission from validated application identity, allowlist bounded propagation fields, and prevent accidental forwarding to unrelated external services.

Log correlation can attach active valid trace/span IDs to safe events. Sampled-out spans can still have valid propagated IDs, so a correlated log does not guarantee a stored trace exists. Avoid raw tokens, full query strings, personal fields, and uncontrolled span names.

## 5. Choose Sampling from What You Need to Preserve

**Head sampling** decides at span creation, before the eventual result is known. A ParentBased sampler follows the parent's decision and a configured root policy; it cannot retroactively retain all errors from root traces it dropped. Sampler options require sampler objects, not boolean-returning callbacks.

**Tail sampling** buffers received spans and chooses after observing them. It needs sufficient upstream collection, bounded memory, decision timing, and routing that brings a trace's spans to the decision point. If head sampling already discarded an error, the collector cannot recover it. Late/missing spans and overloaded buffers limit completeness.

Sampling for diagnosis can bias counts and latency distributions. Use suitable independently collected metrics for contractual SLIs, or explicitly account for the trace selection policy. Measure actual SDK/collector/export cost; fixed "less than 1ms" or "under 50 spans" rules do not establish overhead.

## Real-World Use Cases

- **Slow checkout.** Inspect overlap, dependencies, and uninstrumented gaps, then corroborate with logs and resource profiles.
- **Messaging.** Decide whether processing is a child of a producer context or linked asynchronous work, and carry context in message metadata under privacy bounds.
- **Export outages.** Bound queues/retries and observe losses; telemetry must not make the request path unbounded.

## Summary

Tracing connects observed timed operations across boundaries. Correct context, explicit span lifecycle, and meaningful relationships reveal where a request waits; sampling and missing instrumentation limit that picture. Baggage and trace IDs support correlation, never authorization.

# Error Tracking

After a release, checkout failures rise, but every report has a different request ID and the stack points into minified code. Error tracking groups likely repeats, ties them to the deployed release, and restores source locations so an engineer can choose the next repair.

## Definition

Error tracking is the practice of capturing, grouping, prioritizing, and alerting on application errors across all environments. Unlike logging (which records events), error tracking focuses specifically on exceptions, crashes, and failures — grouping them by stack trace and root cause to help teams fix the most impactful issues first.

> **Textbook Definition:** Error tracking aggregates failure reports into actionable groups using fingerprints and context, connecting observed exceptions or crashes to affected users, releases, ownership, and remediation status.

An **error tracking system** ingests error reports, deduplicates them via fingerprinting, enriches them with context (user, device, release), and provides workflows for resolution.

## First Principles

Many users can encounter the same defect, while similar messages can have different causes. Collect safe failure context, group related reports, and preserve release/ownership history so the team can act on impact. Grouping is a heuristic; neither a stack hash nor a "resolved" status proves the root cause or the absence of future failures.

## 1. Follow a Report into a Repair Decision

```text
exception/crash → SDK captures safe event → bounded transport → issue grouping
               → impact/release/owner triage → repair → recurrence observation
```

Keep environment, actual release identity, operation, and safe error category. Distinguish expected user validation from unexpected defects. A payment rejection need not be a bug; a programming exception that prevents checkout does. Prioritize affected behavior and user impact rather than paging on every captured event.

Fingerprints can merge repeated reports or split distinct operations. Dynamic order/user IDs in messages/fingerprints create one issue per occurrence. Conversely, a broad custom fingerprint can hide unrelated defects. Verify grouping against representative errors and use source maps/symbols so stack locations refer to the deployed code.

## 2. Initialize a Current SDK Before Application Imports

Current Sentry Node integrations use `Sentry.init` before instrumented application libraries load; legacy `Sentry.Handlers`, constructor integrations, and `startTransaction` are not the template for new setups. A dedicated instrumentation preload followed by application startup makes ordering explicit. Follow the current framework-specific setup for Express, Nest, or another framework rather than combining old middleware APIs.

This local demo uses a custom in-memory transport and a fake DSN that is never contacted. Install a reviewed `@sentry/node`; the capture illustrates scoped safe context, not a live Sentry project or source-map integration.

```javascript
// error-tracking.mjs
import * as Sentry from '@sentry/node';
import assert from 'node:assert/strict';
export const sent = [];
Sentry.init({
  dsn: 'https://public@example.invalid/1',
  release: 'checkout-demo@1', environment: 'local-test',
  defaultIntegrations: false, sendDefaultPii: false,
  transport: () => ({
    send(envelope) { sent.push(envelope); return Promise.resolve({ statusCode: 200 }); },
    flush() { return Promise.resolve(true); },
  }),
  beforeSend(event) {
    // This demo permits no request/user/arbitrary-extra context.
    delete event.request; delete event.user; delete event.extra;
    delete event.breadcrumbs; delete event.contexts;
    return event;
  },
});
Sentry.withScope(scope => {
  scope.setTag('operation', 'checkout');
  scope.setExtra('password', 'must-not-leave');
  scope.setUser({ email: 'synthetic@example.test' });
  Sentry.captureException(new Error('Synthetic checkout defect'));
});
assert.equal(await Sentry.flush(1000), true);
const event = sent.flatMap(([, items]) => items)
  .find(([header]) => header.type === 'event')?.[1];
assert(event);
assert.equal(event.tags.operation, 'checkout');
assert.equal(event.release, 'checkout-demo@1');
assert.equal(event.user, undefined); assert.equal(event.extra, undefined);
assert.equal(event.exception.values[0].value, 'Synthetic checkout defect');
await Sentry.close(1000);
```

The hook deliberately omits useful context to show the boundary clearly. Production needs an allowlisted event contract and tests covering exception messages/stacks, tags, contexts, breadcrumbs, URLs, bodies, automatic integration fields, and other enabled signals. `sendDefaultPii: false` does not remove sensitive data you explicitly attach, and `beforeSend` for error events does not universally scrub logs, traces, profiles, or replays.

Use request-scoped isolation/context rather than mutating shared global user data for concurrent requests. Attach authenticated identity only when necessary and permitted; do not trust a body userId. Avoid duplicate capture when both a custom error handler and framework integration observe the same exception.

## 3. Match Source Maps to the Bytes That Execute

Generate maps for the actual build. Current browser SDK/CLI workflows can inject **debug IDs** that connect emitted JavaScript and maps; then upload the artifact bundle under configured organization/project/auth policy. Injection changes artifacts, so perform it before final integrity hashes/publication and deploy those injected bytes.

```bash
# Template: installed reviewed sentry-cli, built dist/ and authorized project/token.
sentry-cli sourcemaps inject ./dist
sentry-cli sourcemaps upload ./dist
```

The auth token stays in protected CI credentials, never in browser output or committed properties. A browser DSN is a routing identifier, not the secret upload token. Preserve maps privately when their source content should not be public. Verify a synthetic error from the deployed bundle resolves to the correct source; listing an uploaded file does not prove symbolication matches.

Release tags describe what was emitted, while first-seen/regression state depends on captured events and configured issue workflow. A deployment breadcrumb inside one process is not automatically a global deployment record.

## 4. Separate Sampling, Filtering, and Reliability Measurement

`tracesSampleRate` controls trace sampling, not the capture volume of every error. Error sampling and logs/replay/profile options have their own contracts and versions. Filtering all network or ChunkLoad errors can hide a broken release; classify known noise and monitor the removed population.

A captured exception count is not automatically a user error fraction: some requests emit multiple events, some failures emit none, and sampling/transport can omit them. Use eligible-request metrics for the SLI, then investigate matched errors. Mark unresolved issues and recurrence windows honestly; absence of a sampled report does not prove the defect was repaired.

React boundaries observe selected render/lifecycle errors; asynchronous/event-handler/server errors require other capture paths. Session replay can reveal private UI content and has its own masking/access/retention requirements. Enable only deliberate signals with tested privacy boundaries.

## Summary

Error tracking turns selected failure reports into owned repair work. Correct SDK initialization, scoped context, grouping, and source-map identity make reports useful; privacy, sampling, and transport determine what they can establish. An issue status or captured count is not itself proof of recovery.

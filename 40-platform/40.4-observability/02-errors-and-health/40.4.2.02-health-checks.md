# Health Checks

Every pod returns HTTP 200 from /health, yet checkout fails because the database pool is exhausted. The endpoint proves only what it checks; restart, traffic-routing, and user-journey decisions need separate signals.

## Definition

A **health check** observes one stated condition, such as whether an instance has finished starting or can accept new requests. Load balancers, orchestrators, and monitors use the result to decide what to do. A passing check establishes only its chosen condition; a service can answer a health endpoint while a user operation fails.

> **Textbook Definition:** A health check is a bounded observation of a service's ability to satisfy a stated condition, used as an input to traffic routing, restart decisions, or operational monitoring.

Distinguish three control questions: a **liveness check** asks whether the process is stuck in a condition that restarting it can repair; a **readiness check** asks whether it should receive new traffic under the service contract; a **startup check** asks whether initialization has progressed enough to begin ordinary liveness/readiness probing.

## First Principles

An orchestrator needs to decide whether to restart a process and whether to send it new work. Those decisions can diverge: a healthy process may temporarily lack a dependency, and restarting every replica during a shared dependency outage can worsen the incident. Define each check by the action it controls and make the observation bounded.

## How It Works

### 1. Keep Control Signals and User Observations Separate

| Check | Question | Typical control effect |
| --------- | ---------------------------------------------------------- | --------------------------------------------------- |
| Startup | Has initialization reached its stated milestone? | Gates ordinary probes; repeated failure can restart |
| Liveness | Is this process stuck in a condition a restart can repair? | Restart after configured failure policy |
| Readiness | Should this instance receive new work? | Remove from eligible traffic endpoints |
| Synthetic | Can a chosen user path work from this observation point? | Evidence/alert under monitoring policy |

A separate health process may stay alive while the application event loop is stuck. Test the actual serving process or a meaningful local watchdog condition. A TCP accept or always-200 response proves only that narrow observation. Readiness normally cannot promise every user path or dependency is healthy.

A temporary optional-cache outage may permit degraded service; a required primary database outage may block certain requests. If every replica depends on the same unavailable service, making all unready may leave no serving capacity. Choose the policy from application behavior and recovery instead of mechanically checking every dependency.

### 2. Trace a Bounded Outside-In Check

The function below checks a configured URL's status and full body under one deadline. It restricts redirect behavior and clears the timer on every path. It stops after a configured response-body size limit as well as a deadline; the endpoint should return a short contract body.

```javascript
// health-check.mjs
export async function probe({ url, expectedStatus = 200, expectedBody = 'ok', timeoutMs = 1000, maxBytes = 1024 }) {
  if (!Number.isFinite(timeoutMs) || timeoutMs <= 0) throw new RangeError('Invalid timeout');
  if (!Number.isInteger(maxBytes) || maxBytes < 1) throw new RangeError('Invalid size limit');
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);
  const start = performance.now();
  try {
    const response = await fetch(url, { signal: controller.signal, redirect: 'error' });
    const reader = response.body?.getReader();
    let bytes = 0; const chunks = [];
    if (reader) {
      try {
        while (true) {
          const { done, value } = await reader.read();
          if (done) break;
          bytes += value.byteLength;
          if (bytes > maxBytes) { await reader.cancel(); throw new Error('Body too large'); }
          chunks.push(value);
        }
      } finally { reader.releaseLock(); }
    }
    const joined = new Uint8Array(bytes); let offset = 0;
    for (const chunk of chunks) { joined.set(chunk, offset); offset += chunk.byteLength; }
    const body = new TextDecoder().decode(joined);
    return { success: response.status === expectedStatus && body === expectedBody,
      elapsedMs: performance.now() - start };
  } catch {
    return { success: false, elapsedMs: performance.now() - start };
  } finally { clearTimeout(timer); }
}
```

A slow body is still part of the timeout, unlike clearing the timer immediately after headers. A redirect can otherwise turn a failed endpoint into a login-page 200. Do not point this example at a fabricated provider `/health`; use the provider's documented contract or your own endpoint. Restrict configured targets so a user-controlled URL cannot become an internal-network probing service.

Run probes sequentially or with bounded concurrency and avoid starting another round while the prior round is outstanding. Record observation time/location and missing scheduler runs separately from failed endpoint observations. A cached success can grow stale; attach age and define expiry.

### 3. Understand Probe Timing and Restart Effects

Kubernetes startup/liveness/readiness operate under periods, thresholds, timeouts, and lifecycle policy. `periodSeconds × failureThreshold` is a rough design budget, not an exact wall-clock restart promise; initial delays, execution duration, and scheduling also matter. Readiness changes propagate through endpoint/routing state and do not forcibly end all existing connections.

A dependency operation needs a real driver/request timeout. `Promise.race` can stop waiting without cancelling the losing database query. A circuit breaker must receive failure as rejection/result semantics it understands; wrapping a helper that returns `{status: unhealthy}` as a fulfilled value can falsely count it as success.

Detailed application lifecycle and complete probe manifests have canonical homes in [health and graceful shutdown](../../../30-architecture/30.3-infra-patterns/01-liveness-lifecycle/30.3.1.01-health-checks-graceful-shutdown.md) and [Kubernetes probes](../../40.2-kubernetes/04-production-hardening/40.2.4.01-health-checks.md). This chapter explains what their observations establish and how to monitor them.

### 4. Drain Deliberately During Shutdown

Mark draining state so readiness rejects new routing, stop accepting appropriate new work, and allow bounded in-flight completion. The routing change takes time; fixed sleep alone is not a complete drain. `preStop` and application termination consume the termination grace period, so size and observe the whole deadline.

Track HTTP requests, connections, streams/WebSockets, and worker jobs according to their own lifecycle. A deprecated server.connections field cannot stand in for all outstanding work. Close resources after dependent work finishes, force termination at the agreed deadline, and record incomplete operations for safe retry/idempotent recovery.

Docker HEALTHCHECK marks container health; plain Docker does not automatically restart a container merely because it becomes unhealthy. The supervising platform's policy decides the action. Likewise, a failed canary health check does not automatically roll back unless the release controller implements that policy.

### 5. Expose Only the Necessary Diagnostic Detail

Keep public probes small and generic. Dependency hostnames, credentials, stack traces, and raw driver errors belong behind authorized operator access. A separate port still needs network controls; it is not private just because its number differs.

Observe readiness transitions, restart reasons, probe duration, and user SLIs together. A healthy endpoint and a failed authenticated checkout can coexist. Avoid triggering database failover from a single application endpoint without the database system's authority/quorum and fencing protocol.

## Summary

Health checks are bounded observations used by restart, routing, or monitoring policy. Startup, liveness, readiness, and synthetic checks answer different questions. A good policy separates process recovery from shared outages and verifies user behavior beyond a successful health response.

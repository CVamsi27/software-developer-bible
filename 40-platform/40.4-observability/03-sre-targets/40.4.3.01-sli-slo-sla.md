# SLI, SLO & SLA

## Definition

A **Service Level Indicator (SLI)** is a measurement, such as the proportion of successful requests. A **Service Level Objective (SLO)** sets a target for that measurement over a stated period. A **Service Level Agreement (SLA)** is a contractual commitment, which may specify consequences if the target is missed. Site reliability engineering (SRE) uses these distinctions to separate measurement, internal targets, and contractual obligations.

> **Textbook Definition:** A service level indicator (SLI) measures defined service behavior; a service level objective (SLO) sets its target over a period; a service level agreement (SLA) specifies contractual service commitments and consequences.

- **SLI**: a quantitative measure of service behavior (e.g., p99 request latency)
- **SLO**: the target value for an SLI over a window (e.g., 99.9% of eligible requests complete below 200ms over 30 days)
- **SLA**: a contractual agreement with consequences (refund, credit) when the SLO is missed

The **error budget** is the complement of the SLO target — the allowed bad-event fraction under that SLI's contract. A 99.9% request-based SLO permits 0.1% bad eligible requests; it does not imply the same number of downtime minutes.

## First Principles

A service cannot make every operation succeed under every failure, and users value different operations differently. Define the population and what good means, measure that behavior over a window and agree on an achievable target. The remaining allowed bad events create a policy input; contractual commitments may use different definitions and must be read separately.

## Why Do We Need It?

1. **Align engineering with users**: measure what users experience, not what ops monitors
2. **Avoid over-engineering**: 100% reliability is impossible and unaffordable; SLOs define "good enough"
3. **Data-driven reliability decisions**: when to invest in reliability vs. features
4. **Customer trust**: SLAs formalize commitments in vendor contracts
5. **Burn rate alerting**: alert when error budget is consumed too fast, not on individual failures

## How It Works

### The Reliability Hierarchy

```text
SLI: good eligible requests / all eligible requests
  good = completed below the chosen latency threshold
SLO: target good-event ratio over a defined window
  example = 99.9% over 30 days
SLA: agreed service commitment and contractual consequences
  define its own measurement and exclusions explicitly
Request error budget: allowed bad fraction = 1 - SLO
```

For a request-based target, count bad requests rather than converting their fraction into downtime minutes. Elapsed-time availability is a different SLI contract.

### Common SLI Categories

| Category | SLI Example | Good For |
| ---------------- | ----------------------------------------------- | ------------------------------ |
| **Availability** | ratio of defined successful eligible operations | User-facing APIs |
| **Latency** | p99 of request duration < threshold | Performance-critical paths |
| **Throughput** | completed eligible work by a deadline | Batch jobs, queues |
| **Correctness** | ratio of correct responses | ML models, search relevance |
| **Freshness** | age of last successful data update | Dashboards, cache invalidation |
| **Durability** | ratio of data retained over time | Storage systems |

### Calculate the Budget in Its Own Units

Suppose an exercise SLO requires 99.9% of eligible checkout requests to be good over 30 days. For 1,000,000 eligible requests, 1,000 bad requests are allowed. If 600 are bad, 400 remain. A request ratio does not turn into downtime minutes unless the separate time-based measurement contract justifies that conversion.

For **time-based** availability over exactly 30 days (43,200 minutes), allowed downtime is:

| Target | Allowed time |
| ------- | ------------- |
| 99% | 432 minutes |
| 99.9% | 43.2 minutes |
| 99.95% | 21.6 minutes |
| 99.99% | 4.32 minutes |
| 99.999% | 25.92 seconds |

These are arithmetic examples, not appropriate targets for named industries. Reliability cost depends on failure modes, architecture and user value; there is no universal tenfold cost rule for another nine.

## Code Examples

### Trace Request Counts Into Remaining Budget

```javascript
// slo-budget.mjs
import assert from 'node:assert/strict';
function budget({ eligible, bad, target }) {
  if (!Number.isInteger(eligible) || !Number.isInteger(bad) ||
      eligible < 0 || bad < 0 || bad > eligible ||
      !Number.isFinite(target) || target <= 0 || target >= 1) throw new Error('Invalid input');
  if (!eligible) return { observed: null, allowed: 0, remaining: 0 };
  const allowed = eligible * (1 - target);
  return { observed: 1 - bad / eligible, allowed, remaining: allowed - bad };
}
const result = budget({ eligible: 1_000_000, bad: 600, target: 0.999 });
assert(Math.abs(result.allowed - 1000) < 1e-8);
assert(Math.abs(result.remaining - 400) < 1e-8);
assert.equal(budget({ eligible: 0, bad: 0, target: 0.999 }).observed, null);
assert(budget({ eligible: 1000, bad: 2, target: 0.999 }).remaining < 0);
assert.throws(() => budget({ eligible: 1, bad: 2, target: 0.999 }));
```

The example keeps fractional arithmetic; reports must define rounding, missing instrumentation, window selection and count accuracy. Use the actual eligible/good event contract rather than blindly classifying all 2xx as correct and every 4xx as user failure.

### Trace error ratio into a two-window alert

For a request-based 99.9% SLO, the allowed bad-event fraction is `0.001`. This example classifies 5xx responses as bad and assumes the `job="api"` population already represents eligible requests. Product-specific definitions may differ.

```yaml
groups:
  - name: api-slo
    interval: 30s
    rules:
      - record: api:error_ratio:5m
        expr: sum(rate(http_requests_total{job="api",status=~"5[0-9][0-9]"}[5m])) / sum(rate(http_requests_total{job="api"}[5m]))
      - record: api:error_ratio:1h
        expr: sum(rate(http_requests_total{job="api",status=~"5[0-9][0-9]"}[1h])) / sum(rate(http_requests_total{job="api"}[1h]))
      - alert: SLO_HighBurnRate
        expr: api:error_ratio:1h > (14.4 * 0.001) and api:error_ratio:5m > (14.4 * 0.001)
        for: 2m
        labels:
          severity: critical
          slo: api-availability
        annotations:
          summary: "Sustained API error-budget burn"
```

Burn rate divides observed bad-event fraction by the allowed fraction. The one-hour window establishes sustained consumption; the five-minute window checks that the problem is still active. At a constant 14.4-times burn over one hour, a 30-day budget loses about 2%. This is a planning approximation, not a prediction under changing traffic.

Define low-traffic and missing-telemetry policy separately: absence of samples does not establish healthy service. Add the real runbook and routing configuration before treating the example as deployable alerting.

### Measuring p99 Latency in Prometheus

```yaml
# histogram for latency SLI
- record: slo:slo_latency_p99:histogram_quantile_5m
  expr: |
    histogram_quantile(0.99,
      sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m]))
    )
```

## Real-World Use Cases

### 1. Multi-Tier SLOs

The targets below are hypothetical designs requiring explicit population/window and user agreement.

```text
User-Facing Tier:
  SLO: page LCP < 2.5s for 99% of page views
  SLI: defined page-view measurements; CrUX is aggregated field evidence and does not supply every private journey

API Tier:
  SLO: checkout endpoint p99 < 500ms, 99.95% success
  SLI: Prometheus histogram_quantile + success rate

Storage Tier:
  SLO: defined successful retention/readability of eligible stored objects
  SLI: verified retained objects / eligible objects, with window and audit limits
```

### 2. Error Budget Policy

```markdown
## Error Budget Policy (api-service)

If we burn 50% of the monthly budget before day 15:
  - Pause non-critical feature releases
  - Engineering lead reviews top 3 contributors
  - SRE team runs a reliability sprint (2 weeks)

If we burn 100% of the monthly budget:
  - Feature freeze until next budget window
  - Root cause analysis on top 5 incidents
  - Reliability OKRs prioritized over feature OKRs
```

### 3. SLA Tiers in B2B

These are hypothetical commercial terms, not standard contractual entitlements. The actual agreement defines measurement, exclusions, claims and consequences.

```text
Free tier: 99% uptime, no SLA, no refund
Pro tier: 99.9% uptime, 10% credit if violated
Enterprise: 99.95% uptime, 25% credit + dedicated support
```

## Common Mistakes

### 1. Setting SLO = 100%

A finite observation can show 100% success, but an absolute future guarantee leaves no failure budget. Choose targets from user needs and achievable failure/recovery behavior instead of asserting an uncited product-wide target.

### 2. Measuring the Wrong Thing

```text
 Bad: server CPU < 80% (proxy for health)
 Good: 99% of user requests complete in < 500ms (user experience)
```

### 3. Single-Window Burn Rate Alerts

```text
 Bad: alert when 5xx > 0.1% over 5 min (alert on every blip)
 Good: require 1h sustained burn AND 5m ongoing burn
```

### 4. Forgetting to Communicate SLOs

Engineering, product, and leadership must agree on SLOs. Without this, SLOs become an "SRE team's problem" and are ignored when convenient.

### 5. Tracking Only Availability

Latency SLOs are often more important. A service that always returns 200 but takes 30 seconds is unusable.

## Best Practices

1. **Start with availability + latency SLI** — easiest to measure, most user-visible
2. **Choose realistic targets** — what you can sustain, not what sounds impressive
3. **Use multi-window burn-rate alerts** (1h long, 5m short in this example)
4. **Document the error budget policy** — what happens when budget is exhausted?
5. **Review SLOs quarterly** with product and engineering
6. **Tie SLOs to user journeys**, not internal components
7. **Track SLO compliance over rolling 30/90 days** for trend analysis
8. **Publish SLOs internally** — dashboard, monthly review
9. **Pair SLOs with runbooks** — every alert links to a runbook
10. **Measure from the user's perspective** — synthetic + RUM, not just server metrics

## Performance Considerations

| Factor | Impact on SLO |
| -------------------- | --------------------------------------- |
| Tail latency (p99) | Most user-visible pain point |
| Cold starts (Lambda) | Can blow latency SLOs |
| Network jitter | Affects p99 disproportionately |
| DB query time | Common root cause of latency SLO breach |
| Retry storms | Can amplify and extend incidents |

## Summary

- SLI is a metric, SLO is a target, SLA is a contract
- Error budget = 1 − SLO target; burn rate measures consumption
- Multi-window burn-rate alerts (1h + 5m here) require sustained and ongoing budget consumption
- Set targets from the actual user contract and sustainable recovery
- Pair SLOs with runbooks, dashboards, and error budget policies
- Review SLOs quarterly with stakeholders

# Alerting

An error ratio crosses a threshold for ten seconds and then recovers. Paging on every spike trains responders to ignore alerts; useful alerting ties evidence to urgency, ownership, and a response deadline.

## Definition

**Alerting** notifies a person or automated system when behavior needs attention. Prefer alerts about user-visible problems over every internal change. To reduce noise, compare how quickly failures consume the allowed error budget over both short and long time windows; this is called a **multi-window burn-rate alert**. Route each alert to someone who can act on it, with a severity that matches the urgency.

> **Textbook Definition:** Alerting evaluates observed conditions against response criteria and delivers actionable notifications with defined urgency, ownership, and escalation, linking service signals to operational intervention.

Noise trains responders to ignore signals. A useful page identifies a time-critical condition, an owner, and a response; no universal weekly page count establishes quality.

## First Principles

Signals only improve recovery if someone or something can act before the consequence becomes unacceptable. Every notification consumes attention, while false negatives leave damage unobserved. Define urgency, ownership, and evidence, then test the complete detection-to-response path rather than optimizing the number of green dashboards.

## 1. Follow an Alert from Query to Acknowledgment

```text
observations → rule evaluation → pending/firing state → Alertmanager routing
             → grouping/deduplication/silence/inhibition → receiver/escalation
             → acknowledgment/action → recovery verification
```

Prometheus `for` requires a condition to remain true across evaluations before firing. Alertmanager groups/routes notifications; it does not determine whether the query correctly represents user impact. Receiver delivery and escalation need separate credentials, schedules, and verification. A configured route does not prove a responder received the page.

Page for time-critical actionable user failure or imminent destructive conditions such as exhausted storage. Cause signals also support diagnosis and can justify action when the consequence is clear; "never page on CPU" is too absolute. Lower urgency can use tickets or reviews. Define severity from your response contract rather than assuming P0/P1 have universal channel mappings.

## 2. Compose Short and Long Burn Windows Correctly

For a 99.9% request SLO, allowed bad fraction is 0.001. Observed bad fraction 0.0144 is 14.4 times that budget rate. A long window estimates sustained consumption; a paired short window checks ongoing burn.

```text
fast policy:  (1h burn > 14.4 AND 5m burn > 14.4)
slow policy:  (6h burn > 6    AND 30m burn > 6)
notify:       fast policy OR slow policy
```

Do not require the independent fast and slow policies both to pass. Their urgency/routing may differ. Under an approximately steady traffic model, 14.4x for one hour consumes about 2% of a 30-day budget, while 6x for six hours consumes about 5%. Changing traffic changes the actual request-budget contribution; report that assumption.

This rule file assumes correctly populated eligible request counters. The source [SLI/SLO chapter](40.4.3.01-sli-slo-sla.md) owns the measurement contract; missing and low-traffic handling remains an explicit separate policy.

```yaml
# burn-alerts.yml
groups:
  - name: checkout-burn
    rules:
      - record: checkout:bad_ratio:5m
        expr: sum(rate(http_requests_total{job="checkout",status=~"5.."}[5m])) / sum(rate(http_requests_total{job="checkout"}[5m]))
      - record: checkout:bad_ratio:1h
        expr: sum(rate(http_requests_total{job="checkout",status=~"5.."}[1h])) / sum(rate(http_requests_total{job="checkout"}[1h]))
      - record: checkout:bad_ratio:30m
        expr: sum(rate(http_requests_total{job="checkout",status=~"5.."}[30m])) / sum(rate(http_requests_total{job="checkout"}[30m]))
      - record: checkout:bad_ratio:6h
        expr: sum(rate(http_requests_total{job="checkout",status=~"5.."}[6h])) / sum(rate(http_requests_total{job="checkout"}[6h]))
      - alert: CheckoutFastBurn
        expr: checkout:bad_ratio:1h > 0.0144 and checkout:bad_ratio:5m > 0.0144
        for: 2m
        labels: { severity: critical, service: checkout }
        annotations: { summary: "Checkout has sustained and ongoing fast budget burn" }
      - alert: CheckoutSlowBurn
        expr: checkout:bad_ratio:6h > 0.006 and checkout:bad_ratio:30m > 0.006
        for: 5m
        labels: { severity: warning, service: checkout }
        annotations: { summary: "Checkout has sustained and ongoing slow budget burn" }
```

Add real runbook/dashboard links and receiver policy before using this as operational alerting. An absent error series can yield absent ratios; a stopped scraper or no eligible requests must not quietly become healthy. Test counter reset, all-zero traffic, absent labels, and telemetry failure as well as high errors.

## 3. Treat Routing as a Separate Configured Contract

A minimal local Alertmanager config can prove parsing and grouping without sending messages:

```yaml
# alertmanager-local.yml: local validation only, receiver deliberately has no integration
route:
  receiver: local-validation
  group_by: [alertname, service]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
receivers:
  - name: local-validation
```

Production must replace this with actual authorized receivers and escalation settings. Choose a valid default receiver for otherwise-unmatched alerts. Configure credential files/secret injection, receiver timeout/retries, and access; avoid embedding a real webhook or routing key in documentation. Grouping uses label dimensions, not a regex over summary text.

A **silence** temporarily matches alert labels under an owner/reason/expiry; it does not remove the incident or necessarily remove it from SLA accounting. An **inhibition** suppresses notifications for target alerts while a matching source alert is active. Keep dependency/service matching narrow so one failure cannot hide unrelated user impact. Test missing equal-label behavior and expiry.

## 4. Make the Runbook Resolve a Decision

Start with the user symptom, relevant dashboards, and recent artifact/config changes. Define safe checks, authority, and limits for mitigations, plus how to verify restoration and escalate. "Restart the Pod" is not universally safe: it can erase evidence, duplicate work, or amplify a dependency outage. The responder should choose from documented observations rather than execute an unconditional action.

Validate detection delay from scrape/evaluation/window/for/group_wait, then actual receiver delivery, acknowledgment, and escalation. Rehearse a synthetic alert in an agreed test route without paging unrelated users. Track false positives, missed incidents, and unactionable notifications under consistent definitions.

## 5. Keep Release and Infrastructure Signals Honest

Do not suppress latency failures merely because deployment is in progress: releases are precisely when user regressions matter. Use planned maintenance scope/expiry only where policy justifies it, retaining user-facing reliability evidence.

A Pod restart counter detects restarts, not specifically CrashLoopBackOff. State metrics and duration define that condition. Node readiness and failed application probes are different signals. Blackbox probing can cover external DNS/TLS/path behavior, but probe exporter failure and absent targets need their own completeness checks. Separate blackbox module configuration from Prometheus scrape and alert-rule files.

## Summary

Alerting connects valid observations to timely action. Correct paired burn windows, deliberate severity, receiver routing, and accountable suppression keep signals useful. A passed query, parsed config, or delivered page is only one step in the detection-to-recovery path.

# OpenTelemetry (OTel)

## Definition

When checkout calls a payment service, each process sees only its own work. OpenTelemetry gives those processes a common way to describe operations, carry request context and export observations to analysis systems.

> **Textbook Definition:** OpenTelemetry is a vendor-neutral collection of specifications, APIs, SDKs and collection components for generating, propagating, processing and exporting telemetry.

It is not a dashboard or storage engine. Its API is the application-facing contract; an SDK implements collection and export. An exporter sends data to a receiver. A Collector is a separately deployed pipeline that can receive, transform and forward telemetry.

## First Principles

1. A distributed operation crosses process boundaries, so a local identifier alone cannot connect its observations. The caller must pass context and the receiver must use it.
2. Every language and backend otherwise needs a different integration. A common data model and protocol reduce those producer-to-consumer combinations.
3. Observation consumes resources and can fail independently of the application. Buffers, sampling, privacy rules and shutdown therefore belong in the design.

## Why a Common Contract Helps

Changing an exporter often avoids rewriting application spans. Still verify attribute mappings, backend query behavior, supported signals, sampling and retention: compatibility does not make vendors interchangeable in every feature. Auto-instrumentation covers supported libraries; manual spans describe business work that library hooks cannot infer.

## How the Pieces Fit Together

```text
application API calls → SDK → exporter → OTLP receiver
                                         ↓
                           Collector processors → backend
```

**OTLP**, the OpenTelemetry Protocol, transports supported telemetry, commonly over gRPC (default port 4317) or HTTP/protobuf (4318). Signal-specific HTTP endpoints include `/v1/traces`; a base URL and a full trace URL are different configuration contracts. TLS, authentication and network access are separate requirements.

A direct SDK-to-backend path is valid for a simple deployment. Add a Collector when centralized routing, filtering, processing or operational isolation justifies another service. The Collector does not automatically redact personal information or persist data through an outage.

### What each signal describes

| Signal | Meaning | Important boundary |
| ------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Trace | Timed spans for a selected operation, connected through parentage and links | Missing propagation or dropped spans can make it incomplete |
| Metric | Aggregated measurements over dimensions and time | Raw user IDs or URLs multiply series cardinality |
| Log | A discrete event, optionally carrying active trace/span IDs | Correlation requires a compatible logger bridge and active context |
| Profile | Samples of code-level resource use | OTel profiles are Alpha in the primary status page checked October 2026; runtime/exporter support varies |

A span has an operation name, timestamps, kind, attributes, events and status. Precision of a timestamp representation is not accuracy of a machine clock. Use semantic conventions for your instrumentation version, such as `http.request.method` and `http.response.status_code`; do not copy obsolete keys or captured SQL parameters blindly.

Metrics include counters, up/down counters, gauges and histograms. Summary is not a JavaScript metric instrument; the data model can represent legacy summaries. A histogram is the usual choice for a mergeable latency distribution. See the monitoring chapter for bucket and percentile reasoning.

### Request context is different from service identity

A **resource** describes the producer (`service.name`, version and environment). **Span attributes** describe one operation. **Baggage** is a set of values that may cross service boundaries alongside trace context. Baggage is not automatically copied into all spans or logs.

W3C `traceparent` carries a 32-hex-digit trace ID and 16-hex-digit parent span ID. Extraction creates a remote parent; starting the server span creates a new span ID. Supported HTTP instrumentation can perform this automatically when initialized before the instrumented modules load. Verify queue and worker boundaries separately: fan-out, retries and batched messages may need span links rather than a single inherited parent.

Treat incoming baggage as untrusted. A claimed `user_tier=premium` cannot authorize priority or access. Allow-list small non-sensitive values, cap sizes, and avoid forwarding them to unrelated external services. Hashing an identifier does not by itself anonymize it.

## Example: Producer Identity and Parent-Based Sampling

This complete local ES module uses SDK 2.x APIs. Install `@opentelemetry/api`, `@opentelemetry/core`, `@opentelemetry/resources` and `@opentelemetry/sdk-trace-node` together in a disposable Node project. It uses an in-memory exporter; it does not contact a telemetry service.

```javascript
import assert from 'node:assert/strict';
import { ROOT_CONTEXT, trace, TraceFlags } from '@opentelemetry/api';
import { resourceFromAttributes } from '@opentelemetry/resources';
import {
  NodeTracerProvider, SimpleSpanProcessor, InMemorySpanExporter,
  ParentBasedSampler, TraceIdRatioBasedSampler,
} from '@opentelemetry/sdk-trace-node';

const exporter = new InMemorySpanExporter();
const provider = new NodeTracerProvider({
  resource: resourceFromAttributes({
    'service.name': 'checkout',
    'service.version': 'demo',
    'deployment.environment.name': 'local',
  }),
  sampler: new ParentBasedSampler({ root: new TraceIdRatioBasedSampler(0) }),
  spanProcessors: [new SimpleSpanProcessor(exporter)],
});
provider.register();
const tracer = trace.getTracer('checkout-example');
tracer.startSpan('unsampled-local-root', {}, ROOT_CONTEXT).end();
const remote = trace.setSpanContext(ROOT_CONTEXT, {
  traceId: '4bf92f3577b34da6a3ce929d0e0e4736',
  spanId: '00f067aa0ba902b7',
  traceFlags: TraceFlags.SAMPLED,
  isRemote: true,
});
tracer.startSpan('accepted-remote-child', {}, remote).end();
await provider.forceFlush();
const spans = exporter.getFinishedSpans();
assert.equal(spans.length, 1);
assert.equal(spans[0].name, 'accepted-remote-child');
assert.equal(spans[0].parentSpanContext.spanId, '00f067aa0ba902b7');
assert.equal(spans[0].resource.attributes['service.name'], 'checkout');
await provider.shutdown();
```

The root rule drops a new local trace, but the parent-based policy accepts a child of an already sampled remote parent. It does not mean every child is always kept: unsampled parents normally remain unsampled. The tracing chapter owns the full active-context, exception and propagation example.

## Decide What Sampling Can Promise

**Head sampling** decides when a span starts. It bounds work early but cannot know that a request will later fail. **Tail sampling** waits for received spans and chooses using their observed outcome. It can retain qualifying errors only among traces it actually received and processed within its decision/buffer policy.

If head sampling sends only 1% of traces, downstream tail sampling cannot recover errors from the missing 99%. Choose an acceptable loss tradeoff, or send the needed population to a suitably sized tail pipeline. A sampled bit is not an authorization decision; protect against untrusted clients inflating collection costs.

Collector tail sampling also needs trace affinity: spans of one trace must reach the same decision maker. Simply adding two randomly balanced replicas can split the trace. Plan late spans, maximum buffered traces, decision caches, load balancing and failure recovery. Queues and retries have finite capacity; a persistent queue helps only within its configured storage and recovery bounds.

A typical pipeline orders memory protection before expensive processing and batches before export. Components must exist in the chosen Collector distribution; configuration for contrib-only processors does not work in every binary. Use the current `debug` exporter for local inspection rather than retired `logging` examples. Do not expose unauthenticated debug output with production payloads.

## Real-World Decisions

For a slow checkout, first confirm an eligible-user latency symptom. Find a trace for that cohort, inspect its critical path, and correlate the service version with a profile. Parallel child spans cannot simply be added to get end-to-end latency. If trace coverage is absent, inspect propagation and sampling before concluding that a service did no work.

For a backend migration, send a bounded pilot population to both destinations. Compare retained traces, attributes, histogram aggregation and costs. Keep the old export path available until the new operational queries and alert policies work.

For browsers, use the browser SDK/context support and propagate only to approved origins. Cross-origin trace headers need an appropriate CORS contract. End a manual span in `finally`, including fetch rejection and body parsing; a header alone does not prove full end-to-end coverage.

## Mistakes and Best Practices

- Initialize instrumentation before supported modules load; verify native `fetch`, databases and queues against their specific instrumentation packages.
- Set stable producer identity and bounded span names. Keep raw customer IDs, query strings and credentials out of telemetry by default.
- Bound export queues and timeouts; observe drops and exporter errors. Application shutdown must allow a finite flush deadline.
- Test meaningful spans with an in-memory exporter. Disabling all telemetry in tests misses propagation regressions.
- Measure overhead on representative traffic, payload sizes and instrumentation. There is no universal 1% sampling rule, millisecond overhead or storage price.

## Summary

OpenTelemetry standardizes the telemetry pipeline while leaving storage and analysis to a backend. Connect producer identity, request context and instrumentation deliberately. Sampling and buffering determine what evidence survives; privacy, backend compatibility and the pipeline's own health require explicit verification.

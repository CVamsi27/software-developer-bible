# OpenTelemetry (OTel)

> **The single vendor-neutral standard for observability.** Traces, metrics, logs — one SDK, one collector, one data model. Once you instrument with OpenTelemetry, you can ship to Datadog, Honeycomb, Tempo, Jaeger, New Relic, Lightstep, or self-hosted, **without re-instrumenting your code**. This file covers the data model (signals, spans, attributes, baggage), the architecture (SDK + collector + exporters), the propagation mechanism (W3C Trace Context), the sampling strategies, and the production-grade patterns. Every senior backend interview expects you to know what OTel is, when it matters, and how to debug with it.

## TL;DR

- **OpenTelemetry (OTel)** = vendor-neutral open-source observability framework. Successor to OpenTracing and OpenCensus. CNCF graduated project.
- **Three signals**: **traces** (request flows), **metrics** (numeric time series), **logs** (discrete events). The new "fourth" is **profiles** (in beta).
- **Architecture**: **Instrumentation** (auto + manual) → **SDK** (in-process) → **OTLP** (wire protocol) → **Collector** (pipeline) → **Backend** (Jaeger, Tempo, Datadog, etc.).
- **W3C Trace Context** — the propagation mechanism. `traceparent` and `tracestate` HTTP headers carry the trace across services.
- **Sampling** is the #1 production concern. `head-based` (decide at start) vs `tail-based` (decide after, with full context). Most teams use head-based; advanced teams use tail-based.
- **Baggage** — key/value pairs that travel with the trace across services. Used to pass `tenant_id`, `request_priority`, `feature_flags` without changing every function signature.
- **In interviews: name the signals, name the propagation mechanism, name the sampling strategy, name the backend-agnostic benefit.**

---

## Why it matters

Pre-OTel (and even now, for the holdouts), observability was vendor-locked:

```text
Old world:
  App → Datadog agent → Datadog backend (locked to Datadog)
  App → Jaeger client → Jaeger backend (locked to Jaeger)
  App → New Relic agent → New Relic (locked to New Relic)
```

**Every vendor had its own SDK, its own agent, its own data model.** Switching backends meant re-instrumenting every service. The "vendor lock-in" tax on observability was real.

OpenTelemetry ends this:

```text
OTel world:
  App → OTel SDK → OTLP → OTel Collector → [Datadog OR Tempo OR Jaeger OR Honeycomb OR ...]
                                                  (switch any time)
```

The SDK is one. The wire protocol is one (OTLP). The backend is your choice — change it by changing the exporter config, no code change.

OTel is the **de facto standard**. Every major observability vendor supports it. The CNCF graduated the project in 2025. New Relic, Datadog, Honeycomb, and Grafana all have first-class OTel support. If you're not using OTel in 2026, you're paying a vendor tax.

## The Three Signals (and a Fourth)

### Traces

A **trace** is the journey of a single request through a distributed system. It's a directed acyclic graph (DAG) of **spans**. Each span is a timed operation with a name, start/end, attributes, events, and a parent.

```text
Trace: GET /api/orders/123
├── Span: api-gateway (350ms)
│ ├── Span: auth-service (20ms)
│ └── Span: order-service (300ms)
│ ├── Span: db.query: SELECT * FROM orders (180ms)
│ └── Span: cache.get: order:123 (5ms)
└── Span: analytics-event (10ms)
```

A span has:
- **Name**: `db.query`, `http.GET /users`, custom
- **Start / end time** (with sub-microsecond precision)
- **Attributes**: key/value metadata (`http.status_code = 200`, `db.statement = "SELECT..."`)
- **Events**: timestamped log entries within a span (`exception`, `log`)
- **Status**: `unset` / `ok` / `error`
- **Span kind**: `client` / `server` / `producer` / `consumer` / `internal`
- **Parent span ID**: the parent in the DAG

### Metrics

A **metric** is a numeric time series. OTel supports:
- **Counter** — monotonically increasing value (requests, errors, bytes sent)
- **UpDownCounter** — can go up or down (active connections, queue depth)
- **Gauge** — point-in-time value (CPU, memory, temperature)
- **Histogram** — distribution of values (request duration, response size)
- **Summary** — pre-computed quantiles (deprecated; use Histogram + backend aggregation)

```typescript
const requestCounter = meter.createCounter("http_requests_total", {
  description: "Total HTTP requests",
});
requestCounter.add(1, { method: "GET", path: "/api/orders", status: 200 });

const requestDuration = meter.createHistogram("http_request_duration_ms", {
  description: "HTTP request duration",
  unit: "ms",
});
requestDuration.record(42, { method: "GET", path: "/api/orders" });
```

### Logs

A **log** is a discrete event with structured fields. OTel doesn't reinvent logging — it provides a **log signal** that integrates with the trace context.

```typescript
logger.emit({
  severityText: "INFO",
  body: "Order shipped",
  attributes: {
    order_id: "ord_42",
    user_id: "u_7",
    carrier: "UPS",
  },
});
// The SDK automatically attaches the current trace_id and span_id
// to the log. Click on the log in the backend → jump to the trace.
```

The killer feature: **a log line knows which trace it belongs to**. Click a log, see the full request flow.

### Profiles (beta)

A **profile** is a sampled set of stack traces over time, correlated with traces. The fourth signal. OTel is standardizing this as of 2025-2026; expect broader backend support in 2026-2027.

## Architecture: The OTel Pipeline

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ Instrumentation│→ │ SDK        │→│ OTLP       │ │ Collector  │ │         │
│ (auto+manual)  │  │ (in-process│ │ (gRPC/HTTP)│ │ (pipeline) │ │ (Tempo, │
│                │  │            │ │            │ │            │ │         │
│                │  │            │ │            │ │            │ │         │
└──────────────────────────────────────────────────────────────────────────┘
```

### 1. Instrumentation

**Auto-instrumentation** (zero-code):
- HTTP servers (Express, Fastify, NestJS)
- HTTP clients (fetch, axios, undici)
- Databases (pg, mysql2, prisma, typeorm, mongoose)
- Message queues (kafkajs, amqplib, bullmq)
- Caches (ioredis, memcached)
- Frameworks (Next.js, React Server Components)

```typescript
// Just import the auto-instrumentation at the top of your entry point
import { NodeSDK } from "@opentelemetry/sdk-node";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";

const sdk = new NodeSDK({
  serviceName: "orders-service",
  traceExporter: new OTLPTraceExporter({ url: "http://otel-collector:4318" }),
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

**Manual instrumentation** (when auto doesn't cover it):
```typescript
import { trace, SpanStatusCode } from "@opentelemetry/api";

const tracer = trace.getTracer("orders-service");

async function shipOrder(orderId: string) {
  return tracer.startActiveSpan("shipOrder", async (span) => {
    span.setAttribute("order.id", orderId);

    try {
      const result = await shippingService.ship(orderId);
      span.setStatus({ code: SpanStatusCode.OK });
      return result;
    } catch (err) {
      span.recordException(err as Error);
      span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message });
      throw err;
    } finally {
      span.end();
    }
  });
}
```

### 2. SDK (in-process)

The SDK lives in your app. It:
- Buffers spans, metrics, logs
- Batches and exports via OTLP
- Handles sampling decisions
- Propagates context (W3C Trace Context)

```typescript
// Configure sampling
const sdk = new NodeSDK({
  serviceName: "orders-service",
  sampler: new ParentBasedTraceIdRatioSampler(0.1), // 10% of root spans, 100% of children
  traceExporter: new OTLPTraceExporter({ url: "http://otel-collector:4318" }),
});
```

### 3. OTLP (wire protocol)

**OTLP** = OpenTelemetry Protocol. Wire format for traces, metrics, logs. Two transports:
- **gRPC** (port 4317) — binary, faster, more efficient
- **HTTP/protobuf** (port 4318) — easier to set up, no gRPC dependency

Every OTel-compatible backend accepts OTLP. **Use OTLP**, not vendor-specific protocols.

### 4. Collector

The **OTel Collector** is a vendor-neutral service that:
- Receives OTLP from your apps
- Processes (sampling, enrichment, filtering)
- Exports to one or many backends

```yaml
# otel-collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 1024
  memory_limiter:
    check_interval: 1s
    limit_percentage: 80
  tail_sampling:
    decision_wait: 10s
    num_traces: 50000
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-traces
        type: latency
        latency: { threshold_ms: 1000 }

exporters:
  prometheusremotewrite:
    endpoint: http://prometheus:9090/api/v1/write
  otlp/tempo:
    endpoint: tempo:4317
    tls: { insecure: true }
  logging:
    verbosity: basic

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, tail_sampling, batch]
      exporters: [otlp/tempo, logging]
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [prometheusremotewrite]
```

The collector is where the magic happens: **tail-based sampling**, **PII redaction**, **attribute enrichment**, **multi-backend export**. Always run a collector; don't export directly from your app to the backend.

### 5. Backend

Your choice:
- **Tempo** (Grafana stack, OSS, cheap)
- **Jaeger** (OSS, classic)
- **Datadog** (commercial, popular)
- **Honeycomb** (commercial, observability-focused)
- **Lightstep** (commercial, distributed tracing)
- **New Relic** (commercial, full APM)

Switching is a collector-config change. No app change. **This is the entire point of OTel.**

## W3C Trace Context: Cross-Service Propagation

The killer feature of OTel. The `traceparent` HTTP header carries the trace context across services.

```http
GET /api/orders/123 HTTP/1.1
Host: orders-service.internal
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
tracestate: yourcompany=04f067aa0ba902b7
```

Format: `00-<trace-id>-<parent-span-id>-<flags>`
- `00` — version
- `4bf92f3577b34da6a3ce929d0e0e4736` — 16-byte trace ID (32 hex chars)
- `00f067aa0ba902b7` — 8-byte parent span ID
- `01` — flags (sampled)

The receiving service extracts the trace context, creates a child span with the parent ID, and the trace is joined across services.

**In Node.js, this is automatic with the HTTP auto-instrumentation.** You don't have to write any code. The auto-instrumentation:
- On outgoing requests: injects `traceparent` header.
- On incoming requests: extracts `traceparent`, sets up the parent context.

**Across message queues (Kafka, RabbitMQ, SQS):** inject the `traceparent` into message headers, extract on the consumer side. Auto-instrumentation for kafkajs/amqplib does this.

## Sampling: The #1 Production Decision

Naive: "let's trace 100% of requests". Cost: 100% of every request's overhead (1-5ms), 100% storage (~$0.10/GB-month at scale, so 1M requests × 50 spans × 1KB = 50GB/day = $50/day just for traces).

Smart: **sample**.

### Head-based sampling (decide at start)

When the root span is created, decide whether to sample. Default propagates the decision to children.

```typescript
new ParentBasedTraceIdRatioSampler(0.1)
// 10% of root spans kept; 100% of their children kept
```

Pros: simple, cheap, predictable.
Cons: you miss slow traces that happen to be in the 90% you didn't sample.

### Tail-based sampling (decide after, with full context)

The collector holds the entire trace in memory, then decides. Common policies:
- **Keep all errors** (status code = error)
- **Keep all slow traces** (e.g. > 1 second)
- **Keep 10% of normal traces**

```yaml
processors:
  tail_sampling:
    decision_wait: 10s # wait this long for all spans to arrive
    num_traces: 50000 # max in-memory traces
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: sample-10pct
        type: probabilistic
        probabilistic: { sampling_percentage: 10 }
```

Pros: keep all the interesting traces, sample the boring ones.
Cons: needs more memory, more complex, the collector becomes a single point of failure (mitigate with HA collector).

### The production pattern

**Head-based at the SDK** (cheap, predictable, ~1% sample rate). **Tail-based at the collector** (keep all errors + slow, sample the rest). Most teams land on this.

## Baggage: Cross-Service Key/Value

`Baggage` is a key/value store that travels with the trace context across services. Use it for non-PII metadata that every service in the trace should know.

```typescript
import { propagation, context, trace } from "@opentelemetry/api";

// Service A: set baggage
const baggage = propagation.createBaggage({
  tenant_id: { value: "tenant_42" },
  feature_flags: { value: "new-checkout,fast-search" },
});
const ctx = propagation.setBaggage(context.active(), baggage);

// Service B (downstream): read baggage
const activeBaggage = propagation.getBaggage(context.active());
const tenantId = activeBaggage?.getEntry("tenant_id")?.value;
```

**W3C Baggage header** (`baggage: tenant_id=tenant_42, feature_flags=new-checkout`) is the wire format.

**Use cases:**
- `tenant_id` — for multi-tenant systems, every log/span should carry it.
- `feature_flags` — know which A/B test variant the user is in.
- `request_priority` — high-priority requests get more resources.
- `user_tier` — for cost attribution.

**Do not put in baggage:** PII (no user_id, no email, no IP). Baggage is logged everywhere — it leaks.

## Resource Attributes: The Service Identity

Every span and metric is associated with a **resource** — the entity that produced it.

```typescript
import { Resource } from "@opentelemetry/resources";
import { SemanticResourceAttributes } from "@opentelemetry/semantic-conventions";

const resource = new Resource({
  [SemanticResourceAttributes.SERVICE_NAME]: "orders-service",
  [SemanticResourceAttributes.SERVICE_VERSION]: "1.2.3",
  [SemanticResourceAttributes.DEPLOYMENT_ENVIRONMENT]: "production",
  [SemanticResourceAttributes.SERVICE_NAMESPACE]: "checkout",
  [SemanticResourceAttributes.HOST_NAME]: "orders-pod-abc123",
});
```

The backend uses these to filter, group, and slice. `service.name` is the most important attribute in OTel — it's how you find your service in the UI.

**Always set:** `service.name`, `service.version`, `deployment.environment`. Without these, traces are useless at scale.

## Code Examples

### Node.js — full setup with auto-instrumentation

```typescript
// tracing.ts — must be loaded BEFORE the app
import { NodeSDK } from "@opentelemetry/sdk-node";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";
import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-http";
import { OTLPMetricExporter } from "@opentelemetry/exporter-metrics-otlp-http";
import { Resource } from "@opentelemetry/resources";
import { SemanticResourceAttributes } from "@opentelemetry/semantic-conventions";
import {
  ConsoleSpanExporter,
  BatchSpanProcessor,
  ParentBasedTraceIdRatioSampler,
} from "@opentelemetry/sdk-trace-node";

const sdk = new NodeSDK({
  resource: new Resource({
    [SemanticResourceAttributes.SERVICE_NAME]: "orders-service",
    [SemanticResourceAttributes.SERVICE_VERSION]: process.env.GIT_SHA || "dev",
    [SemanticResourceAttributes.DEPLOYMENT_ENVIRONMENT]: process.env.NODE_ENV || "development",
  }),

  sampler: new ParentBasedTraceIdRatioSampler(
    parseFloat(process.env.OTEL_SAMPLE_RATIO || "0.1"),
  ),

  spanProcessor: new BatchSpanProcessor(new OTLPTraceExporter({
    url: process.env.OTEL_EXPORTER_OTLP_TRACES_ENDPOINT || "http://localhost:4318/v1/traces",
  })),

  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({
      url: process.env.OTEL_EXPORTER_OTLP_METRICS_ENDPOINT || "http://localhost:4318/v1/metrics",
    }),
    exportIntervalMillis: 10_000,
  }),

  instrumentations: [
    getNodeAutoInstrumentations({
      "@opentelemetry/instrumentation-fs": { enabled: false }, // too noisy
    }),
  ],
});

sdk.start();
process.on("SIGTERM", () => sdk.shutdown().catch(console.error));
```

### Manual span with attributes and events

```typescript
import { trace, SpanStatusCode, SpanKind } from "@opentelemetry/api";

const tracer = trace.getTracer("orders-service");

async function processOrder(orderId: string) {
  return tracer.startActiveSpan(
    "process-order",
    {
      kind: SpanKind.INTERNAL,
      attributes: {
        "order.id": orderId,
        "app.queue_depth": queueDepth(),
      },
    },
    async (span) => {
      try {
        const order = await db.getOrder(orderId);
        span.setAttribute("order.amount", order.total);
        span.setAttribute("order.item_count", order.items.length);

        if (order.total > 10_000) {
          span.addEvent("high_value_order", { amount: order.total });
        }

        await chargePayment(order);
        await reserveInventory(order);

        span.setStatus({ code: SpanStatusCode.OK });
        return order;
      } catch (err) {
        span.recordException(err as Error);
        span.setStatus({
          code: SpanStatusCode.ERROR,
          message: (err as Error).message,
        });
        throw err;
      } finally {
        span.end();
      }
    },
  );
}
```

### Custom metric

const meter = metrics.getMeter("orders-service");

  description: "Number of orders processed",

### Browser — manual span with trace context propagation

```typescript
import { trace, context, propagation } from "@opentelemetry/api";
import { W3CTraceContextPropagator } from "@opentelemetry/core";

propagation.setGlobalPropagator(new W3CTraceContextPropagator());

const tracer = trace.getTracer("web-app");

async function fetchUser(id: string) {
  return tracer.startActiveSpan("fetchUser", async (span) => {
    const headers: Record<string, string> = {};
    propagation.inject(context.active(), headers);

    const res = await fetch(`/api/users/${id}`, { headers });
    span.setAttribute("http.status_code", res.status);
    span.end();
    return res.json();
  });
}
```

The browser sends the `traceparent` header. The backend extracts it, and the frontend's span is a parent of the backend's span. **Full E2E visibility.**

## Common Mistakes

- **Not setting `service.name`.** Every span looks the same in the UI. Useless.
- **Tracing 100% of requests in production.** Cost melts. Sample 1-10% head-based; tail-sample for errors and slow.
- **Auto-instrumenting `fs` in Node.js.** Too noisy. Every file read becomes a span. Disable it.
- **Not using W3C Trace Context.** If you propagate a custom header, you lose interop with other OTel-instrumented services. Use the standard.
- **Putting PII in attributes.** Spans are logged. Don't put user email, IP, or name. Use a hash or omit.
- **Not using a collector.** Exporting directly to the backend means no tail-sampling, no PII redaction, no multi-backend. Always use a collector.
- **Single point of failure collector.** Run at least 2 collector replicas. Or use a managed collector (Grafana Agent, Datadog Agent, etc.).
- **Sampling at the wrong layer.** Tail-based at the SDK doesn't work (you don't have the full trace yet). Use head-based at the SDK + tail-based at the collector.
- **Storing traces forever.** Set a retention policy. Tempo, Jaeger, Datadog all have TTL. 7-30 days is typical.
- **Tracing in tests.** Adds noise and overhead. Use a no-op exporter in tests.
- **Forgetting the SDK shutdown.** On SIGTERM, the SDK may have buffered spans. Call `sdk.shutdown()` to flush.

## Best Practices

1. **Always set `service.name`, `service.version`, `deployment.environment`.** Without these, traces are ungroupable.
2. **Run a Collector in production.** Tail-based sampling + multi-backend export.
3. **Sample aggressively.** 1-10% head-based is plenty. Tail-sample to keep all errors and slow traces.
4. **Use W3C Trace Context.** Standard header. Interop with every other OTel-instrumented service.
5. **Use resource attributes consistently.** `service.namespace` for the product, `service.name` for the service.
6. **Propagate `traceparent` across queues.** Kafka, RabbitMQ, SQS — inject the header, extract on the consumer side. Auto-instrumentation does this.
7. **Add baggage for tenant_id, feature_flags, request_priority.** Non-PII metadata that should follow the trace.
8. **Disable noisy auto-instrumentations.** `fs`, `dns` — disable or filter.
9. **Use a span name schema.** `http.method route` (`http.GET /api/orders/:id`), `db.statement table` (`db.query orders`). Pre-aggregate at the backend.
10. **Set up a span name cardinality budget.** No `span.name = user_email_42` (cardinality explosion). Use attributes for high-cardinality data.
11. **Test with a no-op exporter.** In unit tests, `trace.setTracerProvider(new NoopTracerProvider())`.
12. **Monitor the OTel pipeline itself.** Export failures, dropped spans, collector lag. OTel can become a silent failure.

## Performance Considerations

| Concern                     | OTel SDK                    | OTel Collector                  |
| --------------------------- | --------------------------- | ------------------------------- |
| Per-request overhead        | 1-5ms (auto-instrumented)   | N/A                             |
| Memory per process          | ~10-50 MB                   | ~100-500 MB (for tail-sampling) |
| Throughput                  | 10K-100K spans/sec/instance | 100K+ spans/sec/instance        |
| Network                     | OTLP to collector (gRPC)    | OTLP to backend (gRPC)          |
| Cost (storage)              | $0.10/GB-month at backend   | N/A                             |
| Tail-sampling decision wait | N/A                         | 5-30s (the wait is the cost)    |

**The 1% rule:** keep at most 1% of traces in production. Tail-sample to keep all errors and slow traces; the rest is sampled.

## Summary

- **OpenTelemetry** is the vendor-neutral observability framework. Traces + metrics + logs (and profiles in beta).
- **Architecture**: Instrumentation → SDK → OTLP → Collector → Backend. The collector is where production features live (tail-sampling, enrichment, multi-backend).
- **W3C Trace Context** propagates traces across services. `traceparent` header.
- **Sampling is the #1 decision**: head-based at SDK (1-10%), tail-based at collector (errors + slow).
- **Baggage** carries tenant_id, feature_flags across services. No PII.
- **In interviews: name the signals, name the propagation, name the sampling, name the backend-agnostic benefit.**

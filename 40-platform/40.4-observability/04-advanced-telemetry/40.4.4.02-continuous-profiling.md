# Continuous Profiling

> **Always-on production profiling at ~1% overhead.** Where metrics tell you CPU went up and traces tell you which endpoint got slow, profiles tell you *which functions burned the time or allocated the bytes* — sampled continuously, stored with labels like any other telemetry, and diffable across releases. This file covers what continuous profiling adds over ad-hoc `pprof`, how Pyroscope/Parca ingest and store folded stacks, the profile types worth collecting (CPU, heap, allocations), regression hunting via profile diffing, overhead budgets, and the trace-to-profile correlation (span profiles) that closes the observability loop.

## Definition

**Continuous profiling** regularly samples what running code is doing in production. It stores those samples with timestamps and labels so you can later ask which functions used CPU time or memory during an incident. Profiles add another observability signal alongside logs, metrics, and traces. You can investigate a past period without waiting to start a profiler after the problem appears.

> **Textbook Definition:** Continuous profiling repeatedly samples runtime execution or allocation behavior and retains time-indexed profiles, enabling analysis of resource use during both normal operation and past incidents.

Key concepts:

- **Sampling profiler**: interrupts execution at a fixed frequency (e.g., 100 Hz), records the stack, resumes. Statistical, not exhaustive — accuracy comes from volume.
- **Folded stacks**: compressed representation (`funcA;funcB;funcC count`) that backends aggregate into flamegraphs/icicle charts.
- **Labels**: service name, version/git SHA, pod, zone — attached to every sample so profiles slice like metrics do.
- **Profile diff**: aggregation of one time window minus another, highlighting functions whose share of resource use grew.
- **Span profiles**: profiler context tied to active trace spans, enabling span -> flamegraph navigation.

---

## First Principles

Continuous profiling answers "where does CPU/memory go *in production*," always:

1. **Profiles are aggregated stack samples with negligible overhead** — low enough to run always, which converts profiling from incident archaeology to a baseline signal: you see the regression the day it ships, not the month it hurts.
2. **Flamegraphs over time are the analysis**: compare this week's CPU profile to last's — the diff *is* the answer (new cache-miss path, new allocation site).  (→ 20.1.4.02's Node-specific view.)
3. **It closes the loop from SLO burn to code line**: metrics say p99 regressed; the profile says which function — the only telemetry that lands at commit granularity.

## Why It Matters

1. **Metrics raise the alarm; profiles name the culprit.** "checkout-service p99 up 40%" ends at the dashboard without a flamegraph showing `json.Marshal` eating 60% of CPU.
2. **Regressions hide below alert thresholds.** A 15% CPU-per-request increase may not page anyone, but a profile diff against last week's build makes it obvious — before it compounds into an SLO breach.
3. **Reproduction is expensive; sampling is cheap.** Load-testing a memory leak locally can take days; alloc_space trends from production pinpoint the leak's owner in hours.
4. **Capacity planning gets empirical.** Continuous CPU/heap profiles reveal right-sizing opportunities worth real money at fleet scale (fewer replicas for the same p99).
5. **It completes OTel's four signals.** Traces answer "where in the request", logs answer "what happened", metrics answer "how much", profiles answer "in which code".

## How It Works

### 1. Architecture

```text
┌──────────────────────────────┐
│ POD: orders-service          │
│  ┌────────────────────────┐  │  samples (~100 Hz)
│  │ APP                       │  ├───────────────► folded stacks
│  │  + profiler agent      │  │                  {service, version,
│  └────────────────────────┘  │                   zone} labels
└──────────────────────────────┘
        │ push / agent scrapes pprof endpoints
        ▼
┌──────────────────────────────────────────────┐
│ PROFILE BACKEND (Pyroscope / Parca)          │
│  • aggregates trees per label set            │
│  • stores time-bucketed profiles             │
│  • serves flamegraph + diff queries          │
└──────────────────┬───────────────────────────┘
                   ▼
        UI: single flamegraph | diff view |
            span-profile link from Tempo trace
```

### 2. What each profile type answers

| Type | Mechanism | Answers |
| ------------------ | --------------------------------- | ------------------------------------- |
| CPU time | Sample on-CPU stacks at fixed Hz | Which functions burn compute? |
| Wall time | Include off-CPU waits (IO, locks) | Why is this slow despite idle CPU? |
| Heap in-use | Sample live allocations | What holds memory right now? |
| Alloc space/rate | Sample at allocation events | What churns GC pressure? Leak source? |
| Mutex/block | Instrument contention points | Which lock serializes requests? |
| Goroutines/threads | Dump counts | Leak of concurrent tasks? |

Start with CPU + heap; add allocation profiling wherever GC dominates (high-throughput Node/Go services).

### 3. Diffing: finding regressions

```text
DIFF: release v1.8.0 window vs v1.7.3 window (same traffic class)
═══════════════════════════════════════════════════════
net/http.(*Server).serve           ▓▓▓▓▓▓▓  (unchanged)
encoding/json.Marshal              ██████ +38%   <-- suspect
github.com/acme/api.enrichOrder     ████ +22%    <-- calls json
runtime.mallocgc                    ██ +19%      <- downstream effect
```

Reading order: start at the largest red leaf, walk up to your own code, confirm the commit range between versions touches it. A diff that shows only runtime frames growing usually means allocation churn introduced upstream of the hot loop.

### 4. Trace integration (span profiles)

With Grafana's profiles-in-traces integration, the SDK wraps span boundaries: while a span is active, the profiler attributes its samples to that span ID. Tempo then renders a "Profiles" tab on the span — click a 900 ms `process-order` span and see exactly which functions spent the time, no reproduction needed.

### 5. Overhead mechanics

- **CPU profiling**: timer-based interrupt at 100 Hz. At typical request latencies this samples each request a handful of times; cost scales with cores, not traffic.
- **Heap/allocation profiling**: samples every ~512 KiB of allocation (tunable); cost is a hash insert per sampled alloc — low single-digit % of allocator throughput.
- **eBPF profilers** (Parca, Grafana Alloy profiles, Pixie): read stacks from the kernel for ALL processes on the node — zero application change, slightly higher constant node cost.

## Code Examples

### Node.js service pushing profiles to Pyroscope

```typescript
// src/profiling.ts — import FIRST, before the app starts
import Pyroscope from "@pyroscope/nodejs";

export function startProfiling(): void {
  if (process.env.PROFILING_ENABLED !== "true") return;

  Pyroscope.init({
    appName: process.env.SERVICE_NAME || "orders-service",
    // Version label makes release-over-release diffs possible:
    tags: {
      version: process.env.GIT_SHA || "dev",
      zone: process.env.ZONE || "eu-central-1a",
    },
    serverAddress: process.env.PYROSCOPE_URL || "http://pyroscope:4040",
    // Wall-clock + CPU + heap; tune interval to your overhead budget:
    samplingIntervalMs: 10, // ~100 Hz
  });

  Pyroscope.start();

  const shutdown = async () => {
    await Pyroscope.stop();
  };
  process.on("SIGTERM", shutdown);
  process.on("SIGINT", shutdown);
}
```

### Go service with span-level profiling

```go
// main.go — Pyroscope Go SDK with span profiles (traces <-> profiles)
package main

import (
	"net/http"
	"os"

	"github.com/grafana/pyroscope-go"
)

func main() {
	pyroscope.Start(pyroscope.Config{
		ApplicationName: "payments-api",
		ServerAddress:   envOr("PYROSCOPE_URL", "http://pyroscope:4040"),
		Tags:            map[string]string{"version": envOr("GIT_SHA", "dev")},
		ProfileTypes: []pyroscope.ProfileType{
			pyroscope.ProfileCPU,
			pyroscope.ProfileAllocObjects,
			pyroscope.ProfileAllocSpace,
			pyroscope.ProfileInuseSpace,
		},
	})

	mux := http.NewServeMux()
	mux.HandleFunc("/charge", handleCharge)
	_ = http.ListenAndServe(":8080", mux)
}

func handleCharge(w http.ResponseWriter, r *http.Request) {
	// With the OTel bridge registered, samples inside this handler
	// attach to the current span -> visible as a span profile in Tempo.
	ctx := r.Context()
	if err := chargeCard(ctx, r); err != nil {
		http.Error(w, "charge failed", http.StatusBadGateway)
	}
	w.WriteHeader(http.StatusOK)
}

func envOr(key, fallback string) string {
	if v, ok := os.LookupEnv(key); ok && v != "" {
		return v
	}
	return fallback
}
```

### Ad-hoc fallback: expose pprof, scrape on demand

```typescript
// Even with continuous profiling on, keep pprof endpoints for deep dives.
import pprof from "pprof";

export function mountDebugRoutes(app: Express): void {
  app.get("/debug/pprof/cpu", async (_req, res) => {
    const buf = await pprof.time.profile({ durationSecs: 10 });
    res.setHeader("content-type", "application/protobuf");
    res.send(buf.toBuffer());
  });
  app.get("/debug/pprof/heap", (_req, res) => {
    const buf = pprof.heap.profile();
    res.setHeader("content-type", "application/protobuf");
    res.send(buf.toBuffer());
  });
}
```

### Diffing two windows from the CLI

```bash
# Fetch profiles for the pre-release and post-release hour from Pyroscope
curl -s "http://pyroscope:4040/pyroscope/render-diff" \
  --data 'serviceName=orders-service&from=now-48h&until=now-47h' > old.pprof

curl -s "http://pyroscope:4040/pyroscope/render-diff" \
  --data 'serviceName=orders-service&from=now-1h&until=now' > new.pprof

# Or pull raw pprof endpoints and let go tool pprof show the delta
go tool pprof -top -diff_base=old.pprof new.pprof
# flat  diff   function
# +0.61s       encoding/json.Marshal      <- regression lives here
```

### Agent-side scraping (no SDK in the app)

```text
# Grafana Alloy (river syntax excerpt) — scrape pprof targets node-wide

  ]
  forward_to = [pyroscope.write.default.receiver]
  scrape_interval = "15s"
  scheme = "http"
}

pyroscope.write "default" {
  endpoint { url = "http://pyroscope:4040" }
}
```

## Real-World Use Cases

### 1. The JSON regression caught before paging

Diff after a routine deploy shows `json.Marshal` up 38% CPU. Root cause: a struct gained a nested interface field forcing reflection-heavy marshaling. Fixed with generated marshalers; SLO dashboards never blinked because continuous profiling saw it first.

### 2. Memory leak owned in one afternoon

Pod restarts creep upward weekly. Heap `alloc_space` trend grouped by version shows `sessionCache.Put` retaining objects since v1.4.0; a missing TTL eviction is found without ever reproducing locally.

### 3. Fleet right-sizing worth real money

CPU flamegraphs show 55% of checkout-service CPU in TLS handshakes terminated at the app. Moving termination to the mesh freed a third of the replica count — capacity decisions justified with profile screenshots, not vibes.

### 4. Noisy-neighbor forensics in multi-tenant pods

Wall-time profiles distinguish on-CPU work from lock waits; a tenant batch job holding a shared mutex explains why other tenants' p99 moved — mutex profiles turn "the pod was slow" into "this lock, this holder".

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------- | ------------------------------------------------------------------------- |
| Profiling only staging | Staging lacks prod's data shapes; sample prod at low rate instead |
| Sampling at max frequency everywhere | Budget overhead explicitly (100 Hz CPU default, tune down at fleet scale) |
| No version/zone labels on samples | Unlabeled profiles cannot be sliced or diffed — always tag git SHA |
| Reading flamegraph width as latency | Width = share of samples/resources, not per-request duration |
| Comparing diffs across different traffic mixes | Filter both windows to the same route/tenant class first |
| Keeping profiles forever | Profiles are small but not free; 30-90d retention matches release cadence |
| Treating profiles as incident-only tooling | The value is the BASELINE; ad-hoc snapshots lack comparison anchors |

---

## Best Practices

1. **Ship the profiler in every production workload**, enabled via config flag; disabled in unit tests, optionally on in load-test environments.
2. **Label everything**: `version` (git SHA), `zone`, `env`, and one business dimension (route class) — labels make diffs honest.
3. **Start with CPU + heap**, add allocation and wall-time profiles where GC or IO dominate.
4. **Wire profiles into release review**: a diff between previous and current release belongs next to the changelog.
5. **Keep pprof endpoints available** behind auth even with a backend running — they are your deep-dive escape hatch.
6. **Prefer SDK push for app services; prefer agent/eBPF scraping for fleets you cannot re-instrument** (legacy, third-party).
7. **Correlate with traces** via span profiles so on-call moves from "endpoint slow" to "function X inside span Y" in one click.
8. **Set retention deliberately** (30-90 days) and monitor backend storage like any other datastore.
9. **Watch overhead empirically**: measure p99 and CPU with profiling on/off once, document the number, stop arguing folklore.
10. **Treat a sudden baseline shift as an event**: even without an alert firing, an unexplained 20% CPU-share change in a function deserves a look.

## Performance Considerations

| Profiler mode | Typical overhead | Notes |
| ------------------------- | --------------------------------- | ---------------------------------------- |
| CPU @ 100 Hz | ~0.5-2% of one core per busy core | Frequency is the knob |
| Wall-clock sampling | Similar to CPU | Adds off-CPU visibility |
| Heap sampling (per-alloc) | < 1-3% allocator cost | Sampling interval trades fidelity |
| Full heap dumps | Stop-the-world spikes | Avoid in hot paths; use sampled profiles |
| eBPF node-wide profiler | Constant few-% per node | Zero app change; covers every process |

## Summary

- Continuous profiling turns flamegraphs from a debugging artifact into a **queryable signal with history**.
- Metrics say "what changed", traces say "where in the request", profiles say "**which functions and allocations**".
- The highest-value workflow is **release-over-release diffing** — catching regressions invisible to SLO alerts.
- Overhead is small and tunable (sub-2% CPU at sane sampling rates); eBPF profilers remove instrumentation friction entirely.
- **Span profiles** connect traces to flamegraphs, completing the click-path from symptom to code line.
- Labels (version, zone, route) are what make profiles comparable — treat them as part of your schema.
- **In interviews: explain sampling vs instrumentation, give the CPU+heap starting point, and lead with the diff story.**

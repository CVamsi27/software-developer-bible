# Continuous Profiling

> **Retain sampled evidence of production resource use.** Where metrics tell you CPU went up and traces tell you which endpoint got slow, profiles tell you *which functions burned the time or allocated the bytes* — sampled continuously, stored with labels like any other telemetry, and diffable across releases. This file covers what continuous profiling adds over ad-hoc `pprof`, how Pyroscope/Parca ingest and store folded stacks, the profile types worth collecting (CPU, heap, allocations), regression hunting via profile diffing, overhead budgets, and the trace-to-profile correlation (span profiles) that closes the observability loop.

## Definition

**Continuous profiling** regularly samples what running code is doing in production. It stores those samples with timestamps and labels so you can later ask which functions used CPU time or memory during an incident. Profiles add another observability signal alongside logs, metrics, and traces. You can investigate a past period without waiting to start a profiler after the problem appears.

> **Textbook Definition:** Continuous profiling repeatedly samples runtime execution or allocation behavior and retains time-indexed profiles, enabling analysis of resource use during both normal operation and past incidents.

Key concepts:

- **Sampling profiler**: interrupts execution at a fixed frequency (e.g., 100 Hz), records the stack, resumes. Statistical, not exhaustive — accuracy comes from volume.
- **Folded stacks**: compressed representation (`funcA;funcB;funcC count`) that backends aggregate into flamegraphs/icicle charts.
- **Labels**: service name, version/git SHA, pod, zone — attached to every sample so profiles slice like metrics do.
- **Profile diff**: aggregation of one time window minus another, highlighting functions whose share of resource use grew.
- **Span profiles**: profiler context tied to active trace spans, enabling span -> flamegraph navigation.

---

## First Principles

A latency metric is an aggregate outcome; it does not identify the code consuming resources. A one-off profile started after an incident misses past execution. Retaining periodic samples creates historical evidence, but finite samples are statistical: short operations may have no samples, and unavailable stack symbols can hide the useful frame. Collection itself uses CPU, memory and export bandwidth, so always-on use requires a measured budget.

## Why It Matters

1. **Metrics raise the alarm; profiles name the culprit.** "checkout-service p99 up 40%" ends at the dashboard without a flamegraph showing `json.Marshal` eating 60% of CPU.
2. **Regressions hide below alert thresholds.** A 15% CPU-per-request increase may not page anyone, but a profile diff against last week's build makes it obvious — before it compounds into an SLO breach.
3. **Reproduction is expensive; sampling is cheap.** Load-testing a memory leak locally can take days; allocation and retained-heap comparisons narrow the investigation; churn alone does not prove a leak.
4. **Capacity planning gets empirical.** Continuous CPU/heap profiles reveal right-sizing opportunities worth real money at fleet scale (fewer replicas for the same p99).
5. **It complements other signals.** Traces answer "where in the request", logs answer "what happened", metrics answer "how much", profiles answer "in which code".

## How It Works

### 1. Architecture

```text
┌──────────────────────────────┐
│ POD: orders-service          │
│  ┌────────────────────────┐  │  samples (~100 Hz)
│  │ APP                       │  ├───────────────► folded stacks
│  │  + profiler agent      │  │                  {service, version,
│  └────────────────────────┘  │                   zone} labels
└──────────────────────────────┘
        │ push / agent scrapes pprof endpoints
        ▼
┌──────────────────────────────────────────────┐
│ PROFILE BACKEND (Pyroscope / Parca)          │
│  • aggregates trees per label set            │
│  • stores time-bucketed profiles             │
│  • serves flamegraph + diff queries          │
└──────────────────┬───────────────────────────┘
                   ▼
        UI: single flamegraph | diff view |
            span-profile link from Tempo trace
```

### 2. What each profile type answers

| Type | Mechanism | Answers |
| ------------------ | --------------------------------- | ------------------------------------- |
| CPU time | Sample on-CPU stacks at fixed Hz | Which functions burn compute? |
| Wall time | Include off-CPU waits (IO, locks) | Why is this slow despite idle CPU? |
| Heap in-use | Sample live allocations | What holds memory right now? |
| Alloc space/rate | Sample at allocation events | What churns GC pressure? Leak source? |
| Mutex/block | Instrument contention points | Which lock serializes requests? |
| Goroutines/threads | Dump counts | Leak of concurrent tasks? |

Start with a supported CPU mode. Add live-heap and allocation modes when memory pressure or garbage collection warrants their distinct evidence.

### 3. Diffing: finding regressions

```text
DIFF: release v1.8.0 window vs v1.7.3 window (same traffic class)
═══════════════════════════════════════════════════════
net/http.(*Server).serve           ▓▓▓▓▓▓▓  (unchanged)
encoding/json.Marshal              ██████ +38%   <-- suspect
github.com/acme/api.enrichOrder     ████ +22%    <-- calls json
runtime.mallocgc                    ██ +19%      <- downstream effect
```

Reading order: start at the largest red leaf, walk up to your own code, confirm the commit range between versions touches it. A diff that shows only runtime frames growing usually means allocation churn introduced upstream of the hot loop.

### 4. Trace integration (span profiles)

With Grafana's profiles-in-traces integration, the SDK wraps span boundaries: while a span is active, the profiler attributes its samples to that span ID. Tempo then renders a "Profiles" tab on the span — click a 900 ms `process-order` span and see exactly which functions spent the time, where that runtime and integration support span attribution. Sampling may be sparse, and a CPU profile does not account for all 900 ms of wall time.

### 5. Match the profiler to the runtime

A timer or runtime hook samples stacks; not every profiler interrupts execution in the same way. CPU, wall-time, live-heap and allocation modes have different sampling units and costs. The 512 KiB allocation interval is a configurable runtime-specific example, not a universal profiler rule. Native/JIT stack unwinding and symbol/source-map availability affect attribution. An eBPF agent can cover compatible processes without code changes, but unsupported runtimes, missing symbols and dropped samples still limit evidence.

## Code Example: A Complete Local CPU Profile

Node's built-in profiler produces a local artifact without a telemetry backend. Save this as `profile-demo.cjs`:

```javascript
const { createHash } = require('node:crypto');
function hashBatch() {
  let last;
  for (let i = 0; i < 200_000; i++) {
    last = createHash('sha256').update(`demo-${i}`).digest('hex');
  }
  return last;
}
console.log(hashBatch());
```

```bash
mkdir -p profiles
node --cpu-prof --cpu-prof-dir=./profiles profile-demo.cjs
```

Open the resulting `.cpuprofile` in a compatible CPU-profile viewer. Its samples describe this synthetic CPU workload, not a production latency result. Compare it with a second run under the same Node version and workload before attributing a change. Inclusive sample time includes descendants; exclusive time belongs to that frame. Flamegraph width is sampled resource share, not a left-to-right execution timeline.

### Production collection is a deployment integration

Pyroscope, Parca and runtime profilers offer different push and pull integrations. In the current [Pyroscope Node SDK documentation](https://grafana.com/docs/pyroscope/latest/configure-client/language-sdks/nodejs/), initialize the SDK and **call** `start()`; merely importing a module that exports a startup function does not start profiling. CPU collection is configured within wall profiling, and runtime/native-binary support must be checked. Do not copy a generic `samplingIntervalMs` field into an SDK that documents another shape.

For an actual integration, set service/version labels, endpoint authentication, supported profile modes and a bounded shutdown flush. Test native module installation on the deployed OS/architecture, not just a development laptop. Span profiles require the tracing/profiling bridge and compatible backend setup; ordinary profiler startup does not establish that bridge.

A `pprof` endpoint is a sensitive debug interface. Keep it on a private authenticated path with rate limits and a bounded collection duration; heap dumps may contain secrets. Go's `go tool pprof -diff_base=old.pprof new.pprof` compares compatible **actual pprof files**. A UI render/diff HTTP response is not automatically a pprof binary. Obtain artifacts through the backend's documented export interface instead of inventing an endpoint.

## Real-World Use Cases

The following scenarios are illustrative investigations, not measured outcomes from a named deployment.

### 1. A JSON regression before paging

Diff after a routine deploy shows `json.Marshal` up 38% CPU. Root cause: a struct gained a nested interface field forcing reflection-heavy marshaling. Fixed with generated marshalers; SLO dashboards never blinked because continuous profiling saw it first.

### 2. Memory leak owned in one afternoon

Pod restarts creep upward weekly. A retained-heap profile, compared with allocation volume and version, points to `sessionCache.Put` holding objects since v1.4.0; a missing TTL eviction is found without ever reproducing locally.

### 3. Fleet right-sizing worth real money

CPU flamegraphs show 55% of checkout-service CPU in TLS handshakes terminated at the app. Moving termination to the mesh freed a third of the replica count — capacity decisions justified with profile screenshots, not vibes.

### 4. Noisy-neighbor forensics in multi-tenant pods

Wall-time profiles distinguish on-CPU work from lock waits; a tenant batch job holding a shared mutex explains why other tenants' p99 moved — mutex profiles turn "the pod was slow" into "this lock, this holder".

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Profiling only staging | Staging lacks prod's data shapes; sample prod at low rate instead |
| Sampling at max frequency everywhere | Budget overhead explicitly (100 Hz CPU default, tune down at fleet scale) |
| No version/zone labels on samples | Stable labels make release comparisons attributable; cap dimensions to prevent storage growth |
| Reading flamegraph width as latency | Width = share of samples/resources, not per-request duration |
| Comparing diffs across different traffic mixes | Filter both windows to the same route/tenant class first |
| Keeping profiles forever | Choose retention from incident history needs, sensitivity and measured storage cost |
| Treating profiles as incident-only tooling | The value is the BASELINE; ad-hoc snapshots lack comparison anchors |

## Best Practices

1. **Roll out to a measured pilot**, then expand compatible workloads after overhead, privacy and failure checks.
2. **Label everything**: `version` (git SHA), `zone`, `env`, and one business dimension (route class) — labels make diffs honest.
3. **Start with CPU + heap**, add allocation and wall-time profiles where GC or IO dominate.
4. **Wire profiles into release review**: a diff between previous and current release belongs next to the changelog.
5. **Keep pprof endpoints available** behind auth even with a backend running — they are your deep-dive escape hatch.
6. **Prefer SDK push for app services; prefer agent/eBPF scraping for fleets you cannot re-instrument** (legacy, third-party).
7. **Correlate with traces** via span profiles so on-call moves from "endpoint slow" to "function X inside span Y" in one click.
8. **Set retention deliberately** (30-90 days) and monitor backend storage like any other datastore.
9. **Measure overhead empirically** under representative load and periodically after runtime, profiler or configuration changes. Compare CPU, memory, tail latency and export traffic.
10. **Treat a sudden baseline shift as an event**: even without an alert firing, an unexplained 20% CPU-share change in a function deserves a look.

---

## Performance Considerations

Do not assume a fixed sub-2% overhead. Sampling frequency, stack depth, allocation rate, runtime and export behavior change cost. Measure a representative control/candidate workload and monitor lost samples, agent CPU/memory and exporter backlog. Higher sampling improves statistical resolution while increasing collection work. A full heap snapshot can pause execution and expose object contents; it has a different operational risk from sampled profiles.

## Summary

Continuous profiling preserves sampled code-level resource evidence across time. Compare equivalent workloads and release identities, distinguish allocation churn from retained memory, and connect profiles to the user-critical trace path. Verify runtime support, sample loss, privacy and overhead before expanding continuous collection.

# eBPF Observability

> **Teach the kernel to observe — without touching the application.** eBPF lets sandboxed programs run inside the Linux kernel, hooked on syscalls, network events, and tracepoints. For observability that means zero-instrumentation visibility: every connection, DNS lookup, and HTTP call seen at the kernel boundary, with no sidecars, no SDKs, and no code changes. This file is a practical primer (programs, verifier, maps), then the production tools built on it — Cilium/Hubble for network flows and service graphs, Pixie-style auto-telemetry, Falco/Tetragon for security — plus honest notes on overhead, risks, and when plain OTel is still the right answer.

## TL;DR

- **eBPF** = a kernel VM + verifier. You write a small program, the verifier proves it cannot crash or leak the kernel, and you attach it to hooks (kprobes, tracepoints, XDP/tc, LSM, uprobes).
- **Maps** are the data bridge: kernel program writes events into ring buffers; a user-space agent reads them and turns them into telemetry.
- **Network observability without instrumentation**: Cilium's Hubble records L3-L7 flows from socket-level hooks — service graph, drop reasons, DNS/HTTP detail — for every workload on the node, including legacy binaries.
- **Pixie-style auto-telemetry** captures protocol payloads dynamically (PEBBL scripts), producing per-request traces with no libraries.
- **Security overlap is real**: Falco (syscall rules) and Tetragon (policy-enforced tracing, can kill offending processes) consume the same kernel events — one plane serves both observability and runtime security.
- **Costs**: 1-5% CPU per active hook set (XDP can be cheaper), ring-buffer memory, kernel/BTF version constraints, and a serious privilege surface.
- **In interviews: "eBPF moves observation INTO the kernel boundary where all truth passes; apps can hide nothing."**

## Definition

**eBPF** (extended Berkeley Packet Filter) is a Linux kernel technology for running sandboxed, event-driven programs in kernel space. Programs are compiled to bytecode, statically analyzed by an in-kernel **verifier** (safety: no invalid memory access, no unbounded loops, no crashes), attached to hook points, and communicate with user space through **maps** (hash tables, ring buffers).

Key concepts:

| Concept     | What it is                                                                   |
| ----------- | ---------------------------------------------------------------------------- |
| Program     | Compiled bytecode executed by the kernel VM on hook triggers                 |
| Hook        | Attachment point: kprobe, tracepoint, XDP, tc, LSM, uprobe, socket ops       |
| Verifier    | Static analysis pass guaranteeing kernel safety before load                  |
| Maps        | Shared key/value stores between kernel programs and user space               |
| CO-RE + BTF | Compile Once, Run Everywhere — portable binaries against kernel BTF metadata |
| Ring buffer | High-throughput map type streaming events to user-space agents               |

Observability angle: because syscalls and packets are chokepoints every workload must cross, eBPF yields complete visibility **without touching application code, images, or manifests**.

---

## Why It Matters

1. **Zero instrumentation coverage.** Polyglot fleets, vendor binaries, and legacy services nobody dares recompile still emit full telemetry — the kernel sees everything.
2. **No sidecar tax.** Visibility rides in-node (Cilium agent / Pixie edge module), avoiding sidecar latency, memory duplication, and rollout coordination.
3. **Ground truth beats sampling.** Every connection, packet, and syscall is observable — not a sampled slice reconstructed from app logs.
4. **L7 depth from the outside.** HTTP/gRPC/Kafka/DNS semantics parsed at the socket layer: service graphs and red/teal latency maps appear for free.
5. **One plane for reliability AND security.** The same events power flow logs (Hubble), threat detection (Falco), and enforcement (Tetragon, Cilium NetworkPolicy) — fewer agents, consistent story.

## How It Works

### 1. From source to telemetry

```text
┌─────────────────────────────────────────────────────────────────────┐
│ eBPF source │────────►│ bytecode │─────►│ KERNEL                                               │
│ (C / Rust)  │         │ (LLVM)   │      │ 1. VERIFIER proves safe                              │
└─────────────┘         └──────────┘      │ 2. JIT to native          │
                                          │ 3. attach to hook         │
                                          │    (kprobe/tc/XDP/LSM)    │
                                          └──────────┬───────────────┘
                                                     │ events
                                              ┌──────▼───────┐
                                              │ MAPS         │
                                              │ hash/ringbuf │
                                              └──────┬───────┘
                                                     │ poll/read
                                          ┌──────────▼───────────────┐
                                          │ USER-SPACE AGENT          │
                                          │ cilium-agent / pixie /    │
                                          │ tetragon                  │
                                          └──────────┬───────────────┘
                                                     ▼
                                       flows, metrics, profiles, alerts
```

### 2. Common hook points

| Hook                 | Fires on                                        | Observability use                   |
| -------------------- | ----------------------------------------------- | ----------------------------------- |
| kprobe/fentry        | Kernel function entry/exit (`tcp_v4_connect`)   | Connection counts, latency          |
| tracepoint           | Fixed kernel event sites (sched, net, syscalls) | Stable syscall tracing              |
| XDP                  | Earliest packet ingress (driver level)          | DDoS metrics, fast drops            |
| tc (traffic control) | Packet in/out per interface                     | Per-pod flow accounting             |
| LSM                  | Security decision points                        | Enforcement (Tetragon)              |
| uprobe               | User-space function entry (SSL_write)           | Payload capture without code change |

### 3. Zero-instrumentation network observability (Cilium/Hubble)

Cilium attaches programs at the socket/cgroup layer so each pod's traffic is labeled with Kubernetes identity (namespace, service account) *before* policy and logging run. Hubble reads those flow events:

```text
SERVICE GRAPH (auto-derived)
frontend ──HTTP──► checkout ──gRPC──► payments ──TCP──► vault
                       │
                       └──DNS──► *.rds.amazonaws.com

FLOW RECORD: {verdict=FWD, proto=HTTP, method=POST, path=/charge,
              src=frontend, dst=payments, verdict-delay=0.4ms,
              drop_reason=-, tcp_flags=...}
```

You get: who-calls-whom (service map), error/drop breakdowns with kernel drop reasons, DNS analytics, and L7 latency histograms — all without a single line of app code.

### 4. Pixie-style auto-telemetry

Pixie runs an edge module per node using uprobes on dynamic libraries (OpenSSL `SSL_read/SSL_write`) and protocol parsers ("PEBBL" scripts) to reconstruct request/response pairs. Result: distributed traces with full payload context for applications that were never instrumented — powerful for brownfield audits.

### 5. Security use overlap

| Tool                 | Mechanism                                              | Posture          |
| -------------------- | ------------------------------------------------------ | ---------------- |
| Falco                | Syscall event sources -> rule engine -> alerts         | Detect (default) |
| Tetragon             | kprobe/LSM policies; synchronous actions incl. SIGKILL | Detect + ENFORCE |
| Cilium NetworkPolicy | Identity-based L3-L7 filtering at the same hooks       | Enforce          |

Because all three read the same kernel events, mature platforms ship them together: Hubble flow logs double as forensics for whatever Tetragon blocks.

### 6. Risks and overhead

- **Kernel coupling**: features need modern kernels (5.x+), BTF for portability; managed clouds vary.
- **CPU cost**: per-hook, typically 1-5%; XDP paths can offload drops near the driver; idle systems pay little.
- **Memory**: ring buffers sized in MiB per node; undersized buffers DROP events silently — monitor buffer loss.
- **Privilege surface**: loading programs requires root-equivalent capabilities (CAP_BPF, CAP_PERFMON); treat who-can-load-programs as production access.
- **Verifier friction**: legitimate programs get rejected; iteration requires verifier literacy.

## Code Examples

### A minimal kernel-side counter (C)

```c
/* count_connects.c — count outbound TCP connects per cgroup/pod.
   Loaded by a user-space loader (cilium/ebpf, libbpf). */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

struct event {
    __u32 daddr;
    __u16 dport;
};

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 1 << 20);
} events SEC(".maps");

SEC("kprobe/tcp_v4_connect")
int BPF_KPROBE(trace_connect, struct sock *sk)
{
    struct event *e;

    /* Verifier rule #1: every pointer dereference must be proven valid */
    if (!sk)
        return 0;

    e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e)
        return 0; /* buffer full: drop sample, never block the kernel */

    e->daddr = sk->__sk_common.skc_daddr;
    e->dport = bpf_ntohs(sk->__sk_common.skc_dport);
    bpf_ringbuf_submit(e, 0);
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

The user-space side (Go with `cilium/ebpf`) pins the program, polls the ring buffer, and exports Prometheus counters — this agent pattern is exactly what Cilium/Hubble industrialize.

### Watching flows with Hubble

```bash
# Follow live HTTP flows toward the checkout service
hubble observe --since=5m \
  --protocol http \
  --to-label app=checkout \
  --print-identity

# Top talkers + dropped flows for the namespace (service-graph seeds)
hubble observe flows --namespace prod \
  --verdict DROPPED \
  -o table

# Why was this denied? Drop reasons come from the KERNEL, not guesses:
hubble observe --to-fqdn api.stripe.com --last 20
```

### Identity-aware L7 policy (the same plane enforces)

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: checkout-l7
  namespace: prod
spec:
  endpointSelector:
    matchLabels:
      app: checkout
  ingress:
    - fromEndpoints:
        - matchLabels:
            app: frontend
      toPorts:
        - ports:
            - port: "8080"
              protocol: TCP
          rules:
            http:
              - method: POST
                path: "/api/checkout.*"
  egress:
    - toEndpoints:
        - matchLabels:
            app: payments
    - toEndpoints:
        - matchLabels:
            io.kubernetes.pod.namespace: kube-system
            k8s-app: kube-dns
```

Every allowed AND denied match here appears in Hubble as a flow record — policy and telemetry share one truth.

### Tetragon: detect (or kill) sensitive file access

```yaml
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: sensitive-file-reads
spec:
  kprobes:
    - call: "security_file_permission"
      syscall: false
      args:
        - index: 0
          type: "file"
        - index: 1
          type: "int"
      selectors:
        - matchArgs:
            - index: 0
              operator: "prefix"
              values:
                - "/etc/shadow"
                - "/etc/kubernetes"
          matchActions:
            - action: Sigkill # enforcement, not just logging
```

### bpftrace one-liners for ad-hoc kernel questions

```bash
# Syscalls per second by process (top offenders)
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

# TCP retransmit events with destination
bpftrace -e 'kprobe:tcp_retransmit_skb { @[ntop(args->skb->data)] = count(); }'

# Latency histogram of vfs_read
bpftrace -e 'kprobe:vfs_read { @start[tid] = nsecs; }
             kretprobe:vfs_read /@start[tid]/ {
               @usecs = hist((nsecs - @start[tid]) / 1000);
               delete(@start[tid]);
             }'
```

## Real-World Use Cases

### 1. Legacy monolith gets a service map overnight

A bank's COBOL-adjacent Java estate cannot take SDK changes. Installing Cilium + Hubble produces a full service graph with p99 per edge in a week — the first accurate dependency inventory the org ever had.

### 2. Diagnosing "network is slow" with kernel evidence

Intermittent checkout timeouts. Hubble flow logs show `drop_reason: POLICY_DENIED` spikes from a mislabeled staging namespace leaking into prod CIDRs — kernel drop reasons end the blame game between app and network teams.

### 3. Runtime breach containment

Tetragon policy kills a compromised pod attempting `/etc/shadow` access mid-attack; the synchronous event log provides the exact binary, PID, and ancestor chain for forensics — detection, response, and evidence from one hook.

### 4. Sidecar-free mesh economics

A 300-node fleet replaces its Envoy sidecars' telemetry role with Cilium node-level visibility, cutting ~256 MiB and per-hop proxy latency per pod while keeping mTLS via the kernel — observability was the argument that closed the migration.

## Common Mistakes

| Mistake                                           | Fix                                                                                 |
| ------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Loading ad-hoc probes on prod kernels casually    | Version-controlled programs, staged rollout, verifier-tested against target kernels |
| Undersized ring buffers, silent event loss        | Size buffers to peak; alert on buffer-drop counters                                 |
| Ignoring kernel/version matrix (BTF availability) | Document supported nodes; pin distro images where possible                          |
| Granting broad BPF-loading rights widely          | Restrict CAP_BPF/CAP_PERFMON to the platform agents only                            |
| Replacing OTel entirely with eBPF                 | Keep app-context spans (queue depth, feature flags); eBPF sees I/O, not intentions  |
| Reading Hubble flows as full audit logs           | Flow records summarize; enable deep L7 tracing selectively                          |
| Assuming zero overhead                            | Measure per-hook CPU; disable debug probes after incidents                          |

---

## Best Practices

1. **Prefer platform agents over hand-rolled probes**: Cilium/Hubble, Pixie, Parca, Tetragon maintain kernel-compatibility matrices you do not want to own.
2. **Pin minimum kernel versions** (5.10+ recommended) and verify BTF support in your node images before rollout.
3. **Monitor the monitoring**: buffer drops, agent restarts, per-hook CPU belong on dashboards.
4. **Use eBPF for breadth, OTel for depth**: kernel-level flows catch everything; SDK spans add business context. They compose.
5. **Tie security policy to the same identity model as telemetry** (Cilium labels) so "what happened" and "what is allowed" never disagree.
6. **Stage probe rollouts like code deploys**: canary nodes first, rollback plan ready, verifier output archived.
7. **Keep enforcement separate from exploration**: debugging probes stay read-only; anything with Sigkill lives under change control.
8. **Document the privilege story**: who can load programs, from which registry, signed how — auditors will ask.
9. **Sample smartly for L7 payloads**: capture bodies only for allow-listed routes; default to metadata.
10. **Rehearse kernel-upgrade compatibility**: test new node images against your eBPF stack in preprod every cycle.

## Performance Considerations

| Concern                  | Reality                              | Guidance                                      |
| ------------------------ | ------------------------------------ | --------------------------------------------- |
| Per-hook CPU             | ~1-5% total for typical agent stacks | Fewer hooks > clever tuning; measure per hook |
| XDP fast-path drops      | Near-line-rate, sub-% cost           | Prefer XDP for volumetric defenses            |
| Ring buffer sizing       | Too small = lost events              | Start 8-64 MiB/node; watch drop counters      |
| L7 parsing cost          | Proportional to captured bytes       | Metadata-first; payload capture selective     |
| Cold-start JIT/load time | Milliseconds per program             | Negligible; irrelevant at steady state        |

## Summary

- eBPF runs **verifier-checked programs inside the kernel**, hooked on syscalls/network events, streaming data out via maps — observability at the chokepoint every workload crosses.
- **Zero instrumentation** is the headline: Cilium/Hubble builds service graphs and L7 flow telemetry for unmodified apps; Pixie reconstructs traces via dynamic probing.
- **Security shares the plane**: Falco detects, Tetragon detects-and-enforces, Cilium filters — one event stream, three jobs.
- Costs are real but bounded: single-digit % CPU per active hook set, ring-buffer memory, and a hardened privilege model.
- It complements rather than replaces OTel: kernel truth below, application intent above.
- **In interviews: explain verifier + maps in two sentences, then reach for Hubble/Tetragon examples — specificity sells this topic.**

## Cheat Sheet

```text
EBPF OBSERVABILITY CHEAT SHEET
════════════════════════════════════════════════════════════════

CORE MODEL
  source(C) -> LLVM bytecode -> VERIFIER -> JIT -> attach(hook)
  hooks : kprobe | tracepoint | XDP | tc | LSM | uprobe
  maps  : hash | ringbuf (kernel <-> user-space bridge)
  agent : cilium / pixie / tetragon / parca (user-space reader)

WHY IT WINS
  • zero app instrumentation (legacy + polyglot covered)
  • no sidecars (node-level agents)
  • kernel ground truth: every conn, packet, syscall
  • L7 parsing from OUTSIDE the app (Hubble, Pixie)

TOOL MAP
  Cilium+Hubble : flows, service graph, L7 policy (enforce+detect)
  Pixie         : auto-traces w/ payloads via dynamic probing
  Falco         : syscall rule alerts (detect)
  Tetragon      : policy tracing w/ sync actions (SIGKILL)
  bpftrace      : ad-hoc kernel one-liners

COSTS / RISKS
  1-5% CPU per hook set | ringbuf mem (drops if small!)
  kernel >= 5.10 + BTF | CAP_BPF/CAP_PERFMON = privileged access

PATTERN
  eBPF = BREADTH (everything, outside-in)
  OTel = DEPTH   (app intent, business context)  -> combine both

INTERVIEW FORMULA
  verifier+maps in 2 sentences -> Hubble service graph ->
  Tetragon kill example -> overhead number -> complements OTel
```

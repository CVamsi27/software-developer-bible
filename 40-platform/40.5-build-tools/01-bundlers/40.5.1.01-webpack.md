# Webpack

A dashboard imports its export dialog on every visit, although most users never open it. Moving that import behind a user action can reduce the initial download, but now the feature can fail to load after a deployment. Webpack's graph and chunking rules let you make that trade-off deliberately.

## Definition

Webpack starts from one or more entry modules, follows their dependencies, applies configured transformations, and emits browser-ready assets. Static imports normally belong to the initial graph; a dynamic `import()` creates an asynchronous loading boundary.

> **Textbook Definition:** Webpack is a static module bundler that builds dependency graphs from configured entry points, applies module transformations and optimization, then emits bundles, chunks and assets together with runtime code for loading them.

## First Principles

An import describes what code can be reached; it does not decide when that code reaches the browser. The build tool must resolve each dependency, turn supported source files into modules, and choose which modules ship together. Webpack then emits both the files and, when needed, runtime instructions to request later chunks. Bundling is a delivery strategy, not a requirement that every browser use one giant JavaScript file.

## Follow one import through the build

Suppose a rarely used export dialog is imported at the top of the entry file. It becomes part of the initial module graph, so a visitor who never exports data may still download and parse its code. Changing that import to `import()` gives Webpack a point where it can emit a separate chunk and load it only when the feature is requested.

```text
entry → resolve dependencies → parse modules → apply rules and transforms
      → analyze usage and chunk boundaries → optimize → emit assets + runtime
```

Resolution answers which file a request names. Webpack 5 understands JavaScript, JSON, and WebAssembly. Since 5.109, built-in CSS and HTML handling defaults to `auto`: it applies unless a matching loader or explicit module type keeps the existing path. Both native paths are still experimental and do not replace every loader or plugin behavior, so check the pinned release's limits before migrating. Asset Modules make imported images and fonts part of the graph without legacy loaders: `asset/resource` emits a file and exports its URL, `asset/inline` exports a data URI, and `asset` chooses between them by size. Use `asset/source` when the module should export a resource as text.

Loaders remain useful when a project needs a particular source transform or resource representation. Some TypeScript transforms, such as Babel or a loader configured for transpile-only, emit JavaScript without checking types. Verify whether the selected pipeline type-checks and add a separate check when it does not. A rule selects matching resources; when a rule uses multiple loaders, they run from right to left. In a project that chooses a CSS loader pipeline, for example, `css-loader` turns CSS imports and references into a JavaScript module before `style-loader` injects the styles at runtime; Webpack also documents native CSS support, so this loader chain is not a universal requirement.

Plugins work at a broader level. A loader transforms an individual module; a plugin can subscribe to compiler and compilation hooks to generate HTML, optimize assets, emit a manifest, or integrate a feature such as Module Federation. Choose a loader for source transformation and a plugin when the work belongs to the build lifecycle or its output as a whole.

Static ESM exports let production optimization determine which exports are used. The package-level `sideEffects` field answers a different question: can evaluating an otherwise unused module be skipped? Setting it incorrectly can remove required CSS imports or registration code. Check the production output because development builds do not prove what the production optimizer removed.

## Example: load a feature on demand

This small example emits a stable entry file and a content-hashed feature chunk. In a disposable directory, install `webpack` and `webpack-cli`, create the files below, then build and copy the page into the output directory:

```bash
npx webpack --config webpack.config.cjs
node -e "require('node:fs').copyFileSync('index.html', 'dist/index.html')"
```

```javascript
// src/index.js
document.querySelector('#load-feature').addEventListener('click', async () => {
  const output = document.querySelector('#output');
  try {
    const { render } = await import(
      /* webpackChunkName: "feature" */ './feature.js'
    );
    output.textContent = render();
  } catch {
    output.textContent = 'Feature unavailable. Please retry.';
  }
});
```

```javascript
// src/feature.js
export const render = () => 'The feature chunk has loaded.';
```

```html
<!-- index.html, served from the site root -->
<button id="load-feature">Load feature</button>
<output id="output"></output>
<script defer src="/main.js"></script>
```

```javascript
// webpack.config.cjs
const path = require('node:path');

module.exports = {
  mode: 'production',
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'main.js',
    chunkFilename: '[name].[contenthash].js',
    publicPath: 'auto',
    clean: true,
  },
  cache: { type: 'filesystem' },
};
```

The initial page requests `main.js`; clicking the button invokes `import()` and returns a promise while the browser fetches the feature chunk. If the chunk is missing or unreachable, that promise rejects, so production UI should handle the failure. `publicPath: 'auto'` lets Webpack infer the chunk base from runtime context, but a subpath or CDN deployment still needs a path check. The entry name stays stable here so the HTML can name it directly; production builds often hash the entry too and generate HTML or a manifest that points to its current filename.

Content hashes support long-lived caching because a changed chunk gets a new filename. They do not keep an old file available. A tab that loaded yesterday's `main.js` can request yesterday's chunk after today's deploy, so publish assets atomically or retain old hashed assets for the client lifetime you support. `output.clean` removes old files from the local build directory; your deployment strategy decides whether already-published chunks survive. The sample's filesystem cache is a compiler cache for repeat builds, separate from browser/HTTP caching; restore a CI build cache only when its toolchain and configuration inputs match. Measure initial transfer and parse cost before adding split points: each asynchronous boundary can also add a request and a loading step.

## Development updates and production boundaries

Hot Module Replacement (HMR) is a development update path. After a change, the compiler emits an update and the runtime tries to replace an accepted module without reloading the page. An update applies only when the changed module or a dependency boundary accepts it and any stateful side effects are handled. If the update cannot be applied, the development client may fall back to a full reload; HMR itself does not guarantee application state survives. It is separate from production code splitting and deployment.

Use `mode: 'development'` for fast feedback and an HMR-capable dev server; use `mode: 'production'` for production optimizations. Inspect bundle composition with a stats or analyzer tool before tuning `splitChunks`, loader parallelism, or caches. `DefinePlugin` performs build-time substitutions; any substituted value included in client code is public, and the plugin does not load `.env` files for you. Module Federation adds runtime-loaded remotes and shared-dependency negotiation, so it also adds release compatibility, trust, network-failure, and CSP decisions. A configured singleton does not guarantee compatible versions.

For framework applications, follow the framework's supported bundler and configuration surface. For example, Next.js 16 uses Turbopack by default for development and builds; projects that need Webpack must opt into it. Existing Webpack compatibility is not a reason to assume a framework still uses Webpack by default.

## Summary

Webpack resolves and transforms a dependency graph, then emits assets and runtime behavior for the chosen chunk boundaries. Use static imports for required code and dynamic imports for measured asynchronous boundaries; distinguish loaders from lifecycle plugins, export analysis from side-effect metadata, and hashed names from asset availability. Verify production output and the real deployment path, while treating HMR as a development-only update mechanism.

# Vite

Suppose a route imports hundreds of application modules and a few large packages. Building the entire graph before every edit would delay feedback; asking the browser to fetch every tiny dependency file would create a different delay. Vite uses different delivery strategies for development and production, so understanding where each strategy begins and ends is more useful than calling it simply "a fast bundler."

## Definition

Vite is a frontend development server and production build tool. In its default development flow, it serves application modules as browser-native ES modules, resolving and transforming them when requested and pre-bundling dependencies. A production build follows a separate path that emits optimized assets.

> **Textbook Definition:** Vite is a frontend build system that combines an on-demand module development server, a transform and plugin pipeline, and a production asset builder. It trades a prebuilt application bundle during ordinary development for URL-addressable source modules, while still optimizing dependencies and bundling release output.

This chapter targets Vite 8; the currently supported stable minor is 8.3 (checked 14 October 2026). Vite 8 uses Rolldown for dependency optimization and production bundling, Oxc for JavaScript and TypeScript transforms and JavaScript minification, and Lightning CSS for CSS minification. Vite 8.1 also added an experimental bundled-development mode for very large graphs; it is opt-in and some third-party plugins may not support it.

## First Principles

An editor and an end user pay different costs. The editor waits for startup and each update, so the development server should avoid producing the complete release bundle before it can serve a page. The browser still pays for package compatibility and request fan-out, so dependencies need their own preparation step. A released app reverses that priority: precompute assets and their loading boundaries so users do less work at runtime. Those constraints explain Vite's two pipelines; the trace below shows how an import moves through them.

## How It Works

### From the HTML entry to an edit

Vite starts from `index.html`, not from a JavaScript-only entry. A script such as `<script type="module" src="/src/main.tsx"></script>` gives the browser a module URL. The browser can request relative ES module URLs, but it cannot resolve a bare package import such as `import React from 'react'` by itself. Vite resolves that package, rewrites it to a browser URL, and serves a compatible dependency module.

```text
index.html → browser requests source modules → Vite resolves and transforms each request
                                         ├→ dependencies are pre-bundled and cached
                                         └→ edits update an HMR-accepted boundary
vite build → production graph → Rolldown chunks + Oxc transforms + CSS minification
```

Vite pre-bundles dependencies for two reasons: it converts CommonJS or UMD packages to ESM for the browser, and it can combine a package made of hundreds of small ESM files into fewer requests. Application source is still served on demand; dependency pre-bundling happens only in development. Vite scans imports at startup and caches optimized packages under `node_modules/.vite`. A lockfile, relevant Vite configuration, or `NODE_ENV` change invalidates that cache. If a dependency first appears only after the scan, Vite may optimize again and reload the page. Linked workspace packages are generally treated as source, so their entry points should be ESM; otherwise include them in dependency optimization.

HMR applies updates at module boundaries that accept them. Framework integrations such as React Fast Refresh handle common component edits; arbitrary edits do not preserve arbitrary application state. A changed export shape or unhandled side effect may require a full reload. The HMR API is primarily for framework and tooling authors, so application code should normally rely on the selected framework plugin.

### Why the production build is different

`vite build` runs the production pipeline and emits the files a host must serve. Dynamic imports create asynchronous chunk boundaries, while Rolldown determines the final chunk graph. Vite 8 removed object-form `manualChunks`; function-form configuration is deprecated in favor of Rolldown's `codeSplitting` options. The compatibility name `build.rollupOptions` is deprecated; use `build.rolldownOptions` for Vite 8-specific bundler options. Review the Vite migration guide before copying older configuration.

The default unbundled development server can become request-bound on a very large application. Vite 8.1's `experimental.bundledDev` mode bundles modules during development to reduce request overhead, but plugin support is still limited. Measure cold startup, a representative edit, full reload, and memory use before opting in; do not assume the experimental path is interchangeable with the default.

### Configuration and deployment boundaries

```javascript
// vite.config.js
import react from '@vitejs/plugin-react';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [react()],
  base: '/app/',
  server: {
    proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } },
  },
  build: { sourcemap: 'hidden' },
});
```

Set `base` to the public path where the built site is served; a root deployment uses `/`. `server.proxy` only belongs to the development server, so production API routing must be configured at the actual server, reverse proxy, or platform. A static single-page app also needs a host rule that sends application routes back to its HTML entry. `vite preview` is useful for checking `dist`, but it is not the production server.

The example requests hidden source maps for an error tracker. "Hidden" omits the source-map reference from generated JavaScript; the `.map` files still exist. Upload them to the tracker and exclude them from public deployment when source disclosure is not intended.

Vite transpiles TypeScript and JSX so the browser can run them; it does not type-check the TypeScript program. Run `tsc --noEmit` in the build or CI path. Likewise, build-time environment values are not runtime configuration:

```dotenv
# .env.production
VITE_API_URL=https://api.example.test
```

```javascript
const apiUrl = import.meta.env.VITE_API_URL;
```

Any `VITE_` value read by client code is embedded in client-visible output as a string. Keep secrets on a trusted server. `vite build` defaults to production mode and loads `.env.production`; `vite build --mode staging` loads `.env.staging` but still produces a production build by default. Vite `mode` selects mode-specific configuration, while `NODE_ENV` controls a separate set of production/development constants. Changing server variables after building a static site does not rewrite its JavaScript.

If a deployment removes an old hashed chunk while a tab still runs the previous entry code, a later dynamic import can fail. Vite emits a `vite:preloadError` event for this case; retain old assets for supported sessions or handle the event with a controlled reload. Serve HTML with `Cache-Control: no-cache` so clients do not keep receiving a stale entry page.

### Plugins and server rendering

Vite's plugin API shares many build hooks with Rollup and adds hooks for its development server. A `transform` hook can convert a custom resource into JavaScript; with Vite 8/Rolldown, return `moduleType: 'js'` when the resource's extension does not identify the generated module type. `configureServer` runs only for the development server, so code placed there does not automatically configure production. Check a plugin's Vite 8/Rolldown support and exercise the plugin in both `vite` and `vite build`.

Vite can support SSR development and server/client builds through its APIs, but the client `dist` folder is not an SSR server. For server-rendered routes, a framework or application server handles requests and renders HTML; if every route can be generated ahead of time, static output avoids that runtime server.

## Summary

In default development, Vite lets the browser request transformed application modules while pre-bundling packages that need compatibility or request reduction. Production uses a separate Rolldown-based output pipeline. Treat HMR acceptance, TypeScript checking, mode and runtime configuration, plugin hooks, asset retention, and hosting routes as separate contracts, and verify both development and production behavior.

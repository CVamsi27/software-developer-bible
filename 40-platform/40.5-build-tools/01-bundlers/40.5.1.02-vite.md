# Vite

## Definition

**Vite** is a development server and production build tool. Its standard development flow serves source modules through native browser ESM, transforming them on demand; its production flow bundles and optimizes the application for deployment.

> **Textbook Definition:** Vite is a web development and build tool that integrates a development server, module transformation, and production asset generation through framework integrations and a configurable plugin pipeline.

This chapter targets **Vite 8**; the latest stable minor checked is 8.3. Vite 5–7 used esbuild for dependency optimization/transforms and Rollup for production bundling. Vite 8 uses **Rolldown** for dependency optimization and bundling, **Oxc** for JavaScript transforms/minification, and Lightning CSS for CSS minification. The dev/build distinction survives that engine change.

## First Principles

1. A browser can request modules as it traverses imports. Development can defer transforms until a module is needed instead of building every route before serving anything.
2. Dependency packages can contain CommonJS or many small files. Pre-bundling those dependencies avoids compatibility problems and excessive requests, so “unbundled source” does not mean “no bundling anywhere.”
3. A deployed site has different costs: network waterfalls, cache lifetimes, and unused code matter more than edit latency. Production therefore needs a separate optimization pass.

## Why It Matters

Vite provides a short feedback loop for apps and libraries while exposing plugins for framework transforms, HMR, and SSR. Startup and HMR still depend on dependency scans, imported modules, plugins, and invalidation scope; they are not constant-time guarantees.

## How It Works

```text
Development: HTML -> browser imports -> dev server resolves/transforms modules
                                 -> optimized dependency modules
                                 -> HMR updates affected consumers
Production: entry graph -> Rolldown -> split/minified/hashed assets
```

The two flows can expose different resolution and CommonJS interop bugs. Verify both `vite` and `vite build`; the development proxy is not a production API gateway.

## Code Examples

### A small React application configuration

```javascript
// vite.config.js (ESM)
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import { fileURLToPath, URL } from 'node:url';

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
  server: {
    port: 3000,
    proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } },
  },
  build: {
    outDir: 'dist',
    sourcemap: 'hidden',
  },
});
```

`index.html` is an entry, and imported assets participate in the graph. React JSX belongs in `.jsx` or `.tsx` files. Vue and Svelte require their framework plugins, not the React plugin.

Hidden source maps omit the bundle's `sourceMappingURL` comment; the `.map` files still exist. Upload them to the error tracker and exclude them from public deployment when that is the intended policy.

### Environment variables

```dotenv
# .env.development
VITE_API_URL=http://localhost:8080
```

```javascript
const apiUrl = import.meta.env.VITE_API_URL;
```

Variables exposed through `VITE_` are embedded in client output. They are configuration, not a place to store secrets. Production build mode selects `.env.production`; changing server environment variables after a static build does not rewrite the already emitted JavaScript.

### A format transform plugin

```javascript
// my-plugin.js
export default function myPlugin() {
  return {
    name: 'custom-text',
    transform(code, id) {
      if (!id.endsWith('.custom')) return;
      return {
        code: `export default ${JSON.stringify(code)}`,
        map: null,
        moduleType: 'js',
      };
    },
  };
}
```

Vite 8/Rolldown may infer module types from extensions, so a plugin that emits JavaScript from another format must make that output type clear. Development-only `configureServer` middleware does not become a production service.

## Real-World Use Cases

Use Vite for framework SPAs, library builds, and frameworks built on its tooling. SSR requires a framework or server integration: building an SPA and deploying `dist` alone does not provide server rendering.

## Common Mistakes

- Publishing `VITE_` secrets or relying on the development proxy after deployment.
- Treating TypeScript transformation as type checking; run `tsc --noEmit` separately.
- Copying Vite 7 object-form `output.manualChunks` into Vite 8: that form was removed. `build.rollupOptions` is a deprecated compatibility name; current configuration uses `build.rolldownOptions`.
- Assuming hidden maps reduce JavaScript payload or prevent public map access by themselves.
- Serving a single-page app without a route fallback, or applying immutable caching to the entry HTML.

## Best Practices

Start with default chunking and measure before overriding it. Pin the toolchain, test a production preview, choose an explicit browser target when the audience requires it, and let the hosting layer handle compression and cache headers. Keep framework plugins aligned with the Vite version.

## Summary

Vite separates on-demand development work from deployment optimization. Vite 8 changed its engines to Rolldown/Oxc; older Rollup/esbuild examples need a version label or migration. Verify type checking, environment exposure, production routing, and cache policy alongside build speed.

# Turbopack

An edit to a shared component can affect a browser bundle, a server render, and a React Server Component payload. Recompiling every route after each save wastes work; reusing a result after one of its real inputs changed produces stale output. Turbopack is designed to find the smaller set of computations that must run again.

## Definition

Turbopack is the incremental bundler integrated into Next.js. It resolves modules, transforms code, and produces the JavaScript, CSS, and assets needed for development and production. It tracks dependencies between computations so that unchanged work can be reused. **Turborepo** is a separate task runner for coordinating scripts across packages; it can cache tasks that happen to invoke Next.js and Turbopack.

> **Textbook Definition:** An incremental bundler models compilation as a dependency graph of computations. When an input changes, it invalidates results that depend on that input and reuses results whose complete inputs remain unchanged, while generating distinct outputs for each target environment.

This chapter targets Next.js 16.4. Turbopack is the default for both `next dev` and `next build`. If an application still depends on an unsupported Webpack plugin, Next.js can use Webpack for that command with `--webpack`; migrating to Turbopack requires testing the integration, not merely renaming its configuration.

## First Principles

A compilation result depends on more than a source file: resolution rules, transforms, environment, and target all affect its output. A change should invalidate the computations that depend on its changed inputs, then propagate only as far as needed — fine-grained dependency tracking makes reuse possible, while correct invalidation makes that reuse safe. Client code, server code, and React Server Component output have different runtime contracts, so a shared source file can produce different results for different targets even when some earlier work is reusable.

## How It Works

### Follow a change through the graph

```text
route request or source edit
  -> resolve modules and select client/server/RSC targets
  -> reuse valid transforms and recompute invalidated dependencies
  -> update the active route in development or emit production assets
```

The development server compiles routes as they are requested, so the first visit to a route can still pay its initial compilation cost. A later edit should do less work when the changed module affects only part of the graph. In Next.js 16.4, server updates are applied when a route is requested rather than eagerly rebuilding every previously visited route. This reduces unnecessary work; it does not make an expensive dependency or a broad invalidation free.

### The cache has two lifetimes

An in-process cache can reuse computations until the process exits. A filesystem cache can also restore compiler work after a restart. Next.js 16.1 made Turbopack's development filesystem cache stable and enabled it by default. The Next.js 16.3 release notes say filesystem caching for `next build` is enabled by default, while the current Turbopack API reference still describes the build option as opt-in. Because those official sources conflict, verify the behavior against the documentation bundled with the exact Next.js version before changing CI configuration. When enabled, the build cache lives under `.next/cache` and helps only when the build environment preserves that directory between runs. A CI job that removes it starts cold each time. Keep cold and warm measurements separate, and make the CI cache key sensitive to the lockfile, Next.js version, and build configuration.

Next.js 16.4 reduces the disk cache size and uses a shared runtime chunk across routes, so historical size and timing measurements may describe a different output strategy. Its experimental `turbopackLazyDynamicImports` option delays compilation of client-side `import()` modules until requested, but some `next/dynamic` imports remain eager. If lazy compilation is a requirement, test the exact import path instead of inferring behavior from the option name.

### Keep migration compatibility explicit

Turbopack has built-in CSS and modern JavaScript support. The `turbopack.rules` option can apply supported Webpack loaders to other file types, but only a subset of the Webpack loader API is implemented and loaders must produce JavaScript. Webpack plugins do not run under Turbopack.

```typescript
// next.config.ts — install @svgr/webpack before using this rule
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  turbopack: {
    rules: {
      '*.svg': {
        loaders: ['@svgr/webpack'],
        as: '*.js',
      },
    },
    resolveAlias: { '@components': './src/components' },
  },
};

export default nextConfig;
```

Test the rule by importing an SVG as a component in a real route, then run both `next dev` and `next build`. `turbopack.resolveAlias` adds a bundler-level resolution rule; Next.js already reads TypeScript `paths`, so do not add a duplicate alias without a reason. If setting `resolveExtensions`, include the default extensions you still need because the option replaces the default list. Next.js 16 uses `turbopack`; the older `experimental.turbo` key is removed. A detected Babel configuration is handled automatically, so a Babel config alone does not require switching back to Webpack.

### Measure the actual task

Compare equivalent runs on the same machine and project state: cold startup, first route compilation, save-to-refresh time, peak memory, and production build. For a cold comparison, clear `.next`; for a warm comparison, restore the same valid cache and record that fact. Separate Turbopack compile time from type checking and other build work before attributing a slower `next build` to the bundler.

To inspect a slow development route or update, collect a Turbopack trace:

```bash
NEXT_TURBOPACK_TRACING=1 npx next dev
```

Reproduce the slow route or edit, stop the server, then inspect `.next/dev/trace-turbopack` with `npx next internal trace`. The trace can contain local paths and workload details; review it before sharing. A trace explains where time went in that run — it does not by itself prove that a migration improves user-facing performance.

## Summary

Turbopack incrementally compiles Next.js module graphs and reuses valid work across edits and, when preserved, filesystem caches. Next.js 16.4 uses it by default for development and production. Measure cold and warm work separately, test every needed loader in both commands, and keep `--webpack` only while a required integration is unsupported.

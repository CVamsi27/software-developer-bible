# Turbopack

## TL;DR

Turbopack is Vercel's **Rust bundler built on an incremental computation engine**: instead of rebuilding the graph, it tracks dependencies at function granularity and recomputes only what a change invalidated. It is the intended Webpack successor inside Next.js and is strongest in development; production behavior and the general-purpose plugin story are the parts still maturing, so adoption should track the framework's own defaults rather than be a separate migration project.

---

## First Principles

Turbopack is Webpack's graph model in Rust with incremental computation:

1. **The insight is persistent incremental caching**: every transform is a cached, content-addressed function — restart and unchanged work isn't redone. Incrementality is why Rust speed survives large graphs.
2. **Same graph semantics as webpack** (loaders→transforms, plugins) — designed as the drop-in future for Next.js (→ 40.5.1.01's model, re-engineered), which is why its surface area is framework-shaped.

## Definition
Turbopack is an incremental bundler optimized for JavaScript and TypeScript, built in Rust by Vercel. It's designed as a successor to Webpack, focusing on performance through incremental computation and caching.

## Why Do We Need It?
Traditional bundlers rebuild entire dependency graphs on changes, causing slow development cycles in large applications. Turbopack addresses this by:

- **Incremental Bundling**: Only recomputes what changed
- **Rust Performance**: 10x faster than Webpack, 700x faster than Vite for large apps
- **Incremental Computation**: Remembers work done across sessions
- **Next.js Integration**: Optimized for Next.js applications

## Code Examples

### Turbopack vs Turborepo (The Critical Distinction)

| Aspect | Turbopack (`next dev --turbo`) | Turborepo (`turbo run build`) |
| ----------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| **What it is** | Incremental asset/module **bundler** in Rust | Monorepo build **task orchestrator** in Go/Rust |
| **Operates on** | JavaScript, TypeScript, CSS, asset dependency graphs | Package workspace tasks (`build`, `test`, `lint`) |
| **Analogy** | Webpack, Vite, Rollup, esbuild, Rspack | Nx, Lerna, Bazel |
| **Primary home** | Inside Next.js (`40.5.1.03`) | Monorepo root (`turbo.json`) (`40.8.02`) |

### Next.js Turbopack Configuration

Turbopack in Next.js is configured via the `turbopack` (or legacy `experimental.turbo`) key in `next.config.js` or `next.config.ts`:

```typescript
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  // Turbopack bundler options
  turbopack: {
    // Custom loader rules (translating Webpack loaders to Turbopack)
    rules: {
      '*.svg': {
        loaders: ['@svgr/webpack'],
        as: '*.js',
      },
      '*.mdx': {
        loaders: ['@mdx-js/loader'],
        as: '*.jsx',
      },
    },
    // Module path aliases resolved natively in Rust
    resolveAlias: {
      '@components': './src/components',
      '@shared-types': './packages/types/src',
      // Dynamic aliasing or browser shims
      'canvas': false, // Exclude server-only or unsupported modules from client bundle
    },
    // Custom file extension resolution order
    resolveExtensions: [
      '.tsx',
      '.ts',
      '.jsx',
      '.js',
      '.json',
    ],
  },
};

export default nextConfig;
```

### Running Turbopack

```bash
# Start local development server with Turbopack incremental HMR
npx next dev --turbo

# Run production build with Turbopack (Next.js 15+)
npx next build --turbo

# Profile Turbopack memory and compile times
npx next dev --turbo --experimental-turbo-timing
```

## Real-World Use Cases

1. **Large Next.js Codebases**: Eliminates multi-minute cold starts and sluggish HMR when projects exceed 5,000 modules.
2. **Design System & Component Library Development**: Instant feedback during live component iteration without restarting bundler processes.
3. **Heavy MDX / Content Platforms**: Content-addressed incremental caching ensures updating a single article recompiles only that article's subtree.
4. **Monorepo Next.js Applications**: Fast local iteration across shared internal packages without requiring pre-compilation steps.

## Common Mistakes

1. **Confusing Turbopack with Turborepo**: Turbopack is the Rust bundler for modules; Turborepo is the workspace orchestrator that runs scripts.
2. **Expecting 100% Webpack plugin parity**: Turbopack does not run arbitrary Webpack AST-mutating plugins; loaders must be adapted via `turbopack.rules`.
3. **Using Node-only modules in client bundles**: Relying on Webpack 4 automatic polyfills (`crypto`, `stream`); Turbopack requires explicit browser equivalents or resolve aliases.
4. **Hardcoding custom Babel transforms**: Turbopack uses SWC in Rust; custom Babel plugins should be migrated to SWC plugins or Next.js compiler options.

## Best Practices

1. **Adopt incrementally in development**: Use `next dev --turbo` during everyday development to enjoy instant HMR while keeping standard `next build` for stable CI pipelines until fully verified.
2. **Minimize custom loader chains**: Rely on Next.js native features (built-in CSS Modules, Tailwind, Next Image) rather than bespoke Webpack loaders.
3. **Verify alias definitions**: Keep `resolveAlias` synchronized between `tsconfig.json` paths and `next.config.ts`.
4. **Profile memory usage**: For massive monorepos, track heap usage to ensure the Rust daemon runs efficiently alongside the Node.js runtime.

## Performance Considerations

- **Function-Level Granularity**: The `turbo-tasks` engine stores the outputs of pure functions in memory. If function inputs have not changed, execution is skipped entirely.
- **Persistent Caching**: Cache keys are content-addressed hashes of source code and build parameters, persisting across server restarts.
- **Multithreaded Parsing**: Rust utilizes all available CPU cores for simultaneous parallel module parsing and transform passes.

## Summary

Turbopack is Vercel's Rust-based bundler engineered on the `turbo-tasks` reactive incremental computation engine. Designed as the high-speed successor to Webpack within the Next.js ecosystem, it delivers sub-10ms HMR and fast cold starts by never re-evaluating unchanged subtrees. In senior interviews, clearly distinguish Turbopack (the module bundler) from Turborepo (the monorepo task runner), and contrast its function-level incremental architecture with Vite's unbundled ESM and Rspack's Webpack API compatibility.

## Cheat Sheet
```text
TURBOPACK CHEAT SHEET
============================================================

POSITIONING:
  • Successor to Webpack, written in Rust
  • Built by Vercel, used in Next.js (--turbo flag)
  • Alpha: dev server only, no production builds yet
  • 10x faster Webpack, ~700x faster Vite (cold start large apps)

INCREMENTAL COMPUTATION:
  • Content-addressable storage (cache by file hash)
  • Dependency tracking at module level (not file level)
  • Recomputes only the changed subtree
  • Persistent cache survives dev server restarts

NEXT.JS USAGE:
  • next dev --turbo (enable Turbopack)
  • next build --turbo (production, beta)
  • Supported: pages/app router, CSS modules, images
  • Limitations: some webpack plugins, Storybook

INTERVIEW TIPS:
  • Explain incremental computation vs full rebuild
  • Discuss Rust vs Go vs Node for bundlers
  • Compare Turbopack vs Rspack vs Vite
  • Know Turbopack is dev-first, Webpack still prod-stable
```

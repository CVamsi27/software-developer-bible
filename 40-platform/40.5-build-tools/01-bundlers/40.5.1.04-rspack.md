# Rspack

## Definition

Rspack is a Rust-based module bundler with broad webpack configuration and extension compatibility. Rsbuild wraps it in application-oriented defaults; Rspress builds documentation sites on that ecosystem.

> **Textbook Definition:** Rspack constructs and compiles application module graphs into deployable assets while implementing much of webpack's configuration, loader and plugin model.

## First Principles

An existing application depends on extension behavior as well as emitted JavaScript. Reusing familiar interfaces reduces migration work only where behavior remains compatible. Build throughput also depends on graph traversal, transforms, cache reuse and extension overhead; an implementation language alone cannot predict the gain.

## Why It Matters

Rspack is a candidate when webpack-compatible integration matters and a measured build bottleneck justifies migration. It is not a universal drop-in replacement or a guaranteed 5–10x speedup. A custom plugin using webpack internals may require replacement even if standard loader rules work.

## How It Works

The core resolves a graph and chooses output chunks. Built-in SWC transforms can handle supported TypeScript/JSX syntax; JavaScript loaders and plugins still execute through their integration interfaces. Type stripping is not type checking. CSS and cache configuration depend on the Rspack major version: do not transfer an old experiments block blindly.

## Example: Compile One Typed Module

Install `@rspack/core@2` in a disposable directory. Save:

```typescript
// src/index.ts
const greeting: string = 'rspack fixture';
console.log(greeting);
```

```javascript
// build.cjs
const path = require('node:path');
const { rspack } = require('@rspack/core');
const compiler = rspack({
  mode: 'production',
  entry: './src/index.ts',
  output: { path: path.resolve(__dirname, 'dist'), filename: 'main.js', clean: true },
  module: { rules: [{
    test: /\.ts$/,
    use: { loader: 'builtin:swc-loader', options: {
      jsc: { parser: { syntax: 'typescript' }, target: 'es2020' },
    } },
  }] },
});
compiler.run((error, stats) => {
  const failed = error || stats?.hasErrors();
  if (failed) console.error(error || stats.toString({ colors: false }));
  compiler.close(closeError => {
    if (closeError) console.error(closeError);
    if (failed || closeError) process.exitCode = 1;
  });
});
```

```bash
node build.cjs
node dist/main.js
```

This complete fixture exercises the built-in transform and emitted code. It does not prove application plugins, CSS, federation or persistent cache behavior. Verify those integrations separately on the deployed major version.

## Real-World Decisions

Inventory webpack extensions and compare their compatibility documentation before modifying configuration. Migrate one application/route set first, compare emitted behavior and source maps, then benchmark equivalent cold and warm workloads. Keep fallback configuration until the required production paths pass.

Federation remains a runtime distributed dependency system: remote availability, version negotiation and shared React identity need tests beyond compilation. Prefer a documented federation integration over assuming the plugin is exported identically by every major version.

## Mistakes and Best Practices

Do not copy fixed module-count speed tables without workload evidence. Choose SWC only if its semantics/plugins meet the requirement; Babel can remain for required transforms. Use the current cache API and include transform configuration/environment in cache identity. Renaming a config file is a migration step, not an acceptance test.

## Summary

Rspack offers a webpack-oriented compatibility path with a different core implementation. Decide using actual integration behavior, emitted output and measured build cost. Rsbuild can simplify application setup, while direct Rspack suits deliberate low-level configuration.

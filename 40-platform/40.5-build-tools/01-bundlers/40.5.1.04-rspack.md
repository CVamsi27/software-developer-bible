# Rspack

A team with a large Webpack application may want faster builds without replacing every loader and plugin. Rspack keeps much of the Webpack 5 configuration model, but compatibility is a migration question to prove against the application's actual extensions and output—not a promise that any Webpack config works unchanged.

## Definition

Rspack is a Rust-based module bundler with a Webpack-oriented configuration, loader and plugin API. It resolves a module graph, transforms its inputs and emits assets for an application. **Rsbuild** adds application-level defaults on top of Rspack; direct Rspack configuration is useful when the application needs lower-level control.

> **Textbook Definition:** A module bundler constructs a dependency graph from entry points, applies configured transformations and build hooks, then emits deployable assets. Rspack implements this bundling model with a Rust core and compatibility interfaces for much of the Webpack ecosystem.

This chapter targets Rspack 2.2, the latest stable minor checked on 14 October 2026. `@rspack/core@2` requires Node.js `^20.19.0 || >=22.12.0`; keep local development, CI and production builds on supported versions.

## First Principles

1. A migration must preserve the application contract: which modules resolve, what each transform emits, which hooks run, and what the browser or server loads.
2. Compatibility reduces rewrite cost only when the required feature behaves the same. Matching option names do not prove matching semantics, especially for plugins that use bundler internals.
3. Build speed depends on graph work, transforms, cache hits, output optimization and plugin overhead. Rust changes the implementation; it does not establish the speedup for a particular project.

## Follow one module into the output

The build starts at an entry, resolves its imports and sends each file through matching rules. Rspack's built-in SWC loader can remove TypeScript syntax and emit JavaScript. That transform does not type-check the full program, so run `tsc --noEmit` separately when type correctness is a build requirement.

This isolated fixture compiles one typed module and executes the emitted file:

```typescript
// src/index.ts
const greeting: string = 'rspack fixture';
console.log(greeting);
```

```javascript
// build.cjs
const path = require('node:path');
const { rspack } = require('@rspack/core');

const compiler = rspack({
  mode: 'production',
  entry: './src/index.ts',
  output: { path: path.resolve(__dirname, 'dist'), filename: 'main.js', clean: true },
  module: {
    rules: [{
      test: /\.ts$/,
      use: {
        loader: 'builtin:swc-loader',
        options: { jsc: { parser: { syntax: 'typescript' }, target: 'es2020' } },
      },
    }],
  },
});

compiler.run((error, stats) => {
  const failed = Boolean(error) || !stats || stats.hasErrors();
  if (error) console.error(error);
  if (stats?.hasErrors()) console.error(stats.toString({ colors: false }));

  compiler.close(closeError => {
    if (closeError) console.error(closeError);
    if (failed || closeError) process.exitCode = 1;
  });
});
```

```bash
node build.cjs
node dist/main.js
```

The first command must fail for a compiler error or compilation error, and it closes the compiler so Rspack can finish low-priority work. This fixture proves only that this entry, rule and output run; it says nothing about the application's CSS, plugins, source maps or federation behavior.

## Keep cache mechanisms separate

Rspack 2 has two independent reuse mechanisms. `incremental` preserves work between development rebuilds and updates affected passes; `cache` stores fine-grained compilation results in memory or on disk. In v2, cache defaults to memory in development and off in production. Use `cache: { type: 'persistent' }` when later processes should reuse disk results. For a fully cold comparison, disable both `cache` and `incremental`; turning off one does not turn off the other.

Webpack's filesystem-cache settings do not map by renaming the cache object. Rspack persistent cache uses `type: 'persistent'`; dependencies that must invalidate cached results belong in `cache.buildDependencies`. With the Rspack CLI, the config file is added automatically, but other externally loaded build inputs still need to be accounted for. Compare cold and warm builds separately and confirm that CI restores the intended cache before attributing a speedup to the bundler.

## Migrate the integration, not just the config

Rspack supports most Webpack loaders and many Webpack plugins, but neither set is universal. Check the current compatibility list for the exact package and version. A plugin that imports `webpack/lib/*` or depends on a compiler hook can still fail even when ordinary rules work. Replace only the incompatible integration, then test real production routes in both development and production builds.

Module Federation needs runtime tests beyond compilation: remote availability, version negotiation and shared React identity can fail after the bundle succeeds. Rsbuild may be simpler when its application defaults fit; use direct Rspack where its lower-level configuration is required. Keep a tested Webpack fallback until required output and runtime behavior are verified.

## Summary

Rspack offers a Rust implementation with broad Webpack-oriented compatibility. Migrate against the actual plugin and loader inventory, keep `incremental` and persistent cache behavior distinct, and compare equivalent cold and warm workloads. A successful fixture or faster compile proves only the path it exercises.

# Babel

A Babel build can succeed while the deployed page still fails: the compiler may rewrite optional chaining, but it cannot make an old browser provide `fetch`. Babel is a compiler stage, not a compatibility guarantee for every syntax feature and runtime API.

## Definition

Babel parses JavaScript and related syntax, transforms the parsed program according to configured plugins and targets, then generates JavaScript and optional source maps. It can also remove TypeScript or Flow annotations, but that does not type-check the program.

> **Textbook Definition:** Babel is a source-to-source compiler toolkit that parses input into an abstract syntax tree, applies configurable transformations to that tree, and generates target JavaScript and source maps.

## First Principles

The emitted program must satisfy three separate contracts: the target runtime can parse its syntax, the APIs it calls exist at runtime, and any static type rules have been checked. A syntax transform can address the first contract. Polyfills may address a selected part of the second; a checker such as TypeScript addresses the third. Treating these as one "compile" step hides production failures.

## How It Works

### 1. Follow a Class Through Babel

```text
source → parser → AST + scope/bindings → configured visitors → JavaScript + source map
```

An abstract syntax tree (AST) represents code as nodes rather than text. Babel plugins can use node paths and scope bindings to change a declaration without accidentally rewriting an unrelated identifier with the same spelling. Plugins are applied before presets; plugins run first to last, while presets run last to first. Ordering and traversal interactions can affect output, so inspect the resolved configuration when a test runner and bundler emit different code.

Install `@babel/core@^8` and `@babel/preset-env@^8` in a disposable project, then save this as `transform.mjs`. Babel 8 requires Node.js `^22.18.0 || >=24.11.0` and ships as ESM.

```javascript
import assert from 'node:assert/strict';
import vm from 'node:vm';
import { transformSync } from '@babel/core';

const source = `
class Counter {
  #value = 0;
  increment = () => ++this.#value;
}
globalThis.result = new Counter().increment();
`;

const { code, map } = transformSync(source, {
  configFile: false,
  babelrc: false,
  filename: 'counter.js',
  presets: [['@babel/preset-env', { targets: { ie: '11' } }]],
  sourceMaps: true,
});

const sandbox = {};
vm.runInNewContext(code, sandbox);
assert.equal(sandbox.result, 1);
assert(map.sources.includes('counter.js'));
```

The generated helper code preserves the private-field behavior in this test. The IE 11 target asks Babel to lower syntax; execution happens in Node, so this is not an IE 11 browser test and does not prove that browser APIs are polyfilled.

### 2. Set the Output and Runtime Contract

In Babel 8, `@babel/preset-env` uses Browserslist's `defaults` when no targets are configured. It no longer lowers everything to ES5 or converts modules to CommonJS by default. Set explicit targets when the product has a defined support policy; set `modules: 'commonjs'` only when the consuming tool requires that format. A workspace's `.browserslistrc`, config root, and caller supplied by a framework or bundler can affect the effective configuration. In a monorepo, a nested command may need `rootMode: 'upward'` to find the project-wide config; `.babelrc` discovery follows package-boundary rules. Compare the resolved config from the actual test and build commands before debugging output differences.

Polyfills are a separate decision. Babel 8 removed `useBuiltIns` and `corejs` from `@babel/preset-env`, and removed `corejs` from `@babel/plugin-transform-runtime`. Use `babel-plugin-polyfill-corejs3` when the project needs Babel-managed `core-js` injection, and pin the `core-js` minor version it can provide. Babel 7 projects may still use the older preset options; do not copy those settings into a Babel 8 configuration. Even injected polyfills do not cover every browser API, such as `fetch` in environments where it is absent. For helper deduplication, `@babel/plugin-transform-runtime` imports helpers from `@babel/runtime`; declare that runtime dependency, especially when publishing a library. It does not supply host APIs.

Type erasure is separate too. Babel can strip TypeScript syntax, but it does not check type relationships or emit public declarations. Keep the project's type-check and declaration-generation steps explicit.

### 3. Decide When Babel Belongs in the Pipeline

Babel is useful when a project needs its AST plugin ecosystem, a specific proposal transform, codemods, or framework integration. For a one-time codemod, validate representative binding and syntax cases, then remove the temporary transform. For a library, document its output target and runtime dependencies so consumers know which syntax and APIs they must support. For an application, choose targets from the actual audience and measure the resulting bundle rather than assuming every transform has a fixed cost. Any transform cache must include the resolved configuration and target inputs that affect emitted code.

## Summary

Babel parses, transforms, and prints code according to an explicit output contract. Targets govern syntax lowering; a polyfill strategy governs selected runtime APIs; a type checker governs static relationships. Babel 8 defaults and configuration differ from Babel 7, so make the major-version boundary explicit during upgrades.

# Babel

## TL;DR

Babel is a **JavaScript compiler, not a bundler**: it parses to an AST, runs transform plugins, and generates code — which is what makes `@babel/preset-env` (targets from browserslist) and custom syntax plugins possible. In a modern stack it is mostly the *compatibility layer* under the bundler, and the two settings that matter are your target list and whether polyfills come from `core-js` (globals, use sparingly) or `@babel/plugin-transform-runtime` (no global pollution). Cost is build time; use it where downleveling is genuinely required.

---

## First Principles

Babel is source-to-source transpilation as a plugin system:

1. **The AST is the interface**: parse → transform → generate; every feature (JSX, TypeScript strip, proposals) is a plugin over the same tree. The pattern (→ 30.1.4.10's visitor) at compiler scale.
2. **Its role shrank by its own success**: the JS features it polyfilled became native; TS became the layer; bundlers absorbed transforms (→ 40.5.2.02). Babel remains for the newest proposals and AST tooling — the frontier's staging ground.
3. **Cost awareness is the senior skill**: Babel transforms are per-file, single-threaded compared to esbuild/SWC — knowing *why* your build is slow often means finding Babel in the graph.

## Definition

**Babel** is a JavaScript compiler that transforms modern ES6+ code into backward-compatible JavaScript for older browsers. It processes syntax transformation (arrow functions, optional chaining), polyfills (Promise, Array.flatMap), and is extensible via plugins and presets.

## Why Do We Need It?

1. **Browser compatibility**: Use modern syntax while supporting IE11 and older browsers
2. **Experimental features**: Try stage-0/1 proposals before standardization
3. **Custom transforms**: JSX, TypeScript (without tsc), Flow, decorators
4. **Polyfills**: `core-js` bridges runtime gaps for new APIs
5. **Optimization**: Minification, dead code elimination via plugins

## How It Works

### The pipeline: parse → transform → generate

Babel parses source into an **AST** (ESTree-adjacent, produced by its own parser), walks the tree with **visitors**, and prints it back out. Plugins are pure visitor objects: `visitor.FunctionDeclaration(path) {...}` receives every function declaration node with `path` — the node *plus* scope, parent links, and traversal control (`path.skip()`, `path.replaceWith()`). Scope analysis is what makes transforms correct: renaming a variable must check its binding, not its name. Code is then *generated* from the tree — which is why Babel's output historically looked verbose: generator templates and inline helpers. Helpers dedupe via `@babel/plugin-transform-runtime` (helpers imported from a module instead of inlined per file — the difference between a 200 KB and a 40 KB bundle of small files).

### Config resolution: the part that bites monorepos

Babel merges configs from **two roots**: project-wide `babel.config.*` (found from the CWD upward — *root*) and file-relative `.babelrc.*` (found in each package, *file-relative*, and only applying to files under it). `babelrcRoots` controls which packages' `.babelrc` files are even considered — without it, a monorepo's `packages/*` configs are silently ignored. The senior defaults: one `babel.config.json` at the repo root, `presets` ordered bottom-up, `plugins` before presets, and `caller`-based conditionals when the same config must serve Jest and webpack differently.

### The polyfill model

Syntax transforms need nothing but output; *APIs* (`Array.flat`, `Promise.allSettled`) need runtime libraries. `useBuiltIns: 'usage'` injects imports for exactly the builtins a file references, per your browserslist targets — the minimal-and-correct setting; `'entry'` imports the full polyfill set at one designated entry. `corejs: 3` pins the polyfill library version. The security-conscious alternative: `transform-runtime` remaps APIs to non-global module imports — no `window.Promise` mutation, which matters for libraries shipped to other people's pages.

## Code Examples

### Configuration

```json
// babel.config.json
{
  "presets": [
    ["@babel/preset-env", {
      "targets": "> 0.25%, not dead",
      "useBuiltIns": "usage",
      "corejs": 3
    }],
    ["@babel/preset-react", {
      "runtime": "automatic"
    }],
    ["@babel/preset-typescript"]
  ],
  "plugins": [
    "@babel/plugin-transform-runtime",
    ["@babel/plugin-proposal-decorators", { "version": "2023-05" }]
  ]
}
```

### Transform Example

```javascript
// Input (ES6+)
const double = (x) => x * 2;
const obj = { a: 1, b: 2 };
const merged = { ...obj, c: 3 };
class Animal {
  #name;
  constructor(name) { this.#name = name; }
  speak() { console.log(`${this.#name} speaks`); }
}

// Output (ES5)
var double = function double(x) { return x * 2; };
var obj = { a: 1, b: 2 };
var merged = Object.assign({}, obj, { c: 3 });
function Animal(name) { this._name = name; }
Animal.prototype.speak = function() { console.log(this._name + ' speaks'); };
```

## Real-World Usage

- **The modern role is selective**: bundlers with native TS/JSX (→ 40.5.2.02) handle the 95%, and Babel enters the graph for what they can't yet do — decorators with current-stage semantics, custom proposal plugins, or a bespoke macro/codemod. Vite's `@vitejs/plugin-react` still runs Babel for fast refresh + JSX; the esbuild path (`plugin-react-swc`) trades plugin reach for speed.
- **Jest transforms**: `babel-jest` is the default transformer — in large repos the Babel transform (not the test framework) dominates test startup time, which is why `@swc/jest` swaps are the first win in test-latency audits.
- **Codemods are Babel's cleanest superpower**: `jscodeshift` on the Babel AST rewrites APIs across hundreds of files with scope-correct renames — the mechanism behind most large React migrations. One-off transform, not a build step: the AST pays for itself where grep-and-pray fails.
- **Debug a slow build by finding Babel**: `browserslist` targets wider than your real audience (a lingering `IE 11`) silently re-adds the heaviest downleveling; `npx browserslist` prints the resolved set, and deleting stale entries is often a double-digit build-time win.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Omitting `@babel/plugin-transform-runtime` | Helpers like `_extends` duplicate across every file; runtime imports them from a module |
| Using `useBuiltIns: 'entry'` without modern browserslist | Ships megabytes of obsolete polyfills; use `useBuiltIns: 'usage'` to import on demand |
| Relying on `.babelrc` instead of `babel.config.json` in monorepos | File-relative configs fail across workspaces; use root `babel.config.json` with `babelrcRoots` |
| Transpiling TS with Babel without `tsc --noEmit` in CI | Babel strips types without validating them; always pair with `tsc --noEmit` in CI |
| Running `babel-loader` without filesystem caching | Webpack re-parses every AST on rebuilds; enable `cacheDirectory: true` in loader options |
| Misunderstanding preset execution order | Plugins run first (top to bottom); Presets run reversed (bottom to top / right to left) |

## Best Practices

1. **Use `babel.config.json`** (project-wide) over `.babelrc` (file-relative)
2. **Set `useBuiltIns: 'usage'`** for minimal polyfills
3. **Pin `core-js` version** and install as dependency
4. **Use `@babel/plugin-transform-runtime`** to avoid helper duplication
5. **Cache Babel output** (`babel-loader` cacheDirectory in webpack)

## Summary

- Babel is a JavaScript compiler that transforms modern JS/TS code into backwards-compatible versions
- Presets (@babel/preset-env, @babel/preset-react, @babel/preset-typescript) configure transformation rules
- Plugins enable fine-grained control over specific syntax transformations and optimizations
- Polyfilling via core-js and @babel/polyfill adds runtime support for missing browser features
- Babel integrates with Webpack, Vite, and other bundlers through loader/plugin interfaces

## Cheat Sheet
```text
BABEL CHEAT SHEET
============================================================

PURPOSE:
  • Transform modern JS/TS to backward-compatible JS
  • No type-checking (use tsc for that)
  • No bundling (use webpack/vite/rollup)
  • Polyfill missing runtime features (core-js)

PRESETS (composable plugin bundles):
  • @babel/preset-env -> ES20XX down-level per browserslist
  • @babel/preset-react -> JSX -> React.createElement
  • @babel/preset-typescript -> strip TS types
  • @babel/preset-flow -> strip Flow types

PLUGINS (single transformations):
  • @babel/plugin-transform-runtime (avoid helper duplication)
  • @babel/plugin-proposal-* (stage 0-3 proposals)
  • @babel/plugin-transform-class-properties

CONFIG FILES:
  • babel.config.json -> project-wide, monorepo root
  • .babelrc -> file-relative, single package
  • babel.config.js -> programmatic config

POLYFILLS:
  • core-js + @babel/preset-env useBuiltIns: 'usage' (auto)
  • 'entry' (full set) vs 'usage' (minimal)
  • @babel/polyfill (deprecated, use core-js directly)
  • Modern: prefer browser polyfills over heavy babel-runtime
```

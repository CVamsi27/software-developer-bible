# ESBuild & SWC

## Definition

**ESBuild** and **SWC** are next-generation JavaScript/TypeScript bundlers and compilers written in Go and Rust respectively. They offer 10-100x faster performance than traditional tools like Babel and Webpack by leveraging native code and parallel processing.

| Feature | ESBuild | SWC |
| ------------- | :-----------------------: | :------------------------: |
| Language | Go | Rust |
| Speeds | 10-100x Babel | 20-50x Babel |
| Bundling | Built-in (ESM, CJS, IIFE) | Via `spack` (experimental) |
| Minification | Built-in | Built-in |
| TypeScript | Transpile only (no check) | Transpile only (no check) |
| JSX | Built-in (React, Preact) | Built-in (React, Preact) |
| Plugins | Yes (JS / Go API) | Yes (WASM / Rust) |
| Target Output | Modern (ES2015+) | Modern & downlevel (ES5) |

## First Principles

esbuild/SWC rewrote the toolchain for the multicore era:

1. **Language + architecture, both**: Go/Rust parallelism × from-scratch design (no plugin API tax, minimal AST) = 10–100× transforms. The lesson: the old tools' slowness was architectural, not JavaScript's.
2. **The trade is extensibility**: few plugins, API surfaces frozen narrow — they cover the 95% (TS, JSX, minify) and leave the exotic to overlay tools (→ 40.5.2.01 for the long tail).
3. **They became *components*, not products**: Vite's deps optimizer, Next's compiler, Jest's transformer — the fast engine underneath everyone's tool of choice.

## Why Do We Need It?

1. **Build speed**: Sub-second rebuilds in development
2. **Development experience**: Near-instant HMR with Vite (uses ESBuild)
3. **Production builds**: SWC replaces Babel in Next.js 13+ for faster builds
4. **Smaller bundles**: Efficient tree-shaking and minification

## How It Works

### Why native beats JavaScript here

The old toolchain was bottlenecked architecturally, not by JavaScript the language: Babel processes files serially per worker, allocates heavyweight AST objects on the GC heap, and crosses a plugin boundary per transform. esbuild/SWC parse with **hand-written, allocation-minimal parsers**, transform on **all cores**, and print without source-map-aware regeneration overhead — the same phases, engineered for throughput. The consequence: transforms that took 30s take 300ms, which changes *what you build* — watch mode becomes the primary interface, not an afterthought.

### The trade, concretely

Depth is the price. esbuild's plugin API is deliberately narrow (onResolve/onLoad — resolution and content, no per-node AST access); SWC's is Rust/WASM — faster but a different skill set, and neither supports Babel's plugin ecosystem for exotic proposals. TypeScript handling is **strip-only in both**: types are erased, never checked — `tsc --noEmit` (or `tsc --project` in CI) remains the type gate; the build pipeline is *transpile fast, check separately*. Downleveling covers modern targets (es2015+) well; deep ES5 output for legacy browsers is where Babel still wins. And esbuild bundles CSS and has a built-in dev server; SWC's `spack` remains experimental — for bundling, SWC appears inside platforms (Next, Parcel) rather than as a CLI product.

### Where each one lives today

- **esbuild**: Vite's dependency pre-bundler (the reason `npm install` → dev server in seconds), standalone bundler for CLIs and server bundles, minifier inside Vite/Rollup ecosystems (`vite-plugin-compression`-adjacent), Jest's `ts-jest` replacement via `esbuild-jest`.
- **SWC**: Next.js's compiler (`.next` builds and fast refresh), Parcel's transform core, `@swc/jest` for test transforms, and standalone via `.swcrc` when a platform embeds it.

## Code Examples

### ESBuild

```javascript
// build.js
const esbuild = require('esbuild');

// Build
esbuild.buildSync({
  entryPoints: ['src/index.ts'],
  bundle: true,
  outfile: 'dist/bundle.js',
  platform: 'browser',
  target: ['es2020'],
  minify: true,
  sourcemap: true,
  loader: { '.ts': 'ts', '.tsx': 'tsx' },
});

// Serve with HMR
async function serve() {
  const ctx = await esbuild.context({
    entryPoints: ['src/index.tsx'],
    bundle: true,
    outdir: 'dist',
    define: { 'process.env.NODE_ENV': '"development"' },
  });
  await ctx.watch();
  await ctx.serve({ port: 3000, servedir: 'dist' });
}

// CSS bundling
esbuild.buildSync({
  entryPoints: ['src/styles.css'],
  bundle: true,
  outfile: 'dist/styles.css',
  loader: { '.css': 'css' },
});
```


## Real-World Usage

- **The Vite pattern is the architecture lesson**: esbuild for dev (pre-bundle deps, transform on demand — speed where feedback happens), Rollup for production build (mature chunking/plugin ecosystem — control where it matters once per release). Tools compose by phase; "esbuild vs Rollup" was always a false binary.
- **Test-latency audits start with the transformer**: a suite whose startup is 20s of Babel transforms drops to ~2s with `@swc/jest` or `esbuild-jest` — usually the single largest DX win available in an established repo, and safe because transforms are strip-only (type-checking stays with `tsc --noEmit` in CI).
- **Migration coexistence is normal**: `enforce: 'pre'` Babel chains in webpack for the one plugin you can't replace, esbuild-loader for everything else — measure per-file transform counts (`speed-measure-webpack-plugin`, esbuild `--metafile`) before and after; the goal is shrinking Babel's surface, not ideological removal.
- **Know the failure shape**: type errors do *not* fail an esbuild/SWC build — a CI that relies on the bundler for correctness will ship type errors; the gate must be explicit (`tsc --noEmit` as a separate pipeline stage), and this is the most common integration mistake in teams adopting these tools.

## Common Mistakes

| Mistake | Root Cause | Fix |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Relying on esbuild/SWC to catch TypeScript type errors | Both compilers strip types without validating type compatibility | Always run `tsc --noEmit` as a dedicated type-check gate in CI |
| Expecting ES5 downleveling with full polyfills from esbuild | ESBuild focuses on modern ES2015+ output; it does not inject runtime API polyfills | Use SWC with `env.targets` or Babel with `core-js` for legacy browser downleveling |
| Assuming esbuild has full Webpack/Rollup code-splitting | ESBuild ESM splitting lacks HTML injection, federation, and complex dynamic vendor chunks | Use Vite/Rollup or Webpack for complex web applications; use esbuild for deps & CLIs |
| Decorator metadata mismatches in NestJS/Angular | TypeScript legacy decorators (`emitDecoratorMetadata`) require specific flags in `.swcrc` | Configure `parser.decorators: true` and `transform.legacyDecorator: true` in `.swcrc` |
| Shipping Node.js built-ins to the browser without polyfills | ESBuild does not polyfill `Buffer`, `crypto`, or `process` by default for browser targets | Add `@esbuild-plugins/node-globals-polyfill` or rely on Vite's browser-safe packaging |

## Best Practices

1. **Use ESBuild for development bundling** (Vite uses it internally)
2. **Use SWC for production TypeScript compilation** (faster than tsc)
3. **Keep Babel for advanced transforms** if plugins lack ESBuild/SWC equivalents
4. **Combine with Webpack** for complex code-splitting needs
5. **Use ESBuild for one-off builds** (CLI tools, server bundles)

## Summary

- ESBuild is an extremely fast JavaScript bundler and minifier written in Go (10-100x faster than Webpack)
- SWC is a Rust-based platform for compilation, bundling, and minification with Babel-compatible plugins
- Both tools are designed as drop-in replacements for Babel and Webpack in modern build pipelines
- ESBuild excels at single-file bundling and is used internally by Vite for dependency pre-bundling
- SWC powers Next.js and Parcel, offering TypeScript compilation and minification in a single binary

# Asset Pipelines — CSS, Images & Fonts

A page can compile successfully and still download an oversized image, render with a missing glyph, or request an old stylesheet after deployment. The pipeline is correct only when transformed bytes, browser-facing references, and release behavior agree.

## Definition

An asset pipeline turns source styles, images, fonts, and other resources into browser-loadable outputs while keeping their references and cache identities consistent. It coordinates build tools and deployment so each browser request resolves to the intended representation.

> **Textbook Definition:** An asset pipeline is a build and delivery process that resolves, transforms, identifies, and publishes non-code resources together with the references and metadata required to load the intended representation safely.

## First Principles

Browsers load URLs, not source filenames. If a build changes an asset's bytes or name, it must also update every reference to that asset. If the bytes later change under an immutable URL, a cache can serve a different version from the one the page expects. Transformations, references, and deployment therefore form one release contract.

## How It Works

### Follow an asset from source to request

The path is: resolve the source reference, apply the required transformation, finalize the output bytes, write the generated manifest (the build's asset-to-URL map) or markup reference, then deploy both reference and target. A bundler import usually adds a resource to its graph and gives the application a deployable URL; it does not automatically resize an image, create format variants, or subset a font. A public-directory copy often keeps its original name and bypasses graph-based hashing, so its URL and cache policy need separate ownership.

Cascading Style Sheets (CSS) processing has distinct jobs. Import resolution, syntax transforms, prefixing, and minification are not interchangeable. PostCSS runs the configured plugin chain. In current Vite, PostCSS is the default CSS transformer, while Lightning CSS minifies production CSS by default. Setting `css.transformer: 'lightningcss'` opts into its full CSS-processing path, which current Vite documentation marks experimental; a required PostCSS plugin may make that choice unsuitable. Set browser targets deliberately and avoid running overlapping transforms without checking their order and output.

Tailwind v4 scans source files as text for complete class candidates; it does not evaluate runtime string interpolation. A value such as ``bg-${tone}-600`` does not contain a complete class the scanner can emit. Map allowed values to complete strings such as `bg-red-600` and `bg-green-600`, or register a deliberate source with `@source`/`@source inline()`. The v4 CSS-first source model differs from v3 JavaScript safelist configuration.

### Let the browser choose an image

Generate candidates at widths that match real layouts. Put each candidate's intrinsic width in `srcset` (for example, `800w`); set `sizes` to the image's expected CSS slot width at each breakpoint. The browser combines that information with viewport and device pixel ratio to choose a candidate. Use `<picture>` when format support should select among AV1 Image File Format (AVIF), WebP, and a fallback; the `type` belongs on `<source>`, while the final `<img>` provides the fallback and alternative text.

This example assumes the files exist, share an aspect ratio, and are generated by the build or image service. At a 400-CSS-pixel display width, an 800-pixel candidate is a useful starting point for a device-pixel ratio of two; measure quality and transfer size for the actual image and devices.

```html
<picture>
  <source type="image/avif"
          srcset="/assets/hero-200.avif 200w, /assets/hero-400.avif 400w, /assets/hero-800.avif 800w"
          sizes="(max-width: 400px) 100vw, 400px">
  <source type="image/webp"
          srcset="/assets/hero-200.webp 200w, /assets/hero-400.webp 400w, /assets/hero-800.webp 800w"
          sizes="(max-width: 400px) 100vw, 400px">
  <img src="/assets/hero-800.jpg"
       srcset="/assets/hero-200.jpg 200w, /assets/hero-400.jpg 400w, /assets/hero-800.jpg 800w"
       sizes="(max-width: 400px) 100vw, 400px"
       width="800" height="600" alt="A mountain landscape">
</picture>
```

The dimensions reserve layout space. Give a likely Largest Contentful Paint (LCP) image high fetch priority only when measurement supports it; do not lazy-load that image by default. Lazy-load images that are below the fold. Choose alternative text from the image's purpose, and inspect the selected candidate in the production layout rather than assuming a fixed pixel-ratio rule.

### Generate variants within explicit limits

Pre-generate known static images during the build. A transformation service can suit a large, changing upload catalog, but it needs bounded formats, dimensions, concurrency, cache identity, and failure behavior. This example writes one WebP variant with `sharp`; it is not a responsive-set or manifest generator.

```javascript
// generate-image.mjs; install sharp and pass input and output paths
import sharp from 'sharp';
import { mkdir } from 'node:fs/promises';
import { dirname } from 'node:path';

const [input, output] = process.argv.slice(2);
if (!input || !output) throw new Error('input and output paths required');
await mkdir(dirname(output), { recursive: true });

const info = await sharp(input, { limitInputPixels: 25_000_000 })
  .rotate() // honor camera orientation metadata
  .resize({ width: 800, withoutEnlargement: true })
  .webp({ quality: 75 })
  .toFile(output);

console.log(JSON.stringify({ width: info.width, height: info.height, bytes: info.size }));
```

Choose crop and aspect-ratio behavior deliberately; `withoutEnlargement` avoids stretching a smaller original. A pixel limit is useful but is not a complete hostile-upload boundary: sharp assumes dimensions in input metadata are trustworthy. Validate byte size and formats, bound concurrent work and total output, and isolate or time-limit processing according to the upload threat model. Compare visual quality as well as bytes.

### Deliver fonts without hiding text or shifting layout

Subset a font only for the scripts and glyphs the product must render, including user-entered names and translated content. A `unicode-range` descriptor lets the browser select applicable font resources; it does not create the subset file. Keep a fallback for characters the subset omits. A variable font can cover several weight or axis values, but it is not automatically smaller than separate files.

`font-display: swap` allows fallback text to appear after a very short block period, then swaps to the web font if it arrives. Differences in glyph widths and line metrics can still move content. On a fallback `@font-face`, descriptors such as `size-adjust`, `ascent-override`, `descent-override`, and `line-gap-override` can tune those metrics; verify the result with real content. Preload only a font needed for the initial view; use the same URL and CORS mode as the eventual font request so the browser can reuse it. An unused or mismatched preload competes for bandwidth without helping the page.

### Publish one consistent release

Finalize transformations, filenames, source maps, and references before publishing. A content-hashed URL can be cached as immutable only while it always identifies the same bytes. HTML or a release manifest needs a freshness policy that lets clients discover new hashes, and older chunks or assets must remain available for already-open pages during rollout.

If a post-build step changes JavaScript after its hash or source map is produced, regenerate the identity and all references or use an integration that runs at the correct stage. Upload maps paired with the final release, verify one error maps to the intended source, and exclude map files from public hosting when source disclosure is not intended. A hidden source-map setting suppresses a discovery comment; it does not make an emitted map private. Client-side secrets remain public even when maps are removed.

## Summary

Trace each resource from source through transformation to the URL and bytes served to the browser. Let layout choose responsive images, preserve the required font repertoire, and set cache identities only after output is final. A successful build proves neither visual quality nor a safe rollout; verify the deployed page and its asset references together.

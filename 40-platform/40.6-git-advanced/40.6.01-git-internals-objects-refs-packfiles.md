# Git Internals: Objects, Refs & Packfiles

## Definition

Suppose `git reset --hard` moves `main` from commit C4 back to C2. C4 is no longer the branch tip, but Git may still have its objects and a local reflog entry that names it. By contrast, edits that were never staged or committed may have no Git object to recover. The difference becomes clear once you follow how Git stores a snapshot and names it.

**Practical definition:** Git stores file contents and snapshots as immutable objects, then uses mutable references such as branches to identify useful commits. Its object database is content-addressed: an object's ID is calculated from its type, size and contents.

> **Textbook Definition:** Git is a distributed version-control system whose object database represents file contents, directory trees, commits and tags as content-addressed objects. References identify selected objects in that graph; packfiles compress and organize objects for storage and transfer.

## First Principles

A saved version should not change when the next version is created. Git therefore stores objects by identity and builds a new snapshot from objects rather than editing an old snapshot in place. A separate reference can move to select a different commit without rewriting the commits it used to name. This separation explains both efficient reuse and why moving a branch is not the same as immediately deleting history.

## Follow a file into a commit

A normal commit traces one path through four pieces of state:

```text
working-tree file
   │ git add
   ▼
blob object ── object ID ──┐
                           ▼
index entry: path + mode + blob ID
   │ git commit
   ▼
tree object(s) ── root tree ID ──> commit object
                                      │
                                      ▼
                              current branch ref moves
```

The **working tree** is the checked-out files on disk. The **index** (also called the staging area) records the exact path, mode and object ID that the next commit will include. `git add` updates the index and writes any needed blob objects. `git commit` writes tree objects from the index, writes a commit object that points at the root tree and its parent commit(s), then updates the current branch reference. If HEAD is detached, Git updates HEAD without advancing a named branch.

This is why editing a file after `git add` does not silently change what is staged: the index still names the staged blob. Add again to replace that index entry. A commit is not a stored diff; commands such as `git show` compare its tree with another tree to display changes.

### The four object types

| Object | What it contains | Important boundary |
| -------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **Blob** | File bytes | It has no filename or executable bit; the same bytes can be reused at different paths. |
| **Tree** | Names, modes and IDs of child blobs or trees | It represents one directory; nested trees represent subdirectories. |
| **Commit** | Root tree ID, parent commit IDs, author/committer data and message | A merge commit has multiple parents; a root commit has none. |
| **Tag object** | Target ID and type, tag name, tagger metadata and message; it may also carry a signature | An annotated tag is an object. A lightweight tag is a ref directly naming its target. |

An object ID hashes a header followed by the object bytes: `"<type> <size>\0<content>"`. The repository's object format determines the hash algorithm and ID length; repositories commonly use SHA-1, and Git also supports SHA-256-format repositories. Exact content of the same type has the same ID within the same object format, so Git can reuse it. The ID identifies content; it does not authenticate the author, establish review, or make an untrusted remote safe.

### Build a tiny object graph with plumbing

Porcelain commands such as `git add` and `git commit` coordinate the index, objects and refs for you. These plumbing commands expose the same pieces directly. Run them in an empty repository; the example creates a commit without checking files out into the working tree.

```bash
git init -q
git config user.name 'Demo Author'
git config user.email 'demo@example.invalid'

blob=$(printf 'A tiny Git repository\n' | git hash-object -w --stdin)
tree=$(printf '100644 blob %s\tREADME.md\n' "$blob" | git mktree)
commit=$(git commit-tree "$tree" -m 'Create README snapshot')

git update-ref refs/heads/demo "$commit"
git symbolic-ref HEAD refs/heads/demo

git cat-file -t "$blob"    # blob
git cat-file -p "$tree"    # tree entry: mode, type, ID, name
git cat-file -p "$commit"  # tree, identity metadata, message
```

`hash-object -w` writes a blob, `mktree` writes a tree from entries, `commit-tree` creates a commit, and `update-ref` moves a named ref. They are useful for debugging tools and understanding the model, not a replacement for everyday porcelain. In normal work, `git write-tree` writes a tree from the index.

## Names that move: HEAD, branches and tags

Objects provide stable history; refs provide convenient names for its current positions.

- **HEAD** usually symbolically names the checked-out branch, such as `refs/heads/main`. A commit then advances that branch. In detached-HEAD state it names a commit ID directly, so new commits need a branch or tag if they should remain easy to find after checkout elsewhere.
- **A branch** is a movable ref that normally points to a commit. Creating or deleting the branch changes the name, not the commit contents. A commit remains reachable while some ref points to it or to a descendant. Once no ref reaches it, a local reflog may keep it findable temporarily, subject to expiry and cleanup.
- **A lightweight tag** is a ref to an object, usually a commit. **An annotated tag** points to a tag object, which in turn names its target and metadata.
- **A remote-tracking branch**, such as `origin/main`, is the local repository's recorded view of a remote ref. Fetch updates that local ref; it is not the server's live branch or a server-side recovery log.

Do not edit `.git/refs` directly. Refs may be loose, packed, or stored by a different backend. Use commands such as `git branch`, `git tag` and `git update-ref`, which validate names and coordinate updates safely.

## How Git stores objects efficiently

A small repository may hold objects as individually compressed files under its object database. As the repository grows, Git can write **packfiles**: files containing many objects, optionally storing a similar object as a delta against a base object. To read a deltified object, Git resolves its base; a delta may depend on a chain of bases. A companion `.idx` index maps object IDs to locations in the pack. Delta compression is a storage choice; the logical object graph and object IDs stay the same.

```bash
git count-objects -vH
# Reports loose and packed object counts and approximate disk usage.
```

For detailed object sizes and delta depth, run `git verify-pack -v <pack-index>` against an existing pack index. Do not assume every small repository already has a pack.

`git gc` performs repository housekeeping, which can include packing objects and pruning objects that are no longer retained. It cannot remove a large blob that remains reachable through a commit kept by a branch or tag. Avoid tuning repack or aggressive collection until measurements identify an actual storage or lookup problem; delta behavior depends on the data and repository.

The `.git` path is an interface detail, not a reliable assumption about one directory layout. In a linked worktree, `.git` is a **gitfile** pointing to a private administrative directory under the main repository's `worktrees/` directory. That private directory holds the worktree's HEAD, index and worktree-specific state; its `commondir` points to the shared repository directory, which holds the common object database and most shared refs and metadata. This is why separate worktrees can check out different branches while reusing stored objects. Submodules also commonly use a gitfile. Ask Git for paths instead of constructing them:

```bash
git rev-parse --git-dir --git-common-dir
git rev-parse --git-path objects
git worktree list
```

## When history moves—and how to recover

Rebase, amend and reset do not edit existing commit objects. Rewriting creates replacement commits because a commit's parent, tree or metadata is part of its identity. The current branch then moves to the replacement history.

| Operation | Object/ref effect | Index and working-tree effect | Typical use |
| ---------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `git reset --soft <commit>` | Moves current branch, or detached HEAD | Leaves index and working tree unchanged | Move a private branch while keeping everything staged |
| `git reset --mixed <commit>` | Moves current branch, or detached HEAD | Resets the index; leaves working-tree files in place | Unstage changes or rebuild the next snapshot |
| `git reset --hard <commit>` | Moves current branch, or detached HEAD | Resets index and tracked files; may remove obstructing untracked paths | Discard local state only after confirming it is safe to lose |
| `git revert <commit>` | Adds a new commit whose changes reverse the selected commit | Uses the normal merge/index/worktree process | Undo a change without rewriting shared history |
| `git rebase <base>` | Recreates replayed commits with new IDs, then moves the branch | Checks out and applies the replayed changes | Reorder or move private work; coordinate before rewriting shared history |
| `git commit --amend` | Replaces the tip commit with a new commit ID | Uses the current index for the amended snapshot | Correct a private tip before others depend on it |

Reverting a merge commit needs an explicit mainline parent (`-m`); choose the parent whose line of development should be retained.

A **reflog** is a local record of ref updates. In a typical non-bare repository, `HEAD` and branch updates have reflogs, but not every ref is logged, reflogs are not pushed or fetched, and entries expire. The documented defaults are 90 days for reachable entries and 30 days for unreachable entries; configuration can change them. A reflog helps find a commit whose object still exists. It does not store uncommitted file bytes and is not a backup.

If a commit appears lost, inspect before moving the branch again:

```bash
git status --short
git reflog show HEAD
```

Choose a candidate from the reflog, inspect it with `git show --stat <object-id>`, and preserve a verified commit with `git branch rescue <object-id>`. The rescue branch keeps that commit and its reachable objects while you investigate. A reflog does not identify uncommitted edits. Staging can write a blob before a commit exists, but an unreferenced blob is not a dependable recovery point and may later be pruned; never-staged or untracked bytes may have no object at all. A damaged or incomplete object database may also lack objects named by a reflog, so restore missing objects from a verified backup or trusted complete clone.

## Two consequences worth remembering

**Deleting a file does not erase its earlier versions.** `git rm` removes the path from the next tree. Earlier commits still reference their blob objects, so the repository retains them while that history is reachable. Reducing repository size may require a coordinated history rewrite, followed by cleanup after all retained refs and recovery windows are handled. Rewriting changes commit IDs and affects other clones. Git LFS stores large file bytes outside ordinary Git objects, so back up and verify both the Git history and LFS content; see [Git at Scale](40.6.08-git-at-scale-lfs-partial-clones.md).

**Integrity is different from trust and recoverability.** `git fsck` checks the object database and its graph for corruption or connectivity problems. It cannot prove who authored or reviewed a commit, restore bytes absent from the object store, or ensure external LFS content is available. Use a separate signature policy and verified backups for those guarantees.

## Summary

- `git add` connects file content to a path in the index; `git commit` records the index as trees and a commit, then moves HEAD or its branch.
- Blobs store bytes, trees store paths and modes, commits store snapshots and ancestry, and annotated tags store tag metadata. IDs identify typed content.
- Refs move; existing objects do not. Packfiles change physical storage, not the logical history graph.
- Reflogs can help recover recorded ref positions while their objects and entries remain available. They cannot recover never-recorded edits or replace backups.
- `reset` changes the current position and may replace index/worktree state; `revert` adds a compensating commit; `rebase` and `amend` create replacement commits.

# Git Internals: Objects, Refs & Packfiles

## Definition

Git is fundamentally a **key-value store of immutable objects**, addressed by a hash of their typed content (SHA-1 or SHA-256, depending on repository format), plus a layer of **references** (branch and tag names) that point into that object graph. There are exactly four object types:

> **Textbook Definition:** Git stores versioned snapshots as content-addressed blobs, trees, commits, and annotated tags. References name positions in that object graph, while packfiles compress and consolidate stored objects.

| Object | Stores | Addressed by |
| ---------- | -------------------------------------------------------------------------- | ---------------------------- |
| **blob** | File content; filename and executable mode belong to the tree | Hash of typed object content |
| **tree** | Directory listing: mode + name + child blob/tree hashes | Hash of typed tree content |
| **commit** | Snapshot pointer (root tree), parent(s), author, committer, message | Hash of typed commit content |
| **tag** | Annotated tag: points at another object + tag message + optional signature | Hash of typed tag content |

A branch is a reference to a commit. In the traditional files backend, a loose SHA-1 branch ref holds 40 hexadecimal characters plus a newline. References may instead be packed or stored through another ref backend; their logical role remains the same.

```text
HEAD → main → commit C4 → parent commit C3
                │                      │
              tree T4                tree T3
                │                      │
           file blobs             file blobs
```

## First Principles

A snapshot must be saved without mutating the version another reader already uses. Addressing each typed object by its content lets unchanged bytes reuse an existing object. A tree associates content with paths and modes; a commit associates a tree with its parents and metadata. Humans need stable names for moving lines of work, so refs select commits without copying snapshots. Objects are immutable; refs, the index, and the working tree are separate mutable state.

## Why Do We Need It?

1. **Debugging confidence** — when you understand that commits are immutable objects and branches are movable pointers, `git reset --hard` has distinct ref, index and worktree effects; uncommitted tracked data can be lost.
2. **Explaining rebase and merge precisely** — rebase copies commits (new SHAs) onto a new base; a non-fast-forward merge commonly creates a commit with two parents; a fast-forward just advances the branch. Interviews probe this constantly.
3. **Repository size management** — knowing packfiles and deltas explains why `.git` grows, why `gc` matters, and how to audit bloat (see [Git at Scale](40.6.08-git-at-scale-lfs-partial-clones.md)).
4. **Recovery skills** — reflog is only comprehensible if you know HEAD movements are recorded per ref; unreachable objects may remain until applicable retention and pruning permit deletion.
5. **Tooling literacy** — CI systems, code hosts, and backup tools all manipulate refs and objects; you can reason about shallow clones, mirrors, and force-push policies only at this level.
6. **Senior interview signal** — "what happens when you commit?" is a real senior question; the plumbing answer separates seniors from juniors.

## How It Works

### Content Addressing

An object ID hashes `"<type> <size>\0<content>"` using the repository's object hash algorithm. The examples below use a SHA-1 repository. Identical file content anywhere in history collapses to the same blob — that is why Git stores snapshots efficiently without diffing for storage.

```bash
# Create a blob from stdin and print its address
echo "hello world" | git hash-object --stdin
# 3b18e512dba79e4c8300dd08aeb37f8e728b8dad

# Write it into .git/objects (loose object, zlib-compressed)
echo "hello world" | git hash-object -w --stdin

# Inspect it
git cat-file -t 3b18e512   # type:  blob
git cat-file -p 3b18e512   # print: hello world
git cat-file -s 3b18e512   # size:  12
```

### Building a Commit by Hand (Plumbing)

You never do this in daily work, but doing it once proves there is no magic:

```bash
# 1. Create blobs
blob1=$(echo "console.log('hi')" | git hash-object -w --stdin)
blob2=$(echo "# Demo" | git hash-object -w --stdin)

# 2. Build a tree referencing them (mode, type, hash, name)
tree=$(printf '100644 blob %s\tindex.ts\n100644 blob %s\tREADME.md\n' "$blob1" "$blob2" | git mktree)

# 3. Create a commit object pointing at the tree (-m message, parents optional)
commit=$(git commit-tree "$tree" -m "Hand-forged commit")

# 4. Point a branch at it — congratulations, you built a commit with no working copy
git update-ref refs/heads/hand-made "$commit"
```

```text
WHAT ONE COMMIT CONTAINS

┌───────────────────────────────────────────────┐
│ commit <size>\0                               │
│ tree     e5f6a7...   ◄── root tree (snapshot) │
│ parent   c3d4e5...   ◄── previous commit(s)   │
│ author   Ada <ada@x.dev> 1738020000 +0100     │
│ committer Ada <ada@x.dev> 1738020000 +0100    │
│                                               │
│ Fix login race on token refresh               │
└───────────────────────────────────────────────┘
```

### Refs and HEAD

```text
.git/
├── HEAD                  → ref: refs/heads/main   (symbolic)
├── refs/
│   ├── heads/            local branches (shown here as loose refs)
│   │   ├── main          → c4d5e6... (raw SHA)
│   │   └── feature/login → 9a8b7c...
│   ├── remotes/origin/   remote-tracking branches
│   └── tags/v1.2.0       → tag or commit object
├── packed-refs           many refs flattened into one file
└── logs/HEAD, logs/refs/...   ← THE REFLOGS (append-only)
```

- `HEAD` is usually **symbolic**: it names a branch, so committing advances that branch.
- **Detached HEAD**: HEAD holds a raw SHA instead of a branch name — new commits here need a durable branch/tag to remain reachable after leaving them; local reflog retention is temporary.
- A branch "contains" nothing. Deleting a branch deletes one pointer; the commits live on until unreachable *and* expired.

### Packfiles and Deltas

Loose objects are fine for small repos but wasteful at scale. Git periodically packs objects:

```text
LOOSE OBJECTS                     PACKFILE (.pack + .idx)
.git/objects/3b/18e51...          .git/objects/pack/pack-abc123.pack
one zlib file per object          thousands of objects per file
full content every time           delta compression against base objects

git gc / git repack:
  • sorts objects by type, name, size
  • picks delta bases (recent similar versions preferred)
  • writes one pack + binary index (.idx) for O(log n) lookup
```

Key commands:

```bash
git count-objects -v          # loose vs packed counts, KB on disk
git verify-pack -v .git/objects/pack/pack-*.idx | sort -k3 -n -r | head
                              # biggest objects incl. delta chain depth
git repack -d                 # remove redundant packs after packing
git gc                        # pack, prune unreachable, expire reflogs
git gc --aggressive           # recomputes deltas; measure whether it helps
git unpack-objects < foo.pack # explode a pack back to loose objects
```

Delta chains matter: a 50 MB file edited ten times stores roughly a chosen base plus deltas when the content compresses well; compressed or substantially changed binaries can remain expensive — but very deep chains slow reads. `git repack --depth=50 --window=250` tunes this.

### The Reflog: Your Safety Net

When reflog recording is enabled for a reference, Git records its updates locally. A normal non-bare repository records HEAD and branch movements; not every ref has a reflog. Reflogs are not transferred by push or fetch.

```text
$ git reflog
c4d5e6 (HEAD -> main) HEAD@{0}: rebase (finish): refs/heads/main onto f1e2d3
9a8b7c HEAD@{1}: rebase (pick): Add retry logic
000000 HEAD@{2}: reset: moving to origin/main
dead12 HEAD@{3}: commit: WIP: debug logging     ← "lost" after the reset
...
Default expiry: 90 days (gc.reflogExpire), 30 days for unreachable.
```

Preserve a verified recorded commit with the recovery example below; retaining a ref keeps its reachable objects eligible for normal storage retention.

### What Reset and Rebase Actually Do

```text
BEFORE                          git reset --hard f1e2d3
main ──► C4                     main ──► C2   (pointer moved BACK)
HEAD ──► main                   index + worktree overwritten
                                C3, C4 now UNREACHABLE (reflog keeps them)

git revert C4                   NEW commit C5 that undoes C4's changes
main ──► C4 ──► C5              history preserved — safe on shared branches

git rebase main                 COPIES C3',C4' as new objects onto main tip,
feature: C3,C4  main: C2        then moves feature pointer to C4'
feature ──► C3' ──► C4'         original C3,C4 remain via reflog (ORIG_HEAD)
```

| Command | Moves which ref? | Rewrites history? | Shared-branch safe? |
| -------------- | ------------------------- | ----------------------------------------------------- | ------------------------------------ |
| `commit` | current branch forward | no | yes |
| `reset --soft` | branch only | changes selected branch history; keeps index/worktree | risky |
| `reset --hard` | branch + index + worktree | moves branch; overwrites index/worktree | risky |
| `revert` | adds new commit | no | yes |
| `rebase` | branch to copied commits | yes (new SHAs) | only with coordinated rewrite policy |
| `amend` | replaces last commit | yes | only with coordinated rewrite policy |

### Reading .git Directly

| Path | Purpose |
| ----------------------------------------------- | --------------------------------------------------------- |
| `HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, `MERGE_HEAD` | where you are / was, last fetch, merge-in-progress |
| `index` | binary staging area (compare with `git ls-files --stage`) |
| `objects/info/alternates` | borrow objects from another repo (used by some CI caches) |
| `objects/pack/` | packfiles + indexes |
| `logs/` | reflogs — the append-only safety journal |
| `shallow` | marks shallow clone cut-offs (see partial clones chapter) |
| `config` | remotes, hooks paths, fsmonitor flags |
| `info/exclude` | per-repo ignores outside version control |

## Code Examples

### Inspect Any Commit's True Contents

```bash
# Full metadata + root tree of HEAD
git cat-file -p HEAD

# List files inside a tree object
git ls-tree HEAD src/

# Show which blob a path pointed to in an old commit
git rev-parse HEAD~10:package.json

# Compare two trees directly (no working copy involved)
git diff-tree -r HEAD~3 HEAD --name-status
```

### Recover committed history before changing the worktree

```bash
git status --short
git reflog show HEAD
# Inspect the selected candidate before anchoring it:
git show --stat <candidate-object-id>
git branch rescue <candidate-object-id>
```

Reflogs track ref updates, not every editor change. An unstaged file overwritten by reset may never have existed as a Git object. `fsck` can locate existing unreachable objects but cannot reconstruct arbitrary unrecorded bytes. Stashes contain recorded state; inspect `git stash list` and use `git stash apply 'stash@{0}'` only when that is the intended saved work.

`ORIG_HEAD` can be overwritten by later operations. Inspect the correct reflog entry and anchor it instead of assuming a fixed `HEAD@{3}` or blindly resetting. `git log -g origin/main` reads your local remote-tracking reflog, not the server's private push journal.

### Audit object sizes without conflating blobs and commits

```bash
git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  awk '$1 == "blob" {print $3, $2, $4}' | sort -rn | head -10
```

This checks blobs, not every object as if it were file data. Paths containing whitespace need structured/NUL-aware handling in enforcement tools. A CI range also needs an explicitly fetched trusted base; `@{push}` is not always configured. See [scale](40.6.08-git-at-scale-lfs-partial-clones.md) for a complete bounded local blob-size example.

## Real-World Use Cases

### 1. Shrinking a Repo After Someone Committed a 200 MB Video

A coordinated history rewrite can remove the video from selected retained refs, but changes commit identities and may invalidate signatures. First preserve needed history and agree how clones, tags and external refs are handled. Removing a file today leaves older reachable versions intact; immediate reflog expiry/pruning removes recovery evidence and is not routine cleanup.

Understanding objects tells you why a plain `git rm` does nothing for size: the old blobs remain reachable through history.

### 2. Explaining a Broken Teammate Repo After a Force-Push

Teammate pulls, gets conflicts on commits they "already have." Explanation: rebased commits are **new objects**; the old ones still exist locally. Inspect old/new histories and preserve local-only work before choosing a coordinated rebase or ref reset. Neither is an automatic repair for every force-push.

### 3. CI Cache Corruption Debugging

A CI cache tarred up `.git` including stale `alternates` and shallow markers, causing `fatal: bad object`. Knowing that `objects/info/alternates` borrows from another store makes the bug obvious in seconds.

### 4. Auditing Who Changed What Without Checkout

```bash
git diff-tree -r --name-only v1.0.0 v1.1.0 -- src/api/
```

Release managers diff two tagged trees directly — no working copy, no checkout, works in bare repos on servers.

### 5. Verifying Integrity After a Suspected Disk Issue

```bash
git fsck --full --strict        # validates every object hash + link graph
git fsck --unreachable          # shows objects no ref can reach (future gc food)
```

## Common Mistakes

### 1. Believing reset Deletes Commits

Moving a branch does not immediately destroy its old committed objects. Other refs may still reach them; otherwise reflog/GC policy determines retention. Inspect the correct recorded object and anchor it, rather than assuming `HEAD@{1}` always names the desired state. Uncommitted bytes may have no recoverable object.

### 2. Relying on Reflog Forever

Reflogs are local and expire (90 days default). They are a personal safety net, not a backup strategy. Push branches or open draft PRs for anything valuable.

### 3. Confusing amend/rebase Signatures With Immutability

Rewriting creates brand-new objects with new SHAs. Anyone who based work on the old SHAs must coordinate how to integrate the rewritten history; signed commits lose their valid signatures because the signed bytes changed.

### 4. Running Aggressive GC on Active Feature Repos "To Clean Up"

`git gc --aggressive` rewrites delta chains for hours on big repos and adds CPU/I/O cost; immediate pruning concurrent with writers has additional race risks. Prefer letting auto-gc handle it; intervene only with evidence from `count-objects -v`.

### 5. Editing .git Files by Hand Without Understanding Formats

```bash
# Bad: echo a sha into .git/refs/heads/main with trailing garbage
# Good: use the porcelain that validates
git update-ref refs/heads/main <sha>
```

`update-ref` also takes locks, so concurrent tooling cannot corrupt the ref.

### 6. Treating GitHub as the Source of Truth for History

The remote is a ref holder like any other. Server-side reflogs exist but are an admin feature; recovery windows differ per host. Keep mirrors for anything critical.

## Best Practices

1. **Learn five plumbing commands** (`hash-object`, `cat-file`, `mktree`, `commit-tree`, `update-ref`) — they demystify everything else.
2. **Check `git status` before reset** — know what the index and worktree hold before moving refs.
3. **Prefer `revert` on shared branches**, `reset`/`rebase` on private ones.
4. **Anchor recovered work in a branch immediately** (`git branch rescue <sha>`), then decide later.
5. **Audit size with `count-objects -v` and `verify-pack`** before reaching for destructive history rewrites.
6. **Let auto-gc run**; schedule explicit `gc` only for known-bloat events (post `filter-repo`).
7. **Record reflog knowledge in runbooks** — recorded commits can often be recovered, while never-recorded bytes cannot.
8. **Use `--force-with-lease` instead of `--force`** — it checks an expected remote ref value; a background fetch can weaken its implicit expectation. An explicit expected object ID gives a reviewed comparison.

## Performance considerations

A commit graph reduces some ancestry traversal work; it does not make arbitrary log queries instant. Filesystem monitoring can reduce path scans where supported, and checkout still has to materialize selected changed files. Fetch/repack cost depends on object content, network, storage, and delta choices. Use the scale chapter's measured workflow before tuning these mechanisms.

## Summary

- Git stores four immutable object types addressed by content hash; identical content deduplicates automatically.
- Branches and tags name objects through the selected ref backend; snapshots and commits are separate from the worktree.
- Packfiles compress objects with deltas; `count-objects`/`verify-pack` expose size problems.
- Reflog is an append-only local journal — the first place to look after any destructive command, subject to separate reachable/unreachable expiry settings.
- `reset` moves a ref (optionally rewriting index/worktree); `rebase` copies commits and moves the ref; `revert` preserves history.
- `.git` is readable documentation once you know the layout; `fsck` checks object integrity and connectivity, not signer authority, deployments, or external LFS availability.

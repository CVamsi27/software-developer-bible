# Git Internals: Objects, Refs & Packfiles

> Senior engineers who understand the object model stop fearing Git. `reset`, `rebase`, `gc`, and "where did my commit go?" all become mechanical once you know that **Git is a content-addressable filesystem with pointers on top**.

## Definition

Git is fundamentally a **key-value store of immutable objects**, addressed by the SHA-1 hash of their content, plus a layer of **references** (branch and tag names) that point into that object graph. There are exactly four object types:

| Object | Stores | Addressed by |
| ---------- | ------------------------------------------------------------------- | -------------------- |
| **blob** | File content (no filename, no permissions beyond executable bit) | SHA-1 of content |
| **tree** | Directory listing: mode + name + child blob/tree hashes | SHA-1 of listing |
| **commit** | Snapshot pointer (root tree), parent(s), author, committer, message | SHA-1 of commit text |
| **tag** | Annotated tag: points at another object + tag message + signer | SHA-1 of tag object |

A branch is just a 41-byte file containing a commit hash. That is the entire trick.

```text
COMMIT GRAPH (each commit points to a full tree snapshot)

  main ──► ┌──────────┐      ┌──────────┐
           │ commit C3│ ◄────│ commit C4│ ◄── HEAD (symbolic ref)
           └────┬─────┘parent└────┬─────┘
                │                 │
             tree a1b2         tree e5f6
            /    |    \       /    |    \
         blob  blob  tree   blob  blob  tree
         (src) (README)(lib) ...
```

## Why Do We Need It?

1. **Debugging confidence** — when you understand that commits are immutable objects and branches are movable pointers, `git reset --hard` stops being scary: it moves one pointer.
2. **Explaining rebase and merge precisely** — rebase copies commits (new SHAs) onto a new base; merge creates a merge commit with two parents. Interviews probe this constantly.
3. **Repository size management** — knowing packfiles and deltas explains why `.git` grows, why `gc` matters, and how to audit bloat (see [Git at Scale](40.6.08-git-at-scale-lfs-partial-clones.md)).
4. **Recovery skills** — reflog is only comprehensible if you know HEAD movements are recorded per ref; dangling commits survive until gc expires them.
5. **Tooling literacy** — CI systems, code hosts, and backup tools all manipulate refs and objects; you can reason about shallow clones, mirrors, and force-push policies only at this level.
6. **Senior interview signal** — "what happens when you commit?" is a real senior question; the plumbing answer separates seniors from juniors.

## How It Works

### Content Addressing

Every object's name is `SHA-1("<type> <size>\0<content>")`. Identical file content anywhere in history collapses to the same blob — that is why Git stores snapshots efficiently without diffing for storage.

```bash
# Create a blob from stdin and print its address
echo "hello world" | git hash-object --stdin
# 3b18e512dba79e4c8300dd08aeb37f8e728b8dad

# Write it into .git/objects (loose object, zlib-compressed)
echo "hello world" | git hash-object -w --stdin

# Inspect it
git cat-file -t 3b18e512   # type:  blob
git cat-file -p 3b18e512   # print: hello world
git cat-file -s 3b18e512   # size:  12
```

### Building a Commit by Hand (Plumbing)

You never do this in daily work, but doing it once proves there is no magic:

```bash
# 1. Create blobs
blob1=$(echo "console.log('hi')" | git hash-object -w --stdin)
blob2=$(echo "# Demo" | git hash-object -w --stdin)

# 2. Build a tree referencing them (mode, type, hash, name)
tree=$(printf '100644 blob %s\tindex.ts\n100644 blob %s\tREADME.md\n' "$blob1" "$blob2" | git mktree)

# 3. Create a commit object pointing at the tree (-m message, parents optional)
commit=$(git commit-tree "$tree" -m "Hand-forged commit")

# 4. Point a branch at it — congratulations, you built a commit with no working copy
git update-ref refs/heads/hand-made "$commit"
```

```text
WHAT ONE COMMIT CONTAINS

┌────────────────────────────────────────────────┐
│ commit <size>\0                                │
│ tree     e5f6a7...   ◄── root tree (snapshot)  │
│ parent   c3d4e5...   ◄── previous commit(s)    │
│ author   Ada <ada@x.dev> 1738020000 +0100      │
│ committer Ada <ada@x.dev> 1738020000 +0100     │
│                                                │
│ Fix login race on token refresh                │
└────────────────────────────────────────────────┘
```

### Refs and HEAD

```text
.git/
├── HEAD                  → ref: refs/heads/main   (symbolic)
├── refs/
│   ├── heads/            local branches (one small file each)
│   │   ├── main          → c4d5e6... (raw SHA)
│   │   └── feature/login → 9a8b7c...
│   ├── remotes/origin/   remote-tracking branches
│   └── tags/v1.2.0       → tag or commit object
├── packed-refs           many refs flattened into one file
└── logs/HEAD, logs/refs/...   ← THE REFLOGS (append-only)
```

- `HEAD` is usually **symbolic**: it names a branch, so committing advances that branch.
- **Detached HEAD**: HEAD holds a raw SHA instead of a branch name — commits here are unanchored and will be garbage-collected unless a ref points to them.
- A branch "contains" nothing. Deleting a branch deletes one pointer; the commits live on until unreachable *and* expired.

### Packfiles and Deltas

Loose objects are fine for small repos but wasteful at scale. Git periodically packs objects:

```text
LOOSE OBJECTS                     PACKFILE (.pack + .idx)
.git/objects/3b/18e51...          .git/objects/pack/pack-abc123.pack
one zlib file per object          thousands of objects per file
full content every time           delta compression against base objects

git gc / git repack:
  • sorts objects by type, name, size
  • picks delta bases (recent similar versions preferred)
  • writes one pack + binary index (.idx) for O(log n) lookup
```

Key commands:

```bash
git count-objects -v          # loose vs packed counts, KB on disk
git verify-pack -v .git/objects/pack/pack-*.idx | sort -k3 -n -r | head
                              # biggest objects incl. delta chain depth
git repack -d                 # remove redundant packs after packing
git gc                        # pack, prune unreachable, expire reflogs
git gc --aggressive           # slower, better delta selection
git unpack-objects < foo.pack # explode a pack back to loose objects
```

Delta chains matter: a 50 MB file edited ten times stores roughly the newest version plus nine tiny deltas — but very deep chains slow reads. `git repack --depth=50 --window=250` tunes this.

### The Reflog: Your Safety Net

Every time HEAD or any ref moves (commit, reset, rebase checkout step, merge), Git appends a line to `logs/refs/...`. This is **local-only** and never pushed.

```text
$ git reflog
c4d5e6 (HEAD -> main) HEAD@{0}: rebase (finish): refs/heads/main onto f1e2d3
9a8b7c HEAD@{1}: rebase (pick): Add retry logic
000000 HEAD@{2}: reset: moving to origin/main
dead12 HEAD@{3}: commit: WIP: debug logging     ← "lost" after the reset
...
Default expiry: 90 days (gc.reflogExpire), 30 days for unreachable.
```

Recovery is just pointing a ref at an old entry:

```bash
git reset --hard HEAD@{2}         # move branch back
git branch rescue dead12          # or anchor the lost work in a new branch
```

### What Reset and Rebase Actually Do

```text
BEFORE                          git reset --hard f1e2d3
main ──► C4                     main ──► C2   (pointer moved BACK)
HEAD ──► main                   index + worktree overwritten
                                C3, C4 now UNREACHABLE (reflog keeps them)

git revert C4                   NEW commit C5 that undoes C4's changes
main ──► C4 ──► C5              history preserved — safe on shared branches

git rebase main                 COPIES C3',C4' as new objects onto main tip,
feature: C3,C4  main: C2        then moves feature pointer to C4'
feature ──► C3' ──► C4'         original C3,C4 remain via reflog (ORIG_HEAD)
```

| Command | Moves which ref? | Rewrites history? | Shared-branch safe? |
| -------------- | ------------------------- | ------------------------- | ---------------------- |
| `commit` | current branch forward | no | yes |
| `reset --soft` | branch only | no (keeps index/worktree) | risky |
| `reset --hard` | branch + index + worktree | discards reachable state | dangerous |
| `revert` | adds new commit | no | yes |
| `rebase` | branch to copied commits | yes (new SHAs) | only your own branches |
| `amend` | replaces last commit | yes | only unpushed |

### Reading .git Directly

| Path | Purpose |
| ----------------------------------------------- | --------------------------------------------------------- |
| `HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, `MERGE_HEAD` | where you are / was, last fetch, merge-in-progress |
| `index` | binary staging area (compare with `git ls-files --stage`) |
| `objects/info/alternates` | borrow objects from another repo (used by some CI caches) |
| `objects/pack/` | packfiles + indexes |
| `logs/` | reflogs — the append-only safety journal |
| `shallow` | marks shallow clone cut-offs (see partial clones chapter) |
| `config` | remotes, hooks paths, fsmonitor flags |
| `info/exclude` | per-repo ignores outside version control |

## Code Examples

### Inspect Any Commit's True Contents

```bash
# Full metadata + root tree of HEAD
git cat-file -p HEAD

# List files inside a tree object
git ls-tree HEAD src/

# Show which blob a path pointed to in an old commit
git rev-parse HEAD~10:package.json

# Compare two trees directly (no working copy involved)
git diff-tree -r HEAD~3 HEAD --name-status
```

### Find Why a Repository Is Large

```bash
# Top 10 largest blobs ever committed
git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  awk '$1 == "blob" {print $3, $4}' | sort -rn | head -10

# Delta statistics per packfile
git verify-pack -v .git/objects/pack/*.idx |
  grep chain | sort -k4 -n -r | head
```

### Recover From Every Classic Disaster

```bash
# Disaster 1: reset --hard discarded uncommitted work
git fsck --lost-found          # lists dangling blobs/commits
git stash apply $(git stash list | head -1)   # stashes are commits too

# Disaster 2: deleted a branch that had unmerged work
git reflog                      # find its last position
git branch restored <sha>

# Disaster 3: bad interactive rebase mangled history
git reset --hard ORIG_HEAD      # rebase records pre-state in ORIG_HEAD

# Disaster 4: force-pushed over by a teammate
git log -g origin/main          # remote reflog IF server exposes push reflogs
```

### TypeScript: Reading Git Objects Programmatically

```typescript
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const run = promisify(execFile);

export async function commitSize(sha: string): Promise<number> {
  // cat-file gives raw object bytes; -s prints size
  const { stdout } = await run('git', ['cat-file', '-s', sha]);
  return Number(stdout.trim());
}

export async function repoObjectCount(): Promise<Record<string, number>> {
  const { stdout } = await run('git', ['count-objects', '-v']);
  const map: Record<string, number> = {};
  for (const line of stdout.split('\n')) {
    const [key, value] = line.split(': ');
    if (key && value && /^\d+$/.test(value)) map[key] = Number(value);
  }
  return map;
}

// Guard in CI: fail PRs that add >1 MB blobs (binaries belong in LFS)
export async function assertNoBigBlobs(limitBytes = 1_048_576): Promise<void> {
  const { stdout } = await run('git', [
    'rev-list', '--objects', '@{push}..HEAD',
  ]);
  const shas = stdout.split('\n').filter(Boolean).map((l) => l.split(' ')[0]);
  for (const sha of shas) {
    if ((await commitSize(sha)) > limitBytes) {
      throw new Error(`Oversized object ${sha} — use Git LFS instead`);
    }
  }
}
```

## Real-World Use Cases

### 1. Shrinking a Repo After Someone Committed a 200 MB Video

```bash
git rev-list --objects --all | grep '\.mp4$'        # locate offending blobs
git filter-repo --path media/demo.mp4 --invert-paths
git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

Understanding objects tells you why a plain `git rm` does nothing for size: the old blobs remain reachable through history.

### 2. Explaining a Broken Teammate Repo After a Force-Push

Teammate pulls, gets conflicts on commits they "already have." Explanation: rebased commits are **new objects**; the old ones still exist locally. Fix is `git pull --rebase` or resetting to the new remote tip — not manual conflict surgery.

### 3. CI Cache Corruption Debugging

A CI cache tarred up `.git` including stale `alternates` and shallow markers, causing `fatal: bad object`. Knowing that `objects/info/alternates` borrows from another store makes the bug obvious in seconds.

### 4. Auditing Who Changed What Without Checkout

```bash
git diff-tree -r --name-only v1.0.0 v1.1.0 -- src/api/
```

Release managers diff two tagged trees directly — no working copy, no checkout, works in bare repos on servers.

### 5. Verifying Integrity After a Suspected Disk Issue

```bash
git fsck --full --strict        # validates every object hash + link graph
git fsck --unreachable          # shows objects no ref can reach (future gc food)
```

## Common Mistakes

### 1. Believing reset Deletes Commits

```bash
# Bad assumption: "I reset --hard, my work is gone forever"
# Reality: commits are unreachable, reflog retains ~90 days
git reflog                       # find them
git branch rescue HEAD@{1}
```

### 2. Relying on Reflog Forever

Reflogs are local and expire (90 days default). They are a personal safety net, not a backup strategy. Push branches or open draft PRs for anything valuable.

### 3. Confusing amend/rebase Signatures With Immutability

Rewriting creates brand-new objects with new SHAs. Anyone who based work on the old SHAs must rebase; signed commits lose their valid signatures because the signed bytes changed.

### 4. Running Aggressive GC on Active Feature Repos "To Clean Up"

`git gc --aggressive` rewrites delta chains for hours on big repos and can invalidate server-side deltas mid-fetch. Prefer letting auto-gc handle it; intervene only with evidence from `count-objects -v`.

### 5. Editing .git Files by Hand Without Understanding Formats

```bash
# Bad: echo a sha into .git/refs/heads/main with trailing garbage
# Good: use the porcelain that validates
git update-ref refs/heads/main <sha>
```

`update-ref` also takes locks, so concurrent tooling cannot corrupt the ref.

### 6. Treating GitHub as the Source of Truth for History

The remote is a ref holder like any other. Server-side reflogs exist but are an admin feature; recovery windows differ per host. Keep mirrors for anything critical.

## Best Practices

1. **Learn five plumbing commands** (`hash-object`, `cat-file`, `mktree`, `commit-tree`, `update-ref`) — they demystify everything else.
2. **Check `git status` before reset** — know what the index and worktree hold before moving refs.
3. **Prefer `revert` on shared branches**, `reset`/`rebase` on private ones.
4. **Anchor recovered work in a branch immediately** (`git branch rescue <sha>`), then decide later.
5. **Audit size with `count-objects -v` and `verify-pack`** before reaching for destructive history rewrites.
6. **Let auto-gc run**; schedule explicit `gc` only for known-bloat events (post `filter-repo`).
7. **Record reflog knowledge in runbooks** — most "Git ate my code" incidents resolve with two reflog commands.
8. **Use `--force-with-lease` instead of `--force`** — it refuses to overwrite refs you have not fetched, protecting teammates' pushes.

## Performance Considerations

| Operation | Mechanism | Typical cost |
| ---------------------- | ----------------------------------- | ------------------------------- |
| `status` on huge repo | index stat cache, fsmonitor | fast with `core.fsmonitor=true` |
| Checkout/branch switch | rewrite changed blobs only | scales with diff, not repo |
| `git log` | commit-graph file accelerates walks | near-instant with commit-graph |
| Fetch | negotiates haves/wants over packs | network-bound; shallow trims it |
| `gc` on monorepo | full repack | minutes-hours; run off-peak |

Enable the accelerators early: `git config core.commitGraph true && git commit-graph write --reachable`.

## Summary

- Git stores four immutable object types addressed by content hash; identical content deduplicates automatically.
- Branches and tags are tiny ref files; all branch operations are pointer moves plus new objects.
- Packfiles compress objects with deltas; `count-objects`/`verify-pack` expose size problems.
- Reflog is an append-only local journal — the first place to look after any destructive command, expiring in ~90 days.
- `reset` moves a ref (optionally rewriting index/worktree); `rebase` copies commits and moves the ref; `revert` preserves history.
- `.git` is readable documentation once you know the layout; `fsck` verifies integrity end-to-end.

## Cheat Sheet

```text
GIT INTERNALS CHEAT SHEET
════════════════════════════════════════════════════

OBJECT TYPES:
  • blob    file content (address = SHA-1 of content)
  • tree    directory: mode + name + child hashes
  • commit  root tree + parents + author/committer + message
  • tag     annotated/signable wrapper around another object

PLUMBING DEMO PIPELINE:
  git hash-object -w --stdin      create blob
  git mktree                      build tree from listing
  git commit-tree <tree> -m msg   create commit object
  git update-ref refs/heads/x sha anchor a branch

INSPECT:
  git cat-file -p|-t|-s <sha>     print / type / size
  git ls-tree HEAD src/           list a tree
  git rev-parse HEAD~3:path       blob behind an old path
  git diff-tree -r A B            compare two trees

SIZE & HEALTH:
  git count-objects -v            loose vs packed stats
  git verify-pack -v *.idx        biggest objects + delta depth
  git fsck --full                 integrity check
  git gc / git repack -d          compact packs

SAFETY NET:
  git reflog                      every HEAD/ref movement (local, 90d)
  git reset --hard HEAD@{n}       rewind to a logged state
  git branch rescue <sha>         pin recovered work
  git reset --hard ORIG_HEAD      undo a bad rebase

REF MOVES AT A GLANCE:
  commit    branch forward
  reset     branch backward (soft/mixed/hard scope)
  revert    new inverse commit (history intact)
  rebase    copy commits, move branch (new SHAs)

INTERVIEW TIPS:
  • Draw blob→tree→commit graph before answering
  • Say "branches are pointers" out loud
  • Mention reflog expiry when discussing recovery limits
```

# Branching Strategies

A team can say “we use Git Flow” and still ship a hotfix to one customer version while leaving another exposed. A branch model is useful only when everyone knows how a change is reviewed, integrated, released, and carried to supported versions.

## Definition

A branching strategy is a team's agreement about where work branches from, how changes are reviewed and integrated, which lines represent releases, and when branch references are retired.

> **Textbook Definition:** A branching strategy is a version-control policy that defines the topology and lifecycle of development and release branches, together with the rules for integrating, validating, and promoting changes across them.

## First Principles

Each branch name points to a commit. When work is committed on separate branches, their histories can diverge; the longer they evolve independently, the more work is needed to reconcile assumptions and test the result. A product that supports several released versions also needs a safe way to apply fixes without releasing unfinished work.

Choose the policy from three facts: how quickly changes should integrate, what review and CI gates protect integration, and how many released versions still receive fixes. A branch strategy does not by itself define deployment, approval authority, or artifact rollback.

## Choose an integration and release path

| Model | Integration | Release handling |
| ----------------------- | --------------------------------------- | ------------------------------- |
| Trunk-based | Frequent small changes reach trunk | Trunk or short support branches |
| GitHub Flow | Short PR branch → default branch | Separate release policy |
| Git Flow | Features → `develop`; releases → `main` | Hotfixes start from `main` |
| Scoped release branches | Regular work stays on trunk | Patch each supported line |

These labels describe overlapping choices. GitHub Flow describes a pull-request workflow; a team can use it while practicing trunk-based development if its branches are short and changes integrate frequently. Git Flow adds distinct integration and release lines. The original author recommends a simpler flow for continuous delivery and reserves Git Flow for explicitly versioned products or products that support several live versions.

In classic Git Flow, feature branches merge into `develop`; a release branch starts from `develop`, then its finished state is merged and tagged on `main` and merged back into `develop`; a hotfix starts from the production line and returns to both. This is a coordination contract, not behavior enforced by Git. If a team only needs to patch older supported versions, trunk plus scoped release branches may provide that support without a permanent `develop` line.

## Trace one reviewed change

In a pull-request workflow, the local commands create and publish a review branch. The hosting platform performs the protected merge after required reviews and checks pass; the developer does not bypass that policy by pushing directly to `main`.

```bash
# Start from the remote default branch; replace main if the repo uses another name.
git switch main
git pull --ff-only
git switch -c fix/coupon-expiry

# Edit the implementation and its focused test, then run the required checks.
git add src/coupon.ts test/coupon.test.ts
git commit -m "fix: reject expired coupons"
git push --set-upstream origin fix/coupon-expiry

# Open a pull request. Reviewers and CI validate it; the host merges it.
```

The hosting platform may delete the remote branch after merge. The pull request and commit history preserve the review record. Remove the local branch only after confirming the PR merged and that no unique work remains; squash and rebase merges may not make Git consider the branch an ancestor of `main`. Branch protection belongs on the server: require the intended reviews and status checks there, because a local naming convention or hook cannot enforce a shared policy. In trunk-based development, keep changes small enough to integrate frequently; where review branches are used, the trunk-based guidance recommends keeping them to roughly a day or two. Set a limit that matches the team's feedback and release cadence rather than treating that interval as a universal rule.

Feature flags can let incomplete behavior merge while remaining disabled, but they add a second code path. Test the enabled and disabled states, assign an owner, and define when the flag and obsolete path will be removed. A flag is not a substitute for integrating or testing the change.

## Carry fixes to every supported version

Suppose a defect affects the current trunk and two maintained releases. Reproduce it and add a regression test. Agree on the canonical fix, then port only that change to each affected release line. Test each port with that line's dependencies and release checks; the trunk's green result does not prove an older version is safe. If the defect can only be reproduced on an old release, fix it there and forward-port the change to the trunk so future versions do not reintroduce it. See [Rebase & Cherry-Pick](40.6.03-rebase-cherry-pick.md) for commit-porting mechanics.

A just-in-time release branch can also separate a stabilization window from ongoing development. Cut it from a known-good trunk commit or release tag, accept only approved fixes there, and continue normal integration on trunk. Keep the line only while that release is supported. A permanent `develop` branch is not required merely because a team needs maintenance branches.

## Make the release traceable

A branch tip moves; it is not a permanent release identity. Record the exact source commit and built artifact digest for each release, and protect the release tag or ref through the hosting and release systems. `main` need not equal the version currently running in production. Define who can approve backports, which tests run on each maintenance line, how fixes flow forward, and how to roll back the published artifact.

## Summary

Choose a branching strategy from integration speed, review and CI policy, and the number of versions that need support. Keep ordinary work close to the trunk; create release lines only when they isolate a real support or stabilization need. Protect integration on the host and record the commit and artifact that were released.

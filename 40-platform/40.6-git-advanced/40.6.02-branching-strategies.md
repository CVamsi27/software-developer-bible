# Branching Strategies

## Definition

A branching strategy is a framework that defines how branches are created, named, merged, and deleted in a version control system. It provides a structured approach to managing parallel development, releases, and collaboration.

> **Textbook Definition:** A branching strategy defines how a team isolates changes, integrates work, maintains release lines, and governs branch lifetime in a version-controlled repository.

## First Principles

Developers need to isolate unfinished changes while shipping a reviewed version. Isolation creates divergence: two changes that work independently can conflict when combined. Supported older releases create another constraint: a fix may need to be replayed and tested on several dependency sets. A strategy must therefore define when integration happens, which release lines remain supported, and who owns conflicts and backports.

## How the common strategies answer those constraints

| Strategy | Integration path | Main cost to manage |
| ----------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| GitHub Flow | Short topic branch → reviewed main | Keep main releasable and changes reviewable |
| Trunk-based development | Frequent small integration, often through short reviewed branches | Strong checks and temporary feature flags |
| Git Flow | Features → develop → release/main, with hotfix return paths | More long-lived integration lines and backport coordination |
| Scoped release branches | Integration plus supported release lines | Define which fixes belong on each supported line |

These are conventions for refs and reviews, not deployment commands. A mobile support window or multiple customer versions can justify release branches without adopting every Git Flow branch. Team size alone does not choose the model.

The command sequences below illustrate separate ref workflows after edits are staged. Use required host reviews/checks for protected integration; do not execute all examples as a single script.

## Code Examples

### Git Flow

```bash
# Start a new feature
git checkout develop
git checkout -b feature/user-authentication

# Work on feature
git add .
git commit -m "feat: add login form"

# Finish feature
git checkout develop
git merge --no-ff feature/user-authentication
git branch -d feature/user-authentication

# Start release
git checkout -b release/1.0.0 develop

# Finish release
git checkout main
git merge --no-ff release/1.0.0
git tag -a v1.0.0 -m "Release 1.0.0"
git checkout develop
git merge --no-ff release/1.0.0

# Hotfix
git checkout main
git checkout -b hotfix/fix-security-issue
# Edit and stage the specific fix before committing
git commit -m "fix: security vulnerability"
git checkout main
git merge --no-ff hotfix/fix-security-issue
git tag -a v1.0.1 -m "Release 1.0.1"
git checkout develop
git merge --no-ff hotfix/fix-security-issue

```

### GitHub Flow

```bash
# Create feature branch
git checkout main
git checkout -b feature/add-shopping-cart

# Make changes
git add .
git commit -m "feat: implement shopping cart"

# Push and create PR
git push origin feature/add-shopping-cart
# Create Pull Request on GitHub

# After review and approval
git checkout main
git merge feature/add-shopping-cart
git push origin main

# Delete branch
git branch -d feature/add-shopping-cart
git push origin --delete feature/add-shopping-cart

```

### Trunk-Based Development

```bash
# Work directly on main (or short-lived branches)
git checkout main

# Make small, frequent commits
git add .
git commit -m "refactor: extract validation logic"

# Push frequently
git push origin main

# For larger changes, use short-lived branches
git checkout -b feature/add-payment-integration
# Work for 1-2 days max
git push origin feature/add-payment-integration
# Create PR, review quickly, merge to main

```

### Feature Flags with Branching

```bash
# Feature flag approach
git checkout main
git checkout -b feature/new-checkout-flow

# Implement with feature flag
git commit -m "feat: add new checkout flow with feature flag"

# Merge to main (flag disabled)
git checkout main
git merge feature/new-checkout-flow

# Enable flag when ready
# In code: if (featureFlags.newCheckout) { ... }

```

## Trace an urgent fix across supported versions

Suppose main contains unreleased checkout work, while versions 1 and 2 both need a login fix. Make the fix in the agreed canonical line, review and test it, then backport only that change to each affected supported branch. Record the source commit and test each target's dependencies. Build explicit artifacts from the approved commits; publish and roll back those artifacts through the release workflow. Closing the topic branch does not prove every supported version was fixed.

## Mistakes and best practices

Long-lived branches postpone integration risk instead of removing it. Keep changes reviewable, integrate within a documented target, and assign an owner to unresolved conflicts. Feature flags require both paths to remain tested and a retirement plan; they are not permanent substitutes for integration.

Protect required integration refs server-side, document emergency/backport procedures, and delete merged branch names only after preserving required work. Measure review delay, conflicting integrations, and release recovery rather than judging a strategy by its branch-name diagram.

## Release identity and urgent-fix propagation

A branch tip is mutable; a deployment should record the built commit and artifact digest. `main` need not equal the currently running version. Release branches keep supported lines separate, but fixes must flow back to the integration branch and all affected supported lines. Test each backport under its own dependencies.

The command sequences above illustrate branch/ref mechanics after changes are staged. On a protected host, merge through the required review/check path rather than bypassing it with a local push to main. Feature flags separate release from integration only when both paths remain tested and flag retirement has an owner.

## Summary
Branching strategies are essential for managing code changes in teams. Choose a strategy based on your team size, release cadence, and deployment process. Common strategies include Git Flow, GitHub Flow, and trunk-based development. The key is consistency and team alignment.

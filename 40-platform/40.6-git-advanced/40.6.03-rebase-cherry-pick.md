# Rebase & Cherry-Pick

## Definition

- **Rebase**: A Git operation that reapplies commits on top of another base tip, usually replaying a selected commit sequence; merge-preserving modes also exist
- **Cherry-pick**: A Git operation that applies a specific commit from one branch to another

> **Textbook Definition:** Rebase reapplies commits onto a chosen base, generally creating new commit identities. Cherry-pick applies the change introduced by a selected commit to the current branch, also generally creating a new commit.

## First Principles

Two branches can contain independently useful changes but different parents and dependencies. Bringing a selected change into another line requires applying it to that line's state and testing the result. Because parent references are part of commit content, changing ancestry creates new commit identities; it cannot mutate the original objects. Existing consumers may depend on the old identities, so coordinate the history contract before replacing a published series.

## Why replay selected changes?

A release branch may need a security fix without unrelated features. A feature author may want to present their patch series against today's integration tip. Cherry-pick serves the first case; rebase serves the second. Neither operation proves the result behaves correctly on its new base.

## How It Works

### Rebase Flow

```text
Before: A--B--C--D       main
            \--E--F--G   feature
After:  A--B--C--D--E'--F'--G'   feature (main still names D)
```

### Cherry-Pick Flow

```text
Before: A--B--C--D       main
            \--E--F--G   feature
After:  A--B--C--D--E'   main
            \--E--F--G   feature (unchanged)
```

## Code Examples

### Basic Rebase

```bash
# Rebase feature branch onto main
git checkout feature
git rebase main

# Resolve conflicts during rebase
# After resolving conflicts:
git add <resolved-paths>
git rebase --continue

# Abort rebase if needed
git rebase --abort

# Skip a commit during rebase
git rebase --skip

```

### Interactive Rebase

```bash
# Interactive rebase last 3 commits
git rebase -i HEAD~3

# In editor:
pick abc1234 First commit
pick def5678 Second commit
pick a1b2c3d Third commit

# Commands:
# pick = keep commit as is
# reword = change commit message
# edit = amend commit
# squash = combine with previous commit
# fixup = like squash but discard commit message
# drop = remove commit

```

### Rebase vs Merge

```bash
# Merge (preserves history)
git checkout main
git merge --no-ff feature

# Rebase (linear history)
git checkout feature
git rebase main
git checkout main
git merge feature # Fast-forward merge

```

### Cherry-Pick Single Commit

```bash
# Cherry-pick a specific commit
git cherry-pick abc1234

# Cherry-pick multiple commits
git cherry-pick abc1234 def5678 a1b2c3d

# Cherry-pick range of commits
git cherry-pick abc1234..a1b2c3d

# Cherry-pick without committing
git cherry-pick --no-commit abc1234

```

### Cherry-Pick from Another Branch

```bash
# Cherry-pick from specific branch
git cherry-pick feature~2 # Ancestor two first-parent edges behind feature
git cherry-pick feature^ # First parent of feature tip

# Cherry-pick merge commit
git cherry-pick -m 1 <merge-commit-hash>

```

### Squash Commits

```bash
# Interactive rebase to squash
git rebase -i HEAD~5

# Mark commits to squash
pick abc1234 Feature commit 1
squash def5678 Feature commit 2
squash a1b2c3d Feature commit 3

# Or use squash flag directly
git merge --squash feature
git commit -m "Feature: combine all changes"

```

### Rebase with Upstream

```bash
# Rebase onto remote main
git fetch origin
git rebase origin/main

# Rebase with autostash
git rebase --autostash origin/main

# Set upstream tracking
git branch --set-upstream-to=origin/main feature

```

### Disaster Recovery with Git Reflog

```bash
# View recent HEAD movements and commit SHA changes
git reflog

# Output example:
# a1b2c3d HEAD@{0}: rebase (finish): returning to refs/heads/feature
# 4e5f6a7 HEAD@{1}: rebase (pick): Feat: add user payment service
# 9a8b7c6 HEAD@{2}: checkout: moving from main to feature
# 1a2b3c4 HEAD@{3}: commit: Feat: add initial payment logic (before rebase)

# Preserve a verified pre-rebase commit without changing the checkout
git branch rescue-before-rebase <verified-pre-rebase-object-id>

# Only after coordinating/authorizing the rewrite and reviewing the remote tip:
git push --force-with-lease=refs/heads/feature:<reviewed-remote-object-id> origin feature
```

## Inspect the selected range and rewritten result

`A..B` excludes A and includes commits reachable from B but not A. Inspect it with `git log --oneline A..B` before cherry-picking. `--skip` discards the current selected change; it is not a generic conflict resolution. `--autostash` can conflict while restoring saved changes after a successful rebase.

A merge cherry-pick's `-m 1` selects the parent relative to which the change is computed; it does not recreate the original merge ancestry. Rebase may omit already-applied patches or flatten merges unless the selected options preserve them. Compare old/new ranges with `git range-diff` and run relevant behavior checks after conflict resolution.

During a rebase conflict, “ours” is the rebased/upstream side and “theirs” is the replayed commit, which can feel reversed from ordinary branch merge intuition. Inspect the actual content rather than blindly choosing a side.

## Real-World Use Cases

1. **Keeping feature branches updated**: Rebase feature onto main regularly
2. **Applying hotfixes**: Cherry-pick fix to multiple release branches
3. **Cleaning up history**: Interactive rebase before merging
4. **Selective feature deployment**: Cherry-pick specific features
5. **Release management**: Cherry-pick only needed commits to release

## Common Mistakes

| Mistake | Risk / Root Cause | Proper Git Workflow |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Rebasing shared public branches (`main`, `develop`) | Rewrites commit SHAs; forces teammates into divergent history requiring coordinated repair | Only rebase personal feature branches; use merge or fast-forward for shared branches |
| Using raw `git push --force` after a rebase | Overwrites teammate commits pushed to remote branch during your rebase | Use an explicit expected remote tip when a rewrite is authorized; implicit leases can be weakened by background fetches |
| Panicking during conflicts and deleting the branch | Forgetting that a rebase can be safely halted at any step | Run `git rebase --abort` to return cleanly to the pre-rebase branch state |
| Losing commits during an interactive squash or rebase | Misconfigured squash/drop commands in the interactive TODO list | Inspect `git reflog` and reset back to pre-rebase pointer (preserve the verified pre-operation commit with a rescue branch before considering a reset) |
| Cherry-picking a merge commit without parent flag | Git fails because a merge commit has multiple parents and diff is ambiguous | Specify parent number via `-m 1` (mainline parent) or avoid cherry-picking merges |
| Rebasing with dirty unstaged changes in working tree | Git refuses to rebase or conflicts with unstaged files | Preserve or commit required work first; autostash restoration can still conflict |

## Best Practices

1. **Rebase local branches only**: Coordinate any rewrite of history others may use
2. **Use interactive rebase for cleanup**: Before merging feature branches
3. **Cherry-pick carefully**: Ensure context is correct
4. **Test thoroughly**: After any rebase or cherry-pick
5. **Communicate with team**: When rewriting history
6. **Use autostash**: For convenience during rebase
7. **Keep commits atomic**: Easier to cherry-pick
8. **Document cherry-picks**: Track applied commits

## Performance Considerations

- **Rebase**: Can be slow with many commits
- **Cherry-pick**: Fast for individual commits
- **Interactive rebase**: Requires manual intervention
- **Conflict resolution**: Can be time-consuming
- **Large repositories**: Ensure required ancestry exists; shallow boundaries can prevent the needed operation

## Summary
Rebase and cherry-pick are powerful Git operations for managing history and applying specific changes. Rebase creates clean, linear history while cherry-pick allows selective commit application. Use them carefully, especially on shared branches, and always test after applying these operations.

# Rebase & Cherry-Pick

A fix is ready on the current release, but an older supported version still has the same defect. You need the fix on that older line without bringing along unrelated work. In another situation, your feature branch needs the latest integration changes before review. Cherry-pick and rebase solve these different problems by replaying changes onto a destination.

## Definition

Rebase replays a branch's selected commits onto a different base; cherry-pick applies the change from selected commits to the current branch. Replayed or copied commits usually get new identities, and neither operation proves that the result works on its destination line.

> **Textbook Definition:** Rebase selects commits that are not represented in an upstream history and reapplies them, in sequence, onto a chosen base. Cherry-pick applies the change introduced by one or more existing commits relative to their parents, normally recording new commits on the current branch. They can reproduce the intended file changes, but they do not preserve the original ancestry.

## First Principles

A commit stores a snapshot, its parent commit IDs, and metadata. Changing the parent changes the commit object and its ID even when the file changes look identical. Rebase changes ancestry; cherry-pick copies a patch to a different ancestry. Neither operation edits the source object in place, but either can make later comparison and collaboration harder if people still depend on the old branch history. Unreferenced objects can later be pruned. A signature covers a specific commit object, so an old signature does not authenticate the rewritten or copied commit; re-sign the new commit if repository policy requires it.

| Need | Operation | Result |
| ----------------------- | ----------- | ----------------------------- |
| Update a private branch | Rebase | Replay commits on a new base |
| Backport one fix | Cherry-pick | Apply its patch on the target |
| Integrate shared work | Merge | Preserve shared ancestry |

Use rebase when you own the topic branch and want its patch series based on a newer integration tip. Use cherry-pick when one reviewed change belongs on a separate maintained line. Use merge when shared history must remain visible; team policy and release needs decide which integration path is allowed. See [Branching Strategies](40.6.02-branching-strategies.md) for choosing that policy.

Start with a clean worktree and review the commit range before replaying. Rebase's `--autostash` can save local changes temporarily, but restoring them can conflict after a successful rebase; it does not remove the need to inspect local work.

## Rebase a private feature branch

Before rebase, `main` has advanced from `B` to `D`, while the feature branch contains `E` and `F` from `B`:

```text
      C---D  main
     /
A---B
     \
      E---F  feature
```

Rebasing the feature branch onto `main` replays its commits on `D`:

```text
A---B---C---D---E'---F'  feature
            |
            main
```

`E'` and `F'` have new IDs because their parents changed. Rebase moves the feature ref; it does not mutate the original commit objects. The old commits remain reachable if another ref, such as the backup below, points to them. Otherwise, a reflog may make them recoverable for a limited time; see [Git Internals](40.6.01-git-internals-objects-refs-packfiles.md).

```bash
git fetch origin
git switch feature/coupon-expiry

# Save the old tip so the original patch series remains easy to inspect.
old_base=$(git merge-base HEAD origin/main)
old_tip=$(git rev-parse HEAD)
git branch backup/feature-before-rebase

git rebase origin/main
git range-diff "$old_base..$old_tip" "origin/main..HEAD"
```

The first range records the commits that were on the branch; the second is the rewritten series on the new base. Review the range-diff for dropped or changed patches, then run the feature's tests against the new base. Rebasing may omit patches Git recognizes as already present. By default, merge commits are flattened; `--rebase-merges` can recreate merge structure with new commit identities when that topology matters.

If one unfinished feature is based on another and only the dependent feature should move to `main`, `--onto` selects the commits unique to the dependent branch and changes their base:

```bash
# feature-b was created from feature-a; move only feature-b's commits onto main.
git rebase --onto origin/main feature-a feature-b
```

The second argument identifies the old base boundary; the third names the branch to update. Inspect both branches first, because commits in `feature-b` that are not reachable from `feature-a` are selected for replay.

For private cleanup, `git rebase -i <base>` opens a todo list. `pick` keeps a commit, `reword` changes its message, `edit` stops for amendment, `squash` combines changes and messages, `fixup` combines changes while discarding the later message, and `drop` removes a commit. A `--fixup` commit plus `git rebase -i --autosquash <base>` places targeted cleanup beside its target automatically. Review the final range and tests; never use this to rewrite history others are using without agreement. Cherry-pick's `--ff` is an exception to its usual new-commit behavior: Git can fast-forward to the original commit when it is already a direct child of `HEAD`.

During a conflict, inspect the stopped commit and actual file contents instead of trusting the labels `ours` and `theirs`: with rebase's default merge backend, “ours” is the new base plus commits already replayed, while “theirs” is the commit currently being replayed. After editing and testing the intended result, stage only the resolved paths and continue. `--skip` discards that commit's replay; it is not another way to mark a conflict resolved. `--abort` returns the branch to its pre-rebase state.

| Operation stopped on conflict | Inspect | Continue | Cancel |
| ----------------------------- | --------------------------- | ---------------------------- | ------------------------- |
| Rebase | `git show REBASE_HEAD` | `git rebase --continue` | `git rebase --abort` |
| Cherry-pick | `git show CHERRY_PICK_HEAD` | `git cherry-pick --continue` | `git cherry-pick --abort` |

Edit and test the intended result, then stage only resolved paths before continuing. `--skip` drops the current commit's replay from a rebase or cherry-pick sequence; choose it only after confirming that the change is unnecessary. A rebase's `ours`/`theirs` labels differ from ordinary branch-merge intuition, so inspect the actual sides rather than resolving by label alone.

If you already published the topic branch, rewriting it changes what collaborators see. Coordinate first and never rewrite a shared integration branch. When policy permits updating the published topic branch, capture the remote tip after fetching and use an explicit lease; it rejects the push if that exact remote ref changed in the meantime.

```bash
git fetch origin
expected=$(git rev-parse refs/remotes/origin/feature/coupon-expiry)
git push --force-with-lease=refs/heads/feature/coupon-expiry:$expected origin HEAD:refs/heads/feature/coupon-expiry
```

## Backport one fix with cherry-pick

Suppose `fix-commit` contains a reviewed, self-contained correction on the current line. Start a review branch from the maintained release, apply that commit's change, and validate it with that release's dependencies and checks.

```bash
git fetch origin
git switch -c backport/coupon-expiry-2.4 origin/release/2.4
fix_commit=0123456 # replace with the reviewed fix commit ID; use an unambiguous ID
git cherry-pick -x "$fix_commit"

# Run the release-specific tests now; push only after they pass.
git push --set-upstream origin backport/coupon-expiry-2.4
# Open a pull request targeting release/2.4.
```

`-x` adds the source commit ID to the message for a clean cherry-pick, making cross-branch traceability easier. A cherry-pick copies the selected patch, not its prerequisite commits or original ancestry. Inspect the source diff and dependency chain first; apply prerequisite commits in dependency order or make the fix self-contained. Run the target release's tests because a patch that passed on the current line can still fail against older APIs, schemas, or dependencies.

For a range such as `A..B`, Git selects commits reachable from `B` but not `A`; inspect the list with `git log --oneline A..B` before replaying it. If order or dependencies matter, cherry-pick the intended commits explicitly in dependency order. A merge commit has multiple parents, so `git cherry-pick -m 1 <merge>` means “compute the change relative to parent 1”; it does not recreate the merge ancestry and may include more changes than the desired fix. Prefer the original focused commit when possible.

If a patch is already present, the cherry-pick may become empty or conflict. Verify whether the intended behavior is actually in the target before skipping or dropping it. On a conflict, inspect `CHERRY_PICK_HEAD`, resolve and test the result, then continue; `--abort` returns to the state before the cherry-pick sequence. Test the complete target branch, not only the lines changed by the patch.

## Summary

Rebase a private patch series when you deliberately want new ancestry; cherry-pick a reviewed, preferably self-contained patch when a different release needs it. Both replay changes rather than transferring original ancestry. Compare rewritten patches, preserve provenance for backports, resolve conflicts by inspecting the actual change, and run the destination line's checks before merging.

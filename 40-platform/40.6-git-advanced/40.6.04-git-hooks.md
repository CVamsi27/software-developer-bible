# Git Hooks

## Definition

Git hooks are scripts that run automatically when specific Git events occur (commit, push, merge, etc.). They allow you to enforce policies, automate tasks, and integrate with other tools.

> **Textbook Definition:** Git hooks are event-associated executable programs that extend repository operations locally or on a server; their authority and bypass behavior depend on where and how they run.

## First Principles

A check protects an operation only where it actually executes and where failure can stop that operation. A local hook may be absent, modified or bypassed, so shared policy needs a trusted server/host gate. Post-operation hooks cannot retroactively reject a completed commit or push.

The staged snapshot can differ from files on disk. A linter over the worktree is useful feedback, but it does not prove the exact committed bytes passed when a file is only partially staged.

## Follow a commit and a push through their gates

```text
commit: pre-commit -> prepare-commit-msg -> commit-msg -> commit -> post-commit
push:   local pre-push -> server pre-receive/update -> accepted refs -> post-receive
```

Git uses executable hook files in its hooks directory, or the configured `core.hooksPath`. Discover paths through Git in linked worktrees rather than assuming `.git` is a directory. A clone transfers tracked hook configuration/code but does not automatically install or trust executable local hooks.

`--no-verify` can bypass specific pre-commit/commit-msg/pre-push hooks; it is not a universal switch for every hook. Server/host required checks still apply. Hook installation itself runs repository code, so review the source and dependency lifecycle before enabling it in an untrusted checkout.

## A complete commit-message hook

Save this as the configured executable `commit-msg`. It checks only the first subject line under a small local policy; bodies remain allowed. It is not a full Conventional Commits parser or proof that the change is correct.

```sh
#!/bin/sh
subject=$(sed -n '1p' "$1") || exit 1
if ! printf '%s\n' "$subject" | grep -Eq '^(feat|fix|docs|test|chore|ci|build|refactor|perf)(\([A-Za-z0-9_-]+\))?!?: .+'; then
  echo 'Expected type(scope): subject, with optional !' >&2
  exit 1
fi
if [ "${#subject}" -gt 100 ]; then
  echo 'Subject exceeds local 100-character policy' >&2
  exit 1
fi
```

A body containing a valid-looking line must not rescue an invalid subject. Failure status must reach Git; catching a failed test and later exiting zero defeats the gate. A basic pre-push command can be `npm test || exit 1`, but required CI must independently test the reviewed commit/merge result.

## Managed installation and staged checks

With current Husky, install the reviewed package and initialize its tracked hooks:

```bash
npm install --save-dev husky
npx husky init
```

Inspect the generated `prepare` script and `.husky/pre-commit`; edit tracked hook files directly. Historical `husky install` and `husky add` recipes are not the current initialization path. Use the installed version's documentation and lockfile, rather than copying arbitrary old dependency versions.

A supported staged-file runner can lint selected paths and manage partially staged content according to its documented options. Use NUL-safe file handling for filenames with spaces/newlines. Formatting changes must be staged deliberately; “tests ran” is insufficient if the final index was never tested. Keep local checks proportionate and move full integration/security gates to the shared boundary.

## A complete server gate for a narrow ref policy

On a self-hosted test server, this executable `pre-receive` rejects all changes to the named refs. It intentionally permits other ref creation/deletion and does not inspect object sizes. It cannot identify a “pull request merge” by magic; a real host needs authorized merge identities/rules.

```sh
#!/bin/sh
while IFS=' ' read -r old_oid new_oid refname; do
  case "$refname" in
    refs/heads/main|refs/heads/develop)
      echo "Updates to $refname require the configured integration path" >&2
      exit 1
      ;;
  esac
done
exit 0
```

Pre-receive receives old/new object IDs and ref names for the push; creation/deletion uses a zero ID on one side. A validator that diffs every pair without handling those cases fails valid operations. Inspect newly introduced reachable commits/blobs, not just endpoint diffs, when enforcing historical size or secret rules. Pipelines spawning subshells can lose an inner `exit 1`; test rejection at the real push boundary.

## Keep automation within its authority

A keyword grep for “token” both flags ordinary code and misses many real secrets. Use a supported scanner against the intended staged/introduced history, then rotate exposed credentials: removing a file does not revoke it. Do not print matched secrets in hook output.

Post-merge can remind a developer to install dependencies; automatically running arbitrary migrations/deployments with local credentials changes a different environment and needs its own controlled workflow. Post-receive notification/deployment runs after accepted refs and cannot make the original push atomic with those effects.

## Validate and operate hooks

Test missing executable permission, configured hook paths, subject/body differences, failing subprocesses, ref creation/deletion and multi-ref rejection. Record what is advisory versus required. A hook bypass should be an explicit documented local exception; production policy must remain enforced at integration.

## Summary

Hooks give timely feedback at named Git events. Match checks to the staged/introduced content, propagate failures, and handle real ref updates. Use local hooks for convenience and trusted shared gates for policy; post-operation automation has a separate effect boundary.

# Git Hooks

A formatter passes on a developer's laptop, but the commit contains different bytes because the file was only partly staged. Another developer can skip a local hook entirely. Hooks are useful only when they check the right snapshot at a boundary that has authority to stop the operation.

## Definition

A Git hook is an executable program Git runs at a named event, such as preparing a commit, pushing refs, or receiving them on a server. A hook can reject an operation only if it runs before the operation completes and exits unsuccessfully; where it runs determines which changes and policies it can enforce.

> **Textbook Definition:** Git hooks are event-associated programs invoked by Git with operation-specific arguments, environment and input. Their ability to modify or reject an operation depends on the hook's lifecycle position and execution context.

## First Principles

The index is the exact snapshot a commit records. The worktree may contain both staged and unstaged edits, so a linter that reads only files on disk can check bytes that will not be committed. At a push boundary, the server sees proposed ref updates and their commit histories, not the developer's entire working tree. Run fast checks locally for feedback, then enforce required policy in trusted CI or at the receiving host. A post-operation hook can notify or start follow-up work, but it cannot retroactively reject a completed commit or push.

## 1. Follow the Operation to the Right Hook

```text
ordinary commit: pre-commit -> prepare-commit-msg -> commit-msg -> create commit -> post-commit
merge commit:    pre-merge-commit runs instead of pre-commit
push:            client pre-push -> server pre-receive -> per-ref update -> accept refs -> post-receive
```

`pre-commit` can test staged content before a regular commit; `commit-msg` can validate its proposed subject and body. `pre-push` can stop the client's push. On the receiver, `pre-receive` runs once for the whole push and can reject every proposed ref; `update` runs once per ref and can reject refs independently. `post-receive` runs only after at least one ref has been accepted and cannot change that result.

Git reads hooks from `$GIT_DIR/hooks` or the configured `core.hooksPath`; a hook without its executable bit is ignored. A clone does not copy custom files from its source repository's `.git/hooks`. Projects can track hook scripts and install them through a tool, but that setup remains local and can be disabled or changed. `git rev-parse --git-path hooks` shows the default Git directory path; a configured `core.hooksPath` overrides it, and `git config --show-origin` shows where that override came from. These commands work without assuming `.git` is a directory:

```bash
git rev-parse --git-path hooks
git config --show-origin --get core.hooksPath || true
```

Some `--no-verify` options skip client hooks such as `pre-commit`, `commit-msg`, or `pre-push`; `prepare-commit-msg` is not bypassed by that option. A user can still remove, change, or disable local hooks, so they are feedback — not shared enforcement.

## 2. Check the Exact Commit Locally

A small `commit-msg` hook can enforce a project's message rule. This example checks only the first line and a local 100-character limit; it is intentionally not a complete Conventional Commits parser. Save it as the configured executable hook:

```sh
#!/bin/sh
subject=$(sed -n '1p' "$1") || exit 1
if ! printf '%s\n' "$subject" | grep -Eq '^(feat|fix|docs|test|chore|ci|build|refactor|perf)(\([A-Za-z0-9_-]+\))?!?: .+'; then
  echo 'Expected type(scope): subject, with optional !' >&2
  exit 1
fi
if [ "${#subject}" -gt 100 ]; then
  echo 'Subject exceeds local 100-character policy' >&2
  exit 1
fi
```

Because it reads the message file's first line, a valid-looking body cannot rescue an invalid subject. For a shared Conventional Commits policy, use a maintained parser such as commitlint rather than extending a regular expression.

For staged-file checks in a JavaScript project, Husky can install a tracked `pre-commit` entry point and lint-staged can select the staged paths:

```bash
npm install --save-dev husky lint-staged
npx husky init
```

After initialization, set `.husky/pre-commit` to run `npx lint-staged` and add a project-specific configuration such as:

```json
{
  "lint-staged": {
    "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"]
  }
}
```

Current Husky uses `husky init`; older `husky install`/`husky add` instructions are version-specific. Review the generated `prepare` script and lockfile, and use your package manager's equivalent commands if the project does not use npm. By default, lint-staged targets staged files, hides unstaged hunks from partially staged files while tasks run, and stages task changes. Inspect both `git diff --cached` and `git diff` afterward; fixers can change what will be committed.

## 3. Enforce a Ref Policy on the Receiver

For a self-hosted bare repository, this executable `pre-receive` rejects a push if it proposes changing `main` or `develop`:

```sh
#!/bin/sh
while IFS=' ' read -r old_oid new_oid refname; do
  case "$refname" in
    refs/heads/main|refs/heads/develop)
      echo "Updates to $refname require the configured integration path" >&2
      exit 1
      ;;
  esac
done
exit 0
```

Git calls `pre-receive` once with one input line per proposed ref. Returning nonzero rejects the entire push, including other refs in that same transaction. With a normal non-atomic push, the per-ref `update` hook can reject one ref while allowing others; `git push --atomic` deliberately makes the ref set all-or-nothing. A new or deleted ref has an all-zero object ID on one side, so validators that inspect ancestry must handle both cases. Server hooks execute in the bare repository's Git directory, not in an application worktree; run builds and integration tests in CI. Hosted platforms usually express protected-branch policy through their own review and required-check settings.

## 4. Keep Follow-Up Work Inside Its Boundary

Scan staged or newly introduced objects with a maintained secret scanner rather than grepping for words such as "token." Do not print a matched secret; rotate exposed credentials because deleting the file does not revoke them. A post-merge hook may remind a developer to install dependencies, while deployments and migrations belong to controlled workflows with their own credentials and audit trail. A failed post-receive notification does not undo refs already accepted.

Test the hook at the boundary it claims to protect: valid and invalid subjects, a good-looking body with a bad subject, a failing subprocess, a hook without execute permission, ref creation/deletion, mixed-ref pushes, and failure behavior after acceptance. Record which checks are advisory, which are required, and how emergency bypasses are audited.

## Summary

Hooks provide fast feedback at named Git events, but their authority comes from when and where they run. Check the staged snapshot for commit-time feedback, inspect proposed refs on the server, propagate failures, and keep post-operation effects separate from acceptance. Enforce shared policy in CI or at a trusted host because local hooks can be bypassed.

# Git Advanced Commands

A release regression has appeared, but the last known-good version is dozens of commits behind. You also have unfinished work in your checkout. You need to find the change without losing your work, then decide whether the fix belongs in shared history. Git’s advanced commands make those decisions explicit: they inspect saved history, preserve local state, and choose how references and files move.

## Definition

In practice, these commands help you investigate a change, recover a recorded commit, isolate parallel work, or restore an external dependency to its reviewed version.

> **Textbook Definition:** Advanced Git operations inspect the commit graph, manage local reference history and working state, or select external repository revisions. Their effects differ across committed objects, references, the index, and the working tree.

## First Principles

Git separates saved objects from the names that point to them and from edits that have not been committed. A moved branch can often be recovered if its previous commit and local reflog entry still exist; bytes that were never saved are outside that recovery path. A history search is only as trustworthy as its test: every candidate must be judged against the same observable property.

## Find which change introduced the regression

`git bisect` narrows the commits between a known-good and known-bad revision by repeatedly checking out a midpoint. It works for any property that changes once along the history being searched, not only a bug: for example, the first revision that exceeds a latency threshold. Define one reproducible test and confirm both endpoints before starting.

```bash
git bisect start
git bisect bad <known-bad-revision>
git bisect good <known-good-revision>
# Run the same reproduction on each checked-out revision.
git bisect good # if the property is absent
git bisect bad  # if the property is present
git bisect log > /tmp/bisect.log
git bisect reset
```

For an automated test, `git bisect run ./scripts/check-regression.sh` interprets exit `0` as good, `1`–`127` except `125` as bad, and `125` as untestable. Any other exit aborts the search. Make the script distinguish the target failure from setup problems: if an old revision cannot install dependencies or build, return `125` rather than falsely labeling it bad. Skipped commits near the transition can leave more than one possible first-bad commit. When the question is which merge introduced the issue on the integration line, `git bisect start --first-parent` searches that first-parent path; it intentionally ignores commits reachable only from merged side branches. See the [bisect manual](https://git-scm.com/docs/git-bisect).

## Recover a commit after moving a branch

Suppose a reset or rebase moved a branch, and a commit seems to have disappeared. A reflog records recent local updates to references, including `HEAD` movements when switching branches. Inspect a candidate before creating a durable name for it:

```bash
git reflog --date=relative
git show <candidate-commit>
git branch rescue/incident <candidate-commit>
```

The rescue branch keeps that commit reachable while you inspect or cherry-pick its changes. Reflogs are local records, not shared history or backups; retention is configurable, and Git may eventually prune unreachable objects. They cannot restore uncommitted bytes erased from the working tree. If the object is missing, preserve the repository and recover it from a trusted clone or backup instead of assuming the reflog contains the commit itself. See the [reflog manual](https://git-scm.com/docs/git-reflog).

## Preserve unfinished work while changing tasks

For a short interruption, a stash records local changes and returns the checkout toward `HEAD`:

```bash
git stash push -u -m "unfinished checkout fix"
git stash list
git stash show --stat stash@{0}
git stash apply stash@{0}
```

By default, stash saves tracked changes. `-u` also includes untracked files; `-a` includes ignored files. Inspect the saved paths before relying on them. `apply` keeps the entry available while you verify the restored work; a successful `pop` removes it, while a conflicted pop leaves it in the stash. `--index` also tries to restore which changes were staged and can fail when that index state conflicts.

For a longer task or a side-by-side test, use a linked worktree instead of repeatedly stashing:

```bash
git worktree add -b hotfix/issue ../hotfix main
git worktree list
```

Each worktree has its own checkout, index, and `HEAD`, while sharing the repository’s object database and most references. That makes task switching cheap, but it is not an independent backup. Git normally prevents the same branch from being checked out in two worktrees. After preserving any local work, remove a finished linked checkout with `git worktree remove ../hotfix`; use `git worktree prune` to clear stale administrative records after a directory was deleted outside Git. See the [stash](https://git-scm.com/docs/git-stash) and [worktree](https://git-scm.com/docs/git-worktree) manuals.

## Restore the dependency version selected by a repository

A submodule is a separate Git repository checked out inside a superproject. The superproject records a *gitlink*: the exact submodule commit expected at that path. A fresh clone can restore those pinned revisions, including nested submodules, with:

```bash
git submodule update --init --recursive
```

`git submodule update --remote` follows a configured remote-tracking branch instead of the commit recorded by the superproject. That can be useful when intentionally advancing a dependency, but it changes the gitlink that the parent repository must review and commit. CI should use the recorded revision unless the build explicitly tests an update. The referenced repository must still be accessible and contain the required commit. See the [submodule manual](https://git-scm.com/docs/git-submodule).

## Choose how to undo a change

The branch’s audience determines whether to move history or add to it. On a private, unpublished branch, `reset` can move the current branch back; its mode controls how much local state also moves:

| Mode | Branch reference | Index | Tracked working files |
| ------------------- | ---------------- | -------------- | --------------------------------------------- |
| `--soft` | Moves to target | Kept | Kept |
| `--mixed` (default) | Moves to target | Matches target | Kept |
| `--hard` | Moves to target | Matches target | Matches target; may overwrite untracked paths |

On a branch other people have based work on, prefer `git revert <commit>`. It records a new commit that applies the inverse change, preserving the published ancestry. Reverting a merge requires choosing a mainline parent with `-m`; that choice also affects what a later merge can reintroduce. Inspect the merge and its follow-up plan before proceeding. A hard reset can remove tracked files absent from the target and overwrite obstructing untracked files, so save required work first. See the [reset](https://git-scm.com/docs/git-reset) and [revert](https://git-scm.com/docs/git-revert) manuals, and the [Git object model](40.6.01-git-internals-objects-refs-packfiles.md) for how reference movement relates to recoverability.

## Summary

Use bisect to locate a change only when the test classifies every revision consistently. Use reflog to find a previous local reference value, then preserve a verified commit with a branch. Choose stash for a short interruption and worktree for independent parallel checkouts. Restore submodules from the parent’s recorded gitlinks. Move private history with care; add a revert commit when shared history must remain intact.

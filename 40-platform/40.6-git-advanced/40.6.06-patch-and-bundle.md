# Git Patch & Bundle

## Definition

**`git format-patch`** and **`git am`** are Git's email-based patch workflow — the way Linux kernel maintainers, OSS maintainers, and many enterprise teams collaborate. A patch is a unified diff with commit metadata; a bundle carries selected references and their reachable objects, possibly excluding prerequisite history already held by the recipient. Both allow Git changes to be transferred over email, USB drives, or any text channel that Git's HTTP/SSH transport can't reach.

> **Textbook Definition:** A Git patch represents a change with optional commit metadata for application to another history. A Git bundle transports selected references and their required objects, possibly relative to prerequisite commits.

Patches are the lingua franca of OSS contribution. The Linux kernel commonly uses email-based patch review; maintainers may also integrate changes through Git pull requests between trusted trees. Understanding this workflow is essential for contributing to large open-source projects.

## First Principles

A recipient can apply a change without possessing the sender's exact object graph. A patch supplies changed content and optional author/message metadata; applying it normally creates a new commit with the recipient's parent and committer data. A bundle instead transports object identities and advertised refs, subject to any prerequisite history.

Neither representation includes arbitrary working-tree changes, secret-store credentials or hosting configuration. Offline transport must state exactly which information is included and what the recipient already needs.

## Trace one patch series from author to recipient

```bash
# While on a reviewed topic branch based on main:
git format-patch --stdout main..HEAD > review.mbox
# Recipient, on a clean branch with compatible base history:
git am --3way review.mbox
```

Without `--stdout`, format-patch writes patch files and prints their paths. Redirecting that output to `review.patch` stores filenames, not the patch series. Use `-1 <commit>` for one commit or `-o patches` for a directory. A cover letter is introductory text, not another code commit.

`git am` preserves authored metadata/message where supported and creates commits. `git apply` changes the worktree/index under selected options without creating a commit. `--3way` needs relevant base blob identities available locally; it is not guaranteed to resolve every conflict. After a conflict, stage reviewed paths and use `git am --continue`, or abort. Applying a patch still requires tests and review of its trust/domain effects.

## Sign-off, footer and cryptography are different

`git commit -s` or format-patch `--signoff` adds a `Signed-off-by` trailer when the project's contributor policy requires it. It is a textual assertion, not a cryptographic signature. Format-patch `--signature` controls a mail footer. It does not cryptographically sign the patch.

A signed original commit's signature is not automatically preserved by applying its diff to another parent. `git am -S` signs newly created commits with the recipient's configured signing key; there is no `git am --verify-signature` patch-verification option. Verify original signed commits/tags or authenticated mail/attestation through the appropriate tooling and trust policy, then separately verify the resulting imported history.

## Bundle complete versus prerequisite history

```bash
# Run inside a repository; the output goes outside the worktree:
git bundle create ../repo.bundle --all
git bundle verify ../repo.bundle
git clone ../repo.bundle ../restored-repo
```

`--all` selects refs, not all personal work or every unreachable object. A full bundle carries reachable history for selected refs, including notes/stashes when selected; a clone's ordinary ref mapping is still not a full restore of every custom namespace. Check advertised heads and restore required refs explicitly. Git configuration, hooks, local reflogs, LFS payloads and external submodule repositories need separate backup.

```bash
# Requires the recipient to already possess main~2 and its history:
git bundle create ../increment.bundle main~2..main
git bundle verify ../increment.bundle
```

Verification in the sender can pass while an empty recipient lacks prerequisites. Retain/test the base backup chain; an incremental bundle alone cannot bootstrap an empty clone. Inspect `git bundle list-heads` and `git bundle verify` in the actual recipient before relying on it.

## Preserve review order and transport integrity

A series can contain dependencies between patches. Send/apply the complete intended order and compare the imported result, rather than globbing arbitrary mixed revision files. Regenerate revised patches from corrected commits; manual edits can invalidate context/counts. Merge commits are not represented as ordinary replayable patches by default, so select a suitable reviewed series without pretending to preserve merge topology.

Mail delivery through send-email is a separate externally visible action with reviewed recipients/content and configured credentials. Sending only `0000-*` sends the cover letter without the code patches. Offline copying should preserve checksums and verify sender/trust where the threat model requires it.

Do not casually push a restored clone with `--mirror`: it can overwrite/delete destination refs. Plan the exact destination namespace and authorization before publishing restored history. The local bundle exercise does not require publishing anything.

## Summary

Use patches to replay reviewed changes and bundles to transfer selected object history. Separate sign-off/footer from cryptographic signing, verify incremental prerequisites at the recipient, and back up non-Git/LFS/submodule/host state separately.

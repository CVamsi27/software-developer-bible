# Git Patch, Bundle & Archive

An external maintainer needs a reviewable change. A release machine needs the files from one exact tag. A disconnected replica needs commit history. These are different transfer jobs: choosing the wrong format can lose commit context, include a hidden prerequisite, or omit state required to restore the repository.

## Definition

In practice, a patch series sends reviewed changes for replay, a bundle transfers selected Git references and objects, and an archive exports files from a named tree.

> **Textbook Definition:** A Git patch encodes a commit's message, author metadata, and change for application to another history; a bundle packages selected references and reachable objects, with any declared prerequisites; an archive serializes the files in a selected tree without transferring its commit graph.

## First Principles

Each artifact preserves a different boundary. `format-patch` plus `git am` reapplies changes on the recipient's base and creates new commits. A bundle transports existing Git objects, so included commits keep their identities, but an incremental bundle assumes the receiver already has its prerequisite objects. `git archive` is only a snapshot of tracked tree content: it cannot restore branches, commit history, the index, or local changes.

| Artifact | Recipient receives | Best fit |
| ------------ | -------------------------------------------------------------------- | -------------------------------------------------------------- |
| Patch series | One mail-like message and diff per commit | Review or replay a focused change on another compatible base |
| Bundle | Selected refs and reachable Git objects, possibly with prerequisites | Move history to a disconnected repository or preserve Git refs |
| Archive | Files from one tree, filtered by archive attributes | Build or distribute a source snapshot for a release |

## 1. Send a Change Series Without Losing Its Review Context

`git format-patch` creates mailbox messages from non-merge commits. It writes numbered patch files by default; use `--stdout` when you want one mailbox file instead. The series carries changes, not merge topology; choose a bundle when the original commit graph itself must travel:

```bash
# On a topic branch based on main; writes one file per commit.
git format-patch --full-index --output-directory patches main..HEAD

# Alternative: collect the same ordered series in one mailbox file.
git format-patch --full-index --stdout main..HEAD > review.mbox
```

For commits that change binary files, add `--binary`. Keep each commit to one reviewable logical change, and preserve the generated order because later patches may depend on earlier ones. A cover letter describes the series; it is not a code patch. When applying a series, start on a clean branch based on the intended compatible version:

```bash
git switch -c import/topic <compatible-base>
git am --3way ../review.mbox
```

`git am` reads the author, date, subject, message, and diff from each mail. It uses the current repository and committer identity to create commits from the replayed result. Their IDs commonly differ when the parent or committer metadata differs; the original commit object and signature are not transferred. `--3way` can fall back to a merge when the patch does not apply cleanly and the required base blobs are available. If it stops on a conflict, inspect and resolve the files, stage the result, then continue; abort if the patch should not be applied:

```bash
git status
git add <resolved-paths>
git am --continue
# Or, to abandon the series:
git am --abort
```

Use `git apply` when you want patch content in the worktree or index without creating commits. Use `git am` when the mailbox's author and message should become commit metadata. Neither command proves the change is safe: review the diff and run the recipient project's tests.

For an email-based project, `git send-email --annotate --to maintainer@example.org patches/*.patch` reviews and sends the selected patch files. Check the complete recipient list, order, and contents before sending; a cover letter alone does not send the code. Email is one project workflow, not a requirement for every open-source contribution. The [Linux kernel submission guide](https://www.kernel.org/doc/html/latest/process/submitting-patches.html) is a concrete example of a project whose maintainers review inline patch series.

## 2. Separate Sign-Off, Mail Footer, and Cryptographic Signing

Use `--signoff` only when the project's contribution policy asks for a `Signed-off-by` trailer; it records a contributor's textual declaration. The `format-patch --signature` option adds a plain-text footer, commonly the Git version. Neither is a cryptographic signature. `git am --verify` runs local apply-patch hooks; it does not verify a sender's commit signature. If a policy requires cryptographic proof, verify an authenticated original commit, tag, or attestation through the project's trust policy. `git am -S` signs the newly created commit with the recipient's key; it does not preserve or validate the sender's signature.

## 3. Transfer History with a Bundle

A self-contained bundle can seed a disconnected clone:

```bash
# Run inside the repository; --all selects refs, not working-tree state.
git bundle create ../project.bundle --all
git bundle list-heads ../project.bundle
git bundle verify ../project.bundle
git clone ../project.bundle ../restored-project
```

`--all` selects refs and their reachable objects; it does not save the index, working tree, repository configuration, hooks, or reflogs. A stash list depends on the `refs/stash` reflog, so a bundle clone is not a reliable stash restore. In a local Git 2.48 test, `--all` advertised the current `refs/stash`, but cloning the bundle did not recreate that ref or its stash list. The Git manual treats stash as local state outside a bundle backup. Large-file storage and submodule repositories also need separate handling. Inspect `git bundle list-heads`, fetch required custom refs explicitly, and restore a test clone before treating a bundle as a backup.

Git 2.51 added `git stash export` and `git stash import` for transferring stash entries. When both repositories run Git 2.51 or newer, export the stash chain to a ref, bundle that ref, then import it on the receiver:

```bash
# Sender: export all stash entries to a transferable ref, then bundle it.
git stash export --to-ref refs/backup/stash-transfer
git bundle create ../stashes.bundle refs/backup/stash-transfer

# Receiver: fetch the ref from the bundle and import its stash chain.
git bundle verify ../stashes.bundle
git fetch ../stashes.bundle refs/backup/stash-transfer:refs/heads/recovery/stash-export
git stash import refs/heads/recovery/stash-export
```

Check `git --version` on both ends; older versions do not provide `export`/`import`. Test the imported entries before deleting the transferred ref or source backup.

An incremental bundle is smaller because it omits a known base. The named prerequisite must already exist in the recipient:

```bash
# Sender: last-synced must be a commit already held by the recipient.
git bundle create ../updates.bundle last-synced..main

# Recipient: run verification here, then fetch into a reviewable remote ref.
git bundle verify ../updates.bundle
git fetch ../updates.bundle main:refs/remotes/bundle/main
git log --oneline --decorate refs/remotes/bundle/main
```

Running `git bundle verify` only in the sender does not prove the recipient has the prerequisite objects. Verify in the actual target repository before fetching. Verification checks bundle format and required history; it does not authenticate who created the file, so use a trusted transfer and any required checksum or signature policy. Review the fetched commits before integrating them.

## 4. Export Files When History Is Not Needed

For a release source snapshot, archive a commit or tag rather than copying a mutable working tree:

```bash
git archive --format=tar.gz --prefix=app-1.2.0/ v1.2.0 > ../app-1.2.0.tar.gz
```

The archive contains the tree at that tag, not its history or refs. The committed `.gitattributes` may omit files with `export-ignore` or substitute placeholders with `export-subst`; inspect the result against the intended build inputs. If the project uses Git LFS, confirm its release process provides the required LFS payloads separately. See [Git at Scale](40.6.08-git-at-scale-lfs-partial-clones.md) for the pointer/object distinction and the [git-archive manual](https://git-scm.com/docs/git-archive) for archive attributes.

## Summary

Use a patch series to replay a reviewed change, a bundle to transfer selected history, and an archive to export a tree snapshot. Confirm the recipient's base before applying or fetching. Test incremental prerequisites on the recipient. Back up local work, stash entries, hooks, configuration, LFS data, and submodules through mechanisms that preserve and restore each one.

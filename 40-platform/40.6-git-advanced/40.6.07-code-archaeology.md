# Git Code Archaeology

A login regression appears after a deploy. The current code shows what runs now, but it does not explain which change altered the behavior or why that change was accepted. Git history can narrow the investigation; the diff, tests, and linked review evidence establish what the change actually did.

## Definition

In practice, code archaeology is tracing a program's evolution to explain present behavior, locate a change, or test a suspected cause. Git supplies the code history; issues, pull requests, reviews, and release records often supply the missing rationale.

> **Textbook Definition:** Code archaeology is the systematic analysis of source history and associated engineering records to reconstruct how and why software behavior changed, while treating recorded attribution as evidence rather than proof of intent.

## First Principles

A line's last edit, the commit that changed its behavior, and the discussion that justified the change may be three separate events. Start with the observed behavior, follow the evidence backward, and verify the candidate against its parent or a reproducible test. A name beside a line is an attribution field — not a verdict about responsibility.

## How It Works

### 1. Follow the Behavior to Its Change

First define a stable reproduction and the last-known-good revision. Keep the search on the affected path instead of reading the entire repository log:

```bash
# Commits that changed this file between a verified good revision and HEAD.
git log --oneline --decorate <last-known-good>..HEAD -- src/auth/session.ts

# Attribute only the lines involved in the failing behavior.
git blame -L 80,105 HEAD -- src/auth/session.ts
```

`git blame` reports the commit currently associated with each line and normally follows whole-file renames. Open that commit before drawing a conclusion:

```bash
git show --format=fuller --find-renames <commit-from-blame> -- src/auth/session.ts
```

Read the parent-to-commit diff, surrounding code, tests, and message together. A refactor may be the last edit to a line while an earlier change introduced the behavior. Author and committer names and dates are stored metadata; they are not verified identity or evidence of who reviewed the change.

If a mechanical formatting commit obscures the earlier edit, ignore only that known revision for attribution:

```bash
git blame -w --ignore-rev <formatting-commit> -L 80,105 HEAD -- src/auth/session.ts
```

`-w` ignores whitespace differences. `--ignore-rev` tells blame to treat the selected commit as if it had not changed the lines; use it only for a verified mechanical change, or meaningful edits may be hidden. If code moved, `-M` detects moved or copied lines within a file and `-C` also searches other files changed in the same commit. Repeating `-C` widens that search and can cost more:

```bash
git blame -M -C -L 80,105 HEAD -- src/auth/session.ts
```

### 2. Search When the Line Is Gone or Renamed

Blame cannot annotate a deleted line. Search the patch history instead. Use `-S` when you know an exact string and want commits that change its occurrence count; use `-G` when you want commits whose added or removed lines match a regular expression:

```bash
# Find when the exact identifier appeared or disappeared.
git log -S'checkSession' --all --oneline -- src/auth/session.ts

# Find changed lines that match a pattern, even if the match count is unchanged.
git log -G'active.*===' --all --oneline -- src/auth/session.ts
```

Add `-p` to inspect matching patches. Add `--follow` when a single current path must be traced through detected renames. `--all` searches refs already present locally; it does not retrieve deleted remote branches or missing history. Fetch the relevant refs when authorized, and check whether a shallow clone stops before the period in question. In a partial clone, historical content may be fetched lazily from its promisor remote.

When a file was renamed, `git log --follow -- <path>` asks Git to continue one file's history across detected renames. Rename detection is heuristic, and `--follow` works for a single path. To trace how a current function or line range changed, `git log -L` emits its patches:

```bash
git log --follow --oneline -- src/auth/session.ts
git log -L 80,105:src/auth/session.ts
```

`-L` starts from one revision and the range must exist there; it cannot be combined with path limiters. For commit-message references, use `git log --grep='AUTH-431' --all --oneline`. These searches identify candidates, not causes; inspect each relevant diff.

### 3. Confirm the Explanation Outside Git

Git records snapshots, ancestry, and commit metadata. It does not automatically contain the pull request conversation, issue discussion, design decision, deployed configuration, or production trace. Follow ticket identifiers into the review and incident records, compare the relevant tests, and reproduce the behavior under the historical dependency and runtime conditions. Once a deterministic test classifies known-good and known-bad endpoints, use the controlled regression search in [Git Advanced Commands](40.6.05-git-advanced-commands.md).

History can locate when a dependency or credential was introduced, but it cannot establish license compliance or make a leaked secret safe. Verify dependency provenance and notices against the project policy. If a credential reached shared history, rotate it first and follow the coordinated history-remediation process; deleting the current file does not revoke exposed credentials.

## Summary

Begin with a reproducible behavior and a bounded revision range. Use blame to locate a candidate, then inspect its diff and surrounding evidence; use `-S`, `-G`, `-L`, and single-file rename following when line attribution is insufficient. Git history narrows the question, while tests and review records support the conclusion.

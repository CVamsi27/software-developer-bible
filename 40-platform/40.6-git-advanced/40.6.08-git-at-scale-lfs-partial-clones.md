# Git at Scale: LFS & Partial Clones

> When a repository holds gigabytes of binaries or a million files, naive `git clone` collapses. This chapter covers the two escape hatches — **Git LFS** for large blobs and **partial clone / sparse-checkout** for huge trees — plus CI shallow clones and repo-size audits.

## Definition

Git-at-scale tooling changes **what gets downloaded and when**, without changing the commit graph:

| Technique | What it optimizes | Mechanism |
| ------------------------------ | -------------------- | ---------------------------------------------------------------------------------- |
| **Git LFS** | Large binary files | Replaces blobs with pointer files in Git; real content lives on an LFS server |
| **Partial clone** (`--filter`) | Blob download volume | Fetches commits/trees first; downloads blobs lazily on demand (promisor remote) |
| **Sparse-checkout** | Working-copy size | Limits which directories materialize on disk, regardless of history size |
| **Shallow clone** (`--depth`) | History length | Truncates the commit walk to N commits (`--filter` + `--depth` compose) |
| **Scalar** | Everything above | Microsoft's opinionated wrapper enabling all accelerators + background maintenance |

All four keep full-fidelity workflows available while paying only for the data you touch.

```text
NORMAL CLONE                    PARTIAL CLONE (--filter=blob:none)
clone → every blob ever         clone → all commits+trees, zero blobs
checkout → local                checkout → lazy fetch of needed blobs
size ∝ total history            size ∝ trees you browse; misses cost a roundtrip

GIT LFS
repo stores:  version https://git-lfs.github.com/spec/v1
              oid sha256:e0eb42...   ← tiny pointer file (130 bytes)
              size 48211300
LFS store:    actual bytes, fetched by smudge filter on checkout
```

## Why Do We Need It?

1. **Clone time is developer time** — a 5 GB repo costs each new hire an hour and every CI run minutes.
2. **Binaries do not delta well** — videos, models, design assets, datasets bloat packfiles because each version stores near-full content.
3. **Monorepos exceed working-memory limits** — a million-path tree makes `status`, indexing, and globbing slow without sparse checkout and fsmonitor.
4. **CI rarely needs full history** — most pipelines build one commit; `fetch-depth: 1` cuts network transfer by 10-100x.
5. **Hosting limits bite silently** — GitHub blocks repos/packs over ~2 GB per push window; LFS keeps Git payloads small enough to stay under.
6. **Audits prevent recurrence** — size problems are cumulative; teams that measure catch offenders before they land.

## How It Works

### LFS Mechanics: Pointer Files and Filters

LFS is a clean-filter pair wired through `.gitattributes`:

```text
COMMIT PATH                          CHECKOUT PATH
work file (4 GB video)               .gitattributes declares filter=lfs
        │ clean filter runs on add           │
        ▼                                    ▼
store bytes in LFS server            smudge filter replaces pointer
leave pointer blob in Git            with real content from LFS store

.git/objects: 130-byte pointer       disk: real 4 GB file
```

The pointer format is deliberately boring text:

```text
version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b06882dcae35913e34e709f6
size 134218528
```

Setup and day-two operations:

```bash
git lfs install                                   # register filters globally
git lfs track "*.psd" "*.mp4" "assets/**/*.bin"   # writes .gitattributes
git add .gitattributes media/demo.mp4
git commit -m "Track demo video via LFS"

git lfs ls-files                 # what is tracked (shows * = downloaded, - = pointer)
git lfs pull --include="assets/" # fetch only some paths' content
git lfs migrate import --everything --include="*.mp4"
                                 # rewrite history so old mp4s become pointers
```

`migrate import` is the critical step teams skip: tracking a pattern only affects **new** files; historical blobs stay fat until you rewrite.

### Partial Clone: Promisor Remotes

```bash
git clone --filter=blob:none https://github.com/org/monorepo.git
# commits + trees arrive; blobs fetched on demand

git clone --filter=blob:limit=100k ...   # small blobs inline, big ones lazy
```

Internals:

```text
.git/config:
  [remote "origin"]
      promisor = true                     ← marks partial clone
      partialclonefilter = blob:none

First git log -p src/x.ts:
  1. walk local commits/trees             (fast)
  2. miss blob → GET batch from promisor remote
  3. cache fetched blobs locally          (subsequent ops fast)
```

Trade-off: every missed blob is a network roundtrip batched per command — great for `log --stat`, painful for tools that touch everything (`grep` across history).

### Sparse-Checkout: Shrink the Working Copy

```bash
git sparse-checkout init --cone          # cone mode: fast dir-based patterns
git sparse-checkout set services/api packages/ui
ls                                       # only those dirs exist on disk
git sparse-checkout list                 # inspect current set
git sparse-checkout disable              # back to full tree
```

History still contains everything; only the worktree is filtered. Combine with partial clone for maximum effect: no big blobs *and* few directories.

### Scalar and Repo Accelerators

Scalar (shipped inside Git as `scalar`) enables the full checklist and background upkeep:

```bash
scalar clone https://github.com/org/huge.git     # does everything below
# or retrofit:
git config core.fsmonitor true                   # fs-watch daemon for status
git config core.untrackedCache true              # cache untracked listing
git commit-graph write --reachable --changed-paths  # O(1)-ish history walks
git config feature.manyFiles true                # tuned index format flags
git config index.version 4                       # path-prefix compression
git maintenance start                            # background prefetch/gc/commit-graph
```

| Flag | Effect | Typical win |
| --------------------- | ----------------------------------- | ----------------------------- |
| `core.fsmonitor` | daemon answers changed-file queries | `status` 10s → <200ms |
| `commit-graph` | binary commit metadata | `log`/merge-base near-instant |
| `index.version=4` | compressed index entries | smaller/faster index IO |
| `core.untrackedCache` | remember empty/ignored dirs | fewer directory scans |
| `maintenance` | scheduled repack/prefetch | keeps gains without thinking |

### CI Shallow Clones With fetch-depth

```yaml
# GitHub Actions
jobs:
  build:
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 1            # default IS 1 since v2 — be explicit anyway
      # Needs tags for versioning? Trade depth for refs, not history:
      - run: git fetch --prune --unshallow --tags   # only when required
```

```yaml
# GitLab CI
build:
  variables:
    GIT_DEPTH: 1
    GIT_LFS_SKIP_SMUDGE: 1        # skip multi-GB LFS download; pull selectively later
  script:
    - git lfs pull --include="models/current.bin"   # opt-in heavy assets
```

Rules of thumb: shallow by default; unshallow only for changelog generation, blame-aware checks, or merge-base logic; never mix `fetch-depth: 0` with LFS smudge unless the job truly needs both.

### Repository Size Audits

```bash
# 1. Overall shape
git count-objects -vH            # size-pack tells the truth after gc

# 2. Biggest historical blobs
git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  awk '$1=="blob"{print $3, $4}' | sort -rn | head -25

# 3. Structural risk report (Microsoft's git-sizer)
git-sizer --verbose              # flags >4k paths/dir, huge blobs, deep histories

# 4. Per-directory weight at HEAD
git ls-tree -r -l HEAD | sort -k4 -n -r | head -15
```

Remediation ladder: move new binaries to LFS → `git lfs migrate import` for history → `git filter-repo --path <fat-dir> --invert-paths` for outright removal → coordinate force-push + team re-clones.

## Code Examples

### Enforcing an LFS Policy in CI

```typescript
// scripts/check-lfs.ts — fail PRs adding big blobs outside LFS
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const run = promisify(execFile);
const LIMIT = 512 * 1024;

export async function checkBigBlobs(): Promise<void> {
  const { stdout } = await run('git', ['rev-list', '--objects', 'origin/main..HEAD']);
  const shas = stdout.split('\n').map((line) => line.split(' ')[0]).filter(Boolean);

  const { stdout: sizes } = await run('git', [
    'cat-file',
    `--batch-check=%(objectname) %(objecttype) %(objectsize)`,
  ], { maxBuffer: 64 * 1024 * 1024, input: shas.join('\n') });

  const offenders = sizes
    .split('\n')
    .filter((line) => line.includes('blob'))
    .map((line) => line.split(' '))
    .filter(([, type, size]) => type === 'blob' && Number(size) > LIMIT)
    .map(([sha, , size]) => `${sha} (${Number(size) / 1024 | 0} KB)`);

  if (offenders.length) {
    throw new Error(`Blobs >${LIMIT / 1024} KB must use LFS:\n${offenders.join('\n')}`);
  }
}
```

### Sparse-Aware Build Script

```typescript
// Only build services present in this sparse checkout
import { readdirSync, existsSync } from 'node:fs';

export function discoverServices(root = 'services'): string[] {
  if (!existsSync(root)) return [];            // sparse-checkout excluded them
  return readdirSync(root, { withFileTypes: true })
    .filter((e) => e.isDirectory())
    .map((e) => e.name);
}
```

## Real-World Use Cases

### 1. Game Studio With Multi-GB Art Assets

`.gitattributes` tracks `.fbx/.png/.wav`; designers push through LFS; engineers add `GIT_LFS_SKIP_SMUDGE: 1` to their global env and pull only asset folders they edit. Git history stays under 500 MB while the LFS store grows freely.

### 2. 40k-Path Monorepo Onboarding

New hires previously waited 25 minutes for clone plus 90-second `status` loops. Switch to `--filter=blob:none` + cone-mode sparse checkout of their team's service + fsmonitor: clone 3 minutes, `status` sub-second, and cross-team browsing works via on-demand fetch when needed.

### 3. ML Training Repo With Dataset Versioning

Datasets live in LFS with read-only team permissions on the LFS server; training jobs use `git lfs pull --include="datasets/v3/**"` inside ephemeral runners, keeping runner images small and reproducible (dataset identity = commit SHA + pointer OID).

### 4. Release Engineering Needs Tags Without Full History

Changelog job starts from `fetch-depth: 1` then `git fetch --depth=500 origin '+refs/tags/*:refs/tags/*'` — enough history for conventional-commit scanning at 2% of a full clone's cost.

### 5. Quarterly Size Audit Gate

A scheduled workflow runs `count-objects -vH` + top-blobs script on a bare mirror and posts deltas to Slack; any pack growth over 5% triggers investigation before the next quarter's clone pain.

## Common Mistakes

### 1. Tracking LFS Patterns After the Fat Blobs Landed

```bash
# Bad: git lfs track "*.zip" today; yesterday's zips remain full blobs forever
# Good: rewrite so existing objects become pointers
git lfs migrate import --everything --include="*.zip"
```

### 2. Forgetting That LFS Rewrites File Identity

Because smudge/clean replace content, checksums of the *Git* blob are pointer hashes; diff/merge behavior changes (`lfs.diff=...` drivers). Tools hashing raw files must hash the worktree file, not the stored blob.

### 3. Partial Cloning Then Running Full-History Tools Blindly

`--filter=blob:none` + `git grep $(git rev-list --all)` = thousands of lazy fetches. Either accept the cost consciously, `git fetch --refill` up front, or scope tools to current HEAD.

### 4. Shallow Clones Breaking Merge-Base Logic

CI jobs that call `git merge-base origin/main HEAD` can crash with `not a valid commit` when the common ancestor was truncated. Fix: `fetch-depth: 0` for those jobs, or fetch `origin/main` explicitly to sufficient depth.

### 5. Sparse Checkout Without Cone Mode

Legacy (non-cone) patterns use regex-ish `.gitignore`-style rules that scale badly and surprise people. Always `init --cone` unless you have an exotic need.

### 6. Treating Scalar/GC as Set-and-Forget on Shared Servers

Background maintenance on a repo served to many users can hold locks during peak hours. Schedule `git maintenance run --schedule=frequent` windows off-peak on build hosts.

## Best Practices

1. **Default new large repos to `--filter=blob:none`** — full clones should be an explicit choice.
2. **Commit `.gitattributes` early** — policy files prevent accidents better than post-hoc audits.
3. **Pair sparse-checkout with fsmonitor** — either alone helps little on giant trees; together they fix status.
4. **Keep `fetch-depth` explicit in pipeline YAML** even when defaults match intent — reviewers see the decision.
5. **Run `git-sizer` in CI weekly** — structural warnings (path counts, blob sizes) precede user-visible slowness by months.
6. **Document the unshallow commands** your release process needs; tribal knowledge dies at the worst time.
7. **Budget LFS bandwidth** — hosts meter it; aggressive CI smudge of all assets is a common bill shock.
8. **Prefer `filter-repo` over `filter-branch`** for rewrites — faster and far less error-prone (see [Advanced Commands](40.6.05-git-advanced-commands.md)).

## Performance Considerations

| Scenario | Naive cost | Scaled setup |
| ----------------------------------- | ------------------ | ----------------------------------------- |
| Clone 8 GB repo | 8 GB down, 25 min | 400 MB (blob:none), 4 min |
| `git status`, 60k files | 8-15 s | <300 ms (fsmonitor+untrackedCache) |
| CI checkout, 50k commits | full history fetch | `fetch-depth:1`, seconds |
| Blame across renames, monorepo | minutes | seconds with commit-graph + changed-paths |
| LFS checkout of 100 assets serially | slow cold start | parallel: `lfs.concurrenttransfers=8` |

Measure with the audit scripts above before/after; wins are workload-dependent (history-heavy vs worktree-heavy).

## Summary

- LFS moves large blobs out of Git into pointer files backed by an LFS server; `migrate import` is required to shrink history, not just future adds.
- Partial clones fetch commits/trees first and blobs lazily via promisor remotes; combine with sparse-checkout to slim both history and worktree.
- Scalar bundles the accelerator stack: fsmonitor, untracked cache, commit-graph, index v4, background maintenance.
- CI should shallow-clone by default and opt into depth/tags/LFS only where the job proves it needs them.
- Regular audits (`count-objects`, top-blobs script, `git-sizer`) turn repo bloat from folklore into a dashboard metric.
